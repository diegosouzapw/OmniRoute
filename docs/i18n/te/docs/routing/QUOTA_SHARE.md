## అవలోకనం

కోటా షేరింగ్ ఇంజిన్, ఒకే కనెక్షన్ను పంచుకునే అనేక API కీల మధ్య ప్రొవైడర్కు చెందిన సమయ-ఆధారిత కోటాను (ఉదా. Codex
5-గంటల విండో, Kimi 1500 req/h) న్యాయంగా పంపిణీ చేస్తుంది.

**ఇది పరిష్కరించే సమస్య:** OmniRoute ఒకే అప్స్ట్రీమ్ ప్రొవైడర్ ఖాతాకు అనేక API కీలను ప్రాక్సీ చేస్తుంది.
భాగస్వామ్య లాజిక్ లేకుండా, కీ A నుంచి వచ్చే అభ్యర్థనల ఉద్ధృతి ఆ గంటకు సంబంధించిన
ప్రొవైడర్ కోటాను పూర్తిగా వినియోగించగలదు, దీంతో విండో రీసెట్ అయ్యే వరకు కీలు B మరియు C బ్లాక్ అవుతాయి.
ఇంజిన్ దీనిని ఈ విధంగా నివారిస్తుంది:

1. ప్రతి డైమెన్షన్కు (%, అభ్యర్థనలు, టోకెన్లు, $) ప్రతి కీ యొక్క రోలింగ్ వినియోగాన్ని ట్రాక్ చేయడం.
2. పని-సంరక్షణ న్యాయ-వాటా అల్గారిథమ్ను వర్తింపజేయడం: గ్లోబల్ పూల్ సంతృప్తం కానంత వరకు ఒక కీ నిష్క్రియంగా ఉన్న
   వాటాల నుంచి అరువు తీసుకోవచ్చు.
3. అభ్యర్థన అప్స్ట్రీమ్ ఎగ్జిక్యూటర్ను చేరుకోవడానికి ముందే హాట్ పాత్లో (`chatCore.ts`)
   ఫలితాన్ని అమలు చేయడం.

## అల్గారిథమ్: పని-సంరక్షణ న్యాయ-వాటా

`src/lib/quota/fairShare.ts`లో అమలు చేయబడింది.

### మోడ్లు

| షరతు                                       | మోడ్          | ప్రవర్తన                                                                |
| ------------------------------------------ | ------------- | ----------------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **ఉదారమైనది** | వినియోగించిన మొత్తం తీసివేసిన గ్లోబల్ పరిమితి వరకు కీ అరువు తీసుకోవచ్చు |
| `globalUsedPercent >= saturationThreshold` | **కఠినమైనది** | వ్యక్తిగత న్యాయమైన వాటాను కచ్చితంగా అమలు చేయండి                         |

డిఫాల్ట్ `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`).

### ప్రతి డైమెన్షన్కు నిర్ణయం

పూల్లోని ప్రతి యాక్టివ్ డైమెన్షన్ కోసం, ఇంజిన్ ఇలా గణిస్తుంది:

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = ఈ కీకి సంబంధించిన ప్రస్తుత రోలింగ్ విలువ (QuotaStore.peek నుంచి)
remaining       = fairShareAllowed - consumed
```

తర్వాత:

- **`policy = hard`**: `consumed > fairShareAllowed` అయి, మోడ్ కఠినంగా ఉంటే → **బ్లాక్ చేయండి**.
- **`policy = soft`**: `consumed > fairShareAllowed` అయి, మోడ్ కఠినంగా ఉంటే → **పెనాల్టీ విధించండి** (కాంబోలో ప్రాధాన్యతను తగ్గించండి; ఎప్పుడూ పూర్తిగా బ్లాక్ చేయవద్దు).
- **`policy = burst`**: న్యాయమైన వాటాతో సంబంధం లేకుండా గ్లోబల్ హెడ్రూమ్ ఉన్నంత వరకు అనుమతించండి.

### సంపూర్ణ పరిమితి

ఒక కేటాయింపులోని `capValue` + `capUnit`, మోడ్ లేదా పాలసీతో సంబంధం లేని కఠినమైన గరిష్ఠ పరిమితి.
`consumed >= capValue` అయిన ఏ డైమెన్షన్ అయినా అభ్యర్థనను ఎల్లప్పుడూ **బ్లాక్ చేస్తుంది**.

### బహుళ-డైమెన్షన్ తనిఖీ

పూల్లోని **ఏదైనా** డైమెన్షన్ అభ్యర్థనను బ్లాక్ చేసే పరిస్థితి ఉంటే, ఆ అభ్యర్థన బ్లాక్ చేయబడుతుంది. డైమెన్షన్లు
స్వతంత్రంగా ఉంటాయి — 5h% పూర్తిగా వినియోగించబడటం weekly% డైమెన్షన్ను ప్రభావితం చేయదు.

### అరువు తీసుకోవడం

ఉదారమైన మోడ్లో, తన కేటాయింపును పూర్తిగా వినియోగించని కీ, ఇతర కీలకు కేటాయించబడినా వినియోగించని
వాటాల మిగులును ఉపయోగించవచ్చు. ఫార్ములా:

```
maxAllowed = globalLimit - consumedByOtherKeys
```

ఇక్కడ `consumedByOtherKeys = consumedTotal - consumedByThisKey`. ఆ డైమెన్షన్కు సంబంధించిన గ్లోబల్ గరిష్ఠ పరిమితి
(పూల్ `limit`) ఎల్లప్పుడూ కఠినమైన గరిష్ఠ పరిమితిగా ఉంటుంది.

## స్లైడింగ్ విండో కౌంటర్

`src/lib/quota/sqliteQuotaStore.ts` మరియు `redisQuotaStore.ts`లో అమలు చేయబడింది.

ప్రతి `(apiKeyId, dimensionKey)`కు రెండు బకెట్లు:

- `curr`: ప్రస్తుత బకెట్ (`floor(nowMs / windowMs)`)
- `prev`: మునుపటి బకెట్ (`curr - 1`)

ప్రభావవంతమైన రోలింగ్ విలువ:

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**ఖచ్చితత్వం**: ~99% ఖచ్చితమైనది. బకెట్ల మధ్య సరిహద్దు వద్ద లోపం గరిష్ఠంగా విండో పరిమాణంలో 1% ఉంటుంది
(ఇది 2-బకెట్ అంచనా విధానానికి అంతర్గతమైనది).

### ఏకకాలికత

SQLite డ్రైవర్: ప్రతి `(apiKeyId | dimensionKey)` కీకి ఇన్-మెమరీ మ్యూటెక్స్,
రీడ్-మాడిఫై-రైట్ రేస్ను నివారిస్తుంది. ఈ నమూనా `src/sse/services/auth.ts`లోని యాంటీ-థండరింగ్-హర్డ్ విధానాన్ని అనుసరిస్తుంది.

Redis డ్రైవర్: అటామిక్ ఇంక్రిమెంట్ కోసం Lua EVAL స్క్రిప్ట్ — ఇది ఒకే Redis కమాండ్గా అమలవుతుంది.

## డ్రైవర్లు

### SQLite (డిఫాల్ట్, ఇన్స్టాలేషన్ అవసరం లేదు)

- టేబుల్: `quota_consumption` (మైగ్రేషన్ `073_quota_pools.sql` / `074_quota_consumption.sql` చూడండి).
- ఒకే ఇన్స్టాన్స్తో కూడిన డిప్లాయ్మెంట్లకు ఉత్తమమైనది.
- మొత్తం పర్సిస్టెన్స్ ఇప్పటికే ఉన్న OmniRoute SQLite DB (`DATA_DIR/storage.sqlite`)లో ఉంటుంది.

### Redis (ఐచ్ఛికం, బహుళ-ఇన్స్టాన్స్)

- `ioredis` npm ప్యాకేజీ అవసరం.
- కౌంటర్లు Redisలో నిల్వ చేయబడతాయి; మెటాడేటా (పూల్లు/కేటాయింపులు) మాత్రం SQLiteలోనే ఉంటుంది.
- కౌంటర్లను పంచుకోవాల్సిన బహుళ-రెప్లికా డిప్లాయ్మెంట్లకు ఉత్తమమైనది.

### డ్రైవర్లను మార్చడం

సెట్టింగ్ల UI (`/dashboard/settings` → కోటా స్టోర్) ద్వారా లేదా env వేరియబుల్స్ ద్వారా:

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

env కంటే DB సెట్టింగ్కు ప్రాధాన్యత ఉంటుంది. `driver=redis`గా ఉండి URL లేకపోయినా లేదా
`ioredis` ఇన్స్టాల్ చేయకపోయినా, ఫ్యాక్టరీ SQLiteకు తిరిగి మారి హెచ్చరికను లాగ్ చేస్తుంది.

డ్రైవర్ ఎంపిక క్రమం:

1. DB సెట్టింగ్ `quotaStore.driver`
2. Env `QUOTA_STORE_DRIVER`
3. డిఫాల్ట్: `sqlite`

## బహుళ-డైమెన్షన్

ఒక పూల్కు అనేక డైమెన్షన్లు ఉండవచ్చు. ప్రతి డైమెన్షన్ స్వతంత్రంగా ఉంటుంది:

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // ఈ డైమెన్షన్కు గ్లోబల్ పూల్ గరిష్ఠ పరిమితి
}
```

**ఉదాహరణ: Codex ప్లాన్** (5h% + weekly%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

అనుమతించబడాలంటే ఒక అభ్యర్థన అన్ని డైమెన్షన్లను సంతృప్తిపరచాలి.

## ప్లాన్ రిజాల్వర్

`src/lib/quota/planResolver.ts`లో అమలు చేయబడింది.

ప్రాధాన్యత (అత్యధికం నుండి అత్యల్పం వరకు):

1. **మాన్యువల్ DB ఓవర్రైడ్** — ప్రతి `connectionId`కు `provider_plans` టేబుల్.

3. **ఖాళీ ప్లాన్** — డైమెన్షన్లు లేవు, మాన్యువల్ కాన్ఫిగరేషన్ అవసరం.

## పైప్లైన్ ఇంటిగ్రేషన్

### PRE హుక్ (`open-sse/handlers/chatCore.ts`)

ఆథ్ మరియు పాలసీ తనిఖీల తర్వాత, అప్స్ట్రీమ్ ఎగ్జిక్యూటర్కు ముందు అమలవుతుంది:

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → ప్రతి డైమెన్షన్కు getQuotaStore().peek()
      → fairShare.decideFairShare()
      → బ్లాక్ చేస్తే → 429ని రిటర్న్ చేయండి (buildErrorBody, కఠిన నియమం #12)
      → అనుమతించి + ప్రాధాన్యత తగ్గిస్తే → అభ్యర్థిపై quotaSoftPenalty=trueగా సెట్ చేయండి
  → executor.execute()
```

**ఫెయిల్-ఓపెన్**: `enforceQuotaShare` ఎర్రర్ను విసిరితే, `pino.warn` లాగ్తో
అభ్యర్థనను కొనసాగనిస్తారు. ఇది కోటా-ఇంజిన్ బగ్ మొత్తం ట్రాఫిక్ను బ్లాక్ చేయకుండా
నిరోధిస్తుంది.

### POST హుక్ (వినియోగాన్ని రికార్డ్ చేయడం)

విజయవంతమైన రెస్పాన్స్ తర్వాత:

```
ఎగ్జిక్యూటర్ విజయాన్ని రిటర్న్ చేస్తుంది
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → ప్రతి డైమెన్షన్కు getQuotaStore().consume()
      → ఫెయిల్-ఓపెన్: ఎర్రర్లు pino.warnగా లాగ్ చేయబడతాయి, క్లయింట్కు ఎప్పుడూ పంపబడవు
```

**డ్రిఫ్ట్ గమనిక**: రెస్పాన్స్ తర్వాత `consume` విఫలమైతే, రోలింగ్ కౌంటర్ తక్కువగా లెక్కిస్తుంది.
ప్రొవైడర్ నుండి వచ్చే సాచురేషన్ సిగ్నల్ (ఉదా. `anthropic-ratelimit-unified-5h-utilization`)
తదుపరి అభ్యర్థనలో గ్లోబల్ అంచనాను సరిచేస్తుంది.

### కాంబో సాఫ్ట్ పెనాల్టీ (`open-sse/services/combo.ts`)

`decision.deprioritize === true` అయినప్పుడు:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // డిఫాల్ట్ 0.7
}
```

ఇతర అన్ని స్కోరింగ్ కారకాల తర్వాత పెనాల్టీ వర్తించబడుతుంది. ఇది పూర్తిగా బ్లాక్ చేయకుండానే,
సాచురేట్ అయిన కీని ఎంచుకునే ఆటో-కాంబో సంభావ్యతను తగ్గిస్తుంది.

## సమస్య పరిష్కారం

### Redis కాన్ఫిగర్ చేయబడింది, కానీ కనెక్ట్ కావడం లేదు

`ioredis` ఇన్స్టాల్ అయిందో లేదో (`npm ls ioredis`), అలాగే `QUOTA_STORE_REDIS_URL`
అందుబాటులో ఉందో లేదో తనిఖీ చేయండి. కనెక్షన్ విఫలమైతే ఫ్యాక్టరీ SQLiteకు ఫాల్బ్యాక్ అవుతుంది (`warn` స్థాయిలో
లాగ్ చేయబడుతుంది).

### `peek` పాత డేటాను అందిస్తుంది / ఫెయిల్-ఓపెన్ అవుతుంది

`peek` ఎర్రర్ను విసిరితే, `enforceQuotaShare` ఫలితాన్ని "అనుమతించు"గా (ఫెయిల్-ఓపెన్)
పరిగణిస్తుంది. మూల కారణాన్ని గుర్తించడానికి `quota:enforce` మరియు `quota:factory` ఎంట్రీల కోసం
`pino` లాగ్లను తనిఖీ చేయండి.

### వినియోగ కౌంటర్ డ్రిఫ్ట్

వాస్తవ ప్రొవైడర్ వినియోగం కౌంటర్లతో భిన్నంగా ఉంటే, అది ఊహించినదే — 2-బకెట్
స్లైడింగ్ విండోలో విండో సరిహద్దుల వద్ద సుమారు 1% లోపం ఉంటుంది, అలాగే `consume`
రెస్పాన్స్ తర్వాత ఫైర్-అండ్-ఫర్గెట్ విధానంలో నడుస్తుంది. సాచురేషన్ సిగ్నల్ (`saturationSignals.ts`)
30 సెకన్ల TTLతో వాస్తవ ప్రొవైడర్ వినియోగాన్ని చదివి, దానికి అనుగుణంగా `globalUsedPercent`ను
సర్దుబాటు చేస్తుంది.

### బర్న్ రేట్ కోసం పూల్ "డేటా లేదు" అని చూపిస్తుంది

`computeBurnRate`కు కనీసం 2 చారిత్రక శాంపిల్స్ అవసరం. ఇంతకుముందు
`consume` కాల్స్ లేని కొత్త పూల్స్ `tokensPerSecond: 0` మరియు `timeToExhaustionMs: null`ను చూపిస్తాయి.

## localStorage నుండి మైగ్రేషన్

`/dashboard/costs/quota-share` మొదటిసారి లోడ్ అయినప్పుడు, `useLocalStoragePoolMigration`
హుక్ వీటిని తనిఖీ చేస్తుంది:

1. `localStorage.getItem("omniroute:quota-share:pools")` ఖాళీగా లేదు.
2. `GET /api/quota/pools` `[]`ను తిరిగి ఇస్తుంది (DB ఖాళీగా ఉంది).

రెండూ నిజమైతే, అది ప్రతి లెగసీ పూల్ను బ్యాచ్గా `POST /api/quota/pools`కు పోస్ట్ చేసి,
ఆ తర్వాత localStorage కీని తొలగిస్తుంది. ఈ మైగ్రేషన్ ఐడెంపోటెంట్గా ఉంటుంది: షరతు 2
మళ్లీ మైగ్రేట్ చేయడాన్ని నిరోధిస్తుంది.

- `quota_pools` + `quota_allocations` — పూల్ నిర్వచనాలు మరియు ప్రతి కీకి కేటాయింపులు.
- `quota_consumption` — ప్రతి `(apiKeyId, dimensionKey)`కు రోలింగ్ 2-బకెట్ కౌంటర్లు.
- `provider_plans` — మాన్యువల్ ప్రొవైడర్ ప్లాన్ ఓవర్రైడ్లు (ప్రతి connectionIdకు డైమెన్షన్ల JSON).

అన్ని టేబుల్లు ఐడెంపోటెంట్ `CREATE TABLE IF NOT EXISTS` మైగ్రేషన్ల ద్వారా జోడించబడ్డాయి.
