### ఉచిత ప్రొవైడర్లపై రేట్ పరిమితి (429 / 400 / 401)

**లక్షణం**: ఉచిత/ప్రమాణీకరణ అవసరం లేని ప్రొవైడర్లతో (opencode, auggie మొదలైనవి) `model: "auto"` ఉపయోగిస్తున్నప్పుడు, సమాధానాలకు బదులుగా అప్పుడప్పుడు `HTTP 429`, `400`, లేదా `401` వస్తుంది. కొన్ని క్షణాల తర్వాత అదే ప్రాంప్ట్ను మళ్లీ ప్రయత్నించినప్పుడు అభ్యర్థనలు విజయవంతమవుతాయి, కానీ ఆటోమేషన్ (cron జాబ్లు, ఏజెంట్లు, స్క్రిప్ట్లు) మొదటి వైఫల్యంతోనే ఆగిపోతుంది.

**మూల కారణం**: మూడు స్వతంత్ర వైఫల్య రీతులు ఒకదానిపై మరొకటి పేరుకుపోతాయి:

1. **ప్రొవైడర్ రేట్ పరిమితి (`429`)**: ఉచిత టియర్లు ఒక్కో సమయ-విండోకు కోటాను అమలు చేయవచ్చు. సమాంతర కాల్ల వెల్లువ దాన్ని పూర్తిగా వినియోగిస్తుంది, కాబట్టి విండో రీసెట్ అయ్యే వరకు తదుపరి అభ్యర్థన తిరస్కరించబడుతుంది.
2. **పాస్త్రూలో పనిచేయని మోడల్ (`400`/`401`)**: `auto/*` పూల్లలో `opencode` నుండి కేటలాగ్లో నమోదై ఉన్నప్పటికీ ప్రత్యక్ష ఆధారాలు లేని పాస్త్రూ మోడల్లు ఉండవచ్చు (ఉదా. `oc/north-mini-code-free` → `401`). ఆటో-రౌటర్ ఒకదాన్ని ప్రయత్నిస్తుంది, విఫలమవుతుంది, ఫాల్బ్యాక్ అమలులోకి రాకముందే లోపం ముందుకు పంపబడుతుంది.
3. **కరెన్సీ విస్తరణ (లోడ్లో `429`)**: అనేక ఏజెంట్/cron సెషన్లు ఒకేసారి `auto`ను ఉపయోగించినప్పుడు, మొత్తం అభ్యర్థన రేటు ఉచిత ప్రొవైడర్లు భరించగలిగిన స్థాయిని మించిపోతుంది, అందువల్ల చెల్లుబాటు అయ్యే కాల్లు కూడా దుర్వినియోగంగా గుర్తించబడతాయి.

**ధృవీకరించబడిన పరిష్కారం (కమ్యూనిటీ నివేదిక, 2026-08-10)**: ఉచిత-టియర్లోని అస్థిరత కారణంగా విఫలమవకుండా, రొటేషన్, కరెన్సీ, మరియు ఫాల్బ్యాక్ దాన్ని గ్రహించేలా మూడు ఎన్విరాన్మెంట్ వేరియబుల్లను సర్దుబాటు చేయండి:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 వచ్చినప్పుడు మరొక మోడల్/ప్రొవైడర్కు మారండి (పనిచేయని పాస్త్రూ మోడల్లను దాటవేస్తుంది)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # హెవీవెయిట్ అడ్మిషన్కు స్పష్టమైన గరిష్ఠ పరిమితి (డిఫాల్ట్గా సెట్ చేయబడదు: అభ్యర్థనల సంఖ్యకు పరిమితి లేదు, దిగువ గమనికను చూడండి)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # నెమ్మదైన అప్స్ట్రీమ్ల కోసం పరిమిత నిరీక్షణను RATE_LIMIT_MAX_WAIT_MS డిఫాల్ట్ కంటే ఎక్కువగా పెంచండి
```

వీటిని OmniRoute ప్రాసెస్ ఎన్విరాన్మెంట్లో (డీమన్లో, ఉదా. LaunchAgent plist లేదా `systemctl edit` ద్వారా) సెట్ చేసి, ఆపై OmniRouteను పునఃప్రారంభించండి. రొటేషన్ ఫ్లాగ్ అత్యధిక ప్రభావం చూపే ఏకైక నియంత్రకం: ఇది కఠిన వైఫల్యాన్ని పూల్లోని ఆరోగ్యకరమైన ప్రొవైడర్పై పారదర్శక పునఃప్రయత్నంగా మారుస్తుంది.

**గమనిక**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ఒకేసారి ఎన్ని హెవీవెయిట్ — దీర్ఘ-కాంటెక్స్ట్ — అభ్యర్థనలు అమలు కావచ్చో పరిమితం చేస్తుంది; ఈ పరిమితి ఒక అడ్మిషన్ గేట్, ప్రొవైడర్ రేట్ లిమిటర్ కాదు. **#503-ఫ్యాన్అవుట్ నవీకరణ:** ఈ వేరియబుల్ ఇకపై డిఫాల్ట్గా సెట్ చేయబడదు (ఇప్పుడు పైన చూపినట్లుగా స్పష్టంగా కాన్ఫిగర్ చేసినప్పుడు మాత్రమే ఇది వర్తిస్తుంది) — బదులుగా హెవీవెయిట్ అడ్మిషన్, హోస్ట్ యొక్క వాస్తవ మెమరీ పరిమితిని బట్టి స్వయంగా స్కేల్ అయ్యే ఆటోమేటిక్గా లెక్కించిన బైట్ బడ్జెట్ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ద్వారా నియంత్రించబడుతుంది. అందువల్ల కొత్త డిప్లాయ్మెంట్లో ఈ వేరియబుల్ను సెట్ చేయకుండానే చాలా తక్కువ `503 chat_admission_busy` తిరస్కరణలు కనిపించాలి; ఇక్కడ దీన్ని స్పష్టంగా సెట్ చేయడం ఇప్పటికీ డాక్యుమెంట్ చేసిన విధంగానే పనిచేస్తుంది. స్పష్టమైన బైట్-బడ్జెట్ ఓవర్రైడ్లు 8 MiB–2 GiBకు పరిమితం చేయబడతాయి. `413 body_exceeds_budget` తాత్కాలికం కాదు: ఆ బైట్ బడ్జెట్ను పెంచండి, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`ను తగ్గించండి, లేదా ప్రాసెస్ మెమరీ పరిమితిని పెంచండి. `inflight_bytes_budget` షెడ్ అనేది తాత్కాలిక వనరుల పోటీ; దాన్ని మళ్లీ ప్రయత్నించవచ్చు. ఒక్కో ప్రొవైడర్కు వర్తించే రేట్ పరిమితి (`open-sse/services/rateLimitManager.ts`) విడిగా `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, మరియు `RATE_LIMIT_AUTO_ENABLE` ద్వారా నియంత్రించబడుతుంది — `.env.example` చూడండి.

**ఇది పనిచేసిందో ఎలా ధృవీకరించాలి**: మీ agent/cronను వెంటవెంటనే రెండుసార్లు అమలు చేసి, రెండుసార్లూ విజయవంతమయ్యాయని నిర్ధారించండి. పరిష్కారానికి ముందు, రెండవ అమలు సాధారణంగా `429`/`401` లోపాన్ని చూపుతుంది. పరిష్కారం తర్వాత, వైఫల్యాలు (ఏవైనా ఉంటే) పారదర్శకంగా మళ్లీ ప్రయత్నించబడతాయి మరియు కాల్ పూర్తవుతుంది. మీరు `curl /monitoring/health`ను కూడా అమలు చేసి, provider కనెక్షన్లలోని `rateLimitedUntil` ఫీల్డ్ను మరియు ప్రభావిత providerల కోసం `circuitBreakers.providerBreakers[].state`ను గమనించవచ్చు — స్థితి `CLOSED`, `DEGRADED`, `OPEN`, లేదా `HALF_OPEN`లలో ఒకటిగా ఉంటుంది (`src/shared/utils/circuitBreaker.ts` చూడండి). వరుసగా విఫలమవుతున్న provider, reset window ఒక probeను అనుమతించే ముందు `CLOSED → DEGRADED → OPEN`కు మారుతుంది (`HALF_OPEN`).

**మీకు ఇంకా 429 కనిపిస్తే**: ఆ providerకు సంబంధించిన సక్రియ account నిజంగానే దాని _quota_ను పూర్తిగా వినియోగించింది (కేవలం rate మాత్రమే కాదు). OmniRoute dashboard → Providers → Accountsలో అదే provider కోసం రెండవ accountను జోడించండి లేదా మరొక ఉచిత providerను (ఉదా. `routeway`, `auggie`) కలిపి ఉపయోగించండి. Rotation అనేది తాత్కాలిక rate/400/401 సమస్యలకు మాత్రమే సహాయపడుతుంది; quota పూర్తిగా అయిపోతే రెండవ credential లేదా వేరే provider అవసరం.

**vision modelలలో (`auto/vision`, `bazaarlink/*`) 403 కనిపిస్తే**: కనెక్ట్ చేసిన accountకు visionను కలిగి ఉన్న paid plan లేదు లేదా API keyకు తగిన permissions లేవు. provider dashboardలో key scopeలో vision/multimodal ఉన్నట్లు ధృవీకరించండి లేదా paid tier accountను కనెక్ట్ చేసి, దానిని vision targetగా ఉంచండి.

## npm install హెచ్చరికలు (ERESOLVE / peer / deprecated)

మీరు `npm install -g omniroute` అమలు చేసినప్పుడు, `npm warn ERESOLVE`, peer-dependency నోటీసులు మరియు `deprecated` సందేశాలు వంటి అనేక హెచ్చరికలు కనిపించవచ్చు. **ఇవి ఊహించినవే మరియు హానికరం కావు.** అవుట్పుట్లో `added <N> packages` కనిపిస్తే మీ ఇన్స్టాలేషన్ విజయవంతమైనట్లే.

peer-dependency పరిష్కార హెచ్చరికలను అణచివేయడానికి, OmniRoute మద్దతిచ్చే ఇన్స్టాలేషన్ రూపాన్ని ఉపయోగించండి:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` కేవలం `ERESOLVE` మరియు peer-dependency నోటీసులను మాత్రమే అణచివేస్తుంది. డిప్రికేషన్ నోటీసులు ట్రాన్సిటివ్ థర్డ్-పార్టీ ప్యాకేజీల నుంచి వస్తాయి కాబట్టి అవి కనిపిస్తూనే ఉంటాయి; ఇన్స్టాలేషన్ విఫలమైందని అవి సూచించవు.

OmniRoute నియంత్రణలో లేని థర్డ్-పార్టీ ప్యాకేజీలలో కాలం చెల్లిన peer-dependency పరిధుల కారణంగా ఈ హెచ్చరికలు వస్తాయి:

1. **`marked-terminal`కు `marked >=1 <16` కావాలి, కానీ `marked@18` కనుగొనబడింది** — ఆచరణలో ఇది సరిగ్గా పనిచేస్తుంది; upstream peer పరిధి కాలం చెల్లినది మాత్రమే.
2. **`deprecated prebuild-install@7.1.3`** — ట్రాన్సిటివ్ స్థానిక-బైనరీ పొందే సహాయక సాధనం. పిన్ చేసిన `wreq-js` ట్రాన్స్పోర్ట్ బైండింగ్ను ఇన్స్టాల్ చేయడానికి ఇది
   ఉపయోగించబడదు మరియు web-cookie ప్రొవైడర్ ట్రాన్స్పోర్ట్ సెటప్ విఫలమైందని
   సూచించదు.

**ఎలాంటి చర్య అవసరం లేదు** — upstream ప్యాకేజీలను fork చేయకుండా ఈ హెచ్చరికలను పూర్తిగా నిశ్శబ్దం చేయడం సాధ్యం కాదు.

## npm install-scripts నిరోధించబడిన హెచ్చరిక (గ్లోబల్ ఇన్స్టాలేషన్)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` అమలు చేస్తున్నప్పుడు, కొత్త npm వెర్షన్లు (v11+ మరియు v12+) డిఫాల్ట్గా ప్యాకేజీ లైఫ్సైకిల్ స్క్రిప్ట్లను నిరోధించి, install-scripts హెచ్చరికను ప్రదర్శిస్తాయి:

```
npm warn install-scripts allowScripts పరిధిలో లేనందున 7 ప్యాకేజీల ఇన్స్టాల్ స్క్రిప్ట్లు నిరోధించబడ్డాయి:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### ఈ హెచ్చరికను విస్మరించవచ్చా?

**పాక్షికంగా, కానీ స్క్రిప్ట్లు లేకుండా అమలు చేయడం సిఫార్సు చేయబడదు.** OmniRoute సునాయాస ప్రత్యామ్నాయాలను కలిగి ఉంది: standalone bundle నుంచి స్థానిక `better-sqlite3` బైండింగ్లను లోడ్ చేయలేకపోతే, అప్లికేషన్ `node:sqlite` లేదా `sql.js` వంటి ప్రత్యామ్నాయ డ్రైవర్లకు మారుతుంది ([SQLite రన్టైమ్ పరిష్కారం](../ops/SQLITE_RUNTIME.md) చూడండి). సర్వర్ అయినప్పటికీ ప్రారంభమవుతుంది, కానీ `sql.js` వంటి WASM ప్రత్యామ్నాయాలపై అమలు చేయడం SQLite WAL (Write-Ahead Logging) మోడ్ను నిలిపివేసి, మెమరీ మరియు డిస్క్-సింక్ ఓవర్హెడ్ను పెంచుతుంది.

### వాస్తవంగా ఏ స్క్రిప్ట్లు అవసరం?

నిరోధించబడిన అన్ని స్క్రిప్ట్లు OmniRouteను అమలు చేయడానికి తప్పనిసరి కావు:

- **అత్యవసరమైనవి (`omniroute`, `better-sqlite3`):** OmniRoute ఒక Next.js standalone అప్లికేషన్ బండిల్ (`dist/`) నుంచి అమలవుతుంది. ఇన్స్టాలేషన్ సమయంలో, npm హోస్ట్కు ప్రత్యేకమైన స్థానిక SQLite డ్రైవర్ను అగ్ర-స్థాయి `node_modules/better-sqlite3/`లో డౌన్లోడ్ చేస్తుంది లేదా కంపైల్ చేస్తుంది. ఆ తర్వాత OmniRoute యొక్క `postinstall` స్క్రిప్ట్ (`scripts/build/postinstall.mjs`) ఈ హోస్ట్-నిర్దిష్ట బైనరీలను ధృవీకరించి, standalone సర్వర్ వాటిని యాక్సెస్ చేయగలిగేలా `dist/node_modules/`లోకి కాపీ చేస్తుంది. `omniroute` యొక్క postinstall స్క్రిప్ట్ నిరోధించబడితే, ఈ కాపీ దశ దాటవేయబడుతుంది.
- **ఐచ్ఛికం/ట్రాన్సిటివ్ (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** ఇవి బిల్డ్ సహాయకాలు, వాచర్ సాధనాలు లేదా సిస్టమ్ కీచైన్ యుటిలిటీలు. వీటిని అనుమతించడం బిల్డ్ హెచ్చరికలను నివారిస్తుంది, కానీ ప్రధాన రూటింగ్ కార్యాచరణకు ఇవి అవసరం లేదు.
- **మినహాయించబడినది (`onnxruntime-node`):** స్థానిక AI embeddings కోసం ఐచ్ఛిక dependency మరియు OmniRoute అమలుకు ఇది **అవసరం లేదు**. దీని postinstall స్క్రిప్ట్ NuGet నుంచి దాదాపు 300MB CUDA ఆస్తులను డౌన్లోడ్ చేస్తుంది; మద్దతున్న హార్డ్వేర్పై స్థానిక ONNX యాక్సిలరేషన్ను ఉపయోగించాలని మీరు స్పష్టంగా భావిస్తే తప్ప దీన్ని allow-listలో చేర్చవద్దు.

### సిఫార్సు చేసిన పరిష్కారం

గ్లోబల్ ఇన్స్టాలేషన్ సమయంలో అవసరమైన ఇన్స్టాల్ స్క్రిప్ట్లను అనుమతించి, హెచ్చరికలను నిశ్శబ్దం చేయడానికి, OmniRoute మరియు దాని స్థానిక dependencies కోసం `--allow-scripts`ను పాస్ చేయండి:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

ప్రత్యామ్నాయంగా, మీ యూజర్ ఖాతాలోని అన్ని గ్లోబల్ ఇన్స్టాలేషన్ల కోసం దీన్ని శాశ్వతంగా కాన్ఫిగర్ చేయడానికి:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### మీ ఇన్స్టాలేషన్ను ధృవీకరించండి

ఇన్స్టాలేషన్ తర్వాత, స్థానిక బైండింగ్లు మరియు రన్టైమ్ వాతావరణం సరిగ్గా ఉన్నాయని నిర్ధారించుకోవడానికి అంతర్నిర్మిత డయాగ్నస్టిక్ సాధనాన్ని అమలు చేయండి:

```bash
omniroute doctor
```

## Gemini Web మరియు Playwright Chromium

Gemini Web అభ్యర్థన `503` స్థితితో పాటు Playwright Chromium ఇన్స్టాల్ కాలేదనే సందేశాన్ని అందిస్తే, npm ప్యాకేజీ అందుబాటులో ఉంది కానీ బ్రౌజర్ బైనరీ లేదు. Playwright ఉద్దేశపూర్వకంగా బ్రౌజర్ డౌన్లోడ్లను npm ప్యాకేజీ ఇన్స్టాలేషన్ నుండి వేరుగా ఉంచుతుంది, కాబట్టి బ్రౌజర్ను ఇన్స్టాల్ చేసే వరకు ఈ ప్రతిస్పందన రావడం సహజమే.

గ్లోబల్ npm ఇన్స్టాలేషన్ కోసం, బ్రౌజర్ క్యాష్ అదే Playwright ఇన్స్టాలేషన్కు చెందినదిగా ఉండేలా OmniRoute ప్యాకేజీ డైరెక్టరీ నుండి Chromiumను ఇన్స్టాల్ చేయండి:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ఇన్స్టాలేషన్ తర్వాత OmniRouteను పునఃప్రారంభించి, Gemini Web అభ్యర్థనను మళ్లీ ప్రయత్నించండి. మీరు Docker ఇమేజ్ నుండి OmniRouteను అమలు చేస్తే, Chromium మరియు దాని డిపెండెన్సీలను కలిగి ఉండే `-web` ఇమేజ్ను (లేదా `runner-web` బిల్డ్ టార్గెట్ను) ఉపయోగించండి; బేస్ ఇమేజ్లో అవి ఉండవు.

   స్పందించడమే దీనికి కారణం కాబట్టి, అందరికీ సహాయపడే పరిష్కారం ఇదే.

**మేము దీనిని మా వైపు ఎందుకు "పరిష్కరించము":** అన్ని ఉదాహరణలూ `http://localhost`ను ఉపయోగిస్తాయి,
మరియు స్వీయ-సంతకం చేసిన సర్టిఫికేట్ వల్ల కలిగే ఇబ్బందులు లేకుండా localhostను `https`గా ఉపయోగించడం
సాధ్యం కాదు. ఒక విక్రేత హ్యూరిస్టిక్ను తప్పించుకోవడానికి డాక్యుమెంటేషన్ను వక్రీకరించడం, ఒక స్కానర్
బగ్ను సంతృప్తిపరచడానికి ప్రతి పాఠకుడికీ ఇబ్బంది కలిగిస్తుంది.

### Kaspersky, Desktop యాప్ను `PDM:Trojan.Win32.Generic`గా ఫ్లాగ్ చేస్తుంది

**ఇది ప్రవర్తనా హ్యూరిస్టిక్ వల్ల సంభవించిన తప్పుడు పాజిటివ్. దేనికీ ఇన్ఫెక్షన్ సోకలేదు.** Kasperskyలోని
`PDM:` ప్రిఫిక్స్ అంటే, తెలిసిన మాల్వేర్తో పోల్చడం కాకుండా ఇన్స్టాలర్ _చేసే పనులను_ అంచనా వేసే
దాని Proactive Defense Module (System Watcher) నుండి ఈ నిర్ణయం వచ్చిందని అర్థం. ఇది ప్రేరేపించబడినప్పుడు,
Kaspersky మొత్తం ఇన్స్టాలేషన్ను "రోల్ బ్యాక్" చేస్తుంది — అప్పటికే రాసిన ఫైల్లను తొలగిస్తుంది —
దాంతో యాప్ పనిచేయకుండా పోతుంది లేదా పూర్తిగా కనిపించకుండా పోతుంది.

ఇది ఫ్లాగ్ చేసే ఫైల్లు Desktop యాప్తో బండిల్ చేయబడిన, ప్రకటించిన ఓపెన్-సోర్స్ డిపెండెన్సీలలోని
ప్రామాణిక భాగాలు, ఉదాహరణకు:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` మరియు
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), యాప్లోనే ప్రొవైడర్ లాగిన్ మరియు
  బ్రౌజర్ ఆధారిత చాట్ కోసం ఉపయోగించే బ్రౌజర్-ఆటోమేషన్ లైబ్రరీ.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — వెబ్-కుకీ ప్రొవైడర్లపై బ్రౌజర్-ఫింగర్ప్రింట్ చేసిన HTTP కోసం ఉపయోగించే, నిర్దిష్ట వెర్షన్కు
  స్థిరపరచిన `wreq-js` నేటివ్ బైండింగ్ (`<arch>` అనేది `x64` లేదా `arm64`).

**ఇది ఎందుకు ప్రేరేపించబడుతుంది:** Windows ఇన్స్టాలర్కు **ఇంకా కోడ్-సంతకం చేయలేదు**, కాబట్టి
సంతకం చేయని NSIS ఇన్స్టాలర్కు సున్నా ప్రతిష్ఠ ఉంటుంది మరియు ప్రవర్తనా హ్యూరిస్టిక్లు అత్యంత
దూకుడుగా పనిచేస్తాయి. బండిల్ చేసిన నేటివ్ DLLతో పాటు `%LOCALAPPDATA%\Programs\OmniRoute` కింద
వ్రాయబడిన వందలాది `.js` ఫైల్లు (Next.js స్వతంత్ర బిల్డ్ నుండి హాష్-సఫిక్స్ కలిగిన ప్యాకేజీ
డైరెక్టరీలతో సహా) కలిసినప్పుడు, అది హ్యూరిస్టిక్ను ప్రేరేపించడానికి సరిపోతుంది. కోడ్ సైనింగ్
ప్రణాళికలో ఉంది; అది అమల్లోకి వచ్చే వరకు కొత్త విడుదలల్లో ఇది పునరావృతం కావచ్చు.

**ఏం చేయాలి:**

1. **ముందుగా మీ డౌన్లోడ్ను ధృవీకరించండి** (ఫైల్లో మార్పులు జరిగి ఉండే అవకాశాన్ని ఇది
   తొలగిస్తుంది). ప్రతి విడుదల `latest.yml`ను ప్రచురిస్తుంది, దానిలోని `sha512` ఫీల్డ్ (base64)
   `OmniRoute.Setup.<version>.exe` ఇన్స్టాలర్ను కవర్ చేస్తుంది. PowerShellలో, ఇన్స్టాలర్ ఉన్న
   ఫోల్డర్ నుండి:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   అవుట్పుట్ తప్పనిసరిగా `latest.yml` → `sha512`తో సరిపోలాలి. సరిపోకపోతే, ఫైల్ను తొలగించి
   [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) నుండి మాత్రమే
   మళ్లీ డౌన్లోడ్ చేయండి.
2. **పునరుద్ధరించండి + మినహాయించండి** — రోల్ బ్యాక్ చేయబడిన అంశాలను క్వారంటైన్ నుండి పునరుద్ధరించి,
   `%LOCALAPPDATA%\Programs\OmniRoute` కోసం మినహాయింపును జోడించండి (Kaspersky → Settings →
   Threats and Exclusions), ఆపై మళ్లీ ఇన్స్టాల్ చేయండి.
3. **తప్పుడు పాజిటివ్ను నివేదించండి** — <https://opentip.kaspersky.com/>. వినియోగదారులు సమర్పించే
   తప్పుడు పాజిటివ్ నివేదికలు అలౌలిస్టింగ్ను నిజంగానే వేగవంతం చేస్తాయి.

## Node.js అనుకూలత

<a name="nodejs-compatibility"></a>

### లాగిన్ పేజీ క్రాష్ అవుతోంది లేదా "Module self-registration" లోపాన్ని చూపుతోంది

**కారణం:** మీరు OmniRoute ఆమోదించిన సురక్షిత రన్టైమ్ కనిష్ఠ పరిమితికి వెలుపల ఉన్న Node.js వెర్షన్ను అమలు చేస్తున్నారు. OmniRouteకు అవసరమైన ప్యాచ్ చేసిన భద్రతా కనిష్ఠ పరిమితి కంటే తక్కువగా ఉన్న పాత Node 22 లేదా 24 ప్యాచ్ స్థాయిని అమలు చేయడం అత్యంత సాధారణ సందర్భం.

**లక్షణాలు:**

- లాగిన్ పేజీ ఖాళీ స్క్రీన్ లేదా సర్వర్ లోపాన్ని చూపుతుంది
- కన్సోల్లో `Error: Module did not self-register` లేదా ఇలాంటి నేటివ్ బైండింగ్ లోపాలు కనిపిస్తాయి
- రన్టైమ్ మద్దతు ఉన్న సురక్షిత విధానానికి వెలుపల ఉంటే, లాగిన్ పేజీ మీ Node వెర్షన్తో కూడిన **నారింజ రంగు హెచ్చరిక బ్యానర్ను** చూపుతుంది

**పరిష్కారం:**

1. మద్దతు ఉన్న Node.js LTS విడుదలను ఇన్స్టాల్ చేయండి (సిఫార్సు చేయబడింది: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. మీ వెర్షన్ను ధృవీకరించండి: 24.x LTS శ్రేణిలో `node --version` అనేది `v24.0.0` లేదా అంతకంటే కొత్త వెర్షన్ను చూపాలి
3. OmniRouteను మళ్లీ ఇన్స్టాల్ చేయండి: `npm install -g omniroute`
4. పునఃప్రారంభించండి: `omniroute`

> **మద్దతు ఉన్న సురక్షిత వెర్షన్లు:** `>=22.22.2 <23` లేదా `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) మరియు Node.js 26కు పూర్తి మద్దతు ఉంది.

### npm v11+: `better-sqlite3` ఇన్స్టాల్ కాలేదు (మాడ్యూల్ను కనుగొనలేకపోయింది)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**కారణం:** npm v11 (Node.js 24+తో అందించబడుతుంది) డిఫాల్ట్గా ఐచ్ఛిక
డిపెండెన్సీల ఇన్స్టాల్ స్క్రిప్ట్లను నిరోధిస్తుంది. `better-sqlite3` అనేది `optionalDependencies`లో జాబితా చేయబడి,
నేటివ్ కంపైలేషన్ (`node-gyp rebuild`) అవసరం కావడం వల్ల, npm దానిని ఎలాంటి సమాచారం ఇవ్వకుండా దాటవేస్తుంది.

**లక్షణాలు:**

- ప్రారంభ సమయంలో సర్వర్ `Cannot find module 'better-sqlite3'` లోపంతో క్రాష్ అవుతుంది
- `ls node_modules/better-sqlite3` అనేది "No such file or directory" అని చూపుతుంది
- `npm ls better-sqlite3` అనేది `(empty)` అని చూపుతుంది

**పరిష్కారం:**

1. ఇన్స్టాల్ స్క్రిప్ట్లను ఆమోదించి, మళ్లీ ఇన్స్టాల్ చేయండి:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. లేదా ముందే బిల్డ్ చేసినదాన్ని మాన్యువల్గా ఇన్స్టాల్ చేయండి:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. అది పనిచేస్తోందని ధృవీకరించండి: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**కారణం:** గ్లోబల్ `npm install -g omniroute` తర్వాత, ప్యాకేజీలోని `better-sqlite3` నేటివ్ బైనరీ స్థానికంగా అమలవుతున్న ఆర్కిటెక్చర్ లేదా Node.js ABIకి భిన్నమైన దాని కోసం కంపైల్ చేయబడి ఉండవచ్చు. ముందే బిల్డ్ చేసిన బైనరీ మీ ఎన్విరాన్మెంట్తో సరిపోలనప్పుడు, ఇది macOSలో (Apple Silicon మరియు Intel రెండింటిలోనూ) సాధారణంగా జరుగుతుంది.

**లక్షణాలు:**

- ప్రారంభ సమయంలోనే సర్వర్ `dlopen` లోపంతో విఫలమవుతుంది
- లోపంలో `slice is not valid mach-o file` ఉంటుంది
- పూర్తి ఉదాహరణ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**పరిష్కారం — మీ స్థానిక ఎన్విరాన్మెంట్ కోసం మళ్లీ బిల్డ్ చేయండి (Node.js డౌన్గ్రేడ్ అవసరం లేదు):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **గమనిక:** ఇది మీ స్థానిక Node.js వెర్షన్ మరియు CPU ఆర్కిటెక్చర్కు అనుగుణంగా నేటివ్ బైండింగ్ను మళ్లీ కంపైల్ చేసి, బైనరీ అసమతుల్యతను పరిష్కరిస్తుంది. అధికారికంగా మద్దతు ఉన్న రన్టైమ్ పరిధి **`>=22.22.2 <23` లేదా `>=24.0.0 <27`** (`src/shared/utils/nodeRuntimeSupport.ts`లోని `SUPPORTED_NODE_RANGE`, `package.json`లోని `engines` ఫీల్డ్తో సమలేఖనం చేయబడింది). `better-sqlite3` v12.xతో Node.js 24.x LTS (Krypton) మరియు Node.js 26కు పూర్తి మద్దతు ఉంది.

## ప్రాక్సీ సమస్యలు

<a name="proxy-issues"></a>

### ప్రొవైడర్ ధ్రువీకరణలో "fetch failed" చూపబడుతుంది

**కారణం:** API కీ ధ్రువీకరణ ఎండ్పాయింట్ (`POST /api/providers/validate`) గతంలో ప్రాక్సీ కాన్ఫిగరేషన్ను దాటవేసేది, దీనివల్ల ప్రాక్సీ రూటింగ్ అవసరమైన ఎన్విరాన్మెంట్లలో వైఫల్యాలు సంభవించేవి.

**పరిష్కారం (v3.5.5+):** ఇది ఇప్పుడు పరిష్కరించబడింది. ప్రొవైడర్ ధ్రువీకరణ `runWithProxyContext` ద్వారా రూట్ అవుతుంది మరియు ప్రొవైడర్-స్థాయి, గ్లోబల్ ప్రాక్సీ సెట్టింగ్లను స్వయంచాలకంగా అనుసరిస్తుంది.

### టోకెన్ హెల్త్ చెక్ "fetch failed"తో విఫలమవుతుంది

**కారణం:** బ్యాక్గ్రౌండ్ OAuth టోకెన్ రిఫ్రెష్ ప్రతి కనెక్షన్కు ప్రాక్సీ కాన్ఫిగరేషన్ను పరిష్కరించడం లేదు.

**పరిష్కారం (v3.5.5+):** టోకెన్ హెల్త్ చెక్ షెడ్యూలర్ ఇప్పుడు రిఫ్రెష్ చేయడానికి ప్రయత్నించే ముందు ప్రతి కనెక్షన్కు ప్రాక్సీ కాన్ఫిగరేషన్ను పరిష్కరిస్తుంది. v3.5.5+కు అప్డేట్ చేయండి.

### SOCKS5 ప్రాక్సీ "invalid onRequestStart method"ను తిరిగి ఇస్తుంది

**కారణం:** Node.js 22లో, undici@8 డిస్పాచర్ Nodeలో అంతర్నిర్మితంగా ఉన్న `fetch()` అమలుతో అనుకూలంగా ఉండదు.

**పరిష్కారం (v3.5.5+):** ప్రాక్సీ డిస్పాచర్ సక్రియంగా ఉన్నప్పుడు OmniRoute ఇప్పుడు undici సొంత `fetch()` ఫంక్షన్ను ఉపయోగిస్తుంది, తద్వారా స్థిరమైన ప్రవర్తనను నిర్ధారిస్తుంది. v3.5.5+కు అప్డేట్ చేయండి.

### WSLలో MITM ప్రాక్సీ: Windows హోస్ట్లోని డెస్క్టాప్ యాప్లు ఇంటర్సెప్ట్ కావడం లేదు

**కారణం:** MITM ప్రాక్సీ మరియు దాని CA సర్టిఫికేట్ OmniRoute నడుస్తున్న ఎన్విరాన్మెంట్లో ఇన్స్టాల్ అవుతాయి. WSLలో ఆ ఎన్విరాన్మెంట్ Linux గెస్ట్గా ఉంటుంది, కాగా AI డెస్క్టాప్ యాప్లు (Kiro, Trae, Copilot, Zed, …) Windows హోస్ట్లో నడుస్తాయి. హోస్ట్ యాప్లు గెస్ట్ సర్టిఫికేట్ స్టోర్ను విశ్వసించవు మరియు గెస్ట్ సిస్టమ్ ప్రాక్సీ ద్వారా రూట్ కావు, కాబట్టి అక్కడ డెస్క్టాప్ ఇంటర్సెప్షన్ సక్రియం కాదు.

**సిఫార్సు:** మీరు ఇంటర్సెప్ట్ చేయాలనుకుంటున్న డెస్క్టాప్ యాప్లు ఉన్న అదే OSలో OmniRouteను నేటివ్గా అమలు చేయండి (Windows యాప్ల కోసం Windows; అలాగే macOS/Linux కోసం వాటి సంబంధిత OS). హోస్ట్ యాప్లను లక్ష్యంగా చేసుకుంటూ OmniRouteను WSLలోనే ఉంచాలంటే, రూపొందించిన CA సర్టిఫికేట్ను Windows హోస్ట్లో మాన్యువల్గా విశ్వసనీయంగా జోడించి, ప్రతి హోస్ట్ యాప్ నెట్వర్క్/ప్రాక్సీ సెట్టింగ్లను WSL ప్రాక్సీ ఎండ్పాయింట్కు సూచించాలి — ఇది మద్దతు లేని, సులభంగా విఫలమయ్యే సెటప్.

## క్లౌడ్ సమస్యలు

### క్లౌడ్ సింక్ లోపాలు

1. `BASE_URL` మీ రన్ అవుతున్న ఇన్స్టాన్స్ను సూచిస్తోందని నిర్ధారించుకోండి (ఉదా., `http://localhost:20128`)
2. `CLOUD_URL` మీ క్లౌడ్ ఎండ్పాయింట్ను సూచిస్తోందని నిర్ధారించుకోండి (ఉదా., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` విలువలను సర్వర్-సైడ్ విలువలతో సమలేఖనంలో ఉంచండి

### క్లౌడ్లో `stream=false` 500ను అందిస్తుంది

**లక్షణం:** నాన్-స్ట్రీమింగ్ కాల్స్ కోసం క్లౌడ్ ఎండ్పాయింట్లో `Unexpected token 'd'...`.

**కారణం:** క్లయింట్ JSONను ఆశిస్తున్నప్పుడు అప్స్ట్రీమ్ SSE పేలోడ్ను అందిస్తుంది.

**తాత్కాలిక పరిష్కారం:** క్లౌడ్కు నేరుగా చేసే కాల్స్ కోసం `stream=true` ఉపయోగించండి. లోకల్ రన్టైమ్లో SSE→JSON ఫాల్బ్యాక్ ఉంటుంది.

### క్లౌడ్ కనెక్ట్ అయిందని చూపుతున్నా "Invalid API key" అని చెబుతోంది

1. లోకల్ డ్యాష్బోర్డ్ (`/api/keys`) నుండి కొత్త కీని సృష్టించండి
2. క్లౌడ్ సింక్ను అమలు చేయండి: Enable Cloud → Sync Now
3. పాత/సింక్ కాని కీలు క్లౌడ్లో ఇప్పటికీ `401`ను అందించవచ్చు

## Docker సమస్యలు

### Docker IPv6 / కనెక్షన్ రీసెట్

<a name="docker-ipv6"></a>

**లక్షణాలు:** `curl http://localhost:20128/v1/models` అనేది `curl: (56) Recv failure: Connection reset by peer`ను అందిస్తుంది. డ్యాష్బోర్డ్ మరియు ప్రామాణీకరణ అవసరం లేని ఎండ్పాయింట్లు పనిచేస్తాయి, కానీ ప్రామాణీకరించబడిన ఎండ్పాయింట్లు విఫలమవుతాయి — ఇది ప్రామాణీకరణ సమస్యలా కనిపించినప్పటికీ వాస్తవానికి కాదు.

**కారణం:** `docker run -p 20128:20128` అనేది `0.0.0.0` (IPv4) మరియు `::` (IPv6) రెండింటిపైనా పోర్ట్ను ప్రచురిస్తుంది, కానీ కంటైనర్లోని ప్రాసెస్ IPv4లో మాత్రమే లిసన్ చేస్తుంది. `localhost` ముందుగా `::1`కు రిజాల్వ్ అయ్యే హోస్ట్లలో, కనెక్షన్ వెనుక లిసనర్ లేని IPv6 ప్రచురిత పోర్ట్పైకి చేరుతుంది → కనెక్షన్ రీసెట్ అవుతుంది.

**పరిష్కారం:**

1. **త్వరిత నిర్ధారణ:** `curl -4 http://localhost:20128/v1/models`ను అమలు చేయండి. ఇది `-4`తో పనిచేసి, అది లేకుండా విఫలమైతే, మీ వద్ద IPv6 బైండ్ అసమతుల్యత ఉంది.
2. **శాశ్వత పరిష్కారం:** మీ `docker run` కమాండ్లో `-p 127.0.0.1:20128:20128`ను ఉపయోగించడం ద్వారా IPv4కు స్పష్టంగా బైండ్ చేయండి:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ఇది IPv4 బైండ్ను నిర్బంధిస్తుంది, అలాగే అన్ని హోస్ట్ ఇంటర్ఫేస్లపై ప్రాక్సీ బహిర్గతం కాకుండా నివారిస్తుంది.

2. పోర్టబుల్ మోడ్ కోసం: `runner-cli` ఇమేజ్ టార్గెట్ను ఉపయోగించండి (CLIలు బండిల్ చేయబడ్డాయి)

4. `installed=true` మరియు `runnable=false` అయితే: బైనరీ కనుగొనబడింది, కానీ హెల్త్చెక్లో విఫలమైంది

### త్వరిత రన్టైమ్ ధ్రువీకరణ

```bash
curl -s http://localhost:20128/api/cli-tools/codex-settings | jq '{installed,runnable,commandPath,runtimeMode,reason}'
curl -s http://localhost:20128/api/cli-tools/claude-settings | jq '{installed,runnable,commandPath,runtimeMode,reason}'
curl -s http://localhost:20128/api/cli-tools/openclaw-settings | jq '{installed,runnable,commandPath,runtimeMode,reason}'
```

## డీబగ్గింగ్

### లాగ్ ఫైళ్లను ప్రారంభించండి

మీ `.env` ఫైల్లో `APP_LOG_TO_FILE=true`ను సెట్ చేయండి. అప్లికేషన్ లాగ్లు `logs/` కింద వ్రాయబడతాయి.
సెట్టింగ్లలో కాల్ లాగ్ పైప్లైన్ ప్రారంభించబడినప్పుడు, రిక్వెస్ట్ ఆర్టిఫ్యాక్ట్లు `${DATA_DIR}/call_logs/` కింద నిల్వ చేయబడతాయి.
పైప్లైన్ క్యాప్చర్ ప్రారంభించబడినప్పుడు, స్ట్రీమ్ చంక్ పేలోడ్లను మినహాయించడానికి `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false`ను సెట్ చేయండి లేదా ఆర్టిఫ్యాక్ట్ పరిమితిని KBలో మార్చడానికి `CALL_LOG_PIPELINE_MAX_SIZE_KB`ను సర్దుబాటు చేయండి.

### ప్రొవైడర్ ఆరోగ్యాన్ని తనిఖీ చేయండి

```bash
# హెల్త్ డ్యాష్బోర్డ్
http://localhost:20128/dashboard/health

# API హెల్త్ చెక్
curl http://localhost:20128/api/monitoring/health
```

### రన్టైమ్ నిల్వ

- ప్రధాన స్థితి: `${DATA_DIR}/storage.sqlite` (ప్రొవైడర్లు, కాంబోలు, అలియాస్లు, కీలు, సెట్టింగ్లు)
- వినియోగం: `storage.sqlite`లోని SQLite టేబుల్లు (`usage_history`, `call_logs`, `proxy_logs`) + ఐచ్ఛిక `${DATA_DIR}/call_logs/`
- అప్లికేషన్ లాగ్లు: `<repo>/logs/...` (`APP_LOG_TO_FILE=true`గా ఉన్నప్పుడు)
- కాల్ లాగ్ ఆర్టిఫ్యాక్ట్లు: కాల్ లాగ్ పైప్లైన్ ప్రారంభించబడినప్పుడు `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs పేజీలోని **Clean history** చర్య `call_logs`, పాత `request_detail_logs` మరియు లోకల్ `${DATA_DIR}/call_logs/` ఆర్టిఫ్యాక్ట్ డైరెక్టరీని క్లియర్ చేస్తుంది.

## సర్క్యూట్ బ్రేకర్ సమస్యలు

### ప్రొవైడర్ OPEN స్థితిలో నిలిచిపోయింది

ప్రొవైడర్ సర్క్యూట్ బ్రేకర్ OPEN స్థితిలో ఉన్నప్పుడు, కూల్డౌన్ గడువు ముగిసే వరకు అభ్యర్థనలు నిరోధించబడతాయి.

**పరిష్కారం:**

1. **డ్యాష్బోర్డ్ → సెట్టింగ్లు → స్థితిస్థాపకత**కు వెళ్లండి
2. ప్రభావిత ప్రొవైడర్కు సంబంధించిన సర్క్యూట్ బ్రేకర్ కార్డ్ను తనిఖీ చేయండి
3. అన్ని బ్రేకర్లను క్లియర్ చేయడానికి **అన్నింటినీ రీసెట్ చేయండి**పై క్లిక్ చేయండి లేదా కూల్డౌన్ గడువు ముగిసే వరకు వేచి ఉండండి
4. రీసెట్ చేసే ముందు ప్రొవైడర్ నిజంగా అందుబాటులో ఉందని నిర్ధారించుకోండి

### ప్రొవైడర్ సర్క్యూట్ బ్రేకర్ను పదేపదే ట్రిప్ చేస్తోంది

ప్రొవైడర్ పదేపదే OPEN స్థితిలోకి ప్రవేశిస్తుంటే:

1. వైఫల్య నమూనా కోసం **డ్యాష్బోర్డ్ → హెల్త్ → ప్రొవైడర్ హెల్త్**ను తనిఖీ చేయండి
2. **సెట్టింగ్లు → స్థితిస్థాపకత → ప్రొవైడర్ ప్రొఫైల్లు**కు వెళ్లి వైఫల్య పరిమితిని పెంచండి
3. ప్రొవైడర్ API పరిమితులను మార్చిందా లేదా మళ్లీ ప్రామాణీకరణ అవసరమా అని తనిఖీ చేయండి
4. లేటెన్సీ టెలిమెట్రీని సమీక్షించండి — అధిక లేటెన్సీ కారణంగా టైమ్అవుట్-ఆధారిత వైఫల్యాలు సంభవించవచ్చు

## ఆడియో ట్రాన్స్క్రిప్షన్ సమస్యలు

### "మద్దతు లేని మోడల్" లోపం

- మొదటి సెగ్మెంట్ మీకు క్రెడెన్షియల్స్ ఉన్న ప్రొవైడర్గా ఉండే మోడల్ idని ఉపయోగించండి (`openai/whisper-1`, `openrouter/deepgram/nova-3`). కేవలం `deepgram/nova-3`ను ఉపయోగించడానికి స్థానిక Deepgram కీ అవసరం.
- **డ్యాష్బోర్డ్ → ప్రొవైడర్లు**లో ప్రొవైడర్ కనెక్ట్ అయిందని నిర్ధారించుకోండి

### ట్రాన్స్క్రిప్షన్ ఖాళీగా వస్తోంది లేదా విఫలమవుతోంది

- మద్దతు ఉన్న ఆడియో ఫార్మాట్లను తనిఖీ చేయండి: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ఫైల్ పరిమాణం ప్రొవైడర్ పరిమితులలో ఉందని నిర్ధారించుకోండి (సాధారణంగా < 25MB)
- ప్రొవైడర్ కార్డ్లో ప్రొవైడర్ API కీ చెల్లుబాటును తనిఖీ చేయండి

## ట్రాన్స్లేటర్ డీబగ్గింగ్

| **చాట్ టెస్టర్** | లైవ్ సందేశాలను పంపి, హెడర్లతో సహా పూర్తి అభ్యర్థన/ప్రతిస్పందన పేలోడ్ను పరిశీలించండి                                    |

### సాధారణ ఫార్మాట్ సమస్యలు

- **థింకింగ్ ట్యాగ్లు కనిపించడం లేదు** — లక్ష్య ప్రొవైడర్ థింకింగ్కు మద్దతు ఇస్తుందా మరియు థింకింగ్ బడ్జెట్ సెట్టింగ్ను తనిఖీ చేయండి
- **టూల్ కాల్లు తొలగిపోతున్నాయి** — కొన్ని ఫార్మాట్ అనువాదాలు మద్దతు లేని ఫీల్డ్లను తొలగించవచ్చు; ప్లేగ్రౌండ్ మోడ్లో నిర్ధారించుకోండి
- **సిస్టమ్ ప్రాంప్ట్ కనిపించడం లేదు** — Claude మరియు Gemini సిస్టమ్ ప్రాంప్ట్లను వేర్వేరుగా నిర్వహిస్తాయి; అనువాద అవుట్పుట్ను తనిఖీ చేయండి
- **SDK ఆబ్జెక్ట్కు బదులుగా ముడి స్ట్రింగ్ను అందిస్తోంది** — v1.xలో పరిష్కరించబడింది; OpenAI SDK Pydantic ధ్రువీకరణ వైఫల్యాలకు కారణమయ్యే ప్రామాణికం కాని ఫీల్డ్లను (`x_groq`, `usage_breakdown`, మొదలైనవి) ప్రతిస్పందన శానిటైజర్ తొలగిస్తుంది. v3.x+లో కూడా ఇది కనిపిస్తే, దయచేసి సమస్యను నమోదు చేయండి.
- **GLM/ERNIE `system` రోల్ను తిరస్కరిస్తోంది** — v1.xలో పరిష్కరించబడింది; అనుకూలం కాని మోడల్ల కోసం రోల్ నార్మలైజర్ సిస్టమ్ సందేశాలను స్వయంచాలకంగా యూజర్ సందేశాల్లో విలీనం చేస్తుంది. v3.x+లో కూడా ఇది కనిపిస్తే, దయచేసి సమస్యను నమోదు చేయండి.
- **`developer` రోల్ గుర్తించబడటం లేదు** — v1.xలో పరిష్కరించబడింది; OpenAI కాని ప్రొవైడర్ల కోసం స్వయంచాలకంగా `system`కు మార్చబడుతుంది. v3.x+లో కూడా ఇది కనిపిస్తే, దయచేసి సమస్యను నమోదు చేయండి.
- **Geminiతో `json_schema` పనిచేయడం లేదు** — v1.xలో పరిష్కరించబడింది; ఇప్పుడు `response_format` అనేది Gemini యొక్క `responseMimeType` + `responseSchema`కు మార్చబడుతుంది. v3.x+లో కూడా ఇది కనిపిస్తే, దయచేసి సమస్యను నమోదు చేయండి.

- **Settings → Resilience → Provider Profiles**లో స్వయంచాలక రేట్-లిమిట్ ప్రారంభించబడిందో లేదో ధృవీకరించండి
- ప్రొవైడర్ `429` స్థితి కోడ్లు లేదా `Retry-After` హెడర్లను తిరిగి ఇస్తుందో లేదో తనిఖీ చేయండి

### ఎక్స్పోనెన్షియల్ బ్యాక్ఆఫ్ను ట్యూన్ చేయడం

- **ప్రాథమిక ఆలస్యం** — మొదటి వైఫల్యం తర్వాత ప్రారంభ నిరీక్షణ సమయం (డిఫాల్ట్: 1s)
- **గరిష్ఠ ఆలస్యం** — గరిష్ఠ నిరీక్షణ సమయ పరిమితి (డిఫాల్ట్: 30s)
- **గుణకం** — వరుసగా సంభవించే ప్రతి వైఫల్యానికి ఆలస్యాన్ని ఎంత పెంచాలి (డిఫాల్ట్: 2x)

### థండరింగ్ హెర్డ్ నివారణ

అనేక సమకాలీన అభ్యర్థనలు రేట్-లిమిట్ చేయబడిన ప్రొవైడర్ను చేరుకున్నప్పుడు, అభ్యర్థనలను క్రమబద్ధీకరించడానికి మరియు వరుస వైఫల్యాలను నివారించడానికి OmniRoute మ్యూటెక్స్ + స్వయంచాలక రేట్-లిమిటింగ్ను ఉపయోగిస్తుంది. API కీ ప్రొవైడర్లకు ఇది స్వయంచాలకంగా జరుగుతుంది.

### చాట్ అభ్యర్థనలు 503 / chat_admission_busyతో విఫలమవుతాయి

**లక్షణాలు:**

- చాట్ కంప్లీషన్స్ ఎండ్పాయింట్, ఎర్రర్ కోడ్
  `chat_admission_busy`గా ఉన్న మళ్లీ ప్రయత్నించదగిన `503` ప్రతిస్పందనను తిరిగి ఇస్తుంది.
- ప్రతిస్పందనలో `Retry-After` ఉంటుంది. #12135 నుంచి, దాని విలువ గమనించిన
  ఆక్యుపెన్సీ ఆధారంగా నిర్ణయించబడుతుంది — అభ్యర్థన ఇప్పటికే వేచి ఉన్న `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  విండో మరియు ప్రస్తుత హెవీవెయిట్ లీజ్లు కొనసాగిన సమయం, వీటిలో పెద్దది — పూర్తి
  సెకన్లకు పైకి రౌండ్ చేసి, 60 వద్ద పరిమితం చేయబడుతుంది. నిష్క్రియ గేట్పై ఇది చారిత్రక కనిష్ఠాలను ఉంచుతుంది:
  బైట్-ఆధారిత మార్గంలో 2 సెకన్లు, నిర్మాణ-ఆధారిత మార్గంలో 1 సెకను (ఇందులో
  `reason: "structure_limit"` కూడా ఉంటుంది).
- మరొక హెవీవెయిట్ చాట్ లేదా దీర్ఘకాలం నడిచే స్ట్రీమింగ్ ప్రతిస్పందన ఇంకా
  ప్రాసెస్లో ఉన్నప్పుడు ఇది జరగవచ్చు.

బైట్-ఆధారిత ప్రతిస్పందన బాడీ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

నిర్మాణ-ఆధారిత ప్రతిస్పందన అదే రకం మరియు కోడ్ను ఉపయోగిస్తుంది, దాని సందేశం
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
మరియు `reason: "structure_limit"`.
డిఫాల్ట్ థ్రెషోల్డ్ల వద్ద, ఒక అభ్యర్థనలో కనీసం `200` సందేశాలు,
కనీసం `64` టూల్స్ లేదా కనీసం `32,000` అంచనా టోకెన్లు ఉన్నప్పుడు, లేదా పరిమిత నిర్మాణ అంచనా
సందర్శించిన `10,000` నోడ్ల పరిమితిని లేదా లోతు `12` పరిమితిని చేరుకున్నప్పుడు, ఆ అభ్యర్థన నిర్మాణపరంగా హెవీగా పరిగణించబడుతుంది.

**కారణం:** ఇది OmniRoute లోపల ఉద్దేశపూర్వకంగా జరిగే లోడ్ షెడ్డింగ్, అప్స్ట్రీమ్-ప్రొవైడర్ వైఫల్యం కాదు.
పెద్ద అభ్యర్థన బాడీని నిల్వ చేసి పార్స్ చేయడానికి ముందు, పరిమిత హెవీవెయిట్ సామర్థ్యాన్ని రిజర్వ్ చేయడానికి
ప్రతి ప్రాసెస్ ఒక ప్రాసెస్-లోకల్ గార్డ్ను ఉపయోగిస్తుంది. SSE ప్రతిస్పందన జీవితకాలమంతా హెవీవెయిట్ లీజ్
కొనసాగుతుంది.

**#503-ఫ్యాన్అవుట్:** ఈ పరిష్కారానికి ముందు, హోస్ట్ మెమరీతో సంబంధం లేకుండా గార్డ్ సమకాలీనతను స్థిర అభ్యర్థన COUNTకు
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, డిఫాల్ట్ `1`) పరిమితం చేసేది, కాబట్టి కోడింగ్-ఏజెంట్
ఫ్యాన్అవుట్ (బహుళ సబ్ఏజెంట్లు/CLIలు, సాధారణంగా > 256 KB పరిమాణం గల బాడీలు) ప్రభావవంతమైన
సమకాలీనతను ~1కి తగ్గించి, పూర్తిగా సాధారణ లోడ్లోనే 503లకు దారితీసేది. ఇప్పుడు గార్డ్ స్వయంగా ట్యూన్ అవుతుంది: ప్రాసెస్
యొక్క వాస్తవ మెమరీ పరిమితి నుంచి పరిమాణం నిర్ణయించబడిన, స్వయంచాలకంగా ఉత్పన్నమైన ఇన్జెస్ట్ BYTE బడ్జెట్
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ద్వారా ఇది గేట్ చేయబడుతుంది, అలాగే ప్రత్యక్ష రిసోర్స్-ప్రెజర్
సిగ్నల్ను కూడా పరిగణిస్తుంది — కాబట్టి ఒకేసారి ఒకటి కంటే ఎక్కువ హెవీ అభ్యర్థనలు వచ్చాయనే కారణంతో కాకుండా,
హోస్ట్ నిజంగా మెమరీ ఒత్తిడిలో ఉన్నప్పుడు మాత్రమే ఇది లోడ్ను తగ్గిస్తుంది. పాత కౌంట్ పరిమితి
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ఇప్పటికీ గౌరవించబడుతుంది, కానీ మీరు దాన్ని స్పష్టంగా సెట్ చేసినప్పుడు మాత్రమే.

సామర్థ్యం బిజీగా ఉన్నప్పుడు, మళ్లీ ప్రయత్నించదగిన `503`తో సమాధానం ఇవ్వడానికి ముందు, ఒక స్లాట్ ఖాళీ కావడం కోసం హెవీవెయిట్ అభ్యర్థన మొదట
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` వరకు వేచి ఉంటుంది (డిఫాల్ట్గా `RATE_LIMIT_MAX_WAIT_MS`; `0` నిరీక్షణను నిలిపివేస్తుంది).
భారీ సబ్-అభ్యర్థనలను సమకాలీనంగా ఫ్యాన్అవుట్ చేసే ఏజెంట్-శైలి క్లయింట్లు
(OpenCode, Claude Code, Cursor), తక్షణ తిరస్కరణలపై తమ మొత్తం రీట్రై బడ్జెట్ను వృథా చేసి టాస్క్ మధ్యలో విఫలమవకుండా,
బర్స్ట్ను క్రమబద్ధీకరించడానికి ఈ పరిమిత నిరీక్షణ ఉంటుంది.
ప్రస్తుత హెవీవెయిట్ లీజ్ ఆక్యుపెన్సీ, నిర్ధారించబడిన బైట్ బడ్జెట్ మరియు ప్రత్యక్ష ప్రెజర్ తీవ్రత
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) వద్ద అందుబాటులో ఉంటాయి — ఏ env varను మార్చే ముందైనా వీటిని తనిఖీ చేయండి.
Settings → Resilience → Request Queue → Concurrent Requests దీన్ని నియంత్రించదు; ఆ సెట్టింగ్
ప్రత్యేక ప్రొవైడర్ అభ్యర్థన-క్యూ విధానాన్ని నియంత్రిస్తుంది.

**పరిష్కారం:**

1. ముందుగా మళ్లీ ప్రయత్నించండి. క్లయింట్లు అభ్యర్థనను వెంటనే
   పునరావృతం చేయకుండా `Retry-After`ను గౌరవించి బ్యాక్ఆఫ్ను ఉపయోగించాలి.
2. ఏదైనా ట్యూన్ చేసే ముందు `/api/monitoring/health` → `chatAdmission`ను తనిఖీ చేయండి. `countCapEnabled:
false` మరియు తగినంత పెద్ద `maxInflightBytes` అంటే స్వయంచాలకంగా ఉత్పన్నమైన బడ్జెట్ ఇప్పటికే తన
   పనిని చేస్తోందని అర్థం; `high`/`critical`గా ఉన్న `pressureSeverity` అంటే హోస్ట్లో నిజంగానే మెమరీ తక్కువగా ఉందని అర్థం —
   అడ్మిషన్ env varతో దీన్ని పరిష్కరించలేరు; దీనికి ఎక్కువ RAM లేదా చిన్న వర్క్లోడ్ అవసరం.
3. `/api/monitoring/health`లో స్వయంచాలకంగా ఉత్పన్నమైన బడ్జెట్ మీ
   హోస్ట్కు నిజంగానే చాలా చిన్నదని చూపితే మాత్రమే (ఇది అరుదు — ఇది ఇప్పటికే కంటైనర్ నుంచి బేర్-మెటల్ వరకు స్కేల్ అవుతుంది), పాత అభ్యర్థన-కౌంట్ పరిమితికి తిరిగి వెళ్లకుండా
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`తో దాన్ని నేరుగా ఓవర్రైడ్ చేయండి.

అధికారిక అడ్మిషన్ సెట్టింగ్ల కోసం [ఎన్విరాన్మెంట్-వేరియబుల్ రిఫరెన్స్](../reference/ENVIRONMENT.md#4-security--authentication)ను
చూడండి.

## ఐచ్ఛిక RAG / LLM వైఫల్య వర్గీకరణ (16 సమస్యలు)

కొంతమంది OmniRoute వినియోగదారులు గేట్వేను RAG లేదా ఏజెంట్ స్టాక్ల ముందు ఉంచుతారు. అలాంటి సెటప్లలో ఒక విచిత్రమైన నమూనా కనిపించడం సాధారణం: OmniRoute ఆరోగ్యంగా కనిపిస్తుంది (ప్రొవైడర్లు అందుబాటులో ఉంటారు, రూటింగ్ ప్రొఫైల్లు సరిగ్గా ఉంటాయి, రేట్ లిమిట్ హెచ్చరికలు ఉండవు), కానీ తుది సమాధానం మాత్రం తప్పుగా ఉంటుంది.

ఆచరణలో, ఈ సంఘటనలు సాధారణంగా గేట్వే నుంచే కాకుండా, దిగువన ఉన్న RAG పైప్లైన్ నుండి వస్తాయి.

ఆ వైఫల్యాలను వివరించడానికి మీకు ఉమ్మడి పదజాలం కావాలంటే, WFGY ProblemMapను ఉపయోగించవచ్చు. ఇది పునరావృతమయ్యే పదహారు RAG / LLM వైఫల్య నమూనాలను నిర్వచించే, MIT లైసెన్స్ కలిగిన బాహ్య పాఠ్య వనరు. స్థూలంగా ఇది వీటిని కవర్ చేస్తుంది:

- రిట్రీవల్ డ్రిఫ్ట్ మరియు దెబ్బతిన్న కాంటెక్స్ట్ సరిహద్దులు
- ఖాళీగా లేదా పాతబడిపోయిన ఇండెక్స్లు మరియు వెక్టర్ స్టోర్లు
- ఎంబెడింగ్ మరియు సెమాంటిక్ అర్థం మధ్య అసమతుల్యత
- ప్రాంప్ట్ అసెంబ్లీ మరియు కాంటెక్స్ట్ విండో సమస్యలు
- లాజిక్ కుప్పకూలడం మరియు అతివిశ్వాసంతో ఇచ్చే సమాధానాలు
- దీర్ఘ చైన్ మరియు ఏజెంట్ సమన్వయ వైఫల్యాలు
- మల్టీ-ఏజెంట్ మెమరీ మరియు పాత్ర డ్రిఫ్ట్
- డిప్లాయ్మెంట్ మరియు బూట్స్ట్రాప్ క్రమ సమస్యలు

ఆలోచన సులభమే:

1. తప్పు ప్రతిస్పందనను పరిశోధిస్తున్నప్పుడు, వీటిని నమోదు చేయండి:
   - వినియోగదారు టాస్క్ మరియు అభ్యర్థన
   - OmniRouteలోని రూట్ లేదా ప్రొవైడర్ కాంబో
   - దిగువన ఉపయోగించిన ఏదైనా RAG కాంటెక్స్ట్ (రిట్రీవ్ చేసిన డాక్యుమెంట్లు, టూల్ కాల్లు మొదలైనవి)
2. సంఘటనను ఒకటి లేదా రెండు WFGY ProblemMap నంబర్లకు (`No.1` … `No.16`) మ్యాప్ చేయండి.
3. OmniRoute లాగ్ల పక్కన, ఆ నంబర్ను మీ స్వంత డ్యాష్బోర్డ్, రన్బుక్ లేదా ఇన్సిడెంట్ ట్రాకర్లో నిల్వ చేయండి.
4. మీ RAG స్టాక్, రిట్రీవర్ లేదా రూటింగ్ వ్యూహాన్ని మార్చాల్సిన అవసరం ఉందో లేదో నిర్ణయించడానికి సంబంధిత WFGY పేజీని ఉపయోగించండి.

పూర్తి పాఠ్యం మరియు నిర్దిష్ట విధానాలు ఇక్కడ ఉన్నాయి (MIT లైసెన్స్, పాఠ్యం మాత్రమే):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

మీరు OmniRoute వెనుక RAG లేదా ఏజెంట్ పైప్లైన్లను అమలు చేయకపోతే, ఈ విభాగాన్ని విస్మరించవచ్చు.

## v3.8.0లో తెలిసిన సమస్యలు

v3.8.0 విడుదలకు ప్రత్యేకమైన సమస్యలు మరియు వాటి ప్రస్తుత తాత్కాలిక పరిష్కారాలు. తరువాతి ప్యాచ్లో పరిష్కారం అందుబాటులోకి వస్తే, ఈ నమోదు నవీకరించబడుతుంది లేదా తొలగించబడుతుంది.

### Devin CLI ప్రామాణీకరణ వైఫల్యాలు

**లక్షణాలు:**

- Devin ఆధారిత టూల్లను అమలు చేసినప్పుడు "Devin CLI కనుగొనబడలేదు" లేదా "ప్రామాణీకరణ విఫలమైంది" అని కనిపించడం
- CLI రన్టైమ్ తనిఖీ `installed=false` అని నివేదించడం

**కారణాలు:**

- `CLI_DEVIN_BIN` ఉనికిలో లేని పాత్ను సూచిస్తోంది
- హోస్ట్లో Devin CLI ఇన్స్టాల్ చేయబడలేదు

**పరిష్కారం:**

1. మీ ప్లాట్ఫారమ్ కోసం Devin CLIను ఇన్స్టాల్ చేయండి
2. `.env`లో `CLI_DEVIN_BIN=/usr/local/bin/devin` (లేదా అసలు పాత్) సెట్ చేయండి
3. OmniRouteను పునఃప్రారంభించి, **డ్యాష్బోర్డ్ → CLI టూల్స్** నుండి మళ్లీ పరీక్షించండి

### మోడల్ కూల్డౌన్ నిలిచిపోవడం (మాన్యువల్ రీసెట్)

**లక్షణాలు:**

- గడువు ముగిసిన తర్వాత కూడా మోడల్ కూల్డౌన్లో ఉన్నట్లు జాబితాలో కనిపించడం
- టైమ్స్టాంప్ గతంలో ఉన్నప్పటికీ, కాంబో రూటింగ్లో అభ్యర్థనలు ఇప్పటికీ ఆ మోడల్ను దాటవేయడం

**మాన్యువల్ రీసెట్:**

- **డ్యాష్బోర్డ్:** **సెట్టింగ్లు → మోడల్ కూల్డౌన్లు** → ప్రభావిత కార్డ్పై **మళ్లీ ప్రారంభించు** క్లిక్ చేయండి
- **API:** మేనేజ్మెంట్ ప్రామాణీకరణ హెడర్లతో `DELETE /api/resilience/model-cooldowns`

### Command Code ప్రొవైడర్ కనెక్షన్ 403తో విఫలమవడం

**లక్షణాలు:**

- Command Code ప్రొవైడర్ కనెక్షన్ను పరీక్షిస్తున్నప్పుడు 403 రావడం
- కొత్తగా జోడించిన తర్వాత ప్రొవైడర్ కార్డ్ "అనధికారికం" అని చూపించడం

**కారణం:** OAuth ఫ్లో పూర్తికాలేదు (కాల్బ్యాక్ అందలేదు లేదా టోకెన్ నిల్వ చేయబడలేదు).

**పరిష్కారం:**

- OAuth ఫ్లోను మళ్లీ ట్రిగ్గర్ చేయడానికి CLI నుండి `omniroute providers` అమలు చేయండి, లేదా
- **డ్యాష్బోర్డ్ → ప్రొవైడర్లు → Command Code → మళ్లీ కనెక్ట్ చేయండి** నుండి OAuthను మళ్లీ అమలు చేయండి

### ModelScope తీవ్రమైన 429 కూల్డౌన్లను అందించడం

**లక్షణాలు:**

- కొద్దిపాటి అభ్యర్థనల బర్స్ట్ తర్వాత ModelScopeలో చాలా చిన్న లేదా తక్షణ కూల్డౌన్లు ఏర్పడడం
- ఊహించిన దానికంటే ముందుగానే కాంబో రూటింగ్ ModelScopeను దాటవేయడం

**కారణం:** ModelScope ప్రొవైడర్కు ప్రత్యేకమైన `Retry-After` హెడర్లను పంపుతుంది. v3.8.0లో ఆ హెడర్ల కోసం ప్రత్యేక హ్యాండ్లింగ్ అందించబడింది, కాబట్టి పాత వెర్షన్లు వాటిని సాధారణ రేట్-లిమిట్ సూచనలుగా తప్పుగా అర్థం చేసుకుంటాయి.

**పరిష్కారం:**

- మీరు v3.8.0 లేదా తరువాతి వెర్షన్ను ఉపయోగిస్తున్నారని నిర్ధారించుకోండి
- **సెట్టింగ్లు → రెసిలియెన్స్** కింద `useUpstream429BreakerHints` టాగుల్ ప్రారంభించబడి ఉందని ధృవీకరించండి

### ప్రొడక్షన్లో OMNIROUTE_WS_BRIDGE_SECRET లేకపోవడం

**లక్షణాలు:**

- రిమోట్ ప్రొడక్షన్ హోస్ట్లో అమలు చేస్తున్నప్పుడు ప్రతి Codex/Responses WebSocket బ్రిడ్జ్ అభ్యర్థనపై 401 రావడం
- కనెక్ట్ అయిన వెంటనే WebSocket బ్రిడ్జ్ హ్యాండ్షేక్ మూసివేయబడడం

**కారణం:** ప్రొడక్షన్ ఎన్విరాన్మెంట్లో `OMNIROUTE_WS_BRIDGE_SECRET` ఎన్విరాన్మెంట్ వేరియబుల్ లేదు.

**పరిష్కారం:**

1. యాదృచ్ఛిక సీక్రెట్ను రూపొందించండి: `openssl rand -hex 32`
2. ప్రొడక్షన్ సర్వర్ ఎన్విరాన్మెంట్లో (మరియు బ్రిడ్జ్తో కమ్యూనికేట్ చేసే ఏదైనా క్లయింట్లో) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` సెట్ చేయండి
3. OmniRouteను పునఃప్రారంభించండి

### Responses API: బ్యాక్గ్రౌండ్ మోడ్ సింక్రోనస్కు తగ్గించబడటం

**లక్షణాలు:**

- లాగ్ చేయబడిన హెచ్చరిక: `background mode degraded to synchronous`
- `background: true` అభ్యర్థన బ్యాక్గ్రౌండ్ జాబ్ హ్యాండిల్కు బదులుగా సాధారణ సింక్రోనస్ ప్రతిస్పందనను అందించడం

**కారణం:** v3.8.0లో Responses APIపై `background: true` ఉద్దేశపూర్వకంగా సింక్రోనస్ అమలుకు తగ్గించబడుతుంది మరియు అదే సమయంలో హెచ్చరికను జారీ చేస్తుంది. పూర్తి అసింక్రోనస్ బ్యాక్గ్రౌండ్ అమలు భవిష్యత్తులో అందించాల్సిన ఫీచర్.

**పరిష్కారం:**

- `background` లేకుండా కాల్ చేసేలా క్లయింట్ను సర్దుబాటు చేయండి, లేదా
- పూర్తి అసింక్రోనస్ బ్యాక్గ్రౌండ్ మోడ్ను అందించే తరువాతి విడుదల కోసం వేచి ఉండండి (చేంజ్లాగ్ను అనుసరించండి)

## నెమ్మదైన ప్రారంభం / సిద్ధత సమయం ముగిసింది

CLIలో `⚠ Server did not respond within 60s` అని కనిపించినప్పటికీ సర్వర్ వాస్తవంగా పనిచేస్తుంటే, మీ వాతావరణానికి సిద్ధత తనిఖీ కోసం కేటాయించిన సమయం చాలా తక్కువగా ఉంది.

ఇది సాధారణంగా Windowsలో (యాంటీవైరస్, ఫైల్సిస్టమ్ వాచర్లు) లేదా ప్రారంభ సమయంలో అధిక పనిభారం ఉన్న కంటైనర్లలో జరుగుతుంది.

**పరిష్కారం — సమయ పరిమితిని పెంచండి:**

```bash
# పర్యావరణ వేరియబుల్ ద్వారా (ప్రారంభాల మధ్య కొనసాగుతుంది):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 నిమిషాలు
omniroute serve

# CLI ఫ్లాగ్ ద్వారా (ఒక్కసారి మాత్రమే):
omniroute serve --ready-timeout 180000
```

డిఫాల్ట్ విలువ 60 000 ms (60 s). ఈ హెచ్చరిక కేవలం సమాచార ప్రయోజనం కోసం మాత్రమే; సర్వర్ నేపథ్యంలో ప్రారంభమవడం కొనసాగుతుంది మరియు బూట్ పూర్తయిన తర్వాత అందుబాటులోకి వస్తుంది.

`OMNIROUTE_READY_TIMEOUT_MS` గురించి పూర్తి వివరాల కోసం [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) చూడండి.
