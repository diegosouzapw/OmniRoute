## వివరణాత్మక సమస్య పరిష్కారం

---

### ఉచిత ప్రొవైడర్లపై రేట్ పరిమితి (429 / 400 / 401)

**లక్షణం**: ఉచిత/ప్రామాణీకరణ అవసరం లేని ప్రొవైడర్లతో (opencode, auggie మొదలైనవి) `model: "auto"` ఉపయోగిస్తున్నప్పుడు, సమాధానాలకు బదులుగా అప్పుడప్పుడు `HTTP 429`, `400` లేదా `401` వస్తుంది. కొన్ని క్షణాల తర్వాత అదే ప్రాంప్ట్ను మళ్లీ ప్రయత్నిస్తే అభ్యర్థనలు విజయవంతమవుతాయి, కానీ మొదటి వైఫల్యంతో ఆటోమేషన్ (cron జాబ్లు, ఏజెంట్లు, స్క్రిప్ట్లు) నిలిచిపోతుంది.

**మూల కారణం**: మూడు స్వతంత్ర వైఫల్య రీతులు ఒకదానిపై మరొకటి ప్రభావం చూపుతాయి:

1. **ప్రొవైడర్ రేట్ పరిమితి (`429`)**: ఉచిత టియర్లు ప్రతి సమయ విండోకు ఒక కోటాను అమలు చేయవచ్చు. ఒకేసారి వచ్చే సమాంతర కాల్లు దాన్ని పూర్తిగా వినియోగిస్తాయి, కాబట్టి విండో రీసెట్ అయ్యే వరకు తదుపరి అభ్యర్థన తిరస్కరించబడుతుంది.
2. **పాస్త్రూలో పనిచేయని మోడల్ (`400`/`401`)**: `auto/*` పూల్లలో `opencode` నుండి వచ్చిన, కేటలాగ్లో నమోదై ఉన్నప్పటికీ సక్రియ క్రెడెన్షియల్లు లేని పాస్త్రూ మోడల్లు ఉండవచ్చు (ఉదా. `oc/north-mini-code-free` → `401`). ఆటో-రౌటర్ ఒకదాన్ని ప్రయత్నించి విఫలమవుతుంది, ఫాల్బ్యాక్ అమలయ్యేలోపే లోపం ముందుకు పంపబడుతుంది.
3. **కంకరెన్సీ విస్తరణ (లోడ్లో `429`)**: అనేక ఏజెంట్/cron సెషన్లు ఒకేసారి `auto`ను యాక్సెస్ చేసినప్పుడు, మొత్తం అభ్యర్థన రేటు ఉచిత ప్రొవైడర్లు భరించగల స్థాయిని మించిపోతుంది, అందువల్ల చెల్లుబాటు అయ్యే కాల్లు కూడా దుర్వినియోగమైనవిగా గుర్తించబడతాయి.

**ధృవీకరించిన పరిష్కారం (కమ్యూనిటీ నివేదిక, 2026-08-10)**: రొటేషన్, కంకరెన్సీ, ఫాల్బ్యాక్లు ఉచిత-టియర్ అస్థిరత కారణంగా విఫలమవకుండా దాన్ని తట్టుకునేలా ఈ మూడు ఎన్విరాన్మెంట్ వేరియబుల్లను సర్దుబాటు చేయండి:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 వచ్చినప్పుడు మరొక మోడల్/ప్రొవైడర్కు మారుతుంది (పనిచేయని పాస్త్రూ మోడల్లను దాటవేస్తుంది)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # హెవీవెయిట్ అడ్మిషన్కు స్పష్టమైన గరిష్ఠ పరిమితి (డిఫాల్ట్గా సెట్ చేయబడదు: అభ్యర్థనల సంఖ్యపై పరిమితి లేదు, దిగువ గమనిక చూడండి)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # వెంటనే మళ్లీ ప్రయత్నించగల 503 ఇవ్వడానికి బదులుగా హెవీవెయిట్ సామర్థ్యం కోసం ఎక్కువసేపు పరిమిత నిరీక్షణ
```

వీటిని OmniRoute ప్రాసెస్ ఎన్విరాన్మెంట్లో (డీమన్లో, ఉదా. LaunchAgent plist లేదా `systemctl edit` ద్వారా) సెట్ చేసి, ఆపై OmniRouteను రీస్టార్ట్ చేయండి. రొటేషన్ ఫ్లాగ్ అత్యధిక ప్రభావం చూపే ఏకైక నియంత్రణ: ఇది తీవ్రమైన వైఫల్యాన్ని పూల్లోని ఆరోగ్యకరమైన ప్రొవైడర్పై పారదర్శకంగా మళ్లీ ప్రయత్నించే ప్రక్రియగా మారుస్తుంది.

**గమనిక**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ఒకేసారి ఎన్ని హెవీవెయిట్ — దీర్ఘ-కాంటెక్స్ట్ — అభ్యర్థనలు రన్ కావచ్చో పరిమితం చేస్తుంది; ఈ పరిమితి ఒక అడ్మిషన్ గేట్ మాత్రమే, ప్రొవైడర్ రేట్ లిమిటర్ కాదు. **#503-fanout నవీకరణ:** ఈ వేరియబుల్ ఇకపై డిఫాల్ట్గా సెట్ చేయబడదు (ఇప్పుడు పైన చూపినట్లుగా స్పష్టంగా కాన్ఫిగర్ చేసినప్పుడు మాత్రమే ఇది వర్తిస్తుంది) — బదులుగా, హెవీవెయిట్ అడ్మిషన్ను హోస్ట్ వాస్తవ మెమరీ పరిమితి ఆధారంగా స్వయంగా స్కేల్ అయ్యే, ఆటోమేటిక్గా నిర్ధారించిన బైట్ బడ్జెట్ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) నియంత్రిస్తుంది. అందువల్ల కొత్త డిప్లాయ్మెంట్లో ఈ వేరియబుల్ను అసలు సెట్ చేయకుండానే చాలా తక్కువ `503 chat_admission_busy` తిరస్కరణలు కనిపించాలి; ఇక్కడ దీన్ని స్పష్టంగా సెట్ చేయడం ఇప్పటికీ డాక్యుమెంట్ చేసిన విధంగానే పనిచేస్తుంది. స్పష్టమైన బైట్-బడ్జెట్ ఓవర్రైడ్లు 8 MiB–2 GiB పరిధికి పరిమితం చేయబడతాయి. `413 body_exceeds_budget` తాత్కాలికమైనది కాదు: ఆ బైట్ బడ్జెట్ను పెంచండి, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`ను తగ్గించండి లేదా ప్రాసెస్ మెమరీ పరిమితిని పెంచండి. `inflight_bytes_budget` షెడ్ అనేది తాత్కాలిక వనరుల పోటీ, కాబట్టి దాన్ని మళ్లీ ప్రయత్నించవచ్చు. ప్రతి ప్రొవైడర్కు సంబంధించిన రేట్ పరిమితి (`open-sse/services/rateLimitManager.ts`) `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, మరియు `RATE_LIMIT_AUTO_ENABLE` ద్వారా విడిగా నియంత్రించబడుతుంది — `.env.example` చూడండి.

**ఇది పనిచేసిందని ఎలా ధృవీకరించాలి**: మీ ఏజెంట్/cronను వెంటవెంటనే రెండుసార్లు రన్ చేసి, రెండూ విజయవంతమయ్యాయని నిర్ధారించండి. పరిష్కారానికి ముందు, రెండవ రన్ సాధారణంగా `429`/`401`ను విసురుతుంది. పరిష్కారం తర్వాత, వైఫల్యాలు (ఏవైనా ఉంటే) పారదర్శకంగా మళ్లీ ప్రయత్నించబడతాయి మరియు కాల్ పూర్తవుతుంది. మీరు `curl /monitoring/health`ను కూడా రన్ చేసి, ప్రొవైడర్ కనెక్షన్లలోని `rateLimitedUntil` ఫీల్డ్ను మరియు ప్రభావిత ప్రొవైడర్ల కోసం `circuitBreakers.providerBreakers[].state`ను గమనించవచ్చు — స్థితి `CLOSED`, `DEGRADED`, `OPEN` లేదా `HALF_OPEN`లో ఒకటిగా ఉంటుంది (`src/shared/utils/circuitBreaker.ts` చూడండి), అలాగే పదేపదే విఫలమయ్యే ప్రొవైడర్లో రీసెట్ విండో ఒక ప్రోబ్ను అనుమతించే ముందు స్థితి `CLOSED → DEGRADED → OPEN`గా మారుతుంది (`HALF_OPEN`).

**మీకు ఇంకా 429 కనిపిస్తే**: ఆ ప్రొవైడర్కు ప్రస్తుతం సక్రియంగా ఉన్న ఖాతా తన _కోటా_ను నిజంగానే పూర్తిగా వినియోగించుకుంది (ఇది కేవలం రేట్ పరిమితి కాదు). OmniRoute డ్యాష్బోర్డ్లో → Providers → Accounts ద్వారా అదే ప్రొవైడర్కు రెండవ ఖాతాను జోడించండి, లేదా మరో ఉచిత ప్రొవైడర్ను (ఉదా. `routeway`, `auggie`) కలిపి ఉపయోగించండి. రొటేషన్ తాత్కాలిక రేట్/400/401 సమస్యల విషయంలో మాత్రమే సహాయపడుతుంది; కోటా పూర్తిగా అయిపోయినప్పుడు రెండవ క్రెడెన్షియల్ లేదా వేరే ప్రొవైడర్ అవసరం.

**విజన్ మోడళ్లలో (`auto/vision`, `bazaarlink/*`) 403 కనిపిస్తే**: కనెక్ట్ చేసిన ఖాతాకు విజన్ను కలిగి ఉన్న చెల్లింపు ప్లాన్ లేదు, లేదా API కీకి తగిన అనుమతులు లేవు. ప్రొవైడర్ డ్యాష్బోర్డ్లో కీ స్కోప్లో విజన్/మల్టీమోడల్ ఉన్నట్లు ధృవీకరించండి, లేదా చెల్లింపు టియర్ ఖాతాను కనెక్ట్ చేసి దానిని విజన్ లక్ష్యంగా ఉంచండి.

## npm install హెచ్చరికలు (ERESOLVE / peer / deprecated)

మీరు `npm install -g omniroute` అమలు చేసినప్పుడు, `npm warn ERESOLVE`, peer-dependency నోటీసులు మరియు `deprecated` సందేశాల వంటి అనేక హెచ్చరికలు కనిపించవచ్చు. **ఇవి ఊహించినవే మరియు హానికరం కావు.** అవుట్పుట్లో `added <N> packages` కనిపిస్తే, మీ ఇన్స్టాలేషన్ విజయవంతమైనట్లే.

peer-dependency పరిష్కార హెచ్చరికలను అణచివేయడానికి, OmniRoute మద్దతిచ్చే ఇన్స్టాలేషన్ రూపాన్ని ఉపయోగించండి:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` కేవలం `ERESOLVE` మరియు peer-dependency నోటీసులను మాత్రమే అణచివేస్తుంది. డిప్రికేషన్ నోటీసులు ట్రాన్సిటివ్ థర్డ్-పార్టీ ప్యాకేజీల నుండి వస్తాయి కాబట్టి అవి కనిపిస్తూనే ఉంటాయి; ఇన్స్టాలేషన్ విఫలమైందని అవి సూచించవు.

OmniRoute నియంత్రణలో లేని థర్డ్-పార్టీ ప్యాకేజీలలోని పాత peer-dependency పరిధుల కారణంగా ఈ హెచ్చరికలు వస్తాయి:

1. **`marked-terminal`కి `marked >=1 <16` కావాలి, కానీ `marked@18` కనుగొనబడింది** — ఆచరణలో ఇది సరిగ్గా పనిచేస్తుంది; upstream peer పరిధి కేవలం పాతది.
2. **`deprecated prebuild-install@7.1.3`** — ఇది ట్రాన్సిటివ్ నేటివ్-బైనరీ ఫెచ్ సహాయకం. పిన్ చేసిన `wreq-js` ట్రాన్స్పోర్ట్ బైండింగ్ను ఇన్స్టాల్ చేయడానికి ఇది
   ఉపయోగించబడదు మరియు web-cookie ప్రొవైడర్ ట్రాన్స్పోర్ట్ సెటప్ విఫలమైందని
   సూచించదు.

**ఎటువంటి చర్య అవసరం లేదు** — upstream ప్యాకేజీలను ఫోర్క్ చేయకుండా ఈ హెచ్చరికలను పూర్తిగా అణచివేయడం సాధ్యం కాదు.

## యాంటీవైరస్ తప్పుడు పాజిటివ్లు

<a name="antivirus-false-positives"></a>

### Avast/AVG ద్వారా `MD:HttpRequest-inf[Susp]`తో `README.md` క్వారంటైన్ చేయబడటం

**ఇది తప్పుడు పాజిటివ్. దేనికీ ఇన్ఫెక్షన్ లేదు, ఎలాంటి చర్యా అవసరం లేదు.**

అనేక HTTP అభ్యర్థనల వలె కనిపించే లింకులను కలిగి ఉన్న సాధారణ టెక్స్ట్/Markdown ఫైళ్లను ఫ్లాగ్ చేసే హ్యూరిస్టిక్ను Avast మరియు AVG అమలు చేస్తాయి. OmniRoute యొక్క `README.md` npm ప్యాకేజీలోనే వస్తుంది (ఇది `package.json` → `files`లో జాబితా చేయబడింది), కాబట్టి గ్లోబల్ ఇన్స్టాల్లో అది `node_modules/omniroute/README.md` వద్దకు చేరుతుంది — అలాగే అందులో దాదాపు 15 `http://localhost:20128/...` ఉదాహరణలు (MCP HTTP/SSE ఎండ్పాయింట్లు, A2A `.well-known` URL మరియు `curl` స్నిప్పెట్లు) ఉన్నాయి. అంతటి లింక్ సాంద్రత హ్యూరిస్టిక్ను ట్రిగ్గర్ చేయడానికి సరిపోతుంది.

ఇది ఇటీవలే ప్రారంభమై ఉంటే: ఫైల్ స్వభావం మారలేదు. READMEలోని ఎండ్పాయింట్ల పట్టిక విస్తరించింది (MCP HTTP + SSE + A2A జోడించబడ్డాయి), అలాగే మరిన్ని `curl` ఉదాహరణలు చేరాయి; దీనివల్ల అది పరిమితిని దాటింది.

ఈ ఫైల్ ఎటువంటి ఎక్జిక్యూటబుల్ కంటెంట్ లేని నిష్క్రియాత్మక డాక్యుమెంటేషన్ మాత్రమే. మీరు దాన్ని క్వారంటైన్ నుండి సురక్షితంగా పునరుద్ధరించవచ్చు.

**ఏం చేయాలి:**

1. **నోటిఫికేషన్లను ఆపండి** — మీ యాంటీవైరస్లో ఇన్స్టాల్ డైరెక్టరీని మినహాయించండి
   (Avast: Settings → Exceptions); మీ గ్లోబల్ `node_modules` పాత్ను మరియు/లేదా
   OmniRoute డేటా డైరెక్టరీని (`~/.omniroute/`) జోడించండి.
2. **తప్పుడు పాజిటివ్ను నివేదించండి** — <https://www.avast.com/false-positive-file-form.php>,
   క్వారంటైన్ చేయబడిన `README.md`ను జతచేయండి. ఒక టెక్స్ట్ ఫైల్పై విక్రేత హ్యూరిస్టిక్ అతిగా స్పందించడం వల్ల ఇది జరుగుతోంది కాబట్టి, అందరికీ ఉపయోగపడే పరిష్కారం ఇదే.

**మా వైపు నుంచి దీన్ని ఎందుకు "పరిష్కరించము":** ఉదాహరణలన్నీ `http://localhost`ను ఉపయోగిస్తాయి, అలాగే సెల్ఫ్-సైన్డ్ సర్టిఫికేట్ ఇబ్బందులు లేకుండా localhostను `https`గా ఉపయోగించడం సాధ్యం కాదు. ఒక విక్రేత హ్యూరిస్టిక్ను తప్పించుకోవడానికి డాక్యుమెంటేషన్ను వక్రీకరించడం, స్కానర్ బగ్ను సంతృప్తిపరచడం కోసం ప్రతి పాఠకుడికీ ఇబ్బంది కలిగిస్తుంది.

### Kaspersky డెస్క్టాప్ యాప్ను `PDM:Trojan.Win32.Generic`గా ఫ్లాగ్ చేయడం

**ఇది బిహేవియరల్ హ్యూరిస్టిక్ వల్ల ఏర్పడిన తప్పుడు పాజిటివ్. దేనికీ ఇన్ఫెక్షన్ లేదు.** Kasperskyలోని
`PDM:` ప్రిఫిక్స్ అంటే, తెలిసిన మాల్వేర్తో సరిపోల్చడం కాకుండా ఇన్స్టాలర్ _ఏం చేస్తుందో_ విశ్లేషించే దాని Proactive Defense Module (System Watcher) నుంచి ఈ నిర్ధారణ వచ్చిందని అర్థం. ఇది ట్రిగ్గర్ అయినప్పుడు, Kaspersky మొత్తం ఇన్స్టాలేషన్ను "రోల్ బ్యాక్" చేస్తుంది — అది అప్పటికే వ్రాసిన ఫైళ్లను తొలగిస్తుంది — అందువల్ల యాప్ పనిచేయకుండా పోవచ్చు లేదా పూర్తిగా కనిపించకపోవచ్చు.

అది ఫ్లాగ్ చేసే ఫైళ్లు డెస్క్టాప్ యాప్తో బండిల్ చేయబడిన, ప్రకటిత ఓపెన్-సోర్స్ డిపెండెన్సీలలోని ప్రామాణిక భాగాలు. ఉదాహరణకు:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` మరియు
  `workerProcessEntry.js` — యాప్లోనే ప్రొవైడర్ లాగిన్ మరియు బ్రౌజర్ ఆధారిత చాట్ కోసం ఉపయోగించే బ్రౌజర్-ఆటోమేషన్ లైబ్రరీ [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — వెబ్-కుకీ ప్రొవైడర్లపై బ్రౌజర్-ఫింగర్ప్రింటెడ్ HTTP కోసం ఉపయోగించే, పిన్ చేయబడిన `wreq-js` నేటివ్ బైండింగ్ (`<arch>` అనేది `x64` లేదా `arm64`).

**ఇది ఎందుకు ట్రిగ్గర్ అవుతుంది:** Windows ఇన్స్టాలర్కు **ఇంకా కోడ్ సంతకం చేయలేదు**, కాబట్టి సంతకం చేయని NSIS ఇన్స్టాలర్కు ఎలాంటి రెప్యుటేషన్ ఉండదు మరియు బిహేవియరల్ హ్యూరిస్టిక్లు గరిష్ఠ దూకుడుతో అమలవుతాయి. దీనితో పాటు బండిల్ చేయబడిన నేటివ్ DLL మరియు `%LOCALAPPDATA%\Programs\OmniRoute` కింద వ్రాయబడే వందలాది `.js` ఫైళ్లు (Next.js స్టాండ్అలోన్ బిల్డ్లోని హ్యాష్-సఫిక్స్ కలిగిన ప్యాకేజీ డైరెక్టరీలతో సహా) ఉండటం హ్యూరిస్టిక్ను ట్రిగ్గర్ చేయడానికి సరిపోతుంది. కోడ్ సైనింగ్ ప్రణాళికలో ఉంది; అది అమల్లోకి వచ్చే వరకు కొత్త విడుదలల్లో ఇది మళ్లీ జరగవచ్చు.

**ఏం చేయాలి:**

1. **మొదట మీ డౌన్లోడ్ను ధృవీకరించండి** (ఫైల్లో ఎవరైనా మార్పులు చేశారనే అవకాశాన్ని ఇది తోసిపుచ్చుతుంది). ప్రతి విడుదల `latest.yml`ను ప్రచురిస్తుంది; దాని `sha512` ఫీల్డ్ (base64) `OmniRoute.Setup.<version>.exe` ఇన్స్టాలర్ను కవర్ చేస్తుంది. PowerShellలో, ఇన్స్టాలర్ ఉన్న ఫోల్డర్ నుంచి:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   అవుట్పుట్ `latest.yml` → `sha512`తో సరిపోలాలి. సరిపోలకపోతే, ఫైల్ను తొలగించి [GitHub విడుదలల పేజీ](https://github.com/diegosouzapw/OmniRoute/releases) నుంచి మాత్రమే మళ్లీ డౌన్లోడ్ చేయండి.
2. **పునరుద్ధరించి + మినహాయించండి** — రోల్ బ్యాక్ చేయబడిన అంశాలను క్వారంటైన్ నుంచి పునరుద్ధరించి, `%LOCALAPPDATA%\Programs\OmniRoute` కోసం మినహాయింపును జోడించండి (Kaspersky → Settings → Threats and Exclusions), ఆపై మళ్లీ ఇన్స్టాల్ చేయండి.
3. **తప్పుడు పాజిటివ్ను నివేదించండి** — <https://opentip.kaspersky.com/>. వినియోగదారులు సమర్పించే FP నివేదికలు అలౌలిస్టింగ్ను నిజంగానే వేగవంతం చేస్తాయి.

## Node.js అనుకూలత

<a name="nodejs-compatibility"></a>

### లాగిన్ పేజీ క్రాష్ అవుతోంది లేదా "Module self-registration" లోపాన్ని చూపుతోంది

**కారణం:** మీరు OmniRoute ఆమోదించిన సురక్షిత రన్టైమ్ కనిష్ఠ పరిమితికి వెలుపల ఉన్న Node.js వెర్షన్ను అమలు చేస్తున్నారు. OmniRouteకు అవసరమైన సెక్యూరిటీ ప్యాచ్ కనిష్ఠ పరిమితి కంటే దిగువన ఉన్న పాత Node 22 లేదా 24 ప్యాచ్ స్థాయిని అమలు చేయడం అత్యంత సాధారణ సందర్భం.

**లక్షణాలు:**

- లాగిన్ పేజీ ఖాళీ స్క్రీన్ లేదా సర్వర్ లోపాన్ని చూపుతుంది
- కన్సోల్లో `Error: Module did not self-register` లేదా ఇలాంటి నేటివ్ బైండింగ్ లోపాలు కనిపిస్తాయి
- రన్టైమ్ మద్దతు ఉన్న సురక్షిత విధానానికి వెలుపల ఉంటే, లాగిన్ పేజీ మీ Node వెర్షన్తో కూడిన **నారింజ రంగు హెచ్చరిక బ్యానర్ను** చూపుతుంది

**పరిష్కారం:**

1. మద్దతు ఉన్న Node.js LTS విడుదలను ఇన్స్టాల్ చేయండి (సిఫార్సు: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. మీ వెర్షన్ను ధృవీకరించండి: `node --version` అనేది 24.x LTS శ్రేణిలో `v24.0.0` లేదా అంతకంటే కొత్త వెర్షన్ను చూపాలి
3. OmniRouteను మళ్లీ ఇన్స్టాల్ చేయండి: `npm install -g omniroute`
4. పునఃప్రారంభించండి: `omniroute`

> **మద్దతు ఉన్న సురక్షిత వెర్షన్లు:** `>=22.22.2 <23` లేదా `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) మరియు Node.js 26కు పూర్తి మద్దతు ఉంది.

### npm v11+: `better-sqlite3` ఇన్స్టాల్ కాలేదు (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**కారణం:** npm v11 (Node.js 24+తో అందించబడుతుంది) డిఫాల్ట్గా ఐచ్ఛిక
డిపెండెన్సీల ఇన్స్టాల్ స్క్రిప్ట్లను నిరోధిస్తుంది. `better-sqlite3` అనేది `optionalDependencies`లో జాబితా చేయబడి ఉండటం
మరియు దానికి నేటివ్ కంపైలేషన్ (`node-gyp rebuild`) అవసరం కావడం వల్ల, npm ఎలాంటి సందేశం లేకుండానే దాన్ని దాటవేస్తుంది.

**లక్షణాలు:**

- ప్రారంభ సమయంలో `Cannot find module 'better-sqlite3'`తో సర్వర్ క్రాష్ అవుతుంది
- `ls node_modules/better-sqlite3` అనేది "No such file or directory"ను చూపుతుంది
- `npm ls better-sqlite3` అనేది `(empty)`ని చూపుతుంది

**పరిష్కారం:**

1. ఇన్స్టాల్ స్క్రిప్ట్లను ఆమోదించి, మళ్లీ ఇన్స్టాల్ చేయండి:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. లేదా ముందే బిల్డ్ చేసిన ప్యాకేజీని మాన్యువల్గా ఇన్స్టాల్ చేయండి:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ఇది పనిచేస్తోందని ధృవీకరించండి: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**కారణం:** గ్లోబల్ `npm install -g omniroute` తర్వాత, ప్యాకేజీలోని `better-sqlite3` నేటివ్ బైనరీ స్థానికంగా అమలవుతున్న దానికంటే భిన్నమైన ఆర్కిటెక్చర్ లేదా Node.js ABI కోసం కంపైల్ చేయబడి ఉండవచ్చు. ముందే బిల్డ్ చేసిన బైనరీ మీ ఎన్విరాన్మెంట్తో సరిపోలనప్పుడు, macOSలో (Apple Silicon మరియు Intel రెండింటిలోనూ) ఇది సాధారణంగా జరుగుతుంది.

**లక్షణాలు:**

- ప్రారంభ సమయంలోనే `dlopen` లోపంతో సర్వర్ విఫలమవుతుంది
- లోపంలో `slice is not valid mach-o file` ఉంటుంది
- పూర్తి ఉదాహరణ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**పరిష్కారం — మీ స్థానిక ఎన్విరాన్మెంట్ కోసం మళ్లీ బిల్డ్ చేయండి (Node.js డౌన్గ్రేడ్ అవసరం లేదు):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **గమనిక:** ఇది మీ స్థానిక Node.js వెర్షన్ మరియు CPU ఆర్కిటెక్చర్కు అనుగుణంగా నేటివ్ బైండింగ్ను మళ్లీ కంపైల్ చేసి, బైనరీ అసమతుల్యతను పరిష్కరిస్తుంది. అధికారికంగా మద్దతు ఉన్న రన్టైమ్ పరిధి **`>=22.22.2 <23` లేదా `>=24.0.0 <27`** (`src/shared/utils/nodeRuntimeSupport.ts`లోని `SUPPORTED_NODE_RANGE`, `package.json`లోని `engines` ఫీల్డ్కు అనుగుణంగా ఉంటుంది). `better-sqlite3` v12.xతో Node.js 24.x LTS (Krypton) మరియు Node.js 26కు పూర్తి మద్దతు ఉంది.

## ప్రాక్సీ సమస్యలు

<a name="proxy-issues"></a>

### ప్రొవైడర్ ధృవీకరణలో "fetch failed" కనిపిస్తోంది

**కారణం:** API కీ ధృవీకరణ ఎండ్పాయింట్ (`POST /api/providers/validate`) గతంలో ప్రాక్సీ కాన్ఫిగరేషన్ను దాటవేసేది, దీనివల్ల ప్రాక్సీ రూటింగ్ అవసరమైన ఎన్విరాన్మెంట్లలో వైఫల్యాలు సంభవించేవి.

**పరిష్కారం (v3.5.5+):** ఇది ఇప్పుడు పరిష్కరించబడింది. ప్రొవైడర్ ధృవీకరణ `runWithProxyContext` ద్వారా రూట్ అవుతుంది, అలాగే ప్రొవైడర్-స్థాయి మరియు గ్లోబల్ ప్రాక్సీ సెట్టింగ్లను స్వయంచాలకంగా పాటిస్తుంది.

### టోకెన్ హెల్త్ చెక్ "fetch failed"తో విఫలమవుతోంది

**కారణం:** బ్యాక్గ్రౌండ్ OAuth టోకెన్ రిఫ్రెష్ ప్రతి కనెక్షన్కు ప్రాక్సీ కాన్ఫిగరేషన్ను పరిష్కరించడం లేదు.

**పరిష్కారం (v3.5.5+):** టోకెన్ హెల్త్ చెక్ షెడ్యూలర్ ఇప్పుడు రిఫ్రెష్ చేయడానికి ప్రయత్నించే ముందు ప్రతి కనెక్షన్కు ప్రాక్సీ కాన్ఫిగరేషన్ను పరిష్కరిస్తుంది. v3.5.5+కు అప్డేట్ చేయండి.

### SOCKS5 ప్రాక్సీ "invalid onRequestStart method"ను తిరిగి ఇస్తోంది

**కారణం:** Node.js 22లో, undici@8 డిస్పాచర్ Nodeలో అంతర్నిర్మితంగా ఉన్న `fetch()` అమలుతో అనుకూలంగా ఉండదు.

**పరిష్కారం (v3.5.5+):** ప్రాక్సీ డిస్పాచర్ యాక్టివ్గా ఉన్నప్పుడు OmniRoute ఇప్పుడు undici సొంత `fetch()` ఫంక్షన్ను ఉపయోగిస్తుంది, తద్వారా స్థిరమైన ప్రవర్తనను నిర్ధారిస్తుంది. v3.5.5+కు అప్డేట్ చేయండి.

### WSL కింద MITM ప్రాక్సీ: Windows హోస్ట్లోని డెస్క్టాప్ యాప్లు ఇంటర్సెప్ట్ కావడం లేదు

**కారణం:** MITM ప్రాక్సీ మరియు దాని CA సర్టిఫికేట్ OmniRoute నడుస్తున్న ఎన్విరాన్మెంట్లో ఇన్స్టాల్ అవుతాయి. WSL కింద ఆ ఎన్విరాన్మెంట్ Linux గెస్ట్గా ఉంటుంది, అయితే AI డెస్క్టాప్ యాప్లు (Kiro, Trae, Copilot, Zed, …) Windows హోస్ట్లో నడుస్తాయి. హోస్ట్ యాప్లు గెస్ట్ సర్టిఫికేట్ స్టోర్ను విశ్వసించవు మరియు గెస్ట్ సిస్టమ్ ప్రాక్సీ ద్వారా రూట్ కావు, కాబట్టి అక్కడ డెస్క్టాప్ ఇంటర్సెప్షన్ అమలులోకి రాదు.

**సిఫార్సు:** మీరు ఇంటర్సెప్ట్ చేయాలనుకునే డెస్క్టాప్ యాప్లు ఉన్న అదే OSలో OmniRouteను నేటివ్గా అమలు చేయండి (Windows యాప్ల కోసం Windows; macOS/Linuxకు కూడా ఇదే వర్తిస్తుంది). హోస్ట్ యాప్లను లక్ష్యంగా చేసుకుంటూ OmniRouteను WSLలోనే ఉంచాలంటే, రూపొందించిన CA సర్టిఫికేట్ను Windows హోస్ట్లో మాన్యువల్గా విశ్వసనీయమైనదిగా చేయాలి మరియు ప్రతి హోస్ట్ యాప్ నెట్వర్క్/ప్రాక్సీ సెట్టింగ్లను WSL ప్రాక్సీ ఎండ్పాయింట్కు మళ్లించాలి — ఇది మద్దతు లేని, సులభంగా విఫలమయ్యే సెటప్.

## క్లౌడ్ సమస్యలు

### క్లౌడ్ సింక్ లోపాలు

1. `BASE_URL` మీ రన్ అవుతున్న ఇన్స్టాన్స్ను సూచిస్తోందని నిర్ధారించుకోండి (ఉదా., `http://localhost:20128`)
2. `CLOUD_URL` మీ క్లౌడ్ ఎండ్పాయింట్ను సూచిస్తోందని నిర్ధారించుకోండి (ఉదా., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` విలువలను సర్వర్-సైడ్ విలువలకు అనుగుణంగా ఉంచండి

### క్లౌడ్లో `stream=false` 500ను అందిస్తుంది

**లక్షణం:** నాన్-స్ట్రీమింగ్ కాల్స్ కోసం క్లౌడ్ ఎండ్పాయింట్లో `Unexpected token 'd'...`.

**కారణం:** క్లయింట్ JSONను ఆశిస్తుండగా అప్స్ట్రీమ్ SSE పేలోడ్ను అందిస్తుంది.

**తాత్కాలిక పరిష్కారం:** క్లౌడ్కు నేరుగా చేసే కాల్స్ కోసం `stream=true` ఉపయోగించండి. లోకల్ రన్టైమ్లో SSE→JSON ఫాల్బ్యాక్ ఉంటుంది.

### క్లౌడ్ కనెక్ట్ అయిందని చూపిస్తుంది కానీ "చెల్లని API కీ" అని చెబుతుంది

1. లోకల్ డ్యాష్బోర్డ్ (`/api/keys`) నుండి కొత్త కీని సృష్టించండి
2. క్లౌడ్ సింక్ను అమలు చేయండి: క్లౌడ్ను ప్రారంభించండి → ఇప్పుడే సింక్ చేయండి
3. పాత/సింక్ కాని కీలు క్లౌడ్లో ఇప్పటికీ `401`ను అందించవచ్చు

## Docker సమస్యలు

### Docker IPv6 / కనెక్షన్ రీసెట్

<a name="docker-ipv6"></a>

**లక్షణాలు:** `curl http://localhost:20128/v1/models` అనేది `curl: (56) Recv failure: Connection reset by peer`ను అందిస్తుంది. డ్యాష్బోర్డ్ మరియు ప్రామాణీకరణ అవసరం లేని ఎండ్పాయింట్లు పనిచేస్తాయి, కానీ ప్రామాణీకరించిన ఎండ్పాయింట్లు విఫలమవుతాయి — ఇది ప్రామాణీకరణ సమస్యలా కనిపిస్తుంది కానీ కాదు.

**కారణం:** `docker run -p 20128:20128` అనేది `0.0.0.0` (IPv4) మరియు `::` (IPv6) రెండింటిలోనూ ప్రచురిస్తుంది, కానీ కంటైనర్లోని ప్రాసెస్ IPv4లో మాత్రమే లిజన్ చేస్తుంది. `localhost` మొదట `::1`కు రిజాల్వ్ అయ్యే హోస్ట్లలో, కనెక్షన్ దాని వెనుక లిజనర్ లేని ప్రచురించిన IPv6 పోర్ట్కు చేరుతుంది → కనెక్షన్ రీసెట్ అవుతుంది.

**పరిష్కారం:**

1. **త్వరిత నిర్ధారణ:** `curl -4 http://localhost:20128/v1/models`ను అమలు చేయండి. ఇది `-4`తో పనిచేసి, అది లేకుండా విఫలమైతే, మీ వద్ద IPv6 బైండ్ అసమతుల్యత ఉంది.
2. **శాశ్వత పరిష్కారం:** మీ `docker run` కమాండ్లో `-p 127.0.0.1:20128:20128` ఉపయోగించడం ద్వారా IPv4కు స్పష్టంగా బైండ్ చేయండి:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ఇది IPv4 బైండ్ను నిర్బంధిస్తుంది, అలాగే అన్ని హోస్ట్ ఇంటర్ఫేస్లలో ప్రాక్సీని బహిర్గతం చేయడాన్ని నివారిస్తుంది.

4. `installed=true` మరియు `runnable=false` అయితే: బైనరీ కనుగొనబడింది కానీ హెల్త్చెక్లో విఫలమైంది

## డీబగ్గింగ్

### లాగ్ ఫైళ్లను ప్రారంభించండి

మీ `.env` ఫైల్లో `APP_LOG_TO_FILE=true`ను సెట్ చేయండి. అప్లికేషన్ లాగ్లు `logs/` కింద వ్రాయబడతాయి.
సెట్టింగ్లలో కాల్ లాగ్ పైప్లైన్ ప్రారంభించబడినప్పుడు, రిక్వెస్ట్ ఆర్టిఫాక్ట్లు `${DATA_DIR}/call_logs/` కింద నిల్వ చేయబడతాయి.
పైప్లైన్ క్యాప్చర్ ప్రారంభించబడినప్పుడు, స్ట్రీమ్ చంక్ పేలోడ్లను మినహాయించడానికి `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false`ను సెట్ చేయండి లేదా ఆర్టిఫాక్ట్ పరిమితిని KBలో మార్చడానికి `CALL_LOG_PIPELINE_MAX_SIZE_KB`ను సర్దుబాటు చేయండి.

### ప్రొవైడర్ ఆరోగ్యాన్ని తనిఖీ చేయండి

```bash
# హెల్త్ డ్యాష్బోర్డ్
http://localhost:20128/dashboard/health

# API హెల్త్ చెక్
curl http://localhost:20128/api/monitoring/health
```

### రన్టైమ్ స్టోరేజ్

- ప్రధాన స్థితి: `${DATA_DIR}/storage.sqlite` (ప్రొవైడర్లు, కాంబోలు, అలియాస్లు, కీలు, సెట్టింగ్లు)
- వినియోగం: `storage.sqlite`లోని SQLite టేబుళ్లు (`usage_history`, `call_logs`, `proxy_logs`) + ఐచ్ఛిక `${DATA_DIR}/call_logs/`
- అప్లికేషన్ లాగ్లు: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` అయినప్పుడు)
- కాల్ లాగ్ ఆర్టిఫాక్ట్లు: కాల్ లాగ్ పైప్లైన్ ప్రారంభించబడినప్పుడు `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

రిక్వెస్ట్ లాగ్స్ పేజీలోని **చరిత్రను శుభ్రం చేయండి** చర్య `call_logs`, లెగసీ
`request_detail_logs`, మరియు లోకల్ `${DATA_DIR}/call_logs/` ఆర్టిఫాక్ట్ డైరెక్టరీని క్లియర్ చేస్తుంది.

## సర్క్యూట్ బ్రేకర్ సమస్యలు

### ప్రొవైడర్ OPEN స్థితిలో నిలిచిపోయింది

ప్రొవైడర్ సర్క్యూట్ బ్రేకర్ OPEN స్థితిలో ఉన్నప్పుడు, కూల్డౌన్ ముగిసే వరకు అభ్యర్థనలు బ్లాక్ చేయబడతాయి.

**పరిష్కారం:**

1. **Dashboard → Settings → Resilience**కు వెళ్లండి
2. ప్రభావిత ప్రొవైడర్కు సంబంధించిన సర్క్యూట్ బ్రేకర్ కార్డ్ను తనిఖీ చేయండి
3. అన్ని బ్రేకర్లను క్లియర్ చేయడానికి **Reset All**పై క్లిక్ చేయండి లేదా కూల్డౌన్ ముగిసే వరకు వేచి ఉండండి
4. రీసెట్ చేయడానికి ముందు ప్రొవైడర్ నిజంగా అందుబాటులో ఉందని నిర్ధారించుకోండి

### ప్రొవైడర్ సర్క్యూట్ బ్రేకర్ను పదేపదే ట్రిప్ చేస్తోంది

ప్రొవైడర్ పదేపదే OPEN స్థితిలోకి ప్రవేశిస్తుంటే:

1. వైఫల్య నమూనా కోసం **Dashboard → Health → Provider Health**ను తనిఖీ చేయండి
2. **Settings → Resilience → Provider Profiles**కు వెళ్లి, వైఫల్య పరిమితిని పెంచండి
3. ప్రొవైడర్ API పరిమితులను మార్చిందా లేదా మళ్లీ ప్రామాణీకరణ అవసరమా అని తనిఖీ చేయండి
4. లేటెన్సీ టెలిమెట్రీని సమీక్షించండి — అధిక లేటెన్సీ వల్ల టైమ్అవుట్-ఆధారిత వైఫల్యాలు సంభవించవచ్చు

## ఆడియో ట్రాన్స్క్రిప్షన్ సమస్యలు

### "Unsupported model" లోపం

- మొదటి భాగం మీ వద్ద క్రెడెన్షియల్స్ ఉన్న ప్రొవైడర్గా ఉండే మోడల్ idని ఉపయోగించండి (`openai/whisper-1`, `openrouter/deepgram/nova-3`). కేవలం `deepgram/nova-3`ని ఉపయోగించడానికి స్థానిక Deepgram కీ అవసరం.
- **Dashboard → Providers**లో ప్రొవైడర్ కనెక్ట్ అయి ఉందని నిర్ధారించుకోండి

### ట్రాన్స్క్రిప్షన్ ఖాళీగా వస్తోంది లేదా విఫలమవుతోంది

- మద్దతు ఉన్న ఆడియో ఫార్మాట్లను తనిఖీ చేయండి: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ఫైల్ పరిమాణం ప్రొవైడర్ పరిమితుల్లోనే ఉందని నిర్ధారించుకోండి (సాధారణంగా < 25MB)
- ప్రొవైడర్ కార్డ్లో ప్రొవైడర్ API కీ చెల్లుబాటును తనిఖీ చేయండి

- **టూల్ కాల్లు తొలగిపోతున్నాయి** — కొన్ని ఫార్మాట్ అనువాదాలు మద్దతు లేని ఫీల్డ్లను తొలగించవచ్చు; Playground మోడ్లో నిర్ధారించుకోండి

- **SDK ఆబ్జెక్ట్కు బదులుగా ముడి స్ట్రింగ్ను అందిస్తోంది** — v1.xలో పరిష్కరించబడింది; OpenAI SDK Pydantic ధ్రువీకరణ వైఫల్యాలకు కారణమయ్యే ప్రామాణికం కాని ఫీల్డ్లను (`x_groq`, `usage_breakdown`, మొదలైనవి) రెస్పాన్స్ శానిటైజర్ తొలగిస్తుంది. v3.x+లో కూడా ఇది కనిపిస్తే, దయచేసి సమస్యను నివేదించండి.
- **GLM/ERNIE `system` పాత్రను తిరస్కరిస్తోంది** — v1.xలో పరిష్కరించబడింది; అనుకూలం కాని మోడల్ల కోసం రోల్ నార్మలైజర్ సిస్టమ్ సందేశాలను స్వయంచాలకంగా యూజర్ సందేశాల్లో విలీనం చేస్తుంది. v3.x+లో కూడా ఇది కనిపిస్తే, దయచేసి సమస్యను నివేదించండి.
- **`developer` పాత్ర గుర్తించబడటం లేదు** — v1.xలో పరిష్కరించబడింది; OpenAI కాని ప్రొవైడర్ల కోసం ఇది స్వయంచాలకంగా `system`గా మార్చబడుతుంది. v3.x+లో కూడా ఇది కనిపిస్తే, దయచేసి సమస్యను నివేదించండి.
- **Geminiతో `json_schema` పనిచేయడం లేదు** — v1.xలో పరిష్కరించబడింది; `response_format` ఇప్పుడు Gemini యొక్క `responseMimeType` + `responseSchema`గా మార్చబడుతుంది. v3.x+లో కూడా ఇది కనిపిస్తే, దయచేసి సమస్యను నివేదించండి.

## స్థితిస్థాపకత సెట్టింగ్లు

### ఆటోమేటిక్ రేట్-లిమిట్ ట్రిగర్ కావడం లేదు

- ఆటోమేటిక్ రేట్-లిమిట్ API కీ ప్రొవైడర్లకు మాత్రమే వర్తిస్తుంది (OAuth/సబ్స్క్రిప్షన్కు కాదు)
- **సెట్టింగ్లు → స్థితిస్థాపకత → ప్రొవైడర్ ప్రొఫైల్లు**లో ఆటోమేటిక్ రేట్-లిమిట్ ప్రారంభించబడిందని ధృవీకరించండి
- ప్రొవైడర్ `429` స్థితి కోడ్లు లేదా `Retry-After` హెడర్లను తిరిగి ఇస్తుందో లేదో తనిఖీ చేయండి

### ఎక్స్పోనెన్షియల్ బ్యాక్ఆఫ్ను సర్దుబాటు చేయడం

ప్రొవైడర్ ప్రొఫైల్లు ఈ సెట్టింగ్లకు మద్దతు ఇస్తాయి:

- **ప్రాథమిక ఆలస్యం** — మొదటి వైఫల్యం తర్వాత ప్రారంభ నిరీక్షణ సమయం (డిఫాల్ట్: 1s)
- **గరిష్ఠ ఆలస్యం** — గరిష్ఠ నిరీక్షణ సమయ పరిమితి (డిఫాల్ట్: 30s)
- **గుణకం** — వరుసగా సంభవించే ప్రతి వైఫల్యానికి ఆలస్యాన్ని ఎంత పెంచాలి (డిఫాల్ట్: 2x)

### థండరింగ్ హెర్డ్ నివారణ

అనేక సమకాలీన అభ్యర్థనలు రేట్-లిమిట్ చేయబడిన ప్రొవైడర్ను చేరుకున్నప్పుడు, అభ్యర్థనలను వరుసగా అమలు చేయడానికి మరియు వరుస వైఫల్యాలను నివారించడానికి OmniRoute మ్యూటెక్స్ + ఆటోమేటిక్ రేట్-లిమిటింగ్ను ఉపయోగిస్తుంది. API కీ ప్రొవైడర్ల కోసం ఇది స్వయంచాలకంగా జరుగుతుంది.

### చాట్ అభ్యర్థనలు 503 / chat_admission_busyతో విఫలమవుతున్నాయి

**లక్షణాలు:**

- చాట్ కంప్లీషన్ల ఎండ్పాయింట్, ఎర్రర్ కోడ్
  `chat_admission_busy`గా ఉండే, మళ్లీ ప్రయత్నించదగిన `503` ప్రతిస్పందనను తిరిగి ఇస్తుంది.
- ప్రతిస్పందనలో `Retry-After` ఉంటుంది. #12135 నుంచి, ఈ విలువ గమనించిన
  ఆక్యుపెన్సీ ఆధారంగా నిర్ణయించబడుతుంది — అభ్యర్థన ఇప్పటికే వేచి ఉన్న `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  విండో మరియు ప్రస్తుత హెవీవెయిట్ లీజ్లు ఉంచబడిన సమయం, వీటిలో పెద్దదాన్ని తీసుకుని — తదుపరి పూర్ణ
  సెకనుకు రౌండ్ చేసి, గరిష్ఠంగా 60కి పరిమితం చేస్తారు. గేట్ నిష్క్రియంగా ఉన్నప్పుడు ఇది చారిత్రక కనిష్ఠాలను కొనసాగిస్తుంది:
  బైట్-ఆధారిత మార్గంలో 2 సెకన్లు, నిర్మాణ-ఆధారిత మార్గంలో 1 సెకను (ఇందులో
  `reason: "structure_limit"` కూడా ఉంటుంది).
- మరొక హెవీవెయిట్ చాట్ లేదా దీర్ఘకాలంగా నడుస్తున్న స్ట్రీమింగ్ ప్రతిస్పందన ఇంకా
  కొనసాగుతున్నప్పుడు ఇది సంభవించవచ్చు.

బైట్-ఆధారిత ప్రతిస్పందన బాడీ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

నిర్మాణ-ఆధారిత ప్రతిస్పందన అదే రకం మరియు కోడ్ను ఉపయోగిస్తుంది, దాని సందేశం
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
మరియు `reason: "structure_limit"`.
డిఫాల్ట్ థ్రెషోల్డ్ల వద్ద, ఒక అభ్యర్థనలో కనీసం `200` సందేశాలు,
కనీసం `64` టూల్స్ లేదా కనీసం `32,000` అంచనా టోకెన్లు ఉంటే, లేదా పరిమిత నిర్మాణ అంచనా
`10,000` సందర్శించిన నోడ్ల పరిమితిని లేదా `12` లోతు పరిమితిని చేరుకుంటే, ఆ అభ్యర్థన నిర్మాణపరంగా హెవీగా పరిగణించబడుతుంది.

**కారణం:** ఇది OmniRouteలో ఉద్దేశపూర్వకంగా చేసే లోడ్ షెడ్డింగ్, అప్స్ట్రీమ్-ప్రొవైడర్ వైఫల్యం కాదు.
పెద్ద అభ్యర్థన బాడీని నిల్వ చేసి పార్స్ చేయడానికి ముందు పరిమిత హెవీవెయిట్ సామర్థ్యాన్ని రిజర్వ్ చేయడానికి
ప్రతి ప్రాసెస్, ప్రాసెస్-లోకల్ గార్డ్ను ఉపయోగిస్తుంది. SSE ప్రతిస్పందన జీవితకాలం మొత్తం
హెవీవెయిట్ లీజ్ ఉంచబడుతుంది.

**#503-ఫ్యాన్అవుట్:** ఈ పరిష్కారానికి ముందు, హోస్ట్ మెమరీతో సంబంధం లేకుండా గార్డ్ సమకాలీనతను స్థిర అభ్యర్థన COUNTకు
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, డిఫాల్ట్ `1`) పరిమితం చేసేది, కాబట్టి కోడింగ్-ఏజెంట్
ఫ్యాన్అవుట్ (అనేక సబ్ఏజెంట్లు/CLIలు, సాధారణంగా > 256 KB ఉండే బాడీలు) ప్రభావవంతమైన
సమకాలీనతను ~1కి తగ్గించి, పూర్తిగా సాధారణ లోడ్లోనే 503లకు దారితీసేది. ఇప్పుడు గార్డ్ స్వయంగా సర్దుబాటు అవుతుంది: ప్రాసెస్ యొక్క
వాస్తవ మెమరీ పరిమితి నుంచి పరిమాణం నిర్ణయించబడే, స్వయంచాలకంగా ఉత్పన్నమైన ఇంజెస్ట్ BYTE బడ్జెట్
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ద్వారా ఇది నియంత్రించబడుతుంది, అలాగే ప్రత్యక్ష రిసోర్స్-ప్రెజర్
సిగ్నల్ను కూడా పరిగణనలోకి తీసుకుంటుంది — అందువల్ల ఒకేసారి ఒకటి కంటే ఎక్కువ హెవీ అభ్యర్థనలు వచ్చాయనే
కారణంతో కాకుండా, హోస్ట్ నిజంగా మెమరీ ఒత్తిడిలో ఉన్నప్పుడు మాత్రమే ఇది లోడ్ను తగ్గిస్తుంది.
పాత కౌంట్ పరిమితి (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ఇప్పటికీ గౌరవించబడుతుంది, కానీ మీరు దాన్ని స్పష్టంగా సెట్ చేసినప్పుడు మాత్రమే.

సామర్థ్యం బిజీగా ఉన్నప్పుడు, మళ్లీ ప్రయత్నించదగిన `503`తో సమాధానం ఇవ్వడానికి ముందు, ఒక స్లాట్ ఖాళీ కావడానికి
హెవీవెయిట్ అభ్యర్థన మొదట `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` వరకు (డిఫాల్ట్ `2000`, `0` నిరీక్షణను నిలిపివేస్తుంది)
వేచి ఉంటుంది. ఏజెంట్-శైలి క్లయింట్లు (OpenCode, Claude Code, Cursor) హెవీ సబ్-అభ్యర్థనలను
ఏకకాలంలో ఫ్యాన్అవుట్ చేసినప్పుడు, తక్షణ తిరస్కరణలపై తమ మొత్తం రీట్రై బడ్జెట్ను ఖర్చు చేసి
టాస్క్ మధ్యలో విఫలం కాకుండా, ఆ బర్స్ట్ను వరుసగా అమలు చేయడానికి ఈ పరిమిత నిరీక్షణ ఉంటుంది.
ప్రస్తుత హెవీవెయిట్ లీజ్ ఆక్యుపెన్సీ, నిర్ధారించిన బైట్ బడ్జెట్ మరియు ప్రత్యక్ష ప్రెజర్ తీవ్రత
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) వద్ద చూపబడతాయి — ఏదైనా env varను మార్చే ముందు వీటిని తనిఖీ చేయండి.
సెట్టింగ్లు → స్థితిస్థాపకత → అభ్యర్థన క్యూ → సమకాలీన అభ్యర్థనలు దీన్ని నియంత్రించదు; ఆ సెట్టింగ్
వేరొక ప్రొవైడర్ అభ్యర్థన-క్యూ మెకానిజాన్ని నియంత్రిస్తుంది.

**పరిష్కారం:**

1. ముందుగా మళ్లీ ప్రయత్నించండి. క్లయింట్లు అభ్యర్థనను వెంటనే పునరావృతం చేయడానికి బదులుగా
   `Retry-After`ను పాటించి బ్యాక్ఆఫ్ను ఉపయోగించాలి.
2. ఏదైనా సర్దుబాటు చేయడానికి ముందు `/api/monitoring/health` → `chatAdmission`ను తనిఖీ చేయండి. `countCapEnabled:
false` మరియు తగినంత పెద్ద `maxInflightBytes` అంటే స్వయంచాలకంగా ఉత్పన్నమైన బడ్జెట్ ఇప్పటికే తన
   పనిని చేస్తోందని అర్థం; `high`/`critical`గా ఉన్న `pressureSeverity` అంటే హోస్ట్లో నిజంగానే మెమరీ తక్కువగా ఉందని అర్థం —
   దాన్ని అడ్మిషన్ env varతో పరిష్కరించలేరు, దానికి మరింత RAM లేదా చిన్న వర్క్లోడ్ అవసరం.
3. `/api/monitoring/health`లో స్వయంచాలకంగా ఉత్పన్నమైన బడ్జెట్ మీ హోస్ట్కు నిజంగా చాలా చిన్నదిగా ఉందని
   కనిపిస్తే మాత్రమే (ఇది అరుదు — ఇది ఇప్పటికే కంటైనర్ నుంచి బేర్-మెటల్ వరకు స్కేల్ అవుతుంది), పాత అభ్యర్థన-కౌంట్ పరిమితికి
   తిరిగి వెళ్లడానికి బదులుగా `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`తో దాన్ని నేరుగా ఓవర్రైడ్ చేయండి.

అధికారిక అడ్మిషన్ సెట్టింగ్ల కోసం [ఎన్విరాన్మెంట్-వేరియబుల్ రిఫరెన్స్](../reference/ENVIRONMENT.md#4-security--authentication)ను
చూడండి.

## ఐచ్ఛిక RAG / LLM వైఫల్య వర్గీకరణ (16 సమస్యలు)

కొంతమంది OmniRoute వినియోగదారులు గేట్వేను RAG లేదా ఏజెంట్ స్టాక్ల ముందు ఉంచుతారు. అలాంటి సెటప్లలో ఒక విచిత్రమైన నమూనా కనిపించడం సాధారణం: OmniRoute సక్రమంగా ఉన్నట్లు కనిపిస్తుంది (ప్రొవైడర్లు అందుబాటులో ఉంటారు, రూటింగ్ ప్రొఫైల్లు సరిగ్గా ఉంటాయి, రేట్ లిమిట్ హెచ్చరికలు ఉండవు), అయినప్పటికీ తుది సమాధానం తప్పుగా ఉంటుంది.

ఆచరణలో, ఈ సంఘటనలు సాధారణంగా గేట్వే వల్ల కాకుండా డౌన్స్ట్రీమ్ RAG పైప్లైన్ వల్ల సంభవిస్తాయి.

ఆ వైఫల్యాలను వివరించడానికి మీకు ఉమ్మడి పదజాలం కావాలంటే, WFGY ProblemMapను ఉపయోగించవచ్చు. ఇది పునరావృతమయ్యే పదహారు RAG / LLM వైఫల్య నమూనాలను నిర్వచించే, MIT లైసెన్స్తో కూడిన బాహ్య టెక్స్ట్ వనరు. స్థూలంగా ఇది వీటిని కవర్ చేస్తుంది:

- రిట్రీవల్ డ్రిఫ్ట్ మరియు విచ్ఛిన్నమైన కాంటెక్స్ట్ సరిహద్దులు
- ఖాళీగా లేదా పాతబడిన ఇండెక్స్లు మరియు వెక్టర్ స్టోర్లు
- ఎంబెడ్డింగ్ మరియు సెమాంటిక్ అర్థం మధ్య అసమతుల్యత
- ప్రాంప్ట్ అసెంబ్లీ మరియు కాంటెక్స్ట్ విండో సమస్యలు
- లాజిక్ వైఫల్యం మరియు అతివిశ్వాసంతో ఇచ్చే సమాధానాలు
- సుదీర్ఘ చైన్ మరియు ఏజెంట్ సమన్వయ వైఫల్యాలు
- బహుళ ఏజెంట్ మెమరీ మరియు పాత్ర డ్రిఫ్ట్
- డిప్లాయ్మెంట్ మరియు బూట్స్ట్రాప్ క్రమానికి సంబంధించిన సమస్యలు

ఆలోచన సరళమైనది:

1. మీరు ఒక తప్పు ప్రతిస్పందనను పరిశోధిస్తున్నప్పుడు, వీటిని నమోదు చేయండి:
   - వినియోగదారు టాస్క్ మరియు అభ్యర్థన
   - OmniRouteలోని రూట్ లేదా ప్రొవైడర్ కాంబో
   - డౌన్స్ట్రీమ్లో ఉపయోగించిన ఏదైనా RAG కాంటెక్స్ట్ (రిట్రీవ్ చేసిన డాక్యుమెంట్లు, టూల్ కాల్లు మొదలైనవి)
2. సంఘటనను ఒకటి లేదా రెండు WFGY ProblemMap నంబర్లకు (`No.1` … `No.16`) మ్యాప్ చేయండి.
3. OmniRoute లాగ్ల పక్కన మీ స్వంత డ్యాష్బోర్డ్, రన్బుక్ లేదా ఇన్సిడెంట్ ట్రాకర్లో ఆ నంబర్ను నిల్వ చేయండి.
4. మీ RAG స్టాక్, రిట్రీవర్ లేదా రూటింగ్ వ్యూహాన్ని మార్చాల్సిన అవసరం ఉందో లేదో నిర్ణయించడానికి సంబంధిత WFGY పేజీని ఉపయోగించండి.

పూర్తి టెక్స్ట్ మరియు నిర్దిష్ట విధానాలు ఇక్కడ ఉన్నాయి (MIT లైసెన్స్, టెక్స్ట్ మాత్రమే):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

మీరు OmniRoute వెనుక RAG లేదా ఏజెంట్ పైప్లైన్లను అమలు చేయకపోతే, ఈ విభాగాన్ని విస్మరించవచ్చు.

## v3.8.0లో తెలిసిన సమస్యలు

v3.8.0 విడుదలకు ప్రత్యేకమైన సమస్యలు మరియు వాటికి ప్రస్తుతం అందుబాటులో ఉన్న ప్రత్యామ్నాయ పరిష్కారాలు. తరువాతి ప్యాచ్లో పరిష్కారం అందుబాటులోకి వస్తే, ఈ నమోదు నవీకరించబడుతుంది లేదా తొలగించబడుతుంది.

### Devin CLI ప్రమాణీకరణ వైఫల్యాలు

**లక్షణాలు:**

- Devin ఆధారిత టూల్లను ప్రారంభించినప్పుడు "Devin CLI not found" లేదా "auth failed" సందేశం రావడం
- CLI రన్టైమ్ తనిఖీ `installed=false` అని నివేదించడం

**కారణాలు:**

- `CLI_DEVIN_BIN` ఉనికిలో లేని పాత్ను సూచిస్తోంది
- హోస్ట్లో Devin CLI ఇన్స్టాల్ చేయబడలేదు

**పరిష్కారం:**

1. మీ ప్లాట్ఫారమ్ కోసం Devin CLIని ఇన్స్టాల్ చేయండి
2. `.env`లో `CLI_DEVIN_BIN=/usr/local/bin/devin` (లేదా వాస్తవ పాత్) సెట్ చేయండి
3. OmniRouteను రీస్టార్ట్ చేసి, **Dashboard → CLI Tools** నుండి మళ్లీ పరీక్షించండి

### మోడల్ కూల్డౌన్ నిలిచిపోవడం (మాన్యువల్ రీసెట్)

**లక్షణాలు:**

- గడువు ముగిసిన సమయం దాటిన తర్వాత కూడా ఒక మోడల్ కూల్డౌన్లో ఉన్నట్లు జాబితాలో కనిపించడం
- టైమ్స్టాంప్ గతంలో ఉన్నప్పటికీ, కాంబో రూటింగ్లోని అభ్యర్థనలు ఇప్పటికీ ఆ మోడల్ను దాటవేయడం

**మాన్యువల్ రీసెట్:**

- **డ్యాష్బోర్డ్:** **Settings → Model Cooldowns** → ప్రభావిత కార్డ్పై **Re-enable** క్లిక్ చేయండి
- **API:** మేనేజ్మెంట్ ప్రమాణీకరణ హెడర్లతో `DELETE /api/resilience/model-cooldowns`

### Command Code ప్రొవైడర్ కనెక్షన్ 403తో విఫలమవడం

**లక్షణాలు:**

- Command Code ప్రొవైడర్ కనెక్షన్ను పరీక్షిస్తున్నప్పుడు 403 రావడం
- కొత్తగా జోడించిన తర్వాత ప్రొవైడర్ కార్డ్ "unauthorized" అని చూపించడం

**కారణం:** OAuth ప్రక్రియ పూర్తికాలేదు (కాల్బ్యాక్ అందలేదు లేదా టోకెన్ స్థిరంగా నిల్వ చేయబడలేదు).

**పరిష్కారం:**

- OAuth ప్రక్రియను మళ్లీ ప్రారంభించడానికి CLI నుండి `omniroute providers`ను అమలు చేయండి, లేదా
- **Dashboard → Providers → Command Code → Reconnect** నుండి OAuthను మళ్లీ అమలు చేయండి

### ModelScope తీవ్రమైన 429 కూల్డౌన్లను ఇవ్వడం

**లక్షణాలు:**

- స్వల్ప సంఖ్యలో అభ్యర్థనలు వరుసగా పంపిన తర్వాత ModelScopeలో చాలా చిన్న లేదా తక్షణ కూల్డౌన్లు రావడం
- ఊహించిన దానికంటే ముందుగానే కాంబో రూటింగ్ ModelScopeను దాటవేయడం

**కారణం:** ModelScope ప్రొవైడర్కు ప్రత్యేకమైన `Retry-After` హెడర్లను పంపుతుంది. v3.8.0లో ఆ హెడర్ల కోసం ప్రత్యేక హ్యాండ్లింగ్ అందించబడింది, కాబట్టి పాత వెర్షన్లు వాటిని సాధారణ రేట్-లిమిట్ సూచనలుగా తప్పుగా అర్థం చేసుకుంటాయి.

**పరిష్కారం:**

- మీరు v3.8.0 లేదా తరువాతి వెర్షన్ను ఉపయోగిస్తున్నారని నిర్ధారించుకోండి
- **Settings → Resilience** కింద `useUpstream429BreakerHints` టాగుల్ ఎనేబుల్ చేయబడిందని ధృవీకరించండి

### ప్రొడక్షన్లో OMNIROUTE_WS_BRIDGE_SECRET లేకపోవడం

**లక్షణాలు:**

- రిమోట్ ప్రొడక్షన్ హోస్ట్లో అమలు చేస్తున్నప్పుడు ప్రతి Codex/Responses WebSocket బ్రిడ్జ్ అభ్యర్థనపై 401 రావడం
- కనెక్ట్ అయిన వెంటనే WebSocket బ్రిడ్జ్ హ్యాండ్షేక్ మూసివేయబడటం

**కారణం:** ప్రొడక్షన్ ఎన్విరాన్మెంట్లో `OMNIROUTE_WS_BRIDGE_SECRET` ఎన్విరాన్మెంట్ వేరియబుల్ లేదు.

**పరిష్కారం:**

1. యాదృచ్ఛిక సీక్రెట్ను రూపొందించండి: `openssl rand -hex 32`
2. ప్రొడక్షన్ సర్వర్ ఎన్విరాన్మెంట్లో (మరియు బ్రిడ్జ్తో కమ్యూనికేట్ చేసే ఏ క్లయింట్లోనైనా) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` సెట్ చేయండి
3. OmniRouteను రీస్టార్ట్ చేయండి

### Responses API: బ్యాక్గ్రౌండ్ మోడ్ సింక్రోనస్గా తగ్గించబడటం

**లక్షణాలు:**

- ఈ హెచ్చరిక లాగ్ చేయబడుతుంది: `background mode degraded to synchronous`
- `background: true` అభ్యర్థన బ్యాక్గ్రౌండ్ జాబ్ హ్యాండిల్కు బదులుగా సాధారణ సింక్రోనస్ ప్రతిస్పందనను అందించడం

**కారణం:** v3.8.0లో Responses APIపై `background: true` ఉద్దేశపూర్వకంగా సింక్రోనస్ అమలుకు తగ్గించబడుతుంది, అదే సమయంలో హెచ్చరికను కూడా పంపుతుంది. పూర్తి అసింక్రోనస్ బ్యాక్గ్రౌండ్ అమలు భవిష్యత్తులో అందించబడే ఫీచర్.

**పరిష్కారం:**

- `background` లేకుండా కాల్ చేసేలా క్లయింట్ను సర్దుబాటు చేయండి, లేదా
- పూర్తి అసింక్రోనస్ బ్యాక్గ్రౌండ్ మోడ్ను అందించే తరువాతి విడుదల కోసం వేచి ఉండండి (చేంజ్లాగ్ను అనుసరించండి)

## నెమ్మదైన ప్రారంభం / సిద్ధత గడువు ముగియడం

CLI `⚠ Server did not respond within 60s` అని చూపించినప్పటికీ సర్వర్ వాస్తవంగా పనిచేస్తుంటే, మీ ఎన్విరాన్మెంట్కు సిద్ధత ప్రోబ్ సమయ పరిమితి చాలా తక్కువగా ఉందని అర్థం.

ఇది సాధారణంగా Windowsలో (యాంటీవైరస్, ఫైల్సిస్టమ్ వాచర్లు) లేదా ప్రారంభ సమయంలో అధిక పనిభారం ఉన్న కంటైనర్లలో జరుగుతుంది.

**పరిష్కారం — సమయ పరిమితిని పెంచండి:**

```bash
# ఎన్విరాన్మెంట్ వేరియబుల్ ద్వారా (ప్రారంభాల మధ్య కొనసాగుతుంది):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 నిమిషాలు
omniroute serve

# CLI ఫ్లాగ్ ద్వారా (ఒక్కసారి మాత్రమే):
omniroute serve --ready-timeout 180000
```

డిఫాల్ట్ విలువ 60 000 ms (60 s). ఈ హెచ్చరిక కేవలం సమాచారార్థం మాత్రమే; సర్వర్ బ్యాక్గ్రౌండ్లో ప్రారంభమవుతూనే ఉంటుంది మరియు బూట్ పూర్తయిన తర్వాత అందుబాటులోకి వస్తుంది.

`OMNIROUTE_READY_TIMEOUT_MS` గురించి పూర్తి వివరాల కోసం [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) చూడండి.
