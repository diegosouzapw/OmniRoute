OmniRouteను OpenAI-అనుకూల బ్యాకెండ్గా ఉపయోగించేలా Codex CLIను కాన్ఫిగర్ చేయడానికి పూర్తి మార్గదర్శిని.

---

> **TOML మాత్రమే సమర్థవంతమైన ఫార్మాట్.** ఆధునిక Codex ప్రత్యేకంగా
> `~/.codex/config.toml`ను మాత్రమే చదువుతుంది (codex-cli 0.147.0తో ధృవీకరించబడింది:
> `codex --help` ప్రకారం `-c/--config` ఓవర్రైడ్లు "`~/.codex/config.toml` నుంచి
> లోడ్ చేయబడతాయి"). పాత `~/.codex/config.yaml` లెగసీ npm CLIకి చెందినది,
> కాబట్టి అది ఎలాంటి హెచ్చరిక లేకుండా విస్మరించబడుతుంది. డ్యాష్బోర్డ్ జనరేటర్
> (`/api/cli-tools/apply`, సాధనం `codex`) కన్జర్వేటివ్ మెర్జ్తో TOMLను రాస్తుంది —
> ఇప్పటికే ఉన్న కీలు మరియు ఇతర ప్రొవైడర్ బ్లాక్లు భద్రపరచబడతాయి, API కీ
> `OMNIROUTE_API_KEY`లోనే ఉంటుంది (ఫైల్లో ఎప్పుడూ ఉండదు), అలాగే మిగిలిపోయిన లెగసీ
> `config.yaml`ను మార్చకుండా, దాని గురించి మైగ్రేషన్ గమనికగా నివేదిస్తుంది.

## నేరుగా పేస్ట్ చేయడానికి సిద్ధంగా ఉన్న config.toml

`<YOUR_HOST>` మరియు `<YOUR_KEY>`లను మీ విలువలతో భర్తీ చేయండి:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # ప్రతి సాధన కాల్కు చరిత్ర నిల్వ పరిమితి

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc లేదా ~/.zshrc — అసలు కీ విలువ, config.tomlలో ఎప్పుడూ ఉంచవద్దు
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT యాప్లో బండిల్ చేయబడిన Codex

మీరు ChatGPT డెస్క్టాప్ యాప్ ద్వారా Codexను ఇన్స్టాల్ చేసి ఉంటే, `codex` బైనరీ
యాప్ బండిల్లో మాత్రమే ఉండవచ్చు మరియు ఇంకా మీ షెల్ `PATH`లో ఉండకపోవచ్చు. రిసోర్సెస్
డైరెక్టరీని మీ షెల్ స్టార్టప్ ఫైల్కు జోడించండి:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

కొత్త షెల్ను తెరిచి, ఆపై ధృవీకరించండి:

```bash
command -v codex
codex --version
```

### ప్రామాణీకరణ అవసరం లేని స్థానిక OmniRoute: ప్లేస్హోల్డర్ కీ సరిపోతుంది

మొదటి అభ్యర్థన CLI నుంచి బయటకు వెళ్లడానికి **ముందే**, `env_key` ద్వారా సూచించబడిన
ఎన్విరాన్మెంట్ వేరియబుల్ ఉందో లేదో Codex ధృవీకరిస్తుంది. మీ **స్థానిక** OmniRoute
ఇన్స్టాన్స్కు ప్రామాణీకరణ అవసరం లేకపోతే, ఖాళీ కాని ఏ ప్లేస్హోల్డర్ అయినా పనిచేస్తుంది:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

మీ OmniRoute సర్వర్ రక్షించబడి ఉంటే లేదా రిమోట్లో ఉంటే, దానికి బదులుగా నిజమైన కీని ఉపయోగించండి.

> **సాధారణ హోస్ట్ ఎంపికలు**
>
> | యాక్సెస్          | URL                           |
> | ----------------- | ----------------------------- |
> | స్థానిక నెట్వర్క్ | `http://192.168.0.1:20128/v1` |
> | Tailscale         | `http://100.x.x.x:20128/v1`   |
> | లూప్బ్యాక్        | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — ఇది అన్ని మోడళ్లకూ ఎందుకు పనిచేస్తుంది

Codex CLI ఫిబ్రవరి 2026లో `wire_api = "chat"` (Chat Completions)ను డిప్రికేట్ చేసింది మరియు ఇప్పుడు `wire_api = "responses"` (OpenAI Responses API)ను **తప్పనిసరిగా అవసరం చేస్తుంది**. v0.138 నుంచి `wire_api = "chat"`ను సెట్ చేస్తే స్టార్టప్ సమయంలో వెంటనే క్రాష్ అవుతుంది.

GLM మరియు Kimiతో సహా అనేక ప్రొవైడర్లు ఇప్పటికీ Chat Completions ఎండ్పాయింట్ను మాత్రమే అందిస్తున్నాయి. DeepSeek V4 ఇప్పుడు స్థానిక Responses APIతో పాటు Anthropic-అనుకూల ఎండ్పాయింట్ను కూడా అందిస్తోంది; OmniRoute డిఫాల్ట్గా Responsesను ఉపయోగిస్తుంది మరియు ప్రతి DeepSeek కనెక్షన్కు Anthropic అనుకూలతను ఎంచుకునే వీలు కల్పిస్తుంది.

**OmniRoute దీన్ని పారదర్శకంగా పరిష్కరిస్తుంది:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute ప్రొవైడర్ యొక్క స్థానిక ప్రోటోకాల్ను ఎంచుకుని, అవసరమైనప్పుడు అనువదిస్తుంది
    → POST /responses (DeepSeek V4) లేదా /chat/completions (Mistral / GLM / Kimi / ఇతరాలు)
```

OmniRouteను ఉపయోగిస్తున్నప్పుడు మీకు ఎప్పుడూ ప్రత్యేక ట్రాన్స్లేషన్ ప్రాక్సీ అవసరం లేదు. **అన్ని మోడళ్లు `wire_api = "responses"`ను ఉపయోగిస్తాయి** — మిగతాదంతా OmniRoute నిర్వహిస్తుంది.

> **`wire_api` డిఫాల్ట్ విలువ** — ఈ ఫీల్డ్ డిఫాల్ట్గా `"responses"`ను ఉపయోగిస్తుంది మరియు దీన్ని `config.toml` నుంచి పూర్తిగా తొలగించవచ్చు. మీ ఉద్దేశాన్ని డాక్యుమెంట్ చేయాలనుకున్నప్పుడు మాత్రమే దీన్ని స్పష్టంగా సెట్ చేయండి.

## కాంటెక్స్ట్ విండో మరియు కాంపాక్షన్

### టోకెన్ కాన్ఫిగరేషన్ ఫీల్డ్లు

| ఫీల్డ్                           | వివరణ                                                                                                                                                                                   |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | యాక్టివ్ మోడల్కు మొత్తం టోకెన్ బడ్జెట్. దీన్ని మోడల్ ప్రకటించిన పరిమితికి సెట్ చేయండి.                                                                                                  |
| `model_auto_compact_token_limit` | ఆటోమేటిక్ హిస్టరీ కాంపాక్షన్ను ట్రిగ్గర్ చేసే థ్రెషోల్డ్. **గరిష్ఠం: `model_context_window`లో 90%** — 90% కంటే ఎక్కువ విలువలు ఎలాంటి సూచన లేకుండా విస్మరించబడతాయి.                      |
| `tool_output_token_limit`        | ప్రతి టూల్ కాల్ అవుట్పుట్కు హిస్టరీలో నిల్వ చేసే టోకెన్ల పరిమితి. ఒకే పెద్ద టూల్ రెస్పాన్స్ విండోను నింపకుండా నిరోధిస్తుంది. **ఇది గరిష్ఠ అవుట్పుట్ కాదు** — ఇది హిస్టరీ నిల్వ పరిమితి. |
| `compact_prompt`                 | కాంపాక్షన్ సమయంలో ఉపయోగించే సిస్టమ్ ప్రాంప్ట్కు ఇన్లైన్ ఓవర్రైడ్ (v0.138+).                                                                                                             |

> **`model_max_output_tokens` గురించి గమనిక**: ఈ ఫీల్డ్ **Codex CLI కాన్ఫిగ్ స్కీమాలో భాగం కాదు** (Codex Rust కోడ్బేస్లో లేదు). దీన్ని సెట్ చేసినా ఎలాంటి సూచన లేకుండా విస్మరించబడుతుంది. దీనిపై ఆధారపడవద్దు — హిస్టరీలో ఎంత టూల్ అవుట్పుట్ నిల్వ చేయాలో నియంత్రించడానికి `tool_output_token_limit`ను ఉపయోగించండి.

## రీజనింగ్ శ్రమ

ప్రతిస్పందించే ముందు మోడల్ ఎంతగా "ఆలోచించాలి" అనేదాన్ని నియంత్రిస్తుంది.

| విలువ    | దేనికి ఉపయోగించాలి                               |
| -------- | ------------------------------------------------ |
| `none`   | రీజనింగ్ లేదు — నేరుగా ప్రతిస్పందన               |
| `low`    | అతి సులభమైన పనులు (పేరు మార్చడం, ఫార్మాట్ చేయడం) |
| `medium` | పేర్కొననప్పుడు **సర్వర్ డిఫాల్ట్**               |
| `high`   | మధ్యస్థ పనులు (రీఫ్యాక్టరింగ్, డీబగ్ చేయడం)      |
| `xhigh`  | ఆర్కిటెక్చర్, లోతైన విశ్లేషణ, సంక్లిష్ట సమస్యలు  |

```bash
# ప్రతి అమలుకు ఓవర్రైడ్
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

Desktop ఆలోచనల టెక్స్ట్ను (ఎన్క్రిప్ట్ చేసిన బ్లాబ్లను మాత్రమే కాకుండా) రెండర్ చేయగలిగేలా రీజనింగ్ **సారాంశాన్ని** కూడా సెట్ చేయండి:

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # మద్దతు ఉన్నప్పుడు ultra కూడా ఉపయోగించవచ్చు
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute థింకింగ్ బడ్జెట్ (సర్వర్ సెట్టింగ్)

OmniRoute హోస్ట్లో, Codex శ్రమ/సారాంశం అప్స్ట్రీమ్కు చేరాలంటే **Settings → AI → Thinking Budget** తప్పనిసరిగా **`passthrough`**గా ఉండాలి. **`auto` మోడ్** అన్ని క్లయింట్ `reasoning` / `reasoning_effort` ఫీల్డ్లను తొలగిస్తుంది మరియు Codex సరిగ్గా కాన్ఫిగర్ చేసినప్పటికీ థింకింగ్ ప్యానెల్లను ఖాళీ చేస్తుంది.

పూర్తి గైడ్: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

కంప్రెషన్ మరియు ప్రాంప్ట్ క్యాష్ స్వతంత్రంగా ఉంటాయి మరియు `passthrough` కింద కూడా పనిచేస్తూనే ఉంటాయి.

## ప్రొఫైల్లు — ఒక్కో మోడల్/వర్క్ఫ్లోకు పేరు పెట్టిన కాన్ఫిగరేషన్లు

ఒకే ఫ్లాగ్తో మోడల్ + కాంటెక్స్ట్ విండోను మార్చడానికి ప్రొఫైల్లు మిమ్మల్ని అనుమతిస్తాయి. ప్రతి ప్రొఫైల్, బేస్ `config.toml`పై ఓవర్లే అయ్యే ఫ్లాట్
`~/.codex/<name>.config.toml` ఫైల్.

```bash

codex -p glm52 "architecture review"
```

## `omniroute setup-codex`తో ప్రొఫైల్లను స్వయంచాలకంగా రూపొందించడం

మీరు OmniRouteను VPSలో అమలు చేస్తుంటే, ప్రత్యక్ష మోడల్ కేటలాగ్ నుండి ప్రొఫైల్ ఫైల్లను స్వయంచాలకంగా రూపొందించవచ్చు:

```bash
# VPS నుండి (పోర్ట్ 20128లో స్థానిక OmniRouteను ఉపయోగిస్తుంది)
omniroute setup-codex

# ఏ మెషీన్ నుండైనా — మీ VPSను సూచించండి
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# ఫైల్లను వ్రాయకుండా ప్రివ్యూ చేయండి
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# GLM మరియు Kimi ప్రొఫైల్లను మాత్రమే రూపొందించండి
omniroute setup-codex --only glm,kimi

# అనుకూల డైరెక్టరీలో వ్రాయండి
omniroute setup-codex --codex-home /path/to/.codex
```

ఈ కమాండ్ `/v1/models`ను పొందుతుంది, తెలిసిన మోడల్ల కోసం ట్యూన్ చేసిన ప్రొఫైల్లను ఉపయోగిస్తుంది, ఇతర అనుకూల టెక్స్ట్ మోడల్ల కోసం కేటలాగ్ మెటాడేటాను ప్రత్యామ్నాయంగా ఉపయోగిస్తుంది, అలాగే ప్రతి దానికీ `~/.codex/<name>.config.toml`ను వ్రాస్తుంది. ఇది ఐడెంపోటెంట్ — మళ్లీ అమలు చేయడం సురక్షితం.

విజయవంతమైన ప్రొవైడర్ మోడల్ డిస్కవరీ/ఇంపోర్ట్ ప్రత్యక్ష కేటలాగ్ను మార్చిన తర్వాత, OmniRoute ఇదే ప్రొఫైల్ ఫైల్లను **స్వయంచాలకంగా సింక్** కూడా చేయగలదు. ఇది **ఐచ్ఛికం మరియు డిఫాల్ట్గా ఆఫ్లో ఉంటుంది**: దీన్ని **CLI Code డ్యాష్బోర్డ్** నుండి ("CLI profile auto-sync" → Codex) టాగుల్ చేయండి లేదా `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true`గా సెట్ చేయండి (ఇది డిఫాల్ట్గా ఆన్లో ఉండే `CLI_ALLOW_CONFIG_WRITES`ను కూడా గౌరవిస్తుంది). ప్రారంభించినప్పుడు, ఇది విడివిడిగా ఉన్న `~/.codex/*.config.toml` ప్రొఫైల్ ఫైల్లను మాత్రమే వ్రాస్తుంది; సక్రియ/డిఫాల్ట్ `~/.codex/config.toml`, Codex-lb సెట్టింగ్లు, ఆథెంటికేషన్ లేదా ప్రొవైడర్ ఎంపికను ఎప్పటికీ మార్చదు.

## `omniroute launch-codex`తో Codexను ప్రారంభించడం

Codexను ప్రారంభించే ముందు మీ OmniRoute ఇన్స్టాన్స్ ఆరోగ్యాన్ని తనిఖీ చేస్తుంది:

## దీర్ఘకాలం నడిచే టాస్క్లు

రెండు OmniRoute డిఫాల్ట్లు అనేక గంటల పాటు నడిచే Codex CLI సెషన్లను తెలియకుండానే దెబ్బతీయగలవు. వీటిలో ఏదీ Codex CLI సెట్టింగ్ కాదు — రెండూ OmniRoute వైపునే ఉంటాయి. ఖాతాలను పిన్ చేసి, ఐడిల్ కటాఫ్లను నిలిపివేసే అప్స్ట్రీమ్ ప్రాక్సీల నుంచి కాన్ఫిగ్ను మైగ్రేట్ చేసే వినియోగదారులు తరచుగా ఈ రెండు సమస్యలనూ ఎదుర్కొని, OmniRoute “దీర్ఘ సెషన్ను కొనసాగించలేదని” నిర్ధారించుకుంటారు.

| లక్షణం                                                                             | సంభావ్య కారణం                                                              | నియంత్రణ                 |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------ |
| సెషన్ ఖాతాలను మారుస్తూనే ఉంటుంది / టర్న్ల మధ్య ప్రాంప్ట్-క్యాష్ కొనసాగింపు పోతుంది | సెషన్ అఫినిటీ TTL `0`గా ఉంది (నిలిపివేయబడింది)                             | `sessionAffinityTtlMs`   |
| క్లయింట్కు కనిపించే ప్రాంప్ట్ ఏదీ లేకుండానే రీజనింగ్ మధ్యలో కనెక్షన్ తెగిపోతుంది   | అప్స్ట్రీమ్ చంక్ లేకుండా 10 నిమిషాల తర్వాత స్ట్రీమ్ ఐడిల్ వాచ్డాగ్ అమలైంది | `STREAM_IDLE_TIMEOUT_MS` |

సంబంధిత చర్చలు: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (దీర్ఘ టాస్క్లు మధ్యలో ఆగిపోవడం), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (అఫినిటీ డిఫాల్ట్గా ఎందుకు నిలిపివేయబడింది). ట్రాకింగ్: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. సెషన్ అఫినిటీ — ఒక సంభాషణను ఒక ఖాతాకు పిన్ చేయండి

**డిఫాల్ట్:** `sessionAffinityTtlMs = 0` (నిలిపివేయబడింది).

**దీన్ని ఎక్కడ సెట్ చేయాలి**

- డ్యాష్బోర్డ్ → **సెట్టింగ్లు → రూటింగ్** → **సెషన్ అఫినిటీ** → **అఫినిటీ TTL (సెకన్లు)** (`ComboDefaultsTab`)
- లేదా **మిల్లీసెకన్లలో** `sessionAffinityTtlMs`తో సెట్టింగ్లను PATCH చేయండి (Zod పరిధి `0`–`86_400_000`, అంటే గరిష్ఠంగా 24 గంటలు)

> #7274లో Codexకు మాత్రమే సంబంధించిన `codexSessionAffinityTtlMs` నుంచి పేరు మార్చబడింది. పాత కీ ఇప్పటికీ రీడ్-ఓన్లీ అలియాస్గా అంగీకరించబడుతుంది; కొత్త కాన్ఫిగ్లు `sessionAffinityTtlMs`ను ఉపయోగించాలి. TTL `0` కంటే ఎక్కువగా ఉంటే, అఫినిటీ ఇప్పుడు Codexకు మాత్రమే కాకుండా **ఏ** ప్రొవైడర్కైనా వర్తిస్తుంది — [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → సెషన్ అఫినిటీ చూడండి.

**ఇది 0గానే ఉన్నప్పుడు ఏమి పనిచేయదు**

బహుళ-టర్న్ Codex సంభాషణలోని ప్రతి టర్న్ క్రియాశీల కాంబో వ్యూహం ద్వారా స్వతంత్రంగా రూట్ చేయబడుతుంది మరియు **ప్రతి టర్న్కు వేరే ఖాతాకు** చేరవచ్చు. ఇది అప్స్ట్రీమ్ సెషన్ / ప్రాంప్ట్-క్యాష్ కొనసాగింపును దెబ్బతీస్తుంది. TTL `0` కంటే ఎక్కువగా ఉన్నప్పుడు మాత్రమే OmniRoute, Codex సెషన్ హెడర్లను (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) మరియు `prompt_cache_key` / `session_id` వంటి బాడీ ఫీల్డ్లను పరిశీలిస్తుంది (`src/sse/services/auth.ts`లోని `extractSessionAffinityKey`).

**అనేక గంటలు నడిచే ఒకే టాస్క్ కోసం సిఫార్సు**

టాస్క్ అంచనా వాల్-క్లాక్ వ్యవధి కంటే TTLను **ఎక్కువగా** సెట్ చేయండి (UI గరిష్ఠ పరిమితి **86400 సెకన్లు** = 24 గంటలు):

| అంచనా టాస్క్ వ్యవధి | అఫినిటీ TTL (UI, సెకన్లు) | `sessionAffinityTtlMs` |
| ------------------- | ------------------------- | ---------------------- |
| కొన్ని గంటలు        | `14400` (4గం)             | `14400000`             |
| రాత్రంతా / ~12గం    | `43200` (12గం)            | `43200000`             |
| పూర్తి రోజు         | `86400` (24గం, గరిష్ఠం)   | `86400000`             |

ఎంపిక చేసుకుని ప్రారంభించే విధానం ఉద్దేశపూర్వకమైనది: అఫినిటీని నిలిపివేయడం ఖాతాల మధ్య లోడ్-బ్యాలెన్సింగ్కు అనుకూలంగా ఉంటుంది; దాన్ని ప్రారంభించడం ఒక దీర్ఘకాల ఏజెంట్ సెషన్ కొనసాగింపుకు అనుకూలంగా ఉంటుంది. ఈ గైడ్ డిఫాల్ట్ను **మార్చదు** — దీర్ఘకాల Codex టాస్క్లను అమలు చేసే ఆపరేటర్లు దీన్ని స్వయంగా ప్రారంభించాలి.

### 2. స్ట్రీమ్ ఐడిల్ టైమ్అవుట్ — నిశ్శబ్ద రీజనింగ్ టర్న్లను నిలిపివేయవద్దు

**డిఫాల్ట్:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 నిమిషాలు). సెట్ చేయనప్పుడు ఇది `REQUEST_TIMEOUT_MS` నుంచి విలువను పొందుతుంది; ఉమ్మడి ప్రాథమిక విలువ కూడా 600000. [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → టైమ్అవుట్లు చూడండి.

**డిఫాల్ట్ వద్ద ఏమి పనిచేయదు**

10 నిమిషాల కంటే ఎక్కువసేపు **నిజమైన అప్స్ట్రీమ్ చంక్ ఏదీ లేకుండా** నిశ్శబ్దంగా ఉండే Codex రీజనింగ్ / టూల్ టర్న్ను SSE ఐడిల్ వాచ్డాగ్ (`open-sse/utils/stream.ts`) బలవంతంగా మూసివేస్తుంది. క్లయింట్కు తరచుగా ఎలాంటి వివరాలు లేని కనెక్షన్ డ్రాప్ మాత్రమే కనిపిస్తుంది — ఇది “ఎటువంటి నోటిఫికేషన్ లేకుండా స్వయంచాలకంగా ఆగిపోయింది” అనే పరిస్థితికి సరిపోతుంది.

కీలకమైన వివరము: OmniRoute యొక్క సింథటిక్ SSE **హార్ట్బీట్ ఐడిల్ గడియారాన్ని రీసెట్ చేయదు**. నిజమైన అప్స్ట్రీమ్ బాడీ చంక్ మాత్రమే `lastChunkTime`ను అప్డేట్ చేస్తుంది. ఇంకా “ఆలోచిస్తున్న” నిశ్శబ్ద మోడల్, వాచ్డాగ్ దృష్టిలో నిలిచిపోయిన అప్స్ట్రీమ్లాగే కనిపిస్తుంది.

సంబంధిత Undici బాడీ ఇనాక్టివిటీ: `FETCH_BODY_TIMEOUT_MS` (ఇది కూడా అదే 10 నిమిషాల ప్రాథమిక విలువకు డిఫాల్ట్ అవుతుంది; `0` దాన్ని నిలిపివేస్తుంది). స్ట్రీమింగ్ కోసం, `FETCH_TIMEOUT_MS` కనెక్షన్ సెటప్ / మొదటి హెడర్లను మాత్రమే కవర్ చేస్తుంది — స్ట్రీమ్ సక్రియమైన తర్వాత, నిలిచిపోవడాన్ని `STREAM_IDLE_TIMEOUT_MS` మరియు `FETCH_BODY_TIMEOUT_MS` నియంత్రిస్తాయి.

**అనేక గంటలు సాగే ఒకే టాస్క్ కోసం సిఫార్సు**

OmniRoute ప్రాసెస్ ఎన్విరాన్మెంట్లో (`.env` / compose / systemd):

```bash
# సుదీర్ఘ రీజనింగ్ టర్న్ల కోసం స్ట్రీమ్ ఐడిల్ + బాడీ ఇనాక్టివిటీ కటాఫ్లను నిలిపివేయండి
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

లేదా మీరు ఊహించే అత్యంత సుదీర్ఘ నిశ్శబ్ద విరామం కంటే ఎక్కువగా వాటిని పెంచండి (విలువలు మిల్లీసెకన్లలో ఉంటాయి):

```bash
# ఉదాహరణ: అప్స్ట్రీమ్ చంక్ల మధ్య గరిష్ఠంగా 2 గంటల నిశ్శబ్దాన్ని అనుమతించండి
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

ఈ env varsను మార్చిన తర్వాత OmniRouteను రీస్టార్ట్ చేయండి.

### నిర్దిష్ట విధానం — అనేక గంటలు సాగే Codex టాస్క్

1. **అకౌంట్ను పిన్ చేయండి:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12గం) లేదా `86400` (గరిష్ఠంగా 24గం).
2. OmniRoute ఎన్విరాన్మెంట్లో **ఐడిల్ కటాఫ్లను పెంచండి / నిలిపివేయండి**:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. సాధారణ Codex `config.toml`ను (`wire_api = "responses"`, సరైన `base_url`, `OMNIROUTE_API_KEY`) అలాగే ఉంచండి — ఈ రెండు ప్రవర్తనల కోసం Codex వైపు affinity/idle నియంత్రణలు లేవు.
4. OmniRouteను రీస్టార్ట్ చేసి, ఆపై సుదీర్ఘ Codex టాస్క్ను ప్రారంభించండి.

### డిఫాల్ట్ల నిర్ణయం (#7287)

| నియంత్రణ                 | విడుదల డిఫాల్ట్    | ఈ గైడ్లో మార్చాలా?                                                                                                                   |
| ------------------------ | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `sessionAffinityTtlMs`   | `0` (ఆఫ్)          | **లేదు** — ఆప్ట్-ఇన్గానే ఉంటుంది (లోడ్-బ్యాలెన్సింగ్ vs కొనసాగింపు; Discussion #5718 చూడండి)                                         |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 నిమి) | **లేదు** — సాధారణ ట్రాఫిక్ కోసం 10 నిమిషాలుగానే ఉంటుంది; సుదీర్ఘ Codex టాస్క్లను నిర్వహించేవారు దాన్ని పెంచుతారు లేదా నిలిపివేస్తారు |

ఈ డిఫాల్ట్లలో దేనినైనా ప్రపంచవ్యాప్తంగా మార్చడం వల్ల ఒక ఇన్స్టాన్స్లోని ప్రతి క్లయింట్ ప్రవర్తన మారుతుంది, Codexది మాత్రమే కాదు. నియంత్రణలను డాక్యుమెంట్ చేయండి; స్పష్టమైన ఆపరేటర్ నిర్ణయం వేరుగా చెప్పే వరకు డిఫాల్ట్లను మార్చకుండా ఉంచండి.

### ఐడిల్ కటాఫ్లను నిర్ధారించడం

ఐడిల్ వాచ్డాగ్ ట్రిగ్గర్ అయినప్పుడు, OmniRoute ఈ ఆకృతిలో ఒక లైన్ను లాగ్ చేస్తుంది:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

`Idle timeout: no data from` కోసం grep చేయండి (లేదా `stream_idle_timeout` కోడ్ / `StreamIdleTimeoutError` ఎర్రర్ పేరు కోసం). ప్రొవైడర్ సెగ్మెంట్ అనేది ఆ రిక్వెస్ట్ కోసం OmniRoute ఉపయోగించినది (`codex`, మరో ప్రొవైడర్ id, లేదా తెలియకపోతే `provider`) — అది ఎల్లప్పుడూ అక్షరాలా `codex` స్ట్రింగ్గా ఉండదు.

## సమస్య పరిష్కారం

**`Error: wire_api = "chat" is no longer supported`**
మీ కాన్ఫిగ్ నుండి `wire_api = "chat"`ను తొలగించండి. `wire_api = "responses"`గా సెట్ చేయండి లేదా ఆ ఫీల్డ్ను వదిలివేయండి (v0.138 నుండి డిఫాల్ట్గా `"responses"` ఉంటుంది).

**`Error: model not found`**
సరైన ప్రిఫిక్స్తో ఆ మోడల్ OmniRouteలో ఉందో లేదో ధృవీకరించండి. `omniroute models list` ఉపయోగించండి లేదా `/dashboard/providers/<provider>` తెరవండి.

**`Authentication error`**
`OMNIROUTE_API_KEY` ఎక్స్పోర్ట్ చేయబడిందని నిర్ధారించండి: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
మొదటి అభ్యర్థన చేయడానికి ముందు env var ఉందో లేదో Codex ధృవీకరిస్తుంది. రక్షిత సర్వర్ల కోసం
నిజమైన కీని ఎక్స్పోర్ట్ చేయండి లేదా మీ **స్థానిక** OmniRoute ఇన్స్టాన్స్కు
ప్రమాణీకరణ అవసరం లేనప్పుడు `OMNIROUTE_API_KEY=local` వంటి ఖాళీ కాని ప్లేస్హోల్డర్ను ఉపయోగించండి.
దాన్ని `~/.bashrc` లేదా `~/.zshrc`కు జోడించినట్లయితే shellను పునఃప్రారంభించండి.

**`Connection refused`**
OmniRoute రన్ అవుతోందని, అలాగే మీ నెట్వర్క్కు (స్థానికం vs Tailscale vs VPS) సంబంధించి `base_url` హోస్ట్/పోర్ట్ సరైనదని ధృవీకరించండి.

**కాంటెక్స్ట్ పరిమితికి సమీపంలో సెషన్ క్రాష్ అవుతోంది**
`model_context_window` మరియు `model_auto_compact_token_limit`ను స్పష్టంగా సెట్ చేయండి. పైన ఉన్న కాంటెక్స్ట్ విండో పట్టికను చూడండి.

**కాంపాక్షన్ చాలా ఆలస్యంగా ప్రారంభమవుతోంది**
`model_auto_compact_token_limit`ను విండోలో 80–85%కి తగ్గించండి. ఎప్పుడూ 90% కంటే ఎక్కువగా సెట్ చేయవద్దు.

**ప్రొఫైల్ లోడ్ కావడం లేదు (`-p <name>` నిశ్శబ్దంగా విస్మరించబడుతోంది)**
ఫైల్ `~/.codex/<name>.config.toml` వద్ద ఉందని నిర్ధారించండి (`profile-` ప్రిఫిక్స్ లేకుండా). `ls ~/.codex/*.config.toml` రన్ చేయండి.

**దీర్ఘకాలం నడిచే Codex టాస్క్ మధ్యలో ఆగిపోతోంది / టర్న్ల మధ్య ఖాతాలు మారుతున్నాయి**
[దీర్ఘకాలం నడిచే టాస్క్లు](#long-running-tasks) చూడండి. సెషన్ అఫినిటీని ప్రారంభించండి (టాస్క్ నిడివి కంటే ఎక్కువ TTLతో), అలాగే `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`ను పెంచండి లేదా నిలిపివేయండి. `Idle timeout: no data from` కోసం OmniRoute లాగ్లలో grep చేయండి.
