ఈ పత్రం OmniRouteకు జోడించిన ఫీడ్బ్యాక్-ఆధారిత అడాప్టివ్ రూటింగ్ పునాదిని వివరిస్తుంది.
ఇది ఉద్దేశపూర్వకంగా చిన్నదిగా ఉంచబడింది: ఇది టైప్ చేయబడిన రూటింగ్-ఫలిత
ఛానల్ను, ఇప్పటికే ఉన్న auto-combo స్కోరర్కు ఇన్పుట్ను అందించే ఆన్లైన్ నాణ్యత సిగ్నల్ను,
ఐచ్ఛిక OpenTelemetry ఎక్స్పోర్టర్ను మరియు వివరణాత్మకత ఎండ్పాయింట్ను పరిచయం చేస్తుంది. ఇది ఇప్పటికే
ఉన్న రెసిలియెన్స్ స్టాక్ను (circuit breaker, connection cooldown,
model lockout, health matrix, autopilot) భర్తీ **చేయదు** — దానికి అనుబంధంగా పనిచేస్తుంది.

## 1. ఆర్కిటెక్చరల్ సందర్భం

OmniRoute అనేది **రిక్వెస్ట్ హాట్ పాత్** మరియు **కంట్రోల్/ఇంటెలిజెన్స్
ప్లేన్** కలిగిన డేటా ప్లేన్. హాట్ పాత్ వేగంగా, మెమరీ-సమర్థవంతంగా, అసింక్రోనస్గా, స్థితిస్థాపకంగా మరియు
అంచనా వేయగలిగే విధంగా ఉండాలి. మూల్యాంకనం, నాణ్యత స్కోరింగ్, ప్రయోగాలు మరియు చారిత్రక విశ్లేషణ
కంట్రోల్ ప్లేన్కు చెందినవి.

```
AI ఏజెంట్ / IDE
      │
      ▼
┌─────────────────────┐
│    OmniRoute        │   డేటా ప్లేన్ (వేగవంతం, సింక్, ఇన్-మెమరీ)
│  రూటింగ్ / ఫెయిల్ఓవర్ │
│  హెల్త్ / గార్డ్రైల్ │
│  క్యాష్ / స్ట్రీమింగ్  │
└──────────┬──────────┘
           │ RoutingEvent (ఫైర్-అండ్-ఫర్గెట్, ~0.2µs)
           ▼
┌─────────────────────┐
│  ఫీడ్బ్యాక్ సింక్లు  │   కంట్రోల్ ప్లేన్ (అసింక్, బెస్ట్-ఎఫర్ట్)
│  క్వాలిటీ ట్రాకర్     │
│  OTel ఎక్స్పోర్టర్   │
│  ఎక్స్ప్లెయిన్ స్టోర్ │
└──────────┬──────────┘
           ▼  నాణ్యత స్కోర్
      auto-combo స్కోరర్
```

### ఇప్పటికే ఉన్నవి (ఆడిట్ చేయబడ్డాయి, నకలు చేయలేదు)

| భావన                                      | ఇప్పటికే ఉన్న అమలు                                                                                         |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| లభ్యత (మనం ట్రాఫిక్ను పంపగలమా?)           | Circuit breaker (CLOSED/DEGRADED/OPEN/HALF_OPEN, DBలో నిల్వ చేయబడింది), connection cooldown, model lockout |
| హెల్త్ రిపోర్టింగ్                        | `providerHealthMatrix.ts`, `providerHealthAutopilot.ts`                                                    |
| షాడో ట్రాఫిక్                             | `open-sse/services/combo/shadowRouting.ts`                                                                 |
| గార్డ్రైల్స్                              | `src/lib/guardrails/` (ముందు/తర్వాత హుక్స్)                                                                |
| ఖచ్చితమైన క్యాష్                          | `src/lib/semanticCache.ts` (సిగ్నేచర్-ఆధారితం)                                                             |
| ఎవాల్యుయేటర్లు / మూల్యాంకన-ఆధారిత రూటింగ్ | `src/lib/evals/`, `open-sse/services/evalRouting.ts`                                                       |
| కాంబో నిర్ణయ వివరణాత్మకత                  | `open-sse/services/combo/decisionTrace.ts`                                                                 |
| డ్యాష్బోర్డ్ రియల్-టైమ్ ఈవెంట్లు          | `src/lib/events/eventBus.ts` (UI నోటిఫికేషన్ ఛానల్, `unknown` పేలోడ్లు, 100-ఎంట్రీల చరిత్ర)                |

రూటింగ్-ఈవెంట్ లేయర్ `eventBus` యొక్క పునఃఅమలు **కాదు**: ఆ బస్
డ్యాష్బోర్డ్ యొక్క రియల్-టైమ్ నోటిఫికేషన్ ఛానల్ (టైప్ చేయబడిన _ఈవెంట్ పేర్లు_, అపారదర్శక
పేలోడ్లు, UI వినియోగదారులు). `RoutingEvent` అనేది టైప్ చేయబడిన _ఫలితం_ స్ట్రక్ట్
(లేటెన్సీ/టోకెన్లు/ఖర్చు/ఫలితం/ముగింపు-కారణం), దీనిని కంట్రోల్ ప్లేన్కు చెందిన
ఫీడ్బ్యాక్ సింక్లు (క్వాలిటీ ట్రాకర్, OTel ఎక్స్పోర్టర్, ఎక్స్ప్లెయిన్ స్టోర్) ఉపయోగిస్తాయి.

### లోపించినవి (ఇక్కడ జోడించబడ్డాయి)

1. ఒక **టైప్ చేయబడిన రూటింగ్-ఫలిత ఈవెంట్ + సింక్ అబ్స్ట్రాక్షన్** (`RoutingEvent` /
   `RoutingEventSink`). `decisionTrace` కాంబో-పరిధికి పరిమితమై, ఇన్-మెమరీలో మాత్రమే ఉంటుంది;
   `comboMetrics` సమీకృత కౌంటర్లు; `call_logs` ముడి అసింక్ పర్సిస్టెన్స్.
   వీటిలో ఏదీ క్వాలిటీ ట్రాకర్, OTel
   ఎక్స్పోర్టర్ లేదా Future-AGI-శైలి ఎవాల్యుయేటర్ సబ్స్క్రైబ్ చేయగల టైప్ చేయబడిన, సింక్-ఆధారిత ఫలిత ఛానల్ కాదు.
2. అవుట్పుట్ నాణ్యత కోసం ఒక **ఆన్లైన్ నాణ్యత సిగ్నల్** (EWMA) — ఇంతకు ముందు స్కోరర్
   స్థిరమైన టాస్క్ ఫిట్నెస్ మరియు ఆప్ట్-ఇన్ ఎవాల్ పాస్-రేట్ల ద్వారా మాత్రమే "నాణ్యత"ను పరోక్షంగా అంచనా వేసేది.
3. GenAI సెమాంటిక్ కన్వెన్షన్లను ఉపయోగించే ఒక **ఐచ్ఛిక, డిపెండెన్సీ-రహిత OTel ఎక్స్పోర్టర్**.
4. వాస్తవ రూటింగ్ నిర్ణయాలు + నాణ్యత స్థితిని తిరిగి ఇచ్చే ఒక **వివరణాత్మకత ఎండ్పాయింట్**.

## 2. రూటింగ్ ఈవెంట్లు (ఫీడ్బ్యాక్ పునాది)

ఫైళ్లు: `open-sse/services/routing/events.ts`, `.../index.ts`

ఒక `RoutingEvent` కేవలం రూటింగ్ మెటాడేటాను మాత్రమే కలిగి ఉంటుంది:

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ...
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // అనుమతించబడిన యూనియన్
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

`RoutingEventSink` అనేది TypeScriptలోని `Send+Sync`-శైలి ట్రెయిట్:

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // తప్పనిసరిగా O(1) అయి ఉండాలి, సమకాలిక I/O ఉండకూడదు
}
```

హాట్ పాత్ పూర్తయిన ప్రతి అభ్యర్థనకు ఒకసారి `emitRoutingEvent(event)`ను కాల్ చేస్తుంది
(స్ట్రీమింగ్-పూర్తి కాల్బ్యాక్, నాన్-స్ట్రీమింగ్ విజయ పాత్, అలాగే
`handleChatCore`లోని తప్పుగా రూపొందిన-200 వైఫల్య పాత్). నమోదిత సింక్లకు డిస్పాచ్
సమకాలిక ఫ్యాన్-అవుట్గా జరుగుతుంది, కానీ ప్రతి సింక్ ఇన్-మెమరీ స్థితిని మాత్రమే
క్యూలో చేరుస్తుంది/నవీకరిస్తుంది. **హాట్ పాత్లో సమకాలిక డేటాబేస్ రైట్లు లేదా
నెట్వర్క్ I/O ఉండవు.**

డిఫాల్ట్ సింక్లు:

- `MemoryRoutingEventStore` — ఎక్స్ప్లెయిన్ ఎండ్పాయింట్ కోసం పరిమిత (500)
  రింగ్ బఫర్, సరికొత్తవి-ముందుగా.
- `QualityTracker` వినియోగదారు — EWMA నాణ్యత అంచనాను నవీకరిస్తుంది.
- `OtlpHttpsEventSink` — ఐచ్ఛికం; `OMNIROUTE_OTEL_ENDPOINT`
  (లేదా `OTEL_EXPORTER_OTLP_ENDPOINT`) సెట్ చేసినప్పుడు మాత్రమే ప్రారంభించబడుతుంది.

### కొలిచిన ఓవర్హెడ్ (నిష్పాక్షిక పోలిక)

ఈ వర్క్స్టేషన్లో `npm run bench:routing-events` (100k ఇటరేషన్లు; ప్రతి ఆపరేషన్
పర్సెంటైల్లు `performance.now()` టైమర్ రిజల్యూషన్ కంటే తక్కువగా ఉన్నందున,
సబ్-µs ఆపరేషన్లను సమగ్ర µs/opగా కొలిచారు):

| సందర్భం                             | µs/op  | ops/s  |
| ----------------------------------- | ------ | ------ |
| బేస్లైన్ (స్కోరింగ్ మాత్రమే)        | ~0.045 | ~22 M  |
| బేస్లైన్ + RoutingEvent (2 సింక్లు) | ~0.168 | ~5.9 M |
| బేస్లైన్ + ఈవెంట్ + OTel క్యూయింగ్  | ~0.163 | ~6.1 M |
| సమకాలికం (8 ఇంటర్లీవ్డ్ బర్స్ట్లు)  | ~0.18  | —      |

బేస్లైన్ స్కోరింగ్పై ఈవెంట్-డిస్పాచ్ వ్యత్యాసం ~0.12 µs/request; OTel సింక్
కేవలం క్యూలో చేరుస్తుంది (O(1) బఫర్ పుష్), కాబట్టి కొలవగలిగిన అదనపు భారం ఏదీ
జోడించదు. ఈ సంఖ్యలు యంత్ర-నిర్దిష్టమైనవి మరియు సాపేక్షమైనవి — ఇవి ప్రొడక్షన్
హామీ కావు. v1లోని "~0.2 µs" సంఖ్య ఒక సమగ్ర అంచనా; ఈ పద్ధతి స్కోరింగ్ బేస్లైన్ను
ఈవెంట్-డిస్పాచ్ వ్యయం నుండి వేరు చేస్తుంది.

## 3. నాణ్యత సంకేతం (ఫీడ్బ్యాక్-ఆధారిత ప్రొవైడర్ స్థితి)

ఫైళ్లు: `open-sse/services/routing/quality.ts`

v2 **కార్యాచరణ** నాణ్యతను **సెమాంటిక్** నాణ్యత నుండి వేరు చేస్తుంది:

- **కార్యాచరణ** — రూటింగ్ హాట్ పాత్ నుండి ఉత్పన్నమవుతుంది (HTTP 4xx/5xx,
  కనెక్షన్ వైఫల్యాలు, 429లు, తప్పుగా రూపొందిన ప్రతిస్పందనలు, స్ట్రీమ్ అంతరాయాలు,
  `finish_reason=length`, సున్నా-అవుట్పుట్ విజయాలు, లేటెన్సీ/TTFT EWMA). 200ను
  సెమాంటిక్ నాణ్యతగా పరిగణించరు.
- **సెమాంటిక్** — రూపొందించిన అవుట్పుట్ యొక్క వాస్తవ విలువ. ఇది కేవలం
  ఎవాల్యుయేటర్ ద్వారా `setSemanticQuality()`తో మాత్రమే ఉత్పత్తి అవుతుంది. ఒక
  ఎవాల్యుయేటర్ దాన్ని అందించే వరకు ఇది `null`గా ఉంటుంది మరియు కార్యాచరణ స్కోర్లోకి
  ఎప్పటికీ లీక్ అవదు.

ప్రతి-(ప్రొవైడర్, మోడల్) స్థితి (EWMA + పరిమిత కౌంటర్లు):

- `successEwma` — ఫలిత విజయం యొక్క EWMA (α=0.2).
- `latencyEwma` / `ttftEwma` — లేటెన్సీ యొక్క EWMA (α=0.1).
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`.
- `recencyMs` — మోడల్ను చివరిసారిగా ఎంత ఇటీవల పరిశీలించారో సూచిస్తుంది.

### విశ్వసనీయత / శాంపిల్ అవగాహన

`confidence = clamp01(samples / 50)`, మరియు స్కోరర్కు తిరిగి ఇచ్చే స్కోర్
తటస్థ మధ్యబిందువు వైపు బ్లెండ్ చేయబడుతుంది:

```
score = 0.5 + confidence * (operational - 0.5)
```

పరిణామాలు (పరీక్షల ద్వారా ధృవీకరించబడ్డాయి):

- కోల్డ్ ప్రొవైడర్ (0 శాంపిల్లు) **0.5** స్కోర్ పొందుతుంది — అన్యాయంగా జరిమానా
  విధించబడదు, కానీ వేలాది స్థిరమైన పరిశీలనలు ఉన్న ప్రొవైడర్పై ఆధిపత్యం చెలాయించలేరు.
- 7 అదృష్టవంతమైన విజయాలు ఉన్న ప్రొవైడర్ 0.5 వైపు లాగబడుతుంది (ఆశావహ
  ఇనిషియలైజేషన్ కారణంగా ఎప్పటికీ ఆధిపత్యం చెలాయించదు).
- 50+ శాంపిల్లు ఉన్న ప్రొవైడర్ తన నిజమైన కార్యాచరణ స్కోర్కు కన్వర్జ్ అవుతుంది.
- క్షీణత మరియు రికవరీ క్రమంగా జరుగుతాయి (EWMA), అలాగే ఒక విడి వైఫల్యం ఆరోగ్యకరమైన
  ప్రొవైడర్ను నాశనం చేయదు.

`ProviderQuality` అనేది `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }`ను బహిర్గతం చేస్తుంది.

ఇది `quality` స్కోరింగ్ ఫ్యాక్టర్గా ఆటో-కాంబో స్కోరర్కు ఫీడ్ అవుతుంది:

- `open-sse/services/autoCombo/scoring.ts`లో `ScoringFactors.quality` /
  `ScoringWeights.quality`.
- `DEFAULT_WEIGHTS`: `health` 0.1905 → 0.1605, `quality` 0.03. మొత్తం 1.0గానే ఉంటుంది.
- `buildAutoCandidates`, ట్రాకర్ నుండి `candidate.quality`ను పాప్యులేట్ చేస్తుంది;
  డేటా లేని అభ్యర్థులు డిఫాల్ట్గా తటస్థ **0.5**ను పొందుతారు (కోల్డ్ అభ్యర్థికి
  బూస్ట్ లేదా జరిమానా ఉండదు).

క్లోజ్డ్ లూప్:

```
RoutingEvent → QualityTracker → getQualityScore → ఆటో-కాంబో నాణ్యత ఫ్యాక్టర్
      ↑                                                    │
      └────── అభ్యర్థన ఫలితం (handleChatCore) ←────────────┘
```

### కఠిన మినహాయింపు vs మృదువైన జరిమానా

నాణ్యత సంకేతం కేవలం ఒక **మృదువైన అనుకూల ప్రాధాన్యత** మాత్రమే. కఠిన మినహాయింపు
ఇప్పటికే ఉన్న రెసిలియన్స్ స్టాక్ వద్దనే ఉంటుంది: సర్క్యూట్ బ్రేకర్ OPEN, కోటా
అయిపోవడం, ప్రామాణీకరణ వైఫల్యం, మోడల్ లాక్అవుట్ — వీటిలో ఏదీ నాణ్యత స్కోర్ వల్ల
ప్రభావితం కాదు. నాణ్యత స్కోర్ తాత్కాలికంగా తగ్గిన ప్రొవైడర్కు ప్రాధాన్యత
తగ్గించబడుతుంది, కానీ ఎప్పటికీ పూర్తిగా నిలిపివేయబడదు.

## 3b. ప్రామాణిక స్ట్రీమ్ టైమింగ్ (TTFT / ITL)

ఫైళ్లు: `open-sse/utils/streamTiming.ts`

`createStreamTiming()` అనేది స్ట్రీమింగ్ మార్గానికి ఏకైక ఇన్స్ట్రుమెంటేషన్ సీమ్,
ఇది `createSSEStream` (`open-sse/utils/stream.ts`)లో అనుసంధానించబడింది:

- `markByte()` — మొదటి అప్స్ట్రీమ్ చంక్ అందుకుంది.
- `markForward()` — క్లయింట్కు ఫార్వర్డ్ చేసిన మొదటి చంక్ (TTFT కోసం ఉపయోగించబడుతుంది).
- `markInterrupted()` — సజావుగా ముగియడానికి ముందు స్ట్రీమ్ టైమ్అవుట్/అబార్ట్/ఎర్రర్.
- `ttft()` = మొదట ఫార్వర్డ్ చేసిన SSE చంక్ లేటెన్సీ. **ఇది టోకెన్-స్థాయి TTFT కాదు** —
  ఒకే SSE చంక్లో సున్నా/ఒకటి/అనేక టోకెన్లు ఉండవచ్చు. ఇది ఖచ్చితంగా డాక్యుమెంట్ చేయబడింది.
- `avgItlMs()` = చంక్ల మధ్య సగటు విరామం (ITL కోసం చంక్-లేటెన్సీ ప్రాక్సీ).

TTFT/ITL/అంతరాయం వివరాలు `RoutingEvent` (`ttftMs`, `itlMs`)లోకి ప్రవహిస్తాయి మరియు
OTel సింక్ ద్వారా GenAI/OmniRoute స్పాన్ అట్రిబ్యూట్లుగా ఎక్స్పోర్ట్ చేయబడతాయి.

## 4. OpenTelemetry / GenAI అబ్జర్వబిలిటీ

ఫైళ్లు: `open-sse/services/routing/otel.ts`

- డిపెండెన్సీ-రహిత OTLP/HTTP JSON ఎక్స్పోర్టర్ (గ్లోబల్ `fetch`ను ఉపయోగిస్తుంది,
  `@opentelemetry/*` SDKను ఉపయోగించదు).
- స్పాన్లు GenAI సెమాంటిక్ కన్వెన్షన్లను (`gen_ai.provider.name`,
  `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`,
  `gen_ai.completion.finish_reason`, `gen_ai.system`) అలాగే OmniRoute రూటింగ్
  అట్రిబ్యూట్లను (ఫలితం, స్థితి, ttft, పునఃప్రయత్నాలు, ఫాల్బ్యాక్) అనుసరిస్తాయి.
- `record()` పరిమిత బఫర్లోకి మాత్రమే క్యూలో చేరుస్తుంది (O(1)); బ్యాక్గ్రౌండ్ టైమర్
  అసింక్రోనస్గా `POST {endpoint}/v1/traces` ద్వారా ఫ్లష్ చేస్తుంది. ఓవర్లోడ్ సమయంలో
  అత్యంత పాత ఈవెంట్లు తొలగించబడతాయి (`dropped` కౌంటర్) — డేటా ప్లేన్పై ఎప్పుడూ
  బ్యాక్ప్రెజర్ కలిగించదు.
- **కాన్ఫిగర్ చేస్తే తప్ప డిసేబుల్ అయి ఉంటుంది.** `OMNIROUTE_OTEL_ENDPOINT` (లేదా
  `OTEL_EXPORTER_OTLP_ENDPOINT`) తప్పనిసరిగా సెట్ చేయాలి; లేకపోతే సింక్
  రిజిస్టర్ చేయబడదు మరియు OTel కోడ్ ఏదీ అమలు కాదు.

## 5. వివరణీయత

- `GET /v1/explain/routing` ఇటీవలి `RoutingEvent`లను (వాస్తవ
  నిర్ణయాలు, కొత్తవి మొదట) మరియు ప్రతి ప్రొవైడర్/మోడల్ నాణ్యత స్నాప్షాట్ను అందిస్తుంది.
- ఆథ్ `/v1/combos`ను ప్రతిబింబిస్తుంది (Bearer API కీ లేదా డాష్బోర్డ్ సెషన్;
  `REQUIRE_API_KEY=false` ఉన్న సింగిల్-యూజర్ లోకల్ డిప్లాయ్మెంట్లలో అనామక యాక్సెస్).
- కాంబో-స్థాయి ప్రతి-ఇన్వొకేషన్ ట్రేస్లు ఇప్పటికే ఉన్న
  `decisionTrace.ts` (హెడర్ `X-OmniRoute-Combo-Trace`) ద్వారా అందుబాటులో ఉంటాయి.
- భద్రత: ఈవెంట్లు రూటింగ్ మెటాడేటాను మాత్రమే కలిగి ఉంటాయి, ప్రాంప్ట్లు/బాడీలు/క్రెడెన్షియల్లను ఎప్పుడూ కలిగి ఉండవు.

## 6. ఎవాల్యుయేషన్-ప్లేన్ ఇంటిగ్రేషన్ (భవిష్యత్ AGI సంసిద్ధత)

OmniRoute, Future AGIని (లేదా ఏదైనా ఎవాల్యుయేటర్ను) **సంభావ్య
ఇంటెలిజెన్స్/ఎవాల్యుయేషన్ బ్యాకెండ్గా పరిగణిస్తుంది, డిపెండెన్సీగా కాదు**. సీమ్లు:

- ఒక `RoutingEventSink` ఈవెంట్లను అసింక్రోనస్గా ఎవాల్యుయేటర్కు ఫార్వర్డ్ చేయగలదు.
- `MemoryRoutingEventStore` + నాణ్యత స్నాప్షాట్ ఎవాల్యుయేటర్కు ముడి
  డెసిషన్ స్ట్రీమ్ను అందిస్తాయి.
- భవిష్యత్ `Evaluator` (డిటర్మినిస్టిక్, లోకల్ జడ్జ్, HTTP, WASM) ఈవెంట్లు/ట్రేస్లను
  వినియోగించి, అదే `getQualityScore`/క్వాలిటీ-ఫ్యాక్టర్ మార్గంలోకి ఫీడ్ అయ్యే
  `QualityScore`ను అందిస్తుంది.
- ఇప్పటికే ఉన్న ఎవాల్-ఆధారిత రూటింగ్ (`open-sse/services/evalRouting.ts`) ఎనేబుల్ చేసినప్పుడు
  `eval_runs` పాస్-రేట్ల ఆధారంగా కాంబో టార్గెట్లను ఇప్పటికే తిరిగి క్రమబద్ధీకరిస్తుంది.

రిక్వెస్ట్ మార్గంలో ఏ ఎవాల్యుయేషన్ కూడా సింక్రోనస్గా అమలు కాదు, అలాగే ఎవాల్యుయేటర్
లేకపోయినా గేట్వే పూర్తిగా పనిచేస్తుంది.

## 7. తుది ఆర్కిటెక్చరల్ సమీక్ష

1. **సింక్రోనస్ హాట్ పాత్లో ఇంకా ఏమి మిగిలి ఉంది?** రూటింగ్/స్కోరింగ్, గార్డ్రైల్
   ప్రీ-చెక్లు, క్యాష్ లుకప్ మరియు ఇన్-మెమరీ సింక్లకు ఒక `emitRoutingEvent`
   ఫ్యాన్-అవుట్ (బేస్లైన్ స్కోరింగ్ కంటే ~0.12 µs అదనం).
2. **అసింక్రోనస్ ప్రాసెసింగ్కు ఏమి తరలించబడింది?** OTel ఎక్స్పోర్ట్ (టైమర్ + fetch),
   `call_logs`/వినియోగ పర్సిస్టెన్స్, సెమాంటిక్-క్యాష్ రైట్లు; క్వాలిటీ ఇన్-మెమరీలో
   మరియు O(1)గా ఉంటుంది (అసింక్ అవసరం లేదు).
3. **రూటింగ్ ఫలితం ఫీడ్బ్యాక్గా ఎలా మారుతుంది?** `handleChatCore` ఒక
   `RoutingEvent`ను ఎమిట్ చేస్తుంది → `QualityTracker` EWMA స్థితిని అప్డేట్ చేస్తుంది →
   `getQualityScore` ఆటో-కాంబో `quality` ఫ్యాక్టర్కు ఫీడ్ చేస్తుంది.
4. **నాణ్యత భవిష్యత్ రూటింగ్ను ఎలా ప్రభావితం చేస్తుంది?** తక్కువ నాణ్యత స్కోర్
   `scoreAutoTargets`లో ఆ ప్రొవైడర్/మోడల్ వెయిటెడ్ స్కోర్ను తగ్గిస్తుంది, తద్వారా
   క్షీణించిన మోడల్లకు క్రమంగా తక్కువ ప్రాధాన్యం ఇవ్వబడుతుంది మరియు వాటి EWMA మెరుగుపడే కొద్దీ అవి కోలుకుంటాయి.
5. **డిపెండెన్సీగా మారకుండా Future AGI ఎలా ఇంటిగ్రేట్ కాగలదు?**
   `RoutingEventSink` ఇంటర్ఫేస్ / భవిష్యత్ `Evaluator` అడాప్టర్ ద్వారా —
   హార్డ్కోడ్ చేసిన డిపెండెన్సీ ఉండదు.
6. **ఎవాల్యుయేటర్ అందుబాటులో లేకపోతే ఏమి జరుగుతుంది?** రూటింగ్ ప్రభావితం కాదు;
   గమనించిన సిగ్నల్ లేని మోడల్లకు నాణ్యత న్యూట్రల్ విలువ (1.0)కు ఫాల్బ్యాక్ అవుతుంది.
7. **టెలిమెట్రీ అందుబాటులో లేకపోతే ఏమి జరుగుతుంది?** OTel సింక్ రిజిస్టర్
   చేయబడదు; మిగిలిన రూటింగ్ లేయర్ ఎటువంటి మార్పు లేకుండా నడుస్తుంది.
8. **ఓవర్లోడ్లో ఏమి జరుగుతుంది?** OTel బఫర్ అత్యంత పాత ఈవెంట్లను తొలగిస్తుంది;
   క్వాలిటీ మరియు రింగ్ బఫర్ నిర్మాణరీత్యా పరిమితంగా ఉంటాయి; బ్యాక్ప్రెజర్ ఉండదు.
9. **క్షీణత తర్వాత ప్రొవైడర్ స్థితి ఎలా కోలుకుంటుంది?** విజయాలు పేరుకుపోయే కొద్దీ
   EWMA తిరిగి కన్వర్జ్ అవుతుంది; వార్మప్ కోల్డ్ మోడల్లను న్యూట్రల్గా ఉంచుతుంది;
   సర్క్యూట్ బ్రేకర్ స్వతంత్రంగా HALF_OPEN ప్రోబ్ల ద్వారా కోలుకుంటుంది.
10. **ప్రతిపాదించిన ఏ ఫీచర్లను ఉద్దేశపూర్వకంగా అమలు చేయలేదు, ఎందుకు?**
    - షాడో ట్రాఫిక్ / ప్రయోగాలు — ఇప్పటికే అమలు చేయబడ్డాయి
      (`combo/shadowRouting.ts`); తిరిగి నిర్మించలేదు.
    - గార్డ్రైల్స్ — ఇప్పటికే అమలు చేయబడ్డాయి (`src/lib/guardrails/`); డూప్లికేట్ చేయలేదు.
    - సెమాంటిక్ క్యాష్ — ఇప్పటికే అమలు చేయబడింది (`src/lib/semanticCache.ts`);
      డూప్లికేట్ చేయలేదు.
    - సంపూర్ణ ఎక్స్పెరిమెంట్-మేనేజ్మెంట్ ప్లాట్ఫారమ్, డేటాసెట్ టూలింగ్, ప్రాంప్ట్-ఆప్టిమైజేషన్
      ప్లాట్ఫారమ్, వెక్టర్ DB లేదా తప్పనిసరి బాహ్య OTel ఇన్ఫ్రాస్ట్రక్చర్ —
      తేలికపాటి డేటా ప్లేన్ పరిధికి వెలుపల ఉన్నాయి.
    - ఒక Rust `RoutingEvent` స్ట్రక్ట్ — డేటా ప్లేన్ TypeScriptలో ఉంది; TS టైప్
      దానికి అనుగుణంగా మార్చిన సమాన రూపం.

## 9. పరీక్షలు

- `tests/unit/routing-events.test.ts` — ఈవెంట్ సాధారణీకరణ, స్థితి
  వర్గీకరణ, పరిమిత రింగ్ బఫర్, సింక్ ఫ్యాన్-అవుట్ + ఐసోలేషన్.
- `tests/unit/routing-quality.test.ts` — EWMA వార్మప్, వైఫల్యం/విజయం నుంచి పునరుద్ధరణ,
  అనామలీ పెనాల్టీలు, 429 తాత్కాలిక నిర్వహణ, స్నాప్షాట్, రీసెట్.
- `tests/unit/routing-scoring-quality.test.ts` — వెయిట్ సమగ్రత, తటస్థ
  డిఫాల్ట్, నాణ్యతా కారకం ర్యాంకింగ్.
- `tests/unit/routing-otel.test.ts` — ప్రారంభ నియంత్రణ, GenAI స్పాన్ పేలోడ్, అసింక్
  ఫ్లష్, ఓవర్లోడ్లో డ్రాప్.
- `tests/unit/routing-events-concurrency.test.ts` — వేలాది ఈవెంట్లు, రింగ్
  బఫర్ పరిమితత్వం, ఎర్రర్ విసిరే సింక్ ఐసోలేషన్, పరస్పరం కలిసిన అసింక్ బర్స్ట్లు,
  చొప్పింపుల సమయంలో రీసెట్.
- `tests/unit/routing-adaptive-e2e.test.ts` — వాస్తవ
  `scoreAutoTargets` స్కోరర్ ద్వారా నిర్ణయాత్మక ఎండ్-టు-ఎండ్ లూప్: ఆరోగ్యకరం → క్షీణత → పునరుద్ధరణ → తాత్కాలిక అంతరాయం, అదనంగా
  కోల్డ్-స్టార్ట్ మరియు అదృష్టవంతమైన కోల్డ్-ప్రొవైడర్ సందర్భాలు.
- `tests/unit/stream-timing.test.ts` — TTFT (మొదట ఫార్వర్డ్ చేసిన చంక్), ITL,
  మొదటి-బైట్ vs మొదటి-ఫార్వర్డ్, అంతరాయం, తప్పుగా రూపొందిన/ఖాళీ చంక్ భద్రత.
