IDE సెషన్ లేకుండా Cursorను OmniRoute వెనుక ఉంచడానికి రెండు మార్గాలు:

1. **`cursor-api` ప్రొవైడర్** (కార్డ్ "Cursor API", అలియాస్ `cua`): Cursor వినియోగదారు API కీని (`crsr_…`, `https://cursor.com/dashboard/api` వద్ద రూపొందించబడుతుంది) కలిగి ఉండే API-కీ ప్రొవైడర్. ఆపై ఏ OmniRoute క్లయింట్ అయినా సాధారణ కోటా, ఫాల్బ్యాక్ మరియు లాగింగ్ లేయర్లతో `/v1/chat/completions` ద్వారా `cursor-api/<model>` లేదా `cua/<model>` రూపంలో Cursor మోడళ్లను యాక్సెస్ చేయగలదు. IDE ప్రొవైడర్ (`cursor`, OAuth/IDE సెషన్) మారదు.
2. **Cursor CLI పాస్త్రూ**: Cursor CLI (`agent`)ని OmniRoute వైపు మళ్లించండి, తద్వారా CLI చేసే ప్రతి RPC ఒక OmniRoute API కీతో ప్రామాణీకరించబడి, `cursor-api` కనెక్షన్ క్రెడెన్షియల్తో Cursorకు ఫార్వర్డ్ చేయబడి, Logs పేజీలో నమోదు చేయబడుతుంది.

## కీ ఎందుకు ఎక్స్చేంజ్ చేయబడుతుంది

`api2.cursor.sh` ముడి `crsr_…` కీని Bearer టోకెన్గా తిరస్కరిస్తుంది (401). Cursor CLI మొదట కీని `/auth/exchange_user_api_key`కి POST చేసి, ఒక గంట తర్వాత గడువు ముగిసే సెషన్ JWTని అందుకుంటుంది; తిరిగి వచ్చే `refreshToken`లో కూడా అదే `exp` ఉంటుంది, కాబట్టి రిఫ్రెష్ చేయడం అంటే కీని మళ్లీ ఎక్స్చేంజ్ చేయడమే.
`open-sse/services/cursorApiKeyAuth.ts` ఆ ఎక్స్చేంజ్ను నిర్వహించి, ప్రతి కీకి ఒక సెషన్ టోకెన్ను క్యాష్ చేస్తుంది, గడువు ముగియడానికి ఐదు నిమిషాల ముందు మళ్లీ ఎక్స్చేంజ్ చేస్తుంది మరియు Cursor 401తో స్పందించినప్పుడు క్యాష్ చేసిన టోకెన్ను తొలగిస్తుంది. `cursor-api` కనెక్షన్ల కోసం అప్స్ట్రీమ్ స్ట్రీమ్ను తెరవడానికి సరిగ్గా ముందు `CursorExecutor` దీన్ని కాల్ చేస్తుంది.

## `cursor-api` ప్రొవైడర్

రిజిస్ట్రీ: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"`, `cursor` మాదిరిగానే అదే `format`, `baseUrl` మరియు `models`). కేటలాగ్ కార్డ్:
`src/shared/constants/providers/apikey/specialty-media.ts`. ఎగ్జిక్యూటర్ మ్యాప్:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`).

డ్యాష్బోర్డ్: Providers → Cursor API → Add API key.

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

తర్వాత:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

గమనికలు:

- `cursor-api` కోసం మోడల్ జాబితా స్థిరమైన Cursor రిజిస్ట్రీ నుండి వస్తుంది (IDE ప్రొవైడర్ ఫాల్బ్యాక్గా ఉపయోగించే అదే జాబితా); OmniRoute హోస్ట్లో `cursor-agent` ఇన్స్టాల్ చేయాల్సిన అవసరం లేదు.
- `POST /api/providers/{id}/refresh-cursor` అనేది `cursor` IDE ప్రొవైడర్కు మాత్రమే; `cursor-api` కనెక్షన్లలో పునరుద్ధరించాల్సిన IDE సెషన్ ఉండదు.

## స్థానిక మోడల్ IDలు మరియు ఎఫర్ట్

`cursor` / `cu` మరియు `cursor-api` / `cua` కోసం, భాగస్వామ్య Claude-ఎఫర్ట్ నార్మలైజర్ అభ్యర్థించిన మోడల్ IDని యథాతథంగా ఉంచుతుంది. OmniRoute ఎఫర్ట్ అలియాస్గా కాకుండా, వాస్తవ మోడల్ IDలో భాగంగా `-low` వంటి సఫిక్స్ను Cursor ప్రకటించగలదు.
Cursor ఎగ్జిక్యూటర్ ఖచ్చితమైన లైవ్-కేటలాగ్ సరిపోలికను అలాగే ఉంచుతుంది; సరిపోలిక లేనప్పుడు, దాని ప్రస్తుత మోడల్ రిజాల్వర్ సఫిక్స్-టు-పారామీటర్ ఫాల్బ్యాక్ను నిర్వహిస్తుంది.

ఇది నేరుగా ఉపయోగించే Claude, Claude-అనుకూలమైన లేదా Vertex రూట్ల ఎఫర్ట్ నార్మలైజేషన్ను మార్చదు. లభ్యత ఇప్పటికీ ఎంచుకున్న Cursor ఖాతా కేటలాగ్ మరియు అర్హతపై ఆధారపడి ఉంటుంది.

## Cursor CLI పాస్త్రూ

రూట్: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`. `/api/cursor-cli/` ప్రిఫిక్స్
`src/shared/constants/publicApiRoutes.ts`లో నమోదు చేయబడింది, ఎందుకంటే హ్యాండ్లర్
తన స్వంత ప్రమాణీకరణను అమలు చేస్తుంది:

| పాత్                                                                                                                       | CLI నుండి ఆశించే ప్రమాణీకరణ  | OmniRoute చేసే పని                                                                                                                                                                      |
| -------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                         | `Bearer <OmniRoute API key>` | కీని ధృవీకరించి, 1 గంట చెల్లుబాటయ్యే HS256 JWTని (`JWT_SECRET`తో సంతకం చేసినది) రూపొందించి, దానిని తిరిగి పంపుతుంది                                                                     |
| ప్రతి ఇతర పాత్ (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`          | జారీదారు/ఆడియన్స్/గడువును ధృవీకరించి, సక్రియ `cursor-api` కనెక్షన్ను ఎంచుకుని, Authorization హెడర్ను మార్పిడి చేసిన Cursor టోకెన్తో భర్తీ చేసి, ప్రతిస్పందనను తిరిగి స్ట్రీమ్ చేస్తుంది |

CLI తాను అందుకునే ఏ టోకెన్ నుండైనా `exp`ను డీకోడ్ చేస్తుంది, కాబట్టి దానికి అపారదర్శక
టోకెన్ను అందిస్తే దాదాపు ప్రతి అభ్యర్థనకు ముందు మళ్లీ మార్పిడి చేస్తుంది; రూపొందించిన JWT
దాన్ని నివారిస్తుంది. OmniRoute నుండి వచ్చే 401 వల్ల CLI మళ్లీ మార్పిడి చేస్తుంది.

### సెటప్

1. OmniRoute API కీని (Dashboard → API keys) మరియు `cursor-api`
   కనెక్షన్ను సృష్టించండి.
2. ఏజెంట్ స్ట్రీమ్ కోసం HTTP/1.1ను ఉపయోగించమని CLIకి తెలియజేయండి.
   `~/.cursor/cli-config.json`లో:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   ఇది లేకపోతే CLI, ఏజెంట్ టర్న్ను విడిగా కాన్ఫిగర్ చేసిన ఏజెంట్ హోస్ట్కు
   HTTP/2 ద్వారా తెరుస్తుంది; కేవలం కంట్రోల్-ప్లేన్ RPCలు మాత్రమే
   ఎండ్పాయింట్ గుండా వెళ్తాయి.

3. OmniRouteకు వ్యతిరేకంగా CLIని అమలు చేయండి:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

ప్రతి హాప్ Logsలో ప్రొవైడర్ `cursor-api`, అభ్యర్థన రకం `cursor-cli`,
పాత్ `/api/cursor-cli/<rpc>`గా నమోదవుతుంది మరియు దానికి OmniRoute API కీతో పాటు
దాన్ని సేవించిన కనెక్షన్ ఆపాదించబడతాయి.

### వైఫల్య సందర్భాలు

| పరిస్థితి                                         | CLIకి వచ్చే ప్రతిస్పందన                                 |
| ------------------------------------------------- | ------------------------------------------------------- |
| తెలియని OmniRoute కీ మరియు `REQUIRE_API_KEY=true` | మార్పిడి సమయంలో 401 `unauthenticated`                   |
| `REQUIRE_API_KEY=false`                           | అనామక సెషన్ (`/v1/*` ప్రవర్తనను ప్రతిబింబిస్తుంది)      |
| గడువు ముగిసిన / విదేశీ / తారుమారు చేసిన సెషన్ JWT | 401, CLI మళ్లీ మార్పిడి చేస్తుంది                       |
| మార్పిడి తర్వాత OmniRoute API కీ రద్దు చేయబడింది  | తదుపరి RPCలో 401                                        |
