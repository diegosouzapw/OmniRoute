> అర్హమైన సందర్భంపై స్వయంచాలకంగా 15-95% ఆదా చేయండి. త్వరిత అవలోకనం కోసం, [README Compression విభాగం](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) చూడండి.

## అవలోకనం

OmniRoute, అభ్యర్థనలు అప్స్ట్రీమ్ ప్రొవైడర్లకు చేరకముందే **ముందస్తుగా** అమలయ్యే మాడ్యులర్ ప్రాంప్ట్ కంప్రెషన్ పైప్లైన్ను అమలు చేస్తుంది. అంటే మీ టోకెన్ ఆదా పారదర్శకంగా జరుగుతుంది — మీ వర్క్ఫ్లోలో ఎలాంటి మార్పులు అవసరం లేదు.

```
క్లయింట్ అభ్యర్థన
  → కంప్రెషన్ వ్యూహ ఎంపిక సాధనం
    → కాంబో ఓవర్రైడ్ ఉందా? → కాంబో సెట్టింగ్ను ఉపయోగించండి
    → ఆటో-ట్రిగ్గర్ థ్రెషోల్డ్ చేరిందా? → ఆటో మోడ్ను ఉపయోగించండి
    → డిఫాల్ట్ మోడ్ ఉందా? → గ్లోబల్ సెట్టింగ్ను ఉపయోగించండి
    → Offలో ఉందా? → కంప్రెషన్ను దాటవేయండి
  → ఎంచుకున్న కంప్రెషన్ మోడ్
    → Off: కంప్రెషన్ లేదు
    → Lite: సురక్షితమైన వైట్స్పేస్/ఫార్మాటింగ్ శుభ్రపరచడం (~15%)
    → Standard: Caveman-శైలి అనవసర పదాల తొలగింపు (~30%)
    → Aggressive: హిస్టరీ ఏజింగ్ + సారాంశీకరణ (~50%)
    → Ultra: హ్యూరిస్టిక్ ప్రూనింగ్ + కోడ్-బ్లాక్ సన్నబరచడం (~75%)
    → RTK: కమాండ్ను గుర్తించే టెర్మినల్/టూల్-అవుట్పుట్ ఫిల్టరింగ్ (60-90% అప్స్ట్రీమ్ పరిధి)
    → Stacked: క్రమబద్ధమైన బహుళ-ఇంజిన్ పైప్లైన్, సాధారణంగా RTK తర్వాత Caveman (78-95% అర్హమైన పరిధి)
  → కంప్రెస్ చేసిన అభ్యర్థన → ప్రొవైడర్
```

## కంప్రెషన్ మోడ్లు

### Off

ఎలాంటి కంప్రెషన్ వర్తించదు. అన్ని సందేశాలు మార్పు లేకుండా పంపబడతాయి.

### Lite మోడ్ (~15% ఆదా, <1ms లేటెన్సీ)

అత్యంత సురక్షితమైన మోడ్ — అర్థపరమైన మార్పు శూన్యం, ఫార్మాటింగ్ శుభ్రపరచడం మాత్రమే:

| సాంకేతికత                | వివరణ                                                            |
| ------------------------ | ---------------------------------------------------------------- |
| `collapseWhitespace`     | వరుస ఖాళీ పంక్తులను విలీనం చేసి, చివరలోని స్పేస్లను తొలగిస్తుంది |
| `dedupSystemPrompt`      | నకిలీ సిస్టమ్ సందేశాలను తొలగిస్తుంది                             |
| `compressToolResults`    | సుదీర్ఘమైన టూల్/ఫంక్షన్ అవుట్పుట్లను కంప్రెస్ చేస్తుంది          |
| `removeRedundantContent` | పునరావృత సూచనలను తొలగిస్తుంది                                    |
| `replaceImageUrls`       | base64 ఇమేజ్ డేటా URIలను సంక్షిప్తం చేస్తుంది                    |

**దీనికి ఉత్తమం:** ఎల్లప్పుడూ ఆన్లో ఉండే వినియోగం, భద్రత అత్యంత కీలకమైన వర్క్ఫ్లోలు.

### Standard మోడ్ (~30% ఆదా)

[Caveman](https://github.com/JuliusBrussee/caveman) స్ఫూర్తితో రూపొందించబడింది — అర్థాన్ని కాపాడుతూ అనవసర పదాలు మరియు సుదీర్ఘ పదబంధాలను తొలగిస్తుంది:

- అనవసర పదాలను తొలగిస్తుంది ("please", "I think", "basically", "actually")
- సుదీర్ఘ పదబంధాలను సంక్షిప్తం చేస్తుంది ("in order to" → "to", "as a result of" → "because")
- మర్యాదపూర్వక సందిగ్ధ పదబంధాలను తొలగిస్తుంది ("Would you mind...", "If you could possibly...")
- కోడింగ్ ప్రాంప్ట్ల కోసం సర్దుబాటు చేసిన 30+ regex నియమాలు

**దీనికి ఉత్తమం:** రోజువారీ కోడింగ్ వర్క్ఫ్లోలు, ఖర్చుపై శ్రద్ధగల బృందాలు.

### Aggressive మోడ్ (~50% ఆదా)

సుదీర్ఘ సెషన్ల కోసం తెలివైన హిస్టరీ నిర్వహణ:

- **సందేశాల ఏజింగ్** — పాత సందేశాలు క్రమంగా మరింత కంప్రెస్ అవుతాయి
- **టూల్ ఫలితాల కంప్రెషన్** — సుదీర్ఘమైన టూల్ అవుట్పుట్లు కత్తిరించబడతాయి లేదా తొలగించబడతాయి (మొదటి/చివరి పంక్తులు,
  సరిపోలే పంక్తుల ఫిల్టరింగ్, JSON కీ కంపాక్షన్)
- **నిర్మాణ సమగ్రత రక్షణలు** — `tool_use` + `tool_result` జతలు స్థిరంగా ఉండేలా నిర్ధారిస్తాయి
- **కాంటెక్స్ట్ విండో అవగాహన** — ప్రతి మోడల్కు సంబంధించిన టోకెన్ పరిమితులను గౌరవిస్తుంది

**దీనికి ఉత్తమం:** సుదీర్ఘ డీబగ్గింగ్ సెషన్లు, పెద్ద కోడ్బేస్లు.

### Ultra మోడ్ (~75% ఆదా)

టోకెన్లు అత్యంత కీలకమైన సందర్భాల కోసం గరిష్ఠ కంప్రెషన్:

- **హ్యూరిస్టిక్ ప్రూనింగ్** — గద్యాన్ని స్కోర్ ఆధారంగా టోకెన్ ప్రూనింగ్ చేయడం
- **నిర్మాణ పరిరక్షణ** — ఫెన్స్ చేసిన కోడ్ బ్లాక్లు, ఇన్లైన్ కోడ్, URLలు మరియు ఐడెంటిఫైయర్లు
  టూంబ్స్టోన్ చేసి, యథాతథంగా తిరిగి జోడించబడతాయి; వాటిని ఎన్నడూ ప్రూన్ చేయరు
- **ఐచ్ఛిక SLM స్థాయి** — కాన్ఫిగర్ చేసినప్పుడు చిన్న లోకల్ మోడల్ ప్రూనింగ్ను మెరుగుపరచగలదు
- Aggressive మోడ్తో సంబంధం లేకుండా పనిచేస్తుంది: ఇది సందేశాల ఏజింగ్, టూల్-ఫలితాల కంప్రెషన్
  లేదా ఫాల్బ్యాక్ సారాంశీకరణను అమలు చేయదు (SLM-స్థాయి వైఫల్యం మాత్రమే ఫాల్బ్యాక్ పాస్ను
  aggressive ద్వారా రూట్ చేయగలదు)

**దీనికి ఉత్తమం:** మీరు పదేపదే కాంటెక్స్ట్ పరిమితులను చేరుకుంటున్నప్పుడు.

### RTK మోడ్ (60-90% అప్స్ట్రీమ్ పరిధి)

కోడింగ్-ఏజెంట్ సెషన్లలో కనిపించే సుదీర్ఘ టూల్ అవుట్పుట్ల కోసం RTK మోడ్ ఆప్టిమైజ్ చేయబడింది:

- `git status`, `git diff`, `git log`, టెస్ట్ రన్నర్లు,
  TypeScript/Vite/Webpack బిల్డ్లు, ESLint/Biome/Prettier, npm ఆడిట్లు/ఇన్స్టాల్లు, Docker లాగ్లు, ఇన్ఫ్రా
  అవుట్పుట్ మరియు సాధారణ షెల్ అవుట్పుట్ వంటి కమాండ్/అవుట్పుట్ తరగతులను గుర్తిస్తుంది
- `open-sse/services/compression/engines/rtk/filters/` నుండి JSON ఫిల్టర్ ప్యాక్లను వర్తింపజేస్తుంది
- ప్రాజెక్ట్ లేదా గ్లోబల్ `filters.toml` ఫైల్ల నుండి RTK TOML schema v1 ఫిల్టర్లను ఇంపోర్ట్ చేస్తుంది; ప్రాజెక్ట్ ఫైల్ల కోసం ఇన్లైన్-టెస్ట్
  ధ్రువీకరణ మరియు ట్రస్ట్-గేటింగ్ను ఉపయోగిస్తుంది
- ఇన్లైన్ ధ్రువీకరణ నమూనాలతో 55 అంతర్నిర్మిత ఫిల్టర్లను అందిస్తుంది
- ANSI నియంత్రణ క్రమాలు, ప్రోగ్రెస్ బార్లు, పునరావృత పంక్తులు మరియు చర్య అవసరం లేని అనవసర సమాచారాన్ని తొలగిస్తుంది
- వైఫల్యాలు, ఎర్రర్లు, హెచ్చరికలు, మారిన ఫైల్లు, సారాంశాలు మరియు సుదీర్ఘ అవుట్పుట్ చివరి భాగాన్ని సంరక్షిస్తుంది
- ట్రస్ట్-గేటెడ్ ప్రాజెక్ట్ ఫిల్టర్లు, గ్లోబల్ ఫిల్టర్లు మరియు ఐచ్ఛికంగా సవరించిన ముడి అవుట్పుట్ రికవరీకి మద్దతు ఇస్తుంది

**దీనికి ఉత్తమం:** షెల్, బిల్డ్, టెస్ట్, git, grep మరియు ఫైల్-అవుట్పుట్ ట్రాన్స్క్రిప్ట్లు ఉన్న ఏజెంట్ సెషన్లు.

### Stacked మోడ్ (78-95% అర్హమైన పరిధి)

Stacked మోడ్ బహుళ కంప్రెషన్ ఇంజిన్లను నిర్ణీత క్రమంలో అమలు చేస్తుంది. డిఫాల్ట్ పైప్లైన్:

```txt
RTK -> Caveman
```

ఈ క్రమం ముందుగా టెర్మినల్/టూల్ అవుట్పుట్ను సంక్షిప్తంగా ఉంచి, ఆపై మిగిలిన సహజ-భాష ప్రాంప్ట్పై Caveman అర్థపరమైన సంక్షేపణను వర్తింపజేస్తుంది. Stacked పైప్లైన్లను గ్లోబల్గా లేదా రూటింగ్ కాంబోలకు కేటాయించిన కంప్రెషన్ కాంబోల ద్వారా కాన్ఫిగర్ చేయవచ్చు.

**దీనికి ఉత్తమం:** భారీ టూల్ లాగ్లతో పాటు మానవ సూచనలు లేదా అసిస్టెంట్ సారాంశాలు కలిగిన మిశ్రమ కాంటెక్స్ట్.

## అప్స్ట్రీమ్ పొదుపుల గణితం

OmniRoute రెండు మూలాల నుండి కంప్రెషన్ పొదుపులను డాక్యుమెంట్ చేస్తుంది: అప్స్ట్రీమ్ ప్రాజెక్ట్ బెంచ్మార్క్లు మరియు
OmniRoute స్వంత ఇంజిన్ కూర్పు.

| మూలం    | ఇక్కడ ఉపయోగించిన అప్స్ట్రీమ్ README సంఖ్య                                                                                        |
| ------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` తక్కువ అవుట్పుట్ టోకెన్లు, `65%` బెంచ్మార్క్ సగటు అవుట్పుట్ పొదుపులు, `22-87%` పరిధి మరియు `~46%` ఇన్పుట్ కంప్రెషన్ సాధనం |
| RTK     | `60-90%` కమాండ్-అవుట్పుట్ పొదుపులు; నమూనా సెషన్లో `~118,000 -> ~23,900` టోకెన్లు లేదా `79.7%` పొదుపు (`~80%`)                    |

ఒకదానితో ఒకటి అతివ్యాప్తి చెందే సాధనం/కాంటెక్స్ట్ పేలోడ్ల కోసం, డిఫాల్ట్ OmniRoute కాంబో ఇంజిన్లను ఇలా వరుసగా అమర్చుతుంది:

```txt
RTK -> Caveman
```

సంయుక్త పొదుపులు సంకలనాత్మకమైనవి కావు, గుణకారాత్మకమైనవి:

```txt
సంయుక్తం = 1 - (1 - RTK పొదుపులు) * (1 - Caveman ఇన్పుట్ పొదుపులు)
సగటు    = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
పరిధి    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

RTK మరియు Caveman రెండూ ఒకే ఇన్పుట్/కాంటెక్స్ట్ పేలోడ్ను తగ్గించగలిగినప్పుడు ఆ `78-95%` సంఖ్య వర్తిస్తుంది.
Caveman రెస్పాన్స్ అవుట్పుట్ మోడ్ వేరు: అది ప్రారంభించబడినప్పుడు, Caveman స్వంత అవుట్పుట్ పొదుపులను (`65%`
సగటు, `~75%` ప్రధాన సంఖ్య, `22-87%` పరిధి) ఉపయోగించండి. మొత్తం బిల్లింగ్ పొదుపులు మీ ప్రాంప్ట్/అవుట్పుట్ నిష్పత్తిపై ఆధారపడి ఉంటాయి.

### "అర్హమైనది" అంటే నిజానికి ఏమిటి

15-95% ప్రధాన పరిధి వాస్తవమైనదే, కానీ అది **పునరావృతమైన లేదా అనవసరంగా సుదీర్ఘమైన** కంటెంట్కు మాత్రమే వర్తిస్తుంది — పదేపదే వచ్చే
ఎర్రర్ లైన్లు, ఒకే హెచ్చరికను వరుసగా ఉత్పత్తి చేసే బిల్డ్ లాగ్, పరిమితికి మించిన `grep`/ఫైల్-రీడ్ డంప్. ప్రతి
రిక్వెస్ట్ అంత పొదుపు చేస్తుందని దీని అర్థం **కాదు**.

ప్రయోగాత్మకంగా ధృవీకరించబడింది (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300 ఒకే విధమైన
ఎర్రర్ లైన్లు కలిగిన Anthropic-ఆకృతి `tool_result` బ్లాక్పై `stacked` (RTK + Caveman) రన్ **95.93% టోకెన్ పొదుపులు / 96.26% అక్షర పొదుపులు** సాధించింది — ఇది ప్రచారం చేసిన
పరిధిలోనే ఉంది. కానీ సాధారణమైన, పునరావృతం కాని టూల్ అవుట్పుట్పై (శుభ్రమైన `grep` మ్యాచ్ జాబితా,
చిన్న ఫైల్ రీడ్, సాధారణ సంభాషణ టెక్స్ట్) అదే పైప్లైన్ను రన్ చేసినప్పుడు సరిగ్గా **దాదాపు సున్నా పొదుపులు** వస్తాయి, ఎందుకంటే
తొలగించడానికి పునరావృతమైనది ఏమీ ఉండదు మరియు కోడ్ బ్లాక్లు, URLలు, హెడ్డింగ్లు, వెర్షన్లు లేదా ALL-CAPS కాన్స్టంట్ ఐడెంటిఫైయర్లను తొలగించే లేదా మార్చే
రీరైట్ను పంపడానికి `validateCompression()` (`validation.ts`) నిరాకరిస్తుంది.

ఇది ఆశించిన, సురక్షితమైన ప్రవర్తనే, బగ్ కాదు: ప్రధానంగా శుభ్రమైన ఫైళ్లను రీడ్/grep చేసే కోడింగ్ సెషన్లో
కంప్రెషన్ పూర్తిగా ప్రారంభించబడినప్పటికీ మొత్తం పొదుపులు పరిమితంగానే ఉంటాయి, అయితే విఫలమవుతున్న
లూప్ లేదా అతిగా అవుట్పుట్ ఇచ్చే లింటర్ను ఎదుర్కొనే సెషన్లో ఆ ట్రాఫిక్పై పూర్తి 78-95% పరిధి కనిపిస్తుంది. ఒకే సెషన్లోని
తక్కువ సమగ్ర పొదుపు శాతాన్ని కంప్రెషన్ తప్పుగా కాన్ఫిగర్ చేయబడిందనే ఆధారంగా ఉపయోగించవద్దు — ముందుగా
అంతర్లీన టూల్ అవుట్పుట్ నిజంగా పునరావృతమైందో లేదో తనిఖీ చేయండి.

## కాన్ఫిగరేషన్

### డ్యాష్బోర్డ్

`Dashboard → Context & Cache`కు వెళ్లండి:

- **Caveman** — మోడ్ ఎంపిక, భాషా ప్యాక్లు, ప్రివ్యూ మరియు గ్లోబల్ డిఫాల్ట్లు
- **RTK** — కమాండ్-ఫిల్టర్ ప్రివ్యూ, RTK భద్రతా సెట్టింగ్లు మరియు ఫిల్టర్ కేటలాగ్
- **Compression Combos** — రూటింగ్ కాంబోలకు కేటాయించిన పేరుగల ఇంజిన్ పైప్లైన్లు
- **Auto-Trigger Threshold** — టోకెన్ల సంఖ్య థ్రెషోల్డ్ను మించినప్పుడు స్వయంచాలకంగా కంప్రెషన్ను ప్రారంభిస్తుంది

### ఒక్కో కాంబోకు ఓవర్రైడ్

`Dashboard → Context & Cache → Compression Combos`లో, ఒక రూటింగ్ కాంబోకు కంప్రెషన్ కాంబోను కేటాయించండి:

```txt
కాంబో: "free-tier-fallback"
  కంప్రెషన్ కాంబో: "coding-agent-stack"
  పైప్లైన్: RTK -> Caveman
  లక్ష్యాలు:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

దీని ద్వారా చెల్లింపు సబ్స్క్రిప్షన్లపై లైట్ మోడ్ను కొనసాగిస్తూనే, ఉచిత/కోడింగ్ ప్రొవైడర్లపై స్టాక్డ్ కంప్రెషన్ను ఉపయోగించవచ్చు.

ఈ "Per-Combo Override" కేటాయింపు, **routing-combo compression mode** ఓవర్రైడ్కు (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — ఈ ఫీల్డ్ స్కీమా `rtk`, `stacked` మరియు `omniglyph`లను కూడా అంగీకరిస్తుంది) భిన్నమైన నియంత్రణ — ఆ ఓవర్రైడ్ పేరుగల కంప్రెషన్-కాంబో పైప్లైన్ను ఎంచుకోదు; అది కేవలం `resolveCompressionPlan` పరిశీలించే `compressionMode` ఫీల్డ్ను సెట్ చేస్తుంది. దీన్ని కాంబో కార్డ్లో (`Dashboard → Combos`) లేదా #6760 నుంచి, పైన డాక్యుమెంట్ చేసిన పైప్లైన్-కేటాయింపు చెక్బాక్స్ పక్కనే ఉన్న `Dashboard → Context & Cache → Compression Combos`లోని "Assign to routing" జాబితాలో ఒక్కో రూటింగ్ కాంబోకు సెట్ చేయవచ్చు. రెండు ఇంటర్ఫేస్లలో చేసిన మార్పులూ ఒకే `PUT /api/combos/{id}` ఎండ్పాయింట్ ద్వారా నిల్వ చేయబడతాయి.

### ఒక్కో రిక్వెస్ట్కు ఓవర్రైడ్

ఒకే రిక్వెస్ట్కు కంప్రెషన్ ప్లాన్ను ఓవర్రైడ్ చేయడానికి `x-omniroute-compression` రిక్వెస్ట్ హెడర్ను పంపండి. దీనికే అత్యధిక ప్రాధాన్యత ఉంటుంది — ఇది రూటింగ్-కాంబో ఓవర్రైడ్, యాక్టివ్ ప్రొఫైల్, ఆటో-ట్రిగ్గర్ మరియు ప్యానెల్ Default కంటే ప్రాధాన్యత పొందుతుంది. తెలియని విలువలు విస్మరించబడతాయి (రిక్వెస్ట్ను ఎప్పుడూ తిరస్కరించరు), అలాగే గ్లోబల్ మాస్టర్ స్విచ్ ఇప్పటికీ అన్నింటినీ నియంత్రిస్తుంది: కంప్రెషన్ గ్లోబల్గా ఆఫ్లో ఉన్నప్పుడు, హెడర్ దాన్ని ఆన్ చేయలేదు. విలువలు:

| విలువ         | ప్రభావం                                                                                                   |
| ------------- | --------------------------------------------------------------------------------------------------------- |
| `off`         | ఈ రిక్వెస్ట్కు కంప్రెషన్ ఉండదు.                                                                           |
| `default`     | ప్యానెల్-ఉత్పన్న Default ప్రొఫైల్ (యాక్టివ్ ప్రొఫైల్ను విస్మరిస్తుంది). లాసీ ఇంజిన్లు ఆఫ్లోనే ఉంటాయి.     |
| `safe`        | హెడర్ను ఇవ్వకపోవడంతో సమానం: డీడప్ మరియు వైట్స్పేస్ ఫోల్డింగ్ మాత్రమే.                                     |
| `allow-lossy` | సమరీలు, ప్రాసంగికత ఫిల్టర్లు మరియు శైలి రీరైట్లతో సహా ఈ రిక్వెస్ట్ యొక్క ఆపరేటర్ ప్లాన్ను కొనసాగిస్తుంది. |
| `engine:<id>` | ప్రారంభించబడి ఉన్నప్పుడు ఒకే ఇంజిన్, ఉదా. `engine:rtk`. ఇది ఆ ఇంజిన్ కోసం ఒక్కో రిక్వెస్ట్కు ఆప్ట్-ఇన్.   |
| `<combo>`     | పేరుగల కాంబో; ముందుగా పేరు ఆధారంగా (కేస్ను పట్టించుకోకుండా), ఆపై id ఆధారంగా సరిపోల్చబడుతుంది.             |

`allow-lossy`, `engine:<id>` లేదా పేరుగల కాంబో లేకుండా, లాసీ ఇంజిన్లు వర్తింపజేయబడవు. కంప్రెషన్ ఆన్లో ఉన్నప్పుడు రిక్వెస్ట్కు ఇప్పటికీ సెషన్ డీడప్ మరియు వైట్స్పేస్ ఫోల్డింగ్ వర్తిస్తాయి.

వర్తింపజేసిన ప్లాన్ `X-OmniRoute-Compression: <mode>; source=<source>` రెస్పాన్స్ హెడర్లో తిరిగి అందించబడుతుంది, ఇందులో `<source>` అనేది `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` లేదా `off`లో ఒకటి.

కంప్రెషన్ ఆన్లో ఉన్నప్పుడు క్యాషింగ్ ప్రొవైడర్ల కోసం `aggressive` మరియు `ultra`ను `standard`కు

మోడల్ అవుట్పుట్ను రూపొందించే, డిఫాల్ట్గా ఆఫ్లో ఉండే, ఆప్ట్-ఇన్ సిస్టమ్-ప్రాంప్ట్ సూచనలు.

### క్యాష్-అవేర్ కంప్రెషన్

కొన్ని ప్రొవైడర్లు (ప్రాంప్ట్ క్యాషింగ్తో కూడిన Anthropic వంటివి) **ప్రాంప్ట్ క్యాషింగ్**కు మద్దతు ఇస్తాయి,
ఇది ఖర్చులు మరియు లేటెన్సీని తగ్గించడానికి ప్రాంప్ట్లోని భాగాలను క్యాష్ చేయడానికి వీలు కల్పిస్తుంది. క్యాషింగ్
ప్రారంభించబడినప్పుడు, aggressive కంప్రెషన్ వాస్తవానికి పనితీరును **దెబ్బతీయవచ్చు**,
ఎందుకంటే అది క్యాష్ చేసిన టోకెన్లను మార్చి, క్యాష్ను చెల్లనిదిగా చేస్తుంది.

`cachingAware.ts` మాడ్యూల్ **క్యాషింగ్ సందర్భాన్ని గుర్తించడం** మరియు
దానికి అనుగుణంగా **కంప్రెషన్ వ్యూహాన్ని సర్దుబాటు చేయడం** ద్వారా దీనిని పరిష్కరిస్తుంది.

#### ఇది ఎలా పనిచేస్తుంది

1. **క్యాషింగ్ సందర్భాన్ని గుర్తించడం** — `cache_control` మార్కర్ల కోసం అభ్యర్థన బాడీని స్కాన్ చేస్తుంది
2. **క్యాషింగ్ ప్రొవైడర్లను గుర్తించడం** — లక్ష్య ప్రొవైడర్ క్యాషింగ్కు మద్దతు ఇస్తుందో లేదో తనిఖీ చేస్తుంది
3. **వ్యూహాన్ని సర్దుబాటు చేయడం** — క్యాషింగ్ ప్రొవైడర్ల కోసం `aggressive`/`ultra`ను `standard`కు డౌన్గ్రేడ్ చేస్తుంది
4. **సిస్టమ్ ప్రాంప్ట్ను దాటవేయడం** — సిస్టమ్ ప్రాంప్ట్లు సాధారణంగా క్యాష్ చేయబడతాయి, కాబట్టి వాటిని కంప్రెస్ చేయవద్దు

వ్యూహ సహాయకం `deterministicOnly` ఫ్లాగ్ను కూడా తిరిగి ఇస్తుంది, కానీ ప్లాన్ బిల్డర్
వ్యూహాన్ని మాత్రమే వినియోగిస్తుంది — ప్రస్తుతం దిగువ దశల్లో ఏదీ ఆ ఫ్లాగ్ను చదవదు.

#### కోడ్ ఉదాహరణ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← క్యాష్ మార్కర్
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ఎప్పుడు ఉపయోగించాలి

క్యాష్-అవేర్ కంప్రెషన్ **ఎల్లప్పుడూ ఆన్లో ఉంటుంది** — ఎలాంటి కాన్ఫిగరేషన్ అవసరం లేదు. కంప్రెషన్
ఆన్లో ఉండి, లక్ష్య ప్రొవైడర్ ప్రాంప్ట్ క్యాషింగ్కు (Anthropic, OpenAI,
మొదలైనవి) మద్దతు ఇచ్చినప్పుడల్లా ఇది అమలవుతుంది; స్పష్టమైన `cache_control` మార్కర్లు అవసరం లేదు — క్యాషింగ్ ప్రొవైడర్ ఒక్కటే
డౌన్గ్రేడ్ను ప్రారంభిస్తుంది, మార్కర్లు మాత్రమే ఎప్పుడూ ప్రారంభించవు (మార్కర్ గుర్తింపు క్యాష్
టెలిమెట్రీకి సమాచారాన్ని అందిస్తుంది, వ్యూహ నిర్ణయానికి కాదు).

### ప్రోగ్రెసివ్ ఏజింగ్

సుదీర్ఘ సంభాషణల్లో అనేక సందేశ టర్న్లు పేరుకుపోతాయి, కానీ పాత టర్న్ల ప్రాసంగికత
తగ్గిపోతుంది. `progressiveAging.ts` మాడ్యూల్ **టర్న్ దూరం ఆధారంగా సందేశాలను క్రమంగా కుదిస్తుంది**
(సంభాషణ ముగింపు నుంచి దూరాన్ని కొలుస్తారు). విడుదల చేసిన డిఫాల్ట్లతో
(`verbatim: 2, light: 2, moderate: 3`):

- **చివరి 2 టర్న్లు (దూరం ≤ 2)**: యథాతథంగా ఉంచబడతాయి
- **దూరం 3**: కేవ్మ్యాన్ కంప్రెషన్ (అనవసర పదాల తొలగింపు)
- **దూరం 4+**: అసిస్టెంట్ సందేశాలు సంక్షిప్తీకరించబడతాయి; యూజర్ సందేశాలు వాటి మొదటి
  పంక్తికి కుదించబడి, 120 అక్షరాలకు పరిమితం చేయబడతాయి; ఇతర పాత్రలు మార్చబడవు. దూరంతో సంబంధం లేకుండా సిస్టమ్ ప్రాంప్ట్లు, ఇప్పటికే-ఏజ్ చేయబడిన
  సందేశాలు మరియు తాజా యూజర్ సందేశం ఎల్లప్పుడూ యథాతథంగా ఉంచబడతాయి.
  ఏదీ పూర్తిగా తొలగించబడదు, అలాగే అందించబడే డిఫాల్ట్లతో `light`
  బ్యాండ్ను చేరుకోవడం సాధ్యం కాదు (`light` అనేది `verbatim`కు సమానం).

#### కోడ్ ఉదాహరణ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... మరో 50 టర్న్లు ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // చివరి 3 టర్న్లు: యథాతథంగా
  light: 8, // దూరం <= 8: తేలికపాటి కంప్రెషన్
  moderate: 20, // దూరం <= 20: కేవ్మ్యాన్ కంప్రెషన్
  fullSummary: 5, // టైప్కు అవసరం, బ్యాండింగ్ కోడ్ దీనిని చదవదు
  // దూరం > 20: సంక్షిప్తీకరించబడుతుంది (అసిస్టెంట్) / మొదటి పంక్తి ఉంచబడుతుంది (యూజర్)
});

// saved = ఆదా చేసిన టోకెన్ల సంఖ్య
```

#### ఎప్పుడు ఉపయోగించాలి

`aggressive` మోడ్లో ప్రోగ్రెసివ్ ఏజింగ్ **ఎల్లప్పుడూ ఆన్లో ఉంటుంది** — ఇది
`compressAggressive()`లోని 2వ దశ. Ultra మోడ్ దీనిని అమలు చేయదు. ఇది ముఖ్యంగా
వీటికి ప్రభావవంతంగా ఉంటుంది:

- దీర్ఘకాలం కొనసాగే కోడింగ్ సెషన్లు
- అనేక రోజుల సంభాషణలు
- అనేక టూల్ కాల్లు కలిగిన ఏజెంటిక్ వర్క్ఫ్లోలు

### కేవ్మ్యాన్ అవుట్పుట్ మోడ్

కేవ్మ్యాన్ అవుట్పుట్ మోడ్, సంక్షిప్త అవుట్పుట్ ఇవ్వమని మోడల్నే అడిగే **సిస్టమ్ ప్రాంప్ట్ సూచనలను**
జోడిస్తుంది — `lite` స్థాయి పూర్తి వాక్యాలను ఉంచుతూ సంక్షిప్త సమాధానాలను అడుగుతుంది, `full`
స్థాయి "తెలివైన కేవ్మ్యాన్లా క్లుప్తంగా స్పందించమని" అడుగుతుంది, అలాగే `ultra` టెలిగ్రాఫిక్ అవుట్పుట్ను అడుగుతుంది;
సూచనలు కేవలం అభ్యర్థించగలవు, వాటిని హామీ ఇవ్వలేవు. అభ్యర్థనలు వాటిని
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ద్వారా అందుకుంటాయి:
`open-sse/handlers/chatCore.ts` మొదట బ్యాక్వర్డ్-కంపాటిబిలిటీ షిమ్తో ఎంపికను పరిష్కరిస్తుంది
(`open-sse/services/compression/outputStyles/backCompat.ts`లోని
`resolveOutputStyleSelection()`); `outputStyles`
ఖాళీగా ఉన్నప్పుడు, ప్రారంభించబడిన `cavemanOutputMode`ను
`cavemanOutputMode.intensity` వద్ద `terse-prose` అవుట్పుట్ శైలికి మ్యాప్ చేస్తుంది
(క్రింద బ్యాక్వర్డ్-కంపాటిబిలిటీ చూడండి); ఖాళీ కాని `outputStyles`
ఎంపిక యథాతథంగా ఉపయోగించబడుతుంది, అప్పుడు `cavemanOutputMode.enabled` మరియు `intensity`కు ఎలాంటి
ప్రభావం ఉండదు, అయితే దాని `autoClarity` టాగుల్ మాత్రం ఇప్పటికీ వర్తిస్తుంది. `outputMode.ts`లో
సూచన టెక్స్ట్లు (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), కంటెంట్ బైపాస్ మరియు ఇంజెక్షన్ ఉపయోగించే
ప్లేస్మెంట్ హెల్పర్ ఉంటాయి; దాని స్వంత `applyCavemanOutputMode()` ఇంజెక్టర్కు
ప్రొడక్షన్ కాలర్ లేదు.

#### ఇది ఎలా పనిచేస్తుంది

ఈ మోడ్ ఇన్పుట్ను కంప్రెస్ చేయదు. ఇది సిస్టమ్ ప్రాంప్ట్కు ఒక సూచన బ్లాక్ను జోడిస్తుంది
(క్రింద ఇంజెక్షన్ ఎలా పనిచేస్తుందో చూడండి), అలాగే అభ్యర్థన కోసం ఎంచుకున్న ఏదైనా ఇన్పుట్ కంప్రెషన్ మోడ్
ఆ బ్లాక్ను ఇప్పుడు కలిగి ఉన్న బాడీపై ఆ తర్వాత కూడా అమలవుతుంది. ప్రతి స్థాయి చివర ఉండే భాగస్వామ్య
పరిమితుల క్లాజ్కు ముందు, ఆంగ్ల `full` స్థాయి ఇలా ఉంటుంది:

> "తెలివైన కేవ్మ్యాన్లా క్లుప్తంగా స్పందించండి. ఆర్టికల్లను (a/an/the), అనవసర పదాలను (just/really/basically/actually/simply), మర్యాదపూర్వక పదాలను, సందిగ్ధతను సూచించే పదాలను తొలగించండి. వాక్య ఖండాలు అనుమతించబడతాయి. చిన్న పర్యాయపదాలను ఉపయోగించండి (extensiveకు బదులు big, implementకు బదులు fix). సాంకేతిక సారాంశం, కోడ్, ఎర్రర్లు, URLలు, ఐడెంటిఫైయర్లు అన్నింటినీ ఖచ్చితంగా ఉంచండి."

ఇది ముఖ్యంగా వీటికి బాగా పనిచేస్తుంది:

- కోడ్ జనరేషన్ (మరింత క్లుప్తమైన అవుట్పుట్ = తక్కువ టోకెన్లు)
- త్వరిత ప్రశ్నోత్తరాలు (వివరణాత్మక వివరణలు అవసరం లేదు)
- బ్యాచ్ ప్రాసెసింగ్ (త్రూపుట్ను గరిష్ఠం చేయడం)

#### ఎప్పుడు ఉపయోగించాలి

కేవ్మ్యాన్ అవుట్పుట్ మోడ్ **ఆప్ట్-ఇన్**. కంప్రెషన్ ఆన్లో ఉన్నప్పుడు (`enabled: true`, కంప్రెషన్ సెట్టింగ్ల
పేజీలోని ప్రధాన టాగుల్), `cavemanOutputMode.enabled`తో దీనిని ఆన్ చేయండి; `intensity`
`lite`, `full` లేదా `ultra`ను ఎంచుకుంటుంది:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

కంప్రెషన్ కాంబో యొక్క **అవుట్పుట్ మోడ్** టాగుల్ (`outputMode`, స్థాయి `outputModeIntensity`లో)
ఆ కాంబో వర్తించే అభ్యర్థనలకు అదే స్విచ్ను సెట్ చేస్తుంది, అలాగే
`omniroute_set_compression_engine` MCP టూల్ దాని బూలియన్ `outputMode`
ఆర్గ్యుమెంట్ ద్వారా దానిని రాస్తుంది. ఖాళీ కాని `outputStyles` ఎంపిక ఈ స్విచ్ కంటే ప్రాధాన్యం పొందుతుంది. డ్యాష్బోర్డ్లో,
**క్లుప్త గద్యం** అవుట్పుట్ శైలిని ప్రారంభించడం అదే బ్లాక్ను ఇంజెక్ట్ చేస్తుంది (క్రింద అవుట్పుట్
శైలులు చూడండి).

selection చూడండి) `zh`గా ఉన్నప్పుడు మాత్రమే `applyOutputStyles()` దానిని చొప్పిస్తుంది. వరుసను దాచడం వలన సేవ్ చేసిన `terse-cjk` ఎంపిక
తొలగించబడదు: సెట్టింగ్ల API ఏ style idనైనా అంగీకరిస్తుంది, అలాగే పేజీలో ఇతర శైలులను సేవ్ చేయడం దానిని అలాగే ఉంచుతుంది. అభ్యర్థన
సమయంలో, `applyOutputStyles()` భాష తనిఖీ మాత్రమే లొకేల్ పరిమితిగా పనిచేస్తుంది.

#### చొప్పింపు ఎలా పనిచేస్తుంది

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ఎంపికను
క్యాటలాగ్తో సరిపోల్చి నిర్ధారిస్తుంది (తెలియని ids మరియు లొకేల్తో సరిపోలని శైలులు
తొలగించబడతాయి, ఎప్పుడూ ఎర్రర్ ఏర్పడదు; ఏ శైలికీ నిర్ధారించబడని ఎంపిక bodyని
మార్చకుండా ఉంచి, `no_styles`గా దాటవేయబడుతుంది), ఎంచుకున్న సూచనలను క్యాటలాగ్
క్రమంలో కలిపి,
పరిమితుల నిబంధనను **ఒక్కసారి** జోడిస్తుంది (అలాగే `less-code` లేదా `ponytail` ఎంచుకున్నప్పుడు భద్రతా నిబంధన,
`SAFETY_BOUNDARIES` లేదా దాని అనువాదాన్ని జోడిస్తుంది), మరియు బ్లాక్ను
ఒకే idempotency markerతో (`[OmniRoute Output Styles]`) ప్రారంభిస్తుంది, కాబట్టి దాన్ని మళ్లీ వర్తింపజేస్తే ఎలాంటి మార్పూ ఉండదు. నిర్ధారించబడిన
భాషకు (కింద Language selection చూడండి) అనువాదం ఉన్నప్పుడు, ఇంగ్లీష్కు బదులుగా స్థానికీకరించిన
సూచన చొప్పించబడుతుంది.

ఖాళీ కాని `messages` array ఉన్న bodyలో, idempotency తనిఖీ
content bypassకు ముందు అమలవుతుంది: `[OmniRoute Output Styles]` marker ఇప్పటికే top-level
`system` fieldలో (string లేదా content-block array) లేదా string
content ఉన్న system messageలో ఉంటే, body `already_applied`గా మార్చకుండా ఉంచబడుతుంది మరియు keyword తనిఖీ అమలవదు.
లేకపోతే, content bypass (`open-sse/services/compression/outputMode.ts`లోని
`shouldBypassCavemanOutputMode()`) చివరి మూడు
messages యొక్క textను, వాటి role ఏదైనా సరే, తనిఖీ చేసి, ఆ text
security, irreversible-action లేదా clarification keywordsతో సరిపోలినప్పుడు, లేదా
క్రమంపై ఆధారపడే sequenceలో: `first`, `then`, `after that`, `before`, `rollback` లేదా
`backup` తరువాత 240 charactersలోపు `delete`, `drop`, `migrate`, `deploy` లేదా
`release` వచ్చినప్పుడు, మొత్తం turnకు stylesను దాటవేస్తుంది. **Auto-Clarity Bypass** toggle
(`cavemanOutputMode.autoClarity`, డిఫాల్ట్గా on) onలో ఉన్నప్పుడు bypass అమలవుతుంది;
toggleను off చేస్తే keyword తనిఖీ దాటవేయబడుతుంది.

bypass turnను అనుమతించినప్పుడు, ఎప్పుడూ కొత్త `messages[0]`ను సృష్టించని
`placeSystemInstruction()` (అదే ఫైల్), తాను కనుగొనే కింది వాటిలో మొదటిదానిలో blockను ఉంచుతుంది:

1. string content ఉన్న ప్రారంభ system message: దాని text తరువాత block జోడించబడుతుంది.
2. top-level `system` field: string text తరువాత block జోడించబడుతుంది, లేదా
   content-block arrayకు కొత్త text blockగా జోడించబడుతుంది.
3. తరువాత వచ్చే string content ఉన్న మొదటి system message: దాని
   text తరువాత block జోడించబడుతుంది.
4. పైవేవీ లేకపోతే: `messages` చివర ఉన్న కొత్త system messageలో block ఉంచబడుతుంది.

`messages` array లేని bodyలో (లేదా ఖాళీ array ఉన్న bodyలో), content bypass అమలవదు మరియు
top-level `system` field పరిశీలించబడదు. string `instructions` fieldలోని text తరువాత block జోడించబడుతుంది,
అయితే ఆ fieldలో ఇప్పటికే `[OmniRoute Output Styles]` marker ఉంటే,
body `already_applied`గా మార్చకుండా ఉంచబడుతుంది. bodyలో string `instructions` field లేకపోయినా `input`
(string లేదా array) ఉంటే, ఆ fieldలో ఉన్న string కాని విలువను భర్తీ చేస్తూ block `instructions`గా మారుతుంది.
string `instructions` field గానీ, string లేదా array
`input` గానీ లేని body మార్చకుండా ఉంచబడుతుంది మరియు `no_messages`గా దాటవేయబడుతుంది.

#### ఎలా ప్రారంభించాలి

డ్యాష్బోర్డ్లో: **Compression Context → Compression Settings**
(`/dashboard/context/settings`), Output styles విభాగంలో: ప్రతి స్టైల్కు ఆన్/ఆఫ్
టాగుల్ మరియు లెవల్ సెలెక్టర్తో ఒక వరుస ఉంటుంది. కంప్రెషన్ స్వయంగా ఆన్లో ఉన్నప్పుడు
(పేజీ యొక్క మాస్టర్ టాగుల్, `enabled`) స్టైల్స్ ఇంజెక్ట్ అవుతాయి. **Auto-Clarity Bypass**
టాగుల్ **Caveman** పేజీలో (`/dashboard/context/caveman`), దాని **Output Mode** కార్డ్లో
ఉంటుంది. ప్రోగ్రామాటిక్గా, కంప్రెషన్ కాన్ఫిగ్ ఎంపికను ఇలా నిల్వ చేస్తుంది:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

బ్యాక్వర్డ్ కంపాటిబిలిటీ: `outputStyles` ఖాళీగా ఉన్నంతవరకు, పాత
`cavemanOutputMode.enabled` సెట్టింగ్ `cavemanOutputMode.intensity` వద్ద `terse-prose`కు
మ్యాప్ అవుతుంది. ఆ తర్వాత బ్లాక్ `[OmniRoute Output Styles]` మార్కర్తో ప్రారంభమవుతుంది;
పాత `applyCavemanOutputMode()` ఇంజెక్టర్ `[OmniRoute Caveman Output Mode]`ను రాసేది.
మార్కర్కు దిగువన, en, pt-BR, es, de, fr, it, ru, id మరియు viలోని టెక్స్ట్ పాత
ఇంజెక్షన్తో సరిపోతుంది; ja మరియు zhలో boundaries క్లాజ్కు ముందు ఒక అదనపు స్పేస్
ఉంటుంది. `terse-prose`కు pt-BR, es, de, fr, it, ru, zh, ja, id మరియు vi అనువాదాలు
ఉన్నాయి, కాబట్టి పరిష్కరించబడిన భాష `hu`గా ఉన్న రిక్వెస్ట్కు, పాత ఇంజెక్టర్ ఉపయోగించిన
హంగేరియన్ టెక్స్ట్కు బదులుగా ఇంగ్లీష్ టెక్స్ట్ లభిస్తుంది.

అవుట్పుట్-స్టైల్ భాష ఎంపిక (`outputStyles/apply.ts`లోని
`resolveOutputStyleLanguage()`): `languageConfig.enabled` ఆన్లో ఉన్నప్పుడు,
`autoDetect` రిక్వెస్ట్ యొక్క `messages` అర్రేలో టెక్స్ట్ ఉన్న అత్యంత తాజా యూజర్
మెసేజ్ను (స్ట్రింగ్ కంటెంట్ లేదా దాని కంటెంట్ భాగాలలోని `text`) శాంపిల్ చేసి, దానిపై
Caveman ఇంజిన్ డిటెక్టర్ (`detectCompressionLanguage()`)ను అమలు చేస్తుంది. టెక్స్ట్లో
Han అక్షరాలు ఉండి kana లేకపోతే డిటెక్టర్ `zh`ను రిటర్న్ చేస్తుంది; లేకపోతే `it`,
`pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` మరియు `id`లలో అత్యధిక హింట్ మ్యాచ్లు
ఉన్నదాన్ని రిటర్న్ చేస్తుంది; ఏదీ మ్యాచ్ కాకపోతే `en`ను రిటర్న్ చేస్తుంది —
వర్గీకరించలేని టెక్స్ట్కు ఇంగ్లీష్ వస్తుంది, `defaultLanguage` ఎప్పుడూ రాదు; అలాగే
స్టైల్స్లో `vi` టెక్స్ట్ ఉన్నప్పటికీ `vi` ఎప్పుడూ గుర్తించబడదు. Responses API బాడీ తన
టర్న్లను `input`లో ఉంచుతుంది; దాన్ని శాంపిల్ చేయరు, కాబట్టి దానికి మొదట
`defaultLanguage`, ఆ తర్వాత ఇంగ్లీష్ వర్తిస్తాయి. `messages`లోని ఏ యూజర్ మెసేజ్లోనూ
టెక్స్ట్ లేనప్పుడు లేదా `autoDetect` ఆఫ్లో ఉన్నప్పుడు, మొదట `defaultLanguage`, ఆ తర్వాత
ఇంగ్లీష్ వర్తిస్తాయి. `languageConfig.enabled` ఆఫ్లో ఉన్నప్పుడు భాష ఇంగ్లీష్ —
అయితే రిక్వెస్ట్కు కంప్రెషన్ కాంబో వర్తిస్తే మాత్రం కాదు (రిక్వెస్ట్ యొక్క రూటింగ్
కాంబోకు కేటాయించిన కాంబో లేదా బిల్ట్-ఇన్ స్టాక్డ్ పైప్లైన్ కోసం chatCore ఫాల్బ్యాక్
అయ్యే డిఫాల్ట్ కంప్రెషన్ కాంబో): కాంబోను వర్తింపజేయడం వల్ల ఆ రిక్వెస్ట్కు
`languageConfig.enabled` ఆన్ అవుతుంది మరియు కాంబో యొక్క లాంగ్వేజ్ ప్యాక్ల ఆధారంగా
`defaultLanguage` సెట్ అవుతుంది (సేవ్ చేసిన విలువ కాంబో ప్యాక్లలో ఒకటైతే అదే;
లేకపోతే కాంబో యొక్క మొదటి ప్యాక్, ఇది డిఫాల్ట్గా `en`), అదే సమయంలో సేవ్ చేసిన
`autoDetect` (డిఫాల్ట్గా ఆన్) వర్తిస్తూనే ఉంటుంది. Caveman ఇన్పుట్ ఇంజిన్ తన
రూల్-ప్యాక్ భాషను వేరుగా ఎంచుకుంటుంది — ప్రతి టెక్స్ట్ భాగానికి విడిగా, అలాగే
ఆటో-డిటెక్ట్ ఆఫ్లో ఉన్నప్పుడు `enabledPacks` ఆధారంగా గేట్ చేయబడుతుంది.

### టూల్ రిజల్ట్ కంప్రెషన్

`open-sse/services/compression/toolResultCompressor.ts`లోని `compressToolResult()`
టూల్-రిజల్ట్ టెక్స్ట్ను **5 వ్యూహాలతో** కంప్రెస్ చేస్తుంది. ఇది వాటిని ఈ క్రమంలో
ప్రయత్నిస్తుంది; చెక్ కంటెంట్తో సరిపోలే మొదటి ఎనేబుల్ చేసిన వ్యూహమే ఫలితాన్ని
నిర్ణయిస్తుంది:

1. **`fileContent`**: 3 లేదా అంతకంటే ఎక్కువ పంక్తుల కంటెంట్లో, ప్రారంభ ఇండెంటేషన్ను విస్మరిస్తే, కనీసం ఒక పంక్తి `import `, `export `, `function `, `class `,
   `const `, `let `, `var ` లేదా `return `తో (కీవర్డ్తో పాటు ఒక స్పేస్), లేదా `if`,
   `for` లేదా `while` తర్వాత `(` లేదా ` (`తో ప్రారంభమైతే, దాని మొదటి 20 మరియు చివరి 5 పంక్తులను
   ఉంచి, తొలగించిన మధ్య భాగాన్ని గుర్తిస్తుంది.
2. **`grepSearch`**: `<path>:<digits>:` రూపంలో కనీసం ఒక పంక్తి ఉన్న కంటెంట్లో,
   మొదటి కోలన్కు ముందు ఉన్న టెక్స్ట్లో వైట్స్పేస్ లేకపోతే, అటువంటి పంక్తులను మాత్రమే, గరిష్ఠంగా
   30 వరకు ఉంచి, ఆ తర్వాత అదనపు సరిపోలికల సంఖ్యను మరియు సరిపోలిన ఫైళ్ల జాబితాను చూపిస్తుంది;
   మిగతా ప్రతి పంక్తినీ తొలగిస్తుంది. వ్యూహాన్ని ట్రిగ్గర్ చేయడానికి అటువంటి ఒక్క పంక్తి సరిపోతుంది, కాబట్టి
   `12:30:45` వంటి టైమ్స్టాంప్తో ప్రారంభమయ్యే లాగ్ పంక్తి కూడా పరిగణించబడుతుంది.
3. **`shellOutput`**: ANSI CSI సీక్వెన్స్ (`ESC[` తర్వాత అంకెలు లేదా
   సెమీకోలన్లు, ఆపై రంగు కోడ్లలో ఉన్నట్లుగా ఒక అక్షరం) లేదా టెక్స్ట్లో ఎక్కడైనా వైట్స్పేస్
   తర్వాత వచ్చే `$` ఉన్న అవుట్పుట్ ఆ సీక్వెన్స్లను కోల్పోతుంది (ఇతర ఎస్కేప్లు, ఉదాహరణకు `ESC[?25l` లేదా
   OSC విండో-టైటిల్ సీక్వెన్స్, అలాగే ఉంచబడతాయి) మరియు వరుసగా పునరావృతమయ్యే పంక్తులను కుదిస్తూ,
   దాని చివరి 50 పంక్తులను ఉంచుతుంది. ఈ తనిఖీ `json` మరియు `errorMessage` కంటే ముందు నడుస్తుంది కాబట్టి,
   అటువంటి `$` ఉన్న JSON లేదా ఎర్రర్ అవుట్పుట్, `shellOutput` ఆన్లో ఉన్నప్పుడు వాటి వరకు
   ఎప్పటికీ చేరదు.
4. **`json`**: ఐచ్ఛిక వైట్స్పేస్ తర్వాత `{` లేదా `[`తో ప్రారంభమై, పార్స్ అయ్యే
   2,000 అక్షరాల కంటే ఎక్కువ పరిమాణం గల JSON పేలోడ్ సంగ్రహించబడుతుంది: 7 కంటే ఎక్కువ అంశాలు ఉన్న అరే
   దాని మొదటి 5 మరియు చివరి 2 అంశాలను, అలాగే మొత్తం సంఖ్యను ఉంచుతుంది; ఒక ఆబ్జెక్ట్ దాని మొదటి 20
   కీలను ఉంచుతుంది, ప్రతి నెస్టెడ్ ఆబ్జెక్ట్ లేదా అరే విలువను `{…N keys}` ప్లేస్హోల్డర్తో
   భర్తీ చేస్తుంది (అరే విషయంలో, N దాని పొడవు), అలాగే మొదటి 20 తర్వాత తొలగించిన కీల సంఖ్యను సూచించే
   `_remaining_<N>_keys` మార్కర్ను జోడిస్తుంది. స్కేలర్ విలువలు పూర్తిగా కాపీ చేయబడతాయి, కాబట్టి
   నెస్టెడ్ విలువలు లేని, 20 లేదా అంతకంటే తక్కువ కీలు గల ఆబ్జెక్ట్ కేవలం మళ్లీ ఇండెంట్ చేయబడుతుంది —
   మినిఫై చేసిన ఆబ్జెక్ట్కు అక్షరాలు పెరుగుతాయి మరియు అది మారకుండా ఉంటుంది.
5. **`errorMessage`**: ఎక్కడైనా, ఏ అక్షర రూపంలోనైనా, `error:`,
   `error ` (`no error found`లో ఉన్నట్లుగా, పదం తర్వాత ఒక స్పేస్), `[error]`,
   `exception:`, `exception `, `[exception]` లేదా `traceback` ఉన్న అవుట్పుట్ దాని మొదటి పంక్తిని,
   తదుపరి 10 పంక్తులను మరియు చివరి 3 పంక్తులను ఉంచి, వాటి మధ్య ఉన్న పంక్తుల స్థానంలో
   `… [N frames elided] …` మార్కర్ను ఉంచుతుంది. మొదటి పంక్తి తర్వాత 13 కంటే ఎక్కువ పంక్తులు
   ఉన్నప్పుడే మార్కర్ కనిపిస్తుంది, కాబట్టి 14 లేదా అంతకంటే తక్కువ పంక్తుల ఎర్రర్ అవుట్పుట్
   కుదించబడదు (12 లేదా 13 పంక్తుల వద్ద చివరి 3 పంక్తులు ఇప్పటికే ఉంచిన పంక్తులను పునరావృతం చేస్తాయి).

ఒక వ్యూహం సరిపోలిన తర్వాత, అది ఏమీ ఆదా చేయకపోయినా, తర్వాతి వ్యూహాలను
ప్రయత్నించరు. సరిపోలిన వ్యూహం అంచనా టోకెన్లను ఏవీ ఆదా చేయనప్పుడు (పొడవు ÷ 4, పై పూర్ణాంకానికి రౌండ్ చేయబడుతుంది) —
ఉదాహరణకు 25 లేదా అంతకంటే తక్కువ పంక్తుల కోడ్-వంటి ఫైల్, లేదా 2,000 కంటే ఎక్కువ
అక్షరాలు ఉన్నప్పటికీ 7 లేదా అంతకంటే తక్కువ అంశాలు గల JSON అరే — అగ్రెసివ్ ఇంజిన్ అసలు టూల్
ఫలితాన్ని ఉంచుతుంది: `saved` 0 లేదా అంతకంటే తక్కువగా ఉన్నప్పుడు ఇద్దరు కాలర్లు (`compressAggressive()` మరియు `compressAnthropicToolResultBlock()`)
అసలుదానినే ఉంచుతారు, అయితే `compressToolResult()` మాత్రం ఇప్పటికీ
ఆ వ్యూహపు అవుట్పుట్ను తిరిగి ఇస్తుంది. టూల్-రిజల్ట్ దశే చివరి నిర్ణయం కాదు:
ఇంజిన్ యొక్క ఫాల్బ్యాక్ సమ్మరైజర్ ఇప్పటికీ 8,192 అక్షరాల కంటే పొడవైన `tool` లేదా `function`
సందేశాన్ని (`maxTokensPerMessage`, 2,048, గుణించబడినది 4తో) కుదించగలదు.

#### ఎప్పుడు ఉపయోగించాలి

టూల్ రిజల్ట్ కంప్రెషన్ అనేది అగ్రెసివ్ ఇంజిన్లోని 1వ దశ (`compressAggressive()` in
`open-sse/services/compression/aggressive.ts`), కాబట్టి ఇది Aggressive మోడ్లో మరియు స్టాక్డ్ పైప్లైన్లోని
`aggressive` దశలో నడుస్తుంది. ఇది OpenAI-రూపంలోని `tool` మరియు `function`
సందేశాలను, అలాగే Anthropic `tool_result` బ్లాక్లలోని టెక్స్ట్ను కంప్రెస్ చేస్తుంది. ప్రతి వ్యూహానికి
`aggressive.toolStrategies` కింద దాని స్వంత స్విచ్ ఉంటుంది; అన్నీ డిఫాల్ట్గా ఆన్లో ఉంటాయి. డ్యాష్బోర్డ్లో,
కంప్రెషన్ ఆన్లో ఉండి డిఫాల్ట్ మోడ్ Aggressiveగా ఉన్నప్పుడు, స్విచ్లు Caveman పేజీ యొక్క **Advanced** వీక్షణలో ఉంటాయి.

### స్టాక్డ్ పైప్లైన్

స్టాక్డ్ మోడ్ **అనేక ఇంజిన్లను వరుసగా** నడుపుతుంది — సాధారణంగా ముందుగా RTK
(టూల్ అవుట్పుట్పై 60-90% ఆదా), ఆ తర్వాత మిగిలిన టెక్స్ట్పై Caveman (~46% ఇన్పుట్
ఆదా). కలిపితే, అది **78-95% అర్హత పరిధి** (పైన ఉన్న Upstream Savings Mathను చూడండి):
`1 - (1 - 0.60..0.90) × (1 - 0.46)` సగటు ≈89%.

#### ఇది ఎలా పనిచేస్తుంది

```
ఇన్పుట్ (1000 టోకెన్లు)
  → RTK (కమాండ్-అవగాహన గల ఫిల్టర్) → 200 టోకెన్లు
    → Caveman (అనవసర పదాల తొలగింపు) → 108 టోకెన్లు
  → అవుట్పుట్ (108 టోకెన్లు, ~89% ఆదా)
```

#### ఎప్పుడు ఉపయోగించాలి

స్టాక్డ్ మోడ్ను వీటి కోసం ఉపయోగించండి:

- టూల్-ఆధిక్య వర్క్ఫ్లోలు (ఏజెంటిక్ కోడింగ్, పరిశోధన)
- ఖర్చు-సున్నితమైన బ్యాచ్ ప్రాసెసింగ్
- మీకు గరిష్ఠ టోకెన్ ఆదా అవసరమైనప్పుడు

స్టాక్డ్ పైప్లైన్లు గ్లోబల్ `stackedPipeline` కంప్రెషన్
సెట్టింగ్ ద్వారా, లేదా రూటింగ్ కాంబోకు కేటాయించిన పేరుగల కంప్రెషన్ కాంబో ద్వారా కాన్ఫిగర్ చేయబడతాయి (పైన ఉన్న
Per-Combo Overrideను చూడండి) — auto-combo `modePack` ద్వారా కాదు (ఆ ఫీల్డ్
auto-combo మోడల్ ఎంపికకు మాత్రమే మళ్లీ వెయిట్లను కేటాయిస్తుంది, మరియు `stacked` చెల్లుబాటు అయ్యే ప్యాక్ పేరు కాదు).

## కాంబోకు ప్రత్యేకమైన కంప్రెషన్ ఓవర్రైడ్లు

వివిధ వినియోగ సందర్భాల కోసం ప్రవర్తనను సూక్ష్మంగా సర్దుబాటు చేయడానికి, గ్లోబల్ కంప్రెషన్ మోడ్ను **ప్రతి కాంబోకు** ఓవర్రైడ్ చేయవచ్చు:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

ఇది వీటికి ఉపయోగకరంగా ఉంటుంది:

- **కోడింగ్ కాంబోలు**: సుదీర్ఘ సెషన్ల కోసం `aggressive` మోడ్ను ఉపయోగించండి
- **త్వరిత ప్రశ్నోత్తర కాంబోలు**: వేగవంతమైన ప్రతిస్పందనల కోసం `lite` మోడ్ను ఉపయోగించండి
- **టూల్స్ను ఎక్కువగా ఉపయోగించే కాంబోలు**: గరిష్ఠ ఆదా కోసం `stacked` మోడ్ను ఉపయోగించండి
- **ప్రొడక్షన్ కాంబోలు**: క్యాషింగ్ ప్రొవైడర్ల కోసం ఓవర్రైడ్ను ఆఫ్లోనే ఉంచండి — ఎల్లప్పుడూ ఆన్లో ఉండే
  క్యాష్-అవేర్ సర్దుబాటు `aggressive`/`ultra`ను స్వయంచాలకంగా `standard`కు డౌన్గ్రేడ్ చేస్తుంది
  (`cache-aware` మోడ్ను ఎంచుకునే అవకాశం లేదు)
