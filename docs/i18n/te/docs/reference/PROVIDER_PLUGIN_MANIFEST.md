`open-sse/config/providerPluginManifest.ts` JSON-సురక్షిత ప్రొవైడర్
ప్లగిన్ కాంట్రాక్ట్ను నిర్వచిస్తుంది. `open-sse/config/providerPluginManifestRegistry.ts` ఆ
కాంట్రాక్ట్ను Bifrost, CLIProxyAPI లేదా భవిష్యత్తులో వచ్చే Go/Rust రౌటర్ వంటి
సైడ్కార్ల కోసం ప్రస్తుత ప్రొవైడర్ రిజిస్ట్రీకి అనుసంధానిస్తుంది. TypeScript రిజిస్ట్రీనే
ప్రామాణిక మూలంగా కొనసాగుతుంది, అయితే సైడ్కార్లు ఎగ్జిక్యూటర్ కోడ్, OAuth డిఫాల్ట్లు,
హెడర్లు లేదా ప్రాసెస్ ఎన్విరాన్మెంట్ స్థితిని దిగుమతి చేసుకోకుండానే మానిఫెస్ట్ను
వినియోగించగలవు.

ప్రాసెస్ వెలుపల అమలయ్యే సైడ్కార్ల కోసం అదే మానిఫెస్ట్ HTTP ద్వారా
`GET /api/v1/provider-plugin-manifest` వద్ద అందుబాటులో ఉంటుంది.

OmniRoute ఆ URLను Bifrost మరియు CLIProxyAPIలకు
`X-OmniRoute-Provider-Manifest-Url` అభ్యర్థన హెడర్ ద్వారా తెలియజేస్తుంది. సైడ్కార్కు
స్థానిక అభ్యర్థన మూలానికి బదులుగా పబ్లిక్ లేదా కంటైనర్ నెట్వర్క్ URL అవసరమైనప్పుడు
`OMNIROUTE_PROVIDER_MANIFEST_URL`ను సెట్ చేయండి.

## మానిఫెస్ట్ను రిఫ్రెష్ చేయడం

HTTP ఎండ్పాయింట్ `Cache-Control: public, max-age=60`తో పాటు బలమైన
`ETag`ను తిరిగి ఇస్తుంది. సైడ్కార్ చివరిగా ధృవీకరించిన మానిఫెస్ట్ను నిల్వ ఉంచి, రిఫ్రెష్
చేసేటప్పుడు దాని ETagను `If-None-Match`లో పంపాలి. `304 Not Modified` ప్రతిస్పందనలో
బాడీ ఉండదు; సైడ్కార్ తన క్యాష్ చేసిన మానిఫెస్ట్ను కొనసాగిస్తుంది. ధృవీకరించిన క్యాష్
మానిఫెస్ట్ ఏదీ లేకపోతే, సైడ్కార్ `304`ను అంగీకరించకుండా షరతుల్లేని అభ్యర్థనను
పంపాలి.

## లక్ష్యం

ప్రొవైడర్ మెటాడేటాను ప్లగిన్ కాంట్రాక్ట్ దిశగా తరలించడం, తద్వారా హాట్ అభ్యర్థన మార్గాన్ని
చివరికి తక్కువ లేటెన్సీ గల సైడ్కార్ నిర్వహించగలదు; ఇదే సమయంలో OmniRoute
TypeScript రూట్ను పాలసీ గేట్గా మరియు ఫాల్బ్యాక్గా ఉంచుతుంది. మానిఫెస్ట్ అదనంగా
జోడించబడేది: అది స్వయంగా అభ్యర్థన రూటింగ్ను మార్చదు.

## కాంట్రాక్ట్

మానిఫెస్ట్లో ఇవి ఉంటాయి:

- ప్రొవైడర్ id మరియు అలియాస్
- అప్స్ట్రీమ్ ఫార్మాట్ మరియు ఎగ్జిక్యూటర్ పేరు
- ఆథ్ రకం, ఆథ్ హెడర్ మరియు ఐచ్ఛిక ఆథ్ ప్రిఫిక్స్
- స్థిర ఎండ్పాయింట్ మెటాడేటా
- సైడ్కార్ అర్హత మరియు ఒక ప్రొవైడర్ TSలోనే కొనసాగాల్సినప్పుడు దానికి స్పష్టమైన కారణాలు
- కాంటెక్స్ట్ పొడవు, విజన్/రీజనింగ్ ఫ్లాగ్లు మరియు మద్దతులేని పారామీటర్లు వంటి
  JSON-సురక్షిత మోడల్ మెటాడేటా
- `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` మరియు `usage-supported`తో సహా సామర్థ్య ట్యాగ్లు

మానిఫెస్ట్ ఉద్దేశపూర్వకంగా వీటిని మినహాయిస్తుంది:

- OAuth క్లయింట్ సీక్రెట్లు మరియు డిఫాల్ట్ సీక్రెట్ విలువలు
- రన్టైమ్ ఎన్విరాన్మెంట్ రిజల్యూషన్
- అభ్యర్థన హెడర్లు మరియు పబ్లిక్ క్రెడెన్షియల్ హెల్పర్లు
- డైనమిక్ URL బిల్డర్లు
- ఎగ్జిక్యూటర్ ఫంక్షన్లు
- సెషన్ పూల్ అంతర్గత అంశాలు

## సామర్థ్య ట్యాగ్లు

`capabilities` అనేది రిజిస్ట్రీ ఎంట్రీ నుంచి ఉత్పన్నమైన, క్రమబద్ధీకరించిన ట్యాగ్ల శ్రేణి. ఇంటిగ్రేటర్లు
TypeScript సోర్స్లను మళ్లీ చదవడానికి బదులుగా, "ఈ ప్రొవైడర్ ఏమి చేయగలదు" అనే ప్రశ్నకు
దీన్ని యంత్రం చదవగల సమాధానంగా పరిగణించాలి.

| ట్యాగ్               | అర్థం                                                                                        |
| -------------------- | -------------------------------------------------------------------------------------------- |
| `apikey`             | API కీని అంగీకరిస్తుంది (`authType` అనేది `apikey` లేదా `optional`).                         |
| `oauth`              | OAuth లేదా సెషన్ ఫ్లోను ఉపయోగిస్తుంది.                                                       |
| `responses`          | OpenAI Responses-API బేస్ URLను అందుబాటులో ఉంచుతుంది.                                        |
| `passthrough-models` | స్థిర కేటలాగ్కు బదులుగా అప్స్ట్రీమ్ నుంచి మోడల్లను నేరుగా అందిస్తుంది.                       |
| `custom-executor`    | డిఫాల్ట్ కాని ఎగ్జిక్యూటర్ను అమలు చేస్తుంది, కాబట్టి ఇది TypeScript మార్గంలోనే కొనసాగుతుంది. |
| `sidecar-candidate`  | `sidecar.eligible`ను ప్రతిబింబిస్తుంది — సైడ్కార్ దిగుమతి కోసం పరిగణించడం సురక్షితం.         |
| `usage-fetch`        | అనుసంధానించబడిన వినియోగం లేదా కోటా ఫెచర్ (`getUsageForProvider`)ను కలిగి ఉంటుంది.            |
| `usage-supported`    | వినియోగ API ఈ ప్రొవైడర్ను అంగీకరిస్తుంది (`isSupportedUsageConnection`).                     |

`usage-fetch` కేవలం డిస్కవరీ కోసం మాత్రమే. ప్రొవైడర్కు సంబంధించిన వినియోగాన్ని ఎలా చదవాలో
OmniRouteకు తెలుసని ఇది నివేదిస్తుంది; ఇది ఫెచింగ్ను సక్రియం చేయదు, కోటా సెమాంటిక్స్ను
మార్చదు లేదా ప్రొవైడర్ కోసం Dashboard కోటా విడ్జెట్ ప్రారంభించబడిందని సూచించదు — ఆ విడ్జెట్
`USAGE_SUPPORTED_PROVIDERS` ద్వారా వేరుగా గేట్ చేయబడుతుంది. ప్రామాణిక మూలం
`open-sse/services/usage/fetcherProviders.ts`లోని `USAGE_FETCHER_PROVIDERS`.

ఆ జాబితా వినియోగ డిస్పాచర్ అంగీకరించే స్ట్రింగ్ల ఆధారంగా కీ చేయబడుతుంది, కాబట్టి అది ప్రామాణిక idలను
అలియాస్లతో కలుపుతుంది మరియు ట్యాగ్ చేయబడిన ప్రొవైడర్ల సంఖ్య కంటే కొద్దిగా ఎక్కువగా ఉంటుంది: మానిఫెస్ట్
రిజిస్ట్రీలో చాట్ ప్రొవైడర్లు కాని ఎంట్రీలకు (ఉదాహరణకు `firecrawl` శోధన ప్రొవైడర్
మరియు `amazon-q` ACP ప్రొవైడర్) ట్యాగ్ చేయడానికి మానిఫెస్ట్ ఎంట్రీ ఉండదు.

`usage-supported` అనేది సర్వర్ మరియు Dashboard వినియోగ రూట్లు ప్రొవైడర్కు సంబంధించిన కనెక్షన్ను
అంగీకరిస్తాయా అనే ప్రశ్నకు సమాధానం ఇస్తుంది. ఇది `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
మరియు `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`)లను ప్రతిబింబిస్తుంది; ఈ రెండూ
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`) ద్వారా గేట్ చేయబడతాయి. `usage-fetch`కు
భిన్నంగా, ఇది ప్రొవైడర్ idపైన మాత్రమే ఉత్పత్తి చేయబడుతుంది — రన్టైమ్ గార్డ్ అలియాస్ రిజల్యూషన్ లేకుండా
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)`ను అమలు చేస్తుంది, కాబట్టి మానిఫెస్ట్
అదే నియమాన్ని కొనసాగిస్తుంది. రెండు ట్యాగ్ల పరిధులు వేర్వేరు: 3 ప్రొవైడర్లు కేవలం
`usage-fetch`ను (`opencode`, `opencode-zen`, `xai`) మరియు 1 కేవలం
`usage-supported`ను (`xiaomi-mimo-token-plan`) కలిగి ఉంటాయి, కాబట్టి ఒకటి మరొకదాన్ని సూచించదు.

## సైడ్కార్ వినియోగం

సైడ్కార్లు `sidecar.eligible`ను షరతులు లేని రూటింగ్ నిర్ణయంగా కాకుండా, పరిమితులతో కూడిన అభ్యర్థి సంకేతంగా పరిగణించాలి. మొదటి ఇంపోర్ట్ లక్ష్యం డిఫాల్ట్ ఎగ్జిక్యూటర్ను ఉపయోగించే API-key, static-endpoint ప్రొవైడర్లు అయి ఉండాలి. సమానమైన ప్రవర్తనను సైడ్కార్ అమలు చేసి, సమానత్వాన్ని టెలిమెట్రీ నిరూపించే వరకు custom web executors, OAuth/session flows, dynamic URL builders లేదా pool config కలిగిన ప్రొవైడర్లు TypeScript ఫాల్బ్యాక్ మార్గంలోనే ఉండాలి.

సూచించిన మైగ్రేషన్ దశలు:

1. TS రిజిస్ట్రీ నుండి ప్రొవైడర్ ప్లగిన్ మానిఫెస్ట్ను రూపొందించి, ధ్రువీకరించండి.
2. API-key/static ప్రొవైడర్ల కోసం మానిఫెస్ట్ను ఇంపోర్ట్ చేసేలా Bifrost లేదా CLIProxyAPIని సిద్ధం చేయండి.
3. TS ఫాల్బ్యాక్ను ప్రారంభ స్థితిలోనే ఉంచుతూ, `OMNIROUTE_RELAY_BACKEND` వెనుక అర్హత గల ప్రొవైడర్లను సైడ్కార్ ద్వారా రూట్ చేయండి.
4. విజయ రేటు, p99 లేటెన్సీ, స్ట్రీమింగ్ ప్రవర్తన మరియు మద్దతులేని పారామీటర్ల నిర్వహణ TS మార్గంతో సరిపోలినప్పుడు మాత్రమే ప్రొవైడర్లను ప్రమోట్ చేయండి.
5. ఒక్కోసారి ఒక ప్రొవైడర్ ఫ్యామిలీ చొప్పున custom executors కోసం సైడ్కార్-నేటివ్ ప్లగిన్లను జోడించండి.

## ప్రొవైడర్లను నేరుగా Nextలో ఎందుకు పొందుపరచకూడదు

ప్రొవైడర్ ఎగ్జిక్యూషన్ను Next ఫ్రంటెండ్ నిర్వహించకూడదు. అది API సరిహద్దును కాల్ చేయాలి. అప్పుడు బ్యాకెండ్ TypeScript ఎగ్జిక్యూటర్, Bifrost, CLIProxyAPI లేదా భవిష్యత్తులోని నేటివ్ సైడ్కార్ను ఉపయోగించాలా అనేది నిర్ణయించగలదు. దీనివల్ల ఏదైనా సైడ్కార్ హ్యాండాఫ్కు ముందు రిక్వెస్ట్ సైనింగ్, అలౌలిస్ట్ తనిఖీలు, DB పాలసీ మరియు ఫాల్బ్యాక్ ప్రవర్తన కేంద్రీకృతంగా ఉంటాయి.
