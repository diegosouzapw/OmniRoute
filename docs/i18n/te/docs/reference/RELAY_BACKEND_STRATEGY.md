## సారాంశం

OmniRoute ఇప్పుడు `/api/v1/relay/chat/completions` కోసం మూడు relay మోడ్లకు మద్దతు ఇస్తుంది:

- `ts`: అదే processలో TypeScript relayని ఉపయోగిస్తుంది.
- `bifrost`: Bifrost gatewayని తప్పనిసరిగా ఉపయోగిస్తుంది.
- `auto`: అందుబాటులో ఉన్నప్పుడు Bifrostకు ప్రాధాన్యం ఇస్తుంది; విఫలమైతే TypeScriptకు fallback అవుతుంది.

మీరు అధిక request rateతో (రోజుకు పెద్ద సంఖ్యలో tokens, దాదాపు నిరంతర throughputతో) అమలు చేస్తున్నప్పుడు, fallback మార్గాన్ని స్పష్టంగా, వేగంగా ఉంచడం ఉత్తమ వ్యూహం. తద్వారా hot path పనిచేయని sidecar కోసం ఎప్పటికీ నిరీక్షిస్తూ block అవదు.

## మోడ్ ప్రవర్తన

- `ts`
  - అత్యల్ప operational complexity.
  - అన్ని routing మరియు validation చర్యలు Nodeలో అమలవుతాయి.
  - availability కోసం sidecar dependency ఉండదు.
- `bifrost`
  - అన్ని requestsను sidecar gateway ద్వారా తప్పనిసరిగా పంపిస్తుంది.
  - automatic fallback ఉండదు.
  - sidecar health మరియు latency హామీగా ఉన్నప్పుడు మాత్రమే ఉపయోగకరం.
- `auto`
  - sidecarను చేరుకోగలిగినప్పుడు మరియు అది enable అయి ఉన్నప్పుడు ఉపయోగిస్తుంది.
  - విఫలమైన ప్రయత్నాలు fallback headersను trigger చేసి, trafficను TSకు తిరిగి పంపిస్తాయి; తద్వారా request success పరిమితుల్లో ఉంటుంది.
  - strict sidecar-only routing కంటే uptimeకు ఎక్కువ ప్రాధాన్యం ఉన్న productionలో ఈ మోడ్ అత్యంత సురక్షితమైన ఎంపిక.

## ప్రస్తుతం 9router మరియు CLIPROXYAPI

9router మరియు CLIPROXYAPI రెండూ, చారిత్రకంగా upstream providers కోసం compatibility pathsను అందించిన integrations.

- 9router అనేది upstream orchestration మరియు compatibility behavior కోసం embedded path.
- CLIPROXYAPI అనేది CLI / SDK తరహా traffic కోసం proxy API bridge.
- మీకు ప్రత్యేకమైన sidecar-తరహా hop మరియు తక్కువ latency గల local dispatch అవసరమైనప్పుడు ఉపయోగించే externalized pathగా Bifrostను స్థిరీకరిస్తున్నారు.

మీరు ప్రస్తుతం 9router/CLIPROXYAPIని పోల్చి చూస్తున్నట్లయితే:

- handoffకు ముందు API routeలో request signing, allowlist checks మరియు DB policy gatesను ఉంచండి.
- workflowకు strict sidecar behavior మరియు తక్కువ per-request variance అవసరమైతే, `OMNIROUTE_RELAY_BACKEND=bifrost` ఉపయోగించండి.
- incident పరిస్థితుల్లో graceful degradationతో sidecar resilience అవసరమైతే, `OMNIROUTE_RELAY_BACKEND=auto` ఉపయోగించండి.

## Backend boundary contract

స్థిరమైన product boundary అనేది OmniRoute relay API, dashboard implementation కాదు. Next.js dashboard local servicesను install చేయవచ్చు, configure చేయవచ్చు మరియు supervise చేయవచ్చు; అయితే request routing relay API ద్వారా ప్రవేశించి, ఆ boundary వెనుక handoff కావాలి.

దీర్ఘకాలిక backend ఎంపికలు:

- TypeScript relayని in-process policy మరియు fallback pathగా ఉంచండి. ఏ backend handoffకైనా ముందు auth, allowlists, request normalization, accounting మరియు safety checks ఇక్కడే ఉండాలి.
- deploymentకు తక్కువ routing variance, centralized provider rotation లేదా అనేక OmniRoute replicasలో scale-out అవసరమైనప్పుడు, Bifrostను ప్రాధాన్య high-throughput Tier-1 sidecarగా ఉపయోగించండి.
- 9router మరియు CLIPROXYAPIని embedded compatibility servicesగా ఉంచండి. అవి supervised local processesగా అమలవుతాయి; వాటి provider/CLI behavior కావలసిన adapterగా ఉన్నప్పుడు ఉపయోగకరంగా ఉంటాయి. అయితే అవి default Tier-1 routing engineగా మారకూడదు.
- dashboard నుంచి hot pathలోకి arbitrary service URLsను పంపించవద్దు. UI అందించిన URLs configuration inputs మాత్రమే; routing code అనేది server-side settings మరియు supervisor state నుంచి registered, health-checked backendsను resolve చేయాలి.
- ప్రస్తుతం supervised services ఇప్పటికే HTTP-compatible APIsను అందిస్తున్నందున, route guard boundaryని audit చేయగలుగుతున్నందున మరియు failure/fallback behavior request logsలో కనిపిస్తున్నందున, supervised services కోసం loopback HTTPకు ప్రాధాన్యం ఇవ్వండి. isolation లేదా fallback semanticsను బలహీనపరచకుండా p99 routing latencyని కొలవదగిన స్థాయిలో తగ్గిస్తే మాత్రమే భవిష్యత్ SDK లేదా socket transportను జోడించడం విలువైనది.

అందువల్ల, అత్యధిక throughput గల deployment కోసం Bifrost enable చేసిన `auto` default సమాధానం: success rateను నిలబెట్టేందుకు TypeScript fallbackను సంరక్షిస్తూనే, hot pathలో Go sidecarను ఉపయోగించండి. graceful degradation కంటే strict sidecar-only behavior ముఖ్యమైనప్పుడు మాత్రమే `bifrost` ఉపయోగించండి.

## అధిక throughput మార్గదర్శకాలు

నిరంతర అధిక RPM/RPS మరియు strict success SLO కోసం:

1. ఆచరణయోగ్యమైన cooldown మరియు failure telemetryతో `auto` ఉపయోగించండి.
2. upstream validation మరియు API-key checksను TypeScript route boundaryలో ఉంచండి.
3. మీ alertingకు fallback frequency మరియు కారణాలు కనిపించేలా explicit headers/countersను enable చేయండి.
4. sidecar timeoutsను ఎప్పటికీ నిరీక్షించేలా కాకుండా, వేగంగా విఫలమయ్యేలా tune చేయండి.
5. fallback నిజంగా అసాధారణమైన సందర్భాల్లో మాత్రమే జరిగేలా service auto-restart మరియు health telemetry loopను ఆరోగ్యకరంగా ఉంచండి.

## సూచించిన baseline

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- route handlersలో API keys, allowlist, sanitizer మరియు rate-limit checksను enable చేసి ఉంచండి (downstream forwardingకు ముందు అవి ఎల్లప్పుడూ అమలవుతాయి).
- sidecar outages ఒక నిమిషంలోపే కనిపించేలా మీ reverse proxy మరియు request logs నుంచి fallback metricsను export చేయండి.
