రిలేలు (Vercel, Deno, Cloudflare) serverless బ్యాకెండ్పై upstream కనెక్షన్ను ముగిస్తాయి, తద్వారా provider API కీని server-sideలోనే ఉంచుతూ OmniRoute స్థిరమైన ప్రాంతం నుండి egress చేయగలదు. ప్రొడక్షన్లో ఆపరేటర్లు ఎదుర్కొనే రెండు వైఫల్య రీతులను, అలాగే ప్రతి దానికి OmniRoute అందించే పునరుద్ధరణ మార్గాలను ఈ పత్రం వివరిస్తుంది.

## రిలే auth ఎలా నిల్వ చేయబడుతుంది

మీరు **Settings → Proxy Pool → Deploy Relay** నుండి ఒక రిలేను డిప్లాయ్ చేసినప్పుడు, డిప్లాయ్ ప్రక్రియ రిలే యొక్క auth టోకెన్ను ప్రాక్సీ `notes` JSON ఫీల్డ్లో నిల్వ చేస్తుంది:

- `STORAGE_ENCRYPTION_KEY` సెట్ చేసి ఉంటే, టోకెన్ `relayAuthEnc`గా
  (నిల్వలో AES-encrypted రూపంలో) వ్రాయబడుతుంది.
- లేకపోతే, అది plaintext `relayAuth`గా వ్రాయబడుతుంది.

రిక్వెస్ట్ సమయంలో `extractRelayAuth(notes)` అందుబాటులో ఉన్న రూపాన్ని తిరిగి ఇస్తుంది,
కాబట్టి రీస్టార్ట్ల తర్వాత కూడా రిలే పని చేస్తూనే ఉంటుంది.

## వైఫల్య రీతి 1 — కీ రొటేషన్ తర్వాత డీక్రిప్ట్ చేయలేని టోకెన్

**లక్షణం:** `STORAGE_ENCRYPTION_KEY` యొక్క environment లేదా secret-manager రొటేషన్ తర్వాత, ఇంతకు ముందు పనిచేసిన రిలేలు ఇప్పుడు upstream `401`/auth లోపాలను తిరిగి ఇస్తాయి. నిల్వ చేసిన `relayAuthEnc` blobను ఇకపై డీక్రిప్ట్ చేయలేరు, కాబట్టి `extractRelayAuth` ఖాళీ stringను తిరిగి ఇస్తుంది మరియు రిలే ఎటువంటి authను పంపదు.

**పునరుద్ధరణ — ఉన్నచోటే రిపేర్ చేయడం (రీడిప్లాయ్ అవసరం లేదు):**

1. **Settings → Proxy Pool** తెరవండి.
2. auth లేని రిలే వరుసలు పసుపు రంగు `auth missing` బ్యాడ్జ్ను మరియు
   **Repair** బటన్ను చూపుతాయి.
3. **Repair** క్లిక్ చేయండి. OmniRoute
   `POST /api/settings/proxies/[id]/repair-relay`ను కాల్ చేస్తుంది, ఇది:
   - **ప్రస్తుత** కీతో `relayAuthEnc`ను డీక్రిప్ట్ చేస్తుంది,
   - plaintext `relayAuth`ను తిరిగి `notes`లో వ్రాస్తుంది,
   - `{ repaired: true, mode: "recovered" }`ను తిరిగి ఇస్తుంది.

డిప్లాయ్ credentialsను మళ్లీ నమోదు చేయకుండానే రిలే సేవలను తిరిగి ప్రారంభిస్తుంది.

ప్రస్తుత `STORAGE_ENCRYPTION_KEY` ఇప్పటికీ blobను డీక్రిప్ట్ చేయగలిగితే మాత్రమే ఇది పనిచేస్తుంది. మీరు migration **లేకుండా** కీని రొటేట్ చేసి ఉంటే, blobను తిరిగి పొందడం సాధ్యం కాదు.

## వైఫల్య రీతి 2 — తిరిగి పొందలేని టోకెన్ (పాత కీ ఇక అందుబాటులో లేదు)

**లక్షణం:** మీరు **Repair** క్లిక్ చేసిన తర్వాత
`{ repaired: false, mode: "redeploy", status: 409 }` వచ్చింది.

**పునరుద్ధరణ — రీడిప్లాయ్:**

ప్రస్తుత కీతో నిల్వ చేసిన టోకెన్ను తిరిగి పొందడం సాధ్యం కాదు. మీరు మొదట ఉపయోగించిన అదే modal నుండి రిలేను మళ్లీ డిప్లాయ్ చేయండి (**Deploy Relay** మెనూ → Vercel / Deno / Cloudflare). డిప్లాయ్ ప్రక్రియ తాజా టోకెన్ను (ప్రస్తుత కీతో encrypted రూపంలో) వ్రాస్తుంది మరియు వరుసలోని `auth missing` బ్యాడ్జ్ తొలగిపోతుంది.

UIలో, టోకెన్ను తిరిగి పొందడం సాధ్యం కానప్పుడు **Repair** బటన్ స్వయంగా రీడిప్లాయ్ modalను తెరుస్తుంది, కాబట్టి మీరు దాన్ని మాన్యువల్గా వెతకాల్సిన అవసరం ఉండదు.

## వైఫల్య రీతి 3 — రిలేను చేరుకోవచ్చు కానీ అది ఆరోగ్యకరంగా లేదు

**లక్షణం:** ప్రాక్సీ పరీక్ష (`speed` బటన్) రిలే పనిచేస్తున్నట్లు చూపుతుంది, కానీ రిక్వెస్ట్లు ఇప్పటికీ అడపాదడపా విఫలమవుతాయి.

OmniRoute యొక్క auto-test probe తిరిగి ఇచ్చే relay awareness headersను తనిఖీ చేయండి
(**Settings → Proxy Pool** మరియు `relayTested` / `relayAlive` కౌంటర్లను చూడండి):

- `x-relay-url` — ఏ relay backend స్పందించింది.
- `x-relay-mode` — ఆ రిక్వెస్ట్కు `ts` | `bifrost` | `auto`.
- `x-relay-attempts` — విజయవంతం కావడానికి ముందు ఎన్ని relay hops ప్రయత్నించబడ్డాయి.
- `x-relay-fallback` — రిక్వెస్ట్ ప్రాధాన్య backend నుండి TypeScript relayకు fallback అయినప్పుడు `true`.

తక్కువ `relayAlive`తో పాటు `x-relay-fallback` రేటు ఎక్కువగా ఉంటే, sidecar backend ఆరోగ్యకరంగా లేదని అర్థం. మీరు దాన్ని సరిచేయాలి లేదా relay backend strategyని `ts`కు మార్చాలి (`RELAY_BACKEND_STRATEGY.md` చూడండి).

## API సూచన

| పద్ధతి | మార్గం                                    | Body                    | విజయం                                                                                                                                         | వైఫల్యం                                                                                        |
| ------ | ----------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | మళ్లీ ఉత్పన్నం చేసినప్పుడు `200 { repaired: true, mode: "recovered" }`; plaintext ఇప్పటికే ఉన్నప్పుడు `200 { repaired: false, mode: "noop" }` | తిరిగి పొందలేనప్పుడు `409 { mode: "redeploy" }`; relay type కాకపోతే `400`; కనుగొనబడకపోతే `404` |

జాబితా route `GET /api/settings/proxies` ప్రతి itemకు secret రహిత
`relayInfo: { isRelay, authMissing, repairMode }`ను జోడిస్తుంది, తద్వారా టోకెన్ను ఎప్పుడూ బహిర్గతం చేయకుండానే dashboard రిపేర్ ఎంపికను చూపగలదు.
