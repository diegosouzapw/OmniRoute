AgentBridge అనేది OmniRoute యొక్క MITM (మ్యాన్-ఇన్-ది-మిడిల్) ప్రాక్సీ. ఇది IDE AI ఏజెంట్ల నుండి వచ్చే HTTPS ట్రాఫిక్ను అడ్డగించి, OmniRoute యొక్క ఏకీకృత రూటింగ్ ఇంజిన్ ద్వారా దారి మళ్లిస్తుంది. ఇది **10 IDE ఏజెంట్లకు** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code మరియు Trae (పరిశీలనలో ఉంది) — మద్దతు ఇస్తుంది, తద్వారా మార్కెట్లోని AI కోడింగ్ అసిస్టెంట్ల కోసం అత్యంత విస్తృత కవరేజ్ కలిగిన MITM ప్రాక్సీగా OmniRoute నిలుస్తుంది.

**డ్యాష్బోర్డ్ స్థానం:** `/dashboard/tools/agent-bridge`
**సైడ్బార్ సమూహం:** సాధనాలు (Cloud Agents తర్వాత)
**ఇవి కూడా చూడండి:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — అడ్డగించబడిన మొత్తం ట్రాఫిక్ను నిజ సమయంలో పర్యవేక్షించండి; `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs`లో కంపైల్ చేయబడదు) — `/api/tools/agent-bridge/tproxy` రూట్ ద్వారా నిర్వహించబడే Linux TPROXY పారదర్శక-డీక్రిప్ట్ క్యాప్చర్ మోడ్.

## §1 అవలోకనం

### AgentBridge అంటే ఏమిటి?

ఒక IDE ఏజెంట్ (ఉదా., GitHub Copilot, Cursor, Claude Code) API కాల్ చేసినప్పుడు, అది నేరుగా అప్స్ట్రీమ్ AI ప్రొవైడర్కు (OpenAI, Anthropic మొదలైనవి) కనెక్ట్ అవుతుంది. AgentBridge ఆ కనెక్షన్ను TLS స్థాయిలో పారదర్శకంగా అడ్డగించి — ఏజెంట్ కాన్ఫిగరేషన్లో ఎలాంటి మార్పు అవసరం లేకుండా — అభ్యర్థనను OmniRoute ద్వారా తిరిగి రాస్తుంది.

దీని వల్ల మీరు:

- **ఏ ఏజెంట్నైనా ఏ ప్రొవైడర్కైనా దారి మళ్లించవచ్చు**: Copilot OpenAIతో కమ్యూనికేట్ చేస్తోందా? దాన్ని Anthropic Claude, Gemini లేదా OmniRoute యొక్క 352 ప్రొవైడర్లలో దేనికైనా దారి మళ్లించండి.
- **మోడల్ మ్యాపింగ్లను వర్తింపజేయవచ్చు**: హ్యాండ్లర్ స్థాయిలో పారదర్శకంగా `gemini-3-flash` → `claude-sonnet-4.7`.
- **ఏజెంట్ ట్రాఫిక్ మొత్తాన్ని పరిశీలించవచ్చు**: అడ్డగించబడిన ప్రతి అభ్యర్థన [Traffic Inspector](./TRAFFIC_INSPECTOR.md)కు ప్రచురించబడుతుంది.
- **OmniRoute స్థితిస్థాపకతను వర్తింపజేయవచ్చు**: కాంబో రూటింగ్, సర్క్యూట్ బ్రేకర్లు, ఫాల్బ్యాక్లు మరియు వ్యయ ట్రాకింగ్ IDE ఏజెంట్ ట్రాఫిక్కు కూడా పనిచేస్తాయి.

### 2.1 కాంపోనెంట్ల అవలోకనం

```
IDE ఏజెంట్ (VS Code / Cursor / మొదలైనవి)

/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← DNS దారి మళ్లింపు
    │
    ▼
src/mitm/server.cjs  (పోర్ట్ 443, CJS చైల్డ్ ప్రాసెస్)
    │  Host హెడర్ SNI ద్వారా లక్ష్యాన్ని పరిష్కరిస్తుంది
    │  AgentBridge CA ద్వారా సంతకం చేయబడిన ప్రతి-SNI TLS సర్టిఫికేట్ను రూపొందిస్తుంది

    │       └── handler.intercept() — TypeScript
    │               ├── అభ్యర్థన బాడీ/హెడర్లపై maskSecrets()

    │               └── fetchRouter() → /v1/chat/completions
    └── సరిపోలిక లేదా? → TCP పాస్త్రూ (డీక్రిప్షన్ లేదు)
```

### 2.2 MITM సర్వర్ (`src/mitm/server.cjs`)

కోర్ MITM సర్వర్ Node.js CJS చైల్డ్ ప్రాసెస్గా నడుస్తుంది (ఇప్పటికే ఉన్న CJS కోడ్బేస్ను తిరిగి వ్రాయకుండా ఉండటానికి). ఇది:

- పోర్ట్ 443పై వింటుంది (ప్రివిలేజ్ లేదా `authbind`/`setcap` అవసరం)
- OS నుండి CONNECT టన్నెల్లను స్వీకరిస్తుంది (`/etc/hosts` DNS దారి మళ్లింపు ద్వారా)
- AgentBridge CA (`DATA_DIR/mitm/ca.crt`) ద్వారా సంతకం చేయబడిన ప్రతి-SNI TLS సర్టిఫికేట్లను రూపొందిస్తుంది
- `targets/index.ts` రిజిస్ట్రీ ద్వారా Host హెడర్ ఆధారంగా లక్ష్య ఏజెంట్ను పరిష్కరిస్తుంది
- HTTP ద్వారా `http://127.0.0.1:20128` వద్ద ఉన్న TypeScript హ్యాండ్లర్ లేయర్కు పంపిస్తుంది

`TARGET_HOSTS`, `DATA_DIR/mitm/targets.json` నుండి లోడ్ చేయబడుతుంది (బూట్ సమయంలో `targets/index.ts` ద్వారా వ్రాయబడుతుంది), దీని వలన CJS సర్వర్ను పునఃప్రారంభించకుండానే డైనమిక్ అప్డేట్లు చేయవచ్చు.

> **రూట్-CA మోడల్ (#6684).** పైన వివరించిన, ప్రతి-SNI సర్టిఫికేట్ను ఒక CAతో సంతకం చేసే
> విధానం #6684లో జోడించిన నిల్వ చేయబడే రూట్-CA మోడల్ (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`; `src/mitm/tproxy/dynamicCert.ts`లో TPROXY కోసం
> ఇప్పటికే నిరూపితమైన CA/లీఫ్ క్రిప్టోగ్రఫీని తిరిగి ఉపయోగిస్తుంది) — ఇది డిస్క్పై కేవలం
> `server.crt`/`server.key` జోడీ సూచించే పాత ఏకైక స్టాటిక్ స్వీయ-సంతక లీఫ్ను
> (`src/mitm/cert/generate.ts`, ఇప్పటికీ antigravity హోస్ట్లకు మాత్రమే పరిమితం)
> భర్తీ చేస్తుంది. **మైగ్రేషన్ ప్రవర్తన**: కొత్త ఇన్స్టాలేషన్కు (మునుపటి
> `server.crt` లేకపోతే) రూట్-CA మోడల్ స్వయంచాలకంగా లభిస్తుంది; పాత స్టాటిక్ లీఫ్ను
> ఇప్పటికే విశ్వసించిన ఇన్స్టాలేషన్లో, ఆపరేటర్ `MITM_ROOT_CA_ENABLED=true` సెట్ చేసి
> బ్రిడ్జ్ను పునఃప్రారంభించే వరకు అదే ఉపయోగించబడుతుంది (`src/mitm/cert/migration.ts`
> అనేది పూర్తిగా నిర్ణయం తీసుకునే ఫంక్షన్ — **ఏ** హోస్ట్కైనా లీఫ్పై సంతకం చేయగల
> విశ్వసనీయ MITM CA, పాత స్థిర-SAN లీఫ్ కంటే గణనీయంగా శక్తివంతమైనది; అందువల్ల ఇప్పటికే
> విశ్వసించిన ఇన్స్టాలేషన్లో ఈ మార్పు ఎప్పుడూ నిశ్శబ్దంగా జరగదు). పాత లీఫ్ ఉపయోగించిన
> అదే `omniroute-mitm.crt` ట్రస్ట్-స్టోర్ స్లాట్లో CA సర్టిఫికేట్ ఇన్స్టాల్ అవుతుంది
> (`cert/install.ts::installCaCert`) — ద్వంద్వ-విశ్వాస క్లీనప్ అవసరం లేదు.

### 2.3 హ్యాండ్లర్ బేస్ (`src/mitm/handlers/base.ts`)

అన్ని ఏజెంట్ హ్యాండ్లర్లు `MitmHandlerBase`ను విస్తరిస్తాయి:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // రక్షిత సహాయకాలు: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

ప్రతి హ్యాండ్లర్ ప్రాక్సీ చేయడానికి ముందు `hookBufferStart()`ను, పూర్తయినప్పుడు `hookBufferUpdate()`ను కాల్ చేస్తుంది. ఇవి `InterceptedRequest` ఎంట్రీలను `globalTrafficBuffer`లోకి పుష్ చేస్తాయి ([Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4 చూడండి).

### 2.4 లక్ష్యాల రిజిస్ట్రీ (`src/mitm/targets/`)

ప్రతి ఏజెంట్కు ఒక డిక్లరేటివ్ లక్ష్య ఫైల్ ఉంటుంది:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

రిజిస్ట్రీ (`targets/index.ts`) `ALL_TARGETS`ను ఎగుమతి చేస్తుంది మరియు బూట్ సమయంలో `DATA_DIR/mitm/targets.json`ను ఉత్పత్తి చేస్తుంది.

### 2.5 పాస్త్రూ మరియు బైపాస్ జాబితా (`src/mitm/passthrough.ts`)

**బైపాస్ జాబితా** (మొదట తనిఖీ చేయబడుతుంది, లక్ష్య సరిపోలిక కంటే దీనికే ప్రాధాన్యత):

- డిఫాల్ట్ నమూనాలు: బ్యాంకింగ్ హోస్ట్లు, `.gov.`, OAuth/SSO ప్రొవైడర్లు (Okta, Auth0), మొదలైనవి
- వినియోగదారు నమూనాలు: DB పట్టిక `agent_bridge_bypass`లో నిల్వ చేయబడతాయి
- బైపాస్ చేయబడిన హోస్ట్లు పారదర్శక TCP టన్నెల్ను పొందుతాయి — TLS **ఎప్పటికీ డీక్రిప్ట్ చేయబడదు**

**పాస్త్రూ డిఫాల్ట్** (లక్ష్యంతో సరిపోలకపోతే మరియు బైపాస్లో లేకపోతే):

- ఇది కూడా TCP టన్నెల్ను పొందుతుంది — కనెక్షన్లు ఎప్పటికీ విచ్ఛిన్నం చేయబడవు
- AgentBridge సాధారణ సిస్టమ్ HTTPS ట్రాఫిక్కు అంతరాయం కలిగించకుండా నిరోధిస్తుంది

రూటింగ్ ప్రాధాన్యత:

```
బైపాస్ జాబితా → లక్ష్య సరిపోలిక → పాస్త్రూ
```

### 2.6 అప్స్ట్రీమ్ CA సర్టిఫికేట్ (`src/mitm/upstreamTrust.ts`)

కస్టమ్ CA ఉన్న కార్పొరేట్ నెట్వర్క్ పరిసరాల కోసం:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

ఇది సెట్ చేసినప్పుడు, అదనపు CA సర్టిఫికేట్తో `undici` యొక్క గ్లోబల్ డిస్పాచర్ను కాన్ఫిగర్ చేస్తుంది; తద్వారా AgentBridge కార్పొరేట్ TLS టెర్మినేషన్ ప్రాక్సీల ద్వారా అప్స్ట్రీమ్ ప్రొవైడర్లను చేరుకోగలుగుతుంది.

### 2.7 సీక్రెట్ మాస్కింగ్ (`src/mitm/maskSecrets.ts`)

స్వతంత్ర క్లీన్-రూమ్ స్కానర్, అభ్యర్థన బాడీలు మరియు క్రెడెన్షియల్ హెడర్లు
Traffic Inspector బఫర్లోకి లేదా ఏదైనా లాగ్లోకి ప్రవేశించడానికి **ముందే** వాటికి వర్తింపజేయబడుతుంది. ఇది ఒకే లీనియర్ పాస్ను నిర్వహిస్తుంది:

- `sk-` / `ak-` / `pk-` ప్రిఫిక్స్ ఉన్న టోకెన్లు (OpenAI/Anthropic తరహా)
- మొత్తం టోకెన్ ప్రాధాన్యతతో RFC 6750 `Authorization: Bearer <token>` క్రెడెన్షియల్లు
- సాధారణ పొడవైన అస్పష్ట టోకెన్లు (≥40 అక్షరాలు), డాట్లు మరియు ప్యాడింగ్ ఉన్న రూపాలతో సహా

`sanitizeHeaders()` నిలుపుకున్న పేర్లను చిన్న అక్షరాలకు మారుస్తుంది, అరే విలువలను నిర్దిష్ట పద్ధతిలో కలుపుతుంది,
షేర్డ్ హాప్-బై-హాప్/ఫ్రేమింగ్ నిరాకరణ జాబితాను (ప్రాక్సీ ప్రమాణీకరణతో సహా) తొలగిస్తుంది, `cookie` మరియు
`set-cookie`లను పూర్తిగా దాచిపెడుతుంది, అలాగే క్రెడెన్షియల్ విలువలను స్కానర్కు అప్పగిస్తుంది.

### 3.1 MITM సర్వర్ను ప్రారంభించడం/ఆపడం

`/dashboard/tools/agent-bridge` వద్ద ఉన్న AgentBridge సర్వర్ కార్డ్ను ఉపయోగించండి:

| చర్య                           | వివరణ                                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------------------------- |
| సర్వర్ను ప్రారంభించు           | పోర్ట్ 443లో `src/mitm/server.cjs`ను ప్రారంభిస్తుంది                                              |
| సర్వర్ను ఆపు                   | చైల్డ్ ప్రాసెస్ను సురక్షితంగా ఆపివేస్తుంది                                                        |
| సర్వర్ను పునఃప్రారంభించు       | ఆపి + ప్రారంభిస్తుంది (టార్గెట్ మార్పులను స్వీకరిస్తుంది)                                         |
| సర్టిఫికేట్ను విశ్వసించు       | `DATA_DIR/mitm/ca.crt`ను OS ట్రస్ట్ స్టోర్లో ఇన్స్టాల్ చేస్తుంది                                  |
| సర్టిఫికేట్ను డౌన్లోడ్ చేయి    | మాన్యువల్ ఇన్స్టాలేషన్ కోసం `ca.crt`ను డౌన్లోడ్ చేస్తుంది                                         |
| సర్టిఫికేట్ను మళ్లీ రూపొందించు | కొత్త CA కీపెయిర్ను సృష్టిస్తుంది (ఇప్పటికే ఉన్న ప్రతి ఏజెంట్ సర్టిఫికేట్ చెల్లుబాటు కోల్పోతుంది) |

### 3.2 సర్టిఫికేట్ను విశ్వసించడం

IDEలు MITM కనెక్షన్ను అంగీకరించాలంటే ముందుగా AgentBridge CA సర్టిఫికేట్ను OS విశ్వసించాలి.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

లేదా డ్యాష్బోర్డ్లోని "సర్టిఫికేట్ను విశ్వసించు" బటన్ను ఉపయోగించండి (ఇది మీ OSకు తగిన కమాండ్ను అమలు చేస్తుంది; అవసరమైతే sudo ప్రాంప్ట్ను చూపుతుంది).

#### Electron-ఆధారిత IDEలు OS ట్రస్ట్ స్టోర్ను విస్మరిస్తాయి (`NODE_EXTRA_CA_CERTS`)

కొన్ని IDEలు — ముఖ్యంగా **Antigravity IDE**, అలాగే ఇతర Electron / VS Code-ఆధారిత యాప్లు — అవుట్బౌండ్
`fetch`/HTTPS కోసం **OS ట్రస్ట్ స్టోర్ను సంప్రదించని** తమ స్వంత Node.js రన్టైమ్ను బండిల్
చేస్తాయి. OS/NSS స్థాయిలో CAను విశ్వసించడం IDE యొక్క స్థానిక **బ్యాకెండ్**కు
(ఉదా. OS CA బండిల్ను ఉపయోగించే Go లాంగ్వేజ్ సర్వర్) సరిపోతుంది, కానీ **Electron ఫ్రంటెండ్**లో
TLS ఇప్పటికీ విఫలమవుతుంది — MITM లాగ్లో బ్యాకెండ్ బూట్స్ట్రాప్ కాల్లు `200`ను అందిస్తున్నట్లు
కనిపించినప్పటికీ, యాప్ _లాగ్ అవుట్ అయినట్లు_ లేదా _"కనెక్షన్ లోపం"_ చూపుతున్నట్లు ఇది
వ్యక్తమవుతుంది. రెండు దశలు అవసరం, రెండూ ముఖ్యమైనవే:

1. రన్టైమ్కు CAను స్పష్టంగా సూచించండి:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **ఆ షెల్ నుంచే IDEను ప్రారంభించండి.** డెస్క్టాప్ ఐకాన్ / Dock / Start మెను నుంచి ప్రారంభిస్తే
   షెల్ ఎక్స్పోర్ట్లు సంక్రమించవు, అలాగే `~/.config/environment.d/*.conf` తాజా గ్రాఫికల్
   లాగిన్ తర్వాత మాత్రమే వర్తిస్తుంది. ముందుగా IDEను పూర్తిగా మూసివేయండి — Electron సింగిల్టన్
   లాక్ కారణంగా రెండోసారి ప్రారంభించడం ఇప్పటికే ఉన్న ప్రాసెస్పై మాత్రమే ఫోకస్ చేస్తుంది, కొత్త
   ఎన్విరాన్మెంట్ విస్మరించబడుతుంది.

పైన పేర్కొన్న OS-ట్రస్ట్ + NSS దశ ఇప్పటికీ అవసరమే (కొన్ని ప్రమాణీకరణ ఫ్లోలు ఉపయోగించే Chromium
నెట్వర్క్ స్టాక్ ప్రతి వినియోగదారుడి NSS స్టోర్ను చదువుతుంది; అలాగే `*.googleapis.com` కోసం
స్థానికంగా విశ్వసించిన CA అధిగమించగల స్వంత స్టాటిక్ పిన్లను కలిగి ఉంటుంది). దీనికి అదనంగా,
Node `fetch` మార్గాన్ని `NODE_EXTRA_CA_CERTS` కవర్ చేస్తుంది.

### 3.3 DNS రూటింగ్

మీరు ఇంటర్సెప్ట్ చేయాలనుకునే ప్రతి ఏజెంట్కు, దాని API హోస్ట్(లు) `127.0.0.1`కు రిజాల్వ్ కావాలి. సెటప్ విజార్డ్లో ఒక ఏజెంట్ కోసం DNSను టాగుల్ చేసినప్పుడు AgentBridge `/etc/hosts` ఎంట్రీలను స్వయంచాలకంగా నిర్వహిస్తుంది.

GitHub Copilot కోసం ఉదాహరణ `/etc/hosts` ఎంట్రీలు:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 మోడల్ మ్యాపింగ్

సోర్స్ → టార్గెట్ మ్యాపింగ్లను నిర్వచించడానికి ప్రతి ఏజెంట్ కార్డ్లోని మోడల్ మ్యాపింగ్ పట్టికను ఉపయోగించండి:

| సోర్స్ మోడల్ (ఏజెంట్ స్థానిక మోడల్) | టార్గెట్ మోడల్ (OmniRoute) |
| ----------------------------------- | -------------------------- |
| `gpt-4o`                            | `claude-sonnet-4.7`        |
| `*` (వైల్డ్కార్డ్)                  | `claude-haiku-4.7`         |

వైల్డ్కార్డ్ `*` గుర్తించబడని ఏ మోడల్నైనా పేర్కొన్న టార్గెట్కు మ్యాప్ చేస్తుంది. ఇది `agent_bridge_mappings` పట్టికలో నిల్వ చేయబడుతుంది.

> **చిట్కా — ఏజెంట్ యొక్క వాస్తవ మోడల్ IDలను కనుగొనండి.** ఒక IDE దాని UI లేబుల్లకు భిన్నమైన,
> అలాగే ప్రధాన వెర్షన్ల మధ్య మారే మోడల్ పేర్లను పంపవచ్చు. ఉదాహరణకు, **Antigravity 2** నెట్వర్క్
> ద్వారా `gemini-3.1-pro-low`, `gemini-pro-agent`, మరియు `gemini-3.1-flash-lite`లను పంపుతుంది —
> పాత డాక్యుమెంటేషన్లో చూపిన `gemini-2.5-pro`ను కాదు. సరిపోలే మ్యాపింగ్ లేకుండా ఒక చాట్ను
> పంపండి: MITM సరిగ్గా వచ్చిన `model:`ను లాగ్ చేసి, అభ్యర్థనను యథాతథంగా పంపిస్తుంది. ఆ ఖచ్చితమైన
> విలువను మ్యాప్ చేయండి; ఆ తర్వాతి అభ్యర్థన ఇంటర్సెప్ట్ చేయబడి మీ టార్గెట్కు రూట్ చేయబడుతుంది.

### 3.5 ప్రమాద సూచన

IDE అప్స్ట్రీమ్ ప్రొవైడర్లతో ప్రమాణీకరించడానికి ఉపయోగించే క్రెడెన్షియల్లను (OAuth టోకెన్లు, API కీలు) AgentBridge ఇంటర్సెప్ట్ చేస్తుంది. ఇవి **లాగ్ చేయడానికి ముందు మాస్క్ చేయబడతాయి** (§2.7 చూడండి), కానీ OmniRoute యొక్క MITM లేయర్కు కనిపిస్తాయి. ప్రతి ఏజెంట్ను మొదటిసారి యాక్టివేట్ చేసినప్పుడు మూసివేయగల ప్రమాద సూచన మోడల్ కనిపిస్తుంది.

### 3.6 నిర్వహణ & డయాగ్నస్టిక్స్

గతంలో UI లేని ఆపరేషనల్ MITM రూట్లను చూపించే **నిర్వహణ & డయాగ్నస్టిక్స్** కార్డ్ను (`AgentBridgeMaintenanceCard`, `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`లో) డ్యాష్బోర్డ్ అందిస్తుంది. దాని ఉపశీర్షిక: _"క్యాప్చర్ పైప్లైన్ను స్వయంగా పరీక్షించండి, మిగిలిపోయిన సిస్టమ్ స్థితిని రద్దు చేయండి, అలాగే మీ సెటప్ను మెషీన్ల మధ్య తరలించండి."_ కార్డ్ క్లయింట్ హెల్పర్లు `src/lib/inspector/agentBridgeMaintenanceApi.ts`లో ఉన్నాయి.

| బటన్                        | రూట్                                   | ఇది చేసే పని                                                                                                                                                                                                                  |
| --------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **నిర్ధారించు**             | `GET /api/tools/agent-bridge/diagnose` | క్యాప్చర్-పైప్లైన్ స్వీయ-పరీక్షను అమలు చేసి, ప్రతి తనిఖీకి సంబంధించిన నివేదికను చూపుతుంది (✓/✗ + పరిష్కార సూచన).                                                                                                              |
| **మరమ్మతు**                 | `POST /api/tools/agent-bridge/repair`  | క్రాష్ లేదా SIGKILL కారణంగా మిగిలిపోయిన అనాథ MITM సిస్టమ్ స్థితిని (DNS స్పూఫ్ ఎంట్రీలు, రూట్ CA, సిస్టమ్ ప్రాక్సీ) రద్దు చేస్తుంది. ఐడెంపోటెంట్ — స్థితి శుభ్రంగా ఉన్నప్పుడు "మరమ్మతు చేయడానికి ఏమీ లేదు" అని నివేదిస్తుంది. |
| **CAని తొలగించు**           | `DELETE /api/tools/agent-bridge/cert`  | OS ట్రస్ట్ స్టోర్ నుండి MITM రూట్ CAపై నమ్మకాన్ని తొలగించి, దాన్ని తీసివేస్తుంది (స్పష్టమైన, ఐడెంపోటెంట్ చర్య). CA ప్రస్తుతం విశ్వసించబడుతున్నప్పుడు మాత్రమే చూపబడుతుంది; ఇన్లైన్ "CAని తొలగించాలా?" నిర్ధారణ అవసరం.          |
| **కాన్ఫిగ్ను ఎగుమతి చేయి**  | `GET /api/tools/agent-bridge/config`   | పోర్టబుల్ కాన్ఫిగ్ JSONను డౌన్లోడ్ చేస్తుంది (§3.7 చూడండి).                                                                                                                                                                   |
| **కాన్ఫిగ్ను దిగుమతి చేయి** | `POST /api/tools/agent-bridge/config`  | గతంలో ఎగుమతి చేసిన కాన్ఫిగ్ JSONను అప్లోడ్ చేస్తుంది (§3.7 చూడండి).                                                                                                                                                           |

**డయాగ్నస్టిక్స్ తనిఖీలు** (`src/mitm/inspector/diagnostics.ts`లోని `summarizeDiagnostics()`). రూట్ ప్రతి తనిఖీకి ప్రభావం కలిగించే ప్రోబ్ను అమలు చేసి, బూలియన్ విలువలను స్వచ్ఛమైన సమ్మరైజర్కు అందిస్తుంది; ఒకే `healthy` తీర్పుతో పాటు ప్రతి వైఫల్యానికి ఒక సూచన తిరిగి ఇవ్వబడుతుంది:

| తనిఖీ పేరు         | ఇది ధృవీకరించేది                                                | వైఫల్యం సంభవించినప్పుడు సూచన                                                                                                                                        |
| ------------------ | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | MITM సర్వర్ ప్రాసెస్ సక్రియంగా ఉంది                             | "MITM సర్వర్ అమలులో లేదు. AgentBridge ట్యాబ్ నుండి దాన్ని ప్రారంభించండి."                                                                                           |
| `server-reachable` | MITM సర్వర్ తన పోర్ట్పై కనెక్షన్లను అంగీకరిస్తుంది (TCP ప్రోబ్) | "MITM సర్వర్ తన పోర్ట్పై కనెక్షన్లను అంగీకరించడం లేదు. పోర్ట్ ఖాళీగా ఉందో, దానికి బైండ్ చేయడానికి మీకు అధికారాలు ఉన్నాయో తనిఖీ చేయండి."                             |
| `cert-exists`      | MITM సర్టిఫికేట్ డిస్క్పై జనరేట్ చేయబడింది                      | "ఇంకా MITM సర్టిఫికేట్ ఏదీ జనరేట్ చేయబడలేదు. AgentBridge ట్యాబ్ నుండి ఒకదాన్ని జనరేట్ చేయండి."                                                                      |
| `cert-trusted`     | MITM రూట్ CA OS ట్రస్ట్ స్టోర్లో ఉంది                           | "MITM రూట్ CAను OS స్టోర్ విశ్వసించడం లేదు, కాబట్టి TLS ఇంటర్సెప్షన్ విఫలమవుతుంది. AgentBridge ట్యాబ్ నుండి సర్టిఫికేట్ను విశ్వసించండి."                            |
| `dns-configured`   | లక్ష్య హోస్ట్నేమ్లు `/etc/hosts`లో స్పూఫ్ చేయబడ్డాయి            | "లక్ష్య హోస్ట్నేమ్లు /etc/hostsలో స్పూఫ్ చేయబడలేదు, కాబట్టి ట్రాఫిక్ ప్రాక్సీకి ఎప్పటికీ చేరదు. మీరు క్యాప్చర్ చేయాలనుకుంటున్న ఏజెంట్(ల) కోసం DNSను ప్రారంభించండి." |

**అనాథ స్థితి బ్యానర్:** క్రాష్ కారణంగా మిగిలిపోయిన స్థితిని (DNS స్పూఫ్ / CA / సిస్టమ్ ప్రాక్సీ) పేజీ గుర్తించినప్పుడు, కార్డ్ అంబర్ రంగు బ్యానర్ను చూపుతుంది — _"మునుపటి సెషన్ సిస్టమ్ స్థితిని మిగిల్చింది (DNS స్పూఫ్, CA లేదా సిస్టమ్ ప్రాక్సీ). దాన్ని శుభ్రం చేయడానికి మరమ్మతును అమలు చేయండి."_ — మరియు **మరమ్మతు** బటన్ను హైలైట్ చేస్తుంది. `Repair` అనేది ProxyBridge యొక్క `--cleanup` ఫ్లాగ్కు అప్లికేషన్-లేయర్ సమానమైనది (ఇది `src/mitm/manager.ts`లోని `repairMitm()`కు బాధ్యతను అప్పగిస్తుంది).

> పదేపదే sudo ప్రాంప్ట్లు రాకుండా ఉండటానికి, ఆపు/ప్రారంభించు చర్యల మధ్య MITM రూట్ CA ఇన్స్టాల్గానే ఉంచబడుతుంది
> (mitmproxy/Charles మాదిరిగానే), కాబట్టి దాన్ని తొలగించడం అనేది ఆపినప్పుడు స్వయంచాలకంగా జరిగే ప్రక్రియ కాకుండా
> స్పష్టమైన **CAని తొలగించు** చర్య.

### 3.7 పోర్టబుల్ కాన్ఫిగ్ దిగుమతి/ఎగుమతి

AgentBridge **ఆపరేటర్ సర్దుబాటు చేయగల** స్థితిని వెర్షన్ చేయబడిన JSON బ్లాబ్గా సీరియలైజ్ చేయగలదు, తద్వారా ఒక సెటప్ను అనేక మెషీన్లలో పునరుత్పత్తి చేయవచ్చు. సీరియలైజర్ `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`), ఇది `AgentBridgeConfigSchema` ద్వారా ధృవీకరించబడుతుంది.

ఎగుమతిలో ఖచ్చితంగా మూడు భాగాలు ఉంటాయి (అంతర్నిర్మిత డిఫాల్ట్లు ఉద్దేశపూర్వకంగా **ఎగుమతి చేయబడవు**, కాబట్టి దిగుమతి చేయడం వాటిని ఎప్పుడూ నకలు చేయదు లేదా వాటితో విభేదించదు):

| ఫీల్డ్           | మూలం                                                           | గమనికలు                                                               |
| ---------------- | -------------------------------------------------------------- | --------------------------------------------------------------------- |
| `bypassPatterns` | వినియోగదారు నిర్వచించిన బైపాస్ నమూనాలు (`agent_bridge_bypass`) | డిఫాల్ట్ bank/gov/okta నమూనాలు మినహాయించబడతాయి                        |
| `customHosts`    | Traffic Inspector కస్టమ్ హోస్ట్లు (`inspector_custom_hosts`)   | ప్రతి ఒక్కటి: `{ host, kind: "llm"\|"app"\|"custom", label? }`        |
| `agentMappings`  | ప్రతి ఏజెంట్కు మోడల్ మ్యాపింగ్లు (`agent_bridge_mappings`)     | మ్యాపింగ్లు ఉన్న ప్రతి ఏజెంట్కు `{ [agentId]: [{ source, target }] }` |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**దిగుమతి ప్రవర్తన** (`POST /api/tools/agent-bridge/config`): బైపాస్ నమూనాలు మరియు ప్రతి ఏజెంట్కు సంబంధించిన మ్యాపింగ్లు **పూర్తిగా భర్తీ చేయబడతాయి**; కస్టమ్ హోస్ట్లు **ఐడెంపోటెంట్గా** జోడించబడతాయి (`INSERT OR IGNORE`). ప్రతి రకంలో ఎన్ని వర్తింపజేయబడ్డాయో ప్రతిస్పందన నివేదిస్తుంది:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

కాన్ఫిగ్లో **లేనివి**: సర్వర్ అమలవుతున్న స్థితి, సర్టిఫికేట్ పాత్లు, ప్రతి ఏజెంట్కు సంబంధించిన DNS స్థితి, అప్స్ట్రీమ్ CA పాత్ మరియు TPROXY సెట్టింగ్లు — ఇవి పోర్టబుల్ ప్రాధాన్యతలు కావు, హోస్ట్/రన్టైమ్ స్థితికి సంబంధించినవి.

### సెటప్ విజార్డ్ దశలు (ప్రతి ఏజెంట్కు)

ప్రతి ఏజెంట్ కార్డ్లో 3-దశల సెటప్ విజార్డ్ ఉంటుంది:

1. **ముందస్తు అవసరాలను ధృవీకరించండి** — సర్వర్ నడుస్తోందా? సర్టిఫికేట్ విశ్వసించబడిందా? IDE ఇన్స్టాల్ చేయబడిందా (స్వయంచాలకంగా గుర్తించబడిందా)?
2. **DNSను ప్రారంభించండి** — `/etc/hosts` ఎంట్రీలను జోడిస్తుంది (sudo అవసరం). ఏ లైన్లు జోడించబడతాయో ఖచ్చితంగా చూపిస్తుంది.
3. **మోడల్లను మ్యాప్ చేయండి** — ఐచ్ఛిక మోడల్ మ్యాపింగ్ పట్టిక. వైల్డ్కార్డ్లు ఆమోదించబడతాయి.

### ఏజెంట్ గుర్తింపు

1–8 ఏజెంట్ల కోసం, IDE ఇన్స్టాలేషన్ను స్వయంచాలకంగా గుర్తించడానికి AgentBridge ప్రయత్నిస్తుంది:

```ts
export async function detectAgent(agentId: AgentId): Promise<DetectionResult>;
// తిరిగి ఇస్తుంది: { installed: boolean, version?: string, path?: string }
```

గుర్తింపు OS-నిర్దిష్ట పాత్లు మరియు బైనరీ తనిఖీలను ఉపయోగిస్తుంది (ఉదా., Copilot కోసం `code --list-extensions | grep github.copilot`, Antigravity కోసం `~/.config/antigravity/`).

### సున్నితమైన హోస్ట్ల కోసం బైపాస్ జాబితా

ఆర్థిక సంస్థలు, OAuth/SSO ప్రొవైడర్లు మరియు ఇతర సున్నితమైన హోస్ట్లు **ఎప్పటికీ డీక్రిప్ట్ చేయబడకుండా** బైపాస్ జాబితా నిర్ధారిస్తుంది. వాటి TLS ట్రాఫిక్ పారదర్శక TCP టన్నెల్గా గుండా వెళుతుంది — OmniRoute ఎప్పటికీ ప్లెయిన్టెక్స్ట్ను చూడదు.

డిఫాల్ట్ బైపాస్ నమూనాల్లో ఇవి ఉన్నాయి:

- `*.bank.*`, `*.gov.*` (ఆర్థిక/ప్రభుత్వ)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/గుర్తింపు)
- `*.apple.com`, `*.icloud.com` (Apple సిస్టమ్ సేవలు)

వినియోగదారు జోడించిన బైపాస్ నమూనాలు `agent_bridge_bypass` పట్టికలో నిల్వ చేయబడతాయి మరియు మిగతా అన్నింటికంటే ప్రాధాన్యం పొందుతాయి.

### రహస్యాల మాస్కింగ్

`src/mitm/maskSecrets.ts` నుండి `maskSecrets()` వర్తింపజేయబడుతుంది:

- `TrafficBuffer.push()`కు ముందు ప్రతి అభ్యర్థన బాడీపై
- లాగింగ్ లేదా బ్రాడ్కాస్టింగ్కు ముందు ప్రతి హెడర్పై

నమూనాలు: `sk-`/`ak-`/`pk-` ప్రిఫిక్స్ టోకెన్లు, `Bearer` టోకెన్లు మరియు ≥40 అక్షరాలు ఉన్న సాధారణ టోకెన్లు.

### అప్స్ట్రీమ్ CA సర్టిఫికేట్

`AGENTBRIDGE_UPSTREAM_CA_CERT` సెట్ చేయబడినప్పుడు, ఫైల్ స్టార్టప్ సమయంలో చదవబడుతుంది. పాత్ ఉనికిలో ఉన్నప్పటికీ ఫైల్ చదవలేనిదైతే, AgentBridge స్పష్టమైన లోపాన్ని లాగ్ చేసి ప్రారంభం కావడానికి నిరాకరిస్తుంది (కార్పొరేట్ వాతావరణాల్లో నిశ్శబ్ద TLS వైఫల్యాలను నివారిస్తుంది).

### తెలిసిన పరిమితులు

- **పోర్ట్ 443కు ప్రత్యేకాధికారం అవసరం**: Linuxలో, AgentBridgeకు Node బైనరీపై `setcap 'cap_net_bind_service=+ep'` అవసరం లేదా `authbind` ద్వారా నడపాలి. సెటప్ విజార్డ్ OS-నిర్దిష్ట సూచనలను ప్రదర్శిస్తుంది.
- **IDE పునఃప్రారంభం అవసరం**: DNS రీడైరెక్ట్ తర్వాత, కొత్త హోస్ట్ రిజల్యూషన్ అమల్లోకి రావడానికి IDEని పునఃప్రారంభించాలి.
- **హార్డ్కోడ్ చేసిన OAuth టోకెన్లు**: కొన్ని ఏజెంట్లు (Kiro, Antigravity) OAuth రిఫ్రెష్ టోకెన్లను స్థానికంగా నిల్వ చేస్తాయి. ఇవి AgentBridgeకు పారదర్శకంగా ఉంటాయి — ప్రతి అభ్యర్థనలోని Bearer టోకెన్ను ఇది చూస్తుంది, లాగింగ్కు ముందు అది మాస్క్ చేయబడుతుంది.
- **Electron ఫ్రంట్ఎండ్లకు `NODE_EXTRA_CA_CERTS` అవసరం**: బండిల్ చేయబడిన Node/Electron రన్టైమ్పై ఫ్రంట్ఎండ్ నడిచే IDEలు OS/NSS ట్రస్ట్ స్టోర్ను విస్మరిస్తాయి మరియు `NODE_EXTRA_CA_CERTS` సెట్ చేసిన షెల్ నుండి ప్రారంభించాలి (§3.2 చూడండి). ఇది లేకపోతే కనిపించే లక్షణం: IDE బ్యాక్ఎండ్ ప్రామాణీకరిస్తుంది (MITMలో `200`లు కనిపిస్తాయి), కానీ UI లాగ్ అవుట్ స్థితిలోనే ఉంటుంది.
- **ఒకే IDE యొక్క బహుళ ఇన్స్టాలేషన్లు స్వతంత్రంగా ఉంటాయి**: సిస్టమ్ ఇన్స్టాలేషన్ (ఉదా. `/usr/share/antigravity/antigravity`) మరియు వినియోగదారు-స్థానిక "Full" ఇన్స్టాలేషన్ (ఉదా. `~/AntigravityIDE_Full/antigravity-ide`) వాటి స్వంత రన్టైమ్లతో వేర్వేరు ప్రాసెస్లు — ప్రతి దానినీ CA ఇంజెక్ట్ చేసి మళ్లీ ప్రారంభించాలి. మళ్లీ ప్రారంభించే ముందు ఏది నడుస్తోందో దాని బైనరీ పాత్ ద్వారా గుర్తించండి.
- **గుర్తింపును రూట్ చేసిన మోడల్ కాకుండా ఏజెంట్ సిస్టమ్ ప్రాంప్ట్ సెట్ చేస్తుంది**: మీరు ఏజెంట్ మోడల్ను వేరే ప్రొవైడర్కు రీమ్యాప్ చేసినప్పుడు కూడా, ప్రత్యుత్తరం ఏజెంట్ స్థానిక గుర్తింపునే పేర్కొంటుంది (ఉదా. Antigravity "I am powered by Gemini" అని సమాధానం ఇస్తుంది), ఎందుకంటే IDE దాన్ని సిస్టమ్ ప్రాంప్ట్లోకి ఇంజెక్ట్ చేస్తుంది. మోడల్ను అది ఎవరో అడగడం ద్వారా కాకుండా, `call_logs` / `proxy_logs`లో (`provider`, `model`, `target_format`) వాస్తవ బ్యాక్ఎండ్ను నిర్ధారించండి.

## §6 సమస్య పరిష్కారం

### Port 443 సంఘర్షణ

మరొక process ఇప్పటికే port 443పై వింటుంటే (web server, VPN మొదలైనవి):

```bash
lsof -i :443          # processను కనుగొనండి
sudo fuser -k 443/tcp  # బలవంతంగా నిలిపివేయండి (జాగ్రత్తగా ఉపయోగించండి)
```

ప్రత్యామ్నాయంగా, AgentBridge settingsలో non-privileged portను configure చేసి, `iptables` / `pf` redirect rulesను ఏర్పాటు చేయండి.

### Certificate విశ్వసనీయంగా లేదు

AgentBridgeను ప్రారంభించిన తర్వాత IDEలో TLS errors కనిపిస్తే:

1. cert install అయిందో లేదో ధృవీకరించండి: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) లేదా `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. కొన్ని apps తమ స్వంత trust storeను నిర్వహిస్తాయి (Firefox, Linuxలో Chrome). "Trust Cert"ను మళ్లీ అమలు చేసి, NSS/Firefoxకు ప్రత్యేకమైన cert storeను తనిఖీ చేయండి.
3. విశ్వసనీయంగా గుర్తించిన తర్వాత IDEని restart చేయండి — ప్రస్తుతం కొనసాగుతున్న TLS sessions పాత trust stateను ఉపయోగిస్తాయి.

### విశ్వసనీయ CA ఉన్నప్పటికీ IDE నుంచి logout కావడం / "connection error"

లక్షణం: DNSను redirect చేసి, CAను విశ్వసనీయంగా గుర్తించిన తర్వాత, Electron-ఆధారిత IDE (ఉదా. Antigravity)
**logged out** స్థితిలో తెరుచుకుంటుంది లేదా authentication/connection errorను చూపుతుంది, అయినప్పటికీ MITM logలో
bootstrap calls (`loadCodeAssist`, `fetchAvailableModels`, …) `200`ను తిరిగి ఇస్తున్నట్లు కనిపిస్తుంది.

కారణం: IDE యొక్క **bundled Node/Electron runtime OS trust storeను విస్మరిస్తుంది**. స్థానిక
backend (ఒక Go language server) OS CAను విశ్వసించి authenticate అవుతుంది, కానీ Electron frontend
అలా చేయదు — అందువల్ల UI తాను offlineలో ఉన్నట్లు భావిస్తుంది.

పరిష్కారం (రెండు దశలూ): `NODE_EXTRA_CA_CERTS=<ca.crt>`ను export చేసి, desktop icon నుంచి కాకుండా **అదే
shell నుంచి IDEని మళ్లీ ప్రారంభించండి**. ముందుగా IDEని పూర్తిగా quit చేయండి — Electron యొక్క singleton lock కారణంగా
రెండోసారి launch చేస్తే ఇప్పటికే ఉన్న process మాత్రమే focus అవుతుంది, కొత్త environment విస్మరించబడుతుంది. §3.2 చూడండి.
స్వతంత్ర agent ఒక MITM ద్వారా పనిచేసినా, అదే setupలో IDE
variant విఫలమవుతున్నట్లు తెలిపిన upstreamలోని open reportకు ఇది సరిపోలుతుంది.

### DNS propagate కాలేదు

`/etc/hosts` update అయిందో లేదో తనిఖీ చేయండి:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

DNS cacheను flush చేయండి:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE గుర్తించబడలేదు

Auto-detection సాధారణ installation pathsను ఉపయోగిస్తుంది. IDE install అయి ఉన్నప్పటికీ detection విఫలమైతే:

- IDE binary ప్రామాణికం కాని locationలో ఉందో లేదో తనిఖీ చేయండి
- Setup Wizard ఇప్పటికీ పనిచేస్తుంది — detection failure అంటే badgeలో install path కనిపించదని మాత్రమే అర్థం

### Handler errors (upstream fetch విఫలమవుతుంది)

AgentBridge intercept చేస్తున్నప్పటికీ అన్ని requests విఫలమైతే:

1. `/dashboard/providers`లో కనీసం ఒక provider connect అయి ఉందని ధృవీకరించండి
2. OmniRoute server logsను తనిఖీ చేయండి: `.env`లో `APP_LOG_LEVEL=debug`
3. `OMNIROUTE_BASE_URL` సరైన router endpointను సూచిస్తోందని ధృవీకరించండి (default: `http://127.0.0.1:20128`)

## §8 రోడ్మ్యాప్

### Trae పరిశోధన

Trae సాపేక్షంగా కొత్త AI కోడింగ్ సహాయకం. హ్యాండ్లర్ను అమలు చేయడానికి ముందు:

1. VS Code / JetBrains మార్కెట్ప్లేస్లలో లేదా స్వతంత్ర యాప్గా బైనరీ/ఎక్స్టెన్షన్ను గుర్తించండి
2. API హోస్ట్లు మరియు ఎండ్పాయింట్ నిర్మాణాలను కనుగొనడానికి mitmproxyతో ట్రాఫిక్ను క్యాప్చర్ చేయండి
3. ప్రమాణీకరణ విధానాన్ని నిర్ధారించండి
4. TOS మరియు API కనుగొనగల సామర్థ్యం ఆధారంగా కొనసాగించాలా వద్దా అనేది అంచనా వేయండి

పరిశోధన పూర్తయ్యే వరకు, డ్యాష్బోర్డ్లోని Trae కార్డ్ "Investigating" బ్యాడ్జ్తో పాటు "Report viability" లింక్ను చూపుతుంది. `src/mitm/handlers/trae.ts` వద్ద ఉన్న హ్యాండ్లర్ స్టబ్ నిర్మాణాత్మకమైన `Not yet implemented` ఎర్రర్ను విసురుతుంది.

### బ్యాక్లాగ్ ఏజెంట్లు (MITM అవసరం — కస్టమ్ బేస్ URL మద్దతు లేదు)

క్రింది సాధనాలు వాటి ప్రస్తుత వెర్షన్లలో కస్టమ్ బేస్ URLలకు మద్దతు ఇవ్వవు, అందువల్ల MITM మాత్రమే ఇంటర్సెప్షన్ మార్గంగా ఉంది. సాధ్యత అంచనా ఇంకా పెండింగ్లో ఉంది:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — Kiro IDEకి వేరు)
- **Cowork** (Anthropic డెస్క్టాప్)

గమనిక: GitHub Copilot CLI ≥v1.0.19 `COPILOT_PROVIDER_BASE_URL`కు మద్దతు ఇస్తుంది — ఆ సాధనం కోసం MITMకు బదులుగా నేరుగా కాన్ఫిగరేషన్ను ఉపయోగించండి.
