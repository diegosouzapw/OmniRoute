Traffic Inspector అనేది OmniRouteలో అంతర్నిర్మిత HTTPS ట్రాఫిక్ డీబగ్గర్ — ఇది Charles Proxy / mitmweb / HTTP Toolkit లాంటి సాధనం, అలాగే **LLM-అవేర్** మరియు **ఏజెంట్-అవేర్**. ఇది `/dashboard/tools/traffic-inspector` వద్ద అందుబాటులో ఉంటుంది మరియు ఏకకాలంలో గరిష్ఠంగా 5 క్యాప్చర్ మూలాల నుండి ప్రత్యక్ష ట్రాఫిక్ను స్వీకరిస్తుంది.

**డ్యాష్బోర్డ్ స్థానం:** `/dashboard/tools/traffic-inspector`
**సైడ్బార్ సమూహం:** సాధనాలు (AgentBridge తర్వాత)
**ఇవి కూడా చూడండి:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge అనేది క్యాప్చర్ మోడ్ 1.

### ఒక పేరాలో ఆర్కిటెక్చర్

`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) అనేది పంచుకోబడిన ఇన్-మెమరీ రింగ్ బఫర్ (డిఫాల్ట్గా 1000 ఎంట్రీలు, `INSPECTOR_BUFFER_SIZE` ద్వారా కాన్ఫిగర్ చేయవచ్చు). అన్ని క్యాప్చర్ మూలాలు `push()` ద్వారా దీనిలో వ్రాస్తాయి. బఫర్ `kindDetector.ts` ఉపయోగించి ప్రతి ఎంట్రీని వర్గీకరిస్తుంది (అది LLM అభ్యర్థనా కాదా అని నిర్ణయిస్తుంది), `contextKey`ను (సిస్టమ్ ప్రాంప్ట్కు సంబంధించిన SHA-256 ఫింగర్ప్రింట్) గణిస్తుంది, అలాగే `globalTrafficBuffer.subscribe()` ద్వారా WebSocket సబ్స్క్రైబర్లందరికీ ప్రసారం చేస్తుంది. డ్యాష్బోర్డ్ `GET /api/tools/traffic-inspector/ws` ద్వారా కనెక్ట్ అవుతుంది మరియు కనెక్ట్ అయినప్పుడు ఒక స్నాప్షాట్ను స్వీకరిస్తుంది; ఆ తర్వాత `new`/`update`/`clear` ఈవెంట్లను స్వీకరిస్తుంది.

## §2 క్యాప్చర్ మోడ్లు

Traffic Inspector **5 ఏకకాలిక క్యాప్చర్ మూలాలకు** మద్దతు ఇస్తుంది. ప్రతి దానిని స్వతంత్రంగా ఆన్ లేదా ఆఫ్ చేయవచ్చు. ప్రతి `InterceptedRequest` (`src/mitm/inspector/types.ts`) లోని `source` ఫీల్డ్ `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"`, లేదా `"tproxy"` లలో ఒకటిగా ఉంటుంది.

### మోడ్ 1 — AgentBridge (డిఫాల్ట్, ఎల్లప్పుడూ ఆన్లో ఉంటుంది)

**మూలం:** AgentBridge హ్యాండ్లర్లు (`src/mitm/handlers/base.ts`)
**విధానం:** `MitmHandlerBase` లోని ప్రతి `intercept()` కాల్, ఫార్వర్డ్ చేయడానికి ముందు `hookBufferStart()` ను, పూర్తయిన తర్వాత `hookBufferUpdate()` ను కాల్ చేస్తుంది. అదనపు కాన్ఫిగరేషన్ ఏదీ అవసరం లేదు — AgentBridge రన్ కావడం ప్రారంభించిన వెంటనే పనిచేస్తుంది.
**పరిధి:** AgentBridge లో కాన్ఫిగర్ చేసిన 9 IDE ఏజెంట్లు
**గమనిక:** `InterceptedRequest` లోని `source` ఫీల్డ్ = `"agent-bridge"`

### మోడ్ 2 — కస్టమ్ హోస్ట్లు (DNS రీడైరెక్ట్)

**మూలం:** వినియోగదారు నిర్వచించిన హోస్ట్ జాబితా (`inspector_custom_hosts` టేబుల్)
**విధానం:** UI ద్వారా ఒక హోస్ట్ను జోడించినప్పుడు, `/etc/hosts` కు `127.0.0.1 <host>` జోడించబడుతుంది (sudo అవసరం). ఇప్పటికే ఉన్న AgentBridge MITM సర్వర్ (పోర్ట్ 443), కొత్త హోస్ట్ కోసం SNI సర్టిఫికెట్ను డైనమిక్గా రూపొందిస్తుంది.
**పరిధి:** జోడించిన హోస్ట్ను ఉపయోగించే ఏ అప్లికేషన్ అయినా — యాప్ కాన్ఫిగరేషన్ను మార్చాల్సిన అవసరం లేదు
**గమనిక:** `source` = `"custom-host"`

ఉదాహరణ వినియోగ సందర్భాలు:

- Python స్క్రిప్ట్ల నుండి `api.openai.com` ను పర్యవేక్షించడం
- `my-internal-llm.company.com` ను డీబగ్ చేయడం
- అదే నెట్వర్క్లోని మొబైల్ పరికరాల ట్రాఫిక్ను క్యాప్చర్ చేయడం (ARP స్పూఫింగ్ ద్వారా — అధునాతనం)

### మోడ్ 3 — HTTP_PROXY లిసనర్ (పోర్ట్ 8080)

**మూలం:** `HTTP_PROXY`/`HTTPS_PROXY` ఎన్విరాన్మెంట్ వేరియబుల్స్ను ఉపయోగించే అప్లికేషన్లు
**విధానం:** ప్రామాణిక స్పష్టమైన HTTP/HTTPS ప్రాక్సీగా పనిచేసే పోర్ట్ 8080 వద్ద సెకండరీ లిసనర్ (`src/mitm/inspector/httpProxyServer.ts`). ఇది `CONNECT` టన్నెల్స్ను (HTTPS), అలాగే నేరుగా వచ్చే HTTP రిక్వెస్ట్లను స్వీకరిస్తుంది.
**పరిధి:** `HTTP_PROXY` ఎన్విరాన్మెంట్ వేరియబుల్ను గౌరవించే ఏ అప్లికేషన్ అయినా — DNS మార్పు లేదా sudo అవసరం లేదు
**గమనిక:** `source` = `"http-proxy"`

```bash
# ఒక్క కమాండ్ కోసం త్వరిత క్యాప్చర్:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# షెల్ సెషన్లో నిరంతర క్యాప్చర్:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**TLS పరిమితి:** HTTPS `CONNECT` టన్నెల్స్ డిఫాల్ట్గా మెటాడేటా రూపంలో మాత్రమే క్యాప్చర్ చేయబడతాయి (హోస్ట్, పోర్ట్, సమయం) — TLS బాడీ డీక్రిప్ట్ చేయబడదు. పూర్తి బాడీని తనిఖీ చేయడానికి "Decrypt HTTPS in proxy mode" టాగుల్ను ప్రారంభించండి (ఇది ఆప్ట్-ఇన్; AgentBridge సర్టిఫికెట్ విశ్వసించబడటం అవసరం).

**పోర్ట్ వైరుధ్యం:** పోర్ట్ 8080 ఇప్పటికే వినియోగంలో ఉంటే, AgentBridge నిర్మిత ఎర్రర్తో 409 ను రిటర్న్ చేస్తుంది. `INSPECTOR_HTTP_PROXY_PORT` ఎన్విరాన్మెంట్ వేరియబుల్ ద్వారా పోర్ట్ను మార్చండి.

### మోడ్ 4 — సిస్టమ్-వ్యాప్త ప్రాక్సీ (అధునాతనం, ఆప్ట్-ఇన్)

**మూలం:** OS-స్థాయి ప్రాక్సీ సెట్టింగ్లు (మెషీన్లోని అన్ని యాప్లకు వర్తిస్తాయి)
**విధానం:** మొత్తం HTTP/HTTPS ట్రాఫిక్ను HTTP_PROXY లిసనర్ ద్వారా రీడైరెక్ట్ చేయడానికి OS APIలను ఉపయోగిస్తుంది:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **పరిధి:** సిస్టమ్ ప్రాక్సీ సెట్టింగ్లను గౌరవించే, మెషీన్లోని ప్రతి అప్లికేషన్
  **గమనిక:** `source` = `"system-proxy"`

**భద్రతా విధానాలు:**

- ఆటో-డిసేబుల్ టైమర్ (డిఫాల్ట్గా 30 నిమిషాలు; `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES` ద్వారా కాన్ఫిగర్ చేయవచ్చు)
- మునుపటి సిస్టమ్ ప్రాక్సీ స్థితి DBలో సేవ్ చేయబడి, రివర్ట్ చేసినప్పుడు పునరుద్ధరించబడుతుంది
- సక్రియంగా ఉన్న సమయంలో వినియోగదారు వేరే పేజీకి వెళ్లినట్లయితే, డ్యాష్బోర్డ్ "Reverting system proxy" ప్రాంప్ట్ను చూపుతుంది
- UIలో `⚠ Advanced` బ్యాడ్జ్తో పాటు స్పష్టమైన నిర్ధారణ చెక్బాక్స్ కనిపిస్తుంది

### మోడ్ 5 — TPROXY పారదర్శక డీక్రిప్షన్ (Linux, root, ఆప్ట్-ఇన్)

**మూలం:** Kernel TPROXY + పాలసీ రూటింగ్ (`src/mitm/tproxy/`)
**విధానం:** `mangle OUTPUT` లో లక్ష్య పోర్ట్కు (డిఫాల్ట్ `443`) వెళ్లే కొత్త లోకల్ అవుట్బౌండ్ TCP కనెక్షన్లను మార్క్ చేస్తుంది; ఒక `ip rule` మార్క్ చేసిన ప్యాకెట్లను లోకల్ డెలివరీకి తిరిగి రూట్ చేస్తుంది; అలాగే `mangle PREROUTING` లోని `TPROXY` టార్గెట్ వాటిని పారదర్శక (**IP_TRANSPARENT**) లిసనర్కు (డిఫాల్ట్ పోర్ట్ `8443`) అప్పగిస్తుంది. లిసనర్, డైనమిక్ CA ద్వారా **అవసరమైనప్పుడు ప్రతి SNI హోస్ట్నేమ్కు విడిగా** జారీ చేయబడిన లీఫ్ సర్టిఫికెట్తో TLSను ముగిస్తుంది, డీక్రిప్ట్ చేసిన ఎక్స్చేంజ్ను క్యాప్చర్ చేస్తుంది, అనంతరం రిక్వెస్ట్ను మళ్లీ ఎన్క్రిప్ట్ చేసి అసలు గమ్యస్థానానికి ఫార్వర్డ్ చేస్తుంది.
**పరిధి:** లక్ష్య పోర్ట్లోని **ఏవైనా** డెస్టినేషన్ హోస్ట్లు — `/etc/hosts` స్పూఫ్, `HTTP_PROXY` ఎన్విరాన్మెంట్ వేరియబుల్, లేదా సిస్టమ్-వ్యాప్త ప్రాక్సీ మార్పు అవసరం లేదు. ఇంటర్సెప్ట్ చేయబడే ప్రాసెస్కు కాన్ఫిగరేషన్ మార్పు అవసరం లేదు, కానీ అది డైనమిక్ CAను విశ్వసించాలి.
**గమనిక:** `source` = `"tproxy"`

**అవసరాలు:** Linux మాత్రమే (**IP_TRANSPARENT** Linuxలో మాత్రమే అందుబాటులో ఉంటుంది), **CAP_NET_ADMIN** సామర్థ్యం (root), అలాగే C టూల్చైన్తో బిల్డ్ చేయాల్సిన నేటివ్ N-API యాడ్ఆన్ (`npm run build:native:tproxy`). ఇది అందుబాటులో లేనప్పుడు, "TPROXY decrypt requires Linux + root + the native addon" టూల్టిప్తో డ్యాష్బోర్డ్ టాగుల్ డిసేబుల్ చేయబడుతుంది. ఫైర్వాల్ నియమాలు లావాదేవీ పద్ధతిలో వర్తింపజేయబడతాయి/రివర్ట్ చేయబడతాయి (క్రాష్ జరిగినా `mangle` నియమం మిగిలిపోదు), అలాగే రీబూట్ సమయంలో ఫ్లష్ చేయబడతాయి. SO_MARK-ఆధారిత యాంటీ-లూప్, ప్రాక్సీ స్వయంగా మళ్లీ ఎన్క్రిప్ట్ చేసి ఫార్వర్డ్ చేసిన ట్రాఫిక్ తిరిగి ఇంటర్సెప్ట్ కాకుండా నిరోధిస్తుంది.

ఇది దానికే ప్రత్యేకమైన ఆపరేటర్ గైడ్ను కలిగిన విస్తృతమైన సబ్సిస్టమ్ — పూర్తి ఫైర్వాల్ విధానం, ప్రతి-SNI డైనమిక్ CA + ట్రస్ట్-స్టోర్ ఇన్స్టాలర్, లోకల్-మాత్రమే రూట్, యాంటీ-లూప్ వివరాలు మరియు కాన్ఫిగరేషన్ స్కీమా కోసం `docs/security/MITM-TPROXY-DECRYPT.md` ను చూడండి (gitలో ఉంది; `/docs` లోకి కంపైల్ చేయబడదు). టాగుల్ `GET / POST / DELETE /api/tools/agent-bridge/tproxy` ద్వారా నియంత్రించబడుతుంది (గమనిక: ఈ రూట్ Traffic Inspector ప్రిఫిక్స్ కింద కాకుండా AgentBridge ప్రిఫిక్స్ కింద ఉంటుంది).

## §4 LLM-అవగాహన గల ఫీచర్లు

### 4.1 రకం గుర్తింపు సాధనం (`src/mitm/inspector/kindDetector.ts`)

4 సంకేతాలను ఉపయోగించి ప్రతి అభ్యర్థనను `"llm"`, `"app"` లేదా `"unknown"`గా వర్గీకరిస్తుంది:

1. **హోస్ట్ రిజిస్ట్రీ** — సుమారు 18 ప్రసిద్ధ LLM API హోస్ట్నేమ్లు (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot మొదలైనవి)
2. **పాత్ నమూనాలు** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses` మొదలైనవి
3. **బాడీ ఆకృతి** — `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input` ఫీల్డ్లను గుర్తిస్తుంది
4. **యూజర్-ఏజెంట్ సూచనలు** — UA స్ట్రింగ్లో `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor`

Mode 2 ద్వారా జోడించిన అనుకూల హోస్ట్లు, ఫారమ్ ఇన్పుట్ నుండి వాటి `kind`ను స్వీకరిస్తాయి (డిఫాల్ట్గా `"custom"`).

### 4.2 SSE విలీన సాధనం (`src/mitm/inspector/sseMerger.ts`)

**స్వతంత్ర క్లీన్-రూమ్ అమలు.** ఈవెంట్ పార్సింగ్
[WHATWG సర్వర్-సెంట్ ఈవెంట్స్ అల్గారిథమ్](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)ను అనుసరిస్తుంది,
కాగా పునర్నిర్మాణం పబ్లిక్ [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming), మరియు
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent)
స్ట్రీమింగ్ స్కీమాలను అనుసరిస్తుంది.

ముడి SSE డెల్టా ఈవెంట్ల నుండి తుది అసిస్టెంట్ సందేశాన్ని పునర్నిర్మిస్తుంది:

- **Anthropic**: ఇండెక్స్ ఆధారంగా `content_block_delta`ను పోగుచేస్తుంది; `text_delta`, `input_json_delta` (టూల్ కాల్స్), `thinking_delta`లను నిర్వహిస్తుంది
- **OpenAI**: Chat Completions ఎంపికలు/టూల్ కాల్స్ మరియు Responses API అవుట్పుట్ అంశాలను ఇండెక్స్ ఆధారంగా పోగుచేస్తుంది
- **Gemini**: `candidates[i].content.parts`ను పోగుచేస్తుంది
- **తెలియనిది**: ముడి ఈవెంట్లను యథాతథంగా తిరిగి ఇస్తుంది

Response ట్యాబ్ ఒక టాగుల్ను చూపుతుంది: **"ముడి ఈవెంట్లు ↔ విలీనం చేసినవి"**.

### 4.3 సంభాషణ సాధారణీకరణ సాధనం (`src/mitm/inspector/conversationNormalizer.ts`)

**స్వతంత్ర క్లీన్-రూమ్ అమలు.** సాధారణీకరణ స్థానిక బ్లాక్-బాక్స్
కాంట్రాక్ట్లు మరియు పబ్లిక్ OpenAI, Anthropic, Gemini సందేశ స్కీమాల ద్వారా నిర్వచించబడింది; ఎటువంటి అప్స్ట్రీమ్
అమలు సోర్స్ ఉపయోగించబడలేదు.

రెండరింగ్కు ముందు OpenAI, Anthropic మరియు Gemini సందేశ ఫార్మాట్లను ఒకే `NormalizedConversation`గా మారుస్తుంది:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // అభ్యర్థన బాడీ నుండి messages / contents / prompt
  response: NormalizedTurn[]; // అసిస్టెంట్ ప్రతిస్పందన (sseMerger ద్వారా విలీనం చేయబడింది)
  contextKey: string | null; // SHA-256 సిస్టమ్-ప్రాంప్ట్ ఫింగర్ప్రింట్
}
```

బ్లాక్ రకాలు: `text`, `tool_use`, `tool_result`. ప్రొవైడర్తో సంబంధం లేకుండా Conversation ట్యాబ్ ఈ ఆకృతినే ఉపయోగిస్తుంది.

### 4.4 కాంటెక్స్ట్ కీ రంగుల కేటాయింపు (`src/mitm/inspector/contextKey.ts`)

- సిస్టమ్ ప్రాంప్ట్కు `SHA-256`ను గణిస్తుంది (మొదటి `role:system` సందేశం, లేదా `system` ఫీల్డ్, లేదా Gemini `systemInstruction`)
- 12-అక్షరాల హెక్స్ ప్రిఫిక్స్ను (`"a3f9c2..."`) తిరిగి ఇస్తుంది
- ఎడమ-అంచు బార్ కోసం ఫ్రంట్ఎండ్ కీని నిర్ణీత HSL రంగుకు మ్యాప్ చేస్తుంది
- **"అదే కాంటెక్స్ట్" ఫిల్టర్**: `ctx #a3f` చిప్ను క్లిక్ చేస్తే అదే ఫింగర్ప్రింట్ ఉన్న అభ్యర్థనలను మాత్రమే చూపించడానికి ఒక ఫిల్టర్ జోడించబడుతుంది

ఇది ఒకే ఏజెంట్ సెషన్లో నడుస్తున్న విభిన్న "వ్యక్తిత్వాలు" లేదా టాస్క్లను దృశ్యపరంగా సులభంగా వేరు చేయడానికి సహాయపడుతుంది.

### 4.5 LLM మెటాడేటా వెలికితీత

LLM అభ్యర్థనల కోసం, LLM Details ట్యాబ్ కింది వాటిని వెలికితీస్తుంది:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // అభ్యర్థన బాడీ లేదా ప్రతిస్పందన నుండి
  messages: number; // టర్న్ల సంఖ్య
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // SSE ప్రతిస్పందన అయితే true
  mappedTo: string | null; // x-omniroute-mapped హెడర్
  costEstimateUsd: number | null; // OmniRoute ధరల ఆధారంగా అంచనా వ్యయం
}
```

### 4.6 ప్రత్యక్ష ప్రాసెసింగ్లో ఉన్న అభ్యర్థనల ఫిల్టర్

అభ్యర్థన `status` ఫీల్డ్ `number | "in-flight" | "error"` — అభ్యర్థన ప్రారంభమైన వెంటనే ఒక ఎంట్రీ
`"in-flight"`గా జోడించబడుతుంది మరియు ప్రతిస్పందన (లేదా లోపం) వచ్చినప్పుడు **అదే స్థానంలో నవీకరించబడుతుంది**.
టూల్బార్లోని **"ప్రత్యక్షం"** టాగుల్
(`liveOnly`, i18n కీ `trafficInspector.liveOnly`) జాబితాను `status === "in-flight"`గా ఉన్న ఎంట్రీలకు
పరిమితం చేస్తుంది, తద్వారా మీరు తెరిచి ఉన్న కనెక్షన్లను నిజ సమయంలో పర్యవేక్షించవచ్చు.

ఈ ఫిల్టర్
`src/lib/inspector/matchesTrafficFilter.ts`లోని పూర్తిగా క్లయింట్-సైడ్ ప్రెడికేట్:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

టాగుల్ స్థితి `useTrafficFilters`లో (ఇన్స్పెక్టర్ డ్యాష్బోర్డ్ హుక్స్) ఉంటుంది మరియు
ఇతర ఫిల్టర్లతో (ప్రొఫైల్, హోస్ట్, ఏజెంట్, సోర్స్, స్టేటస్, కాంటెక్స్ట్) కలసి పనిచేస్తుంది.

### 4.7 ప్రాసెస్ ఆపాదన (Linux)

Linuxలో, అడ్డగించిన ప్రతి అభ్యర్థనను **దాన్ని ప్రారంభించిన స్థానిక
ప్రాసెస్**కు ఆపాదించవచ్చు. `InterceptedRequest`కు రెండు ఐచ్ఛిక ఫీల్డ్లు జోడించబడ్డాయి:

```ts
pid?: number;          // ప్రారంభించిన ప్రాసెస్ ఐడి (Linuxలో మాత్రమే)
processName?: string;  // ప్రారంభించిన ప్రాసెస్ పేరు (Linuxలో మాత్రమే)
```

`src/mitm/inspector/processAttribution.ts`, కనెక్షన్ యొక్క _క్లయింట్_
ఎఫెమరల్ పోర్ట్ను PID + పేరుకు ఇలా మ్యాప్ చేస్తుంది:

1. పోర్ట్కు సంబంధించిన సాకెట్ ఇనోడ్ను కనుగొనడానికి
   `/proc/net/tcp` మరియు `/proc/net/tcp6`ను చదవడం (`parseProcNetTcpForInode`, పూర్తిగా ఫిక్చర్-పరీక్షించగల పార్సర్).
2. `socket:[<inode>]`కు సిమ్లింక్ కోసం `/proc/<pid>/fd/`ను స్కాన్ చేయడం.
3. `/proc/<pid>/comm` నుండి ప్రాసెస్ పేరును చదవడం.

1-సెకను TTL క్యాష్, లోడ్లో procfs స్కాన్ వ్యయాన్ని పరిమితం చేస్తుంది. ఆపాదన
**సాధ్యమైనంత మేరకు మాత్రమే** జరుగుతుంది — ఏదైనా వైఫల్యం `null`గా పరిష్కరించబడుతుంది మరియు క్యాప్చర్ను ఎప్పుడూ నిరోధించదు.
macOS/Windowsలో ఫంక్షన్ `null`ను తిరిగి ఇస్తుంది (స్టబ్; `lsof`/`GetExtendedTcpTable`
మద్దతు తదుపరి పనిగా ఉంటుంది).

## §5 సెషన్లు

### 5.1 సెషన్ను రికార్డ్ చేయడం

1. టూల్బార్లోని **"● సెషన్ను రికార్డ్ చేయండి"**పై క్లిక్ చేయండి → పేరును నమోదు చేయండి (ఐచ్ఛికం)
2. లైవ్ టెయిల్ సాధారణంగా కొనసాగుతుంది; ఎరుపు రంగులో పల్స్ అయ్యే సూచిక `◉ REC · <name> · 00:42 · 23 అభ్యర్థనలు` అని చూపిస్తుంది
3. **"⏹ ఆపివేయండి"**పై క్లిక్ చేయండి → సెషన్ స్నాప్షాట్ `inspector_sessions` + `inspector_session_requests`లో సేవ్ చేయబడుతుంది

### 5.2 రికార్డ్ చేసిన సెషన్ను వీక్షించడం

టూల్బార్లోని **సెషన్లు** డ్రాప్డౌన్ సేవ్ చేసిన సెషన్లను జాబితా చేస్తుంది. ఒకదాన్ని ఎంచుకున్నప్పుడు:

- సెషన్ స్నాప్షాట్ను లోడ్ చేస్తుంది (స్తంభింపజేసిన స్థితి)
- ఒక బ్యానర్ ఇలా చూపిస్తుంది: `రికార్డ్ చేసిన సెషన్ "<name>"ను వీక్షిస్తున్నారు — [లైవ్కు తిరిగి వెళ్లండి]`
- Recharts సమగ్ర గణాంకాలతో Stats ట్యాబ్ అందుబాటులోకి వస్తుంది

| **HAR** (HTTP Archive 1.2) | Chrome DevTools, Charles, Fiddlerతో అనుకూలం — ఆఫ్లైన్ విశ్లేషణ కోసం దిగుమతి చేసుకోండి |
| **JSONL**                  | ప్రతి పంక్తికి ఒక `InterceptedRequest` — `llm-interceptor` ఫార్మాట్తో అనుకూలం         |

`GET /api/tools/traffic-inspector/sessions/{id}/export.har` ద్వారా లేదా సెషన్లు డ్రాప్డౌన్లోని ⬇ బటన్ ద్వారా ఎగుమతి చేయండి.

## §6 భద్రత

Traffic Inspector, ఆథరైజేషన్ హెడర్లు మరియు అభ్యర్థన బాడీలతో సహా, **అడ్డగించిన మొత్తం HTTPS ట్రాఫిక్ను** చూపిస్తుంది. కింది నియంత్రణలు అమలులో ఉన్నాయి:

| నియంత్రణ                   | వివరాలు                                                                                                                                                                               |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LOCAL_ONLY**             | అన్ని రూట్లు మరియు WebSocket ఎండ్పాయింట్ లూప్బ్యాక్కు మాత్రమే పరిమితం చేయబడ్డాయి (ఆథెంటికేషన్కు ముందు `routeGuard.ts`లో అమలు చేయబడుతుంది)                                             |
| **రహస్యాల మాస్కింగ్**      | లీనియర్ `maskSecret()` స్కానర్, `TrafficBuffer.push()`కు ముందు RFC 6750 Bearer క్రెడెన్షియల్లు, ప్రొవైడర్-ప్రిఫిక్స్డ్ కీలు మరియు పొడవైన అస్పష్ట టోకెన్లను తొలగిస్తుంది               |
| **బాడీ పరిమాణ పరిమితి**    | `INSPECTOR_MAX_BODY_KB` కంటే పెద్ద బాడీలు (డిఫాల్ట్ 1024 KB) `"(పనితీరు కోసం కుదించబడింది)"` నోటీసుతో కుదించబడతాయి                                                                    |
| **హెడర్ శుద్ధీకరణ**        | పేర్లు లోయర్కేస్కు మార్చబడతాయి; ఫ్రేమింగ్/హాప్-బై-హాప్ మరియు ప్రాక్సీ-ఆథ్ హెడర్లు తొలగించబడతాయి; కుకీలు పూర్తిగా తొలగించబడతాయి; క్రెడెన్షియల్ విలువలు `maskSecret()`కు అప్పగించబడతాయి |
| **CSP**                    | ఇంజెక్ట్ చేసిన రెస్పాన్స్ బాడీల ద్వారా XSSను నిరోధించడానికి Traffic Inspector పేజీలపై కఠినమైన Content Security Policy                                                                 |
| **డిఫాల్ట్గా నిల్వ ఉండదు** | `TrafficBuffer` ఇన్-మెమరీలో ఉంటుంది మరియు సర్వర్ పునఃప్రారంభమైనప్పుడు పోతుంది. స్పష్టంగా రికార్డ్ చేసినప్పుడు మాత్రమే సెషన్లు నిల్వ చేయబడతాయి                                         |

### అమలు చేసిన కఠిన నియమాలు

| నియమం                             | అనువర్తనం                                                                                    |
| --------------------------------- | -------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | Traffic Inspector రూట్ల నుంచి వచ్చే అన్ని HTTP ఎర్రర్ రెస్పాన్స్లు శుద్ధీకరించబడతాయి         |

### తెలిసిన పరిమితులు

- **సిస్టమ్-వ్యాప్త ప్రాక్సీ మోడ్** VPN క్లయింట్లు మరియు SSOతో సహా మెషీన్లోని అన్ని అప్లికేషన్లను ప్రభావితం చేస్తుంది. ఎల్లప్పుడూ ఆటో-డిసేబుల్ టైమర్తో ఉపయోగించండి. షేర్ చేసిన మెషీన్లపై ఉపయోగించవద్దు.
- **CONNECT టన్నెల్ HTTPS**: TLS ఇంటర్సెప్షన్ ప్రారంభించకపోతే మోడ్ 3 (HTTP_PROXY), HTTPS గమ్యస్థానాలకు సంబంధించిన టన్నెల్ మెటాడేటాను మాత్రమే క్యాప్చర్ చేస్తుంది. ఇది ఉద్దేశపూర్వకమే — AgentBridge సర్టిఫికేట్ను విశ్వసించకుండా పారదర్శకంగా క్యాప్చర్ చేయడం ఆ యాప్ల TLS వెరిఫికేషన్ను విఫలం చేస్తుంది.
- **కొన్ని కంపోనెంట్లలో హార్డ్కోడ్ చేసిన స్ట్రింగ్లు**: కొన్ని UI కంపోనెంట్లు (F7/F8) ఇంకా i18n కీల పరిధిలోకి రాని కొద్ది హార్డ్కోడ్ చేసిన స్ట్రింగ్లను కలిగి ఉన్నాయి. ఇవి i18n గ్యాప్ రిపోర్ట్లో తెలిసిన పరిమితిగా డాక్యుమెంట్ చేయబడ్డాయి; తదుపరి పాస్లో ఇవి మైగ్రేట్ చేయబడతాయి. ప్రభావిత స్ట్రింగ్లు ఫంక్షనల్ ఉపయోగం కోసం అనువాదం అవసరం లేని UI అలంకార లేబుల్లు.

## §7 సమస్య పరిష్కారం

### WebSocket డిస్కనెక్షన్

లైవ్ టెయిల్లో "డిస్కనెక్ట్ అయింది" అని కనిపిస్తే:

1. సర్వర్ ఇప్పటికీ రన్ అవుతోందో లేదో తనిఖీ చేయండి: `GET /api/tools/traffic-inspector/capture-modes`
2. పేజీని రీలోడ్ చేయండి — WebSocket మళ్లీ కనెక్ట్ అయి తాజా స్నాప్షాట్ను అందుకుంటుంది
3. సర్వర్ రీస్టార్ట్ చేయబడితే, ఇన్-మెమరీ బఫర్ క్లియర్ అవుతుంది — సెషన్ రికార్డ్ చేసి ఉంటే తప్ప పాత ఎంట్రీలు ఇక ఉండవు

### పోర్ట్ 8080 ఘర్షణ

HTTP_PROXY మోడ్ ప్రారంభం కాకపోతే:

```bash
lsof -i :8080    # ప్రాసెస్ను కనుగొనండి
```

పోర్ట్ను మార్చండి:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### సిస్టమ్ ప్రాక్సీ మునుపటి స్థితికి మార్చబడలేదు

సిస్టమ్-వ్యాప్త ప్రాక్సీ మోడ్ యాక్టివ్గా ఉన్నప్పుడు OmniRoute క్రాష్ అయితే:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

ప్రాక్సీ యాక్టివ్గా ఉందని DB స్థితి సూచిస్తున్నట్లు గుర్తిస్తే, తదుపరి లోడ్ సమయంలో డ్యాష్బోర్డ్ "సిస్టమ్ ప్రాక్సీని మునుపటి స్థితికి మార్చండి" అనే ఎంపికను కూడా అందిస్తుంది.

### బఫర్ నిండింది

బఫర్ `INSPECTOR_BUFFER_SIZE`కు (డిఫాల్ట్ 1000) చేరుకున్నప్పుడు, కొత్త ఎంట్రీలు అత్యంత పాత ఎంట్రీలను తొలగించి వాటి స్థానాన్ని తీసుకుంటాయి. ముఖ్యమైన రిక్వెస్ట్లు కోల్పోతుంటే:

- `INSPECTOR_BUFFER_SIZE`ను పెంచండి (ఉదా., 5000) — ఇది నిల్వ వ్యవధిని పెంచడానికి బదులుగా ఎక్కువ మెమరీని ఉపయోగిస్తుంది
- సంబంధిత కాలవ్యవధిని DBలో నిలకడగా భద్రపరచడానికి సెషన్ను రికార్డ్ చేయండి
