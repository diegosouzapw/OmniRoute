> **TL;DR**: `open-sse/` అనేది OmniRouteలోని ప్రతి LLM అభ్యర్థనకు శక్తినిచ్చే ప్రధాన స్ట్రీమింగ్ ఇంజిన్. అభ్యర్థన పైప్లైన్, ఎగ్జిక్యూటర్లు, సర్వీసులు, MCP సర్వర్ మరియు అనువాద లేయర్ను అమలు చేసే సుమారు 1,400 ఫైళ్లు ఇందులో ఉన్నాయి. ఈ భాగాలు పరస్పరం ఎలా పనిచేస్తాయో ఈ గైడ్ వివరిస్తుంది.

**మూలం:** `open-sse/` (వర్క్స్పేస్ ప్యాకేజ్, సుమారు 1,440 టెస్ట్-యేతర `.ts` ఫైళ్లు)

## ప్రత్యేక వర్క్స్పేస్ ప్యాకేజ్ ఎందుకు?

అనేక కారణాల వల్ల `open-sse/` అనేది OmniRoute మోనోరెపోలోని ఒక **స్వతంత్ర వర్క్స్పేస్**:

1. **పునర్వినియోగ సామర్థ్యం** — `open-sse` npmలో `@omniroute/open-sse`గా ప్రచురించబడుతుంది, కాబట్టి ఇతర ప్రాజెక్ట్లు దీన్ని స్వతంత్రంగా ఉపయోగించవచ్చు
2. **స్పష్టమైన హద్దులు** — స్ట్రీమింగ్ ఇంజిన్ OmniRoute-నిర్దిష్ట UI/DB లేయర్ నుంచి వేరుచేయబడింది
3. **పనితీరు** — ఈ ఇంజిన్కు Next.js డిపెండెన్సీలు లేవు, తద్వారా CLI/serverless సందర్భాల్లో వేగవంతమైన కోల్డ్ స్టార్ట్లు సాధ్యమవుతాయి
4. **వెర్షనింగ్** — `open-sse` తన స్వంత షెడ్యూల్ ప్రకారం విడుదల కావచ్చు

```json
// package.json
"workspaces": ["open-sse"]
```

## అభ్యర్థన పైప్లైన్

ప్రతి LLM అభ్యర్థన ఒక **5-దశల పైప్లైన్** గుండా ప్రవహిస్తుంది:

```
                              ┌──────────────┐
   HTTP అభ్యర్థన               │  1. రూట్     │   కాంబో పరిష్కారం, మోడల్ ఎంపిక
   (Next.js రూట్)              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. అనువాదం  │   ఫార్మాట్ మార్పిడి (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. అమలు     │   ప్రొవైడర్ ఎగ్జిక్యూటర్, HTTP, రీట్రై, బ్రేకర్
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. స్ట్రీమ్  │   SSE రూపాంతరం, బ్యాక్ప్రెషర్
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. నమోదు    │   వినియోగ ట్రాకింగ్, కాల్ లాగ్, ఎర్రర్ వర్గీకరణ
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP ప్రతిస్పందన (SSE లేదా JSON)
```

### దశ 1: రూట్ (services/combo.ts)

**ఎంట్రీ పాయింట్**: `services/combo.ts`లోని `handleComboChat()`

అభ్యర్థనను నిర్దిష్టమైన `(provider, model, account, credentials)` ట్యూపుల్కు పరిష్కరిస్తుంది:

- ID ద్వారా కాంబోను వెతకడం (లేదా `auto/*` మోడళ్ల కోసం వర్చువల్ కాంబోను నిర్మించడం)
- రూటింగ్ వ్యూహాన్ని వర్తింపజేయడం (ప్రాధాన్యత, వెయిటెడ్, రౌండ్-రాబిన్ మొదలైనవి)
- అనారోగ్యకరమైన ప్రొవైడర్లను మినహాయించడం (సర్క్యూట్ బ్రేకర్)
- తదుపరి ఉపయోగించదగిన లక్ష్యాన్ని ఎంచుకోవడం

`auto/*` మోడళ్ల కోసం, ఈ దశ అదనంగా:

- **16-కారకాల స్కోరింగ్** అల్గోరిథమ్ను అమలు చేస్తుంది (`services/autoCombo/`)
- ఆరోగ్యం, ఖర్చు, లేటెన్సీ మొదలైన వాటి ఆధారంగా `provider+model` జోడీని ఎంచుకుంటుంది

### దశ 2: అనువాదం (translator/)

మూల ఫార్మాట్ (ఉదా., OpenAI) లక్ష్య ఫార్మాట్కు (ఉదా., Claude) భిన్నంగా ఉంటే, అభ్యర్థన **అనువదించబడుతుంది**:

- సిస్టమ్ ప్రాంప్ట్ → సిస్టమ్ సందేశం
- టూల్ నిర్వచనాలు → ప్రొవైడర్-నిర్దిష్ట టూల్ ఫార్మాట్
- రీజనింగ్/థింకింగ్ పారామీటర్లు → ప్రొవైడర్-నిర్దిష్ట సమానార్థకాలు
- సందేశ రోల్ సాధారణీకరణ (OpenAI కాని వాటి కోసం `developer` → `system`)

`translator/index.ts` వీటిని ఎక్స్పోజ్ చేస్తుంది:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### దశ 3: అమలు (executors/)

**ఎంట్రీ పాయింట్**: `getExecutor(providerId).execute(request, options)`

అన్ని ప్రొవైడర్లు `getExecutor()` ఫ్యాక్టరీ ఫాల్బ్యాక్ ద్వారా `DefaultExecutor`ను (`executors/default.ts`) ఉపయోగిస్తారు. ఎగ్జిక్యూటర్:

- అప్స్ట్రీమ్ URLను నిర్మిస్తుంది (`buildUrl()`)
- ప్రొవైడర్-నిర్దిష్ట హెడర్లను జోడిస్తుంది (`buildHeaders()`)
- అభ్యర్థన బాడీని రూపాంతరం చేస్తుంది (`transformRequest()`)
- రీట్రై + ఎక్స్పోనెన్షియల్ బ్యాక్ఆఫ్తో HTTP అభ్యర్థనను పంపుతుంది
- అవసరమైతే ఆథెంటికేషన్ రిఫ్రెష్ను నిర్వహిస్తుంది (OAuth ప్రొవైడర్లు)

అన్ని ఎగ్జిక్యూటర్లు `BaseExecutor`ను (`executors/base.ts`, 1170 LOC) విస్తరిస్తాయి, ఇది వీటిని అందిస్తుంది:

- సాధారణ రీట్రై లాజిక్
- ప్రాక్సీ ఇంటిగ్రేషన్
- సర్క్యూట్ బ్రేకర్ ఇంటిగ్రేషన్
- వినియోగ నమోదు హుక్లు

### దశ 4: స్ట్రీమ్ (utils/stream.ts)

స్ట్రీమింగ్ ప్రతిస్పందనల కోసం, ఎగ్జిక్యూటర్ ఒక **ReadableStream**ను తిరిగి ఇస్తుంది. హ్యాండ్లర్:

- ఒక SSE ట్రాన్స్ఫార్మ్ ద్వారా పైప్ చేస్తుంది (`createSSETransformStreamWithLogger`)
- పనిచేయని కనెక్షన్లను గుర్తించడానికి హార్ట్బీట్ పింగ్లను వర్తింపజేస్తుంది
- క్లయింట్ డిస్కనెక్ట్ను సజావుగా నిర్వహిస్తుంది (`pipeWithDisconnect`)
- స్ట్రీమింగ్ కాని క్లయింట్ల కోసం SSE → JSONగా రూపాంతరం చేస్తుంది

### chatCore.ts (5977 పంక్తులు)

**ప్రధాన రిక్వెస్ట్ హ్యాండ్లర్**. దాని పరిమాణం ఉన్నప్పటికీ, ఇది స్పష్టమైన నిర్మాణాన్ని కలిగి ఉంది:

```ts
// chatCore.ts యొక్క సూడో-నిర్మాణం
export async function handleChat(request: NextRequest) {
  // 1. అథెంటికేషన్ + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. బాడీ ధృవీకరణ
  const body = await parseRequestBody(request);

  // 3. ఫార్మాట్ గుర్తింపు + అనువాదం
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. కాంబో రూటింగ్
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // తదుపరి లక్ష్యానికి కొనసాగండి
    }
  }

  // 5. అత్యవసర ఫాల్బ్యాక్
  return await emergencyFallback(body);
}
```

````
### సాధారణ ప్యాటర్న్లు

ప్రొవైడర్లు `getExecutor(providerId)` ద్వారా రిజాల్వ్ చేయబడతారు, ఇది కాన్ఫిగర్ చేయబడిన ఎగ్జిక్యూటర్ను రిటర్న్ చేస్తుంది. OpenAI/Anthropic-కంపాటబుల్ ప్రొవైడర్లు `DefaultExecutor` (`executors/default.ts`)ను ఉపయోగిస్తారు. ప్రొవైడర్-నిర్దిష్ట ప్రవర్తన (బేస్ URL, ఆత్ హెడర్లు, API వెర్షన్) `open-sse/config/providers/`లో కాన్ఫిగర్ చేయబడుతుంది, అయితే రిక్వెస్ట్ బాడీ ట్రాన్స్ఫార్మేషన్లు `open-sse/translator/`లో హ్యాండిల్ చేయబడతాయి.

**కస్టమ్ URL** ప్రొవైడర్ కాన్ఫిగరేషన్ ద్వారా సెట్ చేయబడుతుంది:

```ts
// open-sse/config/providers/లో ప్రొవైడర్ కాన్ఫిగరేషన్
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**కస్టమ్ ఆత్** ప్రొవైడర్ రిజిస్ట్రీ యొక్క ఆత్ కాన్ఫిగరేషన్ (API కీ, OAuth, హెడర్ ప్రొఫైళ్లు) ద్వారా హ్యాండిల్ చేయబడుతుంది.

**కస్టమ్ రిక్వెస్ట్ బాడీ** ట్రాన్స్ఫార్మేషన్లు (ఉదా., Anthropic `system`ను `messages` నుండి వేరు చేయడం) `open-sse/translator/`లో ప్రొవైడర్ వారీగా రిజిస్టర్ చేయబడతాయి.

````
});
````

రిజల్యూషన్ `ExecutorRegistry` (`executors/registry.ts`) ద్వారా జరుగుతుంది: ప్రతి ప్రత్యేక ఎగ్జిక్యూటర్ `executors/index.ts` యొక్క బిల్ట్-ఇన్ టేబుల్లో డిక్లేర్ చేయబడి, మాడ్యూల్ లోడ్ వద్ద `registerExecutor(alias, instance)` ద్వారా రిజిస్టర్ చేయబడుతుంది; `getExecutor()` రిజిస్ట్రీని సంప్రదించి, ప్రత్యేక ఎంట్రీ లేని ఏ ప్రొవైడర్ కోసమైనా మెమోయిజ్డ్ `DefaultExecutor`కు ఫాల్బ్యాక్ అవుతుంది. పూర్తి అలియాస్ → ఎగ్జిక్యూటర్ మ్యాపింగ్ గోల్డెన్ టెస్ట్ `tests/unit/executor-map-golden.test.ts` ద్వారా నిర్ధారించబడింది.

## అనువాదకాలు

**3 ఫార్మాట్ల** మధ్య అనువదించండి: OpenAI, Anthropic, Gemini, అలాగే కొత్త Responses API.

### అనువాదం ఎప్పుడు జరుగుతుంది

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

సాధారణ అనువాదాలు:

- `OpenAI → Anthropic`: ప్రత్యేక `system` ఫీల్డ్, `x-api-key` హెడర్
- `OpenAI → Gemini`: `messages`కు బదులుగా `contents`, `systemInstruction`
- `OpenAI → Responses API`: `input` అర్రే, `previous_response_id` స్థితి

### నిర్వహించబడే ప్రత్యేక సందర్భాలు

- `developer` పాత్ర → OpenAI కాని వాటికి `system`
- `system` పాత్ర → GLM/ERNIE కోసం మొదటి వినియోగదారు సందేశంలో విలీనం చేయబడుతుంది
- `json_schema` → Gemini యొక్క `responseMimeType` + `responseSchema`
- `tools` → ప్రొవైడర్కు ప్రత్యేకమైన టూల్ ఫార్మాట్
- థింకింగ్ పారామీటర్లు (o1, Claude) → ప్రొవైడర్కు ప్రత్యేకమైన సమానాలు

## MCP సర్వర్

`open-sse/mcp-server/` **Model Context Protocol** సర్వర్ను అమలు చేస్తుంది:

- **110 టూల్స్** (ప్రొవైడర్ నిర్వహణ, కాంబోలు, మెమరీ, క్యాష్, కంప్రెషన్, ప్రాక్సీ, నైపుణ్యాలు, గేమిఫికేషన్, ప్లగిన్లు, Notion, Obsidian, లోకల్ కార్పస్)
- **3 ట్రాన్స్పోర్ట్లు**: stdio, SSE, Streamable HTTP
- సూక్ష్మస్థాయి ఆథరైజేషన్ కోసం **33 స్కోప్లు**

### టూల్ నమోదు

టూల్స్ `open-sse/mcp-server/tools/`లో స్వతంత్ర ఫైల్లుగా నమోదు చేయబడతాయి; ప్రతి ఒక్కటి పేరు, స్కీమా, హ్యాండ్లర్ మరియు స్కోప్ను ఎక్స్పోర్ట్ చేస్తుంది:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### ట్రాన్స్పోర్ట్లు

```ts
// stdio (CLI వినియోగం)
startMcpStdio(server);

// SSE (HTTP-ఆధారిత స్ట్రీమింగ్)
startMcpSse(server, port);

// Streamable HTTP (ఆధునిక MCP)
startMcpStreamable(server, port);
```

### ఆథరైజేషన్

ప్రతి టూల్ కాల్ స్కోప్ తనిఖీల (`open-sse/mcp-server/auth/`) ద్వారా వెళ్తుంది:

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## ట్రాన్స్ఫార్మర్లు

`open-sse/transformer/` **Chat Completions** మరియు **Responses API** ఫార్మాట్ల మధ్య మారుస్తుంది.

### ప్రత్యేక ట్రాన్స్ఫార్మర్ ఎందుకు?

Responses API అనేది **స్థితితో కూడిన సంభాషణలు** (`previous_response_id`) కలిగిన OpenAI యొక్క కొత్త ఫార్మాట్. క్లయింట్ Responses అభ్యర్థనను పంపినప్పుడు, OmniRoute:

1. అంతర్గతంగా Responses → Chat Completionsకు మారుస్తుంది
2. ప్రొవైడర్కు పంపుతుంది (Chat Completionsకు మద్దతిచ్చే ఏ ప్రొవైడర్కైనా)
3. ప్రతిస్పందనను తిరిగి Responses ఫార్మాట్కు మారుస్తుంది
4. మార్చబడిన ప్రతిస్పందనను క్లయింట్కు స్ట్రీమ్ చేస్తుంది

ట్రాన్స్ఫార్మర్ (`transformer/responsesTransformer.ts`) ఇది అందిస్తుంది:

```ts
createResponsesApiTransformStream(): TransformStream
```

ఇది వీటిని నిర్వహిస్తుంది:

- `response.output_item.added` ఈవెంట్లు
- `response.output_text.delta` ఈవెంట్లు
- `response.completed` ఈవెంట్
- టూల్ కాల్ మ్యాపింగ్ (`function_call` ↔ `tool_calls`)

## కొత్త కాంపోనెంట్ను జోడించడం

### కొత్త సర్వీస్ను జోడించడం

1. నిర్దిష్ట బాధ్యతతో `open-sse/services/[serviceName].ts`ని సృష్టించండి
2. ప్రధాన హ్యాండ్లర్ ఫంక్షన్ను మరియు ఏవైనా కాన్స్టెంట్లను ఎగుమతి చేయండి
3. `tests/unit/services/[serviceName].test.mjs`లో యూనిట్ టెస్ట్లను జోడించండి
4. `handlers/chatCore.ts`లోని అభ్యర్థన పైప్లైన్లో ఇంటిగ్రేట్ చేయండి (రూటింగ్కు సంబంధించినదైతే)
5. సర్వీస్ లక్ష్య ఎంపికను ప్రభావితం చేస్తే `combo.ts`లోని రూటింగ్ లాజిక్ను నవీకరించండి
6. ఈ ఫైల్లో డాక్యుమెంట్ చేయండి

### కొత్త ఎగ్జిక్యూటర్ను జోడించడం

1. `BaseExecutor`ను ఎక్స్టెండ్ చేస్తూ `open-sse/executors/[provider].ts`ని సృష్టించండి
2. `config/providerRegistry.ts`లో నమోదు చేయండి
3. `executors/index.ts` ఫ్యాక్టరీకి జోడించండి
4. ఎగ్జిక్యూటర్ కోసం యూనిట్ టెస్ట్లను జోడించండి
5. `docs/architecture/ARCHITECTURE.md`లో డాక్యుమెంట్ చేయండి

### కొత్త MCP టూల్ను జోడించడం

1. `open-sse/mcp-server/tools/[category]Tools.ts`ని సృష్టించండి లేదా నవీకరించండి
2. ఇన్పుట్ల కోసం Zod స్కీమాను నిర్వచించండి
3. `mcp-server/index.ts`లో టూల్ను నమోదు చేయండి
4. `mcp-server/auth/`లోని స్కోప్ మ్యాట్రిక్స్కు జోడించండి
5. యూనిట్ టెస్ట్లను జోడించండి
