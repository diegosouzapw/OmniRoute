> **చివరిగా నవీకరించబడింది:** 2026-06-28 — v3.8.40

రూటింగ్ కాన్ఫిగరేషన్లు, ఒక్కో ప్రొవైడర్/మోడల్ లేదా బండిల్ చేసిన "గోల్డెన్ సెట్" సూట్లను బెంచ్మార్క్ చేయడానికి మీరు ఉపయోగించగల సాధారణ మూల్యాంకన ఫ్రేమ్వర్క్తో OmniRoute వస్తుంది.
రూటింగ్ మార్పులను ధృవీకరించడానికి, కొత్త ప్రొవైడర్లను చెల్లుబాటు చేయడానికి, అలాగే వాటిని ప్రొడక్షన్ ట్రాఫిక్కు ప్రమోట్ చేయడానికి ముందు విడుదలలను నియంత్రించడానికి దీన్ని ఉపయోగించండి.

ఈ ఫ్రేమ్వర్క్ కింది విధంగా అమలు చేయబడింది:

- ఇన్-మెమరీ అంతర్నిర్మిత సూట్లను నమోదు చేసే, ఆశించిన ప్రమాణాలతో అవుట్పుట్లను పోల్చి మూల్యాంకనం చేసే, అలాగే స్కోర్కార్డ్లను సమగ్రపరిచే స్వచ్ఛమైన రన్నర్ (`src/lib/evals/evalRunner.ts`).
- అనుకూల (వినియోగదారు నిర్వచించిన) సూట్లు మరియు చారిత్రక రన్లను SQLiteలో నిల్వ చేయడానికి ఒక పెర్సిస్టెన్స్ లేయర్ (`src/lib/db/evals.ts`).
- `POST /v1/chat/completions`కు వాస్తవ కాల్లను పంపించడం ద్వారా ప్రతి కేస్ను అమలు చేసే, లేటెన్సీ మరియు అవుట్పుట్లను సంగ్రహించే, అలాగే రన్ను నిల్వ చేసే ఆర్కెస్ట్రేషన్ లేయర్ (`src/lib/evals/runtime.ts`).
- `/api/evals/*` కింద REST ఎండ్పాయింట్లు (మేనేజ్మెంట్ ప్రమాణీకరణకు మాత్రమే).
- `Dashboard → Usage → Evals` వద్ద డాష్బోర్డ్ ఇంటర్ఫేస్ (`EvalsTab.tsx`).

## భావనలు

### సూట్

సూట్ అనేది `description` మరియు ఒకటి లేదా అంతకంటే ఎక్కువ కేస్లతో కూడిన, పేరు గల టెస్ట్ కేస్ల సమాహారం. సూట్లు రెండు మూలాల నుంచి వస్తాయి:

| మూలం       | నిర్వచించబడే స్థానం                                     | రన్టైమ్లో మార్చవచ్చా?         |
| ---------- | ------------------------------------------------------- | ----------------------------- |
| `built-in` | బూట్ సమయంలో `registerSuite()` ద్వారా నమోదు చేయబడుతుంది  | లేదు (కోడ్లో నిర్వచించబడింది) |
| `custom`   | SQLite `eval_suites` + `eval_cases`లో నిల్వ చేయబడుతుంది | అవును (API/UI ద్వారా)         |

ప్రస్తుత అంతర్నిర్మిత సూట్లు (`src/lib/evals/evalRunner.ts` చూడండి):

- `golden-set` — అభివాదం/గణితం/అనువాదం/భద్రత విభాగాల్లో 10 బేస్లైన్ కేస్లు
- `coding-proficiency` — Python/JS/SQL/TS/బగ్ గుర్తింపు
- `reasoning-logic` — న్యాయవాక్యాలు, పద సమస్యలు, నమూనా గుర్తింపు
- `multilingual` — అనువాదం మరియు భాష గుర్తింపు
- `safety-guardrails` — PII, జైల్బ్రేక్, తిరస్కరణ, పక్షపాత అవగాహన
- `instruction-following` — JSON మాత్రమే, సంఖ్యా క్రమ జాబితాలు, భాషా పరిమితులు
- `codex-comparison` — కంపేర్ మోడ్ కోసం ఉద్దేశించిన ముఖాముఖి కోడింగ్ టాస్క్లు

### కేస్

ప్రతి కేస్లో ఇవి ఉంటాయి:

| ఫీల్డ్     | వివరణ                                                                             |
| ---------- | --------------------------------------------------------------------------------- |
| `id`       | స్థిరమైన ఐడెంటిఫయర్ (అవుట్పుట్లు మరియు మెట్రిక్లను కీ చేయడానికి ఉపయోగించబడుతుంది) |
| `name`     | మానవులు చదవగల లేబుల్                                                              |
| `model`    | రన్ `suite-default` టార్గెటింగ్ను ఉపయోగించినప్పుడు డిఫాల్ట్ మోడల్                 |
| `input`    | `{ messages, max_tokens? }` — `/v1/chat/completions`కు పంపబడుతుంది                |
| `expected` | `{ strategy, value }` — స్కోరింగ్ ప్రమాణం (కింద చూడండి)                           |
| `tags`     | ఐచ్ఛిక లేబుల్లు (ఉదా. `safety`, `pii`, `jailbreak`)                               |

### టార్గెట్

ఒకే సూట్ను విభిన్న టార్గెట్లపై రన్ చేయవచ్చు. టార్గెట్ స్కీమా అనేది
`src/shared/validation/schemas.ts`లోని `evalTargetSchema`:

| టార్గెట్ రకం    | `id`       | ప్రవర్తన                                                               |
| --------------- | ---------- | ---------------------------------------------------------------------- |
| `suite-default` | `null`     | ప్రతి కేస్ దాని అంతర్నిర్మిత `model` ఫీల్డ్ను ఉపయోగిస్తుంది            |
| `model`         | మోడల్ పేరు | ప్రతి కేస్ను ఒక డైరెక్ట్ మోడల్ ద్వారా బలవంతంగా నడపండి (ఉదా. `gpt-4o`)  |
| `combo`         | కాంబో పేరు | ప్రతి కేస్ను ఒకే కాంబో ద్వారా నడపండి (రూటింగ్ ఇంజిన్ను పరీక్షిస్తుంది) |

`model` మరియు `combo` కోసం, `id` ఫీల్డ్ తప్పనిసరి (Zod
`superRefine` ద్వారా అమలు చేయబడుతుంది). `compareTarget` అందించినప్పుడు, రెండు టార్గెట్లు తప్పనిసరిగా వేర్వేరుగా ఉండాలి —
A/B పోలిక కోసం రన్నర్ రెండు రన్లను ఒకే `runGroupId` కింద నిల్వ చేస్తుంది.

## స్కోరింగ్ ప్రమాణాలు

`evaluateCase()` (evalRunner.ts)లో అమలు చేయబడ్డాయి:

| వ్యూహం     | ఉత్తీర్ణమయ్యే సందర్భం…                                                                    |
| ---------- | ----------------------------------------------------------------------------------------- |
| `exact`    | `actualOutput === expected.value`                                                         |
| `contains` | `actualOutput.toLowerCase().includes(expected.value.toLowerCase())`                       |
| `regex`    | `new RegExp(expected.value).test(actualOutput)` సత్య విలువను ఇస్తుంది                     |
| `custom`   | `expected.fn(actualOutput, evalCase)` సత్య విలువను ఇస్తుంది (అంతర్నిర్మిత వాటికి మాత్రమే) |

**గమనిక:** ఫంక్షన్లను API ద్వారా సీరియలైజ్ చేయడం సాధ్యం కాదు కాబట్టి, కస్టమ్-ఫంక్షన్ స్కోరింగ్ అనేది కోడ్లో నిర్వచించిన (అంతర్నిర్మిత)
సూట్లకు మాత్రమే పరిమితం చేయబడింది. వినియోగదారులు సృష్టించిన సూట్ల కోసం
`evalCaseBuilderSchema` కేవలం `contains | exact | regex`ను మాత్రమే అంగీకరిస్తుంది.

ప్రస్తుతం LLM-ను-న్యాయనిర్ణేతగా ఉపయోగించే లేదా ఎంబెడ్డింగ్-ఆధారిత సారూప్యత స్కోరర్ లేదు — దాన్ని
`evaluateCase()`లో సులభంగా విస్తరణ బిందువుగా జోడించవచ్చు.

## డేటాబేస్ స్కీమా

మూడు పట్టికలు (మైగ్రేషన్లు `030_create_eval_runs.sql` మరియు
`031_create_eval_suites.sql`):

| పట్టిక        | ఉద్దేశ్యం                                                                                                                   |
| ------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `eval_suites` | కస్టమ్ సూట్ మెటాడేటా (`id`, `name`, `description`)                                                                          |
| `eval_cases`  | ప్రతి సూట్కు సంబంధించిన కేసులు — `input_json`, `expected_*`, `tags_json`                                                    |
| `eval_runs`   | చారిత్రక రన్లు — `pass_rate`, `total`, `passed`, `failed`, `avg_latency_ms`, `summary_json`, `results_json`, `outputs_json` |

అంతర్నిర్మిత సూట్లు DBలో నిల్వ చేయబడవు. అవి మెమరీలో ఉంటాయి మరియు
`evalRunner.ts` దిగుమతి చేయబడిన ప్రతిసారీ మళ్లీ నమోదు చేయబడతాయి.

## REST API

అన్ని ఎండ్పాయింట్లకు నిర్వహణ ప్రమాణీకరణ (`requireManagementAuth`) అవసరం — అవి
పబ్లిక్ ప్రాక్సీ ఉపరితలంలో భాగం కావు.

| ఎండ్పాయింట్                   | పద్ధతి   | వివరణ                                                                |
| ----------------------------- | -------- | -------------------------------------------------------------------- |
| `/api/evals`                  | `GET`    | సూట్లు + ఇటీవలి రన్లు + స్కోర్కార్డ్ + లక్ష్యాలు + కీలు జాబితా       |
| `/api/evals`                  | `POST`   | ఒక సూట్ను అమలు చేయడం (ఒకటి లేదా పోలిక) — స్కీమా `evalRunSuiteSchema` |
| `/api/evals/{suiteId}`        | `GET`    | ఒక సూట్ను పొందడం (అంతర్నిర్మిత లేదా కస్టమ్)                          |
| `/api/evals/suites`           | `POST`   | కస్టమ్ సూట్ను సృష్టించడం — స్కీమా `evalSuiteSaveSchema`              |
| `/api/evals/suites/{suiteId}` | `GET`    | కస్టమ్ సూట్ను పొందడం                                                 |
| `/api/evals/suites/{suiteId}` | `PUT`    | కస్టమ్ సూట్ను భర్తీ చేయడం (కేసులు మళ్లీ చేర్చబడతాయి)                 |
| `/api/evals/suites/{suiteId}` | `DELETE` | కస్టమ్ సూట్ను, దాని కేసులను తొలగించడం                                |

### సూట్ను అమలు చేయడం

```bash
curl -X POST http://localhost:20128/api/evals \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "suiteId": "golden-set",
    "target": { "type": "combo", "id": "my-combo" },
    "apiKeyId": "optional-api-key-uuid"
  }'
```

ఐచ్ఛిక ఫీల్డ్లు:

- `outputs` — ముందుగా గణించబడిన అవుట్పుట్ల `Record<caseId, string>`. ఇది అందించబడినప్పుడు,
  రన్నర్ **డిస్పాచ్ను దాటవేసి**, కాష్ చేసిన అవుట్పుట్లకు మాత్రమే స్కోర్ ఇస్తుంది (ఆఫ్లైన్
  మూల్యాంకనానికి ఉపయోగకరం).
- `compareTarget` — సమాంతరంగా అమలు చేయాల్సిన రెండవ లక్ష్యం; ముఖాముఖి వీక్షణ కోసం రెండు రన్లు
  రూపొందించబడిన `runGroupId`ను పంచుకుంటాయి.
- `apiKeyId` — డిస్పాచ్ చేయబడిన `/v1/chat/completions` కాల్లను ప్రమాణీకరించడానికి ఉపయోగించే
  అంతర్గత API కీ. `REQUIRE_API_KEY` ప్రారంభించబడినప్పుడు ఇది తప్పనిసరి.

### కస్టమ్ సూట్ను సృష్టించడం

```bash
curl -X POST http://localhost:20128/api/evals/suites \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Production smoke",
    "description": "Quick sanity check before deploy",
    "cases": [
      {
        "name": "JSON shape",
        "model": "gpt-4o",
        "input": { "messages": [{ "role": "user", "content": "Reply with {\"ok\": true}" }] },
        "expected": { "strategy": "regex", "value": "\"ok\"\\s*:\\s*true" }
      }
    ]
  }'
```

## డిస్పాచ్ పైప్లైన్

`runEvalSuiteAgainstTarget()` (`src/lib/evals/runtime.ts`):

1. సూట్ను (అంతర్నిర్మితమైనది లేదా అనుకూలమైనది) పరిష్కరిస్తుంది.
2. ప్రతి కేసు కోసం, ఆ కేసు యొక్క `messages`, పరిష్కరించిన `model`, `stream: false`,
   మరియు `max_tokens: 512` (లేదా కేసులో పేర్కొన్న ప్రత్యామ్నాయ విలువ)తో
   `/v1/chat/completions`కు ఒక `Request`ను రూపొందిస్తుంది.
3. చాట్ హ్యాండ్లర్ను నేరుగా కాల్ చేస్తుంది (అదే ప్రాసెస్లో — అదనపు HTTP హాప్ ఉండదు).
4. లేటెన్సీని నమోదు చేసి, `choices[0].message.content` లేదా Responses-API
   `output[]` పేలోడ్ నుంచి టెక్స్ట్ను సంగ్రహిస్తుంది.
5. `runSuite()` ద్వారా అన్ని అవుట్పుట్లకు స్కోర్ ఇచ్చి, ఆపై `saveEvalRun()` ద్వారా నిల్వ చేస్తుంది.

కేసులు **వరుసగా** అమలవుతాయి. ప్రస్తుతం కన్కరెన్సీ ఫ్లాగ్ లేదు.

## డ్యాష్బోర్డ్

UI `Dashboard → Usage → Evals`
(`src/app/(dashboard)/dashboard/usage/components/EvalsTab.tsx`) వద్ద ఉంటుంది. అక్కడి నుంచి మీరు:

- ఒక్కో కేసు ప్రివ్యూతో అంతర్నిర్మిత మరియు అనుకూల సూట్లను బ్రౌజ్ చేయవచ్చు.
- కేస్ బిల్డర్తో అనుకూల సూట్లను సృష్టించవచ్చు/సవరించవచ్చు/తొలగించవచ్చు.
- ఒక టార్గెట్ను (సూట్ డిఫాల్ట్లు / మోడల్ / కాంబో), ఐచ్ఛికంగా రెండవ
  `compareTarget`ను, ఐచ్ఛికంగా API కీని ఎంచుకుని, అవసరమైనప్పుడు రన్ చేయవచ్చు.
- రన్ చరిత్ర, ఒక్కో కేసు పాస్/ఫెయిల్ స్థితి, లేటెన్సీ మరియు సంగ్రహించిన అవుట్పుట్లను పరిశీలించవచ్చు.
- ప్రతి `(suite, target)` స్కోప్కు సంబంధించిన తాజా రన్ల ఆధారంగా సమీకరించిన
  రోలింగ్ స్కోర్కార్డ్ను చూడవచ్చు.

## Auto-Assessment RFCతో సంబంధం

ప్రత్యేకమైన, మరింత పరిమితమైన అసెస్మెంట్ సబ్సిస్టమ్
`src/domain/assessment/` వద్ద ఉంటుంది (లైవ్ స్కోరింగ్ ఇంజిన్ కోసం
[AUTO-COMBO.md](../routing/AUTO-COMBO.md) కూడా చూడండి).
ఆ సబ్సిస్టమ్ Auto Combo ఇంజిన్ను లక్ష్యంగా చేసుకుంటుంది — అప్స్ట్రీమ్లు విఫలమైనప్పుడు
కాంబోలు స్వయంగా కోలుకునేలా ప్రొవైడర్లు మరియు మోడల్లకు స్వయంచాలకంగా స్కోర్ ఇస్తుంది.
ఇది తన స్వంత రన్నర్, తన స్వంత కేటగరైజర్ మరియు తన స్వంత స్కోరింగ్ లాజిక్ను ఉపయోగిస్తుంది.

ఇక్కడ డాక్యుమెంట్ చేసిన Evals ఫ్రేమ్వర్క్ **మరింత విస్తృతమైన, సాధారణ ప్రయోజన
టెస్టింగ్ ఉపరితలం**. ఏవైనా రిగ్రెషన్ సూట్లు, A/B పోలికలు మరియు ప్రతి విడుదలకు
స్మోక్ టెస్ట్ల కోసం దీనికి ప్రాధాన్యం ఇవ్వండి. రూటింగ్ నిర్ణయాలను ప్రభావితం చేయడానికి
రియల్-టైమ్ ప్రొవైడర్ స్థితి అవసరమైనప్పుడు Auto-Assessment సబ్సిస్టమ్ను ఉపయోగించండి.

## CI ఇంటిగ్రేషన్

ప్రస్తుతం ప్రత్యేకమైన `eval:ci` npm స్క్రిప్ట్ లేదు. eval ఫలితాల ఆధారంగా
విడుదలలను గేట్ చేయాలనుకుంటే రెండు మార్గాలు ఉన్నాయి:

- **HTTP మార్గం**: సర్వర్ను ప్రారంభించి, తెలిసిన `suiteId` + `target`తో
  `POST /api/evals`ను కాల్ చేసి, ప్రతిస్పందనలో
  `runs[].summary.passRate >= N` అని నిర్ధారించండి.
- **ఇన్-ప్రాసెస్ మార్గం**: ఒక స్క్రిప్ట్లో `@/lib/evals/runtime` నుంచి
  `runEvalSuiteAgainstTarget()`ను ఇంపోర్ట్ చేసి, టెస్ట్ DBపై రన్ చేసి, తిరిగి వచ్చిన
  `PersistedEvalRun.summary`ను తనిఖీ చేయండి.

రూట్ మరియు చరిత్రకు సంబంధించిన టెస్ట్లు
`tests/unit/evals-route.test.ts` మరియు `tests/unit/evals-history.test.ts` వద్ద ఉంటాయి.

## ఎక్స్టెన్షన్ పాయింట్లు

సాధారణ మార్పులు మరియు వాటిని చేయాల్సిన స్థానాలు:

- **కొత్త స్కోరింగ్ వ్యూహం** — `evaluateCase()` (`evalRunner.ts`)లోని
  `switch (evalCase.expected.strategy)` బ్లాక్ను విస్తరించి,
  `src/lib/db/evals.ts`లోని `EvalCaseStrategy`తో పాటు `schemas.ts`లోని
  `evalCaseBuilderSchema`ను కూడా విస్తరించండి.
- **కొత్త అంతర్నిర్మిత సూట్** — ఒక సూట్ ఆబ్జెక్ట్ను నిర్వచించి,
  `evalRunner.ts` చివర `registerSuite()`ను కాల్ చేయండి. అది `listSuites()`
  ద్వారా స్వయంచాలకంగా కనుగొనబడుతుంది.
- **కన్కరెన్సీతో రన్ చేయడం** — `runEvalSuiteAgainstTarget()`లోని వరుస `for`
  లూప్ను పరిమిత `Promise.all`గా మార్చండి (ప్రస్తుతం కన్కరెన్సీ నియంత్రణ లేదు).
- **స్ట్రీమ్/టూల్-కాల్ కేసులు** — ప్రస్తుతం రన్నర్ `stream: false`ను నిర్బంధిస్తుంది.
  స్ట్రీమింగ్ లేదా టూల్-అవేర్ మూల్యాంకనానికి `runtime.ts`లో మార్పులు అవసరం
  (స్కోరింగ్కు ముందు SSE చంక్లను సంగ్రహించి, సమీకరించాలి).
