## npm Trusted Publishing (v3.8.51 నుండి డిఫాల్ట్) — అభ్యర్థనపై స్టేజ్డ్, ఫాల్బ్యాక్గా డైరెక్ట్

`npm-publish.yml` డిఫాల్ట్గా **npm Trusted Publishing (OIDC)** ద్వారా ప్రచురిస్తుంది:
`stage-npm` జాబ్ (github-hosted) ఆ రన్ కోసం GitHub id-tokenను స్వల్పకాలిక npm
క్రెడెన్షియల్గా మార్పిడి చేస్తుంది — రిపోజిటరీ సీక్రెట్స్లో దీర్ఘకాలిక npm టోకెన్ ఉండదు, 2FA ప్రాంప్ట్ ఉండదు, provenance జోడించబడుతుంది.
2FAను దాటవేసే టోకెన్లు విరమించబడుతున్నందున ఇప్పుడు npm అనుమతించే బైపాస్ ఇదే;
ఇది WS1.3 హామీని కొనసాగిస్తూనే, v3.8.48 వరకు ప్రాజెక్ట్లో ఉన్న
పూర్తిగా ఆటోమేటిక్ ప్రక్రియను పునరుద్ధరిస్తుంది (లీకైన టోకెన్ ఒంటరిగా ప్రచురించలేదు — అసలు టోకెనే లేదు).

**ఒకసారి మాత్రమే చేసే సెటప్ (యజమాని):** npmjs.com → ప్యాకేజీ `omniroute` → Settings → _Trusted
Publisher_ → GitHub: యజమాని `diegosouzapw`, రిపో `OmniRoute`, వర్క్ఫ్లో `npm-publish.yml`
(environment: none). ఇది ఉండే వరకు, ఆటోమేటిక్ దశ `ENEEDAUTH`తో విఫలమవుతుంది:
`publish_mode=staged`తో (క్రింద) లేదా `direct`తో మళ్లీ డిస్పాచ్ చేయండి.

### స్టేజ్డ్ ప్రచురణ (అభ్యర్థనపై — `publish_mode=staged`)

npm-publish వర్క్ఫ్లో ఇకపై నేరుగా ప్రచురించదు: ఇది ప్యాక్ చేసిన tarballను
బూట్ చేస్తుంది (`check:pack-boot`), ఆపై `npm stage publish`ను అమలు చేస్తుంది — అవే బైట్లు
రిజిస్ట్రీలో నిలిపి ఉంచబడతాయి, యజమాని ఆమోదించే వరకు **ఇన్స్టాల్ చేయలేరు**. మానవ 2FA గేట్
నిరూపణకు ముందు కాకుండా, దాని తర్వాతికి మార్చబడింది.

**వర్క్ఫ్లో గ్రీన్ అయిన తర్వాత యజమాని అనుసరించాల్సిన ప్రక్రియ:**

1. `npm stage list omniroute` — స్టేజ్ idని కనుగొనండి (వర్క్ఫ్లో సారాంశంలో కూడా ముద్రించబడుతుంది).
2. స్టేజ్ చేసిన బైట్లను ధృవీకరించండి (సిఫార్సు చేయబడింది): `npm stage download <id>`, ఆపై డౌన్లోడ్ చేసిన
   tarballను తాత్కాలిక prefixలో ఇన్స్టాల్ చేసి బూట్ చేయండి (`npm run check:pack-boot` అదే
   pack→install→boot తీర్పును CIలో ఆటోమేట్ చేస్తుంది).
3. `npm stage approve <id>` — 2FA ప్రాంప్టే ప్రచురణ. `npm stage reject <id>` విస్మరిస్తుంది.
4. ప్రచురణ అనంతర భద్రతా వలయం: ప్రచురణ అనంతర వెరిఫయర్ (v3.8.49 ప్రణాళికలోని WS1.4)
   పబ్లిక్ రిజిస్ట్రీ నుంచి ప్రచురించిన వెర్షన్ను శుభ్రమైన కంటైనర్లో ఇన్స్టాల్ చేసి బూట్ చేస్తుంది.

**అత్యవసర ఫాల్బ్యాక్:** `publish_mode=direct`తో `workflow_dispatch` పాత తక్షణ
`npm publish`ను పునరుద్ధరిస్తుంది (స్టేజింగ్లోనే సమస్యలు ఎదురైతే మాత్రమే ఉపయోగించండి; కారణాన్ని నమోదు చేయండి).

**ఒకసారి మాత్రమే చేసే హార్డెనింగ్ (యజమాని, npmjs.com):** `omniroute` కోసం Trusted Publisherను
stage-only మోడ్లో కాన్ఫిగర్ చేయండి, తద్వారా లీకైన దీర్ఘకాలిక టోకెన్ ఎక్కడి నుంచైనా నేరుగా `npm publish`
చేయలేదు — CI స్టేజ్ మాత్రమే చేయగలదు; యజమాని 2FA మాత్రమే విడుదల చేస్తుంది.

**దెబ్బతిన్న ఆర్టిఫాక్ట్ ప్లేబుక్ (మార్పులేదు):** డిఫాల్ట్ తక్షణ చర్యగా
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"`ను ఉపయోగించండి (నిమిషాల్లో పూర్తవుతుంది, తిరిగి మార్చవచ్చు);
72h/no-dependents పరిమితిలో మాత్రమే `npm unpublish`ను ఉపయోగించండి, ఎప్పుడూ మొదటి చర్యగా ఉపయోగించవద్దు.
Docker: వెర్షన్ ట్యాగ్ను ఎప్పుడూ తిరిగి రాయవద్దు — రోల్బ్యాక్ అంటే `latest`ను చివరి మంచి digestకు మళ్లీ సూచించడం.

**Docker Hub `latest` (ప్రతి స్థిరమైన SemVer ప్రచురణకు తప్పనిసరి):**
`docker-publish` వర్క్ఫ్లో **రెండింటినీ** ట్యాగ్ చేయాలి: `X.Y.Z` మరియు
ఇది అత్యధిక స్థిరమైన SemVer అని `should-promote-latest.sh` అంగీకరించినప్పుడు, `:latest`ను
**అదే digest**తో ట్యాగ్ చేయాలి. జాబ్ తర్వాత: Hub `latest` digest కొత్త
SemVer digestకు సమానంగా ఉండాలి మరియు `last_updated` మారి ఉండాలి. gitలో మాత్రమే ఉన్న
పరిష్కారాల గురించి విడుదల గమనికలు పేర్కొంటున్నప్పుడు `:latest`ను పాత బిల్డ్పైనే
వదిలేయవద్దు. Compose క్విక్స్టార్ట్లు `:latest`ను ఉపయోగిస్తాయి; GitOps మాత్రం `X.Y.Z`కు పిన్ చేయడాన్ని కొనసాగించాలి.
[Docker విడుదల ఛానెల్లు](../guides/DOCKER_GUIDE.md#release-channels) మరియు #10317 చూడండి.

## హాట్ఫిక్స్ ఫాస్ట్-లేన్ (లేబుల్ `hotfix`)

`hotfix` లేబుల్ ఉన్న PR భారీ CI మ్యాట్రిక్స్ను (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) దాటవేసి, వేగవంతమైన, అధిక-సంకేతం కలిగిన గేట్లను కొనసాగిస్తుంది: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
మరియు tarball boot-smoke (`check:pack-boot`). లక్ష్యం: ~33min బదులుగా ≤15minలో గ్రీన్ కావడం.

**ప్రవేశ విధానం — నాలుగూ తప్పనిసరి (Chromium/VS Code/Node అత్యవసర లేన్ల ఆధారంగా రూపొందించబడింది):**

1. **తీవ్రత**: ప్రొడక్షన్ పనిచేయడం లేదు — ప్రచురించిన ఆర్టిఫాక్ట్ బూట్ సమయంలో క్రాష్ అవుతుంది /
   భద్రతా పరిష్కారం / విడుదలలోని ప్రతి వినియోగదారు ప్రభావితమవుతున్నారు. "ముఖ్యమైనది" అంటే "పనిచేయడం లేదు" అని కాదు.
2. **అధికారం**: రిపాజిటరీ యజమాని మాత్రమే `hotfix` లేబుల్ను వర్తింపజేస్తారు. ఆ లేబులే
   ఆమోదం — campaign PRలో ఎప్పుడూ స్వయంగా వర్తింపజేయవద్దు.
3. **సాక్ష్యం**: PR వివరణ, గతంలో పూర్తిగా గ్రీన్ అయిన భారీ రన్కు (దాటవేసిన జాబ్లు
   తిరిగి ధ్రువీకరించే సూట్) అలాగే పరిష్కారానికి సంబంధించిన మొదట విఫలమై, తర్వాత పాస్ అయిన టెస్ట్కు లింక్ చేస్తుంది.
4. **పరిధి**: cherry-pick మాత్రమే — కనిష్ఠ పరిష్కారం, refactors వద్దు, సంబంధంలేని మార్పులు వద్దు.

దాటవేసిన coverage/ratchet పరిధి, release branchలో తదుపరి పూర్తి రన్ ద్వారా
(నిరంతర release-green) తిరిగి ధ్రువీకరించబడుతుంది — ఈ లేన్ నిరీక్షణను మాత్రమే దాటవేస్తుంది, ధ్రువీకరణను ఎన్నటికీ కాదు.
టెస్ట్లకు మాత్రమే సంబంధించిన diffs (`tests/` కింద ఉన్న అన్ని ఫైళ్లు, `tests/e2e/` కింద ఏవీ ఉండకూడదు) ఎలాంటి లేబుల్ లేకుండానే E2E
మ్యాట్రిక్స్ను స్వయంచాలకంగా దాటవేస్తాయి.

### Hooks (Husky ద్వారా ధృవీకరించబడినవి)

Husky hooks `.husky/`లో ఉంటాయి మరియు git ఆపరేషన్ల సమయంలో స్వయంచాలకంగా అమలవుతాయి.

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** వేగవంతమైన నిర్దిష్ట గేట్లు — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (2026-06-13న సక్రియం చేయబడింది). ఉద్దేశపూర్వకంగా `test:unit`ను మినహాయిస్తుంది (నెమ్మదిగా ఉంటుంది; CI `test-unit` job ద్వారా కవర్ చేయబడుతుంది).
  - విడుదల బ్రాంచ్లను push చేయడానికి ముందు `npm run test:unit`ను మాన్యువల్గా అమలు చేయండి.

ఏదైనా hook విఫలమైతే: మూల సమస్యను పరిష్కరించండి, `--no-verify`తో దాటవేయవద్దు.

### బిల్డ్ లేఅవుట్

రిపోజిటరీ మూడు వేర్వేరు అవుట్పుట్ డైరెక్టరీలను ఉపయోగిస్తుంది — వాటిని ఎప్పుడూ కలపవద్దు:

| డైరెక్టరీ | ఉద్దేశ్యం                                                                | ట్రాక్ చేయబడుతుందా? |
| --------- | ------------------------------------------------------------------------ | ------------------- |
| `src/`    | అప్లికేషన్ సోర్స్ (TypeScript / TSX)                                     | అవును               |
| `.build/` | బిల్డ్ మధ్యంతర ఫైళ్లు — `next build` అవుట్పుట్ (`distDir`)               | కాదు (gitignored)   |
| `dist/`   | పంపిణీ చేయదగిన npm బండిల్ — `assembleStandalone` ద్వారా సమీకరించబడుతుంది | కాదు (gitignored)   |

> **ఆపరేటర్ గమనిక:** రిమోట్ VPS ఇమేజ్ డైరెక్టరీ `/usr/lib/node_modules/omniroute/app/`గానే ఉంటుంది.
> **రిపోజిటరీలోని** బిల్డ్ అవుట్పుట్ మాత్రమే మారింది (`app/` → `dist/`). డిప్లాయ్ స్కిల్స్
> `dist/` కంటెంట్ను రిమోట్ `app/` డైరెక్టరీలోకి rsync చేస్తాయి — VPS పాత్ మార్పులు అవసరం లేదు.

**ఒకే-బిల్డ్ ఫ్లో:**

```
npm run build:release
  └─ rm -rf .build dist          (శుభ్రపరచడం)
  └─ next build → .build/next/   (మధ్యంతర ఫైళ్లు)
  └─ assembleStandalone          (standalone + static + public + nativesను dist/లోకి కాపీ చేస్తుంది)
  └─ writes dist/BUILD_SHA       (HEAD సెంటినెల్)
```

డిప్లాయ్ కోసం `npm run build` అమలు చేసిన తర్వాత విడిగా `npm run build:cli` అమలు చేయవద్దు — ఒకే కమాండ్లో క్లీన్ రీబిల్డ్ + సెంటినెల్ను చేసే
`npm run build:release`ను ఉపయోగించండి.

`scripts/release/artifact-identity.mjs`) నమోదు చేసి, టార్బాల్కు ప్రత్యేక జాబ్లో అటెస్టేషన్ చేస్తుంది. ప్రివ్యూను

### విభజన (3.9.0, GO తర్వాత)

1. [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md)లో GO నమోదు చేయబడింది.
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` అనేది `RESULT: READY`ను ముద్రిస్తుంది.
3. డ్రై-రన్ ముద్రించే కమాండ్లతో `origin`పై బ్రాంచ్లను మాన్యువల్గా సృష్టించండి —
   స్క్రిప్ట్ `origin`కు పుష్ చేయడానికి నిరాకరిస్తుంది. సమీక్షించిన develop కమిట్ను తిరిగి ఉపయోగించడానికి,
   ముందుగా మీ ఫోర్క్పై 3.9.0 టిప్కు వ్యతిరేకంగా `--execute` సాధనను నడపండి; అది రెండు SHAలను ముద్రిస్తుంది, మరియు
   అవే కమిట్లను పుష్ చేయవచ్చు:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. మొదటి PR విలీనం కావడానికి ముందే `stable/v3` మరియు `develop` శాఖలను రక్షించండి (rulesets + merge queue).
5. నిష్క్రియంగా ఉన్న workflows శాఖ ఉనికిని బట్టి సక్రియమవుతాయి: `forward-port.yml` (`stable/v3`కు push),
   `validate-stable-pr.yml` (`stable/v3`కు PRలు) మరియు `nightly-v4-build.yml`
   (`develop`ను build చేస్తుంది). ప్రారంభానికి ముందు, `secrets.FORWARD_PORT_TOKEN` repository secretను సెట్ చేయండి (దీంతో
   forward-port PRలపై CI అమలవుతుంది); యజమాని repository variable
   `vars.NIGHTLY_PUBLISH`ను `true`గా సెట్ చేసి, npm Trusted Publishing
   `nightly-v4-build.yml`ను ఆమోదించే వరకు nightly publishing నిలిపివేయబడే ఉంటుంది. Channel resolutionను `scripts/release/dist-tag.mjs` నిర్వహిస్తుంది; ఇదే
   resolverను `npm-publish.yml` ఉపయోగిస్తుంది.
6. channelsను ధృవీకరించండి: `npm view omniroute dist-tags --json`లో `latest` = 3.9.0గా కనిపించాలి మరియు
   v4 publish అయ్యే వరకు `next` / `nightly` ఉండకూడదు.
7. అవసరమైతే rollback చేయండి: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   మరియు `npm dist-tag add omniroute@3.8.59 latest`.

## రోల్బ్యాక్

విడుదలలో తీవ్రమైన సమస్య ఉంటే:

1. `gh release edit vX.Y.Z --prerelease` (తాజా విడుదల కాదని గుర్తిస్తుంది)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (వినియోగదారులు ఇంకా స్వీకరించకపోతే మాత్రమే)
3. లేదా: `release/vX.Y.0` పై హాట్ఫిక్స్ → ప్యాచ్ విడుదల `vX.Y.(Z+1)`
4. వెంటనే GitHub Discussions మరియు Discordలో తెలియజేయండి

## కఠినమైన నియమాలు

- `main`కు నేరుగా ఎప్పుడూ కమిట్ చేయవద్దు
- `main` లేదా `release/*` బ్రాంచ్లకు `git push --force`ను ఎప్పుడూ ఉపయోగించవద్దు
- Husky హుక్స్ను (`--no-verify`) ఎప్పుడూ దాటవేయవద్దు
- సీక్రెట్లు, క్రెడెన్షియల్లు లేదా `.env` ఫైల్లను ఎప్పుడూ కమిట్ చేయవద్దు
- కవరేజ్ ≥60/60/60/60 (స్టేట్మెంట్లు/లైన్లు/ఫంక్షన్లు/బ్రాంచ్లు)గా ఉండాలి
- `src/`, `open-sse/`, `electron/` లేదా `bin/`లోని ప్రొడక్షన్ కోడ్ను మార్చేటప్పుడు ఎల్లప్పుడూ పరీక్షలను చేర్చండి లేదా నవీకరించండి
