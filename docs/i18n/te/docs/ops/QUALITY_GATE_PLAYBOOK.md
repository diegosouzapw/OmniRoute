## భాగం 1 — తీర్పు మరియు పరిపక్వత వర్గీకరణ

**మొత్తం గ్రేడ్: A− / "అధునాతనం". ప్రాజెక్ట్లలో అగ్ర ~5–10%.** పరిశ్రమ స్పష్టంగా పేరుపెట్టిన
అనేక నమూనాలను ఈ వ్యవస్థ స్వతంత్రంగా అమలు చేస్తుంది — ఇదే అత్యంత బలమైన సమన్వయ సంకేతం
(మేము చెక్లిస్ట్ను నకలు చేయలేదు; సరైన పద్ధతుల వైపు స్వతంత్రంగా సమీపించాము).

| సూచన ఫ్రేమ్వర్క్                       | మన స్థితి                                                                                                                                                                                                                                                       | గ్రేడ్                                    |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| **OWASP DSOMM** (5 స్థాయిలు, 5 కోణాలు) | బలమైన Level 3; _Test Intensity_ మరియు _Static Depth_లో 4వ స్థాయికి చేరుకుంటోంది. చాలా సంస్థలు 1–2 స్థాయిలలోనే ఉన్నాయి.                                                                                                                                          | **L3→L4**                                 |
| **OpenSSF Scorecard** (18 తనిఖీలు)     | మేము CI-Tests, Code-Review, Dependency-Update-Tool, Fuzzing, SAST, Signed-Releases (provenance), Token-Permissions, Vulnerabilities, Dangerous-Workflowలను పాస్ చేస్తున్నాము. **లోపాలు:** `main`పై Branch-Protection OFFలో ఉంది; కొన్ని actions పిన్ చేయబడలేదు. | **~7–8/10**                               |
| **SLSA** (4 స్థాయిలు)                  | `npm publish --provenance` + `id-token: write` + GitHub-hosted build = **L2**, L3కి చేరువలో ఉంది. L3+ కోసం కఠినతరం చేసిన/hermetic builder లేదు.                                                                                                                 | **L2→L3**                                 |
| **SonarQube "Clean as You Code"**      | ఒకే తత్వం: ratchet _non-regression_ను గేట్ చేస్తుంది (కొత్త code metricను దిగజార్చదు). **భిన్నత:** Sonar **కొద్ది** conditionsనే సిఫార్సు చేస్తుంది; మనకు ~46 gates ఉన్నాయి (అలసటకు దారితీసే ప్రమాదం).                                                          | **సమన్వయంగా ఉంది, అయితే ఒక మినహాయింపుతో** |
| **Quality-Ratchet నమూనా**              | ఆదర్శప్రాయమైన అమలు: ratchet + `dedicatedGate` + `tightenSlack` + `--require-tighten` + graceful-skip. బహిరంగంగా లభించే చాలా ఉదాహరణలకంటే అధునాతనమైనది.                                                                                                           | **ఆదర్శప్రాయం**                           |
| **DORA 2024**                          | _stability_ కోణంలో అత్యంత బలంగా ఉంది. ప్రమాదం: భారీ gates వల్ల _lead time_ పెరగవచ్చు — fast-gates విభజన ద్వారా ఇది తగ్గించబడింది, కానీ coverage లోపం ఉంది (భాగం 2 చూడండి).                                                                                      | **బలమైనది (stability)**                   |
| **OWASP LLM Top 10 (2025)**            | runtime guard + promptfoo (eval) + garak (red-team)తో మేము ప్రమాదం #1 (prompt-injection)ను కవర్ చేస్తున్నాము. ఇవి ప్రామాణిక పరిశ్రమ tools.                                                                                                                      | **కవర్ చేయబడింది**                        |
| **Mutation testing**                   | Stryker nightly, thresholds 70/50, 8 కీలక modules. పరిశ్రమ ఏకాభిప్రాయం (60% existing / 80% new, nightly) — **మేము దానిని మించాము**. **లోపం:** score ఇంకా ratchet కాదు.                                                                                          | **దాదాపు సిద్ధం**                         |

## భాగం 2 — విమర్శనాత్మక అంచనా (బలాలు + నిజాయితీతో కూడిన బలహీనతలు)

### బలాలు (సగటు కంటే మెరుగ్గా ఉన్నవి)

1. **బహుళ-మెట్రిక్ రాచెట్ ఇంజిన్.** ఇది సిస్టమ్కు కేంద్రబిందువు. `quality-baseline.json`లో 24 మెట్రిక్లు
   - 4 ప్రత్యేక బేస్లైన్లు, ప్రతి దానికీ దిశ (`up`/`down`), సహనం (`eps`), స్లాక్
     (`tightenSlack`) మరియు `dedicatedGate` ఫ్లాగ్ ఉన్నాయి. ఒకసారి పరిష్కరించిన అంశాలు **పరిష్కరించబడినవిగానే** ఉంటాయి — ఇది
     కోడ్బేస్ ఎంట్రోపీకి విరుగుడు.
2. **సప్లై-చెయిన్ కోసం బహుళ-స్థాయి రక్షణ.** SAST (CodeQL/Sonar) + సీక్రెట్లు (`useDefault`తో gitleaks)
   - SCA (osv/npm-audit/Trivy/Dependabot) + లైసెన్స్లు + లాక్ఫైల్ + SBOM + SLSA
     ప్రొవెనెన్స్ + Scorecard + వర్క్ఫ్లో హార్డెనింగ్ (zizmor). ఇంత సమగ్ర స్టాక్ చాలా కొద్ది కోడ్బేస్లలోనే ఉంటుంది.
3. **గుడ్హార్ట్ నియమానికి విరుగుడులు.** కవరేజ్ను లక్ష్యంగా పెట్టుకోవడం ఒక సాంప్రదాయ యాంటీ-ప్యాటర్న్
   ("కొలమానం లక్ష్యంగా మారినప్పుడు, అది మంచి కొలమానంగా ఉండటం ఆగిపోతుంది"). మన వద్ద
   ప్రతిసమతుల్యాలు ఉన్నాయి: **మ్యూటేషన్ టెస్టింగ్** (టెస్ట్ కేవలం లైన్ను అమలు చేసిందా కాకుండా,
   బగ్ను గుర్తించిందా అని కొలుస్తుంది), **`check-test-masking`** (పాస్ కావడానికి అసర్ట్లను బలహీనపరచడాన్ని నిరోధిస్తుంది),
   **ప్రతి-మాడ్యూల్ కవరేజ్ కనిష్ఠ పరిమితులు** (సులభమైన భాగాలనే కాకుండా అధిక-ప్రమాద కోడ్ను పరీక్షించేలా చేస్తాయి) మరియు
   **`check-pr-evidence`** (కఠిన నియమం #18).
4. **హాల్యూసినేషన్-నిరోధక / స్థిరత్వ గేట్లు.** అరుదైన, విలువైన వర్గం: `check-known-symbols`,
   `check-fetch-targets`, `check-openapi-routes`, `check-docs-symbols` డాక్యుమెంటేషన్, స్పెసిఫికేషన్లు మరియు
   స్ట్రింగ్ డిస్పాచ్లు ప్రస్తుతం ఉనికిలో ఉన్న సింబల్లనే సూచిస్తున్నాయని నిర్ధారిస్తాయి. lint/test గుర్తించని "క్షీణత"ను గుర్తిస్తాయి.
5. **సలహాత్మకం→నిరోధక జీవనచక్రం.** కొత్త గేట్లు సలహాత్మకంగా ప్రవేశిస్తాయి (పరిపక్వం చెందుతున్నప్పుడు
   మెర్జ్లను నిరోధించవు), ఆపై సైకిల్ ముగింపులో నిరోధకంగా మారతాయి. గరిష్ఠ ప్రమాణాన్ని కోల్పోకుండా ఘర్షణను తగ్గిస్తుంది.
6. **ఇన్ఫ్రా అందుబాటులో లేనప్పుడు సునాయాసంగా స్కిప్ చేయడం.** బైనరీ/నెట్వర్క్ విఫలమైతే స్కానర్లు (`--ratchet`)
   `exit 0`తో ముగుస్తాయి — అందుబాటులో లేని ఇన్ఫ్రా చెల్లుబాటు అయ్యే PRను ఎప్పుడూ నిరోధించదు. ఇది పరిపక్వ ఇంజినీరింగ్.
7. **నియమబద్ధీకరించిన సంస్కృతి.** కఠిన నియమాలు + `trust-but-verify` + పాతబడిన-అనుమతి జాబితా + ఆధార-గేట్
   క్రమశిక్షణను స్వయంచాలక ధృవీకరణగా మారుస్తాయి.

### నిజాయితీతో కూడిన బలహీనతలు (వాస్తవ లోపాలు)

1. **🔴 ఫాస్ట్-గేట్ల విభజన ఇప్పటికీ నిర్మాణాత్మక లోటును మిగులుస్తోంది.** `quality.yml` (PR→`release/**`)
   ఇప్పుడు కోడ్ PRల కోసం typecheck, వేగవంతమైన డిటర్మినిస్టిక్ టెస్ట్లు మరియు సలహాత్మక ప్రొడక్షన్ బిల్డ్ను అమలు చేస్తుంది,
   కానీ ఇది ఇప్పటికీ `ci.yml`లోని పూర్తి release-PR పరిధిని (కవరేజ్ రాచెట్లు,
   ప్యాకేజ్ ఆర్టిఫాక్ట్, ఇంటిగ్రేషన్, E2E, SonarQube) అమలు చేయదు. ప్రేరణ (వేగం) సమంజసమే, కానీ గేట్
   మెర్జ్ జరిగే చోటే ఉండాలి (shift-left). **పెండింగ్లో ఉన్న అతిపెద్ద నిర్మాణాత్మక పరిష్కారం.**
2. **🟠 గేట్ల విస్తరణ/అలసట ప్రమాదం.** ~46 గేట్లు + 25 జాబ్లు చాలా ఎక్కువ. Sonar కూడా హెచ్చరిస్తుంది:
   చాలా ఎక్కువ షరతులు "గేట్ అలసట" మరియు ప్రాధాన్యతపై చర్చలకు దారితీస్తాయి, దీనివల్ల ఏదైనా గేట్
   విస్మరించబడే ప్రమాదం ఉంటుంది. భారీ గేట్లు లీడ్-టైమ్ను పెంచుతాయని DORA హెచ్చరిస్తుంది. సలహాత్మక స్థాయిలు మరియు
   సంపూర్ణం కాని రాచెట్లతో దీనిని తగ్గిస్తున్నాం, కానీ **ప్రతి గేట్కు ఆవర్తన ROI సమీక్ష** లేదు (doc-sync కోసం ఉన్న
   కొన్ని మైక్రో-గేట్లను ఏకీకృతం చేయవచ్చు).
3. **🟠 మ్యూటేషన్ స్కోర్ ఇంకా రాచెట్ కాలేదు.** కవరేజ్-గేమింగ్కు వ్యతిరేకంగా ఉన్న అత్యంత బలమైన విరుగుడు
   **సలహాత్మకం**గానే ఉంది. పెండింగ్లో ఉన్న అంశాల్లో దీనికే అత్యధిక విలువ ఉంది (ఇప్పటికే 90% నిర్మించబడింది).
4. **🟡 నిరోధకంగా మారాల్సిన సలహాత్మక గేట్లు (సరైన పరిధితో).** `osv` (vulnCount) మరియు `oasdiff`
   స్థిరీకరించిన బేస్లైన్లు ఉన్నప్పటికీ సలహాత్మకంగానే ఉన్నాయి. osv సలహాత్మకంగా ఉండటం సమంజసమే (పాత డిపెండెన్సీలో కొత్త CVE
   సంబంధంలేని PRను నిరోధించవచ్చు) — కానీ మధ్యేమార్గం ఉంది (Trivyతో చేసినట్లుగా CRITICAL+fixable మాత్రమే
   నిరోధించడం). oasdiff సలహాత్మకంగా ఉండటం వల్ల కాంట్రాక్ట్ను భంగపరిచే మార్పు పాస్ కావచ్చు.
5. **🟡 రన్టైమ్ భద్రత రాత్రివేళ మాత్రమే అమలవుతుంది.** schemathesis/garak/promptfoo/chaos/k6 రాత్రివేళ అమలవుతాయి.
   ఇది సరైన నిర్ణయం (నెమ్మదిగా ఉంటాయి, లైవ్ సర్వర్ అవసరం), కానీ ఒక PR ఇంజెక్షన్-గార్డ్ రిగ్రెషన్ను ప్రవేశపెట్టవచ్చు,
   అది తరువాతి రాత్రి మాత్రమే గుర్తించబడుతుంది.
6. **🟡 `main`పై బ్రాంచ్-ప్రొటెక్షన్ OFFలో ఉంది.** `BRANCH_LOCK_TOKEN` _release_ బ్రాంచ్లను లాక్ చేస్తుంది, కానీ
   `main`కు రక్షణ లేదు. Scorecard/DSOMMలో దీనికి ప్రతికూల మార్కులు పడతాయి. ఓనర్ చర్య అవసరం.
7. **🟡 CodeQL default-setup; semgrep నియమబద్ధీకరించబడలేదు.** default-setup పనిచేస్తోంది (0 అలర్ట్లు), కానీ
   కమిట్ చేసిన `codeql.yml` మరింత నియంత్రణను ఇస్తుంది; semgrep బాహ్య క్లౌడ్ ప్లాట్ఫామ్ ద్వారా అమలవుతుంది,
   రిపోజిటరీలో వెర్షన్ చేయబడలేదు.

## భాగం 3 — నాణ్యత తనిఖీ కేంద్రాల సంపూర్ణ జాబితా (పోర్టబుల్)

దిగువన ఉన్న 12 వర్గాలు పునర్వినియోగించగల రూపంలోని "నాణ్యత వ్యవస్థ". ప్రతిదానిలో
**లక్ష్యం** (దేనిని రక్షించాలి), **మేము ఉపయోగించే సాధనాలు**, అలాగే ఏ స్టాక్పైనైనా పునరావృతం చేయడానికి **సాధనంతో సంబంధం లేని సమాన విధానం**
జాబితా చేయబడ్డాయి.

### 1. శైలి & ఫార్మాటింగ్ (నిర్ణయాత్మకమైనది, వేగవంతమైనది)

- **OmniRoute:** lint-staged ద్వారా Prettier + ESLint (pre-commit), 2-స్పేసులు/డబుల్-కోట్లు/100col.
- **సాధారణం:** staged ఫైళ్లపై pre-commit సమయంలో అమలయ్యే, స్వయంచాలకంగా సరిచేయగల ఒక formatter + ఒక linter.

### 2. టైప్లు

- **OmniRoute:** `typecheck:core` (నిరోధించేది) + `typecheck:noimplicit:core` (సూచనాత్మకమైనది) + `type-coverage` రాచెట్ 92.17% + ప్రతి ఫైల్కు any-బడ్జెట్.
- **సాధారణం:** CIలో strict typecheck + రాచెట్ చేయబడిన type-coverage మెట్రిక్ + ప్రతి ఫైల్కు `any`/escape-hatch బడ్జెట్.

### 3. పరీక్షలు (తీవ్రత)

- **OmniRoute:** పరస్పరం అతివ్యాప్తి చెందని 2 runners (Node native + vitest), 8 shards, సమగ్ర coverage 60/60/60/60 + రాచెట్ ~76% + **కీలకమైన modules కోసం 8 ప్రతి-module కనిష్ఠ పరిమితులు** + రాత్రివేళ property tests + రాత్రివేళ **mutation testing**.
- **సాధారణం:** test runner(s) + **నిరపేక్ష** coverage కనిష్ఠ పరిమితి (సున్నాను నిరోధించేది) + coverage **రాచెట్** (తిరోగమనాన్ని నిరోధించేది) + **అధిక-ప్రమాద code కోసం ప్రతి-module కనిష్ఠ పరిమితులు** (Goodhart ప్రభావాన్ని నిరోధించేవి) + స్వచ్ఛమైన logic కోసం property-based పరీక్షలు + పరీక్ష నాణ్యతకు అసలైన కొలమానంగా రాత్రివేళ **mutation testing**.

### 4. పరీక్ష విధానం (మోసపూరిత అనుకూలీకరణ నిరోధం)

- **OmniRoute:** `pr-test-policy` (ఉత్పత్తి codeకు test తప్పనిసరి), `check-test-masking` (బలహీనపరచిన assertionsను నిరోధిస్తుంది), `pr-evidence` (విజయవంతమైందనే ప్రకటనకు evidence block అవసరం), `test-discovery` (ప్రతి testను ఒక runner సేకరిస్తుంది).
- **సాధారణం:** "కొత్త code ⇒ కొత్త test" gate + తొలగించిన assert/tautology detector + evidence ఆవశ్యకత (TDD లేదా సజీవ test) + globs వెలుపల ఏ test అనాథగా మిగలదనే హామీ.

### 5. సంక్లిష్టత & code ఆరోగ్యం (రాచెట్లు)

- **OmniRoute:** ESLint-warnings (3769↓), jscpd duplication (5.72%↓), cyclomatic+max-lines complexity (1800↓), cognitive complexity sonarjs (753↓), dead-code/unused-exports knip (339↓), ప్రతి ఫైల్కు file-size (స్థిరీకరించబడింది, తగ్గించడం మాత్రమే), circular-deps (custom Tarjan, నిరోధించేది).
- **సాధారణం:** ప్రతి ఆరోగ్య మెట్రిక్ను రాచెట్ చేయండి (warnings, duplication, cyclomatic **మరియు** cognitive complexity, dead code, file size, import cycles). దిశ ఎల్లప్పుడూ "తిరోగమించవద్దు".

### 6. స్థిర భద్రత (SAST + రహస్యాలు)

- **OmniRoute:** CodeQL (రాచెట్ alerts = 0), gitleaks (`[extend] useDefault=true` — అత్యంత కీలకం!), SonarQube, custom security rules (public-creds, error-helper, route-guard-membership, route-validation).
- **సాధారణం:** alert రాచెట్తో SAST (CodeQL/Sonar/semgrep) + **వారసత్వంగా పొందిన default ruleset** కలిగిన secrets scanner (defaultను override చేసే custom config = అంధత్వం) + ప్రాజెక్ట్కు నిర్దిష్టమైన Hard Rule security gates.

### 7. సరఫరా గొలుసు (dependencies)

- **OmniRoute:** osv-scanner + npm-audit + Trivy + Dependabot (SCA), license-checker (SPDX allowlist), lockfile-lint (HTTPS+sha512+registry), `check-deps` anti-slopsquatting (allowlist + వయస్సు ≥72h).
- **సాధారణం:** బహుళ-మూలాల SCA + license allowlist + lockfile సమగ్రత తనిఖీ + వయస్సు/typosquatting తనిఖీతో dependency allowlist + సమూహీకరించిన update bot.

### 8. సరఫరా గొలుసు (build & release)

- **OmniRoute:** SBOM (CycloneDX + syft), SLSA provenance (`--provenance`), OpenSSF Scorecard (వారానికొకసారి), workflow hardening (zizmor: artipacked→`persist-credentials:false`, cache-poisoning, token-permissions).
- **సాధారణం:** publish సమయంలో SBOMను రూపొందించండి + సంతకం చేసిన provenance (SLSA L2+) + షెడ్యూల్ చేసిన Scorecard + అన్ని workflowsను పటిష్ఠం చేయండి (కనిష్ఠ-అధికార tokens, non-pusher checkoutలో నిల్వచేసిన credentials ఉండకూడదు, actionsను SHA ద్వారా pin చేయాలి).

### 9. Contracts & API

- **OmniRoute:** oasdiff (breaking-change OpenAPI), schemathesis (రాత్రివేళ contract fuzz), openapi-coverage (% నమోదు చేయబడిన routes, రాచెట్ 38.3%), openapi-security-tiers (spec vs route-guard).
- **సాధారణం:** breaking-change contract diff (oasdiff/buf) + specకు వ్యతిరేకంగా property-based fuzz (schemathesis) + రాచెట్ చేయబడిన documentation coverage + spec↔code స్థిరత్వం.

### 10. Docs & i18n (క్షీణత నిరోధం)

- **OmniRoute:** docs-sync (ప్రతిబింబించిన versions), docs-counts-sync (docsలోని సంఖ్యలు vs code), env-doc-sync, doc-links, fabricated-docs, cli-i18n, i18n-ui-coverage (`--threshold=65` + రాచెట్ 80.1%).
- **సాధారణం:** docs మరియు code మధ్య versions/counts/env-varsను సమకాలీకరించండి (gate, నమ్మకం కాదు) + అంతర్గత linksను ధ్రువీకరించండి + రాచెట్ చేయబడిన i18n coverage.

### 11. భ్రమల నిరోధం / స్థిరత్వం (అరుదైన వర్గం)

- **OmniRoute:** known-symbols (string dispatch ⇒ సజీవ symbol), provider-consistency, fetch-targets (client fetch ⇒ నిజమైన route), docs-symbols, db-rules (Hard Rules #2/#5), migration-numbering.
- **సాధారణం:** ప్రతి "నకలు చేయబడిన సత్య మూలం" (registry, string dispatch, cross-layer references) కోసం, రెండు వైపులూ సరిపోలుతున్నాయని నిరూపించే gate ఉండాలి. typecheck/test గుర్తించలేని క్షీణతను ఇది గుర్తిస్తుంది.

### 12. స్థితిస్థాపకత & domain (ఉత్పత్తికి నిర్దిష్టమైనది)

- **OmniRoute:** chaos (fault-injection), heap-growth (leak), k6 (soak), promptfoo+garak (LLM red-team OWASP LLM Top 10), 3 resilience laws (circuit-breaker/cooldown/lockout).
- **సాధారణం:** **మీ** domainలోని failure modesను గుర్తించి, ప్రతిదానికీ ఒక gateను కలిగి ఉండండి (అది రాత్రివేళ మాత్రమే అమలైనా సరే). AI apps కోసం: injection red-team. distributed systems కోసం: chaos + leak + soak.

స్థిరపడిన తర్వాత **నిరోధకంగా** మారాలి.

### పునర్వినియోగ కేంద్రబిందువు: "ర్యాచెట్ గేట్ నిర్మాణం"

మొత్తం వ్యవస్థ ఈ 3-ఫైల్ నమూనా చుట్టూ తిరుగుతుంది. ముందుగా దీన్ని కాపీ చేయండి:

1. **`baseline.json`** — స్థిరీకరించిన మెట్రిక్ విలువ + `direction` (`up`/`down`) + `eps` (అస్థిరత-నిరోధకం) + `tightenSlack` + `dedicatedGate`.
2. **`collect-metrics.<ext>`** — సాధనాన్ని అమలు చేసి, సంఖ్యను సంగ్రహించి, `metrics.json`ను వ్రాస్తుంది.
3. **`check-ratchet.<ext>`** — `metrics.json`ను `baseline.json`తో పోలుస్తుంది; `eps`కు మించి తిరోగమించినప్పుడు **మాత్రమే** `exit 1`; సాధనం/మౌలిక సదుపాయం అందుబాటులో లేకపోతే `exit 0` (అడ్డంకిలేని దాటవేత); `--require-tighten`తో, బేస్లైన్ను నవీకరించకుండా అది **మెరుగుపడితే** `exit 1` (సాధించిన మెరుగుదలను స్థిరపరుస్తుంది).

ఇది అమల్లోకి వచ్చిన తర్వాత, **ప్రతి** కొత్త మెట్రిక్ (కవరేజ్, సంక్లిష్టత, హెచ్చరికలు, SAST అలర్ట్లు, బండిల్ పరిమాణం, మ్యూటేషన్ స్కోర్…) బేస్లైన్లో కేవలం ఒక పంక్తి మాత్రమే.

### దశ 0 — పునాది (1వ వారం)

CI అమల్లో ఉంటుంది; ఫార్మాటర్ + లింటర్ + టైప్చెక్ + 1 టెస్ట్ రన్నర్ + **సంపూర్ణ** కవరేజ్ కనిష్ఠ పరిమితి
(ఉదా., 60%). ప్రీ-కమిట్ వేగవంతమైన, స్వయంచాలకంగా సరిచేయగల తనిఖీలను అమలు చేస్తుంది. _ఫలితం: ఏ PR కూడా ప్రాథమిక అంశాలను దెబ్బతీయదు._

### దశ 1 — ర్యాచెట్ ఇంజిన్ (2వ వారం) — **ప్రతిదానికీ పునాది**

పైన పేర్కొన్న 3 ఫైళ్లను అమలు చేయండి. వీటికి బేస్లైన్లను స్థిరీకరించండి: హెచ్చరికలు, కవరేజ్, సంక్లిష్టత, నకిలీతనం,
డెడ్ కోడ్, ఫైల్ పరిమాణం. _ఫలితం: ఇకపై కోడ్బేస్ మెరుగుపడటం మాత్రమే సాధ్యం._

### దశ 2 — స్థిర విశ్లేషణ లోతు (3వ వారం)

అలర్ట్ ర్యాచెట్తో SAST (CodeQL/Sonar/semgrep); సీక్రెట్స్ స్కానర్ (**డిఫాల్ట్ నియమసమితిని వారసత్వంగా స్వీకరించండి**);
SCA (osv/Dependabot) + లైసెన్స్ అనుమతి జాబితా + lockfile-lint. _ఫలితం: తెలిసిన బలహీనతలు మరియు
బయటపడిన సీక్రెట్లు తనిఖీలను దాటవు._

### దశ 3 — బిల్డ్ సరఫరా గొలుసు (4వ వారం)

ప్రచురణ సమయంలో SBOM + సంతకం చేసిన మూలాధార ధృవీకరణ (SLSA L2) + షెడ్యూల్ చేసిన Scorecard + వర్క్ఫ్లో పటిష్ఠీకరణ
(zizmor: కనిష్ఠ టోకెన్లు, నిల్వ చేసిన క్రెడెన్షియల్లు ఉండకూడదు, పిన్ చేసిన చర్యలు). _ఫలితం: మూలాన్ని గుర్తించగలిగే,
తారుమారు చేయలేని విడుదలలు._

### దశ 4 — పరీక్ష తీవ్రత (5–6 వారాలు)

ఉపయోగకరమైతే 2వ రన్నర్; **కీలక మాడ్యూళ్ల కోసం ప్రతి-మాడ్యూల్ కవరేజ్ కనిష్ఠ పరిమితులు** (గుడ్హార్ట్-నిరోధకం);
స్వచ్ఛమైన లాజిక్ కోసం ప్రాపర్టీ-ఆధారిత పరీక్ష; **ప్రతి రాత్రి మ్యూటేషన్ టెస్టింగ్** → 1వ స్కోర్ వచ్చినప్పుడు,
`mutationScore`ను ర్యాచెట్గా మార్చండి. _ఫలితం: కవరేజ్ కేవలం ప్రదర్శనాత్మక మెట్రిక్గా ఉండదు; పరీక్షలు నిజంగా బగ్లను గుర్తిస్తాయని నిరూపితమవుతుంది._

### దశ 5 — కాంట్రాక్ట్ & డైనమిక్ (7వ వారం)

పబ్లిక్ API ఉంటే: oasdiff (బ్రేకింగ్-చేంజ్, **నిరోధకం**) + schemathesis (ప్రతి రాత్రి ఫజింగ్).
డొమైన్కు తగిన విధంగా ప్రతి రాత్రి DAST/రెడ్-టీమ్ పరీక్షలు. _ఫలితం: కాంట్రాక్ట్లు నిశ్శబ్దంగా విచ్ఛిన్నం కావు._

### దశ 6 — భ్రమ-నిరోధం & డొమైన్ (8వ వారం)

ప్రాజెక్ట్లోని ప్రతి "నకిలీ సత్యం" కోసం ఒక స్థిరత్వ గేట్. డొమైన్-నిర్దిష్ట వైఫల్య-రీతి
గేట్లు (AI కోసం: ఇంజెక్షన్ రెడ్-టీమ్). _ఫలితం: నిర్మాణాత్మక క్షీణత మరియు డొమైన్ వైఫల్యాలకు రక్షణ వలయం ఉంటుంది._

### దశ 7 — పాలన (నిరంతరం)

- ప్రతి కొత్త గేట్కు సలహాత్మకం→నిరోధకం చక్రం.
- `stale-allowlist`: ప్రతి మినహాయింపుకు సమర్థన + ఇష్యూ ఉండాలి; కాలం చెల్లిన మినహాయింపును గుర్తించాలి.
- `evidence-gate`: PRలో విజయవంతమైందనే దావాకు రుజువు (పరీక్ష లేదా సజీవ పరీక్ష) అవసరం.
- **ప్రతి గేట్పై త్రైమాసిక ROI సమీక్ష** (ప్రతిఫలం ఇవ్వని వాటిని తొలగించండి/నిధులు నిలిపివేయండి — ఇది అలసటను ఎదుర్కొంటుంది).
- మీ ప్రాజెక్ట్ యొక్క కఠిన నియమాలను అమలు చేయగల గేట్లుగా ఉన్నతీకరించండి.

### అన్ని దశలకు వర్తించే సూత్రాలు (చర్చకు తావులేనివి)

- **ర్యాచెట్, సంపూర్ణ పరిమితి కాదు.** స్థిర సంఖ్యను కాకుండా _తిరోగమించకపోవడాన్ని_ గేట్ చేయండి (శూన్య-నిరోధక కనిష్ఠ పరిమితులు మినహా).
- **సంపూర్ణ కనిష్ఠ పరిమితి + ర్యాచెట్ కలిపి.** కనిష్ఠ పరిమితి కుప్పకూలడాన్ని నివారిస్తుంది; ర్యాచెట్ నెమ్మదైన క్షీణతను నివారిస్తుంది.
- **రూపకల్పనలోనే గుడ్హార్ట్-నిరోధం.** ప్రతి లక్ష్య మెట్రిక్కు ఒక ప్రతిసమతుల్యం అవసరం (కవరేజ్ ⇒ మ్యూటేషన్ + మాస్కింగ్-నిరోధం; కష్టమైన కోడ్ను తప్పనిసరిగా పరీక్షించేలా ప్రతి-మాడ్యూల్ కనిష్ఠ పరిమితులు).
- **అడ్డంకిలేని దాటవేత.** అందుబాటులో లేని మౌలిక సదుపాయం ఎప్పుడూ నిరోధించదు; నిజమైన తిరోగమనం మాత్రమే నిరోధిస్తుంది.
- **ఖరీదైన మెట్రిక్ల కోసం `dedicatedGate`.** బాహ్య బైనరీ అవసరమైన మెట్రిక్లు, సమకాలిక కేంద్ర ర్యాచెట్ వెలుపల, దాటవేత సదుపాయంతో కూడిన సొంత స్క్రిప్ట్ను కలిగి ఉండాలి.
- **మెర్జ్ జరిగే చోటే గేట్ చేయండి.** వేగవంతమైన గేట్కు, వాస్తవ మెర్జ్కు మధ్య ఖాళీని వదలవద్దు (ఫాస్ట్-గేట్స్ విభజన నుంచి నేర్చుకున్న పాఠం).
- **తక్కువ సంఖ్యలో, చక్కగా ఎంచుకున్న నిరోధక గేట్లు.** Sonar/DORA: మరీ ఎక్కువ షరతులు = అలసట. నిరోధక గేట్ల గోడకు బదులుగా సలహాత్మక గేట్లు + ర్యాచెట్కు ప్రాధాన్యం ఇవ్వండి.

## భాగం 5 — సిఫార్సు చేసిన మెరుగుదలలు (ప్రాధాన్యత క్రమంలో, అనుకూలమైనవి)

**P0 — అత్యధిక ROI, దాదాపు సిద్ధం**

1. **మ్యూటేషన్ స్కోర్ రాచెట్** (మొదటి రాత్రివారీ Stryker విలువలను అందించిన తర్వాత). coverage-Goodhartకు వ్యతిరేకంగా కీలక విరుగుడు; ~90% పూర్తయింది.
2. **మిగిలిన ఫాస్ట్-గేట్స్ లోపాన్ని మూసివేయండి** — `quality.yml` ప్రొడక్షన్ బిల్డ్ను దాని
   సలహా వారాంతం తర్వాత ప్రమోట్ చేయండి, అలాగే నిర్ధారిత release-PR-only తనిఖీలను PR→release మార్గంలోకి తరలిస్తూ ఉండండి.
3. **`main`పై బ్రాంచ్ రక్షణ** (యజమాని సెట్టింగ్) — Scorecardను మెరుగుపరుస్తుంది, DSOMM లోటును పూడుస్తుంది.

**P1 — విలువైనవి** 4. **osv/oasdiff → సరైన పరిధితో బ్లాకింగ్** — osvలో CRITICAL+fixable మాత్రమే (Trivy మాదిరిగా రెండు దశల్లో); oasdiff బ్రేకింగ్ మార్పులను నిరోధిస్తుంది. 5. **`require-tighten` → బ్లాకింగ్** (సైకిల్ ముగింపులో) — మెట్రిక్ మెరుగుదలలను స్థిరపరుస్తుంది. 6. **`ci-summary`లో ఒక్కో గేట్కు ROI/టైమింగ్ సమీక్ష** — నెమ్మదైన/తక్కువ విలువ గల గేట్లను గుర్తించి తొలగించండి.

**P2 — తగ్గుతూ వచ్చే ప్రయోజనాలు** 7. **SLSA L3** — మీరు L2 నుంచి పైకి వెళ్లాలనుకుంటే హెర్మెటిక్/పునరుత్పాదక బిల్డర్ (GitHub SLSA generator). 8. **కమిట్ చేసిన CodeQL కాన్ఫిగ్ + వెర్షన్ చేసిన semgrep** — మరింత నియంత్రణ/పునరుత్పాదకత. 9. **ఒక్కో PRకు DAST స్మోక్** — అత్యధిక-ప్రమాదం గల ఎండ్పాయింట్లపై schemathesis/promptfoo యొక్క వేగవంతమైన ఉపసమితి (రాత్రివారీ మాత్రమే కాదు). 10. **ఫ్లేకీనెస్ డ్యాష్బోర్డ్ + DORA మెట్రిక్స్** — గేట్లు వేగాన్ని క్షీణింపజేయడం లేదని నిర్ధారించండి.

## భాగం 6 — నిర్దిష్ట రిలీజ్ పాఠాలు (Phase 9లో జోడించాల్సిన గేట్లు)

> రిలీజ్ ముగింపు ప్రక్రియల్లో ఒక గేట్ **లేకపోవడం** వల్ల జరిగిన వాస్తవ ఘటనలను,
> నిర్దిష్ట సాక్ష్యాలు మరియు ప్రతిపాదిత గేట్తో ఈ విభాగం నమోదు చేస్తుంది. ప్రతి అంశం భాగం 5లో చేర్చడానికి ఒక అభ్యర్థి.

### పాఠం v3.8.27 (2026-06-17) — "ఫాస్ట్-గేట్స్ లోపం" నిర్ధారిత రిగ్రెషన్లను రిలీజ్ రోజు వరకు చేరనిస్తుంది

**ఏం జరిగింది.** v3.8.27 `/generate-release` సమయంలో, రిలీజ్ PR (`release/v3.8.27` → `main`)
ఏకీకృత సైకిల్లో పూర్తి `ci.yml` మ్యాట్రిక్స్ను అమలు చేసిన **మొదటి** సందర్భం. ఫలితం: ఒకేసారి 12 వైఫల్యాలు
— **3 నిర్ధారిత పరీక్షలు** + ~9 ఫ్లేక్స్/ఎన్విరాన్మెంట్ సమస్యలు. ఏదీ సజీవ ప్రొడక్ట్ రిగ్రెషన్ కాదు, కానీ
సైకిల్ PRలు **Fast QG
(`quality.yml`)** ద్వారా `release/**`లోకి ప్రవేశించడం వల్ల అవన్నీ గుర్తించబడలేదు; ఇది పూర్తి యూనిట్ సూట్నూ, `pr-test-policy` (టెస్ట్-మాస్కింగ్)నూ, పూర్తి
ఇంటిగ్రేషన్ సూట్నూ, స్కీమా పారిటీ తనిఖీనీ అమలు చేయదు. ఆ 3 నిర్ధారిత సమస్యలు:

1. **UI మార్పుతో పాతబడిన పరీక్ష** — `permissions modal switch buttons declare button type`:
   #4034 నాలుగవ స్విచ్ను జోడించింది (a11y `type="button"` యథాతథంగా ఉంది); పరీక్షలోని `=== 3` లెక్క
   పాతబడింది. #4034 PRలోనే స్టాటిక్ విశ్లేషణ దీన్ని గుర్తించి ఉండాల్సింది.
2. **ప్యాకేజింగ్ మార్పుతో పాతబడిన పరీక్ష** — `findMissingArtifactPaths ... root runtime files`:
   `dist/http-method-guard.cjs` చెల్లుబాటు అయ్యే అవసరమైన పాత్గా మారింది; పరీక్షలోని అంచనా జాబితా
   పాతబడింది.
3. **నష్టదాయక మాడ్యులరైజేషన్ డైవర్జెన్స్ (అత్యంత తీవ్రమైనది)** — `settings schemas accept ... unprefixed
toggle`: **మాడ్యులరైజ్ చేసిన** `updateSettingsSchema` (`schemas/settings.ts`, #3988 ద్వారా సృష్టించబడింది)
   కానానికల్ దాని (`settingsSchemas.ts`) నుంచి భిన్నమైంది: **45 ఫీల్డ్లు vs 85 — 40 తొలగించబడ్డాయి + 6 భిన్నంగా ఉన్నాయి (qdrant\*)**. అది
   **డెడ్-కోడ్** (రన్టైమ్ కానానికల్ దానిని ఉపయోగిస్తుంది), కాబట్టి సజీవ ప్రభావం లేదు, కానీ చేతితో రాసిన పారిటీ
   పరీక్ష మాత్రమే దాన్ని గుర్తించింది. #4030, #3988/#3993 నుంచి అలానే తొలగిపోయిన 16 అంశాలను పునరుద్ధరించింది, కానీ ఇది తప్పించుకుంది.

**ప్రతిపాదిత గేట్లు (Phase 9):**

- **G1 — ఫాస్ట్-గేట్స్ లోపాన్ని నిజంగా మూసివేయండి (P0 #2 విస్తరణ).** `quality.yml`లో (PR→`release/**`),
  typecheck + ప్రభావిత పరీక్షలకు అదనంగా **`pr-test-policy` (టెస్ట్-మాస్కింగ్) + పూర్తి నిర్ధారిత
  యూనిట్ సూట్**ను అమలు చేయండి (లేదా కనీసం వేగవంతమైన, ఫ్లేకీ కాని స్టాటిక్/పారిటీ ఫైళ్లను).
  ఈ విధంగా, పాతబడిన పరీక్షలు మరియు assert తొలగింపు వాటిని ప్రవేశపెట్టే PRలోనే గుర్తించబడతాయి — రిలీజ్
  రోజున కాదు. integration/e2eను బయటే ఉంచండి (నెమ్మది/ఫ్లేకీ), కానీ నిర్ధారిత లేయర్ PR→mainలో
  మాత్రమే ఉండకూడదు.
- **G2 — మాడ్యులరైజేషన్ పారిటీ గేట్ (కొత్తది, ప్రస్తుతం కవర్ కాలేదు).** మాడ్యులరైజ్ చేసిన బ్యారెల్ ద్వారా
  రీ-ఎక్స్పోర్ట్ చేసే ప్రతి సింబల్కు (`src/shared/validation/schemas/*`, `providerRegistry`
  మాడ్యూల్స్ మొదలైనవి), కానానికల్ సోర్స్తో **ఆకృతిని** (`z.object` కీలు, రిజిస్ట్రీ ఎంట్రీలు) పోల్చి,
  **డైవర్జెన్స్పై విఫలమయ్యే** తనిఖీ (తొలగించిన/అదనపు ఫీల్డ్). #3988 వల్ల తొలగిన 40 ఫీల్డ్లను
  అదే PRలో ఇది గుర్తించి ఉండేది. చేతితో రాసిన పారిటీ పరీక్షలను ఇది సాధారణీకరిస్తుంది (వాటిని రాయాలని
  ఎవరికైనా గుర్తున్న చోట్ల మాత్రమే ప్రస్తుతం అవి ఉన్నాయి). చౌకైనది: రెండింటినీ ఇంపోర్ట్ చేసి `Object.keys(shape)` మధ్య తేడాను కనుగొంటుంది.
- **G3 — నిర్ధారిత ఫ్లేక్ ట్రయాజ్ (మద్దతు).** LiveWS-startup మరియు integration-combo/breaker
  పరీక్షలు CIలో సర్వర్ టైమ్అవుట్/కాస్కేడ్ (ఎన్విరాన్మెంట్) వల్ల విఫలమవుతాయి, లాజిక్ వల్ల కాదు. వీటిని
  `known-flaky`గా (సమస్యతో పాటు క్వారంటైన్ చేసి) గుర్తించండి, తద్వారా release-PRలోని ఎరుపు **నిజమైన సంకేతాలను మాత్రమే** సూచిస్తుంది; మధ్యలోని
  నిర్ధారిత రిగ్రెషన్లను కప్పిపుచ్చే శబ్దాన్ని కాదు.

**సూత్రం:** _మెర్జ్ జరిగే చోటే గేట్ అమలు కావాలి_ (ఇది ఇప్పటికే "Cross-cutting principles"లో ఉంది).
v3.8.27 ఘటన, ఇది lint/typecheckకే కాకుండా **నిర్ధారిత టెస్ట్ లేయర్కు** కూడా వర్తిస్తుందని చూపిస్తుంది —
లేకపోతే పాతబడిన పరీక్షలు + నష్టదాయక మాడ్యులరైజేషన్ ఋణం PR→mainలో మాత్రమే, సమూహంగా, అత్యంత
అననుకూల సమయంలో బయటపడుతుంది.
