## జానిటర్ను ఇన్స్టాల్ చేయండి (ఒకసారి మాత్రమే, బాక్స్పై)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): ప్రతి 30 నిమిషాలకు, /var/log/runner-janitor.logలో లాగ్ చేయండి
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` అవసరం: ఏదైనా పాత్ను తొలగించే ముందు, తెరిచి ఉన్న ఫైళ్లకు సంబంధించిన ఒక స్నాప్షాట్తో అది నిష్క్రియంగా ఉందని జానిటర్ నిర్ధారిస్తుంది; ఈ సాధనం లేకపోతే అది ఏదీ తొలగించదు, ఆ విషయాన్ని తెలియజేస్తుంది
(exit 1). ఏ మార్పునైనా ముందుగా `--dry-run`తో ప్రయత్నించండి — అది ఏమి చేయబోతుందో యథాతథంగా ముద్రిస్తుంది
మరియు దేనినీ తాకదు.

ప్రతి రన్లో ఇది చేసే పని: మన స్వంత మిగులు ఫైళ్లను (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) **tmpfsపై 3 గం.** తర్వాత, డిస్క్లోని
`_work/_temp`లో 24 గం. తర్వాత తొలగిస్తుంది; 75 నిమిషాల కంటే పాత `next-build`ను నిలిపివేస్తుంది (ఏ జాబ్ కూడా అంతసేపు నడవదు — 2026-08-27న GitHub దాని జాబ్ పోయిందని ప్రకటించిన తర్వాత కూడా ఒకటి 70 నిమిషాలు నడిచింది); యూనిట్ **ఆపివేయబడిన** రన్నర్లకు చెందిన 48 గం. పాత
చెక్అవుట్లను తొలగిస్తుంది; డిస్క్ ≥ 85 %, మెమరీ PSI
`full/avg60` ≥ 10 %, అలాగే `MAX_ACTIVE_RUNNERS` కంటే ఎక్కువ లిసనర్లు ఉన్నప్పుడు హెచ్చరిస్తుంది (omniroute/ఇతర విభజనతో). Exit 1 = శ్రద్ధ అవసరం; లాగ్ను చదవండి.

## రన్నర్ యూనిట్లు: KillMode

రన్నర్ డిఫాల్ట్ `KillMode=process`, ఒక యూనిట్ను నిలిపివేసినప్పుడు లేదా పునఃప్రారంభించినప్పుడు `Runner.Worker → npm → next-build`ను సజీవంగానే ఉంచుతుంది — అనుబంధ జాబ్ లేని అనాథ బిల్డ్ RAM మరియు CPUని వినియోగిస్తూనే ఉంటుంది. ప్రతి OmniRoute యూనిట్లో
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
వద్ద `KillMode=mixed`తో ఒక డ్రాప్-ఇన్ ఉంటుంది: మొదట లిసనర్కు SIGTERM, ఆపై
`TimeoutStop` వద్ద మొత్తం cgroupకు SIGKILL. యూనిట్ తదుపరి పునఃప్రారంభంలో ఇది అమల్లోకి వస్తుంది — **ఒకేసారి ఒక రన్నర్ను మాత్రమే, అది నిష్క్రియంగా ఉన్నప్పుడు మాత్రమే** పునఃప్రారంభించండి; నిష్క్రియ తనిఖీ మరియు పునఃప్రారంభం ఒకే కమాండ్లో ఉండాలి.

## నిర్వహణ నియమాలు

- **భారీ-బిల్డ్ పరిమితి: ఒకేసారి ఒక్కటి — లేబుల్ ద్వారా అమలు చేయబడుతోంది (2026-08-29 నుండి).** పూర్తి `next build`ను అమలు చేసే ప్రతి జాబ్ `[self-hosted, omni-build]`ను లక్ష్యంగా చేసుకుంటుంది, మరియు ఆ లేబుల్ను కలిగి ఉన్నది **`omniroute-113-5`** మాత్రమే (రన్నర్స్ API ద్వారా జోడించబడింది — మళ్లీ నమోదు చేయలేదు): `ci.yml`లోని `Build`, `npm-publish.yml`లోని `publish`, రెండు `nightly-release-green` ధ్రువీకరణలు, మరియు `docker-publish.yml`లోని **amd64** (ఈ ట్రీ కోసం హోస్టెడ్ 7 GBలో ResourceExhausted సంభవించింది — #11976). arm64 Docker లెగ్ webpackతో `ubuntu-24.04-arm`లోనే ఉంటుంది (ARM బాక్స్ లేదు). Docker amd64 కూడా webpackనే ఉపయోగిస్తుంది: 31 GB ఉన్నప్పటికీ ఈ ట్రీపై Turbopack, BuildKitలో (`TurbopackInternalError:
there must be a path to a root`, రన్ 33253576569) పానిక్ అయింది; అదే ట్రీకి చెందిన arm64 webpack బిల్డ్ హోస్టెడ్ ARMపై విజయవంతమైంది. `docker-publish` amd64, `ci.yml`లోని `Build`తో `heavy-build-main` కాంకరెన్సీ గ్రూప్ను పంచుకుంటుంది (`cancel-in-progress: false`), కాబట్టి అది అందుబాటులో ఉన్న ఒక్క స్లాట్ కోసం క్యూలో వేచి ఉంటుంది. Docker Engine తప్పనిసరిగా `omniroute-113-5`లో ఉండాలి (`docker info` అనేది పబ్లిష్ జాబ్లోని మొదటి దశ). ఇంతకుముందు పరిమితి రెండు ఉండేది, కానీ 31 GBకి అది సరైనది కాదు: 2026-08-29 17:26 UTCన ఏకకాలంలో నడిచిన రెండు `next-build`లు (15.4 GB + 17.2 GB RSS) బాక్స్లో ఖాళీ మెమరీని 5 GBకి తగ్గించాయి, 4 GB swap వినియోగంలోకి వచ్చింది, మరియు కర్నెల్ వాటిలో ఒకదాన్ని OOM-kill చేసింది — systemd ఆ కిల్ను _మరొక_ రన్నర్ యూనిట్పై నమోదు చేసింది, `runsvc.sh` ఆ లిసనర్ను SIGKILL చేసింది, మరియు దానిపై ఉన్న జాబ్ "The runner has received a shutdown signal" అనే సందేశంతో నిలిచిపోయింది (హోస్టెడ్-రన్నర్ OOMలోనూ ఇదే సందేశం వస్తుంది). `omniroute-113-6`లో `omni-release` మాత్రమే ఉంటుంది. `main` మెర్జ్లు, PRలు మరియు నైట్లీ నుంచి వచ్చే భారీ బిల్డ్లు ఇప్పుడు ఒకే స్లాట్పై వరుసగా నడుస్తాయి; క్యూ దీనికి చెల్లించాల్సిన మూల్యం. Proxmox VMకి మరింత RAM (48–64 GB) లభించిన రోజున రెండో స్లాట్ తిరిగి వస్తుంది:
