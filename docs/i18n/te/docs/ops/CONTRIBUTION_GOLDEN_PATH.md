పుల్ రిక్వెస్ట్ కోసం అత్యంత చిన్నదైన, విశ్వసనీయ డెవలప్మెంట్ లూప్ను ఎంచుకోవడానికి ఈ మార్గదర్శిని ఉపయోగించండి. ఇది దిగువ లింక్ చేసిన విభాగ-నిర్దిష్ట ఆర్కిటెక్చర్ మరియు భద్రతా పత్రాలకు ప్రత్యామ్నాయం కాదు; ప్రతి సాధారణ మార్పు రకాన్ని దాని ఒప్పందాలు, కేంద్రీకృత తనిఖీలు మరియు CI కవరేజ్తో అనుసంధానిస్తుంది.

## ప్రతి మార్పు అనుసరించే మార్గం

1. **సవరించే ముందు బేస్ను ఎంచుకోండి.** అత్యధిక క్రియాశీల `release/v*` బ్రాంచ్ను కనుగొని, దాని తాజా కమిట్ నుండి బ్రాంచ్ను సృష్టించండి. `main`ను కాకుండా ఆ బ్రాంచ్ను లక్ష్యంగా చేసుకోండి. రిలీజ్ ఫ్రీజ్ అమల్లో ఉంటే, ఫ్రీజ్ చేసిన బ్రాంచ్ను లక్ష్యంగా చేసుకోవద్దు; [బ్రాంచింగ్ & రిలీజ్ మోడల్](BRANCHING_MODEL.md)లో వివరించిన తదుపరి క్రియాశీల సైకిల్ను ఉపయోగించండి.
2. **ఒప్పందాలను పేర్కొనండి.** మార్పు ప్రభావితం చేసే ప్రతి కేటలాగ్, స్కీమా, జనరేట్ చేసిన ఆర్టిఫాక్ట్, పబ్లిక్ API లేదా వినియోగదారు ఇంటర్ఫేస్ను గుర్తించండి. దిగువ పట్టిక కనీస ప్రారంభ సమితిని అందిస్తుంది.
3. **కేంద్రీకృత పరీక్షలను రాయండి లేదా నవీకరించండి.** `src/`, `open-sse/`, `electron/` లేదా `bin/`లోని ప్రొడక్షన్ మార్పులకు అదే PRలో ఆటోమేటెడ్ పరీక్ష అవసరం. ప్రవర్తనను నిరూపించే అత్యంత చిన్న పరీక్ష ఫైళ్లను అమలు చేసి, ఆ తర్వాత జాబితా చేసిన కేంద్రీకృత గేట్లను అమలు చేయండి.
4. **విస్తృత మ్యాట్రిక్స్ను CI అమలు చేయనివ్వండి.** పూర్తి యూనిట్ షార్డ్లు, Vitest, కవరేజ్ రాచెట్ మరియు ప్రొడక్షన్ బిల్డ్ PRపై అమలవుతాయి. కేంద్రీకృత వైఫల్యం విస్తృత ప్రభావాన్ని సూచించినప్పుడు లేదా మార్పు అనేక ఉపవ్యవస్థల్లో విస్తరించినప్పుడు మాత్రమే విస్తృత సూట్ను లోకల్గా అమలు చేయండి.
5. **రివ్యూకు ముందు సమన్వయం చేయండి.** క్రియాశీల బేస్ను fetch చేసి, దాని కొత్త కమిట్లను మరియు దానితో పోల్చిన మీ diffను పరిశీలించి, ఆపై కంట్రిబ్యూటర్ వర్క్ఫ్లో ప్రకారం బేస్ను rebase లేదా merge చేయండి. జనరేట్ చేసిన ఫైల్ మరియు కేటలాగ్ వైరుధ్యాలను వాటి మూలం నుంచే పరిష్కరించి, వాటిని మళ్లీ జనరేట్ చేసి, కేంద్రీకృత లూప్ను తిరిగి అమలు చేయండి మరియు PR ఇప్పటికీ క్రియాశీల రిలీజ్ బ్రాంచ్నే లక్ష్యంగా చేసుకుంటోందని నిర్ధారించండి.
6. **ఆధారాలను నమోదు చేయండి.** PR టెంప్లేట్లో అమలు చేసిన కమాండ్లు, జోడించిన లేదా మార్చిన ప్రతి పరీక్ష ఫైల్, మైగ్రేషన్లు లేదా ఫీచర్ ఫ్లాగ్లు మరియు ఇంకా పెండింగ్లో ఉన్న ఏవైనా CI-మాత్రమే ధ్రువీకరణలను జాబితా చేయండి.

## మార్పు రకం వారీగా గోల్డెన్ పాత్లు

దిగువ కమాండ్లు కనీస కేంద్రీకృత తనిఖీలు మాత్రమే; మీరు మార్చిన ప్రవర్తనను నేరుగా కవర్ చేసే పరీక్షను దాటవేయడానికి ఇవి అనుమతి కావు.

### ప్రొవైడర్

**ఒప్పందాలు**

- `src/shared/constants/providers/`లోని ప్రొవైడర్ నిర్వచనం మరియు `src/shared/constants/providers.ts`లో దాని కంపోజిషన్.
- `open-sse/config/providerRegistry.ts`లో లేదా దాని నుంచి వేరు చేసిన రిజిస్ట్రీ ఫైళ్లలోని మోడల్లు మరియు సామర్థ్యాలు.
- వర్తించే చోట ఎగ్జిక్యూటర్/ట్రాన్స్లేటర్ ఎంపిక, OAuth లేదా API-కీ కాన్ఫిగరేషన్, డాష్బోర్డ్ అసెట్లు మరియు జనరేట్ చేసిన ప్రొవైడర్ రిఫరెన్స్.
- పబ్లిక్ క్రెడెన్షియల్లు తప్పనిసరిగా `resolvePublicCred()`ను ఉపయోగించాలి; లోప ప్రతిస్పందనలు తప్పనిసరిగా షేర్ చేసిన శానిటైజ్డ్ ఎరర్ హెల్పర్లను ఉపయోగించాలి. `docs/security/PUBLIC_CREDS.md` (gitలో ఉంటుంది; `/docs`లోకి కంపైల్ చేయబడదు) మరియు [ఎరర్ శానిటైజేషన్](../security/ERROR_SANITIZATION.md) చూడండి.

**కేంద్రీకృత లూప్**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # కేటలాగ్ మారినప్పుడు; జనరేట్ చేసిన diffను commit చేయండి
npm run lint
```

ప్రభావితమైన ప్రతి రిక్వెస్ట్ ఫ్యామిలీని కూడా పరీక్షించండి: chat, Responses, images, embeddings, audio లేదా video. జనరేట్ చేసిన కేటలాగ్ మరియు గోల్డెన్ diffలను ఒప్పంద మార్పులుగా రివ్యూ చేయండి; వాటిని గుడ్డిగా అంగీకరించవద్దు.

### రూటింగ్

**ఒప్పందాలు**

- `src/shared/constants/routingStrategies.ts`లోని పబ్లిక్ స్ట్రాటజీ విలువలు మరియు UI మెటాడేటా.
- `open-sse/services/combo.ts` మరియు `open-sse/services/combo/` కింద ఉన్న డిస్పాచ్ మరియు క్రమం.
- కాంబో స్కీమాలు, పర్సిస్టెన్స్, రెసిలియెన్స్ స్థితి, మోడల్ సామర్థ్యాలు మరియు API/UI నియంత్రణలు.
- ప్రవర్తన మారినప్పుడు [ఆటో-కాంబో ఇంజిన్](../routing/AUTO-COMBO.md) మరియు రెసిలియెన్స్ డాక్యుమెంటేషన్.

**కేంద్రీకృత లూప్**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # స్ట్రాటజీ లేదా డిస్పాచ్ మార్పులు
npm run check:known-symbols      # స్ట్రాటజీ రిజిస్ట్రేషన్ మార్పులు
npm run lint
```

లోకల్గా నిర్ధారిత ఫలితాలను ఇచ్చే మాక్ చేసిన అప్స్ట్రీమ్ పరీక్షలను ఉపయోగించండి. లైవ్ కాంబో స్మోక్ పరీక్షలకు క్రెడెన్షియల్లు అవసరం మరియు అవి మాన్యువల్గా నిర్వహించాలి; అవి CIకి ప్రత్యామ్నాయాలు కావు.

### UI / UX

**ఒప్పందాలు**

- `src/app/` మరియు `src/shared/components/` కింద ఉన్న Next.js రూట్/పేజీ మరియు షేర్ చేసిన కాంపోనెంట్ సరిహద్దులు.
- API ప్రతిస్పందన ఆకృతులు, లోడింగ్/ఖాళీ/లోప స్థితులు, కీబోర్డ్ మరియు స్క్రీన్-రీడర్ ప్రవర్తన, రెస్పాన్సివ్ లేఅవుట్, థీమింగ్ మరియు లోకేల్ విస్తరణ.
- `src/i18n/messages/en.json`లోని ఇంగ్లీష్ UI సోర్స్ స్ట్రింగ్లు; వినియోగదారుకు కనిపించే కొత్త పాఠ్యాన్ని హార్డ్-కోడ్ చేయవద్దు.

**కేంద్రీకృత లూప్**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

ఇంటరాక్షన్ లేదా విజువల్ మార్పుల కోసం యాప్ను అమలు చేసి, ఇరుకైన మరియు వెడల్పైన వ్యూపోర్ట్లు రెండింటినీ తనిఖీ చేయండి. CI ప్రొడక్షన్ బిల్డ్ మరియు విస్తృత సూట్లను అమలు చేస్తుంది; అయినప్పటికీ విజువల్ ప్రవర్తనకు మార్పుకు తగిన కేంద్రీకృత కాంపోనెంట్ పరీక్ష, Playwright పరీక్ష లేదా డాక్యుమెంట్ చేసిన మాన్యువల్ తనిఖీ అవసరం.

### i18n

**ఒప్పందాలు**

- `src/i18n/messages/en.json` UI సోర్స్; `config/i18n.json` లోకేల్ సోర్స్.
- CLI కేటలాగ్లు `bin/cli/locales/` కింద విడిగా ఉంటాయి.

**కేంద్రీకృత లూప్**

```bash
npm run lint
```

ఇది ఇప్పటికే ఉన్న సిస్టమ్కు సంబంధించిన మార్గదర్శకం మాత్రమే; దాని టూలింగ్ లేదా కీ మోడల్ను విస్తరించడానికి ఆహ్వానం కాదు. ప్రత్యామ్నాయ సిస్టమ్ను రూపొందిస్తున్న సమయంలో i18n ప్యాచ్లను నిర్దిష్ట మార్పులకే పరిమితం చేయండి. టాస్క్కు జనరేట్ చేసిన అనువాదాలు స్పష్టంగా అవసరమైతే మరియు ఫలితంగా వచ్చిన diffను మీరు రివ్యూ చేసి ఉంటే తప్ప, బాహ్య సేవలను కాల్ చేసే అనువాద కమాండ్లను అమలు చేయవద్దు.

### CLI

## స్థానిక candidate లూప్

ప్యాకేజ్ చేసిన artifact బూట్ అవుతుందని source tests నిరూపించలేవు: packaging lists, తొలగించబడిన dependencies,
మరియు native binaries వంటి వాటిలోని లోపాలు tarballను ఇన్స్టాల్ చేసి ప్రారంభించిన తర్వాత మాత్రమే బయటపడతాయి. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) అనేది RFC #8084లోని build-once / validate / promote ప్రవాహానికి స్థానిక భాగం:
ఇది ఒక candidateను build చేసి, అదే artifactను validate చేసి, directory పేర్లను మార్చడం ద్వారా దాన్ని
promote చేస్తుంది; promote చేసిన slot health checkలో విఫలమైతే దాన్ని rollback చేస్తుంది.

```bash
npm run dev:candidate -- run --dry-run --json  # ప్రణాళికను ప్రదర్శించు, ఏదీ మార్చవద్దు
npm run dev:candidate -- run                   # build + validate + promote, స్వయంచాలక rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/లోకి ఇన్స్టాల్
npm run dev:candidate -- validate --id <id>    # ఖాళీ portపై బూట్ చేసి, /api/health + /v1/models తనిఖీ
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current మరియు previousలను పరస్పరం మార్చు
npm run dev:candidate -- run --from-tarball <file.tgz>  # మరెక్కడైనా (CI) build చేసిన tarballను తిరిగి ఉపయోగించు
```

- **ఒక్కసారి build చేయండి.** `build` ప్రస్తుత treeను pack చేస్తుంది (దీనికి `dist/server.js` అవసరం, కాబట్టి ముందుగా
  `npm run build:release` అమలు చేయండి) లేదా `--from-tarball`ను copy చేసి, ఆపై tarballను
  వేరుచేసిన npm prefixలో ఇన్స్టాల్ చేస్తుంది, ఎందుకంటే tarballలో `node_modules` ఉండదు. id అనేది సంక్షిప్త `HEAD`
  sha (treeలో స్థానిక మార్పులు ఉంటే `-dirty`) లేదా tarball కోసం `tgz-<sha256>`. ఇప్పటికే build చేయబడిన clean idను
  మళ్లీ build చేయకుండా తిరిగి ఉపయోగిస్తుంది; దాన్ని మళ్లీ build చేయడానికి `--force`ను పంపండి.
- **Sourceను కాకుండా packageను validate చేయండి.** `validate`, తాజాగా సృష్టించిన
  `DATA_DIR=<candidate>/data`, నకిలీ secretsతో ఇన్స్టాల్ చేసిన CLIని (`serve --port <free port>`) ప్రారంభిస్తుంది;
  అలాగే operator యొక్క `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` మరియు `INITIAL_PASSWORD`లను environment
  నుండి తొలగిస్తుంది, తద్వారా fresh install యొక్క keyless loopback postureను తనిఖీ చేస్తుంది. ఇది
  `GET /api/health` 200ను అందించే వరకు వేచి ఉండి, `GET /v1/models` తప్పనిసరిగా 200ను అందించాలని నిర్ధారించి,
  process groupను ఆపి, tarball hashతో పాటు ఫలితాన్ని `validation.json`లో నమోదు చేస్తుంది.
- **అదే artifactను promote చేయండి.** ప్రస్తుత tarball hash కోసం విజయవంతమైన validation లేని candidateను
  `promote` తిరస్కరిస్తుంది. డిఫాల్ట్ active slot `_artifacts/candidate/current`; `--target <dir>`
  అదే filesystemలోని మరొక directoryని ఎంచుకుంటుంది, దాని previous slot `<dir>.previous`.
  ప్రతి rename atomicగా జరుగుతుంది; మధ్యలో వైఫల్యం సంభవిస్తే, అప్పటికే జరిగిన renameలను వెనక్కి మారుస్తుంది.
- **Rollback చేయండి.** `run` promote చేసిన slotను మళ్లీ validate చేస్తుంది; ఆ తనిఖీ విఫలమైతే
  `current` మరియు `previous`లను తిరిగి పరస్పరం మారుస్తుంది. మొదటి validationలో విఫలమైన candidate ఎప్పటికీ
  promote చేయబడదు.

ప్రతిదీ gitignored `_artifacts/candidate/` కింద వ్రాయబడుతుంది; ఇప్పటికే ఉన్న OmniRoute
installation మరియు దాని data directory ఎప్పటికీ మార్చబడవు. Promote చేసిన CLI
`_artifacts/candidate/current/prefix/bin/omniroute`; దాన్ని ఉపయోగించేటప్పుడు మీ స్వంత `DATA_DIR`తో
ప్రారంభించండి. Exit codes: `0` విజయం, `1` validation లేదా promotion వైఫల్యం, `2` usage error లేదా build లేకపోవడం.

గ్రీన్గా ఉన్న కేంద్రీకృత లూప్, మార్చిన కాంట్రాక్ట్కు సంబంధించిన ఆధారం మాత్రమే; సంబంధంలేని CI తనిఖీలు
పాస్ అవుతాయని అది రుజువు చేయదు. అదే విధంగా, ప్రతి స్థానిక సవరణను పూర్తి రిపోజిటరీ మ్యాట్రిక్స్ కోసం వేచి ఉండేలా చేయవద్దు.

## సమన్వయ చెక్లిస్ట్

సమీక్షను అభ్యర్థించే ముందు:

- PR బేస్ ఇప్పటికీ అత్యున్నత సక్రియ `release/v*` బ్రాంచ్గా ఉందని నిర్ధారించండి.
- ఆ బేస్ను ఫెచ్ చేసి, మీరు బ్రాంచ్ సృష్టించినప్పటి నుంచి చేరిన కమిట్లను సమీక్షించండి.
- అనుకోకుండా జరిగిన లేదా జనరేట్ చేయబడిన మార్పుల కోసం `git diff <active-base>...HEAD`ను సమీక్షించండి.
- మూలాన్ని అప్డేట్ చేసి, అవుట్పుట్ను మళ్లీ జనరేట్ చేయడం ద్వారా కాటలాగ్ మరియు జనరేట్ చేయబడిన డాక్యుమెంట్ ఘర్షణలను పరిష్కరించండి.
- సమన్వయం తర్వాత PR వివరణలో పేర్కొన్న ప్రతి కేంద్రీకృత పరీక్ష/గేట్ను మళ్లీ అమలు చేయండి.
- మారిన బేస్కు సరిపోల్చడం కోసమే అసర్షన్లను ఎప్పుడూ బలహీనపరచవద్దు లేదా అవసరమైన పరీక్షలను తొలగించవద్దు.

రిలీజ్-ఫ్రీజ్ మరియు రీటార్గెటింగ్ నియమాల కోసం,
[బ్రాంచింగ్ & రిలీజ్ మోడల్](BRANCHING_MODEL.md)ను ఉపయోగించండి. పూర్తి CI జాబితా కోసం,
[నాణ్యత గేట్ల సూచన](../architecture/QUALITY_GATES.md)ను ఉపయోగించండి.
