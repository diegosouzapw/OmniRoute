పుల్ రిక్వెస్ట్ కోసం అత్యంత చిన్నదైన, నమ్మదగిన డెవలప్మెంట్ లూప్ను ఎంచుకోవడానికి ఈ మార్గదర్శకాన్ని ఉపయోగించండి. ఇది దిగువన లింక్ చేసిన విభాగ-నిర్దిష్ట ఆర్కిటెక్చర్ మరియు భద్రతా పత్రాలకు
ప్రత్యామ్నాయం కాదు; ప్రతి సాధారణ మార్పు రకాన్ని దాని కాంట్రాక్ట్లు, కేంద్రీకృత తనిఖీలు మరియు CI కవరేజ్తో అనుసంధానిస్తుంది.

## ప్రతి మార్పు అనుసరించే మార్గం

1. **సవరించే ముందు బేస్ను ఎంచుకోండి.** అత్యధిక క్రియాశీల `release/v*` బ్రాంచ్ను కనుగొని, దాని
   తాజా కమిట్ నుండి బ్రాంచ్ను సృష్టించండి. `main`ను కాకుండా, ఆ బ్రాంచ్ను లక్ష్యంగా పెట్టుకోండి. రిలీజ్ ఫ్రీజ్ అమల్లో ఉంటే, ఫ్రీజ్ చేసిన
   బ్రాంచ్ను లక్ష్యంగా పెట్టుకోవద్దు; [Branching & Release Model](BRANCHING_MODEL.md)లో వివరించిన
   తదుపరి క్రియాశీల సైకిల్ను ఉపయోగించండి.
2. **కాంట్రాక్ట్లను పేర్కొనండి.** మార్పు ప్రభావితం చేసే ప్రతి కేటలాగ్, స్కీమా, జనరేట్ చేసిన ఆర్టిఫ్యాక్ట్, పబ్లిక్ API లేదా వినియోగదారు
   ఇంటర్ఫేస్ను గుర్తించండి. దిగువ పట్టిక కనీస ప్రారంభ సమితిని అందిస్తుంది.
3. **కేంద్రీకృత పరీక్షలను వ్రాయండి లేదా నవీకరించండి.** `src/`, `open-sse/`, `electron/` లేదా
   `bin/`లోని ప్రొడక్షన్ మార్పులకు అదే PRలో ఆటోమేటెడ్ పరీక్ష అవసరం. ప్రవర్తనను నిరూపించే అత్యంత చిన్న
   పరీక్ష ఫైళ్లను అమలు చేసి, ఆపై జాబితాలోని కేంద్రీకృత గేట్లను అమలు చేయండి.
4. **విస్తృత మ్యాట్రిక్స్ను CI అమలు చేయనివ్వండి.** పూర్తి యూనిట్ షార్డ్లు, Vitest, కవరేజ్ రాచెట్ మరియు
   ప్రొడక్షన్ బిల్డ్ PRపై అమలవుతాయి. కేంద్రీకృత వైఫల్యం విస్తృత ప్రభావాన్ని సూచించినప్పుడు లేదా మార్పు అనేక
   ఉపవ్యవస్థలకు విస్తరించినప్పుడు మాత్రమే విస్తృత సూట్ను లోకల్గా అమలు చేయండి.
5. **రివ్యూకు ముందు సమన్వయం చేయండి.** క్రియాశీల బేస్ను ఫెచ్ చేసి, దాని కొత్త కమిట్లను మరియు దానితో పోల్చిన మీ డిఫ్ను
   పరిశీలించి, ఆపై కంట్రిబ్యూటర్ వర్క్ఫ్లో ప్రకారం బేస్ను రీబేస్ లేదా మెర్జ్ చేయండి. జనరేట్ చేసిన ఫైల్
   మరియు కేటలాగ్ కాన్ఫ్లిక్ట్లను వాటి సోర్స్ వద్ద పరిష్కరించి, వాటిని మళ్లీ జనరేట్ చేసి, కేంద్రీకృత లూప్ను తిరిగి అమలు చేసి,
   PR ఇప్పటికీ క్రియాశీల రిలీజ్ బ్రాంచ్నే లక్ష్యంగా చేసుకుందని నిర్ధారించండి.
6. **ఆధారాలను నమోదు చేయండి.** PR టెంప్లేట్లో, అమలు చేసిన కమాండ్లు, జోడించిన లేదా మార్చిన ప్రతి పరీక్ష ఫైల్,
   మైగ్రేషన్లు లేదా ఫీచర్ ఫ్లాగ్లు మరియు ఇంకా పెండింగ్లో ఉన్న ఏవైనా CI-మాత్రమే వాలిడేషన్లను జాబితా చేయండి.

## మార్పు రకం వారీగా గోల్డెన్ పాత్లు

దిగువ కమాండ్లు కనీస కేంద్రీకృత తనిఖీలు మాత్రమే; మీరు మార్చిన ప్రవర్తనను నేరుగా కవర్ చేసే పరీక్షను
దాటవేయడానికి ఇవి అనుమతి కావు.

### ప్రొవైడర్

**కాంట్రాక్ట్లు**

- `src/shared/constants/providers/`లోని ప్రొవైడర్ నిర్వచనం మరియు
  `src/shared/constants/providers.ts`లో దాని కంపోజిషన్.
- `open-sse/config/providerRegistry.ts` లేదా దాని నుండి వేరు చేసిన రిజిస్ట్రీ ఫైళ్లలోని మోడల్లు మరియు సామర్థ్యాలు.
- వర్తించే సందర్భంలో ఎగ్జిక్యూటర్/ట్రాన్స్లేటర్ ఎంపిక, OAuth లేదా API-కీ కాన్ఫిగరేషన్, డ్యాష్బోర్డ్ అసెట్లు మరియు జనరేట్ చేసిన
  ప్రొవైడర్ రిఫరెన్స్.
- పబ్లిక్ క్రెడెన్షియల్లు తప్పనిసరిగా `resolvePublicCred()`ను ఉపయోగించాలి; ఎర్రర్ రెస్పాన్స్లు తప్పనిసరిగా షేర్ చేసిన శానిటైజ్డ్
  ఎర్రర్ హెల్పర్లను ఉపయోగించాలి. `docs/security/PUBLIC_CREDS.md` (git; `/docs`లోకి కంపైల్ చేయబడదు) మరియు
  [ఎర్రర్ శానిటైజేషన్](../security/ERROR_SANITIZATION.md) చూడండి.

**కేంద్రీకృత లూప్**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # కేటలాగ్ మారినప్పుడు; జనరేట్ చేసిన డిఫ్ను కమిట్ చేయండి
npm run lint
```

ప్రభావితమైన ప్రతి రిక్వెస్ట్ ఫ్యామిలీని కూడా పరీక్షించండి: చాట్, Responses, ఇమేజ్లు, ఎంబెడ్డింగ్లు, ఆడియో లేదా వీడియో.
జనరేట్ చేసిన కేటలాగ్ మరియు గోల్డెన్ డిఫ్లను కాంట్రాక్ట్ మార్పులుగా రివ్యూ చేయండి; వాటిని గుడ్డిగా అంగీకరించవద్దు.

### రూటింగ్

**కాంట్రాక్ట్లు**

- `src/shared/constants/routingStrategies.ts`లోని పబ్లిక్ స్ట్రాటజీ విలువలు మరియు UI మెటాడేటా.
- `open-sse/services/combo.ts` మరియు `open-sse/services/combo/` కింద డిస్పాచ్ మరియు క్రమం.
- కాంబో స్కీమాలు, పర్సిస్టెన్స్, రెసిలియెన్స్ స్థితి, మోడల్ సామర్థ్యాలు మరియు API/UI నియంత్రణలు.
- ప్రవర్తన మారినప్పుడు [Auto-Combo Engine](../routing/AUTO-COMBO.md) మరియు రెసిలియెన్స్ డాక్యుమెంటేషన్.

**కేంద్రీకృత లూప్**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # స్ట్రాటజీ లేదా డిస్పాచ్ మార్పులు
npm run check:known-symbols      # స్ట్రాటజీ రిజిస్ట్రేషన్ మార్పులు
npm run lint
```

లోకల్గా నిర్ధారణాత్మకమైన మాక్డ్-అప్స్ట్రీమ్ పరీక్షలను ఉపయోగించండి. లైవ్ కాంబో స్మోక్ పరీక్షలకు క్రెడెన్షియల్లు అవసరం మరియు అవి
మాన్యువల్గా నిర్వహించాలి; అవి CIకి ప్రత్యామ్నాయాలు కావు.

### UI / UX

**కాంట్రాక్ట్లు**

- `src/app/` మరియు `src/shared/components/` కింద Next.js రూట్/పేజ్ మరియు షేర్ చేసిన కాంపోనెంట్ సరిహద్దులు.
- API రెస్పాన్స్ ఆకృతులు, లోడింగ్/ఖాళీ/ఎర్రర్ స్థితులు, కీబోర్డ్ మరియు స్క్రీన్-రీడర్ ప్రవర్తన,
  రెస్పాన్సివ్ లేఅవుట్, థీమింగ్ మరియు లోకేల్ విస్తరణ.
- `src/i18n/messages/en.json`లోని ఆంగ్ల UI సోర్స్ స్ట్రింగ్లు; కొత్త వినియోగదారు-అభిముఖ కాపీని హార్డ్-కోడ్ చేయవద్దు.

**కేంద్రీకృత లూప్**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

ఇంటరాక్షన్ లేదా విజువల్ మార్పుల కోసం యాప్ను అమలు చేసి, సన్నని మరియు వెడల్పైన వ్యూపోర్ట్లు రెండింటినీ తనిఖీ చేయండి. CI
ప్రొడక్షన్ బిల్డ్ మరియు విస్తృత సూట్లను అమలు చేస్తుంది; విజువల్ ప్రవర్తనకు ఇప్పటికీ మార్పుకు తగిన కేంద్రీకృత కాంపోనెంట్, Playwright
లేదా డాక్యుమెంట్ చేసిన మాన్యువల్ తనిఖీ అవసరం.

### i18n

**కాంట్రాక్ట్లు**

- `src/i18n/messages/en.json` UI సోర్స్; `config/i18n.json` లోకేల్ సోర్స్.
- CLI కేటలాగ్లు `bin/cli/locales/` కింద విడిగా ఉంటాయి.
- ICU ప్లేస్హోల్డర్లు మరియు ట్యాగ్లను యథాతథంగా ఉంచండి. ప్రొడక్ట్/ప్రొవైడర్/మోడల్ పేర్లు,
  ప్రోటోకాల్ మరియు హెడర్ పేర్లు, కమాండ్లు, కోడ్/JSON ఐడెంటిఫయర్లు, URLలు, ఎన్విరాన్మెంట్ వేరియబుల్లు లేదా
  `OmniRoute`, `OAuth`, `MCP` మరియు `A2A` వంటి రక్షిత పదాలను అనువదించవద్దు. ప్రస్తుత సోర్స్ జాబితా
  `scripts/i18n/glossary/protected-terms.json`.

**కేంద్రీకృత లూప్**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI స్ట్రింగ్లు/కేటలాగ్లు మారినప్పుడు
npm run lint
```

ఇది ప్రస్తుత సిస్టమ్కు సంబంధించిన మార్గదర్శకత్వం మాత్రమే; దాని టూలింగ్ లేదా కీ మోడల్ను విస్తరించడానికి ఆహ్వానం కాదు.
ప్రత్యామ్నాయ సిస్టమ్ రూపకల్పనలో ఉన్నంతకాలం i18n ప్యాచ్లను పరిమితంగా, లక్ష్యితంగా ఉంచండి. టాస్క్ స్పష్టంగా జనరేట్ చేసిన అనువాదాలను
కోరకపోతే మరియు ఫలితంగా వచ్చిన డిఫ్ను మీరు రివ్యూ చేయకపోతే, బాహ్య సర్వీస్లను కాల్ చేసే అనువాద
కమాండ్లను అమలు చేయవద్దు.

### CLI

**కాంట్రాక్ట్లు**

- `bin/cli/`లోని పబ్లిక్ కమాండ్లు మరియు ఫ్లాగ్లు, రూపొందించిన API కమాండ్లు, నిష్క్రమణ కోడ్లు, stdout/stderr మరియు
  JSON అవుట్పుట్ ఆకృతులు, కాన్ఫిగరేషన్/ఎన్విరాన్మెంట్ ప్రవర్తన, అలాగే ప్యాకేజ్ చేసిన ఫైల్లు.
- CLI వినియోగదారుకు కనిపించే స్ట్రింగ్లు తప్పనిసరిగా CLI i18n లేయర్ను ఉపయోగించాలి మరియు `en`/`pt-BR` కేటలాగ్లు సమకాలీకరించబడి ఉండాలి.
- మద్దతు ఉన్న రన్టైమ్గా Nodeను మరియు ప్రచురించిన బైనరీ కాంట్రాక్ట్ను యథాతథంగా ఉంచండి.

**కేంద్రీకృత లూప్**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # రూపొందించిన/బండిల్ చేసిన CLI మార్పులు
npm run check:pack-policy     # ప్యాకేజ్ ఉపరితల మార్పులు
npm run lint
```

ప్రవర్తన పార్సింగ్, ఫైల్లు లేదా నిష్క్రమణ స్థితిపై ఆధారపడినప్పుడు, తాత్కాలిక డేటా డైరెక్టరీలో ఖచ్చితమైన కమాండ్ను ఉపయోగించండి. CI మరింత విస్తృతమైన ప్యాకేజ్ ఆర్టిఫాక్ట్ మరియు ఎకోసిస్టమ్ తనిఖీలను నిర్వహిస్తుంది.

### డేటాబేస్

**కాంట్రాక్ట్లు**

- `src/lib/db/` కింద డొమైన్ మాడ్యూల్లు; నిర్దిష్ట మాడ్యూల్లను నేరుగా ఇంపోర్ట్ చేయండి (పాత `localDb.ts` రీ-ఎక్స్పోర్ట్ లేయర్ తొలగించబడింది).
- `src/lib/db/migrations/` కింద సంఖ్యా క్రమంలో ఉన్న, ఐడెంపోటెంట్ SQL మైగ్రేషన్లు, ట్రాన్సాక్షన్ భద్రత, అప్గ్రేడ్
  ప్రవర్తన, ఇండెక్స్లు మరియు స్కీమా ద్వారా ప్రభావితమయ్యే ప్రతి కాలర్.
- రూట్లు మరియు హ్యాండ్లర్లు ఎప్పుడూ నేరుగా ముడి SQLను అమలు చేయవు.

**కేంద్రీకృత లూప్**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

మైగ్రేషన్ను జోడించేటప్పుడు కొత్త డేటాబేస్ను మరియు మునుపటి స్కీమా నుండి అప్గ్రేడ్ను రెండింటినీ పరీక్షించండి. డేటాబేస్ పరీక్షలు తప్పనిసరిగా హ్యాండిల్లను మూసివేయాలి మరియు క్లీనప్ సమయంలో `resetDbInstance()`ను కాల్ చేయాలి. బెస్ట్-ఎఫర్ట్ Bun అడాప్టర్ పాత్ మారినప్పుడు మాత్రమే `npm run test:bun:db`ను అమలు చేయండి; Node ప్రామాణిక ఆధారంగా కొనసాగుతుంది.

### బిల్డ్ / డిప్లాయ్

**కాంట్రాక్ట్లు**

- రూట్ మరియు వర్క్స్పేస్ మానిఫెస్ట్లు/లాక్ఫైల్, `scripts/build/`, Next.js స్టాండలోన్ అసెంబ్లీ, `dist/`
  ప్యాకేజ్ కంటెంట్లు, Electron ప్లాట్ఫారమ్ మెటాడేటా, CI వర్క్ఫ్లోలు మరియు డిప్లాయ్మెంట్ సెంటినెల్లు.
- మద్దతు ఉన్న Node పరిధులు మరియు `CLAUDE.md`లో అనుమతి జాబితాలో ఉన్న Bun వినియోగం యథాతథంగా ఉండాలి.
- బిల్డ్ ఆర్టిఫాక్ట్లు ట్రాక్ చేయకుండా ఉంటాయి; డిపెండెన్సీ, లైసెన్స్, వర్క్ఫ్లో మరియు ప్యాకేజ్ విధానాలు వర్తిస్తాయి.

**కేంద్రీకృత లూప్**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # డిపెండెన్సీ లేదా లాక్ఫైల్ మార్పులు
npm run check:pack-policy      # ప్రచురించిన ప్యాకేజ్ ఉపరితల మార్పులు
npm run lint
```

మార్పు కంపైలేషన్, స్టాండలోన్ అసెంబ్లీ, అసెట్లు లేదా రన్టైమ్ బండ్లింగ్ను ప్రభావితం చేసినప్పుడు మాత్రమే స్థానికంగా `npm run build`ను ఉపయోగించండి. విడుదల/డిప్లాయ్ ధ్రువీకరణ కోసం మాత్రమే `npm run build:release`ను ఉపయోగించండి. CI బిల్డ్ తుది క్రాస్-ప్లాట్ఫారమ్ సంకేతం; ప్లాట్ఫారమ్-నిర్దిష్ట Electron మార్పులకు సంబంధిత కేంద్రీకృత బిల్డ్ లేదా స్మోక్ ఆధారం అవసరం.

## స్థానిక లూప్ మరియు CI మధ్య తేడా

| ప్రతి ప్యాచ్ కోసం స్థానికంగా అమలు చేయాల్సినవి                                   | విస్తృత సంకేతాన్ని అందించే CI                                                      |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| పైన పేర్కొన్న ప్రత్యక్ష ప్రవర్తన పరీక్షలు మరియు వర్గ గేట్లు                     | విభజించబడిన పూర్తి యూనిట్ సూట్ మరియు సీరియల్ పరీక్షలు                              |
| `npm run lint`                                                                  | Vitest సూట్లు మరియు కవరేజ్/నాణ్యత రాచెట్లు                                         |
| ప్రభావిత కాంట్రాక్ట్ కోరినప్పుడు మాత్రమే టైప్చెక్ లేదా బిల్డ్                   | ప్రొడక్షన్ బిల్డ్, భద్రత, డాక్స్, డిపెండెన్సీ మరియు PR-విధాన గేట్లు                |
| ఆటోమేషన్ ప్రవర్తనను నిరూపించలేనప్పుడు మాత్రమే మాన్యువల్ ఇంటరాక్షన్/లైవ్ తనిఖీలు | వర్క్ఫ్లో ద్వారా కాన్ఫిగర్ చేసిన క్రాస్-జాబ్ ఇంటిగ్రేషన్ మరియు ప్లాట్ఫారమ్ తనిఖీలు |

విజయవంతమైన కేంద్రీకృత లూప్ అనేది మార్చిన కాంట్రాక్ట్కు సంబంధించిన ఆధారం మాత్రమే; సంబంధం లేని CI తనిఖీలు
విజయవంతమవుతాయనడానికి అది రుజువు కాదు. అదే విధంగా, ప్రతి స్థానిక మార్పు పూర్తి రిపోజిటరీ మ్యాట్రిక్స్ కోసం వేచి ఉండేలా చేయవద్దు.

## సమన్వయ తనిఖీ జాబితా

సమీక్షను అభ్యర్థించే ముందు:

- PR బేస్ ఇప్పటికీ అత్యున్నత క్రియాశీల `release/v*` బ్రాంచ్గా ఉందని నిర్ధారించండి.
- ఆ బేస్ను ఫెచ్ చేసి, మీరు బ్రాంచ్ను సృష్టించిన తర్వాత విలీనం చేసిన కమిట్లను సమీక్షించండి.
- అనుకోకుండా లేదా జనరేట్ అయిన అనవసర మార్పుల కోసం `git diff <active-base>...HEAD`ను సమీక్షించండి.
- మూలాన్ని అప్డేట్ చేసి, అవుట్పుట్ను మళ్లీ జనరేట్ చేయడం ద్వారా కేటలాగ్ మరియు జనరేట్ చేసిన డాక్యుమెంట్ వైరుధ్యాలను పరిష్కరించండి.
- సమన్వయం తర్వాత PR వివరణలో పేర్కొన్న ప్రతి కేంద్రీకృత పరీక్ష/గేట్ను మళ్లీ అమలు చేయండి.
- మారిన బేస్కు సరిపోల్చడం కోసం మాత్రమే అసర్షన్లను ఎప్పుడూ బలహీనపరచవద్దు లేదా అవసరమైన పరీక్షలను తొలగించవద్దు.

రిలీజ్-ఫ్రీజ్ మరియు రీటార్గెటింగ్ నియమాల కోసం,
[బ్రాంచింగ్ & రిలీజ్ మోడల్](BRANCHING_MODEL.md)ను ఉపయోగించండి. పూర్తి CI జాబితా కోసం,
[నాణ్యత గేట్ల సూచన](../architecture/QUALITY_GATES.md)ను ఉపయోగించండి.
