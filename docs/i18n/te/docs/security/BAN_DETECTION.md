OmniRoute, ప్రొవైడర్ **ఖాతా శాశ్వతంగా పనిచేయని స్థితిలో ఉంది** (సస్పెండ్ చేయబడింది /
నిష్క్రియం చేయబడింది / ToS ఉల్లంఘన కారణంగా నిషేధించబడింది) అని సూచించే సంకేతాల కోసం అప్స్ట్రీమ్ లోప ప్రతిస్పందనలను
స్కాన్ చేస్తుంది; సరిపోలిక కనుగొనబడినప్పుడు, ఆ కనెక్షన్ను **టెర్మినల్ `banned` స్థితి**లోకి
మారుస్తుంది, తద్వారా అది ఇకపై అభ్యర్థనల కోసం ఎంపిక చేయబడదు. **Security → Banned Keywords**
సెట్టింగ్ల కార్డ్ కాన్ఫిగర్ చేసేది ఇదే ("శాశ్వత ఖాతా
నిషేధ గుర్తింపును ప్రేరేపించే అదనపు కీవర్డ్లు. అంతర్నిర్మిత కీవర్డ్లు ఎల్లప్పుడూ వర్తిస్తాయి.").

ఈ పేజీ అంతర్నిర్మిత జాబితా, గుర్తింపు ప్రవాహం, దాని పరిధి, అనుకూల
కీవర్డ్లను సురక్షితంగా ఎలా జోడించాలి, అలాగే ఫ్లాగ్ చేయబడిన కనెక్షన్ను ఎలా పునరుద్ధరించాలి అనే అంశాలను వివరిస్తుంది. టెర్మినల్
స్థితి కూడా స్థితిస్థాపకత నమూనాలో భాగమే — [RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md)
("టెర్మినల్ స్థితులు") చూడండి.

**ప్రామాణిక మూలం:** `open-sse/services/accountFallback.ts`
(`ACCOUNT_DEACTIVATED_SIGNALS`, `getMergedBannedSignals()`, `isAccountDeactivated()`).

## అంతర్నిర్మిత కీవర్డ్లు

అనుకూల జాబితాతో సంబంధం లేకుండా, ఈ 8 ఉపస్ట్రింగ్లు ఎల్లప్పుడూ వర్తిస్తాయి (అక్షరాల కేసును పట్టించుకోకుండా):

```
account_deactivated
account has been deactivated
account has been disabled
your account has been suspended
this account is deactivated
verify your account to continue                                 (Antigravity / Google Cloud Code)
this service has been disabled in this account for violation    (Antigravity)
this service has been disabled in this account                  (Antigravity)
```

> ప్రొవైడర్లు తమ నిషేధ పదజాలాన్ని మార్చే కొద్దీ ఈ జాబితా కూడా మారుతుంది. అధికారిక
> కాపీ `open-sse/services/accountFallback.ts`లోని `ACCOUNT_DEACTIVATED_SIGNALS`;
> పైన ఉన్న బ్లాక్ను ఒక స్నాప్షాట్గా పరిగణించండి.

అదే ఫైల్లో పక్కపక్కనే ఉన్న రెండు **వేర్వేరు** సంకేత పట్టికలు నిషేధిత-కీవర్డ్
గుర్తింపులో భాగం _కావు_:

- `CREDITS_EXHAUSTED_SIGNALS` — బిల్లింగ్/కోటా అయిపోయింది (`insufficient_quota`,
  `credit_balance_too_low`, `payment required`, …) → టెర్మినల్ `credits_exhausted`.
- `OAUTH_INVALID_TOKEN_SIGNALS` — **నాన్-టెర్మినల్**; టోకెన్ రిఫ్రెష్ ద్వారా పునరుద్ధరించవచ్చు.

గమనిక: **`rate limit`** / `429` వంటి సాధారణ తాత్కాలిక పదబంధాలు
రేట్-లిమిట్ / కనెక్షన్-కూల్డౌన్ మార్గం ద్వారా నిర్వహించబడతాయి మరియు అవి నిషేధ సంకేతాలు **కావు**.

## గుర్తింపు ప్రవాహం

```
అప్స్ట్రీమ్ లోప ప్రతిస్పందన
  → బాడీని స్ట్రింగ్గా మార్చి + చిన్న అక్షరాలకు మార్చడం
  → isAccountDeactivated(body): getMergedBannedSignals().some(sig => body.includes(sig))   [ఉపస్ట్రింగ్ సరిపోలిక]
  → సరిపోలిక ఉందా?
      → కనెక్షన్ testStatus = "banned"      (శాశ్వతం — 1-సంవత్సరం కూల్డౌన్, స్వయంచాలకంగా ఎప్పటికీ పునరుద్ధరించబడదు)
      → `autoDisableBannedAccounts` సెట్టింగ్ ఆన్లో ఉండి, `autoDisableBannedScope`
        ఈ కనెక్షన్ను కలిగి ఉంటే (`all`, లేదా OAuth/cookie/session కోసం `subscription`)
        → అదనంగా isActive = false. స్కోప్
        `subscription`గా ఉన్నప్పుడు ప్రీపెయిడ్ API కీలు యాక్టివ్గానే ఉంటాయి.
      → ఖాతా ఎంపిక సమయంలో కనెక్షన్ దాటవేయబడుతుంది (కాంబో QUOTA_BLOCKING స్థితులు)
```

- ఈ సరిపోలిక అనేది ప్రతిస్పందన **బాడీ**పై జరిగే **అక్షరాల కేసును పట్టించుకోని ఉపస్ట్రింగ్**
  శోధన (`isAccountDeactivated`, `accountFallback.ts`).
- నిషేధ-సంకేత బాడీ ఏ **HTTP స్థితి** వద్ద ఉన్నా శాశ్వత `banned` టెర్మినలైజేషన్
  అమలవుతుంది (`markAccountUnavailable` → `checkFallbackError` ద్వారా). మరింత
  పరిమితమైన **`deactivated`** లేబుల్ (కనెక్షన్కు అదనపు API కీలు లేనప్పుడు
  `isActive=false`) ఇన్లైన్ `chatCore.ts` మార్గం ద్వారా **HTTP 401 / 403** వద్ద
  వ్రాయబడుతుంది (`classifyProviderError` → `ACCOUNT_DEACTIVATED` ద్వారా వర్గీకరించబడుతుంది). అదే
  `ACCOUNT_DEACTIVATED` సంకేతానికి `markAccountUnavailable()` మార్గం
  (`resolveTerminalConnectionStatus` ద్వారా) _వేరొక_ టెర్మినల్ స్థితిని —
  **`expired`** — వ్రాస్తుందని గమనించండి; అందువల్ల ప్రతిస్పందనను ఏ మార్గం నిర్వహించిందనే దానిపై ఆధారపడి
  అదే నిషేధం `deactivated` లేదా `expired`గా కనిపించవచ్చు. (పాత
  కోడ్ వ్యాఖ్యలో "401 బాడీలో ఈ స్ట్రింగ్లు ఉన్నప్పుడు" అని ఉంది — అది
  ప్రస్తుత ప్రవర్తనను పూర్తిగా వివరించదు.)
- టెర్మినల్ స్థితులను ఫిల్టర్ చేసే ప్రతి చోటా `banned` కనెక్షన్ ఎంపిక నుండి
  మినహాయించబడుతుంది (`isTerminalConnectionStatus`, కాంబో `QUOTA_BLOCKING_CONNECTION_STATUSES`).

## పరిధి — ఏ ప్రొవైడర్లు స్కాన్ చేయబడతారు

**అన్ని ప్రొవైడర్లు.** విఫలమైన ప్రతి అప్స్ట్రీమ్ అభ్యర్థన ప్రవహించే సాధారణ ఎర్రర్-హ్యాండ్లింగ్ పైప్లైన్లో ఈ తనిఖీ నడుస్తుంది — ఇది OAuth/సబ్స్క్రిప్షన్ స్క్రేపర్లకు **మాత్రమే** పరిమితం కాదు. ఫలితంగా వచ్చే టెర్మినల్ స్థితి ప్రతి **కనెక్షన్కి** వర్తిస్తుంది, ప్రతి ప్రొవైడర్కి కాదు.

అయితే, అంతర్నిర్మిత _స్ట్రింగ్లు_ నిజమైన బ్యాన్ ప్రమాదం ఉన్న సబ్స్క్రిప్షన్/OAuth ప్రొవైడర్లను (ChatGPT Web Codex, Claude Web, Codex, Muse Spark, Antigravity) దృష్టిలో ఉంచుకుని రూపొందించబడ్డాయి. API-key ప్రొవైడర్ ఎర్రర్ బాడీలో సబ్స్ట్రింగ్లలో ఒకటి అక్షరాలా ఉంటేనే డిటెక్టర్ ట్రిగ్గర్ అవుతుంది.

`autoDisableBannedScope` (`all` | `subscription`, డిఫాల్ట్ `all`) ఒక సరిపోలిక `isActive=false`గా కూడా మార్చాలా వద్దా అనేది నియంత్రిస్తుంది. `subscription` అంటే లాగిన్-శైలి సీట్లు (వెబ్-కుకీ సెషన్లతో సహా చెల్లింపు సబ్స్క్రిప్షన్లు మరియు ఉచిత ఖాతాలు). ప్రీపెయిడ్ API కీల కోసం ఇది ఇప్పటికీ `testStatus=banned`ను నమోదు చేస్తుంది, కానీ వాటిని రౌటింగ్ పూల్లోనే ఉంచుతుంది. దీర్ఘకాలిక రూపకల్పన అనేది ప్రతి ప్రొవైడర్ మరియు ప్రతి ఖాతాకు ఒక ఓవర్రైడ్; గ్లోబల్ enum మొదటి అమలు.

## అనుకూల బ్యాన్ కీవర్డ్లు

**Security → Banned Keywords**లో కీవర్డ్లను జోడించండి లేదా తొలగించండి (`PATCH /api/settings` ద్వారా గ్లోబల్ `customBannedSignals` సెట్టింగ్గా నిల్వ చేయబడతాయి). అవి అంతర్నిర్మిత జాబితాకు **జోడించబడతాయి** — ఎప్పటికీ దానికి ప్రత్యామ్నాయం కావు — మరియు సేవ్ చేసినప్పుడు (అలాగే స్టార్టప్ సమయంలో) `setCustomBannedSignals()` ద్వారా హాట్-రీలోడ్ అవుతాయి. ప్రతి కీవర్డ్ గరిష్ఠంగా 200 అక్షరాలకు పరిమితం చేయబడుతుంది; అర్రే పొడవుకు పరిమితి లేదు.

**⚠ తప్పుడు-పాజిటివ్ ప్రమాదం — నిర్దిష్ట పదబంధాలను ఎంచుకోండి.** డిటెక్షన్ అనేది మొత్తం రెస్పాన్స్ బాడీపై చేసే ముడి సబ్స్ట్రింగ్ సరిపోలిక, మరియు ఒక సరిపోలిక **శాశ్వతం** (1-సంవత్సరం కూల్డౌన్, మాన్యువల్ రికవరీ). విస్తృతమైన కీవర్డ్ పూర్తిగా ఆరోగ్యంగా ఉన్న కనెక్షన్ను బ్యాన్ చేయవచ్చు:

- **చెడు:** `quota`, `limit`, `error`, `denied` — అనేక తాత్కాలిక ఎర్రర్లలో కనిపిస్తాయి.
- **మంచిది:** పూర్తి బ్యాన్ వాక్యాలు, ఉదా. `your account has been suspended for`,
  `account permanently banned`, `violation of our terms`.

నిజమైన బ్యాన్ వచ్చినప్పుడు ప్రొవైడర్ తిరిగి ఇచ్చే అత్యంత పొడవైన, సందిగ్ధతలేని పదబంధానికి ప్రాధాన్యం ఇవ్వండి. సందేహం ఉంటే, ముందుగా కనెక్షన్ యొక్క `lastError`ను గమనించి, తర్వాత ఖచ్చితమైన పదప్రయోగాన్ని జోడించండి.

## ఫ్లాగ్ చేయబడిన కనెక్షన్ను పునరుద్ధరించడం

టెర్మినల్ `banned` / `deactivated` స్థితులు **ఎప్పటికీ స్వయంచాలకంగా పునరుద్ధరించబడవు** (అవి ప్రోయాక్టివ్-రికవరీ టిక్ నుండి మినహాయించబడతాయి — `unavailable` కూల్డౌన్లు మాత్రమే వాటంతట అవే పునరుద్ధరించబడతాయి). ఒక ఆపరేటర్ వాటిని స్పష్టంగా క్లియర్ చేయాలి:

1. **కనెక్షన్ను మళ్లీ పరీక్షించండి** — డ్యాష్బోర్డ్ **Test** చర్య
   (`POST /api/providers/{id}/test`); విజయవంతమైన ప్రోబ్ `testStatus`ను
   `active`కు రీసెట్ చేసి, ఎర్రర్ ఫీల్డ్లను క్లియర్ చేస్తుంది.
2. **మళ్లీ ప్రామాణీకరించండి / క్రెడెన్షియల్లను సవరించండి** — OAuth ప్రొవైడర్ల కోసం, లాగిన్
   / రిఫ్రెష్ ప్రవాహాన్ని మళ్లీ అమలు చేయండి; ప్రొవైడర్ create/import రూట్లు `isActive = true`గా సెట్ చేస్తాయి.
3. **కనెక్షన్ను మళ్లీ ప్రారంభించండి** — ఆటో-డిసేబుల్ `isActive = false`గా సెట్ చేసి ఉంటే
   (`all` పరిధి, లేదా OAuth/cookie/session కనెక్షన్కు `subscription`),
   ఖాతాను సరిచేసిన తర్వాత దాన్ని తిరిగి ఆన్ చేయండి.

ప్రత్యేకమైన "clear ban flag" బటన్ లేదు — పునరుద్ధరణ అంటే సాధారణ టెర్మినల్-స్థితి నియమానికి అనుగుణంగా రీ-టెస్ట్, రీ-ఆత్ లేదా రీ-ఎనేబుల్ చేయడం; వివరాలకు
[RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) చూడండి.

## ప్రోబ్ ఐసోలేషన్ (మోడల్ test-all)

`runAsProbe`లో అమలు చేయబడే **ప్రోబ్-మూల వైఫల్యం** (మోడల్ test-all / హెల్త్-చెక్ డిస్పాచ్లు) కనెక్షన్ను పూల్ నుండి ఎప్పటికీ తొలగించదు (#9817): అది **కనిపించేలా నమోదు చేయబడుతుంది** (`last_error`, `last_error_type`, `error_code`,
`last_error_at`), కానీ **ప్రతి** రౌటింగ్ మ్యూటేషన్ను దాటవేస్తుంది — కూల్డౌన్లు, టెర్మినల్ స్థితి (`banned` / `deactivated` / `credits_exhausted`), ప్రతి-మోడల్ లాకౌట్లు, ప్రొవైడర్ సర్క్యూట్ బ్రేకర్, 5-నిమిషాల కోటా క్యాష్, OAuth టోకెన్ రిఫ్రెష్ మరియు ఆటో-డిసేబుల్. నిజమైన రిక్వెస్ట్-పాత్ వైఫల్యం మాత్రమే డీయాక్టివేట్ చేస్తుంది. కనెక్షన్ ట్రాఫిక్కు సేవలందిస్తూ ఉండగానే, నమోదు చేసిన ఎర్రర్ వల్ల ఫ్లాగ్ చేయబడిన ఖాతా డ్యాష్బోర్డ్లో కనిపిస్తుంది.

ఏకైక నిర్ణయ బిందువు `shouldIsolateProbeFailures()`
(`src/shared/utils/probeOrigin.ts`); ప్రోబ్-మూల వైఫల్యం కారణంగా రౌటింగ్ స్థితిని మార్చగల **ప్రతి** చోట ఇది సంప్రదించబడుతుంది:

- `markAccountUnavailable` (`auth.ts`) — నమోదు మాత్రమే (`lastError` ముడి టెక్స్ట్,
  `lastErrorType`, `errorCode`, `lastErrorAt`; ఎంపిక సమయంలో ఆటో-డికేను ట్రిగ్గర్ చేసి
  రికార్డును తుడిచివేసే `backoffLevel`ను ఉద్దేశపూర్వకంగా **చేర్చదు**)
- `maybeAutoDisableBannedAccount` — ఆటో-డిసేబుల్ లేదు
- `chatCore` — FORBIDDEN, ACCOUNT_DEACTIVATED, QUOTA_EXHAUSTED (నమోదు మాత్రమే,
  టెర్మినల్ `credits_exhausted` లేదు), GEO_BLOCKED (24h మినహాయింపు లేదు),
  MODEL_NOT_FOUND (`lockModel` లేదు), codex 429 ఖాతా-రొటేషన్ ఫెయిల్ఓవర్
  (`markCodexScopeRateLimited` లేదు, నిల్వ చేయబడిన `rate_limited_until` లేదు,
  session-affinity క్లియర్ లేదు), `persistCodexQuotaState` (కోటా-స్థితి రైట్ లేదు,
  క్యాష్ ఇన్వాలిడేషన్ లేదు), `recordKeyHealthStatus` (key-health రొటేటర్
  మార్చబడదు)
- OAuth రిఫ్రెష్ — executor baseలోని ప్రోయాక్టివ్ రిఫ్రెష్
  (`base.ts` `execute()`, refresh-token రొటేషన్ వినియోగించబడదు) మరియు
  `chatCore`లోని రియాక్టివ్ 401/403 పాత్ (`expired` డీయాక్టివేషన్ లేదు) రెండూ
- `chat.ts` — ప్రొవైడర్ సర్క్యూట్ బ్రేకర్ మరియు 5-నిమిషాల కోటా క్యాష్
  (`markAccountExhaustedFrom429`) ఎప్పటికీ డిగ్రేడ్ కావు

కనెక్షన్ ట్రాఫిక్కు సేవలందిస్తూ ఉండగానే, నమోదు చేసిన ఎర్రర్ వల్ల ఫ్లాగ్ చేయబడిన ఖాతా డ్యాష్బోర్డ్లో కనిపిస్తుంది. గమనిక: నిజమైన పాత్లోని `slice(0,100)` ట్రంకేషన్కు భిన్నంగా, ప్రోబ్ రికార్డ్ **ముడి** (స్లైస్ చేయని) ఎర్రర్ టెక్స్ట్ను నిల్వ చేస్తుంది.

test-allను నిర్వహణ సాధనంగా ఉపయోగించే ఆపరేటర్లు ఈ రెండింటిలో దేనినైనా ఉపయోగించి చారిత్రక ప్రవర్తనను (ప్రోబ్ను నిజమైన జనరేషన్గా పరిగణించడం) పునరుద్ధరించవచ్చు:

- `probeCanDisable` సెట్టింగ్ (`{"probeCanDisable": true}`తో
  `POST /api/settings`, లేదా నేరుగా `key_value` DB సవరణ), లేదా
- ఫీచర్ ఫ్లాగ్ **`PROBE_CAN_DISABLE=true`** (env లేదా DB ఓవర్రైడ్; సెట్టింగ్పై దీనికే ప్రాధాన్యం).

ఫెయిల్-సేఫ్: ఫ్లాగ్ లేదా సెట్టింగ్ల లుకప్ ఎర్రర్ను విసిరితే, ఐసోలేషన్ ఆన్లోనే ఉంటుంది.
