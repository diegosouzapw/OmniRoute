> **అధికారిక మూలం:** `src/lib/guardrails/`
> **చివరిగా నవీకరించబడింది:** 2026-08-29 — v3.8.51 (Video Bridge ట్రాన్స్క్రిప్ట్ మూలాధారం కాలర్ ద్వారా ప్రకటించబడుతుంది,
> ఇంకా సర్వర్ ద్వారా ధృవీకరించబడలేదు — #11661 ప్రకారం స్పష్టం చేయబడింది)

OmniRoute మరియు అప్స్ట్రీమ్ ప్రొవైడర్ల మధ్య సరిహద్దులో భద్రత, విధానం మరియు కంటెంట్ రూపాంతరణలను Guardrails అమలు చేస్తాయి. ప్రతి guardrail అభ్యర్థన పేలోడ్లను (`preCall`) మరియు అప్స్ట్రీమ్ ప్రతిస్పందనలను (`postCall`) పరిశీలించగలదు (అలాగే ఐచ్ఛికంగా తిరస్కరించగలదు, రూపాంతరం చేయగలదు లేదా వ్యాఖ్యానించగలదు).

ఈ సిస్టమ్ **fail-open** విధానాన్ని అనుసరిస్తుంది: అమలు సమయంలో ఒక guardrail మినహాయింపును విసిరితే, అభ్యర్థనను విఫలం చేయడానికి బదులుగా registry లోపాన్ని నమోదు చేసి తదుపరి guardrailతో కొనసాగుతుంది. నిరోధించడం అనేది స్పష్టమైన నిర్ణయం (`block: true`), అనుకోకుండా జరిగేది కాదు.

(`registry.ts` → `registerDefaultGuardrails()` చూడండి):

| `6`        | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`        | `video-bridge`      | `preCall`      | `videoBridge.ts`      |

తక్కువ ప్రాధాన్యత సంఖ్యలు **ముందుగా** అమలవుతాయి.

### Vision Bridge (`visionBridge.ts`) — మోడాలిటీ బ్రిడ్జ్ PR-1

**విజన్కు మద్దతు లేని మోడళ్లను** లక్ష్యంగా చేసుకున్న, చిత్రాలను కలిగిన అభ్యర్థనలను అడ్డుకుని, మొత్తం అభ్యర్థనను విజన్ సామర్థ్యం గల మోడల్కు మళ్లిస్తుంది లేదా అప్స్ట్రీమ్ కాల్కు ముందు చిత్ర భాగాలను కాన్ఫిగర్ చేయగల విజన్ మోడల్ రూపొందించిన వచన వివరణలతో భర్తీ చేస్తుంది. దీని వల్ల టెక్స్ట్-ఓన్లీ ప్రొవైడర్లు మల్టీమోడల్ పేలోడ్లను పారదర్శకంగా నిర్వహించగలుగుతారు.

ప్రవాహం:

1. లక్ష్య మోడల్ ఇప్పటికే విజన్కు మద్దతిస్తే దాటవేయండి (అది నిర్బంధ-బ్రిడ్జ్ జాబితా `isVisionBridgeForcedModel`లో కనిపిస్తే తప్ప).
2. `extractImageParts(messages)` ద్వారా చిత్ర భాగాలను సంగ్రహించండి
   (`visionBridgeHelpers.ts`); ఇది `open-sse/utils/mediaParts.ts`లోని **ఏకీకృత మీడియా డిటెక్టర్** `detectMediaParts()`కు బాధ్యతను అప్పగిస్తుంది — ఇది combo అనుకూలత ఫిల్టర్తో పంచుకునే ఏకైక అధికారిక మూలం.
   సంగ్రహణ, `replaceImageParts` తిరిగి చొప్పించగల ఆకృతుల టాప్-లెవల్ భాగాల అనుమతి జాబితాకే పరిమితం చేయబడింది (extract↔replace ఒప్పందం): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, మరియు Responses API `input_image`. నెస్టెడ్ సరిపోలికలు మరియు సూచిక-మాత్రమే ఉన్న ఆకృతులు combo-filterకు సంబంధించినవి; అవి ఎప్పటికీ సంగ్రహించబడవు.
   ఏవీ కనుగొనబడకపోతే దాటవేయండి.
3. `resolveVisionBridgeRuntimeSettings()` ద్వారా రన్టైమ్ కాన్ఫిగరేషన్ను పరిష్కరించండి
   (`src/shared/constants/modalityBridgeDefaults.ts`): కొత్త `modalityBridge*`
   సెట్టింగ్ కీలు ప్రాధాన్యత పొందుతాయి; పాత `visionBridge*` కీలు **ఒక-సైకిల్
   fallback**గా (rollback window) కొనసాగుతాయి. బ్రిడ్జ్ నిలిపివేయబడినప్పుడు ఏదైనా మీడియా ట్రావర్సల్కు ముందే దాటవేయండి.
4. మోడ్ సెలెక్టర్ (`modalityBridgeVisionMode`, దిగువ పట్టిక చూడండి) reroute లేదా describeను నిర్ణయిస్తుంది. Reroute, `model` మాత్రమే మార్చబడిన `modifiedPayload`ను, అలాగే `{ rerouted, fromModel, toModel, imagesKept }` మెటాను తిరిగి ఇస్తుంది.
5. Describe మార్గం: చిత్రాలను `maxImages` వద్ద పరిమితం చేసి, టాస్క్-అవేర్ ప్రాంప్ట్ను రూపొందించి, describe cacheను సంప్రదించి, విజన్ మోడల్ను **సమాంతరంగా**
   (`Promise.allSettled`) కాల్ చేసి, వాటి స్థానంలో `[Image N]: <description>` టెక్స్ట్ భాగాలను చొప్పిస్తుంది. విఫలమైన describe `null`ను ఇస్తుంది మరియు అసలు చిత్ర భాగం
   **సంరక్షించబడుతుంది** (#4012) — అయితే combo describe మార్గంలో ప్రతి
   describe విఫలమైనప్పుడు మాత్రం, విజన్కు మద్దతు లేదని నిర్ధారించబడిన అప్స్ట్రీమ్కు బదులుగా
   `(అందుబాటులో లేదు — విజన్ సామర్థ్యం గల ప్రొవైడర్ కనెక్ట్ కాలేదు)` స్టబ్ పంపబడుతుంది (#8430).
6. `modifiedPayload` + మెటా (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`)ను తిరిగి ఇవ్వండి.

#### మోడ్ సెలెక్టర్ (`modalityBridgeVisionMode`)

| మోడ్       | డిఫాల్ట్ | ప్రవర్తన                                                                                                                                                                                                                                                                                  |
| ---------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔        | లెగసీ హ్యూరిస్టిక్, మార్పులేదు (#6640/#7204): అసలు మోడల్కు ఇప్పటికే ఉపయోగించగల క్రెడెన్షియల్స్ ఉంటే తప్ప (అప్పుడు describe), non-combo/`auto/` మోడళ్లు ఉత్తమ విజన్ మోడల్కు reroute అవుతాయి; combo లక్ష్యాలు ఎల్లప్పుడూ describe అవుతాయి.                                                  |
| `describe` |          | ఎల్లప్పుడూ describe చేయండి — reroute బ్లాక్ పూర్తిగా దాటవేయబడుతుంది; వినియోగదారు ఎంచుకున్న మోడల్ ఎల్లప్పుడూ సమాధానమిస్తుంది.                                                                                                                                                              |
| `reroute`  |          | rerouteను నిర్బంధించండి: keep-credentialed-model guard దాటవేయబడుతుంది. reroute-**target** credential guard మాత్రం ఇప్పటికీ వర్తిస్తుంది — ఉపయోగించగల విజన్ లక్ష్యం లేనప్పుడు, అభ్యర్థన describeకు కొనసాగుతుంది; అందువల్ల ముడి చిత్రాలు టెక్స్ట్-ఓన్లీ బ్యాకెండ్కు ఎప్పటికీ చేరవు (#8430). |

`auto` హ్యూరిస్టిక్ అమలవడానికి **ముందే** నిర్బంధ మోడ్లు షార్ట్-సర్క్యూట్ అవుతాయి; `auto` ప్రవర్తన
PR-1కి ముందున్న guardrailతో బైట్-స్థాయిలో సమానంగా ఉంటుంది.

#### టాస్క్-అవేర్ describe ప్రాంప్ట్ (`modalityBridgeVisionTaskAware`)

డిఫాల్ట్గా **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) బేస్
describe ప్రాంప్ట్కు **చివరి వినియోగదారు సందేశం** యొక్క వచనాన్ని (500 అక్షరాలకు కుదించి) జోడిస్తుంది. తద్వారా వివరణను వినియోగదారు వాస్తవంగా అడిగిన దిశగా నడిపిస్తుంది
(codex-vision-proxy నమూనా), అలాగే కనిపించే వచనాన్ని ట్రాన్స్క్రైబ్ చేయమని విజన్ మోడల్ను కోరుతుంది. ఫ్లాగ్ ఆఫ్లో ఉన్నప్పుడు — లేదా వినియోగదారు వచనం లేనప్పుడు — బేస్ ప్రాంప్ట్ ఎలాంటి మార్పు లేకుండా ఉపయోగించబడుతుంది.

డిస్క్రైబ్ సెల్ఫ్-లూప్కు చెందిన OpenAI-అనుకూల అభ్యర్థన (`callVisionModelSingle()`
in `visionBridgeHelpers.ts`) ఎల్లప్పుడూ `image_url.detail: "high"`ను అభ్యర్థిస్తుంది —
ప్రతి కాలర్/ప్రొవైడర్కు ఎటువంటి షరతులు లేకుండా, ఏ క్లయింట్ సంకేతంపైనా ఆధారపడకుండా.
తక్కువ-వివరాల శాంప్లింగ్, ఈ ప్రాంప్ట్ కోరే టెక్స్ట్-ట్రాన్స్క్రిప్షన్
టాస్క్లో OCR ఖచ్చితత్వాన్ని తగ్గిస్తుంది, కాబట్టి అసలు ఇన్బౌండ్ అభ్యర్థన ఏ
వివరాల స్థాయిని ఉపయోగించినప్పటికీ, డిస్క్రైబ్ కాల్ ఎల్లప్పుడూ అధిక వివరాలను
అభ్యర్థిస్తుంది. ఇది అంతర్గత డిస్క్రైబ్ అభ్యర్థన బాడీని మాత్రమే ప్రభావితం చేస్తుంది;
ప్రాథమిక అభ్యర్థనలో కాలర్కు చెందిన `image_url.detail`ను OmniRoute ఎలా ఫార్వర్డ్
చేస్తుందో ఇది మార్చదు — ఆ డిఫాల్ట్ విడిగా, గుర్తించబడిన OpenCode క్లయింట్లకు మాత్రమే,
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`)లో వర్తింపజేయబడుతుంది.
డిస్క్రైబ్ సెల్ఫ్-లూప్లోని Anthropic వైర్-ఫార్మాట్ బ్రాంచ్లో `detail` ఫీల్డ్ లేదు
మరియు ఈ రెండు డిఫాల్ట్లలో దేనివల్లా ప్రభావితం కాదు.

#### డిస్క్రైబ్ అవుట్పుట్ పరిమితి (`modalityBridgeVisionMaxChars`)

| కీ                             | డిఫాల్ట్ | పరిధి              |
| ------------------------------ | -------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`      | `0` లేదా 100–50000 |

`0` (డిఫాల్ట్) అంటే **పరిమితి లేదు** — `callVisionModel()` తిరిగి ఇచ్చే వివరణ
ఎటువంటి మార్పు లేకుండా పంపబడుతుంది, తద్వారా ప్రస్తుత ప్రవర్తన సంరక్షించబడుతుంది.
100–50000 పరిధిలోని ఏ విలువైనా, వివరణను తిరిగి `[Image N]: <description>`గా
చేర్చడానికి ముందు `…` ప్రత్యయంతో కుదిస్తుంది
(`src/lib/guardrails/visionBridge.ts`లోని `VisionBridgeGuardrail.preCall()`).
డౌన్స్ట్రీమ్ మోడల్కు పూర్తి ట్రాన్స్క్రిప్షన్ అవసరమయ్యే, అధిక వివరాలతో కూడిన OCR
టాస్క్ల కోసం దీన్ని పెంచండి; ఎక్కువగా స్పందించే విజన్ మోడళ్లలో టోకెన్ వినియోగాన్ని
పరిమితం చేయడానికి దీన్ని తగ్గించండి. డ్యాష్బోర్డ్ ఫీల్డ్ Vision ట్యాబ్లోని Advanced
ప్యానెల్లో ఉంటుంది (`ModalityBridgeVisionTab.tsx`లోని
`modality-bridge-max-chars`) మరియు స్పష్టంగా ఇచ్చిన `0`ను మార్చకుండా ఉంచుతూ,
1 నుండి 99 మధ్య ఉన్న ఏ విలువనైనా కనిష్ఠ పరిమితి 100కు పెంచుతుంది — `0` అనేది
కేవలం "సెట్ చేయని" డిఫాల్ట్ మాత్రమే కాదు, దానికదే చెల్లుబాటు అయ్యే Zod విలువ
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`).

#### డిస్క్రైబ్ క్యాష్ (`modalityBridge/bridgeCache.ts`)

డిస్క్రైబ్ అవుట్పుట్ల కోసం ఇన్-మెమరీ LRU + TTL క్యాష్, ప్రాసెస్ అంతటా భాగస్వామ్యం చేయబడుతుంది.
కీ = `sha256(imageRef + composedPrompt + configuredBridgeModel)`, దీనిలో
లెంగ్త్-ప్రిఫిక్స్ ఫ్రేమింగ్ ఉంటుంది (ఫీల్డ్-సరిహద్దు ఢీకొనడాలు ఉండవు). మోడల్ భాగం
**కాన్ఫిగర్ చేసిన** బ్రిడ్జ్ మోడల్, వాస్తవంగా సమాధానమిచ్చిన మోడల్ కాదు —
`callVisionModel` అంతర్గతంగా ఫాల్బ్యాక్ కావచ్చు, ప్రతి ప్రయత్నం ఆధారంగా కీని
నిర్ణయించడం క్యాష్ను విభజిస్తుంది. విఫలమైన డిస్క్రైబ్లు ఎప్పుడూ క్యాష్ చేయబడవు.
సెట్టింగ్లు:

| కీ                              | డిఫాల్ట్ | పరిధి   |
| ------------------------------- | -------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`   | —       |
| `modalityBridgeCacheTtlMinutes` | `60`     | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`    | 10–5000 |

#### రిమోట్ ఇమేజ్ సాధారణీకరణ (సెల్ఫ్-లూప్ డిస్క్రైబ్/base64 ఫెచ్)

బ్రిడ్జ్ స్వయంగా ఒక **రిమోట్** ఇమేజ్ను ఫెచ్ చేసినప్పుడు — Anthropic డిస్క్రైబ్
సెల్ఫ్-కాల్ మరియు claude-వైర్-ఫార్మాట్ base64 మార్పిడి
(`ensureBase64ImagesForClaudeWire`), రెండూ `visionBridgeHelpers.ts`లోని
`fetchRemoteImageAsDataUri()` ద్వారా — ఫలితంగా వచ్చే డేటా URIని విజన్-మోడల్
అభ్యర్థనలో పొందుపరచడానికి ముందు `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) ద్వారా పంపిస్తారు. అతి పెద్ద ఇమేజ్లు
**2048px పొడవైన అంచు** వరకు డౌన్స్కేల్ చేయబడతాయి (OpenAI/Anthropic ఇప్పటికే
సర్వర్ వైపు వర్తింపజేసే రీసైజ్ పరిమితికి అనుగుణంగా), దీనివల్ల విజన్ మోడల్ చూసే
విషయం మారకుండా అప్లోడ్ బైట్లు/లేటెన్సీ తగ్గుతాయి. రీసైజింగ్ `sharp`ను ఉపయోగిస్తుంది,
ఇది డైనమిక్ ఇంపోర్ట్ ద్వారా లోడ్ చేయబడుతుంది: దాని నేటివ్ బైనరీ లోడ్ కావడంలో విఫలమయ్యే
ప్లాట్ఫారమ్లో, `normalizeDataUri()` **ఎప్పుడూ త్రో చేయదు** — ఇది అసలు బైట్లను
మార్పులేకుండా పంపడానికి ఫాల్బ్యాక్ అవుతుంది, కాబట్టి డిస్క్రైబ్/base64-కన్వర్షన్
పాత్ ఎల్లప్పుడూ పనిచేస్తూనే ఉంటుంది. ఇమేజ్ కాని బైట్లు (డీకోడ్ చేయగల ఇమేజ్ను
తిరిగి ఇవ్వని ఫెచ్) కూడా మార్పులేకుండా పంపబడతాయి. ఈ సాధారణీకరణ, బ్రిడ్జ్ తన
సొంత సెల్ఫ్-కాల్ కోసం ఫెచ్ చేసే ఇమేజ్లకే పరిమితం — కాలర్కు చెందిన ముడి
పాస్త్రూ పేలోడ్కు ఇది ఎప్పుడూ వర్తింపజేయబడదు, ఇది ఎంపిక చేసుకున్నప్పుడు మాత్రమే
మార్పులు చేయాలనే సూత్రానికి అనుగుణంగా ఉంటుంది (కఠిన నియమం #20).

#### సెట్టింగ్ల స్కీమా + మైగ్రేషన్

కొత్త `modalityBridge*` కీలు `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`)లో Zod ద్వారా ధృవీకరించబడతాయి:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCache*` త్రయం మరియు Audio Bridge ఉపయోగించే
`modalityBridgeAudio*` సమూహం. మైగ్రేషన్ `141_modality_bridge_settings.sql`
ఇప్పటికే ఉన్న లెగసీ `visionBridge*` విలువలను సరిపోలే కొత్త కీలకు కాపీ చేస్తుంది
(ఐడెంపోటెంట్, ఆపరేటర్ సెట్ చేసిన `modalityBridge*` విలువను ఎప్పుడూ ఓవర్రైట్ చేయదు);
ఒక విడుదల చక్రం పాటు లెగసీ కీలు రీడ్ ఫాల్బ్యాక్గా ఆమోదించబడుతూనే ఉంటాయి.

#### పారదర్శకత హెడర్ + గణాంకాలు

డిస్క్రైబ్ ద్వారా మార్చబడిన ప్రతిస్పందనలు
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`ను కలిగి ఉంటాయి
(`modalityBridge/bridgeStats.ts`లోని `buildModalityBridgeHeader()` ద్వారా నిర్మించబడి,
`src/sse/handlers/chatHelpers.ts`లోని `withModalityBridgeHeader()` ద్వారా జోడించబడుతుంది).
రీరూట్ చేసిన అభ్యర్థనలకు **ఎటువంటి** హెడర్ ఉండదు — పేలోడ్ మార్చబడలేదు మరియు
మోడల్ మార్పు ఇప్పటికే ప్రతిస్పందన బాడీలోని `model` ఫీల్డ్లో కనిపిస్తుంది.

`GET /api/modality-bridge/stats` (నిర్వహణ ఆథెంటికేషన్, `GET /api/settings`తో సమానమైన
స్థాయి) `vision`, `audio`, మరియు `video` కోసం ఇన్-మెమరీ, ప్రతి-మోడాలిటీ కౌంటర్లైన
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }`ను తిరిగి ఇస్తుంది.
`averageLatencyMs` తన హారంలో అన్ని ప్రయత్నాలను కాకుండా `latencySamples`ను
ఉపయోగిస్తుంది; టైమింగ్ లేని ఆపరేషన్ కల్పితంగా సున్నా-మిల్లీసెకండ్ శాంపిల్ను
సృష్టించదు. విజయవంతమైన మార్పిడులకు `bridged` వెనుకకు-అనుకూలమైన మారుపేరుగానే
కొనసాగుతుంది; విఫలమైన ప్రయత్నాలు దాన్ని పెంచవు.
రూపకల్పన ప్రకారం ప్రాసెస్ పునఃప్రారంభమైనప్పుడు కౌంటర్లు రీసెట్ అవుతాయి
(టెలిమెట్రీ, అకౌంటింగ్ కాదు).

#### డ్యాష్బోర్డ్ కాన్ఫిగరేషన్

ప్రత్యేక డ్యాష్బోర్డ్ పేజీ
`/dashboard/settings/modality-bridge`. URL ద్వారా నేరుగా యాక్సెస్ చేయగల దాని `Vision`, `Audio`,
మరియు `Video` ట్యాబ్లు `tab` విలువను మార్చేటప్పుడు క్వెరీ పారామీటర్లను అలాగే ఉంచుతాయి.
Vision ట్యాబ్లో ప్రారంభించడం, మోడ్, మోడల్ ఎంపిక (ఆటోమేటిక్
డిఫాల్ట్తో సహా), టాస్క్-అవేర్ ప్రాంప్టింగ్, అధునాతన టైమ్ఔట్/చిత్రం/వివరణ-పొడవు/క్యాష్
పరిమితులు, రన్టైమ్
కౌంటర్లు, మరియు రక్షిత నమూనా రిక్వెస్ట్ అందుబాటులో ఉంటాయి. Audio ట్యాబ్ కూడా క్రియాశీలంగా ఉంది: ఇందులో
ప్రారంభించడం, Autoతో కూడిన STT-మాత్రమే మోడల్ పికర్, టైమ్ఔట్/గరిష్ఠ-క్లిప్ పరిమితులు, ఆడియో
కౌంటర్లు, మరియు ఒక `input_audio` నమూనా పరీక్ష అందుబాటులో ఉంటాయి. Video ట్యాబ్ పూర్తిగా పనిచేస్తుంది: ఇది
FFmpeg/ffprobe రన్టైమ్ స్థితిని నివేదిస్తుంది — నాలుగు స్పష్టమైన UI స్థితుల్లో ఒకటిగా (`unknown` అనేది
ప్రోబ్ కొనసాగుతున్నప్పుడు లేదా పూర్తి కాలేనప్పుడు, `restricted` అనేది లూప్బ్యాక్ కాని
డ్యాష్బోర్డ్ హోస్ట్లో క్లయింట్ వైపు ప్రోబ్ దాటవేయబడినప్పుడు, `unavailable` అనేది ప్రోబ్ చేసిన తర్వాత
అది లేదని నిర్ధారించబడినప్పుడు, లేదా FFmpeg/ffprobe వెర్షన్లతో `available`) — ప్రారంభం/మోడల్/ఫ్రేమ్/వీడియో/టైమ్ఔట్
పరిమితులను నిల్వ చేస్తుంది, మోడల్ పికర్ను విజన్-సామర్థ్యమున్న
మోడల్లకు పరిమితం చేస్తుంది, మరియు వీడియో కౌంటర్లను అందిస్తుంది.

AI సెట్టింగ్ల క్రింద గతంలో ఉన్న Vision Bridge కార్డ్ ఇప్పుడు కొత్త
పేజీకి అనుకూలత లింక్గా పనిచేస్తుంది; ఇకపై అది ఫారమ్ యొక్క రెండవ కాపీని నిర్వహించదు. Media Providers కూడా
ఇప్పటికే ఉన్న Speech-to-Text ప్లేగ్రౌండ్ను తొలగించకుండా Image-to-Text మరియు Speech-to-Text వర్క్ఫ్లోలను సంబంధిత Modality
Bridge ట్యాబ్లకు లింక్ చేస్తుంది.

**సెల్ఫ్-లూప్ అడ్మిషన్ బైపాస్:** డిస్క్రైబ్ కాల్ OmniRoute యొక్క
సొంత `/v1` సెల్ఫ్-లూప్ (ప్రామాణికం కాని ప్రొవైడర్ మోడల్) ద్వారా రూట్ అయినప్పుడు, సబ్-రిక్వెస్ట్
`x-omniroute-admission-bypass: internal`ను పంపుతుంది మరియు పరిష్కరించబడిన
సెల్ఫ్-లూప్ క్రెడెన్షియల్తో ప్రామాణీకరించబడుతుంది — లోకల్ మోడ్లోని స్థానిక `sk_omniroute` సెంటినెల్, లేదా
ఆపరేటర్ కాన్ఫిగర్ చేసిన `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env కీ (#1350); తద్వారా
`REQUIRE_API_KEY=true` డిప్లాయ్మెంట్లు కూడా డిస్క్రైబ్ కాల్ను అమలు చేయగలవు. ఆ ఖచ్చితమైన
క్రెడెన్షియల్లకు మాత్రమే బైపాస్ అనుమతించబడుతుంది, కాబట్టి బాహ్య క్లయింట్లు అడ్మిషన్ను దాటవేయడానికి
హెడర్ను ఉపయోగించలేరు.

లెగసీ డిఫాల్ట్లు `src/shared/constants/visionBridgeDefaults.ts`లో ఉంటాయి;
కొత్త మోడ్/టాస్క్-అవేర్/క్యాష్ డిఫాల్ట్లు మరియు సెట్టింగ్ల రిజాల్వర్
`src/shared/constants/modalityBridgeDefaults.ts`లో ఉంటాయి. గార్డ్రైల్ ఒక
`deps` కన్స్ట్రక్టర్ ఎంపికను అందిస్తుంది, తద్వారా పరీక్షలు నకిలీ `getSettings` మరియు
`callVisionModel` అమలులను ఇంజెక్ట్ చేయగలవు.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ఆడియో ఇన్పుట్ను అంగీకరిస్తుందని తెలియని లక్ష్యాన్ని చేరుకునే ముందు, ఆడియో కలిగిన చాట్ రిక్వెస్ట్లను
ఇది అడ్డుకుంటుంది. ఇది చాట్ రిక్వెస్ట్ను ఎప్పుడూ వేరే మార్గానికి మళ్లించదు: ఇప్పటికే ఉన్న
OpenAI-అనుకూల మల్టీపార్ట్ ఎండ్పాయింట్ ద్వారా ఆడియో భాగాలు ట్రాన్స్క్రైబ్ చేయబడతాయి మరియు
ఎంచుకున్న చాట్ మోడల్ టెక్స్ట్ ట్రాన్స్క్రిప్ట్లతో కొనసాగుతుంది.

ప్రవాహం:

1. `getResolvedModelCapabilities()` ద్వారా `supportsAudio`ను పరిష్కరించండి. స్పష్టమైన
   ప్రొవైడర్-రిజిస్ట్రీ మెటాడేటాకు మొదటి ప్రాధాన్యం, ఆపై స్థిర మోడల్ మెటాడేటా, తదనంతరం సింక్ చేసిన
   `modalities_input`. `audio` లేని ప్రకటిత ఇన్పుట్ జాబితా `false`; ఎటువంటి
   సామర్థ్య ఆధారం లేకపోతే `null`. `false` మరియు `null` రెండూ
   సంరక్షణాత్మక బ్రిడ్జ్ను సక్రియం చేస్తాయి, అయితే `true` దానిని దాటవేస్తుంది.
2. `modalityBridgeAudio*` సెట్టింగ్లను పరిష్కరించి, షేర్డ్ `detectMediaParts()`
   డిటెక్టర్ ద్వారా ప్రతి సందేశం నుంచి స్ప్లైస్ చేయగల టాప్-లెవల్
   ఆడియో భాగాలను వెలికితీయండి. మద్దతు ఉన్న వైర్ ఆకృతులు OpenAI `input_audio`, `audio_url`, మరియు
   `source.media_type: "audio/*"`. రూటింగ్ కోసం నెస్టెడ్ ఆడియో గుర్తించబడుతుంది, కానీ
   స్ప్లైస్ పాత్ ద్వారా తొలగించబడదు. పని `modalityBridgeAudioMaxClips` ద్వారా పరిమితం చేయబడుతుంది;
   తర్వాతి భాగాలు మార్పులేకుండా ఉంటాయి.
3. కాన్ఫిగర్ చేసిన `provider/model`ను గౌరవించండి, లేదా `selectAudioBridgeModel()`ను
   స్థిరమైన కేటలాగ్ క్రమంలో `AUDIO_TRANSCRIPTION_PROVIDERS` గుండా వెళ్లి ఉపయోగించగల క్రియాశీల
   ప్రొవైడర్ క్రెడెన్షియల్ ఉన్న మొదటి మోడల్ను ఎంచుకోనివ్వండి.
4. `callAudioTranscription()` base64/data-URI ఆడియోను మల్టీపార్ట్
   `file`గా మారుస్తుంది, లేదా DNS పిన్నింగ్ మరియు 25 MB పరిమితితో పబ్లిక్-మాత్రమే అవుట్బౌండ్
   గార్డ్ ద్వారా రిమోట్ `audio_url`ను డౌన్లోడ్ చేస్తుంది. ఆపై అది ఫైల్ను మరియు ఎంచుకున్న
   మోడల్ను స్థానిక `/v1/audio/transcriptions` సెల్ఫ్-లూప్కు POST చేస్తుంది; ఇది
   `resolveSelfLoopBearer()`తో ప్రామాణీకరించబడుతుంది. ఇప్పటికే ఉన్న ట్రాన్స్క్రిప్షన్ రూట్ సాధారణ
   క్రెడెన్షియల్ లుకప్, కూల్డౌన్/రేట్-లిమిట్ నిర్వహణ, మరియు ప్రొవైడర్ డిస్పాచ్ను నిర్వహిస్తుంది.
5. విజయవంతమైన కాల్లు వాటి భాగాలను `[Audio N]: <transcript>`తో భర్తీ చేస్తాయి. కాల్లు
   `Promise.allSettled`తో నడుస్తాయి: ఒక వ్యక్తిగత వైఫల్యం ఆ అసలు
   ఆడియో భాగాన్ని అలాగే ఉంచుతుంది (#4012 ఒప్పందం). ప్రతి కాల్ విఫలమై, లక్ష్యం
   `supportsAudio === false` అని నిరూపితమైతే, ఆ భాగాలు
   `[Audio N]: (అందుబాటులో లేదు — STT ప్రొవైడర్ కనెక్ట్ కాలేదు)`గా మారతాయి (#8430 ఒప్పందం). తెలియని
   లక్ష్యం (`null`) విషయంలో, అన్ని కాల్లు విఫలమైన ఫలితం మార్పులేకుండా ఉంటుంది. ఉపయోగించగల STT క్రెడెన్షియల్ లేని
   నిరూపిత టెక్స్ట్-మాత్రమే లక్ష్యానికి నెట్వర్క్ కాల్ చేయకుండానే అదే స్పష్టమైన
   స్టబ్ అందుతుంది.

విజయవంతమైన ట్రాన్స్క్రిప్ట్లు ప్రాసెస్-వ్యాప్త Modality Bridge LRU/TTL క్యాష్ను ఉపయోగిస్తాయి. కీ
ఆడియో రిఫరెన్స్, స్థిరమైన `audio-transcription` ఆపరేషన్
లేబుల్, మరియు ఎంచుకున్న STT మోడల్ను కలిపి రూపొందించబడుతుంది; వైఫల్యాలు ఎప్పుడూ క్యాష్ చేయబడవు. ఆడియో ప్రయత్నాలు షేర్డ్
`bridged`, `cacheHits`, `failures`, మరియు `lastUsedAt` కౌంటర్లను అప్డేట్ చేస్తాయి.
రూపాంతరం చెందిన రెస్పాన్స్లు
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`ను కలిగి ఉంటాయి; మార్పులేని
రిక్వెస్ట్లకు Audio Bridge సెగ్మెంట్ అందదు.

రన్టైమ్ సెట్టింగ్లు DB-ఆధారితమైనవి మరియు Zod ద్వారా ధ్రువీకరించబడతాయి:

| కీ                            | డిఫాల్ట్ | పరిధి            |
| ----------------------------- | -------- | ---------------- |
| `modalityBridgeAudioEnabled`  | `true`   | —                |
| `modalityBridgeAudioModel`    | `""`     | Auto లేదా STT ID |
| `modalityBridgeAudioTimeout`  | `60000`  | 1000–300000      |
| `modalityBridgeAudioMaxClips` | `3`      | 1–10             |

షేర్డ్ క్యాష్ ఇప్పటికీ `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, మరియు `modalityBridgeCacheMaxEntries` ద్వారా నియంత్రించబడుతుంది.

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

తెలిసిన స్థానిక వీడియో మద్దతు లేని లక్ష్యాన్ని కాల్ చేయడానికి ముందు, Chat Completions `messages` మరియు Responses
API `input`లోని అగ్ర-స్థాయి వీడియో భాగాలను ఇంటర్సెప్ట్ చేస్తుంది.
మద్దతు ఉన్న ఆకృతులు `input_video`, `video_url`, `video_source`, HTTPS URLలు,
మరియు `data:video/*;base64,...` డేటా URIలు. టెక్స్ట్లోని సాధారణ ఫైల్ పేర్లు
వీడియోగా పరిగణించబడవు.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) అభ్యర్థన ట్రావర్సల్,
సామర్థ్యం/విధాన తనిఖీ, ప్రతి-అభ్యర్థన అగ్రిగేషన్ మరియు ప్రతిస్పందన పేలోడ్ను నిర్వహిస్తుంది.
ప్రతి-వీడియో పని — సేకరణ, పూర్తి-ఫలిత క్యాష్, ఫ్రేమ్
క్రమాన్ని వివరించడం (ఇది కాలర్ ప్రకటించిన ఏదైనా ఆడియో ట్రాన్స్క్రిప్ట్ను సమ్మిళితం చేస్తుంది), మరియు ప్రతి-ప్రయత్న
మెట్రిక్స్/అబార్ట్/క్లీనప్ — `videoBridgePipeline.ts`లోని `processVideoPart` వెనుక
దాచబడుతుంది; `preCall` లూప్లో ప్రతి వీడియో భాగానికి ఇది ఒకసారి కాల్ చేయబడుతుంది.
ఆ మాడ్యూల్ స్పష్టమైన పోర్ట్ సరిహద్దులైన `VideoMediaBrokerPort`
(బైట్లను సేకరించడం మరియు నమూనా ఫ్రేమ్లను వెలికితీయడం), `VideoAudioTranscriptionPort`
(కాలర్ ప్రకటించిన ఆడియో ట్రాన్స్క్రిప్ట్ను నమూనా క్యాప్షన్లతో సమ్మిళితం చేయడం), మరియు
`VideoDrilldownPort` (ఫ్రేమ్ డ్రిల్-డౌన్ నిల్వ సరిహద్దు; ఇంకా
`processVideoPart`తో అనుసంధానించబడలేదు — ప్రస్తుతం ప్రత్యేక `/api/modality-bridge/video/drilldown`
రూట్ మాత్రమే డ్రిల్-డౌన్ ఎంట్రీలను వ్రాస్తుంది)ను కూడా నిర్వచిస్తుంది.

నిర్మాణాత్మక విలువలు నిర్ణయాత్మక నమూనా సేకరణకు సంబంధించిన ఆధారాలు మాత్రమే; అవి వీడియో యొక్క అర్థపరమైన అవగాహన కావు. అవి విషయాలను, చర్యలను, క్యాప్షన్లను, మాటలను లేదా వినియోగదారు ఉద్దేశాన్ని ఊహించవు. సీన్ మరియు ఫ్రీజ్ సరిహద్దులు సెగ్మెంట్లను రూపొందిస్తాయి; ఫ్రీజ్ కవరేజ్, బ్లర్, ఎక్స్పోజర్, ప్రాదేశిక వివరాలు మరియు కాలానుగుణ మార్పు—ఇప్పటికే ఉన్న 1–16 ఫ్రేమ్ల బడ్జెట్ను ఎలా కేటాయించాలనే దానిపై మాత్రమే ప్రభావం చూపుతాయి. పూర్తిగా ఫ్రీజ్ అయిన సెగ్మెంట్కు గరిష్ఠంగా ఒక ఫ్రేమ్ మాత్రమే కేటాయించబడుతుంది, ఫ్రీజ్ కాని సెగ్మెంట్లు మిగిలిన బడ్జెట్ కోసం పోటీపడతాయి. సరిహద్దుల సంఖ్య ఫ్రేమ్ల సంఖ్యను మించినప్పుడు, ప్రారంభంలో వేగంగా జరిగే కట్లు చివర ఉన్న పొడవైన సెగ్మెంట్ను దాచకుండా ఉండేందుకు టైమ్లైన్ అంతటా ఏకరీతి కవరేజ్ కొనసాగించబడుతుంది. ఫ్రీజ్ సరిహద్దు యొక్క 1-సెకను విశ్లేషణ రిజల్యూషన్ పరిధిలోని సీన్ సరిహద్దులు ఏకీకృతం చేయబడతాయి.

ఫిల్టర్లు లేకపోవడం, తప్పుగా రూపొందిన/ఖాళీ ఆధారాలు, డిటెక్టర్ లోపం లేదా పరిమిత ముందస్తు-విశ్లేషణ టైమ్అవుట్ సంభవించినప్పుడు, ఖచ్చితమైన ఏకరీతి మధ్యబిందు విధానానికి ఫెయిల్-ఓపెన్ అవుతుంది. కాలర్ అబార్ట్ లేదా బ్రోకర్ గడువు మాత్రం ఫెయిల్-ఓపెన్ కాదు: అది అమలులో ఉన్న సబ్ప్రాసెస్ను ముగిస్తుంది, తదుపరి ఫ్రేమ్ ఎక్స్ట్రాక్షన్ను నిరోధిస్తుంది, అలాగే ప్రైవేట్ తాత్కాలిక ట్రీ `finally`లో తొలగించబడుతుంది.

`scripts/perf/video-bridge-fu07-eval.ts`, డీడూప్లికేషన్ అనంతర క్యాప్షన్-కాల్ ఆదా, అధిక-చలన బడ్జెట్ కేటాయింపు, బ్లర్/ఎక్స్పోజర్/SI-TI ఆధారాలు, పొడవైన చివరి భాగంతో కూడిన వేగవంతమైన కట్లు మరియు క్రమానుగత-ఫేడ్ తప్పుడు పాజిటివ్ల కోసం నిర్ణయాత్మక వాస్తవ FFmpeg ఫిక్చర్లను రూపొందిస్తుంది. ఇది ముందస్తు-విశ్లేషణ వాల్ టైమ్ను, అలాగే `/usr/bin/time` అందుబాటులో ఉన్నచోట చైల్డ్ CPU మరియు గరిష్ఠ RSSను నమోదు చేస్తుంది. దీని నాణ్యత తనిఖీలు నిర్మాణాత్మక ఒరాకిల్లు మాత్రమే. ఈ హార్నెస్కు అధీకృత ఎండ్పాయింట్ లేదా స్థిరీకరించిన జడ్జ్ లేనందున, వాస్తవ క్యాప్షన్-మోడల్ నాణ్యత `HOLD`గానే ఉంటుంది. `--caption-cost-per-call-usd` స్పష్టమైన ధనాత్మక ప్రతి-కాల్ అంచనాను అందించనంతవరకు ద్రవ్య ఆదా కూడా `HOLD`గానే ఉంటుంది; స్క్రిప్ట్ ఈ రెండు ఫలితాల్లో దేనినీ కల్పించదు.

ప్రతి ఫ్రేమ్ 4 MiBకి, అన్ని రా ఫ్రేమ్లు కలిపి 23 MiBకి, సీరియలైజ్ చేసిన బ్రోకర్ ప్రతిస్పందన 32 MiBకి పరిమితం చేయబడతాయి. ప్రైవేట్ తాత్కాలిక డైరెక్టరీ `finally`లో తొలగించబడుతుంది. OmniRouteలో FFmpeg బండిల్ చేయబడదు మరియు అనుకూల ఎగ్జిక్యూటబుల్ పాత్ను అది అంగీకరించదు. క్యాప్షనింగ్కు ముందు, బ్రిడ్జ్ పరిమితమైన విజువల్ డీడూప్లికేషన్ పాస్ను వర్తింపజేస్తుంది: ప్రతి JPEG 16×16 గ్రేస్కేల్ బఫర్గా తగ్గించబడి, చివరిగా నిలుపుకున్న ఫ్రేమ్తో మాత్రమే పోల్చబడుతుంది. ఒక ఫ్రేమ్ కంటే ఎక్కువ క్యాప్షన్ బడ్జెట్ అభ్యర్థించినప్పుడు, ఎక్స్ట్రాక్షన్ ఆ బడ్జెట్కు గరిష్ఠంగా రెండింతల వరకు ఉండే, ఎప్పటికీ 16 ఫ్రేమ్లను మించని పరిమిత అభ్యర్థి పూల్ను అందిస్తుంది. అభ్యర్థించిన పరిమితి డీడూప్లికేషన్ తర్వాత మాత్రమే వర్తింపజేయబడుతుంది; బడ్జెట్ కనీసం రెండు ఉన్నప్పుడు తుది థిన్నింగ్ సమయంలో మొదటి మరియు చివరి ఎంపిక చేసిన అభ్యర్థులు భద్రపరచబడతారు. వెర్షన్ చేయబడిన `grayscale-16x16-mean-cells-v2` విధానం, సగటు లూమా డెల్టా మరియు నార్మలైజ్ చేసిన డెల్టా కనీసం 0.05గా ఉన్న థంబ్నెయిల్ సెల్ల నిష్పత్తి—ఈ రెండింటిలో పెద్దదాన్ని ఉపయోగిస్తుంది. డూప్లికేట్ థ్రెషోల్డ్ స్థిరాంకం 0.04; రన్టైమ్ సెట్టింగ్గా అందుబాటులో ఉంచడం కంటే ముందస్తు అంచనా సాధ్యత కోసం ఇది ఎంపిక చేయబడింది. ఈ ద్వితీయ అధిక-కాంట్రాస్ట్ సంకేతం, సగటు-మాత్రమే పోలిక దాచగల చిన్న కదలికలు మరియు కనిపించే-టెక్స్ట్ మార్పులను సంరక్షిస్తుంది. కంపారేటర్ లేదా డీకోడర్ లోపాలు ఫెయిల్-ఓపెన్ అయి కవరేజ్ను కొనసాగిస్తాయి. అవుట్పుట్ మెటాడేటా ఎక్స్ట్రాక్ట్ చేసిన అభ్యర్థులు, విజయవంతంగా ఉపయోగించిన ఫ్రేమ్లు మరియు తొలగించిన విజువల్ డూప్లికేట్లను వేరు చేసి చూపుతుంది.

స్పష్టంగా గుర్తించిన వీడియో భాగం టైమ్స్టాంప్లతో కూడిన కాంటాక్ట్ షీట్ను అభ్యర్థించవచ్చు. బ్రిడ్జ్ గరిష్ఠంగా 4-కాలమ్, 16-ఫ్రేమ్ JPEG గ్రిడ్ను రూపొందిస్తుంది. ప్రతి 512-పిక్సెల్ సెల్, దాని సోర్స్ టైమ్స్టాంప్ను అధిక-కాంట్రాస్ట్ దిగువ బ్యాండ్లో ముద్రిస్తుంది; అదే టైమ్స్టాంప్లు దిగువస్థాయి అనుసంధానం మరియు ఆడిట్ కోసం పాఠ్య మెటాడేటాలో కూడా ఉంటాయి. పూర్తి JPEG 32 MiBకి పరిమితంగానే ఉంటుంది. `sharp` గ్రిడ్ను డీకోడ్ చేయలేకపోతే లేదా కంపోజ్ చేయలేకపోతే, బ్రిడ్జ్ విడివిడి JPEG ఫ్రేమ్లకు తిరిగి వెళుతుంది; క్లయింట్ అబార్ట్ మాత్రం షీట్ ఆపరేషన్ అంతటా వ్యాపిస్తుంది.

ప్రమోషన్ ఆధారాలు సింథటిక్ కంపోజిషన్ మైక్రోబెంచ్మార్క్ నుండి ఉద్దేశపూర్వకంగా వేరు చేయబడ్డాయి. `scripts/perf/video-bridge-contact-sheet-eval.ts`, వాస్తవ OpenAI-అనుకూల విజన్ మోడల్ల కోసం స్కీమా-వెర్షన్ చేసిన A/B హార్నెస్ను నిర్వచిస్తుంది. ఇది ప్రొవైడర్ నివేదించిన టోకెన్లు, ఎండ్-టు-ఎండ్ వాల్ లేటెన్సీని (షీట్ కంపోజిషన్తో సహా), మోడల్-కాల్ సంఖ్యను మరియు మానిఫెస్ట్ నిర్వచించిన వాస్తవాల నిలుపుదలను కొలుస్తుంది. రా మోడల్ ప్రతిస్పందనలు నివేదికలో వ్రాయబడవు; SHA-256 డైజెస్ట్లు మరియు సరిపోలిన ఫ్యాక్ట్ IDలు మాత్రమే నిలుపుకోబడతాయి. `--execute-real` పాస్ చేయబడి, `--model`, `OMNIROUTE_BASE_URL` మరియు `OMNIROUTE_API_KEY` కాన్ఫిగర్ చేయబడనంతవరకు హార్నెస్ ఎలాంటి నెట్వర్క్ లేదా చెల్లింపు మోడల్ కాల్ చేయదు. అటువంటి స్పష్టమైన వాస్తవ రన్ లేకుండా, దాని యంత్రం చదవగల తీర్పు `HOLD`గానే ఉంటుంది; సింథటిక్ పేలోడ్/కాల్-కౌంట్ కొలతలు మాత్రమే ప్రమోషన్ ఆధారాలు కావు.

కాలర్ల వద్ద ఇప్పటికే సమలేఖనం చేసిన టెక్స్ట్ ఉన్నప్పుడు, మద్దతు ఉన్న వీడియో భాగానికి ఐచ్ఛిక `transcript.cues` అర్రేను జోడించవచ్చు. ప్రతి క్యూ తప్పనిసరిగా `text`, ప్రోబ్ చేసిన వ్యవధి లోపల పరిమిత `start`/`end` అంతరాన్ని మరియు వైట్లిస్ట్ చేసిన `source`ను (`client`, `embedded` లేదా `audio-bridge`) కలిగి ఉండాలి; `confidence` డిఫాల్ట్గా `1` అవుతుంది మరియు తప్పనిసరిగా `0` నుండి `1` మధ్య ఉండాలి. సరిగ్గా ఒకేలా ఉన్న డూప్లికేట్ క్యూలు ఏకీకృతం చేయబడతాయి. OmniRoute ఈ మెటాడేటా ఆధారంగా ఎప్పటికీ ట్రాన్స్క్రిప్షన్ను ప్రారంభించదు: ధ్రువీకరించిన క్యూలు సోర్స్, కాన్ఫిడెన్స్ మరియు అంతరంతో సహా వివరించిన ఫలితంలోకి కాపీ చేయబడతాయి, అలాగే ఫ్రేమ్ క్యాప్షన్లతోపాటు విశ్వసించని పరిశీలనలుగా రెండర్ చేయబడతాయి. చెల్లని, పరిధి వెలుపలి లేదా మూలాధార వివరాలు లేని టెక్స్ట్ను క్యాప్షన్ స్ట్రీమ్లో కలపకుండా తిరస్కరిస్తుంది. `source` ఫీల్డ్ ప్రస్తుతం కాలర్ ప్రకటించినదే, సర్వర్ ధ్రువీకరించినది కాదు: దాని విలువ అనుమతించిన మూడు స్ట్రింగ్లలో ఒకటిగా ఉండాలని OmniRoute నిర్బంధిస్తుంది, కానీ `embedded` లేదా `audio-bridge` లేబుల్ నిజంగా సర్వర్-యాజమాన్యంలోని ఎక్స్ట్రాక్షన్ నుండి వచ్చిందని ఇంకా క్రిప్టోగ్రాఫిక్గా నిర్ధారించదు. ఆ ధ్రువీకరణ అమల్లోకి వచ్చే వరకు `source`ను విశ్వసించని సూచనగా పరిగణించండి; దాని ఆధారంగా అధీకరణ నిర్ణయాలు తీసుకోవద్దు.

ఒక అధునాతన కాలర్ అదే వీడియో కోసం ఇప్పటికే అధీకరించబడిన `audioTranscript` ట్రాక్ను అందించవచ్చు. ఫ్యూజన్ సీమ్ ఒకే గడువు మరియు అబార్ట్ సిగ్నల్ కింద దృశ్య, ఆడియో పరిశీలనలను అమలు చేసి, వాటిని ఒక ఉమ్మడి టైమ్లైన్పై క్రమబద్ధీకరిస్తుంది, సరిగ్గా ఒకేలా ఉన్న నకళ్లను విలీనం చేస్తుంది, అలాగే ఒక వైపు మాత్రమే విజయవంతమైనప్పుడు పాక్షిక ఫలితాన్ని నివేదిస్తుంది. చెల్లని `audioTranscript` ఆ పాక్షిక ఫలితానికి దిగజారుతుంది — దృశ్య వివరణ ఉంచబడుతుంది మరియు ఆడియో బ్రాంచ్ శుద్ధీకరించిన వైఫల్య కోడ్ను నమోదు చేస్తుంది — మొత్తం వీడియోను విఫలం చేయడానికి బదులుగా. ప్రతి బ్రాంచ్ లభ్యత, పాక్షిక ఫ్లాగ్, అలాగే శుద్ధీకరించిన వైఫల్య కోడ్లు వివరించబడిన ఫలితంలో, గార్డ్రైల్ మెటాడేటాలో (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), ఫలిత-క్యాష్ మెటాడేటాలో, అలాగే బ్రిడ్జ్ ఫ్యూజన్ కౌంటర్లలో భద్రపరచబడతాయి. డిఫాల్ట్ Video Bridge మార్గం స్పీచ్-టు-టెక్స్ట్ను ప్రారంభించదు లేదా రెండో మీడియా కాపీని డౌన్లోడ్ చేయదు; ఆ స్పష్టమైన ట్రాక్ లేకుండా, అది వీడియోకు మాత్రమే పరిమితమై ఉంటుంది.

**ట్రాన్స్క్రిప్ట్ నిల్వ (#12150 P1).** Video Bridge (ఇదే స్వయంగా ఆప్ట్-ఇన్) ఒక ట్రాన్స్క్రిప్ట్ క్యూను రెండర్ చేసినప్పుడల్లా ఇది స్వయంచాలకంగా వర్తిస్తుంది — ప్రత్యేక నిల్వ ఫ్లాగ్ ఏదీ లేదు. ఒక అభ్యర్థన ఏదైనా ట్రాన్స్క్రిప్ట్ క్యూను (కాలర్ ప్రకటించిన `transcript` లేదా ఫ్యూజ్ చేసిన `audioTranscript`) రెండర్ చేసినప్పుడు, గార్డ్రైల్ దానిని `videoBridgeObserved`గా గుర్తించి వీడియో వివరణకు సవరించబడిన షాడోను ఉత్పత్తి చేస్తుంది — స్ట్రింగ్ను సమీకరించే ముందు నిర్మిత క్యూ ఫీల్డ్ను ప్రత్యామ్నాయం చేయడం ద్వారా, ప్రతి క్యూ యొక్క స్వేచ్ఛా-టెక్స్ట్ బాడీని `[redacted-video-transcript]`తో భర్తీ చేసిన అదే రెండరింగ్ (ఫ్లాటెన్ చేసిన టెక్స్ట్ను పార్స్ చేయడం ద్వారా ఎప్పుడూ కాదు; అందువల్ల `]`ను కలిగి ఉన్న `[inaudible]`/`[music]` వంటి బాడీలతో సహా, ప్రతికూలమైనదైనా సాధారణమైనదైనా ఏ క్యూ కంటెంట్ కూడా మిగలదు). నిల్వ చేయబడిన కాల్-లాగ్ అభ్యర్థన బాడీ, కంటెంట్ సమానత్వం ఆధారంగా సరిపోల్చి, వీడియో నుంచి ఉత్పన్నమైన ప్రతి టెక్స్ట్ భాగాన్ని ఆ సవరించబడిన షాడోతో మార్చుతుంది; పూర్తయిన ప్రీ-కాల్ గార్డ్రైల్ పేలోడ్ నుంచి `fullText` యాంకర్ మళ్లీ చదవబడుతుంది, కాబట్టి తరువాతి చైన్ గార్డ్రైల్స్ (PII మరియు క్రెడెన్షియల్ మాస్కర్లు, ప్రాధాన్యతలు 10/95) వివరణ టెక్స్ట్ను అదే స్థానంలో తిరిగి వ్రాసిన తర్వాత, అలాగే సిస్టమ్-ప్రాంప్ట్/హ్యాండ్ఆఫ్/మెమరీ ఇంజెక్షన్ మెసేజ్ అర్రేను పునరాకృతీకరించిన తర్వాత కూడా సరిపోలిక విజయవంతమవుతుంది. మోడల్కు అప్స్ట్రీమ్గా పంపబడే బాడీ మారదు. పరిశీలించబడిన అభ్యర్థన ఎటువంటి శాశ్వత Memoryని కూడా నింపదు (అభ్యర్థన మరియు ప్రతిస్పందన రెండింటి నుంచి ఉత్పన్నమయ్యే ఎక్స్ట్రాక్షన్ దాటవేయబడుతుంది), కాబట్టి మోడల్ స్వంత సమాధానం ట్రాన్స్క్రిప్ట్ టెక్స్ట్ను Memoryలోకి ప్రతిధ్వనింపజేయలేదు.

ఇప్పటికీ తెరిచి ఉన్న నిల్వ ఉపరితలాలు, తదుపరి చర్య కోసం ట్రాక్ చేయబడుతున్నాయి (**P2**, #12430): వివరణాత్మక-లాగ్ ఆర్టిఫాక్ట్లోని ముడి ప్రీ-గార్డ్రైల్ క్లయింట్-అభ్యర్థన స్నాప్షాట్; `previous_response_id` కొనసాగింపు ఫెయిల్-క్లోజ్డ్ ప్రవర్తన; సంశ్లేషిత స్ట్రింగ్ ప్రాంప్ట్లో ట్రాన్స్క్రిప్ట్ను పొందుపరిచే డెరైవ్డ్-ప్రాంప్ట్ అంతర్గత డిస్పాచ్లు (పైప్లైన్ దశలు, కాంటెక్స్ట్-హ్యాండ్ఆఫ్); అలాగే ట్రాన్స్క్రిప్ట్ను కోట్ చేసే మోడల్ సమాధానానికి చెందిన ప్రతిస్పందన బాడీ / సెమాంటిక్-క్యాష్ కాపీ. ఇవి P1 యొక్క నిల్వ చేయబడిన-అభ్యర్థన-బాడీ + Memory పరిధికి వెలుపల ఉన్న ముడి/ప్రతిస్పందన-తరగతి లేదా ఆప్ట్-ఇన్ ఉపరితలాలు.

అంతర్గత `/api/modality-bridge/video/drilldown` జీవచక్రం ఒక ప్రత్యేకమైన, లూప్బ్యాక్/టోకెన్-ప్రమాణీకృత క్యాష్ సబ్స్ట్రేట్. ప్రతి ఆపరేషన్కు ఒక ప్రమాణిత అపారదర్శక ప్రిన్సిపల్ ID కూడా అవసరం. ఒక ప్రొడక్షన్ కాలర్ను ప్రారంభించే ముందు, అది ప్రమాణీకరించబడిన టెనెంట్ నుంచి ఆ IDని ఉత్పన్నం చేయాలి మరియు క్లయింట్ ఎంచుకున్న విలువను ఎప్పుడూ ఫార్వర్డ్ చేయకూడదు. క్యాష్ కీలు ఆ ప్రిన్సిపల్ను ప్రమాణిత సెషన్ మరియు వీడియో-రిఫరెన్స్ IDలకు బంధిస్తాయి, వాటి SHA-256-ఉత్పన్న కీలను మాత్రమే నిల్వ చేస్తాయి, అలాగే రీడ్లు మరియు తొలగింపు రెండింటినీ అదే ప్రిన్సిపల్కు పరిమితం చేస్తాయి. క్యాష్ ప్రతి ఎంట్రీకి గరిష్ఠంగా 16 ఉత్పన్న JPEG ఫ్రేమ్లను నిల్వ చేస్తుంది, పది నిమిషాల తర్వాత వాటిని గడువు ముగిసినవిగా చేస్తుంది, అలాగే పరిమిత `start`/`end` రీడ్లు లేదా స్పష్టమైన సెషన్ తొలగింపును మద్దతిస్తుంది.

ప్రతి ప్రిన్సిపల్ 16 ఎంట్రీలు మరియు 64 MiB ప్రమాణిత JPEG డేటాకు పరిమితం చేయబడుతుంది. ఆ పరిమితులు గ్లోబల్ 64-ఎంట్రీలు/256 MiB గరిష్ఠ పరిమితి నుంచి స్వతంత్రంగా ఉంటాయి: గ్లోబల్ LRU ఎవిక్షన్ను పరిగణించే ముందు, ప్రిన్సిపల్ కోటా ఒత్తిడి ఆ ప్రిన్సిపల్కు చెందిన అతి తక్కువగా ఇటీవల ఉపయోగించిన ఎంట్రీలను మాత్రమే తొలగిస్తుంది. క్యాష్ కార్యకలాపాల సమయంలో గడువు ముగిసిన ఎంట్రీలు ప్రిన్సిపల్ మరియు గ్లోబల్ అకౌంటింగ్ రెండింటి నుంచి తొలగించబడతాయి; అయితే రద్దు మరియు ధ్రువీకరణ వైఫల్యం పాక్షిక ప్రత్యామ్నాయాన్ని కమిట్ చేయవు.

క్యాష్ ప్రమాణితంకాని Base64, అధిక ప్యాడింగ్, JPEG కాని మీడియా, తప్పుగా రూపొందిన లేదా కుదించబడిన JPEGలను, అలాగే పరిమిత పూర్తి-చిత్ర `sharp` డీకోడ్ సమయంలో హెచ్చరికను ఉత్పత్తి చేసే JPEGలను తిరస్కరిస్తుంది. అంగీకరించిన ప్రతి చిత్రాన్ని ఇది ప్రమాణిత JPEGగా తిరిగి ఎన్కోడ్ చేస్తుంది, కాలర్ ఫీల్డ్లను విశ్వసించకుండా డీకోడ్ చేసిన బైట్ల నుంచి వెడల్పు మరియు ఎత్తును ఉత్పన్నం చేస్తుంది, అలాగే చివరలో ఉన్న ఏ పాలిగ్లాట్ బైట్లనైనా నిల్వ చేయకుండా విస్మరిస్తుంది. పరిమిత ప్రమాణిత కంప్రెస్డ్ బఫర్ మాత్రమే రెండు కోటాలకు లెక్కించబడుతుంది. JSON వైర్ పరిమితిలో 32 MiB డీకోడ్ చేసిన-ఇన్పుట్ గరిష్ఠ పరిమితికి సంబంధించిన Base64 ఓవర్హెడ్ కూడా ఉంటుంది. నిల్వ చేసిన ప్రతి డెరివేషన్ దాని ధ్రువీకరించిన JPEG ఫార్మాట్/రిజల్యూషన్, శాంప్లింగ్ విధానం, డెరివేషన్ వెర్షన్, సృష్టి సమయం, సర్వర్ లెక్కించిన కంటెంట్ హ్యాష్, హ్యాష్ చేసిన పేరెంట్ రిఫరెన్స్, అలాగే విశ్వసనీయ కాలర్ యొక్క పేరెంట్-కంటెంట్ హ్యాష్ను నమోదు చేస్తుంది. అటామిక్ క్యాష్ కమిట్కు ముందు అసింక్రోనస్ డీకోడ్/హ్యాష్ దశల మధ్య రద్దు తనిఖీ చేయబడుతుంది.

పునర్వినియోగిస్తుంది. మొత్తం-వీడియో ఫలిత క్యాష్, అవుట్పుట్ను మార్చే ప్రతి ఇన్పుట్
ఆధారంగా కీ చేయబడుతుంది — ప్రాంప్ట్, సమర్థవంతమైన మోడల్, శాంప్లింగ్ విధానం, ఫ్రేమ్ల
సంఖ్య, సెమాంటిక్ విశ్లేషణ మోడ్, సాధారణీకరించిన ఫోకస్ హింట్ యొక్క SHA-256
ఫింగర్ప్రింట్, ఫోకస్ విండో, `transcript`, `audioTranscript` మరియు కాంటాక్ట్-షీట్
ఫ్లాగ్ — కాబట్టి వాటిలో ఏ డైమెన్షన్ మారినా అది క్యాష్ మిస్ అవుతుంది, పాత డేటా
పునర్వినియోగం ఎప్పుడూ జరగదు. విజువల్ డీడప్ విధానం వెర్షన్, థ్రెషోల్డ్ మరియు పరిమిత
క్యాండిడేట్-ఫ్రేమ్ల సంఖ్య కూడా ఫలిత-క్యాష్ కీ మరియు మెటాడేటాలో స్పష్టంగా ఉంటాయి;
అందువల్ల విధానం మారితే పాత మొత్తం-వీడియో వివరణను పునర్వినియోగించలేరు. ఫలిత-క్యాష్
v4 మెటాడేటా మోడ్ మరియు ఫింగర్ప్రింట్ను నిలుపుకుంటుంది, కానీ అసలు వినియోగదారు
టాస్క్ను ఎప్పుడూ నిలుపుకోదు. గార్డ్రైల్ మెటాడేటా అభ్యర్థించిన మరియు సమర్థవంతమైన
విశ్లేషణ మోడ్లు రెండింటినీ నివేదిస్తుంది; ఉపయోగించగల వినియోగదారు టెక్స్ట్ లేకుండా
అభ్యర్థించిన `focused` మోడ్, సమర్థవంతంగా `full`గా నివేదించబడుతుంది.

గార్డ్రైల్ మద్దతు ఉన్న ప్రతి వీడియో భాగాన్ని వెలికితీస్తుంది, కానీ
`modalityBridgeVideoMaxVideos` కంటే ఎక్కువ వీడియోలను వివరించదు.
`supportsVideo === false` అని నిరూపితమైన టార్గెట్ కోసం, విఫలమైన మరియు పరిమితిని
మించిన వీడియోలు స్పష్టమైన సురక్షిత టెక్స్ట్ మార్కర్లుగా మారతాయి, తద్వారా ముడి వీడియో
ఏదీ మిగలదు. సామర్థ్యం తెలియనప్పుడు, ఆ భాగాలు మార్చకుండా ఉంచబడతాయి.
`supportsVideo === true` ఉన్న టార్గెట్లు బ్రిడ్జ్ను బైపాస్ చేస్తాయి.
క్లయింట్ అభ్యర్థన అబార్ట్ సిగ్నల్ డౌన్లోడ్, బ్రోకర్ క్యూ, సబ్ప్రాసెస్లు మరియు
క్యాప్షన్ కాల్ల ద్వారా వ్యాపిస్తుంది; అబార్ట్లు వీడియోల మధ్య ప్రాసెసింగ్ను ఆపుతాయి
మరియు ముడి మీడియాను అనుమతించే విధంగా ఎప్పుడూ విఫలం కావు.

రన్టైమ్ సెట్టింగ్లు DB-ఆధారితమైనవి మరియు Zod ద్వారా ధృవీకరించబడతాయి:

| కీ                                  | డిఫాల్ట్    | పరిధి / ప్రవర్తన                                                                                                      |
| ----------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | ఐచ్ఛిక రన్టైమ్, ఎంపికచేసి ప్రారంభించాలి                                                                               |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` సాధారణ క్యాప్షన్లను నిలుపుతుంది; `focused` పరిమితమైన, విశ్వసించరాని తాజా-వినియోగదారు సందర్భాన్ని ఉపయోగిస్తుంది |
| `modalityBridgeVideoModel`          | `""`        | Vision Bridge మోడల్ను వారసత్వంగా పొందుతుంది                                                                           |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                                  |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, లేదా నిష్పత్తి ఆధారిత `segment_aware`; డిటెక్టర్ వైఫల్యమైతే `uniform`కు ఫాల్బ్యాక్ అవుతుంది |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                                   |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                                        |

120 సెకన్లకు మించిన పాత నిల్వచేసిన Video టైమ్అవుట్ విలువలు బ్రోకర్ డెడ్లైన్కు
క్లాంప్ చేయబడతాయి; ఆ పరిమితిని మించిన కొత్త సెట్టింగ్ల రైట్లు తిరస్కరించబడతాయి.
`GET /api/modality-bridge/video/runtime`కు ఆథెంటికేషన్ లేదా రన్టైమ్ ప్రోబింగ్కు
ముందు విశ్వసనీయంగా స్టాంప్ చేసిన లూప్బ్యాక్ లోకాలిటీ అవసరం, ఆ తర్వాత మేనేజ్మెంట్
ఆథరైజేషన్ అవసరం. ఇది `available`, శానిటైజ్ చేసిన FFmpeg/ffprobe వెర్షన్లు మరియు
రన్టైమ్ అందుబాటులో లేనప్పుడు ఒక స్థిరమైన కారణాన్ని మాత్రమే తిరిగి ఇస్తుంది. అంతర్గత
ఎక్స్ట్రాక్షన్ ఎండ్పాయింట్ పబ్లిక్ అప్లోడ్ API కాదు: క్యూ సాచురేషన్ `503`తో పాటు
`Retry-After`ను తిరిగి ఇస్తుంది, కాలర్ డిస్కనెక్ట్ `499`ను తిరిగి ఇస్తుంది మరియు
స్థిరమైన బ్రోకర్ డెడ్లైన్ `504`ను తిరిగి ఇస్తుంది. మార్చబడిన రెస్పాన్స్లు Vision
లేదా Audio సెగ్మెంట్లను తొలగించకుండా, కేంద్ర
`x-omniroute-modality-bridge` హెడర్కు
`video->text;model=<visionModel>;parts=<videos>`ను జోడిస్తాయి.

### PII మాస్కర్ (`piiMasker.ts`)

**రెండు** దశల్లోనూ అమలవుతుంది.

- **`preCall`** పేలోడ్ను క్లోన్ చేసి, `system`, `messages`, `input` మరియు
  `prompt`లోని అంశాల గుండా వెళుతుంది (సాధారణ స్ట్రింగ్ అంశాలతో సహా), అలాగే స్ట్రింగ్
  `content`/`text` ఫీల్డ్లకు (`@/shared/utils/inputSanitizer` నుండి)
  `processPII()`ను వర్తింపజేస్తుంది. `PII_REDACTION_ENABLED=true` ఉన్నప్పుడు,
  గుర్తించిన PII అవుట్బౌండ్ పేలోడ్లో రిడాక్ట్ చేయబడుతుంది. ఇది
  `INPUT_SANITIZER_MODE`కు స్వతంత్రం (అది ప్రాంప్ట్-ఇంజెక్షన్ విధానాన్ని మాత్రమే
  నియంత్రిస్తుంది). రిడాక్షన్ ఆఫ్లో ఉన్నప్పుడు, కంటెంట్ను తిరిగి రాయకుండా కాల్
  గుర్తింపు సంఖ్యలను రికార్డ్ చేస్తుంది.
- **`postCall`** రెస్పాన్స్ను డీప్-క్లోన్ చేసి, `sanitizePIIResponse()`తో పాటు
  Responses-API-ఆకృతి మాస్కర్ను (`maskResponsesOutput` — ఇది
  `output_text` మరియు `output[].content[].text`ను కవర్ చేస్తుంది) అమలు చేస్తుంది.
  ఏదైనా రిడాక్షన్ జరిగితే, సవరించిన రెస్పాన్స్ అసలు రెస్పాన్స్ను భర్తీ చేస్తుంది.

గార్డ్రైల్ ఎప్పుడూ బ్లాక్ చేయదు; అది కేవలం అనోటేట్ చేస్తుంది
(`meta.detections`, `meta.redacted`) లేదా తిరిగి రాస్తుంది.

### ప్రాంప్ట్ ఇంజెక్షన్ (`promptInjection.ts`)

వినియోగదారు అందించిన కంటెంట్లోని ప్రతికూల నిర్మాణాలను గుర్తించి, కాన్ఫిగర్ చేసిన
విధానాన్ని అమలు చేస్తుంది. ప్రవర్తన ఎన్విరాన్మెంట్ వేరియబుల్లు మరియు కన్స్ట్రక్టర్
ఆప్షన్ల ద్వారా నియంత్రించబడుతుంది:

| సెట్టింగ్         | ఎన్విరాన్మెంట్ వేరియబుల్                                                                                             | డిఫాల్ట్ | ప్రభావం                                                                                                                                                                                                   |
| ----------------- | -------------------------------------------------------------------------------------------------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ప్రారంభించబడింది  | `INPUT_SANITIZER_ENABLED`                                                                                            | `true`   | `false` అయినప్పుడు, గార్డ్రైల్ షార్ట్-సర్క్యూట్ అవుతుంది.                                                                                                                                                 |
| మోడ్              | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                                      | `warn`   | ఇంజెక్షన్ విధానం: `block`, `warn`, లేదా `log`. (వెనుకబడిన అనుకూలత కోసం `redact` ఆమోదించబడుతుంది, కానీ ఇంజెక్షన్ టెక్స్ట్ను **తొలగించదు**; అభ్యర్థన PII రీరైట్ను `PII_REDACTION_ENABLED` నియంత్రిస్తుంది.) |
| బ్లాక్ థ్రెషోల్డ్ | `blockThreshold` ఎంపిక / `INPUT_SANITIZER_BLOCK_THRESHOLD` (`INJECTION_GUARD_BLOCK_THRESHOLD` అనే ప్రత్యామ్నాయ పేరు) | `high`   | బ్లాక్ చేయడానికి అవసరమైన కనిష్ఠ తీవ్రత. డిఫాల్ట్గా మధ్యస్థ తీవ్రత కేవలం పరిశీలనకే పరిమితం.                                                                                                                |

**మోడ్ ప్రాధాన్యత క్రమం** (`getMode`): కాలర్ `options.mode` →
`INJECTION_GUARD_MODE` **DB ఫీచర్-ఫ్లాగ్ ఓవర్రైడ్** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` ఎన్విరాన్మెంట్ వేరియబుల్ → `INPUT_SANITIZER_MODE` ఎన్విరాన్మెంట్ వేరియబుల్ →
`warn`. అందువల్ల డాష్బోర్డ్ ఓవర్రైడ్ ఎన్విరాన్మెంట్ వేరియబుల్స్పై ప్రాధాన్యత పొందుతుంది, కాబట్టి Feature
Flags UI అమలులో ఉన్న గార్డ్ను ప్రత్యక్షంగా నియంత్రిస్తుంది (పునఃప్రారంభం అవసరం లేదు). DB రీడ్ ఫెయిల్-సేఫ్గా ఉంటుంది:
అది విఫలమైతే, గార్డ్ ఎన్విరాన్మెంట్ ఆధారిత ప్రవర్తనకు తిరిగి వెళ్తుంది; అలాగే ఎటువంటి
ఓవర్రైడ్ సెట్ చేయకపోతే, ప్రవర్తన పూర్తిగా ఎన్విరాన్మెంట్-మాత్రమే రిజల్యూషన్తో సమానంగా ఉంటుంది.

గుర్తింపు మూలాలు:

1. `@/shared/utils/inputSanitizer` నుండి `sanitizeRequest()` (పైప్లైన్లో
   ఇతర చోట్ల ఉపయోగించే షేర్డ్ డిటెక్టర్ సెట్).
2. అంతర్నిర్మిత `DEFAULT_GUARD_PATTERNS` (ప్రస్తుతం `system_override_inline` మరియు
   `markdown_system_block`; రెండింటి తీవ్రతా స్థాయి `high`).
3. కన్స్ట్రక్టర్ ఎంపికల ద్వారా పంపే ఐచ్ఛిక `customPatterns` (స్ట్రింగ్లు, రెగ్యులర్ ఎక్స్ప్రెషన్లు,
   లేదా `{ name, pattern, severity }` రికార్డ్లు).

`mode === "block"` **మరియు** కనీసం ఒక గుర్తింపు తీవ్రత
థ్రెషోల్డ్ను చేరుకున్నప్పుడు, `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }`ను తిరిగి ఇస్తుంది. `warn`/`log` మోడ్లలో గార్డ్రైల్ లాగ్ చేస్తుంది, కానీ
కాల్ను అనుమతిస్తుంది. రిజిస్ట్రీ ద్వారా వెళ్లకుండా ప్రాంప్ట్లను మూల్యాంకనం చేయాల్సిన
కాలర్ల కోసం షేర్డ్ హెల్పర్ `evaluatePromptInjection()` కూడా ఎక్స్పోర్ట్ చేయబడుతుంది.

**స్కాన్ పరిమితి (v3.8.20):** డిటెక్టర్ కలిపిన ప్రాంప్ట్ టెక్స్ట్లోని **మొదటి 16 KB**ను
మాత్రమే పరిశీలిస్తుంది — `src/shared/utils/inputSanitizer.ts`లో
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 బైట్లు). ప్యాటర్న్ లూప్ను అమలు చేయడానికి ముందు
`detectInjection()` మరియు `evaluatePromptInjection()` రెండూ `slice(0, MAX_INJECTION_SCAN_BYTES)`ను
ఉపయోగిస్తాయి. ఇంజెక్షన్ డైరెక్టివ్లు ఇన్పుట్ ప్రారంభానికి సమీపంలో ఉంటాయి, కాబట్టి ఇది గుర్తింపు సామర్థ్యాన్ని
బలహీనపరచకుండా అనేక వందల-KB పేలోడ్లపై regex CPU/GC వినియోగాన్ని పరిమితం చేస్తుంది (చూ.
#3932, #4041).

### క్రెడెన్షియల్ మాస్కర్ (`credentialMasker.ts`)

డిఫాల్ట్ చైన్లో చివరిగా (ప్రాధాన్యత `95`) **రెండు** దశల్లోనూ అమలవుతుంది. అవుట్బౌండ్ పేలోడ్లోని (సందేశ
కంటెంట్, టూల్-కాల్ ఆర్గ్యుమెంట్లు, టూల్ ఫలితాలు) **మరియు** ప్రొవైడర్ ప్రతిస్పందనలోని
సుపరిచిత API-కీ / సీక్రెట్-టోకెన్ ప్యాటర్న్లను రీడాక్ట్ చేస్తుంది. అందువల్ల ప్రాంప్ట్లో పేస్ట్ చేసిన క్రెడెన్షియల్
(లేదా టూల్ ఫలితం ద్వారా తిరిగి ప్రతిధ్వనించినది) అప్స్ట్రీమ్ ప్రొవైడర్కు లేదా తిరిగి క్లయింట్కు లీక్ కాదు.

- PII రీడాక్షన్ మాదిరిగానే **ఎంపిక చేసుకున్నప్పుడు మాత్రమే ప్రారంభమవుతుంది** (Hard Rule #20కు సమీప నియమం):
  `settings.credentialRedactionEnabled === true` **లేదా**
  `CREDENTIAL_REDACTION_ENABLED=true` అయితే తప్ప ఇది నిలిపివేయబడి ఉంటుంది. ఇది ఆఫ్లో ఉన్నప్పుడు, గార్డ్రైల్ ఎటువంటి చర్యా చేయదు —
  ఇది ఎప్పటికీ బ్లాక్ చేయదు మరియు ఎప్పటికీ రీరైట్ చేయదు.
- `redactCredentials()` పూర్తి పేలోడ్/ప్రతిస్పందన ట్రీలో ప్రయాణిస్తుంది (`walkValue()`,
  ప్రోటోటైప్-పల్యూషన్కు సురక్షితం, `WeakSet` ద్వారా సైకిల్కు సురక్షితం) మరియు సరిపోలికలను
  `[REDACTED:<type>]` ప్లేస్హోల్డర్తో భర్తీ చేస్తుంది; నిజంగా మారిన బ్రాంచ్లను మాత్రమే
  క్లోన్ చేస్తుంది.
- `CREDENTIAL_PATTERNS`లో LLM ప్రొవైడర్ కీలు (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS టోకెన్లు (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), పేమెంట్ కీలు (Stripe, Square), క్లౌడ్
  కీలు (AWS యాక్సెస్ కీ, Twilio, SendGrid, Mailgun), ప్రైవేట్ కీలు / JWTలు,
  క్రెడెన్షియల్లు కలిగిన కనెక్షన్ స్ట్రింగ్లు (`mongodb://user:pass@...`, మొదలైనవి), అలాగే
  సాధారణ `Authorization`/`x-api-key`/`api-key`/`apikey` హెడర్-విలువ
  ప్యాటర్న్ ఉన్నాయి. హెడర్ ఆకారపు కీలు (`authorization`, `x-api-key`, `api-key`,
  `apikey`) సాధారణ టెక్స్ట్ regex ద్వారా కాకుండా నిర్మాణాత్మకంగా రీడాక్ట్ చేయబడతాయి
  (విలువ మాత్రమే; `Bearer `/`Basic ` వంటి స్కీమ్ ప్రిఫిక్స్ అలాగే ఉంచబడుతుంది).
- గార్డ్రైల్ ఎప్పటికీ బ్లాక్ చేయదు; ఇది కేవలం రీరైట్ (`modifiedPayload` /
  `modifiedResponse`) చేసి, అనోటేట్ (`meta.credentialsRedacted`, `meta.count`) చేస్తుంది.

రిగ్రెషన్ గార్డ్: `tests/unit/credential-masker-guardrail.test.ts`.

## ప్రాథమిక కాంట్రాక్ట్ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true అయితే చైన్ వెంటనే నిలిచిపోతుంది
  message?: string; // బ్లాక్ చేసినప్పుడు ప్రదర్శించబడుతుంది
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // అభ్యర్థనను తిరిగి వ్రాయడానికి preCall ద్వారా తిరిగి ఇవ్వబడుతుంది
  modifiedResponse?: TValue; // ప్రతిస్పందనను తిరిగి వ్రాయడానికి postCall ద్వారా తిరిగి ఇవ్వబడుతుంది
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ఒక గార్డ్రైల్ `void`, `{}`, లేదా `{ block: false }`లో దేనినైనా తిరిగి ఇవ్వడం ద్వారా "మార్పు లేదు" అని సూచిస్తుంది. `modifiedPayload`/`modifiedResponse`ను తిరిగి ఇవ్వడం వల్ల, దిగువన ఉన్న గార్డ్రైల్స్ కోసం చైన్ ద్వారా ప్రవహించే విలువ భర్తీ చేయబడుతుంది.
`signal?: AbortSignal` కాలర్ జీవనచక్రాన్ని గార్డ్రైల్స్లోకి తీసుకువెళుతుంది. అభ్యర్థన అబార్ట్ కావడం ఉద్దేశపూర్వక fail-open మినహాయింపు: ముడి మీడియాకు మద్దతు లేదని తెలిసిన లక్ష్యానికి దాన్ని పునరుద్ధరించకుండా, మీడియా బ్రిడ్జ్లు పనిని ఆపి శుభ్రపరుస్తాయి.

## రిజిస్ట్రీ (`registry.ts`)

సింగిల్టన్ `guardrailRegistry` వీటిని అందిస్తుంది:

- `register(guardrail)` — ఒక గార్డ్రైల్ను జోడిస్తుంది (లేదా సాధారణీకరించిన పేరు ఆధారంగా భర్తీ చేస్తుంది) మరియు ఆరోహణ `priority` క్రమంలో మళ్లీ అమర్చుతుంది.
- `clear()` / `list()` — పరిపాలనా సహాయకాలు.
- `runPreCallHooks(payload, context)` — సక్రియ గార్డ్రైల్స్పై పునరావృతమవుతుంది, `modifiedPayload` ద్వారా పేలోడ్ను పంపిస్తుంది మరియు మొదటి `block: true` వద్ద ఆగిపోతుంది.
- `runPostCallHooks(response, context)` — ప్రతిస్పందన వైపు కూడా ఇదే ప్రవాహం.
- `resetGuardrailsForTests({ registerDefaults })` — స్థితిని క్లియర్ చేస్తుంది మరియు స్వచ్ఛమైన పరీక్ష ఐసోలేషన్ కోసం ఐచ్ఛికంగా డిఫాల్ట్లను మళ్లీ నమోదు చేస్తుంది.

రెండు రన్నర్లూ `{ blocked, payload|response, results, guardrail?, message? }`ను తిరిగి ఇస్తాయి. ఇక్కడ `results` అనేది ప్రతి గార్డ్రైల్కు సంబంధించిన `blocked`, `skipped`, `modified`, `error`, మరియు `meta` ఫీల్డ్లను కలిగి ఉన్న `GuardrailExecutionResult` రికార్డ్ల అర్రే; ఇది ట్రేసింగ్కు ఉపయోగకరంగా ఉంటుంది.

### ప్రతి అభ్యర్థనకు గార్డ్రైల్స్ను నిలిపివేయడం

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` ప్రస్తుత అభ్యర్థన కోసం దాటవేయాల్సిన గార్డ్రైల్ పేర్ల డూప్లికేట్లు తొలగించబడిన జాబితాను సమీకరిస్తుంది. మూలాలు (అన్నీ ఐచ్ఛికం, అన్నీ విలీనం చేయబడతాయి):

- `apiKeyInfo.disabledGuardrails`
- అభ్యర్థన బాడీలో `disabledGuardrails` (అగ్ర-స్థాయి)
- అభ్యర్థన బాడీలో `metadata.disabledGuardrails`
- హెడర్ `x-omniroute-disabled-guardrails` (లేదా పాత
  `x-disabled-guardrails`)

విలువలు స్ట్రింగ్ల అర్రేలు లేదా కామాతో వేరు చేసిన స్ట్రింగ్ కావచ్చు; పేర్లు లోయర్కేస్ కబాబ్-కేస్కు సాధారణీకరించబడతాయి (`pii_masker` → `pii-masker`). ఫలితం `context.disabledGuardrails` ద్వారా రిజిస్ట్రీకి పంపబడుతుంది; అది సరిపోలే గార్డ్రైల్స్ను దాటవేస్తుంది (`results`లో `skipped: true`).

## అమలు క్రమం

`src/sse/handlers/chat.ts` మరియు
`open-sse/handlers/chatCore.ts` ద్వారా ప్రవహించే ప్రతి అభ్యర్థనకు:

1. `resolveDisabledGuardrails(...)` API కీ, బాడీ మరియు హెడర్ల నుండి దాటవేయాల్సిన జాబితాను రూపొందిస్తుంది.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` గార్డ్రైల్లను ఆరోహణ ప్రాధాన్యత క్రమంలో అమలు చేస్తుంది:
   - నిలిపివేయబడిన గార్డ్రైల్లు `skipped`గా నమోదు చేయబడతాయి.
   - ప్రతి గార్డ్రైల్కు చెందిన `preCall`, `modifiedPayload` ద్వారా పేలోడ్ను తిరిగి వ్రాయవచ్చు.
   - మొదటి `block: true` చైన్ను తక్షణమే నిలిపివేస్తుంది మరియు హ్యాండ్లర్ గార్డ్రైల్ తిరస్కరణ ప్రతిస్పందనను అందిస్తుంది.
3. (అవసరమైతే తిరిగి వ్రాయబడిన) పేలోడ్ కాంబో రూటింగ్ మరియు అప్స్ట్రీమ్ డిస్పాచ్లోకి ప్రవహిస్తుంది.
4. ప్రతిస్పందన సమీకరించబడిన తర్వాత, `guardrailRegistry.runPostCallHooks(...)` ప్రతిస్పందనపై అదే చైన్ను అమలు చేస్తుంది. ఇక్కడ `block: true` అప్స్ట్రీమ్ ప్రతిస్పందనను విస్మరిస్తుంది.

ఎక్సెప్షన్లను విసిరే గార్డ్రైల్లు `error: <message>`తో నమోదు చేయబడతాయి మరియు
`logger.warn` ద్వారా లాగ్ చేయబడతాయి, కానీ చైన్ కొనసాగుతుంది — ఇది ఉద్దేశపూర్వకంగా ఫెయిల్-ఓపెన్ విధానాన్ని అనుసరిస్తుంది.

| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`          | గుర్తింపును పూర్తిగా నిలిపివేయడానికి `false`గా సెట్ చేయండి.                                              |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`          | ఇంజెక్షన్ విధానం: `warn`, `block`, లేదా `log`. లెగసీ విలువ `redact` ఇంజెక్షన్ టెక్స్ట్ను తిరిగి వ్రాయదు. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`          | ఇంజెక్షన్ గార్డ్ కోసం మోడ్; ఇది env varsను **ఓవర్రైడ్** చేసే DB ఫీచర్ ఫ్లాగ్ కూడా (DB > ENV).            |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`          | `MODE=block` తిరస్కరించే కనిష్ఠ తీవ్రత: `high` (డిఫాల్ట్), `medium`, లేదా `low`.                         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`          | `INPUT_SANITIZER_BLOCK_THRESHOLD`కు లెగసీ మారుపేరు.                                                      |
| `PII_REDACTION_ENABLED`               | `pii-masker`                | `true` అయినప్పుడు, అభ్యర్థనలోని PII రిడాక్ట్ చేయబడుతుంది (ఇంజెక్షన్ మోడ్తో సంబంధం లేకుండా).              |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (డౌన్స్ట్రీమ్) | ప్రతిస్పందన వైపు మాస్కర్ ప్రవర్తనను నియంత్రిస్తుంది.                                                     |

మోడాలిటీ బ్రిడ్జ్ గార్డ్రైల్లు env vars నుండి కాకుండా, DB-ఆధారిత సెట్టింగ్ల
స్టోర్ (`getSettings()`) నుండి రన్టైమ్ కాన్ఫిగరేషన్ను చదువుతాయి. విజన్కు సంబంధించిన ప్రాథమిక కీలు
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, మరియు
`modalityBridgeCacheMaxEntries`. లెగసీ
`visionBridge*` కీలు డాక్యుమెంట్ చేయబడిన ఒక-సైకిల్ రీడ్ ఫాల్బ్యాక్గా మాత్రమే
ఆమోదించబడతాయి; డ్యాష్బోర్డ్ రైట్లు ప్రాథమిక కీలను ఉపయోగిస్తాయి. డిఫాల్ట్లు మరియు ఫాల్బ్యాక్
రిజాల్వర్ `src/shared/constants/modalityBridgeDefaults.ts`లో ఉంటాయి, లెగసీ
స్థిరాంకాలు `src/shared/constants/visionBridgeDefaults.ts`లో కొనసాగించబడతాయి.

ఆడియో `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout`, మరియు `modalityBridgeAudioMaxClips`తో పాటు, షేర్డ్
`modalityBridgeCache*` సెట్టింగ్లను ఉపయోగిస్తుంది. ఈ కీలు మోడాలిటీ బ్రిడ్జ్ స్కీమాతో
పరిచయం చేయబడినందున ఆడియోకు లెగసీ-కీ ఫాల్బ్యాక్ లేదు.

వీడియో `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, మరియు
`modalityBridgeVideoTimeout`తో పాటు, షేర్డ్ `modalityBridgeCache*` సెట్టింగ్లను ఉపయోగిస్తుంది.
FFmpeg/ffprobe ఐచ్ఛిక ఆపరేషనల్ డిపెండెన్సీలు కావడం మరియు ఫ్రేమ్ క్యాప్షనింగ్ అదనపు లేటెన్సీతో పాటు మోడల్ ఖర్చును పెంచడం వల్ల
ఇది డిఫాల్ట్గా నిలిపివేయబడుతుంది.

## అనుకూల Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

దశలు:

1. `BaseGuardrail`ను విస్తరించే `src/lib/guardrails/myGuardrail.ts`ను సృష్టించండి.
2. `preCall` మరియు/లేదా `postCall`ను అమలు చేయండి.
3. ఇంపోర్ట్ సమయంలో నమోదు చేయండి (`registerDefaultGuardrails` నుండి పుష్ చేయండి) లేదా
   రన్టైమ్లో `guardrailRegistry.register(...)`ను కాల్ చేయండి — అదే సాధారణీకరించిన
   పేరు కలిగిన మునుపటి ఏ guardrailనైనా రిజిస్ట్రీ భర్తీ చేస్తుంది.
4. `tests/unit/` కింద పరీక్షలను జోడించండి (ఇప్పటికే ఉన్న ఉదాహరణలు:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## పరీక్షించడం

తెలిసిన స్థితి నుండి ప్రారంభించడానికి పరీక్షల మధ్య `resetGuardrailsForTests()`ను ఉపయోగించండి.
ఖాళీ రిజిస్ట్రీతో ప్రారంభించి, పరీక్షలో ఉన్న guardrailsను మాత్రమే నమోదు చేయడానికి
`{ registerDefaults: false }`ను పాస్ చేయండి. Vision Bridge డిపెండెన్సీ
ఇంజెక్షన్ను (`deps.getSettings`, `deps.callVisionModel`) అంగీకరిస్తుంది; Audio Bridge
సెట్టింగ్లు, సామర్థ్యాలు, STT మోడల్ ఎంపిక, క్రెడెన్షియల్ తనిఖీలు మరియు ట్రాన్స్క్రిప్షన్
కోసం సమానమైన అనుసంధాన బిందువులను అందిస్తుంది. కాబట్టి పరీక్షలు DB లేదా నెట్వర్క్
యాక్సెస్ లేకుండానే రెండు ప్రవాహాలనూ పరీక్షించగలవు.

## ఇంజెక్షన్-గార్డ్ రూట్ కవరేజ్ & రెడ్-టీమ్ (దశ 8 · బ్లాక్ D)

ఇంజెక్షన్-గార్డ్ (`createInjectionGuard` / `withInjectionGuard`) వినియోగదారు ప్రాంప్ట్లను
అంగీకరించే అన్ని రూట్లను కవర్ చేస్తుంది. ఇది `INJECTION_GUARD_MODE`ను గౌరవిస్తుంది
(డిఫాల్ట్ `warn` = లాగ్ మాత్రమే; `block` = HTTP 400 `SECURITY_001`ను తిరిగి ఇస్తుంది).

| రకం                 | రూట్లు                                                                                                                                               | డిఫాల్ట్ మోడ్ |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| టెక్స్ట్ (ప్రస్తుత) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn          |
| జనరేటివ్            | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn          |
| డేటా                | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn          |

టెక్స్ట్ సంగ్రహణ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`ను కవర్ చేస్తుంది.

**రెడ్-టీమ్ (ప్రతి రాత్రి, `nightly-llm-security.yml`):** ప్రతి రూట్
`INJECTION_GUARD_MODE=block`లోని OWASP-LLM కార్పస్ను బ్లాక్ చేస్తుందని promptfoo ధ్రువీకరిస్తుంది;
garak ప్రోబ్లను అమలు చేస్తుంది (సీక్రెట్ లేకపోతే దాటవేస్తుంది).
స్థిరత్వం కోసం `moderations` చేర్చబడింది — బ్లాక్-మోడ్లోని ఆపరేటర్లు
`resolveDisabledGuardrails` ద్వారా దానికి మినహాయింపు ఇవ్వగలరు.

ప్రతి రాత్రి అమలయ్యే వర్క్ఫ్లో (`.github/workflows/nightly-llm-security.yml`, cron + మాన్యువల్
డిస్పాచ్)లో రెండు జాబ్లు ఉన్నాయి:

- **`promptfoo-guard` (బ్లాకింగ్)** — `INJECTION_GUARD_MODE=block`తో
  `promptfoo eval -c promptfooconfig.yaml`ను అమలు చేస్తుంది. ప్రతి ప్రతికూల సందర్భం
  (ఉదా. "మునుపటి సూచనలన్నింటినీ విస్మరించు…", DAN-శైలి జైల్బ్రేక్లు) ప్రతిస్పందనలో
  `error.code === "SECURITY_001"` ఉందని నిర్ధారిస్తుంది, అంటే గార్డ్ నిజంగానే అభ్యర్థనను
  తిరస్కరించిందని అర్థం.
- **`garak` (సలహాత్మకం)** — స్థానిక OmniRoute ఇన్స్టాన్స్కు
  (`http://localhost:20128/v1`) వ్యతిరేకంగా garak `--probes promptinject,dan,leakreplay`ను
  అమలు చేస్తుంది. ఇది ప్రొవైడర్ సీక్రెట్ (`PROMPTFOO_PROVIDER_KEY`)పై ఆధారపడి ఉంటుంది;
  సీక్రెట్ లేకపోతే సజావుగా దాటవేయబడుతుంది మరియు `|| true` ప్రత్యయం జోడించబడుతుంది,
  కాబట్టి ఇది CIని విఫలం చేయకుండా నివేదిస్తుంది.

గార్డ్ సహాయకం (`createInjectionGuard` / `withInjectionGuard`) యొక్క కవరేజ్
ప్రాంప్ట్ను కలిగి ఉన్న ప్రతి `/v1` రూట్కు విస్తరిస్తుంది; ప్రాంప్ట్ టెక్స్ట్ను
`src/shared/utils/inputSanitizer.ts`లోని `extractMessageContents()` ద్వారా
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` నుండి
తీసుకుంటారు.
