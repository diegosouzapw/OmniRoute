## అవలోకనం

అన్ని OmniRoute నిర్వహణ API రూట్లు మూడు రక్షణ స్థాయిలలో ఒకదానిగా వర్గీకరించబడతాయి. వర్గీకరణ స్థిరంగా ఉంటుంది, `src/server/authz/routeGuard.ts`లో నిర్వచించబడుతుంది, అలాగే ఇతర ఏ auth శాఖ అమలవడానికి ముందే మూల్యాంకనం చేయబడుతుంది.

## స్థాయిలు

### స్థాయి 1 — LOCAL_ONLY

**అమలు చేసేది:** `isLocalOnlyPath(path)` → loopback host తనిఖీ  
**బైపాస్:** డిఫాల్ట్గా ఏదీ లేదు. అభ్యర్థనలో `manage` scope ఉన్న చెల్లుబాటు అయ్యే API key ఉన్నప్పుడు, `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`లోని పాత్లకు మాత్రమే పరిమిత మినహాయింపు ఉంటుంది ([Manage-scope మినహాయింపు](#manage-scope-carve-out) చూడండి).

ఈ రూట్లు child processలను ప్రారంభిస్తాయి లేదా runtime codeను అమలు చేస్తాయి. వీటిని non-loopback ట్రాఫిక్కు అందుబాటులో ఉంచడం వలన, చెల్లుబాటు అయ్యే JWTని పొందిన దాడిదారు (ఉదా., Cloudflared/Ngrok tunnel ద్వారా) process spawningను ప్రారంభించగలడు — ఇది తెలిసిన CVE వర్గం ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj అంటే ఏమిటి (దాడి వర్గం):** ఒక నిర్వహణ/agent server subprocessను (`npm install`, `node`, browser, proxy, `git`, `tar`, …) ప్రారంభించే endpointను బహిర్గతం చేస్తుంది. ఆ endpointను host వెలుపలి నుండి చేరుకోగలిగితే — operator OmniRouteను nginx/Cloudflare/Tailscale tunnel వెనుక ఉంచి JWT లీక్ కావడం వల్లగానీ, లేదా auth తప్పుగా కాన్ఫిగర్ చేయబడటం వల్లగానీ — దాడిదారు "APIని కాల్ చేయడం"ను "hostపై commandను అమలు చేయడం"గా మారుస్తాడు (remote code execution). Spawn చేయగల ప్రతి రూట్పై **ఏ auth తనిఖీకి ముందైనా, ఎలాంటి మినహాయింపు లేకుండా loopback host తనిఖీని అమలు చేయడం** ద్వారా OmniRoute దీన్ని నిరోధిస్తుంది: tunnel ద్వారా లీక్ అయిన token కూడా spawnను చేరుకోలేదు.

**పూర్తి LOCAL_ONLY సమితి.** అధికారిక మూలం `src/server/authz/routeGuard.ts`లోని `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`; దిగువ పట్టిక ప్రస్తుత స్థితిని ప్రతిబింబిస్తుంది. `check-route-guard-membership` gate, spawn చేయగల prefixల కింద ఉన్న ప్రతి `route.ts`ను లెక్కించి, వాటిలో ఏదైనా local-onlyగా వర్గీకరించబడకపోతే CIని విఫలం చేస్తుంది.

| `/api/providers/{id}/refresh-cursor` (రెగ్యులర్ ఎక్స్ప్రెషన్)                                            | మాన్యువల్ Cursor సెషన్ పునరుద్ధరణ — `cursor-agent`ను నడ్జ్ చేస్తుంది                                                         |

**ఉల్లంఘనపై ప్రతిస్పందన:** `403 LOCAL_ONLY`

#### మేనేజ్-స్కోప్ మినహాయింపు

LOCAL_ONLY పాత్లలోని ఒక ఉపసమితిని, అభ్యర్థనలో `manage` స్కోప్ (లేదా `admin`)
కలిగిన మెటాడేటాతో కూడిన `Authorization: Bearer <api-key>` ఉన్నప్పుడు మాత్రమే,
నాన్-లూప్బ్యాక్ నుండి కూడా యాక్సెస్ చేయవచ్చు. ఈ మినహాయింపు
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ద్వారా ప్రతి పాత్కు స్పష్టంగా
నియంత్రించబడుతుంది, తద్వారా ఏదైనా కొత్త LOCAL_ONLY పాత్కు డిఫాల్ట్గా
కఠినమైన లూప్బ్యాక్ నియమమే కొనసాగుతుంది. ప్రామాణీకరణ లేని అభ్యర్థనలు మరియు
మేనేజ్ కాని కీలు కలిగిన అభ్యర్థనలు ఇప్పటికీ `403 LOCAL_ONLY`తో
తిరస్కరించబడతాయి.

ప్రస్తుతం బైపాస్ చేయదగిన ఏకైక ప్రిఫిక్స్ `/api/mcp/`. `/api/cli-tools/runtime/`
మరియు `/api/services/` ఉద్దేశపూర్వకంగా మినహాయించబడ్డాయి, ఎందుకంటే అవి ఏవైనా
సబ్ప్రాసెస్లను (`npm install`, `node`) ప్రారంభించగలవు; LOCAL_ONLY స్థాయి
నిరోధించడానికి ఉద్దేశించిన CVE వర్గం సరిగ్గా ఇదే.

**#7895 — `mcp:connect` పరిమిత స్కోప్:** `/api/mcp/` మినహాయింపు
పరిమిత `mcp:connect` స్కోప్ను కలిగిన Bearer కీని కూడా అంగీకరిస్తుంది
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), దీనిని
`src/server/authz/policies/management.ts`లోని `hasMcpConnectOrManageScope()`
ద్వారా తనిఖీ చేస్తారు. ఇది `/api/mcp/`కు మాత్రమే పరిమితం — `mcp:connect` మరే ఇతర
మేనేజ్మెంట్ రూట్పైనా (భవిష్యత్తులో మరొకటి జోడించినా, ప్రతి ఇతర LOCAL_ONLY
బైపాస్ ప్రిఫిక్స్తో సహా) ఎలాంటి అనుమతినీ ఇవ్వదు, అలాగే ఇది ఉద్దేశపూర్వకంగా
`MANAGEMENT_API_KEY_SCOPES` నుండి మినహాయించబడింది. `manage`/`admin` కలిగిన కీ
మునుపటిలాగే ఈ మినహాయింపును దాటుతుంది; విస్తృత మేనేజ్మెంట్ యాక్సెస్ అవసరం
లేని రిమోట్ MCP-మాత్రమే కాలర్ల కోసం `mcp:connect` తక్కువ-అధికార ప్రత్యామ్నాయం.

#### ఆపరేటర్ మార్గదర్శకత్వం & ఆడిటింగ్

మీరు OmniRouteను రివర్స్ ప్రాక్సీ లేదా టన్నెల్ (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) వెనుక నడిపితే, లూప్బ్యాక్ తనిఖీ ఇప్పటికీ పైన పేర్కొన్న
ప్రాసెస్లను ప్రారంభించగల రూట్లను రక్షిస్తుంది — క్లయింట్ చిరునామా నాన్-లూప్బ్యాక్గా
ఉన్న అభ్యర్థన **ప్రామాణీకరణ అమలయ్యే ముందే** `403 LOCAL_ONLY`తో తిరస్కరించబడుతుంది,
కాబట్టి లీకైన JWT కూడా ప్రాసెస్ ప్రారంభానికి చేరుకోలేదు. ఆపరేటర్కు రెండు బాధ్యతలు
మిగిలి ఉంటాయి:

- **క్లయింట్ IPని లూప్బ్యాక్గా నకిలీ చేసి 403ను "సరిచేయవద్దు".**
  `X-Forwarded-For: 127.0.0.1`ను సెట్ చేయడం లేదా సోర్స్ చిరునామాను లూప్బ్యాక్గా
  తిరిగి వ్రాసే ప్రాక్సీని ఉపయోగించడం, ఈ స్థాయి మూసివేసే RCE వర్గాన్నే మళ్లీ
  తెరుస్తుంది. ప్రాక్సీ ద్వారా డ్యాష్బోర్డ్/APIని బహిర్గతం చేయండి — ప్రాసెస్లను
  ప్రారంభించగల రూట్లను ఎప్పుడూ బహిర్గతం చేయవద్దు.
- **మేనేజ్-స్కోప్ బైపాస్ను కనిష్ఠంగా ఉంచండి.** `/api/mcp/` మాత్రమే బైపాస్
  చేయదగినది, అదీ `manage` స్కోప్ కలిగిన API కీతో మాత్రమే. `SPAWN_CAPABLE_PREFIXES`ను
  బైపాస్ జాబితాకు ఎప్పటికీ జోడించలేరు — zod స్కీమా వాటిని తిరస్కరిస్తుంది మరియు
  రన్టైమ్లో `isLocalOnlyBypassableByManageScope` వాటిని నిరాకరిస్తుంది
  (బహుళ-స్థాయి రక్షణ); డ్యాష్బోర్డ్లో "బైపాస్ చేయదగినదిగా మార్చలేరు" అని
  చెప్పడం యొక్క అర్థం ఇదే. `/api/providers/` కింద ఉన్న డైనమిక్-సెగ్మెంట్ మరియు
  స్టాటిక్-పాత్ ప్రాసెస్-ప్రారంభ సామర్థ్యం గల రూట్లు (ఉదా. `/login`,
  `/refresh-cursor`) ఫ్లాట్ `SPAWN_CAPABLE_PREFIXES` అరే ద్వారా కాకుండా,
  `src/shared/constants/spawnCapablePrefixes.ts`లోని రెగ్యులర్ ఎక్స్ప్రెషన్-ఆధారిత
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` సహచరం ద్వారా
  కవర్ చేయబడతాయి — వాటిని పట్టుకోవడానికి ఫ్లాట్ అరే మొత్తం `/api/providers/`
  ప్రిఫిక్స్ను కవర్ చేయాల్సి ఉంటుంది, దీనివల్ల ప్రొవైడర్ CRUD కోసం రిమోట్
  డ్యాష్బోర్డ్లు చట్టబద్ధంగా ఉపయోగించే రూట్ ట్రీ అవసరానికి మించి విస్తరిస్తుంది.

**యాక్సెస్ ఆడిటింగ్** — ఆఫ్-హోస్ట్ నుండి ఏదీ ఈ రూట్లను చేరడం లేదని ధృవీకరించడానికి:

- `/dashboard/settings/security`లో **Authorization Inventory**ని తెరవండి: ఇది ప్రత్యక్ష LOCAL_ONLY ప్రిఫిక్స్ జాబితాను, బైపాస్ చేయగల ప్రిఫిక్స్లను, అలాగే కంపైల్ సమయంలో నిర్ణయించబడే spawn-సామర్థ్యమున్న ("బైపాస్ చేయగలిగేలా మార్చలేని") సమితిని చూపుతుంది.
- పైన పేర్కొన్న ప్రిఫిక్స్లతో పాటు లూప్బ్యాక్ కాని క్లయింట్ చిరునామా ఉన్న నమోదుల కోసం మీ రివర్స్-ప్రాక్సీ / యాక్సెస్ లాగ్లలో Grep చేయండి. అటువంటి అభ్యర్థన ఏదైనా `403 LOCAL_ONLY`కి బదులుగా `200`ని అందిస్తే, ప్రాక్సీ అసలు క్లయింట్ IPని దాచిపెడుతోందని అర్థం — ప్రాక్సీని సరిచేయండి.
- ఈ పాత్లలో ఒకదానికి OmniRoute లాగ్లలో కనిపించే `403 LOCAL_ONLY`, గార్డ్ ఉద్దేశించిన విధంగా పనిచేస్తోందని సూచిస్తుంది; దాన్ని అణచివేయాల్సిన లోపంగా పరిగణించవద్దు.

### టైర్ 2 — ALWAYS_PROTECTED

**అమలు చేసేది:** `isAlwaysProtectedPath(path)` → `requireLogin=false` బైపాస్ను దాటవేయడం
**బైపాస్:** `requireLogin=false`గా ఉన్నప్పుడు ఏదీ లేదు; JWT ఎల్లప్పుడూ అవసరం

ఈ రూట్లు విధ్వంసకరమైనవి లేదా తిరిగి మార్చలేనివి. "పాస్వర్డ్-లేని"
ఇన్స్టాలేషన్లో వీటిని అనుమతిస్తే, అదే LANలో ఉన్న ఎవరైనా డేటాబేస్ను పూర్తిగా తొలగించగలరు లేదా

**ఉల్లంఘనపై ప్రతిస్పందన:** `401 Authentication required`

`/api/settings/obsidian` దాని `/webdav` చైల్డ్ను కూడా కవర్ చేస్తుంది: `POST`, ఈ పైప్లైన్ వెలుపల Next.js కంటే ముందుగా అనుకూల Node లేయర్ ద్వారా అందించబడే WebDAV ఫైల్ సర్వీస్ను కాలర్ ఎంచుకున్న రూట్వైపు మళ్లించి, కొత్తగా జారీ చేసిన Basic క్రెడెన్షియల్లను తిరిగి పంపుతుంది; `DELETE` వాటిని రొటేట్ చేస్తుంది; అలాగే పేరెంట్ `POST`, Obsidian REST API టోకెన్ను నిల్వ చేస్తుంది. GHSA-62vw కేవలం `GET` పాస్వర్డ్ వెల్లడిని మాత్రమే మాస్క్ చేసింది; జారీ ప్రక్రియ మాత్రం ఇప్పటికీ fail-open టైర్పైనే ఉండేది (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` అదనంగా, డేటా డైరెక్టరీగా ఉన్న, దానిలోపల ఉన్న లేదా దాన్ని కలిగి ఉన్న వాల్ట్ను తిరస్కరిస్తుంది.

### తాజా-ఇన్స్టాలేషన్ బూట్స్ట్రాప్ లూప్బ్యాక్కు మాత్రమే — నిజమైన పీర్ ఆధారంగా, `Host` ఆధారంగా కాదు

మేనేజ్మెంట్ పాస్వర్డ్ కాన్ఫిగర్ చేయనప్పుడు (మరియు `INITIAL_PASSWORD` కూడా లేనప్పుడు),
`src/shared/utils/apiAuth.ts`లోని `isAuthRequired()` అనామక బూట్స్ట్రాప్ను **లూప్బ్యాక్ పీర్లకు మాత్రమే** తెరిచి ఉంచుతుంది.
విశ్వసనీయ పీర్ సంకేతాల నుంచి ఈ క్రమంలో లూప్బ్యాక్ నిర్ణయించబడుతుంది: టోకెన్-స్టాంప్ చేసిన నిజమైన TCP పీర్
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, పాలసీ చూసేది), పైప్లైన్ స్వంత
`AUTHZ_HEADER_PEER_LOCALITY` తీర్పు (రూట్ హ్యాండ్లర్లు చూసేది; `OMNIROUTE_PEER_STAMP_TOKEN` సెట్ చేసి ఉన్నంతవరకు మాత్రమే విశ్వసించబడుతుంది), లేదా నేరుగా కాల్ చేసేవారి నిజమైన సాకెట్ పీర్. `Host` /
`nextUrl.hostname`ను ఎప్పుడూ పరిశీలించరు; అలాగే మొదటి-పాస్వర్డ్ రైట్
(`POST /api/settings/require-login`) ప్రతి నెట్వర్క్ పీర్కు తెరిచి ఉండకుండా ఇదే పరిమితికి లోబడి ఉంటుంది
(GHSA-7pq4-8pvv-rx7r). `managementPolicy` తన స్వంత `peerContext` తీర్పును
స్పష్టంగా దిగువకు పంపుతుంది, కాబట్టి ORIGINAL (స్ట్రిప్ చేయడానికి ముందు ఉన్న) అభ్యర్థన హెడర్లు దాన్ని ఎప్పుడూ నిర్ణయించవు.

### టైర్ 3 — MANAGEMENT (డిఫాల్ట్)

మిగతా అన్ని మేనేజ్మెంట్ రూట్లు. `requireLogin=false`గా కాన్ఫిగర్ చేయకపోతే ప్రమాణీకరణ అవసరం.
CLI టోకెన్లు ఈ రూట్లను ప్రమాణీకరించగలవు (లూప్బ్యాక్ + చెల్లుబాటు అయ్యే HMAC).

## మూల్యాంకన క్రమం

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → తదుపరి దశకు వెళ్లండి
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → అనుమతించు (management_key)
     → లేకపోతే                                   → తిరస్కరించు 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → అనుమతించు (system)
  3. hasValidCliToken(headers)?
     → అనుమతించు (cli) [loopback + timingSafeEqual HMAC తనిఖీ]
  4. isAlwaysProtectedPath(path) లేదా requireLogin=true?
     → isDashboardSessionAuthenticated?
        → అనుమతించు (dashboard_session)
     → బైపాస్ చేయలేని మార్గంలో manage-scope Bearer ఉందా?
        → అనుమతించు (management_key)
     → తిరస్కరించు 401/403
  5. requireLogin=false?
     → అనుమతించు (anonymous)
```

LOCAL_ONLY మార్గాన్ని సంతృప్తిపరచగల ఏకైక ప్రామాణీకృత మార్గం దశ 1లోని manage-scope శాఖ;
గడువు ముగిసిన DB నిశ్శబ్దంగా "తిరస్కరించు" స్థితికి దిగజారకుండా ఉండేందుకు auth-backend వైఫల్య
స్థితి 403 కాకుండా 503ను అందిస్తుంది.

## కొత్త spawn-సామర్థ్య మార్గాన్ని జోడించడం

1. మార్గం ప్రిఫిక్స్ను
   `src/server/authz/routeGuard.ts`లోని `LOCAL_ONLY_API_PREFIXES`కు జోడించండి
2. కొత్త ప్రిఫిక్స్కు `isLocalOnlyPath()` trueను అందిస్తుందని నిర్ధారించే పరీక్షను
   `tests/unit/authz/routeGuard.test.ts`లో జోడించండి
3. **ఈ దశను ఎప్పటికీ దాటవేయవద్దు** — `CLAUDE.md`లోని Hard Rule #15 చూడండి
4. నిర్ణయించండి: ఈ మార్గం `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`లో కూడా ఉండాలా?
   డిఫాల్ట్ సమాధానం **లేదు**. manage-scope హోల్డర్కు బహిర్గతం చేయడానికి మార్గం
   సురక్షితమైనప్పుడు మాత్రమే ఎంపిక చేయండి (అంటే, అది వినియోగదారు నియంత్రించే ఏకపక్ష కోడ్ను spawn చేయకూడదు).

## manage-scope ద్వారా బైపాస్ చేయగల మార్గాన్ని జోడించడం

1. మార్గం వినియోగదారు అందించిన కోడ్ లేదా కమాండ్లను అమలు చేయదని నిర్ధారించండి. అలా
   చేస్తే, ఆపివేయండి — ఈ మినహాయింపు దీనికి సరైన సాధనం కాదు.
2. ప్రిఫిక్స్ను `src/server/authz/routeGuard.ts`లోని
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`కు జోడించండి
3. ఈ నాలుగు అభ్యర్థన రూపాలన్నింటికీ `tests/unit/authz/management-policy.test.ts`లో
   కవరేజ్ను జోడించండి: Bearer లేదు (403), manage Bearer (అనుమతించు), non-manage Bearer
   (403), అలాగే manage Bearer ఉన్నప్పటికీ `/api/cli-tools/runtime/*`
   strict-loopbackగానే ఉండేలా ప్రతి ప్రిఫిక్స్కు రిగ్రెషన్ పరీక్ష.

## OpenAPIలో భద్రతా టైర్లను డాక్యుమెంట్ చేయడం

`docs/openapi.yaml`కు కొత్త మార్గాన్ని జోడించేటప్పుడు, ఆ మార్గాన్ని `routeGuard.ts`
వర్గీకరిస్తే దానికి అనుగుణమైన vendor extensionను వర్తింపజేయండి:

| routeGuard.ts వర్గీకరణ             | YAML annotation            | అమలు                                                  |
| ---------------------------------- | -------------------------- | ----------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`          | `x-loopback-only: true`    | non-loopback నుంచి బేషరతుగా నిరోధించబడుతుంది          |
| `ALWAYS_PROTECTED_API_PATHS`       | `x-always-protected: true` | `requireLogin=false` ఉన్నప్పటికీ auth అవసరం           |
| అంతర్గత admin/debug మార్గం         | `x-internal: true`         | డిఫాల్ట్గా /dashboard/api-endpoints నుంచి దాచబడుతుంది |
| ఏదీ కాదు (public / ప్రామాణిక auth) | (annotation అవసరం లేదు)    | ప్రామాణిక `requireLogin`-నియంత్రిత యాక్సెస్           |

### ధ్రువీకరణ

YAML annotationలు మరియు `routeGuard.ts` మధ్య స్థిరత్వాన్ని రెండు స్క్రిప్ట్లు అమలు చేస్తాయి:

- `scripts/check/check-openapi-coverage.mjs` — కవరేజ్ < 99% అయితే విఫలమవుతుంది
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` లేదా
  `x-always-protected` annotationలు compile-time స్థిరాంకాల నుంచి భిన్నంగా ఉంటే విఫలమవుతుంది

రెండు స్క్రిప్ట్లు pre-commit hookలోనూ, CIలోనూ అమలవుతాయి.

### తప్పుడు పాజిటివ్ నియమం

`routeGuard.ts` స్థిరాంకంలో లేని మార్గంపై `x-always-protected` లేదా `x-loopback-only`
annotation ఉంటే, కవరేజ్ స్క్రిప్ట్ విఫలమవుతుంది. పరిష్కారం ఎల్లప్పుడూ YAMLను
`routeGuard.ts` వాస్తవంగా అమలు చేసే దానికి అనుగుణంగా సర్దుబాటు చేయడమే — enforcement
logicను కూడా అమలు చేయకుండా `routeGuard.ts`కు మార్గాలను జోడించడం కాదు.
