TPROXY పారదర్శక డీక్రిప్షన్ అనేది
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM స్టాక్ కోసం OmniRoute అందించే **5వ క్యాప్చర్ మోడ్**. ఇది kernel TPROXY + policy routing ఉపయోగించి Linuxలోని స్థానిక అవుట్బౌండ్ HTTPS ట్రాఫిక్ను ఇంటర్సెప్ట్ చేసి **డీక్రిప్ట్** చేస్తుంది — `/etc/hosts`ను స్పూఫ్ చేయకుండా మరియు OS-వ్యాప్త system-proxy సెట్టింగ్లను మార్చకుండా. ఇది headless వాతావరణాలకు అనుకూలంగా ఉంటుంది (శుభ్రం చేయాల్సిన DNS మార్పులు ఉండవు), అలాగే రీబూట్ చేసినప్పుడు firewall నియమాలు స్వయంచాలకంగా తొలగించబడతాయి.

ఇతర క్యాప్చర్ మోడ్లకు భిన్నంగా, TPROXYకి ప్రతి హోస్ట్కు ప్రత్యేక సెటప్ అవసరం లేదు: ఇది లక్ష్య పోర్ట్లోని **ఏవైనా** గమ్యస్థాన హోస్ట్లను పారదర్శకంగా ఇంటర్సెప్ట్ చేస్తుంది, ప్రతి SNI హోస్ట్నేమ్ కోసం అప్పటికప్పుడు జారీ చేసే leaf certificateతో TLSను ముగిస్తుంది, డీక్రిప్ట్ చేసిన పరస్పర మార్పిడిని క్యాప్చర్ చేస్తుంది, ఆపై అభ్యర్థనను అసలు గమ్యస్థానానికి మళ్లీ ఎన్క్రిప్ట్ చేసి పంపుతుంది.

> **Linuxలో మాత్రమే, rootకు మాత్రమే, స్వచ్ఛందంగా ప్రారంభించాల్సినది.** ఈ మోడ్కు Linux, C toolchainతో నిర్మించిన native addon, మరియు **CAP_NET_ADMIN** సామర్థ్యం (సాధారణంగా root) అవసరం. ఇది loopbackకు మాత్రమే పరిమితమైన AgentBridge API వెనుక నియంత్రించబడుతుంది మరియు డిఫాల్ట్గా నిలిపివేయబడి ఉంటుంది. ఏ హోస్ట్కైనా సంతకం చేయగల విశ్వసనీయ MITM CA ఒక శక్తివంతమైన సామర్థ్యం — [§6 భద్రత](#6-security) చూడండి.

## §1 ఇది ఏమిటి మరియు దీన్ని ఎప్పుడు ఉపయోగించాలి

మిగతా నాలుగు క్యాప్చర్ మోడ్లలో ప్రతి దానికీ ఒక పరిమితి ఉంది:

| మోడ్              | ట్రాఫిక్ ఎలా మళ్లించబడుతుంది                        | పరిమితి                                             |
| ----------------- | --------------------------------------------------- | --------------------------------------------------- |
| AgentBridge       | స్థిరమైన హోస్ట్ల సమితికి `/etc/hosts` DNS స్పూఫింగ్ | నమోదు చేసిన IDE-agent హోస్ట్లు మాత్రమే              |
| Custom Hosts      | ప్రతి హోస్ట్కు `/etc/hosts` DNS స్పూఫింగ్           | ప్రతి హోస్ట్కు ఒక ఎంట్రీ; hostsను సవరించడానికి sudo |
| HTTP_PROXY        | `HTTP_PROXY`/`HTTPS_PROXY` env                      | env varను గౌరవించే యాప్లు మాత్రమే                   |
| System-wide proxy | OS proxy సెట్టింగ్లు                                | గ్లోబల్ స్థితిని మారుస్తుంది; తిరిగి మార్చడం అవసరం  |

దీనికి బదులుగా, TPROXY పారదర్శక డీక్రిప్షన్ ట్రాఫిక్ను **kernel** స్థాయిలో మళ్లిస్తుంది. ఇది `mangle OUTPUT` చైన్లో లక్ష్య పోర్ట్కు (డిఫాల్ట్గా `443`) వెళ్లే కొత్త స్థానిక అవుట్బౌండ్ TCP కనెక్షన్లను గుర్తు పెడుతుంది, ఒక `ip rule` గుర్తు పెట్టిన ప్యాకెట్లను స్థానిక డెలివరీకి మళ్లిస్తుంది, మరియు తిరిగి ప్రవేశించినప్పుడు `mangle PREROUTING`లోని `TPROXY` టార్గెట్ వాటిని **IP_TRANSPARENT** listenerకు అప్పగిస్తుంది — అది TLSను ముగించి plaintextను క్యాప్చర్ చేస్తుంది.

కింది లక్షణాలున్న ప్రాసెస్ ట్రాఫిక్ను క్యాప్చర్ చేసి డీక్రిప్ట్ చేయాలనుకున్నప్పుడు దీన్ని ఉపయోగించండి:

- AgentBridge నమోదు చేయని హోస్ట్తో కమ్యూనికేట్ చేస్తుంది, మరియు
- `HTTP_PROXY`ను గౌరవించదు, మరియు
- system-wide proxy మార్పుతో దానిని ప్రభావితం చేయాలనుకోవడం లేదు.

ఇంటర్సెప్షన్ kernelలో జరుగుతుంది కాబట్టి, ప్రారంభించిన ప్రాసెస్కు **ఎలాంటి కాన్ఫిగరేషన్ మార్పూ అవసరం లేదు** — అయితే ఆ ప్రాసెస్ OmniRoute ఇన్స్టాల్ చేసే dynamic CAను విశ్వసించాలి ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) చూడండి).

## §2 అవసరాలు

| అవసరం              | వివరాలు                                                                                                                                                  |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**             | Linux మాత్రమే — **IP_TRANSPARENT** అనేది Linuxలో మాత్రమే అందుబాటులో ఉండే socket ఎంపిక. ఇతర ప్రతి ప్లాట్ఫారమ్లో loader "unavailable"ను తిరిగి ఇస్తుంది.   |
| **అధికారం**        | transparent socketను సృష్టించి `iptables`/`ip` నియమాలను వర్తింపజేయడానికి **CAP_NET_ADMIN** capability అవసరం — ఆచరణలో, rootగా అమలు చేయండి.                |
| **Native addon**   | ఒక చిన్న N-API addon (`src/mitm/tproxy/native/transparent.c`)ను build చేయాలి లేదా prebuildగా అందించాలి. [§3](#3-the-native-ip_transparent-addon) చూడండి. |
| **Kernel modules** | `TPROXY`, `mangle`, మరియు `mark` match మద్దతుతో కూడిన `iptables` (kernel 6.8.0తో ధ్రువీకరించబడింది).                                                     |

**సున్నితమైన క్షీణత:** ఏదైనా అవసరం లేకపోతే (Linux కాకపోవడం, toolchain లేకపోవడం,
addon build చేయకపోవడం), addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
exceptionను విసరకుండా `null`ను తిరిగి ఇస్తుంది. అప్పుడు capture-mode స్థితి
`available: false`గా నివేదిస్తుంది, dashboard toggle
"TPROXY decrypt కోసం Linux + root + native addon అవసరం" అనే tooltipతో **నిలిపివేయబడుతుంది**,
మరియు OmniRouteలోని మిగతా భాగాలు పని చేస్తూనే ఉంటాయి.

## §3 Native IP_TRANSPARENT addon

Node యొక్క `net` module, `bind()`కు _ముందు_ `setsockopt(IP_TRANSPARENT)`ను అమలు చేయలేదు,
కానీ TPROXYకి ఇది అవసరం (లేకపోతే kernel మళ్లించబడిన packetsను తొలగిస్తుంది). ఈ addon
(`src/mitm/tproxy/native/transparent.c`, `binding.gyp` ద్వారా build చేయబడుతుంది) అనేది
మూడు functionsను అందించే చిన్న N-API module; వీటిని `transparentSocket.ts` ద్వారా ఉపయోగిస్తారు:

| Addon function                        | Socket పని                                                                                           | ఉపయోగం                                                                                  |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`; raw fdను తిరిగి ఇస్తుంది | transparent capture listener (Node, `server.listen({ fd })` ద్వారా fdను స్వీకరిస్తుంది) |
| `setSocketMark(fd, mark)`             | ఇప్పటికే ఉన్న fdపై `setsockopt` **SO_MARK**                                                          | anti-loop (proxy యొక్క స్వంత socketsకు mark వేయడం)                                      |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()`కు **ముందు** `socket()` + **SO_MARK**; fdను తిరిగి ఇస్తుంది                  | మళ్లీ encrypt చేసిన upstream forward (SYN markను కలిగి ఉంటుంది)                         |

అసలు destinationను `socket.localAddress`/`localPort` నుండి చదువుతారు — TPROXY
దానిని అలాగే ఉంచుతుంది, కాబట్టి **SO_ORIGINAL_DST**/NAT lookup అవసరం లేదు.

### Addonను build చేయడం

```bash
npm run build:native:tproxy      # src/mitm/tproxy/nativeకు cd చేసి node-gyp rebuild అమలు చేయండి
                                 # -> native/build/Release/transparent.node
```

- `npm run build` సమయంలో, `scripts/build/build-tproxy-native.mjs`, `node-gyp
rebuild`ను అమలు చేస్తుంది. ఇది **Linuxలో మాత్రమే అమలవుతుంది మరియు విఫలమైనా ప్రాణాంతకం కాదు** — toolchain లేకపోతే
  capture mode అందుబాటులో ఉండదు, అంతే.
- `assembleStandalone.mjs`, `build/Release/transparent.node`ను
  standalone bundleలోకి copy చేస్తుంది; `transparentSocket.ts` దానిని module-relative మరియు
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`) రెండింటి ద్వారా resolve చేస్తుంది.
- `build/` మరియు `prebuilds/` gitలో ignore చేయబడతాయి — binary **build చేయబడుతుంది, కానీ ఎప్పుడూ
  commit చేయబడదు**.

Loader ఈ ప్రాధాన్యత క్రమంలో పరిశీలిస్తుంది:
`native/build/Release/transparent.node`, ఆపై `native/prebuilds/transparent.node`
(రెండూ module-relativeగా మరియు `<cwd>/src/mitm/tproxy/` కింద).

## §4 ప్రతి-SNI డైనమిక్ CA మరియు ట్రస్ట్-స్టోర్ ఇన్స్టాలర్

> **#6684 నవీకరణ:** AgentBridge స్టాటిక్ సర్వర్ (`src/mitm/server.cjs`) ఇప్పుడు
> ఒకే స్టాటిక్ స్వీయ-సంతకం చేసిన లీఫ్కు బదులుగా ఇదే CA/లీఫ్ ఆర్కిటెక్చర్ నమూనాను
> పంచుకుంటుంది. ఇది ఒక **ప్రత్యేక** CA ఇన్స్టాన్స్ను
> (`src/mitm/cert/rootCa.ts`, `<DATA_DIR>/mitm/ca.key`/`ca.crt` వద్ద నిల్వ చేయబడుతుంది)
> ఉపయోగిస్తుంది మరియు ముందే ఉన్న `omniroute-mitm.crt` ట్రస్ట్-స్టోర్ స్లాట్లో
> ఇన్స్టాల్ చేస్తుంది (అక్కడి పాత ఏకైక లీఫ్ను భర్తీ చేస్తుంది — ద్వంద్వ-ట్రస్ట్
> క్లీనప్ అవసరం లేదు); దిగువన ఉన్న TPROXY యొక్క స్వంత `omniroute-tproxy-ca.crt`
> స్లాట్కు ఇది పూర్తిగా వేరుగా ఉంచబడుతుంది. కొత్త AgentBridge ఇన్స్టాలేషన్లు
> CA నమూనాను స్వయంచాలకంగా పొందుతాయి; ఇప్పటికే పాత స్టాటిక్ లీఫ్ను విశ్వసించిన
> ఇన్స్టాలేషన్, ఆపరేటర్ `MITM_ROOT_CA_ENABLED=true` ద్వారా సమ్మతించే వరకు
> దానినే ఉపయోగిస్తూ ఉంటుంది (`src/mitm/cert/migration.ts` చూడండి) — **ఏ**
> హోస్ట్కైనా లీఫ్పై సంతకం చేయగల విశ్వసనీయ MITM CA, పాత స్థిర-SAN లీఫ్తో
> పోలిస్తే గణనీయంగా ఎక్కువ శక్తివంతమైనది, కాబట్టి ఇప్పటికే విశ్వసించిన
> ఇన్స్టాలేషన్లో ఈ మార్పు ఎప్పుడూ నిశ్శబ్దంగా జరగదు.

చారిత్రకంగా, స్టాటిక్ AgentBridge MITM సర్టిఫికేట్ పనిచేయడానికి కారణం AgentBridge
ఒక **స్థిరమైన** హోస్ట్ సమితికి DNS స్పూఫింగ్ చేయడమే (ఇప్పుడు దిగువ నమూనాతో
ఏకీకృతం చేయబడింది). TPROXY **ఏవైనా** హోస్ట్లను ఇంటర్సెప్ట్ చేస్తుంది, కాబట్టి
క్లయింట్ అభ్యర్థించే ఏ SNIకైనా దాని లిసనర్ చెల్లుబాటు అయ్యే లీఫ్ను సమర్పించాలి —
కేవలం 4 antigravity హోస్ట్లకు బదులుగా పూర్తి `MITM_TOOL_HOSTS` సమితి
(9 టూల్ ఎంట్రీలు) కోసం ఇప్పుడు AgentBridgeకూ ఇదే అవసరం ఉంది.

### డైనమిక్ CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore`, `selfsigned` డిపెండెన్సీపై నిర్మించిన స్థానిక CAను నడుపుతుంది, ఇది:

- `generateMitmCa()` ద్వారా దీర్ఘకాలిక CAను రూపొందిస్తుంది (CN `"OmniRoute MITM CA"`,
  10 సంవత్సరాల చెల్లుబాటు, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-bit RSA / SHA-256).
- `issueLeafCert()` ద్వారా **ప్రతి SNI హోస్ట్నేమ్కు అవసరమైనప్పుడు ఒక లీఫ్ను**
  జారీ చేస్తుంది (1 సంవత్సరం చెల్లుబాటు, `subjectAltName` = SNI హోస్ట్) మరియు
  ప్రతి హోస్ట్నేమ్కు ఒక `tls.SecureContext`ను క్యాష్ చేస్తుంది.
- TLSను ముగించే సర్వర్ కోసం `createSNICallback()`ను అందిస్తుంది
  ([§5](#5-how-decrypt-and-capture-work) చూడండి).
- రీస్టార్ట్ల మధ్య CA స్థిరంగా ఉండేలా `existingCa`తో నిర్మించవచ్చు
  (అందువల్ల ట్రస్ట్ స్టోర్ను మళ్లీ ఇన్స్టాల్ చేయాల్సిన అవసరం ఉండదు).

CA ప్రైవేట్ కీ **ఎప్పుడూ మెషీన్ను విడిచి వెళ్లదు**.

### ట్రస్ట్-స్టోర్ ఇన్స్టాలర్ (`src/mitm/tproxy/caTrust.ts`)

ఇంటర్సెప్ట్ చేయబడిన క్లయింట్ డైనమిక్ CAను విశ్వసించాలి, కాబట్టి క్యాప్చర్ మోడ్ను
ప్రారంభించడం ద్వారా CA సర్టిఫికేట్ OS ట్రస్ట్ స్టోర్లో ఒక **ప్రత్యేక స్లాట్** కింద —
`omniroute-tproxy-ca.crt` (`TPROXY_CA_CERT_NAME` స్థిరాంకం) — ఇన్స్టాల్ చేయబడుతుంది.
రెండూ ఒకదానిని మరొకటి ఓవర్రైట్ చేయకుండా ఉండేందుకు ఇది స్టాటిక్ MITM సర్టిఫికేట్
స్లాట్ (`omniroute-mitm.crt`) నుండి వేరుగా ఉంచబడుతుంది.

`installTproxyCa(caPem, sudoPassword?)` డిస్ట్రో యొక్క యాంకర్ డైరెక్టరీని
(మొదట Debian-శైలిని పరిశీలిస్తూ) గుర్తించి, దానికి సరిపోలే రిఫ్రెష్ కమాండ్ను అమలు చేస్తుంది:

| యాంకర్ డైరెక్టరీ                            | రిఫ్రెష్ కమాండ్          |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

ఇన్స్టాలేషన్ ముందుగా PEMను తాత్కాలిక ఫైల్లో ఉంచి, ఆపై (ప్రత్యేక అధికారాలతో)
యాంకర్ డైరెక్టరీపై `mkdir -p`ను అమలు చేసి, స్టేజ్ చేసిన ఫైల్ను దానిలోకి `cp`
చేసి, రిఫ్రెష్ కమాండ్ను అమలు చేస్తుంది. `uninstallTproxyCa()` ప్రత్యేక స్లాట్ను
మాత్రమే తొలగించి (స్టాటిక్ MITM సర్టిఫికేట్ను మార్చకుండా ఉంచి), రిఫ్రెష్ చేస్తుంది —
Linux కాని సిస్టమ్లలో ఇది ఎటువంటి చర్య చేయదు.

ప్రత్యేక అధికారాలు అవసరమైన అన్ని కమాండ్లు `execFileWithPassword`
(`src/mitm/systemCommands.ts`) ద్వారా అమలవుతాయి — **ఆర్గ్యుమెంట్ అరేలతో,
షెల్ లేకుండా, స్ట్రింగ్ ఇంటర్పోలేషన్ లేకుండా** `spawn` చేయబడతాయి (కఠిన నియమం #13).
ప్రాసెస్ rootగా ఉన్నప్పుడు (ఉదా. VPS), లక్ష్య కమాండ్ నేరుగా అమలవుతుంది మరియు
పాస్వర్డ్ అవసరం లేదు; root కాని డెస్క్టాప్లో `sudoPassword`, stdinపై `sudo -S`
ద్వారా పంపబడుతుంది.

> ట్రస్ట్-స్టోర్ ఇన్స్టాలేషన్కు అధికారం ఇవ్వడానికి డెస్క్టాప్ యొక్క
> `sudoPassword` POST బాడీలో అందించబడుతుంది; ప్రాసెస్ rootగా ఉన్నప్పుడు
> అది పూర్తిగా విస్మరించబడుతుంది.

## §5 డీక్రిప్షన్ మరియు క్యాప్చర్ ఎలా పనిచేస్తాయి

పైప్లైన్ (మొత్తం `src/mitm/tproxy/` కింద ఉంటుంది):

```
స్థానిక యాప్  ──TCP/443──▶  mangle OUTPUT కనెక్షన్ను గుర్తిస్తుంది (fwmark)
                             ip rule → స్థానిక రూట్ పట్టిక → lo
                             mangle PREROUTING TPROXY → IP_TRANSPARENT లిసనర్ (పోర్ట్ 8443)
                                 │  captureMode.ts: socket.localAddress నుండి అసలు గమ్యస్థానాన్ని చదువుతుంది
                                 ▼
                             tlsCapture.ts:
                               1. ప్రతి-SNI లీఫ్తో (dynamicCert) CLIENT TLSను టెర్మినేట్ చేస్తుంది
                               2. అంతర్గత http.Server డీక్రిప్ట్ చేసిన ప్లెయిన్టెక్స్ట్ను పార్స్ చేస్తుంది
                               3. క్యాప్చర్ → source: "tproxy"తో globalTrafficBuffer.push()
                                  (sanitizeHeaders + maskSecret వర్తింపజేయబడతాయి)
                               4. బైపాస్-మార్క్ చేసిన సాకెట్ ద్వారా అసలు గమ్యస్థానానికి
                                  మళ్లీ ఎన్క్రిప్ట్ చేసి ఫార్వర్డ్ చేస్తుంది (connectMarked, యాంటీ-లూప్)
                                 │
                                 ▼
                             అసలు అప్స్ట్రీమ్ (api.example.com)
```

- **TLS టెర్మినేషన్** (`createTlsCaptureServer`): డైనమిక్ CA యొక్క SNI కాల్బ్యాక్ను ఉపయోగించి, ఇంటర్సెప్ట్ చేసిన ముడి
  సాకెట్ను సర్వర్-సైడ్ `tls.TLSSocket`లో ర్యాప్ చేసి,
  ఆపై డీక్రిప్ట్ చేసిన స్ట్రీమ్ను అంతర్గత `http.Server`కు అందిస్తుంది (ప్రామాణిక MITM
  టెర్మినేషన్ పద్ధతి). హ్యాంగ్ అయిన టన్నెల్ ఫైల్ డిస్క్రిప్టర్లను పూర్తిగా వినియోగించకుండా ఉండేందుకు
  సాకెట్ జీవితకాలాలు `MITM_IDLE_TIMEOUT_MS` ద్వారా పరిమితం చేయబడతాయి.
- **క్యాప్చర్** (`handleDecryptedRequest`): `source: "tproxy"`, ప్రారంభ స్థితి
  `"in-flight"`తో ఒక `InterceptedRequest`ను పుష్ చేస్తుంది; హెడర్లు బఫర్లోకి
  ప్రవేశించే ముందు `sanitizeHeaders()` ద్వారా, బాడీలు `maskSecret()` ద్వారా
  ప్రాసెస్ చేయబడతాయి. ఆపై ఎంట్రీ రెస్పాన్స్, పరిమాణాలు మరియు లేటెన్సీతో నవీకరించబడుతుంది.
- **మళ్లీ ఎన్క్రిప్ట్ చేసిన ఫార్వర్డ్** (`createForward` / `realForward`): అసలు
  గమ్యస్థానానికి మళ్లీ ఎన్క్రిప్ట్ చేస్తుంది. `rejectUnauthorized` డిఫాల్ట్గా **`true`**
  (డిఫాల్ట్గా సురక్షితం) — క్లయింట్ అభ్యర్థించిన SNI/Hostతో అప్స్ట్రీమ్ సర్టిఫికేట్
  ధృవీకరించబడుతుంది, కాబట్టి అసలు క్లయింట్ తిరస్కరించే వాటినే ప్రాక్సీ కూడా తిరస్కరిస్తుంది.

### యాంటీ-లూప్ (SO_MARK)

నియమాలు కొత్త స్థానిక అవుట్బౌండ్ కనెక్షన్లను గుర్తిస్తాయి కాబట్టి, ప్రాక్సీ యొక్క **సొంత**
మళ్లీ ఎన్క్రిప్ట్ చేసిన ఫార్వర్డ్ సాధారణంగా తిరిగి ఇంటర్సెప్ట్ చేయబడుతుంది — ఇది ఒక అనంత లూప్.
బైపాస్ సాకెట్ మార్క్ (**SO_MARK**)తో ఫార్వర్డ్ పాత్ దీనిని నిరోధిస్తుంది:

- `realForward` తన అప్స్ట్రీమ్ సాకెట్ను `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  ద్వారా తెరుస్తుంది — `DEFAULT_BYPASS_MARK = 0x539` — ఇది `connect()`కు **ముందే**
  **SO_MARK**ను సెట్ చేస్తుంది, అందువల్ల ఫార్వర్డ్ SYN బైపాస్ మార్క్ను కలిగి ఉంటుంది.
- ఇప్పటికే బైపాస్ మార్క్ను కలిగి ఉన్న కనెక్షన్లను `mangle OUTPUT` నియమం
  మినహాయిస్తుంది (`-m mark ! --mark <bypassMark>`), కాబట్టి ప్రాక్సీ ఫార్వర్డ్
  మళ్లీ గుర్తించబడదు మరియు TPROXYలోకి తిరిగి ప్రవేశించదు.

> అమలు గమనిక: బైపాస్-మార్క్ చేసిన సాకెట్ను ఏజెంట్ యొక్క
> `createConnection`పై తప్పనిసరిగా ఇన్స్టాల్ చేయాలి (`https.request({ createConnection })` అనేది
> ఏజెంట్ ఉన్నప్పుడు ఎలాంటి హెచ్చరిక లేకుండా విస్మరించబడుతుంది); లేకపోతే ఫార్వర్డ్ మార్క్ చేయని
> సాకెట్ను తెరుస్తుంది మరియు లూప్ తిరిగి ఏర్పడుతుంది. ఇది e2e ద్వారా ధృవీకరించబడిన యాంటీ-లూప్ పరిష్కారం.

## §7 లావాదేవీ పద్ధతిలో ఫైర్వాల్ను వర్తింపజేయడం / వెనక్కి మార్చడం

క్రాష్ కారణంగా `mangle` నియమం లేదా పాత రూట్ ఎప్పటికీ మిగిలిపోకూడదు. కమాండ్ బిల్డర్
(`src/mitm/tproxy/commands.ts`) మరియు రన్నర్ (`src/mitm/tproxy/setup.ts`)
**revert అనేది apply యొక్క ఖచ్చితమైన విలోమం, అదీ వ్యతిరేక క్రమంలో** అని హామీ ఇస్తాయి.

`applyTproxy(cfg)` వర్తింపు కమాండ్లను క్రమంలో అమలు చేస్తుంది; **ఏదైనా** వైఫల్యం సంభవిస్తే,
సాధ్యమైనంత మేరకు పూర్తి `revertTproxy(cfg)`ను అమలు చేసి, లోపాన్ని మళ్లీ విసురుతుంది — కాబట్టి
ఫైర్వాల్ పూర్తిగా వర్తింపజేయబడుతుంది లేదా పూర్తిగా వెనక్కి మార్చబడుతుంది, పాక్షికంగా
వర్తింపజేయబడదు. `revertTproxy(cfg)` విలోమ కమాండ్లను వ్యతిరేక క్రమంలో అమలు చేసి,
వైఫల్యాలను విస్మరిస్తుంది (ఐడెంపోటెంట్ — షరతులు లేకుండా కాల్ చేయడం సురక్షితం,
ఉదా. AgentBridge `repairMitm()` క్లీనప్ నుండి).

ఏ కమాండ్కైనా ముందు `validateTproxyConfig(cfg)` అమలవుతుంది: పోర్ట్లు `1–65535`
పరిధిలో ఉండాలి, `mark`/`routeTable`/`bypassMark` ధన పూర్ణాంకాలు అయి ఉండాలి, అలాగే
`bypassMark` తప్పనిసరిగా `mark`కు భిన్నంగా ఉండాలి (యాంటీ-లూప్).

### వర్తింపు కమాండ్లు (క్రమంలో)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

వెనక్కి మార్చడం వాటిని వ్యతిరేక క్రమంలో తొలగిస్తుంది: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> ఈ విధానం **OUTPUT-ఆధారితమైనది**, ఎందుకంటే MITM వినియోగ సందర్భం _స్థానిక_ అవుట్బౌండ్
> ట్రాఫిక్ (అదే హోస్ట్లోని యాప్లు); కేవలం `PREROUTING`లోని TPROXY దీనిని
> చూడదు — `PREROUTING` ఫార్వర్డ్ చేయబడిన ట్రాఫిక్ను మాత్రమే చూస్తుంది. `OUTPUT` చైన్ కొత్త
> స్థానిక కనెక్షన్లకు మార్క్ చేస్తుంది, `ip rule` వాటిని స్థానిక డెలివరీకి (`lo`) తిరిగి రూట్ చేస్తుంది,
> ఆ తర్వాత `PREROUTING` వాటిని ట్రాన్స్పరెంట్ లిసనర్కు కేటాయిస్తుంది.

## §8 కాన్ఫిగరేషన్

ప్రారంభ అభ్యర్థన (`POST /api/tools/agent-bridge/tproxy`) క్రింది
ఫీల్డ్లను స్వీకరిస్తుంది, వీటిని `StartTproxyBodySchema` (`tproxy/route.ts`) ధృవీకరిస్తుంది. అన్నీ ఐచ్ఛికం
మరియు అందించనప్పుడు వాటి డిఫాల్ట్ విలువలను ఉపయోగిస్తాయి:

| ఫీల్డ్           | రకం                | డిఫాల్ట్ | గమనికలు                                                                                                                           |
| ---------------- | ------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`    | ట్రాన్స్పరెంట్గా ఇంటర్సెప్ట్ చేయాల్సిన గమ్య TCP పోర్ట్                                                                            |
| **mark**         | int (≥1)           | `0x2333` | `OUTPUT`లో సెట్ చేయబడే ఫైర్వాల్ మార్క్; దీనిని `ip rule` + `PREROUTING` సరిపోల్చుతాయి                                             |
| **onPort**       | int (1–65535)      | `8443`   | ట్రాన్స్పరెంట్ (**IP_TRANSPARENT**) లిసనర్ బైండ్ అయ్యే పోర్ట్                                                                     |
| **routeTable**   | int (≥1)           | `233`    | `local 0.0.0.0/0` రూట్ను కలిగి ఉండే పాలసీ-రూటింగ్ టేబుల్ id                                                                       |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | ప్రాక్సీ తన స్వంత అప్స్ట్రీమ్ కనెక్షన్లపై సెట్ చేసే బైపాస్ సాకెట్ మార్క్ (**SO_MARK**); `OUTPUT`లో మినహాయించబడుతుంది (యాంటీ-లూప్) |
| **sudoPassword** | string             | —        | రూట్ కాని డెస్క్టాప్లకు మాత్రమే: ట్రస్ట్-స్టోర్ ఇన్స్టాల్ను ప్రామాణీకరిస్తుంది; రూట్గా ఉన్నప్పుడు విస్మరించబడుతుంది               |

TPROXY కోసం **ఎలాంటి ఎన్విరాన్మెంట్ వేరియబుల్స్ లేవు** — మొత్తం కాన్ఫిగరేషన్
POST బాడీ ద్వారా లేదా పైన పేర్కొన్న డిఫాల్ట్ల ద్వారా అందించబడుతుంది.

## §9 Traffic Inspector నుండి ప్రారంభించడం

1. **Traffic Inspector** (`/dashboard/tools/traffic-inspector`)ను తెరవండి.
2. క్యాప్చర్-మోడ్ల టూల్బార్లో **"TPROXY Decrypt"** ⚠ బటన్ను కనుగొనండి
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - "TPROXY decrypt requires Linux + root +
     the native addon" అనే టూల్టిప్తో ఇది **నిలిపివేయబడి** ఉంటే, ఈ హోస్ట్లో నేటివ్ యాడాన్ అందుబాటులో లేదు (Linux కానిది,
     టూల్చెయిన్ లేకపోవడం లేదా యాడాన్ బిల్డ్ చేయకపోవడం). [§2](#2-requirements) మరియు [§3](#3-the-native-ip_transparent-addon) చూడండి.
3. బటన్ను క్లిక్ చేయండి. ఇది
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`) ద్వారా `POST /api/tools/agent-bridge/tproxy`ను కాల్ చేస్తుంది, ఇది:
   డైనమిక్ CAను బిల్డ్ చేస్తుంది, ట్రాన్స్పరెంట్ లిసనర్ను తెరుస్తుంది, ఫైర్వాల్
   నియమాలను వర్తింపజేస్తుంది మరియు OS ట్రస్ట్ స్టోర్లో CAను ఇన్స్టాల్ చేస్తుంది.
4. ఇది రన్ అవుతున్నప్పుడు, టాగుల్ అంబర్ రంగులోకి మారి లైవ్ ఇంటర్సెప్ట్ సంఖ్యను
   (`· <interceptCount>`) చూపుతుంది. ఇంటర్సెప్ట్ చేసిన అభ్యర్థనలు
   `source: "tproxy"`తో అభ్యర్థనల జాబితాలో కనిపిస్తాయి.
5. ఆపడానికి మళ్లీ క్లిక్ చేయండి — `stopTproxyCaptureMode()` ద్వారా
   `DELETE /api/tools/agent-bridge/tproxy` లిసనర్ను మూసివేసి, CAను అన్ఇన్స్టాల్ చేసి,
   ఫైర్వాల్ నియమాలను వెనక్కి మారుస్తుంది.

క్యాప్చర్-మోడ్ స్థితి (రన్ అవుతోంది / అందుబాటులో ఉంది / ఇంటర్సెప్ట్ సంఖ్య / లిసనర్ పోర్ట్)
`GET /api/tools/agent-bridge/tproxy` నుండి వస్తుంది (`src/mitm/tproxy/captureManager.ts`లోని
`getCaptureStatus()`). ఒక సమయంలో **ఒక** TPROXY సెషన్ మాత్రమే రన్ అవుతుంది —
రెండవదాన్ని ప్రారంభిస్తే "TPROXY capture mode is already running" అనే సందేశంతో తిరస్కరించబడుతుంది.

## §10 సమస్య పరిష్కారం

### టాగుల్ నిలిపివేయబడింది

నేటివ్ యాడాన్ను లోడ్ చేయడం సాధ్యం కావడం లేదు. వీటిని నిర్ధారించండి: మీరు Linuxలో ఉన్నారు, యాడాన్ను
(`npm run build:native:tproxy`) బిల్డ్ చేశారు మరియు ప్రాసెస్ `transparent.node`ను లోడ్ చేయగలదు.
`isTransparentSocketAvailable()` టాగుల్ను నియంత్రిస్తుంది; యాడాన్ లేకపోతే
`GET /api/tools/agent-bridge/tproxy` అనేది `available: false`ను అందిస్తుంది.

### ఏదీ క్యాప్చర్ కావడం లేదు

- ఇంటర్సెప్ట్ చేసిన ప్రాసెస్ వాస్తవంగా కాన్ఫిగర్ చేసిన `dport`కు
  (డిఫాల్ట్ `443`) కనెక్ట్ అవుతోందని నిర్ధారించండి.
- ప్రాసెస్ డైనమిక్ CAను విశ్వసిస్తోందని నిర్ధారించండి. CA
  `omniroute-tproxy-ca.crt` కింద ఇన్స్టాల్ అవుతుంది; సొంత ట్రస్ట్ స్టోర్ ఉన్న యాప్లకు (Firefox/Chrome NSS)
  అక్కడ కూడా సర్టిఫికెట్ను జోడించాల్సి రావచ్చు.
- సర్టిఫికెట్ విశ్వసనీయత / సర్వర్ ఆరోగ్య తనిఖీల కోసం AgentBridge **Diagnose** స్వీయ-పరీక్షను అమలు చేయండి
  ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md) చూడండి).

### క్రాష్ తర్వాత మిగిలిపోయిన ఫైర్వాల్ నియమాలు

`revertTproxy()` అనేది వర్తింపజేసే చర్యకు ఖచ్చితమైన విలోమం మరియు ఇది ఐడెంపొటెంట్. మోడ్ను ఆపడం
నియమాలను వెనక్కి మారుస్తుంది; సెషన్ మధ్యలో OmniRoute నిలిపివేయబడితే, అనాథగా మిగిలిన సిస్టమ్
స్థితిని (DNS స్పూఫ్, రూట్ CA, సిస్టమ్ ప్రాక్సీ) రద్దు చేయడానికి AgentBridge
**Repair** చర్యను (`POST /api/tools/agent-bridge/repair`) ఉపయోగించండి. TPROXY `mangle` నియమాలు మరియు రూట్ కూడా
రీబూట్ సమయంలో స్వయంచాలకంగా తొలగించబడతాయి.

### అనంత లూప్ / ప్రాక్సీ తన సొంత ఫార్వర్డ్ను ఇంటర్సెప్ట్ చేస్తోంది

ఇది యాంటీ-లూప్ సందర్భం. `bypassMark` అనేది `mark`కు భిన్నంగా ఉందని నిర్ధారించండి (వాలిడేషన్
దీన్ని అమలు చేస్తుంది) మరియు ఫార్వర్డ్ `connectMarked`ను ఉపయోగిస్తోందని నిర్ధారించండి (`realForward`లో ఇది ఉపయోగించబడుతుంది).
[§5 యాంటీ-లూప్](#anti-loop-so_mark) చూడండి.
