## LTS మద్దతు వ్యవధి (v3.9.x)

3.8.59 తర్వాతి సంస్కరణ **3.9.0**, ఇది `stable/v3` బ్రాంచ్లో దీర్ఘకాలిక మద్దతు శ్రేణిని
ప్రారంభిస్తుంది ([`ROADMAP.md`](ROADMAP.md) → "దశ 3 — v3.9.0 LTS" చూడండి).

- **`stable/v3`కు అందేవి:** బగ్ పరిష్కారాలు, భద్రతా ప్యాచ్లు మరియు ప్రొవైడర్ నవీకరణలు. కొత్త
  ఫీచర్లు v4 ఛానెల్కు వెళ్తాయి; LTS శ్రేణి స్థిరత్వానికి మొదటి ప్రాధాన్యం ఇస్తుంది. `npm install omniroute`
  (`latest` dist-tag) మొత్తం v4 చక్రంలో v3పైనే కొనసాగుతుంది.
- **వ్యవధి:** `<T-GAP-3: యజమాని నిర్ణయం పెండింగ్లో ఉంది — ROADMAP.md చూడండి>`. v4.0 GA తర్వాత
  (`latest` v4కు మారినప్పుడు) ఈ వ్యవధి ఎంతకాలం ఉంటుందనేది **ఇంకా నిర్ణయించబడలేదు**; నిర్వహకుడు
  ప్రకటించినప్పుడు ఈ విభాగం నవీకరించబడుతుంది. అప్పటివరకు ముగింపు తేదీని ఊహించవద్దు.
- **LTS శ్రేణిలో దుర్బలత్వాన్ని నివేదించడం:** ఇతర సంస్కరణల మాదిరిగానే అదే ఛానెల్ —
  ప్రైవేట్ [GitHub Security Advisory](https://github.com/diegosouzapw/OmniRoute/security/advisories/new),
  పబ్లిక్ సమస్యను ఎప్పుడూ తెరవవద్దు. మీరు పరీక్షించిన సంస్కరణను పేర్కొనండి (ఉదాహరణకు `3.9.2`);

- **LTS విభజన సమయంలో భద్రతా ప్రామాణిక స్థాయి:** కొలిచిన స్కానర్ స్థితి, రూట్-గార్డ్ మరియు
  పబ్లిక్-క్రెడెన్షియల్ రుజువులు
  [`docs/security/LTS_SECURITY_BASELINE.md`](docs/security/LTS_SECURITY_BASELINE.md)లో నమోదు చేయబడతాయి.

## భద్రతా నిర్మాణం

OmniRoute బహుళ-పొరల భద్రతా నమూనాను అమలు చేస్తుంది:

```
అభ్యర్థన → CORS → Authz పైప్లైన్ (వర్గీకరణ → విధానాలు → అమలు)
       → రక్షణ నియమాలు (PII మాస్కర్, ప్రాంప్ట్ ఇంజెక్షన్, విజన్ బ్రిడ్జ్)
       → రేట్ లిమిటర్ → సర్క్యూట్ బ్రేకర్ → కూల్డౌన్ → మోడల్ లాకౌట్ → ప్రొవైడర్
```

### 🛡️ నిల్వలో ఉన్న డేటా ఎన్క్రిప్షన్

SQLiteలో నిల్వ చేయబడిన అన్ని సున్నితమైన డేటా, scrypt కీ ఉత్పన్నంతో **AES-256-GCM**ను ఉపయోగించి ఎన్క్రిప్ట్ చేయబడుతుంది:

- API కీలు, యాక్సెస్ టోకెన్లు, రిఫ్రెష్ టోకెన్లు మరియు ID టోకెన్లు
- సంస్కరణ కలిగిన ఫార్మాట్: `enc:v1:<iv>:<ciphertext>:<authTag>`
- `STORAGE_ENCRYPTION_KEY` సెట్ చేయనప్పుడు పాస్త్రూ మోడ్ (సాదా టెక్స్ట్)

```bash
# ఎన్క్రిప్షన్ కీని రూపొందించండి:
STORAGE_ENCRYPTION_KEY=$(openssl rand -hex 32)
```

### 🛡️ రక్షణ నియమాల ఫ్రేమ్వర్క్

OmniRoute, ప్రాధాన్యత ప్రకారం అమర్చబడిన 3 అంతర్నిర్మిత రక్షణ నియమాలతో హాట్-రీలోడ్ చేయగల **రక్షణ నియమాల రిజిస్ట్రీ**ని (`src/lib/guardrails/`) అందిస్తుంది:

| రక్షణ నియమం        | ప్రాధాన్యత | ఉద్దేశ్యం                                                                               |
| ------------------ | ---------- | --------------------------------------------------------------------------------------- |
| `vision-bridge`    | 5          | విజన్ లేని మోడల్లను చిత్రం-ఆధారిత వివరణలతో అనుసంధానిస్తుంది; చిత్ర URLల కోసం SSRF రక్షణ |
| `pii-masker`       | 10         | కాల్కు ముందు+తర్వాత PII తొలగింపు (ఇమెయిళ్లు, ఫోన్, CPF, CNPJ, క్రెడిట్ కార్డ్లు, SSN)   |
| `prompt-injection` | 20         | ఓవర్రైడ్/పాత్ర-హైజాక్/జైల్బ్రేక్/లీక్ నమూనాలను గుర్తిస్తుంది                            |

అనుకూల రక్షణ నియమాలు `registerGuardrail(new MyGuardrail())` ద్వారా నమోదు అవుతాయి. ఈ నమూనా ఫెయిల్-ఓపెన్ విధానంలో ఉంటుంది (మినహాయింపులు ట్రాఫిక్ను ఎప్పుడూ నిరోధించవు). ప్రతి అభ్యర్థనలో `x-omniroute-disabled-guardrails` హెడర్ ద్వారా నిలిపివేయవచ్చు. → [`docs/security/GUARDRAILS.md`](docs/security/GUARDRAILS.md) చూడండి.

| ఎన్కోడింగ్ ఎగవేత    | మధ్యస్థం | base64/rot13/hex డీకోడ్ + సూచన కీవర్డ్లు                     |

`block` మోడ్లో **అధిక** తీవ్రత కలిగిన గుర్తింపులు మాత్రమే నిరోధించబడతాయి. మధ్యస్థ-తీవ్రత
కుటుంబాలు లాగ్ చేయబడతాయి, కానీ `sanitizeRequest` ద్వారా ఎప్పటికీ నిరోధించబడవు.

డ్యాష్బోర్డ్ (సెట్టింగ్లు → భద్రత) లేదా `.env` ద్వారా కాన్ఫిగర్ చేయండి:

```env
INPUT_SANITIZER_ENABLED=true
INPUT_SANITIZER_MODE=block    # హెచ్చరించు | నిరోధించు (ఇంజెక్షన్ విధానం; పాత "redact" ఇంజెక్షన్ టెక్స్ట్ను తొలగించదు)
INPUT_SANITIZER_BLOCK_THRESHOLD=high  # అధికం (డిఫాల్ట్) | మధ్యస్థం | తక్కువ — బ్లాక్ మోడ్లో ఈ స్థాయి లేదా అంతకంటే ఎక్కువ తీవ్రతలు నిరోధించబడతాయి
```

## అవసరమైన ఎన్విరాన్మెంట్ వేరియబుల్స్

సర్వర్ను ప్రారంభించే ముందు అన్ని రహస్య విలువలను తప్పనిసరిగా సెట్ చేయాలి. అవి లేకపోయినా లేదా బలహీనంగా ఉన్నా సర్వర్ **వెంటనే విఫలమవుతుంది**.

```bash
# అవసరం — ఇవి లేకుండా సర్వర్ ప్రారంభం కాదు:
JWT_SECRET=$(openssl rand -base64 48)     # కనీసం 32 అక్షరాలు
API_KEY_SECRET=$(openssl rand -hex 32)    # కనీసం 16 అక్షరాలు

# సిఫార్సు చేయబడింది — నిల్వలో ఉన్నప్పుడు ఎన్క్రిప్షన్ను ప్రారంభిస్తుంది:
STORAGE_ENCRYPTION_KEY=$(openssl rand -hex 32)
```

`changeme`, `secret`, లేదా `password` వంటి బలహీనమైనవిగా తెలిసిన విలువలను సర్వర్ క్రియాశీలంగా తిరస్కరిస్తుంది.

## కఠినమైన భద్రతా నియమాలు

ఈ నియమాలు టూలింగ్ మరియు సమీక్షకుల ద్వారా అమలు చేయబడతాయి:

1. **రహస్యాలను ఎప్పుడూ కమిట్ చేయవద్దు** — `.env` gitignore చేయబడింది; `.env.example` టెంప్లేట్ (లిటరల్స్ ఉండవు, వ్యాఖ్యలు మాత్రమే — దిగువన ఉన్న PUBLIC_CREDS.md చూడండి)
2. **`eval()`, `new Function()`, లేదా పరోక్ష evalను ఎప్పుడూ ఉపయోగించవద్దు** — ESLint దీన్ని అమలు చేస్తుంది
3. స్పష్టమైన ఆపరేటర్ ఆమోదం లేకుండా **Husky హుక్లను ఎప్పుడూ దాటవేయవద్దు** (`--no-verify`, `--no-gpg-sign`)
4. **రూట్లలో ముడి SQLను ఎప్పుడూ వ్రాయవద్దు** — ఎల్లప్పుడూ `src/lib/db/` ద్వారా వెళ్లండి (పారామీటరైజ్డ్)
5. **ఇన్పుట్లను ఎల్లప్పుడూ Zodతో ధ్రువీకరించండి** — `src/shared/validation/schemas.ts`
6. **అప్స్ట్రీమ్ హెడర్లను ఎల్లప్పుడూ శానిటైజ్ చేయండి** — `src/shared/constants/upstreamHeaders.ts`లో డినైలిస్ట్
7. **నిల్వలో ఉన్నప్పుడు క్రెడెన్షియల్స్ను ఎన్క్రిప్ట్ చేయండి** — `src/lib/db/encryption.ts` ద్వారా AES-256-GCM
8. **`resolvePublicCred()` ద్వారా పబ్లిక్ అప్స్ట్రీమ్ OAuth ఐడెంటిఫయర్లు** — సోర్స్లో `AIza…` / `GOCSPX-…` / `…apps.googleusercontent.com` లిటరల్స్ను ఎప్పుడూ పొందుపరచవద్దు. [`docs/security/PUBLIC_CREDS.md`](docs/security/PUBLIC_CREDS.md) చూడండి.
9. **`buildErrorBody()` / `sanitizeErrorMessage()` ద్వారా లోప ప్రతిస్పందనలు** — ముడి `err.stack` / `err.message`ను HTTP / SSE / executor / MCP ప్రతిస్పందన బాడీలలో ఎప్పుడూ ఉంచవద్దు. [`docs/security/ERROR_SANITIZATION.md`](docs/security/ERROR_SANITIZATION.md) చూడండి.
10. **`env` ఆప్షన్ ద్వారా `exec()` / `spawn()` రన్టైమ్ విలువలు** — బాహ్య పాత్లు లేదా నమ్మదగని విలువలను షెల్కు పంపే స్క్రిప్ట్లలోకి స్ట్రింగ్ ఇంటర్పోలేషన్ ద్వారా ఎప్పుడూ చేర్చవద్దు. సూచన: `src/mitm/cert/install.ts::updateNssDatabases`.
11. **డిఫాల్ట్గానే సురక్షితమైన లైబ్రరీలకు ప్రాధాన్యం ఇవ్వండి** — [tldrsec/awesome-secure-defaults](https://github.com/tldrsec/awesome-secure-defaults) చూడండి (Helmet.js, DOMPurify, ssrf-req-filter, safe-regex, Google Tink). మీ స్వంత పరిష్కారాన్ని రూపొందించే ముందు వాటిని ఉపయోగించడానికి ప్రయత్నించండి.

హ్యాండ్లర్ `.next/server/*.js` మినిఫైడ్ చంక్లలో చేరుతుంది. హ్యూరిస్టిక్
సప్లై-చైన్ స్కానర్లు తరచుగా ఆ చంక్లను మాల్వేర్ సిగ్నేచర్లతో నమూనా-సరిపోలిక చేస్తాయి.

మేము ఉపయోగించే స్కానర్ కాన్ఫిగరేషన్ రిపోజిటరీ రూట్లోని
[`socket.yml`](socket.yml)లో ఉంటుంది (Socket.dev GitHub App ఫార్మాట్ v2 —
<https://docs.socket.dev/docs/socket-yml> చూడండి). ఇది పంపిణీ చేయని
డైరెక్టరీలను (`tests/`, `_tasks/`, `_references/`, `_ideia/`,
`_mono_repo/`, `docs/`, మొదలైనవి) స్పష్టంగా మినహాయిస్తుంది. అందువల్ల
స్కానర్ వాస్తవంగా ప్రచురిత వినియోగదారులకు చేరే కోడ్ పాత్లపై మాత్రమే
నివేదిస్తుంది — ఈ స్కాన్ను ఈ రిపోజిటరీలోని వర్క్ఫ్లో కాకుండా, ఆ ఫైల్ను
చదివే Socket GitHub App నిర్వహిస్తుంది.

ప్రతి నిర్ధారణ వర్గం కోసం, ఒక్కో నిర్ధారణకు మెయింటెయినర్ ధృవీకరణను నిర్వహిస్తాము:

- **[`docs/security/SOCKET_DEV_FINDINGS.md`](docs/security/SOCKET_DEV_FINDINGS.md)** —
  ఒక్కో నిర్ధారణకు మ్యాప్: సోర్స్ ఫైల్ ↔ ఫ్లాగ్ చేయబడిన చంక్ ↔ ప్రవర్తన ↔
  v3.8.6లో వర్తింపజేసిన ఉపశమన చర్య.
- ఫ్లాగ్ చేయబడిన ప్రతి ఫంక్షన్ వద్ద ఉన్న సోర్స్లోని `SECURITY-AUDITOR-NOTE:`
  బ్లాక్లు అదే డాక్యుమెంట్ను సూచిస్తాయి.

అలర్ట్ను సడలించలేని పైప్లైన్ల వినియోగదారులు:
`OMNIROUTE_BUILD_PROFILE=minimal npm run build`తో బిల్డ్ చేయండి. ఇది నాలుగు
సున్నితమైన మాడ్యూల్లను రన్టైమ్లో HTTP 503 `feature-disabled`ను తిరిగి ఇచ్చే
స్టబ్లతో భర్తీ చేస్తుంది. అందువల్ల ప్రత్యేకాధికార కోడ్ పాత్లు బండిల్లో
భౌతికంగా ఉండవు. ప్రచురణ విధానం కోసం
[`docs/security/SOCKET_DEV_FINDINGS.md`](docs/security/SOCKET_DEV_FINDINGS.md)
చూడండి.
