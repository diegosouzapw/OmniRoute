> **TL;DR**: Az `open-sse/` az OmniRoute minden LLM-kérését kiszolgáló alapvető streamelési motor. Körülbelül 1 400 fájlt tartalmaz, amelyek a kérésfeldolgozási folyamatot, a végrehajtókat, a szolgáltatásokat, az MCP-szervert és a fordítási réteget valósítják meg. Ez az útmutató bemutatja, hogyan kapcsolódnak egymáshoz ezek az elemek.

**Forrás:** `open-sse/` (munkaterület-csomag, ~1 440 nem tesztcélú `.ts` fájl)

## Miért különálló munkaterület-csomag?

Az `open-sse/` több okból is **önálló munkaterület** az OmniRoute monorepóban:

1. **Újrafelhasználhatóság** — az `open-sse` `@omniroute/open-sse` néven van közzétéve az npm-en, így más projektek önállóan is használhatják
2. **Egyértelmű határok** — a streamelési motor el van választva az OmniRoute-specifikus felhasználóifelület-/adatbázisrétegtől
3. **Teljesítmény** — a motor nem rendelkezik Next.js-függőségekkel, így gyorsabb hidegindítást tesz lehetővé CLI- és szerver nélküli környezetekben
4. **Verziókezelés** — az `open-sse` a saját ütemezése szerint adhat ki új verziókat

```json
// package.json
"workspaces": ["open-sse"]
```

## A kérésfeldolgozási folyamat

Minden LLM-kérés egy **ötlépcsős feldolgozási folyamaton** halad keresztül:

```
                              ┌──────────────┐
   HTTP-kérés                  │  1. ÚTVONAL  │   combo feloldása, modell kiválasztása
   (Next.js-útvonal)           └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. FORDÍTÁS │   formátumkonverzió (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. VÉGREHAJT│   szolgáltatói végrehajtó, HTTP, újrapróbálkozás, megszakító
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAM   │   SSE-átalakítás, visszanyomás
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. RÖGZÍTÉS │   használatkövetés, hívásnapló, hibabesorolás
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP-válasz (SSE vagy JSON)
```

### 1. szakasz: Útválasztás (services/combo.ts)

**Belépési pont**: `handleComboChat()` a `services/combo.ts` fájlban

A kérést egy konkrét `(provider, model, account, credentials)` négyesre oldja fel:

- Megkeresi a combót azonosító alapján (vagy virtuális combót hoz létre az `auto/*` modellekhez)
- Alkalmazza az útválasztási stratégiát (prioritásos, súlyozott, ciklikus stb.)
- Kiszűri a nem megfelelő állapotú szolgáltatókat (áramköri megszakító)
- Kiválasztja a következő használható célpontot

Az `auto/*` modellek esetében ez a szakasz továbbá:

- Futtatja a **16 tényezős pontozási** algoritmust (`services/autoCombo/`)
- Az állapot, költség, késleltetés stb. alapján kiválaszt egy `provider+model` párost

### 2. szakasz: Fordítás (translator/)

Ha a forrásformátum (például OpenAI) eltér a célformátumtól (például Claude), a kérés **lefordításra kerül**:

- Rendszerprompt → rendszerüzenet
- Eszközdefiníciók → szolgáltatóspecifikus eszközformátum
- Érvelési/gondolkodási paraméterek → szolgáltatóspecifikus megfelelőik
- Üzenetszerepkörök normalizálása (`developer` → `system` a nem OpenAI-szolgáltatóknál)

A `translator/index.ts` a következőket teszi elérhetővé:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### 3. szakasz: Végrehajtás (executors/)

**Belépési pont**: `getExecutor(providerId).execute(request, options)`

Minden szolgáltató a `DefaultExecutor` (`executors/default.ts`) osztályt használja a `getExecutor()` gyár tartalékmechanizmusán keresztül. A végrehajtó:

- Összeállítja a felsőbb rétegbeli URL-t (`buildUrl()`)
- Hozzáadja a szolgáltatóspecifikus fejléceket (`buildHeaders()`)
- Átalakítja a kérés törzsét (`transformRequest()`)
- Elküldi a HTTP-kérést újrapróbálkozással és exponenciális késleltetéssel
- Szükség esetén kezeli a hitelesítés frissítését (OAuth-szolgáltatók)

Minden végrehajtó a `BaseExecutor` osztályt terjeszti ki (`executors/base.ts`, 1170 kódsor), amely a következőket biztosítja:

- Közös újrapróbálkozási logika
- Proxyintegráció
- Áramkörimegszakító-integráció
- Használatrögzítési hookok

### 4. szakasz: Streamelés (utils/stream.ts)

Streamelt válaszok esetén a végrehajtó egy **ReadableStream** objektumot ad vissza. A kezelő:

- Egy SSE-átalakítón vezeti át (`createSSETransformStreamWithLogger`)
- Életjeleket küld a megszakadt kapcsolatok észleléséhez
- Szabályosan kezeli a kliens kapcsolatának megszakadását (`pipeWithDisconnect`)
- Az SSE-t JSON-ná alakítja a nem streamelő kliensek számára

Nem streamelt válaszok esetén a végrehajtó egy elemzett JSON-objektumot ad vissza, amely változatlanul továbbításra kerül.

### 5. szakasz: Rögzítés (services/usage.ts)

A válasz (sikeres vagy sikertelen) után a használati adatok rögzítésre kerülnek:

- A válaszból származó `prompt_tokens`, `completion_tokens`, `cached_tokens`
- Az árképzési adatok alapján kiszámított `cost_usd`
- `latency_ms`, `status`, valamint hiba esetén `error_class`
- Az adatok a `usage_history` táblában kerülnek megőrzésre

A hívásnapló artefaktumai (ha engedélyezve vannak) a `${DATA_DIR}/call_logs/` könyvtárba kerülnek.

## A fő fájlok részletes bemutatása

### chatCore.ts (5977 sor)

A **fő kéréskezelő**. Mérete ellenére világos szerkezettel rendelkezik:

```ts
// A chatCore.ts pszeudoszerkezete
export async function handleChat(request: NextRequest) {
  // 1. Hitelesítés + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. A törzs ellenőrzése
  const body = await parseRequestBody(request);

  // 3. Formátumészlelés + átalakítás
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Kombinációalapú útválasztás
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Folytatás a következő célponttal
    }
  }

  // 5. Vészhelyzeti tartalékmegoldás
  return await emergencyFallback(body);
}
```

Annak ellenére, hogy egyetlen hatalmas függvényből áll, **megjegyzésekkel ellátott szakaszokra** tagolódik, amelyek megfelelnek az ötlépcsős folyamatnak.

// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("a célpont sikertelen, próbálkozás a következővel", {
        target,
        err,
      });
    }
  }
  throw new ComboExhaustedError("Minden célpont sikertelen volt");
}

## Végrehajtók (75+ fájl)

Szolgáltatónként egy fájl. Mindegyik kiterjeszti a `BaseExecutor` osztályt, és felülírja az eltérő részeket.

### Gyakori minták

A szolgáltatók feloldása a `getExecutor(providerId)` segítségével történik, amely a konfigurált végrehajtót adja vissza. Az OpenAI-/Anthropic-kompatibilis szolgáltatók a `DefaultExecutor` végrehajtót (`executors/default.ts`) használják. A szolgáltatóspecifikus viselkedés (alap URL, hitelesítési fejlécek, API-verzió) az `open-sse/config/providers/` könyvtárban van konfigurálva, míg a kéréstörzs átalakításait az `open-sse/translator/` kezeli.

Az **egyéni URL** a szolgáltató konfigurációján keresztül állítható be:

```ts
// Szolgáltatói konfiguráció az open-sse/config/providers/ könyvtárban
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

Az **egyéni hitelesítést** a szolgáltatói nyilvántartás hitelesítési konfigurációja kezeli (API-kulcs, OAuth, fejlécprofilok).

Az **egyéni kéréstörzs-átalakítások** (például amikor az Anthropic elkülöníti a `system` elemet a `messages` elemtől) szolgáltatónként vannak regisztrálva az `open-sse/translator/` könyvtárban.

````

### A végrehajtógyár

Az `executors/index.ts` exportálja a `getExecutor(providerId)` függvényt:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

A feloldás az `ExecutorRegistry` (`executors/registry.ts`) használatával történik: minden specializált végrehajtó deklarálva van az `executors/index.ts` beépített táblájában, és a modul betöltésekor a `registerExecutor(alias, instance)` segítségével regisztrálódik; a `getExecutor()` lekérdezi a nyilvántartást, és minden olyan szolgáltató esetében, amelyhez nincs specializált bejegyzés, egy gyorsítótárazott `DefaultExecutor` végrehajtót használ tartalékmegoldásként. A teljes alias → végrehajtó leképezést a `tests/unit/executor-map-golden.test.ts` etalonteszt írja le.

## Fordítók

Fordítás **3 formátum** között: OpenAI, Anthropic, Gemini, valamint az új Responses API.

### Mikor történik fordítás?

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Gyakori fordítások:

- `OpenAI → Anthropic`: különálló `system` mező, `x-api-key` fejléc
- `OpenAI → Gemini`: `contents` a `messages` helyett, `systemInstruction`
- `OpenAI → Responses API`: `input` tömb, `previous_response_id` állapot

### Kezelt speciális esetek

- `developer` szerepkör → `system` a nem OpenAI-szolgáltatóknál
- `system` szerepkör → egyesítve az első felhasználói üzenettel a GLM/ERNIE esetében
- `json_schema` → a Gemini `responseMimeType` + `responseSchema` mezői
- `tools` → szolgáltatóspecifikus eszközformátum
- Gondolkodási paraméterek (o1, Claude) → szolgáltatóspecifikus megfelelőik

## MCP-kiszolgáló

Az `open-sse/mcp-server/` valósítja meg a **Model Context Protocol** kiszolgálót:

- **110 eszköz** (szolgáltatókezelés, kombinációk, memória, gyorsítótár, tömörítés, proxy, készségek, játékosítás, beépülő modulok, Notion, Obsidian, helyi korpusz)
- **3 átviteli mód**: stdio, SSE, Streamable HTTP
- **33 hatókör** a részletes jogosultságkezeléshez

### Eszközök regisztrálása

Az eszközök önálló fájlokként vannak regisztrálva az `open-sse/mcp-server/tools/` könyvtárban; mindegyik egy nevet, sémát, kezelőt és hatókört exportál:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Átviteli módok

```ts
// stdio (CLI-használat)
startMcpStdio(server);

// SSE (HTTP-alapú streamelés)
startMcpSse(server, port);

// Streamable HTTP (modern MCP)
startMcpStreamable(server, port);
```

### Jogosultságkezelés

Minden eszközhívás hatókör-ellenőrzésen megy keresztül (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Transzformátorok

Az `open-sse/transformer/` a **Chat Completions** és a **Responses API** formátumai között konvertál.

### Miért van szükség külön transzformátorra?

A Responses API az OpenAI új formátuma, amely **állapottartó beszélgetéseket** (`previous_response_id`) használ. Amikor egy kliens Responses-kérést küld, az OmniRoute:

1. Belsőleg Responses → Chat Completions formátumra konvertál
2. Elküldi a szolgáltatónak (bármely, a Chat Completions formátumot támogató szolgáltatónak)
3. Visszakonvertálja a választ Responses formátumra
4. Streameli a konvertált választ a kliensnek

A transzformátor (`transformer/responsesTransformer.ts`) a következőt biztosítja:

```ts
createResponsesApiTransformStream(): TransformStream
```

Ez a következőket kezeli:

- `response.output_item.added` események
- `response.output_text.delta` események
- `response.completed` esemény
- Eszközhívások leképezése (`function_call` ↔ `tool_calls`)

interface ProviderConfig {

## Új komponens hozzáadása

### Új szolgáltatás hozzáadása

1. Hozd létre az `open-sse/services/[serviceName].ts` fájlt egy jól körülhatárolt felelősségi körrel
2. Exportáld a fő kezelőfüggvényt és az esetleges konstansokat
3. Adj hozzá egységteszteket a `tests/unit/services/[serviceName].test.mjs` fájlban
4. Integráld a kérésfeldolgozási folyamatba a `handlers/chatCore.ts` fájlban (ha útválasztással kapcsolatos)
5. Frissítsd az útválasztási logikát a `combo.ts` fájlban, ha a szolgáltatás befolyásolja a célpont kiválasztását
6. Dokumentáld ebben a fájlban

### Új végrehajtó hozzáadása

1. Hozd létre a `BaseExecutor` osztályt kiterjesztő `open-sse/executors/[provider].ts` fájlt
2. Regisztráld a `config/providerRegistry.ts` fájlban
3. Add hozzá az `executors/index.ts` gyárfüggvényéhez
4. Adj hozzá egységteszteket a végrehajtóhoz
5. Dokumentáld a `docs/architecture/ARCHITECTURE.md` fájlban

### Új MCP-eszköz hozzáadása

1. Hozd létre vagy frissítsd az `open-sse/mcp-server/tools/[category]Tools.ts` fájlt
2. Definiálj Zod-sémát a bemenetekhez
3. Regisztráld az eszközt az `mcp-server/index.ts` fájlban
4. Add hozzá a hatókörmátrixhoz az `mcp-server/auth/` könyvtárban
5. Adj hozzá egységteszteket
