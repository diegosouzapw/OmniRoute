   rendelkezzenek, amikor a megállapításokat a tényleges forráskód alapján

## §1 — MITM gyökér-HK telepítése (`77484.js`)

**Forrásfájlok**:

- `src/mitm/cert/install.ts` — nyilvános `installCert()` / `uninstallCert()`,
  platformonkénti `installCertWindows/Mac/Linux`.
- `src/mitm/systemCommands.ts` — a telepítési útvonalak által használt közös
  `execFile` / `spawn` / PowerShell-segédfüggvények.

**Aktiválási feltétel**: a felhasználó a helyi irányítópulton az „MITM proxy
engedélyezése” lehetőségre kattint a `/dashboard/cli-tools/mitm` útvonalon.
Az útvonal csak a visszacsatolási felületről érhető el — lásd a 17. szigorú
szabályt a `CLAUDE.md` fájlban és a
`src/server/authz/routeGuard.ts::isLocalOnlyPath()` hivatkozást. Egy alagúton
keresztül nyilvánosságra került JWT **nem** aktiválhatja ezt a kódútvonalat.

**Végrehajtott emelt jogosultságú műveletek (platformonként)**:

| OS                     | Parancs(ok)                                                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | `certutil -addstore Root <cert>` UAC-n keresztül                                                                  |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | profilonkénti NSS-adatbázis-frissítés a `certutil -d sql:<profile>` használatával                                 |

Ezek ugyanazok a parancsok, amelyeket a `mitmproxy`, a Charles Proxy, a Fiddler
és a Caddy használ. Az, hogy ezek jelen vannak az OmniRoute-ban, a
`docs/security/STEALTH_GUIDE.md` fájlban van dokumentálva.

**v3.8.6 kockázatcsökkentés**:

- A `runElevatedPowerShell()` már nem használja az
  `-EncodedCommand <base64utf16le>` kapcsolót. Az emelt jogosultságú hasznos
  adat egy hívásonként létrehozott ideiglenes `.ps1` fájlba kerül (0o600 mód,
  egy privát `mkdtempSync` könyvtáron belül), és a hivatkozás az `-File`
  kapcsolóval történik. A fájl törlése a `finally` blokkban történik. Ez
  megszünteti a PowerShellen keresztüli, base64-alapú jogosultságemelés
  klasszikus ujjlenyomatát, amelyet a Socket.dev MI-osztályozója megjelölt.
- Az `installCertWindows` tartalmaz egy beágyazott `SECURITY-AUDITOR-NOTE:`
  blokkot, amely ide mutat.

**Miért tartjuk meg**: a MITM proxy egy dokumentált funkció, amelyet a
`docs/security/STEALTH_GUIDE.md` és a `docs/frameworks/MITM-PROXY.md` ismertet.
Eltávolítása működésképtelenné tenné az ügynökhíd funkciókészletét.

## §2 — Zed hitelesítő adatok importálása (`app/api/providers/zed/import/route.js`)

**Forrásfájlok**:

- `src/app/api/providers/zed/discover/route.ts` _(új a v3.8.6 verzióban)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(új a v3.8.6 verzióban)_

**Aktiválás**: a felhasználó a helyi irányítópult Szolgáltatók oldalán az „Importálás a Zedből” lehetőségre kattint. A végpont elérését a `requireManagementAuth` korlátozza. Maga a Zed szerkesztő dokumentált szolgáltatásnevek alatt írja a szolgáltatói API-kulcsait az operációs rendszer kulcstárolójába — lásd: https://zed.dev/docs/ai/llm-providers.

**A v3.8.5 működése (amelyet a Socket.dev megjelölt)**:

A `POST /import` felderítette a hitelesítő adatokat, majd egyetlen oda-vissza kommunikációval automatikusan elmentette őket a helyi SQLite-tárolóba. Nem volt fiókonkénti megerősítés és ujjlenyomat, csupán annyi, hogy „N token található, mind importálva.”

**v3.8.6 megoldás — kétlépcsős megerősítés**:

1. A **`POST /api/providers/zed/discover`** a következőt adja vissza:
   `{ candidates: [{ provider, service, account, fingerprint }] }`. A nyers
   token továbbítására **soha** nem kerül sor. Az ujjlenyomat:
   `sha256(service|account|token).slice(0,16)`.
2. Az irányítópult megjeleníti a jelöltek listáját, az üzemeltető kiválasztja,
   melyeket szeretné importálni, majd elküldi a
   `{ confirmedAccounts: [{ service, account, fingerprint }] }` objektumot a
   **`POST /api/providers/zed/import`** végpontnak.
3. Az importálási végpont **újra beolvassa a kulcstárolót a kiszolgálón**, és a
   `(service, account, fingerprint)` alapján szűr. Egy manipulált vagy
   újrajátszott felderítési válasz nem tudja rávenni az importálási végpontot
   egy nem kapcsolódó token mentésére — ha az aktuális token a felderítés óta
   megváltozott, az ujjlenyomat már nem egyezik, ezért a hitelesítő adat
   kimarad.

Az `OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` környezeti jelző megőrzi a
v3.8.5 működését azon üzemeltetők számára, akik még nem frissítették az
automatizálásukat. A v3.9 verzióban eltávolítjuk.

**Miért tartjuk meg**: a Zedből történő importálás a legkényelmesebb kezdeti
beállítási lehetőség azoknak a felhasználóknak, akik már használják a Zedet,
és a szolgáltatói kulcsaikat újbóli beillesztés nélkül szeretnék átmásolni az
OmniRoute-ba.

## §3 — `execFile` / `spawn` / emelt jogosultságú PowerShell (`21843.js`)

**Forrásfájlok**: `src/mitm/systemCommands.ts`.

**A megjelölés oka**: a kódrészlet újraexportálja az
`execFileWithPassword`, a `runElevatedPowerShell`, valamint a közös
`quotePowerShell` segédfüggvényt. A Socket.dev MI-osztályozója ezeket egy
általános „gazdagépen történő végrehajtást és jogosultságszint-emelést végző
eszközkészletként” érzékeli. Az OmniRoute-on belül ezeket kizárólag a MITM-
tanúsítvány telepítési útvonala (§1), illetve az `execFileWithPassword` esetén
a `sudo` parancsok végrehajtása használja.

**v3.8.6 megoldás**:

- A `runElevatedPowerShell` átalakítása (lásd: §1).
- A `runElevatedPowerShell` és az `execFileWithPassword` mellett elhelyezett
  beágyazott `SECURITY-AUDITOR-NOTE:` blokk dokumentálja az engedélyezőlistán
  szereplő hívókat és a rögzített futtathatófájl-listát.
- Az `execFileWithPassword` `spawn()` hívása egy `nosemgrep` jelölőt tartalmaz,
  amely felsorolja azokat a futtatható fájlokat, amelyeket a segédfüggvény
  megkaphat — a felhasználói bemenettől **nem vezet út a
  `finalCommand`/`finalArgs` értékekhez**.

## §4 / §6 — A 9router szolgáltatásfelügyelője (`api/services/9router/{start,restart}/route.js`)

**Forrásfájlok**:

- `src/app/api/services/9router/_lib.ts` — felügyelőpéldány-gyár.
- `src/app/api/services/9router/{start,stop,restart,status,install,update,auto-start}/route.ts`.
- `src/lib/services/ServiceSupervisor.ts` — általános folyamatindítás / állapotellenőrzési lekérdezés / naplópuffer.

**Aktiválás**: a felhasználó a helyi irányítópult beágyazott szolgáltatások
oldalán a „Telepítés” / „Indítás” lehetőségre kattint.

**Már meglévő védelmi intézkedések**:

- A `src/server/authz/routeGuard.ts` szerint minden `/api/services/*` útvonal
  LOCAL_ONLY (17. szigorú szabály). A visszacsatolási interfészre történő
  korlátozás minden hitelesítési ellenőrzés előtt megtörténik — egy kiszivárgott
  JWT sem tudja elérni ezeket.
- A 9router adatbázissorának kezdeti értékei `status='not_installed', auto_start=0`
  (lásd: `src/lib/db/migrations/071_services.sql:19`). A szolgáltatás az első
  indításkor **nem** indul el.
- A `spawn()` a `src/lib/services/installers/ninerouter.ts` fájlban található
  `resolveSpawnArgs(apiKey, PORT)` által visszaadott binárisútvonallal kerül
  meghívásra; ez a támogatott bináris fájlok rögzített engedélyezőlistája.
- A szabványos kimenet és hibakimenet memóriabeli pufferbe kerül (5 MB-os
  korláttal, lásd: `_lib.ts`) — nem történik lemezre írás, hacsak a felhasználó
  nem engedélyezi a naplózást az irányítópulton.

**v3.8.6 megoldás**: nincs funkcionális változás. A minimális összeállítási
profil (`OMNIROUTE_BUILD_PROFILE=minimal`) a
`src/lib/services/installers/ninerouter.ts` fájlt egy helyőrző
implementációval helyettesíti azon felhasználók számára, akik fizikailag is el
szeretnék távolítani a csomagból az emelt jogosultságú útvonalakat.

**Miért tartjuk meg**: a 9router egy opcionális, helyileg telepíthető
kísérőszolgáltatás (egy WordPress-stílusú bővítményhez hasonlóan), amelynek
használata szigorúan önkéntes.

## §5 — OmniRoute Cloud Sync hitelesítő adatok visszaírása (`api/keys/[id]/route.js`)

**Forrásfájlok**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`.
- `src/app/api/keys/[id]/route.ts` — meghívja a `syncKeysToCloudIfEnabled()` függvényt.

**Aktiválási feltétel**: az `isCloudEnabled()` értéke `true` (az irányítópulton beállítva) **és**
a `CLOUD_URL` konfigurálva van. Ha mindkettő ki van kapcsolva, nem történik kimenő hálózati hívás a
Cloud-végpontra.

**A v3.8.5 viselkedése (a Socket.dev helyesen észlelte a hibát)**:

Az `updateLocalTokens()` felülírta az `accessToken`, `refreshToken` és
`providerSpecificData` értékét a Cloud válaszából, amikor
`cloudUpdatedAt > localUpdatedAt`. Nem volt HMAC, aláírás vagy ellenőrzőösszeg. Egy
hibásan konfigurált vagy rosszindulatú `CLOUD_URL` (illetve a csatornán végrehajtott MITM-támadás) észrevétlenül
lecserélhette a szolgáltatói OAuth-tokeneket.

**A v3.8.6 védelmi intézkedései**:

1. **HMAC-ellenőrzés**: a `verifyCloudSignature(rawBody, sigHeader)` a JSON feldolgozása előtt ellenőrzi
   az `X-Cloud-Sig` fejlécet (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`). Ha a titkos kulcs be van állítva, az aláírás kötelező.
   Ha nincs beállítva (örökölt mód), a rendszer figyelmeztetést naplóz, és elfogadja
   a választ — a v3.9 verziótól a titkos kulcs kötelező lesz.
2. **Titkos mezők kifejezett engedélyezése**: az `accessToken` / `refreshToken` /
   `providerSpecificData` értékei **csak** akkor lesznek felülírva, ha
   `OMNIROUTE_CLOUD_SYNC_SECRETS=true`. Az alapértelmezett mód kizárólag
   nem hitelesítési metaadatokat szinkronizál (`expiresAt`, `status`, `lastError*`,
   `rateLimitedUntil`, `updatedAt`). Ez **visszafelé nem kompatibilis változás** azon felhasználók
   számára, akik távoli tokenszinkronizálásra támaszkodtak — nekik ezt kifejezetten engedélyezniük kell.

**Miért tartjuk meg**: a Cloud Sync az egyetlen mód arra, hogy egy OmniRoute Cloud-bérlő
központilag kezelje a csapat hitelesítő adatait. A javítás egyértelművé teszi a fenyegetési modellt:
„a kiszolgáló aláír, az ügyfél ellenőriz, az üzemeltető pedig engedélyezi.”

## Buildprofil: `minimal`

Azok a felhasználók, akiknek Socket-barát buildtermékre van szükségük, a következő paranccsal készíthetik el:

```bash
OMNIROUTE_BUILD_PROFILE=minimal npm run build
```

A webpack `NormalModuleReplacementPlugin` négy modult helyettesít stubokkal:

| Modul                                       | Stub                                             |
| ------------------------------------------- | ------------------------------------------------ |
| `src/mitm/cert/install.ts`                  | `src/mitm/cert/install.stub.ts`                  |
| `src/lib/zed-oauth/keychain-reader.ts`      | `src/lib/zed-oauth/keychain-reader.stub.ts`      |
| `src/lib/cloudSync.ts`                      | `src/lib/cloudSync.stub.ts`                      |
| `src/lib/services/installers/ninerouter.ts` | `src/lib/services/installers/ninerouter.stub.ts` |

Minden stub ugyanazt a felületet exportálja, de futásidőben minden függvény
`featureDisabledError(name)` hibát dob. A letiltott modultól függő
útvonalak a bizalmas kódútvonal aktiválása helyett egyértelmű üzenettel HTTP 503 választ adnak.

Az így létrejövő csomagot `omniroute-secure` néven történő közzétételre szánjuk. A
közzétételi eljárást lásd a `docs/ops/PUBLISHING_SECURE.md` fájlban.

## Beépülő modulok szétválasztása (a v4-hez nyomon követve)

Hosszú távon az npm-csomagot külön-külön auditálható modulokra tervezzük felosztani.
A nyomon követési feladatot lásd a GitHub feladatkövetőjének v4 mérföldkövénél.
