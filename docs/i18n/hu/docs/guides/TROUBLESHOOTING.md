## Gyors áttekintés

**Most ismerkedsz az OmniRoute-tal?** Kezdd itt — ezek a problémák 90%-át megoldják:

| Ezt látom                                    | Mit jelent                                                     | Teendő                                                                                                                              |
| -------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| „Nem lehet kapcsolódni”                      | Az OmniRoute nem fut                                           | Futtasd az `omniroute` vagy a `docker restart omniroute` parancsot                                                                  |
| „Érvénytelen API-kulcs”                      | A kulcs hibás vagy lejárt                                      | Másold ki újra a kulcsot a szolgáltató webhelyéről                                                                                  |
| „Túllépted a sebességkorlátot”               | Túl sok kérést küldesz                                         | Várj 1 percet, vagy használj `model: "auto"` beállítást az automatikus tartalékra váltáshoz                                         |
| „Túllépted a kvótát”                         | Felhasználtad az ingyenes/fizetős kvótádat                     | Kapcsolj be további szolgáltatókat, vagy használj ingyenes szolgáltatókat (Kiro, Pollinations)                                      |
| „Lassú válaszok”                             | A szolgáltató túlterhelt vagy messze van                       | Használd a `model: "auto/fast"` beállítást, vagy kapcsolj be egy gyorsabb szolgáltatót (Groq, Cerebras)                             |
| „Nem a megfelelő szolgáltató lett használva” | Az `auto` másik szolgáltatót választott                        | Ez normális! Az `auto` a legjobbat választja. Egy adott szolgáltató kényszerítéséhez használd a `model: "openai/gpt-4o"` beállítást |
| „502 Hibás átjáró”                           | A szolgáltató nem érhető el                                    | Várj, majd próbáld újra, vagy használd a `model: "auto"` beállítást a szolgáltatóváltáshoz                                          |
| „401 Nincs engedélyezve”                     | A hitelesítési adataid hibásak                                 | Ellenőrizd az API-kulcsodat, vagy hitelesítsd újra magad OAuth használatával                                                        |
| „Az omniroute nem ismerhető fel”             | A globális node-modulok hiányoznak a Windows PATH változójából | Add hozzá az npm globális előtagját a Windows PATH változójához. Az `npm config get prefix` paranccsal keresheted meg.              |
| „429 Túl sok kérés”                          | Sebességkorlátozás történt                                     | Várj 1 percet, vagy kapcsolj be további szolgáltatókat                                                                              |

## Részletes hibaelhárítás

---

### Sebességkorlátozás ingyenes szolgáltatóknál (429 / 400 / 401)

**Tünet**: Ha a `model: "auto"` beállítást ingyenes vagy hitelesítést nem igénylő szolgáltatókkal (opencode, auggie stb.) használod, időnként válaszok helyett `HTTP 429`, `400` vagy `401` hibát kapsz. Ha néhány pillanattal később ugyanazzal a prompttal újrapróbálkozol, a kérések sikeresek, de az automatizálás (cron-feladatok, ügynökök, szkriptek) már az első hibánál leáll.

**Kiváltó ok**: Három egymástól független hibamód rakódik egymásra:

1. **Szolgáltatói sebességkorlát (`429`)**: Az ingyenes csomagok időablakonkénti kvótát alkalmazhatnak. A párhuzamos hívások hirtelen megugrása kimeríti ezt, ezért a rendszer a következő kérést elutasítja az időablak visszaállásáig.
2. **Hibás modell az átadás során (`400`/`401`)**: Az `auto/*` készletek tartalmazhatnak olyan átadott modelleket az `opencode` szolgáltatótól, amelyek szerepelnek a katalógusban, de nem rendelkeznek élő hitelesítési adatokkal (például `oc/north-mini-code-free` → `401`). Az automatikus útválasztó megpróbálja az egyiket, az sikertelen lesz, és a hiba még a tartalékra váltás előtt továbbterjed.
3. **A párhuzamosság felerősítő hatása (`429` terhelés alatt)**: Amikor egyszerre több ügynök- vagy cron-munkamenet használja az `auto` beállítást, az összesített kérési sebesség meghaladja az ingyenes szolgáltatók által tolerált mértéket, ezért a rendszer a szabályos hívásokat is visszaélésszerűként jelöli meg.

**Ellenőrzött javítás (közösségi jelentés alapján, 2026-08-10)**: hangolj be három környezeti változót, hogy a rotáció, a párhuzamosság és a tartalékra váltás kezelje az ingyenes csomagok ingadozását, ahelyett hogy a folyamat emiatt leállna:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 esetén váltás másik modellre/szolgáltatóra (kihagyja a hibás átadott modelleket)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # explicit felső befogadási korlát a nagy erőforrás-igényű kérésekhez (alapértelmezetten nincs beállítva: nincs kérésszámkorlát, lásd az alábbi megjegyzést)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # hosszabb, korlátozott várakozás a nagy erőforrás-igényű kapacitásra az azonnali, újrapróbálható 503 helyett
```

Állítsd be ezeket az OmniRoute-folyamat környezetében (a démonnál, például a LaunchAgent plist vagy a `systemctl edit` használatával), majd indítsd újra az OmniRoute-ot. A rotációs jelző messze a leghatékonyabb beállítás: a végleges hibát átlátható újrapróbálkozássá alakítja a készlet egyik működő szolgáltatójánál.

**Megjegyzés**: Az `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` korlátozza, hogy egyszerre hány nagy erőforrás-igényű — hosszú kontextusú — kérés futhat; ez a korlát egy befogadási kapu, nem pedig szolgáltatói sebességkorlátozó. **#503-fanout frissítés:** ez a változó alapértelmezetten már nincs beállítva (mostantól csak explicit konfigurálás esetén lép életbe, mint fent) — a nagy erőforrás-igényű kérések befogadását ehelyett egy automatikusan származtatott bájtkeret (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) szabályozza, amely a gazdagép tényleges memóriakorlátjához igazodik. Emiatt egy friss telepítésnél ennek a változónak a beállítása nélkül is jóval kevesebb `503 chat_admission_busy` elutasításnak kell jelentkeznie; az explicit beállítása továbbra is pontosan a dokumentált módon működik. Az explicit bájtkeret-felülbírálások 8 MiB és 2 GiB közötti tartományra vannak korlátozva. A `413 body_exceeds_budget` nem átmeneti hiba: növeld ezt a bájtkeretet, csökkentsd az `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` értékét, vagy növeld a folyamat memóriakorlátját. Az `inflight_bytes_budget` miatti tehermentesítés átmeneti erőforrás-versengést jelez, és továbbra is újrapróbálható. A szolgáltatónkénti sebességkorlátozást (`open-sse/services/rateLimitManager.ts`) külön a `RATE_LIMIT_MAX_WAIT_MS`, a `RATE_LIMIT_MAX_QUEUE_DEPTH` és a `RATE_LIMIT_AUTO_ENABLE` szabályozza — lásd: `.env.example`.

**A működés ellenőrzése**: futtasd gyors egymásutánban kétszer az agentet/cron feladatot, és ellenőrizd, hogy mindkettő sikeresen lefut-e. A javítás előtt a második futtatás jellemzően `429`/`401` hibát ad. A javítás után a sikertelen kérések újrapróbálása — ha vannak ilyenek — transzparensen történik, és a hívás befejeződik. A `curl /monitoring/health` paranccsal is ellenőrizheted a szolgáltatói kapcsolatok `rateLimitedUntil` mezőjét, illetve az érintett szolgáltatókhoz tartozó `circuitBreakers.providerBreakers[].state` értéket — az állapot a `CLOSED`, `DEGRADED`, `OPEN` vagy `HALF_OPEN` értékek egyike (lásd: `src/shared/utils/circuitBreaker.ts`), és egy folyamatosan hibázó szolgáltató állapota `CLOSED → DEGRADED → OPEN` sorrendben változik, mielőtt az alaphelyzetbe állítási időablak engedélyezne egy próbakérést (`HALF_OPEN`).

**Ha továbbra is 429-es hibát látsz**: az adott szolgáltató aktív fiókja ténylegesen kimerítette a _kvótáját_ (nem csak a sebességkorlátot érte el). Adj hozzá egy második fiókot ugyanahhoz a szolgáltatóhoz az OmniRoute irányítópultján a Providers → Accounts menüpontban, vagy vonj be egy másik ingyenes szolgáltatót is (például `routeway`, `auggie`). A rotáció csak az átmeneti sebességkorlátozási/400/401-es hibák esetén segít; a kvóta teljes kimerüléséhez második hitelesítő adat vagy másik szolgáltató szükséges.

**Ha 403-as hibát látsz a vision modelleknél (`auto/vision`, `bazaarlink/*`)**: a csatlakoztatott fiók nem rendelkezik vision funkciót tartalmazó fizetős csomaggal, vagy az API-kulcs jogosultságai nem elegendők. Ellenőrizd a szolgáltató irányítópultján, hogy a kulcs hatóköre tartalmazza-e a vision/multimodális funkciókat, vagy csatlakoztass egy fizetős szintű fiókot, és továbbra is azt használd vision célként.

## npm install figyelmeztetések (ERESOLVE / peer / deprecated)

Az `npm install -g omniroute` futtatásakor számos figyelmeztetés jelenhet meg, például `npm warn ERESOLVE`, tárfüggőségekkel kapcsolatos értesítések és `deprecated` üzenetek. **Ezek várhatóak és ártalmatlanok.** A telepítés sikeres volt, ha a kimenetben az `added <N> packages` üzenet látható.

A tárfüggőségek feloldásával kapcsolatos figyelmeztetések elnyomásához használja az OmniRoute támogatott telepítési módját:

```bash
npm install -g omniroute --legacy-peer-deps
```

A `--legacy-peer-deps` csak az `ERESOLVE` és a tárfüggőségekkel kapcsolatos értesítéseket nyomja el. Az elavulással kapcsolatos értesítések továbbra is láthatók maradnak, mert tranzitív, külső féltől származó csomagokból erednek; nem jelzik a telepítés sikertelenségét.

A figyelmeztetéseket olyan külső csomagok elavult tárfüggőségi tartományai okozzák, amelyekre az OmniRoute-nak nincs ráhatása:

1. **A `marked-terminal` a `marked >=1 <16` verziót igényli, de a talált verzió `marked@18`** — a gyakorlatban megfelelően működik; csak az upstream tárfüggőségi tartomány elavult.
2. **`deprecated prebuild-install@7.1.3`** — egy tranzitív, natív binárisokat letöltő segédprogram. Nem használatos
   a rögzített verziójú `wreq-js` átviteli kötés telepítéséhez, és nem jelzi, hogy a webes sütiszolgáltató
   átviteli beállítása sikertelen volt.

**Nincs szükség beavatkozásra** — a figyelmeztetések nem némíthatók el teljesen az upstream csomagok forkolása nélkül.

## Gemini Web és Playwright Chromium

Ha egy Gemini Web-kérés `503` választ ad vissza egy olyan üzenettel, amely szerint a Playwright Chromium
nincs telepítve, akkor az npm-csomag jelen van, de a böngésző bináris állománya hiányzik.
A Playwright szándékosan elkülöníti a böngészők letöltését az npm-csomag
telepítésétől, ezért ez a válasz várható a böngésző telepítéséig.

Globális npm-telepítés esetén telepítse a Chromiumot az OmniRoute csomagjának
könyvtárából, hogy a böngésző gyorsítótára ugyanahhoz a Playwright-telepítéshez tartozzon:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

A telepítés után indítsa újra az OmniRoute-ot, majd próbálja meg ismét a Gemini Web-kérést. Ha az
OmniRoute-ot Docker-lemezképből futtatja, használja a `-web` lemezképet (vagy a `runner-web`
buildcélt), amely tartalmazza a Chromiumot és annak függőségeit; az alap lemezkép
nem tartalmazza ezeket.

## Vírusirtói téves riasztások

<a name="antivirus-false-positives"></a>

### Az Avast/AVG karanténba helyezi a `README.md` fájlt `MD:HttpRequest-inf[Susp]` jelzéssel

**Ez téves riasztás. Semmi sem fertőzött, és nincs szükség semmilyen intézkedésre.**

Az Avast és az AVG olyan heurisztikát használ, amely megjelöli a sok,
HTTP-kérésnek tűnő hivatkozást tartalmazó egyszerű szöveges/Markdown-fájlokat. Az OmniRoute `README.md` fájlja az npm-csomag része (szerepel a
`package.json` → `files` listában), ezért globális telepítéskor a `node_modules/omniroute/README.md` helyre
kerül — és körülbelül 15 `http://localhost:20128/...` példát tartalmaz (az MCP
HTTP/SSE-végpontokat, az A2A `.well-known` URL-jét és `curl`-kódrészleteket). Ez a hivatkozássűrűség
elegendő a heurisztika aktiválásához.

Ha ez csak nemrég kezdődött: a fájl jellege nem változott meg. A README
végponttáblázata kibővült (MCP HTTP + SSE + A2A került bele), továbbá több `curl`-példát
tartalmaz, így átlépte a küszöbértéket.

A fájl passzív dokumentáció, végrehajtható tartalom nélkül. Biztonságosan visszaállíthatja
a karanténból.

**Teendők:**

1. **Állítsa le az értesítéseket** — vegye fel a telepítési könyvtárat a vírusirtó
   kivételei közé (Avast: Beállítások → Kivételek), hozzáadva a globális `node_modules` elérési útját és/vagy az
   OmniRoute adatkönyvtárát (`~/.omniroute/`).
2. **Jelentse a téves riasztást** — <https://www.avast.com/false-positive-file-form.php>,
   és csatolja a karanténba helyezett `README.md` fájlt. Ez a megoldás mindenkinek segít, mivel
   a gyártó heurisztikája reagál túlzottan egy szövegfájlra.

**Miért nem „javítjuk” ezt a saját oldalunkon:** az összes példa `http://localhost` címet használ, és
a localhost önaláírt tanúsítványok okozta nehézségek nélkül nem használhat `https`-t. Ha egyetlen gyártó heurisztikájának
kikerülése érdekében eltorzítanánk a dokumentációt, azzal minden olvasónak ártanánk egy ellenőrzőprogram hibája miatt.

### A Kaspersky `PDM:Trojan.Win32.Generic` jelzéssel látja el az asztali alkalmazást

**Ez egy viselkedési heurisztika okozta téves riasztás. Semmi sem fertőzött.** A Kaspersky
`PDM:` előtagja azt jelenti, hogy a minősítés a Proactive Defense Module (System Watcher)
összetevőtől származik, amely nem ismert kártevőkkel veti össze a telepítőt, hanem azt vizsgálja, hogy az _mit tesz_. Amikor
riaszt, a Kaspersky az egész telepítést „visszaállítja” — törölve a már
kiírt fájlokat —, így az alkalmazás végül hibásan működik vagy eltűnik.

Az általa megjelölt fájlok az asztali alkalmazásba csomagolt, deklarált, nyílt forráskódú függőségek
változatlan részei, például:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` és
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), az alkalmazáson belüli szolgáltatói bejelentkezéshez és a böngészőalapú csevegéshez
  használt böngészőautomatizálási könyvtár.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — a rögzített verziójú `wreq-js` natív kötés, amelyet böngésző-ujjlenyomattal ellátott HTTP-kérésekhez használnak a webes sütiket alkalmazó
  szolgáltatóknál (`<arch>` értéke `x64` vagy `arm64`).

**Miért riaszt:** a Windows-telepítő **még nincs kódaláírással ellátva**, ezért egy aláíratlan NSIS
telepítőnek nincs reputációja, a viselkedési heurisztikák pedig maximális szigorral működnek. Ez
egy becsomagolt natív DLL-lel és a
`%LOCALAPPDATA%\Programs\OmniRoute` alá írt több száz `.js` fájllal együtt (beleértve a Next.js önálló buildjéből származó, hash-utótaggal ellátott csomagkönyvtárakat)
elegendő a heurisztika aktiválásához. A kódaláírás tervben van;
a bevezetéséig ez az új kiadásoknál ismét előfordulhat.

**Teendők:**

1. **Először ellenőrizze a letöltést** (ezzel kizárható, hogy a fájlt módosították). Minden kiadáshoz tartozik egy
   `latest.yml`, amelynek `sha512` mezője (base64) az `OmniRoute.Setup.<version>.exe`
   telepítőre vonatkozik. A PowerShellben, a telepítőt tartalmazó mappából:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   A kimenetnek egyeznie kell a `latest.yml` → `sha512` értékével. Ha nem egyezik, törölje a fájlt, és
   kizárólag a [GitHub kiadási oldaláról](https://github.com/diegosouzapw/OmniRoute/releases) töltse le újra.
2. **Állítsa vissza, és vegye fel a kivételek közé** — állítsa vissza a karanténból a visszavonás során eltávolított elemeket, és vegye fel a kivételek
   közé a `%LOCALAPPDATA%\Programs\OmniRoute` könyvtárat (Kaspersky → Beállítások → Fenyegetések és kivételek),
   majd telepítse újra.
3. **Jelentse a téves riasztást** — <https://opentip.kaspersky.com/>. A felhasználók által beküldött tévesriasztás-jelentések
   valóban felgyorsítják az engedélyezési listára kerülést.

## Node.js-kompatibilitás

<a name="nodejs-compatibility"></a>

### A bejelentkezési oldal összeomlik, vagy „Module self-registration” hibát jelenít meg

**Ok:** Az OmniRoute által jóváhagyott biztonságos futtatókörnyezeti minimumon kívül eső Node.js-verziót használ. A leggyakoribb eset az, amikor egy régebbi Node 22- vagy 24-javítóverzió fut, amely nem éri el az OmniRoute által megkövetelt, javításokat tartalmazó biztonsági minimumot.

**Tünetek:**

- A bejelentkezési oldal üres képernyőt vagy szerverhibát jelenít meg
- A konzolon az `Error: Module did not self-register` hiba vagy hasonló natív kötési hibák jelennek meg
- A bejelentkezési oldalon egy **narancssárga figyelmeztető sáv** jelenik meg a Node-verzióval, ha a futtatókörnyezet nem felel meg a támogatott biztonsági szabályzatnak

**Megoldás:**

1. Telepítsen egy támogatott Node.js LTS-kiadást (ajánlott: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Ellenőrizze a verziót: a `node --version` parancsnak a 24.x LTS-ágon `v24.0.0` vagy újabb verziót kell mutatnia
3. Telepítse újra az OmniRoute-ot: `npm install -g omniroute`
4. Indítsa újra: `omniroute`

> **Támogatott biztonságos verziók:** `>=22.22.2 <23` vagy `>=24.0.0 <27`. A Node.js 24.x LTS (Krypton) és a Node.js 26 teljes mértékben támogatott.

### npm v11+: a `better-sqlite3` nincs telepítve (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Ok:** A Node.js 24+-hoz mellékelt npm v11 alapértelmezés szerint blokkolja az opcionális
függőségek telepítési szkriptjeit. Mivel a `better-sqlite3` az `optionalDependencies`
között szerepel, és natív fordítást (`node-gyp rebuild`) igényel, az npm értesítés nélkül kihagyja.

**Tünetek:**

- A szerver indításkor összeomlik a `Cannot find module 'better-sqlite3'` hibával
- Az `ls node_modules/better-sqlite3` parancs a „No such file or directory” üzenetet jeleníti meg
- Az `npm ls better-sqlite3` parancs az `(empty)` eredményt jeleníti meg

**Megoldás:**

1. Engedélyezze a telepítési szkripteket, majd telepítse újra:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Vagy telepítse manuálisan az előre lefordított csomagot:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Ellenőrizze, hogy működik-e: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file”

<a name="macos-native-module-rebuild"></a>

**Ok:** Egy globális `npm install -g omniroute` után előfordulhat, hogy a csomagon belüli natív `better-sqlite3` bináris egy másik architektúrához vagy Node.js ABI-hoz lett lefordítva, mint amely helyileg fut. Ez gyakori macOS rendszeren (Apple Silicon és Intel esetén egyaránt), ha az előre lefordított bináris nem egyezik a környezettel.

**Tünetek:**

- A szerver indításkor azonnal leáll egy `dlopen` hibával
- A hiba tartalmazza a `slice is not valid mach-o file` szöveget
- Teljes példa:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Megoldás — fordítsa újra a helyi környezethez (a Node.js korábbi verziójára való visszaállítása nélkül):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Megjegyzés:** Ez újrafordítja a natív kötést a helyi Node.js-verzióhoz és CPU-architektúrához, megszüntetve a bináris inkompatibilitást. A hivatalosan támogatott futtatókörnyezeti tartomány: **`>=22.22.2 <23` vagy `>=24.0.0 <27`** (a `SUPPORTED_NODE_RANGE` a `src/shared/utils/nodeRuntimeSupport.ts` fájlban, összhangban a `package.json` `engines` mezőjével). A Node.js 24.x LTS (Krypton) és a Node.js 26 teljes mértékben támogatott a `better-sqlite3` v12.x verziójával.

## Proxyproblémák

<a name="proxy-issues"></a>

### A szolgáltató ellenőrzésekor „fetch failed” hiba jelenik meg

**Ok:** Az API-kulcs ellenőrzési végpontja (`POST /api/providers/validate`) korábban megkerülte a proxykonfigurációt, ami hibákat okozott azokban a környezetekben, ahol kötelező a proxyn keresztüli útválasztás.

**Javítás (v3.5.5+):** A probléma kijavításra került. A szolgáltató ellenőrzése mostantól a `runWithProxyContext` használatával történik, így automatikusan figyelembe veszi a szolgáltatói szintű és a globális proxybeállításokat.

### A token állapotellenőrzése „fetch failed” hibával meghiúsul

**Ok:** A háttérben futó OAuth-tokenfrissítés nem oldotta fel kapcsolatonként a proxykonfigurációt.

**Javítás (v3.5.5+):** A tokenek állapotellenőrzését végző ütemező mostantól minden kapcsolat esetében feloldja a proxykonfigurációt, mielőtt megkísérli a frissítést. Frissítsen v3.5.5+ verzióra.

### A SOCKS5 proxy „invalid onRequestStart method” hibát ad vissza

**Ok:** Node.js 22 alatt az undici@8 diszpécsere nem kompatibilis a Node beépített `fetch()` implementációjával.

**Javítás (v3.5.5+):** Aktív proxydiszpécser esetén az OmniRoute mostantól az undici saját `fetch()` függvényét használja, ezzel biztosítva a konzisztens működést. Frissítsen v3.5.5+ verzióra.

### MITM proxy WSL alatt: a Windows gazdagépen futó asztali alkalmazások forgalma nincs elfogva

**Ok:** A MITM proxy és annak CA-tanúsítványa abba a környezetbe települ, amelyben az OmniRoute fut. WSL alatt ez a Linux vendégkörnyezet, míg az asztali AI-alkalmazások (Kiro, Trae, Copilot, Zed, …) a Windows gazdagépen futnak. A gazdagépen futó alkalmazások nem bíznak meg a vendégkörnyezet tanúsítványtárolójában, és nem a vendégkörnyezet rendszerproxyján keresztül irányítják a forgalmat, ezért az asztali alkalmazások forgalmának elfogása nem működik.

**Javaslat:** Az OmniRoute-ot natívan ugyanazon az operációs rendszeren futtassa, mint azokat az asztali alkalmazásokat, amelyek forgalmát el szeretné fogni (Windows-alkalmazások esetén Windowson; macOS/Linux esetén hasonlóképpen). Ha az OmniRoute-ot WSL-en belül tartja, miközben a gazdagépen futó alkalmazásokat célozza meg, manuálisan megbízhatóként kell beállítania a létrehozott CA-tanúsítványt a Windows gazdagépen, és minden gazdagépen futó alkalmazás hálózati/proxybeállításait a WSL proxyvégpontjára kell irányítania — ez egy nem támogatott, instabil konfiguráció.

## Szolgáltatói problémák

### „Language model did not provide messages”

**Ok:** A szolgáltatói kvóta kimerült.

**Javítás:**

1. Ellenőrizze az irányítópult kvótakövetőjét
2. Használjon tartalék szinteket tartalmazó kombinációt
3. Váltson olcsóbb/ingyenes szintre

### Sebességkorlátozás

**Ok:** Az előfizetési kvóta kimerült.

**Javítás:**

- Adjon hozzá tartalék lehetőségeket: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Használja a GLM/MiniMax szolgáltatást olcsó tartalékként

### Az OAuth-token lejárt

Az OmniRoute automatikusan frissíti a tokeneket. Ha a problémák továbbra is fennállnak:

1. Irányítópult → Szolgáltató → Újracsatlakozás
2. Törölje, majd adja hozzá újra a szolgáltatói kapcsolatot

### Több Kiro-fiók: a második fiók érvényteleníti az elsőt

**Ok:** A Kiro háttérrendszere OIDC-kliensregisztrációnként csak egyetlen aktív munkamenetet engedélyez.
Ha két fiók ugyanazt a regisztrált klienst használja (a v3.8.0 előtt importált kapcsolatok esetén),
az egyik fiók tokenjének frissítése érvényteleníti a másik frissítési tokenjét.

**Javítás (v3.8.0+):** Importálja újra az érintett kapcsolatokat.
A v3.8.0 verziótól kezdve minden, az **Import Token**,
a **Google/GitHub social login** vagy az **Auto-Import** használatával létrehozott új Kiro-kapcsolat
automatikusan regisztrál egy saját, dedikált OIDC-klienst. Ennek köszönhetően a kapcsolat teljesen
elkülönül, és az egyik fiók frissítése nincs hatással egyetlen másik fiókra sem.

A v3.8.0 _előtt_ importált kapcsolatok nem rendelkeznek kapcsolatonkénti kliensregisztrációval.
Ezek a kapcsolatok továbbra is a megosztott közösségi hitelesítés frissítési végpontját használják.
Az elkülönítéshez törölje a régi kapcsolatot az Irányítópult → Szolgáltatók menüpontban, majd adja
hozzá újra a három importálási folyamat bármelyikével.

A teljes részletekért és két Kiro-fiók egymás melletti hozzáadásának lépésenkénti útmutatójáért
tekintse meg a [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md) dokumentumot.

## Felhővel kapcsolatos problémák

### Felhőszinkronizálási hibák

1. Ellenőrizze, hogy a `BASE_URL` a futó példányra mutat-e (pl. `http://localhost:20128`)
2. Ellenőrizze, hogy a `CLOUD_URL` a felhőbeli végpontra mutat-e (pl. `https://omniroute.dev`)
3. Tartsa összhangban a `NEXT_PUBLIC_*` értékeit a szerveroldali értékekkel

### A felhőbeli `stream=false` 500-as hibát ad vissza

**Tünet:** `Unexpected token 'd'...` hiba jelenik meg a felhőbeli végponton nem streamelt hívások esetén.

**Ok:** A felsőbb szintű szolgáltatás SSE-adatot ad vissza, miközben a kliens JSON-t vár.

**Kerülő megoldás:** A közvetlen felhőbeli hívásokhoz használja a `stream=true` beállítást. A helyi futtatókörnyezet tartalmaz SSE→JSON tartalékmechanizmust.

### A felhő csatlakoztatott állapotot jelez, de „Invalid API key” hibát ad

## Dockerrel kapcsolatos problémák

### Docker IPv6 / kapcsolat-visszaállítás

<a name="docker-ipv6"></a>

**Tünetek:** A `curl http://localhost:20128/v1/models` parancs `curl: (56) Recv failure: Connection reset by peer` hibát ad vissza. Az irányítópult és a hitelesítést nem igénylő végpontok működnek, a hitelesített végpontok azonban nem — ez hitelesítési problémának tűnik, de nem az.

**Ok:** A `docker run -p 20128:20128` az `0.0.0.0` (IPv4) és a `::` (IPv6) címen is közzéteszi a portot, de a konténeren belüli folyamat csak IPv4-en figyel. Azokon a gépeken, ahol a `localhost` először az `::1` címre oldódik fel, a kapcsolat az IPv6-on közzétett portra érkezik, amely mögött nincs figyelő folyamat → a kapcsolat visszaáll.

**Javítás:**

1. **Gyors diagnosztika:** Futtassa a `curl -4 http://localhost:20128/v1/models` parancsot. Ha a `-4` kapcsolóval működik, nélküle viszont nem, akkor IPv6-címkötési eltérés áll fenn.
2. **Végleges javítás:** Kösse a portot kifejezetten IPv4-hez a `-p 127.0.0.1:20128:20128` használatával a `docker run` parancsban:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Ez kikényszeríti az IPv4-címkötést, és azt is megakadályozza, hogy a proxy a gazdagép összes hálózati interfészén elérhető legyen.

## Rugalmassági beállítások

### Az automatikus sebességkorlátozás nem aktiválódik

- Az automatikus sebességkorlátozás csak API-kulcsot használó szolgáltatókra vonatkozik (OAuth-/előfizetés-alapúakra nem)
- Ellenőrizze, hogy a **Settings → Resilience → Provider Profiles** alatt engedélyezve van-e az automatikus sebességkorlátozás
- Ellenőrizze, hogy a szolgáltató ad-e vissza `429` állapotkódot vagy `Retry-After` fejlécet

### Az exponenciális visszalépés finomhangolása

A szolgáltatói profilok a következő beállításokat támogatják:

- **Alapvető késleltetés** — Az első hiba utáni kezdeti várakozási idő (alapértelmezett: 1s)
- **Maximális késleltetés** — A várakozási idő felső korlátja (alapértelmezett: 30s)
- **Szorzó** — Ennyivel nő a késleltetés minden egymást követő hiba után (alapértelmezett: 2x)

### Tömeges egyidejű újrapróbálkozások elkerülése

Amikor sok párhuzamos kérés ér el egy sebességkorlátozott szolgáltatót, az OmniRoute mutexet és automatikus sebességkorlátozást használ a kérések sorosításához és a továbbgyűrűző hibák megelőzéséhez. Ez automatikusan működik az API-kulcsot használó szolgáltatóknál.

### A csevegési kérések 503 / chat_admission_busy hibával meghiúsulnak

**Tünetek:**

- A csevegéskiegészítési végpont egy újrapróbálható `503` választ ad vissza, amelynek hibakódja
  `chat_admission_busy`.
- A válasz tartalmazza a `Retry-After` fejlécet. A #12135 óta az érték a megfigyelt
  kihasználtságból származik — a kérés által már kivárt `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  időablak és az aktuális nagy terhelésű foglalások fennállási ideje közül a nagyobbik — egész
  másodpercre felfelé kerekítve, legfeljebb 60-ig. Terheletlen beléptetési kapu esetén megmaradnak
  a korábbi alsó korlátok: 2 másodperc a bájtalapú útvonalon, 1 másodperc a struktúraalapú
  útvonalon (amely a `reason: "structure_limit"` értéket is tartalmazza).
- Ez akkor fordulhat elő, amikor egy másik nagy terhelésű csevegési kérés vagy hosszan futó
  streamelt válasz még folyamatban van.

A bájtalapú válasz törzse:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

A struktúraalapú válasz ugyanazt a típust és kódot használja, a következő üzenettel:
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
és a `reason: "structure_limit"` értékkel.
Az alapértelmezett küszöbértékek mellett egy kérés akkor minősül strukturálisan nagynak, ha legalább
`200` üzenetet, legalább `64` eszközt vagy legalább `32,000` becsült tokent tartalmaz, illetve ha
a korlátozott struktúrabecslés eléri a `10,000` bejárt csomópontos vagy `12` mélységi korlátját.

**Ok:** Ez szándékos terheléscsökkentés az OmniRoute-on belül, nem pedig a felsőbb szintű szolgáltató hibája.
Minden folyamat egy folyamatlokális védelmet használ, hogy korlátozott kapacitást foglaljon le a nagy
terhelésű kérések számára, mielőtt megtartaná és feldolgozná a nagy méretű kéréstörzset. Egy nagy
terhelésű foglalás az SSE-válasz teljes élettartama alatt fennmarad.

**#503-szétterjedés:** a javítás előtt a védelem a párhuzamosságot a kérések rögzített SZÁMÁRA
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, alapértelmezett: `1`) korlátozta, a gazdagép memóriájától
függetlenül, ezért a kódolóügynökök többfelé ágazása (több alügynök/CLI, rendszeresen > 256 KB-os
törzsek) a tényleges párhuzamosságot körülbelül 1-re csökkentette, és teljesen normál terhelés
mellett is 503-as hibákhoz vezetett. A védelem most már önhangoló: egy automatikusan meghatározott
beolvasási BÁJTkeret (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) szabályozza, amelyet a folyamat tényleges
memóriakorlátja alapján méretez a rendszer, továbbá egy élő erőforrásterhelési jelzést is figyelembe
vesz — így csak akkor csökkenti a terhelést, amikor a gazdagépen valóban memórianyomás áll fenn, nem
pusztán azért, mert egynél több nagy terhelésű kérés érkezett egyszerre. A régi darabszámkorlátot
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) a rendszer továbbra is figyelembe veszi, de csak akkor, ha
kifejezetten beállítja.

Ha a kapacitás foglalt, a nagy terhelésű kérés először legfeljebb
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ideig (alapértelmezett: `2000`, a `0` letiltja a várakozást)
vár egy hely felszabadulására, mielőtt az újrapróbálható `503` választ adná. A korlátozott várakozás
azért létezik, hogy a nagy terhelésű részkéréseket párhuzamosan elágaztató, ügynökszerű kliensek
(OpenCode, Claude Code, Cursor) sorosítsák a kiugró terhelést ahelyett, hogy azonnali elutasításokkal
felhasználnák a teljes újrapróbálkozási keretüket, majd feladatvégzés közben leállnának.
A nagy terhelésű foglalások aktuális kihasználtsága, a meghatározott bájtkeret és az élő terhelés
súlyossága a `GET /api/monitoring/health` → `chatAdmission` alatt érhető el (`inflightBytes`,
`maxInflightBytes`, `budgetSource`, `pressureSeverity`, `countCapEnabled`) — ellenőrizze ezeket,
mielőtt bármely környezeti változót módosítaná.
A Settings → Resilience → Request Queue → Concurrent Requests beállítás ezt nem szabályozza; az
egy különálló szolgáltatói kérési sor mechanizmusát vezérli.

**Javítás:**

1. Először próbálkozzon újra. A klienseknek figyelembe kell venniük a `Retry-After` értékét, és az
   azonnali ismétlés helyett visszalépési stratégiát kell használniuk.
2. Mielőtt bármit finomhangolna, ellenőrizze a `/api/monitoring/health` → `chatAdmission` értékét. A
   `countCapEnabled: false` és a bőséges `maxInflightBytes` azt jelenti, hogy az automatikusan
   meghatározott keret már megfelelően működik; a `high`/`critical` `pressureSeverity` azt jelenti,
   hogy a gazdagépen valóban kevés a memória — ez beléptetési környezeti változóval nem javítható,
   hanem több RAM-ra vagy kisebb munkaterhelésre van szükség.
3. Csak akkor írja felül közvetlenül az `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` használatával, ha a
   `/api/monitoring/health` azt mutatja, hogy az automatikusan meghatározott keret valóban túl kicsi
   a gazdagépéhez (ez ritka — a rendszer már eleve a konténerektől a fizikai gépekig terjedő
   környezethez igazítja), ahelyett, hogy visszatérne a régi, kérésszámon alapuló korláthoz.

A hiteles beléptetési beállításokat lásd a [környezeti változók referenciájában](../reference/ENVIRONMENT.md#4-security--authentication).

## Opcionális RAG / LLM hibataxonómia (16 probléma)

Egyes OmniRoute-felhasználók az átjárót RAG- vagy ágensrendszerek elé helyezik. Ezekben a konfigurációkban gyakran megfigyelhető egy furcsa jelenség: az OmniRoute megfelelően működőnek tűnik (a szolgáltatók elérhetők, az útválasztási profilok rendben vannak, nincsenek sebességkorlátozási riasztások), a végső válasz mégis hibás.

A gyakorlatban ezek az incidensek általában az átjáró utáni RAG-folyamatból, nem pedig magából az átjáróból erednek.

Ha közös szókészletet szeretne használni ezeknek a hibáknak a leírására, használhatja a WFGY ProblemMap erőforrást. Ez egy külső, MIT-licenccel rendelkező szöveges erőforrás, amely tizenhat visszatérő RAG / LLM hibamintát határoz meg. Átfogóan a következőket fedi le:

- lekérdezési elcsúszás és hibás kontextushatárok
- üres vagy elavult indexek és vektortárak
- eltérés a beágyazások és a szemantika között
- prompt-összeállítási és kontextusablakkal kapcsolatos problémák
- logikai összeomlás és túlzott magabiztossággal adott válaszok
- hosszú láncokkal és ágenskoordinációval kapcsolatos hibák
- többágenses memória- és szerepeltolódás
- telepítési és rendszerindítási sorrenddel kapcsolatos problémák

Az elképzelés egyszerű:

1. Egy hibás válasz kivizsgálásakor rögzítse a következőket:
   - felhasználói feladat és kérés
   - az OmniRoute-ban használt útvonal- vagy szolgáltatókombináció
   - az átjáró után felhasznált bármely RAG-környezet (lekért dokumentumok, eszközhívások stb.)
2. Sorolja be az incidenst egy vagy két WFGY ProblemMap-szám alá (`No.1` … `No.16`).
3. Tárolja a számot a saját irányítópultján, üzemeltetési kézikönyvében vagy incidenskövetőjében az OmniRoute-naplók mellett.
4. A megfelelő WFGY-oldal segítségével döntse el, hogy módosítania kell-e a RAG-rendszerét, a lekérdezőjét vagy az útválasztási stratégiáját.

A teljes szöveg és a konkrét receptek itt találhatók (MIT-licenc, csak szöveg):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Ezt a szakaszt figyelmen kívül hagyhatja, ha az OmniRoute mögött nem futtat RAG- vagy ágensfolyamatokat.

### Beragadt modell-visszahűtés (kézi visszaállítás)

**Tünetek:**

- Egy modell a lejárati idő letelte után is visszahűtési állapotban marad
- A kérések a múltbeli időbélyeg ellenére továbbra is kihagyják a modellt a kombinált útválasztás során

**Kézi visszaállítás:**

- **Irányítópult:** **Settings → Model Cooldowns** → kattintson az érintett kártyán a **Re-enable** gombra
- **API:** `DELETE /api/resilience/model-cooldowns` kezelési hitelesítési fejlécekkel

### A Command Code szolgáltatói kapcsolata 403-as hibával meghiúsul

**Tünetek:**

- 403-as hiba a Command Code szolgáltatói kapcsolatának tesztelésekor
- A szolgáltatói kártyán friss hozzáadás után az „unauthorized” állapot jelenik meg

**Ok:** Az OAuth-folyamat nem fejeződött be (a visszahívás nem érkezett meg, vagy a token nem lett tartósan mentve).

**Javítás:**

- Futtassa az `omniroute providers` parancsot a CLI-ből az OAuth-folyamat újbóli elindításához, vagy
- Futtassa újra az OAuth-folyamatot a **Dashboard → Providers → Command Code → Reconnect** felületen

### A ModelScope túl agresszív 429-es visszahűtéseket ad vissza

**Tünetek:**

- Nagyon rövid vagy azonnali visszahűtések a ModelScope szolgáltatásban egy kisebb kéréssorozat után
- A kombinált útválasztás a vártnál korábban hagyja ki a ModelScope-ot

**Ok:** A ModelScope szolgáltatóspecifikus `Retry-After` fejléceket bocsát ki. A v3.8.0 külön kezelést tartalmaz ezekhez a fejlécekhez, ezért a régebbi verziók általános sebességkorlátozási jelzésekként értelmezik őket.

**Javítás:**

- Győződjön meg arról, hogy a v3.8.0 vagy újabb verziót használja
- Ellenőrizze, hogy a `useUpstream429BreakerHints` kapcsoló engedélyezve van-e a **Settings → Resilience** alatt

### Az OMNIROUTE_WS_BRIDGE_SECRET hiányzik az éles környezetből

**Tünetek:**

- 401-es hiba minden Codex/Responses WebSocket-hídkérésnél, amikor a rendszer távoli éles gazdagépen fut
- A WebSocket-híd kézfogása közvetlenül a csatlakozás után megszakad

**Ok:** Az `OMNIROUTE_WS_BRIDGE_SECRET` környezeti változó hiányzik az éles környezetből.

**Javítás:**

1. Hozzon létre egy véletlenszerű titkot: `openssl rand -hex 32`
2. Állítsa be az `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` értéket az éles kiszolgáló környezetében (és minden olyan kliensben, amely kommunikál a híddal)
3. Indítsa újra az OmniRoute-ot

### Responses API: a háttérmód szinkron működésre korlátozódik

**Tünetek:**

- A naplózott figyelmeztetés: `background mode degraded to synchronous`
- Egy `background: true` kérés háttérfeladat-kezelő helyett normál szinkron választ ad vissza

**Ok:** A v3.8.0 a Responses API `background: true` beállítását szándékosan szinkron végrehajtásra korlátozza, miközben figyelmeztetést bocsát ki. A teljes aszinkron háttér-végrehajtás egy későbbi fejlesztés része lesz.

**Javítás:**

- Módosítsa a klienst úgy, hogy a hívást `background` nélkül hajtsa végre, vagy
- Várjon egy későbbi kiadásra, amely már tartalmazza a teljes aszinkron háttérmódot (kövesse a változásnaplót)

## Lassú indulás / készenléti időtúllépés

Ha a CLI a `⚠ Server did not respond within 60s` üzenetet jeleníti meg, de a szerver valójában működik, akkor a készenléti ellenőrzéshez rendelkezésre álló idő túl rövid az Ön környezetében.

Ez gyakran előfordul Windows rendszeren (vírusirtó, fájlrendszer-figyelők) vagy nagy indulási terheléssel rendelkező konténerekben.

**Megoldás — növelje az időkeretet:**

```bash
# Környezeti változóval (az újraindítások között is megmarad):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 perc
omniroute serve

# CLI-kapcsolóval (egyszeri):
omniroute serve --ready-timeout 180000
```

Az alapértelmezett érték 60 000 ms (60 s). A figyelmeztetés csak tájékoztató jellegű; a szerver a háttérben folytatja az indulást, és a rendszerindítás befejezése után elérhetővé válik.

Az `OMNIROUTE_READY_TIMEOUT_MS` teljes dokumentációját lásd itt: [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
