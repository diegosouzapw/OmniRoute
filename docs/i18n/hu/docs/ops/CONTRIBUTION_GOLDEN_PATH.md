Használja ezt az útmutatót a pull requesthez szükséges legkisebb, megbízható fejlesztési ciklus kiválasztásához. Ez nem
helyettesíti az alább hivatkozott, területspecifikus architektúra- és biztonsági dokumentumokat; az egyes gyakori
módosítástípusokat összekapcsolja a hozzájuk tartozó szerződésekkel, célzott ellenőrzésekkel és CI-lefedettséggel.

## Az összes módosítás által követett útvonal

1. **Szerkesztés előtt válassza ki az alapágat.** Keresse meg a legmagasabb verziójú aktív `release/v*` ágat, és hozzon létre
   belőle egy új ágat az ág legfrissebb commitjánál. A pull request célága ez legyen, ne a `main`. Ha kiadási befagyasztás van érvényben, ne a befagyasztott
   ágat célozza; használja a
   [Branching & Release Model](BRANCHING_MODEL.md) dokumentumban ismertetett következő aktív ciklust.
2. **Nevezze meg a szerződéseket.** Azonosítson minden katalógust, sémát, generált összetevőt, nyilvános API-t vagy felhasználói
   felületet, amelyet a módosítás érint. Az alábbi táblázat megadja a minimális kiindulási készletet.
3. **Írjon vagy frissítsen célzott teszteket.** A `src/`, `open-sse/`, `electron/` vagy
   `bin/` könyvtárban végzett éles módosításokhoz ugyanabban a PR-ben automatizált teszt szükséges. Először a viselkedést igazoló
   legkisebb tesztfájlokat futtassa, majd a felsorolt célzott ellenőrzéseket.
4. **Hagyja, hogy a CI futtassa a széles körű mátrixot.** A teljes egységteszt-szegmensek, a Vitest, a lefedettségi küszöb
   és az éles build a PR-en futnak. Széles körű tesztcsomagot csak akkor futtasson helyben, ha egy célzott hiba
   kiterjedtebb hatásra utal, vagy ha a módosítás több alrendszert érint.
5. **A felülvizsgálat előtt egyeztesse a módosításokat.** Kérje le az aktív alapágat, vizsgálja meg annak új commitjait és a saját módosításainak
   hozzá viszonyított eltéréseit, majd a közreműködői munkafolyamatnak megfelelően végezzen rebase-t, vagy merge-ölje az alapágat. A generált fájlokkal
   és katalógusokkal kapcsolatos ütközéseket a forrásuknál oldja fel, generálja újra őket, futtassa újra a célzott ciklust, és ellenőrizze, hogy a
   PR célága továbbra is az aktív kiadási ág.
6. **Rögzítse a bizonyítékokat.** A PR-sablonban sorolja fel a futtatott parancsokat, minden hozzáadott vagy módosított tesztfájlt,
   a migrációkat vagy funkciójelzőket, valamint minden olyan ellenőrzést, amely még csak a CI-ben vár futtatásra.

## Bevált munkafolyamatok módosítástípusonként

Az alábbi parancsok a minimálisan szükséges célzott ellenőrzések; nem jelentenek engedélyt a módosított
viselkedést közvetlenül lefedő teszt kihagyására.

### Szolgáltató

**Szerződések**

- A szolgáltató definíciója a `src/shared/constants/providers/` könyvtárban, valamint annak összeállítása a
  `src/shared/constants/providers.ts` fájlban.
- Modellek és képességek az `open-sse/config/providerRegistry.ts` fájlban vagy az abból kinyert rendszerleíró fájlokban.
- Végrehajtó-/fordítóválasztás, OAuth- vagy API-kulcs-konfiguráció, irányítópult-erőforrások és adott esetben a generált
  szolgáltatói referencia.
- A nyilvános hitelesítő adatoknak a `resolvePublicCred()` függvényt kell használniuk; a hibaválaszoknak a megosztott, megtisztított
  hibasegédeket kell használniuk. Lásd: `docs/security/PUBLIC_CREDS.md` (git; nincs beépítve a `/docs` könyvtárba), valamint
  [Hibák megtisztítása](../security/ERROR_SANITIZATION.md).

**Célzott ciklus**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # amikor a katalógus módosul; commitolja a generált eltérést
npm run lint
```

Teszteljen minden érintett kéréstípust is: csevegés, Responses, képek, beágyazások, hang vagy videó.
A generált katalógus és a referenciaként szolgáló kimenetek eltéréseit szerződésmódosításként vizsgálja felül; ne fogadja el őket vakon.

### Útválasztás

**Szerződések**

- Nyilvános stratégiaértékek és felhasználóifelület-metaadatok a `src/shared/constants/routingStrategies.ts` fájlban.
- Elosztás és sorrend az `open-sse/services/combo.ts` fájlban és az `open-sse/services/combo/` könyvtárban.
- Kombinációs sémák, perzisztencia, rezilienciaállapot, modellképességek és API-/felhasználóifelület-vezérlők.
- Az [Auto-Combo Engine](../routing/AUTO-COMBO.md) és a rezilienciára vonatkozó dokumentáció, ha a viselkedés módosul.

**Célzott ciklus**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # stratégia- vagy elosztásmódosítások
npm run check:known-symbols      # a stratégiaregisztráció módosításai
npm run lint
```

Helyben determinisztikus, szimulált upstreamet használó teszteket futtasson. Az élő kombinációs füsttesztekhez hitelesítő adatok szükségesek, és
manuálisak; nem helyettesítik a CI-t.

### Felhasználói felület / felhasználói élmény

**Szerződések**

- Next.js-útvonalak/-oldalak és a megosztott komponensek határai a `src/app/` és
  `src/shared/components/` könyvtárban.
- API-válaszformák, betöltési/üres/hibaállapotok, billentyűzet- és képernyőolvasó-használat,
  reszponzív elrendezés, témázás és területi beállítások bővítése.
- Angol felhasználóifelület-forrásszövegek a `src/i18n/messages/en.json` fájlban; ne kódoljon be közvetlenül új, felhasználóknak szánt szöveget.

**Célzott ciklus**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interakciós vagy vizuális módosítások esetén futtassa az alkalmazást, és ellenőrizze keskeny és széles nézetben is. A CI futtatja az
éles buildet és a szélesebb körű tesztcsomagokat; a vizuális viselkedéshez azonban továbbra is szükség van a módosításnak megfelelő célzott komponens- vagy Playwright-tesztre,
illetve dokumentált manuális ellenőrzésre.

### i18n

**Szerződések**

- A `src/i18n/messages/en.json` a felhasználói felület forrása; a `config/i18n.json` a területi beállítások forrása.
- A CLI-katalógusok külön, a `bin/cli/locales/` könyvtárban találhatók.
- Pontosan őrizze meg az ICU-helyőrzőket és -címkéket. Ne fordítsa le a termékek, szolgáltatók és modellek nevét,
  a protokollok és fejlécek nevét, a parancsokat, a kód-/JSON-azonosítókat, az URL-eket, a környezeti változókat, illetve
  az olyan védett kifejezéseket, mint az `OmniRoute`, `OAuth`, `MCP` és `A2A`. Az aktuális forráslista:
  `scripts/i18n/glossary/protected-terms.json`.

**Célzott ciklus**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # amikor a CLI-szövegek/-katalógusok módosulnak
npm run lint
```

Ez a meglévő rendszer használatához nyújt útmutatást, nem pedig felhívás az eszközkészlet vagy a kulcsmodell bővítésére.
Amíg a helyettesítő rendszer tervezése folyamatban van, tartsa az i18n-javításokat célzottan minimálisnak. Ne futtasson külső
szolgáltatásokat meghívó fordítási parancsokat, kivéve, ha a feladat kifejezetten generált fordításokat igényel, és
áttekintette az így létrejött eltéréseket.

### CLI

**Szerződések**

- A `bin/cli/` alatti nyilvános parancsok és kapcsolók, a generált API-parancsok, a kilépési kódok, az stdout/stderr és
  a JSON-kimenetek szerkezete, a konfigurációs/környezeti viselkedés, valamint a csomagolt fájlok.
- A CLI felhasználóknak szánt karakterláncainak a CLI i18n-rétegét kell használniuk, és az `en`/`pt-BR` katalógusokat szinkronban kell tartaniuk.
- A Node maradjon a támogatott futtatókörnyezet, és őrizze meg a közzétett bináris szerződést.

**Célzott ciklus**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # generált/csomagolt CLI-módosítások
npm run check:pack-policy     # a csomag nyilvános felületének módosításai
npm run lint
```

Ha a viselkedés az értelmezéstől, fájloktól vagy a kilépési állapottól függ, használja a pontos parancsot egy ideiglenes adatkönyvtárban. A CI végzi el a csomagösszetevők és az ökoszisztéma átfogóbb ellenőrzéseit.

### Adatbázis

**Szerződések**

- A tartománymodulok a `src/lib/db/` alatt találhatók; az egyes modulokat közvetlenül importálja (a régi `localDb.ts` újraexportálási réteg el lett távolítva).
- Számozott, idempotens SQL-migrációk a `src/lib/db/migrations/` alatt, tranzakcióbiztonság, frissítési
  viselkedés, indexek, valamint a séma által érintett minden hívó.
- Az útvonalak és kezelők soha nem adnak ki közvetlenül nyers SQL-t.

**Célzott ciklus**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migráció hozzáadásakor teszteljen friss adatbázissal és az előző sémáról való frissítéssel is. Az adatbázisteszteknek a tisztítás során le kell zárniuk a leírókat, és meg kell hívniuk a `resetDbInstance()` függvényt. Az `npm run test:bun:db` parancsot csak akkor futtassa, ha a legjobb erőfeszítés elve alapján támogatott Bun-adapter útvonala változik; továbbra is a Node a mérvadó.

### Build / telepítés

**Szerződések**

- Gyökér- és munkaterületi manifestek/lockfile, `scripts/build/`, a Next.js önálló összeállítása, a `dist/`
  csomag tartalma, az Electron platformspecifikus metaadatai, CI-munkafolyamatok és telepítési jelzők.
- A támogatott Node-verziótartományoknak és a Bun `CLAUDE.md` fájlban engedélyezőlistán szereplő használatának változatlanul kell maradniuk.
- A build eredményei ne kerüljenek verziókövetés alá; a függőségi, licenc-, munkafolyamat- és csomagszabályzatok érvényesek.

**Célzott ciklus**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # függőség- vagy lockfile-módosítások
npm run check:pack-policy      # a közzétett csomag felületének módosításai
npm run lint
```

Az `npm run build` parancsot helyben csak akkor használja, ha a módosítás érinti a fordítást, az önálló összeállítást, az erőforrásokat vagy a futásidejű csomagolást. Az `npm run build:release` parancsot csak kiadási/telepítési ellenőrzéshez használja. A CI buildje a végső platformközi jelzés; a platformspecifikus Electron-módosításokhoz a megfelelő célzott build vagy smoke teszt bizonyítéka szükséges.

## Helyi jelöltciklus

A forrástesztek nem tudják bizonyítani, hogy a csomagolt műtermék elindul: a csomagolási listák, a ritkított függőségek
és a natív binárisok hibái csak a tarball telepítése és elindítása után jelentkeznek. Az `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) az RFC #8084 egyszeri összeállítási / ellenőrzési / előléptetési folyamatának
helyi oldala: létrehoz egy jelöltet, pontosan azt a műterméket ellenőrzi, könyvtár-átnevezésekkel
előlépteti, majd visszaállítja, ha az előléptetett hely állapotellenőrzése sikertelen.

```bash
npm run dev:candidate -- run --dry-run --json  # a terv kiírása módosítás nélkül
npm run dev:candidate -- run                   # összeállítás + ellenőrzés + előléptetés, automatikus visszaállítással
npm run dev:candidate -- build                 # npm pack + telepítés az _artifacts/candidate/<id>/ könyvtárba
npm run dev:candidate -- validate --id <id>    # indítás egy szabad porton, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # a current és a previous felcserélése
npm run dev:candidate -- run --from-tarball <file.tgz>  # máshol (CI-ban) létrehozott tarball újrafelhasználása
```

- **Egyszeri összeállítás.** A `build` becsomagolja az aktuális fát (ehhez szükséges a `dist/server.js`, ezért előbb futtassa az
  `npm run build:release` parancsot), vagy bemásolja a `--from-tarball` által megadott fájlt, majd telepíti a tarballt egy
  elkülönített npm-előtag alá, mivel a tarball nem tartalmaz `node_modules` könyvtárat. Az azonosító a rövid `HEAD`
  sha (`-dirty` utótaggal, ha a fában helyi módosítások vannak), tarball esetén pedig `tgz-<sha256>`. A már
  összeállított, tiszta azonosítójú jelöltet a rendszer az újbóli összeállítás helyett újra felhasználja; az újbóli összeállításhoz adja meg a `--force` kapcsolót.
- **A csomagot ellenőrizze, ne a forrást.** A `validate` elindítja a telepített CLI-t
  (`serve --port <free port>`) egy friss `DATA_DIR=<candidate>/data` könyvtárral és hamis titkos értékekkel, miközben az
  operátor `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` és `INITIAL_PASSWORD` változóit eltávolítja a
  környezetből, így egy friss telepítés kulcs nélküli loopback-beállítását ellenőrzi. Megvárja, hogy a
  `GET /api/health` 200-as választ adjon, megköveteli, hogy a `GET /v1/models` szintén 200-as választ adjon, leállítja a folyamatcsoportot,
  majd a tarball kivonatával együtt rögzíti az eredményt a `validation.json` fájlban.
- **Ugyanazt a műterméket léptesse elő.** A `promote` elutasítja azt a jelöltet, amelynek az
  aktuális tarballkivonatához nem tartozik sikeres ellenőrzés. Az alapértelmezett aktív hely az `_artifacts/candidate/current`; a `--target <dir>`
  egy másik, ugyanazon a fájlrendszeren található könyvtárat választ ki, amelynek előző helye a `<dir>.previous`.
  Minden átnevezés atomi művelet, és egy részleges hiba visszafordítja a már végrehajtott átnevezéseket.
- **Visszaállítás.** A `run` ismét ellenőrzi az előléptetett helyet, és az ellenőrzés sikertelenségekor
  visszacseréli a `current` és `previous` helyeket. Az első ellenőrzésen megbukó jelölt soha nem lesz előléptetve.

Minden a git által figyelmen kívül hagyott `_artifacts/candidate/` könyvtárba kerül; a meglévő OmniRoute-
telepítés és annak adatkönyvtára érintetlen marad. Az előléptetett CLI elérési útja:
`_artifacts/candidate/current/prefix/bin/omniroute`; használatkor a saját `DATA_DIR` változójával indítsa el.
Kilépési kódok: `0` siker, `1` sikertelen ellenőrzés vagy előléptetés, `2` használati hiba vagy hiányzó összeállítás.

## Helyi ciklus kontra CI

| Futtatás helyben minden módosításhoz                                                                   | A CI által biztosított széles körű visszajelzés                                    |
| ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| A fenti közvetlen viselkedési tesztek és kategóriakapu-ellenőrzések                                    | Particionált teljes egységtesztcsomag és soros tesztek                             |
| `npm run lint`                                                                                         | Vitest tesztcsomagok, valamint lefedettségi és minőségi küszöbök                   |
| Típusellenőrzés vagy build csak akkor, ha az érintett szerződés megköveteli                            | Éles build, biztonsági, dokumentációs, függőségi és PR-szabályzati kapuk           |
| Manuális interakciós/élő ellenőrzések csak akkor, ha az automatizálás nem képes igazolni a viselkedést | A munkafolyamat által konfigurált feladatközi integrációs és platform-ellenőrzések |

A sikeres célzott ciklus bizonyíték a módosított szerződés helyességére, nem pedig garancia arra, hogy a nem kapcsolódó CI-ellenőrzések is sikeresek lesznek. Ugyanakkor ne várakoztasson minden helyi szerkesztést a teljes adattár-mátrix lefutására.

## Egyeztetési ellenőrzőlista

Felülvizsgálat kérése előtt:

- Ellenőrizze, hogy a PR alapága továbbra is a legmagasabb aktív `release/v*` ág.
- Kérje le ezt az alapágat, és tekintse át az elágazás óta bekerült commitokat.
- Tekintse át a `git diff <active-base>...HEAD` kimenetét a véletlen vagy generált módosítások kiszűréséhez.
- A katalógus- és generált dokumentumok ütközéseit a forrás frissítésével és a kimenet újragenerálásával oldja fel.
- Az egyeztetés után futtassa újra a PR leírásában felsorolt összes célzott tesztet és kapuellenőrzést.
- Soha ne gyengítse az elvárásokat, és ne hagyjon el kötelező teszteket pusztán azért, hogy igazodjon egy elmozdult alapághoz.

A kiadásbefagyasztási és újracélzási szabályokat lásd az
[Ágaztatási és kiadási modellben](BRANCHING_MODEL.md). A CI-ellenőrzések teljes jegyzékét lásd a
[Minőségi kapuk referenciájában](../architecture/QUALITY_GATES.md).
