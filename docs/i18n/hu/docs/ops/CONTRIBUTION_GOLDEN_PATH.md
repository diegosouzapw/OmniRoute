Ezen útmutató segítségével válassza ki a legkisebb megbízható fejlesztési ciklust egy pull requesthez. Ez nem
helyettesíti az alább hivatkozott, területspecifikus architekturális és biztonsági dokumentumokat; minden gyakori
módosítástípust összekapcsol a hozzá tartozó szerződésekkel, célzott ellenőrzésekkel és CI-lefedettséggel.

## Az egyes módosítások által követett útvonal

1. **Szerkesztés előtt válassza ki az alapágat.** Keresse meg a legmagasabb verziójú aktív `release/v*` ágat, és
   annak csúcsából hozzon létre új ágat. Ezt az ágat célozza, ne a `main` ágat. Ha kiadási befagyasztás van érvényben, ne a befagyasztott
   ágat célozza; használja a
   [Ág- és kiadási modellben](BRANCHING_MODEL.md) leírt következő aktív ciklust.
2. **Nevezze meg a szerződéseket.** Azonosítson minden katalógust, sémát, generált műterméket, nyilvános API-t vagy felhasználói
   felületet, amelyet a módosítás érint. Az alábbi táblázat megadja a minimális kiindulási készletet.
3. **Írjon vagy frissítsen célzott teszteket.** A `src/`, `open-sse/`, `electron/` vagy
   `bin/` alatti éles kód módosításaihoz ugyanabban a PR-ben automatizált teszt szükséges. Először a viselkedést igazoló
   legkisebb tesztfájlokat futtassa, majd a felsorolt célzott ellenőrzéseket.
4. **A széles körű mátrixot bízza a CI-re.** A teljes egységteszt-szegmensek, a Vitest, a lefedettségi küszöb fokozatos szigorítása és
   az éles build a PR-en futnak. Széles körű tesztkészletet helyben csak akkor futtasson, ha egy célzott hiba
   szélesebb körű hatásra utal, vagy ha a módosítás több alrendszert érint.
5. **Ellenőrzés előtt egyeztesse a változásokat.** Töltse le az aktív alapágat, vizsgálja meg annak új commitjait és az ahhoz viszonyított
   saját diffjét, majd a közreműködői munkafolyamatnak megfelelően végezzen rebase-t, vagy merge-ölje az alapágat. A generált fájlokkal
   és katalógusokkal kapcsolatos ütközéseket a forrásuknál oldja fel, generálja újra őket, futtassa újra a célzott ciklust, és ellenőrizze, hogy a
   PR továbbra is az aktív kiadási ágat célozza.
6. **Rögzítse a bizonyítékokat.** A PR-sablonban sorolja fel a futtatott parancsokat, minden hozzáadott vagy módosított tesztfájlt,
   a migrációkat vagy funkciójelzőket, valamint minden olyan ellenőrzést, amely még csak a CI-ben vár futtatásra.

## Bevált útvonalak módosítástípusonként

Az alábbi parancsok a minimális célzott ellenőrzések; nem jelentenek engedélyt egy olyan teszt kihagyására, amely közvetlenül lefedi a
módosított viselkedést.

### Szolgáltató

**Szerződések**

- A szolgáltató definíciója a `src/shared/constants/providers/` alatt, valamint annak összeállítása a
  `src/shared/constants/providers.ts` fájlban.
- Modellek és képességek az `open-sse/config/providerRegistry.ts` fájlban vagy annak kiszervezett regisztrációs fájljaiban.
- Végrehajtó-/fordítóválasztás, OAuth- vagy API-kulcs-konfiguráció, irányítópult-erőforrások és adott esetben a generált
  szolgáltatói referencia.
- A nyilvános hitelesítő adatoknak a `resolvePublicCred()` függvényt kell használniuk; a hibaválaszoknak a közös, érzékeny adatokat eltávolító
  hibakezelő segédfüggvényeket kell használniuk. Lásd: `docs/security/PUBLIC_CREDS.md` (git; nincs belefordítva a `/docs` könyvtárba) és
  [Hibák megtisztítása](../security/ERROR_SANITIZATION.md).

**Célzott ciklus**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # amikor a katalógus módosul; commitolja a generált diffet
npm run lint
```

Minden érintett kéréstípust is teszteljen: chat, Responses, képek, beágyazások, hang vagy videó.
A generált katalógus- és golden diffeket szerződésmódosításként ellenőrizze; ne fogadja el őket vakon.

### Útválasztás

**Szerződések**

- Nyilvános stratégiaértékek és felhasználóifelület-metaadatok a `src/shared/constants/routingStrategies.ts` fájlban.
- Elküldés és sorrendezés az `open-sse/services/combo.ts` fájlban és az `open-sse/services/combo/` alatt.
- Combo-sémák, perzisztencia, rezilienciaállapot, modellképességek, valamint API- és felhasználóifelület-vezérlők.
- Az [Auto-Combo motor](../routing/AUTO-COMBO.md) és a rezilienciadokumentáció, ha a viselkedés módosul.

**Célzott ciklus**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # stratégia- vagy elküldési módosítások
npm run check:known-symbols      # a stratégia regisztrációjának módosításai
npm run lint
```

Helyben determinisztikus, szimulált upstreamet használó teszteket futtasson. Az élő combo-füsttesztekhez hitelesítő adatok szükségesek, és
manuálisak; nem helyettesítik a CI-t.

### UI / UX

**Szerződések**

- Next.js-útvonal/-oldal és megosztott komponenshatárok a `src/app/` és a
  `src/shared/components/` alatt.
- API-válaszformátumok, betöltési/üres/hibaállapotok, billentyűzetes és képernyőolvasós használat,
  reszponzív elrendezés, témakezelés és területi beállítások bővítése.
- Angol felhasználóifelület-forrásszövegek a `src/i18n/messages/en.json` fájlban; ne kódoljon be közvetlenül új, felhasználóknak szánt szöveget.

**Célzott ciklus**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interakciós vagy vizuális módosítások esetén futtassa az alkalmazást, és ellenőrizze keskeny és széles nézetablakban is. A CI futtatja az
éles buildet és a szélesebb körű tesztkészleteket; a vizuális viselkedéshez továbbra is szükség van a módosításnak megfelelő célzott komponens- vagy Playwright-tesztre,
illetve dokumentált manuális ellenőrzésre.

### i18n

**Szerződések**

- A `src/i18n/messages/en.json` a felhasználói felület forrása; a `config/i18n.json` a területi beállítások forrása.
- A CLI-katalógusok külön, a `bin/cli/locales/` alatt találhatók.
- Az ICU-helyőrzőket és -címkéket pontosan őrizze meg. Ne fordítsa le a termék-, szolgáltató- és modellneveket,
  a protokoll- és fejlécneveket, parancsokat, kód-/JSON-azonosítókat, URL-eket, környezeti változókat vagy
  védett kifejezéseket, például `OmniRoute`, `OAuth`, `MCP` és `A2A`. Az aktuális forráslista:
  `scripts/i18n/glossary/protected-terms.json`.

**Célzott ciklus**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # amikor a CLI-szövegek/-katalógusok módosulnak
npm run lint
```

Ez a meglévő rendszerhez készült útmutatás, nem pedig felhívás az eszközkészlet vagy a kulcsmodell bővítésére.
Tartsa célzottan szűken az i18n-javításokat, amíg a helyettesítő rendszer tervezése folyamatban van. Ne futtasson külső szolgáltatásokat
meghívó fordítási parancsokat, kivéve, ha a feladat kifejezetten generált fordításokat igényel, és
ellenőrizte az eredményül kapott diffet.

### CLI

**Szerződések**

- Nyilvános parancsok és kapcsolók a `bin/cli/` alatt, generált API-parancsok, kilépési kódok, stdout/stderr és
  JSON-kimeneti struktúrák, konfigurációs/környezeti működés, valamint a csomagolt fájlok.
- A CLI felhasználóknak szánt szövegeinek a CLI i18n-rétegét kell használniuk, az `en`/`pt-BR` katalógusokat pedig összhangban kell tartani.
- A Node maradjon a támogatott futtatókörnyezet, és őrizd meg a közzétett bináris szerződést.

**Célzott ciklus**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # generált/csomagolt CLI-módosítások
npm run check:pack-policy     # a csomag publikus felületének módosításai
npm run lint
```

Használd a pontos parancsot egy ideiglenes adatkönyvtárban, ha a működés az elemzéstől, fájloktól vagy a kilépési
állapottól függ. A CI végzi el a csomag artefaktumainak és az ökoszisztémának az átfogóbb ellenőrzéseit.

### Adatbázis

**Szerződések**

- Tartományi modulok a `src/lib/db/` alatt; a konkrét modulokat közvetlenül importáld (a régi `localDb.ts` újraexportálási réteget eltávolították).
- Számozott, idempotens SQL-migrációk a `src/lib/db/migrations/` alatt, tranzakcióbiztonság, frissítési
  működés, indexek, valamint a séma által érintett összes hívó.
- Az útvonalak és kezelők soha nem hajtanak végre közvetlenül nyers SQL-t.

**Célzott ciklus**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migráció hozzáadásakor tesztelj egy friss adatbázist és az előző sémáról történő frissítést is. Az adatbázisteszteknek
le kell zárniuk a fogantyúkat, és a tisztítás során meg kell hívniuk a `resetDbInstance()` függvényt. Az `npm run test:bun:db` parancsot csak
akkor futtasd, amikor a legjobb szándék szerint támogatott Bun-adapter útvonala módosul; továbbra is a Node a mérvadó.

### Build / telepítés

**Szerződések**

- Gyökér- és munkaterület-manifesztumok/zárolási fájl, `scripts/build/`, Next.js önálló összeállítás, a `dist/`
  csomag tartalma, Electron platformmetaadatok, CI-munkafolyamatok és telepítési jelzőfájlok.
- A támogatott Node-verziótartományoknak és a Bun `CLAUDE.md` fájlban engedélyezőlistán szereplő használatának változatlanul kell maradnia.
- A build-artefaktumok ne kerüljenek verziókövetés alá; a függőségekre, licencekre, munkafolyamatokra és csomagokra vonatkozó szabályzatok érvényesek.

**Célzott ciklus**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # függőség- vagy zárolásifájl-módosítások
npm run check:pack-policy      # a közzétett csomagfelület módosításai
npm run lint
```

Az `npm run build` parancsot helyben csak akkor használd, ha a módosítás érinti a fordítást, az önálló összeállítást, az eszközöket
vagy a futásidejű csomagolást. Az `npm run build:release` parancsot csak kiadási/telepítési ellenőrzéshez használd. A CI buildje
a végső, platformokon átívelő jelzés; a platformspecifikus Electron-módosításokhoz a megfelelő célzott build
vagy smoke tesztelési bizonyíték szükséges.

## Helyi ciklus kontra CI

| Futtasd helyben minden módosításhoz                                                                    | A CI biztosítja az átfogó visszajelzést                                                  |
| ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| A fenti közvetlen viselkedési tesztek és kategóriakorlátok                                             | Részekre osztott teljes egységtesztkészlet és soros tesztek                              |
| `npm run lint`                                                                                         | Vitest tesztkészletek és lefedettségi/minőségi küszöbök                                  |
| Típusellenőrzés vagy build csak akkor, ha az érintett szerződés ezt megköveteli                        | Éles build, biztonsági, dokumentációs, függőségi és PR-szabálykapuk                      |
| Manuális interakciós/élő ellenőrzések csak akkor, ha az automatizálás nem képes igazolni a viselkedést | A munkafolyamat által konfigurált, feladatok közötti integrációs és platformellenőrzések |

A sikeres célzott ciklus bizonyíték a módosított szerződés helyességére, nem pedig garancia arra, hogy a nem kapcsolódó CI-ellenőrzések
is sikeresek lesznek. Ugyanakkor ne várakoztass minden helyi módosítást a teljes adattár-mátrix lefutására.

## Egyeztetési ellenőrzőlista

Felülvizsgálat kérése előtt:

- Győződj meg arról, hogy a PR alapága továbbra is a legmagasabb verziójú aktív `release/v*` ág.
- Töltsd le ezt az alapágat, és tekintsd át az elágazásod óta bekerült commitokat.
- Vizsgáld át a `git diff <active-base>...HEAD` kimenetét a véletlen vagy generált változások kiszűréséhez.
- A katalógus- és generált dokumentumütközéseket a forrás frissítésével és a kimenet újbóli generálásával oldd fel.
- Az egyeztetés után futtasd újra a PR leírásában felsorolt összes célzott tesztet/kaput.
- Soha ne gyengítsd az elvárásokat, és ne hagyj el kötelező teszteket pusztán azért, hogy igazodj egy módosult alapághoz.

A kiadás előtti kódbefagyasztás és az alapág módosításának szabályaihoz lásd:
[Elágazási és kiadási modell](BRANCHING_MODEL.md). A CI-ellenőrzések teljes listájához lásd:
[Minőségi kapuk referenciája](../architecture/QUALITY_GATES.md).
