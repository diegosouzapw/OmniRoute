Use este guia para escolher o menor ciclo de desenvolvimento confiável para uma pull request. Ele não
substitui os documentos de arquitetura e segurança específicos de cada área vinculados abaixo; ele conecta cada tipo
comum de alteração aos seus contratos, verificações focadas e cobertura de CI.

## O caminho seguido por toda alteração

1. **Escolha a base antes de editar.** Encontre a branch `release/v*` ativa mais recente e crie sua branch a partir
   da ponta dela. Direcione a pull request para essa branch, não para `main`. Se houver um congelamento de release ativo, não use a branch
   congelada como destino; use o próximo ciclo ativo descrito em
   [Modelo de branches e releases](BRANCHING_MODEL.md).
2. **Identifique os contratos.** Identifique cada catálogo, esquema, artefato gerado, API pública ou interface de
   usuário afetado pela alteração. A tabela abaixo apresenta o conjunto inicial mínimo.
3. **Escreva ou atualize testes focados.** Alterações de produção em `src/`, `open-sse/`, `electron/` ou
   `bin/` exigem um teste automatizado na mesma PR. Execute os menores arquivos de teste que comprovem o
   comportamento e, em seguida, as verificações focadas listadas.
4. **Deixe a CI executar a matriz ampla.** Os shards completos de testes unitários, o Vitest, o limite progressivo de cobertura e o
   build de produção são executados na PR. Execute uma suíte ampla localmente somente quando uma falha focada indicar
   um impacto mais abrangente ou quando a alteração abranger vários subsistemas.
5. **Reconcilie antes da revisão.** Busque a base ativa, inspecione os novos commits dela e seu diff em relação
   a ela e, então, faça rebase ou merge da base de acordo com o fluxo de trabalho dos contribuidores. Resolva conflitos de arquivos
   gerados e de catálogos a partir de sua fonte, gere-os novamente, execute outra vez o ciclo focado e confirme que a
   PR ainda aponta para a branch de release ativa.
6. **Registre as evidências.** No template da PR, liste os comandos executados, cada arquivo de teste adicionado ou alterado,
   migrações ou feature flags e qualquer validação exclusiva da CI que ainda esteja pendente.

## Fluxos ideais por tipo de alteração

Os comandos abaixo são verificações focadas mínimas, não uma permissão para ignorar um teste que cubra diretamente o
comportamento alterado.

### Provedor

**Contratos**

- Definição do provedor em `src/shared/constants/providers/` e sua composição em
  `src/shared/constants/providers.ts`.
- Modelos e capacidades em `open-sse/config/providerRegistry.ts` ou nos arquivos de registro extraídos.
- Seleção de executor/tradutor, configuração de OAuth ou chave de API, assets do dashboard e referência
  gerada do provedor, quando aplicável.
- Credenciais públicas devem usar `resolvePublicCred()`; respostas de erro devem usar os helpers compartilhados de
  sanitização de erros. Consulte `docs/security/PUBLIC_CREDS.md` (git; não compilado em `/docs`) e
  [Sanitização de erros](../security/ERROR_SANITIZATION.md).

**Ciclo focado**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # quando o catálogo mudar; faça commit do diff gerado
npm run lint
```

Teste também cada família de requisições afetada: chat, Responses, imagens, embeddings, áudio ou vídeo.
Revise os diffs gerados de catálogo e golden como alterações de contrato; não os aceite cegamente.

### Roteamento

**Contratos**

- Valores públicos das estratégias e metadados da UI em `src/shared/constants/routingStrategies.ts`.
- Despacho e ordenação em `open-sse/services/combo.ts` e `open-sse/services/combo/`.
- Esquemas de combo, persistência, estado de resiliência, capacidades dos modelos e controles de API/UI.
- [Mecanismo Auto-Combo](../routing/AUTO-COMBO.md) e documentação de resiliência quando o comportamento mudar.

**Ciclo focado**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # alterações de estratégia ou despacho
npm run check:known-symbols      # alterações no registro de estratégias
npm run lint
```

Use testes determinísticos com upstream simulado localmente. Testes rápidos de combo em ambiente real exigem credenciais e são
manuais, não substitutos da CI.

### UI / UX

**Contratos**

- Rota/página do Next.js e limites dos componentes compartilhados em `src/app/` e
  `src/shared/components/`.
- Formatos das respostas da API, estados de carregamento/vazio/erro, comportamento para teclado e leitores de tela,
  layout responsivo, temas e expansão de localidades.
- Strings-fonte em inglês da UI em `src/i18n/messages/en.json`; não codifique diretamente novos textos voltados ao usuário.

**Ciclo focado**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Execute o aplicativo para alterações visuais ou de interação e verifique viewports estreitos e largos. A CI executa o
build de produção e suítes mais amplas; o comportamento visual ainda precisa de um componente focado, Playwright
ou verificação manual documentada apropriada para a alteração.

### i18n

**Contratos**

- `src/i18n/messages/en.json` é a fonte da UI; `config/i18n.json` é a fonte das localidades.
- Os catálogos da CLI ficam separadamente em `bin/cli/locales/`.
- Preserve exatamente os placeholders e as tags ICU. Não traduza nomes de produtos/provedores/modelos,
  nomes de protocolos e cabeçalhos, comandos, identificadores de código/JSON, URLs, variáveis de ambiente ou
  termos protegidos, como `OmniRoute`, `OAuth`, `MCP` e `A2A`. A lista-fonte atual é
  `scripts/i18n/glossary/protected-terms.json`.

**Ciclo focado**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # quando strings/catálogos da CLI mudarem
npm run lint
```

Esta é uma orientação para o sistema existente, não um convite para expandir suas ferramentas ou seu modelo de chaves.
Mantenha os patches de i18n cirúrgicos enquanto o sistema substituto está sendo projetado. Não execute comandos de tradução
que chamem serviços externos, a menos que a tarefa exija explicitamente traduções geradas e
você tenha revisado o diff resultante.

### CLI

**Contratos**

- Comandos e flags públicos em `bin/cli/`, comandos de API gerados, códigos de saída, stdout/stderr e
  formatos de saída JSON, comportamento de configuração/ambiente e arquivos incluídos no pacote.
- Strings da CLI voltadas ao usuário devem usar a camada de i18n da CLI e manter os catálogos `en`/`pt-BR` alinhados.
- Preserve o Node como o runtime compatível e o contrato do binário publicado.

**Ciclo focado**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # alterações geradas/empacotadas da CLI
npm run check:pack-policy     # alterações na superfície do pacote
npm run lint
```

Use o comando exato em um diretório de dados temporário quando o comportamento depender de análise sintática, arquivos ou status
de saída. A CI executa verificações mais abrangentes dos artefatos do pacote e do ecossistema.

### Banco de dados

**Contratos**

- Módulos de domínio em `src/lib/db/`; importe módulos específicos diretamente (a antiga camada de reexportação `localDb.ts` foi removida).
- Migrações SQL numeradas e idempotentes em `src/lib/db/migrations/`, segurança de transações, comportamento
  de atualização, índices e todos os chamadores afetados pelo esquema.
- Rotas e manipuladores nunca executam SQL bruto diretamente.

**Ciclo focado**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Ao adicionar uma migração, teste tanto um banco de dados novo quanto a atualização a partir do esquema anterior. Os testes de banco de dados
devem fechar os handles e chamar `resetDbInstance()` durante a limpeza. Execute `npm run test:bun:db` somente quando
o caminho do adaptador Bun de melhor esforço for alterado; o Node continua sendo a referência oficial.

### Build / implantação

**Contratos**

- Manifestos/lockfile da raiz e dos workspaces, `scripts/build/`, montagem standalone do Next.js, conteúdo do pacote
  `dist/`, metadados de plataforma do Electron, workflows de CI e sentinelas de implantação.
- Os intervalos de versões compatíveis do Node e o uso permitido do Bun em `CLAUDE.md` devem permanecer intactos.
- Artefatos de build permanecem sem rastreamento; aplicam-se as políticas de dependências, licenças, workflows e pacotes.

**Ciclo focado**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # alterações em dependências ou no lockfile
npm run check:pack-policy      # alterações na superfície do pacote publicado
npm run lint
```

Use `npm run build` localmente somente quando a alteração afetar a compilação, a montagem standalone, os assets
ou o empacotamento em runtime. Use `npm run build:release` somente para validação de release/implantação. O build da CI é
o sinal multiplataforma final; alterações específicas de plataforma no Electron exigem o build focado correspondente
ou evidências de smoke test.

## Ciclo local versus CI

| Executar localmente para cada patch                                                                          | A CI fornece o sinal abrangente                                                             |
| ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| Testes diretos de comportamento e verificações de categoria acima                                            | Suíte completa de testes unitários em shards e testes seriais                               |
| `npm run lint`                                                                                               | Suítes do Vitest e mecanismos de aumento gradual de cobertura/qualidade                     |
| Verificação de tipos ou build somente quando o contrato afetado exigir                                       | Build de produção e verificações de segurança, documentação, dependências e políticas de PR |
| Interações manuais/verificações em tempo real somente quando a automação não puder comprovar o comportamento | Verificações de integração entre jobs e de plataforma configuradas pelo workflow            |

Um ciclo focado bem-sucedido é uma evidência sobre o contrato alterado, não uma prova de que verificações de CI não relacionadas
serão aprovadas. Por outro lado, não faça cada edição local aguardar toda a matriz do repositório.

## Checklist de reconciliação

Antes de solicitar revisão:

- Confirme se a base do PR ainda é a branch `release/v*` ativa mais recente.
- Faça fetch dessa base e revise os commits incorporados desde que você criou sua branch.
- Revise `git diff <active-base>...HEAD` para identificar alterações acidentais ou geradas.
- Resolva conflitos de catálogo e de documentos gerados atualizando a fonte e gerando novamente a saída.
- Execute novamente todos os testes/verificações focados listados na descrição do PR após a reconciliação.
- Nunca enfraqueça as asserções nem remova testes obrigatórios apenas para se adequar a uma base que mudou.

Para regras de congelamento de release e redirecionamento de destino, consulte
[Modelo de Branches e Releases](BRANCHING_MODEL.md). Para o inventário completo da CI, consulte
[Referência de Verificações de Qualidade](../architecture/QUALITY_GATES.md).
