Use este guia para escolher o menor ciclo de desenvolvimento confiável para um pull request. Ele não
substitui os documentos de arquitetura e segurança específicos de cada área vinculados abaixo; ele conecta cada tipo
comum de alteração a seus contratos, verificações direcionadas e cobertura de CI.

## O caminho seguido por cada alteração

1. **Escolha a base antes de editar.** Encontre a branch `release/v*` ativa mais recente e crie sua branch a partir
   da ponta dela. Use essa branch como destino, não `main`. Se um congelamento de release estiver ativo, não use a branch
   congelada como destino; use o próximo ciclo ativo descrito em
   [Modelo de Branches e Releases](BRANCHING_MODEL.md).
2. **Identifique os contratos.** Identifique cada catálogo, esquema, artefato gerado, API pública ou interface
   de usuário afetado pela alteração. A tabela abaixo apresenta o conjunto inicial mínimo.
3. **Escreva ou atualize testes direcionados.** Alterações de produção em `src/`, `open-sse/`, `electron/` ou
   `bin/` exigem um teste automatizado no mesmo PR. Execute os menores arquivos de teste que comprovem o
   comportamento e, depois, as verificações direcionadas listadas.
4. **Deixe o CI executar a matriz ampla.** Os shards completos de testes unitários, Vitest, ajuste progressivo da cobertura e
   build de produção são executados no PR. Execute uma suíte ampla localmente apenas quando uma falha direcionada indicar
   um impacto mais abrangente ou quando a alteração envolver vários subsistemas.
5. **Reconcilie antes da revisão.** Faça fetch da base ativa, inspecione os novos commits dela e seu diff em relação
   a ela e, depois, faça rebase ou merge da base de acordo com o fluxo de trabalho do colaborador. Resolva conflitos de arquivos
   gerados e catálogos a partir de suas fontes, gere-os novamente, execute novamente o ciclo direcionado e confirme que o
   PR ainda tem como destino a branch de release ativa.
6. **Registre as evidências.** No template do PR, liste os comandos executados, cada arquivo de teste adicionado ou alterado,
   migrações ou feature flags e qualquer validação exclusiva de CI ainda pendente.

## Caminhos recomendados por tipo de alteração

Os comandos abaixo são verificações direcionadas mínimas, não uma permissão para ignorar um teste que cubra diretamente o
comportamento alterado.

### Provedor

**Contratos**

- Definição do provedor em `src/shared/constants/providers/` e sua composição em
  `src/shared/constants/providers.ts`.
- Modelos e recursos em `open-sse/config/providerRegistry.ts` ou nos arquivos de registro extraídos dele.
- Seleção de executor/tradutor, configuração de OAuth ou chave de API, recursos do dashboard e referência
  gerada do provedor, quando aplicável.
- Credenciais públicas devem usar `resolvePublicCred()`; respostas de erro devem usar os helpers compartilhados de
  sanitização de erros. Consulte `docs/security/PUBLIC_CREDS.md` (git; não compilado em `/docs`) e
  [Sanitização de Erros](../security/ERROR_SANITIZATION.md).

**Ciclo direcionado**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # quando o catálogo for alterado; faça commit do diff gerado
npm run lint
```

Teste também cada família de solicitações afetada: chat, Responses, imagens, embeddings, áudio ou vídeo.
Revise os diffs do catálogo gerado e dos testes golden como alterações de contrato; não os aceite cegamente.

### Roteamento

**Contratos**

- Valores públicos de estratégia e metadados de UI em `src/shared/constants/routingStrategies.ts`.
- Despacho e ordenação em `open-sse/services/combo.ts` e `open-sse/services/combo/`.
- Esquemas de combo, persistência, estado de resiliência, recursos do modelo e controles de API/UI.
- [Mecanismo Auto-Combo](../routing/AUTO-COMBO.md) e documentação de resiliência quando o comportamento for alterado.

**Ciclo direcionado**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # alterações de estratégia ou despacho
npm run check:known-symbols      # alterações no registro de estratégias
npm run lint
```

Use localmente testes determinísticos com upstreams simulados. Testes rápidos de combo em ambiente real exigem credenciais e são
manuais, não substitutos do CI.

### UI / UX

**Contratos**

- Limites de rota/página do Next.js e de componentes compartilhados em `src/app/` e
  `src/shared/components/`.
- Formatos de resposta da API, estados de carregamento/vazio/erro, comportamento de teclado e leitor de tela,
  layout responsivo, temas e expansão de localidades.
- Strings de origem da UI em inglês em `src/i18n/messages/en.json`; não codifique diretamente novos textos voltados ao usuário.

**Ciclo direcionado**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Execute o aplicativo para alterações visuais ou de interação e verifique tanto viewports estreitos quanto amplos. O CI executa o
build de produção e suítes mais abrangentes; o comportamento visual ainda precisa de um teste direcionado de componente, Playwright
ou uma verificação manual documentada apropriada à alteração.

### i18n

**Contratos**

- `src/i18n/messages/en.json` é a fonte da UI; `config/i18n.json` é a fonte das localidades.
- Os catálogos da CLI ficam separadamente em `bin/cli/locales/`.
- Preserve exatamente os placeholders e as tags ICU. Não traduza nomes de produtos/provedores/modelos,
  nomes de protocolos e cabeçalhos, comandos, identificadores de código/JSON, URLs, variáveis de ambiente ou
  termos protegidos como `OmniRoute`, `OAuth`, `MCP` e `A2A`. A lista de origem atual está em
  `scripts/i18n/glossary/protected-terms.json`.

**Ciclo direcionado**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # quando strings/catálogos da CLI forem alterados
npm run lint
```

Estas são orientações para o sistema existente, não um convite para expandir suas ferramentas ou seu modelo de chaves.
Mantenha os patches de i18n cirúrgicos enquanto o sistema substituto estiver sendo projetado. Não execute comandos de tradução
que chamem serviços externos, a menos que a tarefa exija explicitamente traduções geradas e que você
tenha revisado o diff resultante.

### CLI

**Contratos**

- Comandos públicos e flags em `bin/cli/`, comandos de API gerados, códigos de saída, stdout/stderr e
  formatos de saída JSON, comportamento de configuração/ambiente e arquivos empacotados.
- As strings da CLI voltadas ao usuário devem usar a camada de i18n da CLI e manter os catálogos `en`/`pt-BR` alinhados.
- Preserve o Node como o runtime compatível e o contrato do binário publicado.

**Ciclo focado**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # alterações na CLI gerada/empacotada
npm run check:pack-policy     # alterações na superfície do pacote
npm run lint
```

Use o comando exato em um diretório temporário de dados quando o comportamento depender de análise sintática, arquivos ou status de
saída. A CI executa as verificações mais abrangentes de artefatos de pacote e ecossistema.

### Banco de dados

**Contratos**

- Módulos de domínio em `src/lib/db/`; importe módulos específicos diretamente (a antiga camada de reexportação `localDb.ts` foi removida).
- Migrações SQL numeradas e idempotentes em `src/lib/db/migrations/`, segurança de transações, comportamento de
  atualização, índices e todos os chamadores afetados pelo esquema.
- Rotas e manipuladores nunca executam SQL bruto diretamente.

**Ciclo focado**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Ao adicionar uma migração, teste tanto um banco de dados novo quanto a atualização a partir do esquema anterior. Os testes de banco de dados
devem fechar os identificadores e chamar `resetDbInstance()` durante a limpeza. Execute `npm run test:bun:db` somente quando
o caminho do adaptador Bun de melhor esforço mudar; o Node continua sendo a referência.

### Build / implantação

**Contratos**

- Manifestos/lockfile da raiz e dos workspaces, `scripts/build/`, montagem standalone do Next.js, conteúdo do pacote
  `dist/`, metadados de plataforma do Electron, fluxos de trabalho de CI e sentinelas de implantação.
- Os intervalos de versões compatíveis do Node e o uso permitido do Bun em `CLAUDE.md` devem permanecer intactos.
- Os artefatos de build permanecem não rastreados; as políticas de dependências, licenças, fluxos de trabalho e pacotes se aplicam.

**Ciclo focado**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # alterações em dependências ou no lockfile
npm run check:pack-policy      # alterações na superfície do pacote publicado
npm run lint
```

Use `npm run build` localmente somente quando a alteração afetar a compilação, a montagem standalone, os assets
ou o empacotamento em runtime. Use `npm run build:release` somente para validação de release/implantação. O build da CI é
o sinal final entre plataformas; alterações específicas de plataforma do Electron precisam do build focado correspondente
ou de evidências de smoke test.

## Loop local de candidatos

Os testes do código-fonte não podem comprovar que o artefato empacotado inicializa: listas de empacotamento, dependências removidas e binários nativos só apresentam falhas depois que o tarball é instalado e iniciado. `npm run dev:candidate` (`scripts/dev/candidate.mjs`) é a parte local do fluxo compilar uma vez / validar / promover da RFC #8084: ele compila um candidato, valida exatamente esse artefato, promove-o por meio de renomeações de diretórios e o reverte quando o slot promovido falha na verificação de integridade.

```bash
npm run dev:candidate -- run --dry-run --json  # exibe o plano, sem alterar nada
npm run dev:candidate -- run                   # compila + valida + promove, com reversão automática
npm run dev:candidate -- build                 # executa npm pack + instala em _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # inicializa em uma porta livre, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # troca current e previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # reutiliza um tarball compilado em outro lugar (CI)
```

- **Compile uma vez.** `build` empacota a árvore atual (ele precisa de `dist/server.js`, portanto execute `npm run build:release` primeiro) ou copia `--from-tarball` e, em seguida, instala o tarball em um prefixo npm isolado, pois o tarball não contém `node_modules`. O id é o sha curto de `HEAD` (`-dirty` quando a árvore contém alterações locais) ou `tgz-<sha256>` para um tarball. Um id limpo que já tenha sido compilado é reutilizado em vez de recompilado; use `--force` para recompilá-lo.
- **Valide o pacote, não o código-fonte.** `validate` inicia a CLI instalada (`serve --port <free port>`) com um novo `DATA_DIR=<candidate>/data`, segredos falsos e as variáveis `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` e `INITIAL_PASSWORD` do operador removidas do ambiente, verificando assim a configuração de loopback sem chave de uma instalação nova. Ele aguarda até que `GET /api/health` retorne 200, exige que `GET /v1/models` retorne 200, encerra o grupo de processos e registra o veredito em `validation.json` junto com o hash do tarball.
- **Promova o mesmo artefato.** `promote` rejeita um candidato que não tenha uma validação bem-sucedida para o hash atual de seu tarball. O slot ativo padrão é `_artifacts/candidate/current`; `--target <dir>` seleciona outro diretório no mesmo sistema de arquivos, e seu slot anterior é `<dir>.previous`. Cada renomeação é atômica, e uma falha durante o processo reverte as renomeações que já foram executadas.
- **Reverta.** `run` valida novamente o slot promovido e troca `current` e `previous` de volta quando essa verificação falha. Um candidato que falha na primeira validação nunca é promovido.

Tudo é gravado em `_artifacts/candidate/`, que é ignorado pelo git; uma instalação existente do OmniRoute e seu diretório de dados nunca são alterados. A CLI promovida fica em `_artifacts/candidate/current/prefix/bin/omniroute`; ao usá-la, inicie-a com seu próprio `DATA_DIR`. Códigos de saída: `0` para sucesso, `1` para falha na validação ou promoção, `2` para erro de uso ou compilação ausente.

## Ciclo local versus CI

| Execute localmente para cada patch                                                                     | A CI fornece o sinal abrangente                                                             |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| Testes diretos de comportamento e verificações de categoria acima                                      | Suíte completa de testes unitários em shards e testes seriais                               |
| `npm run lint`                                                                                         | Suítes do Vitest e controles progressivos de cobertura/qualidade                            |
| Verificação de tipos ou build somente quando o contrato afetado exigir                                 | Build de produção e verificações de segurança, documentação, dependências e políticas de PR |
| Interações manuais/verificações ao vivo somente quando a automação não puder comprovar o comportamento | Verificações de integração entre jobs e de plataformas configuradas pelo workflow           |

Um ciclo focado bem-sucedido é uma evidência sobre o contrato alterado, não uma prova de que verificações de CI não relacionadas
serão aprovadas. Por outro lado, não faça com que cada edição local aguarde toda a matriz do repositório.

## Checklist de reconciliação

Antes de solicitar revisão:

- Confirme se a base do PR ainda é a branch `release/v*` ativa mais recente.
- Faça fetch dessa base e revise os commits incorporados desde que você criou sua branch.
- Revise `git diff <active-base>...HEAD` em busca de alterações acidentais ou geradas.
- Resolva conflitos de catálogo e de documentos gerados atualizando a fonte e gerando novamente a saída.
- Execute novamente todos os testes/verificações focados listados na descrição do PR após a reconciliação.
- Nunca enfraqueça as asserções nem remova testes obrigatórios apenas para corresponder a uma base alterada.

Para as regras de congelamento de release e redirecionamento de base, consulte
[Modelo de Branching e Release](BRANCHING_MODEL.md). Para obter o inventário completo da CI, consulte
[Referência de Verificações de Qualidade](../architecture/QUALITY_GATES.md).
