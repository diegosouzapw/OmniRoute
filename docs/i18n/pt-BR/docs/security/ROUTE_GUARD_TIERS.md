## Visão geral

Todas as rotas da API de gerenciamento do OmniRoute são classificadas em um dos três níveis de proteção. A classificação é estática, definida em `src/server/authz/routeGuard.ts`, e avaliada antes da execução de qualquer outro fluxo de autenticação.

## Níveis

### Nível 1 — LOCAL_ONLY

**Imposto por:** `isLocalOnlyPath(path)` → verificação de host de loopback  
**Contorno:** nenhum por padrão. Há uma exceção restrita para caminhos em `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` quando a solicitação contém uma chave de API válida com o escopo `manage` (consulte [Exceção do escopo de gerenciamento](#manage-scope-carve-out)).

Essas rotas iniciam processos filhos ou executam código em tempo de execução. Expô-las a tráfego que não seja de loopback permitiria que um invasor que obtivesse um JWT válido (por exemplo, por meio de um túnel Cloudflared/Ngrok) acionasse a criação de processos — uma classe conhecida de CVE ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**O que é a GHSA-fhh6-4qxv-rpqj (a classe de ataque):** um servidor de gerenciamento/agente expõe um endpoint que inicia um subprocesso (`npm install`, `node`, um navegador, um proxy, `git`, `tar`, …). Se esse endpoint puder ser acessado externamente ao host — porque o operador colocou o OmniRoute atrás de um túnel nginx/Cloudflare/Tailscale e um JWT vazou, ou porque a autenticação foi configurada incorretamente — o invasor transforma “chamar uma API” em “executar um comando no host” (execução remota de código). O OmniRoute impede isso aplicando uma **verificação de host de loopback incondicionalmente, antes de qualquer verificação de autenticação**, em todas as rotas capazes de iniciar processos: um token vazado por meio de um túnel ainda não consegue acessar o mecanismo de criação de processos.

**O conjunto LOCAL_ONLY completo.** A fonte oficial é `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` em `src/server/authz/routeGuard.ts`; a tabela abaixo reflete o estado atual. A verificação `check-route-guard-membership` enumera todos os arquivos `route.ts` sob os prefixos capazes de iniciar processos e faz com que a CI falhe se algum deles não estiver classificado como somente local.

#### Exceção para o escopo de gerenciamento

Um subconjunto dos caminhos LOCAL_ONLY TAMBÉM PODE ser acessado fora do loopback se, e
somente se, a solicitação incluir um `Authorization: Bearer <api-key>` cujos
metadados incluam o escopo `manage` (ou `admin`). A exceção é habilitada
explicitamente por caminho por meio de `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, para que o
padrão de qualquer novo caminho LOCAL_ONLY permaneça restrito ao loopback. Solicitações não
autenticadas e solicitações com chaves sem o escopo de gerenciamento continuam sendo rejeitadas com
`403 LOCAL_ONLY`.

Atualmente, o único prefixo que permite a exceção é `/api/mcp/`. `/api/cli-tools/runtime/` e
`/api/services/` são intencionalmente excluídos porque podem iniciar subprocessos
arbitrários (`npm install`, `node`), que correspondem exatamente à classe de CVE que a
camada LOCAL_ONLY existe para impedir.

**#7895 — escopo restrito `mcp:connect`:** a exceção de `/api/mcp/` TAMBÉM aceita
uma chave Bearer que tenha o escopo restrito `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), verificado por meio de
`hasMcpConnectOrManageScope()` em `src/server/authz/policies/management.ts`.
Isso se aplica SOMENTE a `/api/mcp/` — `mcp:connect` não concede nada em nenhuma outra
rota de gerenciamento (incluindo qualquer outro prefixo de exceção LOCAL_ONLY, caso algum
venha a ser adicionado), e é deliberadamente excluído de
`MANAGEMENT_API_KEY_SCOPES`. Uma chave com `manage`/`admin` ainda passa pela
exceção exatamente como antes; `mcp:connect` é uma alternativa de menor privilégio
para clientes MCP remotos que não precisam de acesso amplo de gerenciamento.

| Solicitação                                         | Caminho                    | Resultado                       |
| --------------------------------------------------- | -------------------------- | ------------------------------- |
| Fora do loopback, sem Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY                  |
| Fora do loopback, Bearer com escopo `manage`        | `/api/mcp/*`               | Permitir                        |
| Fora do loopback, Bearer com escopo `mcp:connect`   | `/api/mcp/*`               | Permitir                        |
| Fora do loopback, Bearer sem `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                  |
| Fora do loopback, Bearer com escopo `mcp:connect`   | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                  |
| Fora do loopback, Bearer com escopo `manage`        | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                  |
| Loopback, com qualquer Bearer ou sem Bearer         | qualquer LOCAL_ONLY        | Permitir (verificação aprovada) |

#### Orientações para operadores e auditoria

Se você executar o OmniRoute por trás de um proxy reverso ou túnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), a verificação de loopback ainda protegerá as rotas acima
capazes de iniciar processos — uma solicitação cujo endereço do cliente não seja de loopback será rejeitada com
`403 LOCAL_ONLY` **antes da execução da autenticação**, portanto, um JWT vazado não conseguirá iniciar
um processo. Permanecem duas responsabilidades para o operador:

- **Não "corrija" um erro 403 falsificando o IP do cliente como loopback.** Definir
  `X-Forwarded-For: 127.0.0.1` ou usar um proxy que reescreva o endereço de origem como
  loopback reabre exatamente a classe de RCE que esta camada elimina. Exponha o
  painel/API por meio do proxy — nunca as rotas capazes de iniciar processos.
- **Mantenha a exceção do escopo de gerenciamento mínima.** Somente `/api/mcp/` permite a exceção, e
  somente com uma chave de API com escopo `manage`. Os `SPAWN_CAPABLE_PREFIXES` nunca podem ser
  adicionados à lista de exceções — o esquema zod os rejeita e
  `isLocalOnlyBypassableByManageScope` os nega em tempo de execução (defesa em profundidade),
  que é o que o painel quer dizer com "não pode permitir exceção". As rotas capazes de
  iniciar processos com segmentos dinâmicos e caminhos estáticos em `/api/providers/` (por exemplo, `/login`,
  `/refresh-cursor`) são abrangidas pelos elementos complementares baseados em regex
  `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` em
  `src/shared/constants/spawnCapablePrefixes.ts`, e não pelo array simples
  `SPAWN_CAPABLE_PREFIXES` — o array simples teria de abranger todo o
  prefixo `/api/providers/` para capturá-las, ampliando excessivamente uma árvore de rotas
  que painéis remotos usam legitimamente para operações CRUD de provedores.

**Auditoria de acesso** — para verificar se nada fora do host está acessando essas rotas:

- Abra o **Inventário de Autorizações** em `/dashboard/settings/security`: ele exibe a
  lista ativa de prefixos LOCAL_ONLY, quais prefixos podem ser contornados e o conjunto
  com capacidade de criar processos definido em tempo de compilação ("não pode ser contornado").
- Pesquise nos logs do proxy reverso / de acesso os prefixos acima associados a um
  endereço de cliente que não seja de loopback. Qualquer ocorrência que tenha retornado `200` em vez de
  `403 LOCAL_ONLY` significa que o proxy está mascarando o IP real do cliente — corrija o proxy.
- Um `403 LOCAL_ONLY` nos logs do OmniRoute para um desses caminhos significa que a proteção
  está funcionando conforme o esperado, e não é um erro que deva ser suprimido.

### Nível 2 — ALWAYS_PROTECTED

**Imposto por:** `isAlwaysProtectedPath(path)` → ignora o contorno por `requireLogin=false`
**Contorno:** nenhum quando `requireLogin=false`; JWT é sempre obrigatório

Essas rotas são destrutivas ou irreversíveis. Permiti-las em uma instalação "sem senha"
significaria que qualquer pessoa na mesma LAN poderia apagar o banco de dados ou encerrar o
processo do servidor.

| Caminho                                   | Motivo                                                            |
| ----------------------------------------- | ----------------------------------------------------------------- |
| `/api/shutdown`                           | Encerra o processo do servidor                                    |
| `/api/settings/database`                  | Exportação, importação e exclusão do banco de dados               |
| `/api/db-backups`                         | Acesso ao arquivo de backup completo do banco de dados            |
| `/api/settings/export-json`               | Exporta o blob completo de configurações (incl. segredos)         |
| `/api/settings/import-json`               | Substitui o blob completo de configurações                        |
| `/api/providers/health-autopilot/actions` | Executa ações de correção do piloto automático                    |
| `/api/settings/obsidian`                  | Gera credenciais WebDAV reutilizáveis para qualquer raiz de cofre |

**Resposta em caso de violação:** `401 Authentication required`

`/api/settings/obsidian` abrange seu filho `/webdav`: `POST` direciona o serviço de arquivos WebDAV —
servido pela camada Node personalizada antes do Next.js, fora deste pipeline — para uma raiz
escolhida pelo chamador e retorna credenciais Basic recém-geradas, `DELETE` as rotaciona, e o `POST`
do pai armazena o token da API REST do Obsidian. O GHSA-62vw apenas ocultou a revelação da senha
por `GET`; a emissão ainda estava no nível que permite acesso em caso de falha (GHSA-7pq4-8pvv-rx7r).
`enableObsidianVaultSync()` também recusa um cofre que seja o diretório de dados, esteja dentro dele
ou o contenha.

### A inicialização de uma nova instalação é restrita ao loopback — pelo par real, não pelo `Host`

Quando nenhuma senha de gerenciamento está configurada (e não há `INITIAL_PASSWORD`), `isAuthRequired()` em
`src/shared/utils/apiAuth.ts` mantém a inicialização anônima aberta **somente para pares de loopback**.
O loopback é determinado pelos sinais confiáveis do par, nesta ordem: o par TCP real marcado por token
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, o que a política vê), o veredito
`AUTHZ_HEADER_PEER_LOCALITY` do próprio pipeline (o que os manipuladores de rota veem, considerado
confiável somente enquanto `OMNIROUTE_PEER_STAMP_TOKEN` estiver definido) ou um par de soquete real
para chamadores diretos. `Host` / `nextUrl.hostname` nunca são consultados, e a definição da primeira
senha (`POST /api/settings/require-login`) está sujeita à mesma restrição, em vez de ficar aberta a
todos os pares da rede (GHSA-7pq4-8pvv-rx7r). `managementPolicy` transmite explicitamente seu próprio
veredito de `peerContext`, de modo que os cabeçalhos da solicitação ORIGINAL (antes da remoção) nunca
o determinem.

### Nível 3 — MANAGEMENT (padrão)

Todas as outras rotas de gerenciamento. A autenticação é obrigatória, a menos que
`requireLogin=false` esteja configurado. Tokens da CLI podem autenticar essas rotas
(loopback + HMAC válido).

## Ordem de avaliação

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → prosseguir
     → não loopback, Bearer com escopo manage
        E isLocalOnlyBypassableByManageScope     → permitir (management_key)
     → caso contrário                            → rejeitar com 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → permitir (system)
  3. hasValidCliToken(headers)?
     → permitir (cli) [loopback + verificação HMAC com timingSafeEqual]
  4. isAlwaysProtectedPath(path) ou requireLogin=true?
     → isDashboardSessionAuthenticated?
        → permitir (dashboard_session)
     → Bearer com escopo manage em um caminho não contornável?
        → permitir (management_key)
     → rejeitar com 401/403
  5. requireLogin=false?
     → permitir (anonymous)
```

A ramificação de escopo manage da etapa 1 é o único caminho autenticado que pode atender a uma rota
LOCAL_ONLY; o modo de falha do backend de autenticação retorna 503 (não 403), para que um
banco de dados expirado não seja silenciosamente rebaixado para "negar".

## Adicionando uma nova rota capaz de iniciar processos

1. Adicione o prefixo do caminho a `LOCAL_ONLY_API_PREFIXES` em
   `src/server/authz/routeGuard.ts`
2. Adicione um teste em `tests/unit/authz/routeGuard.test.ts` verificando que
   `isLocalOnlyPath()` retorna true para o novo prefixo
3. **Nunca pule esta etapa** — consulte a Regra Rígida nº 15 em `CLAUDE.md`
4. Decida: esta rota TAMBÉM deve pertencer a `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   A resposta padrão é **não**. Habilite-a somente quando a rota for segura para exposição a um
   portador do escopo manage (ou seja, quando NÃO iniciar código arbitrário controlado pelo usuário).

## Adicionando um caminho contornável pelo escopo manage

1. Confirme que a rota não executa código nem comandos fornecidos pelo usuário. Se
   executar, pare — esta exceção não é a ferramenta adequada.
2. Adicione o prefixo a `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` em
   `src/server/authz/routeGuard.ts`
3. Adicione cobertura em `tests/unit/authz/management-policy.test.ts` para os quatro
   formatos de requisição: sem Bearer (403), Bearer manage (permitir), Bearer não manage
   (403) e a regressão por prefixo que garante que `/api/cli-tools/runtime/*` permaneça
   restrito a loopback, mesmo com um Bearer manage.

## Documentando níveis de segurança no OpenAPI

Ao adicionar uma nova rota a `docs/openapi.yaml`, aplique a extensão de fornecedor
correspondente caso a rota seja classificada por `routeGuard.ts`:

| Classificação de routeGuard.ts          | Anotação YAML                 | Aplicação                                               |
| --------------------------------------- | ----------------------------- | ------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`               | `x-loopback-only: true`       | Bloqueada incondicionalmente fora de loopback           |
| `ALWAYS_PROTECTED_API_PATHS`            | `x-always-protected: true`    | Autenticação obrigatória mesmo com `requireLogin=false` |
| Rota interna de administração/depuração | `x-internal: true`            | Oculta de /dashboard/api-endpoints por padrão           |
| Nenhuma (pública/autenticação padrão)   | (nenhuma anotação necessária) | Acesso padrão controlado por `requireLogin`             |

### Validação

Dois scripts garantem a consistência entre as anotações YAML e `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — falha se a cobertura for < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — falha se as anotações `x-loopback-only` ou
  `x-always-protected` divergirem das constantes definidas em tempo de compilação

Ambos os scripts são executados no hook de pré-commit e na CI.

### Regra de falso positivo

Se `x-always-protected` ou `x-loopback-only` estiver anotado em uma rota que NÃO esteja na
constante de `routeGuard.ts`, o script de cobertura falhará. A correção é sempre alinhar o
YAML ao que `routeGuard.ts` realmente aplica — e não adicionar rotas a `routeGuard.ts`
sem também implementar a lógica de aplicação.
