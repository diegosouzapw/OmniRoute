Esta página explica o comportamento do `.env` local do projeto e como lidar com arquivos de ambiente e segredos durante o desenvolvimento do OmniRoute.

## Comportamento do `.env` no postinstall

O projeto pode gerar um arquivo `.env` local durante `npm install` / `postinstall` para facilitar o trabalho dos desenvolvedores. Esse arquivo destina-se apenas ao desenvolvimento e aos testes locais e nunca deve ser enviado para o controle de versão.

Pontos principais:

- O `.gitignore` do repositório já ignora arquivos `.env*` (consulte a entrada no `.gitignore`). Não remova nem altere essa regra, a menos que você pretenda deliberadamente enviar um arquivo de exemplo específico e tenha um processo documentado para isso.
- Se um segredo real for acidentalmente enviado para o repositório, rotacione/revogue a credencial imediatamente e remova-a do histórico do repositório (por exemplo, usando `git filter-repo` ou um fluxo de trabalho de correção equivalente). Entre em contato com o responsável pela segurança ou pelo canal de contato caso precise de ajuda.
- Para CI e produção, use os segredos de CI ou um gerenciador de segredos (GitHub Actions Secrets, Azure Key Vault, HashiCorp Vault etc.) em vez de armazenar segredos em arquivos enviados ao repositório.

## Fluxo de trabalho local recomendado

- Mantenha o `.env` apenas no seu ambiente de trabalho local. Use o `.env.example` (já rastreado) para documentar as variáveis necessárias e os valores de exemplo aceitáveis.
- Ao executar localmente testes que exigem valores semelhantes a segredos, prefira espaços reservados sintéticos ou chaves efêmeras geradas em tempo de execução em vez de credenciais reais.
- Adicione um breve comentário aos testes que usam espaços reservados para que os revisores entendam que o dado de teste é sintético.

## Observações sobre scanners

- Alguns recursos compilados ou binários (por exemplo, blobs WASM em base64 incorporados) podem conter substrings ASCII semelhantes a credenciais e acionar scanners de segredos baseados em texto. Se esses recursos forem legítimos, adicione-os à lista de permissões do scanner ou exclua os diretórios na configuração do scanner.

## Se você encontrar um vazamento

1. Rotacione/revogue a chave imediatamente.
2. Remova o segredo do histórico e faça um push forçado de um branch limpo, se necessário.
3. Notifique os mantenedores e siga a lista de verificação de resposta a incidentes da sua organização.
