Os relays (Vercel, Deno, Cloudflare) encerram a conexão upstream em um backend
serverless para que o OmniRoute possa encaminhar o tráfego de saída por uma região estável, mantendo
a chave de API do provedor no lado do servidor. Este documento aborda os dois modos de falha
encontrados pelos operadores em produção e os procedimentos de recuperação fornecidos pelo OmniRoute
para cada um deles.

## Como a autenticação do relay é armazenada

Quando você implanta um relay em **Settings → Proxy Pool → Deploy Relay**, o
fluxo de implantação armazena o token de autenticação do relay no campo JSON `notes`
do proxy:

- Se `STORAGE_ENCRYPTION_KEY` estiver definida, o token será armazenado como `relayAuthEnc`
  (criptografado com AES quando armazenado).
- Caso contrário, ele será armazenado como texto simples em `relayAuth`.

No momento da solicitação, `extractRelayAuth(notes)` retorna a forma que estiver presente,
portanto o relay continuará funcionando após reinicializações.

## Modo de falha 1 — token impossível de descriptografar após a rotação da chave

**Sintoma:** relays que funcionavam anteriormente agora retornam erros upstream de `401`/autenticação
após uma rotação de `STORAGE_ENCRYPTION_KEY` no ambiente ou no gerenciador de segredos.
O blob `relayAuthEnc` armazenado não pode mais ser descriptografado; por isso,
`extractRelayAuth` retorna uma string vazia e o relay não envia
autenticação.

**Recuperação — reparar no local (sem reimplantação):**

1. Abra **Settings → Proxy Pool**.
2. As linhas de relays cuja autenticação está ausente exibem um selo amarelo `auth missing` e um
   botão **Repair**.
3. Clique em **Repair**. O OmniRoute chama
   `POST /api/settings/proxies/[id]/repair-relay`, que:
   - descriptografa `relayAuthEnc` com a chave **atual**,
   - grava novamente o `relayAuth` em texto simples em `notes`,
   - retorna `{ repaired: true, mode: "recovered" }`.

O relay volta a atender solicitações sem que seja necessário inserir novamente as credenciais de implantação.

Isso só funciona se a `STORAGE_ENCRYPTION_KEY` atual ainda puder descriptografar o
blob. Se você tiver rotacionado a chave **sem** uma migração, o blob será
irrecuperável.

## Modo de falha 2 — token irrecuperável (a chave anterior não está mais disponível)

**Sintoma:** você clicou em **Repair** e recebeu
`{ repaired: false, mode: "redeploy", status: 409 }`.

**Recuperação — reimplantar:**

O token armazenado não pode ser recuperado com a chave atual. Reimplante o relay
usando o mesmo modal utilizado originalmente (menu **Deploy Relay** → Vercel / Deno
/ Cloudflare). O fluxo de implantação grava um novo token (criptografado com a chave
atual), e o selo `auth missing` da linha desaparece.

Na interface, o próprio botão **Repair** abre o modal de reimplantação quando o
token é irrecuperável, portanto você nunca precisa procurá-lo manualmente.

## Modo de falha 3 — relay acessível, mas não íntegro

**Sintoma:** o teste do proxy (botão `speed`) mostra que o relay está ativo, mas as solicitações
ainda falham de forma intermitente.

Verifique os cabeçalhos de reconhecimento do relay retornados pela sondagem de teste automático
do OmniRoute (consulte **Settings → Proxy Pool** e os contadores `relayTested` / `relayAlive`):

- `x-relay-url` — qual backend de relay respondeu.
- `x-relay-mode` — `ts` | `bifrost` | `auto` para essa solicitação.
- `x-relay-attempts` — quantos saltos de relay foram tentados antes do sucesso.
- `x-relay-fallback` — `true` quando a solicitação alternou do backend
  preferencial para o relay TypeScript.

Uma taxa elevada de `x-relay-fallback` com um valor baixo de `relayAlive` significa que o backend
sidecar não está íntegro e você deve corrigi-lo ou alterar a estratégia de backend do relay
para `ts` (consulte `RELAY_BACKEND_STRATEGY.md`).

## Referência da API

| Método | Caminho                                   | Corpo                   | Sucesso                                                                                                                                                | Falha                                                                                        |
| ------ | ----------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }` quando derivado novamente; `200 { repaired: false, mode: "noop" }` quando o texto simples já está presente | `409 { mode: "redeploy" }` irrecuperável; `400` não é um tipo de relay; `404` não encontrado |

A rota de listagem `GET /api/settings/proxies` anexa um
`relayInfo: { isRelay, authMissing, repairMode }` sem segredos a cada item, permitindo que o painel
exiba a opção de reparo sem nunca expor o token.
