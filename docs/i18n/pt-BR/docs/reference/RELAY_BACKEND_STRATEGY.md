## Resumo

O OmniRoute agora oferece suporte a três modos de relay para `/api/v1/relay/chat/completions`:

- `ts`: usa o relay TypeScript no processo.
- `bifrost`: força o uso do gateway Bifrost.
- `auto`: dá preferência ao Bifrost quando disponível e recorre ao TypeScript em caso de falha.

Ao operar com uma alta taxa de requisições (grande número de tokens/dia e throughput quase constante), a melhor estratégia é manter o caminho de fallback explícito e rápido, para que o caminho crítico nunca fique bloqueado por um sidecar indisponível.

## Comportamento dos modos

- `ts`
  - Menor complexidade operacional.
  - Todo o roteamento e a validação são executados no Node.
  - Nenhuma dependência de sidecar para disponibilidade.
- `bifrost`
  - Força todas as requisições a passarem pelo gateway sidecar.
  - Sem fallback automático.
  - Útil apenas quando a integridade e a latência do sidecar são garantidas.
- `auto`
  - O sidecar é usado quando está habilitado e pode ser acessado.
  - Tentativas com falha acionam cabeçalhos de fallback e retornam o tráfego ao TS, para que o sucesso das requisições permaneça dentro de limites previsíveis.
  - Esse modo é a opção mais segura para produção quando o tempo de atividade é mais importante do que o roteamento estrito apenas pelo sidecar.

## 9router versus CLIPROXYAPI atualmente

9router e CLIPROXYAPI são integrações que historicamente disponibilizaram caminhos de compatibilidade para provedores upstream.

- 9router é um caminho integrado para orquestração upstream e comportamento de compatibilidade.
- CLIPROXYAPI é uma ponte de API proxy para tráfego no estilo CLI / SDK.
- O Bifrost está sendo estabilizado como o caminho externalizado para quando você precisa de um salto dedicado semelhante a um sidecar e de despacho local com baixa latência.

Se você estiver comparando 9router/CLIPROXYAPI atualmente:

- Mantenha a assinatura de requisições, as verificações de lista de permissões e os controles de política do banco de dados na rota da API antes do encaminhamento.
- Se um fluxo de trabalho precisar de comportamento estrito de sidecar e menor variação por requisição, use `OMNIROUTE_RELAY_BACKEND=bifrost`.
- Se você precisar de resiliência do sidecar com degradação gradual durante incidentes, use `OMNIROUTE_RELAY_BACKEND=auto`.

## Contrato de limite do backend

O limite estável do produto é a API de relay do OmniRoute, não a implementação do painel. O painel Next.js pode instalar, configurar e supervisionar serviços locais, mas o roteamento de requisições deve entrar pela API de relay e ser encaminhado após esse limite.

Opções de backend de longo prazo:

- Mantenha o relay TypeScript como o caminho de política e fallback no processo. Autenticação, listas de permissões, normalização de requisições, contabilização e verificações de segurança permanecem aqui antes de qualquer encaminhamento ao backend.
- Use o Bifrost como o sidecar Tier-1 preferencial de alto throughput quando a implantação exigir menor variação de roteamento, rotação centralizada de provedores ou expansão horizontal entre várias réplicas do OmniRoute.
- Mantenha 9router e CLIPROXYAPI como serviços de compatibilidade integrados. Eles são executados como processos locais supervisionados e são úteis quando o comportamento de provedor/CLI desses serviços é o adaptador desejado, mas não devem se tornar o mecanismo de roteamento Tier-1 padrão.
- Não permita que o painel envie URLs de serviço arbitrárias para o caminho crítico. As URLs fornecidas pela interface são entradas de configuração; o código de roteamento deve resolver backends registrados e com integridade verificada por meio das configurações do servidor e do estado do supervisor.
- Atualmente, prefira HTTP de loopback para serviços supervisionados, pois os processos gerenciados já expõem APIs compatíveis com HTTP, a proteção da rota pode auditar o limite e o comportamento de falha/fallback fica visível nos logs de requisição. Só vale a pena adicionar um SDK ou transporte por socket no futuro se isso reduzir de forma mensurável a latência p99 de roteamento sem enfraquecer o isolamento ou a semântica de fallback.

Portanto, para uma implantação com throughput muito alto, a resposta padrão é `auto` com o Bifrost habilitado: use o sidecar em Go no caminho crítico, preservando o fallback em TypeScript para manter a taxa de sucesso. Use `bifrost` somente quando o comportamento estrito e exclusivo de sidecar for mais importante do que a degradação gradual.

## Orientações para alto throughput

Para RPM/RPS alto e sustentado e um SLO de sucesso rigoroso:

1. Use `auto` com um período de espera prático e telemetria de falhas.
2. Mantenha a validação upstream e as verificações de chave de API no limite da rota TypeScript.
3. Habilite cabeçalhos/contadores explícitos para que seus alertas detectem a frequência e os motivos dos fallbacks.
4. Ajuste os timeouts do sidecar para que falhem rapidamente, em vez de aguardar indefinidamente.
5. Mantenha saudáveis o reinício automático do serviço e o ciclo de telemetria de integridade, para que o fallback seja realmente excepcional.

## Configuração básica sugerida

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- Mantenha habilitadas nos manipuladores de rota as verificações de chaves de API, lista de permissões, sanitizador e limite de taxa (elas sempre são executadas antes do encaminhamento downstream).
- Exporte métricas de fallback do seu proxy reverso e dos logs de requisição para que indisponibilidades do sidecar fiquem visíveis em até um minuto.

## Contrato de plugin de provedor

Os sidecars devem importar os metadados dos provedores por meio do manifesto de plugin de provedor compatível com JSON, em vez de depender dos componentes internos do executor TypeScript. Consulte
[Manifesto de Plugin de Provedor](./PROVIDER_PLUGIN_MANIFEST.md) para conhecer o contrato de elegibilidade do sidecar e as fases de migração.
