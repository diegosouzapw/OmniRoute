`open-sse/config/providerPluginManifest.ts` define o contrato de plugin de
provedor compatível com JSON. `open-sse/config/providerPluginManifestRegistry.ts`
vincula esse contrato ao registro atual de provedores para sidecars como Bifrost,
CLIProxyAPI ou um futuro roteador em Go/Rust. O registro TypeScript continua sendo
a fonte da verdade, mas os sidecars podem consumir o manifesto sem importar código
de executor, padrões de OAuth, cabeçalhos ou o estado do ambiente do processo.

O mesmo manifesto está disponível via HTTP em
`GET /api/v1/provider-plugin-manifest` para sidecars executados fora do processo.

O OmniRoute informa essa URL ao Bifrost e ao CLIProxyAPI por meio do cabeçalho de
requisição `X-OmniRoute-Provider-Manifest-Url`. Defina
`OMNIROUTE_PROVIDER_MANIFEST_URL` quando o sidecar precisar de uma URL pública ou
de rede de contêiner em vez da origem da requisição local.

## Atualização do Manifesto

O endpoint HTTP retorna `Cache-Control: public, max-age=60` e um `ETag` forte.
Um sidecar deve manter o último manifesto validado e enviar seu ETag em
`If-None-Match` durante a atualização. Uma resposta `304 Not Modified` não possui
corpo; o sidecar mantém o manifesto em cache. Se não houver um manifesto validado
em cache, o sidecar deverá fazer uma requisição incondicional em vez de aceitar
um `304`.

## Objetivo

Mover os metadados dos provedores para um contrato de plugin, de modo que o
caminho crítico de requisições possa, futuramente, ficar sob responsabilidade
de um sidecar de menor latência, enquanto o OmniRoute mantém a rota TypeScript
como porta de aplicação de políticas e fallback. O manifesto é aditivo: por si
só, ele não altera o roteamento de requisições.

## Contrato

O manifesto contém:

- id e alias do provedor
- formato upstream e nome do executor
- tipo de autenticação, cabeçalho de autenticação e prefixo de autenticação opcional
- metadados estáticos do endpoint
- elegibilidade para sidecar e motivos explícitos para um provedor permanecer no TS
- metadados de modelo compatíveis com JSON, como tamanho do contexto, indicadores
  de visão/raciocínio e parâmetros não compatíveis
- tags de capacidade, incluindo `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` e `usage-supported`

O manifesto exclui intencionalmente:

- segredos de cliente OAuth e valores padrão de segredos
- resolução do ambiente de runtime
- cabeçalhos de requisição e auxiliares de credenciais públicas
- construtores dinâmicos de URL
- funções de executor
- detalhes internos do pool de sessões

## Tags de Capacidade

`capabilities` é um array ordenado de tags derivadas da entrada do registro. Os
integradores devem tratá-lo como a resposta legível por máquina à pergunta "o que
este provedor pode fazer", em vez de reler os fontes TypeScript.

| Tag                  | Significado                                                                   |
| -------------------- | ----------------------------------------------------------------------------- |
| `apikey`             | Aceita uma chave de API (`authType` é `apikey` ou `optional`).                |
| `oauth`              | Usa um fluxo OAuth ou de sessão.                                              |
| `responses`          | Expõe uma URL base da API Responses da OpenAI.                                |
| `passthrough-models` | Fornece modelos diretamente do upstream em vez de um catálogo estático.       |
| `custom-executor`    | Executa um executor não padrão, portanto permanece no caminho TypeScript.     |
| `sidecar-candidate`  | Reflete `sidecar.eligible` — é seguro considerar sua importação pelo sidecar. |
| `usage-fetch`        | Possui um buscador de uso ou cota configurado (`getUsageForProvider`).        |
| `usage-supported`    | A API de uso aceita este provedor (`isSupportedUsageConnection`).             |

`usage-fetch` serve apenas para descoberta. Ele informa que o OmniRoute sabe como
ler o uso do provedor; não ativa a busca, não altera a semântica de cotas nem
implica que o widget de cotas do Dashboard esteja habilitado para o provedor —
esse widget é controlado separadamente por `USAGE_SUPPORTED_PROVIDERS`. A fonte
da verdade é `USAGE_FETCHER_PROVIDERS` em
`open-sse/services/usage/fetcherProviders.ts`.

Essa lista usa como chaves as strings aceitas pelo dispatcher de uso, portanto
mistura ids canônicos com aliases e é ligeiramente maior que o número de
provedores com tags: entradas que não são provedores de chat no registro do
manifesto (por exemplo, o provedor de busca `firecrawl` e o provedor ACP
`amazon-q`) não possuem uma entrada de manifesto à qual atribuir a tag.

`usage-supported` indica se as rotas de uso do servidor e do Dashboard aceitam
uma conexão para o provedor. Ele reflete `isSupportedUsageConnection()`
(`src/lib/usage/providerLimits.ts`) e `supportsProviderQuota()`
(`src/shared/utils/providerQuotaVisibility.ts`), ambos controlados por
`USAGE_SUPPORTED_PROVIDERS`
(`open-sse/services/usage/supportedProviders.ts`). Diferentemente de
`usage-fetch`, ele é emitido apenas com base no id do provedor — a verificação
em runtime executa `USAGE_SUPPORTED_PROVIDERS.includes(providerId)` sem
resolução de alias, portanto o manifesto mantém a mesma regra. As duas tags têm
escopos diferentes: 3 provedores possuem apenas `usage-fetch` (`opencode`,
`opencode-zen`, `xai`) e 1 possui apenas `usage-supported`
(`xiaomi-mimo-token-plan`), portanto uma não implica a outra.

## Uso de Sidecars

Os sidecars devem tratar `sidecar.eligible` como um sinal conservador de candidatura, e não
como uma decisão incondicional de roteamento. O primeiro alvo de importação deve ser
provedores com chave de API e endpoint estático que usam o executor padrão. Provedores com
executores web personalizados, fluxos de OAuth/sessão, construtores de URL dinâmicos ou configuração
de pool permanecem no caminho de fallback do TypeScript até que um sidecar implemente um
comportamento equivalente e a telemetria comprove a paridade.

Fases de migração sugeridas:

1. Gerar e validar o manifesto de plugins de provedores a partir do registro do TS.
2. Ensinar o Bifrost ou o CLIProxyAPI a importar o manifesto para provedores com
   chave de API/endpoint estático.
3. Rotear os provedores elegíveis pelo sidecar por meio de `OMNIROUTE_RELAY_BACKEND`,
   mantendo o fallback do TS habilitado.
4. Promover provedores somente quando a taxa de sucesso, a latência p99, o comportamento de streaming
   e o tratamento de parâmetros não compatíveis corresponderem ao caminho do TS.
5. Adicionar plugins nativos do sidecar para executores personalizados, uma família de provedores
   por vez.

## Por Que Não Incorporar Provedores Diretamente No Next

O frontend do Next não deve ser responsável pela execução dos provedores. Ele deve chamar o limite da API.
O backend poderá então decidir se usará o executor do TypeScript,
o Bifrost, o CLIProxyAPI ou um futuro sidecar nativo. Isso mantém a assinatura de requisições,
as verificações da lista de permissões, a política do banco de dados e o comportamento de fallback centralizados antes de qualquer
transferência para um sidecar.
