## Solução de problemas detalhada

### Limitação de requisições em provedores gratuitos (429 / 400 / 401)

**Sintoma**: Ao usar `model: "auto"` com provedores gratuitos/sem autenticação (opencode, auggie etc.), você recebe intermitentemente `HTTP 429`, `400` ou `401` em vez de respostas. As requisições funcionam ao tentar novamente com o mesmo prompt alguns instantes depois, mas a automação (tarefas cron, agentes, scripts) falha no primeiro erro.

**Causa raiz**: Três modos de falha independentes se acumulam:

1. **Limite de requisições do provedor (`429`)**: Os níveis gratuitos podem aplicar uma cota por janela. Uma rajada de chamadas paralelas a esgota, fazendo com que a próxima requisição seja recusada até que a janela seja reiniciada.
2. **Modelo com falha no passthrough (`400`/`401`)**: Os pools `auto/*` podem incluir modelos passthrough do `opencode` que estão registrados no catálogo, mas não têm credenciais ativas (por exemplo, `oc/north-mini-code-free` → `401`). O roteador automático tenta um deles, falha e propaga o erro antes que o fallback seja acionado.
3. **Amplificação por concorrência (`429` sob carga)**: Quando várias sessões de agente/cron acessam `auto` ao mesmo tempo, a taxa agregada de requisições excede o que os provedores gratuitos toleram, fazendo com que chamadas legítimas sejam sinalizadas como abusivas.

**Correção verificada (relatada pela comunidade, 2026-08-10)**: ajuste três variáveis de ambiente para que a rotação, a concorrência e o fallback absorvam a instabilidade do nível gratuito em vez de falharem por causa dela:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # muda para outro modelo/provedor em caso de 400/401 (ignora modelos passthrough com falha)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # limite explícito de admissão de requisições pesadas (não definido por padrão: sem limite de contagem de requisições; veja a observação abaixo)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # aumenta a espera limitada para além do padrão de RATE_LIMIT_MAX_WAIT_MS para serviços upstream lentos
```

Defina essas variáveis no ambiente do processo do OmniRoute (o daemon, por exemplo, por meio do plist do LaunchAgent ou de `systemctl edit`) e reinicie o OmniRoute. O sinalizador de rotação é o recurso de maior impacto: ele transforma uma falha definitiva em uma nova tentativa transparente usando um provedor saudável do pool.

**Observação**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` limita quantas requisições pesadas — de contexto longo — são executadas ao mesmo tempo; esse limite é um controle de admissão, não um limitador de requisições do provedor. **Atualização de fan-out #503:** essa variável não é mais definida por padrão (agora, ela só estabelece um limite quando configurada explicitamente, como acima) — em vez disso, a admissão de requisições pesadas é controlada por um orçamento de bytes calculado automaticamente (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), que se ajusta com base no limite real de memória do host. Portanto, uma nova implantação deve apresentar muito menos rejeições `503 chat_admission_busy` sem que seja necessário definir essa variável; defini-la explicitamente aqui ainda funciona exatamente como documentado. Substituições explícitas do orçamento de bytes são limitadas ao intervalo de 8 MiB a 2 GiB. Um `413 body_exceeds_budget` não é transitório: aumente esse orçamento de bytes, reduza `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ou aumente o limite de memória do processo. Um descarte `inflight_bytes_budget` representa uma contenção temporária e continua permitindo novas tentativas. A limitação de requisições por provedor (`open-sse/services/rateLimitManager.ts`) é controlada separadamente por `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` e `RATE_LIMIT_AUTO_ENABLE` — consulte `.env.example`.

**Como verificar se funcionou**: execute seu agente/cron duas vezes em rápida sucessão e confirme que ambas as execuções foram bem-sucedidas. Antes da correção, a segunda execução normalmente retorna `429`/`401`. Após a correção, as falhas (se houver) são repetidas de forma transparente e a chamada é concluída. Você também pode executar `curl /monitoring/health` e observar o campo `rateLimitedUntil` nas conexões dos provedores e o campo `circuitBreakers.providerBreakers[].state` dos provedores afetados — o estado pode ser `CLOSED`, `DEGRADED`, `OPEN` ou `HALF_OPEN` (consulte `src/shared/utils/circuitBreaker.ts`), e um provedor que continua falhando passará de `CLOSED → DEGRADED → OPEN` antes que a janela de redefinição permita uma solicitação de teste (`HALF_OPEN`).

**Se você ainda receber 429**: a conta ativa desse provedor realmente esgotou sua _cota_ (não apenas o limite de requisições). Adicione uma segunda conta para o mesmo provedor no painel do OmniRoute → Provedores → Contas ou inclua outro provedor gratuito (por exemplo, `routeway`, `auggie`). A rotação ajuda apenas com erros transitórios de limite de requisições/400/401; o esgotamento definitivo da cota exige uma segunda credencial ou um provedor diferente.

**Se você receber 403 em modelos de visão (`auto/vision`, `bazaarlink/*`)**: a conta conectada não possui um plano pago que inclua visão ou a chave de API não tem permissões suficientes. Verifique no painel do provedor se o escopo da chave inclui visão/multimodalidade ou conecte uma conta de plano pago e mantenha-a como destino para visão.

## Avisos do npm install (ERESOLVE / peer / deprecated)

Ao executar `npm install -g omniroute`, você poderá ver uma grande quantidade de avisos, como `npm warn ERESOLVE`, notificações sobre dependências de pares e mensagens de `deprecated`. **Eles são esperados e inofensivos.** A instalação foi bem-sucedida se você vir `added <N> packages` na saída.

Para suprimir os avisos de resolução de dependências de pares, use a forma de instalação compatível com o OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` suprime apenas as notificações de `ERESOLVE` e de dependências de pares. Os avisos de descontinuação continuam visíveis porque vêm de pacotes transitivos de terceiros; eles não indicam que a instalação falhou.

Os avisos são causados por intervalos desatualizados de dependências de pares em pacotes de terceiros que o OmniRoute não controla:

1. **`marked-terminal` exige `marked >=1 <16`, mas foi encontrado `marked@18`** — na prática, funciona normalmente; o intervalo de dependência de pares do projeto upstream apenas está desatualizado.
2. **`deprecated prebuild-install@7.1.3`** — um auxiliar transitivo para obtenção de binários nativos. Ele não é
   usado para instalar o binding de transporte fixado `wreq-js` e não indica que a configuração de transporte
   do provedor de cookies da Web falhou.

**Nenhuma ação é necessária** — os avisos não podem ser totalmente silenciados sem criar forks dos pacotes upstream.

## Aviso de scripts de instalação do npm bloqueados (instalação global)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

Ao executar `npm install -g omniroute`, versões mais recentes do npm (v11+ e v12+) bloqueiam scripts de ciclo de vida de pacotes por padrão e exibem um aviso sobre scripts de instalação:

```
npm warn install-scripts 7 pacotes tiveram seus scripts de instalação bloqueados porque não estão incluídos em allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Esse aviso pode ser ignorado?

**Parcialmente, mas não é recomendável executar sem os scripts.** O OmniRoute inclui mecanismos de fallback robustos: se os bindings nativos de `better-sqlite3` não puderem ser carregados a partir do bundle independente, o aplicativo usará drivers alternativos, como `node:sqlite` ou `sql.js` (consulte [Resolução do runtime do SQLite](../ops/SQLITE_RUNTIME.md)). O servidor ainda será iniciado, mas a execução com fallbacks em WASM, como `sql.js`, desabilita o modo WAL (Write-Ahead Logging) do SQLite e aumenta o consumo de memória e a sobrecarga de sincronização com o disco.

### Quais scripts são realmente necessários?

Nem todos os scripts bloqueados são essenciais para executar o OmniRoute:

- **Essenciais (`omniroute`, `better-sqlite3`):** O OmniRoute é executado a partir de um bundle independente de aplicativo Next.js (`dist/`). Durante a instalação, o npm baixa ou compila o driver nativo do SQLite específico para o host no diretório de nível superior `node_modules/better-sqlite3/`. Em seguida, o script `postinstall` do OmniRoute (`scripts/build/postinstall.mjs`) verifica e copia esses binários específicos do host para `dist/node_modules/`, para que o servidor independente possa acessá-los. Se o script `postinstall` do `omniroute` for bloqueado, essa etapa de cópia será ignorada.
- **Opcionais/transitivos (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** São auxiliares de build, ferramentas de monitoramento ou utilitários do chaveiro do sistema. Permiti-los evita avisos de build, mas eles não são necessários para a funcionalidade principal de roteamento.
- **Excluído (`onnxruntime-node`):** É uma dependência opcional para embeddings locais de IA e **não** é necessária para executar o OmniRoute. Seu script `postinstall` baixa aproximadamente 300 MB de recursos CUDA do NuGet; não o inclua na lista de permissões, a menos que você pretenda explicitamente usar aceleração ONNX local em hardware compatível.

### Correção recomendada

Para permitir os scripts de instalação necessários durante uma instalação global e silenciar os avisos, passe `--allow-scripts` para o OmniRoute e suas dependências nativas:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

Como alternativa, para configurar isso permanentemente para todas as instalações globais na sua conta de usuário:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### Verifique sua instalação

Após a instalação, execute a ferramenta de diagnóstico integrada para garantir que os bindings nativos e o ambiente de runtime estejam funcionando corretamente:

```bash
omniroute doctor
```

## Gemini Web e Playwright Chromium

Se uma solicitação do Gemini Web retornar `503` com uma mensagem informando que o Playwright Chromium
não está instalado, o pacote npm está presente, mas o binário do navegador está ausente.
O Playwright mantém deliberadamente os downloads dos navegadores separados da instalação
do pacote npm, portanto, essa resposta é esperada até que o navegador seja instalado.

Para uma instalação global do npm, instale o Chromium a partir do diretório do pacote
OmniRoute para que o cache do navegador pertença à mesma instalação do Playwright:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Reinicie o OmniRoute após a instalação e tente novamente a solicitação do Gemini Web. Se você
executar o OmniRoute a partir de uma imagem do Docker, use a imagem `-web` (ou o destino de compilação
`runner-web`), que inclui o Chromium e suas dependências; a imagem base não
inclui.

## Falsos positivos de antivírus

<a name="antivirus-false-positives"></a>

### Avast/AVG coloca `README.md` em quarentena com `MD:HttpRequest-inf[Susp]`

**Este é um falso positivo. Nada está infectado e nenhuma ação é necessária.**

O Avast e o AVG executam uma heurística que sinaliza arquivos de texto simples/Markdown contendo muitos
links semelhantes a requisições HTTP. O `README.md` do OmniRoute é incluído no pacote npm (ele está
listado em `package.json` → `files`), portanto, em uma instalação global, é colocado em `node_modules/omniroute/README.md`
— e contém cerca de 15 exemplos de `http://localhost:20128/...` (os endpoints HTTP/SSE
do MCP, a URL `.well-known` do A2A e trechos com `curl`). Essa densidade de links é
suficiente para acionar a heurística.

Se isso começou apenas recentemente: o tipo de arquivo não mudou. O README teve sua
tabela de endpoints ampliada (MCP HTTP + SSE + A2A foram adicionados), além de mais exemplos de `curl`, o que fez com que
ultrapassasse o limite.

O arquivo é uma documentação inerte, sem nenhum conteúdo executável. Você pode restaurá-lo da
quarentena com segurança.

**O que fazer:**

1. **Interrompa as notificações** — exclua o diretório de instalação no seu antivírus
   (Avast: Configurações → Exceções), adicionando o caminho global de `node_modules` e/ou o
   diretório de dados do OmniRoute (`~/.omniroute/`).
2. **Reporte o falso positivo** — <https://www.avast.com/false-positive-file-form.php>,
   anexando o `README.md` em quarentena. Essa é a correção que ajuda a todos, pois é
   a heurística do fornecedor reagindo de forma exagerada a um arquivo de texto.

**Por que não "corrigimos" isso do nosso lado:** todos os exemplos usam `http://localhost`, e
localhost não pode usar `https` sem o inconveniente de certificados autoassinados. Adulterar a documentação para
contornar a heurística de um fornecedor prejudicaria todos os leitores para satisfazer um bug do scanner.

### Kaspersky sinaliza o aplicativo para desktop como `PDM:Trojan.Win32.Generic`

**Este é um falso positivo de uma heurística comportamental. Nada está infectado.** O prefixo
`PDM:` da Kaspersky significa que o veredito vem de seu Proactive Defense Module (System Watcher),
que avalia o que o instalador _faz_, em vez de compará-lo com malwares conhecidos. Quando
é acionado, a Kaspersky "reverte" toda a instalação — excluindo arquivos que já havia
gravado —, de modo que o aplicativo acaba corrompido ou ausente.

Os arquivos sinalizados são componentes padrão de dependências declaradas e de código aberto incluídas no
aplicativo para desktop, por exemplo:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` e
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), a biblioteca de automação de navegador
  usada para autenticação de provedores dentro do aplicativo e chat baseado em navegador.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — o binding nativo fixado do `wreq-js`, usado para HTTP com impressão digital de navegador em provedores
  baseados em cookies da web (`<arch>` é `x64` ou `arm64`).

**Por que isso acontece:** o instalador do Windows **ainda não é assinado digitalmente**, portanto, um instalador NSIS
não assinado não tem reputação alguma e as heurísticas comportamentais operam com agressividade máxima. Em conjunto
com uma DLL nativa incluída e centenas de arquivos `.js` gravados em
`%LOCALAPPDATA%\Programs\OmniRoute` (incluindo diretórios de pacotes com sufixos de hash da
compilação standalone do Next.js), isso é suficiente para acionar a heurística. A assinatura de código está planejada;
até que seja implementada, isso pode se repetir em novas versões.

**O que fazer:**

1. **Primeiro, verifique o download** (isso descarta a possibilidade de um arquivo adulterado). Cada versão publica
   `latest.yml`, cujo campo `sha512` (base64) abrange o instalador `OmniRoute.Setup.<version>.exe`.
   No PowerShell, a partir da pasta que contém o instalador:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   A saída deve corresponder a `latest.yml` → `sha512`. Caso contrário, exclua o arquivo e
   faça o download novamente somente pela [página de versões do GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Restaure + exclua** — restaure os itens revertidos da quarentena e adicione uma exclusão
   para `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Configurações → Ameaças e exclusões)
   e, em seguida, reinstale.
3. **Reporte o falso positivo** — <https://opentip.kaspersky.com/>. Relatórios de falsos positivos
   enviados por usuários realmente aceleram a inclusão na lista de permissões.

## Compatibilidade com Node.js

<a name="nodejs-compatibility"></a>

### A página de login trava ou exibe o erro "Module self-registration"

**Causa:** Você está executando uma versão do Node.js fora do limite mínimo de runtime seguro aprovado pelo OmniRoute. O caso mais comum é a execução de uma versão de patch antiga do Node 22 ou 24, abaixo do limite de segurança com correções exigido pelo OmniRoute.

**Sintomas:**

- A página de login exibe uma tela em branco ou um erro do servidor
- O console exibe `Error: Module did not self-register` ou erros semelhantes de bindings nativos
- A página de login exibe um **banner de aviso laranja** com sua versão do Node quando o runtime está fora da política segura compatível

**Correção:**

1. Instale uma versão LTS compatível do Node.js (recomendado: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Verifique sua versão: `node --version` deve exibir `v24.0.0` ou uma versão mais recente da linha LTS 24.x
3. Reinstale o OmniRoute: `npm install -g omniroute`
4. Reinicie: `omniroute`

> **Versões seguras compatíveis:** `>=22.22.2 <23` ou `>=24.0.0 <27`. O Node.js 24.x LTS (Krypton) e o Node.js 26 têm compatibilidade total.

### npm v11+: `better-sqlite3` não instalado (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Causa:** O npm v11 (incluído no Node.js 24+) bloqueia por padrão os scripts de instalação de dependências
opcionais. Como `better-sqlite3` está listado em `optionalDependencies`
e exige compilação nativa (`node-gyp rebuild`), o npm o ignora silenciosamente.

**Sintomas:**

- O servidor trava na inicialização com `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` exibe "No such file or directory"
- `npm ls better-sqlite3` exibe `(empty)`

**Correção:**

1. Aprove os scripts de instalação e reinstale:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Ou instale manualmente o binário pré-compilado:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Verifique se funciona: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Causa:** Após um `npm install -g omniroute` global, o binário nativo do `better-sqlite3` dentro do pacote pode ter sido compilado para uma arquitetura ou ABI do Node.js diferente da que está sendo executada localmente. Isso é comum no macOS (tanto no Apple Silicon quanto no Intel) quando o binário pré-compilado não corresponde ao seu ambiente.

**Sintomas:**

- O servidor falha imediatamente na inicialização com um erro de `dlopen`
- O erro contém `slice is not valid mach-o file`
- Exemplo completo:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Correção — recompile para seu ambiente local (não é necessário fazer downgrade do Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Observação:** Isso recompila o binding nativo para sua versão local do Node.js e arquitetura de CPU, solucionando a incompatibilidade do binário. O intervalo de runtime oficialmente compatível é **`>=22.22.2 <23` ou `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` em `src/shared/utils/nodeRuntimeSupport.ts`, alinhado ao campo `engines` do `package.json`). O Node.js 24.x LTS (Krypton) e o Node.js 26 têm compatibilidade total com o `better-sqlite3` v12.x.

## Problemas de proxy

<a name="proxy-issues"></a>

### A validação do provedor exibe "fetch failed"

**Causa:** O endpoint de validação da chave de API (`POST /api/providers/validate`) anteriormente ignorava a configuração de proxy, causando falhas em ambientes que exigem roteamento por proxy.

**Correção (v3.5.5+):** Isso foi corrigido. A validação do provedor agora é roteada por meio de `runWithProxyContext`, respeitando automaticamente as configurações de proxy globais e no nível do provedor.

### A verificação de integridade do token falha com "fetch failed"

**Causa:** A atualização do token OAuth em segundo plano não resolvia a configuração de proxy por conexão.

**Correção (v3.5.5+):** O agendador de verificação de integridade do token agora resolve a configuração de proxy por conexão antes de tentar a atualização. Atualize para v3.5.5+.

### O proxy SOCKS5 retorna "invalid onRequestStart method"

**Causa:** No Node.js 22, o dispatcher do undici@8 é incompatível com a implementação integrada de `fetch()` do Node.

**Correção (v3.5.5+):** O OmniRoute agora usa a própria função `fetch()` do undici quando um dispatcher de proxy está ativo, garantindo um comportamento consistente. Atualize para v3.5.5+.

### Proxy MITM no WSL: aplicativos de desktop no host Windows não são interceptados

**Causa:** O proxy MITM e seu certificado de CA são instalados no ambiente em que o OmniRoute é executado. No WSL, esse ambiente é o sistema convidado Linux, enquanto os aplicativos de IA para desktop (Kiro, Trae, Copilot, Zed, …) são executados no host Windows. Os aplicativos do host não confiam no repositório de certificados do sistema convidado e não fazem o roteamento pelo proxy do sistema convidado, portanto, a interceptação de desktop não é ativada nesse caso.

**Recomendação:** Execute o OmniRoute nativamente no mesmo sistema operacional dos aplicativos de desktop que você deseja interceptar (Windows para aplicativos Windows; o mesmo se aplica ao macOS/Linux). Manter o OmniRoute dentro do WSL enquanto direciona o tráfego de aplicativos do host exige confiar manualmente no certificado de CA gerado no host Windows e configurar a rede/proxy de cada aplicativo do host para usar o endpoint de proxy do WSL — uma configuração frágil e sem suporte.

## Problemas de provedores

### "Language model did not provide messages"

**Causa:** A cota do provedor foi esgotada.

**Correção:**

1. Verifique o rastreador de cotas no painel
2. Use uma combinação com níveis de fallback
3. Mude para um nível mais barato/gratuito

### Limitação de taxa

**Causa:** A cota da assinatura foi esgotada.

**Correção:**

- Adicione um fallback: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Use GLM/MiniMax como alternativa de baixo custo

### Token OAuth expirado

O OmniRoute atualiza os tokens automaticamente. Se os problemas persistirem:

1. Painel → Provedor → Reconectar
2. Exclua e adicione novamente a conexão do provedor

### Várias contas do Kiro: a segunda conta invalida a primeira

**Causa:** O backend do Kiro impõe uma única sessão ativa por registro de cliente OIDC.
Quando duas contas compartilham o mesmo cliente registrado (conexões importadas antes da v3.8.0),
a atualização do token de uma conta invalida o token de atualização da outra.

**Correção (v3.8.0+):** Importe novamente as conexões afetadas.
A partir da v3.8.0, cada nova conexão do Kiro criada por meio de **Importar token**,
**login social com Google/GitHub** ou **Importação automática** registra automaticamente seu próprio
cliente OIDC dedicado. Portanto, a conexão fica totalmente isolada, e a atualização de uma
conta não afeta nenhuma outra conta.

As conexões importadas _antes_ da v3.8.0 não têm um registro de cliente por conexão.
Essas conexões continuam usando o endpoint compartilhado de atualização da autenticação social.
Para obter isolamento, exclua a conexão antiga em Painel → Provedores e adicione-a novamente
por meio de qualquer um dos três fluxos de importação.

Para obter detalhes completos e instruções passo a passo sobre como adicionar duas contas do Kiro lado a lado,
consulte [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Problemas com a nuvem

### Erros de sincronização com a nuvem

1. Verifique se `BASE_URL` aponta para sua instância em execução (por exemplo, `http://localhost:20128`)
2. Verifique se `CLOUD_URL` aponta para seu endpoint na nuvem (por exemplo, `https://omniroute.dev`)
3. Mantenha os valores `NEXT_PUBLIC_*` alinhados com os valores do lado do servidor

### `stream=false` na nuvem retorna 500

**Sintoma:** `Unexpected token 'd'...` no endpoint da nuvem para chamadas sem streaming.

**Causa:** O upstream retorna uma carga SSE enquanto o cliente espera JSON.

**Solução alternativa:** Use `stream=true` para chamadas diretas à nuvem. O runtime local inclui um fallback de SSE→JSON.

### A nuvem informa que está conectada, mas exibe "Invalid API key"

1. Crie uma nova chave no dashboard local (`/api/keys`)
2. Execute a sincronização com a nuvem: Habilitar nuvem → Sincronizar agora
3. Chaves antigas/não sincronizadas ainda podem retornar `401` na nuvem

## Problemas com Docker

### IPv6 do Docker / Redefinição de conexão

<a name="docker-ipv6"></a>

**Sintomas:** `curl http://localhost:20128/v1/models` retorna `curl: (56) Recv failure: Connection reset by peer`. O dashboard e os endpoints não autenticados funcionam, mas os endpoints autenticados falham — parece um problema de autenticação, mas não é.

**Causa:** `docker run -p 20128:20128` publica tanto em `0.0.0.0` (IPv4) quanto em `::` (IPv6), mas o processo dentro do contêiner escuta apenas em IPv4. Em hosts nos quais `localhost` é resolvido primeiro como `::1`, a conexão chega à porta IPv6 publicada sem haver um listener por trás dela → redefinição da conexão.

**Correção:**

1. **Diagnóstico rápido:** Execute `curl -4 http://localhost:20128/v1/models`. Se funcionar com `-4`, mas falhar sem essa opção, há uma incompatibilidade de bind IPv6.
2. **Correção permanente:** Faça o bind explicitamente ao IPv4 usando `-p 127.0.0.1:20128:20128` no comando `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Isso força o bind IPv4 e também evita expor o proxy em todas as interfaces do host.

## Depuração

### Habilitar arquivos de log

Defina `APP_LOG_TO_FILE=true` no arquivo `.env`. Os logs da aplicação são gravados em `logs/`.
Os artefatos das requisições são armazenados em `${DATA_DIR}/call_logs/` quando o pipeline de logs de chamadas está
habilitado nas configurações.
Quando a captura do pipeline estiver habilitada, defina `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` para omitir
as cargas dos blocos de streaming ou ajuste `CALL_LOG_PIPELINE_MAX_SIZE_KB` para alterar o limite dos artefatos em KB.

### Verificar a integridade do provedor

```bash
# Dashboard de integridade
http://localhost:20128/dashboard/health

# Verificação de integridade da API
curl http://localhost:20128/api/monitoring/health
```

### Armazenamento do runtime

- Estado principal: `${DATA_DIR}/storage.sqlite` (provedores, combinações, aliases, chaves, configurações)
- Uso: tabelas SQLite em `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + `${DATA_DIR}/call_logs/` opcional
- Logs da aplicação: `<repo>/logs/...` (quando `APP_LOG_TO_FILE=true`)
- Artefatos de logs de chamadas: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` quando o pipeline de logs de chamadas está habilitado

A ação **Limpar histórico** da página Logs de requisições limpa `call_logs`, o
`request_detail_logs` legado e o diretório local de artefatos `${DATA_DIR}/call_logs/`.

## Problemas com o Circuit Breaker

### Provedor travado no estado OPEN

Quando o circuit breaker de um provedor está no estado OPEN, as solicitações são bloqueadas até que o período de cooldown termine.

**Correção:**

1. Acesse **Dashboard → Settings → Resilience**
2. Verifique o cartão do circuit breaker do provedor afetado
3. Clique em **Reset All** para limpar todos os circuit breakers ou aguarde o término do período de cooldown
4. Antes de redefinir, confirme se o provedor está realmente disponível

### O provedor continua acionando o circuit breaker

Se um provedor entrar repetidamente no estado OPEN:

1. Verifique o padrão de falhas em **Dashboard → Health → Provider Health**
2. Acesse **Settings → Resilience → Provider Profiles** e aumente o limite de falhas
3. Verifique se o provedor alterou os limites da API ou exige uma nova autenticação
4. Analise a telemetria de latência — uma latência alta pode causar falhas por timeout

## Problemas de Transcrição de Áudio

### Erro "Unsupported model"

- Use um ID de modelo cujo primeiro segmento seja um provedor para o qual você tenha credenciais (`openai/whisper-1`, `openrouter/deepgram/nova-3`). Usar apenas `deepgram/nova-3` exige uma chave nativa da Deepgram.
- Verifique se o provedor está conectado em **Dashboard → Providers**

### A transcrição retorna vazia ou falha

- Verifique os formatos de áudio compatíveis: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- Confirme se o tamanho do arquivo está dentro dos limites do provedor (normalmente < 25 MB)
- Verifique a validade da chave de API no cartão do provedor

## Depuração do Tradutor

Use **Dashboard → Translator** para depurar problemas de tradução de formatos:

| Modo             | Quando usar                                                                                                     |
| ---------------- | --------------------------------------------------------------------------------------------------------------- |
| **Playground**   | Compare os formatos de entrada/saída lado a lado — cole uma solicitação com falha para ver como ela é traduzida |
| **Chat Tester**  | Envie mensagens em tempo real e inspecione o payload completo da solicitação/resposta, incluindo os cabeçalhos  |
| **Test Bench**   | Execute testes em lote em diferentes combinações de formatos para descobrir quais traduções estão com problemas |
| **Live Monitor** | Acompanhe o fluxo de solicitações em tempo real para identificar problemas intermitentes de tradução            |

### Problemas comuns de formato

- **As tags de raciocínio não aparecem** — Verifique se o provedor de destino é compatível com raciocínio e confira a configuração do orçamento de raciocínio
- **As chamadas de ferramentas desaparecem** — Algumas traduções de formato podem remover campos não compatíveis; verifique no modo Playground
- **O prompt do sistema está ausente** — Claude e Gemini processam prompts do sistema de maneiras diferentes; verifique a saída da tradução
- **O SDK retorna uma string bruta em vez de um objeto** — Resolvido na v1.x; o sanitizador de respostas remove campos não padronizados (`x_groq`, `usage_breakdown` etc.) que causam falhas de validação do Pydantic no SDK da OpenAI. Se isso ainda ocorrer na v3.x ou posterior, registre um problema.
- **GLM/ERNIE rejeita a função `system`** — Resolvido na v1.x; o normalizador de funções combina automaticamente as mensagens do sistema com as mensagens do usuário em modelos incompatíveis. Se isso ainda ocorrer na v3.x ou posterior, registre um problema.
- **A função `developer` não é reconhecida** — Resolvido na v1.x; convertida automaticamente em `system` para provedores que não são da OpenAI. Se isso ainda ocorrer na v3.x ou posterior, registre um problema.
- **`json_schema` não funciona com o Gemini** — Resolvido na v1.x; `response_format` agora é convertido em `responseMimeType` + `responseSchema` do Gemini. Se isso ainda ocorrer na v3.x ou posterior, registre um problema.

## Configurações de resiliência

### Limitação automática de taxa não acionada

- A limitação automática de taxa aplica-se apenas a provedores de chave de API (não a OAuth/assinatura)
- Verifique se **Configurações → Resiliência → Perfis de provedores** está com a limitação automática de taxa habilitada
- Verifique se o provedor retorna códigos de status `429` ou cabeçalhos `Retry-After`

### Ajuste do backoff exponencial

Os perfis de provedores oferecem suporte a estas configurações:

- **Atraso base** — Tempo de espera inicial após a primeira falha (padrão: 1s)
- **Atraso máximo** — Limite máximo do tempo de espera (padrão: 30s)
- **Multiplicador** — Quanto aumentar o atraso por falha consecutiva (padrão: 2x)

### Prevenção do efeito manada

Quando muitas solicitações simultâneas atingem um provedor com limitação de taxa, o OmniRoute usa mutex + limitação automática de taxa para serializar as solicitações e evitar falhas em cascata. Isso é automático para provedores de chave de API.

### Solicitações de chat falham com 503 / chat_admission_busy

**Sintomas:**

- O endpoint de conclusões de chat retorna uma resposta `503` que permite nova tentativa e cujo código de erro é
  `chat_admission_busy`.
- A resposta inclui `Retry-After`. Desde a #12135, o valor é derivado da ocupação observada
  — o maior valor entre a janela `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` que a solicitação já
  aguardou e o tempo pelo qual as concessões pesadas atuais foram mantidas — arredondado para cima
  em segundos inteiros e limitado a 60. Em um controle ocioso, ele mantém os valores mínimos históricos: 2 segundos no
  caminho baseado em bytes, 1 segundo no caminho baseado em estrutura (que também inclui
  `reason: "structure_limit"`).
- Isso pode ocorrer enquanto outro chat pesado ou uma resposta de streaming de longa duração ainda está
  em andamento.

O corpo da resposta baseada em bytes é:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

A resposta baseada em estrutura usa o mesmo tipo e código, com a mensagem
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
e `reason: "structure_limit"`.
Nos limites padrão, uma solicitação é estruturalmente pesada quando contém pelo menos `200` mensagens,
pelo menos `64` ferramentas ou pelo menos `32,000` tokens estimados, ou quando a estimativa limitada
da estrutura esgota seus limites de `10,000` nós visitados ou profundidade `12`.

**Causa:** Esta é uma rejeição deliberada de carga dentro do OmniRoute, não uma falha do provedor upstream.
Cada processo usa uma proteção local ao processo para reservar uma capacidade pesada limitada antes de reter
e analisar o corpo de uma solicitação grande. Uma concessão pesada permanece retida durante todo o ciclo de vida de uma resposta
SSE.

**#503-fanout:** antes dessa correção, a proteção limitava a simultaneidade a uma CONTAGEM fixa de solicitações
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, padrão `1`), independentemente da memória do host, portanto o
fan-out de agentes de programação (vários subagentes/CLIs, com corpos rotineiramente > 256 KB) reduzia a
simultaneidade efetiva para ~1 e gerava erros 503 sob uma carga completamente normal. Agora, a proteção se autoajusta: ela é controlada
por um orçamento de ingestão em BYTES derivado automaticamente (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), dimensionado com base no
limite real de memória do processo, e também consulta um sinal dinâmico de pressão sobre recursos — portanto, ela
só rejeita carga quando o host realmente está sob pressão de memória, e não apenas porque mais de uma
solicitação pesada chegou ao mesmo tempo. O antigo limite de contagem (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ainda é
respeitado, mas somente se você o definir explicitamente.

Quando a capacidade está ocupada, uma solicitação pesada primeiro aguarda até
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (o padrão é `RATE_LIMIT_MAX_WAIT_MS`; `0` desabilita a espera) para que uma vaga seja liberada
antes de responder com o `503` que permite nova tentativa. A espera limitada existe para que clientes do tipo agente
(OpenCode, Claude Code, Cursor), que distribuem solicitações secundárias pesadas simultaneamente, serializem o pico
em vez de consumir todo o orçamento de novas tentativas com rejeições imediatas e falhar no meio da tarefa.
A ocupação atual das concessões pesadas, o orçamento de bytes resolvido e a gravidade da pressão em tempo real são
exibidos em `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — verifique esses valores antes de alterar qualquer variável de ambiente.
Configurações → Resiliência → Fila de solicitações → Solicitações simultâneas não controla isso; essa configuração
rege um mecanismo separado de fila de solicitações do provedor.

**Correção:**

1. Primeiro, tente novamente. Os clientes devem respeitar `Retry-After` e usar backoff em vez de repetir
   imediatamente a solicitação.
2. Verifique `/api/monitoring/health` → `chatAdmission` antes de ajustar qualquer coisa. `countCapEnabled:
false` e um `maxInflightBytes` generoso significam que o orçamento derivado automaticamente já está cumprindo sua
   função; uma `pressureSeverity` igual a `high`/`critical` significa que o host realmente está com pouca memória —
   isso não pode ser corrigido por uma variável de ambiente de admissão; é necessário mais RAM ou uma carga de trabalho menor.
3. Somente se `/api/monitoring/health` mostrar que o orçamento derivado automaticamente é realmente pequeno demais para
   seu host (raro — ele já se adapta desde contêineres até bare metal), substitua-o diretamente por
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` em vez de recorrer ao limite legado de contagem de solicitações.

Consulte a [referência de variáveis de ambiente](../reference/ENVIRONMENT.md#4-security--authentication)
para ver as configurações oficiais de admissão.

## Taxonomia opcional de falhas de RAG / LLM (16 problemas)

Alguns usuários do OmniRoute colocam o gateway à frente de stacks de RAG ou de agentes. Nessas configurações, é comum observar um padrão estranho: o OmniRoute parece estar saudável (provedores ativos, perfis de roteamento corretos, nenhum alerta de limite de taxa), mas a resposta final ainda está errada.

Na prática, esses incidentes geralmente têm origem no pipeline de RAG downstream, não no próprio gateway.

Se você quiser um vocabulário comum para descrever essas falhas, poderá usar o WFGY ProblemMap, um recurso de texto externo sob licença MIT que define dezesseis padrões recorrentes de falhas de RAG / LLM. Em linhas gerais, ele abrange:

- desvio na recuperação e limites de contexto interrompidos
- índices e armazenamentos vetoriais vazios ou desatualizados
- incompatibilidade entre embeddings e semântica
- problemas na composição do prompt e na janela de contexto
- colapso lógico e respostas excessivamente confiantes
- falhas em cadeias longas e na coordenação de agentes
- desvio de memória e de função em sistemas multiagente
- problemas de implantação e de ordem de inicialização

A ideia é simples:

1. Ao investigar uma resposta incorreta, registre:
   - a tarefa e a solicitação do usuário
   - a combinação de rota ou provedor no OmniRoute
   - qualquer contexto de RAG usado downstream (documentos recuperados, chamadas de ferramentas etc.)
2. Associe o incidente a um ou dois números do WFGY ProblemMap (`No.1` … `No.16`).
3. Armazene o número em seu próprio painel, runbook ou rastreador de incidentes, junto aos logs do OmniRoute.
4. Use a página correspondente do WFGY para decidir se é necessário alterar sua stack de RAG, o recuperador ou a estratégia de roteamento.

O texto completo e as receitas concretas estão disponíveis aqui (licença MIT, somente texto):

[README do WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Você pode ignorar esta seção se não executar pipelines de RAG ou de agentes por trás do OmniRoute.

## Problemas conhecidos da v3.8.0

Problemas específicos da versão v3.8.0 e suas soluções alternativas atuais. Se uma correção for incluída em um patch posterior, a entrada será atualizada ou removida.

### Falhas de autenticação da Devin CLI

**Sintomas:**

- "Devin CLI não encontrada" ou "falha na autenticação" ao invocar ferramentas baseadas na Devin
- A verificação de runtime da CLI informa `installed=false`

**Causas:**

- `CLI_DEVIN_BIN` aponta para um caminho que não existe
- A Devin CLI não está instalada no host

**Correção:**

1. Instale a Devin CLI para sua plataforma
2. Defina `CLI_DEVIN_BIN=/usr/local/bin/devin` (ou o caminho real) no `.env`
3. Reinicie o OmniRoute e teste novamente em **Painel → Ferramentas de CLI**

### Cooldown do modelo travado (redefinição manual)

**Sintomas:**

- Um modelo permanece listado em cooldown mesmo após o horário de expiração
- As solicitações continuam ignorando o modelo no roteamento por combinação, apesar de o timestamp estar no passado

**Redefinição manual:**

- **Painel:** **Configurações → Cooldowns de modelos** → clique em **Reativar** no cartão afetado
- **API:** `DELETE /api/resilience/model-cooldowns` com cabeçalhos de autenticação de gerenciamento

### Falha na conexão com o provedor Command Code com erro 403

**Sintomas:**

- Erro 403 ao testar a conexão com o provedor Command Code
- O cartão do provedor exibe "não autorizado" após uma nova adição

**Causa:** O fluxo OAuth não foi concluído (o callback não foi recebido ou o token não foi persistido).

**Correção:**

- Execute `omniroute providers` na CLI para acionar novamente o fluxo OAuth ou
- Execute novamente o OAuth em **Painel → Provedores → Command Code → Reconectar**

### ModelScope retorna cooldowns 429 agressivos

**Sintomas:**

- Cooldowns muito curtos ou imediatos no ModelScope após uma pequena sequência de solicitações
- O roteamento por combinação ignora o ModelScope antes do esperado

**Causa:** O ModelScope emite cabeçalhos `Retry-After` específicos do provedor. A v3.8.0 inclui tratamento dedicado para esses cabeçalhos; portanto, versões anteriores os interpretam incorretamente como indicadores genéricos de limite de taxa.

**Correção:**

- Certifique-se de estar usando a v3.8.0 ou posterior
- Verifique se a opção `useUpstream429BreakerHints` está habilitada em **Configurações → Resiliência**

### OMNIROUTE_WS_BRIDGE_SECRET ausente em produção

**Sintomas:**

- Erro 401 em todas as solicitações à ponte WebSocket do Codex/Responses quando executadas em um host remoto de produção
- O handshake da ponte WebSocket é encerrado imediatamente após a conexão

**Causa:** A variável de ambiente `OMNIROUTE_WS_BRIDGE_SECRET` está ausente no ambiente de produção.

**Correção:**

1. Gere um segredo aleatório: `openssl rand -hex 32`
2. Defina `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` no ambiente do servidor de produção (e em qualquer cliente que se comunique com a ponte)
3. Reinicie o OmniRoute

### Responses API: modo em segundo plano degradado para síncrono

**Sintomas:**

- Aviso registrado: `background mode degraded to synchronous`
- Uma solicitação com `background: true` retorna uma resposta síncrona normal em vez de um identificador de tarefa em segundo plano

**Causa:** A v3.8.0 degrada intencionalmente `background: true` na Responses API para execução síncrona, enquanto emite um aviso. A execução assíncrona completa em segundo plano será disponibilizada futuramente.

**Correção:**

- Ajuste o cliente para fazer a chamada sem `background` ou
- Aguarde uma versão posterior que inclua o modo assíncrono completo em segundo plano (acompanhe o changelog)

## Inicialização lenta / tempo limite de prontidão

Se a CLI exibir `⚠ Server did not respond within 60s`, mas o servidor estiver
funcionando, o limite de tempo da verificação de prontidão é muito curto para o seu ambiente.

Isso geralmente ocorre no Windows (antivírus, monitores do sistema de arquivos) ou em contêineres
com cargas de trabalho pesadas durante a inicialização.

**Correção — aumente o limite de tempo:**

```bash
# Via variável de ambiente (persiste entre inicializações):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minutos
omniroute serve

# Via opção da CLI (uso único):
omniroute serve --ready-timeout 180000
```

O padrão é 60 000 ms (60 s). O aviso é apenas informativo; o servidor
continua sendo inicializado em segundo plano e estará acessível assim que a inicialização for concluída.

Consulte [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) para obter detalhes
completos sobre `OMNIROUTE_READY_TIMEOUT_MS`.
