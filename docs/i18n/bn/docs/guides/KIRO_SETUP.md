এই নির্দেশিকায় OmniRoute-এ Kiro (AWS-হোস্টেড AI কোডিং সহকারী) অ্যাকাউন্ট যোগ করার পদ্ধতি আলোচনা করা হয়েছে,
যেখানে সেশন দ্বন্দ্ব ছাড়াই একই সঙ্গে একাধিক অ্যাকাউন্ট চালানোর ওপর গুরুত্ব দেওয়া হয়েছে।

---

## পটভূমি: Kiro অ্যাকাউন্টগুলোর মধ্যে কেন দ্বন্দ্ব হতে পারে

Kiro-এর ব্যাকএন্ড সক্রিয় সেশন ট্র্যাক করতে AWS SSO OIDC ক্লায়েন্ট নিবন্ধন ব্যবহার করে।
গুরুত্বপূর্ণ সীমাবদ্ধতা হলো: **প্রতিটি OIDC ক্লায়েন্ট নিবন্ধন একই সময়ে শুধু একটি সক্রিয়
সেশন সমর্থন করে**। একই নিবন্ধিত ক্লায়েন্ট ব্যবহার করে দ্বিতীয় কোনো ডিভাইস বা ব্যবহারকারী
প্রমাণীকরণ করলে, ব্যাকএন্ড প্রথম অ্যাকাউন্টের রিফ্রেশ টোকেন বাতিল করে দেয়।

এই একই প্রক্রিয়ার কারণে এমন একটি মেশিনে `kiro-cli login` চালালে সমস্যা হয়, যেখানে
অন্য একটি Kiro অ্যাকাউন্ট ইতিমধ্যে সাইন ইন করা আছে — নতুন লগইনটি প্রথম অ্যাকাউন্টের
টোকেন প্রত্যাহার করে দেয়।

---

## OmniRoute কীভাবে এটি সমাধান করে (v3.8.0+)

v3.8.0 থেকে শুরু করে, প্রতিবার Kiro সংযোগ ইমপোর্ট করার সময় OmniRoute `registerClient()`
(AWS SSO OIDC) কল করে। এর ফলে প্রতিটি OmniRoute সংযোগ নিজস্ব নিবেদিত OIDC ক্লায়েন্ট
নিবন্ধন পায়। প্রতিটি ক্লায়েন্ট নিবন্ধন স্বতন্ত্র হওয়ায়, একটি অ্যাকাউন্ট রিফ্রেশ বা পুনরায়
প্রমাণীকরণ করলে অন্য কোনো অ্যাকাউন্টের রিফ্রেশ টোকেন প্রভাবিত হয় না।

এই বিচ্ছিন্নতা রিফ্রেশ-টোকেন ইমপোর্ট পদ্ধতিগুলোতে প্রযোজ্য, আর API-key প্রমাণীকরণ
OIDC রিফ্রেশ সেশন সম্পূর্ণভাবে এড়িয়ে যায়:

| ইমপোর্ট পদ্ধতি                                      | বিচ্ছিন্নতার অবস্থা                                                                          |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| AWS Builder ID / IDC ডিভাইস-কোড প্রবাহ              | ডিভাইস-কোড প্রবাহ চালু হওয়ার পর থেকেই বিচ্ছিন্ন                                             |
| **টোকেন ইমপোর্ট** (ম্যানুয়ালি রিফ্রেশ টোকেন পেস্ট) | v3.8.0 থেকে বিচ্ছিন্ন                                                                        |
| **Google / GitHub সোশ্যাল লগইন**                    | v3.8.0 থেকে বিচ্ছিন্ন                                                                        |
| **স্বয়ংক্রিয় ইমপোর্ট** (kiro-cli SQLite)          | v3.8.0 থেকে বিচ্ছিন্ন (SQLite পাথ আগে থেকেই বিচ্ছিন্ন ছিল; SSO-cache ফলব্যাকও এখন বিচ্ছিন্ন) |
| **API Key** (দীর্ঘমেয়াদি CodeWhisperer কী)         | কোনো রিফ্রেশ সেশন নেই; কীটি যাচাই করে bearer শংসাপত্র হিসেবে সংরক্ষণ করা হয়                 |

## v3.8.0-এর আগে তৈরি করা সংযোগগুলোর জন্য মাইগ্রেশন নোট

v3.8.0-এর আগে ইমপোর্ট করা সংযোগগুলোর `providerSpecificData`-এ কোনো নিবেদিত OIDC ক্লায়েন্ট
নিবন্ধন সংরক্ষিত থাকে না। এই সংযোগগুলো কাজ করতে থাকবে, তবে শেয়ার করা সোশ্যাল-অথ রিফ্রেশ
এন্ডপয়েন্ট ব্যবহার করবে, যার অর্থ এমন দুটি সংযোগ এখনও একে অপরের টোকেন বাতিল করতে পারে।

**বিচ্ছিন্নতা পেতে:** **ড্যাশবোর্ড → প্রোভাইডার** থেকে পুরোনো সংযোগটি মুছে দিন এবং
সমর্থিত যেকোনো ইমপোর্ট প্রবাহ ব্যবহার করে সেটি পুনরায় ইমপোর্ট করুন। নতুন তৈরি হওয়া সব সংযোগ
স্বয়ংক্রিয়ভাবে নিজস্ব ক্লায়েন্ট নিবন্ধন পাবে।

## পাশাপাশি দুটি Kiro অ্যাকাউন্ট যোগ করা

### পূর্বশর্ত

- OmniRoute v3.8.0 বা পরবর্তী সংস্করণ।
- একটি সচল Kiro অ্যাকাউন্ট (ইমেইল + পাসওয়ার্ড, Google অথবা GitHub লগইন)।
- ঐচ্ছিকভাবে একটি দ্বিতীয় Kiro অ্যাকাউন্ট।

### ধাপ ১: প্রথম অ্যাকাউন্টটি ইমপোর্ট করুন

1. **ড্যাশবোর্ড → প্রোভাইডার → প্রোভাইডার যোগ করুন → Kiro** খুলুন।
2. নিচের যেকোনো একটি বেছে নিন:
   - **টোকেন ইমপোর্ট** — `aorAAAAAG` দিয়ে শুরু হওয়া একটি রিফ্রেশ টোকেন পেস্ট করুন।
   - **API Key** — একটি দীর্ঘমেয়াদি Kiro / CodeWhisperer API কী পেস্ট করুন।
   - **Google / GitHub লগইন** — ব্রাউজারে OAuth প্রবাহ সম্পন্ন করুন।
   - **স্বয়ংক্রিয় ইমপোর্ট** — বোতামটিতে ক্লিক করুন; OmniRoute স্থানীয়
     kiro-cli ডেটাবেস অথবা `~/.aws/sso/cache` থেকে শংসাপত্র পড়বে।
3. সংযোগটি সংরক্ষিত হবে। রিফ্রেশ-টোকেন প্রবাহগুলো স্বয়ংক্রিয়ভাবে একটি নিবেদিত
   OIDC ক্লায়েন্ট নিবন্ধন করে। API-key প্রবাহগুলো AWS-এর মাধ্যমে কীটি যাচাই করে এবং কোনো রিফ্রেশ টোকেন সংরক্ষণ করে না।

### ধাপ ২: দ্বিতীয় অ্যাকাউন্টটি ইমপোর্ট করুন

দ্বিতীয় অ্যাকাউন্টের জন্য ধাপ ১ পুনরাবৃত্তি করুন। প্রতিটি ইমপোর্ট আলাদা একটি OIDC
ক্লায়েন্ট নিবন্ধন তৈরি করায়, সংযোগ দুটি সম্পূর্ণভাবে বিচ্ছিন্ন থাকবে।

### ধাপ ৩: উভয় সংযোগ সক্রিয় আছে কি না যাচাই করুন

1. **ড্যাশবোর্ড → প্রোভাইডার** — উভয় Kiro সংযোগের অবস্থা **সক্রিয়** হিসেবে দেখানো উচিত।
2. **ড্যাশবোর্ড → স্বাস্থ্য** — উভয় সংযোগের টোকেন স্বাস্থ্য পরীক্ষা সফল হওয়া উচিত।

### ধাপ ৪: অ্যাকাউন্টগুলোর মধ্যে রাউট করতে একটি কম্বো ব্যবহার করুন

লোড-ব্যালেন্স করতে বা একটি ব্যর্থ হলে অন্যটিতে ফলব্যাক করতে, উভয় সংযোগকে লক্ষ্য হিসেবে রেখে একটি কম্বো তৈরি করুন:

```
kiro/kiro-dev → kiro/kiro-pro
```

কম্বো কনফিগারেশনের জন্য [FEATURES.md](./FEATURES.md) এবং রাউটিং ডকুমেন্টেশন দেখুন।

## এন্টারপ্রাইজ / IDC ব্যবহারকারী

AWS IAM Identity Center (IDC) অ্যাকাউন্টের জন্য, **Dashboard → Providers → Kiro → Device Code** থেকে **AWS Builder ID / IDC ডিভাইস-কোড** প্রবাহ ব্যবহার করুন। ডিভাইস-কোড প্রবাহটি সবসময়ই সম্পূর্ণভাবে বিচ্ছিন্ন ছিল। এসব সংযোগের জন্য পুনরায় ইমপোর্ট করার প্রয়োজন নেই।

যেসব এন্টারপ্রাইজ ব্যবহারকারী ডিফল্ট নয় এমন AWS অঞ্চলে কাজ করেন, তাঁরা Import Token API-এর মাধ্যমে ইমপোর্ট করার সময় অঞ্চলটি নির্দিষ্ট করতে পারেন:

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

বাদ দেওয়া হলে `region` ফিল্ডের ডিফল্ট মান হয় `us-east-1`।

## API-কী ইমপোর্ট প্রবাহ

API-কী প্রমাণীকরণ দীর্ঘমেয়াদি Kiro / AWS CodeWhisperer bearer ক্রেডেনশিয়ালের জন্য ব্যবহৃত হয়। এটি OAuth রিফ্রেশ ব্যবহার করে না, তাই শেয়ার করা OIDC সেশন অবৈধ হয়ে যাওয়ার সমস্যা এড়ায়।

### ড্যাশবোর্ড

1. **Dashboard -> Providers -> Kiro** খুলুন।
2. **API Key** নির্বাচন করুন।
3. API কী এবং ঐচ্ছিক AWS অঞ্চল (`us-east-1` ডিফল্ট) পেস্ট করুন।
4. OmniRoute কীটি যাচাই করে এবং সংযোগটি সংরক্ষণ করে।

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### অভ্যন্তরীণ চুক্তি

API রুটটি `KiroService.validateApiKey()` কল করে কীটি যাচাই করে, যা অঞ্চল-সামঞ্জস্যপূর্ণ CodeWhisperer/Amazon Q এন্ডপয়েন্টের বিপরীতে `ListAvailableProfiles` ব্যবহার করে এবং একটি `profileArn` নির্ধারণ করে।

সংরক্ষিত সংযোগটি নিম্নলিখিতটি ব্যবহার করে:

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

রানটাইমে, `KiroExecutor.buildHeaders()` কীটিকে `Authorization: Bearer <key>` হিসেবে পাঠায় এবং `tokentype: API_KEY` যোগ করে। কোটা/প্রোফাইল কলগুলো একই মার্কার ব্যবহার করে, যাতে AWS bearer-টিকে OIDC বা সামাজিক অ্যাক্সেস টোকেনের পরিবর্তে একটি দীর্ঘমেয়াদি API কী হিসেবে বিবেচনা করে।

## OIDC ক্লায়েন্টের মেয়াদ শেষ হওয়া

AWS SSO OIDC পাবলিক ক্লায়েন্টের মেয়াদ সাধারণত 90 দিন পর শেষ হয় (`clientSecretExpiresAt`)। পর্যবেক্ষণযোগ্যতার জন্য OmniRoute এই টাইমস্ট্যাম্পটি `providerSpecificData`-তে সংরক্ষণ করে। কোনো সংযোগ যদি প্রায় 90 দিন পর রিফ্রেশ হওয়া বন্ধ করে দেয়, তাহলে নতুন OIDC ক্লায়েন্ট নিবন্ধন পেতে সংযোগটি পুনরায় ইমপোর্ট করুন। মেয়াদ শেষ হলে স্বয়ংক্রিয়ভাবে পুনরায় নিবন্ধনের বিষয়টি ভবিষ্যৎ উন্নতি হিসেবে ট্র্যাক করা হচ্ছে।

API-কী সংযোগের ক্ষেত্রে OIDC ক্লায়েন্টের মেয়াদ শেষ হয় না, কারণ এগুলো AWS SSO OIDC-এর মাধ্যমে রিফ্রেশ হয় না।

## সমস্যা সমাধান

### দ্বিতীয় অ্যাকাউন্টটি বারবার লগ আউট হয়ে যাচ্ছে

- **Dashboard → Providers**-এ উভয় সংযোগ পরীক্ষা করুন এবং নিশ্চিত করুন যে প্রতিটির কাঁচা JSON-এ একটি non-null `clientId` দেখাচ্ছে (তথ্য আইকনের মাধ্যমে দৃশ্যমান)। কোনো সংযোগে `clientId` অনুপস্থিত থাকলে, সেটি v3.8.0-এর আগে ইমপোর্ট করা হয়েছিল—এটি পুনরায় ইমপোর্ট করুন।

### "Token validation failed" বার্তাসহ ইমপোর্ট ব্যর্থ হয়

- নিশ্চিত করুন যে রিফ্রেশ টোকেনটি `aorAAAAAG` দিয়ে শুরু হয়েছে।
- নিশ্চিত করুন যে OmniRoute `https://oidc.us-east-1.amazonaws.com`-এ (অথবা কনফিগার করা অঞ্চলে) পৌঁছাতে পারে। আপনি যদি কোনো কর্পোরেট প্রক্সির পেছনে থাকেন, তাহলে **Dashboard → Settings → Proxies**-এ একটি প্রদানকারী-স্তরের প্রক্সি সেট করুন।

### API-কী ইমপোর্ট ব্যর্থ হয়

- নিশ্চিত করুন যে কীটি একটি Kiro / CodeWhisperer API কী, রিফ্রেশ টোকেন নয়।
- নিশ্চিত করুন যে AWS অঞ্চলটি কী/অ্যাকাউন্টের সঙ্গে মেলে। `us-east-1` হলো ডিফল্ট।
- কীটির অবশ্যই `ListAvailableProfiles` কল করার সক্ষমতা থাকতে হবে; অন্যথায় OmniRoute প্রয়োজনীয় `profileArn` নির্ধারণ করতে পারবে না।
