> **সংক্ষেপে**: OmniRoute প্রতিটি অনুরোধের টোকেন ব্যবহার ট্র্যাক করে, খরচ গণনা করে, প্রতি-API-কীর কোটা প্রয়োগ করে এবং ড্যাশবোর্ডে অ্যানালিটিক্স প্রদর্শন করে। এই নির্দেশিকায় এগুলো কীভাবে কাজ করে তা ব্যাখ্যা করা হয়েছে।

**উৎসসমূহ:**

- `open-sse/services/usage.ts` (~70KB) — প্রধান ব্যবহার ট্র্যাকিং
- `src/lib/usageAnalytics.ts` (~10KB) — ড্যাশবোর্ডের জন্য সমষ্টিকরণ
- `src/lib/db/quotaSnapshots.ts` — ঐতিহাসিক কোটা ডেটা
- `src/lib/db/usage*.ts` — ব্যবহার-সম্পর্কিত একাধিক DB মডিউল

## সংক্ষিপ্ত বিবরণ

OmniRoute-এর মধ্য দিয়ে প্রবাহিত প্রতিটি অনুরোধ একটি **ব্যবহার রেকর্ড** তৈরি করে, যা ধারণ করে:

- **পরিচয়**: কোন API কী, প্রোভাইডার, মডেল ও কম্বো
- **টোকেন**: প্রম্পট টোকেন, কমপ্লিশন টোকেন, ক্যাশ করা টোকেন ও মোট টোকেন
- **খরচ**: USD পরিমাণ (মূল্য নির্ধারণের ডেটা থেকে গণনা করা)
- **সময়**: ল্যাটেন্সি, শুরু/শেষের টাইমস্ট্যাম্প
- **স্থিতি**: সফল, ত্রুটি, রেট-লিমিটেড ইত্যাদি

এই রেকর্ডগুলোকে **অ্যানালিটিক্সে** সমষ্টিবদ্ধ করা হয়, **কোটা স্ন্যাপশট** হিসেবে সংরক্ষণ করা হয় এবং **প্রতি-কীর বাজেট সীমা** প্রয়োগ করতে ব্যবহার করা হয়।

```
অনুরোধ ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    অ্যানালিটিক্স  কোটা   বিলিং
                    (ড্যাশবোর্ড) (প্রয়োগ) (এক্সপোর্ট)
```

## কী কী রেকর্ড করা হয়

`usage.ts` সার্ভিস প্রতিটি অনুরোধের জন্য একটি **ব্যবহার ইভেন্ট** ধারণ করে:

| ফিল্ড              | ধরন     | উৎস                                                        |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | রেকর্ড করার সময় তৈরি করা UUID                             |
| `apiKeyId`         | string  | যে API কী অনুরোধটি শুরু করেছে                              |
| `provider`         | string  | প্রোভাইডার ID (openai, anthropic ইত্যাদি)                  |
| `model`            | string  | মডেল ID (gpt-5, claude-opus-4-6 ইত্যাদি)                   |
| `comboId`          | string? | কোনো কম্বোর মাধ্যমে রাউট করা হলে তার কম্বো ID              |
| `promptTokens`     | number  | আপস্ট্রিম রেসপন্স থেকে                                     |
| `completionTokens` | number  | আপস্ট্রিম রেসপন্স থেকে                                     |
| `cachedTokens`     | number  | ক্যাশ হিট টোকেন (Anthropic প্রম্পট ক্যাশিং ইত্যাদি)        |
| `totalTokens`      | number  | প্রম্পট + কমপ্লিশন                                         |
| `costUsd`          | number  | মূল্য নির্ধারণের ডেটা থেকে গণনা করা                        |
| `latencyMs`        | number  | এন্ড-টু-এন্ড অনুরোধের সময়কাল                              |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | status != success হলে ত্রুটির ক্লাস                        |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | প্লাগইন দ্বারা ইনজেক্ট করা কাস্টম ডেটা                     |

### টোকেন কোথা থেকে আসে

**রেসপন্স হ্যান্ডলারে** আপস্ট্রিম প্রোভাইডারের রেসপন্স থেকে টোকেন বের করা হয়:

```ts
// open-sse/handlers/chatCore.ts থেকে
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

যেসব প্রোভাইডার ব্যবহার-সংক্রান্ত ডেটা ফেরত দেয় না (কিছু web-cookie প্রোভাইডার), সেগুলোর ক্ষেত্রে OmniRoute `প্রতি টোকেনে ~4টি অক্ষর` হিউরিস্টিক ব্যবহার করে টোকেনের পরিমাণ **অনুমান** করে (`open-sse/services/autoCombo/pipelineRouter.ts` দেখুন)।

### ক্যাশ করা টোকেন

OmniRoute `cached_tokens`-কে `prompt_tokens` থেকে আলাদাভাবে ট্র্যাক করে, কারণ:

- Anthropic প্রম্পট ক্যাশিংয়ে ক্যাশ করা টোকেনের জন্য কম হারে চার্জ করা হয় (স্বাভাবিক হারের 10%)
- কিছু প্রোভাইডার `cache_read_input_tokens` ফেরত দেয়, যার মূল্য ভিন্নভাবে নির্ধারণ করা উচিত
- অ্যানালিটিক্স **ক্যাশ হিট রেট** = `cached_tokens / prompt_tokens` দেখাতে পারে

## খরচ গণনা

LiteLLM থেকে সিঙ্ক করা **মূল্য নির্ধারণের ডেটা** (`src/lib/pricingSync.ts`) ব্যবহার করে খরচ গণনা করা হয়:

| মডেল              | ইনপুট $/1M | আউটপুট $/1M | ক্যাশড $/1M |
| ----------------- | ---------- | ----------- | ----------- |
| gpt-5             | $2.50      | $10.00      | —           |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50       |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30       |
| gemini-2.5-pro    | $1.25      | $10.00      | —           |

খরচের সূত্র (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **প্রম্পট থেকে ক্যাশড অংশ বাদ দেওয়া হয় কেন?** ক্যাশড অংশের মূল্য আলাদাভাবে নির্ধারিত হয়; পুরো প্রম্পটের ওপর ইনপুট মূল্য প্রয়োগ করলে অতিরিক্ত গণনা হবে।

### মূল্য সিঙ্ক

`/api/pricing/sync` এন্ডপয়েন্টের মাধ্যমে LiteLLM থেকে মূল্য নির্ধারণের ডেটা স্বয়ংক্রিয়ভাবে সিঙ্ক করা হয় (এটি বিল্ট-ইন cron টাস্ক দ্বারা ট্রিগার হয়, ব্যবহারকারীর জন্য উন্মুক্ত কোনো env var দ্বারা নয়):

```bash
# ম্যানুয়াল ট্রিগার
curl -X POST http://localhost:20128/api/pricing/sync
```

যেসব মডেলের জন্য মূল্য নির্ধারণের ডেটা নেই, সেগুলোর ক্ষেত্রে OmniRoute অভ্যন্তরীণ গড় হার ব্যবহার করে **আনুমানিক খরচ নির্ধারণ** করে (LiteLLM-এর মূল্য নির্ধারণের ডেটা থেকে সংগৃহীত)।

## তারিখসীমার সমষ্টিকরণ

`usageAnalytics.ts` মডিউলটি কাঁচা ব্যবহার-সংক্রান্ত ডেটা থেকে ড্যাশবোর্ড উইজেট গণনা করে। এটি ৭টি সময়সীমা সমর্থন করে:

| সীমা     | সময়কাল                        | ব্যবহারের ক্ষেত্র                 |
| -------- | ------------------------------ | --------------------------------- |
| `1d`     | গত ২৪ ঘণ্টা                    | ঘণ্টাভিত্তিক খরচ বৃদ্ধি শনাক্তকরণ |
| `7d`     | গত ৭ দিন                       | সাপ্তাহিক পর্যালোচনা              |
| `30d`    | গত ৩০ দিন                      | মাসিক বিলিং                       |
| `90d`    | গত ৯০ দিন                      | ত্রৈমাসিক বিশ্লেষণ                |
| `ytd`    | চলতি বছরের ১ জানুয়ারি থেকে    | বার্ষিক বাজেট পর্যবেক্ষণ          |
| `all`    | সর্বকালীন                      | পুরো সময়ের পরিসংখ্যান            |
| `custom` | ব্যবহারকারী-নির্ধারিত শুরু/শেষ | অডিট, তাৎক্ষণিক কাস্টম কোয়েরি    |

### গণনা করা ড্যাশবোর্ড উইজেটসমূহ

যেকোনো তারিখসীমার জন্য অ্যানালিটিক্স স্তরটি নিচের বিষয়গুলো গণনা করে:

| উইজেট                        | বিবরণ                                                    |
| ---------------------------- | -------------------------------------------------------- |
| **সারসংক্ষেপ কার্ড**         | মোট অনুরোধ, মোট খরচ, মোট টোকেন, সফলতার হার               |
| **দৈনিক প্রবণতার চার্ট**     | প্রতিদিনের খরচ + টোকেন, মডেল অনুযায়ী স্তূপীকৃত          |
| **অ্যাক্টিভিটি হিটম্যাপ**    | দিনের ঘণ্টা × সপ্তাহের দিনের গ্রিড, রং = অনুরোধের সংখ্যা |
| **মডেলভিত্তিক বিভাজন**       | মডেল অনুযায়ী খরচের পাই চার্ট                            |
| **প্রোভাইডারভিত্তিক বিভাজন** | প্রোভাইডার অনুযায়ী অনুরোধের বার চার্ট                   |
| **শীর্ষ API কীসমূহ**         | খরচ অনুযায়ী শীর্ষ ১০টি কী-এর টেবিল                      |
| **ত্রুটি বিশ্লেষণ**          | সময়ের সঙ্গে ত্রুটির হার, শীর্ষ ত্রুটি শ্রেণিসমূহ        |

### প্রোগ্রাম্যাটিক অ্যাক্সেস

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // ব্যবহারের ইতিহাসের রেকর্ড
  "7d",                 // সময়সীমা: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // প্রোভাইডার সংযোগ ম্যাপ (connectionId → অ্যাকাউন্টের নাম)
  {
    startDate: "2025-01-01",  // ঐচ্ছিক: "custom" সীমার জন্য

console.log(analytics.summary.totalCost);   // 12.34 (সেন্ট)

## কোটা প্রয়োগ

প্রতি-API-কী কোটা দুটি স্থানে প্রয়োগ করা হয়:

1. **সফট লিমিট** (`quotaWarnAt`): ব্যবহার নির্ধারিত সীমা অতিক্রম করলে ড্যাশবোর্ডে সতর্কতা
2. **হার্ড লিমিট** (`quotaLimit`): সীমা অতিক্রম করলে HTTP 429 সহ অনুরোধ প্রত্যাখ্যান করা হয়

### কনফিগারেশন

```ts
// প্রতি API কী
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — সতর্কতা দেখান
  quotaLimit: 10_00,    // $10.00 — সম্পূর্ণরূপে বন্ধ করুন
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### প্রয়োগের প্রবাহ

```
অনুরোধ ──▶ quotaCheck()
              │
              ├── সীমার মধ্যে?  ──▶ অনুমোদন
              │
              └── সীমার বাইরে?  ──▶ 429 Too Many Requests
                                   Retry-After হেডারসহ
```

### কোটা স্ন্যাপশট

প্রবণতা বিশ্লেষণের জন্য `quotaSnapshots` টেবিলটি **ঐতিহাসিক কোটা অবস্থা** সংরক্ষণ করে:

| ফিল্ড | বিবরণ |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | যে কী ট্র্যাক করা হচ্ছে |
| `window` | "day" | "week" | "month" |
| `used` | এই উইন্ডোতে ব্যবহৃত খরচ (সেন্ট) |
| `limit` | সীমা (সেন্ট) |
| `resetAt` | উইন্ডো রিসেট হওয়ার সময় |
| `createdAt` | স্ন্যাপশট নেওয়ার সময় |

> 0 খরচ ব্যবহার করে এমন **প্রতিটি অনুরোধে** স্ন্যাপশট নেওয়া হয় এবং এগুলো ব্যবহার করা হয়:

- ড্যাশবোর্ডে কোটা অগ্রগতি বার রেন্ডার করতে
- ৩০ দিনের কোটা প্রবণতা চার্ট দেখাতে
- ব্যবহার সীমার কাছাকাছি পৌঁছালে সতর্কতা ট্রিগার করতে

## সংরক্ষণ ও পরিষ্কারকরণ

প্রতিটি অনুরোধে ব্যবহারের ডেটা প্রায় ~1-10KB বৃদ্ধি পায়। বৃহৎ পরিসরে এটি উল্লেখযোগ্য হতে পারে।

### সংরক্ষণ সেটিংস

UI-এর Database Settings অথবা `/api/settings/database`-এর মাধ্যমে ব্যবহারের ইতিহাস সংরক্ষণের সময়কাল কনফিগার করা হয়।

ডিফল্টভাবে, ব্যবহারের ইতিহাস **90 দিন** সংরক্ষণ করা হয়।

### পরিষ্কারকরণ

পুরোনো রেকর্ডগুলো `src/lib/db/cleanup.ts` দ্বারা পরিষ্কার করা হয়:

- ব্যাকগ্রাউন্ড cron প্রক্রিয়া দ্বারা ট্রিগার হয়
- কনফিগার করা `usageHistory` সংরক্ষণ সেটিংসের চেয়ে পুরোনো রেকর্ডগুলো `usage_history` থেকে মুছে দেয়

### স্টোরেজের আনুমানিক হিসাব

| অনুরোধের হার       | 30 দিনের স্টোরেজ | 90 দিনের স্টোরেজ |
| ------------------ | ---------------- | ---------------- |
| 100 অনুরোধ/দিন     | ~3MB             | ~9MB             |
| 1,000 অনুরোধ/দিন   | ~30MB            | ~90MB            |
| 10,000 অনুরোধ/দিন  | ~300MB           | ~900MB           |
| 100,000 অনুরোধ/দিন | ~3GB             | ~9GB             |

খুব বেশি ট্রাফিকের ক্ষেত্রে বিবেচনা করুন:

- Database Settings-এর মাধ্যমে সংরক্ষণের সময়কাল কমানো
- কাঁচা রেকর্ডের পরিবর্তে `aggregated_metrics` ব্যবহার করা (শুধু বিশ্লেষণের জন্য)

## খরচ অপ্টিমাইজ করার পরামর্শ

### 1. সঠিক মডেল ব্যবহার করুন

```bash
# দ্রুত উত্তর — সস্তা + দ্রুত বিকল্প ব্যবহার করুন
curl -d '{"model":"auto/fast","messages":[...]}'

# জটিল কাজ — উচ্চমানের বিকল্প ব্যবহার করুন
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. ক্যাশিং সক্রিয় করুন

Anthropic prompt caching পুনরাবৃত্ত কনটেক্সটে **90% খরচ সাশ্রয় করে**:

```ts
// ক্যাশিং স্বয়ংক্রিয় — শুধু একই বড় system prompt অন্তর্ভুক্ত করুন
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // স্বয়ংক্রিয়ভাবে ক্যাশ করা হবে
  messages: [{ role: "user", content: "..." }],
});
```

### 3. কম্প্রেশন ব্যবহার করুন

RTK + Caveman কম্প্রেশন টুল-নির্ভর সেশনে **15-95% খরচ সাশ্রয় করে**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. প্রতিটি কী-এর জন্য কোটা নির্ধারণ করুন

নিয়ন্ত্রণহীন খরচ প্রতিরোধ করতে সবসময় `quotaLimit` নির্ধারণ করুন:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // মাসিক সর্বোচ্চ $10
```

### 5. সর্বোচ্চ ব্যবহারকারীদের অডিট করুন

API key অনুযায়ী গ্রুপ করতে এবং খরচ অনুযায়ী সাজাতে ড্যাশবোর্ড অথবা **`/api/usage/analytics`** ব্যবহার করুন:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## সমস্যা সমাধান

### "খরচ প্রত্যাশার চেয়ে বেশি"

1. **`/api/usage/analytics?groupBy=model`** পরীক্ষা করুন — ব্যয়বহুল মডেলটি খুঁজে বের করুন
2. **`/api/usage/analytics?groupBy=apiKey`** পরীক্ষা করুন — বেশি ব্যবহারকারীকে খুঁজে বের করুন
3. মূল্যের ডেটা হালনাগাদ আছে কিনা যাচাই করুন: `POST /api/pricing/sync`

### "রেকর্ড পাওয়া যাচ্ছে না"

- Dashboard → Database → Cleanup-এর অধীনে DB সংরক্ষণ সেটিংস পরীক্ষা করুন — পর্যায়ক্রমিক পরিষ্কারকরণ টাস্ক (`src/lib/db/cleanup.ts`) পুরোনো রেকর্ড মুছে দেয়
- `src/lib/db/usage*.ts`-এ ত্রুটি আছে কিনা পরীক্ষা করুন — DB-তে লেখার ব্যর্থতা লগ করা হয়, কিন্তু প্রকাশ করা হয় না
- অনুরোধটি সত্যিই `chatCore`-এ পৌঁছেছে কিনা যাচাই করুন — combo routing পরীক্ষা করুন

### "কোটা কার্যকর হচ্ছে না"

- কী-এর `quotaLimit` সেটিংস পরীক্ষা করুন
- `quotaWindow` সঠিকভাবে সেট করা হয়েছে কিনা যাচাই করুন
- `quotaSnapshots` রেকর্ড খুঁজুন — প্রতিটি অনুরোধে এগুলো তৈরি হওয়া উচিত
