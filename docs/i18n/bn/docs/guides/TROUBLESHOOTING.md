## দ্রুত রেফারেন্স

**OmniRoute-এ নতুন?** এখান থেকে শুরু করুন — এগুলো 90% সমস্যার সমাধান করে:

| আমি যা দেখছি                  | এর অর্থ                                        | কী করতে হবে                                                                                                          |
| ----------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| "সংযোগ করা যাচ্ছে না"         | OmniRoute চলছে না                              | `omniroute` চালান অথবা `docker restart omniroute` চালান                                                              |
| "অবৈধ API key"                | আপনার key ভুল অথবা মেয়াদোত্তীর্ণ              | provider-এর website থেকে key-টি আবার কপি করুন                                                                        |
| "Rate limit অতিক্রম করেছে"    | আপনি অত্যধিক request পাঠাচ্ছেন                 | 1 মিনিট অপেক্ষা করুন, অথবা স্বয়ংক্রিয় fallback-এর জন্য `model: "auto"` ব্যবহার করুন                                |
| "Quota অতিক্রম করেছে"         | আপনার বিনামূল্যের/পরিশোধিত quota শেষ হয়ে গেছে | আরও provider সংযুক্ত করুন, অথবা বিনামূল্যের provider (Kiro, Pollinations) ব্যবহার করুন                               |
| "ধীর response"                | Provider ব্যস্ত অথবা অনেক দূরে                 | `model: "auto/fast"` ব্যবহার করুন অথবা আরও দ্রুত provider (Groq, Cerebras) সংযুক্ত করুন                              |
| "ভুল provider ব্যবহৃত হয়েছে" | `auto` অন্য একটি provider বেছে নিয়েছে         | এটি স্বাভাবিক! `auto` সেরা provider-টি বেছে নেয়। `model: "openai/gpt-4o"` দিয়ে নির্দিষ্ট provider বাধ্যতামূলক করুন |
| "502 Bad Gateway"             | Provider বন্ধ আছে                              | অপেক্ষা করে আবার চেষ্টা করুন, অথবা provider পরিবর্তন করতে `model: "auto"` ব্যবহার করুন                               |
| "401 Unauthorized"            | আপনার credential ভুল                           | আপনার API key পরীক্ষা করুন অথবা OAuth দিয়ে আবার authenticate করুন                                                   |
| "429 Too Many Requests"       | Rate limit প্রয়োগ করা হয়েছে                  | 1 মিনিট অপেক্ষা করুন, অথবা আরও provider সংযুক্ত করুন                                                                 |

## বিস্তারিত সমস্যা সমাধান

---

### বিনামূল্যের Provider-এ Rate Limiting (429 / 400 / 401)

**লক্ষণ**: বিনামূল্যের/auth-বিহীন provider (opencode, auggie ইত্যাদি)-এর সঙ্গে `model: "auto"` ব্যবহার করার সময় উত্তরের পরিবর্তে মাঝে মাঝে `HTTP 429`, `400`, অথবা `401` পাওয়া যায়। কয়েক মুহূর্ত পরে একই prompt আবার চেষ্টা করলে request সফল হয়, কিন্তু প্রথম failure-এই automation (cron job, agent, script) ভেঙে যায়।

**মূল কারণ**: তিনটি স্বতন্ত্র failure mode একসঙ্গে জমা হয়:

1. **Provider rate-limit (`429`)**: বিনামূল্যের tier প্রতি-window quota প্রয়োগ করতে পারে। একসঙ্গে অনেকগুলো call-এর burst সেটি নিঃশেষ করে দেয়, ফলে window reset না হওয়া পর্যন্ত পরবর্তী request প্রত্যাখ্যাত হয়।
2. **Passthrough-এ ত্রুটিপূর্ণ model (`400`/`401`)**: `auto/*` pool-এ `opencode`-এর এমন passthrough model থাকতে পারে, যেগুলো catalog-এ নিবন্ধিত কিন্তু কোনো সচল credential নেই (যেমন `oc/north-mini-code-free` → `401`)। Auto-router একটি চেষ্টা করে, ব্যর্থ হয়, এবং fallback কার্যকর হওয়ার আগেই error ছড়িয়ে পড়ে।
3. **Concurrency amplification (load-এর অধীনে `429`)**: একাধিক agent/cron session একসঙ্গে `auto` ব্যবহার করলে সামগ্রিক request rate বিনামূল্যের provider-গুলোর সহনসীমা ছাড়িয়ে যায়, ফলে বৈধ call-ও অপব্যবহার হিসেবে চিহ্নিত হয়।

**যাচাইকৃত সমাধান (community-এর প্রতিবেদন অনুযায়ী, 2026-08-10)**: তিনটি environment variable সামঞ্জস্য করুন, যাতে rotation, concurrency, এবং fallback বিনামূল্যের tier-এর অস্থিরতা সামলে নেয়, তাতে ব্যর্থ না হয়:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 হলে অন্য model/provider-এ যান (ত্রুটিপূর্ণ passthrough model এড়িয়ে যায়)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # heavyweight admission-এর সুস্পষ্ট সর্বোচ্চ সীমা (default-এ unset: কোনো request-count cap নেই, নিচের note দেখুন)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # তাৎক্ষণিক retryable 503-এর পরিবর্তে heavyweight capacity-এর জন্য দীর্ঘতর সীমাবদ্ধ অপেক্ষা
```

এগুলো OmniRoute process-এর environment-এ সেট করুন (daemon-এ, যেমন LaunchAgent plist অথবা `systemctl edit`-এর মাধ্যমে), তারপর OmniRoute restart করুন। Rotation flag-টি একাই সবচেয়ে বেশি কার্যকর: এটি একটি কঠোর failure-কে pool-এর কোনো সুস্থ provider-এর বিরুদ্ধে স্বচ্ছ retry-তে রূপান্তর করে।

**নোট**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` একই সময়ে কতগুলো heavyweight — দীর্ঘ-context — request চলবে তা সীমিত করে; এই সীমাটি একটি admission gate, provider rate limiter নয়। **#503-fanout আপডেট:** এই var এখন আর default হিসেবে সেট করা হয় না (এটি এখন কেবল স্পষ্টভাবে configure করা হলে কার্যকর হয়, যেমন উপরে দেখানো হয়েছে) — এর পরিবর্তে heavyweight admission একটি স্বয়ংক্রিয়ভাবে নির্ধারিত byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) দ্বারা নিয়ন্ত্রিত হয়, যা host-এর প্রকৃত memory ceiling অনুযায়ী নিজেকে scale করে। ফলে কোনো নতুন deployment-এ এই var একেবারেই সেট না করেও অনেক কম `503 chat_admission_busy` rejection দেখা উচিত; এখানে স্পষ্টভাবে এটি সেট করলেও documentation অনুযায়ী ঠিক একইভাবে কাজ করবে। স্পষ্ট byte-budget override 8 MiB–2 GiB-এর মধ্যে clamp করা হয়। একটি `413 body_exceeds_budget` সাময়িক নয়: সেই byte budget বাড়ান, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` কমান, অথবা process-এর memory ceiling বাড়ান। একটি `inflight_bytes_budget` shed সাময়িক contention এবং retryable থাকে। প্রতি-provider rate limiting (`open-sse/services/rateLimitManager.ts`) আলাদাভাবে `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, এবং `RATE_LIMIT_AUTO_ENABLE` দ্বারা নিয়ন্ত্রিত হয় — `.env.example` দেখুন।

**এটি কাজ করেছে কিনা যেভাবে যাচাই করবেন**: অল্প সময়ের ব্যবধানে আপনার agent/cron দুবার চালান এবং নিশ্চিত করুন যে উভয়বারই সফল হয়েছে। সমাধান প্রয়োগের আগে দ্বিতীয় run-এ সাধারণত `429`/`401` দেখা যায়। সমাধানের পরে failure (যদি থাকে) স্বচ্ছভাবে retry করা হয় এবং call সম্পন্ন হয়। এছাড়াও আপনি `curl /monitoring/health` চালিয়ে provider connection-গুলোর `rateLimitedUntil` field এবং প্রভাবিত provider-গুলোর `circuitBreakers.providerBreakers[].state` পর্যবেক্ষণ করতে পারেন — state হলো `CLOSED`, `DEGRADED`, `OPEN`, অথবা `HALF_OPEN`-এর একটি (`src/shared/utils/circuitBreaker.ts` দেখুন), এবং যে provider বারবার ব্যর্থ হতে থাকে সেটি reset window একটি probe-এর অনুমতি দেওয়ার আগে `CLOSED → DEGRADED → OPEN`-এ পরিবর্তিত হবে (`HALF_OPEN`)।

**যদি এখনও 429 দেখেন**: ওই প্রদানকারীর সক্রিয় অ্যাকাউন্টটি সত্যিই তার _কোটা_ শেষ করে ফেলেছে (শুধু রেট নয়)। OmniRoute ড্যাশবোর্ড → Providers → Accounts-এ একই প্রদানকারীর জন্য দ্বিতীয় একটি অ্যাকাউন্ট যোগ করুন, অথবা অন্য কোনো বিনামূল্যের প্রদানকারী (যেমন `routeway`, `auggie`) মিশিয়ে ব্যবহার করুন। রোটেশন শুধু সাময়িক রেট/400/401 সমস্যায় সহায়তা করে; কোটা সম্পূর্ণ শেষ হয়ে গেলে দ্বিতীয় ক্রেডেনশিয়াল বা ভিন্ন কোনো প্রদানকারী প্রয়োজন।

**যদি ভিশন মডেলগুলোতে (`auto/vision`, `bazaarlink/*`) 403 দেখেন**: সংযুক্ত অ্যাকাউন্টে ভিশন-সমর্থিত কোনো পেইড প্ল্যান নেই, অথবা API key-টির অনুমতি অপর্যাপ্ত। প্রদানকারীর ড্যাশবোর্ডে যাচাই করুন যে key scope-এ vision/multimodal অন্তর্ভুক্ত আছে, অথবা একটি পেইড টিয়ার অ্যাকাউন্ট সংযুক্ত করে সেটিকে ভিশন টার্গেট হিসেবে রাখুন।

## npm install সতর্কতা (ERESOLVE / peer / deprecated)

আপনি `npm install -g omniroute` চালালে `npm warn ERESOLVE`, peer-dependency বিজ্ঞপ্তি এবং `deprecated` বার্তার মতো অসংখ্য সতর্কতা দেখতে পারেন। **এগুলো প্রত্যাশিত এবং ক্ষতিকর নয়।** আউটপুটে `added <N> packages` দেখলে বুঝবেন আপনার ইনস্টলেশন সফল হয়েছে।

OmniRoute-এর নিয়ন্ত্রণের বাইরে থাকা তৃতীয়-পক্ষের প্যাকেজগুলোর পুরোনো peer-dependency range থেকে এই সতর্কতাগুলো আসে:

1. **`marked-terminal`-এর প্রয়োজন `marked >=1 <16`, কিন্তু পাওয়া গেছে `marked@18`** — বাস্তবে এটি ঠিকভাবেই কাজ করে; upstream peer range-টি শুধু পুরোনো।
2. **`deprecated prebuild-install@7.1.3`** — এটি একটি transitive native-binary fetch helper। এটি pinned `wreq-js` transport binding ইনস্টল করতে
   ব্যবহৃত হয় না এবং web-cookie provider transport সেটআপ ব্যর্থ হয়েছে—এমনটিও নির্দেশ করে না।

**কোনো পদক্ষেপের প্রয়োজন নেই** — upstream প্যাকেজগুলো fork না করে সতর্কতাগুলো সম্পূর্ণভাবে বন্ধ করা সম্ভব নয়।

### Avast/AVG `MD:HttpRequest-inf[Susp]` দেখিয়ে `README.md` কোয়ারেন্টাইন করে

**এটি একটি ফলস পজিটিভ। কোনো কিছু সংক্রমিত নয় এবং কোনো পদক্ষেপ নেওয়ার প্রয়োজন নেই।**

Avast ও AVG এমন একটি হিউরিস্টিক চালায়, যা অনেকগুলো HTTP অনুরোধের মতো দেখতে লিংক থাকা
প্লেইন-টেক্সট/Markdown ফাইলকে শনাক্ত করে। OmniRoute-এর `README.md` npm প্যাকেজের মধ্যে অন্তর্ভুক্ত থাকে (এটি
`package.json` → `files`-এ তালিকাভুক্ত), তাই গ্লোবাল ইনস্টলের সময় এটি `node_modules/omniroute/README.md`-এ
স্থাপিত হয় — এবং এতে প্রায় ১৫টি `http://localhost:20128/...` উদাহরণ রয়েছে (MCP
HTTP/SSE এন্ডপয়েন্ট, A2A `.well-known` URL এবং `curl` স্নিপেট)। এত বেশি লিংকের ঘনত্বই
হিউরিস্টিকটি সক্রিয় করার জন্য যথেষ্ট।

যদি এটি সম্প্রতি শুরু হয়ে থাকে: ফাইলটির ধরন বদলায়নি। README-তে
এন্ডপয়েন্টের টেবিল (MCP HTTP + SSE + A2A যোগ করা হয়েছে) এবং আরও `curl` উদাহরণ
যুক্ত হওয়ায় এটি সীমা অতিক্রম করেছে।

ফাইলটি নিষ্ক্রিয় ডকুমেন্টেশন, এতে কোনো এক্সিকিউটেবল কনটেন্ট নেই। আপনি নিরাপদে এটিকে
কোয়ারেন্টাইন থেকে পুনরুদ্ধার করতে পারেন।

**করণীয়:**

1. **নোটিফিকেশন বন্ধ করুন** — আপনার অ্যান্টিভাইরাসে ইনস্টল ডিরেক্টরিটি বাদ দিন
   (Avast: Settings → Exceptions); সেখানে আপনার গ্লোবাল `node_modules` পাথ এবং/অথবা
   OmniRoute ডেটা ডিরেক্টরি (`~/.omniroute/`) যোগ করুন।
2. **ফলস পজিটিভ রিপোর্ট করুন** — <https://www.avast.com/false-positive-file-form.php>,
   এবং কোয়ারেন্টাইনে থাকা `README.md` সংযুক্ত করুন। এটিই এমন সমাধান যা সবাইকে সাহায্য করে, কারণ এটি
   একটি টেক্সট ফাইলের ক্ষেত্রে বিক্রেতার হিউরিস্টিকের অতিরিক্ত প্রতিক্রিয়া।

**কেন আমরা নিজেদের দিক থেকে এটি "ঠিক" করি না:** সব উদাহরণই `http://localhost`, এবং
সেলফ-সাইনড সার্টিফিকেটের ঝামেলা ছাড়া localhost-এ `https` ব্যবহার করা যায় না। একটি বিক্রেতার হিউরিস্টিক
এড়ানোর জন্য ডকুমেন্টেশন বিকৃত করলে স্ক্যানারের একটি বাগকে সন্তুষ্ট করতে গিয়ে প্রত্যেক পাঠকই ক্ষতিগ্রস্ত হবেন।

### Kaspersky ডেস্কটপ অ্যাপটিকে `PDM:Trojan.Win32.Generic` হিসেবে শনাক্ত করে

  নেটিভ বাইন্ডিং (`<arch>` হলো `x64` অথবা `arm64`)।

**কেন এটি সক্রিয় হয়:** Windows ইনস্টলারটি **এখনো কোড-সাইন করা হয়নি**, তাই একটি আনসাইনড NSIS
ইনস্টলারের কোনো রেপুটেশন নেই এবং আচরণগত হিউরিস্টিক সর্বোচ্চ আগ্রাসীভাবে চলে। এর সঙ্গে
একটি বান্ডল করা নেটিভ DLL এবং `%LOCALAPPDATA%\Programs\OmniRoute`-এর অধীনে লেখা শত শত `.js` ফাইল
(Next.js স্ট্যান্ডঅ্যালোন বিল্ডের হ্যাশ-সাফিক্সযুক্ত প্যাকেজ ডিরেক্টরিসহ) মিলে
হিউরিস্টিকটি সক্রিয় করার জন্য যথেষ্ট। কোড সাইনিংয়ের পরিকল্পনা রয়েছে;
তা কার্যকর না হওয়া পর্যন্ত নতুন রিলিজগুলোতেও এটি পুনরাবৃত্ত হতে পারে।

**করণীয়:**

1. **প্রথমে আপনার ডাউনলোড যাচাই করুন** (এতে ফাইলটি পরিবর্তন করা হয়েছে কি না, তা নিশ্চিত হওয়া যায়)। প্রতিটি রিলিজে
   `latest.yml` প্রকাশ করা হয়, যার `sha512` ফিল্ডটি (base64) `OmniRoute.Setup.<version>.exe`
   ইনস্টলারকে কভার করে। PowerShell-এ, ইনস্টলার থাকা ফোল্ডার থেকে:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   আউটপুটটি অবশ্যই `latest.yml` → `sha512`-এর সঙ্গে মিলতে হবে। না মিললে ফাইলটি মুছে দিন এবং
   শুধুমাত্র [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) থেকে পুনরায় ডাউনলোড করুন।
2. **পুনরুদ্ধার করুন + বাদ দিন** — কোয়ারেন্টাইন থেকে রোল ব্যাক করা আইটেমগুলো পুনরুদ্ধার করুন এবং
   `%LOCALAPPDATA%\Programs\OmniRoute`-এর জন্য একটি এক্সক্লুশন যোগ করুন (Kaspersky → Settings → Threats and Exclusions),
   তারপর পুনরায় ইনস্টল করুন।
3. **ফলস পজিটিভ রিপোর্ট করুন** — <https://opentip.kaspersky.com/>। ব্যবহারকারীর জমা দেওয়া FP
   রিপোর্ট সত্যিই অ্যালাউলিস্টিং দ্রুততর করে।

## Node.js সামঞ্জস্যতা

<a name="nodejs-compatibility"></a>

### লগইন পৃষ্ঠা ক্র্যাশ করে বা "Module self-registration" ত্রুটি দেখায়

**কারণ:** আপনি OmniRoute-এর অনুমোদিত নিরাপদ রানটাইমের ন্যূনতম সীমার বাইরে থাকা একটি Node.js সংস্করণ চালাচ্ছেন। সবচেয়ে সাধারণ ক্ষেত্রে, Node 22 বা 24-এর এমন একটি পুরোনো প্যাচ স্তর চালানো হয়, যা OmniRoute-এর প্রয়োজনীয় প্যাচকৃত নিরাপত্তা সীমার নিচে।

**লক্ষণসমূহ:**

- লগইন পৃষ্ঠায় একটি ফাঁকা স্ক্রিন বা সার্ভার ত্রুটি দেখা যায়
- কনসোলে `Error: Module did not self-register` বা অনুরূপ নেটিভ বাইন্ডিং ত্রুটি দেখা যায়
- রানটাইমটি সমর্থিত নিরাপত্তা নীতির বাইরে থাকলে লগইন পৃষ্ঠায় আপনার Node সংস্করণসহ একটি **কমলা সতর্কতা ব্যানার** দেখা যায়

**সমাধান:**

1. একটি সমর্থিত Node.js LTS রিলিজ ইনস্টল করুন (প্রস্তাবিত: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. আপনার সংস্করণ যাচাই করুন: 24.x LTS লাইনে `node --version`-এ `v24.0.0` বা তার নতুন সংস্করণ দেখা উচিত
3. OmniRoute পুনরায় ইনস্টল করুন: `npm install -g omniroute`
4. পুনরায় চালু করুন: `omniroute`

> **সমর্থিত নিরাপদ সংস্করণসমূহ:** `>=22.22.2 <23` অথবা `>=24.0.0 <27`। Node.js 24.x LTS (Krypton) এবং Node.js 26 সম্পূর্ণভাবে সমর্থিত।

### npm v11+: `better-sqlite3` ইনস্টল হয়নি (মডিউল খুঁজে পাওয়া যায়নি)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**কারণ:** npm v11 (Node.js 24+-এর সঙ্গে সরবরাহ করা হয়) ডিফল্টভাবে ঐচ্ছিক
ডিপেন্ডেন্সির ইনস্টল স্ক্রিপ্ট ব্লক করে। যেহেতু `better-sqlite3` `optionalDependencies`-এ তালিকাভুক্ত
এবং এর জন্য নেটিভ কম্পাইলেশন (`node-gyp rebuild`) প্রয়োজন, তাই npm কোনো বার্তা ছাড়াই এটি এড়িয়ে যায়।

**লক্ষণসমূহ:**

- চালু হওয়ার সময় `Cannot find module 'better-sqlite3'` ত্রুটিসহ সার্ভার ক্র্যাশ করে
- `ls node_modules/better-sqlite3` চালালে "No such file or directory" দেখা যায়
- `npm ls better-sqlite3` চালালে `(empty)` দেখা যায়

**সমাধান:**

1. ইনস্টল স্ক্রিপ্টগুলো অনুমোদন করে পুনরায় ইনস্টল করুন:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. অথবা প্রিবিল্ট প্যাকেজটি ম্যানুয়ালি ইনস্টল করুন:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. এটি কাজ করছে কিনা যাচাই করুন: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**কারণ:** গ্লোবাল `npm install -g omniroute` চালানোর পরে, প্যাকেজের ভেতরের `better-sqlite3` নেটিভ বাইনারিটি স্থানীয়ভাবে চলমান আর্কিটেকচার বা Node.js ABI-এর চেয়ে ভিন্ন কোনো আর্কিটেকচার বা ABI-এর জন্য কম্পাইল করা থাকতে পারে। প্রিবিল্ট বাইনারি আপনার পরিবেশের সঙ্গে না মিললে macOS-এ (Apple Silicon এবং Intel উভয় ক্ষেত্রেই) এটি সাধারণভাবে ঘটে।

**লক্ষণসমূহ:**

- চালু হওয়ার সঙ্গে সঙ্গেই একটি `dlopen` ত্রুটিসহ সার্ভার ব্যর্থ হয়
- ত্রুটিতে `slice is not valid mach-o file` থাকে
- সম্পূর্ণ উদাহরণ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**সমাধান — আপনার স্থানীয় পরিবেশের জন্য পুনরায় বিল্ড করুন (Node.js ডাউনগ্রেড করার প্রয়োজন নেই):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **দ্রষ্টব্য:** এটি আপনার স্থানীয় Node.js সংস্করণ এবং CPU আর্কিটেকচারের বিপরীতে নেটিভ বাইন্ডিংটি পুনরায় কম্পাইল করে, ফলে বাইনারির অসামঞ্জস্য সমাধান হয়। আনুষ্ঠানিকভাবে সমর্থিত রানটাইম পরিসর হলো **`>=22.22.2 <23` অথবা `>=24.0.0 <27`** (`src/shared/utils/nodeRuntimeSupport.ts`-এ `SUPPORTED_NODE_RANGE`, যা `package.json`-এর `engines` ফিল্ডের সঙ্গে সামঞ্জস্যপূর্ণ)। Node.js 24.x LTS (Krypton) এবং Node.js 26, `better-sqlite3` v12.x-এর সঙ্গে সম্পূর্ণভাবে সমর্থিত।

## প্রক্সি-সংক্রান্ত সমস্যা

<a name="proxy-issues"></a>

### প্রোভাইডার যাচাইকরণে "fetch failed" দেখায়

**কারণ:** API কী যাচাইকরণ এন্ডপয়েন্টটি (`POST /api/providers/validate`) আগে প্রক্সি কনফিগারেশন এড়িয়ে যেত, ফলে যেসব পরিবেশে প্রক্সি রাউটিং প্রয়োজন সেখানে ব্যর্থতা ঘটত।

**সমাধান (v3.5.5+):** এটি এখন ঠিক করা হয়েছে। প্রোভাইডার যাচাইকরণ এখন `runWithProxyContext`-এর মাধ্যমে রাউট হয় এবং স্বয়ংক্রিয়ভাবে প্রোভাইডার-স্তরের ও গ্লোবাল প্রক্সি সেটিংস অনুসরণ করে।

### টোকেন হেলথ চেক "fetch failed" ত্রুটিসহ ব্যর্থ হয়

**কারণ:** ব্যাকগ্রাউন্ড OAuth টোকেন রিফ্রেশ প্রতিটি সংযোগের জন্য আলাদাভাবে প্রক্সি কনফিগারেশন নির্ধারণ করছিল না।

**সমাধান (v3.5.5+):** টোকেন হেলথ চেক শিডিউলার এখন রিফ্রেশের চেষ্টা করার আগে প্রতিটি সংযোগের জন্য প্রক্সি কনফিগারেশন নির্ধারণ করে। v3.5.5+ সংস্করণে আপডেট করুন।

### SOCKS5 প্রক্সি "invalid onRequestStart method" ত্রুটি দেয়

**কারণ:** Node.js 22-এ undici@8 ডিসপ্যাচারটি Node-এর বিল্ট-ইন `fetch()` ইমপ্লিমেন্টেশনের সঙ্গে সামঞ্জস্যপূর্ণ নয়।

**সমাধান (v3.5.5+):** কোনো প্রক্সি ডিসপ্যাচার সক্রিয় থাকলে OmniRoute এখন undici-এর নিজস্ব `fetch()` ফাংশন ব্যবহার করে, যা সামঞ্জস্যপূর্ণ আচরণ নিশ্চিত করে। v3.5.5+ সংস্করণে আপডেট করুন।

### WSL-এর অধীনে MITM প্রক্সি: Windows হোস্টের ডেস্কটপ অ্যাপগুলো ইন্টারসেপ্ট হয় না

**কারণ:** MITM প্রক্সি ও এর CA সার্টিফিকেট সেই পরিবেশে ইনস্টল হয় যেখানে OmniRoute চলে। WSL-এর অধীনে সেই পরিবেশটি হলো Linux গেস্ট, কিন্তু AI ডেস্কটপ অ্যাপগুলো (Kiro, Trae, Copilot, Zed, …) চলে Windows হোস্টে। হোস্ট অ্যাপগুলো গেস্টের সার্টিফিকেট স্টোরকে বিশ্বাস করে না এবং গেস্টের সিস্টেম প্রক্সির মাধ্যমে রাউট হয় না, তাই সেখানে ডেস্কটপ ইন্টারসেপশন সক্রিয় হয় না।

**সুপারিশ:** আপনি যেসব ডেস্কটপ অ্যাপ ইন্টারসেপ্ট করতে চান, OmniRoute-কে সেই অ্যাপগুলোর একই OS-এ নেটিভভাবে চালান (Windows অ্যাপের জন্য Windows; macOS/Linux-এর ক্ষেত্রেও একইভাবে)। হোস্ট অ্যাপগুলোকে লক্ষ্য করে OmniRoute-কে WSL-এর ভেতরে চালু রাখতে হলে Windows হোস্টে জেনারেট করা CA সার্টিফিকেটকে ম্যানুয়ালি বিশ্বস্ত হিসেবে যুক্ত করতে হবে এবং প্রতিটি হোস্ট অ্যাপের নেটওয়ার্ক/প্রক্সি সেটিংসকে WSL প্রক্সি এন্ডপয়েন্টের দিকে নির্দেশ করতে হবে—এটি একটি অসমর্থিত ও ভঙ্গুর সেটআপ।

## ক্লাউড-সংক্রান্ত সমস্যা

### ক্লাউড সিঙ্ক ত্রুটি

1. যাচাই করুন যে `BASE_URL` আপনার চলমান ইনস্ট্যান্সকে নির্দেশ করছে (যেমন, `http://localhost:20128`)
2. যাচাই করুন যে `CLOUD_URL` আপনার ক্লাউড এন্ডপয়েন্টকে নির্দেশ করছে (যেমন, `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` মানগুলো সার্ভার-সাইড মানগুলোর সঙ্গে সামঞ্জস্যপূর্ণ রাখুন

### ক্লাউডে `stream=false` ব্যবহার করলে 500 ফেরত আসে

**লক্ষণ:** নন-স্ট্রিমিং কলের ক্ষেত্রে ক্লাউড এন্ডপয়েন্টে `Unexpected token 'd'...` দেখা যায়।

**কারণ:** ক্লায়েন্ট JSON প্রত্যাশা করলেও আপস্ট্রিম SSE পেলোড ফেরত দেয়।

**বিকল্প সমাধান:** ক্লাউডে সরাসরি কলের জন্য `stream=true` ব্যবহার করুন। লোকাল রানটাইমে SSE→JSON ফলব্যাক অন্তর্ভুক্ত রয়েছে।

### ক্লাউডে Connected দেখালেও "Invalid API key" বলে

1. লোকাল ড্যাশবোর্ড (`/api/keys`) থেকে একটি নতুন কী তৈরি করুন
2. ক্লাউড সিঙ্ক চালান: Enable Cloud → Sync Now
3. পুরোনো/সিঙ্ক না হওয়া কীগুলো ক্লাউডে এখনও `401` ফেরত দিতে পারে

## Docker-সংক্রান্ত সমস্যা

### Docker IPv6 / সংযোগ রিসেট

<a name="docker-ipv6"></a>

**লক্ষণ:** `curl http://localhost:20128/v1/models` চালালে `curl: (56) Recv failure: Connection reset by peer` ফেরত আসে। ড্যাশবোর্ড এবং প্রমাণীকরণবিহীন এন্ডপয়েন্টগুলো কাজ করে, কিন্তু প্রমাণীকৃত এন্ডপয়েন্টগুলো ব্যর্থ হয়—এটি প্রমাণীকরণের সমস্যা মনে হলেও আসলে তা নয়।

**কারণ:** `docker run -p 20128:20128` একই সঙ্গে `0.0.0.0` (IPv4) এবং `::` (IPv6)-এ পোর্ট প্রকাশ করে, কিন্তু কনটেইনারের ভেতরের প্রসেসটি শুধু IPv4-এ শোনে। যেসব হোস্টে `localhost` প্রথমে `::1`-এ রিজলভ হয়, সেখানে সংযোগটি প্রকাশিত IPv6 পোর্টে পৌঁছায়, যার পেছনে কোনো লিসেনার নেই → সংযোগ রিসেট হয়।

**সমাধান:**

1. **দ্রুত শনাক্তকরণ:** `curl -4 http://localhost:20128/v1/models` চালান। `-4` দিয়ে কাজ করলে, কিন্তু এটি ছাড়া ব্যর্থ হলে, আপনার IPv6 বাইন্ডে অসামঞ্জস্য রয়েছে।
2. **স্থায়ী সমাধান:** আপনার `docker run` কমান্ডে `-p 127.0.0.1:20128:20128` ব্যবহার করে স্পষ্টভাবে IPv4-এ বাইন্ড করুন:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   এটি IPv4 বাইন্ড বাধ্যতামূলক করে এবং সব হোস্ট ইন্টারফেসে প্রক্সি প্রকাশ করাও এড়ায়।

## ডিবাগিং

### লগ ফাইল সক্রিয় করুন

আপনার `.env` ফাইলে `APP_LOG_TO_FILE=true` সেট করুন। অ্যাপ্লিকেশন লগগুলো `logs/`-এর অধীনে লেখা হয়।
সেটিংসে কল লগ পাইপলাইন সক্রিয় থাকলে রিকোয়েস্ট আর্টিফ্যাক্টগুলো `${DATA_DIR}/call_logs/`-এর অধীনে সংরক্ষণ করা হয়।
পাইপলাইন ক্যাপচার সক্রিয় থাকলে স্ট্রিম চাঙ্ক পেলোড বাদ দিতে `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` সেট করুন, অথবা KB-তে আর্টিফ্যাক্টের সীমা পরিবর্তন করতে `CALL_LOG_PIPELINE_MAX_SIZE_KB` সমন্বয় করুন।

### প্রোভাইডারের স্বাস্থ্য পরীক্ষা করুন

```bash
# স্বাস্থ্য ড্যাশবোর্ড
http://localhost:20128/dashboard/health

# API স্বাস্থ্য পরীক্ষা
curl http://localhost:20128/api/monitoring/health
```

### রানটাইম স্টোরেজ

- প্রধান স্টেট: `${DATA_DIR}/storage.sqlite` (প্রোভাইডার, কম্বো, অ্যালিয়াস, কী, সেটিংস)
- ব্যবহার: `storage.sqlite`-এর SQLite টেবিলগুলো (`usage_history`, `call_logs`, `proxy_logs`) + ঐচ্ছিক `${DATA_DIR}/call_logs/`
- অ্যাপ্লিকেশন লগ: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` হলে)
- কল লগ আর্টিফ্যাক্ট: কল লগ পাইপলাইন সক্রিয় থাকলে `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs পৃষ্ঠার **Clean history** অ্যাকশনটি `call_logs`, লিগ্যাসি
`request_detail_logs`, এবং লোকাল `${DATA_DIR}/call_logs/` আর্টিফ্যাক্ট ডিরেক্টরি পরিষ্কার করে।

## সার্কিট ব্রেকার সংক্রান্ত সমস্যা

### প্রোভাইডার OPEN অবস্থায় আটকে আছে

কোনো প্রোভাইডারের সার্কিট ব্রেকার OPEN থাকলে, কুলডাউন শেষ না হওয়া পর্যন্ত অনুরোধগুলো ব্লক করা হয়।

**সমাধান:**

1. **Dashboard → Settings → Resilience**-এ যান
2. প্রভাবিত প্রোভাইডারের সার্কিট ব্রেকার কার্ডটি পরীক্ষা করুন
3. সব ব্রেকার সাফ করতে **Reset All**-এ ক্লিক করুন, অথবা কুলডাউন শেষ হওয়া পর্যন্ত অপেক্ষা করুন
4. রিসেট করার আগে নিশ্চিত করুন যে প্রোভাইডারটি সত্যিই উপলভ্য

### প্রোভাইডার বারবার সার্কিট ব্রেকার ট্রিগার করছে

যদি কোনো প্রোভাইডার বারবার OPEN অবস্থায় প্রবেশ করে:

1. ব্যর্থতার ধরন দেখতে **Dashboard → Health → Provider Health** পরীক্ষা করুন
2. **Settings → Resilience → Provider Profiles**-এ গিয়ে ব্যর্থতার থ্রেশহোল্ড বাড়ান
3. প্রোভাইডারটি API সীমা পরিবর্তন করেছে কি না বা পুনরায় প্রমাণীকরণের প্রয়োজন কি না, তা পরীক্ষা করুন
4. লেটেন্সি টেলিমেট্রি পর্যালোচনা করুন — উচ্চ লেটেন্সির কারণে টাইমআউট-ভিত্তিক ব্যর্থতা ঘটতে পারে

## অডিও ট্রান্সক্রিপশন সংক্রান্ত সমস্যা

### "Unsupported model" ত্রুটি

- এমন একটি মডেল আইডি ব্যবহার করুন যার প্রথম সেগমেন্টটি এমন কোনো প্রোভাইডার, যার জন্য আপনার ক্রেডেনশিয়াল রয়েছে (`openai/whisper-1`, `openrouter/deepgram/nova-3`)। শুধু `deepgram/nova-3` ব্যবহার করতে একটি নেটিভ Deepgram কী প্রয়োজন।
- **Dashboard → Providers**-এ প্রোভাইডারটি সংযুক্ত আছে কি না যাচাই করুন

### ট্রান্সক্রিপশন ফাঁকা আসে বা ব্যর্থ হয়

- সমর্থিত অডিও ফরম্যাটগুলো পরীক্ষা করুন: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ফাইলের আকার প্রোভাইডারের সীমার মধ্যে আছে কি না যাচাই করুন (সাধারণত < 25MB)
- প্রোভাইডার কার্ডে প্রোভাইডারের API কী বৈধ কি না পরীক্ষা করুন

| **Live Monitor** | অনিয়মিত অনুবাদ সমস্যা ধরতে রিয়েল-টাইম অনুরোধ প্রবাহ পর্যবেক্ষণ করুন                                         |

### ফরম্যাট সংক্রান্ত সাধারণ সমস্যা

- **থিঙ্কিং ট্যাগ দেখা যাচ্ছে না** — লক্ষ্য প্রোভাইডার থিঙ্কিং সমর্থন করে কি না এবং থিঙ্কিং বাজেট সেটিং পরীক্ষা করুন
- **টুল কল বাদ পড়ছে** — কিছু ফরম্যাট অনুবাদ অসমর্থিত ফিল্ড বাদ দিতে পারে; Playground মোডে যাচাই করুন
- **সিস্টেম প্রম্পট অনুপস্থিত** — Claude এবং Gemini সিস্টেম প্রম্পট ভিন্নভাবে পরিচালনা করে; অনুবাদের আউটপুট পরীক্ষা করুন
- **SDK অবজেক্টের পরিবর্তে কাঁচা স্ট্রিং ফেরত দেয়** — v1.x-এ সমাধান করা হয়েছে; রেসপন্স স্যানিটাইজার অ-মানক ফিল্ড (`x_groq`, `usage_breakdown` ইত্যাদি) সরিয়ে দেয়, যেগুলোর কারণে OpenAI SDK Pydantic যাচাইকরণ ব্যর্থ হয়। v3.x+ সংস্করণেও এটি দেখা গেলে, অনুগ্রহ করে একটি ইস্যু দায়ের করুন।
- **GLM/ERNIE `system` রোল প্রত্যাখ্যান করে** — v1.x-এ সমাধান করা হয়েছে; অসামঞ্জস্যপূর্ণ মডেলগুলোর ক্ষেত্রে রোল নরমালাইজার স্বয়ংক্রিয়ভাবে সিস্টেম বার্তাগুলোকে ইউজার বার্তার সঙ্গে একীভূত করে। v3.x+ সংস্করণেও এটি দেখা গেলে, অনুগ্রহ করে একটি ইস্যু দায়ের করুন।
- **`developer` রোল শনাক্ত হচ্ছে না** — v1.x-এ সমাধান করা হয়েছে; OpenAI ব্যতীত অন্যান্য প্রোভাইডারের জন্য এটি স্বয়ংক্রিয়ভাবে `system`-এ রূপান্তরিত হয়। v3.x+ সংস্করণেও এটি দেখা গেলে, অনুগ্রহ করে একটি ইস্যু দায়ের করুন।
- **Gemini-এর সঙ্গে `json_schema` কাজ করছে না** — v1.x-এ সমাধান করা হয়েছে; `response_format` এখন Gemini-এর `responseMimeType` + `responseSchema`-এ রূপান্তরিত হয়। v3.x+ সংস্করণেও এটি দেখা গেলে, অনুগ্রহ করে একটি ইস্যু দায়ের করুন।

## স্থিতিস্থাপকতা সেটিংস

### স্বয়ংক্রিয় রেট-লিমিট সক্রিয় হচ্ছে না

- স্বয়ংক্রিয় রেট-লিমিট শুধু API key প্রদানকারীদের ক্ষেত্রে প্রযোজ্য (OAuth/subscription-এর ক্ষেত্রে নয়)
- যাচাই করুন যে **Settings → Resilience → Provider Profiles**-এ স্বয়ংক্রিয় রেট-লিমিট সক্রিয় রয়েছে
- প্রদানকারী `429` স্ট্যাটাস কোড বা `Retry-After` হেডার ফেরত দেয় কি না পরীক্ষা করুন

### এক্সপোনেনশিয়াল ব্যাকঅফ টিউন করা

প্রদানকারী প্রোফাইলগুলোতে এই সেটিংস সমর্থিত:

- **Base delay** — প্রথম ব্যর্থতার পর প্রাথমিক অপেক্ষার সময় (ডিফল্ট: 1s)
- **Max delay** — অপেক্ষার সময়ের সর্বোচ্চ সীমা (ডিফল্ট: 30s)
- **Multiplier** — প্রতিটি ধারাবাহিক ব্যর্থতায় বিলম্ব কতটা বাড়বে (ডিফল্ট: 2x)

### অ্যান্টি-থান্ডারিং হার্ড

অনেক সমসাময়িক অনুরোধ কোনো রেট-লিমিটেড প্রদানকারীর কাছে গেলে, OmniRoute অনুরোধগুলোকে ধারাবাহিকভাবে প্রক্রিয়া করতে এবং ক্রমবর্ধমান ব্যর্থতা ঠেকাতে mutex + স্বয়ংক্রিয় রেট-লিমিটিং ব্যবহার করে। API key প্রদানকারীদের জন্য এটি স্বয়ংক্রিয়।

### চ্যাট অনুরোধ 503 / chat_admission_busy সহ ব্যর্থ হয়

**লক্ষণ:**

- চ্যাট কমপ্লিশনস এন্ডপয়েন্ট একটি পুনরায় চেষ্টা-যোগ্য `503` প্রতিক্রিয়া ফেরত দেয়, যার ত্রুটি কোড হলো
  `chat_admission_busy`।
- প্রতিক্রিয়ায় `Retry-After` অন্তর্ভুক্ত থাকে। #12135 থেকে মানটি পর্যবেক্ষণ করা
  দখলের মাত্রা থেকে নির্ধারিত হয় — অনুরোধটি ইতিমধ্যে যতক্ষণ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  উইন্ডোতে অপেক্ষা করেছে এবং বর্তমান হেভিওয়েট লিজগুলো যতক্ষণ ধরে রাখা হয়েছে, এই দুটির মধ্যে
  বড় মানটি — পূর্ণ সেকেন্ডে ঊর্ধ্বমুখী রাউন্ড করা হয় এবং সর্বোচ্চ 60-এ সীমাবদ্ধ থাকে। নিষ্ক্রিয় গেটে এটি
  ঐতিহাসিক ন্যূনতম সীমা বজায় রাখে: বাইট-ভিত্তিক পথে 2 সেকেন্ড, স্ট্রাকচার-ভিত্তিক পথে 1 সেকেন্ড
  (যার মধ্যে `reason: "structure_limit"`-ও অন্তর্ভুক্ত)।
- অন্য একটি হেভিওয়েট চ্যাট বা দীর্ঘমেয়াদি স্ট্রিমিং প্রতিক্রিয়া এখনও
  প্রক্রিয়াধীন থাকলে এটি ঘটতে পারে।

বাইট-ভিত্তিক প্রতিক্রিয়ার বডি হলো:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

স্ট্রাকচার-ভিত্তিক প্রতিক্রিয়ায় একই টাইপ ও কোড ব্যবহৃত হয়, সঙ্গে বার্তা
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
এবং `reason: "structure_limit"`।
ডিফল্ট থ্রেশহোল্ডে, কোনো অনুরোধে অন্তত `200`টি বার্তা,
অন্তত `64`টি টুল বা অন্তত `32,000`টি আনুমানিক টোকেন থাকলে, অথবা সীমাবদ্ধ স্ট্রাকচার অনুমান
`10,000`টি পরিদর্শিত নোড বা `12` গভীরতার সীমা নিঃশেষ করলে, অনুরোধটি স্ট্রাকচারগতভাবে হেভিওয়েট হয়।

**কারণ:** এটি OmniRoute-এর অভ্যন্তরে ইচ্ছাকৃত লোড শেডিং, কোনো আপস্ট্রিম-প্রদানকারীর ব্যর্থতা নয়।
একটি বড় অনুরোধের বডি ধরে রাখা ও পার্স করার আগে সীমিত হেভিওয়েট সক্ষমতা সংরক্ষণ করতে
প্রতিটি প্রসেস একটি প্রসেস-লোকাল গার্ড ব্যবহার করে। একটি SSE
প্রতিক্রিয়ার পুরো জীবনকালজুড়ে হেভিওয়েট লিজটি ধরে রাখা হয়।

**#503-fanout:** এই সংশোধনের আগে, হোস্ট মেমোরি নির্বিশেষে গার্ডটি সমসাময়িকতা একটি নির্দিষ্ট অনুরোধ COUNT-এ
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ডিফল্ট `1`) সীমাবদ্ধ করত, ফলে কোডিং-এজেন্ট
ফ্যান-আউট (একাধিক সাবএজেন্ট/CLI, নিয়মিতভাবে 256 KB-এর বেশি বডি) কার্যকর
সমসাময়িকতা কমিয়ে ~1-এ নিয়ে আসত এবং সম্পূর্ণ স্বাভাবিক লোডেও 503 ত্রুটি দিত। গার্ডটি এখন স্বয়ংক্রিয়ভাবে নিজেকে টিউন করে: এটি
প্রসেসের প্রকৃত মেমোরি সীমা থেকে নির্ধারিত একটি স্বয়ংক্রিয়ভাবে উদ্ভূত ইনজেস্ট BYTE বাজেট
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) দ্বারা নিয়ন্ত্রিত হয় এবং এটি একটি লাইভ রিসোর্স-প্রেশার সংকেতও
বিবেচনা করে — ফলে হোস্ট প্রকৃতপক্ষে মেমোরির চাপে থাকলেই এটি লোড কমায়, শুধু একই সময়ে একাধিক
হেভিওয়েট অনুরোধ আসার কারণে নয়। পুরোনো কাউন্ট সীমা (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) এখনও
মানা হয়, তবে শুধু আপনি স্পষ্টভাবে সেটি সেট করলে।

সক্ষমতা ব্যস্ত থাকলে, পুনরায় চেষ্টা-যোগ্য `503` দিয়ে উত্তর দেওয়ার আগে একটি হেভিওয়েট অনুরোধ
কোনো স্লট খালি হওয়ার জন্য সর্বোচ্চ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ডিফল্ট `2000`,
`0` অপেক্ষা নিষ্ক্রিয় করে) পর্যন্ত অপেক্ষা করে। এই সীমাবদ্ধ অপেক্ষা রাখা হয়েছে যাতে একই সময়ে হেভিওয়েট সাব-অনুরোধ
ফ্যান-আউট করা এজেন্ট-ধাঁচের ক্লায়েন্টগুলো (OpenCode, Claude Code, Cursor) তাৎক্ষণিক প্রত্যাখ্যানের কারণে
তাদের সম্পূর্ণ পুনঃচেষ্টার বাজেট শেষ করে কাজের মাঝপথে বন্ধ হয়ে যাওয়ার পরিবর্তে অনুরোধের বিস্ফোরণটিকে
ধারাবাহিকভাবে প্রক্রিয়া করে।
বর্তমান হেভিওয়েট লিজের দখল, নির্ধারিত বাইট বাজেট এবং লাইভ চাপের তীব্রতা
`GET /api/monitoring/health` → `chatAdmission`-এ (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) দেখানো হয় — কোনো env var পরিবর্তনের আগে এগুলো পরীক্ষা করুন।
Settings → Resilience → Request Queue → Concurrent Requests এটি নিয়ন্ত্রণ করে না; ওই সেটিংটি
একটি পৃথক প্রদানকারী অনুরোধ-কিউ ব্যবস্থা নিয়ন্ত্রণ করে।

**সমাধান:**

1. প্রথমে পুনরায় চেষ্টা করুন। ক্লায়েন্টের উচিত `Retry-After` মেনে চলা এবং সঙ্গে সঙ্গে
   অনুরোধটি পুনরাবৃত্তি না করে ব্যাকঅফ ব্যবহার করা।
2. কিছু টিউন করার আগে `/api/monitoring/health` → `chatAdmission` পরীক্ষা করুন। `countCapEnabled:
false` এবং পর্যাপ্ত বড় `maxInflightBytes` বোঝায় যে স্বয়ংক্রিয়ভাবে উদ্ভূত বাজেটটি ইতিমধ্যেই তার
   কাজ করছে; `high`/`critical` মানের `pressureSeverity` বোঝায় যে হোস্টে সত্যিই মেমোরির ঘাটতি রয়েছে —
   এটি কোনো অ্যাডমিশন env var দিয়ে সমাধান করা যাবে না; এর জন্য আরও RAM বা ছোট ওয়ার্কলোড প্রয়োজন।
3. শুধু `/api/monitoring/health` যদি দেখায় যে স্বয়ংক্রিয়ভাবে উদ্ভূত বাজেটটি আপনার হোস্টের জন্য
   সত্যিই খুব ছোট (বিরল — এটি ইতিমধ্যেই কনটেইনার থেকে বেয়ার-মেটাল পর্যন্ত স্কেল করে), তাহলেই
   লিগ্যাসি অনুরোধ-কাউন্ট সীমায় ফিরে না গিয়ে সরাসরি `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` দিয়ে এটি ওভাররাইড করুন।

প্রামাণিক অ্যাডমিশন সেটিংসের জন্য [এনভায়রনমেন্ট-ভেরিয়েবল রেফারেন্স](../reference/ENVIRONMENT.md#4-security--authentication)
দেখুন।

## ঐচ্ছিক RAG / LLM ব্যর্থতা শ্রেণিবিন্যাস (১৬টি সমস্যা)

কিছু OmniRoute ব্যবহারকারী RAG বা এজেন্ট স্ট্যাকের সামনে গেটওয়ে স্থাপন করেন। এসব সেটআপে একটি অদ্ভুত ধরন প্রায়ই দেখা যায়: OmniRoute-কে সুস্থ মনে হয় (প্রোভাইডার সচল, রাউটিং প্রোফাইল ঠিক আছে, কোনো রেট-লিমিট সতর্কতা নেই), কিন্তু চূড়ান্ত উত্তরটি তবুও ভুল হয়।

বাস্তবে এসব ঘটনার কারণ সাধারণত গেটওয়ে নিজে নয়, বরং ডাউনস্ট্রিম RAG পাইপলাইন।

এসব ব্যর্থতা বর্ণনার জন্য একটি অভিন্ন পরিভাষা চাইলে আপনি WFGY ProblemMap ব্যবহার করতে পারেন। এটি MIT লাইসেন্সের অধীন একটি বাহ্যিক টেক্সট রিসোর্স, যেখানে বারবার ঘটা ষোলোটি RAG / LLM ব্যর্থতার ধরন সংজ্ঞায়িত করা হয়েছে। উচ্চপর্যায়ে এটি যেসব বিষয় অন্তর্ভুক্ত করে:

- রিট্রিভাল ড্রিফট এবং ভাঙা কনটেক্সট সীমা
- খালি বা পুরোনো ইনডেক্স এবং ভেক্টর স্টোর
- এমবেডিং ও অর্থগত অসামঞ্জস্য
- প্রম্পট সংযোজন এবং কনটেক্সট উইন্ডো-সংক্রান্ত সমস্যা
- যুক্তির বিপর্যয় এবং অতিরিক্ত আত্মবিশ্বাসী উত্তর
- দীর্ঘ চেইন এবং এজেন্ট সমন্বয় ব্যর্থতা
- মাল্টি-এজেন্ট মেমরি এবং ভূমিকার ড্রিফট
- ডিপ্লয়মেন্ট এবং বুটস্ট্র্যাপ ক্রমবিন্যাসের সমস্যা

ধারণাটি সহজ:

1. কোনো খারাপ প্রতিক্রিয়া তদন্ত করার সময়, এগুলো সংগ্রহ করুন:
   - ব্যবহারকারীর কাজ এবং অনুরোধ
   - OmniRoute-এ ব্যবহৃত রুট বা প্রোভাইডার কম্বো
   - ডাউনস্ট্রিমে ব্যবহৃত যেকোনো RAG কনটেক্সট (রিট্রিভ করা ডকুমেন্ট, টুল কল ইত্যাদি)
2. ঘটনাটিকে এক বা দুটি WFGY ProblemMap নম্বরের (`No.1` … `No.16`) সঙ্গে ম্যাপ করুন।
3. OmniRoute লগের পাশে আপনার নিজস্ব ড্যাশবোর্ড, রানবুক বা ইনসিডেন্ট ট্র্যাকারে নম্বরটি সংরক্ষণ করুন।
4. আপনার RAG স্ট্যাক, রিট্রিভার বা রাউটিং কৌশল পরিবর্তন করতে হবে কি না তা নির্ধারণ করতে সংশ্লিষ্ট WFGY পৃষ্ঠা ব্যবহার করুন।

সম্পূর্ণ টেক্সট এবং বাস্তবসম্মত রেসিপিগুলো এখানে রয়েছে (MIT লাইসেন্স, শুধু টেক্সট):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute-এর পেছনে RAG বা এজেন্ট পাইপলাইন না চালালে আপনি এই অংশটি উপেক্ষা করতে পারেন।

## v3.8.0-এর পরিচিত সমস্যাসমূহ

v3.8.0 রিলিজের জন্য নির্দিষ্ট সমস্যা এবং সেগুলোর বর্তমান সমাধানপদ্ধতি। পরবর্তী কোনো প্যাচে সমাধান এলে এন্ট্রিটি হালনাগাদ করা হবে বা সরিয়ে ফেলা হবে।

### Devin CLI প্রমাণীকরণ ব্যর্থতা

**লক্ষণ:**

- Devin-সমর্থিত টুল আহ্বান করার সময় "Devin CLI not found" বা "auth failed"
- CLI রানটাইম পরীক্ষায় `installed=false` দেখায়

**কারণ:**

- `CLI_DEVIN_BIN` এমন একটি পাথ নির্দেশ করে যার অস্তিত্ব নেই
- হোস্টে Devin CLI ইনস্টল করা নেই

**সমাধান:**

1. আপনার প্ল্যাটফর্মের জন্য Devin CLI ইনস্টল করুন
2. `.env`-এ `CLI_DEVIN_BIN=/usr/local/bin/devin` (অথবা প্রকৃত পাথ) সেট করুন
3. OmniRoute পুনরায় চালু করুন এবং **Dashboard → CLI Tools** থেকে আবার পরীক্ষা করুন

### মডেল কুলডাউন আটকে থাকা (ম্যানুয়াল রিসেট)

**লক্ষণ:**

- মেয়াদ শেষ হওয়ার সময় পেরিয়ে যাওয়ার পরও একটি মডেল কুলডাউন তালিকায় থেকে যায়
- টাইমস্ট্যাম্প অতীতে হওয়া সত্ত্বেও কম্বো রাউটিংয়ে অনুরোধগুলো মডেলটি এড়িয়ে যায়

**ম্যানুয়াল রিসেট:**

- **Dashboard:** **Settings → Model Cooldowns** → প্রভাবিত কার্ডে **Re-enable** ক্লিক করুন
- **API:** ম্যানেজমেন্ট অথ হেডারসহ `DELETE /api/resilience/model-cooldowns`

### Command Code প্রোভাইডার সংযোগ 403 ত্রুটিসহ ব্যর্থ হয়

**লক্ষণ:**

- Command Code প্রোভাইডার সংযোগ পরীক্ষা করার সময় 403
- নতুন করে যোগ করার পর প্রোভাইডার কার্ডে "unauthorized" দেখায়

**কারণ:** OAuth প্রবাহ সম্পূর্ণ হয়নি (কলব্যাক পাওয়া যায়নি বা টোকেন সংরক্ষিত হয়নি)।

**সমাধান:**

- OAuth প্রবাহ পুনরায় ট্রিগার করতে CLI থেকে `omniroute providers` চালান, অথবা
- **Dashboard → Providers → Command Code → Reconnect** থেকে OAuth আবার চালান

### ModelScope অতিরিক্ত আক্রমণাত্মক 429 কুলডাউন দেয়

**লক্ষণ:**

- অল্পসংখ্যক অনুরোধের আকস্মিক চাপের পর ModelScope-এ খুব সংক্ষিপ্ত বা তাৎক্ষণিক কুলডাউন
- প্রত্যাশার চেয়ে আগেই কম্বো রাউটিং ModelScope এড়িয়ে যায়

**কারণ:** ModelScope প্রোভাইডার-নির্দিষ্ট `Retry-After` হেডার পাঠায়। v3.8.0-এ এসব হেডারের জন্য বিশেষ হ্যান্ডলিং রয়েছে, তাই পুরোনো সংস্করণগুলো এগুলোকে সাধারণ রেট-লিমিট নির্দেশনা হিসেবে ভুলভাবে ব্যাখ্যা করে।

**সমাধান:**

- আপনি v3.8.0 বা পরবর্তী সংস্করণে আছেন তা নিশ্চিত করুন
- **Settings → Resilience**-এর অধীনে `useUpstream429BreakerHints` টগলটি সক্রিয় আছে কি না যাচাই করুন

### প্রোডাকশনে OMNIROUTE_WS_BRIDGE_SECRET অনুপস্থিত

**লক্ষণ:**

- রিমোট প্রোডাকশন হোস্টে চলার সময় প্রতিটি Codex/Responses WebSocket ব্রিজ অনুরোধে 401
- সংযোগের পরপরই WebSocket ব্রিজ হ্যান্ডশেক বন্ধ হয়ে যায়

**কারণ:** প্রোডাকশন এনভায়রনমেন্টে `OMNIROUTE_WS_BRIDGE_SECRET` এনভায়রনমেন্ট ভেরিয়েবলটি অনুপস্থিত।

**সমাধান:**

1. একটি র্যান্ডম সিক্রেট তৈরি করুন: `openssl rand -hex 32`
2. প্রোডাকশন সার্ভারের এনভায়রনমেন্টে `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` সেট করুন (এবং ব্রিজের সঙ্গে যোগাযোগকারী যেকোনো ক্লায়েন্টেও)
3. OmniRoute পুনরায় চালু করুন

### Responses API: ব্যাকগ্রাউন্ড মোড সিঙ্ক্রোনাসে অবনমিত হয়েছে

**লক্ষণ:**

- সতর্কতা লগ হয়: `background mode degraded to synchronous`
- একটি `background: true` অনুরোধ ব্যাকগ্রাউন্ড জব হ্যান্ডেলের পরিবর্তে স্বাভাবিক সিঙ্ক্রোনাস প্রতিক্রিয়া দেয়

**কারণ:** v3.8.0-এ Responses API-র `background: true` ইচ্ছাকৃতভাবে সিঙ্ক্রোনাস এক্সিকিউশনে অবনমিত হয় এবং একই সঙ্গে একটি সতর্কতা পাঠানো হয়। সম্পূর্ণ অ্যাসিঙ্ক ব্যাকগ্রাউন্ড এক্সিকিউশন ভবিষ্যতের একটি ডেলিভারেবল।

**সমাধান:**

- `background` ছাড়া কল করার জন্য ক্লায়েন্টটি সামঞ্জস্য করুন, অথবা
- সম্পূর্ণ অ্যাসিঙ্ক ব্যাকগ্রাউন্ড মোডসহ পরবর্তী কোনো রিলিজের জন্য অপেক্ষা করুন (চেঞ্জলগ অনুসরণ করুন)

## ধীর স্টার্টআপ / প্রস্তুতি টাইমআউট

যদি CLI-তে `⚠ Server did not respond within 60s` দেখানো হয়, কিন্তু সার্ভারটি
আসলে কাজ করে, তাহলে আপনার পরিবেশের জন্য প্রস্তুতি যাচাইয়ের সময়সীমা খুব কম।

এটি সাধারণত Windows-এ (অ্যান্টিভাইরাস, ফাইলসিস্টেম ওয়াচার) অথবা ভারী স্টার্টআপ
ওয়ার্কলোডসহ কন্টেইনারে ঘটে।

**সমাধান — সময়সীমা বাড়ান:**

```bash
# env var-এর মাধ্যমে (পরবর্তী স্টার্টগুলোতেও বহাল থাকে):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # ৩ মিনিট
omniroute serve

# CLI ফ্ল্যাগের মাধ্যমে (একবারের জন্য):
omniroute serve --ready-timeout 180000
```

ডিফল্ট মান 60 000 ms (60 s)। সতর্কবার্তাটি শুধুই তথ্যগত; সার্ভারটি
ব্যাকগ্রাউন্ডে চালু হতে থাকে এবং বুট সম্পন্ন হলে অ্যাক্সেসযোগ্য হবে।

`OMNIROUTE_READY_TIMEOUT_MS`-এর সম্পূর্ণ বিবরণের জন্য
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) দেখুন।
