> যা শিল্পের সর্বোত্তম অনুশীলনের সঙ্গে তুলনা করা হয়েছে, **পাশাপাশি** সব quality
> checkpoint-এর একটি বিস্তৃত ক্যাটালগ এবং একই সিস্টেম যেকোনো প্রকল্পে প্রয়োগের জন্য একটি **tool-agnostic replication plan**।
> এটি 2026-06-16 তারিখে প্রকৃত repository state থেকে তৈরি করা হয়েছে (স্মৃতি থেকে নয়)।
>
> Benchmark: OWASP DSOMM · OpenSSF Scorecard · SLSA · SonarQube "Clean as You Code" ·
> Quality-Ratchet pattern · DORA 2024 · OWASP LLM Top 10 (2025) · mutation-testing-এর সর্বোত্তম অনুশীলন।
>
> প্রতিটি gate-এর প্রামাণিক reference-এর জন্য (প্রতিটি gate কী যাচাই করে, CI job, ratchet বনাম
> policy, blocking বনাম advisory), দেখুন
> [Quality Gates Reference](../architecture/QUALITY_GATES.md)।

## পর্ব 1 — সিদ্ধান্ত ও পরিপক্বতার শ্রেণিবিন্যাস

**সামগ্রিক grade: A− / "উন্নত"। শীর্ষস্থানীয় ~5–10% প্রকল্পের মধ্যে।** সিস্টেমটি স্বাধীনভাবে
এমন কয়েকটি pattern বাস্তবায়ন করে, যেগুলোকে শিল্পে সুস্পষ্টভাবে নামকরণ করা হয়েছে — এটিই সামঞ্জস্যের সবচেয়ে শক্তিশালী
সংকেত (আমরা কোনো checklist অনুলিপি করিনি; আমরা সঠিক অনুশীলনগুলোর দিকেই একীভূত হয়েছি)।

| Reference framework                        | আমাদের অবস্থান                                                                                                                                                                                                                        | Grade                                  |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| **OWASP DSOMM** (5টি level, 5টি dimension) | সুদৃঢ় Level 3; _Test Intensity_ এবং _Static Depth_-এ Level 4-এর দিকে অগ্রসর হচ্ছে। অধিকাংশ সংস্থা 1–2-এ অবস্থান করে।                                                                                                                 | **L3→L4**                              |
| **OpenSSF Scorecard** (18টি check)         | আমরা CI-Tests, Code-Review, Dependency-Update-Tool, Fuzzing, SAST, Signed-Releases (provenance), Token-Permissions, Vulnerabilities, Dangerous-Workflow পাস করি। **ঘাটতি:** `main`-এ Branch-Protection বন্ধ; কিছু action pin করা নেই। | **~7–8/10**                            |
| **SLSA** (4টি level)                       | `npm publish --provenance` + `id-token: write` + GitHub-hosted build = **L2**, L3-এর দিকে অগ্রসর হচ্ছে। L3+-এর জন্য hardened/hermetic builder অনুপস্থিত।                                                                              | **L2→L3**                              |
| **SonarQube "Clean as You Code"**          | অভিন্ন দর্শন: ratchet _non-regression_ নিশ্চিত করে (নতুন code metric-কে আরও খারাপ করে না)। **পার্থক্য:** Sonar **অল্পসংখ্যক** condition সুপারিশ করে; আমাদের ~46টি gate রয়েছে (ক্লান্তির ঝুঁকি)।                                      | **সামঞ্জস্যপূর্ণ, তবে সতর্কতা রয়েছে** |
| **Quality-Ratchet pattern**                | আদর্শ বাস্তবায়ন: ratchet + `dedicatedGate` + `tightenSlack` + `--require-tighten` + graceful-skip। অধিকাংশ public example-এর চেয়ে বেশি পরিশীলিত।                                                                                    | **অনুকরণীয়**                          |
| **DORA 2024**                              | _stability_ axis-এ অত্যন্ত শক্তিশালী। ঝুঁকি: ভারী gate _lead time_ বাড়াতে পারে — fast-gates বিভাজনের মাধ্যমে এটি প্রশমিত করা হয়েছে, তবে coverage gap রয়েছে (পর্ব 2 দেখুন)।                                                         | **শক্তিশালী (stability)**              |
| **OWASP LLM Top 10 (2025)**                | আমরা runtime guard + promptfoo (eval) + garak (red-team) দিয়ে ঝুঁকি #1 (prompt-injection) মোকাবিলা করি। এগুলো শিল্পে প্রচলিত standard tool।                                                                                          | **মোকাবিলা করা হয়েছে**                |
| **Mutation testing**                       | Stryker nightly, threshold 70/50, 8টি critical module। শিল্পমতের ঐকমত্য (বিদ্যমান code-এর জন্য 60% / নতুন code-এর জন্য 80%, nightly) — **আমরা এটিকে ছাড়িয়ে গেছি**। **ঘাটতি:** score এখনও ratchet নয়।                               | **প্রায় সম্পূর্ণ**                    |

## পর্ব 2 — সমালোচনামূলক মূল্যায়ন (শক্তি + সৎ দুর্বলতা)

### শক্তি (যা গড়ের চেয়ে উন্নত)

1. **মাল্টি-মেট্রিক র্যাচেট ইঞ্জিন।** সিস্টেমটির মূলভিত্তি। `quality-baseline.json`-এ 24টি মেট্রিক
   - 4টি নিবেদিত বেসলাইন, প্রতিটিতে দিক (`up`/`down`), সহনশীলতা (`eps`), স্ল্যাক
     (`tightenSlack`) এবং `dedicatedGate` ফ্ল্যাগ রয়েছে। যেসব বিষয় ঠিক করা হয়, সেগুলো **ঠিকই থাকে** — এটি
     কোডবেস এনট্রপির প্রতিষেধক।
2. **সাপ্লাই-চেইনের জন্য বহুস্তরীয় প্রতিরক্ষা।** SAST (CodeQL/Sonar) + সিক্রেটস (`useDefault`-সহ gitleaks)
   - SCA (osv/npm-audit/Trivy/Dependabot) + লাইসেন্স + লকফাইল + SBOM + SLSA
     প্রোভেন্যান্স + Scorecard + ওয়ার্কফ্লো হার্ডেনিং (zizmor)। খুব কম কোডবেসেই এমন পূর্ণাঙ্গ স্ট্যাক রয়েছে।
3. **Goodhart's Law-এর বিরুদ্ধে প্রতিষেধক।** কভারেজকে লক্ষ্য হিসেবে ধরা একটি চিরায়ত অ্যান্টি-প্যাটার্ন
   ("যখন কোনো পরিমাপকই লক্ষ্য হয়ে ওঠে, তখন সেটি আর ভালো পরিমাপক থাকে না")। আমাদের রয়েছে
   ভারসাম্য রক্ষাকারী ব্যবস্থা: **মিউটেশন টেস্টিং** (টেস্টটি বাগ ধরতে পারে কি না তা পরিমাপ করে, শুধু
   লাইনটি এক্সিকিউট করে কি না তা নয়), **`check-test-masking`** (পাস করানোর জন্য অ্যাসার্ট দুর্বল করা প্রতিরোধ করে),
   **প্রতি-মডিউল কভারেজের ন্যূনতম সীমা** (শুধু সহজ অংশ নয়, HIGH-ঝুঁকির কোডও পরীক্ষা করতে বাধ্য করে) এবং
   **`check-pr-evidence`** (Hard Rule #18)।
4. **অ্যান্টি-হ্যালুসিনেশন / সামঞ্জস্য গেট।** একটি বিরল ও মূল্যবান বিভাগ: `check-known-symbols`,
   `check-fetch-targets`, `check-openapi-routes`, `check-docs-symbols` নিশ্চিত করে যে ডকুমেন্টেশন, স্পেসিফিকেশন এবং
   স্ট্রিং ডিসপ্যাচগুলো বিদ্যমান সিম্বলকে নির্দেশ করে। lint/test যে "পচন" ধরতে পারে না, এটি তা ধরে।
5. **পরামর্শমূলক→ব্লকিং জীবনচক্র।** নতুন গেট প্রথমে পরামর্শমূলক হিসেবে প্রবেশ করে (পরিণত হওয়ার সময়
   মার্জ ব্লক করে না), তারপর চক্রের শেষে ব্লকিং হয়ে যায়। সীমা অক্ষুণ্ণ রেখেই প্রতিবন্ধকতা কমায়।
6. **ইনফ্রা অনুপস্থিত থাকলে সুচারুভাবে স্কিপ।** বাইনারি/নেটওয়ার্ক ব্যর্থ হলে স্ক্যানারগুলো (`--ratchet`)
   `exit 0` দিয়ে শেষ হয় — অনুপস্থিত ইনফ্রা কখনোই বৈধ PR ব্লক করে না। পরিণত প্রকৌশলচর্চা।
7. **কোডে সংজ্ঞায়িত সংস্কৃতি।** Hard Rules + `trust-but-verify` + stale-allowlist + evidence-gate
   শৃঙ্খলাকে স্বয়ংক্রিয় যাচাইকরণে রূপান্তর করে।

### সৎ দুর্বলতা (প্রকৃত ঘাটতি)

1. **🔴 fast-gates বিভাজন এখনো একটি কাঠামোগত ফাঁক রেখে গেছে।** `quality.yml` (PR→`release/**`)
   এখন typecheck, দ্রুত নির্ধারণযোগ্য টেস্ট এবং কোড PR-এর জন্য একটি পরামর্শমূলক production build চালায়,
   কিন্তু এটি এখনো `ci.yml`-এর পূর্ণ release-PR পরিসর (কভারেজ র্যাচেট,
   প্যাকেজ আর্টিফ্যাক্ট, ইন্টিগ্রেশন, E2E, SonarQube) চালায় না। প্রেরণাটি (গতি) যৌক্তিক, কিন্তু গেটটি
   মার্জের স্থানেই থাকা উচিত (shift-left)। **সবচেয়ে বড় অমীমাংসিত কাঠামোগত সংশোধন।**
2. **🟠 গেটের আধিক্য/ক্লান্তির ঝুঁকি।** ~46টি গেট + 25টি জব অনেক বেশি। Sonar নিজেই সতর্ক করে:
   অতিরিক্ত শর্ত "গেট ক্লান্তি" ও অগ্রাধিকার নিয়ে বিতর্ক সৃষ্টি করে, ফলে কোনো গেট
   উপেক্ষিত হওয়ার ঝুঁকি থাকে। DORA সতর্ক করে যে ভারী গেট lead-time বাড়ায়। আমরা পরামর্শমূলক স্তর এবং
   নন-অ্যাবসলিউট র্যাচেট দিয়ে এটি প্রশমিত করি, কিন্তু **প্রতিটি গেটের পর্যায়ক্রমিক ROI পর্যালোচনা** অনুপস্থিত (doc-sync-এর
   কিছু মাইক্রো-গেট একীভূত করা সম্ভব)।
3. **🟠 মিউটেশন স্কোর এখনো র্যাচেট নয়।** কভারেজ-গেমিংয়ের বিরুদ্ধে সবচেয়ে শক্তিশালী প্রতিষেধকটি

## পর্ব 4 — যেকোনো প্রকল্পের জন্য প্রতিলিপিকরণ পরিকল্পনা

**পর্যায়ক্রমে** তৈরি করুন, যেখানে প্রতিটি পর্যায় নিজেই মূল্য প্রদান করে। একসঙ্গে সব 12টি বিভাগ বাস্তবায়নের চেষ্টা করবেন না —
এতে ঠিক সেই গেট-ক্লান্তিই তৈরি হয়, যার বিষয়ে পর্ব 2-এ সতর্ক করা হয়েছে। প্রতিটি নতুন গেট প্রথমে **পরামর্শমূলক** হিসেবে যুক্ত হয় এবং
স্থিতিশীল হলে **ব্লকিং** হয়ে ওঠে।

### পুনর্ব্যবহারযোগ্য কেন্দ্রবিন্দু: "র্যাচেট গেটের গঠন"

পুরো সিস্টেমটি এই 3-ফাইলের প্যাটার্নকে কেন্দ্র করে আবর্তিত হয়। প্রথমে এটি কপি করুন:

1. **`baseline.json`** — স্থিরীকৃত মেট্রিক মান + `direction` (`up`/`down`) + `eps` (ফ্লেক-প্রতিরোধী) + `tightenSlack` + `dedicatedGate`।
2. **`collect-metrics.<ext>`** — টুলটি চালায়, সংখ্যাটি বের করে এবং `metrics.json`-এ লেখে।
3. **`check-ratchet.<ext>`** — `metrics.json`-কে `baseline.json`-এর সঙ্গে তুলনা করে; `eps`-এর সীমা ছাড়িয়ে অবনতি হলেই **শুধু তখনই** `exit 1`; টুল/ইনফ্রা অনুপস্থিত থাকলে `exit 0` (সুষ্ঠুভাবে এড়িয়ে যাওয়া); `--require-tighten` ব্যবহার করলে, বেসলাইন আপডেট না করেই **উন্নতি** ঘটলে `exit 1` (অর্জিত উন্নতিটি স্থায়ী করে)।

এটি প্রস্তুত হয়ে গেলে, **প্রতিটি** নতুন মেট্রিক (কভারেজ, জটিলতা, সতর্কতা, SAST অ্যালার্ট, বান্ডলের আকার, মিউটেশন স্কোর…) বেসলাইনে কেবল একটি লাইন।

অব্যবহৃত কোড, ফাইলের আকার। _ফলাফল: এখন থেকে কোডবেস কেবল উন্নতই হতে পারে।_

### পর্যায় 2 — স্ট্যাটিক বিশ্লেষণের গভীরতা (সপ্তাহ 3)

অ্যালার্ট র্যাচেটসহ SAST (CodeQL/Sonar/semgrep); সিক্রেট স্ক্যানার (**ডিফল্ট রুলসেট উত্তরাধিকারসূত্রে নিন**);
SCA (osv/Dependabot) + লাইসেন্স অ্যালাউলিস্ট + lockfile-lint। _ফলাফল: পরিচিত দুর্বলতা ও ফাঁস হওয়া সিক্রেট যাচাই পেরোতে পারে না।_

### পর্যায় 3 — বিল্ড সাপ্লাই চেইন (সপ্তাহ 4)

প্রকাশের সময় SBOM + স্বাক্ষরিত প্রোভেন্যান্স (SLSA L2) + নির্ধারিত Scorecard + ওয়ার্কফ্লো হার্ডেনিং
(zizmor: ন্যূনতম টোকেন, কোনো সংরক্ষিত ক্রেডেনশিয়াল নয়, পিন করা অ্যাকশন)। _ফলাফল: অনুসরণযোগ্য এবং
হস্তক্ষেপ-প্রতিরোধী রিলিজ।_

### পর্যায় 4 — পরীক্ষার তীব্রতা (সপ্তাহ 5–6)

উপযোগী হলে 2য় রানার; **গুরুত্বপূর্ণ মডিউলগুলোর জন্য মডিউল-প্রতি কভারেজের নিম্নসীমা** (গুডহার্ট-বিরোধী);
বিশুদ্ধ লজিকের জন্য প্রপার্টি-ভিত্তিক পরীক্ষা; **প্রতি রাতে মিউটেশন টেস্টিং** → 1ম স্কোর পাওয়া গেলে,
`mutationScore`-কে একটি র্যাচেটে পরিণত করুন। _ফলাফল: কভারেজ শুধু লোকদেখানো মেট্রিক হয়ে থাকা বন্ধ করে; পরীক্ষাগুলো যে সত্যিই বাগ শনাক্ত করে, তা প্রমাণিত হয়।_

### পর্যায় 5 — কনট্র্যাক্ট ও ডায়নামিক বিশ্লেষণ (সপ্তাহ 7)

কোনো পাবলিক API থাকলে: oasdiff (ব্রেকিং পরিবর্তন, **ব্লকিং**) + schemathesis (প্রতি রাতে ফাজিং)।
ডোমেইনের উপযোগিতা অনুযায়ী প্রতি রাতে DAST/রেড-টিম পরীক্ষা। _ফলাফল: কনট্র্যাক্ট নীরবে ভেঙে যায় না।_

### পর্যায় 6 — হ্যালুসিনেশন-বিরোধী ব্যবস্থা ও ডোমেইন (সপ্তাহ 8)

প্রকল্পের প্রতিটি "সদৃশ সত্যের" জন্য একটি সামঞ্জস্য গেট। ডোমেইন-নির্দিষ্ট ব্যর্থতা-মোড
গেট (AI-এর জন্য: ইনজেকশন রেড-টিম)। _ফলাফল: কাঠামোগত অবক্ষয় ও ডোমেইন ব্যর্থতার জন্য একটি সুরক্ষা জাল থাকে।_

### পর্যায় 7 — পরিচালন নীতি (চলমান)

- প্রতিটি নতুন গেটের জন্য পরামর্শমূলক→ব্লকিং চক্র।
- `stale-allowlist`: প্রতিটি দমননীতির একটি যৌক্তিকতা + ইস্যু থাকে; অপ্রচলিত দমননীতি শনাক্ত হয়।
- `evidence-gate`: PR-এ সাফল্যের দাবি করতে প্রমাণ প্রয়োজন (টেস্ট বা চলমান টেস্ট)।
- **প্রতি গেটের ত্রৈমাসিক ROI পর্যালোচনা** (যেগুলো ফলপ্রসূ নয় সেগুলো বাদ দিন/অর্থায়ন বন্ধ করুন — ক্লান্তি প্রতিরোধ করে)।
- আপনার প্রকল্পের কঠোর নিয়মগুলোকে এক্সিকিউটেবল গেটে উন্নীত করুন।

### সর্বব্যাপী নীতি (আপসহীন)

- **পরম মান নয়, র্যাচেট।** নির্দিষ্ট কোনো সংখ্যা নয়, _অবনতি না হওয়া_ গেট করুন (শূন্যতা-প্রতিরোধী নিম্নসীমা ব্যতীত)।
- **পরম নিম্নসীমা ও র্যাচেট একসঙ্গে।** নিম্নসীমা ধস প্রতিরোধ করে; র্যাচেট ধীর ক্ষয় প্রতিরোধ করে।
- **নকশাগতভাবে গুডহার্ট-বিরোধী।** প্রতিটি লক্ষ্য মেট্রিকের একটি ভারসাম্যকারী ব্যবস্থা দরকার (কভারেজ ⇒ মিউটেশন + অ্যান্টি-মাস্কিং; কঠিন কোডের পরীক্ষা নিশ্চিত করতে মডিউল-প্রতি নিম্নসীমা)।
- **সুষ্ঠুভাবে এড়িয়ে যাওয়া।** অনুপস্থিত ইনফ্রা কখনো ব্লক করে না; কেবল প্রকৃত অবনতিই ব্লক করে।
- **ব্যয়বহুল মেট্রিকের জন্য `dedicatedGate`।** যেসব মেট্রিকের বাহ্যিক বাইনারি দরকার, সেগুলো কেন্দ্রীয় সিঙ্ক্রোনাস র্যাচেটের বাইরে নিজস্ব স্ক্রিপ্টে (স্কিপ-সুবিধাসহ) থাকে।
- **যেখানে মার্জ হয়, সেখানেই গেট রাখুন।** দ্রুত গেট এবং প্রকৃত মার্জের মধ্যে কোনো ফাঁক রাখবেন না (দ্রুত-গেট বিভাজন থেকে পাওয়া শিক্ষা)।
- **অল্পসংখ্যক, সুচিন্তিত ব্লকিং গেট।** Sonar/DORA: অত্যধিক শর্ত = ক্লান্তি। ব্লকিং গেটের দেয়ালের বদলে পরামর্শমূলক + র্যাচেট পছন্দ করুন।

## অংশ 5 — প্রস্তাবিত উন্নতিসমূহ (অগ্রাধিকারভিত্তিক, সামঞ্জস্যপূর্ণ)

**P0 — সর্বোচ্চ ROI, প্রায় প্রস্তুত**

1. **Mutation score ratchet** (প্রথম nightly Stryker মান তৈরি করার পর)। coverage-Goodhart-এর বিরুদ্ধে প্রধান প্রতিষেধক; ~90% সম্পন্ন।
2. **অবশিষ্ট fast-gates ফাঁকটি বন্ধ করা** — `quality.yml`-এর production build-টিকে এর
   advisory week-এর পর বাধ্যতামূলক করুন এবং কেবল deterministic release-PR-এ চলা যাচাইগুলোকে PR→release পথে স্থানান্তর করতে থাকুন।
3. **`main`-এ branch-protection** (মালিকের সেটিং) — Scorecard বাড়ায়, DSOMM-এর ঘাটতি পূরণ করে।

**P1 — মূল্যবান** 4. **osv/oasdiff → সঠিক scope-সহ blocking** — osv-তে কেবল CRITICAL+fixable (Trivy-এর মতো দুই ধাপে); oasdiff breaking-changes ব্লক করে। 5. **`require-tighten` → blocking** (চক্রের শেষে) — metric-এর উন্নতি ধরে রাখে। 6. **`ci-summary`-তে প্রতি-gate ROI/timing পর্যালোচনা** — ধীর/কম-মূল্যের gate শনাক্ত করে বাদ দিন।

**P2 — ক্রমহ্রাসমান সুফল** 7. **SLSA L3** — L2 থেকে আরও ওপরে যেতে চাইলে hermetic/reproducible builder (GitHub SLSA generator)। 8. **Commit করা CodeQL config + versioned semgrep** — আরও নিয়ন্ত্রণ/reproducibility। 9. **প্রতি-PR DAST smoke** — সর্বোচ্চ-ঝুঁকির endpoint-গুলোতে schemathesis/promptfoo-এর দ্রুত subset (শুধু nightly নয়)। 10. **Flakiness dashboard + DORA metrics** — নিশ্চিত করুন যে gate-গুলো গতি ক্ষয় করছে না।

## অংশ 6 — নির্দিষ্ট release থেকে পাওয়া শিক্ষা (Phase 9-এ যোগ করার gate)

> এই অংশে release closure-এর বাস্তব incident নথিভুক্ত করা হয়েছে, যেখানে একটি gate **অনুপস্থিত ছিল**,
> সঙ্গে রয়েছে সুনির্দিষ্ট প্রমাণ ও প্রস্তাবিত gate। প্রতিটি item অংশ 5-এর প্রার্থী।

### শিক্ষা v3.8.27 (2026-06-17) — "fast-gates hole" deterministic regression-কে release-এর দিন পর্যন্ত পৌঁছাতে দেয়

**কী ঘটেছিল।** v3.8.27 `/generate-release` চলাকালে release PR (`release/v3.8.27` → `main`)
ছিল সমন্বিত চক্রে পূর্ণ `ci.yml` matrix-এর **প্রথম** execution। ফলাফল: একসঙ্গে 12টি failure
— **3টি deterministic test** + ~9টি flake/env। কোনোটিই live product regression ছিল না, কিন্তু
সবগুলোই অশনাক্ত থেকে যায়, কারণ cycle PR-গুলো **Fast QG
(`quality.yml`)**-এর মাধ্যমে `release/**`-এ প্রবেশ করে, যা পূর্ণ unit suite, `pr-test-policy` (test-masking),
পূর্ণ integration suite কিংবা schema parity checking—কোনোটিই চালায় না। 3টি deterministic failure ছিল:

1. **UI পরিবর্তনে test পুরোনো হয়ে যাওয়া** — `permissions modal switch buttons declare button type`:
   #4034 একটি 4র্থ switch যোগ করেছিল (a11y `type="button"` বজায় ছিল); test-এর `=== 3` গণনা
   পুরোনো হয়ে যায়। Static analysis-এর #4034 PR-এই এটি ধরার কথা ছিল।
2. **Packaging পরিবর্তনে test পুরোনো হয়ে যাওয়া** — `findMissingArtifactPaths ... root runtime files`:
   `dist/http-method-guard.cjs` একটি বৈধ required-path হয়ে যায়; test-এর expected list
   পুরোনো হয়ে যায়।
3. **Lossy modularization divergence (সবচেয়ে গুরুতর)** — `settings schemas accept ... unprefixed
toggle`: **modularized** `updateSettingsSchema` (`schemas/settings.ts`, #3988 দ্বারা তৈরি) canonical সংস্করণ
   (`settingsSchemas.ts`) থেকে বিচ্যুত হয়েছিল: **45টি field বনাম 85টি — 40টি বাদ + 6টি ভিন্ন (qdrant\*)**। এটি ছিল
   **dead-code** (runtime canonical সংস্করণটি ব্যবহার করে), তাই live impact ছিল না, কিন্তু কেবল হাতে-লেখা parity
   test এটি ধরেছিল। #4030, #3988/#3993 থেকে একই ধরনের 16টি বাদ পড়া field পুনরুদ্ধার করেছিল, কিন্তু এটি এড়িয়ে যায়।

**প্রস্তাবিত gate (Phase 9):**

- **G1 — fast-gates ফাঁকটি প্রকৃতপক্ষে বন্ধ করা (P0 #2-এর সম্প্রসারণ)।** `quality.yml`-এ (PR→`release/**`),
  typecheck + impacted tests-এর পাশাপাশি **`pr-test-policy` (test-masking) + পূর্ণ deterministic
  unit suite** চালান (অথবা অন্তত static/parity file-গুলো, যেগুলো দ্রুত ও non-flaky)।
  এর ফলে পুরোনো test এবং assert অপসারণ release-এর দিনে নয়, বরং যে PR এগুলো প্রবর্তন করে সেখানেই ধরা পড়বে।
  Integration/e2e বাদ রাখুন (ধীর/flaky), কিন্তু deterministic layer কেবল
  PR→main-এ সীমাবদ্ধ থাকতে পারে না।
- **G2 — Modularization parity gate (নতুন, বর্তমানে অন্তর্ভুক্ত নয়)।** এমন একটি check, যা modularized barrel
  (`src/shared/validation/schemas/*`, `providerRegistry`
  module ইত্যাদি) দ্বারা পুনরায় export করা প্রতিটি symbol-এর **shape** (`z.object` key, registry entry) canonical
  source-এর সঙ্গে তুলনা করে এবং **divergence হলে ব্যর্থ হয়** (বাদ পড়া/অতিরিক্ত field)। এটি #3988-এর
  40টি field বাদ পড়ার ঘটনাটি সেই PR-এই ধরত। এটি হাতে-লেখা parity test-গুলোকে সাধারণীকরণ করে (যেগুলো কেবল সেখানেই আছে, যেখানে
  কেউ সেগুলো লেখার কথা মনে রেখেছিল)। সাশ্রয়ী: উভয়টি import করে `Object.keys(shape)` diff করে।
- **G3 — Deterministic flake triage (সহায়ক)।** LiveWS-startup এবং integration-combo/breaker
  test-গুলো logic-এর কারণে নয়, CI-তে server timeout/cascade-এর (env) কারণে ব্যর্থ হয়। এগুলোকে
  `known-flaky` হিসেবে চিহ্নিত করুন (issue-সহ quarantined), যাতে release-PR-এর লাল অবস্থা **শুধু বাস্তব signal** দেখায়,
  মাঝখানে deterministic regression আড়াল করা noise নয়।

**নীতি:** _যেখানে merge ঘটে, gate-টিকেও সেখানেই চলতে হবে_ (ইতিমধ্যেই "Cross-cutting principles"-এ রয়েছে)।
v3.8.27 incident দেখায় যে এটি শুধু lint/typecheck-এর জন্য নয়, **deterministic test layer**-এর ক্ষেত্রেও প্রযোজ্য —
তা না হলে পুরোনো test + lossy modularization-এর ঋণ কেবল PR→main-এ, একসঙ্গে, সবচেয়ে
খারাপ মুহূর্তে দৃশ্যমান হয়।
