## নিয়মাবলি

- কভারেজের লক্ষ্য সোর্স ফাইলের ক্ষেত্রে প্রযোজ্য, `tests/**`-এর ক্ষেত্রে নয়।
- `open-sse/**` পণ্যের অংশ এবং এটিকে অবশ্যই পরিধির মধ্যে রাখতে হবে।
- নতুন কোডের কারণে সংশ্লিষ্ট অংশগুলোর কভারেজ কমা উচিত নয়।
- বাস্তবায়নের খুঁটিনাটির চেয়ে আচরণ এবং ব্রাঞ্চের ফলাফল পরীক্ষা করাকে অগ্রাধিকার দিন।
- `src/lib/db/**`-এর জন্য বিস্তৃত মকের বদলে অস্থায়ী SQLite ডেটাবেস এবং ছোট ফিক্সচারকে অগ্রাধিকার দিন।

## বর্তমান কমান্ডসমূহ

- `npm run test:coverage`
  - ইউনিট টেস্ট স্যুটের প্রধান সোর্স কভারেজ গেট
  - `text-summary`, `html`, `json-summary`, এবং `lcov` তৈরি করে
- `npm run coverage:report`
  - সর্বশেষ রান থেকে ফাইলভিত্তিক বিস্তারিত রিপোর্ট
- `npm run test:coverage:legacy`
  - কেবল ঐতিহাসিক তুলনার জন্য

## র্যাচেট নীতি

প্রকল্পটি স্বাচ্ছন্দ্যজনক ব্যবধানে পরবর্তী মাইলফলক অতিক্রম করার পরেই কেবল `npm run test:coverage`-এর থ্রেশহোল্ড আপডেট করুন।

**বর্তমান গেট:** `npm run test:coverage` **60 স্টেটমেন্ট / 60 লাইন / 60 ফাংশন / 60 ব্রাঞ্চ** প্রয়োগ করে (Quality-Gates Fase 6A.1-এ মেট্রিকটি পুনরায় বেসলাইন করা হয়েছিল—আগের 82.58% বেসলাইনটি স্ফীত ছিল, কারণ এতে টেস্ট ফাইল গণনা করা হয়েছিল এবং `open-sse` বাদ দেওয়া হয়েছিল)। ঐতিহাসিক তুলনার জন্য `test:coverage:legacy` কমান্ডটি পুরোনো 50/50/50 মেট্রিক সংরক্ষণ করে।

সর্বশেষ রিপোর্টের বিপরীতে তাৎক্ষণিক থ্রেশহোল্ড যাচাইয়ের জন্য ব্যবহার করুন:

```bash
node scripts/check/test-report-summary.mjs --threshold 75
```

প্রস্তাবিত র্যাচেট ক্রম (ক্রমটি হলো `স্টেটমেন্ট-লাইন / ব্রাঞ্চ / ফাংশন`):

1. 55/60/55
2. 60/62/58
3. 65/64/62
4. 70/66/66
5. 75/70/72 <-- বর্তমান গেট (75/70/75)
6. 80/75/78
7. 85/80/84
8. 90/85/88

পরপর দুটি রানে ব্রাঞ্চ কভারেজ 78%-এর ওপরে বজায় থাকলে পরবর্তী র্যাচেট লক্ষ্য হলো `80/75/78`।

## পরিচিত ঘাটতি

বর্তমান কভারেজ কমান্ডটি প্রধান Node ইউনিট স্যুট পরিমাপ করে এবং সেটি থেকে পৌঁছানো সোর্স, যার মধ্যে `open-sse`-ও রয়েছে, অন্তর্ভুক্ত করে। এটি এখনো Vitest কভারেজকে একটি একক সমন্বিত রিপোর্টে মার্জ করে না। পরে এই মার্জটি করা উপযোগী হবে, তবে 60% -> 80% অগ্রগতি শুরু করার ক্ষেত্রে এটি কোনো বাধা নয়।
