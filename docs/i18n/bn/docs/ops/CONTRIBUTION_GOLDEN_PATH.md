একটি pull request-এর জন্য সবচেয়ে ছোট নির্ভরযোগ্য development loop বেছে নিতে এই নির্দেশিকাটি ব্যবহার করুন। এটি নিচে লিঙ্ক করা ক্ষেত্র-নির্দিষ্ট architecture এবং security document-গুলোর
বিকল্প নয়; এটি প্রতিটি সাধারণ পরিবর্তনের ধরনকে তার contract, focused check এবং CI coverage-এর
সঙ্গে সংযুক্ত করে।

## প্রতিটি পরিবর্তন যে পথ অনুসরণ করে

1. **সম্পাদনার আগে base বেছে নিন।** সর্বোচ্চ সক্রিয় `release/v*` branch খুঁজে নিয়ে
   তার tip থেকে branch তৈরি করুন। `main` নয়, সেই branch-টিকেই target করুন। কোনো release freeze সক্রিয় থাকলে frozen
   branch-টিকে target করবেন না; বরং
   [Branching & Release Model](BRANCHING_MODEL.md)-এ বর্ণিত পরবর্তী সক্রিয় cycle ব্যবহার করুন।
2. **Contract-গুলোর নাম উল্লেখ করুন।** পরিবর্তনটি প্রভাবিত করে এমন প্রতিটি catalog, schema, generated artifact, public API অথবা user
   interface শনাক্ত করুন। নিচের table-এ ন্যূনতম প্রারম্ভিক set দেওয়া আছে।
3. **Focused test লিখুন বা হালনাগাদ করুন।** `src/`, `open-sse/`, `electron/` অথবা
   `bin/`-এ production পরিবর্তনের জন্য একই PR-এ একটি automated test আবশ্যক। প্রথমে behavior প্রমাণ করে এমন সবচেয়ে ছোট test file-গুলো চালান,
   তারপর তালিকাভুক্ত focused gate-গুলো চালান।
4. **CI-কে বিস্তৃত matrix চালাতে দিন।** সম্পূর্ণ unit shard, Vitest, coverage ratchet এবং
   production build PR-এ চলে। শুধুমাত্র তখনই স্থানীয়ভাবে broad suite চালান, যখন কোনো focused failure আরও
   বিস্তৃত প্রভাবের ইঙ্গিত দেয় অথবা পরিবর্তনটি একাধিক subsystem জুড়ে বিস্তৃত হয়।
5. **Review-এর আগে সমন্বয় করুন।** সক্রিয় base fetch করুন, এর নতুন commit এবং এর তুলনায় আপনার diff
   পর্যালোচনা করুন, তারপর contributor workflow অনুযায়ী base-টি rebase অথবা merge করুন। Generated-file
   এবং catalog conflict-গুলো তাদের source থেকে সমাধান করুন, সেগুলো regenerate করুন, focused loop আবার চালান এবং নিশ্চিত করুন যে
   PR এখনও সক্রিয় release branch-টিকেই target করছে।
6. **প্রমাণ নথিভুক্ত করুন।** PR template-এ চালানো command, যোগ বা পরিবর্তন করা প্রতিটি test file,
   migration অথবা feature flag এবং এখনও pending থাকা যেকোনো CI-only validation তালিকাভুক্ত করুন।

## পরিবর্তনের ধরন অনুযায়ী Golden path

নিচের command-গুলো ন্যূনতম focused check; এগুলো আপনার পরিবর্তিত behavior সরাসরি cover করে এমন
test এড়িয়ে যাওয়ার অনুমতি নয়।

### Provider

**Contract**

- `src/shared/constants/providers/`-এ থাকা Provider definition এবং
  `src/shared/constants/providers.ts`-এ এর composition।
- `open-sse/config/providerRegistry.ts` অথবা এর extracted registry file-গুলোতে থাকা model এবং capability।
- প্রযোজ্য ক্ষেত্রে executor/translator selection, OAuth অথবা API-key configuration, dashboard asset এবং generated
  provider reference।
- Public credential-গুলোকে অবশ্যই `resolvePublicCred()` ব্যবহার করতে হবে; error response-গুলোকে shared sanitized
  error helper ব্যবহার করতে হবে। `docs/security/PUBLIC_CREDS.md` (git; `/docs`-এ compile করা হয় না) এবং
  [Error Sanitization](../security/ERROR_SANITIZATION.md) দেখুন।

**Focused loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog পরিবর্তিত হলে; generated diff commit করুন
npm run lint
```

প্রভাবিত প্রতিটি request family-ও test করুন: chat, Responses, images, embeddings, audio অথবা video।
Generated catalog এবং golden diff-গুলোকে contract change হিসেবে review করুন; সেগুলো অন্ধভাবে গ্রহণ করবেন না।

### Routing

**Contract**

- `src/shared/constants/routingStrategies.ts`-এ থাকা public strategy value এবং UI metadata।
- `open-sse/services/combo.ts` এবং `open-sse/services/combo/`-এর অধীনে dispatch এবং ordering।
- Combo schema, persistence, resilience state, model capability এবং API/UI control।
- Behavior পরিবর্তিত হলে [Auto-Combo Engine](../routing/AUTO-COMBO.md) এবং resilience documentation।

**Focused loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy অথবা dispatch পরিবর্তন
npm run check:known-symbols      # strategy registration পরিবর্তন
npm run lint
```

স্থানীয়ভাবে deterministic mocked-upstream test ব্যবহার করুন। Live combo smoke-এর জন্য credential প্রয়োজন এবং সেগুলো
manual, CI-এর বিকল্প নয়।

### UI / UX

**Contract**

- `src/app/` এবং `src/shared/components/`-এর অধীনে Next.js route/page এবং shared component boundary।
- API response shape, loading/empty/error state, keyboard ও screen-reader behavior,
  responsive layout, theming এবং locale expansion।
- `src/i18n/messages/en.json`-এ থাকা English UI source string; নতুন user-facing copy hard-code করবেন না।

**Focused loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction অথবা visual পরিবর্তনের জন্য app চালান এবং narrow ও wide উভয় viewport পরীক্ষা করুন। CI
production build এবং বিস্তৃত suite চালায়; visual behavior-এর জন্য এখনও পরিবর্তনের উপযোগী একটি focused component, Playwright
অথবা নথিভুক্ত manual check প্রয়োজন।

### i18n

**Contract**

- `src/i18n/messages/en.json` হলো UI source; `config/i18n.json` হলো locale source।
- CLI catalog-গুলো `bin/cli/locales/`-এর অধীনে আলাদাভাবে থাকে।
- ICU placeholder এবং tag হুবহু সংরক্ষণ করুন। Product/provider/model name,
  protocol এবং header name, command, code/JSON identifier, URL, environment variable অথবা
  `OmniRoute`, `OAuth`, `MCP` এবং `A2A`-এর মতো protected term অনুবাদ করবেন না। বর্তমান source list হলো
  `scripts/i18n/glossary/protected-terms.json`।

**Focused loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI string/catalog পরিবর্তিত হলে
npm run lint
```

এটি বিদ্যমান system-এর জন্য নির্দেশনা, এর tooling অথবা key model সম্প্রসারণের আমন্ত্রণ নয়।
Replacement system design করার সময় i18n patch-গুলো সীমিত ও সুনির্দিষ্ট রাখুন। Task-এ generated translation স্পষ্টভাবে প্রয়োজন না হলে এবং
resulting diff review না করে থাকলে external service call করে এমন translation
command চালাবেন না।

### CLI

**Contract**

- `bin/cli/`-এর পাবলিক কমান্ড ও ফ্ল্যাগ, জেনারেট করা API কমান্ড, এক্সিট কোড, stdout/stderr ও
  JSON আউটপুটের গঠন, কনফিগারেশন/এনভায়রনমেন্টের আচরণ এবং প্যাকেজে অন্তর্ভুক্ত ফাইলসমূহ।
- CLI-তে ব্যবহারকারীর জন্য দৃশ্যমান স্ট্রিংগুলো অবশ্যই CLI i18n স্তর ব্যবহার করবে এবং `en`/`pt-BR` ক্যাটালগগুলোকে সামঞ্জস্যপূর্ণ রাখবে।
- সমর্থিত রানটাইম হিসেবে Node এবং প্রকাশিত বাইনারি কনট্র্যাক্ট অক্ষুণ্ণ রাখুন।

**কেন্দ্রভিত্তিক লুপ**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # জেনারেট করা/বান্ডল করা CLI পরিবর্তন
npm run check:pack-policy     # প্যাকেজ-সারফেসের পরিবর্তন
npm run lint
```

যখন আচরণ পার্সিং, ফাইল বা এক্সিট স্ট্যাটাসের ওপর নির্ভর করে, তখন একটি অস্থায়ী ডেটা ডিরেক্টরিতে হুবহু কমান্ডটি ব্যবহার করুন।
CI আরও বিস্তৃত প্যাকেজ আর্টিফ্যাক্ট ও ইকোসিস্টেম যাচাই সম্পাদন করে।

### ডেটাবেস

**কনট্র্যাক্টসমূহ**

- `src/lib/db/`-এর অধীনে থাকা ডোমেইন মডিউলগুলো; নির্দিষ্ট মডিউল সরাসরি ইমপোর্ট করুন (পুরোনো `localDb.ts` রি-এক্সপোর্ট স্তরটি সরানো হয়েছে)।
- `src/lib/db/migrations/`-এর অধীনে নম্বরযুক্ত, আইডেমপোটেন্ট SQL মাইগ্রেশন, ট্রানজ্যাকশনের নিরাপত্তা, আপগ্রেডের
  আচরণ, ইনডেক্স এবং স্কিমা দ্বারা প্রভাবিত প্রতিটি কলার।
- রুট ও হ্যান্ডলার কখনো সরাসরি র’ SQL ইস্যু করে না।

**কেন্দ্রভিত্তিক লুপ**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

মাইগ্রেশন যোগ করার সময় একটি নতুন ডেটাবেস এবং পূর্ববর্তী স্কিমা থেকে আপগ্রেড—উভয়ই পরীক্ষা করুন। ডেটাবেস টেস্টগুলোকে
অবশ্যই হ্যান্ডেল বন্ধ করতে হবে এবং ক্লিনআপের সময় `resetDbInstance()` কল করতে হবে। কেবল সেরা-প্রচেষ্টা Bun অ্যাডাপ্টার পাথ পরিবর্তিত হলেই
`npm run test:bun:db` চালান; Node-ই কর্তৃত্বপূর্ণ হিসেবে বহাল থাকবে।

### বিল্ড / ডিপ্লয়

**কনট্র্যাক্টসমূহ**

- রুট ও ওয়ার্কস্পেস ম্যানিফেস্ট/লকফাইল, `scripts/build/`, Next.js স্ট্যান্ডঅ্যালোন অ্যাসেম্বলি, `dist/`
  প্যাকেজের বিষয়বস্তু, Electron প্ল্যাটফর্ম মেটাডেটা, CI ওয়ার্কফ্লো এবং ডিপ্লয়মেন্ট সেন্টিনেল।
- সমর্থিত Node রেঞ্জ এবং `CLAUDE.md`-এ অনুমোদিত তালিকাভুক্ত Bun-এর ব্যবহার অবশ্যই অক্ষুণ্ণ রাখতে হবে।
- বিল্ড আর্টিফ্যাক্টগুলো আনট্র্যাকড থাকবে; ডিপেন্ডেন্সি, লাইসেন্স, ওয়ার্কফ্লো ও প্যাকেজ নীতিমালা প্রযোজ্য হবে।

**কেন্দ্রভিত্তিক লুপ**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # ডিপেন্ডেন্সি বা লকফাইলের পরিবর্তন
npm run check:pack-policy      # প্রকাশিত প্যাকেজ সারফেসের পরিবর্তন
npm run lint
```

পরিবর্তনটি কম্পাইলেশন, স্ট্যান্ডঅ্যালোন অ্যাসেম্বলি, অ্যাসেট বা রানটাইম বান্ডলিংকে প্রভাবিত করলেই কেবল স্থানীয়ভাবে `npm run build` ব্যবহার করুন।
শুধু রিলিজ/ডিপ্লয় যাচাইয়ের জন্য `npm run build:release` ব্যবহার করুন। CI-এর বিল্ডই চূড়ান্ত ক্রস-প্ল্যাটফর্ম সংকেত; প্ল্যাটফর্ম-নির্দিষ্ট Electron পরিবর্তনের জন্য সংশ্লিষ্ট কেন্দ্রভিত্তিক বিল্ড
বা স্মোক-টেস্টের প্রমাণ প্রয়োজন।

## লোকাল লুপ বনাম CI

| প্রতিটি প্যাচের জন্য লোকালি চালান                                               | CI বিস্তৃত সংকেত প্রদান করে                                              |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| উপরের সরাসরি আচরণগত পরীক্ষা এবং ক্যাটাগরি গেটসমূহ                               | শার্ড করা সম্পূর্ণ ইউনিট স্যুট এবং সিরিয়াল পরীক্ষা                      |
| `npm run lint`                                                                  | Vitest স্যুট এবং কভারেজ/গুণমান র্যাচেট                                   |
| প্রভাবিত কনট্র্যাক্টে প্রয়োজন হলেই শুধু টাইপচেক বা বিল্ড                       | প্রোডাকশন বিল্ড, নিরাপত্তা, ডকস, ডিপেন্ডেন্সি এবং PR-নীতি গেটসমূহ        |
| অটোমেশন আচরণটি প্রমাণ করতে না পারলেই শুধু ম্যানুয়াল ইন্টারঅ্যাকশন/লাইভ পরীক্ষা | ওয়ার্কফ্লো দ্বারা কনফিগার করা ক্রস-জব ইন্টিগ্রেশন ও প্ল্যাটফর্ম পরীক্ষা |

একটি সফল ফোকাসড লুপ পরিবর্তিত কনট্র্যাক্ট সম্পর্কে প্রমাণ দেয়, সম্পর্কহীন CI পরীক্ষাগুলো
পাস করবে—এমন নিশ্চয়তা নয়। বিপরীতভাবে, প্রতিটি লোকাল সম্পাদনাকে সম্পূর্ণ রিপোজিটরি ম্যাট্রিক্সের জন্য অপেক্ষা করাবেন না।

## সমন্বয় চেকলিস্ট

রিভিউয়ের অনুরোধ করার আগে:

- নিশ্চিত করুন যে PR-এর বেস এখনও সর্বোচ্চ সক্রিয় `release/v*` ব্রাঞ্চ।
- সেই বেস ফেচ করুন এবং আপনি ব্রাঞ্চ তৈরি করার পর থেকে যুক্ত হওয়া কমিটগুলো রিভিউ করুন।
- অনিচ্ছাকৃত বা জেনারেট করা অপ্রয়োজনীয় পরিবর্তনের জন্য `git diff <active-base>...HEAD` পর্যালোচনা করুন।
- সোর্স আপডেট করে এবং আউটপুট পুনরায় জেনারেট করে ক্যাটালগ ও জেনারেট করা ডকুমেন্টের কনফ্লিক্ট সমাধান করুন।
- সমন্বয়ের পর PR-এর বিবরণে তালিকাভুক্ত প্রতিটি ফোকাসড পরীক্ষা/গেট পুনরায় চালান।
- পরিবর্তিত বেসের সঙ্গে মেলাতে কখনোই অ্যাসারশন দুর্বল করবেন না বা আবশ্যক পরীক্ষা বাদ দেবেন না।

রিলিজ-ফ্রিজ এবং রিটার্গেটিংয়ের নিয়মের জন্য
[ব্রাঞ্চিং ও রিলিজ মডেল](BRANCHING_MODEL.md) দেখুন। সম্পূর্ণ CI তালিকার জন্য
[কোয়ালিটি গেটস রেফারেন্স](../architecture/QUALITY_GATES.md) দেখুন।
