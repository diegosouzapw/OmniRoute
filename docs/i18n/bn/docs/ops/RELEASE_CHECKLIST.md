## npm Trusted Publishing (v3.8.51 থেকে ডিফল্ট) — অনুরোধে staged, fallback হিসেবে direct

`npm-publish.yml` ডিফল্টভাবে **npm Trusted Publishing (OIDC)**-এর মাধ্যমে প্রকাশ করে:
`stage-npm` জবটি (github-hosted) ওই রানের জন্য GitHub-এর id-token বিনিময় করে একটি স্বল্পমেয়াদি npm
credential নেয় — repository secrets-এ কোনো দীর্ঘমেয়াদি npm token থাকে না, কোনো 2FA prompt আসে না, এবং provenance সংযুক্ত থাকে।
2FA এড়িয়ে যাওয়া token-গুলো অবসরে পাঠানো হচ্ছে বলে npm এখন এই bypass অনুমোদন করে;
এটি WS1.3 নিশ্চয়তা বজায় রেখেই v3.8.48 পর্যন্ত প্রকল্পটিতে থাকা সম্পূর্ণ স্বয়ংক্রিয় প্রবাহ পুনরুদ্ধার করে
(ফাঁস হওয়া token একা publish করতে পারে না — কারণ কোনো token-ই নেই)।

**একবারের সেটআপ (owner):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none)। এটি তৈরি না হওয়া পর্যন্ত স্বয়ংক্রিয় ধাপটি `ENEEDAUTH` দিয়ে ব্যর্থ হবে:
`publish_mode=staged` (নিচে) অথবা `direct` দিয়ে পুনরায় dispatch করুন।

### Staged publishing (অনুরোধে — `publish_mode=staged`)

npm-publish workflow আর সরাসরি publish করে না: এটি প্যাক করা tarball
বুট করে (`check:pack-boot`) এবং তারপর `npm stage publish` চালায় — হুবহু সেই bytes-গুলো registry-তে রাখা হয়,
কিন্তু owner অনুমোদন না করা পর্যন্ত সেগুলো **install করা যায় না**। মানব-নির্ভর 2FA gate-টি এখন প্রমাণ যাচাইয়ের
আগে নয়, পরে সম্পন্ন হয়।

**Workflow সবুজ হওয়ার পর owner-এর প্রবাহ:**

1. `npm stage list omniroute` — stage id খুঁজুন (workflow summary-তেও দেখানো হয়)।
2. Staged bytes যাচাই করুন (সুপারিশকৃত): `npm stage download <id>`, তারপর ডাউনলোড করা
   tarball-টি একটি অস্থায়ী prefix-এ install করে বুট করুন (`npm run check:pack-boot` CI-তে
   একই pack→install→boot সিদ্ধান্ত স্বয়ংক্রিয় করে)।
3. `npm stage approve <id>` — 2FA prompt-টিই হলো publish। `npm stage reject <id>` বাতিল করে।
4. Publish-পরবর্তী সুরক্ষা: publish-পরবর্তী verifier (v3.8.49 পরিকল্পনার WS1.4) একটি পরিষ্কার
   container-এ public registry থেকে প্রকাশিত version install করে সেটি বুট করে।

**জরুরি fallback:** `publish_mode=direct`-সহ `workflow_dispatch` পুরোনো
তাৎক্ষণিক `npm publish` পুনরুদ্ধার করে (শুধু staging নিজেই ঠিকমতো কাজ না করলে ব্যবহার করুন; কারণটি নথিভুক্ত করুন)।

**একবারের hardening (owner, npmjs.com):** `omniroute`-এর Trusted Publisher-কে
stage-only mode-এ কনফিগার করুন, যাতে ফাঁস হওয়া কোনো দীর্ঘমেয়াদি token কোথাও থেকে সরাসরি `npm publish`
করতে না পারে — CI কেবল stage করতে পারে; শুধু owner-এর 2FA রিলিজ করতে পারে।

**ত্রুটিপূর্ণ artifact-এর playbook (অপরিবর্তিত):** ডিফল্ট তাৎক্ষণিক পদক্ষেপ হিসেবে
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` ব্যবহার করুন (কয়েক মিনিট লাগে, প্রত্যাবর্তনযোগ্য);
শুধু 72h/no-dependents সীমার মধ্যে `npm unpublish` ব্যবহার করুন এবং কখনোই প্রথম পদক্ষেপ হিসেবে নয়।
Docker: কোনো version tag কখনো পুনর্লিখবেন না — rollback হলো `latest`-কে সর্বশেষ ভালো digest-এর দিকে পুনর্নির্দেশ করা।

**Docker Hub `latest` (প্রতিটি stable SemVer publish-এ আবশ্যক):**
`docker-publish` workflow-কে অবশ্যই `X.Y.Z` এবং, যখন
`should-promote-latest.sh` সম্মত হয় যে এটিই সর্বোচ্চ stable SemVer, একই **digest** দিয়ে `:latest`—
**দুটোকেই** tag করতে হবে। Job-এর পরে: Hub-এর `latest` digest নতুন
SemVer digest-এর সমান হবে এবং `last_updated` এগিয়ে যাবে। Release notes-এ এমন fix-এর কথা থাকা অবস্থায়
`:latest`-কে পুরোনো build-এ রেখে দেবেন না, যদি ওই fix শুধু git-এ থাকে। Compose
quickstart-গুলো `:latest` ব্যবহার করে; GitOps-এর `X.Y.Z` pin করাই চালিয়ে যাওয়া উচিত। দেখুন
[Docker release channels](../guides/DOCKER_GUIDE.md#release-channels) এবং #10317।

## হটফিক্স ফাস্ট-লেন (`hotfix` লেবেল)

`hotfix` লেবেলযুক্ত একটি PR ভারী CI ম্যাট্রিক্স (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) এড়িয়ে যায় এবং দ্রুত, উচ্চ-সংকেতসম্পন্ন গেটগুলো বজায় রাখে: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
এবং tarball boot-smoke (`check:pack-boot`)। লক্ষ্য: ~33min-এর পরিবর্তে ≤15min-এ সবুজ অবস্থা।

**প্রবেশনীতি — চারটিই আবশ্যক (Chromium/VS Code/Node-এর জরুরি লেন অনুসারে তৈরি):**

1. **তীব্রতা**: production নষ্ট — প্রকাশিত কোনো artifact boot-এর সময় crash করে /
   একটি security fix / release-এর প্রতিটি ব্যবহারকারী প্রভাবিত। "গুরুত্বপূর্ণ" মানেই "নষ্ট" নয়।
2. **কর্তৃত্ব**: কেবল repository owner-ই `hotfix` লেবেল প্রয়োগ করেন। লেবেলটিই
   অনুমোদন — campaign PR-এ এটি কখনো নিজে থেকে ব্যবহার করা যাবে না।
3. **প্রমাণ**: PR body-তে পূর্ববর্তী সম্পূর্ণ-সবুজ heavy run-এর লিঙ্ক থাকে (যে suite-টি
   বাদ দেওয়া job-গুলো পুনরায় যাচাই করত), সঙ্গে fix-টির নিজস্ব আগে-ব্যর্থ-তারপর-সফল test।
4. **পরিধি**: শুধু cherry-pick — ন্যূনতম fix, কোনো refactor নয়, কোনো অতিরিক্ত পরিবর্তন নয়।

বাদ দেওয়া coverage/ratchet ক্ষেত্রটি release branch-এর পরবর্তী পূর্ণ run-এ
পুনরায় যাচাই করা হয় (ধারাবাহিক release-green) — এই lane কেবল অপেক্ষা এড়ায়, যাচাইকরণ কখনো নয়।
শুধু test-সংক্রান্ত diff (সব file `tests/`-এর অধীনে, একটিও `tests/e2e/`-এর অধীনে নয়) কোনো
লেবেল ছাড়াই স্বয়ংক্রিয়ভাবে E2E matrix এড়িয়ে যায়।

### Build বিন্যাস

Repository-টি তিনটি স্বতন্ত্র output directory ব্যবহার করে — এগুলো কখনো গুলিয়ে ফেলবেন না:

| Directory | উদ্দেশ্য                                                     | ট্র্যাক করা হয়? |
| --------- | ------------------------------------------------------------ | ---------------- |
| `src/`    | Application source (TypeScript / TSX)                        | হ্যাঁ            |
| `.build/` | Build-এর মধ্যবর্তী ফাইল — `next build` output (`distDir`)    | না (gitignored)  |
| `dist/`   | বিতরণযোগ্য npm bundle — `assembleStandalone` দ্বারা প্রস্তুত | না (gitignored)  |

> **অপারেটরের নোট:** remote VPS image directory এখনও `/usr/lib/node_modules/omniroute/app/`।
> কেবল **repository-এর ভেতরের** build output সরানো হয়েছে (`app/` → `dist/`)। Deploy skill-গুলো
> `dist/`-এর বিষয়বস্তু remote `app/` directory-তে rsync করে — VPS path-এ কোনো পরিবর্তন প্রয়োজন নেই।

**একক-build প্রবাহ:**

```
npm run build:release
  └─ rm -rf .build dist          (পরিষ্কার)
  └─ next build → .build/next/   (মধ্যবর্তী ফাইল)
  └─ assembleStandalone          (standalone + static + public + natives → dist/-এ কপি করে)
  └─ writes dist/BUILD_SHA       (HEAD sentinel লেখে)
```

Deploy-এর জন্য `npm run build` চালিয়ে পরে আলাদাভাবে `npm run build:cli` চালাবেন না — এর পরিবর্তে
`npm run build:release` ব্যবহার করুন, যা একটি command-এই clean rebuild + sentinel সম্পন্ন করে।

## রোলব্যাক

রিলিজে গুরুতর সমস্যা থাকলে:

1. `gh release edit vX.Y.Z --prerelease` (সর্বশেষ নয় হিসেবে চিহ্নিত করে)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (শুধু যদি ব্যবহারকারীরা এখনও এটি গ্রহণ না করে থাকেন)
3. অথবা: `release/vX.Y.0`-এ হটফিক্স → প্যাচ রিলিজ `vX.Y.(Z+1)`
4. অবিলম্বে GitHub Discussions এবং Discord-এ জানান

## কঠোর নিয়মাবলি

- কখনোই সরাসরি `main`-এ কমিট করবেন না
- কখনোই `main` বা `release/*` ব্রাঞ্চে `git push --force` ব্যবহার করবেন না
- কখনোই Husky হুক (`--no-verify`) এড়িয়ে যাবেন না
- কখনোই সিক্রেট, ক্রেডেনশিয়াল বা `.env` ফাইল কমিট করবেন না
- কভারেজ অবশ্যই ≥60/60/60/60 (স্টেটমেন্ট/লাইন/ফাংশন/ব্রাঞ্চ) থাকতে হবে
- `src/`, `open-sse/`, `electron/` বা `bin/`-এর প্রোডাকশন কোড পরিবর্তন করার সময় সর্বদা টেস্ট অন্তর্ভুক্ত বা আপডেট করুন
