## npm Trusted Publishing (v3.8.51 থেকে ডিফল্ট) — অনুরোধে staged, fallback হিসেবে direct

ডিফল্টভাবে `npm-publish.yml` **npm Trusted Publishing (OIDC)**-এর মাধ্যমে প্রকাশ করে:
`stage-npm` job (github-hosted) ওই run-এর জন্য GitHub-এর id-token-কে স্বল্পমেয়াদি npm
credential-এ বিনিময় করে—repository secrets-এ দীর্ঘমেয়াদি npm token থাকে না, কোনো 2FA prompt নেই এবং provenance সংযুক্ত থাকে।
2FA এড়িয়ে যাওয়া token-গুলো অবসরে পাঠানো হচ্ছে বলে npm বর্তমানে অনুমোদিত যে bypass ব্যবস্থা দেয়, এটি সেটিই;
এটি WS1.3 নিশ্চয়তা বজায় রেখে প্রকল্পের v3.8.48 পর্যন্ত থাকা সম্পূর্ণ স্বয়ংক্রিয় প্রক্রিয়াটি পুনরুদ্ধার করে
(ফাঁস হওয়া কোনো token একা publish করতে পারে না—কারণ কোনো token-ই নেই)।

**এককালীন setup (owner):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none)। এটি তৈরি না হওয়া পর্যন্ত স্বয়ংক্রিয় ধাপটি `ENEEDAUTH` দিয়ে ব্যর্থ হবে:
`publish_mode=staged` (নিচে) অথবা `direct` দিয়ে পুনরায় dispatch করুন।

### Staged publishing (অনুরোধে—`publish_mode=staged`)

npm-publish workflow আর সরাসরি publish করে না: এটি packed tarball-টি
boot করে (`check:pack-boot`) এবং তারপর `npm stage publish` চালায়—হুবহু একই bytes registry-তে
সংরক্ষিত থাকে, owner অনুমোদন না করা পর্যন্ত **install করা যায় না**। মানবীয় 2FA gate-টি
প্রমাণ যাচাইয়ের আগের অবস্থান থেকে পরের অবস্থানে সরানো হয়েছে।

**Workflow সবুজ হওয়ার পর owner-এর প্রক্রিয়া:**

1. `npm stage list omniroute`—stage id খুঁজুন (workflow summary-তেও দেখানো হয়)।
2. staged bytes যাচাই করুন (সুপারিশকৃত): `npm stage download <id>`, তারপর download করা
   tarball-টি একটি অস্থায়ী prefix-এ install করে boot করুন (`npm run check:pack-boot` CI-তে
   একই pack→install→boot ফলাফল স্বয়ংক্রিয়ভাবে নির্ধারণ করে)।
3. `npm stage approve <id>`—2FA prompt-টিই হলো publish। `npm stage reject <id>` বাতিল করে।
4. Publish-পরবর্তী নিরাপত্তা ব্যবস্থা: post-publish verifier (v3.8.49 পরিকল্পনার WS1.4)
   একটি clean container-এ public registry থেকে প্রকাশিত version install করে এবং সেটি boot করে।

**জরুরি fallback:** `publish_mode=direct` সহ `workflow_dispatch` পুরোনো
তাৎক্ষণিক `npm publish` পুনরুদ্ধার করে (শুধু staging নিজেই ত্রুটিপূর্ণ আচরণ করলে ব্যবহার করুন; কারণটি নথিভুক্ত করুন)।

**এককালীন hardening (owner, npmjs.com):** `omniroute`-এর Trusted Publisher-কে
stage-only mode-এ configure করুন, যাতে ফাঁস হওয়া কোনো দীর্ঘমেয়াদি token কোথাও থেকে সরাসরি
`npm publish` করতে না পারে—CI শুধু stage করতে পারবে; কেবল owner-এর 2FA-ই release করবে।

**ত্রুটিপূর্ণ artifact-এর playbook (অপরিবর্তিত):** ডিফল্ট তাৎক্ষণিক ব্যবস্থা হিসেবে
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` ব্যবহার করুন (কয়েক মিনিট লাগে, প্রত্যাবর্তনযোগ্য);
`npm unpublish` কেবল 72h/no-dependents সীমার মধ্যে ব্যবহার করুন এবং কখনোই প্রথম পদক্ষেপ হিসেবে নয়।
Docker-এর ক্ষেত্রে: কোনো version tag কখনো পুনর্লিখবেন না—rollback মানে `latest`-কে সর্বশেষ ভালো digest-এর দিকে পুনর্নির্দেশ করা।

**Docker Hub `latest` (প্রতিটি stable SemVer publish-এ আবশ্যক):**
`docker-publish` workflow-কে **উভয়** `X.Y.Z` এবং, `should-promote-latest.sh` যদি একমত হয় যে
এটিই সর্বোচ্চ stable SemVer, একই **digest**-সহ `:latest` tag করতে হবে।
Job শেষ হওয়ার পর: Hub-এর `latest` digest নতুন SemVer digest-এর সমান হবে এবং
`last_updated` এগিয়ে যাবে। Release notes-এ এমন fix-এর কথা বলা হলেও যা শুধু git-এ রয়েছে,
`:latest`-কে কোনো পুরোনো build-এ রেখে দেবেন না। Compose quickstart-গুলো `:latest` ব্যবহার করে;
GitOps-এর ক্ষেত্রে `X.Y.Z` pin করা চালিয়ে যেতে হবে। দেখুন
[Docker release channel](../guides/DOCKER_GUIDE.md#release-channels) এবং #10317।

## হটফিক্স ফাস্ট-লেন (লেবেল `hotfix`)

`hotfix` লেবেলযুক্ত একটি PR ভারী CI ম্যাট্রিক্স (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) এড়িয়ে যায় এবং দ্রুত, উচ্চ-সংকেতসম্পন্ন গেটগুলো বজায় রাখে: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
এবং tarball boot-smoke (`check:pack-boot`)। লক্ষ্য: ~33min-এর পরিবর্তে ≤15min-এ সবুজ।

**প্রবেশের নীতি — চারটিই আবশ্যক (Chromium/VS Code/Node-এর জরুরি লেন অনুসারে মডেল করা):**

1. **তীব্রতা**: প্রোডাকশন ভেঙে গেছে — প্রকাশিত artifact বুটের সময় ক্র্যাশ করে / একটি
   নিরাপত্তা সংশোধন / রিলিজটির প্রত্যেক ব্যবহারকারী প্রভাবিত। "গুরুত্বপূর্ণ" মানেই "ভেঙে গেছে" নয়।
2. **কর্তৃত্ব**: কেবল repository owner-ই `hotfix` লেবেল প্রয়োগ করেন। লেবেলটিই
   অনুমোদন — campaign PR-এ কখনোই নিজে থেকে এটি ব্যবহার করবেন না।
3. **প্রমাণ**: PR body-তে আগের সম্পূর্ণ-সবুজ heavy run-এর লিঙ্ক থাকে (যে suite-টি
   বাদ দেওয়া job-গুলো পুনরায় যাচাই করত), সঙ্গে fix-টির নিজস্ব আগে-ব্যর্থ-তারপর-সফল test।
4. **পরিধি**: শুধু cherry-pick — ন্যূনতম fix, কোনো refactor নয়, কোনো অপ্রাসঙ্গিক পরিবর্তন নয়।

বাদ দেওয়া coverage/ratchet surface-টি release branch-এর পরবর্তী পূর্ণ run-এ
পুনরায় যাচাই করা হয় (অবিচ্ছিন্ন release-green) — এই lane কেবল অপেক্ষা এড়িয়ে যায়, validation কখনো নয়।
শুধু test-সংক্রান্ত diff (সব file `tests/`-এর অধীনে, কোনোটি `tests/e2e/`-এর অধীনে নয়) কোনো label ছাড়াই
স্বয়ংক্রিয়ভাবে E2E matrix এড়িয়ে যায়।

### Build Layout

Repository-টি তিনটি স্বতন্ত্র output directory ব্যবহার করে — এগুলো কখনো গুলিয়ে ফেলবেন না:

| Directory | উদ্দেশ্য                                                    | ট্র্যাক করা হয়? |
| --------- | ----------------------------------------------------------- | ---------------- |
| `src/`    | Application source (TypeScript / TSX)                       | হ্যাঁ            |
| `.build/` | Build-এর মধ্যবর্তী ফাইল — `next build` output (`distDir`)   | না (gitignored)  |
| `dist/`   | বিতরণযোগ্য npm bundle — `assembleStandalone` দ্বারা সংযোজিত | না (gitignored)  |

> **Operator নোট:** remote VPS image directory এখনও `/usr/lib/node_modules/omniroute/app/`।
> শুধু **repository-এর ভেতরের** build output সরানো হয়েছে (`app/` → `dist/`)। Deploy skill-গুলো
> `dist/`-এর content remote `app/` directory-তে rsync করে — VPS path পরিবর্তনের প্রয়োজন নেই।

**একক-build flow:**

```
npm run build:release
  └─ rm -rf .build dist          (পরিষ্কার)
  └─ next build → .build/next/   (মধ্যবর্তী ফাইল)
  └─ assembleStandalone          (standalone + static + public + natives → dist/-এ copy করে)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Deploy-এর জন্য `npm run build` চালিয়ে পরে আলাদাভাবে `npm run build:cli` চালাবেন না — একটিমাত্র command-এ clean rebuild + sentinel সম্পন্ন করতে
`npm run build:release` ব্যবহার করুন।

### Dry-run (শুধু পঠনযোগ্য, যেকোনো সময় নিরাপদ)

```bash
npm run release:dry-run-lts-cut                       # প্রকৃত কাট: HEAD থেকে 3.9.0, আগের tag v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # source commit নির্দিষ্ট করুন
```

`scripts/release/dry-run-lts-cut.mjs` কিছুই কার্যকর করে না: এটি git এবং `gh` থেকে তথ্য পড়ে এবং
সম্পূর্ণ ক্রমটি প্রিন্ট করে — পূর্বশর্তসমূহ (source resolve হয়, আগের tag বিদ্যমান,
`package.json`-এ target version রয়েছে, একটি `release-freeze` issue খোলা আছে, বিদ্যমান
release branch-এ কোনো খোলা `Release branch not green` issue নেই — যে branch বিদ্যমান নয়,
সেটির জন্য `?` unknown দেখানো হয়, কখনোই green নয় — Mergify `release` queue কনফিগার করা
আছে (G11: `queue_rules`, `checks_timeout`, label `queue`), `release/*` ruleset এখনও deletion
ও force-push ব্লক করে, এবং `stable/v3` ও `develop` এখনও বিদ্যমান নয়), দুটি branch ধাপ,
কোন dormant-workflow trigger এবং `if:` condition সত্য হয় (এবং কোনগুলো repository variable
দ্বারা gated থাকে বা canonical repository-তে pinned থাকে), প্রত্যাশিত dist-tag-গুলো
(`latest` → 3.9.0, `next` ও `nightly` খালি) এবং rollback। Exit `0` = `RESULT: READY`,
`1` = কোনো blocking precondition ব্যর্থ হয়েছে (`✗`), `2` = usage error।
`--advisory <id,...>` কোনো check গোপন না করে সেটিকে warning (`!`)-এ নামিয়ে আনে।

3.9.0 release freeze এখনও খোলা থাকা অবস্থায় প্রকৃত কাটের dry-run চালান — tag-এর পরে এবং
Phase 12c freeze তুলে নেওয়ার আগে branch-গুলো তৈরি করা হয়।

### PR preview artifact (একবার build করুন, একই byte-গুলো promote করুন)

`.github/workflows/preview-artifact.yml` একটি PR head থেকে একটি production tarball build করে
এবং ঠিক সেই build-টিকেই validate করে (#8084 slice (a))। শুধু একই repository-এর PR;
কিছুই publish করা হয় না।

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # অথবা `preview-artifact` label যোগ করুন
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # preview install
```

run-টি `npm ci`, `npm run build:release`, `npm run check:pack-artifact` চালায়, tarball-টি
pack করে, `npm run check:pack-boot` চালায় (নকল secret, ephemeral data dir), পুনরায় pack
করে এবং digest অভিন্ন না হলে ব্যর্থ হয়; এরপর `artifact-identity.json` (head SHA, base SHA,
lockfile hash, platform, arch, node ABI, bundler, build policy —
`scripts/release/artifact-identity.mjs`) রেকর্ড করে এবং আলাদা job-এ tarball-টির attestation
তৈরি করে। preview promote করার অর্থ হলো সেই tarball install করা: source থেকে কখনোই
পুনরায় build করবেন না।

### কাট (3.9.0, GO-এর পরে)

1. [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md)-এ GO রেকর্ড করা হয়েছে।
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` থেকে `RESULT: READY` প্রিন্ট হয়।
3. dry-run যে command-গুলো প্রিন্ট করে সেগুলো দিয়ে হাতে `origin`-এ branch তৈরি করুন —
   script `origin`-এ push করতে অস্বীকার করে। review করা develop commit পুনরায় ব্যবহার করতে,
   প্রথমে আপনার fork-এর বিরুদ্ধে 3.9.0 tip-এ `--execute` মহড়াটি চালান; এটি উভয় SHA প্রিন্ট
   করে, এবং একই commit-গুলো push করা যায়:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. প্রথম PR land করার আগে `stable/v3` এবং `develop` protect করুন (ruleset + merge queue)।
5. branch-এর অস্তিত্ব অনুযায়ী dormant workflow-গুলো সক্রিয় হয়: `forward-port.yml`
   (`stable/v3`-এ push), `validate-stable-pr.yml` (`stable/v3`-এর PR) এবং
   `nightly-v4-build.yml` (`develop` build করে)। go-live-এর আগে
   `secrets.FORWARD_PORT_TOKEN` repository secret সেট করুন (যাতে forward-port PR-এ CI
   চলে); owner repository variable `vars.NIGHTLY_PUBLISH`-কে `true`-এ সেট না করা এবং npm
   Trusted Publishing `nightly-v4-build.yml` গ্রহণ না করা পর্যন্ত nightly publishing বন্ধ
   থাকে। Channel resolution হলো `scripts/release/dist-tag.mjs`, একই resolver
   `npm-publish.yml` ব্যবহার করে।
6. channel-গুলো যাচাই করুন: `npm view omniroute dist-tags --json`-এ `latest` = 3.9.0 দেখা
   যায় এবং v4 publish না হওয়া পর্যন্ত কোনো `next` / `nightly` থাকে না।
7. প্রয়োজন হলে rollback করুন:
   `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   এবং `npm dist-tag add omniroute@3.8.59 latest`।

3. অথবা: `release/vX.Y.0`-এ হটফিক্স → প্যাচ রিলিজ `vX.Y.(Z+1)`
4. অবিলম্বে GitHub Discussions এবং Discord-এ জানান

## কঠোর নিয়মাবলি

- কখনোই সরাসরি `main`-এ কমিট করবেন না
- `main` বা `release/*` ব্রাঞ্চে কখনোই `git push --force` ব্যবহার করবেন না
- কখনোই Husky হুক এড়িয়ে যাবেন না (`--no-verify`)
- কখনোই সিক্রেট, ক্রেডেনশিয়াল বা `.env` ফাইল কমিট করবেন না
- কভারেজ অবশ্যই ≥60/60/60/60 (স্টেটমেন্ট/লাইন/ফাংশন/ব্রাঞ্চ) বজায় রাখতে হবে
- `src/`, `open-sse/`, `electron/` বা `bin/`-এর প্রোডাকশন কোড পরিবর্তন করার সময় সর্বদা টেস্ট যোগ বা আপডেট করুন
