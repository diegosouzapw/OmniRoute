TPROXY transparent decrypt হলো OmniRoute-এর
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM স্ট্যাকের **৫ম ক্যাপচার মোড**। এটি kernel TPROXY + policy routing ব্যবহার করে Linux-এ
স্থানীয় বহির্মুখী HTTPS ট্র্যাফিক ইন্টারসেপ্ট ও **ডিক্রিপ্ট** করে — `/etc/hosts` স্পুফ
**না করে** এবং OS-ব্যাপী system-proxy সেটিংস পরিবর্তন **না করে**। এটি হেডলেস পরিবেশের
জন্য উপযোগী (পরিষ্কার করার মতো কোনো DNS পরিবর্তন নেই) এবং রিবুটের সময় firewall নিয়মগুলো
স্বয়ংক্রিয়ভাবে ফ্লাশ হয়।

অন্যান্য ক্যাপচার মোডের বিপরীতে, TPROXY-এর জন্য প্রতি-হোস্ট সেটআপের প্রয়োজন নেই: এটি একটি
লক্ষ্য পোর্টে **যেকোনো** গন্তব্য হোস্টকে স্বচ্ছভাবে ইন্টারসেপ্ট করে, প্রতিটি SNI hostname-এর
জন্য তাৎক্ষণিকভাবে ইস্যু করা leaf certificate দিয়ে TLS সমাপ্ত করে, ডিক্রিপ্ট করা
বিনিময়টি ক্যাপচার করে এবং অনুরোধটি মূল গন্তব্যের জন্য পুনরায় এনক্রিপ্ট করে।

> **শুধুমাত্র Linux, শুধুমাত্র root, অপ্ট-ইন।** এই মোডের জন্য Linux, একটি C toolchain
> দিয়ে তৈরি native addon এবং **CAP_NET_ADMIN** capability (সাধারণত root) প্রয়োজন। এটি
> শুধু-loopback AgentBridge API-এর পেছনে সীমাবদ্ধ এবং ডিফল্টভাবে নিষ্ক্রিয়। যেকোনো
> হোস্টের জন্য স্বাক্ষর করতে সক্ষম একটি বিশ্বস্ত MITM CA অত্যন্ত ক্ষমতাশালী —
> [§6 নিরাপত্তা](#6-security) দেখুন।

## §1 এটি কী এবং কখন ব্যবহার করবেন

অন্য চারটি ক্যাপচার মোডের প্রত্যেকটির একটি করে সীমাবদ্ধতা রয়েছে:

| মোড               | ট্র্যাফিক যেভাবে পরিচালিত হয়                | সীমাবদ্ধতা                                        |
| ----------------- | -------------------------------------------- | ------------------------------------------------- |
| AgentBridge       | নির্দিষ্ট হোস্ট সেটের `/etc/hosts` DNS spoof | শুধু নিবন্ধিত IDE-agent হোস্টগুলো                 |
| Custom Hosts      | প্রতি হোস্টে `/etc/hosts` DNS spoof          | প্রতি হোস্টে একটি এন্ট্রি; hosts সম্পাদনায় sudo  |
| HTTP_PROXY        | `HTTP_PROXY`/`HTTPS_PROXY` env               | শুধু env var মেনে চলা অ্যাপগুলো                   |
| System-wide proxy | OS proxy সেটিংস                              | গ্লোবাল স্টেট পরিবর্তন করে; প্রত্যাবর্তন প্রয়োজন |

এর পরিবর্তে TPROXY transparent decrypt **kernel** স্তরে ট্র্যাফিক পরিচালনা করে। এটি
`mangle OUTPUT` চেইনে একটি লক্ষ্য পোর্টে (ডিফল্ট `443`) যাওয়া নতুন স্থানীয় বহির্মুখী TCP
সংযোগগুলো চিহ্নিত করে, একটি `ip rule` চিহ্নিত প্যাকেটগুলোকে স্থানীয় ডেলিভারিতে পুনঃরুট করে,
এবং পুনঃপ্রবেশের সময় `mangle PREROUTING`-এর `TPROXY` target সেগুলোকে একটি
**IP_TRANSPARENT** listener-এর কাছে হস্তান্তর করে — যা এরপর TLS সমাপ্ত করে এবং plaintext
ক্যাপচার করে।

এটি ব্যবহার করুন যখন এমন কোনো প্রক্রিয়ার ট্র্যাফিক ক্যাপচার ও ডিক্রিপ্ট করতে চান, যা:

- AgentBridge-এ নিবন্ধিত নয় এমন কোনো হোস্টের সঙ্গে যোগাযোগ করে, এবং
- `HTTP_PROXY` মেনে চলে না, এবং
- system-wide proxy পরিবর্তন করে যেটিকে ব্যাহত করতে চান না।

যেহেতু ইন্টারসেপশন kernel-এ ঘটে, তাই উৎস প্রক্রিয়ায় **কোনো কনফিগারেশন পরিবর্তনের**
প্রয়োজন নেই — তবে প্রক্রিয়াটিকে অবশ্যই OmniRoute ইনস্টল করা dynamic CA-কে বিশ্বাস করতে
হবে ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) দেখুন)।

## §2 প্রয়োজনীয়তা

| প্রয়োজনীয়তা     | বিস্তারিত                                                                                                                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **OS**            | শুধুমাত্র Linux — **IP_TRANSPARENT** একটি Linux-নির্দিষ্ট socket option। অন্য সব platform-এ loader "অনুপলভ্য" ফেরত দেয়।                                           |
| **বিশেষাধিকার**   | transparent socket তৈরি এবং `iptables`/`ip` rule প্রয়োগের জন্য **CAP_NET_ADMIN** capability — বাস্তবে, root হিসেবে চালান।                                         |
| **Native addon**  | একটি ছোট N-API addon (`src/mitm/tproxy/native/transparent.c`) build করতে হবে অথবা prebuild হিসেবে সরবরাহ করতে হবে। [§3](#3-the-native-ip_transparent-addon) দেখুন। |
| **Kernel module** | `TPROXY`, `mangle`, এবং `mark` match support-সহ `iptables` (kernel 6.8.0-এর বিপরীতে যাচাই করা হয়েছে)।                                                             |

**সুশৃঙ্খল অবনমন:** কোনো প্রয়োজনীয়তা অনুপস্থিত থাকলে (non-Linux, toolchain নেই,
addon build করা হয়নি), addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
exception না ছুড়ে `null` ফেরত দেয়। এরপর capture-mode status-এ
`available: false` দেখানো হয়, dashboard toggle-টি **নিষ্ক্রিয়** থাকে এবং এর tooltip হয়
"TPROXY decrypt-এর জন্য Linux + root + native addon প্রয়োজন", আর OmniRoute-এর
বাকি অংশ কাজ করতে থাকে।

## §3 Native IP_TRANSPARENT addon

Node-এর `net` module `bind()`-এর _আগে_ `setsockopt(IP_TRANSPARENT)` করতে পারে না,
যা TPROXY-এর জন্য আবশ্যক (তা না হলে kernel redirect করা packet বাদ দেয়)। Addon-টি
(`src/mitm/tproxy/native/transparent.c`, `binding.gyp`-এর মাধ্যমে build করা) একটি ছোট N-API
module, যা তিনটি function প্রকাশ করে এবং `transparentSocket.ts`-এর মাধ্যমে ব্যবহৃত হয়:

| Addon function                        | Socket-এর কাজ                                                                                | যে কাজে ব্যবহৃত হয়                                                                 |
| ------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, raw fd ফেরত দেয় | transparent capture listener (Node `server.listen({ fd })`-এর মাধ্যমে fd গ্রহণ করে) |
| `setSocketMark(fd, mark)`             | বিদ্যমান fd-তে `setsockopt` **SO_MARK** প্রয়োগ করে                                          | anti-loop (proxy-এর নিজস্ব socket-গুলোকে mark করা)                                  |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()`-এর **আগে** `socket()` + **SO_MARK**, fd ফেরত দেয়                   | পুনরায় encrypted upstream forward (SYN mark বহন করে)                               |

মূল destination `socket.localAddress`/`localPort` থেকে পড়া হয় — TPROXY
এটি সংরক্ষণ করে, তাই কোনো **SO_ORIGINAL_DST**/NAT lookup-এর প্রয়োজন নেই।

### Addon build করা

```bash
npm run build:native:tproxy      # src/mitm/tproxy/native-এ cd করুন এবং node-gyp rebuild চালান
                                 # -> native/build/Release/transparent.node
```

- `npm run build` চলাকালে, `scripts/build/build-tproxy-native.mjs` `node-gyp
rebuild` চালায়। এটি **শুধুমাত্র Linux-এর জন্য এবং ব্যর্থ হলেও মারাত্মক নয়** — toolchain না থাকলে
  capture mode কেবল অনুপলভ্য থাকে।
- `assembleStandalone.mjs`, `build/Release/transparent.node`-কে
  standalone bundle-এ copy করে; `transparentSocket.ts` এটিকে module-relative এবং
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`)—উভয়ভাবেই resolve করে।
- `build/` এবং `prebuilds/` git-ignored — binary-টি **build করা হয়, কখনোই
  commit করা হয় না**।

Loader অগ্রাধিকারের ক্রমে অনুসন্ধান করে:
`native/build/Release/transparent.node`, তারপর `native/prebuilds/transparent.node`
(দুটিই module-relative এবং `<cwd>/src/mitm/tproxy/`-এর অধীনে)।

## §4 প্রতি-SNI ডায়নামিক CA এবং ট্রাস্ট-স্টোর ইনস্টলার

> **#6684 আপডেট:** AgentBridge স্ট্যাটিক সার্ভারটি (`src/mitm/server.cjs`) এখন
> একটি একক স্ট্যাটিক স্ব-স্বাক্ষরিত লিফের পরিবর্তে একই CA/লিফ আর্কিটেকচার প্যাটার্ন
> ব্যবহার করে। এটি একটি **স্বতন্ত্র** CA ইনস্ট্যান্স ব্যবহার করে
> (`src/mitm/cert/rootCa.ts`, যা `<DATA_DIR>/mitm/ca.key`/`ca.crt`-এ সংরক্ষিত)
> এবং আগে থেকেই থাকা `omniroute-mitm.crt` ট্রাস্ট-স্টোর স্লটের অধীনে ইনস্টল করে
> (সেখানে থাকা পুরোনো একক লিফটিকে প্রতিস্থাপন করে—দ্বৈত-ট্রাস্ট পরিষ্কার করার
> প্রয়োজন নেই), যা নিচে বর্ণিত TPROXY-এর নিজস্ব `omniroute-tproxy-ca.crt` স্লট
> থেকে সম্পূর্ণ আলাদা রাখা হয়। নতুন AgentBridge ইনস্টলেশনগুলো স্বয়ংক্রিয়ভাবে
> CA মডেল পায়; যে ইনস্টলেশন ইতোমধ্যে পুরোনো স্ট্যাটিক লিফকে ট্রাস্ট করেছে, সেটি
> অপারেটর `MITM_ROOT_CA_ENABLED=true`-এর মাধ্যমে সম্মতি না দেওয়া পর্যন্ত সেটিই
> ব্যবহার করতে থাকে (`src/mitm/cert/migration.ts` দেখুন)—**যেকোনো** হোস্টের জন্য
> লিফ স্বাক্ষর করতে সক্ষম একটি ট্রাস্টেড MITM CA পুরোনো নির্দিষ্ট-SAN লিফের তুলনায়
> কার্যত অনেক বেশি ক্ষমতাশালী, তাই ইতোমধ্যে ট্রাস্ট করা কোনো ইনস্টলেশনে এই পরিবর্তন
> কখনোই নীরবে করা হয় না।

ঐতিহাসিকভাবে, স্ট্যাটিক AgentBridge MITM সার্টিফিকেটটি শুধু এ কারণেই কাজ করত যে
AgentBridge একটি **নির্দিষ্ট** হোস্ট সেটের DNS স্পুফ করে (এখন নিচের মডেলটির সঙ্গে
একীভূত)। TPROXY **যেকোনো** হোস্ট ইন্টারসেপ্ট করে, তাই ক্লায়েন্ট যে SNI অনুরোধ
করে তার জন্য এর লিসেনারকে অবশ্যই একটি বৈধ লিফ উপস্থাপন করতে হবে—শুধু 4টি
antigravity হোস্টের পরিবর্তে সম্পূর্ণ `MITM_TOOL_HOSTS` সেটের (9টি টুল এন্ট্রি)
জন্য AgentBridge-এরও এখন একই প্রয়োজনীয়তা রয়েছে।

### ডায়নামিক CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` একটি লোকাল CA পরিচালনা করে (`selfsigned` ডিপেন্ডেন্সির ওপর
নির্মিত), যা:

- `generateMitmCa()`-এর মাধ্যমে একটি দীর্ঘমেয়াদি CA তৈরি করে (CN `"OmniRoute MITM CA"`,
  10 বছরের বৈধতা, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-বিট RSA / SHA-256)।
- `issueLeafCert()`-এর মাধ্যমে **চাহিদামতো প্রতি SNI হোস্টনেমের জন্য একটি লিফ**
  ইস্যু করে (1 বছরের বৈধতা, `subjectAltName` = SNI হোস্ট) এবং প্রতি হোস্টনেমে
  একটি করে `tls.SecureContext` ক্যাশ করে।
- TLS-টার্মিনেটিং সার্ভারের জন্য `createSNICallback()` প্রকাশ করে
  ([§5](#5-how-decrypt-and-capture-work) দেখুন)।
- রিস্টার্টের পরেও CA স্থিতিশীল রাখতে একটি `existingCa` দিয়ে নির্মাণ করা যায়
  (ফলে ট্রাস্ট স্টোর পুনরায় ইনস্টল করার প্রয়োজন হয় না)।

CA প্রাইভেট কী **কখনোই মেশিনের বাইরে যায় না**।

### ট্রাস্ট-স্টোর ইনস্টলার (`src/mitm/tproxy/caTrust.ts`)

ইন্টারসেপ্ট করা ক্লায়েন্টকে অবশ্যই ডায়নামিক CA-কে ট্রাস্ট করতে হবে, তাই ক্যাপচার
মোড চালু করলে CA সার্টিফিকেটটি OS ট্রাস্ট স্টোরে একটি **নিবেদিত স্লটের** অধীনে
ইনস্টল করা হয়—`omniroute-tproxy-ca.crt` (কনস্ট্যান্ট `TPROXY_CA_CERT_NAME`)—
যা স্ট্যাটিক MITM সার্টিফিকেটের স্লট (`omniroute-mitm.crt`) থেকে আলাদা রাখা হয়,
যাতে তারা কখনো একে অপরকে ওভাররাইট না করে।

`installTproxyCa(caPem, sudoPassword?)` ডিস্ট্রোর অ্যাঙ্কর ডিরেক্টরি শনাক্ত করে
(ক্রম অনুযায়ী: প্রথমে Debian-স্টাইল) এবং সংশ্লিষ্ট রিফ্রেশ কমান্ড চালায়:

| অ্যাঙ্কর ডিরেক্টরি                          | রিফ্রেশ কমান্ড           |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

ইনস্টলেশন প্রথমে PEM-টি একটি অস্থায়ী ফাইলে স্টেজ করে, তারপর (বিশেষাধিকারসহ)
অ্যাঙ্কর ডিরেক্টরিতে `mkdir -p` চালায়, স্টেজ করা ফাইলটি সেখানে `cp` করে এবং
রিফ্রেশ কমান্ড চালায়। `uninstallTproxyCa()` শুধু নিবেদিত স্লটটি সরিয়ে দেয়
(স্ট্যাটিক MITM সার্টিফিকেট অক্ষত রেখে) এবং রিফ্রেশ করে—Linux নয় এমন সিস্টেমে
এটি কোনো কাজ করে না।

বিশেষাধিকারপ্রাপ্ত সব কমান্ড `execFileWithPassword` (`src/mitm/systemCommands.ts`)
এর মাধ্যমে চলে—**আর্গুমেন্ট অ্যারে, কোনো shell নয়, কোনো স্ট্রিং ইন্টারপোলেশন
নয়** এমন `spawn` (কঠোর নিয়ম #13)। প্রসেসটি root হলে (যেমন VPS-এ), টার্গেটটি
সরাসরি চলে এবং কোনো পাসওয়ার্ডের প্রয়োজন হয় না; root নয় এমন ডেস্কটপে
`sudoPassword` stdin-এ `sudo -S`-এর মাধ্যমে পাঠানো হয়।

> ট্রাস্ট-স্টোর ইনস্টলেশন অনুমোদনের জন্য ডেস্কটপের `sudoPassword` POST body-তে
> সরবরাহ করা হয়; প্রসেসটি root হলে এটি সম্পূর্ণভাবে উপেক্ষা করা হয়।

## §5 ডিক্রিপশন ও ক্যাপচার যেভাবে কাজ করে

পাইপলাইনটি (সবকিছু `src/mitm/tproxy/`-এর অধীনে):

```
স্থানীয় অ্যাপ  ──TCP/443──▶  mangle OUTPUT সংযোগটিকে চিহ্নিত করে (fwmark)
                              ip rule → স্থানীয় রাউটিং টেবিল → lo
                              mangle PREROUTING TPROXY → IP_TRANSPARENT লিসেনার (পোর্ট 8443)
                                  │  captureMode.ts: socket.localAddress থেকে মূল গন্তব্য পড়ে
                                  ▼
                              tlsCapture.ts:
                                1. প্রতি-SNI লিফ (dynamicCert) দিয়ে CLIENT-এর TLS সমাপ্ত করে
                                2. অভ্যন্তরীণ http.Server ডিক্রিপ্ট করা প্লেইনটেক্সট পার্স করে
                                3. ক্যাপচার → source: "tproxy" সহ globalTrafficBuffer.push()
                                   (sanitizeHeaders + maskSecret প্রয়োগ করা হয়)
                                4. বাইপাস-মার্কযুক্ত সকেটের মাধ্যমে মূল গন্তব্যে
                                   পুনরায় এনক্রিপ্ট করে ফরোয়ার্ড করে (connectMarked, অ্যান্টি-লুপ)
                                  │
                                  ▼
                              মূল আপস্ট্রিম (api.example.com)
```

- **TLS সমাপ্তি** (`createTlsCaptureServer`): ডায়নামিক CA-এর SNI কলব্যাক ব্যবহার করে
  কাঁচা ইন্টারসেপ্ট করা সকেটটিকে সার্ভার-সাইড `tls.TLSSocket`-এ র্যাপ করে,
  তারপর ডিক্রিপ্ট করা স্ট্রিমটি একটি অভ্যন্তরীণ `http.Server`-এর কাছে পাঠায় (প্রচলিত MITM
  সমাপ্তি কৌশল)। সকেটের আয়ুষ্কাল `MITM_IDLE_TIMEOUT_MS` দ্বারা সীমাবদ্ধ থাকে, যাতে
  আটকে থাকা কোনো টানেল ফাইল ডেস্ক্রিপ্টর নিঃশেষ করতে না পারে।
- **ক্যাপচার** (`handleDecryptedRequest`): `source: "tproxy"`, শুরুতে
  `"in-flight"` স্ট্যাটাস, `sanitizeHeaders()`-এর মধ্য দিয়ে পাঠানো হেডার এবং
  `maskSecret()`-এর মধ্য দিয়ে পাঠানো বডিসহ একটি `InterceptedRequest` বাফারে
  পুশ করে। এরপর রেসপন্স, আকার এবং ল্যাটেন্সি দিয়ে এন্ট্রিটি আপডেট করা হয়।
- **পুনরায় এনক্রিপ্ট করা ফরোয়ার্ড** (`createForward` / `realForward`): মূল
  গন্তব্যে পুনরায় এনক্রিপ্ট করে। `rejectUnauthorized`-এর ডিফল্ট মান **`true`**
  (ডিফল্টভাবে সুরক্ষিত) — ক্লায়েন্ট যে SNI/Host অনুরোধ করেছে, তার বিপরীতে আপস্ট্রিম
  সার্টিফিকেট যাচাই করা হয়; ফলে মূল ক্লায়েন্ট যা প্রত্যাখ্যান করত, প্রক্সিও ঠিক সেটিই
  প্রত্যাখ্যান করে।

### অ্যান্টি-লুপ (SO_MARK)

যেহেতু নিয়মগুলো নতুন স্থানীয় আউটবাউন্ড সংযোগ চিহ্নিত করে, তাই প্রক্সির **নিজস্ব**
পুনরায় এনক্রিপ্ট করা ফরোয়ার্ড সাধারণত আবার ইন্টারসেপ্ট হতো—যার ফলে একটি অসীম লুপ
সৃষ্টি হতো। ফরোয়ার্ড পাথ একটি বাইপাস সকেট মার্ক (**SO_MARK**) দিয়ে এটি প্রতিরোধ করে:

- `realForward` তার আপস্ট্রিম সকেটটি `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  দিয়ে খোলে—`DEFAULT_BYPASS_MARK = 0x539`—যা `connect()`-এর **আগেই**
  **SO_MARK** সেট করে, ফলে ফরোয়ার্ডের SYN বাইপাস মার্ক বহন করে।
- `mangle OUTPUT` নিয়মটি ইতিমধ্যেই বাইপাস মার্ক বহনকারী সংযোগগুলোকে বাদ দেয়
  (`-m mark ! --mark <bypassMark>`), ফলে প্রক্সির ফরোয়ার্ডকে পুনরায় চিহ্নিত করা
  হয় **না** এবং এটি আবার TPROXY-তে প্রবেশ করে না।

> বাস্তবায়ন-সংক্রান্ত নোট: বাইপাস-মার্কযুক্ত সকেটটি অবশ্যই এজেন্টের
> `createConnection`-এ ইনস্টল করতে হবে (`https.request({ createConnection })` কোনো
> এজেন্ট উপস্থিত থাকলে নীরবে উপেক্ষিত হয়), নইলে ফরোয়ার্ড একটি মার্কবিহীন সকেট খুলবে
> এবং লুপটি ফিরে আসবে। এটি ছিল e2e-যাচাইকৃত অ্যান্টি-লুপ সংশোধন।

| **কোনো শেল ইন্টারপোলেশন নেই**        | সব `iptables`/`ip`/ট্রাস্ট-স্টোর কমান্ড আর্গুমেন্ট অ্যারে সহ `execFile`/`execFileWithPassword`-এর মাধ্যমে চালানো হয় (কঠোর নিয়ম #13)।                                                                                                                                                                                                                                                                    |
| **আপস্ট্রিম সার্টিফিকেট যাচাইকরণ**   | পুনরায় এনক্রিপ্ট করা ফরওয়ার্ডটি ডিফল্টভাবে আপস্ট্রিম সার্টিফিকেট যাচাই করে (`rejectUnauthorized: true`)।                                                                                                                                                                                                                                                                                                |
| **ত্রুটি স্যানিটাইজেশন**             | রুটটির ত্রুটি প্রতিক্রিয়াগুলো `sanitizeErrorMessage()`-এর মধ্য দিয়ে যায় (কঠোর নিয়ম #12)।                                                                                                                                                                                                                                                                                                              |

**MITM CA একটি শক্তিশালী সক্ষমতা।** OS-এর বিশ্বস্ত এমন একটি CA, যা যেকোনো
হোস্টের জন্য স্বাক্ষর করতে পারে, তার অর্থ OmniRoute যা কিছু ইন্টারসেপ্ট করে, তা ডিক্রিপ্ট করা সম্ভব। এটি
স্পষ্ট, শুধু-লোকাল TPROXY ক্যাপচার মোডের আড়ালে সুরক্ষিত, ডিফল্টভাবে বন্ধ থাকে এবং মোডটি
বন্ধ করলে ট্রাস্ট-স্টোর এন্ট্রিটি সরিয়ে ফেলা হয়।

## §7 ট্রানজ্যাকশনাল ফায়ারওয়াল প্রয়োগ / পূর্বাবস্থায় ফেরানো

কোনো ক্র্যাশের ফলে কখনোই একটি `mangle` নিয়ম বা অচল রুট অবশিষ্ট থাকা উচিত নয়। কমান্ড বিল্ডার
(`src/mitm/tproxy/commands.ts`) এবং রানার (`src/mitm/tproxy/setup.ts`) নিশ্চিত করে যে
**পূর্বাবস্থায় ফেরানো হলো প্রয়োগের হুবহু বিপরীত, বিপরীত ক্রমে**।

`applyTproxy(cfg)` প্রয়োগের কমান্ডগুলো ক্রমানুসারে চালায়; **যেকোনো** ব্যর্থতায় এটি
সর্বোচ্চ প্রচেষ্টায় পূর্ণ `revertTproxy(cfg)` চালায় এবং ত্রুটিটি পুনরায় নিক্ষেপ করে — ফলে ফায়ারওয়ালটি হয়
সম্পূর্ণভাবে প্রয়োগ করা থাকে, নয়তো সম্পূর্ণভাবে পূর্বাবস্থায় ফেরানো থাকে, কখনোই আংশিকভাবে প্রয়োগ করা থাকে না। `revertTproxy(cfg)`
বিপরীত কমান্ডগুলো বিপরীত ক্রমে চালায় এবং ব্যর্থতাগুলো উপেক্ষা করে (আইডেমপোটেন্ট — নিঃশর্তভাবে কল করা
নিরাপদ, যেমন AgentBridge-এর `repairMitm()` ক্লিনআপ থেকে)।

যেকোনো কমান্ডের আগে `validateTproxyConfig(cfg)` চালানো হয়: পোর্টগুলো অবশ্যই `1–65535` হতে হবে,
`mark`/`routeTable`/`bypassMark` অবশ্যই ধনাত্মক পূর্ণসংখ্যা হতে হবে, এবং `bypassMark` অবশ্যই
`mark` থেকে আলাদা হতে হবে (অ্যান্টি-লুপ)।

### প্রয়োগের কমান্ডসমূহ (ক্রম অনুযায়ী)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

পূর্বাবস্থায় ফেরানোর সময় এগুলো বিপরীত ক্রমে মুছে ফেলা হয়: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`।

> রেসিপিটি **OUTPUT-ভিত্তিক**, কারণ MITM ব্যবহারের ক্ষেত্রটি হলো _স্থানীয়_ আউটবাউন্ড
> ট্র্যাফিক (একই হোস্টে থাকা অ্যাপ), যা শুধু `PREROUTING`-এ থাকা TPROXY দেখতে
> পায় না — `PREROUTING` শুধু ফরওয়ার্ড করা ট্র্যাফিক দেখে। `OUTPUT` চেইনটি নতুন
> স্থানীয় সংযোগগুলোতে মার্ক বসায়, `ip rule` সেগুলোকে স্থানীয় ডেলিভারিতে (`lo`) পুনরায় রুট করে, এবং
> এরপর `PREROUTING` সেগুলোকে ট্রান্সপারেন্ট লিসেনারের কাছে বরাদ্দ করে।

## §8 কনফিগারেশন

শুরু করার অনুরোধটি (`POST /api/tools/agent-bridge/tproxy`) নিম্নলিখিত
ফিল্ডগুলো গ্রহণ করে, যেগুলো `StartTproxyBodySchema` (`tproxy/route.ts`) দ্বারা যাচাই করা হয়। সবগুলোই ঐচ্ছিক
এবং দেওয়া না হলে তাদের ডিফল্ট মান ব্যবহৃত হয়:

| ফিল্ড            | ধরন                | ডিফল্ট   | নোট                                                                                                                      |
| ---------------- | ------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------ |
| **dport**        | int (1–65535)      | `443`    | স্বচ্ছভাবে ইন্টারসেপ্ট করার জন্য গন্তব্য TCP পোর্ট                                                                       |
| **mark**         | int (≥1)           | `0x2333` | `OUTPUT`-এ সেট করা ফায়ারওয়াল মার্ক, যা `ip rule` + `PREROUTING` দ্বারা মেলানো হয়                                      |
| **onPort**       | int (1–65535)      | `8443`   | ট্রান্সপারেন্ট (**IP_TRANSPARENT**) লিসেনার যে পোর্টে বাইন্ড করে                                                         |
| **routeTable**   | int (≥1)           | `233`    | `local 0.0.0.0/0` রুট ধারণকারী পলিসি-রাউটিং টেবিলের আইডি                                                                 |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | প্রক্সি তার নিজস্ব আপস্ট্রিম সংযোগে যে বাইপাস সকেট মার্ক (**SO_MARK**) সেট করে; `OUTPUT`-এ বাদ দেওয়া হয় (অ্যান্টি-লুপ) |
| **sudoPassword** | string             | —        | শুধু নন-রুট ডেস্কটপের জন্য: ট্রাস্ট-স্টোর ইনস্টল অনুমোদন করে; রুট হিসেবে চললে উপেক্ষা করা হয়                            |

TPROXY-এর জন্য **কোনো এনভায়রনমেন্ট ভেরিয়েবল নেই** — সব কনফিগারেশন
POST বডি অথবা উপরের ডিফল্টগুলোর মাধ্যমে করা হয়।

## §9 Traffic Inspector থেকে সক্রিয় করা

1. **Traffic Inspector** (`/dashboard/tools/traffic-inspector`) খুলুন।
2. ক্যাপচার-মোড টুলবারে **"TPROXY ডিক্রিপ্ট"** ⚠ বোতামটি খুঁজুন
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`)।
   - যদি এটি **নিষ্ক্রিয়** থাকে এবং টুলটিপে "TPROXY ডিক্রিপ্টের জন্য Linux + root +
     নেটিভ অ্যাডঅন প্রয়োজন" দেখায়, তাহলে এই হোস্টে নেটিভ অ্যাডঅনটি অনুপলভ্য (Linux নয়,
     কোনো টুলচেইন নেই, অথবা অ্যাডঅন বিল্ড করা হয়নি)। [§2](#2-requirements) এবং [§3](#3-the-native-ip_transparent-addon) দেখুন।
3. বোতামটিতে ক্লিক করুন। এটি `startTproxyCaptureMode()`-এর মাধ্যমে
   `POST /api/tools/agent-bridge/tproxy` কল করে
   (`src/lib/inspector/tproxyCaptureApi.ts`), যা:
   ডায়নামিক CA তৈরি করে, ট্রান্সপারেন্ট লিসেনার খোলে, ফায়ারওয়াল
   রুল প্রয়োগ করে এবং OS ট্রাস্ট স্টোরে CA ইনস্টল করে।
4. চলমান অবস্থায় টগলটি অ্যাম্বার রঙের হয়ে যায় এবং লাইভ ইন্টারসেপ্ট সংখ্যা
   (`· <interceptCount>`) দেখায়। ইন্টারসেপ্ট করা রিকোয়েস্টগুলো রিকোয়েস্ট তালিকায়
   `source: "tproxy"` সহ দেখা যায়।
5. বন্ধ করতে আবার ক্লিক করুন — `stopTproxyCaptureMode()`-এর মাধ্যমে
   `DELETE /api/tools/agent-bridge/tproxy` লিসেনার বন্ধ করে, CA আনইনস্টল করে এবং
   ফায়ারওয়াল রুলগুলো প্রত্যাবর্তন করায়।

ক্যাপচার-মোডের স্ট্যাটাস (চলমান / উপলভ্য / ইন্টারসেপ্ট সংখ্যা / লিসেনার পোর্ট)
`GET /api/tools/agent-bridge/tproxy` থেকে আসে (`src/mitm/tproxy/captureManager.ts`-এ
`getCaptureStatus()`)। একবারে কেবল **একটি** TPROXY সেশন চলে —
দ্বিতীয়টি শুরু করার চেষ্টা "TPROXY ক্যাপচার মোড ইতিমধ্যেই চলছে" বার্তাসহ প্রত্যাখ্যাত হয়।

## §10 সমস্যা সমাধান

### টগলটি নিষ্ক্রিয়

নেটিভ অ্যাডঅনটি লোড করা যাচ্ছে না। নিশ্চিত করুন: আপনি Linux ব্যবহার করছেন, অ্যাডঅনটি
বিল্ড করেছেন (`npm run build:native:tproxy`) এবং প্রসেসটি `transparent.node` লোড
করতে পারে। `isTransparentSocketAvailable()` টগলটির প্রাপ্যতা নিয়ন্ত্রণ করে;
অ্যাডঅন অনুপস্থিত থাকলে `GET /api/tools/agent-bridge/tproxy`
`available: false` ফেরত দেয়।

### কিছুই ক্যাপচার হচ্ছে না

- নিশ্চিত করুন যে ইন্টারসেপ্ট করা প্রসেসটি প্রকৃতপক্ষে কনফিগার করা `dport`-এর সঙ্গে
  সংযোগ করে (ডিফল্ট `443`)।
- নিশ্চিত করুন যে প্রসেসটি ডায়নামিক CA-কে বিশ্বাস করে। CA-টি
  `omniroute-tproxy-ca.crt` নামে ইনস্টল করা হয়; নিজস্ব ট্রাস্ট স্টোরযুক্ত অ্যাপে
  (Firefox/Chrome NSS) সার্টিফিকেটটি সেখানেও যোগ করার প্রয়োজন হতে পারে।
- সার্টিফিকেট-বিশ্বস্ততা / সার্ভার স্বাস্থ্য পরীক্ষার জন্য AgentBridge-এর
  **Diagnose** স্ব-পরীক্ষা চালান
  ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md) দেখুন)।

### ক্র্যাশের পরে থেকে যাওয়া ফায়ারওয়াল রুল

`revertTproxy()` হলো apply-এর সঠিক বিপরীত এবং এটি আইডেমপোটেন্ট। মোড বন্ধ করলে
রুলগুলো প্রত্যাবর্তিত হয়; যদি সেশনের মাঝখানে OmniRoute বন্ধ হয়ে যায়, তাহলে
অনাথ হয়ে থাকা সিস্টেম স্টেট (DNS spoof, root CA, system proxy) পূর্বাবস্থায়
ফেরাতে AgentBridge-এর **Repair** অ্যাকশন
(`POST /api/tools/agent-bridge/repair`) ব্যবহার করুন। TPROXY `mangle` রুল এবং রুটও
রিবুটের সময় স্বয়ংক্রিয়ভাবে ফ্লাশ হয়ে যায়।

### অসীম লুপ / প্রক্সি তার নিজের ফরওয়ার্ড ইন্টারসেপ্ট করে

এটি অ্যান্টি-লুপ পরিস্থিতি। নিশ্চিত করুন যে `bypassMark`, `mark` থেকে আলাদা
(ভ্যালিডেশন এটি নিশ্চিত করে) এবং ফরওয়ার্ডে `connectMarked` ব্যবহার করা হয়
(`realForward`-এ এটি করা হয়)। [§5 অ্যান্টি-লুপ](#anti-loop-so_mark) দেখুন।
