## সারসংক্ষেপ

OmniRoute এখন `/api/v1/relay/chat/completions`-এর জন্য তিনটি রিলে মোড সমর্থন করে:

- `ts`: একই প্রসেসের মধ্যে TypeScript রিলে ব্যবহার করে।
- `bifrost`: Bifrost গেটওয়ে বাধ্যতামূলকভাবে ব্যবহার করে।
- `auto`: উপলভ্য থাকলে Bifrost-কে অগ্রাধিকার দেয় এবং ব্যর্থ হলে TypeScript-এ ফলব্যাক করে।

যখন আপনি উচ্চ অনুরোধ হারে সিস্টেম চালান (প্রতিদিন বিপুল সংখ্যক টোকেন, প্রায়-অবিচ্ছিন্ন থ্রুপুট), তখন সর্বোত্তম কৌশল হলো ফলব্যাক পথটি স্পষ্ট ও দ্রুত রাখা, যাতে মূল কার্যকর পথটি কোনো অচল সাইডকারের কারণে কখনো অবরুদ্ধ না হয়।

## মোডের আচরণ

- `ts`
  - পরিচালনাগত জটিলতা সর্বনিম্ন।
  - সব রাউটিং ও যাচাইকরণ Node-এ চলে।
  - উপলভ্যতার জন্য সাইডকারের ওপর কোনো নির্ভরতা নেই।
- `bifrost`
  - সব অনুরোধ বাধ্যতামূলকভাবে সাইডকার গেটওয়ের মধ্য দিয়ে পাঠায়।
  - কোনো স্বয়ংক্রিয় ফলব্যাক নেই।
  - কেবল তখনই উপযোগী, যখন সাইডকারের স্বাস্থ্য ও ল্যাটেন্সি নিশ্চিত।
- `auto`
  - সাইডকারে পৌঁছানো গেলে এবং এটি সক্রিয় থাকলে সেটি ব্যবহার করা হয়।
  - ব্যর্থ প্রচেষ্টা ফলব্যাক হেডার সক্রিয় করে এবং ট্র্যাফিক TS-এ ফিরিয়ে দেয়, যাতে অনুরোধ সফল হওয়ার সময়সীমা নিয়ন্ত্রিত থাকে।
  - যখন কেবল সাইডকারের মাধ্যমে কঠোর রাউটিংয়ের চেয়ে আপটাইম বেশি গুরুত্বপূর্ণ, তখন প্রোডাকশনের জন্য এই মোডটি সবচেয়ে নিরাপদ পছন্দ।

## বর্তমানে 9router বনাম CLIPROXYAPI

9router এবং CLIPROXYAPI উভয়ই এমন ইন্টিগ্রেশন, যা ঐতিহাসিকভাবে আপস্ট্রিম প্রোভাইডারগুলোর জন্য সামঞ্জস্যপূর্ণ পথ প্রদান করেছে।

- 9router হলো আপস্ট্রিম অর্কেস্ট্রেশন ও সামঞ্জস্য আচরণের জন্য একটি এম্বেডেড পথ।
- CLIPROXYAPI হলো CLI / SDK ধরনের ট্র্যাফিকের জন্য একটি প্রক্সি API ব্রিজ।
- যখন আপনার একটি স্বতন্ত্র সাইডকার-সদৃশ হপ এবং কম-ল্যাটেন্সির লোকাল ডিসপ্যাচ প্রয়োজন, তখন এক্সটার্নালাইজড পথ হিসেবে Bifrost-কে স্থিতিশীল করা হচ্ছে।

আপনি বর্তমানে 9router/CLIPROXYAPI তুলনা করলে:

- হ্যান্ডঅফের আগে API রুটেই অনুরোধ স্বাক্ষরকরণ, অ্যালাউলিস্ট যাচাই এবং DB নীতির গেটগুলো রাখুন।
- কোনো ওয়ার্কফ্লোতে কঠোর সাইডকার আচরণ ও প্রতি-অনুরোধে কম বৈচিত্র্য প্রয়োজন হলে, `OMNIROUTE_RELAY_BACKEND=bifrost` ব্যবহার করুন।
- কোনো ঘটনার সময় মসৃণ অবনতি-সহ সাইডকার স্থিতিস্থাপকতা প্রয়োজন হলে, `OMNIROUTE_RELAY_BACKEND=auto` ব্যবহার করুন।

## ব্যাকএন্ড সীমানার চুক্তি

স্থিতিশীল প্রোডাক্ট সীমানা হলো OmniRoute রিলে API, ড্যাশবোর্ডের বাস্তবায়ন নয়। Next.js ড্যাশবোর্ড লোকাল সার্ভিস ইনস্টল, কনফিগার ও তত্ত্বাবধান করতে পারে, কিন্তু অনুরোধের রাউটিং রিলে API দিয়ে প্রবেশ করা এবং সেই সীমানার পেছনে হ্যান্ডঅফ হওয়া উচিত।

দীর্ঘমেয়াদি ব্যাকএন্ড বিকল্পসমূহ:

- TypeScript রিলেকে একই প্রসেসের মধ্যে চলা নীতি ও ফলব্যাক পথ হিসেবে রাখুন। যেকোনো ব্যাকএন্ড হ্যান্ডঅফের আগে প্রমাণীকরণ, অ্যালাউলিস্ট, অনুরোধ স্বাভাবিকীকরণ, হিসাবরক্ষণ এবং নিরাপত্তা যাচাই এখানেই থাকবে।
- ডিপ্লয়মেন্টে রাউটিংয়ের কম বৈচিত্র্য, কেন্দ্রীভূত প্রোভাইডার রোটেশন অথবা একাধিক OmniRoute রেপ্লিকা জুড়ে স্কেল-আউট প্রয়োজন হলে, Bifrost-কে পছন্দের উচ্চ-থ্রুপুট Tier-1 সাইডকার হিসেবে ব্যবহার করুন।
- 9router এবং CLIPROXYAPI-কে এম্বেডেড সামঞ্জস্য সার্ভিস হিসেবে রাখুন। এগুলো তত্ত্বাবধানে থাকা লোকাল প্রসেস হিসেবে চলে এবং যখন এদের প্রোভাইডার/CLI আচরণই কাঙ্ক্ষিত অ্যাডাপ্টার, তখন উপযোগী; তবে এগুলোকে ডিফল্ট Tier-1 রাউটিং ইঞ্জিন করা উচিত নয়।
- ড্যাশবোর্ডকে মূল কার্যকর পথে ইচ্ছামতো সার্ভিস URL পাঠাতে দেবেন না। UI-প্রদত্ত URL হলো কনফিগারেশন ইনপুট; রাউটিং কোডের উচিত সার্ভার-সাইড সেটিংস ও সুপারভাইজরের অবস্থা থেকে নিবন্ধিত এবং স্বাস্থ্য-পরীক্ষিত ব্যাকএন্ড নির্ধারণ করা।
- বর্তমানে তত্ত্বাবধানে থাকা সার্ভিসগুলোর জন্য লুপব্যাক HTTP-কে অগ্রাধিকার দিন, কারণ পরিচালিত প্রসেসগুলো ইতিমধ্যেই HTTP-সামঞ্জস্যপূর্ণ API প্রকাশ করে, রুট গার্ড সীমানাটি অডিট করতে পারে এবং ব্যর্থতা/ফলব্যাক আচরণ অনুরোধ লগে দৃশ্যমান থাকে। ভবিষ্যতে SDK বা সকেট ট্রান্সপোর্ট যোগ করা কেবল তখনই সার্থক, যখন সেটি বিচ্ছিন্নতা বা ফলব্যাকের অর্থগত আচরণ দুর্বল না করে পরিমাপযোগ্যভাবে p99 রাউটিং ল্যাটেন্সি কমায়।

অত্যন্ত উচ্চ-থ্রুপুট ডিপ্লয়মেন্টের জন্য তাই ডিফল্ট উত্তর হলো Bifrost সক্রিয় রেখে `auto`: সফলতার হার বজায় রাখতে TypeScript ফলব্যাক সংরক্ষণ করে মূল কার্যকর পথে Go সাইডকার ব্যবহার করুন। মসৃণ অবনতির চেয়ে কঠোরভাবে কেবল সাইডকার ব্যবহারের আচরণ বেশি গুরুত্বপূর্ণ হলেই `bifrost` ব্যবহার করুন।

## উচ্চ-থ্রুপুট নির্দেশিকা

ধারাবাহিক উচ্চ RPM/RPS এবং কঠোর সফলতা SLO-এর জন্য:

1. ব্যবহারিক কুলডাউন ও ব্যর্থতা টেলিমেট্রিসহ `auto` ব্যবহার করুন।
2. আপস্ট্রিম যাচাইকরণ ও API-কী যাচাই TypeScript রুটের সীমানায় রাখুন।
3. স্পষ্ট হেডার/কাউন্টার সক্রিয় করুন, যাতে আপনার সতর্কীকরণ ব্যবস্থা ফলব্যাকের হার ও কারণ দেখতে পায়।
4. অনির্দিষ্টকাল অপেক্ষা না করে দ্রুত ব্যর্থ হওয়ার জন্য সাইডকার টাইমআউট সমন্বয় করুন।
5. সার্ভিসের স্বয়ংক্রিয় পুনরারম্ভ এবং স্বাস্থ্য টেলিমেট্রি লুপ সচল রাখুন, যাতে ফলব্যাক সত্যিই ব্যতিক্রমী থাকে।

## প্রস্তাবিত ভিত্তিগত কনফিগারেশন

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- API কী, অ্যালাউলিস্ট, স্যানিটাইজার এবং রেট-লিমিট যাচাই রুট হ্যান্ডলারে সক্রিয় রাখুন (ডাউনস্ট্রিমে ফরওয়ার্ড করার আগে এগুলো সবসময় চলে)।
- আপনার রিভার্স প্রক্সি ও অনুরোধ লগ থেকে ফলব্যাক মেট্রিক্স এক্সপোর্ট করুন, যাতে সাইডকার বিভ্রাট এক মিনিটের মধ্যে দৃশ্যমান হয়।

## প্রোভাইডার প্লাগইন চুক্তি

সাইডকারগুলোর TypeScript এক্সিকিউটরের অভ্যন্তরীণ বাস্তবায়নের ওপর নির্ভর না করে JSON-নিরাপদ প্রোভাইডার প্লাগইন
ম্যানিফেস্টের মাধ্যমে প্রোভাইডার মেটাডেটা ইমপোর্ট করা উচিত। সাইডকারের
যোগ্যতার চুক্তি ও মাইগ্রেশন ধাপগুলোর জন্য [প্রোভাইডার প্লাগইন ম্যানিফেস্ট](./PROVIDER_PLUGIN_MANIFEST.md) দেখুন।
