> தகுதியான சூழலில் 15-95% வரை தானாகச் சேமிக்கவும். விரைவான மேலோட்டத்திற்கு, [README Compression பகுதியைப்](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) பார்க்கவும்.

## மேலோட்டம்

OmniRoute, கோரிக்கைகள் மேல்நிலை வழங்குநர்களை அடைவதற்கு முன்பே **முன்கூட்டியே** இயங்கும் ஒரு கூறுநிலை prompt compression pipeline-ஐச் செயல்படுத்துகிறது. இதனால் உங்கள் token சேமிப்பு வெளிப்படையாக நிகழ்கிறது — உங்கள் பணிப்பாய்வில் எந்த மாற்றமும் தேவையில்லை.

```
Client கோரிக்கை
  → Compression உத்தித் தேர்வி
    → Combo override உள்ளதா? → combo அமைப்பைப் பயன்படுத்து
    → Auto-trigger வரம்பு உள்ளதா? → auto mode-ஐப் பயன்படுத்து
    → இயல்புநிலை mode உள்ளதா? → global அமைப்பைப் பயன்படுத்து
    → Off ஆக உள்ளதா? → compression-ஐத் தவிர்
  → தேர்ந்தெடுக்கப்பட்ட Compression Mode
    → Off: Compression இல்லை
    → Lite: பாதுகாப்பான whitespace/வடிவமைப்புச் சுத்திகரிப்பு (~15%)
    → Standard: Caveman பாணியிலான தேவையற்ற சொல் நீக்கம் (~30%)
    → Aggressive: வரலாற்றுப் பழமையாக்கம் + சுருக்கமாக்கல் (~50%)
    → Ultra: Heuristic pruning + code-block thinning (~75%)
    → RTK: கட்டளையை அறிந்த terminal/tool-output வடிகட்டல் (மேல்நிலை வரம்பில் 60-90%)
    → Stacked: வரிசைப்படுத்தப்பட்ட பல-engine pipeline, பொதுவாக முதலில் RTK, பின்னர் Caveman (தகுதியான வரம்பில் 78-95%)
  → சுருக்கப்பட்ட கோரிக்கை → வழங்குநர்
```

## Compression Modes

### Off

Compression எதுவும் பயன்படுத்தப்படாது. அனைத்து செய்திகளும் மாற்றமின்றி அனுப்பப்படும்.

### Lite Mode (~15% சேமிப்பு, <1ms தாமதம்)

மிகவும் பாதுகாப்பான mode — அர்த்தத்தில் எந்த மாற்றமும் இல்லை; வடிவமைப்பு மட்டும் சுத்திகரிக்கப்படும்:

| நுட்பம்                  | விளக்கம்                                                               |
| ------------------------ | ---------------------------------------------------------------------- |
| `collapseWhitespace`     | தொடர்ச்சியான வெற்று வரிகளையும் வரி இறுதி இடைவெளிகளையும் ஒன்றிணைக்கிறது |
| `dedupSystemPrompt`      | நகலான system செய்திகளை நீக்குகிறது                                     |
| `compressToolResults`    | விரிவான tool/function வெளியீடுகளைச் சுருக்குகிறது                      |
| `removeRedundantContent` | மீண்டும் இடம்பெறும் வழிமுறைகளை நீக்குகிறது                             |
| `replaceImageUrls`       | base64 படத் தரவு URI-களைச் சுருக்குகிறது                               |

**இதற்கு உகந்தது:** எப்போதும் இயக்கத்தில் இருக்கும் பயன்பாடு, பாதுகாப்பு மிக முக்கியமான பணிப்பாய்வுகள்.

### Standard Mode (~30% சேமிப்பு)

[Caveman](https://github.com/JuliusBrussee/caveman)-இலிருந்து உத்வேகம் பெற்றது — பொருளைப் பாதுகாத்தபடி தேவையற்ற சொற்களையும் நீளமான சொற்றொடர்களையும் நீக்குகிறது:

- தேவையற்ற சொற்களை நீக்குகிறது ("please", "I think", "basically", "actually")
- நீளமான சொற்றொடர்களைச் சுருக்குகிறது ("in order to" → "to", "as a result of" → "because")
- பணிவான தயக்க வெளிப்பாடுகளை நீக்குகிறது ("Would you mind...", "If you could possibly...")
- Coding prompt-களுக்காகச் சீரமைக்கப்பட்ட 30+ regex விதிகள்

**இதற்கு உகந்தது:** அன்றாட coding பணிப்பாய்வுகள், செலவில் கவனம் செலுத்தும் அணிகள்.

### Aggressive Mode (~50% சேமிப்பு)

நீண்ட அமர்வுகளுக்கான அறிவார்ந்த வரலாற்று மேலாண்மை:

- **செய்திப் பழமையாக்கம்** — பழைய செய்திகள் படிப்படியாக அதிகமாகச் சுருக்கப்படும்
- **Tool Result Compression** — நீண்ட tool வெளியீடுகள் துண்டிக்கப்படும் அல்லது விடுபடுத்தப்படும் (முதல்/கடைசி வரிகள்,
  பொருந்தும்-வரி வடிகட்டல், JSON key சுருக்கம்)
- **கட்டமைப்பு ஒருமைப்பாட்டுப் பாதுகாப்புகள்** — `tool_use` + `tool_result` இணைகள் சீராக இருப்பதை உறுதிசெய்கின்றன
- **Context Window விழிப்புணர்வு** — ஒவ்வொரு model-க்குமான token வரம்புகளை மதிக்கிறது

**இதற்கு உகந்தது:** நீண்டகால debugging அமர்வுகள், பெரிய codebase-கள்.

### Ultra Mode (~75% சேமிப்பு)

Token மிக முக்கியமான சூழல்களுக்கான அதிகபட்ச compression:

- **Heuristic Pruning** — உரைநடையின் மதிப்பெண் அடிப்படையிலான token pruning
- **கட்டமைப்புப் பாதுகாப்பு** — fenced code block-கள், inline code, URL-கள் மற்றும் identifier-கள்
  tombstone செய்யப்பட்டு, pruning செய்யப்படாமல், அப்படியே மீண்டும் இணைக்கப்படுகின்றன
- **விருப்பத்திற்குரிய SLM tier** — கட்டமைக்கப்பட்டிருந்தால், சிறிய local model ஒன்று prune-ஐச் செம்மைப்படுத்தலாம்
- Aggressive mode-இலிருந்து சுயாதீனமானது: இது message aging, tool-result compression
  அல்லது fallback summarizer-ஐ இயக்காது (SLM-tier தோல்வி மட்டுமே fallback pass ஒன்றை
  aggressive வழியாக அனுப்பக்கூடும்)

**இதற்கு உகந்தது:** Context வரம்புகளை நீங்கள் மீண்டும் மீண்டும் எட்டும்போது.

### RTK Mode (மேல்நிலை வரம்பில் 60-90%)

Coding-agent அமர்வுகளில் தோன்றும் விரிவான tool வெளியீடுகளுக்காக RTK mode மேம்படுத்தப்பட்டுள்ளது:

- `git status`, `git diff`, `git log`, test runner-கள்,
  TypeScript/Vite/Webpack build-கள், ESLint/Biome/Prettier, npm audit/install-கள், Docker log-கள், infra
  வெளியீடு மற்றும் பொதுவான shell வெளியீடு போன்ற command/output வகைகளைக் கண்டறிகிறது
- `open-sse/services/compression/engines/rtk/filters/` இலிருந்து JSON filter pack-களைப் பயன்படுத்துகிறது
- Project அல்லது global `filters.toml` கோப்புகளிலிருந்து RTK TOML schema v1 filter-களை இறக்குமதி செய்கிறது; இதில் inline-test
  validation மற்றும் project கோப்புகளுக்கான trust-gating அடங்கும்
- Inline verify sample-களுடன் 55 built-in filter-களை வழங்குகிறது
- ANSI கட்டுப்பாட்டு வரிசைகள், progress bar-கள், மீண்டும் வரும் வரிகள் மற்றும் செயல்படுத்த இயலாத இரைச்சலை நீக்குகிறது
- தோல்விகள், பிழைகள், எச்சரிக்கைகள், மாற்றப்பட்ட கோப்புகள், சுருக்கங்கள் மற்றும் நீண்ட வெளியீட்டின் இறுதிப் பகுதியைப் பாதுகாக்கிறது
- Trust-gated project filter-கள், global filter-கள் மற்றும் விருப்பத்திற்குரிய திருத்தப்பட்ட raw-output மீட்டெடுப்பை ஆதரிக்கிறது

**இதற்கு உகந்தது:** Shell, build, test, git, grep மற்றும் file-output transcript-களைக் கொண்ட agent அமர்வுகள்.

### Stacked Mode (தகுதியான வரம்பில் 78-95%)

Stacked mode பல compression engine-களைத் தீர்மானிக்கப்பட்ட வரிசையில் இயக்குகிறது. இயல்புநிலை pipeline:

```txt
RTK -> Caveman
```

இந்த வரிசை முதலில் terminal/tool வெளியீட்டைச் சுருக்கமாக வைத்திருந்து, பின்னர் மீதமுள்ள இயல்புமொழி prompt-க்கு Caveman semantic condensation-ஐப் பயன்படுத்துகிறது. Stacked pipeline-களை global அளவில் அல்லது routing combo-களுக்கு ஒதுக்கப்பட்ட
compression combo-கள் வழியாகக் கட்டமைக்கலாம்.

**இதற்கு உகந்தது:** பெரிய tool log-களுடன் மனித வழிமுறைகள் அல்லது assistant சுருக்கங்கள் கலந்த context.

| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` குறைவான வெளியீட்டு டோக்கன்கள், அளவீடுகளில் சராசரியாக `65%` வெளியீட்டுச் சேமிப்பு, `22-87%` வரம்பு மற்றும் `~46%` உள்ளீட்டுச் சுருக்கக் கருவி |
| RTK     | கட்டளை வெளியீட்டில் `60-90%` சேமிப்பு; மாதிரி அமர்வில் `~118,000 -> ~23,900` டோக்கன்கள் அல்லது `79.7%` சேமிப்பு (`~80%`)                            |

ஒன்றுடன் ஒன்று மேற்பொருந்தும் கருவி/சூழல் பேலோடுகளுக்கு, இயல்புநிலை OmniRoute சேர்க்கை எஞ்சின்களை அடுக்குகிறது:

```txt
RTK -> Caveman
```

ஒருங்கிணைந்த சேமிப்புகள் கூட்டல் முறையிலானவை அல்ல, பெருக்கல் முறையிலானவை:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

RTK மற்றும் Caveman இரண்டும் ஒரே உள்ளீடு/சூழல் பேலோடைக் குறைக்க முடியும் போது அந்த `78-95%` அளவு பொருந்தும்.
Caveman மறுமொழி வெளியீட்டு முறை தனியானது: அது இயக்கப்பட்டிருக்கும்போது, Caveman-இன் சொந்த வெளியீட்டுச் சேமிப்புகளைப் பயன்படுத்தவும் (`65%`
சராசரி, `~75%` முதன்மை மதிப்பு, `22-87%` வரம்பு). மொத்த பில்லிங் சேமிப்புகள் உங்கள் ப்ராம்ப்ட்/வெளியீட்டு விகிதத்தைச் சார்ந்தவை.

### "தகுதியானது" என்பதன் உண்மையான பொருள்

15-95% என்ற முதன்மை வரம்பு உண்மையானதே, ஆனால் அது **தேவையற்ற விதத்தில் மீண்டும் வரும் அல்லது அளவுக்கு அதிகமாக விவரமான** உள்ளடக்கத்திற்கு மட்டுமே பொருந்தும் — மீண்டும் மீண்டும் வரும்
பிழை வரிகள், ஒரே எச்சரிக்கையைத் தொடர்ந்து வெளியிடும் பில்ட் பதிவு, அளவுக்கு அதிகமான `grep`/கோப்பு-வாசிப்பு டம்ப் போன்றவை. இது
ஒவ்வொரு கோரிக்கையிலும் அவ்வளவு சேமிப்பு கிடைக்கும் என்று **பொருளல்ல**.

சோதனை மூலம் உறுதிசெய்யப்பட்டது (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): ஒரே மாதிரியான 300
பிழை வரிகளைக் கொண்ட Anthropic-வடிவ `tool_result` தொகுதிக்கு எதிராக இயக்கப்பட்ட
`stacked` (RTK + Caveman) செயலாக்கம் **95.93% டோக்கன் சேமிப்பு / 96.26% எழுத்துச் சேமிப்பு** அளித்தது — இது விளம்பரப்படுத்தப்பட்ட
வரம்பிற்குள் துல்லியமாக உள்ளது. ஆனால் அதே பைப்லைனை இயல்பான, மீளுருவாக்கமற்ற கருவி வெளியீட்டில் (சுத்தமான `grep` பொருத்தப் பட்டியல்,
குறுகிய கோப்பு வாசிப்பு, சாதாரண உரையாடல் உரை) இயக்கும்போது, அது சரியாகவே **கிட்டத்தட்ட பூஜ்ஜிய சேமிப்பை** அளிக்கிறது; ஏனெனில்
அகற்றுவதற்கு மீண்டும் வரும் எதுவும் இல்லை, மேலும் குறியீட்டுத் தொகுதிகள், URL-கள், தலைப்புகள், பதிப்புகள் அல்லது ALL-CAPS மாறிலி அடையாளங்காட்டிகளை நீக்கும் அல்லது மாற்றும்
மறுஎழுத்தாக்கத்தை அனுப்ப `validateCompression()` (`validation.ts`) மறுக்கிறது.

இது எதிர்பார்க்கப்பட்ட, பாதுகாப்பான நடத்தை; பிழை அல்ல: பெரும்பாலும் சுத்தமான கோப்புகளை வாசிக்கும்/grep செய்யும் ஒரு குறியீட்டாக்க அமர்வு,
சுருக்கம் முழுமையாக இயக்கப்பட்டிருந்தாலும், மிதமான மொத்தச் சேமிப்பையே காணும்; அதே சமயம் தோல்வியுறும்
சுழற்சி அல்லது அதிக வெளியீட்டை உருவாக்கும் லின்டரை எதிர்கொள்ளும் அமர்வு, அந்தப் போக்குவரத்தில் முழு 78-95% வரம்பைக் காணும். ஒரே அமர்வின்
குறைந்த மொத்தச் சேமிப்பு சதவீதத்தைச் சுருக்கம் தவறாக உள்ளமைக்கப்பட்டுள்ளது என்பதற்கான ஆதாரமாகப் பயன்படுத்த வேண்டாம் — முதலில்
அடிப்படைக் கருவி வெளியீடு உண்மையில் மீண்டும் மீண்டும் வந்ததா என்பதைச் சரிபார்க்கவும்.

## உள்ளமைவு

### கட்டுப்பாட்டுப் பலகை

`Dashboard → Context & Cache` என்பதற்குச் செல்லவும்:

- **Caveman** — பயன்முறைத் தேர்வு, மொழித் தொகுப்புகள், முன்னோட்டம் மற்றும் உலகளாவிய இயல்புநிலைகள்
- **RTK** — கட்டளை-வடிகட்டி முன்னோட்டம், RTK பாதுகாப்பு அமைப்புகள் மற்றும் வடிகட்டி பட்டியல்
- **Compression Combos** — வழிச்செலுத்தல் சேர்க்கைகளுக்கு ஒதுக்கப்பட்ட பெயரிடப்பட்ட எஞ்சின் செயலாக்கத் தொடர்கள்
- **Auto-Trigger Threshold** — டோக்கன் எண்ணிக்கை வரம்பை மீறும்போது சுருக்கத்தைத் தானாகச் செயல்படுத்தும்

### ஒவ்வொரு சேர்க்கைக்குமான மீறல்

`Dashboard → Context & Cache → Compression Combos` என்பதில், ஒரு வழிச்செலுத்தல் சேர்க்கைக்கு சுருக்கச் சேர்க்கை ஒன்றை ஒதுக்கவும்:

```txt
சேர்க்கை: "free-tier-fallback"
  சுருக்கச் சேர்க்கை: "coding-agent-stack"
  செயலாக்கத் தொடர்: RTK -> Caveman
  இலக்குகள்:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

கட்டணச் சந்தாக்களில் லைட் பயன்முறையை வைத்துக்கொண்டே, இலவச/நிரலாக்க வழங்குநர்களில் அடுக்கப்பட்ட சுருக்கத்தைப் பயன்படுத்த இது உங்களை அனுமதிக்கிறது.

இந்த "ஒவ்வொரு சேர்க்கைக்குமான மீறல்" ஒதுக்கீடு, **வழிச்செலுத்தல்-சேர்க்கை சுருக்கப் பயன்முறை** மீறலில் (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — அந்தப் புலத்தின் திட்டவடிவம் `rtk`, `stacked` மற்றும் `omniglyph` ஆகியவற்றையும் ஏற்கிறது) இருந்து வேறுபட்ட ஒரு கட்டுப்பாடாகும் — அந்த மீறல் பெயரிடப்பட்ட சுருக்கச்-சேர்க்கை செயலாக்கத் தொடரைத் தேர்ந்தெடுக்காது; அது `resolveCompressionPlan` பயன்படுத்தும் `compressionMode` புலத்தை மட்டும் அமைக்கிறது. இதைச் சேர்க்கை அட்டையில் (`Dashboard → Combos`) அல்லது, #6760 முதல், மேலே ஆவணப்படுத்தப்பட்ட செயலாக்கத் தொடர்-ஒதுக்கீட்டுத் தேர்வுப்பெட்டிக்கு அடுத்துள்ள `Dashboard → Context & Cache → Compression Combos` என்பதன் "Assign to routing" பட்டியலில் ஒவ்வொரு வழிச்செலுத்தல் சேர்க்கைக்கும் அமைக்கலாம். இரு இடைமுகங்களும் ஒரே `PUT /api/combos/{id}` முனைப்புள்ளி வழியாக நிலைநிறுத்தப்படுகின்றன.

### ஒவ்வொரு கோரிக்கைக்குமான மீறல்

ஒற்றைக் கோரிக்கைக்கான சுருக்கத் திட்டத்தை மீற `x-omniroute-compression` கோரிக்கைத் தலைப்பை அனுப்பவும். இதுவே மிக உயர்ந்த முன்னுரிமையைக் கொண்டுள்ளது — இது வழிச்செலுத்தல்-சேர்க்கை மீறல், செயலில் உள்ள சுயவிவரம், தானியங்கித் தூண்டுதல் மற்றும் பலகையின் Default ஆகியவற்றை மீறுகிறது. அறியப்படாத மதிப்புகள் புறக்கணிக்கப்படும் (கோரிக்கை ஒருபோதும் நிராகரிக்கப்படாது), மேலும் உலகளாவிய முதன்மைச் சுவிட்ச் அனைத்தையும் தொடர்ந்து கட்டுப்படுத்தும்: சுருக்கம் உலகளவில் முடக்கப்பட்டிருக்கும்போது, தலைப்பால் அதை இயக்க முடியாது. மதிப்புகள்:

| மதிப்பு       | விளைவு                                                                                                                                |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `off`         | இந்தக் கோரிக்கைக்குச் சுருக்கம் இல்லை.                                                                                                |
| `default`     | பலகையிலிருந்து பெறப்பட்ட Default சுயவிவரம் (செயலில் உள்ள சுயவிவரத்தைப் புறக்கணிக்கும்). இழப்புடைய எஞ்சின்கள் முடக்கப்பட்டே இருக்கும். |
| `safe`        | தலைப்பைத் தவிர்ப்பதற்குச் சமம்: நகல்நீக்கம் மற்றும் வெற்றிட மடிப்பு மட்டும்.                                                          |
| `allow-lossy` | சுருக்கங்கள், பொருத்த வடிகட்டிகள் மற்றும் பாணி மறுஎழுத்துகள் உள்ளிட்ட இந்தக் கோரிக்கையின் இயக்குநர் திட்டத்தைத் தக்கவைக்கும்.         |
| `engine:<id>` | இயக்கப்பட்டிருக்கும்போது ஒற்றை எஞ்சின், எ.கா. `engine:rtk`. அந்த எஞ்சினுக்கான ஒவ்வொரு கோரிக்கைக்குமான விருப்பச் சேர்க்கை இதுவாகும்.   |
| `<combo>`     | பெயரிடப்பட்ட ஒரு சேர்க்கை; முதலில் பெயரால் (எழுத்துப் பெட்டி வேறுபாட்டைப் பொருட்படுத்தாமல்), பின்னர் id மூலம் பொருத்தப்படும்.         |

`allow-lossy`, `engine:<id>` அல்லது பெயரிடப்பட்ட சேர்க்கை இல்லாமல், இழப்புடைய எஞ்சின்கள் பயன்படுத்தப்படாது. சுருக்கம் இயக்கப்பட்டிருக்கும்போது, கோரிக்கைக்கு அமர்வு நகல்நீக்கமும் வெற்றிட மடிப்பும் தொடர்ந்து பயன்படுத்தப்படும்.

பயன்படுத்தப்பட்ட திட்டம் `X-OmniRoute-Compression: <mode>; source=<source>` பதில் தலைப்பில் திருப்பி அனுப்பப்படும்; இங்கு `<source>` என்பது `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` அல்லது `off` ஆகியவற்றில் ஒன்றாகும்.

## மேம்பட்ட சுருக்க அமைப்புகள்

மேலே விவரிக்கப்பட்ட 7 பயன்முறைகளுக்கு அப்பால் (மூலமானது `codex-responses` மற்றும்
`omniglyph` பயன்முறைகளையும் ஏற்கிறது, ஆனால் இந்த வழிகாட்டி அவற்றை உள்ளடக்கவில்லை), கீழுள்ள பிரிவுகள்
அந்தப் பயன்முறைகளுக்குள் அல்லது அவற்றுடன் இணைந்து செயல்படும் அம்சங்களை விவரிக்கின்றன: Tool Result Compression மற்றும் Progressive Aging
ஆகியவை aggressive இயந்திரத்தின் படிகள் 1 மற்றும் 2 ஆகும் (Aggressive பயன்முறை மற்றும் ஒரு
அடுக்கப்பட்ட செயலாக்கப் பாதையின் `aggressive` படி), Stacked Pipeline என்பது Stacked பயன்முறை செயல்படும் விதமாகும், Cache-Aware Compression
சுருக்கம் இயக்கத்தில் இருக்கும்போது தற்காலிகச் சேமிப்பை ஆதரிக்கும் வழங்குநர்களுக்காக `aggressive` மற்றும் `ultra` ஆகியவற்றை `standard` ஆகத்
தரமிறக்குகிறது; மேலும் Caveman Output Mode மற்றும் Output Styles ஆகியவை விருப்பத்தின் பேரில் பயன்படுத்தப்படும் முறைமைத்-தூண்டுதல் அறிவுறுத்தல்களாகும்,
இயல்புநிலையில் முடக்கப்பட்டுள்ள இவை கோரிக்கையைச் சுருக்குவதற்குப் பதிலாக மாதிரியின் வெளியீட்டை வடிவமைக்கின்றன.

### தற்காலிகச் சேமிப்பை அறிந்த சுருக்கம்

சில வழங்குநர்கள் (தூண்டுதல் தற்காலிகச் சேமிப்புடன் கூடிய Anthropic போன்றவை) **தூண்டுதல் தற்காலிகச் சேமிப்பை**
ஆதரிக்கின்றனர்; இது செலவுகளையும் தாமதத்தையும் குறைக்கத் தூண்டுதலின் சில பகுதிகளைத் தற்காலிகமாகச் சேமிக்க அவர்களுக்கு உதவுகிறது.
தற்காலிகச் சேமிப்பு இயக்கப்பட்டிருக்கும்போது, aggressive சுருக்கம் உண்மையில் செயல்திறனை **பாதிக்கலாம்**,
ஏனெனில் அது தற்காலிகமாகச் சேமிக்கப்பட்ட டோக்கன்களை மாற்றி, அந்தச் சேமிப்பைச் செல்லாததாக்குகிறது.

`cachingAware.ts` தொகுதி, **தற்காலிகச் சேமிப்புச் சூழலைக் கண்டறிந்து** அதற்கேற்ப
**சுருக்க உத்தியைச் சரிசெய்வதன்** மூலம் இதைத் தீர்க்கிறது.

#### இது செயல்படும் விதம்

1. **தற்காலிகச் சேமிப்புச் சூழலைக் கண்டறிதல்** — `cache_control` குறியீடுகளுக்காகக் கோரிக்கை உடலை வருடுகிறது
2. **தற்காலிகச் சேமிப்பு வழங்குநர்களைக் கண்டறிதல்** — இலக்கு வழங்குநர் தற்காலிகச் சேமிப்பை ஆதரிக்கிறாரா என்பதைச் சரிபார்க்கிறது
3. **உத்தியைச் சரிசெய்தல்** — தற்காலிகச் சேமிப்பு வழங்குநர்களுக்காக `aggressive`/`ultra` ஆகியவற்றை `standard` ஆகத் தரமிறக்குகிறது
4. **முறைமைத் தூண்டுதலைத் தவிர்த்தல்** — முறைமைத் தூண்டுதல்கள் வழக்கமாகத் தற்காலிகமாகச் சேமிக்கப்படுவதால், அவற்றைச் சுருக்காது

உத்தி உதவிச் செயல்பாடு ஒரு `deterministicOnly` கொடியையும் வழங்குகிறது, ஆனால் திட்ட உருவாக்கி
உத்தியை மட்டுமே பயன்படுத்துகிறது — தற்போது பின்வரும் எந்தக் கூறும் அந்தக் கொடியைப் படிப்பதில்லை.

#### குறியீட்டு எடுத்துக்காட்டு

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← தற்காலிகச் சேமிப்புக் குறியீடு
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### எப்போது பயன்படுத்த வேண்டும்

தற்காலிகச் சேமிப்பை அறிந்த சுருக்கம் **எப்போதும் இயக்கத்தில் இருக்கும்** — எந்த உள்ளமைவும் தேவையில்லை. சுருக்கம்
இயக்கத்தில் இருந்து, இலக்கு வழங்குநர் தூண்டுதல் தற்காலிகச் சேமிப்பை (Anthropic, OpenAI,
போன்றவை) ஆதரிக்கும்போதெல்லாம் இது செயல்படும்; வெளிப்படையான `cache_control` குறியீடுகள் தேவையில்லை — தற்காலிகச் சேமிப்பை ஆதரிக்கும் வழங்குநர் மட்டுமே
தரமிறக்கத்தைத் தூண்டும், மேலும் குறியீடுகள் மட்டும் ஒருபோதும் அதைத் தூண்டாது (குறியீடு கண்டறிதல் தற்காலிகச் சேமிப்புத்
தொலைஅளவீட்டிற்குத் தரவை வழங்குகிறது, உத்தி முடிவுக்கு அல்ல).

### படிப்படியான பழமையாக்கம்

நீண்ட உரையாடல்கள் பல செய்திச் சுற்றுகளைக் குவிக்கின்றன, ஆனால் பழைய சுற்றுகள் படிப்படியாகக் குறைவான
தொடர்புடையவையாகின்றன. `progressiveAging.ts` தொகுதி **சுற்று இடைவெளியின் அடிப்படையில் செய்திகளின் தரத்தைக் குறைக்கிறது**
(உரையாடலின் இறுதியிலிருந்து இடைவெளி அளவிடப்படுகிறது). வெளியிடப்பட்ட இயல்புநிலை மதிப்புகளுடன்
(`verbatim: 2, light: 2, moderate: 3`):

- **கடைசி 2 உரையாடல் சுற்றுகள் (தொலைவு ≤ 2)**: மாற்றமின்றி வைக்கப்படும்
- **தொலைவு 3**: கேவ்மேன் சுருக்கம் (நிரப்பு வார்த்தைகள் நீக்கம்)
- **தொலைவு 4+**: உதவியாளர் செய்திகள் சுருக்கப்படும்; பயனர் செய்திகள் அவற்றின் முதல்
  வரியாகக் குறைக்கப்பட்டு, 120 எழுத்துகளுக்குள் வரம்பிடப்படும்; மற்ற பாத்திரங்கள் மாற்றப்படாது. சிஸ்டம் ப்ராம்ப்ட்கள், ஏற்கெனவே காலமடைந்த
  செய்திகள் மற்றும் சமீபத்திய பயனர் செய்தி ஆகியவை தொலைவைப் பொருட்படுத்தாமல் எப்போதும் மாற்றமின்றி வைக்கப்படும்.
  எதுவும் முழுமையாக நீக்கப்படாது, மேலும் வழங்கப்பட்ட இயல்புநிலைகளில் `light`
  வரம்பை அடைய முடியாது (`light` என்பது `verbatim`-க்கு சமம்).

#### குறியீட்டு எடுத்துக்காட்டு

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... மேலும் 50 உரையாடல் சுற்றுகள் ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // கடைசி 3 உரையாடல் சுற்றுகள்: மாற்றமின்றி
  light: 8, // தொலைவு <= 8: இலகுவான சுருக்கம்
  moderate: 20, // தொலைவு <= 20: கேவ்மேன் சுருக்கம்
  fullSummary: 5, // வகையால் தேவைப்படுகிறது, வரம்புப் பிரிப்புக் குறியீட்டால் படிக்கப்படாது
  // தொலைவு > 20: சுருக்கப்படும் (உதவியாளர்) / முதல் வரி வைக்கப்படும் (பயனர்)
});

// saved = சேமிக்கப்பட்ட டோக்கன்களின் எண்ணிக்கை
```

#### எப்போது பயன்படுத்துவது

`aggressive` பயன்முறையில் படிப்படியான காலமடைதல் **எப்போதும் இயக்கத்தில் இருக்கும்** — இது
`compressAggressive()`-இன் படி 2 ஆகும். Ultra பயன்முறை இதை இயக்காது. இது குறிப்பாகப் பின்வருவனவற்றில்
பயனுள்ளதாக இருக்கும்:

- நீண்டகாலக் குறியீட்டாக்க அமர்வுகள்
- பல நாட்கள் நீடிக்கும் உரையாடல்கள்
- பல கருவி அழைப்புகளைக் கொண்ட முகவர் சார்ந்த பணிப்பாய்வுகள்

### கேவ்மேன் வெளியீட்டுப் பயன்முறை

கேவ்மேன் வெளியீட்டுப் பயன்முறை, மாதிரியிடமே சுருக்கமான வெளியீட்டைக் கோரும் **சிஸ்டம் ப்ராம்ப்ட் வழிமுறைகளைச்**
சேர்க்கிறது — `lite` நிலை முழுமையான வாக்கியங்களைத் தக்கவைத்துச் சுருக்கமான பதில்களைக் கோருகிறது, `full`
நிலை "respond terse like smart caveman" எனக் கோருகிறது, மேலும் `ultra` தந்தி பாணி வெளியீட்டைக் கோருகிறது;
வழிமுறைகள் கோர மட்டுமே முடியும், அவற்றால் இதை உறுதிப்படுத்த முடியாது. கோரிக்கைகள் அவற்றை
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) மூலம் பெறுகின்றன:
`open-sse/handlers/chatCore.ts` முதலில் பின்னோக்கு-இணக்க ஷிம் மூலம் தேர்வைத் தீர்மானிக்கிறது
(`open-sse/services/compression/outputStyles/backCompat.ts`-இல் உள்ள
`resolveOutputStyleSelection()`); `outputStyles` காலியாக இருக்கும்போது, செயல்படுத்தப்பட்ட
`cavemanOutputMode`-ஐ `cavemanOutputMode.intensity`-இல் உள்ள `terse-prose` வெளியீட்டு பாணிக்கு
வரைபடமாக்குகிறது (கீழே உள்ள பின்னோக்கு-இணக்கத்தைப் பார்க்கவும்); காலியாக இல்லாத `outputStyles`
தேர்வு அப்படியே பயன்படுத்தப்படும், அதன் பின்னர் `cavemanOutputMode.enabled` மற்றும் `intensity` எந்த
விளைவையும் ஏற்படுத்தாது, ஆனால் அதன் `autoClarity` நிலைமாற்றி தொடர்ந்து பொருந்தும். `outputMode.ts`,
வழிமுறை உரைகள் (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), உள்ளடக்கத் தவிர்ப்பு மற்றும் உட்செலுத்தல் பயன்படுத்தும்
இடமமைப்பு உதவிச் செயல்பாடு ஆகியவற்றைக் கொண்டுள்ளது; அதன் சொந்த `applyCavemanOutputMode()` உட்செலுத்திக்கு
உற்பத்திச் சூழலில் எந்த அழைப்பாளரும் இல்லை.

#### இது எவ்வாறு செயல்படுகிறது

இந்தப் பயன்முறை உள்ளீட்டைச் சுருக்காது. இது சிஸ்டம் ப்ராம்ப்டில் ஒரு வழிமுறைத் தொகுதியைச்
சேர்க்கிறது (கீழே உள்ள உட்செலுத்தல் எவ்வாறு செயல்படுகிறது என்பதைப் பார்க்கவும்), மேலும் கோரிக்கைக்குத்
தேர்ந்தெடுக்கப்பட்ட எந்த உள்ளீட்டுச் சுருக்கப் பயன்முறையும், இப்போது அந்தத் தொகுதியைக் கொண்டுள்ள உடலில்,
அதற்குப் பிறகும் இயங்கும். ஒவ்வொரு நிலையும் முடிவடையும் பகிரப்பட்ட வரம்புகள் உட்பிரிவுக்கு முன்பாக,
ஆங்கில `full` நிலை பின்வருமாறு கூறுகிறது:

> "புத்திசாலி கேவ்மேன் போலச் சுருக்கமாகப் பதிலளி. உருபுகள் (a/an/the), நிரப்பு வார்த்தைகள் (just/really/basically/actually/simply), மரியாதைச் சொற்கள், தயக்க வெளிப்பாடுகள் ஆகியவற்றைத் தவிர். வாக்கியத் துண்டுகள் பரவாயில்லை. குறுகிய இணைச்சொற்களைப் பயன்படுத்து (extensive என்பதற்குப் பதில் big, implement என்பதற்குப் பதில் fix). அனைத்து தொழில்நுட்ப உள்ளடக்கம், குறியீடு, பிழைகள், URL-கள், அடையாளங்காட்டிகள் ஆகியவற்றைத் துல்லியமாக வைத்திரு."

இது குறிப்பாகப் பின்வருவனவற்றில் சிறப்பாகச் செயல்படுகிறது:

- குறியீடு உருவாக்குதல் (இன்னும் சுருக்கமான வெளியீடு = குறைவான டோக்கன்கள்)
- விரைவான கேள்வி-பதில் (விரிவான விளக்கங்கள் தேவையில்லை)
- தொகுதி செயலாக்கம் (செயல்திறனை அதிகப்படுத்துதல்)

#### எப்போது பயன்படுத்துவது

கேவ்மேன் வெளியீட்டுப் பயன்முறை **விருப்பத் தேர்வுக்குரியது**. சுருக்கம் இயக்கப்பட்டிருக்கும்போது
(`enabled: true`, சுருக்க அமைப்புகள் பக்கத்தில் உள்ள முதன்மை நிலைமாற்றி), அதை
`cavemanOutputMode.enabled` மூலம் இயக்கவும்; `intensity` என்பது `lite`, `full` அல்லது `ultra`-ஐத்
தேர்ந்தெடுக்கிறது:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

ஒரு சுருக்கச் சேர்க்கையின் **வெளியீட்டுப் பயன்முறை** நிலைமாற்றி (`outputMode`, நிலை
`outputModeIntensity`-இல்) அந்தச் சேர்க்கை பொருந்தும் கோரிக்கைகளுக்கு அதே நிலைமாற்றியை அமைக்கிறது,
மேலும் `omniroute_set_compression_engine` MCP கருவி அதன் பூலியன் `outputMode` அளவுரு மூலம் அதை
எழுதுகிறது. காலியாக இல்லாத `outputStyles` தேர்வு இந்த நிலைமாற்றியைவிட முன்னுரிமை பெறும். டாஷ்போர்டில்,
**சுருக்கமான உரைநடை** வெளியீட்டுப் பாணியை இயக்குவது அதே தொகுதியை உட்செலுத்தும் (கீழே உள்ள வெளியீட்டுப்
பாணிகளைப் பார்க்கவும்).

### வெளியீட்டுப் பாணிகள் (பட்டியல்)

மேலே உள்ள கேவ்மேன் வெளியீட்டுப் பயன்முறை **மரபுவழி ஒற்றைப் பாணிப் பாதை** ஆகும். கட்டம் 4 அதை
இணைத்துப் பயன்படுத்தக்கூடிய வெளியீட்டுப் பாணிகளின் பட்டியலாகப் பொதுமைப்படுத்தியது:
`open-sse/services/compression/outputStyles/catalog.ts`-இல் உள்ள `OUTPUT_STYLE_CATALOG`.
ஒவ்வொரு பாணியும் குறைந்த செலவிலான வெளியீட்டை மாதிரியிடமே கோரும் ஒரு சிஸ்டம் ப்ராம்ப்ட் வழிமுறையாகும்;

#### செலுத்துதல் எவ்வாறு செயல்படுகிறது

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) தேர்வை
catalog-க்கு எதிராகத் தீர்மானிக்கிறது (அறியப்படாத id-களும் locale பொருந்தாத பாணிகளும்
நீக்கப்படும், ஒருபோதும் பிழையாகாது; எந்தப் பாணிக்கும் தீர்மானிக்கப்படாத தேர்வு body-ஐ
மாற்றாமல் விட்டு, `no_styles` ஆகத் தவிர்க்கப்படும்), தேர்ந்தெடுக்கப்பட்ட வழிமுறைகளை catalog
வரிசையில் ஒன்றிணைக்கிறது,
வரம்புகள் பிரிவை **ஒருமுறை** சேர்க்கிறது (கூடுதலாக, `less-code` அல்லது `ponytail`
தேர்ந்தெடுக்கப்பட்டால் பாதுகாப்புப் பிரிவு, `SAFETY_BOUNDARIES` அல்லது அதன் மொழிபெயர்ப்பு),
மேலும் ஒரே ஒரு idempotency marker (`[OmniRoute Output Styles]`) உடன் block-ஐத் தொடங்குகிறது;
எனவே அதை மீண்டும் பயன்படுத்துவது எந்த விளைவையும் ஏற்படுத்தாது. தீர்மானிக்கப்பட்ட மொழிக்கு
(கீழே உள்ள மொழித் தேர்வைப் பார்க்கவும்) மொழிபெயர்ப்பு இருக்கும்போது, ஆங்கிலத்திற்குப் பதிலாக
உள்ளூர்மயமாக்கப்பட்ட வழிமுறை செலுத்தப்படுகிறது.

காலியாக இல்லாத `messages` array கொண்ட body-இல், idempotency சரிபார்ப்பு
content bypass-க்கு முன் இயங்குகிறது: `[OmniRoute Output Styles]` marker ஏற்கனவே மேல்நிலை
`system` field-இல் (string அல்லது content-block array) அல்லது string content கொண்ட system
message-இல் இருந்தால், body `already_applied` ஆக மாற்றமின்றி விடப்படும்; keyword சரிபார்ப்பு
எதுவும் இயங்காது. இல்லையெனில், content bypass (`open-sse/services/compression/outputMode.ts`-இல்
`shouldBypassCavemanOutputMode()`) அவற்றின் role எதுவாக இருந்தாலும், கடைசி மூன்று
messages-இன் உரையைச் சரிபார்த்து, அந்த உரை அதன் பாதுகாப்பு, மாற்றமுடியாத செயல் அல்லது
தெளிவுபடுத்தல் keywords-க்கு பொருந்தினால், அல்லது வரிசை உணர்வுள்ள தொடர் ஒன்றுக்குப் பொருந்தினால்,
முழு turn-க்கும் பாணிகளைத் தவிர்க்கிறது: `first`, `then`, `after that`, `before`, `rollback`
அல்லது `backup` என்பதற்குப் பின் 240 எழுத்துகளுக்குள் `delete`, `drop`, `migrate`, `deploy`
அல்லது `release` வருவது. **Auto-Clarity Bypass** toggle
(`cavemanOutputMode.autoClarity`, இயல்பாக இயக்கப்பட்டிருக்கும்) இயக்கப்பட்டிருக்கும்போது bypass
இயங்குகிறது; toggle-ஐ அணைப்பது keyword சரிபார்ப்பைத் தவிர்க்கிறது.

bypass turn-ஐ அனுமதிக்கும்போது, `placeSystemInstruction()` (அதே கோப்பு), புதிய
`messages[0]`-ஐ ஒருபோதும் உருவாக்காமல், அது கண்டறியும் பின்வரும் முதல் இடத்தில் block-ஐ
வைக்கிறது:

1. string content கொண்ட தொடக்க system message: அதன் உரைக்குப் பிறகு block சேர்க்கப்படுகிறது.
2. மேல்நிலை `system` field: string-இன் உரைக்குப் பிறகு block சேர்க்கப்படும், அல்லது
   content-block array-க்கு புதிய text block ஆகச் சேர்க்கப்படும்.
3. பின்னர் வரும், string content கொண்ட முதல் system message: அதன் உரைக்குப் பிறகு block
   சேர்க்கப்படுகிறது.
4. மேலே உள்ளவை எதுவும் இல்லை: `messages`-இன் இறுதியில் புதிய system message ஒன்றில் block
   வைக்கப்படுகிறது.

`messages` array இல்லாத (அல்லது காலியான array கொண்ட) body-இல், content bypass எதுவும்
இயங்காது; மேல்நிலை `system` field-ம் பரிசீலிக்கப்படாது. string `instructions` field-இன்
உரைக்குப் பிறகு block சேர்க்கப்படும்; ஆனால் அந்த field ஏற்கனவே
`[OmniRoute Output Styles]` marker-ஐக் கொண்டிருந்தால், body `already_applied` ஆக
மாற்றமின்றி விடப்படும். body-இல் string `instructions` field இல்லாமல், `input`
(string அல்லது array) இருந்தால், அந்த field-இல் இருந்த string அல்லாத எந்த மதிப்பையும்
மாற்றி, block `instructions` ஆகிறது. string `instructions` field-ம் string அல்லது array
`input`-ம் இல்லாத body மாற்றமின்றி விடப்பட்டு `no_messages` ஆகத் தவிர்க்கப்படுகிறது.

#### எவ்வாறு இயக்குவது

டாஷ்போர்டில்: **Compression Context → Compression Settings**
(`/dashboard/context/settings`), Output styles பிரிவு: ஒவ்வொரு பாணிக்கும் on/off
நிலைமாற்றி மற்றும் நிலைத் தேர்வியுடன் ஒரு வரிசை உள்ளது. சுருக்கம் செயல்பாட்டில் இருக்கும்போது
(பக்கத்தின் முதன்மை நிலைமாற்றியான `enabled`) பாணிகள் உட்செலுத்தப்படுகின்றன. **Auto-Clarity Bypass**
நிலைமாற்றி **Caveman** பக்கத்தின் (`/dashboard/context/caveman`) **Output Mode**
அட்டையில் உள்ளது. நிரலாக்க ரீதியாக, compression config தேர்வை இவ்வாறு நிலைநிறுத்துகிறது:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

பின்னோக்கி இணக்கத்தன்மை: `outputStyles` காலியாக இருக்கும்போது, பழைய
`cavemanOutputMode.enabled` அமைப்பு, `cavemanOutputMode.intensity`-இல் உள்ள அளவுடன்
`terse-prose`-க்கு பொருத்தப்படுகிறது. அதன் பிறகு தொகுதி `[OmniRoute Output Styles]`
குறிப்பானுடன் தொடங்குகிறது; பழைய `applyCavemanOutputMode()` உட்செலுத்தி
`[OmniRoute Caveman Output Mode]` என்பதை எழுதியது. குறிப்பானுக்குக் கீழே, en, pt-BR,
es, de, fr, it, ru, id மற்றும் vi ஆகிய மொழிகளில் உரை பழைய உட்செலுத்தலுடன் பொருந்துகிறது;
ja மற்றும் zh மொழிகளில் எல்லைகள் பற்றிய உட்பிரிவுக்கு முன் ஓர் கூடுதல் இடைவெளி உள்ளது.
`terse-prose` ஆனது pt-BR, es, de, fr, it, ru, zh, ja, id மற்றும் vi ஆகிய மொழிகளுக்கு
மொழிபெயர்க்கப்படுகிறது; எனவே தீர்மானிக்கப்பட்ட மொழி `hu` ஆக உள்ள கோரிக்கைக்கு, பழைய
உட்செலுத்தி அதன் Hungarian உரையைப் பயன்படுத்திய இடத்தில் English உரை கிடைக்கிறது.

`resolveOutputStyleLanguage()`): `languageConfig.enabled` செயல்பாட்டில் இருக்கும்போது,
`autoDetect`, கோரிக்கையின் `messages` அணியில் உரையைக் கொண்டுள்ள சமீபத்திய பயனர் செய்தியை
(சர உள்ளடக்கம் அல்லது அதன் உள்ளடக்கப் பகுதிகளின் `text`) மாதிரியாக எடுத்து, அதில் Caveman
இயந்திரத்தின் கண்டறிவியை (`detectCompressionLanguage()`) இயக்குகிறது. உரையில் Han

`it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` மற்றும் `id` ஆகியவற்றில் எதற்கு
அதிக குறிப்பு பொருத்தங்கள் உள்ளனவோ அதைத் திருப்பியளிக்கிறது; எதுவும் பொருந்தாதபோது `en`-ஐத்
திருப்பியளிக்கிறது — வகைப்படுத்த முடியாத உரைக்கு `defaultLanguage` ஒருபோதும் இல்லாமல்
English கிடைக்கிறது; மேலும் பாணிகளில் `vi` உரை இருந்தாலும் `vi` ஒருபோதும்
கண்டறியப்படுவதில்லை. Responses API உடல் அதன் திருப்பங்களை `input`-இல் வைத்திருக்கிறது;
அது மாதிரியாக எடுக்கப்படாததால், முதலில் `defaultLanguage`, பின்னர் English கிடைக்கிறது.
`messages`-இல் உள்ள எந்தப் பயனர் செய்தியிலும் உரை இல்லாதபோது அல்லது `autoDetect`
செயலிழந்திருக்கும்போது, முதலில் `defaultLanguage`, பின்னர் English பயன்படுத்தப்படுகிறது.
`languageConfig.enabled` செயலிழந்திருக்கும்போது மொழி English ஆகும் — ஆனால் ஒரு

### அடுக்கப்பட்ட Pipeline

Stacked mode **பல engine-களை வரிசையாக** இயக்கும் — பொதுவாக முதலில் RTK
(tool வெளியீட்டில் 60-90% சேமிப்பு), பின்னர் மீதமுள்ள உரையில் Caveman (~46% உள்ளீட்டுச்
சேமிப்பு). ஒன்றிணைக்கும்போது, அது **78-95% தகுதியான வரம்பு** ஆகும் (மேலுள்ள Upstream Savings Math-ஐப்
பார்க்கவும்): `1 - (1 - 0.60..0.90) × (1 - 0.46)`-ன் சராசரி ≈89%.

#### இது எவ்வாறு செயல்படுகிறது

```
உள்ளீடு (1000 token-கள்)
  → RTK (command-aware filter) → 200 token-கள்
    → Caveman (நிரப்புச் சொற்களை அகற்றுதல்) → 108 token-கள்
  → வெளியீடு (108 token-கள், ~89% சேமிப்பு)
```

#### எப்போது பயன்படுத்த வேண்டும்

பின்வருவனவற்றுக்கு stacked mode-ஐப் பயன்படுத்தவும்:

- Tool-அதிகமுள்ள workflow-கள் (agentic coding, ஆராய்ச்சி)
- செலவைக் கருத்தில் கொள்ளும் batch processing
- உங்களுக்கு அதிகபட்ச token சேமிப்பு தேவைப்படும்போது

Stacked pipeline-கள் உலகளாவிய `stackedPipeline` compression
அமைப்பு வழியாகவோ, அல்லது routing combo-க்கு ஒதுக்கப்பட்ட பெயரிடப்பட்ட compression combo வழியாகவோ கட்டமைக்கப்படுகின்றன (மேலுள்ள
Per-Combo Override-ஐப் பார்க்கவும்) — auto-combo `modePack` வழியாக அல்ல (அந்த field
auto-combo model தேர்வின் எடைகளை மட்டுமே மறுசீரமைக்கும்; மேலும் `stacked` என்பது செல்லுபடியாகும் pack பெயர் அல்ல).

## சுருக்கச் சேர்க்கை மேலெழுதல்கள்

வெவ்வேறு பயன்பாட்டு நிலைகளுக்கான நடத்தையை நுணுக்கமாகச் சரிசெய்ய, உலகளாவிய சுருக்க முறையை **ஒவ்வொரு சேர்க்கைக்கும் தனித்தனியாக** மேலெழுதலாம்:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

இது பின்வருவனவற்றுக்குப் பயனுள்ளதாக இருக்கும்:

- **குறியீட்டாக்கச் சேர்க்கைகள்**: நீண்ட அமர்வுகளுக்கு `aggressive` முறையைப் பயன்படுத்தவும்
- **விரைவான கேள்வி-பதில் சேர்க்கைகள்**: விரைவான பதில்களுக்கு `lite` முறையைப் பயன்படுத்தவும்
- **கருவி-செறிந்த சேர்க்கைகள்**: அதிகபட்சச் சேமிப்புக்கு `stacked` முறையைப் பயன்படுத்தவும்
- **உற்பத்திச் சேர்க்கைகள்**: தேக்கக வழங்குநர்களுக்கு மேலெழுதலை முடக்கியே வைக்கவும் — எப்போதும் செயல்பாட்டிலுள்ள
  தேக்கக-விழிப்புணர்வு சரிசெய்தல், `aggressive`/`ultra` முறைகளைத் தானாகவே `standard` முறைக்குத் தரமிறக்கும்
  (தேர்ந்தெடுக்கக்கூடிய `cache-aware` முறை எதுவும் இல்லை)
