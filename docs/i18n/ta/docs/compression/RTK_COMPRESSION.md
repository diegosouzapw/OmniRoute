RTK சுருக்கம் என்பது டெர்மினல் மற்றும் கருவி வெளியீட்டிற்கான OmniRoute-இன் கட்டளை-அறிவு கொண்ட சுருக்க இயந்திரமாகும். சோதனைப் பதிவுகள், உருவாக்க வெளியீடு,
தொகுப்பு மேலாளர் இரைச்சல், ஷெல் பதிவுகள், Docker வெளியீடு, git வெளியீடு மற்றும் ஸ்டாக் டிரேஸ்கள் ஆகியவற்றிலிருந்து பெரும்பாலான சூழல் வளர்ச்சி ஏற்படும் குறியீட்டு-முகவர் அமர்வுகளுக்காக இது
வடிவமைக்கப்பட்டுள்ளது.

RTK-ஐ `defaultMode: "rtk"` உடன் நேரடியாகவோ அல்லது அடுக்கப்பட்ட பைப்லைனின் முதல் படியாகவோ இயக்கலாம்; வழக்கமாக:

```txt
rtk -> caveman
```

இந்த வரிசை முதலில் இரைச்சலான இயந்திர வெளியீட்டைச் சுருக்கி, பின்னர் மீதமுள்ள உரையை Caveman சுருக்க அனுமதிக்கிறது.

அப்ஸ்ட்ரீம் RTK கட்டளை வெளியீட்டில் `60-90%` சேமிப்பைப் பதிவுசெய்கிறது. அதன் README மாதிரி அமர்வு
`~118,000` நிலையான டோக்கன்களிலிருந்து `~23,900` RTK டோக்கன்களாகக் குறைகிறது; இது `79.7%` சேமிப்பு (`~80%`) ஆகும். Caveman உள்ளீட்டுச் சுருக்கத்துடன் அடுக்கப்பட்ட சேமிப்பைக் கணக்கிடுவதற்கு OmniRoute
அந்த அப்ஸ்ட்ரீம் சராசரியைப் பயன்படுத்துகிறது:

```txt
RTK சராசரி:      80% சேமிப்பு
Caveman உள்ளீடு: 46% சேமிப்பு
அடுக்கப்பட்டது:  1 - (1 - 0.80) * (1 - 0.46) = 89.2% சேமிப்பு
வரம்பு:          1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

## இது எவற்றைச் சுருக்குகிறது

உள்ளமைக்கப்பட்ட பட்டியலில் தற்போது இந்த வகைகளில் 49 வடிகட்டிகள் வழங்கப்படுகின்றன:

| வகை       | எடுத்துக்காட்டுகள்                                            |
| --------- | ------------------------------------------------------------- |
| `git`     | `git status`, `git branch`, `git diff`, `git log`             |
| `test`    | Vitest, Jest, Pytest, Playwright, Go சோதனைகள், Cargo சோதனைகள் |
| `build`   | TypeScript, ESLint, Biome, Prettier, Vite, Webpack, Turbo, Nx |
| `package` | `npm install`, `npm audit`, `pip`, `uv sync`, Poetry, Bundler |
| `shell`   | `ls`, `find`, `grep`, பொதுவான ஷெல் பதிவுகள்                   |
| `docker`  | `docker ps`, Docker பதிவுகள்                                  |
| `infra`   | Terraform, OpenTofu, `systemctl status`                       |
| `generic` | JSON வெளியீடு, ஸ்டாக் டிரேஸ்கள், பொதுவான வெளியீட்டு மாற்றுவழி |

`open-sse/services/compression/engines/rtk/commandDetector.ts`-இல் உள்ள கண்டறிவி, வடிகட்டி தேர்வுக்கு முன் வெளியீட்டை
வகைப்படுத்துகிறது. ஒரு கட்டளை வகுப்பு போதுமானதாக இல்லாதபோது, கட்டளை வடிவம் அல்லது வெளியீட்டு ரெகுலர் எக்ஸ்பிரஷன் மூலமும் வடிகட்டிகள் பொருத்தப்படலாம்.

## வடிகட்டி தீர்மானம்

RTK வடிகட்டிகளை இந்த வரிசையில் ஏற்றுகிறது:

1. நம்பகமானதாக இருக்கும்போது மட்டும் `.rtk/filters.toml` மற்றும் `.rtk/filters.json` ஆகியவற்றிலிருந்து திட்ட வடிகட்டிகள்.
2. `DATA_DIR/rtk/filters.toml` மற்றும் `DATA_DIR/rtk/filters.json` ஆகியவற்றிலிருந்து உலகளாவிய வடிகட்டிகள்.
3. `open-sse/services/compression/engines/rtk/filters/`-இலிருந்து உள்ளமைக்கப்பட்ட வடிகட்டிகள்.

ஒரே நோக்கெல்லைக்குள், OmniRoute JSON வடிகட்டிகளைவிட RTK TOML ஸ்கீமா v1 வடிகட்டிகளுக்கு முன்னுரிமை அளிக்கப்படுகிறது. இறக்குமதி செய்யப்பட்ட கட்டளை-சார்ந்த
வடிகட்டி, அந்த நோக்கெல்லையில் உள்ள ஒரு பரந்த வடிகட்டியை மேலெழுதுவதற்காக, TOML `match_command` கோவைகள் கட்டளை-வகைப் பொருத்தத்திற்கு முன் சரிபார்க்கப்படுகின்றன. கோப்பு வடிவமைப்பைப் பொருட்படுத்தாமல், உலகளாவிய
நோக்கெல்லையைவிட திட்ட நோக்கெல்லைக்கே இன்னும் முன்னுரிமை அளிக்கப்படுகிறது.

ரெகுலர் எக்ஸ்பிரஷன் வடிகட்டிகள் கருவி வெளியீடு முகவர்களுக்குக் காட்டப்படும் விதத்தை மாற்றக்கூடும் என்பதால், திட்ட வடிகட்டிகள் திட்டமிட்டே நம்பிக்கை-கட்டுப்பாட்டுக்கு உட்படுத்தப்படுகின்றன. பின்வருவனவற்றில் ஒன்று உண்மையாக இருக்கும்போது திட்ட வடிகட்டி கோப்பு ஏற்றுக்கொள்ளப்படுகிறது:

- `rtkConfig.trustProjectFilters` என்பது `true`.
- `OMNIROUTE_RTK_TRUST_PROJECT_FILTERS=1` அமைக்கப்பட்டுள்ளது.
- திட்ட வடிகட்டி கோப்பிற்குப் பொருந்தும் SHA-256 ஹாஷை `.rtk/trust.json` கொண்டுள்ளது.

நம்பிக்கைக் கோப்பு எடுத்துக்காட்டு:

```json
{
  "filtersSha256": "0123456789abcdef...",
  "filtersTomlSha256": "fedcba9876543210..."
}
```

ஹாஷ்கள் தனித்தனியானவை: `filtersSha256` என்பது `.rtk/filters.json`-ஐ நம்புகிறது; `filtersTomlSha256`
என்பது `.rtk/filters.toml`-ஐ நம்புகிறது. இரண்டில் எந்தக் கோப்பைத் திருத்தினாலும், அதற்குரிய நம்பிக்கைப் பதிவு மட்டுமே செல்லாததாக்கப்படும். உலகளாவிய கோப்புகள்
நிர்வாகியால் நிறுவப்பட்டவை மற்றும் ஏற்கெனவே உள்ள உலகளாவிய-வடிகட்டி நம்பிக்கை நடத்தையைப் பயன்படுத்துகின்றன.

தனிப்பயன் வடிகட்டிகள் ஒரு வடிகட்டி பொருளாகவோ அல்லது வடிகட்டி பொருட்களின் அணியாகவோ இருக்கலாம். செல்லாத தனிப்பயன் வடிகட்டிகள்
தவிர்க்கப்பட்டு, `/api/context/rtk/filters` கண்டறிதல்களால் அறிக்கையிடப்படுகின்றன. செல்லாத உள்ளமைக்கப்பட்ட வடிகட்டிகள் உடனடியாகத் தோல்வியடைகின்றன.

## RTK TOML schema v1 இணக்கத்தன்மை

RTK TOML schema v1-ஐப் பயன்படுத்தும் அறிவிப்புமுறை வடிகட்டி கோப்புகளை OmniRoute பகுப்பாய்வு செய்யவும், சரிபார்க்கவும், சோதிக்கவும், நிறுவவும் முடியும்.
ஆதரிக்கப்படும் புலங்கள்: `description`, `match_command`, `strip_ansi`, `filter_stderr`,
`strip_lines_matching`, `keep_lines_matching`, `replace`, `match_output`, `truncate_lines_at`,
`head_lines`, `tail_lines`, `max_lines`, `on_empty`, மற்றும் `[[tests.<filter>]]` உள்வரி சோதனைகள்.
அறியப்படாத புலங்கள், செல்லுபடியாகாத அல்லது பாதுகாப்பற்ற வழக்கமான கோவைகள், ஒரே நேரத்தில் பயன்படுத்தப்படும் strip/keep விதிகள், 1 MiB-ஐ விடப் பெரிய கோப்புகள் மற்றும் அறியப்படாத வடிகட்டிகளுக்கான குறிப்புகள் ஆகியவை நிராகரிக்கப்படும். உள்வரி சோதனைகள் தோல்வியடையும் ஒரு கோப்பை ஆய்வுக்காகச் சரிபார்க்கலாம்; ஆனால் அதை நிறுவவோ ஏற்றவோ முடியாது. தனிப்பயன் கோப்பை ஏற்றுவதில் ஏற்படும் தோல்விகள் fail-open முறையிலேயே இருக்கும்: செல்லுபடியாகாத கோப்பு தவிர்க்கப்பட்டு, மீதமுள்ள வடிகட்டிகள் தொடர்ந்து செயல்படும்.

கிளையன்ட் ஏற்கெனவே கருவியின் வெளியீட்டைக் கைப்பற்றிய பிறகே OmniRoute அதைப் பெறுகிறது; எனவே `filter_stderr = true`
செயல்முறை வெளியீட்டைக் கைப்பற்றும் விதத்தை மாற்ற முடியாது. இந்தப் புலம் எந்தச் செயல்பாடும் இல்லாததாக ஏற்கப்பட்டு, சரிபார்ப்பின்போது ஓர் எச்சரிக்கை வழங்கப்படும்.
இது வேண்டுமென்றே **RTK TOML schema v1 இணக்கத்தன்மை** என விவரிக்கப்படுகிறது; RTK செயல்படுத்தக்கூடிய கோப்பு, shell hooks, Rust கட்டளைச் செயலாக்கங்கள் அல்லது அதன் trust-store அமைப்புடன் முழுமையான இணக்கத்தன்மை என அல்ல.

Dashboard-இன் மேம்பட்ட RTK காட்சி, ஒட்டப்பட்ட அல்லது பதிவேற்றப்பட்ட TOML-ஐ ஏற்கிறது. சரிபார்ப்பு வாசிப்பதற்கு மட்டும் உரியது.
நிறுவல், கட்டுப்படுத்தப்பட்ட அனுமதிகளுடன் `DATA_DIR/rtk/filters.toml` கோப்பை அணுவியல் முறையில் எழுதி, மறுதொடக்கம் இல்லாமல் நேரடி வடிகட்டிப் பட்டியலைப் புதுப்பிக்கிறது. ஏற்கெனவே உள்ள கோப்பை மாற்றுவதற்கு வெளிப்படையான `overwrite`
உறுதிப்படுத்தல் தேவை; மேலும் முதலில் `DATA_DIR/rtk/filters.toml.bak` உருவாக்கப்படும்.

## வடிகட்டி DSL

வடிகட்டிகள் [Compression Rules Format](./COMPRESSION_RULES_FORMAT.md) ஆவணத்தில் விவரிக்கப்பட்டுள்ள JSON schema-ஐப் பயன்படுத்துகின்றன.
இயக்கநேரம் பின்வரும் கட்டங்களை இந்த வரிசையில் செயல்படுத்துகிறது:

```txt
stripAnsi -> filterStderr -> replace -> matchOutput -> drop/include lines
  -> truncateLineAt -> head/tail/maxLines -> onEmpty
```

முக்கியமான புலங்கள்:

| புலம்                        | நோக்கம்                                                                           |
| ---------------------------- | --------------------------------------------------------------------------------- |
| `rules.stripAnsi`            | பொருத்துவதற்கு முன் முனைய நிற/கட்டுப்பாட்டுத் தொடர்களை அகற்றுதல்                  |
| `rules.filterStderr`         | பொருத்துதல்/வடிகட்டுதலுக்கு முன் பொதுவான stderr முன்னொட்டுகளை இயல்பாக்குதல்       |
| `rules.replace`              | வரிசைப்படுத்தப்பட்ட வழக்கமான கோவை மாற்றீடுகளைப் பயன்படுத்துதல்                    |
| `rules.matchOutput`          | அறியப்பட்ட நிபந்தனையுடன் வெளியீடு பொருந்தும்போது சுருக்கமான சாராம்சத்தை வழங்குதல் |
| `rules.matchOutput[].unless` | பிழை/தோல்விக் கோவை இருந்தால் குறுக்குவழியைத் தவிர்த்தல்                           |
| `rules.dropPatterns`         | தேவையற்ற வரிகளை அகற்றுதல்                                                         |
| `rules.includePatterns`      | நடவடிக்கை எடுக்கக்கூடிய வரிகளுக்கு முன்னுரிமை அளித்தல்                            |
| `rules.collapsePatterns`     | மீண்டும் மீண்டும் வரும் பொருந்தும் வரிகளைச் சுருக்குதல்                           |
| `rules.deduplicate`          | ஒவ்வொரு வடிகட்டிக்குமான விருப்பத் தேர்வு: தொடர்ச்சியான நகல் வரிகளைச் சுருக்குதல்  |
| `rules.truncateLineAt`       | Unicode-க்குப் பாதுகாப்பான ஒவ்வொரு வரிக்குமான துண்டிப்பு                          |
| `rules.onEmpty`              | அனைத்து வரிகளும் வடிகட்டப்பட்டால் பயன்படுத்த வேண்டிய மாற்றுச் செய்தி              |
| `tests[]`                    | சரிபார்ப்பு வாயிலால் பயன்படுத்தப்படும் உள்வரி மாதிரிகள்                           |

உள்ளமைந்த வடிகட்டிகளில் உள்வரி `tests[]` மாதிரிகள் இடம்பெற வேண்டும் என எதிர்பார்க்கப்படுகிறது. தனிப்பயன் வடிகட்டிகளிலும் அவை இடம்பெற வேண்டும்,
குறிப்பாக அவை பல திட்டங்களுக்கு இடையே பகிரப்படும்போது.

## வரி நகல்நீக்கம் (இரண்டு அடுக்குகள்)

RTK, இரண்டு தனித்தனி அடுக்குகளில் நகல் வரிகளைச் சுருக்குகிறது:

1. **ஒவ்வொரு வடிகட்டிக்குமான `deduplicate` (விருப்பத் தேர்வு, இயல்புநிலை `false`).** ஒரு வடிகட்டி, துண்டிப்பதற்கு முன், _அந்த வடிகட்டியுடன் பொருந்திய வெளியீட்டிற்குள்_ அடுத்தடுத்து வரும் நகல் வரிகளைச் சுருக்க `rules.deduplicate: true` என அமைக்கலாம்.
   இது `lineFilter.ts`-இன் உள்ளே இயங்குகிறது. பழைய வடிகட்டிகளுக்கு, வடிகட்டி `collapsePatterns`-ஐ வரையறுத்திருந்தால் இது தானாகவே இயக்கப்படும். `open-sse/services/compression/engines/rtk/filterSchema.ts`-இல் உள்ள ஸ்கீமா:
   `deduplicate: z.boolean().default(false)`.
2. **எஞ்சின் முழுவதற்குமான `deduplicateThreshold` (இயல்புநிலை `3`).** அனைத்து வடிகட்டிகளும் இயங்கிய பிறகு, முழு முடிவிலும் அடுத்தடுத்து வரும் ஒரே மாதிரியான வரிகளின் எந்த `>= deduplicateThreshold` தொடரையும் எஞ்சின் சுருக்குகிறது
   (`deduplicateRepeatedLines`, `engines/rtk/index.ts`-இல் பயன்படுத்தப்படுகிறது). இயல்பாக்கத்தின்போது இந்த மதிப்பு 2–100 வரம்பிற்குள் கட்டுப்படுத்தப்படுகிறது.

ஒவ்வொரு வடிகட்டிக்குமான சுற்று முதலில் (வடிகட்டிக்குள்) இயங்குகிறது; எஞ்சின் முழுவதற்குமான சுற்று கடைசியாக (இணைக்கப்பட்ட வெளியீட்டின் மீது) இயங்குகிறது. எனவே, இரட்டை எண்ணிக்கையிடல் இல்லாமல் இரண்டும் ஒன்றிணைந்து செயல்படுகின்றன.

## வரித் தொகுப்பாக்கம் (`enableGrouping`)

`rtkConfig.enableGrouping` என்பது `true` ஆக இருக்கும்போது (இயல்புநிலை `false`), நகல்நீக்கத்திற்குப் பிந்தைய முடிவின் மீது RTK கூடுதலாக ஒரு `groupSimilarLines` சுற்றை இயக்குகிறது. இது அடுத்தடுத்து வரும் _கிட்டத்தட்ட சமமான_ (பைட் அளவில் முற்றிலும் ஒரே மாதிரியாக இல்லாத) வரிகளின் தொடர்களைச் சுருக்குகிறது. `rtkConfig.groupingThreshold` (இயல்புநிலை `3`) என்பது தொகுப்பாக்கத்தைத் தூண்டும் குறைந்தபட்ச தொடர் நீளம்.
இது `deduplicateThreshold`-இன் கட்டமைப்புரீதியான இணை அம்சமாகும்: நகல்நீக்கம் துல்லியமான மறுநிகழ்வுகளைக் கையாள்கிறது; தொகுப்பாக்கம் "சிறிய வேறுபாடுகளுடன் அதே வடிவத்தைக் கொண்டவற்றை" கையாள்கிறது. இரண்டு கொடிகளும் `key_value` அட்டவணையில் நிலையாகச் சேமிக்கப்படும் `rtkConfig` JSON-இன் பகுதிகளாகும் (மேலே உள்ள கட்டமைப்பைப் பார்க்கவும்); எனவே மறுதொடக்கங்களுக்குப் பிறகும் இந்த அமைப்பு நீடிக்கும்.

## குறியீட்டுக் கருத்துரை நீக்கம் (`stripCodeComments` / `preserveDocstrings`)

`rtkConfig.applyToCodeBlocks` இயக்கப்பட்டிருக்கும்போது, வேலியிடப்பட்ட குறியீட்டுத் தொகுதிகளிலிருந்தும் RTK கருத்துரைகளை நீக்க முடியும்:

- `stripCodeComments` (இயல்புநிலை `false`) — விருப்பத் தேர்வு. இது `true` ஆக இருக்கும்போது, JavaScript மற்றும் TypeScript வேலியிடப்பட்ட தொகுதிகளிலிருந்து RTK கருத்துரைகளை நீக்குகிறது. வரலாற்று ரீதியாக இந்தக் கொடி வாசிக்கப்பட்டது, ஆனால் ஒருபோதும் பயன்படுத்தப்படவில்லை; எனவே உற்பத்திச் சூழலில் அறிவிப்பின்றி மாற்றம் ஏற்படுவதைத் தவிர்க்க, இயல்புநிலை "பாதுகாத்தல்" என்றே தொடர்கிறது.
- `preserveDocstrings` (இயல்புநிலை `true`) — கருத்துரைகளை நீக்கும்போது, JSDoc/`/** … */` தொகுதிக் கருத்துரைகள் பாதுகாக்கப்படுகின்றன (அவை பயன்படுத்தும் பைட்களைவிட அதிக மதிப்புள்ள API ஆவணத்தைக் கொண்டுள்ளன). அவற்றையும் நீக்க இதை `false` ஆக அமைக்கவும்.

கருத்துரை நீக்கம் `open-sse/services/compression/engines/rtk/codeStripper.ts`-இல் செயல்படுத்தப்பட்டுள்ளது. சரம், வார்ப்புரு மற்றும் regex நேரடிக் குறியீடுகள் ஒருபோதும் கருத்துரைகளாகத் தவறாகக் கருதப்படாமல் இருக்க இது **TypeScript parser**-ஐப் பயன்படுத்துகிறது (regex அல்ல); மேலும் JSX கண்டறியப்படும்போது இது முழுமையாக வெளியேறுகிறது (எனவே JSX வெளிப்பாட்டுக் கொள்கலன் கருத்துரைகள் ஒருபோதும் சிதைக்கப்படுவதில்லை). கருத்துரை நீக்கம் தற்போது **JavaScript மற்றும் TypeScript-க்கு மட்டுமே** பொருந்துகிறது — நீக்கியின் `CodeLanguage` தொகுப்பில் உள்ள பிற மொழிகளில் (Python, Rust, Go, Ruby, Java) காலி வரிகளும் இடைவெளிகளும் சுருக்கப்படுகின்றன; ஆனால் கருத்துரைகள் நீக்கப்படுவதில்லை. நீக்கப்பட்ட தொகுதியின் இயக்கம் `rulesApplied`-இல் `rtk:code-strip` எனக் குறியிடப்படுகிறது.

> **குறிப்பு — GCF / அட்டவணை குறியாக்கம் என்பது ஒரு தனி எஞ்சின்.** RTK-இல் "GCF"
> (Graph Compact Format) அட்டவணை/நிரல் சார்ந்த JSON குறியாக்கி **இல்லை**. பழைய
> `omni-tabular` குறியாக்கிக்குப் பதிலாக வந்த அந்தக் குறியாக்கி, **headroom** எஞ்சினில் உள்ளது
> (`open-sse/services/compression/engines/headroom/`, அதனுடன் சேர்க்கப்பட்ட codec
> `headroom/gcf/`-இன் கீழ் உள்ளது). இங்கு ஆவணப்படுத்தப்பட்டுள்ள RTK வடிகட்டிக் குழாயமைப்புடன் இதற்கு எந்தத் தொடர்பும் இல்லை.

## உள்ளமைவு

உலகளாவிய அமைப்புகள் `/api/settings/compression` வழியாகக் கிடைக்கின்றன. RTK-க்கான குறிப்பிட்ட அமைப்புகளும்
`/api/context/rtk/config` வழியாகக் கிடைக்கின்றன.

```json
{
  "defaultMode": "stacked",
  "autoTriggerMode": "stacked",
  "autoTriggerTokens": 32000,
  "stackedPipeline": [
    { "engine": "rtk", "intensity": "standard" },
    { "engine": "caveman", "intensity": "full" }
  ],
  "rtkConfig": {
    "enabled": true,
    "intensity": "standard",
    "applyToToolResults": true,
    "applyToCodeBlocks": false,
    "applyToAssistantMessages": false,
    "enabledFilters": [],
    "disabledFilters": [],
    "maxLinesPerResult": 120,
    "maxCharsPerResult": 12000,
    "deduplicateThreshold": 3,
    "customFiltersEnabled": true,
    "trustProjectFilters": false,
    "rawOutputRetention": "never",
    "rawOutputMaxBytes": 1048576,
    "enableGrouping": false,
    "groupingThreshold": 3,
    "stripCodeComments": false,
    "preserveDocstrings": true
  }
}
```

`enabledFilters` மற்றும் `disabledFilters` ஆகியவை filter id-களைப் பயன்படுத்துகின்றன; எடுத்துக்காட்டாக, `test-vitest` அல்லது `git-diff`.

முழுமையான `rtkConfig` வடிவம் `open-sse/services/compression/types.ts`-இல் உள்ள
`RtkConfig` / `DEFAULT_RTK_CONFIG` மூலம் வரையறுக்கப்பட்டுள்ளது. முழு object-உம் SQLite
`key_value` table-இல் `namespace = "compression"`, `key = "rtkConfig"` என்பதன் கீழ் ஒற்றை JSON மதிப்பாகச்
சேமிக்கப்படுகிறது (`src/lib/db/compression.ts`), மேலும் படிக்கப்படும்போது `normalizeRtkConfig` மூலம் சீராக்கப்படுகிறது. எனவே கீழே உள்ள ஒவ்வொரு field-உம்
— `enableGrouping`, `groupingThreshold`, `stripCodeComments`, மற்றும் `preserveDocstrings` உட்பட —
அதே store வழியாக எழுதப்பட்டு மீண்டும் படிக்கப்படுவதுடன், மறுதொடக்கத்திற்குப் பிறகும் நிலைத்திருக்கும்.

| Key                    | இயல்புநிலை | நோக்கம்                                                                                                                 |
| ---------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------- |
| `deduplicateThreshold` | `3`        | Engine முழுவதற்கும்: சுருக்கப்பட வேண்டிய தொடர்ச்சியான ஒரே மாதிரியான வரிகளின் குறைந்தபட்ச எண்ணிக்கை (2–100 வரம்பிற்குள்) |
| `enableGrouping`       | `false`    | விருப்பத்தேர்வு: ஏறக்குறைய ஒரே மாதிரியான தொடர்ச்சியான வரிகளின் தொடர்களைச் சுருக்கும்                                    |
| `groupingThreshold`    | `3`        | தொகுத்தலைத் தூண்டும் தொடர்ச்சியான ஒத்த வரிகளின் குறைந்தபட்ச எண்ணிக்கை                                                   |
| `stripCodeComments`    | `false`    | விருப்பத்தேர்வு: fenced code block-களிலிருந்து comment-களை அகற்றும் (`applyToCodeBlocks` தேவை)                          |
| `preserveDocstrings`   | `true`     | comment-களை அகற்றும்போது, JSDoc/`/** … */` block-களைத் தக்கவைக்கும்                                                     |

## API

| Route                              | முறை | நோக்கம்                                                            |
| ---------------------------------- | ---- | ------------------------------------------------------------------ |
| `/api/context/rtk/config`          | GET  | RTK config-ஐப் படிக்கும்                                           |
| `/api/context/rtk/config`          | PUT  | RTK config-ஐப் புதுப்பிக்கும்                                      |
| `/api/context/rtk/filters`         | GET  | filter பட்டியல் மற்றும் ஏற்றுதல் கண்டறிதல் தகவல்களைப் பட்டியலிடும் |
| `/api/context/rtk/import`          | POST | RTK TOML schema v1 file-களைச் சரிபார்க்கும் அல்லது நிறுவும்        |
| `/api/context/rtk/test`            | POST | ஒரு text payload-க்கான RTK compression-ஐ முன்னோட்டமிடும்           |
| `/api/context/rtk/raw-output/[id]` | GET  | தக்கவைக்கப்பட்ட, மறைக்கப்பட்ட raw output-ஐப் படிக்கும்             |
| `/api/compression/preview`         | POST | எந்த compression mode-ஐயும் முன்னோட்டமிடும்                        |

RTK சோதனை payload:

```json
{
  "command": "npm test",
  "text": "FAIL tests/example.test.ts\nAssertionError: expected true\nTest Files 1 failed",
  "config": {
    "intensity": "standard"
  }
}
```

Compression முன்னோட்ட payload:

```json
{
  "mode": "stacked",
  "messages": [
    {
      "role": "tool",
      "content": "FAIL tests/example.test.ts\nAssertionError: expected true\nTest Files 1 failed"
    }
  ],
  "config": {
    "rtkConfig": {
      "rawOutputRetention": "failures"
    }
  }
}
```

நிர்வாக route-களுக்கு dashboard நிர்வாக அங்கீகாரம் அல்லது பொருந்தும் API-key policy தேவை.

RTK TOML சரிபார்ப்பு payload:

```json
{
  "action": "validate",
  "content": "schema_version = 1\n\n[filters.my-tool]\nmatch_command = \"^my-tool\\\\b\"\nmax_lines = 20\n"
}
```

சரிபார்க்கப்பட்ட file-ஐ உலகளவில் நிறுவ `"action": "install"` என்பதைப் பயன்படுத்தவும். ஏற்கெனவே உள்ள global file-ஐ மாற்றுவதை மதிப்பாய்வு செய்து உறுதிப்படுத்திய
பிறகு மட்டுமே `"overwrite": true` என்பதைச் சேர்க்கவும்.

## மூல வெளியீட்டை மீட்டெடுத்தல்

RTK பொதுவாகச் சுருக்கப்பட்ட உரையை மட்டுமே வழங்குகிறது. பிழைத்திருத்தத்திற்காக, திருத்தப்பட்ட
மூல வெளியீட்டைத் தக்கவைக்க `rawOutputRetention`-ஐப் பயன்படுத்தலாம்:

| மதிப்பு    | செயல்பாடு                                                                          |
| ---------- | ---------------------------------------------------------------------------------- |
| `never`    | மூல வெளியீட்டைத் தக்கவைக்காது                                                      |
| `failures` | தோல்வியாக இருக்கக்கூடிய வெளியீட்டை மட்டும் தக்கவைக்கும்                            |
| `always`   | திருத்தத்திற்குப் பிறகு, சுருக்கப்பட்ட ஒவ்வொரு RTK மூல வெளியீட்டையும் தக்கவைக்கும் |

தக்கவைக்கப்பட்ட கோப்புகள் இதன் கீழ் எழுதப்படும்:

```txt
DATA_DIR/rtk/raw-output/
```

பொதுவான bearer token-கள், API key-கள், Slack token-கள்,
AWS access key-கள் மற்றும் ஒதுக்கீட்டு-பாணி `token=...`, `secret=...`, `password=...` மதிப்புகள் உள்ளிட்ட ரகசியங்கள் நிலையாகச் சேமிக்கப்படுவதற்கு முன் திருத்தப்படும். பகுப்பாய்வு
சுட்டி id, அளவு மற்றும் hash metadata-வை மட்டுமே சேமிக்கும்.

## சரிபார்ப்பு வாயில்

கவனம் செலுத்தப்பட்ட சரிபார்ப்பு வாயில், வெளிப்புறக் கட்டளைகளை shell மூலம் இயக்காமல் உள்ளமைக்கப்பட்ட inline filter சோதனைகளை இயக்குகிறது:

```bash
node --import tsx/esm --test tests/unit/compression/rtk-verify.test.ts
```

விரிவான RTK வாயில்:

```bash
node --import tsx/esm --test \
  tests/unit/compression/rtk-*.test.ts \
  tests/unit/compression/pipeline-integration.test.ts \
  tests/unit/compression/context-compression-api.test.ts
```

வெளியீட்டிற்கு முன் விரிவான சுருக்க வாயிலை இயக்கவும்:

```bash
node --import tsx/esm --test \
  tests/unit/compression/*.test.ts \
  tests/golden-set/*.test.ts \
  tests/integration/compression-pipeline.test.ts \
  tests/unit/api/compression/compression-api.test.ts
```

## RTK-ஐ விரிவாக்குதல்

1. filter JSON கோப்பைச் சேர்க்கவும் அல்லது புதுப்பிக்கவும்.
2. முக்கியமான செயல்பாட்டை நிரூபிக்கும் குறைந்தபட்சம் ஒரு `tests[]` மாதிரியைச் சேர்க்கவும்.
3. புதிய கட்டளைக் குடும்பங்களுக்கு `tests/unit/compression/fixtures/rtk/`-இன் கீழ் fixture ஒன்றைச் சேர்க்கவும்.
4. புதிய வெளியீட்டு வகுப்பை அறிமுகப்படுத்தும்போது கட்டளை கண்டறிதல் coverage-ஐச் சேர்க்கவும்.
5. சரிபார்ப்பு மற்றும் விரிவான RTK வாயில்களை இயக்கவும்.
6. filter திட்டத்திற்குரிய உள்ளூர் filter ஆக இருந்தால், ஆய்வுக்குப் பிறகு மட்டுமே `.rtk/filters.json`-ஐ commit செய்து `.rtk/trust.json`-ஐப் புதுப்பிக்கவும்.

## தீவிரத்தன்மை நிலைகள் (v3.8.16+)

**சுருக்கத்தின் தீவிரத்தன்மை** மற்றும் **பாதுகாப்பு** ஆகியவற்றுக்கு இடையே சமநிலையை ஏற்படுத்தும் **3 தீவிரத்தன்மை நிலைகளை** RTK ஆதரிக்கிறது. engine config-இல் உள்ள `config.intensity` வழியாக நிலை அமைக்கப்படுகிறது.

### 3 நிலைகள்

| நிலை                    | துண்டிப்பு வரம்பு       | token சேமிப்பு | அபாயம்       | மிகவும் ஏற்றது                     |
| ----------------------- | ----------------------- | -------------- | ------------ | ---------------------------------- |
| `minimal`               | ஒரு பகுதிக்கு 24 வரிகள் | ~20-40%        | மிகக் குறைவு | முக்கியமான சூழல் கொண்ட production  |
| `standard` (இயல்புநிலை) | ஒரு பகுதிக்கு 24 வரிகள் | ~50-70%        | குறைவு       | தினசரி coding அமர்வுகள்            |
| `aggressive`            | ஒரு பகுதிக்கு 16 வரிகள் | ~70-90%        | நடுத்தரம்    | நீண்ட அமர்வுகள், அதிகபட்ச சேமிப்பு |

```ts
config.intensity === "aggressive" ? 16 : 24,
```

### தனிப்பயன் வடிகட்டிகளை ஏற்றுதல்

அங்கீகரிக்கப்பட்ட இடத்தில் கோப்பை வைக்கவும்:

```
~/.omniroute/rtk/filters/my-filter.json     # பயனர் நிலை
<project>/.rtk/filters/my-filter.json      # திட்ட நிலை
```

தொடக்கத்தின்போது `open-sse/services/compression/engines/rtk/filterLoader.ts`-இல் உள்ள `loadRtkFilters()` வழியாக வடிகட்டிகள் தானாகவே ஏற்றப்படும். ஏற்றி பின்வரும் இடங்களிலிருந்து வடிகட்டிகளைக் கண்டறிகிறது:

- உள்ளமைக்கப்பட்ட பட்டியல்: `open-sse/services/compression/engines/rtk/filters/`
- பயனர் கோப்பகம்: `~/.omniroute/rtk/filters/`
- திட்டக் கோப்பகம்: `<project>/.rtk/filters/`

நிரல்முறையில் வடிகட்டிகளை ஏற்ற:

```ts
import { loadRtkFilters } from "@omniroute/open-sse/services/compression/engines/rtk/filterLoader";

// விருப்பங்கள்: customFiltersEnabled (பயனர்/திட்ட வடிகட்டிகளை ஏற்றும், இயல்பாக இயக்கப்பட்டிருக்கும்),
// trustProjectFilters, refresh.
const filters = loadRtkFilters({ customFiltersEnabled: true });
```

### சரிபார்ப்பு

ஏற்றப்படும்போது வடிகட்டிகள் Zod திட்டவடிவத்திற்கு எதிராகச் சரிபார்க்கப்படுகின்றன. தவறான கட்டமைப்பைக் கொண்ட வடிகட்டி ஏற்றப்படாமல், பிழை பதிவு செய்யப்படும்:

```
RTK_FILTER_LOADER: "my-filter" வடிகட்டி சரிபார்ப்பில் தோல்வியடைந்தது:
  - rules.replace.0.pattern: தவறான regex
  - match.commands: காலியாக இருக்கக்கூடாது
```

நிறுவப்பட்டுள்ள அனைத்து வடிகட்டிகளையும் சரிபார்க்க, `open-sse/services/compression/engines/rtk/verify.ts`-இலிருந்து ஏற்றுமதி செய்யப்படும் `runRtkFilterTests()`-ஐ அழைக்கவும்.

### சிறந்த நடைமுறைகள்

1. **எப்போதும் `tests[]`-ஐச் சேர்க்கவும்** — அவை உங்கள் வடிகட்டி செயல்படுகிறது என்பதை நிரூபித்து, பின்னடைவுகளைத் தடுக்கின்றன
2. **குறுக்குவழி முடிவுகளுக்கு `matchOutput`-ஐப் பயன்படுத்தவும்** — ஒரே வரி முழு விவரத்தையும் தெரிவித்தால், முழுத் தொகுதியையும் மாற்றவும்
3. **`strip`-ஐ விட `keep`-ஐ விரும்பவும்** — வெளிப்படையான "எப்போதும் பாதுகாக்கவும்" விதிகள், "எப்போதும் அகற்றவும்" விதிகளை விடப் பாதுகாப்பானவை
4. **அனைத்து 3 தீவிர நிலைகளிலும் சோதிக்கவும்** — `minimal` எந்த மாற்றமும் செய்யக்கூடாது; `aggressive` நிலையிலும் பிழைகள் பாதுகாக்கப்பட வேண்டும்
5. **`unless` புலத்தைப் பயன்படுத்தவும்** — "X இருந்தால் தூண்ட வேண்டாம்" என்ற நிபந்தனையுடன் குறுக்குவழி முடிவுகளைப் பாதுகாக்கவும்

## மூல வெளியீட்டு மீட்பு & சரிபார்ப்பு நுழைவாயில்

RTK வெளியீட்டைத் தீவிரமாகச் சுருக்கும்போது, பிழைத்திருத்தம், தணிக்கை அல்லது மீண்டும் இயக்குதல் ஆகியவற்றுக்காக நீங்கள் **அசல் உரையை மீட்டெடுக்கலாம்**.

### மூல வெளியீட்டு மீட்பு எவ்வாறு செயல்படுகிறது

```
அசல் வெளியீடு (10K டோக்கன்கள்)
        │
        ▼
RTK சுருக்கம் (rawOutput.enabled=true உடன்)
        │
        ├─▶ சுருக்கப்பட்ட வெளியீடு (2K டோக்கன்கள்)  ──▶ LLM-க்கு
        │
        └─▶ அசல் வெளியீடு (10K டோக்கன்கள்)         ──▶ DB-இல் சேமிக்கப்படும்
                                                  (request_id மூலம் இணைக்கப்பட்டது)
```

### மூல வெளியீட்டுச் சேமிப்பைச் செயல்படுத்துதல்

**ஒவ்வொரு கோரிக்கைக்கும்** (combo உள்ளமைவில்):

```json
{
  "compression": {
    "engine": "rtk",
    "intensity": "aggressive",
    "rawOutput": {
      "enabled": true,
      "maxBytes": 1048576 // 1MB வரம்பு
    }
  }
}
```

**இயல்புநிலை**: `rawOutput.enabled: false` (சேமிப்பிடத்தைச் சேமிக்கிறது).

### சேமிப்பிடச் செலவு

| ஒவ்வொரு கோரிக்கைக்கும்           | 1MB வரம்பு    | 10MB வரம்பு    |
| -------------------------------- | ------------- | -------------- |
| சராசரி சுருக்கப்பட்ட வெளியீடு    | ~5KB          | ~5KB           |
| சேமிக்கப்பட்ட மூல வெளியீடு       | ~50-500KB     | ~500KB-5MB     |
| நாளொன்றுக்கு 1000 கோரிக்கைகளுடன் | 50-500MB/நாள் | 500MB-5GB/நாள் |

> **பரிந்துரை**: மூல வெளியீட்டை எப்போதும் செயல்பாட்டில் வைத்திருக்காமல், **பிழைத்திருத்த அமர்வுகள்** அல்லது **மாதிரி அடிப்படையிலான தணிக்கை** ஆகியவற்றுக்கு மட்டும் செயல்படுத்தவும்.

### அசலை மீட்டெடுத்தல்

```ts
import { readRtkRawOutput } from "omniroute/compression/engines/rtk/rawOutput";

const raw = readRtkRawOutput(pointerId); // சுருக்கப் புள்ளிவிவரங்களிலிருந்து pointerId
if (raw) {
  console.log("Original output:", raw);
}
```

சுருக்கத்திற்குப் பிறகு `CompressionStats.rtkRawOutputPointers[]`-இல் `pointerId` திருப்பி அனுப்பப்படுகிறது.
செயல்பாட்டுக் கையொப்பத்திற்கு `open-sse/services/compression/engines/rtk/rawOutput.ts:102`-ஐப் பார்க்கவும்.

### சரிபார்ப்பு நுழைவாயில்

**RTK வடிகட்டி சரிபார்ப்பு** (`open-sse/services/compression/engines/rtk/verify.ts`) அனைத்து வடிகட்டிகளையும் அவற்றின் `tests[]`-க்கு எதிராகச் சரிபார்த்து, அனைத்து 3 தீவிர நிலைகளிலும் செயல்பாடு சரியாக இருப்பதை உறுதிப்படுத்துகிறது.

சரிபார்ப்பை இயக்குவதற்கு **`runRtkFilterTests()`-ஐ அழைக்கவும்**:

```ts
import { runRtkFilterTests } from "open-sse/services/compression/engines/rtk/verify";

const result = runRtkFilterTests();
console.log(`Passed: ${result.outcomes.filter((o) => o.passed).length}`);
console.log(`Failed: ${result.outcomes.filter((o) => !o.passed).length}`);
if (!result.passed) {
  console.error("Filters failed verification");
  result.outcomes
    .filter((o) => !o.passed)
    .forEach((o) => {
      console.error(
        `  - ${o.filterId} / ${o.testName}: expected "${o.expected}", got "${o.actual}"`
      );
    });
}
```

**இது சரிபார்ப்பவை**:

1. ஒவ்வொரு வடிகட்டியும் ஏற்றப்பட்டு, schema சரிபார்ப்பில் தேர்ச்சி பெறுகிறது
2. ஒவ்வொரு `tests[]` பதிவும் எதிர்பார்க்கப்படும் வெளியீட்டை உருவாக்குகிறது
3. `minimal` தீவிரம் எந்தச் செயல்பாடும் செய்யாது (அசலைப் பாதுகாத்து, கட்டமைப்பு வடிகட்டிகளை மட்டும் பயன்படுத்துகிறது)
4. `aggressive` தீவிரம் பிழைகள், சோதனைத் தோல்விகள் மற்றும் stack trace-களைப் பாதுகாக்கிறது
5. சுருக்கப்பட்ட வெளியீடு ஒருபோதும் அசல் உள்ளீட்டைவிடப் பெரிதாக இருப்பதில்லை

- மூலம்: `open-sse/services/compression/engines/rtk/` (63 கோப்புகள், ~70KB)

- **ஒரு வடிகட்டி மாற்றத்தை merge செய்வதற்கு முன்** — சோதனைகள் தேர்ச்சி பெறுவதை எப்போதும் உறுதிப்படுத்தவும்
