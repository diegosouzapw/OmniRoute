> **இந்த ஆவணம் என்ன.** தொழில்துறையின் சிறந்த நடைமுறைகளுடன் ஒப்பிடப்பட்ட OmniRoute-இன்
> தரக் கட்டுப்பாட்டு அமைப்பைப் பற்றிய விமர்சன மதிப்பீடு, **அத்துடன்** அனைத்து தரச்
> சோதனைச் சாவடிகளின் விரிவான பட்டியல் மற்றும் இதே அமைப்பை எந்தத் திட்டத்திலும்
> பயன்படுத்துவதற்கான **கருவி-சார்பற்ற மறுஉருவாக்கத் திட்டம்**. நினைவிலிருந்து அல்லாமல்,
> களஞ்சியத்தின் உண்மையான நிலையிலிருந்து 2026-06-16 அன்று உருவாக்கப்பட்டது.
>
> அளவுகோல்கள்: OWASP DSOMM · OpenSSF Scorecard · SLSA · SonarQube "Clean as You Code" ·
> Quality-Ratchet முறை · DORA 2024 · OWASP LLM Top 10 (2025) · மாற்றச் சோதனையின் சிறந்த நடைமுறைகள்.
>
> ஒவ்வொரு கட்டுப்பாட்டிற்குமான அதிகாரப்பூர்வ மேற்கோளுக்கு (ஒவ்வொரு கட்டுப்பாடும் எதைச் சரிபார்க்கிறது,
> CI பணி, ratchet மற்றும் கொள்கைக்கு இடையிலான வேறுபாடு, தடுப்பது மற்றும் ஆலோசனை வழங்குவதற்கு இடையிலான வேறுபாடு),
> [தரக் கட்டுப்பாடுகள் மேற்கோள்](../architecture/QUALITY_GATES.md)-ஐப் பார்க்கவும்.

## பகுதி 1 — தீர்ப்பும் முதிர்ச்சி வகைப்பாடும்

**ஒட்டுமொத்தத் தரம்: A− / "மேம்பட்டது". முதல் ~5–10% திட்டங்களில் ஒன்று.** தொழில்துறை வெளிப்படையாகப்
பெயரிட்டுள்ள பல முறைகளை இந்த அமைப்பு சுயாதீனமாகச் செயல்படுத்துகிறது — இதுவே மிகவும் வலுவான
ஒத்திசைவுக் குறியீடு (நாங்கள் ஒரு சரிபார்ப்புப் பட்டியலை நகலெடுக்கவில்லை; சரியான நடைமுறைகளைத் தனித்தனியாக அடைந்தோம்).

## பகுதி 2 — விமர்சன மதிப்பீடு (பலங்கள் + நேர்மையான பலவீனங்கள்)

### பலங்கள் (சராசரிக்கும் மேலானவை)

1. **பல-அளவீட்டு ratchet இயந்திரம்.** அமைப்பின் மையம். `quality-baseline.json`-இல் 24 அளவீடுகள்
   - 4 பிரத்யேக baseline-கள்; ஒவ்வொன்றிலும் திசை (`up`/`down`), சகிப்புத்தன்மை (`eps`), தளர்வு
     (`tightenSlack`) மற்றும் `dedicatedGate` கொடி உள்ளன. சரிசெய்யப்பட்டவை **தொடர்ந்தும்**
     சரியாகவே இருக்கும் — இது codebase சீரழிவுக்கான எதிர்மருந்து.
2. **விநியோகச் சங்கிலிக்கான பல-அடுக்கு பாதுகாப்பு.** SAST (CodeQL/Sonar) + ரகசியங்கள் (`useDefault`
   உடன் gitleaks) + SCA (osv/npm-audit/Trivy/Dependabot) + உரிமங்கள் + lockfile + SBOM + SLSA
   மூலம் + Scorecard + workflow வலுப்படுத்தல் (zizmor). மிகச் சில codebase-களிலேயே இவ்வளவு
   முழுமையான தொகுப்பு உள்ளது.
3. **Goodhart விதிக்கு எதிரான பாதுகாப்புகள்.** Coverage-ஐ இலக்காகக் கொள்வது ஒரு வழக்கமான
   எதிர்முறை ("அளவீடு இலக்காக மாறும்போது, அது ஒரு நல்ல அளவீடாக இருப்பதை நிறுத்திவிடுகிறது").
   அதற்கான சமநிலைகள் நம்மிடம் உள்ளன: **mutation testing** (test அந்த வரியை இயக்குகிறதா என்பதை
   மட்டும் அல்லாமல், அது bug-ஐக் கண்டறிகிறதா என்பதையும் அளவிடுகிறது), **`check-test-masking`**
   (தேர்ச்சி பெறுவதற்காக assert-களை பலவீனப்படுத்துவதைத் தடுக்கிறது), **ஒவ்வொரு module-க்குமான
   coverage குறைந்தபட்சங்கள்** (எளிய பகுதிகளை மட்டுமல்லாமல், HIGH-risk code-ஐயும் சோதிக்கக்
   கட்டாயப்படுத்துகின்றன) மற்றும் **`check-pr-evidence`** (கடுமையான விதி #18).
4. **புனைவு-எதிர்ப்பு / ஒத்திசைவு gate-கள்.** அரிதானதும் மதிப்புமிக்கதுமான ஒரு வகை:
   `check-known-symbols`, `check-fetch-targets`, `check-openapi-routes`, `check-docs-symbols`
   ஆகியவை docs, specs மற்றும் string dispatches ஆகியவை இன்னும் பயன்பாட்டிலுள்ள symbol-களைக்
   குறிக்கின்றனவா என்பதை உறுதிப்படுத்துகின்றன. lint/test கண்டறியாத "சிதைவை" இவை கண்டறிகின்றன.
5. **ஆலோசனை→தடுப்பு வாழ்க்கைச் சுழற்சி.** புதிய gate-கள் ஆலோசனை நிலையாக நுழைகின்றன
   (முதிர்ச்சியடையும் காலத்தில் merge-களைத் தடுப்பதில்லை), பின்னர் cycle முடிவில் தடுக்கும்
   நிலைக்கு மாறுகின்றன. உச்ச வரம்பை இழக்காமல் உராய்வைக் குறைக்கிறது.
6. **உள்கட்டமைப்பு இல்லாதபோது சீரான skip.** binary/network செயலிழந்தால் scanner-கள்
   (`--ratchet`) `exit 0` உடன் வெளியேறுகின்றன — இல்லாத உள்கட்டமைப்பு ஒருபோதும் நியாயமான PR-ஐத்
   தடுப்பதில்லை. முதிர்ந்த பொறியியல் அணுகுமுறை.
7. **முறைப்படுத்தப்பட்ட பண்பாடு.** கடுமையான விதிகள் + `trust-but-verify` + stale-allowlist +
   evidence-gate ஆகியவை ஒழுக்கத்தைத் தானியக்கச் சரிபார்ப்பாக மாற்றுகின்றன.

### நேர்மையான பலவீனங்கள் (உண்மையான இடைவெளிகள்)

1. **🔴 fast-gates பிரிப்பு இன்னும் ஓர் அமைப்புசார் இடைவெளியை விட்டுச் செல்கிறது.**
   `quality.yml` (PR→`release/**`) இப்போது code PR-களுக்காக typecheck, வேகமான deterministic
   test-கள் மற்றும் ஆலோசனை நிலையிலான production build ஆகியவற்றை இயக்குகிறது; ஆனால் இன்னும்
   `ci.yml`-இல் உள்ள முழுமையான release-PR பரப்பை (coverage ratchet-கள், package artifact,
   integration, E2E, SonarQube) இயக்குவதில்லை. இதற்கான காரணம் (வேகம்) நியாயமானது, ஆனால் merge
   நடைபெறும் இடத்திலேயே gate இருக்க வேண்டும் (shift-left). **நிலுவையிலுள்ள மிகப்பெரிய அமைப்புசார்
   திருத்தம்.**
2. **🟠 Gate பெருக்கம்/சோர்வு அபாயம்.** ~46 gate-கள் + 25 job-கள் என்பது மிகவும் அதிகம். Sonar
   தானே எச்சரிக்கிறது: அதிகமான நிபந்தனைகள் "gate சோர்வு" மற்றும் முன்னுரிமை விவாதங்களை
   ஏற்படுத்துகின்றன; இதனால் ஒரு gate புறக்கணிக்கப்படும் அபாயம் உள்ளது. கடுமையான gate-கள்
   lead-time-ஐ அதிகரிப்பதாக DORA எச்சரிக்கிறது. ஆலோசனை அடுக்குகள் மற்றும் absolute அல்லாத
   ratchet-கள் மூலம் இதைத் தணிக்கிறோம்; ஆனால் **ஒவ்வொரு gate-க்கும் காலமுறை ROI மதிப்பாய்வு**
   இல்லை (doc-sync-க்கான சில micro-gate-களை ஒருங்கிணைக்கலாம்).
3. **🟠 Mutation score இன்னும் ratchet அல்ல.** Coverage சூழ்ச்சிக்கு எதிரான மிகவும் வலுவான
   பாதுகாப்பு இன்னும் **ஆலோசனை** நிலையிலேயே உள்ளது. இது நிலுவையிலுள்ள மிக உயர்ந்த மதிப்புடைய
   உருப்படி (மேலும் ஏற்கனவே 90% உருவாக்கப்பட்டுள்ளது).
4. **🟡 தடுப்பவையாக இருக்க வேண்டிய ஆலோசனைகள் (சரியான வரம்புடன்).** உறையவைக்கப்பட்ட
   baseline-கள் இருந்தபோதிலும் `osv` (vulnCount) மற்றும் `oasdiff` ஆகியவை ஆலோசனை நிலையிலேயே
   உள்ளன. osv-ஐ ஆலோசனையாக வைத்திருப்பது பொருத்தமானதே (பழைய dependency-யில் ஒரு புதிய CVE,
   தொடர்பில்லாத PR-ஐத் தடுக்கக்கூடும்) — ஆனால் ஒரு நடுநிலை உள்ளது (Trivy-இல் செய்தது போல,
   CRITICAL+fixable மட்டும் தடுக்கலாம்). oasdiff ஆலோசனை நிலையில் இருப்பதால், contract-ஐ
   உடைக்கும் மாற்றம் கடந்து செல்லலாம்.
5. **🟡 Runtime பாதுகாப்பு இரவுநேரத்தில் மட்டுமே.** schemathesis/garak/promptfoo/chaos/k6
   இரவில் இயங்குகின்றன. இது சரியான முடிவு (மெதுவானவை, live server தேவை), ஆனால் ஒரு PR
   அறிமுகப்படுத்தும் injection-guard regression அடுத்த இரவு வரை கண்டறியப்படாமல் போகலாம்.
6. **🟡 `main`-இல் branch-protection முடக்கப்பட்டுள்ளது.** `BRANCH_LOCK_TOKEN`, _release_
   branch-களைப் பூட்டுகிறது; ஆனால் `main` பாதுகாப்பின்றி உள்ளது. Scorecard/DSOMM இதற்காக
   மதிப்பைக் குறைக்கின்றன. Owner நடவடிக்கை தேவை.
7. **🟡 CodeQL default-setup; semgrep முறைப்படுத்தப்படவில்லை.** default-setup செயல்படுகிறது
   (0 alert-கள்), ஆனால் commit செய்யப்பட்ட `codeql.yml` கூடுதல் கட்டுப்பாட்டை வழங்குகிறது;
   semgrep, repo-வில் version செய்யப்படாமல் வெளிப்புற cloud platform வழியாக இயங்குகிறது.

## பகுதி 3 — தரச் சோதனைச் சாவடிகளின் முழுமையான பட்டியல் (எங்கும் பயன்படுத்தக்கூடியது)

கீழே உள்ள 12 வகைகளும் மீண்டும் பயன்படுத்தக்கூடிய வடிவிலுள்ள "தர அமைப்பு" ஆகும். ஒவ்வொன்றும்
**நோக்கம்** (எதைப் பாதுகாக்க வேண்டும்), **நாங்கள் பயன்படுத்தும் கருவிகள்** மற்றும் எந்தவொரு தொழில்நுட்ப அடுக்கிலும் இதை மீளுருவாக்குவதற்கான **கருவி சார்பற்ற நிகர் முறையையும்**
பட்டியலிடுகிறது.

### 1. பாணி & வடிவமைப்பு (தீர்மானகரமானது, வேகமானது)

- **OmniRoute:** lint-staged வழியாக Prettier + ESLint (pre-commit), 2-இடைவெளிகள்/இரட்டை மேற்கோள்கள்/100 நெடுவரிசைகள்.
- **பொதுவானது:** தானாகத் திருத்தக்கூடிய ஒரு formatter + ஒரு linter; staged கோப்புகளில் pre-commit நேரத்தில் இயங்குதல்.

### 2. வகைகள்

- **OmniRoute:** `typecheck:core` (தடுக்கும்) + `typecheck:noimplicit:core` (ஆலோசனை வழங்கும்) + `type-coverage` ratchet 92.17% + ஒவ்வொரு கோப்பிற்குமான any-budget.
- **பொதுவானது:** CI-இல் கடுமையான typecheck + ratchet செய்யப்பட்ட type-coverage அளவீடு + ஒவ்வொரு கோப்பிற்குமான `any`/தப்புவழி வரம்பு.

### 3. சோதனைகள் (தீவிரம்)

- **OmniRoute:** ஒன்றுடன் ஒன்று மேற்பொருந்தாத 2 runners (Node native + vitest), 8 shards, ஒட்டுமொத்த coverage 60/60/60/60 + ratchet ~76% + **முக்கியமான modules-க்கு 8 தனித்தனி குறைந்தபட்ச வரம்புகள்** + இரவுநேர property tests + இரவுநேர **mutation testing**.
- **பொதுவானது:** test runner(கள்) + **முழுமையான** coverage குறைந்தபட்ச வரம்பு (பூஜ்ஜியத்தைத் தடுக்க) + coverage **ratchet** (பின்னடைவைத் தடுக்க) + **அதிக ஆபத்துள்ள code-க்கு தனித்தனி module குறைந்தபட்ச வரம்புகள்** (Goodhart விளைவைத் தடுக்க) + தூய logic-க்கான property-based சோதனைகள் + சோதனைத் தரத்தின் உண்மையான அளவீடாக இரவுநேர **mutation testing**.

### 4. சோதனைக் கொள்கை (முறைகேட்டைத் தடுக்க)

- **OmniRoute:** `pr-test-policy` (production code-க்கு ஒரு test தேவை), `check-test-masking` (பலவீனப்படுத்தப்பட்ட asserts-ஐத் தடுக்கிறது), `pr-evidence` (வெற்றிக் கூற்றுக்கு ஆதாரத் தொகுதி தேவை), `test-discovery` (ஒவ்வொரு test-உம் ஒரு runner-ஆல் சேகரிக்கப்படுகிறது).
- **பொதுவானது:** "புதிய code ⇒ புதிய test" வாயில் + நீக்கப்பட்ட assert/எப்போதும் உண்மையாகும் கூற்றைக் கண்டறியும் கருவி + ஆதாரத் தேவை (TDD அல்லது தொடர்ந்து செயல்படும் test) + globs-க்கு வெளியே எந்த test-உம் தனித்துவிடப்படவில்லை என்பதற்கான உத்தரவாதம்.

### 5. சிக்கல்தன்மை & code ஆரோக்கியம் (ratchets)

- **OmniRoute:** ESLint-warnings (3769↓), jscpd duplication (5.72%↓), cyclomatic+max-lines complexity (1800↓), cognitive complexity sonarjs (753↓), dead-code/unused-exports knip (339↓), ஒவ்வொரு கோப்பிற்குமான file-size (உறையவைக்கப்பட்டு, குறைக்க மட்டுமே அனுமதி), circular-deps (தனிப்பயன் Tarjan, தடுக்கும்).
- **பொதுவானது:** ஒவ்வொரு ஆரோக்கிய அளவீட்டையும் ratchet செய்யவும் (எச்சரிக்கைகள், நகலாக்கம், cyclomatic **மற்றும்** cognitive complexity, dead code, கோப்பு அளவு, import சுழற்சிகள்). திசை எப்போதும் "பின்னடைவு ஏற்படக்கூடாது".

### 6. நிலையான பாதுகாப்பு (SAST + ரகசியங்கள்)

- **OmniRoute:** CodeQL (ratchet எச்சரிக்கைகள் = 0), gitleaks (`[extend] useDefault=true` — மிக முக்கியம்!), SonarQube, தனிப்பயன் பாதுகாப்பு விதிகள் (public-creds, error-helper, route-guard-membership, route-validation).
- **பொதுவானது:** எச்சரிக்கை ratchet கொண்ட SAST (CodeQL/Sonar/semgrep) + **மரபுரிமையாகப் பெறப்பட்ட இயல்புநிலை விதித்தொகுப்பைக்** கொண்ட secrets scanner (இயல்புநிலையை மேலெழுதும் தனிப்பயன் config = கண்மூடித்தனம்) + திட்டத்திற்கே உரிய கடுமையான பாதுகாப்பு விதிகளுக்கான வாயில்கள்.

### 7. விநியோகச் சங்கிலி (சார்புகள்)

- **OmniRoute:** osv-scanner + npm-audit + Trivy + Dependabot (SCA), license-checker (SPDX அனுமதிப்பட்டியல்), lockfile-lint (HTTPS+sha512+registry), `check-deps` anti-slopsquatting (அனுமதிப்பட்டியல் + வயது ≥72h).
- **பொதுவானது:** பல-மூல SCA + உரிம அனுமதிப்பட்டியல் + lockfile ஒருமைப்பாட்டுச் சோதனை + வயது/typosquatting சோதனையுடன் கூடிய சார்பு அனுமதிப்பட்டியல் + தொகுப்பாக்கப்பட்ட update bot.

### 8. விநியோகச் சங்கிலி (build & release)

- **OmniRoute:** SBOM (CycloneDX + syft), SLSA provenance (`--provenance`), OpenSSF Scorecard (வாரந்தோறும்), workflow வலுப்படுத்தல் (zizmor: artipacked→`persist-credentials:false`, cache-poisoning, token-permissions).
- **பொதுவானது:** publish செய்யும்போது SBOM உருவாக்கவும் + கையொப்பமிடப்பட்ட provenance (SLSA L2+) + திட்டமிடப்பட்ட Scorecard + அனைத்து workflows-ஐயும் வலுப்படுத்தவும் (குறைந்தபட்சச் சலுகையுள்ள tokens, push செய்யாதவரின் checkout-இல் credentials-ஐச் சேமிக்காமை, SHA மூலம் நிலைநிறுத்தப்பட்ட actions).

### 9. ஒப்பந்தங்கள் & API

- **OmniRoute:** oasdiff (breaking-change OpenAPI), schemathesis (இரவுநேர contract fuzz), openapi-coverage (% ஆவணப்படுத்தப்பட்ட routes, ratchet 38.3%), openapi-security-tiers (spec மற்றும் route-guard ஒப்பீடு).
- **பொதுவானது:** breaking-change contract diff (oasdiff/buf) + spec-க்கு எதிரான property-based fuzz சோதனை (schemathesis) + ratchet செய்யப்பட்ட ஆவண coverage + spec↔code நிலைத்தன்மை.

### 10. ஆவணங்கள் & i18n (தேக்கத்தைத் தடுக்க)

- **OmniRoute:** docs-sync (பிரதிபலிக்கப்பட்ட versions), docs-counts-sync (ஆவணங்கள் மற்றும் code-இல் உள்ள எண்கள்), env-doc-sync, doc-links, fabricated-docs, cli-i18n, i18n-ui-coverage (`--threshold=65` + ratchet 80.1%).
- **பொதுவானது:** ஆவணங்களுக்கும் code-க்கும் இடையே versions/counts/env-vars-ஐ ஒத்திசைக்கவும் (நம்பிக்கை அல்ல, வாயில்) + உள் இணைப்புகளைச் சரிபார்க்கவும் + ratchet செய்யப்பட்ட i18n coverage.

### 11. புனைவைத் தடுப்பது / நிலைத்தன்மை (அரிதான வகை)

- **OmniRoute:** known-symbols (string dispatch ⇒ செயல்பாட்டிலுள்ள symbol), provider-consistency, fetch-targets (client fetch ⇒ உண்மையான route), docs-symbols, db-rules (கடுமையான விதிகள் #2/#5), migration-numbering.
- **பொதுவானது:** ஒவ்வொரு "நகலாக்கப்பட்ட உண்மை மூலத்திற்கும்" (registry, string dispatch, அடுக்குகளுக்கிடையேயான references), இரு பக்கங்களும் பொருந்துகின்றன என்பதை நிரூபிக்கும் ஒரு வாயில். typecheck/test கண்டறியாத தேக்கத்தை இது கண்டறிகிறது.

### 12. மீள்திறன் & துறை (தயாரிப்புக்கே உரியது)

- **OmniRoute:** chaos (தவறு-உட்செலுத்தல்), heap-growth (கசிவு), k6 (நீடித்த சுமை), promptfoo+garak (LLM red-team OWASP LLM Top 10), 3 மீள்திறன் விதிகள் (circuit-breaker/cooldown/lockout).
- **பொதுவானது:** **உங்கள்** துறையின் தோல்வி முறைகளைக் கண்டறிந்து, ஒவ்வொன்றுக்கும் ஒரு வாயிலை வைத்திருக்கவும் (அது இரவில் மட்டும் இயங்கினாலும் கூட). AI apps-க்கு: injection red-team. Distributed systems-க்கு: chaos + leak + soak.

## பகுதி 4 — எந்தத் திட்டத்திற்குமான பிரதியாக்கத் திட்டம்

தனித்தனியாக மதிப்பை வழங்கும் **கட்டங்களாக** உருவாக்குங்கள். 12 வகைகளையும் ஒரே நேரத்தில் முயற்சிக்காதீர்கள் —
அது பகுதி 2 எச்சரிக்கும் தடைச் சோர்வையே ஏற்படுத்தும். ஒவ்வொரு புதிய தடையும் **ஆலோசனை நிலையாக** அறிமுகமாகி,
நிலையானதும் **தடுக்கும் நிலைக்கு** மாறும்.

### மீண்டும் பயன்படுத்தக்கூடிய மையக்கூறு: "ராட்செட் தடையின் உடற்கூறியல்"

முழு அமைப்பும் இந்த 3-கோப்பு வடிவத்தைச் சுற்றியே இயங்குகிறது. முதலில் இதைப் பிரதியெடுங்கள்:

1. **`baseline.json`** — உறையவைக்கப்பட்ட அளவீட்டு மதிப்பு + `direction` (`up`/`down`) + `eps` (நிலையற்ற தோல்வித் தடுப்பு) + `tightenSlack` + `dedicatedGate`.
2. **`collect-metrics.<ext>`** — கருவியை இயக்கி, எண்ணைப் பிரித்தெடுத்து, `metrics.json`-இல் எழுதுகிறது.
3. **`check-ratchet.<ext>`** — `metrics.json`-ஐ `baseline.json`-உடன் ஒப்பிடுகிறது; `eps`-ஐத் தாண்டி பின்னடைவு ஏற்பட்டால் **மட்டுமே** `exit 1`; கருவி/உள்கட்டமைப்பு இல்லாதிருந்தால் `exit 0` (பாதிப்பில்லா தவிர்ப்பு); `--require-tighten` உடன், அடிப்படையைப் புதுப்பிக்காமலேயே அது **மேம்பட்டிருந்தால்** `exit 1` (மேம்பாட்டை நிலைநிறுத்துகிறது).

இது அமைந்ததும், **ஒவ்வொரு** புதிய அளவீடும் (சோதனை உள்ளடக்கம், சிக்கல்தன்மை, எச்சரிக்கைகள், SAST விழிப்பூட்டல்கள், தொகுப்பளவு, மாற்றச் சோதனை மதிப்பெண்…) அடிப்படையில் ஒரு வரி மட்டுமே.

### கட்டம் 0 — அடித்தளம் (வாரம் 1)

CI உள்ளது; வடிவமைப்பி + lint கருவி + வகைச் சரிபார்ப்பு + 1 சோதனை இயக்கி + **முழுமையான** சோதனை உள்ளடக்கக் குறைந்தபட்ச வரம்பு
(எ.கா., 60%). முன்-commit விரைவான, தானாகச் சரிசெய்யக்கூடிய சோதனைகளை இயக்குகிறது. _விளைவு: எந்த PR-உம் அடிப்படைகளை உடைக்காது._

### கட்டம் 1 — ராட்செட் இயந்திரம் (வாரம் 2) — **அனைத்திற்குமான அடித்தளம்**

மேலுள்ள 3 கோப்புகளையும் செயல்படுத்துங்கள். பின்வருவனவற்றுக்கான அடிப்படைகளை உறையவையுங்கள்: எச்சரிக்கைகள், சோதனை உள்ளடக்கம், சிக்கல்தன்மை, நகலாக்கம்,
பயன்பாடற்ற குறியீடு, கோப்பு அளவு. _விளைவு: இங்கிருந்து குறியீட்டுத் தளம் மேம்பட மட்டுமே முடியும்._

### கட்டம் 2 — நிலையான பகுப்பாய்வின் ஆழம் (வாரம் 3)

விழிப்பூட்டல் ராட்செட்டுடன் SAST (CodeQL/Sonar/semgrep); ரகசியத் தகவல் வருடி (**இயல்புநிலை விதித்தொகுப்பை மரபுரிமையாகப் பெறுங்கள்**);
SCA (osv/Dependabot) + உரிம அனுமதிப்பட்டியல் + lockfile-lint. _விளைவு: அறியப்பட்ட பாதிப்புகளும்
கசிந்த ரகசியத் தகவல்களும் அனுமதிக்கப்படாது._

### கட்டம் 3 — உருவாக்க விநியோகச் சங்கிலி (வாரம் 4)

வெளியிடும்போது SBOM + கையொப்பமிட்ட மூலச்சான்று (SLSA L2) + திட்டமிட்ட Scorecard + பணிப்பாய்வு வலுப்படுத்தல்
(zizmor: குறைந்தபட்ச டோக்கன்கள், நிலைத்த நற்சான்றுகள் இல்லை, பதிப்பு நிலைப்படுத்தப்பட்ட actions). _விளைவு: கண்டறியக்கூடிய மற்றும்
சேதப்படுத்த முடியாத வெளியீடுகள்._

### கட்டம் 4 — சோதனைத் தீவிரம் (வாரம் 5–6)

பயனுள்ளதாக இருந்தால் 2-வது இயக்கி; **முக்கிய தொகுதிகளுக்குத் தொகுதி வாரியான சோதனை உள்ளடக்கக் குறைந்தபட்ச வரம்புகள்** (Goodhart எதிர்ப்பு);
தூய தர்க்கத்திற்குப் பண்பு-அடிப்படையிலான சோதனை; **ஒவ்வொரு இரவும் மாற்றச் சோதனை** → முதல் மதிப்பெண் வந்ததும்,
`mutationScore`-ஐ ஒரு ராட்செட்டாக மாற்றுங்கள். _விளைவு: சோதனை உள்ளடக்கம் வெறும் பகட்டான அளவீடாக இருப்பது நிற்கிறது; சோதனைகள் பிழைகளைப் பிடிக்கின்றன என்பது நிரூபிக்கப்படுகிறது._

### கட்டம் 5 — ஒப்பந்தம் மற்றும் இயக்கநிலை (வாரம் 7)

பொது API இருந்தால்: oasdiff (முறிக்கும் மாற்றம், **தடுக்கும்**) + schemathesis (ஒவ்வொரு இரவும் fuzz சோதனை).
களத்திற்குப் பொருத்தமாக ஒவ்வொரு இரவும் DAST/சிவப்பு-அணி சோதனை. _விளைவு: ஒப்பந்தங்கள் அமைதியாக முறிவதில்லை._

### கட்டம் 6 — புனைவைத் தடுப்பது மற்றும் களம் (வாரம் 8)

திட்டத்தில் உள்ள ஒவ்வொரு "நகலாக்கப்பட்ட உண்மை"க்கும் ஒரு நிலைத்தன்மைத் தடை. களம் சார்ந்த தோல்வி-முறைத்
தடைகள் (AI-க்கு: உட்செலுத்தல் சிவப்பு-அணி சோதனை). _விளைவு: கட்டமைப்புச் சிதைவுக்கும் களம் சார்ந்த தோல்விகளுக்கும் பாதுகாப்பு வலை உள்ளது._

### கட்டம் 7 — ஆளுகை (தொடர்ச்சியாக)

- ஒவ்வொரு புதிய தடைக்கும் ஆலோசனை→தடுப்பு சுழற்சி.
- `stale-allowlist`: ஒவ்வொரு விலக்கலுக்கும் ஒரு நியாயப்படுத்தல் + சிக்கல் இருக்க வேண்டும்; காலாவதியான விலக்கல் கண்டறியப்படும்.
- `evidence-gate`: PR-இல் வெற்றிக் கூற்றுக்கு ஆதாரம் தேவை (சோதனை அல்லது நிகழ்நிலைச் சோதனை).
- **ஒவ்வொரு தடைக்கும் காலாண்டு ROI மதிப்பாய்வு** (பலன் தராதவற்றை நீக்குங்கள்/நிதியைக் குறையுங்கள் — இது சோர்வை எதிர்க்கிறது).
- உங்கள் திட்டத்தின் கடுமையான விதிகளைச் செயல்படுத்தக்கூடிய தடைகளாக உயர்த்துங்கள்.

### அனைத்துக் கட்டங்களுக்கும் பொதுவான கொள்கைகள் (பேரம் பேச முடியாதவை)

- **ராட்செட், முழுமையான மதிப்பு அல்ல.** நிலையான எண்ணை அல்ல, _பின்னடைவு ஏற்படாமையைத்_ தடை மூலம் உறுதிப்படுத்துங்கள் (பூஜ்ஜியத்தைத் தடுக்கும் குறைந்தபட்ச வரம்புகள் தவிர).
- **முழுமையான குறைந்தபட்ச வரம்பு + ராட்செட் இரண்டும் ஒன்றாக.** குறைந்தபட்ச வரம்பு சரிவைத் தடுக்கிறது; ராட்செட் மெதுவான அரிப்பைத் தடுக்கிறது.
- **வடிவமைப்பிலேயே Goodhart எதிர்ப்பு.** ஒவ்வொரு இலக்கு அளவீட்டுக்கும் ஓர் எதிர்சமநிலை தேவை (சோதனை உள்ளடக்கம் ⇒ மாற்றச் சோதனை + மறைத்தல் எதிர்ப்பு; கடினமான குறியீட்டைச் சோதிக்கக் கட்டாயப்படுத்தத் தொகுதி வாரியான குறைந்தபட்ச வரம்புகள்).
- **பாதிப்பில்லா தவிர்ப்பு.** இல்லாத உள்கட்டமைப்பு ஒருபோதும் தடுக்காது; உண்மையான பின்னடைவு மட்டுமே தடுக்கும்.
- **செலவுமிக்க அளவீடுகளுக்கு `dedicatedGate`.** வெளிப்புற executable தேவைப்படும் அளவீடுகள், ஒத்திசைவாக இயங்கும் மைய ராட்செட்டுக்கு வெளியே, தமக்கெனத் தனி script-ஐக் கொண்டிருக்க வேண்டும் (தவிர்ப்பு வசதியுடன்).
- **இணைப்பு நிகழும் இடத்திலேயே தடை அமைக்கவும்.** விரைவுத் தடைக்கும் உண்மையான இணைப்புக்கும் இடையே இடைவெளியை விட்டுவிடாதீர்கள் (fast-gates பிரிப்பிலிருந்து கிடைத்த பாடம்).
- **நன்கு தேர்ந்தெடுக்கப்பட்ட சில தடுப்புத் தடைகள்.** Sonar/DORA: மிக அதிகமான நிபந்தனைகள் = சோர்வு. தடுப்புத் தடைகளின் சுவரைவிட ஆலோசனை + ராட்செட்டை விரும்புங்கள்.

## பகுதி 5 — பரிந்துரைக்கப்பட்ட மேம்பாடுகள் (முன்னுரிமைப்படுத்தப்பட்டவை, இணக்கமானவை)

**P0 — மிக உயர்ந்த ROI, ஏறக்குறைய தயாராக உள்ளது**

1. **Mutation score ratchet** (முதல் nightly Stryker மதிப்புகளை உருவாக்கிய பிறகு). coverage-Goodhart-க்கு எதிரான முக்கியத் தீர்வு; ~90% முடிந்துள்ளது.
2. **மீதமுள்ள fast-gates இடைவெளியை மூடுதல்** — `quality.yml` production build-ஐ அதன்
   advisory வாரத்திற்குப் பிறகு உயர்த்தி, deterministic release-PR-only சோதனைகளை PR→release பாதைக்கு தொடர்ந்து நகர்த்தவும்.
3. **`main`-இல் Branch-protection** (உரிமையாளர் அமைப்பு) — Scorecard-ஐ உயர்த்தி, DSOMM இடைவெளியை மூடுகிறது.

**P1 — மதிப்புமிக்கது** 4. **osv/oasdiff → சரியான வரம்புடன் blocking** — osv-க்கு CRITICAL+fixable மட்டும் (Trivy போன்ற இரண்டு-படி முறை); breaking-changes-ஐ oasdiff தடுக்க வேண்டும். 5. **`require-tighten` → blocking** (சுழற்சியின் முடிவில்) — அளவீட்டு மேம்பாடுகளை நிலைநிறுத்துகிறது. 6. **ஒவ்வொரு gate-க்கும் ROI/நேர மதிப்பாய்வு** `ci-summary`-இல் — மெதுவான/குறைந்த மதிப்புள்ள gates-ஐக் கண்டறிந்து நீக்கவும்.

**P2 — குறைந்து வரும் பலன்கள்** 7. **SLSA L3** — L2-இலிருந்து மேலே செல்ல விரும்பினால் hermetic/reproducible builder (GitHub SLSA generator). 8. **Commit செய்யப்பட்ட CodeQL config + versioned semgrep** — அதிக கட்டுப்பாடு/reproducibility. 9. **ஒவ்வொரு PR-க்கும் DAST smoke** — அதிக ஆபத்துள்ள endpoints-இல் schemathesis/promptfoo-வின் விரைவான துணைத்தொகுப்பு (nightly மட்டும் அல்ல). 10. **Flakiness dashboard + DORA அளவீடுகள்** — gates வேகத்தைக் குறைக்கவில்லை என்பதை உறுதிசெய்யவும்.

## பகுதி 6 — உறுதியான release பாடங்கள் (Phase 9-இல் சேர்க்க வேண்டிய gates)

> release நிறைவு செயல்முறைகளில் ஒரு gate **இல்லாமல் இருந்ததால்** நிகழ்ந்த உண்மையான சம்பவங்களை,
> உறுதியான ஆதாரங்களுடனும் முன்மொழியப்பட்ட gate-உடனும் இந்தப் பகுதி பதிவுசெய்கிறது. ஒவ்வொரு உருப்படியும் பகுதி 5-க்கான வேட்பாளராகும்.

### பாடம் v3.8.27 (2026-06-17) — "fast-gates இடைவெளி" deterministic regressions-ஐ release நாளை அடைய அனுமதிக்கிறது

**என்ன நடந்தது.** v3.8.27 `/generate-release` செயலின்போது, ஒருங்கிணைந்த சுழற்சியில் முழு `ci.yml` matrix முதன்முறையாக இயக்கப்பட்டது
release PR-இல்தான் (`release/v3.8.27` → `main`).
விளைவு: ஒரே நேரத்தில் 12 தோல்விகள் — **3 deterministic tests** + ~9 flakes/env. எதுவும் நேரடி product regression அல்ல; ஆனால்
சுழற்சி PR-கள் **Fast QG (`quality.yml`)** வழியாக `release/**`-க்குள் நுழைவதால் அனைத்தும் கவனிக்கப்படாமல் போயின.
அது முழு unit suite-ஐயோ, `pr-test-policy` (test-masking)-ஐயோ, முழு integration suite-ஐயோ அல்லது schema parity checking-ஐயோ இயக்காது. அந்த 3 deterministic தோல்விகள்:

1. **UI மாற்றத்தால் காலாவதியான test** — `permissions modal switch buttons declare button type`:
   #4034 ஒரு 4-வது switch-ஐச் சேர்த்தது (a11y `type="button"` பராமரிக்கப்பட்டது); test-இன் `=== 3` எண்ணிக்கை
   காலாவதியானது. #4034 PR-இல் static analysis இதைப் பிடித்திருக்க வேண்டும்.
2. **Packaging மாற்றத்தால் காலாவதியான test** — `findMissingArtifactPaths ... root runtime files`:
   `dist/http-method-guard.cjs` ஒரு முறையான required-path ஆனது; test-இன் எதிர்பார்க்கப்பட்ட பட்டியல்
   காலாவதியானது.
3. **தகவல் இழப்புள்ள modularization விலகல் (மிகவும் தீவிரமானது)** — `settings schemas accept ... unprefixed
toggle`: **modularized** `updateSettingsSchema` (`schemas/settings.ts`, #3988-ஆல் உருவாக்கப்பட்டது)
   canonical ஒன்றிலிருந்து (`settingsSchemas.ts`) விலகியது: **45 fields vs 85 — 40 நீக்கப்பட்டன + 6 விலகின (qdrant\*)**. அது
   **dead-code** ஆக இருந்தது (runtime canonical ஒன்றைப் பயன்படுத்துகிறது), எனவே நேரடி தாக்கம் இல்லை; ஆனால் கையால் எழுதப்பட்ட parity
   test மட்டுமே இதைக் கண்டுபிடித்தது. #4030, #3988/#3993-இலிருந்து இதேபோன்ற 16 நீக்கங்களை மீட்டெடுத்தது; ஆனால் இது தப்பிவிட்டது.

**முன்மொழியப்பட்ட gates (Phase 9):**

- **G1 — fast-gates இடைவெளியை உண்மையாக மூடுதல் (P0 #2-ஐ விரிவாக்குகிறது).** `quality.yml`-இல் (PR→`release/**`),
  typecheck + impacted tests-ஐத் தாண்டி, **`pr-test-policy` (test-masking) + முழு deterministic
  unit suite**-ஐ இயக்கவும் (அல்லது குறைந்தபட்சம் வேகமானதும் flakiness இல்லாததுமான static/parity files-ஐ இயக்கவும்).
  இதன் மூலம் காலாவதியான tests மற்றும் assert நீக்கம் ஆகியவை அவற்றை அறிமுகப்படுத்தும் PR-இலேயே கண்டறியப்படும் — release
  நாளில் அல்ல. integration/e2e-ஐத் தவிர்க்கவும் (மெதுவானது/flaky); ஆனால் deterministic layer
  PR→main-இல் மட்டும் இருக்கவே **கூடாது**.
- **G2 — Modularization parity gate (புதியது, தற்போது உள்ளடக்கப்படவில்லை).** ஒரு modularized barrel (`src/shared/validation/schemas/*`, `providerRegistry`
  modules போன்றவை) மூலம் மீண்டும் export செய்யப்படும் ஒவ்வொரு symbol-க்கும், அதன் **shape**-ஐ (`z.object` keys, registry entries) canonical
  source-உடன் ஒப்பிட்டு, **விலகல் ஏற்பட்டால் தோல்வியடையும்** (நீக்கப்பட்ட/கூடுதல் field) ஒரு சோதனை.
  #3988-இல் ஏற்பட்ட 40-field நீக்கத்தை அதே PR-இலேயே இது கண்டறிந்திருக்கும். கையால் எழுதப்பட்ட parity tests-ஐ இது பொதுமைப்படுத்துகிறது
  (யாராவது அவற்றை எழுத நினைவில் வைத்திருந்த இடங்களில் மட்டுமே அவை தற்போது உள்ளன). செலவு குறைவு: இரண்டையும் import செய்து `Object.keys(shape)`-ஐ ஒப்பிடுகிறது.
- **G3 — Deterministic flake triage (ஆதரவு).** LiveWS-startup மற்றும் integration-combo/breaker
  tests, logic காரணமாக அல்லாமல் CI-இல் server timeout/cascade (env) காரணமாகத் தோல்வியடைகின்றன. release-PR-இன் சிவப்பு நிலை,
  நடுவே உள்ள deterministic regressions-ஐ மறைக்கும் இரைச்சலாக இல்லாமல் **உண்மையான signals மட்டும்** கொண்டிருக்குமாறு, இவற்றை
  `known-flaky` (issue-உடன் quarantine செய்யப்பட்டவை) எனக் குறிக்கவும்.

**கொள்கை:** _merge நிகழும் இடத்திலேயே gate இயங்க வேண்டும்_ ("Cross-cutting principles"-இல் ஏற்கெனவே உள்ளது). இந்த
v3.8.27 சம்பவம், இது lint/typecheck-க்கு மட்டுமல்லாமல் **deterministic test layer**-க்கும் பொருந்தும் என்பதைக் காட்டுகிறது —
இல்லையெனில் காலாவதியான tests + தகவல் இழப்புள்ள modularization ஆகியவற்றின் தொழில்நுட்பக் கடன் PR→main-இல் மட்டுமே, தொகுப்பாக,
மிக மோசமான தருணத்தில் வெளிப்படும்.
