## npm Trusted Publishing (v3.8.51 முதல் இயல்புநிலை) — கோரிக்கையின்போது staged, மாற்றுவழியாக direct

`npm-publish.yml`, இயல்பாக **npm Trusted Publishing (OIDC)** மூலம் வெளியிடுகிறது:
`stage-npm` job (github-hosted), அந்த இயக்கத்திற்காக GitHub-இன் id-token-ஐக் குறுகிய கால npm
credential-ஆக மாற்றுகிறது — repository secrets-இல் நீண்டகால npm token இல்லை, 2FA prompt இல்லை, provenance இணைக்கப்படுகிறது.
2FA-ஐத் தவிர்க்கும் tokens படிப்படியாக நிறுத்தப்படுவதால், npm தற்போது அனுமதிக்கும் bypass இதுவே;
WS1.3 உத்தரவாதத்தைத் தக்கவைத்துக்கொண்டே, v3.8.48 வரை திட்டத்தில் இருந்த முழுமையான
தானியக்கச் செயல்முறையை இது மீட்டெடுக்கிறது (கசிந்த token மட்டும் வெளியிட முடியாது — ஏனெனில் token எதுவும் இல்லை).

**ஒருமுறை மட்டும் செய்ய வேண்டிய அமைப்பு (உரிமையாளர்):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none). இது உருவாக்கப்படும் வரை, தானியக்கப் படி `ENEEDAUTH` உடன் தோல்வியடையும்:
`publish_mode=staged` (கீழே) அல்லது `direct` உடன் மீண்டும் dispatch செய்யவும்.

### Staged வெளியீடு (கோரிக்கையின்போது — `publish_mode=staged`)

npm-publish workflow இனி நேரடியாக வெளியிடாது: packed tarball-ஐ
(`check:pack-boot`) boot செய்துவிட்டு, பின்னர் `npm stage publish`-ஐ இயக்கும் — அதே bytes registry-இல்
நிறுத்திவைக்கப்படும்; உரிமையாளர் அங்கீகரிக்கும் வரை அவற்றை **நிறுவ முடியாது**. மனித 2FA சரிபார்ப்பு,
ஆதாரத்திற்கு முன் அல்லாமல் அதற்குப் பிறகு நகர்த்தப்பட்டுள்ளது.

**Workflow பச்சை நிலையை அடைந்த பிறகு உரிமையாளருக்கான செயல்முறை:**

1. `npm stage list omniroute` — stage id-ஐக் கண்டறியவும் (workflow சுருக்கத்திலும் அச்சிடப்படும்).
2. Staged bytes-ஐச் சரிபார்க்கவும் (பரிந்துரைக்கப்படுகிறது): `npm stage download <id>`, பின்னர் பதிவிறக்கப்பட்ட
   tarball-ஐ ஒரு தற்காலிக prefix-இல் நிறுவி boot செய்யவும் (`npm run check:pack-boot`, அதே
   pack→install→boot முடிவை CI-இல் தானியக்கமாக்குகிறது).
3. `npm stage approve <id>` — 2FA prompt-தான் வெளியீடு. `npm stage reject <id>` அதை நிராகரிக்கும்.
4. வெளியீட்டுக்குப் பிந்தைய பாதுகாப்பு: வெளியீட்டுக்குப் பிந்தைய verifier (v3.8.49 திட்டத்தின் WS1.4),
   வெளியிடப்பட்ட பதிப்பைப் பொது registry-இலிருந்து சுத்தமான container ஒன்றில் நிறுவி boot செய்கிறது.

**அவசரகால மாற்றுவழி:** `publish_mode=direct` உடன் `workflow_dispatch`, பழைய உடனடி
`npm publish` முறையை மீட்டெடுக்கும் (staging-இலேயே கோளாறு ஏற்பட்டால் மட்டும் பயன்படுத்தவும்; காரணத்தைப் பதிவு செய்யவும்).

**ஒருமுறை மட்டும் செய்ய வேண்டிய பாதுகாப்பு வலுப்படுத்தல் (உரிமையாளர், npmjs.com):**
`omniroute`-க்கான Trusted Publisher-ஐ stage-only பயன்முறையில் உள்ளமைக்கவும்; இதனால் கசிந்த நீண்டகால token
எங்கிருந்தும் நேரடியாக `npm publish` செய்ய முடியாது — CI-ஆல் stage செய்ய மட்டுமே முடியும்;
உரிமையாளரின் 2FA மட்டுமே வெளியீட்டைச் செய்கிறது.

**சிதைந்த artifact-க்கான நடைமுறை வழிகாட்டி (மாற்றமில்லை):** இயல்புநிலை உடனடி நடவடிக்கையாக
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"`-ஐப் பயன்படுத்தவும் (சில நிமிடங்கள், மீளக்கூடியது);
`npm unpublish`-ஐ 72h/no-dependents காலவரம்பிற்குள் மட்டும் பயன்படுத்தவும், ஒருபோதும் முதல் நடவடிக்கையாகப் பயன்படுத்த வேண்டாம்.
Docker: ஒரு version tag-ஐ ஒருபோதும் மீண்டும் எழுத வேண்டாம் — rollback என்பது `latest`-ஐக் கடைசியாகச் சரியாக இருந்த digest-க்குத் திருப்புவதாகும்.

**Docker Hub `latest` (ஒவ்வொரு நிலையான SemVer வெளியீட்டிலும் கட்டாயம்):**
`docker-publish` workflow, `X.Y.Z` மற்றும் `should-promote-latest.sh` இது மிக உயர்ந்த நிலையான SemVer என
ஒப்புக்கொள்ளும்போது `:latest` ஆகிய **இரண்டிற்கும்** **ஒரே digest** உடன் tag செய்ய வேண்டும்.
Job முடிந்த பிறகு: Hub `latest` digest புதிய SemVer digest-க்கு சமமாகவும்,
`last_updated` முன்னேறியதாகவும் இருக்க வேண்டும். Git-இல் மட்டுமே உள்ள திருத்தங்களைப் பற்றி release notes
குறிப்பிடும்போது, பழைய build ஒன்றில் `:latest`-ஐ விட்டுவிட வேண்டாம்.
Compose quickstarts `:latest`-ஐப் பயன்படுத்துகின்றன; GitOps தொடர்ந்து `X.Y.Z`-ஐ pin செய்ய வேண்டும்.
[Docker வெளியீட்டு channels](../guides/DOCKER_GUIDE.md#release-channels) மற்றும் #10317-ஐப் பார்க்கவும்.

## ஹாட்ஃபிக்ஸ் விரைவுப் பாதை (`hotfix` லேபிள்)

`hotfix` என லேபிளிடப்பட்ட PR, கனமான CI மேட்ரிக்ஸை (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) தவிர்த்து, விரைவான, அதிகத் தெளிவான கேட்களைத் தக்கவைக்கிறது: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
மற்றும் tarball boot-smoke (`check:pack-boot`). இலக்கு: ~33 நிமிடங்களுக்குப் பதிலாக ≤15 நிமிடங்களில் வெற்றி நிலை.

**நுழைவுக் கொள்கை — நான்கும் கட்டாயம் (Chromium/VS Code/Node அவசரப் பாதைகளை அடிப்படையாகக் கொண்டது):**

1. **தீவிரம்**: production செயலிழந்துள்ளது — வெளியிடப்பட்ட artifact தொடங்கும்போது செயலிழக்கிறது / ஒரு
   பாதுகாப்புத் திருத்தம் / வெளியீட்டின் ஒவ்வொரு பயனரும் பாதிக்கப்படுகின்றனர். "முக்கியமானது" என்பது "செயலிழந்தது" அல்ல.
2. **அதிகாரம்**: repository உரிமையாளர் மட்டுமே `hotfix` லேபிளைப் பயன்படுத்துவார். அந்த லேபிளே
   ஒப்புதல் — campaign PR-இல் ஒருபோதும் சுயமாகப் பயன்படுத்த வேண்டாம்.
3. **ஆதாரம்**: PR விளக்கத்தில், முன்பு முழுமையாக வெற்றிபெற்ற கனமான run-க்கான இணைப்பும் (தவிர்க்கப்பட்ட jobs
   மீண்டும் சரிபார்த்திருக்கும் suite), திருத்தத்துக்கான முதலில் தோல்வியடைந்து பின்னர் வெற்றிபெற்ற test-உம் இருக்க வேண்டும்.
4. **வரம்பு**: cherry-pick மட்டும் — குறைந்தபட்சத் திருத்தம்; refactors அல்லது தொடர்பற்ற மாற்றங்கள் கூடாது.

தவிர்க்கப்பட்ட coverage/ratchet பரப்பு, release branch-இன் அடுத்த முழு run-இல்
மீண்டும் சரிபார்க்கப்படும் (தொடர்ச்சியான release-green) — இந்தப் பாதை காத்திருப்பை மட்டுமே தவிர்க்கிறது, சரிபார்ப்பை ஒருபோதும் தவிர்ப்பதில்லை.
Tests மட்டும் கொண்ட diffs (`tests/`-இன் கீழுள்ள அனைத்து files; `tests/e2e/`-இன் கீழ் எதுவுமில்லை) எந்த லேபிளும் இல்லாமல் E2E
மேட்ரிக்ஸைத் தானாகவே தவிர்க்கும்.

### Hooks (Husky மூலம் சரிபார்க்கப்பட்டது)

Husky hooks `.husky/`-இல் உள்ளன; git செயல்பாடுகளின்போது தானாக இயங்கும்.

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** விரைவான, தீர்மானகரமான gates — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (2026-06-13 அன்று செயல்படுத்தப்பட்டது). `test:unit` வேண்டுமென்றே விலக்கப்பட்டுள்ளது (மெதுவானது; CI `test-unit` job மூலம் கையாளப்படுகிறது).
  - release branches-ஐ push செய்வதற்கு முன் `npm run test:unit`-ஐ கைமுறையாக இயக்கவும்.

ஒரு hook தோல்வியடைந்தால்: அடிப்படைச் சிக்கலைச் சரிசெய்யவும்; `--no-verify` மூலம் அதைத் தவிர்க்க வேண்டாம்.

### Build அமைப்பு

களஞ்சியம் மூன்று தனித்துவமான வெளியீட்டு அடைவுகளைப் பயன்படுத்துகிறது — அவற்றை ஒருபோதும் குழப்ப வேண்டாம்:

| அடைவு     | நோக்கம்                                                                         | கண்காணிக்கப்படுகிறதா? |
| --------- | ------------------------------------------------------------------------------- | --------------------- |
| `src/`    | பயன்பாட்டு மூலக்குறியீடு (TypeScript / TSX)                                     | ஆம்                   |
| `.build/` | Build இடைநிலைகள் — `next build` வெளியீடு (`distDir`)                            | இல்லை (gitignored)    |
| `dist/`   | விநியோகிக்கக்கூடிய npm bundle — `assembleStandalone` மூலம் ஒருங்கிணைக்கப்பட்டது | இல்லை (gitignored)    |

> **இயக்குநர் குறிப்பு:** தொலைநிலை VPS image அடைவு தொடர்ந்து `/usr/lib/node_modules/omniroute/app/` ஆகவே உள்ளது.
> **களஞ்சியத்திற்குள் உள்ள** build வெளியீடு மட்டுமே நகர்த்தப்பட்டது (`app/` → `dist/`). Deploy skills,
> `dist/` உள்ளடக்கங்களைத் தொலைநிலை `app/` அடைவிற்குள் rsync செய்கின்றன — VPS பாதையில் எந்த மாற்றமும் தேவையில்லை.

**ஒற்றை-build ஓட்டம்:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Deploy செய்வதற்கு `npm run build`-ஐ இயக்கிவிட்டு, அதைத் தொடர்ந்து தனியாக `npm run build:cli`-ஐ இயக்க வேண்டாம் — ஒரே கட்டளையில் சுத்தமான மறுகட்டமைப்பு + sentinel-ஐச் செய்யும்
`npm run build:release`-ஐப் பயன்படுத்தவும்.

trigger-களும் `if:` நிபந்தனைகளும் true ஆகின்றன (மேலும் எவை repository variable ஒன்றால் இன்னும் தடுக்கப்பட்டுள்ளன அல்லது

`nightly` காலி) மற்றும் rollback. Exit `0` = `RESULT: READY`, `1` = தடுக்கும் முன்நிபந்தனை
தோல்வியடைந்தது (`✗`), `2` = பயன்பாட்டுப் பிழை. `--advisory <id,...>` ஒரு சரிபார்ப்பை மறைக்காமல்

### PR முன்னோட்ட artifact (ஒருமுறை build செய்து, அதே bytes-ஐ முன்னேற்றவும்)

`.github/workflows/preview-artifact.yml` ஒரு PR head-இலிருந்து ஒரே ஒரு production tarball-ஐ build செய்து,
அதே build-ஐச் சரிபார்க்கிறது (#8084 பகுதி (a)). அதே repository-யிலுள்ள PR-கள் மட்டும்; எதுவும் publish செய்யப்படாது.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # அல்லது `preview-artifact` label-ஐச் சேர்க்கவும்
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # முன்னோட்ட நிறுவல்
```

இந்த run, `npm ci`, `npm run build:release`, `npm run check:pack-artifact` ஆகியவற்றைச் செய்து, tarball-ஐ pack செய்து,
`npm run check:pack-boot`-ஐ (போலியான secrets, தற்காலிக data dir) இயக்கி, மீண்டும் pack செய்து,
digest ஒரே மாதிரியாக இல்லாவிட்டால் தோல்வியடைகிறது; பின்னர் `artifact-identity.json`-ஐ (head SHA, base
SHA, lockfile hash, platform, arch, node ABI, bundler, build policy —
`scripts/release/artifact-identity.mjs`) பதிவு செய்து, தனி job ஒன்றில் tarball-ஐ attest செய்கிறது. முன்னோட்டத்தை
முன்னேற்றுவது என்பது அந்த tarball-ஐ நிறுவுவதாகும்: மூலத்திலிருந்து ஒருபோதும் மீண்டும் build செய்ய வேண்டாம்.

### பிரிப்பு (3.9.0, GO-க்குப் பிறகு)

1. GO, [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md)-இல் பதிவு செய்யப்பட்டுள்ளது.

3. உலர் இயக்கம் அச்சிடும் command-களைப் பயன்படுத்தி `origin`-இல் branch-களை கைமுறையாக உருவாக்கவும் —
   script, `origin`-க்கு push செய்ய மறுக்கும். மதிப்பாய்வு செய்யப்பட்ட develop commit-ஐ மீண்டும் பயன்படுத்த,
   முதலில் உங்கள் fork-க்கு எதிராக 3.9.0 முனையில் `--execute` ஒத்திகையை இயக்கவும்; அது இரண்டு SHA-களையும் அச்சிடும்,
   மேலும் அதே commit-களை push செய்யலாம்:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. முதல் PR இணைக்கப்படுவதற்கு முன் `stable/v3` மற்றும் `develop`-ஐப் பாதுகாக்கவும் (ruleset-கள் + merge queue).
5. branch இருப்பின் அடிப்படையில் செயலற்ற workflow-கள் இயங்கத் தொடங்குகின்றன: `forward-port.yml` (`stable/v3`-க்கு
   push), `validate-stable-pr.yml` (`stable/v3`-க்கான PR-கள்) மற்றும் `nightly-v4-build.yml`
   (`develop`-ஐ build செய்கிறது). நேரடி பயன்பாட்டுக்கு முன், `secrets.FORWARD_PORT_TOKEN` repository secret-ஐ அமைக்கவும் (இதனால்
   forward-port PR-களில் CI இயங்கும்); உரிமையாளர் repository variable ஆன `vars.NIGHTLY_PUBLISH`-ஐ
   `true` என அமைத்து, npm Trusted Publishing `nightly-v4-build.yml`-ஐ ஏற்கும் வரை nightly publishing
   முடக்கப்பட்டே இருக்கும். சேனல் தீர்மானம் `scripts/release/dist-tag.mjs` ஆகும்; `npm-publish.yml`
   பயன்படுத்தும் அதே resolver இதுவாகும்.
6. சேனல்களைச் சரிபார்க்கவும்: `npm view omniroute dist-tags --json`, `latest` = 3.9.0 என்றும், v4 publish ஆகும் வரை
   `next` / `nightly` இல்லை என்றும் காட்டும்.
7. தேவைப்பட்டால் rollback செய்யவும்: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   மற்றும் `npm dist-tag add omniroute@3.8.59 latest`.

## முந்தைய நிலைக்குத் திரும்புதல்

வெளியீட்டில் கடுமையான சிக்கல் இருந்தால்:

1. `gh release edit vX.Y.Z --prerelease` (சமீபத்திய வெளியீடு அல்ல எனக் குறிக்கும்)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (பயனர்கள் இன்னும் ஏற்றுக்கொள்ளவில்லை என்றால் மட்டும்)
3. அல்லது: `release/vX.Y.0`-இல் hotfix → patch வெளியீடு `vX.Y.(Z+1)`
4. GitHub Discussions மற்றும் Discord-இல் உடனடியாகத் தெரிவிக்கவும்

## கட்டாய விதிகள்

- `main`-க்கு ஒருபோதும் நேரடியாக commit செய்ய வேண்டாம்
- `main` அல்லது `release/*` கிளைகளுக்கு `git push --force`-ஐ ஒருபோதும் பயன்படுத்த வேண்டாம்
- Husky hooks-ஐ (`--no-verify`) ஒருபோதும் தவிர்க்க வேண்டாம்
- secrets, credentials அல்லது `.env` கோப்புகளை ஒருபோதும் commit செய்ய வேண்டாம்
- Coverage ≥60/60/60/60 (statements/lines/functions/branches) ஆகத் தொடர்ந்து இருக்க வேண்டும்
- `src/`, `open-sse/`, `electron/` அல்லது `bin/`-இல் உள்ள production code-ஐ மாற்றும்போது எப்போதும் tests-ஐச் சேர்க்கவும் அல்லது புதுப்பிக்கவும்
