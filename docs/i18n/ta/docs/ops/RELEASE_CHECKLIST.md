## சுருக்கமாக

```bash
# 1. பதிப்பை உயர்த்தி CHANGELOG-ஐ உருவாக்கவும் (திறன்)
/version-bump-cc patch    # அல்லது minor/major

# 2. தரச் சரிபார்ப்பை உள்ளூரில் இயக்கவும்
npm run check              # lint + சோதனைகள்
npm run test:coverage      # முழுமையான coverage சரிபார்ப்பு (60/60/60/60)

# 3. Build செய்து smoke சோதனை செய்யவும்
npm run build
npm run test:e2e           # விருப்பத்திற்குரியது, ஆனால் பரிந்துரைக்கப்படுகிறது

# 4. வெளியீட்டை உருவாக்கவும் (திறன்)
/generate-release-cc

# 5. Deploy செய்யவும் (திறன்)
/deploy-vps-both-cc        # அல்லது akamai-cc / local-cc

# 6. வெளியீட்டுச் சான்றுகளைப் பதிவு செய்யவும் (திறன்)
/capture-release-evidences-cc
```

## npm Trusted Publishing (v3.8.51 முதல் இயல்புநிலை) — கோரிக்கையின் பேரில் staged, மாற்று வழியாக direct

`npm-publish.yml` இயல்பாக **npm Trusted Publishing (OIDC)** மூலம் வெளியிடுகிறது:
`stage-npm` job (github-hosted), அந்த இயக்கத்திற்காக GitHub-இன் id-token-ஐ குறுகிய கால npm
நற்சான்றாக மாற்றுகிறது — repository secrets-இல் நீண்டகால npm token இல்லை, 2FA prompt இல்லை, provenance இணைக்கப்பட்டுள்ளது.
2FA-ஐத் தவிர்க்கும் tokens படிப்படியாக நிறுத்தப்படுவதால், npm தற்போது அனுமதிக்கும் bypass இதுவாகும்;
WS1.3 உத்தரவாதத்தைத் தக்கவைத்துக்கொண்டே, v3.8.48 வரை திட்டத்தில் இருந்த முழுத் தானியங்கி
செயல்முறையை இது மீட்டெடுக்கிறது (கசிந்த token மட்டும் வெளியிட முடியாது — token என்பதே இல்லை).

**ஒருமுறை செய்ய வேண்டிய அமைப்பு (உரிமையாளர்):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none). இது உருவாக்கப்படும் வரை, தானியங்குப் படி `ENEEDAUTH` பிழையுடன் தோல்வியடையும்:
`publish_mode=staged` (கீழே) அல்லது `direct` கொண்டு மீண்டும் dispatch செய்யவும்.

### Staged publishing (கோரிக்கையின் பேரில் — `publish_mode=staged`)

npm-publish workflow இனி நேரடியாக வெளியிடாது: அது pack செய்யப்பட்ட tarball-ஐ
(`check:pack-boot`) boot செய்து, பின்னர் `npm stage publish`-ஐ இயக்கும் — அதே bytes registry-இல்
நிறுத்திவைக்கப்படும்; உரிமையாளர் ஒப்புதல் அளிக்கும் வரை அவற்றை **நிறுவ முடியாது**. மனித 2FA சரிபார்ப்பு,
ஆதாரத்திற்கு முன்பாக அல்லாமல் அதற்குப் பிறகு நடைபெறுமாறு மாற்றப்பட்டுள்ளது.

**Workflow green ஆன பிறகு உரிமையாளருக்கான செயல்முறை:**

1. `npm stage list omniroute` — stage id-ஐக் கண்டறியவும் (workflow summary-யிலும் அச்சிடப்படும்).
2. Staged bytes-ஐச் சரிபார்க்கவும் (பரிந்துரைக்கப்படுகிறது): `npm stage download <id>`, பின்னர் பதிவிறக்கப்பட்ட
   tarball-ஐ ஒரு தற்காலிக prefix-இல் நிறுவி boot செய்யவும் (`npm run check:pack-boot`, CI-இல் அதே
   pack→install→boot முடிவைத் தானியக்கமாக்குகிறது).
3. `npm stage approve <id>` — 2FA prompt-தான் publish ஆகும். `npm stage reject <id>` நிராகரித்து அகற்றும்.
4. வெளியீட்டுக்குப் பிந்தைய பாதுகாப்பு: post-publish verifier (v3.8.49 திட்டத்தின் WS1.4), வெளியிடப்பட்ட
   பதிப்பை public registry-இலிருந்து சுத்தமான container ஒன்றில் நிறுவி boot செய்கிறது.

**அவசரகால மாற்று வழி:** `publish_mode=direct` உடன் `workflow_dispatch`, மரபுவழி உடனடி
`npm publish`-ஐ மீட்டெடுக்கிறது (staging செயல்முறையே தவறாக நடந்துகொண்டால் மட்டும் பயன்படுத்தவும்; காரணத்தைப் பதிவுசெய்யவும்).

**ஒருமுறை செய்ய வேண்டிய பாதுகாப்புக் கடினப்படுத்தல் (உரிமையாளர், npmjs.com):**
`omniroute`-க்கான Trusted Publisher-ஐ stage-only பயன்முறையில் உள்ளமைக்கவும்; இதனால் கசிந்த நீண்டகால token மூலம்
எங்கிருந்தும் நேரடியாக `npm publish` செய்ய முடியாது — CI-ஆல் stage மட்டுமே செய்ய முடியும்;
உரிமையாளரின் 2FA மட்டுமே வெளியிட முடியும்.

**சிதைந்த artifact-க்கான செயல்திட்டம் (மாற்றமில்லை):** இயல்புநிலை உடனடி நடவடிக்கையாக
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"`-ஐப் பயன்படுத்தவும் (சில நிமிடங்களில் செய்யலாம், மீளக்கூடியது);
72h/no-dependents வரம்பிற்குள் மட்டுமே `npm unpublish` செய்யவும், அதை ஒருபோதும் முதல் நடவடிக்கையாகச் செய்யாதீர்கள்.
Docker: ஒரு version tag-ஐ ஒருபோதும் மீண்டும் எழுதாதீர்கள் — rollback என்பது `latest`-ஐக் கடைசியாகச் சரியாக இருந்த
digest-க்கு மீண்டும் சுட்டுவதாகும்.

**Docker Hub `latest` (ஒவ்வொரு நிலையான SemVer வெளியீட்டிலும் கட்டாயம்):**
`should-promote-latest.sh`, இது உயர்ந்த நிலையான SemVer என்பதை உறுதிப்படுத்தும்போது,
`docker-publish` workflow ஆனது **ஒரே digest** உடன் `X.Y.Z` மற்றும் `:latest`
ஆகிய **இரண்டையும்** tag செய்ய வேண்டும். Job முடிந்த பிறகு: Hub `latest` digest புதிய
SemVer digest-க்கு சமமாகவும், `last_updated` நகர்ந்திருக்கவும் வேண்டும். Git-இல் மட்டுமே உள்ள
திருத்தங்களைப் பற்றி release notes குறிப்பிடும்போது, `:latest`-ஐ பழைய build-இல் விட்டுவிடாதீர்கள்.
Compose quickstarts, `:latest`-ஐப் பயன்படுத்துகின்றன; GitOps தொடர்ந்து `X.Y.Z`-ஐ pin செய்ய வேண்டும்.
[Docker release channels](../guides/DOCKER_GUIDE.md#release-channels) மற்றும் #10317-ஐப் பார்க்கவும்.

## Hotfix விரைவுப் பாதை (`hotfix` லேபிள்)

`hotfix` என லேபிளிடப்பட்ட PR, அதிகச் சுமையுள்ள CI மேட்ரிக்ஸை (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) தவிர்த்துவிட்டு, வேகமானதும் வலுவான சிக்னல் தருவதுமான சோதனைத் தடைகளைத் தக்கவைக்கிறது: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
மற்றும் tarball boot-smoke (`check:pack-boot`). இலக்கு: ~33min-க்குப் பதிலாக ≤15min-இல் green நிலை.

**நுழைவுக் கொள்கை — நான்கும் கட்டாயம் (Chromium/VS Code/Node அவசரப் பாதைகளை அடிப்படையாகக் கொண்டது):**

1. **தீவிரம்**: production செயலிழந்துள்ளது — வெளியிடப்பட்ட artifact துவக்கத்தின்போது crash ஆகிறது / ஒரு
   பாதுகாப்புத் திருத்தம் / release-இன் ஒவ்வொரு பயனரும் பாதிக்கப்பட்டுள்ளனர். "முக்கியமானது" என்பது "செயலிழந்தது" அல்ல.
2. **அதிகாரம்**: repository உரிமையாளர் மட்டுமே `hotfix` லேபிளைப் பயன்படுத்துவார். அந்த லேபிளே
   ஒப்புதல் — campaign PR-இல் ஒருபோதும் சுயமாகப் பயன்படுத்தக் கூடாது.
3. **ஆதாரம்**: முந்தைய முழுமையாக-green ஆன heavy run-ஐ (தவிர்க்கப்பட்ட jobs மீண்டும் சரிபார்க்கவிருந்த suite)
   மற்றும் திருத்தத்திற்கான முதலில் தோல்வியடைந்து பின்னர் வெற்றிபெற்ற test-ஐ PR body இணைக்க வேண்டும்.
4. **வரம்பு**: cherry-pick மட்டும் — மிகக் குறைந்தபட்சத் திருத்தம்; refactor-களோ, தொடர்பற்ற கூடுதல் மாற்றங்களோ கூடாது.

தவிர்க்கப்பட்ட coverage/ratchet பரப்பு, release branch-இன் அடுத்த முழுமையான run மூலம்
மீண்டும் சரிபார்க்கப்படும் (தொடர்ச்சியான release-green) — இந்தப் பாதை காத்திருப்பதை மட்டுமே தவிர்க்கிறது; சரிபார்ப்பை ஒருபோதும் தவிர்ப்பதில்லை.
Tests மட்டும் கொண்ட diff-கள் (`tests/`-இன் கீழுள்ள அனைத்து கோப்புகளும், `tests/e2e/`-இன் கீழ் எதுவும் இல்லாதவை) எந்த லேபிளும் இல்லாமல் தானாகவே E2E
மேட்ரிக்ஸைத் தவிர்க்கும்.

### Hooks (Husky மூலம் சரிபார்க்கப்பட்டது)

Husky hooks `.husky/`-இல் உள்ளன; git செயல்பாடுகளின்போது தானாக இயங்கும்.

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** வேகமான deterministic gates — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (2026-06-13 அன்று செயல்படுத்தப்பட்டது). `test:unit` வேண்டுமென்றே விலக்கப்பட்டுள்ளது (மெதுவானது; CI `test-unit` job மூலம் கையாளப்படுகிறது).
  - release branches-ஐ push செய்வதற்கு முன் `npm run test:unit`-ஐக் கைமுறையாக இயக்கவும்.

ஒரு hook தோல்வியடைந்தால்: அடிப்படைச் சிக்கலைச் சரிசெய்யவும்; `--no-verify` மூலம் அதைக் கடந்து செல்ல வேண்டாம்.

## முந்தைய பதிப்புக்கு மீட்டமைத்தல்

வெளியீட்டில் கடுமையான சிக்கல் இருந்தால்:

1. `gh release edit vX.Y.Z --prerelease` (சமீபத்திய வெளியீடு அல்ல எனக் குறிக்கும்)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (பயனர்கள் இன்னும் பயன்படுத்தத் தொடங்கவில்லை என்றால் மட்டும்)
3. அல்லது: `release/vX.Y.0`-இல் அவசரத் திருத்தம் → திருத்த வெளியீடு `vX.Y.(Z+1)`
4. GitHub Discussions மற்றும் Discord-இல் உடனடியாகத் தெரிவிக்கவும்

## கடுமையான விதிகள்

- ஒருபோதும் நேரடியாக `main`-இல் commit செய்ய வேண்டாம்
- `main` அல்லது `release/*` கிளைகளில் ஒருபோதும் `git push --force` பயன்படுத்த வேண்டாம்
- Husky hooks-ஐ (`--no-verify`) ஒருபோதும் தவிர்க்க வேண்டாம்
- ரகசியங்கள், நற்சான்றுகள் அல்லது `.env` கோப்புகளை ஒருபோதும் commit செய்ய வேண்டாம்
- Coverage ≥60/60/60/60 ஆகவே இருக்க வேண்டும் (statements/lines/functions/branches)
- `src/`, `open-sse/` அல்லது `bin/`-இல் உள்ள உற்பத்திக் குறியீட்டை மாற்றும்போது எப்போதும் சோதனைகளைச் சேர்க்கவும் அல்லது புதுப்பிக்கவும்
