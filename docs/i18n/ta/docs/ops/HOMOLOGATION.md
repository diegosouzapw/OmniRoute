## முன்நிபந்தனைகள்

1. `.env.homolog.example`-ஐ `.env.homolog`-க்கு நகலெடுத்து (gitignored — இதை ஒருபோதும் commit செய்ய வேண்டாம்), பின்வருவனவற்றை நிரப்பவும்:
   - `HOMOLOG_BASE_URL` — இலக்கு deploy, எ.கா. `http://192.168.0.15:20128`.
   - `HOMOLOG_ADMIN_PASSWORD` — அந்த deploy-க்கான dashboard நிர்வாகக் கடவுச்சொல்.
   - `HOMOLOG_CRITICAL_PROVIDERS` — உண்மையான smoke chat கோரிக்கையைப் பெறும், காற்புள்ளியால் பிரிக்கப்பட்ட provider முன்னொட்டுகள் (எ.கா. `openai,anthropic,gemini,codex,grok,glm,deepseek,openrouter`).
   - `HOMOLOG_API_KEY` — வழக்கமான இயக்கங்களில் காலியாக விடவும்; suite தனது சொந்த தற்காலிக key-ஐ உருவாக்கி ரத்து செய்கிறது. தனிப்பட்ட ஒரு layer-ஐத் தனிமைப்படுத்தி debug செய்வதற்கு மட்டுமே இதை அமைக்கவும்.
2. repo-வில் `npm install`-ஐ இயக்கவும் (suite-இன் சார்புகள் — `httpyac`, `promptfoo`, `playwright-ctrf-json-reporter`, `junit-to-ctrf`, `ctrf` — வழக்கமான devDependencies ஆகும்).
3. browser binary-கள் ஏற்கெனவே இல்லையெனில் `npx playwright install`-ஐ இயக்கவும்.

## இயக்குவது எப்படி

```bash
npm run homolog
```

உள்ளூர் `package.json`-உடன் பொருந்தாத பதிப்பைக் கொண்ட deploy-க்கு எதிராகச் சரிபார்க்க (எ.கா. இன்னும் முந்தைய patch release-இல் இருக்கும் homologation box), எதிர்பார்க்கப்படும் பதிப்பை வெளிப்படையாக override செய்யவும்:

```bash
HOMOLOG_EXPECT_VERSION=3.8.47 npm run homolog
```

ஏதேனும் layer தோல்வியடைந்தால், இயக்கம் பூஜ்ஜியமல்லாத exit code-உடன் வெளியேறும். தோல்வி ஏற்பட்டாலும் கூட, தான் உருவாக்கிய தற்காலிக API key-ஐ ரத்து செய்ய எப்போதும் முயற்சிக்கும் (`scripts/homolog/run.mjs`-இல் உள்ள `finally` block).

## அறிக்கையைப் படித்தல்

அனைத்து வெளியீடுகளும் `homolog-report/`-இல் சேமிக்கப்படும் (gitignored):

- `summary.md` — stdout-க்கு அச்சிடப்படும் அதே அட்டவணை; ஒவ்வொரு layer-க்கும் ஒரு வரிசை (✅/❌ + விவரம்).
- `homolog-ctrf.json` — ஒருங்கிணைந்த CTRF அறிக்கை (API/SSE, provider-smoke மற்றும் UI முடிவுகளின் merge) — release STOP #2 checklist-உடன் இணைக்க வேண்டிய artifact இதுவாகும்.
- `httpyac-junit.xml`, `api-ctrf.json`, `providers-ctrf.json`, `ui-ctrf.json` — ஒவ்வொரு layer-க்குமான மூல/இடைநிலை அறிக்கைகள்.
- `promptfooconfig.yaml`, `provider-misses.json` — தற்போதைய இயக்கத்திற்காக உருவாக்கப்பட்ட promptfoo config மற்றும் live catalog-இல் இல்லாத முக்கியமான provider-கள்.

L0 தோல்வியடைந்தால் உடனடியாக நிறுத்தப்படும் (தற்காலிக key உருவாக்கப்படாது), ஏனெனில் பதிப்பு/health பொருத்தமின்மை என்பது கீழ்நிலை layer ஒவ்வொன்றும் தவறான deploy-ஐச் சரிபார்க்கும் என்பதைக் குறிக்கிறது.

## UI நியாயமான முறையில் மாறும்போது baseline-ஐ மீண்டும் அமைத்தல்

L4b (route smoke) மற்றும் L4c (API-key UI flow) ஆகியவை snapshot-களால் அல்லாமல் உண்மையான DOM locator-களால் இயக்கப்படுகின்றன; எனவே பெரும்பாலான நியாயமான UI மாற்றங்களுக்கு suite புதுப்பிப்பு தேவையில்லை. ஒரு மாற்றம் locator-ஐச் செயலிழக்கச் செய்யும்போது (எ.கா. மறுபெயரிடப்பட்ட button label அல்லது இடம் மாற்றப்பட்ட settings page):

1. தற்போதைய source-க்கு எதிராக locator-ஐ மீண்டும் உறுதிப்படுத்தவும் (ஒவ்வொரு locator-மும் எந்த file/line-க்கு எதிராக உறுதிப்படுத்தப்பட்டது என்பதை spec-கள் ஏற்கெனவே ஆவணப்படுத்துகின்றன — அதே முறையைப் பின்பற்றவும், ஊகிக்க வேண்டாம்).
2. `tests/homolog/ui/`-இல் உள்ள spec-ஐப் புதுப்பிக்கவும்.
3. திருத்தத்தை உறுதிப்படுத்த VPS-க்கு எதிராக `npm run homolog`-ஐ (அல்லது பாதிக்கப்பட்ட Playwright spec-ஐ மட்டும்) மீண்டும் இயக்கி, பின்னர் commit செய்யவும்.

இந்த suite-இல் visual/pixel baseline இல்லை (F1) — அதற்கு Roadmap-ஐப் பார்க்கவும்.

## செயல்திட்டம் (F2 / F3)
