ஒரு pull request-க்கு ஏற்ற, நம்பகமான மிகச் சிறிய மேம்பாட்டுச் சுழற்சியைத் தேர்ந்தெடுக்க இந்த வழிகாட்டியைப் பயன்படுத்தவும். இது கீழே இணைக்கப்பட்டுள்ள பகுதி சார்ந்த கட்டமைப்பு மற்றும் பாதுகாப்பு ஆவணங்களுக்கு மாற்றாக அமையாது; ஒவ்வொரு பொதுவான மாற்ற வகையையும் அதற்கான ஒப்பந்தங்கள், இலக்குநோக்கிய சரிபார்ப்புகள் மற்றும் CI உள்ளடக்கத்துடன் இது இணைக்கிறது.

## ஒவ்வொரு மாற்றமும் பின்பற்றும் பாதை

1. **திருத்துவதற்கு முன் அடிப்படைக் கிளையைத் தேர்ந்தெடுக்கவும்.** செயலில் உள்ள மிக உயர்ந்த `release/v*` கிளையைக் கண்டறிந்து, அதன் நுனியிலிருந்து புதிய கிளையை உருவாக்கவும். `main`-ஐ அல்லாமல் அந்தக் கிளையையே இலக்காகக் கொள்ளவும். வெளியீட்டு முடக்கம் செயலில் இருந்தால், முடக்கப்பட்ட கிளையை இலக்காகக் கொள்ள வேண்டாம்; [கிளையிடல் மற்றும் வெளியீட்டு மாதிரி](BRANCHING_MODEL.md) ஆவணத்தில் விவரிக்கப்பட்டுள்ள அடுத்த செயலில் உள்ள சுழற்சியைப் பயன்படுத்தவும்.
2. **ஒப்பந்தங்களைக் குறிப்பிடவும்.** மாற்றம் பாதிக்கும் ஒவ்வொரு பட்டியல், schema, உருவாக்கப்பட்ட கலைப்பொருள், பொது API அல்லது பயனர் இடைமுகத்தையும் அடையாளம் காணவும். கீழே உள்ள அட்டவணை குறைந்தபட்ச தொடக்கத் தொகுப்பை வழங்குகிறது.
3. **இலக்குநோக்கிய சோதனைகளை எழுதவும் அல்லது புதுப்பிக்கவும்.** `src/`, `open-sse/`, `electron/` அல்லது `bin/` ஆகியவற்றில் செய்யப்படும் தயாரிப்பு மாற்றங்களுக்கு அதே PR-இல் ஒரு தானியக்கச் சோதனை தேவை. நடத்தையை நிரூபிக்கும் மிகச் சிறிய சோதனைக் கோப்புகளை முதலில் இயக்கி, பின்னர் பட்டியலிடப்பட்டுள்ள இலக்குநோக்கிய கட்டுப்பாடுகளை இயக்கவும்.
4. **பரந்த matrix-ஐ CI இயக்க அனுமதிக்கவும்.** முழுமையான unit shards, Vitest, coverage ratchet மற்றும் production build ஆகியவை PR-இல் இயங்கும். இலக்குநோக்கிய தோல்வி ஒன்று பரந்த தாக்கத்தைக் குறிப்பிடும்போது அல்லது மாற்றம் பல துணை அமைப்புகளை உள்ளடக்கும்போது மட்டுமே பரந்த சோதனைத் தொகுப்பை உள்ளூரில் இயக்கவும்.
5. **மதிப்பாய்வுக்கு முன் ஒத்திசைக்கவும்.** செயலில் உள்ள அடிப்படைக் கிளையை fetch செய்து, அதன் புதிய commits மற்றும் அதற்கு எதிரான உங்கள் diff-ஐ ஆய்வு செய்து, பின்னர் பங்களிப்பாளர் பணிப்பாய்வுக்கு ஏற்ப அடிப்படைக் கிளையை rebase அல்லது merge செய்யவும். உருவாக்கப்பட்ட கோப்புகள் மற்றும் பட்டியல்களில் ஏற்படும் முரண்பாடுகளை அவற்றின் மூலத்திலிருந்து தீர்த்து, அவற்றை மீண்டும் உருவாக்கி, இலக்குநோக்கிய சுழற்சியை மீண்டும் இயக்கி, PR இன்னும் செயலில் உள்ள வெளியீட்டுக் கிளையையே இலக்காகக் கொண்டிருப்பதை உறுதிப்படுத்தவும்.
6. **ஆதாரத்தைப் பதிவு செய்யவும்.** PR வார்ப்புருவில் இயக்கப்பட்ட commands, சேர்க்கப்பட்ட அல்லது மாற்றப்பட்ட ஒவ்வொரு சோதனைக் கோப்பு, migrations அல்லது feature flags மற்றும் இன்னும் நிலுவையில் உள்ள CI-மட்டும் சரிபார்ப்புகள் ஆகியவற்றைப் பட்டியலிடவும்.

## மாற்ற வகைகளுக்கான சிறந்த நடைமுறைப் பாதைகள்

கீழே உள்ள commands குறைந்தபட்ச இலக்குநோக்கிய சரிபார்ப்புகளாகும்; நீங்கள் மாற்றிய நடத்தையை நேரடியாகச் சரிபார்க்கும் சோதனையைத் தவிர்ப்பதற்கான அனுமதி அல்ல.

### Provider

**ஒப்பந்தங்கள்**

- `src/shared/constants/providers/`-இல் உள்ள Provider வரையறையும், `src/shared/constants/providers.ts`-இல் அதன் தொகுப்பும்.
- `open-sse/config/providerRegistry.ts` அல்லது அதிலிருந்து பிரித்தெடுக்கப்பட்ட registry கோப்புகளில் உள்ள models மற்றும் capabilities.
- Executor/translator தேர்வு, OAuth அல்லது API-key உள்ளமைவு, dashboard assets மற்றும் பொருந்தும் இடங்களில் உருவாக்கப்பட்ட provider reference.
- பொது credentials, `resolvePublicCred()`-ஐப் பயன்படுத்த வேண்டும்; error responses, பகிரப்பட்ட sanitized error helpers-ஐப் பயன்படுத்த வேண்டும். `docs/security/PUBLIC_CREDS.md` (git-இல் உள்ளது; `/docs`-இல் தொகுக்கப்படாது) மற்றும் [Error Sanitization](../security/ERROR_SANITIZATION.md) ஆகியவற்றைப் பார்க்கவும்.

**இலக்குநோக்கிய சுழற்சி**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # பட்டியல் மாறும்போது; உருவாக்கப்பட்ட diff-ஐ commit செய்யவும்
npm run lint
```

பாதிக்கப்பட்ட ஒவ்வொரு request family-யையும் சோதிக்கவும்: chat, Responses, images, embeddings, audio அல்லது video. உருவாக்கப்பட்ட பட்டியல் மற்றும் golden diffs-ஐ ஒப்பந்த மாற்றங்களாக மதிப்பாய்வு செய்யவும்; அவற்றைக் கண்மூடித்தனமாக ஏற்க வேண்டாம்.

### Routing

**ஒப்பந்தங்கள்**

- `src/shared/constants/routingStrategies.ts`-இல் உள்ள பொது strategy values மற்றும் UI metadata.
- `open-sse/services/combo.ts` மற்றும் `open-sse/services/combo/` ஆகியவற்றின் கீழ் உள்ள dispatch மற்றும் ordering.
- Combo schemas, persistence, resilience state, model capabilities மற்றும் API/UI controls.
- நடத்தை மாறும்போது [Auto-Combo Engine](../routing/AUTO-COMBO.md) மற்றும் resilience ஆவணங்கள்.

**இலக்குநோக்கிய சுழற்சி**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy அல்லது dispatch மாற்றங்கள்
npm run check:known-symbols      # strategy registration மாற்றங்கள்
npm run lint
```

உள்ளூரில் உறுதியான முடிவுகளைத் தரும் mocked-upstream சோதனைகளைப் பயன்படுத்தவும். நேரடி combo smoke சோதனைகளுக்கு credentials தேவை; அவை கைமுறையானவை, CI-க்கான மாற்றுகள் அல்ல.

### UI / UX

**ஒப்பந்தங்கள்**

- `src/app/` மற்றும் `src/shared/components/` ஆகியவற்றின் கீழ் உள்ள Next.js route/page மற்றும் பகிரப்பட்ட component எல்லைகள்.
- API response shapes, loading/empty/error நிலைகள், keyboard மற்றும் screen-reader நடத்தை, responsive layout, theming மற்றும் locale விரிவாக்கம்.
- `src/i18n/messages/en.json`-இல் உள்ள ஆங்கில UI மூல சரங்கள்; பயனர் பார்க்கக்கூடிய புதிய உரையை hard-code செய்ய வேண்டாம்.

**இலக்குநோக்கிய சுழற்சி**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

interaction அல்லது visual மாற்றங்களுக்காகப் பயன்பாட்டை இயக்கி, குறுகிய மற்றும் அகலமான viewports இரண்டிலும் சரிபார்க்கவும். CI, production build மற்றும் பரந்த சோதனைத் தொகுப்புகளை இயக்குகிறது; எனினும் visual நடத்தைக்கு மாற்றத்துக்குப் பொருத்தமான இலக்குநோக்கிய component, Playwright அல்லது ஆவணப்படுத்தப்பட்ட கைமுறைச் சரிபார்ப்பு இன்னும் தேவைப்படுகிறது.

### i18n

**ஒப்பந்தங்கள்**

- `src/i18n/messages/en.json` என்பது UI மூலம்; `config/i18n.json` என்பது locale மூலம்.
- CLI பட்டியல்கள் `bin/cli/locales/`-இன் கீழ் தனியாக உள்ளன.
- ICU placeholders மற்றும் tags-ஐ அப்படியே பாதுகாக்கவும். product/provider/model பெயர்கள், protocol மற்றும் header பெயர்கள், commands, code/JSON identifiers, URLs, environment variables அல்லது `OmniRoute`, `OAuth`, `MCP`, `A2A` போன்ற பாதுகாக்கப்பட்ட சொற்களை மொழிபெயர்க்க வேண்டாம். தற்போதைய மூலப் பட்டியல் `scripts/i18n/glossary/protected-terms.json` ஆகும்.

**இலக்குநோக்கிய சுழற்சி**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI சரங்கள்/பட்டியல்கள் மாறும்போது
npm run lint
```

இது ஏற்கனவே உள்ள அமைப்பிற்கான வழிகாட்டுதலாகும்; அதன் tooling அல்லது key model-ஐ விரிவாக்குவதற்கான அழைப்பு அல்ல. மாற்று அமைப்பு வடிவமைக்கப்பட்டுக் கொண்டிருக்கும்போது i18n patches-ஐ மிகத் துல்லியமாகவும் வரம்புக்குட்பட்டதாகவும் வைத்திருக்கவும். பணி வெளிப்படையாக உருவாக்கப்பட்ட மொழிபெயர்ப்புகளைக் கோரினால் மற்றும் அதன் விளைவான diff-ஐ நீங்கள் மதிப்பாய்வு செய்திருந்தால் மட்டுமே வெளிப்புற சேவைகளை அழைக்கும் translation commands-ஐ இயக்கவும்.

### CLI

**ஒப்பந்தங்கள்**

- `bin/cli/`-இல் உள்ள பொது commands மற்றும் flags, உருவாக்கப்பட்ட API commands, exit codes, stdout/stderr மற்றும்
  JSON output வடிவங்கள், config/environment நடத்தை மற்றும் தொகுக்கப்பட்ட கோப்புகள்.
- CLI பயனர்களுக்குக் காட்டப்படும் strings, CLI i18n layer-ஐப் பயன்படுத்த வேண்டும்; மேலும் `en`/`pt-BR` catalogs ஒருங்கிணைந்த நிலையில் பராமரிக்கப்பட வேண்டும்.
- ஆதரிக்கப்படும் runtime ஆக Node-ஐயும், வெளியிடப்பட்ட binary contract-ஐயும் பாதுகாக்கவும்.

**கவனம் செலுத்திய சுழற்சி**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # உருவாக்கப்பட்ட/தொகுக்கப்பட்ட CLI மாற்றங்கள்
npm run check:pack-policy     # package மேற்பரப்பு மாற்றங்கள்
npm run lint
```

நடத்தை parsing, கோப்புகள் அல்லது exit status-ஐச் சார்ந்திருக்கும்போது, ஒரு தற்காலிக data directory-இல் துல்லியமான command-ஐப் பயன்படுத்தவும். CI விரிவான package artifact மற்றும் ecosystem சோதனைகளைச் செய்கிறது.

### தரவுத்தளம்

**ஒப்பந்தங்கள்**

- `src/lib/db/`-இன் கீழ் உள்ள domain modules; குறிப்பிட்ட modules-ஐ நேரடியாக import செய்யவும் (பழைய `localDb.ts` re-export layer அகற்றப்பட்டது).
- `src/lib/db/migrations/`-இன் கீழ் எண்ணிடப்பட்ட, idempotent SQL migrations, transaction பாதுகாப்பு, upgrade
  நடத்தை, indexes மற்றும் schema-வால் பாதிக்கப்படும் ஒவ்வொரு caller-உம்.
- Routes மற்றும் handlers ஒருபோதும் raw SQL-ஐ நேரடியாக இயக்கக்கூடாது.

**கவனம் செலுத்திய சுழற்சி**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

ஒரு migration-ஐச் சேர்க்கும்போது, புதிதாக உருவாக்கப்பட்ட தரவுத்தளம் மற்றும் முந்தைய schema-விலிருந்து செய்யப்படும் upgrade ஆகிய இரண்டையும் சோதிக்கவும். Cleanup செய்யும்போது database tests handles-ஐ மூடி, `resetDbInstance()`-ஐ அழைக்க வேண்டும். Best-effort Bun adapter பாதை மாறும்போது மட்டுமே `npm run test:bun:db`-ஐ இயக்கவும்; Node தொடர்ந்து அதிகாரப்பூர்வமானதாக இருக்கும்.

### Build / deploy

**ஒப்பந்தங்கள்**

- Root மற்றும் workspace manifests/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/`
  package உள்ளடக்கங்கள், Electron platform metadata, CI workflows மற்றும் deployment sentinels.
- ஆதரிக்கப்படும் Node ranges மற்றும் `CLAUDE.md`-இல் allow-list செய்யப்பட்ட Bun பயன்பாடு அப்படியே பராமரிக்கப்பட வேண்டும்.
- Build artifacts கண்காணிக்கப்படாமல் இருக்க வேண்டும்; dependency, license, workflow மற்றும் package policies பொருந்தும்.

**கவனம் செலுத்திய சுழற்சி**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency அல்லது lockfile மாற்றங்கள்
npm run check:pack-policy      # வெளியிடப்பட்ட package மேற்பரப்பு மாற்றங்கள்
npm run lint
```

மாற்றம் compilation, standalone assembly, assets அல்லது runtime bundling-ஐப் பாதிக்கும்போது மட்டுமே உள்ளூரில் `npm run build`-ஐப் பயன்படுத்தவும். Release/deploy சரிபார்ப்பிற்காக மட்டுமே `npm run build:release`-ஐப் பயன்படுத்தவும். CI-இன் build-தான் இறுதியான cross-platform signal; platform-specific Electron மாற்றங்களுக்கு, அதற்குப் பொருந்தும் focused build அல்லது smoke evidence தேவை.

## உள்ளூர் சுழற்சி மற்றும் CI

| ஒவ்வொரு திருத்தத்திற்கும் உள்ளூரில் இயக்க வேண்டியவை                                | CI வழங்கும் விரிவான அறிகுறி                                                     |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| மேலே உள்ள நேரடி நடத்தைச் சோதனைகள் மற்றும் வகைத் தடுப்புகள்                         | பகிர்ந்தளிக்கப்பட்ட முழுமையான unit தொகுப்பு மற்றும் தொடர் சோதனைகள்              |
| `npm run lint`                                                                     | Vitest தொகுப்புகள் மற்றும் coverage/quality ratchets                            |
| பாதிக்கப்பட்ட ஒப்பந்தம் கோரும்போது மட்டும் typecheck அல்லது build                  | Production build, பாதுகாப்பு, ஆவணங்கள், dependency மற்றும் PR-policy தடுப்புகள் |
| தானியக்கம் நடத்தையை நிரூபிக்க முடியாதபோது மட்டும் கைமுறை interaction/live சோதனைகள் | workflow-ஆல் உள்ளமைக்கப்பட்ட cross-job integration மற்றும் platform சோதனைகள்    |

பச்சை நிலையில் உள்ள இலக்குவைத்த சுழற்சி, மாற்றப்பட்ட ஒப்பந்தத்தைப் பற்றிய சான்றாகும்; தொடர்பில்லாத CI சோதனைகள்
வெற்றிபெறும் என்பதற்கான நிரூபணம் அல்ல. அதேபோல், ஒவ்வொரு உள்ளூர் திருத்தமும் முழு repository matrix-க்காகக் காத்திருக்குமாறு செய்ய வேண்டாம்.

## ஒத்திசைவுச் சரிபார்ப்புப் பட்டியல்

மதிப்பாய்வைக் கோருவதற்கு முன்:

- PR base இன்னும் செயலிலுள்ள மிக உயர்ந்த `release/v*` branch என்பதை உறுதிப்படுத்தவும்.
- அந்த base-ஐ fetch செய்து, நீங்கள் branch உருவாக்கியதிலிருந்து சேர்க்கப்பட்ட commits-ஐ மதிப்பாய்வு செய்யவும்.
- தற்செயலான அல்லது உருவாக்கப்பட்ட தேவையற்ற மாற்றங்கள் உள்ளனவா என `git diff <active-base>...HEAD`-ஐ மதிப்பாய்வு செய்யவும்.
- மூலத்தைப் புதுப்பித்து output-ஐ மீண்டும் உருவாக்குவதன் மூலம் catalog மற்றும் generated-document முரண்பாடுகளைத் தீர்க்கவும்.
- ஒத்திசைவுக்குப் பிறகு PR விளக்கத்தில் பட்டியலிடப்பட்டுள்ள ஒவ்வொரு இலக்குவைத்த test/gate-ஐயும் மீண்டும் இயக்கவும்.
- மாற்றப்பட்ட base-க்கு ஏற்ப மாற்றுவதற்காக மட்டும் assertions-ஐ ஒருபோதும் தளர்த்தவோ தேவையான tests-ஐ நீக்கவோ வேண்டாம்.

release-freeze மற்றும் retargeting விதிகளுக்கு,
[Branching & Release Model](BRANCHING_MODEL.md)-ஐப் பயன்படுத்தவும். முழுமையான CI பட்டியலுக்கு,
[Quality Gates Reference](../architecture/QUALITY_GATES.md)-ஐப் பயன்படுத்தவும்.
