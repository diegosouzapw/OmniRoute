ஒரு pull request-க்கான மிகச் சிறிய, நம்பகமான development loop-ஐத் தேர்வுசெய்ய இந்த வழிகாட்டியைப் பயன்படுத்தவும். கீழே இணைக்கப்பட்டுள்ள பகுதி-சார்ந்த architecture மற்றும் security ஆவணங்களுக்கு இது
மாற்றாகாது; பொதுவான ஒவ்வொரு change type-ஐயும் அதற்குரிய contracts, focused checks மற்றும் CI coverage உடன் இது இணைக்கிறது.

## ஒவ்வொரு மாற்றமும் பின்பற்றும் பாதை

1. **திருத்துவதற்கு முன் base-ஐத் தேர்வுசெய்யவும்.** மிகவும் உயர்ந்த செயலில் உள்ள `release/v*` branch-ஐக் கண்டறிந்து, அதன்
   tip-இலிருந்து branch உருவாக்கவும். `main`-ஐ அல்ல, அந்த branch-ஐ target செய்யவும். release freeze செயலில் இருந்தால், freeze செய்யப்பட்ட
   branch-ஐ target செய்ய வேண்டாம்; [Branching & Release Model](BRANCHING_MODEL.md)-இல்
   விவரிக்கப்பட்டுள்ள அடுத்த செயலில் உள்ள cycle-ஐப் பயன்படுத்தவும்.
2. **Contracts-ஐக் குறிப்பிடவும்.** மாற்றம் பாதிக்கும் ஒவ்வொரு catalog, schema, generated artifact, public API அல்லது user
   interface-ஐயும் அடையாளம் காணவும். கீழேயுள்ள அட்டவணை குறைந்தபட்ச தொடக்கத் தொகுப்பை வழங்குகிறது.
3. **Focused tests-ஐ எழுதவும் அல்லது புதுப்பிக்கவும்.** `src/`, `open-sse/`, `electron/` அல்லது
   `bin/`-இல் செய்யப்படும் production மாற்றங்களுக்கு அதே PR-இல் automated test தேவை. நடத்தையை நிரூபிக்கும் மிகச் சிறிய test files-ஐ
   முதலில் இயக்கி, பின்னர் பட்டியலிடப்பட்டுள்ள focused gates-ஐ இயக்கவும்.
4. **பரந்த matrix-ஐ CI இயக்க அனுமதிக்கவும்.** முழுமையான unit shards, Vitest, coverage ratchet மற்றும்
   production build ஆகியவை PR-இல் இயங்கும். focused failure பரந்த தாக்கத்தைக் காட்டும்போது அல்லது மாற்றம் பல
   subsystems-ஐ உள்ளடக்கும்போது மட்டுமே பரந்த suite-ஐ உள்ளூரில் இயக்கவும்.
5. **Review-க்கு முன் ஒத்திசைக்கவும்.** செயலில் உள்ள base-ஐ fetch செய்து, அதன் புதிய commits மற்றும் அதனுடன் ஒப்பிடப்பட்ட உங்கள் diff-ஐப்
   பரிசோதித்து, பின்னர் contributor workflow-க்கு ஏற்ப base-ஐ rebase அல்லது merge செய்யவும். generated-file
   மற்றும் catalog conflicts-ஐ அவற்றின் source-இலிருந்து தீர்த்து, அவற்றை regenerate செய்து, focused loop-ஐ மீண்டும் இயக்கி,
   PR இன்னும் செயலில் உள்ள release branch-ஐ target செய்கிறது என்பதை உறுதிப்படுத்தவும்.
6. **ஆதாரத்தைப் பதிவுசெய்யவும்.** PR template-இல், இயக்கப்பட்ட commands, சேர்க்கப்பட்ட அல்லது மாற்றப்பட்ட ஒவ்வொரு test file,
   migrations அல்லது feature flags மற்றும் இன்னும் நிலுவையில் உள்ள CI-only validation ஆகியவற்றைப் பட்டியலிடவும்.

## மாற்ற வகையின் அடிப்படையிலான Golden paths

கீழேயுள்ள commands குறைந்தபட்ச focused checks ஆகும்; நீங்கள் மாற்றிய நடத்தையை நேரடியாகச் சோதிக்கும் test-ஐத்
தவிர்ப்பதற்கான அனுமதி அல்ல.

### Provider

**Contracts**

- `src/shared/constants/providers/`-இல் உள்ள Provider definition மற்றும்
  `src/shared/constants/providers.ts`-இல் அதன் composition.
- `open-sse/config/providerRegistry.ts` அல்லது அதிலிருந்து பிரிக்கப்பட்ட registry files-இல் உள்ள Models மற்றும் capabilities.
- Executor/translator selection, OAuth அல்லது API-key configuration, dashboard assets மற்றும் பொருந்தும்போது generated
  provider reference.
- Public credentials, `resolvePublicCred()`-ஐப் பயன்படுத்த வேண்டும்; error responses, பகிரப்பட்ட sanitized
  error helpers-ஐப் பயன்படுத்த வேண்டும். `docs/security/PUBLIC_CREDS.md` (git; `/docs`-க்குள் compile செய்யப்படாது) மற்றும்
  [Error Sanitization](../security/ERROR_SANITIZATION.md)-ஐப் பார்க்கவும்.

**Focused loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog மாறும்போது; generated diff-ஐ commit செய்யவும்
npm run lint
```

பாதிக்கப்பட்ட ஒவ்வொரு request family-ஐயும் சோதிக்கவும்: chat, Responses, images, embeddings, audio அல்லது video.
Generated catalog மற்றும் golden diffs-ஐ contract மாற்றங்களாக review செய்யவும்; அவற்றைக் கண்மூடித்தனமாக ஏற்க வேண்டாம்.

### Routing

**Contracts**

- `src/shared/constants/routingStrategies.ts`-இல் உள்ள Public strategy values மற்றும் UI metadata.
- `open-sse/services/combo.ts` மற்றும் `open-sse/services/combo/`-இன் கீழ் உள்ள Dispatch மற்றும் ordering.
- Combo schemas, persistence, resilience state, model capabilities மற்றும் API/UI controls.
- நடத்தை மாறும்போது [Auto-Combo Engine](../routing/AUTO-COMBO.md) மற்றும் resilience documentation.

**Focused loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy அல்லது dispatch மாற்றங்கள்
npm run check:known-symbols      # strategy registration மாற்றங்கள்
npm run lint
```

உள்ளூரில் deterministic mocked-upstream tests-ஐப் பயன்படுத்தவும். Live combo smokes-க்கு credentials தேவை; அவை
manual சோதனைகள், CI-க்கு மாற்றீடுகள் அல்ல.

### UI / UX

**Contracts**

- `src/app/` மற்றும் `src/shared/components/`-இன் கீழ் உள்ள Next.js route/page மற்றும் shared component boundaries.
- API response shapes, loading/empty/error states, keyboard மற்றும் screen-reader நடத்தை,
  responsive layout, theming மற்றும் locale expansion.
- `src/i18n/messages/en.json`-இல் உள்ள English UI source strings; பயனருக்குக் காட்டப்படும் புதிய உரையை hard-code செய்ய வேண்டாம்.

**Focused loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction அல்லது visual மாற்றங்களுக்கு app-ஐ இயக்கி, narrow மற்றும் wide viewports இரண்டையும் சரிபார்க்கவும். CI,
production build மற்றும் பரந்த suites-ஐ இயக்கும்; visual நடத்தைக்கு இன்னும் மாற்றத்திற்குப் பொருத்தமான focused component, Playwright
அல்லது ஆவணப்படுத்தப்பட்ட manual check தேவை.

### i18n

**Contracts**

- `src/i18n/messages/en.json` என்பது UI source; `config/i18n.json` என்பது locale source.
- CLI catalogs, `bin/cli/locales/`-இன் கீழ் தனியாக உள்ளன.
- ICU placeholders மற்றும் tags-ஐ அப்படியே பாதுகாக்கவும். product/provider/model names,
  protocol மற்றும் header names, commands, code/JSON identifiers, URLs, environment variables அல்லது
  `OmniRoute`, `OAuth`, `MCP` மற்றும் `A2A` போன்ற protected terms-ஐ மொழிபெயர்க்க வேண்டாம். தற்போதைய source list
  `scripts/i18n/glossary/protected-terms.json` ஆகும்.

**Focused loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI strings/catalogs மாறும்போது
npm run lint
```

இது தற்போதுள்ள system-க்கான வழிகாட்டல்; அதன் tooling அல்லது key model-ஐ விரிவாக்குவதற்கான அழைப்பு அல்ல.
மாற்று system வடிவமைக்கப்பட்டுக் கொண்டிருக்கும் நிலையில் i18n patches-ஐத் துல்லியமான குறுகிய வரம்பில் வைத்திருக்கவும். task வெளிப்படையாக generated translations-ஐக் கோருவதோடு,
அதன் விளைவாக உருவான diff-ஐ நீங்கள் review செய்திருந்தால் மட்டுமே, external services-ஐ அழைக்கும் translation
commands-ஐ இயக்கவும்.

### CLI

**Contracts**

- `bin/cli/`-இல் உள்ள பொதுக் கட்டளைகள் மற்றும் கொடிகள், உருவாக்கப்பட்ட API கட்டளைகள், வெளியேறும் குறியீடுகள், stdout/stderr மற்றும்
  JSON வெளியீட்டு வடிவங்கள், config/environment நடத்தை, மேலும் தொகுப்பில் சேர்க்கப்பட்ட கோப்புகள்.
- CLI பயனருக்குக் காட்டப்படும் சரங்கள் CLI i18n அடுக்கைப் பயன்படுத்த வேண்டும்; மேலும் `en`/`pt-BR` பட்டியல்கள் ஒத்திசைவாக இருக்க வேண்டும்.
- ஆதரிக்கப்படும் இயக்கநேரமாக Node-ஐயும், வெளியிடப்பட்ட binary ஒப்பந்தத்தையும் அப்படியே பேணவும்.

**கவனம் செலுத்திய சுழற்சி**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # உருவாக்கப்பட்ட/தொகுக்கப்பட்ட CLI மாற்றங்கள்
npm run check:pack-policy     # தொகுப்பு-மேற்பரப்பு மாற்றங்கள்
npm run lint
```

நடத்தை parsing, கோப்புகள் அல்லது வெளியேறும் நிலையைச் சார்ந்திருக்கும்போது, ஒரு தற்காலிகத் தரவுக் கோப்பகத்தில் துல்லியமான கட்டளையைப் பயன்படுத்தவும்.
CI விரிவான தொகுப்பு artifact மற்றும் ecosystem சோதனைகளைச் செய்கிறது.

### தரவுத்தளம்

**ஒப்பந்தங்கள்**

- `src/lib/db/`-இன் கீழுள்ள domain தொகுதிகள்; குறிப்பிட்ட தொகுதிகளை நேரடியாக import செய்யவும் (பழைய `localDb.ts` மறு-export அடுக்கு அகற்றப்பட்டது).
- `src/lib/db/migrations/`-இன் கீழ் எண்ணிடப்பட்ட, மீண்டும் இயக்கினாலும் அதே விளைவைத் தரும் SQL migrations, transaction பாதுகாப்பு, upgrade
  நடத்தை, indexes, மற்றும் schema-வால் பாதிக்கப்படும் ஒவ்வொரு caller-உம்.
- Routes மற்றும் handlers ஒருபோதும் raw SQL-ஐ நேரடியாக இயக்கக்கூடாது.

**கவனம் செலுத்திய சுழற்சி**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

ஒரு migration-ஐச் சேர்க்கும்போது, புதிய தரவுத்தளம் மற்றும் முந்தைய schema-விலிருந்து upgrade செய்வது ஆகிய இரண்டையும் சோதிக்கவும். தரவுத்தளச் சோதனைகள்
handles-ஐ மூடி, cleanup செய்யும்போது `resetDbInstance()`-ஐ அழைக்க வேண்டும். best-effort Bun adapter பாதை மாறும்போது மட்டும்
`npm run test:bun:db`-ஐ இயக்கவும்; Node தான் அதிகாரப்பூர்வமானது.

### Build / deploy

**ஒப்பந்தங்கள்**

- Root மற்றும் workspace manifests/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/`
  தொகுப்பு உள்ளடக்கங்கள், Electron platform metadata, CI workflows, மற்றும் deployment sentinels.
- ஆதரிக்கப்படும் Node வரம்புகளும் `CLAUDE.md`-இல் அனுமதிப்பட்டியலில் உள்ள Bun பயன்பாடும் அப்படியே இருக்க வேண்டும்.
- Build artifacts கண்காணிக்கப்படாமல் இருக்க வேண்டும்; dependency, license, workflow மற்றும் package கொள்கைகள் பொருந்தும்.

**கவனம் செலுத்திய சுழற்சி**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency அல்லது lockfile மாற்றங்கள்
npm run check:pack-policy      # வெளியிடப்பட்ட தொகுப்பு மேற்பரப்பு மாற்றங்கள்
npm run lint
```

மாற்றம் compilation, standalone assembly, assets அல்லது runtime bundling-ஐப் பாதிக்கும்போது மட்டும் உள்ளூரில் `npm run build`-ஐப் பயன்படுத்தவும்.
Release/deploy சரிபார்ப்புக்கு மட்டும் `npm run build:release`-ஐப் பயன்படுத்தவும். CI-இன் build தான் இறுதியான cross-platform அறிகுறி;
platform-சார்ந்த Electron மாற்றங்களுக்கு அதனுடன் பொருந்தும் கவனம் செலுத்திய build அல்லது smoke சோதனைச் சான்று தேவை.

## உள்ளக candidate சுழற்சி

தொகுக்கப்பட்ட artifact இயங்கத் தொடங்கும் என்பதை source சோதனைகளால் நிரூபிக்க முடியாது: packaging பட்டியல்கள், நீக்கப்பட்ட dependencies,
மற்றும் native binaries ஆகியவை tarball நிறுவப்பட்டு தொடங்கப்பட்ட பின்னரே தோல்வியடையும். `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) என்பது RFC #8084-இல் உள்ள ஒருமுறை build செய்தல் / சரிபார்த்தல் / promote செய்தல் ஓட்டத்தின்
உள்ளகப் பகுதியாகும்: இது ஒரு candidate-ஐ build செய்து, அதே artifact-ஐச் சரிபார்த்து, directory பெயர்
மாற்றங்கள் மூலம் அதை promote செய்கிறது; மேலும் promote செய்யப்பட்ட slot அதன் health check-இல் தோல்வியடைந்தால்
அதை rollback செய்கிறது.

```bash
npm run dev:candidate -- run --dry-run --json  # திட்டத்தை அச்சிடும்; எதையும் மாற்றாது
npm run dev:candidate -- run                   # build + சரிபார்ப்பு + promote, தானியங்கி rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ இல் நிறுவுதல்
npm run dev:candidate -- validate --id <id>    # காலியான port-இல் தொடங்கி, /api/health + /v1/models ஐச் சரிபார்த்தல்
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current மற்றும் previous ஐ இடமாற்றுதல்
npm run dev:candidate -- run --from-tarball <file.tgz>  # வேறொரு இடத்தில் (CI) build செய்யப்பட்ட tarball-ஐ மீண்டும் பயன்படுத்துதல்
```

- **ஒருமுறை build செய்யவும்.** `build` தற்போதைய tree-ஐ pack செய்கிறது (இதற்கு `dist/server.js` தேவைப்படுவதால், முதலில்
  `npm run build:release`-ஐ இயக்கவும்) அல்லது `--from-tarball`-ஐ நகலெடுக்கிறது; பின்னர் tarball-இல்
  `node_modules` இல்லாததால், அதைத் தனிமைப்படுத்தப்பட்ட npm prefix-இல் நிறுவுகிறது. id என்பது சுருக்கமான `HEAD`
  sha (tree-இல் உள்ளக மாற்றங்கள் இருந்தால் `-dirty`) அல்லது tarball-க்கான `tgz-<sha256>` ஆகும். ஏற்கெனவே
  build செய்யப்பட்ட clean id, மீண்டும் build செய்யப்படுவதற்குப் பதிலாக மறுபயன்பாடு செய்யப்படும்; அதை மீண்டும்
  build செய்ய `--force`-ஐ வழங்கவும்.
- **Source-ஐ அல்ல, package-ஐச் சரிபார்க்கவும்.** `validate`, நிறுவப்பட்ட CLI-ஐ
  (`serve --port <free port>`) புதிய `DATA_DIR=<candidate>/data`, போலியான secrets ஆகியவற்றுடன் தொடங்குகிறது;
  மேலும் operator-இன் `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` மற்றும் `INITIAL_PASSWORD` ஆகியவற்றை
  environment-இலிருந்து அகற்றுகிறது. இதனால் புதிய installation-இன் key இல்லாத loopback நிலைப்பாடு
  சரிபார்க்கப்படுகிறது. இது `GET /api/health` 200-ஐத் திருப்பும் வரை காத்திருந்து, `GET /v1/models` 200-ஐத்
  திருப்ப வேண்டும் எனக் கோருகிறது, process group-ஐ நிறுத்துகிறது, மேலும் tarball hash-உடன் முடிவை
  `validation.json`-இல் பதிவுசெய்கிறது.
- **அதே artifact-ஐ promote செய்யவும்.** தற்போதைய tarball hash-க்கான வெற்றிகரமான validation இல்லாத
  candidate-ஐ `promote` நிராகரிக்கிறது. இயல்புநிலை active slot `_artifacts/candidate/current` ஆகும்;
  `--target <dir>` அதே filesystem-இல் மற்றொரு directory-ஐத் தேர்ந்தெடுக்கிறது, மேலும் அதன் previous slot
  `<dir>.previous` ஆகும். ஒவ்வொரு rename-உம் atomic ஆகும்; இடையில் தோல்வி ஏற்பட்டால், ஏற்கெனவே செய்யப்பட்ட
  rename-கள் எதிர்த்திசையில் மீளமைக்கப்படும்.
- **Rollback செய்யவும்.** `run`, promote செய்யப்பட்ட slot-ஐ மீண்டும் சரிபார்த்து, அந்தச் சோதனை தோல்வியடைந்தால்
  `current` மற்றும் `previous` ஆகியவற்றை மீண்டும் இடமாற்றுகிறது. முதல் validation-இல் தோல்வியடையும் candidate
  ஒருபோதும் promote செய்யப்படாது.

அனைத்தும் gitignore செய்யப்பட்ட `_artifacts/candidate/`-இன் கீழ் எழுதப்படும்; ஏற்கெனவே உள்ள OmniRoute
installation மற்றும் அதன் data directory ஒருபோதும் தொடப்படாது. Promote செய்யப்பட்ட CLI
`_artifacts/candidate/current/prefix/bin/omniroute` ஆகும்; அதைப் பயன்படுத்தும்போது உங்கள் சொந்த `DATA_DIR`-உடன்
அதைத் தொடங்கவும். Exit codes: வெற்றிக்கு `0`, validation அல்லது promotion தோல்விக்கு `1`, usage error அல்லது
build காணப்படாததற்கு `2`.

## உள்ளூர் சுழற்சியும் CI-யும்

| ஒவ்வொரு patch-க்கும் உள்ளூரில் இயக்க வேண்டியவை                                       | CI வழங்கும் விரிவான சமிக்ஞை                                                  |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| மேலே உள்ள நேரடி நடத்தைச் சோதனைகளும் வகைத் தடைகளும்                                   | பிரிக்கப்பட்ட முழுமையான unit suite மற்றும் தொடர் சோதனைகள்                    |
| `npm run lint`                                                                       | Vitest suite-கள் மற்றும் coverage/quality ratchet-கள்                        |
| பாதிக்கப்பட்ட contract தேவைப்படும்போது மட்டும் typecheck அல்லது build                | Production build, security, docs, dependency மற்றும் PR-policy தடைகள்        |
| automation மூலம் நடத்தையை நிரூபிக்க முடியாதபோது மட்டும் கைமுறை தொடர்பு/live சோதனைகள் | workflow-ஆல் உள்ளமைக்கப்பட்ட cross-job integration மற்றும் platform சோதனைகள் |

பச்சை நிலையில் உள்ள கவனம் செலுத்தப்பட்ட சுழற்சி, மாற்றப்பட்ட contract குறித்த ஆதாரமாகும்; தொடர்பில்லாத CI சோதனைகள்
வெற்றிபெறும் என்பதற்கான நிரூபணம் அல்ல. அதேபோல், ஒவ்வொரு உள்ளூர் திருத்தமும் முழு repository matrix-க்காகக் காத்திருக்குமாறு செய்யாதீர்கள்.

## ஒத்திசைவுச் சரிபார்ப்புப் பட்டியல்

மதிப்பாய்வைக் கோருவதற்கு முன்:

- PR base இன்னும் செயலிலுள்ள உயர்ந்த `release/v*` branch என்பதை உறுதிப்படுத்தவும்.
- அந்த base-ஐ fetch செய்து, நீங்கள் branch செய்ததிலிருந்து சேர்க்கப்பட்ட commit-களை மதிப்பாய்வு செய்யவும்.
- தற்செயலான அல்லது உருவாக்கப்பட்ட தேவையற்ற மாற்றங்களுக்காக `git diff <active-base>...HEAD`-ஐ மதிப்பாய்வு செய்யவும்.
- மூலத்தைப் புதுப்பித்து output-ஐ மீண்டும் உருவாக்குவதன் மூலம் catalog மற்றும் உருவாக்கப்பட்ட-document முரண்பாடுகளைத் தீர்க்கவும்.
- ஒத்திசைவுக்குப் பிறகு PR விளக்கத்தில் பட்டியலிடப்பட்டுள்ள ஒவ்வொரு கவனம் செலுத்தப்பட்ட test/gate-ஐயும் மீண்டும் இயக்கவும்.
- நகர்த்தப்பட்ட base-உடன் பொருந்துவதற்காக assertions-ஐ ஒருபோதும் பலவீனப்படுத்தாதீர்கள் அல்லது தேவையான test-களை நீக்காதீர்கள்.

release-freeze மற்றும் retargeting விதிகளுக்கு,
[Branching & Release Model](BRANCHING_MODEL.md)-ஐப் பயன்படுத்தவும். முழுமையான CI பட்டியலுக்கு,
[Quality Gates Reference](../architecture/QUALITY_GATES.md)-ஐப் பயன்படுத்தவும்.
