## மேலோட்டம்

அனைத்து OmniRoute மேலாண்மை API வழிகளும் மூன்று பாதுகாப்பு
அடுக்குகளில் ஒன்றாக வகைப்படுத்தப்படுகின்றன. வகைப்பாடு நிலையானது,
`src/server/authz/routeGuard.ts`-இல் வரையறுக்கப்பட்டு, வேறு எந்த அங்கீகாரக்
கிளையும் இயங்குவதற்கு முன் மதிப்பீடு செய்யப்படுகிறது.

## அடுக்குகள்

### அடுக்கு 1 — LOCAL_ONLY

**செயல்படுத்தப்படுவது:** `isLocalOnlyPath(path)` → loopback host சரிபார்ப்பு  
**தவிர்ப்பு:** இயல்புநிலையில் எதுவுமில்லை. கோரிக்கையில் `manage` scope கொண்ட செல்லுபடியாகும் API key இருந்தால், `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-இல் உள்ள பாதைகளுக்கு மட்டும் குறுகிய விதிவிலக்கு வழங்கப்படும் ([Manage-scope விதிவிலக்கு](#manage-scope-carve-out) என்பதைப் பார்க்கவும்).

இந்த routes, child processes-ஐத் தொடங்குகின்றன அல்லது runtime code-ஐ இயக்குகின்றன. இவற்றை loopback அல்லாத traffic-க்கு வெளிப்படுத்துவது, செல்லுபடியாகும் JWT-ஐப் பெற்ற தாக்குதலாளரை (எ.கா., Cloudflared/Ngrok tunnel வழியாக) process spawning-ஐத் தூண்ட அனுமதிக்கும் — இது அறியப்பட்ட ஒரு CVE வகையாகும் ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj என்றால் என்ன (தாக்குதல் வகை):** ஒரு management/agent server, subprocess ஒன்றைத் தொடங்கும் endpoint-ஐ வெளிப்படுத்துகிறது (`npm install`, `node`, ஒரு browser, ஒரு proxy, `git`, `tar`, …). அந்த endpoint-ஐ host-க்கு வெளியிலிருந்து அணுக முடிந்தால் — operator, OmniRoute-ஐ nginx/Cloudflare/Tailscale tunnel-க்குப் பின்னால் வைத்திருந்து JWT கசிந்ததாலோ அல்லது auth தவறாக உள்ளமைக்கப்பட்டதாலோ — தாக்குதலாளர் "API-ஐ அழைப்பது" என்பதை "host-இல் command ஒன்றை இயக்குவது" (remote code execution) என்பதாக மாற்றுகிறார். spawn செய்யக்கூடிய ஒவ்வொரு route-இலும், **எந்த auth சரிபார்ப்புக்கும் முன்பாக, நிபந்தனையின்றி loopback host சரிபார்ப்பைச் செயல்படுத்துவதன் மூலம்** OmniRoute இதைத் தடுக்கிறது: tunnel வழியாகக் கசிந்த token-ஆல் கூட spawn-ஐ அணுக முடியாது.

**முழுமையான LOCAL_ONLY தொகுப்பு.** இதற்கான அதிகாரப்பூர்வ மூலம் `src/server/authz/routeGuard.ts`-இல் உள்ள `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ஆகும்; கீழேயுள்ள அட்டவணை தற்போதைய நிலையைக் பிரதிபலிக்கிறது. `check-route-guard-membership` gate, spawn செய்யக்கூடிய prefixes-இன் கீழ் உள்ள ஒவ்வொரு `route.ts`-ஐயும் கணக்கிட்டு, அவற்றில் ஏதேனும் local-only என வகைப்படுத்தப்படாமல் இருந்தால் CI-ஐத் தோல்வியடையச் செய்கிறது.

#### நிர்வாக-scope விதிவிலக்கு

LOCAL_ONLY பாதைகளின் ஒரு துணைத்தொகுப்பை loopback அல்லாத இடத்திலிருந்தும் அணுகலாம், ஆனால்
கோரிக்கையில் `Authorization: Bearer <api-key>` இருக்க வேண்டும், மேலும் அதன்
metadata-வில் `manage` scope (அல்லது `admin`) இடம்பெற்றிருக்க வேண்டும். இந்த விதிவிலக்கு
ஒவ்வொரு பாதைக்கும் `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` வழியாக வெளிப்படையாகக்
கட்டுப்படுத்தப்படுகிறது; எனவே எந்தப் புதிய LOCAL_ONLY பாதைக்கும் இயல்புநிலை கடுமையான-loopback
ஆகவே இருக்கும். அங்கீகரிக்கப்படாத கோரிக்கைகளும் manage அல்லாத keys கொண்ட கோரிக்கைகளும்
இன்னும் `403 LOCAL_ONLY` மூலம் நிராகரிக்கப்படும்.

தற்போது விதிவிலக்கைப் பயன்படுத்தக்கூடிய ஒரே prefix `/api/mcp/` ஆகும். `/api/cli-tools/runtime/` மற்றும்
`/api/services/` ஆகியவை வேண்டுமென்றே விலக்கப்பட்டுள்ளன, ஏனெனில் அவை தன்னிச்சையான
துணைச் செயல்முறைகளை (`npm install`, `node`) தொடங்கக்கூடும்; இதுவே
LOCAL_ONLY அடுக்கு தடுப்பதற்காக உள்ள துல்லியமான CVE வகையாகும்.

**#7895 — `mcp:connect` குறுகிய scope:** `/api/mcp/` விதிவிலக்கு,
குறுகிய `mcp:connect` scope-ஐக் கொண்ட Bearer key-ஐயும் ஏற்கிறது
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), இது
`src/server/authz/policies/management.ts`-இல் உள்ள `hasMcpConnectOrManageScope()` வழியாகச்
சரிபார்க்கப்படுகிறது. இது `/api/mcp/`-க்கு மட்டுமே வரையறுக்கப்பட்டுள்ளது — வேறு எந்த
நிர்வாகப் பாதையிலும் `mcp:connect` எதையும் வழங்காது (எதிர்காலத்தில் சேர்க்கப்படக்கூடிய
மற்ற எல்லா LOCAL_ONLY bypass prefix-களும் உட்பட), மேலும் இது வேண்டுமென்றே
`MANAGEMENT_API_KEY_SCOPES`-இலிருந்து விலக்கப்பட்டுள்ளது. `manage`/`admin` கொண்ட key,
முன்பு போலவே விதிவிலக்கைத் தாண்டும்; விரிவான நிர்வாக அணுகல் தேவையில்லாத
தொலைநிலை MCP-மட்டும் அழைப்பாளர்களுக்கான குறைந்த-சலுகை மாற்றாக `mcp:connect` உள்ளது.

#### இயக்குநர் வழிகாட்டுதலும் தணிக்கையும்

நீங்கள் OmniRoute-ஐ reverse proxy அல்லது tunnel-க்குப் பின்னால் (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) இயக்கினால், மேலுள்ள செயல்முறைகளைத் தொடங்கக்கூடிய பாதைகளை
loopback சரிபார்ப்பு தொடர்ந்து பாதுகாக்கும் — client address loopback அல்லாத ஒரு கோரிக்கை
**அங்கீகாரம் இயங்குவதற்கு முன்பே** `403 LOCAL_ONLY` மூலம் நிராகரிக்கப்படும்; எனவே கசிந்த JWT-யால்
ஒரு செயல்முறைத் தொடக்கத்தை அடைய முடியாது. இயக்குநருக்கு இன்னும் இரண்டு பொறுப்புகள் உள்ளன:

- **Client IP-ஐ loopback ஆகப் போலியாக அமைத்து 403-ஐ "சரி செய்யாதீர்கள்".**
  `X-Forwarded-For: 127.0.0.1`-ஐ அமைப்பது அல்லது source address-ஐ loopback ஆக
  மாற்றி எழுதும் proxy-ஐப் பயன்படுத்துவது, இந்த அடுக்கு மூடும் அதே RCE வகையை மீண்டும் திறக்கும்.
  Proxy வழியாக டாஷ்போர்டு/API-ஐ வெளிப்படுத்துங்கள் — செயல்முறைகளைத் தொடங்கக்கூடிய பாதைகளை ஒருபோதும் வெளிப்படுத்தாதீர்கள்.
- **Manage-scope bypass-ஐக் குறைந்தபட்சமாக வைத்திருங்கள்.** `/api/mcp/` மட்டுமே bypass செய்யக்கூடியது,
  அதுவும் `manage`-scope கொண்ட API key மூலம் மட்டுமே. `SPAWN_CAPABLE_PREFIXES`-ஐ bypass
  பட்டியலில் ஒருபோதும் சேர்க்க முடியாது — zod schema அவற்றை நிராகரிக்கிறது, மேலும்
  runtime-இல் `isLocalOnlyBypassableByManageScope` அவற்றை மறுக்கிறது (பல-அடுக்கு பாதுகாப்பு);
  இதைத்தான் டாஷ்போர்டில் "bypass செய்யக்கூடியதாக மாற்ற முடியாது" என்பது குறிக்கிறது. `/api/providers/`-இன் கீழுள்ள
  dynamic-segment மற்றும் static-path செயல்முறைகளைத் தொடங்கக்கூடிய பாதைகள் (எ.கா. `/login`,
  `/refresh-cursor`) `src/shared/constants/spawnCapablePrefixes.ts`-இல் உள்ள regex-அடிப்படையிலான
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` துணை அமைப்பால்
  கையாளப்படுகின்றன; சமதளமான `SPAWN_CAPABLE_PREFIXES` array-ஆல் அல்ல — அவற்றைப் பிடிக்க
  சமதள array முழு `/api/providers/` prefix-ஐ உள்ளடக்க வேண்டியிருக்கும்; இது provider CRUD-க்காக
  தொலைநிலை டாஷ்போர்டுகள் சட்டபூர்வமாகப் பயன்படுத்தும் route tree-ஐ அளவுக்கு மீறி விரிவாகக் கட்டுப்படுத்திவிடும்.

**அணுகலைத் தணிக்கை செய்தல்** — host-க்கு வெளியிலிருந்து எதுவும் இந்தப் பாதைகளை அடையவில்லை என்பதைச் சரிபார்க்க:

- `/dashboard/settings/security` இல் உள்ள **அங்கீகார இன்வென்டரியை** திறக்கவும்: இது நேரடி
  LOCAL_ONLY முன்னொட்டுப் பட்டியல், எந்த முன்னொட்டுகளைத் தவிர்க்க முடியும், மற்றும் தொகுத்தல்-நேரத்தில்
  செயல்முறைகளைத் தொடங்கக்கூடிய ("தவிர்க்கக்கூடியவையாக மாற்ற முடியாது") தொகுப்பு ஆகியவற்றைக் காட்டுகிறது.
- மேலே உள்ள முன்னொட்டுகளுடன் loopback அல்லாத கிளையன்ட் முகவரி இணைந்துள்ளதா என உங்கள்
  reverse-proxy / அணுகல் பதிவுகளில் grep செய்யவும். `403 LOCAL_ONLY` என்பதற்குப் பதிலாக
  `200` வழங்கிய அத்தகைய எந்தப் பதிவும் proxy உண்மையான கிளையன்ட் IP-ஐ மறைக்கிறது என்பதைக்
  குறிக்கிறது — proxy-ஐச் சரிசெய்யவும்.
- இந்தப் பாதைகளில் ஒன்றுக்காக OmniRoute-இன் பதிவுகளில் தோன்றும் `403 LOCAL_ONLY` என்பது guard
  நோக்கம்போலச் செயல்படுவதைக் குறிக்கிறது; அடக்க வேண்டிய பிழை அல்ல.

### அடுக்கு 2 — ALWAYS_PROTECTED

**செயல்படுத்துவது:** `isAlwaysProtectedPath(path)` → `requireLogin=false` தவிர்ப்பைத் தாண்டிச் செல்லும்
**தவிர்த்தல்:** `requireLogin=false` ஆக இருக்கும்போது எதுவுமில்லை; JWT எப்போதும் தேவை

இந்த routes அழிவை ஏற்படுத்துபவை அல்லது மீளமுடியாதவை. "கடவுச்சொல் இல்லாத"
நிறுவலில் இவற்றை அனுமதிப்பது, அதே LAN-இல் உள்ள யார் வேண்டுமானாலும் தரவுத்தளத்தை அழிக்கவோ
server process-ஐ நிறுத்தவோ முடியும் என்பதைக் குறிக்கும்.

| பாதை                                      | காரணம்                                                                            |
| ----------------------------------------- | --------------------------------------------------------------------------------- |
| `/api/shutdown`                           | server process-ஐ நிறுத்துகிறது                                                    |
| `/api/settings/database`                  | தரவுத்தள ஏற்றுமதி, இறக்குமதி மற்றும் அழித்தல்                                     |
| `/api/db-backups`                         | முழு தரவுத்தளக் காப்பகத்தை அணுகுதல்                                               |
| `/api/settings/export-json`               | முழு settings blob-ஐ ஏற்றுமதி செய்கிறது (ரகசியங்கள் உட்பட)                        |
| `/api/settings/import-json`               | முழு settings blob-ஐ மாற்றுகிறது                                                  |
| `/api/providers/health-autopilot/actions` | autopilot தீர்வு நடவடிக்கைகளைச் செயல்படுத்துகிறது                                 |
| `/api/settings/obsidian`                  | எந்த vault root-க்கும் மீண்டும் பயன்படுத்தக்கூடிய WebDAV சான்றுகளை உருவாக்குகிறது |

**மீறலின்போதான பதில்:** `401 Authentication required`

`/api/settings/obsidian` அதன் `/webdav` child-ஐ உள்ளடக்குகிறது: `POST`, இந்த pipeline-க்கு வெளியே
Next.js-க்கு முன்பாகத் தனிப்பயன் Node layer மூலம் வழங்கப்படும் WebDAV file service-ஐ,
அழைப்பவர் தேர்ந்தெடுத்த root-ஐ நோக்கச் செய்து, புதிதாக உருவாக்கப்பட்ட Basic சான்றுகளைத் திருப்பியளிக்கிறது;
`DELETE` அவற்றைச் சுழற்சி முறையில் மாற்றுகிறது, மேலும் parent `POST` Obsidian REST API token-ஐச் சேமிக்கிறது.
GHSA-62vw ஆனது `GET` கடவுச்சொல் வெளிப்பாட்டை மட்டுமே மறைத்தது; சான்றுகளை வழங்குதல் இன்னும் fail-open
அடுக்கிலேயே இருந்தது (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` கூடுதலாக, data directory ஆகவோ,
அதன் உள்ளேயோ, அல்லது அதை உள்ளடக்கியதாகவோ இருக்கும் vault-ஐ மறுக்கிறது.

### புதிய நிறுவலின் bootstrap உண்மையான peer அடிப்படையில் loopback-க்கு மட்டுமே — `Host` அடிப்படையில் அல்ல

management password எதுவும் கட்டமைக்கப்படாமல் (மேலும் `INITIAL_PASSWORD` இல்லாமல்) இருக்கும்போது,
`src/shared/utils/apiAuth.ts` இல் உள்ள `isAuthRequired()` அநாமதேய bootstrap-ஐ **loopback peers-க்கு மட்டுமே**
திறந்து வைக்கிறது. நம்பகமான peer signals-இலிருந்து பின்வரும் வரிசையில் loopback தீர்மானிக்கப்படுகிறது:
token முத்திரையிடப்பட்ட உண்மையான TCP peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, policy காண்பது),
pipeline-இன் சொந்த `AUTHZ_HEADER_PEER_LOCALITY` தீர்ப்பு (route handlers காண்பது,
`OMNIROUTE_PEER_STAMP_TOKEN` அமைக்கப்பட்டிருக்கும் வரை மட்டுமே நம்பப்படும்), அல்லது நேரடியாக
அழைப்பவர்களுக்கான உண்மையான socket peer. `Host` / `nextUrl.hostname` ஒருபோதும் பரிசீலிக்கப்படாது;
மேலும் முதல் கடவுச்சொல்லை எழுதுவதும் (`POST /api/settings/require-login`) ஒவ்வொரு network peer-க்கும்
திறந்துவிடப்படாமல் இதே கட்டுப்பாட்டின் கீழ் உள்ளது (GHSA-7pq4-8pvv-rx7r). `managementPolicy` தனது
சொந்த `peerContext` தீர்ப்பைத் தெளிவாகக் கீழே அனுப்புவதால், ORIGINAL (நீக்கப்படுவதற்கு முந்தைய)
request-இன் headers அதை ஒருபோதும் தீர்மானிப்பதில்லை.

### அடுக்கு 3 — MANAGEMENT (இயல்புநிலை)

மற்ற அனைத்து management routes-உம் இதில் அடங்கும். `requireLogin=false` எனக்
கட்டமைக்கப்படாவிட்டால் authentication தேவை. CLI tokens இந்த routes-ஐ authenticate செய்யலாம்
(loopback + செல்லுபடியாகும் HMAC).

## மதிப்பீட்டு வரிசை

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → அடுத்த படிக்குச் செல்
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → அனுமதி (management_key)
     → இல்லையெனில்                                → நிராகரி 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → அனுமதி (system)
  3. hasValidCliToken(headers)?
     → அனுமதி (cli) [loopback + timingSafeEqual HMAC சரிபார்ப்பு]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → அனுமதி (dashboard_session)
     → தளர்த்த முடியாத பாதையில் manage-scope Bearer உள்ளதா?
        → அனுமதி (management_key)
     → நிராகரி 401/403
  5. requireLogin=false?
     → அனுமதி (anonymous)
```

படி 1-இன் manage-scope கிளை மட்டுமே LOCAL_ONLY வழித்தடத்தைப் பூர்த்திசெய்யக்கூடிய அங்கீகரிக்கப்பட்ட பாதையாகும்; காலாவதியான DB அமைதியாக "deny" நிலைக்குத் தாழ்த்தப்படாமல் இருக்க, auth-backend தோல்வி நிலை 503-ஐத் (403 அல்ல) திருப்பியளிக்கிறது.

## உருவாக்கும் திறனுள்ள புதிய வழித்தடத்தைச் சேர்த்தல்

1. `src/server/authz/routeGuard.ts`-இல் உள்ள `LOCAL_ONLY_API_PREFIXES`-க்குப் பாதை முன்னொட்டைச் சேர்க்கவும்
2. புதிய முன்னொட்டுக்கு `isLocalOnlyPath()` true-ஐத் திருப்பியளிக்கிறது என்பதை உறுதிப்படுத்தும் சோதனையை `tests/unit/authz/routeGuard.test.ts`-இல் சேர்க்கவும்
3. **இந்தப் படியை ஒருபோதும் தவிர்க்க வேண்டாம்** — `CLAUDE.md`-இல் உள்ள கடுமையான விதி #15-ஐப் பார்க்கவும்
4. முடிவெடுக்கவும்: இந்த வழித்தடம் `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-லும் இடம்பெற வேண்டுமா?
   இயல்புநிலைப் பதில் **இல்லை**. manage-scope வைத்திருப்பவருக்கு இந்த வழித்தடத்தை வெளிப்படுத்துவது பாதுகாப்பானதாக இருக்கும்போது மட்டுமே இதைத் தேர்வுசெய்யவும் (அதாவது, பயனர் கட்டுப்படுத்தும் தன்னிச்சையான குறியீட்டை இது உருவாக்கக் கூடாது).

## manage-scope மூலம் தளர்த்தக்கூடிய பாதையைச் சேர்த்தல்

1. இந்த வழித்தடம் பயனர் வழங்கிய குறியீடு அல்லது கட்டளைகளைச் செயல்படுத்தவில்லை என்பதை உறுதிப்படுத்தவும். அவ்வாறு செயல்படுத்தினால், நிறுத்தவும் — இந்த விதிவிலக்கு அதற்கான சரியான கருவி அல்ல.
2. `src/server/authz/routeGuard.ts`-இல் உள்ள `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-க்கு முன்னொட்டைச் சேர்க்கவும்
3. பின்வரும் நான்கு கோரிக்கை வடிவங்களுக்கும் `tests/unit/authz/management-policy.test.ts`-இல் சோதனைகளைச் சேர்க்கவும்: Bearer இல்லை (403), manage Bearer (அனுமதி), non-manage Bearer (403), மேலும் manage Bearer இருந்தாலும் `/api/cli-tools/runtime/*` strict-loopback ஆகவே இருப்பதை உறுதிப்படுத்தும் ஒவ்வொரு முன்னொட்டுக்குமான பின்னடைவு சோதனை.

## OpenAPI-இல் பாதுகாப்பு அடுக்குகளை ஆவணப்படுத்துதல்

`docs/openapi.yaml`-இல் புதிய வழித்தடத்தைச் சேர்க்கும்போது, அந்த வழித்தடம் `routeGuard.ts` மூலம் வகைப்படுத்தப்பட்டிருந்தால், அதற்குரிய vendor extension-ஐப் பயன்படுத்தவும்:

| routeGuard.ts வகைப்பாடு                 | YAML குறிப்பு              | அமலாக்கம்                                                |
| --------------------------------------- | -------------------------- | -------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`               | `x-loopback-only: true`    | non-loopback-இலிருந்து நிபந்தனையின்றித் தடுக்கப்படும்    |
| `ALWAYS_PROTECTED_API_PATHS`            | `x-always-protected: true` | `requireLogin=false` ஆக இருந்தாலும் அங்கீகாரம் தேவை      |
| உள் admin/debug வழித்தடம்               | `x-internal: true`         | இயல்பாக /dashboard/api-endpoints-இலிருந்து மறைக்கப்படும் |
| எதுவுமில்லை (பொது / நிலையான அங்கீகாரம்) | (குறிப்பு தேவையில்லை)      | நிலையான `requireLogin`-ஆல் கட்டுப்படுத்தப்படும் அணுகல்   |

### சரிபார்ப்பு

YAML குறிப்புகளுக்கும் `routeGuard.ts`-க்கும் இடையிலான ஒத்திசைவை இரண்டு scripts அமல்படுத்துகின்றன:

- `scripts/check/check-openapi-coverage.mjs` — coverage < 99% எனில் தோல்வியடையும்
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` அல்லது
  `x-always-protected` குறிப்புகள் compile-time மாறிலிகளிலிருந்து வேறுபட்டால் தோல்வியடையும்

இரண்டு scripts-உம் pre-commit hook-இலும் CI-இலும் இயங்குகின்றன.

### தவறான நேர்மறை விதி

`routeGuard.ts` மாறிலியில் இல்லாத ஒரு வழித்தடத்தில் `x-always-protected` அல்லது `x-loopback-only` குறிக்கப்பட்டிருந்தால், coverage script தோல்வியடையும். `routeGuard.ts` உண்மையில் அமல்படுத்துவதுடன் YAML-ஐ ஒத்திசைப்பதே எப்போதும் சரியான தீர்வு — அமலாக்கத் தர்க்கத்தையும் சேர்க்காமல் `routeGuard.ts`-க்கு வழித்தடங்களைச் சேர்ப்பது தீர்வல்ல.
