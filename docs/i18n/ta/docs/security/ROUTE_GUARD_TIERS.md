## மேலோட்டம்

அனைத்து OmniRoute மேலாண்மை API வழிகளும் மூன்று பாதுகாப்பு
அடுக்குகளில் ஒன்றாக வகைப்படுத்தப்படுகின்றன. வகைப்பாடு நிலையானது,
`src/server/authz/routeGuard.ts`-இல் வரையறுக்கப்பட்டு, வேறு எந்த அங்கீகாரக்
கிளையும் இயங்குவதற்கு முன் மதிப்பீடு செய்யப்படுகிறது.

## அடுக்குகள்

### அடுக்கு 1 — LOCAL_ONLY

**செயல்படுத்தப்படுவது:** `isLocalOnlyPath(path)` → loopback host சரிபார்ப்பு
**தவிர்த்தல்:** இயல்பாக எதுவுமில்லை. கோரிக்கையில் `manage` scope கொண்ட செல்லுபடியாகும்
API key இருக்கும்போது, `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-இல் உள்ள பாதைகளுக்கு
மட்டும் குறுகிய விதிவிலக்கு உண்டு ([Manage-scope carve-out](#manage-scope-carve-out)-ஐப் பார்க்கவும்).

இந்த வழிகள் child process-களைத் தொடங்குகின்றன அல்லது runtime code-ஐ இயக்குகின்றன.
அவற்றை loopback அல்லாத traffic-க்கு வெளிப்படுத்துவது, செல்லுபடியாகும் JWT-ஐப் பெற்ற
தாக்குநரை (எ.கா., Cloudflared/Ngrok tunnel வழியாக) process-களைத் தொடங்கச் செய்யும் —
இது அறியப்பட்ட ஒரு CVE வகையாகும்
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj என்பது என்ன (தாக்குதல் வகை):** ஒரு மேலாண்மை/agent server,
subprocess ஒன்றைத் தொடங்கும் endpoint-ஐ (`npm install`, `node`, ஒரு browser,
ஒரு proxy, `git`, `tar`, …) வெளிப்படுத்துகிறது. அந்த endpoint-ஐ host-க்கு வெளியிலிருந்து
அணுக முடிந்தால் — operator OmniRoute-ஐ nginx/Cloudflare/Tailscale tunnel-க்குப் பின்னால்
வைத்ததால் மற்றும் JWT கசிந்ததால், அல்லது auth தவறாக உள்ளமைக்கப்பட்டதால் — தாக்குநர்
"API-ஐ அழைப்பது" என்பதை "host-இல் command ஒன்றை இயக்குவது" ஆக மாற்றுகிறார்
(remote code execution). spawn செய்யக்கூடிய ஒவ்வொரு வழியிலும், **வேறு எந்த auth
சரிபார்ப்புக்கும் முன்பாக, நிபந்தனையின்றி loopback host சரிபார்ப்பைச் செயல்படுத்துவதன்**
மூலம் OmniRoute இதைத் தடுக்கிறது: tunnel வழியாகக் கசிந்த token-ஆலும் spawn-ஐ இன்னும்
அணுக முடியாது.

**முழுமையான LOCAL_ONLY தொகுப்பு.** அதிகாரப்பூர்வ ஆதாரம்
`src/server/authz/routeGuard.ts`-இல் உள்ள `LOCAL_ONLY_API_PREFIXES` /
`LOCAL_ONLY_API_PATTERNS`; கீழே உள்ள அட்டவணை தற்போதைய நிலையைப் பிரதிபலிக்கிறது.
`check-route-guard-membership` gate, spawn செய்யக்கூடிய prefix-களின் கீழுள்ள ஒவ்வொரு
`route.ts`-ஐயும் பட்டியலிட்டு, அவற்றில் ஏதேனும் local-only என வகைப்படுத்தப்படவில்லை
என்றால் CI-ஐ தோல்வியடையச் செய்கிறது.

**மீறலுக்கான பதில்:** `403 LOCAL_ONLY`

#### நிர்வகிப்பு-scope விதிவிலக்கு

LOCAL_ONLY பாதைகளின் ஒரு துணைத்தொகுப்பை loopback அல்லாத இடத்திலிருந்தும் அணுகலாம், ஆனால்
கோரிக்கையில் `Authorization: Bearer <api-key>` இருந்து, அதன்
metadata-வில் `manage` scope (அல்லது `admin`) இருந்தால் மட்டுமே. இந்த விதிவிலக்கு
ஒவ்வொரு பாதைக்கும் `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` வழியாக வெளிப்படையாகக் கட்டுப்படுத்தப்படுகிறது; எனவே
எந்தப் புதிய LOCAL_ONLY பாதைக்கும் இயல்புநிலை strict-loopback ஆகவே இருக்கும். அங்கீகரிக்கப்படாத
கோரிக்கைகளும், manage அல்லாத keys கொண்ட கோரிக்கைகளும் இன்னும்
`403 LOCAL_ONLY` மூலம் நிராகரிக்கப்படும்.

தற்போது விதிவிலக்கு பெறக்கூடிய ஒரே prefix `/api/mcp/` ஆகும். `/api/cli-tools/runtime/` மற்றும்
`/api/services/` ஆகியவை தன்னிச்சையான
துணைச் செயல்முறைகளை (`npm install`, `node`) தொடங்கக்கூடியவை என்பதால் வேண்டுமென்றே விலக்கப்பட்டுள்ளன; இதுவே
LOCAL_ONLY அடுக்கு தடுப்பதற்காக உருவாக்கப்பட்ட துல்லியமான CVE வகையாகும்.

**#7895 — `mcp:connect` குறுகிய scope:** `/api/mcp/` விதிவிலக்கு,
குறுகிய `mcp:connect` scope-ஐக் கொண்ட Bearer key-யையும் ஏற்கிறது
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`); இது
`src/server/authz/policies/management.ts`-இல் உள்ள `hasMcpConnectOrManageScope()` மூலம் சரிபார்க்கப்படுகிறது.
இது `/api/mcp/`-க்கு மட்டுமே வரையறுக்கப்பட்டுள்ளது — வேறு எந்த
management route-க்கும் (எதிர்காலத்தில் சேர்க்கப்படக்கூடிய மற்ற எல்லா LOCAL_ONLY விதிவிலக்கு prefix-களும் உட்பட)
`mcp:connect` எந்த அனுமதியையும் வழங்காது; மேலும் இது வேண்டுமென்றே
`MANAGEMENT_API_KEY_SCOPES`-இலிருந்து விலக்கப்பட்டுள்ளது. `manage`/`admin` கொண்ட key,

தொலைநிலை MCP-மட்டும் அழைப்பாளர்களுக்கான குறைந்த-அனுமதி மாற்றாக

#### இயக்குநர் வழிகாட்டுதலும் தணிக்கையும்

OmniRoute-ஐ reverse proxy அல்லது tunnel-க்குப் பின்னால் (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) இயக்கினாலும், மேலே உள்ள செயல்முறை-தொடக்கத் திறன் கொண்ட
routes-ஐ loopback சரிபார்ப்பு தொடர்ந்து பாதுகாக்கும் — client address loopback அல்லாத
கோரிக்கை, **auth இயங்குவதற்கு முன்பே** `403 LOCAL_ONLY` மூலம் நிராகரிக்கப்படும்;
எனவே கசிந்த JWT-யால் செயல்முறையைத் தொடங்க முடியாது. இயக்குநருக்கு இரண்டு பொறுப்புகள்
மீதமுள்ளன:

- **client IP-ஐ loopback எனப் போலியாக்கி 403-ஐ "சரிசெய்ய" வேண்டாம்.**
  `X-Forwarded-For: 127.0.0.1` என அமைப்பது, அல்லது source address-ஐ
  loopback ஆக மாற்றியெழுதும் proxy-ஐப் பயன்படுத்துவது, இந்த அடுக்கு மூடும் அதே RCE வகையை
  மீண்டும் திறக்கிறது. proxy வழியாக dashboard/API-ஐ வெளிப்படுத்துங்கள் — செயல்முறை-தொடக்கத் திறன் கொண்ட
  routes-ஐ ஒருபோதும் வெளிப்படுத்தாதீர்கள்.
- **manage-scope விதிவிலக்கை மிகக் குறைவாக வைத்திருங்கள்.** `/api/mcp/` மட்டுமே விதிவிலக்கு பெறக்கூடியது; அதுவும்
  `manage` scope கொண்ட API key மூலம் மட்டுமே. `SPAWN_CAPABLE_PREFIXES`-ஐ ஒருபோதும்
  விதிவிலக்குப் பட்டியலில் சேர்க்க முடியாது — zod schema அவற்றை நிராகரிக்கிறது; மேலும்
  `isLocalOnlyBypassableByManageScope` இயக்க நேரத்தில் அவற்றை மறுக்கிறது (பல அடுக்குப் பாதுகாப்பு);
  dashboard-இல் "விதிவிலக்கு பெறக்கூடியதாக மாற்ற முடியாது" என்பதன் பொருள் இதுவே. `/api/providers/`-ன் கீழுள்ள
  dynamic-segment மற்றும் static-path செயல்முறை-தொடக்கத் திறன் கொண்ட routes (எ.கா. `/login`,
  `/refresh-cursor`) ஆகியவை, சமதளமான `SPAWN_CAPABLE_PREFIXES` array-ஆல் அல்லாமல்,
  `src/shared/constants/spawnCapablePrefixes.ts`-இல் உள்ள regex-அடிப்படையிலான
  `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` துணையால் கையாளப்படுகின்றன — அவற்றைக் கண்டறிய
  சமதள array முழு `/api/providers/` prefix-ஐ உள்ளடக்க வேண்டியிருக்கும்; இது தொலைநிலை
  dashboard-கள் provider CRUD-க்காகச் சட்டபூர்வமாகப் பயன்படுத்தும் route tree-ஐ
  அளவுக்கு மீறி விரிவுபடுத்திவிடும்.

**அணுகல் தணிக்கை** — host-க்கு வெளியிலிருந்து எதுவும் இந்த routes-ஐ அடையவில்லை என்பதைச் சரிபார்க்க:

- `/dashboard/settings/security` இல் உள்ள **அங்கீகார இருப்புப் பட்டியலை** திறக்கவும்: அது
  நிகழ்நேர LOCAL_ONLY முன்னொட்டுப் பட்டியல், எந்த முன்னொட்டுகளைத் தவிர்க்க முடியும், மற்றும் தொகுப்பு நேரத்தில்
  உருவாக்கக்கூடிய ("தவிர்க்கக்கூடியதாக மாற்ற முடியாது") தொகுப்பு ஆகியவற்றைக் காட்டுகிறது.
- மேலே உள்ள முன்னொட்டுகள், loopback அல்லாத கிளையன்ட் முகவரியுடன் இணைந்து இடம்பெற்றுள்ளனவா என உங்கள் reverse-proxy / அணுகல் பதிவுகளில் Grep செய்யவும்.
  அத்தகைய கோரிக்கைகளில் ஏதேனும் `403 LOCAL_ONLY` என்பதற்குப் பதிலாக `200` ஐத் திருப்பியிருந்தால்,
  proxy உண்மையான கிளையன்ட் IP-ஐ மறைக்கிறது என்று பொருள் — proxy-ஐச் சரிசெய்யவும்.
- இந்தப் பாதைகளில் ஒன்றுக்காக OmniRoute-இன் பதிவுகளில் தோன்றும் `403 LOCAL_ONLY` என்பது guard
  திட்டமிட்டபடி செயல்படுவதைக் குறிக்கிறது; அது ஒடுக்கப்பட வேண்டிய பிழை அல்ல.

### புதிய நிறுவலின் bootstrap, `Host` அடிப்படையில் அல்லாமல் உண்மையான peer அடிப்படையில் loopback-க்கு மட்டுமே அனுமதிக்கப்படுகிறது

management password எதுவும் அமைக்கப்படாதபோது (மேலும் `INITIAL_PASSWORD` இல்லாதபோது),
`src/shared/utils/apiAuth.ts` இல் உள்ள `isAuthRequired()`, அநாமதேய bootstrap-ஐ **loopback peers-க்கு மட்டும்**
திறந்த நிலையில் வைத்திருக்கிறது. Loopback என்பது பின்வரும் நம்பகமான peer signals-இலிருந்து வரிசையாகத் தீர்மானிக்கப்படுகிறது:
token முத்திரையிடப்பட்ட உண்மையான TCP peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, policy காண்பது),
pipeline-இன் சொந்த `AUTHZ_HEADER_PEER_LOCALITY` தீர்ப்பு (route handlers காண்பது,
`OMNIROUTE_PEER_STAMP_TOKEN` அமைக்கப்பட்டிருக்கும்போது மட்டுமே நம்பகமானது), அல்லது நேரடி callers-க்கான உண்மையான socket peer.
`Host` / `nextUrl.hostname` ஒருபோதும் பரிசீலிக்கப்படுவதில்லை; மேலும் முதல் கடவுச்சொல்லை எழுதுவது
(`POST /api/settings/require-login`), ஒவ்வொரு network peer-க்கும் திறந்திருப்பதற்குப் பதிலாக அதே கட்டுப்பாட்டின் கீழ் உள்ளது
(GHSA-7pq4-8pvv-rx7r). `managementPolicy`, அதன் சொந்த `peerContext` தீர்ப்பை வெளிப்படையாகக்
கீழ்நிலைக்கு அனுப்புவதால், ORIGINAL (strip செய்யப்படுவதற்கு முந்தைய) request-இன் headers அதை ஒருபோதும் தீர்மானிப்பதில்லை.

### அடுக்கு 3 — MANAGEMENT (இயல்புநிலை)

மற்ற அனைத்து management routes-உம் இதில் அடங்கும். `requireLogin=false` என
உள்ளமைக்கப்படாத வரை அங்கீகாரம் தேவை. CLI tokens இந்த routes-ஐ அங்கீகரிக்க முடியும் (loopback + செல்லுபடியாகும் HMAC).

## மதிப்பீட்டு வரிசை

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → அடுத்த படிக்குச் செல்
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → அனுமதி (management_key)
     → இல்லையெனில்                                → நிராகரி 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → அனுமதி (system)
  3. hasValidCliToken(headers)?
     → அனுமதி (cli) [loopback + timingSafeEqual HMAC சரிபார்ப்பு]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → அனுமதி (dashboard_session)
     → தளர்த்த முடியாத பாதையில் manage-scope Bearer உள்ளதா?
        → அனுமதி (management_key)
     → நிராகரி 401/403
  5. requireLogin=false?
     → அனுமதி (anonymous)
```

படி 1-இன் manage-scope கிளை மட்டுமே LOCAL_ONLY வழித்தடத்தைப் பூர்த்திசெய்யக்கூடிய அங்கீகரிக்கப்பட்ட பாதையாகும்; காலாவதியான DB அமைதியாக "deny" நிலைக்குத் தாழ்த்தப்படாமல் இருக்க, auth-backend தோல்வி நிலை 503-ஐத் (403 அல்ல) திருப்பியளிக்கிறது.

## உருவாக்கும் திறனுள்ள புதிய வழித்தடத்தைச் சேர்த்தல்

1. `src/server/authz/routeGuard.ts`-இல் உள்ள `LOCAL_ONLY_API_PREFIXES`-க்குப் பாதை முன்னொட்டைச் சேர்க்கவும்
2. புதிய முன்னொட்டுக்கு `isLocalOnlyPath()` true-ஐத் திருப்பியளிக்கிறது என்பதை உறுதிப்படுத்தும் சோதனையை `tests/unit/authz/routeGuard.test.ts`-இல் சேர்க்கவும்
3. **இந்தப் படியை ஒருபோதும் தவிர்க்க வேண்டாம்** — `CLAUDE.md`-இல் உள்ள கடுமையான விதி #15-ஐப் பார்க்கவும்
4. முடிவெடுக்கவும்: இந்த வழித்தடம் `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-லும் இடம்பெற வேண்டுமா?
   இயல்புநிலைப் பதில் **இல்லை**. manage-scope வைத்திருப்பவருக்கு இந்த வழித்தடத்தை வெளிப்படுத்துவது பாதுகாப்பானதாக இருக்கும்போது மட்டுமே இதைத் தேர்வுசெய்யவும் (அதாவது, பயனர் கட்டுப்படுத்தும் தன்னிச்சையான குறியீட்டை இது உருவாக்கக் கூடாது).

## manage-scope மூலம் தளர்த்தக்கூடிய பாதையைச் சேர்த்தல்

1. இந்த வழித்தடம் பயனர் வழங்கிய குறியீடு அல்லது கட்டளைகளைச் செயல்படுத்தவில்லை என்பதை உறுதிப்படுத்தவும். அவ்வாறு செயல்படுத்தினால், நிறுத்தவும் — இந்த விதிவிலக்கு அதற்கான சரியான கருவி அல்ல.
2. `src/server/authz/routeGuard.ts`-இல் உள்ள `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-க்கு முன்னொட்டைச் சேர்க்கவும்
3. பின்வரும் நான்கு கோரிக்கை வடிவங்களுக்கும் `tests/unit/authz/management-policy.test.ts`-இல் சோதனைகளைச் சேர்க்கவும்: Bearer இல்லை (403), manage Bearer (அனுமதி), non-manage Bearer (403), மேலும் manage Bearer இருந்தாலும் `/api/cli-tools/runtime/*` strict-loopback ஆகவே இருப்பதை உறுதிப்படுத்தும் ஒவ்வொரு முன்னொட்டுக்குமான பின்னடைவு சோதனை.

## OpenAPI-இல் பாதுகாப்பு அடுக்குகளை ஆவணப்படுத்துதல்

`docs/openapi.yaml`-இல் புதிய வழித்தடத்தைச் சேர்க்கும்போது, அந்த வழித்தடம் `routeGuard.ts` மூலம் வகைப்படுத்தப்பட்டிருந்தால், அதற்குரிய vendor extension-ஐப் பயன்படுத்தவும்:

| routeGuard.ts வகைப்பாடு                 | YAML குறிப்பு              | அமலாக்கம்                                                |
| --------------------------------------- | -------------------------- | -------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`               | `x-loopback-only: true`    | non-loopback-இலிருந்து நிபந்தனையின்றித் தடுக்கப்படும்    |
| `ALWAYS_PROTECTED_API_PATHS`            | `x-always-protected: true` | `requireLogin=false` ஆக இருந்தாலும் அங்கீகாரம் தேவை      |
| உள் admin/debug வழித்தடம்               | `x-internal: true`         | இயல்பாக /dashboard/api-endpoints-இலிருந்து மறைக்கப்படும் |
| எதுவுமில்லை (பொது / நிலையான அங்கீகாரம்) | (குறிப்பு தேவையில்லை)      | நிலையான `requireLogin`-ஆல் கட்டுப்படுத்தப்படும் அணுகல்   |

### சரிபார்ப்பு

YAML குறிப்புகளுக்கும் `routeGuard.ts`-க்கும் இடையிலான ஒத்திசைவை இரண்டு scripts அமல்படுத்துகின்றன:

- `scripts/check/check-openapi-coverage.mjs` — coverage < 99% எனில் தோல்வியடையும்
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` அல்லது
  `x-always-protected` குறிப்புகள் compile-time மாறிலிகளிலிருந்து வேறுபட்டால் தோல்வியடையும்

இரண்டு scripts-உம் pre-commit hook-இலும் CI-இலும் இயங்குகின்றன.

### தவறான நேர்மறை விதி

`routeGuard.ts` மாறிலியில் இல்லாத ஒரு வழித்தடத்தில் `x-always-protected` அல்லது `x-loopback-only` குறிக்கப்பட்டிருந்தால், coverage script தோல்வியடையும். `routeGuard.ts` உண்மையில் அமல்படுத்துவதுடன் YAML-ஐ ஒத்திசைப்பதே எப்போதும் சரியான தீர்வு — அமலாக்கத் தர்க்கத்தையும் சேர்க்காமல் `routeGuard.ts`-க்கு வழித்தடங்களைச் சேர்ப்பது தீர்வல்ல.
