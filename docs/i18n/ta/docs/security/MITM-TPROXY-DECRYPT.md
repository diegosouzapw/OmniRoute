TPROXY வெளிப்படையான மறைகுறியாக்கம் என்பது OmniRoute-இன்
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM அடுக்கிற்கான **5வது பிடிப்பு முறை** ஆகும். இது kernel TPROXY + policy routing-ஐப் பயன்படுத்தி Linux-இல் உள்ளூர் வெளிச்செல்லும் HTTPS போக்குவரத்தை இடைமறித்து **மறைகுறியாக்கத்தை நீக்குகிறது** — `/etc/hosts`-ஐப் போலியாக்காமலும்,
OS முழுவதற்குமான system-proxy அமைப்புகளை மாற்றாமலும். இது headless சூழலுக்கு ஏற்றது
(சுத்தம் செய்ய வேண்டிய DNS திருத்தங்கள் இல்லை), மேலும் மறுதொடக்கத்தின்போது firewall விதிகள் தானாகவே நீக்கப்படும்.

மற்ற பிடிப்பு முறைகளைப் போலன்றி, TPROXY-க்கு ஒவ்வொரு host-க்கும் தனித்தனி அமைப்பு தேவையில்லை: இலக்கு port-இல் உள்ள **எந்தவொரு** destination host-க்குமான போக்குவரத்தையும் இது வெளிப்படையாக
இடைமறித்து, ஒவ்வொரு SNI hostname-க்கும் உடனடியாக வழங்கும் leaf certificate மூலம் TLS-ஐ
முடிவுறச் செய்து, மறைகுறியாக்கம் நீக்கப்பட்ட பரிமாற்றத்தைப் பிடித்து, கோரிக்கையை அசல் இலக்கிற்கு மீண்டும் மறைகுறியாக்கி அனுப்புகிறது.

> **Linux-க்கு மட்டும், root-க்கு மட்டும், விருப்பத் தேர்வு.** இந்த முறைக்கு Linux, C toolchain மூலம் உருவாக்கப்பட்ட native addon,
> மற்றும் **CAP_NET_ADMIN** capability (பொதுவாக root) தேவை. இது loopback-only AgentBridge API-க்குப்
> பின்னால் கட்டுப்படுத்தப்பட்டு, இயல்பாக முடக்கப்பட்டுள்ளது. எந்த host-க்கும் கையொப்பமிடக்கூடிய நம்பகமான
> MITM CA என்பது சக்திவாய்ந்த capability — [§6 பாதுகாப்பு](#6-security)-ஐப் பார்க்கவும்.

## §1 இது என்ன, எப்போது பயன்படுத்த வேண்டும்

மற்ற நான்கு பிடிப்பு முறைகள் ஒவ்வொன்றுக்கும் ஒரு வரம்பு உள்ளது:

| முறை               | போக்குவரத்து எவ்வாறு வழிநடத்தப்படுகிறது              | வரம்பு                                                     |
| ------------------ | ---------------------------------------------------- | ---------------------------------------------------------- |
| AgentBridge        | நிலையான host தொகுப்பின் `/etc/hosts` DNS போலியாக்கம் | பதிவுசெய்யப்பட்ட IDE-agent host-கள் மட்டும்                |
| தனிப்பயன் host-கள் | ஒவ்வொரு host-க்கும் `/etc/hosts` DNS போலியாக்கம்     | ஒவ்வொரு host-க்கும் ஓர் entry; hosts-ஐத் திருத்த sudo தேவை |
| HTTP_PROXY         | `HTTP_PROXY`/`HTTPS_PROXY` env                       | env var-ஐ மதிக்கும் app-கள் மட்டும்                        |
| System-wide proxy  | OS proxy அமைப்புகள்                                  | global state-ஐ மாற்றுகிறது; மீட்டமைப்பு தேவை               |

அதற்குப் பதிலாக TPROXY வெளிப்படையான மறைகுறியாக்கம் **kernel** அடுக்கில் போக்குவரத்தை வழிநடத்துகிறது. இது
`mangle OUTPUT` chain-இல் இலக்கு port-க்கு (இயல்புநிலை `443`) செல்லும் புதிய உள்ளூர் வெளிச்செல்லும் TCP இணைப்புகளைக்
குறியிடுகிறது; ஓர் `ip rule`, குறியிடப்பட்ட packet-களை உள்ளூர் delivery-க்கு மறுவழிப்படுத்துகிறது;
மீண்டும் நுழையும்போது `mangle PREROUTING`-இன் `TPROXY` target அவற்றை
**IP_TRANSPARENT** listener-க்கு ஒப்படைக்கிறது — பின்னர் அது TLS-ஐ முடிவுறச் செய்து plaintext-ஐப் பிடிக்கிறது.

பின்வரும் பண்புகளைக் கொண்ட process-இலிருந்து போக்குவரத்தைப் பிடித்து மறைகுறியாக்கத்தை நீக்க விரும்பும்போது இதைப் பயன்படுத்தவும்:

- AgentBridge பதிவு செய்யாத ஒரு host உடன் தொடர்புகொள்கிறது, மேலும்
- `HTTP_PROXY`-ஐ மதிப்பதில்லை, மேலும்
- system-wide proxy மாற்றத்தின் மூலம் அதைப் பாதிக்க விரும்பவில்லை.

இடைமறிப்பு kernel-இல் நிகழ்வதால், தொடக்க process-க்கு **எந்த
configuration மாற்றமும்** தேவையில்லை — ஆனால் OmniRoute நிறுவும் dynamic CA-ஐ அந்த process நம்ப வேண்டும்
([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)-ஐப் பார்க்கவும்).

## §2 தேவைகள்

| தேவை               | விவரம்                                                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**             | Linux மட்டும் — **IP_TRANSPARENT** என்பது Linux-க்கு மட்டுமான socket விருப்பமாகும். மற்ற எல்லா இயங்குதளங்களிலும் loader "கிடைக்கவில்லை" எனத் திருப்பியளிக்கும்.                       |
| **சிறப்புரிமை**    | transparent socket-ஐ உருவாக்கி `iptables`/`ip` விதிகளைப் பயன்படுத்துவதற்கான **CAP_NET_ADMIN** திறன் — நடைமுறையில், root ஆக இயக்கவும்.                                                 |
| **Native addon**   | ஒரு சிறிய N-API addon (`src/mitm/tproxy/native/transparent.c`) உருவாக்கப்பட வேண்டும் அல்லது prebuild ஆக வழங்கப்பட வேண்டும். [§3](#3-the-native-ip_transparent-addon)-ஐப் பார்க்கவும். |
| **Kernel modules** | `TPROXY`, `mangle`, மற்றும் `mark` பொருத்த ஆதரவுடன் கூடிய `iptables` (kernel 6.8.0-க்கு எதிராகச் சரிபார்க்கப்பட்டது).                                                                 |

**சீரான தரக்குறைப்பு:** ஏதேனும் தேவை இல்லாவிட்டால் (Linux அல்லாதது, toolchain
இல்லாதது, addon உருவாக்கப்படாதது), addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
பிழையை எறிவதற்குப் பதிலாக `null`-ஐத் திருப்பியளிக்கும். அதன் பிறகு capture-mode நிலை
`available: false` எனத் தெரிவிக்கும்; dashboard toggle **முடக்கப்பட்டு**, அதில்
"TPROXY மறைகுறிநீக்கத்திற்கு Linux + root + native addon தேவை" என்ற tooltip
காட்டப்படும்; மேலும் OmniRoute-இன் மற்ற பகுதிகள் தொடர்ந்து செயல்படும்.

## §3 இயல்புநிலை IP_TRANSPARENT addon

Node-இன் `net` module-ஆல் `bind()`-க்கு _முன்_ `setsockopt(IP_TRANSPARENT)`-ஐப்
பயன்படுத்த முடியாது; ஆனால் TPROXY-க்கு இது தேவைப்படுகிறது (இல்லையெனில் kernel
திசைமாற்றப்பட்ட packet-களை நிராகரிக்கும்). இந்த addon
(`src/mitm/tproxy/native/transparent.c`, `binding.gyp` வழியாக உருவாக்கப்படுகிறது)
மூன்று function-களை வெளிப்படுத்தும் ஒரு சிறிய N-API module ஆகும்; இவை
`transparentSocket.ts` வழியாகப் பயன்படுத்தப்படுகின்றன:

| Addon function                        | Socket செயல்பாடு                                                                                         | பயன்பாடு                                                                          |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`; raw fd-ஐத் திருப்பியளிக்கும் | transparent capture listener (Node, `server.listen({ fd })` வழியாக fd-ஐ ஏற்கிறது) |
| `setSocketMark(fd, mark)`             | ஏற்கனவே உள்ள fd மீது `setsockopt` **SO_MARK**                                                            | loop தடுப்பு (proxy-இன் சொந்த socket-களைக் குறியிடுதல்)                           |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()`-க்கு **முன்** `socket()` + **SO_MARK**; fd-ஐத் திருப்பியளிக்கும்                | மீண்டும் மறைகுறியாக்கப்பட்ட upstream forward (SYN, mark-ஐக் கொண்டுசெல்கிறது)      |

அசல் இலக்கு `socket.localAddress`/`localPort`-இலிருந்து படிக்கப்படுகிறது — TPROXY
அதைப் பாதுகாப்பதால், **SO_ORIGINAL_DST**/NAT தேடல் தேவையில்லை.

### Addon-ஐ உருவாக்குதல்

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- `npm run build` செயல்பாட்டின்போது, `scripts/build/build-tproxy-native.mjs`,
  `node-gyp rebuild`-ஐ இயக்குகிறது. இது **Linux-க்கு மட்டுமானது மற்றும் தோல்வி
  ஏற்பட்டாலும் பாதிப்பில்லாதது** — toolchain இல்லாவிட்டால் capture mode
  கிடைக்காமல் மட்டுமே இருக்கும்.
- `assembleStandalone.mjs`, `build/Release/transparent.node`-ஐ standalone
  bundle-க்குள் நகலெடுக்கிறது; `transparentSocket.ts`, module-relative மற்றும்
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`) ஆகிய இரு முறைகளிலும் அதைத்
  தீர்மானிக்கிறது.
- `build/` மற்றும் `prebuilds/` ஆகியவை git-ல் புறக்கணிக்கப்படுகின்றன — binary
  **உருவாக்கப்படுகிறது, ஒருபோதும் commit செய்யப்படுவதில்லை**.

Loader பின்வரும் முன்னுரிமை வரிசையில் சோதிக்கிறது:
`native/build/Release/transparent.node`, பின்னர் `native/prebuilds/transparent.node`
(இரண்டும் module-relative ஆகவும் `<cwd>/src/mitm/tproxy/`-இன் கீழும்).

## §4 ஒவ்வொரு-SNI-க்குமான மாறும் CA மற்றும் நம்பிக்கைச் சேமிப்பக நிறுவி

> **#6684 புதுப்பிப்பு:** AgentBridge நிலையான சேவையகம் (`src/mitm/server.cjs`) இப்போது
> ஒற்றை நிலையான சுய-கையொப்பமிட்ட leaf-க்குப் பதிலாக இதே CA/leaf கட்டமைப்பு
> வடிவமைப்பைப் பகிர்கிறது. இது ஒரு **தனித்துவமான** CA நிகழ்வைப் பயன்படுத்துகிறது
> (`src/mitm/cert/rootCa.ts`, `<DATA_DIR>/mitm/ca.key`/`ca.crt` என்பதில் நிலைநிறுத்தப்படுகிறது)
> மற்றும் முன்பே உள்ள `omniroute-mitm.crt` நம்பிக்கைச் சேமிப்பக இடத்தில் நிறுவுகிறது
> (அங்கிருந்த பழைய ஒற்றை leaf-ஐ மாற்றுகிறது — இரட்டை-நம்பிக்கை சுத்தப்படுத்தல் தேவையில்லை);
> கீழே உள்ள TPROXY-யின் சொந்த `omniroute-tproxy-ca.crt` இடத்திலிருந்து இது
> முழுமையாகத் தனியாக வைக்கப்படுகிறது. புதிய AgentBridge நிறுவல்கள் CA மாதிரியைத்
> தானாகப் பெறுகின்றன; பழைய நிலையான leaf-ஐ ஏற்கனவே நம்பியிருக்கும் நிறுவல்,
> இயக்குநர் `MITM_ROOT_CA_ENABLED=true` மூலம் தேர்வுசெய்யும் வரை அதையே தொடர்ந்து
> பயன்படுத்தும் (`src/mitm/cert/migration.ts`-ஐப் பார்க்கவும்) — **எந்தவொரு**
> host-க்கும் leaf-ஐ கையொப்பமிடக்கூடிய நம்பகமான MITM CA, பழைய நிலையான-SAN
> leaf-ஐவிட கணிசமாக அதிக சக்திவாய்ந்தது; எனவே ஏற்கனவே நம்பப்பட்டுள்ள நிறுவலில்
> இந்த மாற்றம் ஒருபோதும் அமைதியாக நிகழாது.

வரலாற்று ரீதியாக, நிலையான AgentBridge MITM சான்றிதழ் செயல்பட்டதற்குக் காரணம்,
AgentBridge ஒரு **நிலையான** host தொகுப்புக்கான DNS-ஐ ஏமாற்றிப் பதிலளித்ததே
(இப்போது கீழே உள்ள மாதிரியுடன் ஒருங்கிணைக்கப்பட்டுள்ளது). TPROXY **தன்னிச்சையான**
host-களை இடைமறிப்பதால், client கோரும் எந்த SNI-க்கும் செல்லுபடியாகும் leaf-ஐ
அதன் listener வழங்க வேண்டும் — 4 antigravity host-களுக்கு மட்டும் பதிலாக
முழு `MITM_TOOL_HOSTS` தொகுப்புக்கும் (9 tool பதிவுகள்) இப்போது AgentBridge-க்கும்
இதே தேவை பொருந்துகிறது.

### மாறும் CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore`, `selfsigned` சார்புநிலையின் மீது கட்டமைக்கப்பட்ட உள்ளூர் CA-ஐ இயக்குகிறது; அது:

- `generateMitmCa()` வழியாக நீண்டகால CA-ஐ உருவாக்குகிறது (CN `"OmniRoute MITM CA"`,
  10 ஆண்டு செல்லுபடிக் காலம், `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-bit RSA / SHA-256).
- `issueLeafCert()` வழியாக **ஒவ்வொரு SNI hostname-க்கும் தேவைக்கேற்ப ஒரு leaf-ஐ**
  வழங்குகிறது (1 ஆண்டு செல்லுபடிக் காலம், `subjectAltName` = SNI host) மற்றும்
  ஒவ்வொரு hostname-க்கும் ஒரு `tls.SecureContext`-ஐ cache செய்கிறது.
- TLS-ஐ முடிவுறுத்தும் சேவையகத்திற்காக `createSNICallback()`-ஐ வெளிப்படுத்துகிறது
  ([§5](#5-how-decrypt-and-capture-work)-ஐப் பார்க்கவும்).
- மறுதொடக்கங்களுக்கு இடையிலும் CA நிலையாக இருக்குமாறு `existingCa` உடன்
  உருவாக்கப்படலாம் (எனவே நம்பிக்கைச் சேமிப்பகத்தை மீண்டும் நிறுவ வேண்டியதில்லை).

CA தனிப்பட்ட key **ஒருபோதும் இயந்திரத்தை விட்டு வெளியேறாது**.

### நம்பிக்கைச் சேமிப்பக நிறுவி (`src/mitm/tproxy/caTrust.ts`)

இடைமறிக்கப்படும் client, மாறும் CA-ஐ நம்ப வேண்டும். எனவே capture பயன்முறையைத்
தொடங்குவது, OS நம்பிக்கைச் சேமிப்பகத்தில் CA சான்றிதழை ஒரு **பிரத்யேக இடத்தின்**
கீழ் நிறுவுகிறது — `omniroute-tproxy-ca.crt` (`TPROXY_CA_CERT_NAME` மாறிலி) —
நிலையான MITM சான்றிதழின் இடத்திலிருந்து (`omniroute-mitm.crt`) தனியாக
வைக்கப்படுவதால், அவை ஒன்றையொன்று ஒருபோதும் மேலெழுதாது.

`installTproxyCa(caPem, sudoPassword?)`, distro-வின் anchor கோப்பகத்தைக்
கண்டறிந்து (வரிசைப்படி: முதலில் Debian-பாணி), அதற்குப் பொருந்தும் புதுப்பிப்பு
கட்டளையை இயக்குகிறது:

| Anchor கோப்பகம்                             | புதுப்பிப்பு கட்டளை      |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

நிறுவல், PEM-ஐ ஒரு தற்காலிகக் கோப்பில் முதலில் வைக்கிறது; பின்னர் (சிறப்புரிமையுடன்)
anchor கோப்பகத்தில் `mkdir -p`-ஐ இயக்கி, அங்கு வைக்கப்பட்ட கோப்பை `cp` செய்து,
புதுப்பிப்பு கட்டளையை இயக்குகிறது. `uninstallTproxyCa()` பிரத்யேக இடத்தை மட்டும்
நீக்கி (நிலையான MITM சான்றிதழைத் தொடாமல் விட்டு), புதுப்பிக்கிறது — Linux அல்லாத
அமைப்புகளில் இது எந்தச் செயலையும் செய்யாது.

அனைத்து சிறப்புரிமை பெற்ற கட்டளைகளும் `execFileWithPassword`
(`src/mitm/systemCommands.ts`) வழியாக இயக்கப்படுகின்றன — **argument array-களுடன்,
shell இல்லாமல், string interpolation இல்லாமல்** `spawn` பயன்படுத்தப்படுகிறது
(கடுமையான விதி #13). process root ஆக இருக்கும்போது (எ.கா., VPS), இலக்கு நேரடியாக
இயக்கப்படுகிறது; password தேவையில்லை. root அல்லாத desktop-இல், `sudoPassword`
stdin வழியாக `sudo -S`-க்கு அனுப்பப்படுகிறது.

> நம்பிக்கைச் சேமிப்பக நிறுவலுக்கு அங்கீகாரம் வழங்க, desktop-இன் `sudoPassword`
> POST body-இல் வழங்கப்படுகிறது; process root ஆக இருக்கும்போது அது முழுமையாகப்
> புறக்கணிக்கப்படுகிறது.

## §5 மறைகுறியாக்க நீக்கமும் கைப்பற்றலும் எவ்வாறு செயல்படுகின்றன

செயலாக்கத் தொடர் (அனைத்தும் `src/mitm/tproxy/`-இன் கீழ்):

```
உள்ளமை பயன்பாடு ──TCP/443──▶ mangle OUTPUT இணைப்பைக் குறிக்கிறது (fwmark)
                               ip rule → உள்ளமை வழித்தட அட்டவணை → lo
                               mangle PREROUTING TPROXY → IP_TRANSPARENT செவிமடுப்பான் (port 8443)
                                   │  captureMode.ts: socket.localAddress-இலிருந்து அசல் இலக்கைப் படிக்கிறது
                                   ▼
                               tlsCapture.ts:
                                 1. ஒவ்வொரு SNI-க்கும் உரிய leaf-ஐக் கொண்டு CLIENT-இன் TLS-ஐ நிறுத்துகிறது (dynamicCert)
                                 2. உள் http.Server மறைகுறியாக்கம் நீக்கப்பட்ட எளிய உரையைப் பகுப்பாய்வு செய்கிறது
                                 3. கைப்பற்றல் → source: "tproxy" உடன் globalTrafficBuffer.push()
                                    (sanitizeHeaders + maskSecret பயன்படுத்தப்படும்)
                                 4. bypass-mark செய்யப்பட்ட socket வழியாக அசல் இலக்கிற்கு
                                    மீண்டும் மறைகுறியாக்கி அனுப்புகிறது (connectMarked, anti-loop)
                                   │
                                   ▼
                               அசல் upstream (api.example.com)
```

- **TLS நிறுத்தம்** (`createTlsCaptureServer`): dynamic CA-இன் SNI callback-ஐப் பயன்படுத்தி, இடைமறிக்கப்பட்ட மூல
  socket-ஐ server-side `tls.TLSSocket`-இல் சுற்றி, பின்னர் மறைகுறியாக்கம் நீக்கப்பட்ட stream-ஐ உள் `http.Server`-க்கு வழங்குகிறது (வழக்கமான MITM
  நிறுத்த உத்தி). செயலற்ற tunnel ஒன்று file descriptor-களைத் தீர்த்துவிடாமல் இருக்க, socket-களின் ஆயுட்காலம் `MITM_IDLE_TIMEOUT_MS` மூலம் வரையறுக்கப்படுகிறது.
- **கைப்பற்றல்** (`handleDecryptedRequest`): `source: "tproxy"`, `"in-flight"` எனத் தொடங்கும் status ஆகியவற்றுடன் ஓர் `InterceptedRequest`-ஐச்
  சேர்க்கிறது; buffer-க்குள் நுழைவதற்கு முன் header-கள்
  `sanitizeHeaders()` வழியாகவும் body-கள் `maskSecret()` வழியாகவும் செயலாக்கப்படுகின்றன.
  பின்னர் response, அளவுகள் மற்றும் தாமதத்தைக் கொண்டு அந்த entry புதுப்பிக்கப்படுகிறது.
- **மீண்டும் மறைகுறியாக்கப்பட்ட அனுப்புதல்** (`createForward` / `realForward`): அசல் இலக்கிற்கு மீண்டும் மறைகுறியாக்கி அனுப்புகிறது.
  `rejectUnauthorized`-இன் இயல்புநிலை **`true`** (இயல்பாகவே பாதுகாப்பானது) — client கோரிய SNI/Host-க்கு எதிராக upstream certificate
  சரிபார்க்கப்படுவதால், அசல் client நிராகரித்திருப்பதையே proxy-யும் துல்லியமாக நிராகரிக்கிறது.

### முடிவற்ற சுழற்சித் தடுப்பு (SO_MARK)

விதிகள் புதிய உள்ளமை outbound connection-களைக் குறிப்பதால், proxy-யின் **சொந்த**
மீண்டும் மறைகுறியாக்கப்பட்ட அனுப்புதல் வழக்கமாக மீண்டும் இடைமறிக்கப்படும் — இது ஒரு முடிவற்ற சுழற்சியாகும். ஒரு bypass socket mark-ஐ (**SO_MARK**) பயன்படுத்தி
forward பாதை இதைத் தடுக்கிறது:

- `realForward`, `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` வழியாகத் தனது upstream socket-ஐத் திறக்கிறது
  — `DEFAULT_BYPASS_MARK = 0x539` — இது `connect()`-க்கு **முன்பே** **SO_MARK**-ஐ அமைப்பதால்,
  forward-இன் SYN bypass mark-ஐக் கொண்டிருக்கும்.
- ஏற்கெனவே bypass mark கொண்டுள்ள connection-களை `mangle OUTPUT` விதி விலக்குகிறது
  (`-m mark ! --mark <bypassMark>`); எனவே proxy-யின் forward மீண்டும் குறிக்கப்படுவதில்லை,
  மேலும் அது TPROXY-க்குள் மீண்டும் நுழைவதில்லை.

> செயலாக்கக் குறிப்பு: bypass-mark செய்யப்பட்ட socket, agent-இன்
> `createConnection`-இல் நிறுவப்பட வேண்டும் (agent ஒன்று இருக்கும்போது `https.request({ createConnection })` எந்த அறிவிப்புமின்றி புறக்கணிக்கப்படுகிறது);
> இல்லையெனில் forward குறிக்கப்படாத socket ஒன்றைத் திறந்து, சுழற்சி மீண்டும் தொடங்கும்.
> இது e2e மூலம் சரிபார்க்கப்பட்ட முடிவற்ற சுழற்சித் தடுப்புத் திருத்தமாகும்.

| **லூப்பேக்கிற்கு மட்டும் உரிய API**              | `/api/tools/agent-bridge/tproxy` என்பது `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`) இல் உள்ள `/api/tools/agent-bridge/` முன்னொட்டால் உள்ளடக்கப்படுகிறது. லூப்பேக் அமலாக்கம் அங்கீகாரத்திற்கு **முன்** இயங்குகிறது (கடுமையான விதிகள் #15 + #17) — டன்னல் வழியாகக் கசிந்த JWT-ஆல் TPROXY கைப்பற்றலைத் தொடங்க முடியாது; இது `iptables` விதிகளைப் பயன்படுத்துவதுடன், துணைச் செயல்முறைகள் வழியாக நம்பகச் சேமிப்பக CA-ஐ நிறுவுகிறது. |
| **பிரத்யேக CA இடம்**                             | இயக்கநிலை CA ஆனது `omniroute-tproxy-ca.crt` இல் நிறுவப்படுகிறது; நிலையான MITM சான்றிதழை ஒருபோதும் மேலெழுதாது.                                                                                                                                                                                                                                                                                                                                   |
| **CA விசை ஹோஸ்ட்டை விட்டு ஒருபோதும் வெளியேறாது** | `DynamicCertStore` CA விசையை நினைவகத்தில் வைத்திருக்கிறது; அது ஏற்றுமதி செய்யப்படுவதில்லை.                                                                                                                                                                                                                                                                                                                                                      |

| **ஷெல் இடைச்செருகல் இல்லை**                      | அனைத்து `iptables`/`ip`/நம்பகச் சேமிப்பகக் கட்டளைகளும் அளவுருத் தொடர்களுடன் `execFile`/`execFileWithPassword` வழியாக இயங்குகின்றன (கடுமையான விதி #13).                                                                                                                                                                                                                                                                                          |
| **அப்ஸ்ட்ரீம் சான்றிதழ் சரிபார்ப்பு**            | மீண்டும் குறியாக்கப்பட்ட முன்னனுப்பல், இயல்பாக அப்ஸ்ட்ரீம் சான்றிதழைச் சரிபார்க்கிறது (`rejectUnauthorized: true`).                                                                                                                                                                                                                                                                                                                             |
| **பிழை தூய்மைப்படுத்தல்**                        | ரூட்டின் பிழைப் பதில்கள் `sanitizeErrorMessage()` வழியாகச் செல்கின்றன (கடுமையான விதி #12).                                                                                                                                                                                                                                                                                                                                                      |

**MITM CA ஒரு சக்திவாய்ந்த திறனாகும்.** எந்த ஹோஸ்ட்டிற்கும் கையொப்பமிடக்கூடிய, OS-ஆல்
நம்பப்படும் ஒரு CA இருப்பதால், OmniRoute இடைமறிக்கும் அனைத்தையும் மறைகுறியாக்க முடியும்.
இது வெளிப்படையான, உள்ளூருக்கு மட்டும் உரிய TPROXY கைப்பற்றல் பயன்முறைக்குப் பின்னால்
கட்டுப்படுத்தப்பட்டுள்ளது; இயல்பாக முடக்கப்பட்டிருக்கும், மேலும் அந்தப் பயன்முறையை நிறுத்தும்போது
நம்பகச் சேமிப்பகப் பதிவு அகற்றப்படும்.

## §7 பரிவர்த்தனை முறையிலான firewall apply / revert

ஒரு செயலிழப்பு, எந்தச் சூழலிலும் ஒரு `mangle` விதியையோ காலாவதியான route-ஐயோ விட்டுச் செல்லக்கூடாது. கட்டளை உருவாக்கி
(`src/mitm/tproxy/commands.ts`) மற்றும் இயக்கி (`src/mitm/tproxy/setup.ts`) ஆகியவை
**revert என்பது apply-யின் துல்லியமான எதிர்செயலாக, தலைகீழ் வரிசையில் இருப்பதை** உறுதிசெய்கின்றன.

`applyTproxy(cfg)` apply கட்டளைகளை வரிசையாக இயக்குகிறது; **எந்தவொரு** தோல்வியின்போதும்,
முழுமையான `revertTproxy(cfg)`-ஐ இயன்றவரை சிறப்பாக இயக்கிவிட்டு பிழையை மீண்டும் எறிகிறது — எனவே firewall
முழுமையாகப் பயன்படுத்தப்பட்டிருக்கும் அல்லது முழுமையாக மீட்டமைக்கப்பட்டிருக்கும்; ஒருபோதும் பகுதியளவில் பயன்படுத்தப்பட்டிருக்காது. `revertTproxy(cfg)`
எதிர்செயல் கட்டளைகளைத் தலைகீழ் வரிசையில் இயக்கி, தோல்விகளைப் புறக்கணிக்கிறது (idempotent — நிபந்தனையின்றி அழைப்பது
பாதுகாப்பானது, எ.கா. AgentBridge `repairMitm()` cleanup-இலிருந்து).

எந்தக் கட்டளைக்கும் முன்பாக `validateTproxyConfig(cfg)` இயங்குகிறது: ports `1–65535` வரம்பில் இருக்க வேண்டும்,
`mark`/`routeTable`/`bypassMark` நேர்மறை முழு எண்களாக இருக்க வேண்டும், மேலும் `bypassMark`,
`mark`-இலிருந்து வேறுபட்டிருக்க வேண்டும் (சுழற்சி தடுப்பு).

### Apply கட்டளைகள் (வரிசையில்)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Revert அவற்றைத் தலைகீழ் வரிசையில் நீக்குகிறது: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> இந்தச் செய்முறை **OUTPUT-ஐ அடிப்படையாகக் கொண்டது**, ஏனெனில் MITM பயன்பாட்டுச் சூழல் என்பது _உள்ளமை_
> வெளியேறும் போக்குவரத்து (அதே host-இல் உள்ள apps); இதை `PREROUTING`-இல் உள்ள TPROXY மட்டும்
> காணாது — `PREROUTING` முன்னனுப்பப்பட்ட போக்குவரத்தை மட்டுமே காணும். `OUTPUT` chain புதிய
> உள்ளமை இணைப்புகளைக் குறியிடுகிறது, `ip rule` அவற்றை உள்ளமை வழங்கலுக்கு (`lo`) மறுவழிப்படுத்துகிறது, பின்னர்
> `PREROUTING` அவற்றை transparent listener-க்கு ஒதுக்குகிறது.

## §8 உள்ளமைவு

தொடக்கக் கோரிக்கை (`POST /api/tools/agent-bridge/tproxy`) கீழுள்ள
புலங்களை ஏற்கிறது; இவை `StartTproxyBodySchema` (`tproxy/route.ts`) மூலம் சரிபார்க்கப்படுகின்றன. அனைத்தும் விருப்பத் தேர்வானவை
மற்றும் குறிப்பிடப்படாவிட்டால் அவற்றின் இயல்புநிலைகளுக்குத் திரும்பும்:

| புலம்            | வகை                | இயல்புநிலை | குறிப்புகள்                                                                                                                        |
| ---------------- | ------------------ | ---------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`      | வெளிப்படையாக இடைமறிக்க வேண்டிய இலக்கு TCP port                                                                                     |
| **mark**         | int (≥1)           | `0x2333`   | `OUTPUT`-இல் அமைக்கப்படும் firewall mark; இது `ip rule` + `PREROUTING` மூலம் பொருத்தப்படுகிறது                                     |
| **onPort**       | int (1–65535)      | `8443`     | transparent (**IP_TRANSPARENT**) listener இணைக்கப்படும் port                                                                       |
| **routeTable**   | int (≥1)           | `233`      | `local 0.0.0.0/0` route-ஐக் கொண்டுள்ள கொள்கை-வழிப்படுத்தல் அட்டவணை id                                                              |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`    | proxy தனது சொந்த upstream இணைப்புகளில் அமைக்கும் bypass socket mark (**SO_MARK**); `OUTPUT`-இல் விலக்கப்படுகிறது (சுழற்சி தடுப்பு) |
| **sudoPassword** | string             | —          | root அல்லாத desktop-களுக்கு மட்டும்: trust-store நிறுவலை அங்கீகரிக்கிறது; root ஆக இருக்கும்போது புறக்கணிக்கப்படுகிறது              |

TPROXY-க்கான **environment variables எதுவும் இல்லை** — அனைத்து உள்ளமைவுகளும்
POST body அல்லது மேலே உள்ள இயல்புநிலைகள் வழியாக வழங்கப்படுகின்றன.

## §9 போக்குவரத்து ஆய்வியிலிருந்து செயல்படுத்துதல்

1. **போக்குவரத்து ஆய்வியை** (`/dashboard/tools/traffic-inspector`) திறக்கவும்.
2. பிடிப்பு-முறைகள் கருவிப்பட்டியில், **"TPROXY மறைகுறியாக்கம்"** ⚠ பொத்தானைக் கண்டறியவும்
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - "TPROXY மறைகுறியாக்கத்திற்கு Linux + root + நேட்டிவ் addon தேவை" என்ற கருவிக்குறிப்புடன் அது
     **முடக்கப்பட்டிருந்தால்**, இந்த ஹோஸ்டில் நேட்டிவ் addon கிடைக்கவில்லை (Linux அல்லாதது,
     toolchain இல்லாதது அல்லது addon உருவாக்கப்படாதது). [§2](#2-requirements) மற்றும் [§3](#3-the-native-ip_transparent-addon) ஆகியவற்றைப் பார்க்கவும்.
3. பொத்தானைக் கிளிக் செய்யவும். இது `startTproxyCaptureMode()` வழியாக
   `POST /api/tools/agent-bridge/tproxy`-ஐ அழைக்கிறது
   (`src/lib/inspector/tproxyCaptureApi.ts`); இது:
   மாறும் CA-ஐ உருவாக்கி, வெளிப்படையான listener-ஐத் திறந்து, firewall
   விதிகளைப் பயன்படுத்தி, OS நம்பிக்கைச் சேமிப்பகத்தில் CA-ஐ நிறுவுகிறது.
4. இயங்கும்போது, மாற்றுப் பொத்தான் ஆம்பர் நிறமாக மாறி, நேரடி இடைமறிப்பு எண்ணிக்கையைக்
   (`· <interceptCount>`) காட்டும். இடைமறிக்கப்பட்ட கோரிக்கைகள்,
   `source: "tproxy"` உடன் கோரிக்கைப் பட்டியலில் தோன்றும்.
5. நிறுத்த மீண்டும் கிளிக் செய்யவும் — `stopTproxyCaptureMode()` வழியாக
   `DELETE /api/tools/agent-bridge/tproxy` listener-ஐ மூடி, CA நிறுவலை நீக்கி,
   firewall விதிகளை மீட்டமைக்கிறது.

பிடிப்பு-முறை நிலை (இயங்குகிறது / கிடைக்கிறது / இடைமறிப்பு எண்ணிக்கை / listener port)
`GET /api/tools/agent-bridge/tproxy`-இலிருந்து வருகிறது (`src/mitm/tproxy/captureManager.ts`-இல் உள்ள
`getCaptureStatus()`). ஒரே நேரத்தில் **ஒரு** TPROXY அமர்வு மட்டுமே இயங்கும் —
இரண்டாவதைத் தொடங்க முயன்றால் "TPROXY பிடிப்பு முறை ஏற்கெனவே இயங்குகிறது" என்ற பிழையுடன் நிராகரிக்கப்படும்.

## §10 சிக்கல் தீர்த்தல்

### மாற்றுப் பொத்தான் முடக்கப்பட்டுள்ளது

நேட்டிவ் addon-ஐ ஏற்ற முடியவில்லை. பின்வருவனவற்றை உறுதிப்படுத்தவும்: நீங்கள் Linux-இல் உள்ளீர்கள்,
addon-ஐ உருவாக்கியுள்ளீர்கள் (`npm run build:native:tproxy`), மேலும் செயல்முறையால்
`transparent.node`-ஐ ஏற்ற முடிகிறது. `isTransparentSocketAvailable()` மாற்றுப் பொத்தானைக்
கட்டுப்படுத்துகிறது; addon இல்லாதபோது `GET /api/tools/agent-bridge/tproxy`,
`available: false` என்பதைத் திருப்பியளிக்கும்.

### எதுவும் பிடிக்கப்படவில்லை

- இடைமறிக்கப்படும் செயல்முறை உண்மையில் உள்ளமைக்கப்பட்ட `dport`-உடன்
  (இயல்புநிலை `443`) இணைகிறது என்பதை உறுதிப்படுத்தவும்.
- செயல்முறை மாறும் CA-ஐ நம்புகிறது என்பதை உறுதிப்படுத்தவும். CA,
  `omniroute-tproxy-ca.crt` என்ற பெயரில் நிறுவப்படுகிறது; சொந்த நம்பிக்கைச் சேமிப்பகத்தைக் கொண்ட
  பயன்பாடுகளுக்கு (Firefox/Chrome NSS) சான்றிதழை அங்கும் சேர்க்க வேண்டியிருக்கலாம்.
- சான்றிதழ்-நம்பகத்தன்மை / server நலநிலைச் சோதனைகளுக்காக AgentBridge
  **கண்டறிதல்** சுய-சோதனையை இயக்கவும்
  ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)-ஐப் பார்க்கவும்).

### செயலிழப்புக்குப் பிறகு எஞ்சியிருக்கும் firewall விதிகள்

`revertTproxy()` என்பது பயன்படுத்துதல் செயல்பாட்டின் துல்லியமான எதிர்செயலாகும்; மேலும் அது
idempotent ஆகும். முறையை நிறுத்துவது விதிகளை மீட்டமைக்கும்; அமர்வின் நடுவில் OmniRoute
நிறுத்தப்பட்டிருந்தால், அனாதையாகிவிட்ட system நிலையை (DNS spoof, root CA, system proxy)
நீக்க AgentBridge **பழுதுபார்த்தல்** செயலை
(`POST /api/tools/agent-bridge/repair`) பயன்படுத்தவும். TPROXY `mangle` விதிகளும் route-உம்
மறுதொடக்கத்தின்போது தானாகவே அகற்றப்படும்.

### முடிவற்ற சுழற்சி / proxy அதன் சொந்த forward-ஐ இடைமறிக்கிறது

இது சுழற்சித் தடுப்பு நிலையாகும். `bypassMark`, `mark`-இலிருந்து வேறுபடுகிறது என்பதை
உறுதிப்படுத்தவும் (சரிபார்ப்பு இதைக் கட்டாயப்படுத்துகிறது); மேலும் forward,
`connectMarked`-ஐப் பயன்படுத்துகிறது என்பதையும் உறுதிப்படுத்தவும் (`realForward`-இல் அவ்வாறே உள்ளது).
[§5 சுழற்சித் தடுப்பு](#anti-loop-so_mark)-ஐப் பார்க்கவும்.
