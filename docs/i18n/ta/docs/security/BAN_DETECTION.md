OmniRoute, வழங்குநரின் **கணக்கு நிரந்தரமாகச் செயலிழந்துவிட்டது** (இடைநிறுத்தப்பட்டது / செயலிழக்கச் செய்யப்பட்டது / சேவை விதிமுறைகளை மீறியதால் தடைசெய்யப்பட்டது) என்பதைக் குறிக்கும் சைகைகளுக்காக மேல்நிலைப் பிழைப் பதில்களை ஸ்கேன் செய்கிறது; பொருத்தம் கண்டறியப்படும்போது, அந்த இணைப்பை **இறுதி `banned` நிலைக்கு** மாற்றுகிறது, எனவே கோரிக்கைகளுக்கு அது இனி தேர்ந்தெடுக்கப்படாது. இதைத்தான் **Security → Banned Keywords**
அமைப்புகள் அட்டை உள்ளமைக்கிறது ("நிரந்தரக் கணக்குத் தடை கண்டறிதலைத் தூண்டும் கூடுதல் முக்கியச் சொற்கள். உள்ளமைக்கப்பட்ட முக்கியச் சொற்கள் எப்போதும் பயன்படுத்தப்படும்.").

இந்தப் பக்கம் உள்ளமைக்கப்பட்ட பட்டியல், கண்டறிதல் ஓட்டம், அதன் வரம்பு, தனிப்பயன் முக்கியச் சொற்களைப் பாதுகாப்பாகச் சேர்ப்பது மற்றும் குறியிடப்பட்ட இணைப்பை மீட்டெடுப்பது ஆகியவற்றை ஆவணப்படுத்துகிறது. இறுதி நிலையே மீள்திறன் மாதிரியின் ஒரு பகுதியாகும் — பார்க்கவும்
[RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) ("இறுதி நிலைகள்").

**உண்மையின் ஆதாரம்:** `open-sse/services/accountFallback.ts`
(`ACCOUNT_DEACTIVATED_SIGNALS`, `getMergedBannedSignals()`, `isAccountDeactivated()`).

## உள்ளமைக்கப்பட்ட முக்கியச் சொற்கள்

எந்தவொரு தனிப்பயன் பட்டியலையும் பொருட்படுத்தாமல், இந்த 8 உட்சரங்கள் எப்போதும் பயன்படுத்தப்படும் (எழுத்துப் பெரிய/சிறிய வேறுபாடின்றி):

```
account_deactivated
account has been deactivated
account has been disabled
your account has been suspended
this account is deactivated
verify your account to continue                                 (Antigravity / Google Cloud Code)
this service has been disabled in this account for violation    (Antigravity)
this service has been disabled in this account                  (Antigravity)
```

> வழங்குநர்கள் தங்கள் தடைச் சொற்றொடர்களை மாற்றுவதற்கேற்ப இந்தப் பட்டியல் மாறிக்கொண்டே இருக்கும். அதிகாரப்பூர்வமான
> நகல் `open-sse/services/accountFallback.ts`-இல் உள்ள `ACCOUNT_DEACTIVATED_SIGNALS`;
> மேலே உள்ள தொகுதியை ஒரு குறிப்பிட்ட நேரத்தின் நகலாகக் கருதவும்.

அதே கோப்பில் அருகருகே உள்ள, **தனித்தனி** இரண்டு சைகை அட்டவணைகள் தடைசெய்யப்பட்ட-முக்கியச் சொல் கண்டறிதலின் பகுதியாக _இல்லை_:

- `CREDITS_EXHAUSTED_SIGNALS` — பில்லிங்/ஒதுக்கீடு தீர்ந்துவிட்டது (`insufficient_quota`,
  `credit_balance_too_low`, `payment required`, …) → இறுதி `credits_exhausted`.
- `OAUTH_INVALID_TOKEN_SIGNALS` — **இறுதியற்றது**; டோக்கன் புதுப்பிப்பு மூலம் மீட்கலாம்.

குறிப்பு: **`rate limit`** / `429` போன்ற பொதுவான தற்காலிகச் சொற்றொடர்கள்
விகித-வரம்பு / இணைப்புக் காத்திருப்புப் பாதையால் கையாளப்படுகின்றன; அவை தடைச் சைகைகள் **அல்ல**.

## கண்டறிதல் ஓட்டம்

```
மேல்நிலைப் பிழைப் பதில்
  → உடல் சரமாக்கப்பட்டு + சிற்றெழுத்துகளாக மாற்றப்படுகிறது
  → isAccountDeactivated(body): getMergedBannedSignals().some(sig => body.includes(sig))   [உட்சரப் பொருத்தம்]
  → பொருத்தமா?
      → இணைப்பின் testStatus = "banned"      (நிரந்தரம் — 1 ஆண்டு காத்திருப்பு, தானாக ஒருபோதும் மீளாது)
      → `autoDisableBannedAccounts` அமைப்பு இயக்கத்தில் இருந்து, `autoDisableBannedScope`
        இந்த இணைப்பை உள்ளடக்கியிருந்தால் (`all`, அல்லது OAuth/cookie/session-க்கு `subscription`)
        → கூடுதலாக isActive = false. வரம்பு `subscription` ஆக இருக்கும்போது முன்பணம் செலுத்திய API விசைகள்
        செயலில் இருக்கும்.
      → கணக்குத் தேர்வின்போது இணைப்பு தவிர்க்கப்படும் (ஒருங்கிணைந்த QUOTA_BLOCKING நிலைகள்)
```

- இந்தப் பொருத்தம், பதில் **உடலில்** செய்யப்படும் **எழுத்துப் பெரிய/சிறிய வேறுபாடற்ற உட்சரத்** தேடலாகும்
  (`isAccountDeactivated`, `accountFallback.ts`).
- தடைச் சைகையைக் கொண்ட உடல் கிடைக்கும்போது, நிரந்தர `banned` இறுதிநிலையாக்கம் **எந்த
  HTTP நிலையிலும்** தூண்டப்படும் (`markAccountUnavailable` → `checkFallbackError` வழியாக). குறுகிய
  **`deactivated`** குறிச்சொல் (இணைப்பில் உபரி API விசைகள் இல்லாதபோது `isActive=false`) உள்வரி `chatCore.ts` பாதையால் **HTTP 401 / 403**-இல் எழுதப்படுகிறது
  (`classifyProviderError` → `ACCOUNT_DEACTIVATED` வழியாக வகைப்படுத்தப்படுகிறது). அதே `ACCOUNT_DEACTIVATED` சைகைக்காக `markAccountUnavailable()` பாதை _வேறொரு_ இறுதி நிலையான
  **`expired`**-ஐ (`resolveTerminalConnectionStatus` வழியாக) எழுதுகிறது என்பதைக் கவனிக்கவும்; எனவே பதிலை எந்தப் பாதை கையாண்டது என்பதைப் பொறுத்து, ஒரே தடை
  `deactivated` அல்லது `expired` எனத் தோன்றலாம். (பழைய குறியீட்டுக் கருத்துரை "401 உடலில் இந்தச் சரங்கள் இருக்கும்போது" என்று கூறுகிறது — அது தற்போதைய நடத்தையை முழுமையாக விவரிக்கவில்லை.)
- இறுதி நிலைகள் வடிகட்டப்படும் எல்லா இடங்களிலும் `banned` இணைப்பு தேர்விலிருந்து விலக்கப்படும்
  (`isTerminalConnectionStatus`, ஒருங்கிணைந்த `QUOTA_BLOCKING_CONNECTION_STATUSES`).

## வரம்பு — எந்த வழங்குநர்கள் ஸ்கேன் செய்யப்படுகிறார்கள்

**அனைத்து வழங்குநர்களும்.** தோல்வியடைந்த ஒவ்வொரு upstream கோரிக்கையும் கடந்து செல்லும் பொதுவான பிழை-கையாளல் pipeline-இல் இந்தச் சரிபார்ப்பு இயங்குகிறது — இது OAuth/subscription scrapers-க்கு மட்டும் கட்டுப்படுத்தப்படவில்லை. இதன் விளைவாக உருவாகும் terminal நிலை ஒவ்வொரு **connection**-க்கும் உரியது, ஒவ்வொரு provider-க்கும் அல்ல.

இருப்பினும், உள்ளமைந்த _strings_ உண்மையான தடை அபாயம் கொண்ட subscription/OAuth வழங்குநர்களை மையமாகக் கொண்டவை (ChatGPT Web Codex, Claude Web, Codex, Muse Spark, Antigravity). API-key வழங்குநரின் பிழை body-இல் substring-களில் ஒன்று அப்படியே இருந்தால் மட்டுமே அது detector-ஐத் தூண்டும்.

`autoDisableBannedScope` (`all` | `subscription`, இயல்புநிலை `all`) ஒரு பொருத்தம் `isActive=false` என்றும் மாற்ற வேண்டுமா என்பதைக் கட்டுப்படுத்துகிறது. `subscription` என்பது login-பாணியிலான seats-ஐக் குறிக்கிறது (கட்டண subscriptions மற்றும் இலவச accounts, web-cookie sessions உட்பட). Prepaid API keys-க்கு இது இன்னும் `testStatus=banned` எனப் பதிவுசெய்யும், ஆனால் அவற்றை routing pool-இல் தொடர்ந்து வைத்திருக்கும். நீடித்த வடிவமைப்பு என்பது ஒவ்வொரு provider மற்றும் ஒவ்வொரு account-க்குமான override ஆகும்; global enum அதன் முதல் செயலாக்கமாகும்.

## தனிப்பயன் தடைசெய்யப்பட்ட முக்கியச் சொற்கள்

**Security → Banned Keywords** என்பதில் keywords-ஐச் சேர்க்கவும் அல்லது நீக்கவும் (`PATCH /api/settings` வழியாக global `customBannedSignals` setting ஆக நிலையாகச் சேமிக்கப்படும்). அவை உள்ளமைந்த பட்டியலுடன் **சேர்க்கப்படுகின்றன** — ஒருபோதும் அதற்கு மாற்றாக அமையாது — மேலும் save செய்யும்போதும் (startup-இலும்) `setCustomBannedSignals()` வழியாக hot-reload ஆகின்றன. ஒவ்வொரு keyword-உம் அதிகபட்சம் 200 characters வரை மட்டுப்படுத்தப்பட்டுள்ளது; array நீளத்திற்கு வரம்பில்லை.

**⚠ தவறான நேர்மறை முடிவு அபாயம் — குறிப்பிட்ட சொற்றொடர்களைத் தேர்ந்தெடுக்கவும்.** முழு response body-இலும் raw substring பொருத்தமாக detection செயல்படுகிறது; ஒரு பொருத்தம் **நிரந்தரமானது** (1-year cooldown, manual recovery). மிகப் பொதுவான keyword, முழுமையாகச் செயல்படும் connection-ஐயும் தடை செய்யக்கூடும்:

- **மோசமானவை:** `quota`, `limit`, `error`, `denied` — பல தற்காலிகப் பிழைகளில் தோன்றுகின்றன.
- **நல்லவை:** முழுமையான தடை வாக்கியங்கள், எ.கா. `your account has been suspended for`,
  `account permanently banned`, `violation of our terms`.

உண்மையான தடையின்போது provider திருப்பித் தரும் மிக நீளமான, குழப்பமற்ற சொற்றொடரைத் தேர்ந்தெடுக்கவும். சந்தேகம் இருந்தால், முதலில் connection-இன் `lastError`-ஐக் கவனித்து, பின்னர் அதிலுள்ள சரியான வாசகத்தையே சேர்க்கவும்.

## குறியிடப்பட்ட connection-ஐ மீட்டெடுத்தல்

Terminal `banned` / `deactivated` நிலைகள் **ஒருபோதும் தானாக மீளாது** (அவை proactive-recovery tick-இலிருந்து விலக்கப்பட்டுள்ளன — `unavailable` cooldowns மட்டுமே தாமாக மீளும்). Operator அவற்றை வெளிப்படையாக நீக்க வேண்டும்:

1. **Connection-ஐ மீண்டும் சோதிக்கவும்** — dashboard-இன் **Test** செயல்
   (`POST /api/providers/{id}/test`); வெற்றிகரமான probe, `testStatus`-ஐ
   `active` என மீட்டமைத்து பிழை fields-ஐ அழிக்கும்.
2. **மீண்டும் authenticate செய்யவும் / credentials-ஐத் திருத்தவும்** — OAuth providers-க்கு, login
   / refresh flow-ஐ மீண்டும் இயக்கவும்; provider create/import routes `isActive = true` என அமைக்கும்.
3. **Connection-ஐ மீண்டும் இயக்கவும்** — auto-disable `isActive = false` என அமைத்திருந்தால்
   (`all` scope, அல்லது OAuth/cookie/session connection-க்கு `subscription`),
   account-ஐச் சரிசெய்த பிறகு அதை மீண்டும் இயக்கவும்.

தனியான "clear ban flag" button எதுவும் இல்லை — recovery என்பது re-test, re-auth அல்லது re-enable ஆகும்; இது
[RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md)-இல் உள்ள பொதுவான terminal-state விதியுடன் பொருந்துகிறது.

## Probe தனிமைப்படுத்தல் (model test-all)

`runAsProbe`-க்குள் இயக்கப்படும் **probe-origin failure** (model test-all / health-check dispatches) ஒருபோதும் pool-இலிருந்து connection-ஐ அகற்றாது (#9817): அது **பார்வைக்காகப் பதிவுசெய்யப்படும்** (`last_error`, `last_error_type`, `error_code`,
`last_error_at`), ஆனால் **ஒவ்வொரு** routing mutation-ஐயும் தவிர்க்கும் — cooldowns, terminal
status (`banned` / `deactivated` / `credits_exhausted`), per-model lockouts,
provider circuit breaker, 5-minute quota cache, OAuth token refresh
மற்றும் auto-disable. உண்மையான request-path failure மட்டுமே செயல்நீக்கம் செய்யும். பதிவுசெய்யப்பட்ட
பிழை, குறியிடப்பட்ட account-ஐ dashboard-இல் காணக்கூடியதாக்குகிறது; அதே நேரத்தில் அது
traffic-ஐத் தொடர்ந்து வழங்குகிறது.

ஒரே decision point `shouldIsolateProbeFailures()`
(`src/shared/utils/probeOrigin.ts`) ஆகும்; probe-origin failure-இலிருந்து
routing state-ஐ மாற்றக்கூடிய **ஒவ்வொரு** இடமும் இதைப் பயன்படுத்துகிறது:

- `markAccountUnavailable` (`auth.ts`) — பதிவு மட்டும் (`lastError` raw text,
  `lastErrorType`, `errorCode`, `lastErrorAt`; selection-time auto-decay-ஐத் தூண்டி
  பதிவை அழித்துவிடக்கூடிய `backoffLevel` வேண்டுமென்றே **சேர்க்கப்படவில்லை**)
- `maybeAutoDisableBannedAccount` — auto-disable இல்லை
- `chatCore` — FORBIDDEN, ACCOUNT_DEACTIVATED, QUOTA_EXHAUSTED (பதிவு மட்டும்,
  terminal `credits_exhausted` இல்லை), GEO_BLOCKED (24h விலக்கு இல்லை),
  MODEL_NOT_FOUND (`lockModel` இல்லை), codex 429 account-rotation failover
  (`markCodexScopeRateLimited` இல்லை, நிலையாகச் சேமிக்கப்பட்ட `rate_limited_until` இல்லை,
  session-affinity clear இல்லை), `persistCodexQuotaState` (quota-state write இல்லை,
  cache invalidation இல்லை), `recordKeyHealthStatus` (key-health rotator
  மாற்றப்படாது)
- OAuth refresh — executor base-இல் உள்ள proactive refresh
  (`base.ts` `execute()`, refresh-token rotation பயன்படுத்தப்படாது) மற்றும்
  `chatCore`-இல் உள்ள reactive 401/403 path (`expired` deactivation இல்லை) ஆகிய இரண்டும்
- `chat.ts` — provider circuit breaker மற்றும் 5-minute quota cache
  (`markAccountExhaustedFrom429`) ஒருபோதும் degraded ஆகாது

பதிவுசெய்யப்பட்ட பிழை, குறியிடப்பட்ட account-ஐ dashboard-இல் காணக்கூடியதாக்குகிறது;
அதே நேரத்தில் அது traffic-ஐத் தொடர்ந்து வழங்குகிறது. குறிப்பு: உண்மையான path-இன்
`slice(0,100)` truncation போலல்லாமல், probe பதிவு **raw**
(unsliced) error text-ஐச் சேமிக்கிறது.

Test-all-ஐ maintenance tool ஆகப் பயன்படுத்தும் operators, பின்வருவனவற்றில் ஏதேனும் ஒன்றின் வழியாக வரலாற்றுச் செயல்பாட்டை (probe ஒரு உண்மையான generation ஆகக் கணக்கிடப்படும்) மீட்டெடுக்கலாம்:

- `probeCanDisable` setting (`POST /api/settings` உடன்
  `{"probeCanDisable": true}`, அல்லது நேரடியான `key_value` DB திருத்தம்), அல்லது
- feature flag **`PROBE_CAN_DISABLE=true`** (env அல்லது DB override; setting-ஐ விட முன்னுரிமை பெறும்).

Fail-safe: flag அல்லது settings lookup exception எழுப்பினால், isolation தொடர்ந்து ON-இல் இருக்கும்.
