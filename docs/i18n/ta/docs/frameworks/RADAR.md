## பொது அறிவிப்பு வாசிப்பான்

பொதுவான அறிவிப்பு வாசிப்பான் Radar அம்சக் கொடியிலிருந்து தனியானது. டாஷ்போர்டின் Home மற்றும்
Changelog பார்வையகம், சாதாரண `GET` மூலம் களஞ்சியத்தின் பொது `news.json`-ஐ
`NEWS_JSON_URL`-இலிருந்து (`src/shared/utils/releaseNotes.ts`) பெறுகின்றன. அவை எந்த Radar அமைப்பு, prompt, provider
உள்ளமைவு, பயன்பாட்டுப் பதிவு அல்லது உள்ளூர் நிராகரிப்பு நிலையையும் அனுப்புவதில்லை.

`news.json`, `parseNewsPayload()` மூலம் செயல்படுத்தப்பட்ட மூடப்பட்ட v2 schema-ஐப் பயன்படுத்துகிறது:

- `schemaVersion: 2` மற்றும் வரம்பிடப்பட்ட `items[]` தொகுப்பு;
- நிலையான, தனித்துவமான அறிவிப்பு `id` மதிப்புகள்;
- வெளிப்படையான `active` மற்றும் ISO `publishedAt` புலங்கள்;
- கட்டாயமான ஆங்கில உரையுடன் விருப்பத்திற்குரிய உள்ளூர்மயமாக்கப்பட்ட உரை;
- விருப்பத்திற்குரிய, நற்சான்று தேவையற்ற HTTPS இணைப்புகள் மற்றும் அனுமதிப் பட்டியலில் உள்ள ஓர் icon;
- புதிய செயலில் உள்ளவை முதலில் என்ற தேர்வு, locale கிடைக்காதபோது ஆங்கிலத்திற்கான fallback, மற்றும் ஒவ்வொரு ID-க்குமான உள்ளூர் நிராகரிப்பு.

பழைய forks, Changelog காட்சி செயலிழக்காமல் இடம்பெயர்வதற்காக, முந்தைய ஒற்றை `{ active, title, message, ... }` வடிவத்தை parser தற்காலிகமாக ஏற்றுக்கொள்கிறது. செல்லுபடியாகாத feeds செயலற்றவையாக இருக்கும். Radar அறிமுகப் பதிவு `active: false` உடன் வெளியிடப்படுகிறது; அதை `true` என மாற்றுவது merge மற்றும் deploy ஆகியவற்றிற்குப் பிந்தைய தனியான release நடவடிக்கையாகும்; அது `RADAR_ENABLED` அல்லது தனித்துவமான feed-sync opt-in-ஐ மாற்றாது.

## கொடி: `RADAR_ENABLED` (இயல்பாக முடக்கப்பட்டுள்ளது)

Radar முழுமையாக `RADAR_ENABLED` அம்சக் கொடியால் கட்டுப்படுத்தப்படுகிறது
(`src/shared/constants/featureFlagDefinitions.ts`, வகை `policies`,
`defaultValue: "false"`).

**கொடி முடக்கப்பட்டிருக்கும்போது, இந்தப் பரப்பு இருப்பதே இல்லை:**

- உள்ளூர் model-state வாசிப்புகள் மற்றும் எழுதுதல்கள் உட்பட அனைத்து `/api/radar/*` endpoint-களும்,
  எந்த Radar module-ஐயும் தொடுவதற்கு முன் `404`-ஐ வழங்கும்.
- டாஷ்போர்டு திரைகள் (`/dashboard/radar`, `/dashboard/radar/setup`,
  `/dashboard/radar/combos`, `/dashboard/radar/offers`, `/dashboard/radar/intel`)
  `notFound()`-ஐ render செய்யும்.
- `getRadarCatalog()` (`src/lib/radar/index.ts`) எந்த மாற்றமும் இல்லாத baseline-ஐ வழங்கும் —
  அதே entry எண்ணிக்கை, அதே மதிப்புகள், ஒவ்வொரு entry-க்கும் `origin: "baseline"` tag — மேலும்
  feed cache-ஐ ஒருபோதும் வாசிக்காது.
- எந்த Radar network call-உம் ஒருபோதும் செய்யப்படாது; ஒவ்வொரு sync module-உம் `fetch`-ஐத்
  தொடுவதற்கு முன் `{ status: "disabled" }`-ஐ வழங்கும்.

இது கண்டிப்பான superset gate: கொடியை இயக்குவது _திரைகளை_ மட்டுமே திறக்கும்,
வேறெதையும் அல்ல. இது தரவை upload செய்யாது, background sync-ஐத் தொடங்காது, மேலும்
routing அல்லது model தேர்வை மாற்றாது — கீழே உள்ள தனியான opt-in-ஐப் பார்க்கவும்.

## தரவு sync ஒரு தனியான opt-in — தனியுரிமை வாக்குறுதி

`RADAR_ENABLED`-ஐ இயக்குவது UI-ஐ மட்டுமே திறக்கும். Feed-ஐ sync செய்வதற்கு
`radar_settings.opt_in`-இல் சேமிக்கப்படும் இரண்டாவது, தனித்த opt-in தேவை (`src/lib/db/radar.ts`,
migration `136_radar_cache_settings.sql`). எந்த network call-ஐயும் செய்வதற்கு முன் `syncRadar()` கொடியையும் _மற்றும்_
opt-in-ஐயும் சரிபார்க்கிறது:

```
கொடி முடக்கம்   → { status: "disabled" }   — network call இல்லை
Opt-in false    → { status: "opt_out" }    — network call இல்லை
```

இரண்டும் இயக்கப்பட்டிருக்கும்போது, sync பாதை பின்வருமாறு:

1. `x-omniroute-radar-schema: 2` மற்றும் விருப்பத்திற்குரிய
   `Authorization: Bearer <supporter key>` header உடன் `GET <feed base URL>/v1/catalog/latest` (கீழே பார்க்கவும்). Schema header இல்லாதபோது servers தனியாகக்
   கையொப்பமிடப்பட்ட v1 transition artifact-ஐ இயல்புநிலையாக வழங்குவதால், நிறுவப்பட்ட பழைய clients தொடர்ந்து
   updates-ஐப் பெறுகின்றன.
2. இது download-only application flow ஆகும்; இருப்பினும் இது ஓர் HTTPS request. Hosted
   infrastructure, source IP போன்ற வழக்கமான connection metadata-ஐப் பெறுகிறது. Supporter
   key உள்ளமைக்கப்பட்டிருக்கும்போது, entitlement-ஐ service தீர்மானிக்கும்படி sync அந்த key-ஐ Bearer header-இலும் அனுப்புகிறது.
   மேலே உள்ள evidence boundary-இல் அடையாளப்படுத்தப்பட்ட துல்லியமான private-server revision-இல்,
   feed-request கணக்கீடு, key hashes, aggregate usage மற்றும் கைமுறை abuse review-க்காக IP-இன்
   தினசரி சுழலும் truncated HMAC ஆகியவற்றைப் பயன்படுத்துகிறது; அந்த tables, key அல்லது IP-ஐ raw வடிவில் சேமிப்பதில்லை.
   Infrastructure access logs மற்றும் encrypted delivery outbox ஆகியவை தனித்தனி operational
   boundaries ஆகும்.
3. OmniRoute ஒருபோதும் prompts, responses, conversations, provider credentials, model traffic,
   uptime, latency அல்லது உள்ளூர் provider உள்ளமைவை Radar service-க்கு அனுப்பாது.
4. Response சரிபார்க்கப்பட்டு, செல்லுபடியாக்கப்பட்டு, உள்ளூரில் cache செய்யப்படுகிறது (பார்க்க:
   [பாதுகாப்பு மாதிரி](#security-model)). Radar-க்கு சரியாக நான்கு server-side network paths உள்ளன:
   catalog-க்காக `syncRadar()`, referrals-க்காக `syncRadarReferrals()`, மேலும்
   supporter-only offers மற்றும் Intel-க்காக `syncRadarOffers()` / `syncRadarIntel()`.

**Supporter key** என்பது எந்த tier-ஐ வழங்க வேண்டும் என்பதை feed service தீர்மானிக்க உதவும் விருப்பத்திற்குரிய Bearer token (`radar_settings.supporter_key`)
ஆகும் (பார்க்க:
[Tiers](#tiers-community-and-live)). இது:

- Provider credentials-க்குப் பயன்படுத்தப்படும் அதே AES-256-GCM `encrypt()`/`decrypt()`
  helpers (`src/lib/db/encryption.ts`) மூலம் **சேமிப்பிடத்தில் encrypted** ஆக வைக்கப்படுகிறது.
- `POST /api/radar/settings` (`{ supporterKey: "omr_" + 40 hex chars }`) மூலம் அமைக்கப்படுகிறது; மேலும்
  **ஒருபோதும் மீண்டும் வெளியிடப்படாது** — response மறைக்கப்பட்ட வடிவத்தை (`omr_****abcd`) வழங்குகிறது.
- அதை மாற்றுவது அல்லது அழிப்பது catalog, referrals, offers மற்றும் Intel caches அனைத்தையும் atomically செல்லாததாக்குகிறது. அடுத்த
  sync/read புதிய entitlement-ஐ server-side-இல் தீர்மானிக்கிறது; ஒரு key-ஐச் சேமிப்பது தானாகவே
  network request-ஐச் செய்யாது அல்லது single-use activation key-ஐப் பயன்படுத்தாது.
- Sync GET-இல் Bearer token ஆக feed service-க்கு அனுப்பப்படுகிறது — key குறித்த வேறு எதுவும்
  client-ஐ விட்டு வெளியேறாது.

குறியாக்கச் சாதன குத்தகையைப் பராமரிப்பதோ இல்லை. மேலே சரிபார்க்கப்பட்ட தனியார்-சேவையகத் திருத்தத்தில், செயல்படுத்தப்பட்ட அமலாக்கம்
உரிமைச் சரிபார்ப்பையும், அதே நேரடி விசை 24 மணிநேரத்திற்குள் நான்காவது
தனித்துவமான IP-இலிருந்து காணப்படும்போது உருவாகும் கைமுறை-மதிப்பாய்வு சமிக்ஞையையும் உள்ளடக்கியது. அந்தச் சமிக்ஞை ஒருபோதும் ஒரு விசையைத் தானாகத் தடுக்கவோ ரத்து செய்யவோ செய்யாது. மீட்பு,
இழந்த விசையை ரத்து செய்து மாற்றுகிறது; அதே நேரத்தில் தற்போதைய காலாவதியைப் பாதுகாக்கிறது; வாங்கப்பட்ட
அல்லது வழங்கப்பட்ட காலத்தை அது மீண்டும் தொடங்காது.

நேரடி சலுகைகள் கைமுறையாகத் தொகுக்கப்படுகின்றன; அவை மாறலாம் அல்லது காலாவதியாகலாம். விருப்ப ஒப்புதல் திரை சரியான
தனியுரிமை எல்லையையும் குறிப்பிடுகிறது: கையொப்பமிடப்பட்ட பட்டியல்/பரிந்துரை மெட்டாடேட்டா பதிவிறக்கப்படுகிறது; செல்லுபடியாகும் விசை கூடுதலாக
கையொப்பமிடப்பட்ட சலுகைகளையும் Intel-ஐயும் திறக்கிறது; Bearer விசையும் வழக்கமான இணைப்பு மெட்டாடேட்டாவும் ஹோஸ்ட் செய்யப்பட்ட சேவையைச் சென்றடைகின்றன;
தூண்டல்கள், பதில்கள், உரையாடல்கள், வழங்குநர் சான்றுகள், மாதிரி போக்குவரத்து, செயல்பாட்டு நேரம், தாமதம் மற்றும் உள்ளூர்
வழங்குநர் உள்ளமைவு ஆகியவை சென்றடைவதில்லை.

## ஆதரவாளர் விசையைப் பெறுதல்

செயல்படுத்தல் திரை (`/dashboard/radar`), ஆதரவாளர் விசையைப் **பெறுவதற்கான** இரண்டு செயல்முறைகளுக்கான இணைப்புகளை வழங்குகிறது. OSS களஞ்சியம் தானாக எந்த விசையையும் வழங்குவதில்லை, கட்டணக் குறியீட்டை ஒருபோதும் இயக்குவதில்லை, மேலும் **விலையை ஒருபோதும் குறிப்பிடுவதில்லை** — விலை நிர்ணயம் செய்யப்பட்டு முழுமையாக இலக்குப் பக்கங்களிலேயே காட்டப்படுகிறது; இந்தக் களஞ்சியத்தில் அல்ல (விவரக்குறிப்பு முடிவு D14).

- **"நான் ஒரு பங்களிப்பாளர்"** — `RADAR_CONTRIBUTOR_CLAIM_URL`-ஐத் திறக்கிறது (இயல்புநிலை
  `https://radar.omniroute.online/auth/github`); இது தனிப்பட்ட Radar சேவையகத்தில் ஹோஸ்ட் செய்யப்பட்டுள்ள GitHub OAuth உரிமைகோரல் செயல்முறையாகும். இது சமீபத்திய முழுமையான வாராந்திர தரவரிசையைச் சரிபார்க்கிறது: முதல் 10 இடங்களைப் பெறுபவர்களுக்கு 365 நாட்களும்,
  11–100 இடங்களைப் பெறுபவர்களுக்கு 90 நாட்களும் வழங்கப்படும். முதல் 100 இடங்களுக்கு வெளியே, PR எண்ணிக்கை ஒருபோதும் அணுகலை வழங்காது; அதற்குப் பதிலாக இந்தச் செயல்முறை தனியான நட்சத்திரமிடுதல் + பின்தொடர்தல் அடிப்படையிலான ஒற்றைப் பயன்பாட்டு நிலையைச் சரிபார்க்கிறது.
- **"திட்டத்தை ஆதரிக்கவும்"** — `RADAR_SUPPORTER_PLANS_URL`-ஐத் திறக்கிறது (இயல்புநிலை
  `https://radar.omniroute.online/planos`); இது ஒருமுறை செலுத்தும் 6 மாத, 1 ஆண்டு மற்றும்
  வாழ்நாள் விருப்பங்களுக்கான ஹோஸ்ட் செய்யப்பட்ட பக்கமாகும். OSS பக்கம் இன்னும் எந்தப் பண மதிப்பையும் காட்டாது.

இரண்டு URL-களும் சேவையகப் பக்கத்தில் தீர்மானிக்கப்படுகின்றன (`src/lib/radar/links.ts`, `RADAR_FEED_URL` பயன்படுத்தும் அதே env-மேலெழுதும்
முறை) மற்றும் ஏற்கனவே உள்ள
`GET /api/radar/settings` பதில் (`contributorClaimUrl`, `supporterPlansUrl`) மூலம் டாஷ்போர்டுக்கு அனுப்பப்படுகின்றன — கிளையன்ட் கூறு `process.env`-ஐத் தானாக ஒருபோதும் வாசிப்பதில்லை.

### தொலைந்த ஆதரவாளர் விசையை மீட்டெடுத்தல்

ஹோஸ்ட் செய்யப்பட்ட சேவையின் மீட்பு நுழைவுப்புள்ளி `https://radar.omniroute.online/recover`; இது திட்டங்கள் பக்கத்திலிருந்தும்
இணைக்கப்பட்டுள்ளது. உள்ளூர் நிறுவல் வாங்குபவர்/பங்களிப்பாளரின் மின்னஞ்சலை ஒருபோதும் பெறாததாலும், அதன் மறைகுறியாக்கப்பட்ட அமைப்புகளிலிருந்து மூல விசையை மீண்டும் உருவாக்க முடியாததாலும், மீட்பு முழுவதுமாக OSS கிளையன்ட்டுக்கு வெளியிலேயே இருக்கும்.

1. விசையுடன் தொடர்புடைய மின்னஞ்சலைச் சமர்ப்பிக்கவும். மீட்டெடுக்கக்கூடிய உரிமம் இருந்தாலும் இல்லாவிட்டாலும் சேவை அதே ஏற்றுக்கொள்ளப்பட்ட பக்கத்தையே வழங்கும்; எனவே படிவம் கணக்குகளைப் பட்டியலிட்டு வெளிப்படுத்தாது.
2. தகுதி இருந்தால், வழங்கல் வொர்க்கர் குறுகிய ஆயுளுள்ள, ஒருமுறை மட்டுமே பயன்படுத்தக்கூடிய இணைப்பை அனுப்பும். அதைத் திறந்தவுடன் டோக்கன் உடனடியாக ஒரு தற்காலிக மறைகுறியாக்கப்பட்ட `HttpOnly`/`Secure` குக்கிக்குள் நகர்த்தப்பட்டு, தூய்மையான
   `/recover` URL-க்கு வழிமாற்றப்படும்; பக்கத்தில் டோக்கன், மின்னஞ்சல், பழைய விசை அல்லது மாற்று விசை எதுவும் இருக்காது.
3. திரும்பப்பெறுதலை உறுதிப்படுத்தவும். தனிப்பட்ட சேவை முந்தைய விசையைத் திரும்பப்பெற்று, அதே திட்டம்/காலாவதியுடன் மாற்று விசையை உருவாக்கி, ஒரே பரிவர்த்தனையில் அதை மின்னஞ்சலுக்காக வரிசைப்படுத்தும். மாற்று விசை ஒருபோதும் உலாவிக்குத் திருப்பி அனுப்பப்படாது.
4. மாற்று விசையை `/dashboard/radar`-இல் ஒட்டவும். பழைய விசை இப்போது `community` நிலைக்குக் குறைய வேண்டும்; மாற்று விசை சரிபார்க்கப்பட்ட `live` ஒத்திசைவை உருவாக்க வேண்டும். அதே மீட்பு இணைப்பை மீண்டும் திறப்பது பொதுவான தவறானது/காலாவதியானது என்ற பதிலுடன் தோல்வியடைய வேண்டும்.

ஹோஸ்ட் செய்யப்பட்ட மீட்பு வழித்தடமும் அஞ்சல் வொர்க்கரும் குறியீட்டில் இருந்தாலும், ஒரு குறிப்பிட்ட வரிசைப்படுத்தலில் கிடைக்காமல் இருக்கலாம். சேவையகம் வரிசைப்படுத்தப்பட்டு, வழங்கல் வழங்குநர் கட்டுப்படுத்தப்பட்ட பெறுநருடன் கட்டமைக்கப்பட்டு, முழுமையான ஒருமுறைப் பயன்பாட்டு இணைப்பு சோதிக்கப்படும் வரை இந்தச் செயல்முறையை உற்பத்திக்குத் தயாரானது என்று கூற வேண்டாம்.

ஒரு பார்வையாளர் விசையைப் பெற்றதும் (`omr_` + 40 hex எழுத்துகள்), செயல்படுத்தல் திரையில்
(`src/app/(dashboard)/dashboard/radar/page.tsx`) விசையை ஒட்டுவதற்கான உள்ளீடு முதன்மைப் பாதையாக உள்ளது:
ஒரு விசையை ஒட்டிச் சமர்ப்பிப்பது ஒரே அழைப்பில் `POST /api/radar/settings`
(`{ optIn: true, supporterKey }`)-ஐ அனுப்புகிறது — விசையை ஒட்டுவது அதை அமைப்பதுடன் பங்கேற்பையும் இயக்கி,
திரையைத் திறக்கிறது. வடிவமைப்பு (`omr_` + 40 hex எழுத்துகள்) முதலில் கிளையன்ட் பக்கத்தில் பகிரப்பட்ட `isValidSupporterKeyFormat()` உதவிச் செயல்பாட்டின் (`src/lib/radar/supporterKey.ts`) மூலம் UX வசதிக்காகச் சரிபார்க்கப்படுகிறது; எந்த நிலையிலும் சேவையகத்தின் Zod schema-வே அதிகாரப்பூர்வச் சரிபார்ப்பாகும். ஒரு விசை அமைக்கப்பட்டதும், செயல்படுத்தல் திரை வெற்று உள்ளீட்டுக்குப் பதிலாக முகமூடியிடப்பட்ட வடிவத்தை (`GET /api/radar/settings`-இலிருந்து `supporterKeyMasked`) காட்டும்; புதிய விசையை ஒட்டுவதற்கான "விசையை மாற்று" கட்டுப்பாடும் இருக்கும் — மூல விசை ஒருபோதும் மீண்டும் காட்டப்படாது. மேலே உள்ள இரண்டு உரிமைகோரல்/திட்டங்கள் பொத்தான்களே முதலில் விசையைப் _பெறுவதற்கான_ வழியாகத் தொடர்கின்றன; ஏற்கனவே விசையை வைத்துள்ள ஓர் இயக்குநர் அதை இங்கே செயல்படுத்துகிறார்.

### முழுமையான செயல்படுத்தலும் வழிகாட்டப்பட்ட அமைப்பும்

தனிப்பட்ட feed சேவைக்கும் இந்த OSS கிளையன்ட்டுக்கும் இடையே திட்டமிட்டு குறுகிய எல்லை உள்ளது: சேவை ஆதரவாளர் விசையை வழங்கிச் சரிபார்க்கிறது; அதே நேரத்தில் உள்ளூர் OmniRoute நிறுவல் விசையை மறைகுறியாக்கி, கையொப்பமிடப்பட்ட கலைப்பொருட்களை சேவையகப் பக்கத்தில் ஒத்திசைத்து, வழங்குநர் அமைப்புக்கு வழிகாட்டுகிறது. உதவியுடனான சரிபார்ப்பு வரிசை:

1. பங்களிப்பாளர் உரிமைகோரல், plans/checkout, மீட்பு பயணம் அல்லது அங்கீகரிக்கப்பட்ட தனியார் சர்வர் இயக்குநரிடமிருந்து புதிதாக வழங்கப்பட்ட அல்லது மீட்டெடுக்கப்பட்ட விசையைப் பெறவும். மூல விசையைப் பதிவுகள், திரைப்பிடிப்புகள், issue கருத்துகள் அல்லது கட்டளை-வரி arguments ஆகியவற்றில் ஒட்ட வேண்டாம்.
2. உள்ளூர் OmniRoute நிறுவலில் `RADAR_ENABLED` அம்சக் கொடியை இயக்கவும். இது UI-ஐ வெளிப்படுத்தும், ஆனால் தனியான விருப்பச்சேர்வு சேமிக்கப்படும் வரை பிணையச் செயல்பாடு எதையும் மேற்கொள்ளாது.
3. `/dashboard/radar`-ஐத் திறந்து, விசையை ஒட்டி, செயல்படுத்தவும். உலாவி `{ optIn: true, supporterKey }` உடன் உள்ளூரில் ஒரு `POST /api/radar/settings` கோரிக்கையை அனுப்பும்; விசை உள்ளூரிலேயே குறியாக்கப்பட்டு, பதிலில் `omr_****<last4>` மட்டுமே இருக்கும்.
4. செயல்படுத்தல் திரையில் catalog sync இயங்க அனுமதிக்கவும் அல்லது **இப்போது ஒத்திசைக்கவும்** என்பதைத் தேர்ந்தெடுக்கவும். பக்கம் `live`, ஒரு feed பதிப்பு மற்றும் பெறப்பட்ட நேரத்தைத் தெரிவிக்கிறதா என்பதை உறுதிப்படுத்தவும். அங்கீகரிக்கப்பட்ட உள்ளூர் diagnostic-க்கு, `GET /api/radar/status` விசையைத் திருப்பி அனுப்பாமல் விருப்பச்சேர்வு/விசை இருப்பையும் நான்கு cache நிலைகளையும் தெரிவிக்கும். `POST /api/radar/sync-all` மூலம் catalog, referrals, offers மற்றும் Intel ஆகியவற்றை வெளிப்படையாகப் புதுப்பிக்கலாம்.
5. `/dashboard/radar/setup?provider=<provider>`-ஐத் திறக்கவும். provider-க்குச் சொந்தமான credential URL-ஐப் பின்தொடர்ந்து, **API விசையைச் சேர்க்கவும்** என்பதைத் தேர்ந்தெடுத்து, உண்மையான provider படிவத்தின் மூலம் சேமித்து, வழிகாட்டிக்குத் திரும்பி, **இணைப்பைச் சோதிக்கவும்** என்பதை இயக்கவும். வழிகாட்டி வழக்கமான `/api/providers` மற்றும் `/api/providers/<connection-id>/test` routes-ஐப் பயன்படுத்துகிறது; அது இணையான Radar credential ஒன்றை உருவாக்காது.
6. குறைந்தது இரண்டு இணக்கமான provider இணைப்புகள் செயலிலுள்ள பிறகு `/dashboard/radar/combos`-ஐத் திறக்கவும். பரிந்துரைக்கப்பட்ட family-ஐ மதிப்பாய்வு செய்து, ஏற்கனவே உள்ள combo API மூலம் combo-ஐ உருவாக்கவும். Offers மற்றும் Intel ஆகியவை தனித்தனி live-only signed caches ஆகவே இருக்கும்; அவற்றுக்கென உள்ள Radar பக்கங்களில் அவற்றைச் சரிபார்க்கலாம்.
7. `/dashboard/radar` மற்றும் setup பக்கத்தை மீண்டும் ஏற்றவும். விருப்பச்சேர்வு, மறைக்கப்பட்ட விசை நிலை, சரிபார்க்கப்பட்ட cache, சேமிக்கப்பட்ட provider இணைப்பு மற்றும் சோதனைச் செயல் ஆகியவை மீளேற்றத்திற்குப் பிறகும் நீடிக்க வேண்டும். மூல விசையும் provider credential-உம் இனி காணப்படாத பிறகு மட்டுமே ஆதாரத்தைப் பதிவு செய்யவும்.

ஒரு விசையைச் சேமிப்பது மட்டும் live entitlement-க்கான ஆதாரம் அல்ல. தனியார் சேவையின் `GET /v1/license/check` முடிவு, OSS catalog வழங்கும் `live` tier, சரிபார்க்கப்பட்ட signed cache மற்றும் உண்மையான provider இணைப்பு/சோதனைச் செயல்முறை ஆகியவற்றின் சேர்க்கையே ஆதாரமாகும். செல்லாத, காலாவதியான அல்லது திரும்பப்பெறப்பட்ட விசை catalog-ஐப் பாதுகாப்பாக `community` நிலைக்குக் குறைக்கும்; அது வெற்றிகரமான live-key validation எனத் தெரிவிக்கப்படக் கூடாது.

### தனியார் admin-panel இணைப்பு

`RADAR_ADMIN_URL` விருப்பத்தேர்வாக Costs பக்கப்பட்டிப் பிரிவில் பயனர் எதிர்கொள்ளும் Radar உருப்படிக்குப் பிறகு உடனடியாக **Radar Admin ↗** என்பதைச் சேர்க்கிறது. இதற்கு வேண்டுமென்றே default எதுவும் இல்லை: variable அமைக்கப்படாமல் அல்லது செல்லாததாக இருக்கும்போது, static sidebar, command palette மற்றும் sidebar-customization திரை ஆகியவற்றில் admin உருப்படியோ தனியார் URL-ஓ இருக்காது.

இந்த மதிப்பு server-side-இல் தீர்மானிக்கப்பட்டு, management-authenticated `GET /api/settings` பதில் மூலம் அங்கீகரிக்கப்பட்ட dashboard session-க்கு மட்டும் அல்லது உள்ளூர் no-login bootstrap நேரத்தில் நம்பகமான loopback உரிமையாளருக்கு மட்டும் அனுப்பப்படுகிறது. CLI, internal-service மற்றும் manage-scope API-key authentication ஆகியவை இதைப் பெறாது. வெளிப்புற இணைப்பை உருவாக்கும் முன் உலாவி பதிலை மீண்டும் சரிபார்க்கிறது; அந்த இணைப்பு `noopener noreferrer` உடன் திறக்கப்படும்.

Credential இல்லாத HTTPS tunnel/tailnet URL-ஐப் பயன்படுத்தவும். `http://127.0.0.1:9351` போன்ற loopback SSH forward-க்கு மட்டுமே plain HTTP ஏற்கப்படும்; பிற schemes, உட்பொதிக்கப்பட்ட credentials, தவறாக வடிவமைக்கப்பட்ட URLs மற்றும் தொலைநிலை HTTP destinations ஆகியவை பாதுகாப்பாக மறுக்கப்பட்டு navigation-ஐச் செயலற்றதாக விடும்.

## பாதுகாப்பு மாதிரி

### துல்லியமான பைட்டுகள் மீதான Ed25519 கையொப்பம்

ஊட்டத் தரவுச்சுமை Ed25519 மூலம் கையொப்பமிடப்படுகிறது. `verifyFeedBytes()`
(`src/lib/radar/verify.ts`) நெட்வொர்க் வழியாகப் பெறப்பட்ட **துல்லியமான மறுமொழி பைட்டுகள்**
மீதான கையொப்பத்தைச் சரிபார்க்கிறது — சரிபார்ப்பதற்கு முன் தரவுச்சுமை ஒருபோதும் மீண்டும்
தொடராக்கப்படுவதில்லை; எனவே, பைட்டுக்கு-பைட் மறுகுறியாக்கம் கையொப்பச் சரிபார்ப்பை
அமைதியாகச் செல்லாததாக்கவோ தவிர்க்கவோ முடியாது. சரிபார்ப்புத் தோல்வி
(`invalid_signature`), தரவுச்சுமை பாகுபடுத்தப்படுவதற்கோ தேக்ககத்தில் சேமிக்கப்படுவதற்கோ
முன்பே ஒத்திசைவை நிறுத்துகிறது.

### நிலைநிறுத்தப்பட்ட பொது விசை + விசைச் சுழற்சி

சரிபார்ப்புப் பொது விசை `src/lib/radar/pinnedKeys.ts`
(`PINNED_FEED_PUBLIC_KEYS`) இல் நிலைநிறுத்தப்பட்டுள்ளது. இது ஓர் அணியாக இருப்பதால்,
விசைச் சுழற்சிக்கு முன்பாகப் புதிய விசையைத் தொடக்கத்தில் சேர்க்க முடியும்; அதேவேளையில்,
முந்தைய விசையால் கையொப்பமிடப்பட்ட பழைய தேக்கக ஊட்டங்கள் மீண்டும் ஒத்திசைக்கப்படும் வரை
செல்லுபடியாக இருக்கும்.

### கிளையாக்கத்திற்கு ஏற்ற env மேலெழுதல்கள்

இரண்டு env மாறிகள், கிளைகள் மற்றும் சுயமாக ஹோஸ்ட் செய்பவர்கள் இயல்புநிலை OmniRoute
சேவைக்குப் பதிலாகத் தங்களுடைய ஊட்டத்தைப் பயன்படுத்துமாறு கிளையண்டை அமைக்க அனுமதிக்கின்றன
— கீழே உள்ள
[ஊட்டத்தைச் சுயமாக ஹோஸ்ட் செய்வது எப்படி](#how-to-self-host-a-feed) என்பதைப் பார்க்கவும்:

| மாறி                | நோக்கம்                                                                                                                     |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `RADAR_FEED_URL`    | ஊட்டத்தின் அடிப்படை URL-ஐ மேலெழுதுகிறது (இயல்புநிலை `https://radar.omniroute.online`).                                      |
| `RADAR_FEED_PUBKEY` | நிலைநிறுத்தப்பட்ட பொது விசையை (base64-DER SPKI அல்லது PEM) மேலெழுதி, உள்ளமைக்கப்பட்ட அணியை இந்த ஒற்றை விசையால் மாற்றுகிறது. |

### குறைந்தபட்சப் பதிப்பு

பதிவிறக்கப்பட்ட ஊட்டத்தின் `version`, தற்போது தேக்ககத்தில் உள்ள பதிப்பைவிட கண்டிப்பாகப்
புதியதாக இல்லாவிட்டால், `syncRadar()` அதை நிராகரிக்கிறது (`compareVersions()`,
புள்ளிகளால் பிரிக்கப்பட்ட `YYYY.MM.DD.n` ஒப்பீடு) — `{ status: "stale" }`. இதனால்,
சமரசம் செய்யப்பட்ட அல்லது தவறாக உள்ளமைக்கப்பட்ட ஊட்ட முனைப்புள்ளி, ஒரு கிளையண்டை
பழையதும் வேறு விதமாகக் கையொப்பமிடப்பட்டதுமான தரவுச்சுமைக்குப் பின்னோக்கி மாற்றுவது
தடுக்கப்படுகிறது.

### இரண்டு தேதிகள், மேலும் இரண்டுமே ஏன் வைக்கப்படுகின்றன

தேக்ககத்தில் உள்ள ஓர் ஊட்டம் இரண்டு தனித்தனி தேதிகளைக் கொண்டுள்ளது; அவற்றைக் குழப்பாமல்
இருப்பதே இரண்டையும் வைத்திருப்பதன் முழு நோக்கம்:

| புலம்         | எங்கிருந்து வருகிறது             | எதற்குப் பதிலளிக்கிறது                     |
| ------------- | -------------------------------- | ------------------------------------------ |
| `generatedAt` | கையொப்பமிடப்பட்ட ஊட்ட உள்ளடக்கம் | **தரவு** எவ்வளவு பழையது                    |
| `fetchedAt`   | இந்த நிறுவலின் கடிகாரம்          | இந்த நிறுவல் அதை எப்போது **பதிவிறக்கியது** |

சில நிமிடங்களுக்கு முன்பு பெறப்பட்ட ஓர் ஊட்டத்தில் பல வாரங்கள் பழைய புள்ளிவிவரங்கள்
இருக்கக்கூடும்; எனவே, மேலடுக்கின் அடிப்படைத் தரவைக் காட்டிலும் அது புதிதானதா என்பதை
`fetchedAt` மட்டும் ஓர் இயக்குநருக்குத் தெரிவிக்க முடியாது. இரண்டுமே
`radar_feed_cache` இல் நிலையாகச் சேமிக்கப்பட்டு, `getRadarCatalog().meta` மூலம்
திருப்பி அளிக்கப்பட்டு, `GET /api/radar/status` மூலம் தனித்தனியாக அறிக்கையிடப்படுகின்றன.
`generated_at` நெடுவரிசை உருவாக்கப்படுவதற்கு முன்பு (இடம்பெயர்வு 163) தேக்ககத்தில்
சேமிக்கப்பட்ட ஒரு வரிசை `null` ஆக மீண்டும் வாசிக்கப்படும் — பெறப்பட்ட நேரத்தைப்
பயன்படுத்துவதற்குப் பதிலாக, தெரியாதது தெரியாததாகவே இருக்கும்.
`radar_referrals_cache`, இடம்பெயர்வு 142 முதல் அதன் சொந்த `generated_at` மதிப்பை
வைத்துள்ளது.

மேலே உள்ள குறைந்தபட்சப் பதிப்பு, எந்தத் தேதியையும் அல்லாமல் `version`-ஐ ஒப்பிடுகிறது.

இரண்டு இடைவெளிகள் எஞ்சியுள்ளன; இரண்டுமே திட்டமிட்டவை: டாஷ்போர்டு இன்னமும் `Last fetched`
என்பதை மட்டுமே காட்டுகிறது; எனவே அங்கு உருவாக்கத் தேதியைக் காட்ட ஒரு புதிய லேபிளும்
(மேலும் அதற்கான 41 மொழிபெயர்ப்பு உள்ளீடுகளும்) தேவைப்படுகின்றன; மேலும் offers மற்றும் intel
தேக்ககங்கள், அவற்றின் ஊட்டத் திட்டவரைகள் ஒரு உருவாக்கத் தேதியைக் கொண்டிருந்தாலும், அதைச்
சேமிப்பதில்லை — எனவே `GET
/api/radar/status`, "தெரியவில்லை" என்று பொருள்படக்கூடிய `null` மதிப்பை அறிக்கையிடுவதற்குப்
பதிலாக, அந்த இரண்டுக்கும் அந்தப் புலத்தைத் தவிர்க்கிறது.

### திட்டவரைச் சரிபார்ப்பு

பதிவிறக்கப்பட்ட பைட்டுகள், கையொப்பச் சரிபார்ப்பிற்குப் **பிறகு**
`RadarFeedSchema`-க்கு (`src/lib/radar/feedSchema.ts`, ஒரு Zod திட்டவரை) எதிராகப்
பாகுபடுத்தப்பட்டுச் சரிபார்க்கப்படுகின்றன. திட்டவரைப் பொருத்தமின்மை
`{ status: "invalid_schema" }` என்பதைத் திருப்பி அளிக்கிறது; தேக்ககம் மாற்றப்படாமல்
விடப்படுகிறது. தேக்ககத் தரவுச்சுமை ஒவ்வொரு வாசிப்பின்போதும் (`getRadarCatalog()`)
தற்காப்பு நோக்கில் மீண்டும் சரிபார்க்கப்படுகிறது — சிதைந்த அல்லது கையால் திருத்தப்பட்ட
தேக்கக வரிசை வழங்கப்படுவதற்குப் பதிலாக அடிப்படைத் தரவுக்குத் திரும்புகிறது.

### மறுமொழி அளவு வரம்பு (10 MB)

ஊட்ட மறுமொழி உள்ளடக்கத்தின் மீது `syncRadar()` ஒரு **10 MB கடுமையான வரம்பை**
அமல்படுத்துகிறது — கையொப்பமிடப்பட்ட ஊட்டம் KB அளவிலான JSON ஆவணம் என்பதால், இதைத்
தாண்டும் எதுவும் சட்டபூர்வமான தரவுத்தொகுப்பைக் குறிக்காமல், தவறாக உள்ளமைக்கப்பட்ட அல்லது
தீங்கிழைக்கும் `RADAR_FEED_URL`-ஐ (அல்லது தேவையற்ற தரவை வழங்கும் மேல்நிலைச் சேவையை)
சுட்டிக்காட்டுகிறது. அமலாக்கம் இரண்டு அடுக்குகளைக் கொண்டது:

1. தலைப்பிலேயே வரம்பை மீறிய மதிப்பு அறிவிக்கப்பட்டிருந்தால், `Content-Length`
   முன்சரிபார்ப்பு உள்ளடக்கத்தை வாசிப்பதை முழுமையாகத் தவிர்க்கிறது.
2. உள்ளடக்கத்தை வாசிக்கும்போது இயங்கும் மொத்தச் சரிபார்ப்பு, `Content-Length`
   இல்லாவிட்டாலும் அல்லது உண்மையான அளவைக் குறைத்துக் காட்டினாலும் வரம்பை அமல்படுத்துகிறது
   — தலைப்பு மட்டும் ஒருபோதும் நம்பப்படுவதில்லை. சேர்க்கப்பட்ட துண்டுகளை ஒன்றிணைப்பது,
   அதன் பிறகு நடைபெறும் Ed25519 கையொப்பச் சரிபார்ப்பிற்குத் தேவையான துல்லியமான பைட்டுகளைப்
   பாதுகாக்கிறது.

வரம்பை மீறுவது `{ status: "too_large" }` என்பதைத் திருப்பி அளித்து, தேக்ககத்தை
மாற்றாமல் விடுகிறது; இது மற்ற ஒவ்வொரு ஒத்திசைவுத் தோல்விக்கும் பின்பற்றப்படும் அதே
அழிவற்ற முறையைப் பின்பற்றுகிறது (`invalid_signature`, `invalid_schema`, `stale`).

## அடுக்குகள்: `community` மற்றும் `live`

ஃபீட் ஸ்கீமாவில் `tier: "community" | "live"` புலம் உள்ளது. கோரிக்கையின் அடிப்படையில் (ஆதரவாளர் விசை உள்ளதா, செல்லுபடியாகிறதா என்பதைப் பொறுத்து) ஃபீட் சேவை இதை **சேவையகப் பக்கத்தில்** தீர்மானிக்கிறது — கிளையன்ட் ஒருபோதும் தனது அடுக்கைத் தானே தீர்மானிப்பதில்லை.

- **`community`** — மிகப் புதிய தரவைவிட சுமார் 30 நாட்கள் தாமதமான இலவச பட்டியல். அங்கீகரிக்கப்படாத அல்லது செல்லாத விசையைக் கொண்ட கோரிக்கை இதையே பெறும்.
- **`live`** — செல்லுபடியாகும் ஆதரவாளர் விசையைக் கொண்ட கோரிக்கைகளுக்கு வழங்கப்படும் மிகப் புதிய பட்டியல்.

**செல்லாத அல்லது காலாவதியான ஆதரவாளர் விசை `community` ஆகத் தரமிறக்கப்படும் — அது ஒருபோதும் பிழையாகாது.** ஒத்திசைவுப் பாதை கையொப்பம்/ஸ்கீமா/பதிப்புத் தோல்விகளையும் (அனைத்தும் மீட்கக்கூடியவை; தேக்கக நிலையைக் கடுமையாகப் பாதிக்காதவை) வெற்றிகரமான `{ status:
"updated", version, tier }` முடிவையும் மட்டுமே வேறுபடுத்துகிறது. கிளையன்ட் கையாள வேண்டிய அடுக்கு சார்ந்த பிழைப் பாதை எதுவும் இல்லை.

### வழங்கப்பட்ட அடுக்கு கையொப்பமிடப்பட்ட உடலிலிருந்து அல்ல, பதில் தலைப்பிலிருந்து வருகிறது

கையொப்பமிடப்பட்ட ஃபீட் **உடலின்** `tier` புலம் எப்போதும் `"live"` ஆகவே இருக்கும் — ஃபீட் சேவை **ஒவ்வொரு பதிப்பிற்கும் கையொப்பமிடப்பட்ட இரண்டு கலைப்பொருட்களை** வழங்குகிறது: live தற்போதைய பிரச்சாரங்களை உள்ளடக்கும்; community அவற்றைத் தவிர்க்கும். ஒவ்வொரு கலைப்பொருளும் அதற்குரிய துல்லியமான பைட்டுகளின் அடிப்படையில் கையொப்பமிடப்படுகிறது. இருந்தாலும், உரிமைத் தீர்மானத்திற்கு உடல் ஆதாரமாக இருப்பதில்லை; ஒரு கோரிக்கைக்காக உண்மையில் தேர்ந்தெடுக்கப்பட்ட அடுக்கு **`x-omniroute-feed-tier` பதில் தலைப்பில்** இடம்பெறும். கோரிக்கையின் `Authorization` விசையின் அடிப்படையில் இது சேவையகப் பக்கத்தில் தீர்மானிக்கப்படுகிறது.

கிளையன்ட் நம்ப வேண்டிய அடுக்கைத் தீர்மானிக்கும் ஒரே இடம் `syncRadar()` (`src/lib/radar/sync.ts::parseServedTierHeader()`):

1. `RadarTierSchema` (Zod) மூலம் `x-omniroute-feed-tier`-ஐப் பகுப்பாய்வு செய்யவும் — தலைப்பு இல்லாவிட்டாலோ அல்லது அதன் மதிப்பு சரியாக `"community"` அல்லது `"live"` ஆக இல்லாவிட்டாலோ, அது **இல்லாததாகவே** கருதப்படும் (அப்படியே தேக்ககம்/UI-இல் ஒருபோதும் நம்பப்படாது; இந்தத் தலைப்பு அறிமுகமாவதற்கு முன்பிருந்த பழைய ஃபீட் சேவையகங்களும் இதில் அடங்கும்).
2. படி 1 எந்த மதிப்பையும் தராதபோது மட்டும், கையொப்பமிடப்பட்ட உடலின் `tier` புலத்தைப் பின்சார்பாகப் பயன்படுத்தவும் (அது எப்போதும் `"live"`).
3. தீர்மானிக்கப்பட்ட அடுக்கே தேக்ககத்தில் சேமிக்கப்பட்டு `{ status: "updated",
version, tier }` ஆகத் திருப்பி அனுப்பப்படும் — டாஷ்போர்டு காட்டுவது இந்த மதிப்பையே; மூல உடல் புலத்தை ஒருபோதும் அல்ல.

## வாசிப்பு நேர மேலடுக்கு ஒன்றிணைப்பு விதிகள்

`applyFeed()` (`src/lib/radar/applyFeed.ts`) நிலையான அடிப்படையின் **மேல்** தேக்கக ஃபீடை `getRadarCatalog()`-க்குள் **வாசிப்பு நேரத்தில்** ஒன்றிணைக்கிறது. அடிப்படை வரிசை (`FREE_MODEL_BUDGETS`) ஒருபோதும் மாற்றப்படுவதில்லை — ஒவ்வொரு அழைப்பின்போதும் ஒரு புதிய `MergedEntry[]` கணக்கிடப்படுகிறது.

முன்னுரிமை வரிசையில் நான்கு விதிகள்:

1. **ஃபீட் ஒருபோதும் உள்ளூர் மேலெழுதலை மாற்றி எழுதாது.** ஒவ்வொரு புலத்திற்கும்: ஓர் உள்ளீட்டிலுள்ள புலத்தை இயக்குநர் தனிப்பயனாக்கியிருந்தால் (`provider:modelId` விசையைக் கொண்ட `localOverrides` மேப்), அந்தக் குறிப்பிட்ட புலத்திற்கான ஃபீட் மதிப்பு தவிர்க்கப்படும் — இயக்குநரின் மதிப்பே வெல்லும்.
2. **`enabled: false` உள்ளீட்டை முடக்கும்; அதன் மூலமும் பதிவு செய்யப்படும்.** ஓர் உள்ளீட்டை முடக்கும் ஃபீட் உள்ளீடு, ஒன்றிணைக்கப்பட்ட முடிவில் `enabled: false` மற்றும் `disabledBy: "radar"` ஆகியவற்றை அமைக்கும். இதனால் ஓர் உள்ளீடு ஏன் கிடைக்கக்கூடிய நிலையிலிருந்து முடக்கப்பட்ட நிலைக்குச் சென்றது என்பதை UI விளக்க முடியும்.
3. **ஃபீடில் இல்லாத, பயனர் சேர்த்த உள்ளீடு மாற்றமின்றித் தொடரும்.** அடிப்படையில் மட்டும் உள்ள (அல்லது உள்ளூரில் சேர்க்கப்பட்ட), அதற்கிணையான ஃபீட் உள்ளீடு இல்லாத பதிவுகள் மாற்றமின்றிக் கடந்து செல்லும்.
4. **கல்லறைக் குறியிடப்பட்ட உள்ளீடு ஒருபோதும் மீண்டும் உயிர்ப்பிக்கப்படாது.** இயக்குநர் ஓர் உள்ளீட்டை வெளிப்படையாக நீக்கியிருந்தால் (`tombstones` தொகுப்பு), பிந்தைய பதிப்பில் ஃபீட் அந்த `provider:modelId`-ஐ மீண்டும் சேர்த்தாலும் அது திரும்பக் கொண்டுவரப்படாது.

திருத்தக்கூடிய புலங்களும் கல்லறைக் குறியீடுகளும் `radar_local_model_state`-இல் (இடம்பெயர்வு `153_radar_local_model_state.sql`) நிலையாகச் சேமிக்கப்படுகின்றன. பொது DB அடாப்டர் (`src/lib/db/radar.ts`) அந்த வரிசைகளை `applyFeed()` பயன்படுத்தும் `localOverrides` மேப் மற்றும் `tombstones` தொகுப்பாக மாற்றுகிறது; தயாரிப்புச் சூழலிலுள்ள `getRadarCatalog()`, கொடி, தேக்ககம் மற்றும் ஸ்கீமா வாயில்கள் கடந்த பிறகு அந்த நிலையை ஏற்றுகிறது. `displayName` மற்றும் `enabled` மட்டுமே இயக்குநரால் திருத்தக்கூடியவை. வழங்குநர்/மாடல் அடையாளம், ஃபீட் மூலம், ஒதுக்கீடு, திறன்கள், ToS மற்றும் அமைவுத் தரவு ஆகியவற்றை இந்த இடைமுகத்தின் வழியாக எழுத முடியாது.

டாஷ்போர்டு நான்கு உள்ளூர் செயல்களை வழங்குகிறது:

- **திருத்து** என்பது உள்ளூர் காட்சிப் பெயரையும் செயல்படுத்தப்பட்ட நிலையையும் மாற்றும்.
- **உள்ளூர் மாற்றங்களை மீட்டமை** என்பது கல்லறைக் குறியீட்டை மாற்றாமல் திருத்தக்கூடிய இரு புலங்களையும் அழிக்கும்.
- **மறை** என்பது கல்லறைக் குறியீட்டை உருவாக்கும்; இதனால் பிந்தைய ஃபீட் புதுப்பிப்புகள் அந்த வரிசையை மீண்டும் உருவாக்க முடியாது.
- **மீட்டெடு** என்பது கல்லறைக் குறியீட்டை நீக்கும்; தனியாகச் சேமிக்கப்பட்ட எந்த மேலெழுதலும் தொடர்ந்து செயல்படும்.

ஃபீடின் `enabled: false` பாதுகாப்பு விதிவிலக்காகத் தொடரும்: அது பழைய உள்ளூர் `enabled: true` மதிப்பை மீறி வென்று, ஒன்றிணைக்கப்பட்ட உள்ளீட்டை முடக்கப்பட்ட நிலையிலேயே வைத்து, `disabledBy: "radar"` என்பதைப் பதிவு செய்யும்.

பட்டியல் வெளியீடுகள் `schemaVersion: 2`-ஐப் பயன்படுத்துகின்றன. `contextWindow` மற்றும் `tools`, `vision`, `thinking` ஆகிய ஒவ்வொன்றும் தனித்தனியாக `number | null` / `boolean | null` ஆகும்: `null` என்பது தெரியாதது என்று பொருள்படும்; `false` என்பது அந்தத் திறன் இல்லை என்று D16 மூலம் உறுதிப்படுத்தப்பட்ட அதிகாரப்பூர்வ வழங்குநர் மூலம் வெளிப்படையாகக் குறிப்பிடுகிறது என்று பொருள்படும். உள் OmniRoute பதிவகம்/மாடல்-விவரக்குறிப்புக் கொடிகள் ஒருபோதும் நேரடியாக ஃபீட் உண்மைகளாக உயர்த்தப்படுவதில்லை. கிளையன்ட் இன்னமும் v1 ஸ்னாப்ஷாட்களை ஏற்றுக்கொள்கிறது; பழைய பில்டர் இல்லாமையைக் குறிக்கும் இடநிரப்பியாக `false`-ஐப் பயன்படுத்தியதால், v1 `false` தெரியாததாக இயல்பாக்கப்படுகிறது; அதேசமயம் v1 `true` உண்மையானதாகவே தொடர்கிறது. தெரியாத ஸ்கீமா பதிப்புகள் பாதுகாப்பாகத் தோல்வியடையும்; கடைசியாகச் செல்லுபடியான தேக்ககம் தொடர்ந்து கிடைக்கும். பூஜ்யமல்லாத சூழல்/திறனைக் கொண்ட ஒவ்வொரு v2 மாடலும் நற்சான்றுகள் தேவையற்ற HTTPS `metadataEvidenceUrls[]`-ஐக் கொண்டிருக்க வேண்டும்; இல்லையெனில் ஸ்கீமா சரிபார்ப்பு தோல்வியடைந்து, தேக்ககம் மாற்றப்படாது. பட்டியல் அட்டவணை மூன்று நிலைகளையும் `✓`, `✕` மற்றும் `?` ஆகக் காட்டுகிறது.

### வழிகாட்டப்பட்ட சேர்க்கைகளும் MCP அணுகலும்

உறுதிப்படுத்தப்பட்ட `familyId` மதிப்புகள் வாசிப்பு நேர மேலடுக்கைக் கடந்தும் நிலைத்து, தூய `buildRadarComboSuggestions()` மாட்யூலை (`src/lib/radar/comboSuggestions.ts`) இயக்குகின்றன. குறைந்தது இரண்டு தனித்துவமான வழங்குநர்கள் செயலில் உள்ள இணைப்புகளைக் கொண்டிருந்து, துல்லியமாகத் தொகுக்கப்பட்ட மாடல் ID-ஐ வெளிப்படுத்தினால் மட்டுமே ஒரு குடும்பம் பரிந்துரைக்கப்படும். முடக்கப்பட்ட மாடல்கள், செயலற்ற வழங்குநர்கள், விடுபட்ட மாடல் ID-கள், ஒரே உறுப்பினரைக் கொண்ட குடும்பங்கள் மற்றும் தெளிவற்ற மாற்றுப்பெயர்/முன்னொட்டுப் பொருத்தங்கள் ஆகியவை பாதுகாப்பாகத் தோல்வியடையும். பரிந்துரைகள் தற்போதுள்ள `priority` உத்தியைப் பயன்படுத்தி, அதிகமான தொடர் மாதாந்திர பட்ஜெட்டை முதலில் வரிசைப்படுத்துகின்றன; UI அவற்றை `POST /api/combos` மூலமாக மட்டுமே உருவாக்குகிறது.

வழிகாட்டப்பட்ட UI `/dashboard/radar/combos` இல் உள்ளது. இது உள்ளக
`GET /api/radar/catalog` மற்றும் `GET /api/combos/builder/options` முனைப்புள்ளிகளை மட்டுமே வாசிக்கிறது. இது ஒருபோதும் Radar ஒத்திசைவைத் தூண்டாது,
வழங்குநர் நற்சான்றுகளை வாசிக்காது அல்லது combo தரவுத்தளத்தில் நேரடியாக எழுதாது.

MCP கிளையன்ட்கள் அதே உள்ளகத் திட்டத்தை `omniroute_radar_catalog` (`read:radar`) மூலம் வாசிக்கலாம். விருப்பத்திற்குரிய
`provider`, `familyId`, மற்றும் `enabledOnly` வடிப்பான்கள் ஓர் உள்ளக
`GET /api/radar/catalog` வாசிப்பிற்குப் பிறகு மதிப்பீடு செய்யப்படுகின்றன. இதன் மூடப்பட்ட வெளியீட்டில் catalog metadata மற்றும் provider/model,
காட்சிப் பெயர், `familyId`, ஒதுக்கீடு, திறன்கள், இயக்கப்பட்ட நிலை, தோற்றம் மற்றும் `disabledBy` ஆகியவை அடங்கும்; அமைப்பு URL-கள்,
படிநிலைகள், இணைப்புகள், மின்னஞ்சல் முகவரிகள், விசைகள் மற்றும் பரிந்துரைத் தரவு ஆகியவை ஒருபோதும் திருப்பி அனுப்பப்படாது. இந்தக் கருவி
வாசிப்புக்கு மட்டுமானது மற்றும் ஒருபோதும் `/api/radar/sync`-ஐ அழைக்காது.

### தோற்றக் குறிப்பான்கள்

ஒன்றிணைக்கப்பட்ட ஒவ்வொரு பதிவிலும் UI ஒரு அடையாள வில்லையாகக் காட்டும் `origin` புலம் உள்ளது:

- `"baseline"` — நிலையான வெளியீட்டு catalog-இலிருந்து மாற்றப்படாதது.
- `"radar"` — feed மூலம் ஒன்று அல்லது அதற்கு மேற்பட்ட புலங்கள் புதுப்பிக்கப்பட்டன.
- `"local"` — இந்தப் பதிவில் இயக்குநர் குறைந்தது ஓர் உள்ளக மேலெழுதலைக் கொண்டுள்ளார் (feed என்ன கூறினாலும்,
  விதி 1-இன்படி உள்ளக மேலெழுதல்களே எப்போதும் முன்னுரிமை பெறும்).

| `/api/radar/local-model-state` | PATCH  | சரிபார்க்கப்பட்ட `displayName`/`enabled` override fields-ஐ அமைக்கிறது அல்லது அழிக்கிறது.                                                                     |
| `/api/radar/local-model-state` | PUT    | `{ provider, modelId, tombstoned }` மூலம் tombstone ஒன்றை உருவாக்குகிறது அல்லது அகற்றுகிறது.                                                                 |
| `/api/radar/local-model-state` | DELETE | ஏற்கனவே உள்ள tombstone-ஐப் பாதுகாத்தபடி திருத்தக்கூடிய override fields-ஐ அழிக்கிறது.                                                                         |

**கடுமையான விதி: இந்த routes ஒருபோதும் feed service-க்கு proxy ஆகாது.** Browser எப்போதும்
உள்ளூர் OmniRoute server உடன் மட்டுமே தொடர்புகொள்கிறது. Radar service-ஐ அணுகும் நான்கு modules
`src/lib/radar/sync.ts` (catalog), `src/lib/radar/referralsSync.ts` (referrals), மற்றும்
`src/lib/radar/offersSync.ts` (offers), அதோடு `src/lib/radar/intelSync.ts` (Intel); இவை அனைத்தும்
server-side-இல் இயங்குகின்றன, client-side-இல் ஒருபோதும் இயங்காது. இதனால்
feed URL மற்றும் எந்தவொரு supporter key-உம் client-facing network traffic-இலிருந்து முழுமையாக விலக்கி வைக்கப்படுகின்றன.

`RADAR_ENABLED` முடக்கப்பட்டிருக்கும்போது அனைத்து Radar endpoints-உம் `404`-ஐத் திருப்பியளிக்கின்றன (மேலேயுள்ள
[Flag](#flag-radar_enabled-default-off)-ஐப் பார்க்கவும்), மேலும் repo முழுவதற்குமான error-sanitization விதியின்படி
(`docs/security/ERROR_SANITIZATION.md`) route error responses-ஐ
`buildErrorBody()`/`sanitizeErrorMessage()` வழியாக அனுப்புகின்றன.

### அங்கீகாரம்

அனைத்து Radar endpoints-க்கும் `isAuthenticated()`
(`src/shared/utils/apiAuth.ts`) வழியாக authentication தேவை — dashboard session cookie அல்லது management-scoped
API key; இது `/api/settings/*`-இன் மற்ற பகுதிகளைப் பாதுகாக்கும் அதே gate ஆகும். Flag-off
`404` சோதனை எப்போதும் auth சோதனைக்கு **முன்னதாகவே** இயங்கும்; எனவே `RADAR_ENABLED`
முடக்கப்பட்டுள்ள installation byte-identical ஆகவே இருக்கும் (அந்த surface இல்லை என்பதை அறிய மட்டும் auth prompt வராது);
flag இயக்கப்பட்டதும், authentication இல்லாத request எந்தவொரு DB read அல்லது
write-க்கும் முன்பாக `401`-ஐப் பெறும். Auth state எதுவாக இருந்தாலும் `GET /api/radar/settings` ஒருபோதும் raw supporter key-ஐத் திருப்பியளிக்காது —
masked வடிவத்தையும் `hasSupporterKey` boolean-ஐயும் மட்டுமே திருப்பியளிக்கும்.

## ஆதரவாளர் சலுகைகள்

சலுகைகள் அவற்றுக்கென தனியாக கையொப்பமிடப்பட்ட artifact-ஐ, `GET /v1/offers/latest`, பயன்படுத்துகின்றன; மேலும் catalog அல்லது referrals cache-ஐ ஒருபோதும் பகிர்வதில்லை. server endpoint-க்கு செல்லுபடியாகும் live ஆதரவாளர் Bearer key தேவை; community fallback எதுவும் இல்லை. ஆகவே feature flag முடக்கப்பட்டிருந்தாலோ, operator விருப்பத் தேர்வு செய்யாமல் இருந்தாலோ அல்லது ஆதரவாளர் key எதுவும் உள்ளமைக்கப்படாமல் இருந்தாலோ, `syncRadarOffers()` network-ஐ அணுகுவதற்கு முன்பே நிறுத்தப்படும்.

GET வெற்றியடைந்த பிறகு, client துல்லியமான response bytes-ன் மீதான Ed25519 signature-ஐச் சரிபார்த்து, `RadarOffersFeedSchema`-ஐ validate செய்து, கையொப்பமிடப்பட்ட body மற்றும் `x-omniroute-feed-tier` header ஆகிய இரண்டும் `live` என்று குறிப்பிட வேண்டும் எனக் கட்டாயப்படுத்தி, கண்டிப்பாகப் புதிய dotted version-ஐ அமல்படுத்திய பிறகே `radar_offers_cache`-ஐ (migration `144_radar_offers_cache.sql`) அணு நிலையிலான செயல்பாடாக மாற்றுகிறது. மற்ற feeds பயன்படுத்தும் அதே 10 MB header-plus-stream வரம்பு இதற்கும் பொருந்தும். Signature, schema, tier, replay, size, HTTP மற்றும் network தோல்விகள் அனைத்தின்போதும் கடைசியாகச் சரிபார்க்கப்பட்ட cache பாதுகாக்கப்படும்.

மூடப்பட்ட offer வடிவம் ஒப்பிடக்கூடிய மூன்று benefit வகைகளை ஆதரிக்கிறது: basis points-ல் percentage, சிறிய currency units-ல் credit அல்லது trial days. ஒரு partner offer, அதே வகையைச் சேர்ந்த public baseline-ஐக் கட்டாயமாக உள்ளடக்க வேண்டும்; மேலும் அதன் benefit கண்டிப்பாக அதிகமாக இருக்க வேண்டும். Official offers-க்கு partner baseline கிடையாது. URLs, credentials இல்லாத HTTPS ஆக இருக்க வேண்டும். `getRadarOffers()` முன்னெச்சரிக்கையாக cached payload-ஐ மீண்டும் validate செய்து, ஒவ்வொரு local read-ன்போதும் காலாவதியான entries-ஐ வடிகட்டுகிறது; `/dashboard/radar/offers`, render செய்வதற்கு முன் காலாவதியை மீண்டும் வடிகட்டி, Portuguese உரை கிடைக்கும்போது அதைப் பயன்படுத்தி, இல்லையெனில் English fallback-ஐப் பயன்படுத்துகிறது; மேலும் partner offers-ஐ வெளிப்படையாக label செய்கிறது.

Browser, local routes-ஐ மட்டுமே அழைக்கிறது: அது masked settings snapshot-ஐப் படித்து, server-side-ல் புதுப்பிக்க `POST /api/radar/offers/sync`-ஐக் கோரி, பின்னர் `GET /api/radar/offers`-ஐப் படிக்கிறது. key இல்லாதபோது, feed request-ஐ முயற்சிப்பதற்குப் பதிலாக ஏற்கனவே உள்ள contributor/support links-ஐக் காட்டுகிறது. வெளிப்புற offer links, `noopener noreferrer` உடன் புதிய tab-ல் திறக்கப்படுகின்றன. இந்த release-ல் `radar_offers` MCP tool எதுவும் வழங்கப்படவில்லை.

## Radar Intel, ஆதரவாளர் badge மற்றும் CLI

Intel என்பது `GET /v1/intel/latest`-ல் கிடைக்கும் கையொப்பமிடப்பட்ட artifact ஆகும். மூடப்பட்ட `RadarIntelFeedSchema`, உறுதிப்படுத்தப்பட்ட comparisons-லிருந்து private curator உருவாக்கிய Radar-க்குச் சொந்தமான ELO rankings மற்றும் கையொப்பமிடப்பட்ட catalog snapshots-லிருந்து பெறப்பட்ட உண்மைசார்ந்த catalog வயது/எண்ணிக்கை deltas ஆகியவற்றை மட்டுமே ஏற்கிறது. Methodology, ஆரம்ப rating 1000 மற்றும் K=32 என நிலையாக நிர்ணயிக்கப்பட்டுள்ளது. எந்த comparison-மும் உறுதிப்படுத்தப்படாதபோது காலியான ranking செல்லுபடியாகும்; client ஒருபோதும் ஒன்றைச் செயற்கையாக உருவாக்காது.

`syncRadarIntel()`, offers-ஐப் போலவே அதே server-side Bearer, 30-second timeout, 10 MiB streamed cap, exact-byte Ed25519 verification, strict schema, `live` body/header தேவை, version floor மற்றும் கடைசியாகச் சரிபார்க்கப்பட்ட சிறந்த cache-ஐப் பாதுகாத்தல் ஆகியவற்றைப் பயன்படுத்துகிறது. சரிபார்க்கப்பட்ட live snapshot சேமிக்கப்பட்ட பிறகு, client `radar:<sha256(supporter key)>`-ஐப் பெற்று, அந்த one-way identity-ஐ மட்டும் சேமித்து, பிரத்யேகமான `radar_supporter` recognition event-ஐ வெளியிடுகிறது. அதன் `radar-supporter` badge idempotent ஆகும் மற்றும் பூஜ்ஜிய XP-ஐ வழங்குகிறது; அது ஒருபோதும் leaderboards-ஐப் புதுப்பிப்பதோ `token_share`-ஐ மீண்டும் பயன்படுத்துவதோ இல்லை. `/dashboard/radar/intel`, சரிபார்க்கப்பட்ட local cache metadata-விலிருந்து மட்டுமே badge-ஐ render செய்கிறது.

CLI, `omniroute radar status` மற்றும் `omniroute radar sync` ஆகியவற்றை வழங்குகிறது. இரண்டும் local OmniRoute API உடன் மட்டுமே தொடர்புகொள்கின்றன. `status`, read-only `GET /api/radar/status`-ஐச் செய்கிறது; `sync`, ஒரே ஒரு `POST /api/radar/sync-all`-ஐ அனுப்பி, ஒவ்வொரு feed-க்குமான முடிவை அச்சிடுகிறது. எந்த command-மும் ஆதரவாளர் key-ஐப் படிப்பதோ, ஏற்றுக்கொள்வதோ அல்லது அச்சிடுவதோ இல்லை; மேலும் எந்த command-மும் Radar service-ஐ நேரடியாகத் தொடர்புகொள்வதில்லை.

## பரிந்துரை இணைப்புகள் (இலவச கிரெடிட்கள்)

பரிந்துரை இணைப்புகள், பட்டியல் ஊட்டத்திலிருந்து தனியாக உள்ள ஒரு **தனித்தியங்கும், எப்போதும் தற்போதைய நிலையில் இருக்கும்** ஊட்டத்திலிருந்து வழங்கப்படுகின்றன —
`GET /v1/referrals/latest`. இது வேண்டுமென்றே செய்யப்பட்ட வடிவமைப்பு: சமூக அடுக்கிலுள்ள
பட்டியல் ஊட்டம் அதிகபட்சம் 30 நாட்கள் பழமையான ஒரு நிலைப்படமாக இருக்கக்கூடும்; எனவே அதிலிருந்து
பிரித்தெடுக்கப்பட்ட ஒரு பரிந்துரை இணைப்பு, சேவையகத்தின் உண்மையான இணைப்புப் பட்டியலை அதே
கால அளவிற்கு பின்தொடர்ந்தது (புதிதாகச் சேர்க்கப்பட்ட ஒரு பரிந்துரை, இலவச/சமூகப் பயனரைச் சென்றடைய
ஒரு மாதம் வரை ஆகக்கூடும்). பரிந்துரைகள் ஊட்டம் தனக்கான, மிகவும் குறுகிய கால இடைவெளியில்
ஒத்திசைவதன் மூலம் அந்தத் தாமதத்தை நீக்குகிறது.

```ts
// GET /v1/referrals/latest மறுமொழி உடல் (Ed25519-கையொப்பமிடப்பட்டது, பட்டியல்
// ஊட்டத்தில் உள்ள அதே நிலைநிறுத்தப்பட்ட விசை):
{
  feed: "omniroute-radar-referrals",
  schemaVersion: 1,
  generatedAt: string,           // ISO — தீர்மானகரமானது: அனைத்துப் பரிந்துரை
                                  // இணைப்புகளிலும் max(updatedAt), எனவே ஒரே மாதிரியான இரண்டு
                                  // கோரிக்கைகள் துல்லியமாக அதே கையொப்பமிட்ட பைட்டுகள்/கையொப்பத்தை உருவாக்கும்
  referrals: {
    fixed: RadarReferral[],      // அங்கீகாரம்-இல்லாத/சமூக அடுக்கு உட்பட ஒவ்வோர் அடுக்கிலும் இருக்கும்
    campaigns: RadarReferral[],  // செல்லுபடியாகும், செயலிலுள்ள (ஆதரவாளர்) Bearer
                                  // விசைக்கு மட்டுமே நிரப்பப்படும்; அங்கீகாரம்-இல்லாத/காலாவதியான-விசை கோரிக்கைகள் [] பெறும்
  },
}
// RadarReferral = { provider, url, kind: "fixo" | "campanha", validUntil,
//                    requiredAction, isDefault }
```

பட்டியல் ஊட்டத்தைப் போலன்றி, இந்த உடலில் `tier` புலம் எதுவும் இல்லை — ஒவ்வொரு கோரிக்கைக்கும்
எதைச் சேர்க்க வேண்டும் என்பதை `Authorization` விசையின் அடிப்படையில் சேவையகம் முடிவு செய்கிறது; எனவே
வழங்கப்பட்ட அடுக்கிற்கான ஒரே ஆதாரம் `x-omniroute-feed-tier` மறுமொழித் தலைப்பே
(`referralsSync.ts::syncRadarReferrals`); இல்லாத/அடையாளம் காணப்படாத ஒரு தலைப்பு, மிகக் குறைந்த
சலுகைகள் கொண்ட அனுமானமான `"community"` ஆகத் தரமிறக்கப்படுகிறது. `RadarReferralsFeedSchema`
(`src/lib/radar/referralsFeedSchema.ts`) முழு உடலையும் சரிபார்க்கிறது; இரு ஊட்டங்களும் தனிப்பட்ட
பரிந்துரைகளை ஒரே மாதிரியாகச் சரிபார்க்கும் வகையில், `feedSchema.ts` இலிருந்து ஏற்றுமதி செய்யப்பட்ட
அதே ஒவ்வொரு-பரிந்துரைக்குமான `RadarReferralSchema` ஐ மீண்டும் பயன்படுத்துகிறது. ஒவ்வொரு
`RadarReferral.url` உம் `https://` ஆக இருக்க வேண்டும் — ஒரு `http://` url திட்டக்கூறு
சரிபார்ப்பில் தோல்வியடையும்.

`RadarFeedSchema` (`feedSchema.ts`) இல் உள்ள பழைய பட்டியல்-உட்பொதிக்கப்பட்ட `referrals` புலம்,
ஏற்கெனவே தேக்ககப்படுத்தப்பட்ட பட்டியல் ஊட்டங்களுடனான பின்னோக்கிய இணக்கத்தன்மைக்காகத்
தக்கவைக்கப்பட்டுள்ளது; ஆனால் `getRadarReferrals()` இனி அதைப் படிப்பதில்லை — கீழே உள்ள
[அணுகி](#accessor) பகுதியைப் பார்க்கவும்.

### ஒத்திசைவு

`syncRadarReferrals()` (`src/lib/radar/referralsSync.ts`) என்பது பரிந்துரைகளுக்காக
வலையமைப்பைத் தொடும் ஒரே தொகுதியாகும்; இது `syncRadar()` இன் ஒப்பந்தத்தைத் துல்லியமாகப்
பிரதிபலிக்கிறது: கொடி முடக்கம் → `disabled`; விருப்பச் சேர்க்கை false → `opt_out`;
`${RADAR_FEED_URL}/v1/referrals/latest` ஐப் பதிவிறக்குகிறது (பட்டியலில் உள்ள அதே
`RADAR_FEED_URL`/`RADAR_FEED_PUBKEY` fork மேலெழுதல்கள்), துல்லியமான மறுமொழி பைட்டுகளின்
மீதுள்ள Ed25519 கையொப்பத்தைச் சரிபார்க்கிறது (`verifyFeedBytes`),
`RadarReferralsFeedSchema` உடன் சரிபார்க்கிறது, மேலும் `radar_referrals_cache` அட்டவணையில்
(இடம்பெயர்வு `142_radar_referrals_cache.sql`) தேக்ககப்படுத்துகிறது — இது பட்டியலின்
`radar_feed_cache` இலிருந்து முற்றிலும் தனியான அட்டவணை. 10 MB மறுமொழி வரம்பும்,
`generatedAt` கீழ் வரம்பும் தேக்ககப்படுத்தப்பட்டதைவிடப் பழையதாக இருக்கும் உள்வரும் ஊட்டத்தை
நிராகரித்து, பழைய கையொப்பமிட்ட கலைப்பொருளை மீண்டும் இயக்குவதிலிருந்து பாதுகாக்கின்றன. சமமான
நேரமுத்திரை ஏற்கப்படுகிறது: சமூக மற்றும் செயலிலுள்ள பரிந்துரை மாறுபாடுகளுக்கு சேவையகம்
வேண்டுமென்றே அதே தீர்மானகரமான `generatedAt` ஐ வழங்குகிறது; எனவே அடிப்படை இணைப்புத் தொகுப்பு
மாறாமலேயே, ஆதரவாளர்-விசை மாற்றத்திற்குப் பிறகு கையொப்பமிட்ட தரவுத்தொகுதியும் வழங்கப்பட்ட
அடுக்கும் மாறலாம். இது ஒருபோதும் விதிவிலக்கை எழுப்பாது — எப்போதும் ஒரு நிலைப் பொருளைத்
திருப்பியளிக்கும்; பிழைகளின் `reason` இல் அடுக்குத் தடம் ஒருபோதும் இருக்காது.

இரண்டு தூண்டிகள் பரிந்துரைகள் தேக்ககத்தைப் புதுப்பித்த நிலையில் வைத்திருக்கின்றன; இரண்டும்
பட்டியலின் சொந்த 24h கால இடைவெளியிலிருந்து சுயாதீனமானவை:

- **படிக்கும்போது ஒத்திசைவு** — தேக்ககம் இல்லாதபோது அல்லது `REFERRALS_STALE_MS` ஐவிடப்
  (1h, `shouldSyncReferralsOnRead()`) பழமையானபோது, மறுமொழியை வழங்குவதற்கு முன்
  `GET /api/radar/referrals` தானே `syncRadarReferrals()` ஐ உடனடியாக அழைக்கிறது. எந்தப்
  பின்னணிக் காலஅளவிக்காகவும் காத்திருக்காமல், அடுத்த முகப்புப் பலகை ஏற்றுதலிலேயே நிலையான
  இணைப்புகளை "எப்போதும் தற்போதைய நிலையில்" வைத்திருப்பது இதுதான்.
- **திட்டமிடுபவரின் துணை-ஒத்திசைவு** — `radarSchedulerTick()` (`scheduler.ts`), பட்டியலுக்குப்
  பயன்படுத்தப்படும் அதே மணிநேர டிக்கில் பரிந்துரைகளின் பழைமையைச் சுயாதீனமாக மதிப்பிட்டு,
  நேரம் வந்ததும் `syncRadarReferrals()` ஐ அழைக்கிறது. அந்த டிக்கில் பட்டியலுக்கான நேரம்
  வந்திருந்ததா என்பதைப் பொருட்படுத்தாமல் இது இயங்கும்; மேலும் `RadarTickResult` இன் வடிவத்தை
  ஒருபோதும் பாதிக்காது (சிறந்த-முயற்சி துணை விளைவு மட்டுமே; பிழை ஏற்பட்டால் அடக்கப்படும்).

### அணுகி

`src/lib/radar/index.ts` இரண்டு படிக்க-மட்டுமான அணுகிகளை ஏற்றுமதி செய்கிறது; இரண்டுமே ஒருபோதும்
விதிவிலக்கை எழுப்பாது (`getRadarCatalog()` இன் அதே தற்காப்பு ஒப்பந்தம் — கொடி முடக்கப்பட்டிருத்தல்,
தேக்ககம் இல்லாமை அல்லது சிதைந்த தேக்ககத் தரவுத்தொகுதி ஆகிய அனைத்தும் பிழைக்குப் பதிலாக வெற்று
வடிவத்தையே வழங்கும்):

- `getRadarReferrals()` → `{ fixed: RadarReferral[], campaigns: RadarReferral[] }`,
  `radar_referrals_cache` இலிருந்து (`getRadarReferralsCache()` வழியாக) படித்து,
  `RadarReferralsFeedSchema` மூலம் சரிபார்க்கிறது — பட்டியல் தேக்ககத்திலிருந்து **அல்ல**.
- `getDefaultReferralFor(provider)` → அந்த வழங்குநருக்கான `isDefault: true` கொண்ட `fixed`
  பரிந்துரை அல்லது `null`. இது `fixed` ஐ மட்டுமே பார்க்கிறது — ஒரு பிரச்சாரம் ஒருபோதும்
  வழங்குநரின் "இயல்புநிலை" இணைப்பாகப் பயன்படுத்தப்படாது.

உண்மையான "ஒரு வழங்குநருக்கு எந்தப் பரிந்துரை இயல்புநிலையானது" என்ற விதி,
`findDefaultReferral()` (`src/lib/radar/referrals.ts`) இல் உள்ளது; இது **DB import இல்லாத**
ஒரு சிறிய தூய செயல்பாடாகும் — இதை ஒரு `"use client"` கூறுக்குள் பாதுகாப்பாக இறக்குமதி செய்யலாம்.
`getRadarReferrals`/`getDefaultReferralFor` (`index.ts` இல்) ஆகியவை `@/lib/db/radar` ஐ
உள்ளிழுப்பதால் சேவையகம்-மட்டும் பயன்பாட்டில் தொடர்கின்றன; `better-sqlite3` ஐ உலாவியில்
தொகுப்பதைத் தவிர்ப்பதற்காக, வழங்குநர்கள் முகப்புப் பலகை `index.ts` க்குப் பதிலாக
`referrals.ts` ஐ நேரடியாக இறக்குமதி செய்கிறது (கீழே காண்க).

### `GET /api/radar/referrals`

மற்ற எல்லா Radar வழித்தடங்களிலும் உள்ள அதே துல்லியமான gate வரிசையைப் பின்பற்றுகிறது: `RADAR_ENABLED` முடக்கப்பட்டிருந்தால் →
`404` (முதலில் சரிபார்க்கப்படும், byte அளவில் மாறாத செயலற்ற நிலை); அங்கீகரிக்கப்படாதது → `401`; இல்லையெனில்
தரவு காலாவதியாகியிருக்கும்போது sync-on-read-ஐ (மேலே காண்க) தூண்டி, அதன் பின்னர்
`{ fixed, campaigns, tier }` உடன் `200` வழங்கும் — `tier` என்பது (ஒருவேளை அப்போதுதான் புதுப்பிக்கப்பட்ட)
cache வரிசையிலிருந்து நேரடியாக வருகிறது, மேலும் இது தகவல் நோக்கத்திற்காக மட்டுமே பயன்படுத்தப்படுகிறது (கீழேயுள்ள UI-இன் மென்மையான upsell உரையை இயக்குகிறது). Feed server-ஐ ஒருபோதும்
நேரடியாக proxy செய்வதில்லை — இந்த வழித்தடத்தின் சொந்த source-இல் `fetch(` அழைப்பு இல்லை;
network செயல்பாடு எப்போதும் `syncRadarReferrals()`-க்குள் மட்டுமே நிகழ்கிறது; இது
`/api/radar/catalog` பயன்படுத்தும் அதே local-cache-only கொள்கையாகும்.

### Dashboard UI — `/dashboard/radar`-இல் "இலவச credits" tab

ஏற்கனவே உள்ள Radar பக்கத்தை (`src/app/(dashboard)/dashboard/radar/page.tsx`) ஒரு
புதிய வழித்தடமாக உருவாக்குவதற்குப் பதிலாக இரண்டாவது tab ஆக மீண்டும் பயன்படுத்துகிறது — பக்கம் ஏற்கனவே பெறும்
தரவின் ஒரு மாறுபாடாக மட்டுமே உள்ள அம்சத்திற்காக routing/i18n பரப்பை குறைக்கிறது.
விருப்பத்தேர்வு செய்த பிறகு, tab bar **Catalog** (ஏற்கனவே உள்ள table) மற்றும்
**இலவச credits** ஆகியவற்றை வழங்குகிறது:

- நிலையான links provider வாரியாகக் குழுவாக்கப்படும்; ஒவ்வொன்றும் `requiredAction`-ஐ (இருந்தால்)
  மற்றும் referral URL-க்கு செல்லும் `target="_blank" rel="noopener noreferrer"` button-ஐக் காட்டும்.
- Campaigns-லும் இதே தகவல்களுடன், `validUntil` இருந்தால் அதுவும் காட்டப்படும்.
- `campaigns` காலியாகவும் வழங்கப்பட்ட tier `community` ஆகவும் இருக்கும்போது, UI ஒரு
  சுருக்கமான upsell குறிப்பைக் காட்டும் ("குறுகிய கால campaigns என்பது ஆதரவாளர்களுக்கான கூடுதல் அம்சம்") — இது நிலையான links பட்டியலை
  **ஒருபோதும்** மறைக்கவோ கட்டுப்படுத்தவோ செய்யாது; அந்தப் பட்டியல் ஒவ்வொரு tier-க்கும் முழுமையாகக் கிடைக்கும். இந்த
  upsell மென்மையான செய்தி மட்டுமே; ஒருபோதும் தடையாக இருக்காது.

### Provider பெயரில் referral link (providers dashboard)

`ProviderPageHeader` (`src/app/(dashboard)/dashboard/providers/[id]/components/`)
ஏற்கனவே `providerInfo.website` இருந்தால் provider பெயரை அதனுடன் link செய்தது; மேலும்
வருமானம் ஈட்டும் link-க்கான ஒரு முன்னுதாரணமும் உள்ளது: Kimi (Moonshot AI) partner-link குறிப்பு
(`providers.kimiPartnerLinkNote` i18n key). புதிய key ஒன்றை அறிமுகப்படுத்துவதற்குப் பதிலாக,
Radar-இன் இயல்புநிலை referrals-க்கு D28 அதே நுட்பமான குறிப்பு வடிவத்தையே மீண்டும் பயன்படுத்துகிறது.

வடிவமைப்பின்படியே தளர்வான இணைப்பு:

- `resolveProviderHeaderLink()` (`src/app/(dashboard)/dashboard/providers/providerPageUtils.ts`)
  ஒரு **pure** function — `(staticWebsite, referralUrl) => { website, isReferralLink }`
  — இதற்கு `@/lib/radar` அல்லது `@/lib/db/*` மீது எந்த dependency-யும் இல்லை. மொத்தமாக
  `providerPageUtils.ts` இந்த imports எதையும் கொண்டிருக்காது (இது
  `tests/unit/provider-header-referral-link.test.ts` மூலம் உறுதிப்படுத்தப்படுகிறது).
- `ProviderDetailPageClient.tsx` (`"use client"` component) மட்டுமே
  Radar தரவைப் பெற அனுமதிக்கப்பட்ட இடமாகும் — Radar dashboard பக்கமே பயன்படுத்தும் அதே local-route
  வடிவத்தில் `fetch("/api/radar/referrals")` வழியாகப் பெறுகிறது — மேலும் DB இல்லாத
  `src/lib/radar/referrals.ts`-இலுள்ள `findDefaultReferral()` மூலம் இயல்புநிலை referral-ஐ
  client-side-இல் கணக்கிடுகிறது.
- `RADAR_ENABLED` முடக்கப்பட்டிருக்கும்போது, fetch `404` வழங்கும், `referralUrl` தொடர்ந்து `null` ஆகவே இருக்கும், மேலும்
  `resolveProviderHeaderLink()` நிலையான catalog `website`-ஐ மாற்றமின்றித் திருப்பித் தரும் — இந்த
  அம்சம் உருவாக்கப்படுவதற்கு முன்பு இருந்த provider பக்கத்துடன் byte அளவில் அப்படியே ஒத்திருக்கும். இன்னும்
  cache இல்லாதபோதும் அல்லது அந்தக் குறிப்பிட்ட provider-க்கு இயல்புநிலை referral இல்லாதபோதும் இதே விளைவு கிடைக்கும்.
- இயல்புநிலை referral பொருந்தும்போது, `ProviderPageHeader` `isReferralLink`-ஐப் பெற்று,
  Kimi partner link பயன்படுத்தும் அதே நுட்பமான குறிப்பு/tooltip-ஐக் காட்டும்
  (`providers.kimiPartnerLinkNote` key-ஐ மீண்டும் பயன்படுத்தி) — ஒருபோதும் புதிய, தனியான
  காட்சித் தோற்றத்தைப் பயன்படுத்தாது.

## ஒரு feed-ஐ சுயமாக ஹோஸ்ட் செய்வது எப்படி

catalog மீது முழுக் கட்டுப்பாட்டை விரும்பும் ஒரு fork அல்லது self-hoster, client code-ஐ மாற்றாமலேயே தங்களுக்கான feed சேவையை இயக்கலாம்:

1. `RadarFeedSchema` (`src/lib/radar/feedSchema.ts`) தேவைகளைப் பூர்த்தி செய்யும் JSON body-ஐ வழங்கும் `GET /v1/catalog/latest` endpoint-ஐச் செயல்படுத்தவும் — top-level `feed:
"omniroute-radar"`, `schemaVersion: 2`, `version`, `tier`, `providers`, `models`,
   `quirks`, மற்றும் `totals`. `x-omniroute-radar-schema: 2`-ஐ மதிக்கவும்; மாற்றக் காலத்துடன் இணக்கமான server, அது இல்லாத requests-க்கு தனியாகக் கையொப்பமிடப்பட்ட v1 artifact-ஐ இயல்புநிலையாக வழங்க வேண்டும்.
2. சரியான response bytes-ஐ Ed25519 key pair மூலம் கையொப்பமிட்டு, base64
   signature-ஐ `x-omniroute-feed-signature` response header-இல் வழங்கவும்.
3. `RADAR_FEED_URL`-ஐப் புதிய base URL-ஆகவும், `RADAR_FEED_PUBKEY`-ஐ அதற்குப் பொருந்தும்
   public key-ஆகவும் (base64-DER SPKI அல்லது PEM) அமைக்கவும் —
   [environment variable reference](../reference/ENVIRONMENT.md#27-radar-feed-self-hosting)-ஐப் பார்க்கவும்.
4. `RADAR_ENABLED`-ஐ இயக்கி, `POST /api/radar/settings`
   (`{ optIn: true }`) மூலம் பங்கேற்க ஒப்புதல் அளிக்கவும்.

வேறு எந்த code மாற்றங்களும் தேவையில்லை — `verifyFeedBytes()` override-ஐத் தானாகவே எடுத்துக்கொள்கிறது
(`src/lib/radar/pinnedKeys.ts`-இல் உள்ள `getFeedPublicKeys()`); மேலும் version
ஒப்பீடு, schema சரிபார்ப்பு மற்றும் merge விதிகள் ஆகியவை சுயமாக ஹோஸ்ட் செய்யப்பட்ட
feed-க்கும் அதேபோல் பொருந்தும்.

Referral links (மேலே உள்ள [Referral links (free credits)](#referral-links-free-credits)-ஐப் பார்க்கவும்)
ஒரு தனியான, விருப்பத்திற்குரிய artifact ஆகும்: `/v1/catalog/latest`-ஐ மட்டும் வழங்கும் ஒரு fork
முழுமையாகத் தொடர்ந்து செயல்படும் — `/v1/referrals/latest`-இலிருந்து `404` கிடைக்கும்போது
`syncRadarReferrals()` `{ status: "error" }` என்ற நிலைக்குத் தாழ்கிறது; cache வெறுமையாகவே இருப்பதால்,
மீதமுள்ள page தோல்வியடைவதற்குப் பதிலாக `GET /api/radar/referrals`
தொடர்ந்து `{ fixed: [], campaigns: [], tier: null }`-ஐ வழங்கும்.
Referral links-ஐயும் வழங்க, `RadarReferralsFeedSchema`
(`src/lib/radar/referralsFeedSchema.ts`) தேவைகளைப் பூர்த்தி செய்யும்
`GET /v1/referrals/latest`-ஐச் செயல்படுத்தி, catalog feed-க்குப் பயன்படுத்திய அதே Ed25519 key pair மூலம் அதற்குக் கையொப்பமிடவும்.

Supporter offers மற்றொரு விருப்பத்திற்குரிய artifact ஆகும். அவற்றை வழங்க,
மூடப்பட்ட `RadarOffersFeedSchema` (`src/lib/radar/offersFeedSchema.ts`)-ஐப் பயன்படுத்தி
`GET /v1/offers/latest`-ஐச் செயல்படுத்தவும்; செயலில் உள்ள entitlement-ஐக் கட்டாயப்படுத்தி,
`x-omniroute-feed-tier: live`-ஐ வழங்கி, சரியான bytes-க்கு அதே key மூலம் கையொப்பமிடவும்.
இந்த endpoint-ஐத் தவிர்க்கும் ஒரு fork-இல் catalog/referrals செயல்பாடு மாறாமல் இருக்கும்;
offer refresh தரவை அழிக்காமல் தோல்வியடையும், மேலும் கடைசியாகச் சரிபார்க்கப்பட்ட உள்ளூர் offer cache தொடர்ந்து கிடைக்கும்.

Intel-உம் இதேபோல் விருப்பத்திற்குரியது. ஒரு self-hoster,
`RadarIntelFeedSchema` (`src/lib/radar/intelFeedSchema.ts`)-ஐப் பயன்படுத்தி
`GET /v1/intel/latest`-ஐ வழங்கலாம்; செயலில் உள்ள entitlement-ஐக் கட்டாயப்படுத்தி,
`x-omniroute-feed-tier: live`-ஐ வழங்கி, சரியான bytes-க்கு பகிரப்பட்ட Ed25519 key மூலம் கையொப்பமிடலாம்.
இந்த endpoint-ஐத் தவிர்ப்பது catalog, referrals மற்றும் offers ஆகியவற்றை மாற்றாது;
Intel refresh, கடைசியாகச் சரிபார்க்கப்பட்ட உள்ளூர் snapshot ஏதேனும் இருந்தால் அதைப் பாதுகாக்கும்.
