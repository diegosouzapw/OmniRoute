> **சுருக்கமாக**: `open-sse/` என்பது OmniRoute-இல் உள்ள ஒவ்வொரு LLM கோரிக்கையையும் இயக்கும் மைய ஸ்ட்ரீமிங் எஞ்சின் ஆகும். கோரிக்கை பைப்லைன், executors, services, MCP server மற்றும் மொழிபெயர்ப்பு அடுக்கு ஆகியவற்றைச் செயல்படுத்தும் ~1,400 கோப்புகள் இதில் உள்ளன. இந்தப் பகுதிகள் எவ்வாறு ஒன்றிணைந்து செயல்படுகின்றன என்பதை இந்த வழிகாட்டி விளக்குகிறது.

**மூலம்:** `open-sse/` (workspace package, ~1,440 சோதனை அல்லாத `.ts` கோப்புகள்)

## ஏன் ஒரு தனி Workspace Package?

பல காரணங்களுக்காக OmniRoute monorepo-இல் `open-sse/` ஒரு **தனித்த workspace** ஆக உள்ளது:

1. **மறுபயன்பாடு** — `open-sse`, npm-இல் `@omniroute/open-sse` ஆக வெளியிடப்படுவதால், மற்ற திட்டங்கள் இதைத் தனியாகப் பயன்படுத்தலாம்
2. **தெளிவான எல்லைகள்** — ஸ்ட்ரீமிங் எஞ்சின், OmniRoute-க்கே உரிய UI/DB அடுக்கிலிருந்து பிரிக்கப்பட்டுள்ளது
3. **செயல்திறன்** — இந்த எஞ்சினுக்கு Next.js சார்புகள் எதுவும் இல்லை; இதனால் CLI/serverless சூழல்களில் விரைவான cold start-கள் சாத்தியமாகின்றன
4. **பதிப்பிடல்** — `open-sse` அதன் சொந்த வெளியீட்டு சுழற்சிக்கு ஏற்ப பதிப்புகளை வெளியிட முடியும்

```json
// package.json
"workspaces": ["open-sse"]
```

## கோரிக்கை பைப்லைன்

ஒவ்வொரு LLM கோரிக்கையும் ஒரு **5-கட்ட பைப்லைன்** வழியாகப் பாய்கிறது:

```
                              ┌──────────────┐
   HTTP கோரிக்கை              │  1. ROUTE    │   combo தீர்மானம், model தேர்வு
   (Next.js route)             └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. TRANSLATE│   வடிவ மாற்றம் (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. EXECUTE  │   வழங்குநர் executor, HTTP, மீள்முயற்சி, breaker
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAM   │   SSE மாற்றம், backpressure
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. RECORD   │   பயன்பாட்டுக் கண்காணிப்பு, அழைப்புப் பதிவு, பிழை வகைப்பாடு
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP பதில் (SSE அல்லது JSON)
```

### கட்டம் 1: வழித்தடத் தேர்வு (services/combo.ts)

**நுழைவுப் புள்ளி**: `services/combo.ts`-இல் உள்ள `handleComboChat()`

கோரிக்கையை ஒரு குறிப்பிட்ட `(provider, model, account, credentials)` தொகுப்பாகத் தீர்மானிக்கிறது:

- ID மூலம் combo-ஐக் கண்டறிதல் (அல்லது `auto/*` models-க்காக ஒரு மெய்நிகர் combo-ஐ உருவாக்குதல்)
- வழித்தடத் தேர்வு உத்தியைப் பயன்படுத்துதல் (முன்னுரிமை, எடையிடப்பட்டது, round-robin போன்றவை)
- ஆரோக்கியமற்ற வழங்குநர்களை வடிகட்டுதல் (circuit breaker)
- அடுத்த செயல்படக்கூடிய இலக்கைத் தேர்ந்தெடுத்தல்

`auto/*` models-க்கு, இந்தக் கட்டம் மேலும்:

- **16-காரணி மதிப்பீட்டு** வழிமுறையை இயக்குகிறது (`services/autoCombo/`)
- ஆரோக்கியம், செலவு, தாமதம் போன்றவற்றின் அடிப்படையில் ஒரு `provider+model` இணையைத் தேர்ந்தெடுக்கிறது

### கட்டம் 2: மொழிபெயர்ப்பு (translator/)

மூல வடிவம் (எ.கா., OpenAI), இலக்கு வடிவத்திலிருந்து (எ.கா., Claude) வேறுபட்டால், கோரிக்கை **மொழிபெயர்க்கப்படும்**:

- System prompt → system message
- கருவி வரையறைகள் → வழங்குநருக்கே உரிய கருவி வடிவம்
- Reasoning/thinking அளவுருக்கள் → வழங்குநருக்கே உரிய இணையான அளவுருக்கள்
- Message role இயல்பாக்கம் (OpenAI அல்லாதவற்றுக்கு `developer` → `system`)

`translator/index.ts` பின்வருவனவற்றை வெளிப்படுத்துகிறது:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### கட்டம் 3: செயல்படுத்தல் (executors/)

**நுழைவுப் புள்ளி**: `getExecutor(providerId).execute(request, options)`

அனைத்து வழங்குநர்களும் `getExecutor()` factory fallback மூலம் `DefaultExecutor`-ஐ (`executors/default.ts`) பயன்படுத்துகின்றனர். Executor பின்வருவனவற்றைச் செய்கிறது:

- Upstream URL-ஐ உருவாக்குகிறது (`buildUrl()`)
- வழங்குநருக்கே உரிய headers-ஐச் சேர்க்கிறது (`buildHeaders()`)
- கோரிக்கை body-ஐ மாற்றுகிறது (`transformRequest()`)
- மீள்முயற்சி + exponential backoff உடன் HTTP கோரிக்கையை அனுப்புகிறது
- தேவைப்பட்டால் அங்கீகாரப் புதுப்பிப்பைக் கையாளுகிறது (OAuth வழங்குநர்கள்)

அனைத்து executors-உம் `BaseExecutor`-ஐ (`executors/base.ts`, 1170 LOC) விரிவாக்குகின்றன; இது பின்வருவனவற்றை வழங்குகிறது:

- பொதுவான மீள்முயற்சி தர்க்கம்
- Proxy ஒருங்கிணைப்பு
- Circuit breaker ஒருங்கிணைப்பு
- பயன்பாட்டைப் பதிவுசெய்யும் hooks

### கட்டம் 4: ஸ்ட்ரீமிங் (utils/stream.ts)

ஸ்ட்ரீமிங் பதில்களுக்கு, executor ஒரு **ReadableStream**-ஐத் திருப்பித் தருகிறது. Handler பின்வருவனவற்றைச் செய்கிறது:

- SSE transform வழியாக அனுப்புகிறது (`createSSETransformStreamWithLogger`)
- செயலிழந்த இணைப்புகளைக் கண்டறிய heartbeat pings-ஐப் பயன்படுத்துகிறது
- Client துண்டிப்பைச் சீராகக் கையாளுகிறது (`pipeWithDisconnect`)
- ஸ்ட்ரீமிங் அல்லாத clients-க்காக SSE → JSON மாற்றத்தைச் செய்கிறது

ஸ்ட்ரீமிங் அல்லாத பதில்களுக்கு, executor பகுப்பாய்வு செய்யப்பட்ட JSON object-ஐத் திருப்பித் தருகிறது; அது எந்த மாற்றமும் இல்லாமல் அனுப்பப்படுகிறது.

### கட்டம் 5: பதிவுசெய்தல் (services/usage.ts)

பதில் கிடைத்த பிறகு (வெற்றி அல்லது தோல்வி), பயன்பாடு பதிவு செய்யப்படும்:

- பதிலிலிருந்து `prompt_tokens`, `completion_tokens`, `cached_tokens`
- விலைத் தரவிலிருந்து கணக்கிடப்பட்ட `cost_usd`
- தோல்வியடைந்தால் `latency_ms`, `status`, `error_class`
- `usage_history` அட்டவணையில் நிலையாகச் சேமிக்கப்படும்

அழைப்புப் பதிவு துணைக்கோப்புகள் (இயக்கப்பட்டிருந்தால்) `${DATA_DIR}/call_logs/` இல் எழுதப்படும்.

### chatCore.ts (5977 வரிகள்)

**முதன்மை கோரிக்கைக் கையாளி**. அதன் அளவு பெரியதாக இருந்தாலும், அது தெளிவான கட்டமைப்பைக் கொண்டுள்ளது:

```ts
// chatCore.ts-இன் போலிக் கட்டமைப்பு
export async function handleChat(request: NextRequest) {
  // 1. அங்கீகாரம் + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. கோரிக்கை உடல் சரிபார்ப்பு
  const body = await parseRequestBody(request);

  // 3. வடிவமைப்பைக் கண்டறிதல் + மொழிபெயர்ப்பு
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo வழிப்படுத்தல்
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // அடுத்த இலக்கிற்குத் தொடரவும்
    }
  }

  // 5. அவசர மாற்றுவழி
  return await emergencyFallback(body);
}
```

இது ஒரே மிகப்பெரிய செயல்பாடாக இருந்தாலும், 5-கட்டச் செயலாக்கத் தொடருடன் பொருந்தும் வகையில் **கருத்துரையிடப்பட்ட பிரிவுகளாக** ஒழுங்கமைக்கப்பட்டுள்ளது.

### base.ts (1170 LOC)

அனைத்து 107 செயலாக்கிகளும் நீட்டிக்கும் **அருவச் செயலாக்கி**. இது பின்வருவனவற்றைக் கொண்டுள்ளது:

- `buildUrl()` — இயல்புநிலை URL உருவாக்கம் (தனிப்பயன் தேவைகளுக்காக துணைவகுப்புகள் இதை மேலெழுதுகின்றன)
- `buildHeaders()` — இயல்புநிலை தலைப்புகள் (அங்கீகாரம், உள்ளடக்க வகை)
- `transformRequest()` — இயல்பாக மாற்றமின்றி அனுப்புதல்
- `execute()` — மறுமுயற்சி/பின்வாங்கல்/தடைப்பான் ஆகியவற்றைக் கொண்ட முதன்மை HTTP சுழற்சி

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // OpenAI/Anthropic-இணக்கமான அனைத்து வழங்குநர்களையும் கையாள்கிறது
  // வழங்குநர்கள் உள்ளமைவுகளைப் (URL, அங்கீகாரம், தலைப்புகள்) பதிவுசெய்கின்றனர், ஆனால் செயலாக்கித் தர்க்கத்தைப் பகிர்கின்றனர்
}
```

வழங்குநருக்கே உரிய செயல்பாடு (அங்கீகாரத் தலைப்புகள், அடிப்படை URL, பதிப்புத் தலைப்புகள்) தனித்தனி செயலாக்கி வகுப்புகள் வழியாக அல்லாமல், வழங்குநர் பதிவகம் வழியாக உள்ளமைக்கப்படுகிறது.

## செயல்படுத்திகள் (75+ கோப்புகள்)

ஒவ்வொரு provider-க்கும் ஒரு கோப்பு. அவை அனைத்தும் `BaseExecutor`-ஐ நீட்டித்து, வேறுபடும் அம்சங்களை override செய்கின்றன.

### பொதுவான வடிவமைப்புகள்

Providers, `getExecutor(providerId)` வழியாகத் தீர்மானிக்கப்படுகின்றன; இது கட்டமைக்கப்பட்ட executor-ஐ வழங்குகிறது. OpenAI/Anthropic-இணக்கமான providers, `DefaultExecutor`-ஐ (`executors/default.ts`) பயன்படுத்துகின்றன. Provider-க்கே உரிய நடத்தை (அடிப்படை URL, auth headers, API பதிப்பு) `open-sse/config/providers/`-இல் கட்டமைக்கப்படுகிறது; அதேவேளை கோரிக்கை body transformations, `open-sse/translator/`-இல் கையாளப்படுகின்றன.

**தனிப்பயன் URL**, provider கட்டமைப்பின் வழியாக அமைக்கப்படுகிறது:

```ts
// open-sse/config/providers/-இல் உள்ள provider கட்டமைப்பு
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**தனிப்பயன் auth**, provider registry-இன் auth கட்டமைப்பு (API key, OAuth, header profiles) வழியாகக் கையாளப்படுகிறது.

**தனிப்பயன் கோரிக்கை body** transformations (எ.கா., Anthropic, `system`-ஐ `messages`-இலிருந்து பிரித்தல்), `open-sse/translator/`-இல் ஒவ்வொரு provider-க்கும் தனித்தனியாகப் பதிவு செய்யப்படுகின்றன.

````

### Executor Factory

`executors/index.ts`, `getExecutor(providerId)`-ஐ export செய்கிறது:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

தீர்மானம் `ExecutorRegistry` (`executors/registry.ts`) வழியாக நடைபெறுகிறது: ஒவ்வொரு சிறப்பு executor-உம் `executors/index.ts`-இன் உள்ளமைக்கப்பட்ட அட்டவணையில் அறிவிக்கப்பட்டு, module load நேரத்தில் `registerExecutor(alias, instance)` வழியாகப் பதிவு செய்யப்படுகிறது; `getExecutor()`, registry-ஐப் பரிசீலித்து, சிறப்பு entry இல்லாத எந்த provider-க்கும் memoize செய்யப்பட்ட `DefaultExecutor`-ஐ fallback ஆகப் பயன்படுத்துகிறது. முழுமையான alias → executor mapping, golden test ஆன `tests/unit/executor-map-golden.test.ts` மூலம் விவரிக்கப்படுகிறது.

## MCP சேவையகம்

`open-sse/mcp-server/` ஆனது **Model Context Protocol** சேவையகத்தைச் செயல்படுத்துகிறது:

- **110 கருவிகள்** (வழங்குநர் மேலாண்மை, சேர்க்கைகள், நினைவகம், தற்காலிகச் சேமிப்பு, சுருக்கம், ப்ராக்ஸி, திறன்கள், விளையாட்டுமயமாக்கல், செருகுநிரல்கள், Notion, Obsidian, உள்ளகத் தரவுத்தொகுப்பு)
- **3 பரிமாற்ற முறைகள்**: stdio, SSE, Streamable HTTP
- நுணுக்கமான அங்கீகாரத்திற்கான **33 வரம்புகள்**

### கருவிப் பதிவு

கருவிகள் `open-sse/mcp-server/tools/` இல் தனித்தனி கோப்புகளாகப் பதிவு செய்யப்படுகின்றன; ஒவ்வொன்றும் ஒரு பெயர், திட்டவமைப்பு, கையாளுநர் மற்றும் வரம்பை ஏற்றுமதி செய்கிறது:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "கணினி நலநிலையின் உடனடிப் படத்தைப் பெறுக",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### பரிமாற்ற முறைகள்

```ts
// stdio (CLI பயன்பாடு)
startMcpStdio(server);

// SSE (HTTP-அடிப்படையிலான தொடர் பரிமாற்றம்)
startMcpSse(server, port);

// Streamable HTTP (நவீன MCP)
startMcpStreamable(server, port);
```

### அங்கீகாரம்

ஒவ்வொரு கருவி அழைப்பும் வரம்புச் சரிபார்ப்புகளுக்கு உட்படுகிறது (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("போதுமான வரம்பு இல்லை");
}
```

## மாற்றிகள்

`open-sse/transformer/` ஆனது **Chat Completions** மற்றும் **Responses API** வடிவங்களுக்கு இடையே மாற்றுகிறது.

### தனி மாற்றி ஏன் தேவை?

Responses API என்பது **நிலையுள்ள உரையாடல்களைக்** (`previous_response_id`) கொண்ட OpenAI-யின் புதிய வடிவமாகும். ஒரு கிளையன்ட் Responses கோரிக்கையை அனுப்பும்போது, OmniRoute:

1. Responses → Chat Completions என்பதை உட்புறமாக மாற்றுகிறது
2. வழங்குநருக்கு அனுப்புகிறது (Chat Completions-ஐ ஆதரிக்கும் எந்த வழங்குநராகவும் இருக்கலாம்)
3. பதிலை மீண்டும் Responses வடிவத்திற்கு மாற்றுகிறது
4. மாற்றப்பட்ட பதிலை கிளையன்ட்டிற்குத் தொடராக அனுப்புகிறது

மாற்றி (`transformer/responsesTransformer.ts`) வழங்குவது:

```ts
createResponsesApiTransformStream(): TransformStream
```

இது பின்வருவனவற்றைக் கையாளுகிறது:

- `response.output_item.added` நிகழ்வுகள்
- `response.output_text.delta` நிகழ்வுகள்
- `response.completed` நிகழ்வு
- கருவி அழைப்பு பொருத்தம் (`function_call` ↔ `tool_calls`)

## உள்ளமைவு

`open-sse/config/` ஆனது உள்ளமைவு அடுக்கைக் கொண்டுள்ளது:

| கோப்பு                        | நோக்கம்                                             |
| ----------------------------- | --------------------------------------------------- |
| `providerRegistry.ts`         | 352-வழங்குநர் பட்டியலுக்கான அரட்டை-மாதிரிப் பதிவகம் |
| `providerModels.ts`           | மாதிரி மாற்றுப் பெயர்கள், வடிவப் பொருத்தம்          |
| `constants.ts`                | காலக்கெடுக்கள், வரம்புகள், நிலைக் குறியீடுகள்       |
| `defaultThinkingSignature.ts` | இயல்புநிலை Claude சிந்தனைக் கையொப்பம்               |
| `modelStrip.ts` (சேவைகளில்)   | வழங்குநர் வாரியான புல நீக்கம்                       |

### வழங்குநர் பதிவகத் திட்டவமைப்பு

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

தொகுதி ஏற்றத்தின்போது செய்யப்படும் Zod சரிபார்ப்பு, அனைத்து வழங்குநர் உள்ளமைவுகளும் செல்லுபடியாக இருப்பதை உறுதிசெய்கிறது.

## செயல்திறன் கட்டுப்பாடுகள்

வழிப்படுத்தல் இயந்திரத்திற்குக் கடுமையான செயல்திறன் வரம்புகள் உள்ளன:

| செயல்பாடு                                                             | இலக்கு | அளவீடு                                     |
| --------------------------------------------------------------------- | ------ | ------------------------------------------ |
| Combo தீர்மானம்                                                       | <10ms  | 50 இலக்குகளுக்கு                           |
| வீத வரம்புச் சரிபார்ப்பு                                              | <1ms   | நினைவகத்திலுள்ள token bucket               |
| மாதிரிக் குடும்ப மாற்று                                               | <5ms   | தற்காலிகச் சேமிப்பிலுள்ள குடும்ப வரையறைகள் |
| கோரிக்கை வழிப்படுத்தல் அனுப்புகை                                      | <2ms   | அடிக்கடி செயல்படும் பாதை                   |
| **வழிப்படுத்தலின் அடிக்கடி செயல்படும் பாதையில் தடுக்கும் I/O கூடாது** | —      | அனைத்தும் ஒத்திசைவற்றவை                    |

---

## தவிர்க்க வேண்டிய நடைமுறைகள்

❌ **`combo.ts`-இல் ஒத்திசைவான DB அழைப்புகள்** — முன்கூட்டியே கணக்கிட்டு தற்காலிகமாகச் சேமிக்கவும்
❌ **கையாளிகளில் மறுமுயற்சி தர்க்கம்** — மீள்திறன் சேவையிலிருந்து `retry()`-ஐப் பயன்படுத்தவும்
❌ **வழங்குநர் உள்ளமைவை நேரடியாக அணுகுதல்** — `providerRegistry` பெறும் செயல்பாடுகளைப் பயன்படுத்தவும்
❌ **நிரலில் நேரடியாகப் பதிக்கப்பட்ட மாற்றுத் தொடர்கள்** — `modelFamilyFallback.ts`-இல் வரையறுக்கவும்
❌ **ஒரே நேரத்தில் நடைபெறும் கோரிக்கைகளுக்கு இடையிலான நிலை மாற்றங்கள்** — கோரிக்கை வரம்பிற்குட்பட்ட சூழலை மட்டும் பயன்படுத்தவும்

## புதிய கூறைச் சேர்த்தல்

### புதிய சேவையைச் சேர்த்தல்

1. குறிப்பிட்ட பொறுப்புடன் `open-sse/services/[serviceName].ts`-ஐ உருவாக்கவும்
2. முதன்மைக் கையாளி செயல்பாட்டையும் ஏதேனும் மாறிலிகளையும் ஏற்றுமதி செய்யவும்
3. `tests/unit/services/[serviceName].test.mjs`-இல் அலகுச் சோதனைகளைச் சேர்க்கவும்
4. வழிப்படுத்தல் தொடர்பானதாக இருந்தால், `handlers/chatCore.ts`-இல் உள்ள கோரிக்கை செயலாக்கத் தொடரில் ஒருங்கிணைக்கவும்
5. சேவை இலக்குத் தேர்வைப் பாதித்தால், `combo.ts`-இல் உள்ள வழிப்படுத்தல் தர்க்கத்தைப் புதுப்பிக்கவும்
6. இந்தக் கோப்பில் ஆவணப்படுத்தவும்

### புதிய Executor-ஐச் சேர்த்தல்

1. `BaseExecutor`-ஐ நீட்டிக்கும் `open-sse/executors/[provider].ts`-ஐ உருவாக்கவும்
2. `config/providerRegistry.ts`-இல் பதிவுசெய்யவும்
3. `executors/index.ts` தொழிற்சாலையில் சேர்க்கவும்
4. Executor-க்கான அலகுச் சோதனைகளைச் சேர்க்கவும்
5. `docs/architecture/ARCHITECTURE.md`-இல் ஆவணப்படுத்தவும்

### புதிய MCP கருவியைச் சேர்த்தல்

1. `open-sse/mcp-server/tools/[category]Tools.ts`-ஐ உருவாக்கவும் அல்லது புதுப்பிக்கவும்
2. உள்ளீடுகளுக்கான Zod schema-ஐ வரையறுக்கவும்
3. கருவியை `mcp-server/index.ts`-இல் பதிவுசெய்யவும்
4. `mcp-server/auth/`-இல் உள்ள scope matrix-இல் சேர்க்கவும்
5. அலகுச் சோதனைகளைச் சேர்க்கவும்
