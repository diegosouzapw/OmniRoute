> விருப்பத்தின் பேரில் இயக்கக்கூடியது; இயல்புநிலையில் முடக்கப்பட்டிருக்கும் (`settings.freeAccessPolicy !== "strict"` எனில் ஒவ்வொரு `auto/*`
> candidate pool-உம் byte அளவில் மாற்றமின்றி இருக்கும்). பணச் செலவில் ஏற்படும் எந்தவொரு அதிகரிப்புக்கும் எதிராகக் கடுமையான
> உத்தரவாதம் தேவைப்படும் operators-க்காக, `hidePaidModels`-இன் கடுமையான இணை அம்சம்
> (`open-sse/services/autoCombo/paidModelFilter.ts`, #6512); இது வெறுமனே "இலவசம் என ஆவணப்படுத்தப்பட்டுள்ளது"
> என்பதற்கு அப்பாற்பட்டது.

## இது ஏன் உள்ளது, மேலும் `hidePaidModels` மட்டும் ஏன் போதாது

`hidePaidModels` என்பது "இந்த model தற்போது `FREE_MODEL_BUDGETS`-இல் இலவசமானதாக வகைப்படுத்தப்பட்டுள்ளதா?" என்ற
கேள்விக்குப் பதிலளிக்கிறது — இது குறிப்பிட்ட நேரத்திற்கான catalog உண்மையாகும்; `isFreeModel()`/`providerHasFreeModels()`
(`src/shared/utils/freeModels.ts`) வழியாகச் சரிபார்க்கப்படுகிறது. ஆனால் இது இரண்டு உண்மையான அபாயங்களைப் பற்றி எதுவும் கூறாது:

1. `recurring-*`/`one-time-initial` இலவச tier-இன் allowance **தீர்ந்துவிடலாம்** — catalog-இல்
   model இன்னும் இலவசமாகவே பட்டியலிடப்பட்டிருக்கும், ஆனால் அதன் பின்னணியில் உள்ள account-இல் பயன்படுத்தக்கூடிய அளவு எதுவும் மீதமிருக்காது.
2. இலவச tier-ஐத் தாண்டுவது எப்போதும் கட்டாயத் தடையாக இருப்பதில்லை. சில providers, payment method-ஐ
   ஒருபோதும் இணைக்க முடியாது என்பதை வெளிப்படையாக ஆவணப்படுத்துகின்றனர் ("credit card தேவையில்லை"); மற்றவர்கள் அவ்வாறு கூறுவதில்லை,
   மேலும் சிலர் இலவச allowance-ஐத் தாண்டியதும் தானாகவே கட்டணம் விதிக்கின்றனர்.

`hidePaidModels` இவற்றை வேறுபடுத்த முடியாது — அது அதற்காக உருவாக்கப்படவே இல்லை. STRICT_ZERO_COST துல்லியமாக
இந்த இரண்டு சோதனைகளையும் சேர்க்கிறது; அவை ஒவ்வொரு candidate-க்கும், category/tier ranking-க்கு **முன்பும்**
dispatch-க்கு **முன்பும்** மதிப்பிடப்படுகின்றன — request ஏற்கெனவே அனுப்பப்பட்ட பிறகு ஒருபோதும் அல்ல.

## Candidate வகைப்பாடு

pool-இல் உள்ள ஒவ்வொரு candidate-க்கும் (`open-sse/services/autoCombo/virtualFactory.ts::buildPreparedPool`,
`filterPaidOnlyCandidates`-க்கு உடனடியாக அடுத்து):

1. **`FREE_MODEL_BUDGETS`-இல் முற்றிலும் இல்லாதது** → விலக்கப்படும். இது உண்மையிலேயே கட்டணம் செலுத்த வேண்டிய models மற்றும்
   OmniRoute இதுவரை வகைப்படுத்தாத எந்த provider/model-ஐயும் உள்ளடக்கும் — புதிய candidates சேர்க்கப்பட்ட நிலையில் அல்ல,
   விலக்கப்பட்ட நிலையிலேயே தொடங்குகின்றன.
2. **`freeType: "keyless"`** → உடனடியாக அனுமதிக்கப்படும், **ஆனால் உண்மையாகவே
   no-auth பாதை வழியாக வந்த candidate-க்கு மட்டும்** (`connectionId === SYNTHETIC_NOAUTH_CONNECTION_ID`,
   `open-sse/services/autoCombo/resilienceCandidateFilter.ts`). அந்த candidate-க்கு credential எதுவும் இல்லை;
   எனவே அதற்கு எதிரான எந்த request-க்கும் ஒருபோதும் கட்டணம் விதிக்க முடியாது — runtime சோதனை தேவையுமில்லை,
   சாத்தியமுமில்லை. அதே catalog-இல் உள்ள `keyless` provider/model ஒரு **உண்மையான** DB
   connection வழியாக அணுகப்பட்டால் (`connectionId` என்பது உண்மையான connection id ஆக இருந்தால் அல்லது candidate-இல்
   `allowedConnectionIds` இருந்தால்), இந்தச் சுருக்குவழி கிடைக்காது — `keyless` metadata குறிப்பாக
   no-auth பாதையையே விவரிக்கிறது, provider-ஐப் பொதுவாக அல்ல; மேலும் அது உண்மையான,
   credential கொண்ட account-க்கு ஒருபோதும் அனுமதியளிக்காது. அத்தகைய candidate மற்றவற்றைப் போலவே சோதனை 3-க்குச் செல்லும்;
   அங்கு catalog entry-இல் தனியாக `hardStopGuaranteed: true` இல்லாவிட்டால் அது விலக்கப்படும் (உண்மையான
   `keyless` entries-இல் இது ஒருபோதும் இருக்காது — அந்தச் சுருக்குவழியே அவற்றின் ஒரே பாதுகாப்பான பாதை).
3. **வேறு எந்த `freeType`-உம்** (`recurring-daily`, `recurring-monthly`, `recurring-credit`,
   `recurring-uncapped`, `one-time-initial`, மற்றும் இந்த module சிறப்பாகக் கையாளாத எதிர்கால type எதுவும்) →
   பின்வருவன **அனைத்தும்** பூர்த்தியானால் மட்டுமே அனுமதிக்கப்படும்:
   - catalog entry-இல் `hardStopGuaranteed: true` அமைக்கப்பட்டிருக்க வேண்டும் (`FreeModelBudget.hardStopGuaranteed`,
     `open-sse/config/freeModelCatalog.ts`) — இது provider வெளியிட்டுள்ள சொந்த விதிமுறைகளைப் பற்றிய
     **தேர்ந்தெடுக்கப்பட்டு, கையால் அமைக்கப்பட்ட உண்மை** (எ.கா. வெளிப்படையான "credit card தேவையில்லை" என்ற கூற்று);
     இது `freeType`-இலிருந்தோ live API response-இலிருந்தோ ஒருபோதும் பெறப்படாது. அமைக்கப்படாத (`undefined`) நிலையும்
     `false` நிலையும் "உத்தரவாதமில்லை" என்றே கருதப்படும்.
   - `USAGE_FETCHER_PROVIDERS`-இல் provider-க்கான usage adapter இருக்க வேண்டும்
     (`open-sse/services/usage.ts`) — quota dashboard மற்றும்
     `getUsageForProvider()`-ஐ ஏற்கெனவே ஆதரிக்கும் அதே registry. adapter இல்லை → ஒன்று சேர்க்கப்படும் வரை
     நிரந்தரமாக விலக்கப்படும்.
   - **உண்மையில் மதிப்பிடப்படும் குறிப்பிட்ட connection**-க்கான live, cached `FreeAccessState`,
     `status: "SAFE"` ஆக இருக்க வேண்டும்; அது
     `settings.autoRefreshProviderQuotaInterval` காலவரம்புக்குள் சரிபார்க்கப்பட்டிருக்க வேண்டும் (இயல்புநிலை 180s —
     ஏற்கெனவே உள்ள setting, புதிய எண் அல்ல); மேலும் ஒரு சிறிய safety margin-ஐ விட அதிகமான
     `remainingFreeAllowance` இருப்பதாகத் தெரிவிக்க வேண்டும்.
4. **`freeType: "discontinued"`** → எப்போதும் விலக்கப்படும்.

## இணைப்புப் பாதுகாப்பு (ஒவ்வொரு இணைப்பிற்குமான சரிபார்ப்பு, ஒருபோதும் ஒவ்வொரு வேட்பாளருக்குமானதல்ல)

auto-combo தொகுப்பிலுள்ள ஒரு வேட்பாளர் எப்போதும் ஒரே இணைப்புடன் பிணைக்கப்பட்டிருக்க வேண்டியதில்லை. ஒரு "தருக்கரீதியான" வேட்பாளர்
(`connectionId: null`) ஒரு `allowedConnectionIds` அனுமதிப்பட்டியலைக் கொண்டிருக்கும் — கோரிக்கையை நிறைவேற்றக்கூடிய ஒன்று அல்லது அதற்கு மேற்பட்ட உண்மையான
வழங்குநர் இணைப்புகள்/கணக்குகள் — மேலும் உண்மையில் பயன்படுத்தப்படும் கணக்கு, பின்னர் அனுப்பும் நேரத்தில், `open-sse/services/combo/autoStrategy.ts`
மூலம் தீர்மானிக்கப்படுகிறது (`allowedConnectionIds`-ஐ அதன் சொந்த இணைப்புத் தேர்வு தருக்கத்துடன் குறுக்கிட்டு, ~வரி 315-331).

STRICT_ZERO_COST அந்த அனுமதிப்பட்டியலிலுள்ள **ஒவ்வொரு இணைப்பின் இலவச அணுகல் நிலையையும்
தனித்தனியாகச்** சரிபார்க்கிறது (`strictZeroCostFilter.ts`-இல் உள்ள `evaluateCandidateConnections()`) மற்றும்
`allowedConnectionIds`-ஐ `SAFE` எனத் திரும்பிய சரியான துணைத்தொகுப்பாக மட்டும் மாற்றியமைக்கிறது — ஒருபோதும் முழு
அசல் பட்டியலாகவோ, தன்னிச்சையாகத் தேர்ந்தெடுக்கப்பட்ட ஒரே உறுப்பினராகவோ அல்ல. குறிப்பாக:

- கணக்கு A `SAFE`, கணக்கு B `UNKNOWN`/தீர்ந்துவிட்டது/கட்டணம் விதிக்கத்தக்கது → A மட்டுமே தேர்ந்தெடுக்கக்கூடியதாக இருக்கும்.
- அனைத்து கணக்குகளும் `UNKNOWN` → வேட்பாளர் முழுமையாக நீக்கப்படுவார் (பாதுகாப்பான தொகுப்பு காலியாக இருக்கும்).
- தோல்வியடையும் ஒற்றை-இணைப்பு வேட்பாளர் (`connectionId` நேரடியாக அமைக்கப்பட்டு, அனுமதிப்பட்டியல் இல்லாதது)
  முற்றிலுமாக நீக்கப்படுவார்; காலியான `allowedConnectionIds` உடன் ஒருபோதும் திருப்பி அனுப்பப்படமாட்டார்.

அனுப்புவதற்கான இணைப்பைத் தேர்ந்தெடுப்பதற்கு முன்பு `autoStrategy.ts` ஏற்கெனவே `allowedConnectionIds`-ஐ ஒரு கடுமையான அனுமதிப்பட்டியலாகச்
செயல்படுத்துவதால், அதைச் சரிபார்க்கப்பட்ட-`SAFE` துணைத்தொகுப்பாக மாற்றியமைப்பது, அனுப்பும் நேரத்தில் உண்மையில் பயன்படுத்தப்படும் இணைப்பு எப்போதும் இந்த வடிப்பான் தானே சரிபார்த்த ஒன்றாக இருப்பதை உறுதிசெய்யப் போதுமானது —
அதே வேட்பாளரிலுள்ள வேறு, சரிபார்க்கப்படாத கணக்காக ஒருபோதும் இருக்காது. பின்னடைவு சோதனை ஆதாரத்திற்கு
`tests/unit/autoCombo/strict-zero-cost-connection-safety.test.ts`-ஐப் பார்க்கவும்
(keyless-bypass நிலைகள் A/B/C, பல-கணக்கு நிலைகள் 1-5).

`தானாகக் கண்டறியப்பட்டது`: சரியான metadata-வுடன் நாளை வெளியிடப்படும் ஒரு வழங்குநர்/model (catalog-இல்,
ஒரு usage adapter உடன், `hardStopGuaranteed: true`) பற்றி OmniRoute அறிந்த உடனேயே அதைப் பயன்படுத்தலாம்
— code மாற்றமோ, whitelist பதிவோ, இந்த module-இல் திருத்த வேண்டிய எதுவுமோ இல்லை. catalog-இலிருந்து நீக்கப்பட்ட ஒன்று
அதே முறையில் மறைந்துவிடும். பின்னடைவு சோதனை ஆதாரத்திற்கு
`tests/unit/autoCombo/strict-zero-cost-autodiscovery.test.ts`-ஐப் பார்க்கவும் (உண்மையான catalog-ஐ மாற்றாமல்,
செலுத்தக்கூடிய fixtures மூலம்).

## ஒதுக்கீடு cache செய்தல் (`open-sse/services/autoCombo/freeAccessQuota.ts`)

`getUsageForProvider()`-ஐ மீண்டும் பயன்படுத்துகிறது — இரண்டாவது ஒதுக்கீட்டு அமைப்பு இல்லை. குறுகிய கால, நினைவகத்திலுள்ள,
process-ஆயுட்கால cache ஒன்று அதற்கு முன் அமைந்துள்ளது (TTL இயல்புநிலை
`autoRefreshProviderQuotaInterval`-க்குச் சமமானது); எனவே Telegram அளவிலான கோரிக்கை வீதம், ஒவ்வொரு கோரிக்கையிலும் ஒவ்வொரு வேட்பாளருக்கும் நேரடி
billing-API அழைப்பை ஒருபோதும் தூண்டாது. வாசிப்புகள் ஒத்திசைவானவை: cache miss ஏற்பட்டால்
`undefined` திரும்பும் (→ விலக்கப்படும், fail-closed) மற்றும் _அடுத்த_ வாசிப்புக்கான பின்னணிப் புதுப்பிப்பைத் தொடங்கும் —
வேட்பாளர்-தொகுப்பு உருவாக்கப் பாதையில் எதுவும் network அழைப்புக்காக ஒருபோதும் காத்திருக்காது.

எந்தக் காரணத்திற்காகவும் ஓர் இணைப்பு தோல்வியடையும் தருணத்தில்
`src/sse/services/auth.ts::markAccountUnavailable()`-இலிருந்து `invalidateFreeAccessState(provider, connectionId)` அழைக்கப்படுகிறது;
எனவே அடுத்த தொகுப்பு உருவாக்கம், பழைய `SAFE` பதிவுக்குப் பதிலாகத் தூய cache miss-ஐ வாசிக்கும் —
402/403/ஒதுக்கீடு-தீர்ந்துவிட்ட பதிலுக்குப் பிறகு TTL முடியும் வரை காத்திருக்க வேண்டியதில்லை.

## ToS பாதுகாப்பு (பொருளாதாரப் பாதுகாப்பிலிருந்து தனிப்பட்டது)

`excludeTosAvoid` (இயல்புநிலை `false`) என்பது பராமரிக்கப்பட்ட `tos` தீர்ப்பு
(`FreeModelBudget.tos`) `"avoid"` ஆக உள்ள எந்தவொரு தேர்வையும் நீக்குகிறது — ஏற்கெனவே நிரப்பப்படும் `hidePaidModels`-இன் இணை ஆவணங்களில்
(`docs/reference/FREE_TIERS.md`) உள்ள அதே புலத்தை மீண்டும் பயன்படுத்துகிறது. இது வேண்டுமென்றே
`freeAccessPolicy`-இலிருந்து தனியாக வைக்கப்பட்டுள்ளது: ஒரு தேர்வு பொருளாதார ரீதியாக `SAFE` ஆக இருந்தும் ஒப்பந்தக்
காரணங்களுக்காக இங்கே விலக்கப்படலாம்; அல்லது இந்தப் பாதுகாப்பு அணைக்கப்பட்டிருக்கும்போது, `freeAccessPolicy: "strict"` இயக்கத்தில் இருந்தாலும் சேர்க்கப்பட்டிருக்கலாம்.

விலக்கி வைக்கும் தேர்வுகளும் இதில் அடங்கும். மேலும் ஒவ்வொன்றிலும் `freeAccessExclusion` இருக்கும் — பாதுகாப்பின்

கடைசி இரண்டையும் தனித்தனியாக வேறுபடுத்திப் பார்ப்பது முக்கியம். முழுமையாகப் பயன்படுத்தப்பட்ட அனுமதிக்கப்பட்ட அளவு தானாகவே மீட்டமைக்கப்படும்; ஆனால் ஒருபோதும் வந்து சேராத
அளவீடு என்பது தேடலிலேயே கோளாறு இருப்பதைக் குறிக்கிறது. இதுவரை வெளிப்புறத்திலிருந்து பார்க்கும்போது இவை இரண்டும் ஒரே மாதிரியாகத் தெரிந்தன —
தேர்வு வெறுமனே மறைந்துவிட்டது.

**ஒரு இடைவெளி இன்னும் உள்ளது; அது வேண்டுமென்றே விடப்பட்டுள்ளது.** பட்டியல் உருவாக்கப்படுவதற்கு முன்பே
`excludeTosAvoid` இன்னும் தேர்வுகளை நீக்குகிறது. எனவே `tos: "avoid"` எனப் பராமரிக்கப்பட்ட ஒரு model எந்தக் காரணமும் வழங்கப்படாமல் பட்டியலில் இருக்காது —
பூஜ்ஜியச் செலவுப் பாதுகாப்புக்காக இந்தப் பகுதி இப்போது நீக்கிய அதே மறைவுநிலை இது. இதையும் சரிசெய்வதற்கு
ஒரு ToS விலக்கு என்ன தகவலைத் தெரிவிக்க வேண்டும் என்பதைத் தீர்மானிக்க வேண்டும்; அது பொருளாதாரப் பாதுகாப்பிலிருந்து வேறுபட்ட கேள்வி. இந்தப் பக்கம்
அந்த இடைவெளி இல்லை என்று பாசாங்கு செய்யாமல், அதை வெளிப்படையாகக் குறிப்பிடுகிறது.

இணையமில்லா முன்/பின் ஒப்பீட்டிற்கு, இயங்கும் instance-இன் candidates output-க்கு எதிராக
`npx tsx scripts/ad-hoc/dry-run-strict-zero-cost.ts` இன்னும் செயல்படும்; இது ஒவ்வொரு தேர்வின் உண்மையான `connectionId`-ஐப் படிப்பதால்,
connection-பாதுகாப்புப் பாதையையும் சோதிக்கிறது. Keyless தேர்வுகள் செயற்கையான no-auth `connectionId` உடன் வர வேண்டும்;
உண்மையான connection உடன் ஒருபோதும் வரக்கூடாது. தற்போதைய உள்ளமைந்த keyless auto பாதை OpenCode Free ஆகும்; துல்லியமான தேர்வு எண்ணிக்கைகள்
இன்னும் நேரடி model கண்டறிதலைச் சார்ந்துள்ளன, எனவே பழைய இயக்கத்திலிருந்து நகலெடுப்பதற்குப் பதிலாக இலக்கு deployment-இல்
அளவிடப்பட வேண்டும். ஒரு `recurring-*` தேர்வு, பதிவுசெய்யப்பட்ட usage adapter மற்றும் `hardStopGuaranteed: true`
ஆகிய இரண்டையும் கொண்டிருந்தால் மட்டுமே தேர்ச்சி பெறும்; முழுமையற்ற metadata பாதுகாப்பாகத் தொடர்ந்து தோல்வியடையும்.

`excludeTosAvoid: true` ஆக இருக்கும்போது, `tos: "avoid"` எனப் பராமரிக்கப்பட்ட ஒவ்வொரு தேர்வும் நீக்கப்படும். OpenCode Free
தற்போது அந்தத் தீர்ப்பைக் கொண்டுள்ளது; எனவே பாதுகாப்பை இயக்குவது deployment-இல் மீதமுள்ள keyless
தொகுப்பைக் காலியாக்கக்கூடும். இது ToS பாதுகாப்பை இயக்குவதால் ஏற்படும் எதிர்பார்க்கப்பட்ட சமரசமே அன்றி bug அல்ல: இதே காரணத்திற்காகவே பாதுகாப்பின்
இயல்புநிலை `false` ஆக உள்ளது (மேலே உள்ள "ToS பாதுகாப்பு" பகுதியைப் பார்க்கவும்).

## செயல்படுத்துதல்

```json
PUT /api/settings
{ "freeAccessPolicy": "strict", "excludeTosAvoid": false }
```

இரண்டு புதிய அமைப்புகளும் இயல்பாக அவற்றின் அம்சத்திற்கு முந்தைய மதிப்புகளையே (`"off"` / `false`) கொண்டிருக்கும் — இரண்டில் எதையும் செயல்படுத்தாமல் இருப்பது, ஏற்கனவே உள்ள எந்த `auto/*` வழிப்படுத்தல் நடத்தையையும் மாற்றாது.
