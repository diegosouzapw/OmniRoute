Reasoning routing விதிகள் ஏற்கனவே உள்ள model மற்றும் combo routing-ஐ விரிவுபடுத்துகின்றன. செயலில் உள்ள எந்த விதியும் பொருந்தாதபோது, ஏற்கனவே உள்ள thinking, suffix, connection-default மற்றும் provider-translation செயல்பாடுகள் மாறாமல் இருக்கும்.

## நிர்வாகம்

விதி நிர்வாகம் **Settings → Global Routing** என்பதன் கீழ் கிடைக்கிறது. API-key திருத்தி, தேர்ந்தெடுக்கப்பட்ட key-க்கு வடிகட்டப்பட்ட அதே நிர்வாக UI-ஐ வழங்குகிறது.

நிர்வாக API பின்வரும் routes மூலம் வெளிப்படுத்தப்படுகிறது:

- `/api/settings/reasoning-routing-rules` இல் `GET` மற்றும் `POST`
- `/api/settings/reasoning-routing-rules/[id]` இல் `GET`, `PATCH` மற்றும் `DELETE`
- `/api/settings/reasoning-routing-rules/simulate` இல் `POST`

அனைத்து routes-உம் `requireManagementAuth`-ஐப் பயன்படுத்துகின்றன. உள்ளீடுகள் `src/shared/validation/schemas/reasoningRouting.ts` இல் உள்ள schemas மூலம் சரிபார்க்கப்படுகின்றன. Simulator ஒருபோதும் upstream அழைப்பைச் செய்யாது.

## விதித் தீர்மானம்

ஆரம்பகட்ட மதிப்பீடு மிகச்சரியாக ஒரு விதியைத் தேர்ந்தெடுக்கிறது. Scopes பின்வரும் வரிசையில் சரிபார்க்கப்படுகின்றன:

1. `apiKey`
2. `combo`
3. `model`
4. `global`

ஒரு scope-க்குள், முதலில் அதிக `priority` கொண்டது வெற்றி பெறும்; அதைத் தொடர்ந்து glob pattern-ஐ விட exact model பொருத்தம் முன்னுரிமை பெறும்; பின்னர் நிலையான `createdAt` மற்றும் `id` வரிசைப்படுத்தல் பயன்படுத்தப்படும். `requestTags`, `metadata.tags` இலிருந்து மட்டுமே படிக்கப்படுகின்றன; அவை `any` அல்லது `all` பொருத்தத்தை ஆதரிக்கின்றன.

எந்த ஆரம்பகட்ட விதியும் வெற்றிபெறாமல், ஒரு குறிப்பிட்ட provider connection ஏற்கனவே தேர்ந்தெடுக்கப்பட்டிருக்கும்போது மட்டுமே `connection` விதி மதிப்பிடப்படும். அது effort மற்றும் budget-ஐ மட்டுமே மாற்ற முடியும்.

## Effort மற்றும் Budget

`sourceEffort`, `any`, `missing`, `none`, `low`, `medium`, `high`, `xhigh`, `max` மற்றும் `ultra` ஆகியவற்றை ஏற்கிறது. Request-இல் discrete effort, thinking toggle அல்லது thinking budget எதுவும் இல்லை என்பதே `missing` என்பதன் பொருள். எனவே budget மட்டும் கொண்ட signal, `any` மூலம் மட்டுமே பொருத்தப்படும்.

`effortMode` மூன்று வகைகளைக் கொண்டுள்ளது:

- Model அல்லது combo மாறுவதற்கு இன்னும் அனுமதித்தபடியே, client effort-ஐ `inherit` தக்கவைக்கிறது.
- வெளிப்படையான reasoning signal எதுவும் இல்லாதபோது மட்டுமே `default`, `targetEffort`-ஐ அமைக்கிறது.
- `force`, discrete effort-ஐ `targetEffort` கொண்டு மாற்றுகிறது.

தனித்தனியாக, `budgetAction` என்பது `preserve`, `remove` அல்லது `set` ஆக இருக்கலாம். `none` உடன் பயன்படுத்தப்படும் `force`, அடையாளம் காணப்பட்ட அனைத்து effort மற்றும் budget fields-ஐயும் நீக்குகிறது. `set` உடன் `none` பயன்படுத்துவது செல்லுபடியாகாது.

பொருந்தாதவை என்று அறியப்பட்ட models-ஐ இலக்காகக் கொண்ட requests, upstream அழைப்பிற்கு முன்பே நிராகரிக்கப்படும். Combo இலக்குகளுக்கு, பொருந்தாத entries நீக்கப்படும்; எதுவும் மீதமில்லை என்றால், request `400` status-ஐத் திருப்பியளிக்கும். அறியப்படாத capability data ஒரு எச்சரிக்கையை உருவாக்கி, விதியைச் செயலில் வைத்திருக்கும்.

## பாதுகாப்பு மற்றும் Transports

Source மற்றும் target model, அல்லது source மற்றும் target combo ஆகியவை தொடர்ந்து ஏற்கனவே உள்ள API-key policy-க்கு உட்பட்டவையாக இருக்கும். ஒரு reasoning விதி, model, combo அல்லது quota அனுமதிகளை ஒருபோதும் விரிவுபடுத்தாது.

இந்த engine, Chat Completions, Responses, Anthropic Messages மற்றும் உள் Codex WebSocket path ஆகியவற்றில் ஒருங்கிணைக்கப்பட்டுள்ளது. WebSocket path, Codex target models-ஐ மட்டுமே ஏற்கிறது; combo இலக்குகளை அங்கு இயக்க முடியாது. விதித் தீர்மானம் இரகசியங்கள் எதுவுமின்றி, ஏற்கனவே உள்ள route trace-இல் சேமிக்கப்படுகிறது.

## நிலைத்த சேமிப்பு

`src/lib/db/migrations/126_reasoning_routing_rules.sql` migration, `reasoning_routing_rules` table-ஐ உருவாக்குகிறது. விதிகள் சேமிக்கப்பட்ட API keys, combos மற்றும் provider connections-ஐக் குறிப்பிடுகின்றன. நீக்குதல் தொடர்புடைய விதிகளைச் சுத்தப்படுத்துகிறது. `src/lib/db/reasoningRoutingRules.ts` இல் உள்ள database access layer, request path-க்காக invalidate செய்யக்கூடிய cache-ஐப் பராமரிக்கிறது.

விதிகள் SQLite backups, முழுமையான database export மற்றும் config-sync bundle ஆகியவற்றில் சேர்க்கப்படுகின்றன. `reconcileReasoningRulesForSync`, references இல்லாத imported விதிகளை முடக்கி, அந்த முரண்பாடுகளைப் புகாரளிக்கிறது.
