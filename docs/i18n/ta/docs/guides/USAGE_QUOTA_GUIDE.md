**மூலங்கள்:**

- `open-sse/services/usage.ts` (~70KB) — முதன்மைப் பயன்பாட்டுக் கண்காணிப்பு
- `src/lib/usageAnalytics.ts` (~10KB) — டாஷ்போர்டுக்கான திரட்டல்
- `src/lib/db/quotaSnapshots.ts` — வரலாற்று ஒதுக்கீட்டுத் தரவு
- `src/lib/db/usage*.ts` — பயன்பாடு தொடர்பான பல DB தொகுதிகள்

## மேலோட்டம்

OmniRoute வழியாகச் செல்லும் ஒவ்வொரு கோரிக்கையும் பின்வருவனவற்றைப் பதிவு செய்யும் ஒரு **பயன்பாட்டுப் பதிவை** உருவாக்குகிறது:

- **அடையாளம்**: எந்த API விசை, வழங்குநர், மாதிரி, காம்போ
- **டோக்கன்கள்**: ப்ராம்ப்ட் டோக்கன்கள், நிறைவு டோக்கன்கள், தற்காலிகச் சேமிப்பு டோக்கன்கள், மொத்தம்
- **செலவு**: USD தொகை (விலைத் தரவிலிருந்து கணக்கிடப்பட்டது)
- **நேர விவரங்கள்**: தாமதம், தொடக்க/முடிவு நேரமுத்திரைகள்
- **நிலை**: வெற்றி, பிழை, விகித வரம்பிடப்பட்டது போன்றவை

இந்தப் பதிவுகள் **பகுப்பாய்வுகளாகத்** திரட்டப்பட்டு, **ஒதுக்கீட்டு ஸ்னாப்ஷாட்களாகச்** சேமிக்கப்பட்டு, **ஒவ்வொரு விசைக்குமான பட்ஜெட் வரம்புகளைச்** செயல்படுத்தப் பயன்படுத்தப்படுகின்றன.

```
கோரிக்கை ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    பகுப்பாய்வு  ஒதுக்கீடு  பில்லிங்
                    (டாஷ்போர்டு) (செயலாக்கம்) (ஏற்றுமதி)
```

## என்னென்ன பதிவு செய்யப்படுகின்றன

`usage.ts` சேவை ஒவ்வொரு கோரிக்கைக்கும் ஒரு **பயன்பாட்டு நிகழ்வைப்** பதிவு செய்கிறது:

| புலம்              | வகை     | மூலம்                                                                                         |
| ------------------ | ------- | --------------------------------------------------------------------------------------------- |
| `id`               | string  | பதிவு செய்யும்போது உருவாக்கப்படும் UUID                                                       |
| `apiKeyId`         | string  | கோரிக்கையைத் தொடங்கிய API விசை                                                                |
| `provider`         | string  | வழங்குநர் ID (openai, anthropic போன்றவை)                                                      |
| `model`            | string  | மாதிரி ID (gpt-5, claude-opus-4-6 போன்றவை)                                                    |
| `comboId`          | string? | ஒரு காம்போ வழியாக வழிமாற்றப்பட்டிருந்தால் அதன் காம்போ ID                                      |
| `promptTokens`     | number  | அப்ஸ்ட்ரீம் பதிலிலிருந்து                                                                     |
| `completionTokens` | number  | அப்ஸ்ட்ரீம் பதிலிலிருந்து                                                                     |
| `cachedTokens`     | number  | தற்காலிகச் சேமிப்பில் பொருந்திய டோக்கன்கள் (Anthropic ப்ராம்ப்ட் தற்காலிகச் சேமிப்பு போன்றவை) |
| `totalTokens`      | number  | ப்ராம்ப்ட் + நிறைவு                                                                           |
| `costUsd`          | number  | விலைத் தரவிலிருந்து கணக்கிடப்பட்டது                                                           |
| `latencyMs`        | number  | தொடக்கத்திலிருந்து முடிவுவரையிலான கோரிக்கை கால அளவு                                           |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`                                    |
| `errorClass`       | string? | நிலை `success` ஆக இல்லாவிட்டால் பிழை வகுப்பு                                                  |
| `timestamp`        | string  | ISO 8601 UTC                                                                                  |
| `metadata`         | object  | தனிப்பயன் செருகுநிரலால் உட்செலுத்தப்பட்ட தரவு                                                 |

### டோக்கன்கள் எங்கிருந்து வருகின்றன

**பதில் கையாளுநரில்**, அப்ஸ்ட்ரீம் வழங்குநரின் பதிலிலிருந்து டோக்கன்கள் பிரித்தெடுக்கப்படுகின்றன:

```ts
// open-sse/handlers/chatCore.ts இலிருந்து
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

பயன்பாட்டு விவரங்களைத் திருப்பி அனுப்பாத வழங்குநர்களுக்கு (சில வலை-குக்கீ வழங்குநர்கள்), `~4 chars per token` என்ற தோராயக் கணிப்பு முறையைப் பயன்படுத்தி OmniRoute டோக்கன்களை **மதிப்பிடுகிறது** (`open-sse/services/autoCombo/pipelineRouter.ts` ஐப் பார்க்கவும்).

### தற்காலிகச் சேமிப்பு டோக்கன்கள்

OmniRoute, `cached_tokens` ஐ `prompt_tokens` இலிருந்து தனியாகக் கண்காணிக்கிறது, ஏனெனில்:

- தற்காலிகச் சேமிப்பு டோக்கன்களுக்கு Anthropic prompt caching குறைக்கப்பட்ட கட்டணத்தை வசூலிக்கிறது (வழக்கமான கட்டணத்தின் 10%)
- சில வழங்குநர்கள் வேறுபட்ட விலையில் கணக்கிடப்பட வேண்டிய `cache_read_input_tokens` ஐத் திருப்பி அனுப்புகின்றனர்
- பகுப்பாய்வுகள் **தற்காலிகச் சேமிப்பு பொருத்த விகிதத்தை** = `cached_tokens / prompt_tokens` காட்ட முடியும்

## செலவுக் கணக்கீடு

LiteLLM இலிருந்து ஒத்திசைக்கப்பட்ட **விலை நிர்ணயத் தரவைக்** (`src/lib/pricingSync.ts`) கொண்டு செலவுகள் கணக்கிடப்படுகின்றன:

| மாடல்             | உள்ளீடு $/1M | வெளியீடு $/1M | தற்காலிகச் சேமிப்பு $/1M |
| ----------------- | ------------ | ------------- | ------------------------ |
| gpt-5             | $2.50        | $10.00        | —                        |
| claude-opus-4-6   | $15.00       | $75.00        | $1.50                    |
| claude-sonnet-4-5 | $3.00        | $15.00        | $0.30                    |
| gemini-2.5-pro    | $1.25        | $10.00        | —                        |

செலவுச் சூத்திரம் (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Prompt இலிருந்து தற்காலிகச் சேமிப்பை ஏன் கழிக்க வேண்டும்?** தற்காலிகச் சேமிப்பில் உள்ள பகுதிக்குத் தனியாக விலை நிர்ணயிக்கப்படுகிறது; முழு prompt-க்கும் உள்ளீட்டு விலையை வசூலித்தால் செலவு அதிகமாகக் கணக்கிடப்படும்.

### விலை நிர்ணய ஒத்திசைவு

உள்ளமைக்கப்பட்ட cron பணியால் தூண்டப்படும் `/api/pricing/sync` endpoint வழியாக LiteLLM இலிருந்து விலை நிர்ணயத் தரவு தானாக ஒத்திசைக்கப்படுகிறது; இது பயனர் அணுகக்கூடிய env var அல்ல:

```bash
# கைமுறையாகத் தூண்டுதல்
curl -X POST http://localhost:20128/api/pricing/sync
```

விலை நிர்ணயத் தரவு இல்லாத மாடல்களுக்கு, உள்நிலை சராசரி விகிதங்களைப் பயன்படுத்தி OmniRoute **செலவை மதிப்பிடும்**; இந்த விகிதங்கள் LiteLLM இன் விலை நிர்ணயத் தரவிலிருந்து பெறப்படுகின்றன.

## தேதி வரம்புத் தொகுப்பு

மூலப் பயன்பாட்டுத் தரவிலிருந்து dashboard widget-களை `usageAnalytics.ts` module கணக்கிடுகிறது. இது 7 கால வரம்புகளை ஆதரிக்கிறது:

| வரம்பு   | காலச் சாளரம்                    | பயன்பாடு                              |

| `1d`     | கடந்த 24 மணிநேரம்               | மணிநேரச் செலவு அதிகரிப்பைக் கண்டறிதல் |
| `7d`     | கடந்த 7 நாட்கள்                 | வாராந்திர மதிப்பாய்வு                 |
| `30d`    | கடந்த 30 நாட்கள்                | மாதாந்திரக் கட்டணக் கணக்கீடு          |
| `90d`    | கடந்த 90 நாட்கள்                | காலாண்டுப் பகுப்பாய்வு                |
| `ytd`    | நடப்பு ஆண்டின் ஜனவரி 1 முதல்    | வருடாந்திர பட்ஜெட் கண்காணிப்பு        |
| `all`    | அனைத்து காலமும்                 | வாழ்நாள் புள்ளிவிவரங்கள்              |
| `custom` | பயனர் வரையறுத்த தொடக்கம்/முடிவு | தணிக்கைகள், தேவைக்கேற்ற வினவல்கள்     |

| Widget                         | விளக்கம்                                                            |

| **சுருக்க அட்டைகள்**           | மொத்த கோரிக்கைகள், மொத்தச் செலவு, மொத்த token-கள், வெற்றி விகிதம்   |

| **Provider பிரிவாக்கம்**       | provider வாரியான கோரிக்கைகளைக் காட்டும் பட்டை விளக்கப்படம்          |

## ஒதுக்கீட்டு வரம்பு அமலாக்கம்

ஒவ்வொரு API விசைக்குமான ஒதுக்கீட்டு வரம்பு இரண்டு இடங்களில் அமல்படுத்தப்படுகிறது:

1. **மென்மையான வரம்பு** (`quotaWarnAt`): பயன்பாடு வரம்பை மீறும்போது டாஷ்போர்டில் எச்சரிக்கை
2. **கடின வரம்பு** (`quotaLimit`): வரம்பை மீறும்போது கோரிக்கை HTTP 429 உடன் நிராகரிக்கப்படும்

### உள்ளமைவு

```ts
// ஒவ்வொரு API விசைக்கும்
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — எச்சரிக்கையைக் காட்டு
  quotaLimit: 10_00,    // $10.00 — முழுமையான நிறுத்தம்
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### அமலாக்க ஓட்டம்

```
கோரிக்கை ──▶ quotaCheck()
              │
              ├── வரம்பிற்குள் உள்ளதா?  ──▶ அனுமதி
              │
              └── வரம்பை மீறியதா?  ──▶ 429 Too Many Requests
                                   Retry-After தலைப்புடன்
```

### ஒதுக்கீட்டு நிலைப் பதிவுகள்

போக்குப் பகுப்பாய்விற்கான **வரலாற்று ஒதுக்கீட்டு நிலையைக்** `quotaSnapshots` அட்டவணை சேமிக்கிறது:

| புலம் | விளக்கம் |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | கண்காணிக்கப்படும் விசை |
| `window` | "day" | "week" | "month" |
| `used` | இந்தக் காலச்சாளரத்தில் பயன்படுத்தப்பட்ட செலவு (சென்ட்களில்) |
| `limit` | வரம்பு (சென்ட்களில்) |
| `resetAt` | காலச்சாளரம் மீட்டமைக்கப்படும் நேரம் |
| `createdAt` | நிலைப் பதிவு எடுக்கப்பட்ட நேரம் |

> 0 செலவைப் பயன்படுத்தும் **ஒவ்வொரு கோரிக்கையிலும்** நிலைப் பதிவுகள் எடுக்கப்பட்டு, பின்வருவனவற்றிற்குப் பயன்படுத்தப்படுகின்றன:

- டாஷ்போர்டில் ஒதுக்கீட்டு முன்னேற்றப் பட்டையைக் காண்பிக்க
- 30 நாள் ஒதுக்கீட்டுப் போக்கு வரைபடங்களைக் காட்ட
- பயன்பாடு வரம்பை நெருங்கும்போது எச்சரிக்கைகளைத் தூண்ட

## தக்கவைப்பும் சுத்தப்படுத்தலும்

ஒவ்வொரு கோரிக்கைக்கும் பயன்பாட்டுத் தரவு ~1-10KB அளவுக்கு வளர்கிறது. பெரிய அளவில், இது குறிப்பிடத்தக்கதாக இருக்கலாம்.

### தக்கவைப்பு அமைப்புகள்

பயன்பாட்டு வரலாற்றின் தக்கவைப்பு, UI-இல் உள்ள தரவுத்தள அமைப்புகள் வழியாகவோ அல்லது `/api/settings/database` வழியாகவோ கட்டமைக்கப்படுகிறது.

இயல்புநிலையாக, பயன்பாட்டு வரலாறு **90 நாட்களுக்கு** தக்கவைக்கப்படுகிறது.

### சுத்தப்படுத்தல்

பழைய பதிவுகள் `src/lib/db/cleanup.ts` மூலம் சுத்தப்படுத்தப்படுகின்றன:

- பின்னணி cron செயல்முறையால் தூண்டப்படுகிறது
- கட்டமைக்கப்பட்ட `usageHistory` தக்கவைப்பு அமைப்பை விடப் பழைய `usage_history` பதிவுகளை நீக்குகிறது

### சேமிப்பக மதிப்பீடு

| கோரிக்கை வீதம்  | 30 நாள் சேமிப்பகம் | 90 நாள் சேமிப்பகம் |
| --------------- | ------------------ | ------------------ |
| 100 req/day     | ~3MB               | ~9MB               |
| 1,000 req/day   | ~30MB              | ~90MB              |
| 10,000 req/day  | ~300MB             | ~900MB             |
| 100,000 req/day | ~3GB               | ~9GB               |

மிக அதிகமான போக்குவரத்துக்கு, பின்வருவனவற்றைக் கருத்தில் கொள்ளுங்கள்:

- தரவுத்தள அமைப்புகள் வழியாகத் தக்கவைப்புக் காலத்தைக் குறைத்தல்
- மூலப் பதிவுகளுக்குப் பதிலாக `aggregated_metrics`-ஐப் பயன்படுத்துதல் (பகுப்பாய்வுக்கு மட்டும்)

## சிக்கல் தீர்த்தல்

### "எதிர்பார்த்ததை விடச் செலவு அதிகமாக உள்ளது"

1. **`/api/usage/analytics?groupBy=model`**-ஐச் சரிபார்த்து — விலையுயர்ந்த மாடலைக் கண்டறியுங்கள்
2. **`/api/usage/analytics?groupBy=apiKey`**-ஐச் சரிபார்த்து — அதிகம் பயன்படுத்துபவரைக் கண்டறியுங்கள்
3. விலைத் தரவு புதுப்பித்த நிலையில் இருப்பதை உறுதிப்படுத்துங்கள்: `POST /api/pricing/sync`

### "பதிவுகளைக் காணவில்லை"

- Dashboard → Database → Cleanup என்பதன் கீழ் DB தக்கவைப்பு அமைப்புகளைச் சரிபார்க்கவும் — காலமுறை சுத்தப்படுத்தல் பணி (`src/lib/db/cleanup.ts`) பழைய பதிவுகளை நீக்குகிறது
- `src/lib/db/usage*.ts`-இல் பிழைகள் உள்ளதா எனச் சரிபார்க்கவும் — DB எழுதுதல் தோல்விகள் பதிவுசெய்யப்படுகின்றன, ஆனால் வெளிப்படுத்தப்படுவதில்லை
- கோரிக்கை உண்மையில் `chatCore`-ஐ அடைந்ததா என்பதை உறுதிப்படுத்துங்கள் — combo routing-ஐச் சரிபார்க்கவும்

### "ஒதுக்கீடு அமல்படுத்தப்படவில்லை"

- சாவியின் `quotaLimit` அமைப்பைச் சரிபார்க்கவும்
- `quotaWindow` சரியாக அமைக்கப்பட்டுள்ளதை உறுதிப்படுத்தவும்
- `quotaSnapshots` பதிவுகளைத் தேடுங்கள் — அவை ஒவ்வொரு கோரிக்கையிலும் உருவாக்கப்பட வேண்டும்
