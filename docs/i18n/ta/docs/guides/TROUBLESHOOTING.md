## விரிவான சிக்கல் தீர்வு

---

### இலவச வழங்குநர்களில் விகித வரம்பிடல் (429 / 400 / 401)

**அறிகுறி**: இலவச/அங்கீகாரம் தேவையற்ற வழங்குநர்களுடன் (auggie போன்றவை) `model: "auto"`-ஐப் பயன்படுத்தும்போது, பதில்களுக்குப் பதிலாக இடையிடையே `HTTP 429`, `400` அல்லது `401` கிடைக்கிறது. சில நொடிகளுக்குப் பிறகு அதே கோரிக்கையை மீண்டும் முயற்சிக்கும்போது அது வெற்றியடைகிறது; ஆனால் தானியக்கம் (cron பணிகள், முகவர்கள், ஸ்கிரிப்ட்கள்) முதல் தோல்வியிலேயே செயலிழக்கிறது.

**மூலக் காரணம்**: மூன்று தனித்தனி தோல்வி நிலைகள் ஒன்றோடொன்று சேர்கின்றன:

1. **வழங்குநர் விகித வரம்பு (`429`)**: இலவச அடுக்குகள் ஒவ்வொரு நேரச் சாளரத்திற்குமான ஒதுக்கீட்டை அமல்படுத்தலாம். ஒரே நேரத்தில் பல அழைப்புகள் குவிந்தால் அது தீர்ந்துவிடும்; எனவே சாளரம் மீட்டமைக்கப்படும் வரை அடுத்த கோரிக்கை மறுக்கப்படும்.
2. **பாஸ்த்ரூவில் செயலிழந்த மாடல் (`400`/`401`)**: `auto/*` தொகுப்புகளில், பட்டியலில் பதிவுசெய்யப்பட்டிருந்தாலும் செயலிலுள்ள நற்சான்றுகள் இல்லாத `opencode`-இன் பாஸ்த்ரூ மாடல்கள் இருக்கலாம் (எ.கா. `oc/north-mini-code-free` → `401`). தானியக்க ரூட்டர் அவற்றில் ஒன்றை முயற்சிக்கிறது, தோல்வியடைகிறது, மாற்று முயற்சி தொடங்குவதற்கு முன்பே பிழை வெளியே பரவுகிறது.
3. **ஒரேநேரச் செயலாக்கப் பெருக்கம் (சுமையின் கீழ் `429`)**: பல முகவர்/cron அமர்வுகள் ஒரே நேரத்தில் `auto`-ஐ அணுகும்போது, மொத்தக் கோரிக்கை விகிதம் இலவச வழங்குநர்கள் பொறுத்துக்கொள்ளக்கூடிய அளவை மீறுகிறது; இதனால் முறையான அழைப்புகள்கூட தவறான பயன்பாடாகக் குறிக்கப்படுகின்றன.

**சரிபார்க்கப்பட்ட தீர்வு (சமூகத்தால் தெரிவிக்கப்பட்டது, 2026-08-10)**: இலவச அடுக்கின் நிலையற்ற தன்மையால் செயலிழப்பதற்குப் பதிலாக, சுழற்சி, ஒரேநேரச் செயலாக்கம் மற்றும் மாற்று முயற்சி ஆகியவை அதைத் தாங்கும் வகையில் மூன்று சூழல் மாறிகளைச் சீரமைக்கவும்:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ஏற்பட்டால் மற்றொரு மாடல்/வழங்குநருக்குத் தாவும் (செயலிழந்த பாஸ்த்ரூ மாடல்களைத் தவிர்க்கும்)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # அதிகச் சுமையுள்ள கோரிக்கைகளுக்கான வெளிப்படையான அனுமதி உச்சவரம்பு (இயல்புநிலையில் அமைக்கப்படவில்லை: கோரிக்கை எண்ணிக்கை வரம்பு இல்லை, கீழேயுள்ள குறிப்பைப் பார்க்கவும்)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # மெதுவான அப்ஸ்ட்ரீம்களுக்காக, வரம்பிடப்பட்ட காத்திருப்பை RATE_LIMIT_MAX_WAIT_MS இயல்புநிலையைத் தாண்டி உயர்த்தும்
```

இவற்றை OmniRoute செயல்முறையின் சூழலில் (டீமன், எ.கா. LaunchAgent plist அல்லது `systemctl edit` வழியாக) அமைத்துவிட்டு, OmniRoute-ஐ மறுதொடக்கம் செய்யவும். சுழற்சிக் கொடியே மிக அதிக தாக்கத்தை ஏற்படுத்தும் ஒற்றை அமைப்பாகும்: இது கடுமையான தோல்வியை, தொகுப்பிலுள்ள ஆரோக்கியமான வழங்குநருக்கு எதிரான வெளிப்படையான மறுமுயற்சியாக மாற்றுகிறது.

**குறிப்பு**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ஒரே நேரத்தில் இயங்கும் அதிகச் சுமையுள்ள — நீண்ட சூழல் கொண்ட — கோரிக்கைகளின் எண்ணிக்கையைக் கட்டுப்படுத்துகிறது; இந்த வரம்பு ஒரு அனுமதி வாயில், வழங்குநர் விகித வரம்பி அல்ல. **#503-fanout புதுப்பிப்பு:** இந்த மாறி இனி இயல்புநிலையில் அமைக்கப்படுவதில்லை (மேலே காட்டியதுபோல் வெளிப்படையாக உள்ளமைக்கப்பட்டால் மட்டுமே இப்போது அது கட்டுப்படும்) — அதற்குப் பதிலாக, புரவலரின் உண்மையான நினைவக உச்சவரம்புக்கு ஏற்ப தானாக அளவிடப்படும் பைட் பட்ஜெட் (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) மூலம் அதிகச் சுமையுள்ள கோரிக்கைகளின் அனுமதி கட்டுப்படுத்தப்படுகிறது. ஆகவே, புதிதாகச் செய்யப்பட்ட ஒரு நிறுத்துவம் இந்த மாறியை அமைக்காமலேயே மிகக் குறைவான `503 chat_admission_busy` நிராகரிப்புகளைக் காண வேண்டும்; இங்கு இதை வெளிப்படையாக அமைப்பதும் ஆவணப்படுத்தப்பட்டுள்ளபடியே தொடர்ந்து செயல்படும். வெளிப்படையான பைட்-பட்ஜெட் மேலெழுதல்கள் 8 MiB–2 GiB வரம்புக்குள் கட்டுப்படுத்தப்படும். `413 body_exceeds_budget` என்பது தற்காலிகமானதல்ல: அந்த பைட் பட்ஜெட்டை அதிகரிக்கவும், `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`-ஐக் குறைக்கவும் அல்லது செயல்முறையின் நினைவக உச்சவரம்பை அதிகரிக்கவும். `inflight_bytes_budget` காரணமான சுமைநீக்கம் தற்காலிக வளப் போட்டியாகும்; அதை மீண்டும் முயற்சிக்கலாம். ஒவ்வொரு வழங்குநருக்குமான விகித வரம்பிடல் (`open-sse/services/rateLimitManager.ts`) `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` மற்றும் `RATE_LIMIT_AUTO_ENABLE` ஆகியவற்றால் தனியாக நிர்வகிக்கப்படுகிறது — `.env.example`-ஐப் பார்க்கவும்.

**இது செயல்பட்டதா என்பதைச் சரிபார்ப்பது எப்படி**: உங்கள் முகவர்/cron-ஐ அடுத்தடுத்து இருமுறை இயக்கி, இரண்டும் வெற்றியடைவதை உறுதிப்படுத்தவும். தீர்வுக்கு முன்பு, இரண்டாவது இயக்கம் பொதுவாக `429`/`401` பிழையை ஏற்படுத்தும். தீர்வுக்குப் பிறகு, தோல்விகள் (ஏதேனும் இருந்தால்) வெளிப்படையாக மீண்டும் முயற்சிக்கப்பட்டு அழைப்பு நிறைவடையும். மேலும், `curl /monitoring/health`-ஐ இயக்கி, வழங்குநர் இணைப்புகளில் உள்ள `rateLimitedUntil` புலத்தையும் பாதிக்கப்பட்ட வழங்குநர்களுக்கான `circuitBreakers.providerBreakers[].state`-ஐயும் கண்காணிக்கலாம் — நிலை என்பது `CLOSED`, `DEGRADED`, `OPEN` அல்லது `HALF_OPEN` ஆகியவற்றில் ஒன்றாக இருக்கும் (`src/shared/utils/circuitBreaker.ts`-ஐப் பார்க்கவும்); தொடர்ந்து தோல்வியடையும் ஒரு வழங்குநர், மீட்டமைப்புச் சாளரம் ஒரு சோதனையை அனுமதிப்பதற்கு (`HALF_OPEN`) முன்பு `CLOSED → DEGRADED → OPEN` என மாறும்.

**இன்னும் 429 தோன்றினால்**: அந்த வழங்குநருக்கான செயலில் உள்ள கணக்கின் _ஒதுக்கீடு_ உண்மையிலேயே தீர்ந்துவிட்டது (விகிதம் மட்டும் அல்ல). OmniRoute முகப்புப் பலகை → Providers → Accounts என்பதில் அதே வழங்குநருக்கான இரண்டாவது கணக்கைச் சேர்க்கவும் அல்லது மற்றொரு இலவச வழங்குநரைக் (எ.கா. `routeway`, `auggie`) கலந்து பயன்படுத்தவும். சுழற்சி தற்காலிக விகித/400/401 சிக்கல்களுக்கு மட்டுமே உதவும்; முழுமையான ஒதுக்கீட்டுத் தீர்வுக்கு இரண்டாவது நற்சான்று அல்லது வேறு வழங்குநர் தேவை.

**பார்வை மாடல்களில் (`auto/vision`, `bazaarlink/*`) 403 தோன்றினால்**: இணைக்கப்பட்ட கணக்கில் பார்வை அம்சத்தை உள்ளடக்கிய கட்டணத் திட்டம் இல்லை அல்லது API விசைக்கு போதுமான அனுமதிகள் இல்லை. வழங்குநரின் முகப்புப் பலகையில், விசையின் நோக்கெல்லை பார்வை/பல்முறைமையை உள்ளடக்குகிறதா என்பதைச் சரிபார்க்கவும் அல்லது கட்டண அடுக்குக் கணக்கை இணைத்து, அதைப் பார்வை இலக்காக வைத்திருக்கவும்.

## npm install எச்சரிக்கைகள் (ERESOLVE / peer / deprecated)

நீங்கள் `npm install -g omniroute`-ஐ இயக்கும்போது, `npm warn ERESOLVE`, peer-dependency அறிவிப்புகள் மற்றும் `deprecated` செய்திகள் போன்ற ஏராளமான எச்சரிக்கைகளைப் பார்க்கலாம். **இவை எதிர்பார்க்கப்பட்டவை மற்றும் பாதிப்பற்றவை.** வெளியீட்டில் `added <N> packages` என்பதைக் கண்டால், உங்கள் நிறுவல் வெற்றிகரமாக முடிந்துள்ளது.

peer-dependency தீர்மான எச்சரிக்கைகளைத் தவிர்க்க, OmniRoute ஆதரிக்கும் நிறுவல் வடிவத்தைப் பயன்படுத்தவும்:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` என்பது `ERESOLVE` மற்றும் peer-dependency அறிவிப்புகளை மட்டும் தவிர்க்கிறது. வழக்கொழிந்தவை குறித்த அறிவிப்புகள் தொடர்ந்து காட்டப்படும்; ஏனெனில் அவை மறைமுக மூன்றாம் தரப்புத் தொகுப்புகளிலிருந்து வருகின்றன. நிறுவல் தோல்வியடைந்ததைக் அவை குறிக்கவில்லை.

OmniRoute-இன் கட்டுப்பாட்டில் இல்லாத மூன்றாம் தரப்புத் தொகுப்புகளிலுள்ள காலாவதியான peer-dependency வரம்புகளிலிருந்தே இந்த எச்சரிக்கைகள் வருகின்றன:

1. **`marked-terminal`-க்கு `marked >=1 <16` தேவை, ஆனால் `marked@18` கண்டறியப்பட்டது** — நடைமுறையில் இது நன்றாகச் செயல்படுகிறது; upstream peer வரம்பு காலாவதியானதாக மட்டுமே உள்ளது.
2. **`deprecated prebuild-install@7.1.3`** — இது மறைமுகமாகப் பயன்படுத்தப்படும் native-binary பதிவிறக்க உதவியாளர். நிலைநிறுத்தப்பட்ட `wreq-js` போக்குவரத்து binding-ஐ நிறுவுவதற்கு இது
   பயன்படுத்தப்படுவதில்லை; மேலும் web-cookie வழங்குநரின் போக்குவரத்து அமைப்பு தோல்வியடைந்ததையும் இது
   குறிக்கவில்லை.

**எந்த நடவடிக்கையும் தேவையில்லை** — upstream தொகுப்புகளை fork செய்யாமல் இந்த எச்சரிக்கைகளை முழுமையாக முடக்க முடியாது.

## Gemini Web மற்றும் Playwright Chromium

ஒரு Gemini Web கோரிக்கை, Playwright Chromium நிறுவப்படவில்லை என்ற செய்தியுடன் `503`-ஐத்
திருப்பினால், npm தொகுப்பு உள்ளது; ஆனால் உலாவி binary காணவில்லை என்று பொருள்.
Playwright, உலாவி பதிவிறக்கங்களை npm தொகுப்பு நிறுவலிலிருந்து வேண்டுமென்றே
தனியாக வைத்திருக்கிறது; எனவே உலாவி நிறுவப்படும் வரை இந்தப் பதில் எதிர்பார்க்கப்பட்டதே.

உலகளாவிய npm நிறுவலுக்கு, OmniRoute தொகுப்பின் கோப்பகத்திலிருந்து Chromium-ஐ
நிறுவவும்; இதனால் உலாவியின் cache அதே Playwright நிறுவலுக்குச் சொந்தமானதாக இருக்கும்:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

நிறுவலுக்குப் பிறகு OmniRoute-ஐ மறுதொடக்கம் செய்து, பின்னர் Gemini Web கோரிக்கையை மீண்டும் முயற்சிக்கவும். நீங்கள்
Docker image-இலிருந்து OmniRoute-ஐ இயக்கினால், Chromium மற்றும் அதன் சார்புகளை உள்ளடக்கிய `-web` image-ஐ (அல்லது `runner-web`
build target-ஐ) பயன்படுத்தவும்; base image அவற்றை
உள்ளடக்காது.

## வைரஸ் தடுப்பு மென்பொருளின் தவறான நேர்மறை முடிவுகள்

<a name="antivirus-false-positives"></a>

### Avast/AVG, `README.md` கோப்பை `MD:HttpRequest-inf[Susp]` எனத் தனிமைப்படுத்துகிறது

**இது ஒரு தவறான நேர்மறை முடிவு. எதுவும் பாதிக்கப்படவில்லை; எந்த நடவடிக்கையும் தேவையில்லை.**

பல HTTP கோரிக்கைகளைப் போலத் தோன்றும் இணைப்புகளைக் கொண்ட எளிய உரை/Markdown கோப்புகளைக் குறியிடும் ஒரு heuristic சோதனையை Avast மற்றும் AVG இயக்குகின்றன. OmniRoute-இன் `README.md`, npm தொகுப்பிற்குள் வழங்கப்படுகிறது (இது `package.json` → `files` என்பதில் பட்டியலிடப்பட்டுள்ளது), எனவே global install செய்யும்போது அது `node_modules/omniroute/README.md` என்ற இடத்தில் சேமிக்கப்படுகிறது — மேலும் அதில் சுமார் 15 `http://localhost:20128/...` எடுத்துக்காட்டுகள் உள்ளன (MCP HTTP/SSE endpoints, A2A `.well-known` URL மற்றும் `curl` துணுக்குகள்). அந்த அளவிலான இணைப்பு அடர்த்தியே இந்த heuristic சோதனையைத் தூண்டுவதற்குப் போதுமானது.

இது சமீபத்தில்தான் தொடங்கியிருந்தால்: கோப்பின் தன்மை மாறவில்லை. README-இன் endpoints அட்டவணை விரிவடைந்தது (MCP HTTP + SSE + A2A சேர்க்கப்பட்டன), மேலும் அதிகமான `curl` எடுத்துக்காட்டுகள் சேர்க்கப்பட்டதால், அது வரம்பைத் தாண்டியது.

இந்தக் கோப்பு எந்த இயக்கக்கூடிய உள்ளடக்கமும் இல்லாத, செயலற்ற ஆவணமாகும். தனிமைப்படுத்தலில் இருந்து இதைப் பாதுகாப்பாக மீட்டெடுக்கலாம்.

**என்ன செய்ய வேண்டும்:**

1. **அறிவிப்புகளை நிறுத்துங்கள்** — உங்கள் வைரஸ் தடுப்பு மென்பொருளில் நிறுவல் கோப்பகத்தை விலக்காகச் சேருங்கள் (Avast: Settings → Exceptions); உங்கள் global `node_modules` பாதை மற்றும்/அல்லது OmniRoute தரவுக் கோப்பகத்தை (`~/.omniroute/`) சேர்க்கவும்.
2. **தவறான நேர்மறை முடிவைப் புகாரளியுங்கள்** — <https://www.avast.com/false-positive-file-form.php> என்ற படிவத்தில், தனிமைப்படுத்தப்பட்ட `README.md` கோப்பை இணைக்கவும். ஒரு உரைக் கோப்பிற்கு vendor-இன் heuristic அளவுக்கு அதிகமாக எதிர்வினையாற்றுவதே இதற்குக் காரணம் என்பதால், அனைவருக்கும் உதவும் தீர்வு இதுதான்.

**எங்கள் தரப்பில் இதை ஏன் "சரிசெய்வதில்லை":** எல்லா எடுத்துக்காட்டுகளும் `http://localhost` ஆகும்; மேலும், சுயமாகக் கையொப்பமிடப்பட்ட சான்றிதழால் ஏற்படும் சிக்கல்கள் இல்லாமல் localhost-ஐ `https` ஆகப் பயன்படுத்த முடியாது. ஒரு vendor-இன் heuristic சோதனையைத் தவிர்ப்பதற்காக ஆவணங்களைச் சிதைப்பது, scanner பிழையைத் திருப்திப்படுத்துவதற்காக ஒவ்வொரு வாசகருக்கும் பாதிப்பை ஏற்படுத்தும்.

### Kaspersky, Desktop செயலியை `PDM:Trojan.Win32.Generic` எனக் குறியிடுகிறது

**இது நடத்தை சார்ந்த heuristic-இலிருந்து வரும் ஒரு தவறான நேர்மறை முடிவு. எதுவும் பாதிக்கப்படவில்லை.** Kaspersky-இன் `PDM:` முன்னொட்டு, இந்தத் தீர்ப்பு அதன் Proactive Defense Module (System Watcher)-இலிருந்து வருகிறது என்பதைக் குறிக்கிறது; இது installer-ஐ அறியப்பட்ட malware-உடன் ஒப்பிடுவதற்குப் பதிலாக, அது _என்ன செய்கிறது_ என்பதை மதிப்பிடுகிறது. இது தூண்டப்படும்போது, Kaspersky முழு நிறுவலையும் "roll back" செய்கிறது — ஏற்கெனவே எழுதப்பட்ட கோப்புகளை நீக்குகிறது — எனவே செயலி இறுதியில் செயலிழந்தோ காணாமலோ போகிறது.

இது குறியிடும் கோப்புகள், desktop செயலியுடன் தொகுக்கப்பட்டுள்ள, அறிவிக்கப்பட்ட open-source dependencies-இன் வழக்கமான பகுதிகளாகும். எடுத்துக்காட்டாக:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` மற்றும் `workerProcessEntry.js` — செயலிக்குள் provider உள்நுழைவு மற்றும் browser-backed chat ஆகியவற்றுக்குப் பயன்படுத்தப்படும் browser automation நூலகமான [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — web-cookie providers-இல் browser-fingerprinted HTTP-க்குப் பயன்படுத்தப்படும், குறிப்பிட்ட பதிப்பில் நிலைப்படுத்தப்பட்ட `wreq-js` native binding (`<arch>` என்பது `x64` அல்லது `arm64`).

**இது ஏன் தூண்டப்படுகிறது:** Windows installer **இன்னும் code-signed செய்யப்படவில்லை**; எனவே கையொப்பமிடப்படாத NSIS installer-க்கு எந்த நற்பெயரும் இல்லை, மேலும் நடத்தை சார்ந்த heuristic சோதனைகள் அதிகபட்ச தீவிரத்துடன் இயங்குகின்றன. தொகுக்கப்பட்ட native DLL மற்றும் `%LOCALAPPDATA%\Programs\OmniRoute` என்பதன் கீழ் எழுதப்படும் நூற்றுக்கணக்கான `.js` கோப்புகளுடன் (Next.js standalone build-இலிருந்து hash பின்னொட்டு கொண்ட package கோப்பகங்கள் உட்பட) சேரும்போது, heuristic சோதனையைத் தூண்டுவதற்கு அது போதுமானதாகிறது. Code signing திட்டமிடப்பட்டுள்ளது; அது நடைமுறைக்கு வரும் வரை, புதிய releases-இல் இது மீண்டும் நிகழலாம்.

**என்ன செய்ய வேண்டும்:**

1. **முதலில் உங்கள் பதிவிறக்கத்தைச் சரிபாருங்கள்** (இது கோப்பு சேதப்படுத்தப்பட்டிருக்கலாம் என்ற சாத்தியத்தை நீக்குகிறது). ஒவ்வொரு release-உம் `latest.yml`-ஐ வெளியிடுகிறது; அதிலுள்ள `sha512` புலம் (base64), `OmniRoute.Setup.<version>.exe` installer-ஐ உள்ளடக்குகிறது. PowerShell-இல், installer உள்ள கோப்பகத்திலிருந்து:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   வெளியீடு `latest.yml` → `sha512` உடன் பொருந்த வேண்டும். அது பொருந்தவில்லை என்றால், கோப்பை நீக்கிவிட்டு [GitHub releases பக்கத்திலிருந்து](https://github.com/diegosouzapw/OmniRoute/releases) மட்டும் மீண்டும் பதிவிறக்கவும்.
2. **மீட்டெடுத்து + விலக்காகச் சேருங்கள்** — roll back செய்யப்பட்ட உருப்படிகளைத் தனிமைப்படுத்தலில் இருந்து மீட்டெடுத்து, `%LOCALAPPDATA%\Programs\OmniRoute` என்பதற்கு ஒரு விலக்கைச் சேர்க்கவும் (Kaspersky → Settings → Threats and Exclusions); பின்னர் மீண்டும் நிறுவவும்.
3. **தவறான நேர்மறை முடிவைப் புகாரளியுங்கள்** — <https://opentip.kaspersky.com/>. பயனர்கள் சமர்ப்பிக்கும் தவறான நேர்மறை அறிக்கைகள் allowlisting செயல்முறையை உண்மையாகவே வேகப்படுத்துகின்றன.

### உள்நுழைவுப் பக்கம் செயலிழக்கிறது அல்லது "Module self-registration" பிழையைக் காட்டுகிறது

**காரணம்:** OmniRoute அங்கீகரித்த பாதுகாப்பான இயக்கச் சூழலின் குறைந்தபட்ச வரம்பிற்கு வெளியே உள்ள Node.js பதிப்பை நீங்கள் இயக்குகிறீர்கள். OmniRoute தேவைப்படுத்தும் பாதுகாப்புத் திருத்தங்களின் குறைந்தபட்ச வரம்பிற்குக் கீழே உள்ள பழைய Node 22 அல்லது 24 திருத்தப் பதிப்பை இயக்குவதே மிகவும் பொதுவான நிலையாகும்.

**அறிகுறிகள்:**

- உள்நுழைவுப் பக்கம் வெற்றுத் திரையையோ சேவையகப் பிழையையோ காட்டுகிறது
- கன்சோலில் `Error: Module did not self-register` அல்லது அதைப் போன்ற நேட்டிவ் பைண்டிங் பிழைகள் காட்டப்படுகின்றன
- இயக்கச் சூழல் ஆதரிக்கப்படும் பாதுகாப்புக் கொள்கைக்கு வெளியே இருந்தால், உள்நுழைவுப் பக்கம் உங்கள் Node பதிப்புடன் **ஆரஞ்சு நிற எச்சரிக்கைப் பட்டையை** காட்டுகிறது

**தீர்வு:**

1. ஆதரிக்கப்படும் Node.js LTS வெளியீட்டை நிறுவவும் (பரிந்துரைக்கப்படுவது: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. உங்கள் பதிப்பைச் சரிபார்க்கவும்: 24.x LTS தொடரில் `node --version` என்பது `v24.0.0` அல்லது அதற்குப் புதிய பதிப்பைக் காட்ட வேண்டும்
3. OmniRoute-ஐ மீண்டும் நிறுவவும்: `npm install -g omniroute`
4. மறுதொடக்கம் செய்யவும்: `omniroute`

> **ஆதரிக்கப்படும் பாதுகாப்பான பதிப்புகள்:** `>=22.22.2 <23` அல்லது `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) மற்றும் Node.js 26 முழுமையாக ஆதரிக்கப்படுகின்றன.

### npm v11+: `better-sqlite3` நிறுவப்படவில்லை (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**காரணம்:** npm v11 (Node.js 24+ உடன் வழங்கப்படுகிறது) இயல்பாகவே விருப்பச்
சார்புகளுக்கான நிறுவல் ஸ்கிரிப்ட்களைத் தடுக்கிறது. `better-sqlite3` என்பது `optionalDependencies`-இல் பட்டியலிடப்பட்டிருப்பதாலும்,
நேட்டிவ் கம்பைலேஷன் (`node-gyp rebuild`) தேவைப்படுவதாலும், npm எந்த அறிவிப்புமின்றி அதைத் தவிர்க்கிறது.

**அறிகுறிகள்:**

- தொடக்கத்தின்போது `Cannot find module 'better-sqlite3'` என்ற பிழையுடன் சேவையகம் செயலிழக்கிறது
- `ls node_modules/better-sqlite3` என்பது "No such file or directory" என்பதைக் காட்டுகிறது
- `npm ls better-sqlite3` என்பது `(empty)` என்பதைக் காட்டுகிறது

**தீர்வு:**

1. நிறுவல் ஸ்கிரிப்ட்களுக்கு ஒப்புதல் அளித்து மீண்டும் நிறுவவும்:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. அல்லது முன்கூட்டியே உருவாக்கப்பட்ட தொகுப்பைக் கைமுறையாக நிறுவவும்:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. அது செயல்படுகிறதா என்பதைச் சரிபார்க்கவும்: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**காரணம்:** உலகளாவிய `npm install -g omniroute` நிறுவலுக்குப் பிறகு, தொகுப்பிற்குள் உள்ள `better-sqlite3` நேட்டிவ் பைனரி, உள்ளூரில் இயங்கும் கட்டமைப்பு அல்லது Node.js ABI-இலிருந்து வேறுபட்ட ஒன்றிற்காக கம்பைல் செய்யப்பட்டிருக்கலாம். முன்கூட்டியே உருவாக்கப்பட்ட பைனரி உங்கள் சூழலுடன் பொருந்தாதபோது, macOS-இல் (Apple Silicon மற்றும் Intel இரண்டிலும்) இது பொதுவாக நிகழ்கிறது.

**அறிகுறிகள்:**

- தொடக்கத்தின்போது `dlopen` பிழையுடன் சேவையகம் உடனடியாகத் தோல்வியடைகிறது
- பிழையில் `slice is not valid mach-o file` இடம்பெறுகிறது
- முழுமையான எடுத்துக்காட்டு:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**தீர்வு — உங்கள் உள்ளூர் சூழலுக்காக மீண்டும் உருவாக்கவும் (Node.js பதிப்பைக் குறைக்கத் தேவையில்லை):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **குறிப்பு:** இது உங்கள் உள்ளூர் Node.js பதிப்பு மற்றும் CPU கட்டமைப்புக்கு எதிராக நேட்டிவ் பைண்டிங்கை மீண்டும் கம்பைல் செய்து, பைனரி பொருந்தாமையைத் தீர்க்கிறது. அதிகாரப்பூர்வமாக ஆதரிக்கப்படும் இயக்கச் சூழல் வரம்பு **`>=22.22.2 <23` அல்லது `>=24.0.0 <27`** (`src/shared/utils/nodeRuntimeSupport.ts`-இல் உள்ள `SUPPORTED_NODE_RANGE`, `package.json`-இன் `engines` புலத்துடன் ஒத்திசைக்கப்பட்டுள்ளது). Node.js 24.x LTS (Krypton) மற்றும் Node.js 26 ஆகியவை `better-sqlite3` v12.x உடன் முழுமையாக ஆதரிக்கப்படுகின்றன.

### வழங்குநர் சரிபார்ப்பு "fetch failed" எனக் காட்டுகிறது

**காரணம்:** API விசை சரிபார்ப்பு முனைப்புள்ளி (`POST /api/providers/validate`) முன்பு ப்ராக்ஸி உள்ளமைவைத் தவிர்த்து வந்ததால், ப்ராக்ஸி வழித்தடம் தேவைப்படும் சூழல்களில் தோல்விகள் ஏற்பட்டன.

**தீர்வு (v3.5.5+):** இது இப்போது சரிசெய்யப்பட்டுள்ளது. வழங்குநர் சரிபார்ப்பு `runWithProxyContext` வழியாகச் சென்று, வழங்குநர்-நிலை மற்றும் உலகளாவிய ப்ராக்ஸி அமைப்புகளைத் தானாகவே மதிக்கிறது.

### டோக்கன் நிலைச் சரிபார்ப்பு "fetch failed" பிழையுடன் தோல்வியடைகிறது

**காரணம்:** பின்னணியில் நடைபெறும் OAuth டோக்கன் புதுப்பிப்பு, ஒவ்வொரு இணைப்பிற்குமான ப்ராக்ஸி உள்ளமைவைத் தீர்மானிக்கவில்லை.

**தீர்வு (v3.5.5+):** டோக்கன் நிலைச் சரிபார்ப்பு திட்டமிடுபவர், புதுப்பிக்க முயல்வதற்கு முன் இப்போது ஒவ்வொரு இணைப்பிற்குமான ப்ராக்ஸி உள்ளமைவைத் தீர்மானிக்கிறார். v3.5.5+ பதிப்புக்குப் புதுப்பிக்கவும்.

### SOCKS5 ப்ராக்ஸி "invalid onRequestStart method" எனத் திருப்பியளிக்கிறது

**காரணம்:** Node.js 22-இல், undici@8 அனுப்புநர் Node-இன் உள்ளமைக்கப்பட்ட `fetch()` செயலாக்கத்துடன் இணக்கமற்றதாக உள்ளது.

**தீர்வு (v3.5.5+):** ப்ராக்ஸி அனுப்புநர் செயலில் இருக்கும்போது, தொடர்ச்சியான நடத்தையை உறுதிசெய்ய OmniRoute இப்போது undici-இன் சொந்த `fetch()` செயல்பாட்டைப் பயன்படுத்துகிறது. v3.5.5+ பதிப்புக்குப் புதுப்பிக்கவும்.

### WSL-இல் MITM ப்ராக்ஸி: Windows ஹோஸ்டில் உள்ள டெஸ்க்டாப் செயலிகள் இடைமறிக்கப்படுவதில்லை

**காரணம்:** OmniRoute இயங்கும் சூழலில் MITM ப்ராக்ஸியும் அதன் CA சான்றிதழும் நிறுவப்படுகின்றன. WSL-இன் கீழ், அந்தச் சூழல் Linux விருந்தினர் அமைப்பாகும்; ஆனால் AI டெஸ்க்டாப் செயலிகள் (Kiro, Trae, Copilot, Zed, …) Windows ஹோஸ்டில் இயங்குகின்றன. ஹோஸ்ட் செயலிகள் விருந்தினர் அமைப்பின் சான்றிதழ் சேமிப்பகத்தை நம்புவதில்லை; மேலும் விருந்தினர் அமைப்பின் சிஸ்டம் ப்ராக்ஸி வழியாகப் போக்குவரத்தை அனுப்புவதில்லை. எனவே, டெஸ்க்டாப் இடைமறிப்பு அங்கு செயல்படாது.

**பரிந்துரை:** நீங்கள் இடைமறிக்க விரும்பும் டெஸ்க்டாப் செயலிகள் இயங்கும் அதே OS-இல் OmniRoute-ஐ நேரடியாக இயக்கவும் (Windows செயலிகளுக்கு Windows; அதேபோல் macOS/Linux). ஹோஸ்ட் செயலிகளைக் குறிவைத்தபடி OmniRoute-ஐ WSL-க்குள் வைத்திருப்பதற்கு, உருவாக்கப்பட்ட CA சான்றிதழை Windows ஹோஸ்டில் கைமுறையாக நம்பகமானதாகச் சேர்த்து, ஒவ்வொரு ஹோஸ்ட் செயலியின் நெட்வொர்க்/ப்ராக்ஸி அமைப்புகளையும் WSL ப்ராக்ஸி முனைப்புள்ளியை நோக்கி அமைக்க வேண்டும் — இது ஆதரிக்கப்படாத, நிலையற்ற அமைப்பாகும்.

## கிளவுட் சிக்கல்கள்

### கிளவுட் ஒத்திசைவுப் பிழைகள்

1. `BASE_URL` இயங்கிக்கொண்டிருக்கும் உங்கள் இன்ஸ்டன்ஸைக் குறிக்கிறதா என்பதைச் சரிபார்க்கவும் (எ.கா., `http://localhost:20128`)
2. `CLOUD_URL` உங்கள் கிளவுட் எண்ட்பாயிண்டைக் குறிக்கிறதா என்பதைச் சரிபார்க்கவும் (எ.கா., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` மதிப்புகளை சர்வர்-பக்க மதிப்புகளுடன் ஒத்திசைவாக வைத்திருக்கவும்

### கிளவுடில் `stream=false` 500 பிழையை வழங்குகிறது

**அறிகுறி:** ஸ்ட்ரீமிங் அல்லாத அழைப்புகளுக்கான கிளவுட் எண்ட்பாயிண்டில் `Unexpected token 'd'...` தோன்றுகிறது.

**காரணம்:** கிளையன்ட் JSON-ஐ எதிர்பார்க்கும்போது, அப்ஸ்ட்ரீம் SSE பேலோடை வழங்குகிறது.

**தற்காலிகத் தீர்வு:** கிளவுடுக்கான நேரடி அழைப்புகளில் `stream=true` பயன்படுத்தவும். உள்ளூர் ரன்டைமில் SSE→JSON மாற்று ஏற்பாடு உள்ளது.

### கிளவுட் இணைக்கப்பட்டுள்ளதாகக் கூறினாலும் "Invalid API key" தோன்றுகிறது

1. உள்ளூர் டாஷ்போர்டிலிருந்து (`/api/keys`) புதிய விசையை உருவாக்கவும்
2. கிளவுட் ஒத்திசைவை இயக்கவும்: கிளவுடை இயக்கு → இப்போது ஒத்திசை
3. பழைய/ஒத்திசைக்கப்படாத விசைகள் கிளவுடில் இன்னும் `401` பிழையை வழங்கக்கூடும்

## Docker சிக்கல்கள்

### Docker IPv6 / இணைப்பு மீட்டமைப்பு

<a name="docker-ipv6"></a>

**அறிகுறிகள்:** `curl http://localhost:20128/v1/models` என்பது `curl: (56) Recv failure: Connection reset by peer` என வழங்குகிறது. டாஷ்போர்டும் அங்கீகரிக்கப்படாத எண்ட்பாயிண்ட்களும் செயல்படுகின்றன, ஆனால் அங்கீகரிக்கப்பட்ட எண்ட்பாயிண்ட்கள் தோல்வியடைகின்றன — இது அங்கீகாரச் சிக்கல் போலத் தோன்றினாலும், உண்மையில் அப்படியல்ல.

**காரணம்:** `docker run -p 20128:20128` ஆனது `0.0.0.0` (IPv4) மற்றும் `::` (IPv6) ஆகிய இரண்டிலும் வெளியிடுகிறது, ஆனால் கண்டெய்னருக்குள் உள்ள செயல்முறை IPv4-இல் மட்டுமே கவனிக்கிறது. `localhost` முதலில் `::1` ஆகத் தீர்மானிக்கப்படும் ஹோஸ்ட்களில், இணைப்பு IPv6-இல் வெளியிடப்பட்ட போர்ட்டை அடைகிறது; அதன் பின்னால் எந்த லிஸனரும் இல்லாததால் → இணைப்பு மீட்டமைக்கப்படுகிறது.

**தீர்வு:**

1. **விரைவான கண்டறிதல்:** `curl -4 http://localhost:20128/v1/models` என்பதை இயக்கவும். இது `-4` உடன் செயல்பட்டு, அது இல்லாமல் தோல்வியடைந்தால், உங்களிடம் IPv6 பைண்ட் பொருத்தமின்மை உள்ளது.
2. **நிரந்தரத் தீர்வு:** உங்கள் `docker run` கட்டளையில் `-p 127.0.0.1:20128:20128` பயன்படுத்துவதன் மூலம் வெளிப்படையாக IPv4 உடன் பைண்ட் செய்யவும்:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   இது IPv4 பைண்டை கட்டாயப்படுத்துவதுடன், அனைத்து ஹோஸ்ட் இடைமுகங்களிலும் ப்ராக்ஸி வெளிப்படுத்தப்படுவதையும் தவிர்க்கிறது.

## பிழைத்திருத்தம்

### பதிவு கோப்புகளை இயக்குதல்

உங்கள் `.env` கோப்பில் `APP_LOG_TO_FILE=true` என்பதை அமைக்கவும். பயன்பாட்டுப் பதிவுகள் `logs/` கீழ் எழுதப்படும்.
அமைப்புகளில் அழைப்புப் பதிவு பைப்லைன் இயக்கப்பட்டிருக்கும்போது, கோரிக்கை ஆர்டிஃபாக்ட்கள் `${DATA_DIR}/call_logs/` கீழ் சேமிக்கப்படும்.
பைப்லைன் பதிவு இயக்கப்பட்டிருக்கும்போது, ஸ்ட்ரீம் சங்க் பேலோடுகளைத் தவிர்க்க `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` என அமைக்கவும் அல்லது ஆர்டிஃபாக்ட் வரம்பை KB-இல் மாற்ற `CALL_LOG_PIPELINE_MAX_SIZE_KB`-ஐச் சரிசெய்யவும்.

### வழங்குநரின் ஆரோக்கியத்தைச் சரிபார்த்தல்

```bash
# ஆரோக்கிய டாஷ்போர்டு
http://localhost:20128/dashboard/health

# API ஆரோக்கியச் சோதனை
curl http://localhost:20128/api/monitoring/health
```

### ரன்டைம் சேமிப்பகம்

- முதன்மை நிலை: `${DATA_DIR}/storage.sqlite` (வழங்குநர்கள், சேர்க்கைகள், மாற்றுப்பெயர்கள், விசைகள், அமைப்புகள்)
- பயன்பாடு: `storage.sqlite`-இல் உள்ள SQLite அட்டவணைகள் (`usage_history`, `call_logs`, `proxy_logs`) + விருப்பமான `${DATA_DIR}/call_logs/`
- பயன்பாட்டுப் பதிவுகள்: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` என இருக்கும்போது)
- அழைப்புப் பதிவு ஆர்டிஃபாக்ட்கள்: அழைப்புப் பதிவு பைப்லைன் இயக்கப்பட்டிருக்கும்போது `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

கோரிக்கைப் பதிவுகள் பக்கத்தில் உள்ள **வரலாற்றை அழி** செயல், `call_logs`, பழைய
`request_detail_logs`, மற்றும் உள்ளூர் `${DATA_DIR}/call_logs/` ஆர்டிஃபாக்ட் அடைவு ஆகியவற்றை அழிக்கிறது.

## சர்க்யூட் பிரேக்கர் சிக்கல்கள்

### வழங்குநர் OPEN நிலையில் சிக்கியுள்ளது

ஒரு வழங்குநரின் சர்க்யூட் பிரேக்கர் OPEN நிலையில் இருக்கும்போது, கூல்டவுன் காலம் முடியும் வரை கோரிக்கைகள் தடுக்கப்படும்.

**தீர்வு:**

1. **டாஷ்போர்டு → அமைப்புகள் → மீள்திறன்** என்பதற்குச் செல்லவும்
2. பாதிக்கப்பட்ட வழங்குநருக்கான சர்க்யூட் பிரேக்கர் கார்டைச் சரிபார்க்கவும்
3. எல்லா பிரேக்கர்களையும் அழிக்க **அனைத்தையும் மீட்டமை** என்பதைக் கிளிக் செய்யவும் அல்லது கூல்டவுன் காலம் முடியும் வரை காத்திருக்கவும்
4. மீட்டமைப்பதற்கு முன் வழங்குநர் உண்மையிலேயே கிடைக்கிறாரா என்பதைச் சரிபார்க்கவும்

### வழங்குநர் தொடர்ந்து சர்க்யூட் பிரேக்கரைத் தூண்டுகிறது

ஒரு வழங்குநர் மீண்டும் மீண்டும் OPEN நிலைக்குச் சென்றால்:

1. தோல்வி முறையை அறிய **டாஷ்போர்டு → உடல்நிலை → வழங்குநர் உடல்நிலை** என்பதைச் சரிபார்க்கவும்
2. **அமைப்புகள் → மீள்திறன் → வழங்குநர் சுயவிவரங்கள்** என்பதற்குச் சென்று தோல்வி வரம்பை அதிகரிக்கவும்
3. வழங்குநர் API வரம்புகளை மாற்றியுள்ளாரா அல்லது மீண்டும் அங்கீகரிக்க வேண்டுமா என்பதைச் சரிபார்க்கவும்
4. தாமதத் தொலைஅளவீட்டை மதிப்பாய்வு செய்யவும் — அதிகத் தாமதம் நேர முடிவை அடிப்படையாகக் கொண்ட தோல்விகளை ஏற்படுத்தக்கூடும்

### "ஆதரிக்கப்படாத மாடல்" பிழை

- முதல் பகுதி, உங்களிடம் நற்சான்றுகள் உள்ள ஒரு வழங்குநராக இருக்கும் மாடல் ஐடியைப் பயன்படுத்தவும் (`openai/whisper-1`, `openrouter/deepgram/nova-3`). தனித்த `deepgram/nova-3`-க்கு சொந்த Deepgram விசை தேவை.
- **டாஷ்போர்டு → வழங்குநர்கள்** என்பதில் வழங்குநர் இணைக்கப்பட்டுள்ளதைச் சரிபார்க்கவும்

### உரைமாற்றம் காலியாக வருகிறது அல்லது தோல்வியடைகிறது

- ஆதரிக்கப்படும் ஆடியோ வடிவங்களைச் சரிபார்க்கவும்: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- கோப்பின் அளவு வழங்குநரின் வரம்பிற்குள் இருப்பதை உறுதிப்படுத்தவும் (பொதுவாக < 25MB)
- வழங்குநர் கார்டில் வழங்குநரின் API விசை செல்லுபடியாகிறதா என்பதைச் சரிபார்க்கவும்

## மொழிபெயர்ப்பி பிழைத்திருத்தம்

வடிவமைப்பு மொழிபெயர்ப்புச் சிக்கல்களைப் பிழைத்திருத்த **டாஷ்போர்டு → மொழிபெயர்ப்பி** என்பதைப் பயன்படுத்தவும்:

| பயன்முறை                  | எப்போது பயன்படுத்த வேண்டும்                                                                                                         |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **சோதனைக் களம்**          | உள்ளீடு/வெளியீட்டு வடிவங்களை அருகருகே ஒப்பிடவும் — அது எவ்வாறு மொழிபெயர்க்கப்படுகிறது என்பதைக் காண தோல்வியடைந்த கோரிக்கையை ஒட்டவும் |
| **அரட்டைச் சோதனையாளர்**   | நேரடி செய்திகளை அனுப்பி, தலைப்புகள் உட்பட முழுமையான கோரிக்கை/பதில் பேலோடை ஆய்வு செய்யவும்                                           |
| **சோதனைத் தளம்**          | எந்த மொழிபெயர்ப்புகள் செயலிழந்துள்ளன என்பதைக் கண்டறிய வடிவமைப்புச் சேர்க்கைகள் முழுவதும் தொகுதிச் சோதனைகளை இயக்கவும்                |
| **நேரடிக் கண்காணிப்பான்** | இடையிடையே ஏற்படும் மொழிபெயர்ப்புச் சிக்கல்களைக் கண்டறிய நிகழ்நேரக் கோரிக்கை ஓட்டத்தைக் கண்காணிக்கவும்                               |

### பொதுவான வடிவமைப்புச் சிக்கல்கள்

- **சிந்தனைக் குறிச்சொற்கள் தோன்றவில்லை** — இலக்கு வழங்குநர் சிந்தனை அம்சத்தையும் சிந்தனை பட்ஜெட் அமைப்பையும் ஆதரிக்கிறாரா என்பதைச் சரிபார்க்கவும்
- **கருவி அழைப்புகள் விடுபடுகின்றன** — சில வடிவமைப்பு மொழிபெயர்ப்புகள் ஆதரிக்கப்படாத புலங்களை அகற்றக்கூடும்; சோதனைக் களப் பயன்முறையில் சரிபார்க்கவும்
- **கணினித் தூண்டுரை காணவில்லை** — Claude மற்றும் Gemini ஆகியவை கணினித் தூண்டுரைகளை வெவ்வேறு விதமாகக் கையாளுகின்றன; மொழிபெயர்ப்பு வெளியீட்டைச் சரிபார்க்கவும்
- **SDK பொருளுக்குப் பதிலாக மூலச் சரத்தை வழங்குகிறது** — v1.x-இல் தீர்க்கப்பட்டது; OpenAI SDK Pydantic சரிபார்ப்புத் தோல்விகளை ஏற்படுத்தும் தரநிலையற்ற புலங்களை (`x_groq`, `usage_breakdown` போன்றவை) பதில் தூய்மைப்படுத்தி அகற்றுகிறது. v3.x+ பதிப்பிலும் இதை நீங்கள் இன்னும் கண்டால், தயவுசெய்து ஒரு சிக்கலைப் பதிவு செய்யவும்.
- **GLM/ERNIE `system` பாத்திரத்தை நிராகரிக்கிறது** — v1.x-இல் தீர்க்கப்பட்டது; பொருந்தாத மாடல்களுக்கு, பாத்திர இயல்பாக்கி கணினிச் செய்திகளைத் தானாகவே பயனர் செய்திகளுடன் ஒன்றிணைக்கிறது. v3.x+ பதிப்பிலும் இதை நீங்கள் இன்னும் கண்டால், தயவுசெய்து ஒரு சிக்கலைப் பதிவு செய்யவும்.
- **`developer` பாத்திரம் அடையாளம் காணப்படவில்லை** — v1.x-இல் தீர்க்கப்பட்டது; OpenAI அல்லாத வழங்குநர்களுக்குத் தானாகவே `system` ஆக மாற்றப்படுகிறது. v3.x+ பதிப்பிலும் இதை நீங்கள் இன்னும் கண்டால், தயவுசெய்து ஒரு சிக்கலைப் பதிவு செய்யவும்.
- **Gemini உடன் `json_schema` செயல்படவில்லை** — v1.x-இல் தீர்க்கப்பட்டது; `response_format` இப்போது Gemini-இன் `responseMimeType` + `responseSchema` ஆக மாற்றப்படுகிறது. v3.x+ பதிப்பிலும் இதை நீங்கள் இன்னும் கண்டால், தயவுசெய்து ஒரு சிக்கலைப் பதிவு செய்யவும்.

## மீள்திறன் அமைப்புகள்

### தானியங்கு விகித வரம்பு தூண்டப்படவில்லை

- தானியங்கு விகித வரம்பு API விசை வழங்குநர்களுக்கு மட்டுமே பொருந்தும் (OAuth/சந்தாவிற்கு அல்ல)
- **அமைப்புகள் → மீள்திறன் → வழங்குநர் சுயவிவரங்கள்** என்பதில் தானியங்கு விகித வரம்பு இயக்கப்பட்டுள்ளதா என்பதைச் சரிபார்க்கவும்
- வழங்குநர் `429` நிலைக் குறியீடுகள் அல்லது `Retry-After` தலைப்புகளை வழங்குகிறாரா என்பதைச் சரிபார்க்கவும்

### அடுக்குக்குறி பின்னடைவைச் சீரமைத்தல்

வழங்குநர் சுயவிவரங்கள் இந்த அமைப்புகளை ஆதரிக்கின்றன:

- **அடிப்படைத் தாமதம்** — முதல் தோல்விக்குப் பிறகான ஆரம்பக் காத்திருப்பு நேரம் (இயல்புநிலை: 1s)
- **அதிகபட்சத் தாமதம்** — அதிகபட்சக் காத்திருப்பு நேர வரம்பு (இயல்புநிலை: 30s)
- **பெருக்கி** — தொடர்ச்சியான ஒவ்வொரு தோல்விக்கும் தாமதத்தை எவ்வளவு அதிகரிக்க வேண்டும் (இயல்புநிலை: 2x)

### ஒரே நேரக் கோரிக்கை வெள்ளத் தடுப்பு

விகித வரம்பிடப்பட்ட வழங்குநருக்குப் பல ஒரேநேரக் கோரிக்கைகள் வரும்போது, கோரிக்கைகளைத் தொடர்வரிசைப்படுத்தவும் தொடர் தோல்விகளைத் தடுக்கவும் OmniRoute mutex + தானியங்கு விகித வரம்பைப் பயன்படுத்துகிறது. API விசை வழங்குநர்களுக்கு இது தானாகவே நிகழும்.

### அரட்டைக் கோரிக்கைகள் 503 / chat_admission_busy உடன் தோல்வியடைகின்றன

**அறிகுறிகள்:**

- அரட்டை நிறைவு endpoint, பிழைக் குறியீடாக
  `chat_admission_busy` கொண்ட, மீண்டும் முயற்சிக்கக்கூடிய `503` பதிலை வழங்குகிறது.
- பதிலில் `Retry-After` இடம்பெறும். #12135 முதல், அதன் மதிப்பு கவனிக்கப்பட்ட
  பயன்பாட்டு அளவிலிருந்து பெறப்படுகிறது — கோரிக்கை ஏற்கெனவே காத்திருந்த `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  காலச்சாளரம் அல்லது தற்போதைய கனரக குத்தகைகள் வைத்திருக்கப்பட்டுள்ள நேரம் ஆகியவற்றில்
  பெரிய மதிப்பு, முழு வினாடிகளுக்கு மேல்நோக்கிச் சுருட்டப்பட்டு 60 என வரம்பிடப்படும்.
  செயலற்ற gate-இல், வரலாற்றுக் குறைந்தபட்சங்கள் தக்கவைக்கப்படுகின்றன: byte அடிப்படையிலான
  பாதையில் 2 வினாடிகள், கட்டமைப்பு அடிப்படையிலான பாதையில் 1 வினாடி (இதில்
  `reason: "structure_limit"` என்பதும் இடம்பெறும்).
- மற்றொரு கனரக அரட்டை அல்லது நீண்ட நேரம் இயங்கும் streaming பதில் இன்னும்
  செயல்பாட்டில் இருக்கும்போது இது நிகழலாம்.

byte அடிப்படையிலான பதில் body:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

கட்டமைப்பு அடிப்படையிலான பதில் அதே type மற்றும் code-ஐப் பயன்படுத்துகிறது; அதன் message
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
என்பதாகவும், `reason: "structure_limit"` என்பதையும் கொண்டிருக்கும்.
இயல்புநிலை வரம்புகளில், ஒரு கோரிக்கையில் குறைந்தது `200` messages, குறைந்தது `64` tools,
அல்லது குறைந்தது `32,000` மதிப்பிடப்பட்ட tokens இருந்தால், அல்லது வரம்புக்குட்பட்ட கட்டமைப்பு
மதிப்பீடு, பார்வையிடப்பட்ட `10,000` nodes அல்லது ஆழம் `12` என்ற அதன் வரம்புகளை முழுமையாகப்
பயன்படுத்திவிட்டால், அந்தக் கோரிக்கை கட்டமைப்பு ரீதியாகக் கனரகமானதாகும்.

**காரணம்:** இது OmniRoute-க்குள் வேண்டுமென்றே செய்யப்படும் சுமைக் குறைப்பு; upstream வழங்குநரின்
தோல்வி அல்ல. ஒரு பெரிய request body-ஐத் தக்கவைத்துப் parse செய்வதற்கு முன், வரம்பிடப்பட்ட
கனரகத் திறனை ஒதுக்க ஒவ்வொரு process-உம் process-local guard-ஐப் பயன்படுத்துகிறது. ஒரு SSE
பதிலின் ஆயுட்காலம் முழுவதும் கனரகக் குத்தகை வைத்திருக்கப்படும்.

**#503-fanout:** இந்தத் திருத்தத்திற்கு முன்பு, host memory-ஐப் பொருட்படுத்தாமல் guard ஒரேநேரச்
செயல்பாட்டை நிலையான கோரிக்கை COUNT-க்கு (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, இயல்புநிலை `1`)
வரம்பிட்டது. இதனால் coding-agent fan-out (பல subagents/CLIs, வழக்கமாக 256 KB-ஐ விடப் பெரிய
bodies) செயல்திறன்மிக்க ஒரேநேரச் செயல்பாட்டை ~1 ஆகக் குறைத்து, முற்றிலும் இயல்பான சுமையில்கூட
503 பதில்களை ஏற்படுத்தியது. இப்போது guard தன்னைத்தானே சீரமைக்கிறது: process-இன் உண்மையான
memory உச்சவரம்பிலிருந்து அளவிடப்படும், தானாகப் பெறப்பட்ட ingest BYTE budget
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) மூலம் அது கட்டுப்படுத்தப்படுகிறது; மேலும், நேரடி
வள-அழுத்தக் குறியீட்டையும் அது கருத்தில் கொள்கிறது — எனவே ஒன்றுக்கு மேற்பட்ட கனரகக் கோரிக்கைகள்
ஒரே நேரத்தில் வந்ததால் மட்டும் அல்லாமல், host உண்மையிலேயே memory அழுத்தத்தில் இருக்கும்போது
மட்டுமே அது சுமையைக் குறைக்கிறது. பழைய count cap (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
இன்னும் மதிக்கப்படுகிறது, ஆனால் அதை நீங்கள் வெளிப்படையாக அமைத்தால் மட்டுமே.

திறன் நிரம்பியிருக்கும்போது, மீண்டும் முயற்சிக்கக்கூடிய `503` பதிலை வழங்குவதற்கு முன்,
ஒரு இடம் காலியாகும் வரை கனரகக் கோரிக்கை முதலில் `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
(இயல்புநிலை `RATE_LIMIT_MAX_WAIT_MS`; `0` காத்திருப்பை முடக்கும்) நேரம் வரை காத்திருக்கும்.
ஒரேநேரத்தில் கனரகத் துணைக் கோரிக்கைகளை fan out செய்யும் agent-பாணி clients
(OpenCode, Claude Code, Cursor), உடனடி நிராகரிப்புகளிலேயே தங்களின் முழு retry budget-ஐச்
செலவழித்து பணியின் நடுவில் செயலிழப்பதற்குப் பதிலாக, அந்தத் திடீர் கோரிக்கைத் தொகுப்பைத்
தொடர்வரிசைப்படுத்துவதற்காகவே இந்த வரம்புக்குட்பட்ட காத்திருப்பு உள்ளது.
தற்போதைய கனரகக் குத்தகைப் பயன்பாடு, தீர்மானிக்கப்பட்ட byte budget, மற்றும் நேரடி அழுத்தத்தின்
தீவிரம் ஆகியவை `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`,
`maxInflightBytes`, `budgetSource`, `pressureSeverity`, `countCapEnabled`) என்பதில்
காட்டப்படுகின்றன — எந்த env var-ஐயும் மாற்றுவதற்கு முன் இவற்றைச் சரிபார்க்கவும்.
அமைப்புகள் → மீள்திறன் → கோரிக்கை வரிசை → ஒரேநேரக் கோரிக்கைகள் என்பது இதைக் கட்டுப்படுத்தாது;
அந்த அமைப்பு தனியான வழங்குநர் கோரிக்கை-வரிசைச் செயல்முறையை நிர்வகிக்கிறது.

**தீர்வு:**

1. முதலில் மீண்டும் முயற்சிக்கவும். Clients, கோரிக்கையை உடனடியாக மீண்டும் அனுப்புவதற்குப் பதிலாக
   `Retry-After`-ஐ மதித்து backoff-ஐப் பயன்படுத்த வேண்டும்.
2. எதையும் சீரமைப்பதற்கு முன் `/api/monitoring/health` → `chatAdmission` என்பதைச் சரிபார்க்கவும்.
   `countCapEnabled: false` மற்றும் போதுமான `maxInflightBytes` இருந்தால், தானாகப் பெறப்பட்ட
   budget ஏற்கெனவே தனது பணியைச் செய்கிறது என்று பொருள்; `high`/`critical` என்ற
   `pressureSeverity`, host-இல் உண்மையிலேயே memory குறைவாக இருப்பதைக் குறிக்கிறது —
   இதை admission env var மூலம் சரிசெய்ய முடியாது; கூடுதல் RAM அல்லது சிறிய workload தேவை.
3. `/api/monitoring/health`, தானாகப் பெறப்பட்ட budget உங்கள் host-க்கு உண்மையிலேயே மிகவும்
   சிறியதாக இருப்பதைக் காட்டினால் மட்டுமே (இது அரிது — container முதல் bare-metal வரை அது
   ஏற்கெனவே அளவிடப்படுகிறது), பழைய request-count cap-க்குத் திரும்புவதற்குப் பதிலாக
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` மூலம் அதை நேரடியாக override செய்யவும்.

அதிகாரப்பூர்வ admission அமைப்புகளுக்கு [சுற்றுச்சூழல் மாறி மேற்கோளை](../reference/ENVIRONMENT.md#4-security--authentication)
பார்க்கவும்.

## விருப்பத்திற்குரிய RAG / LLM தோல்வி வகைப்பாடு (16 சிக்கல்கள்)

சில OmniRoute பயனர்கள், RAG அல்லது ஏஜென்ட் ஸ்டாக்குகளுக்கு முன்னால் கேட்வேயை அமைக்கின்றனர். அத்தகைய அமைப்புகளில் ஒரு விசித்திரமான போக்கைக் காண்பது பொதுவானது: OmniRoute ஆரோக்கியமாகத் தோன்றும் (வழங்குநர்கள் இயங்குகின்றனர், ரூட்டிங் சுயவிவரங்கள் சரியாக உள்ளன, விகித வரம்பு எச்சரிக்கைகள் இல்லை), ஆனால் இறுதிப் பதில் இன்னும் தவறாக இருக்கும்.

நடைமுறையில், இந்தச் சம்பவங்கள் வழக்கமாக கேட்வேயிலிருந்து அல்லாமல், அதன் கீழ்நிலை RAG பைப்லைனிலிருந்தே உருவாகின்றன.

அந்தத் தோல்விகளை விவரிக்க ஒரு பொதுவான சொற்களஞ்சியத்தைப் பயன்படுத்த விரும்பினால், WFGY ProblemMap-ஐப் பயன்படுத்தலாம். இது மீண்டும் மீண்டும் ஏற்படும் பதினாறு RAG / LLM தோல்வி வடிவங்களை வரையறுக்கும், MIT உரிமம் பெற்ற ஒரு வெளிப்புற உரை வளமாகும். உயர்நிலையில், இது பின்வருவனவற்றை உள்ளடக்குகிறது:

- மீட்டெடுப்பு விலகல் மற்றும் உடைந்த சூழல் எல்லைகள்
- காலியான அல்லது காலாவதியான இன்டெக்ஸ்கள் மற்றும் வெக்டர் ஸ்டோர்கள்
- எம்பெட்டிங் மற்றும் சொற்பொருள் இடையேயான பொருத்தமின்மை
- ப்ராம்ப்ட் ஒருங்கிணைப்பு மற்றும் சூழல் சாளரச் சிக்கல்கள்
- தர்க்கச் சரிவு மற்றும் அளவுக்கு மீறிய நம்பிக்கையுடன் வழங்கப்படும் பதில்கள்
- நீண்ட சங்கிலி மற்றும் ஏஜென்ட் ஒருங்கிணைப்புத் தோல்விகள்
- பல ஏஜென்ட் நினைவகம் மற்றும் பங்குப் பிறழ்வு
- டிப்ளாய்மென்ட் மற்றும் பூட்ஸ்ட்ராப் வரிசைப்படுத்தல் சிக்கல்கள்

இதன் கருத்து எளிமையானது:

1. தவறான பதிலை ஆய்வு செய்யும்போது, பின்வருவனவற்றைப் பதிவு செய்யவும்:
   - பயனர் பணி மற்றும் கோரிக்கை
   - OmniRoute-இல் பயன்படுத்தப்பட்ட ரூட் அல்லது வழங்குநர் சேர்க்கை
   - கீழ்நிலையில் பயன்படுத்தப்பட்ட எந்தவொரு RAG சூழலும் (மீட்டெடுக்கப்பட்ட ஆவணங்கள், கருவி அழைப்புகள் போன்றவை)
2. சம்பவத்தை ஒன்று அல்லது இரண்டு WFGY ProblemMap எண்களுடன் (`No.1` … `No.16`) பொருத்தவும்.
3. OmniRoute பதிவுகளுக்கு அருகில், உங்கள் சொந்த டாஷ்போர்டு, ரன்புக் அல்லது சம்பவக் கண்காணிப்பியில் அந்த எண்ணைச் சேமிக்கவும்.
4. உங்கள் RAG ஸ்டாக், ரிட்ரீவர் அல்லது ரூட்டிங் உத்தியை மாற்ற வேண்டுமா என்பதைத் தீர்மானிக்க, அதற்குரிய WFGY பக்கத்தைப் பயன்படுத்தவும்.

முழு உரையும் உறுதியான வழிமுறைகளும் இங்கே உள்ளன (MIT உரிமம், உரை மட்டும்):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute-க்குப் பின்னால் RAG அல்லது ஏஜென்ட் பைப்லைன்களை நீங்கள் இயக்கவில்லை என்றால், இந்தப் பகுதியைப் புறக்கணிக்கலாம்.

## v3.8.0 அறியப்பட்ட சிக்கல்கள்

v3.8.0 வெளியீட்டுக்கே உரிய சிக்கல்களும் அவற்றுக்கான தற்போதைய தற்காலிகத் தீர்வுகளும். பின்னர் வரும் பேட்சில் ஒரு தீர்வு சேர்க்கப்பட்டால், இந்தப் பதிவு புதுப்பிக்கப்படும் அல்லது அகற்றப்படும்.

### Devin CLI அங்கீகாரத் தோல்விகள்

**அறிகுறிகள்:**

- Devin ஆதரவுள்ள கருவிகளை அழைக்கும்போது "Devin CLI கிடைக்கவில்லை" அல்லது "அங்கீகாரம் தோல்வியடைந்தது"
- CLI இயக்கநேரச் சரிபார்ப்பு `installed=false` எனத் தெரிவிக்கிறது

**காரணங்கள்:**

- `CLI_DEVIN_BIN` இல்லாத ஒரு பாதையைக் குறிக்கிறது
- ஹோஸ்ட்டில் Devin CLI நிறுவப்படவில்லை

**தீர்வு:**

1. உங்கள் இயங்குதளத்திற்கான Devin CLI-ஐ நிறுவவும்
2. `.env`-இல் `CLI_DEVIN_BIN=/usr/local/bin/devin` (அல்லது உண்மையான பாதை) என்பதை அமைக்கவும்
3. OmniRoute-ஐ மறுதொடக்கம் செய்து, **டாஷ்போர்டு → CLI கருவிகள்** என்பதிலிருந்து மீண்டும் சோதிக்கவும்

### மாடல் கூல்டவுன் முடங்கியுள்ளது (கைமுறை மீட்டமைப்பு)

**அறிகுறிகள்:**

- காலாவதி நேரம் கடந்த பின்னரும் ஒரு மாடல் கூல்டவுனில் இருப்பதாகப் பட்டியலிடப்படுகிறது
- நேரமுத்திரை கடந்த காலத்தில் இருந்தாலும், சேர்க்கை ரூட்டிங்கில் கோரிக்கைகள் அந்த மாடலைத் தொடர்ந்து தவிர்க்கின்றன

**கைமுறை மீட்டமைப்பு:**

- **டாஷ்போர்டு:** **அமைப்புகள் → மாடல் கூல்டவுன்கள்** → பாதிக்கப்பட்ட கார்டில் **மீண்டும் இயக்கு** என்பதைக் கிளிக் செய்யவும்
- **API:** மேலாண்மை அங்கீகார ஹெடர்களுடன் `DELETE /api/resilience/model-cooldowns`

### Command Code வழங்குநர் இணைப்பு 403 பிழையுடன் தோல்வியடைகிறது

**அறிகுறிகள்:**

- Command Code வழங்குநர் இணைப்பைச் சோதிக்கும்போது 403
- புதிதாகச் சேர்த்த பிறகு வழங்குநர் கார்டு "அங்கீகரிக்கப்படவில்லை" எனக் காட்டுகிறது

**காரணம்:** OAuth ஓட்டம் நிறைவடையவில்லை (கால்பேக் பெறப்படவில்லை அல்லது டோக்கன் நிலையாகச் சேமிக்கப்படவில்லை).

**தீர்வு:**

- OAuth ஓட்டத்தை மீண்டும் தூண்ட CLI-இலிருந்து `omniroute providers`-ஐ இயக்கவும், அல்லது
- **டாஷ்போர்டு → வழங்குநர்கள் → Command Code → மீண்டும் இணை** என்பதிலிருந்து OAuth-ஐ மீண்டும் இயக்கவும்

### ModelScope அளவுக்கு மீறிய 429 கூல்டவுன்களை வழங்குகிறது

**அறிகுறிகள்:**

- சிறிய அளவிலான தொடர்ச்சியான கோரிக்கைகளுக்குப் பிறகு ModelScope-இல் மிகக் குறுகிய அல்லது உடனடி கூல்டவுன்கள்
- எதிர்பார்த்ததைவிட முன்கூட்டியே சேர்க்கை ரூட்டிங் ModelScope-ஐத் தவிர்க்கிறது

**காரணம்:** ModelScope வழங்குநருக்கே உரிய `Retry-After` ஹெடர்களை வெளியிடுகிறது. அந்த ஹெடர்களுக்கான பிரத்யேகக் கையாளுதலுடன் v3.8.0 வழங்கப்படுகிறது; எனவே, பழைய பதிப்புகள் அவற்றைப் பொதுவான விகித வரம்புக் குறிப்புகளாகத் தவறாகப் புரிந்துகொள்கின்றன.

**தீர்வு:**

- நீங்கள் v3.8.0 அல்லது அதற்குப் பிந்தைய பதிப்பைப் பயன்படுத்துவதை உறுதிசெய்யவும்
- **அமைப்புகள் → மீட்சித்திறன்** என்பதன் கீழ் `useUpstream429BreakerHints` நிலைமாற்றி இயக்கப்பட்டுள்ளதைச் சரிபார்க்கவும்

### தயாரிப்புச் சூழலில் OMNIROUTE_WS_BRIDGE_SECRET இல்லை

**அறிகுறிகள்:**

- தொலைநிலை தயாரிப்பு ஹோஸ்ட்டில் இயக்கும்போது, ஒவ்வொரு Codex/Responses WebSocket பிரிட்ஜ் கோரிக்கையிலும் 401
- இணைத்த உடனேயே WebSocket பிரிட்ஜ் ஹேண்ட்ஷேக் மூடப்படுகிறது

**காரணம்:** தயாரிப்புச் சூழலில் `OMNIROUTE_WS_BRIDGE_SECRET` சூழல் மாறி இல்லை.

**தீர்வு:**

1. சீரற்ற ரகசியத்தை உருவாக்கவும்: `openssl rand -hex 32`
2. தயாரிப்பு சர்வர் சூழலில் `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` என்பதை அமைக்கவும் (மேலும் பிரிட்ஜுடன் தொடர்புகொள்ளும் எந்த கிளையண்டிலும் அமைக்கவும்)
3. OmniRoute-ஐ மறுதொடக்கம் செய்யவும்

### Responses API: பின்னணி பயன்முறை ஒத்திசைவு முறைக்குத் தரமிறக்கப்பட்டது

**அறிகுறிகள்:**

- பதிவுசெய்யப்பட்ட எச்சரிக்கை: `background mode degraded to synchronous`
- `background: true` கோரிக்கை, பின்னணி வேலைக்கான ஹேண்டிலுக்குப் பதிலாக வழக்கமான ஒத்திசைவுப் பதிலை வழங்குகிறது

**காரணம்:** v3.8.0, எச்சரிக்கையை வெளியிட்டபடியே Responses API-இல் `background: true` என்பதை வேண்டுமென்றே ஒத்திசைவு செயல்பாட்டுக்குத் தரமிறக்குகிறது. முழுமையான அசின்க்ரோனஸ் பின்னணி செயல்பாடு எதிர்காலத்தில் வழங்கப்படவுள்ளது.

**தீர்வு:**

- `background` இல்லாமல் அழைக்குமாறு கிளையண்டைச் சரிசெய்யவும், அல்லது
- முழுமையான அசின்க்ரோனஸ் பின்னணி பயன்முறையைக் கொண்ட பின்னர் வரும் வெளியீட்டிற்காகக் காத்திருக்கவும் (மாற்றப் பதிவைக் கண்காணிக்கவும்)

## மெதுவான தொடக்கம் / தயார்நிலை நேர முடிவு

CLI ஆனது `⚠ Server did not respond within 60s` எனக் காட்டினாலும், சேவையகம் உண்மையில் இயங்கிக்கொண்டிருந்தால், உங்கள் சூழலுக்கான தயார்நிலைச் சோதனையின் நேர வரம்பு மிகவும் குறைவாக உள்ளது.

இது பொதுவாக Windows-இல் (வைரஸ் தடுப்பு, கோப்பு முறைமை கண்காணிப்பான்கள்) அல்லது அதிக தொடக்கப் பணிச்சுமைகளைக் கொண்ட கண்டெய்னர்களில் நிகழ்கிறது.

**தீர்வு — நேர வரம்பை அதிகரிக்கவும்:**

```bash
# சூழல் மாறி வழியாக (தொடக்கங்களுக்கு இடையிலும் நீடிக்கும்):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 நிமிடங்கள்
omniroute serve

# CLI கொடி வழியாக (ஒருமுறை மட்டும்):
omniroute serve --ready-timeout 180000
```

இயல்புநிலை 60 000 ms (60 s) ஆகும். இந்த எச்சரிக்கை தகவலுக்காக மட்டுமே; சேவையகம் பின்னணியில் தொடர்ந்து தொடங்கும், மேலும் தொடக்கச் செயல்முறை முடிந்ததும் அதை அணுக முடியும்.

`OMNIROUTE_READY_TIMEOUT_MS` பற்றிய முழு விவரங்களுக்கு [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md)-ஐப் பார்க்கவும்.
