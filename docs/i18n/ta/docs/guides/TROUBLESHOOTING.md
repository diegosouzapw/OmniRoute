## விரைவுக் குறிப்பு

**OmniRoute-க்குப் புதியவரா?** இங்கே தொடங்குங்கள் — இவை 90% சிக்கல்களைத் தீர்க்கும்:

| நான் இதைப் பார்க்கிறேன்              | இதன் பொருள்                                                    | என்ன செய்ய வேண்டும்                                                                                                                       |
| ------------------------------------ | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| "இணைக்க முடியவில்லை"                 | OmniRoute இயங்கவில்லை                                          | `omniroute` அல்லது `docker restart omniroute`-ஐ இயக்கவும்                                                                                 |
| "தவறான API விசை"                     | உங்கள் விசை தவறானது அல்லது காலாவதியானது                        | வழங்குநரின் இணையதளத்திலிருந்து விசையை மீண்டும் நகலெடுக்கவும்                                                                              |
| "விகித வரம்பு மீறப்பட்டது"           | நீங்கள் மிக அதிகமான கோரிக்கைகளை அனுப்புகிறீர்கள்               | 1 நிமிடம் காத்திருக்கவும் அல்லது தானியங்கி மாற்றுத் தேர்வுக்கு `model: "auto"`-ஐப் பயன்படுத்தவும்                                         |
| "ஒதுக்கீடு மீறப்பட்டது"              | உங்கள் இலவச/கட்டண ஒதுக்கீடு முழுவதையும் பயன்படுத்திவிட்டீர்கள் | மேலும் வழங்குநர்களை இணைக்கவும் அல்லது இலவச வழங்குநர்களைப் (Kiro, Pollinations) பயன்படுத்தவும்                                             |
| "மெதுவான பதில்கள்"                   | வழங்குநர் பரபரப்பாக உள்ளார் அல்லது தொலைவில் உள்ளார்            | `model: "auto/fast"`-ஐப் பயன்படுத்தவும் அல்லது வேகமான வழங்குநரை (Groq, Cerebras) இணைக்கவும்                                               |
| "தவறான வழங்குநர் பயன்படுத்தப்பட்டது" | `auto` வேறொரு வழங்குநரைத் தேர்ந்தெடுத்தது                      | அது இயல்பானதே! `auto` சிறந்ததைத் தேர்ந்தெடுக்கும். `model: "openai/gpt-4o"` மூலம் குறிப்பிட்ட வழங்குநரைப் பயன்படுத்தக் கட்டாயப்படுத்தவும் |
| "502 தவறான நுழைவாயில்"               | வழங்குநர் செயலிழந்துள்ளார்                                     | காத்திருந்து மீண்டும் முயலவும் அல்லது வழங்குநர்களை மாற்ற `model: "auto"`-ஐப் பயன்படுத்தவும்                                               |
| "401 அங்கீகரிக்கப்படவில்லை"          | உங்கள் சான்றுகள் தவறாக உள்ளன                                   | உங்கள் API விசையைச் சரிபார்க்கவும் அல்லது OAuth மூலம் மீண்டும் அங்கீகரிக்கவும்                                                            |
| "omniroute அடையாளம் காணப்படவில்லை"   | Windows PATH-இல் உலகளாவிய node தொகுதிகள் இல்லை                 | உங்கள் npm உலகளாவிய முன்னொட்டை Windows PATH-இல் சேர்க்கவும். அதை `npm config get prefix` மூலம் கண்டறியவும்.                               |
| "429 மிக அதிகமான கோரிக்கைகள்"        | விகித வரம்பு விதிக்கப்பட்டுள்ளது                               | 1 நிமிடம் காத்திருக்கவும் அல்லது மேலும் வழங்குநர்களை இணைக்கவும்                                                                           |

**இன்னும் சிக்கியுள்ளீர்களா?** கீழே உள்ள [விரிவான சிக்கல் தீர்வு](#detailed-troubleshooting)-ஐப் பார்க்கவும் அல்லது [Discord](https://discord.gg/U47eFqAXCn)-இல் கேட்கவும்.

### இலவச வழங்குநர்களில் விகித வரம்பிடல் (429 / 400 / 401)

**அறிகுறி**: இலவச/அங்கீகாரம் தேவையில்லாத வழங்குநர்களுடன் (opencode, auggie போன்றவை) `model: "auto"`-ஐப் பயன்படுத்தும்போது, பதில்களுக்குப் பதிலாக இடையிடையே `HTTP 429`, `400` அல்லது `401` கிடைக்கும். சில கணங்கள் கழித்து அதே தூண்டுதலை மீண்டும் முயலும்போது கோரிக்கைகள் வெற்றி பெறுகின்றன; ஆனால் தானியக்கம் (cron பணிகள், முகவர்கள், ஸ்கிரிப்ட்கள்) முதல் தோல்வியிலேயே செயலிழக்கிறது.

**மூலக் காரணம்**: மூன்று தனித்தனி தோல்வி முறைகள் ஒன்றின் மேல் ஒன்று சேர்கின்றன:

1. **வழங்குநர் விகித வரம்பு (`429`)**: இலவச அடுக்குகள் ஒவ்வொரு காலச் சாளரத்திற்குமான ஒதுக்கீட்டைச் செயல்படுத்தலாம். ஒரே நேரத்தில் அனுப்பப்படும் பல இணை அழைப்புகள் அதைத் தீர்த்துவிடுகின்றன; எனவே சாளரம் மீட்டமைக்கப்படும் வரை அடுத்த கோரிக்கை நிராகரிக்கப்படுகிறது.
2. **நேரடி அனுப்பலில் செயலிழந்த மாதிரி (`400`/`401`)**: `auto/*` தொகுப்புகளில், பட்டியலில் பதிவுசெய்யப்பட்டிருந்தாலும் செயலிலுள்ள சான்றுகள் இல்லாத `opencode`-இன் நேரடி அனுப்பல் மாதிரிகள் இடம்பெறலாம் (எ.கா. `oc/north-mini-code-free` → `401`). தானியங்கி வழிப்படுத்தி ஒன்றை முயன்று தோல்வியடைகிறது; மாற்றுத் தேர்வு செயல்படுவதற்கு முன்பே பிழை பரவுகிறது.
3. **ஒரேநேரச் செயல்பாட்டால் ஏற்படும் பெருக்கம் (சுமையின் கீழ் `429`)**: பல முகவர்/cron அமர்வுகள் ஒரே நேரத்தில் `auto`-ஐ அணுகும்போது, மொத்தக் கோரிக்கை விகிதம் இலவச வழங்குநர்கள் பொறுத்துக்கொள்ளக்கூடிய அளவை மீறுகிறது; இதனால் முறையான அழைப்புகள்கூட முறைகேடானவையாகக் குறிக்கப்படுகின்றன.

**சரிபார்க்கப்பட்ட தீர்வு (சமூகத்தால் தெரிவிக்கப்பட்டது, 2026-08-10)**: சுழற்சி, ஒரேநேரச் செயல்பாடு மற்றும் மாற்றுத் தேர்வு ஆகியவை இலவச அடுக்கின் நிலையற்ற தன்மையைச் சமாளிக்குமாறு, தோல்வியடைந்து நிற்காமல் இருக்க மூன்று சூழல் மாறிகளைச் சரிசெய்யவும்:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ஏற்பட்டால் மற்றொரு மாதிரி/வழங்குநருக்குத் தாவும் (செயலிழந்த நேரடி அனுப்பல் மாதிரிகளைத் தவிர்க்கும்)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # அதிகச் சுமையுள்ள கோரிக்கைகளுக்கான வெளிப்படையான அனுமதி உச்சவரம்பு (இயல்பாக அமைக்கப்படாது: கோரிக்கை எண்ணிக்கை வரம்பில்லை, கீழேயுள்ள குறிப்பைப் பார்க்கவும்)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # மெதுவான மேல்நிலைச் சேவைகளுக்காக வரம்பிடப்பட்ட காத்திருப்பை RATE_LIMIT_MAX_WAIT_MS இயல்புநிலையைத் தாண்டி உயர்த்தும்
```

இவற்றை OmniRoute செயல்முறைச் சூழலில் (daemon-இல், எ.கா. LaunchAgent plist அல்லது `systemctl edit` வழியாக) அமைத்து, பின்னர் OmniRoute-ஐ மறுதொடக்கம் செய்யவும். சுழற்சிக் கொடியே மிக அதிகப் பயன் தரும் ஒரே கட்டுப்பாடு: இது ஒரு கடுமையான தோல்வியை, தொகுப்பிலுள்ள ஆரோக்கியமான வழங்குநருக்கு எதிரான வெளிப்படையான மறுமுயற்சியாக மாற்றுகிறது.

**குறிப்பு**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ஒரே நேரத்தில் இயங்கும் அதிகச் சுமையுள்ள — நீண்ட சூழல் கொண்ட — கோரிக்கைகளின் எண்ணிக்கைக்கு உச்சவரம்பு விதிக்கிறது; இந்த வரம்பு ஓர் அனுமதி வாயில், வழங்குநர் விகித வரம்பி அல்ல. **#503-fanout புதுப்பிப்பு:** இந்த மாறி இனி இயல்பாக அமைக்கப்படாது (மேலே காட்டியுள்ளதுபோல் வெளிப்படையாக உள்ளமைக்கப்பட்டால் மட்டுமே இப்போது செயல்படும்) — அதற்குப் பதிலாக, புரவலனின் உண்மையான நினைவக உச்சவரம்பிலிருந்து தானாக அளவுமாற்றப்படும், தானாகக் கணிக்கப்பட்ட பைட் வரவுசெலவுத் திட்டம் (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) மூலம் அதிகச் சுமையுள்ள கோரிக்கைகளுக்கான அனுமதி கட்டுப்படுத்தப்படுகிறது. ஆகவே, இந்த மாறியை அமைக்காமலேயே புதிய நிறுவலில் மிகக் குறைவான `503 chat_admission_busy` நிராகரிப்புகளே ஏற்பட வேண்டும்; இங்கே இதை வெளிப்படையாக அமைப்பது ஆவணப்படுத்தப்பட்டுள்ளபடியே தொடர்ந்து செயல்படும். வெளிப்படையான பைட் வரவுசெலவுத் திட்ட மேலெழுதல்கள் 8 MiB–2 GiB வரம்புக்குள் கட்டுப்படுத்தப்படும். `413 body_exceeds_budget` தற்காலிகமானது அல்ல: அந்த பைட் வரவுசெலவுத் திட்டத்தை அதிகரிக்கவும், `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`-ஐக் குறைக்கவும் அல்லது செயல்முறையின் நினைவக உச்சவரம்பை அதிகரிக்கவும். `inflight_bytes_budget` காரணமாகச் சுமை குறைக்கப்படுவது தற்காலிக வளப் போட்டியாகும்; அதை மீண்டும் முயலலாம். ஒவ்வொரு வழங்குநருக்குமான விகித வரம்பிடல் (`open-sse/services/rateLimitManager.ts`) தனியாக `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` மற்றும் `RATE_LIMIT_AUTO_ENABLE` ஆகியவற்றால் நிர்வகிக்கப்படுகிறது — `.env.example`-ஐப் பார்க்கவும்.

**இது செயல்பட்டதைச் சரிபார்ப்பது எப்படி**: உங்கள் agent/cron-ஐ அடுத்தடுத்து விரைவாக இருமுறை இயக்கி, இரண்டுமே வெற்றிகரமாக முடிவதை உறுதிப்படுத்தவும். திருத்தத்திற்கு முன்பு, இரண்டாவது இயக்கம் பொதுவாக `429`/`401` பிழையை ஏற்படுத்தும். திருத்தத்திற்குப் பிறகு, தோல்விகள் (ஏதேனும் இருந்தால்) வெளிப்படையாகத் தெரியாத வகையில் மீண்டும் முயற்சிக்கப்படும், மேலும் அழைப்பு நிறைவடையும். நீங்கள் `curl /monitoring/health` என்பதையும் இயக்கி, provider இணைப்புகளில் உள்ள `rateLimitedUntil` புலத்தையும், பாதிக்கப்பட்ட provider-களுக்கான `circuitBreakers.providerBreakers[].state` மதிப்பையும் கண்காணிக்கலாம் — நிலை `CLOSED`, `DEGRADED`, `OPEN`, அல்லது `HALF_OPEN` ஆகியவற்றில் ஒன்றாக இருக்கும் (`src/shared/utils/circuitBreaker.ts`-ஐப் பார்க்கவும்); தொடர்ந்து தோல்வியடையும் provider ஒன்று, மீட்டமைப்புச் சாளரம் ஒரு சோதனை அழைப்பை அனுமதிக்கும் (`HALF_OPEN`) முன் `CLOSED → DEGRADED → OPEN` என மாறும்.

**நீங்கள் இன்னும் 429 பிழையைக் கண்டால்**: அந்த provider-க்கான செயலில் உள்ள கணக்கு அதன் _quota_-வை (வெறும் rate அல்ல) உண்மையாகவே முழுமையாகப் பயன்படுத்திவிட்டது. OmniRoute dashboard → Providers → Accounts என்பதில் அதே provider-க்கு இரண்டாவது கணக்கைச் சேர்க்கவும், அல்லது மற்றொரு இலவச provider-ஐ (எ.கா. `routeway`, `auggie`) இணைத்துப் பயன்படுத்தவும். தற்காலிகமான rate/400/401 சிக்கல்களுக்கு மட்டுமே rotation உதவும்; quota முழுமையாகத் தீர்ந்துவிட்டால், இரண்டாவது credential அல்லது வேறொரு provider தேவைப்படும்.

**vision model-களில் (`auto/vision`, `bazaarlink/*`) 403 பிழையைக் கண்டால்**: இணைக்கப்பட்ட கணக்கில் vision வசதியை உள்ளடக்கிய கட்டணத் திட்டம் இல்லை, அல்லது API key-க்கு போதுமான அனுமதிகள் இல்லை. provider dashboard-இல் key scope, vision/multimodal அணுகலை உள்ளடக்கியுள்ளதா என்பதைச் சரிபார்க்கவும்; இல்லையெனில், கட்டண tier கணக்கை இணைத்து அதை vision இலக்காக வைத்திருக்கவும்.

## npm install எச்சரிக்கைகள் (ERESOLVE / peer / deprecated)

நீங்கள் `npm install -g omniroute`-ஐ இயக்கும்போது, `npm warn ERESOLVE`, peer-dependency அறிவிப்புகள் மற்றும் `deprecated` செய்திகள் போன்ற ஏராளமான எச்சரிக்கைகளைப் பார்க்கலாம். **இவை எதிர்பார்க்கப்படுபவை மற்றும் தீங்கற்றவை.** வெளியீட்டில் `added <N> packages` என்று தோன்றினால், நிறுவல் வெற்றிகரமாக முடிந்துள்ளது.

peer-dependency தீர்மான எச்சரிக்கைகளைத் தவிர்க்க, OmniRoute ஆதரிக்கும் பின்வரும் நிறுவல் வடிவத்தைப் பயன்படுத்தவும்:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` ஆனது `ERESOLVE` மற்றும் peer-dependency அறிவிப்புகளை மட்டுமே மறைக்கிறது. வழக்கொழிப்பு அறிவிப்புகள், மறைமுகமான மூன்றாம் தரப்புத் தொகுப்புகளிலிருந்து வருவதால் தொடர்ந்து காட்டப்படும்; நிறுவல் தோல்வியடைந்தது என்பதை அவை குறிக்கவில்லை.

OmniRoute-ன் கட்டுப்பாட்டில் இல்லாத மூன்றாம் தரப்புத் தொகுப்புகளில் உள்ள காலாவதியான peer-dependency வரம்புகளே இந்த எச்சரிக்கைகளுக்குக் காரணம்:

1. **`marked-terminal`-க்கு `marked >=1 <16` தேவை, ஆனால் `marked@18` கண்டறியப்பட்டது** — நடைமுறையில் இது நன்றாகச் செயல்படுகிறது; upstream peer வரம்பு காலாவதியாகியுள்ளது.
2. **`deprecated prebuild-install@7.1.3`** — இது ஒரு மறைமுகமான native-binary பதிவிறக்க உதவிக் கருவி. நிலையான பதிப்பாகப் பொருத்தப்பட்ட `wreq-js` போக்குவரத்து binding-ஐ நிறுவ இது பயன்படுத்தப்படுவதில்லை; மேலும் web-cookie
   வழங்குநரின் போக்குவரத்து அமைவு தோல்வியடைந்ததையும் இது குறிக்கவில்லை.

**எந்த நடவடிக்கையும் தேவையில்லை** — upstream தொகுப்புகளை fork செய்யாமல் இந்த எச்சரிக்கைகளை முழுமையாக மறைக்க முடியாது.

## npm install-scripts தடுக்கப்பட்ட எச்சரிக்கை (உலகளாவிய நிறுவல்)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute`-ஐ இயக்கும்போது, புதிய npm பதிப்புகள் (v11+ மற்றும் v12+) தொகுப்பின் lifecycle scripts-ஐ இயல்பாகவே தடுத்து, install-scripts எச்சரிக்கையைக் காட்டுகின்றன:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### இந்த எச்சரிக்கையைப் புறக்கணிக்க முடியுமா?

**ஓரளவுக்கு முடியும், ஆனால் scripts இல்லாமல் இயக்குவது பரிந்துரைக்கப்படவில்லை.** OmniRoute சிக்கலைச் சமாளிக்கும் மாற்று வழிமுறைகளை உள்ளடக்கியுள்ளது: தனித்தொகுப்பிலிருந்து native `better-sqlite3` bindings-ஐ ஏற்ற முடியாவிட்டால், பயன்பாடு `node:sqlite` அல்லது `sql.js` போன்ற மாற்று drivers வழியாகச் செயல்படும் (பார்க்க: [SQLite இயக்கநேரத் தீர்மானம்](../ops/SQLITE_RUNTIME.md)). சேவையகம் தொடர்ந்து தொடங்கும்; ஆனால் `sql.js` போன்ற WASM மாற்று வழிமுறைகளில் இயக்குவது SQLite WAL (முன்கூட்டிய பதிவு எழுதுதல்) பயன்முறையை முடக்குவதுடன், நினைவகம் மற்றும் வட்டு ஒத்திசைவு மேலதிகச் செலவையும் அதிகரிக்கும்.

### உண்மையில் எந்த scripts தேவை?

தடுக்கப்பட்ட அனைத்து scripts-உம் OmniRoute-ஐ இயக்குவதற்கு அத்தியாவசியமானவை அல்ல:

- **அத்தியாவசியமானவை (`omniroute`, `better-sqlite3`):** OmniRoute ஒரு Next.js தனித்த பயன்பாட்டுத் தொகுப்பிலிருந்து (`dist/`) இயங்குகிறது. நிறுவலின்போது, host-க்கு ஏற்ற native SQLite driver-ஐ மேல்-நிலை `node_modules/better-sqlite3/`-இல் npm பதிவிறக்குகிறது அல்லது தொகுக்கிறது. பின்னர் OmniRoute-ன் `postinstall` script (`scripts/build/postinstall.mjs`), இந்த host-க்கு ஏற்ற binaries-ஐச் சரிபார்த்து `dist/node_modules/`-இல் நகலெடுக்கிறது; இதனால் தனித்த சேவையகம் அவற்றை அணுக முடியும். `omniroute`-ன் postinstall script தடுக்கப்பட்டால், இந்த நகலெடுக்கும் படிநிலை தவிர்க்கப்படும்.
- **விருப்பமானவை/மறைமுகமானவை (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** இவை build உதவிக் கருவிகள், watcher கருவிகள் அல்லது கணினி keychain பயன்பாடுகள். இவற்றை அனுமதிப்பது build எச்சரிக்கைகளைத் தவிர்க்கிறது; ஆனால் அடிப்படை routing செயல்பாட்டிற்கு இவை தேவையில்லை.
- **விலக்கப்பட்டது (`onnxruntime-node`):** உள்ளூர் AI embeddings-க்கான ஒரு விருப்ப dependency; OmniRoute இயங்குவதற்கு இது **தேவையில்லை**. இதன் postinstall script, NuGet-இலிருந்து சுமார் 300MB அளவிலான CUDA assets-ஐப் பதிவிறக்குகிறது; ஆதரிக்கப்படும் வன்பொருளில் உள்ளூர் ONNX acceleration-ஐப் பயன்படுத்தத் தெளிவாகத் திட்டமிட்டிருந்தால் மட்டுமே இதை allow-list-இல் சேர்க்கவும்.

### பரிந்துரைக்கப்படும் தீர்வு

உலகளாவிய நிறுவலின்போது தேவையான install scripts-ஐ அனுமதித்து எச்சரிக்கைகளை மறைக்க, OmniRoute மற்றும் அதன் native dependencies-க்கு `--allow-scripts`-ஐ வழங்கவும்:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

மாற்றாக, உங்கள் பயனர் கணக்கில் மேற்கொள்ளப்படும் அனைத்து உலகளாவிய நிறுவல்களுக்கும் இதை நிரந்தரமாக உள்ளமைக்க:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### உங்கள் நிறுவலைச் சரிபார்க்கவும்

நிறுவலுக்குப் பிறகு, native bindings மற்றும் இயக்கநேரச் சூழல் சரியாக உள்ளனவா என்பதை உறுதிப்படுத்த, உள்ளமைக்கப்பட்ட diagnostic கருவியை இயக்கவும்:

```bash
omniroute doctor
```

## Gemini Web மற்றும் Playwright Chromium

Gemini Web கோரிக்கை, Playwright Chromium நிறுவப்படவில்லை என்ற செய்தியுடன் `503` நிலையைத் திருப்பினால், npm தொகுப்பு உள்ளது, ஆனால் உலாவி binary இல்லை என்று பொருள்.
Playwright வேண்டுமென்றே உலாவிப் பதிவிறக்கங்களை npm தொகுப்பு நிறுவலில் இருந்து தனியாக வைத்திருப்பதால், உலாவி நிறுவப்படும் வரை இந்தப் பதில் எதிர்பார்க்கப்பட்டதே.

உலகளாவிய npm நிறுவலுக்கு, உலாவி cache அதே Playwright நிறுவலுக்குச் சொந்தமானதாக இருக்கும்படி OmniRoute தொகுப்பின்
கோப்பகத்திலிருந்து Chromium-ஐ நிறுவவும்:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

நிறுவிய பிறகு OmniRoute-ஐ மறுதொடக்கம் செய்து, பின்னர் Gemini Web கோரிக்கையை மீண்டும் முயற்சிக்கவும். Docker image-இலிருந்து
OmniRoute-ஐ இயக்கினால், Chromium மற்றும் அதன் சார்புகளை உள்ளடக்கிய `-web` image-ஐ (அல்லது `runner-web`
build target-ஐ) பயன்படுத்தவும்; base image அவற்றை உள்ளடக்காது.

## ஆன்டிவைரஸ் தவறான நேர்மறை முடிவுகள்

<a name="antivirus-false-positives"></a>

### Avast/AVG, `README.md`-ஐ `MD:HttpRequest-inf[Susp]` எனத் தனிமைப்படுத்துகிறது

**இது ஒரு தவறான நேர்மறை முடிவு. எதுவும் பாதிக்கப்படவில்லை, எந்த நடவடிக்கையும் தேவையில்லை.**

HTTP கோரிக்கைகளைப் போன்ற பல இணைப்புகளைக் கொண்ட எளிய உரை/Markdown கோப்புகளைக் குறியிடும் ஒரு ஹியூரிஸ்டிக்கை Avast மற்றும் AVG இயக்குகின்றன. OmniRoute-இன் `README.md`, npm தொகுப்பிற்குள் வழங்கப்படுகிறது (இது `package.json` → `files` என்பதில் பட்டியலிடப்பட்டுள்ளது); எனவே, முழுமையான நிறுவலின்போது அது `node_modules/omniroute/README.md` என்ற இடத்தில் சேர்கிறது — மேலும் அதில் சுமார் 15 `http://localhost:20128/...` எடுத்துக்காட்டுகள் உள்ளன (MCP HTTP/SSE முனைப்புள்ளிகள், A2A `.well-known` URL மற்றும் `curl` துணுக்குகள்). அந்த அளவிலான இணைப்பு அடர்த்தி, இந்த ஹியூரிஸ்டிக்கைத் தூண்டப் போதுமானது.

இது சமீபத்தில்தான் தொடங்கியிருந்தால்: கோப்பின் தன்மை மாறவில்லை. README-இன் முனைப்புள்ளிகள் அட்டவணை விரிவடைந்தது (MCP HTTP + SSE + A2A சேர்க்கப்பட்டன), மேலும் அதிகமான `curl` எடுத்துக்காட்டுகளும் சேர்க்கப்பட்டன; இதனால் அது வரம்பைத் தாண்டியது.

இந்தக் கோப்பு இயக்கக்கூடிய உள்ளடக்கம் எதுவுமற்ற செயலற்ற ஆவணமாகும். இதைத் தனிமைப்படுத்தப்பட்ட இடத்திலிருந்து நீங்கள் பாதுகாப்பாக மீட்டெடுக்கலாம்.

**என்ன செய்ய வேண்டும்:**

1. **அறிவிப்புகளை நிறுத்துங்கள்** — உங்கள் ஆன்டிவைரஸில் நிறுவல் கோப்பகத்தை விலக்காகச் சேருங்கள்
   (Avast: Settings → Exceptions); உங்கள் முழுமையான `node_modules` பாதை மற்றும்/அல்லது
   OmniRoute தரவுக் கோப்பகத்தை (`~/.omniroute/`) சேர்க்கவும்.
2. **தவறான நேர்மறை முடிவைப் புகாரளியுங்கள்** — <https://www.avast.com/false-positive-file-form.php>,
   தனிமைப்படுத்தப்பட்ட `README.md`-ஐ இணைக்கவும். ஒரு உரைக் கோப்புக்கு வழங்குநரின் ஹியூரிஸ்டிக்
   அளவுக்கு மீறி எதிர்வினையாற்றுவதே காரணம் என்பதால், அனைவருக்கும் உதவும் தீர்வு இதுவாகும்.

**எங்கள் தரப்பில் இதை ஏன் "சரிசெய்வதில்லை":** அனைத்து எடுத்துக்காட்டுகளும் `http://localhost`-ஐப் பயன்படுத்துகின்றன; மேலும் சுய-கையொப்பமிட்ட சான்றிதழால் ஏற்படும் சிக்கல்கள் இல்லாமல் localhost-ஐ `https` ஆக்க முடியாது. ஒரு வழங்குநரின் ஹியூரிஸ்டிக்கைத் தவிர்ப்பதற்காக ஆவணங்களைச் சிதைப்பது, ஸ்கேனர் பிழையைத் திருப்திப்படுத்த ஒவ்வொரு வாசகருக்கும் பாதிப்பை ஏற்படுத்தும்.

### Kaspersky, Desktop செயலியை `PDM:Trojan.Win32.Generic` எனக் குறியிடுகிறது

**இது நடத்தை சார்ந்த ஹியூரிஸ்டிக்கால் ஏற்படும் தவறான நேர்மறை முடிவு. எதுவும் பாதிக்கப்படவில்லை.** Kaspersky-இன் `PDM:` முன்னொட்டு, அறியப்பட்ட தீம்பொருளுடன் பொருத்திப் பார்ப்பதற்குப் பதிலாக நிறுவி _என்ன செய்கிறது_ என்பதை மதிப்பிடும் அதன் Proactive Defense Module (System Watcher)-இலிருந்து இந்தத் தீர்ப்பு வருகிறது என்பதைக் குறிக்கிறது. இது தூண்டப்படும்போது, Kaspersky முழு நிறுவலையும் "முந்தைய நிலைக்குத் திருப்புகிறது" — ஏற்கெனவே எழுதப்பட்ட கோப்புகளை நீக்குகிறது — இதனால் செயலி செயலிழந்ததாகவோ காணாமல் போனதாகவோ முடிகிறது.

இது குறியிடும் கோப்புகள், Desktop செயலியுடன் தொகுக்கப்பட்டுள்ள அறிவிக்கப்பட்ட திறந்த மூல சார்புகளின் வழக்கமான பகுதிகளாகும், எடுத்துக்காட்டாக:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` மற்றும்
  `workerProcessEntry.js` — செயலிக்குள்ளான வழங்குநர் உள்நுழைவு மற்றும் உலாவி ஆதரவுள்ள அரட்டைக்குப் பயன்படுத்தப்படும் உலாவி தானியக்க நூலகமான [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — வலைக் குக்கீ வழங்குநர்களில் உலாவி கைரேகையிடப்பட்ட HTTP-க்குப் பயன்படுத்தப்படும், பதிப்பு நிலைநிறுத்தப்பட்ட `wreq-js` சொந்த பிணைப்பு (`<arch>` என்பது `x64` அல்லது `arm64`).

**இது ஏன் தூண்டப்படுகிறது:** Windows நிறுவி **இன்னும் குறியீட்டுக் கையொப்பமிடப்படவில்லை**; எனவே கையொப்பமிடப்படாத NSIS நிறுவிக்கு எந்த நற்பெயரும் இல்லாததால், நடத்தை சார்ந்த ஹியூரிஸ்டிக்குகள் அதிகபட்ச தீவிரத்துடன் இயங்குகின்றன. தொகுக்கப்பட்ட சொந்த DLL மற்றும் `%LOCALAPPDATA%\Programs\OmniRoute` என்பதன் கீழ் எழுதப்படும் நூற்றுக்கணக்கான `.js` கோப்புகளுடன் (Next.js தனித்தியங்கும் கட்டமைப்பிலிருந்து வரும் hash பின்னொட்டு கொண்ட தொகுப்புக் கோப்பகங்கள் உட்பட) இது இணைவது, ஹியூரிஸ்டிக்கைத் தூண்டப் போதுமானது. குறியீட்டுக் கையொப்பமிடுதல் திட்டமிடப்பட்டுள்ளது; அது நடைமுறைக்கு வரும்வரை, புதிய வெளியீடுகளில் இது மீண்டும் நிகழலாம்.

**என்ன செய்ய வேண்டும்:**

1. **முதலில் உங்கள் பதிவிறக்கத்தைச் சரிபாருங்கள்** (கோப்பு முறைகேடாக மாற்றப்பட்டிருக்கலாம் என்ற வாய்ப்பை இது விலக்குகிறது). ஒவ்வொரு வெளியீடும் `latest.yml`-ஐ வெளியிடுகிறது; அதிலுள்ள `sha512` புலம் (base64), `OmniRoute.Setup.<version>.exe` நிறுவியை உள்ளடக்குகிறது. PowerShell-இல், நிறுவி உள்ள கோப்பகத்திலிருந்து:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   வெளியீடு `latest.yml` → `sha512` உடன் பொருந்த வேண்டும். பொருந்தவில்லை என்றால், கோப்பை நீக்கிவிட்டு [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases)-இலிருந்து மட்டும் மீண்டும் பதிவிறக்கவும்.
2. **மீட்டெடுத்து + விலக்காகச் சேருங்கள்** — முந்தைய நிலைக்குத் திருப்பப்பட்ட உருப்படிகளைத் தனிமைப்படுத்தப்பட்ட இடத்திலிருந்து மீட்டெடுத்து, `%LOCALAPPDATA%\Programs\OmniRoute`-ஐ விலக்காகச் சேருங்கள் (Kaspersky → Settings → Threats and Exclusions), பின்னர் மீண்டும் நிறுவவும்.
3. **தவறான நேர்மறை முடிவைப் புகாரளியுங்கள்** — <https://opentip.kaspersky.com/>. பயனர்கள் சமர்ப்பிக்கும் தவறான நேர்மறை முடிவு அறிக்கைகள், அனுமதிப்பட்டியலில் சேர்க்கப்படுவதை உண்மையிலேயே விரைவுபடுத்துகின்றன.

## Node.js இணக்கத்தன்மை

<a name="nodejs-compatibility"></a>

### உள்நுழைவுப் பக்கம் செயலிழக்கிறது அல்லது "Module self-registration" பிழையைக் காட்டுகிறது

**காரணம்:** OmniRoute அங்கீகரித்த பாதுகாப்பான இயக்கநேரக் குறைந்தபட்ச வரம்பிற்கு வெளியே உள்ள Node.js பதிப்பை நீங்கள் இயக்குகிறீர்கள். OmniRoute தேவைப்படுத்தும் பாதுகாப்புத் திருத்தங்கள் செய்யப்பட்ட குறைந்தபட்ச வரம்பிற்குக் கீழே உள்ள பழைய Node 22 அல்லது 24 திருத்தப் பதிப்பை இயக்குவதே மிகவும் பொதுவான காரணமாகும்.

**அறிகுறிகள்:**

- உள்நுழைவுப் பக்கம் வெற்றுத் திரை அல்லது சேவையகப் பிழையைக் காட்டுகிறது
- கன்சோலில் `Error: Module did not self-register` அல்லது அதுபோன்ற நேட்டிவ் பைண்டிங் பிழைகள் காட்டப்படுகின்றன
- இயக்கநேரம் ஆதரிக்கப்படும் பாதுகாப்புக் கொள்கைக்கு வெளியே இருந்தால், உள்நுழைவுப் பக்கம் உங்கள் Node பதிப்புடன் **ஆரஞ்சு நிற எச்சரிக்கைப் பட்டையை** காட்டுகிறது

**தீர்வு:**

1. ஆதரிக்கப்படும் Node.js LTS வெளியீட்டை நிறுவவும் (பரிந்துரைக்கப்படுவது: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. உங்கள் பதிப்பைச் சரிபார்க்கவும்: `node --version`, 24.x LTS வரிசையில் `v24.0.0` அல்லது அதற்குப் புதிய பதிப்பைக் காட்ட வேண்டும்
3. OmniRoute-ஐ மீண்டும் நிறுவவும்: `npm install -g omniroute`
4. மீண்டும் தொடங்கவும்: `omniroute`

> **ஆதரிக்கப்படும் பாதுகாப்பான பதிப்புகள்:** `>=22.22.2 <23` அல்லது `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) மற்றும் Node.js 26 முழுமையாக ஆதரிக்கப்படுகின்றன.

### npm v11+: `better-sqlite3` நிறுவப்படவில்லை (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**காரணம்:** npm v11 (Node.js 24+ உடன் வழங்கப்படுகிறது) விருப்பச் சார்புகளுக்கான நிறுவல் ஸ்கிரிப்ட்களை இயல்பாகத் தடுக்கிறது. `better-sqlite3`, `optionalDependencies`-இல் பட்டியலிடப்பட்டிருப்பதாலும் நேட்டிவ் தொகுப்பு (`node-gyp rebuild`) தேவைப்படுவதாலும், npm எந்த அறிவிப்புமின்றி அதைத் தவிர்க்கிறது.

**அறிகுறிகள்:**

- தொடங்கும்போது `Cannot find module 'better-sqlite3'` என்ற பிழையுடன் சேவையகம் செயலிழக்கிறது
- `ls node_modules/better-sqlite3`, "No such file or directory" என்பதைக் காட்டுகிறது
- `npm ls better-sqlite3`, `(empty)` என்பதைக் காட்டுகிறது

**தீர்வு:**

1. நிறுவல் ஸ்கிரிப்ட்களை அங்கீகரித்து மீண்டும் நிறுவவும்:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. அல்லது முன்தொகுக்கப்பட்ட பதிப்பைக் கைமுறையாக நிறுவவும்:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. அது செயல்படுகிறதா என்பதைச் சரிபார்க்கவும்: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**காரணம்:** உலகளாவிய `npm install -g omniroute` நிறுவலுக்குப் பிறகு, தொகுப்பிற்குள் உள்ள `better-sqlite3` நேட்டிவ் பைனரி, உள்ளூரில் இயங்கும் கட்டமைப்பு அல்லது Node.js ABI-க்குப் பதிலாக வேறொன்றிற்காகத் தொகுக்கப்பட்டிருக்கலாம். முன்தொகுக்கப்பட்ட பைனரி உங்கள் சூழலுடன் பொருந்தாதபோது, macOS-இல் (Apple Silicon மற்றும் Intel இரண்டிலும்) இது பொதுவாக நிகழ்கிறது.

**அறிகுறிகள்:**

- தொடங்கியவுடன் `dlopen` பிழையுடன் சேவையகம் உடனடியாகத் தோல்வியடைகிறது
- பிழையில் `slice is not valid mach-o file` இடம்பெறுகிறது
- முழுமையான எடுத்துக்காட்டு:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**தீர்வு — உங்கள் உள்ளூர் சூழலுக்காக மீண்டும் தொகுக்கவும் (Node.js பதிப்பைத் தரமிறக்க வேண்டியதில்லை):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **குறிப்பு:** இது உங்கள் உள்ளூர் Node.js பதிப்பு மற்றும் CPU கட்டமைப்பிற்கு ஏற்ப நேட்டிவ் பைண்டிங்கை மீண்டும் தொகுத்து, பைனரி பொருத்தமின்மையைத் தீர்க்கிறது. அதிகாரப்பூர்வமாக ஆதரிக்கப்படும் இயக்கநேர வரம்பு **`>=22.22.2 <23` அல்லது `>=24.0.0 <27`** (`src/shared/utils/nodeRuntimeSupport.ts`-இல் உள்ள `SUPPORTED_NODE_RANGE`, `package.json`-இன் `engines` புலத்துடன் ஒத்திசைக்கப்பட்டுள்ளது). Node.js 24.x LTS (Krypton) மற்றும் Node.js 26 ஆகியவை `better-sqlite3` v12.x உடன் முழுமையாக ஆதரிக்கப்படுகின்றன.

### வழங்குநர் சரிபார்ப்பில் "fetch failed" எனக் காட்டப்படுகிறது

**காரணம்:** API விசை சரிபார்ப்பு முனைப்புள்ளி (`POST /api/providers/validate`) முன்பு ப்ராக்ஸி உள்ளமைவைத் தவிர்த்ததால், ப்ராக்ஸி வழித்தடம் தேவைப்படும் சூழல்களில் தோல்விகள் ஏற்பட்டன.

**தீர்வு (v3.5.5+):** இது இப்போது சரிசெய்யப்பட்டுள்ளது. வழங்குநர் சரிபார்ப்பு `runWithProxyContext` வழியாகச் செலுத்தப்பட்டு, வழங்குநர் நிலை மற்றும் உலகளாவிய ப்ராக்ஸி அமைப்புகள் தானாகவே பின்பற்றப்படுகின்றன.

### டோக்கன் நிலைச் சரிபார்ப்பு "fetch failed" எனத் தோல்வியடைகிறது

**காரணம்:** பின்னணியில் நிகழும் OAuth டோக்கன் புதுப்பிப்பு, ஒவ்வொரு இணைப்பிற்குமான ப்ராக்ஸி உள்ளமைவைத் தீர்மானிக்கவில்லை.

**தீர்வு (v3.5.5+):** டோக்கன் நிலைச் சரிபார்ப்பு திட்டமிடுபவர் இப்போது புதுப்பிக்க முயல்வதற்கு முன் ஒவ்வொரு இணைப்பிற்குமான ப்ராக்ஸி உள்ளமைவைத் தீர்மானிக்கிறார். v3.5.5+ க்கு புதுப்பிக்கவும்.

### SOCKS5 ப்ராக்ஸி "invalid onRequestStart method" எனத் திருப்புகிறது

**காரணம்:** Node.js 22 இல், undici@8 dispatcher ஆனது Node-இன் உள்ளமைந்த `fetch()` செயலாக்கத்துடன் இணக்கமற்றது.

**தீர்வு (v3.5.5+):** ப்ராக்ஸி dispatcher செயலில் இருக்கும்போது OmniRoute இப்போது undici-இன் சொந்த `fetch()` செயல்பாட்டைப் பயன்படுத்துகிறது; இது சீரான நடத்தையை உறுதிசெய்கிறது. v3.5.5+ க்கு புதுப்பிக்கவும்.

### WSL-இன் கீழ் MITM ப்ராக்ஸி: Windows ஹோஸ்டில் உள்ள டெஸ்க்டாப் செயலிகள் இடைமறிக்கப்படுவதில்லை

**காரணம்:** MITM ப்ராக்ஸியும் அதன் CA சான்றிதழும் OmniRoute இயங்கும் சூழலில் நிறுவப்படுகின்றன. WSL-இன் கீழ் அந்தச் சூழல் Linux கெஸ்ட் ஆகும்; ஆனால் AI டெஸ்க்டாப் செயலிகள் (Kiro, Trae, Copilot, Zed, …) Windows ஹோஸ்டில் இயங்குகின்றன. ஹோஸ்ட் செயலிகள் கெஸ்ட்டின் சான்றிதழ் சேமிப்பகத்தை நம்புவதில்லை மற்றும் கெஸ்ட்டின் சிஸ்டம் ப்ராக்ஸி வழியாகச் செல்லுவதில்லை; எனவே அங்கு டெஸ்க்டாப் இடைமறிப்பு செயல்படாது.

**பரிந்துரை:** நீங்கள் இடைமறிக்க விரும்பும் டெஸ்க்டாப் செயலிகள் இயங்கும் அதே OS-இல் OmniRoute-ஐ நேரடியாக இயக்கவும் (Windows செயலிகளுக்கு Windows; அதேபோல் macOS/Linux). ஹோஸ்ட் செயலிகளைக் குறிவைத்தபடி OmniRoute-ஐ WSL-க்குள் வைத்திருப்பதற்கு, உருவாக்கப்பட்ட CA சான்றிதழை Windows ஹோஸ்டில் கைமுறையாக நம்பகமானதாகச் சேர்த்து, ஒவ்வொரு ஹோஸ்ட் செயலியின் நெட்வொர்க்/ப்ராக்ஸி அமைப்புகளையும் WSL ப்ராக்ஸி முனைப்புள்ளியை நோக்கி அமைக்க வேண்டும் — இது ஆதரிக்கப்படாத, எளிதில் செயலிழக்கக்கூடிய அமைப்பாகும்.

இரண்டு கணக்குகள் ஒரே பதிவுசெய்யப்பட்ட கிளையன்டைப் பகிரும்போது (v3.8.0 க்கு முன் இறக்குமதி செய்யப்பட்ட இணைப்புகள்),
ஒரு கணக்கின் டோக்கனைப் புதுப்பிப்பது மற்றொன்றின் புதுப்பிப்பு டோக்கனைச் செல்லாததாக்குகிறது.

**தீர்வு (v3.8.0+):** பாதிக்கப்பட்ட இணைப்புகளை மீண்டும் இறக்குமதி செய்யவும்.
v3.8.0 முதல், **Import Token**,
**Google/GitHub சமூக உள்நுழைவு** அல்லது **Auto-Import** வழியாக உருவாக்கப்படும் ஒவ்வொரு புதிய Kiro இணைப்பும் தானாகவே

கணக்கைப் புதுப்பிப்பது வேறு எந்தக் கணக்கையும் பாதிக்காது.

v3.8.0 க்கு _முன்_ இறக்குமதி செய்யப்பட்ட இணைப்புகளில், ஒவ்வொரு இணைப்பிற்குமான தனிப்பட்ட கிளையன்ட்
பதிவு இருக்காது. அந்த இணைப்புகள் பகிரப்பட்ட சமூக அங்கீகாரப் புதுப்பிப்பு முனைப்புள்ளியைத் தொடர்ந்து பயன்படுத்தும்.

## கிளவுட் சிக்கல்கள்

### கிளவுட் ஒத்திசைவுப் பிழைகள்

1. `BASE_URL` உங்கள் இயங்கும் நிகழ்வைச் சுட்டுகிறது என்பதைச் சரிபார்க்கவும் (எ.கா., `http://localhost:20128`)
2. `CLOUD_URL` உங்கள் கிளவுட் முனைப்புள்ளியைச் சுட்டுகிறது என்பதைச் சரிபார்க்கவும் (எ.கா., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` மதிப்புகளைச் சர்வர்-பக்க மதிப்புகளுடன் ஒரே நிலையில் வைத்திருக்கவும்

### கிளவுடில் `stream=false` பயன்படுத்தும்போது 500 திரும்புகிறது

**அறிகுறி:** ஸ்ட்ரீமிங் அல்லாத அழைப்புகளுக்கான கிளவுட் முனைப்புள்ளியில் `Unexpected token 'd'...` தோன்றுகிறது.

**காரணம்:** கிளையன்ட் JSON-ஐ எதிர்பார்க்கும் நிலையில், மேல்நிலைச் சேவை SSE பேலோடைத் திருப்புகிறது.

**தற்காலிகத் தீர்வு:** கிளவுடுக்கான நேரடி அழைப்புகளில் `stream=true` பயன்படுத்தவும். உள்ளூர் இயக்கச்சூழலில் SSE→JSON மாற்று ஏற்பாடு உள்ளது.

### கிளவுட் இணைக்கப்பட்டுள்ளதாகக் கூறினாலும் "Invalid API key" தோன்றுகிறது

1. உள்ளூர் டாஷ்போர்டிலிருந்து புதிய விசையை உருவாக்கவும் (`/api/keys`)
2. கிளவுட் ஒத்திசைவை இயக்கவும்: கிளவுடை இயக்கு → இப்போது ஒத்திசை
3. பழைய/ஒத்திசைக்கப்படாத விசைகள் கிளவுடில் இன்னும் `401`-ஐத் திருப்பக்கூடும்

## Docker சிக்கல்கள்

### Docker IPv6 / இணைப்பு மீட்டமைப்பு

<a name="docker-ipv6"></a>

**அறிகுறிகள்:** `curl http://localhost:20128/v1/models` என்பது `curl: (56) Recv failure: Connection reset by peer` என்பதைத் திருப்புகிறது. டாஷ்போர்டும் அங்கீகரிக்கப்படாத முனைப்புள்ளிகளும் செயல்படுகின்றன, ஆனால் அங்கீகரிக்கப்பட்ட முனைப்புள்ளிகள் தோல்வியடைகின்றன — இது அங்கீகாரச் சிக்கல் போல் தோன்றினாலும் உண்மையில் அப்படியல்ல.

**காரணம்:** `docker run -p 20128:20128` என்பது `0.0.0.0` (IPv4) மற்றும் `::` (IPv6) ஆகிய இரண்டிலும் வெளியிடுகிறது, ஆனால் கண்டெய்னருக்குள் உள்ள செயல்முறை IPv4-இல் மட்டுமே கோரிக்கைகளுக்காகக் காத்திருக்கிறது. `localhost` முதலில் `::1` ஆகத் தீர்மானிக்கப்படும் ஹோஸ்ட்களில், இணைப்பு அதற்குப் பின்னால் எந்தக் கேட்பானும் இல்லாத IPv6 வெளியிடப்பட்ட போர்ட்டை அடைகிறது → இணைப்பு மீட்டமைக்கப்படுகிறது.

**தீர்வு:**

1. **விரைவான கண்டறிதல்:** `curl -4 http://localhost:20128/v1/models`-ஐ இயக்கவும். இது `-4` உடன் செயல்பட்டு, அது இல்லாமல் தோல்வியடைந்தால், உங்களிடம் IPv6 பிணைப்பு பொருத்தமின்மை உள்ளது.
2. **நிரந்தரத் தீர்வு:** உங்கள் `docker run` கட்டளையில் `-p 127.0.0.1:20128:20128`-ஐப் பயன்படுத்தி IPv4-க்கு வெளிப்படையாகப் பிணைக்கவும்:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   இது IPv4 பிணைப்பைக் கட்டாயப்படுத்துவதுடன், அனைத்து ஹோஸ்ட் இடைமுகங்களிலும் ப்ராக்ஸி வெளிப்படுத்தப்படுவதையும் தவிர்க்கிறது.

2. எடுத்துச் செல்லக்கூடிய பயன்முறைக்கு: `runner-cli` இமேஜ் இலக்கைப் பயன்படுத்தவும் (CLI-கள் தொகுக்கப்பட்டுள்ளன)
3. ஹோஸ்ட் மவுண்ட் பயன்முறைக்கு: `CLI_EXTRA_PATHS`-ஐ அமைத்து, ஹோஸ்ட் பைனரி கோப்பகத்தை வாசிக்க மட்டும் அனுமதியுடன் மவுண்ட் செய்யவும்
4. `installed=true` மற்றும் `runnable=false` எனில்: பைனரி கண்டறியப்பட்டது, ஆனால் நலச் சோதனையில் தோல்வியடைந்தது

### விரைவான இயக்கச்சூழல் சரிபார்ப்பு

```bash
curl -s http://localhost:20128/api/cli-tools/codex-settings | jq '{installed,runnable,commandPath,runtimeMode,reason}'
curl -s http://localhost:20128/api/cli-tools/claude-settings | jq '{installed,runnable,commandPath,runtimeMode,reason}'
curl -s http://localhost:20128/api/cli-tools/openclaw-settings | jq '{installed,runnable,commandPath,runtimeMode,reason}'
```

## பிழைத்திருத்தம்

### பதிவுக் கோப்புகளை இயக்குதல்

உங்கள் `.env` கோப்பில் `APP_LOG_TO_FILE=true` என அமைக்கவும். பயன்பாட்டுப் பதிவுகள் `logs/`-இன் கீழ் எழுதப்படும்.
அமைப்புகளில் அழைப்புப் பதிவுப் பைப்லைன் இயக்கப்பட்டிருக்கும்போது, கோரிக்கைத் துணைக்கோப்புகள் `${DATA_DIR}/call_logs/`-இன் கீழ் சேமிக்கப்படும்.
பைப்லைன் பதிவெடுப்பு இயக்கப்பட்டிருக்கும்போது, ஸ்ட்ரீம் துண்டு பேலோடுகளைத் தவிர்க்க `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` என அமைக்கவும் அல்லது KB-இல் துணைக்கோப்பின் உச்சவரம்பை மாற்ற `CALL_LOG_PIPELINE_MAX_SIZE_KB`-ஐச் சரிசெய்யவும்.

### வழங்குநரின் நலநிலையைச் சரிபார்த்தல்

```bash
# நலநிலை டாஷ்போர்டு
http://localhost:20128/dashboard/health

# API நலநிலைச் சோதனை
curl http://localhost:20128/api/monitoring/health
```

### இயக்கச்சூழல் சேமிப்பகம்

- முதன்மை நிலை: `${DATA_DIR}/storage.sqlite` (வழங்குநர்கள், சேர்க்கைகள், மாற்றுப்பெயர்கள், விசைகள், அமைப்புகள்)
- பயன்பாடு: `storage.sqlite`-இல் உள்ள SQLite அட்டவணைகள் (`usage_history`, `call_logs`, `proxy_logs`) + விருப்பத்திற்குரிய `${DATA_DIR}/call_logs/`
- பயன்பாட்டுப் பதிவுகள்: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ஆக இருக்கும்போது)
- அழைப்புப் பதிவுத் துணைக்கோப்புகள்: அழைப்புப் பதிவுப் பைப்லைன் இயக்கப்பட்டிருக்கும்போது `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

கோரிக்கைப் பதிவுகள் பக்கத்தில் உள்ள **வரலாற்றை அழி** செயல், `call_logs`, பழைய
`request_detail_logs` மற்றும் உள்ளூர் `${DATA_DIR}/call_logs/` துணைக்கோப்புக் கோப்பகத்தை அழிக்கிறது.

## சர்க்யூட் பிரேக்கர் சிக்கல்கள்

### வழங்குநர் OPEN நிலையில் சிக்கியுள்ளது

ஒரு வழங்குநரின் சர்க்யூட் பிரேக்கர் OPEN நிலையில் இருக்கும்போது, cooldown காலம் முடியும் வரை கோரிக்கைகள் தடுக்கப்படும்.

**தீர்வு:**

1. **Dashboard → Settings → Resilience** என்பதற்குச் செல்லவும்
2. பாதிக்கப்பட்ட வழங்குநருக்கான சர்க்யூட் பிரேக்கர் அட்டையைச் சரிபார்க்கவும்
3. அனைத்து பிரேக்கர்களையும் அழிக்க **Reset All** என்பதைக் கிளிக் செய்யவும் அல்லது cooldown காலம் முடியும் வரை காத்திருக்கவும்
4. மீட்டமைப்பதற்கு முன் வழங்குநர் உண்மையில் கிடைக்கிறாரா என்பதை உறுதிப்படுத்தவும்

### வழங்குநர் தொடர்ந்து சர்க்யூட் பிரேக்கரைத் தூண்டுகிறது

ஒரு வழங்குநர் மீண்டும் மீண்டும் OPEN நிலைக்குச் சென்றால்:

1. தோல்வி முறையை அறிய **Dashboard → Health → Provider Health** என்பதைச் சரிபார்க்கவும்
2. **Settings → Resilience → Provider Profiles** என்பதற்குச் சென்று தோல்வி வரம்பை அதிகரிக்கவும்
3. வழங்குநர் API வரம்புகளை மாற்றியுள்ளாரா அல்லது மறுஅங்கீகாரம் தேவையா என்பதைச் சரிபார்க்கவும்
4. தாமதத் தொலைஅளவீட்டை மதிப்பாய்வு செய்யவும் — அதிக தாமதம் timeout அடிப்படையிலான தோல்விகளை ஏற்படுத்தக்கூடும்

- வழங்குநர் **Dashboard → Providers** என்பதில் இணைக்கப்பட்டுள்ளாரா என்பதை உறுதிப்படுத்தவும்

### ஒலிப்பெயர்ப்பு வெறுமையாகத் திரும்புகிறது அல்லது தோல்வியடைகிறது

- ஆதரிக்கப்படும் ஆடியோ வடிவங்களைச் சரிபார்க்கவும்: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- கோப்பின் அளவு வழங்குநரின் வரம்புகளுக்குள் உள்ளதா என்பதை உறுதிப்படுத்தவும் (பொதுவாக < 25MB)
- வழங்குநர் அட்டையில் API விசையின் செல்லுபடித்தன்மையைச் சரிபார்க்கவும்

### பொதுவான வடிவமைப்புச் சிக்கல்கள்

- **Thinking குறிச்சொற்கள் தோன்றவில்லை** — இலக்கு வழங்குநர் thinking-ஐ ஆதரிக்கிறாரா என்பதையும் thinking budget அமைப்பையும் சரிபார்க்கவும்
- **கருவி அழைப்புகள் விடுபடுகின்றன** — சில வடிவமைப்பு மொழிபெயர்ப்புகள் ஆதரிக்கப்படாத புலங்களை நீக்கக்கூடும்; Playground பயன்முறையில் உறுதிப்படுத்தவும்
- **System prompt காணவில்லை** — Claude மற்றும் Gemini ஆகியவை system prompt-களை வெவ்வேறு விதமாகக் கையாளுகின்றன; மொழிபெயர்ப்பு வெளியீட்டைச் சரிபார்க்கவும்
- **SDK பொருளுக்குப் பதிலாக மூலச் சரத்தைத் திருப்புகிறது** — v1.x-இல் தீர்க்கப்பட்டது; OpenAI SDK Pydantic சரிபார்ப்புத் தோல்விகளை ஏற்படுத்தும் தரநிலையற்ற புலங்களை (`x_groq`, `usage_breakdown` போன்றவை) பதில் சுத்திகரிப்பான் நீக்குகிறது. v3.x+-இல் இதை இன்னும் கண்டால், தயவுசெய்து சிக்கலைப் பதிவு செய்யவும்.
- **GLM/ERNIE `system` பங்கை நிராகரிக்கிறது** — v1.x-இல் தீர்க்கப்பட்டது; இணக்கமற்ற மாதிரிகளுக்காக பங்கு இயல்பாக்கி, system செய்திகளைத் தானாகவே user செய்திகளுடன் ஒன்றிணைக்கிறது. v3.x+-இல் இதை இன்னும் கண்டால், தயவுசெய்து சிக்கலைப் பதிவு செய்யவும்.
- **`developer` பங்கு அடையாளம் காணப்படவில்லை** — v1.x-இல் தீர்க்கப்பட்டது; OpenAI அல்லாத வழங்குநர்களுக்காக இது தானாகவே `system` ஆக மாற்றப்படுகிறது. v3.x+-இல் இதை இன்னும் கண்டால், தயவுசெய்து சிக்கலைப் பதிவு செய்யவும்.
- **Gemini உடன் `json_schema` செயல்படவில்லை** — v1.x-இல் தீர்க்கப்பட்டது; `response_format` இப்போது Gemini-யின் `responseMimeType` + `responseSchema` ஆக மாற்றப்படுகிறது. v3.x+-இல் இதை இன்னும் கண்டால், தயவுசெய்து சிக்கலைப் பதிவு செய்யவும்.

## மீள்திறன் அமைப்புகள்

### தானியங்கு வீத வரம்பு தூண்டப்படவில்லை

- தானியங்கு வீத வரம்பு API விசை வழங்குநர்களுக்கு மட்டுமே பொருந்தும் (OAuth/சந்தாவுக்குப் பொருந்தாது)
- **Settings → Resilience → Provider Profiles** என்பதில் தானியங்கு வீத வரம்பு இயக்கப்பட்டுள்ளதா என்பதைச் சரிபார்க்கவும்
- வழங்குநர் `429` நிலைக் குறியீடுகள் அல்லது `Retry-After` தலைப்புகளை வழங்குகிறாரா என்பதைச் சரிபார்க்கவும்

### அதிவேகப் பின்னடைவைச் சரிசெய்தல்

வழங்குநர் சுயவிவரங்கள் பின்வரும் அமைப்புகளை ஆதரிக்கின்றன:

- **அடிப்படைத் தாமதம்** — முதல் தோல்விக்குப் பிறகான தொடக்கக் காத்திருப்பு நேரம் (இயல்புநிலை: 1s)
- **அதிகபட்சத் தாமதம்** — அதிகபட்சக் காத்திருப்பு நேர வரம்பு (இயல்புநிலை: 30s)
- **பெருக்கி** — தொடர்ச்சியான ஒவ்வொரு தோல்விக்கும் தாமதத்தை எவ்வளவு அதிகரிப்பது (இயல்புநிலை: 2x)

### ஒரே நேரக் கோரிக்கை வெள்ளத்தைத் தடுத்தல்

வீத வரம்பிடப்பட்ட வழங்குநரைப் பல ஒரேநேரக் கோரிக்கைகள் அணுகும்போது, கோரிக்கைகளைத் தொடர்முறையாக்கவும் தொடர் தோல்விகளைத் தடுக்கவும் OmniRoute mutex + தானியங்கு வீத வரம்பைப் பயன்படுத்துகிறது. API விசை வழங்குநர்களுக்கு இது தானாகவே செயல்படும்.

### அரட்டைக் கோரிக்கைகள் 503 / chat_admission_busy உடன் தோல்வியடைகின்றன

**அறிகுறிகள்:**

- அரட்டை நிறைவு முனைப்புள்ளி, மீண்டும் முயற்சிக்கக்கூடிய `503` பதிலை வழங்குகிறது; அதன் பிழைக் குறியீடு
  `chat_admission_busy`.
- பதிலில் `Retry-After` இடம்பெறும். #12135 முதல், அதன் மதிப்பு கவனிக்கப்பட்ட
  பயன்பாட்டு அளவிலிருந்து பெறப்படுகிறது — கோரிக்கை ஏற்கெனவே காத்திருந்த `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  சாளரம் மற்றும் தற்போதைய கனரகக் குத்தகைகள் வைத்திருக்கப்பட்டுள்ள நேரம் ஆகியவற்றில் பெரியது — முழு
  வினாடிகளாக மேல்நோக்கி வட்டமிடப்பட்டு, 60 என்ற உச்சவரம்புடன் வழங்கப்படும். செயலற்ற நுழைவாயிலில்,
  வரலாற்றுக் குறைந்தபட்சங்கள் தொடர்கின்றன: பைட்-அடிப்படையிலான பாதையில் 2 வினாடிகள்,
  கட்டமைப்பு-அடிப்படையிலான பாதையில் 1 வினாடி (இதில் `reason: "structure_limit"` என்பதும் அடங்கும்).
- மற்றொரு கனரக அரட்டை அல்லது நீண்ட நேரம் இயங்கும் ஸ்ட்ரீமிங் பதில் இன்னும்
  செயல்பாட்டில் இருக்கும்போது இது நிகழலாம்.

பைட்-அடிப்படையிலான பதில் உடல்:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

கட்டமைப்பு-அடிப்படையிலான பதில் அதே வகையையும் குறியீட்டையும் பயன்படுத்துகிறது; அதன் செய்தி
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
என்பதாகவும், `reason: "structure_limit"` என்பதையும் கொண்டிருக்கும்.
இயல்புநிலை வரம்புகளில், ஒரு கோரிக்கையில் குறைந்தது `200` செய்திகள்,
குறைந்தது `64` கருவிகள் அல்லது குறைந்தது `32,000` மதிப்பிடப்பட்ட டோக்கன்கள் இருந்தாலோ, அல்லது வரம்பிடப்பட்ட கட்டமைப்பு மதிப்பீடு
`10,000` பார்வையிடப்பட்ட முனைகள் அல்லது `12` ஆழம் என்ற வரம்புகளைத் தீர்த்துவிட்டாலோ, அது கட்டமைப்பு ரீதியாகக் கனமானதாகக் கருதப்படும்.

**காரணம்:** இது OmniRoute-க்குள் திட்டமிட்டு செய்யப்படும் சுமைக் குறைப்பு; அப்ஸ்ட்ரீம் வழங்குநரின் தோல்வி அல்ல.
பெரிய கோரிக்கை உடலைத் தக்கவைத்து பாகுபடுத்துவதற்கு முன், வரம்பிடப்பட்ட கனரகத் திறனை முன்பதிவு செய்ய ஒவ்வொரு செயல்முறையும் செயல்முறை-உள்ளூர் பாதுகாப்பைப் பயன்படுத்துகிறது.
ஒரு SSE பதிலின் முழு ஆயுட்காலத்திலும் கனரகக் குத்தகை தக்கவைக்கப்படும்.

**#503-விரிவாக்கம்:** இந்தத் திருத்தத்திற்கு முன், புரவலன் நினைவகத்தைப் பொருட்படுத்தாமல் பாதுகாப்பு அமைப்பு ஒரேநேரச் செயல்பாட்டை ஒரு நிலையான கோரிக்கை எண்ணிக்கையில்
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, இயல்புநிலை `1`) கட்டுப்படுத்தியது; எனவே குறியீட்டு முகவர்களின்
விரிவாக்கம் (பல துணைமுகவர்கள்/CLI-கள், வழக்கமாக > 256 KB அளவுள்ள உடல்கள்) நடைமுறை ஒரேநேரச் செயல்பாட்டை
~1 ஆகக் குறைத்து, முற்றிலும் இயல்பான சுமையிலேயே 503 தோல்விகளை ஏற்படுத்தியது. இப்போது பாதுகாப்பு அமைப்பு தானாகச் சீரமைக்கப்படுகிறது: செயல்முறையின் உண்மையான
நினைவக உச்சவரம்பிலிருந்து அளவிடப்படும், தானாகப் பெறப்பட்ட உள்வாங்கல் பைட் ஒதுக்கீட்டால் (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) இது கட்டுப்படுத்தப்படுகிறது;
மேலும் நேரடி வள-அழுத்தச் சமிக்ஞையையும் இது பரிசீலிக்கிறது — ஆகவே ஒரே நேரத்தில் ஒன்றுக்கும் மேற்பட்ட கனரகக் கோரிக்கைகள் வந்ததற்காக அல்லாமல்,
புரவலன் உண்மையாகவே நினைவக அழுத்தத்தில் இருக்கும்போது மட்டுமே இது சுமையைக் குறைக்கும். பழைய எண்ணிக்கை உச்சவரம்பு
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) இன்னும் மதிக்கப்படுகிறது, ஆனால் அதை நீங்கள் வெளிப்படையாக அமைத்தால் மட்டுமே.

திறன் நெரிசலில் இருக்கும்போது, மீண்டும் முயற்சிக்கக்கூடிய `503` பதிலை வழங்குவதற்கு முன், ஒரு இடம் காலியாகும் வரை கனரகக் கோரிக்கை முதலில்
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` வரை காத்திருக்கும் (இயல்புநிலை `RATE_LIMIT_MAX_WAIT_MS`; `0` காத்திருப்பை முடக்கும்).
முகவர்-பாணி கிளையன்ட்கள் (OpenCode, Claude Code, Cursor) கனரகத் துணைக் கோரிக்கைகளை ஒரேநேரத்தில் விரிவாக்கும்போது,
உடனடியாக நிராகரிக்கப்படுவதால் அவற்றின் முழு மறுமுயற்சி ஒதுக்கீட்டையும் வீணாக்கி பணியின் நடுவில் தோல்வியடைவதற்குப் பதிலாக,
அந்தக் கோரிக்கை வெடிப்பைத் தொடர்முறையாக்கவே இந்த வரம்பிடப்பட்ட காத்திருப்பு உள்ளது.
தற்போதைய கனரகக் குத்தகைப் பயன்பாடு, தீர்மானிக்கப்பட்ட பைட் ஒதுக்கீடு மற்றும் நேரடி அழுத்தத் தீவிரம் ஆகியவை
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) என்பதில் காண்பிக்கப்படுகின்றன — எந்தச் சூழல் மாறியையும் மாற்றுவதற்கு முன் இவற்றைச் சரிபார்க்கவும்.
Settings → Resilience → Request Queue → Concurrent Requests இதைக் கட்டுப்படுத்தாது; அந்த அமைப்பு
தனியான வழங்குநர் கோரிக்கை-வரிசை இயங்குமுறையை நிர்வகிக்கிறது.

**தீர்வு:**

1. முதலில் மீண்டும் முயற்சிக்கவும். கோரிக்கையை உடனடியாக மீண்டும் அனுப்புவதற்குப் பதிலாக, கிளையன்ட்கள் `Retry-After`-ஐ மதித்து பின்னடைவைப்
   பயன்படுத்த வேண்டும்.
2. எதையும் சரிசெய்வதற்கு முன் `/api/monitoring/health` → `chatAdmission` என்பதைச் சரிபார்க்கவும். `countCapEnabled:
false` மற்றும் தாராளமான `maxInflightBytes` ஆகியவை, தானாகப் பெறப்பட்ட ஒதுக்கீடு ஏற்கெனவே தனது
   பணியைச் செய்கிறது என்பதைக் குறிக்கும்; `high`/`critical` என்ற `pressureSeverity`, புரவலனில் உண்மையாகவே நினைவகம் குறைவாக உள்ளது என்பதைக் குறிக்கும் —
   இதை அனுமதிப்பு சூழல் மாறியால் சரிசெய்ய முடியாது; கூடுதல் RAM அல்லது சிறிய பணிச்சுமை தேவை.
3. `/api/monitoring/health`, தானாகப் பெறப்பட்ட ஒதுக்கீடு உங்கள்
   புரவலனுக்கு உண்மையாகவே மிகவும் சிறியது என்பதைக் காட்டினால் மட்டுமே (அரிதானது — இது ஏற்கெனவே கொள்கலனிலிருந்து வெறும்-உலோகம் வரை அளவிடப்படுகிறது),
   பழைய கோரிக்கை-எண்ணிக்கை உச்சவரம்புக்கு மாறுவதற்குப் பதிலாக, `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` மூலம் அதை நேரடியாக மீறியமைக்கவும்.

அதிகாரப்பூர்வ அனுமதிப்பு அமைப்புகளுக்கு [சூழல்-மாறி மேற்கோளை](../reference/ENVIRONMENT.md#4-security--authentication)
பார்க்கவும்.

## விருப்பத்தேர்வு RAG / LLM தோல்வி வகைப்பாடு (16 சிக்கல்கள்)

சில OmniRoute பயனர்கள், RAG அல்லது agent அடுக்குகளுக்கு முன்னால் gateway-ஐ அமைக்கிறார்கள். அந்த அமைப்புகளில் ஒரு விசித்திரமான போக்கு பொதுவாகக் காணப்படுகிறது: OmniRoute ஆரோக்கியமாகத் தோன்றுகிறது (providers இயங்குகின்றன, routing profiles சரியாக உள்ளன, rate limit எச்சரிக்கைகள் இல்லை), ஆனால் இறுதிப் பதில் இன்னும் தவறாக இருக்கிறது.

நடைமுறையில், இந்தச் சம்பவங்கள் பொதுவாக gateway-இலிருந்து அல்லாமல், downstream RAG pipeline-இலிருந்தே ஏற்படுகின்றன.

அந்தத் தோல்விகளை விவரிப்பதற்கான பொதுவான சொற்களஞ்சியம் உங்களுக்கு வேண்டுமெனில், WFGY ProblemMap-ஐப் பயன்படுத்தலாம். இது மீண்டும் மீண்டும் ஏற்படும் பதினாறு RAG / LLM தோல்வி வடிவங்களை வரையறுக்கும் வெளிப்புற MIT உரிமம் பெற்ற உரை வளமாகும். உயர்நிலையில் இது பின்வருவனவற்றை உள்ளடக்குகிறது:

- retrieval விலகல் மற்றும் முறிந்த context எல்லைகள்
- காலியான அல்லது காலாவதியான indexes மற்றும் vector stores
- embedding மற்றும் semantic பொருத்தமின்மை
- prompt தொகுப்பு மற்றும் context window சிக்கல்கள்
- logic சிதைவு மற்றும் அளவுக்கு மீறிய நம்பிக்கையுடன் வழங்கப்படும் பதில்கள்
- நீண்ட chain மற்றும் agent ஒருங்கிணைப்புத் தோல்விகள்
- multi-agent memory மற்றும் role விலகல்
- deployment மற்றும் bootstrap வரிசைப்படுத்தல் சிக்கல்கள்

கருத்து எளிமையானது:

1. தவறான பதிலை நீங்கள் ஆராயும்போது, பின்வருவனவற்றைப் பதிவு செய்யவும்:
   - பயனர் பணி மற்றும் கோரிக்கை
   - OmniRoute-இல் பயன்படுத்தப்பட்ட route அல்லது provider combo
   - downstream-இல் பயன்படுத்தப்பட்ட ஏதேனும் RAG context (மீட்டெடுக்கப்பட்ட ஆவணங்கள், tool calls போன்றவை)
2. சம்பவத்தை ஒன்று அல்லது இரண்டு WFGY ProblemMap எண்களுடன் (`No.1` … `No.16`) பொருத்தவும்.
3. OmniRoute logs-க்கு அருகில், உங்கள் சொந்த dashboard, runbook அல்லது incident tracker-இல் அந்த எண்ணைச் சேமிக்கவும்.
4. உங்கள் RAG stack, retriever அல்லது routing strategy-ஐ மாற்ற வேண்டுமா என்பதைத் தீர்மானிக்க, தொடர்புடைய WFGY பக்கத்தைப் பயன்படுத்தவும்.

முழு உரையும் நடைமுறைச் செய்முறைகளும் இங்கே உள்ளன (MIT உரிமம், உரை மட்டும்):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute-க்குப் பின்னால் RAG அல்லது agent pipelines-ஐ நீங்கள் இயக்கவில்லை என்றால், இந்தப் பகுதியைப் புறக்கணிக்கலாம்.

## v3.8.0 அறியப்பட்ட சிக்கல்கள்

v3.8.0 வெளியீட்டுக்கே உரிய சிக்கல்களும் அவற்றுக்கான தற்போதைய மாற்றுத் தீர்வுகளும். பிந்தைய patch-இல் தீர்வு சேர்க்கப்பட்டால், இந்தப் பதிவு புதுப்பிக்கப்படும் அல்லது அகற்றப்படும்.

### Devin CLI அங்கீகாரத் தோல்விகள்

**அறிகுறிகள்:**

- Devin ஆதரவு பெற்ற tools-ஐ அழைக்கும்போது "Devin CLI not found" அல்லது "auth failed"
- CLI runtime சரிபார்ப்பு `installed=false` எனக் காட்டுகிறது

**காரணங்கள்:**

- `CLI_DEVIN_BIN` இல்லாத ஒரு path-ஐச் சுட்டிக்காட்டுகிறது
- host-இல் Devin CLI நிறுவப்படவில்லை

**தீர்வு:**

1. உங்கள் platform-க்கான Devin CLI-ஐ நிறுவவும்
2. `.env`-இல் `CLI_DEVIN_BIN=/usr/local/bin/devin` (அல்லது உண்மையான path) என அமைக்கவும்
3. OmniRoute-ஐ மறுதொடக்கம் செய்து, **Dashboard → CLI Tools**-இலிருந்து மீண்டும் சோதிக்கவும்

### Model cooldown முடங்கியுள்ளது (கைமுறை reset)

**அறிகுறிகள்:**

- காலாவதி நேரம் கடந்த பின்னரும் ஒரு model cooldown நிலையில் பட்டியலிடப்பட்டே இருக்கிறது
- timestamp கடந்த காலத்தில் இருந்தாலும், combo routing அந்த model-ஐத் தொடர்ந்து தவிர்க்கிறது

**கைமுறை reset:**

- **Dashboard:** **Settings → Model Cooldowns** → பாதிக்கப்பட்ட card-இல் **Re-enable** என்பதைக் கிளிக் செய்யவும்
- **API:** management auth headers உடன் `DELETE /api/resilience/model-cooldowns`

### Command Code provider இணைப்பு 403 பிழையுடன் தோல்வியடைகிறது

**அறிகுறிகள்:**

- Command Code provider இணைப்பைச் சோதிக்கும்போது 403
- புதிதாகச் சேர்த்த பிறகு provider card "unauthorized" எனக் காட்டுகிறது

**காரணம்:** OAuth flow நிறைவடையவில்லை (callback பெறப்படவில்லை அல்லது token நிலையாகச் சேமிக்கப்படவில்லை).

**தீர்வு:**

- OAuth flow-ஐ மீண்டும் தொடங்க CLI-இலிருந்து `omniroute providers`-ஐ இயக்கவும், அல்லது
- **Dashboard → Providers → Command Code → Reconnect** என்பதிலிருந்து OAuth-ஐ மீண்டும் இயக்கவும்

### ModelScope தீவிரமான 429 cooldown-களை வழங்குகிறது

**அறிகுறிகள்:**

- சிறிய அளவிலான தொடர்ச்சியான கோரிக்கைகளுக்குப் பிறகு ModelScope-இல் மிகக் குறுகிய அல்லது உடனடி cooldown-கள்
- எதிர்பார்த்ததைவிட முன்பாக combo routing ModelScope-ஐத் தவிர்க்கிறது

**காரணம்:** ModelScope, provider-க்கே உரிய `Retry-After` headers-ஐ வெளியிடுகிறது. v3.8.0, அந்த headers-க்கான பிரத்யேக கையாளுதலுடன் வருகிறது; எனவே பழைய பதிப்புகள் அவற்றைப் பொதுவான rate-limit குறிப்புகளாகத் தவறாகப் புரிந்துகொள்கின்றன.

**தீர்வு:**

- நீங்கள் v3.8.0 அல்லது அதற்குப் பிந்தைய பதிப்பில் இருப்பதை உறுதிப்படுத்தவும்
- **Settings → Resilience** என்பதன் கீழ் `useUpstream429BreakerHints` toggle இயக்கப்பட்டுள்ளதா என்பதைச் சரிபார்க்கவும்

### Production-இல் OMNIROUTE_WS_BRIDGE_SECRET இல்லை

**அறிகுறிகள்:**

- தொலைநிலை production host-இல் இயங்கும்போது ஒவ்வொரு Codex/Responses WebSocket bridge கோரிக்கையிலும் 401
- இணைத்த உடனேயே WebSocket bridge handshake மூடப்படுகிறது

**காரணம்:** production environment-இல் `OMNIROUTE_WS_BRIDGE_SECRET` env var இல்லை.

**தீர்வு:**

1. சீரற்ற secret ஒன்றை உருவாக்கவும்: `openssl rand -hex 32`
2. production server env-இல் (மேலும் bridge உடன் தொடர்புகொள்ளும் எந்த client-இலும்) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` என அமைக்கவும்
3. OmniRoute-ஐ மறுதொடக்கம் செய்யவும்

### Responses API: background mode synchronous நிலைக்குத் தரமிறக்கப்பட்டது

**அறிகுறிகள்:**

- பதிவு செய்யப்பட்ட எச்சரிக்கை: `background mode degraded to synchronous`
- `background: true` கோரிக்கை, background job handle-க்குப் பதிலாக இயல்பான synchronous பதிலை வழங்குகிறது

**காரணம்:** v3.8.0, Responses API-இல் `background: true` என்பதை வேண்டுமென்றே synchronous செயல்பாடாகத் தரமிறக்கி, அதே நேரத்தில் எச்சரிக்கையையும் வெளியிடுகிறது. முழுமையான async background செயல்பாடு எதிர்காலத்தில் வழங்கப்படவுள்ளது.

**தீர்வு:**

- `background` இல்லாமல் அழைக்குமாறு client-ஐச் சரிசெய்யவும், அல்லது
- முழுமையான async background mode உடன் வரும் பிந்தைய வெளியீட்டுக்காகக் காத்திருக்கவும் (changelog-ஐக் கண்காணிக்கவும்)

## மெதுவான தொடக்கம் / தயார்நிலை நேர முடிவு

CLI-ல் `⚠ Server did not respond within 60s` என்று காட்டப்பட்டாலும் சேவையகம்
உண்மையில் இயங்கிக்கொண்டிருந்தால், உங்கள் சூழலுக்கான தயார்நிலைச் சோதனையின் நேர வரம்பு மிகவும் குறைவாக உள்ளது.

இது பொதுவாக Windows-ல் (வைரஸ் தடுப்பு, கோப்பு முறைமை கண்காணிப்பிகள்) அல்லது அதிகமான
தொடக்கப் பணிச்சுமைகளைக் கொண்ட கொள்கலன்களில் நிகழ்கிறது.

**தீர்வு — நேர வரம்பை அதிகரிக்கவும்:**

```bash
# சூழல் மாறி வழியாக (தொடக்கங்களுக்கு இடையிலும் நீடிக்கும்):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 நிமிடங்கள்
omniroute serve

# CLI கொடி வழியாக (ஒரு முறை மட்டும்):
omniroute serve --ready-timeout 180000
```

இயல்புநிலை 60 000 ms (60 s) ஆகும். இந்த எச்சரிக்கை தகவலுக்காக மட்டுமே; சேவையகம்
பின்னணியில் தொடர்ந்து தொடங்கும், மேலும் தொடக்கச் செயல்முறை முடிந்தவுடன் அதை அணுக முடியும்.

`OMNIROUTE_READY_TIMEOUT_MS` குறித்த முழு விவரங்களுக்கு
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md)-ஐப் பார்க்கவும்.
