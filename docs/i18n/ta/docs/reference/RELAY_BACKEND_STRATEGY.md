## சுருக்கம்

OmniRoute இப்போது `/api/v1/relay/chat/completions`-க்கு மூன்று relay முறைகளை ஆதரிக்கிறது:

- `ts`: TypeScript relay-ஐ அதே process-க்குள் பயன்படுத்தும்.
- `bifrost`: Bifrost gateway-ஐ கட்டாயமாகப் பயன்படுத்தும்.
- `auto`: Bifrost கிடைக்கும்போது அதற்கு முன்னுரிமை அளித்து, தோல்வியடைந்தால் TypeScript-க்கு மாறும்.

நீங்கள் அதிக கோரிக்கை விகிதத்தில் (ஒரு நாளுக்கு அதிக எண்ணிக்கையிலான tokens, ஏறத்தாழ தொடர்ச்சியான throughput) இயக்கும்போது, செயல்பாட்டிலுள்ள முக்கிய பாதை செயலிழந்த sidecar-க்காக ஒருபோதும் காத்திருக்காமல் இருக்க, fallback பாதையை வெளிப்படையாகவும் வேகமாகவும் வைத்திருப்பதே சிறந்த உத்தியாகும்.

## முறைகளின் செயல்பாடு

- `ts`
  - மிகக் குறைந்த செயல்பாட்டுச் சிக்கல்.
  - அனைத்து routing மற்றும் validation செயல்களும் Node-இல் இயங்கும்.
  - கிடைப்புத்தன்மைக்கு sidecar சார்பு இல்லை.
- `bifrost`
  - அனைத்து கோரிக்கைகளையும் sidecar gateway வழியாகக் கட்டாயமாக அனுப்பும்.
  - தானியங்கு fallback இல்லை.
  - sidecar-இன் ஆரோக்கியமும் latency-யும் உறுதிசெய்யப்பட்டிருக்கும்போது மட்டுமே பயனுள்ளது.
- `auto`
  - Sidecar-ஐ அணுக முடியும் நிலையிலும் அது இயக்கப்பட்டிருக்கும்போதும் அது பயன்படுத்தப்படும்.
  - தோல்வியடைந்த முயற்சிகள் fallback headers-ஐத் தூண்டி, கோரிக்கையின் வெற்றி வரையறுக்கப்பட்ட எல்லைக்குள் இருப்பதை உறுதிசெய்ய traffic-ஐ TS-க்குத் திருப்பும்.
  - sidecar வழியாக மட்டுமே routing செய்ய வேண்டும் என்ற கடுமையான தேவையைவிட uptime முக்கியமாக இருக்கும் production சூழலுக்கு இந்த முறை மிகவும் பாதுகாப்பான தேர்வாகும்.

## இன்றைய 9router மற்றும் CLIPROXYAPI ஒப்பீடு

9router மற்றும் CLIPROXYAPI இரண்டும், வரலாற்று ரீதியாக upstream providers-க்கான compatibility பாதைகளை வழங்கிய integrations ஆகும்.

- 9router என்பது upstream orchestration மற்றும் compatibility செயல்பாட்டுக்கான உட்பொதிக்கப்பட்ட பாதையாகும்.
- CLIPROXYAPI என்பது CLI / SDK பாணி traffic-க்கான proxy API bridge ஆகும்.
- பிரத்யேக sidecar போன்ற hop மற்றும் குறைந்த latency கொண்ட local dispatch தேவைப்படும்போது பயன்படுத்தக்கூடிய வெளிப்புற பாதையாக Bifrost நிலைப்படுத்தப்பட்டு வருகிறது.

நீங்கள் தற்போது 9router/CLIPROXYAPI-ஐ ஒப்பிட்டுக் கொண்டிருந்தால்:

- ஒப்படைப்பதற்கு முன் request signing, allowlist checks மற்றும் DB policy gates ஆகியவற்றை API route-இல் வைத்திருங்கள்.
- ஒரு workflow-க்கு கடுமையான sidecar செயல்பாடும் ஒவ்வொரு கோரிக்கைக்குமான குறைந்த variance-உம் தேவைப்பட்டால், `OMNIROUTE_RELAY_BACKEND=bifrost`-ஐப் பயன்படுத்தவும்.
- incident சூழ்நிலைகளில் படிப்படியான செயல்திறன் குறைப்புடன் கூடிய sidecar resilience தேவைப்பட்டால், `OMNIROUTE_RELAY_BACKEND=auto`-ஐப் பயன்படுத்தவும்.

## Backend எல்லை ஒப்பந்தம்

நிலையான தயாரிப்பு எல்லை என்பது OmniRoute relay API ஆகும்; dashboard செயலாக்கம் அல்ல. Next.js dashboard உள்ளூர் services-ஐ நிறுவலாம், உள்ளமைக்கலாம் மற்றும் மேற்பார்வையிடலாம்; ஆனால் request routing என்பது relay API வழியாக நுழைந்து, அந்த எல்லைக்குப் பின்னால் ஒப்படைக்கப்பட வேண்டும்.

நீண்டகால backend தேர்வுகள்:

- TypeScript relay-ஐ அதே process-க்குள் செயல்படும் policy மற்றும் fallback பாதையாக வைத்திருங்கள். எந்தவொரு backend ஒப்படைப்புக்கும் முன் Auth, allowlists, request normalization, accounting மற்றும் safety checks ஆகியவை இங்கேயே இருக்கும்.
- deployment-க்கு குறைந்த routing variance, மையப்படுத்தப்பட்ட provider rotation அல்லது பல OmniRoute replicas முழுவதும் scale-out தேவைப்படும்போது, Bifrost-ஐ முன்னுரிமைக்குரிய உயர்-throughput Tier-1 sidecar ஆகப் பயன்படுத்தவும்.
- 9router மற்றும் CLIPROXYAPI-ஐ உட்பொதிக்கப்பட்ட compatibility services ஆக வைத்திருங்கள். அவை மேற்பார்வையிடப்படும் உள்ளூர் processes ஆக இயங்குகின்றன; அவற்றின் provider/CLI செயல்பாடே விரும்பப்படும் adapter ஆக இருக்கும்போது அவை பயனுள்ளவை. ஆனால் அவை இயல்புநிலை Tier-1 routing engine ஆக மாறக்கூடாது.
- செயல்பாட்டிலுள்ள முக்கிய பாதைக்குள் dashboard தன்னிச்சையான service URLs-ஐ அனுப்ப அனுமதிக்காதீர்கள். UI வழங்கும் URLs என்பது configuration inputs ஆகும்; routing code ஆனது server-side settings மற்றும் supervisor state ஆகியவற்றிலிருந்து பதிவுசெய்யப்பட்ட, ஆரோக்கியம் சரிபார்க்கப்பட்ட backends-ஐத் தேர்ந்தெடுக்க வேண்டும்.
- மேற்பார்வையிடப்படும் processes ஏற்கெனவே HTTP-compatible APIs-ஐ வழங்குவதாலும், route guard எல்லையைத் தணிக்கை செய்ய முடிவதாலும், தோல்வி/fallback செயல்பாடு request logs-இல் காணப்படுவதாலும், தற்போது மேற்பார்வையிடப்படும் services-க்கு loopback HTTP-க்கு முன்னுரிமை அளிக்கவும். isolation அல்லது fallback semantics-ஐப் பலவீனப்படுத்தாமல் p99 routing latency-ஐ அளவிடத்தக்க வகையில் குறைத்தால் மட்டுமே எதிர்கால SDK அல்லது socket transport-ஐச் சேர்ப்பது பயனுள்ளதாக இருக்கும்.

எனவே, மிக அதிக throughput கொண்ட deployment-க்கு Bifrost இயக்கப்பட்ட `auto` என்பதே இயல்புநிலை பதிலாகும்: வெற்றி விகிதத்திற்காக TypeScript fallback-ஐப் பாதுகாத்துக்கொண்டே, செயல்பாட்டிலுள்ள முக்கிய பாதையில் Go sidecar-ஐப் பயன்படுத்தவும். படிப்படியான செயல்திறன் குறைப்பைவிட sidecar வழியாக மட்டுமே செயல்பட வேண்டும் என்ற கடுமையான தேவை முக்கியமாக இருந்தால் மட்டுமே `bifrost`-ஐப் பயன்படுத்தவும்.

## உயர்-throughput வழிகாட்டுதல்

நீடித்த உயர் RPM/RPS மற்றும் கடுமையான வெற்றி SLO-க்கு:

1. நடைமுறைக்கு ஏற்ற cooldown மற்றும் failure telemetry-யுடன் `auto`-ஐப் பயன்படுத்தவும்.
2. upstream validation மற்றும் API-key checks ஆகியவற்றை TypeScript route எல்லையில் வைத்திருங்கள்.
3. உங்கள் alerting அமைப்பு fallback நிகழ்வு விகிதத்தையும் காரணங்களையும் கண்டறிய, வெளிப்படையான headers/counters-ஐ இயக்கவும்.
4. எப்போதும் காத்திருப்பதற்குப் பதிலாக விரைவாகத் தோல்வியடையும் வகையில் sidecar timeouts-ஐச் சரிசெய்யவும்.
5. fallback உண்மையிலேயே விதிவிலக்கான நிகழ்வாக இருக்க, service auto-restart மற்றும் health telemetry loop ஆகியவற்றை ஆரோக்கியமான நிலையில் வைத்திருங்கள்.

## பரிந்துரைக்கப்படும் அடிப்படை அமைப்பு

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- API keys, allowlist, sanitizer மற்றும் rate-limit checks ஆகியவற்றை route handlers-இல் இயக்கப்பட்ட நிலையில் வைத்திருங்கள் (downstream forwarding-க்கு முன் அவை எப்போதும் இயங்கும்).
- sidecar செயலிழப்புகள் ஒரு நிமிடத்திற்குள் தெரியும்படி, உங்கள் reverse proxy மற்றும் request logs-இலிருந்து fallback metrics-ஐ export செய்யவும்.
