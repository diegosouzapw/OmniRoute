ரிலேக்கள் (Vercel, Deno, Cloudflare), serverless backend ஒன்றில் upstream இணைப்பை முடித்து, provider API key-ஐ server-side-ல் வைத்துக்கொண்டே OmniRoute ஒரு நிலையான region-இலிருந்து வெளியேறும் போக்குவரத்தை அனுப்ப அனுமதிக்கின்றன. உற்பத்திச் சூழலில் operators எதிர்கொள்ளும் இரண்டு தோல்வி நிலைகளையும், ஒவ்வொன்றிற்கும் OmniRoute வழங்கும் மீட்பு வழிமுறைகளையும் இந்த ஆவணம் விளக்குகிறது.

## ரிலே அங்கீகாரம் எவ்வாறு சேமிக்கப்படுகிறது

**Settings → Proxy Pool → Deploy Relay** என்பதிலிருந்து ஒரு ரிலேவை deploy செய்யும்போது, deploy செயல்முறை ரிலேவின் அங்கீகார token-ஐ proxy-யின் `notes` JSON புலத்தில் சேமிக்கிறது:

- `STORAGE_ENCRYPTION_KEY` அமைக்கப்பட்டிருந்தால், token `relayAuthEnc` ஆக எழுதப்படும்
  (சேமிப்பில் AES மூலம் குறியாக்கப்பட்டது).
- இல்லையெனில், அது plaintext `relayAuth` ஆக எழுதப்படும்.

கோரிக்கை நேரத்தில், `extractRelayAuth(notes)` கிடைக்கக்கூடிய எந்த வடிவத்தையும் திருப்பித் தருவதால், மறுதொடக்கங்களுக்குப் பிறகும் ரிலே தொடர்ந்து செயல்படும்.

## தோல்வி நிலை 1 — key rotation-க்குப் பிறகு குறிவிலக்க முடியாத token

**அறிகுறி:** முன்பு செயல்பட்ட ரிலேக்கள், environment அல்லது secret-manager-இல் `STORAGE_ENCRYPTION_KEY` மாற்றப்பட்ட பிறகு upstream `401`/அங்கீகாரப் பிழைகளை வழங்குகின்றன. சேமிக்கப்பட்ட `relayAuthEnc` blob-ஐ இனி குறிவிலக்க முடியாததால், `extractRelayAuth` வெற்று string-ஐ திருப்பித் தருகிறது; இதன் விளைவாக ரிலே எந்த அங்கீகாரத்தையும் அனுப்பாது.

**மீட்பு — redeploy செய்யாமல் அதே இடத்தில் பழுதுபார்த்தல்:**

1. **Settings → Proxy Pool** என்பதைத் திறக்கவும்.
2. அங்கீகாரம் இல்லாத ரிலே வரிசைகளில் மஞ்சள் நிற `auth missing` badge மற்றும்
   **Repair** பொத்தான் காட்டப்படும்.
3. **Repair** என்பதைக் கிளிக் செய்யவும். OmniRoute,
   `POST /api/settings/proxies/[id]/repair-relay` என்பதை அழைக்கும்; இது:
   - **தற்போதைய** key-ஐப் பயன்படுத்தி `relayAuthEnc`-ஐ குறிவிலக்கும்,
   - plaintext `relayAuth`-ஐ மீண்டும் `notes`-இல் எழுதும்,
   - `{ repaired: true, mode: "recovered" }` என்பதைத் திருப்பித் தரும்.

எந்த deploy சான்றுகளையும் மீண்டும் உள்ளிடாமல் ரிலே சேவை வழங்குவதைத் தொடரும்.

தற்போதைய `STORAGE_ENCRYPTION_KEY`-ஆல் blob-ஐ இன்னும் குறிவிலக்க முடிந்தால் மட்டுமே இது செயல்படும். migration செய்யாமல் key-ஐ மாற்றியிருந்தால், blob-ஐ மீட்டெடுக்க முடியாது.

## தோல்வி நிலை 2 — மீட்டெடுக்க முடியாத token (பழைய key இனி இல்லை)

**அறிகுறி:** நீங்கள் **Repair** என்பதைக் கிளிக் செய்தபோது
`{ repaired: false, mode: "redeploy", status: 409 }` கிடைத்தது.

**மீட்பு — மீண்டும் deploy செய்தல்:**

சேமிக்கப்பட்ட token-ஐ தற்போதைய key மூலம் மீட்டெடுக்க முடியாது. ஆரம்பத்தில் பயன்படுத்திய அதே modal-இலிருந்து ரிலேவை மீண்டும் deploy செய்யவும் (**Deploy Relay** menu → Vercel / Deno / Cloudflare). deploy செயல்முறை ஒரு புதிய token-ஐ எழுதும் (தற்போதைய key மூலம் குறியாக்கப்பட்டு), பின்னர் அந்த வரிசையின் `auth missing` badge மறையும்.

token-ஐ மீட்டெடுக்க முடியாதபோது, UI-யிலுள்ள **Repair** பொத்தானே redeploy modal-ஐத் திறக்கும்; எனவே அதை நீங்கள் கைமுறையாகத் தேட வேண்டியதில்லை.

## தோல்வி நிலை 3 — ரிலேவை அணுக முடிந்தாலும் அது ஆரோக்கியமாக இல்லை

**அறிகுறி:** proxy சோதனை (`speed` பொத்தான்) ரிலே இயங்குவதாகக் காட்டினாலும், கோரிக்கைகள் இடையிடையே தோல்வியடைகின்றன.

OmniRoute-இன் தானியங்கு சோதனை probe வழங்கும் ரிலே விழிப்புணர்வு headers-ஐச் சரிபார்க்கவும்
(**Settings → Proxy Pool** மற்றும் `relayTested` / `relayAlive` counters-ஐப் பார்க்கவும்):

- `x-relay-url` — பதிலளித்த ரிலே backend எது.
- `x-relay-mode` — அந்தக் கோரிக்கைக்கான `ts` | `bifrost` | `auto`.
- `x-relay-attempts` — வெற்றிக்கு முன் எத்தனை ரிலே hops முயற்சிக்கப்பட்டன.
- `x-relay-fallback` — விருப்பமான backend-இலிருந்து TypeScript ரிலேவுக்கு கோரிக்கை
  fallback ஆனபோது `true`.

குறைந்த `relayAlive` உடன் அதிகமான `x-relay-fallback` விகிதம் இருந்தால், sidecar backend ஆரோக்கியமாக இல்லை என்று பொருள். அதைச் சரிசெய்ய வேண்டும் அல்லது ரிலே backend strategy-ஐ `ts`-க்கு மாற்ற வேண்டும் (`RELAY_BACKEND_STRATEGY.md`-ஐப் பார்க்கவும்).

## API குறிப்பு

| முறை   | பாதை                                      | Body                    | வெற்றி                                                                                                                                 | தோல்வி                                                                                                       |
| ------ | ----------------------------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | மீண்டும் பெறப்பட்டால் `200 { repaired: true, mode: "recovered" }`; plaintext ஏற்கனவே இருந்தால் `200 { repaired: false, mode: "noop" }` | மீட்டெடுக்க முடியாவிட்டால் `409 { mode: "redeploy" }`; ரிலே வகை இல்லையெனில் `400`; காணப்படவில்லை எனில் `404` |

பட்டியல் route ஆன `GET /api/settings/proxies`, ஒவ்வொரு item-க்கும் ரகசியத் தகவல்கள் இல்லாத `relayInfo: { isRelay, authMissing, repairMode }` என்பதை இணைக்கிறது. இதனால் token-ஐ ஒருபோதும் வெளிப்படுத்தாமல் dashboard பழுதுபார்க்கும் வசதியைக் காட்ட முடியும்.
