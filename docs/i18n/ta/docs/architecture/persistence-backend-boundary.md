- **நிலை:** முன்மொழியப்பட்டது — இயக்கநேரப் பணிகள் தொடங்குவதற்கு முன் பராமரிப்பாளர் ஒப்புதல் தேவை
- **கண்காணிப்புச் சிக்கல்:** [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075)
- **வரம்பு:** நிலைபேறாக்கக் கட்டமைப்பு மட்டும்; இந்த முடிவு வெளிப்புற தரவுத்தளத்தைச் சேர்க்கவோ தேர்ந்தெடுக்கவோ இல்லை

## சூழல்

OmniRoute தற்போது `src/lib/db/` இலிருந்து களம் சார்ந்த நிலைபேறாக்கச் செயல்பாடுகளை வழங்குகிறது; அதே நேரத்தில்,
`src/lib/db/core.ts` வழங்கும் பகிரப்பட்ட இணைப்பு, `src/lib/db/adapters/types.ts` இல் உள்ள ஒத்தியக்க
`SqliteAdapter` ஒப்பந்தத்தைச் செயல்படுத்துகிறது. அந்த அடாப்டர் பல SQLite இயக்கநேரங்களை ஆதரித்தாலும், அதன்
இடைமுகம் SQLite வடிவிலேயே உள்ளது: ஒத்தியக்கத் தயார் செய்யப்பட்ட கூற்றுகள், `pragma`, ஒத்திவைக்கப்பட்ட மற்றும் உடனடிப்
பரிவர்த்தனைகள், சொந்த/கோப்பு-நகல் காப்புப்பிரதி, சோதனைப்புள்ளி, மற்றும் உள்ளூர் தரவுத்தளக் கைப்பிடி.

தற்போதைய தொடக்க மற்றும் மீட்புப் பாதை SQLite கோப்பின் வாழ்நிலையையும் நிர்வகிக்கிறது. `src/lib/db/core.ts`
`storage.sqlite` ஐத் தீர்மானித்து, செயல்முறை முழுவதற்குமான ஓர் அடாப்டரைப் பராமரித்து, WAL-க்கு சோதனைப்புள்ளி அமைத்து, மீட்பின்போது
தேர்ந்தெடுக்கப்பட்ட அட்டவணைகளைப் பாதுகாத்து, தரவுத்தளத்தை மீண்டும் உருவாக்கும்போது SQLite துணைக் கோப்புகளை அகற்றுகிறது. இயக்கி
தேர்வு, `src/lib/db/adapters/driverFactory.ts` இல் ஆதரிக்கப்படும் SQLite இயக்கநேரங்களில் ஒன்றைத் தேர்ந்தெடுக்கிறது; அது
வெளிப்புறப் பின்தளச் சுருக்கம் அல்ல.

திட்டவடிவ வளர்ச்சியும் இதேபோல் இறுக்கமாகப் பிணைக்கப்பட்டுள்ளது. `src/lib/db/migrationRunner.ts` எண்ணிடப்பட்ட SQL கோப்புகளைப்
பயன்படுத்தி, `sqlite_master` மற்றும் `PRAGMA table_info` ஆகியவற்றைச் சோதித்து, விருப்பமான FTS5 ஆதரவைக் கண்டறிந்து, இடம்பெயர்வுப்
பணிகளை SQLite பரிவர்த்தனைகளில் இயக்குகிறது. `src/lib/db/backup.ts` மற்றும்
`src/lib/db/optimizationSettings.ts` போன்ற செயல்பாட்டு தொகுதிகள் காப்புப்பிரதி, `PRAGMA`, WAL, பக்க அளவு,
தானியங்கி வெற்றிடமாக்கல் மற்றும் `VACUUM` சொற்பொருளியலை நேரடியாகப் பயன்படுத்துகின்றன.

இவை உட்பொதிக்கப்பட்ட SQLite நிறுவலின் செல்லுபடியாகும் பண்புகள். PostgreSQL அல்லது MySQL-ஐ SQLite API-ஐப்
போலச் செயல்படுமாறு கட்டாயப்படுத்தாமல், இவை தொடர்ந்து கிடைக்க வேண்டும்.

## முடிவு

எளிதில் மாற்றியமைக்கக்கூடிய நீடித்த நிலைக்காக இருநிலை நிலைபேறாக்க எல்லையை ஏற்கவும்:

1. **களக் களஞ்சிய ஒப்பந்தங்கள்**, வணிக மற்றும் வழிப்படுத்தல் குறியீட்டிற்குத் தேவையான நிலைபேறாக்கச் செயல்பாடுகளை
   வரையறுக்கின்றன. அழைப்பாளர்கள் SQL உரை, தயார் செய்யப்பட்ட கூற்றுகள், தரவுத்தளக் கோப்புகள் அல்லது வட்டார மொழி பொருள்களைச்
   சார்ந்திருக்காமல், கள நடத்தை மற்றும் களத் தரவைச் சார்ந்திருப்பார்கள்.
2. **ஓர் உள் ஒத்தியங்கா பின்தள ஒப்பந்தம்**, பரிவர்த்தனைச் சூழல்கள், ஆரோக்கியம்/தயார்நிலை, இடம்பெயர்வு ஒருங்கிணைப்பு, பின்தளத்
   திறன்கள் மற்றும் வகைப்படுத்தப்பட்ட பிழைகள் ஆகியவற்றுடன் களஞ்சியச் செயலாக்கங்களை ஆதரிக்கிறது. துல்லியமான TypeScript இடைமுகம்
   முதல் செயலாக்க PR உடன் முன்மொழியப்பட்டு, இணக்கச் சோதனைகளால் நிரூபிக்கப்படும்; இந்த ADR ஊகத்தின் அடிப்படையிலான API ஒன்றை
   வேண்டுமென்றே நிலைநிறுத்தவில்லை.

SQLite இயல்புநிலைச் செயலாக்கமாகத் தொடர்கிறது. களங்கள் சிறிய செங்குத்துத் துண்டுகளாக இடம்பெயர்க்கப்படும்போது, தற்போதுள்ள SQLite
இயக்கி அடுக்குத் தேர்வும் ஒத்தியக்க `SqliteAdapter` உம் SQLite களஞ்சியச் செயலாக்கத்திற்குப் பின்னால் தொடர்ந்து இருக்கும்.
எந்தப் பயனரும் வெளிப்புறச் சேவையை உள்ளமைக்க வேண்டியதில்லை.

SQLite-க்கு எதிராக களஞ்சிய எல்லை நிரூபிக்கப்பட்ட பிறகு, PostgreSQL முதலாவது முன்மொழியப்பட்ட வெளிப்புறச் செயலாக்கமாகும்.
MySQL, இரண்டாவது வணிக-தர்க்கப் பிரிவாக அல்லாமல், அதே இணக்கத் தொகுப்பிற்கு எதிரான இணைச் செயலாக்கமாக அதைத் தொடரும்.

## எல்லை விதிகள்

### மாற்றியமைக்கக்கூடிய களஞ்சிய இடைமுகம்

மாற்றியமைக்கக்கூடிய களஞ்சியம் பின்வருவனவற்றை வழங்கலாம்:

- கள வாசிப்புகள் மற்றும் எழுதுதல்கள்;
- வெளிப்படையான அணுச் செயல்பாடுகள் மற்றும் பரிவர்த்தனை வரம்பிற்குட்பட்ட களஞ்சிய அணுகல்;
- ஒருங்குநிகழ்வுச் சொற்பொருளியல் களத்தின் ஒரு பகுதியாக இருக்கும் இடங்களில் ஒப்பீடு/புதுப்பித்தல் அல்லது குத்தகைச் செயல்பாடுகள்;
- பின்தளச் சார்பற்ற பக்கமாக்கல், வரிசைப்படுத்தல் மற்றும் கட்டுப்பாட்டுப் பிழைகள்.

பின்தள ஆரோக்கியம், தயார்நிலை மற்றும் இடம்பெயர்வு ஒருங்கிணைப்பு ஆகியவை தனிப்பட்ட களக் களஞ்சியங்களுக்கு அல்லாமல்,
உள் பின்தள/செயல்பாட்டு ஒப்பந்தத்தைச் சேர்ந்தவை.

மாற்றியமைக்கக்கூடிய களஞ்சியம் பின்வருவனவற்றை வழங்கக்கூடாது:

- `prepare`, `get`, `all`, `run` அல்லது மூல இயக்கிக் கைப்பிடிகள்;
- `PRAGMA`, WAL சோதனைப்புள்ளி முறைகள், `VACUUM` அல்லது பக்கம்/தற்காலிகச் சேமிப்பகச் சீரமைப்பு;
- SQLite கோப்புப் பாதைகள், துணைக் கோப்புகள் அல்லது கோப்பு-நகல் காப்புப்பிரதி;
- பின்தளங்களுக்கிடையேயான கள ஒப்பந்தமாக `lastInsertRowid`;
- FTS5 அல்லது `sqlite-vec` தொடரியல்;
- வழக்கமான வணிகக் குறியீடு பயன்படுத்தும் பொதுவான வட்டார மொழித் தப்புவழி.

### பின்தளத் திறன் இடைமுகம்

பின்தளம் சார்ந்த நடத்தை வெளிப்படையாகவும் எளிதில் கண்டறியக்கூடியதாகவும் தொடர்கிறது. SQLite-க்கு மட்டுமான பராமரிப்பு,
அதற்கே உரிய செயலாக்கம் மற்றும் செயல்பாட்டு இடைமுகத்திற்குப் பின்னால் இருக்கும்; அவற்றில் பின்வருவன அடங்கும்:

- இயக்கநேர இயக்கித் தேர்வு;
- WAL சோதனைப்புள்ளி மற்றும் SQLite பணிநிறுத்த நடத்தை;
- பக்க அளவு, தற்காலிகச் சேமிப்பக அளவு மற்றும் தானியங்கி வெற்றிடமாக்கல் அமைப்புகள்;
- தரவுத்தளக் கோப்புக் காப்புப்பிரதி, மீட்டமைப்பு மற்றும் மீட்பு;
- SQLite திட்டவடிவ ஆய்வு;
- FTS5 மற்றும் `sqlite-vec` ஒருங்கிணைப்பு.

வெளிப்புறப் பின்தளம் அந்த அம்சங்களைப் போலச் செயல்பட வேண்டியதில்லை. களஞ்சியங்கள் மாற்றியமைக்கக்கூடிய திறனைப் பயன்படுத்த வேண்டும்,
அல்லது ஆவணப்படுத்தப்பட்ட நடத்தையைக் கொண்ட பின்தளம் சார்ந்த செயலாக்கத்தை வழங்க வேண்டும், அல்லது ஒரு திறன் கிடைக்கவில்லை என்று
தெரிவிக்க வேண்டும்.

## பரிவர்த்தனை மற்றும் இடம்பெயர்வு மாதிரி

Repository API-கள் அணுக்கமான வணிகச் செயல்பாட்டை வரையறுக்கின்றன; அழைப்பாளர்கள் SQL பரிவர்த்தனை முறையைத் தேர்ந்தெடுப்பதில்லை.
ஒவ்வொரு செயல்பாடும் அதன் வெளிப்படையாகக் காணக்கூடிய ஒருங்குநிகழ்வு உத்தரவாதங்களை வரையறுக்க வேண்டும்: பாதுகாக்கப்பட்ட மாறாத விதிகள், முரண்பாடு
கண்டறிதல், மறுமுயற்சி வகைப்பாடு, idempotency எதிர்பார்ப்புகள் மற்றும் பரிவர்த்தனைச் சூழல் பரவல்.
அந்த வெளிப்படையாகக் காணக்கூடிய உத்தரவாதங்கள் சமமாக இருக்கும் பட்சத்தில் மட்டுமே செயலாக்கங்கள் வெவ்வேறு பரிவர்த்தனை மற்றும் தனிமைப்படுத்தல் வழிமுறைகளைப் பயன்படுத்தலாம்.
செயல்பாட்டின் ஒப்பந்தத்தை நிறைவேற்றும் இடங்களில் SQLite தனது தற்போதைய deferred அல்லது immediate
பரிவர்த்தனை நடத்தையை அகநிலையில் தொடர்ந்து பயன்படுத்தலாம்.

பல பயன்பாட்டு replica-க்கள் ஒரே schema மாற்றத்திற்காகப் போட்டியிட முடியாதவாறு, வெளிப்புற backend-களுக்கு வெளிப்படையான இடம்பெயர்வு உரிமையாண்மை தேவை.
Backend இடம்பெயர்வு வரலாறுகள் தர்க்கரீதியான மைல்கற்களைப் பகிரலாம், ஆனால் SQLite SQL
கோப்புகள் மற்றொரு dialect-க்கு எடுத்துச் செல்லக்கூடியவை அல்லது மறுபயன்படுத்தக்கூடியவை என்று கருதப்படுவதில்லை.

## Backend-களுக்கு இடையேயான இணக்கச் சொற்பொருளியல்

இணக்கச் சோதனைகள் repository முறைமைகளின் கையொப்பங்களை மட்டுமல்லாமல் நடத்தையையும் உள்ளடக்க வேண்டும். இடம்பெயர்க்கப்பட்ட ஒவ்வொரு domain-மும்
பின்வருவனவற்றை வரையறுத்துச் சரிபார்க்க வேண்டும்:

- timestamp நேர மண்டலம், துல்லியம் மற்றும் serialization;
- `NULL` வரிசைப்படுத்தல், collation மற்றும் எழுத்துப் பெட்டி உணர்திறன் எதிர்பார்ப்புகள்;
- JSON பிரதிநிதித்துவம் மற்றும் ஒப்பீட்டு நடத்தை;
- முழு எண், தசம எண் மற்றும் பண மதிப்புகளின் துல்லியம்;
- pagination-க்கான நிலையான வரிசைப்படுத்தலும் தீர்மானகரமான சமநிலை முறிப்பான்களும்;
- SQLite row ID-களைச் சாராத ID உருவாக்கம்;
- uniqueness மற்றும் foreign-key மீறல் வகைப்பாடு;
- எந்த மாற்றமும் இல்லாத, compare/update மற்றும் delete செயல்பாடுகளுக்கான பாதிக்கப்பட்ட-row நடத்தை;
- ஒருங்குநிகழ் எழுதுதல்களின் விளைவுகள், மறுமுயற்சி செய்யக்கூடிய முரண்பாடுகள் மற்றும் idempotent மறுமுயற்சிகள்.

ஒரு domain-ஆல் சமமான வெளிப்படையாகக் காணக்கூடிய சொற்பொருளியலைக் குறிப்பிட முடியாவிட்டால், அது இன்னும் எடுத்துச் செல்லக்கூடியது அல்ல; அந்த ஒப்பந்தம் வடிவமைக்கப்படும் வரை அது
backend-க்கே உரியதாக இருக்க வேண்டும்.

## இணக்கத்தன்மைத் தேவைகள்

இந்த ADR-ஐப் பின்பற்றும் எந்தவொரு செயலாக்கமும் பின்வரும் பண்புகளைப் பாதுகாக்க வேண்டும்:

- SQLite எந்த உள்ளமைவும் தேவையில்லாத இயல்புநிலையாகத் தொடர்கிறது.
- ஏற்கெனவே உள்ள SQLite கோப்புகளும் இடம்பெயர்வு வரலாறும் தொடர்ந்து வாசிக்கக்கூடியவையாக இருக்கின்றன.
- npm, Electron, Docker மற்றும் கட்டுப்படுத்தப்பட்ட runtime SQLite fallback-கள் அவற்றின் தற்போதைய தொடக்கப் பாதையைத் தக்கவைக்கின்றன.
- சேமிக்கப்பட்ட provider சான்றுகள் ஏற்கெனவே உள்ள பயன்பாட்டு encryption நடத்தையையே தொடர்ந்து பயன்படுத்துகின்றன.
- ஒரு repository இடம்பெயர்வு routing, quota, API-key அல்லது audit சொற்பொருளியலை மறைமுகமாக மாற்றாது.
- காப்புப்பிரதி மற்றும் மீட்பு நடத்தை அனைத்துக்கும் பொதுவானதாகக் காட்டப்படாமல், ஒவ்வொரு backend-க்கும் தனித்தனியாக ஆவணப்படுத்தப்படுகிறது.
- SQLite மட்டுமே கொண்ட ஒரு சுத்தமான நிறுவல் வெளிப்புற database driver-ஐ ஏற்றவோ தேவைப்படவோ செய்யாது.

## வழங்கல் வரிசை

1. மீளுருவாக்கக்கூடிய SQLite சார்பு விவரப்பட்டியலை ஒரு தனியான மதிப்பாய்வுக் கலைப்பொருளாக வெளியிடவும்.
2. முதல் domain repository ஒப்பந்தங்களையும் இணக்கச் சோதனைகளையும் அறிமுகப்படுத்தவும்.
3. இயல்புநிலைகளை மாற்றாமல், ஏற்கெனவே உள்ள SQLite செயலாக்கத்தை அந்த ஒப்பந்தங்களுக்குப் பின்னால் தகவமைக்கவும்.
4. பராமரிப்பாளர் ஒப்புதலுக்கு உட்பட்டு, வரம்பிடப்பட்ட ஒரு control-plane பகுதிக்கான முதல் வெளிப்புற செயலாக்கமாக PostgreSQL-ஐச் சேர்க்கவும்.
5. ஒருங்குநிகழ் எழுதுதல் மற்றும் இடம்பெயர்வு உரிமையாண்மைச் சோதனைகள் உருவான பின்னரே பகிரப்பட்ட நிலையை விரிவுபடுத்தவும்.
6. database மாற்றத்தை விளம்பரப்படுத்துவதற்கு முன், offline-ஆக இயங்கும், சரிபார்க்கப்பட்ட SQLite-இலிருந்து வெளிப்புற backend-க்கான இடம்பெயர்வுப் பாதையைச் சேர்க்கவும்.
7. நிரூபிக்கப்பட்ட repository மற்றும் backend ஒப்பந்தங்களுக்கு ஏற்ப MySQL-ஐச் சேர்க்கவும்.

ஒவ்வொரு runtime படியும் தனியான, மதிப்பாய்வு செய்யக்கூடிய PR ஆகும். முந்தைய படியில் நிரூபிக்கப்படாத ஓர் abstraction-ஐ merge செய்வதை நியாயப்படுத்தப் பிந்தைய படியைப் பயன்படுத்தக் கூடாது.

## முதல் செயலாக்கத் துண்டு

இணைப்புச் சார்புகளின் பட்டியல் மதிப்பாய்வு செய்யப்பட்ட பிறகு முதல் இயக்கநேரத் துண்டு தேர்ந்தெடுக்கப்பட வேண்டும். வழங்குநர்
இணைப்புகள், API விசைகள், சேர்க்கைகள் மற்றும் வழித்தட உள்ளமைவு ஆகியவை சாத்தியமான தேர்வுகள்; ஏனெனில் அவற்றின் அடிப்படை அட்டவணைகள்
`src/lib/db/core.ts`-இல் காணப்படுகின்றன. ஆனால் இந்த ADR எந்த அட்டவணைப் பட்டியலையோ இடம்பெயர்வு PR-ஐயோ அங்கீகரிக்கவில்லை.
அந்தத் துண்டில் பின்வருவன கட்டாயம் இடம்பெற வேண்டும்:

- SQLite நடத்தையைப் பாதுகாக்கும் சோதனைகள்;
- களஞ்சிய ஒத்திசைவுச் சோதனைகள்;
- வெளிப்படையான பரிவர்த்தனை எல்லைகள்;
- சேமிக்கப்பட்ட நற்சான்றுகளுக்கான குறியாக்கம் மற்றும் மறைத்தல் சரிபார்ப்பு;
- இயல்புநிலை தொடக்க உள்ளமைவில் எந்த மாற்றமும் இல்லாமை.

## பரிசீலிக்கப்பட்ட மாற்று வழிகள்

### `SqliteAdapter`-இன் கீழ் PostgreSQL-ஐச் சேர்த்தல்

நிராகரிக்கப்பட்டது. `SqliteAdapter` என்பது SQLite இயக்கநேரங்களுக்கான இணக்கத்தன்மை அடுக்கு; இது SQLite-க்கே உரிய
செயல்பாடுகளை வெளிப்படுத்துகிறது. அந்த இடைமுகத்தைப் போலச் செயல்படச் செய்வது ஒத்திசைவு மற்றும் தரவுத்தள வழக்குமொழி சார்ந்த அனுமானங்களைப்
புதிய பின்தளத்துக்குள் கசியவிடும்.

### அனைத்து களங்களுக்கும் பொதுவான query/execute API-ஐ வெளிப்படுத்துதல்

முதன்மை எல்லையாக நிராகரிக்கப்பட்டது. இது இணைப்புக் கையாளுதலை மையப்படுத்தும்; ஆனால் SQL வழக்குமொழி,
பரிவர்த்தனை மற்றும் அட்டவணைச் சார்புகளை வணிகத் தொகுதிகளிலேயே விட்டுவிடும். கீழ்நிலை பின்தள அடிப்படை வசதி
களஞ்சியச் செயலாக்கங்களுக்குள் இருக்கலாம்; பயன்பாடு எதிர்கொள்ளும் நிலைத்த சேமிப்பு API-ஆக இருக்கக்கூடாது.

### ஒரு துண்டைச் சரிபார்ப்பதற்கு முன் அனைத்து நிலைத்த சேமிப்பையும் மீண்டும் எழுதுதல்

நிராகரிக்கப்பட்டது. தற்போதைய நிலைத்த சேமிப்பு இடைமுகம் பரந்தது; மேலும் கோப்பு வாழ்நாள் சுழற்சி, மீட்டெடுப்பு, தேடல்
மற்றும் செயல்பாட்டு அமைப்புகள் ஆகியவற்றை உள்ளடக்கியது. செங்குத்துத் துண்டுகள் மதிப்பாய்வு செய்யக்கூடிய நடத்தை மற்றும் மீளமைப்பு எல்லைகளை வழங்குகின்றன.

### SQLite-ஐ இயல்புநிலையிலிருந்து மாற்றுதல்

நிராகரிக்கப்பட்டது. உட்பொதிக்கப்பட்ட மற்றும் டெஸ்க்டாப் நிறுவல்கள் தற்போதைய சேவை தேவையற்ற தொடக்க மாதிரியைச் சார்ந்துள்ளன. ஒரு
வெளிப்புற பின்தளம் விருப்பத் தேர்வாகும்.

### Redis-ஐ நீடித்த தரவுகளுக்கான அதிகாரப்பூர்வ ஆதாரமாகப் பயன்படுத்துதல்

நிராகரிக்கப்பட்டது. வெளிப்படையாகத் தற்காலிகமான ஒருங்கிணைப்பு, தற்காலிகச் சேமிப்பு அல்லது எண்ணிகளுக்கு Redis உதவலாம்; ஆனால் இது இங்கே
விவரிக்கப்பட்டுள்ள நீடித்த களஞ்சிய ஒப்பந்தத்திற்கு மாற்றாகாது.

## விளைவுகள்

### நேர்மறையானவை

- தரவுத்தள வழக்குமொழியைச் சாராத நிலையான நிலைத்த சேமிப்பு இணைப்புப் புள்ளியை வணிகக் குறியீடு பெறுகிறது.
- ஒரு வெளிப்புற பின்தளம் சுருக்கத்தை வரையறுப்பதற்கு முன் SQLite நடத்தை சோதிக்கப்படுகிறது.
- PostgreSQL மற்றும் MySQL ஆகியவை களத் தர்க்கத்தை நகலெடுப்பதற்குப் பதிலாக ஒப்பந்தங்களையும் சோதனைகளையும் பகிர்ந்துகொள்கின்றன.
- SQLite-க்கு மட்டுமே உரிய திறன்கள், உட்புற விவரங்களைக் கசியவிடும் இணக்கத்தன்மை இடைநிலைகளாக மாறாமல், முதன்மைத் திறன்களாகவே நீடிக்கின்றன.
- பல பிரதிகளுக்கான இடம்பெயர்வு மற்றும் பரிவர்த்தனை நடத்தை வெளிப்படையான வடிவமைப்புக் கருத்தாகிறது.

### செலவுகள் மற்றும் அபாயங்கள்

- களஞ்சியத்தைப் பிரித்தெடுப்பதற்கு அழைப்பிடங்களைப் படிப்படியாக இடம்பெயர்த்தல் தேவைப்படுகிறது.
- தற்போது ஒத்திசைவாக இயங்கும் சேவைக் குறியீடு முழுவதும் ஒத்திசைவற்ற எல்லைகள் பரவக்கூடும்.
- பின்தளங்களுக்கு இடையிலான பொருளியலுக்கு SQL தொடரமைப்பு இணக்கத்தன்மையைத் தாண்டிய ஒத்திசைவுச் சோதனைகள் தேவைப்படுகின்றன.
- காப்புப்பிரதி, தேடல், வெக்டர் சேமிப்பு மற்றும் பராமரிப்பு ஆகியவை குறிப்பிட்ட திறன்களைச் சார்ந்தவையாகவே நீடிக்கின்றன.
- ஒன்றுக்கு மேற்பட்ட நிலைத்த சேமிப்புச் செயலாக்கங்களை இயக்குவது CI மற்றும் செயல்பாட்டு ஆதரவுச் செலவை அதிகரிக்கிறது.

## நோக்கமல்லாதவை

இந்த ADR பின்வருவனவற்றைச் செய்யாது:

- தரவுத்தளச் சார்பு, சூழல் மாறி, திட்டவடிவம் அல்லது இடம்பெயர்வைச் சேர்த்தல்;
- செயலிலுள்ள SQLite singleton அல்லது இயக்கி அடுக்கை மாற்றுதல்;
- குறிப்பிட்ட வெளியீட்டில் PostgreSQL அல்லது MySQL ஆதரவுக்கு உறுதியளித்தல்;
- FTS5, `sqlite-vec`, காப்புப்பிரதிக் கோப்புகள் அல்லது SQLite பராமரிப்பை எங்கும் பயன்படுத்தக்கூடியதாக மாற்றுதல்;
- பகிரப்பட்ட நிலை மற்றும் ஒருங்கிணைப்புச் சோதனைகள் இருப்பதற்கு முன் active-active தயார்நிலையை வரையறுத்தல்;
- `src/lib/db/`-ஐ ஒரே கட்டமாக மீண்டும் எழுதுவதற்கு ஒப்புதல் அளித்தல்.

## பராமரிப்பாளர் ஒப்புதலுக்கான தீர்க்கப்படாத கேள்விகள்

1. களஞ்சியத்தையும் உள்புற async பின்தள எல்லையையும் இணைத்த அணுகுமுறையே விரும்பப்படும் திசையா, அல்லது
   வெளிப்புற நிலைத்த சேமிப்பகம் ஒரு தனியான control-plane சேவைக்குப் பின்னால் இருக்க வேண்டுமா?
2. SQLite இணக்கத்தன்மைக்குப் பிறகான முதல் வெளிப்புறச் செயலாக்கமாக PostgreSQL ஏற்கத்தக்கதா?
3. வரையறுக்கப்பட்ட முதல் களஞ்சியப் பகுதியாக எந்த domain இருக்க வேண்டும்?
4. முதல் multi-replica மைல்கல்லுக்காக எந்த state பகிரப்பட வேண்டும், எது node-local ஆகவே இருக்க வேண்டும்?
5. இடையில் தடைப்பட்ட அல்லது பின்னோக்கி மாற்றப்பட்ட களஞ்சிய migration-க்கு எந்த இணக்கத்தன்மைக் காலச்சாளரம் தேவை?

இந்தக் கேள்விகள் தீர்க்கப்படும் வரை, இந்த ஆவணம் ஒரு முன்மொழிவு மட்டுமே; எந்த runtime refactor-உம் மறைமுகமாகக் குறிக்கப்படவில்லை.
