## الملخص

يدعم OmniRoute الآن ثلاثة أوضاع ترحيل للمسار `/api/v1/relay/chat/completions`:

- `ts`: استخدام مُرحِّل TypeScript داخل العملية.
- `bifrost`: فرض استخدام بوابة Bifrost.
- `auto`: تفضيل Bifrost عند توفره، والرجوع إلى TypeScript عند حدوث فشل.

عند التشغيل بمعدل طلبات مرتفع (عدد كبير من الرموز المميزة يوميًا، ومعدل نقل شبه ثابت)، تتمثل أفضل استراتيجية في إبقاء مسار الرجوع صريحًا وسريعًا حتى لا يتعطل المسار الساخن أبدًا بانتظار خدمة جانبية متوقفة.

## سلوك الأوضاع

- `ts`
  - أدنى مستوى من التعقيد التشغيلي.
  - تُنفَّذ جميع عمليات التوجيه والتحقق في Node.
  - لا يعتمد التوفر على خدمة جانبية.
- `bifrost`
  - فرض تمرير جميع الطلبات عبر بوابة الخدمة الجانبية.
  - لا يوجد رجوع تلقائي.
  - لا يكون مفيدًا إلا عندما تكون سلامة الخدمة الجانبية وزمن استجابتها مضمونين.
- `auto`
  - تُستخدم الخدمة الجانبية عندما تكون مفعّلة ويمكن الوصول إليها.
  - تؤدي المحاولات الفاشلة إلى إضافة ترويسات الرجوع وإعادة حركة البيانات إلى TS، بحيث يظل نجاح الطلب ضمن حدود زمنية مضبوطة.
  - هذا الوضع هو الخيار الأكثر أمانًا لبيئات الإنتاج عندما يكون وقت التشغيل أهم من التوجيه الصارم عبر الخدمة الجانبية فقط.

## ‏9router مقارنةً بـ CLIPROXYAPI حاليًا

يُعد كل من 9router وCLIPROXYAPI تكاملين وفّرا تاريخيًا مسارات توافق لموفري الخدمة في المنبع.

- يمثّل 9router مسارًا مضمنًا لتنسيق خدمات المنبع وتوفير سلوك التوافق.
- يمثّل CLIPROXYAPI جسر API وكيلًا لحركة البيانات بنمط CLI / SDK.
- يجري تثبيت Bifrost بصفته المسار الخارجي عندما تحتاج إلى قفزة مخصصة شبيهة بخدمة جانبية وإرسال محلي منخفض زمن الاستجابة.

إذا كنت تقارن حاليًا بين 9router وCLIPROXYAPI:

- أبقِ توقيع الطلبات وعمليات التحقق من قائمة السماح وبوابات سياسات DB داخل مسار API قبل التسليم.
- إذا كان سير العمل يحتاج إلى سلوك صارم للخدمة الجانبية وتباين أقل بين الطلبات، فاستخدم `OMNIROUTE_RELAY_BACKEND=bifrost`.
- إذا كنت تحتاج إلى مرونة الخدمة الجانبية مع تدهور تدريجي سلس في حالات الأعطال، فاستخدم `OMNIROUTE_RELAY_BACKEND=auto`.

## عقد حدود الواجهة الخلفية

حدود المنتج المستقرة هي واجهة API للترحيل في OmniRoute، وليست آلية تنفيذ لوحة المعلومات. يمكن للوحة معلومات Next.js تثبيت الخدمات المحلية وتهيئتها والإشراف عليها، لكن يجب أن يدخل توجيه الطلبات عبر واجهة API للترحيل وأن يُسلَّم خلف تلك الحدود.

خيارات الواجهة الخلفية طويلة الأجل:

- احتفظ بمُرحِّل TypeScript بصفته مسار السياسات والرجوع داخل العملية. تبقى المصادقة وقوائم السماح وتوحيد الطلبات والمحاسبة وفحوصات الأمان هنا قبل أي تسليم إلى واجهة خلفية.
- استخدم Bifrost بصفته الخدمة الجانبية المفضلة من المستوى الأول ذات الإنتاجية العالية عندما يحتاج النشر إلى تباين أقل في التوجيه، أو تدوير مركزي لموفري الخدمة، أو توسع عبر عدة نسخ من OmniRoute.
- احتفظ بـ 9router وCLIPROXYAPI بصفتهما خدمتي توافق مضمنتين. تعملان كعمليات محلية خاضعة للإشراف، وتكونان مفيدتين عندما يكون سلوك الموفّر/CLI الخاص بهما هو المحوّل المطلوب، لكن يجب ألا تصبحا محرك التوجيه الافتراضي من المستوى الأول.
- لا تجعل لوحة المعلومات تمرر عناوين URL عشوائية للخدمات إلى المسار الساخن. عناوين URL المقدمة من واجهة المستخدم هي مدخلات تهيئة؛ وينبغي أن تحل شيفرة التوجيه الواجهات الخلفية المسجلة والخاضعة لفحص السلامة من إعدادات الخادم وحالة المشرف.
- فضّل HTTP عبر واجهة الاسترجاع للخدمات الخاضعة للإشراف حاليًا، لأن العمليات المُدارة توفر بالفعل واجهات API متوافقة مع HTTP، ويمكن لحارس المسار تدقيق الحدود، ويظهر سلوك الفشل/الرجوع في سجلات الطلبات. لا تستحق إضافة وسيلة نقل مستقبلية عبر SDK أو المقابس إلا إذا خفّضت زمن استجابة التوجيه عند p99 بصورة قابلة للقياس دون إضعاف العزل أو دلالات الرجوع.

لذلك، بالنسبة إلى نشر ذي إنتاجية عالية جدًا، تكون الإجابة الافتراضية هي `auto` مع تفعيل Bifrost: استخدم خدمة Go الجانبية في المسار الساخن مع الاحتفاظ بمسار الرجوع إلى TypeScript للحفاظ على معدل النجاح. استخدم `bifrost` فقط عندما يكون السلوك الصارم المعتمد على الخدمة الجانبية وحدها أهم من التدهور التدريجي السلس.

## إرشادات الإنتاجية العالية

لمعدلات RPM/RPS مرتفعة ومستدامة ومع هدف صارم لمستوى خدمة النجاح:

1. استخدم `auto` مع فترة تهدئة عملية وبيانات قياس عن حالات الفشل.
2. أبقِ عمليات التحقق من خدمات المنبع ومفاتيح API عند حدود مسار TypeScript.
3. فعّل ترويسات/عدادات صريحة حتى تتمكن تنبيهاتك من رصد وتيرة الرجوع وأسبابه.
4. اضبط مُهل الخدمة الجانبية لتفشل بسرعة بدلًا من الانتظار إلى أجل غير مسمى.
5. حافظ على سلامة إعادة التشغيل التلقائي للخدمة وحلقة قياس حالتها حتى يظل الرجوع حالة استثنائية فعلًا.

## خط الأساس المقترح

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- أبقِ مفاتيح API وقائمة السماح وأداة التنقية وفحوصات تحديد المعدل مفعّلة في معالجات المسارات (فهي تُنفَّذ دائمًا قبل إعادة التوجيه إلى المصب).
- صدّر مقاييس الرجوع من الوكيل العكسي وسجلات الطلبات حتى تصبح حالات توقف الخدمة الجانبية مرئية خلال دقيقة واحدة.

## عقد المكوّن الإضافي للموفّر

ينبغي أن تستورد الخدمات الجانبية البيانات الوصفية للموفّر من خلال بيان المكوّن الإضافي للموفّر المتوافق مع JSON بدلًا من الاعتماد على التفاصيل الداخلية لمنفّذ TypeScript. راجع [بيان المكوّن الإضافي للموفّر](./PROVIDER_PLUGIN_MANIFEST.md) للاطلاع على عقد أهلية الخدمة الجانبية ومراحل الترحيل.
