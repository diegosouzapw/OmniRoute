يعرّف `open-sse/config/providerPluginManifest.ts` عقد المكوّن الإضافي لمزوّد الخدمة المتوافق مع JSON.
ويربط `open-sse/config/providerPluginManifestRegistry.ts` هذا العقد بسجل مزوّدي الخدمة الحالي للعمليات الجانبية مثل Bifrost،
وCLIProxyAPI، أو موجّه مستقبلي مكتوب بلغة Go/Rust. يظل سجل TypeScript هو
مصدر الحقيقة، لكن يمكن للعمليات الجانبية استهلاك البيان دون استيراد
شيفرة المنفّذ، أو إعدادات OAuth الافتراضية، أو الترويسات، أو حالة بيئة العملية.

يتوفر البيان نفسه عبر HTTP على
`GET /api/v1/provider-plugin-manifest` للعمليات الجانبية التي تعمل خارج العملية.

تعلن OmniRoute عن عنوان URL هذا إلى Bifrost وCLIProxyAPI عبر ترويسة الطلب
`X-OmniRoute-Provider-Manifest-Url`. اضبط
`OMNIROUTE_PROVIDER_MANIFEST_URL` عندما تحتاج العملية الجانبية إلى عنوان URL عام أو عنوان URL ضمن شبكة الحاويات
بدلًا من أصل الطلب المحلي.

## تحديث البيان

تعيد نقطة نهاية HTTP القيمة `Cache-Control: public, max-age=60` ووسم
`ETag` قويًا. ينبغي للعملية الجانبية الاحتفاظ بآخر بيان تم التحقق من صحته وإرسال وسم ETag الخاص به
في `If-None-Match` عند التحديث. لا تحتوي استجابة `304 Not Modified` على جسم؛
وتحتفظ العملية الجانبية بالبيان المخزّن مؤقتًا. إذا لم يوجد بيان مخزّن مؤقتًا تم التحقق من صحته،
فيجب على العملية الجانبية إرسال طلب غير مشروط بدلًا من قبول استجابة `304`.

## الهدف

نقل بيانات مزوّدي الخدمة الوصفية نحو عقد مكوّن إضافي كي يصبح من الممكن في النهاية
إسناد مسار الطلبات النشط إلى عملية جانبية ذات زمن استجابة أقل، بينما تحتفظ OmniRoute
بمسار TypeScript بوصفه بوابة السياسات والمسار الاحتياطي. البيان إضافي: فهو
لا يغيّر توجيه الطلبات بحد ذاته.

## العقد

يحتوي البيان على:

- معرّف مزوّد الخدمة والاسم البديل
- تنسيق الخدمة المصدر واسم المنفّذ
- نوع المصادقة، وترويسة المصادقة، وبادئة المصادقة الاختيارية
- بيانات نقطة النهاية الوصفية الثابتة
- أهلية العملية الجانبية والأسباب الصريحة لبقاء مزوّد الخدمة ضمن TS
- بيانات النماذج الوصفية المتوافقة مع JSON، مثل طول السياق، وعلامات الرؤية/الاستدلال،
  والمعلمات غير المدعومة
- وسوم القدرات، بما في ذلك `apikey`، و`oauth`، و`custom-executor`،
  و`passthrough-models`، و`responses`، و`sidecar-candidate`، و`usage-fetch`، و`usage-supported`

يستبعد البيان عمدًا:

- أسرار عميل OAuth وقيم الأسرار الافتراضية
- تحليل بيئة وقت التشغيل
- ترويسات الطلب ومساعدات بيانات الاعتماد العامة
- أدوات إنشاء عناوين URL الديناميكية
- دوال المنفّذ
- التفاصيل الداخلية لمجمّع الجلسات

## وسوم القدرات

`capabilities` هي مصفوفة مرتبة من الوسوم المشتقة من إدخال السجل. ينبغي للجهات التي تجري عمليات التكامل
التعامل معها بوصفها الإجابة القابلة للقراءة آليًا عن سؤال "ما الذي يستطيع مزوّد الخدمة هذا فعله"، بدلًا من
إعادة قراءة مصادر TypeScript.

| الوسم                | المعنى                                                                            |
| -------------------- | --------------------------------------------------------------------------------- |
| `apikey`             | يقبل مفتاح API (تكون قيمة `authType` هي `apikey` أو `optional`).                  |
| `oauth`              | يستخدم تدفق OAuth أو تدفق جلسة.                                                   |
| `responses`          | يوفّر عنوان URL أساسيًا لواجهة OpenAI Responses API.                              |
| `passthrough-models` | يقدّم النماذج مباشرة من الخدمة المصدر بدلًا من كتالوج ثابت.                       |
| `custom-executor`    | يشغّل منفّذًا غير افتراضي، ولذلك يبقى ضمن مسار TypeScript.                        |
| `sidecar-candidate`  | يعكس `sidecar.eligible` — ويمكن النظر فيه بأمان للاستيراد إلى العملية الجانبية.   |
| `usage-fetch`        | لديه أداة جلب موصولة لبيانات الاستخدام أو الحصة (`getUsageForProvider`).          |
| `usage-supported`    | تقبل واجهة API الخاصة بالاستخدام مزوّد الخدمة هذا (`isSupportedUsageConnection`). |

يُستخدم `usage-fetch` للاكتشاف فقط. فهو يشير إلى أن OmniRoute يعرف كيفية قراءة بيانات الاستخدام الخاصة
بمزوّد الخدمة؛ لكنه لا يفعّل الجلب، ولا يغيّر دلالات الحصة، ولا يعني أن
أداة الحصة في Dashboard مفعّلة لمزوّد الخدمة — إذ تتحكم فيها بشكل منفصل
`USAGE_SUPPORTED_PROVIDERS`. مصدر الحقيقة هو `USAGE_FETCHER_PROVIDERS` في
`open-sse/services/usage/fetcherProviders.ts`.

تُفهرس تلك القائمة باستخدام السلاسل التي يقبلها موزّع الاستخدام، ولذلك فهي تمزج بين المعرّفات الأساسية
والأسماء البديلة، كما أنها أطول قليلًا من عدد مزوّدي الخدمة الموسومين: الإدخالات التي
ليست مزوّدي محادثة في سجل البيان (مثل مزوّد البحث `firecrawl`
ومزوّد ACP ‏`amazon-q`) لا يوجد لها إدخال بيان لإضافة وسم إليه.

يجيب `usage-supported` عما إذا كانت مسارات الاستخدام في الخادم وDashboard تقبل اتصالًا
لمزوّد الخدمة. وهو يعكس `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
و`supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`)، وكلاهما محكوم بواسطة
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). وعلى خلاف
`usage-fetch`، يُصدر هذا الوسم استنادًا إلى معرّف مزوّد الخدمة وحده — إذ ينفّذ حارس وقت التشغيل
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` دون تحليل للأسماء البديلة، ولذلك يحافظ البيان
على القاعدة نفسها. للوسمين نطاقان مختلفان: يحمل 3 من مزوّدي الخدمة وسم
`usage-fetch` فقط (`opencode`، و`opencode-zen`، و`xai`)، ويحمل مزوّد واحد وسم
`usage-supported` فقط (`xiaomi-mimo-token-plan`)، ولذلك لا يستلزم أحدهما الآخر.

## استخدام العملية الجانبية

يجب أن تتعامل العمليات الجانبية مع `sidecar.eligible` بوصفها إشارة محافظة لتحديد المرشحين، وليس قرار توجيه غير مشروط. ينبغي أن تكون أهداف الاستيراد الأولى هي موفّري مفاتيح API ونقاط النهاية الثابتة الذين يستخدمون المنفّذ الافتراضي. أما الموفّرون الذين لديهم منفّذات ويب مخصّصة، أو تدفقات OAuth/الجلسات، أو منشئات URL ديناميكية، أو إعدادات مجمّعات، فيبقون ضمن مسار TypeScript الاحتياطي إلى أن تنفّذ إحدى العمليات الجانبية سلوكًا مكافئًا وتُثبت بيانات القياس عن بُعد تحقيق التكافؤ.

مراحل الترحيل المقترحة:

1. إنشاء بيان المكوّنات الإضافية للموفّرين من سجل TS والتحقق من صحته.
2. تهيئة Bifrost أو CLIProxyAPI لاستيراد البيان الخاص بموفّري مفاتيح API/نقاط النهاية الثابتة.
3. توجيه الموفّرين المؤهلين عبر العملية الجانبية خلف `OMNIROUTE_RELAY_BACKEND` مع إبقاء مسار TS الاحتياطي مفعّلًا.
4. عدم ترقية الموفّرين إلا عندما يتطابق معدل النجاح، وزمن انتقال p99، وسلوك البث، والتعامل مع المعلمات غير المدعومة مع مسار TS.
5. إضافة مكوّنات إضافية أصلية للعملية الجانبية للمنفّذات المخصّصة، لعائلة موفّرين واحدة في كل مرة.

## لماذا لا نضمّن الموفّرين مباشرةً في Next

ينبغي ألا تتولى واجهة Next الأمامية تنفيذ الموفّرين. بل يجب أن تستدعي حدود API. ويمكن للواجهة الخلفية بعد ذلك أن تقرر ما إذا كانت ستستخدم منفّذ TypeScript، أو Bifrost، أو CLIProxyAPI، أو عملية جانبية أصلية مستقبلية. يحافظ هذا النهج على مركزية توقيع الطلبات، وعمليات التحقق من قائمة السماح، وسياسة DB، وسلوك الرجوع الاحتياطي قبل أي تسليم إلى عملية جانبية.
