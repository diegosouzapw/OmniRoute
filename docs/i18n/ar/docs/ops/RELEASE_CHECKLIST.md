## النشر الموثوق في npm (الافتراضي منذ v3.8.51) — مرحلي عند الطلب، ومباشر كخيار احتياطي

ينشر `npm-publish.yml` عبر **النشر الموثوق في npm ‏(OIDC)** افتراضيًا: تستبدل مهمة
`stage-npm` (المستضافة على GitHub) رمز id-token الخاص بـ GitHub ببيانات اعتماد npm
قصيرة الأجل لذلك التشغيل — من دون رمز npm طويل الأجل في أسرار المستودع، ومن دون مطالبة بالمصادقة الثنائية، مع إرفاق مصدر موثّق.
وهذا هو التجاوز الذي تسمح به npm الآن بعد بدء إيقاف الرموز التي تتخطى المصادقة الثنائية؛
إذ يعيد مسار العمل المؤتمت بالكامل الذي كان لدى المشروع حتى v3.8.48، مع الحفاظ على
ضمان WS1.3 (لا يمكن لرمز مسرّب النشر بمفرده — إذ لا يوجد رمز أصلًا).

**إعداد لمرة واحدة (المالك):** npmjs.com ← الحزمة `omniroute` ← Settings ← _Trusted
Publisher_ ← GitHub: المالك `diegosouzapw`، المستودع `OmniRoute`، سير العمل `npm-publish.yml`
(البيئة: لا شيء). إلى أن يتوفر ذلك، تفشل الخطوة التلقائية مع `ENEEDAUTH`:
أعد التشغيل باستخدام `publish_mode=staged` (أدناه) أو `direct`.

### النشر المرحلي (عند الطلب — `publish_mode=staged`)

لم يعد سير عمل npm-publish ينشر مباشرةً: بل يشغّل الحزمة المضغوطة
(`check:pack-boot`) ثم ينفّذ `npm stage publish` — حيث تُركن البايتات نفسها تمامًا في
السجل، وتكون **غير قابلة للتثبيت** حتى يوافق المالك. انتقلت بوابة المصادقة الثنائية البشرية
إلى ما بعد الإثبات، لا قبله.

**مسار المالك بعد نجاح سير العمل:**

1. `npm stage list omniroute` — ابحث عن معرّف المرحلة (يُطبع أيضًا في ملخص سير العمل).
2. تحقّق من البايتات المرحلية (موصى به): `npm stage download <id>`، ثم ثبّت ملف الحزمة
   المضغوط الذي تم تنزيله في بادئة مؤقتة وشغّله (`npm run check:pack-boot` يؤتمت
   حكم الحزم←التثبيت←التشغيل نفسه في CI).
3. `npm stage approve <id>` — مطالبة المصادقة الثنائية هي عملية النشر نفسها. أما `npm stage reject <id>` فيتخلص من المرحلة.
4. شبكة أمان ما بعد النشر: يثبّت مدقّق ما بعد النشر (WS1.4 من خطة v3.8.49)
   الإصدار المنشور من السجل العام داخل حاوية نظيفة ويشغّله.

**الخيار الاحتياطي الطارئ:** يعيد `workflow_dispatch` مع `publish_mode=direct`
سلوك `npm publish` الفوري القديم (استخدمه فقط إذا تعطّل النشر المرحلي نفسه؛ وسجّل السبب).

**تحصين لمرة واحدة (المالك، npmjs.com):** اضبط الناشر الموثوق للحزمة
`omniroute` على وضع المرحلة فقط، بحيث لا يتمكن رمز طويل الأجل مسرّب من تنفيذ `npm publish`
مباشرةً من أي مكان — لا يستطيع CI سوى إنشاء مرحلة؛ ولا يصدرها إلا المالك عبر المصادقة الثنائية.

**دليل التعامل مع العناصر التالفة (من دون تغيير):** استخدم `npm deprecate omniroute@<bad> "<reason> — use <fixed>"`
بوصفه الإجراء الافتراضي الفوري (يستغرق دقائق، ويمكن التراجع عنه)؛ ولا تستخدم `npm unpublish` إلا ضمن
نافذة 72 ساعة/عدم وجود معتمدين، وألا يكون أبدًا الخطوة الأولى. بالنسبة إلى Docker: لا تُعِد كتابة وسم إصدار مطلقًا — يكون
التراجع عبر إعادة توجيه `latest` إلى آخر ملخص سليم.

**وسم Docker Hub المسمى `latest` (مطلوب عند كل نشر SemVer مستقر):** يجب على سير عمل
`docker-publish` وضع الوسم **لكل من** `X.Y.Z`، وعندما يقرّر
`should-promote-latest.sh` أن هذا أعلى إصدار SemVer مستقر، وسم `:latest`
باستخدام **الملخص نفسه**. بعد انتهاء المهمة: يجب أن يساوي ملخص `latest` على Hub ملخص
SemVer الجديد، وأن تتغير قيمة `last_updated`. لا تترك `:latest` يشير إلى
بنية أقدم بينما تتحدث ملاحظات الإصدار عن إصلاحات لا توجد إلا في git. تستخدم بدايات
Compose السريعة `:latest`؛ وينبغي أن يستمر GitOps في تثبيت `X.Y.Z`. راجع
[قنوات إصدار Docker](../guides/DOCKER_GUIDE.md#release-channels) و#10317.

## المسار السريع للإصلاحات العاجلة (التسمية `hotfix`)

يتجاوز طلب السحب الذي يحمل التسمية `hotfix` مصفوفة CI الثقيلة (اختبارات E2E موزعة على 9 أجزاء، وتشديد التغطية،
وquality-gate، وquality-extended)، مع الإبقاء على بوابات التحقق السريعة وعالية الدلالة: البناء،
وأجزاء اختبارات الوحدة، والتكامل، وvitest، وlint/typecheck، وdocs-sync، و`check:pack-artifact`
واختبار الإقلاع الأولي لحزمة tarball (`check:pack-boot`). الهدف: نتيجة ناجحة خلال ≤15 دقيقة بدلًا من ~33 دقيقة.

**سياسة الدخول — الشروط الأربعة كلها مطلوبة (على غرار مسارات الطوارئ في Chromium/VS Code/Node):**

1. **الخطورة**: بيئة الإنتاج معطلة — حزمة منشورة تتعطل عند الإقلاع / إصلاح
   أمني / كل مستخدمي الإصدار متأثرون. «مهم» لا تعني «معطل».
2. **الصلاحية**: مالك المستودع وحده يطبق التسمية `hotfix`. التسمية هي
   الموافقة — ويُمنع تطبيقها ذاتيًا على طلب سحب خاص بحملة.
3. **الدليل**: يتضمن وصف طلب السحب رابطًا إلى آخر تشغيل ثقيل ناجح بالكامل (الحزمة التي
   كانت المهام المتجاوزة ستعيد التحقق منها)، إضافةً إلى اختبار الإصلاح نفسه الذي يفشل أولًا ثم ينجح.
4. **النطاق**: تطبيق عبر cherry-pick فقط — الحد الأدنى من الإصلاح، بلا إعادة هيكلة ولا تغييرات إضافية مصاحبة.

يُعاد التحقق من نطاق التغطية/التشديد المتجاوز في التشغيل الكامل التالي على
فرع الإصدار (استمرار نجاح الإصدار) — يتجاوز المسار الانتظار فقط، ولا يتجاوز التحقق أبدًا.
تتجاوز التغييرات الخاصة بالاختبارات فقط (جميع الملفات ضمن `tests/`، ولا يوجد أي منها ضمن `tests/e2e/`) مصفوفة E2E
تلقائيًا، دون أي تسمية.

### الخطافات (تم التحقق منها بواسطة Husky)

توجد خطافات Husky في `.husky/` وتعمل تلقائيًا أثناء عمليات git.

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** بوابات تحقق سريعة وحتمية — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (فُعّلت في 2026-06-13). تستبعد `test:unit` عمدًا (بطيئة؛ وتغطيها مهمة CI المسماة `test-unit`).
  - شغّل `npm run test:unit` يدويًا قبل دفع فروع الإصدار.

إذا فشل أحد الخطافات: أصلح المشكلة الأساسية، ولا تتجاوزه باستخدام `--no-verify`.

### عمليات التثبيت التقليدية

يجب أن تتبع جميع عمليات التثبيت المخصصة للإصدار التنسيق `type(scope): subject`.

**الأنواع الصالحة:** `feat`، و`fix`، و`refactor`، و`docs`، و`test`، و`chore`، و`perf`، و`style`، و`ci`

**النطاقات الصالحة:** `db`، و`sse`، و`oauth`، و`dashboard`، و`api`، و`cli`، و`docker`، و`ci`، و`mcp`، و`a2a`، و`memory`، و`skills`، و`cloud-agent`، و`guardrails`، و`compression`، و`auto-combo`، و`resilience`، و`providers`، و`executors`، و`translator`، و`domain`، و`authz`

التغييرات الكاسرة للتوافق: أضف التذييل `BREAKING CHANGE:` أو `!` بعد النطاق (مثلًا `feat(api)!: drop /v0`).

### تخطيط البناء

يستخدم المستودع ثلاثة أدلة إخراج منفصلة — لا تخلط بينها مطلقًا:

| الدليل    | الغرض                                                  | متتبّع؟          |
| --------- | ------------------------------------------------------ | ---------------- |
| `src/`    | مصدر التطبيق (TypeScript / TSX)                        | نعم              |
| `.build/` | وسائط البناء — مخرجات `next build` (`distDir`)         | لا (يتجاهله git) |
| `dist/`   | حزمة npm القابلة للتوزيع — يجمعها `assembleStandalone` | لا (يتجاهله git) |

> **ملاحظة للمشغّل:** يظل دليل الصورة على VPS البعيد هو `/usr/lib/node_modules/omniroute/app/`.
> انتقلت فقط مخرجات البناء **داخل المستودع** (`app/` → `dist/`). تستخدم مهارات النشر rsync لمزامنة
> محتويات `dist/` مع دليل `app/` البعيد — ولا يلزم إجراء أي تغييرات على مسارات VPS.

**تدفق البناء الواحد:**

```
npm run build:release
  └─ rm -rf .build dist          (تنظيف)
  └─ next build → .build/next/   (وسائط)
  └─ assembleStandalone          (ينسخ النسخة المستقلة + الملفات الثابتة + العامة + الأصلية → dist/)
  └─ يكتب dist/BUILD_SHA         (علامة HEAD)
```

لا تشغّل `npm run build` متبوعًا بتشغيل منفصل لـ `npm run build:cli` من أجل النشر — استخدم
`npm run build:release`، الذي ينفّذ إعادة بناء نظيفة + إنشاء العلامة بأمر واحد.

مانع (`✗`)، و`2` = خطأ في الاستخدام. يخفض `--advisory <id,...>` مستوى أحد الفحوصات إلى تحذير (`!`)
من دون إخفائه.

شغّل التشغيل التجريبي للفصل الفعلي بينما لا يزال تجميد إصدار 3.9.0 مفتوحًا — إذ تُنشأ الفروع
بعد الوسم وقبل أن ترفع المرحلة 12c التجميد.

### تجربة 3.8.58 (على نسخة متفرعة فقط)

```bash
# 1. تشغيل تجريبي على القمة الحالية باستخدام معلمات التجربة
npm run release:dry-run-lts-cut -- --target-version 3.8.58 --previous-tag v3.8.57 \
  --advisory freeze,base-green

# 2. التنفيذ على جهاز تحكم بعيد لنسخة متفرعة (يُرفض origin، أو أي جهاز تحكم بعيد يكون عنوان URL
#    الخاص به هو المستودع الأساسي؛ وتطلب كل خطوة التأكيد في الطرفية)
git remote add rehearsal https://github.com/<you>/OmniRoute.git
node scripts/release/dry-run-lts-cut.mjs --execute --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green

# 3. اختبار مسارات العمل الخاملة في النسخة المتفرعة (workflow_dispatch حيث يُبلغ التشغيل
#    التجريبي عن تثبيت على المستودع الأساسي)، ثم التراجع
node scripts/release/dry-run-lts-cut.mjs --execute --rollback --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green
```

يُنشأ التزام رفع إصدار develop باستخدام أدوات git منخفضة المستوى (من دون لمس شجرة العمل)، ويرفع
الإصدار في الملفات الخمسة نفسها التي يعدّلها التزام فتح دورة: `package.json`، و`open-sse/package.json`،
و`electron/package.json`، و`package-lock.json`، و`docs/openapi.yaml`. يُفتح قسم `[4.0.0]`
في CHANGELOG ونُسخه المترجمة على `develop` بعد ذلك، قبل أول
PR له. لا يغيّر البرنامج النصي وسوم توزيع npm مطلقًا — تدرّب عليها باستخدام حزمة تجريبية.

### أثر معاينة PR (أنشئه مرة واحدة، ثم روّج البايتات نفسها)

ينشئ `.github/workflows/preview-artifact.yml` حزمة tarball إنتاجية واحدة من رأس PR
ويتحقق من تلك البنية نفسها تمامًا (جزء #8084 (a)). يقتصر ذلك على طلبات PR داخل المستودع نفسه؛ ولا يُنشر شيء.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # أو أضف التسمية `preview-artifact`
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # تثبيت المعاينة
```

يشغّل التنفيذ `npm ci`، و`npm run build:release`، و`npm run check:pack-artifact`، ويحزم
حزمة tarball، ثم يشغّل `npm run check:pack-boot` (أسرار وهمية، ودليل بيانات مؤقت)، ويعيد الحزم
ويفشل ما لم تكن البصمة متطابقة، ثم يسجّل `artifact-identity.json` (‏SHA للرأس، وSHA
للأساس، وتجزئة ملف القفل، والمنصة، والمعمارية، وnode ABI، وأداة التجميع، وسياسة البناء —
`scripts/release/artifact-identity.mjs`) ويُصدر شهادة لحزمة tarball في مهمة منفصلة. يعني ترويج
معاينة تثبيت حزمة tarball تلك: لا تُعِد البناء من المصدر مطلقًا.

### الفصل (3.9.0، بعد GO)

1. تسجيل GO في [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md).
2. يطبع `npm run release:dry-run-lts-cut -- --from v3.9.0` النتيجة `RESULT: READY`.
3. أنشئ الفرعين على `origin` يدويًا باستخدام الأوامر التي يطبعها التشغيل التجريبي — يرفض
   البرنامج النصي الدفع إلى `origin`. لإعادة استخدام التزام develop خضع للمراجعة، شغّل
   تجربة `--execute` أولًا على قمة 3.9.0 مقابل نسختك المتفرعة؛ حيث يطبع قيمتي SHA، ويمكن
   دفع الالتزامين نفسيهما:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. احمِ `stable/v3` و`develop` (مجموعات القواعد + قائمة انتظار الدمج) قبل دمج أول PR.
5. تُفعَّل مسارات العمل الخاملة عند وجود الفرع: `forward-port.yml` (الدفع إلى
   `stable/v3`)، و`validate-stable-pr.yml` (طلبات PR إلى `stable/v3`)، و`nightly-v4-build.yml`
   (يبني `develop`). قبل الإطلاق الفعلي، عيّن سر المستودع `secrets.FORWARD_PORT_TOKEN` (لكي يعمل CI على
   طلبات PR الخاصة بالنقل التقدمي)؛ ويظل النشر الليلي متوقفًا حتى يعيّن المالك متغير المستودع
   `vars.NIGHTLY_PUBLISH` إلى `true` ويقبل npm Trusted Publishing الملف
   `nightly-v4-build.yml`. يُنفَّذ تحديد القناة بواسطة `scripts/release/dist-tag.mjs`، وهو
   المحلّل نفسه الذي يستخدمه `npm-publish.yml`.
6. تحقّق من القنوات: يعرض `npm view omniroute dist-tags --json` القيمة `latest` = 3.9.0، ولا يعرض
   `next` / `nightly` حتى نشر v4.
7. للتراجع عند الحاجة: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   و`npm dist-tag add omniroute@3.8.59 latest`.

## التراجع عن الإصدار

إذا كان الإصدار يحتوي على مشكلة حرجة:

1. `gh release edit vX.Y.Z --prerelease` (يضع علامة عليه بأنه ليس الأحدث)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (فقط إذا لم يكن المستخدمون قد اعتمدوه بعد)
3. أو: إصلاح عاجل على `release/vX.Y.0` ← إصدار تصحيحي `vX.Y.(Z+1)`
4. أبلغ فورًا عبر GitHub Discussions وDiscord

## قواعد صارمة

- لا تلتزم بالتغييرات مباشرةً في `main` مطلقًا
- لا تستخدم `git push --force` مطلقًا مع `main` أو فروع `release/*`
- لا تتخطَّ خطافات Husky (`--no-verify`) مطلقًا
- لا تلتزم مطلقًا بالأسرار أو بيانات الاعتماد أو ملفات `.env`
- يجب أن تظل التغطية ≥60/60/60/60 (التعليمات/الأسطر/الدوال/الفروع)
- أدرج الاختبارات أو حدّثها دائمًا عند تغيير كود الإنتاج في `src/` أو `open-sse/` أو `electron/` أو `bin/`

## فحص المزامنة الآلي

شغّل أداة التحقق من مزامنة الوثائق محليًا قبل فتح طلب سحب:

