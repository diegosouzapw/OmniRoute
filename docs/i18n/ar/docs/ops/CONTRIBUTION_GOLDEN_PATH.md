استخدم هذا الدليل لاختيار أصغر دورة تطوير موثوقة لطلب سحب. وهو لا يحل محل مستندات البنية والأمان الخاصة بكل مجال والمرتبطة أدناه؛ بل يربط كل نوع شائع من التغييرات بعقوده، وفحوصه المركزة، وتغطية CI الخاصة به.

## المسار الذي يتبعه كل تغيير

1. **اختر الفرع الأساسي قبل التحرير.** ابحث عن أعلى فرع نشط من فروع `release/v*` وأنشئ فرعك من آخر نقطة فيه. استهدف ذلك الفرع، وليس `main`. إذا كان تجميد إصدار نشطًا، فلا تستهدف الفرع المجمّد؛ استخدم دورة الإصدار النشطة التالية الموضحة في
   [نموذج التفريع والإصدار](BRANCHING_MODEL.md).
2. **حدّد العقود.** حدّد كل كتالوج، أو مخطط، أو عنصر مُنشأ، أو API عام، أو واجهة مستخدم يتأثر بالتغيير. يوضّح الجدول أدناه الحد الأدنى لمجموعة البداية.
3. **اكتب الاختبارات المركزة أو حدّثها.** تتطلب تغييرات الإنتاج في `src/`، أو `open-sse/`، أو `electron/`، أو `bin/` اختبارًا آليًا في طلب السحب نفسه. شغّل أصغر مجموعة من ملفات الاختبار التي تثبت السلوك، ثم شغّل بوابات الفحص المركزة المدرجة.
4. **دع CI يشغّل المصفوفة الواسعة.** تُشغَّل في طلب السحب جميع تقسيمات اختبارات الوحدة، وVitest، وآلية رفع حد التغطية، وبناء الإنتاج. لا تشغّل مجموعة اختبارات واسعة محليًا إلا عندما يشير فشل مركّز إلى تأثير أوسع، أو عندما يمتد التغيير عبر عدة أنظمة فرعية.
5. **وفّق التغييرات قبل المراجعة.** اجلب الفرع الأساسي النشط، وافحص التثبيتات الجديدة فيه والفرق بين تغييراتك وبينه، ثم أعد التأسيس أو ادمج الفرع الأساسي وفقًا لسير عمل المساهمين. عالج تعارضات الملفات المُنشأة والكتالوجات انطلاقًا من مصادرها، ثم أعد إنشاءها، وأعد تشغيل الدورة المركزة، وتأكد من أن طلب السحب لا يزال يستهدف فرع الإصدار النشط.
6. **سجّل الأدلة.** في قالب طلب السحب، أدرج الأوامر التي شغّلتها، وكل ملف اختبار أُضيف أو عُدّل، وعمليات الترحيل أو أعلام الميزات، وأي تحقق لا يزال معلقًا ولا يُجرى إلا عبر CI.

## المسارات المثالية حسب نوع التغيير

الأوامر أدناه هي الحد الأدنى من الفحوص المركزة، وليست إذنًا بتجاوز اختبار يغطي مباشرةً السلوك الذي غيّرته.

### المزوّد

**العقود**

- تعريف المزوّد في `src/shared/constants/providers/` ودمجه في
  `src/shared/constants/providers.ts`.
- النماذج والقدرات في `open-sse/config/providerRegistry.ts` أو ملفات السجل المستخرجة منه.
- اختيار المنفّذ/المترجم، وإعداد OAuth أو مفتاح API، وأصول لوحة المعلومات، ومرجع المزوّد المُنشأ عند الاقتضاء.
- يجب أن تستخدم بيانات الاعتماد العامة `resolvePublicCred()`؛ ويجب أن تستخدم استجابات الأخطاء أدوات الأخطاء المشتركة والمنقّاة. راجع `docs/security/PUBLIC_CREDS.md` ‏(ضمن git؛ ولا يُضمَّن في `/docs`) و
  [تنقية الأخطاء](../security/ERROR_SANITIZATION.md).

**الدورة المركزة**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # عند تغيير الكتالوج؛ ثبّت الفرق المُنشأ
npm run lint
```

اختبر أيضًا كل عائلة طلبات متأثرة: المحادثة، أو Responses، أو الصور، أو التضمينات، أو الصوت، أو الفيديو. راجع اختلافات الكتالوج المُنشأ والاختبارات المرجعية باعتبارها تغييرات في العقود؛ ولا تقبلها دون تدقيق.

### التوجيه

**العقود**

- قيم الاستراتيجيات العامة وبيانات واجهة المستخدم الوصفية في `src/shared/constants/routingStrategies.ts`.
- الإرسال والترتيب ضمن `open-sse/services/combo.ts` و`open-sse/services/combo/`.
- مخططات Combo، والاستمرارية، وحالة المرونة، وقدرات النماذج، وعناصر تحكم API/واجهة المستخدم.
- [محرك Auto-Combo](../routing/AUTO-COMBO.md) ووثائق المرونة عند تغيّر السلوك.

**الدورة المركزة**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # تغييرات الاستراتيجية أو الإرسال
npm run check:known-symbols      # تغييرات تسجيل الاستراتيجية
npm run lint
```

استخدم محليًا اختبارات حتمية بمصادر علوية وهمية. تتطلب اختبارات التحقق المباشر السريعة لـ Combo بيانات اعتماد، وهي يدوية وليست بدائل لـ CI.

### واجهة المستخدم / تجربة المستخدم

**العقود**

- حدود مسارات/صفحات Next.js والمكوّنات المشتركة ضمن `src/app/` و
  `src/shared/components/`.
- أشكال استجابات API، وحالات التحميل/الفراغ/الخطأ، وسلوك لوحة المفاتيح وقارئات الشاشة، والتخطيط المتجاوب، والسمات، وتوسعة اللغات.
- سلاسل مصدر واجهة المستخدم الإنجليزية في `src/i18n/messages/en.json`؛ لا تضمّن نصوصًا جديدة موجّهة للمستخدم مباشرةً في الشفرة.

**الدورة المركزة**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

شغّل التطبيق عند إجراء تغييرات تفاعلية أو مرئية، وتحقق من إطارات العرض الضيقة والعريضة. يشغّل CI بناء الإنتاج ومجموعات الاختبارات الأوسع؛ ومع ذلك، يحتاج السلوك المرئي إلى اختبار مكوّن مركّز، أو Playwright، أو فحص يدوي موثّق يناسب التغيير.

### التدويل

**العقود**

- `src/i18n/messages/en.json` هو مصدر واجهة المستخدم؛ و`config/i18n.json` هو مصدر اللغات.
- توجد كتالوجات CLI بشكل منفصل ضمن `bin/cli/locales/`.
- حافظ على العناصر النائبة والوسوم الخاصة بـ ICU كما هي تمامًا. لا تترجم أسماء المنتجات/المزوّدين/النماذج، أو أسماء البروتوكولات والترويسات، أو الأوامر، أو معرّفات الشفرة/JSON، أو عناوين URL، أو متغيرات البيئة، أو المصطلحات المحمية مثل `OmniRoute`، و`OAuth`، و`MCP`، و`A2A`. قائمة المصدر الحالية هي
  `scripts/i18n/glossary/protected-terms.json`.

**الدورة المركزة**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # عند تغيير سلاسل/كتالوجات CLI
npm run lint
```

هذه إرشادات للنظام الحالي، وليست دعوة لتوسيع أدواته أو نموذج مفاتيحه. اجعل رقع التدويل محدودة ودقيقة أثناء تصميم النظام البديل. لا تشغّل أوامر ترجمة تستدعي خدمات خارجية إلا إذا كانت المهمة تتطلب صراحةً ترجمات مُنشأة وكنت قد راجعت الفرق الناتج.

### واجهة سطر الأوامر

**العقود**

- الأوامر العامة والخيارات في `bin/cli/`، وأوامر API المُولَّدة، ورموز الخروج، وstdout/stderr،
  وبُنى مخرجات JSON، وسلوك الإعدادات/البيئة، والملفات المضمّنة في الحزمة.
- يجب أن تستخدم السلاسل النصية الظاهرة لمستخدمي CLI طبقة i18n الخاصة بـ CLI، مع إبقاء كتالوجَي `en`/`pt-BR` متوافقين.
- حافظ على Node بوصفه بيئة التشغيل المدعومة، وعلى عقد الملف التنفيذي المنشور.

**الحلقة المركّزة**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # تغييرات CLI المُولَّدة/المُجمَّعة
npm run check:pack-policy     # تغييرات واجهة الحزمة
npm run lint
```

استخدم الأمر نفسه تمامًا داخل دليل بيانات مؤقت عندما يعتمد السلوك على التحليل، أو الملفات، أو حالة
الخروج. ينفّذ CI فحوصات أوسع لعناصر الحزمة ونظامها البيئي.

### قاعدة البيانات

**العقود**

- وحدات النطاق موجودة ضمن `src/lib/db/`؛ استورد الوحدات المحددة مباشرةً (أُزيلت طبقة إعادة التصدير القديمة `localDb.ts`).
- ترحيلات SQL مرقّمة وقابلة لإعادة التنفيذ بأمان ضمن `src/lib/db/migrations/`، مع ضمان سلامة المعاملات، وسلوك
  الترقية، والفهارس، وكل مستدعٍ يتأثر بالمخطط.
- لا تنفّذ المسارات والمعالجات SQL خامًا بصورة مباشرة مطلقًا.

**الحلقة المركّزة**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

اختبر كلاً من قاعدة بيانات جديدة والترقية من المخطط السابق عند إضافة ترحيل. يجب أن تُغلق اختبارات قاعدة البيانات
المقابض وأن تستدعي `resetDbInstance()` أثناء التنظيف. شغّل `npm run test:bun:db` فقط عندما
يتغير مسار محوّل Bun ذي أفضل جهد ممكن؛ يظل Node هو المرجع المعتمد.

### البناء / النشر

**العقود**

- بيانات الحزمة/ملف القفل في الجذر ومساحة العمل، و`scripts/build/`، وتجميع Next.js المستقل، ومحتويات حزمة
  `dist/`، وبيانات Electron الوصفية الخاصة بالمنصات، ومسارات عمل CI، وحواجز النشر.
- يجب أن تظل نطاقات Node المدعومة واستخدام Bun المدرج في قائمة السماح داخل `CLAUDE.md` دون تغيير.
- تبقى نواتج البناء غير متتبعة؛ وتُطبَّق سياسات التبعيات، والتراخيص، ومسارات العمل، والحزم.

**الحلقة المركّزة**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # تغييرات التبعيات أو ملف القفل
npm run check:pack-policy      # تغييرات واجهة الحزمة المنشورة
npm run lint
```

استخدم `npm run build` محليًا فقط عندما يؤثر التغيير في الترجمة البرمجية، أو التجميع المستقل، أو الأصول،
أو حزم بيئة التشغيل. استخدم `npm run build:release` فقط للتحقق من الإصدار/النشر. يمثّل بناء CI
الإشارة النهائية عبر المنصات؛ وتتطلب تغييرات Electron الخاصة بمنصة معينة دليلًا من البناء المركّز المطابق
أو اختبار الدخان.

## الحلقة المحلية مقابل CI

| التشغيل محليًا لكل تصحيح                                                 | يوفّر CI الإشارة الشاملة                                            |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| اختبارات السلوك المباشرة وبوابات الفئات المذكورة أعلاه                   | حزمة اختبارات الوحدات الكاملة المجزأة والاختبارات التسلسلية         |
| `npm run lint`                                                           | حزم Vitest وآليات رفع حدود التغطية/الجودة تدريجيًا                  |
| فحص الأنواع أو البناء فقط عندما يتطلب العقد المتأثر ذلك                  | بناء الإنتاج وبوابات الأمان والتوثيق والتبعيات وسياسات PR           |
| اختبارات التفاعل اليدوي/المباشر فقط عندما يتعذر على الأتمتة إثبات السلوك | اختبارات التكامل بين المهام واختبارات المنصات التي يضبطها سير العمل |

تُعدّ الحلقة المركزة الناجحة دليلًا على العقد المتغيّر، وليست إثباتًا على نجاح اختبارات CI غير ذات الصلة.
وفي المقابل، لا تجعل كل تعديل محلي ينتظر مصفوفة المستودع الكاملة.

## قائمة التحقق من المواءمة

قبل طلب المراجعة:

- تأكد من أن فرع الأساس لـ PR لا يزال أعلى فرع نشط من `release/v*`.
- اجلب فرع الأساس هذا وراجع الالتزامات التي أُضيفت منذ إنشاء فرعك.
- راجع `git diff <active-base>...HEAD` بحثًا عن تغييرات عرضية أو مولّدة.
- عالج تعارضات الكتالوج والمستندات المولّدة عبر تحديث المصدر وإعادة توليد المخرجات.
- أعد تشغيل كل اختبار/بوابة مركزة مدرجة في وصف PR بعد المواءمة.
- لا تُضعف التأكيدات مطلقًا ولا تحذف الاختبارات المطلوبة لمجرد التوافق مع فرع أساس تغيّر موضعه.

للاطلاع على قواعد تجميد الإصدار وإعادة الاستهداف، استخدم
