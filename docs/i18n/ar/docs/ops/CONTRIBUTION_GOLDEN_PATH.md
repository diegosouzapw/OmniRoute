استخدم هذا الدليل لاختيار أصغر دورة تطوير موثوقة لطلب سحب. وهو لا
يحل محل مستندات البنية والأمان الخاصة بكل مجال والمرتبطة أدناه؛ بل يربط كل نوع شائع
من التغييرات بعقوده وفحوصاته المركزة وتغطية CI الخاصة به.

## المسار الذي يتبعه كل تغيير

1. **اختر الفرع الأساسي قبل التعديل.** ابحث عن أعلى فرع نشط من فروع `release/v*` وأنشئ فرعك انطلاقًا
   من أحدث نقطة فيه. استهدف ذلك الفرع، وليس `main`. إذا كان تجميد الإصدار ساريًا، فلا تستهدف الفرع
   المجمّد؛ استخدم دورة الإصدار النشطة التالية الموضحة في
   [نموذج التفريع والإصدار](BRANCHING_MODEL.md).
2. **حدّد العقود.** حدّد كل كتالوج أو مخطط أو عنصر مولّد أو API عام أو واجهة
   مستخدم يتأثر بها التغيير. يوضح الجدول أدناه الحد الأدنى لمجموعة البداية.
3. **اكتب الاختبارات المركزة أو حدّثها.** تتطلب تغييرات الإنتاج في `src/` أو `open-sse/` أو `electron/` أو
   `bin/` اختبارًا آليًا في طلب السحب نفسه. شغّل أصغر مجموعة من ملفات الاختبار التي تثبت
   السلوك، ثم بوابات التحقق المركزة المدرجة.
4. **دع CI يشغّل المصفوفة الشاملة.** تعمل في طلب السحب شظايا اختبارات الوحدة الكاملة وVitest وآلية
   الرفع التدريجي للتغطية وبناء الإنتاج. شغّل مجموعة شاملة محليًا فقط عندما يشير فشل مركّز إلى
   تأثير أوسع أو عندما يمتد التغيير عبر عدة أنظمة فرعية.
5. **وفّق التغييرات قبل المراجعة.** اجلب الفرع الأساسي النشط، وافحص التزاماته الجديدة والفروقات الخاصة بك مقارنةً
   به، ثم أعد تأسيس الفرع أو ادمج الفرع الأساسي وفقًا لسير عمل المساهمين. عالج تعارضات الملفات
   المولّدة والكتالوجات من مصادرها، وأعد توليدها، ثم أعد تشغيل الدورة المركزة، وتأكد من أن
   طلب السحب لا يزال يستهدف فرع الإصدار النشط.
6. **سجّل الأدلة.** في قالب طلب السحب، اذكر الأوامر التي شغّلتها وكل ملف اختبار أضفته أو عدّلته،
   وعمليات الترحيل أو علامات الميزات، وأي تحقق مقتصر على CI لا يزال معلقًا.

## المسارات المثالية حسب نوع التغيير

الأوامر أدناه هي الحد الأدنى من الفحوصات المركزة، وليست إذنًا بتخطي اختبار يغطي مباشرةً
السلوك الذي غيّرته.

### المزوّد

**العقود**

- تعريف المزوّد في `src/shared/constants/providers/` وتركيبه في
  `src/shared/constants/providers.ts`.
- النماذج والإمكانات في `open-sse/config/providerRegistry.ts` أو ملفات السجل المستخرجة منه.
- اختيار المنفّذ/المترجم، وإعداد OAuth أو مفتاح API، وأصول لوحة المعلومات، ومرجع
  المزوّد المولّد عند الاقتضاء.
- يجب أن تستخدم بيانات الاعتماد العامة `resolvePublicCred()`؛ ويجب أن تستخدم استجابات الأخطاء مساعدات
  الأخطاء المشتركة والمنقّحة. راجع `docs/security/PUBLIC_CREDS.md` (في git؛ غير مضمن في `/docs`) و
  [تنقيح الأخطاء](../security/ERROR_SANITIZATION.md).

**الدورة المركزة**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # عند تغيير الكتالوج؛ ثبّت الفروقات المولّدة
npm run lint
```

اختبر أيضًا كل عائلة طلبات متأثرة: المحادثة أو Responses أو الصور أو التضمينات أو الصوت أو الفيديو.
راجع الفروقات المولّدة للكتالوج والاختبارات الذهبية باعتبارها تغييرات في العقود؛ ولا تقبلها دون تدقيق.

### التوجيه

**العقود**

- قيم الاستراتيجيات العامة والبيانات الوصفية لواجهة المستخدم في `src/shared/constants/routingStrategies.ts`.
- الإرسال والترتيب ضمن `open-sse/services/combo.ts` و`open-sse/services/combo/`.
- مخططات Combo والاستمرارية وحالة المرونة وإمكانات النماذج وعناصر تحكم API/واجهة المستخدم.
- [محرّك Auto-Combo](../routing/AUTO-COMBO.md) ووثائق المرونة عند تغيّر السلوك.

**الدورة المركزة**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # تغييرات الاستراتيجية أو الإرسال
npm run check:known-symbols      # تغييرات تسجيل الاستراتيجية
npm run lint
```

استخدم محليًا اختبارات حتمية تحاكي الخدمات المصدرية. تتطلب اختبارات Combo المباشرة بيانات اعتماد وهي
يدوية، وليست بدائل عن CI.

### واجهة المستخدم / تجربة المستخدم

**العقود**

- مسار/صفحة Next.js وحدود المكوّنات المشتركة ضمن `src/app/` و
  `src/shared/components/`.
- أشكال استجابات API، وحالات التحميل/الفراغ/الخطأ، وسلوك لوحة المفاتيح وقارئ الشاشة،
  والتخطيط المتجاوب، والسمات، وتوسعة اللغات.
- سلاسل المصدر الإنجليزية لواجهة المستخدم في `src/i18n/messages/en.json`؛ لا تضع نصوصًا جديدة موجهة للمستخدم داخل الشيفرة.

**الدورة المركزة**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

شغّل التطبيق عند إجراء تغييرات تفاعلية أو مرئية، وتحقق من إطارات العرض الضيقة والواسعة. يشغّل CI
بناء الإنتاج ومجموعات الاختبارات الأوسع؛ لكن السلوك المرئي يظل بحاجة إلى مكوّن مركّز أو Playwright
أو فحص يدوي موثّق يناسب التغيير.

### التدويل

**العقود**

- `src/i18n/messages/en.json` هو مصدر واجهة المستخدم؛ و`config/i18n.json` هو مصدر اللغات.
- توجد كتالوجات CLI بشكل منفصل ضمن `bin/cli/locales/`.
- حافظ على العناصر النائبة والوسوم في ICU كما هي تمامًا. لا تترجم أسماء المنتجات/المزوّدين/النماذج،
  أو أسماء البروتوكولات والترويسات، أو الأوامر، أو معرّفات الشيفرة/JSON، أو عناوين URL، أو متغيرات البيئة، أو
  المصطلحات المحمية مثل `OmniRoute` و`OAuth` و`MCP` و`A2A`. قائمة المصدر الحالية هي
  `scripts/i18n/glossary/protected-terms.json`.

**الدورة المركزة**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # عند تغيير سلاسل/كتالوجات CLI
npm run lint
```

هذه إرشادات للنظام الحالي، وليست دعوة لتوسيع أدواته أو نموذج مفاتيحه.
أبقِ رقع التدويل محدودة ودقيقة بينما يجري تصميم النظام البديل. لا تشغّل أوامر الترجمة
التي تستدعي خدمات خارجية إلا إذا كانت المهمة تتطلب ترجمات مولّدة صراحةً وكنت قد
راجعت الفروقات الناتجة.

### CLI

**العقود**

- الأوامر العامة والخيارات في `bin/cli/`، وأوامر API المُنشأة، ورموز الخروج، وstdout/stderr وأشكال مخرجات
  JSON، وسلوك الإعدادات/البيئة، والملفات المضمّنة في الحزمة.
- يجب أن تستخدم السلاسل النصية الموجّهة لمستخدمي CLI طبقة التدويل i18n الخاصة بـ CLI، مع إبقاء كتالوجَي `en`/`pt-BR` متوافقين.
- حافظ على Node بوصفه بيئة التشغيل المدعومة، وعلى عقد الملف التنفيذي المنشور.

**حلقة العمل المركّزة**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # تغييرات CLI المُنشأة/المجمّعة
npm run check:pack-policy     # تغييرات السطح العام للحزمة
npm run lint
```

استخدم الأمر نفسه تمامًا داخل دليل بيانات مؤقت عندما يعتمد السلوك على التحليل، أو الملفات، أو حالة
الخروج. ينفّذ CI الفحوصات الأوسع لعناصر الحزمة ونظامها البيئي.

### قاعدة البيانات

**العقود**

- وحدات النطاق ضمن `src/lib/db/`؛ استورد وحدات محددة مباشرةً (أُزيلت طبقة إعادة التصدير القديمة `localDb.ts`).
- ترحيلات SQL مرقّمة ومتكررة التنفيذ بأمان ضمن `src/lib/db/migrations/`، وسلامة المعاملات، وسلوك
  الترقية، والفهارس، وكل مستدعٍ يتأثر بالمخطط.
- لا تنفّذ المسارات والمعالجات استعلامات SQL خامًا مباشرةً مطلقًا.

**حلقة العمل المركّزة**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

اختبر كلاً من قاعدة بيانات جديدة والترقية من المخطط السابق عند إضافة ترحيل. يجب أن تغلق اختبارات قاعدة
البيانات المقابض وأن تستدعي `resetDbInstance()` أثناء التنظيف. شغّل `npm run test:bun:db` فقط عندما
يتغير مسار محوّل Bun المبذول على أساس أفضل جهد؛ يظل Node هو المرجع المعتمد.

### البناء / النشر

**العقود**

- ملفات البيان/ملف القفل في الجذر ومساحات العمل، و`scripts/build/`، وتجميع Next.js المستقل، ومحتويات حزمة
  `dist/`، وبيانات Electron الوصفية الخاصة بالمنصات، وسير عمل CI، ومؤشرات النشر.
- يجب أن تظل نطاقات Node المدعومة واستخدام Bun المدرج في قائمة السماح داخل `CLAUDE.md` دون تغيير.
- تظل عناصر البناء خارج التتبع؛ وتُطبّق سياسات التبعيات، والتراخيص، وسير العمل، والحزم.

**حلقة العمل المركّزة**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # تغييرات التبعيات أو ملف القفل
npm run check:pack-policy      # تغييرات السطح العام للحزمة المنشورة
npm run lint
```

استخدم `npm run build` محليًا فقط عندما يؤثر التغيير على الترجمة البرمجية، أو التجميع المستقل، أو الأصول،
أو تجميع بيئة التشغيل. استخدم `npm run build:release` فقط للتحقق من الإصدار/النشر. يُعد بناء CI
الإشارة النهائية العابرة للمنصات؛ وتتطلب تغييرات Electron الخاصة بمنصة معينة بناءً مركّزًا مطابقًا
أو دليل اختبار دخاني.

## حلقة المرشح المحلية

لا يمكن لاختبارات المصدر إثبات أن الحزمة المُنشأة قابلة للإقلاع: فقوائم التضمين في الحزمة، والتبعيات المشذّبة،
والملفات الثنائية الأصلية لا تفشل إلا بعد تثبيت ملف tarball وتشغيله. يمثّل `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) الجانب المحلي من تدفق البناء مرة واحدة / التحقق / الترقية الوارد في
RFC #8084: إذ يبني مرشحًا واحدًا، ويتحقق من تلك الحزمة نفسها، ويرقّيها عبر إعادة تسمية الأدلة،
ويتراجع عنها عندما تفشل الخانة المُرقّاة في فحص السلامة.

```bash
npm run dev:candidate -- run --dry-run --json  # اطبع الخطة دون تغيير أي شيء
npm run dev:candidate -- run                   # بناء + تحقق + ترقية، مع تراجع تلقائي
npm run dev:candidate -- build                 # تنفيذ npm pack + التثبيت في _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # الإقلاع على منفذ متاح، وفحص /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> ← current، وcurrent ← previous
npm run dev:candidate -- rollback              # بدّل current وprevious
npm run dev:candidate -- run --from-tarball <file.tgz>  # أعد استخدام ملف tarball بُني في مكان آخر (CI)
```

- **البناء مرة واحدة.** يحزم `build` الشجرة الحالية (وهو يحتاج إلى `dist/server.js`، لذا شغّل
  `npm run build:release` أولًا) أو ينسخ `--from-tarball`، ثم يثبّت ملف tarball في بادئة npm
  معزولة، لأن ملف tarball لا يحتوي على `node_modules`. يكون المعرّف هو قيمة sha المختصرة لـ `HEAD`
  (مع اللاحقة `-dirty` عندما تحتوي الشجرة على تغييرات محلية)، أو `tgz-<sha256>` لملف tarball. يُعاد
  استخدام المعرّف النظيف الذي سبق بناؤه بدلًا من إعادة بنائه؛ مرّر `--force` لإعادة بنائه.
- **تحقق من الحزمة، لا من المصدر.** يشغّل `validate` واجهة سطر الأوامر المثبّتة
  (`serve --port <free port>`) باستخدام `DATA_DIR=<candidate>/data` جديد، وأسرار وهمية، مع إزالة
  `OMNIROUTE_API_KEY` و`STORAGE_ENCRYPTION_KEY` و`INITIAL_PASSWORD` الخاصة بالمشغّل من البيئة،
  بحيث يتحقق من وضع الاسترجاع المحلي بلا مفتاح لتثبيت جديد. وينتظر حتى يعيد
  `GET /api/health` الحالة 200، ويشترط أن يعيد `GET /v1/models` الحالة 200، ثم يوقف مجموعة العمليات،
  ويسجّل النتيجة في `validation.json` مع تجزئة ملف tarball.
- **رقِّ الحزمة نفسها.** يرفض `promote` أي مرشح لا يملك تحققًا ناجحًا لتجزئة ملف tarball الحالية
  الخاصة به. الخانة النشطة الافتراضية هي `_artifacts/candidate/current`؛ ويحدّد `--target <dir>`
  دليلًا آخر على نظام الملفات نفسه، وتكون خانته السابقة هي `<dir>.previous`.
  كل عملية إعادة تسمية ذرّية، وأي فشل في منتصف العملية يعكس عمليات إعادة التسمية التي نُفّذت بالفعل.
- **التراجع.** يتحقق `run` من الخانة المُرقّاة مرة أخرى، ويعيد تبديل `current` و`previous` عند
  فشل ذلك الفحص. ولا تتم ترقية أي مرشح يفشل في التحقق الأول.

يُكتب كل شيء داخل `_artifacts/candidate/` المتجاهَل بواسطة git؛ ولا يتم أبدًا المساس بتثبيت
OmniRoute موجود أو بدليل بياناته. واجهة سطر الأوامر المُرقّاة هي
`_artifacts/candidate/current/prefix/bin/omniroute`؛ شغّلها باستخدام `DATA_DIR` الخاص بك عند
استعمالها. رموز الخروج: `0` للنجاح، و`1` لفشل التحقق أو الترقية، و`2` لخطأ في الاستخدام أو بناء مفقود.

## الحلقة المحلية مقابل CI

| ما يُشغَّل محليًا لكل تصحيح                                         | ما يوفّره CI من مؤشرات شاملة                                 |
| ------------------------------------------------------------------- | ------------------------------------------------------------ |
| اختبارات السلوك المباشرة وبوابات الفئات المذكورة أعلاه              | حزمة اختبارات الوحدات الكاملة المجزأة والاختبارات التسلسلية  |
| `npm run lint`                                                      | حزم Vitest وآليات التشديد التدريجي للتغطية/الجودة            |
| فحص الأنواع أو البناء فقط عندما يتطلب العقد المتأثر ذلك             | بناء الإنتاج وبوابات الأمان والتوثيق والتبعيات وسياسات PR    |
| فحوصات التفاعل اليدوي/المباشر فقط عندما يتعذر إثبات السلوك بالأتمتة | فحوصات التكامل بين المهام والمنصات المُهيأة بواسطة سير العمل |

نجاح الحلقة المركزة دليل على صحة العقد الذي جرى تغييره، وليس إثباتًا على نجاح فحوصات CI غير المرتبطة
به. وفي المقابل، لا تجعل كل تعديل محلي ينتظر مصفوفة المستودع الكاملة.

## قائمة تحقق المزامنة

قبل طلب المراجعة:

- تأكد من أن أساس PR لا يزال أعلى فرع نشط من `release/v*`.
- اجلب ذلك الأساس وراجع الالتزامات التي أُضيفت منذ إنشاء فرعك.
- راجع `git diff <active-base>...HEAD` بحثًا عن تغييرات عرضية أو مولَّدة.
- عالج تعارضات الفهارس والمستندات المولَّدة بتحديث المصدر وإعادة توليد المخرجات.
- أعد تشغيل كل اختبار/بوابة مركزة مُدرجة في وصف PR بعد المزامنة.
- لا تُضعف التأكيدات ولا تحذف الاختبارات المطلوبة لمجرد التوافق مع أساس تغيّر موضعه.

للاطلاع على قواعد تجميد الإصدار وإعادة الاستهداف، استخدم
[نموذج التفريع والإصدار](BRANCHING_MODEL.md). وللاطلاع على القائمة الكاملة لفحوصات CI، استخدم
[مرجع بوابات الجودة](../architecture/QUALITY_GATES.md).
