> **باختصار**: يتتبّع OmniRoute استخدام الرموز لكل طلب، ويحسب التكلفة، ويفرض حصة لكل مفتاح API، ويعرض التحليلات في لوحة المعلومات. يشرح هذا الدليل كيفية عمل كل ذلك.

**المصادر:**

- `open-sse/services/usage.ts` (~70KB) — الخدمة الرئيسية لتتبّع الاستخدام
- `src/lib/usageAnalytics.ts` (~10KB) — التجميع للوحة المعلومات
- `src/lib/db/quotaSnapshots.ts` — بيانات الحصص التاريخية
- `src/lib/db/usage*.ts` — عدة وحدات لقاعدة البيانات مرتبطة بالاستخدام

## نظرة عامة

يُنشئ كل طلب يمر عبر OmniRoute **سجل استخدام** يتضمن:

- **الهوية**: مفتاح API، والموفّر، والنموذج، والتركيبة المستخدمة
- **الرموز**: رموز المُدخل، ورموز الإكمال، والرموز المخزنة مؤقتًا، والإجمالي
- **التكلفة**: المبلغ بالدولار الأمريكي (محسوب من بيانات التسعير)
- **التوقيت**: زمن الاستجابة والطوابع الزمنية للبدء/الانتهاء
- **الحالة**: نجاح، أو خطأ، أو تقييد بسبب معدل الطلبات، وما إلى ذلك

```
الطلب ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    التحليلات  الحصة   الفوترة
                 (لوحة المعلومات) (الفرض) (التصدير)
```

## ما الذي يتم تسجيله

تلتقط خدمة `usage.ts` **حدث استخدام** لكل طلب:

| الحقل              | النوع   | المصدر                                                                               |
| ------------------ | ------- | ------------------------------------------------------------------------------------ |
| `id`               | string  | UUID يتم إنشاؤه عند التسجيل                                                          |
| `apiKeyId`         | string  | مفتاح API الذي بدأ الطلب                                                             |
| `provider`         | string  | معرّف الموفّر (openai، anthropic، وما إلى ذلك)                                       |
| `model`            | string  | معرّف النموذج (gpt-5، claude-opus-4-6، وما إلى ذلك)                                  |
| `comboId`          | string? | معرّف التركيبة إذا تم التوجيه عبر تركيبة                                             |
| `promptTokens`     | number  | من استجابة المنبع                                                                    |
| `completionTokens` | number  | من استجابة المنبع                                                                    |
| `cachedTokens`     | number  | رموز إصابة ذاكرة التخزين المؤقت (التخزين المؤقت للمُدخلات في Anthropic، وما إلى ذلك) |
| `totalTokens`      | number  | المُدخل + الإكمال                                                                    |
| `costUsd`          | number  | محسوبة من بيانات التسعير                                                             |
| `latencyMs`        | number  | مدة الطلب من البداية إلى النهاية                                                     |
| `status`           | enum    | `success`، `error`، `rate_limited`، `timeout`، `cancelled`                           |
| `errorClass`       | string? | فئة الخطأ إذا كانت الحالة != نجاح                                                    |
| `timestamp`        | string  | ISO 8601 UTC                                                                         |
| `metadata`         | object  | بيانات مخصصة تُحقن عبر المكوّن الإضافي                                               |

### مصدر الرموز

تُستخرج الرموز من استجابة موفّر المنبع في **معالج الاستجابة**:

```ts
// من open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

بالنسبة إلى الموفّرين الذين لا يُرجعون بيانات الاستخدام (مثل بعض موفّري ملفات تعريف الارتباط عبر الويب)، يقوم OmniRoute **بتقدير** الرموز باستخدام قاعدة تقريبية قدرها `~4 أحرف لكل رمز` (راجع `open-sse/services/autoCombo/pipelineRouter.ts`).

### الرموز المخزنة مؤقتًا

يتتبّع OmniRoute قيمة `cached_tokens` بصورة منفصلة عن `prompt_tokens` للأسباب التالية:

- يفرض التخزين المؤقت للمُدخلات في Anthropic سعرًا مخفّضًا للرموز المخزنة مؤقتًا (10% من السعر العادي)
- يُرجع بعض الموفّرين قيمة `cache_read_input_tokens` التي يجب تسعيرها بشكل مختلف
- يمكن للتحليلات إظهار **معدل إصابة ذاكرة التخزين المؤقت** = `cached_tokens / prompt_tokens`

## حساب التكلفة

تُحتسب التكاليف من **بيانات التسعير** المتزامنة من LiteLLM (`src/lib/pricingSync.ts`):

| النموذج           | الإدخال $/1M | الإخراج $/1M | المخزّن مؤقتًا $/1M |
| ----------------- | ------------ | ------------ | ------------------- |
| gpt-5             | $2.50        | $10.00       | —                   |
| claude-opus-4-6   | $15.00       | $75.00       | $1.50               |
| claude-sonnet-4-5 | $3.00        | $15.00       | $0.30               |
| gemini-2.5-pro    | $1.25        | $10.00       | —                   |

معادلة التكلفة (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **لماذا تُطرح الرموز المخزّنة مؤقتًا من رموز المطالبة؟** يُسعَّر الجزء المخزّن مؤقتًا بشكل منفصل؛ واحتساب سعر الإدخال على المطالبة كاملةً سيؤدي إلى زيادة غير صحيحة في الحساب.

### مزامنة التسعير

تتم مزامنة بيانات التسعير تلقائيًا من LiteLLM عبر نقطة النهاية `/api/pricing/sync` (وتُشغَّل بواسطة مهمة cron المضمّنة، وليس بواسطة متغير بيئة موجّه للمستخدم):

```bash
# تشغيل يدوي
curl -X POST http://localhost:20128/api/pricing/sync
```

بالنسبة إلى النماذج التي لا تتوفر لها بيانات تسعير، يلجأ OmniRoute إلى **تقدير التكلفة** باستخدام متوسطات الأسعار الداخلية (المأخوذة من بيانات تسعير LiteLLM).

## التجميع حسب النطاق الزمني

تحسب الوحدة `usageAnalytics.ts` عناصر لوحة المعلومات من بيانات الاستخدام الأولية. وهي تدعم 7 نطاقات زمنية:

| النطاق   | الفترة الزمنية               | حالة الاستخدام                                |
| -------- | ---------------------------- | --------------------------------------------- |
| `1d`     | آخر 24 ساعة                  | اكتشاف الارتفاعات المفاجئة في التكلفة كل ساعة |
| `7d`     | آخر 7 أيام                   | المراجعة الأسبوعية                            |
| `30d`    | آخر 30 يومًا                 | الفوترة الشهرية                               |
| `90d`    | آخر 90 يومًا                 | التحليل ربع السنوي                            |
| `ytd`    | منذ 1 يناير من السنة الحالية | تتبّع الميزانية السنوية                       |
| `all`    | كل الوقت                     | إحصاءات مدى الاستخدام الكامل                  |
| `custom` | بداية/نهاية يحددهما المستخدم | عمليات التدقيق والاستعلامات المخصصة           |

### عناصر لوحة المعلومات المحسوبة

لأي نطاق زمني، تحسب طبقة التحليلات ما يلي:

| العنصر                      | الوصف                                                            |
| --------------------------- | ---------------------------------------------------------------- |
| **بطاقات الملخص**           | إجمالي الطلبات، والتكلفة الإجمالية، وإجمالي الرموز، ومعدل النجاح |
| **مخطط الاتجاه اليومي**     | التكلفة + الرموز يوميًا، مكدّسة حسب النموذج                      |
| **الخريطة الحرارية للنشاط** | شبكة ساعة اليوم × يوم الأسبوع، اللون = عدد الطلبات               |
| **تفصيل النماذج**           | مخطط دائري للتكلفة حسب النموذج                                   |
| **تفصيل المزوّدين**         | مخطط شريطي للطلبات حسب المزوّد                                   |
| **أهم مفاتيح API**          | جدول لأهم 10 مفاتيح حسب التكلفة                                  |
| **تحليل الأخطاء**           | معدل الأخطاء بمرور الوقت، وأهم فئات الأخطاء                      |

### الوصول البرمجي

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // سجلات محفوظات الاستخدام
  "7d",                 // النطاق الزمني: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // خريطة اتصال المزوّد (connectionId → اسم الحساب)
  {
    startDate: "2025-01-01",  // اختياري: للنطاق "custom"
    endDate: "2025-06-01",   // اختياري: للنطاق "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (سنتًا)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## فرض الحصص

تُفرض الحصة الخاصة بكل مفتاح API في موضعين:

1. **الحد المرن** (`quotaWarnAt`): تحذير في لوحة المعلومات عندما يتجاوز الاستخدام الحد
2. **الحد الصارم** (`quotaLimit`): يُرفض الطلب مع HTTP 429 عند تجاوز الحد

### الإعداد

```ts
// لكل مفتاح API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — إظهار تحذير
  quotaLimit: 10_00,    // $10.00 — إيقاف صارم
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### مسار الفرض

```
الطلب ──▶ quotaCheck()
              │
              ├── ضمن الحد؟  ──▶ السماح
              │
              └── تجاوز الحد؟  ──▶ 429 Too Many Requests
                                   مع ترويسة Retry-After
```

### لقطات الحصص

يخزّن جدول `quotaSnapshots` **الحالة التاريخية للحصص** لتحليل الاتجاهات:

| الحقل | الوصف |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | المفتاح الذي يجري تتبعه |
| `window` | "day" | "week" | "month" |
| `used` | التكلفة المستخدمة في هذه النافذة (بالسنت) |
| `limit` | الحد (بالسنت) |
| `resetAt` | وقت إعادة تعيين النافذة |
| `createdAt` | وقت التقاط اللقطة |

تُلتقط اللقطات **عند كل طلب** يستخدم تكلفة أكبر من 0، وتُستخدم من أجل:

- عرض شريط تقدم الحصة في لوحة المعلومات
- عرض مخططات اتجاه الحصة خلال 30 يومًا
- تشغيل التنبيهات عندما يقترب الاستخدام من الحد

## الاحتفاظ بالبيانات وتنظيفها

تنمو بيانات الاستخدام بمقدار ~1-10KB لكل طلب. وعلى نطاق واسع، قد يصبح هذا الحجم كبيرًا.

### إعدادات الاحتفاظ

يتم ضبط مدة الاحتفاظ بسجل الاستخدام عبر إعدادات قاعدة البيانات في واجهة المستخدم أو عبر `/api/settings/database`.

افتراضيًا، يُحتفظ بسجل الاستخدام لمدة **90 يومًا**.

### التنظيف

تُنظَّف السجلات القديمة بواسطة `src/lib/db/cleanup.ts`:

- يتم تشغيلها بواسطة عملية cron في الخلفية
- تحذف السجلات من `usage_history` التي يتجاوز عمرها مدة الاحتفاظ المضبوطة في إعداد `usageHistory`

### تقدير مساحة التخزين

| معدل الطلبات    | مساحة التخزين لمدة 30 يومًا | مساحة التخزين لمدة 90 يومًا |
| --------------- | --------------------------- | --------------------------- |
| 100 طلب/يوم     | ~3MB                        | ~9MB                        |
| 1,000 طلب/يوم   | ~30MB                       | ~90MB                       |
| 10,000 طلب/يوم  | ~300MB                      | ~900MB                      |
| 100,000 طلب/يوم | ~3GB                        | ~9GB                        |

بالنسبة إلى معدلات الزيارات المرتفعة جدًا، ضع في اعتبارك ما يلي:

- تقليل مدة الاحتفاظ عبر إعدادات قاعدة البيانات
- استخدام `aggregated_metrics` بدلًا من السجلات الأولية (للتحليلات فقط)

## نصائح لتحسين التكلفة

### 1. استخدم النموذج المناسب

```bash
# إجابة سريعة — استخدم خيارًا رخيصًا + سريعًا
curl -d '{"model":"auto/fast","messages":[...]}'

# مهمة معقدة — استخدم خيار الجودة
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. فعّل التخزين المؤقت

يوفر التخزين المؤقت للمطالبات من Anthropic نسبة **90% عند تكرار السياق**:

```ts
// التخزين المؤقت تلقائي — ما عليك سوى تضمين مطالبة النظام الكبيرة نفسها
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // سيتم تخزينها مؤقتًا تلقائيًا
  messages: [{ role: "user", content: "..." }],
});
```

### 3. استخدم الضغط

يوفر ضغط RTK + Caveman نسبة **15-95% في الجلسات كثيفة استخدام الأدوات**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. اضبط الحصص لكل مفتاح

اضبط دائمًا `quotaLimit` لمنع التكاليف غير المنضبطة:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // حد أقصى قدره $10/شهر
```

### 5. راجع المستهلكين الأعلى

استخدم لوحة المعلومات أو **`/api/usage/analytics`** للتجميع حسب مفتاح API والفرز حسب التكلفة:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## استكشاف الأخطاء وإصلاحها

### "التكلفة أعلى من المتوقع"

1. افحص **`/api/usage/analytics?groupBy=model`** — للعثور على النموذج مرتفع التكلفة
2. افحص **`/api/usage/analytics?groupBy=apiKey`** — للعثور على المستهلك كثيف الاستخدام
3. تحقق من أن بيانات التسعير محدّثة: `POST /api/pricing/sync`

### "السجلات مفقودة"

- تحقق من إعدادات الاحتفاظ بقاعدة البيانات ضمن Dashboard → Database → Cleanup — تُحذف السجلات القديمة بواسطة مهمة التنظيف الدورية (`src/lib/db/cleanup.ts`)
- تحقق من وجود أخطاء في `src/lib/db/usage*.ts` — يتم تسجيل حالات فشل الكتابة إلى قاعدة البيانات، لكنها لا تظهر للمستخدم
- تحقق من أن الطلب وصل بالفعل إلى `chatCore` — افحص توجيه combo

### "الحصة لا تُطبَّق"

- تحقق من إعداد `quotaLimit` الخاص بالمفتاح
- تحقق من ضبط `quotaWindow` بشكل صحيح
- ابحث عن سجلات `quotaSnapshots` — يجب إنشاؤها مع كل طلب
