## مرجع سريع

**هل أنت جديد على OmniRoute؟** ابدأ من هنا — فهذه الحلول تعالج 90% من المشكلات:

| ما أراه                        | ما يعنيه                               | ما يجب فعله                                                                                  |
| ------------------------------ | -------------------------------------- | -------------------------------------------------------------------------------------------- |
| "يتعذر الاتصال"                | OmniRoute لا يعمل                      | شغّل `omniroute` أو `docker restart omniroute`                                               |
| "مفتاح API غير صالح"           | مفتاحك غير صحيح أو منتهي الصلاحية      | أعد نسخ المفتاح من موقع موفّر الخدمة                                                         |
| "تم تجاوز حد المعدل"           | أنت ترسل طلبات كثيرة جدًا              | انتظر دقيقة واحدة، أو استخدم `model: "auto"` للتبديل الاحتياطي التلقائي                      |
| "تم تجاوز الحصة"               | لقد استنفدت حصتك المجانية/المدفوعة     | صِل المزيد من الموفّرين، أو استخدم الموفّرين المجانيين (Kiro، Pollinations)                  |
| "استجابات بطيئة"               | الموفّر مشغول أو بعيد                  | استخدم `model: "auto/fast"` أو صِل موفّرًا أسرع (Groq، Cerebras)                             |
| "تم استخدام موفّر غير صحيح"    | اختار `auto` موفّرًا مختلفًا           | هذا طبيعي! يختار `auto` الخيار الأفضل. افرض موفّرًا محددًا باستخدام `model: "openai/gpt-4o"` |
| "502 Bad Gateway"              | الموفّر متوقف                          | انتظر وأعد المحاولة، أو استخدم `model: "auto"` للتبديل بين الموفّرين                         |
| "401 Unauthorized"             | بيانات اعتمادك غير صحيحة               | تحقّق من مفتاح API أو أعد المصادقة باستخدام OAuth                                            |
| "لم يتم التعرّف على omniroute" | يفتقد Windows PATH وحدات node العمومية | أضف بادئة npm العمومية إلى Windows PATH. اعثر عليها باستخدام `npm config get prefix`.        |
| "429 Too Many Requests"        | تم تقييد معدل الطلبات                  | انتظر دقيقة واحدة، أو صِل المزيد من الموفّرين                                                |

**أما زلت عالقًا؟** راجع [استكشاف الأخطاء وإصلاحها بالتفصيل](#detailed-troubleshooting) أدناه، أو اطرح سؤالك على [Discord](https://discord.gg/U47eFqAXCn).

## استكشاف الأخطاء وإصلاحها بالتفصيل

---

### تقييد المعدل لدى الموفّرين المجانيين (429 / 400 / 401)

**العَرَض**: عند استخدام `model: "auto"` مع الموفّرين المجانيين/الذين لا يتطلبون مصادقة (opencode وauggie وغيرهما)، قد تحصل بشكل متقطع على `HTTP 429` أو `400` أو `401` بدلًا من الإجابات. تنجح الطلبات عند إعادة محاولة الموجّه نفسه بعد لحظات، لكن الأتمتة (مهام cron والوكلاء والبرامج النصية) تتعطل عند أول إخفاق.

**السبب الجذري**: تتراكم ثلاثة أوضاع إخفاق مستقلة:

1. **حد معدل الموفّر (`429`)**: يمكن للخطط المجانية فرض حصة لكل نافذة زمنية. تستنفد دفعة من الاستدعاءات المتوازية هذه الحصة، ولذلك يُرفض الطلب التالي حتى إعادة ضبط النافذة.
2. **نموذج معطّل في التمرير المباشر (`400`/`401`)**: يمكن أن تتضمن مجموعات `auto/*` نماذج تمرير مباشر من `opencode` تكون مسجلة في الكتالوج، لكنها لا تملك بيانات اعتماد فعّالة (مثلًا `oc/north-mini-code-free` ← `401`). يجرّب الموجّه التلقائي أحدها، فيفشل، وينتشر الخطأ قبل بدء التبديل الاحتياطي.
3. **تضخيم التزامن (`429` تحت الحمل)**: عندما تصل جلسات متعددة للوكلاء/cron إلى `auto` في الوقت نفسه، يتجاوز معدل الطلبات الإجمالي ما يستطيع الموفّرون المجانيون تحمّله، فتُصنَّف الاستدعاءات المشروعة على أنها مسيئة.

**الحل المتحقق منه (وفقًا لتقارير المجتمع، 2026-08-10)**: اضبط ثلاثة متغيرات بيئة بحيث تستوعب آليات التدوير والتزامن والتبديل الاحتياطي تقلّبات الخطة المجانية بدلًا من التعطل بسببها:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # انتقل إلى نموذج/موفّر آخر عند 400/401 (يتخطى نماذج التمرير المباشر المعطّلة)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # حد قبول صريح للطلبات الثقيلة (غير معيّن افتراضيًا: لا يوجد حد لعدد الطلبات، راجع الملاحظة أدناه)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # ارفع الانتظار المحدود ليتجاوز القيمة الافتراضية لـ RATE_LIMIT_MAX_WAIT_MS مع المصادر البطيئة
```

عيّن هذه المتغيرات في بيئة عملية OmniRoute (الخدمة الخلفية، مثلًا عبر ملف LaunchAgent plist أو `systemctl edit`)، ثم أعد تشغيل OmniRoute. علامة التدوير هي الأداة الوحيدة ذات التأثير الأكبر: فهي تحوّل الإخفاق الحتمي إلى إعادة محاولة شفافة لدى موفّر سليم ضمن المجموعة.

**ملاحظة**: يضع `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` حدًا لعدد الطلبات الثقيلة — ذات السياق الطويل — التي تعمل في آن واحد؛ وهذا الحد بوابة قبول وليس مقيّد معدل خاصًا بالموفّر. **تحديث #503-fanout:** لم يعد هذا المتغير معيّنًا افتراضيًا (إذ لا يُطبّق الآن إلا عند ضبطه صراحةً، كما هو موضح أعلاه) — وبدلًا من ذلك، يُنظَّم قبول الطلبات الثقيلة بواسطة ميزانية بايتات مشتقة تلقائيًا (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) تتكيّف مع الحد الفعلي لذاكرة المضيف، ولذلك يُفترض أن يشهد النشر الجديد عددًا أقل بكثير من حالات رفض `503 chat_admission_busy` من دون ضبط هذا المتغير إطلاقًا؛ ومع ذلك، يظل تعيينه صراحةً هنا يعمل تمامًا كما هو موثّق. تُقيَّد التجاوزات الصريحة لميزانية البايتات ضمن النطاق 8 MiB–2 GiB. لا يُعد `413 body_exceeds_budget` حالة مؤقتة: زِد ميزانية البايتات تلك، أو اخفض `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`، أو ارفع حد ذاكرة العملية. يُعد تخفيف الحمل بسبب `inflight_bytes_budget` تنازعًا مؤقتًا ويظل قابلًا لإعادة المحاولة. يُدار تقييد المعدل لكل موفّر (`open-sse/services/rateLimitManager.ts`) بشكل منفصل بواسطة `RATE_LIMIT_MAX_WAIT_MS` و`RATE_LIMIT_MAX_QUEUE_DEPTH` و`RATE_LIMIT_AUTO_ENABLE` — راجع `.env.example`.

**كيفية التحقق من نجاح الإصلاح**: شغّل الوكيل/مهمة cron مرتين بتتابع سريع، وتأكد من نجاح كلتا المحاولتين. قبل الإصلاح، كانت المحاولة الثانية تُظهر عادةً الخطأ `429`/`401`. بعد الإصلاح، تُعاد محاولة الطلبات الفاشلة (إن وُجدت) بشفافية، وتكتمل المكالمة. يمكنك أيضًا تنفيذ `curl /monitoring/health` ومراقبة الحقل `rateLimitedUntil` ضمن اتصالات مزوّدي الخدمة، وكذلك `circuitBreakers.providerBreakers[].state` لمزوّدي الخدمة المتأثرين — تكون الحالة واحدة من `CLOSED` أو `DEGRADED` أو `OPEN` أو `HALF_OPEN` (راجع `src/shared/utils/circuitBreaker.ts`)، وسيتحول مزوّد الخدمة الذي يستمر في الفشل من `CLOSED → DEGRADED → OPEN` قبل أن تسمح نافذة إعادة الضبط بمرور محاولة اختبار (`HALF_OPEN`).

**إذا استمر ظهور الخطأ 429**: فهذا يعني أن الحساب النشط لدى مزوّد الخدمة قد استنفد بالفعل _حصته_ (وليس مجرد حد المعدل). أضف حسابًا ثانيًا لمزوّد الخدمة نفسه في لوحة تحكم OmniRoute ← مزوّدو الخدمة ← الحسابات، أو أضف مزوّد خدمة مجانيًا آخر (مثل `routeway` أو `auggie`). لا يفيد التناوب إلا مع أخطاء المعدل/400/401 المؤقتة؛ أما الاستنفاد الكامل للحصة فيتطلب بيانات اعتماد ثانية أو مزوّد خدمة مختلفًا.

**إذا ظهر الخطأ 403 في نماذج الرؤية (`auto/vision`، `bazaarlink/*`)**: فالحساب المتصل لا يمتلك خطة مدفوعة تشمل الرؤية، أو أن مفتاح API لا يملك أذونات كافية. تحقق في لوحة تحكم مزوّد الخدمة من أن نطاق المفتاح يشمل الرؤية/الوسائط المتعددة، أو اربط حسابًا من فئة مدفوعة واحتفظ به كوجهة للرؤية.

## تحذيرات npm install ‏(ERESOLVE / peer / deprecated)

عند تشغيل `npm install -g omniroute`، قد ترى عددًا كبيرًا من التحذيرات مثل `npm warn ERESOLVE`، وإشعارات تبعيات peer، ورسائل `deprecated`. **هذه التحذيرات متوقعة وغير ضارة.** يكون التثبيت قد نجح إذا رأيت `added <N> packages` في المخرجات.

لإخفاء تحذيرات حل تبعيات peer، استخدم صيغة التثبيت المدعومة من OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

يخفي `--legacy-peer-deps` إشعارات `ERESOLVE` وتبعيات peer فقط. تظل إشعارات الإهمال ظاهرة لأنها تأتي من حزم خارجية انتقالية؛ وهي لا تشير إلى فشل التثبيت.

تأتي التحذيرات من نطاقات قديمة لتبعيات peer في حزم خارجية لا يتحكم فيها OmniRoute:

1. **يتطلب `marked-terminal` الإصدار `marked >=1 <16`، ولكن عُثر على `marked@18`** — يعمل بصورة سليمة عمليًا؛ فنطاق peer في المشروع الأصلي قديم فحسب.
2. **`deprecated prebuild-install@7.1.3`** — أداة مساعدة انتقالية لجلب الملفات الثنائية الأصلية. لا تُستخدم
   لتثبيت رابط النقل المثبّت الإصدار `wreq-js`، ولا تشير إلى فشل إعداد نقل
   موفّر ملفات تعريف ارتباط الويب.

**لا يلزم اتخاذ أي إجراء** — لا يمكن إسكات التحذيرات بالكامل دون إنشاء تفرعات من الحزم الأصلية.

## تحذير حظر نصوص تثبيت npm (التثبيت العام)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

عند تشغيل `npm install -g omniroute`، تحظر إصدارات npm الأحدث (v11+ وv12+) نصوص دورة حياة الحزم افتراضيًا، وتعرض تحذيرًا بشأن نصوص التثبيت:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### هل يمكن تجاهل هذا التحذير؟

**جزئيًا، ولكن لا يُنصح بالتشغيل من دون النصوص البرمجية.** يتضمن OmniRoute آليات احتياطية سلسة: إذا تعذر تحميل روابط `better-sqlite3` الأصلية من الحزمة المستقلة، ينتقل التطبيق إلى برامج تشغيل بديلة مثل `node:sqlite` أو `sql.js` (راجع [حل بيئة تشغيل SQLite](../ops/SQLITE_RUNTIME.md)). سيظل الخادم يعمل، لكن التشغيل باستخدام بدائل WASM مثل `sql.js` يعطّل وضع WAL (التسجيل المسبق للكتابة) في SQLite ويزيد الحمل على الذاكرة ومزامنة القرص.

### ما النصوص البرمجية المطلوبة فعليًا؟

ليست كل النصوص البرمجية المحظورة ضرورية لتشغيل OmniRoute:

- **أساسية (`omniroute`، `better-sqlite3`):** يعمل OmniRoute من حزمة تطبيق Next.js مستقلة (`dist/`). أثناء التثبيت، ينزّل npm برنامج تشغيل SQLite الأصلي الخاص بالمضيف أو يجمعه في `node_modules/better-sqlite3/` ذي المستوى الأعلى. بعد ذلك، يتحقق نص `postinstall` الخاص بـ OmniRoute (`scripts/build/postinstall.mjs`) من هذه الملفات الثنائية الخاصة بالمضيف وينسخها إلى `dist/node_modules/` لكي يتمكن الخادم المستقل من الوصول إليها. إذا حُظر نص postinstall الخاص بـ `omniroute`، فسيتم تخطي خطوة النسخ هذه.
- **اختيارية/انتقالية (`keytar`، `@parcel/watcher`، `@swc/core`، `protobufjs`، `esbuild`):** هذه أدوات مساعدة للبناء أو أدوات مراقبة أو أدوات لسلسلة مفاتيح النظام. يؤدي السماح بها إلى منع تحذيرات البناء، لكنها ليست مطلوبة لوظائف التوجيه الأساسية.
- **مستبعدة (`onnxruntime-node`):** تبعية اختيارية لعمليات تضمين الذكاء الاصطناعي المحلية، وهي **غير** مطلوبة لتشغيل OmniRoute. ينزّل نص postinstall الخاص بها نحو 300MB من أصول CUDA من NuGet؛ لا تُدرجها في قائمة السماح ما لم تكن تنوي صراحةً استخدام تسريع ONNX المحلي على أجهزة مدعومة.

### الإصلاح الموصى به

للسماح بنصوص التثبيت المطلوبة أثناء التثبيت العام وإسكات التحذيرات، مرّر `--allow-scripts` إلى OmniRoute وتبعياته الأصلية:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

بدلًا من ذلك، لضبط هذا بصورة دائمة لجميع عمليات التثبيت العامة في حساب المستخدم الخاص بك:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### التحقق من التثبيت

بعد التثبيت، شغّل أداة التشخيص المضمّنة للتأكد من سلامة الروابط الأصلية وبيئة التشغيل:

```bash
omniroute doctor
```

## Gemini Web وPlaywright Chromium

إذا أعاد طلب Gemini Web الحالة `503` مع رسالة تفيد بأن Playwright Chromium
غير مثبّت، فهذا يعني أن حزمة npm موجودة، لكن الملف الثنائي للمتصفح مفقود.
يفصل Playwright عمدًا تنزيلات المتصفح عن تثبيت حزمة npm،
لذلك تكون هذه الاستجابة متوقعة إلى أن يتم تثبيت المتصفح.

عند استخدام تثبيت عام لـ npm، ثبّت Chromium من دليل حزمة OmniRoute
بحيث تنتمي ذاكرة التخزين المؤقت للمتصفح إلى تثبيت Playwright نفسه:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

أعد تشغيل OmniRoute بعد التثبيت، ثم أعد محاولة طلب Gemini Web. إذا كنت
تشغّل OmniRoute من صورة Docker، فاستخدم صورة `-web` (أو هدف البناء `runner-web`)،
التي تتضمن Chromium واعتمادياته؛ أما الصورة الأساسية فلا تتضمنها.

## النتائج الإيجابية الكاذبة لمكافحة الفيروسات

<a name="antivirus-false-positives"></a>

### يضع Avast/AVG ملف `README.md` في الحجر الصحي مع التصنيف `MD:HttpRequest-inf[Susp]`

**هذه نتيجة إيجابية كاذبة. لا توجد أي إصابة، ولا يلزم اتخاذ أي إجراء.**

يشغّل Avast وAVG آلية استدلالية تضع علامة على الملفات النصية العادية/ملفات Markdown التي تحتوي على العديد من الروابط التي تبدو كطلبات HTTP. يأتي ملف `README.md` الخاص بـ OmniRoute ضمن حزمة npm (فهو مدرج في `package.json` ← `files`)، ولذلك يُوضَع في `node_modules/omniroute/README.md` عند التثبيت العام — ويحتوي على نحو 15 مثالًا من نوع `http://localhost:20128/...` (نقاط نهاية MCP الخاصة بـ HTTP/SSE، وعنوان URL الخاص بـ A2A `.well-known`، ومقتطفات `curl`). كثافة الروابط هذه كافية لتشغيل الآلية الاستدلالية.

إذا بدأ هذا مؤخرًا فقط: لم تتغير طبيعة الملف. توسّع جدول نقاط النهاية في README (أُضيفت MCP HTTP وSSE وA2A)، كما أُضيف المزيد من أمثلة `curl`، ما جعله يتجاوز الحد.

الملف مجرد توثيق غير نشط ولا يحتوي إطلاقًا على أي محتوى قابل للتنفيذ. يمكنك استعادته بأمان من الحجر الصحي.

**ما يجب فعله:**

1. **أوقف الإشعارات** — استثنِ دليل التثبيت في برنامج مكافحة الفيروسات لديك
   (Avast: الإعدادات ← الاستثناءات)، مع إضافة مسار `node_modules` العام و/أو دليل بيانات
   OmniRoute (`~/.omniroute/`).
2. **أبلغ عن النتيجة الإيجابية الكاذبة** — <https://www.avast.com/false-positive-file-form.php>،
   مع إرفاق ملف `README.md` الموضوع في الحجر الصحي. هذا هو الإصلاح الذي يفيد الجميع، لأن
   الآلية الاستدلالية للمورّد تبالغ في رد فعلها تجاه ملف نصي.

**لماذا لا «نصلح» هذا من جانبنا:** تستخدم جميع الأمثلة `http://localhost`، ولا يمكن أن يستخدم
localhost بروتوكول `https` من دون مشكلات الشهادات الموقّعة ذاتيًا. إن تشويه التوثيق للتحايل على
الآلية الاستدلالية لأحد المورّدين سيضر بكل قارئ من أجل إرضاء خلل في أداة الفحص.

### يضع Kaspersky علامة على تطبيق سطح المكتب باعتباره `PDM:Trojan.Win32.Generic`

**هذه نتيجة إيجابية كاذبة صادرة عن آلية استدلالية سلوكية. لا توجد أي إصابة.** تعني البادئة
`PDM:` لدى Kaspersky أن الحكم صادر عن وحدة الدفاع الاستباقي (مراقب النظام)، التي تقيّم ما
_يفعله_ برنامج التثبيت بدلًا من مطابقته مع برمجيات ضارة معروفة. عند تشغيلها، يقوم Kaspersky
«بالتراجع» عن عملية التثبيت بأكملها — ويحذف الملفات التي سبق أن كتبها — ولذلك ينتهي الأمر
بالتطبيق معطّلًا أو مفقودًا.

الملفات التي يضع عليها علامة هي أجزاء قياسية من تبعيات معلنة ومفتوحة المصدر مضمّنة مع تطبيق
سطح المكتب، مثل:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` و
  `workerProcessEntry.js` — مكتبة [Playwright](https://playwright.dev) لأتمتة المتصفح،
  والمستخدمة لتسجيل الدخول إلى الموفّر من داخل التطبيق وللدردشة المعتمدة على المتصفح.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — الربط الأصلي المثبّت الإصدار لـ `wreq-js`، والمستخدم لطلبات HTTP ذات بصمة المتصفح لدى
  الموفّرين المعتمدين على ملفات تعريف ارتباط الويب (`<arch>` تكون `x64` أو `arm64`).

**سبب تشغيلها:** برنامج تثبيت Windows **غير موقّع برمجيًا حتى الآن**، ولذلك لا يتمتع برنامج
تثبيت NSIS غير الموقّع بأي سمعة، وتعمل الآليات الاستدلالية السلوكية بأقصى قدر من التشدد. وعند
الجمع بين ذلك وبين DLL أصلي مضمّن ومئات ملفات `.js` المكتوبة ضمن
`%LOCALAPPDATA%\Programs\OmniRoute` (بما في ذلك أدلة الحزم ذات لاحقات التجزئة من إصدار
Next.js المستقل)، يكون هذا كافيًا لتشغيل الآلية الاستدلالية. توقيع الشفرة مخطط له؛ وحتى
تنفيذه، قد يتكرر هذا الأمر مع الإصدارات الجديدة.

**ما يجب فعله:**

1. **تحقق أولًا من التنزيل** (لاستبعاد احتمال العبث بالملف). ينشر كل إصدار ملف
   `latest.yml`، الذي يغطي حقله `sha512` (بتنسيق base64) برنامج التثبيت
   `OmniRoute.Setup.<version>.exe`. في PowerShell، من المجلد الذي يحتوي على برنامج التثبيت:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   يجب أن يطابق الناتج `latest.yml` ← `sha512`. إذا لم يتطابق، فاحذف الملف وأعد تنزيله
   فقط من [صفحة إصدارات GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **الاستعادة + الاستثناء** — استعد العناصر التي جرى التراجع عنها من الحجر الصحي، وأضف
   استثناءً لـ `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky ← الإعدادات ← التهديدات
   والاستثناءات)، ثم أعد التثبيت.
3. **أبلغ عن النتيجة الإيجابية الكاذبة** — <https://opentip.kaspersky.com/>. تساعد بلاغات
   النتائج الإيجابية الكاذبة المقدّمة من المستخدمين فعلًا في تسريع الإدراج في قائمة السماح.

## توافق Node.js

<a name="nodejs-compatibility"></a>

### تعطُّل صفحة تسجيل الدخول أو ظهور خطأ "Module self-registration"

**السبب:** أنت تستخدم إصدارًا من Node.js خارج الحد الأدنى المعتمد لبيئة التشغيل الآمنة في OmniRoute. والحالة الأكثر شيوعًا هي استخدام مستوى تصحيح قديم من Node 22 أو 24 يقل عن الحد الأمني المحدَّث الذي يتطلبه OmniRoute.

**الأعراض:**

- تعرض صفحة تسجيل الدخول شاشة فارغة أو خطأً من الخادم
- تعرض وحدة التحكم `Error: Module did not self-register` أو أخطاء مشابهة في الربط الأصلي
- تعرض صفحة تسجيل الدخول **شريط تحذير برتقاليًا** يتضمن إصدار Node لديك إذا كانت بيئة التشغيل خارج سياسة الدعم الآمنة

**الإصلاح:**

1. ثبّت إصدار LTS مدعومًا من Node.js (الموصى به: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. تحقّق من إصدارك: يجب أن يعرض `node --version` الإصدار `v24.0.0` أو إصدارًا أحدث ضمن خط LTS من 24.x
3. أعد تثبيت OmniRoute: `npm install -g omniroute`
4. أعد التشغيل: `omniroute`

> **الإصدارات الآمنة المدعومة:** `>=22.22.2 <23` أو `>=24.0.0 <27`. يحظى كل من Node.js 24.x LTS (Krypton) وNode.js 26 بدعم كامل.

### npm v11+: لم يتم تثبيت `better-sqlite3` (تعذّر العثور على الوحدة)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**السبب:** يحظر npm v11 (المضمّن مع Node.js 24+) افتراضيًا البرامج النصية الخاصة بتثبيت التبعيات الاختيارية. ونظرًا إلى أن `better-sqlite3` مُدرج في `optionalDependencies` ويتطلب ترجمة أصلية (`node-gyp rebuild`)، فإن npm يتخطاه بصمت.

**الأعراض:**

- يتعطّل الخادم عند بدء التشغيل مع ظهور `Cannot find module 'better-sqlite3'`
- يعرض `ls node_modules/better-sqlite3` الرسالة "No such file or directory"
- يعرض `npm ls better-sqlite3` القيمة `(empty)`

**الإصلاح:**

1. وافق على البرامج النصية الخاصة بالتثبيت ثم أعد التثبيت:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. أو ثبّت الحزمة المبنية مسبقًا يدويًا:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. تحقّق من أنها تعمل: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**السبب:** بعد تنفيذ `npm install -g omniroute` عالميًا، ربما تم تجميع الملف الثنائي الأصلي لـ `better-sqlite3` داخل الحزمة لمعمارية أو ABI خاص بـ Node.js يختلف عما يعمل محليًا. وهذا شائع على macOS (سواء Apple Silicon أو Intel) عندما لا يتطابق الملف الثنائي المبني مسبقًا مع بيئتك.

**الأعراض:**

- يفشل الخادم فورًا عند بدء التشغيل مع ظهور خطأ `dlopen`
- يحتوي الخطأ على `slice is not valid mach-o file`
- مثال كامل:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**الإصلاح — أعد البناء لبيئتك المحلية (لا يلزم الرجوع إلى إصدار أقدم من Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ملاحظة:** يؤدي هذا إلى إعادة ترجمة الربط الأصلي بما يتوافق مع إصدار Node.js المحلي ومعمارية وحدة المعالجة المركزية لديك، مما يحل مشكلة عدم تطابق الملفات الثنائية. نطاق بيئة التشغيل المدعوم رسميًا هو **`>=22.22.2 <23` أو `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` في `src/shared/utils/nodeRuntimeSupport.ts`، بما يتوافق مع حقل `engines` في `package.json`). يحظى كل من Node.js 24.x LTS (Krypton) وNode.js 26 بدعم كامل مع `better-sqlite3` v12.x.

## مشكلات الوكيل

<a name="proxy-issues"></a>

### يُظهر التحقق من المزوّد الخطأ "fetch failed"

**السبب:** كانت نقطة نهاية التحقق من مفتاح API ‏(`POST /api/providers/validate`) تتجاوز سابقًا إعدادات الوكيل، مما تسبب في حدوث أعطال ضمن البيئات التي تتطلب التوجيه عبر وكيل.

**الإصلاح (v3.5.5+):** تم إصلاح ذلك الآن. يمر التحقق من المزوّد عبر `runWithProxyContext`، مع الالتزام تلقائيًا بإعدادات الوكيل على مستوى المزوّد والإعدادات العامة للوكيل.

### يفشل فحص سلامة الرمز المميز مع ظهور "fetch failed"

**السبب:** لم تكن عملية تحديث رموز OAuth المميزة في الخلفية تحل إعدادات الوكيل لكل اتصال.

**الإصلاح (v3.5.5+):** يحل الآن مجدول فحص سلامة الرمز المميز إعدادات الوكيل لكل اتصال قبل محاولة التحديث. حدّث إلى v3.5.5+.

### يُرجع وكيل SOCKS5 الخطأ "invalid onRequestStart method"

**السبب:** في Node.js 22، لا يتوافق موزّع undici@8 مع تنفيذ `fetch()` المضمّن في Node.

**الإصلاح (v3.5.5+):** يستخدم OmniRoute الآن دالة `fetch()` الخاصة بـ undici عند تنشيط موزّع وكيل، مما يضمن سلوكًا متسقًا. حدّث إلى v3.5.5+.

### وكيل MITM ضمن WSL: لا يتم اعتراض تطبيقات سطح المكتب على مضيف Windows

**السبب:** يتم تثبيت وكيل MITM وشهادة CA الخاصة به داخل البيئة التي يعمل فيها OmniRoute. في WSL، تكون هذه البيئة هي نظام Linux الضيف، بينما تعمل تطبيقات الذكاء الاصطناعي لسطح المكتب (Kiro وTrae وCopilot وZed و…) على مضيف Windows. لا تثق تطبيقات المضيف بمخزن شهادات النظام الضيف ولا تمرّر اتصالاتها عبر وكيل النظام الضيف، ولذلك لا يتم تفعيل اعتراض تطبيقات سطح المكتب هناك.

**التوصية:** شغّل OmniRoute مباشرةً على نظام التشغيل نفسه الذي تعمل عليه تطبيقات سطح المكتب التي تريد اعتراضها (Windows لتطبيقات Windows؛ وينطبق الأمر نفسه على macOS/Linux). يتطلب إبقاء OmniRoute داخل WSL مع استهداف تطبيقات المضيف الوثوق يدويًا بشهادة CA التي تم إنشاؤها على مضيف Windows، وتوجيه إعدادات الشبكة/الوكيل لكل تطبيق على المضيف إلى نقطة نهاية وكيل WSL — وهذا إعداد غير مدعوم وهش.

## مشكلات المزوّد

### "Language model did not provide messages"

**السبب:** تم استنفاد حصة المزوّد.

**الإصلاح:**

1. تحقق من متعقب الحصة في لوحة التحكم
2. استخدم مجموعة تتضمن مستويات احتياطية
3. انتقل إلى مستوى أرخص/مجاني

### تحديد معدل الطلبات

**السبب:** تم استنفاد حصة الاشتراك.

**الإصلاح:**

- أضف خيارات احتياطية: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- استخدم GLM/MiniMax كخيار احتياطي منخفض التكلفة

### انتهاء صلاحية رمز OAuth المميز

يحدّث OmniRoute الرموز المميزة تلقائيًا. إذا استمرت المشكلات:

1. لوحة التحكم → المزوّد → إعادة الاتصال
2. احذف اتصال المزوّد وأضفه من جديد

### حسابات Kiro المتعددة: الحساب الثاني يبطل الأول

**السبب:** تفرض الواجهة الخلفية لـ Kiro جلسة نشطة واحدة لكل تسجيل عميل OIDC.
عندما يشترك حسابان في العميل المسجّل نفسه (الاتصالات المستوردة قبل v3.8.0)،
يؤدي تحديث الرمز المميز لأحد الحسابين إلى إبطال رمز التحديث الخاص بالحساب الآخر.

**الإصلاح (v3.8.0+):** أعِد استيراد الاتصالات المتأثرة.
بدءًا من v3.8.0، يسجّل كل اتصال Kiro جديد يُنشأ عبر **استيراد الرمز المميز**،
أو **تسجيل الدخول الاجتماعي عبر Google/GitHub**، أو **الاستيراد التلقائي** تلقائيًا عميل
OIDC مخصصًا له. وبذلك يكون الاتصال معزولًا بالكامل، ولا يؤثر تحديث أحد
الحسابات في أي حساب آخر.

لا تتضمن الاتصالات التي تم استيرادها _قبل_ v3.8.0 تسجيل عميل خاصًا بكل اتصال.
تستمر هذه الاتصالات في استخدام نقطة نهاية التحديث المشتركة للمصادقة الاجتماعية.
للحصول على العزل، احذف الاتصال القديم من لوحة التحكم → المزوّدون، ثم أعد إضافته
عبر أي من مسارات الاستيراد الثلاثة.

للاطلاع على التفاصيل الكاملة والتعليمات خطوة بخطوة لإضافة حسابي Kiro جنبًا إلى جنب،
راجع [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## مشكلات السحابة

### أخطاء المزامنة السحابية

1. تحقّق من أن `BASE_URL` يشير إلى المثيل قيد التشغيل لديك (مثلًا، `http://localhost:20128`)
2. تحقّق من أن `CLOUD_URL` يشير إلى نقطة النهاية السحابية لديك (مثلًا، `https://omniroute.dev`)
3. حافظ على توافق قيم `NEXT_PUBLIC_*` مع القيم الموجودة على جانب الخادم

### تُرجع السحابة عند `stream=false` الخطأ 500

**العَرَض:** ظهور `Unexpected token 'd'...` على نقطة النهاية السحابية للمكالمات غير المتدفقة.

**السبب:** يُرجع المصدر الأساسي حمولة SSE بينما يتوقع العميل JSON.

**الحل البديل:** استخدم `stream=true` للمكالمات السحابية المباشرة. تتضمن بيئة التشغيل المحلية آلية احتياطية للتحويل من SSE إلى JSON.

### تشير السحابة إلى أنها متصلة، لكنها تعرض "مفتاح API غير صالح"

1. أنشئ مفتاحًا جديدًا من لوحة التحكم المحلية (`/api/keys`)
2. شغّل المزامنة السحابية: فعّل السحابة ← زامِن الآن
3. قد تستمر المفاتيح القديمة/غير المتزامنة في إرجاع `401` على السحابة

## مشكلات Docker

### إعادة تعيين اتصال Docker عبر IPv6

<a name="docker-ipv6"></a>

**الأعراض:** يُرجع `curl http://localhost:20128/v1/models` الرسالة `curl: (56) Recv failure: Connection reset by peer`. تعمل لوحة التحكم ونقاط النهاية التي لا تتطلب مصادقة، لكن نقاط النهاية التي تتطلب مصادقة تفشل — ما يجعل الأمر يبدو كمشكلة مصادقة، لكنه ليس كذلك.

**السبب:** ينشر `docker run -p 20128:20128` المنفذ على كل من `0.0.0.0` ‏(IPv4) و`::` ‏(IPv6)، لكن العملية داخل الحاوية تستمع إلى IPv4 فقط. على المضيفات التي يُحل فيها `localhost` إلى `::1` أولًا، يصل الاتصال إلى المنفذ المنشور عبر IPv6 من دون وجود مستمع خلفه ← تتم إعادة تعيين الاتصال.

**الإصلاح:**

1. **تشخيص سريع:** شغّل `curl -4 http://localhost:20128/v1/models`. إذا كان يعمل مع `-4` ويفشل من دونه، فلديك عدم تطابق في ربط IPv6.
2. **إصلاح دائم:** اربط بـ IPv4 صراحةً باستخدام `-p 127.0.0.1:20128:20128` في أمر `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   يفرض هذا الربط عبر IPv4، كما يمنع تعريض الوكيل على جميع واجهات المضيف.

## تصحيح الأخطاء

### تفعيل ملفات السجل

عيّن `APP_LOG_TO_FILE=true` في ملف `.env` لديك. تُكتب سجلات التطبيق ضمن `logs/`.
تُخزَّن عناصر الطلبات ضمن `${DATA_DIR}/call_logs/` عندما يكون مسار سجل المكالمات
مفعّلًا في الإعدادات.
عندما يكون التقاط المسار مفعّلًا، عيّن `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` لاستبعاد
حُمُولات أجزاء التدفق، أو اضبط `CALL_LOG_PIPELINE_MAX_SIZE_KB` لتغيير الحد الأقصى لحجم العناصر بوحدة KB.

### التحقق من سلامة المزوّد

```bash
# لوحة معلومات السلامة
http://localhost:20128/dashboard/health

# فحص سلامة API
curl http://localhost:20128/api/monitoring/health
```

### تخزين بيئة التشغيل

- الحالة الرئيسية: `${DATA_DIR}/storage.sqlite` (المزوّدون، والمجموعات، والأسماء البديلة، والمفاتيح، والإعدادات)
- الاستخدام: جداول SQLite في `storage.sqlite` ‏(`usage_history`، و`call_logs`، و`proxy_logs`) + `${DATA_DIR}/call_logs/` اختياريًا
- سجلات التطبيق: `<repo>/logs/...` (عندما تكون `APP_LOG_TO_FILE=true`)
- عناصر سجل المكالمات: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` عندما يكون مسار سجل المكالمات مفعّلًا

يؤدي إجراء **مسح السجل** في صفحة سجلات الطلبات إلى مسح `call_logs`، و`request_detail_logs`
القديم، ودليل العناصر المحلي `${DATA_DIR}/call_logs/`.

## مشكلات قاطع الدائرة

### بقاء المزوّد عالقًا في حالة OPEN

عندما يكون قاطع الدائرة الخاص بمزوّد في حالة OPEN، تُحظر الطلبات حتى انتهاء فترة التهدئة.

**الحل:**

1. انتقل إلى **لوحة المعلومات → الإعدادات → المرونة**
2. تحقّق من بطاقة قاطع الدائرة الخاصة بالمزوّد المتأثر
3. انقر على **إعادة تعيين الكل** لمسح جميع القواطع، أو انتظر حتى انتهاء فترة التهدئة
4. تأكّد من أن المزوّد متاح بالفعل قبل إعادة التعيين

### استمرار المزوّد في تفعيل قاطع الدائرة

إذا دخل مزوّد في حالة OPEN بشكل متكرر:

1. تحقّق من **لوحة المعلومات → الصحة → صحة المزوّد** للاطّلاع على نمط الفشل
2. انتقل إلى **الإعدادات → المرونة → ملفات تعريف المزوّدين** وزِد حدّ الفشل
3. تحقّق مما إذا كان المزوّد قد غيّر حدود واجهة API أو كان يتطلب إعادة المصادقة
4. راجع بيانات قياس زمن الاستجابة — فقد يؤدي زمن الاستجابة المرتفع إلى حالات فشل ناتجة عن انتهاء المهلة

## مشكلات نسخ الصوت

### خطأ "Unsupported model"

- استخدم معرّف نموذج يكون مقطعه الأول مزوّدًا لديك بيانات اعتماد له (`openai/whisper-1`، `openrouter/deepgram/nova-3`). يتطلب `deepgram/nova-3` المجرّد مفتاح Deepgram أصليًا.
- تحقّق من اتصال المزوّد في **لوحة المعلومات → المزوّدون**

### النسخ فارغ أو يفشل

- تحقّق من تنسيقات الصوت المدعومة: `mp3`، `wav`، `m4a`، `flac`، `ogg`، `webm`
- تأكّد من أن حجم الملف ضمن حدود المزوّد (عادةً < 25MB)
- تحقّق من صلاحية مفتاح API الخاص بالمزوّد في بطاقة المزوّد

| **المراقب المباشر** | راقب تدفق الطلبات في الوقت الفعلي لاكتشاف مشكلات الترجمة المتقطعة                   |

### مشكلات التنسيق الشائعة

- **عدم ظهور وسوم التفكير** — تحقّق مما إذا كان المزوّد المستهدف يدعم التفكير ومن إعداد ميزانية التفكير
- **اختفاء استدعاءات الأدوات** — قد تزيل بعض ترجمات التنسيقات الحقول غير المدعومة؛ تحقّق من ذلك في وضع ساحة التجربة
- **فقدان موجّه النظام** — يتعامل Claude وGemini مع موجّهات النظام بشكل مختلف؛ تحقّق من مخرجات الترجمة
- **تُرجع SDK سلسلة نصية أولية بدلًا من كائن** — حُلّت المشكلة في v1.x؛ يزيل معقّم الاستجابة الحقول غير القياسية (`x_groq`، `usage_breakdown`، إلخ) التي تتسبب في فشل تحقق Pydantic ضمن OpenAI SDK. إذا كنت لا تزال ترى هذه المشكلة في v3.x+، فيُرجى فتح بلاغ.
- **يرفض GLM/ERNIE الدور `system`** — حُلّت المشكلة في v1.x؛ يدمج مطبّع الأدوار رسائل النظام تلقائيًا مع رسائل المستخدم للنماذج غير المتوافقة. إذا كنت لا تزال ترى هذه المشكلة في v3.x+، فيُرجى فتح بلاغ.
- **الدور `developer` غير معروف** — حُلّت المشكلة في v1.x؛ يُحوّل تلقائيًا إلى `system` للمزوّدين من غير OpenAI. إذا كنت لا تزال ترى هذه المشكلة في v3.x+، فيُرجى فتح بلاغ.
- **عدم عمل `json_schema` مع Gemini** — حُلّت المشكلة في v1.x؛ يُحوّل `response_format` الآن إلى `responseMimeType` + `responseSchema` الخاصين بـGemini. إذا كنت لا تزال ترى هذه المشكلة في v3.x+، فيُرجى فتح بلاغ.

## إعدادات المرونة

### عدم تشغيل التحديد التلقائي لمعدل الطلبات

- لا ينطبق التحديد التلقائي لمعدل الطلبات إلا على موفّري مفاتيح API (وليس OAuth/الاشتراك)
- تحقّق من تمكين التحديد التلقائي لمعدل الطلبات في **الإعدادات → المرونة → ملفات تعريف الموفّرين**
- تحقّق مما إذا كان الموفّر يعيد رموز الحالة `429` أو ترويسات `Retry-After`

### ضبط التراجع الأُسّي

تدعم ملفات تعريف الموفّرين الإعدادات التالية:

- **التأخير الأساسي** — مدة الانتظار الأولية بعد أول فشل (القيمة الافتراضية: 1s)
- **الحد الأقصى للتأخير** — الحد الأقصى لمدة الانتظار (القيمة الافتراضية: 30s)
- **المُضاعِف** — مقدار زيادة التأخير لكل فشل متتالٍ (القيمة الافتراضية: 2x)

### منع الاندفاع المتزامن

عندما تصل طلبات متزامنة كثيرة إلى موفّر خاضع لتحديد معدل الطلبات، يستخدم OmniRoute قفل mutex مع التحديد التلقائي لمعدل الطلبات لتسلسل الطلبات ومنع حالات الفشل المتتابعة. يحدث هذا تلقائيًا لموفّري مفاتيح API.

### فشل طلبات الدردشة مع 503 / chat_admission_busy

**الأعراض:**

- تعيد نقطة نهاية إكمالات الدردشة استجابة `503` قابلة لإعادة المحاولة يكون رمز خطئها
  `chat_admission_busy`.
- تتضمن الاستجابة `Retry-After`. منذ #12135، تُشتق القيمة من الإشغال المرصود
  — وهي القيمة الأكبر بين نافذة `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` التي انتظرها الطلب بالفعل
  والمدة التي ظلت فيها الحجوزات الثقيلة الحالية محتجزة — مع التقريب إلى ثوانٍ كاملة
  ووضع حد أقصى قدره 60. عندما تكون بوابة القبول خاملة، تُحافظ القيمة على الحدود الدنيا السابقة: ثانيتان في
  المسار المستند إلى البايتات، وثانية واحدة في المسار المستند إلى البنية (والذي يتضمن أيضًا
  `reason: "structure_limit"`).
- قد يحدث هذا بينما تظل دردشة ثقيلة أخرى أو استجابة بث طويلة الأمد
  قيد التنفيذ.

نص استجابة المسار المستند إلى البايتات هو:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

تستخدم الاستجابة المستندة إلى البنية النوع والرمز نفسيهما، مع الرسالة
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
والقيمة `reason: "structure_limit"`.
عند الحدود الافتراضية، يُعد الطلب ثقيلًا من حيث البنية عندما يحتوي على `200` رسالة على الأقل،
أو `64` أداة على الأقل، أو `32,000` رمزًا مميزًا مقدّرًا على الأقل، أو عندما يستنفد تقدير البنية المحدود
حدوده البالغة `10,000` عقدة تمت زيارتها أو عمقًا قدره `12`.

**السبب:** هذا إجراء متعمّد لتخفيف الحمل داخل OmniRoute، وليس فشلًا لدى الموفّر المنبع.
تستخدم كل عملية آلية حماية محلية للعملية لحجز سعة محدودة للطلبات الثقيلة قبل الاحتفاظ
بنص طلب كبير وتحليله. يظل حجز الطلب الثقيل محتجزًا طوال عمر استجابة SSE.

**انتشار أخطاء #503:** قبل هذا الإصلاح، كانت آلية الحماية تضع حدًا للتزامن وفق عدد ثابت من الطلبات
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`، والقيمة الافتراضية `1`) بصرف النظر عن ذاكرة المضيف، ولذلك كان
توزيع عمل وكلاء البرمجة (عدة وكلاء فرعيين/واجهات CLI، مع نصوص طلبات تتجاوز عادةً 256 KB) ينهار إلى
تزامن فعلي يبلغ نحو 1 ويعيد أخطاء 503 تحت حمل طبيعي تمامًا. تضبط آلية الحماية نفسها الآن تلقائيًا:
إذ تتحكم فيها ميزانية بايتات تلقائية الاشتقاق لعمليات الإدخال (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`)
يُحدد حجمها استنادًا إلى الحد الفعلي لذاكرة العملية، كما أنها تراعي إشارة مباشرة لضغط الموارد — ولذلك
لا تخفف الحمل إلا عندما يتعرض المضيف فعلًا لضغط على الذاكرة، وليس لمجرد وصول أكثر من
طلب ثقيل واحد في الوقت نفسه. لا يزال حد العدد القديم (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
مُطبّقًا، ولكن فقط إذا عيّنته صراحةً.

عندما تكون السعة مشغولة، ينتظر الطلب الثقيل أولًا مدة تصل إلى
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (القيمة الافتراضية هي `RATE_LIMIT_MAX_WAIT_MS`؛ وتؤدي القيمة `0` إلى تعطيل الانتظار) حتى تتوفر خانة
قبل إعادة استجابة `503` القابلة لإعادة المحاولة. وُضع الانتظار المحدود لكي تتمكن
العملاء ذات نمط الوكلاء (OpenCode، وClaude Code، وCursor)، التي توزّع الطلبات الفرعية الثقيلة بالتزامن،
من تسلسل الاندفاع بدلًا من استنفاد ميزانية إعادة المحاولة بالكامل بسبب الرفض الفوري والتوقف في منتصف المهمة.
يُعرض الإشغال الحالي لحجوزات الطلبات الثقيلة وميزانية البايتات المحسوبة ومستوى ضغط الموارد المباشر
في `GET /api/monitoring/health` ← `chatAdmission` (`inflightBytes`، و`maxInflightBytes`،
و`budgetSource`، و`pressureSeverity`، و`countCapEnabled`) — تحقّق منها قبل تعديل أي متغير بيئة.
لا يتحكم الإعداد الإعدادات → المرونة → قائمة انتظار الطلبات → الطلبات المتزامنة في هذا الأمر؛ فهذا الإعداد
يدير آلية منفصلة لقائمة انتظار طلبات الموفّر.

**الإصلاح:**

1. أعد المحاولة أولًا. ينبغي للعملاء احترام `Retry-After` واستخدام التراجع بدلًا من تكرار
   الطلب فورًا.
2. تحقّق من `/api/monitoring/health` ← `chatAdmission` قبل ضبط أي شيء. تشير `countCapEnabled:
false` و`maxInflightBytes` ذات القيمة السخية إلى أن الميزانية المشتقة تلقائيًا تؤدي
   وظيفتها بالفعل؛ أما القيمة `high`/`critical` في `pressureSeverity` فتعني أن ذاكرة المضيف منخفضة فعلًا —
   ولا يمكن إصلاح ذلك باستخدام متغير بيئة للقبول، بل يتطلب مزيدًا من RAM أو عبء عمل أصغر.
3. لا تتجاوز الميزانية مباشرةً باستخدام `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` بدلًا من الرجوع إلى حد عدد
   الطلبات القديم إلا إذا أظهر `/api/monitoring/health` أن الميزانية المشتقة تلقائيًا صغيرة فعلًا
   بالنسبة إلى مضيفك (وهذا نادر — فهي تتدرج بالفعل من الحاويات إلى الأجهزة الفعلية).

راجع [مرجع متغيرات البيئة](../reference/ENVIRONMENT.md#4-security--authentication)
للاطلاع على إعدادات القبول المعتمدة.

## تصنيف اختياري لإخفاقات RAG / LLM ‏(16 مشكلة)

يضع بعض مستخدمي OmniRoute البوابة أمام حِزم RAG أو الوكلاء. في هذه الإعدادات، من الشائع ملاحظة نمط غريب: يبدو OmniRoute سليمًا (المزوّدون يعملون، وملفات تعريف التوجيه سليمة، ولا توجد تنبيهات بشأن حدود المعدل)، لكن الإجابة النهائية تظل خاطئة.

عمليًا، تنشأ هذه الحوادث عادةً من مسار RAG اللاحق، وليس من البوابة نفسها.

إذا كنت تريد مفردات مشتركة لوصف هذه الإخفاقات، فيمكنك استخدام WFGY ProblemMap، وهو مورد نصي خارجي بترخيص MIT يعرّف ستة عشر نمطًا متكررًا لإخفاقات RAG / LLM. وعلى مستوى عام، فهو يغطي:

- انحراف الاسترجاع وحدود السياق المعطّلة
- الفهارس ومخازن المتجهات الفارغة أو القديمة
- عدم التطابق بين التضمينات والدلالة
- مشكلات تجميع الموجّه ونافذة السياق
- انهيار المنطق والإجابات المفرطة في الثقة
- إخفاقات السلاسل الطويلة وتنسيق الوكلاء
- ذاكرة الوكلاء المتعددين وانحراف الأدوار
- مشكلات ترتيب النشر والتهيئة الأولية

الفكرة بسيطة:

1. عند التحقيق في استجابة سيئة، سجّل:
   - مهمة المستخدم وطلبه
   - تركيبة المسار أو المزوّد في OmniRoute
   - أي سياق RAG مستخدم في المراحل اللاحقة (المستندات المسترجعة، واستدعاءات الأدوات، وما إلى ذلك)
2. اربط الحادث برقم واحد أو رقمين من WFGY ProblemMap (`No.1` … `No.16`).
3. خزّن الرقم في لوحة المعلومات أو دليل التشغيل أو متتبّع الحوادث الخاص بك بجوار سجلات OmniRoute.
4. استخدم صفحة WFGY المقابلة لتحديد ما إذا كنت بحاجة إلى تغيير حزمة RAG أو المسترجِع أو استراتيجية التوجيه.

يتوفر النص الكامل والوصفات العملية هنا (ترخيص MIT، نص فقط):

[ملف README الخاص بـ WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

يمكنك تجاهل هذا القسم إذا كنت لا تشغّل مسارات RAG أو الوكلاء خلف OmniRoute.

## المشكلات المعروفة في v3.8.0

المشكلات الخاصة بإصدار v3.8.0 والحلول البديلة الحالية لها. إذا توفر إصلاح في تصحيح لاحق، فسيتم تحديث الإدخال أو إزالته.

### إخفاقات مصادقة Devin CLI

**الأعراض:**

- ظهور "Devin CLI غير موجود" أو "فشلت المصادقة" عند استدعاء الأدوات المدعومة من Devin
- يُبلغ فحص وقت تشغيل CLI عن `installed=false`

**الأسباب:**

- يشير `CLI_DEVIN_BIN` إلى مسار غير موجود
- Devin CLI غير مثبّت على المضيف

**الإصلاح:**

1. ثبّت Devin CLI لمنصتك
2. عيّن `CLI_DEVIN_BIN=/usr/local/bin/devin` (أو المسار الفعلي) في `.env`
3. أعد تشغيل OmniRoute واختبر مجددًا من **لوحة المعلومات → أدوات CLI**

### توقف فترة تهدئة النموذج (إعادة ضبط يدوية)

**الأعراض:**

- يظل النموذج مدرجًا ضمن فترة التهدئة حتى بعد انقضاء وقت انتهاء الصلاحية
- تستمر الطلبات في تخطي النموذج ضمن التوجيه المركّب رغم أن الطابع الزمني أصبح في الماضي

**إعادة الضبط اليدوية:**

- **لوحة المعلومات:** **الإعدادات → فترات تهدئة النماذج** → انقر على **إعادة التفعيل** في البطاقة المتأثرة
- **API:** ‏`DELETE /api/resilience/model-cooldowns` مع ترويسات مصادقة الإدارة

### فشل اتصال مزوّد Command Code مع الخطأ 403

**الأعراض:**

- ظهور 403 عند اختبار اتصال مزوّد Command Code
- تعرض بطاقة المزوّد "غير مصرح به" بعد إضافته حديثًا

**السبب:** لم يكتمل تدفق OAuth (لم يتم تلقي رد الاتصال أو لم يتم حفظ الرمز المميز).

**الإصلاح:**

- شغّل `omniroute providers` من CLI لإعادة تشغيل تدفق OAuth، أو
- أعد تشغيل OAuth من **لوحة المعلومات → المزوّدون → Command Code → إعادة الاتصال**

### يعيد ModelScope فترات تهدئة صارمة مع الخطأ 429

**الأعراض:**

- فترات تهدئة قصيرة جدًا أو فورية على ModelScope بعد دفعة صغيرة من الطلبات
- يتخطى التوجيه المركّب ModelScope في وقت أبكر من المتوقع

**السبب:** يرسل ModelScope ترويسات `Retry-After` خاصة بالمزوّد. يتضمن v3.8.0 معالجة مخصصة لهذه الترويسات، ولذلك تسيء الإصدارات الأقدم تفسيرها على أنها إشارات عامة لحد المعدل.

**الإصلاح:**

- تأكد من استخدامك v3.8.0 أو إصدارًا أحدث
- تحقق من تمكين مفتاح التبديل `useUpstream429BreakerHints` ضمن **الإعدادات → المرونة**

### غياب OMNIROUTE_WS_BRIDGE_SECRET في بيئة الإنتاج

**الأعراض:**

- ظهور 401 في كل طلبات جسر WebSocket الخاصة بـ Codex/Responses عند التشغيل على مضيف إنتاج بعيد
- تُغلق مصافحة جسر WebSocket فور الاتصال

**السبب:** متغير البيئة `OMNIROUTE_WS_BRIDGE_SECRET` غير موجود في بيئة الإنتاج.

**الإصلاح:**

1. أنشئ سرًا عشوائيًا: `openssl rand -hex 32`
2. عيّن `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` في بيئة خادم الإنتاج (وفي أي عميل يتصل بالجسر)
3. أعد تشغيل OmniRoute

### Responses API: خفض وضع الخلفية إلى الوضع المتزامن

**الأعراض:**

- تسجيل التحذير: `background mode degraded to synchronous`
- يعيد طلب `background: true` استجابة متزامنة عادية بدلًا من معرّف مهمة تعمل في الخلفية

**السبب:** يخفض v3.8.0 عمدًا طلبات `background: true` في Responses API إلى التنفيذ المتزامن مع إصدار تحذير. التنفيذ الكامل غير المتزامن في الخلفية ميزة ستتوفر مستقبلًا.

**الإصلاح:**

- عدّل العميل لإجراء الاستدعاء من دون `background`، أو
- انتظر إصدارًا لاحقًا يوفر وضع الخلفية الكامل غير المتزامن (تابع سجل التغييرات)

## بطء بدء التشغيل / انتهاء مهلة الجاهزية

إذا عرضت واجهة سطر الأوامر `⚠ Server did not respond within 60s` مع أن الخادم
يعمل فعليًا، فإن المهلة المخصصة لفحص الجاهزية قصيرة جدًا بالنسبة إلى بيئتك.

يحدث هذا عادةً على Windows (بسبب برامج مكافحة الفيروسات أو مراقبات نظام الملفات) أو في الحاويات
ذات أعباء عمل بدء التشغيل الثقيلة.

**الحل — زِد المهلة:**

```bash
# عبر متغير بيئة (يستمر عبر عمليات التشغيل):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 دقائق
omniroute serve

# عبر خيار واجهة سطر الأوامر (لمرة واحدة):
omniroute serve --ready-timeout 180000
```

القيمة الافتراضية هي 60 000 مللي ثانية (60 ثانية). هذا التحذير لأغراض إعلامية فقط؛ إذ يواصل الخادم
بدء التشغيل في الخلفية وسيصبح متاحًا بمجرد اكتمال الإقلاع.

راجع [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) للاطلاع على
التفاصيل الكاملة حول `OMNIROUTE_READY_TIMEOUT_MS`.
