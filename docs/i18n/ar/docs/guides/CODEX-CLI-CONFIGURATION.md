دليل شامل لاستخدام Codex CLI مع توجيهه إلى OmniRoute كواجهة خلفية متوافقة مع OpenAI.

---

> **TOML هو التنسيق الفعّال الوحيد.** تقرأ الإصدارات الحديثة من Codex الملف `~/.codex/config.toml`
> حصريًا (تم التحقق باستخدام codex-cli 0.147.0: توثّق `codex --help`
> أن تجاوزات `-c/--config` «تُحمَّل من `~/.codex/config.toml`»). كان الملف القديم
> `~/.codex/config.yaml` تابعًا لواجهة npm CLI القديمة، ويتم تجاهله بصمت.
> يكتب مولّد لوحة المعلومات (`/api/cli-tools/apply`، الأداة `codex`) بصيغة TOML مع
> دمج متحفظ — إذ تُحفَظ المفاتيح الحالية وكتل المزوّدين الأخرى، ويبقى
> مفتاح API في `OMNIROUTE_API_KEY` (ولا يُكتب في الملف مطلقًا)، كما يُبلَّغ عن أي
> ملف `config.yaml` قديم متبقٍّ ضمن ملاحظة ترحيل من دون تعديله.

## ملف config.toml جاهز للصق

استبدل `<YOUR_HOST>` و`<YOUR_KEY>` بالقيم الخاصة بك:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # الحد الأقصى لتخزين السجل لكل استدعاء أداة

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc أو ~/.zshrc — قيمة المفتاح الفعلية، ولا تُوضع أبدًا في config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ‏Codex المضمّن داخل تطبيق ChatGPT

إذا ثبّتَّ Codex من خلال تطبيق ChatGPT لسطح المكتب، فقد يوجد الملف التنفيذي `codex`
داخل حزمة التطبيق فقط، وألا يكون مضافًا بعد إلى `PATH` الخاص بالصدفة. أضف
دليل الموارد إلى ملف بدء تشغيل الصدفة:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

افتح صدفة جديدة، ثم تحقّق:

```bash
command -v codex
codex --version
```

### ‏OmniRoute محلي من دون مصادقة: يكفي مفتاح نائب

يتحقق Codex من وجود متغير البيئة المحدد بواسطة `env_key`
**قبل** أن يغادر أول طلب واجهة CLI. إذا كانت نسخة OmniRoute **المحلية**
لديك لا تتطلب مصادقة، فستكفي أي قيمة نائبة غير فارغة:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

استخدم مفتاحًا حقيقيًا بدلًا من ذلك عندما يكون خادم OmniRoute محميًا أو بعيدًا.

> **خيارات المضيف الشائعة**
>
> | الوصول           | URL                           |
> | ---------------- | ----------------------------- |
> | الشبكة المحلية   | `http://192.168.0.1:20128/v1` |
> | Tailscale        | `http://100.x.x.x:20128/v1`   |
> | الاسترجاع الحلقي | `http://localhost:20128/v1`   |

## ‏`wire_api = "responses"` — لماذا يعمل مع جميع النماذج

أوقف Codex CLI دعم `wire_api = "chat"` ‏(Chat Completions) في فبراير 2026، وأصبح الآن **يتطلب** `wire_api = "responses"` ‏(OpenAI Responses API). يؤدي تعيين `wire_api = "chat"` إلى تعطل فوري عند بدء التشغيل منذ v0.138.

لا يزال العديد من المزوّدين، بما في ذلك GLM وKimi، يوفّرون نقطة نهاية Chat Completions فقط. يوفّر DeepSeek V4 الآن Responses API أصلية، بالإضافة إلى نقطة نهاية متوافقة مع Anthropic؛ ويستخدم OmniRoute ‏Responses افتراضيًا، ويتيح لكل اتصال DeepSeek تحديد التوافق مع Anthropic.

**يحل OmniRoute هذه المشكلة بشفافية:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → يحدد OmniRoute البروتوكول الأصلي للمزوّد ويُجري التحويل عند الحاجة
    → POST /responses (DeepSeek V4) أو /chat/completions (Mistral / GLM / Kimi / غيرها)
```

لن تحتاج مطلقًا إلى وكيل ترجمة منفصل عند استخدام OmniRoute. **تستخدم جميع النماذج `wire_api = "responses"`** — ويتولى OmniRoute الباقي.

> **`wire_api` هو الإعداد الافتراضي** — القيمة الافتراضية للحقل هي `"responses"`، ويمكن حذفه بالكامل من `config.toml`. لا تعيّنه صراحةً إلا إذا كنت توثّق الغرض من استخدامه.

## نافذة السياق والضغط

### حقول إعداد الرموز

| الحقل                            | الوصف                                                                                                                                                               |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | إجمالي ميزانية الرموز للنموذج النشط. اضبطه على الحد المُعلن للنموذج.                                                                                                |
| `model_auto_compact_token_limit` | الحد الذي يؤدي إلى تشغيل الضغط التلقائي للسجل. **الحد الأقصى: 90% من `model_context_window`** — يتم تجاهل القيم التي تتجاوز 90% بصمت.                               |
| `tool_output_token_limit`        | حد أقصى للرموز المخزنة في السجل لكل مخرجات استدعاء أداة. يمنع استجابة كبيرة واحدة من أداة من ملء النافذة. **هذا ليس الحد الأقصى للمخرجات** — بل هو حد لتخزين السجل. |
| `compact_prompt`                 | تجاوز مضمّن لموجّه النظام المستخدم أثناء الضغط (v0.138+).                                                                                                           |

> **ملاحظة حول `model_max_output_tokens`**: هذا الحقل **ليس جزءًا من مخطط إعداد Codex CLI** (فهو غير موجود في قاعدة شيفرة Codex المكتوبة بلغة Rust). ويتم تجاهله بصمت إذا جرى ضبطه. لا تعتمد عليه — استخدم `tool_output_token_limit` للتحكم في مقدار مخرجات الأدوات المخزنة في السجل.

## جهد الاستدلال

يتحكم في مقدار «التفكير» الذي يجريه النموذج قبل الرد.

| القيمة   | الاستخدام                                      |
| -------- | ---------------------------------------------- |
| `none`   | بلا استدلال — استجابة مباشرة                   |
| `low`    | المهام البسيطة (إعادة التسمية، التنسيق)        |
| `medium` | **إعداد الخادم الافتراضي** عند عدم تحديد قيمة  |
| `high`   | المهام المتوسطة (إعادة الهيكلة، تصحيح الأخطاء) |
| `xhigh`  | البنية، التحليل المتعمق، المشكلات المعقدة      |

```bash
# تجاوز الإعداد لكل استدعاء
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

اضبط أيضًا **ملخصًا** للاستدلال حتى يتمكن Desktop من عرض نص التفكير (وليس فقط الكتل المشفّرة):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # أو ultra عند دعمه
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### ميزانية التفكير في OmniRoute (إعداد الخادم)

على مضيف OmniRoute، يجب أن تكون قيمة **Settings → AI → Thinking Budget** هي **`passthrough`** حتى يصل جهد/ملخص Codex إلى الجهة المزودة العليا. يعمل وضع **`auto` على إزالة** جميع حقول `reasoning` / `reasoning_effort` الخاصة بالعميل، وسيؤدي إلى إفراغ لوحات التفكير حتى عند ضبط Codex بصورة صحيحة.

الدليل الكامل: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

يُعد الضغط وذاكرة التخزين المؤقت للمطالبات مستقلين، ويستمران في العمل عند استخدام `passthrough`.

## الملفات الشخصية — إعدادات مسماة لكل نموذج/سير عمل

تتيح لك الملفات الشخصية تبديل النموذج + نافذة السياق باستخدام خيار واحد. كل ملف شخصي هو ملف مسطح باسم
`~/.codex/<name>.config.toml` يُطبّق فوق ملف `config.toml` الأساسي.

> **قاعدة التسمية (Codex CLI v0.137+):** يجب أن يكون الملف `~/.codex/<name>.config.toml` — **من دون بادئة `profile-`**.
> يحل CLI الخيار `-p kimi-k27` إلى `~/.codex/kimi-k27.config.toml`. إذا لم يُعثر على الملف، يُطبّق الإعداد الافتراضي بصمت.

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # سريع، منخفض التكلفة
```

### ملفات جهد شخصية (النموذج نفسه، جهد مختلف)

```bash
codex -p low      # cx/gpt-5.5، الجهد=low
codex -p medium   # cx/gpt-5.5، الجهد=medium
codex -p high     # cx/gpt-5.5، الجهد=high
codex -p xhigh    # cx/gpt-5.5، الجهد=xhigh (الافتراضي)
codex -p chat     # cx/gpt-5.5، لم يُضبط الجهد (إعداد الخادم الافتراضي)
```

## إنشاء الملفات التعريفية تلقائيًا باستخدام `omniroute setup-codex`

إذا كنت تشغّل OmniRoute على خادم VPS، فيمكنك إنشاء ملفات التعريف تلقائيًا من كتالوج النماذج المباشر:

```bash
# من خادم VPS (يستخدم OmniRoute المحلي على المنفذ 20128)
omniroute setup-codex

# من أي جهاز — وجّه الأمر إلى خادم VPS الخاص بك
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# معاينة دون كتابة ملفات
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# إنشاء ملفات تعريف GLM وKimi فقط
omniroute setup-codex --only glm,kimi

# الكتابة إلى دليل مخصص
omniroute setup-codex --codex-home /path/to/.codex
```

يجلب الأمر `/v1/models`، ويستخدم ملفات تعريف مضبوطة للنماذج المعروفة، ويلجأ إلى بيانات تعريف الكتالوج للنماذج النصية المتوافقة الأخرى، ويكتب `~/.codex/<name>.config.toml` لكل نموذج. العملية متكررة آمنة — لذا يمكن إعادة تشغيلها بأمان.

يمكن لـ OmniRoute أيضًا إجراء **مزامنة تلقائية** لملفات التعريف نفسها بعد نجاح اكتشاف/استيراد نماذج المزوّد وتغيير الكتالوج المباشر. هذه الميزة **اختيارية ومعطّلة افتراضيًا**: فعّلها من **لوحة معلومات CLI Code** عبر ("CLI profile auto-sync" ← Codex)، أو عيّن `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (كما أنها تراعي `CLI_ALLOW_CONFIG_WRITES`، وهو مفعّل افتراضيًا). عند تمكينها، لا تكتب سوى ملفات تعريف منفصلة بصيغة `~/.codex/*.config.toml`؛ ولا تغيّر أبدًا الملف النشط/الافتراضي `~/.codex/config.toml`، أو إعدادات Codex-lb، أو المصادقة، أو اختيار المزوّد.

## المهام طويلة الأمد

يمكن لإعدادين افتراضيين في OmniRoute تخريب جلسات Codex CLI التي تمتد لساعات بصمت. لا يُعد أي منهما إعدادًا في Codex CLI — فكلاهما موجود في جانب OmniRoute. غالبًا ما يواجه المستخدمون الذين يرحّلون إعدادًا من وكلاء منبع يثبّتون الحسابات ويعطّلون حدود الخمول كلتا المشكلتين، ثم يستنتجون أن OmniRoute «لا يستطيع الحفاظ على جلسة طويلة».

| العَرَض                                                                              | السبب المحتمل                                                      | عنصر التحكم              |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------ | ------------------------ |
| تستمر الجلسة في تبديل الحسابات / تُفقد استمرارية ذاكرة المطالبات المؤقتة بين الأدوار | قيمة TTL لتقارب الجلسة هي `0` (معطّل)                              | `sessionAffinityTtlMs`   |
| ينقطع الاتصال أثناء الاستدلال دون مطالبة ظاهرة للعميل                                | فُعّلت آلية مراقبة خمول التدفق بعد 10 دقائق دون جزء وارد من المنبع | `STREAM_IDLE_TIMEOUT_MS` |

مناقشات ذات صلة: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (انقطاع المهام الطويلة)، [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (سبب تعطيل التقارب افتراضيًا). التتبع: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. تقارب الجلسة — تثبيت محادثة واحدة على حساب واحد

**القيمة الافتراضية:** `sessionAffinityTtlMs = 0` (معطّل).

**مكان ضبطه**

- لوحة المعلومات ← **الإعدادات ← التوجيه** ← **تقارب الجلسة** ← **مدة TTL للتقارب (بالثواني)** (`ComboDefaultsTab`)
- أو حدّث الإعدادات باستخدام PATCH مع `sessionAffinityTtlMs` بوحدة **المللي ثانية** (نطاق Zod من `0` إلى `86_400_000`، أي حتى 24 ساعة)

> أُعيدت تسميته في #7274 من `codexSessionAffinityTtlMs` الخاص بـ Codex فقط. ما زال المفتاح القديم مقبولًا بوصفه اسمًا مستعارًا للقراءة فقط؛ ويجب أن تستخدم الإعدادات الجديدة `sessionAffinityTtlMs`. ينطبق التقارب الآن على **أي** موفّر بمجرد أن تزيد قيمة TTL على `0`، وليس على Codex فقط — راجع [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) ← تقارب الجلسة.

**ما الذي يتعطل عندما تبقى القيمة عند 0**

يُوجَّه كل دور من محادثة Codex متعددة الأدوار بصورة مستقلة وفق استراتيجية الدمج النشطة، وقد يصل إلى **حساب مختلف في كل دور**. يؤدي ذلك إلى قطع استمرارية جلسة المنبع / ذاكرة المطالبات المؤقتة. لا يستشير OmniRoute ترويسات جلسة Codex (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) وحقول النص مثل `prompt_cache_key` / `session_id` إلا عندما تكون قيمة TTL أكبر من `0` (`extractSessionAffinityKey` في `src/sse/services/auth.ts`).

**الموصى به لمهمة واحدة تمتد عدة ساعات**

اضبط قيمة TTL بحيث تكون **أكبر من مدة التنفيذ الفعلية المتوقعة للمهمة** (الحد الأقصى في واجهة المستخدم هو **86400 ثانية** = 24 ساعة):

| مدة المهمة المتوقعة   | قيمة TTL للتقارب (واجهة المستخدم، بالثواني) | `sessionAffinityTtlMs` |
| --------------------- | ------------------------------------------- | ---------------------- |
| بضع ساعات             | `14400` (4 ساعات)                           | `14400000`             |
| طوال الليل / ~12 ساعة | `43200` (12 ساعة)                           | `43200000`             |
| يوم كامل              | `86400` (24 ساعة، الحد الأقصى)              | `86400000`             |

الاشتراك اختياري عن قصد: يؤدي تعطيل التقارب إلى تفضيل موازنة الحمل بين الحسابات، بينما يؤدي تمكينه إلى تفضيل الاستمرارية لجلسة وكيل واحدة طويلة. **لا** يغيّر هذا الدليل القيمة الافتراضية — يجب على المشغّلين الذين ينفذون مهام Codex طويلة الاشتراك صراحةً.

### 2. مهلة خمول التدفق — لا تنه أدوار الاستدلال الصامتة

**القيمة الافتراضية:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 دقائق). ترث قيمتها من `REQUEST_TIMEOUT_MS` عندما لا تكون مضبوطة؛ والقيمة الأساسية المشتركة هي أيضًا 600000. راجع [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) ← المهل الزمنية.

**ما الذي يتعطل عند استخدام القيمة الافتراضية**

يتم الإغلاق القسري لأي دورة استدلال / أداة في Codex تظل صامتة لأكثر من 10 دقائق من دون **أي جزء فعلي وارد من المنبع** بواسطة مراقب خمول SSE (`open-sse/utils/stream.ts`). وغالبًا ما يرى العميل انقطاعًا مباشرًا للاتصال — وهو ما يطابق وصف «توقف تلقائيًا من دون أي إشعار».

تفصيل بالغ الأهمية: إن **نبضة القلب** الاصطناعية لـ SSE في OmniRoute لا تعيد ضبط مؤقت الخمول. وحده وصول جزء فعلي من جسم الاستجابة من المنبع يحدّث `lastChunkTime`. لذلك، يبدو النموذج الهادئ الذي لا يزال «يفكر» مماثلًا تمامًا لمنبع متوقف من وجهة نظر المراقب.

مهلة خمول جسم Undici ذات الصلة: `FETCH_BODY_TIMEOUT_MS` (وتكون افتراضيًا أيضًا عند خط الأساس نفسه البالغ 10 دقائق؛ وتعطّلها القيمة `0`). بالنسبة إلى البث، لا تغطي `FETCH_TIMEOUT_MS` سوى إعداد الاتصال / الترويسات الأولى — وبمجرد تنشيط البث، تصبح حالات التوقف محكومة بـ `STREAM_IDLE_TIMEOUT_MS` و`FETCH_BODY_TIMEOUT_MS`.

**الإعداد الموصى به لمهمة واحدة تمتد لعدة ساعات**

في بيئة عملية OmniRoute (`.env` / compose / systemd):

```bash
# تعطيل حدود خمول البث وخمول الجسم لدورات الاستدلال الطويلة
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

أو ارفع القيم لتتجاوز أطول فترة صمت تتوقعها (القيم بالمللي ثانية):

```bash
# مثال: السماح بما يصل إلى ساعتين من الصمت بين الأجزاء الواردة من المنبع
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

أعد تشغيل OmniRoute بعد تغيير متغيرات البيئة هذه.

### وصفة عملية — مهمة Codex تمتد لعدة ساعات

1. **ثبّت الحساب:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` ‏(12 ساعة) أو `86400` ‏(24 ساعة كحد أقصى).
2. **ارفع / عطّل حدود الخمول** في بيئة OmniRoute:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. احتفظ بإعدادات Codex المعتادة في `config.toml` (`wire_api = "responses"`، و`base_url` الصحيح، و`OMNIROUTE_API_KEY`) — لا توجد إعدادات من جانب Codex للتحكم في تقارب الجلسة أو الخمول لهذين السلوكين.
4. أعد تشغيل OmniRoute، ثم ابدأ مهمة Codex الطويلة.

### قرار القيم الافتراضية (#7287)

| الإعداد                  | القيمة الافتراضية عند الإصدار | هل ستتغير في هذا الدليل؟                                                         |
| ------------------------ | ----------------------------- | -------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (معطّل)                   | **لا** — سيبقى اختياريًا (موازنة الحمل مقابل الاستمرارية؛ راجع Discussion #5718) |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 دقائق)           | **لا** — سيبقى 10 دقائق لحركة البيانات العامة؛ وعلى مشغّلي Codex رفعه أو تعطيله  |

إن تغيير أي من القيمتين الافتراضيتين على مستوى النظام سيغيّر السلوك لكل عميل في المثيل، وليس لـ Codex وحده. وثّق الإعدادات، واترك القيم الافتراضية كما هي إلى أن يصدر قرار صريح بخلاف ذلك من المشغّل.

### تشخيص حالات القطع بسبب الخمول

عند تشغيل مراقب الخمول، يسجّل OmniRoute سطرًا بالشكل الآتي:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

ابحث باستخدام grep عن `Idle timeout: no data from` (أو الرمز `stream_idle_timeout` / اسم الخطأ `StreamIdleTimeoutError`). مقطع المزوّد هو المزوّد الذي استخدمه OmniRoute لذلك الطلب (`codex`، أو معرّف مزوّد آخر، أو `provider` إذا كان غير معروف) — وليس دائمًا السلسلة النصية الحرفية `codex`.

## استكشاف الأخطاء وإصلاحها

**`Error: wire_api = "chat" is no longer supported`**
أزل `wire_api = "chat"` من إعداداتك. عيّن `wire_api = "responses"` أو احذف الحقل (القيمة الافتراضية هي `"responses"` منذ v0.138).

**`Error: model not found`**
تحقق من وجود النموذج في OmniRoute بالبادئة الصحيحة. استخدم `omniroute models list` أو افتح `/dashboard/providers/<provider>`.

**`Authentication error`**
تأكد من تصدير `OMNIROUTE_API_KEY`:‏ `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
يتحقق Codex من وجود متغير البيئة قبل إرسال الطلب الأول. صدّر
مفتاحًا حقيقيًا للخوادم المحمية، أو قيمة بديلة غير فارغة مثل
`OMNIROUTE_API_KEY=local` عندما لا يتطلب مثيل OmniRoute **المحلي** لديك
مصادقة. أعد تشغيل الصدفة إذا أضفته إلى `~/.bashrc` أو `~/.zshrc`.

**`Connection refused`**
تحقق من أن OmniRoute قيد التشغيل وأن المضيف/المنفذ في `base_url` صحيحان لشبكتك (محلية مقابل Tailscale مقابل VPS).

**تعطل الجلسة عند الاقتراب من حد السياق**
عيّن `model_context_window` و`model_auto_compact_token_limit` صراحةً. راجع جدول نافذة السياق أعلاه.

**يحدث الضغط متأخرًا جدًا**
خفّض `model_auto_compact_token_limit` إلى 80–85% من النافذة. لا تعيّنه أبدًا فوق 90%.

**عدم تحميل ملف التعريف (يتم تجاهل `-p <name>` دون تنبيه)**
تأكد من وجود الملف في `~/.codex/<name>.config.toml` (من دون البادئة `profile-`). نفّذ `ls ~/.codex/*.config.toml`.

**انقطاع مهمة Codex طويلة في أثناء التشغيل / التبديل بين الحسابات في الفواصل بين الأدوار**
راجع [المهام طويلة التشغيل](#long-running-tasks). فعّل تقارب الجلسة (بقيمة TTL أطول من مدة المهمة)، وارفع قيمتي `STREAM_IDLE_TIMEOUT_MS` و`FETCH_BODY_TIMEOUT_MS` أو عطّلهما. ابحث في سجلات OmniRoute باستخدام grep عن `Idle timeout: no data from`.
