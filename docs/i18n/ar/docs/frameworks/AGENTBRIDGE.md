AgentBridge هو وكيل MITM (الرجل في المنتصف) الخاص بـ OmniRoute، ويعترض حركة مرور HTTPS الصادرة من وكلاء الذكاء الاصطناعي في بيئات التطوير المتكاملة، ثم يعيد توجيهها عبر محرك التوجيه الموحّد في OmniRoute. وهو يدعم **10 وكلاء لبيئات التطوير المتكاملة** — Antigravity وKiro وGitHub Copilot وGHE Copilot وOpenAI Codex وCursor وZed وClaude Code وOpen Code وTrae (قيد البحث) — ما يجعل OmniRoute وكيل MITM الأوسع تغطيةً لمساعدي البرمجة بالذكاء الاصطناعي في السوق.

**موقع لوحة المعلومات:** `/dashboard/tools/agent-bridge`
**مجموعة الشريط الجانبي:** الأدوات (بعد الوكلاء السحابيين)
**انظر أيضًا:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — راقب جميع حركات المرور المعترضة في الوقت الفعلي؛ `docs/security/MITM-TPROXY-DECRYPT.md` ‏(git؛ غير مضمّن في `/docs`) — وضع الالتقاط لفك التشفير الشفاف باستخدام TPROXY على Linux، والذي يتحكم فيه المسار `/api/tools/agent-bridge/tproxy`.

## §1 نظرة عامة

### ما هو AgentBridge؟

عندما يُجري وكيل في بيئة تطوير متكاملة (مثل GitHub Copilot أو Cursor أو Claude Code) استدعاءً لواجهة API، فإنه يتصل مباشرةً بموفّر الذكاء الاصطناعي الرئيسي (OpenAI أو Anthropic أو غيرهما). يعترض AgentBridge هذا الاتصال بشفافية على مستوى TLS — من دون الحاجة إلى أي تغيير في إعدادات الوكيل — ويعيد كتابة الطلب ليمر عبر OmniRoute.

وهذا يعني أنه يمكنك:

- **إعادة توجيه أي وكيل إلى أي موفّر**: هل يتواصل Copilot مع OpenAI؟ أعد توجيهه إلى Anthropic Claude أو Gemini أو أي موفّر من موفّري OmniRoute البالغ عددهم 352.
- **تطبيق تعيينات النماذج**: `gemini-3-flash` ← `claude-sonnet-4.7` بشفافية على مستوى المعالج.
- **مراقبة جميع حركات مرور الوكلاء**: يُنشر كل طلب معترض في [فاحص حركة المرور](./TRAFFIC_INSPECTOR.md).
- **تطبيق إمكانات المرونة في OmniRoute**: يعمل التوجيه المجمّع وقواطع الدوائر وآليات الرجوع الاحتياطي وتتبع التكلفة أيضًا مع حركة مرور وكلاء بيئات التطوير المتكاملة.

## §2 البنية المعمارية

### 2.1 نظرة عامة على المكوّنات

```
وكيل IDE ‏(VS Code / Cursor / إلخ.)
    │  HTTPS (المنفذ 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← إعادة توجيه DNS
    │
    ▼
src/mitm/server.cjs  (المنفذ 443، عملية فرعية CJS)
    │  يحلّ الوجهة حسب SNI في ترويسة Host
    │  ينشئ شهادة TLS لكل SNI موقّعة من مرجع التصديق AgentBridge CA
    ├── تطابق مع قائمة التجاوز؟ → تمرير TCP مباشر (من دون فك التشفير)
    ├── تطابق مع وجهة؟ → fetch → موجّه OmniRoute (المنفذ 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() على متن الطلب/ترويساته
    │               ├── TrafficBuffer.push() — ينشر إلى أداة فحص حركة المرور
    │               └── fetchRouter() → /v1/chat/completions
    └── لا يوجد تطابق؟ → تمرير TCP مباشر (من دون فك التشفير)
```

### 2.2 خادم MITM ‏(`src/mitm/server.cjs`)

يعمل خادم MITM الأساسي كعملية فرعية CJS في Node.js (لتجنّب إعادة كتابة قاعدة الشفرة الحالية المبنية على CJS). وهو:

- يستمع على المنفذ 443 (يتطلب امتيازات أو `authbind`/`setcap`)
- يستقبل أنفاق CONNECT من نظام التشغيل (عبر إعادة توجيه DNS في `/etc/hosts`)
- ينشئ شهادات TLS لكل SNI موقّعة من مرجع التصديق AgentBridge CA ‏(`DATA_DIR/mitm/ca.crt`)
- يحلّ الوكيل المستهدف حسب ترويسة Host عبر سجل `targets/index.ts`
- يرسل الطلب إلى طبقة المعالج المكتوبة بلغة TypeScript عبر HTTP إلى `http://127.0.0.1:20128`

يُحمَّل `TARGET_HOSTS` من `DATA_DIR/mitm/targets.json` (الذي يكتبه `targets/index.ts` عند الإقلاع)، مما يسمح بإجراء تحديثات ديناميكية من دون إعادة تشغيل خادم CJS.

> **نموذج مرجع التصديق الجذري (#6684).** إن الوصف أعلاه، الذي يتناول شهادةً لكل SNI موقّعةً من مرجع تصديق،
> هو نموذج مرجع التصديق الجذري الدائم المُضاف في #6684 ‏(`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`، مع إعادة استخدام تشفير مرجع التصديق/الشهادة الفرعية الذي سبق
> إثباته لـ TPROXY في `src/mitm/tproxy/dynamicCert.ts`) — وهو يستبدل
> الشهادة الفرعية الثابتة الأقدم والموقّعة ذاتيًا (`src/mitm/cert/generate.ts`، التي ما زال
> نطاقها مقتصرًا على مضيفي antigravity) والتي يشير إليها وجود زوج مجرد من
> `server.crt`/`server.key` على القرص. **سلوك الترحيل**: يحصل التثبيت الجديد (من دون
> `server.crt` سابق) على نموذج مرجع التصديق الجذري تلقائيًا؛ أما التثبيت الذي سبق له
> الوثوق بالشهادة الفرعية الثابتة القديمة، فيستمر في استخدامها إلى أن يضبط المشغّل
> `MITM_ROOT_CA_ENABLED=true` ويعيد تشغيل الجسر (`src/mitm/cert/migration.ts`
> هي دالة القرار الصرفة — فمرجع تصديق MITM موثوق يمكنه توقيع شهادة فرعية
> **لأي** مضيف أقوى بكثير من الشهادة الفرعية القديمة ذات SAN الثابت، ولذلك
> لا يحدث التبديل بصمت أبدًا في تثبيت سبق منحه الثقة). تُثبَّت شهادة مرجع التصديق
> في خانة مخزن الثقة `omniroute-mitm.crt` نفسها التي كانت تستخدمها الشهادة الفرعية القديمة
> (`cert/install.ts::installCaCert`) — ولا حاجة إلى تنظيف ثقة مزدوجة.

### 2.3 قاعدة المعالج (`src/mitm/handlers/base.ts`)

ترث جميع معالجات الوكلاء من `MitmHandlerBase`:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // أدوات مساعدة محمية: fetchRouter وpipeSSE وhookBufferStart وhookBufferUpdate
}
```

يستدعي كل معالج `hookBufferStart()` قبل تمرير الطلب عبر الوكيل، ويستدعي `hookBufferUpdate()` عند الاكتمال. تدفع هذه الاستدعاءات إدخالات `InterceptedRequest` إلى `globalTrafficBuffer` (راجع [أداة فحص حركة المرور](./TRAFFIC_INSPECTOR.md) §4).

### 2.4 سجل الوجهات (`src/mitm/targets/`)

لكل وكيل ملف وجهة تصريحي:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

يصدّر السجل (`targets/index.ts`) القيمة `ALL_TARGETS`، وينشئ `DATA_DIR/mitm/targets.json` عند الإقلاع.

### 2.5 التمرير المباشر وقائمة التجاوز (`src/mitm/passthrough.ts`)

**قائمة التجاوز** (يتم فحصها أولًا، ولها الأولوية على تطابق الوجهة):

- الأنماط الافتراضية: مضيفو الخدمات المصرفية، و`.gov.`، وموفرو OAuth/SSO ‏(Okta وAuth0)، وما إلى ذلك.
- أنماط المستخدم: مخزّنة في جدول قاعدة البيانات `agent_bridge_bypass`
- تحصل المضيفات المتجاوزة على نفق TCP شفاف — ولا يُفك تشفير TLS **أبدًا**

**التمرير المباشر الافتراضي** (لا يوجد تطابق مع وجهة وليست ضمن قائمة التجاوز):

- يحصل أيضًا على نفق TCP — ولا تُقطع الاتصالات أبدًا
- يمنع AgentBridge من تعطيل حركة مرور HTTPS العامة للنظام

أولوية التوجيه:

```
قائمة التجاوز → تطابق الوجهة → التمرير المباشر
```

### 2.6 شهادة مرجع التصديق للاتصال الصاعد (`src/mitm/upstreamTrust.ts`)

لبيئات شبكات الشركات التي تستخدم مرجع تصديق مخصصًا:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

عند ضبطه، يهيئ المرسِل العام الخاص بـ `undici` باستخدام شهادة مرجع التصديق الإضافية، مما يسمح لـ AgentBridge بالوصول إلى الموفّرين في الاتصال الصاعد عبر وكلاء إنهاء TLS التابعين للشركة.

### 2.7 إخفاء الأسرار (`src/mitm/maskSecrets.ts`)

يُطبّق الماسح المستقل المُنشأ وفق نهج الغرفة النظيفة على متون الطلبات وترويسات بيانات الاعتماد
**قبل** دخولها إلى مخزن أداة فحص حركة المرور أو أي سجل. وهو يجري مرورًا خطيًا واحدًا:

- الرموز المميزة ذات البادئات `sk-` / `ak-` / `pk-` (بأسلوب OpenAI/Anthropic)
- بيانات اعتماد RFC 6750 بصيغة `Authorization: Bearer <token>`، مع إعطاء الأولوية للرمز المميز كاملًا
- الرموز المميزة العامة الطويلة والمبهمة (≥40 محرفًا)، بما فيها الصيغ المنقّطة والمُبطّنة

تحوّل `sanitizeHeaders()` الأسماء المحتفَظ بها إلى أحرف صغيرة، وتدمج قيم المصفوفات بصورة حتمية، وتحذف
قائمة الحظر المشتركة لترويسات قفزة-بقَفزة/التأطير (بما فيها مصادقة الوكيل)، وتحجب `cookie` و
`set-cookie` بالكامل، وتفوّض قيم بيانات الاعتماد إلى الماسح.

## §3 الإعداد

### 3.1 تشغيل/إيقاف خادم MITM

استخدم بطاقة خادم AgentBridge في `/dashboard/tools/agent-bridge`:

| الإجراء             | الوصف                                                                     |
| ------------------- | ------------------------------------------------------------------------- |
| تشغيل الخادم        | يشغّل `src/mitm/server.cjs` على المنفذ 443                                |
| إيقاف الخادم        | يوقف العملية الفرعية بصورة سليمة                                          |
| إعادة تشغيل الخادم  | إيقاف + تشغيل (لالتقاط تغييرات الوجهة)                                    |
| الوثوق بالشهادة     | يثبّت `DATA_DIR/mitm/ca.crt` في مخزن الثقة لنظام التشغيل                  |
| تنزيل الشهادة       | ينزّل `ca.crt` للتثبيت اليدوي                                             |
| إعادة إنشاء الشهادة | ينشئ زوج مفاتيح جديدًا لسلطة التصديق (تُبطَل جميع شهادات الوكلاء الحالية) |

### 3.2 الوثوق بالشهادة

يجب أن يثق نظام التشغيل بشهادة سلطة التصديق الخاصة بـ AgentBridge قبل أن تقبل بيئات التطوير المتكاملة اتصال MITM.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (سلسلة المفاتيح):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

أو استخدم زر "الوثوق بالشهادة" في لوحة المعلومات (يشغّل الأمر المناسب لنظام التشغيل لديك، مع مطالبة sudo عند الحاجة).

#### تتجاهل بيئات التطوير المتكاملة المستندة إلى Electron مخزن الثقة لنظام التشغيل (`NODE_EXTRA_CA_CERTS`)

تضم بعض بيئات التطوير المتكاملة — ولا سيما **Antigravity IDE**، وغيرها من التطبيقات المشتقة من Electron / VS Code —
بيئة تشغيل Node.js خاصة بها **لا تستعلم من مخزن الثقة لنظام التشغيل** عند إجراء طلبات
`fetch`/HTTPS الصادرة. تكفي الثقة بسلطة التصديق على مستوى نظام التشغيل/NSS للواجهة **الخلفية** الأصلية
لبيئة التطوير المتكاملة (مثل خادم لغة Go الذي يستخدم حزمة سلطات التصديق لنظام التشغيل)، لكن **واجهة Electron الأمامية**
ستظل تفشل في TLS — ويظهر ذلك على هيئة _تسجيل خروج_ من التطبيق أو عرض _"خطأ في الاتصال"_
مع أن سجل MITM يبيّن أن استدعاءات التمهيد الخاصة بالواجهة الخلفية تُرجع `200`. يلزم تنفيذ خطوتين،
وكلتاهما مهمتان:

1. وجّه بيئة التشغيل إلى سلطة التصديق صراحةً:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **شغّل بيئة التطوير المتكاملة من تلك الصدفة.** لا يؤدي تشغيلها من أيقونة سطح المكتب / Dock / قائمة Start
   إلى توريث متغيرات البيئة المصدّرة من الصدفة، كما لا يُطبَّق `~/.config/environment.d/*.conf` إلا بعد
   تسجيل دخول رسومي جديد. أغلق بيئة التطوير المتكاملة بالكامل أولًا — فقفل المثيل الفردي في Electron يعني أن التشغيل
   الثاني يركّز على العملية الحالية فحسب، ويُتجاهل متغير البيئة الجديد.

تظل خطوة الثقة على مستوى نظام التشغيل + NSS أعلاه ضرورية (إذ تقرأ حزمة شبكة Chromium التي تستخدمها بعض
تدفقات المصادقة مخزن NSS الخاص بكل مستخدم، ولديها دبابيس ثابتة خاصة بها لـ `*.googleapis.com` يمكن
لسلطة تصديق موثوق بها محليًا تجاوزها). يغطي `NODE_EXTRA_CA_CERTS` مسار `fetch` الخاص بـ Node إضافةً إلى ذلك.

### 3.3 توجيه DNS

لكل وكيل تريد اعتراضه، يجب أن تُحل أسماء مضيف API الخاص به إلى `127.0.0.1`. يدير AgentBridge إدخالات `/etc/hosts` تلقائيًا عند تبديل DNS لوكيل في معالج الإعداد.

مثال على إدخالات `/etc/hosts` الخاصة بـ GitHub Copilot:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 تعيين النماذج

استخدم جدول تعيين النماذج في بطاقة كل وكيل لتعريف تعيينات المصدر → الوجهة:

| نموذج المصدر (الأصلي للوكيل) | نموذج الوجهة (OmniRoute) |
| ---------------------------- | ------------------------ |
| `gpt-4o`                     | `claude-sonnet-4.7`      |
| `*` (حرف بدل)                | `claude-haiku-4.7`       |

يعيّن حرف البدل `*` أي نموذج غير معروف إلى الوجهة المحددة. ويُحفَظ ذلك في جدول `agent_bridge_mappings`.

> **تلميح — اكتشف معرّفات النماذج الحقيقية للوكيل.** قد ترسل بيئة التطوير المتكاملة أسماء نماذج تختلف عن
> تسميات واجهتها، وقد تتغير هذه الأسماء بين الإصدارات الرئيسية. على سبيل المثال، يرسل **Antigravity 2**
> القيم `gemini-3.1-pro-low` و`gemini-pro-agent` و`gemini-3.1-flash-lite` عبر الشبكة — وليس
> `gemini-2.5-pro` الظاهر في الوثائق الأقدم. أرسل محادثة واحدة من دون تعيين مطابق: سيسجّل MITM
> قيمة `model:` الواردة بالضبط ويمرر الطلب كما هو. عيّن تلك القيمة الحرفية، وحينها سيُعترض
> الطلب التالي ويُوجَّه إلى وجهتك.

### 3.5 إشعار المخاطر

يعترض AgentBridge بيانات الاعتماد (رموز OAuth المميزة ومفاتيح API) التي تستخدمها بيئة التطوير المتكاملة للمصادقة لدى المزوّدين المنبعين. **تُخفى هذه البيانات قبل تسجيلها** (راجع §2.7)، لكنها تكون مرئية لطبقة MITM في OmniRoute. يعرض أول تفعيل لكل وكيل نافذة إشعار مخاطر يمكن إغلاقها.

### 3.6 الصيانة والتشخيص

تعرض لوحة المعلومات بطاقة **الصيانة والتشخيص** (`AgentBridgeMaintenanceCard`، في `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`) التي تُظهر مسارات MITM التشغيلية التي لم تكن لها واجهة مستخدم سابقًا. عنوانها الفرعي: _"اختبر ذاتيًا مسار الالتقاط، وتراجع عن حالة النظام المتبقية، وانقل إعدادك بين الأجهزة."_ توجد الدوال المساعدة للعميل الخاصة بالبطاقة في `src/lib/inspector/agentBridgeMaintenanceApi.ts`.

| الزر                | المسار                                 | وظيفته                                                                                                                                                                                          |
| ------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **التشخيص**         | `GET /api/tools/agent-bridge/diagnose` | يشغّل الاختبار الذاتي لمسار الالتقاط ويعرض تقريرًا لكل فحص (✓/✗ + تلميح للمعالجة).                                                                                                              |
| **الإصلاح**         | `POST /api/tools/agent-bridge/repair`  | يتراجع عن حالة نظام MITM المتروكة بسبب تعطل أو SIGKILL (إدخالات انتحال DNS، وشهادة CA الجذرية، ووكيل النظام). متكرر التنفيذ بأمان — يُبلغ بأنه «لا يوجد شيء لإصلاحه» عندما تكون الحالة سليمة.   |
| **إزالة CA**        | `DELETE /api/tools/agent-bridge/cert`  | يلغي الثقة بشهادة CA الجذرية لـ MITM ويزيلها من مخزن الثقة في نظام التشغيل (إجراء صريح ومتكرر التنفيذ بأمان). يظهر فقط عندما تكون CA موثوقة حاليًا؛ ويتطلب تأكيدًا مضمّنًا «هل تريد إزالة CA؟». |
| **تصدير الإعداد**   | `GET /api/tools/agent-bridge/config`   | ينزّل ملف JSON للإعداد القابل للنقل (راجع §3.7).                                                                                                                                                |
| **استيراد الإعداد** | `POST /api/tools/agent-bridge/config`  | يرفع ملف JSON لإعداد تم تصديره مسبقًا (راجع §3.7).                                                                                                                                              |

**فحوصات التشخيص** (`summarizeDiagnostics()` في `src/mitm/inspector/diagnostics.ts`). يشغّل المسار الاستقصاء ذا التأثيرات الجانبية لكل فحص ويمرر القيم المنطقية إلى أداة التلخيص النقية؛ ثم يُرجع حكمًا واحدًا باسم `healthy` مع تلميح لكل حالة فشل:

| اسم الفحص          | ما يتحقق منه                                                | التلميح عند الفشل                                                                                                                                     |
| ------------------ | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | عملية خادم MITM نشطة                                        | «خادم MITM لا يعمل. شغّله من علامة تبويب AgentBridge.»                                                                                                |
| `server-reachable` | خادم MITM يقبل الاتصالات على منفذه (فحص TCP)                | «خادم MITM لا يقبل الاتصالات على منفذه. تحقق من أن المنفذ متاح وأن لديك صلاحيات الربط به.»                                                            |
| `cert-exists`      | تم إنشاء شهادة MITM على القرص                               | «لم يتم إنشاء شهادة MITM بعد. أنشئ واحدة من علامة تبويب AgentBridge.»                                                                                 |
| `cert-trusted`     | شهادة CA الجذرية لـ MITM موجودة في مخزن الثقة لنظام التشغيل | «شهادة CA الجذرية لـ MITM غير موثوقة في مخزن نظام التشغيل، ولذلك سيفشل اعتراض TLS. امنح الشهادة الثقة من علامة تبويب AgentBridge.»                    |
| `dns-configured`   | أسماء المضيفين المستهدفة منتحلة في `/etc/hosts`             | «أسماء المضيفين المستهدفة غير منتحلة في /etc/hosts، ولذلك لا تصل حركة المرور إلى الوكيل مطلقًا. فعّل DNS للوكيل أو الوكلاء الذين تريد التقاط حركتهم.» |

**شعار الحالة المتروكة:** عندما تكتشف الصفحة حالة متروكة بسبب تعطل (انتحال DNS /‏ CA / وكيل النظام)، تعرض البطاقة شعارًا كهرمانيًا — _«تركت جلسة سابقة حالةً في النظام (انتحال DNS أو CA أو وكيل النظام). شغّل الإصلاح لتنظيفها.»_ — وتبرز زر **الإصلاح**. يمثّل `Repair` النظير على مستوى التطبيق للعلامة `--cleanup` الخاصة بـ ProxyBridge (إذ يفوّض المهمة إلى `repairMitm()` في `src/mitm/manager.ts`).

> تُترك شهادة CA الجذرية لـ MITM مثبتةً عبر عمليات الإيقاف/التشغيل لتجنب مطالبات sudo
> المتكررة (وهو السلوك نفسه في mitmproxy/Charles)، ولذلك فإن إزالتها تتم عبر إجراء
> **إزالة CA** صريح بدلًا من حدوث ذلك تلقائيًا عند الإيقاف.

### 3.7 استيراد/تصدير الإعداد القابل للنقل

يستطيع AgentBridge إجراء تسلسل للحالة **القابلة للضبط بواسطة المشغّل** في كتلة JSON ذات إصدار محدد، بحيث يمكن نسخ الإعداد عبر الأجهزة. أداة التسلسل هي `src/lib/inspector/configPortability.ts` ‏(`exportConfig()` / `importConfig()`)، ويجري التحقق منها بواسطة `AgentBridgeConfigSchema`.

يتضمن التصدير ثلاثة أجزاء بالضبط (لا يتم تصدير الإعدادات الافتراضية المضمّنة **عمدًا**، بحيث لا يؤدي الاستيراد مطلقًا إلى تكرارها أو التعارض معها):

| الحقل            | المصدر                                                            | ملاحظات                                                         |
| ---------------- | ----------------------------------------------------------------- | --------------------------------------------------------------- |
| `bypassPatterns` | أنماط التجاوز المعرّفة من المستخدم (`agent_bridge_bypass`)        | تُستبعد الأنماط الافتراضية الخاصة بالمصارف/الجهات الحكومية/okta |
| `customHosts`    | المضيفون المخصصون في Traffic Inspector (`inspector_custom_hosts`) | كل عنصر: `{ host, kind: "llm"\|"app"\|"custom", label? }`       |
| `agentMappings`  | تعيينات النماذج لكل وكيل (`agent_bridge_mappings`)                | `{ [agentId]: [{ source, target }] }` لكل وكيل لديه تعيينات     |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**سلوك الاستيراد** (`POST /api/tools/agent-bridge/config`): تحل أنماط التجاوز والتعيينات الخاصة بكل وكيل **محل القيم السابقة بالكامل**؛ بينما تُضاف أسماء المضيفين المخصصة **بشكل متكرر التنفيذ بأمان** (`INSERT OR IGNORE`). توضح الاستجابة عدد العناصر التي تم تطبيقها من كل نوع:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

ما **لا** يتضمنه ملف الإعدادات: حالة تشغيل الخادم، ومسارات الشهادات، وحالة DNS لكل وكيل، ومسار مرجع التصديق (CA) الرئيسي، وإعدادات TPROXY — فهذه حالات خاصة بالمضيف/وقت التشغيل، وليست تفضيلات قابلة للنقل.

### خطوات معالج الإعداد (لكل وكيل)

export async function detectAgent(agentId: AgentId): Promise<DetectionResult>;

### قائمة التجاوز للمضيفين الحسّاسين

تضمن قائمة التجاوز عدم فك تشفير حركة مرور المؤسسات المالية وموفري OAuth/SSO والمضيفين الحسّاسين الآخرين **مطلقًا**. تمر حركة مرور TLS الخاصة بهم عبر نفق TCP شفاف — ولا يرى OmniRoute النص الصريح أبدًا.

تتضمن أنماط التجاوز الافتراضية:

- `*.bank.*`، `*.gov.*` (الجهات المالية/الحكومية)
- `*.okta.com`، `*.auth0.com`، `*.microsoft.com` (SSO/الهوية)
- `*.apple.com`، `*.icloud.com` (خدمات نظام Apple)

تُخزَّن أنماط التجاوز التي يضيفها المستخدم في جدول `agent_bridge_bypass`، وتكون لها الأولوية على كل شيء.

### إخفاء الأسرار

تُطبَّق `maskSecrets()` من `src/mitm/maskSecrets.ts`:

- على متن كل طلب قبل `TrafficBuffer.push()`
- على كل ترويسة قبل تسجيلها أو بثها

الأنماط: رموز تبدأ بالبادئات `sk-`/`ak-`/`pk-`، ورموز `Bearer`، والرموز العامة التي يبلغ طولها 40 محرفًا أو أكثر.

### شهادة CA للمنبع

عند تعيين `AGENTBRIDGE_UPSTREAM_CA_CERT`، يُقرأ الملف عند بدء التشغيل. إذا كان المسار موجودًا ولكن تعذّرت قراءة الملف، يسجّل AgentBridge خطأً واضحًا ويرفض بدء التشغيل (لمنع إخفاقات TLS الصامتة في بيئات الشركات).

### القيود المعروفة

- **يتطلب المنفذ 443 امتيازات**: على Linux، يحتاج AgentBridge إلى `setcap 'cap_net_bind_service=+ep'` على ملف Node الثنائي، أو إلى التشغيل عبر `authbind`. يعرض معالج الإعداد تعليمات خاصة بنظام التشغيل.
- **يلزم إعادة تشغيل بيئة التطوير المتكاملة**: بعد إعادة توجيه DNS، يجب إعادة تشغيل بيئة التطوير المتكاملة كي يدخل تحليل المضيف الجديد حيز التنفيذ.
- **رموز OAuth المضمّنة مباشرةً**: تخزّن بعض الوكلاء (Kiro وAntigravity) رموز تحديث OAuth محليًا. تكون هذه الرموز شفافة لـ AgentBridge — إذ يرى رمز Bearer في كل طلب، ويُخفى قبل التسجيل.
- **تحتاج واجهات Electron الأمامية إلى `NODE_EXTRA_CA_CERTS`**: تتجاهل بيئات التطوير المتكاملة التي تعمل واجهتها الأمامية ضمن وقت تشغيل Node/Electron مضمّن مخزن الثقة الخاص بنظام التشغيل/NSS، ويجب تشغيلها من صدفة مع تعيين `NODE_EXTRA_CA_CERTS` (راجع §3.2). العَرَض عند غيابه: تنجح مصادقة الواجهة الخلفية لبيئة التطوير المتكاملة (يعرض MITM استجابات `200`) لكن واجهة المستخدم تظل مسجّلة الخروج.
- **عمليات التثبيت المتعددة لبيئة التطوير المتكاملة نفسها مستقلة**: تثبيت النظام (مثل `/usr/share/antigravity/antigravity`) وتثبيت "Full" المحلي للمستخدم (مثل `~/AntigravityIDE_Full/antigravity-ide`) هما عمليتان منفصلتان لهما وقتا تشغيل خاصان بهما — ويجب إعادة تشغيل كل منهما مع حقن CA. حدّد أيّهما قيد التشغيل من خلال مسار ملفه الثنائي قبل إعادة تشغيله.
- **تُحدَّد الهوية بواسطة موجّه النظام الخاص بالوكيل، وليس النموذج الموجَّه إليه**: عند إعادة تعيين نموذج وكيل إلى موفّر مختلف، تظل الاستجابة تدّعي الهوية الأصلية للوكيل (مثل أن يجيب Antigravity: «أعمل بواسطة Gemini») لأن بيئة التطوير المتكاملة تحقن ذلك في موجّه النظام. تحقّق من الواجهة الخلفية الفعلية في `call_logs` / `proxy_logs` (`provider`، `model`، `target_format`)، وليس بسؤال النموذج عن هويته.

## §6 استكشاف الأخطاء وإصلاحها

### تعارض المنفذ 443

إذا كانت عملية أخرى تستمع بالفعل إلى المنفذ 443 (خادم ويب، VPN، وما إلى ذلك):

```bash
lsof -i :443          # ابحث عن العملية
sudo fuser -k 443/tcp  # إنهاء قسري (استخدمه بحذر)
```

بدلاً من ذلك، اضبط منفذًا غير مميز في إعدادات AgentBridge، ثم أعدّ قواعد إعادة التوجيه باستخدام `iptables` / `pf`.

### الشهادة غير موثوق بها

إذا أظهرت بيئة التطوير المتكاملة أخطاء TLS بعد تشغيل AgentBridge:

1. تحقق من تثبيت الشهادة: `security find-certificate -c "OmniRoute AgentBridge"` ‏(macOS) أو `certutil -L -d sql:$HOME/.pki/nssdb` ‏(Linux/NSS)
2. تحتفظ بعض التطبيقات بمخزن ثقة خاص بها (Firefox وChrome على Linux). شغّل "الوثوق بالشهادة" مرة أخرى وتحقق من مخزن الشهادات الخاص بـNSS/Firefox.
3. أعد تشغيل بيئة التطوير المتكاملة بعد منح الثقة — تستخدم جلسات TLS الجارية حالة الثقة القديمة.

### تسجيل الخروج من بيئة التطوير المتكاملة / "خطأ في الاتصال" رغم وجود مرجع مصدّق موثوق

العَرَض: بعد إعادة توجيه DNS ومنح الثقة للمرجع المصدّق، تُفتح بيئة تطوير متكاملة مبنية على Electron (مثل Antigravity)
في حالة **تسجيل الخروج** أو تعرض خطأ في المصادقة/الاتصال، مع أن سجل MITM يُظهر أن
استدعاءات التمهيد (`loadCodeAssist` و`fetchAvailableModels` و…) تُرجع `200`.

السبب: **تتجاهل بيئة تشغيل Node/Electron المضمّنة في بيئة التطوير المتكاملة مخزن الثقة الخاص بنظام التشغيل**. تثق
الواجهة الخلفية الأصلية (خادم لغة مكتوب بلغة Go) في المرجع المصدّق لنظام التشغيل وتنجح في المصادقة، لكن واجهة Electron الأمامية
لا تفعل ذلك — لذا تعتقد واجهة المستخدم أنها غير متصلة.

الإصلاح (الخطوتان معًا): صدّر `NODE_EXTRA_CA_CERTS=<ca.crt>` **ثم أعد تشغيل بيئة التطوير المتكاملة من
صدفة الأوامر نفسها**، وليس من أيقونة سطح المكتب. أغلق بيئة التطوير المتكاملة بالكامل أولاً — فقفل المثيل الوحيد في Electron يعني أن
التشغيل الثاني يركّز فقط على العملية الموجودة، ويتم تجاهل البيئة الجديدة. راجع §3.2.
يتطابق هذا مع بلاغ مفتوح لدى المشروع الأصلي، حيث يعمل وكيل مستقل عبر MITM، لكن إصدار بيئة التطوير المتكاملة
يفشل في ظل الإعداد نفسه.

### عدم انتشار DNS

تحقق من تحديث `/etc/hosts`:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

امسح ذاكرة DNS المؤقتة:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### عدم اكتشاف بيئة التطوير المتكاملة

يستخدم الاكتشاف التلقائي مسارات التثبيت الشائعة. إذا فشل الاكتشاف رغم تثبيت بيئة التطوير المتكاملة:

- تحقق مما إذا كان الملف الثنائي لبيئة التطوير المتكاملة موجودًا في موقع غير قياسي
- يظل معالج الإعداد يعمل — فشل الاكتشاف يعني فقط أن الشارة لن تعرض مسار التثبيت

### أخطاء المعالج (فشل الجلب من المنبع)

إذا اعترض AgentBridge الطلبات ولكنها فشلت جميعًا:

1. تحقق من اتصال موفّر واحد على الأقل في `/dashboard/providers`
2. تحقق من سجلات خادم OmniRoute: ‏`APP_LOG_LEVEL=debug` في `.env`
3. تحقق من أن `OMNIROUTE_BASE_URL` يشير إلى نقطة نهاية الموجّه الصحيحة (الافتراضي: `http://127.0.0.1:20128`)

## §8 خارطة الطريق

### استقصاء Trae

يُعد Trae مساعدًا جديدًا نسبيًا للبرمجة بالذكاء الاصطناعي. قبل تنفيذ معالج:

1. حدّد الملف التنفيذي/الامتداد في متاجر VS Code / JetBrains أو كتطبيق مستقل
2. التقط حركة البيانات باستخدام mitmproxy لاكتشاف مضيفي API وبُنى نقاط النهاية
3. حدّد آلية المصادقة
4. قيّم قرار المضي أو عدم المضي بناءً على شروط الخدمة وإمكانية اكتشاف API

حتى اكتمال الاستقصاء، تعرض بطاقة Trae في لوحة المعلومات شارة "قيد الاستقصاء" مع رابط "الإبلاغ عن الجدوى". يطرح هيكل المعالج الأولي في `src/mitm/handlers/trae.ts` خطأً منظّمًا من نوع `Not yet implemented`.

### الوكلاء في قائمة المهام المتراكمة (يتطلبون MITM — لا يدعمون عنوان URL أساسيًا مخصصًا)

لا تدعم الأدوات التالية عناوين URL أساسية مخصصة في إصداراتها الحالية، ما يجعل MITM مسار الاعتراض الوحيد. لا يزال تقييم الجدوى معلّقًا:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — منفصل عن Kiro IDE)
- **Cowork** (تطبيق Anthropic لسطح المكتب)

ملاحظة: يدعم GitHub Copilot CLI ≥v1.0.19 المتغير `COPILOT_PROVIDER_BASE_URL` — استخدم الإعداد المباشر بدلًا من MITM لهذه الأداة.
