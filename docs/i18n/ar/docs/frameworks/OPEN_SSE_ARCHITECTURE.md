> **الخلاصة**: يُعدّ `open-sse/` محرك البث الأساسي الذي يشغّل كل طلبات LLM في OmniRoute. ويحتوي على نحو 1,400 ملف تنفّذ مسار معالجة الطلبات، والمنفّذات، والخدمات، وخادم MCP، وطبقة الترجمة. يوضّح هذا الدليل كيفية ترابط هذه الأجزاء معًا.

**المصدر:** `open-sse/` (حزمة مساحة عمل، نحو 1,440 ملف `.ts` غير اختباري)

## لماذا توجد حزمة مستقلة لمساحة العمل؟

يمثّل `open-sse/` **مساحة عمل مستقلة** داخل المستودع الأحادي OmniRoute لعدة أسباب:

1. **قابلية إعادة الاستخدام** — يُنشر `open-sse` باسم `@omniroute/open-sse` على npm، لذا يمكن للمشاريع الأخرى استخدامه بصورة مستقلة
2. **حدود واضحة** — محرك البث منفصل عن طبقة واجهة المستخدم/قاعدة البيانات الخاصة بـ OmniRoute
3. **الأداء** — لا يعتمد المحرك على Next.js، ما يتيح عمليات بدء تشغيل باردة أسرع في سياقات CLI والحوسبة عديمة الخوادم
4. **إدارة الإصدارات** — يمكن لـ `open-sse` إصدار نسخ وفق وتيرته الخاصة

```json
// package.json
"workspaces": ["open-sse"]
```

## مسار معالجة الطلب

يمر كل طلب LLM عبر **مسار معالجة من 5 مراحل**:

```
                              ┌──────────────┐
   طلب HTTP                   │  1. التوجيه  │   حلّ المجموعة، اختيار النموذج
   (مسار Next.js)             └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. الترجمة  │   تحويل التنسيق (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. التنفيذ  │   منفّذ المزوّد، HTTP، إعادة المحاولة، قاطع الدائرة
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. البث     │   تحويل SSE، الضغط العكسي
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. التسجيل  │   تتبّع الاستخدام، سجل الاستدعاءات، تصنيف الأخطاء
                              └──────┬───────┘
                                     │
                                     ▼
                              استجابة HTTP ‏(SSE أو JSON)
```

### المرحلة 1: التوجيه (services/combo.ts)

**نقطة الدخول**: `handleComboChat()` في `services/combo.ts`

تحلّ الطلب إلى صفّ محدد `(provider, model, account, credentials)`:

- البحث عن المجموعة حسب المعرّف (أو إنشاء مجموعة افتراضية لنماذج `auto/*`)
- تطبيق استراتيجية التوجيه (الأولوية، والموزّعة بالأوزان، والتناوب الدوري، وما إلى ذلك)
- استبعاد المزوّدين غير السليمين (قاطع الدائرة)
- اختيار الهدف الصالح التالي

بالنسبة إلى نماذج `auto/*`، تنفّذ هذه المرحلة أيضًا ما يلي:

- تشغيل خوارزمية **التقييم ذات العوامل الـ16** (`services/autoCombo/`)
- اختيار زوج `provider+model` استنادًا إلى السلامة، والتكلفة، وزمن الاستجابة، وما إلى ذلك

### المرحلة 2: الترجمة (translator/)

إذا كان تنسيق المصدر (مثل OpenAI) مختلفًا عن التنسيق الهدف (مثل Claude)، تتم **ترجمة** الطلب:

- موجّه النظام → رسالة النظام
- تعريفات الأدوات → تنسيق الأدوات الخاص بالمزوّد
- معاملات الاستدلال/التفكير → المقابلات الخاصة بالمزوّد
- توحيد أدوار الرسائل (`developer` → `system` لغير OpenAI)

يكشف `translator/index.ts` ما يلي:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### المرحلة 3: التنفيذ (executors/)

**نقطة الدخول**: `getExecutor(providerId).execute(request, options)`

يستخدم جميع المزوّدين `DefaultExecutor` (`executors/default.ts`) عبر الخيار الاحتياطي لمصنع `getExecutor()`. ويقوم المنفّذ بما يلي:

- إنشاء عنوان URL للجهة المنبع (`buildUrl()`)
- إضافة الترويسات الخاصة بالمزوّد (`buildHeaders()`)
- تحويل نص الطلب (`transformRequest()`)
- إرسال طلب HTTP مع إعادة المحاولة + تراجع أُسّي
- معالجة تحديث المصادقة عند الحاجة (مزوّدو OAuth)

توسّع جميع المنفّذات `BaseExecutor` (`executors/base.ts`، بعدد 1170 سطرًا برمجيًا)، الذي يوفّر ما يلي:

- منطق مشترك لإعادة المحاولة
- تكامل الوكيل
- تكامل قاطع الدائرة
- خطافات تسجيل الاستخدام

### المرحلة 4: البث (utils/stream.ts)

بالنسبة إلى الاستجابات المتدفقة، يعيد المنفّذ **ReadableStream**. ويقوم المعالج بما يلي:

- التمرير عبر تحويل SSE (`createSSETransformStreamWithLogger`)
- تطبيق نبضات دورية لاكتشاف الاتصالات المعطّلة
- التعامل بسلاسة مع قطع اتصال العميل (`pipeWithDisconnect`)
- تحويل SSE ← JSON للعملاء الذين لا يستخدمون البث

بالنسبة إلى الاستجابات غير المتدفقة، يعيد المنفّذ كائن JSON محللًا يُمرّر دون تغيير.

### المرحلة 5: التسجيل (services/usage.ts)

بعد الاستجابة (سواء نجحت أم فشلت)، يُسجَّل الاستخدام:

- `prompt_tokens` و`completion_tokens` و`cached_tokens` من الاستجابة
- `cost_usd` محسوبة من بيانات التسعير
- `latency_ms` و`status` و`error_class` في حال الفشل
- تُحفَظ في جدول `usage_history`

تُكتب عناصر سجل الاستدعاءات (إذا كانت مفعّلة) في `${DATA_DIR}/call_logs/`.

## نظرة متعمقة على الملفات الرئيسية

### chatCore.ts (5977 سطرًا)

**معالج الطلبات الرئيسي**. رغم حجمه، فإنه يتمتع ببنية واضحة:

```ts
// البنية التقريبية لملف chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. المصادقة + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. التحقق من صحة جسم الطلب
  const body = await parseRequestBody(request);

  // 3. اكتشاف التنسيق + التحويل
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. توجيه المجموعة
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // المتابعة إلى الهدف التالي
    }
  }

  // 5. البديل الاحتياطي للطوارئ
  return await emergencyFallback(body);
}
```

رغم كونه دالة عملاقة واحدة، فإنه منظّم في **أقسام موضحة بالتعليقات** تتوافق مع خط الأنابيب ذي المراحل الخمس.

### combo.ts (4456 سطرًا من التعليمات البرمجية)

**محرك التوجيه** الذي يحوّل المجموعة إلى أهداف مرتبة.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

يدعم **19 استراتيجية توجيه** (راجع `src/shared/constants/routingStrategies.ts`):

| الاستراتيجية        | السلوك                                                                      |
| ------------------- | --------------------------------------------------------------------------- |
| `priority`          | قائمة مرتبة يبدأ تنفيذها من الهدف الأول                                     |
| `weighted`          | اختيار احتمالي بحسب وزن كل هدف                                              |
| `round-robin`       | التنقل دوريًا بين الأهداف بالترتيب                                          |
| `context-relay`     | تمرير السياق بين الأهداف                                                    |
| `fill-first`        | استنفاد الحصة قبل الانتقال إلى الهدف التالي                                 |
| `p2c`               | قوة الاختيار بين خيارين                                                     |
| `random`            | اختيار عشوائي منتظم                                                         |
| `least-used`        | اختيار الهدف ذي أقل عدد من الاستخدامات الأخيرة                              |
| `cost-optimized`    | اختيار أرخص هدف سليم أولًا                                                  |
| `reset-aware`       | مراعاة نوافذ إعادة تعيين المزوّد                                            |
| `reset-window`      | التوجيه استنادًا إلى نافذة إعادة التعيين                                    |
| `headroom`          | اختيار الهدف ذي أكبر هامش متبقٍ من الحصة أولًا                              |
| `strict-random`     | اختيار منتظم فعليًا (من دون ترجيح الجودة)                                   |
| `auto`              | استخدام تقييم قائم على 16 عاملًا (`autoCombo/`)                             |
| `lkgp`              | استخدام آخر مزوّد معروف بأنه يعمل جيدًا أولًا                               |
| `context-optimized` | الأنسب للطلبات ذات السياق الطويل                                            |
| `fusion`            | إرسال الطلب بالتوازي إلى مجموعة، ثم توليف النتائج عبر مُحكِّم (`fusion.ts`) |

## المنفّذات (أكثر من 75 ملفًا)

ملف واحد لكل موفّر. جميعها توسّع `BaseExecutor` وتتجاوز ما يختلف.

### الأنماط الشائعة

يُحدَّد الموفّرون عبر `getExecutor(providerId)`، التي تعيد المنفّذ الذي جرى تكوينه. تستخدم الموفّرات المتوافقة مع OpenAI/Anthropic المنفّذ `DefaultExecutor` (`executors/default.ts`). يُضبط السلوك الخاص بكل موفّر (عنوان URL الأساسي، وترويسات المصادقة، وإصدار API) في `open-sse/config/providers/`، بينما تُعالَج تحويلات جسم الطلب في `open-sse/translator/`.

يُعيَّن **عنوان URL المخصّص** عبر تكوين الموفّر:

```ts
// تكوين الموفّر في open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

تُعالَج **المصادقة المخصّصة** من خلال تكوين المصادقة في سجل الموفّرين (مفتاح API، وOAuth، وملفات تعريف الترويسات).

تُسجَّل تحويلات **جسم الطلب المخصّص** (مثل فصل Anthropic للحقل `system` عن `messages`) لكل موفّر في `open-sse/translator/`.

````

### مصنع المنفّذات

يصدّر `executors/index.ts` الدالة `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

تمر عملية التحديد عبر `ExecutorRegistry` (`executors/registry.ts`): يُصرَّح بكل منفّذ متخصص في الجدول المضمّن داخل `executors/index.ts` ويُسجَّل عبر `registerExecutor(alias, instance)` عند تحميل الوحدة؛ وتستشير `getExecutor()` السجل، ثم ترجع إلى `DefaultExecutor` مخزّن مؤقتًا لأي موفّر لا يملك إدخالًا متخصصًا. ويحدّد الاختبار الذهبي `tests/unit/executor-map-golden.test.ts` التعيين الكامل من الاسم البديل إلى المنفّذ.

## المترجمات

الترجمة بين **3 تنسيقات**: OpenAI وAnthropic وGemini، بالإضافة إلى Responses API الجديدة.

### متى تحدث الترجمة

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

الترجمات الشائعة:

- `OpenAI → Anthropic`: حقل `system` منفصل، وترويسة `x-api-key`
- `OpenAI → Gemini`: استخدام `contents` بدلاً من `messages`، و`systemInstruction`
- `OpenAI → Responses API`: مصفوفة `input`، وحالة `previous_response_id`

### الحالات الحدّية التي تتم معالجتها

- دور `developer` → `system` لموفّري الخدمات غير OpenAI
- دور `system` → يُدمج في رسالة المستخدم الأولى لـ GLM/ERNIE
- `json_schema` → الخاصيتان `responseMimeType` و`responseSchema` في Gemini
- `tools` → تنسيق الأدوات الخاص بموفّر الخدمة
- معاملات التفكير (o1 وClaude) → المكافئات الخاصة بموفّر الخدمة

## خادم MCP

ينفّذ `open-sse/mcp-server/` خادم **Model Context Protocol**:

- **110 أدوات** (إدارة موفّري الخدمات، والتركيبات، والذاكرة، وذاكرة التخزين المؤقت، والضغط، والوكيل، والمهارات، والتلعيب، والمكوّنات الإضافية، وNotion، وObsidian، والمجموعة المحلية)
- **3 وسائل نقل**: stdio وSSE وStreamable HTTP
- **33 نطاقاً** للتخويل الدقيق

### تسجيل الأدوات

تُسجَّل الأدوات كملفات مستقلة في `open-sse/mcp-server/tools/`، ويُصدّر كل منها اسماً ومخططاً ومعالجاً ونطاقاً:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### وسائل النقل

```ts
// stdio (استخدام CLI)
startMcpStdio(server);

// SSE (بث قائم على HTTP)
startMcpSse(server, port);

// Streamable HTTP (MCP حديث)
startMcpStreamable(server, port);
```

### التخويل

تمر كل عملية استدعاء لأداة عبر عمليات التحقق من النطاق (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## المحوّلات

يحوّل `open-sse/transformer/` بين تنسيقات **Chat Completions** و**Responses API**.

### لماذا يوجد محوّل منفصل؟

Responses API هو التنسيق الجديد من OpenAI، ويدعم **المحادثات ذات الحالة** (`previous_response_id`). عندما يرسل عميل طلب Responses، يقوم OmniRoute بما يلي:

1. يحوّل Responses → Chat Completions داخلياً
2. يرسل الطلب إلى موفّر الخدمة (أي موفّر يدعم Chat Completions)
3. يحوّل الاستجابة مرة أخرى إلى تنسيق Responses
4. يبث الاستجابة المحوّلة إلى العميل

يوفّر المحوّل (`transformer/responsesTransformer.ts`) ما يلي:

```ts
createResponsesApiTransformStream(): TransformStream
```

يتعامل هذا مع:

- أحداث `response.output_item.added`
- أحداث `response.output_text.delta`
- حدث `response.completed`
- تعيين استدعاءات الأدوات (`function_call` ↔ `tool_calls`)

يحتوي `open-sse/config/` على طبقة الإعداد:

interface ProviderConfig {

يمتلك محرك التوجيه ميزانيات أداء صارمة:

| العملية                                                      | الهدف | القياس                          |
| ------------------------------------------------------------ | ----- | ------------------------------- |
| حلّ التركيبات                                                | <10ms | لـ 50 هدفًا                     |

| **لا توجد عمليات إدخال/إخراج حاجبة في المسار الحرج للتوجيه** | —     | جميعها غير متزامنة              |

## الأنماط المضادة

❌ **استدعاءات متزامنة لقاعدة البيانات في `combo.ts`** — نفّذ الحساب مسبقًا وخزّن النتائج مؤقتًا
❌ **منطق إعادة المحاولة في المعالِجات** — استخدم `retry()` من خدمة المرونة
❌ **الوصول المباشر إلى إعدادات المزوّد** — استخدم دوال الجلب الخاصة بـ `providerRegistry`
❌ **سلاسل رجوع احتياطي ثابتة في الشفرة** — عرّفها في `modelFamilyFallback.ts`
❌ **تعديلات الحالة عبر الطلبات المتزامنة** — استخدم سياقًا خاصًا بكل طلب فقط

## إضافة مكوّن جديد

### إضافة خدمة جديدة

1. أنشئ `open-sse/services/[serviceName].ts` بمسؤولية محددة
2. صدّر دالة المعالجة الرئيسية وأي ثوابت
3. أضف اختبارات وحدة في `tests/unit/services/[serviceName].test.mjs`
4. ادمجها في مسار معالجة الطلبات في `handlers/chatCore.ts` (إذا كانت مرتبطة بالتوجيه)
5. حدّث منطق التوجيه في `combo.ts` إذا كانت الخدمة تؤثر في اختيار الهدف
6. وثّقها في هذا الملف

### إضافة منفّذ جديد

1. أنشئ `open-sse/executors/[provider].ts` مع توسيع `BaseExecutor`
2. سجّله في `config/providerRegistry.ts`
3. أضفه إلى مصنع `executors/index.ts`
4. أضف اختبارات وحدة للمنفّذ
5. وثّقه في `docs/architecture/ARCHITECTURE.md`

### إضافة أداة MCP جديدة

1. أنشئ أو حدّث `open-sse/mcp-server/tools/[category]Tools.ts`
2. عرّف مخطط Zod للمدخلات
3. سجّل الأداة في `mcp-server/index.ts`
4. أضفها إلى مصفوفة النطاقات في `mcp-server/auth/`
5. أضف اختبارات وحدة
