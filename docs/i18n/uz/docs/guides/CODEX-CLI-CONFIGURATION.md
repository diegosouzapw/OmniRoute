> **TOML — yagona ishlaydigan format.** Zamonaviy Codex faqat
> `~/.codex/config.toml` faylini oʻqiydi (codex-cli 0.147.0 bilan tekshirilgan:
> `codex --help` hujjatida `-c/--config` orqali qayta belgilashlar
> "`~/.codex/config.toml` faylidan yuklanishi" koʻrsatilgan). Eski
> `~/.codex/config.yaml` avvalgi npm CLIʼga tegishli boʻlib, indamay eʼtiborsiz
> qoldiriladi. Boshqaruv paneli generatori (`/api/cli-tools/apply`, `codex`
> vositasi) TOMLʼni ehtiyotkor birlashtirish bilan yozadi — mavjud kalitlar va
> boshqa provayder bloklari saqlanadi, API kaliti `OMNIROUTE_API_KEY` ichida
> qoladi (hech qachon fayl ichida emas), qolib ketgan eski `config.yaml` fayliga
> esa tegilmasdan, migratsiya eslatmasi sifatida xabar beriladi.

## Nusxalab qoʻyishga tayyor config.toml

`<YOUR_HOST>` va `<YOUR_KEY>` oʻrniga oʻz qiymatlaringizni kiriting:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # har bir vosita chaqiruvi uchun tarixni saqlash chegarasi

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc yoki ~/.zshrc — haqiqiy kalit qiymati, hech qachon config.toml ichida emas
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT ilovasiga biriktirilgan Codex

Agar Codexʼni ChatGPT ish stoli ilovasi orqali oʻrnatgan boʻlsangiz, `codex`
binar fayli faqat ilova toʻplami ichida boʻlishi va hali shell `PATH` roʻyxatiga
kiritilmagan boʻlishi mumkin. Resurslar katalogini shell ishga tushirish fayliga
qoʻshing:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Yangi shell oching, soʻng tekshiring:

```bash
command -v codex
codex --version
```

### Autentifikatsiyasiz mahalliy OmniRoute: vaqtinchalik kalit yetarli

Codex birinchi soʻrov CLIʼdan chiqishidan **oldin** `env_key` orqali nomlangan
muhit oʻzgaruvchisi mavjudligini tekshiradi. Agar **mahalliy** OmniRoute
instansiyangiz autentifikatsiyani talab qilmasa, istalgan boʻsh boʻlmagan
vaqtinchalik qiymat ishlaydi:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

OmniRoute serveringiz himoyalangan yoki masofaviy boʻlsa, uning oʻrniga haqiqiy
kalitdan foydalaning.

> **Keng tarqalgan host variantlari**
>
> | Kirish          | URL                           |
> | --------------- | ----------------------------- |
> | Mahalliy tarmoq | `http://192.168.0.1:20128/v1` |
> | Tailscale       | `http://100.x.x.x:20128/v1`   |
> | Loopback        | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — nega u barcha modellar bilan ishlaydi

Codex CLI 2026-yil fevral oyida `wire_api = "chat"` (Chat Completions)ʼni eskirgan deb belgiladi va endi `wire_api = "responses"` (OpenAI Responses API)ʼni **talab qiladi**. v0.138ʼdan boshlab `wire_api = "chat"` sozlamasi ishga tushish vaqtida darhol nosozlikka olib keladi.

Koʻplab provayderlar, jumladan GLM va Kimi, hanuz faqat Chat Completions endpointʼini taqdim etadi. DeepSeek V4 endi mahalliy Responses API bilan birga Anthropic bilan mos endpointʼni ham taqdim etadi; OmniRoute standart holatda Responsesʼdan foydalanadi va har bir DeepSeek ulanishiga Anthropic mosligini tanlash imkonini beradi.

**OmniRoute buni shaffof tarzda hal qiladi:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute provayderning mahalliy protokolini tanlaydi va zarur boʻlganda tarjima qiladi
    → POST /responses (DeepSeek V4) yoki /chat/completions (Mistral / GLM / Kimi / boshqalar)
```

OmniRouteʼdan foydalanganda sizga hech qachon alohida tarjima proksisi kerak boʻlmaydi. **Barcha modellar `wire_api = "responses"`ʼdan foydalanadi** — qolganini OmniRoute bajaradi.

> **`wire_api` standart qiymatdir** — maydonning standart qiymati `"responses"` boʻlib, uni `config.toml` faylidan butunlay chiqarib tashlash mumkin. Uni faqat maqsadni hujjatlashtirmoqchi boʻlsangizgina aniq koʻrsating.

## Kontekst oynasi va ixchamlashtirish

### Token konfiguratsiyasi maydonlari

| Maydon                           | Tavsif                                                                                                                                                                                                                        |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Faol model uchun umumiy token budjeti. Model uchun eʼlon qilingan limitga sozlang.                                                                                                                                            |
| `model_auto_compact_token_limit` | Tarixni avtomatik ixchamlashtirishni ishga tushiradigan chegara. **Maksimum: `model_context_window` qiymatining 90%i** — 90%dan yuqori qiymatlar bildirishsiz eʼtiborsiz qoldiriladi.                                         |
| `tool_output_token_limit`        | Har bir vosita chaqiruvi natijasi uchun tarixda saqlanadigan tokenlar chegarasi. Bitta katta vosita javobi oynani toʻldirib yuborishining oldini oladi. **Bu maksimal chiqish hajmi emas** — bu tarixda saqlash chegarasidir. |
| `compact_prompt`                 | Ixchamlashtirish vaqtida ishlatiladigan tizim prompti uchun bevosita qayta belgilash (v0.138+).                                                                                                                               |

> **`model_max_output_tokens` haqida eslatma**: Bu maydon **Codex CLI konfiguratsiya sxemasiga kirmaydi** (Codex Rust kod bazasida mavjud emas). Sozlansa, u bildirishsiz eʼtiborsiz qoldiriladi. Unga tayanmang — vosita chiqishining qancha qismi tarixda saqlanishini boshqarish uchun `tool_output_token_limit`dan foydalaning.

## Fikrlash darajasi

Model javob berishdan oldin qancha «fikrlashi»ni boshqaradi.

| Qiymat   | Qo‘llanishi                                                      |
| -------- | ---------------------------------------------------------------- |
| `none`   | Fikrlashsiz — to‘g‘ridan-to‘g‘ri javob                           |
| `low`    | Oddiy vazifalar (nomini o‘zgartirish, formatlash)                |
| `medium` | Ko‘rsatilmaganda **server standarti**                            |
| `high`   | O‘rta darajadagi vazifalar (refaktoring, nosozliklarni tuzatish) |
| `xhigh`  | Arxitektura, chuqur tahlil, murakkab muammolar                   |

```bash
# Har bir ishga tushirish uchun alohida sozlash
codex -c model_reasoning_effort=low "x o‘zgaruvchisini count deb qayta nomla"
codex -c model_reasoning_effort=xhigh "autentifikatsiya modulini loyihala"
```

Desktop faqat shifrlangan bloklarni emas, fikrlash matnini ham ko‘rsata olishi uchun fikrlash **xulosasi**ni ham sozlang:

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # yoki qo‘llab-quvvatlanganda ultra
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute fikrlash budjeti (server sozlamasi)

Codex darajasi/xulosasi yuqori oqimga yetib borishi uchun OmniRoute xostida **Settings → AI → Thinking Budget** qiymati **`passthrough`** bo‘lishi kerak. **`auto` rejimi** mijozning barcha `reasoning` / `reasoning_effort` maydonlarini olib tashlaydi va Codex to‘g‘ri sozlangan bo‘lsa ham fikrlash panellarini bo‘sh qoldiradi.

To‘liq qo‘llanma: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Siqish va prompt keshi bir-biridan mustaqil bo‘lib, `passthrough` rejimida ishlashda davom etadi.

## Profillar — har bir model/ish jarayoni uchun nomlangan konfiguratsiyalar

Profillar model va kontekst oynasini bitta bayroq yordamida almashtirish imkonini beradi. Har bir profil asosiy `config.toml` ustiga qo‘llanadigan oddiy
`~/.codex/<name>.config.toml` faylidir.

> **Nomlash qoidasi (Codex CLI v0.137+):** fayl `~/.codex/<name>.config.toml` ko‘rinishida bo‘lishi shart — **`profile-` prefiksisiz**.
> CLI `-p kimi-k27` parametrini → `~/.codex/kimi-k27.config.toml` sifatida aniqlaydi. Agar fayl topilmasa, standart sozlama bildirishsiz qo‘llanadi.

```bash
codex --profile kimi-k27 "ushbu kod bazasining 10 ming qatorini tahlil qil"
codex -p glm52 "arxitekturani ko‘rib chiq"
codex --profile deepseek-flash "o‘zgaruvchi nomini o‘zgartir"   # tez, arzon
```

### Daraja profillari (bir xil model, turli daraja)

```bash
codex -p low      # cx/gpt-5.5, daraja=low

codex -p xhigh    # cx/gpt-5.5, daraja=xhigh (standart)
codex -p chat     # cx/gpt-5.5, daraja belgilanmagan (server standarti)
```

## `omniroute setup-codex` yordamida profillarni avtomatik yaratish

Agar OmniRoute’ni VPS’da ishga tushirsangiz, faol modellar katalogidan profil fayllarini avtomatik yaratishingiz mumkin:

```bash
# VPS'dan (20128-portdagi mahalliy OmniRoute'dan foydalanadi)
omniroute setup-codex

# Istalgan qurilmadan — VPS manzilingizni ko'rsating
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Fayllarni yozmasdan oldindan ko'rish
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Faqat GLM va Kimi profillarini yaratish
omniroute setup-codex --only glm,kimi

# Maxsus katalogga yozish
omniroute setup-codex --codex-home /path/to/.codex
```

Buyruq `/v1/models` ma’lumotlarini oladi, ma’lum modellar uchun moslashtirilgan profillardan foydalanadi, boshqa mos matn modellari uchun katalog metama’lumotlariga tayanadi va har biri uchun `~/.codex/<name>.config.toml` faylini yozadi. Idempotent — qayta ishga tushirish xavfsiz.

Shuningdek, provayder modellarini muvaffaqiyatli aniqlash/import qilish faol katalogni o‘zgartirgach, OmniRoute ayni profil fayllarini **avtomatik sinxronlashi** mumkin. Bu imkoniyat **ixtiyoriy va birlamchi holatda o‘chirilgan**: uni **CLI Code boshqaruv paneli** orqali yoqing ("CLI profile auto-sync" → Codex) yoki `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` qiymatini o‘rnating (u birlamchi holatda yoqilgan `CLI_ALLOW_CONFIG_WRITES` parametrini ham hisobga oladi). Yoqilganda, u faqat alohida `~/.codex/*.config.toml` profil fayllarini yozadi; faol/standart `~/.codex/config.toml`, Codex-lb sozlamalari, autentifikatsiya yoki provayder tanlovini hech qachon o‘zgartirmaydi.

## Uzoq davom etuvchi vazifalar

OmniRoute’ning ikkita standart sozlamasi bir necha soat davom etadigan Codex CLI seanslariga sezdirmasdan xalal berishi mumkin. Ularning hech biri Codex CLI sozlamasi emas — ikkalasi ham OmniRoute tomonida joylashgan. Hisoblarni biriktirib qo‘yadigan va faolsizlik bo‘yicha uzilishlarni o‘chiradigan yuqori oqim proksilaridan konfiguratsiyani ko‘chirayotgan foydalanuvchilar ko‘pincha har ikkala muammoga duch kelib, OmniRoute «uzoq seansni ushlab tura olmaydi» degan xulosaga kelishadi.

| Alomat                                                                                              | Ehtimoliy sabab                                                                                         | Sozlama                  |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------ |
| Seans hisoblarni almashtirishda davom etadi / navbatlar orasida prompt keshi uzluksizligi yo‘qoladi | Seansga bog‘liqlik TTL qiymati `0` (o‘chirilgan)                                                        | `sessionAffinityTtlMs`   |
| Mijozga hech qanday so‘rov ko‘rsatilmasdan, mulohaza yuritish o‘rtasida ulanish uziladi             | Yuqori oqimdan 10 daqiqa davomida bo‘lak kelmagani uchun oqimning faolsizlik nazoratchisi ishga tushgan | `STREAM_IDLE_TIMEOUT_MS` |

Tegishli muhokamalar: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (uzoq vazifalarning uzilishi), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (bog‘liqlik nega standart holatda o‘chiq). Kuzatuv: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Seansga bog‘liqlik — bitta suhbatni bitta hisobga biriktirish

**Standart:** `sessionAffinityTtlMs = 0` (o‘chirilgan).

**Uni qayerda sozlash kerak**

- Boshqaruv paneli → **Sozlamalar → Yo‘naltirish** → **Seansga bog‘liqlik** → **Bog‘liqlik TTL (soniyalarda)** (`ComboDefaultsTab`)
- Yoki **millisoniyalarda** ko‘rsatilgan `sessionAffinityTtlMs` bilan sozlamalarni PATCH qiling (Zod oralig‘i `0`–`86_400_000`, ya’ni 24 soatgacha)

> #7274 da faqat Codex uchun mo‘ljallangan `codexSessionAffinityTtlMs` nomidan o‘zgartirilgan. Eski kalit hali ham faqat o‘qish uchun taxallus sifatida qabul qilinadi; yangi konfiguratsiyalar `sessionAffinityTtlMs` dan foydalanishi kerak. Endi TTL `0` dan yuqori bo‘lsa, bog‘liqlik faqat Codex uchun emas, **istalgan** provayderga qo‘llanadi — [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Seansga bog‘liqlik bo‘limiga qarang.

**Qiymat 0 bo‘lib qolsa, nima buziladi**

Ko‘p navbatli Codex suhbatining har bir navbati faol kombinatsiya strategiyasi orqali mustaqil yo‘naltiriladi va **har bir navbatda boshqa hisobga** tushishi mumkin. Bu yuqori oqim seansi / prompt keshi uzluksizligini buzadi. OmniRoute faqat TTL qiymati `0` dan katta bo‘lgandagina Codex seans sarlavhalari (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) va `prompt_cache_key` / `session_id` kabi tana maydonlarini tekshiradi (`src/sse/services/auth.ts` ichidagi `extractSessionAffinityKey`).

**Bir necha soatlik yagona vazifa uchun tavsiya**

TTL qiymatini **vazifaning kutilayotgan real vaqt davomiyligidan yuqori** qilib belgilang (UI dagi maksimum — **86400 soniya** = 24 soat):

| Kutilayotgan vazifa davomiyligi | Bog‘liqlik TTL (UI, soniyalarda) | `sessionAffinityTtlMs` |
| ------------------------------- | -------------------------------- | ---------------------- |
| Bir necha soat                  | `14400` (4 soat)                 | `14400000`             |
| Tun davomida / ~12 soat         | `43200` (12 soat)                | `43200000`             |
| To‘liq kun                      | `86400` (24 soat, maksimum)      | `86400000`             |

Ixtiyoriy yoqish ataylab tanlangan: bog‘liqlikni o‘chirish hisoblar orasida yukni muvozanatlashga ustunlik beradi; uni yoqish esa bitta uzoq agent seansi uchun uzluksizlikka ustunlik beradi. Ushbu qo‘llanma standart qiymatni **o‘zgartirmaydi** — uzoq Codex vazifalarini bajarayotgan operatorlar bu imkoniyatni o‘zlari yoqishlari kerak.

### 2. Oqimning faolsizlik taymauti — sokin mulohaza yuritish navbatlarini to‘xtatmang

**Standart:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 daqiqa). Agar belgilanmagan bo‘lsa, u `REQUEST_TIMEOUT_MS` qiymatini meros qilib oladi; umumiy boshlang‘ich qiymat ham 600000. [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Taymautlar bo‘limiga qarang.

**Standart qiymatda nima buziladi**

10 daqiqadan ortiq jim qoladigan, **yuqori oqimdan hech qanday haqiqiy boʻlak kelmaydigan** Codex reasoning / vosita bosqichi SSE bekor turish kuzatuvchisi (`open-sse/utils/stream.ts`) tomonidan majburan yopiladi. Mijoz koʻpincha ulanishning hech qanday izohsiz uzilganini koʻradi — bu “hech qanday bildirishnomasiz avtomatik toʻxtadi” holatiga mos keladi.

Muhim tafsilot: OmniRoute’ning sintetik SSE **heartbeat signali bekor turish taymerini qayta boshlamaydi**. Faqat yuqori oqim tanasining haqiqiy boʻlagi `lastChunkTime` qiymatini yangilaydi. Hali ham “oʻylayotgan” jim model kuzatuvchi nuqtayi nazaridan toʻxtab qolgan yuqori oqim bilan bir xil koʻrinadi.

Undici tanasining harakatsizlik sozlamasi ham tegishli: `FETCH_BODY_TIMEOUT_MS` (u ham sukut boʻyicha ayni 10 daqiqalik asosiy qiymatdan foydalanadi; `0` uni oʻchiradi). Oqimli uzatishda `FETCH_TIMEOUT_MS` faqat ulanishni oʻrnatish / dastlabki sarlavhalarni qamrab oladi — oqim faollashgach, toʻxtab qolishlar `STREAM_IDLE_TIMEOUT_MS` va `FETCH_BODY_TIMEOUT_MS` orqali boshqariladi.

**Bir necha soatlik yagona vazifa uchun tavsiya**

OmniRoute jarayoni muhitida (`.env` / compose / systemd):

```bash
# Uzoq reasoning bosqichlari uchun oqimning bekor turishi va tana harakatsizligi cheklovlarini o‘chirish
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Yoki ularni kutilayotgan eng uzoq jimlik oraligʻidan yuqoriroq qiymatga oshiring (qiymatlar millisekundlarda):

```bash
# Misol: yuqori oqim bo‘laklari orasida 2 soatgacha jimlikka ruxsat berish
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Ushbu muhit oʻzgaruvchilarini oʻzgartirgandan soʻng OmniRoute’ni qayta ishga tushiring.

### Aniq yoʻriqnoma — bir necha soatlik Codex vazifasi

1. **Hisobni biriktiring:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12 soat) yoki `86400` (maksimal 24 soat).
2. OmniRoute muhitida **bekor turish cheklovlarini oshiring / oʻchiring**:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Odatdagi Codex `config.toml` sozlamalarini (`wire_api = "responses"`, toʻgʻri `base_url`, `OMNIROUTE_API_KEY`) saqlang — ushbu ikki xatti-harakat uchun Codex tomonida affinity/bekor turish sozlamalari mavjud emas.
4. OmniRoute’ni qayta ishga tushiring, soʻng uzoq davom etuvchi Codex vazifasini boshlang.

### Standart qiymatlar boʻyicha qaror (#7287)

| Sozlama                  | Yetkazib beriladigan standart qiymat | Ushbu qoʻllanmada oʻzgartirilsinmi?                                                                                    |
| ------------------------ | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (oʻchirilgan)                    | **Yoʻq** — ixtiyoriy boʻlib qoladi (yuklamani muvozanatlash va uzluksizlik; Discussion #5718 ga qarang)                |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 daqiqa)                 | **Yoʻq** — umumiy trafik uchun 10 daqiqa boʻlib qoladi; uzoq Codex vazifalari operatorlari uni oshiradi yoki oʻchiradi |

Har ikkala standart qiymatdan birini global tarzda oʻzgartirish faqat Codex emas, instansning har bir mijozi uchun xatti-harakatni oʻzgartiradi. Sozlamalarni hujjatlashtiring; operatorning aniq qarori boshqacha koʻrsatma bermaguncha standart qiymatlarni oʻz holicha qoldiring.

### Bekor turish sababli uzilishlarni diagnostika qilish

Bekor turish kuzatuvchisi ishga tushganda, OmniRoute quyidagi shakldagi qatorni jurnalga yozadi:

```text
[STREAM] Bekor turish taym-auti: codex xizmatidan 600000ms davomida ma’lumot kelmadi (model: cx/gpt-5.5)
```

`Idle timeout: no data from` iborasini (yoki `stream_idle_timeout` kodini / `StreamIdleTimeoutError` xato nomini) grep orqali qidiring. Provayder segmenti OmniRoute ushbu soʻrov uchun foydalangan qiymatdir (`codex`, boshqa provayder identifikatori yoki nomaʼlum boʻlsa `provider`) — u har doim ham aynan `codex` satri boʻlavermaydi.

## Muammolarni bartaraf etish

**`Error: wire_api = "chat" is no longer supported`**
Konfiguratsiyangizdan `wire_api = "chat"` qatorini olib tashlang. `wire_api = "responses"` qilib belgilang yoki maydonni kiritmang (v0.138 dan boshlab standart qiymat — `"responses"`).

**`Error: model not found`**
Model OmniRoute’da toʻgʻri prefiks bilan mavjudligini tekshiring. `omniroute models list` buyrugʻidan foydalaning yoki `/dashboard/providers/<provider>` sahifasini oching.

**`Authentication error`**
`OMNIROUTE_API_KEY` eksport qilinganini tasdiqlang: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex birinchi soʻrovni yuborishdan oldin muhit oʻzgaruvchisi mavjudligini tekshiradi. Himoyalangan serverlar uchun haqiqiy kalitni eksport qiling yoki **mahalliy** OmniRoute nusxangiz autentifikatsiyani talab qilmasa, `OMNIROUTE_API_KEY=local` kabi boʻsh boʻlmagan o‘rinbosar qiymatdan foydalaning. Agar uni `~/.bashrc` yoki `~/.zshrc` fayliga qoʻshgan boʻlsangiz, shell’ni qayta ishga tushiring.

**`Connection refused`**
OmniRoute ishlayotganini va `base_url` host/porti tarmogʻingiz uchun toʻgʻri ekanini tekshiring (mahalliy, Tailscale yoki VPS).

**Seans kontekst chegarasiga yaqinlashganda ishdan chiqadi**
`model_context_window` va `model_auto_compact_token_limit` qiymatlarini aniq belgilang. Yuqoridagi kontekst oynasi jadvaliga qarang.

**Ixchamlashtirish juda kech ishga tushadi**
`model_auto_compact_token_limit` qiymatini oyna hajmining 80–85%igacha kamaytiring. Uni hech qachon 90%dan yuqori belgilamang.

**Profil yuklanmayapti (`-p <name>` indamay eʼtiborsiz qoldiriladi)**
Fayl `~/.codex/<name>.config.toml` manzilida mavjudligini tasdiqlang (`profile-` prefiksisiz). `ls ~/.codex/*.config.toml` buyrugʻini ishga tushiring.

**Uzoq davom etuvchi Codex vazifasi bajarilish oʻrtasida uziladi / soʻrovlar orasida hisoblarni almashtiradi**
[Uzoq davom etuvchi vazifalar](#long-running-tasks) boʻlimiga qarang. Seansga bogʻliqlikni yoqing (TTL vazifa davomiyligidan uzun boʻlsin) va `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS` qiymatlarini oshiring yoki ularni oʻchirib qoʻying. OmniRoute jurnallarida `Idle timeout: no data from` matnini grep orqali qidiring.
