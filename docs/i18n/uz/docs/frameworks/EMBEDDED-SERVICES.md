## 1. Umumiy ko‘rinish

### Nima uchun ichki xizmatlar?

Oltita xizmat ichki tarzda biriktirilgan:

| Xizmat          | npm paketi                            | Standart port | Maqsad                                                                                                                                                                                                        |
| --------------- | ------------------------------------- | :-----------: | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **9Router**     | `9router`                             |     20130     | OmniRoute quyi provayder sifatida foydalanishi mumkin bo‘lgan AI routeri. Modellar `9router/{sub}/{model}` ko‘rinishida taqdim etiladi                                                                        |
| **CLIProxyAPI** | GitHub reliz binar fayli (`cliproxy`) |     8317      | Anthropic CLI autentifikatsiya oqimlari uchun lokal proksi adapteri. OAuth tokenlarining muddati tugaganda zaxira marshrutlashni ta’minlaydi                                                                  |

| **Bifrost**     | `@maximhq/bifrost`                    |     8080      | Go AI-shlyuzining retranslyatsiya bekendi. Ishlayotganida retranslyatsiya marshruti (`/v1/relay/`) tomonidan avtomatik tanlanadi                                                                              |

Oltala xizmat ham bir xil nazorat modeliga amal qiladi:

- OmniRoute ularni `DATA_DIR/services/{name}/` ostiga o‘rnatadi (OmniRoute’ning o‘z `package.json` faylidan ajratilgan holda)
- OmniRoute ularni quyi jarayonlar sifatida ishga tushiradi va kuzatadi
- OmniRoute vaqtinchalik API kalitini quyi jarayon muhitiga kiritadi va uni uzilishlarsiz almashtiradi (tegishli hollarda)
- Barcha boshqaruv marshrutlari (`/api/services/*`) **LOCAL_ONLY** — ularga faqat loopback orqali kirish mumkin (qat’iy qoida #17)

## 3. Hayot sikli holat mashinasi

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
             holat tekshiruvi yaxshi│         nosozlik / SIGTERM │
                               ┌────▼─────┐  (5 s ichida chiqish)│
                               │ running  │──── nosozlik ───────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

Holatlar `version_manager` DB jadvalida (`status` ustuni) saqlanadi va
`ServiceSupervisor` xotiradagi holatida aks ettiriladi. Ishlayotgan jarayon uchun
xotiradagi holat asosiy hisoblanadi; DB holati yuklanish paytidagi doimiy zaxira
hisoblanadi.

### Holat o‘tishlari

| Qayerdan        | Hodisa                                | Qayerga                   |
| --------------- | ------------------------------------- | ------------------------- |
| `not_installed` | `install()` muvaffaqiyatli            | `stopped`                 |
| `stopped`       | `start()` chaqirildi                  | `starting`                |
| `starting`      | holat tekshiruvi 200 qaytardi         | `running`                 |
| `starting`      | jarayon sog‘lom holatga kelmay chiqdi | `error`                   |
| `running`       | `stop()` chaqirildi                   | `stopping` → `stopped`    |
| `running`       | jarayon kutilmaganda chiqdi (< 5 s)   | `error` (tezkor nosozlik) |
| `running`       | jarayon kutilmaganda chiqdi (> 5 s)   | `error`                   |
| `error`         | `start()` chaqirildi                  | `starting`                |
| istalgan        | `stopping` paytida `stop()`           | hech qanday amal yo‘q     |

### Amaliyot qulfi

`ServiceSupervisor` hayot sikli amaliyotlarini asinxron amaliyot qulfi
(`withLock()`) orqali ketma-ketlashtiradi. Bir xil nazoratchida parallel `start()`
chaqiruvlari aniq bitta jarayonni ishga tushiradi; ikkinchi chaqiruvchi kutadi va
mavjud holatni qaytaradi. Bu, masalan, avtomatik ishga tushirish va UI tugmasi bir
vaqtda faollashganda poyga holatlarining oldini oladi.

## 4. API maʼlumotnomasi

`/api/services/` ostidagi barcha marshrutlar **LOCAL_ONLY** hisoblanadi (faqat loopback, qatʼiy qoida #17).
Loopback bo‘lmagan so‘rovlar autentifikatsiya tokenidan qatʼi nazar `403 LOCAL_ONLY` javobini oladi.

### 4.1 9Router endpointlari (11 ta marshrut)

#### `POST /api/services/9router/install`

9Router’ni npm orqali o‘rnatadi. O‘zining `package.json` va `node_modules/` fayllariga ega
`DATA_DIR/services/9router/` katalogini yaratadi. OmniRoute’ning o‘z bog‘liqliklari bilan ziddiyatga kirishmaydi.

**So‘rov tanasi** (barchasi ixtiyoriy):

```json
{ "version": "latest" }
```

| Maydon    | Tur      | Standart qiymat | Tavsif                                      |
| --------- | -------- | --------------- | ------------------------------------------- |
| `version` | `string` | `"latest"`      | O‘rnatiladigan npm versiya tegi yoki semver |

**Javoblar:**

| Holat | Tavsif                                                                       |
| ----- | ---------------------------------------------------------------------------- |
| `200` | `{ ok: true, installedVersion: "x.y.z", path: "..." }`                       |
| `400` | So‘rov tanasi noto‘g‘ri (Zod validatsiyasi muvaffaqiyatsiz)                  |
| `409` | O‘rnatish allaqachon bajarilmoqda (qulf band)                                |
| `500` | npm o‘rnatilishi muvaffaqiyatsiz — tushunarli xato uchun `message`ni ko‘ring |

**Izohlar:** `execFile('npm', [...])`dan foydalanadi — shell va interpolatsiya yo‘q (qatʼiy qoida #13).
EACCES xatolari tushunarli xabarlar sifatida ko‘rsatiladi.

---

#### `POST /api/services/9router/start`

9Router’ni ishga tushiradi. Agar supervisor hali ro‘yxatdan o‘tkazilmagan bo‘lsa, uni ro‘yxatdan o‘tkazadi va
keyin `supervisor.start()`ni chaqiradi. Allaqachon ishlayotgan bo‘lsa, idempotent hisoblanadi.

**So‘rov tanasi:** yo‘q

**Javoblar:**

| Holat | Tavsif                                                                  |
| ----- | ----------------------------------------------------------------------- |
| `200` | `ServiceStatus` obyekti (quyidagi sxemaga qarang)                       |
| `409` | 9Router o‘rnatilmagan (`status: "not_installed"`)                       |
| `503` | Ishga tushirish muvaffaqiyatsiz (jarayon xatosi — `lastError`ga qarang) |

**ServiceStatus sxemasi:**

```json
{
  "tool": "9router",
  "state": "running",
  "pid": 12345,
  "port": 20130,
  "health": "healthy",
  "startedAt": "2026-05-25T10:00:00.000Z",
  "lastError": null
}
```

---

#### `POST /api/services/9router/stop`

9Router’ni xavfsiz tarzda to‘xtatadi. SIGTERM yuboradi, 15 soniya kutadi, so‘ng jarayon hali ham ishlayotgan bo‘lsa, SIGKILL yuboradi.
Allaqachon to‘xtatilgan bo‘lsa, idempotent hisoblanadi.

**So‘rov tanasi:** yo‘q

**Javoblar:**

| Holat | Tavsif                                         |
| ----- | ---------------------------------------------- |
| `200` | `ServiceStatus` (state: "stopped")             |
| `503` | To‘xtatish kutilmaganda muvaffaqiyatsiz bo‘ldi |

---

#### `POST /api/services/9router/restart`

Amaliyot qulfi ostida `stop()` va undan keyin `start()` bajarilishiga teng.

**So‘rov tanasi:** yo‘q

**Javoblar:** `start` bilan bir xil (yakuniy `ServiceStatus`ni qaytaradi).

---

#### `POST /api/services/9router/update`

9Router’ni yangiroq npm versiyasiga yangilaydi. Agar xizmat ishlayotgan bo‘lsa, avval u
to‘xtatiladi, npm install ishga tushiriladi (yangiroq versiya mavjud joyga o‘rnatiladi), keyin esa

### 4.7 Teskari proksi (9Router boshqaruv panelini joylashtirish)

Boshqaruv paneli 9Router veb interfeysini iframe ichiga quyidagi manzildagi ichki teskari proksi orqali joylashtiradi:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

Bu proksi:

- Soʻrovni `http://127.0.0.1:{port}/{path}` manziliga yoʻnaltiradi (faqat loopback)
- Kiruvchi `cookie` va `authorization` sarlavhalarini olib tashlaydi (OmniRoute sessiyasi sizib chiqmaydi)
- 9Router autentifikatsiyasi uchun `Authorization: Bearer {apiKey}` sarlavhasini kiritadi
- Javobdan `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*` sarlavhalarini olib tashlaydi
- `<base href>` elementini kiritish va mutlaq yoʻllarni normallashtirish uchun HTML javoblarini qayta yozadi (`/foo` → `/dashboard/.../embed/foo`)

Joylashtirilgan boshqaruv paneli uchun WebSocket yangilanishlari alohida portdagi yordamchi server tomonidan boshqariladi (`src/lib/services/embedWsProxy.ts` fayliga qarang).

**Xavfsizlik:** Joylashtirish proksi marshrutlari `LOCAL_ONLY_API_PREFIXES` tarkibida tasniflangan va ularga faqat loopback orqali kirish mumkin. Cloudflare/Ngrok tunneli orqali JWT olgan hujumchi joylashtirilgan xizmatlarga proksi orqali kira olmaydi.

## 5. Xavfsizlik

### LOCAL_ONLY talabi (qatʼiy qoida #17)

`/api/services/` va `/dashboard/providers/services/*/embed/` ostidagi barcha yoʻnalishlar
`src/server/authz/routeGuard.ts` faylida LOCAL_ONLY sifatida tasniflangan. Loopback tekshiruvi
har qanday autentifikatsiya tarmogʻidan oldin, shartsiz bajariladi:

```
soʻrov keladi
  → isLocalOnlyPath(path)?
      → loopback emas → 403 LOCAL_ONLY (har doim, autentifikatsiya tekshiruvidan oldin)
      → loopback      → odatiy autentifikatsiyaga oʻtish
```

Bu sizib chiqqan JWT (masalan, tunnel orqali) `npm install` ishga tushirishi yoki
jarayon yaratishining oldini oladi. Toʻliq darajalar matritsasi uchun
`docs/security/ROUTE_GUARD_TIERS.md` fayliga qarang.

### API kalitini kiritish

9Router va Mux oʻz HTTP soʻnggi nuqtalari uchun API kaliti/bearer tokenini talab qiladi.
OmniRoute:

1. Xizmatga xos prefiks (`nr_` — 9Router uchun, `mx_` — Mux uchun) bilan
   `crypto.randomBytes(32).toString("base64url")` orqali kalit yaratadi.
2. Uni AES-256-GCM yordamida saqlash vaqtida shifrlaydi (provayder hisob maʼlumotlari
   uchun ishlatiladigan ayni shifr).
3. Jarayonni ishga tushirish vaqtida uni deshifrlaydi va muhit oʻzgaruvchisi sifatida
   kiritadi — 9Router uchun `NINEROUTER_API_KEY`, Mux uchun `MUX_SERVER_AUTH_TOKEN`
   (hech qachon CLI bayrogʻi sifatida emas, shuning uchun token `ps`/jarayon
   roʻyxatlarida hech qachon koʻrinmaydi).
4. Hech qanday HTTP javobida ochiq matndagi kalitni qaytarmaydi.

CLIProxyAPI ishga tushirish vaqtida kiritiladigan maxsus maʼlumotlar tekisligi kalitini
oladi (`needsApiKey: true` — adapterga nisbatan model sinxronizatsiyasi uchun ishlatiladi).

### SSRF himoyasi

Teskari HTTP proksi (`/dashboard/.../embed/[...path]`) soʻrovlarni faqat
`http://127.0.0.1:{port}` manziliga yoʻnaltirish uchun qatʼiy sozlangan. U loopback
boʻlmagan manzillarga qayta yoʻnaltirishlarni hech qachon kuzatmaydi.
`ssrf-req-filter` kutubxonasi loopback diapazonidan tashqaridagi manzilga aniqlanadigan
har qanday yuqori oqim URL manzilini rad etish uchun ishlatiladi.

### Shell xavfsizligi (qatʼiy qoida #13)

`npm install` `execFile('npm', ['install', pkg, '--prefix', dir])` orqali chaqiriladi —
shablon literallari, shell va tashqi yoʻllarni buyruq satriga interpolatsiya qilish
ishlatilmaydi. Ishlash vaqti qiymatlari (portlar, API kalitlari) bola jarayonning `env`
obyekti orqali uzatiladi.

### Xatolarni zararsizlantirish (qatʼiy qoida #12)

`/api/services/*` dan qaytariladigan barcha xato javoblari `buildErrorBody()` yoki
`sanitizeErrorMessage()` orqali oʻtadi. Xom `err.stack` va `err.message` hech qachon
chaqiruvchiga aynan qaytarilmaydi.

#### Ulanadigan provayder plagini shartnomasi (1-bosqich, #7333)

`src/lib/services/providerPlugins/` bir xil backend shaklini oʻzaro bogʻliq boʻlmagan
ikkita alohida faylda ifodalash oʻrniga, backendning `bootstrap.ts` dagi `ServiceEntry`
maydonlari va `serviceBackends.ts` dagi manifest-shablon maydonlarini bitta obyektga
birlashtiruvchi `ServiceProviderPlugin` shartnomasini taqdim etadi. Ushbu matn yozilgan
paytda **faqat `9router` koʻchirilgan** — `bootstrap.ts` oʻzining `SERVICES[]` yozuvini
`getServiceProviderPlugin("9router")` (`src/lib/services/providerPlugins/registry.ts`)
orqali hosil qiladi va plagin yoʻq boʻlsa, ishga tushirish xatosini chiqaradi. `cliproxy`,
`mux` va `bifrost` avvaldan mavjud ichki `SERVICES[]` literallarida oʻzgarishsiz qoladi.

`open-sse/config/providerPluginManifest.ts` shuningdek
`SERVICE_BACKEND_MANIFEST_TEMPLATE` yozuvidan toʻgʻri shakllangan
`ProviderPluginManifestEntry` yaratadigan qoʻshimcha
`createServiceBackendManifestEntry(pluginId, template)` yordamchi funksiyasiga ega
boʻldi — u hozircha hech qanday faol soʻrov yoʻliga ulanmagan
(`generateProviderPluginManifestFromRegistry()` ham, `/v1/providers/[provider]/models`
ham emas); shartnoma ikkinchi backend uchun isbotlangach, bu keyingi ish sifatida qoladi.

Keyingi PRlarga qoldirilgan va #7333 muammosi doirasida kuzatiladigan ishlar:
`cliproxyapi` ni xuddi shu reyestr orqali koʻchirish, `mux`/`bifrost` ni
`ServiceBackendPluginId` birlashmasiga umumlashtirish, bajaruvchi yoʻnaltirishining
maxsus holatlarini (`open-sse/executors/index.ts`,
`open-sse/handlers/chatCore/executorProxy.ts`) plagin shartnomasiga kiritish va
`createServiceBackendManifestEntry()` ni faol manifest/modellar kod yoʻliga ulash.

### 7-qadam — Provayder yozuvini qoʻshish (agar xizmat marshrutlash nishoni boʻlsa)

Agar ichki xizmat OpenAI bilan mos keluvchi `/v1/chat/completions` endpointini taqdim etsa:

1. `src/shared/constants/providers.ts` fayliga `isEmbeddedService: true` xususiyatiga ega provayder yozuvini qoʻshing.
2. `BaseExecutor`dan kengaytirilgan `open-sse/executors/{name}.ts` faylini yarating. Har bir soʻrovda port va
   API kalitini qayta aniqlang (ularni konstruktorda hech qachon keshlamang). Nazoratchi holati `"running"`
   boʻlmasa, `503 service_not_running` javobini qaytaring.
3. Modellarni `open-sse/config/providerRegistry.ts` faylida xizmat prefiksi bilan
   (masalan, `myservice/sub/model`) roʻyxatdan oʻtkazing. `modelSync.ts` ularni yangilab turadi.

### 8-qadam — Hujjatlashtirish va sinovdan oʻtkazish

1. `docs/frameworks/EMBEDDED-SERVICES.md` faylini (ushbu faylni) yangilang — xizmatni
   §1 dagi jadvalga, yangi endpointlarni esa §4 ga qoʻshing.
2. `tests/unit/services/` ichiga modul testlarini qoʻshing (hayotiy sikl, oʻrnatuvchi, API shakli).
3. `tests/integration/services/` ichiga integratsion test qoʻshing (`RUN_SERVICES_INT=1` orqali yoqiladi).
4. `docs/openapi.yaml` faylini yangi endpointlar bilan yangilang.

## 7. Muammolarni bartaraf etish

### Xizmat ishga tushmaydi

**Alomatlar:** Ishga tushirish tugmasi 503 kodini qaytaradi, holat `"error"` yoki `"starting"` bo‘lib qoladi.

**Tekshiruv ro‘yxati:**

1. `GET /api/services/{name}/logs` so‘rovini (yoki boshqaruv panelidagi Logs panelini) tekshiring. `Error: ENOENT`, `address already in use` yoki `Cannot find module` kabi
   qatorlarni qidiring.
2. `npm` PATH ichida ekanini tekshiring: OmniRoute’ni ishga tushiradigan o‘sha foydalanuvchi hisobidan `which npm` buyrug‘ini bajaring.
3. Xizmat o‘rnatilganini tekshiring: `installedVersion` qiymatini ko‘rish uchun
   `GET /api/services/{name}/status` so‘rovini tekshiring. Agar u `null` bo‘lsa, avval o‘rnatishni ishga tushiring.
4. `DATA_DIR/services/{name}/node_modules/` mavjudligini va bo‘sh emasligini tekshiring.
5. Tozalangan chiqish sababini bilish uchun holat javobidagi `lastError` maydonini tekshiring.

---

### Sovuq ishga tushirish sekin (`running` holatiga yetish > 10 s)

**Alomatlar:** Holat `"running"` yoki `"error"` holatiga o‘tishdan oldin uzoq vaqt `"starting"` bo‘lib qoladi.

**Izoh:** 9Router’ning sovuq ishga tushirilishi katta bog‘liqlik daraxtlarini (DNS,
tunnel, MITM modullarini) import qilishni o‘z ichiga oladi. Standart sog‘lomlik tekshiruvi oralig‘i 2 s bo‘lib, nazoratchi vaqt tugaganini e’lon qilishidan oldin 3 marta urinadi (ammo so‘rovlarni davom ettiradi).

**Yechim:** `healthIntervalMs` va `waitForHealthy` kutish vaqti
(`healthIntervalMs * 3`) `bootstrap.ts` ichida sozlanadi. Ishga tushishi uzoqroq davom etadigan xizmatlar uchun `healthIntervalMs` qiymatini 5000 ga va `stopTimeoutMs` qiymatini 30 000 ga oshiring.

---

### Port to‘qnashuvi (`EADDRINUSE`)

**Alomatlar:** Jurnallarda `address already in use :::20130` ko‘rsatiladi.

**Sabablar:**

- Boshqa jarayon allaqachon 20130 portidan foydalanmoqda.
- Avvalgi 9Router jarayoni to‘liq to‘xtatilmagan (zombi PID).

**Yechim:**

1. `.env` ichidagi `NINEROUTER_PORT` muhit o‘zgaruvchisi orqali standart portni o‘zgartiring.
2. To‘qnashayotgan jarayonni toping va to‘xtating: `lsof -ti :20130 | xargs kill -9`.
3. Port har bir xizmat uchun `bootstrap.ts` ichidagi `port` maydoni orqali sozlanadi.

**Eslatma:** 9Router OmniRoute’ning standart 20128 porti bilan to‘qnashuvni oldini olish uchun aynan 20130 portidan foydalanadi.

---

### O‘rnatishda ruxsat rad etildi (EACCES)

**Alomatlar:** O‘rnatish 500 kodini qaytaradi, jurnallarda `EACCES` yoki `permission denied` ko‘rsatiladi.

**Sabablar:**

- OmniRoute jarayoni `DATA_DIR` yoki uning ota katalogiga yoza olmaydi.
- Docker ichida rootless rejimida, ulangan jildga yozish huquqisiz ishlatilmoqda.

**Yechim:**

1. `DATA_DIR` katalogini tekshiring (standart: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. Katalog OmniRoute jarayoni foydalanuvchisiga tegishli ekanini ta’minlang: `chown -R $USER ~/.omniroute/`
3. Docker’da jild ulanishi konteyner foydalanuvchisi uchun to‘g‘ri ruxsatlarga ega ekanini ta’minlang.

---

### Yangilash muvaffaqiyatsiz (`npm install` kutish vaqti tugashi yoki tarmoq xatosi)

**Alomatlar:** Yangilash `InstallError` bilan 500 kodini qaytaradi, jurnallarda tarmoq kutish vaqti tugagani ko‘rsatiladi.

**Tekshiruv ro‘yxati:**

1. npm reyestriga ulanish mumkinligini tasdiqlang: `npm ping`.
2. Korporativ proksi mavjudligini tekshiring: `npm config get proxy`, `npm config get https-proxy`.
3. O‘rnatishni qo‘lda sinab ko‘ring: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`.
4. Agar tarmoqdan uzilgan muhitda bo‘lsangiz, tarball faylini oldindan yuklab oling va `npm install /path/to/tarball.tgz` buyrug‘idan foydalaning.

---

### Xizmat ishga tushirilgandan so‘ng darhol `"error"` holatini ko‘rsatadi (tezkor nosozlik)

**Alomatlar:** Holat 5 soniyadan kamroq vaqt ichida `"starting"` holatidan `"error"` holatiga o‘tadi.
`lastError` maydonida `"Fast crash (exited with code 1)"` ko‘rsatiladi.

**Tekshiruv ro‘yxati:**

1. Jurnalning to‘liq oxirgi qismini o‘qing: `GET /api/services/{name}/logs?tail=500`.
2. Keng tarqalgan sabab: xizmat kutayotgan muhit o‘zgaruvchilarining mavjud emasligi.
3. 9Router uchun: `NINEROUTER_DISABLE_MITM=true` va
   `NINEROUTER_DISABLE_TUNNEL=true` jarayonni yaratishda uzatiladigan muhit tarkibida ekanini tekshiring (`installers/ninerouter.ts` ichidagi `resolveSpawnArgs` bo‘limiga qarang).

## 8. Koʻp soʻraladigan savollar

**Savol: Oʻrnatilgan xizmatlarning endpointlarini loopback boʻlmagan mijozlarga ochishim mumkinmi?**

Yoʻq. LOCAL_ONLY darajasi ataylab shunday belgilangan (qatʼiy qoida #17). `npm install` buyrugʻini ishga tushirishi yoki `node` jarayonlarini yaratishi mumkin boʻlgan marshrutlar loopback boʻlmagan trafikdan ochiq boʻlmasligi kerak, chunki tunnel (Cloudflare, Ngrok, Tailscale) orqali JWT sizib chiqsa, aks holda bu ixtiyoriy jarayonlarni yaratish imkonini beradi. `/api/services/` uchun istisno tariqasida voz kechish imkoniyati yoʻq — `/api/mcp/` dan farqli ravishda, u manage-scope chetlab oʻtish roʻyxatiga kiritilmagan. `docs/security/ROUTE_GUARD_TIERS.md` fayliga qarang.

---

**Savol: 9Router va CLIProxyAPI production/bulut muhitlarida mavjud boʻladimi?**

Ha. Har ikkala xizmat ham OmniRoute kabi bir xil local-first modeliga amal qiladi. Ular ayni bir mashinada ishlaydi va loopback orqali aloqa qiladi. Bu yerda "Production" masofaviy bulut provayderini emas, balki OmniRoute joylashtirilgan VPS yoki mahalliy serverni anglatadi.

---

**Savol: Supervisorʼni qanday disk raskadrovka qilishim mumkin?**

1. SSE jurnal oqimining oxirgi qismini kuzating: `curl -N http://localhost:20128/api/services/9router/logs`.
2. OmniRouteʼning pino chiqishidagi `service:supervisor` namespace boʻyicha filtrlangan tuzilmaviy jurnallarni tekshiring.
3. DB qatorini tekshiring: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`.
4. Joriy real vaqtdagi holat, PID, xizmat salomatligi va `lastError` qiymatini bitta soʻrovda koʻrish uchun `GET /api/services/9router/status` dan foydalaning.

---

**Savol: Supervisor `health: "degraded"` yoki `health: "unknown"` ni koʻrsatmoqda, ammo holat `"running"`. Bu muammomi?**

`"degraded"` salomatlik tekshiruvi 200 dan boshqa javob qaytarganini anglatadi. `"unknown"` hali hech qanday tekshiruv yakunlanmaganini anglatadi (birinchi soʻrov bilan poyga holati). Ishga tushirish vaqtida har ikkala holat ham vaqtinchalikdir. Agar `"running"` holatidan keyin salomatlik `healthIntervalMs * 3` ms dan koʻproq vaqt davomida `"degraded"` boʻlib qolsa, oʻrnatilgan xizmat ishlayotgan, ammo uning HTTP APIʼsi javob bermayotgan boʻladi. Holat javobidagi port toʻgʻri ekanini va xizmat haqiqatda shu portni tinglayotganini tekshiring.

---

**Savol: 9Router API kalitini toʻliq qayta ishga tushirmasdan oʻzgartirishim mumkinmi?**

Yoʻq. API kaliti jarayon yaratilayotgan vaqtda muhit oʻzgaruvchisi orqali 9Routerʼga uzatiladi. Ishlayotgan jarayonda muhit oʻzgaruvchilarini oʻzgartirib boʻlmaydi. `POST .../rotate-key` yangi kalitni qoʻllash uchun xizmatni avtomatik ravishda toʻxtatadi va qayta ishga tushiradi. Kalitni almashtirish xizmatning `stopTimeoutMs` muddati (standart qiymati 15 s) va uning ishga tushish vaqti yigʻindisi ichida kuchga kiradi.

---

**Savol: Halqali bufer cheklovi qancha va u toʻlganda nima sodir boʻladi?**

Har bir xizmat uchun alohida 5 MB hajmli halqali bufer mavjud. Bufer toʻlganda, yangi qatorlar uchun joy boʻshatish maqsadida eng eski jurnal qatorlari chiqarib tashlanadi. SSE `snapshot` hodisasi `tail` chegarasi doirasidagi eng soʻnggi qatorlarni qaytaradi. DB qatorida `logsBufferPath` belgilanmagan boʻlsa, jurnallar diskda saqlanmaydi.
