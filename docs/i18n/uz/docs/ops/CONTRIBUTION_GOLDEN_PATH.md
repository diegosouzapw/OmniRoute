Pull request uchun eng kichik ishonchli ishlab chiqish siklini tanlashda ushbu qoʻllanmadan foydalaning. U
quyida havola qilingan muayyan sohaga oid arxitektura va xavfsizlik hujjatlarini almashtirmaydi; u har bir keng tarqalgan
oʻzgartirish turini uning shartnomalari, yoʻnaltirilgan tekshiruvlari va CI qamrovi bilan bogʻlaydi.

## Har bir oʻzgartirish oʻtadigan yoʻl

1. **Tahrirlashdan oldin asosiy branchni tanlang.** Eng yuqori faol `release/v*` branchini toping va
   uning eng soʻnggi holatidan yangi branch yarating. `main`ni emas, oʻsha branchni nishon sifatida belgilang. Agar relizni muzlatish amal qilayotgan boʻlsa, muzlatilgan
   branchni nishon sifatida belgilamang; [Branch yaratish va reliz modeli](BRANCHING_MODEL.md)da
   tavsiflangan keyingi faol sikldan foydalaning.
2. **Shartnomalarni sanab chiqing.** Oʻzgartirish taʼsir qiladigan har bir katalog, sxema, generatsiya qilingan artefakt, ommaviy API yoki foydalanuvchi
   interfeysini aniqlang. Quyidagi jadval minimal boshlangʻich toʻplamni beradi.
3. **Yoʻnaltirilgan testlarni yozing yoki yangilang.** `src/`, `open-sse/`, `electron/` yoki
   `bin/` ichidagi ishlab chiqarish oʻzgarishlari ayni PRda avtomatlashtirilgan testni talab qiladi. Xatti-harakatni
   tasdiqlaydigan eng kichik test fayllarini, soʻng sanab oʻtilgan yoʻnaltirilgan tekshiruvlarni ishga tushiring.
4. **Keng matritsani CI ishga tushirsin.** Toʻliq unit shardlar, Vitest, qamrov ratcheti va
   ishlab chiqarish buildi PRda ishga tushadi. Keng toʻplamni lokal ravishda faqat yoʻnaltirilgan nosozlik
   kengroq taʼsirni koʻrsatsa yoki oʻzgartirish bir nechta quyi tizimni qamrab olsa ishga tushiring.
5. **Koʻrib chiqishdan oldin muvofiqlashtiring.** Faol asosiy branchni fetch qiling, uning yangi commitlarini va unga nisbatan
   diffingizni tekshiring, soʻng hissa qoʻshuvchi ish jarayoniga muvofiq asosiy branchni rebase yoki merge qiling. Generatsiya qilingan fayl
   va katalog ziddiyatlarini ularning manbasida hal qiling, ularni qayta generatsiya qiling, yoʻnaltirilgan siklni qayta ishga tushiring va
   PR hali ham faol reliz branchini nishonlayotganini tasdiqlang.
6. **Dalillarni qayd eting.** PR shablonida ishga tushirilgan buyruqlarni, qoʻshilgan yoki oʻzgartirilgan har bir test faylini,
   migratsiyalar yoki feature flaglarni hamda hali bajarilishi kutilayotgan faqat CIga oid tekshiruvlarni sanab oʻting.

## Oʻzgartirish turi boʻyicha tavsiya etilgan yoʻllar

Quyidagi buyruqlar minimal yoʻnaltirilgan tekshiruvlardir, ular siz oʻzgartirgan xatti-harakatni bevosita qamrab oluvchi
testni oʻtkazib yuborishga ruxsat bermaydi.

### Provayder

**Shartnomalar**

- `src/shared/constants/providers/` ichidagi provayder taʼrifi va uning
  `src/shared/constants/providers.ts` ichidagi kompozitsiyasi.
- `open-sse/config/providerRegistry.ts` yoki undan ajratib olingan reyestr fayllaridagi modellar va imkoniyatlar.
- Tegishli boʻlganda executor/translator tanlovi, OAuth yoki API kaliti konfiguratsiyasi, dashboard resurslari va generatsiya qilingan
  provayder maʼlumotnomasi.
- Ommaviy hisob maʼlumotlari `resolvePublicCred()`dan foydalanishi kerak; xato javoblari umumiy sanitarizatsiya qilingan
  xato yordamchi funksiyalaridan foydalanishi kerak. `docs/security/PUBLIC_CREDS.md` (gitda mavjud; `/docs` ichiga kompilyatsiya qilinmaydi) va
  [Xatolarni sanitarizatsiya qilish](../security/ERROR_SANITIZATION.md)ga qarang.

**Yoʻnaltirilgan sikl**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # katalog oʻzgarganda; generatsiya qilingan diffni commit qiling
npm run lint
```

Shuningdek, taʼsirlangan har bir soʻrov oilasini sinang: chat, Responses, tasvirlar, embeddinglar, audio yoki video.
Generatsiya qilingan katalog va etalon diffalarni shartnoma oʻzgarishlari sifatida koʻrib chiqing; ularni koʻr-koʻrona qabul qilmang.

### Marshrutlash

**Shartnomalar**

- `src/shared/constants/routingStrategies.ts` ichidagi ommaviy strategiya qiymatlari va UI metamaʼlumotlari.
- `open-sse/services/combo.ts` va `open-sse/services/combo/` ostidagi dispatch va tartiblash.
- Combo sxemalari, saqlash, chidamlilik holati, model imkoniyatlari va API/UI boshqaruv elementlari.
- Xatti-harakat oʻzgarganda [Auto-Combo mexanizmi](../routing/AUTO-COMBO.md) va chidamlilik hujjatlari.

**Yoʻnaltirilgan sikl**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategiya yoki dispatch oʻzgarishlari
npm run check:known-symbols      # strategiyani roʻyxatdan oʻtkazish oʻzgarishlari
npm run lint
```

Lokal ravishda deterministik, soxta upstream testlaridan foydalaning. Jonli combo smoke testlari hisob maʼlumotlarini talab qiladi va
qoʻlda bajariladi, ular CI oʻrnini bosmaydi.

### UI / UX

**Shartnomalar**

- `src/app/` va `src/shared/components/` ostidagi Next.js route/page hamda umumiy komponent
  chegaralari.
- API javob shakllari, yuklanish/boʻsh/xato holatlari, klaviatura va ekran oʻqigich xatti-harakati,
  moslashuvchan maket, mavzular va lokal kengayishi.
- `src/i18n/messages/en.json` ichidagi inglizcha UI manba satrlari; foydalanuvchiga koʻrinadigan yangi matnni kod ichiga toʻgʻridan-toʻgʻri yozmang.

**Yoʻnaltirilgan sikl**


Interaksiya yoki vizual oʻzgarishlar uchun ilovani ishga tushiring va tor hamda keng viewportlarni tekshiring. CI
ishlab chiqarish buildi va kengroq toʻplamlarni ishga tushiradi; vizual xatti-harakat baribir oʻzgarishga mos
yoʻnaltirilgan komponent, Playwright yoki hujjatlashtirilgan qoʻlda tekshiruvni talab qiladi.

### i18n

**Shartnomalar**

- `src/i18n/messages/en.json` — UI manbasi; `config/i18n.json` — lokallar manbasi.
- CLI kataloglari `bin/cli/locales/` ostida alohida joylashgan.

  `scripts/i18n/glossary/protected-terms.json`.

Almashtiruvchi tizim loyihalanayotgan vaqtda i18n patchlarini aniq va kichik saqlang. Vazifa generatsiya qilingan tarjimalarni aniq talab qilmasa va

Xatti-harakat tahlil qilish, fayllar yoki chiqish holatiga bog‘liq bo‘lsa, aniq buyruqni vaqtinchalik ma’lumotlar katalogida ishlating. CI paket artefaktlari va ekotizimga oid kengroq tekshiruvlarni bajaradi.

**Shartnomalar**

- Ildiz va ish maydoni manifestlari/bloklash fayli, `scripts/build/`, Next.js mustaqil yig‘masi, `dist/`

## Mahalliy nomzod sikli

Manba testlari paketlangan artefakt ishga tushishini isbotlay olmaydi: paketlash roʻyxatlari, qisqartirilgan bogʻliqliklar
va mahalliy ikkilik fayllardagi xatolar faqat tarball oʻrnatilib, ishga tushirilgandan keyin yuzaga chiqadi. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) — RFC #8084 dagi bir marta qurish / tekshirish / ilgari surish jarayonining mahalliy
qismi: u bitta nomzodni quradi, aynan shu artefaktni tekshiradi, kataloglar nomini oʻzgartirish orqali uni
ilgari suradi va ilgari surilgan slotning ishlash holati tekshiruvi muvaffaqiyatsiz tugasa, uni ortga qaytaradi.

```bash
npm run dev:candidate -- run --dry-run --json  # rejani chiqarish, hech narsani o‘zgartirmaslik
npm run dev:candidate -- run                   # qurish + tekshirish + ilgari surish, avtomatik ortga qaytarish
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ ichiga o‘rnatish
npm run dev:candidate -- validate --id <id>    # bo‘sh portda ishga tushirish, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current va previous o‘rnini almashtirish
npm run dev:candidate -- run --from-tarball <file.tgz>  # boshqa joyda (CI) qurilgan tarball faylidan qayta foydalanish
```

- **Bir marta quring.** `build` joriy daraxtni paketlaydi (unga `dist/server.js` kerak, shuning uchun avval
  `npm run build:release` ni ishga tushiring) yoki `--from-tarball` orqali berilgan faylni nusxalaydi, soʻng tarball faylini
  izolyatsiyalangan npm prefiksiga oʻrnatadi, chunki tarball tarkibida `node_modules` mavjud emas. Identifikator — qisqa `HEAD`
  sha (daraxtda mahalliy oʻzgarishlar boʻlsa, `-dirty`) yoki tarball uchun `tgz-<sha256>`. Allaqachon qurilgan toza identifikator
  qayta qurish oʻrniga qayta ishlatiladi; uni qayta qurish uchun `--force` parametrini bering.
- **Manbani emas, paketni tekshiring.** `validate` oʻrnatilgan CLIʼni
  (`serve --port <free port>`) yangi `DATA_DIR=<candidate>/data`, soxta maxfiy qiymatlar bilan hamda operatorning
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` va `INITIAL_PASSWORD` qiymatlarini muhitdan olib tashlagan holda
  ishga tushiradi va shu orqali yangi oʻrnatmaning kalitsiz loopback holatini tekshiradi. U
  `GET /api/health` soʻrovi 200 qaytarishini kutadi, `GET /v1/models` soʻrovi 200 qaytarishini talab qiladi, jarayonlar guruhini
  toʻxtatadi va natijani tarball xeshi bilan birga `validation.json` fayliga yozadi.
- **Aynan shu artefaktni ilgari suring.** `promote` joriy tarball xeshi uchun muvaffaqiyatli tekshiruvga ega boʻlmagan
  nomzodni rad etadi. Standart faol slot — `_artifacts/candidate/current`; `--target <dir>`
  ayni fayl tizimidagi boshqa katalogni tanlaydi, uning oldingi sloti esa `<dir>.previous` boʻladi.
  Har bir nom oʻzgartirish atomar bajariladi; jarayonning oʻrtasida xatolik yuz bersa, allaqachon bajarilgan nom
  oʻzgartirishlar ortga qaytariladi.
- **Ortga qaytaring.** `run` ilgari surilgan slotni yana tekshiradi va ushbu tekshiruv muvaffaqiyatsiz tugasa,
  `current` hamda `previous` joylarini qayta almashtiradi. Birinchi tekshiruvdan oʻta olmagan nomzod hech qachon
  ilgari surilmaydi.

Barcha maʼlumotlar git tomonidan eʼtiborsiz qoldiriladigan `_artifacts/candidate/` ichiga yoziladi; mavjud OmniRoute
oʻrnatmasi va uning maʼlumotlar katalogiga hech qachon tegilmaydi. Ilgari surilgan CLI:
`_artifacts/candidate/current/prefix/bin/omniroute`; undan foydalanganda uni oʻzingizning `DATA_DIR` qiymatingiz bilan
ishga tushiring. Chiqish kodlari: `0` — muvaffaqiyat, `1` — muvaffaqiyatsiz tekshiruv yoki ilgari surish, `2` — foydalanish xatosi yoki qurilma mavjud emas.

Muvaffaqiyatli maqsadli sikl — oʻzgartirilgan shartnoma haqidagi dalil, biroq aloqador boʻlmagan CI tekshiruvlari
muvaffaqiyatli oʻtishining isboti emas. Aksincha, har bir mahalliy tahrirni repozitoriyning toʻliq matritsasi yakunlanishini kutishga majbur qilmang.

## Muvofiqlashtirish nazorat roʻyxati

Koʻrib chiqishni soʻrashdan oldin:

- PR bazasi hali ham eng yuqori faol `release/v*` branch ekanini tasdiqlang.
- Shu bazani fetch qiling va branch yaratganingizdan beri qoʻshilgan commitlarni koʻrib chiqing.
- Tasodifiy yoki generatsiya qilingan ortiqcha oʻzgarishlarni aniqlash uchun `git diff <active-base>...HEAD` natijasini koʻrib chiqing.
- Katalog va generatsiya qilingan hujjatlardagi ziddiyatlarni manbani yangilash va natijani qayta generatsiya qilish orqali hal qiling.
- Muvofiqlashtirishdan soʻng PR tavsifida keltirilgan har bir maqsadli test/nazoratni qayta ishga tushiring.
- Oʻzgargan bazaga moslashish uchungina tasdiqlarni hech qachon zaiflashtirmang yoki talab qilinadigan testlarni olib tashlamang.

Relizni muzlatish va nishonni oʻzgartirish qoidalari uchun
[Branchlash va reliz modeli](BRANCHING_MODEL.md)dan foydalaning. Toʻliq CI roʻyxati uchun
[Sifat nazoratlari maʼlumotnomasi](../architecture/QUALITY_GATES.md)dan foydalaning.
