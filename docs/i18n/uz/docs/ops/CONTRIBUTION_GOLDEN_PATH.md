Har bir pull request uchun eng kichik ishonchli ishlab chiqish siklini tanlashda ushbu qoʻllanmadan foydalaning. U quyida havola qilingan muayyan sohaga oid arxitektura va xavfsizlik hujjatlarini
almashtirmaydi; u har bir keng tarqalgan oʻzgartirish turini uning shartnomalari, yoʻnaltirilgan
tekshiruvlari va CI qamrovi bilan bogʻlaydi.

## Har bir oʻzgartirish oʻtadigan yoʻl

1. **Tahrirlashdan oldin asosiy shoxobchani tanlang.** Eng yuqori faol `release/v*` shoxobchasini toping va
   uning uchidan yangi shoxobcha yarating. `main` emas, shu shoxobchani maqsad qilib belgilang. Agar relizni muzlatish davri faol boʻlsa, muzlatilgan
   shoxobchani maqsad qilib belgilamang; [Shoxobchalash va reliz modeli](BRANCHING_MODEL.md) hujjatida
   tavsiflangan keyingi faol sikldan foydalaning.
2. **Shartnomalarni sanab oʻting.** Oʻzgartirish taʼsir qiladigan har bir katalog, sxema, yaratilgan artefakt, ommaviy API yoki foydalanuvchi
   interfeysini aniqlang. Quyidagi jadval minimal boshlangʻich toʻplamni koʻrsatadi.
3. **Yoʻnaltirilgan testlarni yozing yoki yangilang.** `src/`, `open-sse/`, `electron/` yoki
   `bin/` ichidagi ishlab chiqarish kodiga kiritilgan oʻzgartirishlar ayni PR ichida avtomatlashtirilgan testni talab qiladi. Xatti-harakatni
   tasdiqlaydigan eng kichik test fayllarini, soʻngra sanab oʻtilgan yoʻnaltirilgan tekshiruvlarni ishga tushiring.
4. **Keng matritsani CI ishga tushirsin.** Toʻliq unit-test segmentlari, Vitest, qamrovni bosqichma-bosqich oshirish tekshiruvi va
   ishlab chiqarish buildi PR doirasida ishga tushadi. Keng testlar toʻplamini mahalliy muhitda faqat yoʻnaltirilgan tekshiruvdagi xato
   taʼsir doirasi kengroq ekanini koʻrsatsa yoki oʻzgartirish bir nechta quyi tizimni qamrab olsa ishga tushiring.
5. **Koʻrib chiqishdan oldin muvofiqlashtiring.** Faol asosiy shoxobchani yuklab oling, undagi yangi commitlarni va unga nisbatan oʻz diffingizni
   tekshiring, soʻng hissa qoʻshuvchi ish jarayoniga muvofiq asosiy shoxobchani rebase yoki merge qiling. Yaratilgan fayllar
   va kataloglardagi ziddiyatlarni ularning manbasida hal qiling, ularni qayta yarating, yoʻnaltirilgan siklni qayta ishga tushiring va
   PR hali ham faol reliz shoxobchasiga yoʻnaltirilganini tasdiqlang.
6. **Dalillarni qayd eting.** PR shablonida ishga tushirilgan buyruqlarni, qoʻshilgan yoki oʻzgartirilgan har bir test faylini,
   migratsiyalar yoki feature flaglarni hamda faqat CI orqali bajariladigan, hali kutilayotgan tekshiruvlarni sanab oʻting.

## Oʻzgartirish turi boʻyicha tavsiya etilgan yoʻllar

Quyidagi buyruqlar minimal yoʻnaltirilgan tekshiruvlardir; ular siz oʻzgartirgan xatti-harakatni bevosita
qamrab oluvchi testni oʻtkazib yuborishga ruxsat bermaydi.

### Provayder

**Shartnomalar**

- `src/shared/constants/providers/` ichidagi provayder taʼrifi va uning
  `src/shared/constants/providers.ts` ichidagi kompozitsiyasi.
- `open-sse/config/providerRegistry.ts` yoki undan ajratib olingan registr fayllaridagi modellar va imkoniyatlar.
- Tegishli hollarda ijrochi/tarjimon tanlovi, OAuth yoki API kaliti konfiguratsiyasi, boshqaruv paneli resurslari va yaratilgan
  provayder maʼlumotnomasi.
- Ommaviy hisob maʼlumotlari `resolvePublicCred()`dan foydalanishi kerak; xato javoblari umumiy sanitizatsiya qilingan
  xato yordamchilaridan foydalanishi kerak. `docs/security/PUBLIC_CREDS.md` (git ichida; `/docs` tarkibiga kompilyatsiya qilinmaydi) va
  [Xatolarni sanitizatsiya qilish](../security/ERROR_SANITIZATION.md) hujjatiga qarang.

**Yoʻnaltirilgan sikl**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # katalog oʻzgarganda; yaratilgan diffni commit qiling
npm run lint
```

Taʼsirlangan har bir soʻrov oilasini ham sinang: chat, Responses, tasvirlar, embeddinglar, audio yoki video.
Yaratilgan katalog va etalon difflarni shartnoma oʻzgarishlari sifatida koʻrib chiqing; ularni koʻr-koʻrona qabul qilmang.

### Marshrutlash

**Shartnomalar**

- `src/shared/constants/routingStrategies.ts` ichidagi ommaviy strategiya qiymatlari va UI metamaʼlumotlari.
- `open-sse/services/combo.ts` va `open-sse/services/combo/` ostidagi taqsimlash va tartiblash.
- Combo sxemalari, saqlash, chidamlilik holati, model imkoniyatlari hamda API/UI boshqaruv elementlari.
- Xatti-harakat oʻzgarganda [Auto-Combo mexanizmi](../routing/AUTO-COMBO.md) va chidamlilik hujjatlari.

**Yoʻnaltirilgan sikl**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategiya yoki taqsimlash oʻzgarishlari
npm run check:known-symbols      # strategiyani roʻyxatdan oʻtkazishdagi oʻzgarishlar
npm run lint
```

Mahalliy muhitda deterministik, yuqori oqim tizimi mock qilingan testlardan foydalaning. Jonli combo smoke-testlar hisob maʼlumotlarini talab qiladi va
qoʻlda bajariladi; ular CI oʻrnini bosmaydi.

### UI / UX

**Shartnomalar**

- `src/app/` va `src/shared/components/` ostidagi Next.js marshrut/sahifa hamda umumiy komponent chegaralari.
- API javob shakllari, yuklanish/boʻsh/xato holatlari, klaviatura va ekran oʻqigich xatti-harakati,
  moslashuvchan maket, mavzular va lokal kengaytmasi.
- `src/i18n/messages/en.json` ichidagi inglizcha UI manba satrlari; foydalanuvchiga koʻrinadigan yangi matnni kod ichiga qattiq yozmang.

**Yoʻnaltirilgan sikl**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaktiv yoki vizual oʻzgarishlar uchun ilovani ishga tushiring va tor hamda keng koʻrish maydonlarini tekshiring. CI
ishlab chiqarish buildini va kengroq testlar toʻplamini ishga tushiradi; vizual xatti-harakat baribir oʻzgartirishga mos
yoʻnaltirilgan komponent testi, Playwright testi yoki hujjatlashtirilgan qoʻlda tekshiruvni talab qiladi.

### i18n

**Shartnomalar**

- `src/i18n/messages/en.json` — UI manbasi; `config/i18n.json` — lokal manbasi.
- CLI kataloglari `bin/cli/locales/` ostida alohida joylashgan.
- ICU toʻldirgichlari va teglarini aynan saqlang. Mahsulot/provayder/model nomlari,
  protokol va sarlavha nomlari, buyruqlar, kod/JSON identifikatorlari, URL manzillari, muhit oʻzgaruvchilari yoki
  `OmniRoute`, `OAuth`, `MCP` va `A2A` kabi himoyalangan atamalarni tarjima qilmang. Joriy manba roʻyxati:
  `scripts/i18n/glossary/protected-terms.json`.

**Yoʻnaltirilgan sikl**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI satrlari/kataloglari oʻzgarganda
npm run lint
```

Bu mavjud tizim uchun yoʻriqnoma boʻlib, uning vositalari yoki kalit modelini kengaytirishga taklif emas.
Oʻrnini bosuvchi tizim loyihalanayotgan paytda i18n patchlarini faqat zarur joylarga kiriting. Vazifa yaratilgan tarjimalarni aniq talab qilmasa va
hosil boʻlgan diffni koʻrib chiqmagan boʻlsangiz, tashqi xizmatlarni chaqiradigan tarjima buyruqlarini ishga tushirmang.

### CLI

**Shartnomalar**

- `bin/cli/` ichidagi ommaviy buyruqlar va flaglar, yaratilgan API buyruqlari, chiqish kodlari, stdout/stderr va
  JSON chiqish shakllari, konfiguratsiya/muhit xatti-harakati hamda paketlangan fayllar.
- CLI foydalanuvchiga ko‘rinadigan satrlar CLI i18n qatlamidan foydalanishi va `en`/`pt-BR` kataloglari o‘zaro muvofiq saqlanishi kerak.
- Node’ni qo‘llab-quvvatlanadigan bajarilish muhiti sifatida va e’lon qilingan ikkilik fayl shartnomasini saqlang.

**Yo‘naltirilgan sikl**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # yaratilgan/to‘plamlangan CLI o‘zgarishlari
npm run check:pack-policy     # paket interfeysi o‘zgarishlari
npm run lint
```

Xatti-harakat tahlil qilish, fayllar yoki chiqish holatiga bog‘liq bo‘lsa, aniq buyruqni vaqtinchalik ma’lumotlar katalogida ishlating. CI kengroq paket artefakti va ekotizim tekshiruvlarini bajaradi.

### Ma’lumotlar bazasi

**Shartnomalar**

- `src/lib/db/` ichidagi domen modullari; muayyan modullarni bevosita import qiling (eski `localDb.ts` qayta eksport qatlami olib tashlangan).
- `src/lib/db/migrations/` ichidagi raqamlangan, idempotent SQL migratsiyalari, tranzaksiya xavfsizligi, yangilash
  xatti-harakati, indekslar va sxema ta’sir qiladigan har bir chaqiruvchi.
- Marshrutlar va ishlov beruvchilar hech qachon bevosita xom SQL so‘rovlarini bajarmaydi.

**Yo‘naltirilgan sikl**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migratsiya qo‘shilganda ham yangi ma’lumotlar bazasini, ham oldingi sxemadan yangilashni sinang. Ma’lumotlar bazasi testlari tozalash vaqtida ulanish deskriptorlarini yopishi va `resetDbInstance()` funksiyasini chaqirishi kerak. Faqat imkon qadar ishlaydigan Bun adapteri yo‘li o‘zgarganda `npm run test:bun:db` buyrug‘ini ishga tushiring; Node asosiy mezon bo‘lib qoladi.

### Yig‘ish / joylashtirish

**Shartnomalar**

- Ildiz va ish maydoni manifestlari/qulf fayli, `scripts/build/`, Next.js mustaqil yig‘masi, `dist/`
  paketi tarkibi, Electron platformasi metama’lumotlari, CI ish jarayonlari va joylashtirish nazorat belgilari.
- Qo‘llab-quvvatlanadigan Node diapazonlari va `CLAUDE.md` faylida ruxsat etilgan Bun ishlatilishi o‘zgarishsiz qolishi kerak.
- Yig‘ish artefaktlari kuzatuvga olinmasligi kerak; bog‘liqliklar, litsenziya, ish jarayoni va paket siyosatlari amal qiladi.

**Yo‘naltirilgan sikl**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # bog‘liqlik yoki qulf fayli o‘zgarishlari
npm run check:pack-policy      # e’lon qilingan paket interfeysi o‘zgarishlari
npm run lint
```

Faqat o‘zgarish kompilyatsiya, mustaqil yig‘ma, resurslar yoki bajarilish muhiti to‘plamlanishiga ta’sir qilganda `npm run build` buyrug‘ini lokal ravishda ishlating. `npm run build:release` buyrug‘idan faqat reliz/joylashtirishni tekshirish uchun foydalaning. CI yig‘ishi yakuniy platformalararo ko‘rsatkichdir; platformaga xos Electron o‘zgarishlari tegishli yo‘naltirilgan yig‘ish yoki smoke-test dalillarini talab qiladi.

## Lokal sikl va CI taqqoslanishi

| Har bir patch uchun lokal ravishda ishga tushiriladi                                         | CI keng qamrovli natijani taqdim etadi                                            |
| -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Yuqoridagi bevosita xatti-harakat testlari va toifa nazoratlari                              | Boʻlaklarga ajratilgan toʻliq unit-testlar toʻplami va ketma-ket testlar          |
| `npm run lint`                                                                               | Vitest test toʻplamlari va qamrov/sifat ratchet nazoratlari                       |
| Typecheck yoki build faqat taʼsirlangan kontrakt talab qilganda                              | Production build, xavfsizlik, hujjatlar, bogʻliqliklar va PR siyosati nazoratlari |
| Qoʻlda ishlash/jonli tekshiruvlar faqat avtomatlashtirish xatti-harakatni isbotlay olmaganda | Workflow tomonidan sozlangan joblararo integratsiya va platforma tekshiruvlari    |

Muvaffaqiyatli fokuslangan sikl — oʻzgartirilgan kontrakt haqidagi dalil, aloqador boʻlmagan CI tekshiruvlari
ham muvaffaqiyatli oʻtishining isboti emas. Aksincha, har bir lokal tahrirni repozitoriyning toʻliq matritsasini kutishga majbur qilmang.

## Muvofiqlashtirish nazorat roʻyxati

Koʻrib chiqishni soʻrashdan oldin:

- PR bazasi hali ham eng yuqori faol `release/v*` branch ekanini tasdiqlang.
- Ushbu bazani fetch qiling va branch yaratganingizdan beri qoʻshilgan commitlarni koʻrib chiqing.
- Tasodifiy yoki generatsiya qilingan keraksiz oʻzgarishlarni aniqlash uchun `git diff <active-base>...HEAD` natijasini koʻrib chiqing.
- Katalog va generatsiya qilingan hujjatlardagi ziddiyatlarni manbani yangilash va natijani qayta generatsiya qilish orqali hal qiling.
- Muvofiqlashtirishdan keyin PR tavsifida keltirilgan har bir fokuslangan test/nazoratni qayta ishga tushiring.
- Oʻzgargan bazaga moslashish uchungina assertionlarni hech qachon zaiflashtirmang yoki talab qilinadigan testlarni olib tashlamang.

Release freeze va qayta targetlash qoidalari uchun
[Branch yaratish va release modeli](BRANCHING_MODEL.md)dan foydalaning. Toʻliq CI roʻyxati uchun
[Sifat nazoratlari maʼlumotnomasi](../architecture/QUALITY_GATES.md)dan foydalaning.
