`open-sse/config/providerPluginManifest.ts` JSON uchun xavfsiz provayder
plagini shartnomasini belgilaydi. `open-sse/config/providerPluginManifestRegistry.ts` ushbu
shartnomani Bifrost, CLIProxyAPI yoki kelajakdagi Go/Rust routeri kabi saydkarlar uchun
joriy provayderlar reyestriga bogʻlaydi. TypeScript reyestri asosiy haqiqat manbai boʻlib
qoladi, ammo saydkarlar manifestdan ijrochi kodini, OAuth standartlarini, sarlavhalarni yoki
jarayon muhiti holatini import qilmasdan foydalanishi mumkin.

Xuddi shu manifest jarayondan tashqarida ishlaydigan saydkarlar uchun HTTP orqali
`GET /api/v1/provider-plugin-manifest` manzilida mavjud.

OmniRoute ushbu URL manzilini Bifrost va CLIProxyAPI uchun
`X-OmniRoute-Provider-Manifest-Url` soʻrov sarlavhasi orqali eʼlon qiladi. Saydkarga
mahalliy soʻrov manbasi oʻrniga ommaviy yoki konteyner tarmogʻi URL manzili kerak boʻlsa,
`OMNIROUTE_PROVIDER_MANIFEST_URL` ni sozlang.

## Manifestni yangilash

HTTP yakuniy nuqtasi `Cache-Control: public, max-age=60` va kuchli
`ETag` qaytaradi. Saydkar soʻnggi tekshirilgan manifestni saqlab turishi va yangilashda uning
ETag qiymatini `If-None-Match` orqali yuborishi kerak. `304 Not Modified` javobida tana
boʻlmaydi; saydkar keshlangan manifestdan foydalanishda davom etadi. Agar tekshirilgan
keshlangan manifest mavjud boʻlmasa, saydkar `304` javobini qabul qilish oʻrniga shartsiz
soʻrov yuborishi shart.

## Maqsad

Provayder metamaʼlumotlarini plagin shartnomasi tomon yoʻnaltirish, natijada tezkor soʻrov
yoʻli pastroq kechikishga ega saydkar tomonidan boshqarilishi, OmniRoute esa TypeScript
marshrutini siyosat darvozasi va zaxira sifatida saqlab qolishi mumkin. Manifest qoʻshimcha
xususiyatdir: uning oʻzi soʻrovlarni marshrutlashni oʻzgartirmaydi.

## Shartnoma

Manifest quyidagilarni oʻz ichiga oladi:

- provayder identifikatori va taxallusi
- yuqori oqim formati va ijrochi nomi
- autentifikatsiya turi, autentifikatsiya sarlavhasi va ixtiyoriy autentifikatsiya prefiksi
- statik yakuniy nuqta metamaʼlumotlari
- saydkar uchun moslik va provayder TS yoʻlida qolishi kerak boʻlganda buning aniq sabablari
- kontekst uzunligi, koʻrish/mulohaza yuritish bayroqlari va qoʻllab-quvvatlanmaydigan
  parametrlar kabi JSON uchun xavfsiz model metamaʼlumotlari
- `apikey`, `oauth`, `custom-executor`, `passthrough-models`, `responses`,
  `sidecar-candidate`, `usage-fetch` va `usage-supported` kabi imkoniyat teglari

Manifest ataylab quyidagilarni oʻz ichiga olmaydi:

- OAuth mijoz sirlari va standart maxfiy qiymatlar
- bajarilish vaqtidagi muhitni aniqlash
- soʻrov sarlavhalari va ommaviy hisob maʼlumotlari yordamchilari
- dinamik URL yaratuvchilar
- ijrochi funksiyalar
- seans puli ichki tafsilotlari

## Imkoniyat teglari

`capabilities` — reyestr yozuvidan olingan teglarning saralangan massivi. Integratorlar
TypeScript manba kodlarini qayta oʻqish oʻrniga uni «bu provayder nima qila oladi?» degan
savolga mashina oʻqiy oladigan javob sifatida qabul qilishlari kerak.

| Teg                  | Maʼnosi                                                                                |
| -------------------- | -------------------------------------------------------------------------------------- |
| `apikey`             | API kalitini qabul qiladi (`authType` — `apikey` yoki `optional`).                     |
| `oauth`              | OAuth yoki seans oqimidan foydalanadi.                                                 |
| `responses`          | OpenAI Responses-API asosiy URL manzilini taqdim etadi.                                |
| `passthrough-models` | Modellarga statik katalog oʻrniga toʻgʻridan-toʻgʻri yuqori oqimdan xizmat koʻrsatadi. |
| `custom-executor`    | Nostandart ijrochini ishga tushiradi, shuning uchun TypeScript yoʻlida qoladi.         |
| `sidecar-candidate`  | `sidecar.eligible` ni aks ettiradi — saydkarga import qilish uchun xavfsiz nomzod.     |
| `usage-fetch`        | Ulangan foydalanish yoki kvota oluvchisiga (`getUsageForProvider`) ega.                |
| `usage-supported`    | Foydalanish APIʼsi ushbu provayderni qabul qiladi (`isSupportedUsageConnection`).      |

`usage-fetch` faqat aniqlash uchun moʻljallangan. U OmniRoute provayder uchun foydalanish
maʼlumotlarini qanday oʻqishni bilishini bildiradi; u maʼlumotlarni olishni faollashtirmaydi,
kvota semantikasini oʻzgartirmaydi yoki Dashboard kvota vidjeti provayder uchun
yoqilganini anglatmaydi — ushbu vidjet alohida ravishda `USAGE_SUPPORTED_PROVIDERS`
orqali boshqariladi. Asosiy haqiqat manbai
`open-sse/services/usage/fetcherProviders.ts` ichidagi `USAGE_FETCHER_PROVIDERS` hisoblanadi.

Bu roʻyxat foydalanish dispetcheri qabul qiladigan satrlar asosida kalitlangan, shu sababli
unda kanonik identifikatorlar taxalluslar bilan aralashgan va u teglangan provayderlar
sonidan biroz uzunroq: manifest reyestrida chat provayderi boʻlmagan yozuvlar (masalan,
`firecrawl` qidiruv provayderi va `amazon-q` ACP provayderi) teglash uchun manifest
yozuviga ega emas.

`usage-supported` server va Dashboard foydalanish marshrutlari provayder ulanishini qabul
qiladimi yoki yoʻqmi, degan savolga javob beradi. U `isSupportedUsageConnection()`
(`src/lib/usage/providerLimits.ts`) va `supportsProviderQuota()`
(`src/shared/utils/providerQuotaVisibility.ts`) ni aks ettiradi; ularning ikkalasi ham
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`) orqali
boshqariladi. `usage-fetch` dan farqli ravishda, u faqat provayder identifikatori uchun
chiqariladi — bajarilish vaqtidagi tekshiruv taxalluslarni aniqlamasdan
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` ni bajaradi, shu sababli manifest ham
xuddi shu qoidani saqlaydi. Ikki tegning qamrov doiralari turlicha: 3 ta provayder faqat
`usage-fetch` tegiga (`opencode`, `opencode-zen`, `xai`), 1 tasi esa faqat
`usage-supported` tegiga (`xiaomi-mimo-token-plan`) ega, shuning uchun ulardan biri
ikkinchisini anglatmaydi.

## Sidecardan foydalanish

Sidecarlar `sidecar.eligible`ni soʻzsiz marshrutlash qarori sifatida emas, balki konservativ nomzod signali sifatida qabul qilishi kerak. Dastlab API kaliti va statik endpointlardan foydalanadigan hamda standart ijrochini qoʻllaydigan provayderlar import qilinishi kerak. Maxsus veb-ijrochilar, OAuth/sessiya oqimlari, dinamik URL yaratuvchilar yoki pool konfiguratsiyasiga ega provayderlar sidecar teng funksionallikni amalga oshirib, telemetriya muvofiqlikni tasdiqlamaguncha TypeScript zaxira yoʻlida qoladi.

Tavsiya etilgan migratsiya bosqichlari:

1. TS reyestridan provayder plagini manifestini yaratish va tekshirish.
2. Bifrost yoki CLIProxyAPIga API kaliti/statik endpoint provayderlari uchun manifestni import qilishni oʻrgatish.
3. TS zaxira yoʻlini faol holda saqlab, mos provayderlarni `OMNIROUTE_RELAY_BACKEND` ortidagi sidecar orqali marshrutlash.
4. Provayderlarni faqat muvaffaqiyat darajasi, p99 kechikishi, oqimli uzatish xatti-harakati va qoʻllab-quvvatlanmaydigan parametrlarni qayta ishlash TS yoʻliga mos kelgandagina asosiy yoʻlga oʻtkazish.
5. Har safar bittadan provayder oilasi uchun maxsus ijrochilarga moʻljallangan sidecarning oʻz plaginlarini qoʻshish.

## Nega provayderlarni bevosita Next ichiga joylashtirmaslik kerak

Next frontend provayder bajarilishini boshqarmasligi kerak. U API chegarasiga murojaat qilishi kerak. Shundan soʻng backend TypeScript ijrochisi, Bifrost, CLIProxyAPI yoki kelajakdagi mahalliy sidecardan foydalanishni tanlashi mumkin. Bu har qanday sidecarga topshirishdan oldin soʻrovlarni imzolash, ruxsat etilganlar roʻyxatini tekshirish, DB siyosati va zaxira xatti-harakatini markazlashtirilgan holda saqlaydi.
