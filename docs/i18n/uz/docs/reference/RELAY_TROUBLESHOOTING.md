Releylar (Vercel, Deno, Cloudflare) yuqori oqim ulanishini serversiz
backendda yakunlaydi, bu OmniRouteʼga provayder API kalitini server tomonida
saqlagan holda barqaror hududdan tashqi ulanishni amalga oshirish imkonini
beradi. Ushbu hujjatda operatorlar amaliy muhitda duch keladigan ikkita nosozlik
holati va OmniRoute ularning har biri uchun taqdim etadigan tiklash usullari
bayon etilgan.

## Reley autentifikatsiyasi qanday saqlanadi

Releyni **Sozlamalar → Proksi puli → Releyni joylashtirish** orqali
joylashtirganingizda, joylashtirish jarayoni releyning autentifikatsiya tokenini
proksining `notes` JSON maydonida saqlaydi:

- Agar `STORAGE_ENCRYPTION_KEY` o‘rnatilgan bo‘lsa, token `relayAuthEnc`
  ko‘rinishida yoziladi (saqlash vaqtida AES bilan shifrlanadi).
- Aks holda, u ochiq matn ko‘rinishida `relayAuth` sifatida yoziladi.

So‘rov vaqtida `extractRelayAuth(notes)` mavjud bo‘lgan shaklni qaytaradi,
shuning uchun reley qayta ishga tushirishlardan keyin ham ishlashda davom etadi.

## 1-nosozlik holati — kalit almashtirilgandan keyin tokenni deshifrlab bo‘lmaydi

**Alomat:** avval ishlagan releylar muhit yoki sirlar menejerida
`STORAGE_ENCRYPTION_KEY` almashtirilganidan keyin yuqori oqimdan `401`/autentifikatsiya
xatolarini qaytara boshlaydi. Saqlangan `relayAuthEnc` blokini endi deshifrlab
bo‘lmaydi, shu sababli `extractRelayAuth` bo‘sh satrni qaytaradi va reley hech
qanday autentifikatsiya maʼlumotini yubormaydi.

**Tiklash — joyida tuzatish (qayta joylashtirishsiz):**

1. **Sozlamalar → Proksi puli** bo‘limini oching.
2. Autentifikatsiya maʼlumotlari mavjud bo‘lmagan reley qatorlarida sariq
   `auth missing` belgisi va **Taʼmirlash** tugmasi ko‘rsatiladi.
3. **Taʼmirlash** tugmasini bosing. OmniRoute
   `POST /api/settings/proxies/[id]/repair-relay` so‘rovini yuboradi, u:
   - `relayAuthEnc` qiymatini **joriy** kalit bilan deshifrlaydi;
   - ochiq matndagi `relayAuth` qiymatini qayta `notes` ichiga yozadi;
   - `{ repaired: true, mode: "recovered" }` qiymatini qaytaradi.

Reley joylashtirish hisob maʼlumotlarini qayta kiritmasdan xizmat ko‘rsatishni
davom ettiradi.

Bu faqat joriy `STORAGE_ENCRYPTION_KEY` blokni hali ham deshifrlay olsa ishlaydi.
Agar kalitni migratsiyasiz almashtirgan bo‘lsangiz, blokni tiklab bo‘lmaydi.

## 2-nosozlik holati — tiklab bo‘lmaydigan token (eski kalit endi mavjud emas)

**Alomat:** **Taʼmirlash** tugmasini bosdingiz va
`{ repaired: false, mode: "redeploy", status: 409 }` javobini oldingiz.

**Tiklash — qayta joylashtirish:**

Saqlangan tokenni joriy kalit yordamida tiklab bo‘lmaydi. Releyni dastlab
foydalangan modalingizdan qayta joylashtiring (**Releyni joylashtirish** menyusi
→ Vercel / Deno / Cloudflare). Joylashtirish jarayoni yangi tokenni yozadi
(joriy kalit bilan shifrlangan holda) va qatordagi `auth missing` belgisi
yo‘qoladi.

Foydalanuvchi interfeysida tokenni tiklab bo‘lmasa, **Taʼmirlash** tugmasining
o‘zi qayta joylashtirish modalini ochadi, shuning uchun uni qo‘lda qidirishingiz
shart emas.

## 3-nosozlik holati — releyga ulanish mumkin, ammo u nosog‘lom

**Alomat:** proksi testi (`speed` tugmasi) reley ishlayotganini ko‘rsatadi, ammo
so‘rovlar baribir vaqti-vaqti bilan muvaffaqiyatsiz tugaydi.

OmniRouteʼning avtomatik sinov probasi qaytaradigan reley holatidan xabardorlik
sarlavhalarini tekshiring (**Sozlamalar → Proksi puli** hamda `relayTested` /
`relayAlive` hisoblagichlariga qarang):

- `x-relay-url` — qaysi reley backendi javob bergani.
- `x-relay-mode` — ushbu so‘rov uchun `ts` | `bifrost` | `auto`.
- `x-relay-attempts` — muvaffaqiyatga erishishdan oldin nechta reley o‘tishi
  sinab ko‘rilgani.
- `x-relay-fallback` — so‘rov afzal ko‘rilgan backenddan TypeScript releyiga
  o‘tganda `true` bo‘ladi.

`relayAlive` past bo‘lgan holda `x-relay-fallback` darajasi yuqori bo‘lsa,
sidecar backend nosog‘lom bo‘ladi va uni tuzatishingiz yoki reley backend
strategiyasini `ts` ga o‘zgartirishingiz kerak (`RELAY_BACKEND_STRATEGY.md` ga
qarang).

## API maʼlumotnomasi

| Metod  | Yo‘l                                      | Tana                    | Muvaffaqiyat                                                                                                                                    | Xatolik                                                                                |
| ------ | ----------------------------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | Qayta hosil qilinganda `200 { repaired: true, mode: "recovered" }`; ochiq matn allaqachon mavjud bo‘lsa `200 { repaired: false, mode: "noop" }` | Tiklab bo‘lmasa `409 { mode: "redeploy" }`; reley turi bo‘lmasa `400`; topilmasa `404` |

`GET /api/settings/proxies` ro‘yxat marshruti har bir elementga sirlardan xoli
`relayInfo: { isRelay, authMissing, repairMode }` qiymatini biriktiradi, shunda
boshqaruv paneli tokenni hech qachon oshkor qilmasdan taʼmirlash imkoniyatini
ko‘rsatishi mumkin.
