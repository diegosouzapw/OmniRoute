TPROXY shaffof deshifrlash — OmniRoute’ning
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM steki uchun **5-qamrab olish rejimi**. U Linux’da yadro TPROXY’i + siyosatga asoslangan marshrutlashdan foydalanib, mahalliy chiquvchi HTTPS trafikni tutib oladi va **deshifrlaydi** — bunda `/etc/hosts` soxtalashtirilmaydi va operatsion tizim miqyosidagi tizim proksi sozlamalari **oʻzgartirilmaydi**. U grafik interfeyssiz muhitlar uchun qulay
(tozalash kerak boʻladigan DNS oʻzgarishlari yoʻq) va xavfsizlik devori qoidalari qayta yuklashda avtomatik ravishda tozalanadi.

Boshqa qamrab olish rejimlaridan farqli ravishda, TPROXY har bir xost uchun alohida sozlashni talab qilmaydi: u maqsadli portdagi **istalgan** manzil xostlarini shaffof tarzda tutib oladi, har bir SNI xost nomi uchun tezkor ravishda chiqarilgan yakuniy sertifikat bilan TLS’ni yakunlaydi, deshifrlangan almashinuvni yozib oladi va soʻrovni asl manzilga qayta shifrlab yuboradi.

> **Faqat Linux, faqat root, ixtiyoriy yoqiladi.** Bu rejim Linux’ni, C asboblar zanjiri bilan yaratilgan mahalliy addonni va **CAP_NET_ADMIN** imkoniyatini (odatda root) talab qiladi. U faqat loopback orqali ishlaydigan AgentBridge API ortida himoyalangan va standart holatda oʻchirilgan. Istalgan xost uchun imzo qoʻya oladigan ishonchli MITM CA kuchli imkoniyatdir — [§6 Xavfsizlik](#6-security) boʻlimiga qarang.

**Manba:** `src/mitm/tproxy/`
**API yoʻnalishi:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**Boshqaruv paneli tugmasi:** Traffic Inspector → qamrab olish rejimlari asboblar paneli → **"TPROXY Decrypt"** ⚠
**Shuningdek qarang:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 Bu nima va undan qachon foydalanish kerak

Qolgan toʻrtta qamrab olish rejimining har birida cheklov mavjud:

| Rejim             | Trafik qanday yoʻnaltiriladi                                                  | Cheklov                                                                      |
| ----------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| AgentBridge       | Belgilangan xostlar toʻplami uchun `/etc/hosts` orqali DNS’ni soxtalashtirish | faqat roʻyxatdan oʻtgan IDE-agent xostlari                                   |
| Custom Hosts      | Har bir xost uchun `/etc/hosts` orqali DNS’ni soxtalashtirish                 | har bir xost uchun bittadan yozuv; hosts faylini tahrirlash uchun sudo kerak |
| HTTP_PROXY        | `HTTP_PROXY`/`HTTPS_PROXY` muhit oʻzgaruvchisi                                | faqat muhit oʻzgaruvchisini hisobga oladigan ilovalar                        |
| System-wide proxy | Operatsion tizim proksi sozlamalari                                           | global holatni oʻzgartiradi; ortga qaytarish talab etiladi                   |

TPROXY shaffof deshifrlash esa trafikni **yadro** darajasida yoʻnaltiradi. U
`mangle OUTPUT` zanjirida maqsadli portga (standart qiymat `443`) yoʻnalgan yangi mahalliy chiquvchi TCP ulanishlarini belgilaydi, `ip rule` belgilangan paketlarni mahalliy yetkazib berishga qayta yoʻnaltiradi va ular qayta kirganida `mangle PREROUTING` zanjiridagi `TPROXY` nishoni ularni **IP_TRANSPARENT** tinglovchisiga uzatadi — u esa TLS’ni yakunlaydi va ochiq matnni yozib oladi.

Quyidagi jarayondan keladigan trafikni tutib olish va deshifrlashni istaganingizda undan foydalaning:

- AgentBridge roʻyxatdan oʻtkazmagan xost bilan bogʻlansa va
- `HTTP_PROXY`’ni hisobga olmasa va
- tizim miqyosidagi proksi oʻzgarishi bilan uning ishiga xalaqit berishni istamasangiz.

Tutib olish yadroda amalga oshirilgani sababli, trafikni boshlovchi jarayon uchun **hech qanday
konfiguratsiya oʻzgarishi** talab qilinmaydi — biroq jarayon OmniRoute oʻrnatadigan dinamik CA’ga ishonishi kerak ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) bo‘limiga qarang).

## §3 Mahalliy IP_TRANSPARENT addoni

Nodeʼning `net` moduli `bind()`dan _oldin_ `setsockopt(IP_TRANSPARENT)`ni bajara olmaydi,
ammo TPROXY buni talab qiladi (aks holda yadro qayta yoʻnaltirilgan paketlarni tashlab yuboradi). Addon
(`src/mitm/tproxy/native/transparent.c`, `binding.gyp` orqali yigʻiladi) uchta funksiyani
taqdim etuvchi kichik N-API moduli boʻlib, ulardan `transparentSocket.ts` orqali foydalaniladi:

| Addon funksiyasi                      | Soket amali                                                                                  | Qoʻllanilishi                                                                             |
| ------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, xom fd qaytaradi | shaffof yozib olish tinglovchisi (Node fdʼni `server.listen({ fd })` orqali qabul qiladi) |
| `setSocketMark(fd, mark)`             | Mavjud fd uchun `setsockopt` **SO_MARK**                                                     | siklning oldini olish (proksining oʻz soketlarini belgilash)                              |
| `connectMarked(ip, port, mark)`       | Bloklamaydigan `connect()`dan **oldin** `socket()` + **SO_MARK**, fd qaytaradi               | qayta shifrlangan yuqori oqimga yoʻnaltirish (SYN belgini olib yuradi)                    |

Asl manzil `socket.localAddress`/`localPort`dan oʻqiladi — TPROXY
uni saqlab qoladi, shuning uchun **SO_ORIGINAL_DST**/NAT qidiruvi talab qilinmaydi.

### Addonni yigʻish

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- `npm run build` davomida `scripts/build/build-tproxy-native.mjs` `node-gyp
rebuild`ni ishga tushiradi. U **faqat Linux uchun va xatoga olib kelmaydi** — asboblar toʻplami mavjud boʻlmasa,
  yozib olish rejimi shunchaki mavjud boʻlmaydi.
- `assembleStandalone.mjs` `build/Release/transparent.node`ni mustaqil
  toʻplamga nusxalaydi; `transparentSocket.ts` uni modulga nisbatan ham,
  cwdʼga nisbatan ham (`<cwd>/src/mitm/tproxy/native/...`) aniqlaydi.
- `build/` va `prebuilds/` git tomonidan eʼtiborga olinmaydi — binar fayl **yigʻiladi, hech qachon
  commit qilinmaydi**.

Yuklagich quyidagi ustuvorlik tartibida tekshiradi:
`native/build/Release/transparent.node`, soʻng `native/prebuilds/transparent.node`
(har ikkisi ham modulga nisbatan va `<cwd>/src/mitm/tproxy/` ostida).

## §4 Har bir SNI uchun dinamik CA va ishonchli sertifikatlar ombori o‘rnatuvchisi

> **#6684 yangilanishi:** AgentBridge statik serveri (`src/mitm/server.cjs`) endi
> yagona statik, o‘zi imzolagan yakuniy sertifikat o‘rniga ayni shu CA/yakuniy
> sertifikat arxitekturasi andozasidan foydalanadi. U **alohida** CA nusxasidan
> (`src/mitm/cert/rootCa.ts`, `<DATA_DIR>/mitm/ca.key`/`ca.crt` manzilida saqlanadi)
> foydalanadi va avvaldan mavjud `omniroute-mitm.crt` ishonchli sertifikatlar
> ombori slotiga o‘rnatiladi (u yerdagi eski yagona yakuniy sertifikatni
> almashtiradi — ikkita ishonch yozuvini tozalash shart emas); u quyida
> keltirilgan TPROXY’ning o‘z `omniroute-tproxy-ca.crt` slotidan butunlay
> alohida saqlanadi. AgentBridge’ning yangi o‘rnatmalari CA modelidan avtomatik
> foydalanadi; eski statik yakuniy sertifikatga allaqachon ishongan o‘rnatma
> operator `MITM_ROOT_CA_ENABLED=true` orqali foydalanishni yoqmaguncha undan
> foydalanishda davom etadi (`src/mitm/cert/migration.ts` fayliga qarang) —
> **istalgan** host uchun yakuniy sertifikatni imzolay oladigan ishonchli MITM
> CA eski, qat’iy belgilangan SAN’li yakuniy sertifikatdan sezilarli darajada
> kuchliroq, shu sababli allaqachon ishonch bildirilgan o‘rnatmada o‘tish hech
> qachon yashirin amalga oshirilmaydi.

Tarixan statik AgentBridge MITM sertifikati faqat AgentBridge **qat’iy
belgilangan** hostlar to‘plami uchun DNS soxtalashtirishini amalga oshirgani
sababli ishlagan (endi bu to‘plam quyidagi model bilan birlashtirilgan).
TPROXY **ixtiyoriy** hostlarni tutib qoladi, shuning uchun uning tinglovchisi
mijoz so‘ragan har qanday SNI uchun yaroqli yakuniy sertifikatni taqdim etishi
kerak — endi AgentBridge uchun ham atigi 4 ta antigravity hosti o‘rniga to‘liq
`MITM_TOOL_HOSTS` to‘plami (9 ta vosita yozuvi) uchun ayni shu talab amal qiladi.

### Dinamik CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` mahalliy CA’ni (`selfsigned` bog‘liqligi asosida yaratilgan)
ishga tushiradi va u:

- `generateMitmCa()` orqali uzoq muddat amal qiladigan CA yaratadi (CN
  `"OmniRoute MITM CA"`, amal qilish muddati 10 yil, `basicConstraints CA=true`
  - `keyUsage keyCertSign,cRLSign`, 2048 bitli RSA / SHA-256).
- `issueLeafCert()` orqali **har bir SNI host nomi uchun talab bo‘yicha yakuniy
  sertifikat** chiqaradi (amal qilish muddati 1 yil, `subjectAltName` = SNI hosti)
  va har bir host nomi uchun bittadan `tls.SecureContext` keshda saqlaydi.
- TLS’ni yakunlovchi server uchun `createSNICallback()` funksiyasini taqdim etadi
  ([§5](#5-how-decrypt-and-capture-work) ga qarang).
- Qayta ishga tushirishlar orasida CA’ni o‘zgarmas saqlash uchun `existingCa`
  bilan yaratilishi mumkin (natijada ishonchli sertifikatlar omboriga qayta
  o‘rnatish talab etilmaydi).

CA maxfiy kaliti **hech qachon qurilmani tark etmaydi**.

### Ishonchli sertifikatlar ombori o‘rnatuvchisi (`src/mitm/tproxy/caTrust.ts`)

Tutib qolingan mijoz dinamik CA’ga ishonishi kerak, shu sababli yozib olish
rejimi ishga tushirilganda CA sertifikati OT ishonchli sertifikatlar omboridagi
**maxsus slot** — `omniroute-tproxy-ca.crt` (`TPROXY_CA_CERT_NAME` konstantasi) —
ichiga o‘rnatiladi. Bu slot statik MITM sertifikati slotidan
(`omniroute-mitm.crt`) alohida saqlanadi, shuning uchun ular hech qachon
bir-birining ustiga yozilmaydi.

`installTproxyCa(caPem, sudoPassword?)` distributivning tayanch sertifikatlar
katalogini aniqlaydi (avval Debian uslubidagi katalog tekshiriladi) va unga mos
yangilash buyrug‘ini ishga tushiradi:

| Tayanch sertifikatlar katalogi              | Yangilash buyrug‘i       |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

O‘rnatish jarayonida PEM vaqtinchalik faylga joylanadi, so‘ngra (imtiyozli
tarzda) tayanch katalog uchun `mkdir -p` bajariladi, tayyorlangan fayl unga `cp`
orqali ko‘chiriladi va yangilash buyrug‘i ishga tushiriladi.
`uninstallTproxyCa()` faqat maxsus slotni olib tashlaydi (statik MITM
sertifikatiga tegmaydi) va omborni yangilaydi — Linux bo‘lmagan tizimlarda bu
hech qanday amal bajarmaydi.

Barcha imtiyozli buyruqlar `execFileWithPassword`
(`src/mitm/systemCommands.ts`) orqali bajariladi — **argumentlar massiviga ega,
shell’siz va satr interpolyatsiyasisiz** `spawn` (Qat’iy qoida #13). Jarayon
root sifatida ishlayotganida (masalan, VPS’da) maqsadli buyruq to‘g‘ridan-to‘g‘ri
bajariladi va parol talab qilinmaydi; root bo‘lmagan ish stoli tizimida
`sudoPassword` standart kirish orqali `sudo -S` ga uzatiladi.

> Ish stolidagi `sudoPassword` ishonchli sertifikatlar omboriga o‘rnatishni
> tasdiqlash uchun POST so‘rovi tanasida yuboriladi; jarayon root sifatida
> ishlayotganida u butunlay e’tiborsiz qoldiriladi.

## §5 Shifrni yechish va yozib olish qanday ishlaydi

Konveyer (barchasi `src/mitm/tproxy/` ichida):

```
mahalliy ilova  ──TCP/443──▶  mangle OUTPUT ulanishni belgilaydi (fwmark)
                              ip rule → mahalliy marshrutlash jadvali → lo
                              mangle PREROUTING TPROXY → IP_TRANSPARENT tinglovchisi (8443-port)
                                  │  captureMode.ts: asl manzilni socket.localAddress orqali o‘qiydi
                                  ▼
                              tlsCapture.ts:
                                1. Har bir SNI uchun alohida sertifikat (dynamicCert) bilan MIJOZ TLS ulanishini yakunlaydi
                                2. ichki http.Server shifri yechilgan ochiq matnni tahlil qiladi
                                3. yozib olish → source: "tproxy" bilan globalTrafficBuffer.push()
                                   (sanitizeHeaders + maskSecret qo‘llanadi)
                                4. bypass belgili soket (connectMarked, sikldan himoya) orqali
                                   qayta shifrlab, asl manzilga yo‘naltiradi
                                  │
                                  ▼
                              asl yuqori oqim serveri (api.example.com)
```

- **TLS ulanishini yakunlash** (`createTlsCaptureServer`): xom ushlangan
  soketni dinamik CA sertifikatining SNI callback funksiyasidan foydalanib,
  server tomonidagi `tls.TLSSocket` bilan o‘raydi, so‘ng shifri yechilgan oqimni
  ichki `http.Server` serveriga uzatadi (standart MITM ulanishini yakunlash
  usuli). Osilib qolgan tunnel fayl deskriptorlarini tugatib qo‘ymasligi uchun
  soketlarning ishlash muddati `MITM_IDLE_TIMEOUT_MS` bilan cheklanadi.
- **Yozib olish** (`handleDecryptedRequest`): `source: "tproxy"`, boshlang‘ich
  holati `"in-flight"` bo‘lgan `InterceptedRequest` obyektini buferga qo‘shadi;
  sarlavhalar buferga kirishidan oldin `sanitizeHeaders()` orqali, tanalar esa
  `maskSecret()` orqali o‘tkaziladi. Keyin yozuv javob, hajmlar va kechikish
  ma’lumotlari bilan yangilanadi.
- **Qayta shifrlab yo‘naltirish** (`createForward` / `realForward`): trafikni
  qayta shifrlab, asl manzilga yo‘naltiradi. `rejectUnauthorized` standart
  holatda **`true`** (standart bo‘yicha xavfsiz) — yuqori oqim sertifikati mijoz
  so‘ragan SNI/Host asosida tekshiriladi, shu sababli proksi aynan asl mijoz rad
  etadigan sertifikatlarni rad etadi.

### Sikldan himoya (SO_MARK)

Qoidalar yangi mahalliy chiquvchi ulanishlarni belgilagani sababli, proksining
**o‘z** qayta shifrlangan yo‘naltirishi odatda yana ushlanadi — natijada cheksiz
sikl yuzaga keladi. Yo‘naltirish yo‘li bundan bypass soket belgisi (**SO_MARK**)
yordamida himoyalanadi:

- `realForward` yuqori oqim soketini `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  orqali ochadi — `DEFAULT_BYPASS_MARK = 0x539` — bu **SO_MARK** belgisini
  `connect()` chaqirilishidan **oldin** o‘rnatadi, shu sababli yo‘naltirishning
  SYN paketi bypass belgisini olib yuradi.
- `mangle OUTPUT` qoidasi bypass belgisiga ega ulanishlarni chiqarib tashlaydi
  (`-m mark ! --mark <bypassMark>`), shu sababli proksining yo‘naltirishi qayta
  belgilanmaydi va TPROXY tizimiga qaytadan kirmaydi.

> Amalga oshirish bo‘yicha eslatma: bypass belgili soket agentning
> `createConnection` funksiyasiga o‘rnatilishi kerak
> (`https.request({ createConnection })` agent mavjud bo‘lganda bildirmasdan
> e’tiborsiz qoldiriladi), aks holda yo‘naltirish belgilanmagan soketni ochadi va
> sikl qaytadan yuzaga keladi. Bu e2e sinovlari orqali tasdiqlangan sikldan himoya
> tuzatishi edi.

## §7 Tranzaksion firewall qoʻllash / qaytarish

Nosozlik hech qachon `mangle` qoidasini yoki eskirgan marshrutni qoldirmasligi kerak. Buyruqlar tuzuvchisi
(`src/mitm/tproxy/commands.ts`) va bajaruvchi (`src/mitm/tproxy/setup.ts`)
**qaytarish — qoʻllashning teskari tartibdagi aniq teskarisi** ekanini kafolatlaydi.

`applyTproxy(cfg)` qoʻllash buyruqlarini tartib bilan bajaradi; **har qanday** xatolik yuz bersa, u
imkon qadar toʻliq `revertTproxy(cfg)`ni bajaradi va xatolikni qayta chiqaradi — shu sababli firewall
yoki toʻliq qoʻllanadi, yoki toʻliq qaytariladi, hech qachon qisman qoʻllangan holda qolmaydi. `revertTproxy(cfg)`
teskari buyruqlarni teskari tartibda bajaradi va xatoliklarni eʼtiborsiz qoldiradi (idempotent — uni
shartsiz chaqirish xavfsiz, masalan, AgentBridge `repairMitm()` tozalashidan).

`validateTproxyConfig(cfg)` har qanday buyruqdan oldin ishlaydi: portlar `1–65535`
oraligʻida boʻlishi, `mark`/`routeTable`/`bypassMark` musbat butun sonlar boʻlishi va `bypassMark`
`mark`dan farq qilishi kerak (siklga qarshi himoya).

### Qoʻllash buyruqlari (tartib bilan)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Qaytarish ularni teskari tartibda oʻchiradi: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> Ushbu retsept **OUTPUT asosida**, chunki MITM foydalanish holati _lokal_ chiquvchi
> trafikni (ayni xostdagi ilovalarni) qamrab oladi, `PREROUTING`dagi TPROXYning oʻzi esa buni
> koʻrmaydi — `PREROUTING` faqat yoʻnaltirilayotgan trafikni koʻradi. `OUTPUT` zanjiri yangi
> lokal ulanishlarni belgilaydi, `ip rule` ularni lokal yetkazib berishga (`lo`) qayta yoʻnaltiradi va
> shundan soʻng `PREROUTING` ularni shaffof tinglovchiga biriktiradi.

## §8 Konfiguratsiya

Ishga tushirish soʻrovi (`POST /api/tools/agent-bridge/tproxy`) `StartTproxyBodySchema`
(`tproxy/route.ts`) tomonidan tekshiriladigan quyidagi maydonlarni qabul qiladi. Ularning barchasi ixtiyoriy
boʻlib, koʻrsatilmasa standart qiymatlaridan foydalaniladi:

| Maydon           | Tur                | Standart | Izohlar                                                                                                                                                   |
| ---------------- | ------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`    | Shaffof tarzda tutib qolinadigan maqsad TCP porti                                                                                                         |
| **mark**         | int (≥1)           | `0x2333` | `OUTPUT`da oʻrnatiladigan va `ip rule` + `PREROUTING` tomonidan moslashtiriladigan firewall belgisi                                                       |
| **onPort**       | int (1–65535)      | `8443`   | Shaffof (**IP_TRANSPARENT**) tinglovchi bogʻlanadigan port                                                                                                |
| **routeTable**   | int (≥1)           | `233`    | `local 0.0.0.0/0` marshrutini saqlovchi siyosat asosidagi marshrutlash jadvali identifikatori                                                             |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | Proksi oʻzining yuqori oqim ulanishlariga oʻrnatadigan chetlab oʻtish soket belgisi (**SO_MARK**); `OUTPUT`dan chiqarib tashlanadi (siklga qarshi himoya) |
| **sudoPassword** | string             | —        | Faqat root boʻlmagan ish stollari uchun: ishonchli sertifikatlar omboriga oʻrnatishga ruxsat beradi; root boʻlganda eʼtiborga olinmaydi                   |

TPROXY uchun **muhit oʻzgaruvchilari mavjud emas** — barcha konfiguratsiya
POST tanasi yoki yuqoridagi standart qiymatlar orqali beriladi.

1. **Traffic Inspector** (`/dashboard/tools/traffic-inspector`) sahifasini oching.
2. Yozib olish rejimlari asboblar panelidan **"TPROXY shifrini ochish"** ⚠ tugmasini toping
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Agar u **faolsizlantirilgan** bo‘lib, "TPROXY shifrini ochish uchun Linux + root +
     mahalliy addon talab qilinadi" degan ko‘rsatma chiqsa, bu xostda mahalliy addon mavjud emas
     (Linux emas, asboblar zanjiri yo‘q yoki addon yig‘ilmagan). [§2](#2-requirements) va
     [§3](#3-the-native-ip_transparent-addon) bo‘limlariga qarang.
3. Tugmani bosing. U `startTproxyCaptureMode()`
   (`src/lib/inspector/tproxyCaptureApi.ts`) orqali
   `POST /api/tools/agent-bridge/tproxy` ni chaqiradi; bu funksiya:
   dinamik CA’ni yaratadi, shaffof tinglovchini ochadi, fayervol qoidalarini
   qo‘llaydi va CA’ni operatsion tizimning ishonchli sertifikatlar omboriga o‘rnatadi.
4. Ishlayotganida almashtirgich qahrabo rangga kiradi va joriy tutib olishlar sonini
   (`· <interceptCount>`) ko‘rsatadi. Tutib olingan so‘rovlar so‘rovlar ro‘yxatida
   `source: "tproxy"` bilan ko‘rinadi.

Yozib olish rejimi holati (ishlamoqda / mavjud / tutib olishlar soni / tinglovchi porti)
`GET /api/tools/agent-bridge/tproxy` dan (`src/mitm/tproxy/captureManager.ts` ichidagi
`getCaptureStatus()`) olinadi. Bir vaqtning o‘zida faqat **bitta** TPROXY seansi ishlaydi —
ikkinchi seansni ishga tushirish "TPROXY capture mode is already running" xatosi bilan rad etiladi.

## §10 Muammolarni bartaraf etish

### Almashtirgich faolsizlantirilgan

Mahalliy addon’ni yuklab bo‘lmaydi. Quyidagilarni tekshiring: Linux tizimidan
foydalanyapsiz, addon’ni (`npm run build:native:tproxy`) orqali yig‘gansiz va jarayon
`transparent.node` faylini yuklay oladi. Almashtirgichni `isTransparentSocketAvailable()`
nazorat qiladi; addon mavjud bo‘lmasa, `GET /api/tools/agent-bridge/tproxy`
`available: false` qaytaradi.

### Hech narsa yozib olinmayapti

- Tutib olinayotgan jarayon haqiqatan ham sozlangan `dport` portiga
  (standart qiymat `443`) ulanayotganini tekshiring.
- Jarayon dinamik CA’ga ishonishini tekshiring. CA
  `omniroute-tproxy-ca.crt` nomi bilan o‘rnatiladi; o‘z ishonchli sertifikatlar omboriga
  ega ilovalarda (Firefox/Chrome NSS) sertifikatni u yerga ham qo‘shish talab qilinishi mumkin.
- Sertifikatga ishonish / server holatini tekshirish uchun AgentBridge’ning
  **Diagnostika** o‘z-o‘zini tekshirish sinovini ishga tushiring
  ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md) fayliga qarang).

### Nosozlikdan keyin qolib ketgan fayervol qoidalari

`revertTproxy()` qo‘llash amalining aynan teskarisi bo‘lib, idempotent hisoblanadi.
Rejimni to‘xtatish qoidalarni bekor qiladi; agar OmniRoute seans o‘rtasida majburan
to‘xtatilgan bo‘lsa, yetim qolgan tizim holatini (DNS spoof, ildiz CA, tizim proksisi)
bekor qilish uchun AgentBridge’ning **Tuzatish** amalidan
(`POST /api/tools/agent-bridge/repair`) foydalaning. TPROXY `mangle` qoidalari va marshrut
qayta yuklash vaqtida ham avtomatik ravishda tozalanadi.

### Cheksiz sikl / proksi o‘z yo‘naltirishini tutib oladi

Bu siklga qarshi himoya holatidir. `bypassMark` qiymati `mark` qiymatidan farq qilishini
tekshiring (validatsiya buni majburiy qiladi) va yo‘naltirish `connectMarked` dan
foydalanishiga ishonch hosil qiling (`realForward` ichida shunday qilingan).
[§5 Siklga qarshi himoya](#anti-loop-so_mark) bo‘limiga qarang.
