> **Σύνοψη**: Το OmniRoute διαθέτει ενσωματωμένη παρακολούθηση εύρυθμης λειτουργίας, αυτόματο πιλότο παρόχων, παρακολούθηση ορίων χρήσης και hooks παρατηρησιμότητας. Αυτός ο οδηγός καλύπτει τον πίνακα ελέγχου, τις ειδοποιήσεις και την αντιμετώπιση προβλημάτων.

**Πηγές:**

- `src/lib/monitoring/observability.ts` — στιγμιότυπο παρατηρησιμότητας
- `src/lib/monitoring/comboHealthAutopilot.ts` — αυτόματος πιλότος εύρυθμης λειτουργίας συνδυασμών
- `src/lib/monitoring/providerHealthAutopilot.ts` — αυτόματος πιλότος παρόχων
- `src/lib/monitoring/providerHealthMatrix.ts` — πίνακας εύρυθμης λειτουργίας παρόχων
- `src/lib/localHealthCheck.ts` — τοπικός έλεγχος εύρυθμης λειτουργίας
- `src/lib/tokenHealthCheck.ts` — εύρυθμη λειτουργία ανανέωσης διακριτικών
- `src/lib/proxyHealth.ts` — κρυφή μνήμη εύρυθμης λειτουργίας διακομιστή μεσολάβησης (καλύπτεται στο PROXY_GUIDE.md)

## Επισκόπηση

Το OmniRoute διαθέτει **3 επίπεδα παρακολούθησης**:

```
┌──────────────────────────────────────────────────────────────┐
│  Επίπεδο 1: Εύρυθμη λειτουργία συστήματος (επίπεδο διακομιστή)│
│  ├─ localHealthCheck.ts — ΒΔ, θύρες, εγγενείς εξαρτήσεις      │
│  ├─ db/healthCheck.ts — ακεραιότητα, FK, ορφανά τεχνουργήματα │
│  └─ Πίνακας ελέγχου: /dashboard/health                       │
├──────────────────────────────────────────────────────────────┤
│  Επίπεδο 2: Εύρυθμη λειτουργία παρόχων (ανθεκτικότητα ανά πάροχο)│
│  ├─ providerHealthAutopilot.ts — διακόπτης κυκλώματος, χρόνοι αναμονής│
│  ├─ providerHealthMatrix.ts — βαθμολογίες εύρυθμης λειτουργίας ανά πάροχο/μοντέλο│
│  └─ Πίνακας ελέγχου: /dashboard/providers                    │
├──────────────────────────────────────────────────────────────┤
│  Επίπεδο 3: Ζωντανή παρατηρησιμότητα (στιγμιότυπα χρόνου εκτέλεσης)│
│  ├─ observability.ts — διακόπτες κυκλώματος, συνεδρίες, όρια χρήσης│
│  ├─ tokenHealthCheck.ts — εύρυθμη λειτουργία ανανέωσης διακριτικών OAuth│
│  └─ Εργαλεία MCP: omniroute_get_health, omniroute_get_session_snapshot │
└──────────────────────────────────────────────────────────────┘
```

## Σελίδες πίνακα ελέγχου

### `/dashboard/health` (Εύρυθμη λειτουργία συστήματος)

Ο πίνακας ελέγχου εύρυθμης λειτουργίας ανώτατου επιπέδου εμφανίζει:

| Ενότητα                  | Τι εμφανίζει                                                  |
| ------------------------ | ------------------------------------------------------------- |
| **Κατάσταση διακομιστή** | Χρόνο λειτουργίας, έκδοση, θύρα, ενεργές συνδέσεις            |
| **Βάση δεδομένων**       | Σύνδεση, ακεραιότητα, μέγεθος WAL, πρόσφατες μετεγκαταστάσεις |
| **Σύνοψη παρόχων**       | Πλήθος ενεργών και υγιών παρόχων, πλήθος ανοικτών διακοπτών   |
| **Παρακολούθηση ορίων**  | Ενεργές συνεδρίες, ειδοποιήσεις, εξαντλημένα όρια             |
| **Πρόσφατα σφάλματα**    | Τελευταία 10 σφάλματα με ίχνη στοίβας                         |
| **Χρήση πόρων**          | Μνήμη, CPU, ένδειξη πίεσης σωρού                              |

### `/dashboard/providers` (Εύρυθμη λειτουργία παρόχων)

Πίνακας ελέγχου ανά πάροχο:

| Στήλη              | Περιγραφή                                                      |
| ------------------ | -------------------------------------------------------------- |
| Πάροχος            | Αναγνωριστικό παρόχου + εμφανιζόμενο όνομα                     |
| Εύρυθμη λειτουργία | Πράσινη/κίτρινη/κόκκινη κατάσταση                              |
| Κύκλωμα            | Ανοικτή/κλειστή/ημιανοικτή κατάσταση                           |
| Συνδέσεις          | Πλήθος συνδέσεων, τελευταία ανανέωση                           |
| Μοντέλα            | Διαθέσιμα μοντέλα, εύρυθμη λειτουργία ανά μοντέλο              |
| Κόστος             | Σημερινό κόστος, τάση 7 ημερών                                 |
| Σφάλματα           | Πλήθος σφαλμάτων τελευταίων 24 ωρών, συχνότερη κλάση σφάλματος |

Κάντε κλικ σε έναν πάροχο για να δείτε:

- Πρόσφατα αιτήματα με ανάλυση καθυστέρησης
- Βαθμολογίες εύρυθμης λειτουργίας ανά σύνδεση
- Κλειδώματα ανά μοντέλο
- Προτάσεις αυτόματου πιλότου

### `/dashboard/quota` (Παρακολούθηση ορίων χρήσης)

Για κάθε κλειδί API:

- Τρέχουσα χρήση έναντι ορίου (γραμμή προόδου)
- Τάση ορίου χρήσης (διάγραμμα 30 ημερών)
- Χρόνος επόμενης επαναφοράς
- Ιστορικό ειδοποιήσεων

### `/dashboard/combos` (Εύρυθμη λειτουργία συνδυασμών)

Ανά συνδυασμό:

- Στρατηγική + στόχοι
- Εύρυθμη λειτουργία ανά στόχο
- Πρόσφατα συμβάντα μετάπτωσης
- Ποσοστό επιτυχίας (24ωρο, 7 ημέρες, 30 ημέρες)

## API ελέγχου υγείας

Το OmniRoute εκθέτει **δύο** HTTP επιφάνειες ελέγχου υγείας. Δεν είναι εναλλάξιμες για ενορχηστρωτές.

| Διαδρομή                     | Σκοπός                                                                | Βάρος                                    | Χρήση για                                                                             |
| ---------------------------- | --------------------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------- |
| `GET /healthz`               | Ζωτικότητα/ετοιμότητα κύκλου ζωής (`ok` / `starting` / `stopping`)    | Αμελητέο (μόνο σημαία φάσης)             | **Ετοιμότητα** Kubernetes· ήπια **ζωτικότητα**, αν πρέπει να χρησιμοποιηθεί HTTP      |
| `GET /api/monitoring/health` | Αναλυτική σύνοψη συστήματος + παρόχων (DB, heap, πλήθος καταλόγου, …) | Βαρύ (σύγχρονες εργασίες DB / εποπτείας) | Πίνακες ελέγχου, αναλυτικοί blackbox έλεγχοι, ενσωματωμένος έλεγχος υγείας του Docker |

> **Σημείωση:** Οι πίνακες υγείας παρόχων, τα ζητήματα αυτόματου πιλότου, οι επόπτες ορίων χρήσης, η υγεία διακριτικών και οι λεπτομέρειες καθυστέρησης πέρα από το `/api/monitoring/health` είναι διαθέσιμα μέσω του **εργαλείου MCP** `observability_snapshot` ή των σελίδων του **πίνακα ελέγχου** — δεν υπάρχουν αποκλειστικές διαδρομές REST για αυτά.

Και οι δύο διαδρομές εκτελούνται στον **ίδιο βρόχο συμβάντων Node** με την εξυπηρέτηση αιτημάτων. Μια διαδρομή που δεσμεύει τη CPU (μεγάλος φόρτος επεξεργασίας καταλόγου στο `GET /v1/models`, συμπίεση μεγάλου context / καταμέτρηση διακριτικών) μπορεί να καθυστερήσει **όλους** τους χειριστές HTTP, συμπεριλαμβανομένου του `/healthz`. Απασχολημένος βρόχος συμβάντων ≠ νεκρή διεργασία. Προτιμήστε τη διόρθωση της αιτίας του φόρτου· η ρύθμιση των probes μειώνει μόνο τους εσφαλμένους τερματισμούς.

### Ελαφρύ probe ενορχηστρωτή

```bash
GET /healthz
# ή HEAD /healthz
```

- **200** + σώμα `ok` όταν η φάση κύκλου ζωής του διακομιστή είναι έτοιμη
- **503** + `starting` / `stopping` κατά την εκκίνηση ή τον τερματισμό
- Υλοποίηση: `src/app/healthz/route.ts` (χωρίς ping στη DB)

### Υγεία συστήματος (αναλυτική)

```bash
GET /api/monitoring/health
```

Απόκριση:

```json
{
  "status": "healthy",
  "version": "3.8.16",
  "uptime": 123456,

    "integrity": { "status": "pass", "result": "ok" },
    "foreign_keys": { "status": "pass", "violations": 0 },
    "heap_pressure": { "status": "pass", "usage_mb": 142, "threshold_mb": 512 },
```

#### `credentialHealth`: προσωρινή μνήμη probes έναντι του `test_status` του SQLite

Το `GET /api/monitoring/health` → `credentialHealth` είναι ο **μετρητής της προσωρινής μνήμης probes στη μνήμη** και όχι μια ζωντανή αποτύπωση του `provider_connections.test_status`. Μετά το #12532, η διαδρομή αιτήματος διαβάζει μόνο το `getCachedCredentialHealthSummary()`· τα probes παρασκηνίου ανανεώνουν την προσωρινή μνήμη εκτός του βρόχου συμβάντων.

| Επίπεδο                            | Πού                                                                   | Τι σημαίνει                                                                                                                                                                                                                             |
| ---------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Μετρητής προσωρινής μνήμης probes  | `credentialHealth.total` / `healthy` / `failed` / `unknown` / `stale` | Τα πιο πρόσφατα αποτελέσματα των probes υγείας διαπιστευτηρίων που εξακολουθούν να διατηρούνται στη μνήμη της διεργασίας. Το `source` είναι πάντα `probe-cache`.                                                                        |
| Λεπτομέρειες αποτυχημένης σύνδεσης | `credentialHealth.failedConnections`                                  | Υπάρχει **μόνο όταν `failed > 0`**. Περιορισμένη λίστα εγγραφών προσωρινής μνήμης με `status=error` (`connectionId`, `status`, εξυγιασμένα `lastError` / `lastErrorType`). Το `failedOmitted` ορίζεται όταν εφαρμόστηκε όριο στη λίστα. |
| Επίμονη κατάσταση SQLite           | `credentialHealth.staleDbNonOkCount`                                  | Πλήθος **ενεργών** (`is_active=1`) εγγραφών σύνδεσης των οποίων το αποθηκευμένο `test_status` είναι μια γνωστή μη εντάξει κατάσταση (`error`, `expired`, `credits_exhausted`, `banned`, `deactivated`, `unavailable`).                  |

Τα δύο επίπεδα μπορούν σκόπιμα να διαφωνούν:

- Μετρητής `failed=0` ενώ `staleDbNonOkCount>0` — το SQLite εξακολουθεί να έχει ένα επίμονο
  `test_status` (για παράδειγμα `expired` ή `credits_exhausted`) που το πιο πρόσφατο
  στιγμιότυπο της προσωρινής μνήμης probes δεν υπολογίζει ως `status=error`.
- Μετρητής `failed>0` ενώ το SQLite φαίνεται υγιές — ένα πρόσφατο probe απέτυχε και έχει
  αποθηκευτεί προσωρινά· η εγγραφή της DB δεν έχει ενημερωθεί ή εκκαθαρίστηκε αργότερα.

Μην ενεργοποιείτε ειδοποίηση αποκλειστικά βάσει του `provider_connections.test_status` κατά τη συλλογή δεδομένων από αυτό το
endpoint. Χρησιμοποιήστε τα `failed` + `failedConnections` για ζωντανές αποτυχίες probes και το
`staleDbNonOkCount` όταν χρειάζεστε το πλήθος των αποθηκευμένων επίμονων καταστάσεων.

### Προτάσεις για probes Kubernetes

Το OmniRoute είναι μια **μεμονωμένη διεργασία Node** (ένας βρόχος συμβάντων). Το προεπιλεγμένο `HEALTHCHECK` του Docker στοχεύει το ελαφρύ `/healthz`. Το `/api/monitoring/health` είναι **υπερβολικά βαρύ** για τα διαστήματα ελέγχου ζωτικότητας του kubelet.

| Έλεγχος                    | Προτεινόμενος στόχος                                                                | Σημειώσεις                                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Εκκίνηση**               | HTTP `GET /healthz` με μεγάλο `failureThreshold` (ή μεγάλο `startPeriod`)           | Η ψυχρή εκκίνηση + η μετεγκατάσταση SQLite μπορεί να διαρκέσουν περισσότερο από μερικά δευτερόλεπτα                                                                                                                                                                                                                                                                                                                           |
| **Ετοιμότητα**             | HTTP `GET /healthz`                                                                 | Κύκλος ζωής `ok` / `starting` / `stopping` (200 έναντι 503). Εξακολουθεί να παρουσιάζει διακυμάνσεις αν ο βρόχος είναι αποκλεισμένος από τη CPU. Μια απόκριση **200 μετά από αρκετά δευτερόλεπτα δεν είναι υγιής** (#10303) — σημαίνει ότι ο βρόχος συμβάντων είχε στερηθεί πόρους προτού εκτελεστεί ο χειριστής των 3 byte                                                                                                   |
| **Ζωτικότητα**             | HTTP `GET /livez`, **ή TCP** στην κύρια θύρα υπηρεσίας (`PORT`, προεπιλογή `20128`) | Το `/livez` ελέγχει μόνο αν η διεργασία είναι ενεργή (πάντα 200 αν εκτελεστεί ο χειριστής). Εξακολουθεί να μοιράζεται τον βρόχο συμβάντων — απασχολημένο ≠ νεκρό, και δεν ανιχνεύει τη στέρηση πόρων του βρόχου συμβάντων (#10303) καλύτερα από το TCP. Προτιμήστε **TCP** αν οι έλεγχοι HTTP λήγουν υπό φόρτο καταλόγου/συμπίεσης· σε κάθε περίπτωση, **μην** τερματίζετε το pod λόγω σύντομων εμπλοκών του βρόχου συμβάντων |
| **Εκτενής έλεγχος υγείας** | `GET /api/monitoring/health` από εξωτερικό ελεγκτή                                  | Δεν προορίζεται για `livenessProbe` του kubelet / αυστηρό `readinessProbe`                                                                                                                                                                                                                                                                                                                                                    |

Παράδειγμα διαμόρφωσης (προσαρμόστε τα όρια στον φόρτο ψυχρής εκκίνησης και συμπίεσης):

```yaml
ports:
  - name: http
    containerPort: 20128
startupProbe:
  httpGet:
    path: /healthz
    port: http
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /healthz
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 6
livenessProbe:
  httpGet:
    path: /livez
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 6
  # Σε περίπτωση εμπλοκής του βρόχου συμβάντων, το HTTP /livez μπορεί και πάλι να λήξει. Το TCP είναι η
  # συντηρητική εναλλακτική:
  # tcpSocket:
  #   port: http
```

**Μην** κατευθύνετε τον έλεγχο **ζωτικότητας** του kubelet στο `/api/monitoring/health`. Αυτή η διαδρομή εκτελεί πραγματικές εργασίες βάσης δεδομένων/παρακολούθησης και θα δώσει ψευδώς θετικά αποτελέσματα υπό φόρτο.

Σχετικά: [#10052](https://github.com/diegosouzapw/OmniRoute/issues/10052) (έλεγχοι ενώ ο βρόχος συμβάντων είναι απασχολημένος), [#9685](https://github.com/diegosouzapw/OmniRoute/issues/9685) / [#10055](https://github.com/diegosouzapw/OmniRoute/pull/10055) (μονοπώληση πόρων από την τιμολόγηση καταλόγου), [#10117](https://github.com/diegosouzapw/OmniRoute/issues/10117) (μονοπώληση πόρων από την καταμέτρηση token συμπίεσης).

### Προαιρετικές εργασίες στη διαδρομή αιτήματος (μνήμη, δεξιότητες, ανανέωση token)

Η εξαγωγή μνήμης, η εισαγωγή δεξιοτήτων και η ανανέωση token OAuth μοιράζονται τον **κύριο βρόχο συμβάντων του Node** με το `/healthz`. Είναι λειτουργίες που ενεργοποιούνται από τον πίνακα ελέγχου (`memoryEnabled`, `skillsEnabled`), όχι worker pool. Δείτε [Περιβάλλον — κόστος βρόχου συμβάντων](../reference/ENVIRONMENT.md#event-loop-cost-of-memory-skills-and-token-refresh-10349).

### Λεπτομέρειες παρόχου

## Αυτόματος πιλότος υγείας παρόχων

Το module `providerHealthAutopilot.ts` είναι ένα **σύστημα αυτοΐασης** που:

1. Εντοπίζει προβλήματα παρόχων (ανοιχτό κύκλωμα, περίοδοι αναμονής, αποκλεισμοί, προειδοποιήσεις ορίου χρήσης)
2. Δημιουργεί **προτεινόμενες ενέργειες** για την επίλυσή τους
3. Προαιρετικά **εκτελεί αυτόματα** ενέργειες χαμηλού κινδύνου

### Τύποι προβλημάτων που εντοπίζονται

| Είδος προβλήματος            | Σοβαρότητα    | Παράδειγμα συνθήκης                                  |
| ---------------------------- | ------------- | ---------------------------------------------------- |
| `provider_circuit_open`      | κρίσιμη       | Ο διακόπτης κυκλώματος άνοιξε μετά από 5 αποτυχίες   |
| `provider_circuit_half_open` | προειδοποίηση | Το κύκλωμα δοκιμάζει την ανάκαμψη                    |
| `connection_cooldown`        | προειδοποίηση | Η σύνδεση βρίσκεται σε αναμονή μετά από απόκριση 429 |
| `stale_connection_error`     | προειδοποίηση | Η τελευταία ανανέωση απέτυχε πριν από 30+ λεπτά      |
| `terminal_connection_error`  | κρίσιμη       | Το OAuth ανακλήθηκε ή το κλειδί δεν είναι έγκυρο     |
| `inactive_connection`        | πληροφορία    | Η σύνδεση είναι απενεργοποιημένη στις ρυθμίσεις      |
| `model_lockout`              | προειδοποίηση | Συγκεκριμένο μοντέλο βρίσκεται σε καραντίνα          |
| `quota_monitor_warning`      | προειδοποίηση | Χρήση ορίου στο 80%+                                 |

### Τύποι ενεργειών που δημιουργούνται

| Ενέργεια                       | Κίνδυνος | Περιγραφή                                              |
| ------------------------------ | -------- | ------------------------------------------------------ |
| `clear_provider_breaker`       | μέτριος  | Επαναφορά του διακόπτη κυκλώματος σε κλειστή κατάσταση |

| `clear_stale_connection_error` | χαμηλός  | Εκκαθάριση της ένδειξης παρωχημένου σφάλματος          |
| `clear_model_lockout`          | χαμηλός  | Επανενεργοποίηση μοντέλου σε καραντίνα                 |
| `reactivate_connection`        | μέτριος  | Επανενεργοποίηση μιας απενεργοποιημένης σύνδεσης       |
| `deactivate_connection`        | υψηλός   | Απενεργοποίηση μιας προβληματικής σύνδεσης             |

### API

> **Δεν υπάρχει τελικό σημείο REST.** Τα προβλήματα του αυτόματου πιλότου είναι διαθέσιμα μέσω του εργαλείου MCP `observability_snapshot` ή του πίνακα ελέγχου. Ο αυτόματος πιλότος εκτελείται εσωτερικά· η συμπεριφορά του διαμορφώνεται μέσω της βάσης δεδομένων ρυθμίσεων (πεδίο `autopilotMode` ανά σύνδεση) και όχι μέσω μεταβλητών περιβάλλοντος — η εντολή `grep -rn` για μια μεταβλητή περιβάλλοντος λειτουργίας αυτόματου πιλότου επιστρέφει μηδενικά αποτελέσματα.

### Λειτουργία αυτόματου πιλότου

Ο αυτόματος πιλότος λειτουργεί από προεπιλογή σε **χειροκίνητη λειτουργία** — εντοπίζει προβλήματα και δημιουργεί προτεινόμενες ενέργειες, αλλά δεν τις εφαρμόζει αυτόματα. Οι ενέργειες μπορούν να εφαρμοστούν μέσω του πίνακα ελέγχου.

### Σημασία καταστάσεων

| Κατάσταση   | Πότε                                  | Ενέργεια διεπαφής χρήστη                              |
| ----------- | ------------------------------------- | ----------------------------------------------------- |
| `starting`  | Η αρχική άντληση βρίσκεται σε εξέλιξη | Ένδειξη φόρτωσης                                      |

| `healthy`   | Απομένει > 50% του ορίου χρήσης       | Πράσινη κουκκίδα                                      |

## Έλεγχος Κατάστασης Token

Οι πάροχοι OAuth (Claude Code, GitHub Copilot, Cursor) χρειάζονται **περιοδική ανανέωση token**. Το `src/lib/tokenHealthCheck.ts` εκτελεί έναν χρονοπρογραμματιστή στο παρασκήνιο:

- **Κύκλος σάρωσης**: κάθε 60 δευτερόλεπτα (σάρωση στο `TICK_MS = 60 * 1000` στο `src/lib/tokenHealthCheck.ts:30`)
- **Διάστημα ελέγχου κατάστασης ανά σύνδεση**: προεπιλεγμένα 60 λεπτά (`DEFAULT_HEALTH_CHECK_INTERVAL_MIN = 60`)· μπορεί να διαμορφωθεί μέσω της βάσης δεδομένων ρυθμίσεων
- **Προληπτική ανανέωση σε 401**: διεκπεραιώνεται από τον interceptor κάθε σύνδεσης

### Κατάσταση Υγείας Token

```ts
interface TokenHealth {
  connectionId: string;
  provider: string;
  status: "valid" | "expiring_soon" | "expired" | "refresh_failed";
  expiresAt: string;
  lastRefresh: string;
  nextRefresh: string;
  consecutiveFailures: number;
}
```

### Διαμόρφωση

Η διαμόρφωση του ελέγχου κατάστασης των token διεκπεραιώνεται εσωτερικά από το `tokenHealthCheck.ts`.

## Αντιμετώπιση Προβλημάτων

### "Ο πάροχος εμφανίζεται υγιής, αλλά τα αιτήματα αποτυγχάνουν"

1. Ελέγξτε τα **προβλήματα αυτόματου πιλότου** — ίσως κάποιο μοντέλο έχει αποκλειστεί
2. Εξετάστε τα **πρόσφατα σφάλματα** για τη συγκεκριμένη κλάση σφάλματος
3. Δοκιμάστε τον **έλεγχο σύνδεσης** στην κάρτα του παρόχου
4. Ελέγξτε αν ο πάροχος υπόκειται σε **περιορισμό ρυθμού στην ανάντη υπηρεσία** (δεν είναι ορατό τοπικά)

### "Το όριο χρήσης εμφανίζεται υγιές, αλλά βλέπω αποκρίσεις 429"

- Το 429 σημαίνει ότι, σύμφωνα με τον πάροχο, έχετε εξαντλήσει το όριο χρήσης σας
- Η παρακολούθηση ορίου χρήσης του OmniRoute ενδέχεται να είναι **παρωχημένη** — τα δεδομένα του παρόχου είναι η έγκυρη πηγή
- Τα δεδομένα ορίου χρήσης ανανεώνονται αυτόματα μέσω της εσωτερικής παρακολούθησης ορίων χρήσης

### "Ο συνδυασμός αποτυγχάνει, αλλά όλοι οι στόχοι φαίνονται υγιείς"

- Ελέγξτε τον πίνακα ελέγχου **υγείας συνδυασμών** για προβλήματα στη σειρά των στόχων
- Εξετάστε τα **συμβάντα εφεδρικής μετάβασης** — ίσως ο συνδυασμός εξαντλεί τις επιλογές του πολύ γρήγορα
- Επαληθεύστε ότι η **στρατηγική** ταιριάζει στην περίπτωση χρήσης σας (προτεραιότητα έναντι κυκλικής εναλλαγής έναντι αυτόματης επιλογής)

### "Ο έλεγχος υγείας της βάσης δεδομένων αποτυγχάνει"

- Εκτελέστε `sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"`
- Αν η απόκριση είναι "ok" — πρόκειται για ψευδή συναγερμό, ο έλεγχος υγείας είναι υπερβολικά αυστηρός
- Αν η απόκριση είναι οτιδήποτε άλλο — **διακόψτε το OmniRoute** και ακολουθήστε τον [οδηγό ανάκαμψης από καταστροφή](./DATABASE_GUIDE.md#disaster-recovery)

### "Η πίεση στη μνήμη σωρού είναι κρίσιμη"

```bash
# Ελέγξτε τον τρέχοντα σωρό
node -e "console.log(process.memoryUsage())"

# Ενεργοποιήστε χειροκίνητα τη συλλογή απορριμμάτων (εάν χρησιμοποιείται το --expose-gc)
node --expose-gc -e "global.gc(); console.log(process.memoryUsage())"

# Μειώστε τα ταυτόχρονα αιτήματα (ρυθμίστε το μέσω της σελίδας Ρυθμίσεων του πίνακα ελέγχου και όχι μέσω μεταβλητής περιβάλλοντος)
# Δεν υπάρχει μεταβλητή περιβάλλοντος `MAX_CONCURRENT_REQUESTS` — διαμορφώστε το στις Ρυθμίσεις → Ταυτόχρονη εκτέλεση.
```
