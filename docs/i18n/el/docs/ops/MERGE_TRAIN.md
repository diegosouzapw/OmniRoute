Από την έκδοση v3.8.49 (WS3.2/WS3.4 του πλάνου ποιότητας/ταχύτητας), η προεπιλεγμένη διαδρομή συγχώνευσης για
ελεγμένα PRs προς το `release/vX.Y.Z` είναι η **ουρά συγχώνευσης του Mergify** (`.mergify.yml`)·
η **μη αυτόματη αμαξοστοιχία συγχώνευσης** που τεκμηριώνεται παρακάτω είναι η ΕΦΕΔΡΙΚΗ ΛΥΣΗ — χρησιμοποιείται κατά τη διάρκεια συμβάντων,
παγώματος έκδοσης ή αν αλλάξει ποτέ το πρόγραμμα Ανοιχτού Κώδικα του Mergify.

## Προεπιλεγμένη διαδρομή: η ουρά του Mergify

1. Το PR ελέγχεται/εγκρίνεται ως επιτυχές από τις καμπάνιες και εγκρίνεται από την πύλη ⭐
   πριν από τη συγχώνευση του κατόχου (η αναφορά + η απόφαση ανά στοιχείο — βλ. `/merge-prs` Βήμα 0.75).
2. Ο κάτοχος (ή η συνεδρία που ενεργεί βάσει της απόφασης του κατόχου) εφαρμόζει την ετικέτα **`queue`**.
   Η ετικέτα ΑΠΟΤΕΛΕΙ την έγκριση συγχώνευσης· το Mergify απλώς την εκτελεί.
3. Το Mergify επικυρώνει τα PR που βρίσκονται στην ουρά **σειριακά** (ένα κάθε φορά) με βάση τις γρήγορες πύλες
   και τα συγχωνεύει (squash). Η ομαδοποίηση + η αυτόματη διχοτόμηση αποτελούν επί πληρωμή βαθμίδα του Mergify
   ("Cannot use Merge Queue batch" στο δωρεάν πλάνο, #7220), επομένως το `.mergify.yml` δεν ορίζει
   `batch_size`· η ομαδοποίηση παραμένει ευθύνη της χειροκίνητης ακολουθίας συγχώνευσης παρακάτω. Ένα PR του οποίου
   οι έλεγχοι εξακολουθούν να εκκρεμούν μετά το `checks_timeout` (240 λεπτά = 2× το μετρημένο p95 του
   `quality.yml`) αφαιρείται από την ουρά αντί να την ακινητοποιεί.
4. Μετά τη συγχώνευση, η συνεχής ροή εργασίας επιτυχούς έκδοσης επικυρώνει τη νέα κορυφή κατά το push
   και ανοίγει ένα ζήτημα απόδοσης ευθύνης αν ο συνδυασμός παρουσίασε παλινδρόμηση (ποτέ δεν πραγματοποιεί αυτόματη επαναφορά).

Προστατευτικοί κανόνες (αντικατοπτρίζουν τους Αυστηρούς Κανόνες #21/#22 του `CLAUDE.md`):

- **Ενεργό πάγωμα έκδοσης** → ΜΗΝ προσθέτετε ετικέτες σε PR που στοχεύουν τον παγωμένο κλάδο· αλλάξτε πρώτα τον στόχο
  στον ενεργό `release/vX+1`.
- **PR άλλης συνεδρίας που βρίσκεται σε εξέλιξη** → μην του προσθέτετε ποτέ ετικέτα· μόνο η συνεδρία που το κατέχει τοποθετεί
  τη δική της εργασία στην ουρά.
- Οι αλλαγές που αφορούν μόνο δοκιμές και τα PR με ετικέτα `hotfix` εκτελούν ήδη μειωμένο CI (βλ.
  `RELEASE_CHECKLIST.md` → Γρήγορη Διαδρομή Επείγουσας Διόρθωσης)· οι συνθήκες της ουράς αποδέχονται οποιοδήποτε
  σύνολο ελέγχων εκτελέστηκε πραγματικά (`#check-failure=0` + `#check-pending=0`).

## Εφεδρική λύση: η μη αυτόματη αμαξοστοιχία συγχώνευσης

Χρησιμοποιείται όταν η ουρά δεν είναι διαθέσιμη. Αυτό κωδικοποιεί την πρακτική που διεκπεραίωσε 33 PRs σε
μία ημέρα κατά τη διάρκεια του κύκλου v3.8.47:

1. **Συγκεντρώστε την παρτίδα** (~10–30 ελεγμένα+εγκεκριμένα PRs). Ελέγξτε για συγκρούσεις `linked:`
   (ίδια `tap.testFiles`, ίδια τμήματα του CHANGELOG) και σειριοποιήστε τα.
2. **Επικυρώστε ΜΙΑ ΦΟΡΑ**: σε ένα απομονωμένο worktree από την κορυφή της έκδοσης, συγχωνεύστε τοπικά όλες τις κεφαλές
   της παρτίδας και, στη συνέχεια, εκτελέστε τη σουίτα που είναι ισοδύναμη με εκείνη της έκδοσης
   (`npm run check:release-green`, προσθέστε `--with-build` πριν από μια έκδοση).
   Το `scripts/release/merge-train.sh <base> <PR#>…` αυτοματοποιεί τα βήματα 1–2 (τα PRs με συγκρούσεις
   αποβάλλονται, η αμαξοστοιχία συνεχίζει). Η πλήρης λειτουργία εκτελεί `npm run test:unit` — τον
   εκτελεστή προσαρμοσμένο στο μηχάνημα (`--test-concurrency=20`), **όχι** τα δύο διαδοχικά τμήματα CI
   4 πυρήνων, τα οποία εκτελούσαν την κυρίαρχη φάση σε ~25% ενός μηχανήματος 16 πυρήνων (διορθώθηκε
   2026-07-18). Το `--fast` (εκκαθαρίσεις ενδοημερήσιων υπερ-αμαξοστοιχιών, εγκεκριμένο από τον κάτοχο στις 2026-07-18)
   διατηρεί κάθε στατική πύλη + vitest, αλλά εκτελεί μόνο τα αρχεία node:test που άλλαξαν από τα
   PRs που επιβιβάστηκαν· η ΠΛΗΡΗΣ σουίτα πρέπει παρ' όλα αυτά να εκτελείται τουλάχιστον μία φορά την ημέρα στην
   αθροιστική κορυφή (μία αμαξοστοιχία χωρίς `--fast`).
3. **Πράσινο** → συγχωνεύστε τα PRs διαδοχικά (επανελέγχοντας τα `state,headRefOid` πριν από το καθένα —
   ένα PR του οποίου η κεφαλή μετακινήθηκε επιστρέφει για έλεγχο). Αποδείξτε ότι η καθαρή διαφορά κάθε συγχώνευσης είναι η
   αλλαγή του ίδιου του PR (χωρίς επαναφορές από αυτόματη επίλυση: ελέγξτε το `git diff --stat` για
   διαγραφές εκτός πεδίου).
4. **Κόκκινο** → διχοτομήστε την παρτίδα σε μισά (επικυρώστε κάθε μισό) αντί να κάνετε επανεπικύρωση
   ένα προς ένα· επιστρέψτε το προβληματικό PR στην ουρά ελέγχου μαζί με τα αποδεικτικά στοιχεία.
5. **Ποτέ**: συγχώνευση στον παγωμένο κλάδο κατά τη διάρκεια παγώματος· `git stash` οπουδήποτε·
   αδιάκριτη επανεκτέλεση του CI με την ελπίδα ότι ένα κόκκινο αποτέλεσμα θα εξαφανιστεί (κανόνας: το κόκκινο αποτέλεσμα είναι πληροφορία).

## Διαβάθμιση (γιατί η ουρά είναι ασφαλής μόνο με τις γρήγορες πύλες)

- **Ανά PR** (γρήγορες πύλες του quality.yml): δοκιμές που επηρεάζονται βάσει TIA + πλήρης εκτέλεση μονάδων σε 4 τμήματα +
  vitest + σύνολο lint + έλεγχος τύπων + ακεραιότητα τεκμηρίωσης/changelog.
- **Ανά παρτίδα/κορυφή** (συνεχές release-green): ΣΚΛΗΡΕΣ πύλες `--quick` σε κάθε push προς
  τον κλάδο έκδοσης· πλήρεις σαρώσεις `--with-build --full-ci` 3×/ημέρα.
- **Ανά έκδοση** (ci.yml στο PR έκδοσης): ο πλήρης πίνακας, συμπεριλαμβανομένων των E2E ×9,
  τεχνουργήματος πακέτου + αρχικού ελέγχου εκκίνησης του tarball, κάλυψης/αναστολέων.

Τίποτα δεν επικυρώνεται λιγότερο από πριν — η βαριά επιφάνεια απλώς εκτελείται ανά παρτίδα/κορυφή
αντί ανά PR, κάτι που εξαλείφει τις O(N) διαδρομές μετ' επιστροφής.

## Προαπαιτούμενα νέου checkout για το `merge-train.sh`

Το script εκτελεί έναν **προκαταρκτικό έλεγχο** άμεσης αποτυχίας στο ριζικό checkout (πριν από οποιαδήποτε εργασία
σε worktree), ώστε μια ελαττωματική εγκατάσταση να μην μπορεί ποτέ να παρουσιαστεί ως κόκκινη αμαξοστοιχία:

1. `npm ci` και, στη συνέχεια, εκτελέστε το postinstall του `bun` που αποκλείει το npm:
   `(cd node_modules/bun && node install.js)` — διαφορετικά τα `check:provider-consistency`
   και `check:known-symbols` (και τα δύο `bun scripts/…`) αποτυγχάνουν στην αμαξοστοιχία ΚΑΙ στη βάση χωρίς
   γραμμή παραβίασης.
2. Κανένα ανεπιθύμητο `node_modules/node_modules` (ένα διπλό δέντρο εξαρτήσεων· το React φορτώνεται δύο φορές
   και οι σουίτες UI του vitest αποτυγχάνουν αμέσως).
3. Το `node_modules/.bin/tsc` να υπάρχει και να είναι εκτελέσιμο (λείπει από μια μερική εγκατάσταση).

Η αμαξοστοιχία εκτελεί το δεσμευτικό `npm run check:cycles:ratchet`· το σκέτο `npm run check:cycles`
είναι συμβουλευτικό (παραθέτει τα SCCs και τερματίζει με μη μηδενικό κωδικό ακόμη και σε μια υγιή βάση).
