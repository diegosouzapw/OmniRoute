> **Εν συντομία**: Το OmniRoute παρακολουθεί τη χρήση token κάθε αιτήματος, υπολογίζει το κόστος, επιβάλλει όριο χρήσης ανά κλειδί API και εμφανίζει αναλυτικά στοιχεία στον πίνακα ελέγχου. Αυτός ο οδηγός εξηγεί πώς λειτουργούν όλα αυτά.

**Πηγές:**

- `open-sse/services/usage.ts` (~70KB) — κύρια παρακολούθηση χρήσης
- `src/lib/usageAnalytics.ts` (~10KB) — συγκέντρωση δεδομένων για τον πίνακα ελέγχου
- `src/lib/db/quotaSnapshots.ts` — ιστορικά δεδομένα ορίων χρήσης
- `src/lib/db/usage*.ts` — πολλαπλές μονάδες βάσης δεδομένων σχετικές με τη χρήση

## Επισκόπηση

Κάθε αίτημα που διέρχεται από το OmniRoute δημιουργεί μια **εγγραφή χρήσης**, η οποία καταγράφει:

- **Ταυτότητα**: ποιο κλειδί API, ποιος πάροχος, ποιο μοντέλο, ποιος συνδυασμός
- **Token**: token προτροπής, token ολοκλήρωσης, αποθηκευμένα στην κρυφή μνήμη token, σύνολο
- **Κόστος**: ποσό σε USD (υπολογίζεται από τα δεδομένα τιμολόγησης)
- **Χρονισμός**: καθυστέρηση, χρονικές σημάνσεις έναρξης/λήξης
- **Κατάσταση**: επιτυχία, σφάλμα, περιορισμός ρυθμού κ.λπ.

Αυτές οι εγγραφές συγκεντρώνονται σε **αναλυτικά στοιχεία**, διατηρούνται ως **στιγμιότυπα ορίων χρήσης** και χρησιμοποιούνται για την επιβολή **ορίων προϋπολογισμού ανά κλειδί**.

```
Αίτημα ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    αναλυτικά  όριο    χρέωση
                    (πίνακας) (επιβολή) (εξαγωγή)
```

## Τι καταγράφεται

Η υπηρεσία `usage.ts` καταγράφει ένα **συμβάν χρήσης** για κάθε αίτημα:

| Πεδίο              | Τύπος   | Πηγή                                                                      |
| ------------------ | ------- | ------------------------------------------------------------------------- |
| `id`               | string  | UUID που δημιουργείται κατά την καταγραφή                                 |
| `apiKeyId`         | string  | Το κλειδί API που ξεκίνησε το αίτημα                                      |
| `provider`         | string  | Αναγνωριστικό παρόχου (openai, anthropic κ.λπ.)                           |
| `model`            | string  | Αναγνωριστικό μοντέλου (gpt-5, claude-opus-4-6 κ.λπ.)                     |
| `comboId`          | string? | Αναγνωριστικό συνδυασμού, εάν η δρομολόγηση έγινε μέσω συνδυασμού         |
| `promptTokens`     | number  | Από την απόκριση του upstream                                             |
| `completionTokens` | number  | Από την απόκριση του upstream                                             |
| `cachedTokens`     | number  | Token από επιτυχίες κρυφής μνήμης (κρυφή μνήμη προτροπών Anthropic κ.λπ.) |
| `totalTokens`      | number  | προτροπή + ολοκλήρωση                                                     |
| `costUsd`          | number  | Υπολογίζεται από τα δεδομένα τιμολόγησης                                  |
| `latencyMs`        | number  | Συνολική διάρκεια αιτήματος                                               |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`                |
| `errorClass`       | string? | Κατηγορία σφάλματος εάν status != success                                 |
| `timestamp`        | string  | ISO 8601 UTC                                                              |
| `metadata`         | object  | Προσαρμοσμένα δεδομένα που εισάγονται από πρόσθετα                        |

### Από πού προέρχονται τα token

Τα token εξάγονται από την απόκριση του upstream παρόχου στον **χειριστή απόκρισης**:

```ts
// Από το open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

Για παρόχους που δεν επιστρέφουν δεδομένα χρήσης (ορισμένοι πάροχοι web-cookie), το OmniRoute **εκτιμά** τα token χρησιμοποιώντας την ευρετική μέθοδο `~4 chars per token` (δείτε το `open-sse/services/autoCombo/pipelineRouter.ts`).

### Token κρυφής μνήμης

Το OmniRoute παρακολουθεί τα `cached_tokens` ξεχωριστά από τα `prompt_tokens`, επειδή:

- Η κρυφή μνήμη προτροπών του Anthropic χρεώνει μειωμένη τιμή για τα token κρυφής μνήμης (10% της κανονικής)
- Ορισμένοι πάροχοι επιστρέφουν `cache_read_input_tokens`, τα οποία πρέπει να τιμολογούνται διαφορετικά
- Τα αναλυτικά στοιχεία μπορούν να εμφανίζουν το **ποσοστό επιτυχιών κρυφής μνήμης** = `cached_tokens / prompt_tokens`

## Υπολογισμός Κόστους

Τα κόστη υπολογίζονται από **δεδομένα τιμολόγησης** που συγχρονίζονται από το LiteLLM (`src/lib/pricingSync.ts`):

| Μοντέλο           | Είσοδος $/1M | Έξοδος $/1M | Σε cache $/1M |
| ----------------- | ------------ | ----------- | ------------- |
| gpt-5             | $2.50        | $10.00      | —             |
| claude-opus-4-6   | $15.00       | $75.00      | $1.50         |
| claude-sonnet-4-5 | $3.00        | $15.00      | $0.30         |
| gemini-2.5-pro    | $1.25        | $10.00      | —             |

Ο τύπος υπολογισμού του κόστους (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Γιατί αφαιρούνται τα αποθηκευμένα σε cache tokens από το prompt;** Το τμήμα που βρίσκεται στην cache τιμολογείται ξεχωριστά· η χρέωση της τιμής εισόδου για ολόκληρο το prompt θα οδηγούσε σε υπερβολικό υπολογισμό.

### Συγχρονισμός Τιμολόγησης

Τα δεδομένα τιμολόγησης συγχρονίζονται αυτόματα από το LiteLLM μέσω του endpoint `/api/pricing/sync` (ενεργοποιείται από την ενσωματωμένη εργασία cron και όχι από κάποια μεταβλητή περιβάλλοντος διαθέσιμη στον χρήστη):

```bash
# Μη αυτόματη ενεργοποίηση
curl -X POST http://localhost:20128/api/pricing/sync
```

Για μοντέλα χωρίς δεδομένα τιμολόγησης, το OmniRoute καταφεύγει σε **εκτίμηση του κόστους** χρησιμοποιώντας εσωτερικές μέσες τιμές (οι οποίες προέρχονται από τα δεδομένα τιμολόγησης του LiteLLM).

## Συγκέντρωση κατά Εύρος Ημερομηνιών

Η μονάδα `usageAnalytics.ts` υπολογίζει τα widget του πίνακα ελέγχου από ανεπεξέργαστα δεδομένα χρήσης. Υποστηρίζει 7 χρονικά εύρη:

| Εύρος    | Χρονικό διάστημα                          | Περίπτωση χρήσης                     |
| -------- | ----------------------------------------- | ------------------------------------ |
| `1d`     | Τελευταίες 24 ώρες                        | Εντοπισμός ωριαίων αιχμών κόστους    |
| `7d`     | Τελευταίες 7 ημέρες                       | Εβδομαδιαία ανασκόπηση               |
| `30d`    | Τελευταίες 30 ημέρες                      | Μηνιαία χρέωση                       |
| `90d`    | Τελευταίες 90 ημέρες                      | Τριμηνιαία ανάλυση                   |
| `ytd`    | Από την 1η Ιανουαρίου του τρέχοντος έτους | Παρακολούθηση ετήσιου προϋπολογισμού |
| `all`    | Από την αρχή                              | Συνολικά στατιστικά                  |
| `custom` | Έναρξη/λήξη που ορίζει ο χρήστης          | Έλεγχοι, ad-hoc ερωτήματα            |

### Widget Πίνακα Ελέγχου που Υπολογίζονται

Για οποιοδήποτε εύρος ημερομηνιών, το επίπεδο αναλυτικών στοιχείων υπολογίζει:

| Widget                             | Περιγραφή                                                                  |
| ---------------------------------- | -------------------------------------------------------------------------- |
| **Κάρτες σύνοψης**                 | Συνολικά αιτήματα, συνολικό κόστος, συνολικά tokens, ποσοστό επιτυχίας     |
| **Γράφημα ημερήσιας τάσης**        | Κόστος + tokens ανά ημέρα, σε στοίβα ανά μοντέλο                           |
| **Θερμικός χάρτης δραστηριότητας** | Πλέγμα ώρας της ημέρας × ημέρας της εβδομάδας, χρώμα = αριθμός αιτημάτων   |
| **Ανάλυση ανά μοντέλο**            | Κυκλικό γράφημα κόστους ανά μοντέλο                                        |
| **Ανάλυση ανά πάροχο**             | Ραβδόγραμμα αιτημάτων ανά πάροχο                                           |
| **Κορυφαία κλειδιά API**           | Πίνακας με τα 10 κορυφαία κλειδιά βάσει κόστους                            |
| **Ανάλυση σφαλμάτων**              | Ποσοστό σφαλμάτων με την πάροδο του χρόνου, κορυφαίες κατηγορίες σφαλμάτων |

### Πρόσβαση μέσω Προγραμματισμού

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // εγγραφές ιστορικού χρήσης
  "7d",                 // χρονικό εύρος: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // αντιστοίχιση σύνδεσης παρόχου (connectionId → όνομα λογαριασμού)
  {
    startDate: "2025-01-01",  // προαιρετικό: για το εύρος "custom"
    endDate: "2025-06-01",   // προαιρετικό: για το εύρος "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (λεπτά)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Επιβολή ορίων χρήσης

Το όριο χρήσης ανά κλειδί API επιβάλλεται σε δύο σημεία:

1. **Ελαστικό όριο** (`quotaWarnAt`): προειδοποίηση στον πίνακα ελέγχου όταν η χρήση υπερβαίνει το όριο
2. **Αυστηρό όριο** (`quotaLimit`): το αίτημα απορρίπτεται με HTTP 429 όταν το όριο ξεπεραστεί

### Διαμόρφωση

```ts
// Ανά κλειδί API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — εμφάνιση προειδοποίησης
  quotaLimit: 10_00,    // $10.00 — αυστηρή διακοπή
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Ροή επιβολής

```
Αίτημα ──▶ quotaCheck()
             │
             ├── Εντός ορίου;  ──▶ αποδοχή
             │
             └── Υπέρβαση ορίου;  ──▶ 429 Πάρα πολλά αιτήματα
                                      με κεφαλίδα Retry-After
```

### Στιγμιότυπα ορίων χρήσης

Ο πίνακας `quotaSnapshots` αποθηκεύει την **ιστορική κατάσταση των ορίων χρήσης** για ανάλυση τάσεων:

| Πεδίο | Περιγραφή |
| ----------- | ------------------------------------------ | ------ | ------- |
| `apiKeyId` | Το κλειδί που παρακολουθείται |
| `window` | "day" | "week" | "month" |
| `used` | Κόστος που χρησιμοποιήθηκε σε αυτό το παράθυρο (σεντ) |
| `limit` | Το όριο (σεντ) |
| `resetAt` | Πότε γίνεται επαναφορά του παραθύρου |
| `createdAt` | Πότε λήφθηκε το στιγμιότυπο |

Τα στιγμιότυπα λαμβάνονται **σε κάθε αίτημα** που χρησιμοποιεί κόστος > 0 και χρησιμοποιούνται για:

- Την απεικόνιση της γραμμής προόδου του ορίου χρήσης στον πίνακα ελέγχου
- Την εμφάνιση γραφημάτων τάσης ορίων χρήσης 30 ημερών
- Την ενεργοποίηση ειδοποιήσεων όταν η χρήση πλησιάζει το όριο

### Υποβολή ερωτημάτων για αναλυτικά στοιχεία χρήσης

Η πρόσβαση στα δεδομένα χρήσης πραγματοποιείται μέσω του πίνακα ελέγχου ή των εργαλείων MCP και όχι μέσω άμεσων καταληκτικών σημείων εξαγωγής REST. Διαθέσιμα αναλυτικά στοιχεία:

- **`/api/usage/analytics`** — συγκεντρωτικές μετρήσεις χρήσης (ομαδοποίηση ανά μοντέλο, πάροχο, κλειδί)
- **`/api/usage/quota`** — τρέχουσα κατάσταση ορίου χρήσης ανά κλειδί API
- **`/api/usage/history`** — αρχεία καταγραφής ιστορικού αιτημάτων

```json
{
  "tool": "omniroute_cost_report",
  "args": { "period": "week" }
}
```

## Διατήρηση και εκκαθάριση

Τα δεδομένα χρήσης αυξάνονται κατά ~1-10KB ανά αίτημα. Σε μεγάλη κλίμακα, αυτό μπορεί να είναι σημαντικό.

### Ρυθμίσεις διατήρησης

Η διατήρηση του ιστορικού χρήσης διαμορφώνεται μέσω των Ρυθμίσεων βάσης δεδομένων στο περιβάλλον χρήστη ή μέσω του `/api/settings/database`.

Από προεπιλογή, το ιστορικό χρήσης διατηρείται για **90 ημέρες**.

### Εκκαθάριση

Οι παλιές εγγραφές εκκαθαρίζονται από το `src/lib/db/cleanup.ts`:

- Ενεργοποιείται από τη διεργασία cron στο παρασκήνιο
- Διαγράφει από το `usage_history` εγγραφές παλαιότερες από τη διαμορφωμένη ρύθμιση διατήρησης `usageHistory`

### Εκτίμηση αποθηκευτικού χώρου

| Ρυθμός αιτημάτων       | Αποθήκευση 30 ημερών | Αποθήκευση 90 ημερών |
| ---------------------- | -------------------- | -------------------- |
| 100 αιτήματα/ημέρα     | ~3MB                 | ~9MB                 |
| 1,000 αιτήματα/ημέρα   | ~30MB                | ~90MB                |
| 10,000 αιτήματα/ημέρα  | ~300MB               | ~900MB               |
| 100,000 αιτήματα/ημέρα | ~3GB                 | ~9GB                 |

Για πολύ υψηλή κίνηση, εξετάστε τα εξής:

- Μείωση της περιόδου διατήρησης μέσω των Ρυθμίσεων βάσης δεδομένων
- Χρήση του `aggregated_metrics` αντί για ανεπεξέργαστες εγγραφές (μόνο για αναλυτικά στοιχεία)

## Συμβουλές βελτιστοποίησης κόστους

### 1. Χρησιμοποιήστε το κατάλληλο μοντέλο

```bash
# Γρήγορη απάντηση — χρησιμοποιήστε οικονομικό + γρήγορο
curl -d '{"model":"auto/fast","messages":[...]}'

# Σύνθετη εργασία — δώστε προτεραιότητα στην ποιότητα
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Ενεργοποιήστε την προσωρινή αποθήκευση

Η προσωρινή αποθήκευση προτροπών της Anthropic εξοικονομεί **90% σε επαναλαμβανόμενο περιεχόμενο**:

```ts
// Η προσωρινή αποθήκευση γίνεται αυτόματα — απλώς συμπεριλάβετε την ίδια μεγάλη προτροπή συστήματος
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Θα αποθηκευτεί αυτόματα στην προσωρινή μνήμη
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Χρησιμοποιήστε συμπίεση

Η συμπίεση RTK + Caveman εξοικονομεί **15-95% σε συνεδρίες με εκτεταμένη χρήση εργαλείων**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Ορίστε ποσοστώσεις ανά κλειδί

Να ορίζετε πάντα το `quotaLimit` για να αποτρέπετε ανεξέλεγκτα κόστη:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Όριο $10/μήνα
```

### 5. Ελέγξτε τους κορυφαίους καταναλωτές

Χρησιμοποιήστε τον πίνακα ελέγχου ή το **`/api/usage/analytics`** για να ομαδοποιήσετε ανά κλειδί API και να ταξινομήσετε ανά κόστος:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Αντιμετώπιση προβλημάτων

### "Το κόστος είναι υψηλότερο από το αναμενόμενο"

1. Ελέγξτε το **`/api/usage/analytics?groupBy=model`** — εντοπίστε το ακριβό μοντέλο
2. Ελέγξτε το **`/api/usage/analytics?groupBy=apiKey`** — εντοπίστε τον μεγάλο καταναλωτή
3. Επαληθεύστε ότι τα δεδομένα τιμολόγησης είναι ενημερωμένα: `POST /api/pricing/sync`

### "Λείπουν εγγραφές"

- Ελέγξτε τις ρυθμίσεις διατήρησης της βάσης δεδομένων στην περιοχή Πίνακας ελέγχου → Βάση δεδομένων → Εκκαθάριση — οι παλιές εγγραφές διαγράφονται από την περιοδική εργασία εκκαθάρισης (`src/lib/db/cleanup.ts`)
- Ελέγξτε για σφάλματα στο `src/lib/db/usage*.ts` — οι αποτυχίες εγγραφής στη βάση δεδομένων καταγράφονται, αλλά δεν εμφανίζονται
- Επαληθεύστε ότι το αίτημα έφτασε πράγματι στο `chatCore` — ελέγξτε τη συνδυαστική δρομολόγηση

### "Η ποσόστωση δεν επιβάλλεται"

- Ελέγξτε τη ρύθμιση `quotaLimit` του κλειδιού
- Επαληθεύστε ότι το `quotaWindow` έχει οριστεί σωστά
- Αναζητήστε εγγραφές `quotaSnapshots` — θα πρέπει να δημιουργούνται σε κάθε αίτημα
