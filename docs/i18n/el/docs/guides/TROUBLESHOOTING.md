## Γρήγορη αναφορά

**Νέοι στο OmniRoute;** Ξεκινήστε εδώ — αυτά λύνουν το 90% των προβλημάτων:

| Βλέπω αυτό                       | Τι σημαίνει                                            | Τι να κάνω                                                                                                         |
| -------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| "Δεν είναι δυνατή η σύνδεση"     | Το OmniRoute δεν εκτελείται                            | Εκτελέστε `omniroute` ή `docker restart omniroute`                                                                 |
| "Μη έγκυρο κλειδί API"           | Το κλειδί σας είναι λανθασμένο ή έχει λήξει            | Αντιγράψτε ξανά το κλειδί από τον ιστότοπο του παρόχου                                                             |
| "Υπέρβαση ορίου αιτημάτων"       | Στέλνετε υπερβολικά πολλά αιτήματα                     | Περιμένετε 1 λεπτό ή χρησιμοποιήστε `model: "auto"` για αυτόματη εναλλακτική δρομολόγηση                           |
| "Υπέρβαση ποσόστωσης"            | Έχετε εξαντλήσει τη δωρεάν/επί πληρωμή ποσόστωση       | Συνδέστε περισσότερους παρόχους ή χρησιμοποιήστε δωρεάν παρόχους (Kiro, Pollinations)                              |
| "Αργές αποκρίσεις"               | Ο πάροχος είναι απασχολημένος ή βρίσκεται μακριά       | Χρησιμοποιήστε `model: "auto/fast"` ή συνδέστε έναν ταχύτερο πάροχο (Groq, Cerebras)                               |
| "Χρησιμοποιήθηκε λάθος πάροχος"  | Το `auto` επέλεξε διαφορετικό πάροχο                   | Αυτό είναι φυσιολογικό! Το `auto` επιλέγει τον καλύτερο. Επιβάλετε συγκεκριμένο πάροχο με `model: "openai/gpt-4o"` |
| "502 Bad Gateway"                | Ο πάροχος είναι εκτός λειτουργίας                      | Περιμένετε και δοκιμάστε ξανά ή χρησιμοποιήστε `model: "auto"` για εναλλαγή παρόχων                                |
| "401 Unauthorized"               | Τα διαπιστευτήριά σας είναι λανθασμένα                 | Ελέγξτε το κλειδί API ή πραγματοποιήστε ξανά έλεγχο ταυτότητας μέσω OAuth                                          |

| "429 Too Many Requests"          | Έχει επιβληθεί περιορισμός ρυθμού αιτημάτων            | Περιμένετε 1 λεπτό ή συνδέστε περισσότερους παρόχους                                                               |

## Αναλυτική αντιμετώπιση προβλημάτων

---

### Περιορισμός ρυθμού αιτημάτων σε δωρεάν παρόχους (429 / 400 / 401)

**Σύμπτωμα**: Όταν χρησιμοποιείτε `model: "auto"` με δωρεάν παρόχους ή παρόχους χωρίς έλεγχο ταυτότητας (opencode, auggie κ.λπ.), λαμβάνετε κατά διαστήματα `HTTP 429`, `400` ή `401` αντί για απαντήσεις. Τα αιτήματα ολοκληρώνονται επιτυχώς όταν επαναλαμβάνετε την ίδια προτροπή λίγα λεπτά αργότερα, αλλά η αυτοματοποίηση (εργασίες cron, πράκτορες, δέσμες ενεργειών) διακόπτεται με την πρώτη αποτυχία.

**Βασική αιτία**: Συνδυάζονται τρεις ανεξάρτητοι τρόποι αποτυχίας:

1. **Περιορισμός ρυθμού από τον πάροχο (`429`)**: Τα δωρεάν επίπεδα μπορούν να επιβάλλουν ποσόστωση ανά χρονικό παράθυρο. Μια ριπή παράλληλων κλήσεων την εξαντλεί, οπότε το επόμενο αίτημα απορρίπτεται μέχρι να γίνει επαναφορά του παραθύρου.
2. **Προβληματικό μοντέλο σε λειτουργία διέλευσης (`400`/`401`)**: Οι ομάδες `auto/*` μπορούν να περιλαμβάνουν μοντέλα διέλευσης από το `opencode`, τα οποία είναι καταχωρισμένα στον κατάλογο αλλά δεν διαθέτουν ενεργά διαπιστευτήρια (π.χ. `oc/north-mini-code-free` → `401`). Ο αυτόματος δρομολογητής δοκιμάζει ένα, αποτυγχάνει και το σφάλμα μεταδίδεται πριν ενεργοποιηθεί η εναλλακτική δρομολόγηση.
3. **Ενίσχυση λόγω ταυτοχρονισμού (`429` υπό φόρτο)**: Όταν πολλαπλές συνεδρίες πρακτόρων/cron προσπελαύνουν ταυτόχρονα το `auto`, ο συνολικός ρυθμός αιτημάτων υπερβαίνει αυτόν που ανέχονται οι δωρεάν πάροχοι, με αποτέλεσμα νόμιμες κλήσεις να επισημαίνονται ως καταχρηστικές.

**Επαληθευμένη λύση (σύμφωνα με αναφορές της κοινότητας, 2026-08-10)**: ρυθμίστε τρεις μεταβλητές περιβάλλοντος, ώστε η εναλλαγή, ο ταυτοχρονισμός και η εναλλακτική δρομολόγηση να απορροφούν την αστάθεια του δωρεάν επιπέδου αντί να αποτυγχάνουν εξαιτίας της:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # μετάβαση σε άλλο μοντέλο/πάροχο σε 400/401 (παραλείπει προβληματικά μοντέλα διέλευσης)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ρητό ανώτατο όριο αποδοχής αιτημάτων βαρέος φόρτου (χωρίς προεπιλεγμένη ρύθμιση: κανένα όριο πλήθους αιτημάτων, δείτε τη σημείωση παρακάτω)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # αύξηση της οριοθετημένης αναμονής πέρα από την προεπιλογή RATE_LIMIT_MAX_WAIT_MS για αργές υπηρεσίες ανάντη
```

Ορίστε αυτές τις μεταβλητές στο περιβάλλον της διεργασίας OmniRoute (στον δαίμονα, π.χ. μέσω του plist του LaunchAgent ή του `systemctl edit`) και, στη συνέχεια, επανεκκινήστε το OmniRoute. Η σημαία εναλλαγής είναι ο μοναδικός μοχλός με τη μεγαλύτερη επίδραση: μετατρέπει μια οριστική αποτυχία σε διαφανή επανάληψη της προσπάθειας μέσω ενός υγιούς παρόχου στην ομάδα.

**Σημείωση**: Η `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` περιορίζει πόσα αιτήματα βαρέος φόρτου — μεγάλου περιβάλλοντος — εκτελούνται ταυτόχρονα· το όριο αποτελεί πύλη αποδοχής και όχι περιοριστή ρυθμού αιτημάτων του παρόχου. **Ενημέρωση #503-fanout:** αυτή η μεταβλητή δεν ορίζεται πλέον από προεπιλογή (εφαρμόζεται πλέον μόνο όταν ρυθμίζεται ρητά, όπως παραπάνω) — αντί γι' αυτό, η αποδοχή αιτημάτων βαρέος φόρτου ελέγχεται από έναν αυτόματα υπολογιζόμενο προϋπολογισμό byte (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), ο οποίος προσαρμόζεται βάσει του πραγματικού ορίου μνήμης του κεντρικού συστήματος. Επομένως, μια νέα ανάπτυξη θα πρέπει να εμφανίζει πολύ λιγότερες απορρίψεις `503 chat_admission_busy` χωρίς να απαιτείται καθόλου η ρύθμιση αυτής της μεταβλητής· η ρητή ρύθμισή της εδώ εξακολουθεί να λειτουργεί ακριβώς όπως τεκμηριώνεται. Οι ρητές παρακάμψεις του προϋπολογισμού byte περιορίζονται μεταξύ 8 MiB–2 GiB. Ένα `413 body_exceeds_budget` δεν είναι παροδικό: αυξήστε αυτόν τον προϋπολογισμό byte, μειώστε την τιμή της `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ή αυξήστε το όριο μνήμης της διεργασίας. Μια απόρριψη `inflight_bytes_budget` οφείλεται σε προσωρινό ανταγωνισμό πόρων και επιτρέπει εκ νέου προσπάθεια. Ο περιορισμός ρυθμού ανά πάροχο (`open-sse/services/rateLimitManager.ts`) ελέγχεται ξεχωριστά από τις `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` και `RATE_LIMIT_AUTO_ENABLE` — δείτε το `.env.example`.

**Πώς να επαληθεύσετε ότι λειτούργησε**: εκτελέστε τον agent/cron σας δύο φορές σε σύντομο χρονικό διάστημα και επιβεβαιώστε ότι και οι δύο εκτελέσεις ολοκληρώνονται επιτυχώς. Πριν από τη διόρθωση, η δεύτερη εκτέλεση συνήθως επιστρέφει σφάλμα `429`/`401`. Μετά τη διόρθωση, οι αποτυχίες (εάν υπάρχουν) επαναλαμβάνονται αυτόματα και η κλήση ολοκληρώνεται. Μπορείτε επίσης να εκτελέσετε `curl /monitoring/health` και να παρακολουθήσετε το πεδίο `rateLimitedUntil` στις συνδέσεις των παρόχων, καθώς και το `circuitBreakers.providerBreakers[].state` για τους επηρεαζόμενους παρόχους — η κατάσταση είναι μία από τις `CLOSED`, `DEGRADED`, `OPEN` ή `HALF_OPEN` (βλ. `src/shared/utils/circuitBreaker.ts`), ενώ ένας πάροχος που συνεχίζει να αποτυγχάνει θα μεταβεί από `CLOSED → DEGRADED → OPEN` προτού το παράθυρο επαναφοράς επιτρέψει τη διέλευση μιας δοκιμαστικής κλήσης (`HALF_OPEN`).

**Εάν εξακολουθείτε να βλέπετε 429**: ο ενεργός λογαριασμός για τον συγκεκριμένο πάροχο έχει πράγματι εξαντλήσει το _όριό_ του (όχι απλώς το όριο ρυθμού). Προσθέστε έναν δεύτερο λογαριασμό για τον ίδιο πάροχο στον πίνακα ελέγχου του OmniRoute → Providers → Accounts ή συμπεριλάβετε έναν ακόμη δωρεάν πάροχο (π.χ. `routeway`, `auggie`). Η εναλλαγή βοηθά μόνο σε παροδικά σφάλματα ρυθμού/400/401· η πλήρης εξάντληση του ορίου απαιτεί δεύτερο διαπιστευτήριο ή διαφορετικό πάροχο.

**Εάν βλέπετε 403 σε μοντέλα όρασης (`auto/vision`, `bazaarlink/*`)**: ο συνδεδεμένος λογαριασμός δεν διαθέτει πρόγραμμα επί πληρωμή που να περιλαμβάνει δυνατότητες όρασης ή το κλειδί API δεν έχει επαρκή δικαιώματα. Επαληθεύστε στον πίνακα ελέγχου του παρόχου ότι το εύρος δικαιωμάτων του κλειδιού περιλαμβάνει όραση/πολυτροπικότητα ή συνδέστε έναν λογαριασμό επί πληρωμή και διατηρήστε τον ως προορισμό για μοντέλα όρασης.

## Προειδοποιήσεις npm install (ERESOLVE / peer / deprecated)

Όταν εκτελείτε `npm install -g omniroute`, ενδέχεται να δείτε έναν καταιγισμό προειδοποιήσεων, όπως `npm warn ERESOLVE`, ειδοποιήσεις για peer dependencies και μηνύματα `deprecated`. **Αυτά είναι αναμενόμενα και ακίνδυνα.** Η εγκατάστασή σας ολοκληρώθηκε με επιτυχία εάν δείτε `added <N> packages` στην έξοδο.

Για να αποκρύψετε τις προειδοποιήσεις επίλυσης peer dependencies, χρησιμοποιήστε την υποστηριζόμενη μορφή εγκατάστασης του OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

Το `--legacy-peer-deps` αποκρύπτει μόνο το `ERESOLVE` και τις ειδοποιήσεις για peer dependencies. Οι ειδοποιήσεις κατάργησης παραμένουν ορατές επειδή προέρχονται από μεταβατικά πακέτα τρίτων· δεν υποδεικνύουν ότι η εγκατάσταση απέτυχε.

Οι προειδοποιήσεις προέρχονται από παρωχημένα εύρη peer dependencies σε πακέτα τρίτων που δεν ελέγχει το OmniRoute:

1. **Το `marked-terminal` απαιτεί `marked >=1 <16`, αλλά βρέθηκε `marked@18`** — στην πράξη λειτουργεί κανονικά· το εύρος peer dependency του upstream έργου είναι απλώς παρωχημένο.
2. **`deprecated prebuild-install@7.1.3`** — ένα μεταβατικό βοηθητικό εργαλείο ανάκτησης εγγενών δυαδικών αρχείων. Δεν
   χρησιμοποιείται για την εγκατάσταση του δεσμευμένου σε συγκεκριμένη έκδοση transport binding `wreq-js` και δεν υποδεικνύει ότι
   απέτυχε η ρύθμιση του transport του παρόχου web-cookie.

**Δεν απαιτείται καμία ενέργεια** — οι προειδοποιήσεις δεν μπορούν να αποκρυφθούν πλήρως χωρίς τη δημιουργία fork των upstream πακέτων.

## Προειδοποίηση αποκλεισμού npm install-scripts (καθολική εγκατάσταση)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

Κατά την εκτέλεση του `npm install -g omniroute`, οι νεότερες εκδόσεις του npm (v11+ και v12+) αποκλείουν από προεπιλογή τα σενάρια κύκλου ζωής πακέτων και εμφανίζουν μια προειδοποίηση install-scripts:

```
npm warn install-scripts 7 πακέτα είχαν σενάρια εγκατάστασης που αποκλείστηκαν επειδή δεν καλύπτονται από το allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Μπορεί να αγνοηθεί αυτή η προειδοποίηση;

**Εν μέρει, αλλά δεν συνιστάται η εκτέλεση χωρίς σενάρια.** Το OmniRoute περιλαμβάνει ομαλούς εναλλακτικούς μηχανισμούς: εάν δεν είναι δυνατή η φόρτωση των εγγενών bindings του `better-sqlite3` από το αυτοτελές bundle, η εφαρμογή χρησιμοποιεί διαδοχικά εναλλακτικούς drivers, όπως `node:sqlite` ή `sql.js` (δείτε [Επίλυση χρόνου εκτέλεσης SQLite](../ops/SQLITE_RUNTIME.md)). Ο διακομιστής θα εξακολουθήσει να εκκινείται, αλλά η εκτέλεση με εναλλακτικές υλοποιήσεις WASM, όπως το `sql.js`, απενεργοποιεί τη λειτουργία WAL (Write-Ahead Logging) του SQLite και αυξάνει την επιβάρυνση της μνήμης και του συγχρονισμού με τον δίσκο.

### Ποια σενάρια απαιτούνται πραγματικά;

Δεν είναι απαραίτητα για την εκτέλεση του OmniRoute όλα τα αποκλεισμένα σενάρια:

- **Απαραίτητα (`omniroute`, `better-sqlite3`):** Το OmniRoute εκτελείται από ένα αυτοτελές bundle εφαρμογής Next.js (`dist/`). Κατά την εγκατάσταση, το npm πραγματοποιεί λήψη ή μεταγλωττίζει τον εγγενή driver SQLite που αντιστοιχεί στο σύστημα φιλοξενίας, στον κατάλογο ανώτατου επιπέδου `node_modules/better-sqlite3/`. Στη συνέχεια, το σενάριο `postinstall` του OmniRoute (`scripts/build/postinstall.mjs`) επαληθεύει και αντιγράφει αυτά τα δυαδικά αρχεία για το συγκεκριμένο σύστημα φιλοξενίας στο `dist/node_modules/`, ώστε να έχει πρόσβαση σε αυτά ο αυτοτελής διακομιστής. Εάν αποκλειστεί το σενάριο postinstall του `omniroute`, αυτό το βήμα αντιγραφής παραλείπεται.
- **Προαιρετικά/μεταβατικά (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** Πρόκειται για βοηθητικά εργαλεία build, εργαλεία παρακολούθησης ή βοηθητικά προγράμματα του system keychain. Η έγκρισή τους αποτρέπει τις προειδοποιήσεις build, αλλά δεν απαιτούνται για τη βασική λειτουργικότητα δρομολόγησης.
- **Εξαιρούμενο (`onnxruntime-node`):** Μια προαιρετική εξάρτηση για τοπικά AI embeddings, η οποία **δεν** απαιτείται για την εκτέλεση του OmniRoute. Το σενάριο postinstall της πραγματοποιεί λήψη περίπου 300MB στοιχείων CUDA από το NuGet· μην τη συμπεριλάβετε στη λίστα επιτρεπόμενων, εκτός εάν σκοπεύετε ρητά να χρησιμοποιήσετε τοπική επιτάχυνση ONNX σε υποστηριζόμενο υλικό.

### Συνιστώμενη διόρθωση

Για να επιτρέψετε τα απαιτούμενα σενάρια εγκατάστασης κατά τη διάρκεια μιας καθολικής εγκατάστασης και να αποκρύψετε τις προειδοποιήσεις, περάστε το `--allow-scripts` για το OmniRoute και τις εγγενείς εξαρτήσεις του:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

Εναλλακτικά, για να το διαμορφώσετε μόνιμα για όλες τις καθολικές εγκαταστάσεις στον λογαριασμό χρήστη σας:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### Επαληθεύστε την εγκατάστασή σας

Μετά την εγκατάσταση, εκτελέστε το ενσωματωμένο διαγνωστικό εργαλείο για να βεβαιωθείτε ότι τα εγγενή bindings και το περιβάλλον χρόνου εκτέλεσης λειτουργούν σωστά:

```bash
omniroute doctor
```

## Gemini Web και Playwright Chromium

Εάν ένα αίτημα Gemini Web επιστρέψει `503` με μήνυμα ότι το Playwright Chromium
δεν είναι εγκατεστημένο, το πακέτο npm υπάρχει αλλά λείπει το εκτελέσιμο αρχείο του προγράμματος περιήγησης.
Το Playwright διατηρεί σκόπιμα τις λήψεις των προγραμμάτων περιήγησης ξεχωριστά από την εγκατάσταση του
πακέτου npm, επομένως αυτή η απόκριση είναι αναμενόμενη μέχρι να εγκατασταθεί το πρόγραμμα περιήγησης.

Για μια καθολική εγκατάσταση npm, εγκαταστήστε το Chromium από τον κατάλογο του πακέτου
OmniRoute, ώστε η κρυφή μνήμη του προγράμματος περιήγησης να ανήκει στην ίδια εγκατάσταση Playwright:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Επανεκκινήστε το OmniRoute μετά την εγκατάσταση και, στη συνέχεια, δοκιμάστε ξανά το αίτημα Gemini Web. Εάν
εκτελείτε το OmniRoute από εικόνα Docker, χρησιμοποιήστε την εικόνα `-web` (ή τον στόχο μεταγλώττισης
`runner-web`), η οποία περιλαμβάνει το Chromium και τις εξαρτήσεις του· η βασική εικόνα δεν
τα περιλαμβάνει.

## Ψευδώς θετικά αποτελέσματα antivirus

<a name="antivirus-false-positives"></a>

### Τα Avast/AVG θέτουν σε καραντίνα το `README.md` με την ένδειξη `MD:HttpRequest-inf[Susp]`

**Πρόκειται για ψευδώς θετικό αποτέλεσμα. Τίποτα δεν έχει μολυνθεί και δεν απαιτείται καμία ενέργεια.**

Τα Avast και AVG εκτελούν έναν ευρετικό έλεγχο που επισημαίνει αρχεία απλού κειμένου/Markdown τα οποία περιέχουν πολλούς
συνδέσμους που μοιάζουν με αιτήματα HTTP. Το `README.md` του OmniRoute περιλαμβάνεται στο πακέτο npm (αναφέρεται
στο `package.json` → `files`), επομένως, σε μια καθολική εγκατάσταση, τοποθετείται στο `node_modules/omniroute/README.md` —
και περιέχει περίπου 15 παραδείγματα `http://localhost:20128/...` (τα τελικά σημεία HTTP/SSE του MCP, τη διεύθυνση URL
`.well-known` του A2A και αποσπάσματα `curl`). Αυτή η πυκνότητα συνδέσμων αρκεί για να ενεργοποιήσει τον ευρετικό έλεγχο.

Αν αυτό άρχισε να συμβαίνει μόλις πρόσφατα: ο χαρακτήρας του αρχείου δεν άλλαξε. Το README επεκτάθηκε με
τον πίνακα τελικών σημείων του (προστέθηκαν τα MCP HTTP + SSE + A2A) και περισσότερα παραδείγματα `curl`, με αποτέλεσμα
να ξεπεράσει το όριο.

Το αρχείο είναι αδρανής τεκμηρίωση χωρίς κανένα εκτελέσιμο περιεχόμενο. Μπορείτε να το επαναφέρετε με ασφάλεια
από την καραντίνα.

**Τι να κάνετε:**

1. **Σταματήστε τις ειδοποιήσεις** — εξαιρέστε τον κατάλογο εγκατάστασης από το antivirus σας
   (Avast: Ρυθμίσεις → Εξαιρέσεις), προσθέτοντας τη διαδρομή του καθολικού `node_modules` ή/και τον
   κατάλογο δεδομένων του OmniRoute (`~/.omniroute/`).
2. **Αναφέρετε το ψευδώς θετικό αποτέλεσμα** — <https://www.avast.com/false-positive-file-form.php>,
   επισυνάπτοντας το `README.md` που τέθηκε σε καραντίνα. Αυτή είναι η διόρθωση που βοηθά όλους, καθώς
   πρόκειται για υπερβολική αντίδραση του ευρετικού ελέγχου του προμηθευτή σε ένα αρχείο κειμένου.

**Γιατί δεν το «διορθώνουμε» από τη δική μας πλευρά:** όλα τα παραδείγματα χρησιμοποιούν `http://localhost` και
το localhost δεν μπορεί να χρησιμοποιήσει `https` χωρίς την ταλαιπωρία των αυτοϋπογεγραμμένων πιστοποιητικών. Η αλλοίωση της τεκμηρίωσης για
να παρακαμφθεί ο ευρετικός έλεγχος ενός προμηθευτή θα δυσχέραινε όλους τους αναγνώστες μόνο και μόνο για να αντιμετωπιστεί ένα σφάλμα του σαρωτή.

### Το Kaspersky επισημαίνει την εφαρμογή για υπολογιστές ως `PDM:Trojan.Win32.Generic`

**Πρόκειται για ψευδώς θετικό αποτέλεσμα από έναν συμπεριφορικό ευρετικό έλεγχο. Τίποτα δεν έχει μολυνθεί.** Το πρόθεμα
`PDM:` του Kaspersky σημαίνει ότι η ετυμηγορία προέρχεται από τη Μονάδα Προληπτικής Άμυνας (System Watcher),
η οποία αξιολογεί τι _κάνει_ το πρόγραμμα εγκατάστασης αντί να το συγκρίνει με γνωστό κακόβουλο λογισμικό. Όταν
ενεργοποιείται, το Kaspersky «αναιρεί» ολόκληρη την εγκατάσταση — διαγράφοντας αρχεία που είχε ήδη
εγγράψει — με αποτέλεσμα η εφαρμογή να καταλήγει κατεστραμμένη ή να λείπει.

Τα αρχεία που επισημαίνει είναι τυπικά μέρη δηλωμένων εξαρτήσεων ανοιχτού κώδικα που περιλαμβάνονται στην
εφαρμογή για υπολογιστές, για παράδειγμα:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` και
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), η βιβλιοθήκη αυτοματοποίησης προγράμματος περιήγησης
  που χρησιμοποιείται για τη σύνδεση σε παρόχους μέσα από την εφαρμογή και για συνομιλίες μέσω προγράμματος περιήγησης.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — η καθηλωμένη σε συγκεκριμένη έκδοση εγγενής διασύνδεση `wreq-js` που χρησιμοποιείται για HTTP με αποτύπωμα προγράμματος περιήγησης σε παρόχους
  που βασίζονται σε web cookies (το `<arch>` είναι `x64` ή `arm64`).

**Γιατί ενεργοποιείται:** το πρόγραμμα εγκατάστασης για Windows **δεν διαθέτει ακόμη υπογραφή κώδικα**, επομένως ένα ανυπόγραφο πρόγραμμα εγκατάστασης NSIS
δεν έχει καμία φήμη και οι συμπεριφορικοί ευρετικοί έλεγχοι λειτουργούν με τη μέγιστη επιθετικότητα. Σε συνδυασμό
με μια ενσωματωμένη εγγενή βιβλιοθήκη DLL και εκατοντάδες αρχεία `.js` που εγγράφονται κάτω από το
`%LOCALAPPDATA%\Programs\OmniRoute` (συμπεριλαμβανομένων καταλόγων πακέτων με επίθεμα κατακερματισμού από την
αυτόνομη έκδοση του Next.js), αυτό αρκεί για να ενεργοποιήσει τον ευρετικό έλεγχο. Η υπογραφή κώδικα έχει προγραμματιστεί·
μέχρι να υλοποιηθεί, αυτό ενδέχεται να επαναλαμβάνεται σε νέες εκδόσεις.

**Τι να κάνετε:**

1. **Επαληθεύστε πρώτα τη λήψη σας** (έτσι αποκλείεται η περίπτωση παραποιημένου αρχείου). Κάθε έκδοση δημοσιεύει το
   `latest.yml`, του οποίου το πεδίο `sha512` (base64) καλύπτει το πρόγραμμα εγκατάστασης
   `OmniRoute.Setup.<version>.exe`. Στο PowerShell, από τον φάκελο που περιέχει το πρόγραμμα εγκατάστασης:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Η έξοδος πρέπει να αντιστοιχεί στο `latest.yml` → `sha512`. Αν δεν αντιστοιχεί, διαγράψτε το αρχείο και
   πραγματοποιήστε ξανά λήψη μόνο από τη [σελίδα εκδόσεων του GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Επαναφορά + εξαίρεση** — επαναφέρετε από την καραντίνα τα στοιχεία που αφαιρέθηκαν κατά την αναίρεση και προσθέστε μια εξαίρεση
   για το `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Ρυθμίσεις → Απειλές και εξαιρέσεις)
   και, στη συνέχεια, επανεγκαταστήστε.

   που υποβάλλονται από χρήστες επιταχύνουν πραγματικά την προσθήκη στη λίστα επιτρεπόμενων.

## Συμβατότητα με το Node.js

<a name="nodejs-compatibility"></a>

### Η σελίδα σύνδεσης καταρρέει ή εμφανίζει το σφάλμα "Module self-registration"

**Αιτία:** Εκτελείτε μια έκδοση του Node.js εκτός του εγκεκριμένου ελάχιστου ασφαλούς περιβάλλοντος εκτέλεσης του OmniRoute. Η συνηθέστερη περίπτωση είναι η εκτέλεση μιας παλαιότερης διορθωτικής έκδοσης του Node 22 ή 24, η οποία βρίσκεται κάτω από το ελάχιστο επίπεδο ασφαλείας με τις απαιτούμενες διορθώσεις που ορίζει το OmniRoute.

**Συμπτώματα:**

- Η σελίδα σύνδεσης εμφανίζει κενή οθόνη ή σφάλμα διακομιστή
- Η κονσόλα εμφανίζει `Error: Module did not self-register` ή παρόμοια σφάλματα εγγενών συνδέσεων
- Η σελίδα σύνδεσης εμφανίζει ένα **πορτοκαλί προειδοποιητικό πλαίσιο** με την έκδοση του Node που χρησιμοποιείτε, εάν το περιβάλλον εκτέλεσης βρίσκεται εκτός της υποστηριζόμενης πολιτικής ασφαλείας

**Λύση:**

1. Εγκαταστήστε μια υποστηριζόμενη έκδοση Node.js LTS (συνιστάται: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Επαληθεύστε την έκδοσή σας: το `node --version` θα πρέπει να εμφανίζει `v24.0.0` ή νεότερη έκδοση στη γραμμή LTS 24.x
3. Επανεγκαταστήστε το OmniRoute: `npm install -g omniroute`
4. Επανεκκινήστε: `omniroute`

> **Υποστηριζόμενες ασφαλείς εκδόσεις:** `>=22.22.2 <23` ή `>=24.0.0 <27`. Το Node.js 24.x LTS (Krypton) και το Node.js 26 υποστηρίζονται πλήρως.

### npm v11+: Το `better-sqlite3` δεν έχει εγκατασταθεί (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Αιτία:** Το npm v11 (το οποίο περιλαμβάνεται στο Node.js 24+) αποκλείει από προεπιλογή τα script εγκατάστασης για προαιρετικές
εξαρτήσεις. Επειδή το `better-sqlite3` παρατίθεται στο `optionalDependencies`
και απαιτεί εγγενή μεταγλώττιση (`node-gyp rebuild`), το npm το παραλείπει χωρίς ειδοποίηση.

**Συμπτώματα:**

- Ο διακομιστής καταρρέει κατά την εκκίνηση με το μήνυμα `Cannot find module 'better-sqlite3'`
- Το `ls node_modules/better-sqlite3` εμφανίζει "No such file or directory"
- Το `npm ls better-sqlite3` εμφανίζει `(empty)`

**Λύση:**

1. Εγκρίνετε τα script εγκατάστασης και εκτελέστε ξανά την εγκατάσταση:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Εναλλακτικά, εγκαταστήστε χειροκίνητα το προκατασκευασμένο πακέτο:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Επαληθεύστε ότι λειτουργεί: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Αιτία:** Μετά από μια καθολική εγκατάσταση μέσω `npm install -g omniroute`, το εγγενές δυαδικό αρχείο του `better-sqlite3` μέσα στο πακέτο ενδέχεται να έχει μεταγλωττιστεί για διαφορετική αρχιτεκτονική ή ABI του Node.js από αυτό που εκτελείται τοπικά. Αυτό είναι σύνηθες στο macOS (τόσο σε Apple Silicon όσο και σε Intel), όταν το προκατασκευασμένο δυαδικό αρχείο δεν αντιστοιχεί στο περιβάλλον σας.

**Συμπτώματα:**

- Ο διακομιστής αποτυγχάνει αμέσως κατά την εκκίνηση με σφάλμα `dlopen`
- Το σφάλμα περιέχει `slice is not valid mach-o file`
- Πλήρες παράδειγμα:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Λύση — ανακατασκευάστε το για το τοπικό σας περιβάλλον (δεν απαιτείται υποβάθμιση του Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Σημείωση:** Αυτή η διαδικασία επαναμεταγλωττίζει την εγγενή σύνδεση με βάση την τοπική έκδοση του Node.js και την αρχιτεκτονική της CPU σας, επιλύοντας την ασυμβατότητα του δυαδικού αρχείου. Το επίσημα υποστηριζόμενο εύρος περιβάλλοντος εκτέλεσης είναι **`>=22.22.2 <23` ή `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` στο `src/shared/utils/nodeRuntimeSupport.ts`, σε αντιστοιχία με το πεδίο `engines` του `package.json`). Το Node.js 24.x LTS (Krypton) και το Node.js 26 υποστηρίζονται πλήρως με το `better-sqlite3` v12.x.

## Προβλήματα διακομιστή μεσολάβησης

<a name="proxy-issues"></a>

### Η επικύρωση παρόχου εμφανίζει "fetch failed"

**Αιτία:** Το endpoint επικύρωσης κλειδιού API (`POST /api/providers/validate`) παρέκαμπτε προηγουμένως τη διαμόρφωση του διακομιστή μεσολάβησης, προκαλώντας αποτυχίες σε περιβάλλοντα που απαιτούν δρομολόγηση μέσω διακομιστή μεσολάβησης.

**Διόρθωση (v3.5.5+):** Αυτό έχει πλέον διορθωθεί. Η επικύρωση παρόχου δρομολογείται μέσω του `runWithProxyContext`, τηρώντας αυτόματα τις ρυθμίσεις διακομιστή μεσολάβησης σε επίπεδο παρόχου και σε καθολικό επίπεδο.

### Ο έλεγχος κατάστασης του token αποτυγχάνει με "fetch failed"

**Αιτία:** Η ανανέωση token OAuth στο παρασκήνιο δεν επέλυε τη διαμόρφωση του διακομιστή μεσολάβησης ανά σύνδεση.

**Διόρθωση (v3.5.5+):** Ο χρονοπρογραμματιστής ελέγχου κατάστασης token επιλύει πλέον τη διαμόρφωση του διακομιστή μεσολάβησης ανά σύνδεση πριν επιχειρήσει ανανέωση. Αναβαθμίστε σε v3.5.5+.

### Ο διακομιστής μεσολάβησης SOCKS5 επιστρέφει "invalid onRequestStart method"

**Αιτία:** Στο Node.js 22, ο dispatcher του undici@8 δεν είναι συμβατός με την ενσωματωμένη υλοποίηση `fetch()` του Node.

**Διόρθωση (v3.5.5+):** Το OmniRoute χρησιμοποιεί πλέον τη δική του συνάρτηση `fetch()` του undici όταν είναι ενεργός ένας dispatcher διακομιστή μεσολάβησης, διασφαλίζοντας συνεπή συμπεριφορά. Αναβαθμίστε σε v3.5.5+.

### Διακομιστής μεσολάβησης MITM στο WSL: οι εφαρμογές επιφάνειας εργασίας στον κεντρικό υπολογιστή Windows δεν αναχαιτίζονται

**Αιτία:** Ο διακομιστής μεσολάβησης MITM και το πιστοποιητικό CA του εγκαθίστανται στο περιβάλλον όπου εκτελείται το OmniRoute. Στο WSL, αυτό το περιβάλλον είναι το φιλοξενούμενο Linux, ενώ οι εφαρμογές AI επιφάνειας εργασίας (Kiro, Trae, Copilot, Zed, …) εκτελούνται στον κεντρικό υπολογιστή Windows. Οι εφαρμογές του κεντρικού υπολογιστή δεν εμπιστεύονται τον χώρο αποθήκευσης πιστοποιητικών του φιλοξενούμενου συστήματος και δεν δρομολογούνται μέσω του διακομιστή μεσολάβησης συστήματος του φιλοξενούμενου, επομένως η αναχαίτιση εφαρμογών επιφάνειας εργασίας δεν ενεργοποιείται εκεί.

**Σύσταση:** Εκτελέστε το OmniRoute εγγενώς στο ίδιο λειτουργικό σύστημα με τις εφαρμογές επιφάνειας εργασίας που θέλετε να αναχαιτίσετε (Windows για εφαρμογές Windows· αντίστοιχα για macOS/Linux). Η διατήρηση του OmniRoute μέσα στο WSL ενώ στοχεύετε εφαρμογές του κεντρικού υπολογιστή απαιτεί να ορίσετε χειροκίνητα ως αξιόπιστο το δημιουργημένο πιστοποιητικό CA στον κεντρικό υπολογιστή Windows και να κατευθύνετε τις ρυθμίσεις δικτύου/διακομιστή μεσολάβησης κάθε εφαρμογής του κεντρικού υπολογιστή στο endpoint του διακομιστή μεσολάβησης WSL — μια μη υποστηριζόμενη και εύθραυστη διαμόρφωση.

μέσω οποιασδήποτε από τις τρεις ροές εισαγωγής.

Για πλήρεις λεπτομέρειες και αναλυτικές οδηγίες βήμα προς βήμα για την παράλληλη προσθήκη δύο λογαριασμών Kiro,
ανατρέξτε στο [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Προβλήματα Docker

### Docker IPv6 / Επαναφορά σύνδεσης

<a name="docker-ipv6"></a>

**Συμπτώματα:** Η εντολή `curl http://localhost:20128/v1/models` επιστρέφει `curl: (56) Recv failure: Connection reset by peer`. Ο πίνακας ελέγχου και τα endpoints χωρίς έλεγχο ταυτότητας λειτουργούν, αλλά τα endpoints με έλεγχο ταυτότητας αποτυγχάνουν — μοιάζει με πρόβλημα ελέγχου ταυτότητας, αλλά δεν είναι.

**Αιτία:** Η εντολή `docker run -p 20128:20128` δημοσιεύει τόσο στο `0.0.0.0` (IPv4) όσο και στο `::` (IPv6), αλλά η διεργασία μέσα στο container ακούει μόνο στο IPv4. Σε hosts όπου το `localhost` επιλύεται πρώτα σε `::1`, η σύνδεση καταλήγει στη δημοσιευμένη θύρα IPv6 χωρίς listener πίσω από αυτήν → επαναφορά σύνδεσης.

**Διόρθωση:**

1. **Γρήγορη διάγνωση:** Εκτελέστε `curl -4 http://localhost:20128/v1/models`. Εάν λειτουργεί με `-4` αλλά αποτυγχάνει χωρίς αυτό, υπάρχει ασυμφωνία δέσμευσης IPv6.
2. **Μόνιμη διόρθωση:** Κάντε ρητή δέσμευση στο IPv4 χρησιμοποιώντας `-p 127.0.0.1:20128:20128` στην εντολή `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Αυτό επιβάλλει τη δέσμευση IPv4 και αποτρέπει επίσης την έκθεση του proxy σε όλες τις διεπαφές του host.

## Αποσφαλμάτωση

### Ενεργοποίηση αρχείων καταγραφής

Ορίστε `APP_LOG_TO_FILE=true` στο αρχείο `.env`. Τα αρχεία καταγραφής της εφαρμογής εγγράφονται στον κατάλογο `logs/`.
Τα τεχνουργήματα αιτημάτων αποθηκεύονται στον κατάλογο `${DATA_DIR}/call_logs/` όταν η διοχέτευση καταγραφής κλήσεων είναι
ενεργοποιημένη στις ρυθμίσεις.
Όταν είναι ενεργοποιημένη η καταγραφή της διοχέτευσης, ορίστε `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` για να παραλείψετε
τα ωφέλιμα φορτία των τμημάτων ροής ή προσαρμόστε το `CALL_LOG_PIPELINE_MAX_SIZE_KB` για να αλλάξετε το όριο των τεχνουργημάτων σε KB.

### Έλεγχος εύρυθμης λειτουργίας παρόχου

```bash
# Πίνακας ελέγχου εύρυθμης λειτουργίας
http://localhost:20128/dashboard/health

# Έλεγχος εύρυθμης λειτουργίας API
curl http://localhost:20128/api/monitoring/health
```

### Αποθήκευση runtime

- Κύρια κατάσταση: `${DATA_DIR}/storage.sqlite` (πάροχοι, συνδυασμοί, ψευδώνυμα, κλειδιά, ρυθμίσεις)
- Χρήση: Πίνακες SQLite στο `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + προαιρετικά `${DATA_DIR}/call_logs/`
- Αρχεία καταγραφής εφαρμογής: `<repo>/logs/...` (όταν `APP_LOG_TO_FILE=true`)
- Τεχνουργήματα καταγραφής κλήσεων: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` όταν είναι ενεργοποιημένη η διοχέτευση καταγραφής κλήσεων

Η ενέργεια **Εκκαθάριση ιστορικού** στη σελίδα Αρχεία καταγραφής αιτημάτων διαγράφει τα `call_logs`, τα παλαιού τύπου
`request_detail_logs` και τον τοπικό κατάλογο τεχνουργημάτων `${DATA_DIR}/call_logs/`.

## Ζητήματα Circuit Breaker

### Ο πάροχος έχει κολλήσει σε κατάσταση OPEN

Όταν το circuit breaker ενός παρόχου βρίσκεται σε κατάσταση OPEN, τα αιτήματα αποκλείονται μέχρι να λήξει ο χρόνος αναμονής.

**Διόρθωση:**

1. Μεταβείτε στο **Dashboard → Settings → Resilience**
2. Ελέγξτε την κάρτα του circuit breaker για τον επηρεαζόμενο πάροχο
3. Κάντε κλικ στο **Reset All** για να επαναφέρετε όλα τα circuit breakers ή περιμένετε να λήξει ο χρόνος αναμονής
4. Βεβαιωθείτε ότι ο πάροχος είναι πράγματι διαθέσιμος πριν από την επαναφορά

### Ο πάροχος ενεργοποιεί συνεχώς το circuit breaker

Αν ένας πάροχος εισέρχεται επανειλημμένα σε κατάσταση OPEN:

1. Ελέγξτε το **Dashboard → Health → Provider Health** για το μοτίβο αποτυχιών
2. Μεταβείτε στο **Settings → Resilience → Provider Profiles** και αυξήστε το όριο αποτυχιών
3. Ελέγξτε αν ο πάροχος έχει αλλάξει τα όρια του API ή απαιτεί εκ νέου έλεγχο ταυτότητας
4. Εξετάστε την τηλεμετρία καθυστέρησης — η υψηλή καθυστέρηση μπορεί να προκαλεί αποτυχίες λόγω λήξης χρονικού ορίου

## Εντοπισμός σφαλμάτων του Translator

### Συνήθη ζητήματα μορφής

- **Δεν εμφανίζονται οι ετικέτες σκέψης** — Ελέγξτε αν ο πάροχος-στόχος υποστηρίζει τη λειτουργία σκέψης και τη ρύθμιση προϋπολογισμού σκέψης
- **Οι κλήσεις εργαλείων χάνονται** — Ορισμένες μεταφράσεις μορφών ενδέχεται να αφαιρούν μη υποστηριζόμενα πεδία· επαληθεύστε το στη λειτουργία Playground
- **Λείπει η προτροπή συστήματος** — Τα Claude και Gemini χειρίζονται διαφορετικά τις προτροπές συστήματος· ελέγξτε το αποτέλεσμα της μετάφρασης
- **Το SDK επιστρέφει ακατέργαστη συμβολοσειρά αντί για αντικείμενο** — Επιλύθηκε στη v1.x· ο μηχανισμός εξυγίανσης αποκρίσεων αφαιρεί μη τυπικά πεδία (`x_groq`, `usage_breakdown` κ.λπ.) που προκαλούν αποτυχίες επικύρωσης Pydantic στο OpenAI SDK. Αν εξακολουθείτε να το βλέπετε στη v3.x+, υποβάλετε μια αναφορά ζητήματος.
- **Το GLM/ERNIE απορρίπτει τον ρόλο `system`** — Επιλύθηκε στη v1.x· ο κανονικοποιητής ρόλων συγχωνεύει αυτόματα τα μηνύματα συστήματος με τα μηνύματα χρήστη για μη συμβατά μοντέλα. Αν εξακολουθείτε να το βλέπετε στη v3.x+, υποβάλετε μια αναφορά ζητήματος.
- **Ο ρόλος `developer` δεν αναγνωρίζεται** — Επιλύθηκε στη v1.x· μετατρέπεται αυτόματα σε `system` για παρόχους εκτός OpenAI. Αν εξακολουθείτε να το βλέπετε στη v3.x+, υποβάλετε μια αναφορά ζητήματος.
- **Το `json_schema` δεν λειτουργεί με το Gemini** — Επιλύθηκε στη v1.x· το `response_format` μετατρέπεται πλέον στα `responseMimeType` + `responseSchema` του Gemini. Αν εξακολουθείτε να το βλέπετε στη v3.x+, υποβάλετε μια αναφορά ζητήματος.

## Ρυθμίσεις ανθεκτικότητας

### Ο αυτόματος περιορισμός ρυθμού δεν ενεργοποιείται

- Ο αυτόματος περιορισμός ρυθμού εφαρμόζεται μόνο σε παρόχους με κλειδί API (όχι OAuth/συνδρομή)
- Επαληθεύστε ότι στην ενότητα **Settings → Resilience → Provider Profiles** είναι ενεργοποιημένος ο αυτόματος περιορισμός ρυθμού
- Ελέγξτε αν ο πάροχος επιστρέφει κωδικούς κατάστασης `429` ή κεφαλίδες `Retry-After`

### Ρύθμιση της εκθετικής οπισθοχώρησης

Τα προφίλ παρόχων υποστηρίζουν τις ακόλουθες ρυθμίσεις:

- **Βασική καθυστέρηση** — Αρχικός χρόνος αναμονής μετά την πρώτη αποτυχία (προεπιλογή: 1s)
- **Μέγιστη καθυστέρηση** — Ανώτατο όριο χρόνου αναμονής (προεπιλογή: 30s)
- **Πολλαπλασιαστής** — Πόσο αυξάνεται η καθυστέρηση ανά διαδοχική αποτυχία (προεπιλογή: 2x)

### Αποτροπή ταυτόχρονων μαζικών αιτημάτων

Όταν πολλά ταυτόχρονα αιτήματα φτάνουν σε έναν πάροχο με περιορισμό ρυθμού, το OmniRoute χρησιμοποιεί mutex + αυτόματο περιορισμό ρυθμού για να σειριοποιεί τα αιτήματα και να αποτρέπει αλυσιδωτές αποτυχίες. Αυτό γίνεται αυτόματα για παρόχους με κλειδί API.

### Τα αιτήματα συνομιλίας αποτυγχάνουν με 503 / chat_admission_busy

**Συμπτώματα:**

- Το endpoint ολοκληρώσεων συνομιλίας επιστρέφει μια επαναλήψιμη απόκριση `503`, της οποίας ο κωδικός σφάλματος είναι
  `chat_admission_busy`.
- Η απόκριση περιλαμβάνει `Retry-After`. Από το #12135, η τιμή προκύπτει από την παρατηρούμενη
  πληρότητα — επιλέγεται η μεγαλύτερη τιμή μεταξύ του χρονικού παραθύρου `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` κατά το οποίο το αίτημα έχει ήδη
  περιμένει και του χρόνου για τον οποίο διατηρούνται οι τρέχουσες μισθώσεις βαρέων αιτημάτων — στρογγυλοποιημένη προς τα επάνω σε ακέραια
  δευτερόλεπτα και με ανώτατο όριο τα 60. Όταν η πύλη είναι αδρανής, διατηρούνται τα ιστορικά κατώτατα όρια: 2 δευτερόλεπτα στη
  διαδρομή βάσει byte, 1 δευτερόλεπτο στη διαδρομή βάσει δομής (η οποία περιλαμβάνει επίσης
  `reason: "structure_limit"`).
- Αυτό μπορεί να συμβεί ενώ μια άλλη βαριά συνομιλία ή μια μακράς διάρκειας απόκριση ροής βρίσκεται ακόμη
  σε εξέλιξη.

Το σώμα της απόκρισης βάσει byte είναι:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Η απόκριση βάσει δομής χρησιμοποιεί τον ίδιο τύπο και κωδικό, με το μήνυμα
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
και `reason: "structure_limit"`.
Με τα προεπιλεγμένα όρια, ένα αίτημα θεωρείται δομικά βαρύ όταν έχει τουλάχιστον `200` μηνύματα,
τουλάχιστον `64` εργαλεία ή τουλάχιστον `32,000` εκτιμώμενα token, ή όταν η οριοθετημένη εκτίμηση δομής
εξαντλεί τα όριά της των `10,000` κόμβων που επισκέφθηκε ή βάθους `12`.

**Αιτία:** Πρόκειται για σκόπιμη απόρριψη φορτίου εντός του OmniRoute και όχι για αποτυχία ανάντη παρόχου.
Κάθε διεργασία χρησιμοποιεί έναν τοπικό στη διεργασία μηχανισμό προστασίας για να δεσμεύει περιορισμένη χωρητικότητα για βαριά αιτήματα πριν διατηρήσει
και αναλύσει ένα μεγάλο σώμα αιτήματος. Μια μίσθωση βαρέος αιτήματος παραμένει ενεργή καθ’ όλη τη διάρκεια ζωής μιας απόκρισης SSE.

**#503-fanout:** πριν από αυτήν τη διόρθωση, ο μηχανισμός προστασίας περιόριζε την ταυτόχρονη εκτέλεση σε ένα σταθερό ΠΛΗΘΟΣ αιτημάτων
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, προεπιλογή `1`) ανεξάρτητα από τη μνήμη του host, οπότε το
fan-out πρακτόρων προγραμματισμού (πολλοί υποπράκτορες/CLI, με σώματα συνήθως > 256 KB) κατέρρεε σε πραγματική
ταυτόχρονη εκτέλεση ~1 και επέστρεφε 503 υπό απολύτως φυσιολογικό φορτίο. Ο μηχανισμός προστασίας πλέον αυτορρυθμίζεται: ελέγχεται
από έναν αυτόματα υπολογιζόμενο προϋπολογισμό BYTE εισαγωγής (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), ο οποίος διαστασιολογείται βάσει του
πραγματικού ορίου μνήμης της διεργασίας, ενώ συμβουλεύεται επίσης ένα ζωντανό σήμα πίεσης πόρων — επομένως
απορρίπτει φορτίο μόνο όταν ο host βρίσκεται πραγματικά υπό πίεση μνήμης και όχι απλώς επειδή έφτασαν ταυτόχρονα περισσότερα από ένα
βαριά αιτήματα. Το παλιό όριο πλήθους (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) εξακολουθεί να τηρείται, αλλά
μόνο αν το ορίσετε ρητά.

Όταν η χωρητικότητα είναι κατειλημμένη, ένα βαρύ αίτημα περιμένει πρώτα έως
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (προεπιλογή: `RATE_LIMIT_MAX_WAIT_MS`· το `0` απενεργοποιεί την αναμονή) μέχρι να ελευθερωθεί μια θέση,
πριν απαντήσει με το επαναλήψιμο `503`. Η οριοθετημένη αναμονή υπάρχει ώστε οι πελάτες τύπου πράκτορα
(OpenCode, Claude Code, Cursor), οι οποίοι πραγματοποιούν ταυτόχρονο fan-out βαρέων υποαιτημάτων, να σειριοποιούν την αιχμή
αντί να εξαντλούν ολόκληρο το περιθώριο επαναλήψεών τους σε άμεσες απορρίψεις και να διακόπτονται στη μέση μιας εργασίας.
Η τρέχουσα πληρότητα των μισθώσεων βαρέων αιτημάτων, ο υπολογισμένος προϋπολογισμός byte και η σοβαρότητα της ζωντανής πίεσης
εμφανίζονται στο `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — ελέγξτε τα πριν αλλάξετε οποιαδήποτε μεταβλητή περιβάλλοντος.
Η ρύθμιση Settings → Resilience → Request Queue → Concurrent Requests δεν το ελέγχει αυτό· η συγκεκριμένη ρύθμιση
διέπει έναν ξεχωριστό μηχανισμό ουράς αιτημάτων παρόχου.

**Διόρθωση:**

1. Δοκιμάστε πρώτα ξανά. Οι πελάτες πρέπει να τηρούν το `Retry-After` και να χρησιμοποιούν οπισθοχώρηση αντί να
   επαναλαμβάνουν αμέσως το αίτημα.
2. Ελέγξτε το `/api/monitoring/health` → `chatAdmission` πριν ρυθμίσετε οτιδήποτε. Οι τιμές `countCapEnabled:
false` και ένα γενναιόδωρο `maxInflightBytes` σημαίνουν ότι ο αυτόματα υπολογιζόμενος προϋπολογισμός ήδη λειτουργεί
   σωστά· μια τιμή `pressureSeverity` ίση με `high`/`critical` σημαίνει ότι ο host έχει πράγματι λίγη διαθέσιμη μνήμη —
   αυτό δεν διορθώνεται μέσω μιας μεταβλητής περιβάλλοντος ελέγχου εισαγωγής, αλλά απαιτεί περισσότερη RAM ή μικρότερο φόρτο εργασίας.
3. Μόνο αν το `/api/monitoring/health` δείχνει ότι ο αυτόματα υπολογιζόμενος προϋπολογισμός είναι πραγματικά πολύ μικρός για
   τον host σας (σπάνιο — ήδη προσαρμόζεται από container έως bare-metal), παρακάμψτε τον απευθείας με
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` αντί να επιστρέψετε στο παλαιότερο όριο πλήθους αιτημάτων.

Ανατρέξτε στην [αναφορά μεταβλητών περιβάλλοντος](../reference/ENVIRONMENT.md#4-security--authentication)
για τις επίσημες ρυθμίσεις ελέγχου εισαγωγής.

## Προαιρετική ταξινόμηση αποτυχιών RAG / LLM (16 προβλήματα)

Ορισμένοι χρήστες του OmniRoute τοποθετούν την πύλη μπροστά από στοίβες RAG ή πρακτόρων. Σε αυτές τις διαμορφώσεις είναι σύνηθες να παρατηρείται ένα παράξενο μοτίβο: το OmniRoute φαίνεται να λειτουργεί κανονικά (οι πάροχοι είναι διαθέσιμοι, τα προφίλ δρομολόγησης είναι εντάξει, δεν υπάρχουν ειδοποιήσεις ορίων ρυθμού), αλλά η τελική απάντηση εξακολουθεί να είναι λανθασμένη.

Στην πράξη, αυτά τα περιστατικά συνήθως προέρχονται από τη μεταγενέστερη διοχέτευση RAG και όχι από την ίδια την πύλη.

Αν θέλετε ένα κοινό λεξιλόγιο για την περιγραφή αυτών των αποτυχιών, μπορείτε να χρησιμοποιήσετε το WFGY ProblemMap, έναν εξωτερικό πόρο κειμένου με άδεια MIT, ο οποίος ορίζει δεκαέξι επαναλαμβανόμενα μοτίβα αποτυχίας RAG / LLM. Σε γενικές γραμμές, καλύπτει:

- απόκλιση ανάκτησης και εσφαλμένα όρια συμφραζομένων
- κενά ή παρωχημένα ευρετήρια και διανυσματικά αποθετήρια
- αναντιστοιχία ενσωματώσεων και σημασιολογίας
- ζητήματα σύνθεσης προτροπών και παραθύρου συμφραζομένων
- κατάρρευση λογικής και απαντήσεις με υπερβολική βεβαιότητα
- αποτυχίες μεγάλων αλυσίδων και συντονισμού πρακτόρων
- απόκλιση μνήμης και ρόλων πολλαπλών πρακτόρων
- προβλήματα σειράς ανάπτυξης και αρχικοποίησης

Η ιδέα είναι απλή:

1. Όταν διερευνάτε μια λανθασμένη απάντηση, καταγράψτε:
   - την εργασία και το αίτημα του χρήστη
   - τη διαδρομή ή τον συνδυασμό παρόχων στο OmniRoute
   - οποιαδήποτε συμφραζόμενα RAG χρησιμοποιήθηκαν μεταγενέστερα (ανακτημένα έγγραφα, κλήσεις εργαλείων κ.λπ.)
2. Αντιστοιχίστε το περιστατικό σε έναν ή δύο αριθμούς του WFGY ProblemMap (`No.1` … `No.16`).
3. Αποθηκεύστε τον αριθμό στον δικό σας πίνακα ελέγχου, οδηγό λειτουργίας ή σύστημα παρακολούθησης περιστατικών, δίπλα στα αρχεία καταγραφής του OmniRoute.
4. Χρησιμοποιήστε την αντίστοιχη σελίδα του WFGY για να αποφασίσετε αν χρειάζεται να αλλάξετε τη στοίβα RAG, το σύστημα ανάκτησης ή τη στρατηγική δρομολόγησής σας.

Το πλήρες κείμενο και συγκεκριμένες συνταγές βρίσκονται εδώ (άδεια MIT, μόνο κείμενο):

[README του WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Μπορείτε να αγνοήσετε αυτήν την ενότητα αν δεν εκτελείτε διοχετεύσεις RAG ή πρακτόρων πίσω από το OmniRoute.

## Γνωστά προβλήματα της v3.8.0

Προβλήματα που αφορούν ειδικά την έκδοση v3.8.0 και οι τρέχουσες λύσεις παράκαμψής τους. Αν μια διόρθωση συμπεριληφθεί σε μεταγενέστερη ενημέρωση κώδικα, η καταχώριση θα ενημερωθεί ή θα αφαιρεθεί.

### Αποτυχίες ελέγχου ταυτότητας του Devin CLI

**Συμπτώματα:**

- "Το Devin CLI δεν βρέθηκε" ή "ο έλεγχος ταυτότητας απέτυχε" κατά την κλήση εργαλείων που υποστηρίζονται από το Devin
- Ο έλεγχος χρόνου εκτέλεσης του CLI αναφέρει `installed=false`

**Αιτίες:**

- Το `CLI_DEVIN_BIN` παραπέμπει σε μια διαδρομή που δεν υπάρχει
- Το Devin CLI δεν είναι εγκατεστημένο στον κεντρικό υπολογιστή

**Διόρθωση:**

1. Εγκαταστήστε το Devin CLI για την πλατφόρμα σας
2. Ορίστε `CLI_DEVIN_BIN=/usr/local/bin/devin` (ή την πραγματική διαδρομή) στο `.env`
3. Επανεκκινήστε το OmniRoute και εκτελέστε ξανά τη δοκιμή από το **Πίνακας ελέγχου → Εργαλεία CLI**

### Αποκλεισμός μοντέλου που έχει κολλήσει (μη αυτόματη επαναφορά)

**Συμπτώματα:**

- Ένα μοντέλο παραμένει καταχωρισμένο ως αποκλεισμένο ακόμα και μετά την παρέλευση του χρόνου λήξης
- Τα αιτήματα εξακολουθούν να παρακάμπτουν το μοντέλο στη συνδυαστική δρομολόγηση, παρότι η χρονική σήμανση ανήκει στο παρελθόν

**Μη αυτόματη επαναφορά:**

- **Πίνακας ελέγχου:** **Ρυθμίσεις → Αποκλεισμοί μοντέλων** → κάντε κλικ στην επιλογή **Επανενεργοποίηση** στην επηρεαζόμενη κάρτα
- **API:** `DELETE /api/resilience/model-cooldowns` με κεφαλίδες ελέγχου ταυτότητας διαχείρισης

### Η σύνδεση του παρόχου Command Code αποτυγχάνει με 403

**Συμπτώματα:**

- Σφάλμα 403 κατά τη δοκιμή της σύνδεσης με τον πάροχο Command Code
- Η κάρτα του παρόχου εμφανίζει την ένδειξη "χωρίς εξουσιοδότηση" μετά από νέα προσθήκη

**Αιτία:** Η ροή OAuth δεν ολοκληρώθηκε (δεν ελήφθη επανάκληση ή το διακριτικό δεν αποθηκεύτηκε).

**Διόρθωση:**

- Εκτελέστε `omniroute providers` από το CLI για να ενεργοποιήσετε ξανά τη ροή OAuth ή
- Εκτελέστε ξανά τη ροή OAuth από το **Πίνακας ελέγχου → Πάροχοι → Command Code → Επανασύνδεση**

### Το ModelScope επιστρέφει επιθετικούς αποκλεισμούς 429

**Συμπτώματα:**

- Πολύ σύντομοι ή άμεσοι αποκλεισμοί στο ModelScope μετά από μια μικρή αιχμή αιτημάτων
- Η συνδυαστική δρομολόγηση παρακάμπτει το ModelScope νωρίτερα από το αναμενόμενο

**Αιτία:** Το ModelScope εκπέμπει κεφαλίδες `Retry-After` ειδικές για τον πάροχο. Η v3.8.0 περιλαμβάνει εξειδικευμένο χειρισμό για αυτές τις κεφαλίδες, επομένως οι παλαιότερες εκδόσεις τις ερμηνεύουν εσφαλμένα ως γενικές υποδείξεις ορίων ρυθμού.

**Διόρθωση:**

- Βεβαιωθείτε ότι χρησιμοποιείτε τη v3.8.0 ή μεταγενέστερη έκδοση
- Επαληθεύστε ότι η εναλλαγή `useUpstream429BreakerHints` είναι ενεργοποιημένη στην ενότητα **Ρυθμίσεις → Ανθεκτικότητα**

### Το OMNIROUTE_WS_BRIDGE_SECRET λείπει από το περιβάλλον παραγωγής

**Συμπτώματα:**

- Σφάλμα 401 σε κάθε αίτημα προς τη γέφυρα WebSocket του Codex/Responses κατά την εκτέλεση σε απομακρυσμένο κεντρικό υπολογιστή παραγωγής
- Η χειραψία της γέφυρας WebSocket κλείνει αμέσως μετά τη σύνδεση

**Αιτία:** Η μεταβλητή περιβάλλοντος `OMNIROUTE_WS_BRIDGE_SECRET` λείπει από το περιβάλλον παραγωγής.

**Διόρθωση:**

1. Δημιουργήστε ένα τυχαίο μυστικό: `openssl rand -hex 32`
2. Ορίστε `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` στο περιβάλλον του διακομιστή παραγωγής (και σε κάθε πρόγραμμα-πελάτη που επικοινωνεί με τη γέφυρα)
3. Επανεκκινήστε το OmniRoute

### Responses API: η λειτουργία παρασκηνίου υποβαθμίζεται σε σύγχρονη

**Συμπτώματα:**

- Καταγράφεται η προειδοποίηση: `background mode degraded to synchronous`
- Ένα αίτημα `background: true` επιστρέφει μια κανονική σύγχρονη απόκριση αντί για μια λαβή εργασίας παρασκηνίου

**Αιτία:** Η v3.8.0 υποβαθμίζει σκόπιμα το `background: true` στο Responses API σε σύγχρονη εκτέλεση, ενώ ταυτόχρονα εκπέμπει μια προειδοποίηση. Η πλήρης ασύγχρονη εκτέλεση στο παρασκήνιο θα παραδοθεί στο μέλλον.

**Διόρθωση:**

- Προσαρμόστε το πρόγραμμα-πελάτη ώστε να πραγματοποιεί την κλήση χωρίς `background` ή
- Περιμένετε μια μεταγενέστερη έκδοση που θα περιλαμβάνει πλήρη ασύγχρονη λειτουργία παρασκηνίου (παρακολουθήστε το αρχείο αλλαγών)

## Αργή Εκκίνηση / Λήξη Χρόνου Ετοιμότητας

Εάν το CLI εμφανίζει `⚠ Server did not respond within 60s`, αλλά ο διακομιστής
λειτουργεί κανονικά, το χρονικό περιθώριο του ελέγχου ετοιμότητας είναι πολύ μικρό για το περιβάλλον σας.

Αυτό συμβαίνει συχνά στα Windows (antivirus, παρακολούθηση συστήματος αρχείων) ή σε containers
με μεγάλο φόρτο εργασίας κατά την εκκίνηση.

**Λύση — αυξήστε το χρονικό περιθώριο:**

```bash
# Μέσω μεταβλητής περιβάλλοντος (διατηρείται μεταξύ εκκινήσεων):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 λεπτά
omniroute serve

# Μέσω σημαίας CLI (για μία φορά):
omniroute serve --ready-timeout 180000
```

Η προεπιλογή είναι 60 000 ms (60 s). Η προειδοποίηση είναι μόνο ενημερωτική· ο διακομιστής
συνεχίζει να εκκινείται στο παρασκήνιο και θα είναι προσβάσιμος μόλις ολοκληρωθεί η εκκίνηση.

Ανατρέξτε στο [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) για πλήρεις
λεπτομέρειες σχετικά με το `OMNIROUTE_READY_TIMEOUT_MS`.
