Τα relay (Vercel, Deno, Cloudflare) τερματίζουν την upstream σύνδεση σε ένα
serverless backend, ώστε το OmniRoute να μπορεί να πραγματοποιεί εξερχόμενες
συνδέσεις από μια σταθερή περιοχή, διατηρώντας παράλληλα το κλειδί API του
παρόχου στην πλευρά του διακομιστή. Αυτό το έγγραφο καλύπτει τις δύο καταστάσεις
αστοχίας που αντιμετωπίζουν οι διαχειριστές στην παραγωγή και τις διαδρομές
ανάκτησης που παρέχει το OmniRoute για καθεμία.

## Πώς αποθηκεύεται ο έλεγχος ταυτότητας του relay

Όταν αναπτύσσετε ένα relay από το **Ρυθμίσεις → Proxy Pool → Ανάπτυξη Relay**,
η ροή ανάπτυξης αποθηκεύει το token ελέγχου ταυτότητας του relay στο πεδίο JSON
`notes` του proxy:

- Αν έχει οριστεί το `STORAGE_ENCRYPTION_KEY`, το token εγγράφεται ως
  `relayAuthEnc` (κρυπτογραφημένο με AES κατά την αποθήκευση).
- Διαφορετικά, εγγράφεται ως απλό κείμενο στο `relayAuth`.

Κατά την εκτέλεση ενός αιτήματος, το `extractRelayAuth(notes)` επιστρέφει όποια
μορφή είναι διαθέσιμη, ώστε το relay να συνεχίζει να λειτουργεί μετά από
επανεκκινήσεις.

## Κατάσταση αστοχίας 1 — μη αποκρυπτογραφήσιμο token μετά από εναλλαγή κλειδιού

**Σύμπτωμα:** τα relay που λειτουργούσαν προηγουμένως επιστρέφουν πλέον upstream
σφάλματα `401`/ελέγχου ταυτότητας μετά από εναλλαγή του
`STORAGE_ENCRYPTION_KEY` στο περιβάλλον ή στον διαχειριστή μυστικών. Το
αποθηκευμένο blob `relayAuthEnc` δεν μπορεί πλέον να αποκρυπτογραφηθεί, οπότε το
`extractRelayAuth` επιστρέφει την κενή συμβολοσειρά και το relay δεν στέλνει
στοιχεία ελέγχου ταυτότητας.

**Ανάκτηση — επιδιόρθωση επιτόπου (χωρίς νέα ανάπτυξη):**

1. Ανοίξτε το **Ρυθμίσεις → Proxy Pool**.
2. Οι γραμμές relay από τις οποίες λείπει ο έλεγχος ταυτότητας εμφανίζουν μια
   κίτρινη ένδειξη `λείπει ο έλεγχος ταυτότητας` και ένα κουμπί
   **Επιδιόρθωση**.
3. Κάντε κλικ στην **Επιδιόρθωση**. Το OmniRoute καλεί το
   `POST /api/settings/proxies/[id]/repair-relay`, το οποίο:
   - αποκρυπτογραφεί το `relayAuthEnc` με το **τρέχον** κλειδί,
   - εγγράφει ξανά το `relayAuth` ως απλό κείμενο στο `notes`,
   - επιστρέφει `{ repaired: true, mode: "recovered" }`.

Το relay συνεχίζει να εξυπηρετεί αιτήματα χωρίς να χρειάζεται να εισαγάγετε
ξανά διαπιστευτήρια ανάπτυξης.

Αυτό λειτουργεί μόνο εάν το τρέχον `STORAGE_ENCRYPTION_KEY` μπορεί ακόμα να
αποκρυπτογραφήσει το blob. Αν εναλλάξατε το κλειδί **χωρίς** μετεγκατάσταση, το
blob δεν μπορεί να ανακτηθεί.

## Κατάσταση αστοχίας 2 — μη ανακτήσιμο token (το κλειδί έχει αντικατασταθεί)

**Σύμπτωμα:** κάνατε κλικ στην **Επιδιόρθωση** και λάβατε
`{ repaired: false, mode: "redeploy", status: 409 }`.

**Ανάκτηση — νέα ανάπτυξη:**

Το αποθηκευμένο token δεν μπορεί να ανακτηθεί με το τρέχον κλειδί. Αναπτύξτε
ξανά το relay από το ίδιο παράθυρο διαλόγου που χρησιμοποιήσατε αρχικά (μενού
**Ανάπτυξη Relay** → Vercel / Deno / Cloudflare). Η ροή ανάπτυξης εγγράφει ένα
νέο token (κρυπτογραφημένο με το τρέχον κλειδί) και η ένδειξη
`λείπει ο έλεγχος ταυτότητας` της γραμμής εξαφανίζεται.

Στο περιβάλλον εργασίας χρήστη, το ίδιο το κουμπί **Επιδιόρθωση** ανοίγει το
παράθυρο διαλόγου νέας ανάπτυξης όταν το token δεν μπορεί να ανακτηθεί, ώστε να
μη χρειάζεται να το αναζητήσετε χειροκίνητα.

## Κατάσταση αστοχίας 3 — το relay είναι προσβάσιμο αλλά δυσλειτουργεί

**Σύμπτωμα:** η δοκιμή του proxy (κουμπί `ταχύτητα`) δείχνει ότι το relay είναι
ενεργό, αλλά τα αιτήματα εξακολουθούν να αποτυγχάνουν κατά διαστήματα.

Ελέγξτε τις κεφαλίδες επίγνωσης relay που επιστρέφονται από τον αυτόματο
ανιχνευτή δοκιμών του OmniRoute (δείτε **Ρυθμίσεις → Proxy Pool** και τους
μετρητές `relayTested` / `relayAlive`):

- `x-relay-url` — ποιο backend του relay αποκρίθηκε.
- `x-relay-mode` — `ts` | `bifrost` | `auto` για το συγκεκριμένο αίτημα.
- `x-relay-attempts` — πόσα άλματα relay δοκιμάστηκαν πριν από την επιτυχία.
- `x-relay-fallback` — `true` όταν το αίτημα μεταπίπτει από το προτιμώμενο
  backend στο relay TypeScript.

Ένα υψηλό ποσοστό `x-relay-fallback` με χαμηλό `relayAlive` σημαίνει ότι το
backend sidecar δυσλειτουργεί και θα πρέπει είτε να το διορθώσετε είτε να
αλλάξετε τη στρατηγική backend του relay σε `ts` (δείτε
`RELAY_BACKEND_STRATEGY.md`).

## Αναφορά API

| Μέθοδος | Διαδρομή                                  | Σώμα                    | Επιτυχία                                                                                                                                  | Αποτυχία                                                                                 |
| ------- | ----------------------------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `POST`  | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }` όταν ανακτηθεί εκ νέου· `200 { repaired: false, mode: "noop" }` όταν υπάρχει ήδη απλό κείμενο | `409 { mode: "redeploy" }` μη ανακτήσιμο· `400` δεν είναι τύπος relay· `404` δεν βρέθηκε |

Η διαδρομή λίστας `GET /api/settings/proxies` προσθέτει ένα
`relayInfo: { isRelay, authMissing, repairMode }` χωρίς μυστικά σε κάθε στοιχείο,
ώστε ο πίνακας εργαλείων να μπορεί να εμφανίσει τη δυνατότητα επιδιόρθωσης χωρίς
να εκθέτει ποτέ το token.
