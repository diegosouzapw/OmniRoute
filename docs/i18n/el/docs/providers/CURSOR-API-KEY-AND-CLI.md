Δύο τρόποι για να τοποθετήσετε το Cursor πίσω από το OmniRoute χωρίς συνεδρία IDE:

1. **Πάροχος `cursor-api`** (κάρτα "Cursor API", ψευδώνυμο `cua`): ένας πάροχος
   API key που διατηρεί ένα Cursor user API key (`crsr_…`, το οποίο δημιουργείται στη
   διεύθυνση `https://cursor.com/dashboard/api`). Οποιοσδήποτε πελάτης OmniRoute μπορεί στη συνέχεια να προσπελάσει
   μοντέλα Cursor μέσω του `/v1/chat/completions` ως `cursor-api/<model>` ή
   `cua/<model>`, με τα συνήθη επίπεδα ορίων χρήσης, εναλλακτικής δρομολόγησης και καταγραφής. Ο πάροχος IDE
   (`cursor`, OAuth/συνεδρία IDE) παραμένει αμετάβλητος.
2. **Διέλευση Cursor CLI**: κατευθύνετε το Cursor CLI (`agent`) προς το OmniRoute, ώστε
   κάθε RPC που πραγματοποιεί το CLI να επαληθεύεται με ένα OmniRoute API key, να προωθείται
   στο Cursor με τα διαπιστευτήρια μιας σύνδεσης `cursor-api` και να καταγράφεται στη
   σελίδα Logs.

## Γιατί γίνεται ανταλλαγή του κλειδιού

Το `api2.cursor.sh` απορρίπτει ένα ακατέργαστο κλειδί `crsr_…` ως Bearer token (401). Το Cursor
CLI στέλνει πρώτα μέσω POST το κλειδί στο `/auth/exchange_user_api_key` και λαμβάνει ένα JWT
συνεδρίας που λήγει μετά από μία ώρα· το επιστρεφόμενο `refreshToken` φέρει το ίδιο
`exp`, επομένως η ανανέωση σημαίνει εκ νέου ανταλλαγή του κλειδιού.
Το `open-sse/services/cursorApiKeyAuth.ts` εκτελεί αυτή την ανταλλαγή, αποθηκεύει προσωρινά ένα token συνεδρίας
ανά κλειδί, πραγματοποιεί εκ νέου ανταλλαγή πέντε λεπτά πριν από τη λήξη και αφαιρεί το αποθηκευμένο
token όταν το Cursor απαντήσει με 401. Το `CursorExecutor` το καλεί αμέσως πριν ανοίξει
τη ροή προς την upstream υπηρεσία για συνδέσεις `cursor-api`.

## Ο πάροχος `cursor-api`

Μητρώο: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"`, ίδιο `format`, `baseUrl` και
`models` με το `cursor`). Κάρτα καταλόγου:
`src/shared/constants/providers/apikey/specialty-media.ts`. Αντιστοίχιση executor:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`).

Πίνακας ελέγχου: Providers → Cursor API → Add API key.

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

Στη συνέχεια:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

Σημειώσεις:

- Η λίστα μοντέλων για το `cursor-api` προέρχεται από το στατικό μητρώο του Cursor (την
  ίδια λίστα στην οποία καταφεύγει ο πάροχος IDE)· δεν απαιτείται εγκατάσταση του `cursor-agent`
  στον κεντρικό υπολογιστή του OmniRoute.
- Το `POST /api/providers/{id}/refresh-cursor` προορίζεται μόνο για τον πάροχο IDE `cursor`·
  οι συνδέσεις `cursor-api` δεν διαθέτουν συνεδρία IDE προς ανανέωση.

## Εγγενή αναγνωριστικά μοντέλων και επίπεδο προσπάθειας

Για τα `cursor` / `cu` και `cursor-api` / `cua`, ο κοινόχρηστος κανονικοποιητής προσπάθειας Claude
αφήνει ανέπαφο το αναγνωριστικό του ζητούμενου μοντέλου. Το Cursor μπορεί να δημοσιεύσει ένα επίθημα όπως
το `-low` ως μέρος ενός πραγματικού αναγνωριστικού μοντέλου και όχι ως ψευδώνυμο προσπάθειας του OmniRoute.
Ο executor του Cursor διατηρεί μια ακριβή αντιστοίχιση με τον ενεργό κατάλογο· όταν δεν υπάρχει
αντιστοίχιση, ο υπάρχων επιλυτής μοντέλων αναλαμβάνει την εναλλακτική μετατροπή του επιθήματος σε παράμετρο.

Αυτό δεν αλλάζει την κανονικοποίηση της προσπάθειας για άμεσες διαδρομές Claude, συμβατές με Claude
ή Vertex. Η διαθεσιμότητα εξακολουθεί να εξαρτάται από τον κατάλογο και τα δικαιώματα του επιλεγμένου
λογαριασμού Cursor.

## Διέλευση Cursor CLI

Διαδρομή: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`. Το πρόθεμα `/api/cursor-cli/` είναι
καταχωρισμένο στο `src/shared/constants/publicApiRoutes.ts`, επειδή ο χειριστής
επιβάλλει τον δικό του έλεγχο ταυτότητας:

| Διαδρομή                                                                                                                       | Αναμενόμενος έλεγχος ταυτότητας από το CLI | Τι κάνει το OmniRoute                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                             | `Bearer <OmniRoute API key>`               | Επικυρώνει το κλειδί, εκδίδει ένα HS256 JWT διάρκειας 1 ώρας (υπογεγραμμένο με `JWT_SECRET`) και το επιστρέφει                                                                                    |
| κάθε άλλη διαδρομή (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`                        | Επαληθεύει εκδότη/κοινό/λήξη, επιλέγει μια ενεργή σύνδεση `cursor-api`, αντικαθιστά την κεφαλίδα Authorization με το ανταλλαγμένο διακριτικό Cursor και μεταδίδει την απόκριση πίσω σε συνεχή ροή |

Το CLI αποκωδικοποιεί το `exp` από οποιοδήποτε διακριτικό λαμβάνει, επομένως η
παροχή ενός αδιαφανούς διακριτικού το αναγκάζει να πραγματοποιεί εκ νέου
ανταλλαγή πριν από σχεδόν κάθε αίτημα· το εκδοθέν JWT το αποτρέπει αυτό. Μια
απόκριση 401 από το OmniRoute αναγκάζει το CLI να πραγματοποιήσει ξανά την
ανταλλαγή.

### Ρύθμιση

1. Δημιουργήστε ένα κλειδί API του OmniRoute (Πίνακας ελέγχου → Κλειδιά API) και
   μια σύνδεση `cursor-api`.
2. Ρυθμίστε το CLI ώστε να χρησιμοποιεί HTTP/1.1 για τη ροή του πράκτορα. Στο
   `~/.cursor/cli-config.json`:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   Χωρίς αυτό, το CLI ανοίγει τη σειρά αλληλεπίδρασης του πράκτορα μέσω HTTP/2
   σε έναν ξεχωριστά διαμορφωμένο κεντρικό υπολογιστή πράκτορα και μόνο οι RPC
   του επιπέδου ελέγχου διέρχονται από το τελικό σημείο.

3. Εκτελέστε το CLI μέσω του OmniRoute:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

Κάθε ενδιάμεσο αίτημα καταγράφεται στα Αρχεία καταγραφής με πάροχο
`cursor-api`, τύπο αιτήματος `cursor-cli`, διαδρομή
`/api/cursor-cli/<rpc>` και αποδίδεται στο κλειδί API του OmniRoute και στη
σύνδεση που το εξυπηρέτησε.

### Καταστάσεις αποτυχίας

| Κατάσταση                                              | Απόκριση προς το CLI                                          |
| ------------------------------------------------------ | ------------------------------------------------------------- |
| Άγνωστο κλειδί OmniRoute και `REQUIRE_API_KEY=true`    | 401 `unauthenticated` κατά την ανταλλαγή                      |
| `REQUIRE_API_KEY=false`                                | ανώνυμη συνεδρία (αντικατοπτρίζει τη συμπεριφορά του `/v1/*`) |
| Ληγμένο / ξένο / αλλοιωμένο JWT συνεδρίας              | 401, το CLI πραγματοποιεί ξανά την ανταλλαγή                  |
| Κλειδί API του OmniRoute ανακλήθηκε μετά την ανταλλαγή | 401 στο επόμενο RPC                                           |
| Καμία ενεργή σύνδεση `cursor-api`                      | 503 `unavailable`                                             |
| Το Cursor απορρίπτει το κλειδί της σύνδεσης            | 401 `unauthenticated`, η αποθηκευμένη συνεδρία διαγράφεται    |
| Η ανάντη υπηρεσία δεν είναι προσβάσιμη                 | 502 `unavailable` (εξυγιασμένο μήνυμα)                        |
| Το `JWT_SECRET` δεν έχει οριστεί                       | 503 κατά την ανταλλαγή                                        |
