> **Συνοπτικά**: Το `open-sse/` είναι η βασική μηχανή ροής που υποστηρίζει κάθε αίτημα LLM στο OmniRoute. Περιέχει ~1.400 αρχεία που υλοποιούν τη διοχέτευση αιτημάτων, τους εκτελεστές, τις υπηρεσίες, τον διακομιστή MCP και το επίπεδο μετάφρασης. Αυτός ο οδηγός εξηγεί πώς συνδέονται μεταξύ τους τα επιμέρους τμήματα.

**Πηγή:** `open-sse/` (πακέτο χώρου εργασίας, ~1.440 αρχεία `.ts` εκτός δοκιμών)

---

## Γιατί ξεχωριστό πακέτο χώρου εργασίας;

Το `open-sse/` είναι ένας **αυτόνομος χώρος εργασίας** στο monorepo του OmniRoute για διάφορους λόγους:

1. **Επαναχρησιμοποίηση** — το `open-sse` δημοσιεύεται ως `@omniroute/open-sse` στο npm, ώστε άλλα έργα να μπορούν να το χρησιμοποιούν ανεξάρτητα
2. **Σαφή όρια** — η μηχανή ροής είναι αποσυνδεδεμένη από το επίπεδο UI/DB που αφορά ειδικά το OmniRoute
3. **Απόδοση** — η μηχανή δεν έχει εξαρτήσεις από το Next.js, επιτρέποντας ταχύτερες ψυχρές εκκινήσεις σε περιβάλλοντα CLI/serverless
4. **Διαχείριση εκδόσεων** — το `open-sse` μπορεί να κυκλοφορεί εκδόσεις με τον δικό του ρυθμό

```json
// package.json
"workspaces": ["open-sse"]
```

## Η διοχέτευση αιτημάτων

Κάθε αίτημα LLM διέρχεται από μια **διοχέτευση 5 σταδίων**:

```
                              ┌──────────────────┐
   Αίτημα HTTP                 │  1. ΔΡΟΜΟΛΟΓΗΣΗ  │   επίλυση combo, επιλογή μοντέλου
   (διαδρομή Next.js)          └────────┬─────────┘
                                       │
                                       ▼
                              ┌──────────────────┐
                              │  2. ΜΕΤΑΦΡΑΣΗ    │   μετατροπή μορφής (OpenAI ↔ Claude ↔ Gemini)
                              └────────┬─────────┘
                                       │
                                       ▼
                              ┌──────────────────┐
                              │  3. ΕΚΤΕΛΕΣΗ     │   εκτελεστής παρόχου, HTTP, επανάληψη, διακόπτης
                              └────────┬─────────┘
                                       │
                                       ▼
                              ┌──────────────────┐
                              │  4. ΡΟΗ          │   μετασχηματισμός SSE, αντίθλιψη
                              └────────┬─────────┘
                                       │
                                       ▼
                              ┌──────────────────┐
                              │  5. ΚΑΤΑΓΡΑΦΗ    │   παρακολούθηση χρήσης, αρχείο κλήσεων, ταξινόμηση σφαλμάτων
                              └────────┬─────────┘
                                       │
                                       ▼
                              Απόκριση HTTP (SSE ή JSON)
```

### Στάδιο 1: Δρομολόγηση (services/combo.ts)

**Σημείο εισόδου**: `handleComboChat()` στο `services/combo.ts`

Αντιστοιχίζει το αίτημα σε μια συγκεκριμένη πλειάδα `(provider, model, account, credentials)`:

- Αναζητά το combo βάσει ID (ή δημιουργεί ένα εικονικό combo για μοντέλα `auto/*`)
- Εφαρμόζει τη στρατηγική δρομολόγησης (προτεραιότητα, σταθμισμένη, round-robin κ.λπ.)
- Φιλτράρει τους μη υγιείς παρόχους (διακόπτης κυκλώματος)
- Επιλέγει τον επόμενο βιώσιμο προορισμό

Για μοντέλα `auto/*`, αυτό το στάδιο επίσης:

- Εκτελεί τον αλγόριθμο **βαθμολόγησης 16 παραγόντων** (`services/autoCombo/`)
- Επιλέγει ένα ζεύγος `provider+model` βάσει εύρυθμης λειτουργίας, κόστους, καθυστέρησης κ.λπ.

### Στάδιο 2: Μετάφραση (translator/)

Εάν η μορφή προέλευσης (π.χ. OpenAI) διαφέρει από τη μορφή προορισμού (π.χ. Claude), το αίτημα **μεταφράζεται**:

- Προτροπή συστήματος → μήνυμα συστήματος
- Ορισμοί εργαλείων → μορφή εργαλείων ειδική για τον πάροχο
- Παράμετροι συλλογισμού/σκέψης → αντίστοιχες παράμετροι ειδικές για τον πάροχο
- Κανονικοποίηση ρόλων μηνυμάτων (`developer` → `system` για παρόχους εκτός OpenAI)

Το `translator/index.ts` εκθέτει:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Στάδιο 3: Εκτέλεση (executors/)

**Σημείο εισόδου**: `getExecutor(providerId).execute(request, options)`

Όλοι οι πάροχοι χρησιμοποιούν το `DefaultExecutor` (`executors/default.ts`) μέσω της εφεδρικής επιλογής του εργοστασίου `getExecutor()`. Ο εκτελεστής:

- Δημιουργεί το URL ανώτερου επιπέδου (`buildUrl()`)
- Προσθέτει κεφαλίδες ειδικές για τον πάροχο (`buildHeaders()`)
- Μετασχηματίζει το σώμα του αιτήματος (`transformRequest()`)
- Στέλνει το αίτημα HTTP με επανάληψη + εκθετική οπισθοχώρηση
- Διαχειρίζεται την ανανέωση ελέγχου ταυτότητας, εάν απαιτείται (πάροχοι OAuth)

Όλοι οι εκτελεστές επεκτείνουν το `BaseExecutor` (`executors/base.ts`, 1170 γραμμές κώδικα), το οποίο παρέχει:

- Κοινή λογική επανάληψης
- Ενσωμάτωση διακομιστή μεσολάβησης
- Ενσωμάτωση διακόπτη κυκλώματος
- Άγκιστρα καταγραφής χρήσης

### Στάδιο 4: Ροή (utils/stream.ts)

Για αποκρίσεις ροής, ο εκτελεστής επιστρέφει ένα **ReadableStream**. Ο χειριστής:

- Διοχετεύει μέσω ενός μετασχηματισμού SSE (`createSSETransformStreamWithLogger`)
- Εφαρμόζει παλμούς heartbeat για τον εντοπισμό νεκρών συνδέσεων
- Διαχειρίζεται ομαλά την αποσύνδεση του πελάτη (`pipeWithDisconnect`)
- Μετασχηματίζει SSE → JSON για πελάτες χωρίς υποστήριξη ροής

Για αποκρίσεις χωρίς ροή, ο εκτελεστής επιστρέφει ένα αναλυμένο αντικείμενο JSON, το οποίο προωθείται χωρίς αλλαγές.

### Στάδιο 5: Καταγραφή (services/usage.ts)

Μετά την απόκριση (επιτυχή ή αποτυχημένη), καταγράφεται η χρήση:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` από την απόκριση
- `cost_usd` που υπολογίζεται από τα δεδομένα τιμολόγησης
- `latency_ms`, `status`, `error_class` σε περίπτωση αποτυχίας
- Αποθηκεύεται στον πίνακα `usage_history`

Τα τεχνουργήματα καταγραφής κλήσεων (εάν είναι ενεργοποιημένα) εγγράφονται στο `${DATA_DIR}/call_logs/`.

## Εμβάθυνση σε Βασικά Αρχεία

### chatCore.ts (5977 γραμμές)

Ο **κύριος χειριστής αιτημάτων**. Παρά το μέγεθός του, έχει σαφή δομή:

```ts
// Ψευδο-δομή του chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Επικύρωση σώματος
  const body = await parseRequestBody(request);

  // 3. Ανίχνευση μορφής + μετάφραση
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Δρομολόγηση combo
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Συνέχεια στον επόμενο στόχο
    }
  }

  // 5. Εφεδρική λύση έκτακτης ανάγκης
  return await emergencyFallback(body);
}
```

Παρότι είναι μία τεράστια συνάρτηση, είναι οργανωμένη σε **ενότητες με σχόλια** που αντιστοιχούν στη ροή εργασίας των 5 σταδίων.

export async function handleComboChat(body, comboId): Promise<ChatResult> {

### base.ts (1170 LOC)

Ο **αφηρημένος executor** τον οποίο επεκτείνει κάθε κλάση executor (άμεσα ή μέσω του `DefaultExecutor` και άλλων υποκλάσεων). Περιέχει:

- `buildUrl()` — προεπιλεγμένη κατασκευή URL (οι υποκλάσεις το παρακάμπτουν για προσαρμοσμένη)
- `buildHeaders()` — προεπιλεγμένα headers (auth, content-type)
- `transformRequest()` — pass-through από προεπιλογή
- `execute()` — ο κύριος βρόχος HTTP με retry/backoff/breaker

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Χειρίζεται όλους τους παρόχους συμβατούς με OpenAI/Anthropic
  // Οι πάροχοι καταχωρούν διαμορφώσεις (URL, auth, headers) αλλά μοιράζονται τη λογική του executor
}
```

Η συμπεριφορά ανά πάροχο (auth headers, base URL, version headers) διαμορφώνεται μέσω του μητρώου παρόχων, όχι με ξεχωριστές κλάσεις executor.

## Executors (150 modules)

Κυρίως ένα αρχείο ανά provider. Οι κλάσεις executor επεκτείνουν όλες το `BaseExecutor` και παρακάμπτουν ό,τι διαφέρει· τα υπόλοιπα modules είναι βοηθητικά ανά provider (σχήματα εργαλείων, adapters fetch/TTS, χειριστές ιδιοτροπιών).

### Κοινά Μοτίβα

Οι providers επιλύονται μέσω `getExecutor(providerId)`, που επιστρέφει τον διαμορφωμένο executor. Providers συμβατοί με OpenAI/Anthropic χρησιμοποιούν τον `DefaultExecutor` (`executors/default.ts`). Η συμπεριφορά ανά provider (base URL, κεφαλίδες auth, έκδοση API) διαμορφώνεται στο `open-sse/config/providers/`, ενώ οι μετασχηματισμοί του σώματος αιτήματος γίνονται στο `open-sse/translator/`.

**Προσαρμοσμένο URL** ορίζεται μέσω της διαμόρφωσης του provider:

```ts
// Διαμόρφωση provider στο open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Προσαρμοσμένο auth** γίνεται μέσω της διαμόρφωσης auth του μητρώου providers (API key, OAuth, προφίλ κεφαλίδων).

Οι μετασχηματισμοί **προσαρμοσμένου σώματος αιτήματος** (π.χ., το Anthropic διαχωρίζει το `system` από τα `messages`) καταχωρούνται ανά provider στο `open-sse/translator/`.

````

### Το Factory του Executor

Το `executors/index.ts` εξάγει το `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Η επίλυση γίνεται μέσω του `ExecutorRegistry` (`executors/registry.ts`): κάθε εξειδικευμένος executor δηλώνεται στον ενσωματωμένο πίνακα του `executors/index.ts` και καταχωρείται μέσω `registerExecutor(alias, instance)` κατά τη φόρτωση του module· το `getExecutor()` συμβουλεύεται το μητρώο και υποχωρεί σε έναν memoized `DefaultExecutor` για οποιονδήποτε provider χωρίς εξειδικευμένη καταχώρηση. Η πλήρης αντιστοίχιση alias → executor χαρακτηρίζεται από το golden test `tests/unit/executor-map-golden.test.ts`.

## Μεταφραστές

Μετατροπή μεταξύ **3 μορφών**: OpenAI, Anthropic, Gemini, καθώς και του νέου Responses API.

### Πότε πραγματοποιείται η μετατροπή

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Συνήθεις μετατροπές:

- `OpenAI → Anthropic`: ξεχωριστό πεδίο `system`, κεφαλίδα `x-api-key`
- `OpenAI → Gemini`: `contents` αντί για `messages`, `systemInstruction`
- `OpenAI → Responses API`: πίνακας `input`, κατάσταση `previous_response_id`

### Οριακές περιπτώσεις που υποστηρίζονται

- Ρόλος `developer` → `system` για παρόχους εκτός OpenAI
- Ρόλος `system` → συγχώνευση στο πρώτο μήνυμα χρήστη για GLM/ERNIE
- `json_schema` → `responseMimeType` + `responseSchema` του Gemini
- `tools` → μορφή εργαλείων ειδική για κάθε πάροχο
- Παράμετροι συλλογισμού (o1, Claude) → ισοδύναμες παράμετροι ειδικές για κάθε πάροχο

## Διακομιστής MCP

Το `open-sse/mcp-server/` υλοποιεί τον διακομιστή **Model Context Protocol**:

- **110 εργαλεία** (διαχείριση παρόχων, συνδυασμοί, μνήμη, κρυφή μνήμη, συμπίεση, διακομιστής μεσολάβησης, δεξιότητες, παιχνιδοποίηση, πρόσθετα, Notion, Obsidian, τοπικό σώμα κειμένων)
- **3 τρόποι μεταφοράς**: stdio, SSE, Streamable HTTP
- **33 πεδία δικαιωμάτων** για λεπτομερή εξουσιοδότηση

### Καταχώριση εργαλείων

Τα εργαλεία καταχωρίζονται ως αυτόνομα αρχεία στο `open-sse/mcp-server/tools/`, καθένα από τα οποία εξάγει ένα όνομα, ένα σχήμα, έναν χειριστή και ένα πεδίο δικαιωμάτων:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Τρόποι μεταφοράς

```ts
// stdio (χρήση μέσω CLI)
startMcpStdio(server);

// SSE (ροή μέσω HTTP)
startMcpSse(server, port);

// Streamable HTTP (σύγχρονο MCP)
startMcpStreamable(server, port);
```

### Εξουσιοδότηση

Κάθε κλήση εργαλείου υποβάλλεται σε ελέγχους πεδίων δικαιωμάτων (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Μετασχηματιστές

Το `open-sse/transformer/` πραγματοποιεί μετατροπές μεταξύ των μορφών **Chat Completions** και **Responses API**.

### Γιατί χρειάζεται ξεχωριστός μετασχηματιστής;

Το Responses API είναι η νέα μορφή της OpenAI με **συνομιλίες με κατάσταση** (`previous_response_id`). Όταν ένας πελάτης στέλνει ένα αίτημα Responses, το OmniRoute:

1. Μετατρέπει εσωτερικά το Responses → Chat Completions
2. Το στέλνει στον πάροχο (οποιονδήποτε πάροχο που υποστηρίζει Chat Completions)
3. Μετατρέπει την απόκριση ξανά στη μορφή Responses
4. Μεταδίδει τη μετατρεπόμενη απόκριση στον πελάτη μέσω ροής

Ο μετασχηματιστής (`transformer/responsesTransformer.ts`) παρέχει:

```ts
createResponsesApiTransformStream(): TransformStream
```

Αυτός χειρίζεται:

- Συμβάντα `response.output_item.added`
- Συμβάντα `response.output_text.delta`
- Συμβάν `response.completed`
- Αντιστοίχιση κλήσεων εργαλείων (`function_call` ↔ `tool_calls`)

## Διαμόρφωση

Ο φάκελος `open-sse/config/` περιέχει το επίπεδο διαμόρφωσης:

| Αρχείο                         | Σκοπός                                                       |
| ------------------------------ | ------------------------------------------------------------ |

### Σχήμα μητρώου παρόχων

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Η επικύρωση με Zod κατά τη φόρτωση της μονάδας διασφαλίζει ότι όλες οι διαμορφώσεις παρόχων είναι έγκυρες.

## Προσθήκη Νέου Στοιχείου

### Προσθήκη Νέας Υπηρεσίας

1. Δημιουργήστε το `open-sse/services/[serviceName].ts` με σαφώς εστιασμένη αρμοδιότητα
2. Εξαγάγετε την κύρια συνάρτηση χειρισμού και τυχόν σταθερές
3. Προσθέστε δοκιμές μονάδας στο `tests/unit/services/[serviceName].test.mjs`
4. Ενσωματώστε την στη διοχέτευση αιτημάτων στο `handlers/chatCore.ts` (εάν σχετίζεται με τη δρομολόγηση)
5. Ενημερώστε τη λογική δρομολόγησης στο `combo.ts` εάν η υπηρεσία επηρεάζει την επιλογή προορισμού
6. Τεκμηριώστε τη σε αυτό το αρχείο

### Προσθήκη Νέου Εκτελεστή

1. Δημιουργήστε το `open-sse/executors/[provider].ts` επεκτείνοντας το `BaseExecutor`
2. Καταχωρίστε τον στο `config/providerRegistry.ts`
3. Προσθέστε τον στο εργοστάσιο του `executors/index.ts`
4. Προσθέστε δοκιμές μονάδας για τον εκτελεστή
5. Τεκμηριώστε τον στο `docs/architecture/ARCHITECTURE.md`

### Προσθήκη Νέου Εργαλείου MCP

1. Δημιουργήστε ή ενημερώστε το `open-sse/mcp-server/tools/[category]Tools.ts`
2. Ορίστε σχήμα Zod για τις εισόδους
3. Καταχωρίστε το εργαλείο στο `mcp-server/index.ts`
4. Προσθέστε το στον πίνακα εμβελειών στο `mcp-server/auth/`
5. Προσθέστε δοκιμές μονάδας
