> **Πηγή αναφοράς:** `src/lib/memory/` και `src/app/api/memory/`
> **Τελευταία ενημέρωση:** 2026-06-28 — v3.8.40 (απενεργοποίηση από προεπιλογή + κάλυψη εκκρεμοτήτων κβαντοποίησης int8)

Το OmniRoute παρέχει μόνιμη μνήμη συνομιλιών με κλειδί ανά API key (και
προαιρετικά ανά session id). Οι μνήμες εξάγονται αυτόματα από τις αποκρίσεις του LLM
μέσω ελαφριάς αντιστοίχισης μοτίβων με κανονικές εκφράσεις και εισάγονται ξανά σε επόμενα
αιτήματα ως αρχικό μήνυμα συστήματος (ή ως πρώτο μήνυμα χρήστη για παρόχους που
απορρίπτουν τον ρόλο συστήματος).

> **Η μνήμη είναι ΑΠΕΝΕΡΓΟΠΟΙΗΜΕΝΗ από προεπιλογή (v3.8.30+).** Το `DEFAULT_MEMORY_SETTINGS.enabled`
> είναι πλέον `false` (`src/lib/memory/settings.ts`). Η ενεργοποίηση της μνήμης εισάγει έως
> `maxTokens` (~2k) ανακτημένου περιεχομένου σε **κάθε** αίτημα συνομιλίας, το οποίο
> χρεώνεται — ένα απροσδόκητο κόστος για νέες εγκαταστάσεις και για πελάτες που διαχειρίζονται
> το δικό τους περιεχόμενο. Ενεργοποιήστε τη ρητά από τις **Ρυθμίσεις → Μνήμη** (η καρτέλα
> `MemorySkillsTab` εμφανίζει μια προειδοποιητική επισήμανση κόστους token όταν η μνήμη είναι ενεργοποιημένη).
> Ένας πελάτης μπορεί να εξαιρέσει ένα μεμονωμένο αίτημα χρησιμοποιώντας την κεφαλίδα αιτήματος
> `x-omniroute-no-memory` (`true`/`1`/`yes`) — δείτε τον πίνακα κεφαλίδων αιτημάτων στο
> [API_REFERENCE.md](../reference/API_REFERENCE.md). Ένα αίτημα χωρίς μνήμη ορίζει το
> `memoryOwnerId = null`, γεγονός που απενεργοποιεί **τόσο** την εισαγωγή μνήμης όσο και την εισαγωγή δεξιοτήτων
> για το συγκεκριμένο αίτημα (`open-sse/handlers/chatCore/headers.ts::isNoMemoryRequested`).

Η μνήμη έχει **πεδίο εφαρμογής ανά API key**, όχι ανά χρήστη — κάθε αίτημα που επαληθεύεται
με το ίδιο API key μοιράζεται το ίδιο σύνολο μνήμης, με προαιρετικό περαιτέρω
περιορισμό ανά `sessionId`.

## Αρχιτεκτονική

```
Πελάτης → /v1/chat/completions (το apiKeyInfo επιλύεται ανάντη)
  → handleChatCore() [open-sse/handlers/chatCore.ts]
    → resolveMemoryOwnerId(apiKeyInfo)        # εξάγει το id
    → getMemorySettings()                     # ρυθμίσεις από την cache
    → shouldInjectMemory(body, {enabled})     # πύλη ελέγχου
    → retrieveMemories(apiKeyId, config)      # SQL + FTS5 + προαιρετικό διάνυσμα
    → injectMemory(body, memories, provider)  # μήνυμα συστήματος ή χρήστη
  → κλήση προς τον ανάντη πάροχο
  → κατά την απόκριση: extractFacts(text, apiKeyId, sessionId)  # χωρίς αποκλεισμό
    → setImmediate → createMemory(fact) ανά αντιστοιχία
                   → embed(content) + upsertVector(id, vec)
```

Τα σημεία κλήσης εισαγωγής και εξαγωγής είναι συνδεδεμένα στο
`open-sse/handlers/chatCore.ts` (αναζητήστε τα `retrieveMemories`, `injectMemory`
και `extractFacts`).

## Αρχιτεκτονική μηχανής (επίλυση 3 επιπέδων)

Η Μηχανή Μνήμης επιλύει τη διαδρομή ανάκτησης κατά τον χρόνο εκτέλεσης, βάσει της διαθέσιμης
υποδομής και των ρυθμίσεων. Υπάρχουν τρία επίπεδα, τα οποία εφαρμόζονται κατά σειρά προτεραιότητας:

```
  ┌─────────────────────────────────────────────────────────────┐
  │  ΕΠΙΠΕΔΟ 0 — Λέξεις-κλειδιά (FTS5)                          │
  │  Διαθεσιμότητα βάσει δοκιμής: FTS5 όταν η έκδοση SQLite     │
  │  το υποστηρίζει (better-sqlite3 / node:sqlite / bun:sqlite)·│
  │  μη διαθέσιμο σε εκδόσεις χωρίς FTS5 (π.χ. sql.js/WASM —    │
  │  "no such module: fts5"). Χρησιμοποιείται όταν strategy =   │
  │  "exact" ή ως εφεδρεία· η ένδειξη keyword στην κατάσταση    │
  │  της μηχανής αντικατοπτρίζει το αποτέλεσμα της δοκιμής.     │
  └──────────────────────────────────┬──────────────────────────┘
                                     │ strategy = semantic|hybrid;
                                     ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  ΕΠΙΠΕΔΟ 1 — Ενσωματωμένο διάνυσμα (sqlite-vec)             │
  │  Το sqlite-vec v0.1.9 φορτώνεται μέσω db.loadExtension().    │
  │  KNN εξαντλητικής αναζήτησης σε διανύσματα Float32. Ενεργό  │
  │  όταν:                                                       │
  │   • το sqlite-vec loadExtension ολοκληρώνεται επιτυχώς       │
  │   • είναι διαθέσιμη μια πηγή embeddings (remote | static |  │
  │     transformers) που μπορεί να παράγει Float32Array         │
  │   • υπάρχει ο πίνακας vec_memories (δημιουργείται κατά την   │
  │     πρώτη κλήση ready())                                     │
  └──────────────────────────────────┬──────────────────────────┘
                                     │ qdrant.enabled;
                                     ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  ΕΠΙΠΕΔΟ 2 — Qdrant (προαιρετική εξωτερική βάση διανυσμάτων)│
  │  Όταν ενεργοποιείται, αντικαθιστά το sqlite-vec για          │
  │  semantic/hybrid. Απαιτεί εκτελούμενο instance του Qdrant +  │
  │  ρυθμισμένα host/port.                                       │
  └─────────────────────────────────────────────────────────────┘
```

Η υποβάθμιση είναι αυτόματη και διαφανής:

- Αν αποτύχει η φόρτωση του sqlite-vec, το επίπεδο 1 δεν είναι διαθέσιμο → γίνεται μετάπτωση στο επίπεδο 0.
- Αν η πηγή embeddings επιστρέψει σφάλμα, το επίπεδο 1 μεταπίπτει στο επίπεδο 0.
- Αν το Qdrant δεν είναι υγιές, το επίπεδο 2 μεταπίπτει στο επίπεδο 1 (ή στο επίπεδο 0, αν και το επίπεδο 1
  δεν είναι επίσης διαθέσιμο).

## Πηγές ενσωματώσεων

Το επίπεδο ενσωματώσεων (`src/lib/memory/embedding/`) επιλέγει την πηγή που θα χρησιμοποιηθεί
βάσει του `MemorySettingsExtended.embeddingSource`:

| Πηγή           | Περιγραφή                                                                                         | Απαιτείται κλειδί | Ψυχρή εκκίνηση   |
| -------------- | ------------------------------------------------------------------------------------------------- | ----------------- | ---------------- |
| `remote`       | Χρησιμοποιεί το API ενσωματώσεων ενός ρυθμισμένου παρόχου (OpenAI, Cohere κ.λπ.)                  | Ναι               | Καμία            |
| `static`       | Τοπική ενσωμάτωση μέσω πίνακα αναζήτησης με `potion-base-8M` (WordPiece + συγκέντρωση μέσου όρου) | Όχι               | ~200ms           |
| `transformers` | Τοπική εξαγωγή συμπερασμάτων ONNX μέσω `@huggingface/transformers` v4, `all-MiniLM-L6-v2`         | Όχι               | ~3s + ~400MB RAM |
| `auto`         | Επίλυση κατά την εκτέλεση: remote (αν υπάρχει κλειδί) → static → transformers → null              | Εξαρτάται         | Εξαρτάται        |

**Σειρά επίλυσης για το `auto`:**

1. Εύρεση του πρώτου παρόχου στο `listEmbeddingProviders()` με `hasKey === true` → `remote`.
2. Αν `settings.staticEnabled === true` → `static`.
3. Αν `settings.transformersEnabled === true` → `transformers`.
4. Διαφορετικά → `null` (υποβάθμιση σε αναζήτηση λέξεων-κλειδιών FTS5).

Η κρυφή μνήμη ενσωματώσεων (`src/lib/memory/embedding/cache.ts`) χρησιμοποιεί έναν
χάρτη LRU στη μνήμη, με κλειδί `${source}:${model}:${dim}:${sha256(text)}`, που περιορίζεται σε
`MEMORY_EMBEDDING_CACHE_MAX` καταχωρίσεις (προεπιλογή 1000) και έχει TTL
`MEMORY_EMBEDDING_CACHE_TTL_MS` (προεπιλογή 5 λεπτά). Είναι κοινόχρηστη μεταξύ όλων των καλούντων
κατά τον κύκλο ζωής κάθε διεργασίας.

## Υβριδικό RRF (k=60)

Όταν `strategy = "hybrid"` και ο χώρος αποθήκευσης διανυσμάτων είναι διαθέσιμος, η ανάκτηση χρησιμοποιεί
Reciprocal Rank Fusion για τη συγχώνευση των αποτελεσμάτων FTS5 και διανυσματικής αναζήτησης:

```
RRF(d) = Σ  1 / (k + rank_i(d))      όπου k = 60 (ρυθμιζόμενο μέσω MEMORY_RRF_K)
          i
```

Συγκεκριμένα:

1. Εκτέλεση αναζήτησης FTS5 → ταξινομημένη λίστα `R_fts` (θέση 1..N).
2. Εκτέλεση διανυσματικής αναζήτησης KNN → ταξινομημένη λίστα `R_vec` (θέση 1..M).
3. Για κάθε μοναδικό `memoryId`:  
   `rrf_score = 1/(60 + fts_rank)` + `1/(60 + vec_rank)` (0 αν δεν βρίσκεται στη λίστα).
4. Ταξινόμηση κατά `rrf_score` DESC και εφαρμογή διαδοχικής επιλογής βάσει του προϋπολογισμού διακριτικών.

Το RRF είναι ευρέως γνωστό ως αποτελεσματικό χωρίς να απαιτεί κανονικοποίηση βαθμολογιών μεταξύ
ετερογενών συστημάτων ανάκτησης. Η προεπιλεγμένη τιμή `k=60` προέρχεται από την αρχική
δημοσίευση των Cormack et al. και λειτουργεί καλά για μικρά σώματα δεδομένων (<10k μνήμες).

## Αναδρομική συμπλήρωση (οκνηρή + επανευρετηρίαση)

Όταν αλλάζει το μοντέλο ενσωματώσεων (ανιχνεύεται μέσω του `embedding_signature`), ο
χώρος αποθήκευσης διανυσμάτων ανακατασκευάζεται και όλες οι υπάρχουσες μνήμες επισημαίνονται με
`needs_reindex = 1` στον πίνακα `memories`.

**Οκνηρή αναδρομική συμπλήρωση**: Κατά την επόμενη ανάκτηση, κάθε μνήμη που δεν διαθέτει διανυσματική καταχώριση
ενσωματώνεται και εισάγεται στο `vec_memories` πριν εκτελεστεί η αναζήτηση. Αυτό
επιμερίζει το κόστος της αναδρομικής συμπλήρωσης στις πραγματικές αιτήσεις, χωρίς να εμποδίζει την εκκίνηση.

**Ρητή επανευρετηρίαση**: Η καρτέλα Engine στο `/dashboard/memory` παρέχει ένα
κουμπί "Επανευρετηρίαση τώρα" που καλεί το `POST /api/memory/reindex`. Ο χειριστής καλεί
το `runReindexBatch()` από το `src/lib/memory/reindex.ts`, το οποίο επεξεργάζεται έως
`limit` εκκρεμείς καταχωρίσεις ανά αίτημα. Η πρόοδος μπορεί να ελέγχεται περιοδικά μέσω του
`GET /api/memory/engine-status` (`vectorStore.needsReindex`).

Ο πίνακας `memory_vec_meta` (μετεγκατάσταση `083_memory_vec.sql`) αποθηκεύει:

- `active_dim` — τρέχουσα διάσταση διανύσματος (null = δεν έχει βαθμονομηθεί ακόμη).
- `embedding_signature` — `${source}:${model}:${dim}` που χρησιμοποιείται για την ανίχνευση αλλαγών.
- `last_reset_at` — χρονική σήμανση της τελευταίας πλήρους επαναφοράς.
- `vec_loaded` — σημαία 0/1 που υποδεικνύει αν το sqlite-vec φορτώθηκε επιτυχώς.

## Επέκταση ρυθμίσεων

Εννέα πεδία ενσωματώσεων και διανυσμάτων είναι διαθέσιμα στο `MemorySettingsExtended` στο
`src/shared/schemas/memory.ts` και διατηρούνται μέσω του `src/lib/db/settings.ts`:

| Πεδίο                    | Τύπος                                              | Προεπιλογή | Περιγραφή                                                               |
| ------------------------ | -------------------------------------------------- | ---------- | ----------------------------------------------------------------------- |
| `embeddingSource`        | `"remote" \| "static" \| "transformers" \| "auto"` | `"auto"`   | Ποια πηγή ενσωματώσεων θα χρησιμοποιείται                               |
| `embeddingProviderModel` | `string \| null`                                   | `null`     | Πάροχος/μοντέλο σε μορφή `provider/model`                               |
| `customBaseUrl`          | `string \| null`                                   | `null`     | Βασικό URL τελικού σημείου συμβατού με OpenAI μόνο για τη Μνήμη         |
| `customModelId`          | `string \| null`                                   | `null`     | Αναγνωριστικό μοντέλου που αποστέλλεται στο προσαρμοσμένο τελικό σημείο |
| `transformersEnabled`    | `boolean`                                          | `false`    | Ρητή ενεργοποίηση του Transformers.js (MiniLM, ~400MB)                  |
| `staticEnabled`          | `boolean`                                          | `false`    | Ρητή ενεργοποίηση του τοπικού στατικού μοντέλου potion-base-8M          |
| `rerankEnabled`          | `boolean`                                          | `false`    | Ενεργοποίηση του βήματος ανακατάταξης (προσθέτει +200-500ms/αίτημα)     |
| `rerankProviderModel`    | `string \| null`                                   | `null`     | Πάροχος/μοντέλο ανακατάταξης σε μορφή `provider/model`                  |

Το `rerankProviderModel` επιλύεται από το `POST /v1/rerank` (καλείται μέσω loopback), επομένως αποδέχεται οτιδήποτε αποδέχεται αυτή η διαδρομή: ένα επιμελημένο μοντέλο ανακατάταξης στο cloud (`cohere/rerank-v3.5`, `jina-ai/jina-reranker-v3.5`, …) ή έναν κόμβο παρόχου συμβατού με OpenAI ως `<node-prefix>/<model>` (π.χ. `skilled-mini/bge-reranker-v2-m3` για ένα σύστημα TEI/Infinity). Οι κόμβοι loopback είναι πάντα επιλέξιμοι· ένας κόμβος σε άλλον κεντρικό υπολογιστή (LAN, Tailscale) απαιτεί επιπλέον τη σημαία δυνατότητας `RERANK_REMOTE_PROVIDER_NODES` και πρέπει να πληροί την πολιτική εξερχόμενων URL παρόχου — δείτε τις [Σημαίες δυνατοτήτων](../reference/FEATURE_FLAGS.md). Ο επιλογέας του πίνακα ελέγχου παραθέτει επιμελημένους παρόχους μαζί με τοπικούς κόμβους· οποιαδήποτε έγκυρη συμβολοσειρά `provider/model` μπορεί να οριστεί απευθείας μέσω του `PUT /api/settings/memory`.
| `vectorStore` | `"sqlite-vec" \| "qdrant" \| "auto"` | `"auto"` | Ποιο διανυσματικό backend θα χρησιμοποιείται |

Αυτά διατίθενται μέσω του `GET /PUT /api/settings/memory` (σχήμα `MemorySettingsExtendedSchema`).

Για την πηγή `remote`, η Μνήμη αποδέχεται επίσης τις προαιρετικές ρυθμίσεις `customBaseUrl` και
`customModelId`. Μαζί επιλέγουν ένα τελικό σημείο `/embeddings` συμβατό με OpenAI
και ένα μοντέλο, χωρίς να αλλάζουν το καθολικό μητρώο ενσωματώσεων. Το τελικό σημείο
κανονικοποιείται πριν από τη χρήση και ελέγχεται από την πολιτική εξερχόμενων URL παρόχου: απαιτείται
HTTP(S), τα ενσωματωμένα διαπιστευτήρια και οι συμβολοσειρές ερωτήματος απορρίπτονται, ενώ οι διευθύνσεις
μεταδεδομένων cloud παραμένουν αποκλεισμένες. Οι κενές τιμές διατηρούν τον επιλεγμένο πάροχο μητρώου. Τα σφάλματα
που επιστρέφονται στον πίνακα ελέγχου εξυγιαίνονται και τα διαπιστευτήρια του τελικού σημείου δεν καταγράφονται ποτέ.

| `id`                        | `TEXT PRIMARY KEY` | UUID που δημιουργείται μέσω `crypto.randomUUID()`                                      |
| `api_key_id`                | `TEXT NOT NULL`    | Κλειδί API κατόχου                                                                     |
| `session_id`                | `TEXT`             | Προαιρετική εμβέλεια ανά συνομιλία                                                     |
| `type`                      | `TEXT NOT NULL`    | Ένα από τα `factual`, `episodic`, `procedural`, `semantic`                             |
| `key`                       | `TEXT`             | Σταθερό κλειδί upsert, π.χ. `preference:i_prefer_python`                               |
| `content`                   | `TEXT NOT NULL`    | Το πραγματικό κείμενο του γεγονότος                                                    |
| `metadata`                  | `TEXT`             | Τμήμα JSON (κατηγορία, extractedAt, προέλευση, ...)                                    |
| `created_at` / `updated_at` | `TEXT`             | Συμβολοσειρές ISO 8601                                                                 |
| `expires_at`                | `TEXT`             | Προαιρετική λήξη· `NULL` σημαίνει μόνιμο                                               |
| `memory_id`                 | `INTEGER UNIQUE`   | Προστέθηκε από το `023_fix_memory_fts_uuid.sql` για τη γεφύρωση UUID ↔ rowids του FTS5 |

Ευρετήρια: `api_key_id`, `session_id`, `type`, `expires_at`, καθώς και το μοναδικό
ευρετήριο `memory_id`.

**Σημασιολογία upsert**: Η `createMemory()` αναζητά μια υπάρχουσα γραμμή με το ίδιο
`(api_key_id, key)` και την ενημερώνει επιτόπου όταν βρεθεί (συγχωνεύοντας το `metadata` μέσω
ρηχής εξάπλωσης). Αυτό αποτρέπει την απεριόριστη αύξηση του πίνακα από επαναλαμβανόμενες
δηλώσεις προτιμήσεων.

### Αναζήτηση πλήρους κειμένου (εικονικός πίνακας `memory_fts`)

Το `022_add_memory_fts5.sql` δημιουργεί έναν εικονικό πίνακα FTS5 πάνω από τα `content` και
`key`. Το `023_fix_memory_fts_uuid.sql` διορθώνει ένα πραγματικό σφάλμα όπου το πρωτεύον
κλειδί UUID δεν μπορούσε να συνδεθεί με το ακέραιο rowid του FTS5 — η μετεγκατάσταση προσθέτει τη
στήλη `memory_id`, δημιουργεί εκ νέου τον πίνακα FTS και συνδέει εναύσματα
(`memory_fts_ai`, `memory_fts_ad`, `memory_fts_au`) που διατηρούν το FTS συγχρονισμένο κατά τα
INSERT, DELETE και UPDATE.

Χρησιμοποιείται από το `retrieval.ts` για τις στρατηγικές `semantic` και `hybrid` (δείτε παρακάτω).
Ο κώδικας ανάκτησης εκτελεί έλεγχο προστασίας με `hasTable("memory_fts")` και επιστρέφει στη
χρονολογική σειρά αν λείπει ο πίνακας FTS ή αν το ερώτημα FTS προκαλέσει εξαίρεση.

### Προαιρετικό: Qdrant (διανυσματική αποθήκη επιπέδου 2)

Το `src/lib/memory/qdrant.ts` υλοποιεί μια προαιρετική ενσωμάτωση Qdrant ως διανυσματική
αποθήκη επιπέδου 2. Η ανάκτηση δρομολογείται στο Qdrant μόνο όταν ο επιλογέας μηχανής
`memoryVectorStore === "qdrant"` — η προεπιλογή `"auto"` (και το `"sqlite-vec"`)
**ποτέ** δεν επιλέγει το Qdrant. Ο διακόπτης της καρτέλας Engine ορίζει **και τα δύο**, `qdrantEnabled` και
`memoryVectorStore`, μαζί: η ενεργοποίηση καθιστά το Qdrant κύρια αποθήκη, ενώ η απενεργοποίηση
το επαναφέρει σε `"auto"` (#5597 — πριν από αυτήν τη διόρθωση, η ενεργοποίηση ήταν ανενεργή επειδή τίποτα
δεν έγραφε στον επιλογέα μηχανής). Αν το Qdrant δεν είναι προσβάσιμο ή δεν επιστρέψει τίποτα, η ανάκτηση
επιστρέφει διαδοχικά σε sqlite-vec → FTS5.

- `upsertSemanticMemoryPoint()` — δημιουργεί ενσωμάτωση για το `key + content` με το διαμορφωμένο
  μοντέλο ενσωμάτωσης, διασφαλίζει ότι υπάρχει η συλλογή (δημιουργεί διανύσματα
  απόστασης συνημιτόνου κατά την πρώτη χρήση) και εισάγει ή ενημερώνει ένα σημείο με ωφέλιμο φορτίο `{memoryId,
apiKeyId, sessionId, key, content, metadata, createdAtUnix, expiresAtUnix}`.
- `searchSemanticMemory(query, topK, scope)` — δημιουργεί ενσωμάτωση για το ερώτημα, πραγματοποιεί αναζήτηση στη
  συλλογή με φίλτρο `kind = "omniroute_memory"` και προαιρετικά κατά
  `apiKeyId` / `sessionId`. Περιορίζει το `topK` στο εύρος `[1, 20]`.
- `deleteSemanticMemoryPoint(id)` — διαγραφή μεμονωμένου σημείου. Καλείται από τη
  `deleteMemory()` αφού αφαιρεθεί η γραμμή του SQLite (D15).
- `cleanupSemanticMemoryPoints({retentionDays})` — μαζική διαγραφή σημείων των οποίων το
  `expiresAtUnix` βρίσκεται στο παρελθόν ή των οποίων το `createdAtUnix` είναι παλαιότερο από το
  όριο διατήρησης. Πραγματοποιεί πρώτα καταμέτρηση, ώστε ο πίνακας ελέγχου να μπορεί να εμφανίζει τους πραγματικούς αριθμούς.
- `checkQdrantHealth()` — έλεγχος εύρυθμης λειτουργίας `GET /readyz` με μέτρηση καθυστέρησης.

Το περιβάλλον χρήστη των ρυθμίσεων παρέχει τη διαμόρφωση του Qdrant, έλεγχο εύρυθμης λειτουργίας, δοκιμή σημασιολογικής αναζήτησης
και εκκαθάριση στην **καρτέλα Engine** του `/dashboard/memory`. Οι αντίστοιχες
διαδρομές στο `src/app/api/settings/qdrant/` είναι όλες συνδεδεμένες από την v3.8.6:

| Διαδρομή                                | Μέθοδος       | Περιγραφή                             |
| --------------------------------------- | ------------- | ------------------------------------- |
| `/api/settings/qdrant`                  | `GET` / `PUT` | Ανάγνωση / ενημέρωση ρυθμίσεων Qdrant |
| `/api/settings/qdrant/health`           | `GET`         | Έλεγχος λειτουργίας + καθυστέρηση     |
| `/api/settings/qdrant/search`           | `POST`        | Δοκιμή σημασιολογικής αναζήτησης      |
| `/api/settings/qdrant/cleanup`          | `POST`        | Αφαίρεση ληγμένων / παλαιών σημείων   |
| `/api/settings/qdrant/embedding-models` | `GET`         | Λίστα διαθέσιμων μοντέλων ενσωμάτωσης |

**Σημειώσεις συμπεριφοράς (τι να αναμένετε):**

- **Επιλογή μηχανής** — η ενεργοποίηση του Qdrant στην καρτέλα Engine το καθιστά το κύριο
  αποθετήριο (ορίζει `memoryVectorStore="qdrant"`), ενώ η απενεργοποίησή του επαναφέρει την τιμή σε `"auto"` (#5597).
- **Χωρίς αναδρομική συμπλήρωση** — μόνο οι μνήμες που δημιουργούνται/ενημερώνονται **μετά** την ενεργοποίηση του Qdrant
  εγγράφονται σε αυτό (διπλή εγγραφή χωρίς αναμονή ολοκλήρωσης). Οι προϋπάρχουσες μνήμες SQLite **δεν**
  μεταφέρονται· η επιλογή "Reindex Now" ανακατασκευάζει μόνο το ευρετήριο sqlite-vec, όχι το Qdrant.
- **Η διάσταση διανύσματος ανιχνεύεται αυτόματα** από την πραγματική ενσωμάτωση κατά την πρώτη χρήση — δεν
  υπάρχει πεδίο διάστασης προς συμπλήρωση. Η αλλαγή του μοντέλου ενσωμάτωσης αφού υπάρχει ήδη μια συλλογή
  **δεν** αντιμετωπίζεται αυτόματα: η υπάρχουσα συλλογή παραμένει ανέπαφη, ενώ οι εγγραφές/αναζητήσεις
  με ασύμβατες διαστάσεις αποτυγχάνουν και επιστρέφουν στο sqlite-vec. Δημιουργήστε ξανά τη συλλογή
  (με νέο όνομα ή διαγράφοντάς την στο Qdrant) για να αλλάξετε μοντέλο ενσωμάτωσης.
- **Μετρική απόστασης** — πάντοτε **Cosine** (είναι ενσωματωμένη στον κώδικα κατά τη δημιουργία της συλλογής και δεν
  μπορεί να διαμορφωθεί).
- **Έλεγχος ταυτότητας** — μόνο μέσω κλειδιού API (αποστέλλεται ως κεφαλίδα `api-key`· προαιρετικό για τοπικό Docker
  χωρίς έλεγχο ταυτότητας). Δεν χρησιμοποιούνται JWT/RBAC.
- **Πεδία διαμόρφωσης** — το περιβάλλον χρήστη παρέχει τα `host`, `port`, `collection`, `embeddingModel`,
  `apiKey`. Τα `vectorSize` / `hnswEfConstruct` διατίθενται μόνο μέσω περιβάλλοντος/DB και το `vectorSize` δεν
  χρησιμοποιείται για τη δημιουργία της συλλογής (η διάσταση προκύπτει από την ενσωμάτωση).

### Κβαντισμός διανυσμάτων (int8 — προαιρετικός, και για τα δύο συστήματα υποστήριξης)

Και τα δύο συστήματα υποστήριξης διανυσμάτων υποστηρίζουν **προαιρετικό κβαντισμό int8**, ώστε να μειώνεται το αποτύπωμα
μνήμης των αποθηκευμένων διανυσμάτων (~4× μικρότερο από το Float32) με μικρό κόστος στην ανάκληση.
Η προεπιλογή είναι **ανενεργή** και στα δύο — τα διανύσματα διατηρούν πλήρη ακρίβεια, εκτός αν η δυνατότητα
ενεργοποιηθεί ρητά.

| Σύστημα υποστήριξης | Ρύθμιση                          | Τύπος                          | Προεπιλογή | Σημείο ανάγνωσης                                            |
| ------------------- | -------------------------------- | ------------------------------ | ---------- | ----------------------------------------------------------- |
| Qdrant              | `qdrantQuantization` (κλειδί DB) | `"none" \| "int8" \| "binary"` | `"none"`   | `src/lib/memory/qdrant.ts::normalizeQdrantConfig()`         |
| sqlite-vec          | `MEMORY_VEC_QUANTIZATION` (env)  | `"none" \| "int8"`             | `"none"`   | `src/lib/memory/vectorStore.ts::requestedVecQuantization()` |

- Το **Qdrant** διαμορφώνεται ανά παρουσία μέσω του κλειδιού ρύθμισης `qdrantQuantization`
  (παρέχεται ως πεδίο `quantization` στο `PUT /api/settings/qdrant`). Όταν είναι
  `"int8"`, η `buildQuantizationConfig()` ζητά βαθμωτό κβαντισμό
  (`always_ram`, ποσοστημόριο `0.99`) και οι αναζητήσεις ενεργοποιούν το `rescore: true`, ώστε τα
  διανύσματα πλήρους ακρίβειας να βελτιώνουν το σύνολο υποψηφίων int8.
- Ο κβαντισμός του **sqlite-vec** πραγματοποιείται **μόνο μέσω περιβάλλοντος** (δεν αποτελεί ρύθμιση DB): ορίστε
  `MEMORY_VEC_QUANTIZATION=int8` για να αποθηκεύονται τα τοπικά διανύσματα ως στήλη `int8[dim]`
  μέσω `vec_quantize_int8(?, 'unit')`. Η επιλεγμένη λειτουργία ενσωματώνεται στο
  `embedding_signature` (με κατάληξη `:int8`), επομένως η εναλλαγή λειτουργίας ενεργοποιεί πλήρη
  επαναδημιουργία ευρετηρίου του πίνακα `vec_memories` — την ίδια διαδρομή οκνηρής αναδρομικής συμπλήρωσης που χρησιμοποιείται όταν
  αλλάζει το μοντέλο ενσωμάτωσης.

## Τύποι Μνήμης

`MemoryType` (`src/lib/memory/types.ts`):

| Τύπος        | Χρησιμοποιείται για                                                                           |
| ------------ | --------------------------------------------------------------------------------------------- |
| `factual`    | Προτιμήσεις, σταθερά στοιχεία χρήστη, μοτίβα συμπεριφοράς                                     |
| `episodic`   | Αποφάσεις που συνδέονται με μια συγκεκριμένη στιγμή ("Επέλεξα Postgres")                      |
| `procedural` | Μνήμη ροής εργασίας / οδηγιών χρήσης (δεσμευμένο· δεν υπάρχει αυτόματη εξαγωγή προς το παρόν) |
| `semantic`   | Δεσμευμένο για καταχωρίσεις διανυσματικής αποθήκευσης                                         |

Η στρατηγική ανάκτησης του `MemoryConfig` είναι μία από τις `exact`, `semantic` ή `hybrid`,
και το πεδίο εφαρμογής είναι ένα από τα `session`, `apiKey` ή `global`. Το προεπιλεγμένο πεδίο εφαρμογής από το
`getMemorySettings()` είναι το `apiKey`.

## Εξαγωγή Στοιχείων (`extraction.ts`)

Η εξαγωγή **βασίζεται σε κανονικές εκφράσεις**, όχι σε LLM — εκτελείται εντός της διεργασίας με
`setImmediate()`, ώστε να μην αποκλείει ποτέ τη ροή απόκρισης:

- **Μοτίβα προτιμήσεων** → `MemoryType.FACTUAL`
  (π.χ. `Προτιμώ …`, `Μου αρέσει πολύ …`, `το αγαπημένο μου είναι …`, `Μισώ …`)
- **Μοτίβα αποφάσεων** → `MemoryType.EPISODIC`
  (π.χ. `Θα χρησιμοποιήσω …`, `Επέλεξα …`, `Κατέληξα στο …`, `Πρόκειται να υιοθετήσω …`)
- **Μοτίβα συμπεριφοράς** → `MemoryType.FACTUAL`
  (π.χ. `Συνήθως …`, `Πάντα …`, `Τείνω να …`)

Κάθε αντιστοίχιση εξυγιαίνεται (`trim`, σύμπτυξη κενών διαστημάτων, περιορισμός στους 500 χαρακτήρες),
αποδιπλοποιείται εντός της παρτίδας μέσω ενός σταθερού `factKey(category, content)` και
αποθηκεύεται μέσω του `createMemory()` με μεταδεδομένα
`{category, extractedAt, source: "llm_response"}`. Το κείμενο εισόδου περιορίζεται στα
64 KiB (`MAX_EXTRACTION_TEXT_LENGTH`) — όταν είναι μεγαλύτερο, χρησιμοποιείται το **τελικό τμήμα** του κειμένου,
ώστε να συμμετέχει πάντα το πιο πρόσφατο περιεχόμενο του βοηθού.

Το `extractFactsFromText(text)` εξάγεται για δοκιμές και επιστρέφει τα δομημένα
στοιχεία χωρίς να τα αποθηκεύει.

## Ανάκτηση (`retrieval.ts`)

Το `retrieveMemories(apiKeyId, config)` είναι το κύριο σημείο εισόδου. Εκτελεί τα εξής:

1. Κανονικοποιεί και επικυρώνει τη διαμόρφωση μέσω του `MemoryConfigSchema`.
2. Επιστρέφει αμέσως `[]` όταν το `enabled` είναι false ή το `maxTokens <= 0`.
3. Περιορίζει το `maxTokens` στο εύρος `[1, 8000]`.
4. Εντοπίζει αν υπάρχει ο σύγχρονος πίνακας `memories` (σε αντίθεση με τον παλαιό πίνακα `memory`),
   ώστε οι παλαιότερες βάσεις δεδομένων να συνεχίσουν να λειτουργούν.
5. Δημιουργεί το βασικό ερώτημα με έλεγχο λήξης
   (`expires_at IS NULL OR datetime(expires_at) > datetime('now')`), προαιρετικό
   πεδίο εφαρμογής συνεδρίας και προαιρετικό όριο `retentionDays`.
6. Διακλαδώνεται ανάλογα με τη στρατηγική:
   - **`exact`** (προεπιλογή): χρονολογική σειρά `ORDER BY created_at DESC LIMIT 100`.
   - **`semantic`**: αν υπάρχει το `config.query` και το `memory_fts`, εκτελεί JOIN με
     `memory_fts MATCH ?` και ταξινομεί κατά κατάταξη FTS· επιστρέφει στη χρονολογική σειρά
     όταν το FTS επιστρέφει 0 γραμμές.
   - **`hybrid`**: ένωση των αποτελεσμάτων FTS (υψηλότερη συνάφεια) και του
     χρονολογικού συνόλου, με αποδιπλοποίηση βάσει id.
7. Υπολογίζει μια βαθμολογία συνάφειας λέξεων-κλειδιών (`getRelevanceScore`) στα
   `content`, `key` και στο JSON `metadata`, όταν παρέχεται ερώτημα. Οι γραμμές με
   μηδενική βαθμολογία φιλτράρονται.
8. Ταξινομεί κατά φθίνουσα βαθμολογία και, στη συνέχεια, κατά φθίνουσα τιμή `createdAt`.
9. Διατρέχει την ταξινομημένη λίστα και αποδέχεται καταχωρίσεις όσο το σωρευτικό
   `estimateTokens(content)` (≈ `length / 4`) παραμένει εντός του ορίου. Επιστρέφει
   πάντα τουλάχιστον μία καταχώριση όταν υπάρχει οποιαδήποτε αντιστοίχιση.

Το `estimateTokens` εξάγεται και χρησιμοποιείται από την ανάκτηση, τη σύνοψη και το εργαλείο MCP
`omniroute_memory_search`.

## Έγχυση (`injection.ts`)

`injectMemory(request, memories, provider)`:

1. Συνενώνει όλα τα περιεχόμενα μνήμης σε μία ενιαία συμβολοσειρά `Memory context: …`.
2. Επιλέγει μια στρατηγική βάσει του ονόματος του παρόχου:
   - **Μήνυμα συστήματος** (προεπιλογή για OpenAI, Anthropic, Gemini, …) — προσθέτει
     ένα `{role: "system", content: memoryText}` πριν από τυχόν υπάρχοντα μηνύματα
     συστήματος, ώστε οι προτροπές συστήματος του χρήστη να εξακολουθούν να έχουν προτεραιότητα.
   - **Μήνυμα χρήστη** (εφεδρική επιλογή) — για παρόχους στο
     `PROVIDERS_WITHOUT_SYSTEM_MESSAGE`: `o1`, `o1-mini`, `o1-preview`,
     `glm`, `glmt`, `glm-cn`, `zai`, `qianfan`. Αυτοί απορρίπτουν τον ρόλο συστήματος
     και διαφορετικά θα επέστρεφαν 400 (βλ. ζήτημα #1701 για GLM/Zhipu).
3. Καταγράφει το πλήθος, τη στρατηγική και το μοντέλο στο `memory.injection.injected`.

Το `providerSupportsSystemMessage(provider)` εξάγεται για καλούντες που χρειάζεται να
λαμβάνουν δικές τους αποφάσεις δρομολόγησης. Οι άγνωστοι πάροχοι έχουν ως προεπιλογή το `true`
(ο ρόλος συστήματος επιτρέπεται) για λόγους ασφαλείας.

| `MEMORY_EMBEDDING_CACHE_TTL_MS` | `300000`                   | TTL της κρυφής μνήμης ενσωματώσεων (5 λεπτά)                                                                                                                                             |

## Σύνοψη (`summarization.ts`)

Η `summarizeMemories(apiKeyId, sessionId?, maxTokens = 4000)` συμπτύσσει παλαιότερο
περιεχόμενο όταν το τρέχον συνολικό πλήθος διακριτικών στις μνήμες ενός κλειδιού υπερβαίνει
το όριο. Διατρέχει τις γραμμές κατά φθίνουσα σειρά βάσει `created_at`, διατηρεί τις γραμμές που χωρούν και,
για τις υπόλοιπες, αντικαθιστά επιτόπου το `content` με τις πρώτες τρεις προτάσεις του
αρχικού κειμένου. Το `tokensSaved` είναι η διαφορά στο `estimateTokens` μεταξύ του παλιού και του
νέου περιεχομένου.

Αυτή η ρουτίνα είναι **διαθέσιμη αλλά δεν καλείται αυτόματα** στην τρέχουσα
ροή συνομιλίας — καλέστε την από μια εργασία cron, μια ενέργεια διαχειριστή ή
τη συνδετική λογική του `MemoryConfig.autoSummarize`, εάν χρειάζεστε συνεχή σύμπτυξη. Η απώλεια
δεδομένων είναι μονόδρομη: το αρχικό κείμενο αντικαθίσταται.

## Εργαλεία MCP (`open-sse/mcp-server/tools/memoryTools.ts`)

Όταν ο διακομιστής MCP είναι ενεργοποιημένος, καταχωρίζονται τρία εργαλεία μνήμης:

- `omniroute_memory_search` — `{apiKeyId, query?, type?, maxTokens?, limit?}`
  → αποτελεί περιτύλιγμα της `retrieveMemories()`. Από την έκδοση v3.8.6 (D16), η
  `strategy` διαβάζεται από τη `getMemorySettings()` αντί να είναι σταθερά
  ορισμένη ως `"exact"`. Αν παρέχεται το `query` και η `strategy` είναι `semantic`
  ή `hybrid`, χρησιμοποιείται το διανυσματικό αποθετήριο όταν είναι διαθέσιμο.
- `omniroute_memory_add` — `{apiKeyId, sessionId?, type, key, content,
metadata?}` → αποτελεί περιτύλιγμα της `createMemory()`. Δέχεται μόνο τους 4 κανονικούς τύπους:
  `factual`, `episodic`, `procedural`, `semantic` (D17).
- `omniroute_memory_clear` — `{apiKeyId, type?, olderThan?}` → παραθέτει τις
  εγγραφές που αντιστοιχούν, τις φιλτράρει προαιρετικά βάσει χρονικής σήμανσης
  δημιουργίας προγενέστερης από την καθορισμένη και κατόπιν διαγράφει καθεμία
  μέσω της `deleteMemory()` (η οποία αφαιρεί επίσης τα διανύσματα από τα sqlite-vec + Qdrant).

Δείτε το [MCP-SERVER.md](./MCP-SERVER.md) για λεπτομέρειες σχετικά με τη μεταφορά και το πεδίο εφαρμογής.

## Προσωρινή αποθήκευση

Το `src/lib/memory/store.ts` διατηρεί μια προσωρινή μνήμη τύπου LRU εντός της διεργασίας
(`MEMORY_CACHE_TTL = 1 min`, `MEMORY_MAX_CACHE_SIZE = 500`, με απομάκρυνση του 20 %
των παλαιότερων εγγραφών) για αναγνώσεις `getMemory(id)`, καθώς και ένα γενικό επίπεδο
προσωρινής αποθήκευσης κλειδιού/τιμής `memoryCache` (`src/lib/memory/cache.ts`) με
μεθόδους `get`/`set`/`invalidate`, το οποίο χρησιμοποιείται από καλούντες που θέλουν τη δική τους
προσωρινή μνήμη με συγκεκριμένο πεδίο εφαρμογής (LRU 1 000 εγγραφών, προεπιλεγμένο TTL 5 min).

## Απόρρητο & Κύκλος ζωής

- Η ιδιοκτησία της μνήμης καθορίζεται από το αναγνωριστικό του κλειδιού API (`resolveMemoryOwnerId` στο
  `chatCore.ts`). Χωρίς `apiKeyInfo.id` δεν εκτελείται ούτε ανάκτηση ούτε εισαγωγή
  ούτε εξαγωγή.
- Οι καταχωρίσεις με μελλοντική τιμή `expires_at` φιλτράρονται από την ανάκτηση· οι παλιές
  καταχωρίσεις πέρα από το `retentionDays` εξαιρούνται από τη ρήτρα
  `created_at >= cutoff` στο `retrieveMemories`.
- Για οριστική διαγραφή, χρησιμοποιήστε `DELETE /api/memory/[id]` ή `omniroute_memory_clear`.
- Η εξαγωγή εκτελείται χωρίς αναμονή αποτελέσματος μέσω `setImmediate`· οι αποτυχίες καταγράφονται στο
  `memory.extraction.background.failed` και δεν εμφανίζονται ποτέ στον καλούντα.
- Οι δοκιμές πλήρους διαδρομής επαλήθευσης (`verifyExtractionPipeline`) διαγράφουν τις δικές τους
  δοκιμαστικές καταχωρίσεις σε ένα μπλοκ `finally`.

## Επιλογή παρόχου ενσωματώσεων (v3.8.16+)

Η μηχανή μνήμης του OmniRoute υποστηρίζει **τέσσερις πηγές ενσωματώσεων** (`src/lib/memory/embedding/`). Καθεμία προσφέρει διαφορετικούς συμβιβασμούς ως προς την **καθυστέρηση, το κόστος, την ποιότητα μοντέλου και την πολυπλοκότητα εγκατάστασης**.

### Οι πηγές ενσωματώσεων

| Πάροχος        | Πηγή                                                   | Καθυστέρηση                                 | Κόστος               | Ποιότητα                                  | Εγκατάσταση                                |
| -------------- | ------------------------------------------------------ | ------------------------------------------- | -------------------- | ----------------------------------------- | ------------------------------------------ |
| `transformers` | Τοπικό μοντέλο ONNX (Xenova/all-MiniLM-L6-v2)          | ~50-150ms (CPU)                             | Δωρεάν               | Καλή                                      | Μόνο `npm install`                         |
| `static`       | Προϋπολογισμένα διανύσματα (σε cache)                  | <1ms                                        | Δωρεάν               | Δ/Υ (εξαρτάται από την εύρεση στην cache) | Καμία                                      |
| `remote`       | API OpenAI / Cohere / Voyage                           | ~100-300ms                                  | $0.02-0.10/1M tokens | Εξαιρετική                                | Κλειδί API                                 |
| `auto`         | Επιλέγει την καλύτερη διαθέσιμη πηγή κατά την εκτέλεση | Ίδια με την επιλεγμένη πηγή                 | Δωρεάν               | Ίδια με την επιλεγμένη πηγή               | Καμία                                      |
| _(cache)_      | Επίπεδο LRU στη μνήμη πάνω από οποιαδήποτε πηγή        | <1ms (εύρεση), πλήρης καθυστέρηση (αστοχία) | Δωρεάν               | Ίδια με την υποκείμενη                    | Πάντα ενεργό (δεν αποτελεί επιλέξιμη πηγή) |

### Δέντρο αποφάσεων

      │           │           │              │
      ▼           ▼           ▼              ▼

### Διαμόρφωση βάσης δεδομένων & API

Οι επιλογές ενσωματώσεων μνήμης διαμορφώνονται μέσω του API/UI ρυθμίσεων και όχι μέσω μεταβλητών περιβάλλοντος. Τα σχετικά κλειδιά ρυθμίσεων της βάσης δεδομένων στις Ρυθμίσεις (`normalizeMemorySettings` στο `src/lib/memory/settings.ts`) είναι:

- `memoryEmbeddingSource`: `"transformers"` (τοπικό), `"remote"` (βασισμένο σε API, π.χ. OpenAI), `"static"` (εξωτερικός χώρος αποθήκευσης) ή `"auto"`
- `memoryEmbeddingProviderModel`: Αναγνωριστικό μοντέλου για απομακρυσμένες/στατικές πηγές (π.χ. `"text-embedding-3-small"`)
- `memoryTransformersEnabled`: `true` | `false`
- `memoryStaticEnabled`: `true` | `false`
- `memoryVectorStore`: `"sqlite-vec"`, `"qdrant"` ή `"auto"`

#### Τοπικό μοντέλο (`transformers`)

Χρησιμοποιεί εσωτερικά το transformers.js για την εκτέλεση τοπικών μοντέλων:

```bash
# Μεταβλητές περιβάλλοντος που διαβάζονται στον κώδικα (src/lib/memory/embedding/index.ts):
MEMORY_TRANSFORMERS_MODEL=Xenova/all-MiniLM-L6-v2  # Αποθετήριο μοντέλου HF
MEMORY_STATIC_MODEL=minishlab/potion-base-8M       # Στατικό μοντέλο potion του HF
MEMORY_STATIC_CACHE_DIR=<DATA_DIR>/embeddings      # Κατάλογος cache
```

#### Cache ενσωματώσεων LRU

## Ρύθμιση Υβριδικού RRF (v3.8.16+)

Ο αλγόριθμος **Reciprocal Rank Fusion (RRF)** συνδυάζει αποτελέσματα FTS5 (λέξεις-κλειδιά) και διανυσματικά (σημασιολογικά) αποτελέσματα. Η παράμετρος `k` ελέγχει το βάρος που δίνεται στα αποτελέσματα χαμηλότερης κατάταξης.

### Ο Τύπος

Για κάθε υποψήφια μνήμη, η βαθμολογία RRF είναι:

```
RRF(d) = Σ  1 / (k + rank_i(d))
```

Όπου:

- `k` είναι η σταθερά (προεπιλογή 60)
- `rank_i(d)` είναι η κατάταξη του εγγράφου `d` στο i-οστό σύστημα ανάκτησης (FTS, διανυσματικό)
- Το άθροισμα υπολογίζεται για όλα τα συστήματα ανάκτησης

### Πώς το `k` Επηρεάζει τα Αποτελέσματα

| Τιμή `k`                | Επίδραση                                                                                                           | Καταλληλότερο για                                   |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| `k=0`                   | Καθαρή συγχώνευση κατατάξεων (χωρίς εξομάλυνση)                                                                    | Θεωρητική γραμμή βάσης                              |
| `k=10-30`               | Δίνει μεγάλο βάρος στα κορυφαία αποτελέσματα, ενώ η χαμηλή κατάταξη συνεισφέρει ελάχιστα                           | Όταν τα 3 κορυφαία αποτελέσματα είναι συνήθως σωστά |
| **`k=60`** (προεπιλογή) | Ισορροπημένο — και τα 10 κορυφαία αποτελέσματα συνεισφέρουν ουσιαστικά                                             | Ανάκτηση γενικής χρήσης                             |
| `k=100+`                | Πιο επίπεδο — ακόμη και αποτελέσματα χαμηλής κατάταξης μπορούν να επικρατήσουν εάν εμφανίζονται σε πολλά συστήματα | Όταν η ανάκληση > ακρίβεια είναι κρίσιμη            |

### Ρύθμιση του `k` στην Πράξη

```bash
# Προεπιλογή
MEMORY_RRF_K=60

# Επιθετική ακρίβεια (μικρή μνήμη, λίγα έγγραφα)
MEMORY_RRF_K=20

# Μέγιστη ανάκληση (μεγάλη μνήμη, ποικίλα ερωτήματα)
MEMORY_RRF_K=120
```

**Παράδειγμα με `k=20`:**

- Κατάταξη FTS 1 → συνεισφορά `1/21 = 0.048`
- Κατάταξη FTS 10 → συνεισφορά `1/30 = 0.033`
- Διανυσματική κατάταξη 1 → συνεισφορά `0.048`
- Συνδυασμένο μέγιστο: `0.096`

**Παράδειγμα με `k=60`:**

- Κατάταξη FTS 1 → συνεισφορά `1/61 = 0.016`
- Κατάταξη FTS 10 → συνεισφορά `1/70 = 0.014`
- Διανυσματική κατάταξη 1 → συνεισφορά `0.016`
- Συνδυασμένο μέγιστο: `0.033`

Με υψηλότερο `k`, η **σχετική διαφορά** μεταξύ της 1ης και της 10ης θέσης είναι μικρότερη, επομένως ο αλγόριθμος βασίζεται περισσότερο στη **συναίνεση μεταξύ των συστημάτων ανάκτησης** παρά στη βεβαιότητα της κορυφαίας κατάταξης.

### Πότε να Αλλάζετε το `k`

| Σύμπτωμα                                                          | Δοκιμάστε                                                                                  |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Το κορυφαίο αποτέλεσμα κερδίζει πάντα, αλλά είναι λάθος           | **Μειώστε** το k (π.χ., 20) — η βεβαιότητα της κορυφαίας κατάταξης έχει μεγαλύτερη σημασία |
| Η σωστή απάντηση βρίσκεται στις 5 κορυφαίες αλλά όχι στην 1η θέση | **Αυξήστε** το k (π.χ., 100) — η πιο επίπεδη βαθμολόγηση επιβραβεύει τη συναίνεση          |
| Η ανάκληση είναι υψηλή αλλά η ακρίβεια χαμηλή                     | **Μειώστε** το k — κάντε την κατάταξη πιο αυστηρή                                          |
| Η ανάκληση είναι χαμηλή (λείπουν σχετικά έγγραφα)                 | **Αυξήστε** το k — δώστε μια ευκαιρία στα έγγραφα χαμηλότερης κατάταξης                    |

### Στάθμιση RRF

Η συγχώνευση αμοιβαίας κατάταξης χρησιμοποιεί ίσα βάρη για τη σημασιολογική διανυσματική κατάταξη και την κατάταξη αναζήτησης πλήρους κειμένου:

```
RRF(d) = 1/(k + rank_vector) + 1/(k + rank_fts)
```

Δεν υπάρχουν μεταβλητές περιβάλλοντος για την προσαρμογή των επιμέρους βαρών (`MEMORY_RRF_VECTOR_WEIGHT`/`MEMORY_RRF_FTS_WEIGHT` δεν υπάρχουν).

## Στρατηγική Σύνοψης (v3.8.16+)

Η μονάδα `summarization.ts` (`src/lib/memory/summarization.ts`) συμπιέζει παλαιότερες μνήμες, ώστε το ενεργό σύνολο να παραμένει μικρό, διατηρώντας παράλληλα τη δυνατότητα ανάκλησης.

### Πότε Ενεργοποιείται η Σύνοψη

| Ενεργοποίηση                      | Όριο (προεπιλογή) |
| --------------------------------- | ----------------- |
| Χειροκίνητη ενεργοποίηση μέσω API | δ/ε               |

### Τι Συνοψίζεται

Δύο σημεία εισόδου εξάγονται από το `summarization.ts`:

- **`summarizeMemories(apiKeyId, sessionId?, maxTokens = 4000)`** — συμπυκνώνει τις
  μνήμες μιας συνεδρίας σε ένα ενιαίο κείμενο σύνοψης, περιορισμένο από έναν προϋπολογισμό token.
- **`summarizeMemoriesOlderThan(apiKeyId, days, dryRun)`** — η συμπίεση βάσει ηλικίας
  που χρησιμοποιείται από το API: επιλέγει κάθε μνήμη παλαιότερη από `days`, δημιουργεί
  από αυτές μία συμπυκνωμένη μνήμη σύνοψης και (όταν το `dryRun` είναι `false`) διαγράφει
  τις αρχικές. Περάστε `dryRun: true` για να κάνετε προεπισκόπηση του συνόλου υποψηφίων και του συνολικού αριθμού token
  χωρίς να τροποποιήσετε τίποτα.

Δεν υπάρχει στάδιο ομαδοποίησης βάσει ετικέτας/κλειδιού ούτε βαθμολόγηση ανά μνήμη ως «βασική έναντι συνοψίσιμης» —
η επιλογή βασίζεται αποκλειστικά στο όριο ηλικίας και το κείμενο της σύνοψης είναι μία συμπυκνωμένη,
με πρόθεμα τύπου γραμμή ανά υποψήφια μνήμη.

### Ενεργοποίηση της Σύνοψης

Η σύνοψη είναι **χειροκίνητη / προαιρετική** — η ρύθμιση `autoSummarize` είναι `false` από
προεπιλογή, επομένως τίποτα δεν συμπιέζεται αυτόματα. Ενεργοποιήστε τη μέσω του API:

```bash
curl -X POST http://localhost:20128/api/memory/summarize \
  -H "Authorization: Bearer $OMNIROUTE_KEY"
```

Για να παραμείνει απενεργοποιημένη, απλώς διατηρήστε το `autoSummarize` στην προεπιλεγμένη τιμή του (`false`).

### Συμβουλές για την Ποιότητα της Σύνοψης

- **Κάντε πρώτα προεπισκόπηση με `dryRun`** — το `summarizeMemoriesOlderThan(..., true)` επιστρέφει
  τη λίστα υποψηφίων και τον συνολικό αριθμό token, ώστε να μπορείτε να επιβεβαιώσετε τι θα συγχωνευτεί
  πριν διαγράψετε τις αρχικές μνήμες.
- **Εκτελείτε τη σύνοψη σε ώρες χαμηλής κίνησης** αν έχετε μεγάλο σώμα μνημών — η κλήση προς το LLM είναι το αργό μέρος

```bash
# Τύπου Cron: σύνοψη καθημερινά στις 3 π.μ.
0 3 * * * curl -X POST http://localhost:20128/api/memory/summarize \
  -H "Authorization: Bearer $OMNIROUTE_KEY"
```

## Πρότυπο Παρόχου MemoryBackend

> **Πηγή αναφοράς:** `src/lib/memory/backend.ts`, `src/lib/memory/genericBackend.ts`, `src/lib/memory/manager.ts`
> **Δοκιμές:** `src/lib/memory/__tests__/generic-backend.test.ts`

Το πρότυπο παρόχου MemoryBackend εισάγει ένα **αρθρωτό επίπεδο αφαίρεσης backend** πάνω από την υπάρχουσα μηχανή μνήμης. Αντί να είναι δεσμευμένο σε μία μόνο υλοποίηση αποθήκευσης, το σύστημα μνήμης υποστηρίζει πλέον πολλαπλά backend (SQLite, Obsidian, Notion, προσαρμοσμένα HTTP backend) με παραμετροποιήσιμη δρομολόγηση κύριου/εφεδρικών backend.

### Αρχιτεκτονική

```
┌──────────────────────────────────────────────────────────┐
│                    Διαδρομές API                          │
│            (src/app/api/memory/route.ts)                  │
└──────────────────────┬───────────────────────────────────┘
                       │
┌──────────────────────▼───────────────────────────────────┐
│                   MemoryManager                           │
│       Ενορχηστρωτής Singleton (manager.ts)                │
│                                                          │
│  Κύριο ─────► Backend A  (π.χ. SQLite)                   │
│  Εφεδρικό ──► Backend B  (π.χ. Obsidian)                 │
│               Backend C  (π.χ. Notion μέσω GenericBackend)│
└──────────────────────┬───────────────────────────────────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
┌────────────┐ ┌────────────┐ ┌──────────────────┐
│ SQLite     │ │ Obsidian   │ │ GenericMemory    │
│ Backend    │ │ Backend    │ │ Backend (HTTP)   │
└────────────┘ └────────────┘ └──────────────────┘
```

#### Βασική Διεπαφή (`backend.ts`)

Κάθε backend πρέπει να υλοποιεί τη διεπαφή `MemoryBackend`:

```typescript
interface MemoryBackend {
  readonly id: string;
  readonly displayName: string;

  // CRUD
  create(input: CreateMemoryInput): Promise<Memory>;
  get(id: string): Promise<Memory | null>;
  update(id: string, updates: Partial<...>): Promise<boolean>;
  delete(id: string): Promise<boolean>;
  list(filter: MemoryFilter): Promise<{ data: Memory[]; total: number; byType: Record<string, number> }>;

  // Αναζήτηση
  search(config: SearchConfig): Promise<Memory[]>;

  // Κατάσταση λειτουργίας
  health(): Promise<HealthCheckResult>;

  // Κύκλος ζωής (προαιρετικό)
  initialize?(): Promise<void>;
  shutdown?(): Promise<void>;
}
```

#### MemoryManager (`manager.ts`)

Ενορχηστρωτής Singleton που:

- **Καταχωρίζει** backend μέσω του `register(backend)` — καλείται κατά την εκκίνηση από το `index.ts`
- **Ρυθμίζει** το κύριο και τα εφεδρικά backend μέσω του `configure(primary, fallbacks)`
- **Δρομολογεί** λειτουργίες CRUD/αναζήτησης προς το κύριο backend, με αλυσίδα εφεδρικών σε περίπτωση αποτυχίας
- **Ελέγχει την κατάσταση λειτουργίας** όλων των backend περιοδικά

**Συμπεριφορά εφεδρικών backend:**

| Λειτουργία | Κύριο                     | Εφεδρικά                                 |
| ---------- | ------------------------- | ---------------------------------------- |
| `create`   | ✅ Μόνο το κύριο          | ❌                                       |
| `get`      | ✅ Δοκιμή πρώτα στο κύριο | ✅ Εφεδρικό αν επιστραφεί null           |
| `update`   | ✅ Μόνο το κύριο          | ✅ Ασύγχρονος συγχρονισμός χωρίς αναμονή |
| `delete`   | ✅ Μόνο το κύριο          | ✅ Ασύγχρονος συγχρονισμός χωρίς αναμονή |
| `list`     | ✅ Μόνο το κύριο          | ❌                                       |
| `search`   | ✅ Πρώτα το κύριο         | ✅ Εφεδρικό σε περίπτωση σφάλματος       |

#### GenericMemoryBackend (`genericBackend.ts`)

Ένας γενικός σύνδεσμος HTTP που προσαρμόζει οποιοδήποτε REST API σε ένα MemoryBackend. Χρήσιμος για:

- **Notion** — σύνδεση μέσω του Notion API
- **Obsidian** — σύνδεση μέσω του Obsidian Local REST API
- **Προσαρμοσμένα backend** — οποιαδήποτε υπηρεσία εκθέτει ένα RESTful API μνήμης

**Ρύθμιση παραμέτρων:**

```typescript
interface GenericBackendConfig {
  baseUrl: string;           // Βασικό URL του backend API
  apiKey?: string;           // Bearer token για έλεγχο ταυτότητας
  headers?: Record<string, string>;  // Προσαρμοσμένες κεφαλίδες HTTP
  timeout?: number;          // Χρονικό όριο αιτήματος (προεπιλογή: 30000ms)
  backendType?: string;      // Για καταγραφή

  // Παρακάμψεις endpoint (οι προεπιλογές χρησιμοποιούν συμβάσεις REST)
  endpoints?: {
    search?: string;   // προεπιλογή: "/memories/search"
    create?: string;   // προεπιλογή: "/memories"
    list?: string;     // προεπιλογή: "/memories"
    get?: string;      // προεπιλογή: "/memories/{id}"
    update?: string;   // προεπιλογή: "/memories/{id}"
    delete?: string;   // προεπιλογή: "/memories/{id}"
    health?: string;   // προεπιλογή: "/health"
  };

  // Αντιστοιχίσεις ονομάτων παραμέτρων ερωτήματος
  queryParams?: {
    query?/apiKeyId?/limit?/offset?/strategy?/maxTokens?/type?/sessionId?/orderBy?/orderDir?/options?
  };

  // Αντιστοιχίσεις ονομάτων παραμέτρων διαδρομής
  pathParams?: {
    id?/memoryId?
  };
}
```

Τα **γνωστά backend** είναι προδιαμορφωμένα στο `KNOWN_BACKENDS`:

```typescript
createKnownBackend("obsidian"); // → GenericMemoryBackend που δείχνει στο localhost:27123
createKnownBackend("notion"); // → GenericMemoryBackend που δείχνει στο api.notion.com/v1
```

### Ρυθμίσεις

Οι ρυθμίσεις των backend μνήμης αποθηκεύονται στον πίνακα ρυθμίσεων της εφαρμογής και διαχειρίζονται μέσω του `src/lib/memory/settings.ts`:

### Ροή Αρχικοποίησης

```

      2. Διαμόρφωση κύριου + εφεδρικών backend

```

1. **Υλοποιήστε τη διεπαφή `MemoryBackend`** στο `src/lib/memory/<name>Backend.ts`
2. **Εξαγάγετέ το** από το `src/lib/memory/index.ts`
3. **Καταχωρίστε το** με `memoryManager.register(yourBackend)` κατά την εκκίνηση
4. **Διαμορφώστε το** μέσω των ρυθμίσεων: ορίστε το `memoryPrimaryBackend` στο ID του backend σας
5. **Δοκιμάστε το** χρησιμοποιώντας το `src/lib/memory/__tests__/generic-backend.test.ts` ως αναφορά

#### Παράδειγμα: Backend Brain

```typescript
import { createGenericMemoryBackend } from "./genericBackend";

const brainBackend = createGenericMemoryBackend("brain", "BK-Brain", {
  baseUrl: process.env.BRAIN_API_URL || "http://localhost:9099",
  apiKey: process.env.BRAIN_API_KEY,
  endpoints: {
    search: "/api/memory/search",
    create: "/api/memory",
    health: "/api/health",
  },
});

memoryManager.register(brainBackend);
```
