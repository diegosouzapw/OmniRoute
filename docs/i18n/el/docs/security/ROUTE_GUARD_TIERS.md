## Επισκόπηση

Όλες οι διαδρομές του API διαχείρισης του OmniRoute ταξινομούνται σε ένα από τρία επίπεδα
προστασίας. Η ταξινόμηση είναι στατική, ορίζεται στο `src/server/authz/routeGuard.ts`
και αξιολογείται πριν εκτελεστεί οποιοσδήποτε άλλος κλάδος ελέγχου ταυτότητας.

## Βαθμίδες

### Βαθμίδα 1 — LOCAL_ONLY

**Επιβάλλεται από:** `isLocalOnlyPath(path)` → έλεγχος loopback host
**Παράκαμψη:** Καμία από προεπιλογή. Περιορισμένη εξαίρεση για διαδρομές στο
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` όταν το αίτημα φέρει ένα έγκυρο
κλειδί API με το πεδίο εφαρμογής `manage` (βλ. [Εξαίρεση πεδίου εφαρμογής διαχείρισης](#manage-scope-carve-out)).

Αυτές οι διαδρομές δημιουργούν θυγατρικές διεργασίες ή εκτελούν κώδικα χρόνου εκτέλεσης. Η έκθεσή τους σε
κίνηση εκτός loopback θα επέτρεπε σε έναν επιτιθέμενο που απέκτησε ένα έγκυρο JWT (π.χ.,
μέσω ενός τούνελ Cloudflared/Ngrok) να ενεργοποιήσει τη δημιουργία διεργασιών — μια γνωστή
κατηγορία CVE ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Τι είναι το GHSA-fhh6-4qxv-rpqj (η κατηγορία επίθεσης):** ένας διακομιστής διαχείρισης/πράκτορα
εκθέτει ένα τελικό σημείο που εκκινεί μια υποδιεργασία (`npm install`, `node`, ένα πρόγραμμα περιήγησης,
έναν διακομιστή μεσολάβησης, `git`, `tar`, …). Εάν αυτό το τελικό σημείο είναι προσβάσιμο από εκτός του host — επειδή
ο χειριστής έβαλε το OmniRoute πίσω από ένα τούνελ nginx/Cloudflare/Tailscale και ένα JWT
διέρρευσε, ή η αυθεντικοποίηση ήταν λανθασμένα διαμορφωμένη — ο επιτιθέμενος μετατρέπει το "κλήση ενός API" σε "εκτέλεση μιας
εντολής στον host" (απομακρυσμένη εκτέλεση κώδικα). Το OmniRoute το κλείνει αυτό επιβάλλοντας έναν
**έλεγχο loopback host άνευ όρων, πριν από οποιονδήποτε έλεγχο αυθεντικοποίησης**, σε κάθε
διαδρομή που είναι ικανή να δημιουργήσει διεργασίες: ένα διαρρεύσαν token μέσω ενός τούνελ εξακολουθεί να μην μπορεί να φτάσει τη δημιουργία.

**Το πλήρες σύνολο LOCAL_ONLY.** Η αυθεντική πηγή είναι τα
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` στο
`src/server/authz/routeGuard.ts`· ο παρακάτω πίνακας αντικατοπτρίζει την τρέχουσα κατάσταση. Η
πύλη `check-route-guard-membership` απαριθμεί κάθε `route.ts` κάτω από τα
προθέματα που είναι ικανά να δημιουργήσουν διεργασίες και αποτυγχάνει το CI εάν κάποιο δεν ταξινομείται ως local-only.

#### Εξαίρεση πεδίου διαχείρισης (Manage-scope carve-out)

Ένα υποσύνολο διαδρομών LOCAL_ONLY ΜΠΟΡΕΙ επίσης να προσπελαστεί από μη-loopback αν και μόνο αν η αίτηση φέρει ένα `Authorization: Bearer <api-key>` του οποίου τα μεταδεδομένα περιλαμβάνουν το πεδίο `manage` (ή `admin`). Η εξαίρεση είναι ρητά περιορισμένη ανά διαδρομή μέσω του `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, οπότε η προεπιλογή για οποιαδήποτε νέα διαδρομή LOCAL_ONLY παραμένει αυστηρά loopback. Μη-πιστοποιημένες αιτήσεις και αιτήσεις με κλειδιά χωρίς `manage` εξακολουθούν να απορρίπτονται με `403 LOCAL_ONLY`.

Σήμερα, το μόνο προσπελάσιμο πρόθεμα είναι το `/api/mcp/`. Τα `/api/cli-tools/runtime/` και `/api/services/` εξαιρούνται σκόπιμα επειδή μπορούν να εκκινήσουν αυθαίρετες υποδιεργασίες (`npm install`, `node`), κάτι που είναι ακριβώς η κατηγορία CVE που ο tier LOCAL_ONLY υπάρχει για να αποτρέψει.

**#7895 — `mcp:connect` στενό πεδίο:** η εξαίρεση `/api/mcp/` ΔΕΧΕΤΑΙ ΕΠΙΣΗΣ ένα κλειδί Bearer που κατέχει το στενό πεδίο `mcp:connect` (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), το οποίο ελέγχεται μέσω του `hasMcpConnectOrManageScope()` στο `src/server/authz/policies/management.ts`. Αυτό περιορίζεται ΜΟΝΟ στο `/api/mcp/` — το `mcp:connect` δεν παρέχει τίποτα σε καμία άλλη διαδρομή διαχείρισης (συμπεριλαμβανομένου κάθε άλλου προθέματος παράκαμψης LOCAL_ONLY, αν ποτέ προστεθεί), και εξαιρείται σκόπιμα από τα `MANAGEMENT_API_KEY_SCOPES`. Ένα κλειδί που κατέχει `manage`/`admin` εξακολουθεί να περνάει την εξαίρεση ακριβώς όπως πριν· το `mcp:connect` είναι μια εναλλακτική λύση χαμηλότερων προνομίων για απομακρυσμένους καλούντες μόνο για MCP που δεν θα πρέπει να χρειάζονται ευρεία πρόσβαση διαχείρισης.

| Αίτηση                                           | Διαδρομή                   | Αποτέλεσμα                   |
| :----------------------------------------------- | :------------------------- | :--------------------------- |
| Μη-loopback, χωρίς Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY               |
| Μη-loopback, Bearer με πεδίο `manage`            | `/api/mcp/*`               | Επιτρέπεται                  |
| Μη-loopback, Bearer με πεδίο `mcp:connect`       | `/api/mcp/*`               | Επιτρέπεται                  |
| Μη-loopback, Bearer χωρίς `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY               |
| Μη-loopback, Bearer με πεδίο `mcp:connect`       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY               |
| Μη-loopback, Bearer με πεδίο `manage`            | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY               |
| Loopback, οποιοδήποτε/χωρίς Bearer               | οποιοδήποτε LOCAL_ONLY     | Επιτρέπεται (η πύλη περνάει) |

#### Οδηγίες χειριστή & έλεγχος

Εάν εκτελείτε το OmniRoute πίσω από έναν αντίστροφο διακομιστή μεσολάβησης ή τούνελ (nginx, Caddy, Cloudflare Tunnel, Tailscale, Ngrok), ο έλεγχος loopback εξακολουθεί να προστατεύει τις παραπάνω διαδρομές με δυνατότητα εκκίνησης — μια αίτηση της οποίας η διεύθυνση πελάτη δεν είναι loopback απορρίπτεται με `403 LOCAL_ONLY` **πριν εκτελεστεί η πιστοποίηση**, οπότε ένα διαρρεύσαν JWT δεν μπορεί να φτάσει σε μια εκκίνηση. Παραμένουν δύο ευθύνες του χειριστή:

- **Μην "διορθώνετε" ένα 403 πλαστογραφώντας την IP του πελάτη ως loopback.** Η ρύθμιση `X-Forwarded-For: 127.0.0.1`, ή ένας διακομιστής μεσολάβησης που ξαναγράφει τη διεύθυνση προέλευσης σε loopback, ανοίγει ξανά ακριβώς την κατηγορία RCE που κλείνει αυτό το επίπεδο. Εκθέστε τον πίνακα ελέγχου/API μέσω του διακομιστή μεσολάβησης — ποτέ τις διαδρομές με δυνατότητα εκκίνησης.
- **Διατηρήστε την παράκαμψη πεδίου διαχείρισης στο ελάχιστο.** Μόνο το `/api/mcp/` μπορεί να παρακαμφθεί, και μόνο με ένα κλειδί API με πεδίο `manage`. Τα `SPAWN_CAPABLE_PREFIXES` δεν μπορούν ποτέ να προστεθούν στη λίστα παράκαμψης — το σχήμα zod τα απορρίπτει και το `isLocalOnlyBypassableByManageScope` τα αρνείται κατά την εκτέλεση (άμυνα σε βάθος), κάτι που είναι αυτό που εννοεί ο πίνακας ελέγχου με το "δεν μπορεί να γίνει παρακάμψιμο". Οι διαδρομές με δυνατότητα εκκίνησης δυναμικού τμήματος και στατικής διαδρομής κάτω από το `/api/providers/` (π.χ. `/login`, `/refresh-cursor`) καλύπτονται από το συνοδευτικό `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` που βασίζεται σε regex στο `src/shared/constants/spawnCapablePrefixes.ts`, όχι από τον επίπεδο πίνακα `SPAWN_CAPABLE_PREFIXES` — ο επίπεδος πίνακας θα έπρεπε να καλύπτει ολόκληρο το πρόθεμα `/api/providers/` για να τις πιάσει, διευρύνοντας υπερβολικά ένα δέντρο διαδρομών που οι απομακρυσμένοι πίνακες ελέγχου χρησιμοποιούν νόμιμα για CRUD παρόχων.

**Έλεγχος πρόσβασης** — για να επαληθεύσετε ότι τίποτα εκτός του κεντρικού υπολογιστή δεν φτάνει σε αυτές τις διαδρομές:

- Ανοίξτε το **Authorization Inventory** στο `/dashboard/settings/security`: εμφανίζει τη ζωντανή λίστα προθεμάτων LOCAL_ONLY, ποια προθέματα μπορούν να παρακαμφθούν και το σύνολο που μπορεί να δημιουργηθεί κατά τη μεταγλώττιση ("δεν μπορεί να γίνει παρακάμψιμο").
- Αναζητήστε στα αρχεία καταγραφής του αντίστροφου διακομιστή μεσολάβησης / πρόσβασης τα παραπάνω προθέματα σε συνδυασμό με μια διεύθυνση πελάτη που δεν είναι loopback. Οποιοδήποτε τέτοιο χτύπημα που επέστρεψε `200` αντί για `403 LOCAL_ONLY` σημαίνει ότι ο διακομιστής μεσολάβησης καλύπτει την πραγματική IP του πελάτη — διορθώστε τον διακομιστή μεσολάβησης.
- Ένα `403 LOCAL_ONLY` στα αρχεία καταγραφής του OmniRoute για μία από αυτές τις διαδρομές είναι η λειτουργία του φύλακα όπως προβλέπεται, όχι ένα σφάλμα που πρέπει να κατασταλεί.

### Επίπεδο 2 — ALWAYS_PROTECTED

**Επιβάλλεται από:** `isAlwaysProtectedPath(path)` → παράλειψη παράκαμψης `requireLogin=false`
**Παράκαμψη:** Καμία όταν `requireLogin=false`; JWT πάντα απαιτείται

Αυτές οι διαδρομές είναι καταστροφικές ή μη αναστρέψιμες. Η ενεργοποίησή τους σε μια εγκατάσταση "χωρίς κωδικό πρόσβασης" θα σήμαινε ότι οποιοσδήποτε στο ίδιο LAN θα μπορούσε να διαγράψει τη βάση δεδομένων ή να τερματίσει τη διαδικασία του διακομιστή.

| Διαδρομή                                  | Λόγος                                                                                      |
| ----------------------------------------- | ------------------------------------------------------------------------------------------ |
| `/api/shutdown`                           | Τερματίζει τη διαδικασία του διακομιστή                                                    |
| `/api/settings/database`                  | Εξαγωγή, εισαγωγή και διαγραφή βάσης δεδομένων                                             |
| `/api/db-backups`                         | Πλήρης πρόσβαση αρχείου αντιγράφων ασφαλείας βάσης δεδομένων                               |
| `/api/settings/export-json`               | Εξάγει ολόκληρο το blob ρυθμίσεων (συμπεριλαμβανομένων των μυστικών)                       |
| `/api/settings/import-json`               | Αντικαθιστά ολόκληρο το blob ρυθμίσεων                                                     |
| `/api/providers/health-autopilot/actions` | Εκτελεί ενέργειες αποκατάστασης αυτόματου πιλότου                                          |
| `/api/settings/obsidian`                  | Δημιουργεί επαναχρησιμοποιήσιμα διαπιστευτήρια WebDAV για οποιαδήποτε ρίζα θησαυροφυλακίου |

**Απόκριση σε παραβίαση:** `401 Απαιτείται έλεγχος ταυτότητας`

Το `/api/settings/obsidian` καλύπτει το παιδί του `/webdav`: το `POST` δείχνει την υπηρεσία αρχείων WebDAV — που εξυπηρετείται από το προσαρμοσμένο επίπεδο Node πριν από το Next.js, εκτός αυτής της διοχέτευσης — σε μια ρίζα που επιλέγεται από τον καλούντα και επαναλαμβάνει τα πρόσφατα δημιουργημένα βασικά διαπιστευτήρια, το `DELETE` τα περιστρέφει και το γονικό `POST` αποθηκεύει το διακριτικό API REST του Obsidian. Το GHSA-62vw κάλυψε μόνο την αποκάλυψη κωδικού πρόσβασης `GET`. Η έκδοση ήταν ακόμα στο επίπεδο fail-open (GHSA-7pq4-8pvv-rx7r). Το `enableObsidianVaultSync()` επιπλέον αρνείται ένα θησαυροφυλάκιο που είναι, βρίσκεται μέσα ή περιέχει τον κατάλογο δεδομένων.

### Η αρχική εκκίνηση είναι μόνο loopback — από πραγματικό ομότιμο, όχι `Host`

Χωρίς διαμορφωμένο κωδικό πρόσβασης διαχείρισης (και χωρίς `INITIAL_PASSWORD`), το `isAuthRequired()` στο `src/shared/utils/apiAuth.ts` διατηρεί την ανώνυμη εκκίνηση ανοιχτή **μόνο για ομότιμους loopback**. Το Loopback αποφασίζεται από τα αξιόπιστα σήματα ομότιμων, με τη σειρά: ο πραγματικός ομότιμος TCP με σφραγίδα διακριτικού (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, αυτό που βλέπει η πολιτική), η δική της ετυμηγορία `AUTHZ_HEADER_PEER_LOCALITY` της διοχέτευσης (αυτό που βλέπουν οι χειριστές διαδρομών, αξιόπιστο μόνο όταν έχει οριστεί το `OMNIROUTE_PEER_STAMP_TOKEN`), ή ένας πραγματικός ομότιμος socket για άμεσους καλούντες. Το `Host` / `nextUrl.hostname` δεν συμβουλεύονται ποτέ, και η εγγραφή του πρώτου κωδικού πρόσβασης (`POST /api/settings/require-login`) υπόκειται στον ίδιο περιορισμό αντί να είναι ανοιχτή σε κάθε ομότιμο δικτύου (GHSA-7pq4-8pvv-rx7r). Η `managementPolicy` μεταβιβάζει τη δική της ετυμηγορία `peerContext` ρητά, οπότε οι ORIGINAL (πριν την αφαίρεση) κεφαλίδες της αίτησης δεν την αποφασίζουν ποτέ.

### Επίπεδο 3 — MANAGEMENT (προεπιλογή)

Όλες οι άλλες διαδρομές διαχείρισης. Απαιτείται έλεγχος ταυτότητας εκτός εάν έχει διαμορφωθεί το `requireLogin=false`. Τα διακριτικά CLI μπορούν να πιστοποιήσουν αυτές τις διαδρομές (loopback + έγκυρο HMAC).

## Σειρά αξιολόγησης

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → συνέχισε στο επόμενο βήμα
     → non-loopback, Bearer με manage-scope
        ΚΑΙ isLocalOnlyBypassableByManageScope   → επέτρεψε (management_key)
     → διαφορετικά                               → απόρριψε με 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → επέτρεψε (system)
  3. hasValidCliToken(headers)?
     → επέτρεψε (cli) [loopback + έλεγχος HMAC με timingSafeEqual]
  4. isAlwaysProtectedPath(path) ή requireLogin=true?
     → isDashboardSessionAuthenticated?
        → επέτρεψε (dashboard_session)
     → Bearer με manage-scope σε μη παρακάμψιμη διαδρομή;
        → επέτρεψε (management_key)
     → απόρριψε με 401/403
  5. requireLogin=false?
     → επέτρεψε (anonymous)
```

Ο κλάδος manage-scope του βήματος 1 είναι η μόνη αυθεντικοποιημένη διαδρομή που μπορεί να ικανοποιήσει μια διαδρομή
LOCAL_ONLY· σε περίπτωση αποτυχίας του auth-backend επιστρέφεται 503 (όχι 403), ώστε μια
ληγμένη DB να μην υποβαθμίζεται σιωπηρά σε "deny".

## Προσθήκη νέας διαδρομής με δυνατότητα spawn

1. Προσθέστε το πρόθεμα διαδρομής στο `LOCAL_ONLY_API_PREFIXES` στο
   `src/server/authz/routeGuard.ts`
2. Προσθέστε μια δοκιμή στο `tests/unit/authz/routeGuard.test.ts` που να επαληθεύει ότι το
   `isLocalOnlyPath()` επιστρέφει true για το νέο πρόθεμα
3. **Μην παραλείψετε ποτέ αυτό το βήμα** — δείτε τον Αυστηρό Κανόνα #15 στο `CLAUDE.md`
4. Αποφασίστε: ανήκει αυτή η διαδρομή ΕΠΙΣΗΣ στο `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`;
   Η προεπιλεγμένη απάντηση είναι **όχι**. Επιλέξτε το μόνο όταν η διαδρομή είναι ασφαλές να εκτεθεί σε έναν
   κάτοχο manage-scope (δηλαδή ΔΕΝ εκκινεί αυθαίρετο κώδικα ελεγχόμενο από τον χρήστη).

## Προσθήκη διαδρομής παρακάμψιμης μέσω manage-scope

1. Επιβεβαιώστε ότι η διαδρομή δεν εκτελεί κώδικα ή εντολές που παρέχονται από τον χρήστη. Αν το
   κάνει, σταματήστε — αυτή η εξαίρεση δεν είναι το κατάλληλο εργαλείο.
2. Προσθέστε το πρόθεμα στο `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` στο
   `src/server/authz/routeGuard.ts`
3. Προσθέστε κάλυψη στο `tests/unit/authz/management-policy.test.ts` και για τις τέσσερις
   μορφές αιτήματος: χωρίς Bearer (403), manage Bearer (επιτρέπεται), μη-manage Bearer
   (403), και τη δοκιμή παλινδρόμησης ανά πρόθεμα που διασφαλίζει ότι το `/api/cli-tools/runtime/*` παραμένει
   αυστηρά loopback ακόμη και με manage Bearer.

## Τεκμηρίωση επιπέδων ασφαλείας στο OpenAPI

Κατά την προσθήκη μιας νέας διαδρομής στο `docs/openapi.yaml`, εφαρμόστε την αντίστοιχη
επέκταση προμηθευτή, εάν η διαδρομή ταξινομείται από το `routeGuard.ts`:

| Ταξινόμηση routeGuard.ts       | Σχολιασμός YAML             | Επιβολή                                              |
| ------------------------------ | --------------------------- | ---------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`      | `x-loopback-only: true`     | Αποκλείεται άνευ όρων από non-loopback               |
| `ALWAYS_PROTECTED_API_PATHS`   | `x-always-protected: true`  | Απαιτείται auth ακόμη και με `requireLogin=false`    |
| Εσωτερική διαδρομή admin/debug | `x-internal: true`          | Κρυφή από το /dashboard/api-endpoints από προεπιλογή |
| Καμία (δημόσια / τυπικό auth)  | (δεν απαιτείται σχολιασμός) | Τυπική πρόσβαση ελεγχόμενη από το `requireLogin`     |

### Επικύρωση

Δύο scripts επιβάλλουν τη συνέπεια μεταξύ των σχολιασμών YAML και του `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — αποτυγχάνει αν η κάλυψη είναι < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — αποτυγχάνει αν οι σχολιασμοί `x-loopback-only` ή
  `x-always-protected` αποκλίνουν από τις σταθερές χρόνου μεταγλώττισης

Και τα δύο scripts εκτελούνται στο pre-commit hook και στο CI.

### Κανόνας ψευδώς θετικών αποτελεσμάτων

Αν το `x-always-protected` ή το `x-loopback-only` έχει προστεθεί ως σχολιασμός σε μια διαδρομή που ΔΕΝ βρίσκεται στη
σταθερά του `routeGuard.ts`, το script κάλυψης αποτυγχάνει. Η διόρθωση είναι πάντα η ευθυγράμμιση του
YAML με ό,τι πραγματικά επιβάλλει το `routeGuard.ts` — όχι η προσθήκη διαδρομών στο `routeGuard.ts`
χωρίς να υλοποιηθεί επίσης η λογική επιβολής.
