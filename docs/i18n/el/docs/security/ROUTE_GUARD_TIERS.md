## Επισκόπηση

Όλες οι διαδρομές του API διαχείρισης του OmniRoute ταξινομούνται σε ένα από τρία επίπεδα
προστασίας. Η ταξινόμηση είναι στατική, ορίζεται στο `src/server/authz/routeGuard.ts`
και αξιολογείται πριν εκτελεστεί οποιοσδήποτε άλλος κλάδος ελέγχου ταυτότητας.

## Επίπεδα

### Επίπεδο 1 — LOCAL_ONLY

**Επιβάλλεται από:** `isLocalOnlyPath(path)` → έλεγχος κεντρικού υπολογιστή loopback
**Παράκαμψη:** Καμία από προεπιλογή. Υπάρχει μια περιορισμένη εξαίρεση για διαδρομές στο
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, όταν το αίτημα περιλαμβάνει έγκυρο
κλειδί API με το scope `manage` (βλ. [Εξαίρεση για το scope manage](#manage-scope-carve-out)).

Αυτές οι διαδρομές δημιουργούν θυγατρικές διεργασίες ή εκτελούν κώδικα κατά τον χρόνο εκτέλεσης. Η έκθεσή τους σε
κίνηση που δεν προέρχεται από loopback θα επέτρεπε σε έναν εισβολέα που απέκτησε έγκυρο JWT (π.χ.
μέσω μιας διοχέτευσης Cloudflared/Ngrok) να ενεργοποιήσει τη δημιουργία διεργασιών — μια γνωστή κατηγορία
CVE ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Τι είναι το GHSA-fhh6-4qxv-rpqj (η κατηγορία επίθεσης):** ένας διακομιστής διαχείρισης/agent
εκθέτει ένα endpoint που εκκινεί μια υποδιεργασία (`npm install`, `node`, ένα πρόγραμμα περιήγησης,
έναν διακομιστή μεσολάβησης, `git`, `tar`, …). Εάν αυτό το endpoint είναι προσβάσιμο εκτός του κεντρικού υπολογιστή — επειδή
ο διαχειριστής τοποθέτησε το OmniRoute πίσω από μια διοχέτευση nginx/Cloudflare/Tailscale και διέρρευσε ένα JWT
ή ο έλεγχος ταυτότητας είχε ρυθμιστεί εσφαλμένα — ο εισβολέας μετατρέπει την «κλήση ενός API» σε «εκτέλεση μιας
εντολής στον κεντρικό υπολογιστή» (απομακρυσμένη εκτέλεση κώδικα). Το OmniRoute το αποτρέπει επιβάλλοντας
**έλεγχο κεντρικού υπολογιστή loopback άνευ όρων, πριν από οποιονδήποτε έλεγχο ταυτότητας**, σε κάθε
διαδρομή που μπορεί να δημιουργήσει διεργασίες: ένα διαρρεύσαν token μέσω διοχέτευσης εξακολουθεί να μην μπορεί να φτάσει στη λειτουργία δημιουργίας διεργασιών.

**Το πλήρες σύνολο LOCAL_ONLY.** Η αυθεντική πηγή είναι τα
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` στο
`src/server/authz/routeGuard.ts`· ο παρακάτω πίνακας αντικατοπτρίζει την τρέχουσα κατάσταση. Η
πύλη `check-route-guard-membership` απαριθμεί κάθε `route.ts` κάτω από τα
προθέματα που μπορούν να δημιουργήσουν διεργασίες και προκαλεί αποτυχία του CI εάν κάποιο από αυτά δεν έχει ταξινομηθεί ως αποκλειστικά τοπικό.

#### Εξαίρεση βάσει εμβέλειας διαχείρισης

Ένα υποσύνολο διαδρομών LOCAL_ONLY ΕΝΔΕΧΕΤΑΙ επίσης να είναι προσβάσιμο από διευθύνσεις εκτός loopback, εάν και μόνο εάν το αίτημα περιλαμβάνει ένα `Authorization: Bearer <api-key>` του οποίου τα μεταδεδομένα περιλαμβάνουν την εμβέλεια `manage` (ή `admin`). Η εξαίρεση ενεργοποιείται ρητά ανά διαδρομή μέσω του `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, ώστε η προεπιλογή για κάθε νέα διαδρομή LOCAL_ONLY να παραμένει αυστηρά περιορισμένη στο loopback. Τα μη αυθεντικοποιημένα αιτήματα και τα αιτήματα με κλειδιά χωρίς εμβέλεια διαχείρισης εξακολουθούν να απορρίπτονται με `403 LOCAL_ONLY`.

Προς το παρόν, το μόνο πρόθεμα που μπορεί να παρακαμφθεί είναι το `/api/mcp/`. Τα `/api/cli-tools/runtime/` και `/api/services/` εξαιρούνται σκόπιμα, επειδή μπορούν να εκκινήσουν αυθαίρετες υποδιεργασίες (`npm install`, `node`), δηλαδή ακριβώς την κατηγορία CVE που υπάρχει για να αποτρέπει το επίπεδο LOCAL_ONLY.

**#7895 — περιορισμένη εμβέλεια `mcp:connect`:** η εξαίρεση του `/api/mcp/` αποδέχεται ΕΠΙΣΗΣ ένα κλειδί Bearer που διαθέτει την περιορισμένη εμβέλεια `mcp:connect` (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), η οποία ελέγχεται μέσω του `hasMcpConnectOrManageScope()` στο `src/server/authz/policies/management.ts`. Αυτό περιορίζεται ΜΟΝΟ στο `/api/mcp/` — το `mcp:connect` δεν παρέχει κανένα δικαίωμα σε οποιαδήποτε άλλη διαδρομή διαχείρισης (συμπεριλαμβανομένου κάθε άλλου προθέματος παράκαμψης LOCAL_ONLY, εάν προστεθεί ποτέ κάποιο) και εξαιρείται σκόπιμα από το `MANAGEMENT_API_KEY_SCOPES`. Ένα κλειδί που διαθέτει `manage`/`admin` εξακολουθεί να περνά την εξαίρεση ακριβώς όπως πριν· το `mcp:connect` αποτελεί μια εναλλακτική χαμηλότερων προνομίων για απομακρυσμένους καλούντες που χρησιμοποιούν αποκλειστικά MCP και δεν θα πρέπει να χρειάζονται ευρεία πρόσβαση διαχείρισης.

| Αίτημα                                              | Διαδρομή                   | Αποτέλεσμα                    |
| --------------------------------------------------- | -------------------------- | ----------------------------- |
| Εκτός loopback, χωρίς Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY                |
| Εκτός loopback, Bearer με εμβέλεια `manage`         | `/api/mcp/*`               | Επιτρέπεται                   |
| Εκτός loopback, Bearer με εμβέλεια `mcp:connect`    | `/api/mcp/*`               | Επιτρέπεται                   |
| Εκτός loopback, Bearer χωρίς `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                |
| Εκτός loopback, Bearer με εμβέλεια `mcp:connect`    | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                |
| Εκτός loopback, Bearer με εμβέλεια `manage`         | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                |
| Loopback, με οποιοδήποτε/χωρίς Bearer               | οποιοδήποτε LOCAL_ONLY     | Επιτρέπεται (ο έλεγχος περνά) |

#### Οδηγίες για διαχειριστές και έλεγχος

Εάν εκτελείτε το OmniRoute πίσω από αντίστροφο διακομιστή μεσολάβησης ή σήραγγα (nginx, Caddy, Cloudflare Tunnel, Tailscale, Ngrok), ο έλεγχος loopback εξακολουθεί να προστατεύει τις παραπάνω διαδρομές που μπορούν να εκκινήσουν διεργασίες — ένα αίτημα του οποίου η διεύθυνση πελάτη δεν είναι loopback απορρίπτεται με `403 LOCAL_ONLY` **πριν εκτελεστεί η αυθεντικοποίηση**, επομένως ένα JWT που έχει διαρρεύσει δεν μπορεί να φτάσει σε λειτουργία εκκίνησης διεργασίας. Παραμένουν δύο ευθύνες για τους διαχειριστές:

- **Μην «διορθώνετε» ένα 403 πλαστογραφώντας τη διεύθυνση IP του πελάτη ως loopback.** Η ρύθμιση του `X-Forwarded-For: 127.0.0.1` ή η χρήση ενός διακομιστή μεσολάβησης που επανεγγράφει τη διεύθυνση προέλευσης ως loopback επαναφέρει ακριβώς την κατηγορία RCE που αποκλείει αυτό το επίπεδο. Εκθέστε τον πίνακα ελέγχου/API μέσω του διακομιστή μεσολάβησης — ποτέ τις διαδρομές που μπορούν να εκκινήσουν διεργασίες.
- **Διατηρείτε ελάχιστη την παράκαμψη βάσει εμβέλειας διαχείρισης.** Μόνο το `/api/mcp/` μπορεί να παρακαμφθεί και μόνο με ένα κλειδί API εμβέλειας `manage`. Τα `SPAWN_CAPABLE_PREFIXES` δεν μπορούν ποτέ να προστεθούν στη λίστα παράκαμψης — το σχήμα zod τα απορρίπτει και το `isLocalOnlyBypassableByManageScope` τα απαγορεύει κατά την εκτέλεση (άμυνα σε βάθος), πράγμα που εννοεί ο πίνακας ελέγχου με τη φράση «δεν μπορεί να καταστεί παρακάμψιμο». Οι διαδρομές με δυναμικά τμήματα και οι στατικές διαδρομές που μπορούν να εκκινήσουν διεργασίες κάτω από το `/api/providers/` (π.χ. `/login`, `/refresh-cursor`) καλύπτονται από τα συνοδευτικά `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS`, τα οποία βασίζονται σε κανονικές εκφράσεις, στο `src/shared/constants/spawnCapablePrefixes.ts`, και όχι από τον επίπεδο πίνακα `SPAWN_CAPABLE_PREFIXES` — ο επίπεδος πίνακας θα έπρεπε να καλύπτει ολόκληρο το πρόθεμα `/api/providers/` για να τις εντοπίσει, διευρύνοντας υπερβολικά ένα δέντρο διαδρομών που οι απομακρυσμένοι πίνακες ελέγχου χρησιμοποιούν νόμιμα για λειτουργίες CRUD παρόχων.

**Έλεγχος πρόσβασης** — για να επαληθεύσετε ότι τίποτα εκτός του κεντρικού υπολογιστή δεν φτάνει σε αυτές τις διαδρομές:

- Ανοίξτε το **Απόθεμα εξουσιοδότησης** στη διαδρομή `/dashboard/settings/security`: εμφανίζει τη ζωντανή λίστα προθεμάτων LOCAL_ONLY, ποια προθέματα μπορούν να παρακαμφθούν και το σύνολο διαδρομών που μπορούν να εκκινήσουν διεργασίες και καθορίζονται κατά τη μεταγλώττιση («δεν μπορούν να καταστούν παρακάμψιμες»).
- Αναζητήστε στα αρχεία καταγραφής του αντίστροφου διακομιστή μεσολάβησης / πρόσβασης τα παραπάνω προθέματα σε συνδυασμό με μια διεύθυνση πελάτη εκτός loopback. Κάθε τέτοια καταχώριση που επέστρεψε `200` αντί για `403 LOCAL_ONLY` σημαίνει ότι ο διακομιστής μεσολάβησης αποκρύπτει την πραγματική διεύθυνση IP του πελάτη — διορθώστε τον διακομιστή μεσολάβησης.
- Μια καταχώριση `403 LOCAL_ONLY` στα αρχεία καταγραφής του OmniRoute για μία από αυτές τις διαδρομές σημαίνει ότι ο μηχανισμός προστασίας λειτουργεί όπως προβλέπεται και δεν αποτελεί σφάλμα που πρέπει να αποκρυφτεί.

### Επίπεδο 2 — ALWAYS_PROTECTED

**Επιβάλλεται από:** `isAlwaysProtectedPath(path)` → παρακάμπτει την παράκαμψη `requireLogin=false`  
**Παράκαμψη:** Καμία όταν `requireLogin=false`· απαιτείται πάντα JWT

Αυτές οι διαδρομές εκτελούν καταστροφικές ή μη αναστρέψιμες ενέργειες. Η αποδοχή τους σε μια εγκατάσταση «χωρίς κωδικό πρόσβασης» θα σήμαινε ότι οποιοσδήποτε στο ίδιο LAN θα μπορούσε να διαγράψει τη βάση δεδομένων ή να τερματίσει τη διεργασία του διακομιστή.

| Διαδρομή                                  | Αιτία                                                                         |
| ----------------------------------------- | ----------------------------------------------------------------------------- |
| `/api/shutdown`                           | Τερματίζει τη διεργασία του διακομιστή                                        |
| `/api/settings/database`                  | Εξαγωγή, εισαγωγή και διαγραφή της βάσης δεδομένων                            |
| `/api/db-backups`                         | Πρόσβαση σε πλήρη αρχεία αντιγράφων ασφαλείας της βάσης                       |
| `/api/settings/export-json`               | Εξάγει ολόκληρο το blob ρυθμίσεων (συμπερ. μυστικών)                          |
| `/api/settings/import-json`               | Αντικαθιστά ολόκληρο το blob ρυθμίσεων                                        |
| `/api/providers/health-autopilot/actions` | Εκτελεί διορθωτικές ενέργειες αυτόματου πιλότου                               |
| `/api/settings/obsidian`                  | Εκδίδει επαναχρησιμοποιήσιμα διαπιστευτήρια WebDAV για οποιαδήποτε ρίζα vault |

**Απόκριση σε περίπτωση παραβίασης:** `401 Authentication required`

Το `/api/settings/obsidian` καλύπτει το θυγατρικό του `/webdav`: το `POST` κατευθύνει την υπηρεσία αρχείων WebDAV —
η οποία εξυπηρετείται από το προσαρμοσμένο επίπεδο Node πριν από το Next.js, εκτός αυτής της διοχέτευσης — σε μια ρίζα
που επιλέγεται από τον καλούντα και επιστρέφει πρόσφατα δημιουργημένα διαπιστευτήρια Basic, το `DELETE` τα ανανεώνει,
και το γονικό `POST` αποθηκεύει το διακριτικό του Obsidian REST API. Το GHSA-62vw απέκρυψε μόνο την αποκάλυψη του κωδικού πρόσβασης μέσω `GET`· η έκδοση
παρέμενε στο επίπεδο ανοικτής αποδοχής σε περίπτωση αποτυχίας (GHSA-7pq4-8pvv-rx7r). Η `enableObsidianVaultSync()` επιπλέον
απορρίπτει ένα vault που είναι ο κατάλογος δεδομένων, βρίσκεται μέσα σε αυτόν ή τον περιέχει.

### Η αρχικοποίηση νέας εγκατάστασης περιορίζεται στο loopback — βάσει του πραγματικού ομότιμου, όχι του `Host`

Όταν δεν έχει ρυθμιστεί κωδικός πρόσβασης διαχείρισης (και δεν υπάρχει `INITIAL_PASSWORD`), η `isAuthRequired()` στο
`src/shared/utils/apiAuth.ts` διατηρεί ανοικτή την ανώνυμη αρχικοποίηση **μόνο για ομότιμους loopback**.
Το loopback προσδιορίζεται από τα αξιόπιστα σήματα του ομότιμου, με την ακόλουθη σειρά: τον πραγματικό ομότιμο TCP που έχει επισημανθεί με διακριτικό
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, αυτό που βλέπει η πολιτική), την ετυμηγορία
`AUTHZ_HEADER_PEER_LOCALITY` της ίδιας της διοχέτευσης (αυτό που βλέπουν οι χειριστές διαδρομών, αξιόπιστο μόνο όσο
έχει οριστεί το `OMNIROUTE_PEER_STAMP_TOKEN`) ή έναν πραγματικό ομότιμο υποδοχής για άμεσους καλούντες. Τα `Host` /
`nextUrl.hostname` δεν λαμβάνονται ποτέ υπόψη και η εγγραφή του πρώτου κωδικού πρόσβασης
(`POST /api/settings/require-login`) υπόκειται στον ίδιο περιορισμό, αντί να είναι ανοικτή σε κάθε
ομότιμο του δικτύου (GHSA-7pq4-8pvv-rx7r). Η `managementPolicy` μεταβιβάζει ρητά τη δική της ετυμηγορία `peerContext`,
ώστε οι κεφαλίδες του ΑΡΧΙΚΟΥ αιτήματος (πριν από την αφαίρεση) να μην την καθορίζουν ποτέ.

### Επίπεδο 3 — ΔΙΑΧΕΙΡΙΣΗ (προεπιλογή)

Όλες οι άλλες διαδρομές διαχείρισης. Απαιτείται έλεγχος ταυτότητας, εκτός εάν έχει
ρυθμιστεί `requireLogin=false`. Τα διακριτικά CLI μπορούν να πιστοποιούν την ταυτότητα για αυτές τις διαδρομές (loopback + έγκυρο HMAC).

## Σειρά αξιολόγησης

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → συνέχισε στο επόμενο βήμα
     → non-loopback, Bearer με manage-scope
        ΚΑΙ isLocalOnlyBypassableByManageScope   → επέτρεψε (management_key)
     → διαφορετικά                               → απόρριψε με 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → επέτρεψε (system)
  3. hasValidCliToken(headers)?
     → επέτρεψε (cli) [loopback + έλεγχος HMAC με timingSafeEqual]
  4. isAlwaysProtectedPath(path) ή requireLogin=true?
     → isDashboardSessionAuthenticated?
        → επέτρεψε (dashboard_session)
     → Bearer με manage-scope σε μη παρακάμψιμη διαδρομή;
        → επέτρεψε (management_key)
     → απόρριψε με 401/403
  5. requireLogin=false?
     → επέτρεψε (anonymous)
```

Ο κλάδος manage-scope του βήματος 1 είναι η μόνη αυθεντικοποιημένη διαδρομή που μπορεί να ικανοποιήσει μια διαδρομή
LOCAL_ONLY· σε περίπτωση αποτυχίας του auth-backend επιστρέφεται 503 (όχι 403), ώστε μια
ληγμένη DB να μην υποβαθμίζεται σιωπηρά σε "deny".

## Προσθήκη νέας διαδρομής με δυνατότητα spawn

1. Προσθέστε το πρόθεμα διαδρομής στο `LOCAL_ONLY_API_PREFIXES` στο
   `src/server/authz/routeGuard.ts`
2. Προσθέστε μια δοκιμή στο `tests/unit/authz/routeGuard.test.ts` που να επαληθεύει ότι το
   `isLocalOnlyPath()` επιστρέφει true για το νέο πρόθεμα
3. **Μην παραλείψετε ποτέ αυτό το βήμα** — δείτε τον Αυστηρό Κανόνα #15 στο `CLAUDE.md`
4. Αποφασίστε: ανήκει αυτή η διαδρομή ΕΠΙΣΗΣ στο `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`;
   Η προεπιλεγμένη απάντηση είναι **όχι**. Επιλέξτε το μόνο όταν η διαδρομή είναι ασφαλές να εκτεθεί σε έναν
   κάτοχο manage-scope (δηλαδή ΔΕΝ εκκινεί αυθαίρετο κώδικα ελεγχόμενο από τον χρήστη).

## Προσθήκη διαδρομής παρακάμψιμης μέσω manage-scope

1. Επιβεβαιώστε ότι η διαδρομή δεν εκτελεί κώδικα ή εντολές που παρέχονται από τον χρήστη. Αν το
   κάνει, σταματήστε — αυτή η εξαίρεση δεν είναι το κατάλληλο εργαλείο.
2. Προσθέστε το πρόθεμα στο `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` στο
   `src/server/authz/routeGuard.ts`
3. Προσθέστε κάλυψη στο `tests/unit/authz/management-policy.test.ts` και για τις τέσσερις
   μορφές αιτήματος: χωρίς Bearer (403), manage Bearer (επιτρέπεται), μη-manage Bearer
   (403), και τη δοκιμή παλινδρόμησης ανά πρόθεμα που διασφαλίζει ότι το `/api/cli-tools/runtime/*` παραμένει
   αυστηρά loopback ακόμη και με manage Bearer.

## Τεκμηρίωση επιπέδων ασφαλείας στο OpenAPI

Κατά την προσθήκη μιας νέας διαδρομής στο `docs/openapi.yaml`, εφαρμόστε την αντίστοιχη
επέκταση προμηθευτή, εάν η διαδρομή ταξινομείται από το `routeGuard.ts`:

| Ταξινόμηση routeGuard.ts       | Σχολιασμός YAML             | Επιβολή                                              |
| ------------------------------ | --------------------------- | ---------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`      | `x-loopback-only: true`     | Αποκλείεται άνευ όρων από non-loopback               |
| `ALWAYS_PROTECTED_API_PATHS`   | `x-always-protected: true`  | Απαιτείται auth ακόμη και με `requireLogin=false`    |
| Εσωτερική διαδρομή admin/debug | `x-internal: true`          | Κρυφή από το /dashboard/api-endpoints από προεπιλογή |
| Καμία (δημόσια / τυπικό auth)  | (δεν απαιτείται σχολιασμός) | Τυπική πρόσβαση ελεγχόμενη από το `requireLogin`     |

### Επικύρωση

Δύο scripts επιβάλλουν τη συνέπεια μεταξύ των σχολιασμών YAML και του `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — αποτυγχάνει αν η κάλυψη είναι < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — αποτυγχάνει αν οι σχολιασμοί `x-loopback-only` ή
  `x-always-protected` αποκλίνουν από τις σταθερές χρόνου μεταγλώττισης

Και τα δύο scripts εκτελούνται στο pre-commit hook και στο CI.

### Κανόνας ψευδώς θετικών αποτελεσμάτων

Αν το `x-always-protected` ή το `x-loopback-only` έχει προστεθεί ως σχολιασμός σε μια διαδρομή που ΔΕΝ βρίσκεται στη
σταθερά του `routeGuard.ts`, το script κάλυψης αποτυγχάνει. Η διόρθωση είναι πάντα η ευθυγράμμιση του
YAML με ό,τι πραγματικά επιβάλλει το `routeGuard.ts` — όχι η προσθήκη διαδρομών στο `routeGuard.ts`
χωρίς να υλοποιηθεί επίσης η λογική επιβολής.
