Η διαφανής αποκρυπτογράφηση TPROXY είναι η **5η λειτουργία καταγραφής** του OmniRoute για τη
στοίβα MITM των [Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md).
Υποκλέπτει και **αποκρυπτογραφεί** την τοπική εξερχόμενη κίνηση HTTPS στο Linux
χρησιμοποιώντας TPROXY του πυρήνα + δρομολόγηση βάσει πολιτικής — **χωρίς** πλαστογράφηση του `/etc/hosts` και
**χωρίς** τροποποίηση των ρυθμίσεων διακομιστή μεσολάβησης σε επίπεδο λειτουργικού συστήματος. Είναι κατάλληλη για περιβάλλοντα χωρίς γραφικό περιβάλλον
(δεν υπάρχουν αλλαγές DNS που πρέπει να αναιρεθούν) και οι κανόνες του τείχους προστασίας εκκαθαρίζονται αυτόματα κατά την επανεκκίνηση.

Σε αντίθεση με τις άλλες λειτουργίες καταγραφής, το TPROXY δεν χρειάζεται ρύθμιση ανά κεντρικό υπολογιστή: υποκλέπτει διαφανώς
**οποιονδήποτε** κεντρικό υπολογιστή προορισμού σε μια θύρα-στόχο, τερματίζει το TLS με
ένα πιστοποιητικό τελικού οντοτήτος που εκδίδει δυναμικά ανά όνομα κεντρικού υπολογιστή SNI, καταγράφει την αποκρυπτογραφημένη
ανταλλαγή και επανακρυπτογραφεί το αίτημα προς τον αρχικό προορισμό.

> **Μόνο για Linux, μόνο για root, με ρητή ενεργοποίηση.** Αυτή η λειτουργία απαιτεί Linux, ένα εγγενές πρόσθετο
> μεταγλωττισμένο με αλυσίδα εργαλείων C και τη δυνατότητα **CAP_NET_ADMIN** (συνήθως root). Προστατεύεται
> πίσω από το API του AgentBridge που είναι προσβάσιμο μόνο μέσω loopback και είναι απενεργοποιημένη από προεπιλογή. Μια έμπιστη
> αρχή πιστοποίησης MITM που μπορεί να υπογράψει για οποιονδήποτε κεντρικό υπολογιστή αποτελεί ισχυρή δυνατότητα — δείτε την [§6 Ασφάλεια](#6-security).

**Πηγαίος κώδικας:** `src/mitm/tproxy/`
**Διαδρομή API:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**Διακόπτης στον πίνακα ελέγχου:** Traffic Inspector → γραμμή εργαλείων λειτουργιών καταγραφής → **"Αποκρυπτογράφηση TPROXY"** ⚠
**Δείτε επίσης:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 Τι είναι και πότε να το χρησιμοποιείτε

Οι άλλες τέσσερις λειτουργίες καταγραφής έχουν καθεμία έναν περιορισμό:

| Λειτουργία                           | Πώς δρομολογείται η κίνηση                                                       | Περιορισμός                                                                    |
| ------------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| AgentBridge                          | Πλαστογράφηση DNS μέσω `/etc/hosts` για ένα σταθερό σύνολο κεντρικών υπολογιστών | μόνο οι καταχωρισμένοι κεντρικοί υπολογιστές πρακτόρων IDE                     |
| Προσαρμοσμένοι κεντρικοί υπολογιστές | Πλαστογράφηση DNS μέσω `/etc/hosts` ανά κεντρικό υπολογιστή                      | μία καταχώριση ανά κεντρικό υπολογιστή· sudo για επεξεργασία του αρχείου hosts |
| HTTP_PROXY                           | Μεταβλητές περιβάλλοντος `HTTP_PROXY`/`HTTPS_PROXY`                              | μόνο εφαρμογές που σέβονται τη μεταβλητή περιβάλλοντος                         |
| Διακομιστής μεσολάβησης συστήματος   | Ρυθμίσεις διακομιστή μεσολάβησης του λειτουργικού συστήματος                     | τροποποιεί την καθολική κατάσταση· απαιτεί επαναφορά                           |

Αντίθετα, η διαφανής αποκρυπτογράφηση TPROXY δρομολογεί την κίνηση στο επίπεδο του **πυρήνα**. Επισημαίνει
τις νέες τοπικές εξερχόμενες συνδέσεις TCP προς μια θύρα-στόχο (προεπιλογή `443`) στην
αλυσίδα `mangle OUTPUT`, ένας κανόνας `ip rule` επαναδρομολογεί τα επισημασμένα πακέτα προς τοπική παράδοση
και, κατά την επανείσοδο, ο στόχος `TPROXY` του `mangle PREROUTING` τα παραδίδει σε έναν
ακροατή **IP_TRANSPARENT** — ο οποίος στη συνέχεια τερματίζει το TLS και καταγράφει το μη κρυπτογραφημένο περιεχόμενο.

Χρησιμοποιήστε τη όταν θέλετε να καταγράψετε και να αποκρυπτογραφήσετε κίνηση από μια διεργασία που:

- επικοινωνεί με έναν κεντρικό υπολογιστή τον οποίο δεν καταχωρίζει το AgentBridge, και
- δεν σέβεται το `HTTP_PROXY`, και
- δεν θέλετε να επηρεάσετε με μια αλλαγή διακομιστή μεσολάβησης σε επίπεδο συστήματος.

Επειδή η υποκλοπή πραγματοποιείται στον πυρήνα, η διεργασία προέλευσης **δεν χρειάζεται καμία
αλλαγή ρύθμισης** — αλλά πρέπει να εμπιστεύεται τη δυναμική αρχή πιστοποίησης που εγκαθιστά το OmniRoute
(δείτε την [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 Απαιτήσεις

| Απαίτηση                | Λεπτομέρειες                                                                                                                                                                |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Λειτουργικό σύστημα** | Μόνο Linux — το **IP_TRANSPARENT** είναι επιλογή socket αποκλειστικά για Linux. Ο loader επιστρέφει "unavailable" σε κάθε άλλη πλατφόρμα.                                   |
| **Προνόμια**            | Η δυνατότητα **CAP_NET_ADMIN** για τη δημιουργία του διαφανούς socket και την εφαρμογή κανόνων `iptables`/`ip` — στην πράξη, εκτελέστε ως root.                             |
| **Εγγενές πρόσθετο**    | Πρέπει να γίνει build ή να διανεμηθεί ως prebuild ένα μικροσκοπικό πρόσθετο N-API (`src/mitm/tproxy/native/transparent.c`). Δείτε [§3](#3-the-native-ip_transparent-addon). |
| **Αρθρώματα πυρήνα**    | `iptables` με υποστήριξη αντιστοίχισης `TPROXY`, `mangle` και `mark` (επικυρωμένο με τον πυρήνα 6.8.0).                                                                     |

**Ομαλή υποβάθμιση:** εάν λείπει οποιαδήποτε απαίτηση (σύστημα εκτός Linux, απουσία toolchain,
μη ολοκληρωμένο build του πρόσθετου), ο loader του πρόσθετου (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
επιστρέφει `null` αντί να προκαλεί εξαίρεση. Στη συνέχεια, η κατάσταση της λειτουργίας καταγραφής αναφέρει
`available: false`, ο διακόπτης στον πίνακα ελέγχου είναι **απενεργοποιημένος** με την επεξήγηση
"Η αποκρυπτογράφηση TPROXY απαιτεί Linux + root + το εγγενές πρόσθετο", ενώ το υπόλοιπο
OmniRoute συνεχίζει να λειτουργεί.

## §3 Το εγγενές πρόσθετο IP_TRANSPARENT

Το module `net` του Node δεν μπορεί να εκτελέσει `setsockopt(IP_TRANSPARENT)` _πριν_ από το `bind()`, κάτι που
απαιτεί το TPROXY (διαφορετικά, ο πυρήνας απορρίπτει τα ανακατευθυνόμενα πακέτα). Το πρόσθετο
(`src/mitm/tproxy/native/transparent.c`, με build μέσω του `binding.gyp`) είναι ένα μικρό module N-API
που εκθέτει τρεις συναρτήσεις, οι οποίες χρησιμοποιούνται μέσω του `transparentSocket.ts`:

| Συνάρτηση πρόσθετου                   | Εργασία στο socket                                                                                       | Χρήση                                                                                     |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, επιστρέφει το ακατέργαστο fd | ο listener διαφανούς καταγραφής (το Node υιοθετεί το fd μέσω του `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | `setsockopt` **SO_MARK** σε υπάρχον fd                                                                   | αποτροπή βρόχου (σήμανση των socket του ίδιου του proxy)                                  |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **πριν** από ένα μη αποκλειστικό `connect()`, επιστρέφει fd                     | η εκ νέου κρυπτογραφημένη προώθηση προς τα ανάντη (το SYN μεταφέρει τη σήμανση)           |

Ο αρχικός προορισμός διαβάζεται από τα `socket.localAddress`/`localPort` — το TPROXY
τον διατηρεί, επομένως δεν απαιτείται αναζήτηση **SO_ORIGINAL_DST**/NAT.

### Δημιουργία build του πρόσθετου

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- Κατά την εκτέλεση του `npm run build`, το `scripts/build/build-tproxy-native.mjs` εκτελεί το `node-gyp
rebuild`. Εκτελείται **μόνο σε Linux και η αποτυχία του δεν είναι κρίσιμη** — η απουσία toolchain απλώς αφήνει
  μη διαθέσιμη τη λειτουργία καταγραφής.
- Το `assembleStandalone.mjs` αντιγράφει το `build/Release/transparent.node` στο
  αυτόνομο bundle· το `transparentSocket.ts` το επιλύει τόσο σε σχέση με το module όσο και
  σε σχέση με το cwd (`<cwd>/src/mitm/tproxy/native/...`).
- Τα `build/` και `prebuilds/` αγνοούνται από το git — το δυαδικό αρχείο **δημιουργείται μέσω build, δεν
  γίνεται ποτέ commit**.

Ο loader πραγματοποιεί αναζήτηση, κατά σειρά προτεραιότητας:
`native/build/Release/transparent.node` και κατόπιν `native/prebuilds/transparent.node`
(τόσο σε σχέση με το module όσο και κάτω από το `<cwd>/src/mitm/tproxy/`).

## §4 Η δυναμική CA ανά SNI και το πρόγραμμα εγκατάστασης του trust store

> **Ενημέρωση #6684:** ο στατικός διακομιστής AgentBridge (`src/mitm/server.cjs`)
> χρησιμοποιεί πλέον το ίδιο αρχιτεκτονικό μοτίβο CA/leaf αντί για ένα μοναδικό
> στατικό, αυτοϋπογεγραμμένο leaf. Χρησιμοποιεί μια **ξεχωριστή** παρουσία CA
> (`src/mitm/cert/rootCa.ts`, η οποία αποθηκεύεται στα `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> και εγκαθίσταται στην προϋπάρχουσα θέση `omniroute-mitm.crt` του trust store
> (αντικαθιστώντας εκεί το παλιό μοναδικό leaf — δεν απαιτείται εκκαθάριση διπλής
> εμπιστοσύνης), ενώ παραμένει πλήρως διαχωρισμένη από την αντίστοιχη θέση
> `omniroute-tproxy-ca.crt` του TPROXY παρακάτω.
> Οι νέες εγκαταστάσεις του AgentBridge λαμβάνουν αυτόματα το μοντέλο CA· μια
> εγκατάσταση που ήδη εμπιστευόταν το παλιό στατικό leaf συνεχίζει να το
> χρησιμοποιεί έως ότου ο διαχειριστής επιλέξει ρητά τη μετάβαση μέσω
> `MITM_ROOT_CA_ENABLED=true` (βλ. `src/mitm/cert/migration.ts`) — μια αξιόπιστη
> MITM CA που μπορεί να υπογράψει leaf για **οποιονδήποτε** host είναι ουσιαστικά
> ισχυρότερη από το παλιό leaf με σταθερό SAN, επομένως η μετάβαση δεν γίνεται
> ποτέ σιωπηρά σε μια ήδη αξιόπιστη εγκατάσταση.

Ιστορικά, το στατικό πιστοποιητικό MITM του AgentBridge λειτουργούσε μόνο επειδή
το AgentBridge παραποιεί μέσω DNS ένα **σταθερό** σύνολο host (το οποίο πλέον
έχει ενοποιηθεί με το παρακάτω μοντέλο). Το TPROXY αναχαιτίζει **αυθαίρετους**
host, επομένως ο listener του πρέπει να παρουσιάζει ένα έγκυρο leaf για
οποιοδήποτε SNI ζητήσει ο client — την ίδια απαίτηση που έχει πλέον και το
AgentBridge για ολόκληρο το σύνολο `MITM_TOOL_HOSTS` (9 καταχωρίσεις εργαλείων)
αντί μόνο για τους 4 host του antigravity.

### Δυναμική CA (`src/mitm/tproxy/dynamicCert.ts`)

Το `DynamicCertStore` εκτελεί μια τοπική CA (βασισμένη στην εξάρτηση `selfsigned`) η οποία:

- Δημιουργεί μια μακράς διάρκειας CA μέσω της `generateMitmCa()` (CN `"OmniRoute MITM CA"`,
  ισχύς 10 ετών, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  RSA 2048 bit / SHA-256).
- Εκδίδει **ένα leaf ανά όνομα host SNI κατ’ απαίτηση** μέσω της `issueLeafCert()` (ισχύς
  1 έτους, `subjectAltName` = ο host SNI) και αποθηκεύει στην cache ένα
  `tls.SecureContext` ανά όνομα host.
- Εκθέτει την `createSNICallback()` για τον διακομιστή που τερματίζει το TLS (βλ. [§5](#5-how-decrypt-and-capture-work)).
- Μπορεί να κατασκευαστεί με μια `existingCa`, ώστε η CA να παραμένει σταθερή μεταξύ
  επανεκκινήσεων (και να μην απαιτείται επανεγκατάσταση στο trust store).

Το ιδιωτικό κλειδί της CA **δεν εγκαταλείπει ποτέ το μηχάνημα**.

### Πρόγραμμα εγκατάστασης trust store (`src/mitm/tproxy/caTrust.ts`)

Ο αναχαιτισμένος client πρέπει να εμπιστεύεται τη δυναμική CA, επομένως η
εκκίνηση της λειτουργίας καταγραφής εγκαθιστά το πιστοποιητικό CA στο trust
store του λειτουργικού συστήματος, σε μια **αποκλειστική θέση** —
`omniroute-tproxy-ca.crt` (σταθερά `TPROXY_CA_CERT_NAME`) — η οποία διατηρείται
ξεχωριστά από τη θέση του στατικού πιστοποιητικού MITM (`omniroute-mitm.crt`),
ώστε τα δύο να μην αντικαθιστούν ποτέ το ένα το άλλο.

Η `installTproxyCa(caPem, sudoPassword?)` εντοπίζει τον κατάλογο αγκυρών της
διανομής (με τον τύπο Debian πρώτο κατά σειρά) και εκτελεί την αντίστοιχη εντολή
ανανέωσης:

| Κατάλογος αγκυρών                           | Εντολή ανανέωσης         |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Η εγκατάσταση τοποθετεί προσωρινά το PEM σε ένα προσωρινό αρχείο και, στη
συνέχεια, εκτελεί προνομιακά την `mkdir -p` για τον κατάλογο αγκυρών, αντιγράφει
με `cp` το προσωρινό αρχείο σε αυτόν και εκτελεί την εντολή ανανέωσης. Η
`uninstallTproxyCa()` αφαιρεί μόνο την αποκλειστική θέση (αφήνοντας ανέπαφο το
στατικό πιστοποιητικό MITM) και εκτελεί ανανέωση — σε συστήματα εκτός Linux δεν
εκτελεί καμία ενέργεια.

Όλες οι προνομιακές εντολές εκτελούνται μέσω της `execFileWithPassword`
(`src/mitm/systemCommands.ts`) — `spawn` με **πίνακες ορισμάτων, χωρίς shell,
χωρίς παρεμβολή συμβολοσειρών** (Αυστηρός Κανόνας #13). Όταν η διεργασία
εκτελείται ως root (π.χ. στο VPS), ο στόχος εκτελείται απευθείας και δεν
απαιτείται κωδικός πρόσβασης· σε desktop όπου η διεργασία δεν εκτελείται ως
root, το `sudoPassword` διοχετεύεται μέσω `sudo -S` στο stdin.

> Το `sudoPassword` του desktop παρέχεται στο σώμα του POST για την
> εξουσιοδότηση της εγκατάστασης στο trust store· αγνοείται πλήρως όταν η
> διεργασία εκτελείται ως root.

## §5 Πώς λειτουργούν η αποκρυπτογράφηση και η καταγραφή

Η διοχέτευση (εξ ολοκλήρου κάτω από το `src/mitm/tproxy/`):

```
τοπική εφαρμογή  ──TCP/443──▶  το mangle OUTPUT επισημαίνει τη σύνδεση (fwmark)
                                ip rule → τοπικός πίνακας δρομολόγησης → lo
                                mangle PREROUTING TPROXY → ακροατής IP_TRANSPARENT (θύρα 8443)
                                    │  captureMode.ts: διαβάζει τον αρχικό προορισμό από το socket.localAddress
                                    ▼
                                tlsCapture.ts:
                                  1. Τερματίζει το TLS του ΠΕΛΑΤΗ με πιστοποιητικό φύλλου ανά SNI (dynamicCert)
                                  2. ένας εσωτερικός http.Server αναλύει το αποκρυπτογραφημένο απλό κείμενο
                                  3. καταγραφή → globalTrafficBuffer.push() με source: "tproxy"
                                     (εφαρμόζονται sanitizeHeaders + maskSecret)
                                  4. προωθεί με ΕΠΑΝΑΚΡΥΠΤΟΓΡΑΦΗΣΗ στον αρχικό προορισμό
                                     μέσω υποδοχής με σήμανση παράκαμψης (connectMarked, αποτροπή βρόχου)
                                    │
                                    ▼
                                αρχικός ανάντη προορισμός (api.example.com)
```

- **Τερματισμός TLS** (`createTlsCaptureServer`): περικλείει την ακατέργαστη υποκλαπείσα
  υποδοχή σε ένα `tls.TLSSocket` από την πλευρά του διακομιστή, χρησιμοποιώντας την
  επανάκληση SNI της δυναμικής CA, και στη συνέχεια παραδίδει την αποκρυπτογραφημένη
  ροή σε έναν εσωτερικό `http.Server` (το τυπικό τέχνασμα τερματισμού MITM). Η
  διάρκεια ζωής των υποδοχών περιορίζεται από το `MITM_IDLE_TIMEOUT_MS`, ώστε μια
  κολλημένη σήραγγα να μην μπορεί να εξαντλήσει τους περιγραφείς αρχείων.
- **Καταγραφή** (`handleDecryptedRequest`): ωθεί ένα `InterceptedRequest` με
  `source: "tproxy"`, αρχικό status `"in-flight"`, κεφαλίδες που έχουν περάσει από
  το `sanitizeHeaders()` και σώματα που έχουν περάσει από το `maskSecret()` πριν
  εισέλθουν στο buffer. Στη συνέχεια, η καταχώριση ενημερώνεται με την απόκριση,
  τα μεγέθη και την καθυστέρηση.
- **Προώθηση με επανακρυπτογράφηση** (`createForward` / `realForward`):
  επανακρυπτογραφεί προς τον αρχικό προορισμό. Το `rejectUnauthorized` έχει ως
  προεπιλογή το **`true`** (ασφαλές από προεπιλογή) — το ανάντη πιστοποιητικό
  επαληθεύεται ως προς το SNI/Host που ζήτησε ο πελάτης, επομένως ο διακομιστής
  μεσολάβησης απορρίπτει ακριβώς ό,τι θα απέρριπτε και ο αρχικός πελάτης.

### Αποτροπή βρόχου (SO_MARK)

Επειδή οι κανόνες επισημαίνουν τις νέες τοπικές εξερχόμενες συνδέσεις, η
επανακρυπτογραφημένη προώθηση του **ίδιου** του διακομιστή μεσολάβησης κανονικά
θα υποκλεπτόταν ξανά — δημιουργώντας έναν άπειρο βρόχο. Η διαδρομή προώθησης
προστατεύεται από αυτό μέσω μιας σήμανσης παράκαμψης υποδοχής (**SO_MARK**):

- Το `realForward` ανοίγει την ανάντη υποδοχή του μέσω
  `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` — `DEFAULT_BYPASS_MARK = 0x539`
  — το οποίο ορίζει το **SO_MARK** **πριν** από το `connect()`, ώστε το SYN της
  προώθησης να φέρει τη σήμανση παράκαμψης.
- Ο κανόνας `mangle OUTPUT` εξαιρεί τις συνδέσεις που φέρουν ήδη τη σήμανση
  παράκαμψης (`-m mark ! --mark <bypassMark>`), επομένως η προώθηση του διακομιστή
  μεσολάβησης **δεν** επισημαίνεται ξανά και δεν εισέρχεται εκ νέου στο TPROXY.

> Σημείωση υλοποίησης: η υποδοχή με σήμανση παράκαμψης πρέπει να εγκαθίσταται στο
> `createConnection` του agent (το `https.request({ createConnection })` αγνοείται
> σιωπηρά όταν υπάρχει agent), διαφορετικά η προώθηση θα άνοιγε μια μη επισημασμένη
> υποδοχή και ο βρόχος θα επανεμφανιζόταν. Αυτή ήταν η διόρθωση αποτροπής βρόχου
> που επικυρώθηκε μέσω e2e δοκιμών.

| Έλεγχος                                                        | Λεπτομέρειες                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

| **Χωρίς παρεμβολή κελύφους**                                   | Όλες οι εντολές `iptables`/`ip`/trust-store εκτελούνται μέσω `execFile`/`execFileWithPassword` με πίνακες ορισμάτων (Αυστηρός Κανόνας #13).                                                                                                                                                                                                                                                                                                            |

**Η CA MITM αποτελεί μια ισχυρή δυνατότητα.** Μια CA την οποία εμπιστεύεται το λειτουργικό σύστημα και η οποία μπορεί να υπογράψει για οποιονδήποτε

ρητή λειτουργία καταγραφής TPROXY μόνο για τοπική χρήση, η οποία είναι απενεργοποιημένη από προεπιλογή, και η καταχώριση στο trust store
καταργείται όταν διακόπτετε τη λειτουργία.

## §7 Συναλλακτική εφαρμογή / αναίρεση του firewall

Μια κατάρρευση δεν πρέπει ποτέ να αφήνει πίσω της έναν κανόνα `mangle` ή μια παρωχημένη διαδρομή. Ο δημιουργός εντολών
(`src/mitm/tproxy/commands.ts`) και ο εκτελεστής (`src/mitm/tproxy/setup.ts`) εγγυώνται ότι
**η αναίρεση είναι το ακριβές αντίστροφο της εφαρμογής, με αντίστροφη σειρά**.

Η `applyTproxy(cfg)` εκτελεί τις εντολές εφαρμογής με τη σειρά· σε **οποιαδήποτε** αποτυχία εκτελεί μια
πλήρη `revertTproxy(cfg)` βέλτιστης προσπάθειας και επανεκπέμπει το σφάλμα — έτσι το firewall είτε
εφαρμόζεται πλήρως είτε αναιρείται πλήρως, και ποτέ δεν παραμένει μερικώς εφαρμοσμένο. Η `revertTproxy(cfg)` εκτελεί τις
αντίστροφες εντολές με αντίστροφη σειρά και αγνοεί τις αποτυχίες (ιδιοδύναμη — ασφαλής για
κλήση χωρίς προϋποθέσεις, π.χ. από την εκκαθάριση `repairMitm()` του AgentBridge).

Η `validateTproxyConfig(cfg)` εκτελείται πριν από οποιαδήποτε εντολή: οι θύρες πρέπει να είναι `1–65535`,
τα `mark`/`routeTable`/`bypassMark` πρέπει να είναι θετικοί ακέραιοι και το `bypassMark` πρέπει
να διαφέρει από το `mark` (αποτροπή βρόχου).

### Εντολές εφαρμογής (με τη σειρά)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Η αναίρεση τις διαγράφει με αντίστροφη σειρά: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> Η συνταγή βασίζεται στο **OUTPUT**, επειδή η περίπτωση χρήσης MITM αφορά _τοπική_ εξερχόμενη
> κίνηση (εφαρμογές στον ίδιο κεντρικό υπολογιστή), την οποία το TPROXY μόνο στο `PREROUTING` δεν
> βλέπει — το `PREROUTING` βλέπει μόνο προωθούμενη κίνηση. Η αλυσίδα `OUTPUT` επισημαίνει τις νέες
> τοπικές συνδέσεις, το `ip rule` τις αναδρομολογεί για τοπική παράδοση (`lo`) και, στη συνέχεια,
> το `PREROUTING` τις εκχωρεί στον διαφανή ακροατή.

## §8 Ρύθμιση παραμέτρων

Το αίτημα εκκίνησης (`POST /api/tools/agent-bridge/tproxy`) δέχεται τα ακόλουθα
πεδία, τα οποία επικυρώνονται από το `StartTproxyBodySchema` (`tproxy/route.ts`). Όλα είναι προαιρετικά
και, αν παραλειφθούν, χρησιμοποιούν τις προεπιλεγμένες τιμές τους:

| Πεδίο            | Τύπος              | Προεπιλογή | Σημειώσεις                                                                                                                                                  |
| ---------------- | ------------------ | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`      | Θύρα προορισμού TCP προς διαφανή υποκλοπή                                                                                                                   |
| **mark**         | int (≥1)           | `0x2333`   | Σήμανση firewall που ορίζεται στο `OUTPUT` και αντιστοιχίζεται από τα `ip rule` + `PREROUTING`                                                              |
| **onPort**       | int (1–65535)      | `8443`     | Θύρα στην οποία δεσμεύεται ο διαφανής ακροατής (**IP_TRANSPARENT**)                                                                                         |
| **routeTable**   | int (≥1)           | `233`      | Αναγνωριστικό πίνακα δρομολόγησης βάσει πολιτικής που περιέχει τη διαδρομή `local 0.0.0.0/0`                                                                |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`    | Η σήμανση socket παράκαμψης (**SO_MARK**) που ορίζει ο διακομιστής μεσολάβησης στις δικές του ανοδικές συνδέσεις· εξαιρείται στο `OUTPUT` (αποτροπή βρόχου) |
| **sudoPassword** | string             | —          | Μόνο για επιτραπέζια συστήματα χωρίς root: εξουσιοδοτεί την εγκατάσταση στο χώρο αποθήκευσης εμπιστοσύνης· αγνοείται όταν υπάρχει root                      |

Δεν υπάρχουν **μεταβλητές περιβάλλοντος** για το TPROXY — όλες οι ρυθμίσεις παραμέτρων παρέχονται μέσω του
σώματος POST ή των παραπάνω προεπιλογών.

## §9 Ενεργοποίηση από το Traffic Inspector

1. Ανοίξτε το **Traffic Inspector** (`/dashboard/tools/traffic-inspector`).
2. Στη γραμμή εργαλείων των λειτουργιών καταγραφής, βρείτε το κουμπί **"TPROXY Decrypt"** ⚠
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Αν είναι **απενεργοποιημένο** με την επεξήγηση "Η αποκρυπτογράφηση TPROXY απαιτεί Linux + root +
     το εγγενές πρόσθετο", το εγγενές πρόσθετο δεν είναι διαθέσιμο σε αυτόν τον κεντρικό υπολογιστή (όχι Linux,
     δεν υπάρχει αλυσίδα εργαλείων ή το πρόσθετο δεν έχει μεταγλωττιστεί). Δείτε [§2](#2-requirements) και [§3](#3-the-native-ip_transparent-addon).
3. Κάντε κλικ στο κουμπί. Καλεί το `POST /api/tools/agent-bridge/tproxy` μέσω της
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`), η οποία:
   δημιουργεί τη δυναμική CA, ανοίγει τον διαφανή ακροατή, εφαρμόζει τους κανόνες
   του τείχους προστασίας και εγκαθιστά τη CA στον χώρο αποθήκευσης αξιόπιστων πιστοποιητικών του λειτουργικού συστήματος.
4. Κατά την εκτέλεση, ο διακόπτης γίνεται πορτοκαλί και εμφανίζει τον αριθμό ενεργών υποκλοπών
   (`· <interceptCount>`). Τα αιτήματα που υποκλέπτονται εμφανίζονται στη λίστα αιτημάτων με
   `source: "tproxy"`.
5. Κάντε ξανά κλικ για διακοπή — το `DELETE /api/tools/agent-bridge/tproxy` μέσω της
   `stopTproxyCaptureMode()` κλείνει τον ακροατή, απεγκαθιστά τη CA και αναιρεί
   τους κανόνες του τείχους προστασίας.

Η κατάσταση της λειτουργίας καταγραφής (εκτελείται / διαθέσιμη / αριθμός υποκλοπών / θύρα ακροατή) προέρχεται
από το `GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` στο
`src/mitm/tproxy/captureManager.ts`). Μόνο **μία** συνεδρία TPROXY εκτελείται κάθε φορά —
η εκκίνηση δεύτερης απορρίπτεται με το μήνυμα "Η λειτουργία καταγραφής TPROXY εκτελείται ήδη".

## §10 Αντιμετώπιση προβλημάτων

### Ο διακόπτης είναι απενεργοποιημένος

Το εγγενές πρόσθετο δεν μπορεί να φορτωθεί. Επιβεβαιώστε ότι: βρίσκεστε σε Linux, έχετε μεταγλωττίσει το πρόσθετο
(`npm run build:native:tproxy`) και η διεργασία μπορεί να φορτώσει το `transparent.node`.
Η `isTransparentSocketAvailable()` ελέγχει τη διαθεσιμότητα του διακόπτη· το `GET /api/tools/agent-bridge/tproxy`
επιστρέφει `available: false` όταν λείπει το πρόσθετο.

### Δεν καταγράφεται τίποτα

- Επιβεβαιώστε ότι η διεργασία που υποκλέπτεται συνδέεται πράγματι στη ρυθμισμένη `dport`
  (προεπιλογή `443`).
- Επιβεβαιώστε ότι η διεργασία εμπιστεύεται τη δυναμική CA. Η CA εγκαθίσταται ως
  `omniroute-tproxy-ca.crt`· εφαρμογές με δικό τους χώρο αποθήκευσης αξιόπιστων πιστοποιητικών (Firefox/Chrome NSS)
  ενδέχεται να χρειάζονται την προσθήκη του πιστοποιητικού και εκεί.
- Εκτελέστε τον αυτοέλεγχο **Diagnose** του AgentBridge (δείτε
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) για ελέγχους αξιοπιστίας πιστοποιητικού / εύρυθμης
  λειτουργίας διακομιστή.

### Παρωχημένοι κανόνες τείχους προστασίας μετά από κατάρρευση

Η `revertTproxy()` είναι το ακριβές αντίστροφο της εφαρμογής και είναι ιδιοδύναμη. Η διακοπή της
λειτουργίας αναιρεί τους κανόνες· αν το OmniRoute τερματίστηκε κατά τη διάρκεια μιας συνεδρίας, χρησιμοποιήστε την ενέργεια
**Repair** του AgentBridge (`POST /api/tools/agent-bridge/repair`) για να αναιρέσετε την ορφανή κατάσταση
του συστήματος (παραποίηση DNS, ριζική CA, διακομιστής μεσολάβησης συστήματος). Οι κανόνες `mangle` του TPROXY και η διαδρομή επίσης
εκκαθαρίζονται αυτόματα κατά την επανεκκίνηση.

### Άπειρος βρόχος / ο διακομιστής μεσολάβησης υποκλέπτει τη δική του προώθηση

Αυτή είναι η περίπτωση αποτροπής βρόχου. Επιβεβαιώστε ότι το `bypassMark` διαφέρει από το `mark` (η επικύρωση
το επιβάλλει) και ότι η προώθηση χρησιμοποιεί τη `connectMarked` (όπως πράγματι συμβαίνει στη `realForward`).
Δείτε [§5 Αποτροπή βρόχου](#anti-loop-so_mark).
