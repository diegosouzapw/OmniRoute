Το παρόν έγγραφο περιγράφει τη βάση προσαρμοστικής δρομολόγησης βάσει ανατροφοδότησης που προστέθηκε στο
OmniRoute. Είναι σκόπιμα περιορισμένη: εισάγει ένα κανάλι αποτελεσμάτων
δρομολόγησης με τύπους, ένα διαδικτυακό σήμα ποιότητας που τροφοδοτεί τον υπάρχοντα βαθμολογητή auto-combo, έναν
προαιρετικό εξαγωγέα OpenTelemetry και ένα endpoint επεξηγησιμότητας. **Δεν**
αντικαθιστά την υπάρχουσα στοίβα ανθεκτικότητας (circuit breaker, χρονικό διάστημα αναμονής σύνδεσης,
αποκλεισμός μοντέλου, πίνακας υγείας, autopilot) — τη συμπληρώνει.

## 1. Αρχιτεκτονικό πλαίσιο

Το OmniRoute είναι ένα επίπεδο δεδομένων με μια **κρίσιμη διαδρομή αιτημάτων** και ένα **επίπεδο ελέγχου/ευφυΐας**.
Η κρίσιμη διαδρομή πρέπει να παραμένει γρήγορη, αποδοτική ως προς τη μνήμη, ασύγχρονη, ανθεκτική και
προβλέψιμη. Η αξιολόγηση, η βαθμολόγηση ποιότητας, τα πειράματα και η ιστορική ανάλυση ανήκουν
στο επίπεδο ελέγχου.

```
Πράκτορας AI / IDE
      │
      ▼
┌─────────────────────┐
│    OmniRoute        │   επίπεδο δεδομένων (γρήγορο, σύγχρονο, στη μνήμη)
│ δρομολόγηση /       │
│ εφεδρική μετάπτωση  │
│ υγεία / περιορισμοί │
│ cache / streaming   │
└──────────┬──────────┘
           │ RoutingEvent (fire-and-forget, ~0.2µs)
           ▼
┌─────────────────────┐
│ Προορισμοί          │   επίπεδο ελέγχου (ασύγχρονο, βέλτιστης προσπάθειας)
│ ανατροφοδότησης     │
│ παρακολούθηση       │
│ ποιότητας           │
│ εξαγωγέας OTel      │
│ χώρος επεξηγήσεων   │
└──────────┬──────────┘
           ▼  βαθμολογία ποιότητας
      βαθμολογητής auto-combo
```

### Τι υπήρχε ήδη (ελέγχθηκε, δεν αναπαράχθηκε)

| Έννοια                                        | Υπάρχουσα υλοποίηση                                                                                                            |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Διαθεσιμότητα (μπορούμε να στείλουμε κίνηση;) | Circuit breaker (CLOSED/DEGRADED/OPEN/HALF_OPEN, με διατήρηση σε DB), χρονικό διάστημα αναμονής σύνδεσης, αποκλεισμός μοντέλου |
| Αναφορά υγείας                                | `providerHealthMatrix.ts`, `providerHealthAutopilot.ts`                                                                        |
| Σκιώδης κίνηση                                | `open-sse/services/combo/shadowRouting.ts`                                                                                     |
| Περιορισμοί                                   | `src/lib/guardrails/` (hooks πριν/μετά)                                                                                        |
| Cache ακριβούς αντιστοίχισης                  | `src/lib/semanticCache.ts` (βάσει υπογραφής)                                                                                   |
| Αξιολογητές / δρομολόγηση βάσει αξιολόγησης   | `src/lib/evals/`, `open-sse/services/evalRouting.ts`                                                                           |
| Επεξηγησιμότητα αποφάσεων combo               | `open-sse/services/combo/decisionTrace.ts`                                                                                     |
| Συμβάντα πραγματικού χρόνου του dashboard     | `src/lib/events/eventBus.ts` (κανάλι ειδοποιήσεων UI, payloads τύπου `unknown`, ιστορικό 100 καταχωρίσεων)                     |

Το επίπεδο συμβάντων δρομολόγησης **δεν** αποτελεί εκ νέου υλοποίηση του `eventBus`: αυτός ο δίαυλος είναι
το κανάλι ειδοποιήσεων πραγματικού χρόνου του dashboard (πληκτρολογημένα _ονόματα συμβάντων_, αδιαφανή
payloads, καταναλωτές UI). Το `RoutingEvent` είναι μια δομή _αποτελέσματος_ με τύπους
(καθυστέρηση/tokens/κόστος/αποτέλεσμα/αιτία-τερματισμού), η οποία καταναλώνεται από τους
προορισμούς ανατροφοδότησης του επιπέδου ελέγχου (παρακολούθηση ποιότητας, εξαγωγέας OTel, χώρος επεξηγήσεων).

### Τι έλειπε (προστέθηκε εδώ)

1. Ένα **συμβάν αποτελέσματος δρομολόγησης με τύπους + αφαίρεση προορισμού** (`RoutingEvent` /
   `RoutingEventSink`). Το `decisionTrace` περιορίζεται στα combo και λειτουργεί μόνο στη μνήμη·
   τα `comboMetrics` είναι αθροιστικοί μετρητές· τα `call_logs` αποτελούν ανεπεξέργαστη ασύγχρονη μόνιμη αποθήκευση.
   Κανένα από αυτά δεν είναι ένα κανάλι αποτελεσμάτων με τύπους και βάσει προορισμών, στο οποίο μπορούν να εγγραφούν
   μια υπηρεσία παρακολούθησης ποιότητας, ένας εξαγωγέας OTel ή ένας αξιολογητής τύπου Future-AGI.
2. Ένα **διαδικτυακό σήμα ποιότητας** (EWMA) για την ποιότητα εξόδου — προηγουμένως, ο βαθμολογητής
   προσέγγιζε έμμεσα την «ποιότητα» μόνο μέσω της στατικής καταλληλότητας εργασίας και των ποσοστών επιτυχίας αξιολόγησης κατόπιν ρητής ενεργοποίησης.
3. Ένας **προαιρετικός εξαγωγέας OTel χωρίς εξαρτήσεις**, ο οποίος χρησιμοποιεί τις σημασιολογικές συμβάσεις GenAI.
4. Ένα **endpoint επεξηγησιμότητας** που επιστρέφει τις πραγματικές αποφάσεις δρομολόγησης + την κατάσταση ποιότητας.

## 2. Συμβάντα δρομολόγησης (θεμέλιο ανάδρασης)

Αρχεία: `open-sse/services/routing/events.ts`, `.../index.ts`

Ένα `RoutingEvent` μεταφέρει μόνο μεταδεδομένα δρομολόγησης:

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ...
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // ένωση με επιτρεπόμενες τιμές
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

Το `RoutingEventSink` είναι ένα trait τύπου `Send+Sync` στην TypeScript:

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // πρέπει να είναι O(1), χωρίς σύγχρονο I/O
}
```

Η κρίσιμη διαδρομή καλεί το `emitRoutingEvent(event)` μία φορά ανά ολοκληρωμένο αίτημα
(στο callback ολοκλήρωσης της ροής, στη διαδρομή επιτυχίας χωρίς ροή και στη
διαδρομή αποτυχίας για αποκρίσεις 200 με εσφαλμένη μορφή στο `handleChatCore`). Η αποστολή πραγματοποιείται ως σύγχρονο fan-out
προς τα καταχωρισμένα sinks, αλλά κάθε sink απλώς προσθέτει σε ουρά/ενημερώνει την κατάσταση στη μνήμη. **Δεν
πραγματοποιούνται σύγχρονες εγγραφές σε βάση δεδομένων ούτε δικτυακό I/O στην κρίσιμη διαδρομή.**

Προεπιλεγμένα sinks:

- `MemoryRoutingEventStore` — περιορισμένο κυκλικό buffer (500), με τα νεότερα πρώτα, για το
  endpoint επεξήγησης.
- Καταναλωτής `QualityTracker` — ενημερώνει την εκτίμηση ποιότητας EWMA.
- `OtlpHttpsEventSink` — προαιρετικό, ενεργοποιείται μόνο όταν έχει οριστεί το `OMNIROUTE_OTEL_ENDPOINT`
  (ή το `OTEL_EXPORTER_OTLP_ENDPOINT`).

### Μετρημένο επιπλέον κόστος (ειλικρινής σύγκριση)

`npm run bench:routing-events` σε αυτόν τον σταθμό εργασίας (100k επαναλήψεις· οι λειτουργίες
κάτω του µs μετρώνται ως συγκεντρωτικά µs/λειτουργία, επειδή τα εκατοστημόρια ανά λειτουργία βρίσκονται κάτω
από την ανάλυση του χρονομέτρου `performance.now()`):

| Σενάριο                                       | µs/λειτουργία | λειτουργίες/s |
| --------------------------------------------- | ------------- | ------------- |
| γραμμή βάσης (μόνο βαθμολόγηση)               | ~0.045        | ~22 M         |
| γραμμή βάσης + RoutingEvent (2 sinks)         | ~0.168        | ~5.9 M        |
| γραμμή βάσης + συμβάν + εισαγωγή σε ουρά OTel | ~0.163        | ~6.1 M        |
| ταυτόχρονα (8 παρεμβαλλόμενες ριπές)          | ~0.18         | —             |

Η διαφορά της αποστολής συμβάντων σε σχέση με τη βαθμολόγηση αναφοράς είναι ~0.12 µs/αίτημα· το sink OTel
απλώς προσθέτει σε ουρά (προσθήκη σε buffer O(1)), χωρίς να προσθέτει κάτι μετρήσιμο. Αυτοί οι αριθμοί είναι
συγκεκριμένοι για το μηχάνημα και σχετικοί — δεν αποτελούν εγγύηση για περιβάλλον παραγωγής. Η τιμή "~0.2 µs"
της v1 ήταν μια συγκεντρωτική εκτίμηση· αυτή η μεθοδολογία διαχωρίζει τη βαθμολόγηση αναφοράς
από το κόστος αποστολής συμβάντων.

## 3. Σήμα ποιότητας (κατάσταση παρόχου βάσει ανάδρασης)

Αρχεία: `open-sse/services/routing/quality.ts`

Η v2 διαχωρίζει τη **λειτουργική** από τη **σημασιολογική** ποιότητα:

- **Λειτουργική** — προκύπτει από την κρίσιμη διαδρομή δρομολόγησης (HTTP 4xx/5xx, αποτυχίες
  σύνδεσης, 429, αποκρίσεις με εσφαλμένη μορφή, διακοπές ροής, `finish_reason=length`,
  επιτυχίες με μηδενική έξοδο, EWMA καθυστέρησης/TTFT). Μια απόκριση 200 ΔΕΝ αντιμετωπίζεται ως ένδειξη σημασιολογικής
  ποιότητας.
- **Σημασιολογική** — η πραγματική αξία της παραγόμενης εξόδου. Παράγεται ΜΟΝΟ από
  έναν αξιολογητή μέσω του `setSemanticQuality()`. Είναι `null` μέχρι να την παράσχει κάποιος και
  δεν διαρρέει ποτέ στη λειτουργική βαθμολογία.

Κατάσταση ανά (πάροχο, μοντέλο) (EWMA + περιορισμένοι μετρητές):

- `successEwma` — EWMA (α=0.2) της επιτυχίας αποτελέσματος.
- `latencyEwma` / `ttftEwma` — EWMA της καθυστέρησης (α=0.1).
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`.
- `recencyMs` — πόσο πρόσφατα παρατηρήθηκε τελευταία φορά το μοντέλο.

### Επίγνωση εμπιστοσύνης / πλήθους δειγμάτων

`confidence = clamp01(samples / 50)`, και η βαθμολογία που επιστρέφεται στον μηχανισμό βαθμολόγησης
συνδυάζεται προς το ουδέτερο μέσο σημείο:

```
score = 0.5 + confidence * (operational - 0.5)
```

Συνέπειες (επαληθευμένες με δοκιμές):

- Ένας πάροχος χωρίς ιστορικό (0 δείγματα) βαθμολογείται με **0.5** — δεν τιμωρείται άδικα, αλλά
  δεν μπορεί να υπερισχύσει έναντι ενός παρόχου με χιλιάδες αξιόπιστες παρατηρήσεις.
- Ένας πάροχος με 7 τυχερές επιτυχίες έλκεται προς το 0.5 (δεν υπερισχύει ποτέ λόγω
  αισιόδοξης αρχικοποίησης).
- Ένας πάροχος με 50+ δείγματα συγκλίνει στην πραγματική λειτουργική βαθμολογία του.
- Η υποβάθμιση και η ανάκαμψη είναι σταδιακές (EWMA) και μία μεμονωμένη αποτυχία δεν
  καταστρέφει έναν υγιή πάροχο.

Το `ProviderQuality` εκθέτει τα `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }`.

Αυτό τροφοδοτεί τον μηχανισμό βαθμολόγησης auto-combo ως παράγοντα βαθμολόγησης `quality`:

- `ScoringFactors.quality` / `ScoringWeights.quality` στο
  `open-sse/services/autoCombo/scoring.ts`.
- `DEFAULT_WEIGHTS`: `health` 0.1905 → 0.1605, `quality` 0.03. Το άθροισμα παραμένει 1.0.
- Το `buildAutoCandidates` συμπληρώνει το `candidate.quality` από τον tracker· οι υποψήφιοι
  χωρίς δεδομένα λαμβάνουν από προεπιλογή την ουδέτερη τιμή **0.5** (ένας υποψήφιος χωρίς ιστορικό ούτε ενισχύεται ούτε
  τιμωρείται).

Ο κλειστός βρόχος:

```
RoutingEvent → QualityTracker → getQualityScore → παράγοντας ποιότητας auto-combo
      ↑                                                    │
      └────── αποτέλεσμα αιτήματος (handleChatCore) ←──────┘
```

### Αυστηρός αποκλεισμός έναντι ήπιας ποινής

Το σήμα ποιότητας αποτελεί μόνο μια **ήπια προσαρμοστική προτίμηση**. Ο αυστηρός αποκλεισμός παραμένει
στην υπάρχουσα στοίβα ανθεκτικότητας: circuit breaker OPEN, εξαντλημένο όριο χρήσης,
αποτυχία ελέγχου ταυτότητας, αποκλεισμός μοντέλου — κανένα από αυτά δεν επηρεάζεται από τη βαθμολογία ποιότητας.
Ένας πάροχος του οποίου η βαθμολογία ποιότητας μειώνεται προσωρινά λαμβάνει χαμηλότερη προτεραιότητα, αλλά δεν
απενεργοποιείται ποτέ πλήρως.

## 3b. Κανονικός χρονισμός ροής (TTFT / ITL)

Αρχεία: `open-sse/utils/streamTiming.ts`

Η `createStreamTiming()` είναι το μοναδικό σημείο ενοργάνωσης για τη διαδρομή ροής,
ενσωματωμένο στη `createSSEStream` (`open-sse/utils/stream.ts`):

- `markByte()` — λήψη του πρώτου τμήματος από την upstream υπηρεσία.
- `markForward()` — προώθηση του πρώτου τμήματος στον πελάτη (χρησιμοποιείται για το TTFT).
- `markInterrupted()` — λήξη χρονικού ορίου/ακύρωση/σφάλμα ροής πριν από την ομαλή ολοκλήρωση.
- `ttft()` = καθυστέρηση του πρώτου προωθημένου τμήματος SSE. **Αυτό ΔΕΝ είναι TTFT σε επίπεδο token** —
  ένα μεμονωμένο τμήμα SSE μπορεί να περιέχει μηδέν/ένα/πολλά token. Τεκμηριώνεται με ακρίβεια.
- `avgItlMs()` = μέσο χρονικό διάστημα μεταξύ τμημάτων (μια προσεγγιστική μέτρηση της ITL βάσει καθυστέρησης τμημάτων).

Τα TTFT/ITL και η κατάσταση διακοπής μεταφέρονται στο `RoutingEvent` (`ttftMs`, `itlMs`) και
εξάγονται ως χαρακτηριστικά span GenAI/OmniRoute από το sink OTel.

## 4. Παρατηρησιμότητα OpenTelemetry / GenAI

Αρχεία: `open-sse/services/routing/otel.ts`

- Εξαγωγέας OTLP/HTTP JSON χωρίς εξαρτήσεις (χρησιμοποιεί το καθολικό `fetch`, χωρίς
  SDK `@opentelemetry/*`).
- Τα span ακολουθούν τις σημασιολογικές συμβάσεις GenAI (`gen_ai.provider.name`,
  `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`,
  `gen_ai.completion.finish_reason`, `gen_ai.system`), μαζί με χαρακτηριστικά
  δρομολόγησης του OmniRoute (αποτέλεσμα, κατάσταση, ttft, επαναλήψεις, εναλλακτική διαδρομή).
- Η `record()` προσθέτει στοιχεία μόνο σε ένα οριοθετημένο buffer (O(1))· ένας χρονοδιακόπτης
  παρασκηνίου πραγματοποιεί ασύγχρονα εκκαθάριση μέσω `POST {endpoint}/v1/traces`. Σε συνθήκες
  υπερφόρτωσης, τα παλαιότερα συμβάντα απορρίπτονται (μετρητής `dropped`) — δεν ασκείται ποτέ
  αντίθλιψη στο επίπεδο δεδομένων.
- **Απενεργοποιημένο εκτός εάν έχει ρυθμιστεί.** Πρέπει να έχει οριστεί το
  `OMNIROUTE_OTEL_ENDPOINT` (ή το `OTEL_EXPORTER_OTLP_ENDPOINT`)· διαφορετικά, το sink δεν
  καταχωρίζεται και δεν εκτελείται καθόλου κώδικας OTel.

## 5. Επεξηγησιμότητα

- Το `GET /v1/explain/routing` επιστρέφει τα πρόσφατα `RoutingEvent` (τις πραγματικές
  αποφάσεις, με τις νεότερες πρώτες) και το στιγμιότυπο ποιότητας ανά πάροχο/μοντέλο.
- Ο έλεγχος ταυτότητας αντικατοπτρίζει το `/v1/combos` (κλειδί API Bearer ή συνεδρία πίνακα
  ελέγχου· ανώνυμη πρόσβαση σε τοπικές αναπτύξεις ενός χρήστη με `REQUIRE_API_KEY=false`).
- Τα ίχνη ανά κλήση σε επίπεδο combo παραμένουν διαθέσιμα μέσω του υπάρχοντος
  `decisionTrace.ts` (κεφαλίδα `X-OmniRoute-Combo-Trace`).
- Ασφάλεια: τα συμβάντα περιέχουν μόνο μεταδεδομένα δρομολόγησης, ποτέ prompt/σώματα/διαπιστευτήρια.

## 6. Ενσωμάτωση επιπέδου αξιολόγησης (ετοιμότητα για το Future AGI)

Το OmniRoute αντιμετωπίζει το Future AGI (ή οποιονδήποτε αξιολογητή) ως **πιθανό
backend νοημοσύνης/αξιολόγησης και όχι ως εξάρτηση**. Τα σημεία διασύνδεσης:

- Ένα `RoutingEventSink` μπορεί να προωθεί ασύγχρονα συμβάντα σε έναν αξιολογητή.
- Το `MemoryRoutingEventStore` μαζί με το στιγμιότυπο ποιότητας παρέχουν στον αξιολογητή την ακατέργαστη
  ροή αποφάσεων.
- Ένας μελλοντικός `Evaluator` (ντετερμινιστικός, τοπικός κριτής, HTTP, WASM) θα καταναλώνει
  συμβάντα/ίχνη και θα επιστρέφει ένα `QualityScore`, το οποίο τροφοδοτεί την ίδια διαδρομή
  `getQualityScore`/συντελεστή ποιότητας.
- Η υπάρχουσα δρομολόγηση βάσει αξιολόγησης (`open-sse/services/evalRouting.ts`) ήδη
  αναδιατάσσει τους προορισμούς combo βάσει των ποσοστών επιτυχίας `eval_runs`, όταν είναι ενεργοποιημένη.

Καμία αξιολόγηση δεν εκτελείται συγχρονισμένα στη διαδρομή του αιτήματος και η πύλη λειτουργεί
πλήρως χωρίς την παρουσία αξιολογητή.

## 7. Τελική αρχιτεκτονική ανασκόπηση

1. **Τι παραμένει στη συγχρονισμένη κρίσιμη διαδρομή;** Δρομολόγηση/βαθμολόγηση, προκαταρκτικοί
   έλεγχοι προστατευτικών μηχανισμών, αναζήτηση στην cache και ένα fan-out `emitRoutingEvent`
   (~0.12 µs πάνω από τη βασική βαθμολόγηση) προς sink στη μνήμη.
2. **Τι μεταφέρθηκε σε ασύγχρονη επεξεργασία;** Εξαγωγή OTel (χρονοδιακόπτης + fetch),
   αποθήκευση `call_logs`/χρήσης, εγγραφές σημασιολογικής cache· η ποιότητα διατηρείται στη μνήμη
   και είναι O(1) (δεν απαιτείται ασύγχρονη επεξεργασία).
3. **Πώς μετατρέπεται ένα αποτέλεσμα δρομολόγησης σε ανάδραση;** Η `handleChatCore` εκπέμπει ένα
   `RoutingEvent` → το `QualityTracker` ενημερώνει την κατάσταση EWMA → η `getQualityScore`
   τροφοδοτεί τον συντελεστή `quality` του αυτόματου combo.
4. **Πώς επηρεάζει η ποιότητα τη μελλοντική δρομολόγηση;** Μια χαμηλή βαθμολογία ποιότητας μειώνει
   τη σταθμισμένη βαθμολογία αυτού του παρόχου/μοντέλου στη `scoreAutoTargets`, επομένως τα
   υποβαθμισμένα μοντέλα λαμβάνουν σταδιακά χαμηλότερη προτεραιότητα και ανακάμπτουν καθώς
   βελτιώνεται ο EWMA τους.
5. **Πώς μπορεί να ενσωματωθεί το Future AGI χωρίς να καταστεί εξάρτηση;** Μέσω της διεπαφής
   `RoutingEventSink` / ενός μελλοντικού προσαρμογέα `Evaluator` — χωρίς ενσωματωμένη εξάρτηση
   στον κώδικα.
6. **Τι συμβαίνει όταν ο αξιολογητής δεν είναι διαθέσιμος;** Η δρομολόγηση δεν επηρεάζεται·
   η ποιότητα επιστρέφει στην ουδέτερη τιμή (1.0) για μοντέλα χωρίς παρατηρούμενο σήμα.
7. **Τι συμβαίνει όταν η τηλεμετρία δεν είναι διαθέσιμη;** Το sink OTel απλώς δεν
   καταχωρίζεται· το υπόλοιπο επίπεδο δρομολόγησης λειτουργεί χωρίς αλλαγές.
8. **Τι συμβαίνει υπό υπερφόρτωση;** Το buffer OTel απορρίπτει τα παλαιότερα συμβάντα· η ποιότητα
   και το ring buffer είναι οριοθετημένα εκ κατασκευής· δεν υπάρχει αντίθλιψη.
9. **Πώς ανακάμπτει η κατάσταση ενός παρόχου μετά από υποβάθμιση;** Ο EWMA συγκλίνει εκ νέου καθώς
   συσσωρεύονται επιτυχίες· η προθέρμανση διατηρεί ουδέτερα τα νέα μοντέλα· ο circuit breaker
   ανακάμπτει ανεξάρτητα μέσω δοκιμών HALF_OPEN.
10. **Ποια προτεινόμενα χαρακτηριστικά ΔΕΝ υλοποιήθηκαν σκόπιμα και γιατί;**
    - Σκιώδης κίνηση / πειράματα — έχουν ήδη υλοποιηθεί
      (`combo/shadowRouting.ts`)· δεν ανακατασκευάστηκαν.
    - Προστατευτικοί μηχανισμοί — έχουν ήδη υλοποιηθεί (`src/lib/guardrails/`)· δεν αντιγράφηκαν.
    - Σημασιολογική cache — έχει ήδη υλοποιηθεί (`src/lib/semanticCache.ts`)· δεν
      αντιγράφηκε.
    - Μια πλήρης πλατφόρμα διαχείρισης πειραμάτων, εργαλεία συνόλων δεδομένων, πλατφόρμα
      βελτιστοποίησης prompt, διανυσματική βάση δεδομένων ή υποχρεωτική εξωτερική υποδομή OTel —
      βρίσκονται εκτός του πεδίου εφαρμογής ενός λιτού επιπέδου δεδομένων.
    - Ένα struct `RoutingEvent` σε Rust — το επίπεδο δεδομένων είναι σε TypeScript· ο τύπος TS
      είναι το προσαρμοσμένο ισοδύναμο.

## 8. Αναφορά ρυθμίσεων

| Μεταβλητή                     | Προεπιλογή  | Επίδραση                                                                               |
| ----------------------------- | ----------- | -------------------------------------------------------------------------------------- |
| `OMNIROUTE_OTEL_ENDPOINT`     | μη ορισμένη | Όταν οριστεί, ενεργοποιεί τον εξαγωγέα ιχνών OTLP/HTTP (π.χ. `http://collector:4318`). |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | μη ορισμένη | Εναλλακτικό ψευδώνυμο για το τελικό σημείο OTLP.                                       |
| `OTEL_SERVICE_NAME`           | `omniroute` | Ιδιότητα πόρου `service.name`.                                                         |

## 9. Δοκιμές

- `tests/unit/routing-events.test.ts` — κανονικοποίηση συμβάντων, ταξινόμηση
  κατάστασης, περιορισμένος κυκλικός buffer, διανομή σε sink + απομόνωση.
- `tests/unit/routing-quality.test.ts` — προθέρμανση EWMA, ανάκαμψη από αποτυχία/επιτυχία,
  ποινές ανωμαλιών, χειρισμός του 429 ως παροδικού σφάλματος, στιγμιότυπο, επαναφορά.
- `tests/unit/routing-scoring-quality.test.ts` — ακεραιότητα βαρών, ουδέτερη
  προεπιλογή, κατάταξη βάσει συντελεστή ποιότητας.
- `tests/unit/routing-otel.test.ts` — έλεγχος ενεργοποίησης, ωφέλιμο φορτίο span GenAI, ασύγχρονη
  εκκαθάριση, απόρριψη υπό υπερφόρτωση.
- `tests/unit/routing-events-concurrency.test.ts` — χιλιάδες συμβάντα, περιορισμένο
  μέγεθος κυκλικού buffer, απομόνωση sink που προκαλεί εξαιρέσεις, εναλλασσόμενες ασύγχρονες ριπές,
  επαναφορά κατά τη διάρκεια εισαγωγών.
- `tests/unit/routing-adaptive-e2e.test.ts` — ντετερμινιστικός βρόχος από άκρο σε άκρο μέσω
  του πραγματικού βαθμολογητή `scoreAutoTargets`: υγιής → υποβάθμιση → ανάκαμψη → στιγμιαία διαταραχή, καθώς και
  σενάρια ψυχρής εκκίνησης και τυχερού παρόχου σε ψυχρή εκκίνηση.
- `tests/unit/stream-timing.test.ts` — TTFT (πρώτο προωθημένο τμήμα), ITL,
  πρώτο byte έναντι πρώτης προώθησης, διακοπή, ασφάλεια έναντι κακοσχηματισμένων/κενών τμημάτων.
