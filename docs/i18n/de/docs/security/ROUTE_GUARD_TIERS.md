## Übersicht

Alle Routen der OmniRoute-Verwaltungs-API sind einer von drei Schutzstufen zugeordnet. Die Klassifizierung ist statisch, wird in `src/server/authz/routeGuard.ts` definiert und ausgewertet, bevor ein anderer Authentifizierungszweig ausgeführt wird.

## Stufen

### Stufe 1 — LOCAL_ONLY

**Erzwungen durch:** `isLocalOnlyPath(path)` → Prüfung auf Loopback-Host  
**Umgehung:** Standardmäßig keine. Eng begrenzte Ausnahme für Pfade in `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, wenn die Anfrage einen gültigen API-Schlüssel mit dem Geltungsbereich `manage` enthält (siehe [Ausnahme für den Geltungsbereich „manage“](#manage-scope-carve-out)).

Diese Routen starten untergeordnete Prozesse oder führen Laufzeitcode aus. Würden sie für Nicht-Loopback-Datenverkehr zugänglich gemacht, könnte ein Angreifer, der ein gültiges JWT erlangt hat (z. B. über einen Cloudflared-/Ngrok-Tunnel), das Starten von Prozessen auslösen — eine bekannte CVE-Klasse ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Was GHSA-fhh6-4qxv-rpqj ist (die Angriffsklasse):** Ein Verwaltungs-/Agent-Server stellt einen Endpunkt bereit, der einen Unterprozess startet (`npm install`, `node`, einen Browser, einen Proxy, `git`, `tar`, …). Wenn dieser Endpunkt von außerhalb des Hosts erreichbar ist — weil der Betreiber OmniRoute hinter einem nginx-/Cloudflare-/Tailscale-Tunnel platziert hat und ein JWT offengelegt wurde oder die Authentifizierung falsch konfiguriert war — macht der Angreifer aus „eine API aufrufen“ ein „einen Befehl auf dem Host ausführen“ (Remote-Codeausführung). OmniRoute verhindert dies, indem es für jede Route, die Prozesse starten kann, **bedingungslos und vor jeder Authentifizierungsprüfung eine Prüfung auf einen Loopback-Host erzwingt**: Ein offengelegtes Token kann die Prozessstartfunktion selbst über einen Tunnel nicht erreichen.

**Die vollständige LOCAL_ONLY-Menge.** Die maßgebliche Quelle sind `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` in `src/server/authz/routeGuard.ts`; die nachstehende Tabelle gibt den aktuellen Stand wieder. Die Prüfung `check-route-guard-membership` erfasst jede `route.ts` unter den Präfixen, die Prozesse starten können, und lässt die CI fehlschlagen, wenn eine davon nicht als ausschließlich lokal klassifiziert ist.

#### Ausnahme für den manage-Scope

Eine Teilmenge der LOCAL_ONLY-Pfade DARF auch von Nicht-Loopback-Adressen aus aufgerufen werden, wenn und
nur wenn die Anfrage einen `Authorization: Bearer <api-key>`-Header enthält, dessen
Metadaten den Scope `manage` (oder `admin`) umfassen. Die Ausnahme wird
explizit pro Pfad über `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` aktiviert, sodass
für jeden neuen LOCAL_ONLY-Pfad standardmäßig weiterhin ausschließlich Loopback-Zugriff zulässig ist. Nicht authentifizierte
Anfragen und Anfragen mit Schlüsseln ohne manage-Scope werden weiterhin mit
`403 LOCAL_ONLY` abgewiesen.

Derzeit ist `/api/mcp/` das einzige Präfix, für das eine Ausnahme möglich ist. `/api/cli-tools/runtime/` und
`/api/services/` sind bewusst ausgeschlossen, da sie beliebige
Unterprozesse (`npm install`, `node`) starten können. Genau diese CVE-Klasse soll
die LOCAL_ONLY-Stufe verhindern.

**#7895 — enger Scope `mcp:connect`:** Die Ausnahme für `/api/mcp/` akzeptiert AUCH
einen Bearer-Schlüssel mit dem engen Scope `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), der über
`hasMcpConnectOrManageScope()` in `src/server/authz/policies/management.ts`
geprüft wird. Dies ist AUSSCHLIESSLICH auf `/api/mcp/` beschränkt — `mcp:connect` gewährt keinerlei Berechtigungen für andere
Verwaltungsrouten (einschließlich aller anderen LOCAL_ONLY-Ausnahmepräfixe, falls jemals eines
hinzugefügt werden sollte), und der Scope ist bewusst nicht in
`MANAGEMENT_API_KEY_SCOPES` enthalten. Ein Schlüssel mit `manage`/`admin` erfüllt die
Ausnahme weiterhin genau wie zuvor; `mcp:connect` ist eine Alternative mit geringeren Berechtigungen
für entfernte, ausschließlich MCP nutzende Aufrufer, die keinen umfassenden Verwaltungszugriff benötigen sollten.

| Anfrage                                            | Pfad                       | Ergebnis                     |
| -------------------------------------------------- | -------------------------- | ---------------------------- |
| Nicht-Loopback, kein Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY               |
| Nicht-Loopback, Bearer mit Scope `manage`          | `/api/mcp/*`               | Zulassen                     |
| Nicht-Loopback, Bearer mit Scope `mcp:connect`     | `/api/mcp/*`               | Zulassen                     |
| Nicht-Loopback, Bearer ohne `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY               |
| Nicht-Loopback, Bearer mit Scope `mcp:connect`     | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY               |
| Nicht-Loopback, Bearer mit Scope `manage`          | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY               |
| Loopback, beliebiger/kein Bearer                   | beliebiger LOCAL_ONLY      | Zulassen (Prüfung bestanden) |

#### Hinweise für Betreiber und Auditierung

Wenn Sie OmniRoute hinter einem Reverse-Proxy oder Tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) betreiben, schützt die Loopback-Prüfung weiterhin die oben genannten
Routen, die Prozesse starten können — eine Anfrage, deren Clientadresse keine Loopback-Adresse ist, wird
`403 LOCAL_ONLY` **abgewiesen, bevor die Authentifizierung ausgeführt wird**, sodass selbst ein kompromittiertes JWT keinen Prozessstart auslösen kann. Zwei
Verantwortlichkeiten verbleiben beim Betreiber:

- **„Beheben“ Sie einen 403-Fehler nicht, indem Sie die Client-IP als Loopback-Adresse fälschen.** Das Setzen von
  `X-Forwarded-For: 127.0.0.1` oder ein Proxy, der die Quelladresse in eine
  Loopback-Adresse umschreibt, öffnet genau die RCE-Klasse erneut, die diese Stufe verhindert. Stellen Sie das
  Dashboard/die API über den Proxy bereit — niemals die Routen, die Prozesse starten können.
- **Halten Sie die Ausnahme für den manage-Scope minimal.** Nur für `/api/mcp/` ist eine Ausnahme möglich, und
  nur mit einem API-Schlüssel mit `manage`-Scope. Die `SPAWN_CAPABLE_PREFIXES` können niemals zur
  Ausnahmeliste hinzugefügt werden — das zod-Schema weist sie ab und
  `isLocalOnlyBypassableByManageScope` verweigert sie zur Laufzeit (mehrschichtige Absicherung),
  was das Dashboard mit „kann nicht umgehbar gemacht werden“ meint. Routen mit dynamischen Segmenten
  und statischen Pfaden unter `/api/providers/`, die Prozesse starten können (z. B. `/login`,
  `/refresh-cursor`), werden durch die auf regulären Ausdrücken basierenden Begleiter
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` in
  `src/shared/constants/spawnCapablePrefixes.ts` abgedeckt, nicht durch das flache
  Array `SPAWN_CAPABLE_PREFIXES` — das flache Array müsste das gesamte Präfix
  `/api/providers/` abdecken, um sie zu erfassen, wodurch ein Routenbaum zu weit gefasst würde,
  den entfernte Dashboards berechtigterweise für CRUD-Operationen an Providern verwenden.

**Zugriffsauditierung** — um zu überprüfen, dass keine externen Zugriffe diese Routen erreichen:

- Öffnen Sie das **Autorisierungsinventar** unter `/dashboard/settings/security`: Es zeigt die
  aktuelle LOCAL_ONLY-Präfixliste, die Präfixe, für die Ausnahmen möglich sind, sowie die zur Kompilierzeit festgelegte
  Gruppe der Routen, die Prozesse starten können („kann nicht umgehbar gemacht werden“).
- Durchsuchen Sie die Reverse-Proxy-/Zugriffsprotokolle nach den oben genannten Präfixen in Verbindung mit einer
  Nicht-Loopback-Clientadresse. Jeder solche Treffer, der `200` statt
  `403 LOCAL_ONLY` zurückgegeben hat, bedeutet, dass der Proxy die tatsächliche Client-IP verbirgt — korrigieren Sie den Proxy.
- Ein `403 LOCAL_ONLY` in den OmniRoute-Protokollen für einen dieser Pfade bedeutet, dass der Schutz
  wie vorgesehen funktioniert, und ist kein Fehler, der unterdrückt werden sollte.

### Stufe 2 — ALWAYS_PROTECTED

**Erzwungen durch:** `isAlwaysProtectedPath(path)` → Umgehung durch `requireLogin=false` überspringen
**Umgehung:** Keine bei `requireLogin=false`; JWT ist immer erforderlich

Diese Routen führen destruktive oder unumkehrbare Aktionen aus. Würden sie in einer Installation
„ohne Passwort“ zugelassen, könnte jeder im selben LAN die Datenbank löschen oder den
Serverprozess beenden.

| Pfad                                      | Grund                                                                                    |
| ----------------------------------------- | ---------------------------------------------------------------------------------------- |
| `/api/shutdown`                           | Beendet den Serverprozess                                                                |
| `/api/settings/database`                  | Export, Import und Löschung der Datenbank                                                |
| `/api/db-backups`                         | Zugriff auf vollständige Datenbank-Backup-Archive                                        |
| `/api/settings/export-json`               | Exportiert den vollständigen Einstellungsblock (einschl. Geheimnissen)                   |
| `/api/settings/import-json`               | Ersetzt den vollständigen Einstellungsblock                                              |
| `/api/providers/health-autopilot/actions` | Führt Autopilot-Behebungsaktionen aus                                                    |
| `/api/settings/obsidian`                  | Erstellt wiederverwendbare WebDAV-Zugangsdaten für ein beliebiges Vault-Stammverzeichnis |

**Antwort bei Verstoß:** `401 Authentication required`

`/api/settings/obsidian` deckt seine untergeordnete Route `/webdav` ab: `POST` richtet den WebDAV-Dateidienst —
der von der benutzerdefinierten Node-Schicht vor Next.js und außerhalb dieser Pipeline bereitgestellt wird — auf ein vom Aufrufer gewähltes Stammverzeichnis aus
und gibt neu erzeugte Basic-Anmeldedaten zurück, `DELETE` rotiert sie, und das übergeordnete `POST` speichert
das Obsidian-REST-API-Token. GHSA-62vw maskierte nur die Offenlegung des Passworts über `GET`; die Ausstellung
erfolgte weiterhin auf der Fail-open-Stufe (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` lehnt außerdem
einen Vault ab, der dem Datenverzeichnis entspricht, sich darin befindet oder es enthält.

### Der Bootstrap bei einer Neuinstallation ist nur über Loopback möglich — gemäß dem tatsächlichen Peer, nicht `Host`

Wenn kein Verwaltungspasswort konfiguriert ist (und kein `INITIAL_PASSWORD` gesetzt ist), hält `isAuthRequired()` in
`src/shared/utils/apiAuth.ts` den anonymen Bootstrap **nur für Loopback-Peers** offen.
Loopback wird anhand der vertrauenswürdigen Peer-Signale in folgender Reihenfolge bestimmt: der mit einem Token gekennzeichnete tatsächliche TCP-Peer
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, den die Richtlinie sieht), die pipelineeigene
`AUTHZ_HEADER_PEER_LOCALITY`-Entscheidung (die von den Route-Handlern gesehen wird und nur vertrauenswürdig ist, solange
`OMNIROUTE_PEER_STAMP_TOKEN` gesetzt ist) oder ein tatsächlicher Socket-Peer für direkte Aufrufer. `Host` /
`nextUrl.hostname` werden niemals herangezogen, und das erstmalige Setzen des Passworts
(`POST /api/settings/require-login`) unterliegt derselben Einschränkung, statt für jeden
Netzwerk-Peer offen zu sein (GHSA-7pq4-8pvv-rx7r). `managementPolicy` reicht seine eigene `peerContext`-Entscheidung
explizit weiter, sodass die Header der ORIGINALEN Anfrage (vor dem Entfernen) niemals darüber entscheiden.

### Stufe 3 — VERWALTUNG (Standard)

Alle anderen Verwaltungsrouten. Authentifizierung ist erforderlich, sofern nicht `requireLogin=false`
konfiguriert ist. CLI-Token können diese Routen authentifizieren (Loopback + gültiger HMAC).

## Auswertungsreihenfolge

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → Loopback                                   → weiter
     → kein Loopback, Bearer mit manage-Berechtigungsumfang
        UND isLocalOnlyBypassableByManageScope    → zulassen (management_key)
     → andernfalls                               → ablehnen 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → zulassen (system)
  3. hasValidCliToken(headers)?
     → zulassen (cli) [Loopback + timingSafeEqual-HMAC-Prüfung]
  4. isAlwaysProtectedPath(path) oder requireLogin=true?
     → isDashboardSessionAuthenticated?
        → zulassen (dashboard_session)
     → Bearer mit manage-Berechtigungsumfang auf einem nicht umgehbaren Pfad?
        → zulassen (management_key)
     → ablehnen 401/403
  5. requireLogin=false?
     → zulassen (anonymous)
```

Der Zweig für den manage-Berechtigungsumfang in Schritt 1 ist der einzige authentifizierte Pfad, der eine
LOCAL_ONLY-Route erfüllen kann; der Fehlermodus des Authentifizierungs-Backends gibt 503 (nicht 403) zurück, damit eine
abgelaufene DB nicht stillschweigend auf „ablehnen“ zurückfällt.

## Hinzufügen einer neuen Route mit Spawn-Fähigkeit

1. Füge das Pfadpräfix zu `LOCAL_ONLY_API_PREFIXES` in
   `src/server/authz/routeGuard.ts` hinzu
2. Füge einen Test in `tests/unit/authz/routeGuard.test.ts` hinzu, der sicherstellt, dass
   `isLocalOnlyPath()` für das neue Präfix true zurückgibt
3. **Überspringe diesen Schritt niemals** — siehe Strikte Regel Nr. 15 in `CLAUDE.md`
4. Entscheide: Gehört diese Route AUCH zu `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Die Standardantwort lautet **nein**. Aktiviere dies nur ausdrücklich, wenn die Route sicher für einen
   Inhaber des manage-Berechtigungsumfangs freigegeben werden kann (d. h. KEINEN beliebigen benutzergesteuerten Code startet).

## Hinzufügen eines Pfads, der mit manage-Berechtigungsumfang umgangen werden kann

1. Stelle sicher, dass die Route keinen vom Benutzer bereitgestellten Code oder entsprechende Befehle ausführt. Falls doch,
   brich ab — diese Ausnahme ist dafür das falsche Werkzeug.
2. Hänge das Präfix an `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` in
   `src/server/authz/routeGuard.ts` an
3. Füge in `tests/unit/authz/management-policy.test.ts` Testabdeckung für alle vier
   Anfragevarianten hinzu: kein Bearer (403), manage-Bearer (zulassen), Nicht-manage-Bearer
   (403) sowie den präfixspezifischen Regressionstest, dass `/api/cli-tools/runtime/*` selbst
   mit einem manage-Bearer strikt auf Loopback beschränkt bleibt.

## Dokumentieren von Sicherheitsstufen in OpenAPI

Wende beim Hinzufügen einer neuen Route zu `docs/openapi.yaml` die entsprechende
Herstellererweiterung an, wenn die Route durch `routeGuard.ts` klassifiziert wird:

| routeGuard.ts-Klassifizierung                  | YAML-Annotation                 | Durchsetzung                                                 |
| ---------------------------------------------- | ------------------------------- | ------------------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`                      | `x-loopback-only: true`         | Von Nicht-Loopback-Verbindungen bedingungslos blockiert      |
| `ALWAYS_PROTECTED_API_PATHS`                   | `x-always-protected: true`      | Authentifizierung auch bei `requireLogin=false` erforderlich |
| Interne Admin-/Debug-Route                     | `x-internal: true`              | Standardmäßig vor /dashboard/api-endpoints verborgen         |
| Keine (öffentlich / Standardauthentifizierung) | (keine Annotation erforderlich) | Standardzugriff, gesteuert durch `requireLogin`              |

### Validierung

Zwei Skripte erzwingen die Konsistenz zwischen YAML-Annotationen und `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — schlägt fehl, wenn die Abdeckung < 99% ist
- `scripts/check/check-openapi-security-tiers.mjs` — schlägt fehl, wenn `x-loopback-only`- oder
  `x-always-protected`-Annotationen von den Konstanten zur Kompilierzeit abweichen

Beide Skripte werden im Pre-Commit-Hook und in CI ausgeführt.

### Regel für falsch-positive Ergebnisse

Wenn `x-always-protected` oder `x-loopback-only` für eine Route annotiert ist, die NICHT in
der `routeGuard.ts`-Konstante enthalten ist, schlägt das Abdeckungsskript fehl. Die Lösung besteht immer darin, das
YAML an die tatsächliche Durchsetzung durch `routeGuard.ts` anzupassen — nicht darin, Routen zu `routeGuard.ts`
hinzuzufügen, ohne zugleich die Durchsetzungslogik zu implementieren.
