## 1. Tatsächliches Dienstverhalten (offizielle Dokumentation, gegengeprüft)

- Basis-URL: `https://api.anysearch.com` (REST) + `POST /mcp` (MCP, JSON-RPC 2.0).
- `POST /v1/search` - Parameter: `query` (erforderlich), `max_results` (1–10, Standardwert 10), `tag` (`{domain}.{sub_domain}` für vertikales Routing), `zone` (cn/intl), `language`, `params` (strukturierte vertikale Felder), `format` (json/markdown).
- `GET /v1/sub-domains?domain=...` - Funktionskatalog; wird NICHT auf das Kontingent angerechnet.
- `POST /v1/extract` - ruft `{url, title, content}` ab bzw. extrahiert diese Felder; strikt validierter JSON-Body, Obergrenze 16 KiB.
- `POST /v1/auth/email/register` - Registrierung mit einem einzigen Aufruf; gibt einmalig einen Klartextschlüssel `as_sk_...` zurück.
- Authentifizierung: optional über `Authorization: Bearer <as_sk_...>`; anonyme Nutzung wird auf Limits pro IP herabgestuft und verbraucht das tägliche Gratiskontingent; ein ungültiger Schlüssel führt zu 401/403, OHNE stillen Rückfall auf anonyme Nutzung.
- Kostenloser Tarif: 1000 Anfragen/Tag, 20 QPS pro Schlüssel. Kostenpflichtiger Tarif: noch ohne Preisangabe (demnächst verfügbar).
- Antwort-Envelope: Erfolg `{code: 0, message: "success", request_id, data}`; Fehler `{code: -1, message}`. Authentifizierungs-/Kontingentfehler enthalten keinen strukturierten `error_code` (der Nachrichtentext dient als Signal); extraktionsspezifische Fehler enthalten hingegen einen `error_code` (`invalid_extract_url`, `extract_failed`). Kein `Retry-After`-Header bei 429.

## 3. Entscheidungen (alle am 2026-08-26 getroffen)

1. **Routing-Strategie: `fallbackOnly`.** Begründung: Ein kostenloser Anbieter mit Kosten von 0 darf das automatische kostenbasierte Routing niemals dominieren; die explizite Auswahl und die Rückkehr nach einem Failover bleiben davon unberührt. Präzedenzfall: zusammengeführter xquik-Eintrag.
2. **Umfang: webSearch + webFetch über `POST /v1/extract` in v1.** Entspricht dem mentalen Modell der Doppelfunktionalität von tavily/exa. Vertikale Funktionen (`tag`, `sub-domains`, `batch_search`) bleiben außerhalb des Umfangs — derzeit gibt es keine IR für vertikale Parameter.
3. **Kontingentanzeige: `freeMonthlyQuota: 0`** (konservative Anzeige im xquik-Stil). Das tatsächliche Kontingent (1000 Anfragen/Tag, tägliche Zurücksetzung) wird stattdessen im Text von `authHint` des UI-Katalogs angegeben. Begründung: Die Kontingentanzeige muss der Zurücksetzungslogik entsprechen; die Umrechnung eines täglichen Limits in ein monatliches Äquivalent (30000) wäre ein falsches Versprechen, das die UI nicht einhalten kann.
4. **searchTypes: nur `["web"]`.** Es gibt keine öffentlich zugänglichen Belege für eine Nachrichten- oder Bildersuche in der AnySearch-API; Gateways, die APIs ohne dokumentierte vertikale Suche integrieren (z. B. Google Custom Search), bieten nur die Websuche an, statt Nachrichtenanfragen stillschweigend der Websuche zuzuordnen.
5. **Schlüsselstrategie:** Der schlüssellose Zugriff funktioniert; ein ungültiger Schlüssel führt zu 401/403 und wird niemals stillschweigend auf anonymen Zugriff herabgestuft (entspricht dem Upstream-Vertrag).
6. **Bewusste Ausschlüsse:** `FETCH_BACKEND_TO_PROVIDER` / `FetchInterceptionBackend` (die Chat-Interzeption bleibt bei firecrawl/jina/tavily); `ANONYMOUS_CAPABLE_WEB_FETCH_PROVIDERS` (anonyme Remote-Endpunkte teilen sich pro Egress-IP einen einzigen IP-limitierten Pool, daher ist die schlüssellose Extraktion eine Opt-in-Funktion und kein Kandidat für automatisches Routing); `QUOTA_STATUS_PROVIDERS` (AnySearch signalisiert das Kontingent über 429 bzw. den Antwort-Envelope, nicht über den Status 402/403).
