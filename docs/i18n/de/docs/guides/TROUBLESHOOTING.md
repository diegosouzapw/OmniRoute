## Kurzreferenz

**Neu bei OmniRoute?** Beginnen Sie hier — damit lassen sich 90 % der Probleme lösen:

| Folgendes wird angezeigt      | Bedeutung                                                                | Vorgehensweise                                                                                                    |
| ----------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| "Verbindung nicht möglich"    | OmniRoute wird nicht ausgeführt                                          | Führen Sie `omniroute` oder `docker restart omniroute` aus                                                        |
| "Ungültiger API-Schlüssel"    | Ihr Schlüssel ist falsch oder abgelaufen                                 | Kopieren Sie den Schlüssel erneut von der Website des Anbieters                                                   |
| "Ratenlimit überschritten"    | Sie senden zu viele Anfragen                                             | Warten Sie 1 Minute oder verwenden Sie `model: "auto"` für einen automatischen Fallback                           |
| "Kontingent überschritten"    | Sie haben Ihr kostenloses oder kostenpflichtiges Kontingent aufgebraucht | Binden Sie weitere Anbieter ein oder verwenden Sie kostenlose Anbieter (Kiro, Pollinations)                       |
| "Langsame Antworten"          | Der Anbieter ist ausgelastet oder weit entfernt                          | Verwenden Sie `model: "auto/fast"` oder binden Sie einen schnelleren Anbieter ein (Groq, Cerebras)                |
| "Falscher Anbieter verwendet" | `auto` hat einen anderen Anbieter ausgewählt                             | Das ist normal! `auto` wählt den besten aus. Erzwingen Sie mit `model: "openai/gpt-4o"` einen bestimmten Anbieter |
| "502 Bad Gateway"             | Der Anbieter ist nicht verfügbar                                         | Warten Sie und versuchen Sie es erneut oder verwenden Sie `model: "auto"`, um den Anbieter zu wechseln            |
| "401 Unauthorized"            | Ihre Anmeldedaten sind falsch                                            | Überprüfen Sie Ihren API-Schlüssel oder authentifizieren Sie sich erneut über OAuth                               |
| "429 Too Many Requests"       | Ratenbegrenzung ist aktiv                                                | Warten Sie 1 Minute oder binden Sie weitere Anbieter ein                                                          |

**Kommen Sie immer noch nicht weiter?** Lesen Sie unten die [detaillierte Fehlerbehebung](#detailed-troubleshooting) oder fragen Sie auf [Discord](https://discord.gg/U47eFqAXCn).

## Detaillierte Fehlerbehebung

---

### Ratenbegrenzung bei kostenlosen Anbietern (429 / 400 / 401)

**Symptom**: Bei der Verwendung von `model: "auto"` mit kostenlosen bzw. authentifizierungsfreien Anbietern (opencode, auggie usw.) erhalten Sie zeitweise `HTTP 429`, `400` oder `401` anstelle von Antworten. Wenn dieselbe Eingabeaufforderung kurz darauf erneut gesendet wird, sind die Anfragen erfolgreich, aber Automatisierungen (Cronjobs, Agenten, Skripte) brechen beim ersten Fehler ab.

**Ursache**: Drei unabhängige Fehlerarten verstärken sich gegenseitig:

1. **Anbieter-Ratenlimit (`429`)**: Kostenlose Tarife können ein Kontingent pro Zeitfenster erzwingen. Eine Serie paralleler Aufrufe schöpft dieses Kontingent aus, sodass die nächste Anfrage abgelehnt wird, bis das Zeitfenster zurückgesetzt wird.
2. **Fehlerhaftes Modell bei der Durchleitung (`400`/`401`)**: `auto/*`-Pools können durchgeleitete Modelle von `opencode` enthalten, die im Katalog registriert sind, aber keine gültigen Anmeldedaten besitzen (z. B. `oc/north-mini-code-free` → `401`). Der automatische Router versucht eines davon, scheitert, und der Fehler wird weitergegeben, bevor der Fallback greift.
3. **Verstärkung durch Parallelität (`429` unter Last)**: Wenn mehrere Agenten- oder Cron-Sitzungen gleichzeitig auf `auto` zugreifen, überschreitet die gesamte Anfragerate das Maß, das kostenlose Anbieter tolerieren, sodass legitime Aufrufe als missbräuchlich eingestuft werden.

**Bestätigte Lösung (aus der Community gemeldet, 2026-08-10)**: Passen Sie drei Umgebungsvariablen so an, dass Rotation, Parallelität und Fallback die Schwankungen kostenloser Tarife abfangen, anstatt daran zu scheitern:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # bei 400/401 zu einem anderen Modell/Anbieter wechseln (überspringt fehlerhafte Durchleitungsmodelle)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # explizite Obergrenze für die Annahme aufwendiger Anfragen (standardmäßig nicht gesetzt: keine Begrenzung der Anfrageanzahl, siehe Hinweis unten)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # längere begrenzte Wartezeit auf Kapazität für aufwendige Anfragen statt eines sofortigen, wiederholbaren 503-Fehlers
```

Legen Sie diese Variablen in der Prozessumgebung von OmniRoute fest (für den Daemon, z. B. über die LaunchAgent-plist oder `systemctl edit`) und starten Sie OmniRoute anschließend neu. Das Rotations-Flag bietet den mit Abstand größten Nutzen: Es wandelt einen endgültigen Fehler in einen transparenten Wiederholungsversuch bei einem funktionierenden Anbieter im Pool um.

**Hinweis**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` begrenzt, wie viele aufwendige Anfragen — also Anfragen mit langem Kontext — gleichzeitig ausgeführt werden. Diese Begrenzung ist eine Zugangsschranke und kein Ratenbegrenzer des Anbieters. **Aktualisierung zum #503-Fan-out:** Diese Variable wird standardmäßig nicht mehr gesetzt (sie greift jetzt nur, wenn sie wie oben explizit konfiguriert wird). Stattdessen wird die Annahme aufwendiger Anfragen durch ein automatisch abgeleitetes Byte-Budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) gesteuert, das sich an der tatsächlichen Speicherobergrenze des Hosts orientiert. Daher sollte es bei einer neuen Bereitstellung deutlich weniger Ablehnungen vom Typ `503 chat_admission_busy` geben, ohne dass diese Variable gesetzt werden muss. Wird sie hier explizit gesetzt, funktioniert sie weiterhin genau wie dokumentiert. Explizit festgelegte Byte-Budgets werden auf 8 MiB bis 2 GiB begrenzt. Ein Fehler vom Typ `413 body_exceeds_budget` ist nicht vorübergehend: Erhöhen Sie dieses Byte-Budget, reduzieren Sie `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` oder erhöhen Sie die Speicherobergrenze des Prozesses. Eine Lastabweisung vom Typ `inflight_bytes_budget` entsteht durch vorübergehende Ressourcenkonkurrenz und kann weiterhin durch einen erneuten Versuch behoben werden. Die Ratenbegrenzung pro Anbieter (`open-sse/services/rateLimitManager.ts`) wird separat durch `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` und `RATE_LIMIT_AUTO_ENABLE` gesteuert — siehe `.env.example`.

**So überprüfen Sie, ob die Lösung funktioniert hat**: Führen Sie Ihren Agenten oder Cronjob zweimal kurz hintereinander aus und vergewissern Sie sich, dass beide Ausführungen erfolgreich sind. Vor der Korrektur löst die zweite Ausführung üblicherweise einen Fehler vom Typ `429`/`401` aus. Nach der Korrektur werden Fehler (falls vorhanden) transparent erneut versucht, und der Aufruf wird abgeschlossen. Sie können auch `curl /monitoring/health` ausführen und das Feld `rateLimitedUntil` bei den Anbieter-Verbindungen sowie `circuitBreakers.providerBreakers[].state` für die betroffenen Anbieter beobachten. Der Status ist entweder `CLOSED`, `DEGRADED`, `OPEN` oder `HALF_OPEN` (siehe `src/shared/utils/circuitBreaker.ts`). Ein Anbieter, bei dem wiederholt Fehler auftreten, wechselt von `CLOSED → DEGRADED → OPEN`, bevor das zurückgesetzte Zeitfenster eine Testanfrage zulässt (`HALF_OPEN`).

**Wenn weiterhin 429 angezeigt wird**: Das aktive Konto für diesen Anbieter hat sein _Kontingent_ tatsächlich aufgebraucht (nicht nur das Ratenlimit). Füge im OmniRoute-Dashboard unter Providers → Accounts ein zweites Konto für denselben Anbieter hinzu oder binde einen weiteren kostenlosen Anbieter ein (z. B. `routeway`, `auggie`). Die Rotation hilft nur bei vorübergehenden Ratenbegrenzungen sowie 400-/401-Fehlern; bei einem vollständig ausgeschöpften Kontingent sind weitere Zugangsdaten oder ein anderer Anbieter erforderlich.

**Wenn bei Vision-Modellen (`auto/vision`, `bazaarlink/*`) der Fehler 403 angezeigt wird**: Das verbundene Konto verfügt nicht über einen kostenpflichtigen Tarif, der Vision unterstützt, oder der API-Schlüssel hat nicht die erforderlichen Berechtigungen. Überprüfe im Anbieter-Dashboard, ob der Berechtigungsumfang des Schlüssels Vision/Multimodalität umfasst, oder verbinde ein Konto mit einem kostenpflichtigen Tarif und verwende es weiterhin als Vision-Ziel.

## Warnungen bei npm install (ERESOLVE / Peer-Abhängigkeiten / veraltet)

Wenn Sie `npm install -g omniroute` ausführen, sehen Sie möglicherweise eine Vielzahl von Warnungen wie `npm warn ERESOLVE`, Hinweise zu Peer-Abhängigkeiten und `deprecated`-Meldungen. **Diese sind zu erwarten und unbedenklich.** Ihre Installation war erfolgreich, wenn in der Ausgabe `added <N> packages` angezeigt wird.

Um die Warnungen zur Auflösung von Peer-Abhängigkeiten zu unterdrücken, verwenden Sie die von OmniRoute unterstützte Installationsform:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` unterdrückt nur `ERESOLVE`- und Peer-Abhängigkeitshinweise. Hinweise zu veralteten Paketen bleiben sichtbar, da sie von transitiven Drittanbieterpaketen stammen; sie bedeuten nicht, dass die Installation fehlgeschlagen ist.

Die Warnungen stammen von veralteten Peer-Abhängigkeitsbereichen in Drittanbieterpaketen, auf die OmniRoute keinen Einfluss hat:

1. **`marked-terminal` erfordert `marked >=1 <16`, gefunden wurde `marked@18`** — funktioniert in der Praxis problemlos; der Peer-Abhängigkeitsbereich des Upstream-Pakets ist lediglich veraltet.
2. **`deprecated prebuild-install@7.1.3`** — ein transitives Hilfsprogramm zum Abrufen nativer Binärdateien. Es wird nicht
   zur Installation der festgelegten `wreq-js`-Transportanbindung verwendet und bedeutet nicht, dass die Einrichtung des Transports
   für den Web-Cookie-Anbieter fehlgeschlagen ist.

**Keine Maßnahmen erforderlich** — die Warnungen können nicht vollständig unterdrückt werden, ohne die Upstream-Pakete zu forken.

## Schnelle Lösungen

| Problem                                                    | Lösung                                                                                                                                                                                              |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Erste Anmeldung funktioniert nicht                         | Legen Sie `INITIAL_PASSWORD` in `.env` fest (kein fest codierter Standardwert)                                                                                                                      |
| Dashboard wird am falschen Port geöffnet                   | Legen Sie `PORT=20128` und `NEXT_PUBLIC_BASE_URL=http://localhost:20128` fest                                                                                                                       |
| Es werden keine Protokolle auf die Festplatte geschrieben  | Legen Sie `APP_LOG_TO_FILE=true` fest und überprüfen Sie, ob die Erfassung von Aufrufprotokollen aktiviert ist                                                                                      |
| EACCES: Zugriff verweigert                                 | Legen Sie `DATA_DIR=/path/to/writable/dir` fest, um `~/.omniroute` zu überschreiben                                                                                                                 |
| Routingstrategie wird nicht gespeichert                    | Aktualisieren Sie auf die neueste v3.x-Version (die Zod-Schemakorrektur zur dauerhaften Speicherung von Einstellungen wurde bereits in früheren Versionen ausgeliefert)                             |
| Absturz bei der Anmeldung / leere Seite                    | Überprüfen Sie die Node.js-Version — siehe [Node.js-Kompatibilität](#nodejs-compatibility) weiter unten                                                                                             |
| `dlopen` / `slice is not valid mach-o file` (macOS)        | Führen Sie `cd $(npm root -g)/omniroute/app && npm rebuild better-sqlite3 && omniroute` aus — siehe [Neukompilierung nativer macOS-Module](#macos-native-module-rebuild) weiter unten               |
| Proxy: „fetch failed“                                      | Stellen Sie sicher, dass die Proxy-Konfiguration auf der richtigen Ebene festgelegt ist — siehe [Proxy-Probleme](#proxy-issues) weiter unten                                                        |
| Docker `curl: (56) Recv failure: Connection reset by peer` | Die Docker-Portbindung verwendet möglicherweise IPv6. Verwenden Sie `-p 127.0.0.1:20128:20128`, um IPv4 zu erzwingen, oder testen Sie mit `curl -4`. Siehe [Docker-IPv6](#docker-ipv6) weiter unten |
| Antivirusprogramm stellt `README.md` unter Quarantäne      | Fehlalarm — siehe [Fehlalarme von Antivirusprogrammen](#antivirus-false-positives) weiter unten                                                                                                     |
| Kaspersky stuft die Desktop-App als Trojaner ein           | Verhaltensbasierter Fehlalarm beim unsignierten Installationsprogramm — siehe [Fehlalarme von Antivirusprogrammen](#antivirus-false-positives) weiter unten                                         |

## Fehlalarme von Antivirenprogrammen

<a name="antivirus-false-positives"></a>

### Avast/AVG verschiebt `README.md` wegen `MD:HttpRequest-inf[Susp]` in Quarantäne

**Dies ist ein Fehlalarm. Nichts ist infiziert und es sind keine Maßnahmen erforderlich.**

Avast und AVG verwenden eine Heuristik, die Klartext-/Markdown-Dateien kennzeichnet, die viele
Links enthalten, die wie HTTP-Anfragen aussehen. Die `README.md` von OmniRoute ist im npm-Paket enthalten (sie ist
in `package.json` → `files` aufgeführt), sodass sie bei einer globalen Installation unter
`node_modules/omniroute/README.md` abgelegt wird — und sie enthält etwa 15 Beispiele mit
`http://localhost:20128/...` (die MCP-HTTP-/SSE-Endpunkte, die A2A-`.well-known`-URL und
`curl`-Beispiele). Diese Linkdichte reicht aus, um die Heuristik auszulösen.

Falls dies erst seit Kurzem auftritt: Die Art der Datei hat sich nicht geändert. Die Endpunkttabelle
der README wurde erweitert (MCP HTTP + SSE + A2A wurden hinzugefügt), ebenso kamen weitere
`curl`-Beispiele hinzu, wodurch der Schwellenwert überschritten wurde.

Bei der Datei handelt es sich um inaktive Dokumentation ohne jeglichen ausführbaren Inhalt. Sie können sie
gefahrlos aus der Quarantäne wiederherstellen.

**Vorgehensweise:**

1. **Benachrichtigungen stoppen** — schließen Sie das Installationsverzeichnis in Ihrem Antivirenprogramm aus
   (Avast: Einstellungen → Ausnahmen), indem Sie den Pfad zu Ihrem globalen `node_modules` und/oder das
   OmniRoute-Datenverzeichnis (`~/.omniroute/`) hinzufügen.
2. **Den Fehlalarm melden** — <https://www.avast.com/false-positive-file-form.php>;
   hängen Sie dabei die unter Quarantäne gestellte `README.md` an. Diese Lösung hilft allen, da hier
   die Heuristik des Anbieters überempfindlich auf eine Textdatei reagiert.

**Warum wir dies nicht auf unserer Seite „beheben“:** Bei allen Beispielen handelt es sich um `http://localhost`,
und localhost kann nicht ohne den zusätzlichen Aufwand selbstsignierter Zertifikate `https` verwenden. Die Dokumentation zu
verunstalten, um die Heuristik eines einzelnen Anbieters zu umgehen, würde allen Lesern schaden, nur um einen
Scannerfehler zu umgehen.

### Kaspersky kennzeichnet die Desktop-App als `PDM:Trojan.Win32.Generic`

**Dies ist ein Fehlalarm einer Verhaltensheuristik. Nichts ist infiziert.** Das Präfix
`PDM:` von Kaspersky bedeutet, dass die Einstufung von seinem Proactive Defense Module (System Watcher)
stammt, das beurteilt, was das Installationsprogramm _tut_, anstatt es mit bekannter Schadsoftware
abzugleichen. Wenn es ausgelöst wird, macht Kaspersky die gesamte Installation „rückgängig“ — und löscht dabei
bereits geschriebene Dateien —, sodass die App anschließend beschädigt ist oder fehlt.

Bei den gekennzeichneten Dateien handelt es sich um unveränderte Bestandteile deklarierter Open-Source-Abhängigkeiten, die mit der
Desktop-App gebündelt sind, zum Beispiel:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` und
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), die Bibliothek zur Browserautomatisierung,
  die für die Anmeldung bei Anbietern innerhalb der App und für browsergestützte Chats verwendet wird.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — die festgelegte native `wreq-js`-Anbindung, die für HTTP mit Browser-Fingerprinting bei Anbietern mit
  Web-Cookies verwendet wird (`<arch>` ist `x64` oder `arm64`).

**Warum dies ausgelöst wird:** Das Windows-Installationsprogramm ist **noch nicht codesigniert**, sodass ein
unsigniertes NSIS-Installationsprogramm keinerlei Reputation besitzt und Verhaltensheuristiken mit maximaler
Aggressivität ausgeführt werden. In Kombination mit einer gebündelten nativen DLL und Hunderten von `.js`-Dateien,
die unter `%LOCALAPPDATA%\Programs\OmniRoute` geschrieben werden (einschließlich Paketverzeichnissen mit angehängtem
Hash aus dem eigenständigen Next.js-Build), reicht dies aus, um die Heuristik auszulösen. Eine Codesignatur ist geplant;
bis sie verfügbar ist, kann dies bei neuen Releases erneut auftreten.

**Vorgehensweise:**

1. **Überprüfen Sie zuerst Ihren Download** (damit wird eine manipulierte Datei ausgeschlossen). Jedes Release veröffentlicht
   `latest.yml`, dessen Feld `sha512` (Base64) das Installationsprogramm
   `OmniRoute.Setup.<version>.exe` abdeckt. Führen Sie in PowerShell im Ordner, der das Installationsprogramm enthält,
   Folgendes aus:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Die Ausgabe muss mit `latest.yml` → `sha512` übereinstimmen. Falls dies nicht der Fall ist, löschen Sie die Datei und
   laden Sie sie ausschließlich von der [GitHub-Releaseseite](https://github.com/diegosouzapw/OmniRoute/releases) erneut herunter.
2. **Wiederherstellen + ausschließen** — stellen Sie die rückgängig gemachten Elemente aus der Quarantäne wieder her und fügen Sie
   eine Ausnahme für `%LOCALAPPDATA%\Programs\OmniRoute` hinzu (Kaspersky → Einstellungen → Bedrohungen und Ausnahmen);
   installieren Sie die App anschließend erneut.
3. **Den Fehlalarm melden** — <https://opentip.kaspersky.com/>. Von Benutzern eingereichte Meldungen zu
   Fehlalarmen beschleunigen die Aufnahme in die Positivliste tatsächlich.

## Node.js-Kompatibilität

<a name="nodejs-compatibility"></a>

### Anmeldeseite stürzt ab oder zeigt den Fehler „Module self-registration“ an

**Ursache:** Sie verwenden eine Node.js-Version außerhalb der von OmniRoute zugelassenen sicheren Laufzeitversionen. Meist wird eine ältere Patch-Version von Node 22 oder 24 verwendet, die unterhalb der von OmniRoute vorausgesetzten gepatchten Sicherheitsversion liegt.

**Symptome:**

- Die Anmeldeseite zeigt einen leeren Bildschirm oder einen Serverfehler an
- Die Konsole zeigt `Error: Module did not self-register` oder ähnliche Fehler nativer Bindings an
- Die Anmeldeseite zeigt ein **orangefarbenes Warnbanner** mit Ihrer Node-Version an, wenn die Laufzeitumgebung außerhalb der unterstützten Sicherheitsrichtlinie liegt

**Lösung:**

1. Installieren Sie eine unterstützte Node.js-LTS-Version (empfohlen: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Überprüfen Sie Ihre Version: `node --version` sollte `v24.0.0` oder neuer innerhalb der LTS-Versionsreihe 24.x anzeigen
3. Installieren Sie OmniRoute erneut: `npm install -g omniroute`
4. Starten Sie OmniRoute neu: `omniroute`

> **Unterstützte sichere Versionen:** `>=22.22.2 <23` oder `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) und Node.js 26 werden vollständig unterstützt.

### npm v11+: `better-sqlite3` nicht installiert (Modul kann nicht gefunden werden)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Ursache:** npm v11 (im Lieferumfang von Node.js 24+) blockiert standardmäßig Installationsskripte für optionale
Abhängigkeiten. Da `better-sqlite3` unter `optionalDependencies` aufgeführt ist
und eine native Kompilierung (`node-gyp rebuild`) erfordert, überspringt npm die Installation ohne Hinweis.

**Symptome:**

- Der Server stürzt beim Start mit `Cannot find module 'better-sqlite3'` ab
- `ls node_modules/better-sqlite3` zeigt „No such file or directory“ an
- `npm ls better-sqlite3` zeigt `(empty)` an

**Lösung:**

1. Genehmigen Sie die Installationsskripte und führen Sie die Installation erneut durch:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Oder installieren Sie das vorkompilierte Paket manuell:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Überprüfen Sie, ob es funktioniert: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file“

<a name="macos-native-module-rebuild"></a>

**Ursache:** Nach einer globalen Installation mit `npm install -g omniroute` wurde die native Binärdatei von `better-sqlite3` innerhalb des Pakets möglicherweise für eine andere Architektur oder Node.js-ABI kompiliert als die lokal verwendete. Dies tritt häufig unter macOS (sowohl auf Apple Silicon als auch auf Intel) auf, wenn die vorkompilierte Binärdatei nicht zu Ihrer Umgebung passt.

**Symptome:**

- Der Server schlägt unmittelbar beim Start mit einem `dlopen`-Fehler fehl
- Der Fehler enthält `slice is not valid mach-o file`
- Vollständiges Beispiel:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Lösung — für Ihre lokale Umgebung neu kompilieren (kein Downgrade von Node.js erforderlich):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Hinweis:** Dadurch wird das native Binding für Ihre lokale Node.js-Version und CPU-Architektur neu kompiliert, wodurch die Binärinkompatibilität behoben wird. Der offiziell unterstützte Laufzeitversionsbereich ist **`>=22.22.2 <23` oder `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` in `src/shared/utils/nodeRuntimeSupport.ts`, abgestimmt auf das Feld `engines` in `package.json`). Node.js 24.x LTS (Krypton) und Node.js 26 werden mit `better-sqlite3` v12.x vollständig unterstützt.

## Proxy-Probleme

<a name="proxy-issues"></a>

### Bei der Anbieter-Validierung wird „fetch failed“ angezeigt

**Ursache:** Der Endpunkt zur API-Schlüsselvalidierung (`POST /api/providers/validate`) hat zuvor die Proxy-Konfiguration umgangen, was in Umgebungen, die Proxy-Routing erfordern, zu Fehlern führte.

**Behebung (v3.5.5+):** Dies wurde behoben. Die Anbieter-Validierung wird nun über `runWithProxyContext` geleitet, wobei anbieterspezifische und globale Proxy-Einstellungen automatisch berücksichtigt werden.

### Die Token-Zustandsprüfung schlägt mit „fetch failed“ fehl

**Ursache:** Bei der OAuth-Token-Aktualisierung im Hintergrund wurde die Proxy-Konfiguration nicht für jede Verbindung einzeln aufgelöst.

**Behebung (v3.5.5+):** Der Scheduler für die Token-Zustandsprüfung löst nun vor dem Aktualisierungsversuch die Proxy-Konfiguration für jede Verbindung auf. Aktualisieren Sie auf v3.5.5+.

### Der SOCKS5-Proxy gibt „invalid onRequestStart method“ zurück

**Ursache:** Unter Node.js 22 ist der Dispatcher von undici@8 nicht mit der integrierten `fetch()`-Implementierung von Node.js kompatibel.

**Behebung (v3.5.5+):** OmniRoute verwendet nun die eigene `fetch()`-Funktion von undici, wenn ein Proxy-Dispatcher aktiv ist, wodurch ein konsistentes Verhalten gewährleistet wird. Aktualisieren Sie auf v3.5.5+.

### MITM-Proxy unter WSL: Desktop-Apps auf dem Windows-Host werden nicht abgefangen

**Ursache:** Der MITM-Proxy und sein CA-Zertifikat werden in der Umgebung installiert, in der OmniRoute ausgeführt wird. Unter WSL ist diese Umgebung das Linux-Gastsystem, während die KI-Desktop-Apps (Kiro, Trae, Copilot, Zed, …) auf dem Windows-Host ausgeführt werden. Die Host-Apps vertrauen dem Zertifikatsspeicher des Gastsystems nicht und leiten ihren Datenverkehr nicht über den System-Proxy des Gastsystems. Daher greift das Abfangen des Desktop-Datenverkehrs dort nicht.

**Empfehlung:** Führen Sie OmniRoute nativ auf demselben Betriebssystem aus wie die Desktop-Apps, die Sie abfangen möchten (Windows für Windows-Apps; entsprechend macOS/Linux). Wenn OmniRoute innerhalb von WSL verbleibt und gleichzeitig Host-Apps abgefangen werden sollen, müssen Sie dem generierten CA-Zertifikat auf dem Windows-Host manuell vertrauen und die Netzwerk-/Proxy-Einstellungen jeder Host-App auf den WSL-Proxy-Endpunkt verweisen lassen — eine nicht unterstützte und fehleranfällige Konfiguration.

## Anbieterprobleme

### „Language model did not provide messages“

**Ursache:** Das Anbieterkontingent ist ausgeschöpft.

**Behebung:**

1. Prüfen Sie die Kontingentanzeige im Dashboard
2. Verwenden Sie eine Kombination mit Ausweichstufen
3. Wechseln Sie zu einer günstigeren/kostenlosen Stufe

### Ratenbegrenzung

**Ursache:** Das Abonnementkontingent ist ausgeschöpft.

**Behebung:**

- Fügen Sie eine Ausweichoption hinzu: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Verwenden Sie GLM/MiniMax als kostengünstige Ausweichoption

### OAuth-Token abgelaufen

OmniRoute aktualisiert Tokens automatisch. Falls die Probleme weiterhin bestehen:

1. Dashboard → Anbieter → Erneut verbinden
2. Löschen Sie die Anbieterverbindung und fügen Sie sie erneut hinzu

### Mehrere Kiro-Konten: Das zweite Konto macht das erste ungültig

**Ursache:** Das Backend von Kiro erzwingt eine einzige aktive Sitzung pro OIDC-Client-Registrierung.
Wenn zwei Konten denselben registrierten Client verwenden (Verbindungen, die vor v3.8.0 importiert wurden),
macht die Aktualisierung des Tokens eines Kontos das Aktualisierungs-Token des anderen ungültig.

**Behebung (v3.8.0+):** Importieren Sie die betroffenen Verbindungen erneut.
Ab v3.8.0 registriert jede neue Kiro-Verbindung, die über **Token importieren**,
**Anmeldung über Google/GitHub** oder **Automatischer Import** erstellt wird, automatisch einen eigenen
dedizierten OIDC-Client. Dadurch ist die Verbindung vollständig isoliert, und die Aktualisierung eines
Kontos hat keine Auswirkungen auf andere Konten.

Verbindungen, die _vor_ v3.8.0 importiert wurden, verfügen nicht über eine verbindungsspezifische
Client-Registrierung. Diese Verbindungen verwenden weiterhin den gemeinsamen Aktualisierungs-Endpunkt für die Anmeldung über soziale Konten.
Um die Isolierung zu erhalten, löschen Sie die alte Verbindung unter Dashboard → Anbieter und fügen Sie sie
über einen der drei Importabläufe erneut hinzu.

Ausführliche Informationen und eine Schritt-für-Schritt-Anleitung zum parallelen Hinzufügen zweier Kiro-Konten
finden Sie unter [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Cloud-Probleme

### Fehler bei der Cloud-Synchronisierung

1. Überprüfen Sie, ob `BASE_URL` auf Ihre laufende Instanz verweist (z. B. `http://localhost:20128`)
2. Überprüfen Sie, ob `CLOUD_URL` auf Ihren Cloud-Endpunkt verweist (z. B. `https://omniroute.dev`)

### Cloud gibt bei `stream=false` den Statuscode 500 zurück

**Symptom:** `Unexpected token 'd'...` am Cloud-Endpunkt bei Nicht-Streaming-Aufrufen.

**Ursache:** Der Upstream-Dienst gibt eine SSE-Nutzlast zurück, während der Client JSON erwartet.

**Problemumgehung:** Verwenden Sie `stream=true` für direkte Cloud-Aufrufe. Die lokale Laufzeitumgebung enthält einen SSE→JSON-Fallback.

### Cloud zeigt „Verbunden“ an, meldet aber „Ungültiger API-Schlüssel“

1. Erstellen Sie im lokalen Dashboard einen neuen Schlüssel (`/api/keys`)
2. Führen Sie die Cloud-Synchronisierung aus: Cloud aktivieren → Jetzt synchronisieren
3. Alte bzw. nicht synchronisierte Schlüssel können in der Cloud weiterhin `401` zurückgeben

## Docker-Probleme

### Docker-IPv6 / Verbindungsabbruch

<a name="docker-ipv6"></a>

**Symptome:** `curl http://localhost:20128/v1/models` gibt `curl: (56) Recv failure: Connection reset by peer` zurück. Das Dashboard und nicht authentifizierte Endpunkte funktionieren, authentifizierte Endpunkte schlagen jedoch fehl — dies sieht wie ein Authentifizierungsproblem aus, ist aber keines.

**Ursache:** `docker run -p 20128:20128` veröffentlicht den Port sowohl auf `0.0.0.0` (IPv4) als auch auf `::` (IPv6), der Prozess im Container lauscht jedoch nur auf IPv4. Auf Hosts, auf denen `localhost` zuerst zu `::1` aufgelöst wird, erreicht die Verbindung den veröffentlichten IPv6-Port, hinter dem kein Dienst lauscht → die Verbindung wird zurückgesetzt.

**Lösung:**

1. **Schnelldiagnose:** Führen Sie `curl -4 http://localhost:20128/v1/models` aus. Wenn es mit `-4` funktioniert, aber ohne diese Option fehlschlägt, liegt eine abweichende IPv6-Bindung vor.
2. **Dauerhafte Lösung:** Binden Sie den Port explizit an IPv4, indem Sie in Ihrem `docker run`-Befehl `-p 127.0.0.1:20128:20128` verwenden:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Dadurch wird die IPv4-Bindung erzwungen und zugleich verhindert, dass der Proxy auf allen Host-Schnittstellen verfügbar ist.

## Fehlerbehebung

### Protokolldateien aktivieren

Legen Sie in Ihrer `.env`-Datei `APP_LOG_TO_FILE=true` fest. Anwendungsprotokolle werden unter `logs/` gespeichert.
Anfrageartefakte werden unter `${DATA_DIR}/call_logs/` gespeichert, wenn die Aufrufprotokoll-Pipeline
in den Einstellungen aktiviert ist.
Wenn die Pipeline-Erfassung aktiviert ist, legen Sie `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` fest, um
Nutzlasten von Streaming-Datenblöcken auszulassen, oder passen Sie `CALL_LOG_PIPELINE_MAX_SIZE_KB` an, um die maximale Artefaktgröße in KB zu ändern.

### Anbieterstatus prüfen

```bash
# Status-Dashboard
http://localhost:20128/dashboard/health

# API-Statusprüfung
curl http://localhost:20128/api/monitoring/health
```

### Laufzeitspeicher

- Hauptzustand: `${DATA_DIR}/storage.sqlite` (Anbieter, Kombinationen, Aliasse, Schlüssel, Einstellungen)
- Nutzung: SQLite-Tabellen in `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + optional `${DATA_DIR}/call_logs/`
- Anwendungsprotokolle: `<repo>/logs/...` (wenn `APP_LOG_TO_FILE=true`)
- Aufrufprotokoll-Artefakte: `${DATA_DIR}/call_logs/YYYY-MM-DD/...`, wenn die Aufrufprotokoll-Pipeline aktiviert ist

Die Aktion **Verlauf bereinigen** auf der Seite „Anfrageprotokolle“ löscht `call_logs`, das veraltete
`request_detail_logs` sowie das lokale Artefaktverzeichnis `${DATA_DIR}/call_logs/`.

## Circuit-Breaker-Probleme

### Provider bleibt im Zustand OPEN hängen

Wenn der Circuit Breaker eines Providers OPEN ist, werden Anfragen blockiert, bis die Abklingzeit abgelaufen ist.

**Lösung:**

1. Gehen Sie zu **Dashboard → Settings → Resilience**
2. Überprüfen Sie die Circuit-Breaker-Karte für den betroffenen Provider
3. Klicken Sie auf **Reset All**, um alle Circuit Breaker zurückzusetzen, oder warten Sie, bis die Abklingzeit abgelaufen ist
4. Vergewissern Sie sich vor dem Zurücksetzen, dass der Provider tatsächlich verfügbar ist

### Provider löst wiederholt den Circuit Breaker aus

Wenn ein Provider wiederholt in den Zustand OPEN wechselt:

1. Prüfen Sie unter **Dashboard → Health → Provider Health** das Fehlermuster
2. Gehen Sie zu **Settings → Resilience → Provider Profiles** und erhöhen Sie den Fehlerschwellenwert
3. Prüfen Sie, ob der Provider seine API-Limits geändert hat oder eine erneute Authentifizierung erfordert
4. Überprüfen Sie die Latenztelemetrie — eine hohe Latenz kann zu zeitüberschreitungsbedingten Fehlern führen

## Fehlersuche bei der Übersetzung

Verwenden Sie **Dashboard → Translator**, um Probleme bei der Formatübersetzung zu untersuchen:

| Modus            | Verwendungszweck                                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **Playground**   | Eingabe- und Ausgabeformate nebeneinander vergleichen — fügen Sie eine fehlerhafte Anfrage ein, um die Übersetzung zu prüfen |
| **Chat Tester**  | Live-Nachrichten senden und die vollständigen Anfrage-/Antwortdaten einschließlich der Header überprüfen                     |
| **Test Bench**   | Batch-Tests über verschiedene Formatkombinationen ausführen, um fehlerhafte Übersetzungen zu ermitteln                       |
| **Live Monitor** | Den Anfragefluss in Echtzeit beobachten, um sporadisch auftretende Übersetzungsprobleme zu erkennen                          |

### Häufige Formatprobleme

- **Thinking-Tags werden nicht angezeigt** — Prüfen Sie, ob der Ziel-Provider Thinking unterstützt, sowie die Einstellung für das Thinking-Budget
- **Tool-Aufrufe gehen verloren** — Bei manchen Formatübersetzungen werden möglicherweise nicht unterstützte Felder entfernt; überprüfen Sie dies im Playground-Modus
- **System-Prompt fehlt** — Claude und Gemini behandeln System-Prompts unterschiedlich; prüfen Sie die Übersetzungsausgabe
- **SDK gibt einen Roh-String statt eines Objekts zurück** — In v1.x behoben; der Antwort-Sanitizer entfernt nicht standardmäßige Felder (`x_groq`, `usage_breakdown` usw.), die zu Pydantic-Validierungsfehlern im OpenAI SDK führen. Wenn dieses Problem unter v3.x+ weiterhin auftritt, erstellen Sie bitte einen Issue.
- **GLM/ERNIE lehnt die Rolle `system` ab** — In v1.x behoben; der Rollen-Normalisierer führt Systemnachrichten für inkompatible Modelle automatisch mit Benutzernachrichten zusammen. Wenn dieses Problem unter v3.x+ weiterhin auftritt, erstellen Sie bitte einen Issue.
- **Rolle `developer` wird nicht erkannt** — In v1.x behoben; für Nicht-OpenAI-Provider wird sie automatisch in `system` umgewandelt. Wenn dieses Problem unter v3.x+ weiterhin auftritt, erstellen Sie bitte einen Issue.
- **`json_schema` funktioniert nicht mit Gemini** — In v1.x behoben; `response_format` wird jetzt in Geminis `responseMimeType` + `responseSchema` umgewandelt. Wenn dieses Problem unter v3.x+ weiterhin auftritt, erstellen Sie bitte einen Issue.

## Resilienz-Einstellungen

### Automatische Ratenbegrenzung wird nicht ausgelöst

- Die automatische Ratenbegrenzung gilt nur für Anbieter mit API-Schlüsseln (nicht für OAuth/Abonnements)
- Überprüfen Sie, ob unter **Einstellungen → Resilienz → Anbieterprofile** die automatische Ratenbegrenzung aktiviert ist
- Prüfen Sie, ob der Anbieter `429`-Statuscodes oder `Retry-After`-Header zurückgibt

### Abstimmen des exponentiellen Backoffs

Anbieterprofile unterstützen diese Einstellungen:

- **Basisverzögerung** — Anfängliche Wartezeit nach dem ersten Fehler (Standard: 1s)
- **Maximale Verzögerung** — Obergrenze für die maximale Wartezeit (Standard: 30s)
- **Multiplikator** — Faktor, um den die Verzögerung bei jedem aufeinanderfolgenden Fehler erhöht wird (Standard: 2x)

### Schutz vor Thundering Herd

Wenn viele gleichzeitige Anfragen auf einen Anbieter mit aktiver Ratenbegrenzung treffen, verwendet OmniRoute Mutex + automatische Ratenbegrenzung, um Anfragen zu serialisieren und kaskadierende Fehler zu verhindern. Dies geschieht bei Anbietern mit API-Schlüsseln automatisch.

### Chat-Anfragen schlagen mit 503 / chat_admission_busy fehl

**Symptome:**

- Der Endpunkt für Chat-Vervollständigungen gibt eine wiederholbare `503`-Antwort zurück, deren Fehlercode
  `chat_admission_busy` lautet.
- Die Antwort enthält `Retry-After`. Seit #12135 wird der Wert aus der beobachteten
  Auslastung abgeleitet — dem größeren Wert aus dem `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`-Zeitfenster, das die Anfrage bereits
  gewartet hat, und der Zeit, die die aktuellen ressourcenintensiven Leases gehalten wurden — auf volle
  Sekunden aufgerundet und auf 60 begrenzt. Bei einem inaktiven Gate bleiben die bisherigen Mindestwerte erhalten: 2 Sekunden beim
  Byte-basierten Pfad, 1 Sekunde beim strukturbasierten Pfad (der außerdem
  `reason: "structure_limit"` enthält).
- Dies kann auftreten, während ein anderer ressourcenintensiver Chat oder eine lang laufende Streaming-Antwort noch
  verarbeitet wird.

Der Byte-basierte Antworttext lautet:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Die strukturbasierte Antwort verwendet denselben Typ und Code mit der Meldung
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
und `reason: "structure_limit"`.
Bei den Standardschwellenwerten gilt eine Anfrage als strukturell ressourcenintensiv, wenn sie mindestens `200` Nachrichten,
mindestens `64` Tools oder mindestens `32,000` geschätzte Tokens enthält oder wenn die begrenzte Strukturschätzung
ihre Grenzen von `10,000` besuchten Knoten oder einer Tiefe von `12` ausschöpft.

**Ursache:** Dies ist eine gezielte Lastabweisung innerhalb von OmniRoute und kein Fehler eines vorgelagerten Anbieters.
Jeder Prozess verwendet einen prozesslokalen Schutzmechanismus, um begrenzte Kapazität für ressourcenintensive Anfragen zu reservieren, bevor
ein großer Anfragekörper vorgehalten und geparst wird. Eine ressourcenintensive Lease bleibt für die gesamte Lebensdauer einer SSE-
Antwort bestehen.

**#503-Fan-out:** Vor dieser Korrektur begrenzte der Schutzmechanismus die Parallelität unabhängig vom Hostspeicher auf eine feste ANZAHL von Anfragen
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, Standard `1`), sodass der Fan-out von Coding-Agenten
(mehrere Subagenten/CLIs, Anfragetexte regelmäßig > 256 KB) auf eine effektive
Parallelität von etwa 1 einbrach und bei vollkommen normaler Last 503-Fehler erzeugte. Der Schutzmechanismus passt sich jetzt selbst an: Er wird
durch ein automatisch abgeleitetes Byte-Budget für die Aufnahme (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) gesteuert, das anhand der
tatsächlichen Speicherobergrenze des Prozesses dimensioniert wird, und berücksichtigt außerdem ein aktuelles Signal für die Ressourcenauslastung — sodass er
Anfragen nur abweist, wenn der Host tatsächlich unter Speicherdruck steht, und nicht nur, weil mehr als eine
ressourcenintensive Anfrage gleichzeitig eingegangen ist. Die alte Anzahlbegrenzung (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) wird
weiterhin berücksichtigt, jedoch nur, wenn Sie sie ausdrücklich festlegen.

Wenn die Kapazität ausgelastet ist, wartet eine ressourcenintensive Anfrage zunächst bis zu
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (Standard `2000`, `0` deaktiviert das Warten) darauf, dass ein Platz frei wird,
bevor mit dem wiederholbaren `503` geantwortet wird. Die begrenzte Wartezeit dient dazu, dass agentenbasierte Clients
(OpenCode, Claude Code, Cursor), die ressourcenintensive Unteranfragen gleichzeitig auffächern, den Laststoß serialisieren,
anstatt ihr gesamtes Wiederholungsbudget durch sofortige Ablehnungen aufzubrauchen und mitten in der Aufgabe abzubrechen.
Die aktuelle Belegung durch ressourcenintensive Leases, das ermittelte Byte-Budget und der aktuelle Schweregrad des Ressourcendrucks werden
unter `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) angezeigt — prüfen Sie diese Werte, bevor Sie eine Umgebungsvariable ändern.
Einstellungen → Resilienz → Anfragewarteschlange → Gleichzeitige Anfragen steuert dies nicht; diese Einstellung
regelt einen separaten Mechanismus für Anbieter-Anfragewarteschlangen.

**Behebung:**

1. Versuchen Sie es zunächst erneut. Clients sollten `Retry-After` beachten und Backoff verwenden, anstatt die Anfrage sofort
   zu wiederholen.
2. Prüfen Sie `/api/monitoring/health` → `chatAdmission`, bevor Sie etwas abstimmen. `countCapEnabled:
false` und ein großzügiger Wert für `maxInflightBytes` bedeuten, dass das automatisch abgeleitete Budget bereits seine
   Aufgabe erfüllt; eine `pressureSeverity` von `high`/`critical` bedeutet, dass der Host tatsächlich nur noch wenig Speicher hat —
   dies lässt sich nicht über eine Umgebungsvariable für die Zulassungssteuerung beheben, sondern erfordert mehr RAM oder eine kleinere Arbeitslast.
3. Nur wenn `/api/monitoring/health` zeigt, dass das automatisch abgeleitete Budget für
   Ihren Host tatsächlich zu klein ist (selten — es skaliert bereits von Containern bis zu Bare-Metal-Systemen), sollten Sie es direkt mit
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` überschreiben, anstatt auf die veraltete Begrenzung nach Anfrageanzahl zurückzugreifen.

Die maßgeblichen Einstellungen für die Zulassungssteuerung finden Sie in der [Referenz der Umgebungsvariablen](../reference/ENVIRONMENT.md#4-security--authentication).

## Optionale RAG-/LLM-Fehlertaxonomie (16 Probleme)

Einige OmniRoute-Benutzer platzieren das Gateway vor RAG- oder Agenten-Stacks. In solchen Konfigurationen tritt häufig ein merkwürdiges Muster auf: OmniRoute scheint fehlerfrei zu funktionieren (Anbieter verfügbar, Routingprofile in Ordnung, keine Ratenbegrenzungswarnungen), aber die endgültige Antwort ist trotzdem falsch.

In der Praxis gehen diese Vorfälle normalerweise von der nachgelagerten RAG-Pipeline und nicht vom Gateway selbst aus.

Wenn Sie ein gemeinsames Vokabular zur Beschreibung dieser Fehler verwenden möchten, können Sie die WFGY ProblemMap nutzen. Dabei handelt es sich um eine externe, unter der MIT-Lizenz veröffentlichte Textressource, die sechzehn wiederkehrende RAG-/LLM-Fehlermuster definiert. Auf hoher Ebene deckt sie Folgendes ab:

- Abweichungen beim Abruf und fehlerhafte Kontextgrenzen
- leere oder veraltete Indizes und Vektorspeicher
- Diskrepanzen zwischen Einbettungen und Semantik
- Probleme bei der Prompt-Zusammenstellung und mit dem Kontextfenster
- Zusammenbruch der Logik und übermäßig selbstsichere Antworten
- Fehler bei langen Ketten und bei der Koordination von Agenten
- Abweichungen bei Speicher und Rollen in Multi-Agenten-Systemen
- Probleme mit der Reihenfolge von Bereitstellung und Initialisierung

Die Idee ist einfach:

1. Erfassen Sie bei der Untersuchung einer fehlerhaften Antwort Folgendes:
   - Benutzeraufgabe und Anfrage
   - Route oder Anbieterkombination in OmniRoute
   - jeglichen nachgelagert verwendeten RAG-Kontext (abgerufene Dokumente, Tool-Aufrufe usw.)
2. Ordnen Sie den Vorfall einer oder zwei Nummern der WFGY ProblemMap (`No.1` … `No.16`) zu.
3. Speichern Sie die Nummer in Ihrem eigenen Dashboard, Runbook oder Incident-Tracker neben den OmniRoute-Protokollen.
4. Entscheiden Sie anhand der entsprechenden WFGY-Seite, ob Sie Ihren RAG-Stack, Retriever oder Ihre Routingstrategie ändern müssen.

Den vollständigen Text und konkrete Anleitungen finden Sie hier (MIT-Lizenz, nur Text):

[README der WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Sie können diesen Abschnitt ignorieren, wenn Sie hinter OmniRoute keine RAG- oder Agenten-Pipelines betreiben.

## Bekannte Probleme in v3.8.0

Probleme, die speziell die Version v3.8.0 betreffen, sowie die derzeit verfügbaren Umgehungslösungen. Wenn eine Korrektur in einem späteren Patch enthalten ist, wird der Eintrag aktualisiert oder entfernt.

### Authentifizierungsfehler der Devin CLI

**Symptome:**

- „Devin CLI nicht gefunden“ oder „Authentifizierung fehlgeschlagen“ beim Aufrufen von durch Devin unterstützten Tools
- Die CLI-Laufzeitprüfung meldet `installed=false`

**Ursachen:**

- `CLI_DEVIN_BIN` verweist auf einen nicht vorhandenen Pfad
- Devin CLI ist auf dem Host nicht installiert

**Behebung:**

1. Installieren Sie die Devin CLI für Ihre Plattform
2. Setzen Sie in `.env` den Wert `CLI_DEVIN_BIN=/usr/local/bin/devin` (oder den tatsächlichen Pfad)
3. Starten Sie OmniRoute neu und testen Sie erneut über **Dashboard → CLI-Tools**

### Modell-Cooldown bleibt hängen (manuelles Zurücksetzen)

**Symptome:**

- Ein Modell wird auch nach Ablauf der Gültigkeitsdauer weiterhin als im Cooldown befindlich aufgeführt
- Bei Kombinations-Routing werden Anfragen weiterhin am Modell vorbeigeleitet, obwohl der Zeitstempel in der Vergangenheit liegt

**Manuelles Zurücksetzen:**

- **Dashboard:** **Einstellungen → Modell-Cooldowns** → klicken Sie auf der betroffenen Karte auf **Erneut aktivieren**
- **API:** `DELETE /api/resilience/model-cooldowns` mit Management-Authentifizierungs-Headern

### Verbindung zum Command Code-Anbieter schlägt mit 403 fehl

**Symptome:**

- 403 beim Testen der Verbindung zum Command Code-Anbieter
- Die Anbieterkarte zeigt nach dem erneuten Hinzufügen „nicht autorisiert“ an

**Ursache:** Der OAuth-Ablauf wurde nicht abgeschlossen (Callback nicht empfangen oder Token nicht gespeichert).

**Behebung:**

- Führen Sie in der CLI `omniroute providers` aus, um den OAuth-Ablauf erneut auszulösen, oder
- führen Sie OAuth erneut über **Dashboard → Anbieter → Command Code → Erneut verbinden** aus

### ModelScope gibt aggressive 429-Cooldowns zurück

**Symptome:**

- Sehr kurze oder sofortige Cooldowns bei ModelScope nach einer kleinen Serie von Anfragen
- Das Kombinations-Routing überspringt ModelScope früher als erwartet

**Ursache:** ModelScope gibt anbieterspezifische `Retry-After`-Header aus. v3.8.0 enthält eine spezielle Verarbeitung dieser Header, während ältere Versionen sie fälschlicherweise als allgemeine Hinweise zur Ratenbegrenzung interpretieren.

**Behebung:**

- Stellen Sie sicher, dass Sie v3.8.0 oder höher verwenden
- Überprüfen Sie, ob der Schalter `useUpstream429BreakerHints` unter **Einstellungen → Resilienz** aktiviert ist

### OMNIROUTE_WS_BRIDGE_SECRET fehlt in der Produktionsumgebung

**Symptome:**

- 401 bei jeder Codex-/Responses-WebSocket-Bridge-Anfrage, wenn die Anwendung auf einem entfernten Produktionshost ausgeführt wird
- Der WebSocket-Bridge-Handshake wird unmittelbar nach dem Verbindungsaufbau geschlossen

**Ursache:** Die Umgebungsvariable `OMNIROUTE_WS_BRIDGE_SECRET` fehlt in der Produktionsumgebung.

**Behebung:**

1. Generieren Sie ein zufälliges Geheimnis: `openssl rand -hex 32`
2. Setzen Sie `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` in der Umgebung des Produktionsservers (und in jedem Client, der mit der Bridge kommuniziert)
3. Starten Sie OmniRoute neu

### Responses API: Hintergrundmodus auf synchrone Ausführung herabgestuft

**Symptome:**

- Protokollierte Warnung: `background mode degraded to synchronous`
- Eine Anfrage mit `background: true` gibt anstelle eines Handles für einen Hintergrundauftrag eine normale synchrone Antwort zurück

**Ursache:** v3.8.0 stuft `background: true` in der Responses API absichtlich auf eine synchrone Ausführung herab und gibt dabei eine Warnung aus. Die vollständige asynchrone Ausführung im Hintergrund ist für eine zukünftige Version vorgesehen.

**Behebung:**

- Passen Sie den Client so an, dass er den Aufruf ohne `background` ausführt, oder
- warten Sie auf eine spätere Version mit vollständigem asynchronem Hintergrundmodus (siehe Änderungsprotokoll)

## Langsamer Start / Zeitüberschreitung bei der Bereitschaftsprüfung

Wenn die CLI `⚠ Server did not respond within 60s` ausgibt, der Server aber
tatsächlich funktioniert, ist das Zeitbudget der Bereitschaftsprüfung für Ihre Umgebung zu kurz.

Dies tritt häufig unter Windows (Antivirenprogramme, Dateisystem-Watcher) oder in Containern
mit hoher Arbeitslast beim Start auf.

**Lösung — Zeitbudget erhöhen:**

```bash
# Über eine Umgebungsvariable (bleibt über mehrere Starts hinweg bestehen):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 Minuten
omniroute serve

# Über ein CLI-Flag (einmalig):
omniroute serve --ready-timeout 180000
```

Der Standardwert beträgt 60 000 ms (60 s). Die Warnung dient nur zur Information; der Server
wird im Hintergrund weiter gestartet und ist erreichbar, sobald der Startvorgang abgeschlossen ist.

Vollständige Informationen zu `OMNIROUTE_READY_TIMEOUT_MS` finden Sie unter
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
