## Kurzreferenz

**Neu bei OmniRoute?** Beginnen Sie hier — damit lassen sich 90 % aller Probleme lösen:

| Das wird angezeigt             | Bedeutung                                           | Vorgehensweise                                                                                                    |
| ------------------------------ | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| „Verbindung nicht möglich“     | OmniRoute wird nicht ausgeführt                     | Führen Sie `omniroute` oder `docker restart omniroute` aus                                                        |
| „Ungültiger API-Schlüssel“     | Ihr Schlüssel ist falsch oder abgelaufen            | Kopieren Sie den Schlüssel erneut von der Website des Anbieters                                                   |
| „Ratenlimit überschritten“     | Sie senden zu viele Anfragen                        | Warten Sie 1 Minute oder verwenden Sie `model: "auto"` für einen automatischen Fallback                           |
| „Kontingent überschritten“     | Sie haben Ihr kostenloses oder bezahltes Kontingent | Verbinden Sie weitere Anbieter oder verwenden Sie kostenlose Anbieter (Kiro, Pollinations)                        |
| „Langsame Antworten“           | Der Anbieter ist ausgelastet oder weit entfernt     | Verwenden Sie `model: "auto/fast"` oder verbinden Sie einen schnelleren Anbieter (Groq, Cerebras)                 |
| „Falscher Anbieter verwendet“  | `auto` hat einen anderen Anbieter ausgewählt        | Das ist normal! `auto` wählt den besten aus. Erzwingen Sie mit `model: "openai/gpt-4o"` einen bestimmten Anbieter |
| „502 Bad Gateway“              | Der Anbieter ist nicht verfügbar                    | Warten Sie und versuchen Sie es erneut oder verwenden Sie `model: "auto"`, um den Anbieter zu wechseln            |
| „401 Unauthorized“             | Ihre Zugangsdaten sind falsch                       | Überprüfen Sie Ihren API-Schlüssel oder authentifizieren Sie sich erneut über OAuth                               |
| „omniroute wird nicht erkannt“ | Im Windows-PATH fehlen globale node-Module          | Fügen Sie Ihr globales npm-Präfix zum Windows-PATH hinzu. Ermitteln Sie es mit `npm config get prefix`.           |
| „429 Too Many Requests“        | Das Ratenlimit wurde erreicht                       | Warten Sie 1 Minute oder verbinden Sie weitere Anbieter                                                           |

**Problem weiterhin nicht gelöst?** Lesen Sie unten die [detaillierte Fehlerbehebung](#detaillierte-fehlerbehebung) oder fragen Sie auf [Discord](https://discord.gg/U47eFqAXCn).

## Detaillierte Fehlerbehebung

---

### Ratenbegrenzung bei kostenlosen Anbietern (429 / 400 / 401)

**Symptom**: Bei der Verwendung von `model: "auto"` mit kostenlosen bzw. authentifizierungsfreien Anbietern (opencode, auggie usw.) erhalten Sie zeitweise `HTTP 429`, `400` oder `401` anstelle von Antworten. Wenn dieselbe Eingabeaufforderung wenige Augenblicke später erneut gesendet wird, sind die Anfragen erfolgreich, aber Automatisierungen (Cronjobs, Agenten, Skripte) brechen beim ersten Fehler ab.

**Grundursache**: Drei voneinander unabhängige Fehlermodi treten gemeinsam auf:

1. **Ratenlimit des Anbieters (`429`)**: Kostenlose Tarife können ein Kontingent pro Zeitfenster erzwingen. Eine Reihe paralleler Aufrufe schöpft es aus, sodass die nächste Anfrage abgelehnt wird, bis das Zeitfenster zurückgesetzt wird.
2. **Defektes Modell im Passthrough (`400`/`401`)**: `auto/*`-Pools können Passthrough-Modelle von `opencode` enthalten, die im Katalog registriert sind, aber über keine gültigen Zugangsdaten verfügen (z. B. `oc/north-mini-code-free` → `401`). Der automatische Router versucht es mit einem solchen Modell, scheitert, und der Fehler wird weitergegeben, bevor der Fallback greift.
3. **Verstärkung durch Parallelität (`429` unter Last)**: Wenn mehrere Agenten- oder Cron-Sitzungen gleichzeitig auf `auto` zugreifen, übersteigt die aggregierte Anfragerate das von kostenlosen Anbietern tolerierte Maß, sodass legitime Aufrufe als missbräuchlich eingestuft werden.

**Verifizierte Lösung (von der Community gemeldet, 2026-08-10)**: Passen Sie drei Umgebungsvariablen so an, dass Rotation, Parallelität und Fallback die Schwankungen der kostenlosen Tarife abfangen, anstatt daran zu scheitern:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # bei 400/401 zu einem anderen Modell/Anbieter wechseln (überspringt defekte Passthrough-Modelle)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # explizite Obergrenze für die Zulassung rechenintensiver Anfragen (standardmäßig nicht gesetzt: keine Begrenzung der Anfrageanzahl, siehe Hinweis unten)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # die begrenzte Wartezeit für langsame Upstreams über den Standardwert von RATE_LIMIT_MAX_WAIT_MS hinaus erhöhen
```

Legen Sie diese Variablen in der Prozessumgebung von OmniRoute fest (für den Daemon, z. B. über die LaunchAgent-plist oder `systemctl edit`) und starten Sie OmniRoute anschließend neu. Das Rotations-Flag bietet den größten Nutzen: Es wandelt einen endgültigen Fehler in einen transparenten Wiederholungsversuch bei einem funktionierenden Anbieter im Pool um.

**Hinweis**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` begrenzt die Anzahl rechenintensiver Anfragen — also Anfragen mit langem Kontext —, die gleichzeitig ausgeführt werden; diese Begrenzung ist eine Zulassungsschranke und kein Ratenlimit des Anbieters. **#503-Fan-out-Aktualisierung:** Diese Variable wird nicht mehr standardmäßig gesetzt (sie greift jetzt nur, wenn sie wie oben explizit konfiguriert wird) — stattdessen wird die Zulassung rechenintensiver Anfragen über ein automatisch abgeleitetes Byte-Budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) gesteuert, das sich anhand der tatsächlichen Speicherobergrenze des Hosts skaliert. Daher sollte eine neue Bereitstellung deutlich weniger Ablehnungen des Typs `503 chat_admission_busy` verzeichnen, ohne dass diese Variable überhaupt gesetzt wird; wird sie hier explizit gesetzt, funktioniert sie weiterhin genau wie dokumentiert. Explizite Überschreibungen des Byte-Budgets werden auf 8 MiB–2 GiB begrenzt. Ein `413 body_exceeds_budget` ist nicht vorübergehend: Erhöhen Sie dieses Byte-Budget, senken Sie `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` oder erhöhen Sie die Speicherobergrenze des Prozesses. Eine Auslastungsablehnung vom Typ `inflight_bytes_budget` ist ein temporärer Engpass, bei dem ein erneuter Versuch weiterhin möglich ist. Die Ratenbegrenzung pro Anbieter (`open-sse/services/rateLimitManager.ts`) wird separat durch `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` und `RATE_LIMIT_AUTO_ENABLE` gesteuert — siehe `.env.example`.

**So überprüfen Sie, ob es funktioniert hat**: Führen Sie Ihren Agenten/Cronjob zweimal kurz hintereinander aus und vergewissern Sie sich, dass beide Durchläufe erfolgreich sind. Vor der Korrektur gibt der zweite Durchlauf normalerweise einen `429`-/`401`-Fehler aus. Nach der Korrektur werden Fehler (sofern vorhanden) transparent erneut versucht und der Aufruf wird abgeschlossen. Sie können auch `curl /monitoring/health` ausführen und das Feld `rateLimitedUntil` bei den Provider-Verbindungen sowie `circuitBreakers.providerBreakers[].state` für die betroffenen Provider beobachten — der Status ist entweder `CLOSED`, `DEGRADED`, `OPEN` oder `HALF_OPEN` (siehe `src/shared/utils/circuitBreaker.ts`). Ein Provider, bei dem weiterhin Fehler auftreten, wechselt von `CLOSED → DEGRADED → OPEN`, bevor nach Ablauf des Rücksetzzeitfensters eine Testanfrage zugelassen wird (`HALF_OPEN`).

**Falls weiterhin 429-Fehler auftreten**: Das aktive Konto für diesen Provider hat sein _Kontingent_ tatsächlich ausgeschöpft (nicht nur das Ratenlimit erreicht). Fügen Sie im OmniRoute-Dashboard unter → Providers → Accounts ein zweites Konto für denselben Provider hinzu oder binden Sie einen weiteren kostenlosen Provider ein (z. B. `routeway`, `auggie`). Die Rotation hilft nur bei vorübergehenden Ratenlimit-/400-/401-Fehlern; bei einem vollständig ausgeschöpften Kontingent sind zweite Zugangsdaten oder ein anderer Provider erforderlich.

**Falls bei Vision-Modellen (`auto/vision`, `bazaarlink/*`) 403-Fehler auftreten**: Für das verbundene Konto besteht kein kostenpflichtiger Tarif, der Vision-Funktionen umfasst, oder der API-Schlüssel verfügt nicht über ausreichende Berechtigungen. Überprüfen Sie im Provider-Dashboard, ob der Geltungsbereich des Schlüssels Vision/Multimodal umfasst, oder verbinden Sie ein Konto mit kostenpflichtigem Tarif und behalten Sie dieses als Vision-Ziel bei.

## Warnungen bei npm install (ERESOLVE / Peer-Abhängigkeiten / veraltet)

Wenn Sie `npm install -g omniroute` ausführen, sehen Sie möglicherweise eine ganze Reihe von Warnungen wie `npm warn ERESOLVE`, Hinweise zu Peer-Abhängigkeiten und `deprecated`-Meldungen. **Diese sind zu erwarten und harmlos.** Ihre Installation war erfolgreich, wenn in der Ausgabe `added <N> packages` angezeigt wird.

Um die Warnungen zur Auflösung von Peer-Abhängigkeiten zu unterdrücken, verwenden Sie die von OmniRoute unterstützte Installationsform:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` unterdrückt ausschließlich `ERESOLVE`- und Peer-Abhängigkeitshinweise. Hinweise zu veralteten Paketen bleiben sichtbar, da sie von transitiven Drittanbieterpaketen stammen; sie bedeuten nicht, dass die Installation fehlgeschlagen ist.

Die Warnungen stammen von veralteten Peer-Abhängigkeitsbereichen in Drittanbieterpaketen, auf die OmniRoute keinen Einfluss hat:

1. **`marked-terminal` erfordert `marked >=1 <16`, gefunden wurde `marked@18`** — funktioniert in der Praxis problemlos; der Peer-Abhängigkeitsbereich des Upstream-Pakets ist lediglich veraltet.
2. **`deprecated prebuild-install@7.1.3`** — ein transitives Hilfsprogramm zum Abrufen nativer Binärdateien. Es wird nicht
   zur Installation der festgelegten `wreq-js`-Transportbindung verwendet und bedeutet nicht, dass die Einrichtung des
   Transports für den Web-Cookie-Anbieter fehlgeschlagen ist.

**Keine Maßnahme erforderlich** — die Warnungen lassen sich ohne einen Fork der Upstream-Pakete nicht vollständig unterdrücken.

## Warnung zu blockierten npm-Installationsskripten (globale Installation)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

Beim Ausführen von `npm install -g omniroute` blockieren neuere npm-Versionen (v11+ und v12+) standardmäßig Paket-Lebenszyklusskripte und zeigen eine Warnung zu Installationsskripten an:

```
npm warn install-scripts 7 Pakete hatten blockierte Installationsskripte, da sie nicht von allowScripts abgedeckt sind:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Kann diese Warnung ignoriert werden?

**Teilweise, aber die Ausführung ohne Skripte wird nicht empfohlen.** OmniRoute enthält robuste Rückfallmechanismen: Wenn native `better-sqlite3`-Bindungen nicht aus dem eigenständigen Bundle geladen werden können, greift die Anwendung auf alternative Treiber wie `node:sqlite` oder `sql.js` zurück (siehe [SQLite-Laufzeitauflösung](../ops/SQLITE_RUNTIME.md)). Der Server startet weiterhin, aber bei der Verwendung von WASM-Rückfalllösungen wie `sql.js` wird der SQLite-WAL-Modus (Write-Ahead Logging) deaktiviert und der Speicherbedarf sowie der Aufwand für die Datenträgersynchronisierung steigen.

### Welche Skripte sind tatsächlich erforderlich?

Nicht alle blockierten Skripte sind für die Ausführung von OmniRoute erforderlich:

- **Erforderlich (`omniroute`, `better-sqlite3`):** OmniRoute wird aus einem eigenständigen Next.js-Anwendungs-Bundle (`dist/`) ausgeführt. Während der Installation lädt npm den hostspezifischen nativen SQLite-Treiber in das übergeordnete Verzeichnis `node_modules/better-sqlite3/` herunter oder kompiliert ihn. Das `postinstall`-Skript von OmniRoute (`scripts/build/postinstall.mjs`) überprüft anschließend diese hostspezifischen Binärdateien und kopiert sie nach `dist/node_modules/`, damit der eigenständige Server darauf zugreifen kann. Wenn das postinstall-Skript von `omniroute` blockiert ist, wird dieser Kopierschritt übersprungen.
- **Optional/transitiv (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** Dabei handelt es sich um Build-Hilfsprogramme, Überwachungswerkzeuge oder Dienstprogramme für den System-Schlüsselbund. Ihre Zulassung verhindert Build-Warnungen, sie sind jedoch nicht für die grundlegende Routing-Funktionalität erforderlich.
- **Ausgeschlossen (`onnxruntime-node`):** Eine optionale Abhängigkeit für lokale KI-Einbettungen, die für die Ausführung von OmniRoute **nicht** erforderlich ist. Ihr postinstall-Skript lädt etwa 300 MB an CUDA-Ressourcen von NuGet herunter; nehmen Sie sie nur dann in die Zulassungsliste auf, wenn Sie ausdrücklich beabsichtigen, lokale ONNX-Beschleunigung auf unterstützter Hardware zu verwenden.

### Empfohlene Lösung

Um die erforderlichen Installationsskripte während einer globalen Installation zuzulassen und Warnungen zu unterdrücken, übergeben Sie `--allow-scripts` für OmniRoute und seine nativen Abhängigkeiten:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

Alternativ können Sie dies dauerhaft für alle globalen Installationen Ihres Benutzerkontos konfigurieren:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### Überprüfen Ihrer Installation

Führen Sie nach der Installation das integrierte Diagnosewerkzeug aus, um sicherzustellen, dass die nativen Bindungen und die Laufzeitumgebung ordnungsgemäß funktionieren:

```bash
omniroute doctor
```

## Gemini Web und Playwright Chromium

Wenn eine Gemini-Web-Anfrage den Status `503` mit einer Meldung zurückgibt, dass Playwright Chromium
nicht installiert ist, ist das npm-Paket vorhanden, aber die Browser-Binärdatei fehlt.
Playwright hält Browser-Downloads bewusst von der Installation des npm-Pakets
getrennt. Daher ist diese Antwort zu erwarten, bis der Browser installiert wurde.

Installieren Sie Chromium bei einer globalen npm-Installation aus dem Verzeichnis des
OmniRoute-Pakets, damit der Browser-Cache zur selben Playwright-Installation gehört:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Starten Sie OmniRoute nach der Installation neu und wiederholen Sie anschließend die Gemini-Web-Anfrage. Wenn Sie
OmniRoute über ein Docker-Image ausführen, verwenden Sie das `-web`-Image (oder das Build-Ziel
`runner-web`), das Chromium und seine Abhängigkeiten enthält. Das Basis-Image enthält
diese nicht.

## Fehlalarme von Antivirenprogrammen

<a name="antivirus-false-positives"></a>

### Avast/AVG verschiebt `README.md` wegen `MD:HttpRequest-inf[Susp]` in Quarantäne

**Dies ist ein Fehlalarm. Nichts ist infiziert und es sind keine Maßnahmen erforderlich.**

Avast und AVG verwenden eine Heuristik, die Klartext-/Markdown-Dateien kennzeichnet, die viele
Links enthalten, welche wie HTTP-Anfragen aussehen. Die `README.md` von OmniRoute wird im npm-Paket mitgeliefert (sie ist
in `package.json` → `files` aufgeführt), sodass sie bei einer globalen Installation unter
`node_modules/omniroute/README.md` landet — und sie enthält etwa 15 Beispiele mit `http://localhost:20128/...`
(die MCP-HTTP-/SSE-Endpunkte, die A2A-URL unter `.well-known` und `curl`-Ausschnitte). Diese Linkdichte
reicht aus, um die Heuristik auszulösen.

Falls dies erst seit Kurzem auftritt: Die Art der Datei hat sich nicht geändert. Die Endpunkttabelle
in der README wurde erweitert (MCP HTTP + SSE + A2A wurden hinzugefügt), ebenso kamen weitere `curl`-Beispiele hinzu,
wodurch der Schwellenwert überschritten wurde.

Bei der Datei handelt es sich um inaktive Dokumentation ohne ausführbare Inhalte. Sie können sie
bedenkenlos aus der Quarantäne wiederherstellen.

**Was zu tun ist:**

1. **Benachrichtigungen unterbinden** — schließen Sie das Installationsverzeichnis in Ihrem Antivirenprogramm aus
   (Avast: Einstellungen → Ausnahmen), indem Sie den Pfad zu Ihrem globalen `node_modules` und/oder das
   OmniRoute-Datenverzeichnis (`~/.omniroute/`) hinzufügen.
2. **Den Fehlalarm melden** — <https://www.avast.com/false-positive-file-form.php>;
   hängen Sie dabei die unter Quarantäne gestellte `README.md` an. Dies ist die Lösung, die allen hilft, da hier
   die Heuristik des Anbieters übermäßig auf eine Textdatei reagiert.

**Warum wir dies nicht auf unserer Seite „beheben“:** Alle Beispiele verwenden `http://localhost`, und
localhost kann nicht ohne den zusätzlichen Aufwand selbstsignierter Zertifikate `https` verwenden. Die Dokumentation zu
verunstalten, um die Heuristik eines einzelnen Anbieters zu umgehen, würde allen Lesern schaden, nur um einen Scannerfehler zufriedenzustellen.

### Kaspersky kennzeichnet die Desktop-App als `PDM:Trojan.Win32.Generic`

**Dies ist ein Fehlalarm einer verhaltensbasierten Heuristik. Nichts ist infiziert.** Das Präfix
`PDM:` von Kaspersky bedeutet, dass die Erkennung von dessen Proactive Defense Module (System Watcher)
stammt, das bewertet, was das Installationsprogramm _tut_, statt es mit bekannter Schadsoftware abzugleichen. Wenn
die Erkennung ausgelöst wird, macht Kaspersky die gesamte Installation „rückgängig“ — einschließlich des Löschens bereits
geschriebener Dateien —, sodass die App anschließend beschädigt ist oder fehlt.

Die gekennzeichneten Dateien sind unveränderte Bestandteile deklarierter Open-Source-Abhängigkeiten, die mit der
Desktop-App gebündelt werden, beispielsweise:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` und
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), die Browserautomatisierungsbibliothek,
  die für die Anmeldung bei Anbietern innerhalb der App sowie für browsergestützte Chats verwendet wird.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — die fest vorgegebene native `wreq-js`-Bindung, die für HTTP mit Browser-Fingerprinting bei Web-Cookie-
  Anbietern verwendet wird (`<arch>` ist `x64` oder `arm64`).

**Warum die Erkennung ausgelöst wird:** Das Windows-Installationsprogramm ist **noch nicht codesigniert**, sodass ein unsigniertes NSIS-
Installationsprogramm keinerlei Reputation besitzt und verhaltensbasierte Heuristiken mit maximaler Aggressivität ausgeführt werden. In Kombination
mit einer gebündelten nativen DLL und Hunderten von `.js`-Dateien, die unter
`%LOCALAPPDATA%\Programs\OmniRoute` geschrieben werden (einschließlich Paketverzeichnissen mit Hash-Suffix aus dem
eigenständigen Next.js-Build), reicht dies aus, um die Heuristik auszulösen. Eine Codesignierung ist geplant;
bis sie umgesetzt ist, kann dies bei neuen Versionen erneut auftreten.

**Was zu tun ist:**

1. **Überprüfen Sie zuerst Ihren Download** (dies schließt eine manipulierte Datei aus). Jede Version veröffentlicht
   `latest.yml`, deren Feld `sha512` (base64) das Installationsprogramm `OmniRoute.Setup.<version>.exe`
   abdeckt. Führen Sie in PowerShell im Ordner, der das Installationsprogramm enthält, Folgendes aus:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Die Ausgabe muss mit `latest.yml` → `sha512` übereinstimmen. Ist dies nicht der Fall, löschen Sie die Datei und
   laden Sie sie ausschließlich von der [GitHub-Releases-Seite](https://github.com/diegosouzapw/OmniRoute/releases) erneut herunter.
2. **Wiederherstellen + ausschließen** — stellen Sie die rückgängig gemachten Elemente aus der Quarantäne wieder her und fügen Sie einen Ausschluss
   für `%LOCALAPPDATA%\Programs\OmniRoute` hinzu (Kaspersky → Einstellungen → Bedrohungen und Ausnahmen);
   installieren Sie die Anwendung anschließend erneut.
3. **Den Fehlalarm melden** — <https://opentip.kaspersky.com/>. Von Benutzern eingereichte Meldungen zu Fehlalarmen
   beschleunigen die Aufnahme in die Positivliste tatsächlich.

## Node.js-Kompatibilität

<a name="nodejs-compatibility"></a>

### Anmeldeseite stürzt ab oder zeigt den Fehler „Module self-registration“ an

**Ursache:** Sie verwenden eine Node.js-Version außerhalb der von OmniRoute freigegebenen sicheren Laufzeitversionen. Der häufigste Fall ist die Verwendung einer älteren Patch-Version von Node 22 oder 24, die unter der von OmniRoute vorausgesetzten gepatchten Sicherheitsversion liegt.

**Symptome:**

- Die Anmeldeseite zeigt einen leeren Bildschirm oder einen Serverfehler an
- Die Konsole zeigt `Error: Module did not self-register` oder ähnliche Fehler nativer Bindings an
- Die Anmeldeseite zeigt ein **orangefarbenes Warnbanner** mit Ihrer Node-Version an, wenn die Laufzeitumgebung außerhalb der unterstützten Sicherheitsrichtlinie liegt

**Behebung:**

1. Installieren Sie eine unterstützte Node.js-LTS-Version (empfohlen: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Überprüfen Sie Ihre Version: `node --version` sollte in der 24.x-LTS-Reihe `v24.0.0` oder neuer anzeigen
3. Installieren Sie OmniRoute erneut: `npm install -g omniroute`
4. Starten Sie neu: `omniroute`

> **Unterstützte sichere Versionen:** `>=22.22.2 <23` oder `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) und Node.js 26 werden vollständig unterstützt.

### npm v11+: `better-sqlite3` nicht installiert (Modul kann nicht gefunden werden)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Ursache:** npm v11 (im Lieferumfang von Node.js 24+) blockiert standardmäßig Installationsskripte für optionale
Abhängigkeiten. Da `better-sqlite3` unter `optionalDependencies` aufgeführt ist
und eine native Kompilierung (`node-gyp rebuild`) erfordert, überspringt npm es ohne Meldung.

**Symptome:**

- Der Server stürzt beim Start mit `Cannot find module 'better-sqlite3'` ab
- `ls node_modules/better-sqlite3` zeigt „No such file or directory“ an
- `npm ls better-sqlite3` zeigt `(empty)` an

**Behebung:**

1. Genehmigen Sie die Installationsskripte und installieren Sie erneut:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Oder installieren Sie das vorkompilierte Paket manuell:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Überprüfen Sie die Funktionsfähigkeit: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file“

<a name="macos-native-module-rebuild"></a>

**Ursache:** Nach einem globalen `npm install -g omniroute` wurde die native Binärdatei von `better-sqlite3` innerhalb des Pakets möglicherweise für eine andere Architektur oder Node.js-ABI kompiliert als die lokal ausgeführte. Dies tritt unter macOS (sowohl Apple Silicon als auch Intel) häufig auf, wenn die vorkompilierte Binärdatei nicht zu Ihrer Umgebung passt.

**Symptome:**

- Der Server schlägt unmittelbar beim Start mit einem `dlopen`-Fehler fehl
- Der Fehler enthält `slice is not valid mach-o file`
- Vollständiges Beispiel:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Behebung — für Ihre lokale Umgebung neu kompilieren (kein Node.js-Downgrade erforderlich):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Hinweis:** Dadurch wird das native Binding für Ihre lokale Node.js-Version und CPU-Architektur neu kompiliert und die Binärinkompatibilität behoben. Der offiziell unterstützte Laufzeitbereich ist **`>=22.22.2 <23` oder `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` in `src/shared/utils/nodeRuntimeSupport.ts`, abgestimmt auf das Feld `engines` in `package.json`). Node.js 24.x LTS (Krypton) und Node.js 26 werden mit `better-sqlite3` v12.x vollständig unterstützt.

## Proxy-Probleme

<a name="proxy-issues"></a>

### Bei der Anbieterüberprüfung wird „fetch failed“ angezeigt

**Ursache:** Der Endpunkt zur Validierung des API-Schlüssels (`POST /api/providers/validate`) hat zuvor die Proxy-Konfiguration umgangen, wodurch es in Umgebungen, die Proxy-Routing erfordern, zu Fehlern kam.

**Lösung (v3.5.5+):** Dies ist jetzt behoben. Die Anbieterüberprüfung wird über `runWithProxyContext` geleitet, wobei die Proxy-Einstellungen auf Anbieter- und globaler Ebene automatisch berücksichtigt werden.

### Die Token-Zustandsprüfung schlägt mit „fetch failed“ fehl

**Ursache:** Bei der OAuth-Token-Aktualisierung im Hintergrund wurde die Proxy-Konfiguration nicht für jede Verbindung separat aufgelöst.

**Lösung (v3.5.5+):** Der Scheduler für die Token-Zustandsprüfung löst jetzt vor dem Aktualisierungsversuch die Proxy-Konfiguration für jede Verbindung separat auf. Aktualisieren Sie auf v3.5.5+.

### SOCKS5-Proxy gibt „invalid onRequestStart method“ zurück

**Ursache:** Unter Node.js 22 ist der Dispatcher von undici@8 nicht mit der integrierten `fetch()`-Implementierung von Node kompatibel.

**Lösung (v3.5.5+):** OmniRoute verwendet jetzt die eigene `fetch()`-Funktion von undici, wenn ein Proxy-Dispatcher aktiv ist, um ein konsistentes Verhalten sicherzustellen. Aktualisieren Sie auf v3.5.5+.

### MITM-Proxy unter WSL: Desktop-Apps auf dem Windows-Host werden nicht abgefangen

**Ursache:** Der MITM-Proxy und sein CA-Zertifikat werden in der Umgebung installiert, in der OmniRoute ausgeführt wird. Unter WSL ist diese Umgebung das Linux-Gastsystem, während die KI-Desktop-Apps (Kiro, Trae, Copilot, Zed, …) auf dem Windows-Host ausgeführt werden. Die Host-Apps vertrauen dem Zertifikatsspeicher des Gastsystems nicht und leiten ihren Datenverkehr nicht über den System-Proxy des Gastsystems. Daher erfolgt dort keine Überwachung des Desktop-Datenverkehrs.

**Empfehlung:** Führen Sie OmniRoute nativ auf demselben Betriebssystem aus wie die Desktop-Apps, deren Datenverkehr Sie abfangen möchten (Windows für Windows-Apps; entsprechend macOS/Linux). Wenn Sie OmniRoute innerhalb von WSL belassen und gleichzeitig auf Host-Apps abzielen, müssen Sie dem generierten CA-Zertifikat auf dem Windows-Host manuell vertrauen und die Netzwerk-/Proxy-Einstellungen jeder Host-App auf den WSL-Proxy-Endpunkt verweisen lassen. Dies ist eine nicht unterstützte und fehleranfällige Konfiguration.

## Anbieterprobleme

### „Language model did not provide messages“

**Ursache:** Das Anbieterkontingent ist ausgeschöpft.

**Lösung:**

1. Kontingentanzeige im Dashboard prüfen
2. Eine Kombination mit Ausweichstufen verwenden
3. Zu einer günstigeren/kostenlosen Stufe wechseln

### Ratenbegrenzung

**Ursache:** Das Abonnementkontingent ist ausgeschöpft.

**Lösung:**

- Ausweichoption hinzufügen: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- GLM/MiniMax als günstige Reserve verwenden

### OAuth-Token abgelaufen

OmniRoute aktualisiert Token automatisch. Falls die Probleme weiterhin bestehen:

1. Dashboard → Anbieter → Erneut verbinden
2. Die Anbieterverbindung löschen und erneut hinzufügen

### Kiro mit mehreren Konten: Das zweite Konto macht das erste ungültig

**Ursache:** Das Backend von Kiro erzwingt eine einzige aktive Sitzung pro OIDC-Client-Registrierung.
Wenn zwei Konten denselben registrierten Client verwenden (Verbindungen, die vor v3.8.0 importiert wurden),
macht die Aktualisierung des Tokens eines Kontos das Aktualisierungstoken des anderen ungültig.

**Lösung (v3.8.0+):** Importieren Sie die betroffenen Verbindungen erneut.
Ab v3.8.0 registriert jede neue Kiro-Verbindung, die über **Token importieren**,
**soziale Anmeldung mit Google/GitHub** oder **automatischen Import** erstellt wird, automatisch einen eigenen
dedizierten OIDC-Client. Dadurch ist die Verbindung vollständig isoliert, und die Aktualisierung eines
Kontos hat keine Auswirkungen auf andere Konten.

Verbindungen, die _vor_ v3.8.0 importiert wurden, verfügen nicht über eine Client-Registrierung
pro Verbindung. Diese Verbindungen verwenden weiterhin den gemeinsamen Endpunkt zur Aktualisierung der Anmeldung über soziale Netzwerke.
Um die Isolierung zu erhalten, löschen Sie die alte Verbindung unter Dashboard → Anbieter und fügen Sie sie
über einen der drei Importabläufe erneut hinzu.

Ausführliche Informationen und Schritt-für-Schritt-Anweisungen zum parallelen Hinzufügen zweier Kiro-Konten
finden Sie unter [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Cloud-Probleme

### Cloud-Synchronisierungsfehler

1. Stellen Sie sicher, dass `BASE_URL` auf Ihre laufende Instanz verweist (z. B. `http://localhost:20128`)
2. Stellen Sie sicher, dass `CLOUD_URL` auf Ihren Cloud-Endpunkt verweist (z. B. `https://omniroute.dev`)
3. Halten Sie die `NEXT_PUBLIC_*`-Werte mit den serverseitigen Werten synchron

### Cloud gibt bei `stream=false` den Status 500 zurück

**Symptom:** `Unexpected token 'd'...` am Cloud-Endpunkt bei Nicht-Streaming-Aufrufen.

**Ursache:** Der Upstream gibt eine SSE-Nutzlast zurück, während der Client JSON erwartet.

**Problemumgehung:** Verwenden Sie `stream=true` für direkte Cloud-Aufrufe. Die lokale Laufzeitumgebung enthält einen SSE→JSON-Fallback.

### Cloud zeigt „Verbunden“ an, meldet aber „Ungültiger API-Schlüssel“

1. Erstellen Sie im lokalen Dashboard einen neuen Schlüssel (`/api/keys`)
2. Führen Sie die Cloud-Synchronisierung aus: Cloud aktivieren → Jetzt synchronisieren
3. Alte oder nicht synchronisierte Schlüssel können in der Cloud weiterhin `401` zurückgeben

## Docker-Probleme

### Docker-IPv6-/Verbindungsabbruch

<a name="docker-ipv6"></a>

**Symptome:** `curl http://localhost:20128/v1/models` gibt `curl: (56) Recv failure: Connection reset by peer` zurück. Das Dashboard und nicht authentifizierte Endpunkte funktionieren, authentifizierte Endpunkte schlagen jedoch fehl – es sieht wie ein Authentifizierungsproblem aus, ist aber keines.

**Ursache:** `docker run -p 20128:20128` veröffentlicht sowohl auf `0.0.0.0` (IPv4) als auch auf `::` (IPv6), aber der Prozess im Container lauscht nur auf IPv4. Auf Hosts, auf denen `localhost` zuerst zu `::1` aufgelöst wird, erreicht die Verbindung den veröffentlichten IPv6-Port, hinter dem kein Listener aktiv ist → Verbindungsabbruch.

**Behebung:**

1. **Schnelldiagnose:** Führen Sie `curl -4 http://localhost:20128/v1/models` aus. Wenn es mit `-4` funktioniert, ohne diese Option jedoch fehlschlägt, liegt eine IPv6-Bindungsabweichung vor.
2. **Dauerhafte Behebung:** Binden Sie explizit an IPv4, indem Sie `-p 127.0.0.1:20128:20128` in Ihrem `docker run`-Befehl verwenden:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Dadurch wird die IPv4-Bindung erzwungen und zugleich vermieden, dass der Proxy auf allen Host-Schnittstellen erreichbar ist.

### CLI-Tool wird als nicht installiert angezeigt

## Probleme mit dem Circuit Breaker

### Anbieter verbleibt im Zustand OPEN

Wenn sich der Circuit Breaker eines Anbieters im Zustand OPEN befindet, werden Anfragen blockiert, bis die Abklingzeit abgelaufen ist.

**Behebung:**

1. Navigieren Sie zu **Dashboard → Settings → Resilience**
2. Überprüfen Sie die Circuit-Breaker-Karte des betroffenen Anbieters
3. Klicken Sie auf **Reset All**, um alle Circuit Breaker zurückzusetzen, oder warten Sie, bis die Abklingzeit abgelaufen ist
4. Stellen Sie vor dem Zurücksetzen sicher, dass der Anbieter tatsächlich verfügbar ist

### Anbieter löst den Circuit Breaker wiederholt aus

Wenn ein Anbieter wiederholt in den Zustand OPEN wechselt:

1. Überprüfen Sie unter **Dashboard → Health → Provider Health** das Fehlermuster
2. Navigieren Sie zu **Settings → Resilience → Provider Profiles** und erhöhen Sie den Fehlerschwellenwert
3. Prüfen Sie, ob der Anbieter seine API-Limits geändert hat oder eine erneute Authentifizierung erforderlich ist
4. Überprüfen Sie die Latenztelemetrie — eine hohe Latenz kann zu zeitüberschreitungsbedingten Fehlern führen

## Fehlerbehebung im Translator

Verwenden Sie **Dashboard → Translator**, um Probleme bei der Formatübersetzung zu untersuchen:

| Modus            | Verwendungszweck                                                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **Playground**   | Ein- und Ausgabeformate nebeneinander vergleichen — fügen Sie eine fehlerhafte Anfrage ein, um deren Übersetzung zu sehen |
| **Chat Tester**  | Live-Nachrichten senden und die vollständigen Anfrage-/Antwort-Nutzdaten einschließlich Header untersuchen                |

### Häufige Formatprobleme

- **Thinking-Tags werden nicht angezeigt** — Prüfen Sie, ob der Zielanbieter Thinking unterstützt, und kontrollieren Sie die Einstellung für das Thinking-Budget
- **Tool-Aufrufe gehen verloren** — Bei manchen Formatübersetzungen werden möglicherweise nicht unterstützte Felder entfernt; überprüfen Sie dies im Playground-Modus
- **System-Prompt fehlt** — Claude und Gemini verarbeiten System-Prompts unterschiedlich; überprüfen Sie die Übersetzungsausgabe
- **SDK gibt anstelle eines Objekts einen unformatierten String zurück** — In v1.x behoben; die Antwortbereinigung entfernt nicht standardmäßige Felder (`x_groq`, `usage_breakdown` usw.), die zu Fehlern bei der Pydantic-Validierung des OpenAI SDK führen. Wenn dieses Problem unter v3.x+ weiterhin auftritt, erstellen Sie bitte einen Issue.
- **GLM/ERNIE lehnt die Rolle `system` ab** — In v1.x behoben; die Rollennormalisierung führt Systemnachrichten bei inkompatiblen Modellen automatisch mit Benutzernachrichten zusammen. Wenn dieses Problem unter v3.x+ weiterhin auftritt, erstellen Sie bitte einen Issue.
- **Rolle `developer` wird nicht erkannt** — In v1.x behoben; für Nicht-OpenAI-Anbieter wird sie automatisch in `system` umgewandelt. Wenn dieses Problem unter v3.x+ weiterhin auftritt, erstellen Sie bitte einen Issue.
- **`json_schema` funktioniert nicht mit Gemini** — In v1.x behoben; `response_format` wird jetzt in Geminis `responseMimeType` + `responseSchema` umgewandelt. Wenn dieses Problem unter v3.x+ weiterhin auftritt, erstellen Sie bitte einen Issue.

## Resilienz-Einstellungen

### Automatische Ratenbegrenzung wird nicht ausgelöst

- Die automatische Ratenbegrenzung gilt nur für Anbieter mit API-Schlüsseln (nicht für OAuth/Abonnements)
- Überprüfen Sie, ob unter **Einstellungen → Resilienz → Anbieterprofile** die automatische Ratenbegrenzung aktiviert ist
- Prüfen Sie, ob der Anbieter `429`-Statuscodes oder `Retry-After`-Header zurückgibt

### Exponentiellen Backoff abstimmen

Anbieterprofile unterstützen diese Einstellungen:

- **Basisverzögerung** — Anfängliche Wartezeit nach dem ersten Fehler (Standard: 1s)
- **Maximale Verzögerung** — Obergrenze der maximalen Wartezeit (Standard: 30s)
- **Multiplikator** — Maß, um das die Verzögerung pro aufeinanderfolgendem Fehler erhöht wird (Standard: 2x)

### Vermeidung des Thundering-Herd-Problems

Wenn viele gleichzeitige Anfragen auf einen ratenbegrenzten Anbieter treffen, verwendet OmniRoute Mutex + automatische Ratenbegrenzung, um Anfragen zu serialisieren und kaskadierende Fehler zu verhindern. Dies geschieht bei Anbietern mit API-Schlüsseln automatisch.

### Chat-Anfragen schlagen mit 503 / chat_admission_busy fehl

**Symptome:**

- Der Endpunkt für Chat-Vervollständigungen gibt eine wiederholbare `503`-Antwort zurück, deren Fehlercode
  `chat_admission_busy` lautet.
- Die Antwort enthält `Retry-After`. Seit #12135 wird der Wert aus der beobachteten
  Auslastung abgeleitet — dem größeren Wert aus dem Fenster `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`, das die Anfrage bereits
  gewartet hat, und der Dauer, für die die aktuellen Schwergewicht-Leases gehalten wurden — auf ganze
  Sekunden aufgerundet und auf 60 begrenzt. Bei einem inaktiven Gate gelten weiterhin die bisherigen Untergrenzen: 2 Sekunden beim
  bytebasierten Pfad, 1 Sekunde beim strukturbasierten Pfad (der außerdem
  `reason: "structure_limit"` enthält).
- Dies kann auftreten, während sich ein anderer Schwergewicht-Chat oder eine lang laufende Streaming-Antwort noch
  in Bearbeitung befindet.

Der bytebasierte Antworttext lautet:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Die strukturbasierte Antwort verwendet denselben Typ und Code, mit der Meldung
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
und `reason: "structure_limit"`.
Bei den Standardschwellenwerten gilt eine Anfrage als strukturell schwergewichtig, wenn sie mindestens `200` Nachrichten,
mindestens `64` Tools oder mindestens `32,000` geschätzte Token enthält oder wenn die begrenzte Strukturschätzung
ihre Grenzen von `10,000` besuchten Knoten oder einer Tiefe von `12` ausschöpft.

**Ursache:** Dies ist eine beabsichtigte Lastabweisung innerhalb von OmniRoute und kein Fehler eines Upstream-Anbieters.
Jeder Prozess verwendet eine prozesslokale Schutzvorrichtung, um begrenzte Schwergewicht-Kapazität zu reservieren, bevor
ein großer Anfrageinhalt vorgehalten und analysiert wird. Eine Schwergewicht-Lease bleibt während der gesamten Lebensdauer einer SSE-
Antwort bestehen.

**#503-Fan-out:** Vor dieser Korrektur begrenzte die Schutzvorrichtung die Nebenläufigkeit unabhängig vom Host-Arbeitsspeicher auf eine feste AnfrageANZAHL
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, Standard `1`), sodass Fan-out von Coding-Agenten
(mehrere Subagenten/CLIs, Anfrageinhalte routinemäßig > 256 KB) auf eine effektive
Nebenläufigkeit von ~1 einbrach und unter völlig normaler Last zu 503-Fehlern führte. Die Schutzvorrichtung stimmt sich nun selbst ab: Sie wird
durch ein automatisch abgeleitetes BYTE-Budget für die Aufnahme (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) gesteuert, dessen Größe sich nach der
tatsächlichen Speicherobergrenze des Prozesses richtet, und berücksichtigt außerdem ein Live-Signal zum Ressourcendruck — sodass sie
nur Last abweist, wenn der Host tatsächlich unter Speicherdruck steht, und nicht lediglich, weil mehr als eine
schwergewichtige Anfrage gleichzeitig eingegangen ist. Die alte Anzahlbegrenzung (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) wird
weiterhin berücksichtigt, aber nur, wenn Sie sie ausdrücklich festlegen.

Wenn die Kapazität ausgelastet ist, wartet eine schwergewichtige Anfrage zunächst bis zu
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (standardmäßig `RATE_LIMIT_MAX_WAIT_MS`; `0` deaktiviert das Warten) darauf, dass ein Platz frei wird,
bevor mit dem wiederholbaren `503` geantwortet wird. Die begrenzte Wartezeit sorgt dafür, dass agentenartige Clients
(OpenCode, Claude Code, Cursor), die gleichzeitig schwergewichtige Unteranfragen per Fan-out senden, den Laststoß serialisieren,
anstatt ihr gesamtes Wiederholungsbudget durch sofortige Ablehnungen aufzubrauchen und mitten in der Aufgabe abzubrechen.
Die aktuelle Belegung durch Schwergewicht-Leases, das aufgelöste Byte-Budget und der aktuelle Schweregrad des Ressourcendrucks werden
unter `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) angezeigt — prüfen Sie diese Werte, bevor Sie eine Umgebungsvariable ändern.
Einstellungen → Resilienz → Anfragewarteschlange → Gleichzeitige Anfragen steuert dies nicht; diese Einstellung
regelt einen separaten Warteschlangenmechanismus für Anbieteranfragen.

**Lösung:**

1. Versuchen Sie es zunächst erneut. Clients sollten `Retry-After` beachten und Backoff verwenden, anstatt die Anfrage sofort
   zu wiederholen.
2. Prüfen Sie `/api/monitoring/health` → `chatAdmission`, bevor Sie etwas abstimmen. `countCapEnabled:
false` und ein großzügiger Wert für `maxInflightBytes` bedeuten, dass das automatisch abgeleitete Budget bereits ordnungsgemäß
   funktioniert; ein `pressureSeverity`-Wert von `high`/`critical` bedeutet, dass der Host tatsächlich nur noch wenig Arbeitsspeicher hat —
   dies lässt sich nicht mit einer Umgebungsvariable für die Zulassung beheben, sondern erfordert mehr RAM oder eine kleinere Arbeitslast.
3. Nur wenn `/api/monitoring/health` zeigt, dass das automatisch abgeleitete Budget für
   Ihren Host tatsächlich zu klein ist (selten — es skaliert bereits von Containern bis zu Bare-Metal-Systemen), sollten Sie es direkt mit
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` überschreiben, anstatt auf die veraltete Begrenzung der Anfrageanzahl zurückzugreifen.

Die maßgeblichen Zulassungseinstellungen finden Sie in der [Referenz zu Umgebungsvariablen](../reference/ENVIRONMENT.md#4-security--authentication).

## Optionale RAG-/LLM-Fehlertaxonomie (16 Probleme)

Einige OmniRoute-Benutzer platzieren das Gateway vor RAG- oder Agenten-Stacks. In solchen Konfigurationen tritt häufig ein ungewöhnliches Muster auf: OmniRoute scheint fehlerfrei zu funktionieren (Provider verfügbar, Routing-Profile in Ordnung, keine Ratenbegrenzungswarnungen), aber die endgültige Antwort ist dennoch falsch.

In der Praxis gehen diese Vorfälle normalerweise von der nachgelagerten RAG-Pipeline und nicht vom Gateway selbst aus.

Wenn Sie ein gemeinsames Vokabular zur Beschreibung dieser Fehler verwenden möchten, können Sie die WFGY ProblemMap nutzen. Dabei handelt es sich um eine externe Textressource unter MIT-Lizenz, die sechzehn wiederkehrende RAG-/LLM-Fehlermuster definiert. Auf hoher Ebene deckt sie Folgendes ab:

- Retrieval-Drift und fehlerhafte Kontextgrenzen
- leere oder veraltete Indizes und Vektorspeicher
- Diskrepanzen zwischen Embeddings und Semantik
- Probleme bei der Prompt-Zusammenstellung und mit dem Kontextfenster
- Logikzusammenbruch und übermäßig selbstsichere Antworten
- Fehler bei langen Ketten und der Agentenkoordination
- Speicher- und Rollen-Drift bei mehreren Agenten
- Probleme bei der Deployment- und Bootstrap-Reihenfolge

Die Vorgehensweise ist einfach:

1. Erfassen Sie bei der Untersuchung einer fehlerhaften Antwort Folgendes:
   - Benutzeraufgabe und Anfrage
   - Route oder Provider-Kombination in OmniRoute
   - jeglichen nachgelagert verwendeten RAG-Kontext (abgerufene Dokumente, Tool-Aufrufe usw.)
2. Ordnen Sie den Vorfall einer oder zwei Nummern der WFGY ProblemMap (`No.1` … `No.16`) zu.
3. Speichern Sie die Nummer neben den OmniRoute-Protokollen in Ihrem eigenen Dashboard, Runbook oder Incident-Tracker.
4. Entscheiden Sie anhand der entsprechenden WFGY-Seite, ob Sie Ihren RAG-Stack, Retriever oder Ihre Routing-Strategie ändern müssen.

Den vollständigen Text und konkrete Anleitungen finden Sie hier (MIT-Lizenz, nur Text):

[README der WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Sie können diesen Abschnitt ignorieren, wenn hinter OmniRoute keine RAG- oder Agenten-Pipelines ausgeführt werden.

## Bekannte Probleme in v3.8.0

Probleme, die speziell die Version v3.8.0 betreffen, sowie die derzeit verfügbaren Problemumgehungen. Wenn eine Fehlerbehebung in einem späteren Patch enthalten ist, wird der Eintrag aktualisiert oder entfernt.

### Authentifizierungsfehler der Devin CLI

**Symptome:**

- „Devin CLI nicht gefunden“ oder „Authentifizierung fehlgeschlagen“ beim Aufrufen von Devin-basierten Tools
- Die CLI-Laufzeitprüfung meldet `installed=false`

**Ursachen:**

- `CLI_DEVIN_BIN` verweist auf einen nicht vorhandenen Pfad
- Devin CLI ist nicht auf dem Host installiert

**Behebung:**

1. Installieren Sie die Devin CLI für Ihre Plattform
2. Legen Sie in `.env` den Wert `CLI_DEVIN_BIN=/usr/local/bin/devin` (oder den tatsächlichen Pfad) fest
3. Starten Sie OmniRoute neu und führen Sie den Test erneut über **Dashboard → CLI-Tools** aus

### Modell-Cooldown bleibt aktiv (manuelles Zurücksetzen)

**Symptome:**

- Ein Modell wird auch nach Ablauf der Frist weiterhin als im Cooldown befindlich aufgeführt
- Anfragen überspringen das Modell beim Kombinations-Routing weiterhin, obwohl der Zeitstempel in der Vergangenheit liegt

**Manuelles Zurücksetzen:**

- **Dashboard:** **Einstellungen → Modell-Cooldowns** → klicken Sie auf der betroffenen Karte auf **Erneut aktivieren**
- **API:** `DELETE /api/resilience/model-cooldowns` mit Management-Authentifizierungs-Headern

### Verbindung zum Command Code-Provider schlägt mit 403 fehl

**Symptome:**

- 403 beim Testen der Verbindung zum Command Code-Provider
- Die Provider-Karte zeigt nach dem erneuten Hinzufügen „nicht autorisiert“ an

**Ursache:** Der OAuth-Ablauf wurde nicht abgeschlossen (Callback wurde nicht empfangen oder Token wurde nicht gespeichert).

**Behebung:**

- Führen Sie `omniroute providers` über die CLI aus, um den OAuth-Ablauf erneut auszulösen, oder
- Führen Sie OAuth erneut über **Dashboard → Provider → Command Code → Erneut verbinden** aus

### ModelScope gibt aggressive 429-Cooldowns zurück

**Symptome:**

- Sehr kurze oder sofortige Cooldowns bei ModelScope nach einer kleinen Serie von Anfragen
- Das Kombinations-Routing überspringt ModelScope früher als erwartet

**Ursache:** ModelScope gibt Provider-spezifische `Retry-After`-Header aus. v3.8.0 enthält eine spezielle Verarbeitung für diese Header, weshalb ältere Versionen sie fälschlicherweise als allgemeine Hinweise zur Ratenbegrenzung interpretieren.

**Behebung:**

- Stellen Sie sicher, dass Sie v3.8.0 oder höher verwenden
- Überprüfen Sie, ob die Option `useUpstream429BreakerHints` unter **Einstellungen → Resilienz** aktiviert ist

### OMNIROUTE_WS_BRIDGE_SECRET fehlt in der Produktionsumgebung

**Symptome:**

- 401 bei jeder Codex-/Responses-WebSocket-Bridge-Anfrage, wenn die Ausführung auf einem entfernten Produktionshost erfolgt
- Der WebSocket-Bridge-Handshake wird unmittelbar nach dem Verbindungsaufbau beendet

**Ursache:** Die Umgebungsvariable `OMNIROUTE_WS_BRIDGE_SECRET` fehlt in der Produktionsumgebung.

**Behebung:**

1. Generieren Sie ein zufälliges Geheimnis: `openssl rand -hex 32`
2. Legen Sie `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` in der Umgebung des Produktionsservers fest (sowie in jedem Client, der mit der Bridge kommuniziert)
3. Starten Sie OmniRoute neu

### Responses API: Hintergrundmodus auf synchrone Ausführung herabgestuft

**Symptome:**

- Protokollierte Warnung: `background mode degraded to synchronous`
- Eine Anfrage mit `background: true` gibt anstelle eines Handles für einen Hintergrundauftrag eine normale synchrone Antwort zurück

**Ursache:** v3.8.0 stuft `background: true` in der Responses API absichtlich auf eine synchrone Ausführung herab und gibt dabei eine Warnung aus. Die vollständige asynchrone Ausführung im Hintergrund ist für eine zukünftige Version vorgesehen.

**Behebung:**

- Passen Sie den Client so an, dass der Aufruf ohne `background` erfolgt, oder
- Warten Sie auf eine spätere Version mit vollständigem asynchronem Hintergrundmodus (siehe Änderungsprotokoll)

## Langsamer Start / Zeitüberschreitung der Bereitschaftsprüfung

Wenn die CLI `⚠ Server hat innerhalb von 60 s nicht geantwortet` ausgibt, der Server aber
tatsächlich funktioniert, ist das Zeitbudget der Bereitschaftsprüfung für Ihre Umgebung zu kurz.

Dies tritt häufig unter Windows (Antivirenprogramme, Dateisystem-Watcher) oder in Containern
mit hoher Arbeitslast beim Start auf.

**Lösung — Zeitbudget erhöhen:**

```bash
# Über eine Umgebungsvariable (bleibt über mehrere Starts hinweg bestehen):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 Minuten
omniroute serve

# Über ein CLI-Flag (einmalig):
omniroute serve --ready-timeout 180000
```

Der Standardwert beträgt 60 000 ms (60 s). Die Warnung dient nur zur Information; der Server
wird im Hintergrund weiter gestartet und ist erreichbar, sobald der Startvorgang abgeschlossen ist.

Vollständige Informationen zu `OMNIROUTE_READY_TIMEOUT_MS` finden Sie unter
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
