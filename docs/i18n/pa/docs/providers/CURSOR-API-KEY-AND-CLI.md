IDE ਸੈਸ਼ਨ ਤੋਂ ਬਿਨਾਂ Cursor ਨੂੰ OmniRoute ਦੇ ਪਿੱਛੇ ਰੱਖਣ ਦੇ ਦੋ ਤਰੀਕੇ:

1. **`cursor-api` ਪ੍ਰਦਾਤਾ** (ਕਾਰਡ "Cursor API", ਉਪਨਾਮ `cua`): ਇੱਕ API-ਕੁੰਜੀ
   ਪ੍ਰਦਾਤਾ ਜੋ Cursor ਵਰਤੋਂਕਾਰ API ਕੁੰਜੀ (`crsr_…`, ਜੋ
   `https://cursor.com/dashboard/api` ਉੱਤੇ ਬਣਾਈ ਜਾਂਦੀ ਹੈ) ਸੰਭਾਲਦਾ ਹੈ। ਫਿਰ ਕੋਈ ਵੀ OmniRoute ਕਲਾਇੰਟ
   ਆਮ ਕੋਟਾ, ਫਾਲਬੈਕ ਅਤੇ ਲੌਗਿੰਗ ਪਰਤਾਂ ਸਮੇਤ `/v1/chat/completions` ਰਾਹੀਂ
   Cursor ਮਾਡਲਾਂ ਤੱਕ `cursor-api/<model>` ਜਾਂ `cua/<model>` ਵਜੋਂ ਪਹੁੰਚਦਾ ਹੈ। IDE
   ਪ੍ਰਦਾਤਾ (`cursor`, OAuth/IDE ਸੈਸ਼ਨ) ਵਿੱਚ ਕੋਈ ਤਬਦੀਲੀ ਨਹੀਂ ਹੁੰਦੀ।
2. **Cursor CLI ਪਾਸਥਰੂ**: Cursor CLI (`agent`) ਨੂੰ OmniRoute ਵੱਲ ਨਿਰਦੇਸ਼ਿਤ ਕਰੋ ਤਾਂ ਜੋ
   CLI ਵੱਲੋਂ ਕੀਤੀ ਹਰ RPC ਨੂੰ OmniRoute API ਕੁੰਜੀ ਨਾਲ ਪ੍ਰਮਾਣਿਤ ਕੀਤਾ ਜਾਵੇ, ਉਸਨੂੰ
   `cursor-api` ਕਨੈਕਸ਼ਨ ਦੇ ਪ੍ਰਮਾਣ-ਪੱਤਰ ਨਾਲ Cursor ਵੱਲ ਅੱਗੇ ਭੇਜਿਆ ਜਾਵੇ ਅਤੇ
   Logs ਪੰਨੇ ਵਿੱਚ ਦਰਜ ਕੀਤਾ ਜਾਵੇ।

## ਕੁੰਜੀ ਦਾ ਵਟਾਂਦਰਾ ਕਿਉਂ ਕੀਤਾ ਜਾਂਦਾ ਹੈ

`api2.cursor.sh` ਇੱਕ ਕੱਚੀ `crsr_…` ਕੁੰਜੀ ਨੂੰ Bearer ਟੋਕਨ ਵਜੋਂ ਅਸਵੀਕਾਰ ਕਰਦਾ ਹੈ (401)। Cursor
CLI ਪਹਿਲਾਂ ਕੁੰਜੀ ਨੂੰ `/auth/exchange_user_api_key` ਉੱਤੇ POST ਕਰਦਾ ਹੈ ਅਤੇ ਇੱਕ ਸੈਸ਼ਨ
JWT ਪ੍ਰਾਪਤ ਕਰਦਾ ਹੈ, ਜਿਸਦੀ ਮਿਆਦ ਇੱਕ ਘੰਟੇ ਬਾਅਦ ਪੁੱਗ ਜਾਂਦੀ ਹੈ; ਵਾਪਸ ਮਿਲਿਆ `refreshToken` ਵੀ ਉਹੀ
`exp` ਰੱਖਦਾ ਹੈ, ਇਸ ਲਈ ਰਿਫ਼ਰੈਸ਼ ਕਰਨ ਦਾ ਅਰਥ ਕੁੰਜੀ ਦਾ ਮੁੜ ਵਟਾਂਦਰਾ ਕਰਨਾ ਹੈ।
`open-sse/services/cursorApiKeyAuth.ts` ਇਹ ਵਟਾਂਦਰਾ ਕਰਦਾ ਹੈ, ਹਰ ਕੁੰਜੀ ਲਈ ਇੱਕ ਸੈਸ਼ਨ
ਟੋਕਨ ਕੈਸ਼ ਕਰਦਾ ਹੈ, ਮਿਆਦ ਪੁੱਗਣ ਤੋਂ ਪੰਜ ਮਿੰਟ ਪਹਿਲਾਂ ਮੁੜ ਵਟਾਂਦਰਾ ਕਰਦਾ ਹੈ ਅਤੇ Cursor ਵੱਲੋਂ 401
ਜਵਾਬ ਆਉਣ ਉੱਤੇ ਕੈਸ਼ ਕੀਤਾ ਟੋਕਨ ਹਟਾ ਦਿੰਦਾ ਹੈ। `CursorExecutor`, `cursor-api`
ਕਨੈਕਸ਼ਨਾਂ ਲਈ ਅੱਪਸਟ੍ਰੀਮ ਸਟ੍ਰੀਮ ਖੋਲ੍ਹਣ ਤੋਂ ਠੀਕ ਪਹਿਲਾਂ ਇਸਨੂੰ ਕਾਲ ਕਰਦਾ ਹੈ।

## `cursor-api` ਪ੍ਰਦਾਤਾ

ਰਜਿਸਟਰੀ: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"`, `cursor` ਵਾਲੇ ਹੀ `format`, `baseUrl` ਅਤੇ
`models`)। ਕੈਟਾਲੌਗ ਕਾਰਡ:
`src/shared/constants/providers/apikey/specialty-media.ts`। ਐਗਜ਼ਿਕਿਊਟਰ ਮੈਪ:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`)।

ਡੈਸ਼ਬੋਰਡ: Providers → Cursor API → Add API key।

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

ਫਿਰ:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

ਨੋਟ:

- `cursor-api` ਲਈ ਮਾਡਲ ਸੂਚੀ ਸਥਿਰ Cursor ਰਜਿਸਟਰੀ ਤੋਂ ਆਉਂਦੀ ਹੈ (ਉਹੀ
  ਸੂਚੀ ਜਿਸਨੂੰ IDE ਪ੍ਰਦਾਤਾ ਫਾਲਬੈਕ ਵਜੋਂ ਵਰਤਦਾ ਹੈ); OmniRoute ਹੋਸਟ ਉੱਤੇ
  `cursor-agent` ਇੰਸਟਾਲ ਕਰਨ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ।
- `POST /api/providers/{id}/refresh-cursor` ਸਿਰਫ਼ `cursor` IDE ਪ੍ਰਦਾਤਾ ਲਈ ਹੈ;
  `cursor-api` ਕਨੈਕਸ਼ਨਾਂ ਕੋਲ ਨਵਿਆਉਣ ਲਈ ਕੋਈ IDE ਸੈਸ਼ਨ ਨਹੀਂ ਹੁੰਦਾ।

## ਮੂਲ ਮਾਡਲ ID ਅਤੇ ਯਤਨ

`cursor` / `cu` ਅਤੇ `cursor-api` / `cua` ਲਈ, ਸਾਂਝਾ Claude-ਯਤਨ ਨਾਰਮਲਾਈਜ਼ਰ
ਬੇਨਤੀ ਕੀਤੇ ਮਾਡਲ ID ਨੂੰ ਬਿਨਾਂ ਬਦਲੇ ਛੱਡਦਾ ਹੈ। Cursor ਕਿਸੇ ਅਸਲ ਮਾਡਲ ID ਦੇ ਹਿੱਸੇ ਵਜੋਂ
`-low` ਵਰਗੇ ਸਫ਼ਿਕਸ ਦਾ ਇਸ਼ਤਿਹਾਰ ਦੇ ਸਕਦਾ ਹੈ, ਨਾ ਕਿ OmniRoute ਯਤਨ ਉਪਨਾਮ ਵਜੋਂ।
Cursor ਐਗਜ਼ਿਕਿਊਟਰ ਲਾਈਵ ਕੈਟਾਲੌਗ ਦੇ ਸਟੀਕ ਮੇਲ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦਾ ਹੈ; ਜਦੋਂ ਕੋਈ
ਮੇਲ ਨਹੀਂ ਹੁੰਦਾ, ਤਾਂ ਇਸਦਾ ਮੌਜੂਦਾ ਮਾਡਲ ਰਿਜ਼ਾਲਵਰ ਸਫ਼ਿਕਸ-ਤੋਂ-ਪੈਰਾਮੀਟਰ ਫਾਲਬੈਕ ਸੰਭਾਲਦਾ ਹੈ।

ਇਹ ਸਿੱਧੇ Claude, Claude-ਅਨੁਕੂਲ ਜਾਂ Vertex ਰੂਟਾਂ ਲਈ ਯਤਨ ਨਾਰਮਲਾਈਜ਼ੇਸ਼ਨ ਨੂੰ
ਨਹੀਂ ਬਦਲਦਾ। ਉਪਲਬਧਤਾ ਹਾਲੇ ਵੀ ਚੁਣੇ ਗਏ Cursor ਖਾਤੇ ਦੇ ਕੈਟਾਲੌਗ ਅਤੇ ਹੱਕਾਂ ਉੱਤੇ ਨਿਰਭਰ ਕਰਦੀ ਹੈ।

## Cursor CLI ਪਾਸਥਰੂ

ਰੂਟ: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`। ਪ੍ਰੀਫਿਕਸ `/api/cursor-cli/` ਨੂੰ
`src/shared/constants/publicApiRoutes.ts` ਵਿੱਚ ਰਜਿਸਟਰ ਕੀਤਾ ਗਿਆ ਹੈ ਕਿਉਂਕਿ ਹੈਂਡਲਰ
ਆਪਣਾ ਪ੍ਰਮਾਣੀਕਰਨ ਖੁਦ ਲਾਗੂ ਕਰਦਾ ਹੈ:

| ਪਾਥ                                                                                                                      | CLI ਤੋਂ ਉਮੀਦ ਕੀਤੀ ਪ੍ਰਮਾਣੀਕਰਨ ਜਾਣਕਾਰੀ | OmniRoute ਕੀ ਕਰਦਾ ਹੈ                                                                                                                                                           |
| ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /auth/exchange_user_api_key`                                                                                       | `Bearer <OmniRoute API key>`         | ਕੁੰਜੀ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ, 1 ਘੰਟੇ ਲਈ HS256 JWT (`JWT_SECRET` ਨਾਲ ਦਸਤਖ਼ਤ ਕੀਤਾ) ਬਣਾਉਂਦਾ ਹੈ ਅਤੇ ਇਸਨੂੰ ਵਾਪਸ ਕਰਦਾ ਹੈ                                                               |
| ਹਰੇਕ ਹੋਰ ਪਾਥ (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`                  | ਜਾਰੀਕਰਤਾ/ਦਰਸ਼ਕ/ਮਿਆਦ ਦੀ ਪੁਸ਼ਟੀ ਕਰਦਾ ਹੈ, ਇੱਕ ਸਰਗਰਮ `cursor-api` ਕਨੈਕਸ਼ਨ ਚੁਣਦਾ ਹੈ, Authorization ਹੈਡਰ ਨੂੰ ਬਦਲੇ ਹੋਏ Cursor ਟੋਕਨ ਨਾਲ ਤਬਦੀਲ ਕਰਦਾ ਹੈ ਅਤੇ ਜਵਾਬ ਨੂੰ ਵਾਪਸ ਸਟ੍ਰੀਮ ਕਰਦਾ ਹੈ |

CLI ਪ੍ਰਾਪਤ ਹੋਣ ਵਾਲੇ ਕਿਸੇ ਵੀ ਟੋਕਨ ਤੋਂ `exp` ਨੂੰ ਡੀਕੋਡ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ ਉਸਨੂੰ ਇੱਕ ਅਪਾਰਦਰਸ਼ੀ
ਟੋਕਨ ਦੇਣ ਨਾਲ ਉਹ ਲਗਭਗ ਹਰ ਬੇਨਤੀ ਤੋਂ ਪਹਿਲਾਂ ਦੁਬਾਰਾ ਐਕਸਚੇਂਜ ਕਰਦਾ ਹੈ; ਬਣਾਇਆ ਗਿਆ JWT
ਇਸ ਤੋਂ ਬਚਾਉਂਦਾ ਹੈ। OmniRoute ਵੱਲੋਂ 401 ਮਿਲਣ 'ਤੇ CLI ਦੁਬਾਰਾ ਐਕਸਚੇਂਜ ਕਰਦਾ ਹੈ।

### ਸੈੱਟਅੱਪ

1. ਇੱਕ OmniRoute API ਕੁੰਜੀ (Dashboard → API keys) ਅਤੇ ਇੱਕ `cursor-api`
   ਕਨੈਕਸ਼ਨ ਬਣਾਓ।
2. CLI ਨੂੰ ਏਜੰਟ ਸਟ੍ਰੀਮ ਲਈ HTTP/1.1 ਵਰਤਣ ਲਈ ਕਹੋ। ਇਸ ਵਿੱਚ
   `~/.cursor/cli-config.json`:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   ਇਸ ਤੋਂ ਬਿਨਾਂ CLI ਏਜੰਟ ਟਰਨ ਨੂੰ HTTP/2 ਰਾਹੀਂ ਇੱਕ ਵੱਖਰੇ ਤੌਰ 'ਤੇ
   ਸੰਰਚਿਤ ਏਜੰਟ ਹੋਸਟ 'ਤੇ ਖੋਲ੍ਹਦਾ ਹੈ ਅਤੇ ਸਿਰਫ਼ ਕੰਟਰੋਲ-ਪਲੇਨ RPCs ਹੀ
   ਐਂਡਪੌਇੰਟ ਰਾਹੀਂ ਜਾਂਦੇ ਹਨ।

3. CLI ਨੂੰ OmniRoute ਦੇ ਵਿਰੁੱਧ ਚਲਾਓ:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

ਹਰੇਕ ਹੌਪ Logs ਵਿੱਚ ਪ੍ਰਦਾਤਾ `cursor-api`, ਬੇਨਤੀ ਕਿਸਮ `cursor-cli`,
ਪਾਥ `/api/cursor-cli/<rpc>` ਵਜੋਂ ਦਰਜ ਹੁੰਦਾ ਹੈ ਅਤੇ ਉਸ OmniRoute API ਕੁੰਜੀ ਅਤੇ
ਉਸਨੂੰ ਸੰਭਾਲਣ ਵਾਲੇ ਕਨੈਕਸ਼ਨ ਨਾਲ ਜੋੜਿਆ ਜਾਂਦਾ ਹੈ।
