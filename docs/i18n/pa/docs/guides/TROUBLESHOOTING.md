### ਮੁਫ਼ਤ ਪ੍ਰਦਾਤਿਆਂ ਉੱਤੇ ਰੇਟ ਸੀਮਾਬੰਦੀ (429 / 400 / 401)

**ਲੱਛਣ**: ਮੁਫ਼ਤ/ਬਿਨਾਂ-ਪ੍ਰਮਾਣੀਕਰਨ ਵਾਲੇ ਪ੍ਰਦਾਤਿਆਂ (opencode, auggie, ਆਦਿ) ਨਾਲ `model: "auto"` ਵਰਤਦੇ ਸਮੇਂ, ਤੁਹਾਨੂੰ ਜਵਾਬਾਂ ਦੀ ਥਾਂ ਕਦੇ-ਕਦਾਈਂ `HTTP 429`, `400`, ਜਾਂ `401` ਮਿਲਦਾ ਹੈ। ਕੁਝ ਪਲਾਂ ਬਾਅਦ ਉਸੇ ਪ੍ਰਾਂਪਟ ਨਾਲ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਕਰਨ 'ਤੇ ਬੇਨਤੀਆਂ ਸਫਲ ਹੋ ਜਾਂਦੀਆਂ ਹਨ, ਪਰ ਆਟੋਮੇਸ਼ਨ (cron ਜੌਬਾਂ, ਏਜੰਟ, ਸਕ੍ਰਿਪਟਾਂ) ਪਹਿਲੀ ਅਸਫਲਤਾ 'ਤੇ ਹੀ ਟੁੱਟ ਜਾਂਦੀ ਹੈ।

**ਮੂਲ ਕਾਰਨ**: ਤਿੰਨ ਸੁਤੰਤਰ ਅਸਫਲਤਾ ਸਥਿਤੀਆਂ ਇਕੱਠੀਆਂ ਹੋ ਜਾਂਦੀਆਂ ਹਨ:

1. **ਪ੍ਰਦਾਤਾ ਰੇਟ ਸੀਮਾ (`429`)**: ਮੁਫ਼ਤ ਟੀਅਰ ਹਰ ਸਮਾਂ-ਵਿੰਡੋ ਲਈ ਕੋਟਾ ਲਾਗੂ ਕਰ ਸਕਦੇ ਹਨ। ਸਮਾਂਤਰ ਕਾਲਾਂ ਦਾ ਅਚਾਨਕ ਵਾਧਾ ਇਸਨੂੰ ਖ਼ਤਮ ਕਰ ਦਿੰਦਾ ਹੈ, ਇਸ ਲਈ ਵਿੰਡੋ ਰੀਸੈੱਟ ਹੋਣ ਤੱਕ ਅਗਲੀ ਬੇਨਤੀ ਨਾਮਨਜ਼ੂਰ ਕਰ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ।
2. **ਪਾਸਥਰੂ ਵਿੱਚ ਖ਼ਰਾਬ ਮਾਡਲ (`400`/`401`)**: `auto/*` ਪੂਲਾਂ ਵਿੱਚ `opencode` ਦੇ ਅਜਿਹੇ ਪਾਸਥਰੂ ਮਾਡਲ ਸ਼ਾਮਲ ਹੋ ਸਕਦੇ ਹਨ ਜੋ ਕੈਟਾਲੌਗ ਵਿੱਚ ਰਜਿਸਟਰਡ ਹਨ ਪਰ ਜਿਨ੍ਹਾਂ ਕੋਲ ਸਰਗਰਮ ਪ੍ਰਮਾਣ-ਪੱਤਰ ਨਹੀਂ ਹਨ (ਉਦਾਹਰਨ ਵਜੋਂ `oc/north-mini-code-free` → `401`)। ਆਟੋ-ਰਾਊਟਰ ਕਿਸੇ ਇੱਕ ਨੂੰ ਅਜ਼ਮਾਉਂਦਾ ਹੈ, ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ, ਅਤੇ ਫਾਲਬੈਕ ਸ਼ੁਰੂ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਹੀ ਗਲਤੀ ਅੱਗੇ ਭੇਜ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ।
3. **ਸਮਕਾਲਤਾ ਵਾਧਾ (ਲੋਡ ਹੇਠ `429`)**: ਜਦੋਂ ਕਈ ਏਜੰਟ/cron ਸੈਸ਼ਨ ਇੱਕੋ ਸਮੇਂ `auto` ਨੂੰ ਵਰਤਦੇ ਹਨ, ਤਾਂ ਕੁੱਲ ਬੇਨਤੀ ਦਰ ਮੁਫ਼ਤ ਪ੍ਰਦਾਤਿਆਂ ਦੀ ਸਹਿਣਯੋਗ ਹੱਦ ਤੋਂ ਵੱਧ ਜਾਂਦੀ ਹੈ, ਜਿਸ ਕਾਰਨ ਵੈਧ ਕਾਲਾਂ ਨੂੰ ਵੀ ਦੁਰਵਰਤੋਂ ਵਜੋਂ ਚਿੰਨ੍ਹਿਤ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ।

**ਪ੍ਰਮਾਣਿਤ ਹੱਲ (ਭਾਈਚਾਰੇ ਵੱਲੋਂ ਰਿਪੋਰਟ ਕੀਤਾ ਗਿਆ, 2026-08-10)**: ਤਿੰਨ ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲਾਂ ਨੂੰ ਇਸ ਤਰ੍ਹਾਂ ਟਿਊਨ ਕਰੋ ਕਿ ਰੋਟੇਸ਼ਨ, ਸਮਕਾਲਤਾ ਅਤੇ ਫਾਲਬੈਕ ਮੁਫ਼ਤ ਟੀਅਰ ਦੀ ਅਸਥਿਰਤਾ ਕਾਰਨ ਬੰਦ ਹੋਣ ਦੀ ਬਜਾਏ ਉਸਨੂੰ ਸੰਭਾਲ ਸਕਣ:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ਉੱਤੇ ਕਿਸੇ ਹੋਰ ਮਾਡਲ/ਪ੍ਰਦਾਤੇ 'ਤੇ ਜਾਓ (ਖ਼ਰਾਬ ਪਾਸਥਰੂ ਮਾਡਲਾਂ ਨੂੰ ਛੱਡਦਾ ਹੈ)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ਭਾਰੀ ਬੇਨਤੀਆਂ ਦੇ ਦਾਖ਼ਲੇ ਲਈ ਸਪਸ਼ਟ ਅਧਿਕਤਮ ਸੀਮਾ (ਮੂਲ ਰੂਪ ਵਿੱਚ ਸੈੱਟ ਨਹੀਂ: ਬੇਨਤੀ-ਗਿਣਤੀ ਦੀ ਕੋਈ ਸੀਮਾ ਨਹੀਂ, ਹੇਠਾਂ ਨੋਟ ਦੇਖੋ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # ਹੌਲੇ ਅੱਪਸਟ੍ਰੀਮਾਂ ਲਈ ਸੀਮਿਤ ਉਡੀਕ ਨੂੰ RATE_LIMIT_MAX_WAIT_MS ਦੀ ਡਿਫਾਲਟ ਮਿਆਦ ਤੋਂ ਵੱਧ ਕਰੋ
```

ਇਨ੍ਹਾਂ ਨੂੰ OmniRoute ਪ੍ਰਕਿਰਿਆ ਦੇ ਇਨਵਾਇਰਨਮੈਂਟ ਵਿੱਚ ਸੈੱਟ ਕਰੋ (ਡੇਮਨ ਵਿੱਚ, ਉਦਾਹਰਨ ਵਜੋਂ LaunchAgent plist ਜਾਂ `systemctl edit` ਰਾਹੀਂ), ਫਿਰ OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ। ਰੋਟੇਸ਼ਨ ਫਲੈਗ ਸਭ ਤੋਂ ਵੱਧ ਅਸਰਦਾਰ ਇਕੱਲਾ ਨਿਯੰਤਰਣ ਹੈ: ਇਹ ਇੱਕ ਸਖ਼ਤ ਅਸਫਲਤਾ ਨੂੰ ਪੂਲ ਵਿਚਲੇ ਕਿਸੇ ਸਿਹਤਮੰਦ ਪ੍ਰਦਾਤੇ ਦੇ ਵਿਰੁੱਧ ਪਾਰਦਰਸ਼ੀ ਮੁੜ-ਕੋਸ਼ਿਸ਼ ਵਿੱਚ ਬਦਲ ਦਿੰਦਾ ਹੈ।

**ਨੋਟ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ਇਸ ਗੱਲ ਨੂੰ ਸੀਮਿਤ ਕਰਦਾ ਹੈ ਕਿ ਇੱਕੋ ਸਮੇਂ ਕਿੰਨੀਆਂ ਭਾਰੀ — ਲੰਬੇ-ਕਾਂਟੈਕਸਟ ਵਾਲੀਆਂ — ਬੇਨਤੀਆਂ ਚੱਲ ਸਕਦੀਆਂ ਹਨ; ਇਹ ਸੀਮਾ ਇੱਕ ਦਾਖ਼ਲਾ ਗੇਟ ਹੈ, ਪ੍ਰਦਾਤਾ ਰੇਟ ਲਿਮਿਟਰ ਨਹੀਂ। **#503-fanout ਅੱਪਡੇਟ:** ਇਹ ਵੇਰੀਏਬਲ ਹੁਣ ਮੂਲ ਰੂਪ ਵਿੱਚ ਸੈੱਟ ਨਹੀਂ ਹੁੰਦਾ (ਹੁਣ ਇਹ ਸਿਰਫ਼ ਉਦੋਂ ਲਾਗੂ ਹੁੰਦਾ ਹੈ ਜਦੋਂ ਉੱਪਰ ਦਿੱਤੇ ਅਨੁਸਾਰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਕੌਂਫਿਗਰ ਕੀਤਾ ਜਾਵੇ) — ਇਸਦੀ ਬਜਾਏ ਭਾਰੀ ਬੇਨਤੀਆਂ ਦਾ ਦਾਖ਼ਲਾ ਇੱਕ ਆਪਣੇ-ਆਪ ਨਿਰਧਾਰਤ ਬਾਈਟ ਬਜਟ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ਦੁਆਰਾ ਨਿਯੰਤਰਿਤ ਹੁੰਦਾ ਹੈ, ਜੋ ਹੋਸਟ ਦੀ ਅਸਲ ਮੈਮੋਰੀ ਸੀਮਾ ਅਨੁਸਾਰ ਆਪਣੇ ਆਪ ਸਕੇਲ ਹੁੰਦਾ ਹੈ, ਇਸ ਲਈ ਇੱਕ ਨਵੀਂ ਡਿਪਲੌਇਮੈਂਟ ਵਿੱਚ ਇਹ ਵੇਰੀਏਬਲ ਬਿਲਕੁਲ ਵੀ ਸੈੱਟ ਕੀਤੇ ਬਿਨਾਂ ਬਹੁਤ ਘੱਟ `503 chat_admission_busy` ਅਸਵੀਕਾਰਤਾਵਾਂ ਦਿਖਾਈ ਦੇਣੀਆਂ ਚਾਹੀਦੀਆਂ ਹਨ; ਇਸਨੂੰ ਇੱਥੇ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਸੈੱਟ ਕਰਨਾ ਹਾਲੇ ਵੀ ਦਸਤਾਵੇਜ਼ ਵਿੱਚ ਦਰਸਾਏ ਅਨੁਸਾਰ ਹੀ ਕੰਮ ਕਰਦਾ ਹੈ। ਸਪਸ਼ਟ ਬਾਈਟ-ਬਜਟ ਓਵਰਰਾਈਡ 8 MiB–2 GiB ਤੱਕ ਸੀਮਿਤ ਕੀਤੇ ਜਾਂਦੇ ਹਨ। ਇੱਕ `413 body_exceeds_budget` ਅਸਥਾਈ ਨਹੀਂ ਹੁੰਦਾ: ਉਸ ਬਾਈਟ ਬਜਟ ਨੂੰ ਵਧਾਓ, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ਨੂੰ ਘਟਾਓ, ਜਾਂ ਪ੍ਰਕਿਰਿਆ ਦੀ ਮੈਮੋਰੀ ਸੀਮਾ ਵਧਾਓ। ਇੱਕ `inflight_bytes_budget` ਸ਼ੈਡ ਅਸਥਾਈ ਸਰੋਤ-ਮੁਕਾਬਲਾ ਹੈ ਅਤੇ ਇਸ ਉੱਤੇ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਕੀਤੀ ਜਾ ਸਕਦੀ ਹੈ। ਹਰ ਪ੍ਰਦਾਤੇ ਲਈ ਰੇਟ ਸੀਮਾਬੰਦੀ (`open-sse/services/rateLimitManager.ts`) ਨੂੰ `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, ਅਤੇ `RATE_LIMIT_AUTO_ENABLE` ਦੁਆਰਾ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਨਿਯੰਤਰਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ — `.env.example` ਦੇਖੋ।

**ਇਹ ਕਿਵੇਂ ਪੁਸ਼ਟੀ ਕਰਨੀ ਹੈ ਕਿ ਇਸ ਨੇ ਕੰਮ ਕੀਤਾ**: ਆਪਣੇ agent/cron ਨੂੰ ਥੋੜ੍ਹੇ ਸਮੇਂ ਦੇ ਅੰਤਰ ਨਾਲ ਦੋ ਵਾਰ ਚਲਾਓ ਅਤੇ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਦੋਵੇਂ ਵਾਰ ਸਫਲਤਾ ਮਿਲਦੀ ਹੈ। fix ਤੋਂ ਪਹਿਲਾਂ, ਦੂਜੀ run ਆਮ ਤੌਰ 'ਤੇ `429`/`401` ਦਿੰਦੀ ਹੈ। fix ਤੋਂ ਬਾਅਦ, ਅਸਫਲਤਾਵਾਂ (ਜੇ ਕੋਈ ਹੋਣ) ਲਈ ਪਾਰਦਰਸ਼ੀ ਢੰਗ ਨਾਲ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਕੀਤੀ ਜਾਂਦੀ ਹੈ ਅਤੇ call ਪੂਰੀ ਹੋ ਜਾਂਦੀ ਹੈ। ਤੁਸੀਂ `curl /monitoring/health` ਵੀ ਚਲਾ ਸਕਦੇ ਹੋ ਅਤੇ provider connections ਉੱਤੇ `rateLimitedUntil` field ਅਤੇ ਪ੍ਰਭਾਵਿਤ providers ਲਈ `circuitBreakers.providerBreakers[].state` ਨੂੰ ਦੇਖ ਸਕਦੇ ਹੋ — state `CLOSED`, `DEGRADED`, `OPEN`, ਜਾਂ `HALF_OPEN` ਵਿੱਚੋਂ ਇੱਕ ਹੁੰਦੀ ਹੈ (`src/shared/utils/circuitBreaker.ts` ਵੇਖੋ), ਅਤੇ ਲਗਾਤਾਰ ਅਸਫਲ ਹੋਣ ਵਾਲਾ provider reset window ਦੁਆਰਾ probe ਨੂੰ ਲੰਘਣ ਦੀ ਆਗਿਆ ਦੇਣ (`HALF_OPEN`) ਤੋਂ ਪਹਿਲਾਂ `CLOSED → DEGRADED → OPEN` ਵਿੱਚ ਬਦਲ ਜਾਵੇਗਾ।

**ਜੇ ਤੁਹਾਨੂੰ ਅਜੇ ਵੀ 429 ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ**: ਉਸ provider ਦੇ ਸਰਗਰਮ account ਨੇ ਵਾਸਤਵ ਵਿੱਚ ਆਪਣਾ _quota_ ਖਤਮ ਕਰ ਲਿਆ ਹੈ (ਸਿਰਫ਼ rate ਨਹੀਂ)। OmniRoute dashboard → Providers → Accounts ਵਿੱਚ ਉਸੇ provider ਲਈ ਦੂਜਾ account ਸ਼ਾਮਲ ਕਰੋ, ਜਾਂ ਕਿਸੇ ਹੋਰ ਮੁਫ਼ਤ provider (ਜਿਵੇਂ `routeway`, `auggie`) ਨੂੰ ਵੀ ਸ਼ਾਮਲ ਕਰੋ। Rotation ਸਿਰਫ਼ ਅਸਥਾਈ rate/400/401 ਨਾਲ ਮਦਦ ਕਰਦੀ ਹੈ; quota ਪੂਰੀ ਤਰ੍ਹਾਂ ਖਤਮ ਹੋਣ 'ਤੇ ਦੂਜੇ credential ਜਾਂ ਕਿਸੇ ਵੱਖਰੇ provider ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।

**ਜੇ ਤੁਹਾਨੂੰ vision models (`auto/vision`, `bazaarlink/*`) ਉੱਤੇ 403 ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ**: connected account ਕੋਲ vision ਸ਼ਾਮਲ ਕਰਨ ਵਾਲਾ paid plan ਨਹੀਂ ਹੈ, ਜਾਂ API key ਕੋਲ ਲੋੜੀਂਦੀਆਂ permissions ਨਹੀਂ ਹਨ। provider dashboard ਵਿੱਚ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ key scope ਵਿੱਚ vision/multimodal ਸ਼ਾਮਲ ਹੈ, ਜਾਂ paid tier account connect ਕਰੋ ਅਤੇ ਉਸਨੂੰ vision target ਵਜੋਂ ਰੱਖੋ।

## npm install ਚੇਤਾਵਨੀਆਂ (ERESOLVE / peer / deprecated)

ਜਦੋਂ ਤੁਸੀਂ `npm install -g omniroute` ਚਲਾਉਂਦੇ ਹੋ, ਤਾਂ ਤੁਹਾਨੂੰ `npm warn ERESOLVE`, peer-dependency ਸੂਚਨਾਵਾਂ ਅਤੇ `deprecated` ਸੁਨੇਹਿਆਂ ਵਰਗੀਆਂ ਬਹੁਤ ਸਾਰੀਆਂ ਚੇਤਾਵਨੀਆਂ ਦਿਖਾਈ ਦੇ ਸਕਦੀਆਂ ਹਨ। **ਇਹ ਉਮੀਦ ਅਨੁਸਾਰ ਹਨ ਅਤੇ ਨੁਕਸਾਨ ਰਹਿਤ ਹਨ।** ਜੇ ਆਉਟਪੁੱਟ ਵਿੱਚ `added <N> packages` ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ, ਤਾਂ ਤੁਹਾਡੀ ਇੰਸਟਾਲੇਸ਼ਨ ਸਫਲ ਰਹੀ ਹੈ।

peer-dependency ਹੱਲ ਕਰਨ ਸੰਬੰਧੀ ਚੇਤਾਵਨੀਆਂ ਨੂੰ ਦਬਾਉਣ ਲਈ, OmniRoute ਦਾ ਸਮਰਥਿਤ ਇੰਸਟਾਲੇਸ਼ਨ ਰੂਪ ਵਰਤੋ:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` ਸਿਰਫ਼ `ERESOLVE` ਅਤੇ peer-dependency ਸੂਚਨਾਵਾਂ ਨੂੰ ਦਬਾਉਂਦਾ ਹੈ। Deprecation ਸੂਚਨਾਵਾਂ ਦਿਖਾਈ ਦਿੰਦੀਆਂ ਰਹਿੰਦੀਆਂ ਹਨ ਕਿਉਂਕਿ ਉਹ transitive ਤੀਜੀ-ਧਿਰ ਪੈਕੇਜਾਂ ਤੋਂ ਆਉਂਦੀਆਂ ਹਨ; ਉਹ ਇਹ ਸੰਕੇਤ ਨਹੀਂ ਦਿੰਦੀਆਂ ਕਿ ਇੰਸਟਾਲੇਸ਼ਨ ਅਸਫਲ ਹੋ ਗਈ ਹੈ।

ਇਹ ਚੇਤਾਵਨੀਆਂ ਤੀਜੀ-ਧਿਰ ਪੈਕੇਜਾਂ ਵਿੱਚ ਪੁਰਾਣੀਆਂ peer-dependency ਰੇਂਜਾਂ ਕਾਰਨ ਆਉਂਦੀਆਂ ਹਨ, ਜਿਨ੍ਹਾਂ ਨੂੰ OmniRoute ਕੰਟਰੋਲ ਨਹੀਂ ਕਰਦਾ:

1. **`marked-terminal` ਨੂੰ `marked >=1 <16` ਚਾਹੀਦਾ ਹੈ, ਪਰ `marked@18` ਮਿਲਿਆ** — ਅਮਲ ਵਿੱਚ ਇਹ ਠੀਕ ਕੰਮ ਕਰਦਾ ਹੈ; upstream peer ਰੇਂਜ ਸਿਰਫ਼ ਪੁਰਾਣੀ ਹੈ।
2. **`deprecated prebuild-install@7.1.3`** — ਇੱਕ transitive native-binary ਪ੍ਰਾਪਤੀ ਸਹਾਇਕ। ਇਸਦੀ ਵਰਤੋਂ
   ਪਿੰਨ ਕੀਤੀ `wreq-js` ਟ੍ਰਾਂਸਪੋਰਟ ਬਾਈਂਡਿੰਗ ਇੰਸਟਾਲ ਕਰਨ ਲਈ ਨਹੀਂ ਹੁੰਦੀ ਅਤੇ ਇਹ ਇਸ ਗੱਲ ਦਾ ਸੰਕੇਤ ਨਹੀਂ ਦਿੰਦਾ ਕਿ web-cookie
   ਪ੍ਰਦਾਤਾ ਦੀ ਟ੍ਰਾਂਸਪੋਰਟ ਸੈੱਟਅੱਪ ਅਸਫਲ ਹੋ ਗਈ ਹੈ।

**ਕਿਸੇ ਕਾਰਵਾਈ ਦੀ ਲੋੜ ਨਹੀਂ** — upstream ਪੈਕੇਜਾਂ ਨੂੰ fork ਕੀਤੇ ਬਿਨਾਂ ਚੇਤਾਵਨੀਆਂ ਨੂੰ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸ਼ਾਂਤ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ।

## npm install-scripts ਬਲੌਕ ਹੋਣ ਦੀ ਚੇਤਾਵਨੀ (ਗਲੋਬਲ ਇੰਸਟਾਲੇਸ਼ਨ)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` ਚਲਾਉਂਦੇ ਸਮੇਂ, npm ਦੇ ਨਵੇਂ ਵਰਜਨ (v11+ ਅਤੇ v12+) ਮੂਲ ਰੂਪ ਵਿੱਚ ਪੈਕੇਜ lifecycle ਸਕ੍ਰਿਪਟਾਂ ਨੂੰ ਬਲੌਕ ਕਰਦੇ ਹਨ ਅਤੇ install-scripts ਚੇਤਾਵਨੀ ਦਿਖਾਉਂਦੇ ਹਨ:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### ਕੀ ਇਸ ਚੇਤਾਵਨੀ ਨੂੰ ਅਣਡਿੱਠਾ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ?

**ਅੰਸ਼ਕ ਤੌਰ 'ਤੇ, ਪਰ ਸਕ੍ਰਿਪਟਾਂ ਤੋਂ ਬਿਨਾਂ ਚਲਾਉਣ ਦੀ ਸਿਫ਼ਾਰਸ਼ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ।** OmniRoute ਵਿੱਚ ਸੁਚਾਰੂ fallback ਸ਼ਾਮਲ ਹਨ: ਜੇ native `better-sqlite3` ਬਾਈਂਡਿੰਗਾਂ ਨੂੰ standalone ਬੰਡਲ ਤੋਂ ਲੋਡ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ, ਤਾਂ ਐਪਲੀਕੇਸ਼ਨ `node:sqlite` ਜਾਂ `sql.js` ਵਰਗੇ ਵਿਕਲਪਕ ਡਰਾਈਵਰਾਂ ਦੀ ਵਰਤੋਂ ਕਰਦੀ ਹੈ ([SQLite ਰਨਟਾਈਮ ਰੈਜ਼ੋਲਿਊਸ਼ਨ](../ops/SQLITE_RUNTIME.md) ਵੇਖੋ)। ਸਰਵਰ ਫਿਰ ਵੀ ਸ਼ੁਰੂ ਹੋ ਜਾਵੇਗਾ, ਪਰ `sql.js` ਵਰਗੇ WASM fallback ਉੱਤੇ ਚਲਾਉਣ ਨਾਲ SQLite WAL (Write-Ahead Logging) ਮੋਡ ਅਸਮਰੱਥ ਹੋ ਜਾਂਦਾ ਹੈ ਅਤੇ ਮੈਮੋਰੀ ਤੇ disk-sync ਦਾ ਵਾਧੂ ਖਰਚ ਵਧ ਜਾਂਦਾ ਹੈ।

### ਅਸਲ ਵਿੱਚ ਕਿਹੜੀਆਂ ਸਕ੍ਰਿਪਟਾਂ ਲੋੜੀਂਦੀਆਂ ਹਨ?

ਸਾਰੀਆਂ ਬਲੌਕ ਕੀਤੀਆਂ ਸਕ੍ਰਿਪਟਾਂ OmniRoute ਚਲਾਉਣ ਲਈ ਜ਼ਰੂਰੀ ਨਹੀਂ ਹਨ:

- **ਜ਼ਰੂਰੀ (`omniroute`, `better-sqlite3`):** OmniRoute ਇੱਕ Next.js standalone ਐਪਲੀਕੇਸ਼ਨ ਬੰਡਲ (`dist/`) ਤੋਂ ਚੱਲਦਾ ਹੈ। ਇੰਸਟਾਲੇਸ਼ਨ ਦੌਰਾਨ, npm ਸਿਖਰਲੇ ਪੱਧਰ ਦੇ `node_modules/better-sqlite3/` ਵਿੱਚ ਹੋਸਟ-ਵਿਸ਼ੇਸ਼ native SQLite ਡਰਾਈਵਰ ਡਾਊਨਲੋਡ ਜਾਂ ਕੰਪਾਇਲ ਕਰਦਾ ਹੈ। ਫਿਰ OmniRoute ਦੀ `postinstall` ਸਕ੍ਰਿਪਟ (`scripts/build/postinstall.mjs`) ਇਨ੍ਹਾਂ ਹੋਸਟ-ਵਿਸ਼ੇਸ਼ ਬਾਈਨਰੀਆਂ ਦੀ ਪੁਸ਼ਟੀ ਕਰਦੀ ਹੈ ਅਤੇ ਇਨ੍ਹਾਂ ਨੂੰ `dist/node_modules/` ਵਿੱਚ ਕਾਪੀ ਕਰਦੀ ਹੈ, ਤਾਂ ਜੋ standalone ਸਰਵਰ ਇਨ੍ਹਾਂ ਤੱਕ ਪਹੁੰਚ ਕਰ ਸਕੇ। ਜੇ `omniroute` ਦੀ postinstall ਸਕ੍ਰਿਪਟ ਬਲੌਕ ਹੋਵੇ, ਤਾਂ ਇਹ ਕਾਪੀ ਕਰਨ ਵਾਲਾ ਪੜਾਅ ਛੱਡ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ।
- **ਵਿਕਲਪਿਕ/transitive (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** ਇਹ build ਸਹਾਇਕ, watcher ਟੂਲ ਜਾਂ ਸਿਸਟਮ keychain ਯੂਟਿਲਿਟੀਆਂ ਹਨ। ਇਨ੍ਹਾਂ ਨੂੰ ਆਗਿਆ ਦੇਣ ਨਾਲ build ਚੇਤਾਵਨੀਆਂ ਤੋਂ ਬਚਿਆ ਜਾ ਸਕਦਾ ਹੈ, ਪਰ ਮੁੱਖ routing ਕਾਰਜਕੁਸ਼ਲਤਾ ਲਈ ਇਹ ਲੋੜੀਂਦੇ ਨਹੀਂ ਹਨ।
- **ਬਾਹਰ ਰੱਖਿਆ ਗਿਆ (`onnxruntime-node`):** ਇਹ ਸਥਾਨਕ AI embeddings ਲਈ ਇੱਕ ਵਿਕਲਪਿਕ dependency ਹੈ ਅਤੇ OmniRoute ਚਲਾਉਣ ਲਈ **ਲੋੜੀਂਦੀ ਨਹੀਂ** ਹੈ। ਇਸਦੀ postinstall ਸਕ੍ਰਿਪਟ NuGet ਤੋਂ ਲਗਭਗ 300MB ਦੇ CUDA assets ਡਾਊਨਲੋਡ ਕਰਦੀ ਹੈ; ਜਦੋਂ ਤੱਕ ਤੁਸੀਂ ਸਮਰਥਿਤ ਹਾਰਡਵੇਅਰ ਉੱਤੇ ਸਥਾਨਕ ONNX acceleration ਵਰਤਣ ਦਾ ਸਪਸ਼ਟ ਇਰਾਦਾ ਨਾ ਰੱਖਦੇ ਹੋਵੋ, ਇਸਨੂੰ allow-list ਵਿੱਚ ਸ਼ਾਮਲ ਨਾ ਕਰੋ।

### ਸਿਫ਼ਾਰਸ਼ ਕੀਤਾ ਹੱਲ

ਗਲੋਬਲ ਇੰਸਟਾਲੇਸ਼ਨ ਦੌਰਾਨ ਲੋੜੀਂਦੀਆਂ install ਸਕ੍ਰਿਪਟਾਂ ਨੂੰ ਆਗਿਆ ਦੇਣ ਅਤੇ ਚੇਤਾਵਨੀਆਂ ਨੂੰ ਸ਼ਾਂਤ ਕਰਨ ਲਈ, OmniRoute ਅਤੇ ਇਸ ਦੀਆਂ native dependencies ਵਾਸਤੇ `--allow-scripts` ਪਾਸ ਕਰੋ:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

ਵਿਕਲਪਕ ਤੌਰ 'ਤੇ, ਆਪਣੇ ਵਰਤੋਂਕਾਰ ਖਾਤੇ ਉੱਤੇ ਸਾਰੀਆਂ ਗਲੋਬਲ ਇੰਸਟਾਲੇਸ਼ਨਾਂ ਲਈ ਇਸਨੂੰ ਸਥਾਈ ਤੌਰ 'ਤੇ ਕੌਂਫਿਗਰ ਕਰਨ ਵਾਸਤੇ:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### ਆਪਣੀ ਇੰਸਟਾਲੇਸ਼ਨ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ

ਇੰਸਟਾਲੇਸ਼ਨ ਤੋਂ ਬਾਅਦ, ਇਹ ਯਕੀਨੀ ਬਣਾਉਣ ਲਈ ਬਿਲਟ-ਇਨ ਡਾਇਗਨੌਸਟਿਕ ਟੂਲ ਚਲਾਓ ਕਿ native ਬਾਈਂਡਿੰਗਾਂ ਅਤੇ ਰਨਟਾਈਮ ਵਾਤਾਵਰਣ ਠੀਕ ਹਨ:

```bash
omniroute doctor
```

## Gemini Web ਅਤੇ Playwright Chromium

ਜੇ Gemini Web ਦੀ ਬੇਨਤੀ `503` ਵਾਪਸ ਕਰਦੀ ਹੈ ਅਤੇ ਸੁਨੇਹਾ ਦਿੰਦੀ ਹੈ ਕਿ Playwright Chromium
ਇੰਸਟਾਲ ਨਹੀਂ ਹੈ, ਤਾਂ npm ਪੈਕੇਜ ਮੌਜੂਦ ਹੈ ਪਰ ਬ੍ਰਾਊਜ਼ਰ ਬਾਈਨਰੀ ਗੁੰਮ ਹੈ।
Playwright ਜਾਣ-ਬੁੱਝ ਕੇ ਬ੍ਰਾਊਜ਼ਰ ਡਾਊਨਲੋਡਾਂ ਨੂੰ npm ਪੈਕੇਜ
ਇੰਸਟਾਲੇਸ਼ਨ ਤੋਂ ਵੱਖ ਰੱਖਦਾ ਹੈ, ਇਸ ਲਈ ਬ੍ਰਾਊਜ਼ਰ ਇੰਸਟਾਲ ਹੋਣ ਤੱਕ ਇਹ ਜਵਾਬ ਉਮੀਦ ਅਨੁਸਾਰ ਹੈ।

ਗਲੋਬਲ npm ਇੰਸਟਾਲੇਸ਼ਨ ਲਈ, OmniRoute ਪੈਕੇਜ ਦੀ
ਡਾਇਰੈਕਟਰੀ ਤੋਂ Chromium ਇੰਸਟਾਲ ਕਰੋ, ਤਾਂ ਜੋ ਬ੍ਰਾਊਜ਼ਰ ਕੈਸ਼ ਉਸੇ Playwright ਇੰਸਟਾਲੇਸ਼ਨ ਨਾਲ ਸੰਬੰਧਿਤ ਹੋਵੇ:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ਇੰਸਟਾਲੇਸ਼ਨ ਤੋਂ ਬਾਅਦ OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ, ਫਿਰ Gemini Web ਦੀ ਬੇਨਤੀ ਦੁਬਾਰਾ ਅਜ਼ਮਾਓ। ਜੇ ਤੁਸੀਂ
OmniRoute ਨੂੰ Docker ਇਮੇਜ ਤੋਂ ਚਲਾਉਂਦੇ ਹੋ, ਤਾਂ `-web` ਇਮੇਜ (ਜਾਂ `runner-web`
ਬਿਲਡ ਟਾਰਗੇਟ) ਵਰਤੋ, ਜਿਸ ਵਿੱਚ Chromium ਅਤੇ ਇਸ ਦੀਆਂ ਡਿਪੈਂਡੈਂਸੀਆਂ ਸ਼ਾਮਲ ਹਨ; ਬੇਸ ਇਮੇਜ ਵਿੱਚ
ਇਹ ਸ਼ਾਮਲ ਨਹੀਂ ਹਨ।

## ਐਂਟੀਵਾਇਰਸ ਦੀਆਂ ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਚੇਤਾਵਨੀਆਂ

<a name="antivirus-false-positives"></a>

### Avast/AVG ਵੱਲੋਂ `README.md` ਨੂੰ `MD:HttpRequest-inf[Susp]` ਨਾਲ ਕਵਾਰੰਟੀਨ ਕਰਨਾ

**ਇਹ ਇੱਕ ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਹੈ। ਕੁਝ ਵੀ ਸੰਕਰਮਿਤ ਨਹੀਂ ਹੈ ਅਤੇ ਕਿਸੇ ਕਾਰਵਾਈ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ।**

Avast ਅਤੇ AVG ਇੱਕ heuristic ਚਲਾਉਂਦੇ ਹਨ ਜੋ ਬਹੁਤ ਸਾਰੇ HTTP ਬੇਨਤੀ ਵਰਗੇ ਦਿਸਣ ਵਾਲੇ ਲਿੰਕਾਂ ਵਾਲੀਆਂ
plain-text/Markdown ਫਾਈਲਾਂ ਨੂੰ ਫਲੈਗ ਕਰਦਾ ਹੈ। OmniRoute ਦੀ `README.md` npm package ਦੇ ਅੰਦਰ ਸ਼ਾਮਲ ਹੁੰਦੀ ਹੈ (ਇਹ
`package.json` → `files` ਵਿੱਚ ਸੂਚੀਬੱਧ ਹੈ), ਇਸ ਲਈ global install ਦੌਰਾਨ ਇਹ `node_modules/omniroute/README.md` ਵਿੱਚ
ਪਹੁੰਚ ਜਾਂਦੀ ਹੈ — ਅਤੇ ਇਸ ਵਿੱਚ ਲਗਭਗ 15 `http://localhost:20128/...` ਉਦਾਹਰਨਾਂ ਹਨ (MCP
HTTP/SSE endpoints, A2A `.well-known` URL ਅਤੇ `curl` snippets)। ਲਿੰਕਾਂ ਦੀ ਇਹ ਘਣਤਾ
heuristic ਨੂੰ ਚਾਲੂ ਕਰਨ ਲਈ ਕਾਫ਼ੀ ਹੈ।

ਜੇ ਇਹ ਹਾਲ ਹੀ ਵਿੱਚ ਹੀ ਸ਼ੁਰੂ ਹੋਇਆ ਹੈ: ਫਾਈਲ ਦੀ ਕਿਸਮ ਨਹੀਂ ਬਦਲੀ। README ਦੀ
endpoints ਸਾਰਣੀ ਵਧੀ ਹੈ (MCP HTTP + SSE + A2A ਸ਼ਾਮਲ ਕੀਤੇ ਗਏ ਸਨ) ਅਤੇ ਹੋਰ `curl` ਉਦਾਹਰਨਾਂ ਜੋੜੀਆਂ ਗਈਆਂ, ਜਿਸ ਕਾਰਨ
ਇਹ ਸੀਮਾ ਤੋਂ ਅੱਗੇ ਲੰਘ ਗਈ।

ਇਹ ਫਾਈਲ ਬਿਨਾਂ ਕਿਸੇ executable ਸਮੱਗਰੀ ਵਾਲਾ ਨਿਸ਼ਕ੍ਰਿਆ ਦਸਤਾਵੇਜ਼ ਹੈ। ਤੁਸੀਂ ਇਸਨੂੰ ਕਵਾਰੰਟੀਨ ਤੋਂ
ਸੁਰੱਖਿਅਤ ਢੰਗ ਨਾਲ restore ਕਰ ਸਕਦੇ ਹੋ।

**ਕੀ ਕਰਨਾ ਹੈ:**

1. **ਸੂਚਨਾਵਾਂ ਰੋਕੋ** — ਆਪਣੇ ਐਂਟੀਵਾਇਰਸ ਵਿੱਚ install directory ਨੂੰ exclude ਕਰੋ
   (Avast: Settings → Exceptions), ਅਤੇ ਆਪਣਾ global `node_modules` path ਅਤੇ/ਜਾਂ
   OmniRoute data dir (`~/.omniroute/`) ਸ਼ਾਮਲ ਕਰੋ।
2. **ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਦੀ ਰਿਪੋਰਟ ਕਰੋ** — <https://www.avast.com/false-positive-file-form.php>,
   ਅਤੇ ਕਵਾਰੰਟੀਨ ਕੀਤੀ `README.md` ਨੱਥੀ ਕਰੋ। ਇਹ ਉਹ ਹੱਲ ਹੈ ਜੋ ਹਰ ਕਿਸੇ ਦੀ ਮਦਦ ਕਰਦਾ ਹੈ, ਕਿਉਂਕਿ ਇਹ
   vendor ਦਾ heuristic ਹੈ ਜੋ ਇੱਕ text file ਉੱਤੇ ਲੋੜ ਤੋਂ ਵੱਧ ਪ੍ਰਤੀਕਿਰਿਆ ਕਰ ਰਿਹਾ ਹੈ।

**ਅਸੀਂ ਆਪਣੇ ਪਾਸੇ ਇਸਨੂੰ "ਠੀਕ" ਕਿਉਂ ਨਹੀਂ ਕਰਦੇ:** ਸਾਰੀਆਂ ਉਦਾਹਰਨਾਂ `http://localhost` ਹਨ, ਅਤੇ
self-signed-certificate ਦੀ ਔਖ ਤੋਂ ਬਿਨਾਂ localhost ਨੂੰ `https` ਨਹੀਂ ਬਣਾਇਆ ਜਾ ਸਕਦਾ। ਇੱਕ vendor ਦੇ heuristic ਤੋਂ
ਬਚਣ ਲਈ ਦਸਤਾਵੇਜ਼ਾਂ ਨੂੰ ਵਿਗਾੜਨਾ scanner ਦੀ ਖਾਮੀ ਨੂੰ ਸੰਤੁਸ਼ਟ ਕਰਨ ਵਾਸਤੇ ਹਰ ਪਾਠਕ ਨੂੰ ਨੁਕਸਾਨ ਪਹੁੰਚਾਏਗਾ।

### Kaspersky ਵੱਲੋਂ Desktop app ਨੂੰ `PDM:Trojan.Win32.Generic` ਵਜੋਂ ਫਲੈਗ ਕਰਨਾ

**ਇਹ behavioral heuristic ਤੋਂ ਆਇਆ ਇੱਕ ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਹੈ। ਕੁਝ ਵੀ ਸੰਕਰਮਿਤ ਨਹੀਂ ਹੈ।** Kaspersky ਦਾ
`PDM:` prefix ਦਰਸਾਉਂਦਾ ਹੈ ਕਿ ਇਹ ਫ਼ੈਸਲਾ ਇਸਦੇ Proactive Defense Module (System Watcher) ਤੋਂ ਆਇਆ ਹੈ,
ਜੋ ਜਾਣੇ-ਪਛਾਣੇ malware ਨਾਲ ਮਿਲਾਨ ਕਰਨ ਦੀ ਬਜਾਏ ਇਹ ਨਿਰਣਾ ਕਰਦਾ ਹੈ ਕਿ installer _ਕੀ ਕਰਦਾ ਹੈ_। ਜਦੋਂ
ਇਹ ਚਾਲੂ ਹੁੰਦਾ ਹੈ, Kaspersky ਪੂਰੀ installation ਨੂੰ "roll back" ਕਰ ਦਿੰਦਾ ਹੈ — ਪਹਿਲਾਂ ਹੀ
ਲਿਖੀਆਂ ਫਾਈਲਾਂ ਨੂੰ ਮਿਟਾਉਂਦਿਆਂ — ਇਸ ਲਈ app ਅੰਤ ਵਿੱਚ ਖਰਾਬ ਜਾਂ ਗਾਇਬ ਹੋ ਜਾਂਦੀ ਹੈ।

ਇਸ ਵੱਲੋਂ ਫਲੈਗ ਕੀਤੀਆਂ ਫਾਈਲਾਂ desktop app ਨਾਲ bundle ਕੀਤੀਆਂ ਘੋਸ਼ਿਤ, open-source dependencies ਦੇ
ਮਿਆਰੀ ਹਿੱਸੇ ਹਨ, ਉਦਾਹਰਨ ਵਜੋਂ:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ਅਤੇ
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), browser-automation
  library ਜੋ app ਦੇ ਅੰਦਰ provider login ਅਤੇ browser-backed chat ਲਈ ਵਰਤੀ ਜਾਂਦੀ ਹੈ।
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — web-cookie providers ਉੱਤੇ browser-fingerprinted HTTP ਲਈ ਵਰਤੀ ਜਾਣ ਵਾਲੀ pinned `wreq-js` native binding
  (`<arch>` `x64` ਜਾਂ `arm64` ਹੈ)।

**ਇਹ ਕਿਉਂ ਚਾਲੂ ਹੁੰਦਾ ਹੈ:** Windows installer ਹਾਲੇ **code-signed ਨਹੀਂ ਹੈ**, ਇਸ ਲਈ ਇੱਕ unsigned NSIS
installer ਦੀ reputation ਸਿਫ਼ਰ ਹੁੰਦੀ ਹੈ ਅਤੇ behavioral heuristics ਵੱਧ ਤੋਂ ਵੱਧ ਸਖ਼ਤੀ ਨਾਲ ਚੱਲਦੇ ਹਨ। ਇਸਦੇ ਨਾਲ
ਇੱਕ bundled native DLL ਅਤੇ `%LOCALAPPDATA%\Programs\OmniRoute` ਦੇ ਅਧੀਨ ਲਿਖੀਆਂ ਸੈਂਕੜੇ `.js` ਫਾਈਲਾਂ
(Next.js standalone build ਤੋਂ hash-suffixed package directories ਸਮੇਤ) ਹੋਣ ਕਾਰਨ,
ਇਹ heuristic ਨੂੰ ਚਾਲੂ ਕਰਨ ਲਈ ਕਾਫ਼ੀ ਹੈ। Code signing ਦੀ ਯੋਜਨਾ ਹੈ;
ਇਸ ਦੇ ਲਾਗੂ ਹੋਣ ਤੱਕ ਨਵੀਆਂ releases ਵਿੱਚ ਇਹ ਮੁੜ ਵਾਪਰ ਸਕਦਾ ਹੈ।

**ਕੀ ਕਰਨਾ ਹੈ:**

1. **ਪਹਿਲਾਂ ਆਪਣੇ download ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ** (ਇਸ ਨਾਲ ਛੇੜਛਾੜ ਕੀਤੀ ਫਾਈਲ ਦੀ ਸੰਭਾਵਨਾ ਖ਼ਾਰਜ ਹੋ ਜਾਂਦੀ ਹੈ)। ਹਰ release
   `latest.yml` ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦੀ ਹੈ, ਜਿਸਦਾ `sha512` field (base64) `OmniRoute.Setup.<version>.exe`
   installer ਨੂੰ cover ਕਰਦਾ ਹੈ। PowerShell ਵਿੱਚ, installer ਵਾਲੇ folder ਤੋਂ:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   output ਦਾ `latest.yml` → `sha512` ਨਾਲ ਮੇਲ ਖਾਣਾ ਲਾਜ਼ਮੀ ਹੈ। ਜੇ ਇਹ ਮੇਲ ਨਹੀਂ ਖਾਂਦਾ, ਤਾਂ ਫਾਈਲ ਮਿਟਾਓ ਅਤੇ
   ਸਿਰਫ਼ [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) ਤੋਂ ਮੁੜ download ਕਰੋ।
2. **Restore + exclude ਕਰੋ** — ਕਵਾਰੰਟੀਨ ਤੋਂ roll back ਕੀਤੀਆਂ items ਨੂੰ restore ਕਰੋ ਅਤੇ
   `%LOCALAPPDATA%\Programs\OmniRoute` ਲਈ exclusion ਸ਼ਾਮਲ ਕਰੋ (Kaspersky → Settings → Threats and Exclusions),
   ਫਿਰ ਦੁਬਾਰਾ install ਕਰੋ।
3. **ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਦੀ ਰਿਪੋਰਟ ਕਰੋ** — <https://opentip.kaspersky.com/>। ਵਰਤੋਂਕਾਰਾਂ ਵੱਲੋਂ ਜਮ੍ਹਾਂ ਕੀਤੀਆਂ FP
   reports ਵਾਸਤਵ ਵਿੱਚ allowlisting ਨੂੰ ਤੇਜ਼ ਕਰਦੀਆਂ ਹਨ।

## Node.js ਅਨੁਕੂਲਤਾ

<a name="nodejs-compatibility"></a>

### ਲੌਗਇਨ ਪੰਨਾ ਕ੍ਰੈਸ਼ ਹੋ ਜਾਂਦਾ ਹੈ ਜਾਂ "Module self-registration" ਗਲਤੀ ਦਿਖਾਉਂਦਾ ਹੈ

**ਕਾਰਨ:** ਤੁਸੀਂ Node.js ਦਾ ਅਜਿਹਾ ਵਰਜਨ ਚਲਾ ਰਹੇ ਹੋ ਜੋ OmniRoute ਦੀ ਮਨਜ਼ੂਰਸ਼ੁਦਾ ਸੁਰੱਖਿਅਤ ਰਨਟਾਈਮ ਦੀ ਘੱਟੋ-ਘੱਟ ਸੀਮਾ ਤੋਂ ਬਾਹਰ ਹੈ। ਸਭ ਤੋਂ ਆਮ ਸਥਿਤੀ Node 22 ਜਾਂ 24 ਦਾ ਅਜਿਹਾ ਪੁਰਾਣਾ ਪੈਚ ਪੱਧਰ ਚਲਾਉਣਾ ਹੈ ਜੋ OmniRoute ਵੱਲੋਂ ਲੋੜੀਂਦੀ ਪੈਚ ਕੀਤੀ ਸੁਰੱਖਿਆ ਸੀਮਾ ਤੋਂ ਹੇਠਾਂ ਹੈ।

**ਲੱਛਣ:**

- ਲੌਗਇਨ ਪੰਨਾ ਖਾਲੀ ਸਕ੍ਰੀਨ ਜਾਂ ਸਰਵਰ ਗਲਤੀ ਦਿਖਾਉਂਦਾ ਹੈ
- ਕੰਸੋਲ ਵਿੱਚ `Error: Module did not self-register` ਜਾਂ ਇਸ ਤਰ੍ਹਾਂ ਦੀਆਂ ਨੇਟਿਵ ਬਾਈਂਡਿੰਗ ਗਲਤੀਆਂ ਦਿਖਾਈ ਦਿੰਦੀਆਂ ਹਨ
- ਜੇ ਰਨਟਾਈਮ ਸਮਰਥਿਤ ਸੁਰੱਖਿਅਤ ਨੀਤੀ ਤੋਂ ਬਾਹਰ ਹੈ, ਤਾਂ ਲੌਗਇਨ ਪੰਨੇ ਉੱਤੇ ਤੁਹਾਡੇ Node ਵਰਜਨ ਸਮੇਤ ਇੱਕ **ਸੰਤਰੀ ਚੇਤਾਵਨੀ ਬੈਨਰ** ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ

**ਹੱਲ:**

1. Node.js ਦਾ ਸਮਰਥਿਤ LTS ਰਿਲੀਜ਼ ਇੰਸਟਾਲ ਕਰੋ (ਸਿਫ਼ਾਰਸ਼ੀ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ਆਪਣੇ ਵਰਜਨ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ: `node --version` ਨੂੰ 24.x LTS ਲਾਈਨ ਉੱਤੇ `v24.0.0` ਜਾਂ ਇਸ ਤੋਂ ਨਵਾਂ ਵਰਜਨ ਦਿਖਾਉਣਾ ਚਾਹੀਦਾ ਹੈ
3. OmniRoute ਨੂੰ ਮੁੜ ਇੰਸਟਾਲ ਕਰੋ: `npm install -g omniroute`
4. ਮੁੜ ਚਾਲੂ ਕਰੋ: `omniroute`

> **ਸਮਰਥਿਤ ਸੁਰੱਖਿਅਤ ਵਰਜਨ:** `>=22.22.2 <23` ਜਾਂ `>=24.0.0 <27`। Node.js 24.x LTS (Krypton) ਅਤੇ Node.js 26 ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਮਰਥਿਤ ਹਨ।

### npm v11+: `better-sqlite3` ਇੰਸਟਾਲ ਨਹੀਂ ਹੋਇਆ (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**ਕਾਰਨ:** npm v11 (Node.js 24+ ਨਾਲ ਸ਼ਾਮਲ) ਮੂਲ ਰੂਪ ਵਿੱਚ ਵਿਕਲਪਿਕ
ਨਿਰਭਰਤਾਵਾਂ ਲਈ ਇੰਸਟਾਲ ਸਕ੍ਰਿਪਟਾਂ ਨੂੰ ਬਲੌਕ ਕਰਦਾ ਹੈ। ਕਿਉਂਕਿ `better-sqlite3` ਨੂੰ `optionalDependencies`
ਵਿੱਚ ਸੂਚੀਬੱਧ ਕੀਤਾ ਗਿਆ ਹੈ ਅਤੇ ਇਸ ਲਈ ਨੇਟਿਵ ਕੰਪਾਇਲੇਸ਼ਨ (`node-gyp rebuild`) ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ, npm ਬਿਨਾਂ ਕੋਈ ਸੂਚਨਾ ਦਿੱਤੇ ਇਸਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ।

**ਲੱਛਣ:**

- ਸਰਵਰ ਸਟਾਰਟਅੱਪ ਵੇਲੇ `Cannot find module 'better-sqlite3'` ਨਾਲ ਕ੍ਰੈਸ਼ ਹੋ ਜਾਂਦਾ ਹੈ
- `ls node_modules/better-sqlite3` "No such file or directory" ਦਿਖਾਉਂਦਾ ਹੈ
- `npm ls better-sqlite3` `(empty)` ਦਿਖਾਉਂਦਾ ਹੈ

**ਹੱਲ:**

1. ਇੰਸਟਾਲ ਸਕ੍ਰਿਪਟਾਂ ਨੂੰ ਮਨਜ਼ੂਰੀ ਦਿਓ ਅਤੇ ਮੁੜ ਇੰਸਟਾਲ ਕਰੋ:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ਜਾਂ ਪਹਿਲਾਂ ਤੋਂ ਬਣੇ ਪੈਕੇਜ ਨੂੰ ਹੱਥੀਂ ਇੰਸਟਾਲ ਕਰੋ:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਇਹ ਕੰਮ ਕਰਦਾ ਹੈ: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**ਕਾਰਨ:** ਗਲੋਬਲ `npm install -g omniroute` ਤੋਂ ਬਾਅਦ, ਪੈਕੇਜ ਦੇ ਅੰਦਰ ਮੌਜੂਦ `better-sqlite3` ਨੇਟਿਵ ਬਾਈਨਰੀ ਸੰਭਵ ਹੈ ਕਿ ਸਥਾਨਕ ਤੌਰ ਉੱਤੇ ਚੱਲ ਰਹੇ ਆਰਕੀਟੈਕਚਰ ਜਾਂ Node.js ABI ਤੋਂ ਵੱਖਰੇ ਆਰਕੀਟੈਕਚਰ ਜਾਂ ABI ਲਈ ਕੰਪਾਇਲ ਕੀਤੀ ਗਈ ਹੋਵੇ। ਇਹ macOS (Apple Silicon ਅਤੇ Intel ਦੋਵਾਂ) ਉੱਤੇ ਆਮ ਹੁੰਦਾ ਹੈ, ਜਦੋਂ ਪਹਿਲਾਂ ਤੋਂ ਬਣੀ ਬਾਈਨਰੀ ਤੁਹਾਡੇ ਵਾਤਾਵਰਣ ਨਾਲ ਮੇਲ ਨਹੀਂ ਖਾਂਦੀ।

**ਲੱਛਣ:**

- ਸਰਵਰ ਸਟਾਰਟਅੱਪ ਵੇਲੇ ਤੁਰੰਤ `dlopen` ਗਲਤੀ ਨਾਲ ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ
- ਗਲਤੀ ਵਿੱਚ `slice is not valid mach-o file` ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ
- ਪੂਰੀ ਉਦਾਹਰਨ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ਹੱਲ — ਆਪਣੇ ਸਥਾਨਕ ਵਾਤਾਵਰਣ ਲਈ ਮੁੜ ਬਿਲਡ ਕਰੋ (Node.js ਨੂੰ ਡਾਊਨਗ੍ਰੇਡ ਕਰਨ ਦੀ ਲੋੜ ਨਹੀਂ):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ਨੋਟ:** ਇਹ ਨੇਟਿਵ ਬਾਈਂਡਿੰਗ ਨੂੰ ਤੁਹਾਡੇ ਸਥਾਨਕ Node.js ਵਰਜਨ ਅਤੇ CPU ਆਰਕੀਟੈਕਚਰ ਦੇ ਅਨੁਸਾਰ ਮੁੜ ਕੰਪਾਇਲ ਕਰਦਾ ਹੈ, ਜਿਸ ਨਾਲ ਬਾਈਨਰੀ ਦਾ ਬੇਮੇਲ ਹੱਲ ਹੋ ਜਾਂਦਾ ਹੈ। ਅਧਿਕਾਰਤ ਤੌਰ ਉੱਤੇ ਸਮਰਥਿਤ ਰਨਟਾਈਮ ਰੇਂਜ **`>=22.22.2 <23` ਜਾਂ `>=24.0.0 <27`** ਹੈ (`src/shared/utils/nodeRuntimeSupport.ts` ਵਿੱਚ `SUPPORTED_NODE_RANGE`, ਜੋ `package.json` ਦੇ `engines` ਫ਼ੀਲਡ ਨਾਲ ਇਕਸਾਰ ਹੈ)। Node.js 24.x LTS (Krypton) ਅਤੇ Node.js 26, `better-sqlite3` v12.x ਨਾਲ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਮਰਥਿਤ ਹਨ।

## ਪ੍ਰੌਕਸੀ ਸੰਬੰਧੀ ਸਮੱਸਿਆਵਾਂ

<a name="proxy-issues"></a>

### ਪ੍ਰਦਾਤਾ ਪ੍ਰਮਾਣਿਕਤਾ ਦੌਰਾਨ "fetch failed" ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ

**ਕਾਰਨ:** API ਕੁੰਜੀ ਪ੍ਰਮਾਣਿਕਤਾ ਐਂਡਪੌਇੰਟ (`POST /api/providers/validate`) ਪਹਿਲਾਂ ਪ੍ਰੌਕਸੀ ਸੰਰਚਨਾ ਨੂੰ ਬਾਈਪਾਸ ਕਰ ਰਿਹਾ ਸੀ, ਜਿਸ ਕਾਰਨ ਪ੍ਰੌਕਸੀ ਰੂਟਿੰਗ ਦੀ ਲੋੜ ਵਾਲੇ ਵਾਤਾਵਰਣਾਂ ਵਿੱਚ ਅਸਫਲਤਾਵਾਂ ਹੁੰਦੀਆਂ ਸਨ।

**ਹੱਲ (v3.5.5+):** ਹੁਣ ਇਹ ਸਮੱਸਿਆ ਹੱਲ ਹੋ ਗਈ ਹੈ। ਪ੍ਰਦਾਤਾ ਪ੍ਰਮਾਣਿਕਤਾ `runWithProxyContext` ਰਾਹੀਂ ਰੂਟ ਹੁੰਦੀ ਹੈ ਅਤੇ ਆਪਣੇ ਆਪ ਪ੍ਰਦਾਤਾ-ਪੱਧਰੀ ਅਤੇ ਗਲੋਬਲ ਪ੍ਰੌਕਸੀ ਸੈਟਿੰਗਾਂ ਦੀ ਪਾਲਣਾ ਕਰਦੀ ਹੈ।

### ਟੋਕਨ ਸਿਹਤ ਜਾਂਚ "fetch failed" ਨਾਲ ਅਸਫਲ ਹੁੰਦੀ ਹੈ

**ਕਾਰਨ:** ਬੈਕਗ੍ਰਾਊਂਡ OAuth ਟੋਕਨ ਰਿਫ੍ਰੈਸ਼ ਹਰੇਕ ਕਨੈਕਸ਼ਨ ਲਈ ਪ੍ਰੌਕਸੀ ਸੰਰਚਨਾ ਨੂੰ ਰਿਜ਼ਾਲਵ ਨਹੀਂ ਕਰ ਰਿਹਾ ਸੀ।

**ਹੱਲ (v3.5.5+):** ਟੋਕਨ ਸਿਹਤ ਜਾਂਚ ਸ਼ਡਿਊਲਰ ਹੁਣ ਰਿਫ੍ਰੈਸ਼ ਕਰਨ ਦੀ ਕੋਸ਼ਿਸ਼ ਤੋਂ ਪਹਿਲਾਂ ਹਰੇਕ ਕਨੈਕਸ਼ਨ ਲਈ ਪ੍ਰੌਕਸੀ ਸੰਰਚਨਾ ਨੂੰ ਰਿਜ਼ਾਲਵ ਕਰਦਾ ਹੈ। v3.5.5+ 'ਤੇ ਅੱਪਡੇਟ ਕਰੋ।

### SOCKS5 ਪ੍ਰੌਕਸੀ "invalid onRequestStart method" ਵਾਪਸ ਕਰਦੀ ਹੈ

**ਕਾਰਨ:** Node.js 22 ਉੱਤੇ, undici@8 ਡਿਸਪੈਚਰ Node ਦੇ ਬਿਲਟ-ਇਨ `fetch()` ਇੰਪਲੀਮੈਂਟੇਸ਼ਨ ਨਾਲ ਅਨੁਕੂਲ ਨਹੀਂ ਹੈ।

**ਹੱਲ (v3.5.5+):** ਜਦੋਂ ਕੋਈ ਪ੍ਰੌਕਸੀ ਡਿਸਪੈਚਰ ਸਰਗਰਮ ਹੁੰਦਾ ਹੈ, ਤਾਂ OmniRoute ਹੁਣ undici ਦੇ ਆਪਣੇ `fetch()` ਫੰਕਸ਼ਨ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ, ਜਿਸ ਨਾਲ ਇਕਸਾਰ ਵਿਹਾਰ ਯਕੀਨੀ ਬਣਦਾ ਹੈ। v3.5.5+ 'ਤੇ ਅੱਪਡੇਟ ਕਰੋ।

### WSL ਅਧੀਨ MITM ਪ੍ਰੌਕਸੀ: Windows ਹੋਸਟ ਉੱਤੇ ਡੈਸਕਟਾਪ ਐਪਾਂ ਇੰਟਰਸੈਪਟ ਨਹੀਂ ਹੁੰਦੀਆਂ

**ਕਾਰਨ:** MITM ਪ੍ਰੌਕਸੀ ਅਤੇ ਇਸਦਾ CA ਸਰਟੀਫਿਕੇਟ ਉਸ ਵਾਤਾਵਰਣ ਵਿੱਚ ਇੰਸਟਾਲ ਹੁੰਦੇ ਹਨ ਜਿੱਥੇ OmniRoute ਚੱਲਦਾ ਹੈ। WSL ਅਧੀਨ ਉਹ ਵਾਤਾਵਰਣ Linux ਗੈਸਟ ਹੁੰਦਾ ਹੈ, ਜਦਕਿ AI ਡੈਸਕਟਾਪ ਐਪਾਂ (Kiro, Trae, Copilot, Zed, …) Windows ਹੋਸਟ ਉੱਤੇ ਚੱਲਦੀਆਂ ਹਨ। ਹੋਸਟ ਐਪਾਂ ਗੈਸਟ ਦੇ ਸਰਟੀਫਿਕੇਟ ਸਟੋਰ ਉੱਤੇ ਭਰੋਸਾ ਨਹੀਂ ਕਰਦੀਆਂ ਅਤੇ ਗੈਸਟ ਦੀ ਸਿਸਟਮ ਪ੍ਰੌਕਸੀ ਰਾਹੀਂ ਰੂਟ ਨਹੀਂ ਹੁੰਦੀਆਂ, ਇਸ ਲਈ ਉੱਥੇ ਡੈਸਕਟਾਪ ਇੰਟਰਸੈਪਸ਼ਨ ਸਰਗਰਮ ਨਹੀਂ ਹੁੰਦਾ।

**ਸਿਫ਼ਾਰਸ਼:** OmniRoute ਨੂੰ ਮੂਲ ਰੂਪ ਵਿੱਚ ਉਸੇ OS ਉੱਤੇ ਚਲਾਓ ਜਿਸ ਉੱਤੇ ਉਹ ਡੈਸਕਟਾਪ ਐਪਾਂ ਚੱਲਦੀਆਂ ਹਨ ਜਿਨ੍ਹਾਂ ਨੂੰ ਤੁਸੀਂ ਇੰਟਰਸੈਪਟ ਕਰਨਾ ਚਾਹੁੰਦੇ ਹੋ (Windows ਐਪਾਂ ਲਈ Windows; macOS/Linux ਲਈ ਵੀ ਇਸੇ ਤਰ੍ਹਾਂ)। ਹੋਸਟ ਐਪਾਂ ਨੂੰ ਨਿਸ਼ਾਨਾ ਬਣਾਉਂਦੇ ਹੋਏ OmniRoute ਨੂੰ WSL ਦੇ ਅੰਦਰ ਰੱਖਣ ਲਈ, ਤਿਆਰ ਕੀਤੇ CA ਸਰਟੀਫਿਕੇਟ ਉੱਤੇ Windows ਹੋਸਟ ਵਿੱਚ ਹੱਥੀਂ ਭਰੋਸਾ ਕਰਨਾ ਅਤੇ ਹਰੇਕ ਹੋਸਟ ਐਪ ਦੀਆਂ ਨੈੱਟਵਰਕ/ਪ੍ਰੌਕਸੀ ਸੈਟਿੰਗਾਂ ਨੂੰ WSL ਪ੍ਰੌਕਸੀ ਐਂਡਪੌਇੰਟ ਵੱਲ ਨਿਰਦੇਸ਼ਿਤ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ — ਇਹ ਇੱਕ ਅਸਮਰਥਿਤ ਅਤੇ ਅਸਥਿਰ ਸੈੱਟਅੱਪ ਹੈ।

## ਕਲਾਉਡ ਸਮੱਸਿਆਵਾਂ

### ਕਲਾਉਡ ਸਿੰਕ ਗਲਤੀਆਂ

1. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `BASE_URL` ਤੁਹਾਡੀ ਚੱਲ ਰਹੀ ਇੰਸਟੈਂਸ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ (ਉਦਾਹਰਨ ਲਈ, `http://localhost:20128`)
2. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `CLOUD_URL` ਤੁਹਾਡੇ ਕਲਾਉਡ ਐਂਡਪੌਇੰਟ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ (ਉਦਾਹਰਨ ਲਈ, `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` ਮੁੱਲਾਂ ਨੂੰ ਸਰਵਰ-ਸਾਈਡ ਮੁੱਲਾਂ ਨਾਲ ਇਕਸਾਰ ਰੱਖੋ

### ਕਲਾਉਡ `stream=false` 500 ਵਾਪਸ ਕਰਦਾ ਹੈ

**ਲੱਛਣ:** ਗੈਰ-ਸਟ੍ਰੀਮਿੰਗ ਕਾਲਾਂ ਲਈ ਕਲਾਉਡ ਐਂਡਪੌਇੰਟ ਉੱਤੇ `Unexpected token 'd'...`।

**ਕਾਰਨ:** ਅੱਪਸਟ੍ਰੀਮ SSE ਪੇਲੋਡ ਵਾਪਸ ਕਰਦਾ ਹੈ, ਜਦਕਿ ਕਲਾਇੰਟ JSON ਦੀ ਉਮੀਦ ਕਰਦਾ ਹੈ।

**ਅਸਥਾਈ ਹੱਲ:** ਕਲਾਉਡ ਨੂੰ ਸਿੱਧੀਆਂ ਕਾਲਾਂ ਲਈ `stream=true` ਵਰਤੋ। ਲੋਕਲ ਰਨਟਾਈਮ ਵਿੱਚ SSE→JSON ਫਾਲਬੈਕ ਸ਼ਾਮਲ ਹੈ।

### ਕਲਾਉਡ ਕਨੈਕਟਡ ਦਿਖਾਉਂਦਾ ਹੈ ਪਰ "Invalid API key"

1. ਲੋਕਲ ਡੈਸ਼ਬੋਰਡ (`/api/keys`) ਤੋਂ ਇੱਕ ਨਵੀਂ ਕੁੰਜੀ ਬਣਾਓ
2. ਕਲਾਉਡ ਸਿੰਕ ਚਲਾਓ: Enable Cloud → Sync Now
3. ਪੁਰਾਣੀਆਂ/ਸਿੰਕ ਨਾ ਹੋਈਆਂ ਕੁੰਜੀਆਂ ਹਾਲੇ ਵੀ ਕਲਾਉਡ ਉੱਤੇ `401` ਵਾਪਸ ਕਰ ਸਕਦੀਆਂ ਹਨ

## Docker ਸਮੱਸਿਆਵਾਂ

### Docker IPv6 / ਕਨੈਕਸ਼ਨ ਰੀਸੈੱਟ

<a name="docker-ipv6"></a>

**ਲੱਛਣ:** `curl http://localhost:20128/v1/models` ਚਲਾਉਣ ਉੱਤੇ `curl: (56) Recv failure: Connection reset by peer` ਵਾਪਸ ਆਉਂਦਾ ਹੈ। ਡੈਸ਼ਬੋਰਡ ਅਤੇ ਬਿਨਾਂ ਪ੍ਰਮਾਣੀਕਰਨ ਵਾਲੇ ਐਂਡਪੌਇੰਟ ਕੰਮ ਕਰਦੇ ਹਨ, ਪਰ ਪ੍ਰਮਾਣੀਕ੍ਰਿਤ ਐਂਡਪੌਇੰਟ ਅਸਫਲ ਹੋ ਜਾਂਦੇ ਹਨ — ਇਹ ਪ੍ਰਮਾਣੀਕਰਨ ਦੀ ਸਮੱਸਿਆ ਲੱਗਦੀ ਹੈ, ਪਰ ਅਸਲ ਵਿੱਚ ਨਹੀਂ ਹੈ।

**ਕਾਰਨ:** `docker run -p 20128:20128` `0.0.0.0` (IPv4) ਅਤੇ `::` (IPv6) ਦੋਵਾਂ ਉੱਤੇ ਪੋਰਟ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ, ਪਰ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰਲੀ ਪ੍ਰਕਿਰਿਆ ਸਿਰਫ਼ IPv4 ਉੱਤੇ ਸੁਣਦੀ ਹੈ। ਉਹਨਾਂ ਹੋਸਟਾਂ ਉੱਤੇ ਜਿੱਥੇ `localhost` ਪਹਿਲਾਂ `::1` ਵਿੱਚ ਰਿਜ਼ਾਲਵ ਹੁੰਦਾ ਹੈ, ਕਨੈਕਸ਼ਨ IPv6 ਰਾਹੀਂ ਪ੍ਰਕਾਸ਼ਿਤ ਪੋਰਟ ਉੱਤੇ ਪਹੁੰਚਦਾ ਹੈ, ਜਿਸ ਦੇ ਪਿੱਛੇ ਕੋਈ ਲਿਸਨਰ ਨਹੀਂ ਹੁੰਦਾ → ਕਨੈਕਸ਼ਨ ਰੀਸੈੱਟ।

**ਹੱਲ:**

1. **ਤੁਰੰਤ ਜਾਂਚ:** `curl -4 http://localhost:20128/v1/models` ਚਲਾਓ। ਜੇ ਇਹ `-4` ਨਾਲ ਕੰਮ ਕਰਦਾ ਹੈ ਪਰ ਇਸ ਤੋਂ ਬਿਨਾਂ ਅਸਫਲ ਹੁੰਦਾ ਹੈ, ਤਾਂ ਤੁਹਾਡੇ ਕੋਲ IPv6 ਬਾਈਂਡ ਬੇਮੇਲ ਹੈ।
2. **ਸਥਾਈ ਹੱਲ:** ਆਪਣੀ `docker run` ਕਮਾਂਡ ਵਿੱਚ `-p 127.0.0.1:20128:20128` ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਸਪਸ਼ਟ ਤੌਰ ਉੱਤੇ IPv4 ਨਾਲ ਬਾਈਂਡ ਕਰੋ:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
   ```

## ਡੀਬੱਗਿੰਗ

### ਲਾਗ ਫਾਈਲਾਂ ਸਮਰੱਥ ਕਰੋ

ਆਪਣੀ `.env` ਫਾਈਲ ਵਿੱਚ `APP_LOG_TO_FILE=true` ਸੈੱਟ ਕਰੋ। ਐਪਲੀਕੇਸ਼ਨ ਲਾਗ `logs/` ਦੇ ਅਧੀਨ ਲਿਖੇ ਜਾਂਦੇ ਹਨ।
ਜਦੋਂ ਸੈਟਿੰਗਾਂ ਵਿੱਚ ਕਾਲ ਲਾਗ ਪਾਈਪਲਾਈਨ ਸਮਰੱਥ ਹੁੰਦੀ ਹੈ, ਤਾਂ ਬੇਨਤੀ ਆਰਟੀਫੈਕਟ `${DATA_DIR}/call_logs/` ਦੇ ਅਧੀਨ ਸਟੋਰ ਕੀਤੇ ਜਾਂਦੇ ਹਨ।
ਜਦੋਂ ਪਾਈਪਲਾਈਨ ਕੈਪਚਰ ਸਮਰੱਥ ਹੋਵੇ, ਤਾਂ ਸਟ੍ਰੀਮ ਚੰਕ ਪੇਲੋਡਾਂ ਨੂੰ ਛੱਡਣ ਲਈ `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` ਸੈੱਟ ਕਰੋ, ਜਾਂ ਆਰਟੀਫੈਕਟ ਦੀ KB ਸੀਮਾ ਬਦਲਣ ਲਈ `CALL_LOG_PIPELINE_MAX_SIZE_KB` ਨੂੰ ਅਨੁਕੂਲ ਕਰੋ।

### ਪ੍ਰੋਵਾਈਡਰ ਦੀ ਸਥਿਤੀ ਜਾਂਚੋ

```bash
# ਸਥਿਤੀ ਡੈਸ਼ਬੋਰਡ
http://localhost:20128/dashboard/health

# API ਸਥਿਤੀ ਜਾਂਚ
curl http://localhost:20128/api/monitoring/health
```

### ਰਨਟਾਈਮ ਸਟੋਰੇਜ

- ਮੁੱਖ ਸਥਿਤੀ: `${DATA_DIR}/storage.sqlite` (ਪ੍ਰੋਵਾਈਡਰ, ਕੌਂਬੋ, ਉਪਨਾਮ, ਕੁੰਜੀਆਂ, ਸੈਟਿੰਗਾਂ)
- ਵਰਤੋਂ: `storage.sqlite` ਵਿੱਚ SQLite ਟੇਬਲਾਂ (`usage_history`, `call_logs`, `proxy_logs`) + ਵਿਕਲਪਿਕ `${DATA_DIR}/call_logs/`
- ਐਪਲੀਕੇਸ਼ਨ ਲਾਗ: `<repo>/logs/...` (ਜਦੋਂ `APP_LOG_TO_FILE=true` ਹੋਵੇ)
- ਕਾਲ ਲਾਗ ਆਰਟੀਫੈਕਟ: ਜਦੋਂ ਕਾਲ ਲਾਗ ਪਾਈਪਲਾਈਨ ਸਮਰੱਥ ਹੋਵੇ ਤਾਂ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs ਪੰਨੇ ਦੀ **Clean history** ਕਾਰਵਾਈ `call_logs`, ਪੁਰਾਣੇ
`request_detail_logs`, ਅਤੇ ਲੋਕਲ `${DATA_DIR}/call_logs/` ਆਰਟੀਫੈਕਟ ਡਾਇਰੈਕਟਰੀ ਨੂੰ ਸਾਫ਼ ਕਰਦੀ ਹੈ।

## ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਸੰਬੰਧੀ ਸਮੱਸਿਆਵਾਂ

### ਪ੍ਰਦਾਤਾ OPEN ਸਥਿਤੀ ਵਿੱਚ ਅਟਕਿਆ ਹੋਇਆ ਹੈ

ਜਦੋਂ ਕਿਸੇ ਪ੍ਰਦਾਤਾ ਦਾ ਸਰਕਿਟ ਬ੍ਰੇਕਰ OPEN ਹੁੰਦਾ ਹੈ, ਤਾਂ ਕੂਲਡਾਊਨ ਦੀ ਮਿਆਦ ਖਤਮ ਹੋਣ ਤੱਕ ਬੇਨਤੀਆਂ ਬਲੌਕ ਰਹਿੰਦੀਆਂ ਹਨ।

**ਹੱਲ:**

1. **Dashboard → Settings → Resilience** 'ਤੇ ਜਾਓ
2. ਪ੍ਰਭਾਵਿਤ ਪ੍ਰਦਾਤਾ ਲਈ ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਕਾਰਡ ਦੀ ਜਾਂਚ ਕਰੋ
3. ਸਾਰੇ ਬ੍ਰੇਕਰ ਸਾਫ਼ ਕਰਨ ਲਈ **Reset All** 'ਤੇ ਕਲਿੱਕ ਕਰੋ, ਜਾਂ ਕੂਲਡਾਊਨ ਦੀ ਮਿਆਦ ਖਤਮ ਹੋਣ ਦੀ ਉਡੀਕ ਕਰੋ
4. ਰੀਸੈੱਟ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਪ੍ਰਦਾਤਾ ਵਾਸਤਵ ਵਿੱਚ ਉਪਲਬਧ ਹੈ

### ਪ੍ਰਦਾਤਾ ਵਾਰ-ਵਾਰ ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਟ੍ਰਿਪ ਕਰਦਾ ਹੈ

ਜੇ ਕੋਈ ਪ੍ਰਦਾਤਾ ਵਾਰ-ਵਾਰ OPEN ਸਥਿਤੀ ਵਿੱਚ ਜਾਂਦਾ ਹੈ:

1. ਅਸਫਲਤਾ ਦੇ ਪੈਟਰਨ ਲਈ **Dashboard → Health → Provider Health** ਦੀ ਜਾਂਚ ਕਰੋ
2. **Settings → Resilience → Provider Profiles** 'ਤੇ ਜਾਓ ਅਤੇ ਅਸਫਲਤਾ ਦੀ ਸੀਮਾ ਵਧਾਓ
3. ਜਾਂਚ ਕਰੋ ਕਿ ਕੀ ਪ੍ਰਦਾਤਾ ਨੇ API ਸੀਮਾਵਾਂ ਬਦਲੀਆਂ ਹਨ ਜਾਂ ਮੁੜ ਪ੍ਰਮਾਣੀਕਰਨ ਦੀ ਲੋੜ ਹੈ
4. ਲੇਟੈਂਸੀ ਟੈਲੀਮੀਟਰੀ ਦੀ ਸਮੀਖਿਆ ਕਰੋ — ਵੱਧ ਲੇਟੈਂਸੀ ਟਾਈਮਆਉਟ-ਆਧਾਰਿਤ ਅਸਫਲਤਾਵਾਂ ਦਾ ਕਾਰਨ ਬਣ ਸਕਦੀ ਹੈ

## ਲਚਕੀਲੇਪਣ ਦੀਆਂ ਸੈਟਿੰਗਾਂ

### ਆਟੋ ਰੇਟ-ਲਿਮਿਟ ਟ੍ਰਿਗਰ ਨਹੀਂ ਹੋ ਰਹੀ

- ਆਟੋ ਰੇਟ-ਲਿਮਿਟ ਸਿਰਫ਼ API ਕੁੰਜੀ ਪ੍ਰਦਾਤਾਵਾਂ 'ਤੇ ਲਾਗੂ ਹੁੰਦੀ ਹੈ (OAuth/ਸਬਸਕ੍ਰਿਪਸ਼ਨ 'ਤੇ ਨਹੀਂ)
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ **Settings → Resilience → Provider Profiles** ਵਿੱਚ ਆਟੋ ਰੇਟ-ਲਿਮਿਟ ਸਮਰੱਥ ਹੈ
- ਜਾਂਚ ਕਰੋ ਕਿ ਕੀ ਪ੍ਰਦਾਤਾ `429` ਸਟੇਟਸ ਕੋਡ ਜਾਂ `Retry-After` ਹੈਡਰ ਵਾਪਸ ਕਰਦਾ ਹੈ

### ਐਕਸਪੋਨੇਨਸ਼ੀਅਲ ਬੈਕਆਫ਼ ਨੂੰ ਟਿਊਨ ਕਰਨਾ

ਪ੍ਰਦਾਤਾ ਪ੍ਰੋਫ਼ਾਈਲ ਇਹਨਾਂ ਸੈਟਿੰਗਾਂ ਦਾ ਸਮਰਥਨ ਕਰਦੇ ਹਨ:

- **ਮੂਲ ਦੇਰੀ** — ਪਹਿਲੀ ਅਸਫਲਤਾ ਤੋਂ ਬਾਅਦ ਸ਼ੁਰੂਆਤੀ ਉਡੀਕ ਸਮਾਂ (ਡਿਫੌਲਟ: 1s)
- **ਵੱਧ ਤੋਂ ਵੱਧ ਦੇਰੀ** — ਉਡੀਕ ਸਮੇਂ ਦੀ ਵੱਧ ਤੋਂ ਵੱਧ ਸੀਮਾ (ਡਿਫੌਲਟ: 30s)
- **ਗੁਣਕ** — ਹਰ ਲਗਾਤਾਰ ਅਸਫਲਤਾ ਨਾਲ ਦੇਰੀ ਕਿੰਨੀ ਵਧਾਉਣੀ ਹੈ (ਡਿਫੌਲਟ: 2x)

### ਐਂਟੀ-ਥੰਡਰਿੰਗ ਹਰਡ

ਜਦੋਂ ਬਹੁਤ ਸਾਰੀਆਂ ਸਮਕਾਲੀ ਬੇਨਤੀਆਂ ਕਿਸੇ ਰੇਟ-ਲਿਮਿਟ ਕੀਤੇ ਪ੍ਰਦਾਤਾ ਤੱਕ ਪਹੁੰਚਦੀਆਂ ਹਨ, ਤਾਂ OmniRoute ਬੇਨਤੀਆਂ ਨੂੰ ਕ੍ਰਮਵਾਰ ਕਰਨ ਅਤੇ ਲੜੀਵਾਰ ਅਸਫਲਤਾਵਾਂ ਨੂੰ ਰੋਕਣ ਲਈ mutex + ਆਟੋ ਰੇਟ-ਲਿਮਿਟਿੰਗ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। API ਕੁੰਜੀ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ ਇਹ ਆਪਣੇ ਆਪ ਹੁੰਦਾ ਹੈ।

### ਚੈਟ ਬੇਨਤੀਆਂ 503 / chat_admission_busy ਨਾਲ ਅਸਫਲ ਹੁੰਦੀਆਂ ਹਨ

**ਲੱਛਣ:**

- ਚੈਟ ਕੰਪਲੀਸ਼ਨਜ਼ ਐਂਡਪੌਇੰਟ ਮੁੜ ਕੋਸ਼ਿਸ਼ਯੋਗ `503` ਜਵਾਬ ਵਾਪਸ ਕਰਦਾ ਹੈ, ਜਿਸਦਾ ਗਲਤੀ ਕੋਡ
  `chat_admission_busy` ਹੁੰਦਾ ਹੈ।
- ਜਵਾਬ ਵਿੱਚ `Retry-After` ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ। #12135 ਤੋਂ ਬਾਅਦ ਮੁੱਲ ਦੇਖੀ ਗਈ
  ਔਕਿਊਪੈਂਸੀ ਤੋਂ ਲਿਆ ਜਾਂਦਾ ਹੈ — ਬੇਨਤੀ ਵੱਲੋਂ ਪਹਿਲਾਂ ਹੀ ਉਡੀਕੀ ਗਈ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ਵਿੰਡੋ
  ਅਤੇ ਮੌਜੂਦਾ ਹੈਵੀਵੇਟ ਲੀਜ਼ਾਂ ਨੂੰ ਰੱਖੇ ਜਾਣ ਦੇ ਸਮੇਂ ਵਿੱਚੋਂ ਵੱਡਾ ਮੁੱਲ — ਜਿਸਨੂੰ ਉੱਪਰ ਵੱਲ ਪੂਰੇ
  ਸਕਿੰਟਾਂ ਤੱਕ ਰਾਊਂਡ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ 60 'ਤੇ ਸੀਮਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਨਿਸ਼ਕਿਰਿਆ ਗੇਟ 'ਤੇ ਇਹ ਇਤਿਹਾਸਕ ਘੱਟੋ-ਘੱਟ ਹੱਦਾਂ ਕਾਇਮ ਰੱਖਦਾ ਹੈ: ਬਾਈਟ-ਅਧਾਰਿਤ
  ਪਾਥ 'ਤੇ 2 ਸਕਿੰਟ, ਸਟਰਕਚਰ-ਅਧਾਰਿਤ ਪਾਥ 'ਤੇ 1 ਸਕਿੰਟ (ਜਿਸ ਵਿੱਚ
  `reason: "structure_limit"` ਵੀ ਸ਼ਾਮਲ ਹੈ)।
- ਇਹ ਉਦੋਂ ਹੋ ਸਕਦਾ ਹੈ ਜਦੋਂ ਕੋਈ ਹੋਰ ਹੈਵੀਵੇਟ ਚੈਟ ਜਾਂ ਲੰਬੇ ਸਮੇਂ ਤੱਕ ਚੱਲਣ ਵਾਲਾ ਸਟ੍ਰੀਮਿੰਗ ਜਵਾਬ ਹਾਲੇ ਵੀ
  ਪ੍ਰਕਿਰਿਆ ਅਧੀਨ ਹੋਵੇ।

ਬਾਈਟ-ਅਧਾਰਿਤ ਜਵਾਬ ਦੀ ਬੌਡੀ ਇਹ ਹੈ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ਸਟਰਕਚਰ-ਅਧਾਰਿਤ ਜਵਾਬ ਉਸੇ ਟਾਈਪ ਅਤੇ ਕੋਡ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ, ਜਿਸਦਾ ਸੁਨੇਹਾ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ਅਤੇ `reason: "structure_limit"` ਹੁੰਦਾ ਹੈ।
ਡਿਫੌਲਟ ਥ੍ਰੈਸ਼ਹੋਲਡਾਂ 'ਤੇ, ਕੋਈ ਬੇਨਤੀ ਸਟਰਕਚਰ ਦੇ ਪੱਖੋਂ ਹੈਵੀ ਉਦੋਂ ਹੁੰਦੀ ਹੈ ਜਦੋਂ ਉਸ ਵਿੱਚ ਘੱਟੋ-ਘੱਟ `200` ਸੁਨੇਹੇ,
ਘੱਟੋ-ਘੱਟ `64` ਟੂਲ, ਜਾਂ ਘੱਟੋ-ਘੱਟ `32,000` ਅਨੁਮਾਨਿਤ ਟੋਕਨ ਹੋਣ, ਜਾਂ ਜਦੋਂ ਸੀਮਾਬੱਧ ਸਟਰਕਚਰ ਅਨੁਮਾਨ
`10,000` ਵਿਜ਼ਿਟ ਕੀਤੇ ਨੋਡਾਂ ਜਾਂ `12` ਡੂੰਘਾਈ ਦੀਆਂ ਆਪਣੀਆਂ ਹੱਦਾਂ ਖ਼ਤਮ ਕਰ ਦੇਵੇ।

**ਕਾਰਨ:** ਇਹ OmniRoute ਦੇ ਅੰਦਰ ਜਾਣਬੁੱਝ ਕੇ ਕੀਤੀ ਗਈ ਲੋਡ ਸ਼ੈਡਿੰਗ ਹੈ, ਨਾ ਕਿ ਅੱਪਸਟ੍ਰੀਮ-ਪ੍ਰਦਾਤਾ ਦੀ ਅਸਫਲਤਾ।
ਹਰ ਪ੍ਰੋਸੈਸ ਵੱਡੀ ਬੇਨਤੀ ਬੌਡੀ ਨੂੰ ਰੱਖਣ ਅਤੇ ਪਾਰਸ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਸੀਮਿਤ ਹੈਵੀਵੇਟ ਸਮਰੱਥਾ ਰਿਜ਼ਰਵ ਕਰਨ ਲਈ
ਪ੍ਰੋਸੈਸ-ਲੋਕਲ ਗਾਰਡ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। ਹੈਵੀਵੇਟ ਲੀਜ਼ ਕਿਸੇ SSE
ਜਵਾਬ ਦੇ ਪੂਰੇ ਜੀਵਨਕਾਲ ਦੌਰਾਨ ਰੱਖੀ ਰਹਿੰਦੀ ਹੈ।

**#503-ਫੈਨਆਉਟ:** ਇਸ ਸੁਧਾਰ ਤੋਂ ਪਹਿਲਾਂ, ਗਾਰਡ ਹੋਸਟ ਮੈਮੋਰੀ ਦੀ ਪਰਵਾਹ ਕੀਤੇ ਬਿਨਾਂ ਸਮਕਾਲੀਤਾ ਨੂੰ ਬੇਨਤੀਆਂ ਦੀ ਇੱਕ ਨਿਸ਼ਚਿਤ ਗਿਣਤੀ
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ਡਿਫੌਲਟ `1`) ਤੱਕ ਸੀਮਿਤ ਕਰਦਾ ਸੀ, ਇਸ ਲਈ ਕੋਡਿੰਗ-ਏਜੰਟ
ਫੈਨਆਉਟ (ਕਈ ਸਬ-ਏਜੰਟ/CLIs, ਬੌਡੀਜ਼ ਆਮ ਤੌਰ 'ਤੇ > 256 KB) ਲਗਭਗ 1 ਦੀ ਪ੍ਰਭਾਵਸ਼ਾਲੀ
ਸਮਕਾਲੀਤਾ ਤੱਕ ਘਟ ਜਾਂਦਾ ਸੀ ਅਤੇ ਬਿਲਕੁਲ ਆਮ ਲੋਡ ਹੇਠ 503 ਦੇ ਦਿੰਦਾ ਸੀ। ਹੁਣ ਗਾਰਡ ਆਪਣੇ ਆਪ ਟਿਊਨ ਹੁੰਦਾ ਹੈ: ਇਹ ਪ੍ਰੋਸੈਸ ਦੀ
ਅਸਲ ਮੈਮੋਰੀ ਸੀਮਾ ਤੋਂ ਆਕਾਰਿਤ, ਆਪਣੇ ਆਪ ਪ੍ਰਾਪਤ ਕੀਤੇ ਇਨਜੈਸਟ BYTE ਬਜਟ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ਰਾਹੀਂ
ਨਿਯੰਤਰਿਤ ਹੁੰਦਾ ਹੈ, ਅਤੇ ਇਹ ਲਾਈਵ ਸਰੋਤ-ਦਬਾਅ ਸੰਕੇਤ ਦੀ ਵੀ ਜਾਂਚ ਕਰਦਾ ਹੈ — ਇਸ ਲਈ ਇਹ
ਸਿਰਫ਼ ਉਦੋਂ ਲੋਡ ਘਟਾਉਂਦਾ ਹੈ ਜਦੋਂ ਹੋਸਟ ਵਾਸਤਵ ਵਿੱਚ ਮੈਮੋਰੀ ਦਬਾਅ ਹੇਠ ਹੋਵੇ, ਨਾ ਕਿ ਸਿਰਫ਼ ਇਸ ਕਰਕੇ ਕਿ ਇੱਕੋ ਸਮੇਂ ਇੱਕ ਤੋਂ ਵੱਧ
ਹੈਵੀ ਬੇਨਤੀਆਂ ਆ ਗਈਆਂ। ਪੁਰਾਣੀ ਗਿਣਤੀ ਸੀਮਾ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ਦਾ
ਹਾਲੇ ਵੀ ਆਦਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਪਰ ਸਿਰਫ਼ ਉਦੋਂ ਜਦੋਂ ਤੁਸੀਂ ਇਸਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਸੈੱਟ ਕਰਦੇ ਹੋ।

ਜਦੋਂ ਸਮਰੱਥਾ ਵਿਅਸਤ ਹੁੰਦੀ ਹੈ, ਤਾਂ ਹੈਵੀਵੇਟ ਬੇਨਤੀ ਮੁੜ ਕੋਸ਼ਿਸ਼ਯੋਗ `503` ਨਾਲ ਜਵਾਬ ਦੇਣ ਤੋਂ ਪਹਿਲਾਂ
ਕਿਸੇ ਸਲਾਟ ਦੇ ਖਾਲੀ ਹੋਣ ਲਈ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ਤੱਕ ਉਡੀਕ ਕਰਦੀ ਹੈ
(ਡਿਫੌਲਟ `RATE_LIMIT_MAX_WAIT_MS`; `0` ਉਡੀਕ ਨੂੰ ਅਸਮਰੱਥ ਕਰਦਾ ਹੈ)।
ਇਹ ਸੀਮਾਬੱਧ ਉਡੀਕ ਇਸ ਲਈ ਮੌਜੂਦ ਹੈ ਤਾਂ ਜੋ ਏਜੰਟ-ਸ਼ੈਲੀ ਕਲਾਇੰਟ
(OpenCode, Claude Code, Cursor), ਜੋ ਹੈਵੀ ਸਬ-ਬੇਨਤੀਆਂ ਨੂੰ ਇੱਕੋ ਸਮੇਂ ਫੈਨਆਉਟ ਕਰਦੇ ਹਨ, ਤੁਰੰਤ ਅਸਵੀਕ੍ਰਿਤੀਆਂ 'ਤੇ ਆਪਣਾ ਪੂਰਾ ਮੁੜ-ਕੋਸ਼ਿਸ਼ ਬਜਟ
ਖਰਚ ਕਰਕੇ ਕੰਮ ਦੇ ਵਿਚਕਾਰ ਬੰਦ ਹੋਣ ਦੀ ਬਜਾਏ, ਬਰਸਟ ਨੂੰ ਕ੍ਰਮਵਾਰ ਕਰ ਸਕਣ।
ਮੌਜੂਦਾ ਹੈਵੀਵੇਟ ਲੀਜ਼ ਔਕਿਊਪੈਂਸੀ, ਨਿਰਧਾਰਤ ਬਾਈਟ ਬਜਟ ਅਤੇ ਲਾਈਵ ਦਬਾਅ ਦੀ ਗੰਭੀਰਤਾ
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) 'ਤੇ ਦਿਖਾਈ ਜਾਂਦੀ ਹੈ — ਕਿਸੇ ਵੀ env var ਨੂੰ ਬਦਲਣ ਤੋਂ ਪਹਿਲਾਂ ਇਹਨਾਂ ਦੀ ਜਾਂਚ ਕਰੋ।
Settings → Resilience → Request Queue → Concurrent Requests ਇਸਨੂੰ ਕੰਟਰੋਲ ਨਹੀਂ ਕਰਦੀ; ਇਹ ਸੈਟਿੰਗ
ਇੱਕ ਵੱਖਰੇ ਪ੍ਰਦਾਤਾ ਬੇਨਤੀ-ਕਤਾਰ ਤੰਤਰ ਨੂੰ ਨਿਯੰਤਰਿਤ ਕਰਦੀ ਹੈ।

**ਹੱਲ:**

1. ਪਹਿਲਾਂ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਕਰੋ। ਕਲਾਇੰਟਾਂ ਨੂੰ ਬੇਨਤੀ ਤੁਰੰਤ ਦੁਹਰਾਉਣ ਦੀ ਬਜਾਏ `Retry-After` ਦਾ ਸਤਿਕਾਰ ਕਰਨਾ
   ਅਤੇ ਬੈਕਆਫ਼ ਵਰਤਣਾ ਚਾਹੀਦਾ ਹੈ।
2. ਕੁਝ ਵੀ ਟਿਊਨ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ `/api/monitoring/health` → `chatAdmission` ਦੀ ਜਾਂਚ ਕਰੋ। `countCapEnabled:
false` ਅਤੇ ਖੁੱਲ੍ਹਾ `maxInflightBytes` ਦਰਸਾਉਂਦੇ ਹਨ ਕਿ ਆਪਣੇ ਆਪ ਪ੍ਰਾਪਤ ਕੀਤਾ ਬਜਟ ਪਹਿਲਾਂ ਹੀ ਆਪਣਾ
   ਕੰਮ ਕਰ ਰਿਹਾ ਹੈ; `high`/`critical` ਦੀ `pressureSeverity` ਦਾ ਮਤਲਬ ਹੈ ਕਿ ਹੋਸਟ ਕੋਲ ਵਾਸਤਵ ਵਿੱਚ ਮੈਮੋਰੀ ਘੱਟ ਹੈ —
   ਇਸਨੂੰ admission env var ਨਾਲ ਠੀਕ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ, ਇਸ ਲਈ ਵਧੇਰੇ RAM ਜਾਂ ਘੱਟ ਵਰਕਲੋਡ ਦੀ ਲੋੜ ਹੈ।
3. ਸਿਰਫ਼ ਉਦੋਂ, ਜਦੋਂ `/api/monitoring/health` ਦਿਖਾਉਂਦਾ ਹੈ ਕਿ ਆਪਣੇ ਆਪ ਪ੍ਰਾਪਤ ਕੀਤਾ ਬਜਟ ਵਾਸਤਵ ਵਿੱਚ ਤੁਹਾਡੇ
   ਹੋਸਟ ਲਈ ਬਹੁਤ ਛੋਟਾ ਹੈ (ਇਹ ਵਿਰਲਾ ਹੈ — ਇਹ ਪਹਿਲਾਂ ਹੀ ਕੰਟੇਨਰ ਤੋਂ ਬੇਅਰ-ਮੈਟਲ ਤੱਕ ਸਕੇਲ ਹੁੰਦਾ ਹੈ), ਪੁਰਾਣੀ ਬੇਨਤੀ-ਗਿਣਤੀ ਸੀਮਾ ਵੱਲ ਮੁੜਨ ਦੀ ਬਜਾਏ
   ਇਸਨੂੰ ਸਿੱਧਾ `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ਨਾਲ ਓਵਰਰਾਈਡ ਕਰੋ।

ਅਧਿਕਾਰਤ admission ਸੈਟਿੰਗਾਂ ਲਈ [ਇਨਵਾਇਰਨਮੈਂਟ-ਵੇਰੀਏਬਲ ਹਵਾਲਾ](../reference/ENVIRONMENT.md#4-security--authentication)
ਦੇਖੋ।

## ਵਿਕਲਪਿਕ RAG / LLM ਅਸਫਲਤਾ ਵਰਗੀਕਰਨ (16 ਸਮੱਸਿਆਵਾਂ)

ਕੁਝ OmniRoute ਵਰਤੋਂਕਾਰ ਗੇਟਵੇ ਨੂੰ RAG ਜਾਂ ਏਜੰਟ ਸਟੈਕਾਂ ਦੇ ਅੱਗੇ ਰੱਖਦੇ ਹਨ। ਅਜਿਹੀਆਂ ਸੈਟਅੱਪਾਂ ਵਿੱਚ ਇੱਕ ਅਜੀਬ ਪੈਟਰਨ ਆਮ ਤੌਰ 'ਤੇ ਵੇਖਣ ਨੂੰ ਮਿਲਦਾ ਹੈ: OmniRoute ਸਿਹਤਮੰਦ ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ (ਪ੍ਰਦਾਤਾ ਚਾਲੂ ਹਨ, ਰੂਟਿੰਗ ਪ੍ਰੋਫ਼ਾਈਲ ਠੀਕ ਹਨ, ਦਰ ਸੀਮਾ ਦੀ ਕੋਈ ਚੇਤਾਵਨੀ ਨਹੀਂ ਹੈ), ਪਰ ਅੰਤਿਮ ਜਵਾਬ ਫਿਰ ਵੀ ਗਲਤ ਹੁੰਦਾ ਹੈ।

ਅਮਲ ਵਿੱਚ ਇਹ ਘਟਨਾਵਾਂ ਆਮ ਤੌਰ 'ਤੇ ਡਾਊਨਸਟ੍ਰੀਮ RAG ਪਾਈਪਲਾਈਨ ਤੋਂ ਪੈਦਾ ਹੁੰਦੀਆਂ ਹਨ, ਨਾ ਕਿ ਖੁਦ ਗੇਟਵੇ ਤੋਂ।

ਜੇ ਤੁਸੀਂ ਇਨ੍ਹਾਂ ਅਸਫਲਤਾਵਾਂ ਦਾ ਵਰਣਨ ਕਰਨ ਲਈ ਇੱਕ ਸਾਂਝੀ ਸ਼ਬਦਾਵਲੀ ਚਾਹੁੰਦੇ ਹੋ, ਤਾਂ ਤੁਸੀਂ WFGY ProblemMap ਵਰਤ ਸਕਦੇ ਹੋ, ਜੋ MIT ਲਾਇਸੈਂਸ ਵਾਲਾ ਇੱਕ ਬਾਹਰੀ ਟੈਕਸਟ ਸਰੋਤ ਹੈ ਅਤੇ ਸੋਲ੍ਹਾਂ ਵਾਰ-ਵਾਰ ਆਉਣ ਵਾਲੇ RAG / LLM ਅਸਫਲਤਾ ਪੈਟਰਨਾਂ ਨੂੰ ਪਰਿਭਾਸ਼ਿਤ ਕਰਦਾ ਹੈ। ਉੱਚ ਪੱਧਰ 'ਤੇ ਇਸ ਵਿੱਚ ਇਹ ਸ਼ਾਮਲ ਹਨ:

- ਰਿਟਰੀਵਲ ਡ੍ਰਿਫਟ ਅਤੇ ਟੁੱਟੀਆਂ ਸੰਦਰਭ ਸੀਮਾਵਾਂ
- ਖਾਲੀ ਜਾਂ ਪੁਰਾਣੇ ਇੰਡੈਕਸ ਅਤੇ ਵੈਕਟਰ ਸਟੋਰ
- ਐਮਬੈਡਿੰਗ ਅਤੇ ਅਰਥਕ ਅਸੰਗਤਤਾ
- ਪ੍ਰੌਮਪਟ ਅਸੈਂਬਲੀ ਅਤੇ ਸੰਦਰਭ ਵਿੰਡੋ ਦੀਆਂ ਸਮੱਸਿਆਵਾਂ
- ਤਰਕ ਦਾ ਢਹਿ ਜਾਣਾ ਅਤੇ ਹੱਦੋਂ ਵੱਧ ਭਰੋਸੇ ਵਾਲੇ ਜਵਾਬ
- ਲੰਬੀ ਚੇਨ ਅਤੇ ਏਜੰਟ ਤਾਲਮੇਲ ਦੀਆਂ ਅਸਫਲਤਾਵਾਂ
- ਮਲਟੀ-ਏਜੰਟ ਮੈਮੋਰੀ ਅਤੇ ਭੂਮਿਕਾ ਡ੍ਰਿਫਟ
- ਡਿਪਲੌਇਮੈਂਟ ਅਤੇ ਬੂਟਸਟਰੈਪ ਕ੍ਰਮ ਦੀਆਂ ਸਮੱਸਿਆਵਾਂ

ਵਿਚਾਰ ਸਧਾਰਨ ਹੈ:

1. ਜਦੋਂ ਤੁਸੀਂ ਕਿਸੇ ਖਰਾਬ ਜਵਾਬ ਦੀ ਜਾਂਚ ਕਰਦੇ ਹੋ, ਤਾਂ ਇਹ ਜਾਣਕਾਰੀ ਸੰਭਾਲੋ:
   - ਵਰਤੋਂਕਾਰ ਦਾ ਕੰਮ ਅਤੇ ਬੇਨਤੀ
   - OmniRoute ਵਿੱਚ ਰੂਟ ਜਾਂ ਪ੍ਰਦਾਤਾ ਦਾ ਜੋੜ
   - ਡਾਊਨਸਟ੍ਰੀਮ ਵਿੱਚ ਵਰਤਿਆ ਗਿਆ ਕੋਈ ਵੀ RAG ਸੰਦਰਭ (ਪ੍ਰਾਪਤ ਕੀਤੇ ਦਸਤਾਵੇਜ਼, ਟੂਲ ਕਾਲਾਂ ਆਦਿ)
2. ਘਟਨਾ ਨੂੰ ਇੱਕ ਜਾਂ ਦੋ WFGY ProblemMap ਨੰਬਰਾਂ (`No.1` … `No.16`) ਨਾਲ ਮੈਪ ਕਰੋ।
3. ਨੰਬਰ ਨੂੰ ਆਪਣੇ ਡੈਸ਼ਬੋਰਡ, ਰਨਬੁੱਕ ਜਾਂ ਘਟਨਾ ਟਰੈਕਰ ਵਿੱਚ OmniRoute ਲੌਗਾਂ ਦੇ ਨਾਲ ਸਟੋਰ ਕਰੋ।
4. ਇਹ ਫ਼ੈਸਲਾ ਕਰਨ ਲਈ ਸੰਬੰਧਿਤ WFGY ਪੰਨਾ ਵਰਤੋ ਕਿ ਤੁਹਾਨੂੰ ਆਪਣਾ RAG ਸਟੈਕ, ਰਿਟਰੀਵਰ ਜਾਂ ਰੂਟਿੰਗ ਰਣਨੀਤੀ ਬਦਲਣ ਦੀ ਲੋੜ ਹੈ ਜਾਂ ਨਹੀਂ।

ਪੂਰਾ ਟੈਕਸਟ ਅਤੇ ਠੋਸ ਵਿਧੀਆਂ ਇੱਥੇ ਉਪਲਬਧ ਹਨ (MIT ਲਾਇਸੈਂਸ, ਕੇਵਲ ਟੈਕਸਟ):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

ਜੇ ਤੁਸੀਂ OmniRoute ਦੇ ਪਿੱਛੇ RAG ਜਾਂ ਏਜੰਟ ਪਾਈਪਲਾਈਨਾਂ ਨਹੀਂ ਚਲਾਉਂਦੇ, ਤਾਂ ਤੁਸੀਂ ਇਸ ਭਾਗ ਨੂੰ ਅਣਡਿੱਠਾ ਕਰ ਸਕਦੇ ਹੋ।

## v3.8.0 ਦੀਆਂ ਜਾਣੀਆਂ ਸਮੱਸਿਆਵਾਂ

v3.8.0 ਰਿਲੀਜ਼ ਨਾਲ ਸੰਬੰਧਿਤ ਸਮੱਸਿਆਵਾਂ ਅਤੇ ਉਨ੍ਹਾਂ ਦੇ ਮੌਜੂਦਾ ਅਸਥਾਈ ਹੱਲ। ਜੇ ਕਿਸੇ ਬਾਅਦਲੇ ਪੈਚ ਵਿੱਚ ਸੁਧਾਰ ਆ ਜਾਂਦਾ ਹੈ, ਤਾਂ ਐਂਟਰੀ ਨੂੰ ਅੱਪਡੇਟ ਜਾਂ ਹਟਾ ਦਿੱਤਾ ਜਾਵੇਗਾ।

### Devin CLI ਪ੍ਰਮਾਣੀਕਰਨ ਅਸਫਲਤਾਵਾਂ

**ਲੱਛਣ:**

- Devin-ਸਮਰਥਿਤ ਟੂਲਾਂ ਨੂੰ ਚਲਾਉਂਦੇ ਸਮੇਂ "Devin CLI ਨਹੀਂ ਮਿਲਿਆ" ਜਾਂ "ਪ੍ਰਮਾਣੀਕਰਨ ਅਸਫਲ ਹੋਇਆ"
- CLI ਰਨਟਾਈਮ ਜਾਂਚ `installed=false` ਰਿਪੋਰਟ ਕਰਦੀ ਹੈ

**ਕਾਰਨ:**

- `CLI_DEVIN_BIN` ਇੱਕ ਅਜਿਹੇ ਪਾਥ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ ਜੋ ਮੌਜੂਦ ਨਹੀਂ ਹੈ
- ਹੋਸਟ ਉੱਤੇ Devin CLI ਇੰਸਟਾਲ ਨਹੀਂ ਹੈ

**ਹੱਲ:**

1. ਆਪਣੇ ਪਲੇਟਫਾਰਮ ਲਈ Devin CLI ਇੰਸਟਾਲ ਕਰੋ
2. `.env` ਵਿੱਚ `CLI_DEVIN_BIN=/usr/local/bin/devin` (ਜਾਂ ਅਸਲ ਪਾਥ) ਸੈੱਟ ਕਰੋ
3. OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ ਅਤੇ **ਡੈਸ਼ਬੋਰਡ → CLI ਟੂਲ** ਤੋਂ ਦੁਬਾਰਾ ਜਾਂਚ ਕਰੋ

### ਮਾਡਲ ਕੂਲਡਾਊਨ ਅਟਕਿਆ ਹੋਇਆ ਹੈ (ਮੈਨੁਅਲ ਰੀਸੈੱਟ)

**ਲੱਛਣ:**

- ਮਿਆਦ ਪੁੱਗਣ ਦਾ ਸਮਾਂ ਲੰਘ ਜਾਣ ਤੋਂ ਬਾਅਦ ਵੀ ਇੱਕ ਮਾਡਲ ਕੂਲਡਾਊਨ ਵਿੱਚ ਸੂਚੀਬੱਧ ਰਹਿੰਦਾ ਹੈ
- ਟਾਈਮਸਟੈਂਪ ਬੀਤੇ ਸਮੇਂ ਦਾ ਹੋਣ ਦੇ ਬਾਵਜੂਦ, ਕੰਬੋ ਰੂਟਿੰਗ ਵਿੱਚ ਬੇਨਤੀਆਂ ਅਜੇ ਵੀ ਮਾਡਲ ਨੂੰ ਛੱਡ ਦਿੰਦੀਆਂ ਹਨ

**ਮੈਨੁਅਲ ਰੀਸੈੱਟ:**

- **ਡੈਸ਼ਬੋਰਡ:** **ਸੈਟਿੰਗਾਂ → ਮਾਡਲ ਕੂਲਡਾਊਨ** → ਪ੍ਰਭਾਵਿਤ ਕਾਰਡ ਉੱਤੇ **ਮੁੜ ਸਮਰੱਥ ਕਰੋ** 'ਤੇ ਕਲਿੱਕ ਕਰੋ
- **API:** ਪ੍ਰਬੰਧਨ ਪ੍ਰਮਾਣੀਕਰਨ ਹੈਡਰਾਂ ਨਾਲ `DELETE /api/resilience/model-cooldowns`

### Command Code ਪ੍ਰਦਾਤਾ ਦਾ ਕਨੈਕਸ਼ਨ 403 ਨਾਲ ਅਸਫਲ ਹੁੰਦਾ ਹੈ

**ਲੱਛਣ:**

- Command Code ਪ੍ਰਦਾਤਾ ਕਨੈਕਸ਼ਨ ਦੀ ਜਾਂਚ ਕਰਦੇ ਸਮੇਂ 403
- ਨਵਾਂ ਜੋੜਨ ਤੋਂ ਬਾਅਦ ਪ੍ਰਦਾਤਾ ਕਾਰਡ "ਅਣਅਧਿਕਾਰਤ" ਦਿਖਾਉਂਦਾ ਹੈ

**ਕਾਰਨ:** OAuth ਪ੍ਰਵਾਹ ਪੂਰਾ ਨਹੀਂ ਹੋਇਆ (ਕਾਲਬੈਕ ਪ੍ਰਾਪਤ ਨਹੀਂ ਹੋਇਆ ਜਾਂ ਟੋਕਨ ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੰਭਾਲਿਆ ਨਹੀਂ ਗਿਆ)।

**ਹੱਲ:**

- OAuth ਪ੍ਰਵਾਹ ਨੂੰ ਮੁੜ ਸ਼ੁਰੂ ਕਰਨ ਲਈ CLI ਤੋਂ `omniroute providers` ਚਲਾਓ, ਜਾਂ
- **ਡੈਸ਼ਬੋਰਡ → ਪ੍ਰਦਾਤਾ → Command Code → ਮੁੜ ਕਨੈਕਟ ਕਰੋ** ਤੋਂ OAuth ਨੂੰ ਦੁਬਾਰਾ ਚਲਾਓ

### ModelScope ਬਹੁਤ ਆਕਰਮਕ 429 ਕੂਲਡਾਊਨ ਵਾਪਸ ਕਰਦਾ ਹੈ

**ਲੱਛਣ:**

- ਬੇਨਤੀਆਂ ਦੇ ਇੱਕ ਛੋਟੇ ਜਿਹੇ ਬਰਸਟ ਤੋਂ ਬਾਅਦ ModelScope ਉੱਤੇ ਬਹੁਤ ਛੋਟੇ ਜਾਂ ਤੁਰੰਤ ਕੂਲਡਾਊਨ
- ਕੰਬੋ ਰੂਟਿੰਗ ਉਮੀਦ ਤੋਂ ਪਹਿਲਾਂ ModelScope ਨੂੰ ਛੱਡ ਦਿੰਦੀ ਹੈ

**ਕਾਰਨ:** ModelScope ਪ੍ਰਦਾਤਾ-ਵਿਸ਼ੇਸ਼ `Retry-After` ਹੈਡਰ ਭੇਜਦਾ ਹੈ। v3.8.0 ਵਿੱਚ ਉਨ੍ਹਾਂ ਹੈਡਰਾਂ ਲਈ ਸਮਰਪਿਤ ਹੈਂਡਲਿੰਗ ਸ਼ਾਮਲ ਹੈ, ਇਸ ਲਈ ਪੁਰਾਣੇ ਵਰਜਨ ਉਨ੍ਹਾਂ ਨੂੰ ਆਮ ਦਰ-ਸੀਮਾ ਸੰਕੇਤਾਂ ਵਜੋਂ ਗਲਤ ਪੜ੍ਹਦੇ ਹਨ।

**ਹੱਲ:**

- ਯਕੀਨੀ ਬਣਾਓ ਕਿ ਤੁਸੀਂ v3.8.0 ਜਾਂ ਇਸ ਤੋਂ ਬਾਅਦਲੇ ਵਰਜਨ ਉੱਤੇ ਹੋ
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ **ਸੈਟਿੰਗਾਂ → ਲਚੀਲਾਪਣ** ਹੇਠਾਂ `useUpstream429BreakerHints` ਟੌਗਲ ਸਮਰੱਥ ਹੈ

### ਪ੍ਰੋਡਕਸ਼ਨ ਵਿੱਚ OMNIROUTE_WS_BRIDGE_SECRET ਮੌਜੂਦ ਨਹੀਂ ਹੈ

**ਲੱਛਣ:**

- ਕਿਸੇ ਰਿਮੋਟ ਪ੍ਰੋਡਕਸ਼ਨ ਹੋਸਟ ਉੱਤੇ ਚਲਾਉਂਦੇ ਸਮੇਂ ਹਰ Codex/Responses WebSocket ਬ੍ਰਿਜ ਬੇਨਤੀ ਉੱਤੇ 401
- ਕਨੈਕਟ ਹੋਣ ਤੋਂ ਤੁਰੰਤ ਬਾਅਦ WebSocket ਬ੍ਰਿਜ ਹੈਂਡਸ਼ੇਕ ਬੰਦ ਹੋ ਜਾਂਦਾ ਹੈ

**ਕਾਰਨ:** ਪ੍ਰੋਡਕਸ਼ਨ ਵਾਤਾਵਰਣ ਵਿੱਚ `OMNIROUTE_WS_BRIDGE_SECRET` env var ਮੌਜੂਦ ਨਹੀਂ ਹੈ।

**ਹੱਲ:**

1. ਇੱਕ ਰੈਂਡਮ ਸੀਕ੍ਰੇਟ ਬਣਾਓ: `openssl rand -hex 32`
2. ਪ੍ਰੋਡਕਸ਼ਨ ਸਰਵਰ env ਵਿੱਚ `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ਸੈੱਟ ਕਰੋ (ਅਤੇ ਬ੍ਰਿਜ ਨਾਲ ਸੰਚਾਰ ਕਰਨ ਵਾਲੇ ਕਿਸੇ ਵੀ ਕਲਾਇੰਟ ਵਿੱਚ ਵੀ)
3. OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ

### Responses API: ਬੈਕਗ੍ਰਾਊਂਡ ਮੋਡ ਨੂੰ ਸਿੰਕ੍ਰੋਨਸ ਵਿੱਚ ਘਟਾਇਆ ਗਿਆ

**ਲੱਛਣ:**

- ਚੇਤਾਵਨੀ ਲੌਗ ਕੀਤੀ ਗਈ: `background mode degraded to synchronous`
- ਇੱਕ `background: true` ਬੇਨਤੀ ਬੈਕਗ੍ਰਾਊਂਡ ਜੌਬ ਹੈਂਡਲ ਦੀ ਬਜਾਏ ਇੱਕ ਆਮ ਸਿੰਕ੍ਰੋਨਸ ਜਵਾਬ ਵਾਪਸ ਕਰਦੀ ਹੈ

**ਕਾਰਨ:** v3.8.0 ਜਾਣ-ਬੁੱਝ ਕੇ Responses API ਉੱਤੇ `background: true` ਨੂੰ ਸਿੰਕ੍ਰੋਨਸ ਐਗਜ਼ੀਕਿਊਸ਼ਨ ਵਿੱਚ ਘਟਾਉਂਦਾ ਹੈ ਅਤੇ ਨਾਲ ਹੀ ਇੱਕ ਚੇਤਾਵਨੀ ਜਾਰੀ ਕਰਦਾ ਹੈ। ਪੂਰੀ ਐਸਿੰਕ੍ਰੋਨਸ ਬੈਕਗ੍ਰਾਊਂਡ ਐਗਜ਼ੀਕਿਊਸ਼ਨ ਭਵਿੱਖ ਵਿੱਚ ਮੁਹੱਈਆ ਕੀਤੀ ਜਾਣ ਵਾਲੀ ਸਮਰੱਥਾ ਹੈ।

**ਹੱਲ:**

- ਕਲਾਇੰਟ ਨੂੰ `background` ਤੋਂ ਬਿਨਾਂ ਕਾਲ ਕਰਨ ਲਈ ਅਨੁਕੂਲਿਤ ਕਰੋ, ਜਾਂ
- ਪੂਰੇ ਐਸਿੰਕ੍ਰੋਨਸ ਬੈਕਗ੍ਰਾਊਂਡ ਮੋਡ ਵਾਲੀ ਬਾਅਦਲੀ ਰਿਲੀਜ਼ ਦੀ ਉਡੀਕ ਕਰੋ (ਚੇਂਜਲੌਗ ਨੂੰ ਟਰੈਕ ਕਰੋ)

## ਹੌਲੀ ਸ਼ੁਰੂਆਤ / ਤਿਆਰੀ ਸਮਾਂ-ਸੀਮਾ

ਜੇ CLI `⚠ Server did not respond within 60s` ਦਿਖਾਉਂਦਾ ਹੈ ਪਰ ਸਰਵਰ ਅਸਲ ਵਿੱਚ
ਕੰਮ ਕਰ ਰਿਹਾ ਹੈ, ਤਾਂ ਤੁਹਾਡੇ ਵਾਤਾਵਰਣ ਲਈ ਤਿਆਰੀ ਜਾਂਚ ਦਾ ਸਮਾਂ-ਬਜਟ ਬਹੁਤ ਘੱਟ ਹੈ।

ਇਹ ਆਮ ਤੌਰ 'ਤੇ Windows (ਐਂਟੀਵਾਇਰਸ, ਫ਼ਾਈਲ-ਸਿਸਟਮ ਵਾਚਰ) ਜਾਂ ਭਾਰੀ ਸ਼ੁਰੂਆਤੀ
ਵਰਕਲੋਡ ਵਾਲੇ ਕੰਟੇਨਰਾਂ ਵਿੱਚ ਹੁੰਦਾ ਹੈ।

**ਹੱਲ — ਸਮਾਂ-ਬਜਟ ਵਧਾਓ:**

```bash
# ਵਾਤਾਵਰਣ ਵੇਰੀਏਬਲ ਰਾਹੀਂ (ਹਰ ਵਾਰ ਸ਼ੁਰੂ ਕਰਨ 'ਤੇ ਲਾਗੂ ਰਹਿੰਦਾ ਹੈ):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 ਮਿੰਟ
omniroute serve

# CLI ਫਲੈਗ ਰਾਹੀਂ (ਸਿਰਫ਼ ਇੱਕ ਵਾਰ ਲਈ):
omniroute serve --ready-timeout 180000
```

ਡਿਫੌਲਟ 60 000 ms (60 s) ਹੈ। ਇਹ ਚੇਤਾਵਨੀ ਸਿਰਫ਼ ਜਾਣਕਾਰੀ ਲਈ ਹੈ; ਸਰਵਰ
ਬੈਕਗ੍ਰਾਊਂਡ ਵਿੱਚ ਸ਼ੁਰੂ ਹੁੰਦਾ ਰਹਿੰਦਾ ਹੈ ਅਤੇ ਬੂਟ ਪੂਰਾ ਹੋਣ ਤੋਂ ਬਾਅਦ ਪਹੁੰਚਯੋਗ ਹੋ ਜਾਵੇਗਾ।

`OMNIROUTE_READY_TIMEOUT_MS` ਬਾਰੇ ਪੂਰੇ ਵੇਰਵਿਆਂ ਲਈ
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) ਵੇਖੋ।
