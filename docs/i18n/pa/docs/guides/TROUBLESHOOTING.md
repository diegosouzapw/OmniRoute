### ਮੁਫ਼ਤ ਪ੍ਰਦਾਤਾਵਾਂ ਉੱਤੇ ਦਰ ਸੀਮਾਬੰਦੀ (429 / 400 / 401)

**ਲੱਛਣ**: ਮੁਫ਼ਤ/ਬਿਨਾਂ-ਪ੍ਰਮਾਣੀਕਰਨ ਵਾਲੇ ਪ੍ਰਦਾਤਾਵਾਂ (opencode, auggie, ਆਦਿ) ਨਾਲ `model: "auto"` ਵਰਤਦੇ ਸਮੇਂ, ਤੁਹਾਨੂੰ ਕਦੇ-ਕਦਾਈਂ ਜਵਾਬਾਂ ਦੀ ਬਜਾਏ `HTTP 429`, `400`, ਜਾਂ `401` ਮਿਲਦਾ ਹੈ। ਕੁਝ ਪਲਾਂ ਬਾਅਦ ਉਸੇ ਪ੍ਰੌਂਪਟ ਨੂੰ ਦੁਬਾਰਾ ਅਜ਼ਮਾਉਣ 'ਤੇ ਬੇਨਤੀਆਂ ਸਫਲ ਹੋ ਜਾਂਦੀਆਂ ਹਨ, ਪਰ ਆਟੋਮੇਸ਼ਨ (cron ਜੌਬਾਂ, ਏਜੰਟ, ਸਕ੍ਰਿਪਟਾਂ) ਪਹਿਲੀ ਅਸਫਲਤਾ 'ਤੇ ਟੁੱਟ ਜਾਂਦੀ ਹੈ।

**ਮੂਲ ਕਾਰਨ**: ਤਿੰਨ ਸੁਤੰਤਰ ਅਸਫਲਤਾ ਢੰਗ ਇਕੱਠੇ ਹੋ ਜਾਂਦੇ ਹਨ:

1. **ਪ੍ਰਦਾਤਾ ਦਰ-ਸੀਮਾ (`429`)**: ਮੁਫ਼ਤ ਟੀਅਰ ਹਰ ਸਮਾਂ-ਵਿੰਡੋ ਲਈ ਕੋਟਾ ਲਾਗੂ ਕਰ ਸਕਦੇ ਹਨ। ਸਮਾਂਤਰ ਕਾਲਾਂ ਦਾ ਇੱਕ ਅਚਾਨਕ ਵਾਧਾ ਇਸਨੂੰ ਖ਼ਤਮ ਕਰ ਦਿੰਦਾ ਹੈ, ਇਸ ਲਈ ਵਿੰਡੋ ਰੀਸੈੱਟ ਹੋਣ ਤੱਕ ਅਗਲੀ ਬੇਨਤੀ ਰੱਦ ਕਰ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ।
2. **ਪਾਸਥਰੂ ਵਿੱਚ ਖ਼ਰਾਬ ਮਾਡਲ (`400`/`401`)**: `auto/*` ਪੂਲਾਂ ਵਿੱਚ `opencode` ਦੇ ਅਜਿਹੇ ਪਾਸਥਰੂ ਮਾਡਲ ਸ਼ਾਮਲ ਹੋ ਸਕਦੇ ਹਨ ਜੋ ਕੈਟਾਲੌਗ ਵਿੱਚ ਰਜਿਸਟਰਡ ਹਨ ਪਰ ਉਨ੍ਹਾਂ ਕੋਲ ਚਾਲੂ ਪ੍ਰਮਾਣ-ਪੱਤਰ ਨਹੀਂ ਹਨ (ਉਦਾਹਰਨ ਵਜੋਂ `oc/north-mini-code-free` → `401`)। ਆਟੋ-ਰਾਊਟਰ ਇੱਕ ਨੂੰ ਅਜ਼ਮਾਉਂਦਾ ਹੈ, ਅਸਫਲ ਹੁੰਦਾ ਹੈ, ਅਤੇ ਫਾਲਬੈਕ ਸ਼ੁਰੂ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਹੀ ਤਰੁੱਟੀ ਅੱਗੇ ਭੇਜ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ।
3. **ਸਮਕਾਲੀਤਾ ਵਧੋਤਰੀ (ਲੋਡ ਹੇਠ `429`)**: ਜਦੋਂ ਕਈ ਏਜੰਟ/cron ਸੈਸ਼ਨ ਇੱਕੋ ਸਮੇਂ `auto` ਨੂੰ ਵਰਤਦੇ ਹਨ, ਤਾਂ ਕੁੱਲ ਬੇਨਤੀ ਦਰ ਮੁਫ਼ਤ ਪ੍ਰਦਾਤਾਵਾਂ ਦੀ ਸਹਿਣਸ਼ੀਲਤਾ ਤੋਂ ਵੱਧ ਜਾਂਦੀ ਹੈ, ਜਿਸ ਕਰਕੇ ਵੈਧ ਕਾਲਾਂ ਨੂੰ ਵੀ ਦੁਰਵਰਤੋਂ ਵਜੋਂ ਚਿੰਨ੍ਹਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

**ਤਸਦੀਕਸ਼ੁਦਾ ਹੱਲ (ਕਮਿਊਨਿਟੀ ਵੱਲੋਂ ਰਿਪੋਰਟ ਕੀਤਾ, 2026-08-10)**: ਤਿੰਨ ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲ ਇਸ ਤਰ੍ਹਾਂ ਟਿਊਨ ਕਰੋ ਕਿ ਰੋਟੇਸ਼ਨ, ਸਮਕਾਲੀਤਾ ਅਤੇ ਫਾਲਬੈਕ ਮੁਫ਼ਤ ਟੀਅਰ ਦੀ ਅਸਥਿਰਤਾ ਕਾਰਨ ਬੰਦ ਹੋਣ ਦੀ ਬਜਾਏ ਉਸਨੂੰ ਸੰਭਾਲ ਸਕਣ:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ਉੱਤੇ ਕਿਸੇ ਹੋਰ ਮਾਡਲ/ਪ੍ਰਦਾਤਾ 'ਤੇ ਜਾਓ (ਖ਼ਰਾਬ ਪਾਸਥਰੂ ਮਾਡਲਾਂ ਨੂੰ ਛੱਡਦਾ ਹੈ)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ਹੈਵੀਵੇਟ ਦਾਖ਼ਲੇ ਦੀ ਸਪਸ਼ਟ ਅਧਿਕਤਮ ਸੀਮਾ (ਮੂਲ ਰੂਪ ਵਿੱਚ ਸੈੱਟ ਨਹੀਂ: ਬੇਨਤੀ-ਗਿਣਤੀ ਦੀ ਕੋਈ ਸੀਮਾ ਨਹੀਂ, ਹੇਠਾਂ ਦਿੱਤਾ ਨੋਟ ਵੇਖੋ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ਤੁਰੰਤ ਦੁਬਾਰਾ ਕੋਸ਼ਿਸ਼ਯੋਗ 503 ਦੀ ਬਜਾਏ ਹੈਵੀਵੇਟ ਸਮਰੱਥਾ ਲਈ ਵਧੇਰੇ ਲੰਬੀ ਪਰ ਸੀਮਾਬੱਧ ਉਡੀਕ
```

ਇਨ੍ਹਾਂ ਨੂੰ OmniRoute ਪ੍ਰਕਿਰਿਆ ਦੇ ਇਨਵਾਇਰਨਮੈਂਟ ਵਿੱਚ ਸੈੱਟ ਕਰੋ (ਡੇਮਨ ਵਿੱਚ, ਉਦਾਹਰਨ ਵਜੋਂ LaunchAgent plist ਜਾਂ `systemctl edit` ਰਾਹੀਂ), ਫਿਰ OmniRoute ਨੂੰ ਰੀਸਟਾਰਟ ਕਰੋ। ਰੋਟੇਸ਼ਨ ਫਲੈਗ ਸਭ ਤੋਂ ਵੱਧ ਪ੍ਰਭਾਵਸ਼ਾਲੀ ਉਪਾਅ ਹੈ: ਇਹ ਇੱਕ ਪੱਕੀ ਅਸਫਲਤਾ ਨੂੰ ਪੂਲ ਦੇ ਕਿਸੇ ਸਿਹਤਮੰਦ ਪ੍ਰਦਾਤਾ ਵਿਰੁੱਧ ਪਾਰਦਰਸ਼ੀ ਮੁੜ-ਕੋਸ਼ਿਸ਼ ਵਿੱਚ ਬਦਲ ਦਿੰਦਾ ਹੈ।

**ਨੋਟ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ਇਹ ਸੀਮਿਤ ਕਰਦਾ ਹੈ ਕਿ ਇੱਕੋ ਸਮੇਂ ਕਿੰਨੀਆਂ ਹੈਵੀਵੇਟ — ਲੰਬੇ-ਕੰਟੈਕਸਟ ਵਾਲੀਆਂ — ਬੇਨਤੀਆਂ ਚੱਲ ਸਕਦੀਆਂ ਹਨ; ਇਹ ਸੀਮਾ ਇੱਕ ਦਾਖ਼ਲਾ ਗੇਟ ਹੈ, ਪ੍ਰਦਾਤਾ ਦਰ-ਸੀਮਾਕਾਰ ਨਹੀਂ। **#503-fanout ਅੱਪਡੇਟ:** ਹੁਣ ਇਹ ਵੇਰੀਏਬਲ ਮੂਲ ਰੂਪ ਵਿੱਚ ਸੈੱਟ ਨਹੀਂ ਹੁੰਦਾ (ਹੁਣ ਇਹ ਸਿਰਫ਼ ਉਦੋਂ ਹੀ ਲਾਗੂ ਹੁੰਦਾ ਹੈ ਜਦੋਂ ਉੱਪਰ ਦਿੱਤੇ ਅਨੁਸਾਰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਸੰਰਚਿਤ ਕੀਤਾ ਜਾਵੇ) — ਇਸਦੀ ਬਜਾਏ ਹੈਵੀਵੇਟ ਦਾਖ਼ਲਾ ਆਪਣੇ ਆਪ ਨਿਰਧਾਰਤ ਕੀਤੇ ਬਾਈਟ ਬਜਟ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ਰਾਹੀਂ ਨਿਯੰਤਰਿਤ ਹੁੰਦਾ ਹੈ, ਜੋ ਹੋਸਟ ਦੀ ਅਸਲ ਮੈਮੋਰੀ ਸੀਮਾ ਦੇ ਅਨੁਸਾਰ ਆਪਣੇ ਆਪ ਸਕੇਲ ਹੁੰਦਾ ਹੈ। ਇਸ ਲਈ ਇੱਕ ਨਵੀਂ ਡਿਪਲੌਇਮੈਂਟ ਵਿੱਚ ਇਸ ਵੇਰੀਏਬਲ ਨੂੰ ਸੈੱਟ ਕੀਤੇ ਬਿਨਾਂ ਵੀ ਬਹੁਤ ਘੱਟ `503 chat_admission_busy` ਅਸਵੀਕਾਰਤਾਵਾਂ ਦਿਖਾਈ ਦੇਣੀਆਂ ਚਾਹੀਦੀਆਂ ਹਨ; ਇੱਥੇ ਇਸਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਸੈੱਟ ਕਰਨਾ ਹਾਲੇ ਵੀ ਦਸਤਾਵੇਜ਼ੀ ਵਰਣਨ ਅਨੁਸਾਰ ਹੀ ਕੰਮ ਕਰਦਾ ਹੈ। ਸਪਸ਼ਟ ਬਾਈਟ-ਬਜਟ ਓਵਰਰਾਈਡਾਂ ਨੂੰ 8 MiB–2 GiB ਤੱਕ ਸੀਮਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। `413 body_exceeds_budget` ਅਸਥਾਈ ਨਹੀਂ ਹੈ: ਉਸ ਬਾਈਟ ਬਜਟ ਨੂੰ ਵਧਾਓ, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ਨੂੰ ਘਟਾਓ, ਜਾਂ ਪ੍ਰਕਿਰਿਆ ਦੀ ਮੈਮੋਰੀ ਸੀਮਾ ਵਧਾਓ। `inflight_bytes_budget` ਕਾਰਨ ਲੋਡ ਘਟਾਉਣਾ ਅਸਥਾਈ ਸਰੋਤ-ਟਕਰਾਅ ਹੈ ਅਤੇ ਇਸ ਲਈ ਦੁਬਾਰਾ ਕੋਸ਼ਿਸ਼ ਕੀਤੀ ਜਾ ਸਕਦੀ ਹੈ। ਹਰ-ਪ੍ਰਦਾਤਾ ਦਰ ਸੀਮਾਬੰਦੀ (`open-sse/services/rateLimitManager.ts`) ਨੂੰ `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, ਅਤੇ `RATE_LIMIT_AUTO_ENABLE` ਵੱਲੋਂ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਨਿਯੰਤਰਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ — `.env.example` ਵੇਖੋ।

**ਇਹ ਕਿਵੇਂ ਤਸਦੀਕ ਕਰਨਾ ਹੈ ਕਿ ਹੱਲ ਕੰਮ ਕਰ ਗਿਆ**: ਆਪਣੇ ਏਜੰਟ/cron ਨੂੰ ਤੁਰੰਤ ਲਗਾਤਾਰ ਦੋ ਵਾਰ ਚਲਾਓ ਅਤੇ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਦੋਵੇਂ ਵਾਰ ਸਫਲਤਾ ਮਿਲਦੀ ਹੈ। ਹੱਲ ਤੋਂ ਪਹਿਲਾਂ, ਦੂਜੀ ਰਨ ਆਮ ਤੌਰ 'ਤੇ `429`/`401` ਦਿੰਦੀ ਹੈ। ਹੱਲ ਤੋਂ ਬਾਅਦ, ਅਸਫਲਤਾਵਾਂ (ਜੇ ਕੋਈ ਹੋਣ) ਲਈ ਪਾਰਦਰਸ਼ੀ ਢੰਗ ਨਾਲ ਦੁਬਾਰਾ ਕੋਸ਼ਿਸ਼ ਕੀਤੀ ਜਾਂਦੀ ਹੈ ਅਤੇ ਕਾਲ ਪੂਰੀ ਹੋ ਜਾਂਦੀ ਹੈ। ਤੁਸੀਂ `curl /monitoring/health` ਵੀ ਚਲਾ ਸਕਦੇ ਹੋ ਅਤੇ ਪ੍ਰਦਾਤਾ ਕਨੈਕਸ਼ਨਾਂ ਉੱਤੇ `rateLimitedUntil` ਫ਼ੀਲਡ ਅਤੇ ਪ੍ਰਭਾਵਿਤ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ `circuitBreakers.providerBreakers[].state` ਦੇਖ ਸਕਦੇ ਹੋ — ਸਥਿਤੀ `CLOSED`, `DEGRADED`, `OPEN`, ਜਾਂ `HALF_OPEN` ਵਿੱਚੋਂ ਇੱਕ ਹੁੰਦੀ ਹੈ (`src/shared/utils/circuitBreaker.ts` ਵੇਖੋ), ਅਤੇ ਵਾਰ-ਵਾਰ ਅਸਫਲ ਹੋਣ ਵਾਲਾ ਪ੍ਰਦਾਤਾ ਰੀਸੈੱਟ ਵਿੰਡੋ ਵੱਲੋਂ ਜਾਂਚ ਨੂੰ ਲੰਘਣ ਦੀ ਆਗਿਆ ਦੇਣ (`HALF_OPEN`) ਤੋਂ ਪਹਿਲਾਂ `CLOSED → DEGRADED → OPEN` ਵਿੱਚ ਬਦਲ ਜਾਵੇਗਾ।

**ਜੇ ਤੁਹਾਨੂੰ ਹਾਲੇ ਵੀ 429 ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ**: ਉਸ ਪ੍ਰਦਾਤਾ ਲਈ ਸਰਗਰਮ ਖਾਤੇ ਦਾ _ਕੋਟਾ_ ਵਾਸਤਵ ਵਿੱਚ ਖ਼ਤਮ ਹੋ ਚੁੱਕਾ ਹੈ (ਸਿਰਫ਼ ਦਰ ਸੀਮਾ ਨਹੀਂ)। OmniRoute ਡੈਸ਼ਬੋਰਡ → Providers → Accounts ਵਿੱਚ ਉਸੇ ਪ੍ਰਦਾਤਾ ਲਈ ਦੂਜਾ ਖਾਤਾ ਸ਼ਾਮਲ ਕਰੋ, ਜਾਂ ਕੋਈ ਹੋਰ ਮੁਫ਼ਤ ਪ੍ਰਦਾਤਾ (ਜਿਵੇਂ `routeway`, `auggie`) ਵੀ ਸ਼ਾਮਲ ਕਰੋ। ਰੋਟੇਸ਼ਨ ਸਿਰਫ਼ ਅਸਥਾਈ ਦਰ ਸੀਮਾ/400/401 ਵਿੱਚ ਮਦਦ ਕਰਦੀ ਹੈ; ਕੋਟਾ ਪੂਰੀ ਤਰ੍ਹਾਂ ਖ਼ਤਮ ਹੋਣ ਦੀ ਸਥਿਤੀ ਵਿੱਚ ਦੂਜੇ ਕ੍ਰੈਡੈਂਸ਼ਲ ਜਾਂ ਕਿਸੇ ਵੱਖਰੇ ਪ੍ਰਦਾਤਾ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।

**ਜੇ ਤੁਹਾਨੂੰ ਵਿਜ਼ਨ ਮਾਡਲਾਂ (`auto/vision`, `bazaarlink/*`) ਉੱਤੇ 403 ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ**: ਕਨੈਕਟ ਕੀਤੇ ਖਾਤੇ ਕੋਲ ਵਿਜ਼ਨ ਸ਼ਾਮਲ ਕਰਨ ਵਾਲੀ ਭੁਗਤਾਨਯੋਗ ਯੋਜਨਾ ਨਹੀਂ ਹੈ, ਜਾਂ API ਕੁੰਜੀ ਕੋਲ ਲੋੜੀਂਦੀਆਂ ਇਜਾਜ਼ਤਾਂ ਨਹੀਂ ਹਨ। ਪ੍ਰਦਾਤਾ ਦੇ ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਕੁੰਜੀ ਦੇ ਸਕੋਪ ਵਿੱਚ ਵਿਜ਼ਨ/ਮਲਟੀਮੋਡਲ ਸ਼ਾਮਲ ਹੈ, ਜਾਂ ਭੁਗਤਾਨਯੋਗ ਟੀਅਰ ਵਾਲਾ ਖਾਤਾ ਕਨੈਕਟ ਕਰੋ ਅਤੇ ਉਸਨੂੰ ਵਿਜ਼ਨ ਟਾਰਗੇਟ ਵਜੋਂ ਰੱਖੋ।

## npm install ਚੇਤਾਵਨੀਆਂ (ERESOLVE / peer / deprecated)

ਜਦੋਂ ਤੁਸੀਂ `npm install -g omniroute` ਚਲਾਉਂਦੇ ਹੋ, ਤਾਂ ਤੁਹਾਨੂੰ `npm warn ERESOLVE`, peer-dependency ਸੂਚਨਾਵਾਂ ਅਤੇ `deprecated` ਸੁਨੇਹਿਆਂ ਵਰਗੀਆਂ ਬਹੁਤ ਸਾਰੀਆਂ ਚੇਤਾਵਨੀਆਂ ਦਿਖਾਈ ਦੇ ਸਕਦੀਆਂ ਹਨ। **ਇਹ ਉਮੀਦ ਕੀਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ ਅਤੇ ਨੁਕਸਾਨ ਰਹਿਤ ਹਨ।** ਜੇ ਆਉਟਪੁੱਟ ਵਿੱਚ `added <N> packages` ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ, ਤਾਂ ਤੁਹਾਡੀ ਇੰਸਟਾਲੇਸ਼ਨ ਸਫਲ ਰਹੀ ਹੈ।

ਇਹ ਚੇਤਾਵਨੀਆਂ ਤੀਜੀ-ਧਿਰ ਦੇ ਪੈਕੇਜਾਂ ਵਿੱਚ ਪੁਰਾਣੀਆਂ peer-dependency ਰੇਂਜਾਂ ਕਾਰਨ ਆਉਂਦੀਆਂ ਹਨ, ਜਿਨ੍ਹਾਂ ਨੂੰ OmniRoute ਨਿਯੰਤਰਿਤ ਨਹੀਂ ਕਰਦਾ:

1. **`marked-terminal` ਨੂੰ `marked >=1 <16` ਚਾਹੀਦਾ ਹੈ, ਪਰ `marked@18` ਮਿਲਿਆ** — ਅਮਲ ਵਿੱਚ ਇਹ ਠੀਕ ਕੰਮ ਕਰਦਾ ਹੈ; upstream peer ਰੇਂਜ ਸਿਰਫ਼ ਪੁਰਾਣੀ ਹੈ।
2. **`deprecated prebuild-install@7.1.3`** — ਇੱਕ transitive native-binary ਪ੍ਰਾਪਤੀ ਸਹਾਇਕ। ਇਸਦੀ ਵਰਤੋਂ
   pin ਕੀਤੀ `wreq-js` transport binding ਨੂੰ ਇੰਸਟਾਲ ਕਰਨ ਲਈ ਨਹੀਂ ਹੁੰਦੀ ਅਤੇ ਇਹ ਨਹੀਂ ਦਰਸਾਉਂਦਾ ਕਿ web-cookie
   provider transport ਸੈੱਟਅੱਪ ਅਸਫਲ ਹੋਇਆ ਹੈ।

**ਕਿਸੇ ਕਾਰਵਾਈ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ** — upstream ਪੈਕੇਜਾਂ ਨੂੰ fork ਕੀਤੇ ਬਿਨਾਂ ਇਨ੍ਹਾਂ ਚੇਤਾਵਨੀਆਂ ਨੂੰ ਪੂਰੀ ਤਰ੍ਹਾਂ ਚੁੱਪ ਨਹੀਂ ਕਰਵਾਇਆ ਜਾ ਸਕਦਾ।

## ਐਂਟੀਵਾਇਰਸ ਦੇ ਗਲਤ ਪਾਜ਼ਿਟਿਵ

<a name="antivirus-false-positives"></a>

### Avast/AVG ਵੱਲੋਂ `README.md` ਨੂੰ `MD:HttpRequest-inf[Susp]` ਦੇ ਤੌਰ 'ਤੇ ਕਵਾਰੰਟੀਨ ਕਰਨਾ

**ਇਹ ਇੱਕ ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਹੈ। ਕੁਝ ਵੀ ਸੰਕਰਮਿਤ ਨਹੀਂ ਹੈ ਅਤੇ ਕਿਸੇ ਕਾਰਵਾਈ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ।**

Avast ਅਤੇ AVG ਇੱਕ ਹਿਊਰਿਸਟਿਕ ਚਲਾਉਂਦੇ ਹਨ ਜੋ ਬਹੁਤ ਸਾਰੇ HTTP ਬੇਨਤੀ ਵਰਗੇ ਦਿਖਣ ਵਾਲੇ ਲਿੰਕਾਂ ਵਾਲੀਆਂ
ਸਧਾਰਨ-ਟੈਕਸਟ/Markdown ਫਾਈਲਾਂ ਨੂੰ ਫਲੈਗ ਕਰਦਾ ਹੈ। OmniRoute ਦੀ `README.md` npm ਪੈਕੇਜ ਦੇ ਅੰਦਰ ਆਉਂਦੀ ਹੈ (ਇਹ
`package.json` → `files` ਵਿੱਚ ਸੂਚੀਬੱਧ ਹੈ), ਇਸ ਲਈ ਗਲੋਬਲ ਇੰਸਟਾਲੇਸ਼ਨ ਦੌਰਾਨ ਇਹ `node_modules/omniroute/README.md` ਵਿੱਚ
ਪਹੁੰਚਦੀ ਹੈ — ਅਤੇ ਇਸ ਵਿੱਚ ਲਗਭਗ 15 `http://localhost:20128/...` ਉਦਾਹਰਨਾਂ ਹਨ (MCP
HTTP/SSE ਐਂਡਪੁਆਇੰਟ, A2A `.well-known` URL, ਅਤੇ `curl` ਸਨਿੱਪਟ)। ਲਿੰਕਾਂ ਦੀ ਇਹ ਘਣਤਾ
ਹਿਊਰਿਸਟਿਕ ਨੂੰ ਚਾਲੂ ਕਰਨ ਲਈ ਕਾਫ਼ੀ ਹੈ।

ਜੇ ਇਹ ਹਾਲ ਹੀ ਵਿੱਚ ਹੀ ਸ਼ੁਰੂ ਹੋਇਆ ਹੈ: ਫਾਈਲ ਦੀ ਕਿਸਮ ਨਹੀਂ ਬਦਲੀ। README ਵਿੱਚ
ਐਂਡਪੁਆਇੰਟ ਸਾਰਣੀ (MCP HTTP + SSE + A2A ਸ਼ਾਮਲ ਕੀਤੇ ਗਏ ਸਨ) ਅਤੇ ਹੋਰ `curl` ਉਦਾਹਰਨਾਂ ਜੋੜੀਆਂ ਗਈਆਂ,
ਜਿਸ ਕਾਰਨ ਇਹ ਸੀਮਾ ਤੋਂ ਪਾਰ ਹੋ ਗਈ।

ਇਹ ਫਾਈਲ ਨਿਸ਼ਕਿਰਿਆ ਦਸਤਾਵੇਜ਼ ਹੈ ਜਿਸ ਵਿੱਚ ਕੋਈ ਵੀ ਚਲਾਉਣਯੋਗ ਸਮੱਗਰੀ ਨਹੀਂ ਹੈ। ਤੁਸੀਂ ਇਸਨੂੰ
ਕਵਾਰੰਟੀਨ ਤੋਂ ਸੁਰੱਖਿਅਤ ਢੰਗ ਨਾਲ ਰੀਸਟੋਰ ਕਰ ਸਕਦੇ ਹੋ।

**ਕੀ ਕਰਨਾ ਹੈ:**

1. **ਸੂਚਨਾਵਾਂ ਰੋਕੋ** — ਆਪਣੇ ਐਂਟੀਵਾਇਰਸ ਵਿੱਚ ਇੰਸਟਾਲੇਸ਼ਨ ਡਾਇਰੈਕਟਰੀ ਨੂੰ ਅਲਹਿਦਾ ਰੱਖੋ
   (Avast: Settings → Exceptions), ਆਪਣੇ ਗਲੋਬਲ `node_modules` ਪਾਥ ਅਤੇ/ਜਾਂ
   OmniRoute ਡਾਟਾ ਡਾਇਰੈਕਟਰੀ (`~/.omniroute/`) ਨੂੰ ਸ਼ਾਮਲ ਕਰਕੇ।
2. **ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਦੀ ਰਿਪੋਰਟ ਕਰੋ** — <https://www.avast.com/false-positive-file-form.php>,
   ਅਤੇ ਕਵਾਰੰਟੀਨ ਕੀਤੀ `README.md` ਨੱਥੀ ਕਰੋ। ਇਹ ਉਹ ਹੱਲ ਹੈ ਜੋ ਸਾਰਿਆਂ ਦੀ ਮਦਦ ਕਰਦਾ ਹੈ, ਕਿਉਂਕਿ ਇਹ
   ਵਿਕਰੇਤਾ ਦਾ ਹਿਊਰਿਸਟਿਕ ਹੈ ਜੋ ਇੱਕ ਟੈਕਸਟ ਫਾਈਲ ਪ੍ਰਤੀ ਲੋੜ ਤੋਂ ਵੱਧ ਪ੍ਰਤੀਕਿਰਿਆ ਕਰ ਰਿਹਾ ਹੈ।

**ਅਸੀਂ ਇਸਨੂੰ ਆਪਣੇ ਪਾਸੇ "ਠੀਕ" ਕਿਉਂ ਨਹੀਂ ਕਰਦੇ:** ਸਾਰੀਆਂ ਉਦਾਹਰਨਾਂ `http://localhost` ਹਨ, ਅਤੇ
ਸਵੈ-ਹਸਤਾਖਰਿਤ ਸਰਟੀਫਿਕੇਟ ਦੀ ਔਖਿਆਈ ਤੋਂ ਬਿਨਾਂ localhost ਨੂੰ `https` ਨਹੀਂ ਬਣਾਇਆ ਜਾ ਸਕਦਾ। ਕਿਸੇ ਇੱਕ
ਵਿਕਰੇਤਾ ਦੇ ਹਿਊਰਿਸਟਿਕ ਤੋਂ ਬਚਣ ਲਈ ਦਸਤਾਵੇਜ਼ਾਂ ਨੂੰ ਵਿਗਾੜਨਾ, ਸਕੈਨਰ ਦੀ ਇੱਕ ਗਲਤੀ ਨੂੰ ਸੰਤੁਸ਼ਟ ਕਰਨ ਵਾਸਤੇ ਹਰ ਪਾਠਕ ਨੂੰ ਨੁਕਸਾਨ ਪਹੁੰਚਾਏਗਾ।

### Kaspersky ਵੱਲੋਂ Desktop ਐਪ ਨੂੰ `PDM:Trojan.Win32.Generic` ਵਜੋਂ ਫਲੈਗ ਕਰਨਾ

**ਇਹ ਵਿਹਾਰਕ ਹਿਊਰਿਸਟਿਕ ਕਾਰਨ ਆਇਆ ਇੱਕ ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਹੈ। ਕੁਝ ਵੀ ਸੰਕਰਮਿਤ ਨਹੀਂ ਹੈ।** Kaspersky ਦਾ
`PDM:` ਅਗੇਤਰ ਦਰਸਾਉਂਦਾ ਹੈ ਕਿ ਨਿਰਣਾ ਇਸਦੇ Proactive Defense Module (System Watcher) ਤੋਂ ਆਉਂਦਾ ਹੈ,
ਜੋ ਜਾਣੇ-ਪਛਾਣੇ ਮਾਲਵੇਅਰ ਨਾਲ ਮੇਲ ਕਰਨ ਦੀ ਬਜਾਏ ਇਹ ਪਰਖਦਾ ਹੈ ਕਿ ਇੰਸਟਾਲਰ _ਕੀ ਕਰਦਾ ਹੈ_। ਜਦੋਂ
ਇਹ ਚਾਲੂ ਹੁੰਦਾ ਹੈ, Kaspersky ਪੂਰੀ ਇੰਸਟਾਲੇਸ਼ਨ ਨੂੰ "ਵਾਪਸ ਮੋੜ ਦਿੰਦਾ ਹੈ" — ਪਹਿਲਾਂ ਹੀ ਲਿਖੀਆਂ
ਫਾਈਲਾਂ ਨੂੰ ਮਿਟਾ ਕੇ — ਇਸ ਲਈ ਐਪ ਅੰਤ ਵਿੱਚ ਟੁੱਟੀ ਹੋਈ ਜਾਂ ਗਾਇਬ ਹੁੰਦੀ ਹੈ।

ਇਸ ਵੱਲੋਂ ਫਲੈਗ ਕੀਤੀਆਂ ਫਾਈਲਾਂ Desktop ਐਪ ਨਾਲ ਬੰਡਲ ਕੀਤੀਆਂ ਘੋਸ਼ਿਤ, ਓਪਨ-ਸੋਰਸ ਡਿਪੈਂਡੈਂਸੀਆਂ ਦੇ
ਮਿਆਰੀ ਹਿੱਸੇ ਹਨ, ਉਦਾਹਰਨ ਲਈ:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ਅਤੇ
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ਐਪ ਅੰਦਰ ਪ੍ਰਦਾਤਾ ਲਾਗਇਨ ਅਤੇ
  ਬ੍ਰਾਊਜ਼ਰ-ਸਮਰਥਿਤ ਚੈਟ ਲਈ ਵਰਤੀ ਜਾਂਦੀ ਬ੍ਰਾਊਜ਼ਰ-ਆਟੋਮੇਸ਼ਨ ਲਾਇਬ੍ਰੇਰੀ।
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — ਵੈੱਬ-ਕੁਕੀ ਪ੍ਰਦਾਤਾਵਾਂ 'ਤੇ ਬ੍ਰਾਊਜ਼ਰ-ਫਿੰਗਰਪ੍ਰਿੰਟ ਵਾਲੇ HTTP ਲਈ ਵਰਤੀ ਜਾਂਦੀ ਪਿੰਨ ਕੀਤੀ `wreq-js`
  ਨੇਟਿਵ ਬਾਈਂਡਿੰਗ (`<arch>` ਜਾਂ ਤਾਂ `x64` ਹੈ ਜਾਂ `arm64`)।

**ਇਹ ਕਿਉਂ ਚਾਲੂ ਹੁੰਦਾ ਹੈ:** Windows ਇੰਸਟਾਲਰ **ਹਾਲੇ ਕੋਡ-ਸਾਈਨ ਨਹੀਂ ਕੀਤਾ ਗਿਆ**, ਇਸ ਲਈ ਇੱਕ ਗੈਰ-ਹਸਤਾਖਰਿਤ NSIS
ਇੰਸਟਾਲਰ ਦੀ ਕੋਈ ਸਾਖ ਨਹੀਂ ਹੁੰਦੀ ਅਤੇ ਵਿਹਾਰਕ ਹਿਊਰਿਸਟਿਕ ਵੱਧ ਤੋਂ ਵੱਧ ਆਕਰਮਕਤਾ ਨਾਲ ਚੱਲਦੇ ਹਨ। ਇਸਦੇ ਨਾਲ
ਇੱਕ ਬੰਡਲ ਕੀਤੀ ਨੇਟਿਵ DLL ਅਤੇ `%LOCALAPPDATA%\Programs\OmniRoute` ਅਧੀਨ ਲਿਖੀਆਂ ਸੈਂਕੜੇ `.js` ਫਾਈਲਾਂ
(ਜਿਨ੍ਹਾਂ ਵਿੱਚ Next.js ਸਟੈਂਡਅਲੋਨ ਬਿਲਡ ਤੋਂ ਹੈਸ਼-ਪਿਛੇਤਰ ਵਾਲੀਆਂ ਪੈਕੇਜ ਡਾਇਰੈਕਟਰੀਆਂ ਵੀ ਸ਼ਾਮਲ ਹਨ) ਮਿਲ ਕੇ
ਹਿਊਰਿਸਟਿਕ ਨੂੰ ਚਾਲੂ ਕਰਨ ਲਈ ਕਾਫ਼ੀ ਹਨ। ਕੋਡ ਸਾਈਨਿੰਗ ਦੀ ਯੋਜਨਾ ਹੈ;
ਜਦੋਂ ਤੱਕ ਇਹ ਲਾਗੂ ਨਹੀਂ ਹੁੰਦੀ, ਨਵੀਆਂ ਰਿਲੀਜ਼ਾਂ ਵਿੱਚ ਇਹ ਮੁੜ ਹੋ ਸਕਦਾ ਹੈ।

**ਕੀ ਕਰਨਾ ਹੈ:**

1. **ਪਹਿਲਾਂ ਆਪਣੇ ਡਾਊਨਲੋਡ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ** (ਇਸ ਨਾਲ ਛੇੜਛਾੜ ਕੀਤੀ ਫਾਈਲ ਦੀ ਸੰਭਾਵਨਾ ਰੱਦ ਹੁੰਦੀ ਹੈ)। ਹਰ ਰਿਲੀਜ਼
   `latest.yml` ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦੀ ਹੈ, ਜਿਸਦਾ `sha512` ਖੇਤਰ (base64) `OmniRoute.Setup.<version>.exe`
   ਇੰਸਟਾਲਰ ਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ। PowerShell ਵਿੱਚ, ਇੰਸਟਾਲਰ ਵਾਲੇ ਫੋਲਡਰ ਤੋਂ:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ਆਉਟਪੁੱਟ ਦਾ `latest.yml` → `sha512` ਨਾਲ ਮੇਲ ਖਾਣਾ ਲਾਜ਼ਮੀ ਹੈ। ਜੇ ਇਹ ਮੇਲ ਨਹੀਂ ਖਾਂਦਾ, ਤਾਂ ਫਾਈਲ ਮਿਟਾਓ ਅਤੇ
   ਸਿਰਫ਼ [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) ਤੋਂ ਮੁੜ ਡਾਊਨਲੋਡ ਕਰੋ।
2. **ਰੀਸਟੋਰ ਕਰੋ + ਅਲਹਿਦਾ ਰੱਖੋ** — ਵਾਪਸ ਮੋੜੀਆਂ ਆਈਟਮਾਂ ਨੂੰ ਕਵਾਰੰਟੀਨ ਤੋਂ ਰੀਸਟੋਰ ਕਰੋ ਅਤੇ
   `%LOCALAPPDATA%\Programs\OmniRoute` ਲਈ ਇੱਕ ਅਪਵਾਦ ਜੋੜੋ (Kaspersky → Settings → Threats and Exclusions),
   ਫਿਰ ਮੁੜ ਇੰਸਟਾਲ ਕਰੋ।
3. **ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਦੀ ਰਿਪੋਰਟ ਕਰੋ** — <https://opentip.kaspersky.com/>। ਉਪਭੋਗਤਾਵਾਂ ਵੱਲੋਂ ਭੇਜੀਆਂ ਗਈਆਂ ਗਲਤ ਪਾਜ਼ਿਟਿਵ
   ਰਿਪੋਰਟਾਂ ਸੱਚਮੁੱਚ ਮਨਜ਼ੂਰਸ਼ੁਦਾ ਸੂਚੀ ਵਿੱਚ ਸ਼ਾਮਲ ਕਰਨ ਦੀ ਪ੍ਰਕਿਰਿਆ ਨੂੰ ਤੇਜ਼ ਕਰਦੀਆਂ ਹਨ।

## Node.js ਅਨੁਕੂਲਤਾ

### ਲੌਗਇਨ ਸਫ਼ਾ ਕਰੈਸ਼ ਹੋ ਜਾਂਦਾ ਹੈ ਜਾਂ "Module self-registration" ਗਲਤੀ ਦਿਖਾਉਂਦਾ ਹੈ

**ਕਾਰਨ:** ਤੁਸੀਂ OmniRoute ਵੱਲੋਂ ਮਨਜ਼ੂਰਸ਼ੁਦਾ ਸੁਰੱਖਿਅਤ ਰਨਟਾਈਮ ਦੀ ਘੱਟੋ-ਘੱਟ ਸੀਮਾ ਤੋਂ ਬਾਹਰ ਦਾ Node.js ਵਰਜਨ ਚਲਾ ਰਹੇ ਹੋ। ਸਭ ਤੋਂ ਆਮ ਸਥਿਤੀ ਵਿੱਚ Node 22 ਜਾਂ 24 ਦਾ ਕੋਈ ਪੁਰਾਣਾ ਪੈਚ ਪੱਧਰ ਚਲਾਇਆ ਜਾ ਰਿਹਾ ਹੁੰਦਾ ਹੈ, ਜੋ OmniRoute ਵੱਲੋਂ ਲੋੜੀਂਦੀ ਪੈਚ ਕੀਤੀ ਸੁਰੱਖਿਆ ਸੀਮਾ ਤੋਂ ਹੇਠਾਂ ਹੁੰਦਾ ਹੈ।

**ਲੱਛਣ:**

- ਲੌਗਇਨ ਸਫ਼ਾ ਖਾਲੀ ਸਕ੍ਰੀਨ ਜਾਂ ਸਰਵਰ ਗਲਤੀ ਦਿਖਾਉਂਦਾ ਹੈ
- ਕੰਸੋਲ ਵਿੱਚ `Error: Module did not self-register` ਜਾਂ ਇਸ ਵਰਗੀਆਂ ਨੇਟਿਵ ਬਾਈਂਡਿੰਗ ਗਲਤੀਆਂ ਦਿਖਾਈ ਦਿੰਦੀਆਂ ਹਨ
- ਜੇ ਰਨਟਾਈਮ ਸਮਰਥਿਤ ਸੁਰੱਖਿਆ ਨੀਤੀ ਤੋਂ ਬਾਹਰ ਹੈ, ਤਾਂ ਲੌਗਇਨ ਸਫ਼ੇ ਉੱਤੇ ਤੁਹਾਡੇ Node ਵਰਜਨ ਸਮੇਤ ਇੱਕ **ਸੰਤਰੀ ਚੇਤਾਵਨੀ ਬੈਨਰ** ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ

**ਹੱਲ:**

1. ਇੱਕ ਸਮਰਥਿਤ Node.js LTS ਰਿਲੀਜ਼ ਇੰਸਟਾਲ ਕਰੋ (ਸਿਫ਼ਾਰਸ਼ੀ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ਆਪਣੇ ਵਰਜਨ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ: `node --version` ਨੂੰ 24.x LTS ਲਾਈਨ ਉੱਤੇ `v24.0.0` ਜਾਂ ਇਸ ਤੋਂ ਨਵਾਂ ਵਰਜਨ ਦਿਖਾਉਣਾ ਚਾਹੀਦਾ ਹੈ
3. OmniRoute ਨੂੰ ਮੁੜ ਇੰਸਟਾਲ ਕਰੋ: `npm install -g omniroute`
4. ਮੁੜ ਚਾਲੂ ਕਰੋ: `omniroute`

> **ਸਮਰਥਿਤ ਸੁਰੱਖਿਅਤ ਵਰਜਨ:** `>=22.22.2 <23` ਜਾਂ `>=24.0.0 <27`। Node.js 24.x LTS (Krypton) ਅਤੇ Node.js 26 ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਮਰਥਿਤ ਹਨ।

### npm v11+: `better-sqlite3` ਇੰਸਟਾਲ ਨਹੀਂ ਹੈ (ਮੋਡੀਊਲ ਨਹੀਂ ਲੱਭਿਆ)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**ਕਾਰਨ:** npm v11 (ਜੋ Node.js 24+ ਨਾਲ ਮਿਲਦਾ ਹੈ) ਮੂਲ ਰੂਪ ਵਿੱਚ ਵਿਕਲਪਿਕ
ਨਿਰਭਰਤਾਵਾਂ ਲਈ ਇੰਸਟਾਲੇਸ਼ਨ ਸਕ੍ਰਿਪਟਾਂ ਨੂੰ ਬਲੌਕ ਕਰਦਾ ਹੈ। ਕਿਉਂਕਿ `better-sqlite3` ਨੂੰ `optionalDependencies`
ਵਿੱਚ ਸੂਚੀਬੱਧ ਕੀਤਾ ਗਿਆ ਹੈ ਅਤੇ ਇਸ ਲਈ ਨੇਟਿਵ ਕੰਪਾਇਲੇਸ਼ਨ (`node-gyp rebuild`) ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ, npm ਇਸਨੂੰ ਬਿਨਾਂ ਕੋਈ ਸੂਚਨਾ ਦਿੱਤੇ ਛੱਡ ਦਿੰਦਾ ਹੈ।

**ਲੱਛਣ:**

- ਸਰਵਰ ਚਾਲੂ ਹੁੰਦੇ ਸਮੇਂ `Cannot find module 'better-sqlite3'` ਨਾਲ ਕਰੈਸ਼ ਹੋ ਜਾਂਦਾ ਹੈ
- `ls node_modules/better-sqlite3` "No such file or directory" ਦਿਖਾਉਂਦਾ ਹੈ
- `npm ls better-sqlite3` `(empty)` ਦਿਖਾਉਂਦਾ ਹੈ

**ਹੱਲ:**

1. ਇੰਸਟਾਲੇਸ਼ਨ ਸਕ੍ਰਿਪਟਾਂ ਨੂੰ ਮਨਜ਼ੂਰੀ ਦਿਓ ਅਤੇ ਮੁੜ ਇੰਸਟਾਲ ਕਰੋ:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ਜਾਂ ਪਹਿਲਾਂ ਤੋਂ ਬਿਲਡ ਕੀਤੇ ਪੈਕੇਜ ਨੂੰ ਹੱਥੀਂ ਇੰਸਟਾਲ ਕਰੋ:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਇਹ ਕੰਮ ਕਰਦਾ ਹੈ: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**ਕਾਰਨ:** ਗਲੋਬਲ `npm install -g omniroute` ਤੋਂ ਬਾਅਦ, ਪੈਕੇਜ ਦੇ ਅੰਦਰ ਮੌਜੂਦ `better-sqlite3` ਨੇਟਿਵ ਬਾਈਨਰੀ ਨੂੰ ਸਥਾਨਕ ਤੌਰ ਉੱਤੇ ਚੱਲ ਰਹੇ ਆਰਕੀਟੈਕਚਰ ਜਾਂ Node.js ABI ਤੋਂ ਵੱਖਰੇ ਆਰਕੀਟੈਕਚਰ ਜਾਂ ABI ਲਈ ਕੰਪਾਇਲ ਕੀਤਾ ਗਿਆ ਹੋ ਸਕਦਾ ਹੈ। ਜਦੋਂ ਪਹਿਲਾਂ ਤੋਂ ਬਿਲਡ ਕੀਤੀ ਬਾਈਨਰੀ ਤੁਹਾਡੇ ਵਾਤਾਵਰਣ ਨਾਲ ਮੇਲ ਨਹੀਂ ਖਾਂਦੀ, ਤਾਂ macOS (Apple Silicon ਅਤੇ Intel ਦੋਵਾਂ) ਉੱਤੇ ਇਹ ਆਮ ਗੱਲ ਹੈ।

**ਲੱਛਣ:**

- ਸਰਵਰ ਚਾਲੂ ਹੁੰਦੇ ਹੀ `dlopen` ਗਲਤੀ ਨਾਲ ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ
- ਗਲਤੀ ਵਿੱਚ `slice is not valid mach-o file` ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ
- ਪੂਰੀ ਉਦਾਹਰਨ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ਹੱਲ — ਆਪਣੇ ਸਥਾਨਕ ਵਾਤਾਵਰਣ ਲਈ ਮੁੜ ਬਿਲਡ ਕਰੋ (Node.js ਨੂੰ ਪੁਰਾਣੇ ਵਰਜਨ ਉੱਤੇ ਲਿਆਉਣ ਦੀ ਲੋੜ ਨਹੀਂ):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ਨੋਟ:** ਇਹ ਨੇਟਿਵ ਬਾਈਂਡਿੰਗ ਨੂੰ ਤੁਹਾਡੇ ਸਥਾਨਕ Node.js ਵਰਜਨ ਅਤੇ CPU ਆਰਕੀਟੈਕਚਰ ਲਈ ਮੁੜ ਕੰਪਾਇਲ ਕਰਦਾ ਹੈ, ਜਿਸ ਨਾਲ ਬਾਈਨਰੀ ਦਾ ਬੇਮੇਲ ਹੱਲ ਹੋ ਜਾਂਦਾ ਹੈ। ਅਧਿਕਾਰਤ ਤੌਰ ਉੱਤੇ ਸਮਰਥਿਤ ਰਨਟਾਈਮ ਰੇਂਜ **`>=22.22.2 <23` ਜਾਂ `>=24.0.0 <27`** ਹੈ (`src/shared/utils/nodeRuntimeSupport.ts` ਵਿੱਚ `SUPPORTED_NODE_RANGE`, ਜੋ `package.json` ਦੇ `engines` ਫ਼ੀਲਡ ਨਾਲ ਇਕਸਾਰ ਹੈ)। Node.js 24.x LTS (Krypton) ਅਤੇ Node.js 26, `better-sqlite3` v12.x ਨਾਲ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਮਰਥਿਤ ਹਨ।

## ਪ੍ਰਾਕਸੀ ਸੰਬੰਧੀ ਸਮੱਸਿਆਵਾਂ

### ਪ੍ਰਦਾਤਾ ਪ੍ਰਮਾਣਿਕਤਾ "fetch failed" ਦਿਖਾਉਂਦੀ ਹੈ

**ਕਾਰਨ:** API ਕੁੰਜੀ ਪ੍ਰਮਾਣਿਕਤਾ ਐਂਡਪੌਇੰਟ (`POST /api/providers/validate`) ਪਹਿਲਾਂ ਪ੍ਰਾਕਸੀ ਸੰਰਚਨਾ ਨੂੰ ਨਜ਼ਰਅੰਦਾਜ਼ ਕਰ ਰਿਹਾ ਸੀ, ਜਿਸ ਕਾਰਨ ਪ੍ਰਾਕਸੀ ਰੂਟਿੰਗ ਦੀ ਲੋੜ ਵਾਲੇ ਵਾਤਾਵਰਣਾਂ ਵਿੱਚ ਅਸਫਲਤਾਵਾਂ ਆ ਰਹੀਆਂ ਸਨ।

**ਹੱਲ (v3.5.5+):** ਹੁਣ ਇਹ ਸਮੱਸਿਆ ਹੱਲ ਹੋ ਗਈ ਹੈ। ਪ੍ਰਦਾਤਾ ਪ੍ਰਮਾਣਿਕਤਾ `runWithProxyContext` ਰਾਹੀਂ ਰੂਟ ਹੁੰਦੀ ਹੈ ਅਤੇ ਪ੍ਰਦਾਤਾ-ਪੱਧਰੀ ਅਤੇ ਗਲੋਬਲ ਪ੍ਰਾਕਸੀ ਸੈਟਿੰਗਾਂ ਦੀ ਆਪਣੇ-ਆਪ ਪਾਲਣਾ ਕਰਦੀ ਹੈ।

### ਟੋਕਨ ਸਿਹਤ ਜਾਂਚ "fetch failed" ਨਾਲ ਅਸਫਲ ਹੋ ਜਾਂਦੀ ਹੈ

**ਕਾਰਨ:** ਬੈਕਗ੍ਰਾਊਂਡ OAuth ਟੋਕਨ ਰਿਫ੍ਰੈਸ਼ ਹਰੇਕ ਕਨੈਕਸ਼ਨ ਲਈ ਪ੍ਰਾਕਸੀ ਸੰਰਚਨਾ ਨੂੰ ਹੱਲ ਨਹੀਂ ਕਰ ਰਿਹਾ ਸੀ।

**ਹੱਲ (v3.5.5+):** ਹੁਣ ਟੋਕਨ ਸਿਹਤ ਜਾਂਚ ਸ਼ਡਿਊਲਰ ਰਿਫ੍ਰੈਸ਼ ਦੀ ਕੋਸ਼ਿਸ਼ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਹਰੇਕ ਕਨੈਕਸ਼ਨ ਲਈ ਪ੍ਰਾਕਸੀ ਸੰਰਚਨਾ ਨੂੰ ਹੱਲ ਕਰਦਾ ਹੈ। v3.5.5+ 'ਤੇ ਅੱਪਡੇਟ ਕਰੋ।

### SOCKS5 ਪ੍ਰਾਕਸੀ "invalid onRequestStart method" ਵਾਪਸ ਕਰਦੀ ਹੈ

**ਕਾਰਨ:** Node.js 22 'ਤੇ, undici@8 ਡਿਸਪੈਚਰ Node ਦੀ ਬਿਲਟ-ਇਨ `fetch()` ਇੰਪਲੀਮੈਂਟੇਸ਼ਨ ਨਾਲ ਅਨੁਕੂਲ ਨਹੀਂ ਹੈ।

**ਹੱਲ (v3.5.5+):** ਜਦੋਂ ਕੋਈ ਪ੍ਰਾਕਸੀ ਡਿਸਪੈਚਰ ਸਰਗਰਮ ਹੁੰਦਾ ਹੈ, ਤਾਂ OmniRoute ਹੁਣ undici ਦੇ ਆਪਣੇ `fetch()` ਫੰਕਸ਼ਨ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ, ਜਿਸ ਨਾਲ ਇਕਸਾਰ ਵਿਹਾਰ ਯਕੀਨੀ ਬਣਦਾ ਹੈ। v3.5.5+ 'ਤੇ ਅੱਪਡੇਟ ਕਰੋ।

### WSL ਅਧੀਨ MITM ਪ੍ਰਾਕਸੀ: Windows ਹੋਸਟ ਉੱਤੇ ਡੈਸਕਟਾਪ ਐਪਾਂ ਇੰਟਰਸੈਪਟ ਨਹੀਂ ਹੁੰਦੀਆਂ

**ਕਾਰਨ:** MITM ਪ੍ਰਾਕਸੀ ਅਤੇ ਇਸ ਦਾ CA ਸਰਟੀਫਿਕੇਟ ਉਸੇ ਵਾਤਾਵਰਣ ਵਿੱਚ ਇੰਸਟਾਲ ਹੁੰਦੇ ਹਨ ਜਿੱਥੇ OmniRoute ਚੱਲਦਾ ਹੈ। WSL ਅਧੀਨ ਉਹ ਵਾਤਾਵਰਣ Linux ਗੈਸਟ ਹੁੰਦਾ ਹੈ, ਜਦਕਿ AI ਡੈਸਕਟਾਪ ਐਪਾਂ (Kiro, Trae, Copilot, Zed, …) Windows ਹੋਸਟ ਉੱਤੇ ਚੱਲਦੀਆਂ ਹਨ। ਹੋਸਟ ਐਪਾਂ ਗੈਸਟ ਦੇ ਸਰਟੀਫਿਕੇਟ ਸਟੋਰ 'ਤੇ ਭਰੋਸਾ ਨਹੀਂ ਕਰਦੀਆਂ ਅਤੇ ਗੈਸਟ ਦੀ ਸਿਸਟਮ ਪ੍ਰਾਕਸੀ ਰਾਹੀਂ ਰੂਟ ਨਹੀਂ ਹੁੰਦੀਆਂ, ਇਸ ਲਈ ਉੱਥੇ ਡੈਸਕਟਾਪ ਇੰਟਰਸੈਪਸ਼ਨ ਸਰਗਰਮ ਨਹੀਂ ਹੁੰਦੀ।

**ਸਿਫ਼ਾਰਸ਼:** OmniRoute ਨੂੰ ਮੂਲ ਰੂਪ ਵਿੱਚ ਉਸੇ OS ਉੱਤੇ ਚਲਾਓ ਜਿਸ ਉੱਤੇ ਉਹ ਡੈਸਕਟਾਪ ਐਪਾਂ ਚੱਲਦੀਆਂ ਹਨ ਜਿਨ੍ਹਾਂ ਨੂੰ ਤੁਸੀਂ ਇੰਟਰਸੈਪਟ ਕਰਨਾ ਚਾਹੁੰਦੇ ਹੋ (Windows ਐਪਾਂ ਲਈ Windows; ਇਸੇ ਤਰ੍ਹਾਂ macOS/Linux ਲਈ)। ਹੋਸਟ ਐਪਾਂ ਨੂੰ ਨਿਸ਼ਾਨਾ ਬਣਾਉਂਦੇ ਹੋਏ OmniRoute ਨੂੰ WSL ਦੇ ਅੰਦਰ ਰੱਖਣ ਲਈ, ਬਣਾਏ ਗਏ CA ਸਰਟੀਫਿਕੇਟ ਨੂੰ Windows ਹੋਸਟ ਉੱਤੇ ਹੱਥੀਂ ਭਰੋਸੇਯੋਗ ਬਣਾਉਣਾ ਅਤੇ ਹਰੇਕ ਹੋਸਟ ਐਪ ਦੀਆਂ ਨੈੱਟਵਰਕ/ਪ੍ਰਾਕਸੀ ਸੈਟਿੰਗਾਂ ਨੂੰ WSL ਪ੍ਰਾਕਸੀ ਐਂਡਪੌਇੰਟ ਵੱਲ ਨਿਰਦੇਸ਼ਿਤ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ — ਇਹ ਇੱਕ ਅਸਮਰਥਿਤ ਅਤੇ ਨਾਜ਼ੁਕ ਸੈਟਅੱਪ ਹੈ।

## ਕਲਾਉਡ ਸਮੱਸਿਆਵਾਂ

### ਕਲਾਉਡ ਸਿੰਕ ਗਲਤੀਆਂ

1. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `BASE_URL` ਤੁਹਾਡੇ ਚੱਲ ਰਹੇ ਇੰਸਟੈਂਸ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ (ਉਦਾਹਰਨ ਲਈ, `http://localhost:20128`)
2. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `CLOUD_URL` ਤੁਹਾਡੇ ਕਲਾਉਡ ਐਂਡਪੌਇੰਟ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ (ਉਦਾਹਰਨ ਲਈ, `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` ਮੁੱਲਾਂ ਨੂੰ ਸਰਵਰ-ਸਾਈਡ ਮੁੱਲਾਂ ਨਾਲ ਇਕਸਾਰ ਰੱਖੋ

### ਕਲਾਉਡ `stream=false` 500 ਵਾਪਸ ਕਰਦਾ ਹੈ

**ਲੱਛਣ:** ਗੈਰ-ਸਟ੍ਰੀਮਿੰਗ ਕਾਲਾਂ ਲਈ ਕਲਾਉਡ ਐਂਡਪੌਇੰਟ 'ਤੇ `Unexpected token 'd'...`।

**ਕਾਰਨ:** ਅੱਪਸਟ੍ਰੀਮ SSE ਪੇਲੋਡ ਵਾਪਸ ਕਰਦਾ ਹੈ, ਜਦੋਂ ਕਿ ਕਲਾਇੰਟ JSON ਦੀ ਉਮੀਦ ਕਰਦਾ ਹੈ।

**ਅਸਥਾਈ ਹੱਲ:** ਕਲਾਉਡ ਨੂੰ ਸਿੱਧੀਆਂ ਕਾਲਾਂ ਲਈ `stream=true` ਵਰਤੋ। ਲੋਕਲ ਰਨਟਾਈਮ ਵਿੱਚ SSE→JSON ਫਾਲਬੈਕ ਸ਼ਾਮਲ ਹੈ।

### ਕਲਾਉਡ ਕਨੈਕਟ ਹੋਣ ਦੀ ਪੁਸ਼ਟੀ ਕਰਦਾ ਹੈ ਪਰ "ਅਵੈਧ API ਕੁੰਜੀ" ਦਿਖਾਉਂਦਾ ਹੈ

1. ਲੋਕਲ ਡੈਸ਼ਬੋਰਡ (`/api/keys`) ਤੋਂ ਇੱਕ ਨਵੀਂ ਕੁੰਜੀ ਬਣਾਓ
2. ਕਲਾਉਡ ਸਿੰਕ ਚਲਾਓ: ਕਲਾਉਡ ਸਮਰੱਥ ਕਰੋ → ਹੁਣੇ ਸਿੰਕ ਕਰੋ
3. ਪੁਰਾਣੀਆਂ/ਸਿੰਕ ਨਾ ਹੋਈਆਂ ਕੁੰਜੀਆਂ ਅਜੇ ਵੀ ਕਲਾਉਡ 'ਤੇ `401` ਵਾਪਸ ਕਰ ਸਕਦੀਆਂ ਹਨ

## Docker ਸਮੱਸਿਆਵਾਂ

### Docker IPv6 / ਕਨੈਕਸ਼ਨ ਰੀਸੈੱਟ

<a name="docker-ipv6"></a>

**ਲੱਛਣ:** `curl http://localhost:20128/v1/models`, `curl: (56) Recv failure: Connection reset by peer` ਵਾਪਸ ਕਰਦਾ ਹੈ। ਡੈਸ਼ਬੋਰਡ ਅਤੇ ਬਿਨਾਂ ਪ੍ਰਮਾਣੀਕਰਨ ਵਾਲੇ ਐਂਡਪੌਇੰਟ ਕੰਮ ਕਰਦੇ ਹਨ, ਪਰ ਪ੍ਰਮਾਣੀਕ੍ਰਿਤ ਐਂਡਪੌਇੰਟ ਅਸਫਲ ਹੋ ਜਾਂਦੇ ਹਨ — ਇਹ ਪ੍ਰਮਾਣੀਕਰਨ ਦੀ ਸਮੱਸਿਆ ਜਾਪਦੀ ਹੈ, ਪਰ ਅਸਲ ਵਿੱਚ ਅਜਿਹਾ ਨਹੀਂ ਹੈ।

**ਕਾਰਨ:** `docker run -p 20128:20128`, `0.0.0.0` (IPv4) ਅਤੇ `::` (IPv6) ਦੋਵਾਂ 'ਤੇ ਪੋਰਟ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ, ਪਰ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰਲੀ ਪ੍ਰਕਿਰਿਆ ਕੇਵਲ IPv4 'ਤੇ ਸੁਣਦੀ ਹੈ। ਉਹਨਾਂ ਹੋਸਟਾਂ 'ਤੇ ਜਿੱਥੇ `localhost` ਪਹਿਲਾਂ `::1` ਵਿੱਚ ਰਿਜ਼ਾਲਵ ਹੁੰਦਾ ਹੈ, ਕਨੈਕਸ਼ਨ IPv6 ਦੀ ਪ੍ਰਕਾਸ਼ਿਤ ਪੋਰਟ 'ਤੇ ਪਹੁੰਚਦਾ ਹੈ ਜਿਸ ਦੇ ਪਿੱਛੇ ਕੋਈ ਲਿਸਨਰ ਨਹੀਂ ਹੁੰਦਾ → ਕਨੈਕਸ਼ਨ ਰੀਸੈੱਟ।

**ਹੱਲ:**

1. **ਤੁਰੰਤ ਜਾਂਚ:** `curl -4 http://localhost:20128/v1/models` ਚਲਾਓ। ਜੇ ਇਹ `-4` ਨਾਲ ਕੰਮ ਕਰਦਾ ਹੈ ਪਰ ਇਸ ਤੋਂ ਬਿਨਾਂ ਅਸਫਲ ਹੁੰਦਾ ਹੈ, ਤਾਂ ਤੁਹਾਡੇ ਕੋਲ IPv6 ਬਾਈਂਡ ਅਸੰਗਤਤਾ ਹੈ।
2. **ਸਥਾਈ ਹੱਲ:** ਆਪਣੀ `docker run` ਕਮਾਂਡ ਵਿੱਚ `-p 127.0.0.1:20128:20128` ਵਰਤ ਕੇ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ IPv4 ਨਾਲ ਬਾਈਂਡ ਕਰੋ:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ਇਹ IPv4 ਬਾਈਂਡ ਨੂੰ ਲਾਜ਼ਮੀ ਬਣਾਉਂਦਾ ਹੈ ਅਤੇ ਸਾਰੇ ਹੋਸਟ ਇੰਟਰਫੇਸਾਂ 'ਤੇ ਪ੍ਰੌਕਸੀ ਨੂੰ ਉਪਲਬਧ ਕਰਵਾਉਣ ਤੋਂ ਵੀ ਬਚਾਉਂਦਾ ਹੈ।

## ਡੀਬੱਗਿੰਗ

### ਲਾਗ ਫਾਈਲਾਂ ਸਮਰੱਥ ਕਰੋ

ਆਪਣੀ `.env` ਫਾਈਲ ਵਿੱਚ `APP_LOG_TO_FILE=true` ਸੈੱਟ ਕਰੋ। ਐਪਲੀਕੇਸ਼ਨ ਲਾਗ `logs/` ਦੇ ਅਧੀਨ ਲਿਖੇ ਜਾਂਦੇ ਹਨ।
ਜਦੋਂ ਸੈਟਿੰਗਾਂ ਵਿੱਚ ਕਾਲ ਲਾਗ ਪਾਈਪਲਾਈਨ ਸਮਰੱਥ ਹੁੰਦੀ ਹੈ, ਤਾਂ ਬੇਨਤੀ ਆਰਟੀਫੈਕਟ `${DATA_DIR}/call_logs/` ਦੇ ਅਧੀਨ ਸਟੋਰ ਕੀਤੇ ਜਾਂਦੇ ਹਨ।
ਜਦੋਂ ਪਾਈਪਲਾਈਨ ਕੈਪਚਰ ਸਮਰੱਥ ਹੋਵੇ, ਤਾਂ ਸਟ੍ਰੀਮ ਚੰਕ ਪੇਲੋਡਾਂ ਨੂੰ ਛੱਡਣ ਲਈ `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` ਸੈੱਟ ਕਰੋ, ਜਾਂ ਆਰਟੀਫੈਕਟ ਦੀ KB ਸੀਮਾ ਬਦਲਣ ਲਈ `CALL_LOG_PIPELINE_MAX_SIZE_KB` ਨੂੰ ਅਨੁਕੂਲ ਕਰੋ।

### ਪ੍ਰੋਵਾਈਡਰ ਦੀ ਸਿਹਤ ਜਾਂਚੋ

```bash
# ਸਿਹਤ ਡੈਸ਼ਬੋਰਡ
http://localhost:20128/dashboard/health

# API ਸਿਹਤ ਜਾਂਚ
curl http://localhost:20128/api/monitoring/health
```

### ਰਨਟਾਈਮ ਸਟੋਰੇਜ

- ਮੁੱਖ ਸਥਿਤੀ: `${DATA_DIR}/storage.sqlite` (ਪ੍ਰੋਵਾਈਡਰ, ਕੰਬੋ, ਉਪਨਾਮ, ਕੁੰਜੀਆਂ, ਸੈਟਿੰਗਾਂ)
- ਵਰਤੋਂ: `storage.sqlite` ਵਿੱਚ SQLite ਟੇਬਲਾਂ (`usage_history`, `call_logs`, `proxy_logs`) + ਵਿਕਲਪਿਕ `${DATA_DIR}/call_logs/`
- ਐਪਲੀਕੇਸ਼ਨ ਲਾਗ: `<repo>/logs/...` (ਜਦੋਂ `APP_LOG_TO_FILE=true` ਹੋਵੇ)
- ਕਾਲ ਲਾਗ ਆਰਟੀਫੈਕਟ: ਕਾਲ ਲਾਗ ਪਾਈਪਲਾਈਨ ਸਮਰੱਥ ਹੋਣ 'ਤੇ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

`request_detail_logs`, ਅਤੇ ਲੋਕਲ `${DATA_DIR}/call_logs/` ਆਰਟੀਫੈਕਟ ਡਾਇਰੈਕਟਰੀ ਨੂੰ ਸਾਫ਼ ਕਰਦੀ ਹੈ।

## ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਸੰਬੰਧੀ ਸਮੱਸਿਆਵਾਂ

### ਪ੍ਰਦਾਤਾ OPEN ਸਥਿਤੀ ਵਿੱਚ ਅਟਕਿਆ ਹੋਇਆ ਹੈ

ਜਦੋਂ ਕਿਸੇ ਪ੍ਰਦਾਤਾ ਦਾ ਸਰਕਿਟ ਬ੍ਰੇਕਰ OPEN ਹੁੰਦਾ ਹੈ, ਤਾਂ cooldown ਦੀ ਮਿਆਦ ਖਤਮ ਹੋਣ ਤੱਕ ਬੇਨਤੀਆਂ ਬਲੌਕ ਰਹਿੰਦੀਆਂ ਹਨ।

**ਹੱਲ:**

1. **Dashboard → Settings → Resilience** 'ਤੇ ਜਾਓ
2. ਪ੍ਰਭਾਵਿਤ ਪ੍ਰਦਾਤਾ ਲਈ ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਕਾਰਡ ਦੀ ਜਾਂਚ ਕਰੋ
3. ਸਾਰੇ ਬ੍ਰੇਕਰ ਸਾਫ਼ ਕਰਨ ਲਈ **Reset All** 'ਤੇ ਕਲਿੱਕ ਕਰੋ, ਜਾਂ cooldown ਦੀ ਮਿਆਦ ਖਤਮ ਹੋਣ ਦੀ ਉਡੀਕ ਕਰੋ
4. ਰੀਸੈੱਟ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਪ੍ਰਦਾਤਾ ਵਾਸਤਵ ਵਿੱਚ ਉਪਲਬਧ ਹੈ

### ਪ੍ਰਦਾਤਾ ਵਾਰ-ਵਾਰ ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਚਾਲੂ ਕਰ ਰਿਹਾ ਹੈ

ਜੇ ਕੋਈ ਪ੍ਰਦਾਤਾ ਵਾਰ-ਵਾਰ OPEN ਸਥਿਤੀ ਵਿੱਚ ਜਾਂਦਾ ਹੈ:

1. ਅਸਫਲਤਾ ਦੇ ਪੈਟਰਨ ਲਈ **Dashboard → Health → Provider Health** ਦੀ ਜਾਂਚ ਕਰੋ
2. **Settings → Resilience → Provider Profiles** 'ਤੇ ਜਾਓ ਅਤੇ ਅਸਫਲਤਾ ਦੀ ਸੀਮਾ ਵਧਾਓ

## ਆਡੀਓ ਟ੍ਰਾਂਸਕ੍ਰਿਪਸ਼ਨ ਸੰਬੰਧੀ ਸਮੱਸਿਆਵਾਂ

### "Unsupported model" ਗਲਤੀ

- ਅਜਿਹੀ model id ਵਰਤੋ ਜਿਸਦਾ ਪਹਿਲਾ ਹਿੱਸਾ ਉਹ ਪ੍ਰਦਾਤਾ ਹੋਵੇ ਜਿਸ ਲਈ ਤੁਹਾਡੇ ਕੋਲ ਪ੍ਰਮਾਣ-ਪੱਤਰ ਹਨ (`openai/whisper-1`, `openrouter/deepgram/nova-3`)। ਸਿਰਫ਼ `deepgram/nova-3` ਲਈ ਮੂਲ Deepgram key ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਪ੍ਰਦਾਤਾ **Dashboard → Providers** ਵਿੱਚ ਕਨੈਕਟ ਹੈ

### ਟ੍ਰਾਂਸਕ੍ਰਿਪਸ਼ਨ ਖਾਲੀ ਵਾਪਸ ਆਉਂਦੀ ਹੈ ਜਾਂ ਅਸਫਲ ਹੋ ਜਾਂਦੀ ਹੈ

- ਸਮਰਥਿਤ ਆਡੀਓ ਫਾਰਮੈਟਾਂ ਦੀ ਜਾਂਚ ਕਰੋ: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਫ਼ਾਈਲ ਦਾ ਆਕਾਰ ਪ੍ਰਦਾਤਾ ਦੀਆਂ ਸੀਮਾਵਾਂ ਦੇ ਅੰਦਰ ਹੈ (ਆਮ ਤੌਰ 'ਤੇ < 25MB)
- ਪ੍ਰਦਾਤਾ ਕਾਰਡ ਵਿੱਚ provider API key ਦੀ ਵੈਧਤਾ ਦੀ ਜਾਂਚ ਕਰੋ

### ਆਮ ਫਾਰਮੈਟ ਸਮੱਸਿਆਵਾਂ

- **Thinking ਟੈਗ ਦਿਖਾਈ ਨਹੀਂ ਦੇ ਰਹੇ** — ਜਾਂਚ ਕਰੋ ਕਿ ਕੀ ਟਾਰਗੇਟ ਪ੍ਰਦਾਤਾ thinking ਅਤੇ thinking budget ਸੈਟਿੰਗ ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ
- **Tool calls ਗਾਇਬ ਹੋ ਰਹੀਆਂ ਹਨ** — ਕੁਝ ਫਾਰਮੈਟ ਅਨੁਵਾਦ ਅਸਮਰਥਿਤ ਫ਼ੀਲਡਾਂ ਨੂੰ ਹਟਾ ਸਕਦੇ ਹਨ; Playground ਮੋਡ ਵਿੱਚ ਪੁਸ਼ਟੀ ਕਰੋ
- **System prompt ਗਾਇਬ ਹੈ** — Claude ਅਤੇ Gemini system prompts ਨੂੰ ਵੱਖਰੇ ਢੰਗ ਨਾਲ ਸੰਭਾਲਦੇ ਹਨ; ਅਨੁਵਾਦ ਆਉਟਪੁੱਟ ਦੀ ਜਾਂਚ ਕਰੋ
- **SDK ਆਬਜੈਕਟ ਦੀ ਬਜਾਏ raw string ਵਾਪਸ ਕਰਦਾ ਹੈ** — v1.x ਵਿੱਚ ਹੱਲ ਕੀਤਾ ਗਿਆ; response sanitizer ਉਹ ਗੈਰ-ਮਿਆਰੀ ਫ਼ੀਲਡ (`x_groq`, `usage_breakdown`, ਆਦਿ) ਹਟਾ ਦਿੰਦਾ ਹੈ ਜੋ OpenAI SDK Pydantic validation ਅਸਫਲਤਾਵਾਂ ਦਾ ਕਾਰਨ ਬਣਦੇ ਹਨ। ਜੇ ਤੁਹਾਨੂੰ v3.x+ 'ਤੇ ਹਾਲੇ ਵੀ ਇਹ ਸਮੱਸਿਆ ਦਿਖਾਈ ਦਿੰਦੀ ਹੈ, ਤਾਂ ਕਿਰਪਾ ਕਰਕੇ ਇੱਕ issue ਦਰਜ ਕਰੋ।
- **GLM/ERNIE `system` ਭੂਮਿਕਾ ਨੂੰ ਅਸਵੀਕਾਰ ਕਰਦਾ ਹੈ** — v1.x ਵਿੱਚ ਹੱਲ ਕੀਤਾ ਗਿਆ; role normalizer ਅਸੰਗਤ ਮਾਡਲਾਂ ਲਈ system ਸੁਨੇਹਿਆਂ ਨੂੰ ਆਪਣੇ-ਆਪ user ਸੁਨੇਹਿਆਂ ਵਿੱਚ ਮਿਲਾ ਦਿੰਦਾ ਹੈ। ਜੇ ਤੁਹਾਨੂੰ v3.x+ 'ਤੇ ਹਾਲੇ ਵੀ ਇਹ ਸਮੱਸਿਆ ਦਿਖਾਈ ਦਿੰਦੀ ਹੈ, ਤਾਂ ਕਿਰਪਾ ਕਰਕੇ ਇੱਕ issue ਦਰਜ ਕਰੋ।
- **`developer` ਭੂਮਿਕਾ ਪਛਾਣੀ ਨਹੀਂ ਗਈ** — v1.x ਵਿੱਚ ਹੱਲ ਕੀਤਾ ਗਿਆ; ਗੈਰ-OpenAI ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ ਆਪਣੇ-ਆਪ `system` ਵਿੱਚ ਬਦਲਿਆ ਜਾਂਦਾ ਹੈ। ਜੇ ਤੁਹਾਨੂੰ v3.x+ 'ਤੇ ਹਾਲੇ ਵੀ ਇਹ ਸਮੱਸਿਆ ਦਿਖਾਈ ਦਿੰਦੀ ਹੈ, ਤਾਂ ਕਿਰਪਾ ਕਰਕੇ ਇੱਕ issue ਦਰਜ ਕਰੋ।
- **`json_schema` Gemini ਨਾਲ ਕੰਮ ਨਹੀਂ ਕਰ ਰਿਹਾ** — v1.x ਵਿੱਚ ਹੱਲ ਕੀਤਾ ਗਿਆ; `response_format` ਨੂੰ ਹੁਣ Gemini ਦੇ `responseMimeType` + `responseSchema` ਵਿੱਚ ਬਦਲਿਆ ਜਾਂਦਾ ਹੈ। ਜੇ ਤੁਹਾਨੂੰ v3.x+ 'ਤੇ ਹਾਲੇ ਵੀ ਇਹ ਸਮੱਸਿਆ ਦਿਖਾਈ ਦਿੰਦੀ ਹੈ, ਤਾਂ ਕਿਰਪਾ ਕਰਕੇ ਇੱਕ issue ਦਰਜ ਕਰੋ।

## ਲਚੀਲਾਪਣ ਸੈਟਿੰਗਾਂ

### ਆਟੋ ਰੇਟ-ਲਿਮਿਟ ਟ੍ਰਿਗਰ ਨਹੀਂ ਹੋ ਰਹੀ

- ਆਟੋ ਰੇਟ-ਲਿਮਿਟ ਸਿਰਫ਼ API ਕੁੰਜੀ ਪ੍ਰਦਾਤਾਵਾਂ 'ਤੇ ਲਾਗੂ ਹੁੰਦੀ ਹੈ (OAuth/ਸਬਸਕ੍ਰਿਪਸ਼ਨ 'ਤੇ ਨਹੀਂ)
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ **Settings → Resilience → Provider Profiles** ਵਿੱਚ ਆਟੋ-ਰੇਟ-ਲਿਮਿਟ ਸਮਰੱਥ ਹੈ
- ਜਾਂਚ ਕਰੋ ਕਿ ਕੀ ਪ੍ਰਦਾਤਾ `429` ਸਥਿਤੀ ਕੋਡ ਜਾਂ `Retry-After` ਹੈਡਰ ਵਾਪਸ ਕਰਦਾ ਹੈ

### ਐਕਸਪੋਨੇਨਸ਼ੀਅਲ ਬੈਕਆਫ਼ ਨੂੰ ਟਿਊਨ ਕਰਨਾ

ਪ੍ਰਦਾਤਾ ਪ੍ਰੋਫ਼ਾਈਲ ਇਨ੍ਹਾਂ ਸੈਟਿੰਗਾਂ ਦਾ ਸਮਰਥਨ ਕਰਦੇ ਹਨ:

- **ਮੂਲ ਦੇਰੀ** — ਪਹਿਲੀ ਅਸਫਲਤਾ ਤੋਂ ਬਾਅਦ ਸ਼ੁਰੂਆਤੀ ਉਡੀਕ ਸਮਾਂ (ਡਿਫਾਲਟ: 1s)
- **ਵੱਧ ਤੋਂ ਵੱਧ ਦੇਰੀ** — ਉਡੀਕ ਸਮੇਂ ਦੀ ਵੱਧ ਤੋਂ ਵੱਧ ਸੀਮਾ (ਡਿਫਾਲਟ: 30s)
- **ਗੁਣਕ** — ਹਰ ਲਗਾਤਾਰ ਅਸਫਲਤਾ ਨਾਲ ਦੇਰੀ ਨੂੰ ਕਿੰਨਾ ਵਧਾਉਣਾ ਹੈ (ਡਿਫਾਲਟ: 2x)

### ਐਂਟੀ-ਥੰਡਰਿੰਗ ਹਰਡ

ਜਦੋਂ ਬਹੁਤ ਸਾਰੀਆਂ ਸਮਕਾਲੀ ਬੇਨਤੀਆਂ ਕਿਸੇ ਰੇਟ-ਲਿਮਿਟ ਕੀਤੇ ਪ੍ਰਦਾਤਾ ਤੱਕ ਪਹੁੰਚਦੀਆਂ ਹਨ, ਤਾਂ OmniRoute ਬੇਨਤੀਆਂ ਨੂੰ ਕ੍ਰਮਵਾਰ ਕਰਨ ਅਤੇ ਲੜੀਵਾਰ ਅਸਫਲਤਾਵਾਂ ਨੂੰ ਰੋਕਣ ਲਈ ਮਿਊਟੈਕਸ + ਆਟੋ ਰੇਟ-ਲਿਮਿਟਿੰਗ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। ਇਹ API ਕੁੰਜੀ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ ਆਪਣੇ ਆਪ ਹੁੰਦਾ ਹੈ।

### ਚੈਟ ਬੇਨਤੀਆਂ 503 / chat_admission_busy ਨਾਲ ਅਸਫਲ ਹੁੰਦੀਆਂ ਹਨ

**ਲੱਛਣ:**

- ਚੈਟ ਕੰਪਲੀਸ਼ਨ ਐਂਡਪੌਇੰਟ ਮੁੜ ਕੋਸ਼ਿਸ਼ਯੋਗ `503` ਜਵਾਬ ਵਾਪਸ ਕਰਦਾ ਹੈ, ਜਿਸਦਾ ਗਲਤੀ ਕੋਡ
  `chat_admission_busy` ਹੁੰਦਾ ਹੈ।
- ਜਵਾਬ ਵਿੱਚ `Retry-After` ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ। #12135 ਤੋਂ ਬਾਅਦ ਇਸਦਾ ਮੁੱਲ ਦੇਖੀ ਗਈ
  ਓਕਿਊਪੈਂਸੀ ਤੋਂ ਨਿਰਧਾਰਤ ਹੁੰਦਾ ਹੈ — ਬੇਨਤੀ ਵੱਲੋਂ ਪਹਿਲਾਂ ਹੀ ਉਡੀਕੀ ਗਈ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  ਵਿੰਡੋ ਅਤੇ ਮੌਜੂਦਾ ਹੈਵੀਵੇਟ ਲੀਜ਼ਾਂ ਦੇ ਰੱਖੇ ਰਹਿਣ ਦੇ ਸਮੇਂ ਵਿੱਚੋਂ ਵੱਡਾ ਮੁੱਲ — ਜਿਸਨੂੰ ਪੂਰੇ
  ਸਕਿੰਟਾਂ ਤੱਕ ਉੱਪਰ ਵੱਲ ਰਾਊਂਡ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ 60 'ਤੇ ਸੀਮਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਨਿਸ਼ਕਿਰਿਆ ਗੇਟ 'ਤੇ ਇਹ ਇਤਿਹਾਸਕ ਨਿਊਨਤਮ ਸੀਮਾਵਾਂ ਬਰਕਰਾਰ
  ਰੱਖਦਾ ਹੈ: ਬਾਈਟ-ਆਧਾਰਿਤ ਪਾਥ 'ਤੇ 2 ਸਕਿੰਟ, ਸਟ੍ਰਕਚਰ-ਆਧਾਰਿਤ ਪਾਥ 'ਤੇ 1 ਸਕਿੰਟ (ਜਿਸ ਵਿੱਚ
  `reason: "structure_limit"` ਵੀ ਸ਼ਾਮਲ ਹੈ)।
- ਇਹ ਉਸ ਵੇਲੇ ਹੋ ਸਕਦਾ ਹੈ ਜਦੋਂ ਕੋਈ ਹੋਰ ਹੈਵੀਵੇਟ ਚੈਟ ਜਾਂ ਲੰਬੇ ਸਮੇਂ ਤੱਕ ਚੱਲਣ ਵਾਲਾ ਸਟ੍ਰੀਮਿੰਗ ਜਵਾਬ ਅਜੇ ਵੀ
  ਪ੍ਰਕਿਰਿਆ ਅਧੀਨ ਹੋਵੇ।

ਬਾਈਟ-ਆਧਾਰਿਤ ਜਵਾਬ ਦੀ ਬਾਡੀ ਇਹ ਹੈ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ਸਟ੍ਰਕਚਰ-ਆਧਾਰਿਤ ਜਵਾਬ ਉਸੇ ਕਿਸਮ ਅਤੇ ਕੋਡ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ, ਜਿਸਦਾ ਸੁਨੇਹਾ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ਅਤੇ `reason: "structure_limit"` ਹੁੰਦਾ ਹੈ।
ਡਿਫਾਲਟ ਥ੍ਰੈਸ਼ਹੋਲਡਾਂ 'ਤੇ, ਇੱਕ ਬੇਨਤੀ ਨੂੰ ਸਟ੍ਰਕਚਰ ਪੱਖੋਂ ਭਾਰੀ ਮੰਨਿਆ ਜਾਂਦਾ ਹੈ ਜਦੋਂ ਉਸ ਵਿੱਚ ਘੱਟੋ-ਘੱਟ `200` ਸੁਨੇਹੇ,
ਘੱਟੋ-ਘੱਟ `64` ਟੂਲ, ਜਾਂ ਘੱਟੋ-ਘੱਟ `32,000` ਅਨੁਮਾਨਿਤ ਟੋਕਨ ਹੋਣ, ਜਾਂ ਜਦੋਂ ਸੀਮਾਬੱਧ ਸਟ੍ਰਕਚਰ ਅਨੁਮਾਨ
`10,000` ਵਿਜ਼ਿਟ ਕੀਤੇ ਨੋਡਾਂ ਜਾਂ `12` ਦੀ ਡੈਪਥ ਦੀਆਂ ਆਪਣੀਆਂ ਸੀਮਾਵਾਂ ਖ਼ਤਮ ਕਰ ਦੇਵੇ।

**ਕਾਰਨ:** ਇਹ OmniRoute ਦੇ ਅੰਦਰ ਜਾਣਬੁੱਝ ਕੇ ਕੀਤੀ ਗਈ ਲੋਡ ਸ਼ੈਡਿੰਗ ਹੈ, ਅੱਪਸਟ੍ਰੀਮ-ਪ੍ਰਦਾਤਾ ਦੀ ਅਸਫਲਤਾ ਨਹੀਂ।
ਹਰੇਕ ਪ੍ਰਕਿਰਿਆ ਇੱਕ ਵੱਡੀ ਬੇਨਤੀ ਬਾਡੀ ਨੂੰ ਸੰਭਾਲ ਕੇ ਰੱਖਣ ਅਤੇ ਪਾਰਸ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਸੀਮਿਤ ਹੈਵੀਵੇਟ ਸਮਰੱਥਾ ਰਾਖਵੀਂ ਕਰਨ ਲਈ
ਪ੍ਰਕਿਰਿਆ-ਸਥਾਨਕ ਗਾਰਡ ਦੀ ਵਰਤੋਂ ਕਰਦੀ ਹੈ। ਇੱਕ ਹੈਵੀਵੇਟ ਲੀਜ਼ SSE
ਜਵਾਬ ਦੇ ਪੂਰੇ ਜੀਵਨਕਾਲ ਲਈ ਰੱਖੀ ਰਹਿੰਦੀ ਹੈ।

**#503-ਫੈਨਆਊਟ:** ਇਸ ਸੁਧਾਰ ਤੋਂ ਪਹਿਲਾਂ, ਗਾਰਡ ਹੋਸਟ ਮੈਮੋਰੀ ਦੀ ਪਰਵਾਹ ਕੀਤੇ ਬਿਨਾਂ ਇੱਕ ਨਿਸ਼ਚਿਤ ਬੇਨਤੀ COUNT
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ਡਿਫਾਲਟ `1`) 'ਤੇ ਸਮਕਾਲੀਤਾ ਨੂੰ ਸੀਮਿਤ ਕਰਦਾ ਸੀ, ਇਸ ਲਈ ਕੋਡਿੰਗ-ਏਜੰਟ
ਫੈਨ-ਆਊਟ (ਕਈ ਸਬਏਜੰਟ/CLI, ਬਾਡੀਆਂ ਆਮ ਤੌਰ 'ਤੇ > 256 KB) ਲਗਭਗ 1 ਦੀ ਪ੍ਰਭਾਵਸ਼ਾਲੀ
ਸਮਕਾਲੀਤਾ ਤੱਕ ਘਟ ਗਿਆ ਅਤੇ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਧਾਰਨ ਲੋਡ ਹੇਠ 503 ਦੇਣ ਲੱਗ ਪਿਆ। ਗਾਰਡ ਹੁਣ ਆਪਣੇ ਆਪ ਟਿਊਨ ਹੁੰਦਾ ਹੈ: ਇਸਨੂੰ
ਪ੍ਰਕਿਰਿਆ ਦੀ ਅਸਲ ਮੈਮੋਰੀ ਸੀਮਾ ਤੋਂ ਆਕਾਰ ਪ੍ਰਾਪਤ ਕਰਨ ਵਾਲੇ ਆਪਣੇ ਆਪ ਨਿਰਧਾਰਤ ਇਨਜੈਸਟ BYTE ਬਜਟ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ਦੁਆਰਾ ਨਿਯੰਤਰਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ,
ਅਤੇ ਇਹ ਇੱਕ ਲਾਈਵ ਸਰੋਤ-ਦਬਾਅ ਸੰਕੇਤ ਨੂੰ ਵੀ ਧਿਆਨ ਵਿੱਚ ਰੱਖਦਾ ਹੈ — ਇਸ ਲਈ ਇਹ ਸਿਰਫ਼ ਉਦੋਂ ਹੀ ਲੋਡ ਘਟਾਉਂਦਾ ਹੈ ਜਦੋਂ ਹੋਸਟ ਸੱਚਮੁੱਚ
ਮੈਮੋਰੀ ਦਬਾਅ ਹੇਠ ਹੋਵੇ, ਨਾ ਕਿ ਸਿਰਫ਼ ਇਸ ਲਈ ਕਿ ਇੱਕੋ ਸਮੇਂ ਇੱਕ ਤੋਂ ਵੱਧ ਭਾਰੀ ਬੇਨਤੀਆਂ ਆ ਗਈਆਂ।
ਪੁਰਾਣੀ ਗਿਣਤੀ ਸੀਮਾ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ਦਾ ਅਜੇ ਵੀ ਸਤਿਕਾਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਪਰ ਸਿਰਫ਼ ਉਦੋਂ ਜਦੋਂ ਤੁਸੀਂ ਇਸਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਸੈੱਟ ਕਰਦੇ ਹੋ।

ਜਦੋਂ ਸਮਰੱਥਾ ਵਿਅਸਤ ਹੁੰਦੀ ਹੈ, ਤਾਂ ਇੱਕ ਹੈਵੀਵੇਟ ਬੇਨਤੀ ਮੁੜ ਕੋਸ਼ਿਸ਼ਯੋਗ `503` ਦਾ ਜਵਾਬ ਦੇਣ ਤੋਂ ਪਹਿਲਾਂ
ਸਲਾਟ ਖਾਲੀ ਹੋਣ ਲਈ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ਡਿਫਾਲਟ `2000`, `0` ਉਡੀਕ ਨੂੰ ਅਸਮਰੱਥ ਕਰਦਾ ਹੈ) ਤੱਕ ਉਡੀਕ ਕਰਦੀ ਹੈ।
ਇਹ ਸੀਮਾਬੱਧ ਉਡੀਕ ਇਸ ਲਈ ਮੌਜੂਦ ਹੈ ਤਾਂ ਜੋ ਏਜੰਟ-ਸ਼ੈਲੀ ਕਲਾਇੰਟ
(OpenCode, Claude Code, Cursor), ਜੋ ਭਾਰੀ ਸਬ-ਬੇਨਤੀਆਂ ਨੂੰ ਸਮਕਾਲੀ ਤੌਰ 'ਤੇ ਫੈਨ-ਆਊਟ ਕਰਦੇ ਹਨ, ਤੁਰੰਤ ਅਸਵੀਕਾਰਤਾਵਾਂ 'ਤੇ ਆਪਣਾ ਪੂਰਾ ਮੁੜ-ਕੋਸ਼ਿਸ਼ ਬਜਟ ਖਰਚਣ
ਅਤੇ ਕੰਮ ਦੇ ਵਿਚਕਾਰ ਬੰਦ ਹੋ ਜਾਣ ਦੀ ਬਜਾਏ ਬਰਸਟ ਨੂੰ ਕ੍ਰਮਵਾਰ ਕਰ ਸਕਣ।
ਮੌਜੂਦਾ ਹੈਵੀਵੇਟ ਲੀਜ਼ ਓਕਿਊਪੈਂਸੀ, ਨਿਰਧਾਰਤ ਬਾਈਟ ਬਜਟ ਅਤੇ ਲਾਈਵ ਦਬਾਅ ਦੀ ਗੰਭੀਰਤਾ
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) 'ਤੇ ਦਿਖਾਈ ਜਾਂਦੀ ਹੈ — ਕਿਸੇ ਵੀ env var ਨੂੰ ਬਦਲਣ ਤੋਂ ਪਹਿਲਾਂ ਇਨ੍ਹਾਂ ਦੀ ਜਾਂਚ ਕਰੋ।
Settings → Resilience → Request Queue → Concurrent Requests ਇਸਨੂੰ ਨਿਯੰਤਰਿਤ ਨਹੀਂ ਕਰਦਾ; ਉਹ ਸੈਟਿੰਗ
ਇੱਕ ਵੱਖਰੀ ਪ੍ਰਦਾਤਾ ਬੇਨਤੀ-ਕਤਾਰ ਵਿਧੀ ਨੂੰ ਨਿਯੰਤਰਿਤ ਕਰਦੀ ਹੈ।

**ਹੱਲ:**

1. ਪਹਿਲਾਂ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਕਰੋ। ਕਲਾਇੰਟਾਂ ਨੂੰ ਬੇਨਤੀ ਤੁਰੰਤ ਦੁਹਰਾਉਣ ਦੀ ਬਜਾਏ `Retry-After` ਦਾ ਸਤਿਕਾਰ ਕਰਨਾ
   ਅਤੇ ਬੈਕਆਫ਼ ਦੀ ਵਰਤੋਂ ਕਰਨੀ ਚਾਹੀਦੀ ਹੈ।
2. ਕੁਝ ਵੀ ਟਿਊਨ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ `/api/monitoring/health` → `chatAdmission` ਦੀ ਜਾਂਚ ਕਰੋ। `countCapEnabled:
false` ਅਤੇ ਇੱਕ ਖੁੱਲ੍ਹਾ `maxInflightBytes` ਦਰਸਾਉਂਦੇ ਹਨ ਕਿ ਆਪਣੇ ਆਪ ਨਿਰਧਾਰਤ ਬਜਟ ਪਹਿਲਾਂ ਹੀ ਆਪਣਾ
   ਕੰਮ ਕਰ ਰਿਹਾ ਹੈ; `high`/`critical` ਦਾ `pressureSeverity` ਦਰਸਾਉਂਦਾ ਹੈ ਕਿ ਹੋਸਟ ਕੋਲ ਸੱਚਮੁੱਚ ਮੈਮੋਰੀ ਘੱਟ ਹੈ —
   ਇਸਨੂੰ ਕਿਸੇ ਐਡਮਿਸ਼ਨ env var ਨਾਲ ਠੀਕ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ, ਇਸ ਲਈ ਵੱਧ RAM ਜਾਂ ਛੋਟੇ ਵਰਕਲੋਡ ਦੀ ਲੋੜ ਹੈ।
3. ਸਿਰਫ਼ ਉਦੋਂ, ਜਦੋਂ `/api/monitoring/health` ਦਿਖਾਉਂਦਾ ਹੈ ਕਿ ਆਪਣੇ ਆਪ ਨਿਰਧਾਰਤ ਬਜਟ ਤੁਹਾਡੇ ਹੋਸਟ ਲਈ ਸੱਚਮੁੱਚ ਬਹੁਤ ਛੋਟਾ ਹੈ
   (ਦੁਰਲੱਭ — ਇਹ ਪਹਿਲਾਂ ਹੀ ਕੰਟੇਨਰ ਤੋਂ ਬੇਅਰ-ਮੈਟਲ ਤੱਕ ਸਕੇਲ ਹੁੰਦਾ ਹੈ), ਪੁਰਾਣੀ ਬੇਨਤੀ-ਗਿਣਤੀ ਸੀਮਾ 'ਤੇ ਵਾਪਸ ਜਾਣ ਦੀ ਬਜਾਏ
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ਨਾਲ ਇਸਨੂੰ ਸਿੱਧੇ ਓਵਰਰਾਈਡ ਕਰੋ।

ਅਧਿਕਾਰਤ ਐਡਮਿਸ਼ਨ ਸੈਟਿੰਗਾਂ ਲਈ [ਵਾਤਾਵਰਣ-ਵੇਰੀਏਬਲ ਹਵਾਲਾ](../reference/ENVIRONMENT.md#4-security--authentication)
ਵੇਖੋ।

## ਵਿਕਲਪਿਕ RAG / LLM ਅਸਫਲਤਾ ਵਰਗੀਕਰਨ (16 ਸਮੱਸਿਆਵਾਂ)

ਕੁਝ OmniRoute ਵਰਤੋਂਕਾਰ ਗੇਟਵੇ ਨੂੰ RAG ਜਾਂ ਏਜੰਟ ਸਟੈਕਾਂ ਦੇ ਅੱਗੇ ਰੱਖਦੇ ਹਨ। ਅਜਿਹੀਆਂ ਸੈਟਅੱਪਾਂ ਵਿੱਚ ਇੱਕ ਅਜੀਬ ਪੈਟਰਨ ਆਮ ਤੌਰ 'ਤੇ ਵੇਖਣ ਨੂੰ ਮਿਲਦਾ ਹੈ: OmniRoute ਠੀਕ-ਠਾਕ ਦਿਸਦਾ ਹੈ (ਪ੍ਰਦਾਤਾ ਚਾਲੂ ਹਨ, ਰੂਟਿੰਗ ਪ੍ਰੋਫ਼ਾਈਲ ਠੀਕ ਹਨ, ਕੋਈ ਰੇਟ ਲਿਮਿਟ ਚੇਤਾਵਨੀ ਨਹੀਂ ਹੈ), ਪਰ ਅੰਤਿਮ ਜਵਾਬ ਫਿਰ ਵੀ ਗਲਤ ਹੁੰਦਾ ਹੈ।

ਅਮਲ ਵਿੱਚ, ਇਹ ਘਟਨਾਵਾਂ ਆਮ ਤੌਰ 'ਤੇ ਡਾਊਨਸਟ੍ਰੀਮ RAG ਪਾਈਪਲਾਈਨ ਤੋਂ ਪੈਦਾ ਹੁੰਦੀਆਂ ਹਨ, ਨਾ ਕਿ ਖੁਦ ਗੇਟਵੇ ਤੋਂ।

ਜੇ ਤੁਸੀਂ ਇਨ੍ਹਾਂ ਅਸਫਲਤਾਵਾਂ ਦਾ ਵਰਣਨ ਕਰਨ ਲਈ ਇੱਕ ਸਾਂਝੀ ਸ਼ਬਦਾਵਲੀ ਚਾਹੁੰਦੇ ਹੋ, ਤਾਂ ਤੁਸੀਂ WFGY ProblemMap ਦੀ ਵਰਤੋਂ ਕਰ ਸਕਦੇ ਹੋ। ਇਹ MIT ਲਾਇਸੈਂਸ ਵਾਲਾ ਇੱਕ ਬਾਹਰੀ ਪਾਠ ਸਰੋਤ ਹੈ, ਜੋ RAG / LLM ਦੀਆਂ ਵਾਰ-ਵਾਰ ਆਉਣ ਵਾਲੀਆਂ ਸੋਲ੍ਹਾਂ ਅਸਫਲਤਾ ਕਿਸਮਾਂ ਨੂੰ ਪਰਿਭਾਸ਼ਿਤ ਕਰਦਾ ਹੈ। ਉੱਚ ਪੱਧਰ 'ਤੇ, ਇਹ ਹੇਠ ਲਿਖਿਆਂ ਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ:

- ਰਿਟਰੀਵਲ ਡ੍ਰਿਫਟ ਅਤੇ ਟੁੱਟੀਆਂ ਕਾਂਟੈਕਸਟ ਸੀਮਾਵਾਂ
- ਖਾਲੀ ਜਾਂ ਪੁਰਾਣੇ ਇੰਡੈਕਸ ਅਤੇ ਵੈਕਟਰ ਸਟੋਰ
- ਐਮਬੈਡਿੰਗ ਅਤੇ ਅਰਥ-ਸੰਬੰਧੀ ਬੇਮੇਲਤਾ
- ਪ੍ਰੌਂਪਟ ਅਸੈਂਬਲੀ ਅਤੇ ਕਾਂਟੈਕਸਟ ਵਿੰਡੋ ਦੀਆਂ ਸਮੱਸਿਆਵਾਂ
- ਤਰਕ ਦਾ ਢਹਿ ਜਾਣਾ ਅਤੇ ਹੱਦੋਂ ਵੱਧ ਭਰੋਸੇ ਵਾਲੇ ਜਵਾਬ
- ਲੰਬੀ ਚੇਨ ਅਤੇ ਏਜੰਟ ਤਾਲਮੇਲ ਦੀਆਂ ਅਸਫਲਤਾਵਾਂ
- ਮਲਟੀ-ਏਜੰਟ ਮੈਮੋਰੀ ਅਤੇ ਭੂਮਿਕਾ ਡ੍ਰਿਫਟ
- ਡਿਪਲੌਇਮੈਂਟ ਅਤੇ ਬੂਟਸਟਰੈਪ ਕ੍ਰਮ ਦੀਆਂ ਸਮੱਸਿਆਵਾਂ

ਵਿਚਾਰ ਸਧਾਰਨ ਹੈ:

1. ਜਦੋਂ ਤੁਸੀਂ ਕਿਸੇ ਗਲਤ ਜਵਾਬ ਦੀ ਜਾਂਚ ਕਰਦੇ ਹੋ, ਤਾਂ ਇਹ ਜਾਣਕਾਰੀ ਦਰਜ ਕਰੋ:
   - ਵਰਤੋਂਕਾਰ ਦਾ ਕੰਮ ਅਤੇ ਬੇਨਤੀ
   - OmniRoute ਵਿੱਚ ਰੂਟ ਜਾਂ ਪ੍ਰਦਾਤਾ ਕੌਂਬੋ
   - ਡਾਊਨਸਟ੍ਰੀਮ ਵਿੱਚ ਵਰਤਿਆ ਗਿਆ ਕੋਈ ਵੀ RAG ਕਾਂਟੈਕਸਟ (ਰਿਟਰੀਵ ਕੀਤੇ ਦਸਤਾਵੇਜ਼, ਟੂਲ ਕਾਲਾਂ ਆਦਿ)
2. ਘਟਨਾ ਨੂੰ ਇੱਕ ਜਾਂ ਦੋ WFGY ProblemMap ਨੰਬਰਾਂ (`No.1` … `No.16`) ਨਾਲ ਮੈਪ ਕਰੋ।
3. OmniRoute ਲੌਗਾਂ ਦੇ ਨਾਲ ਆਪਣੇ ਡੈਸ਼ਬੋਰਡ, ਰਨਬੁੱਕ, ਜਾਂ ਘਟਨਾ ਟ੍ਰੈਕਰ ਵਿੱਚ ਨੰਬਰ ਸਟੋਰ ਕਰੋ।
4. ਇਹ ਫ਼ੈਸਲਾ ਕਰਨ ਲਈ ਸੰਬੰਧਿਤ WFGY ਪੰਨੇ ਦੀ ਵਰਤੋਂ ਕਰੋ ਕਿ ਕੀ ਤੁਹਾਨੂੰ ਆਪਣੇ RAG ਸਟੈਕ, ਰਿਟਰੀਵਰ, ਜਾਂ ਰੂਟਿੰਗ ਰਣਨੀਤੀ ਵਿੱਚ ਤਬਦੀਲੀ ਕਰਨ ਦੀ ਲੋੜ ਹੈ।

ਪੂਰਾ ਪਾਠ ਅਤੇ ਠੋਸ ਵਿਧੀਆਂ ਇੱਥੇ ਉਪਲਬਧ ਹਨ (MIT ਲਾਇਸੈਂਸ, ਕੇਵਲ ਪਾਠ):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

ਜੇ ਤੁਸੀਂ OmniRoute ਦੇ ਪਿੱਛੇ RAG ਜਾਂ ਏਜੰਟ ਪਾਈਪਲਾਈਨਾਂ ਨਹੀਂ ਚਲਾਉਂਦੇ, ਤਾਂ ਤੁਸੀਂ ਇਸ ਭਾਗ ਨੂੰ ਅਣਡਿੱਠਾ ਕਰ ਸਕਦੇ ਹੋ।

- ਮਿਆਦ ਸਮਾਪਤੀ ਦਾ ਸਮਾਂ ਲੰਘ ਜਾਣ ਤੋਂ ਬਾਅਦ ਵੀ ਕੋਈ ਮਾਡਲ ਕੂਲਡਾਊਨ ਵਿੱਚ ਸੂਚੀਬੱਧ ਰਹਿੰਦਾ ਹੈ
- ਟਾਈਮਸਟੈਂਪ ਬੀਤੇ ਸਮੇਂ ਦਾ ਹੋਣ ਦੇ ਬਾਵਜੂਦ, ਕੌਂਬੋ ਰੂਟਿੰਗ ਵਿੱਚ ਬੇਨਤੀਆਂ ਅਜੇ ਵੀ ਮਾਡਲ ਨੂੰ ਛੱਡ ਦਿੰਦੀਆਂ ਹਨ

**ਹੱਥੀਂ ਰੀਸੈੱਟ:**

- **ਡੈਸ਼ਬੋਰਡ:** **Settings → Model Cooldowns** → ਪ੍ਰਭਾਵਿਤ ਕਾਰਡ 'ਤੇ **Re-enable** ਨੂੰ ਕਲਿੱਕ ਕਰੋ
- **API:** ਪ੍ਰਬੰਧਨ ਪ੍ਰਮਾਣੀਕਰਨ ਹੈਡਰਾਂ ਨਾਲ `DELETE /api/resilience/model-cooldowns`

### Command Code ਪ੍ਰਦਾਤਾ ਕਨੈਕਸ਼ਨ 403 ਨਾਲ ਅਸਫਲ ਹੁੰਦਾ ਹੈ

**ਲੱਛਣ:**

- Command Code ਪ੍ਰਦਾਤਾ ਕਨੈਕਸ਼ਨ ਦੀ ਜਾਂਚ ਕਰਦੇ ਸਮੇਂ 403
- ਨਵਾਂ ਜੋੜਨ ਤੋਂ ਬਾਅਦ ਪ੍ਰਦਾਤਾ ਕਾਰਡ "unauthorized" ਦਿਖਾਉਂਦਾ ਹੈ

**ਕਾਰਨ:** OAuth ਪ੍ਰਵਾਹ ਪੂਰਾ ਨਹੀਂ ਹੋਇਆ (ਕਾਲਬੈਕ ਪ੍ਰਾਪਤ ਨਹੀਂ ਹੋਇਆ ਜਾਂ ਟੋਕਨ ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੁਰੱਖਿਅਤ ਨਹੀਂ ਕੀਤਾ ਗਿਆ)।

**ਸੁਧਾਰ:**

- OAuth ਪ੍ਰਵਾਹ ਨੂੰ ਦੁਬਾਰਾ ਸ਼ੁਰੂ ਕਰਨ ਲਈ CLI ਤੋਂ `omniroute providers` ਚਲਾਓ, ਜਾਂ
- **Dashboard → Providers → Command Code → Reconnect** ਤੋਂ OAuth ਨੂੰ ਦੁਬਾਰਾ ਚਲਾਓ

### ModelScope ਬਹੁਤ ਸਖ਼ਤ 429 ਕੂਲਡਾਊਨ ਵਾਪਸ ਕਰਦਾ ਹੈ

**ਲੱਛਣ:**

- ਬੇਨਤੀਆਂ ਦੇ ਇੱਕ ਛੋਟੇ ਜਿਹੇ ਬਰਸਟ ਤੋਂ ਬਾਅਦ ModelScope 'ਤੇ ਬਹੁਤ ਛੋਟੇ ਜਾਂ ਤੁਰੰਤ ਕੂਲਡਾਊਨ
- ਕੌਂਬੋ ਰੂਟਿੰਗ ਉਮੀਦ ਤੋਂ ਪਹਿਲਾਂ ਹੀ ModelScope ਨੂੰ ਛੱਡ ਦਿੰਦੀ ਹੈ

**ਕਾਰਨ:** ModelScope ਪ੍ਰਦਾਤਾ-ਵਿਸ਼ੇਸ਼ `Retry-After` ਹੈਡਰ ਭੇਜਦਾ ਹੈ। v3.8.0 ਵਿੱਚ ਉਨ੍ਹਾਂ ਹੈਡਰਾਂ ਲਈ ਵਿਸ਼ੇਸ਼ ਹੈਂਡਲਿੰਗ ਸ਼ਾਮਲ ਹੈ, ਇਸ ਲਈ ਪੁਰਾਣੇ ਵਰਜਨ ਉਨ੍ਹਾਂ ਨੂੰ ਆਮ ਰੇਟ-ਲਿਮਿਟ ਸੰਕੇਤਾਂ ਵਜੋਂ ਗਲਤ ਪੜ੍ਹਦੇ ਹਨ।

**ਸੁਧਾਰ:**

- ਯਕੀਨੀ ਬਣਾਓ ਕਿ ਤੁਸੀਂ v3.8.0 ਜਾਂ ਇਸ ਤੋਂ ਬਾਅਦਲੇ ਵਰਜਨ 'ਤੇ ਹੋ
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ **Settings → Resilience** ਦੇ ਅਧੀਨ `useUpstream429BreakerHints` ਟੌਗਲ ਸਮਰੱਥ ਹੈ

### ਪ੍ਰੋਡਕਸ਼ਨ ਵਿੱਚ OMNIROUTE_WS_BRIDGE_SECRET ਮੌਜੂਦ ਨਹੀਂ ਹੈ

**ਲੱਛਣ:**

- ਰਿਮੋਟ ਪ੍ਰੋਡਕਸ਼ਨ ਹੋਸਟ 'ਤੇ ਚਲਾਉਂਦੇ ਸਮੇਂ ਹਰ Codex/Responses WebSocket ਬ੍ਰਿਜ ਬੇਨਤੀ ਉੱਤੇ 401
- ਕਨੈਕਟ ਹੋਣ ਤੋਂ ਤੁਰੰਤ ਬਾਅਦ WebSocket ਬ੍ਰਿਜ ਹੈਂਡਸ਼ੇਕ ਬੰਦ ਹੋ ਜਾਂਦਾ ਹੈ

**ਕਾਰਨ:** ਪ੍ਰੋਡਕਸ਼ਨ ਵਾਤਾਵਰਣ ਵਿੱਚ `OMNIROUTE_WS_BRIDGE_SECRET` env var ਮੌਜੂਦ ਨਹੀਂ ਹੈ।

**ਸੁਧਾਰ:**

1. ਇੱਕ ਬੇਤਰਤੀਬ ਸੀਕ੍ਰੇਟ ਬਣਾਓ: `openssl rand -hex 32`
2. ਪ੍ਰੋਡਕਸ਼ਨ ਸਰਵਰ env ਵਿੱਚ `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ਸੈੱਟ ਕਰੋ (ਅਤੇ ਬ੍ਰਿਜ ਨਾਲ ਸੰਚਾਰ ਕਰਨ ਵਾਲੇ ਕਿਸੇ ਵੀ ਕਲਾਇੰਟ ਵਿੱਚ ਵੀ)
3. OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ

### Responses API: ਬੈਕਗ੍ਰਾਊਂਡ ਮੋਡ ਨੂੰ ਸਿੰਕ੍ਰੋਨਸ ਵਿੱਚ ਘਟਾਇਆ ਗਿਆ

**ਲੱਛਣ:**

- ਚੇਤਾਵਨੀ ਲੌਗ ਕੀਤੀ ਗਈ: `background mode degraded to synchronous`
- ਇੱਕ `background: true` ਬੇਨਤੀ, ਬੈਕਗ੍ਰਾਊਂਡ ਜੌਬ ਹੈਂਡਲ ਦੀ ਬਜਾਏ ਇੱਕ ਆਮ ਸਿੰਕ੍ਰੋਨਸ ਜਵਾਬ ਵਾਪਸ ਕਰਦੀ ਹੈ

**ਕਾਰਨ:** v3.8.0 ਜਾਣ-ਬੁੱਝ ਕੇ Responses API ਉੱਤੇ `background: true` ਨੂੰ ਸਿੰਕ੍ਰੋਨਸ ਚਲਾਉਣ ਤੱਕ ਘਟਾਉਂਦਾ ਹੈ ਅਤੇ ਨਾਲ ਹੀ ਇੱਕ ਚੇਤਾਵਨੀ ਜਾਰੀ ਕਰਦਾ ਹੈ। ਪੂਰੀ ਅਸਿੰਕ੍ਰੋਨਸ ਬੈਕਗ੍ਰਾਊਂਡ ਐਗਜ਼ੀਕਿਊਸ਼ਨ ਭਵਿੱਖ ਵਿੱਚ ਉਪਲਬਧ ਕਰਵਾਈ ਜਾਵੇਗੀ।

**ਸੁਧਾਰ:**

- ਕਲਾਇੰਟ ਨੂੰ `background` ਤੋਂ ਬਿਨਾਂ ਕਾਲ ਕਰਨ ਲਈ ਸਮਾਯੋਜਿਤ ਕਰੋ, ਜਾਂ
- ਪੂਰੇ ਅਸਿੰਕ੍ਰੋਨਸ ਬੈਕਗ੍ਰਾਊਂਡ ਮੋਡ ਵਾਲੀ ਕਿਸੇ ਬਾਅਦਲੀ ਰਿਲੀਜ਼ ਦੀ ਉਡੀਕ ਕਰੋ (ਚੇਂਜਲੌਗ ਨੂੰ ਟ੍ਰੈਕ ਕਰੋ)

## ਹੌਲੀ ਸ਼ੁਰੂਆਤ / ਤਿਆਰੀ ਸਮਾਂ-ਸੀਮਾ

ਜੇ CLI `⚠ Server did not respond within 60s` ਦਿਖਾਉਂਦਾ ਹੈ ਪਰ ਸਰਵਰ
ਅਸਲ ਵਿੱਚ ਕੰਮ ਕਰ ਰਿਹਾ ਹੈ, ਤਾਂ ਤੁਹਾਡੇ ਵਾਤਾਵਰਣ ਲਈ ਤਿਆਰੀ ਜਾਂਚ ਦਾ ਸਮਾਂ-ਬਜਟ ਬਹੁਤ ਘੱਟ ਹੈ।

ਇਹ ਆਮ ਤੌਰ 'ਤੇ Windows (ਐਂਟੀਵਾਇਰਸ, ਫ਼ਾਈਲ-ਸਿਸਟਮ ਵਾਚਰ) ਜਾਂ ਭਾਰੀ
ਸ਼ੁਰੂਆਤੀ ਵਰਕਲੋਡ ਵਾਲੇ ਕੰਟੇਨਰਾਂ ਵਿੱਚ ਹੁੰਦਾ ਹੈ।

**ਹੱਲ — ਸਮਾਂ-ਬਜਟ ਵਧਾਓ:**

```bash
# env var ਰਾਹੀਂ (ਹਰ ਵਾਰ ਸ਼ੁਰੂ ਕਰਨ 'ਤੇ ਕਾਇਮ ਰਹਿੰਦਾ ਹੈ):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 ਮਿੰਟ
omniroute serve

# CLI flag ਰਾਹੀਂ (ਸਿਰਫ਼ ਇੱਕ ਵਾਰ ਲਈ):
omniroute serve --ready-timeout 180000
```

ਮੂਲ ਮੁੱਲ 60 000 ms (60 s) ਹੈ। ਚੇਤਾਵਨੀ ਸਿਰਫ਼ ਜਾਣਕਾਰੀ ਲਈ ਹੈ; ਸਰਵਰ
ਬੈਕਗ੍ਰਾਊਂਡ ਵਿੱਚ ਸ਼ੁਰੂ ਹੁੰਦਾ ਰਹਿੰਦਾ ਹੈ ਅਤੇ ਬੂਟ ਪੂਰਾ ਹੋਣ ਤੋਂ ਬਾਅਦ ਪਹੁੰਚਯੋਗ ਹੋ ਜਾਵੇਗਾ।

`OMNIROUTE_READY_TIMEOUT_MS` ਬਾਰੇ ਪੂਰੇ ਵੇਰਵਿਆਂ ਲਈ
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) ਵੇਖੋ।
