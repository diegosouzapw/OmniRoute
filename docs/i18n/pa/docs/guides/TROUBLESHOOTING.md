### ਮੁਫ਼ਤ ਪ੍ਰਦਾਤਿਆਂ ਉੱਤੇ ਦਰ ਸੀਮਾਬੰਦੀ (429 / 400 / 401)

**ਲੱਛਣ**: ਮੁਫ਼ਤ/ਬਿਨਾਂ-ਪ੍ਰਮਾਣੀਕਰਨ ਵਾਲੇ ਪ੍ਰਦਾਤਿਆਂ (opencode, auggie, ਆਦਿ) ਨਾਲ `model: "auto"` ਵਰਤਦਿਆਂ, ਤੁਹਾਨੂੰ ਜਵਾਬਾਂ ਦੀ ਬਜਾਏ ਕਦੇ-ਕਦਾਈਂ `HTTP 429`, `400`, ਜਾਂ `401` ਮਿਲਦਾ ਹੈ। ਕੁਝ ਪਲਾਂ ਬਾਅਦ ਉਸੇ ਪ੍ਰੌਂਪਟ ਨਾਲ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਕਰਨ 'ਤੇ ਬੇਨਤੀਆਂ ਸਫਲ ਹੋ ਜਾਂਦੀਆਂ ਹਨ, ਪਰ ਆਟੋਮੇਸ਼ਨ (cron ਜੌਬਾਂ, ਏਜੰਟ, ਸਕ੍ਰਿਪਟਾਂ) ਪਹਿਲੀ ਅਸਫਲਤਾ 'ਤੇ ਰੁਕ ਜਾਂਦੀ ਹੈ।

**ਮੂਲ ਕਾਰਨ**: ਤਿੰਨ ਸੁਤੰਤਰ ਅਸਫਲਤਾ ਢੰਗ ਇਕੱਠੇ ਹੋ ਜਾਂਦੇ ਹਨ:

1. **ਪ੍ਰਦਾਤਾ ਦਰ-ਸੀਮਾ (`429`)**: ਮੁਫ਼ਤ ਟੀਅਰ ਹਰ ਸਮਾਂ-ਵਿੰਡੋ ਲਈ ਕੋਟਾ ਲਾਗੂ ਕਰ ਸਕਦੇ ਹਨ। ਸਮਾਂਤਰ ਕਾਲਾਂ ਦਾ ਅਚਾਨਕ ਵਾਧਾ ਇਸਨੂੰ ਖ਼ਤਮ ਕਰ ਦਿੰਦਾ ਹੈ, ਇਸ ਲਈ ਵਿੰਡੋ ਰੀਸੈੱਟ ਹੋਣ ਤੱਕ ਅਗਲੀ ਬੇਨਤੀ ਰੱਦ ਕਰ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ।
2. **ਪਾਸਥਰੂ ਵਿੱਚ ਖ਼ਰਾਬ ਮਾਡਲ (`400`/`401`)**: `auto/*` ਪੂਲਾਂ ਵਿੱਚ `opencode` ਤੋਂ ਅਜਿਹੇ ਪਾਸਥਰੂ ਮਾਡਲ ਸ਼ਾਮਲ ਹੋ ਸਕਦੇ ਹਨ ਜੋ ਕੈਟਾਲਾਗ ਵਿੱਚ ਰਜਿਸਟਰਡ ਹਨ ਪਰ ਜਿਨ੍ਹਾਂ ਕੋਲ ਸਰਗਰਮ ਪ੍ਰਮਾਣ-ਪੱਤਰ ਨਹੀਂ ਹਨ (ਉਦਾਹਰਨ ਲਈ, `oc/north-mini-code-free` → `401`)। ਆਟੋ-ਰਾਊਟਰ ਕਿਸੇ ਇੱਕ ਨੂੰ ਅਜ਼ਮਾਉਂਦਾ ਹੈ, ਅਸਫਲ ਹੁੰਦਾ ਹੈ, ਅਤੇ ਫ਼ਾਲਬੈਕ ਸ਼ੁਰੂ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਹੀ ਗਲਤੀ ਅੱਗੇ ਭੇਜ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ।
3. **ਸਮਕਾਲੀਤਾ ਵਧੋਤਰੀ (ਲੋਡ ਹੇਠ `429`)**: ਜਦੋਂ ਕਈ ਏਜੰਟ/cron ਸੈਸ਼ਨ ਇੱਕੋ ਸਮੇਂ `auto` ਨੂੰ ਵਰਤਦੇ ਹਨ, ਤਾਂ ਸਮੁੱਚੀ ਬੇਨਤੀ ਦਰ ਮੁਫ਼ਤ ਪ੍ਰਦਾਤਿਆਂ ਦੀ ਸਹਿਣਸ਼ੀਲਤਾ ਤੋਂ ਵੱਧ ਜਾਂਦੀ ਹੈ, ਜਿਸ ਕਰਕੇ ਵਾਜਬ ਕਾਲਾਂ ਨੂੰ ਵੀ ਦੁਰਵਰਤੋਂ ਵਜੋਂ ਚਿੰਨ੍ਹਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

**ਪ੍ਰਮਾਣਿਤ ਹੱਲ (ਭਾਈਚਾਰੇ ਵੱਲੋਂ ਰਿਪੋਰਟ ਕੀਤਾ ਗਿਆ, 2026-08-10)**: ਤਿੰਨ ਵਾਤਾਵਰਨ ਵੇਰੀਏਬਲਾਂ ਨੂੰ ਇਸ ਤਰ੍ਹਾਂ ਅਨੁਕੂਲ ਕਰੋ ਕਿ ਰੋਟੇਸ਼ਨ, ਸਮਕਾਲੀਤਾ ਅਤੇ ਫ਼ਾਲਬੈਕ ਮੁਫ਼ਤ ਟੀਅਰ ਦੇ ਉਤਰਾਅ-ਚੜ੍ਹਾਅ ਕਾਰਨ ਬੰਦ ਹੋਣ ਦੀ ਬਜਾਏ ਉਸਨੂੰ ਸੰਭਾਲ ਲੈਣ:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ਉੱਤੇ ਕਿਸੇ ਹੋਰ ਮਾਡਲ/ਪ੍ਰਦਾਤਾ 'ਤੇ ਜਾਓ (ਖ਼ਰਾਬ ਪਾਸਥਰੂ ਮਾਡਲਾਂ ਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ਹੈਵੀਵੇਟ ਦਾਖ਼ਲੇ ਦੀ ਸਪਸ਼ਟ ਅਧਿਕਤਮ ਸੀਮਾ (ਮੂਲ ਰੂਪ ਵਿੱਚ ਸੈੱਟ ਨਹੀਂ: ਬੇਨਤੀ-ਗਿਣਤੀ ਉੱਤੇ ਕੋਈ ਸੀਮਾ ਨਹੀਂ, ਹੇਠਾਂ ਨੋਟ ਦੇਖੋ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ਤੁਰੰਤ ਮੁੜ-ਕੋਸ਼ਿਸ਼ਯੋਗ 503 ਦੀ ਬਜਾਏ ਹੈਵੀਵੇਟ ਸਮਰੱਥਾ ਲਈ ਵਧੇਰੇ ਲੰਬੀ ਸੀਮਿਤ ਉਡੀਕ
```

ਇਨ੍ਹਾਂ ਨੂੰ OmniRoute ਪ੍ਰਕਿਰਿਆ ਦੇ ਵਾਤਾਵਰਨ ਵਿੱਚ ਸੈੱਟ ਕਰੋ (ਡੇਮਨ ਵਿੱਚ, ਉਦਾਹਰਨ ਲਈ LaunchAgent plist ਜਾਂ `systemctl edit` ਰਾਹੀਂ), ਫਿਰ OmniRoute ਨੂੰ ਮੁੜ-ਚਾਲੂ ਕਰੋ। ਰੋਟੇਸ਼ਨ ਫਲੈਗ ਸਭ ਤੋਂ ਵੱਧ ਪ੍ਰਭਾਵ ਵਾਲਾ ਇਕੱਲਾ ਉਪਾਅ ਹੈ: ਇਹ ਇੱਕ ਪੱਕੀ ਅਸਫਲਤਾ ਨੂੰ ਪੂਲ ਵਿੱਚ ਕਿਸੇ ਸਿਹਤਮੰਦ ਪ੍ਰਦਾਤਾ ਵਿਰੁੱਧ ਪਾਰਦਰਸ਼ੀ ਮੁੜ-ਕੋਸ਼ਿਸ਼ ਵਿੱਚ ਬਦਲ ਦਿੰਦਾ ਹੈ।

**ਨੋਟ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ਇਹ ਸੀਮਿਤ ਕਰਦਾ ਹੈ ਕਿ ਕਿੰਨੀਆਂ ਹੈਵੀਵੇਟ — ਲੰਬੇ-ਸੰਦਰਭ ਵਾਲੀਆਂ — ਬੇਨਤੀਆਂ ਇੱਕੋ ਸਮੇਂ ਚੱਲਦੀਆਂ ਹਨ; ਇਹ ਸੀਮਾ ਇੱਕ ਦਾਖ਼ਲਾ ਗੇਟ ਹੈ, ਪ੍ਰਦਾਤਾ ਦਰ-ਸੀਮਾਕਾਰ ਨਹੀਂ। **#503-ਫੈਨਆਉਟ ਅੱਪਡੇਟ:** ਇਹ ਵੇਰੀਏਬਲ ਹੁਣ ਮੂਲ ਰੂਪ ਵਿੱਚ ਸੈੱਟ ਨਹੀਂ ਹੁੰਦਾ (ਇਹ ਹੁਣ ਕੇਵਲ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਸੰਰਚਿਤ ਕੀਤੇ ਜਾਣ 'ਤੇ ਹੀ ਲਾਗੂ ਹੁੰਦਾ ਹੈ, ਜਿਵੇਂ ਉੱਪਰ ਦਿੱਤਾ ਗਿਆ ਹੈ) — ਇਸਦੀ ਬਜਾਏ ਹੈਵੀਵੇਟ ਦਾਖ਼ਲੇ ਨੂੰ ਆਪਣੇ-ਆਪ ਨਿਰਧਾਰਤ ਬਾਈਟ ਬਜਟ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ਰਾਹੀਂ ਨਿਯੰਤਰਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਜੋ ਹੋਸਟ ਦੀ ਅਸਲ ਮੈਮੋਰੀ ਸੀਮਾ ਅਨੁਸਾਰ ਆਪਣੇ-ਆਪ ਸਕੇਲ ਹੁੰਦਾ ਹੈ, ਇਸ ਲਈ ਇੱਕ ਨਵੀਂ ਡਿਪਲੌਇਮੈਂਟ ਵਿੱਚ ਇਹ ਵੇਰੀਏਬਲ ਬਿਲਕੁਲ ਵੀ ਸੈੱਟ ਕੀਤੇ ਬਿਨਾਂ ਕਾਫ਼ੀ ਘੱਟ `503 chat_admission_busy` ਅਸਵੀਕ੍ਰਿਤੀਆਂ ਦਿਖਾਈ ਦੇਣੀਆਂ ਚਾਹੀਦੀਆਂ ਹਨ; ਇਸਨੂੰ ਇੱਥੇ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਸੈੱਟ ਕਰਨਾ ਹਾਲੇ ਵੀ ਦਸਤਾਵੇਜ਼ ਵਿੱਚ ਦਿੱਤੇ ਵੇਰਵੇ ਅਨੁਸਾਰ ਹੀ ਕੰਮ ਕਰਦਾ ਹੈ। ਸਪਸ਼ਟ ਬਾਈਟ-ਬਜਟ ਓਵਰਰਾਈਡਾਂ ਨੂੰ 8 MiB–2 GiB ਤੱਕ ਸੀਮਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। `413 body_exceeds_budget` ਅਸਥਾਈ ਨਹੀਂ ਹੈ: ਉਸ ਬਾਈਟ ਬਜਟ ਨੂੰ ਵਧਾਓ, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ਨੂੰ ਘਟਾਓ, ਜਾਂ ਪ੍ਰਕਿਰਿਆ ਦੀ ਮੈਮੋਰੀ ਸੀਮਾ ਵਧਾਓ। `inflight_bytes_budget` ਸ਼ੈੱਡ ਅਸਥਾਈ ਸਰੋਤ-ਟਕਰਾਅ ਹੈ ਅਤੇ ਮੁੜ-ਕੋਸ਼ਿਸ਼ਯੋਗ ਰਹਿੰਦਾ ਹੈ। ਪ੍ਰਤੀ-ਪ੍ਰਦਾਤਾ ਦਰ ਸੀਮਾਬੰਦੀ (`open-sse/services/rateLimitManager.ts`) ਨੂੰ `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, ਅਤੇ `RATE_LIMIT_AUTO_ENABLE` ਵੱਲੋਂ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਨਿਯੰਤਰਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ — `.env.example` ਦੇਖੋ।

**ਇਹ ਕਿਵੇਂ ਪੁਸ਼ਟੀ ਕਰਨੀ ਹੈ ਕਿ ਇਸ ਨੇ ਕੰਮ ਕੀਤਾ**: ਆਪਣੇ agent/cron ਨੂੰ ਥੋੜ੍ਹੇ ਜਿਹੇ ਵਕਫ਼ੇ ਵਿੱਚ ਦੋ ਵਾਰ ਚਲਾਓ ਅਤੇ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਦੋਵੇਂ ਵਾਰ ਸਫਲ ਹੁੰਦੇ ਹਨ। ਸੁਧਾਰ ਤੋਂ ਪਹਿਲਾਂ, ਦੂਜੀ ਰਨ ਆਮ ਤੌਰ 'ਤੇ `429`/`401` ਦਿੰਦੀ ਹੈ। ਸੁਧਾਰ ਤੋਂ ਬਾਅਦ, ਅਸਫਲਤਾਵਾਂ (ਜੇ ਕੋਈ ਹੋਣ) ਦੀ ਪਾਰਦਰਸ਼ੀ ਢੰਗ ਨਾਲ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਕੀਤੀ ਜਾਂਦੀ ਹੈ ਅਤੇ ਕਾਲ ਪੂਰੀ ਹੋ ਜਾਂਦੀ ਹੈ। ਤੁਸੀਂ `curl /monitoring/health` ਵੀ ਚਲਾ ਸਕਦੇ ਹੋ ਅਤੇ ਪ੍ਰਦਾਤਾ ਕਨੈਕਸ਼ਨਾਂ 'ਤੇ `rateLimitedUntil` ਫ਼ੀਲਡ ਅਤੇ ਪ੍ਰਭਾਵਿਤ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ `circuitBreakers.providerBreakers[].state` ਨੂੰ ਦੇਖ ਸਕਦੇ ਹੋ — ਸਥਿਤੀ `CLOSED`, `DEGRADED`, `OPEN`, ਜਾਂ `HALF_OPEN` ਵਿੱਚੋਂ ਇੱਕ ਹੁੰਦੀ ਹੈ (`src/shared/utils/circuitBreaker.ts` ਵੇਖੋ), ਅਤੇ ਲਗਾਤਾਰ ਅਸਫਲ ਹੋਣ ਵਾਲਾ ਪ੍ਰਦਾਤਾ `CLOSED → DEGRADED → OPEN` ਵਿੱਚ ਬਦਲ ਜਾਵੇਗਾ, ਇਸ ਤੋਂ ਪਹਿਲਾਂ ਕਿ ਰੀਸੈੱਟ ਵਿੰਡੋ ਇੱਕ ਜਾਂਚ ਨੂੰ ਲੰਘਣ ਦੇਵੇ (`HALF_OPEN`)।

**ਜੇ ਤੁਹਾਨੂੰ ਹਾਲੇ ਵੀ 429 ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ**: ਉਸ ਪ੍ਰਦਾਤਾ ਲਈ ਸਰਗਰਮ ਖਾਤੇ ਦਾ _ਕੋਟਾ_ ਵਾਸਤਵ ਵਿੱਚ ਖ਼ਤਮ ਹੋ ਗਿਆ ਹੈ (ਸਿਰਫ਼ ਰੇਟ ਨਹੀਂ)। OmniRoute ਡੈਸ਼ਬੋਰਡ → Providers → Accounts ਵਿੱਚ ਉਸੇ ਪ੍ਰਦਾਤਾ ਲਈ ਦੂਜਾ ਖਾਤਾ ਸ਼ਾਮਲ ਕਰੋ, ਜਾਂ ਕੋਈ ਹੋਰ ਮੁਫ਼ਤ ਪ੍ਰਦਾਤਾ (ਉਦਾਹਰਨ ਲਈ `routeway`, `auggie`) ਵੀ ਸ਼ਾਮਲ ਕਰੋ। ਰੋਟੇਸ਼ਨ ਸਿਰਫ਼ ਅਸਥਾਈ ਰੇਟ/400/401 ਸਮੱਸਿਆਵਾਂ ਵਿੱਚ ਮਦਦ ਕਰਦੀ ਹੈ; ਕੋਟੇ ਦੇ ਪੂਰੀ ਤਰ੍ਹਾਂ ਖ਼ਤਮ ਹੋਣ ਦੀ ਸਥਿਤੀ ਵਿੱਚ ਦੂਜੇ ਕ੍ਰੈਡੈਂਸ਼ੀਅਲ ਜਾਂ ਕਿਸੇ ਵੱਖਰੇ ਪ੍ਰਦਾਤਾ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।

**ਜੇ ਤੁਹਾਨੂੰ ਵਿਜ਼ਨ ਮਾਡਲਾਂ (`auto/vision`, `bazaarlink/*`) 'ਤੇ 403 ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ**: ਕਨੈਕਟ ਕੀਤੇ ਖਾਤੇ ਕੋਲ ਵਿਜ਼ਨ ਸ਼ਾਮਲ ਕਰਨ ਵਾਲੀ ਭੁਗਤਾਨਸ਼ੁਦਾ ਯੋਜਨਾ ਨਹੀਂ ਹੈ, ਜਾਂ API ਕੁੰਜੀ ਕੋਲ ਲੋੜੀਂਦੀਆਂ ਇਜਾਜ਼ਤਾਂ ਨਹੀਂ ਹਨ। ਪ੍ਰਦਾਤਾ ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਕੁੰਜੀ ਦੇ ਸਕੋਪ ਵਿੱਚ ਵਿਜ਼ਨ/ਮਲਟੀਮੋਡਲ ਸ਼ਾਮਲ ਹੈ, ਜਾਂ ਭੁਗਤਾਨਸ਼ੁਦਾ ਟੀਅਰ ਵਾਲਾ ਖਾਤਾ ਕਨੈਕਟ ਕਰੋ ਅਤੇ ਉਸਨੂੰ ਵਿਜ਼ਨ ਟਾਰਗੇਟ ਵਜੋਂ ਰੱਖੋ।

## npm install ਚੇਤਾਵਨੀਆਂ (ERESOLVE / peer / deprecated)

ਜਦੋਂ ਤੁਸੀਂ `npm install -g omniroute` ਚਲਾਉਂਦੇ ਹੋ, ਤਾਂ ਤੁਹਾਨੂੰ `npm warn ERESOLVE`, peer-dependency ਸੂਚਨਾਵਾਂ ਅਤੇ `deprecated` ਸੁਨੇਹਿਆਂ ਵਰਗੀਆਂ ਬਹੁਤ ਸਾਰੀਆਂ ਚੇਤਾਵਨੀਆਂ ਦਿਖਾਈ ਦੇ ਸਕਦੀਆਂ ਹਨ। **ਇਹ ਉਮੀਦ ਅਨੁਸਾਰ ਅਤੇ ਨੁਕਸਾਨ-ਰਹਿਤ ਹਨ।** ਜੇ ਆਉਟਪੁੱਟ ਵਿੱਚ `added <N> packages` ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ, ਤਾਂ ਤੁਹਾਡੀ ਇੰਸਟਾਲੇਸ਼ਨ ਸਫਲ ਰਹੀ ਹੈ।

peer-dependency ਹੱਲ ਸੰਬੰਧੀ ਚੇਤਾਵਨੀਆਂ ਨੂੰ ਦਬਾਉਣ ਲਈ, OmniRoute ਦਾ ਸਮਰਥਿਤ ਇੰਸਟਾਲੇਸ਼ਨ ਰੂਪ ਵਰਤੋ:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` ਸਿਰਫ਼ `ERESOLVE` ਅਤੇ peer-dependency ਸੂਚਨਾਵਾਂ ਨੂੰ ਦਬਾਉਂਦਾ ਹੈ। ਬਰਤਰਫ਼ੀ ਸੂਚਨਾਵਾਂ ਦਿਖਾਈ ਦਿੰਦੀਆਂ ਰਹਿੰਦੀਆਂ ਹਨ ਕਿਉਂਕਿ ਉਹ ਅਸਿੱਧੇ ਤੀਜੀ-ਧਿਰ ਪੈਕੇਜਾਂ ਤੋਂ ਆਉਂਦੀਆਂ ਹਨ; ਉਹ ਇਹ ਸੰਕੇਤ ਨਹੀਂ ਦਿੰਦੀਆਂ ਕਿ ਇੰਸਟਾਲੇਸ਼ਨ ਅਸਫਲ ਰਹੀ ਹੈ।

ਇਹ ਚੇਤਾਵਨੀਆਂ ਤੀਜੀ-ਧਿਰ ਪੈਕੇਜਾਂ ਵਿੱਚ ਪੁਰਾਣੀਆਂ peer-dependency ਰੇਂਜਾਂ ਕਾਰਨ ਆਉਂਦੀਆਂ ਹਨ, ਜਿਨ੍ਹਾਂ ਨੂੰ OmniRoute ਨਿਯੰਤਰਿਤ ਨਹੀਂ ਕਰਦਾ:

1. **`marked-terminal` ਨੂੰ `marked >=1 <16` ਚਾਹੀਦਾ ਹੈ, ਪਰ `marked@18` ਮਿਲਿਆ** — ਵਿਹਾਰਕ ਤੌਰ 'ਤੇ ਇਹ ਬਿਲਕੁਲ ਠੀਕ ਕੰਮ ਕਰਦਾ ਹੈ; upstream peer ਰੇਂਜ ਸਿਰਫ਼ ਪੁਰਾਣੀ ਹੈ।
2. **`deprecated prebuild-install@7.1.3`** — ਇੱਕ ਅਸਿੱਧਾ ਮੂਲ-ਬਾਇਨਰੀ ਪ੍ਰਾਪਤੀ ਸਹਾਇਕ। ਇਸਦੀ ਵਰਤੋਂ
   ਪਿੰਨ ਕੀਤੀ `wreq-js` ਟ੍ਰਾਂਸਪੋਰਟ ਬਾਈਂਡਿੰਗ ਨੂੰ ਇੰਸਟਾਲ ਕਰਨ ਲਈ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ ਅਤੇ ਇਹ ਇਸ ਗੱਲ ਦਾ ਸੰਕੇਤ ਨਹੀਂ ਦਿੰਦਾ ਕਿ web-cookie
   ਪ੍ਰਦਾਤਾ ਦੀ ਟ੍ਰਾਂਸਪੋਰਟ ਸੈਟਅੱਪ ਅਸਫਲ ਰਹੀ ਹੈ।

**ਕਿਸੇ ਕਾਰਵਾਈ ਦੀ ਲੋੜ ਨਹੀਂ** — upstream ਪੈਕੇਜਾਂ ਨੂੰ fork ਕੀਤੇ ਬਿਨਾਂ ਚੇਤਾਵਨੀਆਂ ਨੂੰ ਪੂਰੀ ਤਰ੍ਹਾਂ ਬੰਦ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ।

## Gemini Web ਅਤੇ Playwright Chromium

ਜੇ ਕੋਈ Gemini Web ਬੇਨਤੀ ਇਸ ਸੁਨੇਹੇ ਨਾਲ `503` ਵਾਪਸ ਕਰਦੀ ਹੈ ਕਿ Playwright Chromium
ਇੰਸਟਾਲ ਨਹੀਂ ਹੈ, ਤਾਂ npm ਪੈਕੇਜ ਮੌਜੂਦ ਹੈ ਪਰ ਬ੍ਰਾਊਜ਼ਰ ਬਾਇਨਰੀ ਗੁੰਮ ਹੈ।
Playwright ਜਾਣ-ਬੁੱਝ ਕੇ ਬ੍ਰਾਊਜ਼ਰ ਡਾਊਨਲੋਡਾਂ ਨੂੰ npm ਪੈਕੇਜ
ਇੰਸਟਾਲੇਸ਼ਨ ਤੋਂ ਵੱਖ ਰੱਖਦਾ ਹੈ, ਇਸ ਲਈ ਬ੍ਰਾਊਜ਼ਰ ਇੰਸਟਾਲ ਹੋਣ ਤੱਕ ਇਹ ਜਵਾਬ ਉਮੀਦ ਅਨੁਸਾਰ ਹੈ।

ਗਲੋਬਲ npm ਇੰਸਟਾਲੇਸ਼ਨ ਲਈ, OmniRoute ਪੈਕੇਜ ਦੀ
ਡਾਇਰੈਕਟਰੀ ਤੋਂ Chromium ਇੰਸਟਾਲ ਕਰੋ, ਤਾਂ ਜੋ ਬ੍ਰਾਊਜ਼ਰ ਕੈਸ਼ ਉਸੇ Playwright ਇੰਸਟਾਲੇਸ਼ਨ ਨਾਲ ਸੰਬੰਧਿਤ ਹੋਵੇ:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ਇੰਸਟਾਲੇਸ਼ਨ ਤੋਂ ਬਾਅਦ OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ, ਫਿਰ Gemini Web ਬੇਨਤੀ ਦੁਬਾਰਾ ਅਜ਼ਮਾਓ। ਜੇ ਤੁਸੀਂ
Docker ਇਮੇਜ ਤੋਂ OmniRoute ਚਲਾਉਂਦੇ ਹੋ, ਤਾਂ `-web` ਇਮੇਜ (ਜਾਂ `runner-web`
ਬਿਲਡ ਟਾਰਗੇਟ) ਵਰਤੋ, ਜਿਸ ਵਿੱਚ Chromium ਅਤੇ ਇਸ ਦੀਆਂ ਨਿਰਭਰਤਾਵਾਂ ਸ਼ਾਮਲ ਹਨ; ਬੇਸ ਇਮੇਜ ਵਿੱਚ
ਇਹ ਸ਼ਾਮਲ ਨਹੀਂ ਹਨ।

## ਐਂਟੀਵਾਇਰਸ ਦੀਆਂ ਗਲਤ ਸਕਾਰਾਤਮਕ ਪਛਾਣਾਂ

<a name="antivirus-false-positives"></a>

### Avast/AVG ਵੱਲੋਂ `README.md` ਨੂੰ `MD:HttpRequest-inf[Susp]` ਦੇ ਤੌਰ 'ਤੇ ਕਵਾਰੰਟੀਨ ਕਰਨਾ

**ਇਹ ਇੱਕ ਗਲਤ ਸਕਾਰਾਤਮਕ ਪਛਾਣ ਹੈ। ਕੁਝ ਵੀ ਸੰਕਰਮਿਤ ਨਹੀਂ ਹੈ ਅਤੇ ਕਿਸੇ ਕਾਰਵਾਈ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ।**

Avast ਅਤੇ AVG ਇੱਕ ਅਨੁਮਾਨ-ਆਧਾਰਿਤ ਜਾਂਚ ਚਲਾਉਂਦੇ ਹਨ ਜੋ ਬਹੁਤ ਸਾਰੇ
HTTP-ਬੇਨਤੀ ਵਰਗੇ ਦਿਸਣ ਵਾਲੇ ਲਿੰਕਾਂ ਵਾਲੀਆਂ ਸਧਾਰਨ-ਟੈਕਸਟ/Markdown ਫ਼ਾਈਲਾਂ ਨੂੰ ਚਿੰਨ੍ਹਿਤ ਕਰਦੀ ਹੈ।
OmniRoute ਦੀ `README.md` npm ਪੈਕੇਜ ਦੇ ਅੰਦਰ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ (ਇਹ
`package.json` → `files` ਵਿੱਚ ਸੂਚੀਬੱਧ ਹੈ), ਇਸ ਲਈ ਗਲੋਬਲ ਇੰਸਟਾਲ ਕਰਨ 'ਤੇ ਇਹ
`node_modules/omniroute/README.md` ਵਿੱਚ ਪਹੁੰਚਦੀ ਹੈ — ਅਤੇ ਇਸ ਵਿੱਚ ਲਗਭਗ 15
`http://localhost:20128/...` ਉਦਾਹਰਨਾਂ ਹਨ (MCP HTTP/SSE ਐਂਡਪੌਇੰਟ, A2A `.well-known`
URL ਅਤੇ `curl` ਸਨਿੱਪਟ)। ਲਿੰਕਾਂ ਦੀ ਇਹ ਘਣਤਾ ਅਨੁਮਾਨ-ਆਧਾਰਿਤ ਜਾਂਚ ਨੂੰ ਸਰਗਰਮ ਕਰਨ ਲਈ ਕਾਫ਼ੀ ਹੈ।

ਜੇ ਇਹ ਸਿਰਫ਼ ਹਾਲ ਹੀ ਵਿੱਚ ਸ਼ੁਰੂ ਹੋਇਆ ਹੈ: ਫ਼ਾਈਲ ਦੀ ਕਿਸਮ ਨਹੀਂ ਬਦਲੀ। README ਦੀ
ਐਂਡਪੌਇੰਟ ਸਾਰਣੀ ਵਧੀ ਹੈ (MCP HTTP + SSE + A2A ਸ਼ਾਮਲ ਕੀਤੇ ਗਏ ਸਨ) ਅਤੇ ਹੋਰ `curl`
ਉਦਾਹਰਨਾਂ ਜੋੜੀਆਂ ਗਈਆਂ, ਜਿਸ ਕਾਰਨ ਇਹ ਸੀਮਾ ਤੋਂ ਪਾਰ ਹੋ ਗਈ।

ਇਹ ਫ਼ਾਈਲ ਨਿਸ਼ਕਿਰਿਆ ਦਸਤਾਵੇਜ਼ ਹੈ, ਜਿਸ ਵਿੱਚ ਕੋਈ ਵੀ ਚੱਲਣਯੋਗ ਸਮੱਗਰੀ ਨਹੀਂ ਹੈ। ਤੁਸੀਂ ਇਸ ਨੂੰ
ਕਵਾਰੰਟੀਨ ਤੋਂ ਸੁਰੱਖਿਅਤ ਢੰਗ ਨਾਲ ਮੁੜ-ਬਹਾਲ ਕਰ ਸਕਦੇ ਹੋ।

**ਕੀ ਕਰਨਾ ਹੈ:**

1. **ਸੂਚਨਾਵਾਂ ਰੋਕੋ** — ਆਪਣੇ ਐਂਟੀਵਾਇਰਸ ਵਿੱਚ ਇੰਸਟਾਲ ਡਾਇਰੈਕਟਰੀ ਨੂੰ ਜਾਂਚ ਤੋਂ ਬਾਹਰ ਰੱਖੋ
   (Avast: Settings → Exceptions), ਅਤੇ ਆਪਣਾ ਗਲੋਬਲ `node_modules` ਪਾਥ ਅਤੇ/ਜਾਂ
   OmniRoute ਡਾਟਾ ਡਾਇਰੈਕਟਰੀ (`~/.omniroute/`) ਸ਼ਾਮਲ ਕਰੋ।
2. **ਗਲਤ ਸਕਾਰਾਤਮਕ ਪਛਾਣ ਦੀ ਰਿਪੋਰਟ ਕਰੋ** — <https://www.avast.com/false-positive-file-form.php>,
   ਅਤੇ ਕਵਾਰੰਟੀਨ ਕੀਤੀ `README.md` ਨੱਥੀ ਕਰੋ। ਇਹੀ ਉਹ ਸੁਧਾਰ ਹੈ ਜੋ ਹਰ ਕਿਸੇ ਦੀ ਮਦਦ ਕਰਦਾ ਹੈ,
   ਕਿਉਂਕਿ ਵਿਕਰੇਤਾ ਦੀ ਅਨੁਮਾਨ-ਆਧਾਰਿਤ ਜਾਂਚ ਇੱਕ ਟੈਕਸਟ ਫ਼ਾਈਲ 'ਤੇ ਹੱਦੋਂ ਵੱਧ ਪ੍ਰਤੀਕਿਰਿਆ ਕਰ ਰਹੀ ਹੈ।

**ਅਸੀਂ ਆਪਣੇ ਪਾਸੇ ਇਸ ਨੂੰ "ਠੀਕ" ਕਿਉਂ ਨਹੀਂ ਕਰਦੇ:** ਸਾਰੀਆਂ ਉਦਾਹਰਨਾਂ `http://localhost` ਹਨ,
ਅਤੇ ਸਵੈ-ਦਸਤਖ਼ਤਸ਼ੁਦਾ ਸਰਟੀਫਿਕੇਟ ਦੀ ਦਿੱਕਤ ਤੋਂ ਬਿਨਾਂ localhost ਨੂੰ `https` ਨਹੀਂ ਬਣਾਇਆ ਜਾ ਸਕਦਾ।
ਕਿਸੇ ਇੱਕ ਵਿਕਰੇਤਾ ਦੀ ਅਨੁਮਾਨ-ਆਧਾਰਿਤ ਜਾਂਚ ਤੋਂ ਬਚਣ ਲਈ ਦਸਤਾਵੇਜ਼ਾਂ ਨੂੰ ਵਿਗਾੜਨਾ, ਸਕੈਨਰ ਦੀ ਇੱਕ ਖ਼ਾਮੀ
ਨੂੰ ਸੰਤੁਸ਼ਟ ਕਰਨ ਵਾਸਤੇ ਹਰ ਪਾਠਕ ਨੂੰ ਨੁਕਸਾਨ ਪਹੁੰਚਾਏਗਾ।

### Kaspersky ਵੱਲੋਂ Desktop ਐਪ ਨੂੰ `PDM:Trojan.Win32.Generic` ਵਜੋਂ ਚਿੰਨ੍ਹਿਤ ਕਰਨਾ

**ਇਹ ਵਿਹਾਰ-ਆਧਾਰਿਤ ਅਨੁਮਾਨ ਕਾਰਨ ਹੋਈ ਗਲਤ ਸਕਾਰਾਤਮਕ ਪਛਾਣ ਹੈ। ਕੁਝ ਵੀ ਸੰਕਰਮਿਤ ਨਹੀਂ ਹੈ।**
Kaspersky ਦੇ `PDM:` ਅਗੇਤਰ ਦਾ ਮਤਲਬ ਹੈ ਕਿ ਫ਼ੈਸਲਾ ਇਸ ਦੇ Proactive Defense Module
(System Watcher) ਤੋਂ ਆਇਆ ਹੈ, ਜੋ ਜਾਣੇ-ਪਛਾਣੇ ਮਾਲਵੇਅਰ ਨਾਲ ਮੇਲ ਕਰਨ ਦੀ ਬਜਾਏ ਇਹ ਨਿਰਣਾ ਕਰਦਾ ਹੈ
ਕਿ ਇੰਸਟਾਲਰ _ਕੀ ਕਰਦਾ ਹੈ_। ਜਦੋਂ ਇਹ ਸਰਗਰਮ ਹੁੰਦਾ ਹੈ, Kaspersky ਪੂਰੀ ਇੰਸਟਾਲੇਸ਼ਨ ਨੂੰ
"ਵਾਪਸ ਮੋੜਦਾ" ਹੈ — ਪਹਿਲਾਂ ਹੀ ਲਿਖੀਆਂ ਫ਼ਾਈਲਾਂ ਨੂੰ ਮਿਟਾ ਦਿੰਦਾ ਹੈ — ਇਸ ਲਈ ਐਪ ਅੰਤ ਵਿੱਚ
ਖ਼ਰਾਬ ਜਾਂ ਗਾਇਬ ਹੋ ਜਾਂਦੀ ਹੈ।

ਇਸ ਵੱਲੋਂ ਚਿੰਨ੍ਹਿਤ ਕੀਤੀਆਂ ਫ਼ਾਈਲਾਂ Desktop ਐਪ ਨਾਲ ਬੰਡਲ ਕੀਤੀਆਂ, ਘੋਸ਼ਿਤ ਅਤੇ ਓਪਨ-ਸੋਰਸ
ਨਿਰਭਰਤਾਵਾਂ ਦੇ ਮਿਆਰੀ ਹਿੱਸੇ ਹਨ, ਉਦਾਹਰਨ ਲਈ:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ਅਤੇ
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ਬ੍ਰਾਊਜ਼ਰ ਆਟੋਮੇਸ਼ਨ
  ਲਾਇਬ੍ਰੇਰੀ, ਜੋ ਐਪ ਦੇ ਅੰਦਰ ਪ੍ਰਦਾਤਾ ਲੌਗਇਨ ਅਤੇ ਬ੍ਰਾਊਜ਼ਰ-ਸਮਰਥਿਤ ਚੈਟ ਲਈ ਵਰਤੀ ਜਾਂਦੀ ਹੈ।
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — ਵੈੱਬ-ਕੂਕੀ ਪ੍ਰਦਾਤਾਵਾਂ 'ਤੇ ਬ੍ਰਾਊਜ਼ਰ-ਫਿੰਗਰਪ੍ਰਿੰਟ ਵਾਲੇ HTTP ਲਈ ਵਰਤੀ ਜਾਣ ਵਾਲੀ ਨਿਰਧਾਰਤ
  `wreq-js` ਨੇਟਿਵ ਬਾਈਂਡਿੰਗ (`<arch>` ਜਾਂ ਤਾਂ `x64` ਹੈ ਜਾਂ `arm64`)।

**ਇਹ ਸਰਗਰਮ ਕਿਉਂ ਹੁੰਦਾ ਹੈ:** Windows ਇੰਸਟਾਲਰ ਹਾਲੇ **ਕੋਡ-ਸਾਈਨ ਨਹੀਂ ਕੀਤਾ ਗਿਆ**, ਇਸ ਲਈ
ਇੱਕ ਬਿਨਾਂ ਦਸਤਖ਼ਤ ਵਾਲੇ NSIS ਇੰਸਟਾਲਰ ਦੀ ਕੋਈ ਸਾਖ ਨਹੀਂ ਹੁੰਦੀ ਅਤੇ ਵਿਹਾਰ-ਆਧਾਰਿਤ ਜਾਂਚਾਂ ਸਭ ਤੋਂ
ਵੱਧ ਸਖ਼ਤੀ ਨਾਲ ਚਲਦੀਆਂ ਹਨ। ਬੰਡਲ ਕੀਤੀ ਨੇਟਿਵ DLL ਅਤੇ `%LOCALAPPDATA%\Programs\OmniRoute`
ਹੇਠ ਲਿਖੀਆਂ ਸੈਂਕੜੇ `.js` ਫ਼ਾਈਲਾਂ (Next.js ਸਟੈਂਡਅਲੋਨ ਬਿਲਡ ਤੋਂ ਹੈਸ਼-ਪਿਛੇਤਰ ਵਾਲੀਆਂ ਪੈਕੇਜ
ਡਾਇਰੈਕਟਰੀਆਂ ਸਮੇਤ) ਨਾਲ ਮਿਲ ਕੇ, ਇਹ ਅਨੁਮਾਨ-ਆਧਾਰਿਤ ਜਾਂਚ ਨੂੰ ਸਰਗਰਮ ਕਰਨ ਲਈ ਕਾਫ਼ੀ ਹੈ।
ਕੋਡ ਸਾਈਨਿੰਗ ਦੀ ਯੋਜਨਾ ਹੈ; ਇਸ ਦੇ ਲਾਗੂ ਹੋਣ ਤੱਕ ਨਵੀਆਂ ਰਿਲੀਜ਼ਾਂ ਵਿੱਚ ਇਹ ਮੁੜ ਹੋ ਸਕਦਾ ਹੈ।

**ਕੀ ਕਰਨਾ ਹੈ:**

1. **ਪਹਿਲਾਂ ਆਪਣੇ ਡਾਊਨਲੋਡ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ** (ਇਸ ਨਾਲ ਛੇੜਛਾੜ ਕੀਤੀ ਫ਼ਾਈਲ ਦੀ ਸੰਭਾਵਨਾ ਰੱਦ
   ਹੁੰਦੀ ਹੈ)। ਹਰ ਰਿਲੀਜ਼ `latest.yml` ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦੀ ਹੈ, ਜਿਸ ਦਾ `sha512` ਖੇਤਰ (base64)
   `OmniRoute.Setup.<version>.exe` ਇੰਸਟਾਲਰ ਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ। PowerShell ਵਿੱਚ, ਇੰਸਟਾਲਰ
   ਵਾਲੇ ਫੋਲਡਰ ਤੋਂ:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ਆਉਟਪੁੱਟ `latest.yml` → `sha512` ਨਾਲ ਮੇਲ ਖਾਣੀ ਚਾਹੀਦੀ ਹੈ। ਜੇ ਇਹ ਮੇਲ ਨਹੀਂ ਖਾਂਦੀ,
   ਤਾਂ ਫ਼ਾਈਲ ਮਿਟਾਓ ਅਤੇ ਕੇਵਲ [GitHub ਰਿਲੀਜ਼ ਪੰਨੇ](https://github.com/diegosouzapw/OmniRoute/releases)
   ਤੋਂ ਮੁੜ ਡਾਊਨਲੋਡ ਕਰੋ।
2. **ਮੁੜ-ਬਹਾਲ ਕਰੋ + ਜਾਂਚ ਤੋਂ ਬਾਹਰ ਰੱਖੋ** — ਵਾਪਸ ਮੋੜੀਆਂ ਆਈਟਮਾਂ ਨੂੰ ਕਵਾਰੰਟੀਨ ਤੋਂ
   ਮੁੜ-ਬਹਾਲ ਕਰੋ ਅਤੇ `%LOCALAPPDATA%\Programs\OmniRoute` ਲਈ ਇੱਕ ਛੋਟ ਸ਼ਾਮਲ ਕਰੋ
   (Kaspersky → Settings → Threats and Exclusions), ਫਿਰ ਮੁੜ ਇੰਸਟਾਲ ਕਰੋ।
3. **ਗਲਤ ਸਕਾਰਾਤਮਕ ਪਛਾਣ ਦੀ ਰਿਪੋਰਟ ਕਰੋ** — <https://opentip.kaspersky.com/>।
   ਉਪਭੋਗਤਾਵਾਂ ਵੱਲੋਂ ਭੇਜੀਆਂ FP ਰਿਪੋਰਟਾਂ ਵਾਸਤਵ ਵਿੱਚ ਮਨਜ਼ੂਰਸ਼ੁਦਾ ਸੂਚੀ ਵਿੱਚ ਸ਼ਾਮਲ ਕਰਨ ਦੀ
   ਪ੍ਰਕਿਰਿਆ ਨੂੰ ਤੇਜ਼ ਕਰਦੀਆਂ ਹਨ।

## Node.js ਅਨੁਕੂਲਤਾ

<a name="nodejs-compatibility"></a>

### ਲੌਗਇਨ ਪੰਨਾ ਕ੍ਰੈਸ਼ ਹੋ ਜਾਂਦਾ ਹੈ ਜਾਂ "Module self-registration" ਗਲਤੀ ਦਿਖਾਉਂਦਾ ਹੈ

**ਕਾਰਨ:** ਤੁਸੀਂ Node.js ਦਾ ਅਜਿਹਾ ਵਰਜਨ ਚਲਾ ਰਹੇ ਹੋ ਜੋ OmniRoute ਦੀ ਮਨਜ਼ੂਰਸ਼ੁਦਾ ਸੁਰੱਖਿਅਤ ਰਨਟਾਈਮ ਦੀ ਘੱਟੋ-ਘੱਟ ਸੀਮਾ ਤੋਂ ਬਾਹਰ ਹੈ। ਸਭ ਤੋਂ ਆਮ ਮਾਮਲਾ Node 22 ਜਾਂ 24 ਦਾ ਅਜਿਹਾ ਪੁਰਾਣਾ ਪੈਚ ਪੱਧਰ ਚਲਾਉਣਾ ਹੈ ਜੋ OmniRoute ਵੱਲੋਂ ਲੋੜੀਂਦੀ ਪੈਚ ਕੀਤੀ ਸੁਰੱਖਿਆ ਸੀਮਾ ਤੋਂ ਹੇਠਾਂ ਹੁੰਦਾ ਹੈ।

**ਲੱਛਣ:**

- ਲੌਗਇਨ ਪੰਨਾ ਖਾਲੀ ਸਕ੍ਰੀਨ ਜਾਂ ਸਰਵਰ ਗਲਤੀ ਦਿਖਾਉਂਦਾ ਹੈ
- ਕੰਸੋਲ `Error: Module did not self-register` ਜਾਂ ਇਸੇ ਤਰ੍ਹਾਂ ਦੀਆਂ ਨੇਟਿਵ ਬਾਈਂਡਿੰਗ ਗਲਤੀਆਂ ਦਿਖਾਉਂਦਾ ਹੈ
- ਜੇ ਰਨਟਾਈਮ ਸਮਰਥਿਤ ਸੁਰੱਖਿਅਤ ਨੀਤੀ ਤੋਂ ਬਾਹਰ ਹੈ, ਤਾਂ ਲੌਗਇਨ ਪੰਨਾ ਤੁਹਾਡੇ Node ਵਰਜਨ ਸਮੇਤ ਇੱਕ **ਸੰਤਰੀ ਚੇਤਾਵਨੀ ਬੈਨਰ** ਦਿਖਾਉਂਦਾ ਹੈ

**ਹੱਲ:**

1. ਕੋਈ ਸਮਰਥਿਤ Node.js LTS ਰਿਲੀਜ਼ ਇੰਸਟਾਲ ਕਰੋ (ਸਿਫ਼ਾਰਸ਼ੀ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ਆਪਣੇ ਵਰਜਨ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ: `node --version` ਨੂੰ 24.x LTS ਲਾਈਨ ਉੱਤੇ `v24.0.0` ਜਾਂ ਇਸ ਤੋਂ ਨਵਾਂ ਵਰਜਨ ਦਿਖਾਉਣਾ ਚਾਹੀਦਾ ਹੈ
3. OmniRoute ਨੂੰ ਮੁੜ ਇੰਸਟਾਲ ਕਰੋ: `npm install -g omniroute`
4. ਮੁੜ ਸ਼ੁਰੂ ਕਰੋ: `omniroute`

> **ਸਮਰਥਿਤ ਸੁਰੱਖਿਅਤ ਵਰਜਨ:** `>=22.22.2 <23` ਜਾਂ `>=24.0.0 <27`। Node.js 24.x LTS (Krypton) ਅਤੇ Node.js 26 ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਮਰਥਿਤ ਹਨ।

### npm v11+: `better-sqlite3` ਇੰਸਟਾਲ ਨਹੀਂ ਹੋਇਆ (ਮੋਡੀਊਲ ਨਹੀਂ ਲੱਭਿਆ ਜਾ ਸਕਿਆ)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**ਕਾਰਨ:** npm v11 (ਜੋ Node.js 24+ ਨਾਲ ਮਿਲਦਾ ਹੈ) ਮੂਲ ਰੂਪ ਵਿੱਚ ਵਿਕਲਪਿਕ
ਡਿਪੈਂਡੈਂਸੀਆਂ ਲਈ ਇੰਸਟਾਲ ਸਕ੍ਰਿਪਟਾਂ ਨੂੰ ਬਲੌਕ ਕਰਦਾ ਹੈ। ਕਿਉਂਕਿ `better-sqlite3` ਨੂੰ `optionalDependencies`
ਵਿੱਚ ਸੂਚੀਬੱਧ ਕੀਤਾ ਗਿਆ ਹੈ ਅਤੇ ਇਸ ਲਈ ਨੇਟਿਵ ਕੰਪਾਇਲੇਸ਼ਨ (`node-gyp rebuild`) ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ, npm ਚੁੱਪਚਾਪ ਇਸਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ।

**ਲੱਛਣ:**

- ਸਰਵਰ ਸਟਾਰਟਅੱਪ ਸਮੇਂ `Cannot find module 'better-sqlite3'` ਨਾਲ ਕ੍ਰੈਸ਼ ਹੋ ਜਾਂਦਾ ਹੈ
- `ls node_modules/better-sqlite3` "No such file or directory" ਦਿਖਾਉਂਦਾ ਹੈ
- `npm ls better-sqlite3` `(empty)` ਦਿਖਾਉਂਦਾ ਹੈ

**ਹੱਲ:**

1. ਇੰਸਟਾਲ ਸਕ੍ਰਿਪਟਾਂ ਨੂੰ ਮਨਜ਼ੂਰੀ ਦਿਓ ਅਤੇ ਮੁੜ ਇੰਸਟਾਲ ਕਰੋ:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ਜਾਂ ਪਹਿਲਾਂ ਤੋਂ ਬਿਲਡ ਕੀਤਾ ਪੈਕੇਜ ਹੱਥੀਂ ਇੰਸਟਾਲ ਕਰੋ:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਇਹ ਕੰਮ ਕਰਦਾ ਹੈ: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**ਕਾਰਨ:** ਗਲੋਬਲ `npm install -g omniroute` ਤੋਂ ਬਾਅਦ, ਪੈਕੇਜ ਦੇ ਅੰਦਰ ਮੌਜੂਦ `better-sqlite3` ਨੇਟਿਵ ਬਾਇਨਰੀ ਨੂੰ ਸਥਾਨਕ ਤੌਰ 'ਤੇ ਚੱਲ ਰਹੇ ਆਰਕੀਟੈਕਚਰ ਜਾਂ Node.js ABI ਤੋਂ ਵੱਖਰੇ ਆਰਕੀਟੈਕਚਰ ਜਾਂ ABI ਲਈ ਕੰਪਾਇਲ ਕੀਤਾ ਗਿਆ ਹੋ ਸਕਦਾ ਹੈ। ਇਹ macOS (Apple Silicon ਅਤੇ Intel ਦੋਵਾਂ) ਉੱਤੇ ਆਮ ਹੈ, ਜਦੋਂ ਪਹਿਲਾਂ ਤੋਂ ਬਿਲਡ ਕੀਤੀ ਬਾਇਨਰੀ ਤੁਹਾਡੇ ਵਾਤਾਵਰਣ ਨਾਲ ਮੇਲ ਨਹੀਂ ਖਾਂਦੀ।

**ਲੱਛਣ:**

- ਸਰਵਰ ਸਟਾਰਟਅੱਪ ਸਮੇਂ ਤੁਰੰਤ `dlopen` ਗਲਤੀ ਨਾਲ ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ
- ਗਲਤੀ ਵਿੱਚ `slice is not valid mach-o file` ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ
- ਪੂਰੀ ਉਦਾਹਰਨ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ਹੱਲ — ਆਪਣੇ ਸਥਾਨਕ ਵਾਤਾਵਰਣ ਲਈ ਮੁੜ ਬਿਲਡ ਕਰੋ (Node.js ਨੂੰ ਡਾਊਨਗ੍ਰੇਡ ਕਰਨ ਦੀ ਲੋੜ ਨਹੀਂ):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ਨੋਟ:** ਇਹ ਨੇਟਿਵ ਬਾਈਂਡਿੰਗ ਨੂੰ ਤੁਹਾਡੇ ਸਥਾਨਕ Node.js ਵਰਜਨ ਅਤੇ CPU ਆਰਕੀਟੈਕਚਰ ਦੇ ਅਨੁਸਾਰ ਮੁੜ ਕੰਪਾਇਲ ਕਰਦਾ ਹੈ, ਜਿਸ ਨਾਲ ਬਾਇਨਰੀ ਦਾ ਬੇਮੇਲ ਹੱਲ ਹੋ ਜਾਂਦਾ ਹੈ। ਅਧਿਕਾਰਤ ਤੌਰ 'ਤੇ ਸਮਰਥਿਤ ਰਨਟਾਈਮ ਰੇਂਜ **`>=22.22.2 <23` ਜਾਂ `>=24.0.0 <27`** ਹੈ (`src/shared/utils/nodeRuntimeSupport.ts` ਵਿੱਚ `SUPPORTED_NODE_RANGE`, ਜੋ `package.json` ਦੇ `engines` ਫ਼ੀਲਡ ਨਾਲ ਇਕਸਾਰ ਹੈ)। Node.js 24.x LTS (Krypton) ਅਤੇ Node.js 26, `better-sqlite3` v12.x ਨਾਲ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਮਰਥਿਤ ਹਨ।

## ਪ੍ਰਾਕਸੀ ਸੰਬੰਧੀ ਸਮੱਸਿਆਵਾਂ

<a name="proxy-issues"></a>

### ਪ੍ਰੋਵਾਈਡਰ ਪ੍ਰਮਾਣਿਕਤਾ ਵਿੱਚ "fetch failed" ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ

**ਕਾਰਨ:** API ਕੁੰਜੀ ਪ੍ਰਮਾਣਿਕਤਾ ਐਂਡਪੌਇੰਟ (`POST /api/providers/validate`) ਪਹਿਲਾਂ ਪ੍ਰਾਕਸੀ ਸੰਰਚਨਾ ਨੂੰ ਬਾਈਪਾਸ ਕਰ ਰਿਹਾ ਸੀ, ਜਿਸ ਕਾਰਨ ਪ੍ਰਾਕਸੀ ਰਾਊਟਿੰਗ ਦੀ ਲੋੜ ਵਾਲੇ ਵਾਤਾਵਰਣਾਂ ਵਿੱਚ ਅਸਫਲਤਾਵਾਂ ਆ ਰਹੀਆਂ ਸਨ।

**ਹੱਲ (v3.5.5+):** ਹੁਣ ਇਹ ਠੀਕ ਕਰ ਦਿੱਤਾ ਗਿਆ ਹੈ। ਪ੍ਰੋਵਾਈਡਰ ਪ੍ਰਮਾਣਿਕਤਾ `runWithProxyContext` ਰਾਹੀਂ ਰਾਊਟ ਹੁੰਦੀ ਹੈ ਅਤੇ ਪ੍ਰੋਵਾਈਡਰ-ਪੱਧਰੀ ਅਤੇ ਗਲੋਬਲ ਪ੍ਰਾਕਸੀ ਸੈਟਿੰਗਾਂ ਦੀ ਆਪਣੇ ਆਪ ਪਾਲਣਾ ਕਰਦੀ ਹੈ।

### ਟੋਕਨ ਸਿਹਤ ਜਾਂਚ "fetch failed" ਨਾਲ ਅਸਫਲ ਹੁੰਦੀ ਹੈ

**ਕਾਰਨ:** ਬੈਕਗ੍ਰਾਊਂਡ OAuth ਟੋਕਨ ਰਿਫ੍ਰੈਸ਼ ਹਰੇਕ ਕਨੈਕਸ਼ਨ ਲਈ ਪ੍ਰਾਕਸੀ ਸੰਰਚਨਾ ਨੂੰ ਰਿਜ਼ਾਲਵ ਨਹੀਂ ਕਰ ਰਿਹਾ ਸੀ।

**ਹੱਲ (v3.5.5+):** ਟੋਕਨ ਸਿਹਤ ਜਾਂਚ ਸ਼ਡਿਊਲਰ ਹੁਣ ਰਿਫ੍ਰੈਸ਼ ਦੀ ਕੋਸ਼ਿਸ਼ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਹਰੇਕ ਕਨੈਕਸ਼ਨ ਲਈ ਪ੍ਰਾਕਸੀ ਸੰਰਚਨਾ ਨੂੰ ਰਿਜ਼ਾਲਵ ਕਰਦਾ ਹੈ। v3.5.5+ 'ਤੇ ਅੱਪਡੇਟ ਕਰੋ।

### SOCKS5 ਪ੍ਰਾਕਸੀ "invalid onRequestStart method" ਵਾਪਸ ਕਰਦੀ ਹੈ

**ਕਾਰਨ:** Node.js 22 ਉੱਤੇ, undici@8 ਡਿਸਪੈਚਰ Node ਦੇ ਬਿਲਟ-ਇਨ `fetch()` ਇੰਪਲੀਮੈਂਟੇਸ਼ਨ ਨਾਲ ਅਨੁਕੂਲ ਨਹੀਂ ਹੈ।

**ਹੱਲ (v3.5.5+):** ਜਦੋਂ ਕੋਈ ਪ੍ਰਾਕਸੀ ਡਿਸਪੈਚਰ ਸਰਗਰਮ ਹੁੰਦਾ ਹੈ, ਤਾਂ OmniRoute ਹੁਣ ਇਕਸਾਰ ਵਿਹਾਰ ਯਕੀਨੀ ਬਣਾਉਣ ਲਈ undici ਦੇ ਆਪਣੇ `fetch()` ਫੰਕਸ਼ਨ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। v3.5.5+ 'ਤੇ ਅੱਪਡੇਟ ਕਰੋ।

### WSL ਅਧੀਨ MITM ਪ੍ਰਾਕਸੀ: Windows ਹੋਸਟ ਉੱਤੇ ਡੈਸਕਟਾਪ ਐਪਾਂ ਇੰਟਰਸੈਪਟ ਨਹੀਂ ਹੁੰਦੀਆਂ

**ਕਾਰਨ:** MITM ਪ੍ਰਾਕਸੀ ਅਤੇ ਇਸਦਾ CA ਸਰਟੀਫਿਕੇਟ ਉਸ ਵਾਤਾਵਰਣ ਵਿੱਚ ਇੰਸਟਾਲ ਹੁੰਦੇ ਹਨ ਜਿੱਥੇ OmniRoute ਚੱਲਦਾ ਹੈ। WSL ਅਧੀਨ ਉਹ ਵਾਤਾਵਰਣ Linux ਗੈਸਟ ਹੁੰਦਾ ਹੈ, ਜਦਕਿ AI ਡੈਸਕਟਾਪ ਐਪਾਂ (Kiro, Trae, Copilot, Zed, …) Windows ਹੋਸਟ ਉੱਤੇ ਚੱਲਦੀਆਂ ਹਨ। ਹੋਸਟ ਐਪਾਂ ਗੈਸਟ ਦੇ ਸਰਟੀਫਿਕੇਟ ਸਟੋਰ 'ਤੇ ਭਰੋਸਾ ਨਹੀਂ ਕਰਦੀਆਂ ਅਤੇ ਗੈਸਟ ਦੇ ਸਿਸਟਮ ਪ੍ਰਾਕਸੀ ਰਾਹੀਂ ਰਾਊਟ ਨਹੀਂ ਹੁੰਦੀਆਂ, ਇਸ ਲਈ ਉੱਥੇ ਡੈਸਕਟਾਪ ਇੰਟਰਸੈਪਸ਼ਨ ਸਰਗਰਮ ਨਹੀਂ ਹੁੰਦੀ।

**ਸਿਫ਼ਾਰਸ਼:** OmniRoute ਨੂੰ ਉਸੇ OS ਉੱਤੇ ਨੇਟਿਵ ਤੌਰ 'ਤੇ ਚਲਾਓ ਜਿਸ ਉੱਤੇ ਉਹ ਡੈਸਕਟਾਪ ਐਪਾਂ ਚੱਲਦੀਆਂ ਹਨ ਜਿਨ੍ਹਾਂ ਨੂੰ ਤੁਸੀਂ ਇੰਟਰਸੈਪਟ ਕਰਨਾ ਚਾਹੁੰਦੇ ਹੋ (Windows ਐਪਾਂ ਲਈ Windows; ਇਸੇ ਤਰ੍ਹਾਂ macOS/Linux ਲਈ ਵੀ)। ਹੋਸਟ ਐਪਾਂ ਨੂੰ ਨਿਸ਼ਾਨਾ ਬਣਾਉਂਦੇ ਹੋਏ OmniRoute ਨੂੰ WSL ਦੇ ਅੰਦਰ ਰੱਖਣ ਲਈ, ਬਣਾਏ ਗਏ CA ਸਰਟੀਫਿਕੇਟ ਨੂੰ Windows ਹੋਸਟ ਉੱਤੇ ਹੱਥੀਂ ਭਰੋਸੇਯੋਗ ਬਣਾਉਣਾ ਅਤੇ ਹਰੇਕ ਹੋਸਟ ਐਪ ਦੀ ਨੈੱਟਵਰਕ/ਪ੍ਰਾਕਸੀ ਸੈਟਿੰਗ ਨੂੰ WSL ਪ੍ਰਾਕਸੀ ਐਂਡਪੌਇੰਟ ਵੱਲ ਸੈੱਟ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ — ਇਹ ਇੱਕ ਅਸਮਰਥਿਤ ਅਤੇ ਨਾਜ਼ੁਕ ਸੈਟਅੱਪ ਹੈ।

## ਕਲਾਉਡ ਸਮੱਸਿਆਵਾਂ

### ਕਲਾਉਡ ਸਿੰਕ ਤਰੁੱਟੀਆਂ

1. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `BASE_URL` ਤੁਹਾਡੇ ਚੱਲ ਰਹੇ ਇੰਸਟੈਂਸ ਵੱਲ ਸੰਕੇਤ ਕਰਦਾ ਹੈ (ਉਦਾਹਰਨ ਲਈ, `http://localhost:20128`)
2. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `CLOUD_URL` ਤੁਹਾਡੇ ਕਲਾਉਡ ਐਂਡਪੌਇੰਟ ਵੱਲ ਸੰਕੇਤ ਕਰਦਾ ਹੈ (ਉਦਾਹਰਨ ਲਈ, `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` ਮੁੱਲਾਂ ਨੂੰ ਸਰਵਰ-ਸਾਈਡ ਮੁੱਲਾਂ ਨਾਲ ਇਕਸਾਰ ਰੱਖੋ

### ਕਲਾਉਡ `stream=false` 500 ਵਾਪਸ ਕਰਦਾ ਹੈ

**ਲੱਛਣ:** ਗੈਰ-ਸਟ੍ਰੀਮਿੰਗ ਕਾਲਾਂ ਲਈ ਕਲਾਉਡ ਐਂਡਪੌਇੰਟ ਉੱਤੇ `Unexpected token 'd'...`।

**ਕਾਰਨ:** ਅੱਪਸਟ੍ਰੀਮ SSE ਪੇਲੋਡ ਵਾਪਸ ਕਰਦਾ ਹੈ, ਜਦਕਿ ਕਲਾਇੰਟ JSON ਦੀ ਉਮੀਦ ਕਰਦਾ ਹੈ।

**ਅਸਥਾਈ ਹੱਲ:** ਕਲਾਉਡ ਨੂੰ ਸਿੱਧੀਆਂ ਕਾਲਾਂ ਲਈ `stream=true` ਵਰਤੋ। ਲੋਕਲ ਰਨਟਾਈਮ ਵਿੱਚ SSE→JSON ਫਾਲਬੈਕ ਸ਼ਾਮਲ ਹੈ।

### ਕਲਾਉਡ ਕਨੈਕਟਿਡ ਦਿਖਾਉਂਦਾ ਹੈ ਪਰ "Invalid API key"

1. ਲੋਕਲ ਡੈਸ਼ਬੋਰਡ (`/api/keys`) ਤੋਂ ਇੱਕ ਨਵੀਂ ਕੁੰਜੀ ਬਣਾਓ
2. ਕਲਾਉਡ ਸਿੰਕ ਚਲਾਓ: ਕਲਾਉਡ ਸਮਰੱਥ ਕਰੋ → ਹੁਣੇ ਸਿੰਕ ਕਰੋ
3. ਪੁਰਾਣੀਆਂ/ਗੈਰ-ਸਿੰਕ ਕੀਤੀਆਂ ਕੁੰਜੀਆਂ ਹਾਲੇ ਵੀ ਕਲਾਉਡ ਉੱਤੇ `401` ਵਾਪਸ ਕਰ ਸਕਦੀਆਂ ਹਨ

## Docker ਸਮੱਸਿਆਵਾਂ

### Docker IPv6 / ਕਨੈਕਸ਼ਨ ਰੀਸੈੱਟ

<a name="docker-ipv6"></a>

**ਲੱਛਣ:** `curl http://localhost:20128/v1/models` ਚਲਾਉਣ ਉੱਤੇ `curl: (56) Recv failure: Connection reset by peer` ਵਾਪਸ ਆਉਂਦਾ ਹੈ। ਡੈਸ਼ਬੋਰਡ ਅਤੇ ਬਿਨਾਂ ਪ੍ਰਮਾਣੀਕਰਨ ਵਾਲੇ ਐਂਡਪੌਇੰਟ ਕੰਮ ਕਰਦੇ ਹਨ, ਪਰ ਪ੍ਰਮਾਣੀਕ੍ਰਿਤ ਐਂਡਪੌਇੰਟ ਅਸਫਲ ਹੋ ਜਾਂਦੇ ਹਨ — ਇਹ ਪ੍ਰਮਾਣੀਕਰਨ ਸਮੱਸਿਆ ਵਰਗਾ ਲੱਗਦਾ ਹੈ, ਪਰ ਅਸਲ ਵਿੱਚ ਨਹੀਂ ਹੈ।

**ਕਾਰਨ:** `docker run -p 20128:20128`, `0.0.0.0` (IPv4) ਅਤੇ `::` (IPv6) ਦੋਵਾਂ ਉੱਤੇ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ, ਪਰ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰਲੀ ਪ੍ਰਕਿਰਿਆ ਸਿਰਫ਼ IPv4 ਉੱਤੇ ਸੁਣਦੀ ਹੈ। ਜਿਨ੍ਹਾਂ ਹੋਸਟਾਂ ਉੱਤੇ `localhost` ਪਹਿਲਾਂ `::1` ਵਿੱਚ ਰਿਜ਼ਾਲਵ ਹੁੰਦਾ ਹੈ, ਉੱਥੇ ਕਨੈਕਸ਼ਨ IPv6 ਦੇ ਪ੍ਰਕਾਸ਼ਿਤ ਪੋਰਟ ਉੱਤੇ ਪਹੁੰਚਦਾ ਹੈ, ਜਿਸਦੇ ਪਿੱਛੇ ਕੋਈ ਲਿਸਨਰ ਨਹੀਂ ਹੁੰਦਾ → ਕਨੈਕਸ਼ਨ ਰੀਸੈੱਟ।

**ਹੱਲ:**

1. **ਤੁਰੰਤ ਜਾਂਚ:** `curl -4 http://localhost:20128/v1/models` ਚਲਾਓ। ਜੇ ਇਹ `-4` ਨਾਲ ਕੰਮ ਕਰਦਾ ਹੈ ਪਰ ਇਸ ਤੋਂ ਬਿਨਾਂ ਅਸਫਲ ਹੁੰਦਾ ਹੈ, ਤਾਂ ਤੁਹਾਡੇ ਕੋਲ IPv6 ਬਾਈਂਡ ਅਸੰਗਤਤਾ ਹੈ।
2. **ਸਥਾਈ ਹੱਲ:** ਆਪਣੀ `docker run` ਕਮਾਂਡ ਵਿੱਚ `-p 127.0.0.1:20128:20128` ਵਰਤ ਕੇ ਸਪਸ਼ਟ ਤੌਰ ਉੱਤੇ IPv4 ਨਾਲ ਬਾਈਂਡ ਕਰੋ:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ਇਹ IPv4 ਬਾਈਂਡ ਨੂੰ ਲਾਜ਼ਮੀ ਬਣਾਉਂਦਾ ਹੈ ਅਤੇ ਸਾਰੇ ਹੋਸਟ ਇੰਟਰਫੇਸਾਂ ਉੱਤੇ ਪ੍ਰੌਕਸੀ ਨੂੰ ਉਪਲਬਧ ਕਰਨ ਤੋਂ ਵੀ ਬਚਾਉਂਦਾ ਹੈ।

### ਲੌਗ ਫਾਈਲਾਂ ਸਮਰੱਥ ਕਰੋ

ਆਪਣੀ `.env` ਫਾਈਲ ਵਿੱਚ `APP_LOG_TO_FILE=true` ਸੈੱਟ ਕਰੋ। ਐਪਲੀਕੇਸ਼ਨ ਲੌਗ `logs/` ਦੇ ਅਧੀਨ ਲਿਖੇ ਜਾਂਦੇ ਹਨ।
ਜਦੋਂ ਸੈਟਿੰਗਾਂ ਵਿੱਚ ਕਾਲ ਲੌਗ ਪਾਈਪਲਾਈਨ ਸਮਰੱਥ ਹੁੰਦੀ ਹੈ, ਤਾਂ ਬੇਨਤੀ ਆਰਟੀਫੈਕਟ `${DATA_DIR}/call_logs/` ਦੇ ਅਧੀਨ ਸਟੋਰ ਕੀਤੇ ਜਾਂਦੇ ਹਨ।
ਜਦੋਂ ਪਾਈਪਲਾਈਨ ਕੈਪਚਰ ਸਮਰੱਥ ਹੋਵੇ, ਤਾਂ ਸਟ੍ਰੀਮ ਚੰਕ ਪੇਲੋਡਾਂ ਨੂੰ ਛੱਡਣ ਲਈ `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` ਸੈੱਟ ਕਰੋ, ਜਾਂ KB ਵਿੱਚ ਆਰਟੀਫੈਕਟ ਸੀਮਾ ਬਦਲਣ ਲਈ `CALL_LOG_PIPELINE_MAX_SIZE_KB` ਨੂੰ ਅਨੁਕੂਲ ਕਰੋ।

### ਪ੍ਰਦਾਤਾ ਦੀ ਸਿਹਤ ਜਾਂਚੋ

```bash
# ਸਿਹਤ ਡੈਸ਼ਬੋਰਡ
http://localhost:20128/dashboard/health

# API ਸਿਹਤ ਜਾਂਚ
curl http://localhost:20128/api/monitoring/health
```

### ਰਨਟਾਈਮ ਸਟੋਰੇਜ

- ਮੁੱਖ ਸਥਿਤੀ: `${DATA_DIR}/storage.sqlite` (ਪ੍ਰਦਾਤਾ, ਕੌਂਬੋ, ਉਪਨਾਮ, ਕੁੰਜੀਆਂ, ਸੈਟਿੰਗਾਂ)
- ਵਰਤੋਂ: `storage.sqlite` ਵਿੱਚ SQLite ਟੇਬਲਾਂ (`usage_history`, `call_logs`, `proxy_logs`) + ਵਿਕਲਪਿਕ `${DATA_DIR}/call_logs/`
- ਐਪਲੀਕੇਸ਼ਨ ਲੌਗ: `<repo>/logs/...` (ਜਦੋਂ `APP_LOG_TO_FILE=true` ਹੋਵੇ)
- ਕਾਲ ਲੌਗ ਆਰਟੀਫੈਕਟ: ਕਾਲ ਲੌਗ ਪਾਈਪਲਾਈਨ ਸਮਰੱਥ ਹੋਣ ਉੱਤੇ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

ਬੇਨਤੀ ਲੌਗ ਪੰਨੇ ਦੀ **ਇਤਿਹਾਸ ਸਾਫ਼ ਕਰੋ** ਕਾਰਵਾਈ `call_logs`, ਪੁਰਾਣੇ
`request_detail_logs`, ਅਤੇ ਲੋਕਲ `${DATA_DIR}/call_logs/` ਆਰਟੀਫੈਕਟ ਡਾਇਰੈਕਟਰੀ ਨੂੰ ਸਾਫ਼ ਕਰਦੀ ਹੈ।

## ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਸੰਬੰਧੀ ਸਮੱਸਿਆਵਾਂ

### ਪ੍ਰੋਵਾਈਡਰ OPEN ਸਥਿਤੀ ਵਿੱਚ ਅਟਕਿਆ ਹੋਇਆ ਹੈ

ਜਦੋਂ ਕਿਸੇ ਪ੍ਰੋਵਾਈਡਰ ਦਾ ਸਰਕਿਟ ਬ੍ਰੇਕਰ OPEN ਹੁੰਦਾ ਹੈ, ਤਾਂ ਕੂਲਡਾਊਨ ਦੀ ਮਿਆਦ ਖਤਮ ਹੋਣ ਤੱਕ ਬੇਨਤੀਆਂ ਬਲੌਕ ਰਹਿੰਦੀਆਂ ਹਨ।

**ਹੱਲ:**

1. **ਡੈਸ਼ਬੋਰਡ → ਸੈਟਿੰਗਾਂ → ਲਚਕੀਲਾਪਣ** 'ਤੇ ਜਾਓ
2. ਪ੍ਰਭਾਵਿਤ ਪ੍ਰੋਵਾਈਡਰ ਲਈ ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਕਾਰਡ ਦੀ ਜਾਂਚ ਕਰੋ
3. ਸਾਰੇ ਬ੍ਰੇਕਰ ਸਾਫ਼ ਕਰਨ ਲਈ **ਸਾਰੇ ਰੀਸੈੱਟ ਕਰੋ** 'ਤੇ ਕਲਿੱਕ ਕਰੋ, ਜਾਂ ਕੂਲਡਾਊਨ ਦੀ ਮਿਆਦ ਖਤਮ ਹੋਣ ਦੀ ਉਡੀਕ ਕਰੋ
4. ਰੀਸੈੱਟ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਪ੍ਰੋਵਾਈਡਰ ਅਸਲ ਵਿੱਚ ਉਪਲਬਧ ਹੈ

### ਪ੍ਰੋਵਾਈਡਰ ਵਾਰ-ਵਾਰ ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਨੂੰ ਟ੍ਰਿੱਪ ਕਰਦਾ ਹੈ

ਜੇ ਕੋਈ ਪ੍ਰੋਵਾਈਡਰ ਵਾਰ-ਵਾਰ OPEN ਸਥਿਤੀ ਵਿੱਚ ਜਾਂਦਾ ਹੈ:

1. ਅਸਫਲਤਾ ਦੇ ਪੈਟਰਨ ਲਈ **ਡੈਸ਼ਬੋਰਡ → ਸਿਹਤ → ਪ੍ਰੋਵਾਈਡਰ ਦੀ ਸਿਹਤ** ਦੀ ਜਾਂਚ ਕਰੋ
2. **ਸੈਟਿੰਗਾਂ → ਲਚਕੀਲਾਪਣ → ਪ੍ਰੋਵਾਈਡਰ ਪ੍ਰੋਫਾਈਲਾਂ** 'ਤੇ ਜਾਓ ਅਤੇ ਅਸਫਲਤਾ ਦੀ ਸੀਮਾ ਵਧਾਓ
3. ਜਾਂਚ ਕਰੋ ਕਿ ਕੀ ਪ੍ਰੋਵਾਈਡਰ ਨੇ API ਸੀਮਾਵਾਂ ਬਦਲੀਆਂ ਹਨ ਜਾਂ ਮੁੜ-ਪ੍ਰਮਾਣੀਕਰਨ ਦੀ ਲੋੜ ਹੈ
4. ਲੇਟੈਂਸੀ ਟੈਲੀਮੈਟਰੀ ਦੀ ਸਮੀਖਿਆ ਕਰੋ — ਵੱਧ ਲੇਟੈਂਸੀ ਕਾਰਨ ਟਾਈਮਆਊਟ-ਆਧਾਰਿਤ ਅਸਫਲਤਾਵਾਂ ਹੋ ਸਕਦੀਆਂ ਹਨ

## ਆਡੀਓ ਟ੍ਰਾਂਸਕ੍ਰਿਪਸ਼ਨ ਸੰਬੰਧੀ ਸਮੱਸਿਆਵਾਂ

### "ਅਸਮਰਥਿਤ ਮਾਡਲ" ਗਲਤੀ

- ਅਜਿਹੀ ਮਾਡਲ ID ਵਰਤੋ ਜਿਸਦਾ ਪਹਿਲਾ ਹਿੱਸਾ ਉਸ ਪ੍ਰੋਵਾਈਡਰ ਦਾ ਹੋਵੇ ਜਿਸ ਲਈ ਤੁਹਾਡੇ ਕੋਲ ਕ੍ਰੈਡੈਂਸ਼ਲ ਹਨ (`openai/whisper-1`, `openrouter/deepgram/nova-3`)। ਸਿਰਫ਼ `deepgram/nova-3` ਲਈ ਮੂਲ Deepgram ਕੁੰਜੀ ਲੋੜੀਂਦੀ ਹੈ।
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਪ੍ਰੋਵਾਈਡਰ **ਡੈਸ਼ਬੋਰਡ → ਪ੍ਰੋਵਾਈਡਰ** ਵਿੱਚ ਕਨੈਕਟ ਹੈ

### ਟ੍ਰਾਂਸਕ੍ਰਿਪਸ਼ਨ ਖਾਲੀ ਵਾਪਸ ਆਉਂਦੀ ਹੈ ਜਾਂ ਅਸਫਲ ਹੁੰਦੀ ਹੈ

- ਸਮਰਥਿਤ ਆਡੀਓ ਫਾਰਮੈਟਾਂ ਦੀ ਜਾਂਚ ਕਰੋ: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਫਾਈਲ ਦਾ ਆਕਾਰ ਪ੍ਰੋਵਾਈਡਰ ਦੀਆਂ ਸੀਮਾਵਾਂ ਅੰਦਰ ਹੈ (ਆਮ ਤੌਰ 'ਤੇ < 25MB)
- ਪ੍ਰੋਵਾਈਡਰ ਕਾਰਡ ਵਿੱਚ ਪ੍ਰੋਵਾਈਡਰ ਦੀ API ਕੁੰਜੀ ਦੀ ਵੈਧਤਾ ਦੀ ਜਾਂਚ ਕਰੋ

### ਆਮ ਫਾਰਮੈਟ ਸਮੱਸਿਆਵਾਂ

- **ਥਿੰਕਿੰਗ ਟੈਗ ਦਿਖਾਈ ਨਹੀਂ ਦੇ ਰਹੇ** — ਜਾਂਚ ਕਰੋ ਕਿ ਕੀ ਟਾਰਗੇਟ ਪ੍ਰੋਵਾਈਡਰ ਥਿੰਕਿੰਗ ਅਤੇ ਥਿੰਕਿੰਗ ਬਜਟ ਸੈਟਿੰਗ ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ
- **ਟੂਲ ਕਾਲਾਂ ਗਾਇਬ ਹੋ ਰਹੀਆਂ ਹਨ** — ਕੁਝ ਫਾਰਮੈਟ ਅਨੁਵਾਦ ਅਸਮਰਥਿਤ ਫੀਲਡਾਂ ਨੂੰ ਹਟਾ ਸਕਦੇ ਹਨ; ਪਲੇਗ੍ਰਾਊਂਡ ਮੋਡ ਵਿੱਚ ਪੁਸ਼ਟੀ ਕਰੋ
- **ਸਿਸਟਮ ਪ੍ਰੌਂਪਟ ਗਾਇਬ ਹੈ** — Claude ਅਤੇ Gemini ਸਿਸਟਮ ਪ੍ਰੌਂਪਟਾਂ ਨੂੰ ਵੱਖਰੇ ਢੰਗ ਨਾਲ ਸੰਭਾਲਦੇ ਹਨ; ਅਨੁਵਾਦ ਆਉਟਪੁੱਟ ਦੀ ਜਾਂਚ ਕਰੋ
- **SDK ਆਬਜੈਕਟ ਦੀ ਬਜਾਏ ਰੌ ਸਟ੍ਰਿੰਗ ਵਾਪਸ ਕਰਦਾ ਹੈ** — v1.x ਵਿੱਚ ਹੱਲ ਕੀਤਾ ਗਿਆ; ਜਵਾਬ ਸੈਨਿਟਾਈਜ਼ਰ ਗੈਰ-ਮਿਆਰੀ ਫੀਲਡਾਂ (`x_groq`, `usage_breakdown`, ਆਦਿ) ਨੂੰ ਹਟਾ ਦਿੰਦਾ ਹੈ, ਜੋ OpenAI SDK Pydantic ਪ੍ਰਮਾਣਿਕਤਾ ਅਸਫਲਤਾਵਾਂ ਦਾ ਕਾਰਨ ਬਣਦੀਆਂ ਹਨ। ਜੇ ਤੁਹਾਨੂੰ ਅਜੇ ਵੀ v3.x+ 'ਤੇ ਇਹ ਸਮੱਸਿਆ ਦਿਖਾਈ ਦਿੰਦੀ ਹੈ, ਤਾਂ ਕਿਰਪਾ ਕਰਕੇ ਇੱਕ ਮੁੱਦਾ ਦਰਜ ਕਰੋ।
- **GLM/ERNIE `system` ਭੂਮਿਕਾ ਨੂੰ ਅਸਵੀਕਾਰ ਕਰਦਾ ਹੈ** — v1.x ਵਿੱਚ ਹੱਲ ਕੀਤਾ ਗਿਆ; ਭੂਮਿਕਾ ਨਾਰਮਲਾਈਜ਼ਰ ਅਸੰਗਤ ਮਾਡਲਾਂ ਲਈ ਸਿਸਟਮ ਸੁਨੇਹਿਆਂ ਨੂੰ ਆਪਣੇ ਆਪ ਉਪਭੋਗਤਾ ਸੁਨੇਹਿਆਂ ਵਿੱਚ ਮਿਲਾ ਦਿੰਦਾ ਹੈ। ਜੇ ਤੁਹਾਨੂੰ ਅਜੇ ਵੀ v3.x+ 'ਤੇ ਇਹ ਸਮੱਸਿਆ ਦਿਖਾਈ ਦਿੰਦੀ ਹੈ, ਤਾਂ ਕਿਰਪਾ ਕਰਕੇ ਇੱਕ ਮੁੱਦਾ ਦਰਜ ਕਰੋ।
- **`developer` ਭੂਮਿਕਾ ਦੀ ਪਛਾਣ ਨਹੀਂ ਹੁੰਦੀ** — v1.x ਵਿੱਚ ਹੱਲ ਕੀਤਾ ਗਿਆ; ਗੈਰ-OpenAI ਪ੍ਰੋਵਾਈਡਰਾਂ ਲਈ ਇਸਨੂੰ ਆਪਣੇ ਆਪ `system` ਵਿੱਚ ਬਦਲ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ। ਜੇ ਤੁਹਾਨੂੰ ਅਜੇ ਵੀ v3.x+ 'ਤੇ ਇਹ ਸਮੱਸਿਆ ਦਿਖਾਈ ਦਿੰਦੀ ਹੈ, ਤਾਂ ਕਿਰਪਾ ਕਰਕੇ ਇੱਕ ਮੁੱਦਾ ਦਰਜ ਕਰੋ।
- **`json_schema` Gemini ਨਾਲ ਕੰਮ ਨਹੀਂ ਕਰ ਰਿਹਾ** — v1.x ਵਿੱਚ ਹੱਲ ਕੀਤਾ ਗਿਆ; `response_format` ਨੂੰ ਹੁਣ Gemini ਦੇ `responseMimeType` + `responseSchema` ਵਿੱਚ ਬਦਲਿਆ ਜਾਂਦਾ ਹੈ। ਜੇ ਤੁਹਾਨੂੰ ਅਜੇ ਵੀ v3.x+ 'ਤੇ ਇਹ ਸਮੱਸਿਆ ਦਿਖਾਈ ਦਿੰਦੀ ਹੈ, ਤਾਂ ਕਿਰਪਾ ਕਰਕੇ ਇੱਕ ਮੁੱਦਾ ਦਰਜ ਕਰੋ।

## ਲਚਕੀਲੇਪਣ ਦੀਆਂ ਸੈਟਿੰਗਾਂ

### ਆਟੋਮੈਟਿਕ ਦਰ-ਸੀਮਾ ਚਾਲੂ ਨਹੀਂ ਹੋ ਰਹੀ

- ਆਟੋਮੈਟਿਕ ਦਰ-ਸੀਮਾ ਸਿਰਫ਼ API ਕੁੰਜੀ ਪ੍ਰਦਾਤਾਵਾਂ 'ਤੇ ਲਾਗੂ ਹੁੰਦੀ ਹੈ (OAuth/ਸਬਸਕ੍ਰਿਪਸ਼ਨ 'ਤੇ ਨਹੀਂ)
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ **ਸੈਟਿੰਗਾਂ → ਲਚਕੀਲੇਪਣ → ਪ੍ਰਦਾਤਾ ਪ੍ਰੋਫ਼ਾਈਲਾਂ** ਵਿੱਚ ਆਟੋਮੈਟਿਕ ਦਰ-ਸੀਮਾ ਸਮਰੱਥ ਹੈ
- ਜਾਂਚ ਕਰੋ ਕਿ ਕੀ ਪ੍ਰਦਾਤਾ `429` ਸਥਿਤੀ ਕੋਡ ਜਾਂ `Retry-After` ਹੈਡਰ ਵਾਪਸ ਕਰਦਾ ਹੈ

### ਐਕਸਪੋਨੇਨਸ਼ੀਅਲ ਬੈਕਆਫ਼ ਨੂੰ ਟਿਊਨ ਕਰਨਾ

ਪ੍ਰਦਾਤਾ ਪ੍ਰੋਫ਼ਾਈਲ ਇਹਨਾਂ ਸੈਟਿੰਗਾਂ ਦਾ ਸਮਰਥਨ ਕਰਦੇ ਹਨ:

- **ਮੂਲ ਦੇਰੀ** — ਪਹਿਲੀ ਅਸਫਲਤਾ ਤੋਂ ਬਾਅਦ ਸ਼ੁਰੂਆਤੀ ਉਡੀਕ ਸਮਾਂ (ਡਿਫਾਲਟ: 1s)
- **ਵੱਧ ਤੋਂ ਵੱਧ ਦੇਰੀ** — ਉਡੀਕ ਸਮੇਂ ਦੀ ਵੱਧ ਤੋਂ ਵੱਧ ਹੱਦ (ਡਿਫਾਲਟ: 30s)
- **ਗੁਣਕ** — ਹਰ ਲਗਾਤਾਰ ਅਸਫਲਤਾ 'ਤੇ ਦੇਰੀ ਕਿੰਨੀ ਵਧਾਉਣੀ ਹੈ (ਡਿਫਾਲਟ: 2x)

### ਥੰਡਰਿੰਗ ਹਰਡ ਤੋਂ ਬਚਾਅ

ਜਦੋਂ ਬਹੁਤ ਸਾਰੀਆਂ ਸਮਕਾਲੀ ਬੇਨਤੀਆਂ ਕਿਸੇ ਦਰ-ਸੀਮਿਤ ਪ੍ਰਦਾਤਾ ਤੱਕ ਪਹੁੰਚਦੀਆਂ ਹਨ, ਤਾਂ OmniRoute ਬੇਨਤੀਆਂ ਨੂੰ ਲੜੀਵਾਰ ਕਰਨ ਅਤੇ ਲੜੀਵਾਰ ਅਸਫਲਤਾਵਾਂ ਰੋਕਣ ਲਈ mutex + ਆਟੋਮੈਟਿਕ ਦਰ-ਸੀਮਾ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। API ਕੁੰਜੀ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ ਇਹ ਆਪਣੇ-ਆਪ ਹੁੰਦਾ ਹੈ।

### ਚੈਟ ਬੇਨਤੀਆਂ 503 / chat_admission_busy ਨਾਲ ਅਸਫਲ ਹੁੰਦੀਆਂ ਹਨ

**ਲੱਛਣ:**

- ਚੈਟ ਪੂਰਤੀ ਐਂਡਪੌਇੰਟ ਇੱਕ ਮੁੜ-ਕੋਸ਼ਿਸ਼ਯੋਗ `503` ਜਵਾਬ ਵਾਪਸ ਕਰਦਾ ਹੈ, ਜਿਸਦਾ ਤਰੁੱਟੀ ਕੋਡ
  `chat_admission_busy` ਹੁੰਦਾ ਹੈ।
- ਜਵਾਬ ਵਿੱਚ `Retry-After` ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ। #12135 ਤੋਂ ਬਾਅਦ ਇਸਦਾ ਮੁੱਲ ਦੇਖੀ ਗਈ
  ਵਰਤੋਂ ਤੋਂ ਲਿਆ ਜਾਂਦਾ ਹੈ — ਬੇਨਤੀ ਵੱਲੋਂ ਪਹਿਲਾਂ ਹੀ ਉਡੀਕੀ ਗਈ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ਵਿੰਡੋ
  ਅਤੇ ਮੌਜੂਦਾ ਹੈਵੀਵੇਟ ਲੀਜ਼ਾਂ ਨੂੰ ਰੱਖੇ ਹੋਏ ਸਮੇਂ ਵਿੱਚੋਂ ਵੱਡਾ ਮੁੱਲ — ਜਿਸਨੂੰ ਪੂਰੇ
  ਸਕਿੰਟਾਂ ਤੱਕ ਉੱਪਰ ਵੱਲ ਰਾਊਂਡ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ 60 'ਤੇ ਸੀਮਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਨਿਸ਼ਕਿਰਿਆ ਗੇਟ 'ਤੇ ਇਹ ਇਤਿਹਾਸਕ ਨਿਊਨਤਮ ਹੱਦਾਂ ਕਾਇਮ ਰੱਖਦਾ ਹੈ: ਬਾਈਟ-ਅਧਾਰਿਤ
  ਪਾਥ 'ਤੇ 2 ਸਕਿੰਟ, ਅਤੇ ਸਟਰਕਚਰ-ਅਧਾਰਿਤ ਪਾਥ 'ਤੇ 1 ਸਕਿੰਟ (ਜਿਸ ਵਿੱਚ
  `reason: "structure_limit"` ਵੀ ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ)।
- ਇਹ ਉਦੋਂ ਹੋ ਸਕਦਾ ਹੈ ਜਦੋਂ ਕੋਈ ਹੋਰ ਹੈਵੀਵੇਟ ਚੈਟ ਜਾਂ ਲੰਮੇ ਸਮੇਂ ਤੱਕ ਚੱਲਣ ਵਾਲਾ ਸਟ੍ਰੀਮਿੰਗ ਜਵਾਬ ਹਾਲੇ ਵੀ
  ਪ੍ਰਕਿਰਿਆ ਅਧੀਨ ਹੋਵੇ।

ਬਾਈਟ-ਅਧਾਰਿਤ ਜਵਾਬ ਦੀ ਬਾਡੀ ਇਹ ਹੈ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ਸਟਰਕਚਰ-ਅਧਾਰਿਤ ਜਵਾਬ ਉਸੇ ਕਿਸਮ ਅਤੇ ਕੋਡ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ, ਜਿਸਦਾ ਸੁਨੇਹਾ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ਅਤੇ `reason: "structure_limit"` ਹੁੰਦਾ ਹੈ।
ਡਿਫਾਲਟ ਥ੍ਰੈਸ਼ਹੋਲਡਾਂ 'ਤੇ, ਕੋਈ ਬੇਨਤੀ ਸਟਰਕਚਰ ਦੇ ਪੱਖੋਂ ਹੈਵੀ ਮੰਨੀ ਜਾਂਦੀ ਹੈ ਜਦੋਂ ਇਸ ਵਿੱਚ ਘੱਟੋ-ਘੱਟ `200` ਸੁਨੇਹੇ,
ਘੱਟੋ-ਘੱਟ `64` ਟੂਲ, ਜਾਂ ਘੱਟੋ-ਘੱਟ `32,000` ਅਨੁਮਾਨਿਤ ਟੋਕਨ ਹੋਣ, ਜਾਂ ਜਦੋਂ ਸੀਮਾਬੱਧ ਸਟਰਕਚਰ ਅਨੁਮਾਨ
`10,000` ਵਿਜ਼ਿਟ ਕੀਤੇ ਨੋਡਾਂ ਜਾਂ `12` ਡੂੰਘਾਈ ਦੀਆਂ ਆਪਣੀਆਂ ਹੱਦਾਂ ਖ਼ਤਮ ਕਰ ਦੇਵੇ।

**ਕਾਰਨ:** ਇਹ OmniRoute ਦੇ ਅੰਦਰ ਜਾਣਬੁੱਝ ਕੇ ਕੀਤਾ ਗਿਆ ਲੋਡ ਘਟਾਓ ਹੈ, ਅੱਪਸਟ੍ਰੀਮ-ਪ੍ਰਦਾਤਾ ਦੀ ਅਸਫਲਤਾ ਨਹੀਂ।
ਹਰ ਪ੍ਰਕਿਰਿਆ ਕਿਸੇ ਵੱਡੀ ਬੇਨਤੀ ਦੀ ਬਾਡੀ ਨੂੰ ਸੰਭਾਲ ਕੇ ਰੱਖਣ ਅਤੇ ਪਾਰਸ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਸੀਮਿਤ ਹੈਵੀਵੇਟ ਸਮਰੱਥਾ ਰਾਖਵੀਂ ਕਰਨ ਲਈ
ਇੱਕ ਪ੍ਰਕਿਰਿਆ-ਸਥਾਨਕ ਗਾਰਡ ਵਰਤਦੀ ਹੈ। ਇੱਕ ਹੈਵੀਵੇਟ ਲੀਜ਼ SSE
ਜਵਾਬ ਦੇ ਪੂਰੇ ਜੀਵਨਕਾਲ ਲਈ ਰੱਖੀ ਰਹਿੰਦੀ ਹੈ।

**#503-ਫੈਨਆਉਟ:** ਇਸ ਸੁਧਾਰ ਤੋਂ ਪਹਿਲਾਂ, ਗਾਰਡ ਹੋਸਟ ਮੈਮੋਰੀ ਦੀ ਪਰਵਾਹ ਕੀਤੇ ਬਿਨਾਂ ਇੱਕ ਨਿਸ਼ਚਿਤ ਬੇਨਤੀ ਗਿਣਤੀ
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ਡਿਫਾਲਟ `1`) 'ਤੇ ਸਮਕਾਲਿਕਤਾ ਨੂੰ ਸੀਮਿਤ ਕਰਦਾ ਸੀ, ਇਸ ਲਈ ਕੋਡਿੰਗ-ਏਜੰਟ
ਫੈਨਆਉਟ (ਕਈ ਸਬ-ਏਜੰਟ/CLI, ਬਾਡੀਆਂ ਆਮ ਤੌਰ 'ਤੇ > 256 KB) ਲਗਭਗ 1 ਦੀ ਪ੍ਰਭਾਵਸ਼ਾਲੀ
ਸਮਕਾਲਿਕਤਾ ਤੱਕ ਡਿੱਗ ਜਾਂਦਾ ਸੀ ਅਤੇ ਬਿਲਕੁਲ ਆਮ ਲੋਡ ਹੇਠ ਵੀ 503 ਵਾਪਸ ਕਰਦਾ ਸੀ। ਹੁਣ ਗਾਰਡ ਆਪਣੇ-ਆਪ ਟਿਊਨ ਹੁੰਦਾ ਹੈ: ਇਸਨੂੰ
ਪ੍ਰਕਿਰਿਆ ਦੀ ਅਸਲ ਮੈਮੋਰੀ ਸੀਮਾ ਤੋਂ ਆਕਾਰ ਲੈਣ ਵਾਲੇ ਆਪਣੇ-ਆਪ ਨਿਰਧਾਰਤ ਇੰਜੈਸਟ ਬਾਈਟ ਬਜਟ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ਦੁਆਰਾ ਨਿਯੰਤਰਿਤ
ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਅਤੇ ਇਹ ਇੱਕ ਲਾਈਵ ਸਰੋਤ-ਦਬਾਅ ਸੰਕੇਤ ਨੂੰ ਵੀ ਧਿਆਨ ਵਿੱਚ ਰੱਖਦਾ ਹੈ — ਇਸ ਲਈ ਇਹ
ਸਿਰਫ਼ ਉਦੋਂ ਲੋਡ ਘਟਾਉਂਦਾ ਹੈ ਜਦੋਂ ਹੋਸਟ ਸੱਚਮੁੱਚ ਮੈਮੋਰੀ ਦਬਾਅ ਹੇਠ ਹੋਵੇ, ਨਾ ਕਿ ਸਿਰਫ਼ ਇਸ ਕਰਕੇ ਕਿ ਇੱਕੋ ਸਮੇਂ ਇੱਕ ਤੋਂ ਵੱਧ
ਹੈਵੀ ਬੇਨਤੀਆਂ ਆ ਗਈਆਂ। ਪੁਰਾਣੀ ਗਿਣਤੀ ਸੀਮਾ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ਦਾ
ਅਜੇ ਵੀ ਸਤਿਕਾਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਪਰ ਕੇਵਲ ਤਾਂ ਹੀ ਜੇ ਤੁਸੀਂ ਇਸਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਸੈੱਟ ਕਰੋ।

ਜਦੋਂ ਸਮਰੱਥਾ ਰੁੱਝੀ ਹੁੰਦੀ ਹੈ, ਤਾਂ ਹੈਵੀਵੇਟ ਬੇਨਤੀ ਮੁੜ-ਕੋਸ਼ਿਸ਼ਯੋਗ `503` ਨਾਲ ਜਵਾਬ ਦੇਣ ਤੋਂ ਪਹਿਲਾਂ
ਕਿਸੇ ਸਲਾਟ ਦੇ ਖਾਲੀ ਹੋਣ ਲਈ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ਡਿਫਾਲਟ `2000`, `0` ਉਡੀਕ ਨੂੰ ਅਸਮਰੱਥ ਕਰਦਾ ਹੈ) ਤੱਕ
ਉਡੀਕ ਕਰਦੀ ਹੈ। ਇਹ ਸੀਮਾਬੱਧ ਉਡੀਕ ਇਸ ਲਈ ਮੌਜੂਦ ਹੈ ਤਾਂ ਜੋ ਏਜੰਟ-ਸ਼ੈਲੀ ਕਲਾਇੰਟ
(OpenCode, Claude Code, Cursor), ਜੋ ਹੈਵੀ ਉਪ-ਬੇਨਤੀਆਂ ਨੂੰ ਇੱਕੋ ਸਮੇਂ ਫੈਨਆਉਟ ਕਰਦੇ ਹਨ, ਤੁਰੰਤ ਅਸਵੀਕਾਰਤਾਵਾਂ 'ਤੇ ਆਪਣਾ ਸਾਰਾ
ਮੁੜ-ਕੋਸ਼ਿਸ਼ ਬਜਟ ਖਰਚਣ ਅਤੇ ਕੰਮ ਦੇ ਵਿਚਕਾਰ ਬੰਦ ਹੋਣ ਦੀ ਬਜਾਏ ਬਰਸਟ ਨੂੰ ਲੜੀਵਾਰ ਕਰ ਸਕਣ।
ਮੌਜੂਦਾ ਹੈਵੀਵੇਟ ਲੀਜ਼ ਵਰਤੋਂ, ਨਿਰਧਾਰਤ ਬਾਈਟ ਬਜਟ ਅਤੇ ਲਾਈਵ ਦਬਾਅ ਦੀ ਗੰਭੀਰਤਾ
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) 'ਤੇ ਦਰਸਾਈ ਜਾਂਦੀ ਹੈ — ਕਿਸੇ ਵੀ env var ਨੂੰ ਬਦਲਣ ਤੋਂ ਪਹਿਲਾਂ ਇਹਨਾਂ ਦੀ ਜਾਂਚ ਕਰੋ।
ਸੈਟਿੰਗਾਂ → ਲਚਕੀਲੇਪਣ → ਬੇਨਤੀ ਕਤਾਰ → ਸਮਕਾਲੀ ਬੇਨਤੀਆਂ ਇਸਨੂੰ ਨਿਯੰਤਰਿਤ ਨਹੀਂ ਕਰਦੀ; ਉਹ ਸੈਟਿੰਗ
ਇੱਕ ਵੱਖਰੇ ਪ੍ਰਦਾਤਾ ਬੇਨਤੀ-ਕਤਾਰ ਤੰਤਰ ਨੂੰ ਨਿਯੰਤਰਿਤ ਕਰਦੀ ਹੈ।

**ਸੁਧਾਰ:**

1. ਪਹਿਲਾਂ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਕਰੋ। ਕਲਾਇੰਟਾਂ ਨੂੰ ਬੇਨਤੀ ਤੁਰੰਤ
   ਦੁਹਰਾਉਣ ਦੀ ਬਜਾਏ `Retry-After` ਦਾ ਸਤਿਕਾਰ ਕਰਨਾ ਅਤੇ ਬੈਕਆਫ਼ ਵਰਤਣਾ ਚਾਹੀਦਾ ਹੈ।
2. ਕੁਝ ਵੀ ਟਿਊਨ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ `/api/monitoring/health` → `chatAdmission` ਦੀ ਜਾਂਚ ਕਰੋ। `countCapEnabled:
false` ਅਤੇ ਇੱਕ ਖੁੱਲ੍ਹਾ `maxInflightBytes` ਦਰਸਾਉਂਦੇ ਹਨ ਕਿ ਆਪਣੇ-ਆਪ ਨਿਰਧਾਰਤ ਬਜਟ ਪਹਿਲਾਂ ਹੀ ਆਪਣਾ
   ਕੰਮ ਕਰ ਰਿਹਾ ਹੈ; `high`/`critical` ਦੀ `pressureSeverity` ਦਾ ਅਰਥ ਹੈ ਕਿ ਹੋਸਟ ਵਿੱਚ ਸੱਚਮੁੱਚ ਮੈਮੋਰੀ ਘੱਟ ਹੈ —
   ਇਸਨੂੰ ਕਿਸੇ admission env var ਨਾਲ ਠੀਕ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ; ਇਸ ਲਈ ਹੋਰ RAM ਜਾਂ ਛੋਟੇ ਵਰਕਲੋਡ ਦੀ ਲੋੜ ਹੈ।
3. ਕੇਵਲ ਤਾਂ ਹੀ, ਜੇ `/api/monitoring/health` ਦਿਖਾਉਂਦਾ ਹੈ ਕਿ ਆਪਣੇ-ਆਪ ਨਿਰਧਾਰਤ ਬਜਟ ਤੁਹਾਡੇ ਹੋਸਟ ਲਈ ਸੱਚਮੁੱਚ ਬਹੁਤ ਛੋਟਾ ਹੈ
   (ਇਹ ਬਹੁਤ ਘੱਟ ਹੁੰਦਾ ਹੈ — ਇਹ ਪਹਿਲਾਂ ਹੀ ਕੰਟੇਨਰ ਤੋਂ ਬੇਅਰ-ਮੈਟਲ ਤੱਕ ਸਕੇਲ ਕਰਦਾ ਹੈ), ਵਿਰਾਸਤੀ ਬੇਨਤੀ-ਗਿਣਤੀ ਸੀਮਾ ਵੱਲ ਮੁੜਨ ਦੀ ਬਜਾਏ
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ਨਾਲ ਇਸਨੂੰ ਸਿੱਧਾ ਓਵਰਰਾਈਡ ਕਰੋ।

ਪ੍ਰਮਾਣਿਕ admission ਸੈਟਿੰਗਾਂ ਲਈ [ਵਾਤਾਵਰਣ-ਵੇਰੀਏਬਲ ਹਵਾਲਾ](../reference/ENVIRONMENT.md#4-security--authentication)
ਵੇਖੋ।

## ਵਿਕਲਪਿਕ RAG / LLM ਅਸਫਲਤਾ ਵਰਗੀਕਰਨ (16 ਸਮੱਸਿਆਵਾਂ)

ਕੁਝ OmniRoute ਵਰਤੋਂਕਾਰ ਗੇਟਵੇ ਨੂੰ RAG ਜਾਂ ਏਜੰਟ ਸਟੈਕਾਂ ਦੇ ਅੱਗੇ ਰੱਖਦੇ ਹਨ। ਅਜਿਹੀਆਂ ਸੈਟਅੱਪਾਂ ਵਿੱਚ ਇੱਕ ਅਜੀਬ ਪੈਟਰਨ ਆਮ ਤੌਰ 'ਤੇ ਵੇਖਣ ਨੂੰ ਮਿਲਦਾ ਹੈ: OmniRoute ਠੀਕ ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ (ਪ੍ਰਦਾਤਾ ਚਾਲੂ ਹਨ, ਰੂਟਿੰਗ ਪ੍ਰੋਫਾਈਲ ਠੀਕ ਹਨ, ਕੋਈ ਦਰ ਸੀਮਾ ਚੇਤਾਵਨੀ ਨਹੀਂ ਹੈ), ਪਰ ਅੰਤਿਮ ਜਵਾਬ ਫਿਰ ਵੀ ਗਲਤ ਹੁੰਦਾ ਹੈ।

ਅਮਲ ਵਿੱਚ, ਇਹ ਘਟਨਾਵਾਂ ਆਮ ਤੌਰ 'ਤੇ ਡਾਊਨਸਟ੍ਰੀਮ RAG ਪਾਈਪਲਾਈਨ ਤੋਂ ਪੈਦਾ ਹੁੰਦੀਆਂ ਹਨ, ਨਾ ਕਿ ਖੁਦ ਗੇਟਵੇ ਤੋਂ।

ਜੇ ਤੁਸੀਂ ਉਨ੍ਹਾਂ ਅਸਫਲਤਾਵਾਂ ਦਾ ਵਰਣਨ ਕਰਨ ਲਈ ਇੱਕ ਸਾਂਝੀ ਸ਼ਬਦਾਵਲੀ ਚਾਹੁੰਦੇ ਹੋ, ਤਾਂ ਤੁਸੀਂ WFGY ProblemMap ਦੀ ਵਰਤੋਂ ਕਰ ਸਕਦੇ ਹੋ, ਜੋ MIT ਲਾਇਸੈਂਸ ਅਧੀਨ ਇੱਕ ਬਾਹਰੀ ਲਿਖਤੀ ਸਰੋਤ ਹੈ ਅਤੇ ਸੋਲਾਂ ਵਾਰ-ਵਾਰ ਵਾਪਰਨ ਵਾਲੇ RAG / LLM ਅਸਫਲਤਾ ਪੈਟਰਨਾਂ ਨੂੰ ਪਰਿਭਾਸ਼ਿਤ ਕਰਦਾ ਹੈ। ਉੱਚ ਪੱਧਰ 'ਤੇ, ਇਹ ਇਨ੍ਹਾਂ ਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ:

- ਪ੍ਰਾਪਤੀ ਭਟਕਾਅ ਅਤੇ ਟੁੱਟੀਆਂ ਸੰਦਰਭ ਸੀਮਾਵਾਂ
- ਖਾਲੀ ਜਾਂ ਪੁਰਾਣੇ ਇੰਡੈਕਸ ਅਤੇ ਵੈਕਟਰ ਸਟੋਰ
- ਐਂਬੈਡਿੰਗ ਅਤੇ ਅਰਥ-ਵਿਗਿਆਨਕ ਬੇਮੇਲਤਾ
- ਪ੍ਰੌਮਪਟ ਸੰਯੋਜਨ ਅਤੇ ਸੰਦਰਭ ਵਿੰਡੋ ਸੰਬੰਧੀ ਸਮੱਸਿਆਵਾਂ
- ਤਰਕ ਦਾ ਢਹਿ ਜਾਣਾ ਅਤੇ ਹੱਦੋਂ ਵੱਧ ਭਰੋਸੇ ਵਾਲੇ ਜਵਾਬ
- ਲੰਬੀ ਚੇਨ ਅਤੇ ਏਜੰਟ ਤਾਲਮੇਲ ਦੀਆਂ ਅਸਫਲਤਾਵਾਂ
- ਮਲਟੀ-ਏਜੰਟ ਮੈਮੋਰੀ ਅਤੇ ਭੂਮਿਕਾ ਭਟਕਾਅ
- ਡਿਪਲੌਇਮੈਂਟ ਅਤੇ ਬੂਟਸਟਰੈਪ ਕ੍ਰਮਬੱਧਤਾ ਦੀਆਂ ਸਮੱਸਿਆਵਾਂ

ਵਿਚਾਰ ਸਧਾਰਨ ਹੈ:

1. ਜਦੋਂ ਤੁਸੀਂ ਕਿਸੇ ਖਰਾਬ ਜਵਾਬ ਦੀ ਜਾਂਚ ਕਰੋ, ਤਾਂ ਇਹ ਜਾਣਕਾਰੀ ਕੈਪਚਰ ਕਰੋ:
   - ਵਰਤੋਂਕਾਰ ਦਾ ਕੰਮ ਅਤੇ ਬੇਨਤੀ
   - OmniRoute ਵਿੱਚ ਰੂਟ ਜਾਂ ਪ੍ਰਦਾਤਾ ਕੰਬੋ
   - ਡਾਊਨਸਟ੍ਰੀਮ ਵਿੱਚ ਵਰਤਿਆ ਗਿਆ ਕੋਈ ਵੀ RAG ਸੰਦਰਭ (ਪ੍ਰਾਪਤ ਕੀਤੇ ਦਸਤਾਵੇਜ਼, ਟੂਲ ਕਾਲਾਂ ਆਦਿ)
2. ਘਟਨਾ ਨੂੰ ਇੱਕ ਜਾਂ ਦੋ WFGY ProblemMap ਨੰਬਰਾਂ (`No.1` … `No.16`) ਨਾਲ ਮੈਪ ਕਰੋ।
3. ਨੰਬਰ ਨੂੰ OmniRoute ਲੌਗਾਂ ਦੇ ਨਾਲ ਆਪਣੇ ਡੈਸ਼ਬੋਰਡ, ਰਨਬੁੱਕ ਜਾਂ ਘਟਨਾ ਟ੍ਰੈਕਰ ਵਿੱਚ ਸਟੋਰ ਕਰੋ।
4. ਇਹ ਨਿਰਧਾਰਤ ਕਰਨ ਲਈ ਸੰਬੰਧਿਤ WFGY ਪੰਨੇ ਦੀ ਵਰਤੋਂ ਕਰੋ ਕਿ ਕੀ ਤੁਹਾਨੂੰ ਆਪਣੇ RAG ਸਟੈਕ, ਰਿਟਰੀਵਰ ਜਾਂ ਰੂਟਿੰਗ ਰਣਨੀਤੀ ਨੂੰ ਬਦਲਣ ਦੀ ਲੋੜ ਹੈ।

ਪੂਰਾ ਪਾਠ ਅਤੇ ਵਿਹਾਰਕ ਵਿਧੀਆਂ ਇੱਥੇ ਉਪਲਬਧ ਹਨ (MIT ਲਾਇਸੈਂਸ, ਸਿਰਫ਼ ਪਾਠ):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

ਜੇ ਤੁਸੀਂ OmniRoute ਦੇ ਪਿੱਛੇ RAG ਜਾਂ ਏਜੰਟ ਪਾਈਪਲਾਈਨਾਂ ਨਹੀਂ ਚਲਾਉਂਦੇ, ਤਾਂ ਤੁਸੀਂ ਇਸ ਭਾਗ ਨੂੰ ਅਣਡਿੱਠਾ ਕਰ ਸਕਦੇ ਹੋ।

## v3.8.0 ਦੀਆਂ ਜਾਣੀਆਂ-ਪਛਾਣੀਆਂ ਸਮੱਸਿਆਵਾਂ

v3.8.0 ਰਿਲੀਜ਼ ਨਾਲ ਸੰਬੰਧਿਤ ਸਮੱਸਿਆਵਾਂ ਅਤੇ ਉਨ੍ਹਾਂ ਦੇ ਮੌਜੂਦਾ ਅਸਥਾਈ ਹੱਲ। ਜੇ ਕਿਸੇ ਬਾਅਦ ਦੇ ਪੈਚ ਵਿੱਚ ਸੁਧਾਰ ਆ ਜਾਂਦਾ ਹੈ, ਤਾਂ ਐਂਟਰੀ ਨੂੰ ਅੱਪਡੇਟ ਜਾਂ ਹਟਾ ਦਿੱਤਾ ਜਾਵੇਗਾ।

### Devin CLI ਪ੍ਰਮਾਣੀਕਰਨ ਅਸਫਲਤਾਵਾਂ

**ਲੱਛਣ:**

- Devin-ਸਮਰਥਿਤ ਟੂਲਾਂ ਨੂੰ ਚਲਾਉਣ ਵੇਲੇ "Devin CLI not found" ਜਾਂ "auth failed"
- CLI ਰਨਟਾਈਮ ਜਾਂਚ `installed=false` ਰਿਪੋਰਟ ਕਰਦੀ ਹੈ

**ਕਾਰਨ:**

- `CLI_DEVIN_BIN` ਅਜਿਹੇ ਪਾਥ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ ਜੋ ਮੌਜੂਦ ਨਹੀਂ ਹੈ
- ਹੋਸਟ ਉੱਤੇ Devin CLI ਇੰਸਟਾਲ ਨਹੀਂ ਹੈ

**ਸੁਧਾਰ:**

1. ਆਪਣੇ ਪਲੇਟਫਾਰਮ ਲਈ Devin CLI ਇੰਸਟਾਲ ਕਰੋ
2. `.env` ਵਿੱਚ `CLI_DEVIN_BIN=/usr/local/bin/devin` (ਜਾਂ ਅਸਲ ਪਾਥ) ਸੈੱਟ ਕਰੋ
3. OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ ਅਤੇ **Dashboard → CLI Tools** ਤੋਂ ਦੁਬਾਰਾ ਟੈਸਟ ਕਰੋ

### ਮਾਡਲ ਕੂਲਡਾਊਨ ਅਟਕਿਆ ਹੋਇਆ ਹੈ (ਦਸਤੀ ਰੀਸੈੱਟ)

**ਲੱਛਣ:**

- ਮਿਆਦ ਖਤਮ ਹੋਣ ਦਾ ਸਮਾਂ ਲੰਘ ਜਾਣ ਤੋਂ ਬਾਅਦ ਵੀ ਇੱਕ ਮਾਡਲ ਕੂਲਡਾਊਨ ਵਿੱਚ ਸੂਚੀਬੱਧ ਰਹਿੰਦਾ ਹੈ
- ਟਾਈਮਸਟੈਂਪ ਬੀਤੇ ਸਮੇਂ ਦਾ ਹੋਣ ਦੇ ਬਾਵਜੂਦ, ਕੰਬੋ ਰੂਟਿੰਗ ਵਿੱਚ ਬੇਨਤੀਆਂ ਹਾਲੇ ਵੀ ਮਾਡਲ ਨੂੰ ਛੱਡ ਦਿੰਦੀਆਂ ਹਨ

**ਦਸਤੀ ਰੀਸੈੱਟ:**

- **ਡੈਸ਼ਬੋਰਡ:** **Settings → Model Cooldowns** → ਪ੍ਰਭਾਵਿਤ ਕਾਰਡ ਉੱਤੇ **Re-enable** ਨੂੰ ਕਲਿੱਕ ਕਰੋ
- **API:** ਪ੍ਰਬੰਧਨ ਪ੍ਰਮਾਣੀਕਰਨ ਹੈਡਰਾਂ ਨਾਲ `DELETE /api/resilience/model-cooldowns`

### Command Code ਪ੍ਰਦਾਤਾ ਕਨੈਕਸ਼ਨ 403 ਨਾਲ ਅਸਫਲ ਹੁੰਦਾ ਹੈ

**ਲੱਛਣ:**

- Command Code ਪ੍ਰਦਾਤਾ ਕਨੈਕਸ਼ਨ ਦੀ ਜਾਂਚ ਕਰਦੇ ਸਮੇਂ 403
- ਨਵਾਂ ਜੋੜਨ ਤੋਂ ਬਾਅਦ ਪ੍ਰਦਾਤਾ ਕਾਰਡ "unauthorized" ਦਿਖਾਉਂਦਾ ਹੈ

**ਕਾਰਨ:** OAuth ਪ੍ਰਵਾਹ ਪੂਰਾ ਨਹੀਂ ਹੋਇਆ (ਕਾਲਬੈਕ ਪ੍ਰਾਪਤ ਨਹੀਂ ਹੋਇਆ ਜਾਂ ਟੋਕਨ ਸੁਰੱਖਿਅਤ ਨਹੀਂ ਕੀਤਾ ਗਿਆ)।

**ਸੁਧਾਰ:**

- OAuth ਪ੍ਰਵਾਹ ਨੂੰ ਦੁਬਾਰਾ ਸ਼ੁਰੂ ਕਰਨ ਲਈ CLI ਤੋਂ `omniroute providers` ਚਲਾਓ, ਜਾਂ
- **Dashboard → Providers → Command Code → Reconnect** ਤੋਂ OAuth ਨੂੰ ਦੁਬਾਰਾ ਚਲਾਓ

### ModelScope ਬਹੁਤ ਸਖ਼ਤ 429 ਕੂਲਡਾਊਨ ਵਾਪਸ ਕਰਦਾ ਹੈ

**ਲੱਛਣ:**

- ਬੇਨਤੀਆਂ ਦੇ ਇੱਕ ਛੋਟੇ ਜਿਹੇ ਬਰਸਟ ਤੋਂ ਬਾਅਦ ModelScope ਉੱਤੇ ਬਹੁਤ ਛੋਟੇ ਜਾਂ ਤੁਰੰਤ ਕੂਲਡਾਊਨ
- ਕੰਬੋ ਰੂਟਿੰਗ ਉਮੀਦ ਨਾਲੋਂ ਪਹਿਲਾਂ ModelScope ਨੂੰ ਛੱਡ ਦਿੰਦੀ ਹੈ

**ਕਾਰਨ:** ModelScope ਪ੍ਰਦਾਤਾ-ਵਿਸ਼ੇਸ਼ `Retry-After` ਹੈਡਰ ਭੇਜਦਾ ਹੈ। v3.8.0 ਵਿੱਚ ਉਨ੍ਹਾਂ ਹੈਡਰਾਂ ਲਈ ਸਮਰਪਿਤ ਹੈਂਡਲਿੰਗ ਸ਼ਾਮਲ ਹੈ, ਇਸ ਲਈ ਪੁਰਾਣੇ ਵਰਜਨ ਉਨ੍ਹਾਂ ਨੂੰ ਆਮ ਦਰ-ਸੀਮਾ ਸੰਕੇਤਾਂ ਵਜੋਂ ਗਲਤ ਪੜ੍ਹਦੇ ਹਨ।

**ਸੁਧਾਰ:**

- ਯਕੀਨੀ ਬਣਾਓ ਕਿ ਤੁਸੀਂ v3.8.0 ਜਾਂ ਇਸ ਤੋਂ ਬਾਅਦ ਦੇ ਵਰਜਨ ਉੱਤੇ ਹੋ
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ **Settings → Resilience** ਦੇ ਅਧੀਨ `useUpstream429BreakerHints` ਟੌਗਲ ਸਮਰੱਥ ਹੈ

### ਉਤਪਾਦਨ ਵਿੱਚ OMNIROUTE_WS_BRIDGE_SECRET ਮੌਜੂਦ ਨਹੀਂ ਹੈ

**ਲੱਛਣ:**

- ਰਿਮੋਟ ਉਤਪਾਦਨ ਹੋਸਟ ਉੱਤੇ ਚੱਲਦੇ ਸਮੇਂ ਹਰ Codex/Responses WebSocket ਬ੍ਰਿਜ ਬੇਨਤੀ ਉੱਤੇ 401
- ਕਨੈਕਟ ਹੋਣ ਤੋਂ ਤੁਰੰਤ ਬਾਅਦ WebSocket ਬ੍ਰਿਜ ਹੈਂਡਸ਼ੇਕ ਬੰਦ ਹੋ ਜਾਂਦਾ ਹੈ

**ਕਾਰਨ:** ਉਤਪਾਦਨ ਵਾਤਾਵਰਣ ਵਿੱਚ `OMNIROUTE_WS_BRIDGE_SECRET` env var ਮੌਜੂਦ ਨਹੀਂ ਹੈ।

**ਸੁਧਾਰ:**

1. ਇੱਕ ਰੈਂਡਮ ਸੀਕ੍ਰੇਟ ਬਣਾਓ: `openssl rand -hex 32`
2. ਉਤਪਾਦਨ ਸਰਵਰ env ਵਿੱਚ (ਅਤੇ ਬ੍ਰਿਜ ਨਾਲ ਸੰਚਾਰ ਕਰਨ ਵਾਲੇ ਕਿਸੇ ਵੀ ਕਲਾਇੰਟ ਵਿੱਚ) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ਸੈੱਟ ਕਰੋ
3. OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ

### Responses API: ਬੈਕਗ੍ਰਾਊਂਡ ਮੋਡ ਨੂੰ ਸਿੰਕ੍ਰੋਨਸ ਵਿੱਚ ਘਟਾਇਆ ਗਿਆ

**ਲੱਛਣ:**

- ਚੇਤਾਵਨੀ ਲੌਗ ਕੀਤੀ ਜਾਂਦੀ ਹੈ: `background mode degraded to synchronous`
- ਇੱਕ `background: true` ਬੇਨਤੀ ਬੈਕਗ੍ਰਾਊਂਡ ਜੌਬ ਹੈਂਡਲ ਦੀ ਬਜਾਏ ਇੱਕ ਆਮ ਸਿੰਕ੍ਰੋਨਸ ਜਵਾਬ ਵਾਪਸ ਕਰਦੀ ਹੈ

**ਕਾਰਨ:** v3.8.0 ਵਿੱਚ Responses API ਉੱਤੇ `background: true` ਨੂੰ ਜਾਣਬੁੱਝ ਕੇ ਸਿੰਕ੍ਰੋਨਸ ਐਗਜ਼ੀਕਿਊਸ਼ਨ ਵਿੱਚ ਘਟਾਇਆ ਜਾਂਦਾ ਹੈ ਅਤੇ ਨਾਲ ਹੀ ਇੱਕ ਚੇਤਾਵਨੀ ਜਾਰੀ ਕੀਤੀ ਜਾਂਦੀ ਹੈ। ਪੂਰਾ ਅਸਿੰਕ੍ਰੋਨਸ ਬੈਕਗ੍ਰਾਊਂਡ ਐਗਜ਼ੀਕਿਊਸ਼ਨ ਭਵਿੱਖ ਵਿੱਚ ਪ੍ਰਦਾਨ ਕੀਤਾ ਜਾਵੇਗਾ।

**ਸੁਧਾਰ:**

- ਕਲਾਇੰਟ ਨੂੰ `background` ਤੋਂ ਬਿਨਾਂ ਕਾਲ ਕਰਨ ਲਈ ਵਿਵਸਥਿਤ ਕਰੋ, ਜਾਂ
- ਪੂਰੇ ਅਸਿੰਕ੍ਰੋਨਸ ਬੈਕਗ੍ਰਾਊਂਡ ਮੋਡ ਵਾਲੀ ਕਿਸੇ ਬਾਅਦ ਦੀ ਰਿਲੀਜ਼ ਦੀ ਉਡੀਕ ਕਰੋ (ਚੇਂਜਲੌਗ ਨੂੰ ਟ੍ਰੈਕ ਕਰੋ)

## ਹੌਲੀ ਸ਼ੁਰੂਆਤ / ਤਿਆਰੀ ਸਮਾਂ-ਸੀਮਾ

ਜੇ CLI `⚠ Server did not respond within 60s` ਦਿਖਾਉਂਦਾ ਹੈ ਪਰ ਸਰਵਰ ਅਸਲ ਵਿੱਚ
ਕੰਮ ਕਰ ਰਿਹਾ ਹੈ, ਤਾਂ ਤੁਹਾਡੇ ਵਾਤਾਵਰਣ ਲਈ ਤਿਆਰੀ ਜਾਂਚ ਦਾ ਸਮਾਂ-ਬਜਟ ਬਹੁਤ ਘੱਟ ਹੈ।

ਇਹ ਆਮ ਤੌਰ 'ਤੇ Windows (ਐਂਟੀਵਾਇਰਸ, ਫ਼ਾਈਲ-ਸਿਸਟਮ ਵਾਚਰ) ਜਾਂ ਭਾਰੀ ਸ਼ੁਰੂਆਤੀ
ਵਰਕਲੋਡ ਵਾਲੇ ਕੰਟੇਨਰਾਂ ਵਿੱਚ ਹੁੰਦਾ ਹੈ।

**ਹੱਲ — ਸਮਾਂ-ਬਜਟ ਵਧਾਓ:**

```bash
# ਵਾਤਾਵਰਣ ਵੇਰੀਏਬਲ ਰਾਹੀਂ (ਸ਼ੁਰੂਆਤਾਂ ਵਿਚਕਾਰ ਕਾਇਮ ਰਹਿੰਦਾ ਹੈ):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 ਮਿੰਟ
omniroute serve

# CLI ਫਲੈਗ ਰਾਹੀਂ (ਸਿਰਫ਼ ਇੱਕ ਵਾਰ ਲਈ):
omniroute serve --ready-timeout 180000
```

ਡਿਫਾਲਟ 60 000 ms (60 s) ਹੈ। ਚੇਤਾਵਨੀ ਸਿਰਫ਼ ਜਾਣਕਾਰੀ ਲਈ ਹੈ; ਸਰਵਰ
ਬੈਕਗ੍ਰਾਊਂਡ ਵਿੱਚ ਸ਼ੁਰੂ ਹੋਣਾ ਜਾਰੀ ਰੱਖਦਾ ਹੈ ਅਤੇ ਬੂਟ ਪੂਰਾ ਹੋਣ ਤੋਂ ਬਾਅਦ ਪਹੁੰਚਯੋਗ ਹੋਵੇਗਾ।

`OMNIROUTE_READY_TIMEOUT_MS` ਬਾਰੇ ਪੂਰੇ ਵੇਰਵਿਆਂ ਲਈ
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) ਵੇਖੋ।
