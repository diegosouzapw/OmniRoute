OmniRoute OpenAI Codex ਵਰਤਣ ਦੇ **ਦੋ** ਤਰੀਕੇ ਉਪਲਬਧ ਕਰਦਾ ਹੈ:

| ਪ੍ਰਦਾਤਾ                | ਇਹ OpenAI ਨਾਲ ਕਿਵੇਂ ਸੰਚਾਰ ਕਰਦਾ ਹੈ                                                                                                                                                                                    | ਵਰਤੋਂ ਸੰਬੰਧੀ ਸਾਵਧਾਨੀ                                              |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **`codex`**            | ਤੁਹਾਡੇ ChatGPT/OpenAI OAuth ਟੋਕਨ ਨੂੰ ਸਿੱਧਾ Responses API ਉੱਤੇ ਮੁੜ ਚਲਾਉਂਦਾ ਹੈ                                                                                                                                         | **ਹਾਂ** — ਅਧਿਕਾਰਤ ਸੈਸ਼ਨ ਨੂੰ ਪ੍ਰਾਕਸੀ/ਰਾਊਟਰ ਵਰਤੋਂ ਲਈ ਅਧਿਕਾਰ ਨਹੀਂ ਹੈ |
| **`codex-app-server`** | JSON-RPC/WebSocket ਰਾਹੀਂ **Codex CLI ਦੇ ਆਪਣੇ `codex app-server`** ਨੂੰ ਚਲਾਉਂਦਾ ਹੈ; CLI ਆਪਣੇ OAuth (`~/.codex/auth.json`) ਦੀ ਮਾਲਕੀ ਰੱਖਦਾ ਹੈ ਅਤੇ ਇਸਨੂੰ ਬਿਲਕੁਲ ਇੱਕ ਇੰਟਰਐਕਟਿਵ `codex` ਸੈਸ਼ਨ ਵਾਂਗ ਆਪਣੇ ਆਪ ਰਿਫ੍ਰੈਸ਼ ਕਰਦਾ ਹੈ | **ਨਹੀਂ** — OmniRoute ਕਦੇ ਵੀ API ਉੱਤੇ ਟੋਕਨ ਮੁੜ ਨਹੀਂ ਚਲਾਉਂਦਾ        |

ਕਿਉਂਕਿ `codex-app-server` ਕਦੇ ਵੀ ਟੋਕਨ ਮੁੜ ਨਹੀਂ ਚਲਾਉਂਦਾ, ਇਸ ਲਈ ਇਸ ਉੱਤੇ
ਸੈਸ਼ਨ-ਰੀਪਲੇ ਵਰਤੋਂ ਸੰਬੰਧੀ ਸਾਵਧਾਨੀ ਲਾਗੂ ਨਹੀਂ ਹੁੰਦੀ। ਇਸ ਲਈ **ਸੰਰਚਿਤ
app-server URL ਉੱਤੇ ਪਹੁੰਚਯੋਗ Codex CLI** ਲੋੜੀਂਦਾ ਹੈ, ਅਤੇ ਉਸ CLI ਵਿੱਚ
**ਸਾਈਨ ਇਨ** ਹੋਣਾ ਲਾਜ਼ਮੀ ਹੈ।

## 1. ਆਰਕੀਟੈਕਚਰ

```
┌─ OmniRoute ਐਪ ──────────────────┐        ┌─ codex-app-server ਸਾਈਡਕਾਰ ────────┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                   │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456         │
│  (+ ਸਮਰੱਥਾ ਟੋਕਨ)                │  JSON  │  --ws-auth capability-token         │
│                                  │  RPC   │  OpenAI OAuth ਨੂੰ ਆਪ ਸੰਭਾਲਦਾ ਹੈ    │
└──────────────────────────────────┘        │  (~/.codex/auth.json, ਆਟੋ-ਰਿਫ੍ਰੈਸ਼) │
        │ ਸਾਂਝੇ ਕਰਦਾ ਹੈ (compose ਵਾਲਿਊਮ)    └─────────────────────────────────────┘
        ▼
  codex-appserver-token   → WS ਸਮਰੱਥਾ ਟੋਕਨ (ਦੋਵੇਂ ਇਸਨੂੰ ਮਾਊਂਟ ਕਰਦੇ ਹਨ)
  codex-appserver-home    → ~/.codex (auth.json ਡੈਸ਼ਬੋਰਡ ਵੱਲੋਂ ਲਿਖੀ ਜਾਂਦੀ ਹੈ,
                             ਸਾਈਡਕਾਰ ਦਾ codex app-server ਇਸਨੂੰ ਪੜ੍ਹਦਾ ਹੈ)
```

- ਸਾਈਡਕਾਰ ਸਮਰੱਥਾ ਟੋਕਨ ਦੇ ਪਿੱਛੇ **ਸਿਰਫ਼** ਅੰਦਰੂਨੀ compose ਨੈੱਟਵਰਕ
  (`ws://codex-app-server:1456`) ਉੱਤੇ ਸੁਣਦਾ ਹੈ। ਇਸਨੂੰ ਹੋਸਟ ਜਾਂ ਇੰਟਰਨੈੱਟ ਉੱਤੇ
  **ਕਦੇ ਵੀ** ਪ੍ਰਕਾਸ਼ਿਤ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ।
- Codex CLI ਨੂੰ `omniroute:base` ਵਿੱਚ ਹੀ ਸ਼ਾਮਲ ਕੀਤਾ ਗਿਆ ਹੈ, ਇਸ ਲਈ ਸਾਈਡਕਾਰ
  ਚਲਾਉਂਦੇ ਸਮੇਂ ਹੋਸਟ ਜਾਂ ਵਰਤੋਂਕਾਰ ਦੀ ਮਸ਼ੀਨ ਉੱਤੇ codex ਇੰਸਟਾਲ ਕਰਨ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ।

## 2. ਇਸਨੂੰ ਚਾਲੂ ਕਰੋ

```bash
# codex app-server ਸਾਈਡਕਾਰ ਪ੍ਰੋਫਾਈਲ ਸਮੇਤ ਸਟੈਕ ਸ਼ੁਰੂ ਕਰੋ:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

ਸਾਈਡਕਾਰ ਪਹਿਲੀ ਵਾਰ ਬੂਟ ਹੋਣ ਉੱਤੇ ਆਪਣਾ WS ਸਮਰੱਥਾ ਟੋਕਨ ਬਣਾਉਂਦਾ ਹੈ (ਸਾਂਝੇ
`codex-appserver-token` ਵਾਲਿਊਮ ਵਿੱਚ) ਅਤੇ ਐਪ ਉਸੇ ਟੋਕਨ ਨੂੰ
`OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE` ਰਾਹੀਂ ਪੜ੍ਹਦੀ ਹੈ। ਟੋਕਨ ਨੂੰ ਹੱਥੀਂ
ਜੋੜਨ ਦੀ ਕੋਈ ਲੋੜ ਨਹੀਂ ਹੈ।

## 3. ਕਨੈਕਟ ਕਰੋ + ਸਾਈਨ ਇਨ ਕਰੋ

1. ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ **OpenAI Codex (App-Server)** ਲਈ ਇੱਕ ਕਨੈਕਸ਼ਨ ਸ਼ਾਮਲ ਕਰੋ। ਕਿਸੇ API
   ਕੁੰਜੀ ਜਾਂ ਟੋਕਨ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ (ਇਹ ਇੱਕ no-auth ਪ੍ਰਦਾਤਾ ਹੈ — ਪ੍ਰਮਾਣੀਕਰਨ ਦੀ
   ਮਾਲਕੀ ਸਾਈਡਕਾਰ ਕੋਲ ਹੈ)।
2. ਜੇ ਸਾਈਡਕਾਰ ਦਾ Codex CLI **ਹਾਲੇ ਸਾਈਨ ਇਨ ਨਹੀਂ ਹੈ**, ਤਾਂ ਕਨੈਕਸ਼ਨ ਦੀ ਸਿਹਤ
   ਜਾਂਚ _"ਚੱਲ ਰਿਹਾ ਹੈ ਪਰ ਸਾਈਨ ਇਨ ਨਹੀਂ ਹੈ"_ ਰਿਪੋਰਟ ਕਰਦੀ ਹੈ (ਲਾਲ ਪ੍ਰਮਾਣੀਕਰਨ
   ਗਲਤੀ ਨਹੀਂ)। **ChatGPT ਨਾਲ ਸਾਈਨ ਇਨ ਕਰੋ** ਵਰਤੋ: ਇਹ ਤੁਹਾਡੇ ਬ੍ਰਾਊਜ਼ਰ ਵਿੱਚ
   ਮਿਆਰੀ Codex device-OAuth ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਫਿਰ **ਪ੍ਰਮਾਣੀਕਰਨ ਲਾਗੂ ਕਰੋ** ਰਾਹੀਂ
   `~/.codex/auth.json` ਨੂੰ ਸਾਂਝੇ ਵਾਲਿਊਮ ਵਿੱਚ ਲਿਖਦਾ ਹੈ (ਇੱਕੋ ਲੌਗਇਨ `codex`
   ਅਤੇ `codex-app-server` ਦੋਵਾਂ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ ਕੰਮ ਕਰਦਾ ਹੈ)।
3. ਸਾਈਨ ਇਨ ਹੋਣ ਤੋਂ ਬਾਅਦ, ਸਿਹਤ ਜਾਂਚ ਹਰੀ ਹੋ ਜਾਂਦੀ ਹੈ (ਇਹ `/readyz` **ਅਤੇ**
   `account/read` ਦੋਵਾਂ ਦੀ ਪੁਸ਼ਟੀ ਕਰਦੀ ਹੈ — ਅਰਥਾਤ ਚਾਲੂ _ਅਤੇ_ ਪ੍ਰਮਾਣਿਤ) ਅਤੇ
   ਕੰਮ ਕਰਨਾ ਸ਼ੁਰੂ ਕਰ ਦਿੰਦੀ ਹੈ।

ਡੈਸ਼ਬੋਰਡ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਸਿਹਤਮੰਦ `~/.codex/auth.json` ਨੂੰ ਕਦੇ ਵੀ ਓਵਰਰਾਈਟ
ਨਹੀਂ ਕਰਦਾ — ਇਹ ਸਿਰਫ਼ ਉਦੋਂ ਲਿਖਦਾ ਹੈ ਜਦੋਂ ਫ਼ਾਈਲ ਮੌਜੂਦ ਨਾ ਹੋਵੇ ਜਾਂ ਇਸਦਾ ਟੋਕਨ
ਪੁਰਾਣਾ ਹੋਵੇ (ਹਮੇਸ਼ਾ ਇੱਕ ਬੈਕਅੱਪ ਲਿਆ ਜਾਂਦਾ ਹੈ)।

## 4. ਡਿਪਲੌਇਮੈਂਟ ਸਥਿਤੀਆਂ

- **ਪਹਿਲਾਂ ਤੋਂ ਪ੍ਰਮਾਣਿਤ Codex CLI ਵਾਲਾ ਓਪਰੇਟਰ** — ਆਪਣੇ ਹੋਸਟ ਦੇ
  `~/.codex` ਨੂੰ ਸਾਈਡਕਾਰ (`codex-appserver-home`) ਵਿੱਚ ਮਾਊਂਟ ਕਰੋ ਅਤੇ ਸਾਈਨ-ਇਨ
  ਪੜਾਅ ਛੱਡ ਦਿਓ।
- **ਜਨਤਕ ਵਰਤੋਂਕਾਰ, ਸਥਾਨਕ ਤੌਰ ਉੱਤੇ codex ਇੰਸਟਾਲ ਨਹੀਂ ਹੈ** — ਕੋਈ ਫ਼ਰਕ ਨਹੀਂ
  ਪੈਂਦਾ: ਸਾਈਡਕਾਰ ਵਿੱਚ CLI ਮੌਜੂਦ ਹੈ। ਵਰਤੋਂਕਾਰ ਸਿਰਫ਼ ਡੈਸ਼ਬੋਰਡ ਰਾਹੀਂ
  ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ।
- **ਬੇਅਰ-ਮੈਟਲ OmniRoute (ਕੋਈ ਸਾਈਡਕਾਰ ਨਹੀਂ, ਹੋਸਟ codex)** — ਆਪਣੇ
  `codex app-server` ਵੱਲ `OMNIROUTE_CODEX_APPSERVER_WS` ਇਸ਼ਾਰਾ ਕਰੋ ਅਤੇ ਯਕੀਨੀ
  ਬਣਾਓ ਕਿ ਹੋਸਟ codex ਸਾਈਨ ਇਨ ਹੈ; ਜੇ ਬਾਈਨਰੀ ਮੌਜੂਦ ਨਾ ਹੋਵੇ ਤਾਂ
  "codex ਇੰਸਟਾਲ ਨਹੀਂ ਹੈ" ਸੰਕੇਤ ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ।

## 5. ਰਿਹਾਇਸ਼ੀ / UDP ਈਗ੍ਰੈੱਸ (ਓਪਰੇਟਰ ਲਈ ਵਾਧੂ, ਨਾਲ ਨਹੀਂ ਦਿੱਤਾ ਜਾਂਦਾ)

ਉਪਰੋਕਤ ਆਮ ਸਾਈਡਕਾਰ ਕੰਟੇਨਰ ਦੇ ਸਧਾਰਣ ਨੈੱਟਵਰਕ ਰਾਹੀਂ ਈਗ੍ਰੈੱਸ ਕਰਦਾ ਹੈ। ਜਿਸ
ਓਪਰੇਟਰ ਨੂੰ Codex ਟ੍ਰੈਫਿਕ ਨੂੰ **ਰਿਹਾਇਸ਼ੀ ਐਗਜ਼ਿਟ** ਰਾਹੀਂ ਬਾਹਰ ਭੇਜਣ ਦੀ ਲੋੜ ਹੈ
(ਉਦਾਹਰਨ ਲਈ TCP + UDP/QUIC ਲਿਜਾਣ ਵਾਲਾ TUN tailscale ਸਾਈਡਕਾਰ), ਉਹ ਇਸਨੂੰ ਇੱਕ
ਵੱਖਰੇ compose ਓਵਰਰਾਈਡ ਵਜੋਂ ਚਲਾਉਂਦਾ ਹੈ; ਇਸਨੂੰ ਜਾਣਬੁੱਝ ਕੇ ਨਾਲ ਦਿੱਤੇ ਗਏ
`codex-app-server` ਪ੍ਰੋਫਾਈਲ ਦਾ ਹਿੱਸਾ **ਨਹੀਂ** ਬਣਾਇਆ ਗਿਆ। ਉਸ ਸੈਟਅੱਪ ਲਈ ਅੰਦਰੂਨੀ
ਓਪਰੇਸ਼ਨ ਰਨਬੁੱਕ ਵੇਖੋ।
