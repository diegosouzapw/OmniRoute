OmniRoute ਨੂੰ OpenAI-ਅਨੁਕੂਲ ਬੈਕਐਂਡ ਵਜੋਂ ਵਰਤਣ ਲਈ Codex CLI ਦੀ ਸੰਪੂਰਨ ਗਾਈਡ।

---

> **TOML ਹੀ ਇਕੱਲਾ ਪ੍ਰਭਾਵਸ਼ਾਲੀ ਫਾਰਮੈਟ ਹੈ।** ਆਧੁਨਿਕ Codex ਸਿਰਫ਼ `~/.codex/config.toml`
> ਨੂੰ ਪੜ੍ਹਦਾ ਹੈ (codex-cli 0.147.0 ਨਾਲ ਤਸਦੀਕ ਕੀਤਾ ਗਿਆ: `codex --help`
> `-c/--config` ਓਵਰਰਾਈਡਾਂ ਨੂੰ "`~/.codex/config.toml` ਤੋਂ ਲੋਡ ਕੀਤੀਆਂ" ਵਜੋਂ ਦਰਸਾਉਂਦਾ ਹੈ)। ਪੁਰਾਣੀ
> `~/.codex/config.yaml` ਲੈਗੇਸੀ npm CLI ਨਾਲ ਸੰਬੰਧਿਤ ਸੀ ਅਤੇ ਇਸਨੂੰ ਬਿਨਾਂ ਕਿਸੇ ਸੂਚਨਾ ਦੇ ਅਣਡਿੱਠਾ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ।
> ਡੈਸ਼ਬੋਰਡ ਜਨਰੇਟਰ (`/api/cli-tools/apply`, ਟੂਲ `codex`) ਇੱਕ
> ਸੰਭਾਲੂ ਮਰਜ ਨਾਲ TOML ਲਿਖਦਾ ਹੈ — ਮੌਜੂਦਾ ਕੁੰਜੀਆਂ ਅਤੇ ਹੋਰ ਪ੍ਰਦਾਤਾ ਬਲਾਕ ਸੁਰੱਖਿਅਤ ਰਹਿੰਦੇ ਹਨ,
> API ਕੁੰਜੀ `OMNIROUTE_API_KEY` ਵਿੱਚ ਰਹਿੰਦੀ ਹੈ (ਫ਼ਾਈਲ ਵਿੱਚ ਕਦੇ ਨਹੀਂ), ਅਤੇ ਬਚੀ ਹੋਈ ਲੈਗੇਸੀ
> `config.yaml` ਨੂੰ ਛੇੜੇ ਬਿਨਾਂ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨੋਟ ਵਜੋਂ ਰਿਪੋਰਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

## ਸਿੱਧਾ ਪੇਸਟ ਕਰਨ ਲਈ ਤਿਆਰ config.toml

`<YOUR_HOST>` ਅਤੇ `<YOUR_KEY>` ਨੂੰ ਆਪਣੇ ਮੁੱਲਾਂ ਨਾਲ ਬਦਲੋ:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # ਹਰ ਟੂਲ ਕਾਲ ਲਈ ਇਤਿਹਾਸ ਸਟੋਰੇਜ ਦੀ ਹੱਦ

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc ਜਾਂ ~/.zshrc — ਅਸਲ ਕੁੰਜੀ ਮੁੱਲ, config.toml ਵਿੱਚ ਕਦੇ ਨਹੀਂ
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT ਐਪ ਦੇ ਅੰਦਰ ਬੰਡਲ ਕੀਤਾ Codex

ਜੇ ਤੁਸੀਂ ChatGPT ਡੈਸਕਟਾਪ ਐਪ ਰਾਹੀਂ Codex ਇੰਸਟਾਲ ਕੀਤਾ ਹੈ, ਤਾਂ `codex` ਬਾਈਨਰੀ
ਸਿਰਫ਼ ਐਪ ਬੰਡਲ ਦੇ ਅੰਦਰ ਮੌਜੂਦ ਹੋ ਸਕਦੀ ਹੈ ਅਤੇ ਹਾਲੇ ਤੁਹਾਡੇ ਸ਼ੈੱਲ `PATH` ਵਿੱਚ ਨਾ ਹੋਵੇ। ਆਪਣੇ
ਸ਼ੈੱਲ ਸਟਾਰਟਅੱਪ ਫ਼ਾਈਲ ਵਿੱਚ ਰਿਸੋਰਸ ਡਾਇਰੈਕਟਰੀ ਸ਼ਾਮਲ ਕਰੋ:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

ਇੱਕ ਨਵਾਂ ਸ਼ੈੱਲ ਖੋਲ੍ਹੋ, ਫਿਰ ਤਸਦੀਕ ਕਰੋ:

```bash
command -v codex
codex --version
```

### ਸਥਾਨਕ ਬਿਨਾਂ ਪ੍ਰਮਾਣੀਕਰਨ ਵਾਲਾ OmniRoute: ਪਲੇਸਹੋਲਡਰ ਕੁੰਜੀ ਕਾਫ਼ੀ ਹੈ

Codex ਪਹਿਲੀ ਬੇਨਤੀ ਦੇ CLI ਤੋਂ ਬਾਹਰ ਜਾਣ **ਤੋਂ ਪਹਿਲਾਂ** ਤਸਦੀਕ ਕਰਦਾ ਹੈ ਕਿ `env_key`
ਦੁਆਰਾ ਦਰਸਾਇਆ ਗਿਆ ਵਾਤਾਵਰਣ ਵੇਰੀਏਬਲ ਮੌਜੂਦ ਹੈ। ਜੇ ਤੁਹਾਡੀ **ਸਥਾਨਕ** OmniRoute
ਇੰਸਟੈਂਸ ਨੂੰ ਪ੍ਰਮਾਣੀਕਰਨ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ, ਤਾਂ ਕੋਈ ਵੀ ਗੈਰ-ਖਾਲੀ ਪਲੇਸਹੋਲਡਰ ਕੰਮ ਕਰੇਗਾ:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

ਜਦੋਂ ਤੁਹਾਡਾ OmniRoute ਸਰਵਰ ਸੁਰੱਖਿਅਤ ਜਾਂ ਰਿਮੋਟ ਹੋਵੇ, ਤਾਂ ਇਸਦੀ ਬਜਾਏ ਅਸਲ ਕੁੰਜੀ ਵਰਤੋ।

> **ਆਮ ਹੋਸਟ ਵਿਕਲਪ**
>
> | ਪਹੁੰਚ         | URL                           |
> | ------------- | ----------------------------- |
> | ਸਥਾਨਕ ਨੈੱਟਵਰਕ | `http://192.168.0.1:20128/v1` |
> | Tailscale     | `http://100.x.x.x:20128/v1`   |
> | ਲੂਪਬੈਕ        | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — ਇਹ ਸਾਰੇ ਮਾਡਲਾਂ ਲਈ ਕਿਉਂ ਕੰਮ ਕਰਦਾ ਹੈ

Codex CLI ਨੇ ਫ਼ਰਵਰੀ 2026 ਵਿੱਚ `wire_api = "chat"` (Chat Completions) ਨੂੰ ਗੈਰ-ਪ੍ਰਚਲਿਤ ਕਰ ਦਿੱਤਾ ਸੀ ਅਤੇ ਹੁਣ `wire_api = "responses"` (OpenAI Responses API) ਦੀ **ਲੋੜ** ਹੈ। v0.138 ਤੋਂ `wire_api = "chat"` ਸੈੱਟ ਕਰਨ ਨਾਲ ਸਟਾਰਟਅੱਪ ਦੌਰਾਨ ਤੁਰੰਤ ਕ੍ਰੈਸ਼ ਹੋ ਜਾਂਦਾ ਹੈ।

GLM ਅਤੇ Kimi ਸਮੇਤ ਕਈ ਪ੍ਰਦਾਤਾ ਅਜੇ ਵੀ ਸਿਰਫ਼ Chat Completions ਐਂਡਪੌਇੰਟ ਹੀ ਉਪਲਬਧ ਕਰਵਾਉਂਦੇ ਹਨ। DeepSeek V4 ਹੁਣ Anthropic-ਅਨੁਕੂਲ ਐਂਡਪੌਇੰਟ ਦੇ ਨਾਲ ਇੱਕ ਮੂਲ Responses API ਵੀ ਉਪਲਬਧ ਕਰਵਾਉਂਦਾ ਹੈ; OmniRoute ਮੂਲ ਰੂਪ ਵਿੱਚ Responses ਵਰਤਦਾ ਹੈ ਅਤੇ ਹਰ DeepSeek ਕਨੈਕਸ਼ਨ ਨੂੰ Anthropic ਅਨੁਕੂਲਤਾ ਚੁਣਨ ਦਿੰਦਾ ਹੈ।

**OmniRoute ਇਸਨੂੰ ਪਾਰਦਰਸ਼ੀ ਢੰਗ ਨਾਲ ਹੱਲ ਕਰਦਾ ਹੈ:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute ਪ੍ਰਦਾਤਾ ਦਾ ਮੂਲ ਪ੍ਰੋਟੋਕੋਲ ਚੁਣਦਾ ਹੈ ਅਤੇ ਲੋੜ ਪੈਣ 'ਤੇ ਅਨੁਵਾਦ ਕਰਦਾ ਹੈ
    → POST /responses (DeepSeek V4) ਜਾਂ /chat/completions (Mistral / GLM / Kimi / ਹੋਰ)
```

OmniRoute ਵਰਤਦੇ ਸਮੇਂ ਤੁਹਾਨੂੰ ਕਦੇ ਵੀ ਵੱਖਰੇ ਅਨੁਵਾਦ ਪ੍ਰੌਕਸੀ ਦੀ ਲੋੜ ਨਹੀਂ ਪੈਂਦੀ। **ਸਾਰੇ ਮਾਡਲ `wire_api = "responses"` ਵਰਤਦੇ ਹਨ** — ਬਾਕੀ ਸਭ OmniRoute ਸੰਭਾਲਦਾ ਹੈ।

> **`wire_api` ਡਿਫਾਲਟ ਹੈ** — ਇਹ ਫ਼ੀਲਡ ਡਿਫਾਲਟ ਤੌਰ 'ਤੇ `"responses"` ਹੁੰਦੀ ਹੈ ਅਤੇ ਇਸਨੂੰ `config.toml` ਵਿੱਚੋਂ ਪੂਰੀ ਤਰ੍ਹਾਂ ਹਟਾਇਆ ਜਾ ਸਕਦਾ ਹੈ। ਇਸਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਸਿਰਫ਼ ਉਦੋਂ ਹੀ ਸੈੱਟ ਕਰੋ ਜਦੋਂ ਤੁਸੀਂ ਮਕਸਦ ਦਾ ਦਸਤਾਵੇਜ਼ੀਕਰਨ ਕਰ ਰਹੇ ਹੋ।

## ਸੰਦਰਭ ਵਿੰਡੋ ਅਤੇ ਸੰਕੁਚਨ

### ਟੋਕਨ ਸੰਰਚਨਾ ਫ਼ੀਲਡ

| ਫ਼ੀਲਡ                            | ਵੇਰਵਾ                                                                                                                                                                                        |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | ਸਰਗਰਮ ਮਾਡਲ ਲਈ ਕੁੱਲ ਟੋਕਨ ਬਜਟ। ਇਸਨੂੰ ਮਾਡਲ ਦੀ ਪ੍ਰਚਾਰਿਤ ਸੀਮਾ 'ਤੇ ਸੈੱਟ ਕਰੋ।                                                                                                                       |
| `model_auto_compact_token_limit` | ਉਹ ਥ੍ਰੈਸ਼ਹੋਲਡ ਜੋ ਇਤਿਹਾਸ ਦੇ ਆਟੋਮੈਟਿਕ ਸੰਕੁਚਨ ਨੂੰ ਚਾਲੂ ਕਰਦਾ ਹੈ। **ਅਧਿਕਤਮ: `model_context_window` ਦਾ 90%** — 90% ਤੋਂ ਵੱਧ ਮੁੱਲਾਂ ਨੂੰ ਬਿਨਾਂ ਸੂਚਨਾ ਦਿੱਤੇ ਅਣਡਿੱਠਾ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ।                 |
| `tool_output_token_limit`        | ਇਤਿਹਾਸ ਵਿੱਚ ਪ੍ਰਤੀ ਟੂਲ ਕਾਲ ਆਉਟਪੁੱਟ ਸਟੋਰ ਕੀਤੇ ਜਾਣ ਵਾਲੇ ਟੋਕਨਾਂ ਦੀ ਸੀਮਾ। ਇਹ ਕਿਸੇ ਇੱਕ ਵੱਡੇ ਟੂਲ ਜਵਾਬ ਨੂੰ ਪੂਰੀ ਵਿੰਡੋ ਭਰਨ ਤੋਂ ਰੋਕਦਾ ਹੈ। **ਇਹ ਅਧਿਕਤਮ ਆਉਟਪੁੱਟ ਨਹੀਂ ਹੈ** — ਇਹ ਇਤਿਹਾਸ ਸਟੋਰੇਜ ਦੀ ਸੀਮਾ ਹੈ। |
| `compact_prompt`                 | ਸੰਕੁਚਨ ਦੌਰਾਨ ਵਰਤੇ ਜਾਣ ਵਾਲੇ ਸਿਸਟਮ ਪ੍ਰੌਂਪਟ ਲਈ ਇਨਲਾਈਨ ਓਵਰਰਾਈਡ (v0.138+)।                                                                                                                        |

> **`model_max_output_tokens` ਬਾਰੇ ਨੋਟ**: ਇਹ ਫ਼ੀਲਡ **Codex CLI ਸੰਰਚਨਾ ਸਕੀਮਾ ਦਾ ਹਿੱਸਾ ਨਹੀਂ ਹੈ** (Codex Rust ਕੋਡਬੇਸ ਵਿੱਚ ਮੌਜੂਦ ਨਹੀਂ)। ਜੇ ਇਸਨੂੰ ਸੈੱਟ ਕੀਤਾ ਜਾਵੇ, ਤਾਂ ਬਿਨਾਂ ਸੂਚਨਾ ਦਿੱਤੇ ਇਸਨੂੰ ਅਣਡਿੱਠਾ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ। ਇਸ 'ਤੇ ਨਿਰਭਰ ਨਾ ਕਰੋ — ਇਤਿਹਾਸ ਵਿੱਚ ਸਟੋਰ ਕੀਤੇ ਜਾਣ ਵਾਲੇ ਟੂਲ ਆਉਟਪੁੱਟ ਦੀ ਮਾਤਰਾ ਨੂੰ ਨਿਯੰਤਰਿਤ ਕਰਨ ਲਈ `tool_output_token_limit` ਦੀ ਵਰਤੋਂ ਕਰੋ।

### ਮਾਡਲ ਅਨੁਸਾਰ ਸੰਦਰਭ ਵਿੰਡੋ

| ਮਾਡਲ                                 | OmniRoute ID                         | ਸੰਦਰਭ ਵਿੰਡੋ               | `auto_compact` | `tool_output_limit` |

## ਤਰਕ ਕਰਨ ਦੀ ਮਿਹਨਤ

ਇਹ ਨਿਯੰਤਰਿਤ ਕਰਦਾ ਹੈ ਕਿ ਜਵਾਬ ਦੇਣ ਤੋਂ ਪਹਿਲਾਂ ਮਾਡਲ ਕਿੰਨਾ "ਸੋਚਦਾ" ਹੈ।

| ਮੁੱਲ     | ਇਸ ਲਈ ਵਰਤੋ                                 |
| -------- | ------------------------------------------ |
| `none`   | ਕੋਈ ਤਰਕ ਨਹੀਂ — ਸਿੱਧਾ ਜਵਾਬ                  |
| `low`    | ਬਹੁਤ ਸਧਾਰਨ ਕੰਮ (ਨਾਂ ਬਦਲਣਾ, ਫਾਰਮੈਟ ਕਰਨਾ)    |
| `medium` | ਨਾ ਦਿੱਤੇ ਜਾਣ 'ਤੇ **ਸਰਵਰ ਡਿਫਾਲਟ**           |
| `high`   | ਦਰਮਿਆਨੇ ਕੰਮ (ਰੀਫੈਕਟਰਿੰਗ, ਡੀਬੱਗਿੰਗ)         |
| `xhigh`  | ਆਰਕੀਟੈਕਚਰ, ਡੂੰਘਾ ਵਿਸ਼ਲੇਸ਼ਣ, ਜਟਿਲ ਸਮੱਸਿਆਵਾਂ |

```bash
# ਹਰ invocation ਲਈ override
codex -c model_reasoning_effort=low "ਵੇਰੀਏਬਲ x ਦਾ ਨਾਂ ਬਦਲ ਕੇ count ਕਰੋ"
codex -c model_reasoning_effort=xhigh "auth ਮੋਡੀਊਲ ਡਿਜ਼ਾਈਨ ਕਰੋ"
```

ਤਰਕ ਕਰਨ ਦਾ ਇੱਕ **ਸੰਖੇਪ** ਵੀ ਸੈੱਟ ਕਰੋ ਤਾਂ ਜੋ Desktop ਸੋਚਣ ਵਾਲਾ ਟੈਕਸਟ ਰੈਂਡਰ ਕਰ ਸਕੇ (ਸਿਰਫ਼ ਇਨਕ੍ਰਿਪਟ ਕੀਤੇ blobs ਨਹੀਂ):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # ਜਾਂ ਸਮਰਥਿਤ ਹੋਣ 'ਤੇ ultra
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute ਸੋਚਣ ਦਾ ਬਜਟ (ਸਰਵਰ ਸੈਟਿੰਗ)

OmniRoute ਹੋਸਟ ਉੱਤੇ, Codex ਦੀ ਮਿਹਨਤ/ਸੰਖੇਪ ਨੂੰ upstream ਤੱਕ ਪਹੁੰਚਾਉਣ ਲਈ **Settings → AI → Thinking Budget** ਦਾ **`passthrough`** ਹੋਣਾ ਲਾਜ਼ਮੀ ਹੈ। **`auto` ਮੋਡ** ਸਾਰੇ ਕਲਾਇੰਟ `reasoning` / `reasoning_effort` ਫੀਲਡ ਹਟਾ ਦਿੰਦਾ ਹੈ ਅਤੇ Codex ਠੀਕ ਤਰ੍ਹਾਂ ਕਨਫਿਗਰ ਕੀਤਾ ਹੋਣ ਦੇ ਬਾਵਜੂਦ ਸੋਚਣ ਵਾਲੇ ਪੈਨਲ ਖਾਲੀ ਕਰ ਦੇਵੇਗਾ।

ਪੂਰੀ ਗਾਈਡ: [THINKING_BUDGET.md](./THINKING_BUDGET.md)।

ਕੰਪ੍ਰੈਸ਼ਨ ਅਤੇ ਪ੍ਰੌਂਪਟ ਕੈਸ਼ ਇੱਕ-ਦੂਜੇ ਤੋਂ ਸੁਤੰਤਰ ਹਨ ਅਤੇ `passthrough` ਅਧੀਨ ਕੰਮ ਕਰਦੇ ਰਹਿੰਦੇ ਹਨ।

## `omniroute setup-codex` ਨਾਲ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਆਪਣੇ-ਆਪ ਬਣਾਉਣਾ

ਜੇ ਤੁਸੀਂ OmniRoute ਨੂੰ ਕਿਸੇ VPS ਉੱਤੇ ਚਲਾਉਂਦੇ ਹੋ, ਤਾਂ ਤੁਸੀਂ ਲਾਈਵ ਮਾਡਲ ਕੈਟਾਲਾਗ ਤੋਂ ਪ੍ਰੋਫ਼ਾਈਲ ਫ਼ਾਈਲਾਂ ਆਪਣੇ-ਆਪ ਬਣਾ ਸਕਦੇ ਹੋ:

```bash
# ਕਿਸੇ VPS ਤੋਂ (ਪੋਰਟ 20128 ਉੱਤੇ ਸਥਾਨਕ OmniRoute ਵਰਤਦਾ ਹੈ)
omniroute setup-codex

# ਕਿਸੇ ਵੀ ਮਸ਼ੀਨ ਤੋਂ — ਆਪਣੇ VPS ਵੱਲ ਇਸ਼ਾਰਾ ਕਰੋ
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# ਫ਼ਾਈਲਾਂ ਲਿਖੇ ਬਿਨਾਂ ਝਲਕ ਵੇਖੋ
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# ਸਿਰਫ਼ GLM ਅਤੇ Kimi ਪ੍ਰੋਫ਼ਾਈਲ ਬਣਾਓ
omniroute setup-codex --only glm,kimi

# ਕਿਸੇ ਕਸਟਮ ਡਾਇਰੈਕਟਰੀ ਵਿੱਚ ਲਿਖੋ
omniroute setup-codex --codex-home /path/to/.codex
```

ਇਹ ਕਮਾਂਡ `/v1/models` ਪ੍ਰਾਪਤ ਕਰਦੀ ਹੈ, ਜਾਣੇ-ਪਛਾਣੇ ਮਾਡਲਾਂ ਲਈ ਟਿਊਨ ਕੀਤੀਆਂ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਵਰਤਦੀ ਹੈ, ਹੋਰ ਅਨੁਕੂਲ ਟੈਕਸਟ ਮਾਡਲਾਂ ਲਈ ਕੈਟਾਲਾਗ ਮੈਟਾਡੇਟਾ ਉੱਤੇ ਨਿਰਭਰ ਕਰਦੀ ਹੈ, ਅਤੇ ਹਰੇਕ ਲਈ `~/.codex/<name>.config.toml` ਲਿਖਦੀ ਹੈ। ਇਹ ਇਡੈਂਪੋਟੈਂਟ ਹੈ — ਇਸਨੂੰ ਦੁਬਾਰਾ ਚਲਾਉਣਾ ਸੁਰੱਖਿਅਤ ਹੈ।

ਸਫਲ ਪ੍ਰੋਵਾਈਡਰ ਮਾਡਲ ਖੋਜ/ਇੰਪੋਰਟ ਦੁਆਰਾ ਲਾਈਵ ਕੈਟਾਲਾਗ ਵਿੱਚ ਤਬਦੀਲੀ ਕੀਤੇ ਜਾਣ ਤੋਂ ਬਾਅਦ OmniRoute ਇਨ੍ਹਾਂ ਪ੍ਰੋਫ਼ਾਈਲ ਫ਼ਾਈਲਾਂ ਨੂੰ **ਆਪਣੇ-ਆਪ ਸਿੰਕ** ਵੀ ਕਰ ਸਕਦਾ ਹੈ। ਇਹ **ਵਿਕਲਪਿਕ ਹੈ ਅਤੇ ਮੂਲ ਰੂਪ ਵਿੱਚ ਬੰਦ ਹੈ**: ਇਸਨੂੰ **CLI Code ਡੈਸ਼ਬੋਰਡ** ("CLI profile auto-sync" → Codex) ਤੋਂ ਚਾਲੂ ਕਰੋ, ਜਾਂ `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` ਸੈੱਟ ਕਰੋ (ਇਹ `CLI_ALLOW_CONFIG_WRITES` ਦਾ ਵੀ ਸਤਿਕਾਰ ਕਰਦਾ ਹੈ, ਜੋ ਮੂਲ ਰੂਪ ਵਿੱਚ ਚਾਲੂ ਹੈ)। ਚਾਲੂ ਹੋਣ ਉੱਤੇ ਇਹ ਸਿਰਫ਼ ਵੱਖਰੀਆਂ `~/.codex/*.config.toml` ਪ੍ਰੋਫ਼ਾਈਲ ਫ਼ਾਈਲਾਂ ਲਿਖਦਾ ਹੈ; ਇਹ ਸਰਗਰਮ/ਡਿਫ਼ਾਲਟ `~/.codex/config.toml`, Codex-lb ਸੈਟਿੰਗਾਂ, ਪ੍ਰਮਾਣੀਕਰਨ ਜਾਂ ਪ੍ਰੋਵਾਈਡਰ ਚੋਣ ਨੂੰ ਕਦੇ ਨਹੀਂ ਬਦਲਦਾ।

## `omniroute launch-codex` ਨਾਲ Codex ਲਾਂਚ ਕਰਨਾ

Codex ਨੂੰ ਲਾਂਚ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਤੁਹਾਡੀ OmniRoute ਇੰਸਟੈਂਸ ਦੀ ਸਿਹਤ ਜਾਂਚ ਕਰਦਾ ਹੈ:

omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# ਵਾਧੂ ਆਰਗੂਮੈਂਟ codex ਨੂੰ ਪਾਸ ਕਰੋ
omniroute launch-codex --profile glm52 -- --yolo "fix this bug"

Codex ਦੋ ਆਮ ਮੈਨੀਫੈਸਟ-ਸੰਚਾਲਿਤ ਐਂਟਰੀ ਪੁਆਇੰਟਾਂ ਦਾ ਵੀ ਇੱਕ ਟਾਰਗੇਟ ਹੈ
(`bin/cli/cli-manifest.mjs`):

# ਇੰਟਰਐਕਟਿਵ ਮਾਡਲ ਚੋਣਕਾਰ → ~/.codex/<name>.config.toml ਲਿਖਦਾ ਹੈ (TOML, env_key)

## ਲੰਬੇ ਸਮੇਂ ਤੱਕ ਚੱਲਣ ਵਾਲੇ ਕੰਮ

OmniRoute ਦੀਆਂ ਦੋ ਡਿਫਾਲਟ ਸੈਟਿੰਗਾਂ ਕਈ ਘੰਟਿਆਂ ਤੱਕ ਚੱਲਣ ਵਾਲੇ Codex CLI ਸੈਸ਼ਨਾਂ ਨੂੰ ਚੁੱਪਚਾਪ ਵਿਗਾੜ ਸਕਦੀਆਂ ਹਨ। ਇਨ੍ਹਾਂ ਵਿੱਚੋਂ ਕੋਈ ਵੀ Codex CLI ਸੈਟਿੰਗ ਨਹੀਂ ਹੈ — ਦੋਵੇਂ OmniRoute ਵਾਲੇ ਪਾਸੇ ਮੌਜੂਦ ਹਨ। ਉਹ ਵਰਤੋਂਕਾਰ ਜੋ ਅਜਿਹੀਆਂ ਅੱਪਸਟ੍ਰੀਮ ਪ੍ਰੌਕਸੀਆਂ ਤੋਂ ਸੰਰਚਨਾ ਮਾਈਗ੍ਰੇਟ ਕਰਦੇ ਹਨ ਜਿਹੜੀਆਂ ਖਾਤਿਆਂ ਨੂੰ ਪਿੰਨ ਕਰਦੀਆਂ ਅਤੇ ਨਿਸ਼ਕਿਰਿਆਤਾ ਕਟੌਤੀਆਂ ਨੂੰ ਅਸਮਰੱਥ ਕਰਦੀਆਂ ਹਨ, ਅਕਸਰ ਦੋਵਾਂ ਸਮੱਸਿਆਵਾਂ ਦਾ ਸਾਹਮਣਾ ਕਰਦੇ ਹਨ ਅਤੇ ਇਹ ਨਤੀਜਾ ਕੱਢਦੇ ਹਨ ਕਿ OmniRoute “ਲੰਬੇ ਸੈਸ਼ਨ ਨੂੰ ਜਾਰੀ ਨਹੀਂ ਰੱਖ ਸਕਦਾ।”

| ਲੱਛਣ                                                                                        | ਸੰਭਾਵਿਤ ਕਾਰਨ                                                               | ਕੰਟਰੋਲ                   |
| ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------ |
| ਸੈਸ਼ਨ ਲਗਾਤਾਰ ਖਾਤੇ ਬਦਲਦਾ ਰਹਿੰਦਾ ਹੈ / ਵਾਰੀ-ਵਾਰੀ ਦਰਮਿਆਨ ਪ੍ਰੌਮਪਟ-ਕੈਸ਼ ਨਿਰੰਤਰਤਾ ਖਤਮ ਹੋ ਜਾਂਦੀ ਹੈ  | ਸੈਸ਼ਨ ਐਫਿਨਿਟੀ TTL `0` ਹੈ (ਅਸਮਰੱਥ)                                          | `sessionAffinityTtlMs`   |
| ਕਲਾਇੰਟ ਨੂੰ ਦਿਖਾਈ ਦੇਣ ਵਾਲੇ ਕਿਸੇ ਪ੍ਰੌਮਪਟ ਤੋਂ ਬਿਨਾਂ ਰੀਜ਼ਨਿੰਗ ਦੇ ਵਿਚਕਾਰ ਕਨੈਕਸ਼ਨ ਬੰਦ ਹੋ ਜਾਂਦਾ ਹੈ | ਅੱਪਸਟ੍ਰੀਮ ਚੰਕ ਨਾ ਆਉਣ ਦੇ 10 ਮਿੰਟ ਬਾਅਦ ਸਟ੍ਰੀਮ ਨਿਸ਼ਕਿਰਿਆਤਾ ਵਾਚਡੌਗ ਚਾਲੂ ਹੋ ਗਿਆ | `STREAM_IDLE_TIMEOUT_MS` |

ਸੰਬੰਧਿਤ ਚਰਚਾਵਾਂ: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (ਲੰਬੇ ਕੰਮ ਦਾ ਡਿਸਕਨੈਕਟ ਹੋਣਾ), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (ਐਫਿਨਿਟੀ ਡਿਫਾਲਟ ਰੂਪ ਵਿੱਚ ਬੰਦ ਕਿਉਂ ਹੈ)। ਟ੍ਰੈਕਿੰਗ: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287)।

### 1. ਸੈਸ਼ਨ ਐਫਿਨਿਟੀ — ਇੱਕ ਗੱਲਬਾਤ ਨੂੰ ਇੱਕ ਖਾਤੇ ਨਾਲ ਪਿੰਨ ਕਰੋ

**ਡਿਫਾਲਟ:** `sessionAffinityTtlMs = 0` (ਅਸਮਰੱਥ)।

**ਇਸਨੂੰ ਕਿੱਥੇ ਸੈੱਟ ਕਰਨਾ ਹੈ**

- ਡੈਸ਼ਬੋਰਡ → **ਸੈਟਿੰਗਾਂ → ਰਾਊਟਿੰਗ** → **ਸੈਸ਼ਨ ਐਫਿਨਿਟੀ** → **ਐਫਿਨਿਟੀ TTL (ਸਕਿੰਟ)** (`ComboDefaultsTab`)
- ਜਾਂ **ਮਿਲੀਸਕਿੰਟਾਂ** ਵਿੱਚ `sessionAffinityTtlMs` ਨਾਲ ਸੈਟਿੰਗਾਂ ਨੂੰ PATCH ਕਰੋ (Zod ਰੇਂਜ `0`–`86_400_000`, ਭਾਵ 24 ਘੰਟਿਆਂ ਤੱਕ)

> #7274 ਵਿੱਚ ਇਸਦਾ ਨਾਮ ਸਿਰਫ਼ Codex ਲਈ ਵਰਤੇ ਜਾਂਦੇ `codexSessionAffinityTtlMs` ਤੋਂ ਬਦਲਿਆ ਗਿਆ। ਪੁਰਾਣੀ ਕੁੰਜੀ ਹਾਲੇ ਵੀ ਸਿਰਫ਼-ਪੜ੍ਹਨਯੋਗ ਉਪਨਾਮ ਵਜੋਂ ਸਵੀਕਾਰ ਕੀਤੀ ਜਾਂਦੀ ਹੈ; ਨਵੀਆਂ ਸੰਰਚਨਾਵਾਂ ਨੂੰ `sessionAffinityTtlMs` ਵਰਤਣਾ ਚਾਹੀਦਾ ਹੈ। ਹੁਣ TTL ਦੇ `0` ਤੋਂ ਵੱਧ ਹੋਣ 'ਤੇ ਐਫਿਨਿਟੀ ਸਿਰਫ਼ Codex ਹੀ ਨਹੀਂ, ਬਲਕਿ **ਕਿਸੇ ਵੀ** ਪ੍ਰਦਾਤਾ 'ਤੇ ਲਾਗੂ ਹੁੰਦੀ ਹੈ — [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → ਸੈਸ਼ਨ ਐਫਿਨਿਟੀ ਵੇਖੋ।

**ਇਸਦੇ 0 'ਤੇ ਰਹਿਣ ਨਾਲ ਕੀ ਵਿਗੜਦਾ ਹੈ**

ਕਈ ਵਾਰੀਆਂ ਵਾਲੀ Codex ਗੱਲਬਾਤ ਦੀ ਹਰ ਵਾਰੀ ਨੂੰ ਸਰਗਰਮ ਕੌਂਬੋ ਰਣਨੀਤੀ ਦੁਆਰਾ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਰੂਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ ਉਹ **ਹਰ ਵਾਰੀ ਇੱਕ ਵੱਖਰੇ ਖਾਤੇ** 'ਤੇ ਪਹੁੰਚ ਸਕਦੀ ਹੈ। ਇਸ ਨਾਲ ਅੱਪਸਟ੍ਰੀਮ ਸੈਸ਼ਨ / ਪ੍ਰੌਮਪਟ-ਕੈਸ਼ ਨਿਰੰਤਰਤਾ ਟੁੱਟ ਜਾਂਦੀ ਹੈ। OmniRoute ਸਿਰਫ਼ ਉਦੋਂ ਹੀ Codex ਸੈਸ਼ਨ ਹੈਡਰਾਂ (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) ਅਤੇ `prompt_cache_key` / `session_id` ਵਰਗੇ ਬੌਡੀ ਖੇਤਰਾਂ ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ, ਜਦੋਂ TTL `0` ਤੋਂ ਵੱਧ ਹੁੰਦਾ ਹੈ (`src/sse/services/auth.ts` ਵਿੱਚ `extractSessionAffinityKey`)।

**ਕਈ ਘੰਟਿਆਂ ਦੇ ਇੱਕੋ ਕੰਮ ਲਈ ਸਿਫ਼ਾਰਸ਼**

TTL ਨੂੰ **ਕੰਮ ਦੀ ਅਨੁਮਾਨਿਤ ਅਸਲ ਸਮਾਂ-ਅਵਧੀ ਤੋਂ ਵੱਧ** ਸੈੱਟ ਕਰੋ (UI ਦੀ ਵੱਧ ਤੋਂ ਵੱਧ ਸੀਮਾ **86400 ਸਕਿੰਟ** = 24 ਘੰਟੇ ਹੈ):

| ਕੰਮ ਦੀ ਅਨੁਮਾਨਿਤ ਮਿਆਦ | ਐਫਿਨਿਟੀ TTL (UI, ਸਕਿੰਟ)        | `sessionAffinityTtlMs` |
| -------------------- | ------------------------------ | ---------------------- |
| ਕੁਝ ਘੰਟੇ             | `14400` (4 ਘੰਟੇ)               | `14400000`             |
| ਰਾਤ ਭਰ / ~12 ਘੰਟੇ    | `43200` (12 ਘੰਟੇ)              | `43200000`             |
| ਪੂਰਾ ਦਿਨ             | `86400` (24 ਘੰਟੇ, ਵੱਧ ਤੋਂ ਵੱਧ) | `86400000`             |

ਚੋਣ ਕਰਕੇ ਸਮਰੱਥ ਕਰਨਾ ਜਾਣਬੁੱਝ ਕੇ ਰੱਖਿਆ ਗਿਆ ਹੈ: ਐਫਿਨਿਟੀ ਨੂੰ ਅਸਮਰੱਥ ਕਰਨਾ ਖਾਤਿਆਂ ਦਰਮਿਆਨ ਲੋਡ-ਬੈਲੈਂਸਿੰਗ ਨੂੰ ਤਰਜੀਹ ਦਿੰਦਾ ਹੈ; ਇਸਨੂੰ ਸਮਰੱਥ ਕਰਨਾ ਇੱਕ ਲੰਬੇ ਏਜੰਟ ਸੈਸ਼ਨ ਦੀ ਨਿਰੰਤਰਤਾ ਨੂੰ ਤਰਜੀਹ ਦਿੰਦਾ ਹੈ। ਇਹ ਗਾਈਡ ਡਿਫਾਲਟ ਨੂੰ **ਨਹੀਂ** ਬਦਲਦੀ — ਲੰਬੇ Codex ਕੰਮ ਚਲਾਉਣ ਵਾਲੇ ਓਪਰੇਟਰਾਂ ਨੂੰ ਇਸਨੂੰ ਖੁਦ ਸਮਰੱਥ ਕਰਨਾ ਪਵੇਗਾ।

### 2. ਸਟ੍ਰੀਮ ਨਿਸ਼ਕਿਰਿਆਤਾ ਟਾਈਮਆਉਟ — ਸ਼ਾਂਤ ਰੀਜ਼ਨਿੰਗ ਵਾਰੀਆਂ ਨੂੰ ਬੰਦ ਨਾ ਕਰੋ

**ਡਿਫਾਲਟ:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 ਮਿੰਟ)। ਜਦੋਂ ਇਹ ਸੈੱਟ ਨਾ ਹੋਵੇ ਤਾਂ ਇਹ `REQUEST_TIMEOUT_MS` ਤੋਂ ਮੁੱਲ ਲੈਂਦਾ ਹੈ; ਸਾਂਝੀ ਬੇਸਲਾਈਨ ਵੀ 600000 ਹੈ। [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → ਟਾਈਮਆਉਟ ਵੇਖੋ।

**ਡਿਫਾਲਟ 'ਤੇ ਕੀ ਵਿਗੜਦਾ ਹੈ**

ਇੱਕ Codex reasoning / tool turn ਜੋ **ਕਿਸੇ ਅਸਲ upstream chunk ਤੋਂ ਬਿਨਾਂ** 10 ਮਿੰਟ ਤੋਂ ਵੱਧ ਚੁੱਪ ਰਹਿੰਦਾ ਹੈ, ਉਸਨੂੰ SSE idle watchdog (`open-sse/utils/stream.ts`) ਵੱਲੋਂ ਜ਼ਬਰਦਸਤੀ ਬੰਦ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ। ਕਲਾਇੰਟ ਨੂੰ ਅਕਸਰ ਸਿਰਫ਼ ਕਨੈਕਸ਼ਨ ਡ੍ਰੌਪ ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ — ਜੋ “ਬਿਨਾਂ ਕਿਸੇ ਸੂਚਨਾ ਦੇ ਆਪਣੇ ਆਪ ਰੁਕ ਗਿਆ” ਨਾਲ ਮੇਲ ਖਾਂਦਾ ਹੈ।

ਮਹੱਤਵਪੂਰਨ ਵੇਰਵਾ: OmniRoute ਦਾ synthetic SSE **heartbeat idle clock ਨੂੰ ਰੀਸੈੱਟ ਨਹੀਂ ਕਰਦਾ**। ਸਿਰਫ਼ ਇੱਕ ਅਸਲ upstream body chunk ਹੀ `lastChunkTime` ਨੂੰ ਅੱਪਡੇਟ ਕਰਦਾ ਹੈ। ਇੱਕ ਸ਼ਾਂਤ ਮਾਡਲ ਜੋ ਅਜੇ ਵੀ “ਸੋਚ” ਰਿਹਾ ਹੈ, watchdog ਦੇ ਨਜ਼ਰੀਏ ਤੋਂ ਰੁਕੇ ਹੋਏ upstream ਵਰਗਾ ਹੀ ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ।

ਸੰਬੰਧਿਤ Undici body inactivity: `FETCH_BODY_TIMEOUT_MS` (ਇਹ ਵੀ ਮੂਲ ਰੂਪ ਵਿੱਚ ਉਸੇ 10-ਮਿੰਟ baseline 'ਤੇ ਸੈੱਟ ਹੁੰਦਾ ਹੈ; `0` ਇਸਨੂੰ ਅਯੋਗ ਕਰਦਾ ਹੈ)। Streaming ਲਈ, `FETCH_TIMEOUT_MS` ਸਿਰਫ਼ ਕਨੈਕਸ਼ਨ ਸੈੱਟਅੱਪ / ਪਹਿਲੇ headers ਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ — stream ਸਰਗਰਮ ਹੋਣ ਤੋਂ ਬਾਅਦ, ਰੁਕਾਵਟਾਂ ਨੂੰ `STREAM_IDLE_TIMEOUT_MS` ਅਤੇ `FETCH_BODY_TIMEOUT_MS` ਵੱਲੋਂ ਨਿਯੰਤਰਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

**ਕਈ ਘੰਟਿਆਂ ਦੇ ਇੱਕੋ task ਲਈ ਸਿਫ਼ਾਰਸ਼**

OmniRoute process environment (`.env` / compose / systemd) ਵਿੱਚ:

```bash
# ਲੰਬੇ reasoning turns ਲਈ stream idle + body inactivity cutoffs ਨੂੰ ਅਯੋਗ ਕਰੋ
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

ਜਾਂ ਇਨ੍ਹਾਂ ਨੂੰ ਤੁਹਾਡੇ ਵੱਲੋਂ ਉਮੀਦ ਕੀਤੇ ਸਭ ਤੋਂ ਲੰਬੇ ਸ਼ਾਂਤ ਅੰਤਰਾਲ ਤੋਂ ਵੱਧ ਸੈੱਟ ਕਰੋ (ਮੁੱਲ milliseconds ਵਿੱਚ ਹਨ):

```bash
# ਉਦਾਹਰਨ: upstream chunks ਵਿਚਕਾਰ 2 ਘੰਟਿਆਂ ਤੱਕ ਦੀ ਚੁੱਪ ਦੀ ਆਗਿਆ ਦਿਓ
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

ਇਨ੍ਹਾਂ env vars ਨੂੰ ਬਦਲਣ ਤੋਂ ਬਾਅਦ OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ।

### ਠੋਸ ਵਿਧੀ — ਕਈ ਘੰਟਿਆਂ ਦਾ Codex task

1. **ਅਕਾਊਂਟ ਨੂੰ pin ਕਰੋ:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12h) ਜਾਂ `86400` (ਵੱਧ ਤੋਂ ਵੱਧ 24h)।
2. OmniRoute ਦੇ environment ਵਿੱਚ **idle cutoffs ਵਧਾਓ / ਅਯੋਗ ਕਰੋ**:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. ਆਮ Codex `config.toml` (`wire_api = "responses"`, ਸਹੀ `base_url`, `OMNIROUTE_API_KEY`) ਨੂੰ ਹੀ ਵਰਤਦੇ ਰਹੋ — ਇਨ੍ਹਾਂ ਦੋ ਵਿਹਾਰਾਂ ਲਈ Codex-side affinity/idle knobs ਮੌਜੂਦ ਨਹੀਂ ਹਨ।
4. OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ, ਫਿਰ ਲੰਮਾ Codex task ਸ਼ੁਰੂ ਕਰੋ।

### Defaults ਬਾਰੇ ਫ਼ੈਸਲਾ (#7287)

| Knob                     | ਜਾਰੀ ਕੀਤਾ default  | ਇਸ guide ਵਿੱਚ ਬਦਲਣਾ ਹੈ?                                                                     |
| ------------------------ | ------------------ | ------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (ਬੰਦ)          | **ਨਹੀਂ** — opt-in ਹੀ ਰਹੇਗਾ (load-balancing ਬਨਾਮ continuity; Discussion #5718 ਵੇਖੋ)          |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 ਮਿੰਟ) | **ਨਹੀਂ** — ਆਮ traffic ਲਈ 10 ਮਿੰਟ ਹੀ ਰਹੇਗਾ; ਲੰਬੇ Codex ਦੇ operators ਇਸਨੂੰ ਵਧਾਉਣ ਜਾਂ ਅਯੋਗ ਕਰਨ |

ਕਿਸੇ ਵੀ default ਨੂੰ ਵਿਸ਼ਵ ਪੱਧਰ 'ਤੇ ਬਦਲਣ ਨਾਲ instance ਦੇ ਹਰ client ਦਾ ਵਿਹਾਰ ਬਦਲ ਜਾਵੇਗਾ, ਸਿਰਫ਼ Codex ਦਾ ਨਹੀਂ। Knobs ਦਾ documentation ਕਰੋ; ਜਦੋਂ ਤੱਕ operator ਦਾ ਕੋਈ ਸਪਸ਼ਟ ਫ਼ੈਸਲਾ ਇਸਦੇ ਉਲਟ ਨਾ ਹੋਵੇ, defaults ਨੂੰ ਜਿਵੇਂ ਹਨ ਤਿਵੇਂ ਰਹਿਣ ਦਿਓ।

### Idle cuts ਦੀ ਜਾਂਚ

ਜਦੋਂ idle watchdog ਸਰਗਰਮ ਹੁੰਦਾ ਹੈ, OmniRoute ਇਸ ਤਰ੍ਹਾਂ ਦੀ ਇੱਕ line log ਕਰਦਾ ਹੈ:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

`Idle timeout: no data from` (ਜਾਂ code `stream_idle_timeout` / error name `StreamIdleTimeoutError`) ਲਈ grep ਕਰੋ। Provider segment ਉਹ ਹੁੰਦਾ ਹੈ ਜੋ OmniRoute ਨੇ ਉਸ request ਲਈ ਵਰਤਿਆ ਸੀ (`codex`, ਕੋਈ ਹੋਰ provider id, ਜਾਂ ਜੇ ਅਣਜਾਣ ਹੋਵੇ ਤਾਂ `provider`) — ਇਹ ਹਮੇਸ਼ਾ ਸ਼ਾਬਦਿਕ string `codex` ਨਹੀਂ ਹੁੰਦਾ।

## ਸਮੱਸਿਆ ਨਿਵਾਰਣ

**`Error: wire_api = "chat" is no longer supported`**
ਆਪਣੀ ਸੰਰਚਨਾ ਵਿੱਚੋਂ `wire_api = "chat"` ਹਟਾਓ। `wire_api = "responses"` ਸੈੱਟ ਕਰੋ ਜਾਂ ਇਸ ਫ਼ੀਲਡ ਨੂੰ ਛੱਡ ਦਿਓ (v0.138 ਤੋਂ ਡਿਫੌਲਟ `"responses"` ਹੈ)।

**`Error: model not found`**
ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਮਾਡਲ ਸਹੀ ਪ੍ਰੀਫਿਕਸ ਨਾਲ OmniRoute ਵਿੱਚ ਮੌਜੂਦ ਹੈ। `omniroute models list` ਵਰਤੋ ਜਾਂ `/dashboard/providers/<provider>` ਖੋਲ੍ਹੋ।

**`Authentication error`**
ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `OMNIROUTE_API_KEY` ਐਕਸਪੋਰਟ ਕੀਤਾ ਗਿਆ ਹੈ: `echo $OMNIROUTE_API_KEY`।

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex ਪਹਿਲੀ ਬੇਨਤੀ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਜਾਂਚਦਾ ਹੈ ਕਿ env var ਮੌਜੂਦ ਹੈ। ਸੁਰੱਖਿਅਤ ਸਰਵਰਾਂ ਲਈ
ਅਸਲੀ ਕੁੰਜੀ ਐਕਸਪੋਰਟ ਕਰੋ, ਜਾਂ ਜਦੋਂ ਤੁਹਾਡੀ **ਸਥਾਨਕ** OmniRoute ਇੰਸਟੈਂਸ ਨੂੰ
ਪ੍ਰਮਾਣੀਕਰਨ ਦੀ ਲੋੜ ਨਾ ਹੋਵੇ ਤਾਂ `OMNIROUTE_API_KEY=local` ਵਰਗਾ ਕੋਈ ਗੈਰ-ਖਾਲੀ ਪਲੇਸਹੋਲਡਰ ਵਰਤੋ।
ਜੇ ਤੁਸੀਂ ਇਸਨੂੰ `~/.bashrc` ਜਾਂ `~/.zshrc` ਵਿੱਚ ਜੋੜਿਆ ਹੈ, ਤਾਂ ਸ਼ੈੱਲ ਮੁੜ ਚਾਲੂ ਕਰੋ।

**`Connection refused`**
ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ OmniRoute ਚੱਲ ਰਿਹਾ ਹੈ ਅਤੇ `base_url` ਦਾ ਹੋਸਟ/ਪੋਰਟ ਤੁਹਾਡੇ ਨੈੱਟਵਰਕ (ਸਥਾਨਕ ਬਨਾਮ Tailscale ਬਨਾਮ VPS) ਲਈ ਸਹੀ ਹੈ।

**ਸੰਦਰਭ ਸੀਮਾ ਦੇ ਨੇੜੇ ਸੈਸ਼ਨ ਕਰੈਸ਼ ਹੋ ਜਾਂਦਾ ਹੈ**
`model_context_window` ਅਤੇ `model_auto_compact_token_limit` ਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਸੈੱਟ ਕਰੋ। ਉੱਪਰ ਦਿੱਤੀ ਸੰਦਰਭ ਵਿੰਡੋ ਸਾਰਣੀ ਵੇਖੋ।

**ਕੰਪੈਕਸ਼ਨ ਬਹੁਤ ਦੇਰ ਨਾਲ ਸ਼ੁਰੂ ਹੁੰਦੀ ਹੈ**
`model_auto_compact_token_limit` ਨੂੰ ਵਿੰਡੋ ਦੇ 80–85% ਤੱਕ ਘਟਾਓ। ਇਸਨੂੰ ਕਦੇ ਵੀ 90% ਤੋਂ ਵੱਧ ਸੈੱਟ ਨਾ ਕਰੋ।

**ਪ੍ਰੋਫ਼ਾਈਲ ਲੋਡ ਨਹੀਂ ਹੋ ਰਹੀ (`-p <name>` ਨੂੰ ਬਿਨਾਂ ਕਿਸੇ ਸੁਨੇਹੇ ਦੇ ਅਣਡਿੱਠਾ ਕੀਤਾ ਗਿਆ)**
ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਫ਼ਾਈਲ `~/.codex/<name>.config.toml` 'ਤੇ ਮੌਜੂਦ ਹੈ (`profile-` ਪ੍ਰੀਫਿਕਸ ਤੋਂ ਬਿਨਾਂ)। `ls ~/.codex/*.config.toml` ਚਲਾਓ।

**ਲੰਮਾ Codex ਟਾਸਕ ਚੱਲਦੇ ਸਮੇਂ ਵਿਚਕਾਰ ਰੁਕ ਜਾਂਦਾ ਹੈ / ਟਰਨਾਂ ਵਿਚਕਾਰ ਖਾਤੇ ਬਦਲ ਜਾਂਦੇ ਹਨ**
[ਲੰਮੇ ਸਮੇਂ ਤੱਕ ਚੱਲਣ ਵਾਲੇ ਟਾਸਕ](#long-running-tasks) ਵੇਖੋ। ਸੈਸ਼ਨ ਐਫ਼ਿਨਿਟੀ (ਟਾਸਕ ਦੀ ਮਿਆਦ ਤੋਂ ਵੱਧ TTL) ਸਮਰੱਥ ਕਰੋ ਅਤੇ `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS` ਨੂੰ ਵਧਾਓ ਜਾਂ ਅਸਮਰੱਥ ਕਰੋ। OmniRoute ਲੌਗਾਂ ਵਿੱਚ `Idle timeout: no data from` ਲਈ grep ਕਰੋ।
