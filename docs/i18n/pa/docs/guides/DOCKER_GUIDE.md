## ਤੁਰੰਤ ਚਲਾਓ

> **ਇੱਕੋ ਕਮਾਂਡ ਨਾਲ ਸੈਲਫ਼-ਹੋਸਟ ਕਰਨਾ ਹੈ?**
> [ਸੈਲਫ਼-ਹੋਸਟ ਗਾਈਡ](../getting-started/SELF_HOST_GUIDE.md) ਵੇਖੋ —
> `docker compose -f docker-compose.selfhost.yml up -d` (ਪ੍ਰਕਾਸ਼ਿਤ ਇਮੇਜ +
> Redis, ਸਿਰਫ਼ ਲੂਪਬੈਕ, ਕੋਈ ਪ੍ਰੋਫ਼ਾਈਲ ਚੋਣ ਨਹੀਂ)। ਹੇਠਾਂ ਦਿੱਤਾ ਤੁਰੰਤ ਚਲਾਉਣ ਦਾ ਤਰੀਕਾ
> ਉਨ੍ਹਾਂ ਵਰਤੋਂਕਾਰਾਂ ਲਈ ਇਕੱਲੇ ਕੰਟੇਨਰ ਵਾਲਾ ਰਾਹ ਹੈ ਜੋ Redis ਨੂੰ ਪਹਿਲਾਂ ਹੀ ਕਿਸੇ ਹੋਰ ਥਾਂ ਚਲਾ ਰਹੇ ਹਨ।

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## Environment ਫ਼ਾਈਲ ਨਾਲ

```bash
# ਪਹਿਲਾਂ .env ਨੂੰ ਕਾਪੀ ਅਤੇ ਸੰਪਾਦਿਤ ਕਰੋ
cp .env.example .env

docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  --env-file .env \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## Docker Compose

```bash
# ਬੇਸ ਪ੍ਰੋਫ਼ਾਈਲ (ਕੋਈ CLI ਟੂਲ ਨਹੀਂ)
docker compose --profile base up -d

# CLI ਪ੍ਰੋਫ਼ਾਈਲ (Claude Code, Codex, OpenClaw ਬਿਲਟ-ਇਨ)
docker compose --profile cli up -d

# ਹੋਸਟ ਪ੍ਰੋਫ਼ਾਈਲ (ਮੁੱਖ ਤੌਰ 'ਤੇ Linux ਲਈ; ਹੋਸਟ CLI ਬਾਇਨਰੀਆਂ ਨੂੰ ਸਿਰਫ਼ ਪੜ੍ਹਨ ਲਈ ਮਾਊਂਟ ਕਰਦਾ ਹੈ)
docker compose --profile host up -d

# ਵੈੱਬ ਪ੍ਰੋਫ਼ਾਈਲ (ਵੈੱਬ-ਸੈਸ਼ਨ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ Chromium/Playwright)
docker compose --profile web up -d

# CLI + CLIProxyAPI sidecar ਨੂੰ ਜੋੜੋ
docker compose --profile cli --profile cliproxyapi up -d
```

## ਉਪਲਬਧ ਪ੍ਰੋਫ਼ਾਈਲ

OmniRoute ਮੁੱਖ ਡਿਪਲੌਇਮੈਂਟ ਬਣਤਰਾਂ ਲਈ Compose ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਸਮੇਤ ਆਉਂਦਾ ਹੈ। ਆਪਣੇ ਵਾਤਾਵਰਣ ਨਾਲ ਮੇਲ ਖਾਂਦਾ ਪ੍ਰੋਫ਼ਾਈਲ ਚੁਣੋ।

| ਪ੍ਰੋਫ਼ਾਈਲ       | ਸਰਵਿਸ            | ਕਦੋਂ ਵਰਤਣਾ ਹੈ                                                                                                                                     | ਕਮਾਂਡ                                        |
| --------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `base` (ਡਿਫੌਲਟ) | `omniroute-base` | ਹੈੱਡਲੈੱਸ ਸਰਵਰ / ਘੱਟੋ-ਘੱਟ ਰਨਟਾਈਮ, ਕੋਈ ਪ੍ਰਦਾਤਾ CLI ਬੰਡਲ ਨਹੀਂ                                                                                        | `docker compose --profile base up -d`        |
| `cli`           | `omniroute-cli`  | ਏਜੰਟਿਕ ਵਰਕਫ਼ਲੋ ਜੋ `omniroute providers/setup/doctor` ਅਤੇ ਬੰਡਲ ਕੀਤੇ CLI (Codex, Claude Code, Droid, OpenClaw) ਨੂੰ ਕਾਲ ਕਰਦੇ ਹਨ                      | `docker compose --profile cli up -d`         |
| `host`          | `omniroute-host` | ਉਹ Linux ਹੋਸਟ ਜੋ `~/.local/bin`, `~/.codex`, `~/.claude` ਆਦਿ ਨੂੰ ਸਿਰਫ਼ ਪੜ੍ਹਨ ਲਈ ਮਾਊਂਟ ਕਰਕੇ ਹੋਸਟ CLI ਤੱਕ `network_mode` ਵਰਗੀ ਪਹੁੰਚ ਚਾਹੁੰਦੇ ਹਨ      | `docker compose --profile host up -d`        |
| `cliproxyapi`   | `cliproxyapi`    | ਅੱਪਸਟ੍ਰੀਮ CLI ਪ੍ਰਾਕਸੀ ਲਈ ਪੋਰਟ `8317` ਉੱਤੇ [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) sidecar ਚਲਾਓ                                | `docker compose --profile cliproxyapi up -d` |
| `web`           | `omniroute-web`  | ਉਹ ਵੈੱਬ-ਸੈਸ਼ਨ ਪ੍ਰਦਾਤਾ ਜਿਨ੍ਹਾਂ ਨੂੰ ਬ੍ਰਾਊਜ਼ਰ ਦੀ ਲੋੜ ਹੈ: `gemini-web`, `claude-web`, `claude-turnstile` (`runner-web` ਬਣਾਉਂਦਾ ਹੈ, Chromium ਸ਼ਾਮਲ ਹੈ) | `docker compose --profile web up -d`         |

> ਕਈ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਨੂੰ ਇਕੱਠੇ ਵਰਤਿਆ ਜਾ ਸਕਦਾ ਹੈ: `docker compose --profile cli --profile cliproxyapi up -d`।

## ਜਦੋਂ OmniRoute Docker ਵਿੱਚ ਚੱਲਦਾ ਹੋਵੇ ਤਾਂ ਹੋਸਟ CLI ਟੂਲਾਂ ਦੀ ਸੰਰਚਨਾ ਕਰਨੀ

`omniroute setup-codex`, `setup-claude`, `config set <tool>` ਅਤੇ ਡੈਸ਼ਬੋਰਡ ਦਾ
**ਸੰਰਚਨਾ ਸੰਭਾਲੋ** ਬਟਨ ਸਾਰੇ `~/.codex/*.config.toml` ਵਰਗੀਆਂ ਫ਼ਾਈਲਾਂ ਲਿਖਦੇ ਹਨ। ਇਨ੍ਹਾਂ ਪਾਥਾਂ ਦਾ
ਅਰਥ ਸਿਰਫ਼ ਉਸ ਮਸ਼ੀਨ ਉੱਤੇ ਹੁੰਦਾ ਹੈ ਜਿੱਥੇ CLI ਅਸਲ ਵਿੱਚ ਚੱਲਦਾ ਹੈ। ਇਨ੍ਹਾਂ ਨੂੰ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ
ਚਲਾਉਣ ਨਾਲ ਲਿਖਤ ਕੰਟੇਨਰ ਦੀ ਆਪਣੀ ਹੋਮ ਡਾਇਰੈਕਟਰੀ (`/home/node` —
ਇਮੇਜ `USER node` ਵਜੋਂ ਚੱਲਦੀ ਹੈ) ਵਿੱਚ ਜਾਂਦੀ ਹੈ, ਜਿੱਥੋਂ ਕੋਈ ਵੀ ਹੋਸਟ CLI ਇਸਨੂੰ ਕਦੇ ਨਹੀਂ ਪੜ੍ਹੇਗਾ ਅਤੇ ਕੰਟੇਨਰ
ਮੁੜ ਬਣਾਏ ਜਾਣ ਦੇ ਨਾਲ ਹੀ ਇਹ ਮਿਟ ਜਾਂਦੀ ਹੈ।

OmniRoute ਇਸਦਾ ਪਤਾ ਲਗਾਉਂਦਾ ਹੈ ਅਤੇ ਅਜਿਹੀ ਸਫਲਤਾ ਰਿਪੋਰਟ ਕਰਨ ਦੀ ਬਜਾਏ, ਜਿਸਦਾ ਤੁਸੀਂ
ਉਪਯੋਗ ਨਹੀਂ ਕਰ ਸਕਦੇ, ਹਦਾਇਤਾਂ ਸਮੇਤ ਲਿਖਣ ਤੋਂ ਇਨਕਾਰ ਕਰਦਾ ਹੈ: CLI `2` ਨਾਲ ਬੰਦ ਹੁੰਦਾ ਹੈ ਅਤੇ API `422`
ਦੇ ਨਾਲ `containerEphemeralTarget: true` ਜਵਾਬ ਦਿੰਦਾ ਹੈ।

### ਸਿਫ਼ਾਰਸ਼ੀ: CLI ਨੂੰ ਹੋਸਟ ਉੱਤੇ ਅਤੇ OmniRoute ਨੂੰ Docker ਵਿੱਚ ਚਲਾਓ

ਕੰਟੇਨਰ API ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ; CLI ਤੁਹਾਡੇ ਹੋਸਟ ਟੂਲਾਂ ਦੀ ਸੰਰਚਨਾ ਕਰਦਾ ਹੈ।

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # CLI ਨੂੰ ਕੰਟੇਨਰ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਵਾਓ
omniroute setup-codex                      # ਤੁਹਾਡੇ ਹੋਸਟ ਉੱਤੇ ਅਸਲ ~/.codex ਲਿਖਦਾ ਹੈ
```

ਜਦੋਂ Codex, Claude Code, Cursor ਜਾਂ ਇਸੇ ਤਰ੍ਹਾਂ ਦੇ ਟੂਲ ਤੁਹਾਡੇ
ਲੈਪਟਾਪ ਉੱਤੇ ਚੱਲਦੇ ਹਨ ਤਾਂ ਇਹ ਸਹੀ ਚੋਣ ਹੈ — ਅਤੇ ਆਮ ਤੌਰ ਉੱਤੇ ਸੈੱਟਅੱਪ ਅਜਿਹਾ ਹੀ ਹੁੰਦਾ ਹੈ।

### ਵਿਕਲਪ: ਹੋਸਟ ਸੰਰਚਨਾ ਡਾਇਰੈਕਟਰੀਆਂ ਨੂੰ bind-mount ਕਰੋ (`host` ਪ੍ਰੋਫ਼ਾਈਲ)

ਜੇ ਤੁਸੀਂ ਚਾਹੁੰਦੇ ਹੋ ਕਿ ਕੰਟੇਨਰ ਖੁਦ ਤੁਹਾਡੀ ਹੋਸਟ ਸੰਰਚਨਾ ਲਿਖੇ, ਤਾਂ
ਡਾਇਰੈਕਟਰੀਆਂ ਨੂੰ ਮਾਊਂਟ ਕਰੋ ਅਤੇ `CLI_CONFIG_HOME` ਨੂੰ ਮਾਊਂਟ ਰੂਟ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਵਾਓ। `host` ਪ੍ਰੋਫ਼ਾਈਲ
ਇਹ ਪਹਿਲਾਂ ਹੀ ਕਰਦਾ ਹੈ:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

bind mount ਹੀ ਪਾਥ ਨੂੰ ਭਰੋਸੇਯੋਗ ਬਣਾਉਂਦਾ ਹੈ: OmniRoute
`/proc/self/mountinfo` ਨੂੰ ਪੜ੍ਹਦਾ ਹੈ ਅਤੇ ਮਾਊਂਟ ਕੀਤੇ ਪਾਥਾਂ (ਅਤੇ ਉਹਨਾਂ ਡਾਇਰੈਕਟਰੀਆਂ,
ਜਿਨ੍ਹਾਂ ਦੇ ਅਧੀਨ ਪਾਥ ਮਾਊਂਟ ਹਨ, ਜੋ ਬਿਲਕੁਲ ਉੱਪਰ ਦਿੱਤੇ `/host-home` ਵਰਗਾ ਰੂਪ ਹੈ) ਉੱਤੇ ਲਿਖਣ ਦੀ ਇਜਾਜ਼ਤ ਦਿੰਦਾ ਹੈ, ਜਦਕਿ
ਮਾਊਂਟ ਨਾ ਕੀਤੇ ਪਾਥਾਂ ਉੱਤੇ ਲਿਖਣ ਤੋਂ ਹਾਲੇ ਵੀ ਇਨਕਾਰ ਕਰਦਾ ਹੈ।

### ਬਚਾਅ ਦਾ ਰਾਹ: ਕੰਟੇਨਰ ਦੇ ਆਪਣੇ CLIs ਦੀ ਸੰਰਚਨਾ ਕਰੋ (ਸੰਜਮ ਨਾਲ ਵਰਤੋ)

ਜਦੋਂ CLIs ਵਾਸਤਵ ਵਿੱਚ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ ਹੀ ਮੌਜੂਦ ਹੋਣ (`cli` ਪ੍ਰੋਫ਼ਾਈਲ), ਤਾਂ ਲਿਖਣਾ
ਜਾਣਬੁੱਝ ਕੇ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਕਿਸੇ ਵੀ `setup-*` ਕਮਾਂਡ ਨੂੰ `--allow-container-write` ਦਿਓ, ਜਾਂ ਸਰਵਰ ਲਈ
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` ਸੈੱਟ ਕਰੋ। ਲਿਖਣ ਦੀ ਕਾਰਵਾਈ
ਇਸ ਚੇਤਾਵਨੀ ਨਾਲ ਅੱਗੇ ਵਧਦੀ ਹੈ ਕਿ ਇਹ ਕੰਟੇਨਰ ਦੇ ਬਾਅਦ ਕਾਇਮ ਨਹੀਂ ਰਹੇਗੀ।

> **ਸੁਰੱਖਿਆ ਚੇਤਾਵਨੀ — `cli` ਪ੍ਰੋਫ਼ਾਈਲ + `docker.sock` ਮਾਊਂਟ।**
> `cli` ਪ੍ਰੋਫ਼ਾਈਲ `/var/run/docker.sock` ਨੂੰ bind-mount ਕਰਦਾ ਹੈ ਤਾਂ ਜੋ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰਲਾ
> ਆਟੋ-ਅੱਪਡੇਟਰ ਹੋਸਟ daemon ਤੋਂ ਸਟੈਕ ਨੂੰ ਮੁੜ ਬਣਾ ਸਕੇ
> (`src/lib/system/autoUpdate.ts` ਉਸ socket ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ ਅਤੇ ਇਸਦੀ
> ਗੈਰ-ਮੌਜੂਦਗੀ ਵਿੱਚ Docker ਪਾਥ ਛੱਡ ਦਿੰਦਾ ਹੈ)। ਉਹ socket **ਹੋਸਟ-root ਭਰੋਸੇ ਦੀ
> ਸੀਮਾ** ਹੈ: ਜੋ ਕੁਝ ਵੀ ਇਸ ਤੱਕ ਪਹੁੰਚ ਸਕਦਾ ਹੈ, ਉਹ root ਵਜੋਂ ਹੋਸਟ Docker daemon ਨੂੰ
> ਨਿਯੰਤਰਿਤ ਕਰਦਾ ਹੈ — ਇਹ ਹੋਸਟ ਉੱਤੇ ਕਿਸੇ ਵੀ ਕੰਟੇਨਰ ਨੂੰ ਬਣਾ, ਜਾਂਚ, ਰੋਕ ਅਤੇ ਹਟਾ ਸਕਦਾ ਹੈ।
> ਨਤੀਜੇ:
>
> 1. **`cli` ਪ੍ਰੋਫ਼ਾਈਲ ਦੇ ਪੋਰਟ ਨੂੰ ਕਦੇ ਵੀ ਨੈੱਟਵਰਕ ਉੱਤੇ ਉਪਲਬਧ ਨਾ ਕਰੋ।** ਇਸਨੂੰ
>    `127.0.0.1` ਉੱਤੇ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰੋ (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LAN ਤੋਂ ਪਹੁੰਚਯੋਗ `cli` ਪ੍ਰੋਫ਼ਾਈਲ ਡੈਸ਼ਬੋਰਡ-ਪੱਧਰੀ ਕਿਸੇ ਵੀ RCE ਨੂੰ
>    ਹੋਸਟ ਉੱਤੇ ਪੂਰਾ ਕਬਜ਼ਾ ਕਰਨ ਦੀ ਸਮਰੱਥਾ ਦੇ ਦਿੰਦਾ ਹੈ।
> 2. **`cli` ਪ੍ਰੋਫ਼ਾਈਲ ਵਿੱਚ ਕੋਈ ਵੀ ਵਾਧੂ ਹੋਸਟ ਡਾਇਰੈਕਟਰੀ bind ਨਾ ਕਰੋ।**
>    Docker socket ਦੇ ਨਾਲ ਕੋਈ ਹੋਰ ਮਾਊਂਟ ਕੰਟੇਨਰ ਨੂੰ ਤੁਹਾਡੇ ਫ਼ਾਈਲ-ਸਿਸਟਮ ਅਤੇ ਹੋਸਟ ਸੰਰਚਨਾ ਉੱਤੇ
>    ਪੂਰਾ ਪੜ੍ਹਨ/ਲਿਖਣ ਦਾ ਅਧਿਕਾਰ ਦਿੰਦਾ ਹੈ। ਜੇ ਤੁਹਾਨੂੰ ਕਿਸੇ ਟੂਲ ਨੂੰ
>    ਪ੍ਰੋਜੈਕਟ ਦਿਖਾਉਣ ਦੀ ਲੋੜ ਹੈ, ਤਾਂ ਇਸਨੂੰ CLI binary ਨਾਲ ਸਥਾਨਕ ਤੌਰ ਉੱਤੇ ਚਲਾਓ — ਇਸਨੂੰ
>    `cli` ਕੰਟੇਨਰ ਵਿੱਚ ਮਾਊਂਟ ਨਾ ਕਰੋ।
>
> ਜੇ ਤੁਹਾਨੂੰ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ ਆਟੋ-ਅੱਪਡੇਟ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ, ਤਾਂ `cli` ਪ੍ਰੋਫ਼ਾਈਲ ਬੰਦ ਰੱਖੋ
> (`COMPOSE_PROFILES=core,redis` ਜਾਂ ਇਸ ਤੋਂ ਛੋਟਾ)। ਹੋਰ ਪ੍ਰੋਫ਼ਾਈਲ
> Docker socket ਨੂੰ ਮਾਊਂਟ ਨਹੀਂ ਕਰਦੇ।
>
> MITM ਨਾਲ ਸੰਬੰਧਿਤ ਖ਼ਤਰਾ ਮਾਡਲ ਲਈ `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs` ਵਿੱਚ ਕੰਪਾਇਲ ਨਹੀਂ ਕੀਤਾ ਗਿਆ) ਵੇਖੋ,
> ਅਤੇ `codex`/`claude-code`/`droid`/`openclaw` binary ਦੇ ਮੂਲ ਸਰੋਤਾਂ ਦੀ ਲੜੀ ਲਈ
> `docs/security/SUPPLY_CHAIN.md` ਵੇਖੋ।

## Redis ਸਾਈਡਕਾਰ

OmniRoute ਵੰਡੇ ਹੋਏ ਰੇਟ ਲਿਮਿਟਰ ਅਤੇ ਸਾਂਝੀ ਕੈਸ਼ ਨੂੰ ਸਮਰਥਨ ਦੇਣ ਲਈ Redis 'ਤੇ ਨਿਰਭਰ ਕਰਦਾ ਹੈ। `redis` ਸੇਵਾ `docker-compose.yml` ਵਿੱਚ **ਹਮੇਸ਼ਾ ਪਰਿਭਾਸ਼ਿਤ ਹੁੰਦੀ ਹੈ** (ਇਸ 'ਤੇ ਕੋਈ ਪ੍ਰੋਫ਼ਾਈਲ ਗੇਟ ਨਹੀਂ ਹੈ) ਅਤੇ ਕਿਸੇ ਵੀ ਹੋਰ ਪ੍ਰੋਫ਼ਾਈਲ ਦੇ ਨਾਲ ਸ਼ੁਰੂ ਹੁੰਦੀ ਹੈ।

| ਵੇਰਵਾ                | ਮੁੱਲ                                   |
| -------------------- | -------------------------------------- |
| ਇਮੇਜ                 | `redis:7-alpine`                       |
| ਕੰਟੇਨਰ ਦਾ ਨਾਮ        | `omniroute-redis`                      |
| ਅੰਦਰੂਨੀ ਪੋਰਟ         | `6379`                                 |
| ਹੋਸਟ ਪੋਰਟ (ਓਵਰਰਾਈਡ)  | `REDIS_PORT` (ਡਿਫੌਲਟ `6379`)           |
| ਹੋਸਟ ਬਾਈਂਡ (ਓਵਰਰਾਈਡ) | `REDIS_BIND_HOST` (ਡਿਫੌਲਟ `127.0.0.1`) |
| ਵਾਲਿਊਮ               | `omniroute-redis-data` → `/data`       |
| ਹੈਲਥਚੈੱਕ             | `redis-cli ping` (10s ਅੰਤਰਾਲ)          |

ਸੰਬੰਧਿਤ ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲ:

- `REDIS_URL` — ਐਪ ਵਿੱਚ ਇੰਜੈਕਟ ਕੀਤੀ ਕਨੈਕਸ਼ਨ ਸਟ੍ਰਿੰਗ (ਡਿਫੌਲਟ ਤੌਰ 'ਤੇ `redis://redis:6379`)।
- `REDIS_PORT` — Redis ਕੰਟੇਨਰ ਲਈ ਹੋਸਟ-ਸਾਈਡ ਪੋਰਟ ਮੈਪਿੰਗ।
- `REDIS_BIND_HOST` — ਉਹ ਹੋਸਟ ਇੰਟਰਫੇਸ ਜਿਸ 'ਤੇ ਪੋਰਟ ਪ੍ਰਕਾਸ਼ਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਡਿਫੌਲਟ `127.0.0.1` ਹੈ।

> **ਡਿਫੌਲਟ ਤੌਰ 'ਤੇ ਲੂਪਬੈਕ ਕਿਉਂ:** ਸਾਈਡਕਾਰ `requirepass` ਤੋਂ ਬਿਨਾਂ ਚੱਲਦਾ ਹੈ, ਅਤੇ ਐਪ
> ਕੰਟੇਨਰ compose ਨੈੱਟਵਰਕ (`redis:6379`) ਰਾਹੀਂ ਇਸ ਤੱਕ ਪਹੁੰਚਦੇ ਹਨ — ਪ੍ਰਕਾਸ਼ਿਤ ਪੋਰਟ
> ਸਿਰਫ਼ ਹੋਸਟ-ਸਾਈਡ ਟੂਲਿੰਗ (`redis-cli`, ਇੱਕ ਲੋਕਲ `npm run dev`) ਲਈ ਹੈ। `0.0.0.0`
> 'ਤੇ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਨ ਨਾਲ ਇੱਕ ਬਿਨਾਂ ਪ੍ਰਮਾਣੀਕਰਨ ਵਾਲਾ Redis ਤੁਹਾਡੇ LAN ਦੇ ਹਰੇਕ ਹੋਸਟ ਲਈ ਉਪਲਬਧ ਹੋ ਜਾਵੇਗਾ। ਜੇ ਤੁਸੀਂ
> `REDIS_BIND_HOST=0.0.0.0` ਸੈੱਟ ਕਰਦੇ ਹੋ, ਤਾਂ ਸੇਵਾ ਦੇ `command:` ਵਿੱਚ `--requirepass` ਵੀ ਸ਼ਾਮਲ ਕਰੋ।

**Redis ਨੂੰ ਅਯੋਗ ਕਰਨ** ਦੀ ਸਿਫ਼ਾਰਸ਼ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ (ਰੇਟ ਲਿਮਿਟਰ ਇਨ-ਮੈਮੋਰੀ ਫਾਲਬੈਕ 'ਤੇ ਆ ਜਾਵੇਗਾ)। ਜੇ ਇਹ ਲਾਜ਼ਮੀ ਹੋਵੇ, ਤਾਂ `docker-compose.yml` ਵਿੱਚੋਂ `redis:` ਸੇਵਾ ਬਲਾਕ ਨੂੰ ਹਟਾਓ/ਕਮੈਂਟ ਕਰੋ ਜਾਂ ਇਸਨੂੰ ਸਿਫ਼ਰ ਤੱਕ ਸਕੇਲ ਕਰੋ:

```bash
docker compose up -d --scale redis=0
```

## ਪ੍ਰੋਡਕਸ਼ਨ Compose

dev ਦੇ ਨਾਲ-ਨਾਲ ਚੱਲਣ ਵਾਲੇ ਇੱਕ ਵੱਖਰੇ ਪ੍ਰੋਡਕਸ਼ਨ ਸਨੈਪਸ਼ਾਟ ਲਈ `docker-compose.prod.yml` ਵਰਤੋ।

| ਵੇਰਵਾ                | ਮੁੱਲ                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------- |
| ਫ਼ਾਈਲ                | `docker-compose.prod.yml`                                                                   |
| ਡਿਫੌਲਟ ਡੈਸ਼ਬੋਰਡ ਪੋਰਟ | `PROD_DASHBOARD_PORT=20130` (ਅੰਦਰੂਨੀ `${DASHBOARD_PORT:-20128}` ਨਾਲ ਮੈਪ ਕੀਤਾ)               |
| ਡਿਫੌਲਟ API ਪੋਰਟ      | `PROD_API_PORT=20131`                                                                       |
| ਇਮੇਜ                 | `omniroute:prod` (`runner-cli` ਟਾਰਗੇਟ ਤੋਂ ਬਿਲਡ ਕੀਤੀ)                                        |
| Redis ਕੰਟੇਨਰ         | `omniroute-redis-prod` (`redis:8.6.2`, ਸਮਰਪਿਤ `redis-prod-data` ਵਾਲਿਊਮ)                     |
| ਡਾਟਾ ਵਾਲਿਊਮ          | `omniroute-prod-data` (ਨਾਮਿਤ, ਮੁੜ ਬਿਲਡ ਕਰਨ ਦੌਰਾਨ ਵੀ ਕਾਇਮ)                                   |
| ਹੈਲਥਚੈੱਕ             | `node healthcheck.mjs` + `redis-cli ping`, ਜਿਸ ਵਿੱਚ `depends_on` Redis ਦੀ ਸਿਹਤ 'ਤੇ ਨਿਰਭਰ ਹੈ |

ਵਰਤਣ ਦਾ ਤਰੀਕਾ:

```bash
# ਪ੍ਰੋਡਕਸ਼ਨ ਸਟੈਕ ਨੂੰ ਬਿਲਡ ਅਤੇ ਸ਼ੁਰੂ ਕਰੋ
docker compose -f docker-compose.prod.yml up -d --build

# ਲੌਗਾਂ ਨੂੰ ਲਗਾਤਾਰ ਵੇਖੋ
docker compose -f docker-compose.prod.yml logs -f

# ਬੰਦ ਕਰੋ (ਵਾਲਿਊਮ ਕਾਇਮ ਰੱਖੋ)
docker compose -f docker-compose.prod.yml down
```

prod ਸਟੈਕ dev compose ਦੇ ਸਮਾਂਤਰ ਚੱਲਦਾ ਹੈ (ਵੱਖਰੇ ਕੰਟੇਨਰ ਨਾਮਾਂ, ਪੋਰਟਾਂ ਅਤੇ ਵਾਲਿਊਮਾਂ ਨਾਲ), ਇਸ ਲਈ ਪ੍ਰੋਡਕਸ਼ਨ ਨੂੰ ਚੱਲਦਾ ਰੱਖਦੇ ਹੋਏ ਤੁਸੀਂ ਲੋਕਲ ਤੌਰ 'ਤੇ ਕੰਮ ਜਾਰੀ ਰੱਖ ਸਕਦੇ ਹੋ।

## Dockerfile ਪੜਾਅ

ਰਿਪੋਜ਼ਟਰੀ ਇੱਕ ਬਹੁ-ਪੜਾਵੀ Dockerfile (`Dockerfile`) ਨਾਲ ਆਉਂਦੀ ਹੈ। ਚਾਰ ਪੜਾਅ ਉਪਲਬਧ ਹਨ; ਆਪਣੀ ਵਰਤੋਂ ਲਈ ਸਹੀ `target` ਚੁਣੋ।

| ਪੜਾਅ          | ਬੇਸ ਇਮੇਜ              | ਉਦੇਸ਼                                                                                                                                                                                                                                                                                     |
| ------------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `builder`     | `node:26-trixie-slim` | ਡਿਪੈਂਡੈਂਸੀਆਂ ਇੰਸਟਾਲ ਕਰਦਾ ਹੈ (`npm ci --legacy-peer-deps`) ਅਤੇ `npm run build` ਚਲਾਉਂਦਾ ਹੈ (ਮੂਲ ਰੂਪ ਵਿੱਚ Turbopack — ਹੇਠਾਂ ਬਿਲਡ-ਸਮੇਂ ਦੇ ਸਰੋਤ ਵੇਖੋ)                                                                                                                                          |
| `runner-base` | `node:26-trixie-slim` | Next.js ਦੇ ਸਟੈਂਡਅਲੋਨ ਆਉਟਪੁੱਟ ਨਾਲ ਪ੍ਰੋਡਕਸ਼ਨ ਰਨਟਾਈਮ। **ਕੋਈ ਪ੍ਰਦਾਤਾ CLI ਸ਼ਾਮਲ ਨਹੀਂ ਹੈ।**                                                                                                                                                                                                     |
| `runner-cli`  | `runner-base`         | `git`, `docker.io`, `docker-compose` ਅਤੇ ਗਲੋਬਲ CLI ਸ਼ਾਮਲ ਕਰਦਾ ਹੈ: `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw`। **ਏਜੈਂਟਿਕ ਵਰਕਫ਼ਲੋਜ਼ ਲਈ ਇਹ ਚੁਣੋ।**                                                                                                                    |
| `runner-web`  | `runner-base`         | ਵੈੱਬ-ਸੈਸ਼ਨ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ Playwright + ਇੱਕ Chromium ਬ੍ਰਾਊਜ਼ਰ (`--with-deps`) ਸ਼ਾਮਲ ਕਰਦਾ ਹੈ: `gemini-web`, `claude-web`, `claude-turnstile`। **ਜਦੋਂ ਤੁਸੀਂ ਇਹ ਪ੍ਰਦਾਤਾ ਵਰਤਦੇ ਹੋ ਤਾਂ ਇਹ ਚੁਣੋ** — ਇਸ ਤੋਂ ਬਿਨਾਂ ਸਧਾਰਨ ਇਮੇਜ ਬੇਨਤੀ ਦੇ ਸਮੇਂ ਅਸਫਲ ਹੋ ਜਾਂਦੀ ਹੈ (ਰਿਲੀਜ਼ ਚੈਨਲਾਂ ਹੇਠਾਂ `-web` ਨੋਟ ਵੇਖੋ)। |

ਕਿਸੇ ਖ਼ਾਸ ਟਾਰਗੇਟ ਨੂੰ ਹੱਥੀਂ ਬਿਲਡ ਕਰੋ:

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### ਬਿਲਡ-ਸਮੇਂ ਦੇ ਸਰੋਤ

ਤਿੰਨ ਬਿਲਡ ਆਰਗੂਮੈਂਟ ਇਹ ਨਿਯੰਤਰਿਤ ਕਰਦੇ ਹਨ ਕਿ `builder` ਪੜਾਅ ਕਿੰਨੇ ਸਰੋਤ ਵਰਤਦਾ ਹੈ। ਇਹ ਸਿਰਫ਼ ਬਿਲਡ ਸਮੇਂ ਲਈ ਹਨ —
`OMNIROUTE_MEMORY_MB` (ਹੇਠਾਂ) ਇੱਕ ਵੱਖਰੀ, ਰਨਟਾਈਮ ਸੈਟਿੰਗ ਹੈ।

| ਬਿਲਡ ਆਰਗੂਮੈਂਟ               | ਮੂਲ ਮੁੱਲ | ਪ੍ਰਭਾਵ                                                                                               |
| --------------------------- | -------- | ---------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `0`      | `0` webpack ਨਾਲ ਬਿਲਡ ਕਰਦਾ ਹੈ: ਘੱਟ ਪੀਕ ਮੈਮੋਰੀ, ਪਰ ਹੌਲੀ। `1` Turbopack ਦੀ ਚੋਣ ਕਰਦਾ ਹੈ।                 |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144`   | ਸ਼ੁਰੂ ਕੀਤੇ ਗਏ `next build` ਲਈ V8 ਹੀਪ ਸੀਮਾ (`--max-old-space-size`)।                                  |
| `OMNIROUTE_BUILD_WORKERS`   | `2`      | `CIRCLE_NODE_TOTAL` ਨੂੰ ਮੁੱਲ ਦਿੰਦਾ ਹੈ; Next ਪੇਜ-ਡਾਟਾ ਇਕੱਤਰ ਕਰਨ ਲਈ `workers = N - 1` ਨਿਰਧਾਰਤ ਕਰਦਾ ਹੈ। |

ਵੱਡੇ ਬਿਲਡਰ ਉੱਤੇ `OMNIROUTE_BUILD_WORKERS` ਨੂੰ ਵਧਾਉਣਾ ਚਾਹੀਦਾ ਹੈ ਅਤੇ ਜਦੋਂ ਕੋਈ
ਸੀਮਤ ਸਰੋਤਾਂ ਵਾਲਾ ਬਿਲਡ `✓ Compiled successfully` **ਤੋਂ ਬਾਅਦ** ਬੰਦ ਹੋ ਜਾਵੇ ਤਾਂ ਸਭ ਤੋਂ ਪਹਿਲਾਂ ਇਸ ਉੱਤੇ
ਸ਼ੱਕ ਕਰਨਾ ਚਾਹੀਦਾ ਹੈ। ਹਰ ਪੇਜ-ਡਾਟਾ ਵਰਕਰ ਆਪਣੀ ਵੱਖਰੀ ਪ੍ਰਕਿਰਿਆ ਹੈ, ਅਤੇ ਮੁੱਖ `next build` ਵੀ;
ਇੱਕ ਚੱਲਦੇ VPS ਉੱਤੇ ਕੀਤੇ ਪੁਨਰੁਤਪਾਦਨ (ਮੁੱਦਾ #7518) ਵਿੱਚ ਹਰ ਪ੍ਰਕਿਰਿਆ ਦਾ ਪੀਕ RSS
~4.5 GB ਮਾਪਿਆ ਗਿਆ, ਜੋ `NODE_OPTIONS` ਹੀਪ ਫਲੈਗ ਤੋਂ ਸੁਤੰਤਰ ਸੀ (Turbopack, V8 ਹੀਪ ਤੋਂ
ਬਾਹਰ ਨੈਟਿਵ/Rust ਮੈਮੋਰੀ ਵਿੱਚ ਕੰਪਾਇਲ ਕਰਦਾ ਹੈ)। `2` ਦਾ ਮੂਲ ਮੁੱਲ (→ 1 ਵਰਕਰ, ਕੁੱਲ 2
ਪ੍ਰਕਿਰਿਆਵਾਂ) ਉਹਨਾਂ 16 GB / 4 vCPU GitHub-ਹੋਸਟਡ ਰਨਰਾਂ ਲਈ ਨਿਰਧਾਰਤ ਹੈ ਜਿਨ੍ਹਾਂ ਨੂੰ
ਪਬਲਿਸ਼ ਪਾਈਪਲਾਈਨ ਵਰਤਦੀ ਹੈ। `8` ਉੱਤੇ (→ 7 ਵਰਕਰ) ਉਸ ਰਨਰ ਦੀ ਮੈਮੋਰੀ ਖ਼ਤਮ ਹੋ ਗਈ ਅਤੇ
buildkit ਨੇ `ResourceExhausted: ... cannot allocate memory` ਨਾਲ ਪੜਾਅ ਅਸਫਲ ਕਰ ਦਿੱਤਾ;
ਪ੍ਰਤੀ-ਪ੍ਰਕਿਰਿਆ RSS ਦਾ ਅੰਦਾਜ਼ਾ ਲਗਾਉਣ ਦੀ ਬਜਾਏ ਉਸਨੂੰ ਸਿੱਧਾ ਮਾਪਣ ਤੋਂ ਬਾਅਦ `3` (→ 2 ਵਰਕਰ)
ਵੀ ਉਪਲਬਧ ਮੈਮੋਰੀ ਵਿੱਚ ਫਿੱਟ ਨਹੀਂ ਹੋਇਆ। `tests/unit/docker-build-memory-budget.test.ts`
ਮਾਪੇ ਗਏ ਅੰਕੜੇ ਦੇ ਆਧਾਰ ਉੱਤੇ ਗਣਨਾ ਕਰਦਾ ਹੈ ਅਤੇ ਜੇਕਰ ਕੋਈ ਵੀ ਸੈਟਿੰਗ
ਰਨਰ ਦੀ ਸਮਰੱਥਾ ਤੋਂ ਵੱਧ ਜਾਂਦੀ ਹੈ ਤਾਂ ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ।

Turbopack ਨੈਟਿਵ Rust ਮੈਮੋਰੀ ਵਿੱਚ ਕੰਪਾਇਲ ਕਰਦਾ ਹੈ ਜੋ V8 ਹੀਪ ਤੋਂ **ਬਾਹਰ** ਰਹਿੰਦੀ ਹੈ, ਇਸ ਲਈ
`OMNIROUTE_BUILD_MEMORY_MB` ਇਸਨੂੰ ਸੀਮਿਤ ਨਹੀਂ ਕਰਦਾ। ਮੈਮੋਰੀ ਸੀਮਾ ਵਾਲੇ ਹੋਸਟ ਉੱਤੇ
ਬਿਲਡ ਨੂੰ OOM ਕਿਲਰ ਬਿਨਾਂ ਕਿਸੇ ਗਲਤੀ ਸੁਨੇਹੇ ਦੇ SIGKILL ਕਰ ਦਿੰਦਾ ਹੈ — ਇਹ ਬਸ
`Creating an optimized production build` ਦੇ ਵਿਚਕਾਰ ਰੁਕ ਜਾਂਦਾ ਹੈ, ਜੋ ਮੈਮੋਰੀ ਖ਼ਤਮ ਹੋਣ ਦੀ
ਬਜਾਏ ਹੈਂਗ ਹੋਣ ਵਰਗਾ ਲੱਗਦਾ ਹੈ। ਇਸੇ ਲਈ `Dockerfile` ਦਾ ਮੂਲ ਵਿਕਲਪ webpack
(`OMNIROUTE_USE_TURBOPACK=0`) ਹੈ, ਜਦਕਿ `npm run dev` / `npm run build` ਵਿੱਚ
Turbopack ਕੋਡ ਦਾ ਮੂਲ ਵਿਕਲਪ ਹੈ: ਬਿਨਾਂ ਕਿਸੇ ਬਿਲਡ ਆਰਗੂਮੈਂਟ ਦੇ ਸਧਾਰਨ `docker build .`
(ਜੋ Railway ਅਤੇ ਹੋਰ ਇੱਕ-ਕਲਿੱਕ ਹੋਸਟ ਚਲਾਉਂਦੇ ਹਨ) ਮੈਮੋਰੀ-ਸੀਮਤ ਬਿਲਡਰ ਉੱਤੇ ਚੁੱਪਚਾਪ
ਬੰਦ ਨਹੀਂ ਹੋਣਾ ਚਾਹੀਦਾ। ਪ੍ਰਕਾਸ਼ਿਤ ਇਮੇਜ ਪਹਿਲਾਂ ਹੀ `docker-publish.yml` ਵਿੱਚ
`OMNIROUTE_USE_TURBOPACK=0` ਨੂੰ ਸਪਸ਼ਟ ਤੌਰ ਉੱਤੇ ਪਾਸ ਕਰਦੇ ਹਨ। ਕਾਫ਼ੀ RAM ਵਾਲੇ ਬਿਲਡਰ ਉੱਤੇ,
ਤੇਜ਼ ਬਿਲਡ ਲਈ Turbopack ਚੁਣੋ:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

`webpackBuildWorker` ਸਮਰੱਥ ਹੈ, ਇਸ ਲਈ `next build` ਇੱਕ ਮੁੱਖ **ਅਤੇ** ਇੱਕ ਵਰਕਰ
ਪ੍ਰਕਿਰਿਆ ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਹਰੇਕ ਵੱਖਰੇ ਤੌਰ ਉੱਤੇ `OMNIROUTE_BUILD_MEMORY_MB` ਦੀ ਪਾਲਣਾ
ਕਰਦੀ ਹੈ। ਕੰਟੇਨਰ ਦੀ ਸੀਮਾ ਇਸ ਮੁੱਲ ਤੋਂ ਲਗਭਗ ਦੁੱਗਣੀ ਤੋਂ ਉੱਪਰ ਰੱਖੋ, ਨਾ ਕਿ ਸਿਰਫ਼ ਇੱਕ ਗੁਣਾ।

ਇਸ ਟ੍ਰੀ ਉੱਤੇ ਮਾਪਿਆ ਗਿਆ (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| ਬੰਡਲਰ     | ਕੰਟੇਨਰ ਸੀਮਾ    | ਨਤੀਜਾ                                    |
| --------- | -------------- | ---------------------------------------- |
| Turbopack | 8 GiB / 16 GiB | ਦੋਵਾਂ ਉੱਤੇ OOM ਕਾਰਨ ਬੰਦ, ਬਿਨਾਂ ਸੁਨੇਹੇ ਦੇ |
| webpack   | 8 GiB          | ਬਿਲਡ ਵਰਕਰ ਨੂੰ SIGKILL ਕੀਤਾ ਗਿਆ           |
| webpack   | 12 GiB         | ਸਫਲ, ਪੀਕ 11.1 GiB ਤੱਕ ਪਹੁੰਚਿਆ            |

### ਰਨਟਾਈਮ ਦੇ ਮੂਲ ਮੁੱਲ

`runner-base` ਵੱਲੋਂ ਐਕਸਪੋਰਟ ਕੀਤੇ ਮੂਲ ਮੁੱਲ: `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`।

Docker ਵਿੱਚ ਮੈਮੋਰੀ ਦਾ ਵਿਹਾਰ:

- ਇਮੇਜ `OMNIROUTE_MEMORY_MB=1024` ਸੈੱਟ ਕਰਦੀ ਹੈ ਅਤੇ ਇਸ ਤੋਂ `NODE_OPTIONS=--max-old-space-size=1024` ਪ੍ਰਾਪਤ ਕਰਦੀ ਹੈ।
- ਅਸਲ ਸਰਵਰ ਪ੍ਰਕਿਰਿਆ standalone launcher ਦੁਆਰਾ ਸ਼ੁਰੂ ਕੀਤੀ ਜਾਂਦੀ ਹੈ, ਜੋ `OMNIROUTE_MEMORY_MB` ਪੜ੍ਹਦਾ ਹੈ ਅਤੇ `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` ਜੋੜਦਾ ਹੈ।
- Node ਆਖਰੀ ਵਾਰ ਦੁਹਰਾਇਆ ਗਿਆ `--max-old-space-size` ਮੁੱਲ ਵਰਤਦਾ ਹੈ, ਇਸ ਲਈ `OMNIROUTE_MEMORY_MB` ਸੈੱਟ ਕਰਨਾ ਪ੍ਰਭਾਵੀ Docker ਹੀਪ ਸੀਮਾ ਨੂੰ ਨਿਯੰਤਰਿਤ ਕਰਦਾ ਹੈ।
- ਕਿਉਂਕਿ ਇਮੇਜ ਹਮੇਸ਼ਾ ਇਸਨੂੰ ਸੈੱਟ ਕਰਦੀ ਹੈ, launcher ਦਾ ਆਪਣਾ RAM-ਅਨੁਸਾਰ ਕੈਲੀਬਰੇਟ ਕੀਤਾ fallback Docker ਅਧੀਨ ਕਦੇ ਲਾਗੂ ਨਹੀਂ ਹੁੰਦਾ। ਵਰਕਲੋਡ ਲਈ ਇਸਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਵਧਾਓ (ਹੇਠਾਂ ਦਿੱਤੀ ਸਾਰਣੀ)। ਕੋਡਿੰਗ-ਏਜੰਟ `/v1/responses` ਲਈ `2048` ਹਾਲੇ ਵੀ ਬਹੁਤ ਘੱਟ ਹੈ।

### ਕੋਡਿੰਗ ਏਜੰਟਾਂ ਲਈ ਰਨਟਾਈਮ RAM

1 GiB ਦਾ Docker ਡਿਫਾਲਟ ਡੈਸ਼ਬੋਰਡ/ਹਲਕੀ-ਚੈਟ ਲਈ ਨਿਊਨਤਮ ਸੀਮਾ ਹੈ, ਪ੍ਰੋਡਕਸ਼ਨ ਆਕਾਰ ਨਹੀਂ। ਲੰਬੀਆਂ `POST /v1/responses` ਬਾਡੀਆਂ (ਸੈਂਕੜੇ ਸੁਨੇਹੇ, ਦਰਜਨਾਂ ਟੂਲ) ਕੰਪ੍ਰੈਸ਼ਨ ਦੌਰਾਨ ਕਈ ਇਨ-ਮੈਮੋਰੀ ਗ੍ਰਾਫ਼ ਕਾਇਮ ਰੱਖਦੀਆਂ ਹਨ। ਇੱਕ-ਦੂਜੇ ਨਾਲ ਓਵਰਲੈਪ ਹੋਣ ਵਾਲੀਆਂ ਦੋ ~3 MiB / ~750k-token ਬੇਨਤੀਆਂ ਨੇ **12 GiB** old-space ਉੱਤੇ V8 ਨੂੰ ਅਬੋਰਟ ਕੀਤਾ ਹੈ (`FATAL ERROR: Reached heap limit`) ਅਤੇ 16 GiB cgroup OOM ਵੀ ਟ੍ਰਿਗਰ ਕੀਤਾ ਹੈ। [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ਵੇਖੋ।

**cgroup `--memory` ਨੂੰ ਹੀਪ ਤੋਂ ਵੱਧ ਰੱਖੋ** — ਨੇਟਿਵ ਬਫ਼ਰ, SQLite ਅਤੇ ਕੰਪ੍ਰੈਸ਼ਨ ਦੇ ਦਰਮਿਆਨੀ ਡਾਟੇ V8 ਤੋਂ ਬਾਹਰ ਰਹਿੰਦੇ ਹਨ।

| ਵਰਕਲੋਡ                              | `OMNIROUTE_MEMORY_MB`     | ਕੰਟੇਨਰ / cgroup          | ਟਿੱਪਣੀਆਂ                                                                                           |
| ----------------------------------- | ------------------------- | ------------------------ | -------------------------------------------------------------------------------------------------- |
| ਡੈਸ਼ਬੋਰਡ, ਇੱਕ ਹਲਕੀ ਚੈਟ              | `1024` (ਇਮੇਜ ਡਿਫਾਲਟ)      | ≥2 GiB                   |                                                                                                    |
| ਇੱਕ ਕੋਡਿੰਗ ਏਜੰਟ (Claude/Codex/Grok) | `8192`                    | ≥10 GiB                  | ਆਮ ਇਕਹਿਰੇ-ਸੈਸ਼ਨ ਵਾਲਾ `/v1/responses`                                                               |
| ਦੋ ਸਮਕਾਲੀ ਲੰਬੇ `/v1/responses`      | `10240`–`12288`           | ≥12–16 GiB               | ~12 GiB ਹੀਪ ਉੱਤੇ V8 ਅਬੋਰਟ ਮਾਪਿਆ ਗਿਆ                                                                |
| ਤਿੰਨ+ ਸਮਕਾਲੀ ਲੰਬੇ ਕਾਨਟੈਕਸਟ          | ਇੱਕ ਪ੍ਰਕਿਰਿਆ ਉੱਤੇ ਨਾ ਚਲਾਓ | ਕ੍ਰਮਵਾਰ ਚਲਾਓ / ਵਧੇਰੇ RAM | ਡਿਫਾਲਟ ਹੈਵੀਵੇਟ ਐਡਮਿਸ਼ਨ ਵਿੱਚ 1 ਬੇਨਤੀ ਚੱਲ ਸਕਦੀ ਹੈ; RAM ਤੋਂ ਬਿਨਾਂ ਇਸਨੂੰ ਵਧਾਉਣ ਨਾਲ ਅਬੋਰਟ ਮੁੜ ਵਾਪਰਦਾ ਹੈ |

ਬੇਅਰ ਮੈਟਲ ਉੱਤੇ `omniroute serve`, ਜਦੋਂ `OMNIROUTE_MEMORY_MB` **ਸੈੱਟ ਨਾ ਹੋਵੇ**, RAM ਦੇ ~35% ਅਨੁਸਾਰ ਕੈਲੀਬਰੇਟ ਕਰਦਾ ਹੈ (`[512, 4096]` ਤੱਕ ਸੀਮਿਤ)। Docker ਹਮੇਸ਼ਾ `1024` ਸੈੱਟ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ ਅਧਿਕਾਰਤ ਇਮੇਜ ਵਿੱਚ ਇਹ ਕੈਲੀਬ੍ਰੇਸ਼ਨ ਕਦੇ ਨਹੀਂ ਚੱਲਦੀ।

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

## ਸਬਪਾਥ ਉੱਤੇ ਰਿਵਰਸ ਪ੍ਰੌਕਸੀ (Traefik / nginx)

Next.js `basePath` ਨੂੰ standalone ਬੰਡਲ ਵਿੱਚ ਕੰਪਾਇਲ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। OmniRoute ਐਪ ਰੂਟ ਉੱਤੇ ਇੱਕ sentinel ਫ਼ਾਈਲ ਵਿੱਚ ਪਹਿਲਾਂ ਤੋਂ ਸ਼ਾਮਲ ਕੀਤੇ ਮੁੱਲ ਨੂੰ ਦਰਜ ਕਰਦਾ ਹੈ (`npm run build` ਦੌਰਾਨ ਲਿਖਿਆ ਜਾਂਦਾ ਹੈ; `scripts/docker/ensure-docker-base-path.mjs` ਦੁਆਰਾ ਪੜ੍ਹਿਆ ਜਾਂਦਾ ਹੈ) ਅਤੇ ਕੰਟੇਨਰ ਸ਼ੁਰੂ ਹੋਣ ਵੇਲੇ ਇਸਦੀ ਤੁਲਨਾ `OMNIROUTE_BASE_PATH` ਨਾਲ ਕਰਦਾ ਹੈ। ਜਦੋਂ ਇਹ ਵੱਖਰੇ ਹੁੰਦੇ ਹਨ ਅਤੇ ਇਮੇਜ ਡੋਮੇਨ ਰੂਟ ਲਈ ਬਣਾਈ ਗਈ ਸੀ, ਤਾਂ `node dev/run-standalone.mjs` ਦੇ ਚੱਲਣ ਤੋਂ ਪਹਿਲਾਂ entrypoint standalone manifests, embedded `basePath`/`assetPrefix` literals (Next 16 SSR asset URLs ਨੂੰ ਸਿਰਫ਼ `assetPrefix` ਤੋਂ ਰੈਂਡਰ ਕਰਦਾ ਹੈ — patcher ਇਸ ਵਿੱਚ ਵੀ ਸਬਪਾਥ ਨੂੰ ਪ੍ਰਤੀਬਿੰਬਿਤ ਕਰਦਾ ਹੈ), ਪਹਿਲਾਂ ਤੋਂ ਸ਼ਾਮਲ `/_next/static` asset URLs (client-reference manifests, media imports, prerendered error pages) ਅਤੇ client `process.env` shim ਨੂੰ ਮੁੜ ਲਿਖਦਾ ਹੈ।

### Compose ਬਿਲਡ (ਸਿਫ਼ਾਰਸ਼ੀ)

ਦੋਵੇਂ ਵੇਰੀਏਬਲ `.env` ਵਿੱਚ ਸੈੱਟ ਕਰੋ, ਫਿਰ ਮੁੜ ਬਿਲਡ ਕਰੋ ਤਾਂ ਜੋ ਇਮੇਜ ਅਤੇ runtime ਇੱਕਸਾਰ ਹੋਣ:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml`, `OMNIROUTE_BASE_PATH` ਨੂੰ Docker build-arg ਅਤੇ runtime environment variable ਦੋਵਾਂ ਵਜੋਂ ਅੱਗੇ ਭੇਜਦਾ ਹੈ।

### ਪਹਿਲਾਂ ਤੋਂ ਬਣਾਈ root ਇਮੇਜ + runtime ਸਬਪਾਥ

ਪ੍ਰਕਾਸ਼ਿਤ `diegosouzapw/omniroute:*` ਇਮੇਜਾਂ ਡੋਮੇਨ ਰੂਟ ਲਈ ਬਣਾਈਆਂ ਗਈਆਂ ਹਨ। ਤੁਸੀਂ ਫਿਰ ਵੀ runtime ਵੇਲੇ `OMNIROUTE_BASE_PATH` ਸੈੱਟ ਕਰ ਸਕਦੇ ਹੋ; ਕੰਟੇਨਰ startup ਵੇਲੇ ਬੰਡਲ ਨੂੰ ਇੱਕ ਵਾਰ patch ਕਰਦਾ ਹੈ। ਇਸਨੂੰ ਮੇਲ ਖਾਂਦੇ public origin ਨਾਲ ਜੋੜੋ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

ਰਿਵਰਸ ਪ੍ਰੌਕਸੀ ਨੂੰ **ਪੂਰਾ** ਬਾਹਰੀ ਪਾਥ ਅੱਗੇ ਭੇਜਣ ਲਈ ਸੰਰਚਿਤ ਕਰੋ (prefix ਨੂੰ ਨਾ ਹਟਾਓ)। Traefik ਨੂੰ `StripPrefix` ਤੋਂ ਬਿਨਾਂ `PathPrefix(`/omniroute`)` ਨੂੰ ਕੰਟੇਨਰ ਵੱਲ route ਕਰਨਾ ਚਾਹੀਦਾ ਹੈ, ਤਾਂ ਜੋ Next.js ਨੂੰ `/omniroute/...` ਮਿਲੇ ਅਤੇ ਇਹ `/omniroute/_next/...` ਤੋਂ assets ਸਰਵ ਕਰੇ।

Docker healthcheck, ਸਰਗਰਮ `OMNIROUTE_BASE_PATH` ਨਾਲ prefix ਕੀਤੇ ਹਲਕੇ `/healthz` lifecycle endpoint ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ। ਮਨੁੱਖੀ/dashboard diagnostics ਲਈ `/api/monitoring/health` ਉਪਲਬਧ ਰਹਿੰਦਾ ਹੈ; ਕੰਟੇਨਰ HEALTHCHECK ਨੂੰ ਮੁੜ ਇਸ ਵੱਲ ਨਿਰਦੇਸ਼ਿਤ ਕਰਨ ਲਈ (ਉਦਾਹਰਨ ਵਜੋਂ deep health enforcement ਲਈ), `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health` ਸੈੱਟ ਕਰੋ। ਇਹ ਪਾਥ ਇੱਕ **ਡੂੰਘੀ** ਜਾਂਚ ਹੈ (DB + monitoring summary) — ਜੇ ਤੁਸੀਂ ਇਸਨੂੰ ਮੁੜ ਚੁਣਦੇ ਹੋ ਤਾਂ Docker ਦੇ ਘੱਟ-ਵਾਰ ਹੋਣ ਵਾਲੇ `HEALTHCHECK` ਲਈ ਢੁਕਵੀਂ ਹੈ, ਪਰ Kubernetes `livenessProbe` ਅੰਤਰਾਲਾਂ ਲਈ **ਨਹੀਂ**।

orchestrators (Kubernetes, Nomad, ਆਦਿ) ਲਈ:

| ਜਾਂਚ            | ਤਰਜੀਹ ਦਿਓ                                                          | ਪਰਹੇਜ਼ ਕਰੋ                                     |
| --------------- | ------------------------------------------------------------------ | ---------------------------------------------- |
| Liveness        | HTTP `GET /livez`, ਜਾਂ ਮੁੱਖ port ਉੱਤੇ TCP (`PORT`, ਡਿਫਾਲਟ `20128`) | liveness ਵਜੋਂ `/api/monitoring/health`         |
| Readiness       | HTTP `GET /healthz`                                                | ਛੋਟੇ timeouts ਜੋ ਵਿਅਸਤ event loop ਨੂੰ ਬੰਦ ਮੰਨਣ |
| Deep / blackbox | `/api/monitoring/health`                                           | —                                              |

`/healthz` ਪ੍ਰਕਿਰਿਆ lifecycle (`ok` / `starting` / `stopping`) ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ। `/livez` ਸਿਰਫ਼ process-alive ਜਾਂਚ ਹੈ (ਜਦੋਂ ਵੀ handler ਚੱਲ ਸਕੇ ਤਾਂ 200; ਇਹ readiness ਦੀ ਉਡੀਕ ਨਹੀਂ ਕਰਦਾ)। ਦੋਵੇਂ ਹਾਲੇ ਵੀ request handling ਵਾਲੇ ਉਸੇ Node event loop ਉੱਤੇ ਚੱਲਦੇ ਹਨ, ਇਸ ਲਈ CPU-bound catalog ਜਾਂ compression ਕੰਮ ਉਨ੍ਹਾਂ ਨੂੰ ਦੇਰੀ ਕਰ ਸਕਦਾ ਹੈ — ਵਿਅਸਤ ≠ ਬੰਦ। ਜੇ HTTP ਜਾਂਚਾਂ ਦਾ ਸਮਾਂ ਸਮਾਪਤ ਹੋ ਜਾਂਦਾ ਹੈ ਤਾਂ TCP liveness ਨੂੰ ਤਰਜੀਹ ਦਿਓ। ਜਾਂਚਾਂ ਬਾਰੇ ਪੂਰੀ ਸੇਧ:
[Monitoring ਗਾਈਡ — Kubernetes ਜਾਂਚ ਸਿਫ਼ਾਰਸ਼ਾਂ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations)।

## Caddy ਨਾਲ Docker Compose (HTTPS Auto-TLS)

OmniRoute ਨੂੰ Caddy ਦੀ ਆਟੋਮੈਟਿਕ SSL ਪ੍ਰੋਵਿਜ਼ਨਿੰਗ ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਸੁਰੱਖਿਅਤ ਢੰਗ ਨਾਲ ਉਪਲਬਧ ਕਰਵਾਇਆ ਜਾ ਸਕਦਾ ਹੈ। ਯਕੀਨੀ ਬਣਾਓ ਕਿ ਤੁਹਾਡੇ ਡੋਮੇਨ ਦਾ DNS A ਰਿਕਾਰਡ ਤੁਹਾਡੇ ਸਰਵਰ ਦੇ IP ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ।

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # OAuth ਕਾਲਬੈਕਾਂ, ਡੈਸ਼ਬੋਰਡ ਲਿੰਕਾਂ ਅਤੇ ਤਿਆਰ ਕੀਤੇ ਜਨਤਕ URLs ਲਈ ਬ੍ਰਾਊਜ਼ਰ-ਮੁਖੀ ਓਰਿਜਿਨ।
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # ਨਿਯਤ ਜੌਬਾਂ / ਸਵੈ-ਫੈਚਾਂ ਲਈ ਅੰਦਰੂਨੀ ਸਰਵਰ-ਤੋਂ-ਸਰਵਰ URL।
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

Caddy ਅੱਪਸਟ੍ਰੀਮ ਕੰਟੇਨਰ ਲਈ ਮਿਆਰੀ ਫਾਰਵਰਡਿੰਗ ਹੈਡਰ ਸੈੱਟ ਕਰਦਾ ਹੈ। OmniRoute OAuth ਕਾਲਬੈਕਾਂ ਅਤੇ ਤਿਆਰ ਕੀਤੇ ਜਨਤਕ
ਲਿੰਕਾਂ ਲਈ `NEXT_PUBLIC_BASE_URL` ਨੂੰ ਪ੍ਰਮਾਣਿਕ ਜਨਤਕ ਓਰਿਜਿਨ ਵਜੋਂ ਵਰਤਦਾ ਹੈ; ਪ੍ਰਮਾਣਿਤ ਡੈਸ਼ਬੋਰਡ ਰਾਈਟਸ ਇੱਕੋ-ਓਰਿਜਿਨ ਬੇਨਤੀਆਂ ਦੇ ਨਾਲ ਸੈਸ਼ਨ-ਬੱਧ CSRF
ਸੁਰੱਖਿਆ ਵਰਤਦੀਆਂ ਹਨ। `OMNIROUTE_TRUST_PROXY` ਨੂੰ ਸਿਰਫ਼ ਉੱਨਤ ਡਿਪਲੌਇਮੈਂਟਾਂ ਲਈ ਸਮਰੱਥ ਕਰੋ, ਜਿੱਥੇ ਤੁਸੀਂ ਜਾਣਬੁੱਝ ਕੇ
ਚਾਹੁੰਦੇ ਹੋ ਕਿ OmniRoute ਸਪਸ਼ਟ ਸੰਰਚਨਾ ਦੀ ਬਜਾਏ ਭਰੋਸੇਯੋਗ ਫਾਰਵਰਡ ਕੀਤੇ ਹੈਡਰਾਂ ਤੋਂ ਜਨਤਕ ਓਰਿਜਿਨ ਪ੍ਰਾਪਤ ਕਰੇ।

## Cloudflare Quick Tunnel

Docker ਡਿਪਲੌਇਮੈਂਟਾਂ ਲਈ ਡੈਸ਼ਬੋਰਡ ਸਹਾਇਤਾ ਵਿੱਚ `Dashboard → Endpoints` ਉੱਤੇ ਇੱਕ-ਕਲਿੱਕ **Cloudflare Quick Tunnel** ਸ਼ਾਮਲ ਹੈ। ਪਹਿਲੀ ਵਾਰ ਸਮਰੱਥ ਕਰਨ ਉੱਤੇ, ਇਹ ਸਿਰਫ਼ ਲੋੜ ਪੈਣ ਵੇਲੇ `cloudflared` ਡਾਊਨਲੋਡ ਕਰਦਾ ਹੈ, ਤੁਹਾਡੇ ਮੌਜੂਦਾ `/v1` ਐਂਡਪੌਇੰਟ ਲਈ ਇੱਕ ਅਸਥਾਈ ਟਨਲ ਸ਼ੁਰੂ ਕਰਦਾ ਹੈ ਅਤੇ ਤਿਆਰ ਕੀਤਾ `https://*.trycloudflare.com/v1` URL ਸਿੱਧੇ ਤੁਹਾਡੇ ਆਮ ਜਨਤਕ URL ਦੇ ਹੇਠਾਂ ਦਿਖਾਉਂਦਾ ਹੈ।

ਐਂਡਪੌਇੰਟ ਟਨਲ ਪੈਨਲਾਂ (Cloudflare, Tailscale, ngrok) ਨੂੰ ਸਰਗਰਮ ਟਨਲ ਸਥਿਤੀ ਬਦਲੇ ਬਿਨਾਂ `Settings → Appearance` ਤੋਂ ਦਿਖਾਇਆ ਜਾਂ ਲੁਕਾਇਆ ਜਾ ਸਕਦਾ ਹੈ।

### ਟਨਲ ਸੰਬੰਧੀ ਨੋਟਸ

- Quick Tunnel URLs ਅਸਥਾਈ ਹੁੰਦੇ ਹਨ ਅਤੇ ਹਰ ਰੀਸਟਾਰਟ ਤੋਂ ਬਾਅਦ ਬਦਲ ਜਾਂਦੇ ਹਨ।
- OmniRoute ਜਾਂ ਕੰਟੇਨਰ ਦੇ ਰੀਸਟਾਰਟ ਤੋਂ ਬਾਅਦ Quick Tunnels ਆਪਣੇ-ਆਪ ਮੁੜ-ਬਹਾਲ ਨਹੀਂ ਹੁੰਦੇ। ਲੋੜ ਪੈਣ ਉੱਤੇ ਡੈਸ਼ਬੋਰਡ ਤੋਂ ਉਨ੍ਹਾਂ ਨੂੰ ਮੁੜ ਸਮਰੱਥ ਕਰੋ।
- ਪ੍ਰਬੰਧਿਤ ਇੰਸਟਾਲ ਇਸ ਵੇਲੇ `x64` / `arm64` ਉੱਤੇ Linux, macOS ਅਤੇ Windows ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ।
- ਸੀਮਤ ਕੰਟੇਨਰ ਵਾਤਾਵਰਨਾਂ ਵਿੱਚ ਸ਼ੋਰ-ਭਰੀਆਂ QUIC UDP ਬਫ਼ਰ ਚੇਤਾਵਨੀਆਂ ਤੋਂ ਬਚਣ ਲਈ ਪ੍ਰਬੰਧਿਤ Quick Tunnels ਮੂਲ ਰੂਪ ਵਿੱਚ HTTP/2 ਟ੍ਰਾਂਸਪੋਰਟ ਵਰਤਦੇ ਹਨ। ਜੇ ਤੁਸੀਂ ਕੋਈ ਵੱਖਰਾ ਟ੍ਰਾਂਸਪੋਰਟ ਚਾਹੁੰਦੇ ਹੋ, ਤਾਂ `CLOUDFLARED_PROTOCOL=quic` ਜਾਂ `auto` ਸੈੱਟ ਕਰੋ।
- Docker ਇਮੇਜਾਂ ਵਿੱਚ ਸਿਸਟਮ CA ਰੂਟ ਸ਼ਾਮਲ ਹੁੰਦੇ ਹਨ ਅਤੇ ਉਹਨਾਂ ਨੂੰ ਪ੍ਰਬੰਧਿਤ `cloudflared` ਤੱਕ ਪਹੁੰਚਾਇਆ ਜਾਂਦਾ ਹੈ, ਜਿਸ ਨਾਲ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ ਟਨਲ ਬੂਟਸਟਰੈਪ ਹੋਣ ਵੇਲੇ TLS ਭਰੋਸਾ ਅਸਫਲਤਾਵਾਂ ਤੋਂ ਬਚਿਆ ਜਾਂਦਾ ਹੈ।
- ਜੇ ਤੁਸੀਂ ਚਾਹੁੰਦੇ ਹੋ ਕਿ OmniRoute ਕੋਈ ਨਵੀਂ ਬਾਈਨਰੀ ਡਾਊਨਲੋਡ ਕਰਨ ਦੀ ਬਜਾਏ ਮੌਜੂਦਾ ਬਾਈਨਰੀ ਵਰਤੇ, ਤਾਂ `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` ਸੈੱਟ ਕਰੋ।

#### ਵੈੱਬ-ਸੈਸ਼ਨ ਪ੍ਰਦਾਤਾ: `-web` ਇਮੇਜਾਂ

ਉਪਰੋਕਤ ਹਰੇਕ ਚੈਨਲ ਇੱਕ `-web` ਟੈਗ (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`) ਵਜੋਂ ਵੀ ਉਪਲਬਧ ਹੈ, ਜੋ `runner-web` ਸਟੇਜ ਤੋਂ ਬਣਾਇਆ ਗਿਆ ਹੈ — Playwright ਅਤੇ Chromium ਬ੍ਰਾਊਜ਼ਰ ਸਮੇਤ ਉਹੀ ਇਮੇਜ। ਸਧਾਰਨ ਇਮੇਜ Chromium ਤੋਂ **ਬਿਨਾਂ** ਪ੍ਰਦਾਨ ਕੀਤੀ ਜਾਂਦੀ ਹੈ; `gemini-web`, `claude-web` ਅਤੇ `claude-turnstile` ਨੂੰ ਇਸਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।

ਅਸਫਲਤਾ ਸਟਾਰਟਅੱਪ ਸਮੇਂ ਨਹੀਂ, ਸਗੋਂ ਮੁਲਤਵੀ ਹੁੰਦੀ ਹੈ: ਉਹ ਪ੍ਰਦਾਤਾ ਆਪਣੇ ਮਾਡਲ ਸੂਚੀਬੱਧ ਕਰਦੇ ਹਨ ਅਤੇ ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ ਕਨੈਕਟ ਹੋਏ ਦਿਖਾਈ ਦਿੰਦੇ ਹਨ, ਅਤੇ ਸਿਰਫ਼ ਪਹਿਲੀ ਬੇਨਤੀ ਇਸ ਸੁਨੇਹੇ ਨਾਲ ਅਸਫਲ ਹੁੰਦੀ ਹੈ

```
[500]: Failed to load external module playwright: Error: Cannot find module
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

ਜੇ ਤੁਸੀਂ ਉਹਨਾਂ ਪ੍ਰਦਾਤਾਵਾਂ ਦੀ ਵਰਤੋਂ ਕਰਦੇ ਹੋ, ਤਾਂ ਉਸੇ ਚੈਨਲ ਦਾ `-web` ਟੈਗ ਪੁੱਲ ਕਰੋ ਜਿਸ ਉੱਤੇ ਤੁਸੀਂ ਪਹਿਲਾਂ ਹੀ ਹੋ — ਹੋਰ ਕੁਝ ਨਹੀਂ ਬਦਲਦਾ। npm/CLI ਇੰਸਟਾਲ (ਕੋਈ Docker ਇਮੇਜ ਨਹੀਂ) ਉੱਤੇ, ਇਸਦੇ ਬਰਾਬਰ ਗੁੰਮ ਹਿੱਸਾ ਬ੍ਰਾਊਜ਼ਰ ਬਾਈਨਰੀ ਹੈ: ਹੋਸਟ ਉੱਤੇ `npx playwright install chromium` ਚਲਾਓ।

#### ਪ੍ਰੀ-ਰਿਲੀਜ਼ ਚੈਨਲ ਦੀ ਵਰਤੋਂ

`next` ਚੈਨਲ ਨੂੰ ਮੌਜੂਦਾ ਡਿਫਾਲਟ `release/v*` ਬ੍ਰਾਂਚ ਉੱਤੇ ਹਰ push ਨਾਲ ਮੁੜ ਬਣਾਇਆ ਜਾਂਦਾ ਹੈ ਅਤੇ AMD64 ਤੇ ARM64 ਦੋਵਾਂ ਲਈ ਪ੍ਰਕਾਸ਼ਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਪੁਰਾਣੀਆਂ maintenance ਬ੍ਰਾਂਚਾਂ ਇਸਨੂੰ overwrite ਨਹੀਂ ਕਰ ਸਕਦੀਆਂ। ਇਹ ਚੈਨਲ ਉਹਨਾਂ ਸੁਧਾਰਾਂ ਲਈ pull ਕੀਤੀ ਜਾ ਸਕਣ ਵਾਲੀ image ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ ਜੋ ਅਗਲਾ stable tag ਬਣਾਏ ਜਾਣ ਤੋਂ ਪਹਿਲਾਂ active release ਬ੍ਰਾਂਚ ਵਿੱਚ merge ਹੋ ਚੁੱਕੇ ਹਨ।

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Docker Compose ਲਈ, ਚੁਣੇ ਹੋਏ profile ਵੱਲੋਂ ਵਰਤੇ ਜਾਂਦੇ image tag ਨੂੰ override ਕਰੋ, ਫਿਰ service ਨੂੰ pull ਕਰਕੇ ਮੁੜ ਬਣਾਓ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### ਸੁਰੱਖਿਆ ਅਤੇ rollback

`next` ਇੱਕ ਬਦਲਦਾ ਰਹਿਣ ਵਾਲਾ pre-release ਚੈਨਲ ਹੈ। ਇਹ active release ਬ੍ਰਾਂਚ ਉੱਤੇ ਕਿਸੇ ਵੀ push ਨਾਲ ਬਦਲ ਸਕਦਾ ਹੈ ਅਤੇ **production ਵਰਤੋਂ ਲਈ ਸਮਰਥਿਤ ਨਹੀਂ ਹੈ**। ਕਿਸੇ ਖ਼ਾਸ build ਦਾ ਮੁਲਾਂਕਣ ਕਰਦੇ ਸਮੇਂ image digest ਨੂੰ pin ਕਰੋ:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

ਟੈਸਟ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ OmniRoute data volume ਜਾਂ bind-mounted data directory ਦਾ backup ਲਓ। rollback ਕਰਨ ਲਈ, ਪਹਿਲਾਂ ਵਰਤੇ ਗਏ stable version ਜਾਂ digest ਨੂੰ restore ਕਰੋ ਅਤੇ container ਨੂੰ ਮੁੜ ਬਣਾਓ:

```bash
docker pull diegosouzapw/omniroute:<stable-version>
docker compose up -d
```

release-branch build ਕਦੇ ਵੀ `latest` ਨੂੰ ਬਦਲ ਨਹੀਂ ਸਕਦਾ; ਕੇਵਲ ਇੱਕ ਯੋਗ stable semantic version ਹੀ stable pointer ਨੂੰ promote ਕਰ ਸਕਦਾ ਹੈ। `next` images ਵਿੱਚ release image inspection ਅਤੇ CRITICAL vulnerabilities ਨੂੰ ਰੋਕਣ ਵਾਲਾ gate ਬਰਕਰਾਰ ਰਹਿੰਦਾ ਹੈ।

**`latest`, git ਲਈ ਨਵੀਨਤਮ ਹੋਣ ਦੀ ਗਾਰੰਟੀ ਨਹੀਂ ਹੈ।** `main` ਜਾਂ active `release/v*` ਬ੍ਰਾਂਚ ਵਿੱਚ merge ਕੀਤੇ ਗਏ ਸੁਧਾਰ `:latest` ਵਿੱਚ ਉਦੋਂ ਤੱਕ **ਸ਼ਾਮਲ ਨਹੀਂ ਹੁੰਦੇ**, ਜਦੋਂ ਤੱਕ ਇੱਕ stable SemVer image ਪ੍ਰਕਾਸ਼ਿਤ ਨਹੀਂ ਹੋ ਜਾਂਦੀ ਅਤੇ publish job `:latest` ਨੂੰ promote ਨਹੀਂ ਕਰਦਾ (ਉਸ SemVer ਦੇ ਸਮਾਨ digest ਨਾਲ)। ਜੇ GitHub ਉੱਤੇ ਸੁਧਾਰ ਪਹਿਲਾਂ ਹੀ ਦਿਖਾਈ ਦੇ ਰਿਹਾ ਹੈ ਪਰ `latest` ਰੁਕਿਆ ਹੋਇਆ ਲੱਗਦਾ ਹੈ, ਤਾਂ release ਬ੍ਰਾਂਚ ਨੂੰ ਟੈਸਟ ਕਰਨ ਲਈ `:next` pull ਕਰੋ ਜਾਂ SemVer tag ਦੀ ਉਡੀਕ ਕਰੋ।

| ਤੁਸੀਂ ਕੀ ਚਾਹੁੰਦੇ ਹੋ                                                              | ਵਰਤੋਂ                                   |
| -------------------------------------------------------------------------------- | --------------------------------------- |
| GitOps / production ਜਿਸ ਵਿੱਚ ਬਿਨਾਂ ਇਰਾਦੇ ਦੇ ਬਦਲਾਅ ਨਹੀਂ ਹੋਣੇ ਚਾਹੀਦੇ               | `:X.Y.Z` (ਜਾਂ image digest) ਨੂੰ pin ਕਰੋ |
| ਪ੍ਰਕਾਸ਼ਿਤ stable releases ਦੀ ਪਾਲਣਾ ਕਰਨੀ ਅਤੇ ਹਰ release ਉੱਤੇ recreate ਸਵੀਕਾਰ ਕਰਨਾ | `:latest`                               |
| ਅਣ-ਪ੍ਰਕਾਸ਼ਿਤ `release/v*` commits ਨੂੰ ਟੈਸਟ ਕਰਨਾ                                  | `:next` (production ਲਈ ਨਹੀਂ)            |
| `main` ਨੂੰ ਟੈਸਟ ਕਰਨਾ                                                             | `:main` (production ਲਈ ਨਹੀਂ)            |

| ਲਾਈਵਨੈੱਸ         | `PORT` ਉੱਤੇ TCP (ਡਿਫੌਲਟ `20128`), ਜਾਂ ਸੌਫ਼ਟ HTTP `/healthz` | `/api/monitoring/health`                               |
| ਰੈਡੀਨੈੱਸ         | HTTP `GET /healthz`                                         | ਅਜਿਹੇ ਸਖ਼ਤ ਟਾਈਮਆਊਟ ਜੋ ਵਿਅਸਤ ਇਵੈਂਟ ਲੂਪ ਨੂੰ ਬੰਦ ਮੰਨਦੇ ਹਨ |
| ਡੀਪ / ਮਨੁੱਖਾਂ ਲਈ | `/api/monitoring/health`                                    | ਸਵੈਚਾਲਿਤ kubelet ਲਾਈਵਨੈੱਸ                              |

**ਅੱਪਗ੍ਰੇਡ:** ਹਰੇਕ ਸੈਸ਼ਨ ਦੇ ਡਿਸਕਨੈਕਟ ਹੋਣ ਦੀ ਉਮੀਦ ਰੱਖੋ। ਜੇ ਸੰਭਵ ਹੋਵੇ ਤਾਂ ਕਲਾਇੰਟਾਂ ਨੂੰ ਡ੍ਰੇਨ ਕਰੋ; ਡਿਫੌਲਟ SQLite ਉੱਤੇ ਕੋਈ ਰੋਲਿੰਗ ਅੱਪਡੇਟ ਨਹੀਂ ਹੈ। Compose `restart: unless-stopped` ਦੇ ਨਾਲ Docker `HEALTHCHECK` ਵੀ ਕੰਟੇਨਰ ਦੇ Unhealthy ਹੋਣ ਉੱਤੇ ਇਕਲੌਤੀ ਪ੍ਰਕਿਰਿਆ ਨੂੰ ਬਦਲ ਦੇਵੇਗਾ — ਪ੍ਰਭਾਵ ਦਾ ਘੇਰਾ ਉਹੀ ਰਹੇਗਾ।

**ਇੱਕੋ ਰੈਪਲਿਕਾ** ਲਈ Kubernetes ਸਨਿੱਪਟ (Recreate ਲਾਜ਼ਮੀ ਹੈ; ਇੱਕ SQLite ਫ਼ਾਈਲ ਨਾਲ `replicas` ਨਾ ਵਧਾਓ):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` ਸਲੀਪ kube ਨੂੰ SIGTERM ਤੋਂ ਪਹਿਲਾਂ Service ਐਂਡਪੌਇੰਟ ਹਟਾਉਣ ਦਿੰਦੀ ਹੈ, ਤਾਂ ਜੋ **ਨਵਾਂ** ਟ੍ਰੈਫ਼ਿਕ ਬੰਦ ਹੋ ਰਹੀ ਪ੍ਰਕਿਰਿਆ ਤੱਕ ਪਹੁੰਚਣਾ ਬੰਦ ਕਰ ਦੇਵੇ। ਚੱਲ ਰਹੇ `/v1/responses` SSE ਨੂੰ ਹੈਵੀਵੇਟ ਐਡਮਿਸ਼ਨ ਲੀਜ਼ਾਂ ਰਾਹੀਂ `SHUTDOWN_TIMEOUT_MS` (ਡਿਫੌਲਟ 30s) ਤੱਕ ਡ੍ਰੇਨ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (#11015)। ਜਿਹੜੀਆਂ ਨਵੀਆਂ ਬੇਨਤੀਆਂ ਫਿਰ ਵੀ ਪ੍ਰਕਿਰਿਆ ਤੱਕ ਪਹੁੰਚ ਜਾਂਦੀਆਂ ਹਨ, ਉਨ੍ਹਾਂ ਨੂੰ `503` + `Retry-After: 5` ਮਿਲਦਾ ਹੈ। ਬਦਲਵਾਂ ਰੈਪਲਿਕਾ Ready ਹੋਣ ਤੱਕ Recreate ਦਾ ਖਾਲੀ-ਐਂਡਪੌਇੰਟ ਅੰਤਰਾਲ ਇੱਕ ਪੂਰਾ ਆਊਟੇਜ ਹੀ ਰਹਿੰਦਾ ਹੈ — ਇਹ SQLite ਟੋਪੋਲੋਜੀ ਦੇ ਕਾਰਨ ਹੈ, ਪ੍ਰੋਬ ਦੀ ਗ਼ਲਤ ਸੰਰਚਨਾ ਦੇ ਕਾਰਨ ਨਹੀਂ।

ਬਾਹਰੀ Postgres / ਮਲਟੀ-ਰਾਈਟਰ HA ਕੋਈ **ਦਸਤਾਵੇਜ਼ਬੱਧ** ਮਿਆਰੀ ਮਾਰਗ ਨਹੀਂ ਹੈ। ਜੇ ਤੁਹਾਨੂੰ HA ਦੀ ਲੋੜ ਹੈ, ਤਾਂ ਇੱਕੋ ਰੈਪਲਿਕਾ ਰੱਖੋ ਜਾਂ ਅਜਿਹੀ ਟੋਪੋਲੋਜੀ ਚਲਾਓ ਜਿਸਨੂੰ ਪ੍ਰੋਜੈਕਟ ਨੇ ਵੱਖਰੇ ਤੌਰ ਉੱਤੇ ਟੈਸਟ ਅਤੇ ਦਸਤਾਵੇਜ਼ਬੱਧ ਕੀਤਾ ਹੋਵੇ। Postgres/MySQL ਸੰਬੰਧੀ ਕੰਮ [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) ਵਿੱਚ ਹੈ। ਜਦੋਂ ਤੱਕ ਇਹ ਜਾਰੀ ਨਹੀਂ ਹੁੰਦਾ, **ਵੱਡੀਆਂ** `/v1/responses` ਦੀ ਸਮਰੱਥਾ ਵਧਾਉਣ ਦਾ ਇਕਲੌਤਾ ਸਮਰਥਿਤ ਤਰੀਕਾ N ਸੁਤੰਤਰ ਪ੍ਰਕਿਰਿਆਵਾਂ (ਅਗਲਾ ਭਾਗ) ਹਨ, ਨਾ ਕਿ ਇੱਕ ਵਾਲਿਊਮ ਉੱਤੇ `replicas > 1`।

## ਸਕੇਲ-ਆਉਟ: N ਸੁਤੰਤਰ ਪ੍ਰਕਿਰਿਆਵਾਂ

ਇੱਕ Node ਪ੍ਰਕਿਰਿਆ **ਇੱਕ V8 heap** ਹੁੰਦੀ ਹੈ। ਦੋ ਆਪਸ ਵਿੱਚ ਓਵਰਲੈਪ ਕਰਦੀਆਂ ~3 MiB / ~750k-token coding-agent `POST /v1/responses` ਬੇਨਤੀਆਂ (RTK + Caveman) ਉਸ heap ਨੂੰ ~12 Gi ਉੱਤੇ ਅਬੋਰਟ ਕਰ ਦਿੰਦੀਆਂ ਹਨ (`FATAL ERROR: Reached heap limit`) ਅਤੇ 16 Gi cgroup ਵਿੱਚ OOM ਕਰ ਸਕਦੀਆਂ ਹਨ। [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ਵੇਖੋ। ਇਹ ਮਾਪ ਇੱਕ **ਮੈਮੋਰੀ-ਬਜਟ** ਚੇਤਾਵਨੀ ਹੈ, ਦੋ ਸਮਕਾਲੀ ਲੰਬੀਆਂ `/v1/responses` ਲਈ ਉਤਪਾਦ ਦੀ ਹਾਰਡ ਅਧਿਕਤਮ ਸੀਮਾ ਨਹੀਂ। ਹੈਵੀਵੇਟ ਚੈਟ ਦਾਖਲਾ, ਉਸੇ V8/cgroup ਸੀਮਾ ਤੋਂ ਆਟੋਮੈਟਿਕ ਤੌਰ ’ਤੇ ਨਿਰਧਾਰਤ ingest byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) ਰਾਹੀਂ ਨਿਯੰਤਰਿਤ ਹੁੰਦਾ ਹੈ — ਪਹਿਲਾਂ ਹੀ ਸਹੀ ਆਕਾਰ ਦਿੱਤੀ ਪ੍ਰਕਿਰਿਆ ਉੱਤੇ ਇਸਨੂੰ ਵਧਾ ਕੇ ਓਵਰਰਾਈਡ ਕਰਨਾ (ਜਾਂ ਪੁਰਾਣੀ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ਬੇਨਤੀ-ਗਿਣਤੀ ਸੀਮਾ ਸੈੱਟ ਕਰਨਾ) ਅਬੋਰਟ ਨੂੰ ਮੁੜ ਲਿਆਉਂਦਾ ਹੈ। ਛੋਟੀਆਂ ਚੈਟਾਂ, `/healthz`, `/v1/models`, ਅਤੇ MCP ਉਸ ਸੀਮਾ ਵਿੱਚ **ਸ਼ਾਮਲ ਨਹੀਂ** ਹਨ।

### ਇੱਕ ਪ੍ਰਕਿਰਿਆ: ਦੋ ਤੋਂ ਵੱਧ ਲੰਬੀਆਂ `/v1/responses`

ਇੱਕ **ਸਿਹਤਮੰਦ** ਪ੍ਰਕਿਰਿਆ (heap, `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO` ਤੋਂ ਹੇਠਾਂ; ਡਿਫਾਲਟ `0.75`) ਦੋ ਤੋਂ ਵੱਧ ਸਮਕਾਲੀ ਲੰਬੀਆਂ `POST /v1/responses` ਬੇਨਤੀਆਂ ਚਲਾ **ਸਕਦੀ ਹੈ**, ਜਦੋਂ ਪ੍ਰਕਿਰਿਆ-ਵਿਆਪੀ inflight-byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) ਵਿੱਚ ਹਾਲੇ ਥਾਂ ਹੋਵੇ। `OMNIROUTE_CHAT_LARGE_BODY_BYTES` ਦੇ ਬਰਾਬਰ ਜਾਂ ਇਸ ਤੋਂ ਵੱਡੀਆਂ bodies (ਡਿਫਾਲਟ 256 KiB) structure-heavy ਬੇਨਤੀਆਂ ਵਾਂਗ ਉਹੀ ਹੈਵੀਵੇਟ lease ਲੈਂਦੀਆਂ ਹਨ ਅਤੇ ਉਹੀ [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` escape (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ਵਰਤਦੀਆਂ ਹਨ। ਦਰਜਨਾਂ ਸਮਕਾਲੀ ਲੰਬੇ SSE clients (ਓਪਰੇਟਰਾਂ ਨੂੰ ਅਕਸਰ 40–50 ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ) ਇੱਕ **ਮੈਮੋਰੀ-ਬਜਟ** ਦਾ ਸਵਾਲ ਹੈ — heap + primary/headroom slots + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ਦਾ ਆਕਾਰ ਨਿਰਧਾਰਤ ਕਰੋ — ਇਹ ਉਤਪਾਦ ਦੀ ਕੋਈ ਹਾਰਡ “ਅਧਿਕਤਮ 2” ਸੀਮਾ ਨਹੀਂ ਹੈ। ਦਬਾਅ ਹੇਠਲਾ heap ਫਿਰ ਵੀ ਮੁੜ ਕੋਸ਼ਿਸ਼ਯੋਗ `503` ਨਾਲ ਲੋਡ ਘਟਾਉਂਦਾ ਹੈ, ਤਾਂ ਜੋ #7849 ਮੁੜ ਨਾ ਆਵੇ।

**heaps ਦੀ ਗਿਣਤੀ ਵਧਾਉਣ** (ਸੁਤੰਤਰ V8 old-spaces) ਲਈ **ਅੱਜ ਹੀ**:

| ਇਹ ਕਰੋ                                                                                                                                                     | ਇਹ ਨਾ ਕਰੋ                                               |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| **N containers/pods** ਚਲਾਓ, ਹਰ ਇੱਕ ਲਈ ਇਸਦਾ **ਆਪਣਾ** `DATA_DIR` / volume ਹੋਵੇ                                                                               | ਇੱਕ SQLite file ਲਈ `replicas > 1` ਸੈੱਟ ਕਰੋ              |
| heap / inflight-byte budget ਦੇ ਆਧਾਰ ’ਤੇ heavy in-flight + healthy-headroom ਦਾ ਆਕਾਰ ਨਿਰਧਾਰਤ ਕਰੋ; 1–2 ਸੰਭਾਲੂ #7849 ਡਿਫਾਲਟ ਹੈ, ਉਤਪਾਦ ਦੀ ਹਾਰਡ ਅਧਿਕਤਮ ਸੀਮਾ ਨਹੀਂ | ਇੱਕ ਪ੍ਰਕਿਰਿਆ ਨੂੰ 8× RAM ਅਤੇ ਬੇਹੱਦ count cap ਦਿਓ         |
| ਵਿਕਲਪਿਕ: **ਸਾਂਝੇ quota counters** ਲਈ `QUOTA_STORE_DRIVER=redis` + `QUOTA_STORE_REDIS_URL`                                                                  | Redis ਨੂੰ ਸਾਂਝਾ SQLite ਸਮਝੋ — ਇਹ ਅਜਿਹਾ ਨਹੀਂ ਹੈ          |
| provider secrets ਨੂੰ ਹਰ instance ਵਿੱਚ ਡੁਪਲੀਕੇਟ ਕਰੋ (ਜਾਂ ਵੰਡੇ ਹੋਏ dashboards ਸਵੀਕਾਰ ਕਰੋ)                                                                    | instances ਵਿੱਚ ਇੱਕ dashboard / ਇੱਕ call-log ਦੀ ਉਮੀਦ ਕਰੋ |
| ਅੱਗੇ ਕੋਈ ਵੀ load balancer ਲਗਾਓ; API key ਜਾਂ session ਅਨੁਸਾਰ sticky routing ਕਾਫ਼ੀ ਹੈ                                                                         | ਕਿਸੇ vendor-specific size-aware middleware ਦੀ ਲੋੜ ਸਮਝੋ  |

ਹਾਰਡਵੇਅਰ: ਹਰ instance ਦੀਆਂ ਸਮਕਾਲੀ ਲੰਬੀਆਂ `/v1/responses` ਇੱਕ **ਮੈਮੋਰੀ-ਬਜਟ** ਦਾ ਸਵਾਲ ਹਨ (heap + inflight-byte / #10110)। `N` ਸੁਤੰਤਰ `DATA_DIR`s ਫਿਰ ਵੀ heaps ਦੀ ਗਿਣਤੀ ਵਧਾਉਂਦੇ ਹਨ: host RAM ਨੂੰ `N × cgroup` ਸੰਭਾਲਣਾ ਪਵੇਗਾ, ਨਾ ਕਿ “N=8 ਵਾਲਾ ਇੱਕ 16 Gi pod।” ਇੱਕ SQLite file ਉੱਤੇ ਕਦੇ ਵੀ `replicas > 1` ਨਾ ਵਰਤੋ।

Compose ਖਾਕਾ (ਦੋ heaps, ਦੋ volumes — `deploy.replicas: 2` ਨਹੀਂ):

```yaml
services:
  omniroute-a:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

In-process density (HTTP isolate ਤੋਂ ਬਾਹਰ compression) [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023) ਹੈ। ਸਾਂਝੀ durable state ਉੱਤੇ ਇੱਕ logical cluster [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) ਹੈ।

## Docker ਦੇ ਅੰਦਰ Gemini ਦੀਆਂ ਖੇਤਰੀ ਗਲਤੀਆਂ

Google AI Studio / Gemini API, FAILED_PRECONDITION ਦੇ ਨਾਲ HTTP 400 ਅਤੇ
`API ਦੀ ਵਰਤੋਂ ਲਈ ਵਰਤੋਂਕਾਰ ਦਾ ਟਿਕਾਣਾ ਸਮਰਥਿਤ ਨਹੀਂ ਹੈ।` ਵਾਪਸ ਕਰ ਸਕਦਾ ਹੈ। ਹੋਸਟ ਉੱਤੇ ਸਫਲ ਬੇਨਤੀ
ਇਹ ਸਾਬਤ ਨਹੀਂ ਕਰਦੀ ਕਿ ਕੰਟੇਨਰ ਵੀ ਉਹੀ ਆਊਟਬਾਊਂਡ ਰੂਟ ਵਰਤਦਾ ਹੈ। DNS ਕ੍ਰਮ,
IPv4/IPv6 ਕਨੈਕਟਿਵਿਟੀ, VPN ਰੂਟਿੰਗ ਅਤੇ ਸੰਰਚਿਤ ਪ੍ਰੌਕਸੀਆਂ ਵੱਖਰੀਆਂ ਹੋ ਸਕਦੀਆਂ ਹਨ।
[Google ਦੇ ਸਮਰਥਿਤ ਖੇਤਰਾਂ](https://ai.google.dev/gemini-api/docs/available-regions)
ਦੇ ਨਾਲ-ਨਾਲ ਅਸਲ ਕਨੈਕਸ਼ਨ ਰੂਟ ਦੀ ਵੀ ਜਾਂਚ ਕਰੋ; ਸਿਰਫ਼ ਇਹ ਗਲਤੀ ਕਿਸੇ ਖ਼ਰਾਬ API ਕੁੰਜੀ ਦੀ ਪਛਾਣ ਨਹੀਂ ਕਰਦੀ।

### ਕਨੈਕਸ਼ਨ-ਵਿਸ਼ੇਸ਼ ਪ੍ਰੌਕਸੀ ਨੂੰ ਤਰਜੀਹ ਦਿਓ

ਪ੍ਰਭਾਵਿਤ Gemini ਕਨੈਕਸ਼ਨ ਲਈ OmniRoute ਦੀ
[ਪ੍ਰਤੀ-ਕਨੈਕਸ਼ਨ ਪ੍ਰੌਕਸੀ ਸੰਰਚਨਾ](../ops/PROXY_GUIDE.md#4-level-proxy-system)
ਵਰਤੋ, ਫਿਰ ਉਸੇ ਮਾਡਲ ਨਾਲ **ਕਨੈਕਸ਼ਨ ਦੀ ਜਾਂਚ ਕਰੋ** ਅਤੇ ਇੱਕ ਛੋਟੀ ਬੇਨਤੀ ਦੁਬਾਰਾ ਭੇਜੋ।
ਇਸ ਨਾਲ ਰੂਟਿੰਗ ਤਬਦੀਲੀ ਸਿਰਫ਼ ਉਸ ਕਨੈਕਸ਼ਨ ਤੱਕ ਸੀਮਤ ਰਹਿੰਦੀ ਹੈ। ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਪ੍ਰੌਕਸੀ
ਕੰਟੇਨਰ ਤੋਂ ਪਹੁੰਚਯੋਗ ਹੈ ਅਤੇ ਕਨੈਕਸ਼ਨ ਵਾਸਤਵ ਵਿੱਚ ਉਸੇ ਨੂੰ ਚੁਣਦਾ ਹੈ। ਰੂਟ ਬਦਲਣ ਨਾਲ
ਅੱਪਸਟ੍ਰੀਮ ਖੇਤਰੀ ਯੋਗਤਾ ਦੀ ਗਾਰੰਟੀ ਨਹੀਂ ਮਿਲਦੀ।

### ਹੋਸਟ ਅਤੇ ਕੰਟੇਨਰ ਨੈੱਟਵਰਕਿੰਗ ਦੀ ਤੁਲਨਾ ਕਰੋ

ਪ੍ਰਮਾਣਿਤ ਨਤੀਜਿਆਂ ਦੀ ਤੁਲਨਾ ਕਰਦੇ ਸਮੇਂ ਕੁੰਜੀ, ਮਾਡਲ ਅਤੇ ਬੇਨਤੀ ਇੱਕੋ ਜਿਹੇ ਰੱਖੋ; ਕਿਸੇ
ਇਸ਼ੂ ਵਿੱਚ ਕਦੇ ਵੀ ਪ੍ਰਮਾਣ-ਪੱਤਰ, ਪ੍ਰੌਕਸੀ ਪਾਸਵਰਡ ਜਾਂ ਪੂਰੇ ਅਧਿਕਾਰਕਰਨ ਹੈਡਰ ਪੇਸਟ ਨਾ ਕਰੋ।
ਪਹਿਲਾਂ ਜਾਂਚੋ ਕਿ OS ਰਿਜ਼ਾਲਵਰ ਕਿਹੜੀਆਂ ਐਡਰੈੱਸ ਫੈਮਿਲੀਆਂ ਪੇਸ਼ ਕਰਦਾ ਹੈ; ਹੋਸਟ ਅਤੇ
ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ ਇੱਕੋ ਕਮਾਂਡ ਵਰਤੋ:

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

`omniroute` ਨੂੰ ਤੁਹਾਡੇ ਵੱਲੋਂ ਚਲਾਈ ਜਾ ਰਹੀ ਸੇਵਾ ਨਾਲ ਬਦਲੋ (ਉਦਾਹਰਨ ਲਈ,
`omniroute-web`)। ਇਹ ਕਮਾਂਡਾਂ ਪ੍ਰਮਾਣ-ਪੱਤਰਾਂ ਜਾਂ IP ਐਡਰੈੱਸਾਂ ਤੋਂ ਬਿਨਾਂ ਐਡਰੈੱਸ
ਫੈਮਿਲੀਆਂ ਪ੍ਰਿੰਟ ਕਰਦੀਆਂ ਹਨ। ਵਾਪਸ ਆਇਆ `6` ਸਿਰਫ਼ IPv6 DNS ਨਤੀਜਾ ਦਰਸਾਉਂਦਾ ਹੈ:
ਇਹ ਵਰਤੋਂਯੋਗ IPv6 ਰੂਟ ਜਾਂ API ਪਹੁੰਚ ਨੂੰ **ਸਾਬਤ ਨਹੀਂ** ਕਰਦਾ। ਜਿੱਥੇ `curl`
ਇੰਸਟਾਲ ਹੈ, ਦੋਵਾਂ ਵਾਤਾਵਰਣਾਂ ਵਿੱਚ `curl -4 -I https://generativelanguage.googleapis.com`
ਦੀ ਤੁਲਨਾ `curl -6 -I https://generativelanguage.googleapis.com` ਨਾਲ ਕਰੋ।
ਕੋਈ HTTP ਜਵਾਬ ਉਸ ਜਾਂਚ ਲਈ ਕਨੈਕਟਿਵਿਟੀ ਸਾਬਤ ਕਰਦਾ ਹੈ, ਭਾਵੇਂ ਉਹ ਇੱਕ ਗੈਰ-ਪ੍ਰਮਾਣਿਤ
ਗਲਤੀ ਹੀ ਹੋਵੇ; ਸਿਰਫ਼ ਪ੍ਰਮਾਣਿਤ ਮਾਡਲ ਬੇਨਤੀ ਹੀ Gemini ਯੋਗਤਾ ਦੀ ਜਾਂਚ ਕਰਦੀ ਹੈ।

### ਹੋਸਟ-ਪੱਧਰੀ ਵਿਕਲਪ: ਕਾਰਜਸ਼ੀਲ IPv6 ਅਤੇ ਰਿਜ਼ਾਲਵਰ ਨੀਤੀ

[#12762](https://github.com/diegosouzapw/OmniRoute/issues/12762) ਦੇ ਰਿਪੋਰਟਰ ਨੇ
ਆਪਣੇ ਵਾਤਾਵਰਣ ਵਿੱਚ ਕੰਟੇਨਰ IPv6 ਸਮਰੱਥ ਕਰਕੇ ਅਤੇ glibc ਐਡਰੈੱਸ ਚੋਣ ਬਦਲ ਕੇ ਪਹੁੰਚ
ਮੁੜ ਬਹਾਲ ਕੀਤੀ। ਇਸਨੂੰ ਵਾਤਾਵਰਣ-ਵਿਸ਼ੇਸ਼ ਵਿਕਲਪ ਵਜੋਂ ਵਰਤੋ। ਰਿਜ਼ਾਲਵਰ ਤਰਜੀਹਾਂ ਨੂੰ
ਵਿਵਸਥਿਤ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਕਾਰਜਸ਼ੀਲ ਹੋਸਟ IPv6, ਕੰਟੇਨਰ ਈਗ੍ਰੈੱਸ/ਰੂਟਿੰਗ ਅਤੇ ਫਾਇਰਵਾਲ
ਨਿਯਮਾਂ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ। ਸਿਰਫ਼ ਇੱਕ ਨਿੱਜੀ ULA ਐਡਰੈੱਸ ਜਨਤਕ IPv6 ਕਨੈਕਟਿਵਿਟੀ ਸਥਾਪਤ
ਨਹੀਂ ਕਰਦਾ।

Compose ਦੇ ਡਿਫੌਲਟ ਨੈੱਟਵਰਕ ਨਾਲ ਪਹਿਲਾਂ ਤੋਂ ਜੁੜੀਆਂ ਸੇਵਾਵਾਂ ਲਈ, ਇਹ ਫ੍ਰੈਗਮੈਂਟ
ਉਸ ਨੈੱਟਵਰਕ ਉੱਤੇ IPv6 ਸਮਰੱਥ ਕਰਦਾ ਹੈ; ਆਪਣੀ ਬਾਕੀ ਸੇਵਾ, ਪੋਰਟਾਂ, ਵਾਲਿਊਮਾਂ ਅਤੇ
ਸੰਰਚਨਾ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖੋ:

```yaml
networks:
  default:
    enable_ipv6: true
```

ਕਿਸੇ ਨਾਮਿਤ ਨੈੱਟਵਰਕ ਲਈ, ਇਸਨੂੰ ਉਸ ਨੈੱਟਵਰਕ ਉੱਤੇ ਸਮਰੱਥ ਕਰੋ ਜਿਸ ਨਾਲ ਸੇਵਾ ਵਾਸਤਵ
ਵਿੱਚ ਜੁੜਦੀ ਹੈ। Docker ਇੱਕ ULA ਸਬਨੈੱਟ ਨਿਰਧਾਰਤ ਕਰ ਸਕਦਾ ਹੈ; ਕੋਈ ਸਪਸ਼ਟ,
ਗੈਰ-ਓਵਰਲੈਪਿੰਗ ਸਬਨੈੱਟ ਸਿਰਫ਼ ਉਦੋਂ ਚੁਣੋ ਜਦੋਂ ਤੁਹਾਡੇ ਨੈੱਟਵਰਕ ਨੂੰ ਇਸਦੀ ਲੋੜ ਹੋਵੇ।
[Docker IPv6 ਨੈੱਟਵਰਕਿੰਗ](https://docs.docker.com/engine/daemon/ipv6/)
ਅਤੇ [Compose ਨੈੱਟਵਰਕ ਵਿਕਲਪ](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6)
ਵੇਖੋ।

ਕਿਸੇ **glibc-ਅਧਾਰਿਤ ਇਮੇਜ** ਉੱਤੇ, `/etc/gai.conf` ਐਡਰੈੱਸ ਚੋਣ ਨੂੰ ਬਦਲ ਸਕਦੀ ਹੈ।
ਮੌਜੂਦਾ ਰਿਪੋਜ਼ਟਰੀ Dockerfile Debian ਵਰਤਦੀ ਹੈ; ਕਸਟਮ musl-ਅਧਾਰਿਤ ਇਮੇਜਾਂ ਵਿੱਚ
ਇਹ ਵਿਧੀ ਉਪਲਬਧ ਨਹੀਂ ਹੁੰਦੀ। ਰਿਪੋਰਟ ਕੀਤੀ ਵਿਵਸਥਾ ULA ਲੇਬਲ ਨੂੰ
`label fc00::/7 6` ਤੋਂ `label fc00::/7 1` ਵਿੱਚ ਬਦਲਦੀ ਹੈ। ਇਮੇਜ ਦੀ ਪੂਰੀ ਨੀਤੀ
ਸਾਰਣੀ ਤੋਂ ਸ਼ੁਰੂ ਕਰੋ ਅਤੇ ਇਸ ਦੀਆਂ ਹੋਰ ਐਂਟਰੀਆਂ ਬਰਕਰਾਰ ਰੱਖੋ: ਇੱਕ `label` ਜਾਂ
`precedence` ਐਂਟਰੀ ਜੋੜਨ ਨਾਲ ਉਹ ਡਿਫੌਲਟ ਸਾਰਣੀ ਬਦਲ ਜਾਂਦੀ ਹੈ, ਇਸ ਲਈ ਸਿਰਫ਼ ਬਦਲੀ
ਹੋਈ ਲਾਈਨ ਵਾਲੀ ਫਾਇਲ ਕਾਫ਼ੀ ਨਹੀਂ ਹੈ।
[glibc ਸੰਰਚਨਾ ਹਵਾਲਾ](https://github.com/bminor/glibc/blob/master/posix/gai.conf)
ਇਨ੍ਹਾਂ ਅਰਥ-ਵਿਧੀਆਂ ਦਾ ਦਸਤਾਵੇਜ਼ੀਕਰਨ ਕਰਦਾ ਹੈ। ਸਮੀਖਿਆ ਕੀਤੀ ਫਾਇਲ ਨੂੰ `/etc/gai.conf`
ਉੱਤੇ ਸਿਰਫ਼-ਪੜ੍ਹਨਯੋਗ ਰੂਪ ਵਿੱਚ ਬਾਈਂਡ-ਮਾਊਂਟ ਕਰੋ ਅਤੇ ਇਸਨੂੰ ਲਾਗੂ ਕਰਨ ਲਈ ਸੇਵਾ ਮੁੜ ਬਣਾਓ।

ਇਹ ਉਸ ਕੰਟੇਨਰ ਦੇ **ਸਾਰੇ ਆਊਟਬਾਊਂਡ ਟ੍ਰੈਫਿਕ** ਲਈ OS ਐਡਰੈੱਸ ਚੋਣ ਬਦਲਦਾ ਹੈ।
ਇਹ ਹਰ ਐਪਲੀਕੇਸ਼ਨ ਨੂੰ IPv6 ਚੁਣਨ ਲਈ ਮਜਬੂਰ ਨਹੀਂ ਕਰਦਾ: Node ਦਾ DNS ਕ੍ਰਮ ਅਤੇ
ਕਨੈਕਸ਼ਨ ਚੋਣ ਵੀ ਮਹੱਤਵਪੂਰਨ ਹਨ। ਖ਼ਾਸ ਤੌਰ ਉੱਤੇ, `--dns-result-order=ipv4first`
IPv4 ਨੂੰ ਤਰਜੀਹ ਦਿੰਦਾ ਹੈ ਅਤੇ ਇਹ ਸਿਰਫ਼-IPv4 ਅਸਫਲਤਾ ਦਾ ਹੱਲ ਨਹੀਂ ਹੈ।
[Node DNS ਕ੍ਰਮਬੱਧਤਾ](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder) ਵੇਖੋ।

ਕਿਸੇ ਵੀ ਹੋਸਟ-ਪੱਧਰੀ ਤਬਦੀਲੀ ਤੋਂ ਬਾਅਦ Gemini ਅਤੇ ਆਪਣੇ ਹੋਰ ਪ੍ਰਦਾਤਾਵਾਂ ਦੀ ਦੁਬਾਰਾ
ਜਾਂਚ ਕਰੋ। ਤਬਦੀਲੀ ਵਾਪਸ ਲੈਣ ਲਈ, ਕਸਟਮ `gai.conf` ਮਾਊਂਟ ਹਟਾਓ, ਪਿਛਲੀ ਨੈੱਟਵਰਕ
ਸੰਰਚਨਾ ਮੁੜ ਬਹਾਲ ਕਰੋ ਅਤੇ ਰੱਖ-ਰਖਾਅ ਵਿੰਡੋ ਦੌਰਾਨ ਪ੍ਰਭਾਵਿਤ ਸੇਵਾ/ਨੈੱਟਵਰਕ ਨੂੰ ਮੁੜ
ਬਣਾਓ। ਨੈੱਟਵਰਕ ਨੂੰ ਮੁੜ ਬਣਾਉਣ ਨਾਲ ਇਸ ਨਾਲ ਜੁੜੇ ਹੋਰ ਕੰਟੇਨਰਾਂ ਵਿੱਚ ਵਿਘਨ ਪੈ ਸਕਦਾ ਹੈ;
ਸਥਾਈ ਡਾਟਾ ਵਾਲਿਊਮ ਨਾ ਮਿਟਾਓ।

## ਮਹੱਤਵਪੂਰਨ ਨੋਟਸ

- **SQLite WAL ਮੋਡ:** `docker stop` ਨੂੰ ਪੂਰਾ ਹੋਣ ਦੇਣਾ ਚਾਹੀਦਾ ਹੈ ਤਾਂ ਜੋ OmniRoute ਨਵੀਨਤਮ ਤਬਦੀਲੀਆਂ ਨੂੰ ਚੈਕਪੁਆਇੰਟ ਕਰਕੇ ਵਾਪਸ `storage.sqlite` ਵਿੱਚ ਲਿਖ ਸਕੇ। ਨਾਲ ਦਿੱਤੀਆਂ Compose ਫਾਈਲਾਂ ਵਿੱਚ ਪਹਿਲਾਂ ਹੀ 40s ਦੀ ਸਟਾਪ ਗ੍ਰੇਸ ਮਿਆਦ ਸੈੱਟ ਕੀਤੀ ਗਈ ਹੈ। ਜੇ ਤੁਸੀਂ ਇਮੇਜ ਨੂੰ ਸਿੱਧਾ ਚਲਾਉਂਦੇ ਹੋ, ਤਾਂ `--stop-timeout 40` ਨੂੰ ਬਰਕਰਾਰ ਰੱਖੋ।
- **`DISABLE_SQLITE_AUTO_BACKUP`:** ਜੇ ਨਿਯਮਤ/ਲਿਖਣ ਤੋਂ ਪਹਿਲਾਂ ਵਾਲੇ ਬੈਕਅੱਪ ਬਾਹਰੀ ਤੌਰ 'ਤੇ ਪ੍ਰਬੰਧਿਤ ਕੀਤੇ ਜਾਂਦੇ ਹਨ, ਤਾਂ ਇਸਨੂੰ `true` 'ਤੇ ਸੈੱਟ ਕਰੋ। ਮੌਜੂਦਾ ਡੇਟਾਬੇਸ ਮਾਈਗ੍ਰੇਸ਼ਨਾਂ ਲਈ ਫਿਰ ਵੀ ਉਹਨਾਂ ਦਾ ਆਪਣਾ ਟਿਕਾਊ ਸੁਰੱਖਿਆ ਸਨੈਪਸ਼ਾਟ ਅਤੇ ਵਿਆਪਕ ਮਾਈਗ੍ਰੇਸ਼ਨ ਸੁਰੱਖਿਆ-ਉਪਾਅ ਲੋੜੀਂਦਾ ਹੈ।
- **ਡੇਟਾ ਸਥਿਰਤਾ:** ਕੰਟੇਨਰ ਰੀਸਟਾਰਟਾਂ ਦੌਰਾਨ ਆਪਣੇ ਡੇਟਾਬੇਸ, ਕੁੰਜੀਆਂ ਅਤੇ ਕੌਂਫਿਗਰੇਸ਼ਨਾਂ ਨੂੰ ਕਾਇਮ ਰੱਖਣ ਲਈ ਹਮੇਸ਼ਾ `/app/data` 'ਤੇ ਇੱਕ ਵਾਲਿਊਮ ਮਾਊਂਟ ਕਰੋ।
- **ਪੋਰਟ ਕੌਂਫਿਗਰੇਸ਼ਨ:** ਡਿਫੌਲਟ `20128` ਪੋਰਟ ਨੂੰ ਬਦਲਣ ਲਈ `PORT` ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲ ਨੂੰ ਓਵਰਰਾਈਡ ਕਰੋ।
