## ਤੁਰੰਤ ਚਲਾਓ

> **ਇੱਕ ਕਮਾਂਡ ਨਾਲ ਸਵੈ-ਹੋਸਟ ਕਰਨਾ ਹੈ?**
> [ਸਵੈ-ਹੋਸਟ ਗਾਈਡ](../getting-started/SELF_HOST_GUIDE.md) ਵੇਖੋ —
> `docker compose -f docker-compose.selfhost.yml up -d` (ਪ੍ਰਕਾਸ਼ਿਤ ਇਮੇਜ +
> Redis, ਕੇਵਲ ਲੂਪਬੈਕ, ਪ੍ਰੋਫ਼ਾਈਲ ਦੀ ਕੋਈ ਚੋਣ ਨਹੀਂ)। ਹੇਠਾਂ ਦਿੱਤਾ ਤੁਰੰਤ ਚਲਾਉਣ ਦਾ ਤਰੀਕਾ
> ਉਨ੍ਹਾਂ ਵਰਤੋਂਕਾਰਾਂ ਲਈ ਸਿੰਗਲ-ਕੰਟੇਨਰ ਮਾਰਗ ਹੈ ਜੋ ਪਹਿਲਾਂ ਹੀ Redis ਨੂੰ ਕਿਤੇ ਹੋਰ ਚਲਾ ਰਹੇ ਹਨ।

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## ਵਾਤਾਵਰਣ ਫ਼ਾਈਲ ਨਾਲ

```bash
# ਪਹਿਲਾਂ .env ਨੂੰ ਕਾਪੀ ਅਤੇ ਸੰਪਾਦਿਤ ਕਰੋ
cp .env.example .env

docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  --env-file .env \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## Docker Compose

```bash
# ਬੇਸ ਪ੍ਰੋਫ਼ਾਈਲ (ਕੋਈ CLI ਟੂਲ ਨਹੀਂ)
docker compose --profile base up -d

# CLI ਪ੍ਰੋਫ਼ਾਈਲ (Claude Code, Codex, OpenClaw ਬਿਲਟ-ਇਨ)
docker compose --profile cli up -d

# ਹੋਸਟ ਪ੍ਰੋਫ਼ਾਈਲ (Linux-ਪਹਿਲਾਂ; ਹੋਸਟ CLI ਬਾਈਨਰੀਆਂ ਨੂੰ ਸਿਰਫ਼-ਪੜ੍ਹਨਯੋਗ ਢੰਗ ਨਾਲ ਮਾਊਂਟ ਕਰਦਾ ਹੈ)
docker compose --profile host up -d

# ਵੈੱਬ ਪ੍ਰੋਫ਼ਾਈਲ (ਵੈੱਬ-ਸੈਸ਼ਨ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ Chromium/Playwright)
docker compose --profile web up -d

# CLI + CLIProxyAPI ਸਾਈਡਕਾਰ ਨੂੰ ਜੋੜੋ
docker compose --profile cli --profile cliproxyapi up -d
```

## ਉਪਲਬਧ ਪ੍ਰੋਫ਼ਾਈਲ

OmniRoute ਮੁੱਖ ਡਿਪਲੌਇਮੈਂਟ ਰੂਪਾਂ ਲਈ Compose ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਦੇ ਨਾਲ ਆਉਂਦਾ ਹੈ। ਆਪਣੇ ਵਾਤਾਵਰਣ ਨਾਲ ਮੇਲ ਖਾਂਦਾ ਪ੍ਰੋਫ਼ਾਈਲ ਚੁਣੋ।

| ਪ੍ਰੋਫ਼ਾਈਲ       | ਸੇਵਾ             | ਕਦੋਂ ਵਰਤਣਾ ਹੈ                                                                                                                                        | ਕਮਾਂਡ                                        |
| --------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `base` (ਡਿਫੌਲਟ) | `omniroute-base` | ਹੈੱਡਲੈੱਸ ਸਰਵਰ / ਨਿਊਨਤਮ ਰਨਟਾਈਮ, ਕੋਈ ਪ੍ਰਦਾਤਾ CLI ਸ਼ਾਮਲ ਨਹੀਂ                                                                                            | `docker compose --profile base up -d`        |
| `cli`           | `omniroute-cli`  | ਏਜੰਟ-ਅਧਾਰਿਤ ਵਰਕਫ਼ਲੋ ਜੋ `omniroute providers/setup/doctor` ਅਤੇ ਸ਼ਾਮਲ CLI (Codex, Claude Code, Droid, OpenClaw) ਨੂੰ ਕਾਲ ਕਰਦੇ ਹਨ                        | `docker compose --profile cli up -d`         |
| `host`          | `omniroute-host` | ਉਹ Linux ਹੋਸਟ ਜੋ `~/.local/bin`, `~/.codex`, `~/.claude` ਆਦਿ ਨੂੰ ਸਿਰਫ਼-ਪੜ੍ਹਨਯੋਗ ਢੰਗ ਨਾਲ ਮਾਊਂਟ ਕਰਕੇ ਹੋਸਟ CLI ਤੱਕ `network_mode`-ਵਰਗੀ ਪਹੁੰਚ ਚਾਹੁੰਦੇ ਹਨ | `docker compose --profile host up -d`        |
| `cliproxyapi`   | `cliproxyapi`    | ਅੱਪਸਟ੍ਰੀਮ CLI ਪ੍ਰੌਕਸੀ ਲਈ ਪੋਰਟ `8317` ਉੱਤੇ [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) ਸਾਈਡਕਾਰ ਚਲਾਓ                                   | `docker compose --profile cliproxyapi up -d` |
| `web`           | `omniroute-web`  | ਉਹ ਵੈੱਬ-ਸੈਸ਼ਨ ਪ੍ਰਦਾਤਾ ਜਿਨ੍ਹਾਂ ਨੂੰ ਬ੍ਰਾਊਜ਼ਰ ਦੀ ਲੋੜ ਹੈ: `gemini-web`, `claude-web`, `claude-turnstile` (`runner-web` ਬਿਲਡ ਕਰਦਾ ਹੈ, Chromium ਸ਼ਾਮਲ ਹੈ)  | `docker compose --profile web up -d`         |

> ਕਈ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਨੂੰ ਇਕੱਠੇ ਵਰਤਿਆ ਜਾ ਸਕਦਾ ਹੈ: `docker compose --profile cli --profile cliproxyapi up -d`।

## ਜਦੋਂ OmniRoute Docker ਵਿੱਚ ਚੱਲਦਾ ਹੋਵੇ ਤਾਂ ਹੋਸਟ CLI ਟੂਲਾਂ ਨੂੰ ਕਨਫ਼ਿਗਰ ਕਰਨਾ

`omniroute setup-codex`, `setup-claude`, `config set <tool>` ਅਤੇ ਡੈਸ਼ਬੋਰਡ ਦਾ
**ਕਨਫ਼ਿਗ ਸੰਭਾਲੋ** ਬਟਨ ਸਾਰੇ `~/.codex/*.config.toml` ਵਰਗੀਆਂ ਫ਼ਾਈਲਾਂ ਲਿਖਦੇ ਹਨ। ਇਨ੍ਹਾਂ ਪਾਥਾਂ ਦਾ
ਅਰਥ ਸਿਰਫ਼ ਉਸ ਮਸ਼ੀਨ ਉੱਤੇ ਹੁੰਦਾ ਹੈ ਜਿੱਥੇ CLI ਅਸਲ ਵਿੱਚ ਚੱਲਦਾ ਹੈ। ਇਨ੍ਹਾਂ ਨੂੰ
ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ ਚਲਾਉਣ ਨਾਲ ਲਿਖਤ ਕੰਟੇਨਰ ਦੇ ਆਪਣੇ ਹੋਮ (`/home/node` —
ਇਮੇਜ `USER node` ਵਜੋਂ ਚੱਲਦੀ ਹੈ) ਵਿੱਚ ਜਾਂਦੀ ਹੈ, ਜਿੱਥੋਂ ਕੋਈ ਵੀ ਹੋਸਟ CLI ਇਸਨੂੰ ਕਦੇ ਨਹੀਂ ਪੜ੍ਹੇਗਾ ਅਤੇ
ਕੰਟੇਨਰ ਮੁੜ ਬਣਾਏ ਜਾਣ ਦੇ ਨਾਲ ਹੀ ਇਹ ਰੱਦ ਹੋ ਜਾਂਦੀ ਹੈ।

OmniRoute ਇਸਦਾ ਪਤਾ ਲਗਾ ਲੈਂਦਾ ਹੈ ਅਤੇ ਅਜਿਹੀ ਸਫਲਤਾ ਰਿਪੋਰਟ ਕਰਨ ਦੀ ਬਜਾਏ, ਜਿਸਨੂੰ ਤੁਸੀਂ ਵਰਤ ਨਹੀਂ ਸਕਦੇ,
ਹਦਾਇਤਾਂ ਸਮੇਤ ਲਿਖਤ ਤੋਂ ਇਨਕਾਰ ਕਰਦਾ ਹੈ: CLI `2` ਨਾਲ ਬੰਦ ਹੁੰਦਾ ਹੈ, ਅਤੇ API `422`
ਦੇ ਨਾਲ `containerEphemeralTarget: true` ਵਾਪਸ ਕਰਦਾ ਹੈ।

### ਸਿਫ਼ਾਰਸ਼ੀ: CLI ਨੂੰ ਹੋਸਟ ਉੱਤੇ ਅਤੇ OmniRoute ਨੂੰ Docker ਵਿੱਚ ਚਲਾਓ

ਕੰਟੇਨਰ API ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ; CLI ਤੁਹਾਡੇ ਹੋਸਟ ਟੂਲਾਂ ਨੂੰ ਕਨਫ਼ਿਗਰ ਕਰਦਾ ਹੈ।

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # CLI ਨੂੰ ਕੰਟੇਨਰ ਵੱਲ ਨਿਰਦੇਸ਼ਿਤ ਕਰੋ
omniroute setup-codex                      # ਤੁਹਾਡੇ ਹੋਸਟ ਉੱਤੇ ਅਸਲ ~/.codex ਲਿਖਦਾ ਹੈ
```

ਜਦੋਂ Codex, Claude Code, Cursor ਜਾਂ ਇਸੇ ਤਰ੍ਹਾਂ ਦੇ ਟੂਲ ਤੁਹਾਡੇ
ਲੈਪਟਾਪ ਉੱਤੇ ਚੱਲਦੇ ਹਨ—ਜੋ ਕਿ ਆਮ ਸੈੱਟਅੱਪ ਹੈ—ਤਾਂ ਇਹ ਸਹੀ ਚੋਣ ਹੈ।

### ਵਿਕਲਪ: ਹੋਸਟ ਕਨਫ਼ਿਗ ਡਾਇਰੈਕਟਰੀਆਂ ਨੂੰ bind-mount ਕਰੋ (`host` ਪ੍ਰੋਫ਼ਾਈਲ)

ਜੇ ਤੁਸੀਂ ਚਾਹੁੰਦੇ ਹੋ ਕਿ ਕੰਟੇਨਰ ਖੁਦ ਤੁਹਾਡੀ ਹੋਸਟ ਕਨਫ਼ਿਗ ਲਿਖੇ, ਤਾਂ
ਡਾਇਰੈਕਟਰੀਆਂ ਨੂੰ ਮਾਊਂਟ ਕਰੋ ਅਤੇ `CLI_CONFIG_HOME` ਨੂੰ ਮਾਊਂਟ ਰੂਟ ਵੱਲ ਨਿਰਦੇਸ਼ਿਤ ਕਰੋ। `host` ਪ੍ਰੋਫ਼ਾਈਲ
ਪਹਿਲਾਂ ਹੀ ਅਜਿਹਾ ਕਰਦਾ ਹੈ:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

bind mount ਹੀ ਪਾਥ ਨੂੰ ਭਰੋਸੇਯੋਗ ਬਣਾਉਂਦਾ ਹੈ: OmniRoute
`/proc/self/mountinfo` ਨੂੰ ਪੜ੍ਹਦਾ ਹੈ ਅਤੇ ਮਾਊਂਟ ਕੀਤੇ ਪਾਥਾਂ ਉੱਤੇ ਲਿਖਣ ਦੀ ਆਗਿਆ ਦਿੰਦਾ ਹੈ (ਅਤੇ ਉਹਨਾਂ ਡਾਇਰੈਕਟਰੀਆਂ ਉੱਤੇ ਵੀ
ਜਿਨ੍ਹਾਂ ਦੇ ਚਾਈਲਡ ਮਾਊਂਟ ਹਨ, ਜੋ ਉੱਪਰ ਦਿੱਤੇ `/host-home` ਦੇ ਢਾਂਚੇ ਵਰਗਾ ਹੀ ਹੈ), ਜਦਕਿ
ਅਣਮਾਊਂਟ ਕੀਤੇ ਪਾਥਾਂ ਲਈ ਅਜੇ ਵੀ ਇਨਕਾਰ ਕਰਦਾ ਹੈ।

### ਬਚਾਅ ਦਾ ਰਸਤਾ: ਕੰਟੇਨਰ ਦੇ ਆਪਣੇ CLIs ਨੂੰ ਕਨਫ਼ਿਗਰ ਕਰੋ (ਸੰਜਮ ਨਾਲ ਵਰਤੋ)

ਜਦੋਂ CLIs ਅਸਲ ਵਿੱਚ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ ਹੀ ਮੌਜੂਦ ਹੋਣ (`cli` ਪ੍ਰੋਫ਼ਾਈਲ), ਤਾਂ ਲਿਖਤ
ਜਾਣਬੁੱਝ ਕੇ ਕੀਤੀ ਜਾਂਦੀ ਹੈ। ਕਿਸੇ ਵੀ `setup-*` ਕਮਾਂਡ ਨੂੰ `--allow-container-write` ਦਿਓ, ਜਾਂ ਸਰਵਰ ਲਈ
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` ਸੈੱਟ ਕਰੋ। ਲਿਖਤ ਇਸ ਚੇਤਾਵਨੀ ਨਾਲ ਅੱਗੇ ਵਧਦੀ ਹੈ
ਕਿ ਇਹ ਕੰਟੇਨਰ ਦੇ ਬਾਅਦ ਕਾਇਮ ਨਹੀਂ ਰਹੇਗੀ।

> **ਸੁਰੱਖਿਆ ਚੇਤਾਵਨੀ — `cli` ਪ੍ਰੋਫ਼ਾਈਲ + `docker.sock` ਮਾਊਂਟ।**
> `cli` ਪ੍ਰੋਫ਼ਾਈਲ `/var/run/docker.sock` ਨੂੰ bind-mount ਕਰਦਾ ਹੈ ਤਾਂ ਜੋ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰਲਾ
> auto-updater ਹੋਸਟ daemon ਰਾਹੀਂ ਸਟੈਕ ਨੂੰ ਮੁੜ ਬਣਾ ਸਕੇ
> (`src/lib/system/autoUpdate.ts` ਉਸ socket ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ ਅਤੇ ਉਸਦੀ ਗੈਰਹਾਜ਼ਰੀ ਵਿੱਚ
> Docker ਪਾਥ ਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ)। ਉਹ socket **ਹੋਸਟ-root ਭਰੋਸੇ ਦੀ
> ਸੀਮਾ** ਹੈ: ਜੋ ਵੀ ਉਸ ਤੱਕ ਪਹੁੰਚ ਸਕਦਾ ਹੈ, ਉਹ ਹੋਸਟ Docker daemon ਨੂੰ
> root ਵਜੋਂ ਚਲਾਉਂਦਾ ਹੈ—ਉਹ ਹੋਸਟ ਉੱਤੇ ਕਿਸੇ ਵੀ ਕੰਟੇਨਰ ਨੂੰ ਬਣਾ, ਜਾਂਚ, ਰੋਕ ਅਤੇ ਹਟਾ ਸਕਦਾ ਹੈ।
> ਪ੍ਰਭਾਵ:
>
> 1. **`cli` ਪ੍ਰੋਫ਼ਾਈਲ ਦੇ ਪੋਰਟ ਨੂੰ ਕਦੇ ਵੀ ਨੈੱਟਵਰਕ ਉੱਤੇ ਉਪਲਬਧ ਨਾ ਕਰੋ।** ਇਸਨੂੰ
>    `127.0.0.1` ਉੱਤੇ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰੋ (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LAN ਤੋਂ ਪਹੁੰਚਯੋਗ `cli` ਪ੍ਰੋਫ਼ਾਈਲ ਡੈਸ਼ਬੋਰਡ-ਪੱਧਰੀ ਕਿਸੇ ਵੀ RCE ਨੂੰ
>    ਹੋਸਟ ਦੇ ਪੂਰੇ ਕਬਜ਼ੇ ਵਿੱਚ ਬਦਲ ਦਿੰਦਾ ਹੈ।
> 2. **`cli` ਪ੍ਰੋਫ਼ਾਈਲ ਵਿੱਚ ਕੋਈ ਵੀ ਵਾਧੂ ਹੋਸਟ ਡਾਇਰੈਕਟਰੀ bind ਨਾ ਕਰੋ।**
>    Docker socket ਦੇ ਨਾਲ ਕੋਈ ਵੀ ਹੋਰ ਮਾਊਂਟ ਕੰਟੇਨਰ ਨੂੰ ਤੁਹਾਡੇ ਫ਼ਾਈਲ-ਸਿਸਟਮ
>    ਅਤੇ ਹੋਸਟ ਕਨਫ਼ਿਗ ਉੱਤੇ ਪੂਰੀ ਪੜ੍ਹਨ/ਲਿਖਣ ਦੀ ਪਹੁੰਚ ਦਿੰਦਾ ਹੈ। ਜੇ ਕਿਸੇ ਟੂਲ ਨੂੰ
>    ਪ੍ਰੋਜੈਕਟ ਵੇਖਣ ਦੀ ਲੋੜ ਹੈ, ਤਾਂ ਉਸਨੂੰ CLI binary ਨਾਲ ਸਥਾਨਕ ਤੌਰ ਉੱਤੇ ਚਲਾਓ—ਉਸਨੂੰ
>    `cli` ਕੰਟੇਨਰ ਵਿੱਚ ਮਾਊਂਟ ਨਾ ਕਰੋ।
>
> ਜੇ ਤੁਹਾਨੂੰ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ auto-update ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ, ਤਾਂ `cli` ਪ੍ਰੋਫ਼ਾਈਲ ਨੂੰ ਬੰਦ ਰੱਖੋ
> (`COMPOSE_PROFILES=core,redis` ਜਾਂ ਇਸ ਤੋਂ ਛੋਟਾ)। ਹੋਰ ਪ੍ਰੋਫ਼ਾਈਲ
> Docker socket ਨੂੰ ਮਾਊਂਟ ਨਹੀਂ ਕਰਦੇ।
>
> MITM ਨਾਲ ਸੰਬੰਧਿਤ ਖ਼ਤਰੇ ਦੇ ਮਾਡਲ ਲਈ `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs` ਵਿੱਚ ਕੰਪਾਇਲ ਨਹੀਂ ਕੀਤਾ ਗਿਆ) ਵੇਖੋ,
> ਅਤੇ `codex`/`claude-code`/`droid`/`openclaw` binary ਦੇ ਮੂਲ-ਸਰੋਤ ਦੀ ਲੜੀ ਲਈ
> `docs/security/SUPPLY_CHAIN.md` ਵੇਖੋ।

## Redis Sidecar

OmniRoute ਵੰਡੇ ਹੋਏ ਰੇਟ ਲਿਮਿਟਰ ਅਤੇ ਸਾਂਝੇ ਕੈਸ਼ ਲਈ Redis 'ਤੇ ਨਿਰਭਰ ਕਰਦਾ ਹੈ। `redis` ਸੇਵਾ `docker-compose.yml` ਵਿੱਚ **ਹਮੇਸ਼ਾ ਪਰਿਭਾਸ਼ਿਤ ਹੁੰਦੀ ਹੈ** (ਇਸ 'ਤੇ ਕੋਈ ਪ੍ਰੋਫ਼ਾਈਲ ਪਾਬੰਦੀ ਨਹੀਂ ਹੈ) ਅਤੇ ਕਿਸੇ ਵੀ ਹੋਰ ਪ੍ਰੋਫ਼ਾਈਲ ਦੇ ਨਾਲ ਸ਼ੁਰੂ ਹੁੰਦੀ ਹੈ।

| ਵੇਰਵਾ                | ਮੁੱਲ                                         |
| -------------------- | -------------------------------------------- |
| ਇਮੇਜ                 | `redis:7-alpine`                             |
| ਕੰਟੇਨਰ ਦਾ ਨਾਮ        | `omniroute-redis`                            |
| ਅੰਦਰੂਨੀ ਪੋਰਟ         | `6379`                                       |
| ਹੋਸਟ ਪੋਰਟ (ਓਵਰਰਾਈਡ)  | `REDIS_PORT` (ਮੂਲ ਰੂਪ ਵਿੱਚ `6379`)           |
| ਹੋਸਟ ਬਾਈਂਡ (ਓਵਰਰਾਈਡ) | `REDIS_BIND_HOST` (ਮੂਲ ਰੂਪ ਵਿੱਚ `127.0.0.1`) |
| ਵਾਲਿਊਮ               | `omniroute-redis-data` → `/data`             |
| ਹੈਲਥਚੈੱਕ             | `redis-cli ping` (10s ਦਾ ਅੰਤਰਾਲ)             |

ਸੰਬੰਧਿਤ ਵਾਤਾਵਰਣ ਵੇਰੀਏਬਲ:

- `REDIS_URL` — ਐਪ ਵਿੱਚ ਇੰਜੈਕਟ ਕੀਤੀ ਜਾਣ ਵਾਲੀ ਕਨੈਕਸ਼ਨ ਸਟ੍ਰਿੰਗ (ਮੂਲ ਰੂਪ ਵਿੱਚ `redis://redis:6379`)।
- `REDIS_PORT` — Redis ਕੰਟੇਨਰ ਲਈ ਹੋਸਟ-ਸਾਈਡ ਪੋਰਟ ਮੈਪਿੰਗ।
- `REDIS_BIND_HOST` — ਉਹ ਹੋਸਟ ਇੰਟਰਫੇਸ ਜਿਸ 'ਤੇ ਪੋਰਟ ਪ੍ਰਕਾਸ਼ਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਮੂਲ ਰੂਪ ਵਿੱਚ `127.0.0.1`।

> **ਮੂਲ ਰੂਪ ਵਿੱਚ ਲੂਪਬੈਕ ਕਿਉਂ:** ਸਾਈਡਕਾਰ `requirepass` ਤੋਂ ਬਿਨਾਂ ਚੱਲਦਾ ਹੈ, ਅਤੇ ਐਪ
> ਕੰਟੇਨਰ ਕੰਪੋਜ਼ ਨੈੱਟਵਰਕ (`redis:6379`) ਰਾਹੀਂ ਇਸ ਤੱਕ ਪਹੁੰਚਦੇ ਹਨ — ਪ੍ਰਕਾਸ਼ਿਤ ਪੋਰਟ
> ਸਿਰਫ਼ ਹੋਸਟ-ਸਾਈਡ ਟੂਲਿੰਗ (`redis-cli`, ਇੱਕ ਲੋਕਲ `npm run dev`) ਲਈ ਹੈ। ਇਸਨੂੰ
> `0.0.0.0` 'ਤੇ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਨ ਨਾਲ ਬਿਨਾਂ ਪ੍ਰਮਾਣੀਕਰਨ ਵਾਲਾ Redis ਤੁਹਾਡੇ LAN ਦੇ ਹਰੇਕ ਹੋਸਟ ਲਈ ਉਪਲਬਧ ਹੋ ਜਾਵੇਗਾ। ਜੇ ਤੁਸੀਂ
> `REDIS_BIND_HOST=0.0.0.0` ਸੈੱਟ ਕਰਦੇ ਹੋ, ਤਾਂ ਸੇਵਾ ਦੇ `command:` ਵਿੱਚ `--requirepass` ਵੀ ਸ਼ਾਮਲ ਕਰੋ।

**Redis ਨੂੰ ਅਯੋਗ ਕਰਨ** ਦੀ ਸਿਫ਼ਾਰਸ਼ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ (ਰੇਟ ਲਿਮਿਟਰ ਇਨ-ਮੈਮੋਰੀ ਫਾਲਬੈਕ ਤੱਕ ਘਟ ਜਾਵੇਗਾ)। ਜੇ ਇਹ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ, ਤਾਂ ਜਾਂ ਤਾਂ `docker-compose.yml` ਵਿੱਚੋਂ `redis:` ਸੇਵਾ ਬਲਾਕ ਹਟਾਓ/ਟਿੱਪਣੀ ਬਣਾਓ ਜਾਂ ਇਸਨੂੰ ਸਿਫ਼ਰ ਤੱਕ ਸਕੇਲ ਕਰੋ:

```bash
docker compose up -d --scale redis=0
```

## ਪ੍ਰੋਡਕਸ਼ਨ ਕੰਪੋਜ਼

ਡਿਵੈਲਪਮੈਂਟ ਦੇ ਨਾਲ-ਨਾਲ ਚੱਲਣ ਵਾਲੇ ਇੱਕ ਅਲੱਗ ਪ੍ਰੋਡਕਸ਼ਨ ਸਨੈਪਸ਼ਾਟ ਲਈ, `docker-compose.prod.yml` ਵਰਤੋ।

| ਵੇਰਵਾ             | ਮੁੱਲ                                                                                                       |
| ----------------- | ---------------------------------------------------------------------------------------------------------- |
| ਫ਼ਾਈਲ             | `docker-compose.prod.yml`                                                                                  |
| ਮੂਲ ਡੈਸ਼ਬੋਰਡ ਪੋਰਟ | `PROD_DASHBOARD_PORT=20130` (ਅੰਦਰੂਨੀ `${DASHBOARD_PORT:-20128}` ਨਾਲ ਮੈਪ ਕੀਤਾ ਗਿਆ)                          |
| ਮੂਲ API ਪੋਰਟ      | `PROD_API_PORT=20131`                                                                                      |
| ਇਮੇਜ              | `omniroute:prod` (`runner-cli` ਟਾਰਗੇਟ ਤੋਂ ਬਿਲਡ ਕੀਤੀ)                                                       |
| Redis ਕੰਟੇਨਰ      | `omniroute-redis-prod` (`redis:8.6.2`, ਸਮਰਪਿਤ `redis-prod-data` ਵਾਲਿਊਮ)                                    |
| ਡਾਟਾ ਵਾਲਿਊਮ       | `omniroute-prod-data` (ਨਾਮਿਤ, ਮੁੜ-ਬਿਲਡਾਂ ਦੌਰਾਨ ਕਾਇਮ ਰਹਿੰਦਾ ਹੈ)                                             |
| ਹੈਲਥਚੈੱਕ          | `node healthcheck.mjs` + `redis-cli ping`, ਜਿਸ ਵਿੱਚ `depends_on` Redis ਦੀ ਸਿਹਤ ਦੇ ਆਧਾਰ 'ਤੇ ਗੇਟ ਕੀਤਾ ਗਿਆ ਹੈ |

ਵਰਤਣ ਦਾ ਤਰੀਕਾ:

```bash
# ਪ੍ਰੋਡਕਸ਼ਨ ਸਟੈਕ ਨੂੰ ਬਿਲਡ ਅਤੇ ਸ਼ੁਰੂ ਕਰੋ
docker compose -f docker-compose.prod.yml up -d --build

# ਲੌਗਾਂ ਨੂੰ ਸਟ੍ਰੀਮ ਕਰੋ
docker compose -f docker-compose.prod.yml logs -f

# ਬੰਦ ਕਰੋ (ਵਾਲਿਊਮ ਬਣੇ ਰਹਿਣ ਦਿਓ)
docker compose -f docker-compose.prod.yml down
```

ਪ੍ਰੋਡਕਸ਼ਨ ਸਟੈਕ ਡਿਵੈਲਪਮੈਂਟ ਕੰਪੋਜ਼ ਦੇ ਸਮਾਂਤਰ ਚੱਲਦਾ ਹੈ (ਵੱਖਰੇ ਕੰਟੇਨਰ ਨਾਮ, ਪੋਰਟ ਅਤੇ ਵਾਲਿਊਮ), ਇਸ ਲਈ ਪ੍ਰੋਡਕਸ਼ਨ ਨੂੰ ਚਾਲੂ ਰੱਖਦੇ ਹੋਏ ਤੁਸੀਂ ਲੋਕਲ ਤੌਰ 'ਤੇ ਕੰਮ ਜਾਰੀ ਰੱਖ ਸਕਦੇ ਹੋ।

## Dockerfile ਪੜਾਅ

ਰਿਪੋਜ਼ਟਰੀ ਇੱਕ ਬਹੁ-ਪੜਾਵੀ Dockerfile (`Dockerfile`) ਨਾਲ ਆਉਂਦੀ ਹੈ। ਚਾਰ ਪੜਾਅ ਉਪਲਬਧ ਹਨ; ਆਪਣੀ ਵਰਤੋਂ ਦੇ ਮਾਮਲੇ ਲਈ ਸਹੀ `target` ਚੁਣੋ।

| ਪੜਾਅ          | ਬੇਸ ਇਮੇਜ              | ਉਦੇਸ਼                                                                                                                                                                                                                                                                                            |
| ------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `builder`     | `node:26-trixie-slim` | ਡਿਪੈਂਡੈਂਸੀਆਂ ਇੰਸਟਾਲ ਕਰਦਾ ਹੈ (`npm ci --legacy-peer-deps`) ਅਤੇ `npm run build` ਚਲਾਉਂਦਾ ਹੈ (ਮੂਲ ਰੂਪ ਵਿੱਚ Turbopack — ਹੇਠਾਂ ਬਿਲਡ-ਸਮੇਂ ਦੇ ਸਰੋਤ ਵੇਖੋ)                                                                                                                                                 |
| `runner-base` | `node:26-trixie-slim` | Next.js ਦੇ ਸਟੈਂਡਅਲੋਨ ਆਉਟਪੁੱਟ ਵਾਲਾ ਪ੍ਰੋਡਕਸ਼ਨ ਰਨਟਾਈਮ। **ਕੋਈ ਪ੍ਰੋਵਾਈਡਰ CLI ਸ਼ਾਮਲ ਨਹੀਂ ਹੈ।**                                                                                                                                                                                                         |
| `runner-cli`  | `runner-base`         | `git`, `docker.io`, `docker-compose` ਅਤੇ ਗਲੋਬਲ CLI ਜੋੜਦਾ ਹੈ: `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw`। **ਏਜੰਟ-ਅਧਾਰਿਤ ਵਰਕਫ਼ਲੋਜ਼ ਲਈ ਇਹ ਚੁਣੋ।**                                                                                                                            |
| `runner-web`  | `runner-base`         | ਵੈੱਬ-ਸੈਸ਼ਨ ਪ੍ਰੋਵਾਈਡਰਾਂ ਲਈ Playwright + ਇੱਕ Chromium ਬ੍ਰਾਊਜ਼ਰ (`--with-deps`) ਜੋੜਦਾ ਹੈ: `gemini-web`, `claude-web`, `claude-turnstile`। **ਜਦੋਂ ਤੁਸੀਂ ਇਹ ਪ੍ਰੋਵਾਈਡਰ ਵਰਤਦੇ ਹੋ ਤਾਂ ਇਹ ਚੁਣੋ** — ਇਸ ਤੋਂ ਬਿਨਾਂ ਸਧਾਰਨ ਇਮੇਜ ਬੇਨਤੀ ਦੇ ਸਮੇਂ ਅਸਫਲ ਹੋ ਜਾਂਦੀ ਹੈ (Release Channels ਹੇਠਾਂ ਦਿੱਤਾ `-web` ਨੋਟ ਵੇਖੋ)। |

ਕਿਸੇ ਖ਼ਾਸ ਟਾਰਗੇਟ ਨੂੰ ਹੱਥੀਂ ਬਿਲਡ ਕਰੋ:

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### ਬਿਲਡ-ਸਮੇਂ ਦੇ ਸਰੋਤ

ਤਿੰਨ ਬਿਲਡ ਆਰਗੂਮੈਂਟ ਨਿਯੰਤਰਿਤ ਕਰਦੇ ਹਨ ਕਿ `builder` ਪੜਾਅ ਕਿੰਨੇ ਸਰੋਤ ਵਰਤਦਾ ਹੈ। ਇਹ ਸਿਰਫ਼ ਬਿਲਡ ਸਮੇਂ ਲਈ ਹਨ —
`OMNIROUTE_MEMORY_MB` (ਹੇਠਾਂ) ਇੱਕ ਵੱਖਰਾ ਰਨਟਾਈਮ ਨਿਯੰਤਰਣ ਹੈ।

| ਬਿਲਡ ਆਰਗੂਮੈਂਟ               | ਮੂਲ ਮੁੱਲ | ਪ੍ਰਭਾਵ                                                                                               |
| --------------------------- | -------- | ---------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `1`      | `0` ਇਸ ਦੀ ਬਜਾਏ webpack ਨਾਲ ਬਿਲਡ ਕਰਦਾ ਹੈ। ਅਧਿਕਤਮ ਮੈਮੋਰੀ ਘੱਟ, ਪਰ ਹੌਲੀ।                                 |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144`   | ਸ਼ੁਰੂ ਕੀਤੇ ਗਏ `next build` ਲਈ V8 ਹੀਪ ਸੀਮਾ (`--max-old-space-size`)।                                  |
| `OMNIROUTE_BUILD_WORKERS`   | `2`      | `CIRCLE_NODE_TOTAL` ਨੂੰ ਮੁੱਲ ਦਿੰਦਾ ਹੈ; Next ਪੇਜ-ਡਾਟਾ ਇਕੱਤਰ ਕਰਨ ਲਈ `workers = N - 1` ਨਿਰਧਾਰਤ ਕਰਦਾ ਹੈ। |

ਵੱਡੇ ਬਿਲਡਰ ਉੱਤੇ `OMNIROUTE_BUILD_WORKERS` ਨੂੰ ਵਧਾਉਣਾ ਚਾਹੀਦਾ ਹੈ ਅਤੇ ਸੀਮਤ ਸਰੋਤਾਂ ਵਾਲਾ ਬਿਲਡ `✓ Compiled successfully` **ਤੋਂ ਬਾਅਦ** ਬੰਦ ਹੋ ਜਾਵੇ ਤਾਂ ਸਭ ਤੋਂ ਪਹਿਲਾਂ ਇਸੇ ਉੱਤੇ ਸ਼ੱਕ ਕਰਨਾ ਚਾਹੀਦਾ ਹੈ। ਹਰ ਪੇਜ-ਡਾਟਾ ਵਰਕਰ ਆਪਣੀ ਵੱਖਰੀ ਪ੍ਰਕਿਰਿਆ ਹੈ, ਅਤੇ ਪੇਰੈਂਟ `next build` ਵੀ ਵੱਖਰੀ ਪ੍ਰਕਿਰਿਆ ਹੈ; ਇੱਕ ਲਾਈਵ VPS ਪੁਨਰੁਤਪਾਦਨ (issue #7518) ਵਿੱਚ ਹਰ ਪ੍ਰਕਿਰਿਆ ਦਾ ਅਧਿਕਤਮ RSS `NODE_OPTIONS` ਹੀਪ ਫਲੈਗ ਤੋਂ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ~4.5 GB ਮਾਪਿਆ ਗਿਆ ਸੀ (Turbopack, V8 ਹੀਪ ਤੋਂ ਬਾਹਰ ਨੇਟਿਵ/Rust ਮੈਮੋਰੀ ਵਿੱਚ ਕੰਪਾਇਲ ਕਰਦਾ ਹੈ)। `2` ਦਾ ਮੂਲ ਮੁੱਲ (→ 1 ਵਰਕਰ, ਕੁੱਲ 2 ਪ੍ਰਕਿਰਿਆਵਾਂ) ਉਹਨਾਂ 16 GB / 4 vCPU GitHub-ਹੋਸਟ ਕੀਤੇ ਰਨਰਾਂ ਲਈ ਨਿਰਧਾਰਤ ਹੈ ਜੋ ਪਬਲਿਸ਼ ਪਾਈਪਲਾਈਨ ਵਰਤਦੀ ਹੈ। `8` ਉੱਤੇ (→ 7 ਵਰਕਰ) ਉਸ ਰਨਰ ਦੀ ਮੈਮੋਰੀ ਖ਼ਤਮ ਹੋ ਗਈ ਅਤੇ buildkit ਨੇ `ResourceExhausted: ... cannot allocate memory` ਨਾਲ ਪੜਾਅ ਅਸਫਲ ਕਰ ਦਿੱਤਾ; ਪ੍ਰਤੀ-ਪ੍ਰਕਿਰਿਆ RSS ਦਾ ਅਨੁਮਾਨ ਲਗਾਉਣ ਦੀ ਬਜਾਏ ਸਿੱਧਾ ਮਾਪਣ ਤੋਂ ਬਾਅਦ `3` (→ 2 ਵਰਕਰ) ਵੀ ਫਿੱਟ ਨਹੀਂ ਹੋਇਆ। `tests/unit/docker-build-memory-budget.test.ts` ਮਾਪੇ ਗਏ ਅੰਕੜੇ ਦੇ ਆਧਾਰ 'ਤੇ ਗਣਨਾ ਕਰਦਾ ਹੈ ਅਤੇ ਜੇ ਕੋਈ ਵੀ ਨਿਯੰਤਰਣ ਰਨਰ ਦੀ ਸਮਰੱਥਾ ਤੋਂ ਵੱਧ ਜਾਂਦਾ ਹੈ ਤਾਂ ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ।

Turbopack, V8 ਹੀਪ ਤੋਂ **ਬਾਹਰ** ਸਥਿਤ ਨੇਟਿਵ Rust ਮੈਮੋਰੀ ਵਿੱਚ ਕੰਪਾਇਲ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ `OMNIROUTE_BUILD_MEMORY_MB` ਇਸ ਨੂੰ ਸੀਮਿਤ ਨਹੀਂ ਕਰਦਾ। ਮੈਮੋਰੀ ਸੀਮਾ ਵਾਲੇ ਹੋਸਟ ਉੱਤੇ OOM ਕਿਲਰ ਬਿਨਾਂ ਕਿਸੇ ਗਲਤੀ ਸੁਨੇਹੇ ਦੇ ਬਿਲਡ ਨੂੰ SIGKILL ਕਰ ਦਿੰਦਾ ਹੈ — ਇਹ `Creating an optimized production build` ਦੇ ਵਿਚਕਾਰ ਹੀ ਰੁਕ ਜਾਂਦਾ ਹੈ, ਜੋ ਮੈਮੋਰੀ ਖ਼ਤਮ ਹੋਣ ਦੀ ਬਜਾਏ ਅਟਕਣ ਵਰਗਾ ਲੱਗਦਾ ਹੈ। ਜੇ ਬਿਲਡ ਹੋਸਟ ਦੇ ਸਰੋਤ ਸੀਮਤ ਹਨ, ਤਾਂ ਬੰਡਲਰ ਬਦਲੋ:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=0 \
  -t omniroute:base .
```

`webpackBuildWorker` ਸਮਰੱਥ ਹੈ, ਇਸ ਲਈ `next build` ਇੱਕ ਪੇਰੈਂਟ **ਅਤੇ** ਇੱਕ ਵਰਕਰ ਪ੍ਰਕਿਰਿਆ ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਹਰ ਇੱਕ ਵੱਖਰੇ ਤੌਰ 'ਤੇ `OMNIROUTE_BUILD_MEMORY_MB` ਦੀ ਪਾਲਣਾ ਕਰਦੀ ਹੈ। ਕੰਟੇਨਰ ਦੀ ਸੀਮਾ ਇਸ ਮੁੱਲ ਦੇ ਲਗਭਗ ਦੁੱਗਣੇ ਤੋਂ ਉੱਪਰ ਰੱਖੋ, ਸਿਰਫ਼ ਇੱਕ ਗੁਣਾ ਨਹੀਂ।

ਇਸ ਟ੍ਰੀ ਉੱਤੇ ਮਾਪਿਆ ਗਿਆ (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| ਬੰਡਲਰ     | ਕੰਟੇਨਰ ਸੀਮਾ    | ਨਤੀਜਾ                         |
| --------- | -------------- | ----------------------------- |
| Turbopack | 8 GiB / 16 GiB | ਦੋਵਾਂ ਉੱਤੇ ਚੁੱਪਚਾਪ OOM-killed |
| webpack   | 8 GiB          | ਬਿਲਡ ਵਰਕਰ SIGKILLed           |
| webpack   | 12 GiB         | ਸਫਲ, ਅਧਿਕਤਮ ਵਰਤੋਂ 11.1 GiB ਸੀ |

### ਰਨਟਾਈਮ ਦੇ ਮੂਲ ਮੁੱਲ

`runner-base` ਵੱਲੋਂ ਐਕਸਪੋਰਟ ਕੀਤੇ ਮੂਲ ਮੁੱਲ: `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`।

Docker ਵਿੱਚ ਮੈਮੋਰੀ ਦਾ ਵਿਹਾਰ:

- ਇਮੇਜ `OMNIROUTE_MEMORY_MB=1024` ਸੈੱਟ ਕਰਦੀ ਹੈ ਅਤੇ ਇਸ ਤੋਂ `NODE_OPTIONS=--max-old-space-size=1024` ਪ੍ਰਾਪਤ ਕਰਦੀ ਹੈ।
- ਅਸਲ ਸਰਵਰ ਪ੍ਰਕਿਰਿਆ standalone launcher ਦੁਆਰਾ ਸ਼ੁਰੂ ਕੀਤੀ ਜਾਂਦੀ ਹੈ, ਜੋ `OMNIROUTE_MEMORY_MB` ਨੂੰ ਪੜ੍ਹਦਾ ਹੈ ਅਤੇ `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` ਜੋੜਦਾ ਹੈ।
- Node ਆਖਰੀ ਦੁਹਰਾਏ ਗਏ `--max-old-space-size` ਮੁੱਲ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ `OMNIROUTE_MEMORY_MB` ਸੈੱਟ ਕਰਨ ਨਾਲ ਪ੍ਰਭਾਵੀ Docker heap ਸੀਮਾ ਨਿਯੰਤਰਿਤ ਹੁੰਦੀ ਹੈ।
- ਕਿਉਂਕਿ ਇਮੇਜ ਇਸਨੂੰ ਹਮੇਸ਼ਾ ਸੈੱਟ ਕਰਦੀ ਹੈ, launcher ਦਾ ਆਪਣਾ RAM-ਅਨੁਸਾਰ ਕੈਲੀਬਰੇਟ ਕੀਤਾ fallback Docker ਅਧੀਨ ਕਦੇ ਲਾਗੂ ਨਹੀਂ ਹੁੰਦਾ। workload ਲਈ ਇਸਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਵਧਾਓ (ਹੇਠਾਂ ਦਿੱਤੀ ਸਾਰਣੀ)। coding-agent `/v1/responses` ਲਈ `2048` ਫਿਰ ਵੀ ਬਹੁਤ ਘੱਟ ਹੈ।

### coding agents ਲਈ runtime RAM

1 GiB Docker default ਇੱਕ dashboard/light-chat ਲਈ ਘੱਟੋ-ਘੱਟ ਸੀਮਾ ਹੈ, production ਆਕਾਰ ਨਹੀਂ। ਲੰਬੀਆਂ `POST /v1/responses` bodies (ਸੈਂਕੜੇ messages, ਦਰਜਨਾਂ tools) compression ਦੌਰਾਨ ਕਈ in-memory graphs ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦੀਆਂ ਹਨ। ਇੱਕੋ ਸਮੇਂ ਚੱਲ ਰਹੀਆਂ ਦੋ ~3 MiB / ~750k-token requests ਨੇ **12 GiB** old-space 'ਤੇ V8 ਨੂੰ abort ਕੀਤਾ ਹੈ (`FATAL ERROR: Reached heap limit`) ਅਤੇ 16 GiB cgroup OOM ਵੀ ਵਾਪਰਿਆ ਹੈ। [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ਵੇਖੋ।

cgroup `--memory` ਦਾ ਆਕਾਰ **heap ਤੋਂ ਵੱਧ ਰੱਖੋ** — native buffers, SQLite, ਅਤੇ compression intermediates V8 ਤੋਂ ਬਾਹਰ ਰਹਿੰਦੇ ਹਨ।

| workload                             | `OMNIROUTE_MEMORY_MB`  | Container / cgroup     | ਟਿੱਪਣੀਆਂ                                                                                                |
| ------------------------------------ | ---------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------- |
| Dashboard, ਇੱਕ ਹਲਕੀ chat             | `1024` (ਇਮੇਜ default)  | ≥2 GiB                 |                                                                                                         |
| ਇੱਕ coding agent (Claude/Codex/Grok) | `8192`                 | ≥10 GiB                | ਆਮ single-session `/v1/responses`                                                                       |
| ਇੱਕੋ ਸਮੇਂ ਦੋ ਲੰਬੀਆਂ `/v1/responses`  | `10240`–`12288`        | ≥12–16 GiB             | ~12 GiB heap 'ਤੇ ਮਾਪਿਆ ਗਿਆ V8 abort                                                                     |
| ਇੱਕੋ ਸਮੇਂ ਤਿੰਨ+ ਲੰਬੇ contexts        | ਇੱਕ process 'ਤੇ ਨਾ ਕਰੋ | ਕ੍ਰਮਵਾਰ ਚਲਾਓ / ਹੋਰ RAM | default heavyweight admission ਵਿੱਚ 1 in-flight ਹੈ; RAM ਤੋਂ ਬਿਨਾਂ ਇਸਨੂੰ ਵਧਾਉਣ ਨਾਲ abort ਦੁਬਾਰਾ ਵਾਪਰਦਾ ਹੈ |

bare metal ਉੱਤੇ `omniroute serve`, ਜਦੋਂ `OMNIROUTE_MEMORY_MB` **unset** ਹੁੰਦਾ ਹੈ, RAM ਦੇ ~35% ਨੂੰ ਕੈਲੀਬਰੇਟ ਕਰਦਾ ਹੈ (`[512, 4096]` ਤੱਕ ਸੀਮਿਤ)। Docker ਹਮੇਸ਼ਾ `1024` ਸੈੱਟ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ official image ਵਿੱਚ ਉਹ calibration ਕਦੇ ਨਹੀਂ ਚੱਲਦੀ।

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

## ਸਬਪਾਥ ਉੱਤੇ ਰਿਵਰਸ ਪ੍ਰਾਕਸੀ (Traefik / nginx)

Next.js `basePath` ਨੂੰ standalone bundle ਵਿੱਚ ਕੰਪਾਇਲ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। OmniRoute ਐਪ ਰੂਟ ਉੱਤੇ ਇੱਕ sentinel ਫ਼ਾਈਲ ਵਿੱਚ ਬੇਕ ਕੀਤੀ ਵੈਲਯੂ ਦਰਜ ਕਰਦਾ ਹੈ (`npm run build` ਦੌਰਾਨ ਲਿਖੀ ਜਾਂਦੀ ਹੈ; `scripts/docker/ensure-docker-base-path.mjs` ਵੱਲੋਂ ਪੜ੍ਹੀ ਜਾਂਦੀ ਹੈ) ਅਤੇ ਕੰਟੇਨਰ ਸ਼ੁਰੂ ਹੋਣ ਵੇਲੇ ਇਸਦੀ ਤੁਲਨਾ `OMNIROUTE_BASE_PATH` ਨਾਲ ਕਰਦਾ ਹੈ। ਜਦੋਂ ਇਹ ਵੱਖਰੇ ਹੁੰਦੇ ਹਨ ਅਤੇ ਇਮੇਜ ਨੂੰ ਡੋਮੇਨ ਰੂਟ ਲਈ ਬਿਲਡ ਕੀਤਾ ਗਿਆ ਸੀ, ਤਾਂ `node dev/run-standalone.mjs` ਚੱਲਣ ਤੋਂ ਪਹਿਲਾਂ entrypoint standalone manifests, ਏਮਬੈਡ ਕੀਤੇ `basePath`/`assetPrefix` literals (Next 16 SSR ਐਸੈੱਟ URLs ਨੂੰ ਸਿਰਫ਼ `assetPrefix` ਤੋਂ ਰੈਂਡਰ ਕਰਦਾ ਹੈ — patcher ਸਬਪਾਥ ਨੂੰ ਇਸ ਵਿੱਚ ਵੀ ਮਿਰਰ ਕਰਦਾ ਹੈ), ਬੇਕ ਕੀਤੇ `/_next/static` ਐਸੈੱਟ URLs (client-reference manifests, ਮੀਡੀਆ imports, ਪਹਿਲਾਂ ਤੋਂ ਰੈਂਡਰ ਕੀਤੇ error pages) ਅਤੇ ਕਲਾਇੰਟ `process.env` shim ਨੂੰ ਮੁੜ ਲਿਖਦਾ ਹੈ।

### Compose ਬਿਲਡ (ਸਿਫ਼ਾਰਸ਼ੀ)

ਦੋਵੇਂ variables ਨੂੰ `.env` ਵਿੱਚ ਸੈੱਟ ਕਰੋ, ਫਿਰ ਮੁੜ ਬਿਲਡ ਕਰੋ ਤਾਂ ਜੋ ਇਮੇਜ ਅਤੇ runtime ਆਪਸ ਵਿੱਚ ਮੇਲ ਖਾਣ:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml`, `OMNIROUTE_BASE_PATH` ਨੂੰ Docker build-arg ਅਤੇ runtime environment variable ਦੋਵਾਂ ਵਜੋਂ ਅੱਗੇ ਭੇਜਦਾ ਹੈ।

### ਪਹਿਲਾਂ ਤੋਂ ਬਿਲਡ ਕੀਤੀ ਰੂਟ ਇਮੇਜ + runtime ਸਬਪਾਥ

ਪ੍ਰਕਾਸ਼ਿਤ `diegosouzapw/omniroute:*` ਇਮੇਜਾਂ ਡੋਮੇਨ ਰੂਟ ਲਈ ਬਿਲਡ ਕੀਤੀਆਂ ਗਈਆਂ ਹਨ। ਤੁਸੀਂ ਫਿਰ ਵੀ runtime ਉੱਤੇ `OMNIROUTE_BASE_PATH` ਸੈੱਟ ਕਰ ਸਕਦੇ ਹੋ; ਕੰਟੇਨਰ startup ਦੌਰਾਨ bundle ਨੂੰ ਇੱਕ ਵਾਰ patch ਕਰਦਾ ਹੈ। ਇਸਨੂੰ ਮੇਲ ਖਾਂਦੇ public origin ਨਾਲ ਜੋੜੋ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

ਰਿਵਰਸ ਪ੍ਰਾਕਸੀ ਨੂੰ **ਪੂਰਾ** external path ਅੱਗੇ ਭੇਜਣ ਲਈ ਕੌਂਫਿਗਰ ਕਰੋ (prefix ਨੂੰ ਨਾ ਹਟਾਓ)। Traefik ਨੂੰ `StripPrefix` ਤੋਂ ਬਿਨਾਂ `PathPrefix(`/omniroute`)` ਨੂੰ ਕੰਟੇਨਰ ਵੱਲ ਰੂਟ ਕਰਨਾ ਚਾਹੀਦਾ ਹੈ, ਤਾਂ ਜੋ Next.js ਨੂੰ `/omniroute/...` ਪ੍ਰਾਪਤ ਹੋਵੇ ਅਤੇ ਉਹ `/omniroute/_next/...` ਤੋਂ ਐਸੈੱਟ ਸਰਵ ਕਰੇ।

Docker healthcheck, ਸਰਗਰਮ `OMNIROUTE_BASE_PATH` ਨਾਲ prefix ਕੀਤੇ ਹਲਕੇ `/healthz` lifecycle endpoint ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ। ਮਨੁੱਖੀ/dashboard diagnostics ਲਈ `/api/monitoring/health` ਉਪਲਬਧ ਰਹਿੰਦਾ ਹੈ; ਕੰਟੇਨਰ HEALTHCHECK ਨੂੰ ਮੁੜ ਇਸ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਨ ਲਈ (ਉਦਾਹਰਨ ਵਜੋਂ ਡੂੰਘੀ health enforcement ਲਈ), `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health` ਸੈੱਟ ਕਰੋ। ਇਹ ਪਾਥ ਇੱਕ **ਡੂੰਘੀ** ਜਾਂਚ ਹੈ (DB + monitoring summary) — ਜੇ ਤੁਸੀਂ ਇਸਨੂੰ ਮੁੜ ਚੁਣਦੇ ਹੋ ਤਾਂ ਇਹ Docker ਦੇ ਘੱਟ-ਵਾਰ ਚੱਲਣ ਵਾਲੇ `HEALTHCHECK` ਲਈ ਢੁਕਵਾਂ ਹੈ, ਪਰ Kubernetes ਦੇ `livenessProbe` ਅੰਤਰਾਲਾਂ ਲਈ **ਨਹੀਂ**।

orchestrators (Kubernetes, Nomad, ਆਦਿ) ਲਈ:

| ਜਾਂਚ            | ਤਰਜੀਹ ਦਿਓ                                                          | ਇਸ ਤੋਂ ਬਚੋ                                             |
| --------------- | ------------------------------------------------------------------ | ------------------------------------------------------ |
| Liveness        | HTTP `GET /livez`, ਜਾਂ ਮੁੱਖ ਪੋਰਟ ਉੱਤੇ TCP (`PORT`, ਡਿਫੌਲਟ `20128`) | liveness ਵਜੋਂ `/api/monitoring/health`                 |
| Readiness       | HTTP `GET /healthz`                                                | ਛੋਟੇ timeouts ਜੋ event-loop ਦੇ ਰੁੱਝੇ ਹੋਣ ਨੂੰ dead ਮੰਨਣ |
| Deep / blackbox | `/api/monitoring/health`                                           | —                                                      |

`/healthz` process lifecycle (`ok` / `starting` / `stopping`) ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ। `/livez` ਸਿਰਫ਼ process-alive ਜਾਂਚ ਹੈ (ਜਦੋਂ ਵੀ handler ਚੱਲ ਸਕਦਾ ਹੈ ਤਾਂ 200; ਇਹ readiness ਦੀ ਉਡੀਕ ਨਹੀਂ ਕਰਦਾ)। ਦੋਵੇਂ ਹਾਲੇ ਵੀ request handling ਵਾਲੇ ਉਸੇ Node event loop ਉੱਤੇ ਚੱਲਦੇ ਹਨ, ਇਸ ਲਈ CPU-bound catalog ਜਾਂ compression ਕੰਮ ਉਨ੍ਹਾਂ ਨੂੰ ਦੇਰੀ ਕਰ ਸਕਦਾ ਹੈ — ਰੁੱਝਿਆ ਹੋਣਾ ≠ dead ਹੋਣਾ। ਜੇ HTTP probes ਦਾ ਸਮਾਂ ਸਮਾਪਤ ਹੋ ਜਾਂਦਾ ਹੈ, ਤਾਂ TCP liveness ਨੂੰ ਤਰਜੀਹ ਦਿਓ। ਜਾਂਚਾਂ ਬਾਰੇ ਪੂਰੀ ਸੇਧ:
[Monitoring ਗਾਈਡ — Kubernetes ਜਾਂਚ ਸਿਫ਼ਾਰਸ਼ਾਂ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations)।

## Caddy ਨਾਲ Docker Compose (HTTPS Auto-TLS)

OmniRoute ਨੂੰ Caddy ਦੀ ਆਟੋਮੈਟਿਕ SSL ਪ੍ਰੋਵਿਜ਼ਨਿੰਗ ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਸੁਰੱਖਿਅਤ ਢੰਗ ਨਾਲ ਉਪਲਬਧ ਕਰਵਾਇਆ ਜਾ ਸਕਦਾ ਹੈ। ਯਕੀਨੀ ਬਣਾਓ ਕਿ ਤੁਹਾਡੇ ਡੋਮੇਨ ਦਾ DNS A ਰਿਕਾਰਡ ਤੁਹਾਡੇ ਸਰਵਰ ਦੇ IP ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ।

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # OAuth ਕਾਲਬੈਕਾਂ, ਡੈਸ਼ਬੋਰਡ ਲਿੰਕਾਂ ਅਤੇ ਬਣਾਏ ਗਏ ਜਨਤਕ URL ਲਈ ਬ੍ਰਾਊਜ਼ਰ-ਫੇਸਿੰਗ ਓਰਿਜਿਨ।
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # ਤਹਿ ਕੀਤੀਆਂ ਜੌਬਾਂ / ਸੈਲਫ਼-ਫੈਚਾਂ ਲਈ ਅੰਦਰੂਨੀ ਸਰਵਰ-ਤੋਂ-ਸਰਵਰ URL।
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

Caddy ਅੱਪਸਟ੍ਰੀਮ ਕੰਟੇਨਰ ਲਈ ਮਿਆਰੀ ਫਾਰਵਰਡਿੰਗ ਹੈਡਰ ਸੈੱਟ ਕਰਦਾ ਹੈ। OmniRoute, OAuth ਕਾਲਬੈਕਾਂ ਅਤੇ ਬਣਾਏ ਗਏ ਜਨਤਕ ਲਿੰਕਾਂ ਲਈ `NEXT_PUBLIC_BASE_URL` ਨੂੰ ਕੈਨੋਨਿਕਲ ਜਨਤਕ ਓਰਿਜਿਨ ਵਜੋਂ ਵਰਤਦਾ ਹੈ; ਪ੍ਰਮਾਣਿਤ ਡੈਸ਼ਬੋਰਡ ਰਾਈਟਾਂ ਇੱਕੋ-ਓਰਿਜਿਨ ਬੇਨਤੀਆਂ ਦੇ ਨਾਲ ਸੈਸ਼ਨ-ਬਾਊਂਡ CSRF ਸੁਰੱਖਿਆ ਦੀ ਵਰਤੋਂ ਕਰਦੀਆਂ ਹਨ। `OMNIROUTE_TRUST_PROXY` ਨੂੰ ਸਿਰਫ਼ ਉਹਨਾਂ ਉੱਨਤ ਡਿਪਲੌਇਮੈਂਟਾਂ ਲਈ ਚਾਲੂ ਕਰੋ ਜਿੱਥੇ ਤੁਸੀਂ ਜਾਣਬੁੱਝ ਕੇ ਚਾਹੁੰਦੇ ਹੋ ਕਿ OmniRoute ਸਪਸ਼ਟ ਕੌਂਫਿਗਰੇਸ਼ਨ ਦੀ ਬਜਾਏ ਭਰੋਸੇਯੋਗ ਫਾਰਵਰਡ ਕੀਤੇ ਹੈਡਰਾਂ ਤੋਂ ਜਨਤਕ ਓਰਿਜਿਨ ਨਿਰਧਾਰਤ ਕਰੇ।

## Cloudflare Quick Tunnel

Docker ਡਿਪਲੌਇਮੈਂਟਾਂ ਲਈ ਡੈਸ਼ਬੋਰਡ ਸਹਾਇਤਾ ਵਿੱਚ `Dashboard → Endpoints` ਉੱਤੇ ਇੱਕ-ਕਲਿੱਕ **Cloudflare Quick Tunnel** ਸ਼ਾਮਲ ਹੈ। ਪਹਿਲੀ ਵਾਰ ਚਾਲੂ ਕਰਨ ਉੱਤੇ `cloudflared` ਨੂੰ ਕੇਵਲ ਲੋੜ ਪੈਣ 'ਤੇ ਡਾਊਨਲੋਡ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਤੁਹਾਡੇ ਮੌਜੂਦਾ `/v1` ਐਂਡਪੌਇੰਟ ਲਈ ਇੱਕ ਅਸਥਾਈ ਟਨਲ ਸ਼ੁਰੂ ਕੀਤੀ ਜਾਂਦੀ ਹੈ ਅਤੇ ਬਣਾਇਆ ਗਿਆ `https://*.trycloudflare.com/v1` URL ਤੁਹਾਡੇ ਆਮ ਜਨਤਕ URL ਦੇ ਬਿਲਕੁਲ ਹੇਠਾਂ ਦਿਖਾਇਆ ਜਾਂਦਾ ਹੈ।

ਸਰਗਰਮ ਟਨਲ ਦੀ ਸਥਿਤੀ ਬਦਲੇ ਬਿਨਾਂ ਐਂਡਪੌਇੰਟ ਟਨਲ ਪੈਨਲਾਂ (Cloudflare, Tailscale, ngrok) ਨੂੰ `Settings → Appearance` ਤੋਂ ਦਿਖਾਇਆ ਜਾਂ ਲੁਕਾਇਆ ਜਾ ਸਕਦਾ ਹੈ।

### ਟਨਲ ਸੰਬੰਧੀ ਨੋਟਸ

- Quick Tunnel URL ਅਸਥਾਈ ਹੁੰਦੇ ਹਨ ਅਤੇ ਹਰ ਰੀਸਟਾਰਟ ਤੋਂ ਬਾਅਦ ਬਦਲ ਜਾਂਦੇ ਹਨ।
- OmniRoute ਜਾਂ ਕੰਟੇਨਰ ਦੇ ਰੀਸਟਾਰਟ ਤੋਂ ਬਾਅਦ Quick Tunnels ਆਪਣੇ-ਆਪ ਮੁੜ ਬਹਾਲ ਨਹੀਂ ਹੁੰਦੀਆਂ। ਲੋੜ ਪੈਣ 'ਤੇ ਉਨ੍ਹਾਂ ਨੂੰ ਡੈਸ਼ਬੋਰਡ ਤੋਂ ਮੁੜ ਚਾਲੂ ਕਰੋ।
- ਪ੍ਰਬੰਧਿਤ ਇੰਸਟਾਲ ਇਸ ਵੇਲੇ `x64` / `arm64` ਉੱਤੇ Linux, macOS ਅਤੇ Windows ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ।
- ਸੀਮਤ ਕੰਟੇਨਰ ਵਾਤਾਵਰਣਾਂ ਵਿੱਚ ਰੌਲੇਦਾਰ QUIC UDP ਬਫ਼ਰ ਚੇਤਾਵਨੀਆਂ ਤੋਂ ਬਚਣ ਲਈ ਪ੍ਰਬੰਧਿਤ Quick Tunnels ਮੂਲ ਰੂਪ ਵਿੱਚ HTTP/2 ਟ੍ਰਾਂਸਪੋਰਟ ਵਰਤਦੀਆਂ ਹਨ। ਜੇਕਰ ਤੁਸੀਂ ਵੱਖਰਾ ਟ੍ਰਾਂਸਪੋਰਟ ਚਾਹੁੰਦੇ ਹੋ ਤਾਂ `CLOUDFLARED_PROTOCOL=quic` ਜਾਂ `auto` ਸੈੱਟ ਕਰੋ।
- Docker ਇਮੇਜ ਸਿਸਟਮ CA ਰੂਟਾਂ ਨੂੰ ਬੰਡਲ ਕਰਦੇ ਹਨ ਅਤੇ ਉਨ੍ਹਾਂ ਨੂੰ ਪ੍ਰਬੰਧਿਤ `cloudflared` ਤੱਕ ਪਹੁੰਚਾਉਂਦੇ ਹਨ, ਜਿਸ ਨਾਲ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰ ਟਨਲ ਦੇ ਬੂਟਸਟਰੈਪ ਹੋਣ ਸਮੇਂ TLS ਭਰੋਸੇ ਸੰਬੰਧੀ ਅਸਫਲਤਾਵਾਂ ਤੋਂ ਬਚਿਆ ਜਾਂਦਾ ਹੈ।
- ਜੇਕਰ ਤੁਸੀਂ ਚਾਹੁੰਦੇ ਹੋ ਕਿ OmniRoute ਕੋਈ ਨਵੀਂ ਬਾਈਨਰੀ ਡਾਊਨਲੋਡ ਕਰਨ ਦੀ ਬਜਾਏ ਮੌਜੂਦਾ ਬਾਈਨਰੀ ਵਰਤੇ, ਤਾਂ `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` ਸੈੱਟ ਕਰੋ।

ਮਲਟੀ-ਪਲੇਟਫਾਰਮ ਮੈਨਿਫੈਸਟ: ਮੂਲ `linux/amd64` + `linux/arm64` (Apple Silicon, AWS Graviton, Raspberry Pi)। Docker ਆਪਣੇ ਆਪ ਮੇਲ ਖਾਂਦਾ ਆਰਕੀਟੈਕਚਰ ਚੁਣਦਾ ਹੈ; ਜੇ ਤੁਹਾਨੂੰ ARM ਹੋਸਟਾਂ ਉੱਤੇ AMD64 ਇਮੂਲੇਸ਼ਨ ਲਈ ਮਜਬੂਰ ਕਰਨ ਦੀ ਲੋੜ ਹੈ ਤਾਂ `--platform linux/amd64` ਪਾਸ ਕਰੋ।

### ਰਿਲੀਜ਼ ਚੈਨਲ

OmniRoute ਸਥਿਰ ਰਿਲੀਜ਼ਾਂ, ਸਰਗਰਮ ਰਿਲੀਜ਼-ਬ੍ਰਾਂਚ ਟੈਸਟਿੰਗ ਅਤੇ ਡਿਵੈਲਪਮੈਂਟ ਬਿਲਡਾਂ ਲਈ ਵੱਖਰੇ Docker ਚੈਨਲ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ।

| ------------------------------- | ------------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `:<version>` / `:<version>-web` | ਦਸਤਖ਼ਤਸ਼ੁਦਾ/ਵਰਜਨਬੱਧ ਰਿਲੀਜ਼            | ਅਬਦਲਣਯੋਗ                    | ਪ੍ਰੋਡਕਸ਼ਨ ਡਿਪਲੌਇਮੈਂਟ ਜੋ ਕਿਸੇ ਸਟੀਕ ਰਿਲੀਜ਼ ਨੂੰ ਪਿਨ ਕਰਦੇ ਹਨ                                                                         |
| `:latest` / `:latest-web`       | ਸਭ ਤੋਂ ਉੱਚਾ **ਪ੍ਰਕਾਸ਼ਿਤ** ਸਥਿਰ SemVer | ਬਦਲਣਯੋਗ ਸਥਿਰ ਪੁਆਇੰਟਰ        | SemVer ਪ੍ਰਕਾਸ਼ਨ ਜੌਬ **ਤੋਂ ਬਾਅਦ** ਸਥਿਰ ਰਿਲੀਜ਼ਾਂ ਦੀ ਪਾਲਣਾ ਕਰਦਾ ਹੈ — `main` ਜਾਂ ਅਣਰਿਲੀਜ਼ `release/v*` ਕਮਿਟਾਂ ਨੂੰ ਟਰੈਕ **ਨਹੀਂ** ਕਰਦਾ |

| `:main` / `:main-web`           | `main` ਬ੍ਰਾਂਚ                         | ਬਦਲਣਯੋਗ ਡਿਵੈਲਪਮੈਂਟ ਪੁਆਇੰਟਰ  | ਸਿਰਫ਼ ਡਿਵੈਲਪਮੈਂਟ ਅਤੇ ਇੰਟੀਗ੍ਰੇਸ਼ਨ ਟੈਸਟਿੰਗ ਲਈ                                                                                      |

#### ਵੈੱਬ-ਸੈਸ਼ਨ ਪ੍ਰਦਾਤਾ: `-web` ਇਮੇਜ

ਉਪਰੋਕਤ ਹਰ ਚੈਨਲ ਦਾ ਇੱਕ `-web` ਟੈਗ ਵੀ ਹੁੰਦਾ ਹੈ (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`), ਜੋ `runner-web` ਸਟੇਜ ਤੋਂ ਬਣਾਇਆ ਜਾਂਦਾ ਹੈ — ਉਹੀ ਇਮੇਜ, ਨਾਲ Playwright ਅਤੇ ਇੱਕ Chromium ਬ੍ਰਾਊਜ਼ਰ। ਸਧਾਰਨ ਇਮੇਜ Chromium **ਤੋਂ ਬਿਨਾਂ** ਮਿਲਦਾ ਹੈ; `gemini-web`, `claude-web` ਅਤੇ `claude-turnstile` ਨੂੰ ਇਸਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।

ਅਸਫਲਤਾ ਸਟਾਰਟਅੱਪ ਵੇਲੇ ਨਹੀਂ, ਸਗੋਂ ਬਾਅਦ ਲਈ ਟਲ ਜਾਂਦੀ ਹੈ: ਉਹ ਪ੍ਰਦਾਤਾ ਆਪਣੇ ਮਾਡਲ ਸੂਚੀਬੱਧ ਕਰਦੇ ਹਨ ਅਤੇ ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ ਕਨੈਕਟ ਹੋਏ ਦਿਖਾਈ ਦਿੰਦੇ ਹਨ, ਅਤੇ ਸਿਰਫ਼ ਪਹਿਲੀ ਬੇਨਤੀ ਇਸ ਸੁਨੇਹੇ ਨਾਲ ਅਸਫਲ ਹੁੰਦੀ ਹੈ

```
[500]: ਬਾਹਰੀ ਮੋਡੀਊਲ playwright ਲੋਡ ਕਰਨ ਵਿੱਚ ਅਸਫਲ: ਗਲਤੀ: ਮੋਡੀਊਲ ਨਹੀਂ ਲੱਭਿਆ
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

ਜੇ ਤੁਸੀਂ ਉਹ ਪ੍ਰਦਾਤਾ ਵਰਤਦੇ ਹੋ, ਤਾਂ ਉਸੇ ਚੈਨਲ ਦਾ `-web` ਟੈਗ ਪੁੱਲ ਕਰੋ ਜਿਸ ਉੱਤੇ ਤੁਸੀਂ ਪਹਿਲਾਂ ਹੀ ਹੋ — ਹੋਰ ਕੁਝ ਨਹੀਂ ਬਦਲਦਾ। npm/CLI ਇੰਸਟਾਲੇਸ਼ਨ (ਕੋਈ Docker ਇਮੇਜ ਨਹੀਂ) ਉੱਤੇ, ਇਸਦੇ ਬਰਾਬਰ ਗੁੰਮ ਹਿੱਸਾ ਬ੍ਰਾਊਜ਼ਰ ਬਾਈਨਰੀ ਹੈ: ਹੋਸਟ ਉੱਤੇ `npx playwright install chromium` ਚਲਾਓ।

#### ਪ੍ਰੀ-ਰਿਲੀਜ਼ ਚੈਨਲ ਦੀ ਵਰਤੋਂ

`next` ਚੈਨਲ ਮੌਜੂਦਾ ਡਿਫਾਲਟ `release/v*` ਬ੍ਰਾਂਚ ਉੱਤੇ ਹਰ ਪੁਸ਼ ਨਾਲ ਮੁੜ ਬਣਾਇਆ ਜਾਂਦਾ ਹੈ ਅਤੇ AMD64 ਅਤੇ ARM64 ਦੋਵਾਂ ਲਈ ਪ੍ਰਕਾਸ਼ਿਤ ਹੁੰਦਾ ਹੈ। ਪੁਰਾਣੀਆਂ ਮੇਨਟੇਨੈਂਸ ਬ੍ਰਾਂਚਾਂ ਇਸਨੂੰ ਓਵਰਰਾਈਟ ਨਹੀਂ ਕਰ ਸਕਦੀਆਂ। ਇਹ ਚੈਨਲ ਉਹਨਾਂ ਸੁਧਾਰਾਂ ਲਈ ਇੱਕ ਪੁੱਲ ਕਰਨਯੋਗ ਇਮੇਜ ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ ਜੋ ਅਗਲਾ ਸਥਿਰ ਟੈਗ ਬਣਾਏ ਜਾਣ ਤੋਂ ਪਹਿਲਾਂ ਸਰਗਰਮ ਰਿਲੀਜ਼ ਬ੍ਰਾਂਚ ਵਿੱਚ ਮਰਜ ਹੋ ਚੁੱਕੇ ਹਨ।

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Docker Compose ਲਈ, ਚੁਣੇ ਹੋਏ ਪ੍ਰੋਫ਼ਾਈਲ ਦੁਆਰਾ ਵਰਤੇ ਜਾਂਦੇ ਇਮੇਜ ਟੈਗ ਨੂੰ ਓਵਰਰਾਈਡ ਕਰੋ, ਫਿਰ ਸਰਵਿਸ ਨੂੰ ਪੁੱਲ ਕਰਕੇ ਦੁਬਾਰਾ ਬਣਾਓ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### ਸੁਰੱਖਿਆ ਅਤੇ ਰੋਲਬੈਕ

`next` ਇੱਕ ਫਲੋਟਿੰਗ ਪ੍ਰੀ-ਰਿਲੀਜ਼ ਚੈਨਲ ਹੈ। ਇਹ ਸਰਗਰਮ ਰਿਲੀਜ਼ ਬ੍ਰਾਂਚ ਉੱਤੇ ਕਿਸੇ ਵੀ ਪੁਸ਼ ਨਾਲ ਬਦਲ ਸਕਦਾ ਹੈ ਅਤੇ **ਪ੍ਰੋਡਕਸ਼ਨ ਵਰਤੋਂ ਲਈ ਸਮਰਥਿਤ ਨਹੀਂ ਹੈ**। ਕਿਸੇ ਖ਼ਾਸ ਬਿਲਡ ਦਾ ਮੁਲਾਂਕਣ ਕਰਦੇ ਸਮੇਂ ਇਮੇਜ ਡਾਈਜੈਸਟ ਨੂੰ ਪਿਨ ਕਰੋ:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

ਟੈਸਟਿੰਗ ਤੋਂ ਪਹਿਲਾਂ, OmniRoute ਡਾਟਾ ਵਾਲਿਊਮ ਜਾਂ ਬਾਈਂਡ-ਮਾਊਂਟ ਕੀਤੀ ਡਾਟਾ ਡਾਇਰੈਕਟਰੀ ਦਾ ਬੈਕਅੱਪ ਲਓ। ਰੋਲਬੈਕ ਕਰਨ ਲਈ, ਪਹਿਲਾਂ ਵਰਤੇ ਗਏ ਸਥਿਰ ਵਰਜਨ ਜਾਂ ਡਾਈਜੈਸਟ ਨੂੰ ਬਹਾਲ ਕਰੋ ਅਤੇ ਕੰਟੇਨਰ ਨੂੰ ਦੁਬਾਰਾ ਬਣਾਓ:

```bash
docker pull diegosouzapw/omniroute:<stable-version>
docker compose up -d
```

ਕੋਈ ਰਿਲੀਜ਼-ਬ੍ਰਾਂਚ ਬਿਲਡ ਕਦੇ ਵੀ `latest` ਨੂੰ ਅੱਗੇ ਨਹੀਂ ਵਧਾ ਸਕਦਾ; ਸਿਰਫ਼ ਇੱਕ ਯੋਗ ਸਥਿਰ ਸਿਮੈਂਟਿਕ ਵਰਜਨ ਹੀ ਸਥਿਰ ਪੁਆਇੰਟਰ ਨੂੰ ਪ੍ਰਮੋਟ ਕਰ ਸਕਦਾ ਹੈ। `next` ਇਮੇਜ ਰਿਲੀਜ਼ ਇਮੇਜ ਦੀ ਜਾਂਚ ਅਤੇ CRITICAL ਕਮਜ਼ੋਰੀਆਂ ਨੂੰ ਬਲੌਕ ਕਰਨ ਵਾਲਾ ਗੇਟ ਕਾਇਮ ਰੱਖਦੇ ਹਨ।

**`latest` git ਦੀ ਨਵੀਨਤਾ ਦੀ ਗਾਰੰਟੀ ਨਹੀਂ ਹੈ।** `main` ਜਾਂ ਸਰਗਰਮ `release/v*` ਬ੍ਰਾਂਚ ਉੱਤੇ ਮਰਜ ਕੀਤੇ ਸੁਧਾਰ `:latest` ਵਿੱਚ ਉਦੋਂ ਤੱਕ **ਨਹੀਂ** ਹੁੰਦੇ ਜਦੋਂ ਤੱਕ ਕੋਈ ਸਥਿਰ SemVer ਇਮੇਜ ਪ੍ਰਕਾਸ਼ਿਤ ਨਹੀਂ ਹੁੰਦਾ ਅਤੇ ਪ੍ਰਕਾਸ਼ਨ ਜੌਬ `:latest` ਨੂੰ ਪ੍ਰਮੋਟ ਨਹੀਂ ਕਰਦੀ (ਉਸ SemVer ਵਾਲਾ ਹੀ ਡਾਈਜੈਸਟ)। ਜੇ GitHub ਉੱਤੇ ਸੁਧਾਰ ਪਹਿਲਾਂ ਹੀ ਦਿਖਾਈ ਦੇ ਰਿਹਾ ਹੈ ਪਰ `latest` ਰੁਕਿਆ ਹੋਇਆ ਲੱਗਦਾ ਹੈ, ਤਾਂ ਰਿਲੀਜ਼ ਬ੍ਰਾਂਚ ਦੀ ਜਾਂਚ ਕਰਨ ਲਈ `:next` ਪੁੱਲ ਕਰੋ ਜਾਂ SemVer ਟੈਗ ਦੀ ਉਡੀਕ ਕਰੋ।

| ------------------------------------------------------------------------------- | ----------------------------------- |
| GitOps / ਪ੍ਰੋਡਕਸ਼ਨ ਜਿਸ ਵਿੱਚ ਬਦਲਾਅ ਨਹੀਂ ਹੋਣਾ ਚਾਹੀਦਾ                              | `:X.Y.Z` (ਜਾਂ ਇਮੇਜ ਡਾਈਜੈਸਟ) ਪਿਨ ਕਰੋ |
| ਪ੍ਰਕਾਸ਼ਿਤ ਸਥਿਰ ਰਿਲੀਜ਼ਾਂ ਦੀ ਪਾਲਣਾ ਕਰਨੀ ਅਤੇ ਹਰ ਰਿਲੀਜ਼ ਉੱਤੇ ਮੁੜ-ਨਿਰਮਾਣ ਸਵੀਕਾਰ ਕਰਨਾ | `:latest`                           |
| ਅਣਰਿਲੀਜ਼ `release/v*` ਕਮਿਟਾਂ ਦੀ ਜਾਂਚ ਕਰਨੀ                                       | `:next` (ਪ੍ਰੋਡਕਸ਼ਨ ਲਈ ਨਹੀਂ)         |

## ਉਪਲਬਧਤਾ: ਡਿਫਾਲਟ SQLite ਸਿਰਫ਼ ਇੱਕ ਰੈਪਲਿਕਾ ਵਾਲਾ ਹੈ

ਮਿਆਰੀ Docker / Kubernetes OmniRoute ਵਿੱਚ **ਇੱਕ Node ਪ੍ਰਕਿਰਿਆ + ਇੱਕ SQLite ਰਾਈਟਰ** ਹੁੰਦਾ ਹੈ। ਇਸ ਟੋਪੋਲੋਜੀ ਉੱਤੇ ਉੱਚ ਉਪਲਬਧਤਾ **ਸਮਰਥਿਤ ਨਹੀਂ ਹੈ**।

| ਪਾਬੰਦੀ                                  | ਨਤੀਜਾ                                                                                                                                                                                                                                                                                                           |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ਇੱਕ ਰਾਈਟਰ                               | ਇੱਕੋ SQLite ਫ਼ਾਈਲ ਲਈ ਕਈ ਰੈਪਲਿਕਾ **ਨਾ** ਚਲਾਓ। ਇਸ ਨਾਲ DB ਖ਼ਰਾਬ ਹੋ ਜਾਂਦਾ ਹੈ।                                                                                                                                                                                                                                       |
| ਮੁੜ ਬਣਾਉਣਾ / ਰੀਸਟਾਰਟ / HEALTHCHECK kill | ਚੱਲ ਰਹੇ SSE, ਡੈਸ਼ਬੋਰਡ ਸੈਸ਼ਨਾਂ ਅਤੇ ਇਨ-ਮੈਮੋਰੀ ਸਥਿਤੀ ਦੀ **ਪੂਰੀ ਬੰਦਸ਼**। ਹਰ ਕਨੈਕਟ ਕੀਤਾ ਕਲਾਇੰਟ ਡਿਸਕਨੈਕਟ ਹੋ ਜਾਂਦਾ ਹੈ। ਖਾਲੀ-ਐਂਡਪੌਇੰਟ ਅੰਤਰਾਲ ਦੌਰਾਨ ਨਵੀਆਂ ਬੇਨਤੀਆਂ ਨੂੰ OmniRoute JSON ਦੀ ਬਜਾਏ ਰਿਵਰਸ-ਪ੍ਰਾਕਸੀ **`502 Bad Gateway: Unknown error`** ਮਿਲਦਾ ਹੈ — ਕਲਾਇੰਟ ਇਸਨੂੰ ਪ੍ਰਦਾਤਾ ਦੀ ਅਸਫਲਤਾ ਤੋਂ ਵੱਖ ਨਹੀਂ ਕਰ ਸਕਦੇ (#11015)। |
| `/healthz` ਵਾਲਾ ਹੀ ਇਵੈਂਟ ਲੂਪ            | ਇੱਕ ਵਿਅਸਤ ਕੈਟਾਲਾਗ ਜਾਂ ਕੰਪਰੈਸ਼ਨ ਟਿਕ ਪ੍ਰੋਬਾਂ ਵਿੱਚ ਦੇਰੀ ਕਰ ਸਕਦੀ ਹੈ; ਫਿਰ ਛੋਟਾ ਟਾਈਮਆਉਟ **ਇਕਲੌਤੇ** ਰੈਪਲਿਕਾ ਨੂੰ ਰੀਸਟਾਰਟ ਕਰ ਦਿੰਦਾ ਹੈ।                                                                                                                                                                                   |

**ਪ੍ਰੋਬ ਮੈਟ੍ਰਿਕਸ** ([Kubernetes ਪ੍ਰੋਬ ਸਿਫ਼ਾਰਸ਼ਾਂ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations) ਵੀ ਵੇਖੋ):

| ਪ੍ਰੋਬ              | ਟਾਰਗੇਟ                                                      | ਇਹ ਨਾ ਵਰਤੋ                                         |
| ------------------ | ----------------------------------------------------------- | -------------------------------------------------- |
| ਲਾਈਵਨੈੱਸ           | `PORT` ਉੱਤੇ TCP (ਡਿਫਾਲਟ `20128`), ਜਾਂ ਸੌਫ਼ਟ HTTP `/healthz` | `/api/monitoring/health`                           |
| ਰੈਡੀਨੈੱਸ           | HTTP `GET /healthz`                                         | ਅਜਿਹੇ ਸਖ਼ਤ ਟਾਈਮਆਉਟ ਜੋ ਵਿਅਸਤ ਇਵੈਂਟ ਲੂਪ ਨੂੰ ਬੰਦ ਸਮਝਣ |
| ਡੂੰਘੀ ਜਾਂਚ / ਮਨੁੱਖ | `/api/monitoring/health`                                    | ਆਟੋਮੈਟਿਕ kubelet ਲਾਈਵਨੈੱਸ                          |

**ਅੱਪਗ੍ਰੇਡ:** ਹਰ ਸੈਸ਼ਨ ਦੇ ਡਿਸਕਨੈਕਟ ਹੋਣ ਦੀ ਉਮੀਦ ਰੱਖੋ। ਜੇ ਸੰਭਵ ਹੋਵੇ ਤਾਂ ਕਲਾਇੰਟਾਂ ਨੂੰ ਡਰੇਨ ਕਰੋ; ਡਿਫਾਲਟ SQLite ਉੱਤੇ ਕੋਈ ਰੋਲਿੰਗ ਅੱਪਡੇਟ ਨਹੀਂ ਹੈ। Compose `restart: unless-stopped` ਅਤੇ Docker `HEALTHCHECK` ਮਿਲ ਕੇ ਕੰਟੇਨਰ ਦੇ Unhealthy ਹੋਣ ਉੱਤੇ ਇਕਲੌਤੀ ਪ੍ਰਕਿਰਿਆ ਨੂੰ ਵੀ ਬਦਲ ਦੇਣਗੇ — ਪ੍ਰਭਾਵ ਦਾ ਦਾਇਰਾ ਉਹੀ ਰਹੇਗਾ।

**ਇੱਕ ਰੈਪਲਿਕਾ** ਲਈ Kubernetes ਸਨਿੱਪਟ (Recreate ਲਾਜ਼ਮੀ ਹੈ; ਇੱਕ SQLite ਫ਼ਾਈਲ ਲਈ `replicas` ਨਾ ਵਧਾਓ):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` ਦੀ sleep ਕਾਰਨ kube, SIGTERM ਤੋਂ ਪਹਿਲਾਂ Service ਐਂਡਪੌਇੰਟ ਹਟਾ ਸਕਦਾ ਹੈ, ਤਾਂ ਜੋ **ਨਵਾਂ** ਟ੍ਰੈਫ਼ਿਕ ਬੰਦ ਹੋ ਰਹੀ ਪ੍ਰਕਿਰਿਆ ਤੱਕ ਪਹੁੰਚਣਾ ਰੋਕ ਦੇਵੇ। ਚੱਲ ਰਹੇ `/v1/responses` SSE ਨੂੰ ਹੈਵੀਵੇਟ ਐਡਮਿਸ਼ਨ ਲੀਜ਼ਾਂ ਰਾਹੀਂ `SHUTDOWN_TIMEOUT_MS` (ਡਿਫਾਲਟ 30s) ਤੱਕ ਡਰੇਨ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (#11015)। ਜਿਹੜੀਆਂ ਨਵੀਆਂ ਬੇਨਤੀਆਂ ਫਿਰ ਵੀ ਪ੍ਰਕਿਰਿਆ ਤੱਕ ਪਹੁੰਚਦੀਆਂ ਹਨ, ਉਨ੍ਹਾਂ ਨੂੰ `503` + `Retry-After: 5` ਮਿਲਦਾ ਹੈ। ਬਦਲੀ ਵਾਲਾ ਰੈਪਲਿਕਾ Ready ਹੋਣ ਤੱਕ Recreate ਦਾ ਖਾਲੀ-ਐਂਡਪੌਇੰਟ ਅੰਤਰਾਲ ਪੂਰੀ ਬੰਦਸ਼ ਹੀ ਰਹਿੰਦਾ ਹੈ — ਇਹ SQLite ਟੋਪੋਲੋਜੀ ਦਾ ਨਤੀਜਾ ਹੈ, ਪ੍ਰੋਬ ਦੀ ਗਲਤ ਸੰਰਚਨਾ ਨਹੀਂ।

ਬਾਹਰੀ Postgres / ਮਲਟੀ-ਰਾਈਟਰ HA ਇੱਕ ਦਸਤਾਵੇਜ਼ਬੱਧ ਮਿਆਰੀ ਮਾਰਗ **ਨਹੀਂ** ਹੈ। ਜੇ ਤੁਹਾਨੂੰ HA ਦੀ ਲੋੜ ਹੈ, ਤਾਂ ਇੱਕੋ ਰੈਪਲਿਕਾ ਰੱਖੋ ਜਾਂ ਅਜਿਹੀ ਟੋਪੋਲੋਜੀ ਚਲਾਓ ਜਿਸਦੀ ਪ੍ਰੋਜੈਕਟ ਨੇ ਵੱਖਰੇ ਤੌਰ ਉੱਤੇ ਜਾਂਚ ਅਤੇ ਦਸਤਾਵੇਜ਼ੀਕਰਨ ਕੀਤਾ ਹੋਵੇ। Postgres/MySQL ਦਾ ਕੰਮ [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) ਵਿੱਚ ਜਾਰੀ ਹੈ। ਉਸਦੇ ਜਾਰੀ ਹੋਣ ਤੱਕ, **ਵੱਡੀਆਂ** `/v1/responses` ਦੀ ਸਮਰੱਥਾ ਵਧਾਉਣ ਦਾ ਇਕਲੌਤਾ ਸਮਰਥਿਤ ਤਰੀਕਾ N ਸੁਤੰਤਰ ਪ੍ਰਕਿਰਿਆਵਾਂ (ਅਗਲਾ ਭਾਗ) ਹਨ, ਨਾ ਕਿ ਇੱਕ ਵਾਲਿਊਮ ਉੱਤੇ `replicas > 1`।

## ਸਕੇਲ-ਆਉਟ: N ਸੁਤੰਤਰ ਪ੍ਰਕਿਰਿਆਵਾਂ

ਇੱਕ Node ਪ੍ਰਕਿਰਿਆ **ਇੱਕ V8 ਹੀਪ** ਹੁੰਦੀ ਹੈ। ਦੋ ਆਪਸ ਵਿੱਚ ਓਵਰਲੈਪ ਕਰਦੀਆਂ ~3 MiB / ~750k-token ਕੋਡਿੰਗ-ਏਜੰਟ `POST /v1/responses` ਬੇਨਤੀਆਂ (RTK + Caveman) ਉਸ ਹੀਪ ਨੂੰ ~12 Gi 'ਤੇ ਅਬੋਰਟ ਕਰ ਦਿੰਦੀਆਂ ਹਨ (`FATAL ERROR: Reached heap limit`) ਅਤੇ 16 Gi cgroup ਵਿੱਚ OOM ਦਾ ਕਾਰਨ ਬਣ ਸਕਦੀਆਂ ਹਨ। [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ਵੇਖੋ। ਇਹ ਮਾਪ ਇੱਕ **ਮੈਮੋਰੀ-ਬਜਟ** ਚੇਤਾਵਨੀ ਹੈ, ਦੋ ਸਮਕਾਲੀ ਲੰਬੀਆਂ `/v1/responses` ਦੀ ਉਤਪਾਦ-ਪੱਧਰੀ ਸਖ਼ਤ ਅਧਿਕਤਮ ਸੀਮਾ ਨਹੀਂ। ਹੈਵੀਵੇਟ ਚੈਟ ਦਾਖ਼ਲਾ ਉਸੇ V8/cgroup ਸੀਮਾ ਤੋਂ ਆਟੋਮੈਟਿਕ ਤੌਰ 'ਤੇ ਨਿਰਧਾਰਤ ਇੰਜੈਸਟ ਬਾਈਟ ਬਜਟ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) ਦੁਆਰਾ ਨਿਯੰਤਰਿਤ ਹੁੰਦਾ ਹੈ — ਪਹਿਲਾਂ ਹੀ ਸਹੀ ਆਕਾਰ ਵਾਲੀ ਪ੍ਰਕਿਰਿਆ ਵਿੱਚ ਇਸਨੂੰ ਵਧਾ ਕੇ ਓਵਰਰਾਈਡ ਕਰਨਾ (ਜਾਂ ਪੁਰਾਣੀ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ਬੇਨਤੀ-ਗਿਣਤੀ ਸੀਮਾ ਸੈੱਟ ਕਰਨਾ) ਅਬੋਰਟ ਨੂੰ ਮੁੜ ਲਿਆਉਂਦਾ ਹੈ। ਛੋਟੀਆਂ ਚੈਟਾਂ, `/healthz`, `/v1/models`, ਅਤੇ MCP ਉਸ ਸੀਮਾ ਵਿੱਚ **ਸ਼ਾਮਲ ਨਹੀਂ** ਹਨ।

### ਇੱਕ-ਪ੍ਰਕਿਰਿਆ: ਦੋ ਤੋਂ ਵੱਧ ਲੰਬੀਆਂ `/v1/responses`

ਇੱਕ **ਸਿਹਤਮੰਦ** ਪ੍ਰਕਿਰਿਆ (ਹੀਪ `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO` ਤੋਂ ਹੇਠਾਂ, ਡਿਫਾਲਟ `0.75`) ਦੋ ਤੋਂ ਵੱਧ ਸਮਕਾਲੀ ਲੰਬੀਆਂ `POST /v1/responses` ਚਲਾ **ਸਕਦੀ ਹੈ**, ਜਦੋਂ ਪ੍ਰਕਿਰਿਆ-ਵਿਆਪੀ ਇਨਫਲਾਈਟ-ਬਾਈਟ ਬਜਟ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) ਵਿੱਚ ਅਜੇ ਵੀ ਥਾਂ ਹੋਵੇ। `OMNIROUTE_CHAT_LARGE_BODY_BYTES` (ਡਿਫਾਲਟ 256 KiB) ਦੇ ਬਰਾਬਰ ਜਾਂ ਇਸ ਤੋਂ ਵੱਡੀਆਂ ਬਾਡੀਆਂ, ਸੰਰਚਨਾ-ਭਾਰੀ ਬੇਨਤੀਆਂ ਵਾਂਗ ਉਹੀ ਹੈਵੀਵੇਟ ਲੀਜ਼ ਲੈਂਦੀਆਂ ਹਨ ਅਤੇ ਉਹੀ [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` ਐਸਕੇਪ (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ਵਰਤਦੀਆਂ ਹਨ। ਦਰਜਨਾਂ ਸਮਕਾਲੀ ਲੰਬੇ SSE ਕਲਾਇੰਟ (ਓਪਰੇਟਰਾਂ ਨੂੰ ਅਕਸਰ 40–50 ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ) ਇੱਕ **ਮੈਮੋਰੀ-ਬਜਟ** ਦਾ ਸਵਾਲ ਹੈ — ਹੀਪ + ਪ੍ਰਾਇਮਰੀ/ਹੈੱਡਰੂਮ ਸਲਾਟ + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ਦਾ ਆਕਾਰ ਨਿਰਧਾਰਤ ਕਰੋ — ਇਹ ਉਤਪਾਦ ਦੀ ਸਖ਼ਤ “ਅਧਿਕਤਮ 2” ਸੀਮਾ ਨਹੀਂ ਹੈ। ਦਬਾਅ ਹੇਠਲਾ ਹੀਪ ਫਿਰ ਵੀ ਮੁੜ ਕੋਸ਼ਿਸ਼ਯੋਗ `503` ਨਾਲ ਲੋਡ ਘਟਾਉਂਦਾ ਹੈ, ਤਾਂ ਜੋ #7849 ਮੁੜ ਨਾ ਆਵੇ।

**ਹੀਪਾਂ ਦੀ ਗਿਣਤੀ ਵਧਾਉਣ** (ਸੁਤੰਤਰ V8 old-spaces) ਲਈ **ਅੱਜ**:

| ਇਹ ਕਰੋ                                                                                                                                                 | ਇਹ ਨਾ ਕਰੋ                                                  |
| ------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| **N ਕੰਟੇਨਰ/ਪੌਡ** ਚਲਾਓ, ਹਰੇਕ ਲਈ ਇਸਦਾ **ਆਪਣਾ** `DATA_DIR` / ਵਾਲਿਊਮ ਹੋਵੇ                                                                                  | ਇੱਕ SQLite ਫ਼ਾਈਲ ਲਈ `replicas > 1` ਸੈੱਟ ਕਰੋ                |
| ਹੈਵੀ ਇਨ-ਫਲਾਈਟ + ਸਿਹਤਮੰਦ-ਹੈੱਡਰੂਮ ਦਾ ਆਕਾਰ ਹੀਪ / ਇਨਫਲਾਈਟ-ਬਾਈਟ ਬਜਟ ਦੇ ਅਧਾਰ 'ਤੇ ਨਿਰਧਾਰਤ ਕਰੋ; 1–2 ਰੂੜ੍ਹੀਵਾਦੀ #7849 ਡਿਫਾਲਟ ਹੈ, ਉਤਪਾਦ ਦੀ ਸਖ਼ਤ ਅਧਿਕਤਮ ਸੀਮਾ ਨਹੀਂ | ਇੱਕ ਪ੍ਰਕਿਰਿਆ ਨੂੰ 8× RAM ਅਤੇ ਅਸੀਮਿਤ ਗਿਣਤੀ ਸੀਮਾ ਦਿਓ          |
| ਵਿਕਲਪਿਕ: **ਸਾਂਝੇ ਕੋਟਾ ਕਾਊਂਟਰਾਂ** ਲਈ `QUOTA_STORE_DRIVER=redis` + `QUOTA_STORE_REDIS_URL`                                                               | Redis ਨੂੰ ਸਾਂਝੀ SQLite ਸਮਝੋ — ਇਹ ਅਜਿਹਾ ਨਹੀਂ ਹੈ             |
| ਹਰ ਇੰਸਟੈਂਸ ਵਿੱਚ ਪ੍ਰੋਵਾਈਡਰ ਸੀਕ੍ਰੇਟ ਡੁਪਲੀਕੇਟ ਕਰੋ (ਜਾਂ ਵੰਡੇ ਹੋਏ ਡੈਸ਼ਬੋਰਡ ਸਵੀਕਾਰ ਕਰੋ)                                                                      | ਸਾਰੇ ਇੰਸਟੈਂਸਾਂ ਵਿੱਚ ਇੱਕ ਡੈਸ਼ਬੋਰਡ / ਇੱਕ ਕਾਲ-ਲੌਗ ਦੀ ਉਮੀਦ ਕਰੋ |
| ਅੱਗੇ ਕੋਈ ਵੀ ਲੋਡ ਬੈਲੈਂਸਰ ਲਗਾਓ; API ਕੁੰਜੀ ਜਾਂ ਸੈਸ਼ਨ ਅਨੁਸਾਰ ਸਟਿੱਕੀ ਰੂਟਿੰਗ ਕਾਫ਼ੀ ਹੈ                                                                        | ਕਿਸੇ ਵਿਕਰੇਤਾ-ਵਿਸ਼ੇਸ਼ ਆਕਾਰ-ਸਚੇਤ ਮਿਡਲਵੇਅਰ ਨੂੰ ਲਾਜ਼ਮੀ ਸਮਝੋ    |

ਹਾਰਡਵੇਅਰ: ਪ੍ਰਤੀ-ਇੰਸਟੈਂਸ ਸਮਕਾਲੀ ਲੰਬੀਆਂ `/v1/responses` ਇੱਕ **ਮੈਮੋਰੀ-ਬਜਟ** ਦਾ ਸਵਾਲ ਹਨ (ਹੀਪ + ਇਨਫਲਾਈਟ-ਬਾਈਟ / #10110)। `N` ਸੁਤੰਤਰ `DATA_DIR` ਫਿਰ ਵੀ ਹੀਪਾਂ ਦੀ ਗਿਣਤੀ ਵਧਾਉਂਦੇ ਹਨ: ਹੋਸਟ RAM ਨੂੰ `N × cgroup` ਸੰਭਾਲਣਾ ਲਾਜ਼ਮੀ ਹੈ, ਨਾ ਕਿ “N=8 ਵਾਲਾ ਇੱਕ 16 Gi ਪੌਡ।” ਇੱਕ SQLite ਫ਼ਾਈਲ ਉੱਤੇ ਕਦੇ ਵੀ `replicas > 1` ਨਾ ਵਰਤੋ।

Compose ਦਾ ਖ਼ਾਕਾ (ਦੋ ਹੀਪ, ਦੋ ਵਾਲਿਊਮ — `deploy.replicas: 2` ਨਹੀਂ):

```yaml
services:
  omniroute-a:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

ਇਨ-ਪ੍ਰੋਸੈਸ ਘਣਤਾ (HTTP isolate ਤੋਂ ਬਾਹਰ ਕੰਪ੍ਰੈਸ਼ਨ) [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023) ਹੈ। ਸਾਂਝੀ ਟਿਕਾਊ ਸਟੇਟ ਉੱਤੇ ਇੱਕ ਲੌਜਿਕਲ ਕਲੱਸਟਰ [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) ਹੈ।

## ਮਹੱਤਵਪੂਰਨ ਨੋਟਸ

- **SQLite WAL ਮੋਡ:** `docker stop` ਨੂੰ ਪੂਰਾ ਹੋਣ ਦੀ ਆਗਿਆ ਦਿੱਤੀ ਜਾਣੀ ਚਾਹੀਦੀ ਹੈ ਤਾਂ ਜੋ OmniRoute ਨਵੀਨਤਮ ਤਬਦੀਲੀਆਂ ਨੂੰ ਵਾਪਸ `storage.sqlite` ਵਿੱਚ ਚੈਕਪੁਆਇੰਟ ਕਰ ਸਕੇ। ਨਾਲ ਸ਼ਾਮਲ Compose ਫ਼ਾਈਲਾਂ ਵਿੱਚ ਪਹਿਲਾਂ ਹੀ 40s ਦੀ ਸਟਾਪ ਗ੍ਰੇਸ ਮਿਆਦ ਸੈੱਟ ਕੀਤੀ ਹੋਈ ਹੈ। ਜੇ ਤੁਸੀਂ ਇਮੇਜ ਨੂੰ ਸਿੱਧਾ ਚਲਾਉਂਦੇ ਹੋ, ਤਾਂ `--stop-timeout 40` ਬਰਕਰਾਰ ਰੱਖੋ।
- **`DISABLE_SQLITE_AUTO_BACKUP`:** ਜੇ ਰੁਟੀਨ/ਲਿਖਣ ਤੋਂ ਪਹਿਲਾਂ ਵਾਲੇ ਬੈਕਅੱਪ ਬਾਹਰੀ ਤੌਰ 'ਤੇ ਪ੍ਰਬੰਧਿਤ ਕੀਤੇ ਜਾਂਦੇ ਹਨ, ਤਾਂ ਇਸਨੂੰ `true` 'ਤੇ ਸੈੱਟ ਕਰੋ। ਮੌਜੂਦਾ ਡੇਟਾਬੇਸ ਦੀਆਂ ਮਾਈਗ੍ਰੇਸ਼ਨਾਂ ਲਈ ਫਿਰ ਵੀ ਉਹਨਾਂ ਦਾ ਆਪਣਾ ਟਿਕਾਊ ਸੁਰੱਖਿਆ ਸਨੈਪਸ਼ਾਟ ਅਤੇ ਵਿਆਪਕ ਮਾਈਗ੍ਰੇਸ਼ਨ ਗਾਰਡ ਲੋੜੀਂਦਾ ਹੈ।
- **ਡੇਟਾ ਸਥਿਰਤਾ:** ਕੰਟੇਨਰ ਰੀਸਟਾਰਟਾਂ ਦੌਰਾਨ ਆਪਣੇ ਡੇਟਾਬੇਸ, ਕੁੰਜੀਆਂ ਅਤੇ ਸੰਰਚਨਾਵਾਂ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਣ ਲਈ ਹਮੇਸ਼ਾ `/app/data` ਉੱਤੇ ਇੱਕ ਵਾਲਿਊਮ ਮਾਊਂਟ ਕਰੋ।
- **ਪੋਰਟ ਸੰਰਚਨਾ:** ਡਿਫੌਲਟ `20128` ਪੋਰਟ ਨੂੰ ਬਦਲਣ ਲਈ `PORT` ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲ ਨੂੰ ਓਵਰਰਾਈਡ ਕਰੋ।
