> **TL;DR**: OmniRoute ਹਰ ਬੇਨਤੀ ਦੀ ਟੋਕਨ ਵਰਤੋਂ ਨੂੰ ਟ੍ਰੈਕ ਕਰਦਾ ਹੈ, ਲਾਗਤ ਦੀ ਗਣਨਾ ਕਰਦਾ ਹੈ, ਹਰੇਕ API ਕੁੰਜੀ ਲਈ ਕੋਟਾ ਲਾਗੂ ਕਰਦਾ ਹੈ ਅਤੇ ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ ਵਿਸ਼ਲੇਸ਼ਣ ਦਿਖਾਉਂਦਾ ਹੈ। ਇਹ ਗਾਈਡ ਸਮਝਾਉਂਦੀ ਹੈ ਕਿ ਇਹ ਸਭ ਕਿਵੇਂ ਕੰਮ ਕਰਦਾ ਹੈ।

**ਸਰੋਤ:**

- `open-sse/services/usage.ts` (~70KB) — ਮੁੱਖ ਵਰਤੋਂ ਟ੍ਰੈਕਿੰਗ
- `src/lib/usageAnalytics.ts` (~10KB) — ਡੈਸ਼ਬੋਰਡ ਲਈ ਏਗਰੀਗੇਸ਼ਨ
- `src/lib/db/quotaSnapshots.ts` — ਇਤਿਹਾਸਕ ਕੋਟਾ ਡਾਟਾ
- `src/lib/db/usage*.ts` — ਵਰਤੋਂ ਨਾਲ ਸੰਬੰਧਿਤ ਕਈ DB ਮੋਡੀਊਲ

## ਸੰਖੇਪ ਜਾਣਕਾਰੀ

OmniRoute ਵਿੱਚੋਂ ਲੰਘਣ ਵਾਲੀ ਹਰ ਬੇਨਤੀ ਇੱਕ **ਵਰਤੋਂ ਰਿਕਾਰਡ** ਬਣਾਉਂਦੀ ਹੈ, ਜਿਸ ਵਿੱਚ ਇਹ ਜਾਣਕਾਰੀ ਦਰਜ ਹੁੰਦੀ ਹੈ:

- **ਪਛਾਣ**: ਕਿਹੜੀ API ਕੁੰਜੀ, ਪ੍ਰਦਾਤਾ, ਮਾਡਲ ਅਤੇ ਕੌਂਬੋ
- **ਟੋਕਨ**: ਪ੍ਰੌਮਪਟ ਟੋਕਨ, ਕੰਪਲੀਸ਼ਨ ਟੋਕਨ, ਕੈਸ਼ ਕੀਤੇ ਟੋਕਨ ਅਤੇ ਕੁੱਲ
- **ਲਾਗਤ**: USD ਰਕਮ (ਕੀਮਤ-ਨਿਰਧਾਰਣ ਡਾਟੇ ਤੋਂ ਗਣਨਾ ਕੀਤੀ ਗਈ)
- **ਸਮਾਂ**: ਲੇਟੈਂਸੀ, ਸ਼ੁਰੂਆਤ/ਸਮਾਪਤੀ ਟਾਈਮਸਟੈਂਪ
- **ਸਥਿਤੀ**: ਸਫਲਤਾ, ਗਲਤੀ, ਦਰ-ਸੀਮਿਤ ਆਦਿ

ਇਨ੍ਹਾਂ ਰਿਕਾਰਡਾਂ ਨੂੰ **ਵਿਸ਼ਲੇਸ਼ਣ** ਵਿੱਚ ਏਗਰੀਗੇਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, **ਕੋਟਾ ਸਨੈਪਸ਼ਾਟਾਂ** ਵਜੋਂ ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ **ਹਰੇਕ ਕੁੰਜੀ ਲਈ ਬਜਟ ਸੀਮਾਵਾਂ** ਲਾਗੂ ਕਰਨ ਵਾਸਤੇ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ।

```
ਬੇਨਤੀ ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    ਵਿਸ਼ਲੇਸ਼ਣ   ਕੋਟਾ    ਬਿਲਿੰਗ
                    (ਡੈਸ਼ਬੋਰਡ) (ਲਾਗੂਕਰਨ) (ਨਿਰਯਾਤ)
```

## ਕੀ ਰਿਕਾਰਡ ਕੀਤਾ ਜਾਂਦਾ ਹੈ

`usage.ts` ਸੇਵਾ ਹਰ ਬੇਨਤੀ ਲਈ ਇੱਕ **ਵਰਤੋਂ ਇਵੈਂਟ** ਕੈਪਚਰ ਕਰਦੀ ਹੈ:

| ਫ਼ੀਲਡ              | ਕਿਸਮ    | ਸਰੋਤ                                                       |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | ਰਿਕਾਰਡ ਬਣਾਉਣ ਸਮੇਂ ਜਨਰੇਟ ਕੀਤਾ UUID                          |
| `apiKeyId`         | string  | ਉਹ API ਕੁੰਜੀ ਜਿਸ ਨੇ ਬੇਨਤੀ ਸ਼ੁਰੂ ਕੀਤੀ                       |
| `provider`         | string  | ਪ੍ਰਦਾਤਾ ID (openai, anthropic ਆਦਿ)                         |
| `model`            | string  | ਮਾਡਲ ID (gpt-5, claude-opus-4-6 ਆਦਿ)                       |
| `comboId`          | string? | ਜੇ ਕੌਂਬੋ ਰਾਹੀਂ ਰੂਟ ਕੀਤਾ ਗਿਆ ਹੋਵੇ ਤਾਂ ਕੌਂਬੋ ID              |
| `promptTokens`     | number  | ਅੱਪਸਟ੍ਰੀਮ ਜਵਾਬ ਤੋਂ                                         |
| `completionTokens` | number  | ਅੱਪਸਟ੍ਰੀਮ ਜਵਾਬ ਤੋਂ                                         |
| `cachedTokens`     | number  | ਕੈਸ਼ ਹਿੱਟ ਟੋਕਨ (Anthropic ਪ੍ਰੌਮਪਟ ਕੈਸ਼ਿੰਗ ਆਦਿ)             |
| `totalTokens`      | number  | ਪ੍ਰੌਮਪਟ + ਕੰਪਲੀਸ਼ਨ                                         |
| `costUsd`          | number  | ਕੀਮਤ-ਨਿਰਧਾਰਣ ਡਾਟੇ ਤੋਂ ਗਣਨਾ ਕੀਤੀ ਗਈ                         |
| `latencyMs`        | number  | ਸ਼ੁਰੂ ਤੋਂ ਅੰਤ ਤੱਕ ਬੇਨਤੀ ਦੀ ਮਿਆਦ                            |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | ਜੇ ਸਥਿਤੀ != `success` ਹੋਵੇ ਤਾਂ ਗਲਤੀ ਦੀ ਸ਼੍ਰੇਣੀ             |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | ਪਲੱਗਇਨ ਦੁਆਰਾ ਸ਼ਾਮਲ ਕੀਤਾ ਕਸਟਮ ਡਾਟਾ                          |

### ਟੋਕਨ ਕਿੱਥੋਂ ਆਉਂਦੇ ਹਨ

ਟੋਕਨਾਂ ਨੂੰ **ਜਵਾਬ ਹੈਂਡਲਰ** ਵਿੱਚ ਅੱਪਸਟ੍ਰੀਮ ਪ੍ਰਦਾਤਾ ਦੇ ਜਵਾਬ ਤੋਂ ਕੱਢਿਆ ਜਾਂਦਾ ਹੈ:

```ts
// open-sse/handlers/chatCore.ts ਤੋਂ
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

ਜਿਹੜੇ ਪ੍ਰਦਾਤਾ ਵਰਤੋਂ ਦੀ ਜਾਣਕਾਰੀ ਵਾਪਸ ਨਹੀਂ ਕਰਦੇ ਹਨ (ਕੁਝ ਵੈੱਬ-ਕੁਕੀ ਪ੍ਰਦਾਤਾ), ਉਨ੍ਹਾਂ ਲਈ OmniRoute `~4 chars per token` ਅਨੁਮਾਨੀ ਨਿਯਮ ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਟੋਕਨਾਂ ਦਾ **ਅਨੁਮਾਨ** ਲਗਾਉਂਦਾ ਹੈ (`open-sse/services/autoCombo/pipelineRouter.ts` ਵੇਖੋ)।

### ਕੈਸ਼ ਕੀਤੇ ਟੋਕਨ

OmniRoute `cached_tokens` ਨੂੰ `prompt_tokens` ਤੋਂ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਟ੍ਰੈਕ ਕਰਦਾ ਹੈ ਕਿਉਂਕਿ:

- Anthropic ਪ੍ਰੌਮਪਟ ਕੈਸ਼ਿੰਗ, ਕੈਸ਼ ਕੀਤੇ ਟੋਕਨਾਂ ਲਈ ਘੱਟ ਦਰ ਵਸੂਲਦੀ ਹੈ (ਆਮ ਦਰ ਦਾ 10%)
- ਕੁਝ ਪ੍ਰਦਾਤਾ `cache_read_input_tokens` ਵਾਪਸ ਕਰਦੇ ਹਨ, ਜਿਨ੍ਹਾਂ ਦੀ ਕੀਮਤ ਵੱਖਰੇ ਢੰਗ ਨਾਲ ਨਿਰਧਾਰਤ ਕੀਤੀ ਜਾਣੀ ਚਾਹੀਦੀ ਹੈ
- ਵਿਸ਼ਲੇਸ਼ਣ **ਕੈਸ਼ ਹਿੱਟ ਦਰ** = `cached_tokens / prompt_tokens` ਦਿਖਾ ਸਕਦਾ ਹੈ

## ਲਾਗਤ ਦੀ ਗਣਨਾ

ਲਾਗਤਾਂ ਦੀ ਗਣਨਾ LiteLLM ਤੋਂ ਸਿੰਕ ਕੀਤੇ **ਕੀਮਤ ਡੇਟਾ** (`src/lib/pricingSync.ts`) ਤੋਂ ਕੀਤੀ ਜਾਂਦੀ ਹੈ:

| ਮਾਡਲ              | ਇਨਪੁੱਟ $/1M | ਆਉਟਪੁੱਟ $/1M | ਕੈਸ਼ ਕੀਤਾ $/1M |
| ----------------- | ----------- | ------------ | -------------- |
| gpt-5             | $2.50       | $10.00       | —              |
| claude-opus-4-6   | $15.00      | $75.00       | $1.50          |
| claude-sonnet-4-5 | $3.00       | $15.00       | $0.30          |
| gemini-2.5-pro    | $1.25       | $10.00       | —              |

ਲਾਗਤ ਦਾ ਫ਼ਾਰਮੂਲਾ (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **ਕੈਸ਼ ਕੀਤੇ ਟੋਕਨਾਂ ਨੂੰ ਪ੍ਰੌਂਪਟ ਵਿੱਚੋਂ ਕਿਉਂ ਘਟਾਇਆ ਜਾਂਦਾ ਹੈ?** ਕੈਸ਼ ਕੀਤੇ ਹਿੱਸੇ ਦੀ ਕੀਮਤ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਲਗਾਈ ਜਾਂਦੀ ਹੈ; ਪੂਰੇ ਪ੍ਰੌਂਪਟ ਉੱਤੇ ਇਨਪੁੱਟ ਕੀਮਤ ਲਗਾਉਣ ਨਾਲ ਗਿਣਤੀ ਵੱਧ ਹੋ ਜਾਵੇਗੀ।

### ਕੀਮਤ ਸਿੰਕ

ਕੀਮਤ ਡੇਟਾ `/api/pricing/sync` ਐਂਡਪੌਇੰਟ ਰਾਹੀਂ LiteLLM ਤੋਂ ਆਪਣੇ-ਆਪ ਸਿੰਕ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (ਇਹ ਬਿਲਟ-ਇਨ cron ਟਾਸਕ ਦੁਆਰਾ ਟ੍ਰਿਗਰ ਹੁੰਦਾ ਹੈ, ਨਾ ਕਿ ਕਿਸੇ ਯੂਜ਼ਰ-ਫੇਸਿੰਗ env var ਦੁਆਰਾ):

```bash
# ਹੱਥੀਂ ਟ੍ਰਿਗਰ
curl -X POST http://localhost:20128/api/pricing/sync
```

ਜਿਨ੍ਹਾਂ ਮਾਡਲਾਂ ਲਈ ਕੀਮਤ ਡੇਟਾ ਉਪਲਬਧ ਨਹੀਂ ਹੈ, ਉਨ੍ਹਾਂ ਲਈ OmniRoute ਅੰਦਰੂਨੀ ਔਸਤ ਦਰਾਂ (LiteLLM ਦੇ ਕੀਮਤ ਡੇਟਾ ਤੋਂ ਪ੍ਰਾਪਤ) ਦੀ ਵਰਤੋਂ ਕਰਕੇ **ਲਾਗਤ ਦਾ ਅਨੁਮਾਨ ਲਗਾਉਂਦਾ ਹੈ**।

## ਮਿਤੀ-ਸੀਮਾ ਏਗਰੀਗੇਸ਼ਨ

`usageAnalytics.ts` ਮੋਡੀਊਲ ਕੱਚੇ ਵਰਤੋਂ ਡੇਟਾ ਤੋਂ ਡੈਸ਼ਬੋਰਡ ਵਿਜੇਟਾਂ ਦੀ ਗਣਨਾ ਕਰਦਾ ਹੈ। ਇਹ 7 ਸਮਾਂ-ਸੀਮਾਵਾਂ ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ:

| ਸੀਮਾ     | ਮਿਆਦ                              | ਵਰਤੋਂ ਦਾ ਮਾਮਲਾ               |
| -------- | --------------------------------- | ---------------------------- |
| `1d`     | ਪਿਛਲੇ 24 ਘੰਟੇ                     | ਪ੍ਰਤੀ-ਘੰਟਾ ਲਾਗਤ ਵਾਧੇ ਦੀ ਪਛਾਣ |
| `7d`     | ਪਿਛਲੇ 7 ਦਿਨ                       | ਹਫ਼ਤਾਵਾਰੀ ਸਮੀਖਿਆ             |
| `30d`    | ਪਿਛਲੇ 30 ਦਿਨ                      | ਮਹੀਨਾਵਾਰ ਬਿਲਿੰਗ              |
| `90d`    | ਪਿਛਲੇ 90 ਦਿਨ                      | ਤਿਮਾਹੀ ਵਿਸ਼ਲੇਸ਼ਣ             |
| `ytd`    | ਮੌਜੂਦਾ ਸਾਲ ਦੀ 1 ਜਨਵਰੀ ਤੋਂ         | ਸਾਲਾਨਾ ਬਜਟ ਟ੍ਰੈਕਿੰਗ          |
| `all`    | ਹੁਣ ਤੱਕ ਦਾ ਸਾਰਾ ਸਮਾਂ              | ਸਮੁੱਚੇ ਜੀਵਨ-ਕਾਲ ਦੇ ਅੰਕੜੇ     |
| `custom` | ਯੂਜ਼ਰ ਵੱਲੋਂ ਪਰਿਭਾਸ਼ਿਤ ਸ਼ੁਰੂਆਤ/ਅੰਤ | ਆਡਿਟ, ਲੋੜ ਅਨੁਸਾਰ ਕੁਐਰੀਆਂ     |

### ਗਣਨਾ ਕੀਤੇ ਡੈਸ਼ਬੋਰਡ ਵਿਜੇਟ

## ਕੋਟਾ ਲਾਗੂਕਰਨ

ਹਰੇਕ API ਕੁੰਜੀ ਲਈ ਕੋਟਾ ਦੋ ਥਾਵਾਂ 'ਤੇ ਲਾਗੂ ਕੀਤਾ ਜਾਂਦਾ ਹੈ:

1. **ਨਰਮ ਸੀਮਾ** (`quotaWarnAt`): ਵਰਤੋਂ ਹੱਦ ਤੋਂ ਵੱਧ ਹੋਣ 'ਤੇ ਡੈਸ਼ਬੋਰਡ ਚੇਤਾਵਨੀ
2. **ਸਖ਼ਤ ਸੀਮਾ** (`quotaLimit`): ਹੱਦ ਤੋਂ ਵੱਧ ਹੋਣ 'ਤੇ ਬੇਨਤੀ HTTP 429 ਨਾਲ ਅਸਵੀਕਾਰ ਕੀਤੀ ਜਾਂਦੀ ਹੈ

### ਸੰਰਚਨਾ

```ts
// ਹਰੇਕ API ਕੁੰਜੀ ਲਈ
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — ਚੇਤਾਵਨੀ ਦਿਖਾਓ
  quotaLimit: 10_00,    // $10.00 — ਪੂਰੀ ਤਰ੍ਹਾਂ ਰੋਕੋ
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### ਲਾਗੂਕਰਨ ਪ੍ਰਵਾਹ

```
ਬੇਨਤੀ ──▶ quotaCheck()
              │
              ├── ਸੀਮਾ ਦੇ ਅੰਦਰ?  ──▶ ਮਨਜ਼ੂਰ ਕਰੋ
              │
              └── ਸੀਮਾ ਤੋਂ ਵੱਧ?  ──▶ 429 ਬਹੁਤ ਜ਼ਿਆਦਾ ਬੇਨਤੀਆਂ
                                   Retry-After ਹੈਡਰ ਸਮੇਤ
```

### ਕੋਟਾ ਸਨੈਪਸ਼ਾਟ

`quotaSnapshots` ਟੇਬਲ ਰੁਝਾਨ ਵਿਸ਼ਲੇਸ਼ਣ ਲਈ **ਇਤਿਹਾਸਕ ਕੋਟਾ ਸਥਿਤੀ** ਸਟੋਰ ਕਰਦੀ ਹੈ:

| ਫ਼ੀਲਡ | ਵੇਰਵਾ |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | ਟ੍ਰੈਕ ਕੀਤੀ ਜਾ ਰਹੀ ਕੁੰਜੀ |
| `window` | "day" | "week" | "month" |
| `used` | ਇਸ ਵਿੰਡੋ ਵਿੱਚ ਵਰਤੀ ਗਈ ਲਾਗਤ (ਸੈਂਟ) |
| `limit` | ਸੀਮਾ (ਸੈਂਟ) |
| `resetAt` | ਵਿੰਡੋ ਕਦੋਂ ਰੀਸੈੱਟ ਹੁੰਦੀ ਹੈ |
| `createdAt` | ਸਨੈਪਸ਼ਾਟ ਕਦੋਂ ਲਿਆ ਗਿਆ ਸੀ |

ਸਨੈਪਸ਼ਾਟ **ਹਰੇਕ ਉਸ ਬੇਨਤੀ 'ਤੇ** ਲਏ ਜਾਂਦੇ ਹਨ ਜਿਸ ਦੀ ਲਾਗਤ > 0 ਹੁੰਦੀ ਹੈ, ਅਤੇ ਇਨ੍ਹਾਂ ਦੀ ਵਰਤੋਂ ਇਹ ਕਰਨ ਲਈ ਕੀਤੀ ਜਾਂਦੀ ਹੈ:

- ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ ਕੋਟਾ ਪ੍ਰਗਤੀ ਪੱਟੀ ਰੈਂਡਰ ਕਰਨਾ
- 30-ਦਿਨਾਂ ਦੇ ਕੋਟਾ ਰੁਝਾਨ ਚਾਰਟ ਦਿਖਾਉਣਾ
- ਵਰਤੋਂ ਦੇ ਸੀਮਾ ਦੇ ਨੇੜੇ ਪਹੁੰਚਣ 'ਤੇ ਚੇਤਾਵਨੀਆਂ ਟ੍ਰਿਗਰ ਕਰਨਾ

## ਰਿਟੇਨਸ਼ਨ ਅਤੇ ਸਫ਼ਾਈ

ਵਰਤੋਂ ਡਾਟਾ ਹਰ ਬੇਨਤੀ ਪਿੱਛੇ ~1-10KB ਵਧਦਾ ਹੈ। ਵੱਡੇ ਪੈਮਾਨੇ 'ਤੇ, ਇਹ ਕਾਫ਼ੀ ਮਹੱਤਵਪੂਰਨ ਹੋ ਸਕਦਾ ਹੈ।

### ਰਿਟੇਨਸ਼ਨ ਸੈਟਿੰਗਾਂ

ਵਰਤੋਂ ਇਤਿਹਾਸ ਦੀ ਰਿਟੇਨਸ਼ਨ ਨੂੰ UI ਵਿੱਚ Database Settings ਰਾਹੀਂ ਜਾਂ `/api/settings/database` ਰਾਹੀਂ ਕੌਂਫਿਗਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

ਮੂਲ ਰੂਪ ਵਿੱਚ, ਵਰਤੋਂ ਇਤਿਹਾਸ ਨੂੰ **90 ਦਿਨਾਂ** ਲਈ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ।

### ਸਫ਼ਾਈ

ਪੁਰਾਣੇ ਰਿਕਾਰਡਾਂ ਨੂੰ `src/lib/db/cleanup.ts` ਦੁਆਰਾ ਸਾਫ਼ ਕੀਤਾ ਜਾਂਦਾ ਹੈ:

- ਬੈਕਗ੍ਰਾਊਂਡ cron ਪ੍ਰਕਿਰਿਆ ਦੁਆਰਾ ਚਾਲੂ ਹੁੰਦਾ ਹੈ
- ਕੌਂਫਿਗਰ ਕੀਤੀ `usageHistory` ਰਿਟੇਨਸ਼ਨ ਸੈਟਿੰਗ ਤੋਂ ਪੁਰਾਣੇ ਰਿਕਾਰਡਾਂ ਨੂੰ `usage_history` ਵਿੱਚੋਂ ਮਿਟਾਉਂਦਾ ਹੈ

### ਸਟੋਰੇਜ ਅਨੁਮਾਨ

| ਬੇਨਤੀ ਦਰ            | 30-ਦਿਨਾਂ ਦੀ ਸਟੋਰੇਜ | 90-ਦਿਨਾਂ ਦੀ ਸਟੋਰੇਜ |
| ------------------- | ------------------ | ------------------ |
| 100 ਬੇਨਤੀਆਂ/ਦਿਨ     | ~3MB               | ~9MB               |
| 1,000 ਬੇਨਤੀਆਂ/ਦਿਨ   | ~30MB              | ~90MB              |
| 10,000 ਬੇਨਤੀਆਂ/ਦਿਨ  | ~300MB             | ~900MB             |
| 100,000 ਬੇਨਤੀਆਂ/ਦਿਨ | ~3GB               | ~9GB               |

ਬਹੁਤ ਜ਼ਿਆਦਾ ਟ੍ਰੈਫਿਕ ਲਈ, ਇਹਨਾਂ 'ਤੇ ਵਿਚਾਰ ਕਰੋ:

- Database Settings ਰਾਹੀਂ ਰਿਟੇਨਸ਼ਨ ਮਿਆਦ ਘਟਾਉਣਾ
- ਕੱਚੇ ਰਿਕਾਰਡਾਂ ਦੀ ਬਜਾਏ `aggregated_metrics` ਦੀ ਵਰਤੋਂ ਕਰਨਾ (ਕੇਵਲ ਵਿਸ਼ਲੇਸ਼ਣ ਲਈ)

## ਸਮੱਸਿਆ-ਨਿਵਾਰਣ

### "ਲਾਗਤ ਉਮੀਦ ਤੋਂ ਵੱਧ ਹੈ"

1. **`/api/usage/analytics?groupBy=model`** ਦੀ ਜਾਂਚ ਕਰੋ — ਮਹਿੰਗਾ ਮਾਡਲ ਲੱਭੋ
2. **`/api/usage/analytics?groupBy=apiKey`** ਦੀ ਜਾਂਚ ਕਰੋ — ਵੱਧ ਵਰਤੋਂਕਾਰ ਲੱਭੋ
3. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਕੀਮਤ ਡਾਟਾ ਅੱਪ ਟੂ ਡੇਟ ਹੈ: `POST /api/pricing/sync`

### "ਰਿਕਾਰਡ ਗੁੰਮ ਹਨ"

- Dashboard → Database → Cleanup ਅਧੀਨ DB ਰਿਟੇਨਸ਼ਨ ਸੈਟਿੰਗਾਂ ਦੀ ਜਾਂਚ ਕਰੋ — ਪੁਰਾਣੇ ਰਿਕਾਰਡ ਆਵਰਤੀ ਸਫ਼ਾਈ ਟਾਸਕ (`src/lib/db/cleanup.ts`) ਦੁਆਰਾ ਮਿਟਾਏ ਜਾਂਦੇ ਹਨ
- `src/lib/db/usage*.ts` ਵਿੱਚ ਤਰੁੱਟੀਆਂ ਦੀ ਜਾਂਚ ਕਰੋ — DB ਲਿਖਣ ਦੀਆਂ ਅਸਫਲਤਾਵਾਂ ਲੌਗ ਕੀਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ ਪਰ ਸਾਹਮਣੇ ਨਹੀਂ ਦਿਖਾਈਆਂ ਜਾਂਦੀਆਂ
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਬੇਨਤੀ ਅਸਲ ਵਿੱਚ `chatCore` ਤੱਕ ਪਹੁੰਚੀ ਸੀ — ਕੰਬੋ ਰੂਟਿੰਗ ਦੀ ਜਾਂਚ ਕਰੋ

### "ਕੋਟਾ ਲਾਗੂ ਨਹੀਂ ਹੋ ਰਿਹਾ"

- ਕੁੰਜੀ ਦੀ `quotaLimit` ਸੈਟਿੰਗ ਦੀ ਜਾਂਚ ਕਰੋ
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `quotaWindow` ਸਹੀ ਢੰਗ ਨਾਲ ਸੈੱਟ ਕੀਤਾ ਗਿਆ ਹੈ
- `quotaSnapshots` ਰਿਕਾਰਡ ਲੱਭੋ — ਉਹ ਹਰ ਬੇਨਤੀ 'ਤੇ ਬਣਾਏ ਜਾਣੇ ਚਾਹੀਦੇ ਹਨ
