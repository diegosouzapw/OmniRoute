TPROXY ਪਾਰਦਰਸ਼ੀ ਡਿਕ੍ਰਿਪਟ, [Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM ਸਟੈਕ ਲਈ OmniRoute ਦਾ **5ਵਾਂ ਕੈਪਚਰ ਮੋਡ** ਹੈ। ਇਹ kernel TPROXY + policy routing ਦੀ ਵਰਤੋਂ ਕਰਕੇ Linux ਉੱਤੇ ਸਥਾਨਕ ਆਊਟਬਾਊਂਡ HTTPS ਟ੍ਰੈਫਿਕ ਨੂੰ ਇੰਟਰਸੈਪਟ ਅਤੇ **ਡਿਕ੍ਰਿਪਟ** ਕਰਦਾ ਹੈ — `/etc/hosts` ਦੀ ਸਪੂਫ਼ਿੰਗ ਕੀਤੇ **ਬਿਨਾਂ** ਅਤੇ ਪੂਰੇ OS ਦੀਆਂ system-proxy ਸੈਟਿੰਗਾਂ ਨੂੰ ਬਦਲੇ **ਬਿਨਾਂ**। ਇਹ headless ਵਰਤੋਂ ਲਈ ਢੁਕਵਾਂ ਹੈ
(ਸਾਫ਼ ਕਰਨ ਲਈ ਕੋਈ DNS ਤਬਦੀਲੀਆਂ ਨਹੀਂ) ਅਤੇ ਰੀਬੂਟ ਹੋਣ 'ਤੇ firewall ਨਿਯਮ ਆਪਣੇ-ਆਪ ਹਟ ਜਾਂਦੇ ਹਨ।

ਹੋਰ ਕੈਪਚਰ ਮੋਡਾਂ ਤੋਂ ਉਲਟ, TPROXY ਨੂੰ ਹਰ ਹੋਸਟ ਲਈ ਵੱਖਰੇ ਸੈੱਟਅੱਪ ਦੀ ਲੋੜ ਨਹੀਂ ਹੁੰਦੀ: ਇਹ ਟਾਰਗੇਟ ਪੋਰਟ ਉੱਤੇ **ਕਿਸੇ ਵੀ** ਮੰਜ਼ਿਲ ਹੋਸਟ ਨੂੰ ਜਾਣ ਵਾਲੇ ਟ੍ਰੈਫਿਕ ਨੂੰ ਪਾਰਦਰਸ਼ੀ ਢੰਗ ਨਾਲ ਇੰਟਰਸੈਪਟ ਕਰਦਾ ਹੈ, ਹਰ SNI hostname ਲਈ ਤੁਰੰਤ ਜਾਰੀ ਕੀਤੇ leaf certificate ਨਾਲ TLS ਨੂੰ ਸਮਾਪਤ ਕਰਦਾ ਹੈ, ਡਿਕ੍ਰਿਪਟ ਕੀਤੇ ਐਕਸਚੇਂਜ ਨੂੰ ਕੈਪਚਰ ਕਰਦਾ ਹੈ ਅਤੇ ਬੇਨਤੀ ਨੂੰ ਮੁੜ ਇਨਕ੍ਰਿਪਟ ਕਰਕੇ ਮੂਲ ਮੰਜ਼ਿਲ ਵੱਲ ਭੇਜਦਾ ਹੈ।

> **ਸਿਰਫ਼ Linux, ਸਿਰਫ਼ root, ਚੋਣ ਕਰਨ 'ਤੇ ਹੀ।** ਇਸ ਮੋਡ ਲਈ Linux, C toolchain ਨਾਲ ਬਣਾਇਆ ਇੱਕ native addon ਅਤੇ **CAP_NET_ADMIN** capability (ਆਮ ਤੌਰ 'ਤੇ root) ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ। ਇਹ ਸਿਰਫ਼ loopback ਵਾਲੇ AgentBridge API ਦੇ ਪਿੱਛੇ ਸੀਮਿਤ ਹੈ ਅਤੇ ਮੂਲ ਰੂਪ ਵਿੱਚ ਅਸਮਰੱਥ ਹੈ। ਕਿਸੇ ਵੀ ਹੋਸਟ ਲਈ ਦਸਤਖ਼ਤ ਕਰ ਸਕਣ ਵਾਲਾ ਭਰੋਸੇਯੋਗ MITM CA ਇੱਕ ਸ਼ਕਤੀਸ਼ਾਲੀ ਸਮਰੱਥਾ ਹੈ — [§6 ਸੁਰੱਖਿਆ](#6-security) ਵੇਖੋ।

## §1 ਇਹ ਕੀ ਹੈ ਅਤੇ ਇਸਨੂੰ ਕਦੋਂ ਵਰਤਣਾ ਹੈ

ਬਾਕੀ ਚਾਰ ਕੈਪਚਰ ਮੋਡਾਂ ਵਿੱਚੋਂ ਹਰੇਕ ਦੀ ਇੱਕ ਸੀਮਾ ਹੈ:

| ਮੋਡ               | ਟ੍ਰੈਫਿਕ ਨੂੰ ਕਿਵੇਂ ਮੋੜਿਆ ਜਾਂਦਾ ਹੈ            | ਸੀਮਾ                                                 |
| ----------------- | ------------------------------------------- | ---------------------------------------------------- |
| AgentBridge       | ਸਥਿਰ ਹੋਸਟ ਸਮੂਹ ਦੀ `/etc/hosts` DNS ਸਪੂਫ਼ਿੰਗ | ਸਿਰਫ਼ ਰਜਿਸਟਰ ਕੀਤੇ IDE-agent ਹੋਸਟ                     |
| Custom Hosts      | ਹਰ ਹੋਸਟ ਲਈ `/etc/hosts` DNS ਸਪੂਫ਼ਿੰਗ        | ਹਰ ਹੋਸਟ ਲਈ ਇੱਕ ਐਂਟਰੀ; hosts ਨੂੰ ਸੋਧਣ ਲਈ sudo         |
| HTTP_PROXY        | `HTTP_PROXY`/`HTTPS_PROXY` env              | ਸਿਰਫ਼ ਉਹ ਐਪਾਂ ਜੋ env var ਦਾ ਪਾਲਣ ਕਰਦੀਆਂ ਹਨ           |
| System-wide proxy | OS proxy ਸੈਟਿੰਗਾਂ                           | ਗਲੋਬਲ ਸਥਿਤੀ ਬਦਲਦਾ ਹੈ; ਵਾਪਸ ਪਹਿਲਾਂ ਵਰਗੀ ਕਰਨ ਦੀ ਲੋੜ ਹੈ |

ਇਸ ਦੀ ਬਜਾਏ TPROXY ਪਾਰਦਰਸ਼ੀ ਡਿਕ੍ਰਿਪਟ ਟ੍ਰੈਫਿਕ ਨੂੰ **kernel** ਪੱਧਰ 'ਤੇ ਮੋੜਦਾ ਹੈ। ਇਹ `mangle OUTPUT` ਚੇਨ ਵਿੱਚ ਟਾਰਗੇਟ ਪੋਰਟ (ਮੂਲ `443`) ਵੱਲ ਜਾਣ ਵਾਲੀਆਂ ਨਵੀਆਂ ਸਥਾਨਕ ਆਊਟਬਾਊਂਡ TCP ਕਨੈਕਸ਼ਨਾਂ ਨੂੰ ਚਿੰਨ੍ਹਿਤ ਕਰਦਾ ਹੈ, ਇੱਕ `ip rule` ਚਿੰਨ੍ਹਿਤ ਪੈਕੇਟਾਂ ਨੂੰ ਸਥਾਨਕ ਡਿਲੀਵਰੀ ਵੱਲ ਮੁੜ ਰੂਟ ਕਰਦਾ ਹੈ, ਅਤੇ ਮੁੜ ਦਾਖ਼ਲ ਹੋਣ 'ਤੇ `mangle PREROUTING` ਦਾ `TPROXY` ਟਾਰਗੇਟ ਉਨ੍ਹਾਂ ਨੂੰ ਇੱਕ **IP_TRANSPARENT** listener ਦੇ ਹਵਾਲੇ ਕਰ ਦਿੰਦਾ ਹੈ — ਜੋ ਫਿਰ TLS ਨੂੰ ਸਮਾਪਤ ਕਰਕੇ plaintext ਕੈਪਚਰ ਕਰਦਾ ਹੈ।

ਇਸਨੂੰ ਉਦੋਂ ਵਰਤੋ ਜਦੋਂ ਤੁਸੀਂ ਕਿਸੇ ਅਜਿਹੀ ਪ੍ਰਕਿਰਿਆ ਤੋਂ ਆਉਣ ਵਾਲੇ ਟ੍ਰੈਫਿਕ ਨੂੰ ਕੈਪਚਰ ਅਤੇ ਡਿਕ੍ਰਿਪਟ ਕਰਨਾ ਚਾਹੁੰਦੇ ਹੋ ਜੋ:

- ਕਿਸੇ ਅਜਿਹੇ ਹੋਸਟ ਨਾਲ ਸੰਚਾਰ ਕਰਦੀ ਹੈ ਜਿਸਨੂੰ AgentBridge ਰਜਿਸਟਰ ਨਹੀਂ ਕਰਦਾ, ਅਤੇ
- `HTTP_PROXY` ਦਾ ਪਾਲਣ ਨਹੀਂ ਕਰਦੀ, ਅਤੇ
- ਜਿਸਨੂੰ ਤੁਸੀਂ ਪੂਰੇ ਸਿਸਟਮ ਦੀ proxy ਤਬਦੀਲੀ ਨਾਲ ਪ੍ਰਭਾਵਿਤ ਨਹੀਂ ਕਰਨਾ ਚਾਹੁੰਦੇ।

ਕਿਉਂਕਿ ਇੰਟਰਸੈਪਸ਼ਨ kernel ਵਿੱਚ ਹੁੰਦੀ ਹੈ, ਇਸ ਲਈ ਮੂਲ ਪ੍ਰਕਿਰਿਆ ਨੂੰ **ਕਿਸੇ configuration ਤਬਦੀਲੀ** ਦੀ ਲੋੜ ਨਹੀਂ ਹੁੰਦੀ — ਪਰ ਪ੍ਰਕਿਰਿਆ ਨੂੰ OmniRoute ਵੱਲੋਂ ਇੰਸਟਾਲ ਕੀਤੇ dynamic CA 'ਤੇ ਭਰੋਸਾ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) ਵੇਖੋ)।

## §2 ਲੋੜਾਂ

| ਲੋੜ                | ਵੇਰਵਾ                                                                                                                                                                 |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**             | ਕੇਵਲ Linux — **IP_TRANSPARENT** ਸਿਰਫ਼ Linux ਲਈ ਉਪਲਬਧ socket ਵਿਕਲਪ ਹੈ। ਹੋਰ ਹਰ platform ਉੱਤੇ loader "ਉਪਲਬਧ ਨਹੀਂ" ਵਾਪਸ ਕਰਦਾ ਹੈ।                                          |
| **ਵਿਸ਼ੇਸ਼ ਅਧਿਕਾਰ** | transparent socket ਬਣਾਉਣ ਅਤੇ `iptables`/`ip` ਨਿਯਮ ਲਾਗੂ ਕਰਨ ਲਈ **CAP_NET_ADMIN** capability — ਅਮਲ ਵਿੱਚ, root ਵਜੋਂ ਚਲਾਓ।                                                |
| **Native addon**   | ਇੱਕ ਛੋਟਾ N-API addon (`src/mitm/tproxy/native/transparent.c`) build ਕੀਤਾ ਜਾਂ prebuild ਵਜੋਂ ਮੁਹੱਈਆ ਕੀਤਾ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ। [§3](#3-the-native-ip_transparent-addon) ਵੇਖੋ। |
| **Kernel modules** | `TPROXY`, `mangle`, ਅਤੇ `mark` match ਸਹਿਯੋਗ ਵਾਲਾ `iptables` (kernel 6.8.0 ਨਾਲ ਪ੍ਰਮਾਣਿਤ)।                                                                              |

**ਸੁਚੱਜੀ ਗਿਰਾਵਟ:** ਜੇ ਕੋਈ ਵੀ ਲੋੜ ਮੌਜੂਦ ਨਾ ਹੋਵੇ (ਗੈਰ-Linux, ਕੋਈ toolchain ਨਹੀਂ,
addon build ਨਹੀਂ ਹੋਇਆ), ਤਾਂ addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
exception ਸੁੱਟਣ ਦੀ ਬਜਾਏ `null` ਵਾਪਸ ਕਰਦਾ ਹੈ। ਇਸ ਤੋਂ ਬਾਅਦ capture-mode ਸਥਿਤੀ
`available: false` ਰਿਪੋਰਟ ਕਰਦੀ ਹੈ, dashboard toggle **ਅਯੋਗ** ਹੋ ਜਾਂਦਾ ਹੈ ਅਤੇ tooltip
"TPROXY decrypt ਲਈ Linux + root + native addon ਦੀ ਲੋੜ ਹੈ" ਦਿਖਾਉਂਦਾ ਹੈ, ਜਦਕਿ
OmniRoute ਦਾ ਬਾਕੀ ਹਿੱਸਾ ਕੰਮ ਕਰਦਾ ਰਹਿੰਦਾ ਹੈ।

## §3 Native IP_TRANSPARENT addon

Node ਦਾ `net` module `bind()` ਤੋਂ _ਪਹਿਲਾਂ_ `setsockopt(IP_TRANSPARENT)` ਨਹੀਂ ਕਰ ਸਕਦਾ,
ਜਿਸਦੀ TPROXY ਨੂੰ ਲੋੜ ਹੁੰਦੀ ਹੈ (ਨਹੀਂ ਤਾਂ kernel redirect ਕੀਤੇ packets ਨੂੰ drop ਕਰ ਦਿੰਦਾ ਹੈ)। addon
(`src/mitm/tproxy/native/transparent.c`, ਜੋ `binding.gyp` ਰਾਹੀਂ build ਹੁੰਦਾ ਹੈ) ਇੱਕ ਛੋਟਾ N-API
module ਹੈ ਜੋ ਤਿੰਨ functions ਉਪਲਬਧ ਕਰਦਾ ਹੈ, ਜਿਨ੍ਹਾਂ ਦੀ ਵਰਤੋਂ `transparentSocket.ts` ਰਾਹੀਂ ਹੁੰਦੀ ਹੈ:

| Addon function                        | Socket ਦਾ ਕੰਮ                                                                                   | ਇਸ ਲਈ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ                                                             |
| ------------------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, raw fd ਵਾਪਸ ਕਰਦਾ ਹੈ | transparent capture listener (Node `server.listen({ fd })` ਰਾਹੀਂ fd ਅਪਣਾਉਂਦਾ ਹੈ) |
| `setSocketMark(fd, mark)`             | ਮੌਜੂਦਾ fd ਉੱਤੇ `setsockopt` **SO_MARK**                                                         | anti-loop (proxy ਦੇ ਆਪਣੇ sockets ਨੂੰ mark ਕਰਨਾ)                                  |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()` ਤੋਂ **ਪਹਿਲਾਂ** `socket()` + **SO_MARK**, fd ਵਾਪਸ ਕਰਦਾ ਹੈ               | ਮੁੜ-encrypted upstream forward (SYN mark ਨੂੰ ਨਾਲ ਲੈ ਜਾਂਦਾ ਹੈ)                    |

ਮੂਲ destination ਨੂੰ `socket.localAddress`/`localPort` ਤੋਂ ਪੜ੍ਹਿਆ ਜਾਂਦਾ ਹੈ — TPROXY
ਇਸਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦਾ ਹੈ, ਇਸ ਲਈ ਕਿਸੇ **SO_ORIGINAL_DST**/NAT lookup ਦੀ ਲੋੜ ਨਹੀਂ ਹੁੰਦੀ।

### Addon build ਕਰਨਾ

```bash
npm run build:native:tproxy      # src/mitm/tproxy/native ਵਿੱਚ ਜਾਓ ਅਤੇ node-gyp rebuild ਚਲਾਓ
                                 # -> native/build/Release/transparent.node
```

- `npm run build` ਦੌਰਾਨ, `scripts/build/build-tproxy-native.mjs` `node-gyp
rebuild` ਚਲਾਉਂਦਾ ਹੈ। ਇਹ **ਸਿਰਫ਼ Linux ਲਈ ਅਤੇ non-fatal** ਹੈ — toolchain ਦੀ ਗੈਰਹਾਜ਼ਰੀ ਸਿਰਫ਼
  capture mode ਨੂੰ ਅਣਉਪਲਬਧ ਛੱਡਦੀ ਹੈ।
- `assembleStandalone.mjs`, `build/Release/transparent.node` ਨੂੰ standalone
  bundle ਵਿੱਚ copy ਕਰਦਾ ਹੈ; `transparentSocket.ts` ਇਸਨੂੰ module-relative ਅਤੇ
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`) ਦੋਵਾਂ ਢੰਗਾਂ ਨਾਲ resolve ਕਰਦਾ ਹੈ।
- `build/` ਅਤੇ `prebuilds/` git-ignored ਹਨ — binary **build ਕੀਤੀ ਜਾਂਦੀ ਹੈ, ਕਦੇ
  commit ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ**।

Loader ਤਰਜੀਹ ਦੇ ਕ੍ਰਮ ਵਿੱਚ ਇਨ੍ਹਾਂ ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ:
`native/build/Release/transparent.node`, ਫਿਰ `native/prebuilds/transparent.node`
(ਦੋਵੇਂ module-relative ਅਤੇ `<cwd>/src/mitm/tproxy/` ਦੇ ਅਧੀਨ)।

## §4 ਪ੍ਰਤੀ-SNI ਡਾਇਨਾਮਿਕ CA ਅਤੇ ਟਰੱਸਟ-ਸਟੋਰ ਇੰਸਟਾਲਰ

> **#6684 ਅੱਪਡੇਟ:** AgentBridge ਸਟੈਟਿਕ ਸਰਵਰ (`src/mitm/server.cjs`) ਹੁਣ
> ਇੱਕੋ ਸਟੈਟਿਕ ਸਵੈ-ਦਸਤਖ਼ਤ ਕੀਤੇ ਲੀਫ਼ ਦੀ ਬਜਾਏ ਇਸੇ CA/ਲੀਫ਼ ਆਰਕੀਟੈਕਚਰ ਪੈਟਰਨ ਨੂੰ
> ਸਾਂਝਾ ਕਰਦਾ ਹੈ। ਇਹ ਇੱਕ **ਵੱਖਰੀ** CA ਇੰਸਟੈਂਸ
> (`src/mitm/cert/rootCa.ts`, ਜੋ `<DATA_DIR>/mitm/ca.key`/`ca.crt` 'ਤੇ ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੰਭਾਲੀ ਜਾਂਦੀ ਹੈ)
> ਵਰਤਦਾ ਹੈ ਅਤੇ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ `omniroute-mitm.crt` ਟਰੱਸਟ-ਸਟੋਰ ਸਲਾਟ ਹੇਠ
> ਇੰਸਟਾਲ ਹੁੰਦਾ ਹੈ (ਉੱਥੇ ਪੁਰਾਣੇ ਇਕੱਲੇ ਲੀਫ਼ ਦੀ ਥਾਂ ਲੈਂਦਾ ਹੈ — ਦੋਹਰੇ-ਟਰੱਸਟ ਦੀ ਸਫ਼ਾਈ ਦੀ ਲੋੜ ਨਹੀਂ),
> ਅਤੇ ਹੇਠਾਂ ਦਿੱਤੇ TPROXY ਦੇ ਆਪਣੇ `omniroute-tproxy-ca.crt` ਸਲਾਟ ਤੋਂ ਪੂਰੀ ਤਰ੍ਹਾਂ
> ਵੱਖਰਾ ਰੱਖਿਆ ਜਾਂਦਾ ਹੈ। ਨਵੀਆਂ AgentBridge ਇੰਸਟਾਲੇਸ਼ਨਾਂ ਨੂੰ CA ਮਾਡਲ ਆਪਣੇ-ਆਪ ਮਿਲ ਜਾਂਦਾ ਹੈ;
> ਜਿਹੜੀ ਇੰਸਟਾਲੇਸ਼ਨ ਪਹਿਲਾਂ ਹੀ ਪੁਰਾਣੇ ਸਟੈਟਿਕ ਲੀਫ਼ 'ਤੇ ਭਰੋਸਾ ਕਰਦੀ ਹੈ, ਉਹ ਇਸਨੂੰ ਉਦੋਂ ਤੱਕ
> ਵਰਤਦੀ ਰਹਿੰਦੀ ਹੈ ਜਦੋਂ ਤੱਕ ਓਪਰੇਟਰ `MITM_ROOT_CA_ENABLED=true` ਰਾਹੀਂ ਇਸਨੂੰ ਚੋਣਵਾਂ ਤੌਰ 'ਤੇ
> ਸਮਰੱਥ ਨਹੀਂ ਕਰਦਾ (`src/mitm/cert/migration.ts` ਵੇਖੋ) — ਇੱਕ ਭਰੋਸੇਯੋਗ MITM CA ਜੋ
> **ਕਿਸੇ ਵੀ** ਹੋਸਟ ਲਈ ਲੀਫ਼ 'ਤੇ ਦਸਤਖ਼ਤ ਕਰ ਸਕਦੀ ਹੈ, ਪੁਰਾਣੇ ਨਿਸ਼ਚਿਤ-SAN ਲੀਫ਼ ਨਾਲੋਂ
> ਕਾਫ਼ੀ ਵੱਧ ਸ਼ਕਤੀਸ਼ਾਲੀ ਹੈ, ਇਸ ਲਈ ਪਹਿਲਾਂ ਤੋਂ ਭਰੋਸੇਯੋਗ ਇੰਸਟਾਲੇਸ਼ਨ ਲਈ ਇਹ ਬਦਲਾਅ ਕਦੇ ਵੀ
> ਚੁੱਪਚਾਪ ਨਹੀਂ ਹੁੰਦਾ।

ਇਤਿਹਾਸਕ ਤੌਰ 'ਤੇ, ਸਟੈਟਿਕ AgentBridge MITM ਸਰਟੀਫਿਕੇਟ ਸਿਰਫ਼ ਇਸ ਲਈ ਕੰਮ ਕਰਦਾ ਸੀ ਕਿਉਂਕਿ
AgentBridge ਹੋਸਟਾਂ ਦੇ ਇੱਕ **ਨਿਸ਼ਚਿਤ** ਸਮੂਹ ਲਈ DNS ਸਪੂਫ਼ਿੰਗ ਕਰਦਾ ਹੈ (ਜੋ ਹੁਣ ਹੇਠਲੇ
ਮਾਡਲ ਨਾਲ ਇਕਸਾਰ ਕੀਤਾ ਗਿਆ ਹੈ)। TPROXY **ਮਨਮਾਨੇ** ਹੋਸਟਾਂ ਨੂੰ ਇੰਟਰਸੈਪਟ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ
ਇਸਦੇ ਲਿਸਨਰ ਨੂੰ ਕਲਾਇੰਟ ਵੱਲੋਂ ਮੰਗੇ ਗਏ ਕਿਸੇ ਵੀ SNI ਲਈ ਇੱਕ ਵੈਧ ਲੀਫ਼ ਪੇਸ਼ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ —
ਇਹੀ ਲੋੜ ਹੁਣ AgentBridge ਲਈ ਵੀ ਸਿਰਫ਼ 4 antigravity ਹੋਸਟਾਂ ਦੀ ਬਜਾਏ ਪੂਰੇ
`MITM_TOOL_HOSTS` ਸਮੂਹ (9 ਟੂਲ ਐਂਟਰੀਆਂ) ਵਾਸਤੇ ਹੈ।

### ਡਾਇਨਾਮਿਕ CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` ਇੱਕ ਸਥਾਨਕ CA ਚਲਾਉਂਦਾ ਹੈ (`selfsigned` ਡਿਪੈਂਡੈਂਸੀ 'ਤੇ ਬਣੀ ਹੋਈ), ਜੋ:

- `generateMitmCa()` ਰਾਹੀਂ ਇੱਕ ਲੰਬੀ ਮਿਆਦ ਵਾਲੀ CA ਤਿਆਰ ਕਰਦਾ ਹੈ (CN `"OmniRoute MITM CA"`,
  10-ਸਾਲ ਦੀ ਵੈਧਤਾ, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-ਬਿੱਟ RSA / SHA-256)।
- `issueLeafCert()` ਰਾਹੀਂ **ਮੰਗ 'ਤੇ ਹਰੇਕ SNI ਹੋਸਟਨਾਮ ਲਈ ਇੱਕ ਲੀਫ਼** ਜਾਰੀ ਕਰਦਾ ਹੈ
  (1-ਸਾਲ ਦੀ ਵੈਧਤਾ, `subjectAltName` = SNI ਹੋਸਟ) ਅਤੇ ਹਰੇਕ ਹੋਸਟਨਾਮ ਲਈ ਇੱਕ
  `tls.SecureContext` ਕੈਸ਼ ਕਰਦਾ ਹੈ।
- TLS ਸਮਾਪਤ ਕਰਨ ਵਾਲੇ ਸਰਵਰ ਲਈ `createSNICallback()` ਉਪਲਬਧ ਕਰਵਾਉਂਦਾ ਹੈ
  ([§5](#5-how-decrypt-and-capture-work) ਵੇਖੋ)।
- ਰੀਸਟਾਰਟਾਂ ਦੌਰਾਨ CA ਨੂੰ ਸਥਿਰ ਰੱਖਣ ਲਈ `existingCa` ਨਾਲ ਬਣਾਇਆ ਜਾ ਸਕਦਾ ਹੈ
  (ਤਾਂ ਜੋ ਟਰੱਸਟ ਸਟੋਰ ਨੂੰ ਮੁੜ ਇੰਸਟਾਲ ਕਰਨ ਦੀ ਲੋੜ ਨਾ ਪਵੇ)।

CA ਪ੍ਰਾਈਵੇਟ ਕੁੰਜੀ **ਕਦੇ ਵੀ ਮਸ਼ੀਨ ਤੋਂ ਬਾਹਰ ਨਹੀਂ ਜਾਂਦੀ**।

### ਟਰੱਸਟ-ਸਟੋਰ ਇੰਸਟਾਲਰ (`src/mitm/tproxy/caTrust.ts`)

ਇੰਟਰਸੈਪਟ ਕੀਤੇ ਕਲਾਇੰਟ ਲਈ ਡਾਇਨਾਮਿਕ CA 'ਤੇ ਭਰੋਸਾ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ, ਇਸ ਲਈ ਕੈਪਚਰ ਮੋਡ
ਸ਼ੁਰੂ ਕਰਨ 'ਤੇ CA ਸਰਟੀਫਿਕੇਟ ਨੂੰ OS ਟਰੱਸਟ ਸਟੋਰ ਵਿੱਚ ਇੱਕ **ਸਮਰਪਿਤ ਸਲਾਟ** ਹੇਠ ਇੰਸਟਾਲ
ਕੀਤਾ ਜਾਂਦਾ ਹੈ — `omniroute-tproxy-ca.crt` (ਕਾਂਸਟੈਂਟ `TPROXY_CA_CERT_NAME`) —
ਜਿਸਨੂੰ ਸਟੈਟਿਕ MITM ਸਰਟੀਫਿਕੇਟ ਦੇ ਸਲਾਟ (`omniroute-mitm.crt`) ਤੋਂ ਵੱਖਰਾ ਰੱਖਿਆ ਜਾਂਦਾ ਹੈ,
ਤਾਂ ਜੋ ਦੋਵੇਂ ਕਦੇ ਵੀ ਇੱਕ-ਦੂਜੇ ਨੂੰ ਓਵਰਰਾਈਟ ਨਾ ਕਰਨ।

`installTproxyCa(caPem, sudoPassword?)` ਡਿਸਟ੍ਰੋ ਦੀ ਐਂਕਰ ਡਾਇਰੈਕਟਰੀ ਦਾ ਪਤਾ ਲਗਾਉਂਦਾ ਹੈ
(ਕ੍ਰਮ ਅਨੁਸਾਰ: ਪਹਿਲਾਂ Debian-ਸ਼ੈਲੀ) ਅਤੇ ਸੰਬੰਧਿਤ ਰਿਫ੍ਰੈਸ਼ ਕਮਾਂਡ ਚਲਾਉਂਦਾ ਹੈ:

| ਐਂਕਰ ਡਾਇਰੈਕਟਰੀ                              | ਰਿਫ੍ਰੈਸ਼ ਕਮਾਂਡ           |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

ਇੰਸਟਾਲੇਸ਼ਨ ਪਹਿਲਾਂ PEM ਨੂੰ ਇੱਕ ਅਸਥਾਈ ਫ਼ਾਈਲ ਵਿੱਚ ਸਟੇਜ ਕਰਦੀ ਹੈ, ਫਿਰ (ਵਿਸ਼ੇਸ਼ ਅਧਿਕਾਰਾਂ ਨਾਲ)
ਐਂਕਰ ਡਾਇਰੈਕਟਰੀ ਲਈ `mkdir -p` ਚਲਾਉਂਦੀ ਹੈ, ਸਟੇਜ ਕੀਤੀ ਫ਼ਾਈਲ ਨੂੰ ਉਸ ਵਿੱਚ `cp` ਕਰਦੀ ਹੈ,
ਅਤੇ ਰਿਫ੍ਰੈਸ਼ ਕਮਾਂਡ ਚਲਾਉਂਦੀ ਹੈ। `uninstallTproxyCa()` ਸਿਰਫ਼ ਸਮਰਪਿਤ ਸਲਾਟ ਨੂੰ ਹਟਾਉਂਦਾ ਹੈ
(ਸਟੈਟਿਕ MITM ਸਰਟੀਫਿਕੇਟ ਨੂੰ ਅਛੂਤਾ ਛੱਡਦਿਆਂ) ਅਤੇ ਰਿਫ੍ਰੈਸ਼ ਕਰਦਾ ਹੈ — ਗੈਰ-Linux ਸਿਸਟਮਾਂ
'ਤੇ ਇਹ ਕੋਈ ਕਾਰਵਾਈ ਨਹੀਂ ਕਰਦਾ।

ਸਾਰੀਆਂ ਵਿਸ਼ੇਸ਼ ਅਧਿਕਾਰਾਂ ਵਾਲੀਆਂ ਕਮਾਂਡਾਂ `execFileWithPassword`
(`src/mitm/systemCommands.ts`) ਰਾਹੀਂ ਚਲਦੀਆਂ ਹਨ — **ਆਰਗੂਮੈਂਟ ਐਰੇਆਂ ਨਾਲ, ਬਿਨਾਂ shell,
ਬਿਨਾਂ string interpolation** ਦੇ `spawn` (ਸਖ਼ਤ ਨਿਯਮ #13)। ਜਦੋਂ ਪ੍ਰੋਸੈਸ root ਹੁੰਦਾ ਹੈ
(ਉਦਾਹਰਨ ਲਈ VPS), ਤਾਂ ਟਾਰਗੇਟ ਸਿੱਧਾ ਚੱਲਦਾ ਹੈ ਅਤੇ ਕਿਸੇ ਪਾਸਵਰਡ ਦੀ ਲੋੜ ਨਹੀਂ ਹੁੰਦੀ;
ਗੈਰ-root ਡੈਸਕਟਾਪ 'ਤੇ `sudoPassword` ਨੂੰ stdin ਉੱਤੇ `sudo -S` ਰਾਹੀਂ ਪਾਸ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

> ਡੈਸਕਟਾਪ ਦਾ `sudoPassword` ਟਰੱਸਟ-ਸਟੋਰ ਇੰਸਟਾਲੇਸ਼ਨ ਨੂੰ ਅਧਿਕਾਰਤ ਕਰਨ ਲਈ POST ਬਾਡੀ ਵਿੱਚ
> ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ; ਜਦੋਂ ਪ੍ਰੋਸੈਸ root ਹੁੰਦਾ ਹੈ ਤਾਂ ਇਸਨੂੰ ਪੂਰੀ ਤਰ੍ਹਾਂ ਅਣਡਿੱਠਾ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

## §5 ਡਿਕ੍ਰਿਪਸ਼ਨ ਅਤੇ ਕੈਪਚਰ ਕਿਵੇਂ ਕੰਮ ਕਰਦੇ ਹਨ

ਪਾਈਪਲਾਈਨ (ਸਭ ਕੁਝ `src/mitm/tproxy/` ਅਧੀਨ):

```
ਸਥਾਨਕ ਐਪ  ──TCP/443──▶  mangle OUTPUT ਕਨੈਕਸ਼ਨ ਨੂੰ ਮਾਰਕ ਕਰਦਾ ਹੈ (fwmark)
                          ip rule → ਸਥਾਨਕ ਰੂਟ ਟੇਬਲ → lo
                          mangle PREROUTING TPROXY → IP_TRANSPARENT ਲਿਸਨਰ (ਪੋਰਟ 8443)
                              │  captureMode.ts: socket.localAddress ਤੋਂ ਮੂਲ ਮੰਜ਼ਿਲ ਪੜ੍ਹਦਾ ਹੈ
                              ▼
                          tlsCapture.ts:
                            1. ਪ੍ਰਤੀ-SNI ਲੀਫ਼ (dynamicCert) ਨਾਲ CLIENT ਦਾ TLS ਸਮਾਪਤ ਕਰਦਾ ਹੈ
                            2. ਅੰਦਰੂਨੀ http.Server ਡਿਕ੍ਰਿਪਟ ਕੀਤੇ ਪਲੇਨਟੈਕਸਟ ਨੂੰ ਪਾਰਸ ਕਰਦਾ ਹੈ
                            3. ਕੈਪਚਰ → source: "tproxy" ਨਾਲ globalTrafficBuffer.push()
                               (sanitizeHeaders + maskSecret ਲਾਗੂ ਕੀਤੇ ਜਾਂਦੇ ਹਨ)
                            4. ਬਾਈਪਾਸ-ਮਾਰਕ ਕੀਤੇ ਸਾਕਟ ਰਾਹੀਂ ਮੂਲ ਮੰਜ਼ਿਲ ਵੱਲ
                               ਮੁੜ-ਇਨਕ੍ਰਿਪਟ ਕਰਕੇ ਫਾਰਵਰਡ ਕਰਦਾ ਹੈ (connectMarked, ਐਂਟੀ-ਲੂਪ)
                              │
                              ▼
                          ਮੂਲ ਅੱਪਸਟ੍ਰੀਮ (api.example.com)
```

- **TLS ਸਮਾਪਤੀ** (`createTlsCaptureServer`): ਡਾਇਨਾਮਿਕ CA ਦੇ SNI ਕਾਲਬੈਕ ਦੀ ਵਰਤੋਂ ਕਰਦਿਆਂ ਕੱਚੇ ਇੰਟਰਸੈਪਟ ਕੀਤੇ
  ਸਾਕਟ ਨੂੰ ਸਰਵਰ-ਸਾਈਡ `tls.TLSSocket` ਵਿੱਚ ਰੈਪ ਕਰਦਾ ਹੈ,
  ਫਿਰ ਡਿਕ੍ਰਿਪਟ ਕੀਤੀ ਸਟ੍ਰੀਮ ਨੂੰ ਇੱਕ ਅੰਦਰੂਨੀ `http.Server` ਨੂੰ ਸੌਂਪਦਾ ਹੈ (ਮਿਆਰੀ MITM
  ਸਮਾਪਤੀ ਤਰੀਕਾ)। ਸਾਕਟਾਂ ਦੀ ਜੀਵਨ-ਅਵਧੀ `MITM_IDLE_TIMEOUT_MS` ਦੁਆਰਾ ਸੀਮਿਤ ਕੀਤੀ ਜਾਂਦੀ ਹੈ, ਤਾਂ ਜੋ ਕੋਈ
  ਅਟਕੀ ਹੋਈ ਟਨਲ ਫ਼ਾਈਲ ਡਿਸਕ੍ਰਿਪਟਰਾਂ ਨੂੰ ਖ਼ਤਮ ਨਾ ਕਰ ਸਕੇ।
- **ਕੈਪਚਰ** (`handleDecryptedRequest`): ਇੱਕ `InterceptedRequest` ਪੁਸ਼ ਕਰਦਾ ਹੈ, ਜਿਸ ਵਿੱਚ
  `source: "tproxy"` ਹੁੰਦਾ ਹੈ, ਸਥਿਤੀ `"in-flight"` ਤੋਂ ਸ਼ੁਰੂ ਹੁੰਦੀ ਹੈ, ਅਤੇ ਬਫ਼ਰ ਵਿੱਚ
  ਦਾਖ਼ਲ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਹੈਡਰਾਂ ਨੂੰ `sanitizeHeaders()` ਅਤੇ ਬਾਡੀਆਂ ਨੂੰ `maskSecret()` ਵਿੱਚੋਂ
  ਲੰਘਾਇਆ ਜਾਂਦਾ ਹੈ। ਫਿਰ ਐਂਟਰੀ ਨੂੰ ਜਵਾਬ, ਆਕਾਰਾਂ ਅਤੇ ਲੇਟੈਂਸੀ ਨਾਲ ਅੱਪਡੇਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।
- **ਮੁੜ-ਇਨਕ੍ਰਿਪਟ ਕੀਤਾ ਫਾਰਵਰਡ** (`createForward` / `realForward`): ਮੂਲ
  ਮੰਜ਼ਿਲ ਵੱਲ ਮੁੜ-ਇਨਕ੍ਰਿਪਟ ਕਰਦਾ ਹੈ। `rejectUnauthorized` ਦਾ ਡਿਫਾਲਟ **`true`** ਹੈ (ਮੂਲ ਰੂਪ ਵਿੱਚ
  ਸੁਰੱਖਿਅਤ) — ਅੱਪਸਟ੍ਰੀਮ ਸਰਟੀਫਿਕੇਟ ਦੀ ਪੁਸ਼ਟੀ ਕਲਾਇੰਟ ਦੁਆਰਾ ਬੇਨਤੀ ਕੀਤੇ SNI/Host ਦੇ
  ਵਿਰੁੱਧ ਕੀਤੀ ਜਾਂਦੀ ਹੈ, ਇਸ ਲਈ ਪ੍ਰਾਕਸੀ ਠੀਕ ਉਸੇ ਚੀਜ਼ ਨੂੰ ਰੱਦ ਕਰਦਾ ਹੈ ਜਿਸਨੂੰ ਮੂਲ ਕਲਾਇੰਟ ਕਰਦਾ।

### ਐਂਟੀ-ਲੂਪ (SO_MARK)

ਕਿਉਂਕਿ ਨਿਯਮ ਨਵੇਂ ਸਥਾਨਕ ਆਊਟਬਾਊਂਡ ਕਨੈਕਸ਼ਨਾਂ ਨੂੰ ਮਾਰਕ ਕਰਦੇ ਹਨ, ਪ੍ਰਾਕਸੀ ਦਾ **ਆਪਣਾ**
ਮੁੜ-ਇਨਕ੍ਰਿਪਟ ਕੀਤਾ ਫਾਰਵਰਡ ਆਮ ਤੌਰ 'ਤੇ ਦੁਬਾਰਾ ਇੰਟਰਸੈਪਟ ਹੋ ਜਾਂਦਾ — ਇੱਕ ਅਨੰਤ ਲੂਪ। ਇਹ
ਫਾਰਵਰਡ ਪਾਥ ਇੱਕ ਬਾਈਪਾਸ ਸਾਕਟ ਮਾਰਕ (**SO_MARK**) ਨਾਲ ਇਸ ਤੋਂ ਬਚਾਅ ਕਰਦਾ ਹੈ:

- `realForward` ਆਪਣਾ ਅੱਪਸਟ੍ਰੀਮ ਸਾਕਟ `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  ਰਾਹੀਂ ਖੋਲ੍ਹਦਾ ਹੈ — `DEFAULT_BYPASS_MARK = 0x539` — ਜੋ `connect()` ਤੋਂ **ਪਹਿਲਾਂ**
  **SO_MARK** ਸੈੱਟ ਕਰਦਾ ਹੈ, ਤਾਂ ਜੋ ਫਾਰਵਰਡ ਦਾ SYN ਬਾਈਪਾਸ ਮਾਰਕ ਲੈ ਕੇ ਜਾਵੇ।
- `mangle OUTPUT` ਨਿਯਮ ਪਹਿਲਾਂ ਹੀ ਬਾਈਪਾਸ ਮਾਰਕ ਵਾਲੇ ਕਨੈਕਸ਼ਨਾਂ ਨੂੰ ਬਾਹਰ ਰੱਖਦਾ ਹੈ
  (`-m mark ! --mark <bypassMark>`), ਇਸ ਲਈ ਪ੍ਰਾਕਸੀ ਦੇ ਫਾਰਵਰਡ ਨੂੰ ਦੁਬਾਰਾ ਮਾਰਕ **ਨਹੀਂ** ਕੀਤਾ ਜਾਂਦਾ
  ਅਤੇ ਉਹ TPROXY ਵਿੱਚ ਮੁੜ ਦਾਖ਼ਲ ਨਹੀਂ ਹੁੰਦਾ।

> ਲਾਗੂਕਰਨ ਨੋਟ: ਬਾਈਪਾਸ-ਮਾਰਕ ਕੀਤੇ ਸਾਕਟ ਨੂੰ ਏਜੰਟ ਦੇ
> `createConnection` ਉੱਤੇ ਇੰਸਟਾਲ ਕੀਤਾ ਜਾਣਾ ਲਾਜ਼ਮੀ ਹੈ (`https.request({ createConnection })` ਨੂੰ ਚੁੱਪਚਾਪ ਅਣਡਿੱਠਾ ਕੀਤਾ ਜਾਂਦਾ ਹੈ
> ਜਦੋਂ ਕੋਈ ਏਜੰਟ ਮੌਜੂਦ ਹੋਵੇ), ਨਹੀਂ ਤਾਂ ਫਾਰਵਰਡ ਇੱਕ ਬਿਨਾਂ ਮਾਰਕ ਵਾਲਾ ਸਾਕਟ ਖੋਲ੍ਹੇਗਾ ਅਤੇ
> ਲੂਪ ਵਾਪਸ ਆ ਜਾਵੇਗਾ। ਇਹ e2e-ਪ੍ਰਮਾਣਿਤ ਐਂਟੀ-ਲੂਪ ਸੁਧਾਰ ਸੀ।

## §7 ਟ੍ਰਾਂਜ਼ੈਕਸ਼ਨਲ ਫਾਇਰਵਾਲ ਲਾਗੂ ਕਰਨਾ / ਵਾਪਸ ਲੈਣਾ

ਕਿਸੇ ਕਰੈਸ਼ ਤੋਂ ਬਾਅਦ ਕਦੇ ਵੀ ਕੋਈ `mangle` ਨਿਯਮ ਜਾਂ ਪੁਰਾਣਾ ਰੂਟ ਬਚਿਆ ਨਹੀਂ ਰਹਿਣਾ ਚਾਹੀਦਾ। ਕਮਾਂਡ ਬਿਲਡਰ
(`src/mitm/tproxy/commands.ts`) ਅਤੇ ਰਨਰ (`src/mitm/tproxy/setup.ts`) ਇਹ ਗਾਰੰਟੀ ਦਿੰਦੇ ਹਨ ਕਿ
**revert, apply ਦਾ ਬਿਲਕੁਲ ਉਲਟ ਹੈ ਅਤੇ ਉਲਟੇ ਕ੍ਰਮ ਵਿੱਚ ਚੱਲਦਾ ਹੈ**।

`applyTproxy(cfg)` ਲਾਗੂ ਕਰਨ ਵਾਲੀਆਂ ਕਮਾਂਡਾਂ ਨੂੰ ਕ੍ਰਮ ਅਨੁਸਾਰ ਚਲਾਉਂਦਾ ਹੈ; **ਕਿਸੇ ਵੀ** ਅਸਫਲਤਾ ਉੱਤੇ ਇਹ
ਪੂਰਾ `revertTproxy(cfg)` ਸਭ ਤੋਂ ਵਧੀਆ ਸੰਭਵ ਕੋਸ਼ਿਸ਼ ਵਜੋਂ ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਗਲਤੀ ਨੂੰ ਮੁੜ ਸੁੱਟਦਾ ਹੈ — ਇਸ ਲਈ ਫਾਇਰਵਾਲ ਜਾਂ ਤਾਂ
ਪੂਰੀ ਤਰ੍ਹਾਂ ਲਾਗੂ ਹੁੰਦਾ ਹੈ ਜਾਂ ਪੂਰੀ ਤਰ੍ਹਾਂ ਵਾਪਸ ਲਿਆ ਜਾਂਦਾ ਹੈ, ਕਦੇ ਵੀ ਅੱਧਾ ਲਾਗੂ ਨਹੀਂ ਰਹਿੰਦਾ। `revertTproxy(cfg)`
ਉਲਟ ਕਮਾਂਡਾਂ ਨੂੰ ਉਲਟੇ ਕ੍ਰਮ ਵਿੱਚ ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਅਸਫਲਤਾਵਾਂ ਨੂੰ ਅਣਡਿੱਠਾ ਕਰਦਾ ਹੈ (ਆਈਡੈਂਪੋਟੈਂਟ — ਬਿਨਾਂ ਕਿਸੇ ਸ਼ਰਤ ਦੇ
ਕਾਲ ਕਰਨਾ ਸੁਰੱਖਿਅਤ ਹੈ, ਉਦਾਹਰਨ ਲਈ AgentBridge `repairMitm()` ਕਲੀਨਅੱਪ ਤੋਂ)।

`validateTproxyConfig(cfg)` ਕਿਸੇ ਵੀ ਕਮਾਂਡ ਤੋਂ ਪਹਿਲਾਂ ਚੱਲਦਾ ਹੈ: ਪੋਰਟਾਂ `1–65535` ਹੋਣੀਆਂ ਚਾਹੀਦੀਆਂ ਹਨ,
`mark`/`routeTable`/`bypassMark` ਧਨਾਤਮਕ ਪੂਰਨ ਅੰਕ ਹੋਣੇ ਚਾਹੀਦੇ ਹਨ, ਅਤੇ `bypassMark`, `mark`
ਤੋਂ ਵੱਖਰਾ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ (ਐਂਟੀ-ਲੂਪ)।

### ਲਾਗੂ ਕਰਨ ਵਾਲੀਆਂ ਕਮਾਂਡਾਂ (ਕ੍ਰਮ ਅਨੁਸਾਰ)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

ਵਾਪਸੀ ਦੌਰਾਨ ਇਹਨਾਂ ਨੂੰ ਉਲਟੇ ਕ੍ਰਮ ਵਿੱਚ ਮਿਟਾਇਆ ਜਾਂਦਾ ਹੈ: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`।

> ਇਹ ਵਿਧੀ **OUTPUT-ਅਧਾਰਿਤ** ਹੈ ਕਿਉਂਕਿ MITM ਵਰਤੋਂ ਦਾ ਮਾਮਲਾ _ਲੋਕਲ_ ਆਊਟਬਾਊਂਡ
> ਟ੍ਰੈਫਿਕ (ਉਸੇ ਹੋਸਟ ਉੱਤੇ ਐਪਾਂ) ਹੈ, ਜਿਸ ਨੂੰ ਸਿਰਫ਼ `PREROUTING` ਵਿੱਚ TPROXY ਨਹੀਂ
> ਦੇਖਦਾ — `PREROUTING` ਸਿਰਫ਼ ਫਾਰਵਰਡ ਕੀਤਾ ਟ੍ਰੈਫਿਕ ਦੇਖਦਾ ਹੈ। `OUTPUT` ਚੇਨ ਨਵੇਂ
> ਲੋਕਲ ਕਨੈਕਸ਼ਨਾਂ ਨੂੰ ਮਾਰਕ ਕਰਦੀ ਹੈ, `ip rule` ਉਹਨਾਂ ਨੂੰ ਲੋਕਲ ਡਿਲਿਵਰੀ (`lo`) ਵੱਲ ਮੁੜ ਰੂਟ ਕਰਦਾ ਹੈ, ਅਤੇ
> ਫਿਰ `PREROUTING` ਉਹਨਾਂ ਨੂੰ ਟ੍ਰਾਂਸਪੇਰੈਂਟ ਲਿਸਨਰ ਨੂੰ ਸੌਂਪਦਾ ਹੈ।

## §8 ਕੌਂਫਿਗਰੇਸ਼ਨ

ਸ਼ੁਰੂਆਤੀ ਬੇਨਤੀ (`POST /api/tools/agent-bridge/tproxy`) ਹੇਠਾਂ ਦਿੱਤੇ
ਫੀਲਡ ਸਵੀਕਾਰ ਕਰਦੀ ਹੈ, ਜਿਨ੍ਹਾਂ ਨੂੰ `StartTproxyBodySchema` (`tproxy/route.ts`) ਦੁਆਰਾ ਵੈਲੀਡੇਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਸਾਰੇ ਵਿਕਲਪਿਕ ਹਨ
ਅਤੇ ਨਾ ਦਿੱਤੇ ਜਾਣ ਉੱਤੇ ਆਪਣੇ ਡਿਫਾਲਟ ਮੁੱਲ ਵਰਤਦੇ ਹਨ:

| ਫੀਲਡ             | ਕਿਸਮ               | ਡਿਫਾਲਟ   | ਨੋਟਸ                                                                                                                                 |
| ---------------- | ------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **dport**        | int (1–65535)      | `443`    | ਟ੍ਰਾਂਸਪੇਰੈਂਟ ਢੰਗ ਨਾਲ ਇੰਟਰਸੈਪਟ ਕਰਨ ਲਈ ਮੰਜ਼ਿਲ TCP ਪੋਰਟ                                                                                 |
| **mark**         | int (≥1)           | `0x2333` | `OUTPUT` ਉੱਤੇ ਸੈੱਟ ਕੀਤਾ ਫਾਇਰਵਾਲ ਮਾਰਕ, ਜਿਸ ਦਾ `ip rule` + `PREROUTING` ਦੁਆਰਾ ਮਿਲਾਨ ਕੀਤਾ ਜਾਂਦਾ ਹੈ                                      |
| **onPort**       | int (1–65535)      | `8443`   | ਉਹ ਪੋਰਟ ਜਿਸ ਨਾਲ ਟ੍ਰਾਂਸਪੇਰੈਂਟ (**IP_TRANSPARENT**) ਲਿਸਨਰ ਬਾਈਂਡ ਕਰਦਾ ਹੈ                                                                |
| **routeTable**   | int (≥1)           | `233`    | `local 0.0.0.0/0` ਰੂਟ ਰੱਖਣ ਵਾਲੀ ਪਾਲਿਸੀ-ਰੂਟਿੰਗ ਟੇਬਲ ਦੀ id                                                                             |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | ਬਾਈਪਾਸ ਸਾਕਟ ਮਾਰਕ (**SO_MARK**) ਜੋ ਪ੍ਰੌਕਸੀ ਆਪਣੇ ਅੱਪਸਟ੍ਰੀਮ ਕਨੈਕਸ਼ਨਾਂ ਉੱਤੇ ਸੈੱਟ ਕਰਦੀ ਹੈ; `OUTPUT` ਵਿੱਚ ਸ਼ਾਮਲ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ (ਐਂਟੀ-ਲੂਪ) |
| **sudoPassword** | string             | —        | ਸਿਰਫ਼ ਗੈਰ-root ਡੈਸਕਟਾਪ: ਟਰੱਸਟ-ਸਟੋਰ ਇੰਸਟਾਲੇਸ਼ਨ ਨੂੰ ਅਧਿਕਾਰਤ ਕਰਦਾ ਹੈ; root ਹੋਣ ਉੱਤੇ ਅਣਡਿੱਠਾ ਕੀਤਾ ਜਾਂਦਾ ਹੈ                               |

TPROXY ਲਈ **ਕੋਈ environment variables ਨਹੀਂ ਹਨ** — ਸਾਰੀ ਕੌਂਫਿਗਰੇਸ਼ਨ
POST ਬਾਡੀ ਜਾਂ ਉੱਪਰ ਦਿੱਤੇ ਡਿਫਾਲਟਾਂ ਰਾਹੀਂ ਹੁੰਦੀ ਹੈ।

## §9 Traffic Inspector ਤੋਂ ਸਮਰੱਥ ਕਰਨਾ

1. **Traffic Inspector** (`/dashboard/tools/traffic-inspector`) ਖੋਲ੍ਹੋ।
2. ਕੈਪਚਰ-ਮੋਡ ਟੂਲਬਾਰ ਵਿੱਚ **"TPROXY Decrypt"** ⚠ ਬਟਨ ਲੱਭੋ
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`)।
   - ਜੇ ਇਹ "TPROXY ਡਿਕ੍ਰਿਪਟ ਲਈ Linux + root + ਨੇਟਿਵ ਐਡਆਨ ਲੋੜੀਂਦੇ ਹਨ" ਟੂਲਟਿਪ ਨਾਲ
     **ਅਸਮਰੱਥ** ਹੈ, ਤਾਂ ਇਸ ਹੋਸਟ ਉੱਤੇ ਨੇਟਿਵ ਐਡਆਨ ਉਪਲਬਧ ਨਹੀਂ ਹੈ (Linux ਨਹੀਂ,
     ਕੋਈ ਟੂਲਚੇਨ ਨਹੀਂ, ਜਾਂ ਐਡਆਨ ਬਿਲਡ ਨਹੀਂ ਕੀਤਾ ਗਿਆ)। [§2](#2-requirements) ਅਤੇ [§3](#3-the-native-ip_transparent-addon) ਵੇਖੋ।
3. ਬਟਨ ਉੱਤੇ ਕਲਿੱਕ ਕਰੋ। ਇਹ `startTproxyCaptureMode()` ਰਾਹੀਂ
   `POST /api/tools/agent-bridge/tproxy` ਨੂੰ ਕਾਲ ਕਰਦਾ ਹੈ
   (`src/lib/inspector/tproxyCaptureApi.ts`), ਜੋ:
   ਡਾਇਨਾਮਿਕ CA ਬਣਾਉਂਦਾ ਹੈ, ਟ੍ਰਾਂਸਪੇਰੈਂਟ ਲਿਸਨਰ ਖੋਲ੍ਹਦਾ ਹੈ, ਫਾਇਰਵਾਲ
   ਨਿਯਮ ਲਾਗੂ ਕਰਦਾ ਹੈ, ਅਤੇ OS ਟਰੱਸਟ ਸਟੋਰ ਵਿੱਚ CA ਇੰਸਟਾਲ ਕਰਦਾ ਹੈ।
4. ਚੱਲਣ ਦੌਰਾਨ, ਟੌਗਲ ਐਂਬਰ ਰੰਗ ਦਾ ਹੋ ਜਾਂਦਾ ਹੈ ਅਤੇ ਲਾਈਵ ਇੰਟਰਸੈਪਟ ਗਿਣਤੀ
   (`· <interceptCount>`) ਦਿਖਾਉਂਦਾ ਹੈ। ਇੰਟਰਸੈਪਟ ਕੀਤੀਆਂ ਬੇਨਤੀਆਂ ਬੇਨਤੀ ਸੂਚੀ ਵਿੱਚ
   `source: "tproxy"` ਨਾਲ ਦਿਖਾਈ ਦਿੰਦੀਆਂ ਹਨ।
5. ਰੋਕਣ ਲਈ ਦੁਬਾਰਾ ਕਲਿੱਕ ਕਰੋ — `stopTproxyCaptureMode()` ਰਾਹੀਂ
   `DELETE /api/tools/agent-bridge/tproxy` ਲਿਸਨਰ ਬੰਦ ਕਰਦਾ ਹੈ, CA ਅਣਇੰਸਟਾਲ ਕਰਦਾ ਹੈ,
   ਅਤੇ ਫਾਇਰਵਾਲ ਨਿਯਮਾਂ ਨੂੰ ਵਾਪਸ ਕਰਦਾ ਹੈ।

ਕੈਪਚਰ-ਮੋਡ ਸਥਿਤੀ (ਚੱਲ ਰਿਹਾ / ਉਪਲਬਧ / ਇੰਟਰਸੈਪਟ ਗਿਣਤੀ / ਲਿਸਨਰ ਪੋਰਟ)
`GET /api/tools/agent-bridge/tproxy` ਤੋਂ ਆਉਂਦੀ ਹੈ (`src/mitm/tproxy/captureManager.ts`
ਵਿੱਚ `getCaptureStatus()`)। ਇੱਕ ਸਮੇਂ ਸਿਰਫ਼ **ਇੱਕ** TPROXY ਸੈਸ਼ਨ ਚੱਲਦਾ ਹੈ —
ਦੂਜਾ ਸ਼ੁਰੂ ਕਰਨ ਦੀ ਕੋਸ਼ਿਸ਼ "TPROXY ਕੈਪਚਰ ਮੋਡ ਪਹਿਲਾਂ ਹੀ ਚੱਲ ਰਿਹਾ ਹੈ" ਸੁਨੇਹੇ ਨਾਲ ਰੱਦ ਹੋ ਜਾਂਦੀ ਹੈ।

## §10 ਸਮੱਸਿਆ-ਨਿਵਾਰਣ

### ਟੌਗਲ ਅਸਮਰੱਥ ਹੈ

ਨੇਟਿਵ ਐਡਆਨ ਲੋਡ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ। ਪੁਸ਼ਟੀ ਕਰੋ: ਤੁਸੀਂ Linux ਉੱਤੇ ਹੋ, ਤੁਸੀਂ ਐਡਆਨ
ਬਿਲਡ ਕੀਤਾ ਹੈ (`npm run build:native:tproxy`), ਅਤੇ ਪ੍ਰਕਿਰਿਆ `transparent.node`
ਨੂੰ ਲੋਡ ਕਰ ਸਕਦੀ ਹੈ। `isTransparentSocketAvailable()` ਟੌਗਲ ਨੂੰ ਨਿਯੰਤਰਿਤ ਕਰਦਾ ਹੈ;
ਐਡਆਨ ਗੁੰਮ ਹੋਣ ਉੱਤੇ `GET /api/tools/agent-bridge/tproxy`
`available: false` ਵਾਪਸ ਕਰਦਾ ਹੈ।

### ਕੁਝ ਵੀ ਕੈਪਚਰ ਨਹੀਂ ਹੁੰਦਾ

- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਇੰਟਰਸੈਪਟ ਕੀਤੀ ਪ੍ਰਕਿਰਿਆ ਅਸਲ ਵਿੱਚ ਸੰਰਚਿਤ `dport`
  (ਡਿਫਾਲਟ `443`) ਨਾਲ ਕਨੈਕਟ ਹੁੰਦੀ ਹੈ।
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਪ੍ਰਕਿਰਿਆ ਡਾਇਨਾਮਿਕ CA ਉੱਤੇ ਭਰੋਸਾ ਕਰਦੀ ਹੈ। CA
  `omniroute-tproxy-ca.crt` ਦੇ ਤਹਿਤ ਇੰਸਟਾਲ ਹੁੰਦਾ ਹੈ; ਆਪਣੇ ਟਰੱਸਟ ਸਟੋਰ
  (Firefox/Chrome NSS) ਵਾਲੀਆਂ ਐਪਾਂ ਲਈ ਉੱਥੇ ਵੀ ਸਰਟੀਫਿਕੇਟ ਜੋੜਨ ਦੀ ਲੋੜ ਹੋ ਸਕਦੀ ਹੈ।
- ਸਰਟੀਫਿਕੇਟ-ਭਰੋਸੇਯੋਗਤਾ / ਸਰਵਰ ਸਿਹਤ ਜਾਂਚਾਂ ਲਈ AgentBridge **Diagnose**
  ਸਵੈ-ਟੈਸਟ ਚਲਾਓ ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md) ਵੇਖੋ)।

### ਕ੍ਰੈਸ਼ ਤੋਂ ਬਾਅਦ ਬਚੇ ਹੋਏ ਫਾਇਰਵਾਲ ਨਿਯਮ

`revertTproxy()` ਲਾਗੂ ਕਰਨ ਦੀ ਬਿਲਕੁਲ ਉਲਟ ਕਾਰਵਾਈ ਹੈ ਅਤੇ ਆਈਡੈਂਪੋਟੈਂਟ ਹੈ। ਮੋਡ ਰੋਕਣ
ਨਾਲ ਨਿਯਮ ਵਾਪਸ ਹੋ ਜਾਂਦੇ ਹਨ; ਜੇ OmniRoute ਨੂੰ ਸੈਸ਼ਨ ਦੇ ਵਿਚਕਾਰ ਬੰਦ ਕਰ ਦਿੱਤਾ ਗਿਆ ਸੀ,
ਤਾਂ ਬਚੀ ਹੋਈ ਸਿਸਟਮ ਸਥਿਤੀ (DNS ਸਪੂਫ਼, ਰੂਟ CA, ਸਿਸਟਮ ਪ੍ਰੌਕਸੀ) ਨੂੰ ਵਾਪਸ ਕਰਨ ਲਈ
AgentBridge ਦੀ **Repair** ਕਾਰਵਾਈ (`POST /api/tools/agent-bridge/repair`) ਵਰਤੋ।
TPROXY `mangle` ਨਿਯਮ ਅਤੇ ਰੂਟ ਵੀ ਰੀਬੂਟ ਹੋਣ ਉੱਤੇ ਆਪਣੇ ਆਪ ਸਾਫ਼ ਹੋ ਜਾਂਦੇ ਹਨ।

### ਅਨੰਤ ਲੂਪ / ਪ੍ਰੌਕਸੀ ਆਪਣੇ ਹੀ ਫਾਰਵਰਡ ਨੂੰ ਇੰਟਰਸੈਪਟ ਕਰਦੀ ਹੈ

ਇਹ ਐਂਟੀ-ਲੂਪ ਮਾਮਲਾ ਹੈ। ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `bypassMark`, `mark` ਤੋਂ ਵੱਖਰਾ ਹੈ
(ਵੈਲੀਡੇਸ਼ਨ ਇਸਨੂੰ ਲਾਗੂ ਕਰਦੀ ਹੈ) ਅਤੇ ਫਾਰਵਰਡ `connectMarked` ਵਰਤਦਾ ਹੈ
(`realForward` ਵਿੱਚ ਇਹ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ)। [§5 ਐਂਟੀ-ਲੂਪ](#anti-loop-so_mark) ਵੇਖੋ।
