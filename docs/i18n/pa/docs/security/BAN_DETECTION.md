OmniRoute ਅੱਪਸਟ੍ਰੀਮ ਗਲਤੀ ਜਵਾਬਾਂ ਵਿੱਚ ਉਹਨਾਂ ਸੰਕੇਤਾਂ ਲਈ ਸਕੈਨ ਕਰਦਾ ਹੈ ਜੋ ਦਰਸਾਉਂਦੇ ਹਨ ਕਿ ਕਿਸੇ ਪ੍ਰਦਾਤਾ ਦਾ
**ਖਾਤਾ ਸਥਾਈ ਤੌਰ 'ਤੇ ਬੰਦ ਹੋ ਚੁੱਕਾ ਹੈ** (ਮੁਅੱਤਲ / ਨਿਸ਼ਕ੍ਰਿਆ / ToS-ਪਾਬੰਦੀਸ਼ੁਦਾ) ਅਤੇ, ਮੇਲ
ਮਿਲਣ 'ਤੇ, ਉਸ ਕਨੈਕਸ਼ਨ ਨੂੰ ਇੱਕ **ਅੰਤਿਮ `banned` ਸਥਿਤੀ** ਵਿੱਚ ਭੇਜ ਦਿੰਦਾ ਹੈ, ਤਾਂ ਜੋ ਬੇਨਤੀਆਂ ਲਈ
ਹੁਣ ਉਸਦੀ ਚੋਣ ਨਾ ਕੀਤੀ ਜਾਵੇ। ਇਹੀ ਕੁਝ **Security → Banned Keywords**
ਸੈਟਿੰਗ ਕਾਰਡ ਕੌਂਫਿਗਰ ਕਰਦਾ ਹੈ ("ਵਾਧੂ ਕੀਵਰਡ ਜੋ ਸਥਾਈ ਖਾਤਾ
ਪਾਬੰਦੀ ਦੀ ਪਛਾਣ ਨੂੰ ਚਾਲੂ ਕਰਦੇ ਹਨ। ਬਿਲਟ-ਇਨ ਕੀਵਰਡ ਹਮੇਸ਼ਾਂ ਲਾਗੂ ਹੁੰਦੇ ਹਨ।")।

ਇਹ ਪੰਨਾ ਬਿਲਟ-ਇਨ ਸੂਚੀ, ਪਛਾਣ ਪ੍ਰਵਾਹ, ਇਸਦੇ ਦਾਇਰੇ, ਕਸਟਮ ਕੀਵਰਡਾਂ ਨੂੰ
ਸੁਰੱਖਿਅਤ ਢੰਗ ਨਾਲ ਜੋੜਨ ਦੇ ਤਰੀਕੇ ਅਤੇ ਫਲੈਗ ਕੀਤੇ ਕਨੈਕਸ਼ਨ ਨੂੰ ਮੁੜ-ਬਹਾਲ ਕਰਨ ਦੇ ਤਰੀਕੇ ਦਾ ਵੇਰਵਾ ਦਿੰਦਾ ਹੈ। ਅੰਤਿਮ
ਸਥਿਤੀ ਖੁਦ ਲਚੀਲਾਪਣ ਮਾਡਲ ਦਾ ਹਿੱਸਾ ਹੈ — ਵੇਖੋ
[RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) ("ਅੰਤਿਮ ਸਥਿਤੀਆਂ")।

**ਅਧਿਕਾਰਤ ਸਰੋਤ:** `open-sse/services/accountFallback.ts`
(`ACCOUNT_DEACTIVATED_SIGNALS`, `getMergedBannedSignals()`, `isAccountDeactivated()`)।

## ਬਿਲਟ-ਇਨ ਕੀਵਰਡ

ਇਹ 8 ਸਬਸਟਰਿੰਗ ਹਮੇਸ਼ਾਂ ਲਾਗੂ ਹੁੰਦੀਆਂ ਹਨ (ਅੱਖਰਾਂ ਦੇ ਕੇਸ ਤੋਂ ਸੁਤੰਤਰ), ਭਾਵੇਂ ਕੋਈ ਵੀ ਕਸਟਮ ਸੂਚੀ ਹੋਵੇ:

```
account_deactivated
account has been deactivated
account has been disabled
your account has been suspended
this account is deactivated
verify your account to continue                                 (Antigravity / Google Cloud Code)
this service has been disabled in this account for violation    (Antigravity)
this service has been disabled in this account                  (Antigravity)
```

> ਜਿਵੇਂ-ਜਿਵੇਂ ਪ੍ਰਦਾਤਾ ਆਪਣੀ ਪਾਬੰਦੀ ਸੰਬੰਧੀ ਸ਼ਬਦਾਵਲੀ ਬਦਲਦੇ ਹਨ, ਇਹ ਸੂਚੀ ਵਿਕਸਿਤ ਹੁੰਦੀ ਰਹਿੰਦੀ ਹੈ। ਅਧਿਕਾਰਤ
> ਕਾਪੀ `open-sse/services/accountFallback.ts` ਵਿੱਚ `ACCOUNT_DEACTIVATED_SIGNALS` ਹੈ;
> ਉੱਪਰ ਦਿੱਤੇ ਬਲਾਕ ਨੂੰ ਇੱਕ ਸਨੈਪਸ਼ਾਟ ਸਮਝੋ।

ਦੋ ਨਾਲ ਲੱਗਦੀਆਂ, **ਵੱਖਰੀਆਂ** ਸੰਕੇਤ ਸਾਰਣੀਆਂ ਉਸੇ ਫ਼ਾਈਲ ਵਿੱਚ ਮੌਜੂਦ ਹਨ ਅਤੇ ਪਾਬੰਦੀਸ਼ੁਦਾ-ਕੀਵਰਡ ਪਛਾਣ ਦਾ ਹਿੱਸਾ _ਨਹੀਂ_ ਹਨ:

- `CREDITS_EXHAUSTED_SIGNALS` — ਬਿਲਿੰਗ/ਕੋਟਾ ਸਮਾਪਤ (`insufficient_quota`,
  `credit_balance_too_low`, `payment required`, …) → ਅੰਤਿਮ `credits_exhausted`।
- `OAUTH_INVALID_TOKEN_SIGNALS` — **ਗੈਰ-ਅੰਤਿਮ**; ਟੋਕਨ ਰਿਫ੍ਰੈਸ਼ ਨਾਲ ਮੁੜ-ਬਹਾਲੀ ਹੋ ਸਕਦੀ ਹੈ।

ਨੋਟ: **`rate limit`** / `429` ਵਰਗੇ ਆਮ ਅਸਥਾਈ ਵਾਕਾਂਸ਼ਾਂ ਨੂੰ
ਰੇਟ-ਲਿਮਿਟ / ਕਨੈਕਸ਼ਨ-ਕੂਲਡਾਊਨ ਮਾਰਗ ਦੁਆਰਾ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ ਇਹ ਪਾਬੰਦੀ ਸੰਕੇਤ **ਨਹੀਂ** ਹਨ।

## ਪਛਾਣ ਪ੍ਰਵਾਹ

```
ਅੱਪਸਟ੍ਰੀਮ ਗਲਤੀ ਜਵਾਬ
  → ਬੌਡੀ ਨੂੰ ਸਟਰਿੰਗ ਵਿੱਚ ਬਦਲਿਆ ਜਾਂਦਾ ਹੈ + ਲੋਅਰਕੇਸ ਕੀਤਾ ਜਾਂਦਾ ਹੈ
  → isAccountDeactivated(body): getMergedBannedSignals().some(sig => body.includes(sig))   [ਸਬਸਟਰਿੰਗ ਮੇਲ]
  → ਮੇਲ ਮਿਲਿਆ?
      → ਕਨੈਕਸ਼ਨ testStatus = "banned"      (ਸਥਾਈ — 1-ਸਾਲ ਦਾ ਕੂਲਡਾਊਨ, ਕਦੇ ਵੀ ਆਪਣੇ-ਆਪ ਮੁੜ-ਬਹਾਲ ਨਹੀਂ ਹੁੰਦਾ)
      → ਜੇ ਸੈਟਿੰਗ `autoDisableBannedAccounts` ਚਾਲੂ ਹੈ ਅਤੇ `autoDisableBannedScope`
        ਵਿੱਚ ਇਹ ਕਨੈਕਸ਼ਨ ਸ਼ਾਮਲ ਹੈ (`all`, ਜਾਂ OAuth/cookie/session ਲਈ `subscription`)
        → ਤਾਂ isActive = false ਵੀ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਜਦੋਂ ਦਾਇਰਾ
        `subscription` ਹੋਵੇ, ਤਾਂ ਪ੍ਰੀਪੇਡ API ਕੁੰਜੀਆਂ ਸਰਗਰਮ ਰਹਿੰਦੀਆਂ ਹਨ।
      → ਖਾਤਾ ਚੁਣਨ ਦੌਰਾਨ ਕਨੈਕਸ਼ਨ ਨੂੰ ਛੱਡ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ (ਸੰਯੁਕਤ QUOTA_BLOCKING ਸਥਿਤੀਆਂ)
```

- ਮੇਲ ਜਵਾਬ **ਬੌਡੀ** ਉੱਤੇ **ਅੱਖਰਾਂ ਦੇ ਕੇਸ ਤੋਂ ਸੁਤੰਤਰ ਸਬਸਟਰਿੰਗ** ਖੋਜ ਹੁੰਦੀ ਹੈ
  (`isAccountDeactivated`, `accountFallback.ts`)।
- ਪਾਬੰਦੀ-ਸੰਕੇਤ ਵਾਲੀ ਬੌਡੀ ਮਿਲਣ 'ਤੇ ਸਥਾਈ `banned` ਅੰਤਿਮਕਰਨ **ਕਿਸੇ ਵੀ
  HTTP ਸਥਿਤੀ** 'ਤੇ ਚਾਲੂ ਹੋ ਜਾਂਦਾ ਹੈ (`markAccountUnavailable` → `checkFallbackError` ਰਾਹੀਂ)। ਵਧੇਰੇ
  ਸੀਮਤ **`deactivated`** ਲੇਬਲ (ਜਦੋਂ ਕਨੈਕਸ਼ਨ ਕੋਲ ਕੋਈ
  ਵਾਧੂ API ਕੁੰਜੀਆਂ ਨਾ ਹੋਣ ਤਾਂ `isActive=false`) ਨੂੰ ਇਨਲਾਈਨ `chatCore.ts` ਮਾਰਗ ਦੁਆਰਾ **HTTP 401 / 403**
  ਉੱਤੇ ਲਿਖਿਆ ਜਾਂਦਾ ਹੈ (`classifyProviderError` → `ACCOUNT_DEACTIVATED` ਰਾਹੀਂ ਵਰਗੀਕ੍ਰਿਤ)। ਧਿਆਨ ਦਿਓ ਕਿ
  `markAccountUnavailable()` ਮਾਰਗ ਉਸੇ `ACCOUNT_DEACTIVATED` ਸੰਕੇਤ ਲਈ ਇੱਕ _ਵੱਖਰੀ_ ਅੰਤਿਮ ਸਥਿਤੀ —
  **`expired`** — ਲਿਖਦਾ ਹੈ (`resolveTerminalConnectionStatus` ਰਾਹੀਂ), ਇਸ ਲਈ ਉਹੀ ਪਾਬੰਦੀ,
  ਜਵਾਬ ਨੂੰ ਕਿਸ ਮਾਰਗ ਨੇ ਸੰਭਾਲਿਆ, ਇਸਦੇ ਅਧਾਰ 'ਤੇ `deactivated` ਜਾਂ `expired` ਵਜੋਂ ਸਾਹਮਣੇ ਆ ਸਕਦੀ ਹੈ। (ਪੁਰਾਣੀ
  ਕੋਡ ਟਿੱਪਣੀ ਕਹਿੰਦੀ ਹੈ "ਜਦੋਂ ਕਿਸੇ 401 ਬੌਡੀ ਵਿੱਚ ਇਹ ਸਟਰਿੰਗਾਂ ਸ਼ਾਮਲ ਹੋਣ" — ਇਹ ਮੌਜੂਦਾ ਵਿਵਹਾਰ ਨੂੰ
  ਘੱਟ ਕਰਕੇ ਦਰਸਾਉਂਦੀ ਹੈ।)
- ਜਿੱਥੇ ਵੀ ਅੰਤਿਮ ਸਥਿਤੀਆਂ ਨੂੰ ਫਿਲਟਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਉੱਥੇ `banned` ਕਨੈਕਸ਼ਨ ਨੂੰ ਚੋਣ ਤੋਂ ਬਾਹਰ ਰੱਖਿਆ ਜਾਂਦਾ ਹੈ
  (`isTerminalConnectionStatus`, ਸੰਯੁਕਤ `QUOTA_BLOCKING_CONNECTION_STATUSES`)।

## ਦਾਇਰਾ — ਕਿਹੜੇ ਪ੍ਰਦਾਤਾਵਾਂ ਨੂੰ ਸਕੈਨ ਕੀਤਾ ਜਾਂਦਾ ਹੈ

**ਸਾਰੇ ਪ੍ਰਦਾਤਾ।** ਜਾਂਚ ਆਮ ਤਰੁੱਟੀ-ਸੰਭਾਲ ਪਾਈਪਲਾਈਨ ਵਿੱਚ ਚੱਲਦੀ ਹੈ, ਜਿਸ ਵਿੱਚੋਂ
ਹਰ ਅਸਫਲ upstream ਬੇਨਤੀ ਲੰਘਦੀ ਹੈ — ਇਹ OAuth/subscription scrapers ਤੱਕ
ਸੀਮਿਤ **ਨਹੀਂ** ਹੈ। ਨਤੀਜੇ ਵਜੋਂ ਬਣੀ ਟਰਮੀਨਲ ਸਥਿਤੀ ਪ੍ਰਤੀ **connection** ਹੁੰਦੀ ਹੈ,
ਨਾ ਕਿ ਪ੍ਰਤੀ ਪ੍ਰਦਾਤਾ।

ਹਾਲਾਂਕਿ, ਬਿਲਟ-ਇਨ _strings_ ਅਸਲ ਪਾਬੰਦੀ ਦੇ ਜੋਖਮ ਵਾਲੇ subscription/OAuth
ਪ੍ਰਦਾਤਾਵਾਂ (ChatGPT Web Codex, Claude Web, Codex, Muse Spark,
Antigravity) ਲਈ ਬਣਾਏ ਗਏ ਹਨ। API-key ਪ੍ਰਦਾਤਾ ਡਿਟੈਕਟਰ ਨੂੰ ਕੇਵਲ ਉਦੋਂ ਹੀ
ਟ੍ਰਿਗਰ ਕਰੇਗਾ ਜੇ ਉਸਦੀ ਤਰੁੱਟੀ ਬਾਡੀ ਵਿੱਚ ਸ਼ਾਬਦਿਕ ਤੌਰ 'ਤੇ ਉਨ੍ਹਾਂ ਵਿੱਚੋਂ ਕੋਈ
substring ਮੌਜੂਦ ਹੋਵੇ।

`autoDisableBannedScope` (`all` | `subscription`, ਡਿਫੌਲਟ `all`) ਇਹ ਨਿਯੰਤਰਿਤ
ਕਰਦਾ ਹੈ ਕਿ ਕੀ ਮੈਚ ਹੋਣ 'ਤੇ `isActive=false` ਵੀ ਸੈੱਟ ਕੀਤਾ ਜਾਵੇ। `subscription`
ਦਾ ਅਰਥ login-ਸ਼ੈਲੀ ਦੀਆਂ ਸੀਟਾਂ ਹੈ (ਭੁਗਤਾਨਸ਼ੁਦਾ subscriptions ਅਤੇ ਮੁਫ਼ਤ ਖਾਤੇ,
ਜਿਨ੍ਹਾਂ ਵਿੱਚ web-cookie sessions ਵੀ ਸ਼ਾਮਲ ਹਨ)। ਇਹ prepaid API keys ਲਈ ਫਿਰ ਵੀ
`testStatus=banned` ਦਰਜ ਕਰਦਾ ਹੈ, ਪਰ ਉਨ੍ਹਾਂ ਨੂੰ routing pool ਵਿੱਚ ਰਹਿਣ ਦਿੰਦਾ ਹੈ।
ਟਿਕਾਊ ਡਿਜ਼ਾਈਨ ਪ੍ਰਤੀ-ਪ੍ਰਦਾਤਾ ਅਤੇ ਪ੍ਰਤੀ-ਖਾਤਾ override ਹੈ; global enum ਪਹਿਲਾ
ਰੂਪ ਹੈ।

## ਕਸਟਮ ਪਾਬੰਦੀਸ਼ੁਦਾ ਕੀਵਰਡ

**Security → Banned Keywords** ਵਿੱਚ ਕੀਵਰਡ ਸ਼ਾਮਲ ਕਰੋ ਜਾਂ ਹਟਾਓ (global
`customBannedSignals` setting ਵਜੋਂ `PATCH /api/settings` ਰਾਹੀਂ ਸਥਾਈ ਤੌਰ 'ਤੇ
ਸੰਭਾਲੇ ਜਾਂਦੇ ਹਨ)। ਇਹ ਬਿਲਟ-ਇਨ ਸੂਚੀ ਵਿੱਚ **ਜੋੜੇ ਜਾਂਦੇ ਹਨ** — ਕਦੇ ਵੀ ਉਸਦਾ
ਬਦਲ ਨਹੀਂ ਬਣਦੇ — ਅਤੇ save ਕਰਨ 'ਤੇ (ਅਤੇ startup ਵੇਲੇ)
`setCustomBannedSignals()` ਰਾਹੀਂ hot-reload ਹੁੰਦੇ ਹਨ। ਹਰ ਕੀਵਰਡ ਵੱਧ ਤੋਂ ਵੱਧ
200 ਅੱਖਰਾਂ ਦਾ ਹੋ ਸਕਦਾ ਹੈ; array ਦੀ ਲੰਬਾਈ ਲਈ ਕੋਈ ਸੀਮਾ ਨਹੀਂ ਹੈ।

**⚠ ਗਲਤ-ਸਕਾਰਾਤਮਕ ਨਤੀਜੇ ਦਾ ਜੋਖਮ — ਖਾਸ ਵਾਕਾਂਸ਼ ਚੁਣੋ।** ਪਛਾਣ ਪੂਰੀ response
body ਉੱਤੇ raw substring match ਰਾਹੀਂ ਹੁੰਦੀ ਹੈ, ਅਤੇ ਇੱਕ match **ਸਥਾਈ** ਹੁੰਦਾ ਹੈ
(1-ਸਾਲ cooldown, manual recovery)। ਕੋਈ ਵਿਆਪਕ ਕੀਵਰਡ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਿਹਤਮੰਦ
connection ਨੂੰ ਪਾਬੰਦੀਸ਼ੁਦਾ ਕਰ ਸਕਦਾ ਹੈ:

- **ਮਾੜੇ:** `quota`, `limit`, `error`, `denied` — ਕਈ ਅਸਥਾਈ ਤਰੁੱਟੀਆਂ ਵਿੱਚ ਆਉਂਦੇ ਹਨ।
- **ਚੰਗੇ:** ਪਾਬੰਦੀ ਦੇ ਪੂਰੇ ਵਾਕ, ਜਿਵੇਂ `your account has been suspended for`,
  `account permanently banned`, `violation of our terms`।

ਉਹ ਸਭ ਤੋਂ ਲੰਮਾ ਅਤੇ ਅਸਪਸ਼ਟਤਾ-ਰਹਿਤ ਵਾਕਾਂਸ਼ ਤਰਜੀਹ ਦਿਓ ਜੋ ਪ੍ਰਦਾਤਾ ਅਸਲ ਪਾਬੰਦੀ
ਵੇਲੇ ਵਾਪਸ ਕਰਦਾ ਹੈ। ਸ਼ੱਕ ਹੋਣ 'ਤੇ ਪਹਿਲਾਂ connection ਦਾ `lastError` ਵੇਖੋ, ਫਿਰ
ਬਿਲਕੁਲ ਉਹੀ ਸ਼ਬਦਾਵਲੀ ਸ਼ਾਮਲ ਕਰੋ।

## ਫਲੈਗ ਕੀਤੇ connection ਦੀ ਰਿਕਵਰੀ

ਟਰਮੀਨਲ `banned` / `deactivated` ਸਥਿਤੀਆਂ **ਕਦੇ ਵੀ ਆਪਣੇ-ਆਪ ਰਿਕਵਰ ਨਹੀਂ ਹੁੰਦੀਆਂ**
(ਉਹ proactive-recovery tick ਤੋਂ ਬਾਹਰ ਰੱਖੀਆਂ ਜਾਂਦੀਆਂ ਹਨ — ਕੇਵਲ `unavailable`
cooldowns ਆਪਣੇ-ਆਪ ਰਿਕਵਰ ਹੁੰਦੇ ਹਨ)। ਕਿਸੇ operator ਨੂੰ ਉਨ੍ਹਾਂ ਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ
ਸਾਫ਼ ਕਰਨਾ ਪਵੇਗਾ:

1. **Connection ਦੀ ਮੁੜ ਜਾਂਚ ਕਰੋ** — dashboard ਦੀ **Test** ਕਾਰਵਾਈ
   (`POST /api/providers/{id}/test`); ਸਫਲ probe `testStatus` ਨੂੰ ਮੁੜ
   `active` ਕਰਦੀ ਹੈ ਅਤੇ ਤਰੁੱਟੀ fields ਸਾਫ਼ ਕਰਦੀ ਹੈ।
2. **ਮੁੜ authenticate ਕਰੋ / credentials ਸੋਧੋ** — OAuth ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ login
   / refresh flow ਦੁਬਾਰਾ ਚਲਾਓ; provider create/import routes
   `isActive = true` ਸੈੱਟ ਕਰਦੇ ਹਨ।
3. **Connection ਨੂੰ ਮੁੜ enable ਕਰੋ** — ਜੇ auto-disable ਨੇ
   `isActive = false` ਸੈੱਟ ਕੀਤਾ ਸੀ (scope `all`, ਜਾਂ OAuth/cookie/session
   connection ਲਈ `subscription`), ਤਾਂ ਖਾਤਾ ਠੀਕ ਕਰਨ ਤੋਂ ਬਾਅਦ ਇਸਨੂੰ ਮੁੜ
   ਚਾਲੂ ਕਰੋ।

ਕੋਈ ਵੱਖਰਾ "clear ban flag" ਬਟਨ ਨਹੀਂ ਹੈ — ਰਿਕਵਰੀ ਦਾ ਤਰੀਕਾ re-test, re-auth,
ਜਾਂ re-enable ਹੈ, ਜੋ
[RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) ਵਿੱਚ ਦਿੱਤੇ ਆਮ
terminal-state ਨਿਯਮ ਨਾਲ ਮੇਲ ਖਾਂਦਾ ਹੈ।

## Probe isolation (model test-all)

ਇੱਕ **probe-origin failure** (`runAsProbe` ਦੇ ਅੰਦਰ ਚਲਾਈਆਂ ਗਈਆਂ model test-all
/ health-check dispatches) ਕਦੇ ਵੀ connection ਨੂੰ pool ਤੋਂ ਨਹੀਂ ਹਟਾਉਂਦੀ
(#9817): ਇਸਨੂੰ **ਦਿੱਖ ਲਈ ਦਰਜ** ਕੀਤਾ ਜਾਂਦਾ ਹੈ (`last_error`,
`last_error_type`, `error_code`, `last_error_at`), ਪਰ ਇਹ routing ਵਿੱਚ ਹੋਣ ਵਾਲੀ
**ਹਰ** ਤਬਦੀਲੀ ਛੱਡ ਦਿੰਦੀ ਹੈ — cooldowns, terminal status (`banned` /
`deactivated` / `credits_exhausted`), per-model lockouts, provider circuit
breaker, 5-minute quota cache, OAuth token refresh ਅਤੇ auto-disable। ਕੇਵਲ ਅਸਲ
request-path failure ਹੀ deactivate ਕਰਦੀ ਹੈ। ਦਰਜ ਕੀਤੀ ਤਰੁੱਟੀ flagged ਖਾਤੇ ਨੂੰ
dashboard ਵਿੱਚ ਦਿਖਾਈ ਦਿੰਦੀ ਬਣਾਉਂਦੀ ਹੈ, ਜਦੋਂ ਕਿ ਉਹ traffic serve ਕਰਦਾ ਰਹਿੰਦਾ ਹੈ।

ਇੱਕੋ decision point `shouldIsolateProbeFailures()`
(`src/shared/utils/probeOrigin.ts`) ਹੈ, ਜਿਸ ਨਾਲ **ਹਰ** ਉਸ ਸਥਾਨ 'ਤੇ ਸਲਾਹ ਕੀਤੀ
ਜਾਂਦੀ ਹੈ ਜੋ probe-origin failure ਕਾਰਨ routing state ਨੂੰ ਬਦਲ ਸਕਦਾ ਹੈ:

- `markAccountUnavailable` (`auth.ts`) — ਕੇਵਲ ਦਰਜ ਕਰਨਾ (`lastError` raw text,
  `lastErrorType`, `errorCode`, `lastErrorAt`; ਜਾਣ-ਬੁੱਝ ਕੇ **ਕੋਈ**
  `backoffLevel` ਨਹੀਂ, ਕਿਉਂਕਿ ਇਹ selection-time auto-decay ਨੂੰ ਟ੍ਰਿਗਰ ਕਰਕੇ
  ਰਿਕਾਰਡ ਮਿਟਾ ਦੇਵੇਗਾ)
- `maybeAutoDisableBannedAccount` — ਕੋਈ auto-disable ਨਹੀਂ
- `chatCore` — FORBIDDEN, ACCOUNT_DEACTIVATED, QUOTA_EXHAUSTED (ਕੇਵਲ ਦਰਜ ਕਰਨਾ,
  ਕੋਈ terminal `credits_exhausted` ਨਹੀਂ), GEO_BLOCKED (ਕੋਈ 24h exclusion ਨਹੀਂ),
  MODEL_NOT_FOUND (ਕੋਈ `lockModel` ਨਹੀਂ), codex 429 account-rotation failover
  (ਕੋਈ `markCodexScopeRateLimited` ਨਹੀਂ, ਕੋਈ persisted `rate_limited_until`
  ਨਹੀਂ, ਕੋਈ session-affinity clear ਨਹੀਂ), `persistCodexQuotaState` (ਕੋਈ
  quota-state write ਨਹੀਂ, ਕੋਈ cache invalidation ਨਹੀਂ), `recordKeyHealthStatus`
  (key-health rotator ਨੂੰ ਛੇੜਿਆ ਨਹੀਂ ਜਾਂਦਾ)
- OAuth refresh — executor base ਵਿੱਚ proactive refresh
  (`base.ts` `execute()`, ਕੋਈ refresh-token rotation ਵਰਤੀ ਨਹੀਂ ਜਾਂਦੀ) ਅਤੇ
  `chatCore` ਵਿੱਚ reactive 401/403 path (ਕੋਈ `expired` deactivation ਨਹੀਂ), ਦੋਵੇਂ
- `chat.ts` — provider circuit breaker ਅਤੇ 5-minute quota cache
  (`markAccountExhaustedFrom429`) ਕਦੇ ਵੀ degrade ਨਹੀਂ ਹੁੰਦੇ

ਦਰਜ ਕੀਤੀ ਤਰੁੱਟੀ flagged ਖਾਤੇ ਨੂੰ dashboard ਵਿੱਚ ਦਿਖਾਈ ਦਿੰਦੀ ਬਣਾਉਂਦੀ ਹੈ,
ਜਦੋਂ ਕਿ ਉਹ traffic serve ਕਰਦਾ ਰਹਿੰਦਾ ਹੈ। ਧਿਆਨ ਦਿਓ: probe record **raw**
(unsliced) error text ਸੰਭਾਲਦਾ ਹੈ, ਅਸਲ path ਦੀ `slice(0,100)` truncation ਦੇ ਉਲਟ।

ਉਹ operators ਜੋ test-all ਨੂੰ maintenance tool ਵਜੋਂ ਵਰਤਦੇ ਹਨ, ਹੇਠਾਂ ਦਿੱਤਿਆਂ
ਵਿੱਚੋਂ ਕਿਸੇ ਇੱਕ ਰਾਹੀਂ ਪੁਰਾਣਾ ਵਿਹਾਰ (probe ਨੂੰ ਅਸਲ generation ਮੰਨਣਾ) ਬਹਾਲ ਕਰ
ਸਕਦੇ ਹਨ:

- `probeCanDisable` setting (`POST /api/settings` ਨਾਲ
  `{"probeCanDisable": true}`, ਜਾਂ ਸਿੱਧਾ `key_value` DB edit), ਜਾਂ
- feature flag **`PROBE_CAN_DISABLE=true`** (env ਜਾਂ DB override; setting ਉੱਤੇ
  ਤਰਜੀਹ ਲੈਂਦਾ ਹੈ)।

Fail-safe: ਜੇ flag ਜਾਂ settings lookup exception ਸੁੱਟੇ, isolation ਚਾਲੂ ਰਹਿੰਦੀ ਹੈ।
