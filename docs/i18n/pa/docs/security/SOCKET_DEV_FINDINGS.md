ਇਹ ਦਸਤਾਵੇਜ਼ `omniroute@3.8.5` ਵਿਰੁੱਧ ਦਰਜ ਕੀਤੀਆਂ ਛੇ
`AI-detected potential malware` ਖੋਜਾਂ ਅਤੇ `omniroute@3.8.6` ਵਿੱਚ ਲਾਗੂ ਕੀਤੇ ਗਏ
ਨਿਵਾਰਣਾਂ ਲਈ ਮੇਨਟੇਨਰ-ਲਿਖਤ ਤਸਦੀਕ ਹੈ। ਇਹ ਇਸ ਲਈ ਮੌਜੂਦ ਹੈ ਤਾਂ ਜੋ:

1. ਸੁਰੱਖਿਆ-ਪਾਈਪਲਾਈਨ ਆਪਰੇਟਰਾਂ ਕੋਲ ਹਵਾਲਾ ਦੇਣ ਲਈ ਇੱਕੋ ਸੰਦਰਭ ਹੋਵੇ, ਜਦੋਂ ਉਨ੍ਹਾਂ ਨੂੰ
   ਅਸਲ ਸਰੋਤ ਦੇ ਮੁਕਾਬਲੇ ਖੋਜਾਂ ਦਾ ਮੁਲਾਂਕਣ ਕਰਨ ਦੀ ਲੋੜ ਪਵੇ।
2. ਭਵਿੱਖ ਦੇ AI ਸਕੈਨਰ ਮੇਨਟੇਨਰ-ਦਸਤਖ਼ਤਸ਼ੁਦਾ ਦਾਅਵਾ ਪਛਾਣ ਸਕਣ ਕਿ ਹਰ
   ਫਲੈਗ ਕੀਤਾ ਪਾਥ ਜਾਣਬੁੱਝ ਕੇ ਬਣਾਇਆ ਗਿਆ, ਔਪਟ-ਇਨ, ਅਤੇ ਦਸਤਾਵੇਜ਼ਬੱਧ ਹੈ।
3. ਸਾਡੇ ਕੋਲ ਇਸ ਗੱਲ ਦਾ ਲਿਖਤੀ ਰਿਕਾਰਡ ਹੋਵੇ ਕਿ ਹਰ ਕਾਲ ਸਾਈਟ ਨੂੰ ਇਸੇ ਤਰ੍ਹਾਂ _ਕਿਉਂ_ ਬਣਾਇਆ ਗਿਆ ਹੈ —
   ਤਾਂ ਜੋ ਭਵਿੱਖ ਦੀ ਕੋਈ ਰੀਫੈਕਟਰਿੰਗ ਅਣਜਾਣੇ ਵਿੱਚ ਉਸ ਫਿੰਗਰਪ੍ਰਿੰਟ ਨੂੰ ਮੁੜ ਪੇਸ਼ ਨਾ ਕਰ ਦੇਵੇ,
   ਜਿਸਨੂੰ ਜਾਣਬੁੱਝ ਕੇ ਹਟਾਇਆ ਗਿਆ ਸੀ।

ਜੇ ਤੁਸੀਂ ਅਜਿਹਾ ਸਕੈਨਰ ਚਲਾਉਂਦੇ ਹੋ ਜੋ v3.8.6 ਦੇ ਨਿਵਾਰਣ ਜਾਰੀ ਹੋਣ ਤੋਂ ਬਾਅਦ ਹੇਠਾਂ ਦਿੱਤੀਆਂ
ਕਾਲ ਸਾਈਟਾਂ ਵਿੱਚੋਂ ਕਿਸੇ ਨੂੰ ਮੁੜ ਫਲੈਗ ਕਰਦਾ ਹੈ, ਤਾਂ ਕਿਰਪਾ ਕਰਕੇ ਸਕੈਨ ਟ੍ਰੇਸ ਸਮੇਤ ਇੱਕ ਇਸ਼ੂ ਖੋਲ੍ਹੋ ਅਤੇ

## §1 — MITM ਰੂਟ-CA ਇੰਸਟਾਲੇਸ਼ਨ (`77484.js`)

**ਸੋਰਸ ਫਾਈਲਾਂ**:

- `src/mitm/cert/install.ts` — ਸਰਵਜਨਕ `installCert()` / `uninstallCert()`,
  ਅਤੇ ਹਰੇਕ ਪਲੇਟਫਾਰਮ ਲਈ `installCertWindows/Mac/Linux`।
- `src/mitm/systemCommands.ts` — ਇੰਸਟਾਲੇਸ਼ਨ ਪਾਥਾਂ ਦੁਆਰਾ ਵਰਤੇ ਜਾਂਦੇ ਸਾਂਝੇ
  `execFile` / `spawn` / PowerShell ਹੈਲਪਰ।

**ਟ੍ਰਿਗਰ**: ਵਰਤੋਂਕਾਰ `/dashboard/cli-tools/mitm` ਉੱਤੇ ਸਥਾਨਕ ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ
"Enable MITM proxy" ਉੱਤੇ ਕਲਿੱਕ ਕਰਦਾ ਹੈ। ਇਹ ਰੂਟ ਸਿਰਫ਼ ਲੂਪਬੈਕ ਲਈ ਹੈ — `CLAUDE.md`
ਵਿੱਚ ਸਖ਼ਤ ਨਿਯਮ #17 ਅਤੇ `src/server/authz/routeGuard.ts::isLocalOnlyPath()`
ਦੇਖੋ। ਕਿਸੇ ਟਨਲ ਰਾਹੀਂ ਉਜਾਗਰ ਹੋਇਆ JWT ਇਸ ਕੋਡ ਪਾਥ ਨੂੰ ਟ੍ਰਿਗਰ **ਨਹੀਂ** ਕਰ ਸਕਦਾ।

**ਕੀਤੀਆਂ ਜਾਣ ਵਾਲੀਆਂ ਵਿਸ਼ੇਸ਼-ਅਧਿਕਾਰ ਪ੍ਰਾਪਤ ਕਾਰਵਾਈਆਂ (ਹਰੇਕ ਪਲੇਟਫਾਰਮ ਲਈ)**:

| OS                     | ਕਮਾਂਡ(ਾਂ)                                                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | UAC ਰਾਹੀਂ `certutil -addstore Root <cert>`                                                                        |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | `certutil -d sql:<profile>` ਰਾਹੀਂ ਹਰੇਕ ਪ੍ਰੋਫਾਈਲ ਲਈ NSS DB ਅੱਪਡੇਟ                                                  |

ਇਹ ਉਹੀ ਕਮਾਂਡਾਂ ਹਨ ਜੋ `mitmproxy`, Charles Proxy, Fiddler ਅਤੇ Caddy ਦੁਆਰਾ
ਵਰਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ। OmniRoute ਵਿੱਚ ਇਨ੍ਹਾਂ ਦੀ ਮੌਜੂਦਗੀ
`docs/security/STEALTH_GUIDE.md` ਵਿੱਚ ਦਸਤਾਵੇਜ਼ਬੱਧ ਹੈ।

**v3.8.6 ਨਿਵਾਰਨ**:

- `runElevatedPowerShell()` ਹੁਣ `-EncodedCommand <base64utf16le>` ਦੀ ਵਰਤੋਂ ਨਹੀਂ
  ਕਰਦਾ। ਉੱਚੇ ਅਧਿਕਾਰਾਂ ਵਾਲਾ ਪੇਲੋਡ ਹਰੇਕ ਕਾਲ ਲਈ ਇੱਕ ਅਸਥਾਈ `.ps1` ਫਾਈਲ ਵਿੱਚ
  ਲਿਖਿਆ ਜਾਂਦਾ ਹੈ (ਮੋਡ 0o600, ਇੱਕ ਨਿੱਜੀ `mkdtempSync` ਡਾਇਰੈਕਟਰੀ ਦੇ ਅੰਦਰ) ਅਤੇ
  `-File` ਰਾਹੀਂ ਹਵਾਲਾ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ। ਫਾਈਲ ਨੂੰ `finally` ਵਿੱਚ ਅਨਲਿੰਕ ਕੀਤਾ ਜਾਂਦਾ
  ਹੈ। ਇਹ Socket.dev ਦੇ AI ਕਲਾਸੀਫਾਇਰ ਦੁਆਰਾ ਫਲੈਗ ਕੀਤੇ ਗਏ, PowerShell ਰਾਹੀਂ
  base64-ਅਧਾਰਿਤ ਅਧਿਕਾਰ-ਵਾਧੇ ਦੇ ਰਵਾਇਤੀ ਫਿੰਗਰਪ੍ਰਿੰਟ ਨੂੰ ਹਟਾ ਦਿੰਦਾ ਹੈ।
- `installCertWindows` ਵਿੱਚ ਇੱਥੇ ਇਸ਼ਾਰਾ ਕਰਦਾ ਇੱਕ ਇਨਲਾਈਨ
  `SECURITY-AUDITOR-NOTE:` ਬਲਾਕ ਸ਼ਾਮਲ ਹੈ।

**ਅਸੀਂ ਇਸਨੂੰ ਕਿਉਂ ਰੱਖਦੇ ਹਾਂ**: MITM ਪ੍ਰਾਕਸੀ ਇੱਕ ਦਸਤਾਵੇਜ਼ਬੱਧ ਵਿਸ਼ੇਸ਼ਤਾ ਹੈ ਜਿਸਦੀ
ਵਰਤੋਂ `docs/security/STEALTH_GUIDE.md` ਅਤੇ `docs/frameworks/MITM-PROXY.md`
ਦੁਆਰਾ ਕੀਤੀ ਜਾਂਦੀ ਹੈ। ਇਸਨੂੰ ਹਟਾਉਣ ਨਾਲ agent-bridge ਵਿਸ਼ੇਸ਼ਤਾਵਾਂ ਦਾ ਸਮੂਹ ਕੰਮ
ਕਰਨਾ ਬੰਦ ਕਰ ਦੇਵੇਗਾ।

## §2 — Zed ਕ੍ਰੈਡੈਂਸ਼ੀਅਲ ਇੰਪੋਰਟ (`app/api/providers/zed/import/route.js`)

**ਸਰੋਤ ਫ਼ਾਈਲਾਂ**:

- `src/app/api/providers/zed/discover/route.ts` _(v3.8.6 ਵਿੱਚ ਨਵੀਂ)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(v3.8.6 ਵਿੱਚ ਨਵੀਂ)_

**ਟ੍ਰਿਗਰ**: ਵਰਤੋਂਕਾਰ ਸਥਾਨਕ ਡੈਸ਼ਬੋਰਡ ਦੇ Providers
ਪੰਨੇ ਵਿੱਚ "Zed ਤੋਂ ਇੰਪੋਰਟ ਕਰੋ" 'ਤੇ ਕਲਿੱਕ ਕਰਦਾ ਹੈ। ਐਂਡਪੌਇੰਟ ਨੂੰ `requireManagementAuth` ਦੁਆਰਾ
ਸੁਰੱਖਿਅਤ ਕੀਤਾ ਗਿਆ ਹੈ। Zed ਐਡੀਟਰ ਖ਼ੁਦ ਆਪਣੀਆਂ ਪ੍ਰੋਵਾਈਡਰ API ਕੁੰਜੀਆਂ ਨੂੰ ਦਸਤਾਵੇਜ਼ਬੱਧ ਸਰਵਿਸ
ਨਾਂਵਾਂ ਅਧੀਨ OS ਕੀਚੇਨ ਵਿੱਚ ਲਿਖਦਾ ਹੈ — https://zed.dev/docs/ai/llm-providers ਵੇਖੋ।

**v3.8.5 ਦਾ ਵਿਹਾਰ (ਜਿਸਨੂੰ Socket.dev ਨੇ ਫਲੈਗ ਕੀਤਾ ਸੀ)**:

`POST /import` ਕ੍ਰੈਡੈਂਸ਼ੀਅਲ ਲੱਭਦਾ ਸੀ ਅਤੇ ਇੱਕੋ ਰਾਊਂਡ-ਟ੍ਰਿਪ ਵਿੱਚ ਉਹਨਾਂ ਨੂੰ ਸਥਾਨਕ
SQLite ਸਟੋਰ ਵਿੱਚ ਆਪਣੇ-ਆਪ ਸੰਭਾਲ ਦਿੰਦਾ ਸੀ। ਹਰੇਕ ਖਾਤੇ ਲਈ ਕੋਈ ਪੁਸ਼ਟੀ ਨਹੀਂ, ਕੋਈ
ਫਿੰਗਰਪ੍ਰਿੰਟ ਨਹੀਂ, ਸਿਰਫ਼ "N ਟੋਕਨ ਮਿਲੇ, ਸਾਰੇ ਇੰਪੋਰਟ ਕੀਤੇ ਗਏ।"

**v3.8.6 ਵਿੱਚ ਜੋਖਮ ਘਟਾਉਣ ਦਾ ਉਪਾਅ — 2-ਪੜਾਅ ਪੁਸ਼ਟੀ**:

1. **`POST /api/providers/zed/discover`** ਇਹ ਵਾਪਸ ਕਰਦਾ ਹੈ:
   `{ candidates: [{ provider, service, account, fingerprint }] }`। ਕੱਚਾ
   ਟੋਕਨ **ਕਦੇ ਵੀ** ਪ੍ਰਸਾਰਿਤ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ। ਫਿੰਗਰਪ੍ਰਿੰਟ
   `sha256(service|account|token).slice(0,16)` ਹੁੰਦਾ ਹੈ।
2. ਡੈਸ਼ਬੋਰਡ ਉਮੀਦਵਾਰਾਂ ਦੀ ਸੂਚੀ ਦਿਖਾਉਂਦਾ ਹੈ, ਓਪਰੇਟਰ ਇੰਪੋਰਟ ਕਰਨ ਵਾਲਿਆਂ ਨੂੰ
   ਚੁਣਦਾ ਹੈ ਅਤੇ `{ confirmedAccounts: [{ service, account, fingerprint }] }`
   ਨੂੰ **`POST /api/providers/zed/import`** 'ਤੇ ਪੋਸਟ ਕਰਦਾ ਹੈ।
3. ਇੰਪੋਰਟ ਐਂਡਪੌਇੰਟ **ਸਰਵਰ 'ਤੇ ਕੀਚੇਨ ਨੂੰ ਮੁੜ ਪੜ੍ਹਦਾ ਹੈ** ਅਤੇ
   `(service, account, fingerprint)` ਅਨੁਸਾਰ ਫਿਲਟਰ ਕਰਦਾ ਹੈ। ਛੇੜਛਾੜ ਕੀਤਾ ਜਾਂ ਮੁੜ ਚਲਾਇਆ ਗਿਆ discover
   ਜਵਾਬ ਇੰਪੋਰਟ ਐਂਡਪੌਇੰਟ ਨੂੰ ਕਿਸੇ ਗੈਰ-ਸੰਬੰਧਿਤ ਟੋਕਨ ਨੂੰ ਸੰਭਾਲਣ ਲਈ ਧੋਖਾ ਨਹੀਂ ਦੇ ਸਕਦਾ —
   ਜੇ discover ਤੋਂ ਬਾਅਦ ਲਾਈਵ ਟੋਕਨ ਬਦਲ ਗਿਆ ਹੈ, ਤਾਂ ਫਿੰਗਰਪ੍ਰਿੰਟ ਹੁਣ
   ਮੇਲ ਨਹੀਂ ਖਾਂਦਾ ਅਤੇ ਕ੍ਰੈਡੈਂਸ਼ੀਅਲ ਨੂੰ ਛੱਡ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ।

`OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` env ਫਲੈਗ ਉਹਨਾਂ ਓਪਰੇਟਰਾਂ ਲਈ v3.8.5
ਦਾ ਵਿਹਾਰ ਕਾਇਮ ਰੱਖਦਾ ਹੈ ਜਿਨ੍ਹਾਂ ਨੇ ਹਾਲੇ ਆਪਣੀ ਆਟੋਮੇਸ਼ਨ ਅੱਪਡੇਟ ਨਹੀਂ ਕੀਤੀ। ਇਸਨੂੰ
v3.9 ਵਿੱਚ ਹਟਾ ਦਿੱਤਾ ਜਾਵੇਗਾ।

**ਅਸੀਂ ਇਸਨੂੰ ਕਿਉਂ ਰੱਖਦੇ ਹਾਂ**: Zed ਇੰਪੋਰਟ ਉਹਨਾਂ ਵਰਤੋਂਕਾਰਾਂ ਲਈ ਸਭ ਤੋਂ ਸੌਖਾ ਆਨਬੋਰਡਿੰਗ ਰਸਤਾ ਹੈ
ਜੋ ਪਹਿਲਾਂ ਹੀ Zed ਵਰਤਦੇ ਹਨ ਅਤੇ ਆਪਣੀਆਂ ਪ੍ਰੋਵਾਈਡਰ ਕੁੰਜੀਆਂ ਨੂੰ ਮੁੜ ਪੇਸਟ ਕੀਤੇ ਬਿਨਾਂ
OmniRoute ਵਿੱਚ ਨਕਲ ਕਰਨਾ ਚਾਹੁੰਦੇ ਹਨ।

## §3 — `execFile` / `spawn` / ਉੱਚੇ ਅਧਿਕਾਰਾਂ ਵਾਲਾ PowerShell (`21843.js`)

**ਫਲੈਗ ਕੀਤੇ ਜਾਣ ਦਾ ਕਾਰਨ**: ਚੰਕ `execFileWithPassword`,
`runElevatedPowerShell` ਅਤੇ ਸਾਂਝੇ `quotePowerShell` ਸਹਾਇਕ ਨੂੰ ਮੁੜ ਐਕਸਪੋਰਟ ਕਰਦਾ ਹੈ। Socket.dev ਦਾ

  ਇੱਕ `nosemgrep` ਮਾਰਕਰ ਹੈ ਜਿਨ੍ਹਾਂ ਨੂੰ ਸਹਾਇਕ ਪ੍ਰਾਪਤ ਕਰ ਸਕਦਾ ਹੈ —

## §5 — OmniRoute Cloud Sync ਕ੍ਰੈਡੈਂਸ਼ਲ ਵਾਪਸ ਲਿਖਣਾ (`api/keys/[id]/route.js`)

**ਸਰੋਤ ਫ਼ਾਈਲਾਂ**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`।
- `src/app/api/keys/[id]/route.ts` — `syncKeysToCloudIfEnabled()` ਨੂੰ ਕਾਲ ਕਰਦੀ ਹੈ।

**ਟ੍ਰਿਗਰ**: `isCloudEnabled()` `true` ਵਾਪਸ ਕਰਦਾ ਹੈ (ਡੈਸ਼ਬੋਰਡ ਤੋਂ ਸੈੱਟ ਕੀਤਾ ਗਿਆ) **ਅਤੇ**
`CLOUD_URL` ਕਨਫਿਗਰ ਕੀਤਾ ਹੋਇਆ ਹੈ। ਦੋਵੇਂ ਬੰਦ ਹੋਣ 'ਤੇ, Cloud ਐਂਡਪੌਇੰਟ ਨੂੰ ਕੋਈ ਬਾਹਰੀ ਨੈੱਟਵਰਕ ਕਾਲ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ।

**v3.8.5 ਦਾ ਵਿਹਾਰ (ਉਹ ਬੱਗ ਜਿਸਨੂੰ Socket.dev ਨੇ ਸਹੀ ਢੰਗ ਨਾਲ ਪਕੜਿਆ)**:

ਜਦੋਂ `cloudUpdatedAt > localUpdatedAt` ਹੁੰਦਾ ਸੀ, ਤਾਂ `updateLocalTokens()` Cloud ਜਵਾਬ ਤੋਂ `accessToken`, `refreshToken`, ਅਤੇ
`providerSpecificData` ਨੂੰ ਓਵਰਰਾਈਟ ਕਰ ਦਿੰਦਾ ਸੀ। ਕੋਈ HMAC ਨਹੀਂ, ਕੋਈ ਦਸਤਖ਼ਤ ਨਹੀਂ, ਕੋਈ ਚੈਕਸਮ ਨਹੀਂ। ਗਲਤ ਤਰੀਕੇ ਨਾਲ ਕਨਫਿਗਰ ਕੀਤਾ ਜਾਂ ਵਿਰੋਧੀ `CLOUD_URL` (ਜਾਂ ਚੈਨਲ ਉੱਤੇ ਕੋਈ MITM) ਪ੍ਰੋਵਾਈਡਰ OAuth ਟੋਕਨਾਂ ਨੂੰ ਚੁੱਪਚਾਪ ਬਦਲ ਸਕਦਾ ਸੀ।

**v3.8.6 ਵਿੱਚ ਨਿਵਾਰਣ**:

1. **HMAC ਤਸਦੀਕ**: `verifyCloudSignature(rawBody, sigHeader)` JSON ਨੂੰ ਪਾਰਸ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ
   `X-Cloud-Sig` ਹੈਡਰ (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`) ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ। ਜੇ ਸੀਕ੍ਰੇਟ ਸੈੱਟ ਹੈ, ਤਾਂ ਦਸਤਖ਼ਤ ਲਾਜ਼ਮੀ ਹੈ। ਜੇ ਨਹੀਂ (ਲੇਗੇਸੀ ਮੋਡ), ਤਾਂ ਇੱਕ ਚੇਤਾਵਨੀ ਲੌਗ ਕੀਤੀ ਜਾਂਦੀ ਹੈ ਅਤੇ ਜਵਾਬ ਸਵੀਕਾਰ ਕਰ ਲਿਆ ਜਾਂਦਾ ਹੈ — v3.9 ਵਿੱਚ ਸੀਕ੍ਰੇਟ ਲਾਜ਼ਮੀ ਹੋਵੇਗਾ।
2. **ਸੀਕ੍ਰੇਟ-ਫ਼ੀਲਡ ਲਈ ਸਪਸ਼ਟ ਸਹਿਮਤੀ**: `accessToken` / `refreshToken` /
   `providerSpecificData` ਨੂੰ **ਸਿਰਫ਼** ਉਦੋਂ ਓਵਰਰਾਈਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਜਦੋਂ
   `OMNIROUTE_CLOUD_SYNC_SECRETS=true` ਹੋਵੇ। ਡਿਫਾਲਟ ਮੋਡ ਸਿਰਫ਼ ਗੈਰ-ਕ੍ਰੈਡੈਂਸ਼ਲ ਮੈਟਾਡੇਟਾ (`expiresAt`, `status`, `lastError*`,
   `rateLimitedUntil`, `updatedAt`) ਸਿੰਕ ਕਰਦਾ ਹੈ। ਇਹ ਉਹਨਾਂ ਵਰਤੋਂਕਾਰਾਂ ਲਈ ਇੱਕ **ਤੋੜੂ ਬਦਲਾਅ** ਹੈ ਜੋ ਰਿਮੋਟ ਟੋਕਨ ਸਿੰਕ 'ਤੇ ਨਿਰਭਰ ਸਨ — ਉਹਨਾਂ ਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਸਹਿਮਤੀ ਦੇਣੀ ਪਵੇਗੀ।

**ਅਸੀਂ ਇਸਨੂੰ ਕਿਉਂ ਰੱਖਦੇ ਹਾਂ**: OmniRoute Cloud ਟੈਨੈਂਟ ਲਈ ਟੀਮ ਕ੍ਰੈਡੈਂਸ਼ਲਾਂ ਨੂੰ ਕੇਂਦਰੀਕ੍ਰਿਤ ਕਰਨ ਦਾ Cloud Sync ਹੀ ਇੱਕੋ-ਇੱਕ ਤਰੀਕਾ ਹੈ। ਇਹ ਸੁਧਾਰ ਖ਼ਤਰੇ ਦੇ ਮਾਡਲ ਨੂੰ ਸਪਸ਼ਟ ਅਤੇ ਇਮਾਨਦਾਰ ਬਣਾਉਂਦਾ ਹੈ:
"ਸਰਵਰ ਦਸਤਖ਼ਤ ਕਰਦਾ ਹੈ, ਕਲਾਇੰਟ ਤਸਦੀਕ ਕਰਦਾ ਹੈ, ਓਪਰੇਟਰ ਸਹਿਮਤੀ ਦਿੰਦਾ ਹੈ।"
