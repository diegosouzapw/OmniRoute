v3.8.49 (ਗੁਣਵੱਤਾ/ਗਤੀ ਯੋਜਨਾ ਦੇ WS3.2/WS3.4) ਤੋਂ ਸਮੀਖਿਆ ਕੀਤੇ PRs ਨੂੰ
`release/vX.Y.Z` ਵਿੱਚ ਮਿਲਾਉਣ ਲਈ ਡਿਫੌਲਟ ਮਰਜ ਮਾਰਗ **Mergify merge queue** (`.mergify.yml`)
ਹੈ; ਹੇਠਾਂ ਦਸਤਾਵੇਜ਼ਬੱਧ **manual merge-train** FALLBACK ਹੈ — ਜਿਸਦੀ ਵਰਤੋਂ ਘਟਨਾਵਾਂ ਦੌਰਾਨ,
ਰਿਲੀਜ਼ ਫ੍ਰੀਜ਼ ਸਮੇਂ, ਜਾਂ ਜੇ Mergify Open Source ਯੋਜਨਾ ਕਦੇ ਬਦਲਦੀ ਹੈ, ਕੀਤੀ ਜਾਂਦੀ ਹੈ।

## ਡਿਫੌਲਟ ਮਾਰਗ: Mergify ਕਤਾਰ

1. PR ਦੀ ਕੈਂਪੇਨਾਂ ਦੁਆਰਾ ਸਮੀਖਿਆ ਹੋ ਚੁੱਕੀ ਹੈ/ਉਸਨੂੰ ਹਰੀ ਝੰਡੀ ਮਿਲ ਚੁੱਕੀ ਹੈ ਅਤੇ ਮਾਲਕ ਦੇ ਪ੍ਰੀ-ਮਰਜ ⭐
   ਗੇਟ ਦੁਆਰਾ ਮਨਜ਼ੂਰ ਕੀਤਾ ਗਿਆ ਹੈ (ਰਿਪੋਰਟ + ਹਰੇਕ ਆਈਟਮ ਲਈ ਫ਼ੈਸਲਾ — `/merge-prs` ਕਦਮ 0.75 ਵੇਖੋ)।
2. ਮਾਲਕ (ਜਾਂ ਮਾਲਕ ਦੇ ਫ਼ੈਸਲੇ ਅਨੁਸਾਰ ਕੰਮ ਕਰ ਰਿਹਾ ਸੈਸ਼ਨ) **`queue`**
   ਲੇਬਲ ਲਾਗੂ ਕਰਦਾ ਹੈ। ਇਹ ਲੇਬਲ ਹੀ ਮਰਜ ਮਨਜ਼ੂਰੀ ਹੈ; Mergify ਸਿਰਫ਼ ਇਸਨੂੰ ਲਾਗੂ ਕਰਦਾ ਹੈ।
3. Mergify ਕਤਾਰਬੱਧ ਕੀਤੇ ਵੱਧ ਤੋਂ ਵੱਧ 10 PRs ਦਾ ਬੈਚ ਬਣਾਉਂਦਾ ਹੈ, ਬੈਚ ਨੂੰ fast-gates ਦੇ ਮੁਕਾਬਲੇ ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ,
   ਅਤੇ ਮਰਜ (squash) ਕਰਦਾ ਹੈ। ਇੱਕ ਲਾਲ ਬੈਚ **ਆਪਣੇ-ਆਪ ਦੋ ਹਿੱਸਿਆਂ ਵਿੱਚ ਵੰਡਿਆ ਜਾਂਦਾ ਹੈ** — ਸਮੱਸਿਆ ਪੈਦਾ ਕਰਨ ਵਾਲੇ PR
   ਨੂੰ ਲਗਭਗ log2(N) ਮੁੜ-ਪ੍ਰਮਾਣੀਕਰਨਾਂ ਵਿੱਚ ਅਲੱਗ ਕਰਕੇ ਕਤਾਰ ਵਿੱਚੋਂ ਹਟਾ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ; ਬਾਕੀ ਅੱਗੇ ਵਧਦੇ ਹਨ।
4. ਮਰਜ ਤੋਂ ਬਾਅਦ, ਨਿਰੰਤਰ release-green ਵਰਕਫ਼ਲੋ push ਉੱਤੇ ਨਵੇਂ tip ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ
   ਅਤੇ ਜੇ ਸੰਯੋਜਨ ਵਿੱਚ ਰਿਗ੍ਰੈਸ਼ਨ ਹੋਵੇ ਤਾਂ attribution issue ਖੋਲ੍ਹਦਾ ਹੈ (ਕਦੇ ਵੀ ਆਪਣੇ-ਆਪ revert ਨਹੀਂ ਕਰਦਾ)।

ਸੁਰੱਖਿਆ ਨਿਯਮ (`CLAUDE.md` ਦੇ Hard Rules #21/#22 ਦੇ ਅਨੁਰੂਪ):

- **ਰਿਲੀਜ਼ ਫ੍ਰੀਜ਼ ਖੁੱਲ੍ਹਾ ਹੈ** → ਫ੍ਰੀਜ਼ ਕੀਤੀ ਬ੍ਰਾਂਚ ਨੂੰ ਨਿਸ਼ਾਨਾ ਬਣਾਉਣ ਵਾਲੇ PRs ਨੂੰ ਲੇਬਲ ਨਾ ਕਰੋ; ਪਹਿਲਾਂ ਉਹਨਾਂ ਨੂੰ
  ਸਰਗਰਮ `release/vX+1` ਵੱਲ ਮੁੜ-ਨਿਸ਼ਾਨਾਬੱਧ ਕਰੋ।
- **ਕਿਸੇ ਹੋਰ ਸੈਸ਼ਨ ਦਾ ਪ੍ਰਗਤੀ ਅਧੀਨ PR** → ਇਸਨੂੰ ਕਦੇ ਵੀ ਲੇਬਲ ਨਾ ਕਰੋ; ਸਿਰਫ਼ ਮਾਲਕ ਸੈਸ਼ਨ ਹੀ
  ਆਪਣੇ ਕੰਮ ਨੂੰ ਕਤਾਰਬੱਧ ਕਰਦਾ ਹੈ।
- ਕੇਵਲ ਟੈਸਟਾਂ ਵਾਲੇ diffs ਅਤੇ `hotfix`-ਲੇਬਲ ਵਾਲੇ PRs ਪਹਿਲਾਂ ਹੀ ਘਟਾਈ ਹੋਈ CI ਚਲਾਉਂਦੇ ਹਨ (ਵੇਖੋ
  `RELEASE_CHECKLIST.md` → Hotfix Fast-Lane); ਕਤਾਰ ਦੀਆਂ ਸ਼ਰਤਾਂ ਅਸਲ ਵਿੱਚ ਚੱਲੇ
  ਕਿਸੇ ਵੀ check ਸੈੱਟ ਨੂੰ ਸਵੀਕਾਰ ਕਰਦੀਆਂ ਹਨ (`#check-failure=0` + `#check-pending=0`)।

## ਫਾਲਬੈਕ: manual merge-train

ਇਸਦੀ ਵਰਤੋਂ ਉਦੋਂ ਕੀਤੀ ਜਾਂਦੀ ਹੈ ਜਦੋਂ ਕਤਾਰ ਉਪਲਬਧ ਨਾ ਹੋਵੇ। ਇਹ ਉਸ ਅਭਿਆਸ ਨੂੰ ਵਿਧੀਬੱਧ ਕਰਦਾ ਹੈ ਜਿਸਨੇ v3.8.47 ਚੱਕਰ ਦੌਰਾਨ
ਇੱਕ ਦਿਨ ਵਿੱਚ 33 PRs ਨਿਪਟਾਏ ਸਨ:

1. **ਬੈਚ ਇਕੱਠਾ ਕਰੋ** (ਲਗਭਗ 10–30 ਸਮੀਖਿਆ ਕੀਤੇ+ਮਨਜ਼ੂਰਸ਼ੁਦਾ PRs)। `linked:` ਟਕਰਾਵਾਂ ਦੀ ਜਾਂਚ ਕਰੋ
   (ਇੱਕੋ `tap.testFiles`, ਇੱਕੋ CHANGELOG ਹਿੱਸੇ) ਅਤੇ ਉਹਨਾਂ ਨੂੰ ਕ੍ਰਮਵਾਰ ਚਲਾਓ।
2. **ਸਿਰਫ਼ ਇੱਕ ਵਾਰ ਪ੍ਰਮਾਣਿਤ ਕਰੋ**: release tip ਤੋਂ ਬਣੇ ਇੱਕ ਅਲੱਗ worktree ਵਿੱਚ, ਸਾਰੇ ਬੈਚ
   heads ਨੂੰ ਸਥਾਨਕ ਤੌਰ 'ਤੇ ਮਰਜ ਕਰੋ, ਫਿਰ ਰਿਲੀਜ਼-ਬਰਾਬਰ suite ਚਲਾਓ
   (`npm run check:release-green`, ਰਿਲੀਜ਼ ਤੋਂ ਪਹਿਲਾਂ `--with-build` ਜੋੜੋ)।
   `scripts/release/merge-train.sh <base> <PR#>…` ਕਦਮ 1–2 ਨੂੰ ਸਵੈਚਾਲਿਤ ਕਰਦਾ ਹੈ (ਟਕਰਾਉਂਦੇ
   PRs ਬਾਹਰ ਕੱਢੇ ਜਾਂਦੇ ਹਨ, train ਜਾਰੀ ਰਹਿੰਦੀ ਹੈ)। Full mode `npm run test:unit` ਚਲਾਉਂਦਾ ਹੈ —
   box-tuned runner (`--test-concurrency=20`), **ਨਾ ਕਿ** ਦੋ ਲੜੀਵਾਰ 4-core CI
   shards, ਜਿਨ੍ਹਾਂ ਨੇ 16-core box ਉੱਤੇ ਪ੍ਰਮੁੱਖ ਪੜਾਅ ਨੂੰ ਲਗਭਗ 25% ਵਰਤੋਂ 'ਤੇ ਚਲਾਇਆ ਸੀ (ਇਸਨੂੰ
   2026-07-18 ਨੂੰ ਠੀਕ ਕੀਤਾ ਗਿਆ)। `--fast` (ਦਿਨ ਦੇ ਅੰਦਰ mega-train drains, ਮਾਲਕ ਦੁਆਰਾ 2026-07-18 ਨੂੰ ਮਨਜ਼ੂਰ)
   ਹਰ static gate + vitest ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦਾ ਹੈ ਪਰ ਸਿਰਫ਼ boarded PRs ਦੁਆਰਾ ਬਦਲੀਆਂ ਗਈਆਂ
   node:test ਫ਼ਾਈਲਾਂ ਚਲਾਉਂਦਾ ਹੈ; FULL suite ਨੂੰ ਫਿਰ ਵੀ ਇਕੱਠੇ ਹੋਏ tip ਉੱਤੇ
   ਹਰ ਦਿਨ ਘੱਟੋ-ਘੱਟ ਇੱਕ ਵਾਰ ਚਲਾਉਣਾ ਲਾਜ਼ਮੀ ਹੈ (`--fast` ਤੋਂ ਬਿਨਾਂ ਇੱਕ train)।
3. **ਹਰਾ** → PRs ਨੂੰ ਕ੍ਰਮਵਾਰ ਮਰਜ ਕਰੋ (ਹਰੇਕ ਤੋਂ ਪਹਿਲਾਂ `state,headRefOid` ਦੀ ਮੁੜ ਜਾਂਚ ਕਰਦੇ ਹੋਏ —
   ਜਿਸ PR ਦਾ head ਬਦਲ ਗਿਆ ਹੋਵੇ, ਉਹ ਮੁੜ ਸਮੀਖਿਆ ਵਿੱਚ ਜਾਂਦਾ ਹੈ)। ਸਾਬਤ ਕਰੋ ਕਿ ਹਰੇਕ ਮਰਜ ਦਾ ਕੁੱਲ diff
   PR ਦਾ ਆਪਣਾ ਬਦਲਾਅ ਹੀ ਹੈ (ਕੋਈ auto-resolve revert ਨਹੀਂ: ਦਾਇਰੇ ਤੋਂ ਬਾਹਰ ਦੀਆਂ
   ਮਿਟਾਵਟਾਂ ਲਈ `git diff --stat` ਦਾ ਆਡਿਟ ਕਰੋ)।
4. **ਲਾਲ** → ਇੱਕ-ਇੱਕ ਕਰਕੇ ਮੁੜ-ਪ੍ਰਮਾਣਿਤ ਕਰਨ ਦੀ ਬਜਾਏ ਬੈਚ ਨੂੰ ਅੱਧਿਆਂ ਵਿੱਚ ਵੰਡੋ (ਹਰੇਕ ਅੱਧੇ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਕਰੋ);
   ਸਮੱਸਿਆ ਪੈਦਾ ਕਰਨ ਵਾਲੇ PR ਨੂੰ ਸਬੂਤ ਸਮੇਤ ਸਮੀਖਿਆ ਕਤਾਰ ਵਿੱਚ ਵਾਪਸ ਭੇਜੋ।
5. **ਕਦੇ ਵੀ ਨਾ ਕਰੋ**: ਫ੍ਰੀਜ਼ ਦੌਰਾਨ ਫ੍ਰੀਜ਼ ਕੀਤੀ ਬ੍ਰਾਂਚ ਵਿੱਚ ਮਰਜ ਕਰਨਾ; ਕਿਤੇ ਵੀ `git stash` ਕਰਨਾ;
   ਇਸ ਉਮੀਦ ਵਿੱਚ CI ਨੂੰ ਸਮੁੱਚੇ ਤੌਰ 'ਤੇ ਮੁੜ ਚਲਾਉਣਾ ਕਿ ਲਾਲ ਨਤੀਜਾ ਗਾਇਬ ਹੋ ਜਾਵੇਗਾ (ਨਿਯਮ: ਲਾਲ ਨਤੀਜਾ ਜਾਣਕਾਰੀ ਹੈ)।

## ਪੱਧਰੀਕਰਨ (ਕਿਉਂ ਕਤਾਰ ਸਿਰਫ਼ fast-gates ਨਾਲ ਸੁਰੱਖਿਅਤ ਹੈ)

- **ਹਰੇਕ PR ਲਈ** (quality.yml fast-gates): TIA-ਪ੍ਰਭਾਵਿਤ ਟੈਸਟ + ਪੂਰਾ unit 4-shard +
  vitest + lint bag + typecheck + docs/changelog ਅਖੰਡਤਾ।
- **ਹਰੇਕ batch/tip ਲਈ** (ਨਿਰੰਤਰ release-green): release branch ਵੱਲ ਹਰੇਕ push ਉੱਤੇ `--quick` HARD gates;
  ਪੂਰੇ `--with-build --full-ci` sweeps ਦਿਨ ਵਿੱਚ 3×।
- **ਹਰੇਕ ਰਿਲੀਜ਼ ਲਈ** (ਰਿਲੀਜ਼ PR ਉੱਤੇ ci.yml): E2E ×9 ਸਮੇਤ ਪੂਰਾ matrix,
  package-artifact + tarball boot-smoke, coverage/ratchets।

ਕਿਸੇ ਵੀ ਚੀਜ਼ ਨੂੰ ਪਹਿਲਾਂ ਨਾਲੋਂ ਘੱਟ ਪ੍ਰਮਾਣਿਤ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ — ਭਾਰੀ ਸਤਹ ਸਿਰਫ਼ ਹਰੇਕ PR ਦੀ ਬਜਾਏ ਹਰੇਕ batch/tip ਲਈ
ਚਲਦੀ ਹੈ, ਅਤੇ ਇਹੀ O(N) round-trips ਨੂੰ ਖ਼ਤਮ ਕਰਦਾ ਹੈ।
