v3.8.49 (ਗੁਣਵੱਤਾ/ਵੇਗ ਯੋਜਨਾ ਦੇ WS3.2/WS3.4) ਤੋਂ ਸਮੀਖਿਆ ਕੀਤੇ PRs ਨੂੰ
`release/vX.Y.Z` ਵਿੱਚ ਮਿਲਾਉਣ ਲਈ ਡਿਫਾਲਟ ਮਾਰਗ **Mergify merge queue** (`.mergify.yml`)
ਹੈ; ਹੇਠਾਂ ਦਸਤਾਵੇਜ਼ਬੱਧ **manual merge-train** FALLBACK ਹੈ — ਇਸਦੀ ਵਰਤੋਂ ਘਟਨਾਵਾਂ,
ਰਿਲੀਜ਼ ਫ੍ਰੀਜ਼ਾਂ ਦੌਰਾਨ, ਜਾਂ ਜੇ Mergify Open Source ਯੋਜਨਾ ਕਦੇ ਬਦਲਦੀ ਹੈ, ਕੀਤੀ ਜਾਂਦੀ ਹੈ।

## ਡਿਫੌਲਟ ਪਾਥ: Mergify ਕਤਾਰ

1. PR ਦੀ ਕੈਂਪੇਨਾਂ ਦੁਆਰਾ ਸਮੀਖਿਆ ਕੀਤੀ ਜਾਂਦੀ ਹੈ/ਇਸਨੂੰ ਹਰੀ ਝੰਡੀ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ ਅਤੇ ਮਾਲਕ ਦੇ ਪ੍ਰੀ-ਮਰਜ ⭐
   ਗੇਟ ਦੁਆਰਾ ਮਨਜ਼ੂਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (ਰਿਪੋਰਟ + ਪ੍ਰਤੀ-ਆਈਟਮ ਫ਼ੈਸਲਾ — `/merge-prs` ਕਦਮ 0.75 ਵੇਖੋ)।
2. ਮਾਲਕ (ਜਾਂ ਮਾਲਕ ਦੇ ਫ਼ੈਸਲੇ ਅਨੁਸਾਰ ਕੰਮ ਕਰ ਰਿਹਾ ਸੈਸ਼ਨ) **`queue`**
   ਲੇਬਲ ਲਾਗੂ ਕਰਦਾ ਹੈ। ਇਹ ਲੇਬਲ ਹੀ ਮਰਜ ਦੀ ਮਨਜ਼ੂਰੀ ਹੈ; Mergify ਸਿਰਫ਼ ਇਸਨੂੰ ਅਮਲ ਵਿੱਚ ਲਿਆਉਂਦਾ ਹੈ।
3. Mergify ਕਤਾਰਬੱਧ PRs ਨੂੰ ਫਾਸਟ-ਗੇਟਾਂ ਦੇ ਮੁਕਾਬਲੇ **ਲੜੀਵਾਰ** (ਇੱਕ ਸਮੇਂ ਇੱਕ) ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ
   ਅਤੇ ਮਰਜ (squash) ਕਰਦਾ ਹੈ। ਬੈਚਿੰਗ + ਸਵੈਚਲਿਤ ਬਾਈਸੈਕਸ਼ਨ ਇੱਕ ਭੁਗਤਾਨਯੋਗ Mergify ਟੀਅਰ ਹੈ
   (ਮੁਫ਼ਤ ਪਲਾਨ ਉੱਤੇ "Cannot use Merge Queue batch", #7220), ਇਸ ਲਈ `.mergify.yml` ਵਿੱਚ ਕੋਈ
   `batch_size` ਸੈੱਟ ਨਹੀਂ ਕੀਤਾ ਗਿਆ; ਬੈਚਿੰਗ ਹੇਠਾਂ ਦਿੱਤੀ ਮੈਨੂਅਲ ਮਰਜ-ਟ੍ਰੇਨ ਦਾ ਕੰਮ ਰਹਿੰਦੀ ਹੈ। ਉਹ PR ਜਿਸਦੀਆਂ
   ਜਾਂਚਾਂ `checks_timeout` (240 ਮਿੰਟ = `quality.yml` ਦੇ ਮਾਪੇ ਗਏ p95 ਦਾ 2×) ਤੋਂ ਬਾਅਦ ਵੀ ਲੰਬਿਤ ਹਨ,
   ਕਤਾਰ ਨੂੰ ਰੋਕਣ ਦੀ ਬਜਾਏ ਕਤਾਰ ਵਿੱਚੋਂ ਹਟਾ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ।
4. ਮਰਜ ਤੋਂ ਬਾਅਦ, ਨਿਰੰਤਰ ਰਿਲੀਜ਼-ਗ੍ਰੀਨ ਵਰਕਫ਼ਲੋ push ਉੱਤੇ ਨਵੇਂ tip ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ
   ਅਤੇ ਜੇ ਸੰਯੋਜਨ ਵਿੱਚ ਰਿਗ੍ਰੈਸ਼ਨ ਆਇਆ ਹੋਵੇ ਤਾਂ ਇੱਕ ਐਟ੍ਰਿਬਿਊਸ਼ਨ ਇਸ਼ੂ ਖੋਲ੍ਹਦਾ ਹੈ (ਕਦੇ ਵੀ ਆਪਣੇ ਆਪ ਰਿਵਰਟ ਨਹੀਂ ਕਰਦਾ)।

ਸੁਰੱਖਿਆ ਨਿਯਮ (`CLAUDE.md` ਦੇ ਸਖ਼ਤ ਨਿਯਮ #21/#22 ਦੇ ਅਨੁਰੂਪ):

- **ਰਿਲੀਜ਼ ਫ਼੍ਰੀਜ਼ ਲਾਗੂ ਹੈ** → ਫ਼੍ਰੀਜ਼ ਕੀਤੀ ਬ੍ਰਾਂਚ ਨੂੰ ਟਾਰਗੇਟ ਕਰਨ ਵਾਲੇ PRs ਨੂੰ ਲੇਬਲ ਨਾ ਕਰੋ; ਪਹਿਲਾਂ
  ਸਰਗਰਮ `release/vX+1` ਵੱਲ ਮੁੜ ਟਾਰਗੇਟ ਕਰੋ।
- **ਕਿਸੇ ਹੋਰ ਸੈਸ਼ਨ ਦਾ ਜਾਰੀ PR** → ਇਸਨੂੰ ਕਦੇ ਵੀ ਲੇਬਲ ਨਾ ਕਰੋ; ਸਿਰਫ਼ ਮਾਲਕ ਸੈਸ਼ਨ ਹੀ
  ਆਪਣੇ ਕੰਮ ਨੂੰ ਕਤਾਰਬੱਧ ਕਰਦਾ ਹੈ।
- ਸਿਰਫ਼ ਟੈਸਟਾਂ ਵਾਲੇ diffs ਅਤੇ `hotfix`-ਲੇਬਲ ਵਾਲੇ PRs ਪਹਿਲਾਂ ਹੀ ਘਟਾਈ ਹੋਈ CI ਚਲਾਉਂਦੇ ਹਨ (`RELEASE_CHECKLIST.md`
  → Hotfix Fast-Lane ਵੇਖੋ); ਕਤਾਰ ਦੀਆਂ ਸ਼ਰਤਾਂ ਅਸਲ ਵਿੱਚ ਚੱਲੇ ਕਿਸੇ ਵੀ
  ਜਾਂਚ ਸੈੱਟ ਨੂੰ ਸਵੀਕਾਰ ਕਰਦੀਆਂ ਹਨ (`#check-failure=0` + `#check-pending=0`)।

## ਫਾਲਬੈਕ: ਮੈਨੁਅਲ merge-train

ਜਦੋਂ ਕਤਾਰ ਉਪਲਬਧ ਨਾ ਹੋਵੇ ਤਾਂ ਇਸਦੀ ਵਰਤੋਂ ਕੀਤੀ ਜਾਂਦੀ ਹੈ। ਇਹ ਉਸ ਅਭਿਆਸ ਨੂੰ ਨਿਯਮਬੱਧ ਕਰਦਾ ਹੈ ਜਿਸ ਨੇ v3.8.47
ਚੱਕਰ ਦੌਰਾਨ ਇੱਕ ਦਿਨ ਵਿੱਚ 33 PRs ਨਿਪਟਾਏ ਸਨ:

1. **ਬੈਚ ਇਕੱਠਾ ਕਰੋ** (~10–30 ਸਮੀਖਿਆ ਕੀਤੇ+ਮਨਜ਼ੂਰਸ਼ੁਦਾ PRs)। `linked:` ਟਕਰਾਵਾਂ ਦੀ ਜਾਂਚ ਕਰੋ
   (ਇੱਕੋ `tap.testFiles`, ਇੱਕੋ CHANGELOG ਹਿੱਸੇ) ਅਤੇ ਉਹਨਾਂ ਨੂੰ ਲੜੀਵਾਰ ਕਰੋ।
2. **ਸਿਰਫ਼ ਇੱਕ ਵਾਰ ਪ੍ਰਮਾਣਿਤ ਕਰੋ**: ਰਿਲੀਜ਼ tip ਤੋਂ ਵੱਖਰੇ ਇੱਕ isolated worktree ਵਿੱਚ ਸਾਰੇ ਬੈਚ
   heads ਨੂੰ ਸਥਾਨਕ ਤੌਰ 'ਤੇ ਮਰਜ ਕਰੋ, ਫਿਰ ਰਿਲੀਜ਼-ਬਰਾਬਰ suite ਚਲਾਓ
   (`npm run check:release-green`, ਰਿਲੀਜ਼ ਤੋਂ ਪਹਿਲਾਂ `--with-build` ਜੋੜੋ)।
   `scripts/release/merge-train.sh <base> <PR#>…` ਕਦਮ 1–2 ਨੂੰ ਆਟੋਮੇਟ ਕਰਦੀ ਹੈ (ਟਕਰਾਉਣ ਵਾਲੇ
   PRs ਬਾਹਰ ਕੱਢੇ ਜਾਂਦੇ ਹਨ, ਟ੍ਰੇਨ ਜਾਰੀ ਰਹਿੰਦੀ ਹੈ)। Full ਮੋਡ `npm run test:unit` ਚਲਾਉਂਦਾ ਹੈ —
   ਬਾਕਸ ਲਈ ਟਿਊਨ ਕੀਤਾ runner (`--test-concurrency=20`), **ਨਾ ਕਿ** ਦੋ ਲੜੀਵਾਰ 4-core CI
   shards, ਜਿਨ੍ਹਾਂ ਨੇ 16-core ਬਾਕਸ 'ਤੇ ਮੁੱਖ ਪੜਾਅ ਨੂੰ ~25% 'ਤੇ ਚਲਾਇਆ ਸੀ (2026-07-18 ਨੂੰ
   ਠੀਕ ਕੀਤਾ ਗਿਆ)। `--fast` (ਦਿਨ ਦੇ ਅੰਦਰ mega-train ਨਿਪਟਾਰੇ, ਮਾਲਕ ਵੱਲੋਂ 2026-07-18 ਨੂੰ ਮਨਜ਼ੂਰਸ਼ੁਦਾ)
   ਹਰ static gate + vitest ਨੂੰ ਕਾਇਮ ਰੱਖਦਾ ਹੈ, ਪਰ ਸਿਰਫ਼ ਚੜ੍ਹਾਏ ਗਏ PRs ਦੁਆਰਾ ਬਦਲੀਆਂ
   node:test ਫਾਈਲਾਂ ਚਲਾਉਂਦਾ ਹੈ; ਇਕੱਠੇ ਹੋਏ tip 'ਤੇ FULL suite ਫਿਰ ਵੀ ਦਿਨ ਵਿੱਚ ਘੱਟੋ-ਘੱਟ
   ਇੱਕ ਵਾਰ ਚੱਲਣਾ ਲਾਜ਼ਮੀ ਹੈ (`--fast` ਤੋਂ ਬਿਨਾਂ ਇੱਕ ਟ੍ਰੇਨ)।
3. **ਗ੍ਰੀਨ** → PRs ਨੂੰ ਕ੍ਰਮਵਾਰ ਮਰਜ ਕਰੋ (ਹਰ ਇੱਕ ਤੋਂ ਪਹਿਲਾਂ `state,headRefOid` ਦੀ ਮੁੜ ਜਾਂਚ ਕਰਦੇ ਹੋਏ —
   ਜਿਸ PR ਦਾ head ਬਦਲ ਗਿਆ ਹੋਵੇ ਉਹ ਮੁੜ ਸਮੀਖਿਆ ਵਿੱਚ ਜਾਂਦਾ ਹੈ)। ਸਾਬਤ ਕਰੋ ਕਿ ਹਰੇਕ ਮਰਜ ਦਾ ਕੁੱਲ diff
   PR ਦੀ ਆਪਣੀ ਤਬਦੀਲੀ ਹੀ ਹੈ (ਕੋਈ auto-resolve reverts ਨਹੀਂ: ਦਾਇਰੇ ਤੋਂ ਬਾਹਰ ਮਿਟਾਵਾਂ ਲਈ
   `git diff --stat` ਦੀ ਆਡਿਟ ਕਰੋ)।
4. **ਰੈੱਡ** → ਇੱਕ-ਇੱਕ ਕਰਕੇ ਮੁੜ-ਪ੍ਰਮਾਣਿਤ ਕਰਨ ਦੀ ਬਜਾਏ ਬੈਚ ਨੂੰ ਅੱਧਿਆਂ ਵਿੱਚ ਵੰਡੋ
   (ਹਰ ਅੱਧੇ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਕਰੋ); ਸਬੂਤ ਸਮੇਤ ਸਮੱਸਿਆ ਵਾਲੇ PR ਨੂੰ ਮੁੜ ਸਮੀਖਿਆ ਕਤਾਰ ਵਿੱਚ ਭੇਜੋ।
5. **ਕਦੇ ਵੀ ਨਾ ਕਰੋ**: ਫ੍ਰੀਜ਼ ਦੌਰਾਨ ਫ੍ਰੀਜ਼ ਕੀਤੀ ਬ੍ਰਾਂਚ ਵਿੱਚ ਮਰਜ; ਕਿਤੇ ਵੀ `git stash`;
   ਇਸ ਉਮੀਦ ਨਾਲ CI ਨੂੰ ਪੂਰੀ ਤਰ੍ਹਾਂ ਮੁੜ ਚਲਾਉਣਾ ਕਿ ਰੈੱਡ ਗਾਇਬ ਹੋ ਜਾਵੇਗਾ (ਨਿਯਮ: ਰੈੱਡ ਇੱਕ ਜਾਣਕਾਰੀ ਹੈ)।

## ਪੱਧਰੀ ਵੰਡ (ਸਿਰਫ਼ ਫਾਸਟ-ਗੇਟਾਂ ਨਾਲ ਕਤਾਰ ਸੁਰੱਖਿਅਤ ਕਿਉਂ ਹੈ)

- **ਪ੍ਰਤੀ PR** (quality.yml ਫਾਸਟ-ਗੇਟ): TIA-ਪ੍ਰਭਾਵਿਤ ਟੈਸਟ + ਪੂਰੀ unit 4-shard +
  vitest + lint bag + typecheck + docs/changelog ਅਖੰਡਤਾ।
- **ਪ੍ਰਤੀ ਬੈਚ/tip** (ਨਿਰੰਤਰ release-green): ਰਿਲੀਜ਼ ਬ੍ਰਾਂਚ ਵੱਲ ਹਰ push ਉੱਤੇ `--quick`
  HARD ਗੇਟ; ਪੂਰੇ `--with-build --full-ci` sweep ਦਿਨ ਵਿੱਚ 3 ਵਾਰ।
- **ਪ੍ਰਤੀ ਰਿਲੀਜ਼** (ਰਿਲੀਜ਼ PR ਉੱਤੇ ci.yml): E2E ×9 ਸਮੇਤ ਪੂਰਾ matrix,
  package-artifact + tarball boot-smoke, coverage/ratchets।

ਪਹਿਲਾਂ ਨਾਲੋਂ ਕਿਸੇ ਵੀ ਚੀਜ਼ ਦੀ ਘੱਟ ਪ੍ਰਮਾਣਿਕਤਾ ਨਹੀਂ ਹੁੰਦੀ — ਭਾਰੀ ਸਤਹ ਸਿਰਫ਼ ਪ੍ਰਤੀ PR ਦੀ ਬਜਾਏ
ਪ੍ਰਤੀ ਬੈਚ/tip ਚੱਲਦੀ ਹੈ, ਜੋ O(N) round-trips ਨੂੰ ਹਟਾਉਂਦੀ ਹੈ।

## `merge-train.sh` ਲਈ fresh-checkout ਪੂਰਵ-ਲੋੜਾਂ

ਸਕ੍ਰਿਪਟ root checkout ਉੱਤੇ (ਕਿਸੇ ਵੀ worktree ਕੰਮ ਤੋਂ ਪਹਿਲਾਂ) ਇੱਕ fail-fast **preflight**
ਚਲਾਉਂਦੀ ਹੈ, ਤਾਂ ਜੋ ਖਰਾਬ install ਕਦੇ ਵੀ ਰੈੱਡ ਟ੍ਰੇਨ ਵਜੋਂ ਗਲਤ ਨਾ ਦਿਖਾਈ ਦੇ ਸਕੇ:

1. `npm ci`, ਫਿਰ ਉਹ `bun` postinstall ਚਲਾਓ ਜਿਸਨੂੰ npm ਬਲਾਕ ਕਰਦਾ ਹੈ:
   `(cd node_modules/bun && node install.js)` — ਨਹੀਂ ਤਾਂ `check:provider-consistency`
   ਅਤੇ `check:known-symbols` (ਦੋਵੇਂ `bun scripts/…`) ਟ੍ਰੇਨ ਅਤੇ base ਦੋਵਾਂ ਉੱਤੇ ਬਿਨਾਂ
   ਕਿਸੇ violation line ਦੇ ਅਸਫਲ ਹੋ ਜਾਂਦੇ ਹਨ।
2. ਕੋਈ ਵਾਧੂ `node_modules/node_modules` ਨਹੀਂ (ਇੱਕ duplicate dependency tree; React ਦੋ ਵਾਰ
   ਲੋਡ ਹੁੰਦਾ ਹੈ ਅਤੇ UI vitest suites ਤੁਰੰਤ ਅਸਫਲ ਹੋ ਜਾਂਦੀਆਂ ਹਨ)।
3. `node_modules/.bin/tsc` ਮੌਜੂਦ ਅਤੇ executable ਹੋਵੇ (ਅਧੂਰੇ install ਵਿੱਚ ਇਹ ਨਹੀਂ ਹੁੰਦਾ)।

ਟ੍ਰੇਨ blocking `npm run check:cycles:ratchet` ਚਲਾਉਂਦੀ ਹੈ; ਸਧਾਰਨ `npm run check:cycles`
ਸਲਾਹਕਾਰ ਹੈ (ਇਹ SCCs ਨੂੰ ਸੂਚੀਬੱਧ ਕਰਦਾ ਹੈ ਅਤੇ ਸਿਹਤਮੰਦ base ਉੱਤੇ ਵੀ non-zero ਨਾਲ ਬੰਦ ਹੁੰਦਾ ਹੈ)।
