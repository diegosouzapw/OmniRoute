## npm ਭਰੋਸੇਯੋਗ ਪਬਲਿਸ਼ਿੰਗ (v3.8.51 ਤੋਂ ਡਿਫੌਲਟ) — ਬੇਨਤੀ 'ਤੇ ਸਟੇਜਡ, ਫਾਲਬੈਕ ਵਜੋਂ ਡਾਇਰੈਕਟ

`npm-publish.yml` ਡਿਫੌਲਟ ਰੂਪ ਵਿੱਚ **npm Trusted Publishing (OIDC)** ਰਾਹੀਂ ਪਬਲਿਸ਼ ਕਰਦੀ ਹੈ:
`stage-npm` ਜੌਬ (github-hosted) ਉਸ ਰਨ ਲਈ ਥੋੜ੍ਹੇ ਸਮੇਂ ਤੱਕ ਵੈਧ npm ਕ੍ਰੈਡੈਂਸ਼ੀਅਲ ਦੇ ਬਦਲੇ GitHub ਦੇ
id-token ਦੀ ਅਦਲਾ-ਬਦਲੀ ਕਰਦੀ ਹੈ — ਰਿਪੋਜ਼ਿਟਰੀ ਸੀਕ੍ਰੇਟਸ ਵਿੱਚ ਕੋਈ ਲੰਬੇ ਸਮੇਂ ਤੱਕ ਵੈਧ npm ਟੋਕਨ ਨਹੀਂ,
ਕੋਈ 2FA ਪ੍ਰੌਂਪਟ ਨਹੀਂ, ਅਤੇ provenance ਨਾਲ ਨੱਥੀ ਹੁੰਦੀ ਹੈ।
ਹੁਣ ਜਦੋਂ 2FA ਨੂੰ ਛੱਡਣ ਵਾਲੇ ਟੋਕਨ ਰਿਟਾਇਰ ਕੀਤੇ ਜਾ ਰਹੇ ਹਨ, ਇਹ npm ਵੱਲੋਂ ਮਨਜ਼ੂਰ ਕੀਤਾ ਗਿਆ ਬਾਈਪਾਸ ਹੈ;
ਇਹ WS1.3 ਦੀ ਗਾਰੰਟੀ ਕਾਇਮ ਰੱਖਦਿਆਂ ਪ੍ਰੋਜੈਕਟ ਵਿੱਚ v3.8.48 ਤੱਕ ਮੌਜੂਦ ਪੂਰੀ ਤਰ੍ਹਾਂ ਆਟੋਮੈਟਿਕ ਪ੍ਰਵਾਹ ਨੂੰ
ਬਹਾਲ ਕਰਦਾ ਹੈ (ਲੀਕ ਹੋਇਆ ਟੋਕਨ ਇਕੱਲਾ ਪਬਲਿਸ਼ ਨਹੀਂ ਕਰ ਸਕਦਾ — ਕਿਉਂਕਿ ਕੋਈ ਟੋਕਨ ਹੈ ਹੀ ਨਹੀਂ)।

**ਇੱਕ-ਵਾਰ ਦੀ ਸੈਟਅੱਪ (ਮਾਲਕ):** npmjs.com → ਪੈਕੇਜ `omniroute` → Settings → _Trusted
Publisher_ → GitHub: ਮਾਲਕ `diegosouzapw`, ਰੈਪੋ `OmniRoute`, ਵਰਕਫ਼ਲੋ `npm-publish.yml`
(ਇਨਵਾਇਰਨਮੈਂਟ: ਕੋਈ ਨਹੀਂ)। ਜਦੋਂ ਤੱਕ ਇਹ ਮੌਜੂਦ ਨਹੀਂ ਹੁੰਦਾ, ਆਟੋਮੈਟਿਕ ਕਦਮ `ENEEDAUTH` ਨਾਲ ਅਸਫਲ ਹੁੰਦਾ ਹੈ:
`publish_mode=staged` (ਹੇਠਾਂ) ਜਾਂ `direct` ਨਾਲ ਦੁਬਾਰਾ ਡਿਸਪੈਚ ਕਰੋ।

### ਸਟੇਜਡ ਪਬਲਿਸ਼ਿੰਗ (ਬੇਨਤੀ 'ਤੇ — `publish_mode=staged`)

npm-publish ਵਰਕਫ਼ਲੋ ਹੁਣ ਸਿੱਧੇ ਤੌਰ 'ਤੇ ਪਬਲਿਸ਼ ਨਹੀਂ ਕਰਦਾ: ਇਹ ਪੈਕ ਕੀਤੇ tarball ਨੂੰ ਬੂਟ ਕਰਦਾ ਹੈ
(`check:pack-boot`) ਅਤੇ ਫਿਰ `npm stage publish` ਚਲਾਉਂਦਾ ਹੈ — ਬਿਲਕੁਲ ਉਹੀ ਬਾਈਟਾਂ ਰਜਿਸਟਰੀ 'ਤੇ
ਰੱਖੀਆਂ ਜਾਂਦੀਆਂ ਹਨ, ਪਰ ਮਾਲਕ ਦੀ ਮਨਜ਼ੂਰੀ ਤੱਕ ਉਹ **ਇੰਸਟਾਲ ਕਰਨ ਯੋਗ ਨਹੀਂ** ਹੁੰਦੀਆਂ। ਮਨੁੱਖੀ 2FA ਗੇਟ
ਸਬੂਤ ਤੋਂ ਪਹਿਲਾਂ ਨਹੀਂ, ਸਗੋਂ ਉਸ ਤੋਂ ਬਾਅਦ ਚਲਾ ਗਿਆ ਹੈ।

**ਵਰਕਫ਼ਲੋ ਦੇ ਗ੍ਰੀਨ ਹੋਣ ਤੋਂ ਬਾਅਦ ਮਾਲਕ ਦਾ ਪ੍ਰਵਾਹ:**

1. `npm stage list omniroute` — ਸਟੇਜ id ਲੱਭੋ (ਇਹ ਵਰਕਫ਼ਲੋ ਸੰਖੇਪ ਵਿੱਚ ਵੀ ਦਿਖਾਈ ਜਾਂਦੀ ਹੈ)।
2. ਸਟੇਜ ਕੀਤੀਆਂ ਬਾਈਟਾਂ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ (ਸਿਫ਼ਾਰਸ਼ੀ): `npm stage download <id>`, ਫਿਰ ਡਾਊਨਲੋਡ ਕੀਤੇ
   tarball ਨੂੰ ਇੱਕ ਅਸਥਾਈ prefix ਵਿੱਚ ਇੰਸਟਾਲ ਕਰਕੇ ਬੂਟ ਕਰੋ (`npm run check:pack-boot` CI ਵਿੱਚ
   ਇਸੇ pack→install→boot ਫ਼ੈਸਲੇ ਨੂੰ ਆਟੋਮੈਟਿਕ ਕਰਦਾ ਹੈ)।
3. `npm stage approve <id>` — 2FA ਪ੍ਰੌਂਪਟ ਹੀ ਪਬਲਿਸ਼ ਹੈ। `npm stage reject <id>` ਇਸਨੂੰ ਰੱਦ ਕਰਦਾ ਹੈ।
4. ਪਬਲਿਸ਼ ਤੋਂ ਬਾਅਦ ਦੀ ਸੁਰੱਖਿਆ-ਜਾਂਚ: ਪੋਸਟ-ਪਬਲਿਸ਼ ਵੈਰੀਫਾਇਰ (v3.8.49 ਯੋਜਨਾ ਦਾ WS1.4) ਇੱਕ ਸਾਫ਼
   ਕੰਟੇਨਰ ਵਿੱਚ ਪਬਲਿਕ ਰਜਿਸਟਰੀ ਤੋਂ ਪਬਲਿਸ਼ ਕੀਤਾ ਵਰਜਨ ਇੰਸਟਾਲ ਕਰਦਾ ਹੈ ਅਤੇ ਉਸਨੂੰ ਬੂਟ ਕਰਦਾ ਹੈ।

**ਐਮਰਜੈਂਸੀ ਫਾਲਬੈਕ:** `publish_mode=direct` ਨਾਲ `workflow_dispatch` ਪੁਰਾਣੇ ਤਤਕਾਲ
`npm publish` ਨੂੰ ਬਹਾਲ ਕਰਦਾ ਹੈ (ਸਿਰਫ਼ ਉਦੋਂ ਵਰਤੋ ਜੇ ਸਟੇਜਿੰਗ ਖੁਦ ਠੀਕ ਤਰ੍ਹਾਂ ਕੰਮ ਨਾ ਕਰੇ; ਕਾਰਨ ਦਰਜ ਕਰੋ)।

**ਇੱਕ-ਵਾਰ ਦੀ ਹਾਰਡਨਿੰਗ (ਮਾਲਕ, npmjs.com):** `omniroute` ਲਈ Trusted Publisher ਨੂੰ
ਸਿਰਫ਼-ਸਟੇਜ ਮੋਡ ਵਿੱਚ ਕੌਂਫ਼ਿਗਰ ਕਰੋ, ਤਾਂ ਜੋ ਲੀਕ ਹੋਇਆ ਲੰਬੇ ਸਮੇਂ ਤੱਕ ਵੈਧ ਟੋਕਨ ਕਿਤੋਂ ਵੀ ਸਿੱਧਾ
`npm publish` ਨਾ ਕਰ ਸਕੇ — CI ਸਿਰਫ਼ ਸਟੇਜ ਕਰ ਸਕਦੀ ਹੈ; ਕੇਵਲ ਮਾਲਕ ਦਾ 2FA ਹੀ ਰਿਲੀਜ਼ ਕਰਦਾ ਹੈ।

**ਖ਼ਰਾਬ ਆਰਟੀਫੈਕਟ ਲਈ ਕਾਰਜ-ਵਿਧੀ (ਬਿਨਾਂ ਬਦਲਾਅ):** ਡਿਫੌਲਟ ਤੁਰੰਤ ਕਾਰਵਾਈ ਵਜੋਂ
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` (ਮਿੰਟਾਂ ਵਿੱਚ, ਵਾਪਸ ਬਦਲਣ ਯੋਗ);
`npm unpublish` ਸਿਰਫ਼ 72h/ਕੋਈ-ਨਿਰਭਰਤਾ-ਨਹੀਂ ਵਿੰਡੋ ਦੇ ਅੰਦਰ, ਅਤੇ ਕਦੇ ਵੀ ਪਹਿਲੇ ਕਦਮ ਵਜੋਂ ਨਹੀਂ।
Docker: ਕਿਸੇ ਵਰਜਨ ਟੈਗ ਨੂੰ ਕਦੇ ਦੁਬਾਰਾ ਨਾ ਲਿਖੋ — ਰੋਲਬੈਕ ਦਾ ਮਤਲਬ `latest` ਨੂੰ ਆਖਰੀ ਚੰਗੇ digest
ਵੱਲ ਮੁੜ ਇਸ਼ਾਰਾ ਕਰਨਾ ਹੈ।

**Docker Hub `latest` (ਹਰ ਸਥਿਰ SemVer ਪਬਲਿਸ਼ 'ਤੇ ਲਾਜ਼ਮੀ):**
`docker-publish` ਵਰਕਫ਼ਲੋ ਨੂੰ **ਦੋਵੇਂ** `X.Y.Z` ਅਤੇ, ਜਦੋਂ `should-promote-latest.sh`
ਇਸਦੇ ਸਭ ਤੋਂ ਉੱਚਾ ਸਥਿਰ SemVer ਹੋਣ ਨਾਲ ਸਹਿਮਤ ਹੋਵੇ, `:latest` ਨੂੰ **ਇੱਕੋ digest** ਨਾਲ ਟੈਗ ਕਰਨਾ
ਲਾਜ਼ਮੀ ਹੈ। ਜੌਬ ਤੋਂ ਬਾਅਦ: Hub `latest` digest ਨਵੇਂ SemVer digest ਦੇ ਬਰਾਬਰ ਹੋਵੇ ਅਤੇ
`last_updated` ਅੱਗੇ ਵਧਿਆ ਹੋਵੇ। `:latest` ਨੂੰ ਕਿਸੇ ਪੁਰਾਣੇ ਬਿਲਡ 'ਤੇ ਨਾ ਛੱਡੋ ਜਦੋਂ ਰਿਲੀਜ਼ ਨੋਟਸ
ਉਨ੍ਹਾਂ ਸੁਧਾਰਾਂ ਬਾਰੇ ਦੱਸਦੇ ਹੋਣ ਜੋ ਸਿਰਫ਼ git 'ਤੇ ਮੌਜੂਦ ਹਨ। Compose ਕਵਿਕਸਟਾਰਟ `:latest` ਵਰਤਦੇ ਹਨ;
GitOps ਨੂੰ `X.Y.Z` ਪਿੰਨ ਕਰਨਾ ਜਾਰੀ ਰੱਖਣਾ ਚਾਹੀਦਾ ਹੈ। [Docker ਰਿਲੀਜ਼ ਚੈਨਲ](../guides/DOCKER_GUIDE.md#release-channels)
ਅਤੇ #10317 ਵੇਖੋ।

## ਹਾਟਫਿਕਸ ਫਾਸਟ-ਲੇਨ (ਲੇਬਲ `hotfix`)

`hotfix` ਲੇਬਲ ਵਾਲਾ PR ਭਾਰੀ CI ਮੈਟ੍ਰਿਕਸ (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) ਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ ਅਤੇ ਤੇਜ਼, ਉੱਚ-ਸਿਗਨਲ ਗੇਟਾਂ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦਾ ਹੈ: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
ਅਤੇ tarball boot-smoke (`check:pack-boot`)। ਟੀਚਾ: ~33 ਮਿੰਟ ਦੀ ਬਜਾਏ ≤15 ਮਿੰਟ ਵਿੱਚ green।

**ਦਾਖਲਾ ਨੀਤੀ — ਚਾਰੇ ਲਾਜ਼ਮੀ ਹਨ (Chromium/VS Code/Node ਐਮਰਜੈਂਸੀ ਲੇਨਾਂ ਦੇ ਮਾਡਲ ਅਨੁਸਾਰ):**

1. **ਗੰਭੀਰਤਾ**: production ਟੁੱਟਿਆ ਹੋਇਆ ਹੈ — ਕੋਈ ਪ੍ਰਕਾਸ਼ਿਤ artifact boot ਸਮੇਂ crash ਹੁੰਦਾ ਹੈ /
   ਕੋਈ security fix / release ਦਾ ਹਰ ਵਰਤੋਂਕਾਰ ਪ੍ਰਭਾਵਿਤ ਹੈ। "ਮਹੱਤਵਪੂਰਨ" ਦਾ ਅਰਥ "ਟੁੱਟਿਆ ਹੋਇਆ" ਨਹੀਂ ਹੈ।
2. **ਅਧਿਕਾਰ**: ਕੇਵਲ repository owner ਹੀ `hotfix` ਲੇਬਲ ਲਗਾਉਂਦਾ ਹੈ। ਲੇਬਲ ਹੀ
   ਮਨਜ਼ੂਰੀ ਹੈ — campaign PR ਉੱਤੇ ਇਸਨੂੰ ਕਦੇ ਵੀ ਖੁਦ ਨਾ ਲਗਾਓ।
3. **ਸਬੂਤ**: PR body ਵਿੱਚ ਪਿਛਲੀ ਪੂਰੀ ਤਰ੍ਹਾਂ green heavy run ਦਾ link ਹੁੰਦਾ ਹੈ (ਉਹ suite ਜਿਸਨੂੰ
   ਛੱਡੀਆਂ ਗਈਆਂ jobs ਮੁੜ validate ਕਰਦੀਆਂ) ਅਤੇ ਨਾਲ ਹੀ fix ਦਾ ਆਪਣਾ ਪਹਿਲਾਂ-failing-ਫਿਰ-passing test ਹੁੰਦਾ ਹੈ।
4. **ਦਾਇਰਾ**: ਕੇਵਲ cherry-pick — ਨਿਊਨਤਮ fix, ਕੋਈ refactor ਨਹੀਂ, ਕੋਈ ਨਾਲ ਜੋੜੀ ਹੋਈ ਤਬਦੀਲੀ ਨਹੀਂ।

ਛੱਡੇ ਗਏ coverage/ratchet surface ਨੂੰ release branch ਉੱਤੇ ਅਗਲੀ full run ਦੁਆਰਾ ਮੁੜ validate ਕੀਤਾ ਜਾਂਦਾ ਹੈ
(continuous release-green) — ਇਹ lane ਸਿਰਫ਼ ਉਡੀਕ ਨੂੰ ਛੱਡਦੀ ਹੈ, validation ਨੂੰ ਕਦੇ ਨਹੀਂ।
ਕੇਵਲ tests ਵਾਲੇ diffs (`tests/` ਹੇਠਲੀਆਂ ਸਾਰੀਆਂ files, `tests/e2e/` ਹੇਠ ਕੋਈ ਨਹੀਂ) ਬਿਨਾਂ ਕਿਸੇ label ਦੇ
E2E matrix ਨੂੰ ਆਪਣੇ ਆਪ ਛੱਡ ਦਿੰਦੇ ਹਨ।

### Hooks (Husky ਦੁਆਰਾ validate ਕੀਤੇ)

Husky hooks `.husky/` ਵਿੱਚ ਮੌਜੂਦ ਹਨ ਅਤੇ git operations ਉੱਤੇ ਆਪਣੇ ਆਪ ਚੱਲਦੇ ਹਨ।

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** ਤੇਜ਼ deterministic gates — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (2026-06-13 ਨੂੰ ਸਰਗਰਮ ਕੀਤਾ ਗਿਆ)। ਜਾਣਬੁੱਝ ਕੇ `test:unit` ਨੂੰ ਸ਼ਾਮਲ ਨਹੀਂ ਕਰਦਾ (ਹੌਲਾ; CI ਦੀ `test-unit` job ਦੁਆਰਾ cover ਕੀਤਾ ਜਾਂਦਾ ਹੈ)।
  - release branches ਨੂੰ push ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ `npm run test:unit` ਹੱਥੀਂ ਚਲਾਓ।

ਜੇ ਕੋਈ hook fail ਹੁੰਦਾ ਹੈ: ਮੂਲ ਸਮੱਸਿਆ ਨੂੰ ਠੀਕ ਕਰੋ, `--no-verify` ਨਾਲ bypass ਨਾ ਕਰੋ।

### ਬਿਲਡ ਲੇਆਉਟ

ਰਿਪੋਜ਼ਿਟਰੀ ਤਿੰਨ ਵੱਖਰੀਆਂ ਆਉਟਪੁੱਟ ਡਾਇਰੈਕਟਰੀਆਂ ਵਰਤਦੀ ਹੈ — ਇਨ੍ਹਾਂ ਨੂੰ ਕਦੇ ਵੀ ਆਪਸ ਵਿੱਚ ਨਾ ਮਿਲਾਓ:

| ਡਾਇਰੈਕਟਰੀ | ਉਦੇਸ਼                                                           | ਟਰੈਕ ਕੀਤੀ ਜਾਂਦੀ ਹੈ? |
| --------- | --------------------------------------------------------------- | ------------------- |
| `src/`    | ਐਪਲੀਕੇਸ਼ਨ ਸਰੋਤ (TypeScript / TSX)                               | ਹਾਂ                 |
| `.build/` | ਬਿਲਡ ਦੀਆਂ ਵਿਚਕਾਰਲੀਆਂ ਫ਼ਾਈਲਾਂ — `next build` ਆਉਟਪੁੱਟ (`distDir`) | ਨਹੀਂ (gitignored)   |
| `dist/`   | ਵੰਡਣਯੋਗ npm ਬੰਡਲ — `assembleStandalone` ਦੁਆਰਾ ਅਸੈਂਬਲ ਕੀਤਾ       | ਨਹੀਂ (gitignored)   |

> **ਓਪਰੇਟਰ ਨੋਟ:** ਰਿਮੋਟ VPS ਇਮੇਜ ਡਾਇਰੈਕਟਰੀ `/usr/lib/node_modules/omniroute/app/` ਹੀ ਰਹਿੰਦੀ ਹੈ।
> ਸਿਰਫ਼ **ਰਿਪੋਜ਼ਿਟਰੀ ਅੰਦਰਲੀ** ਬਿਲਡ ਆਉਟਪੁੱਟ ਬਦਲੀ ਹੈ (`app/` → `dist/`)। ਡਿਪਲੋਇ ਸਕਿੱਲਾਂ `dist/`
> ਦੀ ਸਮੱਗਰੀ ਨੂੰ ਰਿਮੋਟ `app/` ਡਾਇਰੈਕਟਰੀ ਵਿੱਚ rsync ਕਰਦੀਆਂ ਹਨ — VPS ਪਾਥ ਵਿੱਚ ਕਿਸੇ ਤਬਦੀਲੀ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ।

**ਇੱਕੋ-ਬਿਲਡ ਪ੍ਰਵਾਹ:**

```
npm run build:release
  └─ rm -rf .build dist          (ਸਫ਼ਾਈ)
  └─ next build → .build/next/   (ਵਿਚਕਾਰਲੀਆਂ ਫ਼ਾਈਲਾਂ)
  └─ assembleStandalone          (standalone + static + public + natives ਨੂੰ dist/ ਵਿੱਚ ਕਾਪੀ ਕਰਦਾ ਹੈ)
  └─ writes dist/BUILD_SHA       (HEAD ਸੈਂਟੀਨਲ)
```

ਡਿਪਲੋਇ ਲਈ `npm run build` ਤੋਂ ਬਾਅਦ ਵੱਖਰੇ ਤੌਰ 'ਤੇ `npm run build:cli` ਨਾ ਚਲਾਓ — ਇਸਦੀ ਬਜਾਏ
`npm run build:release` ਵਰਤੋ, ਜੋ ਇੱਕੋ ਕਮਾਂਡ ਵਿੱਚ ਸਾਫ਼ ਪੁਨਰ-ਬਿਲਡ + ਸੈਂਟੀਨਲ ਕਰਦਾ ਹੈ।

## ਰੋਲਬੈਕ

ਜੇ ਰਿਲੀਜ਼ ਵਿੱਚ ਕੋਈ ਗੰਭੀਰ ਸਮੱਸਿਆ ਹੈ:

1. `gh release edit vX.Y.Z --prerelease` (ਇਸ ਨੂੰ ਨਵੀਨਤਮ ਨਹੀਂ ਵਜੋਂ ਚਿੰਨ੍ਹਿਤ ਕਰਦਾ ਹੈ)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (ਕੇਵਲ ਜੇ ਵਰਤੋਂਕਾਰਾਂ ਨੇ ਹਾਲੇ ਇਸਨੂੰ ਅਪਣਾਇਆ ਨਹੀਂ ਹੈ)
3. ਜਾਂ: `release/vX.Y.0` ਉੱਤੇ ਹਾਟਫਿਕਸ → ਪੈਚ ਰਿਲੀਜ਼ `vX.Y.(Z+1)`
4. GitHub Discussions ਅਤੇ Discord ਵਿੱਚ ਤੁਰੰਤ ਸੂਚਿਤ ਕਰੋ

## ਸਖ਼ਤ ਨਿਯਮ

- ਕਦੇ ਵੀ ਸਿੱਧੇ `main` ਵਿੱਚ ਕਮਿਟ ਨਾ ਕਰੋ
- `main` ਜਾਂ `release/*` ਬ੍ਰਾਂਚਾਂ ਲਈ ਕਦੇ ਵੀ `git push --force` ਦੀ ਵਰਤੋਂ ਨਾ ਕਰੋ
- Husky ਹੁੱਕਾਂ (`--no-verify`) ਨੂੰ ਕਦੇ ਵੀ ਨਾ ਛੱਡੋ
- ਸੀਕ੍ਰੇਟ, ਕ੍ਰੈਡੈਂਸ਼ੀਅਲ ਜਾਂ `.env` ਫ਼ਾਈਲਾਂ ਕਦੇ ਵੀ ਕਮਿਟ ਨਾ ਕਰੋ
- ਕਵਰੇਜ ≥60/60/60/60 (ਸਟੇਟਮੈਂਟਾਂ/ਲਾਈਨਾਂ/ਫੰਕਸ਼ਨਾਂ/ਬ੍ਰਾਂਚਾਂ) ਬਣੀ ਰਹਿਣੀ ਚਾਹੀਦੀ ਹੈ
- `src/`, `open-sse/`, `electron/`, ਜਾਂ `bin/` ਵਿੱਚ ਪ੍ਰੋਡਕਸ਼ਨ ਕੋਡ ਬਦਲਦੇ ਸਮੇਂ ਹਮੇਸ਼ਾ ਟੈਸਟ ਸ਼ਾਮਲ ਕਰੋ ਜਾਂ ਅੱਪਡੇਟ ਕਰੋ
