## npm Trusted Publishing (v3.8.51 ਤੋਂ ਡਿਫਾਲਟ) — ਬੇਨਤੀ 'ਤੇ ਪੜਾਅਵਾਰ, ਸਿੱਧਾ ਪ੍ਰਕਾਸ਼ਨ ਵਿਕਲਪ ਵਜੋਂ

`npm-publish.yml` ਡਿਫਾਲਟ ਤੌਰ 'ਤੇ **npm Trusted Publishing (OIDC)** ਰਾਹੀਂ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦੀ ਹੈ:
`stage-npm` ਜੌਬ (github-hosted) ਉਸ ਰਨ ਲਈ GitHub ਦੇ id-token ਨੂੰ ਇੱਕ ਥੋੜ੍ਹੇ ਸਮੇਂ ਲਈ ਵੈਧ npm
ਕ੍ਰੈਡੈਂਸ਼ੀਅਲ ਨਾਲ ਬਦਲਦੀ ਹੈ — ਰਿਪੋਜ਼ਟਰੀ ਸੀਕ੍ਰੇਟਸ ਵਿੱਚ ਕੋਈ ਲੰਬੇ ਸਮੇਂ ਲਈ ਵੈਧ npm ਟੋਕਨ ਨਹੀਂ, ਕੋਈ 2FA ਪ੍ਰੌਂਪਟ ਨਹੀਂ, ਅਤੇ ਮੂਲ-ਸਰੋਤ ਦਾ ਸਬੂਤ ਜੁੜਿਆ ਹੁੰਦਾ ਹੈ।
ਹੁਣ ਜਦੋਂ 2FA ਨੂੰ ਛੱਡਣ ਵਾਲੇ ਟੋਕਨ ਬੰਦ ਕੀਤੇ ਜਾ ਰਹੇ ਹਨ, ਇਹ npm ਵੱਲੋਂ ਮਨਜ਼ੂਰ ਕੀਤਾ ਗਿਆ ਬਾਈਪਾਸ ਹੈ;
ਇਹ WS1.3 ਗਾਰੰਟੀ ਕਾਇਮ ਰੱਖਦੇ ਹੋਏ, ਪ੍ਰੋਜੈਕਟ ਵਿੱਚ v3.8.48 ਤੱਕ ਮੌਜੂਦ ਪੂਰੀ ਤਰ੍ਹਾਂ
ਆਟੋਮੈਟਿਕ ਪ੍ਰਵਾਹ ਨੂੰ ਮੁੜ ਬਹਾਲ ਕਰਦਾ ਹੈ (ਲੀਕ ਹੋਇਆ ਟੋਕਨ ਇਕੱਲਾ ਪ੍ਰਕਾਸ਼ਿਤ ਨਹੀਂ ਕਰ ਸਕਦਾ — ਕਿਉਂਕਿ ਕੋਈ ਟੋਕਨ ਹੈ ਹੀ ਨਹੀਂ)।

**ਇੱਕ-ਵਾਰ ਦੀ ਸੈਟਅੱਪ (ਮਾਲਕ):** npmjs.com → ਪੈਕੇਜ `omniroute` → Settings → _Trusted
Publisher_ → GitHub: ਮਾਲਕ `diegosouzapw`, ਰਿਪੋ `OmniRoute`, ਵਰਕਫ਼ਲੋ `npm-publish.yml`
(ਵਾਤਾਵਰਣ: ਕੋਈ ਨਹੀਂ)। ਜਦੋਂ ਤੱਕ ਇਹ ਮੌਜੂਦ ਨਹੀਂ ਹੁੰਦਾ, ਆਟੋਮੈਟਿਕ ਪੜਾਅ `ENEEDAUTH` ਨਾਲ ਅਸਫਲ ਰਹਿੰਦਾ ਹੈ:
`publish_mode=staged` (ਹੇਠਾਂ) ਜਾਂ `direct` ਨਾਲ ਦੁਬਾਰਾ ਡਿਸਪੈਚ ਕਰੋ।

### ਪੜਾਅਵਾਰ ਪ੍ਰਕਾਸ਼ਨ (ਬੇਨਤੀ 'ਤੇ — `publish_mode=staged`)

npm-publish ਵਰਕਫ਼ਲੋ ਹੁਣ ਸਿੱਧਾ ਪ੍ਰਕਾਸ਼ਿਤ ਨਹੀਂ ਕਰਦਾ: ਇਹ ਪੈਕ ਕੀਤੇ tarball
ਨੂੰ ਬੂਟ ਕਰਦਾ ਹੈ (`check:pack-boot`) ਅਤੇ ਫਿਰ `npm stage publish` ਚਲਾਉਂਦਾ ਹੈ — ਬਿਲਕੁਲ ਉਹੀ ਬਾਈਟਾਂ
ਰਜਿਸਟਰੀ 'ਤੇ ਰੱਖੀਆਂ ਜਾਂਦੀਆਂ ਹਨ, ਪਰ ਮਾਲਕ ਦੀ ਮਨਜ਼ੂਰੀ ਤੱਕ ਉਹ **ਇੰਸਟਾਲ ਕਰਨ ਯੋਗ ਨਹੀਂ** ਹੁੰਦੀਆਂ। ਮਨੁੱਖੀ 2FA ਗੇਟ
ਹੁਣ ਸਬੂਤ ਤੋਂ ਪਹਿਲਾਂ ਨਹੀਂ, ਸਗੋਂ ਉਸ ਤੋਂ ਬਾਅਦ ਆਉਂਦਾ ਹੈ।

**ਵਰਕਫ਼ਲੋ ਹਰਾ ਹੋਣ ਤੋਂ ਬਾਅਦ ਮਾਲਕ ਲਈ ਪ੍ਰਕਿਰਿਆ:**

1. `npm stage list omniroute` — stage id ਲੱਭੋ (ਇਹ ਵਰਕਫ਼ਲੋ ਸੰਖੇਪ ਵਿੱਚ ਵੀ ਪ੍ਰਿੰਟ ਹੁੰਦੀ ਹੈ)।
2. ਪੜਾਅਵਾਰ ਰੱਖੀਆਂ ਬਾਈਟਾਂ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ (ਸਿਫ਼ਾਰਸ਼ੀ): `npm stage download <id>`, ਫਿਰ ਡਾਊਨਲੋਡ ਕੀਤੇ
   tarball ਨੂੰ ਇੱਕ ਅਸਥਾਈ prefix ਵਿੱਚ ਇੰਸਟਾਲ ਕਰਕੇ ਬੂਟ ਕਰੋ (`npm run check:pack-boot`, CI ਵਿੱਚ
   ਉਸੇ pack→install→boot ਫ਼ੈਸਲੇ ਨੂੰ ਆਟੋਮੇਟ ਕਰਦਾ ਹੈ)।
3. `npm stage approve <id>` — 2FA ਪ੍ਰੌਂਪਟ ਹੀ ਪ੍ਰਕਾਸ਼ਨ ਹੈ। `npm stage reject <id>` ਇਸਨੂੰ ਰੱਦ ਕਰ ਦਿੰਦਾ ਹੈ।
4. ਪ੍ਰਕਾਸ਼ਨ ਤੋਂ ਬਾਅਦ ਦਾ ਸੁਰੱਖਿਆ-ਜਾਲ: post-publish verifier (v3.8.49 ਯੋਜਨਾ ਦਾ WS1.4) ਇੱਕ ਸਾਫ਼ container ਵਿੱਚ
   ਜਨਤਕ registry ਤੋਂ ਪ੍ਰਕਾਸ਼ਿਤ ਵਰਜਨ ਇੰਸਟਾਲ ਕਰਦਾ ਹੈ ਅਤੇ ਇਸਨੂੰ ਬੂਟ ਕਰਦਾ ਹੈ।

**ਐਮਰਜੈਂਸੀ ਵਿਕਲਪ:** `publish_mode=direct` ਨਾਲ `workflow_dispatch`, ਪੁਰਾਣਾ
ਤੁਰੰਤ `npm publish` ਮੁੜ ਬਹਾਲ ਕਰਦਾ ਹੈ (ਸਿਰਫ਼ ਉਦੋਂ ਵਰਤੋ ਜੇ staging ਆਪ ਹੀ ਠੀਕ ਤਰ੍ਹਾਂ ਕੰਮ ਨਾ ਕਰੇ; ਕਾਰਨ ਦਰਜ ਕਰੋ)।

**ਇੱਕ-ਵਾਰ ਦੀ ਮਜ਼ਬੂਤੀ (ਮਾਲਕ, npmjs.com):** `omniroute` ਲਈ Trusted Publisher ਨੂੰ
ਸਿਰਫ਼ stage ਮੋਡ ਵਿੱਚ ਸੰਰਚਿਤ ਕਰੋ, ਤਾਂ ਜੋ ਕੋਈ ਲੀਕ ਹੋਇਆ ਲੰਬੇ ਸਮੇਂ ਲਈ ਵੈਧ ਟੋਕਨ ਕਿਸੇ ਵੀ ਥਾਂ ਤੋਂ ਸਿੱਧਾ `npm publish`
ਨਾ ਕਰ ਸਕੇ — CI ਕੇਵਲ stage ਕਰ ਸਕਦੀ ਹੈ; ਸਿਰਫ਼ ਮਾਲਕ ਦਾ 2FA ਹੀ ਰਿਲੀਜ਼ ਕਰਦਾ ਹੈ।

**ਖ਼ਰਾਬ ਆਰਟੀਫੈਕਟ ਲਈ ਕਾਰਵਾਈ-ਵਿਧੀ (ਬਦਲਾਅ ਰਹਿਤ):** ਡਿਫਾਲਟ ਤੁਰੰਤ ਕਾਰਵਾਈ ਵਜੋਂ `npm deprecate omniroute@<bad> "<reason> — use <fixed>"`
ਵਰਤੋ (ਕੁਝ ਮਿੰਟ, ਵਾਪਸ ਮੋੜਨ ਯੋਗ); `npm unpublish` ਸਿਰਫ਼ 72h/no-dependents
ਵਿੰਡੋ ਦੇ ਅੰਦਰ ਵਰਤੋ ਅਤੇ ਕਦੇ ਵੀ ਪਹਿਲੀ ਕਾਰਵਾਈ ਵਜੋਂ ਨਹੀਂ। Docker: ਕਿਸੇ ਵਰਜਨ ਟੈਗ ਨੂੰ ਕਦੇ ਦੁਬਾਰਾ ਨਾ ਲਿਖੋ — ਰੋਲਬੈਕ ਦਾ ਅਰਥ
`latest` ਨੂੰ ਆਖਰੀ ਸਹੀ digest ਵੱਲ ਮੁੜ ਇਸ਼ਾਰਾ ਕਰਨਾ ਹੈ।

**Docker Hub `latest` (ਹਰ ਸਥਿਰ SemVer ਪ੍ਰਕਾਸ਼ਨ 'ਤੇ ਲਾਜ਼ਮੀ):**
`docker-publish` ਵਰਕਫ਼ਲੋ ਨੂੰ **ਦੋਵੇਂ** `X.Y.Z` ਅਤੇ, ਜਦੋਂ
`should-promote-latest.sh` ਸਹਿਮਤ ਹੋਵੇ ਕਿ ਇਹ ਸਭ ਤੋਂ ਉੱਚਾ ਸਥਿਰ SemVer ਹੈ, `:latest`
ਨੂੰ **ਇੱਕੋ digest** ਨਾਲ ਟੈਗ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ। ਜੌਬ ਤੋਂ ਬਾਅਦ: Hub ਦਾ `latest` digest ਨਵੇਂ
SemVer digest ਦੇ ਬਰਾਬਰ ਹੋਵੇ ਅਤੇ `last_updated` ਅੱਗੇ ਵਧਿਆ ਹੋਵੇ। ਜਦੋਂ ਰਿਲੀਜ਼ ਨੋਟ ਉਹਨਾਂ ਸੁਧਾਰਾਂ ਬਾਰੇ ਦੱਸਦੇ ਹੋਣ
ਜੋ ਸਿਰਫ਼ git 'ਤੇ ਮੌਜੂਦ ਹਨ, ਤਾਂ `:latest` ਨੂੰ ਕਿਸੇ ਪੁਰਾਣੇ ਬਿਲਡ 'ਤੇ ਨਾ ਛੱਡੋ।
Compose quickstarts `:latest` ਵਰਤਦੇ ਹਨ; GitOps ਨੂੰ `X.Y.Z` ਹੀ pin ਕਰਦੇ ਰਹਿਣਾ ਚਾਹੀਦਾ ਹੈ।
[Docker ਰਿਲੀਜ਼ ਚੈਨਲ](../guides/DOCKER_GUIDE.md#release-channels) ਅਤੇ #10317 ਵੇਖੋ।

## ਹਾਟਫਿਕਸ ਫਾਸਟ-ਲੇਨ (ਲੇਬਲ `hotfix`)

`hotfix` ਲੇਬਲ ਵਾਲਾ PR ਭਾਰੀ CI ਮੈਟ੍ਰਿਕਸ (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) ਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ ਅਤੇ ਤੇਜ਼, ਉੱਚ-ਸੰਕੇਤ ਵਾਲੇ ਗੇਟ ਕਾਇਮ ਰੱਖਦਾ ਹੈ: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
ਅਤੇ tarball boot-smoke (`check:pack-boot`)। ਟੀਚਾ: ~33min ਦੀ ਬਜਾਏ ≤15min ਵਿੱਚ ਹਰਾ ਨਤੀਜਾ।

**ਦਾਖਲਾ ਨੀਤੀ — ਸਾਰੀਆਂ ਚਾਰ ਸ਼ਰਤਾਂ ਲਾਜ਼ਮੀ (Chromium/VS Code/Node ਦੀਆਂ ਐਮਰਜੈਂਸੀ ਲੇਨਾਂ ਦੇ ਆਧਾਰ 'ਤੇ):**

1. **ਗੰਭੀਰਤਾ**: ਪ੍ਰੋਡਕਸ਼ਨ ਟੁੱਟਿਆ ਹੋਇਆ ਹੈ — ਪ੍ਰਕਾਸ਼ਿਤ ਆਰਟੀਫੈਕਟ ਬੂਟ ਹੋਣ ਸਮੇਂ ਕਰੈਸ਼ ਕਰਦਾ ਹੈ / ਇਹ
   ਸੁਰੱਖਿਆ ਸੁਧਾਰ ਹੈ / ਰਿਲੀਜ਼ ਦਾ ਹਰੇਕ ਵਰਤੋਂਕਾਰ ਪ੍ਰਭਾਵਿਤ ਹੈ। "ਮਹੱਤਵਪੂਰਨ" ਦਾ ਅਰਥ "ਟੁੱਟਿਆ ਹੋਇਆ" ਨਹੀਂ ਹੈ।
2. **ਅਧਿਕਾਰ**: ਕੇਵਲ ਰਿਪੋਜ਼ਟਰੀ ਦਾ ਮਾਲਕ `hotfix` ਲੇਬਲ ਲਗਾਉਂਦਾ ਹੈ। ਲੇਬਲ ਹੀ
   ਮਨਜ਼ੂਰੀ ਹੈ — ਕਿਸੇ campaign PR 'ਤੇ ਇਸਨੂੰ ਕਦੇ ਵੀ ਖੁਦ ਨਾ ਲਗਾਓ।
3. **ਸਬੂਤ**: PR ਦੀ ਬਾਡੀ ਪਿਛਲੀ ਪੂਰੀ ਤਰ੍ਹਾਂ ਹਰੀ heavy run (ਉਹ suite ਜਿਸਨੂੰ
   ਛੱਡੀਆਂ ਗਈਆਂ jobs ਮੁੜ ਪ੍ਰਮਾਣਿਤ ਕਰਦੀਆਂ) ਦੇ ਨਾਲ-ਨਾਲ fix ਦੇ ਆਪਣੇ ਪਹਿਲਾਂ-ਅਸਫਲ-ਫਿਰ-ਸਫਲ test ਨੂੰ ਲਿੰਕ ਕਰਦੀ ਹੈ।
4. **ਦਾਇਰਾ**: ਕੇਵਲ cherry-pick — ਘੱਟੋ-ਘੱਟ ਲੋੜੀਂਦਾ fix, ਕੋਈ refactor ਨਹੀਂ, ਕੋਈ ਗੈਰ-ਸੰਬੰਧਿਤ ਤਬਦੀਲੀ ਨਹੀਂ।

ਛੱਡੀ ਗਈ coverage/ratchet ਸਤਹ ਨੂੰ release branch ਉੱਤੇ ਅਗਲੀ ਪੂਰੀ run
(ਨਿਰੰਤਰ release-green) ਦੁਆਰਾ ਮੁੜ ਪ੍ਰਮਾਣਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ — ਇਹ lane ਸਿਰਫ਼ ਉਡੀਕ ਨੂੰ ਛੱਡਦੀ ਹੈ, ਪ੍ਰਮਾਣਿਕਤਾ ਨੂੰ ਕਦੇ ਨਹੀਂ।
ਕੇਵਲ tests ਵਾਲੇ diffs (ਸਾਰੀਆਂ ਫਾਈਲਾਂ `tests/` ਹੇਠਾਂ, ਕੋਈ ਵੀ `tests/e2e/` ਹੇਠਾਂ ਨਹੀਂ) ਬਿਨਾਂ ਕਿਸੇ ਲੇਬਲ ਦੇ
E2E ਮੈਟ੍ਰਿਕਸ ਨੂੰ ਆਪਣੇ-ਆਪ ਛੱਡ ਦਿੰਦੇ ਹਨ।

### Hooks (Husky ਦੁਆਰਾ ਪ੍ਰਮਾਣਿਤ)

Husky hooks `.husky/` ਵਿੱਚ ਮੌਜੂਦ ਹਨ ਅਤੇ git ਕਾਰਵਾਈਆਂ ਉੱਤੇ ਆਪਣੇ-ਆਪ ਚੱਲਦੇ ਹਨ।

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** ਤੇਜ਼ ਨਿਰਧਾਰਿਤ ਗੇਟ — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (2026-06-13 ਨੂੰ ਸਰਗਰਮ ਕੀਤਾ ਗਿਆ)। ਜਾਣਬੁੱਝ ਕੇ `test:unit` ਨੂੰ ਸ਼ਾਮਲ ਨਹੀਂ ਕਰਦਾ (ਹੌਲਾ; CI ਦੀ `test-unit` job ਦੁਆਰਾ ਕਵਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ)।
  - release branches ਨੂੰ push ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ `npm run test:unit` ਹੱਥੀਂ ਚਲਾਓ।

ਜੇ ਕੋਈ hook ਅਸਫਲ ਹੁੰਦਾ ਹੈ: ਮੂਲ ਸਮੱਸਿਆ ਠੀਕ ਕਰੋ, `--no-verify` ਨਾਲ ਇਸਨੂੰ bypass ਨਾ ਕਰੋ।

### ਬਿਲਡ ਲੇਆਉਟ

ਰਿਪੋਜ਼ਟਰੀ ਤਿੰਨ ਵੱਖਰੀਆਂ ਆਉਟਪੁੱਟ ਡਾਇਰੈਕਟਰੀਆਂ ਦੀ ਵਰਤੋਂ ਕਰਦੀ ਹੈ — ਇਨ੍ਹਾਂ ਨੂੰ ਕਦੇ ਵੀ ਆਪਸ ਵਿੱਚ ਨਾ ਮਿਲਾਓ:

| ਡਾਇਰੈਕਟਰੀ | ਉਦੇਸ਼                                                     | ਟਰੈਕ ਕੀਤੀ ਜਾਂਦੀ ਹੈ? |
| --------- | --------------------------------------------------------- | ------------------- |
| `src/`    | ਐਪਲੀਕੇਸ਼ਨ ਸਰੋਤ (TypeScript / TSX)                         | ਹਾਂ                 |
| `.build/` | ਬਿਲਡ ਦੇ ਵਿਚਕਾਰਲੇ ਨਤੀਜੇ — `next build` ਆਉਟਪੁੱਟ (`distDir`) | ਨਹੀਂ (gitignored)   |
| `dist/`   | ਵੰਡਣਯੋਗ npm ਬੰਡਲ — `assembleStandalone` ਦੁਆਰਾ ਤਿਆਰ ਕੀਤਾ   | ਨਹੀਂ (gitignored)   |

> **ਓਪਰੇਟਰ ਨੋਟ:** ਰਿਮੋਟ VPS ਇਮੇਜ ਡਾਇਰੈਕਟਰੀ `/usr/lib/node_modules/omniroute/app/` ਹੀ ਰਹਿੰਦੀ ਹੈ।
> ਸਿਰਫ਼ **ਰਿਪੋਜ਼ਟਰੀ ਦੇ ਅੰਦਰਲਾ** ਬਿਲਡ ਆਉਟਪੁੱਟ ਬਦਲਿਆ ਹੈ (`app/` → `dist/`)। ਡਿਪਲੌਇ ਕੌਸ਼ਲ
> `dist/` ਦੀ ਸਮੱਗਰੀ ਨੂੰ ਰਿਮੋਟ `app/` ਡਾਇਰੈਕਟਰੀ ਵਿੱਚ rsync ਕਰਦੇ ਹਨ — VPS ਪਾਥ ਵਿੱਚ ਕਿਸੇ ਬਦਲਾਅ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ।

**ਇੱਕ-ਬਿਲਡ ਪ੍ਰਵਾਹ:**

```
npm run build:release
  └─ rm -rf .build dist          (ਸਾਫ਼-ਸਫ਼ਾਈ)
  └─ next build → .build/next/   (ਵਿਚਕਾਰਲੇ ਨਤੀਜੇ)
  └─ assembleStandalone          (standalone + static + public + natives ਨੂੰ dist/ ਵਿੱਚ ਕਾਪੀ ਕਰਦਾ ਹੈ)
  └─ writes dist/BUILD_SHA       (HEAD ਸੰਕੇਤਕ)
```

ਡਿਪਲੌਇ ਲਈ `npm run build` ਤੋਂ ਬਾਅਦ ਵੱਖਰੇ ਤੌਰ 'ਤੇ `npm run build:cli` ਨਾ ਚਲਾਓ — ਇਸਦੀ ਬਜਾਏ
`npm run build:release` ਵਰਤੋ, ਜੋ ਇੱਕੋ ਕਮਾਂਡ ਵਿੱਚ ਸਾਫ਼ ਮੁੜ-ਬਿਲਡ + ਸੰਕੇਤਕ ਬਣਾਉਂਦਾ ਹੈ।

ਪੂਰਾ ਕ੍ਰਮ ਪ੍ਰਿੰਟ ਕਰਦੀ ਹੈ — ਪੂਰਵ-ਸ਼ਰਤਾਂ (ਸਰੋਤ ਰਿਜ਼ਾਲਵ ਹੁੰਦਾ ਹੈ, ਪਿਛਲਾ ਟੈਗ ਮੌਜੂਦ ਹੈ, `package.json`

ਕਦੇ ਵੀ ਗ੍ਰੀਨ ਨਹੀਂ — Mergify `release` ਕਤਾਰ ਕਨਫਿਗਰ ਕੀਤੀ ਹੋਈ ਹੈ (G11: `queue_rules`, `checks_timeout`,
ਲੇਬਲ `queue`), `release/*` ਰੂਲਸੈੱਟ ਅਜੇ ਵੀ ਮਿਟਾਉਣ ਅਤੇ ਫੋਰਸ-ਪੁਸ਼ ਨੂੰ ਰੋਕਦਾ ਹੈ, ਅਤੇ
`stable/v3` ਅਤੇ `develop` ਅਜੇ ਮੌਜੂਦ ਨਹੀਂ ਹਨ), ਦੋ ਬ੍ਰਾਂਚ ਕਦਮ, ਕਿਹੜੇ ਨਿਸ਼ਕ੍ਰਿਯ ਵਰਕਫਲੋ
ਟਰਿੱਗਰ ਅਤੇ `if:` ਸ਼ਰਤਾਂ ਸਹੀ ਹੋ ਜਾਂਦੀਆਂ ਹਨ (ਅਤੇ ਕਿਹੜੀਆਂ ਰਿਪੋਜ਼ਟਰੀ ਵੇਰੀਏਬਲ ਦੁਆਰਾ ਗੇਟ ਕੀਤੀਆਂ ਰਹਿੰਦੀਆਂ

ਅਸਫਲ ਹੋਈ (`✗`), `2` = ਵਰਤੋਂ ਦੀ ਗਲਤੀ। `--advisory <id,...>` ਕਿਸੇ ਜਾਂਚ ਨੂੰ ਲੁਕਾਏ ਬਿਨਾਂ

ਅਸਲ ਕੱਟ ਦਾ ਡ੍ਰਾਈ-ਰਨ ਉਸ ਵੇਲੇ ਚਲਾਓ ਜਦੋਂ 3.9.0 ਰਿਲੀਜ਼ ਫ੍ਰੀਜ਼ ਅਜੇ ਵੀ ਖੁੱਲ੍ਹਾ ਹੋਵੇ — ਬ੍ਰਾਂਚਾਂ

### ਕੱਟ (3.9.0, GO ਤੋਂ ਬਾਅਦ)

1. GO ਨੂੰ [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md) ਵਿੱਚ ਰਿਕਾਰਡ ਕੀਤਾ ਗਿਆ।
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` `RESULT: READY` ਪ੍ਰਿੰਟ ਕਰਦੀ ਹੈ।
3. ਡ੍ਰਾਈ-ਰਨ ਵੱਲੋਂ ਪ੍ਰਿੰਟ ਕੀਤੀਆਂ ਕਮਾਂਡਾਂ ਨਾਲ ਹੱਥੀਂ `origin` ਉੱਤੇ ਬ੍ਰਾਂਚਾਂ ਬਣਾਓ — ਸਕ੍ਰਿਪਟ
   `origin` ਉੱਤੇ ਪੁਸ਼ ਕਰਨ ਤੋਂ ਇਨਕਾਰ ਕਰਦੀ ਹੈ। ਸਮੀਖਿਆ ਕੀਤੀ develop ਕਮਿਟ ਨੂੰ ਮੁੜ ਵਰਤਣ ਲਈ,
   ਪਹਿਲਾਂ ਆਪਣੇ ਫੋਰਕ ਵਿਰੁੱਧ 3.9.0 ਟਿਪ ਉੱਤੇ `--execute` ਅਭਿਆਸ ਚਲਾਓ; ਇਹ ਦੋਵੇਂ SHAs ਪ੍ਰਿੰਟ ਕਰਦਾ ਹੈ,
   ਅਤੇ ਉਹੀ ਕਮਿਟ ਪੁਸ਼ ਕੀਤੀਆਂ ਜਾ ਸਕਦੀਆਂ ਹਨ:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. ਪਹਿਲੀ PR ਦੇ ਲੈਂਡ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ `stable/v3` ਅਤੇ `develop` ਨੂੰ ਸੁਰੱਖਿਅਤ ਕਰੋ (ਰੂਲਸੈੱਟ + ਮਰਜ ਕਤਾਰ)।
5. ਨਿਸ਼ਕ੍ਰਿਯ ਵਰਕਫਲੋ ਬ੍ਰਾਂਚ ਦੀ ਮੌਜੂਦਗੀ ਨਾਲ ਚਾਲੂ ਹੁੰਦੇ ਹਨ: `forward-port.yml` (`stable/v3` ਉੱਤੇ ਪੁਸ਼),
   `validate-stable-pr.yml` (`stable/v3` ਲਈ PRs) ਅਤੇ `nightly-v4-build.yml`
   (`develop` ਨੂੰ ਬਿਲਡ ਕਰਦੀ ਹੈ)। ਗੋ-ਲਾਈਵ ਤੋਂ ਪਹਿਲਾਂ, `secrets.FORWARD_PORT_TOKEN` ਰਿਪੋਜ਼ਟਰੀ
   ਸੀਕ੍ਰੇਟ ਸੈੱਟ ਕਰੋ (ਤਾਂ ਜੋ CI ਫਾਰਵਰਡ-ਪੋਰਟ PRs ਉੱਤੇ ਚੱਲੇ); nightly ਪਬਲਿਸ਼ਿੰਗ ਉਦੋਂ ਤੱਕ ਬੰਦ
   ਰਹਿੰਦੀ ਹੈ ਜਦੋਂ ਤੱਕ ਮਾਲਕ ਰਿਪੋਜ਼ਟਰੀ ਵੇਰੀਏਬਲ `vars.NIGHTLY_PUBLISH` ਨੂੰ `true` ਉੱਤੇ ਸੈੱਟ ਨਹੀਂ
   ਕਰਦਾ ਅਤੇ npm Trusted Publishing `nightly-v4-build.yml` ਨੂੰ ਸਵੀਕਾਰ ਨਹੀਂ ਕਰਦੀ। ਚੈਨਲ
   ਰਿਜ਼ੋਲਿਊਸ਼ਨ `scripts/release/dist-tag.mjs` ਹੈ, ਉਹੀ ਰਿਜ਼ਾਲਵਰ ਜਿਸਨੂੰ `npm-publish.yml` ਵਰਤਦੀ ਹੈ।
6. ਚੈਨਲਾਂ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ: `npm view omniroute dist-tags --json` `latest` = 3.9.0 ਦਿਖਾਉਂਦੀ ਹੈ ਅਤੇ
   v4 ਦੇ ਪਬਲਿਸ਼ ਹੋਣ ਤੱਕ ਕੋਈ `next` / `nightly` ਨਹੀਂ।
7. ਜੇ ਲੋੜ ਹੋਵੇ ਤਾਂ ਰੋਲਬੈਕ ਕਰੋ: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   ਅਤੇ `npm dist-tag add omniroute@3.8.59 latest`।

## ਰੋਲਬੈਕ

ਜੇ ਰਿਲੀਜ਼ ਵਿੱਚ ਕੋਈ ਗੰਭੀਰ ਸਮੱਸਿਆ ਹੋਵੇ:

1. `gh release edit vX.Y.Z --prerelease` (ਇਸਨੂੰ ਨਵੀਨਤਮ ਨਹੀਂ ਵਜੋਂ ਚਿੰਨ੍ਹਿਤ ਕਰਦਾ ਹੈ)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (ਸਿਰਫ਼ ਜੇ ਉਪਭੋਗਤਾਵਾਂ ਨੇ ਹਾਲੇ ਇਸਨੂੰ ਅਪਣਾਇਆ ਨਹੀਂ ਹੈ)
3. ਜਾਂ: `release/vX.Y.0` ਉੱਤੇ ਹਾਟਫਿਕਸ → ਪੈਚ ਰਿਲੀਜ਼ `vX.Y.(Z+1)`
4. GitHub Discussions ਅਤੇ Discord ਵਿੱਚ ਤੁਰੰਤ ਸੂਚਿਤ ਕਰੋ

## ਸਖ਼ਤ ਨਿਯਮ

- ਕਦੇ ਵੀ ਸਿੱਧਾ `main` ਵਿੱਚ ਕਮਿਟ ਨਾ ਕਰੋ
- `main` ਜਾਂ `release/*` ਬ੍ਰਾਂਚਾਂ ਲਈ ਕਦੇ ਵੀ `git push --force` ਦੀ ਵਰਤੋਂ ਨਾ ਕਰੋ
- ਕਦੇ ਵੀ Husky ਹੁੱਕਾਂ ਨੂੰ ਨਾ ਛੱਡੋ (`--no-verify`)
- ਕਦੇ ਵੀ ਸੀਕ੍ਰੇਟ, ਕ੍ਰੀਡੈਂਸ਼ੀਅਲ ਜਾਂ `.env` ਫ਼ਾਈਲਾਂ ਕਮਿਟ ਨਾ ਕਰੋ
- ਕਵਰੇਜ ≥60/60/60/60 (ਸਟੇਟਮੈਂਟਾਂ/ਲਾਈਨਾਂ/ਫੰਕਸ਼ਨਾਂ/ਬ੍ਰਾਂਚਾਂ) ਬਣੀ ਰਹਿਣੀ ਚਾਹੀਦੀ ਹੈ
- `src/`, `open-sse/`, `electron/`, ਜਾਂ `bin/` ਵਿੱਚ ਪ੍ਰੋਡਕਸ਼ਨ ਕੋਡ ਬਦਲਦੇ ਸਮੇਂ ਹਮੇਸ਼ਾ ਟੈਸਟ ਸ਼ਾਮਲ ਜਾਂ ਅੱਪਡੇਟ ਕਰੋ

## ਸਵੈਚਾਲਿਤ ਸਿੰਕ ਜਾਂਚ
