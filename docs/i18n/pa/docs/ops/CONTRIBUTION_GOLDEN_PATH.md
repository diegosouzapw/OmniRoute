ਕਿਸੇ pull request ਲਈ ਸਭ ਤੋਂ ਛੋਟਾ ਭਰੋਸੇਯੋਗ ਵਿਕਾਸ ਚੱਕਰ ਚੁਣਨ ਵਾਸਤੇ ਇਸ ਗਾਈਡ ਦੀ ਵਰਤੋਂ ਕਰੋ। ਇਹ ਹੇਠਾਂ ਲਿੰਕ ਕੀਤੇ ਖੇਤਰ-ਵਿਸ਼ੇਸ਼ ਆਰਕੀਟੈਕਚਰ ਅਤੇ ਸੁਰੱਖਿਆ ਦਸਤਾਵੇਜ਼ਾਂ ਦੀ ਥਾਂ ਨਹੀਂ ਲੈਂਦੀ; ਇਹ ਹਰ ਆਮ ਤਬਦੀਲੀ ਦੀ ਕਿਸਮ ਨੂੰ ਉਸਦੇ ਇਕਰਾਰਨਾਮਿਆਂ, ਕੇਂਦ੍ਰਿਤ ਜਾਂਚਾਂ ਅਤੇ CI ਕਵਰੇਜ ਨਾਲ ਜੋੜਦੀ ਹੈ।

## ਹਰ ਤਬਦੀਲੀ ਦੁਆਰਾ ਅਪਣਾਇਆ ਜਾਣ ਵਾਲਾ ਮਾਰਗ

1. **ਸੰਪਾਦਨ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ base ਚੁਣੋ।** ਸਭ ਤੋਂ ਉੱਚੀ ਸਰਗਰਮ `release/v*` branch ਲੱਭੋ ਅਤੇ ਉਸਦੇ ਸਿਰੇ ਤੋਂ branch ਬਣਾਓ। ਉਸ branch ਨੂੰ target ਕਰੋ, `main` ਨੂੰ ਨਹੀਂ। ਜੇ release freeze ਸਰਗਰਮ ਹੈ, ਤਾਂ frozen branch ਨੂੰ target ਨਾ ਕਰੋ; ਇਸ ਦੀ ਬਜਾਏ
   [Branching & Release Model](BRANCHING_MODEL.md) ਵਿੱਚ ਦਰਸਾਏ ਅਗਲੇ ਸਰਗਰਮ ਚੱਕਰ ਦੀ ਵਰਤੋਂ ਕਰੋ।
2. **ਇਕਰਾਰਨਾਮਿਆਂ ਦੇ ਨਾਮ ਦਿਓ।** ਹਰ ਉਸ catalog, schema, generated artifact, public API ਜਾਂ user interface ਦੀ ਪਛਾਣ ਕਰੋ ਜਿਸਨੂੰ ਤਬਦੀਲੀ ਪ੍ਰਭਾਵਿਤ ਕਰਦੀ ਹੈ। ਹੇਠਾਂ ਦਿੱਤੀ ਸਾਰਣੀ ਘੱਟੋ-ਘੱਟ ਸ਼ੁਰੂਆਤੀ ਸਮੂਹ ਦਿੰਦੀ ਹੈ।
3. **ਕੇਂਦ੍ਰਿਤ ਟੈਸਟ ਲਿਖੋ ਜਾਂ ਅੱਪਡੇਟ ਕਰੋ।** `src/`, `open-sse/`, `electron/`, ਜਾਂ
   `bin/` ਵਿੱਚ production ਤਬਦੀਲੀਆਂ ਲਈ ਉਸੇ PR ਵਿੱਚ ਇੱਕ automated test ਲਾਜ਼ਮੀ ਹੈ। ਪਹਿਲਾਂ ਉਹ ਸਭ ਤੋਂ ਛੋਟੀਆਂ test files ਚਲਾਓ ਜੋ ਵਿਹਾਰ ਨੂੰ ਸਾਬਤ ਕਰਦੀਆਂ ਹਨ, ਫਿਰ ਸੂਚੀਬੱਧ ਕੇਂਦ੍ਰਿਤ gates ਚਲਾਓ।
4. **CI ਨੂੰ ਵਿਆਪਕ matrix ਚਲਾਉਣ ਦਿਓ।** ਪੂਰੇ unit shards, Vitest, coverage ratchet, ਅਤੇ
   production build PR ਉੱਤੇ ਚਲਦੇ ਹਨ। ਕੋਈ ਵਿਆਪਕ suite ਸਥਾਨਕ ਤੌਰ ’ਤੇ ਕੇਵਲ ਉਦੋਂ ਚਲਾਓ ਜਦੋਂ ਕੇਂਦ੍ਰਿਤ failure ਵੱਡੇ ਪ੍ਰਭਾਵ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰੇ ਜਾਂ ਜਦੋਂ ਤਬਦੀਲੀ ਕਈ subsystems ਤੱਕ ਫੈਲੀ ਹੋਵੇ।
5. **ਸਮੀਖਿਆ ਤੋਂ ਪਹਿਲਾਂ ਤਾਲਮੇਲ ਕਰੋ।** ਸਰਗਰਮ base ਨੂੰ fetch ਕਰੋ, ਉਸਦੇ ਨਵੇਂ commits ਅਤੇ ਉਸਦੇ ਮੁਕਾਬਲੇ ਆਪਣੇ diff ਦੀ ਜਾਂਚ ਕਰੋ, ਫਿਰ contributor workflow ਮੁਤਾਬਕ base ਨੂੰ rebase ਜਾਂ merge ਕਰੋ। Generated-file ਅਤੇ catalog conflicts ਨੂੰ ਉਹਨਾਂ ਦੇ ਸਰੋਤ ਤੋਂ ਹੱਲ ਕਰੋ, ਉਹਨਾਂ ਨੂੰ ਮੁੜ generate ਕਰੋ, ਕੇਂਦ੍ਰਿਤ ਚੱਕਰ ਦੁਬਾਰਾ ਚਲਾਓ, ਅਤੇ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ PR ਹਾਲੇ ਵੀ ਸਰਗਰਮ release branch ਨੂੰ target ਕਰਦਾ ਹੈ।
6. **ਸਬੂਤ ਦਰਜ ਕਰੋ।** PR template ਵਿੱਚ ਚਲਾਈਆਂ commands, ਸ਼ਾਮਲ ਜਾਂ ਬਦਲੀ ਗਈ ਹਰ test file, migrations ਜਾਂ feature flags, ਅਤੇ ਹਾਲੇ ਬਕਾਇਆ ਕੋਈ ਵੀ CI-only validation ਸੂਚੀਬੱਧ ਕਰੋ।

## ਤਬਦੀਲੀ ਦੀ ਕਿਸਮ ਅਨੁਸਾਰ ਸੁਨਹਿਰੀ ਮਾਰਗ

ਹੇਠਾਂ ਦਿੱਤੀਆਂ commands ਘੱਟੋ-ਘੱਟ ਕੇਂਦ੍ਰਿਤ ਜਾਂਚਾਂ ਹਨ; ਇਹ ਤੁਹਾਡੇ ਦੁਆਰਾ ਬਦਲੇ ਵਿਹਾਰ ਨੂੰ ਸਿੱਧੇ ਤੌਰ ’ਤੇ ਕਵਰ ਕਰਨ ਵਾਲਾ ਟੈਸਟ ਛੱਡਣ ਦੀ ਇਜਾਜ਼ਤ ਨਹੀਂ ਹਨ।

### Provider

**ਇਕਰਾਰਨਾਮੇ**

- `src/shared/constants/providers/` ਵਿੱਚ Provider definition ਅਤੇ
  `src/shared/constants/providers.ts` ਵਿੱਚ ਇਸਦੀ composition।
- `open-sse/config/providerRegistry.ts` ਜਾਂ ਇਸ ਤੋਂ ਵੱਖ ਕੀਤੀਆਂ registry files ਵਿੱਚ models ਅਤੇ capabilities।
- ਲਾਗੂ ਹੋਣ ’ਤੇ Executor/translator selection, OAuth ਜਾਂ API-key configuration, dashboard assets, ਅਤੇ generated provider reference।
- Public credentials ਲਈ `resolvePublicCred()` ਦੀ ਵਰਤੋਂ ਲਾਜ਼ਮੀ ਹੈ; error responses ਲਈ ਸਾਂਝੇ sanitized error helpers ਦੀ ਵਰਤੋਂ ਲਾਜ਼ਮੀ ਹੈ। `docs/security/PUBLIC_CREDS.md` (git; `/docs` ਵਿੱਚ compile ਨਹੀਂ ਹੁੰਦੀ) ਅਤੇ
  [Error Sanitization](../security/ERROR_SANITIZATION.md) ਵੇਖੋ।

**ਕੇਂਦ੍ਰਿਤ ਚੱਕਰ**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # ਜਦੋਂ catalog ਬਦਲੇ; generated diff ਨੂੰ commit ਕਰੋ
npm run lint
```

ਹਰ ਪ੍ਰਭਾਵਿਤ request family ਦੀ ਵੀ ਜਾਂਚ ਕਰੋ: chat, Responses, images, embeddings, audio, ਜਾਂ video। Generated catalog ਅਤੇ golden diffs ਦੀ ਇਕਰਾਰਨਾਮੇ ਦੀਆਂ ਤਬਦੀਲੀਆਂ ਵਜੋਂ ਸਮੀਖਿਆ ਕਰੋ; ਉਹਨਾਂ ਨੂੰ ਅੰਨ੍ਹੇਵਾਹ ਸਵੀਕਾਰ ਨਾ ਕਰੋ।

### Routing

**ਇਕਰਾਰਨਾਮੇ**

- `src/shared/constants/routingStrategies.ts` ਵਿੱਚ Public strategy values ਅਤੇ UI metadata।
- `open-sse/services/combo.ts` ਅਤੇ `open-sse/services/combo/` ਦੇ ਅਧੀਨ dispatch ਅਤੇ ordering।
- Combo schemas, persistence, resilience state, model capabilities, ਅਤੇ API/UI controls।
- ਵਿਹਾਰ ਬਦਲਣ ’ਤੇ [Auto-Combo Engine](../routing/AUTO-COMBO.md) ਅਤੇ resilience documentation।

**ਕੇਂਦ੍ਰਿਤ ਚੱਕਰ**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy ਜਾਂ dispatch ਦੀਆਂ ਤਬਦੀਲੀਆਂ
npm run check:known-symbols      # strategy registration ਦੀਆਂ ਤਬਦੀਲੀਆਂ
npm run lint
```

ਸਥਾਨਕ ਤੌਰ ’ਤੇ deterministic mocked-upstream tests ਦੀ ਵਰਤੋਂ ਕਰੋ। Live combo smokes ਲਈ credentials ਲੋੜੀਂਦੇ ਹਨ ਅਤੇ ਉਹ manual ਹਨ, CI ਦੇ ਬਦਲ ਨਹੀਂ।

### UI / UX

**ਇਕਰਾਰਨਾਮੇ**

- `src/app/` ਅਤੇ `src/shared/components/` ਦੇ ਅਧੀਨ Next.js route/page ਅਤੇ shared component boundaries।
- API response shapes, loading/empty/error states, keyboard ਅਤੇ screen-reader behavior,
  responsive layout, theming, ਅਤੇ locale expansion।
- `src/i18n/messages/en.json` ਵਿੱਚ English UI source strings; ਨਵੀਂ user-facing copy ਨੂੰ hard-code ਨਾ ਕਰੋ।

**ਕੇਂਦ੍ਰਿਤ ਚੱਕਰ**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction ਜਾਂ visual ਤਬਦੀਲੀਆਂ ਲਈ app ਚਲਾਓ ਅਤੇ narrow ਤੇ wide ਦੋਵਾਂ viewports ਦੀ ਜਾਂਚ ਕਰੋ। CI
production build ਅਤੇ ਵਿਆਪਕ suites ਚਲਾਉਂਦਾ ਹੈ; visual behavior ਲਈ ਫਿਰ ਵੀ ਤਬਦੀਲੀ ਦੇ ਅਨੁਕੂਲ ਕੋਈ ਕੇਂਦ੍ਰਿਤ component, Playwright, ਜਾਂ ਦਸਤਾਵੇਜ਼ਬੱਧ manual check ਲੋੜੀਂਦੀ ਹੈ।

### i18n

**ਇਕਰਾਰਨਾਮੇ**

- `src/i18n/messages/en.json` UI source ਹੈ; `config/i18n.json` locale source ਹੈ।
- CLI catalogs ਵੱਖਰੇ ਤੌਰ ’ਤੇ `bin/cli/locales/` ਦੇ ਅਧੀਨ ਮੌਜੂਦ ਹਨ।
- ICU placeholders ਅਤੇ tags ਨੂੰ ਬਿਲਕੁਲ ਉਸੇ ਤਰ੍ਹਾਂ ਬਰਕਰਾਰ ਰੱਖੋ। Product/provider/model names,
  protocol ਅਤੇ header names, commands, code/JSON identifiers, URLs, environment variables, ਜਾਂ
  `OmniRoute`, `OAuth`, `MCP`, ਅਤੇ `A2A` ਵਰਗੇ protected terms ਦਾ ਅਨੁਵਾਦ ਨਾ ਕਰੋ। ਮੌਜੂਦਾ source list
  `scripts/i18n/glossary/protected-terms.json` ਹੈ।

**ਕੇਂਦ੍ਰਿਤ ਚੱਕਰ**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # ਜਦੋਂ CLI strings/catalogs ਬਦਲਣ
npm run lint
```

ਇਹ ਮੌਜੂਦਾ system ਲਈ ਮਾਰਗਦਰਸ਼ਨ ਹੈ, ਇਸਦੇ tooling ਜਾਂ key model ਨੂੰ ਵਧਾਉਣ ਦਾ ਸੱਦਾ ਨਹੀਂ। ਜਦੋਂ replacement system ਡਿਜ਼ਾਈਨ ਕੀਤਾ ਜਾ ਰਿਹਾ ਹੈ, i18n patches ਨੂੰ ਬਹੁਤ ਸੀਮਿਤ ਅਤੇ ਸਟੀਕ ਰੱਖੋ। ਬਾਹਰੀ services ਨੂੰ call ਕਰਨ ਵਾਲੀਆਂ translation commands ਨਾ ਚਲਾਓ, ਜਦੋਂ ਤੱਕ task ਖਾਸ ਤੌਰ ’ਤੇ generated translations ਦੀ ਮੰਗ ਨਾ ਕਰੇ ਅਤੇ ਤੁਸੀਂ ਨਤੀਜੇ ਵਜੋਂ ਆਏ diff ਦੀ ਸਮੀਖਿਆ ਨਾ ਕਰ ਲਈ ਹੋਵੇ।

### CLI

**ਇਕਰਾਰਨਾਮੇ**

- `bin/cli/` ਵਿੱਚ ਪਬਲਿਕ ਕਮਾਂਡਾਂ ਅਤੇ ਫਲੈਗ, ਜਨਰੇਟ ਕੀਤੀਆਂ API ਕਮਾਂਡਾਂ, ਐਗਜ਼ਿਟ ਕੋਡ, stdout/stderr ਅਤੇ
  JSON ਆਉਟਪੁੱਟ ਸੰਰਚਨਾਵਾਂ, ਕਨਫਿਗਰੇਸ਼ਨ/ਇਨਵਾਇਰਨਮੈਂਟ ਵਿਹਾਰ, ਅਤੇ ਪੈਕੇਜ ਕੀਤੀਆਂ ਫਾਈਲਾਂ।
- CLI ਦੀਆਂ ਯੂਜ਼ਰ-ਫੇਸਿੰਗ ਸਟਰਿੰਗਾਂ ਲਈ CLI i18n ਲੇਅਰ ਦੀ ਵਰਤੋਂ ਲਾਜ਼ਮੀ ਹੈ ਅਤੇ `en`/`pt-BR` ਕੈਟਾਲਾਗ ਇਕਸਾਰ ਰੱਖਣੇ ਲਾਜ਼ਮੀ ਹਨ।
- Node ਨੂੰ ਸਮਰਥਿਤ ਰਨਟਾਈਮ ਵਜੋਂ ਅਤੇ ਪ੍ਰਕਾਸ਼ਿਤ ਬਾਈਨਰੀ ਕਾਂਟ੍ਰੈਕਟ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖੋ।

**ਕੇਂਦਰਿਤ ਲੂਪ**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # ਜਨਰੇਟ ਕੀਤੀਆਂ/ਬੰਡਲ ਕੀਤੀਆਂ CLI ਤਬਦੀਲੀਆਂ
npm run check:pack-policy     # ਪੈਕੇਜ-ਸਰਫੇਸ ਤਬਦੀਲੀਆਂ
npm run lint
```

ਜਦੋਂ ਵਿਹਾਰ ਪਾਰਸਿੰਗ, ਫਾਈਲਾਂ ਜਾਂ ਐਗਜ਼ਿਟ ਸਥਿਤੀ 'ਤੇ ਨਿਰਭਰ ਕਰਦਾ ਹੋਵੇ, ਤਾਂ ਇੱਕ ਅਸਥਾਈ ਡਾਟਾ ਡਾਇਰੈਕਟਰੀ ਵਿੱਚ ਬਿਲਕੁਲ ਸਹੀ ਕਮਾਂਡ ਦੀ ਵਰਤੋਂ ਕਰੋ। CI ਵਧੇਰੇ ਵਿਆਪਕ ਪੈਕੇਜ ਆਰਟੀਫੈਕਟ ਅਤੇ ਇਕੋਸਿਸਟਮ ਜਾਂਚਾਂ ਕਰਦਾ ਹੈ।

### ਡਾਟਾਬੇਸ

**ਕਾਂਟ੍ਰੈਕਟ**

- `src/lib/db/` ਹੇਠਲੇ ਡੋਮੇਨ ਮੋਡੀਊਲ; ਖਾਸ ਮੋਡੀਊਲਾਂ ਨੂੰ ਸਿੱਧੇ ਇੰਪੋਰਟ ਕਰੋ (ਪੁਰਾਣੀ `localDb.ts` ਰੀ-ਐਕਸਪੋਰਟ ਲੇਅਰ ਹਟਾ ਦਿੱਤੀ ਗਈ ਸੀ)।
- `src/lib/db/migrations/` ਹੇਠ ਨੰਬਰਬੱਧ, ਆਈਡੈਂਪੋਟੈਂਟ SQL ਮਾਈਗ੍ਰੇਸ਼ਨਾਂ, ਟ੍ਰਾਂਜ਼ੈਕਸ਼ਨ ਸੁਰੱਖਿਆ, ਅੱਪਗ੍ਰੇਡ
  ਵਿਹਾਰ, ਇੰਡੈਕਸ, ਅਤੇ ਸਕੀਮਾ ਤੋਂ ਪ੍ਰਭਾਵਿਤ ਹਰੇਕ ਕਾਲਰ।
- ਰੂਟ ਅਤੇ ਹੈਂਡਲਰ ਕਦੇ ਵੀ ਸਿੱਧੇ raw SQL ਜਾਰੀ ਨਹੀਂ ਕਰਦੇ।

**ਕੇਂਦਰਿਤ ਲੂਪ**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

ਮਾਈਗ੍ਰੇਸ਼ਨ ਜੋੜਦੇ ਸਮੇਂ ਨਵੇਂ ਡਾਟਾਬੇਸ ਅਤੇ ਪਿਛਲੇ ਸਕੀਮਾ ਤੋਂ ਅੱਪਗ੍ਰੇਡ—ਦੋਵਾਂ ਦੀ ਜਾਂਚ ਕਰੋ। ਡਾਟਾਬੇਸ ਟੈਸਟਾਂ ਲਈ ਹੈਂਡਲ ਬੰਦ ਕਰਨੇ ਅਤੇ ਕਲੀਨਅੱਪ ਦੌਰਾਨ `resetDbInstance()` ਨੂੰ ਕਾਲ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ। `npm run test:bun:db` ਸਿਰਫ਼ ਉਦੋਂ ਚਲਾਓ ਜਦੋਂ best-effort Bun ਅਡੈਪਟਰ ਪਾਥ ਬਦਲਦਾ ਹੈ; Node ਹੀ ਪ੍ਰਮਾਣਿਕ ਰਹਿੰਦਾ ਹੈ।

### ਬਿਲਡ / ਡਿਪਲੌਇ

**ਕਾਂਟ੍ਰੈਕਟ**

- ਰੂਟ ਅਤੇ ਵਰਕਸਪੇਸ ਮੈਨਿਫੈਸਟ/ਲੌਕਫਾਈਲ, `scripts/build/`, Next.js ਸਟੈਂਡਅਲੋਨ ਅਸੈਂਬਲੀ, `dist/`
  ਪੈਕੇਜ ਸਮੱਗਰੀ, Electron ਪਲੇਟਫਾਰਮ ਮੈਟਾਡਾਟਾ, CI ਵਰਕਫਲੋ, ਅਤੇ ਡਿਪਲੌਇਮੈਂਟ ਸੈਂਟੀਨਲ।
- ਸਮਰਥਿਤ Node ਰੇਂਜਾਂ ਅਤੇ `CLAUDE.md` ਵਿੱਚ allow-listed Bun ਦੀ ਵਰਤੋਂ ਨੂੰ ਜਿਉਂ ਦਾ ਤਿਉਂ ਰੱਖਣਾ ਲਾਜ਼ਮੀ ਹੈ।
- ਬਿਲਡ ਆਰਟੀਫੈਕਟ ਟ੍ਰੈਕ ਨਹੀਂ ਕੀਤੇ ਜਾਂਦੇ; ਡਿਪੈਂਡੈਂਸੀ, ਲਾਇਸੈਂਸ, ਵਰਕਫਲੋ ਅਤੇ ਪੈਕੇਜ ਨੀਤੀਆਂ ਲਾਗੂ ਹੁੰਦੀਆਂ ਹਨ।

**ਕੇਂਦਰਿਤ ਲੂਪ**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # ਡਿਪੈਂਡੈਂਸੀ ਜਾਂ ਲੌਕਫਾਈਲ ਤਬਦੀਲੀਆਂ
npm run check:pack-policy      # ਪ੍ਰਕਾਸ਼ਿਤ ਪੈਕੇਜ ਸਰਫੇਸ ਤਬਦੀਲੀਆਂ
npm run lint
```

`npm run build` ਨੂੰ ਲੋਕਲ ਤੌਰ 'ਤੇ ਸਿਰਫ਼ ਉਦੋਂ ਵਰਤੋ ਜਦੋਂ ਤਬਦੀਲੀ ਕੰਪਾਇਲੇਸ਼ਨ, ਸਟੈਂਡਅਲੋਨ ਅਸੈਂਬਲੀ, ਐਸੈੱਟਾਂ ਜਾਂ ਰਨਟਾਈਮ ਬੰਡਲਿੰਗ ਨੂੰ ਪ੍ਰਭਾਵਿਤ ਕਰਦੀ ਹੋਵੇ। `npm run build:release` ਨੂੰ ਸਿਰਫ਼ ਰਿਲੀਜ਼/ਡਿਪਲੌਇ ਵੈਲੀਡੇਸ਼ਨ ਲਈ ਵਰਤੋ। CI ਦਾ ਬਿਲਡ ਆਖਰੀ ਕ੍ਰਾਸ-ਪਲੇਟਫਾਰਮ ਸੰਕੇਤ ਹੈ; ਪਲੇਟਫਾਰਮ-ਵਿਸ਼ੇਸ਼ Electron ਤਬਦੀਲੀਆਂ ਲਈ ਸੰਬੰਧਿਤ ਕੇਂਦਰਿਤ ਬਿਲਡ ਜਾਂ ਸਮੋਕ ਸਬੂਤ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।

## ਸਥਾਨਕ ਲੂਪ ਬਨਾਮ CI

| ਹਰ ਪੈਚ ਲਈ ਸਥਾਨਕ ਤੌਰ 'ਤੇ ਚਲਾਓ                                                   | CI ਵਿਆਪਕ ਸੰਕੇਤ ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ                                  |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| ਉੱਪਰ ਦਿੱਤੇ ਸਿੱਧੇ ਵਿਹਾਰ ਟੈਸਟ ਅਤੇ ਸ਼੍ਰੇਣੀ ਗੇਟ                                    | ਵੰਡਿਆ ਹੋਇਆ ਪੂਰਾ ਯੂਨਿਟ ਸੂਟ ਅਤੇ ਕ੍ਰਮਵਾਰ ਟੈਸਟ                     |
| `npm run lint`                                                                 | Vitest ਸੂਟ ਅਤੇ ਕਵਰੇਜ/ਗੁਣਵੱਤਾ ਰੈਚਿਟ                             |
| ਟਾਈਪ-ਚੈਕ ਜਾਂ ਬਿਲਡ ਕੇਵਲ ਉਦੋਂ, ਜਦੋਂ ਪ੍ਰਭਾਵਿਤ ਕਾਂਟ੍ਰੈਕਟ ਲਈ ਇਸਦੀ ਲੋੜ ਹੋਵੇ          | ਪ੍ਰੋਡਕਸ਼ਨ ਬਿਲਡ, ਸੁਰੱਖਿਆ, ਦਸਤਾਵੇਜ਼, ਡਿਪੈਂਡੈਂਸੀ ਅਤੇ PR-ਨੀਤੀ ਗੇਟ  |
| ਮੈਨੁਅਲ ਇੰਟਰੈਕਸ਼ਨ/ਲਾਈਵ ਜਾਂਚਾਂ ਕੇਵਲ ਉਦੋਂ, ਜਦੋਂ ਆਟੋਮੇਸ਼ਨ ਵਿਹਾਰ ਨੂੰ ਸਾਬਤ ਨਾ ਕਰ ਸਕੇ | ਵਰਕਫ਼ਲੋ ਦੁਆਰਾ ਸੰਰਚਿਤ ਕ੍ਰਾਸ-ਜੌਬ ਇੰਟੀਗ੍ਰੇਸ਼ਨ ਅਤੇ ਪਲੇਟਫਾਰਮ ਜਾਂਚਾਂ |

ਇੱਕ ਸਫਲ ਕੇਂਦ੍ਰਿਤ ਲੂਪ ਬਦਲੇ ਹੋਏ ਕਾਂਟ੍ਰੈਕਟ ਬਾਰੇ ਸਬੂਤ ਹੈ, ਇਹ ਇਸ ਗੱਲ ਦਾ ਪ੍ਰਮਾਣ ਨਹੀਂ ਕਿ ਗੈਰ-ਸੰਬੰਧਿਤ CI ਜਾਂਚਾਂ
ਪਾਸ ਹੋਣਗੀਆਂ। ਇਸਦੇ ਉਲਟ, ਹਰ ਸਥਾਨਕ ਸੋਧ ਨੂੰ ਪੂਰੇ ਰਿਪੋਜ਼ਟਰੀ ਮੈਟ੍ਰਿਕਸ ਦੀ ਉਡੀਕ ਨਾ ਕਰਵਾਓ।

## ਮੇਲ-ਮਿਲਾਪ ਜਾਂਚ-ਸੂਚੀ

ਸਮੀਖਿਆ ਦੀ ਬੇਨਤੀ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ:

- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ PR ਬੇਸ ਹਾਲੇ ਵੀ ਸਭ ਤੋਂ ਉੱਚੀ ਸਰਗਰਮ `release/v*` ਬ੍ਰਾਂਚ ਹੈ।
- ਉਸ ਬੇਸ ਨੂੰ ਫੈਚ ਕਰੋ ਅਤੇ ਤੁਹਾਡੇ ਵੱਲੋਂ ਬ੍ਰਾਂਚ ਬਣਾਉਣ ਤੋਂ ਬਾਅਦ ਸ਼ਾਮਲ ਹੋਏ ਕਮਿਟਾਂ ਦੀ ਸਮੀਖਿਆ ਕਰੋ।
- ਅਣਜਾਣੇ ਜਾਂ ਜਨਰੇਟ ਹੋਏ ਬੇਲੋੜੇ ਬਦਲਾਵਾਂ ਲਈ `git diff <active-base>...HEAD` ਦੀ ਸਮੀਖਿਆ ਕਰੋ।
- ਸਰੋਤ ਨੂੰ ਅੱਪਡੇਟ ਕਰਕੇ ਅਤੇ ਆਉਟਪੁੱਟ ਨੂੰ ਮੁੜ ਜਨਰੇਟ ਕਰਕੇ ਕੈਟਾਲੌਗ ਅਤੇ ਜਨਰੇਟ ਕੀਤੇ ਦਸਤਾਵੇਜ਼ਾਂ ਦੇ ਟਕਰਾਅ ਹੱਲ ਕਰੋ।
- ਮੇਲ-ਮਿਲਾਪ ਤੋਂ ਬਾਅਦ PR ਵੇਰਵੇ ਵਿੱਚ ਸੂਚੀਬੱਧ ਹਰੇਕ ਕੇਂਦ੍ਰਿਤ ਟੈਸਟ/ਗੇਟ ਨੂੰ ਮੁੜ ਚਲਾਓ।
- ਬਦਲੇ ਹੋਏ ਬੇਸ ਨਾਲ ਮੇਲ ਕਰਨ ਲਈ ਕਦੇ ਵੀ ਅਸਰਸ਼ਨਾਂ ਨੂੰ ਕਮਜ਼ੋਰ ਨਾ ਕਰੋ ਜਾਂ ਲੋੜੀਂਦੇ ਟੈਸਟ ਨਾ ਹਟਾਓ।

ਰਿਲੀਜ਼-ਫ਼੍ਰੀਜ਼ ਅਤੇ ਰੀਟਾਰਗੇਟਿੰਗ ਨਿਯਮਾਂ ਲਈ,
[ਬ੍ਰਾਂਚਿੰਗ ਅਤੇ ਰਿਲੀਜ਼ ਮਾਡਲ](BRANCHING_MODEL.md) ਵਰਤੋ। ਪੂਰੀ CI ਸੂਚੀ ਲਈ,
[ਕੁਆਲਿਟੀ ਗੇਟਸ ਹਵਾਲਾ](../architecture/QUALITY_GATES.md) ਵਰਤੋ।
