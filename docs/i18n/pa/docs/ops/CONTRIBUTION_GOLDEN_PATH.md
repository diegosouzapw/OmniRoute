ਇੱਕ pull request ਲਈ ਸਭ ਤੋਂ ਛੋਟਾ ਭਰੋਸੇਯੋਗ ਡਿਵੈਲਪਮੈਂਟ ਲੂਪ ਚੁਣਨ ਵਾਸਤੇ ਇਸ ਗਾਈਡ ਦੀ ਵਰਤੋਂ ਕਰੋ। ਇਹ ਹੇਠਾਂ ਲਿੰਕ ਕੀਤੇ ਖੇਤਰ-ਵਿਸ਼ੇਸ਼ ਆਰਕੀਟੈਕਚਰ ਅਤੇ ਸੁਰੱਖਿਆ ਦਸਤਾਵੇਜ਼ਾਂ ਦੀ
ਥਾਂ ਨਹੀਂ ਲੈਂਦੀ; ਇਹ ਹਰ ਆਮ ਤਬਦੀਲੀ ਦੀ ਕਿਸਮ ਨੂੰ ਉਸਦੇ ਕਾਂਟ੍ਰੈਕਟਾਂ, ਕੇਂਦਰਿਤ ਜਾਂਚਾਂ ਅਤੇ CI ਕਵਰੇਜ ਨਾਲ ਜੋੜਦੀ ਹੈ।

## ਹਰ ਤਬਦੀਲੀ ਵੱਲੋਂ ਅਪਣਾਇਆ ਜਾਣ ਵਾਲਾ ਰਾਹ

1. **ਸੰਪਾਦਨ ਤੋਂ ਪਹਿਲਾਂ ਬੇਸ ਚੁਣੋ।** ਸਭ ਤੋਂ ਉੱਚੀ ਸਰਗਰਮ `release/v*` ਬ੍ਰਾਂਚ ਲੱਭੋ ਅਤੇ ਉਸਦੇ
   ਸਿਰੇ ਤੋਂ ਬ੍ਰਾਂਚ ਬਣਾਓ। ਉਸ ਬ੍ਰਾਂਚ ਨੂੰ ਟਾਰਗੇਟ ਕਰੋ, `main` ਨੂੰ ਨਹੀਂ। ਜੇ ਰਿਲੀਜ਼ ਫ੍ਰੀਜ਼ ਸਰਗਰਮ ਹੈ, ਤਾਂ ਫ੍ਰੀਜ਼ ਕੀਤੀ
   ਬ੍ਰਾਂਚ ਨੂੰ ਟਾਰਗੇਟ ਨਾ ਕਰੋ; ਇਸ ਵਿੱਚ ਵਰਣਿਤ ਅਗਲੇ ਸਰਗਰਮ ਚੱਕਰ ਦੀ ਵਰਤੋਂ ਕਰੋ:
   [ਬ੍ਰਾਂਚਿੰਗ ਅਤੇ ਰਿਲੀਜ਼ ਮਾਡਲ](BRANCHING_MODEL.md)।
2. **ਕਾਂਟ੍ਰੈਕਟਾਂ ਦੇ ਨਾਮ ਦਿਓ।** ਹਰ ਉਸ ਕੈਟਾਲਾਗ, ਸਕੀਮਾ, ਜਨਰੇਟ ਕੀਤੇ ਆਰਟੀਫੈਕਟ, ਪਬਲਿਕ API ਜਾਂ ਯੂਜ਼ਰ
   ਇੰਟਰਫੇਸ ਦੀ ਪਛਾਣ ਕਰੋ ਜਿਸਨੂੰ ਤਬਦੀਲੀ ਪ੍ਰਭਾਵਿਤ ਕਰਦੀ ਹੈ। ਹੇਠਾਂ ਦਿੱਤੀ ਸਾਰਣੀ ਘੱਟੋ-ਘੱਟ ਸ਼ੁਰੂਆਤੀ ਸੈੱਟ ਦਿੰਦੀ ਹੈ।
3. **ਕੇਂਦਰਿਤ ਟੈਸਟ ਲਿਖੋ ਜਾਂ ਅੱਪਡੇਟ ਕਰੋ।** `src/`, `open-sse/`, `electron/`, ਜਾਂ
   `bin/` ਵਿੱਚ ਪ੍ਰੋਡਕਸ਼ਨ ਤਬਦੀਲੀਆਂ ਲਈ ਉਸੇ PR ਵਿੱਚ ਇੱਕ ਆਟੋਮੇਟਡ ਟੈਸਟ ਲੋੜੀਂਦਾ ਹੈ। ਪਹਿਲਾਂ ਉਹ ਸਭ ਤੋਂ ਛੋਟੀਆਂ ਟੈਸਟ ਫਾਈਲਾਂ ਚਲਾਓ ਜੋ
   ਵਿਹਾਰ ਨੂੰ ਸਾਬਤ ਕਰਦੀਆਂ ਹਨ, ਫਿਰ ਸੂਚੀਬੱਧ ਕੇਂਦਰਿਤ ਗੇਟ ਚਲਾਓ।
4. **CI ਨੂੰ ਵਿਸਤ੍ਰਿਤ ਮੈਟ੍ਰਿਕਸ ਚਲਾਉਣ ਦਿਓ।** ਸੰਪੂਰਨ ਯੂਨਿਟ ਸ਼ਾਰਡ, Vitest, ਕਵਰੇਜ ਰੈਚਟ ਅਤੇ
   ਪ੍ਰੋਡਕਸ਼ਨ ਬਿਲਡ PR ਉੱਤੇ ਚੱਲਦੇ ਹਨ। ਕੋਈ ਵਿਸਤ੍ਰਿਤ ਸੂਟ ਸਥਾਨਕ ਤੌਰ ’ਤੇ ਸਿਰਫ਼ ਉਦੋਂ ਚਲਾਓ ਜਦੋਂ ਕੋਈ ਕੇਂਦਰਿਤ ਅਸਫਲਤਾ
   ਵੱਧ ਪ੍ਰਭਾਵ ਵੱਲ ਸੰਕੇਤ ਕਰਦੀ ਹੋਵੇ ਜਾਂ ਜਦੋਂ ਤਬਦੀਲੀ ਕਈ ਸਬਸਿਸਟਮਾਂ ਤੱਕ ਫੈਲੀ ਹੋਵੇ।
5. **ਸਮੀਖਿਆ ਤੋਂ ਪਹਿਲਾਂ ਮਿਲਾਣ ਕਰੋ।** ਸਰਗਰਮ ਬੇਸ ਨੂੰ ਫੈਚ ਕਰੋ, ਇਸਦੇ ਨਵੇਂ ਕਮਿਟਾਂ ਅਤੇ ਇਸਦੇ ਮੁਕਾਬਲੇ ਆਪਣੇ ਡਿਫ਼ ਦੀ
   ਜਾਂਚ ਕਰੋ, ਫਿਰ ਯੋਗਦਾਨਕਰਤਾ ਵਰਕਫ਼ਲੋ ਅਨੁਸਾਰ ਬੇਸ ਨੂੰ ਰੀਬੇਸ ਜਾਂ ਮਰਜ ਕਰੋ। ਜਨਰੇਟ ਕੀਤੀਆਂ ਫਾਈਲਾਂ
   ਅਤੇ ਕੈਟਾਲਾਗ ਦੇ ਟਕਰਾਵਾਂ ਨੂੰ ਉਨ੍ਹਾਂ ਦੇ ਸਰੋਤ ਤੋਂ ਹੱਲ ਕਰੋ, ਉਨ੍ਹਾਂ ਨੂੰ ਮੁੜ ਜਨਰੇਟ ਕਰੋ, ਕੇਂਦਰਿਤ ਲੂਪ ਮੁੜ ਚਲਾਓ ਅਤੇ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ
   PR ਹਾਲੇ ਵੀ ਸਰਗਰਮ ਰਿਲੀਜ਼ ਬ੍ਰਾਂਚ ਨੂੰ ਟਾਰਗੇਟ ਕਰਦਾ ਹੈ।
6. **ਸਬੂਤ ਦਰਜ ਕਰੋ।** PR ਟੈਂਪਲੇਟ ਵਿੱਚ ਚਲਾਈਆਂ ਗਈਆਂ ਕਮਾਂਡਾਂ, ਜੋੜੀ ਜਾਂ ਬਦਲੀ ਗਈ ਹਰ ਟੈਸਟ ਫਾਈਲ,
   ਮਾਈਗ੍ਰੇਸ਼ਨਾਂ ਜਾਂ ਫੀਚਰ ਫਲੈਗਾਂ ਅਤੇ ਹਾਲੇ ਬਾਕੀ ਕਿਸੇ ਵੀ ਕੇਵਲ-CI ਵੈਲੀਡੇਸ਼ਨ ਦੀ ਸੂਚੀ ਦਿਓ।

## ਤਬਦੀਲੀ ਦੀ ਕਿਸਮ ਅਨੁਸਾਰ ਮਿਆਰੀ ਰਾਹ

ਹੇਠਾਂ ਦਿੱਤੀਆਂ ਕਮਾਂਡਾਂ ਘੱਟੋ-ਘੱਟ ਕੇਂਦਰਿਤ ਜਾਂਚਾਂ ਹਨ, ਉਸ ਟੈਸਟ ਨੂੰ ਛੱਡਣ ਦੀ ਇਜਾਜ਼ਤ ਨਹੀਂ ਜੋ ਤੁਹਾਡੇ
ਬਦਲੇ ਵਿਹਾਰ ਨੂੰ ਸਿੱਧੇ ਤੌਰ ’ਤੇ ਕਵਰ ਕਰਦਾ ਹੈ।

### ਪ੍ਰੋਵਾਈਡਰ

**ਕਾਂਟ੍ਰੈਕਟ**

- `src/shared/constants/providers/` ਵਿੱਚ ਪ੍ਰੋਵਾਈਡਰ ਦੀ ਪਰਿਭਾਸ਼ਾ ਅਤੇ
  `src/shared/constants/providers.ts` ਵਿੱਚ ਇਸਦੀ ਸੰਰਚਨਾ।
- `open-sse/config/providerRegistry.ts` ਜਾਂ ਇਸਦੀਆਂ ਵੱਖ ਕੀਤੀਆਂ ਰਜਿਸਟਰੀ ਫਾਈਲਾਂ ਵਿੱਚ ਮਾਡਲ ਅਤੇ ਸਮਰੱਥਾਵਾਂ।
- ਲਾਗੂ ਹੋਣ ’ਤੇ ਐਗਜ਼ੀਕਿਊਟਰ/ਟਰਾਂਸਲੇਟਰ ਚੋਣ, OAuth ਜਾਂ API-key ਸੰਰਚਨਾ, ਡੈਸ਼ਬੋਰਡ ਐਸੈੱਟ ਅਤੇ ਜਨਰੇਟ ਕੀਤਾ
  ਪ੍ਰੋਵਾਈਡਰ ਹਵਾਲਾ।
- ਪਬਲਿਕ ਕ੍ਰੈਡੈਂਸ਼ਲਾਂ ਲਈ `resolvePublicCred()` ਵਰਤਣਾ ਲਾਜ਼ਮੀ ਹੈ; ਗਲਤੀ ਜਵਾਬਾਂ ਲਈ ਸਾਂਝੇ ਸੈਨੀਟਾਈਜ਼ਡ
  ਐਰਰ ਹੈਲਪਰ ਵਰਤਣੇ ਲਾਜ਼ਮੀ ਹਨ। `docs/security/PUBLIC_CREDS.md` (git; `/docs` ਵਿੱਚ ਕੰਪਾਇਲ ਨਹੀਂ ਕੀਤਾ ਗਿਆ) ਅਤੇ
  [ਗਲਤੀ ਸੈਨੀਟਾਈਜ਼ੇਸ਼ਨ](../security/ERROR_SANITIZATION.md) ਵੇਖੋ।

**ਕੇਂਦਰਿਤ ਲੂਪ**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # ਜਦੋਂ ਕੈਟਾਲਾਗ ਬਦਲਦਾ ਹੈ; ਜਨਰੇਟ ਕੀਤਾ ਡਿਫ਼ ਕਮਿਟ ਕਰੋ
npm run lint
```

ਹਰ ਪ੍ਰਭਾਵਿਤ ਰਿਕਵੇਸਟ ਪਰਿਵਾਰ ਦੀ ਵੀ ਜਾਂਚ ਕਰੋ: ਚੈਟ, Responses, ਚਿੱਤਰ, ਐਮਬੈਡਿੰਗ, ਆਡੀਓ ਜਾਂ ਵੀਡੀਓ।
ਜਨਰੇਟ ਕੀਤੇ ਕੈਟਾਲਾਗ ਅਤੇ ਗੋਲਡਨ ਡਿਫ਼ਾਂ ਦੀ ਕਾਂਟ੍ਰੈਕਟ ਤਬਦੀਲੀਆਂ ਵਜੋਂ ਸਮੀਖਿਆ ਕਰੋ; ਉਨ੍ਹਾਂ ਨੂੰ ਅੰਨ੍ਹੇਵਾਹ ਸਵੀਕਾਰ ਨਾ ਕਰੋ।

### ਰਾਊਟਿੰਗ

**ਕਾਂਟ੍ਰੈਕਟ**

- `src/shared/constants/routingStrategies.ts` ਵਿੱਚ ਪਬਲਿਕ ਸਟ੍ਰੈਟਜੀ ਮੁੱਲ ਅਤੇ UI ਮੈਟਾਡੇਟਾ।
- `open-sse/services/combo.ts` ਅਤੇ `open-sse/services/combo/` ਅਧੀਨ ਡਿਸਪੈਚ ਅਤੇ ਕ੍ਰਮਬੱਧਤਾ।
- ਕਾਂਬੋ ਸਕੀਮਾ, ਪਰਸਿਸਟੈਂਸ, ਰੈਜ਼ੀਲਿਅੰਸ ਸਥਿਤੀ, ਮਾਡਲ ਸਮਰੱਥਾਵਾਂ ਅਤੇ API/UI ਕੰਟਰੋਲ।
- ਵਿਹਾਰ ਬਦਲਣ ’ਤੇ [ਆਟੋ-ਕਾਂਬੋ ਇੰਜਣ](../routing/AUTO-COMBO.md) ਅਤੇ ਰੈਜ਼ੀਲਿਅੰਸ ਦਸਤਾਵੇਜ਼।

**ਕੇਂਦਰਿਤ ਲੂਪ**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ਸਟ੍ਰੈਟਜੀ ਜਾਂ ਡਿਸਪੈਚ ਤਬਦੀਲੀਆਂ
npm run check:known-symbols      # ਸਟ੍ਰੈਟਜੀ ਰਜਿਸਟ੍ਰੇਸ਼ਨ ਤਬਦੀਲੀਆਂ
npm run lint
```

ਸਥਾਨਕ ਤੌਰ ’ਤੇ ਨਿਰਧਾਰਿਤ ਨਤੀਜੇ ਦੇਣ ਵਾਲੇ ਮੌਕਡ-ਅੱਪਸਟ੍ਰੀਮ ਟੈਸਟ ਵਰਤੋ। ਲਾਈਵ ਕਾਂਬੋ ਸਮੋਕ ਟੈਸਟਾਂ ਲਈ ਕ੍ਰੈਡੈਂਸ਼ਲ ਲੋੜੀਂਦੇ ਹਨ ਅਤੇ ਇਹ
ਮੈਨੂਅਲ ਹਨ, CI ਦੇ ਬਦਲ ਨਹੀਂ।

### UI / UX

**ਕਾਂਟ੍ਰੈਕਟ**

- `src/app/` ਅਤੇ `src/shared/components/` ਅਧੀਨ Next.js ਰੂਟ/ਪੇਜ ਅਤੇ ਸਾਂਝੇ ਕੰਪੋਨੈਂਟ ਦੀਆਂ ਹੱਦਾਂ।
- API ਜਵਾਬਾਂ ਦੇ ਆਕਾਰ, ਲੋਡਿੰਗ/ਖਾਲੀ/ਗਲਤੀ ਸਥਿਤੀਆਂ, ਕੀਬੋਰਡ ਅਤੇ ਸਕ੍ਰੀਨ-ਰੀਡਰ ਵਿਹਾਰ,
  ਰਿਸਪਾਂਸਿਵ ਲੇਆਉਟ, ਥੀਮਿੰਗ ਅਤੇ ਲੋਕੇਲ ਵਿਸਥਾਰ।

## ਸਥਾਨਕ ਕੈਂਡੀਡੇਟ ਲੂਪ

ਸਰੋਤ ਟੈਸਟ ਇਹ ਸਾਬਤ ਨਹੀਂ ਕਰ ਸਕਦੇ ਕਿ ਪੈਕੇਜ ਕੀਤਾ ਆਰਟੀਫੈਕਟ ਚਾਲੂ ਹੁੰਦਾ ਹੈ: ਪੈਕੇਜਿੰਗ ਸੂਚੀਆਂ, ਹਟਾਈਆਂ ਗਈਆਂ ਡਿਪੈਂਡੈਂਸੀਆਂ,
ਅਤੇ ਨੇਟਿਵ ਬਾਈਨਰੀਆਂ ਸਿਰਫ਼ ਉਦੋਂ ਅਸਫਲ ਹੁੰਦੀਆਂ ਹਨ ਜਦੋਂ tarball ਨੂੰ ਇੰਸਟਾਲ ਕਰਕੇ ਚਲਾਇਆ ਜਾਂਦਾ ਹੈ। `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) RFC #8084 ਦੇ ਇੱਕ ਵਾਰ ਬਿਲਡ ਕਰੋ / ਪ੍ਰਮਾਣਿਤ ਕਰੋ / ਪ੍ਰਮੋਟ ਕਰੋ ਪ੍ਰਵਾਹ ਦਾ ਸਥਾਨਕ ਹਿੱਸਾ ਹੈ:
ਇਹ ਇੱਕ ਕੈਂਡੀਡੇਟ ਬਿਲਡ ਕਰਦਾ ਹੈ, ਉਸੇ ਆਰਟੀਫੈਕਟ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ, ਡਾਇਰੈਕਟਰੀਆਂ ਦੇ ਨਾਮ ਬਦਲ ਕੇ ਇਸਨੂੰ
ਪ੍ਰਮੋਟ ਕਰਦਾ ਹੈ, ਅਤੇ ਜਦੋਂ ਪ੍ਰਮੋਟ ਕੀਤਾ ਸਲਾਟ ਆਪਣੀ ਸਿਹਤ ਜਾਂਚ ਵਿੱਚ ਅਸਫਲ ਹੁੰਦਾ ਹੈ ਤਾਂ ਇਸਨੂੰ ਵਾਪਸ ਰੋਲ ਕਰਦਾ ਹੈ।

```bash
npm run dev:candidate -- run --dry-run --json  # ਯੋਜਨਾ ਪ੍ਰਿੰਟ ਕਰੋ, ਕੁਝ ਵੀ ਨਾ ਬਦਲੋ
npm run dev:candidate -- run                   # ਬਿਲਡ + ਪ੍ਰਮਾਣਿਤ + ਪ੍ਰਮੋਟ, ਸਵੈਚਲਿਤ ਰੋਲਬੈਕ
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ ਵਿੱਚ ਇੰਸਟਾਲ ਕਰੋ
npm run dev:candidate -- validate --id <id>    # ਇੱਕ ਖਾਲੀ ਪੋਰਟ ਉੱਤੇ ਬੂਟ ਕਰੋ, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current ਅਤੇ previous ਨੂੰ ਆਪਸ ਵਿੱਚ ਬਦਲੋ
npm run dev:candidate -- run --from-tarball <file.tgz>  # ਹੋਰ ਕਿਤੇ (CI) ਬਿਲਡ ਕੀਤਾ tarball ਮੁੜ ਵਰਤੋ
```

- **ਇੱਕ ਵਾਰ ਬਿਲਡ ਕਰੋ।** `build` ਮੌਜੂਦਾ ਟ੍ਰੀ ਨੂੰ ਪੈਕ ਕਰਦਾ ਹੈ (ਇਸਨੂੰ `dist/server.js` ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ, ਇਸ ਲਈ ਪਹਿਲਾਂ
  `npm run build:release` ਚਲਾਓ) ਜਾਂ `--from-tarball` ਨੂੰ ਕਾਪੀ ਕਰਦਾ ਹੈ, ਫਿਰ tarball ਨੂੰ ਇੱਕ
  ਅਲੱਗ npm prefix ਵਿੱਚ ਇੰਸਟਾਲ ਕਰਦਾ ਹੈ, ਕਿਉਂਕਿ tarball ਵਿੱਚ ਕੋਈ `node_modules` ਨਹੀਂ ਹੁੰਦਾ। ਆਈਡੀ ਛੋਟਾ `HEAD`
  sha ਹੁੰਦਾ ਹੈ (ਜਦੋਂ ਟ੍ਰੀ ਵਿੱਚ ਸਥਾਨਕ ਤਬਦੀਲੀਆਂ ਹੋਣ ਤਾਂ `-dirty`) ਜਾਂ tarball ਲਈ `tgz-<sha256>`। ਪਹਿਲਾਂ ਹੀ
  ਬਿਲਡ ਕੀਤੀ ਸਾਫ਼ ਆਈਡੀ ਨੂੰ ਦੁਬਾਰਾ ਬਿਲਡ ਕਰਨ ਦੀ ਬਜਾਏ ਮੁੜ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ; ਇਸਨੂੰ ਮੁੜ ਬਿਲਡ ਕਰਨ ਲਈ `--force` ਦਿਓ।
- **ਸਰੋਤ ਨੂੰ ਨਹੀਂ, ਪੈਕੇਜ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਕਰੋ।** `validate` ਇੰਸਟਾਲ ਕੀਤੇ CLI ਨੂੰ
  (`serve --port <free port>`) ਇੱਕ ਨਵੇਂ `DATA_DIR=<candidate>/data`, ਨਕਲੀ ਸੀਕ੍ਰੇਟਾਂ ਨਾਲ, ਅਤੇ ਓਪਰੇਟਰ ਦੇ
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` ਅਤੇ `INITIAL_PASSWORD` ਨੂੰ ਵਾਤਾਵਰਨ ਵਿੱਚੋਂ ਹਟਾ ਕੇ ਚਲਾਉਂਦਾ ਹੈ,
  ਤਾਂ ਜੋ ਇਹ ਇੱਕ ਨਵੀਂ ਇੰਸਟਾਲੇਸ਼ਨ ਦੀ ਕੁੰਜੀ-ਰਹਿਤ ਲੂਪਬੈਕ ਸਥਿਤੀ ਦੀ ਜਾਂਚ ਕਰੇ। ਇਹ
  `GET /api/health` ਵੱਲੋਂ 200 ਵਾਪਸ ਕਰਨ ਦੀ ਉਡੀਕ ਕਰਦਾ ਹੈ, `GET /v1/models` ਵੱਲੋਂ 200 ਵਾਪਸ ਕਰਨਾ ਲਾਜ਼ਮੀ ਬਣਾਉਂਦਾ ਹੈ, ਪ੍ਰਕਿਰਿਆ ਸਮੂਹ ਨੂੰ ਰੋਕਦਾ ਹੈ,
  ਅਤੇ tarball ਹੈਸ਼ ਦੇ ਨਾਲ ਫ਼ੈਸਲੇ ਨੂੰ `validation.json` ਵਿੱਚ ਦਰਜ ਕਰਦਾ ਹੈ।
- **ਉਸੇ ਆਰਟੀਫੈਕਟ ਨੂੰ ਪ੍ਰਮੋਟ ਕਰੋ।** `promote` ਅਜਿਹੇ ਕੈਂਡੀਡੇਟ ਨੂੰ ਅਸਵੀਕਾਰ ਕਰਦਾ ਹੈ ਜਿਸਦੇ
  ਮੌਜੂਦਾ tarball ਹੈਸ਼ ਲਈ ਸਫਲ ਪ੍ਰਮਾਣੀਕਰਨ ਨਾ ਹੋਵੇ। ਮੂਲ ਸਰਗਰਮ ਸਲਾਟ `_artifacts/candidate/current` ਹੈ; `--target <dir>`
  ਉਸੇ ਫ਼ਾਈਲ-ਸਿਸਟਮ ਉੱਤੇ ਇੱਕ ਹੋਰ ਡਾਇਰੈਕਟਰੀ ਚੁਣਦਾ ਹੈ, ਅਤੇ ਇਸਦਾ ਪਿਛਲਾ ਸਲਾਟ `<dir>.previous` ਹੁੰਦਾ ਹੈ।
  ਹਰ ਨਾਮ-ਬਦਲੀ ਐਟਾਮਿਕ ਹੁੰਦੀ ਹੈ, ਅਤੇ ਪ੍ਰਕਿਰਿਆ ਦੇ ਵਿਚਕਾਰ ਆਈ ਅਸਫਲਤਾ ਪਹਿਲਾਂ ਹੀ ਹੋ ਚੁੱਕੀਆਂ ਨਾਮ-ਬਦਲੀਆਂ ਨੂੰ ਉਲਟਾ ਦਿੰਦੀ ਹੈ।
- **ਵਾਪਸ ਰੋਲ ਕਰੋ।** `run` ਪ੍ਰਮੋਟ ਕੀਤੇ ਸਲਾਟ ਨੂੰ ਦੁਬਾਰਾ ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ ਅਤੇ ਜਦੋਂ
  ਉਹ ਜਾਂਚ ਅਸਫਲ ਹੁੰਦੀ ਹੈ ਤਾਂ `current` ਅਤੇ `previous` ਨੂੰ ਵਾਪਸ ਆਪਸ ਵਿੱਚ ਬਦਲ ਦਿੰਦਾ ਹੈ। ਪਹਿਲੇ ਪ੍ਰਮਾਣੀਕਰਨ ਵਿੱਚ ਅਸਫਲ ਹੋਣ ਵਾਲਾ ਕੈਂਡੀਡੇਟ ਕਦੇ ਵੀ ਪ੍ਰਮੋਟ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ।

ਸਭ ਕੁਝ git ਵੱਲੋਂ ਅਣਡਿੱਠੀ `_artifacts/candidate/` ਦੇ ਅਧੀਨ ਲਿਖਿਆ ਜਾਂਦਾ ਹੈ; ਮੌਜੂਦਾ OmniRoute
ਇੰਸਟਾਲੇਸ਼ਨ ਅਤੇ ਇਸਦੀ ਡਾਟਾ ਡਾਇਰੈਕਟਰੀ ਨੂੰ ਕਦੇ ਛੂਹਿਆ ਨਹੀਂ ਜਾਂਦਾ। ਪ੍ਰਮੋਟ ਕੀਤਾ CLI
`_artifacts/candidate/current/prefix/bin/omniroute` ਹੈ; ਇਸਨੂੰ ਵਰਤਣ ਵੇਲੇ ਆਪਣੇ `DATA_DIR` ਨਾਲ ਚਲਾਓ।
ਐਗਜ਼ਿਟ ਕੋਡ: `0` ਸਫਲਤਾ, `1` ਅਸਫਲ ਪ੍ਰਮਾਣੀਕਰਨ ਜਾਂ ਪ੍ਰਮੋਸ਼ਨ, `2` ਵਰਤੋਂ ਦੀ ਗਲਤੀ ਜਾਂ ਗੁੰਮ ਬਿਲਡ।

## ਮੇਲ-ਮਿਲਾਪ ਜਾਂਚ-ਸੂਚੀ

ਸਮੀਖਿਆ ਦੀ ਬੇਨਤੀ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ:

- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ PR ਬੇਸ ਅਜੇ ਵੀ ਸਭ ਤੋਂ ਉੱਚੀ ਸਰਗਰਮ `release/v*` ਬ੍ਰਾਂਚ ਹੈ।
- ਉਸ ਬੇਸ ਨੂੰ ਫੈਚ ਕਰੋ ਅਤੇ ਤੁਹਾਡੇ ਵੱਲੋਂ ਬ੍ਰਾਂਚ ਬਣਾਉਣ ਤੋਂ ਬਾਅਦ ਸ਼ਾਮਲ ਹੋਏ ਕਮਿਟਾਂ ਦੀ ਸਮੀਖਿਆ ਕਰੋ।
- ਅਣਜਾਣੇ ਜਾਂ ਜਨਰੇਟ ਕੀਤੇ ਬੇਲੋੜੇ ਬਦਲਾਵਾਂ ਲਈ `git diff <active-base>...HEAD` ਦੀ ਸਮੀਖਿਆ ਕਰੋ।
- ਸਰੋਤ ਨੂੰ ਅੱਪਡੇਟ ਕਰਕੇ ਅਤੇ ਆਉਟਪੁੱਟ ਮੁੜ ਜਨਰੇਟ ਕਰਕੇ ਕੈਟਾਲੌਗ ਅਤੇ ਜਨਰੇਟ ਕੀਤੇ ਦਸਤਾਵੇਜ਼ਾਂ ਦੇ ਟਕਰਾਅ ਹੱਲ ਕਰੋ।
- ਮੇਲ-ਮਿਲਾਪ ਤੋਂ ਬਾਅਦ PR ਵੇਰਵੇ ਵਿੱਚ ਸੂਚੀਬੱਧ ਹਰ ਫੋਕਸਡ ਟੈਸਟ/ਗੇਟ ਨੂੰ ਮੁੜ ਚਲਾਓ।
- ਬਦਲੇ ਹੋਏ ਬੇਸ ਨਾਲ ਮੇਲ ਕਰਨ ਲਈ ਕਦੇ ਵੀ ਅਸਰਸ਼ਨਾਂ ਨੂੰ ਕਮਜ਼ੋਰ ਨਾ ਕਰੋ ਜਾਂ ਲੋੜੀਂਦੇ ਟੈਸਟ ਨਾ ਹਟਾਓ।

ਰਿਲੀਜ਼-ਫ੍ਰੀਜ਼ ਅਤੇ ਰੀਟਾਰਗੇਟਿੰਗ ਨਿਯਮਾਂ ਲਈ,
[ਬ੍ਰਾਂਚਿੰਗ ਅਤੇ ਰਿਲੀਜ਼ ਮਾਡਲ](BRANCHING_MODEL.md) ਵਰਤੋ। ਪੂਰੀ CI ਸੂਚੀ ਲਈ,
[ਗੁਣਵੱਤਾ ਗੇਟ ਹਵਾਲਾ](../architecture/QUALITY_GATES.md) ਵਰਤੋ।
