`open-sse/config/providerPluginManifest.ts` JSON-ਸੁਰੱਖਿਅਤ ਪ੍ਰਦਾਤਾ
ਪਲੱਗਇਨ ਕਾਂਟ੍ਰੈਕਟ ਨੂੰ ਪਰਿਭਾਸ਼ਿਤ ਕਰਦੀ ਹੈ। `open-sse/config/providerPluginManifestRegistry.ts` ਉਸ
ਕਾਂਟ੍ਰੈਕਟ ਨੂੰ Bifrost, CLIProxyAPI, ਜਾਂ ਭਵਿੱਖ ਦੇ Go/Rust ਰਾਊਟਰ ਵਰਗੇ ਸਾਈਡਕਾਰਾਂ ਲਈ
ਮੌਜੂਦਾ ਪ੍ਰਦਾਤਾ ਰਜਿਸਟਰੀ ਨਾਲ ਜੋੜਦੀ ਹੈ। TypeScript ਰਜਿਸਟਰੀ ਸੱਚਾਈ ਦਾ
ਮੂਲ ਸਰੋਤ ਰਹਿੰਦੀ ਹੈ, ਪਰ ਸਾਈਡਕਾਰ ਐਗਜ਼ਿਕਿਊਟਰ ਕੋਡ, OAuth ਡਿਫਾਲਟਾਂ, ਹੈਡਰਾਂ, ਜਾਂ
ਪ੍ਰਕਿਰਿਆ ਵਾਤਾਵਰਨ ਸਥਿਤੀ ਨੂੰ ਇੰਪੋਰਟ ਕੀਤੇ ਬਿਨਾਂ ਮੈਨੀਫੈਸਟ ਦੀ ਵਰਤੋਂ ਕਰ ਸਕਦੇ ਹਨ।

ਇਹੀ ਮੈਨੀਫੈਸਟ HTTP ਰਾਹੀਂ
`GET /api/v1/provider-plugin-manifest` ਉੱਤੇ ਵੀ ਉਪਲਬਧ ਹੈ, ਉਹਨਾਂ ਸਾਈਡਕਾਰਾਂ ਲਈ ਜੋ ਪ੍ਰਕਿਰਿਆ ਤੋਂ ਬਾਹਰ ਚੱਲਦੇ ਹਨ।

OmniRoute ਉਸ URL ਨੂੰ Bifrost ਅਤੇ CLIProxyAPI ਲਈ
`X-OmniRoute-Provider-Manifest-Url` ਬੇਨਤੀ ਹੈਡਰ ਰਾਹੀਂ ਘੋਸ਼ਿਤ ਕਰਦਾ ਹੈ। ਜਦੋਂ ਸਾਈਡਕਾਰ ਨੂੰ ਸਥਾਨਕ ਬੇਨਤੀ ਮੂਲ ਦੀ ਥਾਂ ਕਿਸੇ ਜਨਤਕ ਜਾਂ ਕੰਟੇਨਰ
ਨੈੱਟਵਰਕ URL ਦੀ ਲੋੜ ਹੋਵੇ ਤਾਂ
`OMNIROUTE_PROVIDER_MANIFEST_URL` ਸੈੱਟ ਕਰੋ।

## ਮੈਨੀਫੈਸਟ ਨੂੰ ਰਿਫ੍ਰੈਸ਼ ਕਰਨਾ

HTTP ਐਂਡਪੌਇੰਟ `Cache-Control: public, max-age=60` ਅਤੇ ਇੱਕ ਮਜ਼ਬੂਤ
`ETag` ਵਾਪਸ ਕਰਦਾ ਹੈ। ਕਿਸੇ ਸਾਈਡਕਾਰ ਨੂੰ ਆਖਰੀ ਪ੍ਰਮਾਣਿਤ ਮੈਨੀਫੈਸਟ ਸੰਭਾਲ ਕੇ ਰੱਖਣਾ ਚਾਹੀਦਾ ਹੈ ਅਤੇ ਰਿਫ੍ਰੈਸ਼ ਕਰਦੇ ਸਮੇਂ ਉਸਦਾ ETag
`If-None-Match` ਵਿੱਚ ਭੇਜਣਾ ਚਾਹੀਦਾ ਹੈ। `304 Not Modified` ਜਵਾਬ ਵਿੱਚ ਕੋਈ ਬਾਡੀ ਨਹੀਂ ਹੁੰਦੀ;
ਸਾਈਡਕਾਰ ਆਪਣਾ ਕੈਸ਼ ਕੀਤਾ ਮੈਨੀਫੈਸਟ ਬਰਕਰਾਰ ਰੱਖਦਾ ਹੈ। ਜੇ ਕੋਈ ਪ੍ਰਮਾਣਿਤ ਕੈਸ਼ ਕੀਤਾ ਮੈਨੀਫੈਸਟ ਮੌਜੂਦ ਨਹੀਂ ਹੈ,
ਤਾਂ ਸਾਈਡਕਾਰ ਨੂੰ `304` ਸਵੀਕਾਰ ਕਰਨ ਦੀ ਥਾਂ ਬਿਨਾਂ ਸ਼ਰਤ ਬੇਨਤੀ ਭੇਜਣੀ ਲਾਜ਼ਮੀ ਹੈ।

## ਟੀਚਾ

ਪ੍ਰਦਾਤਾ ਮੈਟਾਡੇਟਾ ਨੂੰ ਇੱਕ ਪਲੱਗਇਨ ਕਾਂਟ੍ਰੈਕਟ ਵੱਲ ਲੈ ਕੇ ਜਾਣਾ, ਤਾਂ ਜੋ ਤੁਰੰਤ ਬੇਨਤੀ ਪਾਥ ਦੀ
ਮਾਲਕੀ ਆਖ਼ਰਕਾਰ ਘੱਟ-ਲੇਟੈਂਸੀ ਵਾਲੇ ਸਾਈਡਕਾਰ ਕੋਲ ਹੋ ਸਕੇ, ਜਦੋਂਕਿ OmniRoute
TypeScript ਰੂਟ ਨੂੰ ਨੀਤੀ ਗੇਟ ਅਤੇ ਫਾਲਬੈਕ ਵਜੋਂ ਬਰਕਰਾਰ ਰੱਖੇ। ਮੈਨੀਫੈਸਟ ਵਾਧੂ ਹੈ: ਇਹ
ਆਪਣੇ ਆਪ ਬੇਨਤੀ ਰਾਊਟਿੰਗ ਨੂੰ ਨਹੀਂ ਬਦਲਦਾ।

## ਕਾਂਟ੍ਰੈਕਟ

ਮੈਨੀਫੈਸਟ ਵਿੱਚ ਇਹ ਸ਼ਾਮਲ ਹਨ:

- ਪ੍ਰਦਾਤਾ id ਅਤੇ ਉਪਨਾਮ
- ਅੱਪਸਟ੍ਰੀਮ ਫਾਰਮੈਟ ਅਤੇ ਐਗਜ਼ਿਕਿਊਟਰ ਨਾਮ
- ਪ੍ਰਮਾਣੀਕਰਨ ਕਿਸਮ, ਪ੍ਰਮਾਣੀਕਰਨ ਹੈਡਰ, ਅਤੇ ਵਿਕਲਪਿਕ ਪ੍ਰਮਾਣੀਕਰਨ ਪ੍ਰੀਫਿਕਸ
- ਸਥਿਰ ਐਂਡਪੌਇੰਟ ਮੈਟਾਡੇਟਾ
- ਸਾਈਡਕਾਰ ਯੋਗਤਾ ਅਤੇ ਜਦੋਂ ਕੋਈ ਪ੍ਰਦਾਤਾ TS ਉੱਤੇ ਹੀ ਰਹਿਣਾ ਚਾਹੀਦਾ ਹੋਵੇ ਤਾਂ ਉਸਦੇ ਸਪਸ਼ਟ ਕਾਰਨ
- JSON-ਸੁਰੱਖਿਅਤ ਮਾਡਲ ਮੈਟਾਡੇਟਾ, ਜਿਵੇਂ ਕਿ ਸੰਦਰਭ ਲੰਬਾਈ, ਵਿਜ਼ਨ/ਰੀਜ਼ਨਿੰਗ ਫਲੈਗ, ਅਤੇ
  ਅਸਮਰਥਿਤ ਪੈਰਾਮੀਟਰ
- `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch`, ਅਤੇ `usage-supported` ਸਮੇਤ ਸਮਰੱਥਾ ਟੈਗ

ਮੈਨੀਫੈਸਟ ਜਾਣਬੁੱਝ ਕੇ ਇਹਨਾਂ ਨੂੰ ਸ਼ਾਮਲ ਨਹੀਂ ਕਰਦਾ:

- OAuth ਕਲਾਇੰਟ ਸੀਕ੍ਰੇਟ ਅਤੇ ਡਿਫਾਲਟ ਗੁਪਤ ਮੁੱਲ
- ਰਨਟਾਈਮ ਵਾਤਾਵਰਨ ਰਿਜ਼ੋਲਿਊਸ਼ਨ
- ਬੇਨਤੀ ਹੈਡਰ ਅਤੇ ਜਨਤਕ ਕ੍ਰੈਡੈਂਸ਼ਲ ਹੈਲਪਰ
- ਡਾਇਨਾਮਿਕ URL ਬਿਲਡਰ
- ਐਗਜ਼ਿਕਿਊਟਰ ਫੰਕਸ਼ਨ
- ਸੈਸ਼ਨ ਪੂਲ ਦੇ ਅੰਦਰੂਨੀ ਵੇਰਵੇ

## ਸਮਰੱਥਾ ਟੈਗ

`capabilities` ਰਜਿਸਟਰੀ ਐਂਟਰੀ ਤੋਂ ਪ੍ਰਾਪਤ ਟੈਗਾਂ ਦੀ ਕ੍ਰਮਬੱਧ ਐਰੇ ਹੈ। ਇੰਟੀਗ੍ਰੇਟਰਾਂ ਨੂੰ
TypeScript ਸਰੋਤਾਂ ਨੂੰ ਦੁਬਾਰਾ ਪੜ੍ਹਨ ਦੀ ਥਾਂ ਇਸਨੂੰ "ਇਹ ਪ੍ਰਦਾਤਾ ਕੀ ਕਰ ਸਕਦਾ ਹੈ" ਦੇ ਮਸ਼ੀਨ-ਪਾਠਯੋਗ ਜਵਾਬ ਵਜੋਂ
ਵਰਤਣਾ ਚਾਹੀਦਾ ਹੈ।

| ਟੈਗ                  | ਅਰਥ                                                                                      |
| -------------------- | ---------------------------------------------------------------------------------------- |
| `apikey`             | ਇੱਕ API ਕੁੰਜੀ ਸਵੀਕਾਰ ਕਰਦਾ ਹੈ (`authType` `apikey` ਜਾਂ `optional` ਹੈ)।                    |
| `oauth`              | ਇੱਕ OAuth ਜਾਂ ਸੈਸ਼ਨ ਪ੍ਰਵਾਹ ਵਰਤਦਾ ਹੈ।                                                     |
| `responses`          | ਇੱਕ OpenAI Responses-API ਬੇਸ URL ਉਪਲਬਧ ਕਰਦਾ ਹੈ।                                          |
| `passthrough-models` | ਸਥਿਰ ਕੈਟਾਲਾਗ ਦੀ ਥਾਂ ਸਿੱਧੇ ਅੱਪਸਟ੍ਰੀਮ ਤੋਂ ਮਾਡਲ ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ।                             |
| `custom-executor`    | ਇੱਕ ਗੈਰ-ਡਿਫਾਲਟ ਐਗਜ਼ਿਕਿਊਟਰ ਚਲਾਉਂਦਾ ਹੈ, ਇਸ ਲਈ ਇਹ TypeScript ਪਾਥ ਉੱਤੇ ਰਹਿੰਦਾ ਹੈ।            |
| `sidecar-candidate`  | `sidecar.eligible` ਨੂੰ ਪ੍ਰਤੀਬਿੰਬਿਤ ਕਰਦਾ ਹੈ — ਸਾਈਡਕਾਰ ਇੰਪੋਰਟ ਲਈ ਵਿਚਾਰ ਕਰਨ ਵਾਸਤੇ ਸੁਰੱਖਿਅਤ। |
| `usage-fetch`        | ਇੱਕ ਵਾਇਰ ਕੀਤਾ ਵਰਤੋਂ ਜਾਂ ਕੋਟਾ ਫੈਚਰ (`getUsageForProvider`) ਮੌਜੂਦ ਹੈ।                      |
| `usage-supported`    | ਵਰਤੋਂ API ਇਸ ਪ੍ਰਦਾਤਾ ਨੂੰ ਸਵੀਕਾਰ ਕਰਦੀ ਹੈ (`isSupportedUsageConnection`)।                  |

`usage-fetch` ਸਿਰਫ਼ ਖੋਜ ਲਈ ਹੈ। ਇਹ ਦੱਸਦਾ ਹੈ ਕਿ OmniRoute ਪ੍ਰਦਾਤਾ ਲਈ ਵਰਤੋਂ ਕਿਵੇਂ ਪੜ੍ਹਨੀ ਹੈ;
ਇਹ ਫੈਚਿੰਗ ਨੂੰ ਸਰਗਰਮ ਨਹੀਂ ਕਰਦਾ, ਕੋਟਾ ਦੇ ਅਰਥ ਨਹੀਂ ਬਦਲਦਾ, ਅਤੇ ਨਾ ਹੀ ਇਹ ਦਰਸਾਉਂਦਾ ਹੈ ਕਿ
Dashboard ਕੋਟਾ ਵਿਜੇਟ ਪ੍ਰਦਾਤਾ ਲਈ ਸਮਰੱਥ ਹੈ — ਉਹ ਵਿਜੇਟ ਵੱਖਰੇ ਤੌਰ 'ਤੇ
`USAGE_SUPPORTED_PROVIDERS` ਦੁਆਰਾ ਨਿਯੰਤਰਿਤ ਹੁੰਦਾ ਹੈ। ਸੱਚਾਈ ਦਾ ਸਰੋਤ
`open-sse/services/usage/fetcherProviders.ts` ਵਿੱਚ `USAGE_FETCHER_PROVIDERS` ਹੈ।

ਉਸ ਸੂਚੀ ਨੂੰ ਵਰਤੋਂ ਡਿਸਪੈਚਰ ਵੱਲੋਂ ਸਵੀਕਾਰ ਕੀਤੀਆਂ ਸਟ੍ਰਿੰਗਾਂ ਦੇ ਆਧਾਰ 'ਤੇ ਕੁੰਜੀਬੱਧ ਕੀਤਾ ਗਿਆ ਹੈ, ਇਸ ਲਈ ਇਹ ਕੈਨੋਨਿਕਲ ids
ਨੂੰ ਉਪਨਾਮਾਂ ਨਾਲ ਮਿਲਾਉਂਦੀ ਹੈ ਅਤੇ ਟੈਗ ਕੀਤੇ ਪ੍ਰਦਾਤਾਵਾਂ ਦੀ ਗਿਣਤੀ ਨਾਲੋਂ ਥੋੜ੍ਹੀ ਲੰਬੀ ਹੈ: ਉਹ ਐਂਟਰੀਆਂ ਜੋ
ਮੈਨੀਫੈਸਟ ਰਜਿਸਟਰੀ ਵਿੱਚ ਚੈਟ ਪ੍ਰਦਾਤਾ ਨਹੀਂ ਹਨ (ਉਦਾਹਰਨ ਲਈ `firecrawl` ਖੋਜ ਪ੍ਰਦਾਤਾ
ਅਤੇ `amazon-q` ACP ਪ੍ਰਦਾਤਾ), ਉਹਨਾਂ ਕੋਲ ਟੈਗ ਕਰਨ ਲਈ ਕੋਈ ਮੈਨੀਫੈਸਟ ਐਂਟਰੀ ਨਹੀਂ ਹੈ।

`usage-supported` ਇਹ ਦੱਸਦਾ ਹੈ ਕਿ ਸਰਵਰ ਅਤੇ Dashboard ਵਰਤੋਂ ਰੂਟ ਪ੍ਰਦਾਤਾ ਲਈ ਕਨੈਕਸ਼ਨ
ਸਵੀਕਾਰ ਕਰਦੇ ਹਨ ਜਾਂ ਨਹੀਂ। ਇਹ `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
ਅਤੇ `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`) ਨੂੰ ਪ੍ਰਤੀਬਿੰਬਿਤ ਕਰਦਾ ਹੈ, ਦੋਵੇਂ
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`) ਦੁਆਰਾ ਨਿਯੰਤਰਿਤ ਹਨ।
`usage-fetch` ਤੋਂ ਵੱਖਰੇ ਤੌਰ 'ਤੇ, ਇਹ ਸਿਰਫ਼ ਪ੍ਰਦਾਤਾ id ਉੱਤੇ ਹੀ ਨਿਕਲਦਾ ਹੈ — ਰਨਟਾਈਮ ਗਾਰਡ
ਬਿਨਾਂ ਉਪਨਾਮ ਰਿਜ਼ੋਲਿਊਸ਼ਨ ਦੇ `USAGE_SUPPORTED_PROVIDERS.includes(providerId)` ਕਰਦਾ ਹੈ, ਇਸ ਲਈ ਮੈਨੀਫੈਸਟ
ਉਹੀ ਨਿਯਮ ਬਰਕਰਾਰ ਰੱਖਦਾ ਹੈ। ਦੋਵੇਂ ਟੈਗਾਂ ਦੇ ਦਾਇਰੇ ਵੱਖਰੇ ਹਨ: 3 ਪ੍ਰਦਾਤਾਵਾਂ ਕੋਲ ਸਿਰਫ਼
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) ਹੈ ਅਤੇ 1 ਕੋਲ ਸਿਰਫ਼
`usage-supported` (`xiaomi-mimo-token-plan`) ਹੈ, ਇਸ ਲਈ ਇੱਕ ਤੋਂ ਦੂਜਾ ਨਿਹਿਤ ਨਹੀਂ ਹੁੰਦਾ।

## Sidecar ਦੀ ਵਰਤੋਂ

Sidecar ਨੂੰ `sidecar.eligible` ਨੂੰ ਇੱਕ ਸਾਵਧਾਨੀਪੂਰਵਕ ਉਮੀਦਵਾਰ ਸੰਕੇਤ ਵਜੋਂ ਲੈਣਾ ਚਾਹੀਦਾ ਹੈ, ਨਾ ਕਿ ਇੱਕ ਬਿਨਾਂ ਸ਼ਰਤ ਰੂਟਿੰਗ ਫ਼ੈਸਲੇ ਵਜੋਂ। ਪਹਿਲਾ ਇੰਪੋਰਟ ਟੀਚਾ ਡਿਫੌਲਟ executor ਵਰਤਣ ਵਾਲੇ API-key, static-endpoint ਪ੍ਰਦਾਤਾ ਹੋਣੇ ਚਾਹੀਦੇ ਹਨ। custom web executors, OAuth/session flows, dynamic URL builders, ਜਾਂ pool config ਵਾਲੇ ਪ੍ਰਦਾਤਾ ਉਦੋਂ ਤੱਕ TypeScript fallback ਮਾਰਗ 'ਤੇ ਰਹਿਣਗੇ, ਜਦੋਂ ਤੱਕ ਕੋਈ sidecar ਸਮਾਨ ਵਿਹਾਰ ਲਾਗੂ ਨਹੀਂ ਕਰਦਾ ਅਤੇ telemetry ਸਮਾਨਤਾ ਸਾਬਤ ਨਹੀਂ ਕਰਦੀ।

ਸੁਝਾਏ ਗਏ ਮਾਈਗ੍ਰੇਸ਼ਨ ਪੜਾਅ:

1. TS registry ਤੋਂ provider plugin manifest ਤਿਆਰ ਕਰੋ ਅਤੇ ਪ੍ਰਮਾਣਿਤ ਕਰੋ।
2. Bifrost ਜਾਂ CLIProxyAPI ਨੂੰ API-key/static ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ manifest ਇੰਪੋਰਟ ਕਰਨਾ ਸਿਖਾਓ।
3. TS fallback ਨੂੰ ਸਮਰੱਥ ਰੱਖਦੇ ਹੋਏ, ਯੋਗ ਪ੍ਰਦਾਤਾਵਾਂ ਨੂੰ `OMNIROUTE_RELAY_BACKEND` ਦੇ ਪਿੱਛੇ sidecar ਰਾਹੀਂ ਰੂਟ ਕਰੋ।
4. ਪ੍ਰਦਾਤਾਵਾਂ ਨੂੰ ਸਿਰਫ਼ ਉਦੋਂ ਹੀ ਅੱਗੇ ਵਧਾਓ, ਜਦੋਂ ਸਫਲਤਾ ਦਰ, p99 latency, streaming ਵਿਹਾਰ, ਅਤੇ unsupported-param ਸੰਭਾਲ TS ਮਾਰਗ ਨਾਲ ਮੇਲ ਖਾਂਦੇ ਹੋਣ।
5. ਇੱਕ ਸਮੇਂ ਵਿੱਚ ਇੱਕ provider family ਲਈ custom executors ਵਾਸਤੇ sidecar-native plugins ਸ਼ਾਮਲ ਕਰੋ।

## ਪ੍ਰਦਾਤਾਵਾਂ ਨੂੰ ਸਿੱਧੇ Next ਵਿੱਚ Embed ਕਿਉਂ ਨਾ ਕੀਤਾ ਜਾਵੇ

Next frontend ਕੋਲ provider execution ਦੀ ਜ਼ਿੰਮੇਵਾਰੀ ਨਹੀਂ ਹੋਣੀ ਚਾਹੀਦੀ। ਇਸਨੂੰ API boundary ਨੂੰ ਕਾਲ ਕਰਨਾ ਚਾਹੀਦਾ ਹੈ। ਫਿਰ backend ਇਹ ਫ਼ੈਸਲਾ ਕਰ ਸਕਦਾ ਹੈ ਕਿ TypeScript executor, Bifrost, CLIProxyAPI, ਜਾਂ ਭਵਿੱਖ ਦੇ ਕਿਸੇ native sidecar ਨੂੰ ਵਰਤਣਾ ਹੈ। ਇਸ ਨਾਲ ਕਿਸੇ ਵੀ sidecar handoff ਤੋਂ ਪਹਿਲਾਂ request signing, allowlist checks, DB policy, ਅਤੇ fallback ਵਿਹਾਰ ਕੇਂਦਰੀਕ੍ਰਿਤ ਰਹਿੰਦੇ ਹਨ।
