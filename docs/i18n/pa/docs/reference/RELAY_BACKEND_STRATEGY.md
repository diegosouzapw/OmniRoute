## ਸੰਖੇਪ

OmniRoute ਹੁਣ `/api/v1/relay/chat/completions` ਲਈ ਤਿੰਨ ਰਿਲੇ ਮੋਡਾਂ ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ:

- `ts`: TypeScript ਰਿਲੇ ਨੂੰ ਉਸੇ ਪ੍ਰਕਿਰਿਆ ਵਿੱਚ ਵਰਤੋ।
- `bifrost`: Bifrost ਗੇਟਵੇ ਨੂੰ ਲਾਜ਼ਮੀ ਤੌਰ 'ਤੇ ਵਰਤੋ।
- `auto`: ਉਪਲਬਧ ਹੋਣ 'ਤੇ Bifrost ਨੂੰ ਤਰਜੀਹ ਦਿਓ ਅਤੇ ਅਸਫਲਤਾ ਹੋਣ 'ਤੇ TypeScript 'ਤੇ ਵਾਪਸ ਜਾਓ।

ਜਦੋਂ ਤੁਸੀਂ ਉੱਚ ਬੇਨਤੀ ਦਰ 'ਤੇ ਚਲਾ ਰਹੇ ਹੋਵੋ (ਰੋਜ਼ਾਨਾ ਵੱਡੀ ਗਿਣਤੀ ਵਿੱਚ ਟੋਕਨ, ਲਗਭਗ ਨਿਰੰਤਰ ਥਰੂਪੁੱਟ), ਤਾਂ ਸਭ ਤੋਂ ਵਧੀਆ ਰਣਨੀਤੀ ਫਾਲਬੈਕ ਪਾਥ ਨੂੰ ਸਪਸ਼ਟ ਅਤੇ ਤੇਜ਼ ਰੱਖਣਾ ਹੈ, ਤਾਂ ਜੋ ਹਾਟ ਪਾਥ ਕਦੇ ਵੀ ਬੰਦ ਪਏ ਸਾਈਡਕਾਰ ਕਰਕੇ ਬਲੌਕ ਨਾ ਹੋਵੇ।

## ਮੋਡ ਦਾ ਵਿਹਾਰ

- `ts`
  - ਸਭ ਤੋਂ ਘੱਟ ਸੰਚਾਲਨ ਜਟਿਲਤਾ।
  - ਸਾਰੀ ਰੂਟਿੰਗ ਅਤੇ ਪ੍ਰਮਾਣਿਕਤਾ Node ਵਿੱਚ ਚੱਲਦੀ ਹੈ।
  - ਉਪਲਬਧਤਾ ਲਈ ਸਾਈਡਕਾਰ 'ਤੇ ਕੋਈ ਨਿਰਭਰਤਾ ਨਹੀਂ।
- `bifrost`
  - ਸਾਰੀਆਂ ਬੇਨਤੀਆਂ ਨੂੰ ਲਾਜ਼ਮੀ ਤੌਰ 'ਤੇ ਸਾਈਡਕਾਰ ਗੇਟਵੇ ਰਾਹੀਂ ਭੇਜਦਾ ਹੈ।
  - ਕੋਈ ਸਵੈਚਾਲਿਤ ਫਾਲਬੈਕ ਨਹੀਂ।
  - ਕੇਵਲ ਉਦੋਂ ਲਾਭਦਾਇਕ ਹੈ ਜਦੋਂ ਸਾਈਡਕਾਰ ਦੀ ਸਿਹਤ ਅਤੇ ਲੇਟੈਂਸੀ ਦੀ ਗਾਰੰਟੀ ਹੋਵੇ।
- `auto`
  - ਸਾਈਡਕਾਰ ਉਦੋਂ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ ਜਦੋਂ ਉਸ ਤੱਕ ਪਹੁੰਚਿਆ ਜਾ ਸਕੇ ਅਤੇ ਉਹ ਸਮਰੱਥ ਹੋਵੇ।
  - ਅਸਫਲ ਕੋਸ਼ਿਸ਼ਾਂ ਫਾਲਬੈਕ ਹੈਡਰਾਂ ਨੂੰ ਟ੍ਰਿਗਰ ਕਰਦੀਆਂ ਹਨ ਅਤੇ ਟ੍ਰੈਫਿਕ ਨੂੰ TS ਵੱਲ ਵਾਪਸ ਭੇਜਦੀਆਂ ਹਨ, ਤਾਂ ਜੋ ਬੇਨਤੀ ਦੀ ਸਫਲਤਾ ਨਿਰਧਾਰਤ ਹੱਦਾਂ ਵਿੱਚ ਰਹੇ।
  - ਜਦੋਂ ਅਪਟਾਈਮ ਸਿਰਫ਼ ਸਾਈਡਕਾਰ ਰਾਹੀਂ ਸਖ਼ਤ ਰੂਟਿੰਗ ਨਾਲੋਂ ਵੱਧ ਮਹੱਤਵਪੂਰਨ ਹੋਵੇ, ਤਾਂ ਇਹ ਮੋਡ ਪ੍ਰੋਡਕਸ਼ਨ ਲਈ ਸਭ ਤੋਂ ਸੁਰੱਖਿਅਤ ਚੋਣ ਹੈ।

## ਅੱਜ 9router ਬਨਾਮ CLIPROXYAPI

9router ਅਤੇ CLIPROXYAPI ਦੋਵੇਂ ਇੰਟੀਗ੍ਰੇਸ਼ਨ ਹਨ, ਜਿਨ੍ਹਾਂ ਨੇ ਇਤਿਹਾਸਕ ਤੌਰ 'ਤੇ ਅੱਪਸਟ੍ਰੀਮ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ ਅਨੁਕੂਲਤਾ ਪਾਥ ਉਪਲਬਧ ਕਰਵਾਏ ਹਨ।

- 9router ਅੱਪਸਟ੍ਰੀਮ ਆਰਕੈਸਟ੍ਰੇਸ਼ਨ ਅਤੇ ਅਨੁਕੂਲਤਾ ਵਿਹਾਰ ਲਈ ਇੱਕ ਐਂਬੈਡਿਡ ਪਾਥ ਹੈ।
- CLIPROXYAPI CLI / SDK ਸ਼ੈਲੀ ਦੇ ਟ੍ਰੈਫਿਕ ਲਈ ਇੱਕ ਪ੍ਰੌਕਸੀ API ਬ੍ਰਿਜ ਹੈ।
- ਜਦੋਂ ਤੁਹਾਨੂੰ ਇੱਕ ਸਮਰਪਿਤ ਸਾਈਡਕਾਰ-ਵਰਗੇ ਹੌਪ ਅਤੇ ਘੱਟ-ਲੇਟੈਂਸੀ ਵਾਲੀ ਲੋਕਲ ਡਿਸਪੈਚ ਦੀ ਲੋੜ ਹੋਵੇ, ਤਾਂ Bifrost ਨੂੰ ਬਾਹਰੀ ਪਾਥ ਵਜੋਂ ਸਥਿਰ ਕੀਤਾ ਜਾ ਰਿਹਾ ਹੈ।

ਜੇ ਤੁਸੀਂ ਇਸ ਵੇਲੇ 9router/CLIPROXYAPI ਦੀ ਤੁਲਨਾ ਕਰ ਰਹੇ ਹੋ:

- ਹੈਂਡਆਫ ਤੋਂ ਪਹਿਲਾਂ API ਰੂਟ ਵਿੱਚ ਬੇਨਤੀ ਸਾਈਨਿੰਗ, ਅਲਾਊਲਿਸਟ ਜਾਂਚਾਂ ਅਤੇ DB ਨੀਤੀ ਗੇਟਾਂ ਨੂੰ ਬਣਾਈ ਰੱਖੋ।
- ਜੇ ਕਿਸੇ ਵਰਕਫਲੋ ਨੂੰ ਸਖ਼ਤ ਸਾਈਡਕਾਰ ਵਿਹਾਰ ਅਤੇ ਪ੍ਰਤੀ-ਬੇਨਤੀ ਘੱਟ ਭਿੰਨਤਾ ਦੀ ਲੋੜ ਹੈ, ਤਾਂ `OMNIROUTE_RELAY_BACKEND=bifrost` ਵਰਤੋ।
- ਜੇ ਤੁਹਾਨੂੰ ਘਟਨਾ ਵਾਲੀਆਂ ਸਥਿਤੀਆਂ ਦੌਰਾਨ ਸੁਚਾਰੂ ਡਿਗ੍ਰੇਡੇਸ਼ਨ ਦੇ ਨਾਲ ਸਾਈਡਕਾਰ ਲਚਕੀਲੇਪਣ ਦੀ ਲੋੜ ਹੈ, ਤਾਂ `OMNIROUTE_RELAY_BACKEND=auto` ਵਰਤੋ।

## ਬੈਕਐਂਡ ਸੀਮਾ ਇਕਰਾਰਨਾਮਾ

ਸਥਿਰ ਉਤਪਾਦ ਸੀਮਾ OmniRoute ਰਿਲੇ API ਹੈ, ਡੈਸ਼ਬੋਰਡ ਇੰਪਲੀਮੈਂਟੇਸ਼ਨ ਨਹੀਂ। Next.js ਡੈਸ਼ਬੋਰਡ ਲੋਕਲ ਸੇਵਾਵਾਂ ਨੂੰ ਇੰਸਟਾਲ, ਕੌਂਫਿਗਰ ਅਤੇ ਨਿਗਰਾਨੀ ਕਰ ਸਕਦਾ ਹੈ, ਪਰ ਬੇਨਤੀ ਰੂਟਿੰਗ ਨੂੰ ਰਿਲੇ API ਰਾਹੀਂ ਦਾਖ਼ਲ ਹੋਣਾ ਅਤੇ ਉਸ ਸੀਮਾ ਦੇ ਪਿੱਛੇ ਹੈਂਡਆਫ ਕਰਨਾ ਚਾਹੀਦਾ ਹੈ।

ਲੰਬੇ ਸਮੇਂ ਦੀਆਂ ਬੈਕਐਂਡ ਚੋਣਾਂ:

- TypeScript ਰਿਲੇ ਨੂੰ ਉਸੇ ਪ੍ਰਕਿਰਿਆ ਵਿੱਚ ਚੱਲਣ ਵਾਲੀ ਨੀਤੀ ਅਤੇ ਫਾਲਬੈਕ ਪਾਥ ਵਜੋਂ ਰੱਖੋ। ਕਿਸੇ ਵੀ ਬੈਕਐਂਡ ਹੈਂਡਆਫ ਤੋਂ ਪਹਿਲਾਂ Auth, ਅਲਾਊਲਿਸਟਾਂ, ਬੇਨਤੀ ਨਾਰਮਲਾਈਜ਼ੇਸ਼ਨ, ਲੇਖਾ-ਜੋਖਾ ਅਤੇ ਸੁਰੱਖਿਆ ਜਾਂਚਾਂ ਇੱਥੇ ਹੀ ਰਹਿੰਦੀਆਂ ਹਨ।
- ਜਦੋਂ ਡਿਪਲੌਇਮੈਂਟ ਨੂੰ ਘੱਟ ਰੂਟਿੰਗ ਭਿੰਨਤਾ, ਕੇਂਦਰੀਕ੍ਰਿਤ ਪ੍ਰਦਾਤਾ ਰੋਟੇਸ਼ਨ ਜਾਂ ਕਈ OmniRoute ਰੈਪਲਿਕਾਵਾਂ ਵਿੱਚ ਸਕੇਲ-ਆਊਟ ਦੀ ਲੋੜ ਹੋਵੇ, ਤਾਂ Bifrost ਨੂੰ ਤਰਜੀਹੀ ਉੱਚ-ਥਰੂਪੁੱਟ Tier-1 ਸਾਈਡਕਾਰ ਵਜੋਂ ਵਰਤੋ।
- 9router ਅਤੇ CLIPROXYAPI ਨੂੰ ਐਂਬੈਡਿਡ ਅਨੁਕੂਲਤਾ ਸੇਵਾਵਾਂ ਵਜੋਂ ਰੱਖੋ। ਇਹ ਨਿਗਰਾਨੀ ਅਧੀਨ ਲੋਕਲ ਪ੍ਰਕਿਰਿਆਵਾਂ ਵਜੋਂ ਚੱਲਦੀਆਂ ਹਨ ਅਤੇ ਉਦੋਂ ਲਾਭਦਾਇਕ ਹੁੰਦੀਆਂ ਹਨ ਜਦੋਂ ਉਨ੍ਹਾਂ ਦਾ ਪ੍ਰਦਾਤਾ/CLI ਵਿਹਾਰ ਲੋੜੀਂਦਾ ਅਡੈਪਟਰ ਹੋਵੇ, ਪਰ ਇਨ੍ਹਾਂ ਨੂੰ ਡਿਫੌਲਟ Tier-1 ਰੂਟਿੰਗ ਇੰਜਣ ਨਹੀਂ ਬਣਨਾ ਚਾਹੀਦਾ।
- ਡੈਸ਼ਬੋਰਡ ਨੂੰ ਹਾਟ ਪਾਥ ਵਿੱਚ ਮਨਮਾਨੇ ਸੇਵਾ URLs ਪਾਸ ਨਾ ਕਰਨ ਦਿਓ। UI ਵੱਲੋਂ ਦਿੱਤੇ URLs ਕੌਂਫਿਗਰੇਸ਼ਨ ਇਨਪੁੱਟ ਹਨ; ਰੂਟਿੰਗ ਕੋਡ ਨੂੰ ਸਰਵਰ-ਸਾਈਡ ਸੈਟਿੰਗਾਂ ਅਤੇ ਸੁਪਰਵਾਈਜ਼ਰ ਸਥਿਤੀ ਤੋਂ ਰਜਿਸਟਰਡ, ਸਿਹਤ-ਜਾਂਚੇ ਹੋਏ ਬੈਕਐਂਡ ਹੱਲ ਕਰਨੇ ਚਾਹੀਦੇ ਹਨ।
- ਅੱਜ ਨਿਗਰਾਨੀ ਅਧੀਨ ਸੇਵਾਵਾਂ ਲਈ ਲੂਪਬੈਕ HTTP ਨੂੰ ਤਰਜੀਹ ਦਿਓ, ਕਿਉਂਕਿ ਪ੍ਰਬੰਧਿਤ ਪ੍ਰਕਿਰਿਆਵਾਂ ਪਹਿਲਾਂ ਹੀ HTTP-ਅਨੁਕੂਲ APIs ਉਪਲਬਧ ਕਰਵਾਉਂਦੀਆਂ ਹਨ, ਰੂਟ ਗਾਰਡ ਸੀਮਾ ਦਾ ਆਡਿਟ ਕਰ ਸਕਦਾ ਹੈ ਅਤੇ ਅਸਫਲਤਾ/ਫਾਲਬੈਕ ਦਾ ਵਿਹਾਰ ਬੇਨਤੀ ਲੌਗਾਂ ਵਿੱਚ ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ। ਭਵਿੱਖ ਵਿੱਚ SDK ਜਾਂ ਸਾਕਟ ਟ੍ਰਾਂਸਪੋਰਟ ਜੋੜਨਾ ਕੇਵਲ ਉਦੋਂ ਹੀ ਉਚਿਤ ਹੈ ਜੇ ਇਹ ਆਇਸੋਲੇਸ਼ਨ ਜਾਂ ਫਾਲਬੈਕ ਸਿਮੈਂਟਿਕਸ ਨੂੰ ਕਮਜ਼ੋਰ ਕੀਤੇ ਬਿਨਾਂ p99 ਰੂਟਿੰਗ ਲੇਟੈਂਸੀ ਨੂੰ ਮਾਪਣਯੋਗ ਢੰਗ ਨਾਲ ਘਟਾਏ।

ਇਸ ਲਈ ਬਹੁਤ ਉੱਚ-ਥਰੂਪੁੱਟ ਵਾਲੀ ਡਿਪਲੌਇਮੈਂਟ ਲਈ ਡਿਫੌਲਟ ਜਵਾਬ Bifrost ਸਮਰੱਥ ਕੀਤੇ ਹੋਏ `auto` ਹੈ: ਸਫਲਤਾ ਦਰ ਲਈ TypeScript ਫਾਲਬੈਕ ਨੂੰ ਕਾਇਮ ਰੱਖਦੇ ਹੋਏ ਹਾਟ ਪਾਥ 'ਤੇ Go ਸਾਈਡਕਾਰ ਦੀ ਵਰਤੋਂ ਕਰੋ। `bifrost` ਦੀ ਵਰਤੋਂ ਕੇਵਲ ਉਦੋਂ ਕਰੋ ਜਦੋਂ ਸਿਰਫ਼ ਸਾਈਡਕਾਰ ਵਾਲਾ ਸਖ਼ਤ ਵਿਹਾਰ ਸੁਚਾਰੂ ਡਿਗ੍ਰੇਡੇਸ਼ਨ ਨਾਲੋਂ ਵੱਧ ਮਹੱਤਵਪੂਰਨ ਹੋਵੇ।

## ਉੱਚ-ਥਰੂਪੁੱਟ ਮਾਰਗਦਰਸ਼ਨ

ਨਿਰੰਤਰ ਉੱਚ RPM/RPS ਅਤੇ ਸਖ਼ਤ ਸਫਲਤਾ SLO ਲਈ:

1. ਇੱਕ ਵਿਹਾਰਕ ਕੂਲਡਾਊਨ ਅਤੇ ਅਸਫਲਤਾ ਟੈਲੀਮੈਟਰੀ ਨਾਲ `auto` ਵਰਤੋ।
2. ਅੱਪਸਟ੍ਰੀਮ ਪ੍ਰਮਾਣਿਕਤਾ ਅਤੇ API-ਕੁੰਜੀ ਜਾਂਚਾਂ ਨੂੰ TypeScript ਰੂਟ ਸੀਮਾ 'ਤੇ ਰੱਖੋ।
3. ਸਪਸ਼ਟ ਹੈਡਰ/ਕਾਊਂਟਰ ਸਮਰੱਥ ਕਰੋ, ਤਾਂ ਜੋ ਤੁਹਾਡੀ ਅਲਰਟਿੰਗ ਫਾਲਬੈਕ ਦੀ ਆਵਿਰਤੀ ਅਤੇ ਕਾਰਨਾਂ ਨੂੰ ਦੇਖ ਸਕੇ।
4. ਸਾਈਡਕਾਰ ਟਾਈਮਆਊਟਾਂ ਨੂੰ ਤੇਜ਼ੀ ਨਾਲ ਅਸਫਲ ਹੋਣ ਲਈ ਟਿਊਨ ਕਰੋ, ਹਮੇਸ਼ਾ ਉਡੀਕਦੇ ਰਹਿਣ ਲਈ ਨਹੀਂ।
5. ਸੇਵਾ ਦੇ ਸਵੈਚਾਲਿਤ ਰੀਸਟਾਰਟ ਅਤੇ ਸਿਹਤ ਟੈਲੀਮੈਟਰੀ ਲੂਪ ਨੂੰ ਸਿਹਤਮੰਦ ਰੱਖੋ, ਤਾਂ ਜੋ ਫਾਲਬੈਕ ਸੱਚਮੁੱਚ ਅਸਧਾਰਨ ਸਥਿਤੀ ਹੀ ਰਹੇ।

## ਸੁਝਾਈ ਗਈ ਬੇਸਲਾਈਨ

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- API ਕੁੰਜੀਆਂ, ਅਲਾਊਲਿਸਟ, ਸੈਨਿਟਾਈਜ਼ਰ ਅਤੇ ਰੇਟ-ਲਿਮਿਟ ਜਾਂਚਾਂ ਨੂੰ ਰੂਟ ਹੈਂਡਲਰਾਂ ਵਿੱਚ ਸਮਰੱਥ ਰੱਖੋ (ਇਹ ਡਾਊਨਸਟ੍ਰੀਮ ਫਾਰਵਰਡਿੰਗ ਤੋਂ ਪਹਿਲਾਂ ਹਮੇਸ਼ਾ ਚੱਲਦੀਆਂ ਹਨ)।
- ਆਪਣੇ ਰਿਵਰਸ ਪ੍ਰੌਕਸੀ ਅਤੇ ਬੇਨਤੀ ਲੌਗਾਂ ਤੋਂ ਫਾਲਬੈਕ ਮੈਟ੍ਰਿਕਸ ਐਕਸਪੋਰਟ ਕਰੋ, ਤਾਂ ਜੋ ਸਾਈਡਕਾਰ ਆਊਟੇਜ ਇੱਕ ਮਿੰਟ ਦੇ ਅੰਦਰ ਦਿਖਾਈ ਦੇਣ।

## ਪ੍ਰਦਾਤਾ ਪਲੱਗਇਨ ਇਕਰਾਰਨਾਮਾ

ਸਾਈਡਕਾਰਾਂ ਨੂੰ TypeScript ਐਗਜ਼ਿਕਿਊਟਰ ਦੇ ਅੰਦਰੂਨੀ ਹਿੱਸਿਆਂ 'ਤੇ ਨਿਰਭਰ ਹੋਣ ਦੀ ਬਜਾਏ JSON-ਸੁਰੱਖਿਅਤ ਪ੍ਰਦਾਤਾ ਪਲੱਗਇਨ
ਮੈਨੀਫੈਸਟ ਰਾਹੀਂ ਪ੍ਰਦਾਤਾ ਮੈਟਾਡਾਟਾ ਇੰਪੋਰਟ ਕਰਨਾ ਚਾਹੀਦਾ ਹੈ। ਸਾਈਡਕਾਰ
ਯੋਗਤਾ ਇਕਰਾਰਨਾਮੇ ਅਤੇ ਮਾਈਗ੍ਰੇਸ਼ਨ ਪੜਾਵਾਂ ਲਈ [ਪ੍ਰਦਾਤਾ ਪਲੱਗਇਨ ਮੈਨੀਫੈਸਟ](./PROVIDER_PLUGIN_MANIFEST.md) ਵੇਖੋ।
