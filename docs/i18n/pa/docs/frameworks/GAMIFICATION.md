> **ਆਖਰੀ ਅੱਪਡੇਟ:** 2026-06-28 — v3.8.40

OmniRoute ਵਿੱਚ ਇੱਕ ਲੋਕਲ-ਫਰਸਟ ਗੇਮੀਫਿਕੇਸ਼ਨ ਪਰਤ ਸ਼ਾਮਲ ਹੈ ਜੋ ਵਰਤੋਂਕਾਰਾਂ ਨੂੰ
ਪਲੇਟਫਾਰਮ ਨਾਲ ਜੁੜਨ ਲਈ ਇਨਾਮ ਦਿੰਦੀ ਹੈ — ਬੇਨਤੀਆਂ ਕਰਨਾ, ਪ੍ਰਦਾਤਾ ਬਦਲਣਾ, ਕੰਬੋ
ਬਣਾਉਣਾ, ਟੋਕਨ ਸਾਂਝੇ ਕਰਨਾ ਅਤੇ ਭਾਈਚਾਰੇ ਵਿੱਚ ਯੋਗਦਾਨ ਪਾਉਣਾ। ਸਾਰੀ ਸਥਿਤੀ
SQLite ਵਿੱਚ ਰਹਿੰਦੀ ਹੈ; ਭਾਈਚਾਰਕ ਸਰਵਰਾਂ ਨਾਲ ਫੈਡਰੇਸ਼ਨ ਚੋਣਵੀਂ ਅਤੇ ਪੁਸ਼-ਅਧਾਰਿਤ ਹੈ।

ਸਿਸਟਮ ਨੂੰ **ਹੌਟ ਪਾਥ 'ਤੇ ਸਿਫ਼ਰ-ਲੇਟੈਂਸੀ** ਲਈ ਡਿਜ਼ਾਈਨ ਕੀਤਾ ਗਿਆ ਹੈ — ਗੇਮੀਫਿਕੇਸ਼ਨ
ਇਵੈਂਟ ਬੇਨਤੀ ਪਾਈਪਲਾਈਨ ਤੋਂ ਫਾਇਰ-ਐਂਡ-ਫਰਗੈਟ ਢੰਗ ਨਾਲ ਭੇਜੇ ਜਾਂਦੇ ਹਨ ਅਤੇ ਕਦੇ ਵੀ
LLM ਜਵਾਬ ਨੂੰ ਬਲੌਕ ਨਹੀਂ ਕਰਦੇ।

## ਸੰਖੇਪ ਜਾਣਕਾਰੀ

### ਉਦੇਸ਼

ਦ੍ਰਿਸ਼ਮਾਨ ਤਰੱਕੀ (XP, ਪੱਧਰ, ਬੈਜ), ਸਮਾਜਿਕ ਪ੍ਰਮਾਣ (ਲੀਡਰਬੋਰਡ), ਅਤੇ ਆਰਥਿਕ
ਪ੍ਰੋਤਸਾਹਨ (ਟੋਕਨ ਸਾਂਝਾਕਰਨ, ਸੱਦਾ ਇਨਾਮ) ਪ੍ਰਦਾਨ ਕਰਕੇ ਵਰਤੋਂਕਾਰ ਸਹਿਭਾਗਤਾ ਅਤੇ
ਬਰਕਰਾਰਤਾ ਵਧਾਉਣਾ।

### ਦਾਇਰਾ

| ਵਿਸ਼ੇਸ਼ਤਾ      | ਵੇਰਵਾ                                                         |
| -------------- | ------------------------------------------------------------- |
| XP ਅਤੇ ਪੱਧਰ    | ਹਰ ਕਾਰਵਾਈ ਲਈ XP ਕਮਾਓ; ਇੱਕ ਬਹੁਪਦੀ ਵਕਰ ਅਨੁਸਾਰ ਪੱਧਰ ਵਧਾਓ         |
| ਬੈਜ            | 4 ਦੁਲੱਭਤਾ ਪੱਧਰਾਂ ਨਾਲ 5 ਸ਼੍ਰੇਣੀਆਂ ਵਿੱਚ 20+ ਪ੍ਰਾਪਤੀਆਂ           |
| ਸਟ੍ਰੀਕਾਂ       | ਮੌਜੂਦਾ/ਸਭ ਤੋਂ ਲੰਬੀ ਸਟ੍ਰੀਕ ਨਾਲ ਰੋਜ਼ਾਨਾ ਸਰਗਰਮ ਵਰਤੋਂ ਦੀ ਟ੍ਰੈਕਿੰਗ |
| ਲੀਡਰਬੋਰਡ       | ਗਲੋਬਲ, ਹਫ਼ਤਾਵਾਰੀ, ਮਹੀਨਾਵਾਰੀ, ਟੋਕਨ-ਸਾਂਝਾਕਰਨ ਅਤੇ ਯੋਗਦਾਨ ਦਾਇਰੇ   |
| ਟੋਕਨ ਸਾਂਝਾਕਰਨ  | ਡਬਲ-ਐਂਟਰੀ ਲੈਜ਼ਰ ਰਾਹੀਂ ਵਰਤੋਂਕਾਰਾਂ ਵਿਚਕਾਰ ਕ੍ਰੈਡਿਟ ਟ੍ਰਾਂਸਫਰ ਕਰੋ  |
| ਸੱਦਾ ਅਤੇ ਰੀਡੀਮ | SHA-256 ਹੈਸ਼ਡ ਸਟੋਰੇਜ ਵਾਲੇ ਰੈਫ਼ਰਲ ਕੋਡ                          |
| ਭਾਈਚਾਰਕ ਸਰਵਰ   | ਬਾਹਰੀ OmniRoute ਇੰਸਟੈਂਸਾਂ ਨਾਲ ਫੈਡਰੇਟ ਕਰੋ                      |
| ਧੋਖਾਧੜੀ-ਰੋਕੂ   | ਸਰਵਰ-ਸਾਈਡ ਸਕੋਰਿੰਗ, ਦਰ ਸੀਮਾਬੰਦੀ, z-score ਅਸੰਗਤੀ ਪਛਾਣ           |

### ਡਿਜ਼ਾਈਨ ਸਿਧਾਂਤ

1. **ਲੋਕਲ-ਫਰਸਟ** — ਸਾਰੀ ਸਥਿਤੀ SQLite ਵਿੱਚ, ਕਿਸੇ ਬਾਹਰੀ ਸੇਵਾ ਦੀ ਲੋੜ ਨਹੀਂ।
2. **ਨਾਨ-ਬਲੌਕਿੰਗ** — ਇਵੈਂਟ ਫਾਇਰ-ਐਂਡ-ਫਰਗੈਟ ਹੁੰਦੇ ਹਨ; LLM ਜਵਾਬ ਪਾਥ ਵਿੱਚ
   ਗੇਮੀਫਿਕੇਸ਼ਨ ਤਰਕ ਕਾਰਨ ਕਦੇ ਦੇਰੀ ਨਹੀਂ ਹੁੰਦੀ।
3. **ਸਰਵਰ-ਅਧਿਕਾਰਤ** — XP ਦੀ ਗਣਨਾ ਕੇਵਲ ਸਰਵਰ-ਸਾਈਡ ਹੁੰਦੀ ਹੈ; ਕਲਾਇੰਟ
   ਸਕੋਰਾਂ ਨੂੰ ਨਕਲੀ ਤੌਰ 'ਤੇ ਨਹੀਂ ਵਧਾ ਸਕਦੇ।
4. **ਪਰਦੇਦਾਰੀ ਦਾ ਆਦਰ ਕਰਨ ਵਾਲਾ** — ਲੀਡਰਬੋਰਡ ਵਿੱਚ ਭਾਗੀਦਾਰੀ ਚੋਣਵੀਂ ਹੈ; ਵਰਤੋਂਕਾਰ
   ਆਪਣੀ ਪ੍ਰੋਫ਼ਾਈਲ ਲੁਕਾ ਸਕਦੇ ਹਨ।
5. **ਫੈਡਰੇਸ਼ਨ ਲਈ ਤਿਆਰ** — ਭਾਈਚਾਰਕ ਸਰਵਰ ਦਸਤਖ਼ਤ ਕੀਤੀ API ਰਾਹੀਂ ਸਕੋਰ ਪੁਸ਼ ਕਰ ਸਕਦੇ ਹਨ;
   ਸਿੰਕ ਓਵਰਰਾਈਟ ਹੁੰਦਾ ਹੈ, ਜੋੜਾਤਮਕ ਨਹੀਂ।

### ਇਨਾਮ ਦੇਣ ਦਾ ਪ੍ਰਵਾਹ

```typescript
export async function awardXp(
  apiKeyId: string,
  action: XpAction,
  metadata?: Record<string, unknown>
): Promise<{ xp: number; level: number; title: string; levelUp: boolean }>;
```

1. XP ਦੀ ਮਾਤਰਾ ਪ੍ਰਾਪਤ ਕਰਨ ਲਈ `XP_REWARDS[action]` ਵਿੱਚ ਖੋਜ ਕਰੋ।
2. `checkRateLimit()` ਰਾਹੀਂ ਲੰਘਾਓ (ਧੋਖਾਧੜੀ-ਰੋਕਥਾਮ: ਪ੍ਰਤੀ ਕੁੰਜੀ ਵੱਧ ਤੋਂ ਵੱਧ 1000 XP/ਮਿੰਟ)।
3. ਇੱਕ ਟ੍ਰਾਂਜ਼ੈਕਸ਼ਨ ਖੋਲ੍ਹੋ:
   - ਮੌਜੂਦਾ `user_levels` ਕਤਾਰ ਪੜ੍ਹੋ।
   - XP ਜੋੜੋ; `levelFromXp(totalXp)` ਰਾਹੀਂ ਲੈਵਲ ਦੀ ਮੁੜ ਗਣਨਾ ਕਰੋ।
   - ਜੇ ਲੈਵਲ ਬਦਲ ਗਿਆ ਹੈ, ਤਾਂ `levelUp = true` ਸੈੱਟ ਕਰੋ।
   - `user_levels` ਕਤਾਰ ਅੱਪਡੇਟ ਕਰੋ।
   - `xp_audit_log` ਵਿੱਚ ਸ਼ਾਮਲ ਕਰੋ।
4. ਨਤੀਜਾ ਵਾਪਸ ਕਰੋ। ਕਾਲਰ ਸੂਚਨਾਵਾਂ ਨੂੰ ਸੰਭਾਲਦਾ ਹੈ।

### ਸਹਾਇਕ: `levelFromXp(totalXp)`

ਇਹ ਲੈਵਲ 1..100 ਉੱਤੇ ਦੁਹਰਾਉਂਦਾ ਹੈ ਅਤੇ `xp_for_level(n)` ਨੂੰ ਉਦੋਂ ਤੱਕ ਜੋੜਦਾ ਹੈ ਜਦੋਂ ਤੱਕ ਕੁੱਲ XP
`totalXp` ਤੋਂ ਵੱਧ ਨਹੀਂ ਜਾਂਦਾ। ਇਹ ਉਹ ਸਭ ਤੋਂ ਉੱਚਾ ਲੈਵਲ ਵਾਪਸ ਕਰਦਾ ਹੈ ਜਿਸਦੀ ਸੀਮਾ ਪੂਰੀ ਹੋ ਚੁੱਕੀ ਹੈ।
ਇਹ O(100) ਹੈ — ਸਵੀਕਾਰਯੋਗ ਹੈ ਕਿਉਂਕਿ ਲੈਵਲਾਂ ਦੀ ਵੱਧ ਤੋਂ ਵੱਧ ਸੀਮਾ 100 ਹੈ।

### ਮੁਲਾਂਕਣ ਪ੍ਰਵਾਹ

```
emitGamificationEvent(event)
  → evaluateBadges(apiKeyId, event)
    → getBadgeDefinitions()           # ਸਾਰੀਆਂ ਪਰਿਭਾਸ਼ਾਵਾਂ
    → getUserBadges(apiKeyId)         # ਪਹਿਲਾਂ ਹੀ ਪ੍ਰਾਪਤ ਕੀਤੇ ਹੋਏ (ਛੱਡੋ)
    → ਹਰ ਅਜੇ ਤੱਕ ਨਾ ਪ੍ਰਾਪਤ ਕੀਤੇ ਬੈਜ ਲਈ:
       → matchesCriteria(badge, event, userState)
       → ਜੇ ਮੇਲ ਖਾਂਦਾ ਹੈ: awardBadge(apiKeyId, badgeId)
         → ਸੂਚਨਾ ਪੇਲੋਡ ਵਾਪਸ ਕਰੋ
```

ਮੁਲਾਂਕਣ **ਇਵੈਂਟ-ਅਧਾਰਿਤ** ਹੈ — ਇਹ ਹਰ ਗੇਮੀਫਿਕੇਸ਼ਨ ਇਵੈਂਟ ਤੋਂ ਬਾਅਦ ਚੱਲਦਾ ਹੈ, ਪਰ
ਸਿਰਫ਼ ਉਹਨਾਂ ਬੈਜਾਂ ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ ਜਿਨ੍ਹਾਂ ਦਾ `criteria.type` ਇਵੈਂਟ ਕਾਰਵਾਈ ਨਾਲ ਮੇਲ ਖਾਂਦਾ ਹੈ। ਇਸ ਨਾਲ
ਮੁਲਾਂਕਣ ਤੇਜ਼ ਰਹਿੰਦਾ ਹੈ (ਜ਼ਿਆਦਾਤਰ ਇਵੈਂਟਾਂ ਲਈ < 5ms)।

## ਸਟ੍ਰੀਕ ਟ੍ਰੈਕਰ

**ਫ਼ਾਈਲ:** `src/lib/gamification/streaks.ts`

### ਡਾਟਾ ਮਾਡਲ

ਸਟ੍ਰੀਕਾਂ ਨੂੰ `key_value` ਟੇਬਲ (ਸਾਂਝੀ ਯੂਟਿਲਿਟੀ ਟੇਬਲ) ਵਿੱਚ ਨੇਮਸਪੇਸ ਵਾਲੀਆਂ ਕੁੰਜੀਆਂ ਹੇਠ ਸਟੋਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ:

| ਕੁੰਜੀ                         | ਮੁੱਲ                             | ਵੇਰਵਾ             |
| ----------------------------- | -------------------------------- | ----------------- |
| `gamification:streak:{keyId}` | `{current},{longest},{lastDate}` | ਸਰਗਰਮ ਸਟ੍ਰੀਕ ਡਾਟਾ |

### ਤਰਕ

```typescript
export async function updateStreak(
  apiKeyId: string
): Promise<{ current: number; longest: number; milestone: boolean }>;
```

1. `key_value` ਤੋਂ ਸਟ੍ਰੀਕ ਰਿਕਾਰਡ ਪੜ੍ਹੋ।
2. `{current}`, `{longest}`, `{lastDate}` (ISO ਮਿਤੀ ਸਟ੍ਰਿੰਗ) ਨੂੰ ਪਾਰਸ ਕਰੋ।
3. ਜੇ `lastDate === today` — ਕੋਈ ਤਬਦੀਲੀ ਨਹੀਂ (ਅੱਜ ਪਹਿਲਾਂ ਹੀ ਗਿਣਿਆ ਜਾ ਚੁੱਕਾ ਹੈ)।
4. ਜੇ `lastDate === yesterday` — `current` ਨੂੰ ਵਧਾਓ; ਲੋੜ ਪੈਣ 'ਤੇ `longest` ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ।
5. ਜੇ `lastDate < yesterday` — `current = 1` ਰੀਸੈੱਟ ਕਰੋ (ਸਟ੍ਰੀਕ ਟੁੱਟ ਗਈ)।
6. ਅੱਪਡੇਟ ਕੀਤਾ ਰਿਕਾਰਡ ਲਿਖੋ।
7. ਮੀਲਪੱਥਰਾਂ ਦੀ ਜਾਂਚ ਕਰੋ: 7, 14, 30, 60, 90, 180, 365 ਦਿਨ। ਜੇ ਕੋਈ ਮੀਲਪੱਥਰ ਪਾਰ ਹੋਇਆ ਹੈ, ਤਾਂ
   `milestone = true` ਸੈੱਟ ਕਰੋ (ਕਾਲਰ XP ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ ਅਤੇ ਬੈਜਾਂ ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ)।

### ਵਿਸ਼ੇਸ਼ ਸਥਿਤੀਆਂ

- **ਸਮਾਂ ਖੇਤਰ**: ਸਟ੍ਰੀਕਾਂ UTC ਮਿਤੀਆਂ (`new Date().toISOString().slice(0, 10)`) ਦੀ ਵਰਤੋਂ ਕਰਦੀਆਂ ਹਨ।
  ਇਹ ਜਾਣਬੁੱਝ ਕੇ ਕੀਤਾ ਗਿਆ ਹੈ — ਇੱਕੋ ਪ੍ਰਮਾਣਿਕ ਸਮਾਂ ਖੇਤਰ, ਸਮਾਂ ਖੇਤਰ ਬਦਲ ਕੇ ਸਿਸਟਮ ਨਾਲ ਹੇਰਾਫੇਰੀ ਕਰਨ ਤੋਂ ਰੋਕਦਾ ਹੈ।
- **ਨਵੇਂ ਵਰਤੋਂਕਾਰ**: ਕੋਈ ਸਟ੍ਰੀਕ ਰਿਕਾਰਡ ਮੌਜੂਦ ਨਹੀਂ ਹੁੰਦਾ; ਪਹਿਲੀ ਬੇਨਤੀ
  `current=1, longest=1, lastDate=today` ਨਾਲ ਇਸਨੂੰ ਬਣਾਉਂਦੀ ਹੈ।
- **ਪ੍ਰਤੀ ਦਿਨ ਕਈ ਬੇਨਤੀਆਂ**: UTC ਦਿਨ ਦੀ ਸਿਰਫ਼ ਪਹਿਲੀ ਬੇਨਤੀ ਹੀ
  ਸਟ੍ਰੀਕ ਨੂੰ ਵਧਾਉਂਦੀ ਹੈ।

## ਟੋਕਨ ਸਾਂਝਾਕਰਨ

**ਫ਼ਾਈਲ:** `src/lib/gamification/sharing.ts`

### ਦੋਹਰੀ-ਐਂਟਰੀ ਲੈਜਰ

ਹਰ ਟ੍ਰਾਂਸਫ਼ਰ `token_ledger` ਵਿੱਚ ਦੋ ਕਤਾਰਾਂ ਬਣਾਉਂਦਾ ਹੈ:

| ਕਤਾਰ    | `from_key_id` | `to_key_id` | `amount` |
| ------- | ------------- | ----------- | -------- |
| ਡੈਬਿਟ   | ਭੇਜਣ ਵਾਲਾ     | ਪ੍ਰਾਪਤਕਰਤਾ  | +amount  |
| ਕ੍ਰੈਡਿਟ | ਪ੍ਰਾਪਤਕਰਤਾ    | ਭੇਜਣ ਵਾਲਾ   | -amount  |

ਰੁਕੋ — ਪ੍ਰਚਲਿਤ ਨਿਯਮ ਇਹ ਹੈ:

| ਕਤਾਰ        | `from_key_id` | `to_key_id` | `amount` | ਅਰਥ                           |
| ----------- | ------------- | ----------- | -------- | ----------------------------- |
| ਭੇਜਣਾ       | ਭੇਜਣ ਵਾਲਾ     | ਪ੍ਰਾਪਤਕਰਤਾ  | +amount  | ਭੇਜਣ ਵਾਲੇ ਤੋਂ ਬਾਹਰੀ ਪ੍ਰਵਾਹ    |
| ਪ੍ਰਾਪਤ ਕਰਨਾ | ਪ੍ਰਾਪਤਕਰਤਾ    | ਭੇਜਣ ਵਾਲਾ   | +amount  | ਪ੍ਰਾਪਤਕਰਤਾ ਵੱਲ ਅੰਦਰੂਨੀ ਪ੍ਰਵਾਹ |

ਬਕਾਇਆ ਇਸ ਤਰ੍ਹਾਂ ਗਿਣਿਆ ਜਾਂਦਾ ਹੈ:

```sql
SELECT
  COALESCE(SUM(CASE WHEN to_key_id = ? THEN amount ELSE 0 END), 0)
  - COALESCE(SUM(CASE WHEN from_key_id = ? THEN amount ELSE 0 END), 0)
  AS balance
FROM token_ledger
WHERE from_key_id = ? OR to_key_id = ?
```

### ਟ੍ਰਾਂਸਫ਼ਰ ਪ੍ਰਵਾਹ

```typescript
export async function transferTokens(
  fromKeyId: string,
  toKeyId: string,
  amount: number,
  idempotencyKey: string
): Promise<{ success: boolean; balance: number }>;
```

1. **ਪ੍ਰਮਾਣਿਤ ਕਰੋ**: `amount > 0`, `fromKeyId !== toKeyId`।
2. **ਇਡੈਂਪੋਟੈਂਸੀ**: ਜਾਂਚੋ ਕਿ ਕੀ `idempotency_key` ਪਹਿਲਾਂ ਹੀ ਲੈਜਰ ਵਿੱਚ ਮੌਜੂਦ ਹੈ।
   ਜੇ ਹਾਂ, ਤਾਂ ਕੈਸ਼ ਕੀਤਾ ਨਤੀਜਾ ਵਾਪਸ ਕਰੋ।
3. **ਟ੍ਰਾਂਜ਼ੈਕਸ਼ਨ** (ਇੱਕੋ SQLite ਟ੍ਰਾਂਜ਼ੈਕਸ਼ਨ):
   a. ਭੇਜਣ ਵਾਲੇ ਦਾ ਬਕਾਇਆ ਗਿਣੋ।
   b. ਜੇ `balance < amount` ਹੋਵੇ, ਤਾਂ ਰੱਦ ਕਰੋ (ਨਾਕਾਫ਼ੀ ਫੰਡ)।
   c. ਭੇਜਣ ਵਾਲੀ ਕਤਾਰ ਸ਼ਾਮਲ ਕਰੋ (`from=sender,` ਵਾਪਸ ਕਰੋ।

### ਦਰ ਸੀਮਿਤ ਕਰਨਾ

- ਪ੍ਰਤੀ API ਕੁੰਜੀ ਪ੍ਰਤੀ ਮਿੰਟ ਵੱਧ ਤੋਂ ਵੱਧ 10 ਟ੍ਰਾਂਸਫ਼ਰ।
- ਇੱਕ ਟ੍ਰਾਂਸਫ਼ਰ ਵਿੱਚ ਵੱਧ ਤੋਂ ਵੱਧ 10,000 ਟੋਕਨ।
- ਪ੍ਰਤੀ API ਕੁੰਜੀ ਪ੍ਰਤੀ ਦਿਨ ਵੱਧ ਤੋਂ ਵੱਧ 100,000 ਟੋਕਨ ਟ੍ਰਾਂਸਫ਼ਰ ਕੀਤੇ ਜਾ ਸਕਦੇ ਹਨ।

## ਟੋਕਨ ਸੱਦੋ ਅਤੇ ਰੀਡੀਮ ਕਰੋ

**ਫ਼ਾਈਲ:** `src/lib/gamification/invites.ts`

### ਕੋਡ ਫਾਰਮੈਟ

- **ਕੋਡ**: 8-ਅੱਖਰਾਂ ਵਾਲਾ ਅੱਖਰ-ਅੰਕੀ ਕੋਡ (ਉਦਾਹਰਨ ਲਈ, `A3K9-X7M2`), ਮਨੁੱਖਾਂ ਲਈ ਪੜ੍ਹਨਯੋਗ,
  ਜੋ ਵਰਤੋਂਕਾਰ ਨੂੰ ਦਿਖਾਇਆ ਜਾਂਦਾ ਹੈ।
- **ਟੋਕਨ**: 32-ਬਾਈਟ ਦਾ ਬੇਤਰਤੀਬ ਟੋਕਨ, ਜੋ SHA-256 ਹੈਸ਼ ਵਜੋਂ ਸਟੋਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਇਸਦੀ ਵਰਤੋਂ
  ਪ੍ਰੋਗਰਾਮੈਟਿਕ ਰੀਡੈਂਪਸ਼ਨ ਲਈ ਕੀਤੀ ਜਾਂਦੀ ਹੈ (ਉਦਾਹਰਨ ਲਈ, URL ਲਿੰਕ)।

### ਸਟੋਰੇਜ

| ਕਾਲਮ         | ਮੁੱਲ                                  |
| ------------ | ------------------------------------- |
| `code`       | `A3K9X7M2` (ਵਿਲੱਖਣ, ਇੰਡੈਕਸ ਕੀਤਾ ਹੋਇਆ) |
| `token_hash` | SHA-256(raw_token)                    |

ਕੱਚਾ ਟੋਕਨ ਬਣਾਉਣ ਸਮੇਂ ਵਰਤੋਂਕਾਰ ਨੂੰ ਸਿਰਫ਼ ਇੱਕ ਵਾਰ ਵਾਪਸ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ। OmniRoute
ਇਸਨੂੰ ਮੁੜ ਕਦੇ ਵੀ ਸਟੋਰ ਜਾਂ ਪ੍ਰਦਰਸ਼ਿਤ ਨਹੀਂ ਕਰਦਾ — ਸਿਰਫ਼ ਹੈਸ਼ ਹੀ ਕਾਇਮ ਰਹਿੰਦਾ ਹੈ।

### ਖ਼ੁਦ-ਰੈਫ਼ਰਲ ਦੀ ਰੋਕਥਾਮ

ਜਦੋਂ ਕੋਈ ਵਰਤੋਂਕਾਰ ਕੋਡ ਰੀਡੀਮ ਕਰਦਾ ਹੈ, ਤਾਂ ਸਿਸਟਮ ਇਹ ਜਾਂਚਦਾ ਹੈ:

1. ਕੋਡ ਕਿਸੇ ਵੱਖਰੇ `api_key_id` ਨਾਲ ਸੰਬੰਧਿਤ ਹੈ।
2. ਰੀਡੀਮ ਕਰਨ ਵਾਲੇ ਵਰਤੋਂਕਾਰ ਨੇ ਪਹਿਲਾਂ ਉਸੇ
   ਰੈਫ਼ਰਰ ਤੋਂ ਕੋਈ ਕੋਡ ਰੀਡੀਮ ਨਹੀਂ ਕੀਤਾ (`invite_tokens` + ਰੀਡੈਂਪਸ਼ਨ ਲੌਗ ਉੱਤੇ joins)।

ਜੇ ਕੋਈ ਵੀ ਜਾਂਚ ਅਸਫਲ ਰਹਿੰਦੀ ਹੈ, ਤਾਂ ਰੀਡੈਂਪਸ਼ਨ ਨੂੰ ਇੱਕ ਸਪਸ਼ਟ ਗਲਤੀ ਸੁਨੇਹੇ ਨਾਲ ਰੱਦ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ।

### ਮਿਆਦ ਅਤੇ ਸੀਮਾਵਾਂ

- ਡਿਫੌਲਟ `max_uses`: 10 (ਬਣਾਉਣ ਵੇਲੇ ਸੰਰਚਨਾ-ਯੋਗ)।
- ਡਿਫੌਲਟ `expires_at`: ਬਣਾਉਣ ਤੋਂ 30 ਦਿਨ ਬਾਅਦ।
- ਮਿਆਦ ਪੁੱਗੇ ਜਾਂ ਪੂਰੀ ਤਰ੍ਹਾਂ ਵਰਤੇ ਜਾ ਚੁੱਕੇ ਕੋਡ HTTP 410 Gone ਵਾਪਸ ਕਰਦੇ ਹਨ।

## ਕਮਿਊਨਿਟੀ ਸਰਵਰ ਫੈਡਰੇਸ਼ਨ

**ਫ਼ਾਈਲ:** `src/lib/gamification/servers.ts`

### ਕਨੈਕਟ ਕਰਨਾ

ਕਮਿਊਨਿਟੀ ਸਰਵਰ ਨੂੰ ਰਿਮੋਟ ਸਰਵਰ ਵੱਲੋਂ ਜਾਰੀ ਕੀਤੇ ਸੱਦਾ ਟੋਕਨ ਰਾਹੀਂ ਰਜਿਸਟਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਲੋਕਲ ਇੰਸਟੈਂਸ:

1. ਸੱਦਾ ਟੋਕਨ ਪ੍ਰਾਪਤ ਕਰਦਾ ਹੈ (ਉਦਾਹਰਨ ਲਈ, ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ ਪੇਸਟ ਕੀਤਾ ਗਿਆ)।
2. ਟੋਕਨ ਦੀ ਪੁਸ਼ਟੀ ਕਰਨ ਅਤੇ ਮੌਜੂਦਾ ਲੀਡਰਬੋਰਡ ਪ੍ਰਾਪਤ ਕਰਨ ਲਈ ਰਿਮੋਟ ਸਰਵਰ ਉੱਤੇ `POST /api/gamification/federation/leaderboard` ਨੂੰ ਕਾਲ ਕਰਦਾ ਹੈ।
3. ਸਰਵਰ ਰਿਕਾਰਡ ਨੂੰ `status: connected` ਨਾਲ ਸਟੋਰ ਕਰਦਾ ਹੈ।

### ਸਿੰਕ ਮਾਡਲ

ਫੈਡਰੇਸ਼ਨ **ਓਵਰਰਾਈਟ ਸਿੰਕ** ਦੀ ਵਰਤੋਂ ਕਰਦੀ ਹੈ, ਐਡਿਟਿਵ ਸਿੰਕ ਦੀ ਨਹੀਂ:

```
ਲੋਕਲ ਇੰਸਟੈਂਸ                 ਕਮਿਊਨਿਟੀ ਸਰਵਰ
     │                              │
     ├── ਸਕੋਰ ਪੁਸ਼ ਕਰੋ ─────────────►│  POST /federation/score
     │   { api_key_id, score }      │  (ਸਰਵਰ ਟੋਕਨ ਹੈਸ਼ ਦੀ ਪੁਸ਼ਟੀ ਕਰਦਾ ਹੈ)
     │                              │
     ├── ਲੀਡਰਬੋਰਡ ਪੁੱਲ ਕਰੋ ─────────►│  GET /federation/leaderboard
     │◄── ਸਿਖਰਲੇ-N ਰਿਕਾਰਡ ──────────┤  (ਲੋਕਲ ਕੈਸ਼ ਨੂੰ ਓਵਰਰਾਈਟ ਕਰਦਾ ਹੈ)
     │                              │
     └── ਸਿਹਤ ਜਾਂਚ ─────────────────►│  GET /federation/health
         (ਹਰ 60s ਬਾਅਦ, ਟਾਈਮਆਉਟ 5s) │
```

### ਪ੍ਰਮਾਣੀਕਰਨ

ਫੈਡਰੇਸ਼ਨ ਬੇਨਤੀਆਂ ਵਿੱਚ ਇਹ ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ:

```
Authorization: Bearer <raw_token>
X-Federation-Version: 1
```

ਰਿਮੋਟ ਸਰਵਰ ਟੋਕਨ ਨੂੰ ਹੈਸ਼ ਕਰਦਾ ਹੈ ਅਤੇ ਮੇਲ ਖਾਂਦੀ `community_servers` ਕਤਾਰ ਲੱਭਦਾ ਹੈ। ਇਸ ਨਾਲ ਸਟੋਰ ਕੀਤੇ ਹੈਸ਼ ਨੂੰ ਭੇਜਣ ਤੋਂ ਬਚਿਆ ਜਾਂਦਾ ਹੈ।

### ਸਿਹਤ ਨਿਗਰਾਨੀ

ਹਰੇਕ ਸਰਵਰ ਰਿਕਾਰਡ ਇਹਨਾਂ ਨੂੰ ਟਰੈਕ ਕਰਦਾ ਹੈ:

| ਫ਼ੀਲਡ       | ਵੇਰਵਾ                                  |
| ----------- | -------------------------------------- |
| `status`    | `connected`, `degraded`, `unreachable` |
| `last_sync` | ਆਖਰੀ ਸਫਲ ਸਿੰਕ ਦਾ ISO ਟਾਈਮਸਟੈਂਪ         |
| `failures`  | ਲਗਾਤਾਰ ਸਿਹਤ ਜਾਂਚ ਅਸਫਲਤਾਵਾਂ             |

ਲਗਾਤਾਰ 5 ਅਸਫਲਤਾਵਾਂ ਤੋਂ ਬਾਅਦ, ਸਥਿਤੀ `unreachable` ਵਿੱਚ ਬਦਲ ਜਾਂਦੀ ਹੈ ਅਤੇ ਸਿੰਕ ਉਦੋਂ ਤੱਕ ਰੋਕ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ ਜਦੋਂ ਤੱਕ ਹੱਥੀਂ ਕੀਤੀ ਸਿਹਤ ਜਾਂਚ ਸਫਲ ਨਹੀਂ ਹੋ ਜਾਂਦੀ।

## ਧੋਖਾਧੜੀ-ਰੋਕਥਾਮ

**ਫ਼ਾਈਲ:** `src/lib/gamification/antiCheat.ts`

### ਸਰਵਰ-ਸਾਈਡ ਸਕੋਰਿੰਗ

ਸਾਰੀਆਂ XP ਗਣਨਾਵਾਂ `src/lib/gamification/xp.ts` ਵਿੱਚ ਹੁੰਦੀਆਂ ਹਨ। ਕਲਾਇੰਟ ਕਦੇ ਵੀ ਸਕੋਰ ਜਮ੍ਹਾਂ ਨਹੀਂ ਕਰਦੇ — ਉਹ ਕਾਰਵਾਈਆਂ ਜਮ੍ਹਾਂ ਕਰਦੇ ਹਨ ਅਤੇ ਸਰਵਰ XP ਦੀ ਗਣਨਾ ਕਰਦਾ ਹੈ। `leaderboard.score` ਕਾਲਮ ਨੂੰ ਸਿਰਫ਼ ਸਰਵਰ-ਸਾਈਡ ਕੋਡ ਵੱਲੋਂ ਹੀ ਲਿਖਿਆ ਜਾ ਸਕਦਾ ਹੈ।

### ਦਰ ਸੀਮਾਬੰਦੀ

| ਸੀਮਾ                             | ਮੁੱਲ    | ਦਾਇਰਾ           |
| -------------------------------- | ------- | --------------- |
| ਪ੍ਰਤੀ ਮਿੰਟ ਵੱਧ ਤੋਂ ਵੱਧ XP        | 1,000   | ਪ੍ਰਤੀ API ਕੁੰਜੀ |
| ਪ੍ਰਤੀ ਮਿੰਟ ਵੱਧ ਤੋਂ ਵੱਧ ਟ੍ਰਾਂਸਫ਼ਰ | 10      | ਪ੍ਰਤੀ API ਕੁੰਜੀ |
| ਵੱਧ ਤੋਂ ਵੱਧ ਟ੍ਰਾਂਸਫ਼ਰ ਰਕਮ        | 10,000  | ਪ੍ਰਤੀ ਟ੍ਰਾਂਸਫ਼ਰ |
| ਵੱਧ ਤੋਂ ਵੱਧ ਰੋਜ਼ਾਨਾ ਟ੍ਰਾਂਸਫ਼ਰ    | 100,000 | ਪ੍ਰਤੀ API ਕੁੰਜੀ |

ਦਰ ਸੀਮਾਵਾਂ ਇਨ-ਮੈਮੋਰੀ ਸਲਾਈਡਿੰਗ ਵਿੰਡੋ ਦੀ ਵਰਤੋਂ ਕਰਦੀਆਂ ਹਨ (`open-sse/services/` ਵਿੱਚ `RateLimitManager` ਵਾਲਾ ਹੀ ਪੈਟਰਨ)। ਜੇ ਪ੍ਰਕਿਰਿਆ ਮੁੜ ਸ਼ੁਰੂ ਹੁੰਦੀ ਹੈ, ਤਾਂ ਇਹ SQLite-ਸਮਰਥਿਤ ਕਾਊਂਟਰਾਂ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ।

### Z-ਸਕੋਰ ਵਿਸੰਗਤੀ ਪਛਾਣ

ਹਰੇਕ API ਕੁੰਜੀ ਲਈ, ਸਿਸਟਮ ਪ੍ਰਤੀ ਘੰਟਾ ਕਮਾਏ XP ਦੀ 7-ਦਿਨਾਂ ਦੀ ਰੋਲਿੰਗ ਵਿੰਡੋ ਕਾਇਮ ਰੱਖਦਾ ਹੈ। ਹਰੇਕ XP ਇਨਾਮ ਉੱਤੇ:

1. ਵਰਤੋਂਕਾਰ ਦੀ ਮੌਜੂਦਾ ਪ੍ਰਤੀ-ਘੰਟਾ XP ਦਰ ਦੀ ਗਣਨਾ ਕਰੋ।
2. ਸਮੂਹ ਦਾ ਔਸਤ ਅਤੇ ਮਿਆਰੀ ਵਿਸਥਾਪਨ ਗਿਣੋ।
3. `z = (user_rate - mean) / stddev` ਦੀ ਗਣਨਾ ਕਰੋ।
4. ਜੇ `z > 3.0` (3 ਮਿਆਰੀ ਵਿਸਥਾਪਨ) ਹੋਵੇ, ਤਾਂ ਇਸ ਨੂੰ ਵਿਸੰਗਤੀ ਵਜੋਂ ਚਿੰਨ੍ਹਿਤ ਕਰੋ।

ਵਿਸੰਗਤੀਆਂ ਨੂੰ `xp_audit_log` ਵਿੱਚ `action = 'anomaly_detected'` ਨਾਲ ਲੌਗ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ ਐਡਮਿਨ ਡੈਸ਼ਬੋਰਡ ਉੱਤੇ ਦਿਖਾਇਆ ਜਾਂਦਾ ਹੈ।

### ਆਡਿਟ ਟ੍ਰੇਲ

ਹਰੇਕ XP ਇਨਾਮ, ਟ੍ਰਾਂਸਫ਼ਰ, ਬੈਜ ਪ੍ਰਾਪਤੀ ਅਤੇ ਵਿਸੰਗਤੀ ਪਛਾਣ ਨੂੰ `xp_audit_log` ਵਿੱਚ ਇਹਨਾਂ ਦੇ ਨਾਲ ਲੌਗ ਕੀਤਾ ਜਾਂਦਾ ਹੈ:

| ਫ਼ੀਲਡ        | ਵੇਰਵਾ                                     |
| ------------ | ----------------------------------------- |
| `api_key_id` | ਕੌਣ                                       |
| `action`     | ਕੀ ਹੋਇਆ (xp_award, transfer, anomaly, …)  |
| `xp_awarded` | ਰਕਮ (ਗੈਰ-XP ਇਵੈਂਟਾਂ ਲਈ 0)                 |
| `metadata`   | ਸੰਦਰਭ ਵਾਲਾ JSON (ਕਾਰਵਾਈ ਦੀ ਕਿਸਮ, ਟੀਚਾ, …) |
| `created_at` | ਕਦੋਂ (ISO 8601)                           |

ਐਡਮਿਨ `GET /api/gamification/anomalies` ਰਾਹੀਂ ਪੂਰੀ ਆਡਿਟ ਟ੍ਰੇਲ ਦੀ ਪੁੱਛਗਿੱਛ ਕਰ ਸਕਦੇ ਹਨ।

## ਪਾਈਪਲਾਈਨ ਏਕੀਕਰਨ

### ਏਕੀਕਰਨ ਬਿੰਦੂ

ਗੇਮੀਫਿਕੇਸ਼ਨ `open-sse/handlers/chatCore.ts` ਵਿੱਚ ਇੱਕੋ ਬਿੰਦੂ 'ਤੇ ਬੇਨਤੀ ਪਾਈਪਲਾਈਨ
ਨਾਲ ਜੁੜਦਾ ਹੈ:

```typescript
// ਕਲਾਇੰਟ ਨੂੰ ਜਵਾਬ ਭੇਜੇ ਜਾਣ ਤੋਂ ਬਾਅਦ:
setImmediate(() => {
  emitGamificationEvent({
    type: "request.completed",
    apiKeyId,
    metadata: {
      provider: selectedProvider,
      model: selectedModel,
      comboId: resolvedCombo?.id,
      compressionUsed: compressionStats?.applied,
      skillUsed: skillExecution?.name,
    },
  }).catch(() => {
    // ਫਾਇਰ-ਐਂਡ-ਫਰਗੈਟ: ਲੌਗ ਕਰੋ ਪਰ ਕਦੇ ਵੀ ਕਲਾਇੰਟ ਤੱਕ ਨਾ ਪਹੁੰਚਾਓ
  });
});
```

### ਇਵੈਂਟ ਕਿਸਮਾਂ

| ਇਵੈਂਟ ਕਿਸਮ          | ਕਦੋਂ ਉਤਪੰਨ ਹੁੰਦਾ ਹੈ                            |
| ------------------- | ---------------------------------------------- |
| `request.completed` | ਸਫਲ LLM ਜਵਾਬ ਭੇਜਿਆ ਗਿਆ                         |
| `provider.switch`   | ਪ੍ਰਦਾਤਾ ਬਦਲਿਆ ਗਿਆ (ਕੌਂਬੋ ਫਾਲਬੈਕ ਗਿਣੇ ਜਾਂਦੇ ਹਨ) |
| `combo.created`     | ਨਵੀਂ ਕੌਂਬੋ ਸੰਰਚਨਾ ਸੰਭਾਲੀ ਗਈ                    |
| `combo.used`        | ਕੌਂਬੋ ਟੀਚਾ ਸਫਲਤਾਪੂਰਵਕ ਹਿੱਟ ਹੋਇਆ                |
| `badge.earned`      | ਬੈਜ ਮੁਲਾਂਕਣ ਨੂੰ ਮੇਲ ਮਿਲਿਆ                      |
| `streak.milestone`  | ਸਟ੍ਰੀਕ ਸੀਮਾ ਪਾਰ ਹੋਈ                            |
| `transfer.sent`     | ਟੋਕਨ ਟ੍ਰਾਂਸਫਰ ਪੂਰਾ ਹੋਇਆ                        |
| `referral.redeemed` | ਸੱਦਾ ਕੋਡ ਸਫਲਤਾਪੂਰਵਕ ਰੀਡੀਮ ਕੀਤਾ ਗਿਆ             |
| `compression.used`  | ਪ੍ਰੌਮਪਟ ਕੰਪ੍ਰੈਸ਼ਨ ਲਾਗੂ ਕੀਤਾ ਗਿਆ                |
| `skill.executed`    | ਸਕਿੱਲ ਐਗਜ਼ੀਕਿਊਸ਼ਨ ਪੂਰਾ ਹੋਇਆ                    |
| `model.first_use`   | ਮਾਡਲ ਪਿਛਲੇ 7 ਦਿਨਾਂ ਵਿੱਚ ਨਹੀਂ ਵਰਤਿਆ ਗਿਆ         |

### ਨਾਨ-ਬਲਾਕਿੰਗ ਗਾਰੰਟੀ

`setImmediate` + `.catch(() => {})` ਪੈਟਰਨ ਇਹ ਯਕੀਨੀ ਬਣਾਉਂਦਾ ਹੈ:

1. ਗੇਮੀਫਿਕੇਸ਼ਨ ਦੇ ਚੱਲਣ ਤੋਂ ਪਹਿਲਾਂ ਜਵਾਬ ਪੂਰੀ ਤਰ੍ਹਾਂ ਭੇਜਿਆ ਜਾਂਦਾ ਹੈ।
2. ਗੇਮੀਫਿਕੇਸ਼ਨ ਦੀਆਂ ਗਲਤੀਆਂ ਕਦੇ ਵੀ ਕਲਾਇੰਟ ਨੂੰ ਨਹੀਂ ਦਿਖਾਈਆਂ ਜਾਂਦੀਆਂ।
3. ਇਵੈਂਟ ਪ੍ਰੋਸੈਸਿੰਗ ਇਨਲਾਈਨ ਨਹੀਂ, ਸਗੋਂ ਅਗਲੇ ਮਾਈਕ੍ਰੋਟਾਸਕ ਵਿੱਚ ਚੱਲਦੀ ਹੈ।
