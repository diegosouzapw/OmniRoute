OmniRoute ਇੱਕ ਆਮ ਮੁਲਾਂਕਣ ਫ੍ਰੇਮਵਰਕ ਨਾਲ ਆਉਂਦਾ ਹੈ, ਜਿਸਦੀ ਵਰਤੋਂ ਤੁਸੀਂ ਰੂਟਿੰਗ
ਕੰਫਿਗਰੇਸ਼ਨਾਂ, ਇਕੱਲੇ ਪ੍ਰਦਾਤਾਵਾਂ/ਮਾਡਲਾਂ, ਜਾਂ ਬੰਡਲ ਕੀਤੇ "ਗੋਲਡਨ ਸੈੱਟ" ਸੂਟਾਂ ਦੀ
ਕਾਰਗੁਜ਼ਾਰੀ ਮਾਪਣ ਲਈ ਕਰ ਸਕਦੇ ਹੋ। ਇਸਦੀ ਵਰਤੋਂ ਰੂਟਿੰਗ ਤਬਦੀਲੀਆਂ ਦੀ ਪੁਸ਼ਟੀ ਕਰਨ, ਨਵੇਂ
ਪ੍ਰਦਾਤਾਵਾਂ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਕਰਨ, ਅਤੇ ਉਨ੍ਹਾਂ ਨੂੰ ਪ੍ਰੋਡਕਸ਼ਨ ਟ੍ਰੈਫਿਕ ਲਈ ਜਾਰੀ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ
ਰਿਲੀਜ਼ਾਂ 'ਤੇ ਰੋਕ-ਸ਼ਰਤਾਂ ਲਾਗੂ ਕਰਨ ਵਾਸਤੇ ਕਰੋ।

ਫ੍ਰੇਮਵਰਕ ਨੂੰ ਹੇਠਾਂ ਦਿੱਤੇ ਰੂਪ ਵਿੱਚ ਲਾਗੂ ਕੀਤਾ ਗਿਆ ਹੈ:

- ਇੱਕ ਸ਼ੁੱਧ ਰਨਰ (`src/lib/evals/evalRunner.ts`) ਜੋ ਇਨ-ਮੈਮੋਰੀ
  ਬਿਲਟ-ਇਨ ਸੂਟ ਰਜਿਸਟਰ ਕਰਦਾ ਹੈ, ਉਮੀਦ ਕੀਤੇ ਮਾਪਦੰਡਾਂ ਦੇ ਮੁਕਾਬਲੇ ਆਉਟਪੁੱਟਾਂ ਦਾ ਮੁਲਾਂਕਣ
  ਕਰਦਾ ਹੈ, ਅਤੇ ਸਕੋਰਕਾਰਡਾਂ ਨੂੰ ਇਕੱਠਾ ਕਰਦਾ ਹੈ।
- ਕਸਟਮ (ਵਰਤੋਂਕਾਰ-ਪਰਿਭਾਸ਼ਿਤ) ਸੂਟਾਂ ਅਤੇ SQLite ਵਿੱਚ ਪਿਛਲੇ ਰਨਾਂ ਲਈ ਇੱਕ ਸਥਿਰਤਾ
  ਪਰਤ (`src/lib/db/evals.ts`)।
- ਇੱਕ ਆਰਕੈਸਟ੍ਰੇਸ਼ਨ ਪਰਤ (`src/lib/evals/runtime.ts`) ਜੋ `POST /v1/chat/completions`
  ਨੂੰ ਅਸਲ ਕਾਲਾਂ ਭੇਜ ਕੇ ਹਰੇਕ ਕੇਸ ਚਲਾਉਂਦੀ ਹੈ, ਲੇਟੈਂਸੀ ਅਤੇ ਆਉਟਪੁੱਟ ਕੈਪਚਰ ਕਰਦੀ ਹੈ,
  ਅਤੇ ਰਨ ਨੂੰ ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੰਭਾਲਦੀ ਹੈ।
- `/api/evals/*` ਅਧੀਨ REST ਐਂਡਪੌਇੰਟ (ਕੇਵਲ ਪ੍ਰਬੰਧਨ-ਪ੍ਰਮਾਣੀਕਰਨ ਲਈ)।
- `Dashboard → Usage → Evals` (`EvalsTab.tsx`) 'ਤੇ ਇੱਕ ਡੈਸ਼ਬੋਰਡ ਸਤਹ।

## ਧਾਰਨਾਵਾਂ

### ਸੂਟ

ਇੱਕ ਸੂਟ ਟੈਸਟ ਕੇਸਾਂ ਦਾ ਇੱਕ ਨਾਮਿਤ ਸੰਗ੍ਰਹਿ ਹੁੰਦਾ ਹੈ, ਜਿਸ ਵਿੱਚ ਇੱਕ `description` ਅਤੇ
ਇੱਕ ਜਾਂ ਵੱਧ ਕੇਸ ਹੁੰਦੇ ਹਨ। ਸੂਟ ਦੋ ਸਰੋਤਾਂ ਤੋਂ ਆਉਂਦੇ ਹਨ:

| ਸਰੋਤ       | ਕਿੱਥੇ ਪਰਿਭਾਸ਼ਿਤ ਹੈ                                 | ਰਨਟਾਈਮ ਦੌਰਾਨ ਬਦਲਣਯੋਗ? |
| ---------- | -------------------------------------------------- | --------------------- |
| `built-in` | ਬੂਟ ਸਮੇਂ `registerSuite()` ਰਾਹੀਂ ਰਜਿਸਟਰ ਕੀਤਾ       | ਨਹੀਂ (ਕੋਡ-ਪਰਿਭਾਸ਼ਿਤ)  |
| `custom`   | SQLite `eval_suites` + `eval_cases` ਵਿੱਚ ਸਟੋਰ ਕੀਤਾ | ਹਾਂ (API/UI ਰਾਹੀਂ)    |

ਮੌਜੂਦਾ ਬਿਲਟ-ਇਨ ਸੂਟ (`src/lib/evals/evalRunner.ts` ਵੇਖੋ):

- `golden-set` — ਸਵਾਗਤ/ਗਣਿਤ/ਅਨੁਵਾਦ/ਸੁਰੱਖਿਆ ਵਿੱਚ 10 ਬੇਸਲਾਈਨ ਕੇਸ
- `coding-proficiency` — Python/JS/SQL/TS/ਬੱਗ ਪਛਾਣ
- `reasoning-logic` — ਤਰਕ-ਵਾਕ, ਸ਼ਬਦੀ ਸਮੱਸਿਆਵਾਂ, ਪੈਟਰਨ ਪਛਾਣ
- `multilingual` — ਅਨੁਵਾਦ ਅਤੇ ਭਾਸ਼ਾ ਪਛਾਣ
- `safety-guardrails` — PII, ਜੇਲਬ੍ਰੇਕ, ਇਨਕਾਰ, ਪੱਖਪਾਤ ਜਾਗਰੂਕਤਾ
- `instruction-following` — ਕੇਵਲ JSON, ਨੰਬਰਬੱਧ ਸੂਚੀਆਂ, ਭਾਸ਼ਾਈ ਪਾਬੰਦੀਆਂ
- `codex-comparison` — ਤੁਲਨਾ ਮੋਡ ਲਈ ਬਣਾਏ ਆਹਮੋ-ਸਾਹਮਣੇ ਕੋਡਿੰਗ ਕਾਰਜ

### ਕੇਸ

ਹਰੇਕ ਕੇਸ ਵਿੱਚ ਇਹ ਹੁੰਦਾ ਹੈ:

| ਫ਼ੀਲਡ      | ਵੇਰਵਾ                                                                   |
| ---------- | ----------------------------------------------------------------------- |
| `id`       | ਸਥਿਰ ਪਛਾਣਕਰਤਾ (ਆਉਟਪੁੱਟਾਂ ਅਤੇ ਮੈਟ੍ਰਿਕਸ ਦੀ ਕੁੰਜੀ ਵਜੋਂ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ)     |
| `name`     | ਮਨੁੱਖਾਂ ਲਈ ਪੜ੍ਹਨਯੋਗ ਲੇਬਲ                                                |
| `model`    | ਜਦੋਂ ਰਨ `suite-default` ਟਾਰਗੇਟਿੰਗ ਵਰਤਦਾ ਹੈ, ਤਾਂ ਡਿਫੌਲਟ ਮਾਡਲ             |
| `input`    | `{ messages, max_tokens? }` — `/v1/chat/completions` ਨੂੰ ਭੇਜਿਆ ਜਾਂਦਾ ਹੈ |
| `expected` | `{ strategy, value }` — ਸਕੋਰਿੰਗ ਮਾਪਦੰਡ (ਹੇਠਾਂ ਵੇਖੋ)                     |
| `tags`     | ਵਿਕਲਪਿਕ ਲੇਬਲ (ਉਦਾਹਰਨ ਲਈ `safety`, `pii`, `jailbreak`)                   |

### ਟਾਰਗੇਟ

ਇੱਕੋ ਸੂਟ ਨੂੰ ਵੱਖ-ਵੱਖ ਟਾਰਗੇਟਾਂ ਵਿਰੁੱਧ ਚਲਾਇਆ ਜਾ ਸਕਦਾ ਹੈ। ਟਾਰਗੇਟ ਸਕੀਮਾ
`src/shared/validation/schemas.ts` ਵਿੱਚ `evalTargetSchema` ਹੈ:

| ਟਾਰਗੇਟ ਕਿਸਮ     | `id`        | ਵਿਹਾਰ                                                                |
| --------------- | ----------- | -------------------------------------------------------------------- |
| `suite-default` | `null`      | ਹਰੇਕ ਕੇਸ ਆਪਣੇ ਬਿਲਟ-ਇਨ `model` ਫ਼ੀਲਡ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ                 |
| `model`         | ਮਾਡਲ ਦਾ ਨਾਮ | ਹਰੇਕ ਕੇਸ ਨੂੰ ਇੱਕ ਸਿੱਧੇ ਮਾਡਲ ਰਾਹੀਂ ਚਲਾਉਂਦਾ ਹੈ (ਉਦਾਹਰਨ ਲਈ `gpt-4o`)    |
| `combo`         | ਕੰਬੋ ਦਾ ਨਾਮ | ਹਰੇਕ ਕੇਸ ਨੂੰ ਇੱਕ ਕੰਬੋ ਰਾਹੀਂ ਚਲਾਉਂਦਾ ਹੈ (ਰੂਟਿੰਗ ਇੰਜਣ ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ) |

`model` ਅਤੇ `combo` ਲਈ `id` ਫ਼ੀਲਡ ਲਾਜ਼ਮੀ ਹੈ (`superRefine` ਰਾਹੀਂ Zod ਦੁਆਰਾ
ਲਾਗੂ ਕੀਤਾ ਗਿਆ)। ਜਦੋਂ `compareTarget` ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ, ਦੋਵੇਂ ਟਾਰਗੇਟ ਵੱਖਰੇ ਹੋਣੇ
ਲਾਜ਼ਮੀ ਹਨ — ਰਨਰ A/B ਤੁਲਨਾ ਲਈ ਦੋਵੇਂ ਰਨਾਂ ਨੂੰ ਇੱਕੋ `runGroupId` ਅਧੀਨ ਸਥਾਈ ਤੌਰ
'ਤੇ ਸੰਭਾਲਦਾ ਹੈ।

## ਸਕੋਰਿੰਗ ਰੂਬਰਿਕਸ

`evaluateCase()` (evalRunner.ts) ਵਿੱਚ ਲਾਗੂ ਕੀਤੇ ਗਏ ਹਨ:

| ਰਣਨੀਤੀ     | ਪਾਸ ਹੋਵੇਗਾ ਜਦੋਂ…                                                    |
| ---------- | ------------------------------------------------------------------- |
| `exact`    | `actualOutput === expected.value`                                   |
| `contains` | `actualOutput.toLowerCase().includes(expected.value.toLowerCase())` |
| `regex`    | `new RegExp(expected.value).test(actualOutput)` ਸੱਚਾ ਹੋਵੇ           |
| `custom`   | `expected.fn(actualOutput, evalCase)` ਸੱਚਾ ਵਾਪਸ ਕਰੇ (ਸਿਰਫ਼ ਬਿਲਟ-ਇਨ) |

**ਨੋਟ:** ਕਸਟਮ-ਫੰਕਸ਼ਨ ਸਕੋਰਿੰਗ ਕੋਡ-ਪਰਿਭਾਸ਼ਿਤ (ਬਿਲਟ-ਇਨ)
ਸੂਟਾਂ ਲਈ ਰਾਖਵੀਂ ਹੈ ਕਿਉਂਕਿ ਫੰਕਸ਼ਨਾਂ ਨੂੰ API ਰਾਹੀਂ ਸੀਰੀਅਲਾਈਜ਼ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ।
`evalCaseBuilderSchema` ਵਰਤੋਂਕਾਰਾਂ ਵੱਲੋਂ ਬਣਾਏ ਸੂਟਾਂ ਲਈ ਸਿਰਫ਼
`contains | exact | regex` ਨੂੰ ਸਵੀਕਾਰ ਕਰਦਾ ਹੈ।

ਇਸ ਵੇਲੇ ਕੋਈ LLM-ਐਜ਼-ਜੱਜ ਜਾਂ ਐਮਬੈਡਿੰਗ-ਅਧਾਰਿਤ ਸਮਾਨਤਾ ਸਕੋਰਰ ਨਹੀਂ ਹੈ — ਇਹ
`evaluateCase()` ਵਿੱਚ ਇੱਕ ਸਾਫ਼-ਸੁਥਰਾ ਐਕਸਟੈਂਸ਼ਨ ਪੁਆਇੰਟ ਹੋਵੇਗਾ।

## ਡਾਟਾਬੇਸ ਸਕੀਮਾ

ਤਿੰਨ ਟੇਬਲਾਂ (ਮਾਈਗ੍ਰੇਸ਼ਨਾਂ `030_create_eval_runs.sql` ਅਤੇ
`031_create_eval_suites.sql`):

| ਟੇਬਲ          | ਉਦੇਸ਼                                                                                                                   |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `eval_suites` | ਕਸਟਮ ਸੂਟ ਮੈਟਾਡਾਟਾ (`id`, `name`, `description`)                                                                         |
| `eval_cases`  | ਹਰ ਸੂਟ ਦੇ ਕੇਸ — `input_json`, `expected_*`, `tags_json`                                                                 |
| `eval_runs`   | ਇਤਿਹਾਸਕ ਰਨ — `pass_rate`, `total`, `passed`, `failed`, `avg_latency_ms`, `summary_json`, `results_json`, `outputs_json` |

ਬਿਲਟ-ਇਨ ਸੂਟ DB ਵਿੱਚ ਸਟੋਰ **ਨਹੀਂ** ਕੀਤੇ ਜਾਂਦੇ। ਉਹ ਮੈਮੋਰੀ ਵਿੱਚ ਰਹਿੰਦੇ ਹਨ ਅਤੇ
ਹਰ ਵਾਰ `evalRunner.ts` ਇੰਪੋਰਟ ਹੋਣ 'ਤੇ ਮੁੜ ਰਜਿਸਟਰ ਕੀਤੇ ਜਾਂਦੇ ਹਨ।

## REST API

ਸਾਰੇ ਐਂਡਪੌਇੰਟਾਂ ਲਈ ਮੈਨੇਜਮੈਂਟ ਪ੍ਰਮਾਣੀਕਰਨ (`requireManagementAuth`) ਲੋੜੀਂਦਾ ਹੈ — ਉਹ
ਪਬਲਿਕ ਪ੍ਰੌਕਸੀ ਸਰਫੇਸ ਦਾ ਹਿੱਸਾ ਨਹੀਂ ਹਨ।

| ਐਂਡਪੌਇੰਟ                      | ਢੰਗ      | ਵੇਰਵਾ                                                       |
| ----------------------------- | -------- | ----------------------------------------------------------- |
| `/api/evals`                  | `GET`    | ਸੂਟਾਂ + ਹਾਲੀਆ ਰਨਾਂ + ਸਕੋਰਕਾਰਡ + ਟਾਰਗੇਟਾਂ + ਕੁੰਜੀਆਂ ਦੀ ਸੂਚੀ  |
| `/api/evals`                  | `POST`   | ਇੱਕ ਸੂਟ ਚਲਾਓ (ਸਿੰਗਲ ਜਾਂ ਤੁਲਨਾ) — ਸਕੀਮਾ `evalRunSuiteSchema` |
| `/api/evals/{suiteId}`        | `GET`    | ਇੱਕ ਸੂਟ ਪ੍ਰਾਪਤ ਕਰੋ (ਬਿਲਟ-ਇਨ ਜਾਂ ਕਸਟਮ)                       |
| `/api/evals/suites`           | `POST`   | ਇੱਕ ਕਸਟਮ ਸੂਟ ਬਣਾਓ — ਸਕੀਮਾ `evalSuiteSaveSchema`             |
| `/api/evals/suites/{suiteId}` | `GET`    | ਇੱਕ ਕਸਟਮ ਸੂਟ ਪ੍ਰਾਪਤ ਕਰੋ                                     |
| `/api/evals/suites/{suiteId}` | `PUT`    | ਇੱਕ ਕਸਟਮ ਸੂਟ ਬਦਲੋ (ਕੇਸ ਮੁੜ ਇਨਸਰਟ ਕੀਤੇ ਜਾਂਦੇ ਹਨ)             |
| `/api/evals/suites/{suiteId}` | `DELETE` | ਇੱਕ ਕਸਟਮ ਸੂਟ ਅਤੇ ਉਸਦੇ ਕੇਸ ਮਿਟਾਓ                             |

### ਇੱਕ ਸੂਟ ਚਲਾਉਣਾ

```bash
curl -X POST http://localhost:20128/api/evals \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "suiteId": "golden-set",
    "target": { "type": "combo", "id": "my-combo" },
    "apiKeyId": "optional-api-key-uuid"
  }'
```

ਵਿਕਲਪਿਕ ਫੀਲਡ:

- `outputs` — ਪਹਿਲਾਂ ਤੋਂ ਗਣਨਾ ਕੀਤੇ ਆਉਟਪੁੱਟਾਂ ਦਾ `Record<caseId, string>`। ਜਦੋਂ ਇਹ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ,
  ਰਨਰ **ਡਿਸਪੈਚ ਛੱਡ ਦਿੰਦਾ ਹੈ** ਅਤੇ ਸਿਰਫ਼ ਕੈਸ਼ ਕੀਤੇ ਆਉਟਪੁੱਟਾਂ ਨੂੰ ਸਕੋਰ ਕਰਦਾ ਹੈ (ਆਫ਼ਲਾਈਨ
  ਮੁਲਾਂਕਣ ਲਈ ਲਾਭਦਾਇਕ)।
- `compareTarget` — ਸਮਾਂਤਰ ਚਲਾਉਣ ਲਈ ਦੂਜਾ ਟਾਰਗੇਟ; ਦੋਵੇਂ ਰਨ ਆਹਮੋ-ਸਾਹਮਣੇ ਵੇਖਣ ਲਈ
  ਇੱਕ ਜਨਰੇਟ ਕੀਤਾ `runGroupId` ਸਾਂਝਾ ਕਰਦੇ ਹਨ।
- `apiKeyId` — ਡਿਸਪੈਚ ਕੀਤੀਆਂ `/v1/chat/completions` ਕਾਲਾਂ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਕਰਨ ਲਈ ਵਰਤੀ ਜਾਣ ਵਾਲੀ
  ਅੰਦਰੂਨੀ API ਕੁੰਜੀ। ਜਦੋਂ `REQUIRE_API_KEY` ਸਮਰੱਥ ਹੋਵੇ ਤਾਂ ਲੋੜੀਂਦੀ ਹੈ।

### ਇੱਕ ਕਸਟਮ ਸੂਟ ਬਣਾਉਣਾ

```bash
curl -X POST http://localhost:20128/api/evals/suites \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Production smoke",
    "description": "Quick sanity check before deploy",
    "cases": [
      {
        "name": "JSON shape",
        "model": "gpt-4o",
        "input": { "messages": [{ "role": "user", "content": "Reply with {\"ok\": true}" }] },
        "expected": { "strategy": "regex", "value": "\"ok\"\\s*:\\s*true" }
      }
    ]
  }'
```

## ਡਿਸਪੈਚ ਪਾਈਪਲਾਈਨ

`runEvalSuiteAgainstTarget()` (`src/lib/evals/runtime.ts`):

1. ਸੂਟ ਨੂੰ ਰਿਜ਼ਾਲਵ ਕਰਦਾ ਹੈ (ਬਿਲਟ-ਇਨ ਜਾਂ ਕਸਟਮ)।
2. ਹਰੇਕ ਕੇਸ ਲਈ, ਕੇਸ ਦੇ `messages`, ਰਿਜ਼ਾਲਵ ਕੀਤੇ `model`, `stream: false`, ਅਤੇ `max_tokens: 512` (ਜਾਂ ਕੇਸ ਦੇ ਓਵਰਰਾਈਡ) ਨਾਲ `/v1/chat/completions` ਲਈ ਇੱਕ `Request` ਬਣਾਉਂਦਾ ਹੈ।
3. ਚੈਟ ਹੈਂਡਲਰ ਨੂੰ ਸਿੱਧਾ ਕਾਲ ਕਰਦਾ ਹੈ (ਇਨ-ਪ੍ਰੋਸੈੱਸ — ਕੋਈ ਵਾਧੂ HTTP ਹੌਪ ਨਹੀਂ)।
4. ਲੇਟੈਂਸੀ ਕੈਪਚਰ ਕਰਦਾ ਹੈ ਅਤੇ `choices[0].message.content` ਜਾਂ Responses-API ਦੇ `output[]` ਪੇਲੋਡ ਵਿੱਚੋਂ ਟੈਕਸਟ ਕੱਢਦਾ ਹੈ।
5. ਸਾਰੇ ਆਉਟਪੁੱਟਾਂ ਨੂੰ `runSuite()` ਰਾਹੀਂ ਸਕੋਰ ਕਰਦਾ ਹੈ, ਫਿਰ `saveEvalRun()` ਰਾਹੀਂ ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੰਭਾਲਦਾ ਹੈ।

ਕੇਸ **ਕ੍ਰਮਵਾਰ** ਚਲਦੇ ਹਨ। ਇਸ ਵੇਲੇ ਕੋਈ ਕੰਕਰੰਸੀ ਫਲੈਗ ਨਹੀਂ ਹੈ।

## ਡੈਸ਼ਬੋਰਡ

UI `Dashboard → Usage → Evals`
(`src/app/(dashboard)/dashboard/usage/components/EvalsTab.tsx`) 'ਤੇ ਸਥਿਤ ਹੈ। ਉੱਥੋਂ ਤੁਸੀਂ ਇਹ ਕਰ ਸਕਦੇ ਹੋ:

- ਕੇਸ-ਦਰ-ਕੇਸ ਪ੍ਰੀਵਿਊ ਨਾਲ ਬਿਲਟ-ਇਨ ਅਤੇ ਕਸਟਮ ਸੂਟ ਬ੍ਰਾਊਜ਼ ਕਰ ਸਕਦੇ ਹੋ।
- ਕੇਸ ਬਿਲਡਰ ਨਾਲ ਕਸਟਮ ਸੂਟ ਬਣਾਉਣ/ਸੰਪਾਦਿਤ ਕਰਨ/ਮਿਟਾਉਣ ਦਾ ਕੰਮ ਕਰ ਸਕਦੇ ਹੋ।
- ਇੱਕ ਟਾਰਗੇਟ (ਸੂਟ ਡਿਫੌਲਟਸ / ਮਾਡਲ / ਕੌਂਬੋ), ਚੋਣਵੇਂ ਤੌਰ 'ਤੇ ਦੂਜਾ `compareTarget`, ਚੋਣਵੇਂ ਤੌਰ 'ਤੇ ਇੱਕ API ਕੁੰਜੀ ਚੁਣ ਸਕਦੇ ਹੋ, ਅਤੇ ਫਿਰ ਮੰਗ ਅਨੁਸਾਰ ਰਨ ਕਰ ਸਕਦੇ ਹੋ।
- ਰਨ ਇਤਿਹਾਸ, ਹਰੇਕ ਕੇਸ ਦੀ ਪਾਸ/ਫੇਲ ਸਥਿਤੀ, ਲੇਟੈਂਸੀ, ਅਤੇ ਕੈਪਚਰ ਕੀਤੇ ਆਉਟਪੁੱਟ ਵੇਖ ਸਕਦੇ ਹੋ।
- ਹਰੇਕ `(suite, target)` ਸਕੋਪ ਲਈ ਨਵੀਨਤਮ ਰਨ ਤੋਂ ਇਕੱਠਾ ਕੀਤਾ ਰੋਲਿੰਗ ਸਕੋਰਕਾਰਡ ਵੇਖ ਸਕਦੇ ਹੋ।

## ਆਟੋ-ਅਸੈਸਮੈਂਟ RFC ਨਾਲ ਸੰਬੰਧ

ਇੱਕ ਵੱਖਰਾ, ਵਧੇਰੇ ਸੀਮਿਤ ਅਸੈਸਮੈਂਟ ਸਬਸਿਸਟਮ `src/domain/assessment/` ਵਿੱਚ ਸਥਿਤ ਹੈ (ਲਾਈਵ ਸਕੋਰਿੰਗ ਇੰਜਣ ਲਈ [AUTO-COMBO.md](../routing/AUTO-COMBO.md) ਵੀ ਵੇਖੋ)।
ਉਹ ਸਬਸਿਸਟਮ Auto Combo ਇੰਜਣ ਨੂੰ ਟਾਰਗੇਟ ਕਰਦਾ ਹੈ — ਪ੍ਰੋਵਾਈਡਰਾਂ ਅਤੇ ਮਾਡਲਾਂ ਨੂੰ ਆਪਣੇ ਆਪ ਸਕੋਰ ਕਰਦਾ ਹੈ ਤਾਂ ਜੋ ਅੱਪਸਟ੍ਰੀਮ ਫੇਲ ਹੋਣ 'ਤੇ ਕੌਂਬੋ ਆਪਣੇ ਆਪ ਠੀਕ ਹੋ ਸਕਣ। ਇਹ ਆਪਣੇ ਰਨਰ, ਆਪਣੇ ਵਰਗੀਕਰਤਾ, ਅਤੇ ਆਪਣੇ ਸਕੋਰਿੰਗ ਤਰਕ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ।

ਇੱਥੇ ਦਸਤਾਵੇਜ਼ਬੱਧ Evals ਫਰੇਮਵਰਕ **ਵਧੇਰੇ ਵਿਆਪਕ, ਆਮ-ਉਦੇਸ਼ ਵਾਲੀ ਟੈਸਟਿੰਗ ਸਤ੍ਹਾ** ਹੈ। ਮਨਮਾਨੇ ਰਿਗ੍ਰੈਸ਼ਨ ਸੂਟਾਂ, A/B ਤੁਲਨਾਵਾਂ, ਅਤੇ ਹਰੇਕ ਰਿਲੀਜ਼ ਦੇ ਸਮੋਕ ਟੈਸਟਾਂ ਲਈ ਇਸਨੂੰ ਤਰਜੀਹ ਦਿਓ। ਜਦੋਂ ਤੁਹਾਨੂੰ ਰਾਊਟਿੰਗ ਫੈਸਲਿਆਂ ਨੂੰ ਪ੍ਰਭਾਵਿਤ ਕਰਨ ਲਈ ਰੀਅਲ-ਟਾਈਮ ਪ੍ਰੋਵਾਈਡਰ ਸਿਹਤ ਦੀ ਲੋੜ ਹੋਵੇ, ਤਾਂ Auto-Assessment ਸਬਸਿਸਟਮ ਦੀ ਵਰਤੋਂ ਕਰੋ।

## CI ਇੰਟੀਗ੍ਰੇਸ਼ਨ

ਇਸ ਵੇਲੇ ਕੋਈ ਸਮਰਪਿਤ `eval:ci` npm ਸਕ੍ਰਿਪਟ ਨਹੀਂ ਹੈ। ਜੇ ਤੁਸੀਂ ਰਿਲੀਜ਼ਾਂ ਨੂੰ eval ਨਤੀਜਿਆਂ ਦੇ ਆਧਾਰ 'ਤੇ ਗੇਟ ਕਰਨਾ ਚਾਹੁੰਦੇ ਹੋ, ਤਾਂ ਦੋ ਰਸਤੇ ਹਨ:

- **HTTP ਰਸਤਾ**: ਸਰਵਰ ਚਾਲੂ ਕਰੋ, ਜਾਣੇ-ਪਛਾਣੇ `suiteId` + `target` ਨਾਲ `POST /api/evals` ਨੂੰ ਕਾਲ ਕਰੋ, ਅਤੇ ਰਿਸਪਾਂਸ ਵਿੱਚ `runs[].summary.passRate >= N` ਹੋਣ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ।
- **ਇਨ-ਪ੍ਰੋਸੈੱਸ ਰਸਤਾ**: ਇੱਕ ਸਕ੍ਰਿਪਟ ਵਿੱਚ `@/lib/evals/runtime` ਤੋਂ `runEvalSuiteAgainstTarget()` ਇੰਪੋਰਟ ਕਰੋ, ਇੱਕ ਟੈਸਟ DB ਦੇ ਵਿਰੁੱਧ ਚਲਾਓ, ਅਤੇ ਵਾਪਸ ਮਿਲੇ `PersistedEvalRun.summary` ਦੀ ਜਾਂਚ ਕਰੋ।

ਰੂਟ ਅਤੇ ਇਤਿਹਾਸ ਨੂੰ ਕਵਰ ਕਰਨ ਵਾਲੇ ਟੈਸਟ
`tests/unit/evals-route.test.ts` ਅਤੇ `tests/unit/evals-history.test.ts` ਵਿੱਚ ਸਥਿਤ ਹਨ।

## ਵਿਸਤਾਰ ਬਿੰਦੂ

ਆਮ ਤਬਦੀਲੀਆਂ ਅਤੇ ਉਹਨਾਂ ਨੂੰ ਕਰਨ ਵਾਲੀਆਂ ਥਾਵਾਂ:

- **ਨਵੀਂ ਸਕੋਰਿੰਗ ਰਣਨੀਤੀ** — `evaluateCase()` (`evalRunner.ts`) ਵਿੱਚ `switch (evalCase.expected.strategy)` ਬਲਾਕ ਦਾ ਵਿਸਤਾਰ ਕਰੋ ਅਤੇ `src/lib/db/evals.ts` ਵਿੱਚ `EvalCaseStrategy` ਅਤੇ `schemas.ts` ਵਿੱਚ `evalCaseBuilderSchema` ਨੂੰ ਵਿਆਪਕ ਕਰੋ।
- **ਨਵਾਂ ਬਿਲਟ-ਇਨ ਸੂਟ** — ਇੱਕ ਸੂਟ ਆਬਜੈਕਟ ਪਰਿਭਾਸ਼ਿਤ ਕਰੋ ਅਤੇ `evalRunner.ts` ਦੇ ਅੰਤ ਵਿੱਚ `registerSuite()` ਕਾਲ ਕਰੋ। `listSuites()` ਇਸਨੂੰ ਆਪਣੇ ਆਪ ਖੋਜ ਲਵੇਗਾ।
- **ਕੰਕਰੰਸੀ ਨਾਲ ਰਨ ਕਰਨਾ** — `runEvalSuiteAgainstTarget()` ਵਿੱਚ ਕ੍ਰਮਵਾਰ `for` ਲੂਪ ਨੂੰ ਸੀਮਿਤ `Promise.all` ਵਿੱਚ ਬਦਲੋ (ਇਸ ਵੇਲੇ ਕੋਈ ਕੰਕਰੰਸੀ ਕੰਟਰੋਲ ਮੌਜੂਦ ਨਹੀਂ ਹੈ)।
- **ਸਟ੍ਰੀਮ/ਟੂਲ-ਕਾਲ ਕੇਸ** — ਇਸ ਵੇਲੇ ਰਨਰ `stream: false` ਨੂੰ ਲਾਜ਼ਮੀ ਕਰਦਾ ਹੈ। ਸਟ੍ਰੀਮਿੰਗ ਜਾਂ ਟੂਲ-ਅਵੇਅਰ ਮੁਲਾਂਕਣ ਲਈ `runtime.ts` ਵਿੱਚ ਤਬਦੀਲੀਆਂ ਦੀ ਲੋੜ ਹੋਵੇਗੀ (ਸਕੋਰਿੰਗ ਤੋਂ ਪਹਿਲਾਂ SSE ਚੰਕਾਂ ਨੂੰ ਕੈਪਚਰ ਅਤੇ ਇਕੱਠਾ ਕਰਨਾ)।
