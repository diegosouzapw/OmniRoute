Traffic Inspector, OmniRoute ਦਾ ਅੰਦਰੂਨੀ HTTPS ਟ੍ਰੈਫਿਕ ਡੀਬੱਗਰ ਹੈ — Charles Proxy / mitmweb / HTTP Toolkit ਵਰਗਾ ਇੱਕ ਟੂਲ, ਜੋ **LLM-aware** ਅਤੇ **agent-aware** ਹੈ। ਇਹ `/dashboard/tools/traffic-inspector` 'ਤੇ ਉਪਲਬਧ ਹੈ ਅਤੇ ਇੱਕੋ ਸਮੇਂ ਵੱਧ ਤੋਂ ਵੱਧ 5 ਕੈਪਚਰ ਸਰੋਤਾਂ ਤੋਂ ਲਾਈਵ ਟ੍ਰੈਫਿਕ ਪ੍ਰਾਪਤ ਕਰਦਾ ਹੈ।

**ਡੈਸ਼ਬੋਰਡ ਟਿਕਾਣਾ:** `/dashboard/tools/traffic-inspector`
**ਸਾਈਡਬਾਰ ਸਮੂਹ:** ਟੂਲ (AgentBridge ਤੋਂ ਬਾਅਦ)
**ਇਹ ਵੀ ਵੇਖੋ:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge ਕੈਪਚਰ ਮੋਡ 1 ਹੈ।

### ਇੱਕ ਪੈਰਾਗ੍ਰਾਫ ਵਿੱਚ ਆਰਕੀਟੈਕਚਰ

`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) ਇੱਕ ਸਾਂਝਾ ਇਨ-ਮੈਮੋਰੀ ਰਿੰਗ ਬਫ਼ਰ ਹੈ (ਡਿਫਾਲਟ ਤੌਰ 'ਤੇ 1000 ਐਂਟਰੀਆਂ, `INSPECTOR_BUFFER_SIZE` ਰਾਹੀਂ ਸੰਰਚਨਾਯੋਗ)। ਸਾਰੇ ਕੈਪਚਰ ਸਰੋਤ `push()` ਰਾਹੀਂ ਇਸ ਵਿੱਚ ਲਿਖਦੇ ਹਨ। ਬਫ਼ਰ `kindDetector.ts` ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਹਰ ਐਂਟਰੀ ਦਾ ਵਰਗੀਕਰਨ ਕਰਦਾ ਹੈ (ਇਹ ਨਿਰਧਾਰਤ ਕਰਦਾ ਹੈ ਕਿ ਕੀ ਇਹ ਇੱਕ LLM ਬੇਨਤੀ ਹੈ), ਇੱਕ `contextKey` (ਸਿਸਟਮ ਪ੍ਰੌਮਪਟ ਦਾ SHA-256 ਫਿੰਗਰਪ੍ਰਿੰਟ) ਗਣਨਾ ਕਰਦਾ ਹੈ ਅਤੇ `globalTrafficBuffer.subscribe()` ਰਾਹੀਂ ਸਾਰੇ WebSocket ਸਬਸਕ੍ਰਾਈਬਰਾਂ ਨੂੰ ਪ੍ਰਸਾਰਿਤ ਕਰਦਾ ਹੈ। ਡੈਸ਼ਬੋਰਡ `GET /api/tools/traffic-inspector/ws` ਰਾਹੀਂ ਕਨੈਕਟ ਹੁੰਦਾ ਹੈ ਅਤੇ ਕਨੈਕਟ ਹੋਣ 'ਤੇ ਇੱਕ ਸਨੈਪਸ਼ਾਟ ਪ੍ਰਾਪਤ ਕਰਦਾ ਹੈ, ਜਿਸ ਤੋਂ ਬਾਅਦ `new`/`update`/`clear` ਇਵੈਂਟ ਆਉਂਦੇ ਹਨ।

## §2 ਕੈਪਚਰ ਮੋਡ

Traffic Inspector **5 ਸਮਕਾਲੀ ਕੈਪਚਰ ਸਰੋਤਾਂ** ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ। ਹਰੇਕ ਨੂੰ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਚਾਲੂ ਜਾਂ ਬੰਦ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ। ਹਰੇਕ `InterceptedRequest` (`src/mitm/inspector/types.ts`) ਉੱਤੇ `source` ਫ਼ੀਲਡ `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"`, ਜਾਂ `"tproxy"` ਵਿੱਚੋਂ ਇੱਕ ਹੁੰਦੀ ਹੈ।

### ਮੋਡ 1 — AgentBridge (ਡਿਫਾਲਟ, ਹਮੇਸ਼ਾ ਚਾਲੂ)

**ਸਰੋਤ:** AgentBridge ਹੈਂਡਲਰ (`src/mitm/handlers/base.ts`)
**ਕਾਰਜ-ਵਿਧੀ:** `MitmHandlerBase` ਵਿੱਚ ਹਰੇਕ `intercept()` ਕਾਲ ਅੱਗੇ ਭੇਜਣ ਤੋਂ ਪਹਿਲਾਂ `hookBufferStart()` ਅਤੇ ਪੂਰਾ ਹੋਣ 'ਤੇ `hookBufferUpdate()` ਨੂੰ ਕਾਲ ਕਰਦੀ ਹੈ। ਕਿਸੇ ਵਾਧੂ ਸੰਰਚਨਾ ਦੀ ਲੋੜ ਨਹੀਂ — AgentBridge ਦੇ ਚਾਲੂ ਹੁੰਦੇ ਹੀ ਕੰਮ ਕਰਦਾ ਹੈ।
**ਪਹੁੰਚ:** AgentBridge ਵਿੱਚ ਸੰਰਚਿਤ 9 IDE ਏਜੰਟ
**ਨੋਟ:** `InterceptedRequest` ਵਿੱਚ `source` ਫ਼ੀਲਡ = `"agent-bridge"`

### ਮੋਡ 2 — ਕਸਟਮ ਹੋਸਟ (DNS ਰੀਡਾਇਰੈਕਟ)

**ਸਰੋਤ:** ਵਰਤੋਂਕਾਰ ਵੱਲੋਂ ਪਰਿਭਾਸ਼ਿਤ ਹੋਸਟ ਸੂਚੀ (`inspector_custom_hosts` ਟੇਬਲ)
**ਕਾਰਜ-ਵਿਧੀ:** UI ਰਾਹੀਂ ਕੋਈ ਹੋਸਟ ਜੋੜਨ ਨਾਲ `/etc/hosts` ਵਿੱਚ `127.0.0.1 <host>` ਜੋੜਿਆ ਜਾਂਦਾ ਹੈ (sudo ਦੀ ਲੋੜ ਹੈ)। ਮੌਜੂਦਾ AgentBridge MITM ਸਰਵਰ (ਪੋਰਟ 443) ਨਵੇਂ ਹੋਸਟ ਲਈ ਗਤੀਸ਼ੀਲ ਤੌਰ 'ਤੇ ਇੱਕ SNI ਸਰਟੀਫਿਕੇਟ ਬਣਾਉਂਦਾ ਹੈ।
**ਪਹੁੰਚ:** ਜੋੜੇ ਗਏ ਹੋਸਟ ਦੀ ਵਰਤੋਂ ਕਰਨ ਵਾਲੀ ਕੋਈ ਵੀ ਐਪਲੀਕੇਸ਼ਨ — ਐਪ ਦੀ ਸੰਰਚਨਾ ਬਦਲਣ ਦੀ ਲੋੜ ਨਹੀਂ
**ਨੋਟ:** `source` = `"custom-host"`

ਵਰਤੋਂ ਦੇ ਉਦਾਹਰਨ:

- Python ਸਕ੍ਰਿਪਟਾਂ ਤੋਂ `api.openai.com` ਦੀ ਨਿਗਰਾਨੀ ਕਰਨਾ
- `my-internal-llm.company.com` ਨੂੰ ਡੀਬੱਗ ਕਰਨਾ
- ਉਸੇ ਨੈੱਟਵਰਕ ਉੱਤੇ ਮੋਬਾਈਲ ਡਿਵਾਈਸਾਂ ਤੋਂ ਟ੍ਰੈਫ਼ਿਕ ਕੈਪਚਰ ਕਰਨਾ (ARP ਸਪੂਫ਼ਿੰਗ ਰਾਹੀਂ — ਉੱਨਤ)

### ਮੋਡ 3 — HTTP_PROXY ਲਿਸਨਰ (ਪੋਰਟ 8080)

**ਸਰੋਤ:** `HTTP_PROXY`/`HTTPS_PROXY` ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲਾਂ ਦੀ ਵਰਤੋਂ ਕਰਨ ਵਾਲੀਆਂ ਐਪਲੀਕੇਸ਼ਨਾਂ
**ਕਾਰਜ-ਵਿਧੀ:** ਪੋਰਟ 8080 ਉੱਤੇ ਇੱਕ ਸੈਕੰਡਰੀ ਲਿਸਨਰ (`src/mitm/inspector/httpProxyServer.ts`), ਜੋ ਇੱਕ ਮਿਆਰੀ ਸਪਸ਼ਟ HTTP/HTTPS ਪ੍ਰੌਕਸੀ ਵਜੋਂ ਕੰਮ ਕਰਦਾ ਹੈ। `CONNECT` ਟਨਲਾਂ (HTTPS) ਅਤੇ ਸਿੱਧੀਆਂ HTTP ਬੇਨਤੀਆਂ ਨੂੰ ਸਵੀਕਾਰ ਕਰਦਾ ਹੈ।
**ਪਹੁੰਚ:** `HTTP_PROXY` ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲ ਦੀ ਪਾਲਣਾ ਕਰਨ ਵਾਲੀ ਕੋਈ ਵੀ ਐਪਲੀਕੇਸ਼ਨ — ਨਾ DNS ਬਦਲਣ ਦੀ ਲੋੜ, ਨਾ sudo ਦੀ
**ਨੋਟ:** `source` = `"http-proxy"`

```bash
# ਇੱਕ ਇਕੱਲੀ ਕਮਾਂਡ ਲਈ ਤੁਰੰਤ ਕੈਪਚਰ:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# ਸ਼ੈੱਲ ਸੈਸ਼ਨ ਵਿੱਚ ਸਥਾਈ ਕੈਪਚਰ:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**TLS ਸੀਮਾ:** HTTPS `CONNECT` ਟਨਲਾਂ ਨੂੰ ਸਿਰਫ਼ ਮੈਟਾਡਾਟਾ (ਹੋਸਟ, ਪੋਰਟ, ਸਮਾਂ) ਵਜੋਂ ਕੈਪਚਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ — TLS ਬੌਡੀ ਨੂੰ ਡਿਫਾਲਟ ਰੂਪ ਵਿੱਚ ਡਿਕ੍ਰਿਪਟ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ। ਪੂਰੀ ਬੌਡੀ ਦੀ ਜਾਂਚ ਲਈ "ਪ੍ਰੌਕਸੀ ਮੋਡ ਵਿੱਚ HTTPS ਡਿਕ੍ਰਿਪਟ ਕਰੋ" ਟੌਗਲ ਨੂੰ ਸਮਰੱਥ ਕਰੋ (ਚੋਣਵਾਂ, AgentBridge ਸਰਟੀਫਿਕੇਟ ਉੱਤੇ ਭਰੋਸਾ ਕੀਤਾ ਜਾਣਾ ਲਾਜ਼ਮੀ ਹੈ)।

**ਪੋਰਟ ਟਕਰਾਅ:** ਜੇ ਪੋਰਟ 8080 ਵਰਤੋਂ ਵਿੱਚ ਹੈ, ਤਾਂ AgentBridge ਇੱਕ ਸੰਰਚਿਤ ਗਲਤੀ ਸਮੇਤ 409 ਵਾਪਸ ਕਰਦਾ ਹੈ। `INSPECTOR_HTTP_PROXY_PORT` ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲ ਰਾਹੀਂ ਪੋਰਟ ਬਦਲੋ।

### ਮੋਡ 4 — ਸਿਸਟਮ-ਵਿਆਪੀ ਪ੍ਰੌਕਸੀ (ਉੱਨਤ, ਚੋਣਵਾਂ)

**ਸਰੋਤ:** OS-ਪੱਧਰੀ ਪ੍ਰੌਕਸੀ ਸੈਟਿੰਗਾਂ (ਮਸ਼ੀਨ ਉੱਤੇ ਸਾਰੀਆਂ ਐਪਾਂ 'ਤੇ ਲਾਗੂ)
**ਕਾਰਜ-ਵਿਧੀ:** ਸਾਰੇ HTTP/HTTPS ਟ੍ਰੈਫ਼ਿਕ ਨੂੰ HTTP_PROXY ਲਿਸਨਰ ਰਾਹੀਂ ਰੀਡਾਇਰੈਕਟ ਕਰਨ ਲਈ OS API ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **ਪਹੁੰਚ:** ਮਸ਼ੀਨ ਉੱਤੇ ਸਿਸਟਮ ਪ੍ਰੌਕਸੀ ਸੈਟਿੰਗਾਂ ਦੀ ਪਾਲਣਾ ਕਰਨ ਵਾਲੀ ਹਰੇਕ ਐਪਲੀਕੇਸ਼ਨ
  **ਨੋਟ:** `source` = `"system-proxy"`

**ਸੁਰੱਖਿਆ ਵਿਧੀਆਂ:**

- ਆਪਣੇ-ਆਪ ਅਸਮਰੱਥ ਹੋਣ ਵਾਲਾ ਟਾਈਮਰ (ਡਿਫਾਲਟ 30 ਮਿੰਟ, `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES` ਰਾਹੀਂ ਸੰਰਚਨਾਯੋਗ)
- ਪਿਛਲੀ ਸਿਸਟਮ ਪ੍ਰੌਕਸੀ ਸਥਿਤੀ DB ਵਿੱਚ ਸੁਰੱਖਿਅਤ ਕੀਤੀ ਜਾਂਦੀ ਹੈ ਅਤੇ ਵਾਪਸ ਮੋੜਨ 'ਤੇ ਬਹਾਲ ਕੀਤੀ ਜਾਂਦੀ ਹੈ
- ਜੇ ਵਰਤੋਂਕਾਰ ਇਸ ਦੇ ਸਰਗਰਮ ਹੋਣ ਦੌਰਾਨ ਦੂਰ ਨੈਵੀਗੇਟ ਕਰਦਾ ਹੈ, ਤਾਂ ਡੈਸ਼ਬੋਰਡ "ਸਿਸਟਮ ਪ੍ਰੌਕਸੀ ਨੂੰ ਵਾਪਸ ਮੋੜਿਆ ਜਾ ਰਿਹਾ ਹੈ" ਪ੍ਰੌਮਪਟ ਦਿਖਾਉਂਦਾ ਹੈ
- UI `⚠ ਉੱਨਤ` ਬੈਜ + ਸਪਸ਼ਟ ਪੁਸ਼ਟੀਕਰਨ ਚੈੱਕਬਾਕਸ ਦਿਖਾਉਂਦਾ ਹੈ

### ਮੋਡ 5 — TPROXY ਪਾਰਦਰਸ਼ੀ ਡਿਕ੍ਰਿਪਸ਼ਨ (Linux, root, ਚੋਣਵਾਂ)

**ਸਰੋਤ:** ਕਰਨਲ TPROXY + ਪਾਲਿਸੀ ਰੂਟਿੰਗ (`src/mitm/tproxy/`)
**ਕਾਰਜ-ਵਿਧੀ:** `mangle OUTPUT` ਵਿੱਚ ਇੱਕ ਟਾਰਗੇਟ ਪੋਰਟ (ਡਿਫਾਲਟ `443`) ਵੱਲ ਜਾਣ ਵਾਲੇ ਨਵੇਂ ਸਥਾਨਕ ਆਊਟਬਾਊਂਡ TCP ਕਨੈਕਸ਼ਨਾਂ ਨੂੰ ਚਿੰਨ੍ਹਿਤ ਕਰਦਾ ਹੈ, ਇੱਕ `ip rule` ਚਿੰਨ੍ਹਿਤ ਪੈਕੇਟਾਂ ਨੂੰ ਸਥਾਨਕ ਡਿਲਿਵਰੀ ਵੱਲ ਮੁੜ-ਰੂਟ ਕਰਦਾ ਹੈ, ਅਤੇ `mangle PREROUTING` ਦਾ `TPROXY` ਟਾਰਗੇਟ ਉਨ੍ਹਾਂ ਨੂੰ ਇੱਕ ਪਾਰਦਰਸ਼ੀ (**IP_TRANSPARENT**) ਲਿਸਨਰ (ਡਿਫਾਲਟ ਪੋਰਟ `8443`) ਨੂੰ ਸੌਂਪਦਾ ਹੈ। ਲਿਸਨਰ ਇੱਕ ਗਤੀਸ਼ੀਲ CA ਵੱਲੋਂ **ਮੰਗ 'ਤੇ ਹਰੇਕ SNI ਹੋਸਟਨੇਮ ਲਈ** ਜਾਰੀ ਕੀਤੇ ਲੀਫ਼ ਸਰਟੀਫਿਕੇਟ ਨਾਲ TLS ਨੂੰ ਸਮਾਪਤ ਕਰਦਾ ਹੈ, ਡਿਕ੍ਰਿਪਟ ਕੀਤੇ ਆਦਾਨ-ਪ੍ਰਦਾਨ ਨੂੰ ਕੈਪਚਰ ਕਰਦਾ ਹੈ, ਅਤੇ ਬੇਨਤੀ ਨੂੰ ਮੁੜ ਇਨਕ੍ਰਿਪਟ ਕਰਕੇ ਮੂਲ ਮੰਜ਼ਿਲ ਵੱਲ ਭੇਜਦਾ ਹੈ।
**ਪਹੁੰਚ:** ਟਾਰਗੇਟ ਪੋਰਟ ਉੱਤੇ **ਕੋਈ ਵੀ** ਮੰਜ਼ਿਲ ਹੋਸਟ — ਨਾ `/etc/hosts` ਸਪੂਫ਼, ਨਾ `HTTP_PROXY` ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲ, ਨਾ ਸਿਸਟਮ-ਵਿਆਪੀ ਪ੍ਰੌਕਸੀ ਵਿੱਚ ਤਬਦੀਲੀ। ਇੰਟਰਸੈਪਟ ਕੀਤੀ ਪ੍ਰਕਿਰਿਆ ਨੂੰ ਕਿਸੇ ਸੰਰਚਨਾ ਬਦਲਾਅ ਦੀ ਲੋੜ ਨਹੀਂ, ਪਰ ਇਸ ਨੂੰ ਗਤੀਸ਼ੀਲ CA ਉੱਤੇ ਭਰੋਸਾ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ।
**ਨੋਟ:** `source` = `"tproxy"`

**ਲੋੜਾਂ:** ਸਿਰਫ਼ Linux (**IP_TRANSPARENT** ਕੇਵਲ Linux ਲਈ ਹੈ), **CAP_NET_ADMIN** ਸਮਰੱਥਾ (root), ਅਤੇ ਇੱਕ ਨੇਟਿਵ N-API ਐਡਆਨ ਜਿਸ ਨੂੰ C ਟੂਲਚੇਨ ਨਾਲ ਬਿਲਡ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ (`npm run build:native:tproxy`)। ਉਪਲਬਧ ਨਾ ਹੋਣ 'ਤੇ, ਡੈਸ਼ਬੋਰਡ ਟੌਗਲ ਨੂੰ "TPROXY ਡਿਕ੍ਰਿਪਸ਼ਨ ਲਈ Linux + root + ਨੇਟਿਵ ਐਡਆਨ ਦੀ ਲੋੜ ਹੈ" ਟੂਲਟਿਪ ਨਾਲ ਅਸਮਰੱਥ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਫਾਇਰਵਾਲ ਨਿਯਮ ਲੈਣ-ਦੇਣ ਅਧਾਰਿਤ ਢੰਗ ਨਾਲ ਲਾਗੂ/ਵਾਪਸ ਕੀਤੇ ਜਾਂਦੇ ਹਨ (ਕ੍ਰੈਸ਼ ਕਦੇ ਵੀ ਕੋਈ `mangle` ਨਿਯਮ ਪਿੱਛੇ ਨਹੀਂ ਛੱਡਦਾ) ਅਤੇ ਰੀਬੂਟ ਹੋਣ 'ਤੇ ਸਾਫ਼ ਹੋ ਜਾਂਦੇ ਹਨ। SO_MARK-ਅਧਾਰਿਤ ਐਂਟੀ-ਲੂਪ ਪ੍ਰੌਕਸੀ ਦੇ ਆਪਣੇ ਮੁੜ-ਇਨਕ੍ਰਿਪਟ ਕੀਤੇ ਫਾਰਵਰਡ ਨੂੰ ਦੁਬਾਰਾ ਇੰਟਰਸੈਪਟ ਹੋਣ ਤੋਂ ਰੋਕਦਾ ਹੈ।

ਇਹ ਆਪਣੀ ਸਮਰਪਿਤ ਓਪਰੇਟਰ ਗਾਈਡ ਵਾਲਾ ਇੱਕ ਵੱਡਾ ਸਬਸਿਸਟਮ ਹੈ — ਪੂਰੀ ਫਾਇਰਵਾਲ ਵਿਧੀ, ਪ੍ਰਤੀ-SNI ਗਤੀਸ਼ੀਲ CA + ਟਰੱਸਟ-ਸਟੋਰ ਇੰਸਟਾਲਰ, ਸਿਰਫ਼-ਸਥਾਨਕ ਰੂਟ, ਐਂਟੀ-ਲੂਪ ਵੇਰਵਿਆਂ ਅਤੇ ਸੰਰਚਨਾ ਸਕੀਮਾ ਲਈ `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs` ਵਿੱਚ ਕੰਪਾਇਲ ਨਹੀਂ ਕੀਤਾ ਗਿਆ) ਵੇਖੋ। ਟੌਗਲ `GET / POST / DELETE /api/tools/agent-bridge/tproxy` ਦੁਆਰਾ ਚਲਾਇਆ ਜਾਂਦਾ ਹੈ (ਨੋਟ: ਰੂਟ Traffic Inspector ਪ੍ਰੀਫਿਕਸ ਦੀ ਬਜਾਏ AgentBridge ਪ੍ਰੀਫਿਕਸ ਹੇਠ ਮੌਜੂਦ ਹੈ)।

## §4 LLM-ਸਚੇਤ ਵਿਸ਼ੇਸ਼ਤਾਵਾਂ

### 4.1 ਕਿਸਮ ਡਿਟੈਕਟਰ (`src/mitm/inspector/kindDetector.ts`)

4 ਸੰਕੇਤਾਂ ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਹਰ ਬੇਨਤੀ ਨੂੰ `"llm"`, `"app"`, ਜਾਂ `"unknown"` ਵਜੋਂ ਵਰਗੀਕ੍ਰਿਤ ਕਰਦਾ ਹੈ:

1. **ਹੋਸਟ ਰਜਿਸਟਰੀ** — ~18 ਜਾਣੇ-ਪਛਾਣੇ LLM API ਹੋਸਟਨਾਮ (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot, ਆਦਿ)
2. **ਪਾਥ ਪੈਟਰਨ** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses`, ਆਦਿ।
3. **ਬਾਡੀ ਆਕਾਰ** — `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input` ਫ਼ੀਲਡਾਂ ਦੀ ਪਛਾਣ ਕਰਦਾ ਹੈ
4. **ਯੂਜ਼ਰ-ਏਜੰਟ ਸੰਕੇਤ** — UA ਸਟ੍ਰਿੰਗ ਵਿੱਚ `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor`

Mode 2 ਰਾਹੀਂ ਜੋੜੇ ਗਏ ਕਸਟਮ ਹੋਸਟ ਆਪਣੇ ਫ਼ਾਰਮ ਇਨਪੁੱਟ ਤੋਂ `kind` ਪ੍ਰਾਪਤ ਕਰਦੇ ਹਨ (ਡਿਫਾਲਟ `"custom"` ਹੈ)।

### 4.2 SSE ਮਰਜਰ (`src/mitm/inspector/sseMerger.ts`)

**ਸੁਤੰਤਰ ਕਲੀਨ-ਰੂਮ ਇੰਪਲੀਮੈਂਟੇਸ਼ਨ।** ਇਵੈਂਟ ਪਾਰਸਿੰਗ
[WHATWG ਸਰਵਰ-ਸੈਂਟ ਇਵੈਂਟਸ ਐਲਗੋਰਿਦਮ](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)
ਦੀ ਪਾਲਣਾ ਕਰਦੀ ਹੈ, ਜਦਕਿ ਪੁਨਰ-ਨਿਰਮਾਣ ਜਨਤਕ [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming), ਅਤੇ
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent)
ਸਟ੍ਰੀਮਿੰਗ ਸਕੀਮਿਆਂ ਦੀ ਪਾਲਣਾ ਕਰਦਾ ਹੈ।

ਕੱਚੇ SSE ਡੈਲਟਾ ਇਵੈਂਟਾਂ ਤੋਂ ਅੰਤਿਮ ਅਸਿਸਟੈਂਟ ਸੁਨੇਹੇ ਦਾ ਪੁਨਰ-ਨਿਰਮਾਣ ਕਰਦਾ ਹੈ:

- **Anthropic**: ਇੰਡੈਕਸ ਅਨੁਸਾਰ `content_block_delta` ਇਕੱਠਾ ਕਰਦਾ ਹੈ; `text_delta`, `input_json_delta` (ਟੂਲ ਕਾਲਾਂ), `thinking_delta` ਨੂੰ ਸੰਭਾਲਦਾ ਹੈ
- **OpenAI**: Chat Completions ਦੀਆਂ ਚੋਣਾਂ/ਟੂਲ ਕਾਲਾਂ ਅਤੇ Responses API ਆਉਟਪੁੱਟ ਆਈਟਮਾਂ ਨੂੰ ਇੰਡੈਕਸ
  ਅਨੁਸਾਰ ਇਕੱਠਾ ਕਰਦਾ ਹੈ
- **Gemini**: `candidates[i].content.parts` ਇਕੱਠਾ ਕਰਦਾ ਹੈ
- **ਅਣਜਾਣ**: ਕੱਚੇ ਇਵੈਂਟਾਂ ਨੂੰ ਜਿਵੇਂ ਹਨ, ਉਸੇ ਤਰ੍ਹਾਂ ਵਾਪਸ ਕਰਦਾ ਹੈ

Response ਟੈਬ ਇੱਕ ਟੌਗਲ ਦਿਖਾਉਂਦੀ ਹੈ: **"ਕੱਚੇ ਇਵੈਂਟ ↔ ਮਰਜ ਕੀਤੇ"**।

### 4.3 ਗੱਲਬਾਤ ਨਾਰਮਲਾਈਜ਼ਰ (`src/mitm/inspector/conversationNormalizer.ts`)

**ਸੁਤੰਤਰ ਕਲੀਨ-ਰੂਮ ਇੰਪਲੀਮੈਂਟੇਸ਼ਨ।** ਨਾਰਮਲਾਈਜ਼ੇਸ਼ਨ ਨੂੰ ਸਥਾਨਕ ਬਲੈਕ-ਬਾਕਸ
ਕਾਂਟ੍ਰੈਕਟਾਂ ਅਤੇ ਜਨਤਕ OpenAI, Anthropic, ਅਤੇ Gemini ਸੁਨੇਹਾ ਸਕੀਮਿਆਂ ਦੁਆਰਾ ਪਰਿਭਾਸ਼ਿਤ ਕੀਤਾ ਗਿਆ ਹੈ; ਕਿਸੇ ਅੱਪਸਟ੍ਰੀਮ
ਇੰਪਲੀਮੈਂਟੇਸ਼ਨ ਸਰੋਤ ਦੀ ਵਰਤੋਂ ਨਹੀਂ ਕੀਤੀ ਗਈ।

ਰੈਂਡਰ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ OpenAI, Anthropic, ਅਤੇ Gemini ਸੁਨੇਹਾ ਫਾਰਮੈਟਾਂ ਨੂੰ ਇੱਕੋ `NormalizedConversation` ਵਿੱਚ ਬਦਲਦਾ ਹੈ:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // ਬੇਨਤੀ ਬਾਡੀ ਤੋਂ ਸੁਨੇਹੇ / ਸਮੱਗਰੀ / ਪ੍ਰੌਂਪਟ
  response: NormalizedTurn[]; // ਅਸਿਸਟੈਂਟ ਜਵਾਬ (sseMerger ਰਾਹੀਂ ਮਰਜ ਕੀਤਾ)
  contextKey: string | null; // SHA-256 ਸਿਸਟਮ-ਪ੍ਰੌਂਪਟ ਫਿੰਗਰਪ੍ਰਿੰਟ
}
```

ਬਲਾਕ ਕਿਸਮਾਂ: `text`, `tool_use`, `tool_result`। Conversation ਟੈਬ ਪ੍ਰਦਾਤਾ ਦੀ ਪਰਵਾਹ ਕੀਤੇ ਬਿਨਾਂ ਇਸੇ ਆਕਾਰ ਦੀ ਵਰਤੋਂ ਕਰਦੀ ਹੈ।

### 4.4 ਕਾਂਟੈਕਸਟ ਕੀ ਰੰਗੀਕਰਨ (`src/mitm/inspector/contextKey.ts`)

- ਸਿਸਟਮ ਪ੍ਰੌਂਪਟ ਦਾ `SHA-256` ਕੱਢਦਾ ਹੈ (ਪਹਿਲਾ `role:system` ਸੁਨੇਹਾ, ਜਾਂ `system` ਫ਼ੀਲਡ, ਜਾਂ Gemini `systemInstruction`)
- 12-ਅੱਖਰੀ ਹੈਕਸ ਪ੍ਰੀਫਿਕਸ (`"a3f9c2..."`) ਵਾਪਸ ਕਰਦਾ ਹੈ
- ਫਰੰਟਐਂਡ ਖੱਬੇ-ਬਾਰਡਰ ਵਾਲੀ ਪੱਟੀ ਲਈ ਕੀ ਨੂੰ ਇੱਕ ਨਿਰਧਾਰਤ HSL ਰੰਗ ਨਾਲ ਮੈਪ ਕਰਦਾ ਹੈ
- **"ਇੱਕੋ ਕਾਂਟੈਕਸਟ" ਫਿਲਟਰ**: `ctx #a3f` ਚਿੱਪ 'ਤੇ ਕਲਿੱਕ ਕਰਨ ਨਾਲ ਸਿਰਫ਼ ਇੱਕੋ ਫਿੰਗਰਪ੍ਰਿੰਟ ਵਾਲੀਆਂ ਬੇਨਤੀਆਂ ਦਿਖਾਉਣ ਲਈ ਇੱਕ ਫਿਲਟਰ ਜੋੜਿਆ ਜਾਂਦਾ ਹੈ

ਇਸ ਨਾਲ ਇੱਕੋ ਏਜੰਟ ਸੈਸ਼ਨ ਵਿੱਚ ਚੱਲ ਰਹੀਆਂ ਵੱਖ-ਵੱਖ "ਪਰਸੋਨਾਵਾਂ" ਜਾਂ ਟਾਸਕਾਂ ਨੂੰ ਦ੍ਰਿਸ਼ਟੀਗਤ ਤੌਰ 'ਤੇ ਵੱਖ ਕਰਨਾ ਆਸਾਨ ਹੋ ਜਾਂਦਾ ਹੈ।

### 4.5 LLM ਮੈਟਾਡਾਟਾ ਐਕਸਟ੍ਰੈਕਸ਼ਨ

LLM ਬੇਨਤੀਆਂ ਲਈ, LLM Details ਟੈਬ ਇਹ ਜਾਣਕਾਰੀ ਕੱਢਦੀ ਹੈ:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // ਬੇਨਤੀ ਬਾਡੀ ਜਾਂ ਜਵਾਬ ਤੋਂ
  messages: number; // ਟਰਨਾਂ ਦੀ ਗਿਣਤੀ
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // ਜੇ SSE ਜਵਾਬ ਹੋਵੇ ਤਾਂ true
  mappedTo: string | null; // x-omniroute-mapped ਹੈਡਰ
  costEstimateUsd: number | null; // OmniRoute ਕੀਮਤਾਂ ਦੇ ਆਧਾਰ 'ਤੇ ਅਨੁਮਾਨਿਤ ਲਾਗਤ
}
```

### 4.6 ਲਾਈਵ ਚੱਲ ਰਹੀ ਬੇਨਤੀ ਦਾ ਫਿਲਟਰ

ਬੇਨਤੀ ਦਾ `status` ਫ਼ੀਲਡ `number | "in-flight" | "error"` ਹੈ — ਬੇਨਤੀ ਸ਼ੁਰੂ ਹੁੰਦੇ ਹੀ ਇੱਕ ਐਂਟਰੀ
ਨੂੰ `"in-flight"` ਵਜੋਂ ਪੁਸ਼ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ ਜਵਾਬ (ਜਾਂ ਗਲਤੀ) ਆਉਣ 'ਤੇ ਇਸਨੂੰ **ਉਸੇ ਥਾਂ ਅੱਪਡੇਟ**
ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਟੂਲਬਾਰ ਦਾ **"ਲਾਈਵ"** ਟੌਗਲ
(`liveOnly`, i18n ਕੀ `trafficInspector.liveOnly`) ਸੂਚੀ ਨੂੰ ਉਹਨਾਂ ਐਂਟਰੀਆਂ ਤੱਕ ਸੀਮਿਤ ਕਰਦਾ ਹੈ
ਜਿਨ੍ਹਾਂ ਦਾ `status === "in-flight"` ਹੈ, ਜਿਸ ਨਾਲ ਤੁਸੀਂ ਖੁੱਲ੍ਹੇ ਕਨੈਕਸ਼ਨਾਂ ਨੂੰ ਰੀਅਲ ਟਾਈਮ ਵਿੱਚ ਦੇਖ ਸਕਦੇ ਹੋ।

ਇਹ ਫਿਲਟਰ
`src/lib/inspector/matchesTrafficFilter.ts` ਵਿੱਚ ਇੱਕ ਸ਼ੁੱਧ, ਕਲਾਇੰਟ-ਸਾਈਡ ਪ੍ਰੈਡੀਕੇਟ ਹੈ:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

ਟੌਗਲ ਦੀ ਸਥਿਤੀ `useTrafficFilters` (ਇੰਸਪੈਕਟਰ ਡੈਸ਼ਬੋਰਡ ਹੁੱਕਾਂ) ਵਿੱਚ ਰਹਿੰਦੀ ਹੈ ਅਤੇ
ਹੋਰ ਫਿਲਟਰਾਂ (ਪ੍ਰੋਫਾਈਲ, ਹੋਸਟ, ਏਜੰਟ, ਸਰੋਤ, ਸਥਿਤੀ, ਕਾਂਟੈਕਸਟ) ਨਾਲ ਮਿਲ ਕੇ ਕੰਮ ਕਰਦੀ ਹੈ।

### 4.7 ਪ੍ਰੋਸੈਸ ਐਟ੍ਰਿਬਿਊਸ਼ਨ (Linux)

Linux ਉੱਤੇ, ਹਰ ਇੰਟਰਸੈਪਟ ਕੀਤੀ ਬੇਨਤੀ ਨੂੰ **ਮੂਲ ਸਥਾਨਕ
ਪ੍ਰੋਸੈਸ** ਨਾਲ ਜੋੜਿਆ ਜਾ ਸਕਦਾ ਹੈ। `InterceptedRequest` ਵਿੱਚ ਦੋ ਵਿਕਲਪਿਕ ਫ਼ੀਲਡ ਜੋੜੇ ਜਾਂਦੇ ਹਨ:

```ts
pid?: number;          // ਮੂਲ ਪ੍ਰੋਸੈਸ id (ਸਿਰਫ਼ Linux)
processName?: string;  // ਮੂਲ ਪ੍ਰੋਸੈਸ ਦਾ ਨਾਮ (ਸਿਰਫ਼ Linux)
```

`src/mitm/inspector/processAttribution.ts` ਕਨੈਕਸ਼ਨ ਦੇ _ਕਲਾਇੰਟ_
ਐਫਿਮਰਲ ਪੋਰਟ ਨੂੰ ਹੇਠਾਂ ਦਿੱਤੇ ਤਰੀਕੇ ਨਾਲ PID + ਨਾਮ ਨਾਲ ਮੈਪ ਕਰਦਾ ਹੈ:

1. ਪੋਰਟ ਲਈ ਸਾਕਟ inode ਲੱਭਣ ਵਾਸਤੇ `/proc/net/tcp` ਅਤੇ `/proc/net/tcp6` ਨੂੰ ਪੜ੍ਹਨਾ
   (`parseProcNetTcpForInode`, ਇੱਕ ਸ਼ੁੱਧ ਫਿਕਸਚਰ-ਟੈਸਟਯੋਗ ਪਾਰਸਰ)।
2. `socket:[<inode>]` ਦੇ ਸਿਮਲਿੰਕ ਲਈ `/proc/<pid>/fd/` ਨੂੰ ਸਕੈਨ ਕਰਨਾ।
3. `/proc/<pid>/comm` ਤੋਂ ਪ੍ਰੋਸੈਸ ਦਾ ਨਾਮ ਪੜ੍ਹਨਾ।

1-ਸਕਿੰਟ ਦਾ TTL ਕੈਸ਼ ਲੋਡ ਅਧੀਨ procfs ਸਕੈਨ ਦੀ ਲਾਗਤ ਨੂੰ ਸੀਮਿਤ ਰੱਖਦਾ ਹੈ। ਐਟ੍ਰਿਬਿਊਸ਼ਨ
**ਬੈਸਟ-ਐਫਰਟ** ਹੈ — ਕੋਈ ਵੀ ਅਸਫਲਤਾ `null` ਵਿੱਚ ਰਿਜ਼ੌਲਵ ਹੁੰਦੀ ਹੈ ਅਤੇ ਕੈਪਚਰ ਨੂੰ ਕਦੇ ਬਲੌਕ ਨਹੀਂ ਕਰਦੀ।
macOS/Windows ਉੱਤੇ ਫੰਕਸ਼ਨ `null` ਵਾਪਸ ਕਰਦਾ ਹੈ (ਸਟੱਬ; `lsof`/`GetExtendedTcpTable`
ਸਹਾਇਤਾ ਇੱਕ ਅਗਲਾ ਕੰਮ ਹੈ)।

## §5 ਸੈਸ਼ਨ

### 5.1 ਸੈਸ਼ਨ ਰਿਕਾਰਡ ਕਰਨਾ

1. ਟੂਲਬਾਰ ਵਿੱਚ **"● ਸੈਸ਼ਨ ਰਿਕਾਰਡ ਕਰੋ"** 'ਤੇ ਕਲਿੱਕ ਕਰੋ → ਇੱਕ ਨਾਮ ਦਾਖਲ ਕਰੋ (ਵਿਕਲਪਿਕ)
2. ਲਾਈਵ ਟੇਲ ਆਮ ਵਾਂਗ ਜਾਰੀ ਰਹਿੰਦੀ ਹੈ; ਇੱਕ ਲਾਲ ਧੜਕਦਾ ਸੂਚਕ `◉ REC · <ਨਾਮ> · 00:42 · 23 ਬੇਨਤੀਆਂ` ਦਿਖਾਉਂਦਾ ਹੈ
3. **"⏹ ਰੋਕੋ"** 'ਤੇ ਕਲਿੱਕ ਕਰੋ → ਸੈਸ਼ਨ ਸਨੈਪਸ਼ਾਟ `inspector_sessions` + `inspector_session_requests` ਵਿੱਚ ਸੁਰੱਖਿਅਤ ਹੋ ਜਾਂਦਾ ਹੈ

### 5.2 ਰਿਕਾਰਡ ਕੀਤਾ ਸੈਸ਼ਨ ਦੇਖਣਾ

ਟੂਲਬਾਰ ਵਿੱਚ **ਸੈਸ਼ਨ** ਡ੍ਰੌਪਡਾਊਨ ਸੁਰੱਖਿਅਤ ਕੀਤੇ ਸੈਸ਼ਨਾਂ ਦੀ ਸੂਚੀ ਦਿਖਾਉਂਦਾ ਹੈ। ਕਿਸੇ ਇੱਕ ਨੂੰ ਚੁਣਨ ਨਾਲ:

- ਸੈਸ਼ਨ ਦਾ ਸਨੈਪਸ਼ਾਟ ਲੋਡ ਹੁੰਦਾ ਹੈ (ਸਥਿਰ ਸਥਿਤੀ)
- ਇੱਕ ਬੈਨਰ ਦਿਖਾਉਂਦਾ ਹੈ: `ਰਿਕਾਰਡ ਕੀਤਾ ਸੈਸ਼ਨ "<ਨਾਮ>" ਦੇਖ ਰਹੇ ਹੋ — [ਲਾਈਵ 'ਤੇ ਵਾਪਸ ਜਾਓ]`
- ਅੰਕੜੇ ਟੈਬ Recharts ਸਮੁੱਚਿਆਂ ਨਾਲ ਉਪਲਬਧ ਹੋ ਜਾਂਦੀ ਹੈ

### 5.3 ਨਿਰਯਾਤ ਫਾਰਮੈਟ

ਹਰੇਕ ਸੈਸ਼ਨ ਨੂੰ ਇਸ ਤਰ੍ਹਾਂ ਨਿਰਯਾਤ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ:

| ਫਾਰਮੈਟ                     | ਵਰਤੋਂ                                                                       |
| -------------------------- | --------------------------------------------------------------------------- |
| **HAR** (HTTP Archive 1.2) | Chrome DevTools, Charles, Fiddler ਨਾਲ ਅਨੁਕੂਲ — ਆਫਲਾਈਨ ਵਿਸ਼ਲੇਸ਼ਣ ਲਈ ਆਯਾਤ ਕਰੋ |
| **JSONL**                  | ਪ੍ਰਤੀ ਲਾਈਨ ਇੱਕ `InterceptedRequest` — `llm-interceptor` ਫਾਰਮੈਟ ਨਾਲ ਅਨੁਕੂਲ   |

`GET /api/tools/traffic-inspector/sessions/{id}/export.har` ਰਾਹੀਂ ਜਾਂ ਸੈਸ਼ਨ ਡ੍ਰੌਪਡਾਊਨ ਵਿੱਚ ⬇ ਬਟਨ ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਨਿਰਯਾਤ ਕਰੋ।

## §6 ਸੁਰੱਖਿਆ

ਟ੍ਰੈਫਿਕ ਇੰਸਪੈਕਟਰ **ਸਾਰਾ ਇੰਟਰਸੈਪਟ ਕੀਤਾ HTTPS ਟ੍ਰੈਫਿਕ** ਦਿਖਾਉਂਦਾ ਹੈ, ਜਿਸ ਵਿੱਚ ਪ੍ਰਮਾਣੀਕਰਨ ਹੈਡਰ ਅਤੇ ਬੇਨਤੀ ਬਾਡੀਆਂ ਸ਼ਾਮਲ ਹਨ। ਹੇਠਾਂ ਦਿੱਤੇ ਨਿਯੰਤਰਣ ਲਾਗੂ ਹਨ:

| ਨਿਯੰਤਰਣ                                 | ਵੇਰਵੇ                                                                                                                                                                                               |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LOCAL_ONLY**                          | ਸਾਰੇ ਰੂਟ ਅਤੇ WebSocket ਐਂਡਪੁਆਇੰਟ ਕੇਵਲ ਲੂਪਬੈਕ ਲਈ ਹਨ (ਪ੍ਰਮਾਣੀਕਰਨ ਤੋਂ ਪਹਿਲਾਂ `routeGuard.ts` ਵਿੱਚ ਲਾਗੂ ਕੀਤਾ ਜਾਂਦਾ ਹੈ)                                                                                  |
| **ਗੁਪਤ ਜਾਣਕਾਰੀ ਮਾਸਕ ਕਰਨਾ**              | ਲੀਨੀਅਰ `maskSecret()` ਸਕੈਨਰ `TrafficBuffer.push()` ਤੋਂ ਪਹਿਲਾਂ RFC 6750 Bearer ਕ੍ਰੈਡੈਂਸ਼ੀਅਲ, ਪ੍ਰਦਾਤਾ-ਪ੍ਰੀਫਿਕਸ ਵਾਲੀਆਂ ਕੁੰਜੀਆਂ ਅਤੇ ਲੰਬੇ ਅਪਾਰਦਰਸ਼ੀ ਟੋਕਨਾਂ ਨੂੰ ਲੁਕਾਉਂਦਾ ਹੈ                               |
| **ਬਾਡੀ ਆਕਾਰ ਸੀਮਾ**                      | `INSPECTOR_MAX_BODY_KB` (ਡਿਫਾਲਟ 1024 KB) ਤੋਂ ਵੱਡੀਆਂ ਬਾਡੀਆਂ ਨੂੰ `"(ਕਾਰਗੁਜ਼ਾਰੀ ਲਈ ਸੰਖੇਪ ਕੀਤਾ ਗਿਆ)"` ਸੂਚਨਾ ਨਾਲ ਸੰਖੇਪ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ                                                                 |
| **ਹੈਡਰ ਸੈਨੀਟਾਈਜ਼ੇਸ਼ਨ**                  | ਨਾਮ ਛੋਟੇ ਅੱਖਰਾਂ ਵਿੱਚ ਬਦਲੇ ਜਾਂਦੇ ਹਨ; ਫ੍ਰੇਮਿੰਗ/ਹੌਪ-ਬਾਈ-ਹੌਪ ਅਤੇ ਪ੍ਰੌਕਸੀ-ਪ੍ਰਮਾਣੀਕਰਨ ਹੈਡਰ ਹਟਾ ਦਿੱਤੇ ਜਾਂਦੇ ਹਨ; ਕੂਕੀਜ਼ ਪੂਰੀ ਤਰ੍ਹਾਂ ਲੁਕਾਈਆਂ ਜਾਂਦੀਆਂ ਹਨ; ਕ੍ਰੈਡੈਂਸ਼ੀਅਲ ਮੁੱਲ `maskSecret()` ਨੂੰ ਸੌਂਪੇ ਜਾਂਦੇ ਹਨ |
| **CSP**                                 | ਇੰਜੈਕਟ ਕੀਤੀਆਂ ਜਵਾਬ ਬਾਡੀਆਂ ਰਾਹੀਂ XSS ਨੂੰ ਰੋਕਣ ਲਈ ਟ੍ਰੈਫਿਕ ਇੰਸਪੈਕਟਰ ਪੰਨਿਆਂ 'ਤੇ ਸਖ਼ਤ ਸਮੱਗਰੀ ਸੁਰੱਖਿਆ ਨੀਤੀ                                                                                                |
| **ਡਿਫਾਲਟ ਤੌਰ 'ਤੇ ਕੋਈ ਸਥਾਈ ਸਟੋਰੇਜ ਨਹੀਂ** | `TrafficBuffer` ਮੈਮੋਰੀ ਵਿੱਚ ਰਹਿੰਦਾ ਹੈ ਅਤੇ ਸਰਵਰ ਮੁੜ ਚਾਲੂ ਹੋਣ 'ਤੇ ਗੁੰਮ ਜਾਂਦਾ ਹੈ। ਸੈਸ਼ਨ ਕੇਵਲ ਉਦੋਂ ਹੀ ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੰਭਾਲੇ ਜਾਂਦੇ ਹਨ ਜਦੋਂ ਉਹ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਰਿਕਾਰਡ ਕੀਤੇ ਜਾਣ                                |

### ਜਾਣੀਆਂ-ਪਛਾਣੀਆਂ ਸੀਮਾਵਾਂ

- **ਸਿਸਟਮ-ਵਿਆਪੀ ਪ੍ਰੌਕਸੀ ਮੋਡ** ਮਸ਼ੀਨ 'ਤੇ ਮੌਜੂਦ ਸਾਰੀਆਂ ਐਪਲੀਕੇਸ਼ਨਾਂ ਨੂੰ ਪ੍ਰਭਾਵਿਤ ਕਰਦਾ ਹੈ, ਜਿਸ ਵਿੱਚ VPN ਕਲਾਇੰਟ ਅਤੇ SSO ਸ਼ਾਮਲ ਹਨ। ਹਮੇਸ਼ਾ ਆਟੋ-ਡਿਸੇਬਲ ਟਾਈਮਰ ਨਾਲ ਵਰਤੋਂ ਕਰੋ। ਸਾਂਝੀਆਂ ਮਸ਼ੀਨਾਂ 'ਤੇ ਇਸਦੀ ਵਰਤੋਂ ਨਾ ਕਰੋ।
- **CONNECT ਟਨਲ HTTPS**: ਮੋਡ 3 (HTTP_PROXY) HTTPS ਮੰਜ਼ਿਲਾਂ ਲਈ ਕੇਵਲ ਟਨਲ ਮੈਟਾਡਾਟਾ ਕੈਪਚਰ ਕਰਦਾ ਹੈ, ਜਦੋਂ ਤੱਕ TLS ਇੰਟਰਸੈਪਸ਼ਨ ਸਮਰੱਥ ਨਾ ਹੋਵੇ। ਇਹ ਡਿਜ਼ਾਈਨ ਅਨੁਸਾਰ ਹੈ — AgentBridge ਸਰਟੀਫਿਕੇਟ 'ਤੇ ਭਰੋਸਾ ਕੀਤੇ ਬਿਨਾਂ ਪਾਰਦਰਸ਼ੀ ਕੈਪਚਰ ਉਹਨਾਂ ਐਪਾਂ ਲਈ TLS ਪੁਸ਼ਟੀਕਰਨ ਨੂੰ ਤੋੜ ਦੇਵੇਗਾ।
- **ਕੁਝ ਕੰਪੋਨੈਂਟਾਂ ਵਿੱਚ ਹਾਰਡਕੋਡ ਕੀਤੀਆਂ ਸਟ੍ਰਿੰਗਾਂ**: ਕੁਝ UI ਕੰਪੋਨੈਂਟਾਂ (F7/F8) ਵਿੱਚ ਥੋੜ੍ਹੀ ਗਿਣਤੀ ਵਿੱਚ ਹਾਰਡਕੋਡ ਕੀਤੀਆਂ ਸਟ੍ਰਿੰਗਾਂ ਹਨ, ਜੋ ਹਾਲੇ i18n ਕੁੰਜੀਆਂ ਦੁਆਰਾ ਕਵਰ ਨਹੀਂ ਕੀਤੀਆਂ ਗਈਆਂ। ਇਨ੍ਹਾਂ ਨੂੰ i18n ਅੰਤਰ ਰਿਪੋਰਟ ਵਿੱਚ ਜਾਣੀ-ਪਛਾਣੀ ਸੀਮਾ ਵਜੋਂ ਦਰਜ ਕੀਤਾ ਗਿਆ ਹੈ; ਇਨ੍ਹਾਂ ਨੂੰ ਅਗਲੇ ਪੜਾਅ ਵਿੱਚ ਮਾਈਗ੍ਰੇਟ ਕੀਤਾ ਜਾਵੇਗਾ। ਪ੍ਰਭਾਵਿਤ ਸਟ੍ਰਿੰਗਾਂ UI ਦੇ ਸਜਾਵਟੀ ਲੇਬਲ ਹਨ, ਜਿਨ੍ਹਾਂ ਨੂੰ ਕਾਰਜਾਤਮਕ ਵਰਤੋਂ ਲਈ ਅਨੁਵਾਦ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ।

## §7 ਸਮੱਸਿਆ-ਨਿਵਾਰਣ

### WebSocket ਡਿਸਕਨੈਕਸ਼ਨ

ਜੇ ਲਾਈਵ ਟੇਲ "ਡਿਸਕਨੈਕਟ ਕੀਤਾ ਗਿਆ" ਦਿਖਾਉਂਦੀ ਹੈ:

1. ਜਾਂਚ ਕਰੋ ਕਿ ਸਰਵਰ ਹਾਲੇ ਵੀ ਚੱਲ ਰਿਹਾ ਹੈ: `GET /api/tools/traffic-inspector/capture-modes`
2. ਪੰਨੇ ਨੂੰ ਮੁੜ ਲੋਡ ਕਰੋ — WebSocket ਦੁਬਾਰਾ ਕਨੈਕਟ ਹੁੰਦਾ ਹੈ ਅਤੇ ਇੱਕ ਨਵਾਂ ਸਨੈਪਸ਼ਾਟ ਪ੍ਰਾਪਤ ਕਰਦਾ ਹੈ
3. ਜੇ ਸਰਵਰ ਮੁੜ ਚਾਲੂ ਕੀਤਾ ਗਿਆ ਸੀ, ਤਾਂ ਇਨ-ਮੈਮੋਰੀ ਬਫ਼ਰ ਸਾਫ਼ ਹੋ ਗਿਆ ਸੀ — ਪੁਰਾਣੀਆਂ ਐਂਟਰੀਆਂ ਖਤਮ ਹੋ ਗਈਆਂ ਹਨ, ਜਦੋਂ ਤੱਕ ਕੋਈ ਸੈਸ਼ਨ ਰਿਕਾਰਡ ਨਹੀਂ ਕੀਤਾ ਗਿਆ ਸੀ

### ਪੋਰਟ 8080 ਟਕਰਾਅ

ਜੇ HTTP_PROXY ਮੋਡ ਸ਼ੁਰੂ ਹੋਣ ਵਿੱਚ ਅਸਫਲ ਰਹਿੰਦਾ ਹੈ:

```bash
lsof -i :8080    # ਪ੍ਰਕਿਰਿਆ ਲੱਭੋ
```

ਪੋਰਟ ਬਦਲੋ:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### ਸਿਸਟਮ ਪ੍ਰੌਕਸੀ ਵਾਪਸ ਨਹੀਂ ਕੀਤੀ ਗਈ

ਜੇ ਸਿਸਟਮ-ਵਿਆਪੀ ਪ੍ਰੌਕਸੀ ਮੋਡ ਸਰਗਰਮ ਹੋਣ ਦੌਰਾਨ OmniRoute ਕਰੈਸ਼ ਹੋ ਜਾਂਦਾ ਹੈ:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

ਅਗਲੀ ਵਾਰ ਲੋਡ ਹੋਣ 'ਤੇ ਡੈਸ਼ਬੋਰਡ "ਸਿਸਟਮ ਪ੍ਰੌਕਸੀ ਵਾਪਸ ਕਰੋ" ਵਿਕਲਪ ਵੀ ਪੇਸ਼ ਕਰੇਗਾ, ਜੇ ਇਹ ਪਤਾ ਲਗਾਉਂਦਾ ਹੈ ਕਿ DB ਸਥਿਤੀ ਅਨੁਸਾਰ ਪ੍ਰੌਕਸੀ ਸਰਗਰਮ ਸੀ।

### ਬਫ਼ਰ ਭਰਿਆ ਹੋਇਆ ਹੈ

ਜਦੋਂ ਬਫ਼ਰ `INSPECTOR_BUFFER_SIZE` (ਮੂਲ ਰੂਪ ਵਿੱਚ 1000) ਤੱਕ ਪਹੁੰਚਦਾ ਹੈ, ਤਾਂ ਨਵੀਆਂ ਐਂਟਰੀਆਂ ਸਭ ਤੋਂ ਪੁਰਾਣੀਆਂ ਐਂਟਰੀਆਂ ਨੂੰ ਹਟਾ ਦਿੰਦੀਆਂ ਹਨ। ਜੇ ਮਹੱਤਵਪੂਰਨ ਬੇਨਤੀਆਂ ਗੁੰਮ ਹੋ ਰਹੀਆਂ ਹਨ:

- `INSPECTOR_BUFFER_SIZE` ਵਧਾਓ (ਉਦਾਹਰਨ ਲਈ, 5000) — ਇਹ ਵਧੇਰੇ ਸਮੇਂ ਤੱਕ ਡਾਟਾ ਰੱਖਣ ਲਈ ਵਧੇਰੇ ਮੈਮੋਰੀ ਵਰਤਦਾ ਹੈ
- ਸੰਬੰਧਿਤ ਸਮਾਂ-ਅੰਤਰਾਲ ਨੂੰ DB ਵਿੱਚ ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੰਭਾਲਣ ਲਈ ਇੱਕ ਸੈਸ਼ਨ ਰਿਕਾਰਡ ਕਰੋ

| ਵਿਧੀ | ਪਾਥ                            | ਵਰਣਨ                                                                                       |
| ---- | ------------------------------ | ------------------------------------------------------------------------------------------ |
| GET  | `/capture-modes`               | AgentBridge / ਕਸਟਮ-ਹੋਸਟ / HTTP_PROXY / ਸਿਸਟਮ-ਪ੍ਰੌਕਸੀ ਮੋਡਾਂ ਦੀ ਸਥਿਤੀ + `tls-intercept` ਟੌਗਲ |
| POST | `/capture-modes/http-proxy`    | HTTP_PROXY ਲਿਸਨਰ ਸ਼ੁਰੂ/ਬੰਦ ਕਰੋ (`{action: "start"\|"stop"}`)                               |
| POST | `/capture-modes/system-proxy`  | ਸਿਸਟਮ-ਵਿਆਪੀ ਪ੍ਰੌਕਸੀ ਲਾਗੂ ਕਰੋ/ਵਾਪਸ ਕਰੋ (`{action: "apply"\|"revert"}`)                      |
| POST | `/capture-modes/tls-intercept` | ਪ੍ਰੌਕਸੀ ਮੋਡ ਵਿੱਚ HTTPS ਬਾਡੀ ਡਿਕ੍ਰਿਪਸ਼ਨ ਟੌਗਲ ਕਰੋ (`{enabled: boolean}`)                     |

> **TPROXY ਡਿਕ੍ਰਿਪਟ** (ਕੈਪਚਰ ਮੋਡ 5) ਨੂੰ AgentBridge ਪ੍ਰੀਫਿਕਸ ਹੇਠਲੇ ਇੱਕ **ਵੱਖਰੇ** ਰੂਟ ਦੁਆਰਾ ਚਲਾਇਆ ਜਾਂਦਾ ਹੈ —
> `GET / POST / DELETE /api/tools/agent-bridge/tproxy` — ਇਹ
> `/api/tools/traffic-inspector/` ਹੇਠ ਨਹੀਂ ਹੈ।
> `docs/security/MITM-TPROXY-DECRYPT.md` ਵੇਖੋ (git; `/docs` ਵਿੱਚ ਕੰਪਾਇਲ ਨਹੀਂ ਕੀਤਾ ਗਿਆ)।
