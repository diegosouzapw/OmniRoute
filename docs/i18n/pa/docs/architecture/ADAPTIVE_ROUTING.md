ਇਹ ਦਸਤਾਵੇਜ਼ OmniRoute ਵਿੱਚ ਜੋੜੇ ਗਏ ਫੀਡਬੈਕ-ਚਲਿਤ ਅਡੈਪਟਿਵ ਰਾਊਟਿੰਗ ਦੇ ਆਧਾਰ ਦਾ ਵਰਣਨ ਕਰਦਾ ਹੈ। ਇਹ ਜਾਣ-ਬੁੱਝ ਕੇ ਛੋਟਾ ਰੱਖਿਆ ਗਿਆ ਹੈ: ਇਹ ਇੱਕ ਟਾਈਪਡ ਰਾਊਟਿੰਗ-ਨਤੀਜਾ ਚੈਨਲ, ਮੌਜੂਦਾ auto-combo ਸਕੋਰਰ ਨੂੰ ਇਨਪੁੱਟ ਦੇਣ ਵਾਲਾ ਇੱਕ ਆਨਲਾਈਨ ਗੁਣਵੱਤਾ ਸੰਕੇਤ, ਇੱਕ ਵਿਕਲਪਿਕ OpenTelemetry ਐਕਸਪੋਰਟਰ, ਅਤੇ ਇੱਕ ਵਿਆਖਿਆਯੋਗਤਾ ਐਂਡਪੌਇੰਟ ਪੇਸ਼ ਕਰਦਾ ਹੈ। ਇਹ ਮੌਜੂਦਾ ਰੇਜ਼ੀਲੀਅੰਸ ਸਟੈਕ (ਸਰਕਿਟ ਬ੍ਰੇਕਰ, ਕਨੈਕਸ਼ਨ ਕੂਲਡਾਊਨ, ਮਾਡਲ ਲੌਕਆਉਟ, ਹੈਲਥ ਮੈਟ੍ਰਿਕਸ, ਆਟੋਪਾਇਲਟ) ਨੂੰ **ਬਦਲਦਾ ਨਹੀਂ** — ਇਹ ਉਸਦਾ ਪੂਰਕ ਹੈ।

## 1. ਆਰਕੀਟੈਕਚਰਲ ਸੰਦਰਭ

OmniRoute ਇੱਕ ਡਾਟਾ ਪਲੇਨ ਹੈ ਜਿਸ ਵਿੱਚ ਇੱਕ **ਰਿਕਵੈਸਟ ਹੌਟ ਪਾਥ** ਅਤੇ ਇੱਕ **ਕੰਟਰੋਲ/ਇੰਟੈਲੀਜੈਂਸ ਪਲੇਨ** ਹੈ। ਹੌਟ ਪਾਥ ਨੂੰ ਤੇਜ਼, ਮੈਮੋਰੀ-ਕੁਸ਼ਲ, ਅਸਿੰਕ੍ਰੋਨਸ, ਰੇਜ਼ੀਲੀਅੰਟ ਅਤੇ ਅਨੁਮਾਨਯੋਗ ਰਹਿਣਾ ਚਾਹੀਦਾ ਹੈ। ਮੁਲਾਂਕਣ, ਗੁਣਵੱਤਾ ਸਕੋਰਿੰਗ, ਪ੍ਰਯੋਗ ਅਤੇ ਇਤਿਹਾਸਕ ਵਿਸ਼ਲੇਸ਼ਣ ਕੰਟਰੋਲ ਪਲੇਨ ਨਾਲ ਸੰਬੰਧਿਤ ਹਨ।

```
AI ਏਜੰਟ / IDE
      │
      ▼
┌─────────────────────┐
│    OmniRoute        │   ਡਾਟਾ ਪਲੇਨ (ਤੇਜ਼, ਸਿੰਕ, ਇਨ-ਮੈਮੋਰੀ)
│  ਰਾਊਟਿੰਗ / ਫੇਲਓਵਰ  │
│  ਹੈਲਥ / ਗਾਰਡਰੇਲ    │
│  ਕੈਸ਼ / ਸਟ੍ਰੀਮਿੰਗ   │
└──────────┬──────────┘
           │ RoutingEvent (ਫਾਇਰ-ਐਂਡ-ਫਰਗੈੱਟ, ~0.2µs)
           ▼
┌─────────────────────┐
│  ਫੀਡਬੈਕ ਸਿੰਕ        │   ਕੰਟਰੋਲ ਪਲੇਨ (ਅਸਿੰਕ, ਬੈਸਟ-ਐਫਰਟ)
│  ਗੁਣਵੱਤਾ ਟ੍ਰੈਕਰ     │
│  OTel ਐਕਸਪੋਰਟਰ     │
│  ਵਿਆਖਿਆ ਸਟੋਰ       │
└──────────┬──────────┘
           ▼  ਗੁਣਵੱਤਾ ਸਕੋਰ
      auto-combo ਸਕੋਰਰ
```

### ਜੋ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਸੀ (ਆਡਿਟ ਕੀਤਾ ਗਿਆ, ਦੁਹਰਾਇਆ ਨਹੀਂ ਗਿਆ)

| ਧਾਰਨਾ                                   | ਮੌਜੂਦਾ ਇੰਪਲੀਮੈਂਟੇਸ਼ਨ                                                                              |
| --------------------------------------- | ------------------------------------------------------------------------------------------------- |
| ਉਪਲਬਧਤਾ (ਕੀ ਅਸੀਂ ਟ੍ਰੈਫਿਕ ਭੇਜ ਸਕਦੇ ਹਾਂ?) | ਸਰਕਿਟ ਬ੍ਰੇਕਰ (CLOSED/DEGRADED/OPEN/HALF_OPEN, DB ਵਿੱਚ ਸੰਭਾਲਿਆ ਹੋਇਆ), ਕਨੈਕਸ਼ਨ ਕੂਲਡਾਊਨ, ਮਾਡਲ ਲੌਕਆਉਟ |
| ਹੈਲਥ ਰਿਪੋਰਟਿੰਗ                          | `providerHealthMatrix.ts`, `providerHealthAutopilot.ts`                                           |
| ਸ਼ੈਡੋ ਟ੍ਰੈਫਿਕ                           | `open-sse/services/combo/shadowRouting.ts`                                                        |
| ਗਾਰਡਰੇਲ                                 | `src/lib/guardrails/` (ਪ੍ਰੀ/ਪੋਸਟ ਹੁੱਕ)                                                            |
| ਸਟੀਕ ਕੈਸ਼                               | `src/lib/semanticCache.ts` (ਸਿਗਨੇਚਰ-ਆਧਾਰਿਤ)                                                       |
| ਮੁਲਾਂਕਣਕਰਤਾ / ਮੁਲਾਂਕਣ-ਚਲਿਤ ਰਾਊਟਿੰਗ      | `src/lib/evals/`, `open-sse/services/evalRouting.ts`                                              |
| Combo ਫੈਸਲੇ ਦੀ ਵਿਆਖਿਆਯੋਗਤਾ              | `open-sse/services/combo/decisionTrace.ts`                                                        |
| ਡੈਸ਼ਬੋਰਡ ਰੀਅਲ-ਟਾਈਮ ਇਵੈਂਟ                | `src/lib/events/eventBus.ts` (UI ਨੋਟੀਫਿਕੇਸ਼ਨ ਚੈਨਲ, `unknown` ਪੇਲੋਡ, 100-ਐਂਟਰੀ ਇਤਿਹਾਸ)             |

ਰਾਊਟਿੰਗ-ਇਵੈਂਟ ਲੇਅਰ `eventBus` ਦੀ ਮੁੜ-ਇੰਪਲੀਮੈਂਟੇਸ਼ਨ **ਨਹੀਂ** ਹੈ: ਉਹ ਬੱਸ ਡੈਸ਼ਬੋਰਡ ਦਾ ਰੀਅਲ-ਟਾਈਮ ਨੋਟੀਫਿਕੇਸ਼ਨ ਚੈਨਲ ਹੈ (ਟਾਈਪਡ _ਇਵੈਂਟ ਨਾਮ_, ਅਸਪਸ਼ਟ ਪੇਲੋਡ, UI ਉਪਭੋਗਤਾ)। `RoutingEvent` ਇੱਕ ਟਾਈਪਡ _ਨਤੀਜਾ_ ਸਟਰੱਕਟ ਹੈ (ਲੇਟੈਂਸੀ/ਟੋਕਨ/ਲਾਗਤ/ਨਤੀਜਾ/ਸਮਾਪਤੀ-ਕਾਰਨ), ਜਿਸਨੂੰ ਕੰਟਰੋਲ ਪਲੇਨ ਦੇ ਫੀਡਬੈਕ ਸਿੰਕ (ਗੁਣਵੱਤਾ ਟ੍ਰੈਕਰ, OTel ਐਕਸਪੋਰਟਰ, ਵਿਆਖਿਆ ਸਟੋਰ) ਵਰਤਦੇ ਹਨ।

### ਜੋ ਮੌਜੂਦ ਨਹੀਂ ਸੀ (ਇੱਥੇ ਜੋੜਿਆ ਗਿਆ)

1. ਇੱਕ **ਟਾਈਪਡ ਰਾਊਟਿੰਗ-ਨਤੀਜਾ ਇਵੈਂਟ + ਸਿੰਕ ਐਬਸਟਰੈਕਸ਼ਨ** (`RoutingEvent` /
   `RoutingEventSink`)। `decisionTrace` Combo-ਸਕੋਪਡ ਅਤੇ ਸਿਰਫ਼ ਇਨ-ਮੈਮੋਰੀ ਹੈ;
   `comboMetrics` ਸੰਚਿਤ ਕਾਊਂਟਰ ਹਨ; `call_logs` ਕੱਚੀ ਅਸਿੰਕ ਪਰਸਿਸਟੈਂਸ ਹੈ।
   ਇਨ੍ਹਾਂ ਵਿੱਚੋਂ ਕੋਈ ਵੀ ਟਾਈਪਡ, ਸਿੰਕ-ਆਧਾਰਿਤ ਨਤੀਜਾ ਚੈਨਲ ਨਹੀਂ ਹੈ ਜਿਸਨੂੰ ਗੁਣਵੱਤਾ ਟ੍ਰੈਕਰ, OTel
   ਐਕਸਪੋਰਟਰ, ਜਾਂ Future-AGI-ਸ਼ੈਲੀ ਦਾ ਮੁਲਾਂਕਣਕਰਤਾ ਸਬਸਕ੍ਰਾਈਬ ਕਰ ਸਕੇ।
2. ਆਉਟਪੁੱਟ ਗੁਣਵੱਤਾ ਲਈ ਇੱਕ **ਆਨਲਾਈਨ ਗੁਣਵੱਤਾ ਸੰਕੇਤ** (EWMA) — ਪਹਿਲਾਂ ਸਕੋਰਰ
   "ਗੁਣਵੱਤਾ" ਨੂੰ ਕੇਵਲ ਸਥਿਰ ਟਾਸਕ ਫਿਟਨੈੱਸ ਅਤੇ ਆਪਟ-ਇਨ ਮੁਲਾਂਕਣ ਪਾਸ-ਰੇਟਾਂ ਰਾਹੀਂ ਪ੍ਰਾਕਸੀ ਕਰਦਾ ਸੀ।
3. GenAI ਸਿਮੈਂਟਿਕ ਕਨਵੈਨਸ਼ਨਾਂ ਦੀ ਵਰਤੋਂ ਕਰਨ ਵਾਲਾ ਇੱਕ **ਵਿਕਲਪਿਕ, ਡਿਪੈਂਡੈਂਸੀ-ਰਹਿਤ OTel ਐਕਸਪੋਰਟਰ**।
4. ਅਸਲ ਰਾਊਟਿੰਗ ਫੈਸਲੇ + ਗੁਣਵੱਤਾ ਸਥਿਤੀ ਵਾਪਸ ਕਰਨ ਵਾਲਾ ਇੱਕ **ਵਿਆਖਿਆਯੋਗਤਾ ਐਂਡਪੌਇੰਟ**।

## 2. ਰਾਊਟਿੰਗ ਇਵੈਂਟਸ (ਫੀਡਬੈਕ ਦੀ ਬੁਨਿਆਦ)

ਫ਼ਾਈਲਾਂ: `open-sse/services/routing/events.ts`, `.../index.ts`

ਇੱਕ `RoutingEvent` ਸਿਰਫ਼ ਰਾਊਟਿੰਗ ਮੈਟਾਡਾਟਾ ਰੱਖਦਾ ਹੈ:

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ...
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // ਮਨਜ਼ੂਰਸ਼ੁਦਾ ਸੂਚੀ ਵਾਲਾ ਯੂਨੀਅਨ
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

`RoutingEventSink`, TypeScript ਵਿੱਚ ਇੱਕ `Send+Sync`-ਸ਼ੈਲੀ ਦਾ ਟ੍ਰੇਟ ਹੈ:

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // O(1) ਹੋਣਾ ਲਾਜ਼ਮੀ ਹੈ, ਕੋਈ ਸਿੰਕ੍ਰੋਨਸ I/O ਨਹੀਂ
}
```

ਹੌਟ ਪਾਥ ਹਰ ਪੂਰੀ ਹੋਈ ਬੇਨਤੀ ਲਈ ਇੱਕ ਵਾਰ `emitRoutingEvent(event)` ਨੂੰ ਕਾਲ ਕਰਦਾ ਹੈ
(`handleChatCore` ਵਿੱਚ ਸਟ੍ਰੀਮਿੰਗ-ਕੰਪਲੀਸ਼ਨ ਕਾਲਬੈਕ, ਨਾਨ-ਸਟ੍ਰੀਮਿੰਗ ਸਫਲਤਾ ਪਾਥ ਅਤੇ
ਗਲਤ-ਸਰੂਪ ਵਾਲੇ 200 ਦਾ ਅਸਫਲਤਾ ਪਾਥ)। ਡਿਸਪੈਚ ਰਜਿਸਟਰਡ ਸਿੰਕਾਂ ਲਈ ਸਿੰਕ੍ਰੋਨਸ ਫੈਨ-ਆਉਟ
ਹੈ, ਪਰ ਹਰ ਸਿੰਕ ਸਿਰਫ਼ ਕਤਾਰ ਵਿੱਚ ਪਾਉਂਦਾ ਹੈ/ਇਨ-ਮੈਮੋਰੀ ਸਥਿਤੀ ਨੂੰ ਅੱਪਡੇਟ ਕਰਦਾ ਹੈ। **ਹੌਟ
ਪਾਥ ਉੱਤੇ ਕੋਈ ਸਿੰਕ੍ਰੋਨਸ ਡਾਟਾਬੇਸ ਰਾਈਟ ਨਹੀਂ, ਕੋਈ ਨੈੱਟਵਰਕ I/O ਨਹੀਂ।**

ਡਿਫਾਲਟ ਸਿੰਕ:

- `MemoryRoutingEventStore` — ਐਕਸਪਲੇਨ ਐਂਡਪੌਇੰਟ ਲਈ ਸੀਮਿਤ (500) ਰਿੰਗ ਬਫ਼ਰ,
  ਸਭ ਤੋਂ ਨਵਾਂ ਪਹਿਲਾਂ।
- `QualityTracker` ਉਪਭੋਗਤਾ — EWMA ਗੁਣਵੱਤਾ ਅਨੁਮਾਨ ਨੂੰ ਅੱਪਡੇਟ ਕਰਦਾ ਹੈ।
- `OtlpHttpsEventSink` — ਵਿਕਲਪਿਕ, ਸਿਰਫ਼ ਉਦੋਂ ਸਮਰੱਥ ਹੁੰਦਾ ਹੈ ਜਦੋਂ
  `OMNIROUTE_OTEL_ENDPOINT` (ਜਾਂ `OTEL_EXPORTER_OTLP_ENDPOINT`) ਸੈੱਟ ਹੋਵੇ।

### ਮਾਪਿਆ ਗਿਆ ਓਵਰਹੈੱਡ (ਇਮਾਨਦਾਰ ਤੁਲਨਾ)

ਇਸ ਵਰਕਸਟੇਸ਼ਨ ਉੱਤੇ `npm run bench:routing-events` (100k ਦੁਹਰਾਅ; ਸਬ-µs
ਓਪਰੇਸ਼ਨਾਂ ਨੂੰ ਸਮੁੱਚੇ µs/op ਵਜੋਂ ਮਾਪਿਆ ਗਿਆ ਕਿਉਂਕਿ ਪ੍ਰਤੀ-ਓਪਰੇਸ਼ਨ ਪ੍ਰਤੀਸ਼ਤਕ
`performance.now()` ਟਾਈਮਰ ਰੈਜ਼ੋਲਿਊਸ਼ਨ ਤੋਂ ਹੇਠਾਂ ਹਨ):

| ਦ੍ਰਿਸ਼                          | µs/op  | ops/s  |
| ------------------------------- | ------ | ------ |
| ਬੇਸਲਾਈਨ (ਸਿਰਫ਼ ਸਕੋਰਿੰਗ)         | ~0.045 | ~22 M  |
| ਬੇਸਲਾਈਨ + RoutingEvent (2 ਸਿੰਕ) | ~0.168 | ~5.9 M |
| ਬੇਸਲਾਈਨ + ਇਵੈਂਟ + OTel ਕਤਾਰਬੰਦੀ | ~0.163 | ~6.1 M |
| ਸਮਕਾਲੀ (8 ਇੰਟਰਲੀਵਡ ਬਰਸਟ)        | ~0.18  | —      |

ਬੇਸਲਾਈਨ ਸਕੋਰਿੰਗ ਤੋਂ ਵੱਧ ਇਵੈਂਟ-ਡਿਸਪੈਚ ਡੈਲਟਾ ~0.12 µs/ਬੇਨਤੀ ਹੈ; OTel ਸਿੰਕ

ਇਹ ਅੰਕ ਮਸ਼ੀਨ-ਵਿਸ਼ੇਸ਼ ਅਤੇ ਸਾਪੇਖ ਹਨ — ਉਤਪਾਦਨ ਦੀ ਗਾਰੰਟੀ ਨਹੀਂ। v1 ਦਾ "~0.2 µs"
ਅੰਕ ਇੱਕ ਸਮੁੱਚਾ ਅਨੁਮਾਨ ਸੀ; ਇਹ ਕਾਰਜ-ਵਿਧੀ ਸਕੋਰਿੰਗ ਬੇਸਲਾਈਨ ਨੂੰ ਇਵੈਂਟ-ਡਿਸਪੈਚ
ਲਾਗਤ ਤੋਂ ਵੱਖ ਕਰਦੀ ਹੈ।

## 3. ਗੁਣਵੱਤਾ ਸੰਕੇਤ (ਫੀਡਬੈਕ-ਚਲਿਤ ਪ੍ਰਦਾਤਾ ਸਥਿਤੀ)

ਫ਼ਾਈਲਾਂ: `open-sse/services/routing/quality.ts`

v2 **ਸੰਚਾਲਨਾਤਮਕ** ਗੁਣਵੱਤਾ ਨੂੰ **ਅਰਥਗਤ** ਗੁਣਵੱਤਾ ਤੋਂ ਵੱਖ ਕਰਦਾ ਹੈ:

- **ਸੰਚਾਲਨਾਤਮਕ** — ਰਾਊਟਿੰਗ ਹੌਟ ਪਾਥ ਤੋਂ ਪ੍ਰਾਪਤ (HTTP 4xx/5xx, ਕਨੈਕਸ਼ਨ
  ਅਸਫਲਤਾਵਾਂ, 429s, ਗਲਤ-ਸਰੂਪ ਵਾਲੇ ਜਵਾਬ, ਸਟ੍ਰੀਮ ਰੁਕਾਵਟਾਂ, `finish_reason=length`,
  ਸਿਫ਼ਰ-ਆਉਟਪੁੱਟ ਸਫਲਤਾਵਾਂ, ਲੇਟੈਂਸੀ/TTFT EWMA)। 200 ਨੂੰ ਅਰਥਗਤ ਗੁਣਵੱਤਾ ਨਹੀਂ
  ਮੰਨਿਆ ਜਾਂਦਾ।
- **ਅਰਥਗਤ** — ਤਿਆਰ ਕੀਤੀ ਆਉਟਪੁੱਟ ਦਾ ਅਸਲ ਮੁੱਲ। ਇਹ ਸਿਰਫ਼ ਇੱਕ ਮੁਲਾਂਕਣਕਾਰ
  ਵੱਲੋਂ `setSemanticQuality()` ਰਾਹੀਂ ਹੀ ਬਣਾਇਆ ਜਾਂਦਾ ਹੈ। ਜਦੋਂ ਤੱਕ ਕੋਈ ਇਸਨੂੰ
  ਮੁਹੱਈਆ ਨਹੀਂ ਕਰਦਾ, ਇਹ `null` ਰਹਿੰਦਾ ਹੈ ਅਤੇ ਕਦੇ ਵੀ ਸੰਚਾਲਨਾਤਮਕ ਸਕੋਰ ਵਿੱਚ
  ਲੀਕ ਨਹੀਂ ਹੁੰਦਾ।

ਹਰੇਕ (ਪ੍ਰਦਾਤਾ, ਮਾਡਲ) ਲਈ ਸਥਿਤੀ (EWMA + ਸੀਮਿਤ ਕਾਊਂਟਰ):

- `successEwma` — ਨਤੀਜੇ ਦੀ ਸਫਲਤਾ ਦਾ EWMA (α=0.2)।
- `latencyEwma` / `ttftEwma` — ਲੇਟੈਂਸੀ ਦਾ EWMA (α=0.1)।
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`।
- `recencyMs` — ਮਾਡਲ ਨੂੰ ਆਖਰੀ ਵਾਰ ਕਿੰਨਾ ਹਾਲ ਹੀ ਵਿੱਚ ਦੇਖਿਆ ਗਿਆ ਸੀ।

### ਭਰੋਸਾ / ਨਮੂਨਾ ਜਾਗਰੂਕਤਾ

`confidence = clamp01(samples / 50)`, ਅਤੇ ਸਕੋਰਰ ਨੂੰ ਵਾਪਸ ਕੀਤਾ ਸਕੋਰ ਨਿਰਪੱਖ
ਮੱਧ-ਬਿੰਦੂ ਵੱਲ ਮਿਲਾਇਆ ਜਾਂਦਾ ਹੈ:

```
score = 0.5 + confidence * (operational - 0.5)
```

ਨਤੀਜੇ (ਟੈਸਟਾਂ ਦੁਆਰਾ ਪ੍ਰਮਾਣਿਤ):

- ਇੱਕ ਕੋਲਡ ਪ੍ਰਦਾਤਾ (0 ਨਮੂਨੇ) ਦਾ ਸਕੋਰ **0.5** ਹੁੰਦਾ ਹੈ — ਉਸਨੂੰ ਅਨੁਚਿਤ ਢੰਗ
  ਨਾਲ ਦੰਡਿਤ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ, ਪਰ ਉਹ ਹਜ਼ਾਰਾਂ ਠੋਸ ਨਿਰੀਖਣਾਂ ਵਾਲੇ ਪ੍ਰਦਾਤਾ ਉੱਤੇ
  ਹਾਵੀ ਨਹੀਂ ਹੋ ਸਕਦਾ।
- 7 ਖੁਸ਼ਕਿਸਮਤ ਸਫਲਤਾਵਾਂ ਵਾਲੇ ਪ੍ਰਦਾਤਾ ਨੂੰ 0.5 ਵੱਲ ਖਿੱਚਿਆ ਜਾਂਦਾ ਹੈ (ਉਹ
  ਆਸ਼ਾਵਾਦੀ ਸ਼ੁਰੂਆਤੀਕਰਨ ਕਰਕੇ ਕਦੇ ਵੀ ਹਾਵੀ ਨਹੀਂ ਹੁੰਦਾ)।
- 50+ ਨਮੂਨਿਆਂ ਵਾਲਾ ਪ੍ਰਦਾਤਾ ਆਪਣੇ ਅਸਲ ਸੰਚਾਲਨਾਤਮਕ ਸਕੋਰ ਵੱਲ ਕਨਵਰਜ ਕਰਦਾ ਹੈ।
- ਗਿਰਾਵਟ ਅਤੇ ਰਿਕਵਰੀ ਹੌਲੀ-ਹੌਲੀ ਹੁੰਦੇ ਹਨ (EWMA), ਅਤੇ ਇੱਕ ਇਕੱਲੀ ਅਸਫਲਤਾ
  ਇੱਕ ਸਿਹਤਮੰਦ ਪ੍ਰਦਾਤਾ ਨੂੰ ਬਰਬਾਦ ਨਹੀਂ ਕਰਦੀ।

`ProviderQuality`, `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }` ਨੂੰ ਐਕਸਪੋਜ਼ ਕਰਦਾ ਹੈ।

ਇਹ ਆਟੋ-ਕੌਂਬੋ ਸਕੋਰਰ ਨੂੰ `quality` ਸਕੋਰਿੰਗ ਫੈਕਟਰ ਵਜੋਂ ਫੀਡ ਕਰਦਾ ਹੈ:

- `open-sse/services/autoCombo/scoring.ts` ਵਿੱਚ `ScoringFactors.quality` /
  `ScoringWeights.quality`।
- `DEFAULT_WEIGHTS`: `health` 0.1905 → 0.1605, `quality` 0.03। ਜੋੜ 1.0 ਰਹਿੰਦਾ ਹੈ।
- `buildAutoCandidates`, ਟ੍ਰੈਕਰ ਤੋਂ `candidate.quality` ਨੂੰ ਭਰਦਾ ਹੈ; ਬਿਨਾਂ ਡਾਟੇ
  ਵਾਲੇ ਉਮੀਦਵਾਰਾਂ ਲਈ ਡਿਫਾਲਟ ਨਿਰਪੱਖ **0.5** ਹੈ (ਇੱਕ ਕੋਲਡ ਉਮੀਦਵਾਰ ਨੂੰ ਨਾ
  ਬੂਸਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਨਾ ਹੀ ਦੰਡਿਤ)।

ਬੰਦ ਲੂਪ:

```
RoutingEvent → QualityTracker → getQualityScore → ਆਟੋ-ਕੌਂਬੋ ਗੁਣਵੱਤਾ ਫੈਕਟਰ
      ↑                                                    │
      └────── ਬੇਨਤੀ ਦਾ ਨਤੀਜਾ (handleChatCore) ←────────────┘
```

### ਸਖ਼ਤ ਬਹਿਸ਼ਕਰਨ ਬਨਾਮ ਨਰਮ ਦੰਡ

ਗੁਣਵੱਤਾ ਸੰਕੇਤ ਸਿਰਫ਼ ਇੱਕ **ਨਰਮ ਅਨੁਕੂਲੀ ਤਰਜੀਹ** ਹੈ। ਸਖ਼ਤ ਬਹਿਸ਼ਕਰਨ ਮੌਜੂਦਾ
ਲਚਕੀਲੇਪਣ ਸਟੈਕ ਕੋਲ ਹੀ ਰਹਿੰਦਾ ਹੈ: ਸਰਕਿਟ ਬ੍ਰੇਕਰ OPEN, ਕੋਟਾ ਖ਼ਤਮ, ਪ੍ਰਮਾਣਿਕਤਾ
ਅਸਫਲਤਾ, ਮਾਡਲ ਲੌਕਆਉਟ — ਇਨ੍ਹਾਂ ਵਿੱਚੋਂ ਕੋਈ ਵੀ ਗੁਣਵੱਤਾ ਸਕੋਰ ਨਾਲ ਪ੍ਰਭਾਵਿਤ ਨਹੀਂ
ਹੁੰਦਾ। ਜਿਸ ਪ੍ਰਦਾਤਾ ਦਾ ਗੁਣਵੱਤਾ ਸਕੋਰ ਅਸਥਾਈ ਤੌਰ ਉੱਤੇ ਘਟਦਾ ਹੈ, ਉਸਦੀ ਤਰਜੀਹ
ਘਟਾਈ ਜਾਂਦੀ ਹੈ, ਉਸਨੂੰ ਕਦੇ ਵੀ ਸਖ਼ਤੀ ਨਾਲ ਅਸਮਰੱਥ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ।

## 3b. ਕੈਨੋਨਿਕਲ ਸਟ੍ਰੀਮ ਟਾਈਮਿੰਗ (TTFT / ITL)

ਫ਼ਾਈਲਾਂ: `open-sse/utils/streamTiming.ts`

`createStreamTiming()` ਸਟ੍ਰੀਮਿੰਗ ਪਾਥ ਲਈ ਇਕਮਾਤਰ ਇੰਸਟਰੂਮੈਂਟੇਸ਼ਨ ਸੀਮ ਹੈ,
ਜਿਸਨੂੰ `createSSEStream` (`open-sse/utils/stream.ts`) ਵਿੱਚ ਜੋੜਿਆ ਗਿਆ ਹੈ:

- `markByte()` — ਪਹਿਲਾ ਅੱਪਸਟ੍ਰੀਮ ਚੰਕ ਪ੍ਰਾਪਤ ਹੋਇਆ।
- `markForward()` — ਕਲਾਇੰਟ ਨੂੰ ਫਾਰਵਰਡ ਕੀਤਾ ਗਿਆ ਪਹਿਲਾ ਚੰਕ (TTFT ਲਈ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ)।
- `markInterrupted()` — ਸਾਫ਼-ਸੁਥਰੇ ਢੰਗ ਨਾਲ ਸਮਾਪਤ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਸਟ੍ਰੀਮ ਟਾਈਮਆਉਟ/ਅਬੋਰਟ/ਗਲਤੀ।
- `ttft()` = ਪਹਿਲੇ-ਫਾਰਵਰਡ-ਕੀਤੇ-SSE-ਚੰਕ ਦੀ ਲੇਟੈਂਸੀ। **ਇਹ ਟੋਕਨ-ਪੱਧਰ ਦਾ TTFT ਨਹੀਂ ਹੈ** —
  ਇੱਕ SSE ਚੰਕ ਵਿੱਚ ਸਿਫ਼ਰ/ਇੱਕ/ਕਈ ਟੋਕਨ ਹੋ ਸਕਦੇ ਹਨ। ਇਸਦਾ ਸਟੀਕ ਦਸਤਾਵੇਜ਼ੀਕਰਨ ਕੀਤਾ ਗਿਆ ਹੈ।
- `avgItlMs()` = ਚੰਕਾਂ ਵਿਚਕਾਰ ਔਸਤ ਅੰਤਰਾਲ (ITL ਲਈ ਚੰਕ-ਲੇਟੈਂਸੀ ਪ੍ਰਾਕਸੀ)।

TTFT/ITL/interrupted `RoutingEvent` (`ttftMs`, `itlMs`) ਵਿੱਚ ਜਾਂਦੇ ਹਨ ਅਤੇ
OTel ਸਿੰਕ ਦੁਆਰਾ GenAI/OmniRoute ਸਪੈਨ ਐਟ੍ਰਿਬਿਊਟਾਂ ਵਜੋਂ ਐਕਸਪੋਰਟ ਕੀਤੇ ਜਾਂਦੇ ਹਨ।

## 4. OpenTelemetry / GenAI ਨਿਰੀਖਣਯੋਗਤਾ

ਫ਼ਾਈਲਾਂ: `open-sse/services/routing/otel.ts`

- ਡਿਪੈਂਡੈਂਸੀ-ਰਹਿਤ OTLP/HTTP JSON ਐਕਸਪੋਰਟਰ (ਗਲੋਬਲ `fetch` ਵਰਤਦਾ ਹੈ, ਕੋਈ
  `@opentelemetry/*` SDK ਨਹੀਂ)।
- ਸਪੈਨ GenAI ਸਿਮੈਂਟਿਕ ਕਨਵੈਨਸ਼ਨਾਂ (`gen_ai.provider.name`,
  `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`,
  `gen_ai.completion.finish_reason`, `gen_ai.system`) ਦੇ ਨਾਲ OmniRoute ਰਾਊਟਿੰਗ
  ਐਟ੍ਰਿਬਿਊਟਾਂ (ਨਤੀਜਾ, ਸਥਿਤੀ, ttft, ਮੁੜ-ਕੋਸ਼ਿਸ਼ਾਂ, ਫਾਲਬੈਕ) ਦੀ ਪਾਲਣਾ ਕਰਦੇ ਹਨ।
- `record()` ਸਿਰਫ਼ ਇੱਕ ਸੀਮਿਤ ਬਫ਼ਰ ਵਿੱਚ ਕਤਾਰਬੱਧ ਕਰਦਾ ਹੈ (O(1)); ਇੱਕ ਬੈਕਗ੍ਰਾਊਂਡ ਟਾਈਮਰ
  `POST {endpoint}/v1/traces` ਰਾਹੀਂ ਅਸਿੰਕ੍ਰੋਨਸ ਤੌਰ 'ਤੇ ਫਲੱਸ਼ ਕਰਦਾ ਹੈ। ਓਵਰਲੋਡ ਦੌਰਾਨ
  ਸਭ ਤੋਂ ਪੁਰਾਣੇ ਇਵੈਂਟ ਡਰੌਪ ਕੀਤੇ ਜਾਂਦੇ ਹਨ (`dropped` ਕਾਊਂਟਰ) — ਡਾਟਾ
  ਪਲੇਨ 'ਤੇ ਕਦੇ ਵੀ ਬੈਕਪ੍ਰੈਸ਼ਰ ਨਹੀਂ ਪਾਇਆ ਜਾਂਦਾ।
- **ਕਨਫ਼ਿਗਰ ਕੀਤੇ ਬਿਨਾਂ ਅਸਮਰੱਥ।** `OMNIROUTE_OTEL_ENDPOINT` (ਜਾਂ
  `OTEL_EXPORTER_OTLP_ENDPOINT`) ਸੈੱਟ ਹੋਣਾ ਲਾਜ਼ਮੀ ਹੈ; ਨਹੀਂ ਤਾਂ ਸਿੰਕ
  ਰਜਿਸਟਰ ਨਹੀਂ ਹੁੰਦਾ ਅਤੇ ਕੋਈ OTel ਕੋਡ ਨਹੀਂ ਚੱਲਦਾ।

## 5. ਵਿਆਖਿਆਯੋਗਤਾ

- `GET /v1/explain/routing` ਹਾਲੀਆ `RoutingEvent`s (ਅਸਲ
  ਫ਼ੈਸਲੇ, ਸਭ ਤੋਂ ਨਵੇਂ ਪਹਿਲਾਂ) ਅਤੇ ਪ੍ਰਤੀ-ਪ੍ਰੋਵਾਈਡਰ/ਮਾਡਲ ਗੁਣਵੱਤਾ ਸਨੈਪਸ਼ਾਟ ਵਾਪਸ ਕਰਦਾ ਹੈ।
- ਪ੍ਰਮਾਣੀਕਰਨ `/v1/combos` ਦੇ ਅਨੁਸਾਰ ਹੈ (Bearer API ਕੁੰਜੀ ਜਾਂ ਡੈਸ਼ਬੋਰਡ ਸੈਸ਼ਨ;
  `REQUIRE_API_KEY=false` ਵਾਲੀਆਂ ਸਿੰਗਲ-ਯੂਜ਼ਰ ਲੋਕਲ ਡਿਪਲੌਇਮੈਂਟਾਂ 'ਤੇ ਅਗਿਆਤ ਪਹੁੰਚ)।
- ਕੌਂਬੋ-ਪੱਧਰੀ ਪ੍ਰਤੀ-ਇਨਵੋਕੇਸ਼ਨ ਟ੍ਰੇਸ ਮੌਜੂਦਾ
  `decisionTrace.ts` (ਹੈਡਰ `X-OmniRoute-Combo-Trace`) ਰਾਹੀਂ ਉਪਲਬਧ ਰਹਿੰਦੇ ਹਨ।
- ਸੁਰੱਖਿਆ: ਇਵੈਂਟਾਂ ਵਿੱਚ ਸਿਰਫ਼ ਰਾਊਟਿੰਗ ਮੈਟਾਡੇਟਾ ਹੁੰਦਾ ਹੈ, ਕਦੇ ਵੀ ਪ੍ਰੌਮਪਟ/ਬਾਡੀ/ਕ੍ਰੈਡੈਂਸ਼ਲ ਨਹੀਂ।

## 6. ਮੁਲਾਂਕਣ-ਪਲੇਨ ਇੰਟੀਗ੍ਰੇਸ਼ਨ (Future AGI ਤਿਆਰੀ)

OmniRoute, Future AGI (ਜਾਂ ਕਿਸੇ ਵੀ ਮੁਲਾਂਕਣਕਰਤਾ) ਨੂੰ ਇੱਕ **ਸੰਭਾਵੀ
ਇੰਟੈਲੀਜੈਂਸ/ਮੁਲਾਂਕਣ ਬੈਕਐਂਡ ਮੰਨਦਾ ਹੈ, ਡਿਪੈਂਡੈਂਸੀ ਨਹੀਂ**। ਇੰਟੀਗ੍ਰੇਸ਼ਨ ਸੀਮਾਂ:

- ਇੱਕ `RoutingEventSink` ਇਵੈਂਟਾਂ ਨੂੰ ਅਸਿੰਕ੍ਰੋਨਸ ਤੌਰ 'ਤੇ ਮੁਲਾਂਕਣਕਰਤਾ ਨੂੰ ਫਾਰਵਰਡ ਕਰ ਸਕਦਾ ਹੈ।
- `MemoryRoutingEventStore` + ਗੁਣਵੱਤਾ ਸਨੈਪਸ਼ਾਟ ਮੁਲਾਂਕਣਕਰਤਾ ਨੂੰ ਕੱਚੀ
  ਫ਼ੈਸਲਾ ਸਟ੍ਰੀਮ ਪ੍ਰਦਾਨ ਕਰਦੇ ਹਨ।
- ਭਵਿੱਖ ਦਾ ਇੱਕ `Evaluator` (ਡਿਟਰਮਿਨਿਸਟਿਕ, ਲੋਕਲ ਜੱਜ, HTTP, WASM) ਇਵੈਂਟਾਂ/ਟ੍ਰੇਸਾਂ ਦੀ ਖਪਤ ਕਰੇਗਾ
  ਅਤੇ ਇੱਕ `QualityScore` ਵਾਪਸ ਕਰੇਗਾ, ਜੋ ਉਸੇ
  `getQualityScore`/ਗੁਣਵੱਤਾ-ਫੈਕਟਰ ਪਾਥ ਨੂੰ ਫੀਡ ਕਰਦਾ ਹੈ।
- ਮੌਜੂਦਾ ਮੁਲਾਂਕਣ-ਸੰਚਾਲਿਤ ਰਾਊਟਿੰਗ (`open-sse/services/evalRouting.ts`) ਸਮਰੱਥ ਹੋਣ 'ਤੇ
  ਪਹਿਲਾਂ ਹੀ `eval_runs` ਪਾਸ-ਰੇਟਾਂ ਮੁਤਾਬਕ ਕੌਂਬੋ ਟਾਰਗੇਟਾਂ ਨੂੰ ਮੁੜ ਕ੍ਰਮਬੱਧ ਕਰਦੀ ਹੈ।

ਬੇਨਤੀ ਪਾਥ 'ਤੇ ਕੋਈ ਮੁਲਾਂਕਣ ਸਿੰਕ੍ਰੋਨਸ ਤੌਰ 'ਤੇ ਨਹੀਂ ਚੱਲਦਾ, ਅਤੇ ਮੁਲਾਂਕਣਕਰਤਾ ਦੀ ਗੈਰਹਾਜ਼ਰੀ ਵਿੱਚ ਵੀ ਗੇਟਵੇ
ਪੂਰੀ ਤਰ੍ਹਾਂ ਕੰਮ ਕਰਦਾ ਹੈ।

## 7. ਅੰਤਿਮ ਆਰਕੀਟੈਕਚਰਲ ਸਮੀਖਿਆ

1. **ਸਿੰਕ੍ਰੋਨਸ ਹੌਟ ਪਾਥ 'ਤੇ ਕੀ ਬਚਦਾ ਹੈ?** ਰਾਊਟਿੰਗ/ਸਕੋਰਿੰਗ, ਗਾਰਡਰੇਲ
   ਪ੍ਰੀ-ਚੈੱਕ, ਕੈਸ਼ ਲੁੱਕਅੱਪ, ਅਤੇ ਇਨ-ਮੈਮੋਰੀ ਸਿੰਕਾਂ ਲਈ ਇੱਕ `emitRoutingEvent` ਫੈਨ-ਆਉਟ (ਬੇਸਲਾਈਨ
   ਸਕੋਰਿੰਗ ਨਾਲੋਂ ~0.12 µs ਵੱਧ)।
2. **ਅਸਿੰਕ੍ਰੋਨਸ ਪ੍ਰੋਸੈਸਿੰਗ ਵੱਲ ਕੀ ਭੇਜਿਆ ਗਿਆ?** OTel ਐਕਸਪੋਰਟ (ਟਾਈਮਰ + fetch),
   `call_logs`/ਵਰਤੋਂ ਪਰਸਿਸਟੈਂਸ, ਸਿਮੈਂਟਿਕ-ਕੈਸ਼ ਰਾਈਟ; ਗੁਣਵੱਤਾ ਇਨ-ਮੈਮੋਰੀ
   ਅਤੇ O(1) ਹੈ (ਅਸਿੰਕ੍ਰੋਨਸ ਦੀ ਲੋੜ ਨਹੀਂ)।
3. **ਇੱਕ ਰਾਊਟਿੰਗ ਨਤੀਜਾ ਫੀਡਬੈਕ ਕਿਵੇਂ ਬਣਦਾ ਹੈ?** `handleChatCore` ਇੱਕ
   `RoutingEvent` ਐਮਿਟ ਕਰਦਾ ਹੈ → `QualityTracker` EWMA ਸਥਿਤੀ ਅੱਪਡੇਟ ਕਰਦਾ ਹੈ → `getQualityScore`
   ਆਟੋ-ਕੌਂਬੋ `quality` ਫੈਕਟਰ ਨੂੰ ਫੀਡ ਕਰਦਾ ਹੈ।
4. **ਗੁਣਵੱਤਾ ਭਵਿੱਖੀ ਰਾਊਟਿੰਗ ਨੂੰ ਕਿਵੇਂ ਪ੍ਰਭਾਵਿਤ ਕਰਦੀ ਹੈ?** ਘੱਟ ਗੁਣਵੱਤਾ ਸਕੋਰ
   `scoreAutoTargets` ਵਿੱਚ ਉਸ ਪ੍ਰੋਵਾਈਡਰ/ਮਾਡਲ ਦੇ ਭਾਰਿਤ ਸਕੋਰ ਨੂੰ ਘਟਾਉਂਦਾ ਹੈ, ਜਿਸ ਨਾਲ ਘੱਟ ਕਾਰਗੁਜ਼ਾਰੀ ਵਾਲੇ
   ਮਾਡਲਾਂ ਨੂੰ ਹੌਲੀ-ਹੌਲੀ ਘੱਟ ਤਰਜੀਹ ਮਿਲਦੀ ਹੈ ਅਤੇ ਉਹਨਾਂ ਦਾ EWMA ਸੁਧਰਨ ਦੇ ਨਾਲ ਉਹ ਮੁੜ ਬਿਹਤਰ ਸਥਿਤੀ ਵਿੱਚ ਆਉਂਦੇ ਹਨ।
5. **Future AGI ਡਿਪੈਂਡੈਂਸੀ ਬਣੇ ਬਿਨਾਂ ਕਿਵੇਂ ਇੰਟੀਗ੍ਰੇਟ ਹੋ ਸਕਦਾ ਹੈ?**
   `RoutingEventSink` ਇੰਟਰਫੇਸ / ਭਵਿੱਖ ਦੇ `Evaluator` ਐਡਾਪਟਰ ਰਾਹੀਂ — ਕੋਈ ਹਾਰਡਕੋਡ ਕੀਤੀ
   ਡਿਪੈਂਡੈਂਸੀ ਨਹੀਂ।
6. **ਮੁਲਾਂਕਣਕਰਤਾ ਅਣਉਪਲਬਧ ਹੋਣ 'ਤੇ ਕੀ ਹੁੰਦਾ ਹੈ?** ਰਾਊਟਿੰਗ ਪ੍ਰਭਾਵਿਤ ਨਹੀਂ ਹੁੰਦੀ;
   ਬਿਨਾਂ ਕਿਸੇ ਦੇਖੇ ਗਏ ਸਿਗਨਲ ਵਾਲੇ ਮਾਡਲਾਂ ਲਈ ਗੁਣਵੱਤਾ ਨਿਰਪੱਖ (1.0) 'ਤੇ ਵਾਪਸ ਆ ਜਾਂਦੀ ਹੈ।
7. **ਟੈਲੀਮੀਟਰੀ ਅਣਉਪਲਬਧ ਹੋਣ 'ਤੇ ਕੀ ਹੁੰਦਾ ਹੈ?** OTel ਸਿੰਕ ਸਿਰਫ਼
   ਰਜਿਸਟਰ ਨਹੀਂ ਹੁੰਦਾ; ਬਾਕੀ ਰਾਊਟਿੰਗ ਲੇਅਰ ਬਿਨਾਂ ਬਦਲਾਅ ਦੇ ਚੱਲਦੀ ਰਹਿੰਦੀ ਹੈ।
8. **ਓਵਰਲੋਡ ਦੌਰਾਨ ਕੀ ਹੁੰਦਾ ਹੈ?** OTel ਬਫ਼ਰ ਸਭ ਤੋਂ ਪੁਰਾਣੇ ਇਵੈਂਟ ਡਰੌਪ ਕਰਦਾ ਹੈ; ਗੁਣਵੱਤਾ
   ਅਤੇ ਰਿੰਗ ਬਫ਼ਰ ਡਿਜ਼ਾਈਨ ਅਨੁਸਾਰ ਸੀਮਿਤ ਹਨ; ਕੋਈ ਬੈਕਪ੍ਰੈਸ਼ਰ ਨਹੀਂ।
9. **ਗਿਰਾਵਟ ਤੋਂ ਬਾਅਦ ਪ੍ਰੋਵਾਈਡਰ ਦੀ ਸਥਿਤੀ ਕਿਵੇਂ ਮੁੜ ਬਹਾਲ ਹੁੰਦੀ ਹੈ?** ਸਫ਼ਲਤਾਵਾਂ
   ਇਕੱਠੀਆਂ ਹੋਣ ਨਾਲ EWMA ਮੁੜ ਕਨਵਰਜ ਕਰਦਾ ਹੈ; ਵਾਰਮਅੱਪ ਕੋਲਡ ਮਾਡਲਾਂ ਨੂੰ ਨਿਰਪੱਖ ਰੱਖਦਾ ਹੈ; ਸਰਕਿਟ ਬ੍ਰੇਕਰ
   HALF_OPEN ਪ੍ਰੋਬਾਂ ਰਾਹੀਂ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਮੁੜ ਬਹਾਲ ਹੁੰਦਾ ਹੈ।
10. **ਕਿਹੜੀਆਂ ਪ੍ਰਸਤਾਵਿਤ ਵਿਸ਼ੇਸ਼ਤਾਵਾਂ ਜਾਣਬੁੱਝ ਕੇ ਲਾਗੂ ਨਹੀਂ ਕੀਤੀਆਂ ਗਈਆਂ, ਅਤੇ ਕਿਉਂ?**
    - ਸ਼ੈਡੋ ਟ੍ਰੈਫਿਕ / ਪ੍ਰਯੋਗ — ਪਹਿਲਾਂ ਹੀ ਲਾਗੂ ਹਨ
      (`combo/shadowRouting.ts`); ਮੁੜ ਨਹੀਂ ਬਣਾਏ ਗਏ।
    - ਗਾਰਡਰੇਲ — ਪਹਿਲਾਂ ਹੀ ਲਾਗੂ ਹਨ (`src/lib/guardrails/`); ਡੁਪਲੀਕੇਟ ਨਹੀਂ ਕੀਤੇ ਗਏ।
    - ਸਿਮੈਂਟਿਕ ਕੈਸ਼ — ਪਹਿਲਾਂ ਹੀ ਲਾਗੂ ਹੈ (`src/lib/semanticCache.ts`); ਡੁਪਲੀਕੇਟ ਨਹੀਂ ਕੀਤਾ ਗਿਆ।
    - ਇੱਕ ਪੂਰਾ ਪ੍ਰਯੋਗ-ਪ੍ਰਬੰਧਨ ਪਲੇਟਫਾਰਮ, ਡਾਟਾਸੈੱਟ ਟੂਲਿੰਗ, ਪ੍ਰੌਮਪਟ-ਆਪਟੀਮਾਈਜ਼ੇਸ਼ਨ
      ਪਲੇਟਫਾਰਮ, ਵੈਕਟਰ DB, ਜਾਂ ਲਾਜ਼ਮੀ ਬਾਹਰੀ OTel ਇਨਫ੍ਰਾਸਟ੍ਰਕਚਰ — ਇੱਕ ਸੁਚੱਜੇ ਡਾਟਾ ਪਲੇਨ ਦੇ
      ਦਾਇਰੇ ਤੋਂ ਬਾਹਰ ਹਨ।
    - ਇੱਕ Rust `RoutingEvent` ਸਟਰੱਕਟ — ਡਾਟਾ ਪਲੇਨ TypeScript ਵਿੱਚ ਹੈ; TS ਟਾਈਪ
      ਇਸਦਾ ਅਨੁਕੂਲਿਤ ਸਮਕੱਖ ਹੈ।
