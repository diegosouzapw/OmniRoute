ਇਹ ਦਸਤਾਵੇਜ਼ OmniRoute ਵਿੱਚ ਸਾਰੇ CI ਗੁਣਵੱਤਾ ਗੇਟਾਂ ਲਈ ਪ੍ਰਮਾਣਿਕ ਹਵਾਲਾ ਹੈ।
ਇਹ ਹਰ ਗੇਟ ਦਾ ਵਰਣਨ ਕਰਦਾ ਹੈ, ਇਹ ਕੀ ਪ੍ਰਮਾਣਿਤ ਕਰਦਾ ਹੈ, ਇਹ ਕਿਸ CI ਜੌਬ ਵਿੱਚ ਚੱਲਦਾ ਹੈ, ਕੀ ਇਹ
ਰੈਚਟ ਬੇਸਲਾਈਨ ਜਾਂ ਪਾਸ/ਫੇਲ ਨੀਤੀ ਵਰਤਦਾ ਹੈ, ਅਤੇ ਕੀ ਇਹ ਬਿਲਡ ਨੂੰ ਰੋਕਦਾ ਹੈ ਜਾਂ ਸਿਰਫ਼ ਸਲਾਹਕਾਰੀ ਹੈ।

ਸੰਖੇਪ ਸਾਰ ਅਤੇ ਅਲਾਊਲਿਸਟ ਨੀਤੀ ਲਈ, `AGENTS.md` ਵਿੱਚ "ਗੁਣਵੱਤਾ ਗੇਟ ਅਤੇ ਰੈਚਟ" ਭਾਗ
ਦੇਖੋ। ਇਸੇ ਸਿਸਟਮ ਦੇ ਆਲੋਚਨਾਤਮਕ ਮੁਲਾਂਕਣ, ਪਰਿਪੱਕਤਾ ਵਰਗੀਕਰਨ ਅਤੇ ਟੂਲ-ਨਿਰਪੱਖ
ਪੁਨਰ-ਨਿਰਮਾਣ ਯੋਜਨਾ ਲਈ,
[ਗੁਣਵੱਤਾ ਗੇਟ ਪਲੇਬੁੱਕ](../ops/QUALITY_GATE_PLAYBOOK.md) ਦੇਖੋ।

## ਗੇਟ ਇਨਵੈਂਟਰੀ (~90 ਸਕ੍ਰਿਪਟਾਂ)

ਸਕ੍ਰਿਪਟਾਂ `scripts/check/` (ਨੀਤੀ ਗੇਟਾਂ) ਅਤੇ `scripts/quality/` (ਰੈਚਟ ਇੰਜਣ) ਦੇ ਅਧੀਨ ਮੌਜੂਦ ਹਨ।
CI ਲਈ ਸੱਚਾਈ ਦਾ ਮੂਲ ਸਰੋਤ `.github/workflows/ci.yml` ਹੈ।

### ਰਿਲੀਜ਼ PR ਫਾਸਟ-ਪਾਥ (`quality.yml`)

`.github/workflows/quality.yml`, `release/**` ਨੂੰ ਟਾਰਗੇਟ ਕਰਨ ਵਾਲੇ PRs ਉੱਤੇ ਚੱਲਦਾ ਹੈ। ਇਹ ਪਾਥ-ਫਿਲਟਰ ਕੀਤੇ ਤੇਜ਼ ਗੇਟਾਂ ਨਾਲ ਯੋਗਦਾਨਕਰਤਾਵਾਂ ਦੀਆਂ ਬ੍ਰਾਂਚਾਂ ਨੂੰ ਅੱਗੇ ਵਧਾਉਂਦਾ ਰਹਿੰਦਾ ਹੈ, ਨਾਲ ਹੀ ਕੋਡ ਬਦਲਾਵਾਂ ਲਈ ਇੱਕ ਸਲਾਹਕਾਰੀ ਪ੍ਰੋਡਕਸ਼ਨ-ਬਿਲਡ ਸੰਕੇਤ ਵੀ ਦਿੰਦਾ ਹੈ:

| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |

#### ਭੁੱਲੇ ਹੋਏ ਸਿਬਲਿੰਗ ਟੈਸਟਾਂ ਦੀ ਰਿਪੋਰਟ

`npm run check:forgotten-sibling-tests`, ਟੈਸਟ-ਪ੍ਰਭਾਵ ਮੈਪ ਦੇ ਪਿੱਛੇ ਵਾਲੇ ਇੰਪੋਰਟ ਰਿਜ਼ਾਲਵਰ ਨੂੰ ਮੁੜ ਵਰਤਦਾ ਹੈ।
ਹਰੇਕ ਬਦਲੇ ਹੋਏ ਪ੍ਰੋਡਕਸ਼ਨ ਮੌਡਿਊਲ ਲਈ, ਜਦੋਂ ਸੰਭਾਵੀ ਟੈਸਟ ਪੁੱਲ-ਰਿਕਵੇਸਟ diff ਵਿੱਚ ਮੌਜੂਦ ਨਹੀਂ ਹੁੰਦਾ, ਇਹ ਨਿਰਧਾਰਤ
`changed module/symbol -> static consumer -> candidate sibling test` ਲੜੀਆਂ ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ। ਕਿਸੇ ਵੀ ਬਲੌਕਿੰਗ ਰੋਲਆਉਟ ਤੋਂ ਪਹਿਲਾਂ ਕੈਲੀਬ੍ਰੇਸ਼ਨ ਲਈ Markdown ਸੰਖੇਪ ਅਤੇ JSON ਨਤੀਜਾ
`forgotten-sibling-tests` workflow ਆਰਟੀਫੈਕਟ ਵਜੋਂ ਸੰਭਾਲੇ ਜਾਂਦੇ ਹਨ।

ਬੈਰਲ ਰੀ-ਐਕਸਪੋਰਟ ਅਤੇ ਡਾਇਨਾਮਿਕ ਇੰਪੋਰਟ ਸਿਰਫ਼ ਰਿਜ਼ੋਲੂਸ਼ਨ ਡਾਇਗਨੌਸਟਿਕਸ ਹਨ; ਇਹ ਕਦੇ ਵੀ ਕੋਈ
ਬਲੌਕਿੰਗ ਨਤੀਜਾ ਨਹੀਂ ਬਣਾਉਂਦੇ। ਸਮੀਖਿਆ ਕੀਤੇ ਅਪਵਾਦ
`config/quality/forgotten-sibling-allowlist.json` ਵਿੱਚ ਮੌਜੂਦ ਹਨ। ਹਰੇਕ ਐਂਟਰੀ ਵਿੱਚ ਖਪਤਕਾਰ ਅਤੇ ਸੰਭਾਵੀ
ਟੈਸਟ ਦਾ ਨਾਮ ਹੋਣਾ, ਇੱਕ ਖਾਸ ਤਰਕ ਦੇਣਾ, ਅਤੇ GitHub issue ਜਾਂ pull request ਦਾ ਲਿੰਕ ਹੋਣਾ ਲਾਜ਼ਮੀ ਹੈ। ਗਲਤ-ਰੂਪ ਵਾਲੀਆਂ ਐਂਟਰੀਆਂ
ਫੇਲ-ਕਲੋਜ਼ਡ ਹੁੰਦੀਆਂ ਹਨ। ਅਪਵਾਦ ਮਿਟਾਏ ਗਏ ਸੰਭਾਵੀ ਟੈਸਟ ਜਾਂ `.skip`/`.todo` ਜੋੜਨ ਵਾਲੇ diff ਨੂੰ suppress ਨਹੀਂ ਕਰ ਸਕਦੇ;
assertion ਨੂੰ ਕਮਜ਼ੋਰ ਕਰਨਾ ਅਤੇ ਹੋਰ masking, ਸੁਤੰਤਰ ਤੌਰ ’ਤੇ ਬਲੌਕ ਕਰਨ ਵਾਲੇ
`check:test-masking` ਗੇਟ ਦੀ ਜ਼ਿੰਮੇਵਾਰੀ ਰਹਿੰਦੀ ਹੈ।

#### `check-ui-value-drift` — ਪੁਰਾਣੇ-ਅਨੁਵਾਦ ਦਾ ਗੇਟ

ਇਹ ਉਸ ਇੱਕ i18n regression ਨੂੰ ਫੜਦਾ ਹੈ ਜਿਸਨੂੰ ਹੋਰ gates ਸੰਰਚਨਾਤਮਕ ਤੌਰ 'ਤੇ ਨਹੀਂ ਦੇਖ ਸਕਦੇ: ਇੱਕ ਅੰਗਰੇਜ਼ੀ ਮੁੱਲ
ਮੁੜ ਲਿਖਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ _ਪਿਛਲੇ_ ਅੰਗਰੇਜ਼ੀ ਮੁੱਲ ਤੋਂ ਬਣੇ ਅਨੁਵਾਦ ਉੱਥੇ ਹੀ ਰਹਿ ਜਾਂਦੇ ਹਨ, ਜਿਸ ਕਾਰਨ
ਗੈਰ-ਅੰਗਰੇਜ਼ੀ ਵਰਤੋਂਕਾਰ ਭਰੋਸੇ ਨਾਲ ਲਿਖੀ, ਪਰ ਹੁਣ ਗਲਤ, ਕਾਪੀ ਪੜ੍ਹਦੇ ਰਹਿੰਦੇ ਹਨ।

ਇਹ ਸਮੱਸਿਆ ਅਸਲ ਵਿੱਚ ਰਿਲੀਜ਼ ਹੋਈ ਸੀ। ਜਦੋਂ Antigravity
login helper ਜੋੜਿਆ ਗਿਆ (#5203), ਤਾਂ `oauthModal.googleOAuthWarning` ਨੂੰ ਮੁੜ ਲਿਖਿਆ ਗਿਆ; **43 ਵਿੱਚੋਂ 39 locales** ਵਿੱਚ operators ਨੂੰ "ਪੂਰਾ
URL ਕਾਪੀ ਕਰਕੇ ਹੇਠਾਂ ਪੇਸਟ ਕਰਨ" ਲਈ ਕਹਿਣ ਵਾਲਾ ਟੈਕਸਟ ਕਾਇਮ ਰਿਹਾ — ਅਜਿਹਾ flow ਜੋ ਉਸ provider ਲਈ ਪੂਰਾ ਨਹੀਂ ਹੋ ਸਕਦਾ। ਇਹ
#8463 ਤੱਕ ਅਣਦੇਖਿਆ ਰਿਹਾ ਕਿਉਂਕਿ:

- `sync-ui-keys` ਸਿਰਫ਼ ਉਹ keys backfill ਕਰਦਾ ਹੈ ਜੋ **ਗੈਰ-ਮੌਜੂਦ** ਹਨ, **ਪੁਰਾਣੀਆਂ** keys ਨੂੰ ਕਦੇ ਨਹੀਂ;
- `check-ui-keys-coverage` key ਦੀ _ਮੌਜੂਦਗੀ_ ਗਿਣਦਾ ਹੈ, ਇਸ ਲਈ ਪੁਰਾਣਾ ਅਨੁਵਾਦ ਵੀ covered ਵਜੋਂ ਗਿਣਿਆ ਜਾਂਦਾ ਹੈ;
- `check-translation-drift`, `docs/i18n/<locale>/**.md` documentation mirrors ਨੂੰ ਟਰੈਕ ਕਰਦਾ ਹੈ —
  ਇਹ ਕਦੇ ਵੀ `src/i18n/messages/*.json` ਨੂੰ ਨਹੀਂ ਪੜ੍ਹਦਾ। 2026-09 re-sync ਤੋਂ ਜੌਬ `docs-sync-strict` ਵਿੱਚ ਰੋਕਣ ਵਾਲਾ:
  ਕੋਈ core doc ਸੋਧੋ → `npm run i18n:run -- --files=<doc>` (section-level, ਘੱਟ ਲਾਗਤ ਵਾਲਾ)।

**Diff-aware, baseline-backed ਨਹੀਂ।** ਇਹ merge base ਉੱਤੇ ਮੌਜੂਦ `en.json` ਦੀ ਤੁਲਨਾ
working tree ਨਾਲ ਕਰਦਾ ਹੈ; ਹਰੇਕ ਉਸ ਕੁੰਜੀ ਲਈ ਜਿਸਦਾ ਅੰਗਰੇਜ਼ੀ ਮੁੱਲ ਬਦਲਿਆ ਹੈ, ਕੋਈ ਵੀ locale ਜਿਸ ਵਿੱਚ
ਅਜੇ ਵੀ ਨਾ-ਛੁਹਿਆ ਅਨੁਵਾਦ ਮੌਜੂਦ ਹੈ, ਪੁਰਾਣਾ ਮੰਨਿਆ ਜਾਂਦਾ ਹੈ। ਇਹ ਜਾਣ-ਬੁੱਝ ਕੇ **ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਕਰਜ਼ੇ ਨੂੰ ਸਥਿਰ ਰੱਖਦਾ ਹੈ** — ਕੋਈ diff
ਇਹ ਨਹੀਂ ਦੱਸ ਸਕਦਾ ਕਿ ਲੰਮੇ ਸਮੇਂ ਤੋਂ ਮੌਜੂਦ ਅਨੁਵਾਦ ਕਿਸ ਪੁਰਾਣੇ ਅੰਗਰੇਜ਼ੀ ਪਾਠ ਤੋਂ ਆਇਆ ਸੀ, ਇਸ ਲਈ gate
ਸਿਰਫ਼ ਉਹੀ ਜਾਂਚਦਾ ਹੈ ਜਿਸਨੂੰ ਮੌਜੂਦਾ ਤਬਦੀਲੀ ਛੂੰਹਦੀ ਹੈ। ਵਿਕਲਪ (ਹਰੇਕ ਕੁੰਜੀ ਲਈ hash baseline) ਵਾਸਤੇ
ਲਗਭਗ 600 KB ਦੀ generated ਫ਼ਾਈਲ ਚਾਹੀਦੀ ਹੋਵੇਗੀ, ਜੋ ਸਭ ਤੋਂ ਵੱਡੇ ਮੌਜੂਦਾ baseline ਤੋਂ 3× ਵੱਡੀ ਹੈ ਅਤੇ ਹਰੇਕ i18n PR ਉੱਤੇ ਬਦਲੇਗੀ।

ਇਸਨੂੰ ਸੰਤੁਸ਼ਟ ਕਰਨ ਦੇ ਦੋ ਤਰੀਕੇ ਹਨ:

1. ਪ੍ਰਭਾਵਿਤ ਅਨੁਵਾਦਾਂ ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ, ਜਾਂ
2. ਉਨ੍ਹਾਂ ਨੂੰ `__MISSING__:<new english>` ਉੱਤੇ ਸੈੱਟ ਕਰੋ — ਫਿਰ runtime ਸਹੀ ਕੀਤਾ ਅੰਗਰੇਜ਼ੀ ਪਾਠ
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ ਅਤੇ ਕੁੰਜੀ ਅਨੁਵਾਦ ਲਈ ਕਤਾਰ ਵਿੱਚ ਲੱਗ ਜਾਂਦੀ ਹੈ।

ਜੇ string ਦਾ **ਅਰਥ** ਬਦਲਿਆ ਹੈ, ਤਾਂ **ਕੁੰਜੀ ਦਾ ਨਾਮ ਬਦਲਣ** ਨੂੰ ਤਰਜੀਹ ਦਿਓ: ਨਵੀਂ ਕੁੰਜੀ
ਕਿਸੇ ਪੁਰਾਣੇ ਅਨੁਵਾਦ ਨੂੰ ਵਿਰਾਸਤ ਵਿੱਚ ਨਹੀਂ ਲੈ ਸਕਦੀ। #8463 ਨੇ ਇਹੀ ਪੈਟਰਨ ਵਰਤਿਆ ਸੀ।

```bash
npm run i18n:check-value-drift          # ਸਖ਼ਤ (ਜੋ CI ਚਲਾਉਂਦਾ ਹੈ)
npm run i18n:check-value-drift:warn     # ਸਿਰਫ਼ ਰਿਪੋਰਟ
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

ਜਦੋਂ base catalog ਪੜ੍ਹਿਆ ਨਹੀਂ ਜਾ ਸਕਦਾ (base ref ਤੋਂ ਬਿਨਾਂ shallow
clone), ਤਾਂ `SKIP reason=base-unresolved` ਨਾਲ 0 exit ਕਰਦਾ ਹੈ, ਜੋ `check-openapi-breaking` ਦੇ ਵਿਹਾਰ ਵਰਗਾ ਹੈ।

`nightly-release-green.yml` → ਜੌਬ **`bank-ratchet-shrinks`** ਉਸ ਚੱਕਰ ਨੂੰ ਬੰਦ ਕਰਦੀ ਹੈ:

|               |                                                                                                          |
| ------------- | -------------------------------------------------------------------------------------------------------- |
| ਚੱਲਦੀ ਹੈ      | `schedule` (3×/ਦਿਨ) + `workflow_dispatch` — ਜਾਣ-ਬੁੱਝ ਕੇ `push` 'ਤੇ **ਨਹੀਂ**                              |
| ਮਾਪਦੀ ਹੈ      | ਸਭ ਤੋਂ ਉੱਚਾ `release/vX.Y.Z`, `release-green` ਵਰਗਾ ਹੀ ਰਿਜ਼ੋਲਿਊਸ਼ਨ + ਇੰਜੈਕਸ਼ਨ ਗਾਰਡ                        |

ਦੇ ਅੰਦਰ ਬੈਂਕ ਕੀਤੀ ਘਟਾਵ ਠੀਕ ਹੈ), ਜਦਕਿ ਪ੍ਰਤੀ-ਮਰਜ ਰਨ, ਮਰਜ ਮੁਹਿੰਮਾਂ ਦੌਰਾਨ PR ਸ਼ਾਖਾ ਨੂੰ ਵਾਰ-ਵਾਰ
ਮੁੜ ਬਣਾਉਂਦਾ ਅਤੇ ਹਰ ਵਾਰ ਪੂਰੇ ESLint ਵਾਕ ਦੀ ਲਾਗਤ ਭਰਦਾ। ਪਛਾਣ `push` (`release-green`) 'ਤੇ ਹੀ ਰਹਿੰਦੀ ਹੈ;
ਸਿਰਫ਼ ਬੈਂਕਿੰਗ ਬੈਚਾਂ ਵਿੱਚ ਕੀਤੀ ਜਾਂਦੀ ਹੈ।

### ਸੁਰੱਖਿਆ ਤਸਦੀਕਕਾਰ

ਜੌਬ ਬਿਨਾਂ ਨਿਗਰਾਨੀ ਦੇ ਬੇਸਲਾਈਨਾਂ ਵਿੱਚ ਲਿਖਦੀ ਹੈ, ਇਸ ਲਈ `verify-ratchet-bank.mjs` ਹੀ ਇਸਨੂੰ
ਸਵੀਕਾਰਯੋਗ ਬਣਾਉਂਦਾ ਹੈ। ਇਹ `--update` ਤੋਂ ਬਾਅਦ ਵਾਲੇ ਟ੍ਰੀ ਦੀ `HEAD` ਨਾਲ ਤੁਲਨਾ ਕਰਦਾ ਹੈ ਅਤੇ **ਕੋਈ ਵੀ ਕਮਿਟ
ਮੌਜੂਦ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਜੌਬ ਨੂੰ ਰੋਕ ਦਿੰਦਾ ਹੈ** — ਕੋਈ PR ਨਹੀਂ ਖੋਲ੍ਹਦਾ — ਜਦੋਂ ਤੱਕ ਹਰ ਤਬਦੀਲੀ ਇਨ੍ਹਾਂ ਵਿੱਚੋਂ ਇੱਕ ਨਾ ਹੋਵੇ:

- ਇੱਕ `frozen` / `testFrozen` ਅੰਕੀ ਐਂਟਰੀ **ਘਟਾਈ** ਜਾਂ **ਹਟਾਈ** ਗਈ ਹੋਵੇ
- `complexity-baseline.json` → `count` **ਘਟਾਇਆ** ਗਿਆ ਹੋਵੇ
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` **ਘਟਾਇਆ** ਗਿਆ ਹੋਵੇ

ਹੋਰ ਕੁਝ ਵੀ ਅਸਫਲ ਹੁੰਦਾ ਹੈ: ਕੋਈ ਸੰਖਿਆ ਵਧਾਉਣਾ, ਐਂਟਰੀ ਜੋੜਨਾ, `cap`/`testCap` ਬਦਲਣਾ, ਜਾਂ
ਕਿਸੇ `_rebaseline_*` ਨੋਟ ਨੂੰ ਮਿਟਾਉਣਾ/ਮੁੜ ਲਿਖਣਾ (ਉਹ ਨੋਟ ਇਸ ਗੱਲ ਦਾ ਆਡਿਟ ਟ੍ਰੇਲ ਹਨ ਕਿ ਹਰੇਕ
ਉੱਪਰੀ ਸੀਮਾ ਕਿਉਂ ਮੌਜੂਦ ਹੈ ਅਤੇ ਉਹ ਫ਼ਾਈਲ ਐਂਟਰੀਆਂ ਵਾਲੇ ਉਸੇ `frozen` ਆਬਜੈਕਟ ਦੇ ਅੰਦਰ ਸਟੋਰ ਕੀਤੇ ਜਾਂਦੇ ਹਨ)।
ਜੋ ਬੌਟ ਸੀਮਾ ਵਧਾ ਸਕੇ, ਉਹ ਮੌਜੂਦਾ ਸਥਿਤੀ ਨਾਲੋਂ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਹੋਰ ਮਾੜਾ ਹੋਵੇਗਾ। ਰਿਗ੍ਰੈਸ਼ਨ
ਗਾਰਡ: `tests/unit/verify-ratchet-bank.test.ts`.

ਜੌਬ ਕਦੇ ਵੀ `release/*` ਵੱਲ push ਨਹੀਂ ਕਰਦੀ — ਇੱਕ ਮਨੁੱਖ PR ਨੂੰ ਮਰਜ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ ਕੋਈ ਖਰਾਬ ਮਾਪ
ਬਿਨਾਂ ਸਮੀਖਿਆ ਦੇ ਲਾਗੂ ਨਹੀਂ ਹੋ ਸਕਦਾ।

## ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਨੀਤੀ

ਹਰ ਉਹ ਗੇਟ ਜੋ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਉਲੰਘਣਾਵਾਂ ਕਾਰਨ ਅਸਫਲ ਨਹੀਂ ਹੋ ਸਕਦਾ, ਇੱਕ ਸਥਿਰ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਵਰਤਦਾ ਹੈ
(ਉਦਾਹਰਨ ਲਈ, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)। ਨੀਤੀ ਇਹ ਹੈ:

**ਮੂਲ ਕਾਰਨ ਠੀਕ ਕਰੋ; ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਸਿਰਫ਼ ਉਦੋਂ ਵਰਤੋ ਜਦੋਂ ਉਲੰਘਣਾ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਹੋਵੇ ਅਤੇ
ਉਸੇ PR ਵਿੱਚ ਠੀਕ ਨਾ ਕੀਤੀ ਜਾ ਸਕਦੀ ਹੋਵੇ।**

ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਵਿੱਚ ਕੋਈ ਐਂਟਰੀ ਸ਼ਾਮਲ ਕਰਦੇ ਸਮੇਂ:

1. ਕਾਰਨ ਦੱਸਦੀ ਇੱਕ ਟਿੱਪਣੀ ਸ਼ਾਮਲ ਕਰੋ।
2. ਟ੍ਰੈਕਿੰਗ ਮੁੱਦੇ ਦਾ ਹਵਾਲਾ ਦਿਓ (ਉਦਾਹਰਨ ਲਈ, `// #3498 — ਪੜਾਅ 2 ਦੀ ਵਿਸ਼ੇਸ਼ਤਾ, ਹਾਲੇ ਲਾਗੂ ਨਹੀਂ ਕੀਤੀ ਗਈ`)।
3. ਉਲੰਘਣਾ ਠੀਕ ਕਰਨ ਵਾਲੇ ਉਸੇ PR ਵਿੱਚ ਐਂਟਰੀ ਹਟਾਓ — ਇੱਕ ਪੁਰਾਣੀ ਐਂਟਰੀ ਜੋ ਹੁਣ
   ਕਿਸੇ ਸਰਗਰਮ ਉਲੰਘਣਾ ਨੂੰ ਦਬਾਉਂਦੀ ਨਹੀਂ ਹੈ, ਆਪਣੇ ਆਪ ਵਿੱਚ ਇੱਕ ਖ਼ਰਾਬੀ ਹੈ (6A.3 ਪੁਰਾਣੀ-ਲਾਗੂਕਰਨ ਜਾਂਚ,
   ਲਾਗੂ ਹੋਣ ਤੋਂ ਬਾਅਦ, ਇਕੱਲੀ ਰਹਿ ਗਈ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਐਂਟਰੀ ਕਾਰਨ ਗੇਟ ਨੂੰ ਅਸਫਲ ਕਰ ਦੇਵੇਗੀ)।

ਟੈਸਟਾਂ ਨੂੰ ਤੇਜ਼ੀ ਨਾਲ ਪਾਸ ਕਰਵਾਉਣ ਲਈ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਵਿੱਚ ਐਂਟਰੀਆਂ **ਨਾ** ਜੋੜੋ। ਵਧਦੀ ਹੋਈ

## ਨਵਾਂ ਗੇਟ ਸ਼ਾਮਲ ਕਰਨਾ

1. `scripts/check/check-<name>.mjs` (ਜਾਂ `.ts`) ਬਣਾਓ। ਨੀਤੀ ਗੇਟ 0/1 ਨਾਲ ਬੰਦ ਹੁੰਦੇ ਹਨ।
   ਰੈਚਿਟ-ਸ਼ੈਲੀ ਗੇਟ `collect-metrics.mjs` ਰਾਹੀਂ `quality-metrics.json` ਵਿੱਚ ਇੱਕ ਮਾਪਦੰਡ ਲਿਖਦੇ ਹਨ।
2. `package.json` ਵਿੱਚ `"check:<name>": "node scripts/check/check-<name>.mjs"` ਸ਼ਾਮਲ ਕਰੋ।
3. ਇਸਨੂੰ `.github/workflows/ci.yml` ਵਿੱਚ ਢੁਕਵੀਂ ਜੌਬ ਹੇਠ ਜੋੜੋ
   (ਨੀਤੀ → `lint` ਜਾਂ `docs-sync-strict`; ਰੈਚਿਟ → `quality-gate`)।
4. ਜੇ ਇਸਦੀ ਕੋਈ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਹੈ, ਤਾਂ `scripts/check/lib/allowlist.mjs` ਤੋਂ
   `reportStaleEntries()` ਲਾਗੂ ਕਰੋ, ਤਾਂ ਜੋ ਪੁਰਾਣੀਆਂ ਐਂਟਰੀਆਂ ਆਪਣੇ ਆਪ ਪਛਾਣੀਆਂ ਜਾਣ।
5. ਗੇਟ ਦੀ ਪਛਾਣ ਤਰਕ ਨੂੰ ਕਵਰ ਕਰਨ ਵਾਲਾ ਇੱਕ ਟੈਸਟ `tests/unit/build/` ਵਿੱਚ ਲਿਖੋ।
6. ਇਸ ਦਸਤਾਵੇਜ਼ ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ (ਸੰਬੰਧਿਤ ਜੌਬ ਸਾਰਣੀ ਵਿੱਚ ਇੱਕ ਕਤਾਰ ਸ਼ਾਮਲ ਕਰੋ)।

## ਏਜੰਟ ਟੂਲਿੰਗ: LSP-in-the-loop (ਚੋਣਵਾਂ)

CI ਗੇਟਾਂ ਤੋਂ ਇਲਾਵਾ, OmniRoute ਇੱਕ **ਚੋਣਵਾਂ** `agent-lsp` ਸਕੈਫੋਲਡ ਮੁਹੱਈਆ ਕਰਦਾ ਹੈ
(ਇੱਕ ਪ੍ਰੋਜੈਕਟ-ਪੱਧਰੀ `.mcp.json`, Fase 7 Task 15)। ਕੋਡਿੰਗ ਏਜੰਟਾਂ ਨੂੰ TypeScript ਭਾਸ਼ਾ ਸਰਵਰ ਉਪਲਬਧ ਕਰਵਾਉਣ ਲਈ `.mcp.json`
ਬਣਾਓ, ਤਾਂ ਜੋ ਉਹ ਕੋਡ ਲਿਖਣ ਤੋਂ **ਪਹਿਲਾਂ** ਚਿੰਨ੍ਹਾਂ /
ਡਾਇਗਨੋਸਟਿਕਸ ਦਾ ਨਿਰਾਕਰਨ ਕਰਨ — `typecheck:core` ਦਾ ਇੱਕ ਕੰਪਾਇਲ-ਕਰਨ-ਤੋਂ-ਪਹਿਲਾਂ-ਦਾਅਵਾ ਸਾਥੀ,
ਜੋ "ਘੜੇ ਹੋਏ ਚਿੰਨ੍ਹ" ਵਾਲੀਆਂ ਗਲਤੀਆਂ ਨੂੰ ਸਰੋਤ ਉੱਤੇ ਹੀ ਘਟਾਉਂਦਾ ਹੈ। ਇਸਨੂੰ ਜਾਣਬੁੱਝ ਕੇ
ਆਪਣੇ ਆਪ ਲੋਡ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ (ਤੁਸੀਂ MCP↔LSP ਬ੍ਰਿਜ ਚੁਣਦੇ ਅਤੇ ਤਸਦੀਕ ਕਰਦੇ ਹੋ); ਇੱਕ ਖ਼ਰਾਬ ਐਂਟਰੀ ਸਿਰਫ਼
ਕਨੈਕਸ਼ਨ ਗਲਤੀ ਲੌਗ ਕਰਦੀ ਹੈ ਅਤੇ ਕਦੇ ਵੀ ਸੈਸ਼ਨਾਂ ਨੂੰ ਭੰਗ ਨਹੀਂ ਕਰਦੀ।

### ਮਰਜ / ਡੀਡੁਪਲੀਕੇਸ਼ਨ (ਮਕੈਨੀਕਲ, ਘੱਟ ਜੋਖਮ)

ਹਰੇਕ ਉਮੀਦਵਾਰ ਦੀ 2026-06-17 ਨੂੰ ਲਾਈਵ ਗੇਟ ਸਥਿਤੀ ਦੇ ਮੁਕਾਬਲੇ ਪੁਸ਼ਟੀ ਕੀਤੀ ਗਈ ਸੀ (ਭਰੋਸਾ ਕਰੋ, ਪਰ ਤਸਦੀਕ ਵੀ ਕਰੋ);
ਕਈ "ਸਪਸ਼ਟ" ਮਰਜਾਂ ਦੇ ਪਿੱਛੇ ਅਸਲ ਵਿੱਚ ਕਰਜ਼ ਲੁਕਿਆ ਹੋਇਆ ਸੀ ਅਤੇ ਉਹ **ਸਿੱਧੇ ਬਦਲ ਵਜੋਂ ਸਾਫ਼ ਨਹੀਂ** ਹਨ।

- **`check:docs-sync` ਦੋ ਵਾਰ ਚੱਲਦਾ ਹੈ** — `lint` ਜੌਬ ਵਿੱਚ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਅਤੇ ਦੁਬਾਰਾ `check:docs-all` (`docs-sync-strict`) ਅਤੇ husky pre-commit ਹੁੱਕ ਦੇ ਅੰਦਰ। ✅ **ਮੁਕੰਮਲ** — ਵੱਖਰਾ `lint` ਸੱਦਾ ਹਟਾ ਦਿੱਤਾ ਗਿਆ।
- **CVE ਸਕੈਨਿੰਗ** — ❌ **ਸਾਫ਼ ਮਰਜ ਨਹੀਂ ਹੈ।** `audit:deps` ਕਿਸੇ ਵੀ high/critical CVE ਉੱਤੇ ਪੱਕੇ ਤੌਰ 'ਤੇ ਫੇਲ੍ਹ ਹੁੰਦਾ ਹੈ; `check:vuln-ratchet` (osv) ਸਿਰਫ਼ ਬੇਸਲਾਈਨ ਦੇ ਮੁਕਾਬਲੇ ਕਿਸੇ _ਰਿਗ੍ਰੈਸ਼ਨ_ ਉੱਤੇ ਫੇਲ੍ਹ ਹੁੰਦਾ ਹੈ (ਇਸ ਵੇਲੇ 1 MODERATE)। ਅਰਥ-ਵਿਹਾਰ ਵੱਖਰੇ ਹਨ — `audit:deps` ਨੂੰ ਹਟਾਉਣ ਨਾਲ ਪੂਰਨ high/critical ਗੇਟ ਗੁਆਚ ਜਾਵੇਗਾ। ਦੋਵੇਂ ਰੱਖੋ।
- **ਸਾਈਕਲ ਪਛਾਣ** — ❌ **ਸਾਫ਼ ਮਰਜ ਨਹੀਂ ਹੈ।** `check:circular-deps` (dpdm) **91 ਸਾਈਕਲਾਂ** ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ (ਇਸੇ ਲਈ ਇਹ ਸਲਾਹਕਾਰੀ ਹੈ); ਪਹਿਲਾਂ ਉਨ੍ਹਾਂ ਨੂੰ ਹੱਲ ਕੀਤੇ ਬਿਨਾਂ ਇਸਨੂੰ ਬਲੌਕਿੰਗ ਨਹੀਂ ਬਣਾਇਆ ਜਾ ਸਕਦਾ, ਅਤੇ ਇਸਦਾ ਦਾਇਰਾ ਹਰੇ, ਚੁਣੇ ਹੋਏ `check:cycles` ਨਾਲੋਂ ਵੱਡਾ ਹੈ। `check:cycles` ਨੂੰ ਬਲੌਕਿੰਗ ਰੱਖੋ; 91 dpdm ਸਾਈਕਲਾਂ ਨੂੰ ਹੱਲ ਕਰਨਾ ਆਪਣਾ ਵੱਖਰਾ ਬੈਕਲੌਗ ਹੈ।
- **ਜਟਿਲਤਾ** — ✅ **ਮੁਕੰਮਲ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ਇੱਕ ESLint ਵਾਕ, ruleId ਮੁਤਾਬਕ ਗਿਣਤੀ ਕਰਦਾ ਹੈ ਤਾਂ ਜੋ cyclomatic+max-lines ਅਤੇ cognitive ਬੇਸਲਾਈਨਾਂ ਸੁਤੰਤਰ ਰਹਿਣ; ਵੱਖਰੇ `check:complexity` / `check:cognitive-complexity` ਸਥਾਨਕ `--update` ਲਈ ਕਾਇਮ ਹਨ।
- **`/api` ਭਰਮ-ਰੋਕਥਾਮ** — ✅ **ਮੁਕੰਮਲ** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api` ਦੀ ਇੱਕ FS ਇਨਵੈਂਟਰੀ, openapi-routes + docs-symbols ਅਜੇ ਵੀ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਰਿਪੋਰਟ ਕਰਦੇ ਹਨ; ਵੱਖਰੇ ਚੈੱਕ ਸਥਾਨਕ ਰਨਾਂ ਲਈ ਕਾਇਮ ਹਨ।

- **CI lint ਉੱਤੇ `typecheck:noimplicit:core`** — ✅ **lint ਜੌਬ ਤੋਂ ਹਟਾਇਆ ਗਿਆ** (ਇਹ ਸਲਾਹਕਾਰੀ `continue-on-error` ਸੀ); ਬਲੌਕਿੰਗ ਟਾਈਪ ਸਤਹ `typecheck:core` + `check:type-coverage` ਹੈ। ਸਥਾਨਕ ਸਕ੍ਰਿਪਟ ਕਾਇਮ ਰੱਖੀ ਗਈ ਹੈ।

ਇਸ ਵਿੱਚ ਦਰਜ ਘਟਨਾ ਇਹ ਹੈ: Orchestration Canvas ਦੇ Phase 3 ਨੇ ਆਪਣੀਆਂ ਗਿਆਰਾਂ ਕੁੰਜੀਆਂ ਦਾ ਉਸ ਵੇਲੇ
ਮੌਜੂਦ 42 locales ਵਿੱਚ ਅਨੁਵਾਦ ਕੀਤਾ। ਕੁਝ ਘੰਟਿਆਂ ਬਾਅਦ EU-language ਬੈਚ (#13044) ਨੇ repo ਨੂੰ 51
locales ਤੱਕ ਪਹੁੰਚਾ ਦਿੱਤਾ, ਅਤੇ ਨੌਂ ਨਵੇਂ ਆਏ locales (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`,
`sr`) ਨੂੰ ਉਹ ਕੁੰਜੀਆਂ ਕਦੇ ਨਹੀਂ ਮਿਲੀਆਂ। `deepMergeFallback` ਕਿਸੇ ਗੈਰਹਾਜ਼ਰ ਕੁੰਜੀ ਦੀ ਥਾਂ ਅੰਗਰੇਜ਼ੀ
