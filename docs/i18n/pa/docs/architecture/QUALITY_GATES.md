ਰੈਚਟ ਬੇਸਲਾਈਨ ਜਾਂ ਪਾਸ/ਫੇਲ ਨੀਤੀ ਵਰਤਦਾ ਹੈ, ਅਤੇ ਕੀ ਇਹ ਬਿਲਡ ਨੂੰ ਰੋਕਦਾ ਹੈ ਜਾਂ ਸਿਰਫ਼ ਸਲਾਹਕਾਰੀ ਹੈ।

ਸੰਖੇਪ ਸਾਰ ਅਤੇ ਅਲਾਊਲਿਸਟ ਨੀਤੀ ਲਈ, `AGENTS.md` ਵਿੱਚ "ਗੁਣਵੱਤਾ ਗੇਟ ਅਤੇ ਰੈਚਟ" ਭਾਗ
ਦੇਖੋ। ਇਸੇ ਸਿਸਟਮ ਦੇ ਆਲੋਚਨਾਤਮਕ ਮੁਲਾਂਕਣ, ਪਰਿਪੱਕਤਾ ਵਰਗੀਕਰਨ ਅਤੇ ਟੂਲ-ਨਿਰਪੱਖ
ਪੁਨਰ-ਨਿਰਮਾਣ ਯੋਜਨਾ ਲਈ,
[ਗੁਣਵੱਤਾ ਗੇਟ ਪਲੇਬੁੱਕ](../ops/QUALITY_GATE_PLAYBOOK.md) ਦੇਖੋ।

## ਗੇਟ ਇਨਵੈਂਟਰੀ (~90 ਸਕ੍ਰਿਪਟਾਂ)

ਸਕ੍ਰਿਪਟਾਂ `scripts/check/` (ਨੀਤੀ ਗੇਟ) ਅਤੇ `scripts/quality/` (ਰੈਚਟ ਇੰਜਣ) ਦੇ ਅਧੀਨ ਮੌਜੂਦ ਹਨ।
CI ਲਈ ਪ੍ਰਮਾਣਿਕ ਸਰੋਤ `.github/workflows/ci.yml` ਹੈ।

### ਰਿਲੀਜ਼ PR ਫਾਸਟ-ਪਾਥ (`quality.yml`)

`.github/workflows/quality.yml`, `release/**` ਨੂੰ ਟਾਰਗੇਟ ਕਰਨ ਵਾਲੀਆਂ PRs 'ਤੇ ਚੱਲਦੀ ਹੈ। ਇਹ ਪਾਥ-ਫਿਲਟਰ ਕੀਤੇ ਤੇਜ਼ ਗੇਟਾਂ ਨਾਲ ਯੋਗਦਾਨਕਰਤਾਵਾਂ ਦੀਆਂ ਬ੍ਰਾਂਚਾਂ ਨੂੰ ਅੱਗੇ ਵਧਦਾ ਰੱਖਦੀ ਹੈ, ਅਤੇ ਕੋਡ ਤਬਦੀਲੀਆਂ ਲਈ ਇੱਕ ਸਲਾਹਕਾਰੀ ਪ੍ਰੋਡਕਸ਼ਨ-ਬਿਲਡ ਸੰਕੇਤ ਵੀ ਦਿੰਦੀ ਹੈ:

#### ਭੁੱਲੇ ਹੋਏ ਸਿਬਲਿੰਗ ਟੈਸਟਾਂ ਦੀ ਰਿਪੋਰਟ

`npm run check:forgotten-sibling-tests`, ਟੈਸਟ-ਇੰਪੈਕਟ ਮੈਪ ਦੇ ਪਿੱਛੇ ਮੌਜੂਦ ਇੰਪੋਰਟ ਰਿਜ਼ਾਲਵਰ ਨੂੰ ਮੁੜ ਵਰਤਦੀ ਹੈ।
ਹਰੇਕ ਤਬਦੀਲ ਕੀਤੇ ਪ੍ਰੋਡਕਸ਼ਨ ਮੋਡੀਊਲ ਲਈ, ਜਦੋਂ ਸੰਭਾਵੀ ਟੈਸਟ ਪੁੱਲ-ਰਿਕਵੈਸਟ ਡਿਫ਼ ਵਿੱਚ ਮੌਜੂਦ ਨਹੀਂ ਹੁੰਦਾ, ਇਹ ਨਿਰਧਾਰਤ
`changed module/symbol -> static consumer -> candidate sibling test` ਚੇਨਾਂ ਦੀ ਰਿਪੋਰਟ ਕਰਦੀ ਹੈ। Markdown ਸੰਖੇਪ ਅਤੇ JSON ਨਤੀਜੇ ਨੂੰ ਕਿਸੇ ਵੀ ਬਲਾਕਿੰਗ ਰੋਲਆਉਟ ਤੋਂ ਪਹਿਲਾਂ ਕੈਲੀਬ੍ਰੇਸ਼ਨ ਲਈ
`forgotten-sibling-tests` ਵਰਕਫ਼ਲੋ ਆਰਟੀਫੈਕਟ ਵਜੋਂ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ।

ਬੈਰਲ ਰੀ-ਐਕਸਪੋਰਟ ਅਤੇ ਡਾਇਨਾਮਿਕ ਇੰਪੋਰਟ ਸਿਰਫ਼ ਰਿਜ਼ੋਲਿਊਸ਼ਨ ਡਾਇਗਨੋਸਟਿਕਸ ਹਨ; ਇਹ ਕਦੇ ਵੀ ਕੋਈ
ਬਲਾਕਿੰਗ ਨਤੀਜਾ ਨਹੀਂ ਬਣਾਉਂਦੇ। ਸਮੀਖਿਆ ਕੀਤੇ ਅਪਵਾਦ
`config/quality/forgotten-sibling-allowlist.json` ਵਿੱਚ ਮੌਜੂਦ ਹਨ। ਹਰੇਕ ਐਂਟਰੀ ਵਿੱਚ ਖਪਤਕਾਰ ਅਤੇ ਸੰਭਾਵੀ
ਟੈਸਟ ਦਾ ਨਾਮ ਹੋਣਾ, ਇੱਕ ਖ਼ਾਸ ਤਰਕ ਦੇਣਾ, ਅਤੇ ਕਿਸੇ GitHub ਇਸ਼ੂ ਜਾਂ ਪੁੱਲ ਰਿਕਵੈਸਟ ਨਾਲ ਲਿੰਕ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ। ਗ਼ਲਤ ਢੰਗ ਨਾਲ ਬਣੀਆਂ ਐਂਟਰੀਆਂ
ਫੇਲ੍ਹ-ਕਲੋਜ਼ਡ ਹੁੰਦੀਆਂ ਹਨ। ਅਪਵਾਦ ਮਿਟਾਏ ਗਏ ਸੰਭਾਵੀ ਟੈਸਟ ਜਾਂ `.skip`/`.todo` ਜੋੜਨ ਵਾਲੇ ਡਿਫ਼ ਨੂੰ ਦਬਾ ਨਹੀਂ ਸਕਦੇ;
ਅਸਰਸ਼ਨ ਨੂੰ ਕਮਜ਼ੋਰ ਕਰਨਾ ਅਤੇ ਹੋਰ ਮਾਸਕਿੰਗ, ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਬਲਾਕ ਕਰਨ ਵਾਲੇ
`check:test-masking` ਗੇਟ ਦੇ ਅਧੀਨ ਰਹਿੰਦੇ ਹਨ।

#### `check-ui-value-drift` — ਪੁਰਾਣੇ-ਅਨੁਵਾਦ ਦਾ ਗੇਟ

ਇਹ ਉਸ ਇੱਕ i18n ਰਿਗ੍ਰੈਸ਼ਨ ਨੂੰ ਫੜਦਾ ਹੈ ਜਿਸਨੂੰ ਹੋਰ ਗੇਟ ਸੰਰਚਨਾਤਮਕ ਤੌਰ 'ਤੇ ਨਹੀਂ ਦੇਖ ਸਕਦੇ: ਕਿਸੇ ਅੰਗਰੇਜ਼ੀ ਮੁੱਲ ਨੂੰ
ਮੁੜ ਲਿਖਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ _ਪਿਛਲੇ_ ਅੰਗਰੇਜ਼ੀ ਮੁੱਲ ਤੋਂ ਬਣੇ ਅਨੁਵਾਦ ਉੱਥੇ ਹੀ ਰਹਿ ਜਾਂਦੇ ਹਨ, ਇਸ ਲਈ
ਗੈਰ-ਅੰਗਰੇਜ਼ੀ ਵਰਤੋਂਕਾਰ ਭਰੋਸੇ ਨਾਲ ਲਿਖੀ ਹੋਈ, ਪਰ ਹੁਣ ਗਲਤ ਕਾਪੀ ਪੜ੍ਹਦੇ ਰਹਿੰਦੇ ਹਨ।

ਇਹ ਅਸਲ ਵਿੱਚ ਰਿਲੀਜ਼ ਹੋਇਆ ਸੀ। ਜਦੋਂ Antigravity ਲੌਗਇਨ ਸਹਾਇਕ ਸ਼ਾਮਲ ਕੀਤਾ ਗਿਆ (#5203), ਤਾਂ `oauthModal.googleOAuthWarning`
ਨੂੰ ਮੁੜ ਲਿਖਿਆ ਗਿਆ; **43 ਵਿੱਚੋਂ 39 ਲੋਕੇਲਾਂ** ਵਿੱਚ ਉਹੀ ਲਿਖਤ ਰਹੀ ਜੋ ਓਪਰੇਟਰਾਂ ਨੂੰ "ਪੂਰਾ URL ਕਾਪੀ ਕਰਕੇ ਹੇਠਾਂ ਪੇਸਟ ਕਰਨ"
ਲਈ ਕਹਿੰਦੀ ਸੀ — ਇੱਕ ਅਜਿਹਾ ਫ਼ਲੋ ਜੋ ਉਸ ਪ੍ਰਦਾਤਾ ਲਈ ਪੂਰਾ ਨਹੀਂ ਹੋ ਸਕਦਾ। #8463 ਤੱਕ ਇਸਦਾ
ਪਤਾ ਨਹੀਂ ਲੱਗਿਆ ਕਿਉਂਕਿ:

- `sync-ui-keys` ਸਿਰਫ਼ ਉਹਨਾਂ ਕੁੰਜੀਆਂ ਨੂੰ ਬੈਕਫ਼ਿਲ ਕਰਦਾ ਹੈ ਜੋ **ਮੌਜੂਦ ਨਹੀਂ** ਹੁੰਦੀਆਂ, **ਪੁਰਾਣੀਆਂ** ਕੁੰਜੀਆਂ ਨੂੰ ਕਦੇ ਨਹੀਂ;
- `check-ui-keys-coverage` ਕੁੰਜੀ ਦੀ _ਮੌਜੂਦਗੀ_ ਗਿਣਦਾ ਹੈ, ਇਸ ਲਈ ਪੁਰਾਣਾ ਅਨੁਵਾਦ ਵੀ ਕਵਰ ਕੀਤਾ ਹੋਇਆ ਮੰਨਿਆ ਜਾਂਦਾ ਹੈ;
- `check-translation-drift` `docs/i18n/<locale>/**.md` ਦਸਤਾਵੇਜ਼ੀ ਮਿਰਰਾਂ ਨੂੰ ਟ੍ਰੈਕ ਕਰਦਾ ਹੈ —
  ਇਹ ਕਦੇ ਵੀ `src/i18n/messages/*.json` ਨਹੀਂ ਪੜ੍ਹਦਾ। 2026-09 ਦੇ ਮੁੜ-ਸਿੰਕ ਤੋਂ ਬਾਅਦ ਜੌਬ `docs-sync-strict` ਵਿੱਚ ਰੋਕੂ:
  ਕਿਸੇ ਮੁੱਖ ਦਸਤਾਵੇਜ਼ ਨੂੰ ਸੰਪਾਦਿਤ ਕਰੋ → `npm run i18n:run -- --files=<doc>` (ਸੈਕਸ਼ਨ-ਪੱਧਰੀ, ਘੱਟ ਖ਼ਰਚੀਲਾ)।

**ਡਿਫ਼-ਸਚੇਤ, ਬੇਸਲਾਈਨ-ਆਧਾਰਿਤ ਨਹੀਂ।** ਇਹ ਮਰਜ ਬੇਸ ਉੱਤੇ ਮੌਜੂਦ `en.json` ਦੀ ਵਰਕਿੰਗ ਟ੍ਰੀ ਨਾਲ
ਤੁਲਨਾ ਕਰਦਾ ਹੈ; ਹਰ ਉਸ ਕੁੰਜੀ ਲਈ ਜਿਸਦਾ ਅੰਗਰੇਜ਼ੀ ਮੁੱਲ ਬਦਲਿਆ ਹੈ, ਜੇ ਕੋਈ ਲੋਕੇਲ ਅਜੇ ਵੀ
ਨਾ-ਬਦਲਿਆ ਅਨੁਵਾਦ ਰੱਖਦਾ ਹੈ, ਤਾਂ ਉਹ ਪੁਰਾਣਾ ਹੈ। ਇਹ ਜਾਣਬੁੱਝ ਕੇ **ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਕਰਜ਼ੇ ਨੂੰ ਸਥਿਰ ਰੱਖਦਾ ਹੈ** — ਇੱਕ ਡਿਫ਼
ਇਹ ਨਹੀਂ ਦੱਸ ਸਕਦਾ ਕਿ ਲੰਬੇ ਸਮੇਂ ਤੋਂ ਮੌਜੂਦ ਅਨੁਵਾਦ ਕਿਸ ਪੁਰਾਣੇ ਅੰਗਰੇਜ਼ੀ ਮੁੱਲ ਤੋਂ ਆਇਆ ਸੀ, ਇਸ ਲਈ ਗੇਟ
ਸਿਰਫ਼ ਉਸੇ ਨੂੰ ਪਰਖਦਾ ਹੈ ਜਿਸਨੂੰ ਮੌਜੂਦਾ ਬਦਲਾਅ ਛੂੰਹਦਾ ਹੈ। ਵਿਕਲਪ (ਪ੍ਰਤੀ-ਕੁੰਜੀ ਹੈਸ਼ ਬੇਸਲਾਈਨ) ਲਈ
ਲਗਭਗ 600 KB ਦੀ ਜਨਰੇਟ ਕੀਤੀ ਫ਼ਾਈਲ ਚਾਹੀਦੀ ਹੋਵੇਗੀ, ਜੋ ਸਭ ਤੋਂ ਵੱਡੀ ਮੌਜੂਦਾ ਬੇਸਲਾਈਨ ਤੋਂ 3× ਵੱਡੀ ਹੈ ਅਤੇ ਹਰ i18n PR ਉੱਤੇ ਬਦਲੇਗੀ।

ਇਸਨੂੰ ਸੰਤੁਸ਼ਟ ਕਰਨ ਦੇ ਦੋ ਤਰੀਕੇ ਹਨ:

1. ਪ੍ਰਭਾਵਿਤ ਅਨੁਵਾਦਾਂ ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ, ਜਾਂ
2. ਉਹਨਾਂ ਨੂੰ `__MISSING__:<new english>` 'ਤੇ ਸੈੱਟ ਕਰੋ — ਫਿਰ ਰਨਟਾਈਮ ਸਹੀ ਕੀਤੀ ਅੰਗਰੇਜ਼ੀ ਪੇਸ਼ ਕਰਦਾ ਹੈ
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ਅਤੇ ਕੁੰਜੀ ਅਨੁਵਾਦ ਲਈ ਕਤਾਰ ਵਿੱਚ ਸ਼ਾਮਲ ਹੋ ਜਾਂਦੀ ਹੈ।

ਜੇ ਸਟ੍ਰਿੰਗ ਦਾ **ਅਰਥ** ਬਦਲਿਆ ਹੈ, ਤਾਂ **ਕੁੰਜੀ ਦਾ ਨਾਮ ਬਦਲਣ** ਨੂੰ ਤਰਜੀਹ ਦਿਓ: ਨਵੀਂ ਕੁੰਜੀ
ਪੁਰਾਣਾ ਅਨੁਵਾਦ ਵਿਰਾਸਤ ਵਿੱਚ ਨਹੀਂ ਲੈ ਸਕਦੀ। #8463 ਵਿੱਚ ਇਹੀ ਪੈਟਰਨ ਵਰਤਿਆ ਗਿਆ ਸੀ।

```bash
npm run i18n:check-value-drift          # ਸਖ਼ਤ (ਜੋ CI ਚਲਾਉਂਦਾ ਹੈ)
npm run i18n:check-value-drift:warn     # ਸਿਰਫ਼ ਰਿਪੋਰਟ
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

ਜਦੋਂ ਬੇਸ ਕੈਟਾਲੌਗ ਪੜ੍ਹਿਆ ਨਹੀਂ ਜਾ ਸਕਦਾ (ਬੇਸ ref ਤੋਂ ਬਿਨਾਂ ਸ਼ੈਲੋ
ਕਲੋਨ), ਤਾਂ `check-openapi-breaking` ਵਾਂਗ `SKIP reason=base-unresolved` ਨਾਲ 0 ਐਗਜ਼ਿਟ ਕਰਦਾ ਹੈ।

## ਰੈਚਟ ਬੇਸਲਾਈਨ (`quality-baseline.json`)

ਰੈਚਟ ਇੰਜਣ (`scripts/quality/check-quality-ratchet.mjs`) `quality-baseline.json` ਨੂੰ ਪੜ੍ਹਦਾ ਹੈ
ਅਤੇ ਇਸਦੀ ਤੁਲਨਾ ਹੁਣੇ ਇਕੱਤਰ ਕੀਤੀ `quality-metrics.json` ਨਾਲ ਕਰਦਾ ਹੈ। ਕੋਈ ਵੀ ਮੈਟ੍ਰਿਕ ਜੋ ਆਪਣੇ
ਐਪਸਿਲਾਨ ਤੋਂ ਵੱਧ ਪਿੱਛੇ ਜਾਂਦਾ ਹੈ, ਬਿਲਡ ਨੂੰ ਅਸਫਲ ਕਰ ਦਿੰਦਾ ਹੈ।

ਵਰਤਮਾਨ ਵਿੱਚ ਟਰੈਕ ਕੀਤੇ ਜਾਂਦੇ ਮੈਟ੍ਰਿਕ:

| ਮੈਟ੍ਰਿਕ               | ਦਿਸ਼ਾ  | ਅਰਥ                                        |
| --------------------- | ------ | ------------------------------------------ |
| `eslintWarnings`      | `down` | ESLint ਚੇਤਾਵਨੀਆਂ ਦੀ ਗਿਣਤੀ ਵਧਣੀ ਨਹੀਂ ਚਾਹੀਦੀ |
| `coverage.statements` | `up`   | ਸਟੇਟਮੈਂਟ ਕਵਰੇਜ ਘਟਣੀ ਨਹੀਂ ਚਾਹੀਦੀ            |
| `coverage.lines`      | `up`   | ਲਾਈਨ ਕਵਰੇਜ ਘਟਣੀ ਨਹੀਂ ਚਾਹੀਦੀ                |
| `coverage.functions`  | `up`   | ਫੰਕਸ਼ਨ ਕਵਰੇਜ ਘਟਣੀ ਨਹੀਂ ਚਾਹੀਦੀ              |
| `coverage.branches`   | `up`   | ਬ੍ਰਾਂਚ ਕਵਰੇਜ ਘਟਣੀ ਨਹੀਂ ਚਾਹੀਦੀ              |

ਕਿਸੇ ਅਸਲ ਸੁਧਾਰ ਤੋਂ ਬਾਅਦ ਬੇਸਲਾਈਨ ਅੱਪਡੇਟ ਕਰਨ ਲਈ:

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

`--update` ਫਲੈਗ ਮੌਜੂਦਾ ਮਾਪੇ ਹੋਏ ਮੁੱਲਾਂ ਨੂੰ `quality-baseline.json` ਵਿੱਚ ਲਿਖਦਾ ਹੈ।
ਇਸ ਫ਼ਾਈਲ ਨੂੰ ਉਸ ਤਬਦੀਲੀ ਦੇ ਨਾਲ ਹੀ ਕਮਿਟ ਕਰੋ ਜਿਸ ਨੇ ਮੈਟ੍ਰਿਕ ਵਿੱਚ ਸੁਧਾਰ ਕੀਤਾ ਹੈ। ਬੇਸਲਾਈਨ
ਅੱਪਡੇਟ ਕੀਤੇ ਬਿਨਾਂ ਕਿਸੇ ਮੈਟ੍ਰਿਕ ਨੂੰ ਸੁਧਾਰਨ ਵਾਲੀ PR ਨੂੰ `--require-tighten` ਪਕੜ ਲਵੇਗਾ
(ਪੜਾਅ 6A.5, ਲਾਗੂਕਰਨ ਬਕਾਇਆ ਹੈ)।

### CodeQL ਰੈਚਟ: ਰਿਫ੍ਰੈਸ਼ ਦੀ ਆਵਿਰਤੀ ਅਤੇ ਮੈਨੁਅਲ ਟ੍ਰਿਗਰ

`check:codeql-ratchet` **ਰਿਪੋਜ਼ਟਰੀ ਦੀ ਸਥਿਤੀ ਪੜ੍ਹਦਾ ਹੈ, ਜੋ ਇੱਕ ਸਮਾਂ-ਸੂਚੀ ਅਨੁਸਾਰ ਰਿਫ੍ਰੈਸ਼ ਹੁੰਦੀ ਹੈ — ਹਰ PR ਲਈ ਨਹੀਂ।**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` ਵੱਲੋਂ ਰਿਪੋਰਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ:
`state: configured`, `schedule: weekly`: ਇਹ GitHub ਦਾ ਡਿਫਾਲਟ-ਸੈੱਟਅੱਪ ਸਕੈਨ ਹੈ, ਨਾ ਕਿ ਹਰ ਪੁਸ਼
ਲਈ ਕੀਤਾ ਜਾਣ ਵਾਲਾ ਵਿਸ਼ਲੇਸ਼ਣ। ਨਤੀਜਾ: ਅਲਰਟ ਠੀਕ ਕਰਨ ਵਾਲੀ PR ਦੇ ਮਰਜ ਹੋਣ ਤੋਂ ਬਾਅਦ, ਰੈਚਟ
ਅਗਲਾ ਨਿਰਧਾਰਤ ਸਕੈਨ ਚੱਲਣ ਤੱਕ ਪੁਰਾਣੀ, ਵੱਧ ਗਿਣਤੀ ਹੀ ਪੜ੍ਹਦਾ ਰਹਿੰਦਾ ਹੈ — ਇਸ ਲਈ ਸਕੈਨ ਦੇ
ਅੱਪਡੇਟ ਹੋਣ ਤੱਕ ਇਹ ਹਰ ਖੁੱਲ੍ਹੀ PR, ਫਿਕਸ ਕਰਨ ਵਾਲੀ PR ਦੀਆਂ ਆਪਣੀਆਂ ਅਗਲੀਆਂ ਤਬਦੀਲੀਆਂ ਸਮੇਤ,
'ਤੇ ਰਿਗ੍ਰੈਸ਼ਨ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ।

**ਮੈਨੁਅਲ ਰਿਫ੍ਰੈਸ਼**: `gh workflow run codeql.yml --ref release/vX.Y.Z` ਵਿਸ਼ਲੇਸ਼ਣ ਨੂੰ ਮੁੜ
ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਕੁਝ ਮਿੰਟਾਂ ਵਿੱਚ ਅਲਰਟ ਦੁਬਾਰਾ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ। ਪਹਿਲਾਂ `.github/workflows/codeql.yml`
ਪੜ੍ਹੋ — ਇਸਦਾ ਸਿਰਲੇਖ ਸਮਝਾਉਂਦਾ ਹੈ ਕਿ ਇਹ ਸਿਰਫ਼ `workflow_dispatch` ਲਈ ਹੈ, **ਕਿਉਂਕਿ ਇਸਦਾ
GitHub ਦੇ "default setup" ਨਾਲ ਟਕਰਾਅ ਹੁੰਦਾ ਹੈ** (`CodeQL analyses from advanced configurations cannot be
processed when the default setup is enabled`)। `push`/`pull_request`/
`schedule` ਟ੍ਰਿਗਰਾਂ ਨੂੰ ਮੁੜ ਬਹਾਲ ਕਰਨ ਲਈ ਪਹਿਲਾਂ **ਮਾਲਕ ਵੱਲੋਂ ਕਾਰਵਾਈ** ਲੋੜੀਂਦੀ ਹੈ: Settings → Code security →
CodeQL: Default → Advanced। ਇਹ ਸਵਿੱਚ ਕੀਤੇ ਬਿਨਾਂ `schedule:` ਟ੍ਰਿਗਰ ਨਾ ਜੋੜੋ — ਇਹ
ਸਿਰਫ਼ ਅਸਫਲ ਰਨ ਹੀ ਪੈਦਾ ਕਰੇਗਾ।

**ਗਿਣਤੀ ਘਟਣ ਤੋਂ ਬਾਅਦ ਬੇਸਲਾਈਨ ਨੂੰ ਕੱਸੋ** — `node scripts/check/check-codeql-ratchet.mjs
--update` ਨਵੀਂ ਮਾਪੀ ਗਿਣਤੀ ਨੂੰ `quality-baseline.json` →
`metrics.codeqlAlerts.value` ਵਿੱਚ ਲਿਖਦਾ ਹੈ, ਤਾਂ ਜੋ ਰੈਚਟ ਚੁੱਪਚਾਪ ਪੁਰਾਣੀ ਉੱਪਰੀ ਸੀਮਾ ਤੱਕ
ਮੁੜ ਰਿਗ੍ਰੈਸ਼ਨ ਦੀ ਆਗਿਆ ਨਾ ਦੇਵੇ। ਕਾਰਜਸ਼ੀਲ ਉਦਾਹਰਨ (2026-09-02/03): PR #12502 ਨੇ 7 ਅਸਲ ਅਲਰਟ
ਠੀਕ ਕੀਤੇ (ਮਾਪੇ ਗਏ ਖੁੱਲ੍ਹੇ ਅਲਰਟ 13 → 6); PR #12530 ਨੇ ਮੇਲ ਕਰਨ ਲਈ ਜਮੀ ਹੋਈ ਬੇਸਲਾਈਨ ਨੂੰ
11 → 6 ਤੱਕ ਕੱਸਿਆ; ਫਿਰ ਬਾਕੀ 6 ਨੂੰ ਹਰ ਅਲਰਟ ਲਈ ਵੱਖਰੇ ਜਾਇਜ਼ੇ ਨਾਲ ਖਾਰਜ ਕਰਕੇ ਖੁੱਲ੍ਹੇ ਅਲਰਟਾਂ
ਦੀ ਗਿਣਤੀ 0 ਕਰ ਦਿੱਤੀ ਗਈ।

**ਖਾਰਜ ਕਰਨਾ ਆਪਰੇਟਰ ਦਾ ਫ਼ੈਸਲਾ ਹੈ (ਸਖ਼ਤ ਨਿਯਮ #14)** — ਖਾਰਜ ਕਰਨ ਵਾਲੀ ਟਿੱਪਣੀ ਵਿੱਚ
ਤਕਨੀਕੀ ਜਾਇਜ਼ਾ ਦਰਜ ਕੀਤੇ ਬਿਨਾਂ ਕਦੇ ਵੀ CodeQL ਅਲਰਟ ਨੂੰ ਖਾਰਜ ਨਾ ਕਰੋ: ਕਿਸੇ ਅੱਪਸਟ੍ਰੀਮ-ਪ੍ਰੋਟੋਕੋਲ
ਲੋੜ ਲਈ `won't fix`, ਕਿਸੇ ਟੈਸਟ ਫਿਕਸਚਰ ਲਈ `used in tests`, ਅਤੇ ਅਜਿਹੇ ਸੈਨਿਟਾਈਜ਼ਰ ਲਈ
`false positive` ਜਿਸਨੂੰ CodeQL ਨਹੀਂ ਦੇਖ ਸਕਦਾ (ਪਿਛਲੀ ਮਿਸਾਲ: `docs/security/ERROR_SANITIZATION.md`)।

### ਸੁਰੱਖਿਆ ਤਸਦੀਕਕਾਰ

ਜੌਬ ਬਿਨਾਂ ਨਿਗਰਾਨੀ ਦੇ ਬੇਸਲਾਈਨਾਂ ਵਿੱਚ ਲਿਖਦੀ ਹੈ, ਇਸ ਲਈ `verify-ratchet-bank.mjs` ਹੀ ਇਸਨੂੰ
ਸਵੀਕਾਰਯੋਗ ਬਣਾਉਂਦਾ ਹੈ। ਇਹ `--update` ਤੋਂ ਬਾਅਦ ਵਾਲੇ ਟ੍ਰੀ ਦੀ `HEAD` ਨਾਲ ਤੁਲਨਾ ਕਰਦਾ ਹੈ ਅਤੇ **ਕੋਈ ਵੀ ਕਮਿਟ
ਮੌਜੂਦ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਜੌਬ ਨੂੰ ਰੋਕ ਦਿੰਦਾ ਹੈ** — ਕੋਈ PR ਨਹੀਂ ਖੋਲ੍ਹਦਾ — ਜਦੋਂ ਤੱਕ ਹਰ ਤਬਦੀਲੀ ਇਨ੍ਹਾਂ ਵਿੱਚੋਂ ਇੱਕ ਨਾ ਹੋਵੇ:

- ਇੱਕ `frozen` / `testFrozen` ਅੰਕੀ ਐਂਟਰੀ **ਘਟਾਈ** ਜਾਂ **ਹਟਾਈ** ਗਈ ਹੋਵੇ
- `complexity-baseline.json` → `count` **ਘਟਾਇਆ** ਗਿਆ ਹੋਵੇ
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` **ਘਟਾਇਆ** ਗਿਆ ਹੋਵੇ

ਹੋਰ ਕੁਝ ਵੀ ਅਸਫਲ ਹੁੰਦਾ ਹੈ: ਕੋਈ ਸੰਖਿਆ ਵਧਾਉਣਾ, ਐਂਟਰੀ ਜੋੜਨਾ, `cap`/`testCap` ਬਦਲਣਾ, ਜਾਂ
ਕਿਸੇ `_rebaseline_*` ਨੋਟ ਨੂੰ ਮਿਟਾਉਣਾ/ਮੁੜ ਲਿਖਣਾ (ਉਹ ਨੋਟ ਇਸ ਗੱਲ ਦਾ ਆਡਿਟ ਟ੍ਰੇਲ ਹਨ ਕਿ ਹਰੇਕ
ਉੱਪਰੀ ਸੀਮਾ ਕਿਉਂ ਮੌਜੂਦ ਹੈ ਅਤੇ ਉਹ ਫ਼ਾਈਲ ਐਂਟਰੀਆਂ ਵਾਲੇ ਉਸੇ `frozen` ਆਬਜੈਕਟ ਦੇ ਅੰਦਰ ਸਟੋਰ ਕੀਤੇ ਜਾਂਦੇ ਹਨ)।
ਜੋ ਬੌਟ ਸੀਮਾ ਵਧਾ ਸਕੇ, ਉਹ ਮੌਜੂਦਾ ਸਥਿਤੀ ਨਾਲੋਂ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਹੋਰ ਮਾੜਾ ਹੋਵੇਗਾ। ਰਿਗ੍ਰੈਸ਼ਨ
ਗਾਰਡ: `tests/unit/verify-ratchet-bank.test.ts`.

ਜੌਬ ਕਦੇ ਵੀ `release/*` ਵੱਲ push ਨਹੀਂ ਕਰਦੀ — ਇੱਕ ਮਨੁੱਖ PR ਨੂੰ ਮਰਜ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ ਕੋਈ ਖਰਾਬ ਮਾਪ
ਬਿਨਾਂ ਸਮੀਖਿਆ ਦੇ ਲਾਗੂ ਨਹੀਂ ਹੋ ਸਕਦਾ।

## ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਨੀਤੀ

ਹਰ ਉਹ ਗੇਟ ਜੋ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਉਲੰਘਣਾਵਾਂ ਕਾਰਨ ਅਸਫਲ ਨਹੀਂ ਹੋ ਸਕਦਾ, ਇੱਕ ਸਥਿਰ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਵਰਤਦਾ ਹੈ

4. ਜੇ ਇਸਦੀ ਕੋਈ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਹੈ, ਤਾਂ `scripts/check/lib/allowlist.mjs` ਤੋਂ
   `reportStaleEntries()` ਲਾਗੂ ਕਰੋ, ਤਾਂ ਜੋ ਪੁਰਾਣੀਆਂ ਐਂਟਰੀਆਂ ਆਪਣੇ ਆਪ ਪਛਾਣੀਆਂ ਜਾਣ।
5. ਗੇਟ ਦੀ ਪਛਾਣ ਤਰਕ ਨੂੰ ਕਵਰ ਕਰਨ ਵਾਲਾ ਇੱਕ ਟੈਸਟ `tests/unit/build/` ਵਿੱਚ ਲਿਖੋ।
6. ਇਸ ਦਸਤਾਵੇਜ਼ ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ (ਸੰਬੰਧਿਤ ਜੌਬ ਸਾਰਣੀ ਵਿੱਚ ਇੱਕ ਕਤਾਰ ਸ਼ਾਮਲ ਕਰੋ)।

## ਏਜੰਟ ਟੂਲਿੰਗ: LSP-in-the-loop (ਚੋਣਵਾਂ)

ਡਾਇਗਨੋਸਟਿਕਸ ਦਾ ਨਿਰਾਕਰਨ ਕਰਨ — `typecheck:core` ਦਾ ਇੱਕ ਕੰਪਾਇਲ-ਕਰਨ-ਤੋਂ-ਪਹਿਲਾਂ-ਦਾਅਵਾ ਸਾਥੀ,
ਜੋ "ਘੜੇ ਹੋਏ ਚਿੰਨ੍ਹ" ਵਾਲੀਆਂ ਗਲਤੀਆਂ ਨੂੰ ਸਰੋਤ ਉੱਤੇ ਹੀ ਘਟਾਉਂਦਾ ਹੈ। ਇਸਨੂੰ ਜਾਣਬੁੱਝ ਕੇ
ਆਪਣੇ ਆਪ ਲੋਡ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ (ਤੁਸੀਂ MCP↔LSP ਬ੍ਰਿਜ ਚੁਣਦੇ ਅਤੇ ਤਸਦੀਕ ਕਰਦੇ ਹੋ); ਇੱਕ ਖ਼ਰਾਬ ਐਂਟਰੀ ਸਿਰਫ਼
ਕਨੈਕਸ਼ਨ ਗਲਤੀ ਲੌਗ ਕਰਦੀ ਹੈ ਅਤੇ ਕਦੇ ਵੀ ਸੈਸ਼ਨਾਂ ਨੂੰ ਭੰਗ ਨਹੀਂ ਕਰਦੀ।

### ਮਰਜ / ਡੀਡੁਪਲੀਕੇਸ਼ਨ (ਮਕੈਨੀਕਲ, ਘੱਟ ਜੋਖਮ)

ਹਰੇਕ ਉਮੀਦਵਾਰ ਦੀ 2026-06-17 ਨੂੰ ਲਾਈਵ ਗੇਟ ਸਥਿਤੀ ਦੇ ਮੁਕਾਬਲੇ ਪੁਸ਼ਟੀ ਕੀਤੀ ਗਈ ਸੀ (ਭਰੋਸਾ ਕਰੋ, ਪਰ ਤਸਦੀਕ ਵੀ ਕਰੋ);
ਕਈ "ਸਪਸ਼ਟ" ਮਰਜਾਂ ਦੇ ਪਿੱਛੇ ਅਸਲ ਵਿੱਚ ਕਰਜ਼ ਲੁਕਿਆ ਹੋਇਆ ਸੀ ਅਤੇ ਉਹ **ਸਿੱਧੇ ਬਦਲ ਵਜੋਂ ਸਾਫ਼ ਨਹੀਂ** ਹਨ।

- **`check:docs-sync` ਦੋ ਵਾਰ ਚੱਲਦਾ ਹੈ** — `lint` ਜੌਬ ਵਿੱਚ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਅਤੇ ਦੁਬਾਰਾ `check:docs-all` (`docs-sync-strict`) ਅਤੇ husky pre-commit ਹੁੱਕ ਦੇ ਅੰਦਰ। ✅ **ਮੁਕੰਮਲ** — ਵੱਖਰਾ `lint` ਸੱਦਾ ਹਟਾ ਦਿੱਤਾ ਗਿਆ।
- **CVE ਸਕੈਨਿੰਗ** — ❌ **ਸਾਫ਼ ਮਰਜ ਨਹੀਂ ਹੈ।** `audit:deps` ਕਿਸੇ ਵੀ high/critical CVE ਉੱਤੇ ਪੱਕੇ ਤੌਰ 'ਤੇ ਫੇਲ੍ਹ ਹੁੰਦਾ ਹੈ; `check:vuln-ratchet` (osv) ਸਿਰਫ਼ ਬੇਸਲਾਈਨ ਦੇ ਮੁਕਾਬਲੇ ਕਿਸੇ _ਰਿਗ੍ਰੈਸ਼ਨ_ ਉੱਤੇ ਫੇਲ੍ਹ ਹੁੰਦਾ ਹੈ (ਇਸ ਵੇਲੇ 1 MODERATE)। ਅਰਥ-ਵਿਹਾਰ ਵੱਖਰੇ ਹਨ — `audit:deps` ਨੂੰ ਹਟਾਉਣ ਨਾਲ ਪੂਰਨ high/critical ਗੇਟ ਗੁਆਚ ਜਾਵੇਗਾ। ਦੋਵੇਂ ਰੱਖੋ।
- **ਸਾਈਕਲ ਪਛਾਣ** — ❌ **ਸਾਫ਼ ਮਰਜ ਨਹੀਂ ਹੈ।** `check:circular-deps` (dpdm) **91 ਸਾਈਕਲਾਂ** ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ (ਇਸੇ ਲਈ ਇਹ ਸਲਾਹਕਾਰੀ ਹੈ); ਪਹਿਲਾਂ ਉਨ੍ਹਾਂ ਨੂੰ ਹੱਲ ਕੀਤੇ ਬਿਨਾਂ ਇਸਨੂੰ ਬਲੌਕਿੰਗ ਨਹੀਂ ਬਣਾਇਆ ਜਾ ਸਕਦਾ, ਅਤੇ ਇਸਦਾ ਦਾਇਰਾ ਹਰੇ, ਚੁਣੇ ਹੋਏ `check:cycles` ਨਾਲੋਂ ਵੱਡਾ ਹੈ। `check:cycles` ਨੂੰ ਬਲੌਕਿੰਗ ਰੱਖੋ; 91 dpdm ਸਾਈਕਲਾਂ ਨੂੰ ਹੱਲ ਕਰਨਾ ਆਪਣਾ ਵੱਖਰਾ ਬੈਕਲੌਗ ਹੈ।
- **ਜਟਿਲਤਾ** — ✅ **ਮੁਕੰਮਲ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ਇੱਕ ESLint ਵਾਕ, ruleId ਮੁਤਾਬਕ ਗਿਣਤੀ ਕਰਦਾ ਹੈ ਤਾਂ ਜੋ cyclomatic+max-lines ਅਤੇ cognitive ਬੇਸਲਾਈਨਾਂ ਸੁਤੰਤਰ ਰਹਿਣ; ਵੱਖਰੇ `check:complexity` / `check:cognitive-complexity` ਸਥਾਨਕ `--update` ਲਈ ਕਾਇਮ ਹਨ।
- **`/api` ਭਰਮ-ਰੋਕਥਾਮ** — ✅ **ਮੁਕੰਮਲ** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api` ਦੀ ਇੱਕ FS ਇਨਵੈਂਟਰੀ, openapi-routes + docs-symbols ਅਜੇ ਵੀ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਰਿਪੋਰਟ ਕਰਦੇ ਹਨ; ਵੱਖਰੇ ਚੈੱਕ ਸਥਾਨਕ ਰਨਾਂ ਲਈ ਕਾਇਮ ਹਨ।
- **`check:node-runtime` 11 ਜੌਬਾਂ ਵਿੱਚ ਚੱਲਦਾ ਹੈ** — ⚠️ **ਘੱਟ ROI।** ਹਰੇਕ ਇੱਕ ਵੱਖਰਾ ਰਨਰ ਹੈ ਅਤੇ ਚੈੱਕ <1s ਹੈ; ਕੁੱਲ ਬਚਤ ~10s ਹੈ, ਜਿਸਦੇ ਮੁਕਾਬਲੇ ਹਰ ਜੌਬ ਲਈ ਇੱਕ ਸਸਤਾ ਗਾਰਡ ਗੁਆਉਣਾ ਪਵੇਗਾ। ਤਬਦੀਲੀ ਦੀ ਝੰਝਟ ਦੇ ਯੋਗ ਨਹੀਂ।
- **CI lint ਉੱਤੇ `typecheck:noimplicit:core`** — ✅ **lint ਜੌਬ ਤੋਂ ਹਟਾਇਆ ਗਿਆ** (ਇਹ ਸਲਾਹਕਾਰੀ `continue-on-error` ਸੀ); ਬਲੌਕਿੰਗ ਟਾਈਪ ਸਤਹ `typecheck:core` + `check:type-coverage` ਹੈ। ਸਥਾਨਕ ਸਕ੍ਰਿਪਟ ਕਾਇਮ ਰੱਖੀ ਗਈ ਹੈ।

### ਫਲਿੱਪ / ਫ਼ੈਸਲਾ ਕਰੋ (ਆਪਰੇਟਰ ਨੀਤੀ)

- `check:openapi-security-tiers` (ਸਲਾਹਕਾਰੀ) — ❌ **ਸਾਫ਼ ਤੌਰ 'ਤੇ ਫਲਿੱਪ ਕਰਨਯੋਗ ਨਹੀਂ।** ਇਹ 0 ਨਾਲ ਬੰਦ ਹੁੰਦਾ ਹੈ, ਪਰ ਚੇਤਾਵਨੀ ਦਿੰਦਾ ਹੈ ਕਿ `LOCAL_ONLY_API_PREFIXES` ਹੇਠ ਕਈ `traffic-inspector` ਰੂਟਾਂ ਵਿੱਚ `x-loopback-only: true` ਐਨੋਟੇਸ਼ਨ ਮੌਜੂਦ ਨਹੀਂ ਹੈ। ਇਸਨੂੰ ਲਾਗੂ ਕਰਨ ਲਈ ਪਹਿਲਾਂ ਉਹ ਐਨੋਟੇਸ਼ਨ `openapi.yaml` ਵਿੱਚ ਸ਼ਾਮਲ ਕਰਨੇ ਲਾਜ਼ਮੀ ਹਨ।
- `typecheck:noimplicit:core` (ਸਲਾਹਕਾਰੀ) — ਬਲੌਕਿੰਗ `check:type-coverage` ਰੈਚਟ ਵੱਲੋਂ ਕਾਫ਼ੀ ਹੱਦ ਤੱਕ ਸਮੇਟਿਆ ਗਿਆ ਹੈ। ਇਸਨੂੰ ਰੈਚਟ ਵਿੱਚ ਫਲਿੱਪ ਕਰੋ ਜਾਂ ਫ਼ਾਲਤੂ ਦੂਜਾ `tsc` ਪਾਸ ਹਟਾਓ।
- `test:vitest:ui` (ਹੁਣ **ਬਲੌਕਿੰਗ**) — ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਅਸਫਲਤਾਵਾਂ ਨੂੰ `vitest.config.ts` ਵਿੱਚ `// #8618` ਟ੍ਰੈਕਿੰਗ ਟਿੱਪਣੀਆਂ ਨਾਲ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਬਾਹਰ ਰੱਖਿਆ ਗਿਆ ਹੈ; ਨਵੀਆਂ ਅਸਫਲਤਾਵਾਂ ਜੌਬ ਨੂੰ ਫੇਲ੍ਹ ਕਰਦੀਆਂ ਹਨ।
- `check:secrets` (gitleaks, 3 ਦਸਤਾਵੇਜ਼ਬੱਧ ਗਲਤ-ਸਕਾਰਾਤਮਕਾਂ ਉੱਤੇ ਜਮਾਇਆ ਹੋਇਆ ਬਲੌਕਿੰਗ ਰੈਚਟ) — 0 ਤੱਕ ਪਹੁੰਚਣ ਲਈ ਉਨ੍ਹਾਂ 3 ਨੂੰ allowlist ਕਰੋ, ਜਾਂ ਇਸਨੂੰ ਸਲਾਹਕਾਰੀ ਦਰਜੇ ਤੱਕ ਘਟਾਓ। GitHub ਦੀ ਮੂਲ secret-scanning + `check:public-creds` ਨਾਲ ਓਵਰਲੈਪ ਕਰਦਾ ਹੈ।
- `check:pr-evidence` (ਬਲੌਕਿੰਗ, PR-body ਗੱਦ ਨੂੰ greps ਕਰਦਾ ਹੈ) — ਗਲਤ-ਸਕਾਰਾਤਮਕ ਦਾ ਉੱਚ ਜੋਖਮ; ਹਟਾਉਣ ਨਾਲ Hard Rule #18 ਦੀ ਲਾਗੂਅਤ ਕਮਜ਼ੋਰ ਹੁੰਦੀ ਹੈ, ਇਸ ਲਈ ਇਹ ਸੱਚਮੁੱਚ ਇੱਕ ਨੀਤੀਗਤ ਫ਼ੈਸਲਾ ਹੈ।
- `semgrep` (ਵੱਖਰਾ ਸਲਾਹਕਾਰੀ) — OWASP ਪਰਿਵਾਰਾਂ ਲਈ CodeQL ਨਾਲ ਓਵਰਲੈਪ ਕਰਦਾ ਹੈ; ਇਸਦੀ ਬੇਸਲਾਈਨ ਨੂੰ ਕਿਸੇ ਰੈਚਟ ਨਾਲ ਜੋੜੋ ਜਾਂ ਹਟਾਓ।

#### `check-key-completeness` — ਕੁੰਜੀ-ਸੈੱਟ ਸਮਾਨਤਾ ਗੇਟ

`scripts/i18n/check-key-completeness.mjs` (`npm run i18n:check-keys`, ਜੌਬ `i18n-ui-coverage`)।
ਹਰੇਕ `src/i18n/messages/<locale>.json` ਦੇ ਲੀਫ਼ ਕੁੰਜੀ-ਸੈੱਟ ਦੀ `en.json` ਨਾਲ ਤੁਲਨਾ ਕਰਦਾ ਹੈ ਅਤੇ
ਕਿਸੇ ਵੀ ਗੈਰਹਾਜ਼ਰ ਜਾਂ ਵਾਧੂ ਲੀਫ਼ ਉੱਤੇ ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ, ਭਾਵੇਂ ਕੁੰਜੀ ਕਦੋਂ ਵੀ ਜੋੜੀ ਗਈ ਹੋਵੇ। `__MISSING__:`
ਪਲੇਸਹੋਲਡਰ ਮੌਜੂਦ ਮੰਨੇ ਜਾਂਦੇ ਹਨ (ਉਨ੍ਹਾਂ ਦੀ ਸਮੱਗਰੀ ਰੇਸ਼ੋ ਗੇਟ ਦਾ ਮਾਮਲਾ ਹੈ)। ਇਹ ਦੋ diff-ਆਧਾਰਿਤ/ਪ੍ਰਤੀਸ਼ਤ
ਗੇਟਾਂ ਦਾ ਪੂਰਨ ਪੂਰਕ ਹੈ: `check-ui-keys-coverage` ਹਰ locale ਲਈ 80 % ਦੀ ਘੱਟੋ-ਘੱਟ ਹੱਦ ਲਾਗੂ ਕਰਦਾ ਹੈ
(~13,000 ਵਿੱਚੋਂ 43 ਗੈਰਹਾਜ਼ਰ ਕੁੰਜੀਆਂ ਫਿਰ ਵੀ 99.7 % ਦਿਖਾਉਂਦੀਆਂ ਹਨ) ਅਤੇ `check-new-key-coverage`
ਕੇਵਲ ਉਨ੍ਹਾਂ ਕੁੰਜੀਆਂ ਦਾ ਮੁਲਾਂਕਣ ਕਰਦਾ ਹੈ ਜੋ ਕੋਈ PR `en.json` ਵਿੱਚ ਜੋੜਦਾ ਹੈ। ਇੱਕ locale ਬੈਚ ਉਸ ਦਿਨ ਦੇ
`en.json` ਤੋਂ ਬਣਾਇਆ ਜਾਂਦਾ ਹੈ ਜਿਸ ਦਿਨ ਉਸਦੀ branch ਕੱਟੀ ਜਾਂਦੀ ਹੈ ਅਤੇ ਉਹ ਕਈ ਦਿਨਾਂ ਤੱਕ ਅਨੁਵਾਦ ਕਰਦਾ
ਰਹਿੰਦਾ ਹੈ, ਜਦਕਿ base ਵਿੱਚ ਨਵੀਆਂ ਕੁੰਜੀਆਂ ਜੁੜਦੀਆਂ ਰਹਿੰਦੀਆਂ ਹਨ; ਬੈਚ PR ਖੁਦ ਕੋਈ ਕੁੰਜੀ ਨਹੀਂ ਜੋੜਦਾ,
ਇਸ ਲਈ ਜਦੋਂ ਬੈਚ 1 (#13044) ਨੌਂ locales ਵਿੱਚ 43 ਕੁੰਜੀਆਂ ਘੱਟ ਹੋਣ ਦੇ ਬਾਵਜੂਦ merge ਹੋਇਆ ਅਤੇ ਬੈਚ 2

`node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers` ਨਾਲ ਠੀਕ ਕਰੋ; ਇੱਕ `extra`

#### `check-new-key-coverage` — ਨਵੀਂ-ਕੁੰਜੀ i18n ਗੇਟ

`check-ui-value-drift` ਦਾ ਸੰਬੰਧਿਤ ਗੇਟ। ਉਹ ਉਸ ਅੰਗਰੇਜ਼ੀ ਮੁੱਲ ਨੂੰ ਫੜਦਾ ਹੈ ਜਿਸਨੂੰ **ਮੁੜ ਲਿਖਿਆ**
ਗਿਆ ਹੋਵੇ ਜਦਕਿ ਉਸਦੇ ਅਨੁਵਾਦ ਪਿੱਛੇ ਰਹਿ ਗਏ ਹੋਣ; ਇਹ ਉਸ ਅੰਗਰੇਜ਼ੀ ਕੁੰਜੀ ਨੂੰ ਫੜਦਾ ਹੈ ਜਿਸਨੂੰ **ਜੋੜਿਆ**
ਗਿਆ ਹੋਵੇ ਜਦਕਿ ਕੁਝ locales ਨੂੰ ਉਹ ਕਦੇ ਮਿਲੀ ਹੀ ਨਾ ਹੋਵੇ।

`check-ui-keys-coverage` ਇਸ ਸ਼੍ਰੇਣੀ ਨੂੰ ਨਹੀਂ ਦੇਖ ਸਕਦਾ: ਇਹ ਹਰ locale ਲਈ ਪ੍ਰਤੀਸ਼ਤ ਦੀ ਘੱਟੋ-ਘੱਟ ਹੱਦ
ਲਾਗੂ ਕਰਦਾ ਹੈ, ਅਤੇ ~13,000 ਲੀਫ਼ਾਂ ਵਿੱਚੋਂ ਗਿਆਰਾਂ ਗੈਰਹਾਜ਼ਰ ਕੁੰਜੀਆਂ coverage ਨੂੰ 99.9% ਉੱਤੇ ਹੀ
ਰੱਖਦੀਆਂ ਹਨ। ਹਰ ਭਾਸ਼ਾ ਲਈ ਇੱਕ ਪ੍ਰਤੀਸ਼ਤ ਇਹ ਗੱਲ ਪ੍ਰਗਟ ਨਹੀਂ ਕਰ ਸਕਦਾ ਕਿ "ਇਹ ਫੀਚਰ ਬਿਨਾਂ ਅਨੁਵਾਦ ਦੇ

ਇਸ ਵਿੱਚ ਦਰਜ ਘਟਨਾ ਇਹ ਹੈ: Orchestration Canvas ਦੇ Phase 3 ਨੇ ਆਪਣੀਆਂ ਗਿਆਰਾਂ ਕੁੰਜੀਆਂ ਦਾ ਉਸ ਵੇਲੇ
ਮੌਜੂਦ 42 locales ਵਿੱਚ ਅਨੁਵਾਦ ਕੀਤਾ। ਕੁਝ ਘੰਟਿਆਂ ਬਾਅਦ EU-language ਬੈਚ (#13044) ਨੇ repo ਨੂੰ 51
