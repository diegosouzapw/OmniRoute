## ਸੰਖੇਪ ਜਾਣਕਾਰੀ

ਕੋਟਾ ਸਾਂਝਾਕਰਨ ਇੰਜਣ ਕਿਸੇ ਪ੍ਰਦਾਤਾ ਦੇ ਸਮਾਂ-ਅਧਾਰਿਤ ਕੋਟੇ (ਜਿਵੇਂ Codex ਦੀ
5-ਘੰਟਿਆਂ ਦੀ ਵਿੰਡੋ, Kimi ਦੀਆਂ 1500 ਬੇਨਤੀਆਂ/ਘੰਟਾ) ਨੂੰ ਇੱਕੋ ਕਨੈਕਸ਼ਨ ਸਾਂਝਾ ਕਰਨ
ਵਾਲੀਆਂ ਕਈ API ਕੁੰਜੀਆਂ ਵਿਚਕਾਰ ਨਿਰਪੱਖ ਢੰਗ ਨਾਲ ਵੰਡਦਾ ਹੈ।

**ਇਹ ਜਿਸ ਸਮੱਸਿਆ ਨੂੰ ਹੱਲ ਕਰਦਾ ਹੈ:** OmniRoute ਇੱਕੋ ਅੱਪਸਟ੍ਰੀਮ ਪ੍ਰਦਾਤਾ ਖਾਤੇ ਲਈ
ਕਈ API ਕੁੰਜੀਆਂ ਨੂੰ ਪ੍ਰੌਕਸੀ ਕਰਦਾ ਹੈ। ਸਾਂਝਾਕਰਨ ਤਰਕ ਤੋਂ ਬਿਨਾਂ, ਕੁੰਜੀ A ਵੱਲੋਂ
ਅਚਾਨਕ ਆਈਆਂ ਬੇਨਤੀਆਂ ਉਸ ਘੰਟੇ ਲਈ ਪ੍ਰਦਾਤਾ ਕੋਟਾ ਖ਼ਤਮ ਕਰ ਸਕਦੀਆਂ ਹਨ, ਜਿਸ ਨਾਲ ਵਿੰਡੋ
ਰੀਸੈੱਟ ਹੋਣ ਤੱਕ ਕੁੰਜੀਆਂ B ਅਤੇ C ਬਲੌਕ ਰਹਿੰਦੀਆਂ ਹਨ। ਇੰਜਣ ਇਸਨੂੰ ਹੇਠਾਂ ਦਿੱਤੇ ਢੰਗ ਨਾਲ ਰੋਕਦਾ ਹੈ:

1. ਹਰ ਕੁੰਜੀ ਦੀ ਹਰੇਕ ਮਾਪ ਲਈ ਰੋਲਿੰਗ ਖਪਤ (%, ਬੇਨਤੀਆਂ, ਟੋਕਨ, $) ਨੂੰ ਟਰੈਕ ਕਰਨਾ।
2. ਕੰਮ-ਸੰਭਾਲੂ ਨਿਰਪੱਖ-ਹਿੱਸਾ ਐਲਗੋਰਿਦਮ ਲਾਗੂ ਕਰਨਾ: ਜਦੋਂ ਤੱਕ ਗਲੋਬਲ ਪੂਲ ਸੰਤ੍ਰਿਪਤ
   ਨਹੀਂ ਹੁੰਦਾ, ਕੋਈ ਕੁੰਜੀ ਵਿਹਲੇ ਹਿੱਸਿਆਂ ਵਿੱਚੋਂ ਉਧਾਰ ਲੈ ਸਕਦੀ ਹੈ।
3. ਬੇਨਤੀ ਦੇ ਅੱਪਸਟ੍ਰੀਮ ਐਗਜ਼ੀਕਿਊਟਰ ਤੱਕ ਪਹੁੰਚਣ ਤੋਂ ਪਹਿਲਾਂ ਹੌਟ ਪਾਥ
   (`chatCore.ts`) ਵਿੱਚ ਨਤੀਜੇ ਨੂੰ ਲਾਗੂ ਕਰਨਾ।

## ਐਲਗੋਰਿਦਮ: ਕੰਮ-ਸੰਭਾਲੂ ਨਿਰਪੱਖ-ਹਿੱਸਾ

`src/lib/quota/fairShare.ts` ਵਿੱਚ ਲਾਗੂ ਕੀਤਾ ਗਿਆ ਹੈ।

### ਮੋਡ

| ਸ਼ਰਤ                                       | ਮੋਡ      | ਵਿਹਾਰ                                                                 |
| ------------------------------------------ | -------- | --------------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **ਉਦਾਰ** | ਕੁੰਜੀ ਗਲੋਬਲ ਸੀਮਾ ਵਿੱਚੋਂ ਕੁੱਲ ਖਪਤ ਘਟਾ ਕੇ ਬਚੀ ਮਾਤਰਾ ਤੱਕ ਉਧਾਰ ਲੈ ਸਕਦੀ ਹੈ |
| `globalUsedPercent >= saturationThreshold` | **ਸਖ਼ਤ** | ਵਿਅਕਤੀਗਤ ਨਿਰਪੱਖ ਹਿੱਸੇ ਨੂੰ ਸਖ਼ਤੀ ਨਾਲ ਲਾਗੂ ਕਰੋ                          |

ਡਿਫੌਲਟ `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`)।

### ਪ੍ਰਤੀ-ਮਾਪ ਫ਼ੈਸਲਾ

ਪੂਲ ਵਿੱਚ ਹਰੇਕ ਸਰਗਰਮ ਮਾਪ ਲਈ, ਇੰਜਣ ਹੇਠਾਂ ਦਿੱਤੀ ਗਣਨਾ ਕਰਦਾ ਹੈ:

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

ਫਿਰ:

- **`policy = hard`**: ਜੇ `consumed > fairShareAllowed` ਹੈ ਅਤੇ ਮੋਡ ਸਖ਼ਤ ਹੈ → **ਬਲੌਕ ਕਰੋ**।
- **`policy = soft`**: ਜੇ `consumed > fairShareAllowed` ਹੈ ਅਤੇ ਮੋਡ ਸਖ਼ਤ ਹੈ → **ਜੁਰਮਾਨਾ ਲਗਾਓ** (ਕੌਂਬੋ ਵਿੱਚ ਤਰਜੀਹ ਘਟਾਓ; ਕਦੇ ਵੀ ਪੂਰੀ ਤਰ੍ਹਾਂ ਬਲੌਕ ਨਾ ਕਰੋ)।
- **`policy = burst`**: ਨਿਰਪੱਖ ਹਿੱਸੇ ਦੀ ਪਰਵਾਹ ਕੀਤੇ ਬਿਨਾਂ, ਜਦੋਂ ਤੱਕ ਗਲੋਬਲ ਗੁੰਜਾਇਸ਼ ਮੌਜੂਦ ਹੈ, ਆਗਿਆ ਦਿਓ।

### ਪੂਰਨ ਸੀਮਾ

ਕਿਸੇ ਵੰਡ ਉੱਤੇ `capValue` + `capUnit`, ਮੋਡ ਜਾਂ ਨੀਤੀ ਤੋਂ ਸੁਤੰਤਰ ਇੱਕ ਸਖ਼ਤ ਉੱਪਰੀ ਸੀਮਾ ਹੈ।
ਜਿਸ ਵੀ ਮਾਪ ਵਿੱਚ `consumed >= capValue` ਹੋਵੇ, ਉਹ ਹਮੇਸ਼ਾ ਬੇਨਤੀ ਨੂੰ **ਬਲੌਕ ਕਰਦਾ ਹੈ**।

### ਬਹੁ-ਮਾਪੀ ਜਾਂਚ

ਜੇ ਪੂਲ ਵਿੱਚ **ਕੋਈ ਵੀ** ਮਾਪ ਬੇਨਤੀ ਨੂੰ ਬਲੌਕ ਕਰਦਾ ਹੋਵੇ, ਤਾਂ ਬੇਨਤੀ ਬਲੌਕ ਕਰ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ।
ਮਾਪ ਇੱਕ-ਦੂਜੇ ਤੋਂ ਸੁਤੰਤਰ ਹਨ — 5h% ਦੀ ਸਮਾਪਤੀ weekly% ਮਾਪ ਨੂੰ ਪ੍ਰਭਾਵਿਤ ਨਹੀਂ ਕਰਦੀ।

### ਉਧਾਰ ਲੈਣਾ

ਉਦਾਰ ਮੋਡ ਵਿੱਚ, ਉਹ ਕੁੰਜੀ ਜਿਸਦੀ ਵੰਡ ਪੂਰੀ ਤਰ੍ਹਾਂ ਖਪਤ ਨਹੀਂ ਹੋਈ, ਹੋਰ ਕੁੰਜੀਆਂ ਦੇ
ਅਣਵਰਤੇ ਹਿੱਸਿਆਂ ਵਿੱਚੋਂ ਵਾਧੂ ਮਾਤਰਾ ਵਰਤ ਸਕਦੀ ਹੈ। ਫ਼ਾਰਮੂਲਾ ਇਹ ਹੈ:

```
maxAllowed = globalLimit - consumedByOtherKeys
```

ਜਿੱਥੇ `consumedByOtherKeys = consumedTotal - consumedByThisKey` ਹੈ। ਗਲੋਬਲ ਉੱਪਰੀ ਸੀਮਾ
(ਉਸ ਮਾਪ ਲਈ ਪੂਲ ਦੀ `limit`) ਹਮੇਸ਼ਾ ਸਖ਼ਤ ਸੀਮਾ ਰਹਿੰਦੀ ਹੈ।

## ਸਲਾਈਡਿੰਗ ਵਿੰਡੋ ਕਾਊਂਟਰ

`src/lib/quota/sqliteQuotaStore.ts` ਅਤੇ `redisQuotaStore.ts` ਵਿੱਚ ਲਾਗੂ ਕੀਤਾ ਗਿਆ ਹੈ।

ਹਰੇਕ `(apiKeyId, dimensionKey)` ਲਈ ਦੋ ਬੱਕਟ:

- `curr`: ਮੌਜੂਦਾ ਬੱਕਟ (`floor(nowMs / windowMs)`)
- `prev`: ਪਿਛਲਾ ਬੱਕਟ (`curr - 1`)

ਪ੍ਰਭਾਵਸ਼ਾਲੀ ਰੋਲਿੰਗ ਮੁੱਲ:

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**ਸ਼ੁੱਧਤਾ**: ਲਗਭਗ 99% ਸਹੀ। ਬੱਕਟਾਂ ਦੀ ਹੱਦ ਉੱਤੇ ਗਲਤੀ ਵਿੰਡੋ ਦੇ ਆਕਾਰ ਦੇ ਵੱਧ ਤੋਂ ਵੱਧ
1% ਤੱਕ ਹੁੰਦੀ ਹੈ (ਇਹ 2-ਬੱਕਟ ਅਨੁਮਾਨ ਵਿੱਚ ਅੰਦਰੂਨੀ ਤੌਰ 'ਤੇ ਮੌਜੂਦ ਹੈ)।

### ਸਮਕਾਲੀਤਾ

SQLite ਡਰਾਈਵਰ: ਹਰੇਕ `(apiKeyId | dimensionKey)` ਕੁੰਜੀ ਲਈ ਇਨ-ਮੈਮੋਰੀ ਮਿਊਟੈਕਸ
ਰੀਡ-ਮੋਡੀਫਾਈ-ਰਾਈਟ ਰੇਸ ਨੂੰ ਰੋਕਦਾ ਹੈ। ਪੈਟਰਨ `src/sse/services/auth.ts` ਦੇ
ਐਂਟੀ-ਥੰਡਰਿੰਗ-ਹਰਡ ਤਰੀਕੇ ਦੀ ਪਾਲਣਾ ਕਰਦਾ ਹੈ।

Redis ਡਰਾਈਵਰ: ਐਟਾਮਿਕ ਵਾਧੇ ਲਈ Lua EVAL ਸਕ੍ਰਿਪਟ — ਇੱਕੋ Redis ਕਮਾਂਡ ਵਜੋਂ ਚੱਲਦੀ ਹੈ।

## ਡਰਾਈਵਰ

### SQLite (ਡਿਫਾਲਟ, 0-ਇੰਸਟਾਲ)

- ਟੇਬਲ: `quota_consumption` (ਮਾਈਗ੍ਰੇਸ਼ਨ `073_quota_pools.sql` / `074_quota_consumption.sql` ਵੇਖੋ)।
- ਸਿੰਗਲ-ਇੰਸਟੈਂਸ ਡਿਪਲੌਇਮੈਂਟਾਂ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ।
- ਸਾਰੀ ਪਰਸਿਸਟੈਂਸ ਮੌਜੂਦਾ OmniRoute SQLite DB (`DATA_DIR/storage.sqlite`) ਵਿੱਚ ਹੈ।

### Redis (ਵਿਕਲਪਿਕ, ਮਲਟੀ-ਇੰਸਟੈਂਸ)

- `ioredis` npm ਪੈਕੇਜ ਦੀ ਲੋੜ ਹੈ।
- ਕਾਊਂਟਰ Redis ਵਿੱਚ ਸਟੋਰ ਕੀਤੇ ਜਾਂਦੇ ਹਨ; ਮੈਟਾਡਾਟਾ (ਪੂਲ/ਅਲੋਕੇਸ਼ਨ) ਹਾਲੇ ਵੀ SQLite ਵਿੱਚ ਰਹਿੰਦਾ ਹੈ।
- ਮਲਟੀ-ਰੈਪਲਿਕਾ ਡਿਪਲੌਇਮੈਂਟਾਂ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ, ਜਿੱਥੇ ਕਾਊਂਟਰ ਸਾਂਝੇ ਕੀਤੇ ਜਾਣੇ ਲਾਜ਼ਮੀ ਹਨ।

### ਡਰਾਈਵਰ ਬਦਲਣਾ

ਸੈਟਿੰਗਜ਼ UI (`/dashboard/settings` → ਕੋਟਾ ਸਟੋਰ) ਰਾਹੀਂ, ਜਾਂ env vars ਰਾਹੀਂ:

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

DB ਸੈਟਿੰਗ ਨੂੰ env ਉੱਤੇ ਤਰਜੀਹ ਮਿਲਦੀ ਹੈ। ਜੇ `driver=redis` ਹੈ ਪਰ URL ਮੌਜੂਦ ਨਹੀਂ ਹੈ ਜਾਂ
`ioredis` ਇੰਸਟਾਲ ਨਹੀਂ ਹੈ, ਤਾਂ ਫੈਕਟਰੀ SQLite ਉੱਤੇ ਵਾਪਸ ਚਲੀ ਜਾਂਦੀ ਹੈ ਅਤੇ ਇੱਕ ਚੇਤਾਵਨੀ ਲੌਗ ਕਰਦੀ ਹੈ।

ਡਰਾਈਵਰ ਚੋਣ ਦਾ ਕ੍ਰਮ:

1. DB ਸੈਟਿੰਗ `quotaStore.driver`
2. Env `QUOTA_STORE_DRIVER`
3. ਡਿਫਾਲਟ: `sqlite`

## ਬਹੁ-ਆਯਾਮ

ਇੱਕ ਪੂਲ ਦੇ ਕਈ ਆਯਾਮ ਹੋ ਸਕਦੇ ਹਨ। ਹਰ ਆਯਾਮ ਸੁਤੰਤਰ ਹੁੰਦਾ ਹੈ:

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // ਇਸ ਆਯਾਮ ਲਈ ਗਲੋਬਲ ਪੂਲ ਦੀ ਅਧਿਕਤਮ ਸੀਮਾ
}
```

**ਉਦਾਹਰਨ: Codex ਪਲਾਨ** (5h% + ਹਫ਼ਤਾਵਾਰੀ%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

ਮਨਜ਼ੂਰ ਹੋਣ ਲਈ ਇੱਕ ਬੇਨਤੀ ਨੂੰ ਸਾਰੇ ਆਯਾਮਾਂ ਦੀਆਂ ਸ਼ਰਤਾਂ ਪੂਰੀਆਂ ਕਰਨੀਆਂ ਲਾਜ਼ਮੀ ਹਨ।

## ਪਾਈਪਲਾਈਨ ਇੰਟੀਗ੍ਰੇਸ਼ਨ

### PRE ਹੁੱਕ (`open-sse/handlers/chatCore.ts`)

ਆਥ ਅਤੇ ਪਾਲਿਸੀ ਜਾਂਚਾਂ ਤੋਂ ਬਾਅਦ, ਅੱਪਸਟ੍ਰੀਮ ਐਗਜ਼ੀਕਿਊਟਰ ਤੋਂ ਪਹਿਲਾਂ ਚੱਲਦਾ ਹੈ:

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → ਹਰ ਆਯਾਮ ਲਈ getQuotaStore().peek()
      → fairShare.decideFairShare()
      → ਜੇ ਬਲੌਕ ਹੋਵੇ → 429 ਵਾਪਸ ਕਰੋ (buildErrorBody, ਸਖ਼ਤ ਨਿਯਮ #12)
      → ਜੇ ਮਨਜ਼ੂਰ ਹੋਵੇ + ਤਰਜੀਹ ਘਟਾਉਣੀ ਹੋਵੇ → ਉਮੀਦਵਾਰ ਉੱਤੇ quotaSoftPenalty=true ਸੈੱਟ ਕਰੋ
  → executor.execute()
```

**ਫੇਲ-ਓਪਨ**: ਜੇ `enforceQuotaShare` ਐਕਸੈਪਸ਼ਨ ਸੁੱਟਦਾ ਹੈ, ਤਾਂ ਬੇਨਤੀ ਨੂੰ
`pino.warn` ਲੌਗ ਦੇ ਨਾਲ ਅੱਗੇ ਜਾਣ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ। ਇਹ ਕੋਟਾ-ਇੰਜਣ ਦੇ ਬੱਗ ਨੂੰ ਸਾਰੇ
ਟ੍ਰੈਫਿਕ ਨੂੰ ਬਲੌਕ ਕਰਨ ਤੋਂ ਰੋਕਦਾ ਹੈ।

### POST ਹੁੱਕ (ਖਪਤ ਰਿਕਾਰਡ ਕਰੋ)

ਸਫਲ ਜਵਾਬ ਤੋਂ ਬਾਅਦ:

```
ਐਗਜ਼ੀਕਿਊਟਰ ਸਫਲਤਾ ਵਾਪਸ ਕਰਦਾ ਹੈ
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → ਹਰ ਆਯਾਮ ਲਈ getQuotaStore().consume()
      → ਫੇਲ-ਓਪਨ: ਗਲਤੀਆਂ pino.warn ਵਜੋਂ ਲੌਗ ਹੁੰਦੀਆਂ ਹਨ, ਕਦੇ ਵੀ ਕਲਾਇੰਟ ਤੱਕ ਨਹੀਂ ਪਹੁੰਚਾਈਆਂ ਜਾਂਦੀਆਂ
```

**ਡ੍ਰਿਫਟ ਨੋਟ**: ਜੇ ਜਵਾਬ ਤੋਂ ਬਾਅਦ `consume` ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ, ਤਾਂ ਰੋਲਿੰਗ ਕਾਊਂਟਰ ਘੱਟ ਗਿਣਤੀ ਕਰਦਾ ਹੈ।
ਪ੍ਰੋਵਾਈਡਰ ਤੋਂ ਮਿਲਣ ਵਾਲਾ ਸੈਚੁਰੇਸ਼ਨ ਸਿਗਨਲ (ਉਦਾਹਰਨ ਲਈ `anthropic-ratelimit-unified-5h-utilization`)
ਅਗਲੀ ਬੇਨਤੀ ਉੱਤੇ ਗਲੋਬਲ ਅਨੁਮਾਨ ਨੂੰ ਠੀਕ ਕਰਦਾ ਹੈ।

### ਕੰਬੋ ਸੌਫਟ ਪੈਨਲਟੀ (`open-sse/services/combo.ts`)

ਜਦੋਂ `decision.deprioritize === true` ਹੋਵੇ:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // ਡਿਫਾਲਟ 0.7
}
```

ਇਹ ਪੈਨਲਟੀ ਹੋਰ ਸਾਰੇ ਸਕੋਰਿੰਗ ਕਾਰਕਾਂ ਤੋਂ ਬਾਅਦ ਲਾਗੂ ਕੀਤੀ ਜਾਂਦੀ ਹੈ। ਇਹ ਕਿਸੇ ਸੈਚੁਰੇਟਡ ਕੀ ਨੂੰ ਹਾਰਡ-ਬਲੌਕ ਕੀਤੇ ਬਿਨਾਂ
ਉਸਦੀ ਚੋਣ ਹੋਣ ਦੀ ਆਟੋ-ਕੰਬੋ ਸੰਭਾਵਨਾ ਘਟਾਉਂਦੀ ਹੈ।

## ਸਮੱਸਿਆ-ਨਿਵਾਰਣ

### Redis ਸੰਰਚਿਤ ਹੈ ਪਰ ਕਨੈਕਟ ਨਹੀਂ ਹੋ ਰਿਹਾ

ਜਾਂਚ ਕਰੋ ਕਿ `ioredis` ਇੰਸਟਾਲ ਹੈ (`npm ls ioredis`) ਅਤੇ `QUOTA_STORE_REDIS_URL`
ਤੱਕ ਪਹੁੰਚ ਕੀਤੀ ਜਾ ਸਕਦੀ ਹੈ। ਕਨੈਕਸ਼ਨ ਅਸਫਲ ਹੋਣ 'ਤੇ ਫੈਕਟਰੀ ਮੁੜ SQLite ਵਰਤਦੀ ਹੈ (`warn`
ਪੱਧਰ 'ਤੇ ਲੌਗ ਕੀਤਾ ਜਾਂਦਾ ਹੈ)।

### `peek` ਪੁਰਾਣਾ ਡਾਟਾ ਵਾਪਸ ਕਰਦਾ ਹੈ / ਫੇਲ-ਓਪਨ ਹੁੰਦਾ ਹੈ

ਜੇ `peek` ਤਰੁੱਟੀ ਸੁੱਟਦਾ ਹੈ, ਤਾਂ `enforceQuotaShare` ਨਤੀਜੇ ਨੂੰ "ਇਜਾਜ਼ਤ ਦਿਓ" (ਫੇਲ-ਓਪਨ) ਵਜੋਂ ਮੰਨਦਾ ਹੈ।
ਮੂਲ ਕਾਰਨ ਦੀ ਪਛਾਣ ਕਰਨ ਲਈ `quota:enforce` ਅਤੇ `quota:factory` ਐਂਟਰੀਆਂ ਵਾਸਤੇ
`pino` ਲੌਗ ਜਾਂਚੋ।

### ਖਪਤ ਕਾਊਂਟਰ ਵਿੱਚ ਅੰਤਰ

ਜੇ ਪ੍ਰਦਾਤਾ ਦੀ ਅਸਲ ਵਰਤੋਂ ਕਾਊਂਟਰਾਂ ਤੋਂ ਵੱਖਰੀ ਹੈ, ਤਾਂ ਇਹ ਉਮੀਦ ਅਨੁਸਾਰ ਹੈ — 2-ਬਕਟ
ਸਲਾਈਡਿੰਗ ਵਿੰਡੋ ਵਿੱਚ ਵਿੰਡੋ ਦੀਆਂ ਹੱਦਾਂ ਉੱਤੇ ~1% ਤਰੁੱਟੀ ਹੁੰਦੀ ਹੈ, ਅਤੇ `consume`
ਜਵਾਬ ਤੋਂ ਬਾਅਦ ਫਾਇਰ-ਐਂਡ-ਫਰਗੈਟ ਢੰਗ ਨਾਲ ਚੱਲਦਾ ਹੈ। ਸੰਤ੍ਰਿਪਤੀ ਸੰਕੇਤ (`saturationSignals.ts`)
30s TTL ਨਾਲ ਪ੍ਰਦਾਤਾ ਦੀ ਅਸਲ ਵਰਤੋਂ ਪੜ੍ਹਦਾ ਹੈ ਅਤੇ ਉਸ ਅਨੁਸਾਰ `globalUsedPercent`
ਨੂੰ ਸਮਾਯੋਜਿਤ ਕਰਦਾ ਹੈ।

### ਖਪਤ ਦਰ ਲਈ ਪੂਲ "ਕੋਈ ਡਾਟਾ ਨਹੀਂ" ਦਿਖਾਉਂਦਾ ਹੈ

`computeBurnRate` ਲਈ ਘੱਟੋ-ਘੱਟ 2 ਇਤਿਹਾਸਕ ਨਮੂਨੇ ਲੋੜੀਂਦੇ ਹਨ। ਪਹਿਲਾਂ
`consume` ਕਾਲਾਂ ਤੋਂ ਬਿਨਾਂ ਨਵੇਂ ਪੂਲ `tokensPerSecond: 0` ਅਤੇ `timeToExhaustionMs: null` ਦਿਖਾਉਣਗੇ।

## localStorage ਤੋਂ ਮਾਈਗ੍ਰੇਸ਼ਨ

ਜਦੋਂ `/dashboard/costs/quota-share` ਪਹਿਲੀ ਵਾਰ ਲੋਡ ਹੁੰਦਾ ਹੈ, ਤਾਂ ਹੁੱਕ `useLocalStoragePoolMigration`
ਇਹ ਜਾਂਚਦਾ ਹੈ:

1. `localStorage.getItem("omniroute:quota-share:pools")` ਖਾਲੀ ਨਹੀਂ ਹੈ।
2. `GET /api/quota/pools` ਵੱਲੋਂ `[]` ਵਾਪਸ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (DB ਖਾਲੀ ਹੈ)।

ਜੇ ਦੋਵੇਂ ਸ਼ਰਤਾਂ ਸਹੀ ਹਨ, ਤਾਂ ਇਹ ਹਰ ਪੁਰਾਣੇ ਪੂਲ ਨੂੰ ਬੈਚ ਵਿੱਚ `POST /api/quota/pools` ਉੱਤੇ ਪੋਸਟ ਕਰਦਾ ਹੈ,
ਫਿਰ localStorage ਕੁੰਜੀ ਨੂੰ ਹਟਾ ਦਿੰਦਾ ਹੈ। ਮਾਈਗ੍ਰੇਸ਼ਨ ਇਡੈਂਪੋਟੈਂਟ ਹੈ: ਸ਼ਰਤ 2
ਦੁਬਾਰਾ ਮਾਈਗ੍ਰੇਸ਼ਨ ਨੂੰ ਰੋਕਦੀ ਹੈ।

## ਅੰਦਰੂਨੀ ਰਣਨੀਤੀ ਵਰਗੀਕਰਨ

UI ਜਾਂ API ਵਿੱਚ ਵਰਤੋਂਕਾਰ ਦੁਆਰਾ ਚੁਣਨਯੋਗ ਵਿਕਲਪ ਵਜੋਂ ਨਾ ਦਿਖਾਈ ਦੇਵੇ।

## DB ਸਕੀਮਾ ਸੰਖੇਪ

ਮਾਈਗ੍ਰੇਸ਼ਨਾਂ `078`, `079` ਅਤੇ `085` ਦੁਆਰਾ ਤਿੰਨ ਟੇਬਲਾਂ ਜੋੜੀਆਂ ਗਈਆਂ ਹਨ:

- `quota_pools` + `quota_allocations` — ਪੂਲ ਪਰਿਭਾਸ਼ਾਵਾਂ ਅਤੇ ਪ੍ਰਤੀ-ਕੁੰਜੀ ਅਲਾਟਮੈਂਟ।
- `quota_consumption` — ਹਰ `(apiKeyId, dimensionKey)` ਲਈ ਰੋਲਿੰਗ 2-ਬਕੇਟ ਕਾਊਂਟਰ।
- `provider_plans` — ਮੈਨੁਅਲ ਪ੍ਰਦਾਤਾ ਪਲਾਨ ਓਵਰਰਾਈਡ (ਹਰ connectionId ਲਈ ਡਾਇਮੈਂਸ਼ਨ JSON)।

ਸਾਰੀਆਂ ਟੇਬਲਾਂ ਇਡੈਂਪੋਟੈਂਟ `CREATE TABLE IF NOT EXISTS` ਮਾਈਗ੍ਰੇਸ਼ਨਾਂ ਰਾਹੀਂ ਜੋੜੀਆਂ ਗਈਆਂ ਹਨ।
