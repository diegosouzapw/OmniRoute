## ਜ਼ੀਰੋ-ਕਾਨਫ਼ਿਗ ਆਟੋ-ਰਾਊਟਿੰਗ (`auto/` ਪ੍ਰੀਫਿਕਸ)

### ਸ਼੍ਰੇਣੀ × ਟੀਅਰ ਸੰਯੋਜਨ (`auto/<category>:<tier>`)

OpenRouter-ਸ਼ੈਲੀ ਦੇ ਸਫ਼ਿਕਸ **ਕਿਸ ਕਿਸਮ ਦਾ ਰੂਟ** (ਸ਼੍ਰੇਣੀ) ਨੂੰ **ਇਸਨੂੰ ਕਿਵੇਂ ਅਨੁਕੂਲਿਤ ਕਰਨਾ ਹੈ** (ਟੀਅਰ) ਤੋਂ ਵੱਖ ਕਰਦੇ ਹਨ, ਤਾਂ ਜੋ ਤੁਸੀਂ ਉਨ੍ਹਾਂ ਨੂੰ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਜੋੜ ਸਕੋ (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **ਸ਼੍ਰੇਣੀਆਂ** (ਸਮਰੱਥਾ ਅਨੁਸਾਰ ਉਮੀਦਵਾਰ ਪੂਲ ਨੂੰ ਫਿਲਟਰ ਕਰੋ): `coding` · `reasoning` · `vision` · `chat` · `multimodal`। `vision`/`multimodal` ਵਿਜ਼ਨ-ਸਮਰੱਥ ਮਾਡਲ ਰੱਖਦੇ ਹਨ; `reasoning` ਰੀਜ਼ਨਿੰਗ/ਥਿੰਕਿੰਗ ਮਾਡਲ ਰੱਖਦਾ ਹੈ।
- **ਟੀਅਰ** (ਸਕੋਰਿੰਗ ਵੇਟ / ਪੂਲ ਫਿਲਟਰ ਚੁਣੋ): `fast` (ਤੇਜ਼ੀ ਨਾਲ ਜਾਰੀ ਕਰਨ ਲਈ) · `cheap` (ਉਪਨਾਮ `floor`, ਲਾਗਤ-ਬਚਤ) · `reliable` (ਸਰਕਿਟ-ਬ੍ਰੇਕਰ ਸਿਹਤ + ਲੇਟੈਂਸੀ ਸਥਿਰਤਾ) · `free` / `pro` (`classifyTier` ਰਾਹੀਂ ਮਾਡਲ ਟੀਅਰ ਅਨੁਸਾਰ ਪੂਲ ਫਿਲਟਰ ਕਰੋ — ਮੁਫ਼ਤ ਟੀਅਰ ਬਨਾਮ ਪ੍ਰੀਮੀਅਮ)।

| ਉਦਾਹਰਨ                 | ਇਸ ਵਿੱਚ ਰਿਜ਼ਾਲਵ ਹੁੰਦਾ ਹੈ                                 |
| ---------------------- | -------------------------------------------------------- |
| `auto/coding:fast`     | ਕੋਡਿੰਗ ਪੂਲ, ਘੱਟ-ਲੇਟੈਂਸੀ ਵੇਟ                              |
| `auto/coding:cheap`    | ਕੋਡਿੰਗ ਪੂਲ, ਲਾਗਤ-ਅਨੁਕੂਲਿਤ (`auto/coding:floor` ਦਾ ਉਪਨਾਮ) |
| `auto/reasoning:pro`   | ਸਿਰਫ਼ ਰੀਜ਼ਨਿੰਗ/ਥਿੰਕਿੰਗ ਮਾਡਲ, ਪ੍ਰੀਮੀਅਮ ਟੀਅਰ               |
| `auto/vision`          | ਵਿਜ਼ਨ-ਸਮਰੱਥ ਮਾਡਲ (ਕੋਈ ਟੀਅਰ ਨਹੀਂ → ਸੰਤੁਲਿਤ ਵੇਟ)           |
| `auto/multimodal:free` | ਮਲਟੀਮੋਡਲ-ਸਮਰੱਥ ਮਾਡਲ, ਸਿਰਫ਼ ਮੁਫ਼ਤ ਟੀਅਰ                    |

ਕੋਈ ਵੀ ਵੈਧ `auto/<category>[:<tier>]` ਮੰਗ 'ਤੇ ਰਿਜ਼ਾਲਵ ਹੁੰਦਾ ਹੈ; ਇੱਕ ਚੁਣਿਆ ਹੋਇਆ ਸਬਸੈੱਟ `/v1/models` ਅਤੇ ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ ਪ੍ਰਦਰਸ਼ਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (`open-sse/services/autoCombo/builtinCatalog.ts` ਵਿੱਚ `AUTO_SUFFIX_VARIANTS`)। ਫਿਲਟਰਿੰਗ **ਫੇਲ-ਓਪਨ** ਹੈ — ਜੇ ਕਿਸੇ ਪਾਬੰਦੀ ਨਾਲ ਕੋਈ ਵੀ ਕਨੈਕਟ ਕੀਤਾ ਮਾਡਲ ਮੇਲ ਨਹੀਂ ਖਾਂਦਾ, ਤਾਂ ਪੂਰਾ ਪੂਲ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ, ਤਾਂ ਜੋ ਰਾਊਟਿੰਗ ਕਦੇ ਨਾ ਟੁੱਟੇ। ਮੁੱਖ ਸਕੋਰਰ (`combo.ts`) ਅਪਰਿਵਰਤਿਤ ਹੈ; ਸ਼੍ਰੇਣੀ/ਟੀਅਰ ਫਿਲਟਰ `buildAutoCandidates` ਵਿੱਚ ਲਾਗੂ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

> **ਲਾਈਵ ਮਾਡਲ ਇੰਟੈਲੀਜੈਂਸ:** ਜਦੋਂ `ARENA_ELO_SYNC_ENABLED` ਫਲੈਗ ਚਾਲੂ ਹੁੰਦਾ ਹੈ, ਤਾਂ ਆਟੋ-ਰਾਊਟਿੰਗ ਦੀ ਉਚਿਤਤਾ ਲਾਈਵ **Arena ELO** ਰੈਂਕਿੰਗਾਂ + **models.dev** ਟੀਅਰ ਡਾਟਾ ਤੋਂ ਜਾਣਕਾਰੀ ਲੈਂਦੀ ਹੈ (ਨਹੀਂ ਤਾਂ ਸਥਿਰ ਫਿਟਨੈੱਸ ਮੈਪ 'ਤੇ ਵਾਪਸ ਜਾਂਦੀ ਹੈ)।

**ਵਰਤਣ ਦਾ ਤਰੀਕਾ:**

```bash
# ਕੋਈ ਵੀ IDE ਜਾਂ CLI ਟੂਲ ਜੋ OpenAI ਫਾਰਮੈਟ ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ
ਬੇਸ URL: http://localhost:20128/v1
API ਕੁੰਜੀ:  <your-endpoint-key>

# ਆਪਣੇ ਕੋਡ/ਕਾਨਫ਼ਿਗ ਵਿੱਚ, ਮਾਡਲ ਨੂੰ ਇਸ ਤਰ੍ਹਾਂ ਸੈੱਟ ਕਰੋ:
model: "auto"                 # ਸੰਤੁਲਿਤ ਡਿਫਾਲਟ
model: "auto/coding"          # ਕੋਡਿੰਗ ਕਾਰਜਾਂ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ
model: "auto/fast"            # ਸਭ ਤੋਂ ਤੇਜ਼ ਉਪਲਬਧ
model: "auto/cheap"           # ਪ੍ਰਤੀ ਟੋਕਨ ਸਭ ਤੋਂ ਸਸਤਾ
```

**ਕੀ ਹੁੰਦਾ ਹੈ:**

1. OmniRoute `src/sse/handlers/chat.ts` ਵਿੱਚ `auto/` ਪ੍ਰੀਫਿਕਸ ਦਾ ਪਤਾ ਲਗਾਉਂਦਾ ਹੈ
2. ਡਾਟਾਬੇਸ ਤੋਂ ਸਾਰੇ **ਸਰਗਰਮ ਪ੍ਰੋਵਾਈਡਰ ਕਨੈਕਸ਼ਨਾਂ** ਲਈ ਕਵੇਰੀ ਕਰਦਾ ਹੈ
3. ਵੈਧ ਕ੍ਰੈਡੈਂਸ਼ਲਾਂ (API ਕੁੰਜੀ ਜਾਂ OAuth ਟੋਕਨ) ਵਾਲਿਆਂ ਤੱਕ ਫਿਲਟਰ ਕਰਦਾ ਹੈ
4. ਹਰ ਕਨੈਕਸ਼ਨ ਲਈ ਮਾਡਲ ਨਿਰਧਾਰਤ ਕਰਦਾ ਹੈ (`connection.defaultModel` ਜਾਂ ਪ੍ਰੋਵਾਈਡਰ ਦਾ ਪਹਿਲਾ ਮਾਡਲ)
5. ਮੈਮੋਰੀ ਵਿੱਚ ਇੱਕ **ਵਰਚੁਅਲ ਕੰਬੋ** ਬਣਾਉਂਦਾ ਹੈ (DB ਵਿੱਚ ਸਟੋਰ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ)
6. ਚੁਣੇ ਗਏ ਵੇਰੀਐਂਟ ਦੇ ਵੇਟ ਪ੍ਰੋਫਾਈਲ + LKGP ਰਣਨੀਤੀ ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਰਾਊਟ ਕਰਦਾ ਹੈ

**ਮੁੱਖ ਵਿਸ਼ੇਸ਼ਤਾਵਾਂ:**

- ✅ **ਹਮੇਸ਼ਾ ਚਾਲੂ:** ਕਿਸੇ ਟੌਗਲ, ਕੰਬੋ ਬਣਾਉਣ ਜਾਂ ਕਾਨਫ਼ਿਗਰੇਸ਼ਨ ਦੀ ਲੋੜ ਨਹੀਂ
- ✅ **ਡਾਇਨਾਮਿਕ:** ਮੌਜੂਦਾ ਕਨੈਕਟ ਕੀਤੇ ਪ੍ਰੋਵਾਈਡਰਾਂ ਨੂੰ ਆਪਣੇ ਆਪ ਦਰਸਾਉਂਦਾ ਹੈ
- ✅ **ਸੈਸ਼ਨ ਸਟਿੱਕੀਨੈੱਸ:** LKGP ਯਕੀਨੀ ਬਣਾਉਂਦਾ ਹੈ ਕਿ ਆਖਰੀ ਸਫਲ ਪ੍ਰੋਵਾਈਡਰ ਨੂੰ ਤਰਜੀਹ ਦਿੱਤੀ ਜਾਵੇ
- ✅ **ਮਲਟੀ-ਅਕਾਊਂਟ ਜਾਗਰੂਕ:** ਹਰ ਪ੍ਰੋਵਾਈਡਰ ਕਨੈਕਸ਼ਨ ਇੱਕ ਵੱਖਰਾ ਉਮੀਦਵਾਰ ਬਣ ਜਾਂਦਾ ਹੈ
- ✅ **ਕੋਈ DB ਰਾਈਟ ਨਹੀਂ:** ਵਰਚੁਅਲ ਕੰਬੋ ਸਿਰਫ਼ ਬੇਨਤੀ ਲਈ ਮੌਜੂਦ ਰਹਿੰਦਾ ਹੈ, ਸਥਾਈ ਸਟੋਰੇਜ ਦਾ ਕੋਈ ਓਵਰਹੈੱਡ ਨਹੀਂ

### ਪ੍ਰਤੀ-ਕੁੰਜੀ ਉਮੀਦਵਾਰ ਨਿਯੰਤਰਣ (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` ਤੋਂ ਬਾਅਦ ਵਾਲਾ ਸਫ਼ਿਕਸ, ਜਾਂ
ਬੇਸ ਚੈਨਲ ਲਈ ਸ਼ਾਬਦਿਕ `auto`) ਇੱਕ **ਸਿਰਫ਼-ਪੜ੍ਹਨਯੋਗ** ਐਂਡਪੌਇੰਟ ਹੈ, ਜੋ ਕਿਸੇ
`auto/*` ਚੈਨਲ ਦੇ ਮੌਜੂਦਾ ਉਮੀਦਵਾਰ ਪੂਲ ਨੂੰ ਲਾਈਵ ਪਹੁੰਚਯੋਗਤਾ ਨਾਲ ਸਜਾ ਕੇ ਸੂਚੀਬੱਧ ਕਰਦਾ ਹੈ ਅਤੇ
ਮੌਜੂਦਾ ਰੇਜ਼ਿਲੀਅੰਸ ਰੀਡਾਂ ਦੀ ਮੁੜ ਵਰਤੋਂ ਕਰਦਾ ਹੈ (ਕਦੇ ਵੀ ਕੱਚਾ ਬ੍ਰੇਕਰ `state` ਨਹੀਂ):

- ਪ੍ਰੋਵਾਈਡਰ ਸਰਕਿਟ ਬ੍ਰੇਕਰ — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- ਕਨੈਕਸ਼ਨ ਕੂਲਡਾਊਨ — ਰਿਜ਼ਾਲਵ ਕੀਤੀ
  `provider_connections` ਰੋਅ ਉੱਤੇ `rateLimitedUntil` / `testStatus`
- ਮਾਡਲ ਲੌਕਆਉਟ — `isModelLocked(provider, connectionId, model)`

ਹਰ ਉਮੀਦਵਾਰ ਨਾਲ ਇਸ API ਕੁੰਜੀ ਦਾ `excluded` ਫਲੈਗ ਵੀ ਹੁੰਦਾ ਹੈ। ਬਾਹਰ ਰੱਖਣ ਦੀਆਂ ਸੈਟਿੰਗਾਂ
ਹਰ API ਕੁੰਜੀ ਲਈ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਸਟੋਰ ਕੀਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ (`auto_candidate_overrides` ਟੇਬਲ, ਮਾਈਗ੍ਰੇਸ਼ਨ `128`) — OmniRoute
ਇੱਕਲ-ਟੈਨੈਂਟ ਹੈ ਅਤੇ ਇਸ ਵਿੱਚ ਕੋਈ `users` ਟੇਬਲ ਨਹੀਂ ਹੈ, ਇਸ ਲਈ `apiKeyId` ਅਸਲੀ ਪ੍ਰਤੀ-ਕਾਲਰ
ਪਛਾਣ ਦੇ ਸਭ ਤੋਂ ਨੇੜੇ ਹੈ — ਅਤੇ ਇਹਨਾਂ ਨੂੰ
`open-sse/services/autoCombo/virtualFactory.ts` ਵਿੱਚ ਉਮੀਦਵਾਰ-ਪੂਲ ਦੇ ਚੋਕਪੌਇੰਟ 'ਤੇ ਸ਼ੁੱਧ, ਯੂਨਿਟ-ਟੈਸਟ ਕੀਤੇ
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) ਰਾਹੀਂ ਲਾਗੂ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।
ਫਿਲਟਰ **ਫੇਲ-ਓਪਨ** ਹੈ: ਸੈੱਟ ਨਾ ਕੀਤਾ ਹੋਇਆ apiKeyId/ਚੈਨਲ ਜਾਂ DB ਲੁੱਕਅੱਪ ਦੀ ਅਸਫਲਤਾ ਦੋਵੇਂ
ਪੂਲ ਨੂੰ ਬਿਨਾਂ ਫਿਲਟਰ ਕੀਤੇ ਛੱਡਦੇ ਹਨ, ਇਸ ਲਈ ਕੋਈ ਓਪਰੇਟਰ ਜਿਸ ਨੇ ਕੋਈ ਓਵਰਰਾਈਡ ਕਾਨਫ਼ਿਗਰ ਨਹੀਂ ਕੀਤਾ,
ਇਸ ਵਿਸ਼ੇਸ਼ਤਾ ਤੋਂ ਪਹਿਲਾਂ ਵਾਲੀ ਰਾਊਟਿੰਗ ਨੂੰ ਬਾਈਟ-ਦਰ-ਬਾਈਟ ਇੱਕੋ ਜਿਹਾ ਵੇਖਦਾ ਹੈ।

**ਫਾਲੋ-ਅੱਪ ਮੁੱਦੇ ਲਈ ਮੁਲਤਵੀ:** ਪ੍ਰਤੀ-ਉਮੀਦਵਾਰ ਭਾਰ + ਸਪਸ਼ਟ ਕ੍ਰਮਬੱਧਤਾ (ਪੱਧਰ 3
— ਮੌਜੂਦਾ ਭਾਰਿਤ/ਤਰਜੀਹੀ ਰਣਨੀਤੀ ਮਾਰਗਾਂ ਵਿੱਚ ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ) ਅਤੇ ਹਰ `auto/*` ਚੈਨਲ ਲਈ ਇੱਕ ਖ਼ਾਸ
`combo.ts` ਰਣਨੀਤੀ ਨੂੰ ਪਿੰਨ ਕਰਨਾ (ਪੱਧਰ 4)। ਇਸ ਖੁੱਲ੍ਹੇ ਸਵਾਲ ਲਈ #7819 ਯੋਜਨਾ ਵੇਖੋ ਕਿ
ਕੀ ਇਕੱਲੇ-ਕਿਰਾਏਦਾਰ ਮਾਡਲ ਦੇ ਮੱਦੇਨਜ਼ਰ ਓਵਰਰਾਈਡ ਪ੍ਰਤੀ-API-ਕੁੰਜੀ ਹੀ ਰਹਿਣੇ ਚਾਹੀਦੇ ਹਨ ਜਾਂ ਗਲੋਬਲ ਬਣ ਜਾਣੇ ਚਾਹੀਦੇ ਹਨ।

**ਪਰਦੇ ਪਿੱਛੇ:**

```txt
ਬੇਨਤੀ: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts ਪ੍ਰੀਫਿਕਸ ਦੀ ਪਛਾਣ ਕਰਦਾ ਹੈ
   ↓
createVirtualAutoCombo('coding') → ਸਰਗਰਮ ਕਨੈਕਸ਼ਨਾਂ ਤੋਂ candidatePool
   ↓
handleComboChat (ਉਹੀ ਇੰਜਣ ਜੋ ਸਥਾਈ combos ਲਈ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ)
   ↓
ਆਟੋ-ਸਕੋਰਿੰਗ ਹਰ ਬੇਨਤੀ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ ਪ੍ਰਦਾਤਾ/ਮਾਡਲ ਚੁਣਦੀ ਹੈ
```

## ਅਸਲ ਮਾਡਲ Id ਨਾਲ ਮੇਲ ਖਾਂਦੇ ਕੰਬੋ ਨਾਮ

ਅਜਿਹਾ ਕੰਬੋ ਜਿਸਦਾ `name` ਕਿਸੇ ਸਿੱਧੇ ਮਾਡਲ id ਦੇ ਬਿਲਕੁਲ ਸਮਾਨ ਹੋਵੇ (ਉਦਾਹਰਨ ਵਜੋਂ, `gpt-5.5` ਨਾਮ ਵਾਲਾ ਕੰਬੋ), ਇੱਕ **ਜਾਣਬੁੱਝ ਕੇ ਬਣਾਇਆ ਗਿਆ, ਸਮਰਥਿਤ ਪੈਟਰਨ** ਹੈ, ਕੋਈ ਬੱਗ ਨਹੀਂ: ਇਹ ਪ੍ਰਤੀ-ਮਾਡਲ-id ਪ੍ਰੋਵਾਈਡਰ ਫਾਲਬੈਕ ਲਈ ਉਹ ਵਿਧੀ ਹੈ ਜਿਸਦਾ ਦਸਤਾਵੇਜ਼ੀਕਰਨ
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) ਵਿੱਚ ਕੀਤਾ ਗਿਆ ਹੈ। ਕਿਉਂਕਿ ਕੰਬੋ ਰੈਜ਼ੋਲਿਊਸ਼ਨ ਦੀ ਜਾਂਚ ਸਿੱਧੇ-ਮਾਡਲ-id ਰੈਜ਼ੋਲਿਊਸ਼ਨ ਤੋਂ ਪਹਿਲਾਂ ਕੀਤੀ ਜਾਂਦੀ ਹੈ
(`src/sse/services/model.ts` ਵਿੱਚ `getComboForModel()`), ਇਸ ਲਈ ਸਿੱਧੀ
id `gpt-5.5` ਲਈ ਬੇਨਤੀ ਨੂੰ ਸਿੱਧਾ ਕਿਸੇ ਇੱਕ ਪ੍ਰੋਵਾਈਡਰ ਕੋਲ ਭੇਜਣ ਦੀ ਬਜਾਏ ਕੰਬੋ ਦੇ ਟਾਰਗੇਟਾਂ (ਉਦਾਹਰਨ ਵਜੋਂ,
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) ਰਾਹੀਂ ਰੂਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ — ਇਹ
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) ਲਈ ਬਣਾਈ ਗਈ ਕੰਬੋ-ਪਹਿਲਾਂ-ਰੀਰਾਈਟ ਤਰਜੀਹ ਨੂੰ ਮੁੜ ਵਰਤਦਾ ਹੈ ਅਤੇ
`tests/unit/responses-combo-resolution-3227.test.ts` ਅਤੇ
`tests/unit/combo-name-codex-responses-rewrite.test.ts` ਦੁਆਰਾ ਇਸਦੀ ਰਿਗ੍ਰੈਸ਼ਨ ਜਾਂਚ ਕੀਤੀ ਜਾਂਦੀ ਹੈ।

ਕਿਸੇ ਕੰਬੋ ਨੂੰ ਅਜਿਹਾ ਨਾਮ ਦੇ ਕੇ ਬਣਾਉਣਾ ਜਾਂ ਉਸਦਾ ਨਾਮ ਬਦਲਣਾ, ਜੋ ਕਿਸੇ ਅਸਲ ਮਾਡਲ id ਨੂੰ ਓਹਲੇ ਕਰਦਾ ਹੋਵੇ, **ਕਦੇ ਵੀ ਅਸਵੀਕਾਰ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ** — ਅਜਿਹਾ ਕਰਨ ਨਾਲ ਇਹ ਦਸਤਾਵੇਜ਼ਬੱਧ ਕਾਰਜ-ਪ੍ਰਵਾਹ ਟੁੱਟ ਜਾਵੇਗਾ। ਇਸਦੀ ਬਜਾਏ
(#8530), `POST /api/combos` ਅਤੇ `PUT /api/combos/[id]` ਜਵਾਬ ਵਿੱਚ ਇੱਕ ਗੈਰ-ਰੋਕੂ
`warning` ਫੀਲਡ ਜੋੜਦੇ ਹਨ, ਜਦੋਂ (ਨਵਾਂ) ਨਾਮ ਕਿਸੇ ਅਸਲ ਮਾਡਲ id ਨਾਲ ਟਕਰਾਉਂਦਾ ਹੈ:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

ਬੂਟ ਸਮੇਂ, `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) ਇੱਕ-ਲਾਈਨ ਵਾਲੀ `[STARTUP]` ਚੇਤਾਵਨੀ ਵੀ ਲੌਗ ਕਰਦਾ ਹੈ, ਜਿਸ ਵਿੱਚ ਮਾਡਲ id ਨੂੰ ਓਹਲੇ ਕਰਨ ਵਾਲੇ ਹਰੇਕ ਮੌਜੂਦਾ ਕੰਬੋ ਦੀ ਸੂਚੀ ਹੁੰਦੀ ਹੈ, ਤਾਂ ਜੋ ਉਹ ਆਪਰੇਟਰ, ਜੋ ਇਸ ਸਥਿਤੀ ਵਿੱਚ ਜਾਣਬੁੱਝ ਕੇ (#6940 ਅਨੁਸਾਰ) ਨਹੀਂ ਸਗੋਂ ਗਲਤੀ ਨਾਲ ਪਹੁੰਚੇ ਹਨ, ਇਸ ਬਾਰੇ ਸੰਕੇਤ ਪ੍ਰਾਪਤ ਕਰ ਸਕਣ।
ਖੋਜ ਸਹਾਇਕ `src/lib/combos/modelNameCollision.ts` ਵਿੱਚ ਮੌਜੂਦ ਹੈ।

## ਕਲਾਇੰਟ ਤੋਂ ਕਸਟਮ ਕੰਬੋ ਨੂੰ ਕਾਲ ਕਰਨਾ

ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੰਭਾਲੇ ਕੰਬੋ (ਸੈਟਿੰਗਾਂ → ਕੰਬੋ) ਸਿਰਫ਼ ਉਦੋਂ ਵਰਤੇ ਜਾਂਦੇ ਹਨ, ਜਦੋਂ ਕਲਾਇੰਟ `model` ਫੀਲਡ ਵਿੱਚ ਕੰਬੋ ਦਾ **ਬਿਲਕੁਲ ਸਹੀ ਨਾਮ** ਭੇਜਦਾ ਹੈ — ਕੰਬੋ ਨਾਮ ਲਈ ਕੋਈ ਅੰਦਾਜ਼ਨ ਜਾਂ ਅੰਸ਼ਕ ਮਿਲਾਣ ਨਹੀਂ ਹੁੰਦਾ ਅਤੇ ਕੋਈ `auto/` ਪ੍ਰੀਫਿਕਸ ਸ਼ਾਮਲ ਨਹੀਂ ਹੁੰਦਾ। ਰੈਜ਼ੋਲਿਊਸ਼ਨ ਕ੍ਰਮ (`src/sse/services/model.ts` ਵਿੱਚ `getComboForModel()`):

1. ਕੰਬੋ ਨਾਮ ਦਾ ਬਿਲਕੁਲ ਸਹੀ ਮੇਲ (`model: "my-combo"`),
2. `combo/<name>` ਪ੍ਰੀਫਿਕਸ (`model: "combo/my-combo"`),
3. ਮਾਡਲ→ਕੰਬੋ ਗਲੌਬ ਮੈਪਿੰਗਾਂ (`/api/model-combo-mappings`)।

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

ਦੋ ਆਮ ਗਲਤੀਆਂ:

- **`auto` ਤੁਹਾਡੇ ਕੰਬੋ ਦੀ ਵਰਤੋਂ ਨਹੀਂ ਕਰਦਾ।** `auto`/`auto/*` ਆਪਣਾ ਜ਼ੀਰੋ-ਕਾਨਫਿਗ ਉਮੀਦਵਾਰ ਪੂਲ ਬਣਾਉਂਦਾ ਹੈ ਅਤੇ ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੰਭਾਲੇ ਕੰਬੋ ਨਾਲ ਸਿਰਫ਼ ਉਦੋਂ ਸਲਾਹ ਕਰਦਾ ਹੈ, ਜੇ ਕਿਸੇ ਕੰਬੋ ਦਾ ਨਾਮ ਅੱਖਰਸ਼ `auto` ਹੋਵੇ (ਇਸਦੀ ਸਿਫ਼ਾਰਸ਼ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ)। ਕਿਸੇ ਕੰਬੋ ਰਾਹੀਂ ਰੂਟ ਕਰਨ ਲਈ, ਉਸਦਾ ਬਿਲਕੁਲ ਸਹੀ ਨਾਮ ਭੇਜੋ — `auto` ਨਹੀਂ।
- **`openrouter/auto` ਇੱਕ ਅਸਲ ਭੁਗਤਾਨਯੋਗ OpenRouter ਉਤਪਾਦ** ("ਆਟੋ ਸਰਵੋਤਮ ਉਪਲਬਧ") ਹੈ, ਕੋਈ OmniRoute ਉਪਨਾਮ ਨਹੀਂ। ਇਹ OpenRouter ਰਜਿਸਟਰੀ (`open-sse/config/providers/registry/openrouter/index.ts`) ਦੀ ਇਕੱਲੀ ਸਥਿਰ ਮਾਡਲ ਐਂਟਰੀ ਹੈ ਅਤੇ ਇਸਦਾ ਬਿੱਲ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਲੱਗਦਾ ਹੈ। ਇਸਨੂੰ `auto` ਪੂਲਾਂ ਵਿੱਚੋਂ ਬਾਹਰ ਰੱਖਣ ਲਈ ਸੈਟਿੰਗਾਂ → ਰੂਟਿੰਗ → ਭੁਗਤਾਨਯੋਗ ਮਾਡਲ ਲੁਕਾਓ ਦੀ ਵਰਤੋਂ ਕਰੋ।

ਇੱਥੇ ਦਸਤਾਵੇਜ਼ਬੱਧ ਮੂਲ ਉਲਝਣ ਲਈ [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) ਅਤੇ [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) ਵੇਖੋ।

## ਇਹ ਕਿਵੇਂ ਕੰਮ ਕਰਦਾ ਹੈ (ਸਥਾਈ Auto-Combos)

Auto-Combo Engine ਇੱਕ **16-ਕਾਰਕ ਸਕੋਰਿੰਗ ਫੰਕਸ਼ਨ** (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` ਵਿੱਚ ਪਰਿਭਾਸ਼ਿਤ) ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਹਰ ਬੇਨਤੀ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ provider/model ਨੂੰ ਗਤੀਸ਼ੀਲ ਢੰਗ ਨਾਲ ਚੁਣਦਾ ਹੈ। ਡਿਫਾਲਟ ਭਾਰਾਂ ਦਾ ਜੋੜ `1.0` ਹੈ; ਕਸਟਮ ਭਾਰਾਂ ਨੂੰ `normalizeScoringWeights()` ਦੁਆਰਾ ਮੁੜ ਨਾਰਮਲਾਈਜ਼ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਸੋਲ੍ਹਾਂ ਵਿੱਚੋਂ ਦੋ — `cacheAffinity` ਅਤੇ `resetWindowAffinity` — ਦਾ ਡਿਫਾਲਟ ਭਾਰ `0` ਹੈ; `reliability` ਦਾ `DEFAULT_WEIGHTS` ਵਿੱਚ ਭਾਰ `0` ਹੈ, ਪਰ ਆਮ ਪੈਕਾਂ ਵਿੱਚ `0.03` ਅਤੇ `reliability-first` ਵਿੱਚ `0.04` ਹੈ, ਅਤੇ `quality` ਦਾ ਪੈਕਾਂ ਵਿੱਚ ਭਾਰ `0.02` (`quality-first` ਵਿੱਚ `0.03`) ਹੈ: ਫਿਰ ਵੀ ਹਰ ਉਮੀਦਵਾਰ ਲਈ ਇਨ੍ਹਾਂ ਦੀ ਗਣਨਾ ਕੀਤੀ ਜਾਂਦੀ ਹੈ, ਅਤੇ `cacheAffinity` ਸਕੋਰ ਤੋਂ ਬਾਹਰ prompt-cache ਡੀਡੁਪਲੀਕੇਸ਼ਨ ਨੂੰ ਨਿਯੰਤਰਿਤ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ ਸਿਫ਼ਰ-ਡਿਫਾਲਟ ਵਾਲੇ ਕਾਰਕ ਡਿਫਾਲਟ ਤੌਰ 'ਤੇ ਵੋਟ ਨਹੀਂ ਦਿੰਦੇ, ਜਦਕਿ ਪੈਕ ਦਿੰਦੇ ਹਨ।

## ਮੋਡ ਪੈਕ

### `weighted` ਦੇ ਅਰਥ

`weighted` **ਹਰ ਬੇਨਤੀ ਲਈ ਇੱਕ ਅਨੁਪਾਤਕ ਬੇਤਰਤੀਬ ਡਰਾਅ** ਹੈ
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), ਕੋਈ ਸਮਾਨਤਾ ਲਿਆਉਣ ਵਾਲਾ ਤਰੀਕਾ ਨਹੀਂ:

- ਹਰ ਬੇਨਤੀ `weight / totalWeight` ਸੰਭਾਵਨਾ ਨਾਲ **ਇੱਕ** ਪੜਾਅ ਚੁਣਦੀ ਹੈ; ਬਾਕੀ ਪੜਾਅ
  ਉਸ ਬੇਨਤੀ ਲਈ ਫਾਲਬੈਕ ਲੜੀ ਵਜੋਂ ਭਾਰ ਦੇ ਘਟਦੇ ਕ੍ਰਮ ਵਿੱਚ ਰੱਖੇ ਜਾਂਦੇ ਹਨ।
- ਜਿਸ ਪੜਾਅ ਦਾ ਭਾਰ `0` ਹੈ (ਜਾਂ ਮੌਜੂਦ ਨਹੀਂ), ਉਸਨੂੰ ਉਦੋਂ ਤੱਕ **ਕਦੇ ਨਹੀਂ ਚੁਣਿਆ ਜਾਂਦਾ** ਜਦੋਂ ਕਿਸੇ ਹੋਰ ਪੜਾਅ ਦਾ
  ਭਾਰ > 0 ਹੋਵੇ — ਉਹ ਸਿਰਫ਼ ਚੁਣਿਆ ਪੜਾਅ ਅਸਫਲ ਹੋਣ ਤੋਂ ਬਾਅਦ ਫਾਲਬੈਕ ਵਜੋਂ ਕੰਮ ਕਰ ਸਕਦਾ ਹੈ। ਚੋਣ ਸਿਰਫ਼ ਉਦੋਂ ਇਕਸਾਰ ਹੁੰਦੀ ਹੈ ਜਦੋਂ **ਸਾਰੇ**
  ਭਾਰ 0 ਹੋਣ।
- ਉਹ ਪੜਾਅ ਜਿਨ੍ਹਾਂ ਦੇ ਸਾਰੇ ਟਾਰਗੇਟ ਅਣਉਪਲਬਧ ਹਨ — ਪ੍ਰਦਾਤਾ ਸਰਕਿਟ ਬ੍ਰੇਕਰ `OPEN`, ਕਨੈਕਸ਼ਨ
  ਕੂਲਡਾਊਨ, ਮਾਡਲ ਲੌਕਆਊਟ — ਡਰਾਅ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਹੀ ਉਸ ਵਿੱਚੋਂ ਹਟਾ ਦਿੱਤੇ ਜਾਂਦੇ ਹਨ
  (`open-sse/services/combo/targetResolution.ts`), ਇਸ ਲਈ ਇੱਕੋ ਸਿਹਤਮੰਦ ਪੜਾਅ ਅਸਥਾਈ ਤੌਰ 'ਤੇ
  ਹਰ ਬੇਨਤੀ ਜਿੱਤ ਸਕਦਾ ਹੈ।
- `stickyWeightedLimit` (ਕੌਂਬੋ ਸੰਰਚਨਾ, ਮੂਲ `1` = ਬੰਦ) ਮੁੜ ਡਰਾਅ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਚੁਣੇ ਪੜਾਅ ਨੂੰ ਲਗਾਤਾਰ
  ਸਫਲਤਾਵਾਂ ਦੀ ਨਿਰਧਾਰਤ ਗਿਣਤੀ ਤੱਕ ਸਥਿਰ ਰੱਖਦਾ ਹੈ।

ਸਖ਼ਤ ਰੋਟੇਸ਼ਨ ਲਈ `round-robin` ਵਰਤੋ; `weighted` ਵਿੱਚ ਬਰਾਬਰ ਵੇਟ ਅੰਕੜਾਤਮਕ — ਨਾ ਕਿ
ਸਖ਼ਤ — ਸੰਤੁਲਨ ਦਿੰਦੇ ਹਨ।

### ਏਜੈਂਟਿਕ ਪਾਈਪਲਾਈਨ ਮੋਡ

ਘੱਟੋ-ਘੱਟ ਦੋ ਮਾਡਲਾਂ ਵਾਲਾ `pipeline` ਕੰਬੋ
`config.agenticOrchestration.enabled` ਰਾਹੀਂ ਪਲੈਨਰ/ਐਗਜ਼ਿਕਿਊਟਰ ਰਾਊਟਿੰਗ ਦੀ ਚੋਣ ਕਰ ਸਕਦਾ ਹੈ। ਪਹਿਲਾ ਟਾਰਗੇਟ ਯੋਜਨਾ ਬਣਾਉਣ ਅਤੇ ਅੰਤਿਮ ਜਵਾਬਾਂ ਲਈ ਜ਼ਿੰਮੇਵਾਰ ਹੁੰਦਾ ਹੈ;
ਦੂਜਾ ਟਾਰਗੇਟ ਕਲਾਇੰਟ-ਨੇਟਿਵ ਟੂਲ ਕਾਲਾਂ ਜਾਰੀ ਕਰਦਾ ਹੈ। OmniRoute ਬੇਨਤੀ ਪ੍ਰੋਟੋਕੋਲ ਤੋਂ
ਟੂਲ-ਨਤੀਜਾ ਜਾਰੀਕਰਨਾਂ ਦਾ ਪਤਾ ਲਗਾਉਂਦਾ ਹੈ, ਪਲੈਨਰ ਨੂੰ ਪੁੱਛਦਾ ਹੈ ਕਿ ਕੀ ਇੱਕ ਹੋਰ ਟੂਲ ਰਾਊਂਡ ਦੀ
ਲੋੜ ਹੈ, ਅਤੇ ਗਤੀਸ਼ੀਲ ਤੌਰ 'ਤੇ ਐਗਜ਼ਿਕਿਊਟਰ ਜਾਂ ਪਲੈਨਰ ਵਿੱਚੋਂ ਕਿਸੇ ਇੱਕ ਨੂੰ ਕਲਾਇੰਟ ਦੇ ਸਾਹਮਣੇ ਆਉਣ ਵਾਲਾ ਅੰਤਿਮ
ਪੜਾਅ ਬਣਾਉਂਦਾ ਹੈ।

ਦੂਜੇ ਟਾਰਗੇਟ ਤੋਂ ਬਾਅਦ ਵਾਧੂ ਮਾਡਲਾਂ ਨੂੰ ਕ੍ਰਮਬੱਧ ਐਗਜ਼ਿਕਿਊਟਰ ਬੈਕਅੱਪਾਂ ਵਜੋਂ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ। ਇੱਕ ਅਸਫਲ
HTTP ਜਵਾਬ ਜਾਂ ਟ੍ਰਾਂਸਪੋਰਟ ਅਪਵਾਦ ਅਗਲੇ ਐਗਜ਼ਿਕਿਊਟਰ ਵੱਲ ਵਧਦਾ ਹੈ, ਜਦਕਿ ਉਹੀ
ਪਲੈਨਰ ਫ਼ੈਸਲਾ ਅਤੇ ਨੇਟਿਵ ਟੂਲ ਨਾਲ ਲਿਜਾਏ ਜਾਂਦੇ ਹਨ, ਪਰ ਉਸ ਐਗਜ਼ਿਕਿਊਟਰ ਦਾ ਆਪਣਾ ਪੜਾਅ ਪ੍ਰੌਂਪਟ ਅਤੇ
ਰਿਜ਼ਾਲਵ ਕੀਤਾ ਕਨੈਕਸ਼ਨ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ। ਪਹਿਲਾ ਸਫਲ ਜਵਾਬ ਬਿਨਾਂ ਬਦਲਾਅ ਦੇ ਵਾਪਸ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਜਿਸ ਵਿੱਚ
SSE ਸਟ੍ਰੀਮਿੰਗ ਵੀ ਸ਼ਾਮਲ ਹੈ; ਸਫਲ ਸਟ੍ਰੀਮ ਸ਼ੁਰੂ ਹੋਣ ਤੋਂ ਬਾਅਦ ਹੋਣ ਵਾਲੀਆਂ ਅਸਫਲਤਾਵਾਂ ਨੂੰ ਇੱਥੇ ਦੁਬਾਰਾ ਅਜ਼ਮਾਇਆ ਨਹੀਂ ਜਾ ਸਕਦਾ।
ਜੇ ਸਾਰੇ ਐਗਜ਼ਿਕਿਊਟਰ ਅਸਫਲ ਹੋ ਜਾਣ, ਤਾਂ ਆਖ਼ਰੀ ਅਸਫਲਤਾ ਵਾਪਸ ਕੀਤੀ ਜਾਂਦੀ ਹੈ। ਕਲਾਇੰਟ ਵੱਲੋਂ ਰੱਦ ਕੀਤੇ ਜਾਣ 'ਤੇ ਡਿਸਪੈਚ ਰੁਕ ਜਾਂਦਾ ਹੈ।

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

ਐਗਜ਼ਿਕਿਊਟਰ ਇੱਕ ਜਵਾਬ ਵਿੱਚ ਕਈ ਸੁਤੰਤਰ ਕਾਲਾਂ ਜਾਰੀ ਕਰ ਸਕਦਾ ਹੈ। ਨਿਰਭਰ ਕਾਲਾਂ ਨੂੰ
ਬਾਅਦ ਦੀਆਂ ਕਲਾਇੰਟ ਟੂਲ-ਨਤੀਜਾ ਟਰਨਾਂ ਵਿੱਚ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ, ਅਤੇ ਪਲੈਨਰ ਹਰ ਨਤੀਜੇ ਦੀ ਸਮੀਖਿਆ ਕਰਦਾ ਹੈ।
`maxToolRounds` ਦਾ ਡਿਫੌਲਟ `8` ਹੈ ਅਤੇ ਇਹ `1`–`32` ਸਵੀਕਾਰ ਕਰਦਾ ਹੈ; ਸੀਮਾ 'ਤੇ ਪਹੁੰਚਣ ਤੋਂ ਬਾਅਦ, ਪਲੈਨਰ ਨੂੰ
ਉਪਲਬਧ ਸਭ ਤੋਂ ਵਧੀਆ ਅੰਤਿਮ ਜਵਾਬ ਤਿਆਰ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ। ਅੰਦਰੂਨੀ ਪਲੈਨਰ ਫ਼ੈਸਲੇ ਬਫ਼ਰ ਕੀਤੇ ਜਾਂਦੇ ਹਨ, ਜਦਕਿ
ਚੁਣਿਆ ਹੋਇਆ ਕਲਾਇੰਟ-ਫੇਸਿੰਗ ਜਵਾਬ ਮੂਲ ਸਟ੍ਰੀਮਿੰਗ ਤਰਜੀਹ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦਾ ਹੈ।

### `round-robin` ਸਟਿੱਕੀ ਬੈਚ ਅਤੇ ਅਕਾਊਂਟ ਵਿਸਤਾਰ

ਰਾਊਂਡ-ਰੌਬਿਨ ਬੈਚਾਂ ਵਿੱਚ ਕੰਮ ਕਰਦਾ ਹੈ, ਹਰ ਪੜਾਅ ਲਈ ਇੱਕ ਬੇਨਤੀ ਦੇ ਰੂਪ ਵਿੱਚ ਨਹੀਂ:

- `stickyRoundRobinLimit` (ਪਹਿਲਾਂ ਕੰਬੋ ਸੰਰਚਨਾ, ਫਿਰ `comboStickyRoundRobinLimit`, ਫਿਰ
  `settings.stickyRoundRobinLimit`, ਡਿਫੌਲਟ **3**) ਰੋਟੇਟ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਉਸੇ ਟਾਰਗੇਟ ਨੂੰ ਇੰਨੀਆਂ
  ਲਗਾਤਾਰ ਸਫਲਤਾਵਾਂ ਲਈ ਬਰਕਰਾਰ ਰੱਖਦਾ ਹੈ। ਹਰ ਬੇਨਤੀ 'ਤੇ ਰੋਟੇਸ਼ਨ ਲਈ ਕੰਬੋ ਓਵਰਰਾਈਡ ਨੂੰ `1` 'ਤੇ
  ਸੈੱਟ ਕਰੋ। ਕੰਬੋ ਐਡੀਟਰ ਪ੍ਰਭਾਵੀ ਮੁੱਲ ਅਤੇ ਇਹ ਕਿਸ ਲੇਅਰ ਤੋਂ ਆਇਆ ਹੈ, ਦਿਖਾਉਂਦਾ ਹੈ।
- `connectionAwareExpansion` (ਪਹਿਲਾਂ ਕੰਬੋ ਸੰਰਚਨਾ, ਫਿਰ ਸੈਟਿੰਗਾਂ, ਡਿਫੌਲਟ **false**) ਰੋਟੇਸ਼ਨ ਤੋਂ
  ਪਹਿਲਾਂ ਹਰ ਪ੍ਰਦਾਤਾ-ਪੱਧਰੀ ਪੜਾਅ ਨੂੰ ਪ੍ਰਤੀ-ਅਕਾਊਂਟ ਟਾਰਗੇਟਾਂ ਵਿੱਚ ਵਿਸਤਾਰਦਾ ਹੈ। Group-B ਰਣਨੀਤੀਆਂ
  (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp,
  fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion,
  pipeline) ਇਸਨੂੰ ਚਾਲੂ ਕੀਤੇ ਜਾਣ ਤੱਕ ਪ੍ਰਦਾਤਾ-ਪੱਧਰੀ ਦ੍ਰਿਸ਼ ਬਰਕਰਾਰ ਰੱਖਦੀਆਂ ਹਨ। ਕੰਬੋ ਐਡੀਟਰ
  inherit / on / off ਵਿਕਲਪ ਦਿੰਦਾ ਹੈ; inherit ਗਲੋਬਲ ਡਿਫੌਲਟ (off) ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ।
- ਪ੍ਰੌਂਪਟ-ਕੈਸ਼ ਲੋਕੈਲਿਟੀ ਰਾਊਟਿੰਗ (`promptCacheAffinityEnabled`, ਡਿਫੌਲਟ **true**) ਪਿੰਨ ਕੀਤੇ
  ਕਨੈਕਸ਼ਨਾਂ ਨੂੰ ਮੁੜ ਕ੍ਰਮਬੱਧ ਕਰਦੀ ਹੈ, ਤਾਂ ਜੋ ਮੇਲ ਖਾਂਦੀਆਂ ਕੈਸ਼ ਕੁੰਜੀਆਂ ਇੱਕੋ ਅਕਾਊਂਟ 'ਤੇ ਰਹਿਣ। ਇਹ ਪਿੰਨ ਕੀਤੇ
  ਪ੍ਰਤੀ-ਅਕਾਊਂਟ ਪੜਾਵਾਂ ਵਿੱਚ ਰਾਊਂਡ-ਰੌਬਿਨ ਅਤੇ ਵੇਟਡ ਰੋਟੇਸ਼ਨ ਨਾਲੋਂ ਪਹਿਲ ਲੈਂਦੀ ਹੈ। ਜੇ ਤੁਹਾਨੂੰ ਸਖ਼ਤ ਰੋਟੇਸ਼ਨ ਦੀ
  ਲੋੜ ਹੈ, ਤਾਂ Settings → Combo defaults ਅਧੀਨ ਇਸਨੂੰ ਬੰਦ ਕਰੋ। ਕੋਈ ਪ੍ਰਤੀ-ਕੰਬੋ ਓਵਰਰਾਈਡ ਨਹੀਂ ਹੈ।

ਇੱਕ ਮਾਡਲ 'ਤੇ ਮਲਟੀ-ਅਕਾਊਂਟ ਰੋਟੇਸ਼ਨ ਲਈ, ਤਿੰਨ ਪਿੰਨ ਕੀਤੇ `connectionId`s ਦੀ ਬਜਾਏ ਸਟਿੱਕੀ ਸੀਮਾ `1` ਵਾਲੇ
**ਇੱਕ ਡਾਇਨਾਮਿਕ-ਅਕਾਊਂਟ ਪੜਾਅ** (ਖਾਲੀ `connectionId`, ਪੂਰਾ ਪੂਲ) ਨੂੰ ਤਰਜੀਹ ਦਿਓ।
ਪਿੰਨ ਕੀਤੇ ਪੜਾਅ ਅਤੇ ਅਫ਼ਿਨਿਟੀ ਇੱਕੋ ਅਕਾਊਂਟ 'ਤੇ ਇਕੱਠੇ ਹੋ ਜਾਂਦੇ ਹਨ, ਭਾਵੇਂ RR ਕਾਊਂਟਰ
ਅੱਗੇ ਵਧਦਾ ਰਹੇ।

## ਫਿਊਜ਼ਨ ਰਣਨੀਤੀ

`fusion` ਇੱਕੋ-ਇੱਕ ਅਜਿਹੀ ਰਣਨੀਤੀ ਹੈ ਜੋ ਕਿਸੇ ਇੱਕ ਟਾਰਗੇਟ ਨੂੰ **ਨਹੀਂ** ਚੁਣਦੀ। ਇਹ ਪ੍ਰੌਂਪਟ ਨੂੰ
**ਹਰੇਕ ਪੈਨਲ ਮਾਡਲ ਨੂੰ ਸਮਾਂਤਰ ਤੌਰ 'ਤੇ** ਭੇਜਦੀ ਹੈ, ਫਿਰ ਇੱਕ ਸੰਰਚਨਾਯੋਗ **ਜੱਜ ਮਾਡਲ** ਸਾਰੇ
ਪੈਨਲ ਜਵਾਬਾਂ ਤੋਂ ਇੱਕ ਅੰਤਿਮ ਜਵਾਬ ਤਿਆਰ ਕਰਦਾ ਹੈ। ਅੱਪਸਟ੍ਰੀਮ `decolua/9router`
(OpenRouter ਦੇ Fusion ਡਿਜ਼ਾਈਨ) ਤੋਂ ਪੋਰਟ ਕੀਤਾ ਗਿਆ; ਇੰਪਲੀਮੈਂਟੇਸ਼ਨ `open-sse/services/fusion.ts` ਵਿੱਚ ਹੈ।

ਇਹ ਕਿਵੇਂ ਕੰਮ ਕਰਦੀ ਹੈ:

0. **ਟੂਲ-ਯੁਕਤ ਬਾਈਪਾਸ** — ਇੱਕ ਬੇਨਤੀ ਜਿਸ ਵਿੱਚ ਗੈਰ-ਖਾਲੀ `tools` ਐਰੇ ਹੋਵੇ ਅਤੇ
   `tool_choice` ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ `"none"` ਨਾ ਹੋਵੇ, ਪੈਨਲ ਨੂੰ ਪੂਰੀ ਤਰ੍ਹਾਂ ਛੱਡ ਦਿੰਦੀ ਹੈ: ਇਹ
   `tools`/`tool_choice` ਨੂੰ ਬਿਨਾਂ ਤਬਦੀਲੀ ਅੱਗੇ ਭੇਜਦੇ ਹੋਏ ਸਿੱਧੀ ਇੱਕ ਮਾਡਲ
   (ਸੰਰਚਿਤ ਜੱਜ, ਜਾਂ `panel[0]`) ਵੱਲ ਰੂਟ ਹੁੰਦੀ ਹੈ। ਪੈਨਲ ਮੈਂਬਰਾਂ ਕੋਲ ਟੂਲ ਪਹੁੰਚ ਨਹੀਂ ਹੁੰਦੀ ਅਤੇ
   ਜੱਜ ਦਾ ਸੰਸਲੇਸ਼ਣ ਨਿਰਦੇਸ਼ ਟੂਲ-ਕਾਲ ਬਣਾਉਣ ਤੋਂ ਵਰਜਦਾ ਹੈ, ਇਸ ਲਈ ਏਜੈਂਟਿਕ/ਟੂਲ-ਕਾਲਿੰਗ ਕਲਾਇੰਟਾਂ
   ਨੂੰ ਸੰਸਲੇਸ਼ਿਤ ਗੱਦ ਦੀ ਥਾਂ ਇੱਕ ਅਸਲ ਟੂਲ-ਕਾਲ ਫ਼ੈਸਲਾ ਮਿਲਦਾ ਹੈ (#6771)।
1. **ਫੈਨ-ਆਉਟ** (ਸਿਰਫ਼ ਟੂਲ-ਰਹਿਤ ਬੇਨਤੀਆਂ) — ਪ੍ਰੌਂਪਟ ਇੱਕੋ ਸਮੇਂ ਹਰੇਕ ਪੈਨਲ
   ਮਾਡਲ ਨੂੰ ਭੇਜਿਆ ਜਾਂਦਾ ਹੈ, ਟੂਲਾਂ ਨੂੰ ਹਟਾ ਕੇ ਨਾਨ-ਸਟ੍ਰੀਮਿੰਗ ਲਈ ਮਜਬੂਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (ਜੱਜ ਨੂੰ
   ਸੰਸਲੇਸ਼ਣ ਲਈ ਪੂਰਾ ਗੱਦ ਚਾਹੀਦਾ ਹੈ)।
2. **ਕੋਰਮ-ਗ੍ਰੇਸ ਇਕੱਤਰੀਕਰਨ** — ਜਿਵੇਂ ਹੀ `minPanel` ਜਵਾਬ ਆ ਜਾਂਦੇ ਹਨ, ਪਿੱਛੇ ਰਹਿ ਗਏ
   ਮਾਡਲਾਂ ਲਈ ਇੱਕ ਛੋਟਾ ਗ੍ਰੇਸ ਟਾਈਮਰ ਸ਼ੁਰੂ ਹੁੰਦਾ ਹੈ, ਫਿਰ ਜੋ ਵੀ ਇਕੱਠਾ ਹੋਇਆ ਹੋਵੇ ਉਸ ਨਾਲ ਫਿਊਜ਼ਨ
   ਅੱਗੇ ਵਧਦੀ ਹੈ। ਇਹ ਸਭ ਤੋਂ ਹੌਲੀ ਮਾਡਲ ਕਾਰਨ ਅਸਲ ਸਮੇਂ ਵਿੱਚ ਹੋਣ ਵਾਲੀ ਦੇਰੀ ਨੂੰ ਸੀਮਿਤ ਕਰਦਾ ਹੈ,
   ਜਿਸ ਉੱਤੇ ਇੱਕ ਹਾਰਡ ਟਾਈਮਆਉਟ ਦੀ ਹੱਦ ਵੀ ਲਾਗੂ ਹੁੰਦੀ ਹੈ।
3. **ਜੱਜ ਸੰਸਲੇਸ਼ਣ** — ਪੈਨਲ ਜਵਾਬਾਂ ਨੂੰ ਅਗਿਆਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (`Source 1`, `Source 2`, … — ਤਾਂ ਜੋ
   ਜੱਜ ਮਾਡਲ ਬ੍ਰਾਂਡ ਦੀ ਬਜਾਏ ਸਮੱਗਰੀ ਨੂੰ ਮਹੱਤਤਾ ਦੇਵੇ) ਅਤੇ ਜੱਜ ਨੂੰ ਸੌਂਪਿਆ ਜਾਂਦਾ ਹੈ, ਜੋ
   ਸਹਿਮਤੀ / ਵਿਰੋਧਾਭਾਸ / ਅੰਸ਼ਕ ਕਵਰੇਜ / ਵਿਲੱਖਣ ਅੰਤਰਦ੍ਰਿਸ਼ਟੀਆਂ / ਅਣਡਿੱਠੇ ਪੱਖਾਂ ਦਾ ਵਿਸ਼ਲੇਸ਼ਣ ਕਰਦਾ ਹੈ, ਫਿਰ
   **ਇੱਕ** ਪ੍ਰਮਾਣਿਕ ਜਵਾਬ ਲਿਖਦਾ ਹੈ। ਜੱਜ ਕਾਲ ਕਲਾਇੰਟ ਦੇ ਮੂਲ
   `stream` ਫਲੈਗ + ਟੂਲਾਂ ਨੂੰ ਕਾਇਮ ਰੱਖਦੀ ਹੈ, ਇਸ ਲਈ ਸਟ੍ਰੀਮਿੰਗ ਅਤੇ ਡਾਊਨਸਟ੍ਰੀਮ ਟੂਲ ਵਰਤੋਂ ਫਿਰ ਵੀ ਕੰਮ ਕਰਦੀ ਹੈ।
4. **ਸੁਚਾਰੂ ਡਿਗਰੇਡੇਸ਼ਨ** — 0 ਪੈਨਲ ਜਵਾਬ → `503`; ਸਿਰਫ਼ 1 ਬਚਿਆ ਜਵਾਬ → ਉਹ ਜਵਾਬ
   ਸਿੱਧਾ ਵਾਪਸ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (ਫਿਊਜ਼ ਕਰਨ ਲਈ ਕੁਝ ਨਹੀਂ); ਇੱਕ-ਮਾਡਲ ਪੈਨਲ ਸਿੱਧਾ ਜਵਾਬ ਦਿੰਦਾ ਹੈ।

ਕੋਈ ਪੈਨਲ ਮੈਂਬਰ ਇੱਕ `combo-ref` ਪੜਾਅ (`{kind: "combo-ref", comboName: "..."}`) ਵੀ ਹੋ ਸਕਦਾ ਹੈ, ਜੋ
ਕਿਸੇ ਹੋਰ ਕੌਂਬੋ ਦਾ ਹਵਾਲਾ ਦਿੰਦਾ ਹੈ — ਇਹ **ਇੱਕ ਬਲੈਕ-ਬਾਕਸ ਪੈਨਲ ਆਵਾਜ਼** ਵਜੋਂ ਰਿਜ਼ੌਲਵ ਹੁੰਦਾ ਹੈ (ਹਵਾਲਾ ਦਿੱਤੇ
ਕੌਂਬੋ ਵਿੱਚ ਪੂਰਾ ਰਿਕਰਸਿਵ ਡਿਸਪੈਚ, ਨਾ ਕਿ ਉਸ ਕੌਂਬੋ ਦੇ ਆਪਣੇ ਟਾਰਗੇਟਾਂ ਦਾ ਫੈਨ-ਆਉਟ), ਅਤੇ ਇਸ ਵਿੱਚ ਉਹੀ ਡੈਪਥ/ਸਾਈਕਲ
ਸੁਰੱਖਿਆ ਹੁੰਦੀ ਹੈ ਜੋ ਹਰ ਦੂਜੀ combo-ref ਵਰਤਣ ਵਾਲੀ ਰਣਨੀਤੀ ਪਹਿਲਾਂ ਹੀ ਵਰਤਦੀ ਹੈ (#6764)।

### ਸੰਰਚਨਾ

ਕੌਂਬੋ ਦੇ `config` ਬਲੌਬ ਉੱਤੇ ਸੰਰਚਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (ਕਿਸੇ ਸਕੀਮਾ ਮਾਈਗ੍ਰੇਸ਼ਨ ਦੀ ਲੋੜ ਨਹੀਂ — ਇਹ ਮੌਜੂਦਾ
`combos` ਟੇਬਲ ਨੂੰ ਮੁੜ ਵਰਤਦਾ ਹੈ):

| ਫ਼ੀਲਡ                                    | ਕਿਸਮ     | ਡਿਫੌਲਟ          | ਉਦੇਸ਼                                                                          |
| :--------------------------------------- | :------- | :-------------- | :----------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | ਪਹਿਲਾ ਪੈਨਲ ਮਾਡਲ | ਅੰਤਿਮ ਜਵਾਬ ਦਾ ਸੰਸਲੇਸ਼ਣ ਕਰਨ ਵਾਲਾ ਮਾਡਲ                                           |
| `config.fusionTuning.minPanel`           | `number` | `2`             | ਗ੍ਰੇਸ ਟਾਈਮਰ ਸ਼ੁਰੂ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਲੋੜੀਂਦੇ ਸਫਲ ਜਵਾਬ (`[2, panelSize]` ਤੱਕ ਸੀਮਿਤ) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`          | ਕੋਰਮ ਪੂਰਾ ਹੋਣ ਤੋਂ ਬਾਅਦ ਪਿੱਛੇ ਰਹਿ ਗਏ ਮਾਡਲਾਂ ਲਈ ਕਿੰਨਾ ਸਮਾਂ ਉਡੀਕ ਕਰਨੀ ਹੈ          |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`         | ਪੂਰਨ ਸੀਮਾ ਤਾਂ ਜੋ ਇੱਕ ਅਟਕਿਆ ਹੋਇਆ ਮਾਡਲ ਬੇਨਤੀ ਨੂੰ ਰੋਕ ਨਾ ਸਕੇ                      |

ਡਿਫੌਲਟ `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) ਵਿੱਚ ਮੌਜੂਦ ਹਨ।

### ਉਦਾਹਰਨ

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }

```

ਫਿਰ ਇਸਨੂੰ ਕਿਸੇ ਵੀ ਕੌਂਬੋ ਵਾਂਗ ਕਾਲ ਕਰੋ: `{"model":"fusion-panel","messages":[...]}`।

## ਵਰਚੁਅਲ ਆਟੋ-ਕੌਂਬੋ ਫੈਕਟਰੀ

ਆਟੋ ਕੌਂਬੋ ਇੰਜਣ ਨੂੰ ਪਹਿਲਾਂ ਤੋਂ ਪਰਿਭਾਸ਼ਿਤ ਕੌਂਬੋਆਂ ਦੀ ਲੋੜ ਨਹੀਂ ਹੁੰਦੀ। ਇਸ ਦੀ ਬਜਾਏ, `open-sse/services/autoCombo/virtualFactory.ts` ਤੁਰੰਤ ਉਮੀਦਵਾਰ ਬਣਾਉਂਦੀ ਹੈ:

1. `getProviderConnections({ isActive: true })` ਪ੍ਰਾਪਤ ਕਰਦੀ ਹੈ (ਸਾਰੇ ਸਮਰੱਥ ਕੀਤੇ ਕਨੈਕਸ਼ਨ)
2. ਵੈਧ ਕ੍ਰੈਡੈਂਸ਼ਲਾਂ ਵਾਲਿਆਂ ਤੱਕ ਫਿਲਟਰ ਕਰਦੀ ਹੈ (API ਕੁੰਜੀ ਜਾਂ `hasUsableOAuthToken()` ਰਾਹੀਂ ਮਿਆਦ ਨਾ ਪੁੱਗਿਆ OAuth ਟੋਕਨ)
3. ਮਾਡਲ ਉਪਲਬਧਤਾ + ਕੀਮਤ ਲਈ `getProviderRegistry()` ਨਾਲ ਕਰਾਸ-ਰੈਫਰੈਂਸ ਕਰਦੀ ਹੈ
4. ਹਰੇਕ ਟਿਊਪਲ `(provider, model, connection)` ਲਈ, ਇੱਕ `VirtualAutoComboCandidate` ਬਣਾਉਂਦੀ ਹੈ
5. ਡਿਸਪੈਚ ਟਾਰਗੇਟ ਵਜੋਂ `connection.defaultModel` (ਜਾਂ ਰਜਿਸਟਰੀ ਦਾ ਪਹਿਲਾ ਮਾਡਲ) ਚੁਣਦੀ ਹੈ
6. 16-ਫੈਕਟਰ `scorePool()` ਅਤੇ ਵੇਰੀਐਂਟ ਦੇ ਵੇਟ ਪੈਕ ਦੀ ਵਰਤੋਂ ਕਰਕੇ ਹਰੇਕ ਉਮੀਦਵਾਰ ਨੂੰ ਸਕੋਰ ਦਿੰਦੀ ਹੈ
7. `handleComboChat()` ਲਈ ਨਤੀਜੇ ਵਜੋਂ ਬਣਿਆ ਇਨ-ਮੈਮਰੀ `AutoComboConfig` ਵਾਪਸ ਕਰਦੀ ਹੈ — ਇਸਨੂੰ ਕਦੇ ਵੀ DB ਵਿੱਚ ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੁਰੱਖਿਅਤ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ

ਇਸਦਾ ਮਤਲਬ ਹੈ ਕਿ **`auto/*` ਸਮਰੱਥ ਕਿਸੇ ਨਵੇਂ ਪ੍ਰਦਾਤਾ ਨੂੰ ਜੋੜਨ ਨਾਲ ਉਮੀਦਵਾਰ ਪੂਲ ਆਪਣੇ ਆਪ ਵਿਸਤਾਰਿਤ ਹੋ ਜਾਂਦਾ ਹੈ** — ਕੌਂਬੋ ਨੂੰ ਹੱਥੀਂ ਸੰਪਾਦਿਤ ਕਰਨ ਦੀ ਲੋੜ ਨਹੀਂ। ਵਰਚੁਅਲ ਕੌਂਬੋ ਹਰ ਬੇਨਤੀ ਲਈ ਦੁਬਾਰਾ ਬਣਾਇਆ ਜਾਂਦਾ ਹੈ, ਇਸ ਲਈ ਨਵੇਂ ਜੋੜੇ ਗਏ ਜਾਂ ਹੁਣੇ-ਹੁਣੇ ਸਿਹਤਮੰਦ ਹੋਏ ਕਨੈਕਸ਼ਨ ਤੁਰੰਤ ਵਰਤ ਲਏ ਜਾਂਦੇ ਹਨ।

## ਸਵੈ-ਮੁਰੰਮਤ

- **ਅਸਥਾਈ ਬਾਹਰਕੱਢਣਾ**: ਸਕੋਰ < 0.2 → 5 ਮਿੰਟ ਲਈ ਬਾਹਰ (ਪ੍ਰਗਤੀਸ਼ੀਲ ਬੈਕਆਫ਼, ਵੱਧ ਤੋਂ ਵੱਧ 30 ਮਿੰਟ)
- **ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਜਾਗਰੂਕਤਾ**: OPEN → ਆਪਣੇ ਆਪ ਬਾਹਰ; HALF_OPEN → ਜਾਂਚ ਬੇਨਤੀਆਂ
- **ਘਟਨਾ ਮੋਡ**: >50% OPEN → ਖੋਜ ਬੰਦ ਕਰੋ, ਸਥਿਰਤਾ ਵੱਧ ਤੋਂ ਵੱਧ ਕਰੋ
- **ਕੂਲਡਾਊਨ ਰਿਕਵਰੀ**: ਬਾਹਰਕੱਢਣ ਤੋਂ ਬਾਅਦ, ਪਹਿਲੀ ਬੇਨਤੀ ਘਟਾਏ ਹੋਏ ਟਾਈਮਆਊਟ ਨਾਲ ਇੱਕ "ਜਾਂਚ" ਹੁੰਦੀ ਹੈ

## ਬੈਂਡਿਟ ਖੋਜ

5% ਬੇਨਤੀਆਂ (ਕਨਫਿਗਰ ਕਰਨ ਯੋਗ) ਖੋਜ ਲਈ ਬੇਤਰਤੀਬ ਪ੍ਰਦਾਤਾਵਾਂ ਵੱਲ ਰੂਟ ਕੀਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ। ਘਟਨਾ ਮੋਡ ਵਿੱਚ ਇਹ ਬੰਦ ਰਹਿੰਦੀ ਹੈ।

## API

ਕੋਈ **ਸਮਰਪਿਤ `POST /api/combos/auto` ਐਂਡਪੌਇੰਟ ਨਹੀਂ ਹੈ** — Auto-Combo ਨੂੰ ਦੋ ਤਰੀਕਿਆਂ ਨਾਲ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ:

1. **ਜ਼ੀਰੋ-ਕੰਫਿਗ (ਸਿਫ਼ਾਰਸ਼ੀ):** `model: "auto"` ਜਾਂ `model: "auto/<variant>"` ਨਾਲ ਕੋਈ ਵੀ ਚੈਟ ਕੰਪਲੀਸ਼ਨ ਬੇਨਤੀ ਭੇਜੋ। ਵਰਚੁਅਲ ਫੈਕਟਰੀ ਹਰ ਬੇਨਤੀ ਲਈ ਕੌਂਬੋ ਬਣਾਉਂਦੀ ਹੈ — ਕਿਸੇ ਪਰਸਿਸਟੈਂਸ ਜਾਂ API ਕਾਲ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ।

2. **`strategy: "auto"` ਵਾਲਾ ਸਥਾਈ ਕੌਂਬੋ:** `POST /api/combos` ਰਾਹੀਂ ਇੱਕ ਨਿਯਮਤ ਕੌਂਬੋ ਬਣਾਓ ਅਤੇ `strategy: "auto"` ਦੇ ਨਾਲ `config.auto.weights` / `config.auto.candidatePool` ਸੈੱਟ ਕਰੋ। ਉਹੀ ਸਕੋਰਿੰਗ ਇੰਜਣ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ; ਕੌਂਬੋ ਨੂੰ `combos` ਵਿੱਚ ਸਟੋਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ ID ਰਾਹੀਂ ਮੁੜ ਵਰਤਿਆ ਜਾ ਸਕਦਾ ਹੈ।

ਖੋਜ ਲਈ, `GET /api/combos/auto` ਹਰ ਵੇਰੀਐਂਟ ਨੂੰ ਉਸਦੇ ਰਿਜ਼ੌਲਵ ਕੀਤੇ ਕੈਂਡੀਡੇਟ ਪੂਲ ਦੇ ਨਾਲ-ਨਾਲ `context_length` / `max_output_tokens` ਸਮੇਤ ਸੂਚੀਬੱਧ ਕਰਦਾ ਹੈ — ਇਹ ਕੈਂਡੀਡੇਟ ਪੂਲ ਦੀਆਂ ਵਿੰਡੋਜ਼ ਵਿੱਚੋਂ ਸਭ ਤੋਂ ਵੱਧ MAX ਮੁੱਲ ਹੁੰਦਾ ਹੈ। ਕਲਾਇੰਟਾਂ (ਉਦਾਹਰਨ ਵਜੋਂ opencode ਪਲੱਗਇਨ) ਨੂੰ `0` ਦੀ ਬਜਾਏ ਇਹ ਮੁੱਲ ਪ੍ਰਚਾਰਿਤ ਕਰਨੇ ਚਾਹੀਦੇ ਹਨ: ਜ਼ੀਰੋ ਕੌਂਟੈਕਸਟ opencode ਦੀ ਆਟੋ-ਕੰਪੈਕਸ਼ਨ ਨੂੰ ਪੂਰੀ ਤਰ੍ਹਾਂ ਅਯੋਗ ਕਰ ਦਿੰਦਾ ਹੈ, ਜਿਸ ਨਾਲ ਸੈਸ਼ਨ ਉਦੋਂ ਤੱਕ ਵਧਦੇ ਰਹਿੰਦੇ ਹਨ ਜਦੋਂ ਤੱਕ ਗੇਟਵੇ ਦੀ ਹਿਸਟਰੀ ਪਰਜ ਕੌਂਟੈਕਸਟ ਨੂੰ ਨਸ਼ਟ ਨਹੀਂ ਕਰ ਦਿੰਦੀ। MAX ਨੂੰ ਪ੍ਰਚਾਰਿਤ ਕਰਨਾ ਸੁਰੱਖਿਅਤ ਹੈ ਕਿਉਂਕਿ ਆਟੋ-ਕੌਂਬੋ ਕੌਂਟੈਕਸਟ ਪ੍ਰੀ-ਫਿਲਟਰ ਵੱਡੇ ਆਕਾਰ ਵਾਲੀਆਂ ਬੇਨਤੀਆਂ ਨੂੰ ਵੱਡੀ ਵਿੰਡੋ ਵਾਲੇ ਕੈਂਡੀਡੇਟਾਂ ਵੱਲ ਰੂਟ ਕਰਦਾ ਹੈ।

```bash
# ਜ਼ੀਰੋ-ਕੰਫਿਗ ਵਰਤੋਂ (ਕੌਂਬੋ ਬਣਾਉਣ ਦੀ ਲੋੜ ਨਹੀਂ)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# ਨਿਯਮਤ ਕੌਂਬੋਜ਼ ਐਂਡਪੌਇੰਟ ਰਾਹੀਂ ਸਥਾਈ ਆਟੋ ਕੌਂਬੋ
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### ਆਟੋ ਰਾਊਟਰ ਰਣਨੀਤੀਆਂ

ਸਥਾਈ `strategy: "auto"` ਕੌਂਬੋ `config.routerStrategy` (ਜਾਂ ਪੁਰਾਣੇ
`config.auto.routerStrategy`) ਨੂੰ ਹੇਠ ਲਿਖਿਆਂ ਵਿੱਚੋਂ ਕਿਸੇ ਇੱਕ ਮੁੱਲ 'ਤੇ ਸੈੱਟ ਕਰ ਸਕਦੇ ਹਨ:

- `rules` — ਡਿਫੌਲਟ ਭਾਰਿਤ ਸਕੋਰਿੰਗ
- `score` — ਸਭ ਤੋਂ ਵੱਧ ਕੰਫਿਗਰ ਕੀਤਾ ਭਾਰਿਤ ਸਕੋਰ ਚੁਣਦਾ ਹੈ। ਬਿਲਕੁਲ ਬਰਾਬਰ ਸਕੋਰ ਹੋਣ 'ਤੇ ਕੰਫਿਗਰ ਕੀਤਾ
  ਕੈਂਡੀਡੇਟ ਕ੍ਰਮ ਬਰਕਰਾਰ ਰਹਿੰਦਾ ਹੈ; ਮੌਜੂਦਾ `explorationRate` ਪੂਰੇ ਰੈਂਕ ਕੀਤੇ ਪੂਲ ਵਿੱਚੋਂ ਨਮੂਨਾ ਚੁਣਦਾ ਹੈ।
- `cost` / `eco` — ਸਭ ਤੋਂ ਸਸਤਾ ਸਿਹਤਮੰਦ ਪ੍ਰੋਵਾਈਡਰ
- `latency` / `fast` — ਭਰੋਸੇਯੋਗਤਾ ਪੈਨਲਟੀ ਦੇ ਨਾਲ ਸਭ ਤੋਂ ਘੱਟ p95 ਲੇਟੈਂਸੀ
- `sla-aware` / `sla` — ਉਹਨਾਂ ਕੈਂਡੀਡੇਟਾਂ ਨੂੰ ਤਰਜੀਹ ਦਿੰਦਾ ਹੈ ਜੋ p95 ਲੇਟੈਂਸੀ, ਗਲਤੀ ਦਰ ਅਤੇ ਵਿਕਲਪਿਕ
  ਲਾਗਤ SLOs ਨੂੰ ਪੂਰਾ ਕਰਦੇ ਹਨ
- `lkgp` — ਆਖਰੀ ਜਾਣਿਆ ਚੰਗਾ ਪ੍ਰੋਵਾਈਡਰ ਪਹਿਲਾਂ
- `nadir` — [Nadir](https://getnadir.com) ਦੇ ਫ਼ੈਸਲਾ API ਤੋਂ ਪੁੱਛਦਾ ਹੈ ਕਿ ਪੂਲ ਵਿੱਚੋਂ ਪ੍ਰੌਂਪਟ ਨੂੰ ਕਿਹੜੇ ਮਾਡਲ ਦੀ
  ਲੋੜ ਹੈ; ਔਪਟ-ਇਨ, ਅਸਫਲ ਹੋਣ 'ਤੇ `rules` ਲਈ ਫੇਲ-ਓਪਨ

### ਰਾਊਟਰ ਰਣਨੀਤੀਆਂ ਦਾ ਵਿਸਥਾਰ

ਆਟੋ-ਕੌਂਬੋ ਇੰਜਣ 7 ਪਲੱਗ ਕਰਨ ਯੋਗ **RouterStrategy** ਇੰਪਲੀਮੈਂਟੇਸ਼ਨ ਉਪਲਬਧ ਕਰਦਾ ਹੈ, ਜਿਨ੍ਹਾਂ ਨੂੰ
ਤੁਸੀਂ `config.routerStrategy` (ਜਾਂ ਪੁਰਾਣੇ `config.auto.routerStrategy`) ਰਾਹੀਂ ਬਦਲ ਸਕਦੇ ਹੋ।
ਹਰੇਕ ਰਣਨੀਤੀ ਇੱਕ `RoutingContext` ਦੇ ਆਧਾਰ 'ਤੇ ਕੈਂਡੀਡੇਟ ਪੂਲ ਵਿੱਚੋਂ ਇੱਕ ਪ੍ਰੋਵਾਈਡਰ ਚੁਣਦੀ ਹੈ
(ਟਾਸਕ ਕਿਸਮ, ਟੂਲ/ਵਿਜ਼ਨ ਸੰਕੇਤ, ਟੋਕਨ ਅਨੁਮਾਨ, ਵਿਕਲਪਿਕ SLA ਨੀਤੀ, ਵਿਕਲਪਿਕ
ਆਖਰੀ-ਜਾਣਿਆ-ਚੰਗਾ ਪ੍ਰੋਵਾਈਡਰ)।

#### 1. `rules` (ਡਿਫੌਲਟ) — 16-ਫੈਕਟਰ ਭਾਰਿਤ ਸਕੋਰਿੰਗ

ਮੌਜੂਦਾ ਸਕੋਰਿੰਗ ਇੰਜਣ ਨੂੰ ਰੈਪ ਕਰਦਾ ਹੈ। `OPEN` ਸਰਕਿਟ-ਬ੍ਰੇਕਰ
ਕੈਂਡੀਡੇਟਾਂ ਨੂੰ ਫਿਲਟਰ ਕਰਦਾ ਹੈ, ਫਿਰ ਮੌਜੂਦਾ ਟਾਸਕ ਕਿਸਮ ਅਤੇ `getTaskFitness()` ਨਾਲ `scorePool()`
ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਸਭ ਤੋਂ ਵੱਧ ਸਕੋਰ ਵਾਲੇ ਪ੍ਰੋਵਾਈਡਰ ਨੂੰ ਚੁਣਦਾ ਹੈ।

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**ਕਦੋਂ ਵਰਤਣਾ ਹੈ**: ਡਿਫੌਲਟ। ਉਦੋਂ ਵਰਤੋ ਜਦੋਂ ਤੁਸੀਂ ਸਾਰੇ ਸਿਗਨਲਾਂ ਵਿਚਕਾਰ ਸੰਤੁਲਿਤ ਸਮਝੌਤਾ ਚਾਹੁੰਦੇ ਹੋ।

**ਉਪਨਾਮ**: `rules` (ਕੋਈ ਉਪਨਾਮ ਨਹੀਂ)

---

#### 2. `cost` / `eco` — ਸਭ ਤੋਂ ਸਸਤਾ ਸਿਹਤਮੰਦ ਪ੍ਰੋਵਾਈਡਰ

ਕੈਂਡੀਡੇਟ ਪੂਲ ਨੂੰ `costPer1MTokens` (ਵਧਦੇ ਕ੍ਰਮ ਵਿੱਚ) ਅਨੁਸਾਰ ਕ੍ਰਮਬੱਧ ਕਰਦਾ ਹੈ ਅਤੇ ਸਭ ਤੋਂ ਸਸਤਾ ਚੁਣਦਾ ਹੈ।
ਪਹਿਲਾਂ `OPEN` ਕੈਂਡੀਡੇਟਾਂ ਨੂੰ ਫਿਲਟਰ ਕਰਦਾ ਹੈ।

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ਕਦੋਂ ਵਰਤਣਾ ਹੈ**: ਲਾਗਤ-ਸੰਵੇਦਨਸ਼ੀਲ ਵਰਕਲੋਡਾਂ, ਬੈਚ ਪ੍ਰੋਸੈਸਿੰਗ ਜਾਂ ਬੈਕਗ੍ਰਾਊਂਡ ਜੌਬਾਂ ਲਈ।

**ਉਪਨਾਮ**: `cost`, `eco`

---

#### 3. `latency` / `fast` — ਭਰੋਸੇਯੋਗਤਾ ਪੈਨਲਟੀ ਦੇ ਨਾਲ ਸਭ ਤੋਂ ਘੱਟ p95 ਲੇਟੈਂਸੀ

`p95LatencyMs + (errorRate * 1000)` ਅਨੁਸਾਰ ਕ੍ਰਮਬੱਧ ਕਰਦਾ ਹੈ। ਗਲਤੀ-ਦਰ ਪੈਨਲਟੀ ਇਹ ਯਕੀਨੀ ਬਣਾਉਂਦੀ ਹੈ
ਕਿ ਗੈਰ-ਭਰੋਸੇਯੋਗ ਪ੍ਰੋਵਾਈਡਰਾਂ ਨੂੰ ਘੱਟ ਰੈਂਕ ਦਿੱਤਾ ਜਾਵੇ, ਭਾਵੇਂ ਉਨ੍ਹਾਂ ਦੀ ਨਾਮਾਤਰ ਲੇਟੈਂਸੀ ਘੱਟ ਹੋਵੇ।

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ਕਦੋਂ ਵਰਤਣਾ ਹੈ**: ਰੀਅਲ-ਟਾਈਮ ਚੈਟ, ਆਟੋਕੰਪਲੀਟ ਜਾਂ
ਇੰਟਰਐਕਟਿਵ ਕੋਡਿੰਗ ਸਹਾਇਕਾਂ ਵਰਗੇ ਲੇਟੈਂਸੀ-ਸੰਵੇਦਨਸ਼ੀਲ ਵਰਕਲੋਡਾਂ ਲਈ।

**ਉਪਨਾਮ**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — ਲੇਟੈਂਸੀ/ਗਲਤੀ/ਲਾਗਤ SLO ਅਨੁਪਾਲਨਾ

ਹਰੇਕ ਕੈਂਡੀਡੇਟ ਨੂੰ ਇਸ ਆਧਾਰ 'ਤੇ ਸਕੋਰ ਕਰਦਾ ਹੈ ਕਿ ਉਹ ਕੰਫਿਗਰ ਕੀਤੀ SLO ਨੀਤੀ ਨੂੰ ਕਿੰਨੀ ਚੰਗੀ ਤਰ੍ਹਾਂ ਪੂਰਾ ਕਰਦਾ ਹੈ:

| ਕਾਰਕ         | ਭਾਰ | ਫ਼ਾਰਮੂਲਾ                                          |
| ------------ | --- | ------------------------------------------------- |
| ਲੇਟੈਂਸੀ ਸਕੋਰ | 35% | `threshold / max(value, ε)`                       |
| ਗਲਤੀ ਸਕੋਰ    | 35% | `threshold / max(value, ε)`                       |
| ਸਿਹਤ ਸਕੋਰ    | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| ਲਾਗਤ ਸਕੋਰ    | 10% | `threshold / max(value, ε)` ਜਾਂ ਉਲਟ ਨਾਰਮਲਾਈਜ਼ਡ    |
| ਸਥਿਰਤਾ ਸਕੋਰ  | 5%  | ਉਲਟ ਨਾਰਮਲਾਈਜ਼ਡ ਲੇਟੈਂਸੀ stddev                     |

ਜਦੋਂ `hardConstraints: true` ਹੁੰਦਾ ਹੈ, ਤਾਂ ਉਮੀਦਵਾਰਾਂ ਨੂੰ ਮੁੱਖ ਤੌਰ 'ਤੇ **ਉਲੰਘਣਾ ਸਕੋਰ**
(ਉਹ ਕਿਸੇ SLO ਤੋਂ ਕਿੰਨਾ ਵੱਧ ਜਾਂਦੇ ਹਨ), ਅਤੇ ਫਿਰ ਸੰਯੁਕਤ ਸਕੋਰ ਅਨੁਸਾਰ ਕ੍ਰਮਬੱਧ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਨਹੀਂ ਤਾਂ ਸਿਰਫ਼
ਸੰਯੁਕਤ ਸਕੋਰ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ।

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... ਹਰ ਉਮੀਦਵਾਰ ਨੂੰ ਨੀਤੀ ਦੇ ਮੁਕਾਬਲੇ ਸਕੋਰ ਕਰਦਾ ਹੈ: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA ਫ਼ੀਲਡਾਂ** (ਕੌਂਬੋ ਸੰਰਚਨਾ ਵਿੱਚ ਸੈੱਟ ਕੀਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**ਕਦੋਂ ਵਰਤਣਾ ਹੈ**: ਸਖ਼ਤ ਲੇਟੈਂਸੀ, ਗਲਤੀ-ਦਰ ਜਾਂ ਲਾਗਤ ਬਜਟਾਂ ਵਾਲੇ ਪ੍ਰੋਡਕਸ਼ਨ ਵਰਕਲੋਡਾਂ ਲਈ।

**ਉਪਨਾਮ**: `sla-aware`, `sla`

---

#### 5. `lkgp` — ਆਖਰੀ ਜਾਣਿਆ-ਪਛਾਣਿਆ ਚੰਗਾ ਪ੍ਰਦਾਤਾ ਪਹਿਲਾਂ

ਪਹਿਲਾਂ **ਆਖਰੀ ਜਾਣਿਆ-ਪਛਾਣਿਆ ਚੰਗਾ ਪ੍ਰਦਾਤਾ** (ਜੇ ਸੈੱਟ ਕੀਤਾ ਹੋਵੇ) ਅਜ਼ਮਾਉਂਦਾ ਹੈ, ਫਿਰ
`rules` ਰਣਨੀਤੀ 'ਤੇ ਵਾਪਸ ਜਾਂਦਾ ਹੈ। ਇਹ ਸੈਸ਼ਨ ਸਟਿੱਕੀਨੈੱਸ ਲਈ ਲਾਭਦਾਇਕ ਹੈ — ਇੱਕੋ ਪ੍ਰਦਾਤਾ
ਗੱਲਬਾਤ ਵਿੱਚ ਅਗਲੀਆਂ ਬੇਨਤੀਆਂ ਨੂੰ ਸੰਭਾਲਦਾ ਹੈ।

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // ਵਾਪਸੀ ਲਈ rules ਰਣਨੀਤੀ ਵਰਤੋ
    return getStrategy("rules").select(pool, context);
  }
}
```

**ਕਦੋਂ ਵਰਤਣਾ ਹੈ**: ਬਹੁ-ਵਾਰੀ ਗੱਲਬਾਤਾਂ ਵਿੱਚ, ਜਿੱਥੇ ਤੁਸੀਂ ਚਾਹੁੰਦੇ ਹੋ ਕਿ ਉਹੀ ਪ੍ਰਦਾਤਾ
ਅਗਲੀਆਂ ਬੇਨਤੀਆਂ ਨੂੰ ਸੰਭਾਲੇ (ਉਦਾਹਰਨ ਲਈ, ਕੈਸ਼ਿੰਗ, ਸੰਦਰਭ ਨਿਰੰਤਰਤਾ ਜਾਂ ਕੀਮਤ ਇਕਸਾਰਤਾ ਵਾਸਤੇ)।

**ਉਪਨਾਮ**: `lkgp` (ਕੋਈ ਉਪਨਾਮ ਨਹੀਂ)

---

#### 6. `nadir` — Nadir ਰਾਹੀਂ ਪ੍ਰੌਂਪਟ-ਅਵੇਅਰ ਮਾਡਲ ਚੋਣ

ਉੱਪਰ ਦਿੱਤੀ ਹਰ ਰਣਨੀਤੀ ਉਮੀਦਵਾਰਾਂ ਨੂੰ ਆਪਣੀ ਟੈਲੀਮੈਟਰੀ ਅਨੁਸਾਰ ਦਰਜਾ ਦਿੰਦੀ ਹੈ; ਉਨ੍ਹਾਂ ਵਿੱਚੋਂ ਕੋਈ ਵੀ
ਬੇਨਤੀ ਨੂੰ ਨਹੀਂ ਪੜ੍ਹਦੀ। `nadir` ਆਖਰੀ ਯੂਜ਼ਰ ਟਰਨ ਅਤੇ ਪੂਲ ਦੇ ਮਾਡਲ ids ਨੂੰ
[Nadir](https://getnadir.com) ਦੇ ਫ਼ੈਸਲਾ API (`POST /v1/bucket`) ਨੂੰ ਭੇਜਦਾ ਹੈ ਅਤੇ Nadir ਵੱਲੋਂ
ਉਸ ਮੀਨੂ ਵਿੱਚੋਂ ਚੁਣੇ ਮਾਡਲ ਵੱਲ ਰੂਟ ਕਰਦਾ ਹੈ (`simple` → ਸਭ ਤੋਂ ਸਸਤਾ ਸਮਰੱਥ ਮਾਡਲ, `complex` →
ਫਰੰਟੀਅਰ ਮਾਡਲ)। ਉਸ ਮਾਡਲ ਨੂੰ ਸਰਵ ਕਰਨ ਵਾਲਾ ਕਨੈਕਸ਼ਨ ਫਿਰ ਵੀ `rules` ਵੱਲੋਂ ਚੁਣਿਆ ਜਾਂਦਾ ਹੈ, ਇਸ ਲਈ ਕੋਟਾ,
ਸਿਹਤ ਅਤੇ ਲਾਗਤ ਇਹ ਨਿਰਧਾਰਤ ਕਰਦੇ ਰਹਿੰਦੇ ਹਨ ਕਿ ਕਿਹੜਾ ਖਾਤਾ ਵਰਤਿਆ ਜਾਵੇ।

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` ਅਤੇ `OMNIROUTE_NADIR_BASE_URL` ਇਨ੍ਹਾਂ ਦੋ
ਸਟਰਿੰਗਾਂ ਲਈ env ਫਾਲਬੈਕ ਹਨ। `baseUrl` ਦੀ ਲੋੜ ਸਿਰਫ਼ ਸਵੈ-ਹੋਸਟ ਕੀਤੇ Nadir ਲਈ ਹੁੰਦੀ ਹੈ (ਅੰਤ ਵਿੱਚ `/v1` ਸਵੀਕਾਰਯੋਗ ਹੈ)।
ਬਿਨਾਂ ਕੁੰਜੀ ਵਾਲੀਆਂ ਕਾਲਾਂ Nadir ਦੇ ਅਗਿਆਤ ਟੀਅਰ 'ਤੇ ਜਾਂਦੀਆਂ ਹਨ, ਜਿਸ ਦੀ ਦਰ ਪ੍ਰਤੀ IP ਸੀਮਿਤ ਹੈ।

ਬਾਕਸ ਤੋਂ ਬਾਹਰ ਕੀ ਜਾਂਦਾ ਹੈ: ਆਖਰੀ ਯੂਜ਼ਰ ਸੁਨੇਹੇ ਦਾ ਟੈਕਸਟ (ਪਹਿਲੇ 16k ਅੱਖਰ), ਉਮੀਦਵਾਰ
ਮਾਡਲ ids ਅਤੇ ਇੱਕ `source: "omniroute"` ਚੈਨਲ ਟੈਗ। ਕੋਈ ਸਿਸਟਮ ਪ੍ਰੌਂਪਟ, ਇਤਿਹਾਸ, ਟੂਲ ਜਾਂ
ਹੈਡਰ ਨਹੀਂ।

ਅਸਫਲਤਾ ਵਿਹਾਰ fail-open ਹੈ: ਇੱਕ ਟਾਈਮਆਉਟ (ਡਿਫੌਲਟ 2000 ms), ਇੱਕ non-2xx, ਪਹੁੰਚ ਤੋਂ ਬਾਹਰ
ਹੋਸਟ, ਗਲਤ-ਰੂਪ ਵਾਲਾ ਜਵਾਬ ਜਾਂ ਪੂਲ ਤੋਂ ਬਾਹਰ ਦੀ ਚੋਣ `rules`
ਫ਼ੈਸਲੇ 'ਤੇ ਵਾਪਸ ਜਾਂਦੀ ਹੈ ਅਤੇ ਕਾਰਨ ਦੇ ਅੱਗੇ `NadirStrategy: fallback (…)` ਜੋੜਿਆ ਜਾਂਦਾ ਹੈ। ਇੱਕ ਅਸਫਲ ਕਾਲ ਤੋਂ ਬਾਅਦ
ਰਣਨੀਤੀ 30 s ਲਈ ਨੈੱਟਵਰਕ ਨੂੰ ਛੱਡ ਦਿੰਦੀ ਹੈ, ਇਸ ਲਈ ਆਊਟੇਜ ਦੌਰਾਨ ਹਰ ਬੇਨਤੀ ਦੀ ਬਜਾਏ
ਹਰ 30 s ਵਿੱਚ ਇੱਕ ਟਾਈਮਆਉਟ ਦੀ ਲਾਗਤ ਪੈਂਦੀ ਹੈ। ਰੂਟਿੰਗ ਇਵੈਂਟ `strategy: "nadir"` ਦੀ ਰਿਪੋਰਟ ਸਿਰਫ਼ ਉਦੋਂ ਕਰਦੇ ਹਨ ਜਦੋਂ Nadir ਨੇ ਅਸਲ ਵਿੱਚ
ਚੋਣ ਕੀਤੀ ਹੋਵੇ।

**ਕਦੋਂ ਵਰਤਣਾ ਹੈ**: ਵੱਖ-ਵੱਖ ਮੁਸ਼ਕਲ ਪੱਧਰ ਵਾਲਾ ਟ੍ਰੈਫਿਕ, ਅਜਿਹੇ ਪੂਲ 'ਤੇ ਜੋ ਮਾਡਲ ਟੀਅਰਾਂ ਵਿੱਚ ਫੈਲਿਆ ਹੋਵੇ (ਇੱਕ ਛੋਟਾ, ਇੱਕ ਮੱਧਮ
ਅਤੇ ਇੱਕ ਫਰੰਟੀਅਰ ਮਾਡਲ), ਜਿੱਥੇ ਹਮੇਸ਼ਾ-ਫਰੰਟੀਅਰ ਵਰਤਣ ਦੀ ਲਾਗਤ ਨੂੰ ਤੁਸੀਂ ਘਟਾਉਣਾ ਚਾਹੁੰਦੇ ਹੋ।

### ਕਸਟਮ ਰਾਊਟਰ ਰਣਨੀਤੀਆਂ

ਤੁਸੀਂ ਪਬਲਿਕ API ਰਾਹੀਂ ਆਪਣਾ `RouterStrategy` ਇੰਪਲੀਮੈਂਟੇਸ਼ਨ ਰਜਿਸਟਰ ਕਰ ਸਕਦੇ ਹੋ:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // ਆਪਣਾ ਰੂਟਿੰਗ ਤਰਕ ਇੱਥੇ ਲਿਖੋ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

ਫਿਰ ਇਸਨੂੰ ਵਰਤੋ:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## ਟਾਸਕ ਅਨੁਕੂਲਤਾ

6 ਟਾਸਕ ਕਿਸਮਾਂ (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) ਵਿੱਚ 30+ ਮਾਡਲਾਂ ਨੂੰ ਸਕੋਰ ਦਿੱਤਾ ਗਿਆ ਹੈ। ਵਾਈਲਡਕਾਰਡ ਪੈਟਰਨਾਂ ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ (ਉਦਾਹਰਨ ਲਈ, `*-coder` → ਉੱਚ coding ਸਕੋਰ)।

## Auto ਵੇਰੀਐਂਟਾਂ ਦਾ ਸੰਖੇਪ

ਮੂਲ `auto` (ਡਿਫੌਲਟ) ਸਮੇਤ ਅਤੇ `autoPrefix.ts` ਵਿੱਚ ਘੋਸ਼ਿਤ 6 `AutoVariant` ਮੁੱਲਾਂ ਨੂੰ ਜੋੜ ਕੇ, ਕੁੱਲ **7 ਵਰਤੋਂਯੋਗ ਮਾਡਲ IDs** ਹਨ:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ਖੁਦ 6 ਮੁੱਲ ਦਰਸਾਉਂਦਾ ਹੈ; 7ਵਾਂ ਵਿਕਲਪ "ਕੋਈ ਵੇਰੀਐਂਟ ਨਹੀਂ" ਹੈ — ਮੂਲ `auto` — ਜਿਸਨੂੰ `parseAutoPrefix()` ਵੱਲੋਂ `variant: undefined` ਵਜੋਂ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ।)

## ਟੀਅਰ Auto-Combo ਵਿੱਚ ਕਿਵੇਂ ਫਿੱਟ ਹੁੰਦੇ ਹਨ

16-ਫੈਕਟਰ ਸਕੋਰਿੰਗ ਫੰਕਸ਼ਨ (`open-sse/services/autoCombo/scoring.ts`) ਟੀਅਰ
ਮੈਂਬਰਸ਼ਿਪ ਨੂੰ ਦੋ ਸੰਕੇਤਾਂ ਵਜੋਂ ਵਰਤਦਾ ਹੈ: `tierPriority` (0.0476) ਅਤੇ `tierAffinity` (0.0476)। ਪੂਰੇ
`DEFAULT_WEIGHTS` ਸੈੱਟ ਲਈ ਉੱਪਰ ਦਿੱਤੀ ਮਿਆਰੀ [ਸਕੋਰਿੰਗ ਫੈਕਟਰ ਸਾਰਣੀ](#how-it-works-persisted-auto-combos) ਵੇਖੋ — ਹਰ ਪੈਕ ਲਈ ਓਵਰਰਾਈਡ (ship-fast/cost-saver/quality-first/
offline-friendly) "ਹਰ ਪੈਕ ਲਈ ਵਜ਼ਨ ਪ੍ਰੋਫਾਈਲਾਂ" ਸਾਰਣੀ ਵਿੱਚ ਦਿੱਤੇ ਗਏ ਹਨ।

ਇਕੱਲਾ ਟੀਅਰ, ਟੀਅਰ 1 ਨੂੰ ਪਹਿਲਾਂ ਆਉਣ ਲਈ **ਮਜਬੂਰ ਨਹੀਂ** ਕਰਦਾ — ਜੇ ਟੀਅਰ 1 ਦੀ ਲੇਟੈਂਸੀ ਮਾੜੀ ਹੈ ਜਾਂ
ਲਾਗਤ-ਬਨਾਮ-ਗੁਣਵੱਤਾ ਉਚਿਤ ਨਹੀਂ ਹੈ, ਤਾਂ ਟੀਅਰ 2 ਜਿੱਤਦਾ ਹੈ। ਟੀਅਰ ਕ੍ਰਮ ਨੂੰ ਲਾਜ਼ਮੀ ਬਣਾਉਣ ਲਈ, ਕੰਬੋ
ਰਣਨੀਤੀ `priority` ਵਰਤੋ ਅਤੇ ਪ੍ਰਦਾਤਾਵਾਂ ਨੂੰ ਟੀਅਰ ਅਨੁਸਾਰ ਵਿਵਸਥਿਤ ਕਰੋ।

ਟੀਅਰ 1 (ਸਬਸਕ੍ਰਿਪਸ਼ਨ) ਨੂੰ ਮਜ਼ਬੂਤੀ ਨਾਲ ਤਰਜੀਹ ਦੇਣ ਲਈ, `tierPriority` ਦਾ ਵਜ਼ਨ ਵਧਾਓ:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

ਟੀਅਰ ਪਰਿਭਾਸ਼ਾਵਾਂ ਅਤੇ ਪ੍ਰਦਾਤਾ ਵਰਗੀਕਰਨ ਲਈ [`docs/guides/TIERS.md`](../guides/TIERS.md) ਵੇਖੋ।

## ਟੈਸਟਿੰਗ ਅਤੇ ਕਵਰੇਜ

### ਨਿਰਧਾਰਿਤ ਰਾਊਟਿੰਗ-ਫੈਸਲਾ ਮੈਟ੍ਰਿਕਸ (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` ਇੱਕ ਮੌਕ ਕੀਤੇ ਅੱਪਸਟ੍ਰੀਮ ਨਾਲ ਅਸਲ ਕੌਂਬੋ ਪਾਈਪਲਾਈਨ ਰਾਹੀਂ ਸਾਰੀਆਂ 19
ਜਨਤਕ ਰਣਨੀਤੀਆਂ ਦੇ ਰਾਊਟਿੰਗ **ਫੈਸਲੇ** ਨੂੰ ਐਂਡ-ਟੂ-ਐਂਡ ਸਾਬਤ ਕਰਦਾ ਹੈ।
ਕਵਰੇਜ ਵਿੱਚ ਸ਼ਾਮਲ ਹਨ:

- ਸਾਰੀਆਂ 19 `ROUTING_STRATEGY_VALUES` ਰਣਨੀਤੀਆਂ (ordered, weighted, cost, context, fusion, …)।
- `quota-share` (ਅੰਦਰੂਨੀ) ਐਂਡ-ਟੂ-ਐਂਡ: ਅਸਲ
  `selectQuotaShareTarget` ਸੀਮ (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`) ਰਾਹੀਂ DRR ਨਿਰਪੱਖਤਾ + ਸੈਚੂਰੇਸ਼ਨ ਡੀਪ੍ਰਾਇਰਟੀਕਰਨ।
- ਹਰ ਟਾਰਗੇਟ ਗਿਣਤੀ ਲਈ `context-relay` ਯੂਨੀਵਰਸਲ-ਹੈਂਡਆਫ਼ ਕਵਰੇਜ।

ਇਹ ਸੂਟ CI (`test:integration` ਜੌਬ) ਵਿੱਚ `--test-concurrency=1` ਅਤੇ
`--test-force-exit` ਨਾਲ ਚੱਲਦਾ ਹੈ, ਇਸ ਲਈ ਇਹ ਨਿਰਧਾਰਿਤ ਹੈ ਅਤੇ ਇਸਨੂੰ ਲਾਈਵ ਕ੍ਰੈਡੈਂਸ਼ਲਾਂ ਦੀ ਲੋੜ ਨਹੀਂ ਹੁੰਦੀ।

### ਗੇਟ ਕੀਤੇ ਲਾਈਵ ਸਮੋਕ ਟੈਸਟ (CI ਵਿੱਚ ਨਹੀਂ — ਅਸਲ ਪ੍ਰਦਾਤਾ)

| ਕਮਾਂਡ                                  | ਇਹ ਕੀ ਕਰਦੀ ਹੈ                                                                         |
| :------------------------------------- | :------------------------------------------------------------------------------------ |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` ਨਾਲ ਇਨ-ਪ੍ਰੋਸੈਸ ਅਸਲ ਰਾਊਟਿੰਗ; ਲਾਈਵ OmniRoute DB ਦਾ ਸਨੈਪਸ਼ਾਟ ਲੈਂਦੀ ਹੈ |
| `npm run test:combo:live:vps`          | ਲਾਈਵ OmniRoute ਸਰਵਰ ਵਿਰੁੱਧ HTTP ਕਾਲਾਂ (`COMBO_LIVE_BASE_URL` ਸੈੱਟ ਕਰੋ)                |
| `npm run test:combo:live:vps:failover` | ਇਹੀ, ਜਾਣ-ਬੁੱਝ ਕੇ ਬਣਾਏ ਗਏ ਫੇਲਓਵਰ ਦ੍ਰਿਸ਼ਾਂ ਨਾਲ                                          |

ਇਹ ਸਮੋਕ ਟੈਸਟ ਅਸਲ ਵਾਇਰ ਪਾਥ (ਕੌਂਬੋ → ਪ੍ਰਦਾਤਾ → ਕੰਪਲੀਸ਼ਨ) ਦੀ ਜਾਂਚ ਕਰਦੇ ਹਨ। ਇਨ੍ਹਾਂ ਨੂੰ
ਜਾਣ-ਬੁੱਝ ਕੇ CI ਤੋਂ ਬਾਹਰ ਰੱਖਿਆ ਗਿਆ ਹੈ ਕਿਉਂਕਿ ਇਨ੍ਹਾਂ ਲਈ ਲਾਈਵ ਕ੍ਰੈਡੈਂਸ਼ਲਾਂ ਅਤੇ VPS ਪਹੁੰਚ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।
