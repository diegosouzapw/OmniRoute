> ਦੋ ਨਵੀਆਂ `auto/*` ids — `auto/subscription` ਅਤੇ `auto/thrifty`। ਦੋਵੇਂ ਬੇਨਤੀ ਕੀਤੇ ਜਾਣ ਰਾਹੀਂ opt-in ਹਨ:
> ਜਦੋਂ ਤੱਕ ਕੋਈ caller ਨਾਮ ਰਾਹੀਂ id ਦੀ ਮੰਗ ਨਹੀਂ ਕਰਦਾ, ਉਨ੍ਹਾਂ ਵਿੱਚੋਂ ਕੁਝ ਵੀ route ਨਹੀਂ ਹੁੰਦਾ, ਅਤੇ ਕਿਸੇ
> ਮੌਜੂਦਾ pool, strategy, ਜਾਂ default ਵਿੱਚ ਕੋਈ ਬਦਲਾਅ ਨਹੀਂ ਹੁੰਦਾ।

## ਇਹ ਕਿਉਂ ਮੌਜੂਦ ਹੈ

OmniRoute ਪਹਿਲਾਂ ਹੀ ਲਾਗਤ ਸੰਬੰਧੀ ਦੋ ਸਵਾਲਾਂ ਦੇ ਜਵਾਬ ਦਿੰਦਾ ਹੈ, ਪਰ ਦੋਵਾਂ ਵਿੱਚੋਂ ਕੋਈ ਵੀ ਉਹ ਸਵਾਲ ਨਹੀਂ ਹੈ ਜੋ ਜ਼ਿਆਦਾਤਰ operators ਪੁੱਛਦੇ ਹਨ।

| ਮੌਜੂਦਾ ਵਿਧੀ                                              | ਜਿਸਦਾ ਜਵਾਬ ਦਿੰਦੀ ਹੈ                            |
| -------------------------------------------------------- | ---------------------------------------------- |
| `hidePaidModels` (`autoCombo/paidModelFilter.ts`)        | "ਕੀ ਇਹ model catalog ਵਿੱਚ ਮੁਫ਼ਤ ਵਜੋਂ ਦਰਜ ਹੈ?"  |
| `freeAccessPolicy: "strict"` (`strictZeroCostFilter.ts`) | "ਕੀ ਇਹ connection ਕਦੇ ਮੈਨੂੰ bill ਕਰ ਸਕਦਾ ਹੈ?"  |
| `quotaPreflight` (`combo/quotaExhaustionCutoff.ts`)      | "ਕੀ ਇਹ connection ਆਪਣੀ ਹੱਦ ਦੇ ਨੇੜੇ ਹੈ?"        |
| `budgetCap` / `budgetFallback` (`autoCombo/engine.ts`)   | "ਖਰਚ ਨੂੰ ਸੀਮਿਤ ਕਰੋ, ਸਭ ਤੋਂ ਸਸਤੇ ਵਿਕਲਪ ਵੱਲ ਜਾਓ" |

ਹਰ ਸਿਰਫ਼-ਮੁਫ਼ਤ ਵਿਧੀ **fails closed** ਹੁੰਦੀ ਹੈ — ਖ਼ਤਮ ਹੋਇਆ ਮੁਫ਼ਤ pool ਇੱਕ ਖਾਲੀ pool ਹੁੰਦਾ ਹੈ, ਕਦੇ ਵੀ
ਕਿਸੇ ਭੁਗਤਾਨਯੋਗ ਵਿਕਲਪ ਵੱਲ ਉੱਪਰਲਾ ਕਦਮ ਨਹੀਂ — ਅਤੇ ਭੁਗਤਾਨ ਵਾਲੇ ਪਾਸੇ ਦੀ ਹਰ ਵਿਧੀ tier ਤੋਂ ਅਗਿਆਤ ਹੁੰਦੀ ਹੈ। ਕੋਈ ਵੀ ਇਸਦਾ ਜਵਾਬ ਨਹੀਂ ਦਿੰਦੀ:

> "ਉਹ quota ਵਰਤੋ ਜਿਸ ਲਈ ਮੈਂ ਪਹਿਲਾਂ ਹੀ ਭੁਗਤਾਨ ਕਰਦਾ ਹਾਂ। ਜਦੋਂ ਇਹ ਖ਼ਤਮ ਹੋ ਜਾਵੇ, ਤਾਂ ਜਾਂ ਰੁਕ ਜਾਓ, ਜਾਂ
> ਸਭ ਤੋਂ ਸਸਤੇ ਭੁਗਤਾਨਯੋਗ ਵਿਕਲਪਾਂ ਵਿੱਚੋਂ ਇੱਕ ਸਮੇਂ ਇੱਕ ਪੌੜੀ ਉੱਪਰ ਜਾਓ — ਅਤੇ ਇਸਦੇ reset ਹੁੰਦਿਆਂ ਹੀ ਵਾਪਸ ਆ ਜਾਓ।"

## Billing, model ਦੀ ਨਹੀਂ, connection ਦੀ ਵਿਸ਼ੇਸ਼ਤਾ ਹੈ

`classifyTier()` (`open-sse/services/tierResolver.ts`) `(provider, model)` ਨੂੰ key ਵਜੋਂ ਵਰਤਦਾ ਹੈ ਅਤੇ
catalog pricing ਤੋਂ `free | cheap | premium` ਵਾਪਸ ਕਰਦਾ ਹੈ। ਪਰ ਕੋਈ request ਵਾਧੂ ਪੈਸਾ ਖਰਚਦੀ ਹੈ ਜਾਂ ਨਹੀਂ,
ਇਹ ਇਸ ਗੱਲ 'ਤੇ ਨਿਰਭਰ ਕਰਦਾ ਹੈ ਕਿ **ਕਿਹੜਾ connection ਇਸਨੂੰ serve ਕਰਦਾ ਹੈ**: ਉਹੀ model Claude Code
OAuth connection ਰਾਹੀਂ plan ਵਿੱਚ ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ ਅਤੇ API-key connection ਰਾਹੀਂ ਪ੍ਰਤੀ token bill ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

`provider_connections.auth_type` ਕਿਸੇ ਵੀ ਦਿਸ਼ਾ ਵਿੱਚ ਇੱਕ ਸੁਰੱਖਿਅਤ proxy ਨਹੀਂ ਹੈ — metered OAuth
connections ਮੌਜੂਦ ਹਨ, ਅਤੇ plan ਵਿੱਚ ਸ਼ਾਮਲ API-key connections ਵੀ ਮੌਜੂਦ ਹਨ (Copilot seat token ਕੋਈ
metered API key ਨਹੀਂ ਹੈ)। ਇਸ ਲਈ billing class ਇੱਕ **ਹੱਥੀਂ ਸੰਭਾਲੇ catalog**,
`open-sse/config/connectionBillingCatalog.ts`, ਤੋਂ ਆਉਂਦੀ ਹੈ, ਜਿਸਨੂੰ ਹਰ provider ਦੀਆਂ ਪ੍ਰਕਾਸ਼ਿਤ ਸ਼ਰਤਾਂ ਦੇ ਆਧਾਰ 'ਤੇ
ਹੱਥੀਂ ਸੈੱਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ — ਉਹੀ pattern ਜੋ `FreeModelBudget.hardStopGuaranteed` ਨੇ ਮੁਫ਼ਤ models ਲਈ ਪਹਿਲਾਂ ਹੀ ਸਥਾਪਤ ਕੀਤਾ ਹੈ।

```ts
type ConnectionBillingClass = "subscription" | "metered" | "keyless" | "unknown";
type ConnectionOverageBehavior = "hard-stop" | "meters-to-paid" | "unknown";
```

Resolution ਕ੍ਰਮ (`autoCombo/connectionBilling.ts`): synthetic no-auth sentinel →
`keyless`; provider **ਅਤੇ** `authType` ਨਾਲ ਮੇਲ ਖਾਂਦੀ catalog entry; provider-ਵਿਆਪੀ entry;
ਨਹੀਂ ਤਾਂ `unknown`। **ਜਿਸਨੂੰ catalog ਵਿੱਚ ਹੱਥੀਂ ਸ਼ਾਮਲ ਨਹੀਂ ਕੀਤਾ ਗਿਆ, ਉਹ ਮੁਫ਼ਤ ਨਹੀਂ ਹੈ** — `unknown` ਨੂੰ ਹਰ ਥਾਂ `metered`
ਵਜੋਂ ਵਰਤਿਆ ਜਾਂਦਾ ਹੈ, ਇਸ ਲਈ ਕੱਲ੍ਹ ਜੋੜਿਆ ਗਿਆ provider subscription ਪੌੜੀ ਤੋਂ ਬਾਹਰ ਸ਼ੁਰੂ ਹੁੰਦਾ ਹੈ ਅਤੇ ਉਸਨੂੰ
ਜਾਣ-ਬੁੱਝ ਕੇ catalog ਵਿੱਚ ਸ਼ਾਮਲ ਕਰਨਾ ਪੈਂਦਾ ਹੈ।

## ਪੌੜੀ ਮਾਡਲ

escalation ਕ੍ਰਮ ਵਿੱਚ ਪੰਜ ਪੌੜੀਆਂ। ਉਹ ਸਿਰਫ਼ ਕੀਮਤ ਤੋਂ ਵੱਧ ਮਾਮਲਿਆਂ ਵਿੱਚ ਵੱਖਰੀਆਂ ਹਨ — ਹਰੇਕ ਦਾ ਆਪਣਾ
**exhaustion signal** ਹੈ, ਇਸ ਲਈ ਇਹ ਸਿਰਫ਼ ਇੱਕ sort ਨਹੀਂ ਹੈ।

| #   | ਪੌੜੀ           | ਮੈਂਬਰਸ਼ਿਪ                                          | ਖ਼ਤਮ ਮੰਨੀ ਜਾਂਦੀ ਹੈ ਜਦੋਂ                       |
| --- | -------------- | -------------------------------------------------- | --------------------------------------------- |
| 0   | `subscription` | ਹੱਥੀਂ ਦਰਜ `billing: "subscription"`                | quota window cutoff 'ਤੇ ਜਾਂ ਉਸ ਤੋਂ ਹੇਠਾਂ ਹੋਵੇ |
| 1   | `keyless`      | synthetic no-auth path                             | connection cooldown / breaker                 |
| 2   | `free`         | metered connection, `classifyTier() === "free"`    | ਮੁਫ਼ਤ allowance ਖ਼ਤਮ ਹੋ ਜਾਵੇ                  |
| 3   | `cheap`        | metered connection, `classifyTier() === "cheap"`   | ਪ੍ਰਤੀ-ਪੌੜੀ budget ਵਰਤਿਆ ਜਾਵੇ                  |
| 4   | `premium`      | metered connection, `classifyTier() === "premium"` | ਪ੍ਰਤੀ-ਪੌੜੀ budget ਵਰਤਿਆ ਜਾਵੇ                  |

ਪੌੜੀਆਂ 0-2 **quota** 'ਤੇ ਖ਼ਤਮ ਹੁੰਦੀਆਂ ਹਨ, ਜੋ ਦੇਖਣਯੋਗ ਹੈ ਅਤੇ ਪਹਿਲਾਂ ਹੀ track ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਪੌੜੀਆਂ 3-4 ਲਈ ਕੋਈ
quota ਨਹੀਂ ਹੁੰਦਾ — ਇੱਕ paid connection ਹਮੇਸ਼ਾ serve ਕਰਦਾ ਰਹਿੰਦਾ ਹੈ — ਇਸ ਲਈ ਉਨ੍ਹਾਂ ਦਾ ਇੱਕੋ-ਇੱਕ ਵਾਜਬ exhaustion signal ਪ੍ਰਤੀ-ਪੌੜੀ
**budget** ਹੈ। ਇਸ ਤੋਂ ਬਿਨਾਂ, "ਜਦੋਂ cheap ਖ਼ਤਮ ਹੋ ਜਾਵੇ ਤਾਂ escalate ਕਰੋ" ਲਈ ਕੋਈ trigger ਨਹੀਂ ਹੈ।

## `auto/subscription` — ਬੰਦ ਰਹਿ ਕੇ ਅਸਫਲ ਹੋਣਾ

ਪੂਲ = ਸਿਰਫ਼ ਪੌੜੀ 0, ਕੇਵਲ ਉਹਨਾਂ ਕਨੈਕਸ਼ਨਾਂ ਤੱਕ ਸੀਮਤ ਜਿਨ੍ਹਾਂ ਦਾ ਵਾਧੂ ਉਪਯੋਗ ਇੱਕ ਦਸਤਾਵੇਜ਼ਬੱਧ `hard-stop` ਹੈ, ਅਤੇ
ਹਰੇਕ ਦੀ ਲਾਈਵ ਤਸਦੀਕ ਕੀਤੀ ਗਈ ਹੈ ਕਿ ਉਸ ਵਿੱਚ ਕੋਟੇ ਦੀ ਵਾਧੂ ਗੁੰਜਾਇਸ਼ ਮੌਜੂਦ ਹੈ। ਹਰ ਅਸਪਸ਼ਟ ਚੀਜ਼ ਨੂੰ ਬਾਹਰ ਰੱਖਿਆ ਜਾਂਦਾ ਹੈ: ਇੱਕ ਗੈਰ-ਕਿਊਰੇਟ ਕੀਤਾ ਪ੍ਰਦਾਤਾ,
ਇੱਕ ਅਪ੍ਰਮਾਣਿਤ ਕੋਟਾ ਰੀਡਿੰਗ, ਇੱਕ ਪੁਰਾਣੀ ਰੀਡਿੰਗ, ਜਾਂ ਅਜਿਹਾ ਵਾਧੂ ਉਪਯੋਗ ਜਿਸਦਾ ਮੀਟਰ ਭੁਗਤਾਨਯੋਗ ਵਰਤੋਂ ਵਜੋਂ ਚੱਲਦਾ ਹੈ।

ਇੱਕ ਖਾਲੀ ਪੂਲ **ਇੱਛਿਤ** ਜਵਾਬ ਹੈ, ਕੋਈ ਖਾਮੀ ਨਹੀਂ — ਕਾਲਰ ਦਾ ਮੌਜੂਦਾ ਖਾਲੀ-ਪੂਲ ਪਾਥ
ਇਸਨੂੰ ਇੱਕ ਚੁੱਪ, ਬਿਲਯੋਗ ਫਾਲਬੈਕ ਦੀ ਬਜਾਏ ਇੱਕ ਸਪਸ਼ਟ ਗਲਤੀ ਵਿੱਚ ਬਦਲ ਦਿੰਦਾ ਹੈ। ਇਹੀ ਇਸ id ਦਾ ਪੂਰਾ
ਵਾਅਦਾ ਹੈ।

`keyless` ਜਾਣਬੁੱਝ ਕੇ ਯੋਗ **ਨਹੀਂ** ਹੈ: ਇਸ ਗਰੁੱਪਿੰਗ ਦਾ ਅਰਥ ਹੈ "ਉਹ ਪਲਾਨ ਜਿਸ ਲਈ ਮੈਂ ਭੁਗਤਾਨ ਕਰਦਾ ਹਾਂ", ਇਸ ਲਈ ਇੱਕ
ਬਿਨਾਂ-ਪ੍ਰਮਾਣੀਕਰਨ ਵਾਲਾ ਬੈਕਐਂਡ ਇਸ ਵਿੱਚ ਸ਼ਾਮਲ ਨਹੀਂ ਹੁੰਦਾ। ਇਸ ਲਈ `auto/thrifty` (ਜਾਂ `auto/best-free`) ਵਰਤੋ।

### ਕਨੈਕਸ਼ਨ ਸੁਰੱਖਿਆ

ਇੱਕ ਉਮੀਦਵਾਰ ਹਮੇਸ਼ਾ ਕੇਵਲ ਇੱਕ ਕਨੈਕਸ਼ਨ ਨਾਲ ਬੱਝਿਆ ਨਹੀਂ ਹੁੰਦਾ — ਇੱਕ ਲੌਜਿਕਲ ਉਮੀਦਵਾਰ ਕੋਲ
`allowedConnectionIds` ਅਲਾਊਲਿਸਟ ਹੁੰਦੀ ਹੈ, ਅਤੇ ਅਸਲ ਵਿੱਚ ਵਰਤਿਆ ਜਾਣ ਵਾਲਾ ਖਾਤਾ ਬਾਅਦ ਵਿੱਚ, ਡਿਸਪੈਚ ਸਮੇਂ,
`open-sse/services/combo/autoStrategy.ts` ਦੁਆਰਾ ਚੁਣਿਆ ਜਾਂਦਾ ਹੈ। ਇਸ ਲਈ ਦੋਵੇਂ ਗਰੁੱਪਿੰਗਾਂ **ਹਰੇਕ ਕਨੈਕਸ਼ਨ ਦੀ
ਵੱਖਰੇ ਤੌਰ 'ਤੇ** ਤਸਦੀਕ ਕਰਦੀਆਂ ਹਨ ਅਤੇ `allowedConnectionIds` ਨੂੰ ਮੁੜ ਲਿਖ ਕੇ ਬਿਲਕੁਲ ਬਚੇ ਹੋਏ ਸਬਸੈੱਟ ਤੱਕ ਸੀਮਤ ਕਰਦੀਆਂ ਹਨ — ਕਦੇ ਵੀ
ਪੂਰੀ ਮੂਲ ਸੂਚੀ ਨਹੀਂ, ਅਤੇ ਨਾ ਹੀ ਮਨਮਰਜ਼ੀ ਨਾਲ ਚੁਣਿਆ ਗਿਆ ਕੋਈ ਇੱਕ ਮੈਂਬਰ। ਕਿਉਂਕਿ `autoStrategy.ts` ਪਹਿਲਾਂ ਹੀ
ਉਸ ਐਰੇ ਨੂੰ ਇੱਕ ਸਖ਼ਤ ਅਲਾਊਲਿਸਟ ਵਜੋਂ ਲਾਗੂ ਕਰਦਾ ਹੈ, ਇਸ ਲਈ ਇਸਨੂੰ ਇੱਥੇ ਮੁੜ ਲਿਖਣਾ ਬਣਤਰ ਅਨੁਸਾਰ "ਤਸਦੀਕ ਕੀਤੇ" ਅਤੇ "ਅਸਲ ਵਿੱਚ ਵਰਤੇ"
ਸੈੱਟ ਨੂੰ ਇੱਕੋ ਬਣਾ ਦਿੰਦਾ ਹੈ। ਇਹ ਉਹੀ ਇਨਵੇਰੀਐਂਟ ਅਤੇ ਉਹੀ ਤਰਕ ਹੈ ਜੋ
[STRICT_ZERO_COST](./STRICT_ZERO_COST.md) ਵਿੱਚ ਹੈ।

## `auto/thrifty` — ਇੱਕ ਸਮੇਂ ਇੱਕ ਪੌੜੀ ਉੱਪਰ ਜਾਓ

ਪੂਲ = ਸਾਰੀਆਂ ਪੌੜੀਆਂ, ਪੌੜੀ ਸੂਚਕਾਂਕ ਅਨੁਸਾਰ ਕ੍ਰਮਬੱਧ, ਜਿਸ ਵਿੱਚ ਖ਼ਤਮ ਹੋ ਚੁੱਕੇ ਉਮੀਦਵਾਰਾਂ ਨੂੰ ਗੇਟ ਕਰਕੇ ਬਾਹਰ ਰੱਖਿਆ ਜਾਂਦਾ ਹੈ। `auto` ਇੰਜਣ
ਫਿਰ ਵੀ ਬਚੇ ਹੋਏ ਪੂਲ ਦੇ **ਅੰਦਰ** ਸਕੋਰ ਕਰਦਾ ਹੈ: ਲੈਡਰ ਤੈਅ ਕਰਦਾ ਹੈ ਕਿ ਕਿਹੜੀਆਂ ਪੌੜੀਆਂ ਵਰਤੋਂ ਵਿੱਚ ਹਨ, ਜਦਕਿ ਸਕੋਰਿੰਗ
ਤੈਅ ਕਰਦੀ ਹੈ ਕਿ ਉਹਨਾਂ ਦੇ ਅੰਦਰ ਕਿਹੜਾ ਉਮੀਦਵਾਰ ਜਿੱਤਦਾ ਹੈ। ਇੱਕ ਪੌੜੀ ਦੇ ਅੰਦਰ ਕ੍ਰਮ ਸਥਿਰ ਰਹਿੰਦਾ ਹੈ, ਇਸ ਲਈ ਸਕੋਰਰ ਦੀ ਆਪਣੀ
ਰੈਂਕਿੰਗ ਨੂੰ ਇਸ ਓਵਰਲੇ ਦੁਆਰਾ ਕਦੇ ਵੀ ਮੁੜ ਨਹੀਂ ਘੋਲਿਆ ਜਾਂਦਾ।

ਇਹ ਇੱਕ ਕ੍ਰਮਬੱਧਤਾ + ਗੇਟਿੰਗ ਓਵਰਲੇ ਹੈ, ਕੋਈ ਨਵਾਂ ਡਿਸਪੈਚਰ **ਨਹੀਂ**: `combo.ts` ਦਾ ਅਨੁਮਾਨੀ ਲੂਪ
ਪਹਿਲਾਂ ਹੀ ਟਾਰਗੇਟਾਂ ਨੂੰ ਕ੍ਰਮਵਾਰ ਜਾਂਚਦਾ ਹੈ ਅਤੇ ਅਸਫਲਤਾ 'ਤੇ ਅਗਲੇ ਵੱਲ ਵਧ ਜਾਂਦਾ ਹੈ, ਇਸ ਲਈ ਰਨਟਾਈਮ ਦੌਰਾਨ ਹੋਈ ਉਹ ਕੋਟਾ ਸਮਾਪਤੀ ਜਿਸਨੂੰ
ਪ੍ਰੀਫਲਾਈਟ ਨੇ ਨਹੀਂ ਫੜਿਆ, ਫਿਰ ਵੀ ਉਸੇ ਬੇਨਤੀ ਦੇ ਅੰਦਰ ਅਗਲੀ ਪੌੜੀ ਤੱਕ ਲੈ ਜਾਂਦੀ ਹੈ।

ਜਿੱਥੇ `auto/subscription` ਬੰਦ ਰਹਿ ਕੇ ਅਸਫਲ ਹੁੰਦਾ ਹੈ, ਉੱਥੇ `auto/thrifty` **ਖੁੱਲ੍ਹਾ** ਰਹਿ ਕੇ ਅਸਫਲ ਹੁੰਦਾ ਹੈ: ਬਿਨਾਂ ਵਰਤਣਯੋਗ ਕੋਟਾ
ਰੀਡਿੰਗ ਵਾਲੇ ਪਲਾਨ-ਸ਼ਾਮਲ ਕਨੈਕਸ਼ਨ ਨੂੰ ਫਿਰ ਵੀ ਪਹਿਲਾਂ ਅਜ਼ਮਾਇਆ ਜਾਂਦਾ ਹੈ। ਇਸਨੂੰ ਅਜ਼ਮਾਉਣ ਦੀ ਕੋਈ ਲਾਗਤ ਨਹੀਂ, ਅਤੇ ਜੇ
ਇਹ ਖ਼ਤਮ ਹੋਇਆ ਨਿਕਲਦਾ ਹੈ ਤਾਂ ਫਾਲ-ਥਰੂ ਫਿਰ ਵੀ ਅਗਲੀ ਪੌੜੀ ਤੱਕ ਪਹੁੰਚ ਜਾਂਦਾ ਹੈ — ਜਦਕਿ ਇਸਨੂੰ ਅਜ਼ਮਾਉਣ ਤੋਂ ਇਨਕਾਰ ਕਰਨਾ
ਟੈਲੀਮੈਟਰੀ ਨਾ ਮਿਲਣ 'ਤੇ ਬੇਨਤੀ ਨੂੰ ਇੱਕ ਭੁਗਤਾਨਯੋਗ ਪੌੜੀ ਵੱਲ ਭੇਜ ਦੇਵੇਗਾ, ਜੋ ਬਿਲਕੁਲ ਉਹੀ ਨਤੀਜਾ ਹੈ ਜਿਸ ਤੋਂ ਬਚਣ ਲਈ
ਇਹ ਗਰੁੱਪਿੰਗ ਮੌਜੂਦ ਹੈ।

## ਰੀਸੈੱਟ ਤੋਂ ਬਾਅਦ ਪਲਾਨ ਵੱਲ ਵਾਪਸੀ

ਰੂਟਿੰਗ ਦੇ ਪੌੜੀ 0 'ਤੇ ਵਾਪਸ ਆਉਣ ਤੋਂ ਪਹਿਲਾਂ ਤਿੰਨ ਸੁਤੰਤਰ ਚੀਜ਼ਾਂ ਦੀ ਮਿਆਦ ਖ਼ਤਮ ਹੋਣੀ ਲਾਜ਼ਮੀ ਹੈ। ਕੇਵਲ ਇੱਕ ਨੂੰ ਠੀਕ ਕਰਨ ਨਾਲ
ਪਲਾਨ ਮੁੜ ਭਰ ਜਾਣ ਤੋਂ ਕਾਫ਼ੀ ਸਮੇਂ ਬਾਅਦ ਵੀ ਲੈਡਰ ਭੁਗਤਾਨਯੋਗ ਪੌੜੀਆਂ 'ਤੇ ਅਟਕਿਆ ਰਹਿੰਦਾ ਹੈ।

1. **ਕੋਟਾ-ਸਟੇਟ ਕੈਸ਼** — `freeAccessQuota.ts` ਹਰੇਕ `(provider, connection)` ਲਈ 180s TTL ਨਾਲ ਕੈਸ਼ ਕਰਦਾ ਹੈ।
   ਇੱਕ ਅਜਿਹੀ ਕੈਸ਼ ਕੀਤੀ ਐਂਟਰੀ ਜਿਸਦਾ ਆਪਣਾ `resetAt` ਪਹਿਲਾਂ ਹੀ ਲੰਘ ਚੁੱਕਾ ਹੈ, ਉਸ ਵਿੰਡੋ ਦਾ ਵਰਣਨ ਕਰਦੀ ਹੈ ਜੋ ਹੁਣ
   ਮੌਜੂਦ ਨਹੀਂ ਹੈ, ਇਸ ਲਈ ਹੁਣ ਇਸਨੂੰ ਉਮਰ ਦੀ **ਪਰਵਾਹ ਕੀਤੇ ਬਿਨਾਂ** ਪੁਰਾਣਾ ਮੰਨਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ ਰਿਫਰੈਸ਼ ਲਈ ਮਜਬੂਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।
   ਇਸ ਤੋਂ ਬਿਨਾਂ, ਅੱਧੀ ਰਾਤ ਨੂੰ ਮੁੜ ਭਰਿਆ ਗਿਆ ਪਲਾਨ TTL ਦੇ ਆਖ਼ਰਕਾਰ ਖ਼ਤਮ ਹੋਣ ਤੱਕ ਖ਼ਤਮ ਹੋਇਆ ਹੀ ਦਿਖਾਈ ਦਿੰਦਾ ਰਹਿੰਦਾ ਹੈ।
2. **ਲੈਡਰ ਦੀ ਆਪਣੀ ਸਥਿਤੀ** — ਡਿਜ਼ਾਇਨ ਅਨੁਸਾਰ ਅਜਿਹੀ ਕੋਈ ਸਥਿਤੀ ਨਹੀਂ ਹੈ। ਹਰ ਪੂਲ ਬਣਾਉਣ ਵੇਲੇ
   ਲਾਈਵ ਕੋਟਾ ਸਥਿਤੀ ਤੋਂ ਪੌੜੀ ਯੋਗਤਾ ਦੀ ਮੁੜ ਗਣਨਾ ਕੀਤੀ ਜਾਂਦੀ ਹੈ; ਕੋਈ ਸਥਾਈ "ਇਸ ਵੇਲੇ ਪੌੜੀ 3 'ਤੇ" ਰਿਕਾਰਡ ਮੌਜੂਦ ਨਹੀਂ
   ਜੋ ਕਿਸੇ ਰੀਸੈੱਟ ਤੋਂ ਬਾਅਦ ਵੀ ਕਾਇਮ ਰਹਿ ਕੇ ਰੂਟਿੰਗ ਨੂੰ ਅਟਕਾ ਸਕੇ।
3. **ਕਨੈਕਸ਼ਨ ਕੂਲਡਾਊਨ** — ਕੋਟਾ ਖ਼ਤਮ ਕਰਨ ਵਾਲਾ 429 ਐਕਸਪੋਨੇਨਸ਼ੀਅਲ ਬੈਕਆਫ਼ ਤੋਂ `rateLimitedUntil` ਸੈੱਟ ਕਰਦਾ ਹੈ,
   ਜੋ ਕਿਸੇ ਪਲਾਨ ਕਨੈਕਸ਼ਨ ਲਈ ਅਸਲ ਰੀਸੈੱਟ ਤੋਂ ਅੱਗੇ ਨਿਕਲ ਸਕਦਾ ਹੈ। `clampCooldownToReset()`
   (`subscriptionLadder.ts`) ਕੂਲਡਾਊਨ ਨੂੰ ਅੱਪਸਟ੍ਰੀਮ ਦੇ ਆਪਣੇ ਰੀਸੈੱਟ ਪਲ ਤੱਕ ਘਟਾਉਂਦਾ ਹੈ ਅਤੇ
   ਕਦੇ ਵੀ ਇਸਨੂੰ ਵਧਾ ਨਹੀਂ ਸਕਦਾ। **ਇਸਨੂੰ ਲਾਗੂ ਅਤੇ ਟੈਸਟ ਕੀਤਾ ਗਿਆ ਹੈ ਪਰ ਅਜੇ ਵਾਇਰ ਨਹੀਂ ਕੀਤਾ ਗਿਆ**: ਕੋਟਾ ਕੈਸ਼ ਨੂੰ
   `src/sse/services/auth.ts` ਵਿੱਚ ਕੋਈ ਵੀ ਕੂਲਡਾਊਨ ਲਿਖੇ ਜਾਣ ਤੋਂ _ਪਹਿਲਾਂ_ ਅਵੈਧ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ, ਇਸ ਲਈ `resetAt`
   ਨੂੰ ਉਸ ਫੰਕਸ਼ਨ ਵਿੱਚ ਹੋਰ ਪਹਿਲਾਂ ਕੈਪਚਰ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ — ਰੈਜ਼ੀਲੀਅੰਸ ਹਾਟ ਪਾਥ ਵਿੱਚ ਇੱਕ ਅਜਿਹਾ ਬਦਲਾਅ ਜੋ
   ਆਪਣੀ ਵੱਖਰੀ ਸਮੀਖਿਆ ਕੀਤੀ PR ਵਿੱਚ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ। ਉਦੋਂ ਤੱਕ, ਮੁੜ-ਦਾਖਲਾ ਕਨੈਕਸ਼ਨ ਕੂਲਡਾਊਨ ਖ਼ਤਮ ਹੋਣ ਦੀ ਉਡੀਕ ਕਰਦਾ ਹੈ
   (ਜੋ ਪਹਿਲਾਂ ਹੀ ਅੱਪਸਟ੍ਰੀਮ `Retry-After` ਸੰਕੇਤਾਂ ਨੂੰ ਤਰਜੀਹ ਦਿੰਦਾ ਹੈ, ਜਦੋਂ ਪ੍ਰਦਾਤਾ ਉਹਨਾਂ ਨੂੰ ਭੇਜਦਾ ਹੈ)।

### ਉਤਾਰ-ਚੜ੍ਹਾਅ ਰੋਕਥਾਮ

ਹੁਣੇ-ਹੁਣੇ ਰੀਸੈੱਟ ਹੋਈ ਪੌੜੀ ਨੂੰ ਕੇਵਲ `reentryMinRemainingPercent` (ਡਿਫਾਲਟ 5) ਤੋਂ ਉੱਪਰ ਹੋਣ 'ਤੇ ਹੀ ਮੁੜ ਸ਼ਾਮਲ ਕੀਤਾ ਜਾਂਦਾ ਹੈ,
ਜਦਕਿ ਪਹਿਲਾਂ ਹੀ ਵਰਤੋਂ ਵਿੱਚ ਮੌਜੂਦ ਕਨੈਕਸ਼ਨ ਨੂੰ ਸਿਰਫ਼ `exitCutoffPercent` (ਡਿਫਾਲਟ 2,
ਜੋ `quotaPreflight.defaultThresholdPercent` ਨਾਲ ਮੇਲ ਖਾਂਦਾ ਹੈ) ਤੋਂ ਉੱਪਰ ਰਹਿਣਾ ਹੁੰਦਾ ਹੈ। ਇਹ ਅੰਤਰ ਹਿਸਟੈਰਿਸਿਸ ਬੈਂਡ ਹੈ — ਇਸ ਤੋਂ ਬਿਨਾਂ,
ਕਟਆਫ਼ ਦੇ ਨੇੜੇ ਮੰਡਰਾਉਂਦਾ ਕਨੈਕਸ਼ਨ ਲਗਾਤਾਰ ਬੇਨਤੀਆਂ 'ਤੇ ਪੌੜੀਆਂ ਵਿਚਕਾਰ ਝੂਲਦਾ ਰਹਿੰਦਾ ਹੈ।

## ਸੰਰਚਨਾ

ਸਿਰਫ਼ ਟਿਊਨਿੰਗ ਲਈ। ਜਾਣਬੁੱਝ ਕੇ ਕੋਈ `enabled` ਫਲੈਗ **ਨਹੀਂ** ਹੈ: ਇਨ੍ਹਾਂ ਨੂੰ ਬੰਦ ਕਰਨ ਦੇ ਸਮਰੱਥ ਟੌਗਲ ਨਾਲ
`auto/subscription` ਚੁੱਪਚਾਪ ਪੂਰਾ ਪੂਲ — ਭੁਗਤਾਨਯੋਗ ਮਾਡਲਾਂ ਸਮੇਤ — ਉਸ ਨਾਮ ਹੇਠ ਪੇਸ਼ ਕਰਦਾ ਰਹੇਗਾ,
ਜੋ ਇਸਦੇ ਉਲਟ ਦਾ ਵਾਅਦਾ ਕਰਦਾ ਹੈ।

```jsonc
{
  "subscriptionLadder": {
    "exitCutoffPercent": 2,
    "reentryMinRemainingPercent": 5,
    "rungBudgetUsd": { "cheap": 5.0, "premium": 0 }, // 0 ਕਿਸੇ ਪੌੜੀ ਨੂੰ ਪੂਰੀ ਤਰ੍ਹਾਂ ਅਯੋਗ ਕਰ ਦਿੰਦਾ ਹੈ
  },
}
```

ਜਦੋਂ ਤੱਕ ਕੋਈ ਖਰਚ ਰਿਜ਼ਾਲਵਰ ਵਾਇਰ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ, ਬਜਟ ਗੇਟਿੰਗ ਨਿਸ਼ਕ੍ਰਿਆ ਰਹਿੰਦੀ ਹੈ: ਕੋਈ ਲੇਖਾ-ਜੋਖਾ ਉਪਲਬਧ ਨਾ ਹੋਣ 'ਤੇ ਭੁਗਤਾਨਯੋਗ
ਪੌੜੀ ਨੂੰ ਕ੍ਰਮ ਵਿੱਚ ਰੱਖਿਆ ਜਾਂਦਾ ਹੈ, ਪਰ ਕਦੇ ਵੀ ਗੇਟ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ। v3.8.51 ਮੁਤਾਬਕ `rungBudgetUsd` ਸੈਟਿੰਗ ਨੂੰ
ਸਕੀਮਾ ਸਵੀਕਾਰ ਕਰਦਾ ਹੈ, ਪਰ ਇਸਨੂੰ ਹਾਲੇ ਲਾਗੂ **ਨਹੀਂ** ਕੀਤਾ ਗਿਆ — ਇਸਨੂੰ ਰਾਖਵੀਂ ਸੰਰਚਨਾ ਸਮਝੋ, ਨਾ ਕਿ ਸਰਗਰਮ ਖਰਚ ਸੀਮਾ। ਪੌੜੀਆਂ ਦਾ ਕ੍ਰਮ, ਕੋਟਾ-ਅਧਾਰਿਤ ਖ਼ਤਮਾ, ਅਤੇ ਰੀਸੈੱਟ ਤੋਂ ਬਾਅਦ ਮੁੜ-ਦਾਖਲਾ, ਇਹ ਸਭ
ਇਸ ਤੋਂ ਬਿਨਾਂ ਕੰਮ ਕਰਦੇ ਹਨ।

## ਸੰਯੋਜਨ

`subscription` ਅਤੇ `thrifty`, `AutoTier` ਮੁੱਲ ਹਨ, ਇਸ ਲਈ ਇਹ ਹਰ ਸ਼੍ਰੇਣੀ ਨਾਲ ਸੰਯੋਜਿਤ ਹੁੰਦੇ ਹਨ:
`auto/coding:thrifty`, `auto/reasoning:subscription`, ਆਦਿ। ਦੋਵੇਂ ਫਲੈਟ ids
(`auto/subscription`, `auto/thrifty`) ਦਾ `/v1/models` ਅਤੇ ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ ਪ੍ਰਚਾਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

ਦੋਵਾਂ ਵਿੱਚੋਂ ਕੋਈ ਵੀ id ਭੁਗਤਾਨਯੋਗ-ਟੀਅਰ ਨਹੀਂ ਹੈ, ਇਸ ਲਈ `isPaidTierAutoId()` ਦੋਵਾਂ ਲਈ `false` ਵਾਪਸ ਕਰਦਾ ਹੈ ਅਤੇ
`auto/subscription`, `hidePaidModels` ਤੋਂ ਬਚਿਆ ਰਹਿੰਦਾ ਹੈ।
