## ਸੰਖੇਪ ਜਾਣਕਾਰੀ

OmniRoute ਇੱਕ ਮਾਡਿਊਲਰ ਪ੍ਰੋਂਪਟ ਕੰਪਰੈਸ਼ਨ ਪਾਈਪਲਾਈਨ ਨੂੰ ਲਾਗੂ ਕਰਦਾ ਹੈ ਜੋ ਬੇਨਤੀਆਂ ਦੇ ਅੱਪਸਟ੍ਰੀਮ ਪ੍ਰਦਾਤਾਵਾਂ ਤੱਕ ਪਹੁੰਚਣ ਤੋਂ ਪਹਿਲਾਂ **ਸਰਗਰਮੀ ਨਾਲ** ਚੱਲਦਾ ਹੈ। ਇਸਦਾ ਮਤਲਬ ਹੈ ਕਿ ਤੁਹਾਡੀ ਟੋਕਨ ਬਚਤ ਪਾਰਦਰਸ਼ੀ ਢੰਗ ਨਾਲ ਹੁੰਦੀ ਹੈ — ਤੁਹਾਡੇ ਵਰਕਫਲੋ ਵਿੱਚ ਕੋਈ ਬਦਲਾਅ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ।

```
ਕਲਾਇੰਟ ਬੇਨਤੀ
  → ਕੰਪਰੈਸ਼ਨ ਰਣਨੀਤੀ ਚੋਣਕਾਰ
    → ਕੰਬੋ ਓਵਰਰਾਈਡ? → ਕੰਬੋ ਸੈਟਿੰਗ ਦੀ ਵਰਤੋਂ ਕਰੋ
    → ਆਟੋ-ਟ੍ਰਿਗਰ ਥ੍ਰੈਸ਼ਹੋਲਡ? → ਆਟੋ ਮੋਡ ਦੀ ਵਰਤੋਂ ਕਰੋ
    → ਡਿਫੌਲਟ ਮੋਡ? → ਗਲੋਬਲ ਸੈਟਿੰਗ ਦੀ ਵਰਤੋਂ ਕਰੋ
    → ਬੰਦ? → ਕੰਪਰੈਸ਼ਨ ਛੱਡੋ
  → ਚੁਣਿਆ ਕੰਪਰੈਸ਼ਨ ਮੋਡ
    → ਬੰਦ: ਕੋਈ ਕੰਪਰੈਸ਼ਨ ਨਹੀਂ
    → ਲਾਈਟ: ਸੁਰੱਖਿਅਤ ਵ੍ਹਾਈਟਸਪੇਸ/ਫਾਰਮੈਟਿੰਗ ਕਲੀਨਅੱਪ (~15%)
    → ਸਟੈਂਡਰਡ: ਕੇਵਮੈਨ-ਸਪੀਕ ਫਿਲਰ ਹਟਾਉਣਾ (~30%)
    → ਅਗਰੈਸਿਵ: ਇਤਿਹਾਸ ਦੀ ਉਮਰ + ਸੰਖੇਪਕਰਨ (~50%)
    → ਅਲਟਰਾ: ਹੀਊਰਿਸਟਿਕ ਪ੍ਰੂਨਿੰਗ + ਕੋਡ-ਬਲਾਕ ਥਿਨਿੰਗ (~75%)
    → RTK: ਕਮਾਂਡ-ਜਾਗਰੂਕ ਟਰਮੀਨਲ/ਟੂਲ-ਆਉਟਪੁੱਟ ਫਿਲਟਰਿੰਗ (60-90% ਅੱਪਸਟ੍ਰੀਮ ਰੇਂਜ)
    → ਸਟੈਕਡ: ਆਰਡਰਡ ਮਲਟੀ-ਇੰਜਣ ਪਾਈਪਲਾਈਨ, ਆਮ ਤੌਰ 'ਤੇ RTK ਫਿਰ ਕੇਵਮੈਨ (78-95% ਯੋਗ ਰੇਂਜ)
  → ਕੰਪਰੈੱਸਡ ਬੇਨਤੀ → ਪ੍ਰਦਾਤਾ
```

## ਕੰਪਰੈਸ਼ਨ ਮੋਡ

### ਬੰਦ

ਕੋਈ ਕੰਪਰੈਸ਼ਨ ਲਾਗੂ ਨਹੀਂ ਕੀਤਾ ਗਿਆ। ਸਾਰੇ ਸੁਨੇਹੇ ਬਿਨਾਂ ਬਦਲੇ ਲੰਘਦੇ ਹਨ।

### ਲਾਈਟ ਮੋਡ (~15% ਬਚਤ, <1ms ਲੇਟੈਂਸੀ)

ਸਭ ਤੋਂ ਸੁਰੱਖਿਅਤ ਮੋਡ — ਜ਼ੀਰੋ ਸਿਮੈਂਟਿਕ ਬਦਲਾਅ, ਸਿਰਫ ਫਾਰਮੈਟਿੰਗ ਕਲੀਨਅੱਪ:

| ਤਕਨੀਕ                    | ਵਰਣਨ                                           |
| :----------------------- | :--------------------------------------------- |
| `collapseWhitespace`     | ਲਗਾਤਾਰ ਖਾਲੀ ਲਾਈਨਾਂ ਅਤੇ ਪਿਛਲੀਆਂ ਥਾਵਾਂ ਨੂੰ ਮਿਲਾਓ |
| `dedupSystemPrompt`      | ਡੁਪਲੀਕੇਟ ਸਿਸਟਮ ਸੁਨੇਹਿਆਂ ਨੂੰ ਹਟਾਓ               |
| `compressToolResults`    | ਵਿਸਤ੍ਰਿਤ ਟੂਲ/ਫੰਕਸ਼ਨ ਆਉਟਪੁੱਟਾਂ ਨੂੰ ਕੰਪਰੈੱਸ ਕਰੋ  |
| `removeRedundantContent` | ਦੁਹਰਾਉਣ ਵਾਲੀਆਂ ਹਦਾਇਤਾਂ ਨੂੰ ਹਟਾਓ                |
| `replaceImageUrls`       | base64 ਚਿੱਤਰ ਡਾਟਾ URI ਨੂੰ ਛੋਟਾ ਕਰੋ             |

**ਇਸ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ:** ਹਮੇਸ਼ਾ-ਚਾਲੂ ਵਰਤੋਂ, ਸੁਰੱਖਿਆ-ਨਾਜ਼ੁਕ ਵਰਕਫਲੋ।

### ਸਟੈਂਡਰਡ ਮੋਡ (~30% ਬਚਤ)

[ਕੇਵਮੈਨ](https://github.com/JuliusBrussee/caveman) ਤੋਂ ਪ੍ਰੇਰਿਤ — ਅਰਥ ਨੂੰ ਸੁਰੱਖਿਅਤ ਰੱਖਦੇ ਹੋਏ ਫਿਲਰ ਸ਼ਬਦਾਂ ਅਤੇ ਵਿਸਤ੍ਰਿਤ ਵਾਕਾਂਸ਼ਾਂ ਨੂੰ ਹਟਾਉਂਦਾ ਹੈ:

- ਫਿਲਰ ਸ਼ਬਦਾਂ ਨੂੰ ਹਟਾਉਂਦਾ ਹੈ ("ਕਿਰਪਾ ਕਰਕੇ", "ਮੈਨੂੰ ਲੱਗਦਾ ਹੈ", "ਮੂਲ ਰੂਪ ਵਿੱਚ", "ਅਸਲ ਵਿੱਚ")
- ਵਿਸਤ੍ਰਿਤ ਵਾਕਾਂਸ਼ਾਂ ਨੂੰ ਸੰਘਣਾ ਕਰਦਾ ਹੈ ("ਕਰਨ ਲਈ" → "ਕਰਨ ਲਈ", "ਦੇ ਨਤੀਜੇ ਵਜੋਂ" → "ਕਿਉਂਕਿ")
- ਨਿਮਰਤਾਪੂਰਵਕ ਹੈਜਿੰਗ ਨੂੰ ਹਟਾਉਂਦਾ ਹੈ ("ਕੀ ਤੁਹਾਨੂੰ ਕੋਈ ਇਤਰਾਜ਼ ਹੋਵੇਗਾ...", "ਜੇ ਤੁਸੀਂ ਸੰਭਵ ਹੋ ਸਕੇ...")
- ਕੋਡਿੰਗ ਪ੍ਰੋਂਪਟਾਂ ਲਈ 30+ ਰੈਗੈਕਸ ਨਿਯਮ ਟਿਊਨ ਕੀਤੇ ਗਏ ਹਨ

**ਇਸ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ:** ਰੋਜ਼ਾਨਾ ਕੋਡਿੰਗ ਵਰਕਫਲੋ, ਲਾਗਤ-ਸਚੇਤ ਟੀਮਾਂ।

### ਅਗਰੈਸਿਵ ਮੋਡ (~50% ਬਚਤ)

ਲੰਬੇ ਸੈਸ਼ਨਾਂ ਲਈ ਸਮਾਰਟ ਇਤਿਹਾਸ ਪ੍ਰਬੰਧਨ:

- **ਸੁਨੇਹਾ ਉਮਰ ਵਧਾਉਣਾ** — ਪੁਰਾਣੇ ਸੁਨੇਹੇ ਹੌਲੀ-ਹੌਲੀ ਕੰਪਰੈੱਸ ਕੀਤੇ ਜਾਂਦੇ ਹਨ
- **ਟੂਲ ਨਤੀਜਾ ਸੰਖੇਪਕਰਨ** — ਲੰਬੇ ਟੂਲ ਆਉਟਪੁੱਟਾਂ ਨੂੰ ਸੰਖੇਪਾਂ ਨਾਲ ਬਦਲਿਆ ਜਾਂਦਾ ਹੈ
- **ਢਾਂਚਾਗਤ ਅਖੰਡਤਾ ਗਾਰਡ** — `tool_use` + `tool_result` ਜੋੜਿਆਂ ਨੂੰ ਇਕਸਾਰ ਰਹਿਣ ਨੂੰ ਯਕੀਨੀ ਬਣਾਉਂਦਾ ਹੈ
- **ਪ੍ਰਸੰਗ ਵਿੰਡੋ ਜਾਗਰੂਕਤਾ** — ਪ੍ਰਤੀ-ਮਾਡਲ ਟੋਕਨ ਸੀਮਾਵਾਂ ਦਾ ਸਤਿਕਾਰ ਕਰਦਾ ਹੈ

**ਇਸ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ:** ਵਿਸਤ੍ਰਿਤ ਡੀਬੱਗਿੰਗ ਸੈਸ਼ਨ, ਵੱਡੇ ਕੋਡਬੇਸ।

### ਅਲਟਰਾ ਮੋਡ (~75% ਬਚਤ)

ਟੋਕਨ-ਨਾਜ਼ੁਕ ਸਥਿਤੀਆਂ ਲਈ ਵੱਧ ਤੋਂ ਵੱਧ ਕੰਪਰੈਸ਼ਨ:

- **ਹੀਊਰਿਸਟਿਕ ਪ੍ਰੂਨਿੰਗ** — ਪ੍ਰਸੰਗਿਕਤਾ ਥ੍ਰੈਸ਼ਹੋਲਡ ਤੋਂ ਹੇਠਾਂ ਸੁਨੇਹਿਆਂ ਨੂੰ ਹਟਾਉਂਦਾ ਹੈ
- **ਕੋਡ ਬਲਾਕ ਥਿਨਿੰਗ** — ਦੁਹਰਾਉਣ ਵਾਲੀਆਂ ਕੋਡ ਉਦਾਹਰਣਾਂ ਨੂੰ ਕੰਪਰੈੱਸ ਕਰਦਾ ਹੈ
- **ਬਾਈਨਰੀ ਖੋਜ ਛਾਂਟੀ** — ਪ੍ਰਸੰਗ ਵਿੰਡੋ ਲਈ ਅਨੁਕੂਲ ਕੱਟ ਪੁਆਇੰਟ ਲੱਭਦਾ ਹੈ
- ਸਾਰੇ ਅਗਰੈਸਿਵ ਮੋਡ ਵਿਸ਼ੇਸ਼ਤਾਵਾਂ ਸ਼ਾਮਲ ਹਨ

**ਇਸ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ:** ਜਦੋਂ ਤੁਸੀਂ ਵਾਰ-ਵਾਰ ਪ੍ਰਸੰਗ ਸੀਮਾਵਾਂ ਨੂੰ ਮਾਰ ਰਹੇ ਹੋ।

### RTK ਮੋਡ (60-90% ਅੱਪਸਟ੍ਰੀਮ ਰੇਂਜ)

RTK ਮੋਡ ਵਿਸਤ੍ਰਿਤ ਟੂਲ ਆਉਟਪੁੱਟਾਂ ਲਈ ਅਨੁਕੂਲਿਤ ਹੈ ਜੋ ਕੋਡਿੰਗ-ਏਜੰਟ ਸੈਸ਼ਨਾਂ ਵਿੱਚ ਦਿਖਾਈ ਦਿੰਦੇ ਹਨ:

- `git status`, `git diff`, `git log`, ਟੈਸਟ ਰਨਰ,
  TypeScript/Vite/Webpack ਬਿਲਡ, ESLint/Biome/Prettier, npm ਆਡਿਟ/ਇੰਸਟਾਲ, Docker ਲੌਗ, ਇਨਫਰਾ
  ਆਉਟਪੁੱਟ, ਅਤੇ ਆਮ ਸ਼ੈੱਲ ਆਉਟਪੁੱਟ ਵਰਗੀਆਂ ਕਮਾਂਡ/ਆਉਟਪੁੱਟ ਕਲਾਸਾਂ ਦਾ ਪਤਾ ਲਗਾਉਂਦਾ ਹੈ
- `open-sse/services/compression/engines/rtk/filters/` ਤੋਂ JSON ਫਿਲਟਰ ਪੈਕ ਲਾਗੂ ਕਰਦਾ ਹੈ
- ਪ੍ਰੋਜੈਕਟ ਜਾਂ ਗਲੋਬਲ `filters.toml` ਫਾਈਲਾਂ ਤੋਂ RTK TOML ਸਕੀਮਾ v1 ਫਿਲਟਰਾਂ ਨੂੰ ਆਯਾਤ ਕਰਦਾ ਹੈ, ਇਨਲਾਈਨ-ਟੈਸਟ
  ਪ੍ਰਮਾਣਿਕਤਾ ਅਤੇ ਪ੍ਰੋਜੈਕਟ ਫਾਈਲਾਂ ਲਈ ਟਰੱਸਟ-ਗੇਟਿੰਗ ਦੇ ਨਾਲ
- ਇਨਲਾਈਨ ਵੈਰੀਫਾਈ ਨਮੂਨਿਆਂ ਦੇ ਨਾਲ 49 ਬਿਲਟ-ਇਨ ਫਿਲਟਰ ਭੇਜਦਾ ਹੈ
- ANSI ਕੰਟਰੋਲ ਕ੍ਰਮ, ਪ੍ਰਗਤੀ ਪੱਟੀਆਂ, ਦੁਹਰਾਉਣ ਵਾਲੀਆਂ ਲਾਈਨਾਂ, ਅਤੇ ਗੈਰ-ਕਾਰਵਾਈਯੋਗ ਸ਼ੋਰ ਨੂੰ ਹਟਾਉਂਦਾ ਹੈ
- ਅਸਫਲਤਾਵਾਂ, ਗਲਤੀਆਂ, ਚੇਤਾਵਨੀਆਂ, ਬਦਲੀਆਂ ਫਾਈਲਾਂ, ਸੰਖੇਪਾਂ, ਅਤੇ ਲੰਬੇ ਆਉਟਪੁੱਟ ਦੀ ਪੂਛ ਨੂੰ ਸੁਰੱਖਿਅਤ ਰੱਖਦਾ ਹੈ
- ਟਰੱਸਟ-ਗੇਟਡ ਪ੍ਰੋਜੈਕਟ ਫਿਲਟਰਾਂ, ਗਲੋਬਲ ਫਿਲਟਰਾਂ, ਅਤੇ ਵਿਕਲਪਿਕ ਰੀਡੈਕਟਡ ਕੱਚੇ-ਆਉਟਪੁੱਟ ਰਿਕਵਰੀ ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ

**ਇਸ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ:** ਸ਼ੈੱਲ, ਬਿਲਡ, ਟੈਸਟ, ਗਿੱਟ, ਗ੍ਰੇਪ, ਅਤੇ ਫਾਈਲ-ਆਉਟਪੁੱਟ ਟ੍ਰਾਂਸਕ੍ਰਿਪਟਾਂ ਵਾਲੇ ਏਜੰਟ ਸੈਸ਼ਨ।

### ਸਟੈਕਡ ਮੋਡ (78-95% ਯੋਗ ਰੇਂਜ)

ਸਟੈਕਡ ਮੋਡ ਕਈ ਕੰਪਰੈਸ਼ਨ ਇੰਜਣਾਂ ਨੂੰ ਇੱਕ ਨਿਰਧਾਰਤ ਕ੍ਰਮ ਵਿੱਚ ਚਲਾਉਂਦਾ ਹੈ। ਡਿਫੌਲਟ ਪਾਈਪਲਾਈਨ ਹੈ:

```txt
RTK -> ਕੇਵਮੈਨ
```

ਉਹ ਕ੍ਰਮ ਪਹਿਲਾਂ ਟਰਮੀਨਲ/ਟੂਲ ਆਉਟਪੁੱਟ ਨੂੰ ਸੰਖੇਪ ਰੱਖਦਾ ਹੈ, ਫਿਰ ਬਾਕੀ ਬਚੇ ਕੁਦਰਤੀ-ਭਾਸ਼ਾ ਪ੍ਰੋਂਪਟ 'ਤੇ ਕੇਵਮੈਨ ਸਿਮੈਂਟਿਕ ਸੰਘਣਾਕਰਨ ਲਾਗੂ ਕਰਦਾ ਹੈ। ਸਟੈਕਡ ਪਾਈਪਲਾਈਨਾਂ ਨੂੰ ਗਲੋਬਲ ਤੌਰ 'ਤੇ ਜਾਂ ਰੂਟਿੰਗ ਕੰਬੋਜ਼ ਨੂੰ ਨਿਰਧਾਰਤ ਕੰਪਰੈਸ਼ਨ ਕੰਬੋਜ਼ ਦੁਆਰਾ ਕੌਂਫਿਗਰ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ।

**ਇਸ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ:** ਵੱਡੇ ਟੂਲ ਲੌਗਸ ਅਤੇ ਮਨੁੱਖੀ ਹਦਾਇਤਾਂ ਜਾਂ ਸਹਾਇਕ ਸੰਖੇਪਾਂ ਦੇ ਨਾਲ ਮਿਸ਼ਰਤ ਪ੍ਰਸੰਗ।

## ਅੱਪਸਟ੍ਰੀਮ ਬਚਤ ਗਣਿਤ

OmniRoute ਦੋ ਸਰੋਤਾਂ ਤੋਂ ਕੰਪਰੈਸ਼ਨ ਬਚਤਾਂ ਨੂੰ ਦਸਤਾਵੇਜ਼ੀ ਬਣਾਉਂਦਾ ਹੈ: ਅੱਪਸਟ੍ਰੀਮ ਪ੍ਰੋਜੈਕਟ ਬੈਂਚਮਾਰਕ ਅਤੇ OmniRoute ਦੀ ਆਪਣੀ ਇੰਜਣ ਰਚਨਾ।

| ਸਰੋਤ    | ਅੱਪਸਟ੍ਰੀਮ README ਨੰਬਰ ਇੱਥੇ ਵਰਤਿਆ ਗਿਆ ਹੈ                                                                |
| ------- | ------------------------------------------------------------------------------------------------------ |
| Caveman | `~75%` ਘੱਟ ਆਉਟਪੁੱਟ ਟੋਕਨ, `65%` ਬੈਂਚਮਾਰਕ ਔਸਤ ਆਉਟਪੁੱਟ ਬਚਤ, `22-87%` ਰੇਂਜ, ਅਤੇ `~46%` ਇਨਪੁੱਟ ਕੰਪਰੈਸ਼ਨ ਟੂਲ |
| RTK     | `60-90%` ਕਮਾਂਡ-ਆਉਟਪੁੱਟ ਬਚਤ; ਨਮੂਨਾ ਸੈਸ਼ਨ `~118,000 -> ~23,900` ਟੋਕਨ, ਜਾਂ `79.7%` ਬਚਤ (`~80%`)           |

ਓਵਰਲੈਪਿੰਗ ਟੂਲ/ਸੰਦਰਭ ਪੇਲੋਡਾਂ ਲਈ, ਡਿਫੌਲਟ OmniRoute ਕੰਬੋ ਇੰਜਣਾਂ ਨੂੰ ਸਟੈਕ ਕਰਦਾ ਹੈ:

```txt
RTK -> Caveman
```

ਸੰਯੁਕਤ ਬਚਤ ਗੁਣਾਤਮਕ ਹਨ, ਜੋੜਨ ਵਾਲੀਆਂ ਨਹੀਂ:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ਇਹ `78-95%` ਨੰਬਰ ਉਦੋਂ ਲਾਗੂ ਹੁੰਦਾ ਹੈ ਜਦੋਂ RTK ਅਤੇ Caveman ਦੋਵੇਂ ਇੱਕੋ ਇਨਪੁੱਟ/ਸੰਦਰਭ ਪੇਲੋਡ ਨੂੰ ਘਟਾ ਸਕਦੇ ਹਨ। Caveman ਪ੍ਰਤੀਕਿਰਿਆ ਆਉਟਪੁੱਟ ਮੋਡ ਵੱਖਰਾ ਹੈ: ਜਦੋਂ ਸਮਰੱਥ ਹੁੰਦਾ ਹੈ, ਤਾਂ Caveman ਦੀ ਆਪਣੀ ਆਉਟਪੁੱਟ ਬਚਤ (`65%` ਔਸਤ, `~75%` ਸੁਰਖੀ, `22-87%` ਰੇਂਜ) ਦੀ ਵਰਤੋਂ ਕਰੋ। ਕੁੱਲ ਬਿਲਿੰਗ ਬਚਤ ਤੁਹਾਡੇ ਪ੍ਰੋਂਪਟ/ਆਉਟਪੁੱਟ ਮਿਸ਼ਰਣ 'ਤੇ ਨਿਰਭਰ ਕਰਦੀ ਹੈ।

### "ਯੋਗ" ਦਾ ਅਸਲ ਵਿੱਚ ਕੀ ਅਰਥ ਹੈ

15-95% ਸੁਰਖੀ ਰੇਂਜ ਅਸਲੀ ਹੈ, ਪਰ ਇਹ ਸਿਰਫ਼ **ਬੇਲੋੜੀ ਜਾਂ ਬਹੁਤ ਜ਼ਿਆਦਾ** ਸਮੱਗਰੀ 'ਤੇ ਲਾਗੂ ਹੁੰਦੀ ਹੈ — ਦੁਹਰਾਈਆਂ ਗਈਆਂ ਗਲਤੀਆਂ ਦੀਆਂ ਲਾਈਨਾਂ, ਇੱਕ ਬਿਲਡ ਲੌਗ ਜੋ ਇੱਕੋ ਚੇਤਾਵਨੀ ਨੂੰ ਸਪੈਮ ਕਰਦਾ ਹੈ, ਇੱਕ ਵੱਡਾ `grep`/ਫਾਈਲ-ਰੀਡ ਡੰਪ। ਇਸਦਾ ਮਤਲਬ ਇਹ **ਨਹੀਂ** ਹੈ ਕਿ ਹਰ ਬੇਨਤੀ ਇੰਨੀ ਬਚਤ ਕਰਦੀ ਹੈ।

ਪ੍ਰਯੋਗਾਤਮਕ ਤੌਰ 'ਤੇ ਪ੍ਰਮਾਣਿਤ (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): ਇੱਕ Anthropic-ਆਕਾਰ ਦੇ `tool_result` ਬਲਾਕ ਦੇ ਵਿਰੁੱਧ ਇੱਕ `stacked` (RTK + Caveman) ਰਨ ਜਿਸ ਵਿੱਚ 300 ਇੱਕੋ ਜਿਹੀਆਂ ਗਲਤੀਆਂ ਦੀਆਂ ਲਾਈਨਾਂ ਸਨ, ਨੇ **95.93% ਟੋਕਨ ਬਚਤ / 96.26% ਅੱਖਰ ਬਚਤ** ਪੈਦਾ ਕੀਤੀ — ਜੋ ਕਿ ਇਸ਼ਤਿਹਾਰੀ ਰੇਂਜ ਵਿੱਚ ਪੂਰੀ ਤਰ੍ਹਾਂ ਫਿੱਟ ਬੈਠਦਾ ਹੈ। ਪਰ ਆਮ, ਗੈਰ-ਬੇਲੋੜੀ ਟੂਲ ਆਉਟਪੁੱਟ (ਇੱਕ ਸਾਫ਼ `grep` ਮੈਚ ਸੂਚੀ, ਇੱਕ ਛੋਟੀ ਫਾਈਲ ਰੀਡ, ਆਮ ਗੱਲਬਾਤ ਵਾਲਾ ਟੈਕਸਟ) ਦੇ ਵਿਰੁੱਧ ਚਲਾਇਆ ਗਿਆ ਉਹੀ ਪਾਈਪਲਾਈਨ ਸਹੀ ਢੰਗ ਨਾਲ **ਲਗਭਗ-ਜ਼ੀਰੋ ਬਚਤ** ਪੈਦਾ ਕਰਦੀ ਹੈ, ਕਿਉਂਕਿ ਹਟਾਉਣ ਲਈ ਕੁਝ ਵੀ ਦੁਹਰਾਉਣ ਵਾਲਾ ਨਹੀਂ ਹੈ ਅਤੇ `validateCompression()` (`validation.ts`) ਇੱਕ ਅਜਿਹੀ ਮੁੜ-ਲਿਖਤ ਨੂੰ ਭੇਜਣ ਤੋਂ ਇਨਕਾਰ ਕਰਦਾ ਹੈ ਜੋ ਕੋਡ ਬਲਾਕਾਂ, URL, ਸਿਰਲੇਖਾਂ, ਸੰਸਕਰਣਾਂ, ਜਾਂ ਸਾਰੇ-ਕੈਪਸ ਸਥਿਰ ਪਛਾਣਕਰਤਾਵਾਂ ਨੂੰ ਛੱਡ ਜਾਂ ਬਦਲ ਦੇਵੇਗਾ।

ਇਹ ਇੱਕ ਬੱਗ ਨਹੀਂ, ਸਗੋਂ ਇੱਕ ਅਨੁਮਾਨਿਤ, ਸੁਰੱਖਿਅਤ ਵਿਵਹਾਰ ਹੈ: ਇੱਕ ਕੋਡਿੰਗ ਸੈਸ਼ਨ ਜੋ ਜ਼ਿਆਦਾਤਰ ਸਾਫ਼ ਫਾਈਲਾਂ ਨੂੰ ਪੜ੍ਹਦਾ/ਗ੍ਰੇਪ ਕਰਦਾ ਹੈ, ਕੰਪਰੈਸ਼ਨ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਮਰੱਥ ਹੋਣ ਦੇ ਬਾਵਜੂਦ ਵੀ ਮਾਮੂਲੀ ਕੁੱਲ ਬਚਤ ਦੇਖੇਗਾ, ਜਦੋਂ ਕਿ ਇੱਕ ਸੈਸ਼ਨ ਜੋ ਇੱਕ ਅਸਫਲ ਲੂਪ ਜਾਂ ਇੱਕ ਚੈਟੀ ਲਿੰਟਰ ਨੂੰ ਹਿੱਟ ਕਰਦਾ ਹੈ, ਉਸ ਟ੍ਰੈਫਿਕ 'ਤੇ ਪੂਰੀ 78-95% ਰੇਂਜ ਦੇਖੇਗਾ। ਇੱਕ ਸਿੰਗਲ ਸੈਸ਼ਨ ਦੀ ਘੱਟ ਕੁੱਲ ਬਚਤ ਪ੍ਰਤੀਸ਼ਤਤਾ ਨੂੰ ਇਸ ਗੱਲ ਦੇ ਸਬੂਤ ਵਜੋਂ ਨਾ ਵਰਤੋ ਕਿ ਕੰਪਰੈਸ਼ਨ ਗਲਤ ਢੰਗ ਨਾਲ ਕੌਂਫਿਗਰ ਕੀਤਾ ਗਿਆ ਹੈ — ਪਹਿਲਾਂ ਜਾਂਚ ਕਰੋ ਕਿ ਕੀ ਅੰਡਰਲਾਈੰਗ ਟੂਲ ਆਉਟਪੁੱਟ ਅਸਲ ਵਿੱਚ ਬੇਲੋੜੀ ਸੀ।

## ਸੰਰਚਨਾ

### ਡੈਸ਼ਬੋਰਡ

`Dashboard → Context & Cache` 'ਤੇ ਜਾਓ:

- **ਕੇਵਮੈਨ** — ਮੋਡ ਚੋਣ, ਭਾਸ਼ਾ ਪੈਕ, ਪੂਰਵਦਰਸ਼ਨ, ਅਤੇ ਗਲੋਬਲ ਡਿਫਾਲਟਸ
- **RTK** — ਕਮਾਂਡ-ਫਿਲਟਰ ਪੂਰਵਦਰਸ਼ਨ, RTK ਸੁਰੱਖਿਆ ਸੈਟਿੰਗਾਂ, ਅਤੇ ਫਿਲਟਰ ਕੈਟਾਲਾਗ
- **ਕੰਪਰੈਸ਼ਨ ਕੰਬੋਜ਼** — ਰੂਟਿੰਗ ਕੰਬੋਜ਼ ਨੂੰ ਨਿਰਧਾਰਤ ਨਾਮੀ ਇੰਜਣ ਪਾਈਪਲਾਈਨਾਂ
- **ਆਟੋ-ਟ੍ਰਿਗਰ ਥ੍ਰੈਸ਼ਹੋਲਡ** — ਜਦੋਂ ਟੋਕਨ ਗਿਣਤੀ ਥ੍ਰੈਸ਼ਹੋਲਡ ਤੋਂ ਵੱਧ ਜਾਂਦੀ ਹੈ ਤਾਂ ਆਪਣੇ ਆਪ ਕੰਪਰੈਸ਼ਨ ਸ਼ੁਰੂ ਕਰੋ

### ਪ੍ਰਤੀ-ਕੰਬੋ ਓਵਰਰਾਈਡ

`Dashboard → Context & Cache → Compression Combos` ਵਿੱਚ, ਇੱਕ ਰੂਟਿੰਗ ਕੰਬੋ ਨੂੰ ਇੱਕ ਕੰਪਰੈਸ਼ਨ ਕੰਬੋ ਨਿਰਧਾਰਤ ਕਰੋ:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

ਇਹ ਤੁਹਾਨੂੰ ਮੁਫਤ/ਕੋਡਿੰਗ ਪ੍ਰਦਾਤਾਵਾਂ 'ਤੇ ਸਟੈਕਡ ਕੰਪਰੈਸ਼ਨ ਦੀ ਵਰਤੋਂ ਕਰਨ ਦਿੰਦਾ ਹੈ ਜਦੋਂ ਕਿ ਅਦਾਇਗੀ ਗਾਹਕੀਆਂ 'ਤੇ ਲਾਈਟ ਮੋਡ ਰੱਖਿਆ ਜਾਂਦਾ ਹੈ।

ਇਹ "ਪ੍ਰਤੀ-ਕੰਬੋ ਓਵਰਰਾਈਡ" ਅਸਾਈਨਮੈਂਟ **ਰੂਟਿੰਗ-ਕੰਬੋ ਕੰਪਰੈਸ਼ਨ ਮੋਡ** ਓਵਰਰਾਈਡ (Default/Off/Lite/Standard/Aggressive/Ultra) ਤੋਂ ਇੱਕ ਵੱਖਰਾ ਨਿਯੰਤਰਣ ਹੈ — ਉਹ ਓਵਰਰਾਈਡ ਇੱਕ ਨਾਮੀ ਕੰਪਰੈਸ਼ਨ-ਕੰਬੋ ਪਾਈਪਲਾਈਨ ਨਹੀਂ ਚੁਣਦਾ; ਇਹ ਸਿਰਫ਼ `compressionMode` ਫੀਲਡ ਨੂੰ ਸੈੱਟ ਕਰਦਾ ਹੈ ਜਿਸਦੀ `resolveCompressionPlan` ਦੁਆਰਾ ਸਲਾਹ ਲਈ ਜਾਂਦੀ ਹੈ। ਇਸਨੂੰ ਕੰਬੋ ਕਾਰਡ (`Dashboard → Combos`) 'ਤੇ ਜਾਂ, #6760 ਤੋਂ, `Dashboard → Context & Cache → Compression Combos` 'ਤੇ "Assign to routing" ਸੂਚੀ ਵਿੱਚ ਪ੍ਰਤੀ ਰੂਟਿੰਗ ਕੰਬੋ ਸੈੱਟ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ, ਜੋ ਉੱਪਰ ਦਸਤਾਵੇਜ਼ੀ ਪਾਈਪਲਾਈਨ-ਅਸਾਈਨਮੈਂਟ ਚੈੱਕਬਾਕਸ ਦੇ ਬਿਲਕੁਲ ਨਾਲ ਹੈ। ਦੋਵੇਂ ਸਤਹਾਂ ਉਸੇ `PUT /api/combos/{id}` ਐਂਡਪੁਆਇੰਟ ਰਾਹੀਂ ਬਰਕਰਾਰ ਰਹਿੰਦੀਆਂ ਹਨ।

### ਪ੍ਰਤੀ-ਬੇਨਤੀ ਓਵਰਰਾਈਡ

ਇੱਕ ਸਿੰਗਲ ਬੇਨਤੀ ਲਈ ਕੰਪਰੈਸ਼ਨ ਪਲਾਨ ਨੂੰ ਓਵਰਰਾਈਡ ਕਰਨ ਲਈ `x-omniroute-compression` ਬੇਨਤੀ ਹੈਡਰ ਭੇਜੋ। ਇਸਦੀ ਸਭ ਤੋਂ ਉੱਚੀ ਤਰਜੀਹ ਹੈ — ਇਹ ਰੂਟਿੰਗ-ਕੰਬੋ ਓਵਰਰਾਈਡ, ਐਕਟਿਵ ਪ੍ਰੋਫਾਈਲ, ਆਟੋ-ਟ੍ਰਿਗਰ, ਅਤੇ ਪੈਨਲ ਡਿਫਾਲਟ ਨੂੰ ਹਰਾਉਂਦਾ ਹੈ। ਅਣਜਾਣ ਮੁੱਲਾਂ ਨੂੰ ਅਣਡਿੱਠਾ ਕਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ (ਬੇਨਤੀ ਕਦੇ ਵੀ ਰੱਦ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ) ਅਤੇ ਗਲੋਬਲ ਮਾਸਟਰ ਸਵਿੱਚ ਅਜੇ ਵੀ ਸਭ ਕੁਝ ਨਿਯੰਤਰਿਤ ਕਰਦਾ ਹੈ: ਜਦੋਂ ਕੰਪਰੈਸ਼ਨ ਗਲੋਬਲੀ ਬੰਦ ਹੁੰਦਾ ਹੈ, ਤਾਂ ਹੈਡਰ ਇਸਨੂੰ ਚਾਲੂ ਨਹੀਂ ਕਰ ਸਕਦਾ। ਮੁੱਲ:

| ਮੁੱਲ          | ਪ੍ਰਭਾਵ                                                                                                    |
| ------------- | --------------------------------------------------------------------------------------------------------- |
| `off`         | ਇਸ ਬੇਨਤੀ ਲਈ ਕੋਈ ਕੰਪਰੈਸ਼ਨ ਨਹੀਂ।                                                                            |
| `default`     | ਪੈਨਲ-ਡਰਾਈਵਡ ਡਿਫਾਲਟ ਪ੍ਰੋਫਾਈਲ (ਐਕਟਿਵ ਪ੍ਰੋਫਾਈਲ ਨੂੰ ਅਣਡਿੱਠਾ ਕਰਦਾ ਹੈ)। ਲੌਸੀ ਇੰਜਣ ਬੰਦ ਰੱਖੇ ਜਾਂਦੇ ਹਨ।            |
| `safe`        | ਹੈਡਰ ਨੂੰ ਛੱਡਣ ਦੇ ਸਮਾਨ: ਸਿਰਫ਼ ਡੀਡੁਪ ਅਤੇ ਵ੍ਹਾਈਟਸਪੇਸ ਫੋਲਡਿੰਗ।                                                |
| `allow-lossy` | ਇਸ ਬੇਨਤੀ ਦੀ ਆਪਰੇਟਰ ਯੋਜਨਾ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖੋ, ਜਿਸ ਵਿੱਚ ਸਾਰਾਂਸ਼, ਪ੍ਰਸੰਗਿਕਤਾ ਫਿਲਟਰ, ਅਤੇ ਸਟਾਈਲ ਰੀਰਾਈਟਸ ਸ਼ਾਮਲ ਹਨ। |
| `engine:<id>` | ਸਮਰੱਥ ਹੋਣ 'ਤੇ ਇੱਕ ਸਿੰਗਲ ਇੰਜਣ, ਜਿਵੇਂ ਕਿ `engine:rtk`। ਇਹ ਉਸ ਇੰਜਣ ਲਈ ਪ੍ਰਤੀ-ਬੇਨਤੀ ਆਪਟ-ਇਨ ਹੈ।                 |
| `<combo>`     | ਇੱਕ ਨਾਮੀ ਕੰਬੋ, ਪਹਿਲਾਂ ਨਾਮ ਦੁਆਰਾ (ਕੇਸ-ਅਸੰਵੇਦਨਸ਼ੀਲ), ਫਿਰ ਆਈਡੀ ਦੁਆਰਾ ਮੇਲ ਖਾਂਦਾ ਹੈ।                           |

`allow-lossy`, `engine:<id>`, ਜਾਂ ਇੱਕ ਨਾਮੀ ਕੰਬੋ ਤੋਂ ਬਿਨਾਂ, ਲੌਸੀ ਇੰਜਣ ਲਾਗੂ ਨਹੀਂ ਕੀਤੇ ਜਾਂਦੇ। ਜਦੋਂ ਕੰਪਰੈਸ਼ਨ ਚਾਲੂ ਹੁੰਦਾ ਹੈ ਤਾਂ ਬੇਨਤੀ ਨੂੰ ਅਜੇ ਵੀ ਸੈਸ਼ਨ ਡੀਡੁਪ ਅਤੇ ਵ੍ਹਾਈਟਸਪੇਸ ਫੋਲਡਿੰਗ ਮਿਲਦੀ ਹੈ।

ਲਾਗੂ ਕੀਤੀ ਯੋਜਨਾ `X-OmniRoute-Compression: <mode>; source=<source>` ਰਿਸਪਾਂਸ ਹੈਡਰ ਵਿੱਚ ਵਾਪਸ ਗੂੰਜਦੀ ਹੈ, ਜਿੱਥੇ `<source>` `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, ਜਾਂ `off` ਵਿੱਚੋਂ ਇੱਕ ਹੈ।

## ਐਡਵਾਂਸਡ ਕੰਪਰੈਸ਼ਨ ਸਿਸਟਮ

7 ਸਟੈਂਡਰਡ ਮੋਡਾਂ ਤੋਂ ਇਲਾਵਾ, ਓਮਨੀਰੂਟ ਵਿੱਚ ਕਈ ਐਡਵਾਂਸਡ ਕੰਪਰੈਸ਼ਨ ਸਿਸਟਮ ਸ਼ਾਮਲ ਹਨ ਜੋ ਪ੍ਰਸੰਗ ਦੇ ਅਧਾਰ 'ਤੇ ਆਪਣੇ ਆਪ ਕੰਮ ਕਰਦੇ ਹਨ।

### ਕੈਸ਼-ਅਵੇਅਰ ਕੰਪਰੈਸ਼ਨ

ਕੁਝ ਪ੍ਰਦਾਤਾ (ਜਿਵੇਂ ਕਿ ਪ੍ਰੋਂਪਟ ਕੈਚਿੰਗ ਵਾਲੇ ਐਂਥ੍ਰੋਪਿਕ) **ਪ੍ਰੋਂਪਟ ਕੈਚਿੰਗ** ਦਾ ਸਮਰਥਨ ਕਰਦੇ ਹਨ, ਜੋ ਉਹਨਾਂ ਨੂੰ ਲਾਗਤਾਂ ਅਤੇ ਲੇਟੈਂਸੀ ਨੂੰ ਘਟਾਉਣ ਲਈ ਪ੍ਰੋਂਪਟ ਦੇ ਹਿੱਸਿਆਂ ਨੂੰ ਕੈਸ਼ ਕਰਨ ਦਿੰਦਾ ਹੈ। ਜਦੋਂ ਕੈਚਿੰਗ ਸਮਰੱਥ ਹੁੰਦੀ ਹੈ, ਤਾਂ ਹਮਲਾਵਰ ਕੰਪਰੈਸ਼ਨ ਅਸਲ ਵਿੱਚ ਪ੍ਰਦਰਸ਼ਨ ਨੂੰ **ਨੁਕਸਾਨ** ਪਹੁੰਚਾ ਸਕਦਾ ਹੈ ਕਿਉਂਕਿ ਇਹ ਕੈਸ਼ ਕੀਤੇ ਟੋਕਨਾਂ ਨੂੰ ਬਦਲਦਾ ਹੈ, ਕੈਸ਼ ਨੂੰ ਅਵੈਧ ਕਰਦਾ ਹੈ।

`cachingAware.ts` ਮੋਡੀਊਲ **ਕੈਚਿੰਗ ਪ੍ਰਸੰਗ ਦਾ ਪਤਾ ਲਗਾ ਕੇ** ਅਤੇ **ਉਸ ਅਨੁਸਾਰ ਕੰਪਰੈਸ਼ਨ ਰਣਨੀਤੀ ਨੂੰ ਵਿਵਸਥਿਤ ਕਰਕੇ** ਇਸਨੂੰ ਹੱਲ ਕਰਦਾ ਹੈ।

#### ਇਹ ਕਿਵੇਂ ਕੰਮ ਕਰਦਾ ਹੈ

1. **ਕੈਚਿੰਗ ਪ੍ਰਸੰਗ ਦਾ ਪਤਾ ਲਗਾਓ** — `cache_control` ਮਾਰਕਰਾਂ ਲਈ ਬੇਨਤੀ ਬਾਡੀ ਨੂੰ ਸਕੈਨ ਕਰਦਾ ਹੈ
2. **ਕੈਚਿੰਗ ਪ੍ਰਦਾਤਾਵਾਂ ਦੀ ਪਛਾਣ ਕਰੋ** — ਜਾਂਚ ਕਰਦਾ ਹੈ ਕਿ ਕੀ ਨਿਸ਼ਾਨਾ ਪ੍ਰਦਾਤਾ ਕੈਚਿੰਗ ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ
3. **ਰਣਨੀਤੀ ਨੂੰ ਵਿਵਸਥਿਤ ਕਰੋ** — ਕੈਚਿੰਗ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ `aggressive`/`ultra` ਨੂੰ `standard` ਵਿੱਚ ਡਾਊਨਗ੍ਰੇਡ ਕਰਦਾ ਹੈ
4. **ਸਿਸਟਮ ਪ੍ਰੋਂਪਟ ਛੱਡੋ** — ਸਿਸਟਮ ਪ੍ਰੋਂਪਟ ਆਮ ਤੌਰ 'ਤੇ ਕੈਸ਼ ਕੀਤੇ ਜਾਂਦੇ ਹਨ, ਇਸਲਈ ਉਹਨਾਂ ਨੂੰ ਸੰਕੁਚਿਤ ਨਾ ਕਰੋ
5. **ਨਿਰਧਾਰਤ ਪਰਿਵਰਤਨਾਂ ਦੀ ਵਰਤੋਂ ਕਰੋ** — ਸਿਰਫ਼ ਉਹਨਾਂ ਪਰਿਵਰਤਨਾਂ ਦੀ ਵਰਤੋਂ ਕਰੋ ਜੋ ਇਕਸਾਰ ਆਉਟਪੁੱਟ ਪੈਦਾ ਕਰਦੇ ਹਨ

#### ਕੋਡ ਉਦਾਹਰਨ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← ਕੈਸ਼ ਮਾਰਕਰ
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ਕਦੋਂ ਵਰਤਣਾ ਹੈ

ਕੈਸ਼-ਅਵੇਅਰ ਕੰਪਰੈਸ਼ਨ **ਹਮੇਸ਼ਾ ਚਾਲੂ** ਹੁੰਦਾ ਹੈ — ਕਿਸੇ ਸੰਰਚਨਾ ਦੀ ਲੋੜ ਨਹੀਂ। ਇਹ ਸਿਰਫ਼ ਉਦੋਂ ਸ਼ੁਰੂ ਹੁੰਦਾ ਹੈ ਜਦੋਂ:

- ਬੇਨਤੀ ਵਿੱਚ `cache_control` ਮਾਰਕਰ ਹਨ
- ਨਿਸ਼ਾਨਾ ਪ੍ਰਦਾਤਾ ਪ੍ਰੋਂਪਟ ਕੈਚਿੰਗ ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ (ਐਂਥ੍ਰੋਪਿਕ, ਓਪਨਏਆਈ, ਆਦਿ)

### ਪ੍ਰਗਤੀਸ਼ੀਲ ਉਮਰ ਵਧਾਉਣਾ

ਲੰਬੀਆਂ ਗੱਲਬਾਤਾਂ ਵਿੱਚ ਬਹੁਤ ਸਾਰੇ ਸੰਦੇਸ਼ ਵਾਰੀ ਇਕੱਠੇ ਹੁੰਦੇ ਹਨ, ਪਰ ਪੁਰਾਣੀਆਂ ਵਾਰੀ ਘੱਟ ਸੰਬੰਧਿਤ ਹੋ ਜਾਂਦੀਆਂ ਹਨ। `progressiveAging.ts` ਮੋਡੀਊਲ **ਵਾਰੀ ਦੂਰੀ ਦੁਆਰਾ ਸੰਦੇਸ਼ਾਂ ਨੂੰ ਘਟਾਉਂਦਾ ਹੈ**:

- **ਹਾਲੀਆ ਵਾਰੀ (0-3)**: ਜਿਵੇਂ ਹੈ (ਪੂਰਾ ਵੇਰਵਾ) ਰੱਖਿਆ ਗਿਆ
- **ਮੱਧਮ ਵਾਰੀ (4-8)**: ਲਾਈਟ ਕੰਪਰੈਸ਼ਨ (ਵ੍ਹਾਈਟਸਪੇਸ, ਫਾਰਮੈਟਿੰਗ ਸਫਾਈ)
- **ਪੁਰਾਣੀਆਂ ਵਾਰੀ (9+)**: ਕੇਵਮੈਨ ਕੰਪਰੈਸ਼ਨ (ਫਿਲਰ ਹਟਾਉਣਾ, ਸੰਖੇਪਕਰਨ)
- **ਬਹੁਤ ਪੁਰਾਣੀਆਂ ਵਾਰੀ (20+)**: ਬਹੁਤ ਜ਼ਿਆਦਾ ਸੰਖੇਪ ਜਾਂ ਛੱਡ ਦਿੱਤੀਆਂ ਗਈਆਂ

#### ਕੋਡ ਉਦਾਹਰਨ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 ਹੋਰ ਵਾਰੀ ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // ਪਹਿਲੀਆਂ 3 ਵਾਰੀ: ਜਿਵੇਂ ਹੈ
  light: 8, // ਵਾਰੀ 4-8: ਲਾਈਟ ਕੰਪਰੈਸ਼ਨ
  moderate: 20, // ਵਾਰੀ 9-20: ਕੇਵਮੈਨ ਕੰਪਰੈਸ਼ਨ
  // ਵਾਰੀ 21+: ਭਾਰੀ ਸੰਖੇਪਕਰਨ
});

// saved = ਬਚਾਏ ਗਏ ਟੋਕਨਾਂ ਦੀ ਸੰਖਿਆ
```

#### ਕਦੋਂ ਵਰਤਣਾ ਹੈ

ਪ੍ਰਗਤੀਸ਼ੀਲ ਉਮਰ ਵਧਾਉਣਾ `aggressive` ਅਤੇ `ultra` ਮੋਡਾਂ ਲਈ **ਹਮੇਸ਼ਾ ਚਾਲੂ** ਹੁੰਦਾ ਹੈ। ਇਹ ਖਾਸ ਤੌਰ 'ਤੇ ਇਸ ਲਈ ਪ੍ਰਭਾਵਸ਼ਾਲੀ ਹੈ:

- ਲੰਬੇ ਸਮੇਂ ਤੱਕ ਚੱਲਣ ਵਾਲੇ ਕੋਡਿੰਗ ਸੈਸ਼ਨ
- ਕਈ ਦਿਨਾਂ ਦੀਆਂ ਗੱਲਬਾਤਾਂ
- ਬਹੁਤ ਸਾਰੇ ਟੂਲ ਕਾਲਾਂ ਵਾਲੇ ਏਜੰਟਿਕ ਵਰਕਫਲੋ

### ਕੇਵਮੈਨ ਆਉਟਪੁੱਟ ਮੋਡ

`outputMode.ts` ਮੋਡਿਊਲ ਮਾਡਲ ਨੂੰ ਸੰਕੁਚਿਤ, ਸੰਖੇਪ ਆਉਟਪੁੱਟ (ਇੱਕ "ਕੇਵਮੈਨ" ਸ਼ੈਲੀ) ਪੈਦਾ ਕਰਨ ਲਈ **ਸਿਸਟਮ ਪ੍ਰੋਂਪਟ ਨਿਰਦੇਸ਼** ਦਿੰਦਾ ਹੈ।

#### ਇਹ ਕਿਵੇਂ ਕੰਮ ਕਰਦਾ ਹੈ

ਇਨਪੁੱਟ ਨੂੰ ਸੰਕੁਚਿਤ ਕਰਨ ਦੀ ਬਜਾਏ, ਇਹ ਮੋਡ ਇੱਕ ਸਿਸਟਮ ਪ੍ਰੋਂਪਟ ਜੋੜਦਾ ਹੈ ਜਿਵੇਂ:

> "ਘੱਟੋ-ਘੱਟ ਸ਼ਬਦਾਂ ਵਿੱਚ ਜਵਾਬ ਦਿਓ। ਸ਼ਿਸ਼ਟਾਚਾਰ ਛੱਡੋ। ਛੋਟੇ ਵਾਕਾਂ ਦੀ ਵਰਤੋਂ ਕਰੋ।"

ਇਹ ਖਾਸ ਤੌਰ 'ਤੇ ਇਸ ਲਈ ਵਧੀਆ ਕੰਮ ਕਰਦਾ ਹੈ:

- ਕੋਡ ਜਨਰੇਸ਼ਨ (ਵਧੇਰੇ ਸੰਖੇਪ ਆਉਟਪੁੱਟ = ਘੱਟ tokens)
- ਤੇਜ਼ Q&A (ਵਿਸਤ੍ਰਿਤ ਵਿਆਖਿਆਵਾਂ ਦੀ ਕੋਈ ਲੋੜ ਨਹੀਂ)
- ਬੈਚ ਪ੍ਰੋਸੈਸਿੰਗ (ਥਰੂਪੁੱਟ ਨੂੰ ਵੱਧ ਤੋਂ ਵੱਧ ਕਰਨਾ)

#### ਕਦੋਂ ਵਰਤਣਾ ਹੈ

ਕੇਵਮੈਨ ਆਉਟਪੁੱਟ ਮੋਡ **ਆਪਟ-ਇਨ** ਹੈ — ਇਸਨੂੰ ਕੰਬੋ ਕੌਂਫਿਗ ਰਾਹੀਂ ਸੈੱਟ ਕਰੋ:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "outputMode": "caveman"
    }
  }
}
```

#### ਇੰਜੈਕਸ਼ਨ ਕਿਵੇਂ ਕੰਮ ਕਰਦਾ ਹੈ

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ਕੈਟਾਲਾਗ ਦੇ ਵਿਰੁੱਧ ਚੋਣ ਨੂੰ ਹੱਲ ਕਰਦਾ ਹੈ (ਅਣਜਾਣ ਆਈਡੀਜ਼ ਅਤੇ ਲੋਕੇਲ-ਮੇਲ ਨਾ ਖਾਂਦੀਆਂ ਸਟਾਈਲਾਂ ਨੂੰ ਛੱਡ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ, ਕਦੇ ਗਲਤੀ ਨਹੀਂ ਹੁੰਦੀ), ਚੁਣੇ ਗਏ ਨਿਰਦੇਸ਼ਾਂ ਨੂੰ ਕੈਟਾਲਾਗ ਕ੍ਰਮ ਵਿੱਚ ਜੋੜਦਾ ਹੈ, ਸੀਮਾਵਾਂ ਧਾਰਾ ਨੂੰ **ਇੱਕ ਵਾਰ** ਜੋੜਦਾ ਹੈ, ਅਤੇ ਨਤੀਜੇ ਨੂੰ ਇੱਕ ਸਿੰਗਲ idempotency ਮਾਰਕਰ (`[OmniRoute Output Styles]`) ਦੇ ਪਿੱਛੇ ਸਿਸਟਮ ਪ੍ਰੋਂਪਟ ਵਿੱਚ ਅੱਗੇ ਲੋਡ ਕਰਦਾ ਹੈ — ਦੁਬਾਰਾ ਲਾਗੂ ਕਰਨਾ ਇੱਕ no-op ਹੈ। ਜਦੋਂ ਖੋਜੀ ਗਈ ਬੇਨਤੀ ਭਾਸ਼ਾ ਦਾ ਅਨੁਵਾਦ ਹੁੰਦਾ ਹੈ, ਤਾਂ ਅੰਗਰੇਜ਼ੀ ਦੀ ਬਜਾਏ ਸਥਾਨਕ ਨਿਰਦੇਸ਼ ਇੰਜੈਕਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

#### ਕਿਵੇਂ ਸਮਰੱਥ ਕਰਨਾ ਹੈ

ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ: **Context → Settings → Compression** — ਹਰੇਕ ਸਟਾਈਲ ਲਈ ਇੱਕ ਚਾਲੂ/ਬੰਦ ਟੌਗਲ ਅਤੇ ਇੱਕ ਪੱਧਰ ਚੋਣਕਾਰ ਦੇ ਨਾਲ ਇੱਕ ਕਤਾਰ। ਪ੍ਰੋਗਰਾਮੇਟਿਕ ਤੌਰ 'ਤੇ, ਕੰਪਰੈਸ਼ਨ ਕੌਂਫਿਗ ਚੋਣ ਨੂੰ ਇਸ ਤਰ੍ਹਾਂ ਬਰਕਰਾਰ ਰੱਖਦਾ ਹੈ:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

ਬੈਕ-ਕੰਪੈਟ: ਲੈਗਸੀ `outputMode: "caveman"` ਕੰਬੋ ਸੈਟਿੰਗ ਅਜੇ ਵੀ ਕੰਮ ਕਰਦੀ ਹੈ ਅਤੇ `terse-prose` ਨਾਲ ਮੈਪ ਕਰਦੀ ਹੈ, ਹਰ ਲੈਗਸੀ ਭਾਸ਼ਾ ਵਿੱਚ ਪੁਰਾਣੇ ਇੰਜੈਕਸ਼ਨ ਦੇ ਬਾਈਟ-ਆਈਡੈਂਟਿਕਲ।

ਭਾਸ਼ਾ ਚੋਣ: `languageConfig.enabled` ਚਾਲੂ ਹੋਣ 'ਤੇ, `autoDetect` ਨਵੀਨਤਮ ਉਪਭੋਗਤਾ ਸੰਦੇਸ਼ ਦੀ ਭਾਸ਼ਾ ਚੁਣਦਾ ਹੈ (ਇਨਪੁੱਟ ਇੰਜਣਾਂ ਦੇ ਸਮਾਨ ਡਿਟੈਕਟਰ); `autoDetect` ਨੂੰ ਬੰਦ ਕਰਨ ਨਾਲ `defaultLanguage` ਪਿੰਨ ਹੋ ਜਾਂਦਾ ਹੈ। ਬੰਦ → ਅੰਗਰੇਜ਼ੀ।

ਸਟਾਈਲ × ਭਾਸ਼ਾ ਮੈਟ੍ਰਿਕਸ `tests/unit/compression/output-styles-i18n-matrix.test.ts` ਦੁਆਰਾ ਪਿੰਨ ਕੀਤਾ ਗਿਆ ਹੈ: ਇੱਕ ਨਵਾਂ ਸਟਾਈਲ ਘੱਟੋ-ਘੱਟ pt-BR ਅਨੁਵਾਦ (ਜਾਂ ਇੱਕ ਸਪੱਸ਼ਟ ਟਰੈਕ ਕੀਤੀ ਛੋਟ) ਤੋਂ ਬਿਨਾਂ ਸ਼ਿਪ ਨਹੀਂ ਹੋ ਸਕਦਾ, ਅਤੇ ਇੱਕ ਮੌਜੂਦਾ ਸਟਾਈਲ ਚੁੱਪਚਾਪ ਇੱਕ ਲੋਕੇਲ ਨਹੀਂ ਗੁਆ ਸਕਦਾ। ਇੱਕ ਸਟਾਈਲ ਜੋੜਨ ਲਈ, [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) ਦੇਖੋ।

### ਟੂਲ ਨਤੀਜਾ ਕੰਪਰੈਸ਼ਨ

`toolResultCompressor.ts` ਮੋਡਿਊਲ ਟੂਲ ਨਤੀਜਿਆਂ (ਫੰਕਸ਼ਨ ਕਾਲਾਂ, ਏਜੰਟ ਆਉਟਪੁੱਟ, ਖੋਜ ਨਤੀਜੇ, ਆਦਿ) ਲਈ **5 ਵਿਸ਼ੇਸ਼ ਕੰਪਰੈਸ਼ਨ ਰਣਨੀਤੀਆਂ** ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ:

1.  **ਖੋਜ ਨਤੀਜਾ ਕੰਪਰੈਸ਼ਨ** — ਬੇਲੋੜੇ ਨਤੀਜਿਆਂ ਨੂੰ ਹਟਾਉਂਦਾ ਹੈ, ਸਿਖਰਲੇ-N ਨੂੰ ਰੱਖਦਾ ਹੈ
2.  **ਫਾਈਲ ਰੀਡ ਕੰਪਰੈਸ਼ਨ** — ਵੱਡੀਆਂ ਫਾਈਲਾਂ ਨੂੰ ਛੋਟਾ ਕਰਦਾ ਹੈ, ਹੈਡਰ/ਇੰਪੋਰਟਸ ਨੂੰ ਸੁਰੱਖਿਅਤ ਰੱਖਦਾ ਹੈ
3.  **ਕੋਡ ਐਗਜ਼ੀਕਿਊਸ਼ਨ ਕੰਪਰੈਸ਼ਨ** — ਸਿਰਫ ਜ਼ਰੂਰੀ stdout/stderr ਨੂੰ ਰੱਖਦਾ ਹੈ
4.  **ਡੇਟਾਬੇਸ ਕੁਏਰੀ ਕੰਪਰੈਸ਼ਨ** — ਕਤਾਰਾਂ ਨੂੰ ਸੀਮਿਤ ਕਰਦਾ ਹੈ, ਵਿਸਤ੍ਰਿਤ ਮੈਟਾਡੇਟਾ ਨੂੰ ਹਟਾਉਂਦਾ ਹੈ
5.  **API ਰਿਸਪਾਂਸ ਕੰਪਰੈਸ਼ਨ** — ਨਲ ਖੇਤਰਾਂ ਨੂੰ ਹਟਾਉਂਦਾ ਹੈ, ਐਰੇ ਨੂੰ ਸੰਘਣਾ ਕਰਦਾ ਹੈ

#### ਕਦੋਂ ਵਰਤਣਾ ਹੈ

ਟੂਲ ਨਤੀਜਾ ਕੰਪਰੈਸ਼ਨ **ਹਮੇਸ਼ਾ ਚਾਲੂ** ਹੁੰਦਾ ਹੈ ਜਦੋਂ ਟੂਲ ਕਾਲਾਂ ਮੌਜੂਦ ਹੁੰਦੀਆਂ ਹਨ। ਕਿਸੇ ਕੌਂਫਿਗਰੇਸ਼ਨ ਦੀ ਲੋੜ ਨਹੀਂ।

### ਸਟੈਕਡ ਪਾਈਪਲਾਈਨ

ਸਟੈਕਡ ਮੋਡ **ਕਈ ਇੰਜਣਾਂ ਨੂੰ ਕ੍ਰਮਵਾਰ** ਚਲਾਉਂਦਾ ਹੈ — ਆਮ ਤੌਰ 'ਤੇ ਪਹਿਲਾਂ RTK (ਟੂਲ ਆਉਟਪੁੱਟ 'ਤੇ 60-90% ਬਚਤ), ਫਿਰ ਕੇਵਮੈਨ (ਬਾਕੀ ਬਚੇ ਟੈਕਸਟ 'ਤੇ 30% ਵਾਧੂ ਬਚਤ)। ਇਸ ਨਾਲ **ਕੁੱਲ 78-95% ਬਚਤ** ਹੁੰਦੀ ਹੈ।

#### ਇਹ ਕਿਵੇਂ ਕੰਮ ਕਰਦਾ ਹੈ

```
Input (1000 tokens)
  → RTK (command-aware filter) → 200 tokens
    → Caveman (filler removal) → 140 tokens
  → Output (140 tokens, 86% savings)
```

#### ਕਦੋਂ ਵਰਤਣਾ ਹੈ

ਸਟੈਕਡ ਮੋਡ ਦੀ ਵਰਤੋਂ ਇਸ ਲਈ ਕਰੋ:

- ਟੂਲ-ਭਾਰੀ ਵਰਕਫਲੋਜ਼ (ਏਜੰਟਿਕ ਕੋਡਿੰਗ, ਖੋਜ)
- ਲਾਗਤ-ਸੰਵੇਦਨਸ਼ੀਲ ਬੈਚ ਪ੍ਰੋਸੈਸਿੰਗ
- ਜਦੋਂ ਤੁਹਾਨੂੰ ਵੱਧ ਤੋਂ ਵੱਧ ਟੋਕਨ ਬਚਤ ਦੀ ਲੋੜ ਹੋਵੇ

ਕੰਬੋ ਰਾਹੀਂ ਕੌਂਫਿਗਰ ਕਰੋ:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "modePack": "stacked"
    }
  }
}
```

## ਕੰਪਰੈਸ਼ਨ ਕੰਬੋ ਓਵਰਰਾਈਡਜ਼

ਤੁਸੀਂ ਵੱਖ-ਵੱਖ ਵਰਤੋਂ ਦੇ ਮਾਮਲਿਆਂ ਲਈ ਵਿਵਹਾਰ ਨੂੰ ਬਿਹਤਰ ਬਣਾਉਣ ਲਈ **ਪ੍ਰਤੀ ਕੰਬੋ** ਗਲੋਬਲ ਕੰਪਰੈਸ਼ਨ ਮੋਡ ਨੂੰ ਓਵਰਰਾਈਡ ਕਰ ਸਕਦੇ ਹੋ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "auto": {
      "weights": { "taskFit": 0.5 },
      "modePack": "quality-first"
    }
  },
  "compressionOverride": {
    "mode": "aggressive",
    "stackedPipelines": ["rtk", "caveman"],
    "preserveToolDefinitions": true
  }
}
```

ਇਹ ਇਹਨਾਂ ਲਈ ਲਾਭਦਾਇਕ ਹੈ:

- **ਕੋਡਿੰਗ ਕੰਬੋਜ਼**: ਲੰਬੇ ਸੈਸ਼ਨਾਂ ਲਈ `aggressive` ਮੋਡ ਦੀ ਵਰਤੋਂ ਕਰੋ
- **ਤੁਰੰਤ ਸਵਾਲ-ਜਵਾਬ ਕੰਬੋਜ਼**: ਤੇਜ਼ ਜਵਾਬਾਂ ਲਈ `lite` ਮੋਡ ਦੀ ਵਰਤੋਂ ਕਰੋ
- **ਟੂਲ-ਹੈਵੀ ਕੰਬੋਜ਼**: ਵੱਧ ਤੋਂ ਵੱਧ ਬਚਤ ਲਈ `stacked` ਮੋਡ ਦੀ ਵਰਤੋਂ ਕਰੋ
- **ਪ੍ਰੋਡਕਸ਼ਨ ਕੰਬੋਜ਼**: ਕੈਚਿੰਗ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ `cache-aware` ਮੋਡ ਦੀ ਵਰਤੋਂ ਕਰੋ
