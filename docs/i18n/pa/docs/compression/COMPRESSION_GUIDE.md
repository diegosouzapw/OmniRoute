## ਸੰਖੇਪ ਜਾਣਕਾਰੀ

OmniRoute ਇੱਕ ਮੋਡੀਊਲਰ ਪ੍ਰੌਂਪਟ ਕੰਪ੍ਰੈਸ਼ਨ ਪਾਈਪਲਾਈਨ ਲਾਗੂ ਕਰਦਾ ਹੈ ਜੋ ਬੇਨਤੀਆਂ ਦੇ ਅੱਪਸਟ੍ਰੀਮ ਪ੍ਰਦਾਤਾਵਾਂ ਤੱਕ ਪਹੁੰਚਣ ਤੋਂ **ਪਹਿਲਾਂ ਹੀ ਸਰਗਰਮੀ ਨਾਲ** ਚੱਲਦੀ ਹੈ। ਇਸਦਾ ਮਤਲਬ ਹੈ ਕਿ ਤੁਹਾਡੀ ਟੋਕਨ ਬਚਤ ਪਾਰਦਰਸ਼ੀ ਢੰਗ ਨਾਲ ਹੁੰਦੀ ਹੈ — ਤੁਹਾਡੇ ਵਰਕਫ਼ਲੋ ਵਿੱਚ ਕਿਸੇ ਤਬਦੀਲੀ ਦੀ ਲੋੜ ਨਹੀਂ।

```
ਕਲਾਇੰਟ ਬੇਨਤੀ
  → ਕੰਪ੍ਰੈਸ਼ਨ ਰਣਨੀਤੀ ਚੋਣਕਾਰ
    → ਕੌਂਬੋ ਓਵਰਰਾਈਡ? → ਕੌਂਬੋ ਸੈਟਿੰਗ ਵਰਤੋ
    → ਸਵੈ-ਚਾਲੂ ਥ੍ਰੈਸ਼ਹੋਲਡ? → ਆਟੋ ਮੋਡ ਵਰਤੋ
    → ਡਿਫੌਲਟ ਮੋਡ? → ਗਲੋਬਲ ਸੈਟਿੰਗ ਵਰਤੋ
    → ਬੰਦ? → ਕੰਪ੍ਰੈਸ਼ਨ ਛੱਡੋ
  → ਚੁਣਿਆ ਹੋਇਆ ਕੰਪ੍ਰੈਸ਼ਨ ਮੋਡ
    → ਬੰਦ: ਕੋਈ ਕੰਪ੍ਰੈਸ਼ਨ ਨਹੀਂ
    → ਲਾਈਟ: ਸੁਰੱਖਿਅਤ ਖਾਲੀ ਥਾਂ/ਫਾਰਮੈਟਿੰਗ ਸਫ਼ਾਈ (~15%)
    → ਸਟੈਂਡਰਡ: ਆਦਿਮ-ਸ਼ੈਲੀ ਦੇ ਫ਼ਾਲਤੂ ਸ਼ਬਦ ਹਟਾਉਣਾ (~30%)
    → ਅਗਰੈਸਿਵ: ਇਤਿਹਾਸ ਦੀ ਉਮਰ-ਅਧਾਰਿਤ ਛਾਂਟੀ + ਸੰਖੇਪੀਕਰਨ (~50%)
    → ਅਲਟਰਾ: ਹਿਊਰਿਸਟਿਕ ਛਾਂਟੀ + ਕੋਡ-ਬਲਾਕ ਪਤਲੇ ਕਰਨਾ (~75%)
    → RTK: ਕਮਾਂਡ-ਜਾਗਰੂਕ ਟਰਮੀਨਲ/ਟੂਲ-ਆਉਟਪੁੱਟ ਫਿਲਟਰਿੰਗ (60-90% ਅੱਪਸਟ੍ਰੀਮ ਸੀਮਾ)
    → ਸਟੈਕਡ: ਕ੍ਰਮਬੱਧ ਬਹੁ-ਇੰਜਣ ਪਾਈਪਲਾਈਨ, ਆਮ ਤੌਰ 'ਤੇ ਪਹਿਲਾਂ RTK ਫਿਰ Caveman (78-95% ਯੋਗ ਸੀਮਾ)
  → ਕੰਪ੍ਰੈੱਸ ਕੀਤੀ ਬੇਨਤੀ → ਪ੍ਰਦਾਤਾ
```

## ਕੰਪ੍ਰੈਸ਼ਨ ਮੋਡ

### ਬੰਦ

ਕੋਈ ਕੰਪ੍ਰੈਸ਼ਨ ਲਾਗੂ ਨਹੀਂ ਹੁੰਦੀ। ਸਾਰੇ ਸੁਨੇਹੇ ਬਿਨਾਂ ਕਿਸੇ ਤਬਦੀਲੀ ਦੇ ਅੱਗੇ ਭੇਜੇ ਜਾਂਦੇ ਹਨ।

### ਲਾਈਟ ਮੋਡ (~15% ਬਚਤ, <1ms ਲੇਟੈਂਸੀ)

ਸਭ ਤੋਂ ਸੁਰੱਖਿਅਤ ਮੋਡ — ਅਰਥ ਵਿੱਚ ਕੋਈ ਤਬਦੀਲੀ ਨਹੀਂ, ਸਿਰਫ਼ ਫਾਰਮੈਟਿੰਗ ਦੀ ਸਫ਼ਾਈ:

| ਤਕਨੀਕ                    | ਵੇਰਵਾ                                               |
| ------------------------ | --------------------------------------------------- |
| `collapseWhitespace`     | ਲਗਾਤਾਰ ਖਾਲੀ ਲਾਈਨਾਂ ਅਤੇ ਅੰਤਲੀਆਂ ਖਾਲੀ ਥਾਵਾਂ ਨੂੰ ਮਿਲਾਓ |
| `dedupSystemPrompt`      | ਡੁਪਲੀਕੇਟ ਸਿਸਟਮ ਸੁਨੇਹੇ ਹਟਾਓ                          |
| `compressToolResults`    | ਵਿਸਤ੍ਰਿਤ ਟੂਲ/ਫੰਕਸ਼ਨ ਆਉਟਪੁੱਟ ਨੂੰ ਕੰਪ੍ਰੈੱਸ ਕਰੋ        |
| `removeRedundantContent` | ਦੁਹਰਾਈਆਂ ਗਈਆਂ ਹਦਾਇਤਾਂ ਹਟਾਓ                          |
| `replaceImageUrls`       | base64 ਚਿੱਤਰ ਡਾਟਾ URIs ਨੂੰ ਛੋਟਾ ਕਰੋ                 |

**ਇਸ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ:** ਹਮੇਸ਼ਾ-ਚਾਲੂ ਵਰਤੋਂ, ਸੁਰੱਖਿਆ-ਨਾਜ਼ੁਕ ਵਰਕਫ਼ਲੋ।

### ਸਟੈਂਡਰਡ ਮੋਡ (~30% ਬਚਤ)

[Caveman](https://github.com/JuliusBrussee/caveman) ਤੋਂ ਪ੍ਰੇਰਿਤ — ਅਰਥ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦੇ ਹੋਏ ਫ਼ਾਲਤੂ ਸ਼ਬਦ ਅਤੇ ਬੇਲੋੜੀ ਵਿਸਤ੍ਰਿਤ ਵਾਕ-ਰਚਨਾ ਹਟਾਉਂਦਾ ਹੈ:

- ਫ਼ਾਲਤੂ ਸ਼ਬਦ ਹਟਾਉਂਦਾ ਹੈ ("ਕਿਰਪਾ ਕਰਕੇ", "ਮੇਰੇ ਖ਼ਿਆਲ ਵਿੱਚ", "ਮੂਲ ਰੂਪ ਵਿੱਚ", "ਅਸਲ ਵਿੱਚ")
- ਬੇਲੋੜੇ ਲੰਮੇ ਵਾਕਾਂਸ਼ ਸੰਖੇਪ ਕਰਦਾ ਹੈ ("ਕਰਨ ਦੇ ਉਦੇਸ਼ ਨਾਲ" → "ਕਰਨ ਲਈ", "ਦੇ ਨਤੀਜੇ ਵਜੋਂ" → "ਕਿਉਂਕਿ")
- ਨਿਮਰ ਅਨਿਸ਼ਚਿਤਤਾ ਵਾਲੀ ਭਾਸ਼ਾ ਹਟਾਉਂਦਾ ਹੈ ("ਕੀ ਤੁਹਾਨੂੰ ਇਤਰਾਜ਼ ਹੋਵੇਗਾ...", "ਜੇ ਤੁਸੀਂ ਸੰਭਵ ਤੌਰ 'ਤੇ ਕਰ ਸਕੋ...")
- ਕੋਡਿੰਗ ਪ੍ਰੌਂਪਟਾਂ ਲਈ ਅਨੁਕੂਲਿਤ 30+ regex ਨਿਯਮ

**ਇਸ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ:** ਰੋਜ਼ਾਨਾ ਕੋਡਿੰਗ ਵਰਕਫ਼ਲੋ, ਲਾਗਤ ਪ੍ਰਤੀ ਸਚੇਤ ਟੀਮਾਂ।

### ਅਗਰੈਸਿਵ ਮੋਡ (~50% ਬਚਤ)

ਲੰਮੇ ਸੈਸ਼ਨਾਂ ਲਈ ਸਮਾਰਟ ਇਤਿਹਾਸ ਪ੍ਰਬੰਧਨ:

- **ਸੁਨੇਹਾ ਏਜਿੰਗ** — ਪੁਰਾਣੇ ਸੁਨੇਹੇ ਕ੍ਰਮਵਾਰ ਵੱਧ ਕੰਪ੍ਰੈੱਸ ਹੁੰਦੇ ਜਾਂਦੇ ਹਨ
- **ਟੂਲ ਨਤੀਜਾ ਕੰਪ੍ਰੈਸ਼ਨ** — ਲੰਮੇ ਟੂਲ ਆਉਟਪੁੱਟ ਨੂੰ ਕੱਟਿਆ ਜਾਂ ਹਟਾਇਆ ਜਾਂਦਾ ਹੈ (ਪਹਿਲੀਆਂ/ਆਖ਼ਰੀ ਲਾਈਨਾਂ,
  ਮੇਲ ਖਾਂਦੀਆਂ ਲਾਈਨਾਂ ਦੀ ਫਿਲਟਰਿੰਗ, JSON ਕੁੰਜੀਆਂ ਦਾ ਸੰਕੁਚਨ)
- **ਸੰਰਚਨਾਤਮਕ ਅਖੰਡਤਾ ਸੁਰੱਖਿਆ** — ਯਕੀਨੀ ਬਣਾਉਂਦੀ ਹੈ ਕਿ `tool_use` + `tool_result` ਜੋੜੇ ਇਕਸਾਰ ਰਹਿਣ
- **ਸੰਦਰਭ ਵਿੰਡੋ ਜਾਗਰੂਕਤਾ** — ਹਰ ਮਾਡਲ ਦੀ ਟੋਕਨ ਸੀਮਾ ਦਾ ਆਦਰ ਕਰਦੀ ਹੈ

**ਇਸ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ:** ਵਿਸਤ੍ਰਿਤ ਡੀਬੱਗਿੰਗ ਸੈਸ਼ਨ, ਵੱਡੇ ਕੋਡਬੇਸ।

### ਅਲਟਰਾ ਮੋਡ (~75% ਬਚਤ)

ਟੋਕਨ-ਨਾਜ਼ੁਕ ਸਥਿਤੀਆਂ ਲਈ ਵੱਧ ਤੋਂ ਵੱਧ ਕੰਪ੍ਰੈਸ਼ਨ:

- **ਹਿਊਰਿਸਟਿਕ ਛਾਂਟੀ** — ਗੱਦ ਦੀ ਸਕੋਰ-ਅਧਾਰਿਤ ਟੋਕਨ ਛਾਂਟੀ
- **ਸੰਰਚਨਾ ਦੀ ਸੰਭਾਲ** — ਫੈਂਸ ਕੀਤੇ ਕੋਡ ਬਲਾਕ, ਇਨਲਾਈਨ ਕੋਡ, URLs ਅਤੇ ਪਛਾਣਕਰਤਾਵਾਂ ਨੂੰ
  ਟੌਮਸਟੋਨ ਕਰਕੇ ਮੁੜ ਸ਼ਬਦ-ਬ-ਸ਼ਬਦ ਜੋੜਿਆ ਜਾਂਦਾ ਹੈ, ਕਦੇ ਵੀ ਛਾਂਟਿਆ ਨਹੀਂ ਜਾਂਦਾ
- **ਵਿਕਲਪਿਕ SLM ਟੀਅਰ** — ਸੰਰਚਿਤ ਹੋਣ 'ਤੇ ਇੱਕ ਛੋਟਾ ਲੋਕਲ ਮਾਡਲ ਛਾਂਟੀ ਨੂੰ ਹੋਰ ਸੁਧਾਰ ਸਕਦਾ ਹੈ
- ਅਗਰੈਸਿਵ ਮੋਡ ਤੋਂ ਸੁਤੰਤਰ: ਇਹ ਸੁਨੇਹਾ ਏਜਿੰਗ, ਟੂਲ-ਨਤੀਜਾ ਕੰਪ੍ਰੈਸ਼ਨ
  ਜਾਂ ਫਾਲਬੈਕ ਸੰਖੇਪੀਕਰਨ ਨਹੀਂ ਚਲਾਉਂਦਾ (ਸਿਰਫ਼ SLM-ਟੀਅਰ ਦੀ ਅਸਫਲਤਾ ਹੀ ਫਾਲਬੈਕ ਪਾਸ ਨੂੰ
  ਅਗਰੈਸਿਵ ਰਾਹੀਂ ਭੇਜ ਸਕਦੀ ਹੈ)

**ਇਸ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ:** ਜਦੋਂ ਤੁਸੀਂ ਵਾਰ-ਵਾਰ ਸੰਦਰਭ ਸੀਮਾਵਾਂ ਤੱਕ ਪਹੁੰਚ ਰਹੇ ਹੋਵੋ।

### RTK ਮੋਡ (60-90% ਅੱਪਸਟ੍ਰੀਮ ਸੀਮਾ)

RTK ਮੋਡ ਕੋਡਿੰਗ-ਏਜੰਟ ਸੈਸ਼ਨਾਂ ਵਿੱਚ ਦਿਖਾਈ ਦੇਣ ਵਾਲੇ ਵਿਸਤ੍ਰਿਤ ਟੂਲ ਆਉਟਪੁੱਟ ਲਈ ਅਨੁਕੂਲਿਤ ਹੈ:

- `git status`, `git diff`, `git log`, ਟੈਸਟ ਰਨਰ,
  TypeScript/Vite/Webpack ਬਿਲਡ, ESLint/Biome/Prettier, npm ਆਡਿਟ/ਇੰਸਟਾਲ, Docker ਲੌਗ, ਇੰਫਰਾ
  ਆਉਟਪੁੱਟ ਅਤੇ ਆਮ ਸ਼ੈੱਲ ਆਉਟਪੁੱਟ ਵਰਗੀਆਂ ਕਮਾਂਡ/ਆਉਟਪੁੱਟ ਸ਼੍ਰੇਣੀਆਂ ਦੀ ਪਛਾਣ ਕਰਦਾ ਹੈ
- `open-sse/services/compression/engines/rtk/filters/` ਤੋਂ JSON ਫਿਲਟਰ ਪੈਕ ਲਾਗੂ ਕਰਦਾ ਹੈ
- ਪ੍ਰੋਜੈਕਟ ਜਾਂ ਗਲੋਬਲ `filters.toml` ਫਾਈਲਾਂ ਤੋਂ RTK TOML schema v1 ਫਿਲਟਰ ਇੰਪੋਰਟ ਕਰਦਾ ਹੈ, ਜਿਸ ਵਿੱਚ ਇਨਲਾਈਨ-ਟੈਸਟ
  ਪ੍ਰਮਾਣੀਕਰਨ ਅਤੇ ਪ੍ਰੋਜੈਕਟ ਫਾਈਲਾਂ ਲਈ ਭਰੋਸਾ-ਗੇਟਿੰਗ ਸ਼ਾਮਲ ਹੈ
- ਇਨਲਾਈਨ ਤਸਦੀਕੀ ਨਮੂਨਿਆਂ ਸਮੇਤ 55 ਬਿਲਟ-ਇਨ ਫਿਲਟਰ ਪ੍ਰਦਾਨ ਕਰਦਾ ਹੈ
- ANSI ਕੰਟਰੋਲ ਕ੍ਰਮ, ਪ੍ਰਗਤੀ ਬਾਰ, ਦੁਹਰਾਈਆਂ ਲਾਈਨਾਂ ਅਤੇ ਗੈਰ-ਕਾਰਵਾਈਯੋਗ ਸ਼ੋਰ ਹਟਾਉਂਦਾ ਹੈ
- ਅਸਫਲਤਾਵਾਂ, ਗਲਤੀਆਂ, ਚੇਤਾਵਨੀਆਂ, ਬਦਲੀਆਂ ਫਾਈਲਾਂ, ਸੰਖੇਪ ਅਤੇ ਲੰਮੇ ਆਉਟਪੁੱਟ ਦਾ ਅੰਤਲਾ ਹਿੱਸਾ ਬਰਕਰਾਰ ਰੱਖਦਾ ਹੈ
- ਭਰੋਸਾ-ਗੇਟ ਕੀਤੇ ਪ੍ਰੋਜੈਕਟ ਫਿਲਟਰ, ਗਲੋਬਲ ਫਿਲਟਰ ਅਤੇ ਵਿਕਲਪਿਕ ਰੀਡੈਕਟ ਕੀਤੇ ਕੱਚੇ ਆਉਟਪੁੱਟ ਦੀ ਮੁੜ-ਪ੍ਰਾਪਤੀ ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ

**ਇਸ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ:** ਸ਼ੈੱਲ, ਬਿਲਡ, ਟੈਸਟ, git, grep ਅਤੇ ਫਾਈਲ-ਆਉਟਪੁੱਟ ਟ੍ਰਾਂਸਕ੍ਰਿਪਟਾਂ ਵਾਲੇ ਏਜੰਟ ਸੈਸ਼ਨ।

### ਸਟੈਕਡ ਮੋਡ (78-95% ਯੋਗ ਸੀਮਾ)

ਸਟੈਕਡ ਮੋਡ ਕਈ ਕੰਪ੍ਰੈਸ਼ਨ ਇੰਜਣਾਂ ਨੂੰ ਇੱਕ ਨਿਰਧਾਰਤ ਕ੍ਰਮ ਵਿੱਚ ਚਲਾਉਂਦਾ ਹੈ। ਡਿਫੌਲਟ ਪਾਈਪਲਾਈਨ ਹੈ:

```txt
RTK -> Caveman
```

ਇਹ ਕ੍ਰਮ ਪਹਿਲਾਂ ਟਰਮੀਨਲ/ਟੂਲ ਆਉਟਪੁੱਟ ਨੂੰ ਸੰਖੇਪ ਰੱਖਦਾ ਹੈ, ਫਿਰ ਬਾਕੀ ਬਚੇ ਕੁਦਰਤੀ-ਭਾਸ਼ਾ ਪ੍ਰੌਂਪਟ ਉੱਤੇ Caveman ਅਰਥਾਤਮਕ ਸੰਘਣਾਪਣ ਲਾਗੂ ਕਰਦਾ ਹੈ। ਸਟੈਕਡ ਪਾਈਪਲਾਈਨਾਂ ਨੂੰ ਗਲੋਬਲ ਤੌਰ 'ਤੇ ਜਾਂ ਰਾਊਟਿੰਗ ਕੌਂਬੋਜ਼ ਨੂੰ ਸੌਂਪੇ ਕੰਪ੍ਰੈਸ਼ਨ ਕੌਂਬੋਜ਼ ਰਾਹੀਂ ਸੰਰਚਿਤ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ।

**ਇਸ ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ:** ਵੱਡੇ ਟੂਲ ਲੌਗਾਂ ਦੇ ਨਾਲ ਮਨੁੱਖੀ ਹਦਾਇਤਾਂ ਜਾਂ ਸਹਾਇਕ ਸੰਖੇਪਾਂ ਵਾਲਾ ਮਿਲਿਆ-ਜੁਲਿਆ ਸੰਦਰਭ।

## ਅੱਪਸਟ੍ਰੀਮ ਬੱਚਤ ਦਾ ਹਿਸਾਬ

OmniRoute ਦੋ ਸਰੋਤਾਂ ਤੋਂ ਹੋਣ ਵਾਲੀ ਕੰਪ੍ਰੈਸ਼ਨ ਬੱਚਤ ਦਾ ਦਸਤਾਵੇਜ਼ੀਕਰਨ ਕਰਦਾ ਹੈ: ਅੱਪਸਟ੍ਰੀਮ ਪ੍ਰੋਜੈਕਟ ਬੈਂਚਮਾਰਕ ਅਤੇ
OmniRoute ਦੀ ਆਪਣੀ ਇੰਜਣ ਰਚਨਾ।

| ਸਰੋਤ    | ਇੱਥੇ ਵਰਤਿਆ ਗਿਆ ਅੱਪਸਟ੍ਰੀਮ README ਅੰਕ                                                                      |
| ------- | -------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` ਘੱਟ ਆਉਟਪੁੱਟ ਟੋਕਨ, `65%` ਬੈਂਚਮਾਰਕ ਔਸਤ ਆਉਟਪੁੱਟ ਬੱਚਤ, `22-87%` ਰੇਂਜ, ਅਤੇ `~46%` ਇਨਪੁੱਟ ਕੰਪ੍ਰੈਸ਼ਨ ਟੂਲ |
| RTK     | ਕਮਾਂਡ ਆਉਟਪੁੱਟ ਵਿੱਚ `60-90%` ਬੱਚਤ; ਨਮੂਨਾ ਸੈਸ਼ਨ `~118,000 -> ~23,900` ਟੋਕਨ, ਜਾਂ `79.7%` ਬਚਾਏ (`~80%`)      |

ਓਵਰਲੈਪ ਹੋਣ ਵਾਲੇ ਟੂਲ/ਕਾਂਟੈਕਸਟ ਪੇਲੋਡਾਂ ਲਈ, ਮੂਲ OmniRoute ਕੌਂਬੋ ਇੰਜਣਾਂ ਨੂੰ ਇਸ ਤਰ੍ਹਾਂ ਸਟੈਕ ਕਰਦਾ ਹੈ:

```txt
RTK -> Caveman
```

ਸੰਯੁਕਤ ਬੱਚਤ ਗੁਣਾਤਮਕ ਹੈ, ਜੋੜਾਤਮਕ ਨਹੀਂ:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ਇਹ `78-95%` ਅੰਕ ਉਦੋਂ ਲਾਗੂ ਹੁੰਦਾ ਹੈ ਜਦੋਂ RTK ਅਤੇ Caveman ਦੋਵੇਂ ਇੱਕੋ ਇਨਪੁੱਟ/ਕਾਂਟੈਕਸਟ ਪੇਲੋਡ ਨੂੰ ਘਟਾ ਸਕਦੇ ਹੋਣ।
Caveman ਰਿਸਪਾਂਸ ਆਉਟਪੁੱਟ ਮੋਡ ਵੱਖਰਾ ਹੈ: ਸਮਰੱਥ ਹੋਣ 'ਤੇ, Caveman ਦੀ ਆਪਣੀ ਆਉਟਪੁੱਟ ਬੱਚਤ (`65%`
ਔਸਤ, `~75%` ਮੁੱਖ ਅੰਕ, `22-87%` ਰੇਂਜ) ਵਰਤੋ। ਕੁੱਲ ਬਿਲਿੰਗ ਬੱਚਤ ਤੁਹਾਡੇ ਪ੍ਰੌਂਪਟ/ਆਉਟਪੁੱਟ ਮਿਸ਼ਰਣ 'ਤੇ ਨਿਰਭਰ ਕਰਦੀ ਹੈ।

### "ਯੋਗ" ਦਾ ਅਸਲ ਵਿੱਚ ਕੀ ਅਰਥ ਹੈ

15-95% ਦੀ ਮੁੱਖ ਰੇਂਜ ਅਸਲੀ ਹੈ, ਪਰ ਇਹ ਸਿਰਫ਼ **ਦੁਹਰਾਈ ਜਾਂ ਬੇਲੋੜੀ ਲੰਮੀ** ਸਮੱਗਰੀ 'ਤੇ ਲਾਗੂ ਹੁੰਦੀ ਹੈ — ਦੁਹਰਾਈਆਂ
ਗਲਤੀ ਲਾਈਨਾਂ, ਇੱਕ ਬਿਲਡ ਲੌਗ ਜੋ ਇੱਕੋ ਚੇਤਾਵਨੀ ਵਾਰ-ਵਾਰ ਦਿੰਦਾ ਹੈ, ਜਾਂ ਲੋੜ ਤੋਂ ਵੱਡਾ `grep`/ਫ਼ਾਈਲ-ਰੀਡ ਡੰਪ। ਇਸਦਾ
ਇਹ ਅਰਥ **ਨਹੀਂ** ਹੈ ਕਿ ਹਰ ਬੇਨਤੀ ਵਿੱਚ ਇੰਨੀ ਬੱਚਤ ਹੁੰਦੀ ਹੈ।

ਤਜਰਬੇ ਰਾਹੀਂ ਪ੍ਰਮਾਣਿਤ (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300 ਇੱਕੋ ਜਿਹੀਆਂ
ਗਲਤੀ ਲਾਈਨਾਂ ਵਾਲੇ Anthropic-ਆਕਾਰ ਦੇ `tool_result` ਬਲਾਕ ਉੱਤੇ ਇੱਕ `stacked` (RTK + Caveman) ਰਨ ਨੇ
**95.93% ਟੋਕਨ ਬੱਚਤ / 96.26% ਅੱਖਰ ਬੱਚਤ** ਪੈਦਾ ਕੀਤੀ — ਬਿਲਕੁਲ ਇਸ਼ਤਿਹਾਰੀ
ਰੇਂਜ ਦੇ ਅੰਦਰ। ਪਰ ਆਮ, ਗੈਰ-ਦੁਹਰਾਈ ਵਾਲੇ ਟੂਲ ਆਉਟਪੁੱਟ (ਇੱਕ ਸਾਫ਼ `grep` ਮੇਲ ਸੂਚੀ,
ਇੱਕ ਛੋਟੀ ਫ਼ਾਈਲ ਰੀਡ, ਆਮ ਗੱਲਬਾਤੀ ਲਿਖਤ) ਉੱਤੇ ਚਲਾਈ ਗਈ ਉਹੀ ਪਾਈਪਲਾਈਨ ਸਹੀ ਢੰਗ ਨਾਲ **ਲਗਭਗ-ਸਿਫ਼ਰ ਬੱਚਤ** ਪੈਦਾ ਕਰਦੀ ਹੈ, ਕਿਉਂਕਿ
ਹਟਾਉਣ ਲਈ ਕੁਝ ਵੀ ਦੁਹਰਾਇਆ ਹੋਇਆ ਨਹੀਂ ਹੁੰਦਾ ਅਤੇ `validateCompression()` (`validation.ts`) ਅਜਿਹੀ ਮੁੜ-ਲਿਖਤ ਭੇਜਣ ਤੋਂ ਇਨਕਾਰ ਕਰਦਾ ਹੈ ਜੋ
ਕੋਡ ਬਲਾਕਾਂ, URLs, ਸਿਰਲੇਖਾਂ, ਵਰਜਨਾਂ, ਜਾਂ ALL-CAPS ਕਾਂਸਟੈਂਟ ਆਈਡੈਂਟੀਫਾਇਰਾਂ ਨੂੰ ਹਟਾ ਜਾਂ ਬਦਲ ਦੇਵੇ।

ਇਹ ਉਮੀਦ ਕੀਤਾ ਗਿਆ, ਸੁਰੱਖਿਅਤ ਵਿਹਾਰ ਹੈ, ਕੋਈ ਬੱਗ ਨਹੀਂ: ਇੱਕ ਕੋਡਿੰਗ ਸੈਸ਼ਨ ਜੋ ਮੁੱਖ ਤੌਰ 'ਤੇ ਸਾਫ਼ ਫ਼ਾਈਲਾਂ ਨੂੰ ਪੜ੍ਹਦਾ/grep ਕਰਦਾ ਹੈ,
ਕੰਪ੍ਰੈਸ਼ਨ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਮਰੱਥ ਹੋਣ ਦੇ ਬਾਵਜੂਦ ਕੁੱਲ ਬੱਚਤ ਘੱਟ ਦੇਖੇਗਾ, ਜਦਕਿ ਇੱਕ ਅਜਿਹਾ ਸੈਸ਼ਨ ਜੋ ਅਸਫਲ ਹੋ ਰਹੇ
ਲੂਪ ਜਾਂ ਬਹੁਤ ਜ਼ਿਆਦਾ ਆਉਟਪੁੱਟ ਦੇਣ ਵਾਲੇ linter ਨਾਲ ਟਕਰਾਉਂਦਾ ਹੈ, ਉਸ ਟ੍ਰੈਫਿਕ ਉੱਤੇ ਪੂਰੀ 78-95% ਰੇਂਜ ਦੇਖੇਗਾ। ਕਿਸੇ ਇੱਕ ਸੈਸ਼ਨ ਦੀ
ਘੱਟ ਸਮੁੱਚੀ ਬੱਚਤ ਪ੍ਰਤੀਸ਼ਤ ਨੂੰ ਇਸ ਗੱਲ ਦੇ ਸਬੂਤ ਵਜੋਂ ਨਾ ਵਰਤੋ ਕਿ ਕੰਪ੍ਰੈਸ਼ਨ ਗਲਤ ਕੌਂਫਿਗਰ ਕੀਤਾ ਗਿਆ ਹੈ — ਪਹਿਲਾਂ ਜਾਂਚੋ ਕਿ
ਅਧਾਰਭੂਤ ਟੂਲ ਆਉਟਪੁੱਟ ਅਸਲ ਵਿੱਚ ਦੁਹਰਾਈ ਵਾਲਾ ਸੀ ਜਾਂ ਨਹੀਂ।

## ਸੰਰਚਨਾ

### ਡੈਸ਼ਬੋਰਡ

`Dashboard → Context & Cache` 'ਤੇ ਜਾਓ:

- **Caveman** — ਮੋਡ ਦੀ ਚੋਣ, ਭਾਸ਼ਾ ਪੈਕ, ਪੂਰਵਦਰਸ਼ਨ ਅਤੇ ਗਲੋਬਲ ਡਿਫਾਲਟ
- **RTK** — ਕਮਾਂਡ-ਫਿਲਟਰ ਪੂਰਵਦਰਸ਼ਨ, RTK ਸੁਰੱਖਿਆ ਸੈਟਿੰਗਾਂ ਅਤੇ ਫਿਲਟਰ ਕੈਟਾਲਾਗ
- **ਕੰਪ੍ਰੈਸ਼ਨ ਕੰਬੋ** — ਰਾਊਟਿੰਗ ਕੰਬੋਜ਼ ਨੂੰ ਨਿਰਧਾਰਤ ਕੀਤੀਆਂ ਨਾਮਿਤ ਇੰਜਣ ਪਾਈਪਲਾਈਨਾਂ
- **ਆਟੋ-ਟ੍ਰਿਗਰ ਥ੍ਰੈਸ਼ਹੋਲਡ** — ਟੋਕਨ ਗਿਣਤੀ ਦੇ ਥ੍ਰੈਸ਼ਹੋਲਡ ਤੋਂ ਵੱਧ ਜਾਣ 'ਤੇ ਆਪਣੇ-ਆਪ ਕੰਪ੍ਰੈਸ਼ਨ ਚਾਲੂ ਕਰੋ

### ਪ੍ਰਤੀ-ਕੰਬੋ ਓਵਰਰਾਈਡ

`Dashboard → Context & Cache → Compression Combos` ਵਿੱਚ, ਕਿਸੇ ਰਾਊਟਿੰਗ ਕੰਬੋ ਨੂੰ ਇੱਕ ਕੰਪ੍ਰੈਸ਼ਨ ਕੰਬੋ ਨਿਰਧਾਰਤ ਕਰੋ:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

ਇਸ ਨਾਲ ਤੁਸੀਂ ਭੁਗਤਾਨਸ਼ੁਦਾ ਸਬਸਕ੍ਰਿਪਸ਼ਨਾਂ 'ਤੇ ਲਾਈਟ ਮੋਡ ਬਰਕਰਾਰ ਰੱਖਦੇ ਹੋਏ ਮੁਫ਼ਤ/ਕੋਡਿੰਗ ਪ੍ਰਦਾਤਾਵਾਂ 'ਤੇ ਸਟੈਕਡ ਕੰਪ੍ਰੈਸ਼ਨ ਵਰਤ ਸਕਦੇ ਹੋ।

ਇਹ "ਪ੍ਰਤੀ-ਕੰਬੋ ਓਵਰਰਾਈਡ" ਅਸਾਈਨਮੈਂਟ **ਰਾਊਟਿੰਗ-ਕੰਬੋ ਕੰਪ੍ਰੈਸ਼ਨ ਮੋਡ** ਓਵਰਰਾਈਡ (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — ਫੀਲਡ ਦਾ ਸਕੀਮਾ `rtk`, `stacked` ਅਤੇ `omniglyph` ਨੂੰ ਵੀ ਸਵੀਕਾਰ ਕਰਦਾ ਹੈ) ਤੋਂ ਵੱਖਰਾ ਕੰਟਰੋਲ ਹੈ — ਉਹ ਓਵਰਰਾਈਡ ਕਿਸੇ ਨਾਮਿਤ ਕੰਪ੍ਰੈਸ਼ਨ-ਕੰਬੋ ਪਾਈਪਲਾਈਨ ਦੀ ਚੋਣ ਨਹੀਂ ਕਰਦਾ; ਇਹ ਸਿਰਫ਼ `resolveCompressionPlan` ਵੱਲੋਂ ਵਰਤੇ ਜਾਣ ਵਾਲੇ `compressionMode` ਫੀਲਡ ਨੂੰ ਸੈੱਟ ਕਰਦਾ ਹੈ। ਇਸ ਨੂੰ ਕੰਬੋ ਕਾਰਡ (`Dashboard → Combos`) 'ਤੇ ਜਾਂ, #6760 ਤੋਂ ਬਾਅਦ, `Dashboard → Context & Cache → Compression Combos` ਦੀ "Assign to routing" ਸੂਚੀ ਵਿੱਚ ਪ੍ਰਤੀ ਰਾਊਟਿੰਗ ਕੰਬੋ ਸੈੱਟ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ, ਜੋ ਉੱਪਰ ਦਸਤਾਵੇਜ਼ਬੱਧ ਪਾਈਪਲਾਈਨ-ਅਸਾਈਨਮੈਂਟ ਚੈੱਕਬਾਕਸ ਦੇ ਬਿਲਕੁਲ ਨਾਲ ਹੈ। ਦੋਵੇਂ ਇੰਟਰਫੇਸ ਇੱਕੋ `PUT /api/combos/{id}` ਐਂਡਪੌਇੰਟ ਰਾਹੀਂ ਸਥਾਈ ਕੀਤੇ ਜਾਂਦੇ ਹਨ।

### ਪ੍ਰਤੀ-ਬੇਨਤੀ ਓਵਰਰਾਈਡ

ਇੱਕ ਬੇਨਤੀ ਲਈ ਕੰਪ੍ਰੈਸ਼ਨ ਯੋਜਨਾ ਨੂੰ ਓਵਰਰਾਈਡ ਕਰਨ ਵਾਸਤੇ `x-omniroute-compression` ਬੇਨਤੀ ਹੈਡਰ ਭੇਜੋ। ਇਸ ਦੀ ਤਰਜੀਹ ਸਭ ਤੋਂ ਉੱਚੀ ਹੈ — ਇਹ ਰਾਊਟਿੰਗ-ਕੰਬੋ ਓਵਰਰਾਈਡ, ਸਰਗਰਮ ਪ੍ਰੋਫਾਈਲ, ਆਟੋ-ਟ੍ਰਿਗਰ ਅਤੇ ਪੈਨਲ ਡਿਫਾਲਟ ਤੋਂ ਉੱਪਰ ਹੈ। ਅਣਜਾਣ ਮੁੱਲਾਂ ਨੂੰ ਅਣਡਿੱਠਾ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (ਬੇਨਤੀ ਕਦੇ ਵੀ ਰੱਦ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ) ਅਤੇ ਗਲੋਬਲ ਮਾਸਟਰ ਸਵਿੱਚ ਫਿਰ ਵੀ ਹਰ ਚੀਜ਼ ਨੂੰ ਨਿਯੰਤਰਿਤ ਕਰਦਾ ਹੈ: ਜਦੋਂ ਕੰਪ੍ਰੈਸ਼ਨ ਗਲੋਬਲ ਤੌਰ 'ਤੇ ਬੰਦ ਹੋਵੇ, ਤਾਂ ਹੈਡਰ ਇਸ ਨੂੰ ਚਾਲੂ ਨਹੀਂ ਕਰ ਸਕਦਾ। ਮੁੱਲ:

| ਮੁੱਲ          | ਪ੍ਰਭਾਵ                                                                                                      |
| ------------- | ----------------------------------------------------------------------------------------------------------- |
| `off`         | ਇਸ ਬੇਨਤੀ ਲਈ ਕੋਈ ਕੰਪ੍ਰੈਸ਼ਨ ਨਹੀਂ।                                                                             |
| `default`     | ਪੈਨਲ ਤੋਂ ਪ੍ਰਾਪਤ ਡਿਫਾਲਟ ਪ੍ਰੋਫਾਈਲ (ਸਰਗਰਮ ਪ੍ਰੋਫਾਈਲ ਨੂੰ ਅਣਡਿੱਠਾ ਕਰਦਾ ਹੈ)। ਲੌਸੀ ਇੰਜਣ ਬੰਦ ਰਹਿੰਦੇ ਹਨ।              |
| `safe`        | ਹੈਡਰ ਨੂੰ ਛੱਡਣ ਦੇ ਸਮਾਨ: ਕੇਵਲ ਡੀਡੁਪ ਅਤੇ ਵ੍ਹਾਈਟਸਪੇਸ ਫੋਲਡਿੰਗ।                                                   |
| `allow-lossy` | ਇਸ ਬੇਨਤੀ ਦੀ ਓਪਰੇਟਰ ਯੋਜਨਾ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖੋ, ਜਿਸ ਵਿੱਚ ਸਾਰਾਂਸ਼, ਪ੍ਰਸੰਗਿਕਤਾ ਫਿਲਟਰ ਅਤੇ ਸ਼ੈਲੀ ਮੁੜ-ਲਿਖਤਾਂ ਸ਼ਾਮਲ ਹਨ। |
| `engine:<id>` | ਸਮਰੱਥ ਹੋਣ 'ਤੇ ਇੱਕ ਇੰਜਣ, ਜਿਵੇਂ `engine:rtk`। ਇਹ ਉਸ ਇੰਜਣ ਲਈ ਪ੍ਰਤੀ-ਬੇਨਤੀ ਔਪਟ-ਇਨ ਹੈ।                            |
| `<combo>`     | ਇੱਕ ਨਾਮਿਤ ਕੰਬੋ, ਜਿਸ ਦਾ ਪਹਿਲਾਂ ਨਾਮ (ਅੱਖਰਾਂ ਦੇ ਕੇਸ ਤੋਂ ਬੇਪਰਵਾਹ), ਫਿਰ id ਰਾਹੀਂ ਮਿਲਾਨ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।            |

`allow-lossy`, `engine:<id>`, ਜਾਂ ਕਿਸੇ ਨਾਮਿਤ ਕੰਬੋ ਤੋਂ ਬਿਨਾਂ, ਲੌਸੀ ਇੰਜਣ ਲਾਗੂ ਨਹੀਂ ਕੀਤੇ ਜਾਂਦੇ। ਕੰਪ੍ਰੈਸ਼ਨ ਚਾਲੂ ਹੋਣ 'ਤੇ ਬੇਨਤੀ ਨੂੰ ਫਿਰ ਵੀ ਸੈਸ਼ਨ ਡੀਡੁਪ ਅਤੇ ਵ੍ਹਾਈਟਸਪੇਸ ਫੋਲਡਿੰਗ ਮਿਲਦੀ ਹੈ।

ਲਾਗੂ ਕੀਤੀ ਯੋਜਨਾ ਨੂੰ `X-OmniRoute-Compression: <mode>; source=<source>` ਜਵਾਬ ਹੈਡਰ ਵਿੱਚ ਵਾਪਸ ਦਰਸਾਇਆ ਜਾਂਦਾ ਹੈ, ਜਿੱਥੇ `<source>` `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, ਜਾਂ `off` ਵਿੱਚੋਂ ਇੱਕ ਹੁੰਦਾ ਹੈ।


### ਕੈਸ਼-ਅਵੇਅਰ ਕੰਪ੍ਰੈਸ਼ਨ

#### ਇਹ ਕਿਵੇਂ ਕੰਮ ਕਰਦਾ ਹੈ

1. **ਕੈਸ਼ਿੰਗ ਕਾਂਟੈਕਸਟ ਦੀ ਪਛਾਣ ਕਰੋ** — `cache_control` ਮਾਰਕਰਾਂ ਲਈ ਬੇਨਤੀ ਬਾਡੀ ਨੂੰ ਸਕੈਨ ਕਰਦਾ ਹੈ
2. **ਕੈਸ਼ਿੰਗ ਪ੍ਰਦਾਤਾਵਾਂ ਦੀ ਪਛਾਣ ਕਰੋ** — ਜਾਂਚਦਾ ਹੈ ਕਿ ਟਾਰਗੇਟ ਪ੍ਰਦਾਤਾ ਕੈਸ਼ਿੰਗ ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ ਜਾਂ ਨਹੀਂ
3. **ਰਣਨੀਤੀ ਵਿਵਸਥਿਤ ਕਰੋ** — ਕੈਸ਼ਿੰਗ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ `aggressive`/`ultra` ਨੂੰ `standard` ਤੱਕ ਡਾਊਨਗ੍ਰੇਡ ਕਰਦਾ ਹੈ
4. **ਸਿਸਟਮ ਪ੍ਰੌਮਪਟ ਛੱਡੋ** — ਸਿਸਟਮ ਪ੍ਰੌਮਪਟ ਆਮ ਤੌਰ 'ਤੇ ਕੈਸ਼ ਕੀਤੇ ਜਾਂਦੇ ਹਨ, ਇਸ ਲਈ ਉਨ੍ਹਾਂ ਨੂੰ ਕੰਪ੍ਰੈੱਸ ਨਾ ਕਰੋ

ਰਣਨੀਤੀ ਹੈਲਪਰ ਇੱਕ `deterministicOnly` ਫਲੈਗ ਵੀ ਵਾਪਸ ਕਰਦਾ ਹੈ, ਪਰ ਪਲਾਨ ਬਿਲਡਰ
ਸਿਰਫ਼ ਰਣਨੀਤੀ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ — ਇਸ ਵੇਲੇ ਡਾਊਨਸਟ੍ਰੀਮ ਵਿੱਚ ਕੋਈ ਵੀ ਇਸ ਫਲੈਗ ਨੂੰ ਨਹੀਂ ਪੜ੍ਹਦਾ।

#### ਕੋਡ ਉਦਾਹਰਨ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← ਕੈਸ਼ ਮਾਰਕਰ
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ਕਦੋਂ ਵਰਤਣਾ ਹੈ

ਕੈਸ਼-ਅਵੇਅਰ ਕੰਪ੍ਰੈਸ਼ਨ **ਹਮੇਸ਼ਾ ਚਾਲੂ** ਰਹਿੰਦਾ ਹੈ — ਕਿਸੇ ਸੰਰਚਨਾ ਦੀ ਲੋੜ ਨਹੀਂ। ਇਹ ਉਦੋਂ ਸਰਗਰਮ ਹੁੰਦਾ ਹੈ ਜਦੋਂ
ਕੰਪ੍ਰੈਸ਼ਨ ਚਾਲੂ ਹੋਵੇ ਅਤੇ ਟਾਰਗੇਟ ਪ੍ਰਦਾਤਾ ਪ੍ਰੌਮਪਟ ਕੈਸ਼ਿੰਗ (Anthropic, OpenAI,
ਆਦਿ) ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੋਵੇ; ਸਪਸ਼ਟ `cache_control` ਮਾਰਕਰ ਲਾਜ਼ਮੀ ਨਹੀਂ ਹਨ — ਸਿਰਫ਼ ਇੱਕ ਕੈਸ਼ਿੰਗ ਪ੍ਰਦਾਤਾ ਹੀ
ਡਾਊਨਗ੍ਰੇਡ ਨੂੰ ਟ੍ਰਿਗਰ ਕਰ ਦਿੰਦਾ ਹੈ, ਅਤੇ ਸਿਰਫ਼ ਮਾਰਕਰ ਕਦੇ ਵੀ ਅਜਿਹਾ ਨਹੀਂ ਕਰਦੇ (ਮਾਰਕਰ ਦੀ ਪਛਾਣ ਕੈਸ਼
ਟੈਲੀਮੈਟਰੀ ਨੂੰ ਡਾਟਾ ਦਿੰਦੀ ਹੈ, ਰਣਨੀਤੀ ਦੇ ਫ਼ੈਸਲੇ ਨੂੰ ਨਹੀਂ)।

### ਪ੍ਰੋਗਰੈਸਿਵ ਏਜਿੰਗ

ਲੰਬੀਆਂ ਗੱਲਬਾਤਾਂ ਵਿੱਚ ਬਹੁਤ ਸਾਰੇ ਸੁਨੇਹਾ ਟਰਨ ਇਕੱਠੇ ਹੋ ਜਾਂਦੇ ਹਨ, ਪਰ ਪੁਰਾਣੇ ਟਰਨ ਘੱਟ
ਸੰਬੰਧਿਤ ਹੋ ਜਾਂਦੇ ਹਨ। `progressiveAging.ts` ਮੋਡੀਊਲ **ਟਰਨ ਦੀ ਦੂਰੀ ਦੇ ਆਧਾਰ 'ਤੇ ਸੁਨੇਹਿਆਂ ਦੀ ਵਿਸਤਾਰਤਾ ਘਟਾਉਂਦਾ ਹੈ**
(ਦੂਰੀ ਗੱਲਬਾਤ ਦੇ ਅੰਤ ਤੋਂ ਮਾਪੀ ਜਾਂਦੀ ਹੈ)। ਜਾਰੀ ਕੀਤੀਆਂ ਡਿਫਾਲਟ ਸੈਟਿੰਗਾਂ
(`verbatim: 2, light: 2, moderate: 3`) ਨਾਲ:

- **ਆਖਰੀ 2 ਵਾਰਤਾਲਾਪੀ ਚੱਕਰ (ਦੂਰੀ ≤ 2)**: ਜਿਉਂ ਦੇ ਤਿਉਂ ਰੱਖੇ ਜਾਂਦੇ ਹਨ
- **ਦੂਰੀ 3**: ਕੇਵਮੈਨ ਕੰਪਰੈਸ਼ਨ (ਫ਼ਾਲਤੂ ਸ਼ਬਦ ਹਟਾਉਣਾ)
- **ਦੂਰੀ 4+**: ਸਹਾਇਕ ਸੁਨੇਹਿਆਂ ਦਾ ਸਾਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ; ਵਰਤੋਂਕਾਰ ਸੁਨੇਹਿਆਂ ਨੂੰ ਉਨ੍ਹਾਂ ਦੀ ਪਹਿਲੀ
  ਲਾਈਨ ਤੱਕ ਘਟਾਇਆ ਜਾਂਦਾ ਹੈ, ਜਿਸ ਦੀ ਸੀਮਾ 120 ਅੱਖਰ ਹੈ; ਹੋਰ ਭੂਮਿਕਾਵਾਂ ਨੂੰ ਬਦਲਿਆ ਨਹੀਂ ਜਾਂਦਾ। ਸਿਸਟਮ ਪ੍ਰੌਂਪਟ, ਪਹਿਲਾਂ ਹੀ ਪੁਰਾਣੇ ਕੀਤੇ
  ਸੁਨੇਹੇ ਅਤੇ ਸਭ ਤੋਂ ਨਵਾਂ ਵਰਤੋਂਕਾਰ ਸੁਨੇਹਾ ਦੂਰੀ ਦੀ ਪਰਵਾਹ ਕੀਤੇ ਬਿਨਾਂ ਹਮੇਸ਼ਾ ਜਿਉਂ ਦੇ ਤਿਉਂ ਰੱਖੇ ਜਾਂਦੇ ਹਨ।
  ਕੁਝ ਵੀ ਪੂਰੀ ਤਰ੍ਹਾਂ ਹਟਾਇਆ ਨਹੀਂ ਜਾਂਦਾ, ਅਤੇ ਭੇਜੇ ਗਏ ਡਿਫ਼ਾਲਟਾਂ ਨਾਲ `light`
  ਬੈਂਡ ਤੱਕ ਪਹੁੰਚਿਆ ਨਹੀਂ ਜਾ ਸਕਦਾ (`light`, `verbatim` ਦੇ ਬਰਾਬਰ ਹੈ)।

#### ਕੋਡ ਉਦਾਹਰਨ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 ਹੋਰ ਵਾਰਤਾਲਾਪੀ ਚੱਕਰ ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // ਆਖਰੀ 3 ਵਾਰਤਾਲਾਪੀ ਚੱਕਰ: ਜਿਉਂ ਦੇ ਤਿਉਂ
  light: 8, // ਦੂਰੀ <= 8: ਹਲਕਾ ਕੰਪਰੈਸ਼ਨ
  moderate: 20, // ਦੂਰੀ <= 20: ਕੇਵਮੈਨ ਕੰਪਰੈਸ਼ਨ
  fullSummary: 5, // ਕਿਸਮ ਲਈ ਲੋੜੀਂਦਾ, ਬੈਂਡਿੰਗ ਕੋਡ ਵੱਲੋਂ ਨਹੀਂ ਪੜ੍ਹਿਆ ਜਾਂਦਾ
  // ਦੂਰੀ > 20: ਸਾਰ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ (ਸਹਾਇਕ) / ਪਹਿਲੀ ਲਾਈਨ ਰੱਖੀ ਜਾਂਦੀ ਹੈ (ਵਰਤੋਂਕਾਰ)
});

// saved = ਬਚਾਏ ਗਏ ਟੋਕਨਾਂ ਦੀ ਗਿਣਤੀ
```

#### ਕਦੋਂ ਵਰਤਣਾ ਹੈ

`aggressive` ਮੋਡ ਲਈ ਪ੍ਰੋਗਰੈਸਿਵ ਏਜਿੰਗ **ਹਮੇਸ਼ਾ ਚਾਲੂ** ਰਹਿੰਦੀ ਹੈ — ਇਹ
`compressAggressive()` ਦਾ ਕਦਮ 2 ਹੈ। Ultra ਮੋਡ ਇਸਨੂੰ ਨਹੀਂ ਚਲਾਉਂਦਾ। ਇਹ ਖ਼ਾਸ ਤੌਰ 'ਤੇ ਇਨ੍ਹਾਂ ਲਈ ਪ੍ਰਭਾਵਸ਼ਾਲੀ ਹੈ:

- ਲੰਬੇ ਸਮੇਂ ਤੱਕ ਚੱਲਣ ਵਾਲੇ ਕੋਡਿੰਗ ਸੈਸ਼ਨ
- ਕਈ ਦਿਨਾਂ ਦੀਆਂ ਗੱਲਬਾਤਾਂ
- ਬਹੁਤ ਸਾਰੀਆਂ ਟੂਲ ਕਾਲਾਂ ਵਾਲੇ ਏਜੰਟਿਕ ਵਰਕਫ਼ਲੋ

### ਕੇਵਮੈਨ ਆਉਟਪੁੱਟ ਮੋਡ

ਕੇਵਮੈਨ ਆਉਟਪੁੱਟ ਮੋਡ **ਸਿਸਟਮ ਪ੍ਰੌਂਪਟ ਹਦਾਇਤਾਂ** ਜੋੜਦਾ ਹੈ ਜੋ ਮਾਡਲ ਨੂੰ ਖ਼ੁਦ
ਸੰਖੇਪ ਆਉਟਪੁੱਟ ਦੇਣ ਲਈ ਕਹਿੰਦੀਆਂ ਹਨ — `lite` ਪੱਧਰ ਪੂਰੇ ਵਾਕ ਬਰਕਰਾਰ ਰੱਖਦਿਆਂ ਸੰਖੇਪ ਜਵਾਬ ਮੰਗਦਾ ਹੈ, `full`
ਇਸਨੂੰ "ਸਮਝਦਾਰ ਕੇਵਮੈਨ ਵਾਂਗ ਸੰਖੇਪ ਜਵਾਬ ਦੇਣ" ਲਈ ਕਹਿੰਦਾ ਹੈ, ਅਤੇ `ultra` ਟੈਲੀਗ੍ਰਾਫਿਕ ਆਉਟਪੁੱਟ ਮੰਗਦਾ ਹੈ;
ਹਦਾਇਤਾਂ ਸਿਰਫ਼ ਬੇਨਤੀ ਕਰਦੀਆਂ ਹਨ, ਉਹ ਇਸਦੀ ਗਾਰੰਟੀ ਨਹੀਂ ਦੇ ਸਕਦੀਆਂ। ਬੇਨਤੀਆਂ ਇਹਨਾਂ ਨੂੰ
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ਰਾਹੀਂ ਪ੍ਰਾਪਤ ਕਰਦੀਆਂ ਹਨ:
`open-sse/handlers/chatCore.ts` ਪਹਿਲਾਂ ਬੈਕਵਰਡ-ਕੰਪੈਟਿਬਿਲਟੀ ਸ਼ਿਮ ਨਾਲ ਚੋਣ ਨਿਰਧਾਰਤ ਕਰਦਾ ਹੈ
(`open-sse/services/compression/outputStyles/backCompat.ts` ਵਿੱਚ
`resolveOutputStyleSelection()`), ਜੋ `outputStyles`
ਖਾਲੀ ਹੋਣ ਦੌਰਾਨ, ਸਮਰੱਥ ਕੀਤੇ `cavemanOutputMode` ਨੂੰ
`cavemanOutputMode.intensity` 'ਤੇ `terse-prose` ਆਉਟਪੁੱਟ ਸ਼ੈਲੀ ਨਾਲ ਮੈਪ ਕਰਦਾ ਹੈ
(ਹੇਠਾਂ ਬੈਕਵਰਡ-ਕੰਪੈਟਿਬਿਲਟੀ ਵੇਖੋ); ਇੱਕ ਗੈਰ-ਖਾਲੀ `outputStyles`
ਚੋਣ ਜਿਉਂ ਦੀ ਤਿਉਂ ਵਰਤੀ ਜਾਂਦੀ ਹੈ, ਅਤੇ ਫਿਰ `cavemanOutputMode.enabled` ਅਤੇ `intensity` ਦਾ ਕੋਈ
ਅਸਰ ਨਹੀਂ ਹੁੰਦਾ, ਜਦਕਿ ਇਸਦਾ `autoClarity` ਟੌਗਲ ਫਿਰ ਵੀ ਲਾਗੂ ਹੁੰਦਾ ਹੈ। `outputMode.ts` ਵਿੱਚ
ਹਦਾਇਤਾਂ ਦੇ ਪਾਠ (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), ਸਮੱਗਰੀ ਬਾਈਪਾਸ ਅਤੇ
ਪਲੇਸਮੈਂਟ ਸਹਾਇਕ ਮੌਜੂਦ ਹਨ, ਜਿਨ੍ਹਾਂ ਦੀ ਵਰਤੋਂ ਇੰਜੈਕਸ਼ਨ ਕਰਦਾ ਹੈ; ਇਸਦੇ ਆਪਣੇ `applyCavemanOutputMode()` ਇੰਜੈਕਟਰ ਦਾ ਕੋਈ
ਪ੍ਰੋਡਕਸ਼ਨ ਕਾਲਰ ਨਹੀਂ ਹੈ।

#### ਇਹ ਕਿਵੇਂ ਕੰਮ ਕਰਦਾ ਹੈ

ਇਹ ਮੋਡ ਇਨਪੁੱਟ ਨੂੰ ਕੰਪ੍ਰੈੱਸ ਨਹੀਂ ਕਰਦਾ। ਇਹ ਸਿਸਟਮ ਪ੍ਰੌਂਪਟ ਵਿੱਚ ਇੱਕ ਹਦਾਇਤ ਬਲਾਕ ਜੋੜਦਾ ਹੈ
(ਹੇਠਾਂ ਇੰਜੈਕਸ਼ਨ ਕਿਵੇਂ ਕੰਮ ਕਰਦਾ ਹੈ ਵੇਖੋ), ਅਤੇ ਬੇਨਤੀ ਲਈ ਚੁਣਿਆ ਗਿਆ ਕੋਈ ਵੀ ਇਨਪੁੱਟ ਕੰਪਰੈਸ਼ਨ ਮੋਡ
ਉਸ ਤੋਂ ਬਾਅਦ ਵੀ ਉਸ ਬਾਡੀ 'ਤੇ ਚੱਲਦਾ ਹੈ ਜਿਸ ਵਿੱਚ ਹੁਣ ਇਹ ਬਲਾਕ ਮੌਜੂਦ ਹੈ। ਹਰ ਪੱਧਰ ਦੇ ਅੰਤ ਵਿੱਚ ਆਉਣ ਵਾਲੀ ਸਾਂਝੀ
ਸੀਮਾਵਾਂ ਵਾਲੀ ਧਾਰਾ ਤੋਂ ਪਹਿਲਾਂ, ਅੰਗਰੇਜ਼ੀ `full` ਪੱਧਰ ਵਿੱਚ ਇਹ ਲਿਖਿਆ ਹੈ:

> "ਸਮਝਦਾਰ ਕੇਵਮੈਨ ਵਾਂਗ ਸੰਖੇਪ ਜਵਾਬ ਦਿਓ। ਆਰਟੀਕਲ (a/an/the), ਫ਼ਾਲਤੂ ਸ਼ਬਦ (just/really/basically/actually/simply), ਰਸਮੀ ਨਿਮਰਤਾਵਾਂ ਅਤੇ ਹਿਚਕਿਚਾਹਟ ਵਾਲੇ ਸ਼ਬਦ ਹਟਾਓ। ਵਾਕ-ਅੰਸ਼ ਠੀਕ ਹਨ। ਛੋਟੇ ਸਮਾਨਾਰਥੀ ਸ਼ਬਦ ਵਰਤੋ (extensive ਦੀ ਬਜਾਏ big, implement ਦੀ ਬਜਾਏ fix)। ਸਾਰੇ ਤਕਨੀਕੀ ਤੱਥ, ਕੋਡ, ਗਲਤੀਆਂ, URLs ਅਤੇ ਪਛਾਣਕਰਤਾ ਬਿਲਕੁਲ ਸਹੀ ਰੱਖੋ।"

ਇਹ ਖ਼ਾਸ ਤੌਰ 'ਤੇ ਇਨ੍ਹਾਂ ਲਈ ਵਧੀਆ ਕੰਮ ਕਰਦਾ ਹੈ:

- ਕੋਡ ਤਿਆਰ ਕਰਨਾ (ਵਧੇਰੇ ਸੰਖੇਪ ਆਉਟਪੁੱਟ = ਘੱਟ ਟੋਕਨ)
- ਤੁਰੰਤ ਸਵਾਲ-ਜਵਾਬ (ਵਿਸਤ੍ਰਿਤ ਵਿਆਖਿਆਵਾਂ ਦੀ ਲੋੜ ਨਹੀਂ)
- ਬੈਚ ਪ੍ਰੋਸੈਸਿੰਗ (ਥਰੂਪੁੱਟ ਨੂੰ ਵੱਧ ਤੋਂ ਵੱਧ ਕਰਨਾ)

#### ਕਦੋਂ ਵਰਤਣਾ ਹੈ

ਕੇਵਮੈਨ ਆਉਟਪੁੱਟ ਮੋਡ **ਚੋਣਵਾਂ** ਹੈ। ਕੰਪਰੈਸ਼ਨ ਚਾਲੂ ਹੋਣ 'ਤੇ (`enabled: true`, ਕੰਪਰੈਸ਼ਨ ਸੈਟਿੰਗਾਂ ਪੰਨੇ 'ਤੇ
ਮਾਸਟਰ ਟੌਗਲ), ਇਸਨੂੰ `cavemanOutputMode.enabled` ਨਾਲ ਚਾਲੂ ਕਰੋ; `intensity`
`lite`, `full` ਜਾਂ `ultra` ਚੁਣਦਾ ਹੈ:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

ਕੰਪਰੈਸ਼ਨ ਕਾਂਬੋ ਦਾ **ਆਉਟਪੁੱਟ ਮੋਡ** ਟੌਗਲ (`outputMode`, `outputModeIntensity` ਵਿੱਚ ਪੱਧਰ)
ਉਨ੍ਹਾਂ ਬੇਨਤੀਆਂ ਲਈ ਉਹੀ ਸਵਿੱਚ ਸੈੱਟ ਕਰਦਾ ਹੈ ਜਿਨ੍ਹਾਂ 'ਤੇ ਉਹ ਕਾਂਬੋ ਲਾਗੂ ਹੁੰਦਾ ਹੈ, ਅਤੇ
`omniroute_set_compression_engine` MCP ਟੂਲ ਇਸਨੂੰ ਆਪਣੇ ਬੂਲੀਅਨ `outputMode`

settings API ਕਿਸੇ ਵੀ style id ਨੂੰ ਸਵੀਕਾਰ ਕਰਦੀ ਹੈ, ਅਤੇ ਸਫ਼ੇ 'ਤੇ ਹੋਰ ਸ਼ੈਲੀਆਂ ਸੰਭਾਲਣ ਨਾਲ ਇਹ ਕਾਇਮ ਰਹਿੰਦੀ ਹੈ। ਬੇਨਤੀ

#### ਸ਼ਾਮਲਕਰਨ ਕਿਵੇਂ ਕੰਮ ਕਰਦਾ ਹੈ

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ਚੋਣ ਨੂੰ
ਕੈਟਾਲਾਗ ਨਾਲ ਮਿਲਾ ਕੇ ਨਿਰਧਾਰਤ ਕਰਦਾ ਹੈ (ਅਣਜਾਣ ids ਅਤੇ ਲੋਕੇਲ ਨਾਲ ਨਾ ਮਿਲਦੀਆਂ ਸ਼ੈਲੀਆਂ
ਹਟਾ ਦਿੱਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ, ਕਦੇ ਵੀ ਗਲਤੀ ਨਹੀਂ ਬਣਦੀਆਂ; ਜਿਹੜੀ ਚੋਣ ਕਿਸੇ ਸ਼ੈਲੀ ਵਿੱਚ ਨਿਰਧਾਰਤ ਨਹੀਂ ਹੁੰਦੀ, ਉਹ body ਨੂੰ
ਬਿਨਾਂ ਬਦਲੇ ਛੱਡ ਦਿੰਦੀ ਹੈ ਅਤੇ `no_styles` ਵਜੋਂ ਛੱਡੀ ਜਾਂਦੀ ਹੈ), ਚੁਣੀਆਂ ਹਦਾਇਤਾਂ ਨੂੰ ਕੈਟਾਲਾਗ
ਦੇ ਕ੍ਰਮ ਵਿੱਚ ਜੋੜਦਾ ਹੈ,
ਸੀਮਾਵਾਂ ਵਾਲੀ ਧਾਰਾ **ਇੱਕ ਵਾਰ** ਜੋੜਦਾ ਹੈ (ਨਾਲ ਹੀ ਸੁਰੱਖਿਆ ਧਾਰਾ, `SAFETY_BOUNDARIES` ਜਾਂ ਇਸ ਦਾ
ਅਨੁਵਾਦ, ਜਦੋਂ `less-code` ਜਾਂ `ponytail` ਚੁਣਿਆ ਗਿਆ ਹੋਵੇ), ਅਤੇ ਬਲਾਕ ਨੂੰ ਇੱਕੋ
idempotency ਮਾਰਕਰ (`[OmniRoute Output Styles]`) ਨਾਲ ਸ਼ੁਰੂ ਕਰਦਾ ਹੈ, ਤਾਂ ਜੋ ਇਸ ਨੂੰ ਦੁਬਾਰਾ ਲਾਗੂ ਕਰਨ ਦਾ ਕੋਈ ਅਸਰ ਨਾ ਹੋਵੇ। ਜਦੋਂ
ਨਿਰਧਾਰਤ ਭਾਸ਼ਾ (ਹੇਠਾਂ Language selection ਵੇਖੋ) ਦਾ ਅਨੁਵਾਦ ਉਪਲਬਧ ਹੋਵੇ, ਤਾਂ ਅੰਗਰੇਜ਼ੀ ਦੀ ਥਾਂ ਸਥਾਨਕ
ਹਦਾਇਤ ਸ਼ਾਮਲ ਕੀਤੀ ਜਾਂਦੀ ਹੈ।

ਗੈਰ-ਖਾਲੀ `messages` ਐਰੇ ਵਾਲੀ body 'ਤੇ, idempotency ਜਾਂਚ
ਸਮੱਗਰੀ ਬਾਈਪਾਸ ਤੋਂ ਪਹਿਲਾਂ ਚੱਲਦੀ ਹੈ: ਜਦੋਂ `[OmniRoute Output Styles]` ਮਾਰਕਰ ਪਹਿਲਾਂ ਹੀ ਸਿਖਰਲੇ ਪੱਧਰ ਦੇ
`system` ਫ਼ੀਲਡ (ਇੱਕ ਸਤਰ ਜਾਂ content-block ਐਰੇ) ਵਿੱਚ ਜਾਂ ਸਤਰ ਸਮੱਗਰੀ ਵਾਲੇ system ਸੁਨੇਹੇ ਵਿੱਚ ਮੌਜੂਦ ਹੋਵੇ,
ਤਾਂ body ਨੂੰ `already_applied` ਵਜੋਂ ਬਿਨਾਂ ਬਦਲੇ ਛੱਡ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ ਕੋਈ keyword ਜਾਂਚ ਨਹੀਂ ਚੱਲਦੀ।
ਨਹੀਂ ਤਾਂ content bypass (`open-sse/services/compression/outputMode.ts` ਵਿੱਚ
`shouldBypassCavemanOutputMode()`) ਆਖ਼ਰੀ ਤਿੰਨ
ਸੁਨੇਹਿਆਂ ਦੇ ਟੈਕਸਟ ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ, ਭਾਵੇਂ ਉਹਨਾਂ ਦੀ ਭੂਮਿਕਾ ਕੋਈ ਵੀ ਹੋਵੇ, ਅਤੇ ਪੂਰੇ turn ਲਈ ਸ਼ੈਲੀਆਂ ਨੂੰ ਛੱਡ ਦਿੰਦਾ ਹੈ ਜਦੋਂ ਉਹ ਟੈਕਸਟ
ਇਸ ਦੇ ਸੁਰੱਖਿਆ, ਅਪਰਿਵਰਤਨੀ ਕਾਰਵਾਈ ਜਾਂ ਸਪਸ਼ਟੀਕਰਨ keywords, ਜਾਂ ਕਿਸੇ
ਕ੍ਰਮ-ਸੰਵੇਦਨਸ਼ੀਲ ਲੜੀ ਨਾਲ ਮੇਲ ਖਾਂਦਾ ਹੋਵੇ: `first`, `then`, `after that`, `before`, `rollback` ਜਾਂ
`backup`, ਜਿਸ ਤੋਂ ਬਾਅਦ 240 ਅੱਖਰਾਂ ਦੇ ਅੰਦਰ `delete`, `drop`, `migrate`, `deploy` ਜਾਂ
`release` ਆਵੇ। ਬਾਈਪਾਸ ਉਸ ਵੇਲੇ ਚੱਲਦਾ ਹੈ ਜਦੋਂ **Auto-Clarity Bypass** ਟੌਗਲ
(`cavemanOutputMode.autoClarity`, ਮੂਲ ਰੂਪ ਵਿੱਚ ਚਾਲੂ) ਚਾਲੂ ਹੋਵੇ; ਟੌਗਲ ਬੰਦ ਕਰਨ ਨਾਲ
keyword ਜਾਂਚ ਛੱਡ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ।

ਜਦੋਂ ਬਾਈਪਾਸ turn ਨੂੰ ਅੱਗੇ ਜਾਣ ਦਿੰਦਾ ਹੈ, `placeSystemInstruction()` (ਉਹੀ ਫ਼ਾਈਲ), ਜੋ
ਕਦੇ ਵੀ ਨਵਾਂ `messages[0]` ਨਹੀਂ ਬਣਾਉਂਦਾ, ਬਲਾਕ ਨੂੰ ਹੇਠ ਲਿਖਿਆਂ ਵਿੱਚੋਂ ਸਭ ਤੋਂ ਪਹਿਲਾਂ ਮਿਲਣ ਵਾਲੀ ਥਾਂ 'ਤੇ ਰੱਖਦਾ ਹੈ:

1. ਸਤਰ ਸਮੱਗਰੀ ਵਾਲਾ ਸ਼ੁਰੂਆਤੀ system ਸੁਨੇਹਾ: ਬਲਾਕ ਇਸ ਦੇ ਟੈਕਸਟ ਤੋਂ ਬਾਅਦ ਜੋੜਿਆ ਜਾਂਦਾ ਹੈ।
2. ਸਿਖਰਲੇ ਪੱਧਰ ਦਾ `system` ਫ਼ੀਲਡ: ਬਲਾਕ ਇੱਕ ਸਤਰ ਦੇ ਟੈਕਸਟ ਤੋਂ ਬਾਅਦ ਜੋੜਿਆ ਜਾਂਦਾ ਹੈ, ਜਾਂ
   content-block ਐਰੇ ਵਿੱਚ ਨਵੇਂ text block ਵਜੋਂ ਜੋੜਿਆ ਜਾਂਦਾ ਹੈ।
3. ਸਤਰ ਸਮੱਗਰੀ ਵਾਲਾ ਬਾਅਦ ਦਾ ਪਹਿਲਾ system ਸੁਨੇਹਾ: ਬਲਾਕ ਇਸ ਦੇ
   ਟੈਕਸਟ ਤੋਂ ਬਾਅਦ ਜੋੜਿਆ ਜਾਂਦਾ ਹੈ।
4. ਉਪਰੋਕਤ ਵਿੱਚੋਂ ਕੋਈ ਨਹੀਂ: ਬਲਾਕ ਨੂੰ `messages` ਦੇ ਅੰਤ ਵਿੱਚ ਇੱਕ ਨਵੇਂ system ਸੁਨੇਹੇ ਵਿੱਚ ਰੱਖਿਆ ਜਾਂਦਾ ਹੈ।

`messages` ਐਰੇ ਤੋਂ ਬਿਨਾਂ (ਜਾਂ ਖਾਲੀ ਐਰੇ ਵਾਲੀ) body 'ਤੇ, ਕੋਈ content bypass ਨਹੀਂ ਚੱਲਦਾ ਅਤੇ
ਸਿਖਰਲੇ ਪੱਧਰ ਦੇ `system` ਫ਼ੀਲਡ ਦੀ ਜਾਂਚ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ। ਬਲਾਕ ਨੂੰ ਸਤਰ `instructions` ਫ਼ੀਲਡ ਦੇ
ਟੈਕਸਟ ਤੋਂ ਬਾਅਦ ਜੋੜਿਆ ਜਾਂਦਾ ਹੈ, ਜਦ ਤੱਕ ਉਸ ਫ਼ੀਲਡ ਵਿੱਚ ਪਹਿਲਾਂ ਹੀ
`[OmniRoute Output Styles]` ਮਾਰਕਰ ਨਾ ਹੋਵੇ; ਉਸ ਸਥਿਤੀ ਵਿੱਚ body ਨੂੰ
`already_applied` ਵਜੋਂ ਬਿਨਾਂ ਬਦਲੇ ਛੱਡ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ। ਜਦੋਂ body ਵਿੱਚ ਸਤਰ `instructions` ਫ਼ੀਲਡ ਨਾ ਹੋਵੇ ਪਰ `input`
(ਇੱਕ ਸਤਰ ਜਾਂ ਐਰੇ) ਮੌਜੂਦ ਹੋਵੇ, ਤਾਂ ਬਲਾਕ `instructions` ਬਣ ਜਾਂਦਾ ਹੈ ਅਤੇ ਉਸ ਫ਼ੀਲਡ ਵਿੱਚ ਮੌਜੂਦ ਕਿਸੇ ਵੀ ਗੈਰ-ਸਤਰ ਮੁੱਲ ਨੂੰ

#### ਸਮਰੱਥ ਕਿਵੇਂ ਕਰਨਾ ਹੈ

ਮਾਸਟਰ ਟੌਗਲ, `enabled`), ਤਾਂ ਸਟਾਈਲ ਇੰਜੈਕਟ ਹੁੰਦੇ ਹਨ। **Auto-Clarity Bypass** ਟੌਗਲ **Caveman**

   `shellOutput` ਚਾਲੂ ਹੋਵੇ, ਕਦੇ ਵੀ ਉਨ੍ਹਾਂ ਤੱਕ ਨਹੀਂ ਪਹੁੰਚਦਾ।

   ਖਾਲੀ ਥਾਂ ਤੋਂ ਬਾਅਦ `{` ਜਾਂ `[` ਨਾਲ ਸ਼ੁਰੂ ਹੁੰਦਾ ਹੈ ਅਤੇ ਸਫਲਤਾਪੂਰਵਕ ਪਾਰਸ ਹੁੰਦਾ ਹੈ, ਦਾ ਸੰਖੇਪ ਬਣਾਇਆ ਜਾਂਦਾ ਹੈ: 7 ਤੋਂ ਵੱਧ ਆਈਟਮਾਂ ਵਾਲੀ ਐਰੇ
   ਆਪਣੀਆਂ ਪਹਿਲੀਆਂ 5 ਅਤੇ ਆਖਰੀ 2 ਆਈਟਮਾਂ ਅਤੇ ਆਪਣੀ ਕੁੱਲ ਗਿਣਤੀ ਰੱਖਦੀ ਹੈ, ਅਤੇ ਇੱਕ ਆਬਜੈਕਟ ਆਪਣੀਆਂ ਪਹਿਲੀਆਂ 20
   ਕੁੰਜੀਆਂ ਰੱਖਦਾ ਹੈ, ਜਿਸ ਵਿੱਚ ਹਰ ਨੇਸਟਡ ਆਬਜੈਕਟ ਜਾਂ ਐਰੇ ਮੁੱਲ ਨੂੰ `{…N keys}` ਪਲੇਸਹੋਲਡਰ
   ਨਾਲ ਬਦਲਿਆ ਜਾਂਦਾ ਹੈ (ਐਰੇ ਲਈ, N ਉਸਦੀ ਲੰਬਾਈ ਹੈ) ਅਤੇ ਪਹਿਲੀਆਂ 20 ਤੋਂ ਬਾਅਦ
   ਹਟਾਈਆਂ ਗਈਆਂ ਕੁੰਜੀਆਂ ਦੀ ਗਿਣਤੀ ਲਈ `_remaining_<N>_keys` ਮਾਰਕਰ ਲਗਾਇਆ ਜਾਂਦਾ ਹੈ।
   ਸਕੇਲਰ ਮੁੱਲ ਪੂਰੇ ਨਕਲ ਕੀਤੇ ਜਾਂਦੇ ਹਨ, ਇਸ ਲਈ ਬਿਨਾਂ ਨੇਸਟਡ ਮੁੱਲਾਂ ਵਾਲਾ 20 ਜਾਂ ਘੱਟ ਕੁੰਜੀਆਂ ਦਾ ਆਬਜੈਕਟ
   ਸਿਰਫ਼ ਮੁੜ ਇੰਡੈਂਟ ਹੁੰਦਾ ਹੈ — ਮਿਨੀਫਾਈਡ ਆਬਜੈਕਟ ਵਿੱਚ ਅੱਖਰ ਵਧ ਜਾਂਦੇ ਹਨ
   ਅਤੇ ਉਹ ਬਿਨਾਂ ਬਦਲਾਅ ਦੇ ਰਹਿੰਦਾ ਹੈ।
5. **`errorMessage`**: ਉਹ ਆਉਟਪੁੱਟ ਜਿਸ ਵਿੱਚ, ਕਿਤੇ ਵੀ ਅਤੇ ਅੱਖਰਾਂ ਦੇ ਕਿਸੇ ਵੀ ਕੇਸ ਵਿੱਚ, `error:`,
   `error ` (ਸ਼ਬਦ ਤੋਂ ਬਾਅਦ ਇੱਕ ਸਪੇਸ, ਜਿਵੇਂ `no error found` ਵਿੱਚ), `[error]`,
   `exception:`, `exception `, `[exception]` ਜਾਂ `traceback` ਹੋਵੇ, ਆਪਣੀ ਪਹਿਲੀ ਲਾਈਨ,
   ਅਗਲੀਆਂ 10 ਲਾਈਨਾਂ ਅਤੇ ਆਖਰੀ 3 ਲਾਈਨਾਂ ਰੱਖਦੀ ਹੈ, ਅਤੇ ਉਨ੍ਹਾਂ ਦੇ ਵਿਚਕਾਰਲੀਆਂ ਲਾਈਨਾਂ ਦੀ ਥਾਂ
   `… [N frames elided] …` ਮਾਰਕਰ ਲਗਾਉਂਦੀ ਹੈ। ਮਾਰਕਰ ਸਿਰਫ਼ ਉਦੋਂ ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ ਜਦੋਂ ਪਹਿਲੀ
   ਲਾਈਨ ਤੋਂ ਬਾਅਦ 13 ਤੋਂ ਵੱਧ ਲਾਈਨਾਂ ਹੋਣ, ਇਸ ਲਈ 14 ਜਾਂ ਘੱਟ ਲਾਈਨਾਂ ਵਾਲਾ ਗਲਤੀ ਆਉਟਪੁੱਟ ਛੋਟਾ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ (12 ਜਾਂ 13 ਲਾਈਨਾਂ ਉੱਤੇ
   ਆਖਰੀ 3 ਲਾਈਨਾਂ ਪਹਿਲਾਂ ਤੋਂ ਰੱਖੀਆਂ ਲਾਈਨਾਂ ਨੂੰ ਦੁਹਰਾਉਂਦੀਆਂ ਹਨ)।

ਕਿਸੇ ਰਣਨੀਤੀ ਦੇ ਮੇਲ ਖਾਣ ਤੋਂ ਬਾਅਦ, ਭਾਵੇਂ ਉਹ ਕੁਝ ਵੀ ਨਾ ਬਚਾਉਂਦੀ ਹੋਵੇ, ਬਾਅਦ ਦੀਆਂ ਰਣਨੀਤੀਆਂ ਨੂੰ
ਅਜ਼ਮਾਇਆ ਨਹੀਂ ਜਾਂਦਾ। ਜਦੋਂ ਮੇਲ ਖਾਂਦੀ ਰਣਨੀਤੀ ਕੋਈ ਅਨੁਮਾਨਿਤ ਟੋਕਨ ਨਹੀਂ ਬਚਾਉਂਦੀ (ਲੰਬਾਈ ÷ 4, ਉੱਪਰ ਵੱਲ ਪੂਰਨ ਅੰਕ ਬਣਾਈ ਹੋਈ) —
ਉਦਾਹਰਨ ਲਈ 25 ਜਾਂ ਘੱਟ ਲਾਈਨਾਂ ਵਾਲੀ ਕੋਡ-ਵਰਗੀ ਫਾਈਲ, ਜਾਂ 2,000 ਤੋਂ ਵੱਧ
ਅੱਖਰਾਂ ਵਾਲੀ ਅਤੇ 7 ਜਾਂ ਘੱਟ ਆਈਟਮਾਂ ਵਾਲੀ JSON ਐਰੇ — ਤਾਂ ਅਗਰੈਸਿਵ ਇੰਜਣ ਮੂਲ ਟੂਲ
ਨਤੀਜਾ ਰੱਖਦਾ ਹੈ: ਦੋਵੇਂ ਕਾਲਰ (`compressAggressive()` ਅਤੇ `compressAnthropicToolResultBlock()`)
ਜਦੋਂ `saved` 0 ਜਾਂ ਇਸ ਤੋਂ ਘੱਟ ਹੋਵੇ ਤਾਂ ਮੂਲ ਨਤੀਜਾ ਰੱਖਦੇ ਹਨ, ਜਦਕਿ `compressToolResult()` ਖੁਦ ਫਿਰ ਵੀ
ਉਸ ਰਣਨੀਤੀ ਦਾ ਆਉਟਪੁੱਟ ਵਾਪਸ ਕਰਦਾ ਹੈ। ਟੂਲ-ਨਤੀਜਾ ਕਦਮ ਅੰਤਿਮ ਫ਼ੈਸਲਾ ਨਹੀਂ ਹੈ:
ਇੰਜਣ ਦਾ ਫਾਲਬੈਕ ਸੰਖੇਪਕਾਰ ਫਿਰ ਵੀ 8,192 ਅੱਖਰਾਂ ਤੋਂ ਲੰਬੇ `tool` ਜਾਂ `function` ਸੁਨੇਹੇ ਨੂੰ
ਛੋਟਾ ਕਰ ਸਕਦਾ ਹੈ (`maxTokensPerMessage`, 2,048, ਗੁਣਾ 4)।

#### ਕਦੋਂ ਵਰਤਣਾ ਹੈ

ਟੂਲ ਨਤੀਜਾ ਕੰਪ੍ਰੈਸ਼ਨ ਅਗਰੈਸਿਵ ਇੰਜਣ ਦਾ ਕਦਮ 1 ਹੈ (`compressAggressive()` ਵਿੱਚ
`open-sse/services/compression/aggressive.ts`), ਇਸ ਲਈ ਇਹ Aggressive ਮੋਡ ਵਿੱਚ ਅਤੇ
ਸਟੈਕਡ ਪਾਈਪਲਾਈਨ ਦੇ ਇੱਕ `aggressive` ਕਦਮ ਵਿੱਚ ਚੱਲਦਾ ਹੈ। ਇਹ OpenAI-ਆਕਾਰ ਦੇ `tool` ਅਤੇ `function`
ਸੁਨੇਹਿਆਂ ਅਤੇ Anthropic `tool_result` ਬਲਾਕਾਂ ਅੰਦਰਲੇ ਟੈਕਸਟ ਨੂੰ ਕੰਪ੍ਰੈੱਸ ਕਰਦਾ ਹੈ। ਹਰ ਰਣਨੀਤੀ ਦਾ ਆਪਣਾ
ਸਵਿੱਚ `aggressive.toolStrategies` ਹੇਠ ਹੈ, ਅਤੇ ਸਾਰੇ ਮੂਲ ਰੂਪ ਵਿੱਚ ਚਾਲੂ ਹਨ। ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ,
ਜਦੋਂ ਕੰਪ੍ਰੈਸ਼ਨ ਚਾਲੂ ਹੋਵੇ ਅਤੇ ਡਿਫਾਲਟ ਮੋਡ Aggressive ਹੋਵੇ, ਤਾਂ ਸਵਿੱਚ Caveman ਪੰਨੇ ਦੇ **Advanced** ਦ੍ਰਿਸ਼ ਵਿੱਚ ਹੁੰਦੇ ਹਨ।

### ਸਟੈਕਡ ਪਾਈਪਲਾਈਨ

ਸਟੈਕਡ ਮੋਡ **ਕਈ ਇੰਜਣਾਂ ਨੂੰ ਕ੍ਰਮਵਾਰ** ਚਲਾਉਂਦਾ ਹੈ — ਆਮ ਤੌਰ 'ਤੇ ਪਹਿਲਾਂ RTK
(ਟੂਲ ਆਉਟਪੁੱਟ ਉੱਤੇ 60-90% ਬਚਤ), ਫਿਰ ਬਚੇ ਹੋਏ ਟੈਕਸਟ ਉੱਤੇ Caveman (~46% ਇਨਪੁੱਟ
ਬਚਤ)। ਇਕੱਠੇ ਮਿਲਾ ਕੇ, ਇਹ **78-95% ਯੋਗ ਰੇਂਜ** ਹੈ (ਉੱਪਰ Upstream Savings Math
ਦੇਖੋ): `1 - (1 - 0.60..0.90) × (1 - 0.46)` ਦੀ ਔਸਤ ≈89% ਹੈ।

#### ਇਹ ਕਿਵੇਂ ਕੰਮ ਕਰਦਾ ਹੈ

```
ਇਨਪੁੱਟ (1000 ਟੋਕਨ)
  → RTK (ਕਮਾਂਡ-ਜਾਗਰੂਕ ਫਿਲਟਰ) → 200 ਟੋਕਨ
    → Caveman (ਫ਼ਾਲਤੂ ਸਮੱਗਰੀ ਹਟਾਉਣਾ) → 108 ਟੋਕਨ
  → ਆਉਟਪੁੱਟ (108 ਟੋਕਨ, ~89% ਬਚਤ)
```

#### ਕਦੋਂ ਵਰਤਣਾ ਹੈ

ਸਟੈਕਡ ਮੋਡ ਇਨ੍ਹਾਂ ਲਈ ਵਰਤੋ:

- ਵੱਧ ਟੂਲਾਂ ਵਾਲੇ ਵਰਕਫ਼ਲੋ (ਏਜੈਂਟਿਕ ਕੋਡਿੰਗ, ਖੋਜ)
- ਲਾਗਤ-ਸੰਵੇਦਨਸ਼ੀਲ ਬੈਚ ਪ੍ਰੋਸੈਸਿੰਗ
- ਜਦੋਂ ਤੁਹਾਨੂੰ ਵੱਧ ਤੋਂ ਵੱਧ ਟੋਕਨ ਬਚਤ ਦੀ ਲੋੜ ਹੋਵੇ

ਸਟੈਕਡ ਪਾਈਪਲਾਈਨਾਂ ਨੂੰ ਗਲੋਬਲ `stackedPipeline` ਕੰਪ੍ਰੈਸ਼ਨ
ਸੈਟਿੰਗ ਰਾਹੀਂ, ਜਾਂ ਕਿਸੇ ਰਾਊਟਿੰਗ ਕੌਂਬੋ ਨੂੰ ਸੌਂਪੇ ਗਏ ਨਾਮਿਤ ਕੰਪ੍ਰੈਸ਼ਨ ਕੌਂਬੋ ਰਾਹੀਂ ਸੰਰਚਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ (ਉੱਪਰ
Per-Combo Override ਦੇਖੋ) — ਕਿਸੇ ਆਟੋ-ਕੌਂਬੋ `modePack` ਰਾਹੀਂ ਨਹੀਂ (ਉਹ ਫੀਲਡ ਸਿਰਫ਼
ਆਟੋ-ਕੌਂਬੋ ਮਾਡਲ ਚੋਣ ਦੇ ਭਾਰ ਮੁੜ ਨਿਰਧਾਰਤ ਕਰਦੀ ਹੈ, ਅਤੇ `stacked` ਕੋਈ ਵੈਧ ਪੈਕ ਨਾਮ ਨਹੀਂ ਹੈ)।

## ਕੰਪ੍ਰੈਸ਼ਨ ਕਾਂਬੋ ਓਵਰਰਾਈਡ

ਵੱਖ-ਵੱਖ ਵਰਤੋਂ ਦੇ ਮਾਮਲਿਆਂ ਲਈ ਵਿਹਾਰ ਨੂੰ ਬਾਰੀਕੀ ਨਾਲ ਅਨੁਕੂਲ ਕਰਨ ਵਾਸਤੇ, ਤੁਸੀਂ ਗਲੋਬਲ ਕੰਪ੍ਰੈਸ਼ਨ ਮੋਡ ਨੂੰ **ਹਰੇਕ ਕਾਂਬੋ ਲਈ** ਓਵਰਰਾਈਡ ਕਰ ਸਕਦੇ ਹੋ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

ਇਹ ਇਨ੍ਹਾਂ ਲਈ ਲਾਭਦਾਇਕ ਹੈ:

- **ਕੋਡਿੰਗ ਕਾਂਬੋ**: ਲੰਬੇ ਸੈਸ਼ਨਾਂ ਲਈ `aggressive` ਮੋਡ ਵਰਤੋ
- **ਤੁਰੰਤ ਸਵਾਲ-ਜਵਾਬ ਕਾਂਬੋ**: ਤੇਜ਼ ਜਵਾਬਾਂ ਲਈ `lite` ਮੋਡ ਵਰਤੋ
- **ਵੱਧ ਟੂਲਾਂ ਵਾਲੇ ਕਾਂਬੋ**: ਵੱਧ ਤੋਂ ਵੱਧ ਬਚਤ ਲਈ `stacked` ਮੋਡ ਵਰਤੋ
- **ਪ੍ਰੋਡਕਸ਼ਨ ਕਾਂਬੋ**: ਕੈਸ਼ਿੰਗ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ ਓਵਰਰਾਈਡ ਬੰਦ ਰੱਖੋ — ਹਮੇਸ਼ਾ ਚਾਲੂ ਰਹਿਣ ਵਾਲੀ
  ਕੈਸ਼-ਸਚੇਤ ਵਿਵਸਥਾ `aggressive`/`ultra` ਨੂੰ ਆਪਣੇ ਆਪ `standard` ਵਿੱਚ ਡਾਊਨਗ੍ਰੇਡ ਕਰ ਦਿੰਦੀ ਹੈ
  (ਚੁਣਨਯੋਗ `cache-aware` ਮੋਡ ਮੌਜੂਦ ਨਹੀਂ ਹੈ)
