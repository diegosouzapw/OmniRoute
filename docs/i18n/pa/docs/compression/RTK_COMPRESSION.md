RTK ਕੰਪ੍ਰੈਸ਼ਨ, ਟਰਮੀਨਲ ਅਤੇ ਟੂਲ ਆਉਟਪੁੱਟ ਲਈ OmniRoute ਦਾ ਕਮਾਂਡ-ਜਾਗਰੂਕ ਕੰਪ੍ਰੈਸ਼ਨ ਇੰਜਣ ਹੈ। ਇਸਨੂੰ
ਕੋਡਿੰਗ-ਏਜੰਟ ਸੈਸ਼ਨਾਂ ਲਈ ਡਿਜ਼ਾਈਨ ਕੀਤਾ ਗਿਆ ਹੈ, ਜਿੱਥੇ ਸੰਦਰਭ ਦਾ ਜ਼ਿਆਦਾਤਰ ਵਾਧਾ ਟੈਸਟ ਲੌਗਾਂ, ਬਿਲਡ ਆਉਟਪੁੱਟ,
ਪੈਕੇਜ ਮੈਨੇਜਰ ਦੇ ਬੇਲੋੜੇ ਆਉਟਪੁੱਟ, ਸ਼ੈੱਲ ਟ੍ਰਾਂਸਕ੍ਰਿਪਟਾਂ, Docker ਆਉਟਪੁੱਟ, git ਆਉਟਪੁੱਟ ਅਤੇ ਸਟੈਕ ਟ੍ਰੇਸਾਂ ਕਾਰਨ ਹੁੰਦਾ ਹੈ।

RTK ਸਿੱਧੇ `defaultMode: "rtk"` ਨਾਲ ਜਾਂ ਇੱਕ ਸਟੈਕਡ ਪਾਈਪਲਾਈਨ ਦੇ ਪਹਿਲੇ ਪੜਾਅ ਵਜੋਂ ਚੱਲ ਸਕਦਾ ਹੈ, ਆਮ ਤੌਰ 'ਤੇ:

```txt
rtk -> caveman
```

ਇਹ ਕ੍ਰਮ ਪਹਿਲਾਂ ਸ਼ੋਰ-ਭਰੇ ਮਸ਼ੀਨੀ ਆਉਟਪੁੱਟ ਨੂੰ ਸੰਕੁਚਿਤ ਕਰਦਾ ਹੈ, ਫਿਰ Caveman ਨੂੰ ਬਾਕੀ ਰਹਿੰਦੀ ਵਾਰਤਕ ਨੂੰ ਸੰਖੇਪ ਕਰਨ ਦਿੰਦਾ ਹੈ।

ਅੱਪਸਟ੍ਰੀਮ RTK ਕਮਾਂਡ ਆਉਟਪੁੱਟ ਵਿੱਚ `60-90%` ਬਚਤ ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ। ਇਸਦੇ README ਦਾ ਨਮੂਨਾ ਸੈਸ਼ਨ
`~118,000` ਮਿਆਰੀ ਟੋਕਨਾਂ ਤੋਂ ਘਟ ਕੇ `~23,900` RTK ਟੋਕਨ ਰਹਿ ਜਾਂਦਾ ਹੈ, ਜੋ `79.7%` ਬਚਤ (`~80%`) ਹੈ। OmniRoute
Caveman ਇਨਪੁੱਟ ਕੰਪ੍ਰੈਸ਼ਨ ਨਾਲ ਸਟੈਕਡ ਬਚਤ ਦੀ ਗਣਨਾ ਲਈ ਉਸ ਅੱਪਸਟ੍ਰੀਮ ਔਸਤ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ:

```txt
RTK ਔਸਤ:       80% ਬਚਤ
Caveman ਇਨਪੁੱਟ: 46% ਬਚਤ
ਸਟੈਕਡ:         1 - (1 - 0.80) * (1 - 0.46) = 89.2% ਬਚਤ
ਸੀਮਾ:           1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

## ਇਹ ਕੀ ਸੰਕੁਚਿਤ ਕਰਦਾ ਹੈ

ਬਿਲਟ-ਇਨ ਕੈਟਾਲੌਗ ਇਸ ਵੇਲੇ ਇਨ੍ਹਾਂ ਸ਼੍ਰੇਣੀਆਂ ਵਿੱਚ 49 ਫਿਲਟਰਾਂ ਨਾਲ ਆਉਂਦਾ ਹੈ:

| ਸ਼੍ਰੇਣੀ   | ਉਦਾਹਰਨਾਂ                                                      |
| --------- | ------------------------------------------------------------- |
| `git`     | `git status`, `git branch`, `git diff`, `git log`             |
| `test`    | Vitest, Jest, Pytest, Playwright, Go ਟੈਸਟ, Cargo ਟੈਸਟ         |
| `build`   | TypeScript, ESLint, Biome, Prettier, Vite, Webpack, Turbo, Nx |
| `package` | `npm install`, `npm audit`, `pip`, `uv sync`, Poetry, Bundler |
| `shell`   | `ls`, `find`, `grep`, ਆਮ ਸ਼ੈੱਲ ਲੌਗ                            |
| `docker`  | `docker ps`, Docker ਲੌਗ                                       |
| `infra`   | Terraform, OpenTofu, `systemctl status`                       |
| `generic` | JSON ਆਉਟਪੁੱਟ, ਸਟੈਕ ਟ੍ਰੇਸਾਂ, ਆਮ ਆਉਟਪੁੱਟ ਫਾਲਬੈਕ                 |

`open-sse/services/compression/engines/rtk/commandDetector.ts` ਵਿੱਚ ਮੌਜੂਦ ਡਿਟੈਕਟਰ ਫਿਲਟਰ ਦੀ ਚੋਣ ਤੋਂ ਪਹਿਲਾਂ
ਆਉਟਪੁੱਟ ਨੂੰ ਵਰਗੀਕ੍ਰਿਤ ਕਰਦਾ ਹੈ। ਜਦੋਂ ਕੇਵਲ ਇੱਕ ਕਮਾਂਡ ਕਲਾਸ ਕਾਫ਼ੀ ਨਾ ਹੋਵੇ, ਤਾਂ ਫਿਲਟਰ ਕਮਾਂਡ ਪੈਟਰਨ ਜਾਂ ਆਉਟਪੁੱਟ regex ਰਾਹੀਂ ਵੀ ਮੇਲ ਕਰ ਸਕਦੇ ਹਨ।

## ਫਿਲਟਰ ਰਿਜ਼ੋਲਿਊਸ਼ਨ

RTK ਫਿਲਟਰਾਂ ਨੂੰ ਇਸ ਕ੍ਰਮ ਵਿੱਚ ਲੋਡ ਕਰਦਾ ਹੈ:

1. `.rtk/filters.toml` ਅਤੇ `.rtk/filters.json` ਤੋਂ ਪ੍ਰੋਜੈਕਟ ਫਿਲਟਰ, ਸਿਰਫ਼ ਭਰੋਸੇਯੋਗ ਹੋਣ 'ਤੇ।
2. `DATA_DIR/rtk/filters.toml` ਅਤੇ `DATA_DIR/rtk/filters.json` ਤੋਂ ਗਲੋਬਲ ਫਿਲਟਰ।
3. `open-sse/services/compression/engines/rtk/filters/` ਤੋਂ ਬਿਲਟ-ਇਨ ਫਿਲਟਰ।

ਇੱਕੋ ਸਕੋਪ ਦੇ ਅੰਦਰ, RTK TOML schema v1 ਫਿਲਟਰਾਂ ਨੂੰ OmniRoute JSON ਫਿਲਟਰਾਂ ਉੱਤੇ ਤਰਜੀਹ ਮਿਲਦੀ ਹੈ। TOML
`match_command` ਐਕਸਪ੍ਰੈਸ਼ਨਾਂ ਦੀ ਜਾਂਚ ਕਮਾਂਡ-ਟਾਈਪ ਮੇਲ ਤੋਂ ਪਹਿਲਾਂ ਕੀਤੀ ਜਾਂਦੀ ਹੈ, ਤਾਂ ਜੋ ਆਯਾਤ ਕੀਤਾ ਕਮਾਂਡ-ਵਿਸ਼ੇਸ਼
ਫਿਲਟਰ ਉਸ ਸਕੋਪ ਵਿੱਚ ਕਿਸੇ ਵਧੇਰੇ ਵਿਆਪਕ ਫਿਲਟਰ ਨੂੰ ਓਵਰਰਾਈਡ ਕਰ ਸਕੇ। ਫਾਈਲ ਫਾਰਮੈਟ ਦੀ ਪਰਵਾਹ ਕੀਤੇ ਬਿਨਾਂ, ਪ੍ਰੋਜੈਕਟ ਸਕੋਪ ਨੂੰ ਫਿਰ ਵੀ ਗਲੋਬਲ
ਸਕੋਪ ਉੱਤੇ ਤਰਜੀਹ ਮਿਲਦੀ ਹੈ।

ਪ੍ਰੋਜੈਕਟ ਫਿਲਟਰਾਂ ਨੂੰ ਜਾਣਬੁੱਝ ਕੇ ਭਰੋਸੇ ਦੇ ਆਧਾਰ 'ਤੇ ਸੀਮਿਤ ਕੀਤਾ ਗਿਆ ਹੈ, ਕਿਉਂਕਿ regex ਫਿਲਟਰ ਇਹ ਬਦਲ ਸਕਦੇ ਹਨ ਕਿ ਟੂਲ ਆਉਟਪੁੱਟ
ਏਜੰਟਾਂ ਨੂੰ ਕਿਵੇਂ ਦਿਖਾਇਆ ਜਾਂਦਾ ਹੈ। ਇੱਕ ਪ੍ਰੋਜੈਕਟ ਫਿਲਟਰ ਫਾਈਲ ਉਦੋਂ ਸਵੀਕਾਰ ਕੀਤੀ ਜਾਂਦੀ ਹੈ ਜਦੋਂ ਇਨ੍ਹਾਂ ਵਿੱਚੋਂ ਕੋਈ ਇੱਕ ਸ਼ਰਤ ਸਹੀ ਹੋਵੇ:

- `rtkConfig.trustProjectFilters` `true` ਹੋਵੇ।
- `OMNIROUTE_RTK_TRUST_PROJECT_FILTERS=1` ਸੈੱਟ ਹੋਵੇ।
- `.rtk/trust.json` ਵਿੱਚ ਪ੍ਰੋਜੈਕਟ ਫਿਲਟਰ ਫਾਈਲ ਲਈ ਮੇਲ ਖਾਂਦਾ SHA-256 ਹੈਸ਼ ਮੌਜੂਦ ਹੋਵੇ।

ਭਰੋਸਾ ਫਾਈਲ ਦੀ ਉਦਾਹਰਨ:

```json
{
  "filtersSha256": "0123456789abcdef...",
  "filtersTomlSha256": "fedcba9876543210..."
}
```

ਹੈਸ਼ ਵੱਖਰੇ ਹਨ: `filtersSha256` `.rtk/filters.json` 'ਤੇ ਭਰੋਸਾ ਕਰਦਾ ਹੈ, ਜਦਕਿ `filtersTomlSha256`
`.rtk/filters.toml` 'ਤੇ ਭਰੋਸਾ ਕਰਦਾ ਹੈ। ਕਿਸੇ ਵੀ ਫਾਈਲ ਨੂੰ ਸੋਧਣ ਨਾਲ ਸਿਰਫ਼ ਉਸਦੀ ਆਪਣੀ ਭਰੋਸਾ ਐਂਟਰੀ ਅਵੈਧ ਹੁੰਦੀ ਹੈ। ਗਲੋਬਲ ਫਾਈਲਾਂ
ਪ੍ਰਸ਼ਾਸਕ ਵੱਲੋਂ ਇੰਸਟਾਲ ਕੀਤੀਆਂ ਜਾਂਦੀਆਂ ਹਨ ਅਤੇ ਮੌਜੂਦਾ ਗਲੋਬਲ-ਫਿਲਟਰ ਭਰੋਸਾ ਵਿਹਾਰ ਦੀ ਵਰਤੋਂ ਕਰਦੀਆਂ ਹਨ।

ਕਸਟਮ ਫਿਲਟਰ ਇੱਕ ਫਿਲਟਰ ਆਬਜੈਕਟ ਜਾਂ ਫਿਲਟਰ ਆਬਜੈਕਟਾਂ ਦੀ ਇੱਕ ਐਰੇ ਹੋ ਸਕਦੇ ਹਨ। ਅਵੈਧ ਕਸਟਮ ਫਿਲਟਰਾਂ ਨੂੰ
ਛੱਡ ਦਿੱਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ `/api/context/rtk/filters` ਡਾਇਗਨੋਸਟਿਕਸ ਦੁਆਰਾ ਰਿਪੋਰਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਅਵੈਧ ਬਿਲਟ-ਇਨ ਫਿਲਟਰ ਤੁਰੰਤ ਅਸਫਲ ਹੋ ਜਾਂਦੇ ਹਨ।

## RTK TOML ਸਕੀਮਾ v1 ਅਨੁਕੂਲਤਾ

OmniRoute, RTK TOML ਸਕੀਮਾ v1 ਦੀ ਵਰਤੋਂ ਕਰਨ ਵਾਲੀਆਂ ਘੋਸ਼ਣਾਤਮਕ ਫਿਲਟਰ ਫਾਈਲਾਂ ਨੂੰ ਪਾਰਸ, ਪ੍ਰਮਾਣਿਤ, ਟੈਸਟ ਅਤੇ ਇੰਸਟਾਲ ਕਰ ਸਕਦਾ ਹੈ।
ਸਮਰਥਿਤ ਫੀਲਡ ਹਨ: `description`, `match_command`, `strip_ansi`, `filter_stderr`,
`strip_lines_matching`, `keep_lines_matching`, `replace`, `match_output`, `truncate_lines_at`,
`head_lines`, `tail_lines`, `max_lines`, `on_empty`, ਅਤੇ `[[tests.<filter>]]` ਇਨਲਾਈਨ ਟੈਸਟ।
ਅਣਜਾਣ ਫੀਲਡ, ਅਵੈਧ ਜਾਂ ਅਸੁਰੱਖਿਅਤ ਰੈਗੂਲਰ ਐਕਸਪ੍ਰੈਸ਼ਨ, ਇੱਕੋ ਸਮੇਂ ਵਰਤੇ ਗਏ strip/keep ਨਿਯਮ, 1 MiB ਤੋਂ ਵੱਡੀਆਂ ਫਾਈਲਾਂ,
ਅਤੇ ਅਣਜਾਣ ਫਿਲਟਰਾਂ ਦੇ ਹਵਾਲੇ ਰੱਦ ਕਰ ਦਿੱਤੇ ਜਾਂਦੇ ਹਨ। ਜਿਸ ਫਾਈਲ ਦੇ ਇਨਲਾਈਨ ਟੈਸਟ ਅਸਫਲ ਹੋ ਜਾਂਦੇ ਹਨ, ਉਸ ਨੂੰ
ਜਾਂਚ ਲਈ ਪ੍ਰਮਾਣਿਤ ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ, ਪਰ ਇੰਸਟਾਲ ਜਾਂ ਲੋਡ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ। ਕਸਟਮ ਫਾਈਲ ਲੋਡ ਕਰਨ ਦੀਆਂ ਅਸਫਲਤਾਵਾਂ
fail-open ਰਹਿੰਦੀਆਂ ਹਨ: ਅਵੈਧ ਫਾਈਲ ਛੱਡ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ ਅਤੇ ਬਾਕੀ ਫਿਲਟਰ ਕੰਮ ਕਰਦੇ ਰਹਿੰਦੇ ਹਨ।

OmniRoute ਨੂੰ ਟੂਲ ਆਉਟਪੁੱਟ ਕਲਾਇੰਟ ਦੁਆਰਾ ਪਹਿਲਾਂ ਹੀ ਕੈਪਚਰ ਕੀਤੇ ਜਾਣ ਤੋਂ ਬਾਅਦ ਮਿਲਦਾ ਹੈ, ਇਸ ਲਈ `filter_stderr = true`
ਪ੍ਰੋਸੈਸ ਕੈਪਚਰ ਨੂੰ ਨਹੀਂ ਬਦਲ ਸਕਦਾ। ਇਹ ਫੀਲਡ no-op ਵਜੋਂ ਸਵੀਕਾਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ ਪ੍ਰਮਾਣੀਕਰਨ ਇੱਕ ਚੇਤਾਵਨੀ ਦਿੰਦਾ ਹੈ।
ਇਸ ਨੂੰ ਜਾਣ-ਬੁੱਝ ਕੇ **RTK TOML ਸਕੀਮਾ v1 ਅਨੁਕੂਲਤਾ** ਵਜੋਂ ਦਰਸਾਇਆ ਗਿਆ ਹੈ, ਨਾ ਕਿ RTK executable,
shell hooks, Rust ਕਮਾਂਡ ਇੰਪਲੀਮੈਂਟੇਸ਼ਨਾਂ ਜਾਂ ਇਸ ਦੇ trust-store ਲੇਆਉਟ ਨਾਲ ਪੂਰੀ ਅਨੁਕੂਲਤਾ ਵਜੋਂ।

ਡੈਸ਼ਬੋਰਡ ਦਾ ਉੱਨਤ RTK ਵਿਊ ਪੇਸਟ ਜਾਂ ਅਪਲੋਡ ਕੀਤਾ TOML ਸਵੀਕਾਰ ਕਰਦਾ ਹੈ। ਪ੍ਰਮਾਣੀਕਰਨ ਸਿਰਫ਼ ਪੜ੍ਹਨ ਲਈ ਹੈ।
ਇੰਸਟਾਲੇਸ਼ਨ ਪਾਬੰਦੀਸ਼ੁਦਾ ਅਨੁਮਤੀਆਂ ਨਾਲ `DATA_DIR/rtk/filters.toml` ਨੂੰ ਐਟਾਮਿਕ ਢੰਗ ਨਾਲ ਲਿਖਦੀ ਹੈ ਅਤੇ
ਰੀਸਟਾਰਟ ਤੋਂ ਬਿਨਾਂ ਲਾਈਵ ਫਿਲਟਰ ਕੈਟਾਲਾਗ ਨੂੰ ਤਾਜ਼ਾ ਕਰਦੀ ਹੈ। ਕਿਸੇ ਮੌਜੂਦਾ ਫਾਈਲ ਨੂੰ ਬਦਲਣ ਲਈ ਸਪਸ਼ਟ `overwrite`
ਪੁਸ਼ਟੀ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ ਅਤੇ ਪਹਿਲਾਂ `DATA_DIR/rtk/filters.toml.bak` ਬਣਾਈ ਜਾਂਦੀ ਹੈ।

## ਫਿਲਟਰ DSL

ਫਿਲਟਰ [ਕੰਪ੍ਰੈਸ਼ਨ ਨਿਯਮ ਫਾਰਮੈਟ](./COMPRESSION_RULES_FORMAT.md) ਵਿੱਚ ਵਰਣਿਤ JSON ਸਕੀਮਾ ਦੀ ਵਰਤੋਂ ਕਰਦੇ ਹਨ।
ਰਨਟਾਈਮ ਇਹ ਪੜਾਅ ਦਿੱਤੇ ਕ੍ਰਮ ਵਿੱਚ ਲਾਗੂ ਕਰਦਾ ਹੈ:

```txt
stripAnsi -> filterStderr -> replace -> matchOutput -> drop/include lines
  -> truncateLineAt -> head/tail/maxLines -> onEmpty
```

ਮਹੱਤਵਪੂਰਨ ਫੀਲਡ:

| ਫੀਲਡ                         | ਉਦੇਸ਼                                                                       |
| ---------------------------- | --------------------------------------------------------------------------- |
| `rules.stripAnsi`            | ਮੈਚਿੰਗ ਤੋਂ ਪਹਿਲਾਂ ਟਰਮੀਨਲ ਰੰਗ/ਕੰਟਰੋਲ ਲੜੀਆਂ ਹਟਾਓ                              |
| `rules.filterStderr`         | ਮੈਚਿੰਗ/ਫਿਲਟਰਿੰਗ ਤੋਂ ਪਹਿਲਾਂ ਆਮ stderr ਪ੍ਰੀਫਿਕਸਾਂ ਨੂੰ ਨਾਰਮਲਾਈਜ਼ ਕਰੋ           |
| `rules.replace`              | ਕ੍ਰਮਬੱਧ regex ਤਬਦੀਲੀਆਂ ਲਾਗੂ ਕਰੋ                                             |
| `rules.matchOutput`          | ਜਦੋਂ ਆਉਟਪੁੱਟ ਕਿਸੇ ਜਾਣੀ-ਪਛਾਣੀ ਸਥਿਤੀ ਨਾਲ ਮੇਲ ਖਾਂਦਾ ਹੈ, ਤਾਂ ਸੰਖੇਪ ਸਾਰ ਵਾਪਸ ਕਰੋ |
| `rules.matchOutput[].unless` | ਜਦੋਂ ਕੋਈ error/failure ਪੈਟਰਨ ਮੌਜੂਦ ਹੋਵੇ, ਤਾਂ ਸ਼ਾਰਟਕੱਟ ਛੱਡੋ                  |
| `rules.dropPatterns`         | ਬੇਲੋੜੀਆਂ ਲਾਈਨਾਂ ਹਟਾਓ                                                        |
| `rules.includePatterns`      | ਕਾਰਵਾਈਯੋਗ ਲਾਈਨਾਂ ਨੂੰ ਤਰਜੀਹ ਦਿਓ                                              |
| `rules.collapsePatterns`     | ਵਾਰ-ਵਾਰ ਆਉਣ ਵਾਲੀਆਂ ਮੇਲ ਖਾਂਦੀਆਂ ਲਾਈਨਾਂ ਨੂੰ ਇਕੱਠਾ ਕਰੋ                         |
| `rules.deduplicate`          | ਪ੍ਰਤੀ-ਫਿਲਟਰ opt-in: ਲਗਾਤਾਰ ਦੁਹਰਾਈਆਂ ਲਾਈਨਾਂ ਨੂੰ ਇਕੱਠਾ ਕਰੋ                    |
| `rules.truncateLineAt`       | Unicode-ਸੁਰੱਖਿਅਤ ਪ੍ਰਤੀ-ਲਾਈਨ ਕਟੌਤੀ                                           |
| `rules.onEmpty`              | ਜੇ ਸਾਰੀਆਂ ਲਾਈਨਾਂ ਫਿਲਟਰ ਹੋ ਜਾਣ ਤਾਂ ਫਾਲਬੈਕ ਸੁਨੇਹਾ                             |
| `tests[]`                    | verify gate ਦੁਆਰਾ ਵਰਤੇ ਜਾਣ ਵਾਲੇ ਇਨਲਾਈਨ ਨਮੂਨੇ                                |

ਬਿਲਟ-ਇਨ ਫਿਲਟਰਾਂ ਵਿੱਚ ਇਨਲਾਈਨ `tests[]` ਨਮੂਨੇ ਸ਼ਾਮਲ ਹੋਣੇ ਚਾਹੀਦੇ ਹਨ। ਕਸਟਮ ਫਿਲਟਰਾਂ ਵਿੱਚ ਵੀ
ਇਹ ਸ਼ਾਮਲ ਹੋਣੇ ਚਾਹੀਦੇ ਹਨ, ਖ਼ਾਸ ਕਰਕੇ ਜਦੋਂ ਉਹ ਵੱਖ-ਵੱਖ ਪ੍ਰੋਜੈਕਟਾਂ ਵਿੱਚ ਸਾਂਝੇ ਕੀਤੇ ਜਾਂਦੇ ਹਨ।

## ਲਾਈਨ ਡੀਡੁਪਲੀਕੇਸ਼ਨ (ਦੋ ਪਰਤਾਂ)

RTK ਡੁਪਲੀਕੇਟ ਲਾਈਨਾਂ ਨੂੰ ਦੋ ਸੁਤੰਤਰ ਪਰਤਾਂ 'ਤੇ ਇਕੱਠਾ ਕਰਦਾ ਹੈ:

1. **ਪ੍ਰਤੀ-ਫਿਲਟਰ `deduplicate` (ਚੋਣਵਾਂ, ਡਿਫਾਲਟ `false`)।** ਕੋਈ ਫਿਲਟਰ `rules.deduplicate: true`
   ਸੈੱਟ ਕਰ ਸਕਦਾ ਹੈ ਤਾਂ ਜੋ ਕੱਟ-ਛਾਂਟ ਤੋਂ ਪਹਿਲਾਂ, _ਉਸ ਫਿਲਟਰ ਦੇ ਮੇਲ ਖਾਂਦੇ ਆਉਟਪੁੱਟ ਦੇ ਅੰਦਰ_ ਲਗਾਤਾਰ
   ਡੁਪਲੀਕੇਟ ਲਾਈਨਾਂ ਨੂੰ ਇਕੱਠਾ ਕੀਤਾ ਜਾ ਸਕੇ। ਇਹ `lineFilter.ts` ਦੇ ਅੰਦਰ ਚੱਲਦਾ ਹੈ। ਪੁਰਾਣੇ ਫਿਲਟਰਾਂ ਲਈ,
   ਜਦੋਂ ਫਿਲਟਰ `collapsePatterns` ਪਰਿਭਾਸ਼ਿਤ ਕਰਦਾ ਹੈ ਤਾਂ ਇਹ ਆਪਣੇ ਆਪ ਸਮਰੱਥ ਹੋ ਜਾਂਦਾ ਹੈ। ਸਕੀਮਾ:
   `open-sse/services/compression/engines/rtk/filterSchema.ts` ਵਿੱਚ
   `deduplicate: z.boolean().default(false)`।
2. **ਪੂਰੇ ਇੰਜਣ ਲਈ `deduplicateThreshold` (ਡਿਫਾਲਟ `3`)।** ਸਾਰੇ ਫਿਲਟਰਾਂ ਦੇ ਚੱਲਣ ਤੋਂ ਬਾਅਦ, ਇੰਜਣ
   ਪੂਰੇ ਨਤੀਜੇ ਵਿੱਚ `>= deduplicateThreshold` ਇੱਕੋ ਜਿਹੀਆਂ ਲਗਾਤਾਰ ਲਾਈਨਾਂ ਦੇ ਕਿਸੇ ਵੀ ਕ੍ਰਮ ਨੂੰ ਇਕੱਠਾ
   ਕਰਦਾ ਹੈ (`deduplicateRepeatedLines`, ਜਿਸਨੂੰ `engines/rtk/index.ts` ਵਿੱਚ ਲਾਗੂ ਕੀਤਾ ਜਾਂਦਾ ਹੈ)।
   ਨਾਰਮਲਾਈਜ਼ੇਸ਼ਨ ਦੌਰਾਨ ਮੁੱਲ ਨੂੰ 2–100 ਦੀ ਸੀਮਾ ਵਿੱਚ ਰੱਖਿਆ ਜਾਂਦਾ ਹੈ।

ਪ੍ਰਤੀ-ਫਿਲਟਰ ਪਾਸ ਪਹਿਲਾਂ (ਫਿਲਟਰ ਦੇ ਅੰਦਰ) ਚੱਲਦਾ ਹੈ, ਜਦਕਿ ਪੂਰੇ ਇੰਜਣ ਵਾਲਾ ਪਾਸ ਅੰਤ ਵਿੱਚ (ਜੋੜੇ ਹੋਏ
ਆਉਟਪੁੱਟ ਉੱਤੇ) ਚੱਲਦਾ ਹੈ, ਇਸ ਲਈ ਦੋਵੇਂ ਬਿਨਾਂ ਦੋਹਰੀ ਗਿਣਤੀ ਦੇ ਇਕੱਠੇ ਕੰਮ ਕਰਦੇ ਹਨ।

## ਲਾਈਨ ਗਰੁੱਪਿੰਗ (`enableGrouping`)

ਜਦੋਂ `rtkConfig.enableGrouping` `true` ਹੁੰਦਾ ਹੈ (ਡਿਫਾਲਟ `false`), ਤਾਂ RTK ਡੀਡੁਪਲੀਕੇਸ਼ਨ ਤੋਂ ਬਾਅਦ
ਮਿਲੇ ਨਤੀਜੇ ਉੱਤੇ ਇੱਕ ਵਾਧੂ `groupSimilarLines` ਪਾਸ ਚਲਾਉਂਦਾ ਹੈ, ਜੋ _ਲਗਭਗ ਸਮਾਨ_ (ਬਾਈਟ-ਪੱਧਰ 'ਤੇ
ਇੱਕੋ ਜਿਹੀਆਂ ਨਹੀਂ) ਲਗਾਤਾਰ ਲਾਈਨਾਂ ਦੇ ਕ੍ਰਮਾਂ ਨੂੰ ਇਕੱਠਾ ਕਰਦਾ ਹੈ। `rtkConfig.groupingThreshold`
(ਡਿਫਾਲਟ `3`) ਉਹ ਘੱਟੋ-ਘੱਟ ਕ੍ਰਮ-ਲੰਬਾਈ ਹੈ ਜੋ ਗਰੁੱਪਿੰਗ ਨੂੰ ਚਾਲੂ ਕਰਦੀ ਹੈ। ਇਹ
`deduplicateThreshold` ਦਾ ਸੰਰਚਨਾਤਮਕ ਸਮਰੂਪ ਹੈ: ਡੀਡੁਪਲੀਕੇਸ਼ਨ ਬਿਲਕੁਲ ਇੱਕੋ ਜਿਹੀਆਂ ਦੁਹਰਾਈਆਂ ਨੂੰ
ਸੰਭਾਲਦੀ ਹੈ, ਜਦਕਿ ਗਰੁੱਪਿੰਗ "ਛੋਟੇ ਅੰਤਰਾਂ ਨਾਲ ਇੱਕੋ ਆਕਾਰ" ਨੂੰ ਸੰਭਾਲਦੀ ਹੈ। ਦੋਵੇਂ ਫਲੈਗ `key_value`
ਟੇਬਲ ਵਿੱਚ ਸਥਾਈ ਤੌਰ 'ਤੇ ਸੰਭਾਲੇ `rtkConfig` JSON ਦਾ ਹਿੱਸਾ ਹਨ (ਉੱਪਰ ਸੰਰਚਨਾ ਵੇਖੋ), ਇਸ ਲਈ ਸੈਟਿੰਗ
ਰੀਸਟਾਰਟ ਤੋਂ ਬਾਅਦ ਵੀ ਕਾਇਮ ਰਹਿੰਦੀ ਹੈ।

## ਕੋਡ ਟਿੱਪਣੀਆਂ ਹਟਾਉਣਾ (`stripCodeComments` / `preserveDocstrings`)

ਜਦੋਂ `rtkConfig.applyToCodeBlocks` ਸਮਰੱਥ ਹੁੰਦਾ ਹੈ, ਤਾਂ RTK ਫੈਂਸ ਕੀਤੇ ਕੋਡ ਬਲਾਕਾਂ ਵਿੱਚੋਂ ਟਿੱਪਣੀਆਂ
ਵੀ ਹਟਾ ਸਕਦਾ ਹੈ:

- `stripCodeComments` (ਡਿਫਾਲਟ `false`) — ਚੋਣਵਾਂ। ਜਦੋਂ `true` ਹੋਵੇ, ਤਾਂ RTK JavaScript ਅਤੇ
  TypeScript ਦੇ ਫੈਂਸ ਕੀਤੇ ਬਲਾਕਾਂ ਵਿੱਚੋਂ ਟਿੱਪਣੀਆਂ ਹਟਾ ਦਿੰਦਾ ਹੈ। ਇਤਿਹਾਸਕ ਤੌਰ 'ਤੇ ਇਹ ਫਲੈਗ ਪੜ੍ਹਿਆ
  ਜਾਂਦਾ ਸੀ ਪਰ ਕਦੇ ਲਾਗੂ ਨਹੀਂ ਕੀਤਾ ਗਿਆ, ਇਸ ਲਈ ਪ੍ਰੋਡਕਸ਼ਨ ਵਿੱਚ ਬਿਨਾਂ ਸੂਚਨਾ ਬਦਲਾਅ ਤੋਂ ਬਚਣ ਲਈ ਡਿਫਾਲਟ
  "ਸੁਰੱਖਿਅਤ ਰੱਖੋ" ਹੀ ਰਹਿੰਦਾ ਹੈ।
- `preserveDocstrings` (ਡਿਫਾਲਟ `true`) — ਟਿੱਪਣੀਆਂ ਹਟਾਉਂਦੇ ਸਮੇਂ, JSDoc/`/** … */` ਬਲਾਕ ਟਿੱਪਣੀਆਂ
  ਸੁਰੱਖਿਅਤ ਰੱਖੀਆਂ ਜਾਂਦੀਆਂ ਹਨ (ਉਹ ਅਜਿਹੀ API ਦਸਤਾਵੇਜ਼ੀ ਜਾਣਕਾਰੀ ਰੱਖਦੀਆਂ ਹਨ ਜਿਸਦੀ ਕੀਮਤ ਉਹਨਾਂ ਵੱਲੋਂ
  ਵਰਤੇ ਬਾਈਟਾਂ ਨਾਲੋਂ ਵੱਧ ਹੈ)। ਉਹਨਾਂ ਨੂੰ ਵੀ ਹਟਾਉਣ ਲਈ ਇਸਨੂੰ `false` ਸੈੱਟ ਕਰੋ।

ਟਿੱਪਣੀਆਂ ਨੂੰ ਹਟਾਉਣ ਦੀ ਕਾਰਵਾਈ `open-sse/services/compression/engines/rtk/codeStripper.ts` ਵਿੱਚ
ਲਾਗੂ ਕੀਤੀ ਗਈ ਹੈ। ਇਹ **TypeScript ਪਾਰਸਰ** ਦੀ ਵਰਤੋਂ ਕਰਦੀ ਹੈ (regex ਦੀ ਨਹੀਂ), ਤਾਂ ਜੋ ਸਟਰਿੰਗ,
ਟੈਂਪਲੇਟ ਅਤੇ regex ਲਿਟਰਲਾਂ ਨੂੰ ਕਦੇ ਵੀ ਗਲਤੀ ਨਾਲ ਟਿੱਪਣੀਆਂ ਨਾ ਸਮਝਿਆ ਜਾਵੇ, ਅਤੇ JSX ਦਾ ਪਤਾ ਲੱਗਣ 'ਤੇ
ਇਹ ਪੂਰੀ ਤਰ੍ਹਾਂ ਕਾਰਵਾਈ ਛੱਡ ਦਿੰਦੀ ਹੈ (ਤਾਂ ਜੋ JSX ਐਕਸਪ੍ਰੈਸ਼ਨ-ਕੰਟੇਨਰ ਟਿੱਪਣੀਆਂ ਕਦੇ ਖਰਾਬ ਨਾ ਹੋਣ)।
ਟਿੱਪਣੀਆਂ ਹਟਾਉਣਾ ਵਰਤਮਾਨ ਵਿੱਚ **ਕੇਵਲ JavaScript ਅਤੇ TypeScript** 'ਤੇ ਲਾਗੂ ਹੁੰਦਾ ਹੈ — ਸਟ੍ਰਿਪਰ ਦੇ
`CodeLanguage` ਸੈੱਟ ਵਿੱਚ ਹੋਰ ਭਾਸ਼ਾਵਾਂ (Python, Rust, Go, Ruby, Java) ਲਈ ਖਾਲੀ ਲਾਈਨਾਂ ਅਤੇ ਖਾਲੀ
ਥਾਂਵਾਂ ਨੂੰ ਇਕੱਠਾ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਪਰ ਟਿੱਪਣੀਆਂ ਨਹੀਂ ਹਟਾਈਆਂ ਜਾਂਦੀਆਂ। ਸਟ੍ਰਿਪ ਕੀਤੇ ਬਲਾਕ ਦੀ ਰਨ ਨੂੰ
`rulesApplied` ਵਿੱਚ `rtk:code-strip` ਨਾਲ ਟੈਗ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

> **ਨੋਟ — GCF / ਟੇਬਲਰ ਐਨਕੋਡਿੰਗ ਇੱਕ ਵੱਖਰਾ ਇੰਜਣ ਹੈ।** RTK ਵਿੱਚ "GCF"
> (Graph Compact Format) ਟੇਬਲਰ/ਕਾਲਮਨਰ JSON ਐਨਕੋਡਰ ਸ਼ਾਮਲ **ਨਹੀਂ** ਹੈ। ਉਹ ਐਨਕੋਡਰ — ਜਿਸਨੇ ਇੱਕ
> ਪੁਰਾਣੇ `omni-tabular` ਐਨਕੋਡਰ ਦੀ ਥਾਂ ਲਈ ਸੀ — **headroom** ਇੰਜਣ ਵਿੱਚ ਮੌਜੂਦ ਹੈ
> (`open-sse/services/compression/engines/headroom/`, ਜਦਕਿ ਵੇਂਡਰ ਕੀਤਾ ਕੋਡੈਕ
> `headroom/gcf/` ਦੇ ਅਧੀਨ ਹੈ)। ਇਸਦਾ ਇੱਥੇ ਦਸਤਾਵੇਜ਼ਬੱਧ RTK ਫਿਲਟਰ ਪਾਈਪਲਾਈਨ ਨਾਲ ਕੋਈ ਸੰਬੰਧ ਨਹੀਂ ਹੈ।

## ਸੰਰਚਨਾ

ਗਲੋਬਲ ਸੈਟਿੰਗਾਂ `/api/settings/compression` ਰਾਹੀਂ ਉਪਲਬਧ ਹਨ। RTK-ਵਿਸ਼ੇਸ਼ ਸੈਟਿੰਗਾਂ ਵੀ
`/api/context/rtk/config` ਰਾਹੀਂ ਉਪਲਬਧ ਹਨ।

```json
{
  "defaultMode": "stacked",
  "autoTriggerMode": "stacked",
  "autoTriggerTokens": 32000,
  "stackedPipeline": [
    { "engine": "rtk", "intensity": "standard" },
    { "engine": "caveman", "intensity": "full" }
  ],
  "rtkConfig": {
    "enabled": true,
    "intensity": "standard",
    "applyToToolResults": true,
    "applyToCodeBlocks": false,
    "applyToAssistantMessages": false,
    "enabledFilters": [],
    "disabledFilters": [],
    "maxLinesPerResult": 120,
    "maxCharsPerResult": 12000,
    "deduplicateThreshold": 3,
    "customFiltersEnabled": true,
    "trustProjectFilters": false,
    "rawOutputRetention": "never",
    "rawOutputMaxBytes": 1048576,
    "enableGrouping": false,
    "groupingThreshold": 3,
    "stripCodeComments": false,
    "preserveDocstrings": true
  }
}
```

`enabledFilters` ਅਤੇ `disabledFilters` ਫਿਲਟਰ ਆਈਡੀ ਵਰਤਦੇ ਹਨ, ਉਦਾਹਰਨ ਲਈ `test-vitest` ਜਾਂ `git-diff`।

ਪੂਰਾ `rtkConfig` ਢਾਂਚਾ `open-sse/services/compression/types.ts` ਵਿੱਚ `RtkConfig` /
`DEFAULT_RTK_CONFIG` ਦੁਆਰਾ ਪਰਿਭਾਸ਼ਿਤ ਕੀਤਾ ਗਿਆ ਹੈ। ਪੂਰਾ ਆਬਜੈਕਟ SQLite `key_value` ਟੇਬਲ ਵਿੱਚ
`namespace = "compression"`, `key = "rtkConfig"` ਦੇ ਅਧੀਨ ਇੱਕੋ JSON ਮੁੱਲ ਵਜੋਂ ਸੁਰੱਖਿਅਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ
(`src/lib/db/compression.ts`), ਅਤੇ ਪੜ੍ਹਨ ਵੇਲੇ `normalizeRtkConfig` ਦੁਆਰਾ ਸਧਾਰਣ ਬਣਾਇਆ ਜਾਂਦਾ ਹੈ। ਇਸ ਲਈ ਹੇਠਾਂ ਦਿੱਤਾ ਹਰੇਕ ਫੀਲਡ
— `enableGrouping`, `groupingThreshold`, `stripCodeComments`, ਅਤੇ `preserveDocstrings` ਸਮੇਤ —
ਉਸੇ ਸਟੋਰ ਵਿੱਚੋਂ ਰਾਊਂਡ-ਟ੍ਰਿਪ ਕਰਦਾ ਹੈ ਅਤੇ ਰੀਸਟਾਰਟ ਤੋਂ ਬਾਅਦ ਵੀ ਕਾਇਮ ਰਹਿੰਦਾ ਹੈ।

| ਕੁੰਜੀ                  | ਮੂਲ ਮੁੱਲ | ਉਦੇਸ਼                                                                              |
| ---------------------- | -------- | ---------------------------------------------------------------------------------- |
| `deduplicateThreshold` | `3`      | ਪੂਰੇ ਇੰਜਣ ਲਈ: ਸਮੇਟਣ ਵਾਸਤੇ ਲਗਾਤਾਰ ਇੱਕੋ ਜਿਹੀਆਂ ਲਾਈਨਾਂ ਦੀ ਘੱਟੋ-ਘੱਟ ਗਿਣਤੀ (ਸੀਮਾ 2–100) |
| `enableGrouping`       | `false`  | ਚੋਣਵਾਂ: ਲਗਭਗ ਬਰਾਬਰ ਲਗਾਤਾਰ ਲਾਈਨਾਂ ਦੇ ਕ੍ਰਮਾਂ ਨੂੰ ਸਮੇਟੋ                               |
| `groupingThreshold`    | `3`      | ਮਿਲਦੀਆਂ-ਜੁਲਦੀਆਂ ਲਗਾਤਾਰ ਲਾਈਨਾਂ ਦੇ ਕ੍ਰਮ ਦੀ ਘੱਟੋ-ਘੱਟ ਗਿਣਤੀ, ਜੋ ਗਰੁੱਪਿੰਗ ਸ਼ੁਰੂ ਕਰਦੀ ਹੈ |
| `stripCodeComments`    | `false`  | ਚੋਣਵਾਂ: ਫੈਂਸ ਕੀਤੇ ਕੋਡ ਬਲਾਕਾਂ ਤੋਂ ਟਿੱਪਣੀਆਂ ਹਟਾਓ (`applyToCodeBlocks` ਦੀ ਲੋੜ ਹੈ)     |
| `preserveDocstrings`   | `true`   | ਟਿੱਪਣੀਆਂ ਹਟਾਉਂਦੇ ਸਮੇਂ, JSDoc/`/** … */` ਬਲਾਕ ਕਾਇਮ ਰੱਖੋ                             |

| `/api/compression/preview`         | POST | ਕਿਸੇ ਵੀ ਕੰਪਰੈਸ਼ਨ ਮੋਡ ਦੀ ਝਲਕ ਵੇਖੋ                      |

RTK ਟੈਸਟ ਪੇਲੋਡ:

```json
{
  "command": "npm test",
  "text": "FAIL tests/example.test.ts\nAssertionError: expected true\nTest Files 1 failed",
  "config": {
    "intensity": "standard"
  }
}
```

ਕੰਪਰੈਸ਼ਨ ਝਲਕ ਪੇਲੋਡ:

```json
{
  "mode": "stacked",
  "messages": [
    {
      "role": "tool",
      "content": "FAIL tests/example.test.ts\nAssertionError: expected true\nTest Files 1 failed"
    }
  ],
  "config": {
    "rtkConfig": {
      "rawOutputRetention": "failures"
    }
  }
}
```

ਪ੍ਰਬੰਧਨ ਰੂਟਾਂ ਲਈ ਡੈਸ਼ਬੋਰਡ ਪ੍ਰਬੰਧਨ ਪ੍ਰਮਾਣੀਕਰਨ ਜਾਂ ਮੇਲ ਖਾਂਦੀ API-ਕੁੰਜੀ ਨੀਤੀ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।

RTK TOML ਪੁਸ਼ਟੀਕਰਨ ਪੇਲੋਡ:

```json
{
  "action": "validate",
  "content": "schema_version = 1\n\n[filters.my-tool]\nmatch_command = \"^my-tool\\\\b\"\nmax_lines = 20\n"
}
```

ਪੁਸ਼ਟੀ ਕੀਤੀ ਫਾਈਲ ਨੂੰ ਗਲੋਬਲ ਤੌਰ 'ਤੇ ਇੰਸਟਾਲ ਕਰਨ ਲਈ `"action": "install"` ਵਰਤੋ। ਕਿਸੇ ਮੌਜੂਦਾ ਗਲੋਬਲ ਫਾਈਲ ਨੂੰ ਬਦਲਣ ਦੀ ਸਮੀਖਿਆ ਅਤੇ ਪੁਸ਼ਟੀ ਕਰਨ ਤੋਂ ਬਾਅਦ ਹੀ
`"overwrite": true` ਸ਼ਾਮਲ ਕਰੋ।

## ਕੱਚੇ ਆਉਟਪੁੱਟ ਦੀ ਮੁੜ-ਪ੍ਰਾਪਤੀ

RTK ਆਮ ਤੌਰ 'ਤੇ ਸਿਰਫ਼ ਸੰਕੁਚਿਤ ਟੈਕਸਟ ਵਾਪਸ ਕਰਦਾ ਹੈ। ਡੀਬੱਗਿੰਗ ਲਈ, `rawOutputRetention` ਸੰਵੇਦਨਸ਼ੀਲ ਜਾਣਕਾਰੀ ਹਟਾਇਆ ਹੋਇਆ
ਕੱਚਾ ਆਉਟਪੁੱਟ ਸੰਭਾਲ ਸਕਦਾ ਹੈ:

| ਮੁੱਲ       | ਵਿਵਹਾਰ                                                                |
| ---------- | --------------------------------------------------------------------- |
| `never`    | ਕੱਚਾ ਆਉਟਪੁੱਟ ਨਾ ਸੰਭਾਲੋ                                                |
| `failures` | ਸਿਰਫ਼ ਸੰਭਾਵਿਤ ਅਸਫਲਤਾ ਵਾਲਾ ਆਉਟਪੁੱਟ ਸੰਭਾਲੋ                              |
| `always`   | ਸੰਵੇਦਨਸ਼ੀਲ ਜਾਣਕਾਰੀ ਹਟਾਉਣ ਤੋਂ ਬਾਅਦ, ਹਰ ਸੰਕੁਚਿਤ RTK ਕੱਚਾ ਆਉਟਪੁੱਟ ਸੰਭਾਲੋ |

ਸੰਭਾਲੀਆਂ ਫ਼ਾਈਲਾਂ ਇੱਥੇ ਲਿਖੀਆਂ ਜਾਂਦੀਆਂ ਹਨ:

```txt
DATA_DIR/rtk/raw-output/
```

ਸਥਾਈ ਸਟੋਰੇਜ ਤੋਂ ਪਹਿਲਾਂ ਰਾਜ਼ ਹਟਾ ਦਿੱਤੇ ਜਾਂਦੇ ਹਨ, ਜਿਨ੍ਹਾਂ ਵਿੱਚ ਆਮ bearer ਟੋਕਨ, API ਕੁੰਜੀਆਂ, Slack ਟੋਕਨ,
AWS ਐਕਸੈੱਸ ਕੁੰਜੀਆਂ, ਅਤੇ ਅਸਾਈਨਮੈਂਟ-ਸ਼ੈਲੀ ਦੇ `token=...`, `secret=...`, `password=...` ਮੁੱਲ ਸ਼ਾਮਲ ਹਨ। ਵਿਸ਼ਲੇਸ਼ਣ
ਸਿਰਫ਼ ਪੁਆਇੰਟਰ id, ਆਕਾਰ, ਅਤੇ ਹੈਸ਼ ਮੈਟਾਡਾਟਾ ਸਟੋਰ ਕਰਦਾ ਹੈ।

## RTK ਦਾ ਵਿਸਤਾਰ ਕਰਨਾ

1. ਇੱਕ ਫਿਲਟਰ JSON ਫ਼ਾਈਲ ਜੋੜੋ ਜਾਂ ਅੱਪਡੇਟ ਕਰੋ।
2. ਘੱਟੋ-ਘੱਟ ਇੱਕ `tests[]` ਨਮੂਨਾ ਸ਼ਾਮਲ ਕਰੋ ਜੋ ਮਹੱਤਵਪੂਰਨ ਵਿਵਹਾਰ ਨੂੰ ਸਾਬਤ ਕਰਦਾ ਹੋਵੇ।
3. ਨਵੇਂ ਕਮਾਂਡ ਪਰਿਵਾਰਾਂ ਲਈ `tests/unit/compression/fixtures/rtk/` ਦੇ ਅਧੀਨ ਇੱਕ fixture ਜੋੜੋ।
4. ਨਵੀਂ ਆਉਟਪੁੱਟ ਸ਼੍ਰੇਣੀ ਪੇਸ਼ ਕਰਦੇ ਸਮੇਂ ਕਮਾਂਡ ਪਛਾਣ ਕਵਰੇਜ ਜੋੜੋ।
5. ਤਸਦੀਕ ਅਤੇ ਵਿਆਪਕ RTK ਗੇਟ ਚਲਾਓ।
6. ਜੇ ਫਿਲਟਰ ਪ੍ਰੋਜੈਕਟ-ਲੋਕਲ ਹੈ, ਤਾਂ `.rtk/filters.json` ਨੂੰ commit ਕਰੋ ਅਤੇ ਸਮੀਖਿਆ ਤੋਂ ਬਾਅਦ ਹੀ `.rtk/trust.json` ਨੂੰ ਤਾਜ਼ਾ ਕਰੋ।

## ਤੀਬਰਤਾ ਪੱਧਰ (v3.8.16+)

RTK **3 ਤੀਬਰਤਾ ਪੱਧਰਾਂ** ਦਾ ਸਮਰਥਨ ਕਰਦਾ ਹੈ ਜੋ **ਸੰਕੁਚਨ ਦੀ ਆਕਰਮਕਤਾ** ਅਤੇ **ਸੁਰੱਖਿਆ** ਵਿਚਕਾਰ ਸੰਤੁਲਨ ਬਣਾਉਂਦੇ ਹਨ। ਪੱਧਰ ਨੂੰ ਇੰਜਣ ਸੰਰਚਨਾ ਵਿੱਚ `config.intensity` ਰਾਹੀਂ ਸੈੱਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

### 3 ਪੱਧਰ

| ---------------- | ------------------- | -------- | -------- | --------------------------- |

### ਪ੍ਰਭਾਵ ਦੀ ਤਸਦੀਕ ਕਰਨਾ

### ਕਸਟਮ ਫਿਲਟਰ ਲੋਡ ਕਰਨਾ

ਫਾਈਲ ਨੂੰ ਕਿਸੇ ਪਛਾਣੀ ਗਈ ਥਾਂ 'ਤੇ ਰੱਖੋ:

```
~/.omniroute/rtk/filters/my-filter.json     # ਵਰਤੋਂਕਾਰ-ਪੱਧਰ
<project>/.rtk/filters/my-filter.json      # ਪ੍ਰੋਜੈਕਟ-ਪੱਧਰ
```

ਫਿਲਟਰ ਸਟਾਰਟਅੱਪ ਵੇਲੇ `open-sse/services/compression/engines/rtk/filterLoader.ts` ਵਿੱਚ ਮੌਜੂਦ `loadRtkFilters()` ਰਾਹੀਂ ਆਪਣੇ-ਆਪ ਲੋਡ ਹੋ ਜਾਂਦੇ ਹਨ। ਲੋਡਰ ਹੇਠ ਲਿਖੀਆਂ ਥਾਵਾਂ ਤੋਂ ਫਿਲਟਰ ਲੱਭਦਾ ਹੈ:

- ਬਿਲਟ-ਇਨ ਕੈਟਾਲਾਗ: `open-sse/services/compression/engines/rtk/filters/`
- ਵਰਤੋਂਕਾਰ ਡਾਇਰੈਕਟਰੀ: `~/.omniroute/rtk/filters/`
- ਪ੍ਰੋਜੈਕਟ ਡਾਇਰੈਕਟਰੀ: `<project>/.rtk/filters/`

ਫਿਲਟਰਾਂ ਨੂੰ ਪ੍ਰੋਗਰਾਮ ਰਾਹੀਂ ਲੋਡ ਕਰਨ ਲਈ:

```ts
import { loadRtkFilters } from "@omniroute/open-sse/services/compression/engines/rtk/filterLoader";

// ਵਿਕਲਪ: customFiltersEnabled (ਵਰਤੋਂਕਾਰ/ਪ੍ਰੋਜੈਕਟ ਫਿਲਟਰ ਲੋਡ ਕਰੋ, ਡਿਫਾਲਟ ਤੌਰ 'ਤੇ ਚਾਲੂ),
// trustProjectFilters, refresh.
const filters = loadRtkFilters({ customFiltersEnabled: true });
```

### ਪ੍ਰਮਾਣਿਕਤਾ

ਲੋਡ ਹੋਣ ਵੇਲੇ ਫਿਲਟਰਾਂ ਦੀ Zod ਸਕੀਮਾ ਅਨੁਸਾਰ ਪ੍ਰਮਾਣਿਕਤਾ ਜਾਂਚੀ ਜਾਂਦੀ ਹੈ। ਗਲਤ ਬਣਤਰ ਵਾਲਾ ਫਿਲਟਰ ਲੋਡ ਨਹੀਂ ਹੋਵੇਗਾ ਅਤੇ ਇੱਕ ਗਲਤੀ ਲੌਗ ਕਰੇਗਾ:

```
RTK_FILTER_LOADER: filter "my-filter" failed validation:
  - rules.replace.0.pattern: Invalid regex
  - match.commands: must not be empty
```

ਇੰਸਟਾਲ ਕੀਤੇ ਸਾਰੇ ਫਿਲਟਰਾਂ ਦੀ ਪ੍ਰਮਾਣਿਕਤਾ ਜਾਂਚਣ ਲਈ, `runRtkFilterTests()` ਨੂੰ ਕਾਲ ਕਰੋ, ਜੋ `open-sse/services/compression/engines/rtk/verify.ts` ਤੋਂ ਐਕਸਪੋਰਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

### ਸਰਵੋਤਮ ਅਭਿਆਸ

1. **ਹਮੇਸ਼ਾ `tests[]` ਸ਼ਾਮਲ ਕਰੋ** — ਇਹ ਸਾਬਤ ਕਰਦੇ ਹਨ ਕਿ ਤੁਹਾਡਾ ਫ਼ਿਲਟਰ ਕੰਮ ਕਰਦਾ ਹੈ ਅਤੇ ਰਿਗ੍ਰੈਸ਼ਨਾਂ ਨੂੰ ਰੋਕਦੇ ਹਨ
2. **ਸ਼ਾਰਟ-ਸਰਕਿਟਾਂ ਲਈ `matchOutput` ਵਰਤੋ** — ਜੇ ਇੱਕੋ ਲਾਈਨ ਪੂਰੀ ਗੱਲ ਦੱਸਦੀ ਹੈ, ਤਾਂ ਪੂਰੇ ਬਲਾਕ ਨੂੰ ਬਦਲ ਦਿਓ
3. **`strip` ਦੀ ਬਜਾਏ `keep` ਨੂੰ ਤਰਜੀਹ ਦਿਓ** — ਸਪਸ਼ਟ "ਹਮੇਸ਼ਾ ਸੁਰੱਖਿਅਤ ਰੱਖੋ" ਨਿਯਮ "ਹਮੇਸ਼ਾ ਹਟਾਓ" ਨਾਲੋਂ ਵਧੇਰੇ ਸੁਰੱਖਿਅਤ ਹਨ
4. **ਤੀਬਰਤਾ ਦੇ ਸਾਰੇ 3 ਪੱਧਰਾਂ 'ਤੇ ਟੈਸਟ ਕਰੋ** — `minimal` ਨੂੰ ਕੋਈ ਕਾਰਵਾਈ ਨਹੀਂ ਕਰਨੀ ਚਾਹੀਦੀ, ਜਦਕਿ `aggressive` ਨੂੰ ਫਿਰ ਵੀ ਗਲਤੀਆਂ ਸੁਰੱਖਿਅਤ ਰੱਖਣੀਆਂ ਚਾਹੀਦੀਆਂ ਹਨ
5. **`unless` ਫ਼ੀਲਡ ਵਰਤੋ** — ਸ਼ਾਰਟ-ਸਰਕਿਟਾਂ ਨੂੰ "ਜੇ X ਮੌਜੂਦ ਹੋਵੇ ਤਾਂ ਟ੍ਰਿਗਰ ਨਾ ਕਰੋ" ਨਾਲ ਸੁਰੱਖਿਅਤ ਕਰੋ

## ਕੱਚੇ ਆਉਟਪੁੱਟ ਦੀ ਮੁੜ-ਪ੍ਰਾਪਤੀ ਅਤੇ ਤਸਦੀਕ ਗੇਟ

ਜਦੋਂ RTK ਆਉਟਪੁੱਟ ਨੂੰ ਬਹੁਤ ਜ਼ਿਆਦਾ ਸੰਕੁਚਿਤ ਕਰਦਾ ਹੈ, ਤਾਂ ਤੁਸੀਂ ਡੀਬੱਗਿੰਗ, ਆਡਿਟ ਜਾਂ ਮੁੜ ਚਲਾਉਣ ਲਈ **ਮੂਲ ਟੈਕਸਟ ਮੁੜ ਪ੍ਰਾਪਤ** ਕਰ ਸਕਦੇ ਹੋ।

### ਕੱਚੇ ਆਉਟਪੁੱਟ ਦੀ ਮੁੜ-ਪ੍ਰਾਪਤੀ ਕਿਵੇਂ ਕੰਮ ਕਰਦੀ ਹੈ

```
ਮੂਲ ਆਉਟਪੁੱਟ (10K ਟੋਕਨ)
        │
        ▼
RTK ਸੰਕੁਚਨ (rawOutput.enabled=true ਨਾਲ)
        │
        ├─▶ ਸੰਕੁਚਿਤ ਆਉਟਪੁੱਟ (2K ਟੋਕਨ)  ──▶ LLM ਵੱਲ
        │
        └─▶ ਮੂਲ ਆਉਟਪੁੱਟ (10K ਟੋਕਨ)      ──▶ DB ਵਿੱਚ ਸਟੋਰ ਕੀਤਾ ਗਿਆ
                                                  (request_id ਰਾਹੀਂ ਲਿੰਕ ਕੀਤਾ)
```

### ਕੱਚੇ ਆਉਟਪੁੱਟ ਦੀ ਸਟੋਰੇਜ ਨੂੰ ਸਮਰੱਥ ਕਰਨਾ

**ਹਰੇਕ ਬੇਨਤੀ ਲਈ** (ਕੌਂਬੋ ਸੰਰਚਨਾ ਵਿੱਚ):

```json
{
  "compression": {
    "engine": "rtk",
    "intensity": "aggressive",
    "rawOutput": {
      "enabled": true,
      "maxBytes": 1048576 // 1MB ਦੀ ਸੀਮਾ
    }
  }
}
```

**ਡਿਫੌਲਟ**: `rawOutput.enabled: false` (ਸਟੋਰੇਜ ਬਚਾਉਂਦਾ ਹੈ)।

### ਸਟੋਰੇਜ ਲਾਗਤ

| ਹਰੇਕ ਬੇਨਤੀ ਲਈ          | 1MB ਦੀ ਸੀਮਾ  | 10MB ਦੀ ਸੀਮਾ  |
| ---------------------- | ------------ | ------------- |
| ਔਸਤ ਸੰਕੁਚਿਤ ਆਉਟਪੁੱਟ    | ~5KB         | ~5KB          |
| ਸਟੋਰ ਕੀਤਾ ਕੱਚਾ ਆਉਟਪੁੱਟ | ~50-500KB    | ~500KB-5MB    |
| 1000 ਬੇਨਤੀਆਂ/ਦਿਨ ਨਾਲ   | 50-500MB/ਦਿਨ | 500MB-5GB/ਦਿਨ |

> **ਸਿਫ਼ਾਰਸ਼**: ਕੱਚੇ ਆਉਟਪੁੱਟ ਨੂੰ ਹਮੇਸ਼ਾ ਚਾਲੂ ਰੱਖਣ ਦੀ ਬਜਾਏ ਸਿਰਫ਼ **ਡੀਬੱਗਿੰਗ ਸੈਸ਼ਨਾਂ** ਜਾਂ **ਨਮੂਨਾ-ਆਧਾਰਿਤ ਆਡਿਟਿੰਗ** ਲਈ ਸਮਰੱਥ ਕਰੋ।

### ਮੂਲ ਆਉਟਪੁੱਟ ਨੂੰ ਮੁੜ ਪ੍ਰਾਪਤ ਕਰਨਾ

```ts
import { readRtkRawOutput } from "omniroute/compression/engines/rtk/rawOutput";

const raw = readRtkRawOutput(pointerId); // ਕੰਪ੍ਰੈਸ਼ਨ ਅੰਕੜਿਆਂ ਤੋਂ pointerId
if (raw) {
  console.log("ਮੂਲ ਆਉਟਪੁੱਟ:", raw);
}
```

ਕੰਪ੍ਰੈਸ਼ਨ ਤੋਂ ਬਾਅਦ `pointerId`, `CompressionStats.rtkRawOutputPointers[]` ਵਿੱਚ ਵਾਪਸ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।
ਫੰਕਸ਼ਨ ਸਿਗਨੇਚਰ ਲਈ `open-sse/services/compression/engines/rtk/rawOutput.ts:102` ਵੇਖੋ।

### ਤਸਦੀਕ ਗੇਟ

**RTK ਫਿਲਟਰ ਤਸਦੀਕ** (`open-sse/services/compression/engines/rtk/verify.ts`) ਸਾਰੇ ਫਿਲਟਰਾਂ ਨੂੰ ਉਨ੍ਹਾਂ ਦੇ `tests[]` ਦੇ ਮੁਕਾਬਲੇ ਪ੍ਰਮਾਣਿਤ ਕਰਦੀ ਹੈ ਅਤੇ ਇਹ ਯਕੀਨੀ ਬਣਾਉਂਦੀ ਹੈ ਕਿ ਤਿੰਨਾਂ ਤੀਬਰਤਾ ਪੱਧਰਾਂ ਉੱਤੇ ਵਿਵਹਾਰ ਸਹੀ ਹੈ।

ਤਸਦੀਕ ਚਲਾਉਣ ਲਈ **`runRtkFilterTests()` ਨੂੰ ਕਾਲ ਕਰੋ**:

```ts
import { runRtkFilterTests } from "open-sse/services/compression/engines/rtk/verify";

const result = runRtkFilterTests();
console.log(`ਪਾਸ ਹੋਏ: ${result.outcomes.filter((o) => o.passed).length}`);
console.log(`ਅਸਫਲ ਹੋਏ: ${result.outcomes.filter((o) => !o.passed).length}`);
if (!result.passed) {
  console.error("ਫਿਲਟਰ ਤਸਦੀਕ ਵਿੱਚ ਅਸਫਲ ਰਹੇ");
  result.outcomes
    .filter((o) => !o.passed)
    .forEach((o) => {
      console.error(
        `  - ${o.filterId} / ${o.testName}: ਉਮੀਦ ਸੀ "${o.expected}", ਮਿਲਿਆ "${o.actual}"`
      );
    });
}
```

**ਇਹ ਕੀ ਪ੍ਰਮਾਣਿਤ ਕਰਦੀ ਹੈ**:

1. ਹਰੇਕ ਫਿਲਟਰ ਲੋਡ ਹੁੰਦਾ ਹੈ ਅਤੇ ਸਕੀਮਾ ਤਸਦੀਕ ਪਾਸ ਕਰਦਾ ਹੈ
2. ਹਰੇਕ `tests[]` ਐਂਟਰੀ ਉਮੀਦ ਕੀਤਾ ਆਉਟਪੁੱਟ ਪੈਦਾ ਕਰਦੀ ਹੈ
3. `minimal` ਤੀਬਰਤਾ ਕੋਈ ਕਾਰਵਾਈ ਨਹੀਂ ਕਰਦੀ (ਮੂਲ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦੀ ਹੈ, ਸਿਰਫ਼ ਸੰਰਚਨਾਤਮਕ ਫਿਲਟਰ ਲਾਗੂ ਕਰਦੀ ਹੈ)
4. `aggressive` ਤੀਬਰਤਾ ਤਰੁੱਟੀਆਂ, ਟੈਸਟ ਅਸਫਲਤਾਵਾਂ ਅਤੇ ਸਟੈਕ ਟਰੇਸਾਂ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਦੀ ਹੈ
5. ਸੰਕੁਚਿਤ ਆਉਟਪੁੱਟ ਕਦੇ ਵੀ ਮੂਲ ਇਨਪੁੱਟ ਨਾਲੋਂ ਵੱਡਾ ਨਹੀਂ ਹੁੰਦਾ

- ਸਰੋਤ: `open-sse/services/compression/engines/rtk/` (63 ਫਾਈਲਾਂ, ~70KB)

- **ਫਿਲਟਰ ਤਬਦੀਲੀ ਨੂੰ ਮਰਜ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ** — ਹਮੇਸ਼ਾ ਯਕੀਨੀ ਬਣਾਓ ਕਿ ਟੈਸਟ ਪਾਸ ਹੁੰਦੇ ਹਨ
- **RTK ਇੰਜਣ ਨੂੰ ਅੱਪਗ੍ਰੇਡ ਕਰਨ ਤੋਂ ਬਾਅਦ** — ਸਕੀਮਾ ਬਦਲਿਆ ਹੋ ਸਕਦਾ ਹੈ
- **ਨਿਗਰਾਨੀ ਦੌਰਾਨ ਸਮੇਂ-ਸਮੇਂ ਤੇ** — ਟੈਸਟ ਫਿਕਸਚਰਾਂ ਵਿੱਚ ਡ੍ਰਿਫਟ ਤੋਂ ਸੁਰੱਖਿਆ ਦਿੰਦਾ ਹੈ
- **ਨਵਾਂ ਟੂਲ/ਕਮਾਂਡ ਪਰਿਵਾਰ ਜੋੜਦੇ ਸਮੇਂ** — ਸਾਬਤ ਕਰਦਾ ਹੈ ਕਿ ਨਵਾਂ ਫਿਲਟਰ ਕੰਮ ਕਰਦਾ ਹੈ
