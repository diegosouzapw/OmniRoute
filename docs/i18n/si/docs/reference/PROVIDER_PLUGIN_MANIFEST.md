`open-sse/config/providerPluginManifest.ts` මඟින් JSON-ආරක්ෂිත provider
plugin ගිවිසුම නිර්වචනය කරයි. `open-sse/config/providerPluginManifestRegistry.ts` මඟින් එම
ගිවිසුම Bifrost, CLIProxyAPI, හෝ අනාගත Go/Rust router එකක් වැනි sidecar සඳහා
වත්මන් provider registry එකට සම්බන්ධ කරයි. TypeScript registry එක සත්යයේ
ප්රධාන මූලාශ්රය ලෙස පවතින නමුත්, executor code, OAuth පෙරනිමි, headers, හෝ
process environment තත්ත්වය import නොකර sidecar වලට manifest එක භාවිත කළ හැක.

process එකෙන් පිටත ක්රියාත්මක වන sidecar සඳහා එම manifest එකම HTTP හරහා
`GET /api/v1/provider-plugin-manifest` හිදී ලබාගත හැක.

OmniRoute විසින් එම URL එක Bifrost සහ CLIProxyAPI වෙත
`X-OmniRoute-Provider-Manifest-Url` request header එක හරහා දැනුම් දෙයි. sidecar එකට
local request origin එක වෙනුවට පොදු හෝ container network URL එකක් අවශ්ය වන විට
`OMNIROUTE_PROVIDER_MANIFEST_URL` සකසන්න.

## Manifest එක නැවුම් කිරීම

HTTP endpoint එක `Cache-Control: public, max-age=60` සහ ශක්තිමත්
`ETag` එකක් ආපසු ලබා දෙයි. sidecar එකක් අවසන් වරට සත්යාපනය කළ manifest එක රඳවාගෙන,
එය නැවුම් කරන විට එහි ETag එක `If-None-Match` තුළ යැවිය යුතුය.
`304 Not Modified` ප්රතිචාරයක body එකක් නොමැත; sidecar එක එහි cache කළ manifest එක
තබා ගනී. සත්යාපනය කළ cache manifest එකක් නොමැති නම්, sidecar එක `304` එකක්
පිළිගැනීම වෙනුවට කොන්දේසි රහිත request එකක් නිකුත් කළ යුතුය.

## අරමුණ

ඉහළ ප්රමාදයක් ඇති නොකරන hot request path එක අවසානයේ sidecar එකක් මඟින්
පාලනය කළ හැකි වන පරිදි provider metadata plugin ගිවිසුමක් දෙසට ගෙන යන අතර,
OmniRoute විසින් TypeScript route එක policy gate සහ fallback ලෙස තබා ගනී.
manifest එක අතිරේකයකි: එය තනිවම request routing වෙනස් නොකරයි.

## ගිවිසුම

manifest එකේ අඩංගු වන්නේ:

- provider id සහ alias
- upstream format සහ executor නම
- auth type, auth header, සහ විකල්ප auth prefix
- ස්ථිතික endpoint metadata
- sidecar සඳහා සුදුසුකම සහ provider එකක් TS මතම රැඳී සිටිය යුතු විට ඒ සඳහා පැහැදිලි හේතු
- context length, vision/reasoning flags, සහ unsupported params වැනි JSON-ආරක්ෂිත model metadata
- `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch`, සහ `usage-supported` ඇතුළු capability tags

manifest එක හිතාමතාම බැහැර කරන්නේ:

- OAuth client secrets සහ පෙරනිමි secret values
- runtime environment resolution
- request headers සහ public credential helpers
- dynamic URL builders
- executor functions
- session pool අභ්යන්තර

## Capability Tags

`capabilities` යනු registry entry එකෙන් ව්යුත්පන්න කළ, අනුපිළිවෙළට සකස් කළ tags array එකකි. Integratorවරු
TypeScript මූලාශ්ර නැවත කියවීම වෙනුවට, "මෙම provider එකට කළ හැක්කේ කුමක්ද" යන්නට
machine-readable පිළිතුර ලෙස එය සැලකිය යුතුය.

| Tag                  | අර්ථය                                                                          |
| -------------------- | ------------------------------------------------------------------------------ |
| `apikey`             | API key එකක් පිළිගනී (`authType` යනු `apikey` හෝ `optional` වේ).               |
| `oauth`              | OAuth හෝ session flow එකක් භාවිත කරයි.                                         |
| `responses`          | OpenAI Responses-API base URL එකක් නිරාවරණය කරයි.                              |
| `passthrough-models` | ස්ථිතික catalog එකක් වෙනුවට models සෘජුවම upstream වෙතින් සපයයි.               |
| `custom-executor`    | පෙරනිමි නොවන executor එකක් ක්රියාත්මක කරන බැවින් එය TypeScript path එකේම පවතී. |
| `sidecar-candidate`  | `sidecar.eligible` පිළිබිඹු කරයි — sidecar import සඳහා සලකා බැලීමට ආරක්ෂිතය.   |
| `usage-fetch`        | සම්බන්ධ කළ usage හෝ quota fetcher එකක් (`getUsageForProvider`) ඇත.             |
| `usage-supported`    | usage API එක මෙම provider එක පිළිගනී (`isSupportedUsageConnection`).           |

`usage-fetch` යනු සොයාගැනීම සඳහා පමණි. provider එක සඳහා usage කියවන්නේ කෙසේදැයි OmniRoute
දන්නා බව එය වාර්තා කරයි; එය fetching සක්රිය නොකරයි, quota semantics වෙනස් නොකරයි, හෝ
provider එක සඳහා Dashboard quota widget එක සක්රිය බව අඟවන්නේ නැත — එම widget එක
`USAGE_SUPPORTED_PROVIDERS` මඟින් වෙනම gate කර ඇත. සත්යයේ මූලාශ්රය වන්නේ
`open-sse/services/usage/fetcherProviders.ts` හි `USAGE_FETCHER_PROVIDERS` ය.

එම ලැයිස්තුව usage dispatcher එක පිළිගන්නා strings මඟින් key කර ඇති බැවින්, එය canonical ids
සහ aliases මිශ්ර කරන අතර tagged providers සංඛ්යාවට වඩා මඳක් දිගුය: manifest registry එකේ
chat providers නොවන entries සඳහා (උදාහරණයක් ලෙස `firecrawl` search provider එක සහ
`amazon-q` ACP provider එක) tag කිරීමට manifest entry එකක් නොමැත.

`usage-supported` මඟින් server සහ Dashboard usage routes විසින් provider එක සඳහා connection එකක්
පිළිගන්නේද යන්නට පිළිතුරු සපයයි. එය `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
සහ `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`) පිළිබිඹු කරන අතර, දෙකම
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`) මඟින් gate කර ඇත.
`usage-fetch` මෙන් නොව, එය provider id එක මත පමණක් නිකුත් කෙරේ — runtime guard එක alias
resolution නොමැතිව `USAGE_SUPPORTED_PROVIDERS.includes(providerId)` ක්රියාත්මක කරන බැවින්,

## Sidecar භාවිතය

Sidecar විසින් `sidecar.eligible` කොන්දේසි විරහිත routing තීරණයක් ලෙස නොව, ආරක්ෂාකාරී අපේක්ෂක සංඥාවක් ලෙස සැලකිය යුතුය. පළමු import ඉලක්කය විය යුත්තේ පෙරනිමි executor භාවිත කරන API-key සහ static-endpoint providers ය. අභිරුචි web executors, OAuth/session flows, dynamic URL builders, හෝ pool config සහිත providers සඳහා, sidecar එකක් සමාන හැසිරීමක් ක්රියාත්මක කර telemetry මඟින් සමානතාව තහවුරු කරන තෙක් TypeScript fallback මාර්ගය දිගටම භාවිත කළ යුතුය.

යෝජිත migration අදියර:

1. TS registry වෙතින් provider plugin manifest එක ජනනය කර වලංගු කරන්න.
2. API-key/static providers සඳහා manifest එක import කිරීමට Bifrost හෝ CLIProxyAPI සූදානම් කරන්න.
3. TS fallback සක්රියව තබා ගනිමින්, `OMNIROUTE_RELAY_BACKEND` පසුපස ඇති sidecar හරහා සුදුසුකම් ලත් providers route කරන්න.
4. සාර්ථකත්ව අනුපාතය, p99 latency, streaming හැසිරීම සහ සහාය නොදක්වන parameters හැසිරවීම TS මාර්ගයට ගැළපෙන විට පමණක් providers ප්රවර්ධනය කරන්න.
5. වරකට එක් provider family එක බැගින් custom executors සඳහා sidecar-native plugins එක් කරන්න.

## Providers සෘජුවම Next තුළ Embed නොකරන්නේ ඇයි

Next frontend එක provider execution හිමිකර නොගත යුතුය. එය API සීමාව ඇමතිය යුතුය. එවිට backend එකට TypeScript executor, Bifrost, CLIProxyAPI, හෝ අනාගත native sidecar එකක් භාවිත කළ යුතුද යන්න තීරණය කළ හැක. මෙය ඕනෑම sidecar handoff එකකට පෙර request signing, allowlist checks, DB policy සහ fallback හැසිරීම මධ්යගතව තබයි.
