Relays (Vercel, Deno, Cloudflare) මඟින් serverless backend එකකදී upstream සම්බන්ධතාව අවසන් කරනු ලබන අතර, එමඟින් provider API key එක server-side තබා ගනිමින් OmniRoute හට ස්ථාවර කලාපයකින් පිටතට සම්බන්ධ වීමට හැකි වේ. මෙය production පරිසරයේදී operators මුහුණ දෙන අසාර්ථක අවස්ථා දෙක සහ ඒ සෑම එකක් සඳහාම OmniRoute සපයන ප්රතිසාධන ක්රම විස්තර කරයි.

## relay සත්යාපන තොරතුරු ගබඩා කරන ආකාරය

ඔබ **Settings → Proxy Pool → Deploy Relay** වෙතින් relay එකක් deploy කරන විට,
deploy ක්රියාවලිය relay එකේ සත්යාපන token එක proxy හි `notes` JSON field එක තුළ ගබඩා කරයි:

- `STORAGE_ENCRYPTION_KEY` සකසා තිබේ නම්, token එක `relayAuthEnc` ලෙස
  (ගබඩා කර තිබියදී AES මඟින් සංකේතනය කර) ලියනු ලැබේ.
- එසේ නොමැති නම්, එය සරල පෙළ ලෙස `relayAuth` තුළ ලියනු ලැබේ.

Request එකක් ලැබෙන විට `extractRelayAuth(notes)` පවතින ආකාරය ආපසු ලබා දෙන බැවින්,
restart කිරීම් අතරතුරදීත් relay එක ක්රියාත්මකව පවතී.

## අසාර්ථක අවස්ථාව 1 — key rotation එකකින් පසු විකේතනය කළ නොහැකි token එක

**ලක්ෂණය:** කලින් ක්රියා කළ relays, environment එකක් හෝ secret-manager එකක් තුළ
`STORAGE_ENCRYPTION_KEY` rotate කිරීමෙන් පසු දැන් upstream `401`/සත්යාපන
දෝෂ ලබා දෙයි. ගබඩා කර ඇති `relayAuthEnc` blob එක තවදුරටත් විකේතනය කළ නොහැකි බැවින්,
`extractRelayAuth` හිස් string එක ආපසු ලබා දෙන අතර relay එක කිසිදු සත්යාපන තොරතුරක්
යවන්නේ නැත.

**ප්රතිසාධනය — පවතින ස්ථානයේම අලුත්වැඩියා කිරීම (නැවත deploy කිරීමක් නැත):**

1. **Settings → Proxy Pool** විවෘත කරන්න.
2. සත්යාපන තොරතුරු නොමැති relay පේළිවල කහ පැහැති `auth missing` badge එකක් සහ
   **Repair** button එකක් පෙන්වයි.
3. **Repair** ක්ලික් කරන්න. OmniRoute විසින්
   `POST /api/settings/proxies/[id]/repair-relay` අමතනු ලබන අතර, එය:
   - **වත්මන්** key එක භාවිතයෙන් `relayAuthEnc` විකේතනය කරයි,
   - සරල පෙළ `relayAuth` නැවත `notes` තුළට ලියයි,
   - `{ repaired: true, mode: "recovered" }` ආපසු ලබා දෙයි.

කිසිදු deploy අක්තපත්රයක් නැවත ඇතුළත් නොකර relay එක සේවා සැපයීම යළි ආරම්භ කරයි.

මෙය ක්රියා කරන්නේ වත්මන් `STORAGE_ENCRYPTION_KEY` එකට තවමත් blob එක
විකේතනය කළ හැකි නම් පමණි. ඔබ migration එකක් **නොමැතිව** key එක rotate කළේ නම්,
blob එක ප්රතිසාධනය කළ නොහැක.

## අසාර්ථක අවස්ථාව 2 — ප්රතිසාධනය කළ නොහැකි token එක (key එක ඉවත් වන ලෙස rotate කර ඇත)

**ලක්ෂණය:** ඔබ **Repair** ක්ලික් කළ අතර
`{ repaired: false, mode: "redeploy", status: 409 }` ලැබුණි.

**ප්රතිසාධනය — නැවත deploy කිරීම:**

ගබඩා කර ඇති token එක වත්මන් key එක භාවිතයෙන් ප්රතිසාධනය කළ නොහැක. ඔබ මුලින් භාවිත කළ
එම modal එකෙන්ම relay එක නැවත deploy කරන්න (**Deploy Relay** menu → Vercel / Deno
/ Cloudflare). deploy ක්රියාවලිය නව token එකක් (වත්මන් key එකෙන් සංකේතනය කර)
ලියන අතර පේළියේ `auth missing` badge එක ඉවත් වේ.

UI එක තුළ, token එක ප්රතිසාධනය කළ නොහැකි විට **Repair** button එකම redeploy modal එක
විවෘත කරන බැවින්, ඔබට එය අතින් සෙවීමට කිසිවිටෙක අවශ්ය නොවේ.

## අසාර්ථක අවස්ථාව 3 — relay එකට ළඟා විය හැකි නමුත් එය සෞඛ්ය සම්පන්න නොවේ

**ලක්ෂණය:** proxy පරීක්ෂණය (`speed` button එක) relay එක ක්රියාත්මක බව පෙන්වුවත් requests
තවමත් වරින් වර අසාර්ථක වේ.

OmniRoute හි ස්වයංක්රීය පරීක්ෂණ probe එකෙන් ආපසු ලබා දෙන relay දැනුවත් කිරීමේ headers
පරීක්ෂා කරන්න (**Settings → Proxy Pool** සහ `relayTested` / `relayAlive` counters බලන්න):

- `x-relay-url` — ප්රතිචාර දැක්වූ relay backend එක.
- `x-relay-mode` — එම request එක සඳහා `ts` | `bifrost` | `auto`.
- `x-relay-attempts` — සාර්ථක වීමට පෙර උත්සාහ කළ relay hops ගණන.
- `x-relay-fallback` — request එක කැමති backend එකෙන් TypeScript relay එක වෙත
  fallback වූ විට `true`.

අඩු `relayAlive` අගයක් සමඟ ඉහළ `x-relay-fallback` අනුපාතයක් තිබීමෙන් sidecar
backend එක සෞඛ්ය සම්පන්න නොවන බව අදහස් වන අතර, ඔබ එය නිවැරදි කිරීම හෝ relay backend
උපායමාර්ගය `ts` වෙත මාරු කිරීම කළ යුතුය (`RELAY_BACKEND_STRATEGY.md` බලන්න).
