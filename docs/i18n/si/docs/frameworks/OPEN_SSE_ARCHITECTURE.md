## වෙනම Workspace Package එකක් ඇයි?

හේතු කිහිපයක් නිසා `open-sse/` යනු OmniRoute monorepo එක තුළ ඇති **ස්වාධීන workspace** එකකි:

1. **නැවත භාවිත කිරීමේ හැකියාව** — `open-sse`, npm හි `@omniroute/open-sse` ලෙස ප්රකාශයට පත් කර ඇති බැවින් වෙනත් ව්යාපෘතිවලට එය ස්වාධීනව භාවිත කළ හැක
2. **පැහැදිලි සීමා** — streaming එන්ජිම OmniRoute-විශේෂිත UI/DB layer එකෙන් වෙන් කර ඇත
3. **කාර්යසාධනය** — එන්ජිමට Next.js dependencies නොමැති බැවින් CLI/serverless සන්දර්භවල වේගවත් cold starts සක්රීය වේ
4. **අනුවාදකරණය** — `open-sse` හට තමන්ගේම කාලසටහනකට අනුව releases නිකුත් කළ හැක

```json
// package.json
"workspaces": ["open-sse"]
```

## ඉල්ලීම් Pipeline එක

සෑම LLM ඉල්ලීමක්ම **අදියර 5ක pipeline එකක්** හරහා ගලා යයි:

```
                              ┌──────────────┐
   HTTP ඉල්ලීම                │  1. ROUTE    │   combo resolution, model තේරීම
   (Next.js route)             └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. TRANSLATE│   ආකෘති පරිවර්තනය (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. EXECUTE  │   provider executor, HTTP, retry, breaker
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAM   │   SSE පරිවර්තනය, backpressure
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. RECORD   │   භාවිත ලුහුබැඳීම, call log, දෝෂ වර්ගීකරණය
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP ප්රතිචාරය (SSE හෝ JSON)
```

### අදියර 1: Route (services/combo.ts)

**ප්රවේශ ලක්ෂ්යය**: `services/combo.ts` තුළ ඇති `handleComboChat()`

ඉල්ලීම නිශ්චිත `(provider, model, account, credentials)` tuple එකකට විසඳයි:

- ID එක අනුව combo එක සොයන්න (හෝ `auto/*` models සඳහා virtual combo එකක් සාදන්න)
- Routing strategy එක යොදන්න (priority, weighted, round-robin, ආදිය)
- සෞඛ්ය සම්පන්න නොවන providers ඉවත් කරන්න (circuit breaker)
- ඊළඟට භාවිත කළ හැකි target එක තෝරන්න

`auto/*` models සඳහා මෙම අදියර තවදුරටත්:

- **සාධක 16ක scoring** algorithm එක (`services/autoCombo/`) ක්රියාත්මක කරයි
- සෞඛ්යය, පිරිවැය, latency ආදිය මත පදනම්ව `provider+model` යුගලයක් තෝරයි

### අදියර 2: Translate (translator/)

මූලාශ්ර ආකෘතිය (උදා., OpenAI) ඉලක්ක ආකෘතියෙන් (උදා., Claude) වෙනස් නම්, ඉල්ලීම **පරිවර්තනය** කෙරේ:

- System prompt → system message
- Tool definitions → provider-විශේෂිත tool ආකෘතිය
- Reasoning/thinking parameters → provider-විශේෂිත සමාන අගයන්
- Message role normalization (`developer` → OpenAI නොවන ඒවා සඳහා `system`)

`translator/index.ts` මඟින් පහත දෑ නිරාවරණය කරයි:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### අදියර 3: Execute (executors/)

**ප්රවේශ ලක්ෂ්යය**: `getExecutor(providerId).execute(request, options)`

සියලුම providers, `getExecutor()` factory fallback එක හරහා `DefaultExecutor` (`executors/default.ts`) භාවිත කරයි. Executor එක:

- Upstream URL එක සාදයි (`buildUrl()`)
- Provider-විශේෂිත headers එක් කරයි (`buildHeaders()`)
- ඉල්ලීම් body එක පරිවර්තනය කරයි (`transformRequest()`)
- Retry සහ exponential backoff සමඟ HTTP ඉල්ලීම යවයි
- අවශ්ය නම් auth refresh කිරීම හසුරුවයි (OAuth providers)

සියලුම executors, පහත දෑ සපයන `BaseExecutor` (`executors/base.ts`, LOC 1170) විස්තාරණය කරයි:

- පොදු retry logic
- Proxy ඒකාබද්ධ කිරීම
- Circuit breaker ඒකාබද්ධ කිරීම
- භාවිතය වාර්තා කිරීමේ hooks

### අදියර 4: Stream (utils/stream.ts)

Streaming ප්රතිචාර සඳහා executor එක **ReadableStream** එකක් ලබා දෙයි. Handler එක:

- SSE transform එකක් හරහා යොමු කරයි (`createSSETransformStreamWithLogger`)
- අක්රිය සම්බන්ධතා හඳුනාගැනීම සඳහා heartbeat pings යොදයි
- Client එක විසන්ධි වීම නිසි ලෙස හසුරුවයි (`pipeWithDisconnect`)
- Streaming නොවන clients සඳහා SSE → JSON ලෙස පරිවර්තනය කරයි

Streaming නොවන ප්රතිචාර සඳහා executor එක parse කළ JSON object එකක් ලබා දෙන අතර, එය වෙනස් කිරීමකින් තොරව ඉදිරියට යවනු ලැබේ.

### අදියර 5: Record (services/usage.ts)

ප්රතිචාරයෙන් පසු (සාර්ථක හෝ අසාර්ථක වුවත්), භාවිතය සටහන් කරනු ලැබේ:

ඇමතුම් ලොග් කෞතුක (සක්රීය කර ඇත්නම්) `${DATA_DIR}/call_logs/` වෙත ලියනු ලැබේ.

### chatCore.ts (පේළි 5977)

**ප්රධාන ඉල්ලීම් හසුරුවන්නා**. එහි ප්රමාණය තිබියදීත්, එය පැහැදිලි ව්යුහයක් ඇත:

```ts
// chatCore.ts හි ව්යාජ-ව්යුහය
export async function handleChat(request: NextRequest) {
  // 1. සත්යාපනය + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Body වලංගුභාවය
  const body = await parseRequestBody(request);

  // 3. ආකෘති හඳුනාගැනීම + පරිවර්තනය
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo මාර්ගගත කිරීම
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // ඊළඟ ඉලක්කයට ඉදිරියට යන්න
    }
  }

  // 5. හදිසි fallback
  return await emergencyFallback(body);
}
```

එකම විශාල ශ්රිතයක් වුවද, එය පියවර-5 නළ මාර්ගයට අනුරූප වන **අදහස් දක්වා ඇති කොටස්** ලෙස සංවිධානය කර ඇත.

### base.ts (LOC 1170)

සෑම executor පන්තියක්ම දිගු කරන (සෘජුවම හෝ `DefaultExecutor` සහ වෙනත් උපපන්ති හරහා) **වියුක්ත executor**. එය අඩංගු වේ:

- `buildHeaders()` — පෙරනිමි ශීර්ෂක (auth, content-type)

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // සියලුම OpenAI/Anthropic-අනුකූල සැපයුම්කරුවන් හසුරුවයි
  // සැපයුම්කරුවන් වින්යාසයන් (URL, auth, headers) ලියාපදිංචි කරන නමුත් executor තර්කය බෙදාගනී
}
```

සැපයුම්කරු-විශේෂිත හැසිරීම (auth ශීර්ෂක, base URL, අනුවාද ශීර්ෂක) වෙනම executor පන්ති මගින් නොව සැපයුම්කරු ලේඛනය හරහා වින්යාසගත කෙරේ.

## ක්රියාකාරකයන් — Executors (මොඩියුල 150ක්)

බොහෝවිට provider එකකට එක් ගොනුවක් බැගිනි. executor පන්ති සියල්ලම `BaseExecutor` වලින් දිගු වන අතර වෙනස් වන දේ පමණක් override කරයි; අනෙකුත් මොඩියුල provider-එකකට වෙනම උපකාරක වේ (tool schemas, fetch/TTS adapters, quirk handlers).

### පොදු රටාවන්

Providers `getExecutor(providerId)` හරහා resolve වන අතර, එය වින්යාසගත කළ executor එක ලබා දෙයි. OpenAI/Anthropic-ගැළපෙන providers `DefaultExecutor` (`executors/default.ts`) භාවිතා කරයි. Provider-විශේෂිත හැසිරීම (base URL, auth headers, API version) `open-sse/config/providers/` හි වින්යාසගත කරන අතර, request body පරිවර්තන `open-sse/translator/` හි හසුරුවයි.

**අභිරුචි URL** එක provider වින්යාසය මඟින් සකසයි:

```ts
// open-sse/config/providers/ තුළ provider වින්යාසය
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**අභිරුචි සත්යාපනය** provider registry එකේ සත්යාපන වින්යාසය (API key, OAuth, header profiles) මඟින් හසුරුවයි.

**අභිරුචි request body** පරිවර්තන (උදා., Anthropic විසින් `system` එක `messages` වෙතින් වෙන් කිරීම) `open-sse/translator/` හි provider-එකකට වෙනම ලියාපදිංචි කර ඇත.

````

### Executor ෆැක්ටරිය

`executors/index.ts` විසින් `getExecutor(providerId)` export කරයි:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Resolve කිරීම `ExecutorRegistry` (`executors/registry.ts`) හරහා සිදු වේ: සෑම විශේෂිත executor එකක්ම `executors/index.ts` හි built-in වගුවේ declared කර ඇති අතර, module load වන විට `registerExecutor(alias, instance)` මඟින් ලියාපදිංචි වේ; `getExecutor()` registry එක පරීක්ෂා කර, විශේෂිත entry එකක් නොමැති ඕනෑම provider එකක් සඳහා memoized `DefaultExecutor` එකකට fallback වේ. සම්පූර්ණ alias → executor mapping එක golden test `tests/unit/executor-map-golden.test.ts` මඟින් ලක්ෂණාංකගත කර ඇත.

**ආකෘති 3ක්** අතර පරිවර්තනය කරන්න: OpenAI, Anthropic, Gemini, සහ නව Responses API එක.

import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {

- `OpenAI → Responses API`: `input` අරාව, `previous_response_id` තත්ත්වය

- `json_schema` → Gemini හි `responseMimeType` + `responseSchema`
- `tools` → සැපයුම්කරුට විශේෂිත මෙවලම් ආකෘතිය

## පරිණාමක

`open-sse/transformer/` මඟින් **Chat Completions** සහ **Responses API** ආකෘති අතර පරිවර්තනය කරයි.

### වෙනම පරිණාමකයක් අවශ්ය වන්නේ ඇයි?

Responses API යනු **තත්ත්වය සහිත සංවාද** (`previous_response_id`) ඇතුළත් OpenAI හි නව ආකෘතියයි. සේවාලාභියෙකු Responses ඉල්ලීමක් යවන විට, OmniRoute:

1. අභ්යන්තරව Responses → Chat Completions බවට පරිවර්තනය කරයි
2. සැපයුම්කරු වෙත යවයි (Chat Completions සඳහා සහාය දක්වන ඕනෑම සැපයුම්කරුවෙකු)
3. ප්රතිචාරය නැවත Responses ආකෘතියට පරිවර්තනය කරයි
4. පරිවර්තනය කළ ප්රතිචාරය සේවාලාභියා වෙත ප්රවාහ කරයි

පරිණාමකය (`transformer/responsesTransformer.ts`) පහත දෑ සපයයි:

```ts
createResponsesApiTransformStream(): TransformStream
```

මෙය පහත දෑ හසුරුවයි:

- `response.output_item.added` සිදුවීම්
- `response.output_text.delta` සිදුවීම්

මොඩියුල පූරණයේදී සිදු වන Zod වලංගුකරණය, සියලු සපයන්නා වින්යාසයන් වලංගු බව සහතික කරයි.
