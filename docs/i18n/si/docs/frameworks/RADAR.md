## පොදු නිවේදන කියවනය

සාමාන්ය නිවේදන කියවනය Radar විශේෂාංග ධජයෙන් වෙන්ව පවතී. උපකරණ පුවරුවේ Home සහ
Changelog දර්ශකය සරල `GET` ඉල්ලීමක් හරහා ගබඩාවේ පොදු `news.json`,
`NEWS_JSON_URL` වෙතින් ලබා ගනී (`src/shared/utils/releaseNotes.ts`). ඒවා කිසිදු Radar සැකසුමක්, prompt එකක්, provider
වින්යාසයක්, භාවිත වාර්තාවක් හෝ දේශීයව ඉවත දැමීමේ තත්ත්වයක් යවන්නේ නැත.

`news.json`, `parseNewsPayload()` මඟින් ක්රියාත්මක කළ සංවෘත v2 schema එක භාවිත කරයි:

- `schemaVersion: 2` සහ සීමා කළ `items[]` එකතුවක්;
- ස්ථාවර, අනන්ය නිවේදන `id` අගයන්;
- පැහැදිලි `active` සහ ISO `publishedAt` ක්ෂේත්ර;
- විකල්ප ස්ථානීකරණය කළ පිටපත් සමඟ අනිවාර්ය ඉංග්රීසි පිටපතක්;
- විකල්ප, අක්තපත්ර අවශ්ය නොවන HTTPS සබැඳි සහ අවසර ලැයිස්තුගත icon එකක්;
- නවතම සක්රිය අයිතමයට ප්රමුඛත්වය දෙන තේරීම, locale එක නොමැති විට ඉංග්රීසිය භාවිත කිරීම, සහ එක් එක් ID සඳහා දේශීයව ඉවත දැමීම.

පැරණි forks වලට Changelog දසුන බිඳ වැටීමකින් තොරව සංක්රමණය වීමට හැකි වන පරිදි, parser එක කලින් භාවිත කළ ඒකවචන `{ active, title, message, ... }` ආකෘතිය තාවකාලිකව පිළිගනී. වලංගු නොවන feeds අක්රියව පවතී. `radar_settings.opt_in` තුළ ගබඩා කරන දෙවන, ස්වාධීන opt-in එකක් අවශ්ය වේ (`src/lib/db/radar.ts`,
migration `136_radar_cache_settings.sql`). කිසියම් ජාල ඇමතුමක් කිරීමට පෙර `syncRadar()` ධජය _සහ_
opt-in එක පරීක්ෂා කරයි:

```
ධජය අක්රියයි  → { status: "disabled" }   — ජාල ඇමතුමක් නැත
Opt-in අසත්යයි  → { status: "opt_out" }    — ජාල ඇමතුමක් නැත
```

දෙකම සක්රිය වූ විට, sync මාර්ගය මෙසේය:

1. `x-omniroute-radar-schema: 2` සහ විකල්ප
   `Authorization: Bearer <supporter key>` header එකක් සමඟ `GET <feed base URL>/v1/catalog/latest`
   (පහත බලන්න). Schema header එක නොමැති විට servers විසින් වෙනම අත්සන් කරන ලද
   v1 සංක්රාන්ති artifact එක පෙරනිමියෙන් ලබා දෙන නිසා, ස්ථාපනය කර ඇති පැරණි clients වෙතද
   යාවත්කාලීන දිගටම ලැබේ.
2. මෙය download කිරීමට පමණක් සීමා වූ application flow එකක් වුවද, එය තවමත් HTTPS ඉල්ලීමකි. Hosted
   infrastructure එකට මූලාශ්ර IP වැනි සාමාන්ය සම්බන්ධතා metadata ලැබේ. Supporter
   key එකක් වින්යාස කර ඇති විට, service එකට entitlement එක නිරාකරණය කිරීමට හැකි වන පරිදි sync කිරීමේදී එම key එකද
   Bearer header එක තුළ යවයි. ඉහත evidence boundary එකෙහි හඳුනාගත් නිශ්චිත private-server revision එකේදී,
   feed-request ගිණුම්කරණය අතින් සිදු කරන අනිසි භාවිත සමාලෝචනය සඳහා key hashes, සමස්ත භාවිතය සහ IP එකේ දිනපතා මාරු වන කෙටි කළ HMAC එකක්
   භාවිත කරයි; එම වගු key එක හෝ IP එක අමු ආකාරයෙන් සුරකින්නේ නැත.
   Infrastructure access logs සහ encrypted delivery outbox එක වෙනම මෙහෙයුම්
   සීමාවන් වේ.

   uptime, latency, හෝ දේශීය provider වින්යාසය Radar service එක වෙත යවන්නේ නැත.

   [ආරක්ෂක ආකෘතිය](#security-model) බලන්න). Radar සතුව server-side ජාල මාර්ග හරියටම හතරක් ඇත:

  **කිසි විටෙක ආපසු ප්රතිරාවය නොකරයි** — ප්රතිචාරය ආවරණය කළ ආකෘතියක් (`omr_****abcd`) ලබා දෙයි.

### අවම අනුවාද සීමාව

බාගත කළ ෆීඩ් එකක `version` දැනට කෑෂ් කර ඇති අනුවාදයට වඩා අනිවාර්යයෙන්ම අලුත් නොවේ නම්,
`syncRadar()` එය ප්රතික්ෂේප කරයි (`compareVersions()`, තිත් සහිත `YYYY.MM.DD.n` සැසඳීම) —
`{ status: "stale" }`. මෙය අඩපණ කළ හෝ වැරදි ලෙස වින්යාස කළ ෆීඩ් අන්තලක්ෂ්යයකට
ක්ලයන්ටයක් පැරණි, වෙනස් ලෙස අත්සන් කළ පේලෝඩයකට ආපසු හැරවීම වළක්වයි.

### දින දෙකක් සහ ඒ දෙකම තබාගන්නේ ඇයි

කෑෂ් කළ ෆීඩ් එකක එකිනෙකට වෙනස් දින දෙකක් අඩංගු වන අතර, ඒවා පටලවා ගැනීමට ඇති ඉඩකඩම
ඒ දෙකම තබාගැනීමට හේතුවයි:

| ක්ෂේත්රය      | ලැබෙන්නේ                    | පිළිතුරු දෙන්නේ                        |
| ------------- | --------------------------- | -------------------------------------- |
| `generatedAt` | අත්සන් කළ ෆීඩ් අන්තර්ගතයෙන් | **දත්ත** කෙතරම් පැරණිද යන්න            |
| `fetchedAt`   | මෙම ස්ථාපනයේ ඔරලෝසුවෙන්     | මෙම ස්ථාපනය එය **බාගත කළේ** කවදාද යන්න |

මිනිත්තු කිහිපයකට පෙර ලබාගත් ෆීඩ් එකක සති ගණනක් පැරණි සංඛ්යා අඩංගු විය හැකි බැවින්,
එය පිහිටා ඇති මූලික දත්තවලට වඩා අතිස්තරය අලුත්දැයි ක්රියාකරුට `fetchedAt` පමණක් මඟින්
දැනගත නොහැක. දෙකම `radar_feed_cache` තුළ ස්ථිරව ගබඩා කර, `getRadarCatalog().meta`
මඟින් ආපසු ලබා දෙන අතර, `GET /api/radar/status` මඟින් වෙන් වෙන්ව වාර්තා කෙරේ.
`generated_at` තීරුව පැවතීමට පෙර (migration 163) කෑෂ් කළ පේළියක් `null` ලෙස නැවත
කියවෙයි — ලබාගත් වේලාව ණයට ගැනීම වෙනුවට නොදන්නා අගයක් නොදන්නා ලෙසම පවතී.
migration 142 සිට `radar_referrals_cache` තමන්ගේම `generated_at` අගය තබාගෙන ඇත.

ඉහත අවම අනුවාද සීමාව සැසඳෙන්නේ `version` සමඟ මිස දින දෙකෙන් එකක් සමඟ නොවේ.

හිඩැස් දෙකක් ඉතිරිව ඇති අතර, ඒ දෙකම හිතාමතා තබා ඇත: උපකරණ පුවරුව තවමත් පෙන්වන්නේ
`අවසන් වරට ලබාගත්තේ` පමණක් බැවින්, එහි ගොඩනැගීමේ දිනය කියවීමට නව ලේබලයක්
(සහ එහි locale ඇතුළත් කිරීම් 41) අවශ්ය වේ; තවද offers සහ intel කෑෂ්වල ෆීඩ්
යෝජනා ක්රම තුළ ගොඩනැගීමේ දිනයක් තිබුණද, ඒවා කිසිදු ගොඩනැගීමේ දිනයක් තබා නොගනී —
එබැවින් `GET /api/radar/status` එම දෙක සඳහා `"unknown"` ලෙස කියවිය හැකි `null`
අගයක් වාර්තා කිරීම වෙනුවට එම ක්ෂේත්රය මඟහරියි.

### යෝජනා ක්රමය සත්යාපනය

බාගත කළ බයිට්, අත්සන සත්යාපනයෙන් **පසුව**, `RadarFeedSchema`
(`src/lib/radar/feedSchema.ts`, Zod යෝජනා ක්රමයක්) අනුව විග්රහ කර සත්යාපනය කෙරේ.
යෝජනා ක්රම නොගැළපීමක් `{ status: "invalid_schema" }` ආපසු ලබා දෙන අතර කෑෂය
නොවෙනස්ව තබයි. සෑම කියවීමකදීම (`getRadarCatalog()`) කෑෂ් කළ පේලෝඩය ආරක්ෂිතව
නැවත සත්යාපනය කෙරේ — දූෂිත හෝ අතින් සංස්කරණය කළ කෑෂ් පේළියක් සේවය කිරීම වෙනුවට
මූලික දත්ත වෙත ආපසු හැරෙයි.

### ප්රතිචාර ප්රමාණ සීමාව (10 MB)

`syncRadar()` ෆීඩ් ප්රතිචාර අන්තර්ගතයට **10 MB දැඩි සීමාවක්** බලාත්මක කරයි —
අත්සන් කළ ෆීඩ් එක KB-පරිමාණ JSON ලේඛනයක් වන බැවින්, මෙයට වඩා විශාල ඕනෑම දෙයක්
නීත්යානුකූල නාමාවලියක් නොව, වැරදි ලෙස වින්යාස කළ හෝ ද්වේෂසහගත
`RADAR_FEED_URL` එකක් (හෝ අනවශ්ය දත්ත සපයන ඉහළ ප්රවාහ සේවාවක්) පෙන්නුම් කරයි.
බලාත්මක කිරීම ස්ථර දෙකකින් සිදු වේ:

1. ශීර්ෂකය දැනටමත් සීමාව ඉක්මවන අගයක් ප්රකාශ කරන්නේ නම්, `Content-Length`
   පූර්ව පරීක්ෂාවක් මඟින් අන්තර්ගතය කියවීම සම්පූර්ණයෙන්ම මඟහරියි.
2. අන්තර්ගතය කියවන අතරතුර සිදු කරන සමුච්චිත-එකතුවේ පරීක්ෂාවක්, `Content-Length`
   නොමැති විට හෝ සැබෑ ප්රමාණය අඩුවෙන් දැක්වූ විට පවා සීමාව බලාත්මක කරයි —
   ශීර්ෂකය කිසිවිටෙක තනිව විශ්වාස නොකෙරේ. රැස් කළ කොටස් ඒකාබද්ධ කිරීමෙන් පසුව
   සිදු කරන Ed25519 අත්සන පරීක්ෂාවට අවශ්ය නිශ්චිත බයිට් සුරැකේ.

සීමාව ඉක්මවීම `{ status: "too_large" }` ආපසු ලබා දී කෑෂය නොවෙනස්ව තබයි.
මෙය අනෙකුත් සෑම සමමුහුර්තකරණ අසාර්ථකත්වයකම (`invalid_signature`,
`invalid_schema`, `stale`) භාවිත වන එකම විනාශකාරී නොවන රටාව අනුගමනය කරයි.

feed schema එකෙහි `tier: "community" | "live"` ක්ෂේත්රයක් අඩංගු වන අතර, එය ඉල්ලීම මත පදනම්ව (supporter key එක තිබීම සහ එහි වලංගුභාවය)
feed සේවාව විසින් **server-side** තීරණය කරනු ලැබේ
— client එක කිසිවිටෙකත් තමන්ගේම ස්තරය තීරණය නොකරයි.

- **`community`** — නවතම දත්තවලට වඩා ආසන්න වශයෙන් දින 30ක් ප්රමාද වූ නොමිලේ catalog එක. සත්යාපනය නොකළ හෝ වලංගු නොවන key එකක් සහිත ඉල්ලීමකට ලැබෙන්නේ මෙයයි.
- **`live`** — වලංගු supporter key එකක් සහිත ඉල්ලීම් සඳහා සපයනු ලබන නවතම catalog එක.

**වලංගු නොවන හෝ කල් ඉකුත් වූ supporter key එකක් `community` වෙත පහත වැටෙයි — එය කිසිවිටෙකත්
දෝෂයක් නොවේ.** sync මාර්ගය වෙන්කර හඳුනාගන්නේ signature/schema/version අසාර්ථකවීම් (සියල්ල
යථා තත්ත්වයට පත් කළ හැකි සහ cached state එකට මාරාන්තික නොවන ඒවා) සහ සාර්ථක `{ status:
"updated", version, tier }` ප්රතිඵලයක් පමණි. client එකකට හැසිරවීමට අවශ්ය ස්තර-විශේෂිත දෝෂ මාර්ගයක් නොමැත.

### සපයනු ලබන ස්තරය පැමිණෙන්නේ response header එකකින් මිස signed body එකෙන් නොවේ

signed feed **body** එකේ `tier` ක්ෂේත්රය සැමවිටම `"live"` වේ — feed සේවාව එක් version එකකට
**signed artifacts දෙකක්** නිකුත් කරයි: live හි වත්මන් campaigns අඩංගු වන අතර community
ඒවා අත්හරියි. සෑම artifact එකක්ම එයටම අදාළ නිරවද්ය bytes මත sign කර ඇත. body එක තවමත්
හිමිකම් තීරණය ලෙස ක්රියා නොකරයි; ඉල්ලීමක් සඳහා සැබවින්ම තෝරාගත් ස්තරය
**`x-omniroute-feed-tier` response header** එක තුළ ගෙන යනු ලබන අතර, එය ඉල්ලීමේ
`Authorization` key එකෙන් server-side තීරණය කෙරේ.

`syncRadar()` (`src/lib/radar/sync.ts::parseServedTierHeader()`) යනු
client එකක් විශ්වාස කළ යුතු ස්තරය තීරණය කරන එකම ස්ථානයයි:

1. `RadarTierSchema` (Zod) භාවිතයෙන් `x-omniroute-feed-tier` parse කරන්න — header එකක් නොමැති වීම හෝ
   හරියටම `"community"` හෝ `"live"` නොවන අගයක් **නොපවතින** ලෙස
   සලකනු ලැබේ (පවතින ආකාරයෙන්ම cache/UI වෙත කිසිවිටෙකත් විශ්වාසයෙන් ඇතුළත් නොකෙරේ; මෙය header එකට පෙර පැවති පැරණි feed
   servers ද ආවරණය කරයි).
2. පියවර 1 කිසිවක් ලබා නොදෙන විට පමණක් signed body එකේ `tier` ක්ෂේත්රය (සැමවිටම `"live"`) වෙත fallback කරන්න.
3. තීරණය කළ ස්තරය cache කර `{ status: "updated",
version, tier }` ලෙස ආපසු ලබා දෙයි — dashboard එක පෙන්වන්නේ මෙම අගය මිස අමු body
   ක්ෂේත්රය නොවේ.

## කියවීමේ වේලාවේ overlay merge නීති

`applyFeed()` (`src/lib/radar/applyFeed.ts`) විසින් cached feed එක
static baseline එක **මතට**, `getRadarCatalog()` තුළ **කියවීමේ වේලාවේදී** merge කරයි. baseline array එක
(`FREE_MODEL_BUDGETS`) කිසිවිටෙකත් වෙනස් නොකෙරේ — සෑම call එකකදීම අලුතින් `MergedEntry[]` එකක් ගණනය කෙරේ.

ප්රමුඛතා අනුපිළිවෙළ අනුව නීති හතරක් ඇත:

1. **Feed එක කිසිවිටෙකත් local override එකක් උඩින් ලියන්නේ නැත.** ක්ෂේත්රයකට-ක්ෂේත්රයක් ලෙස: operator විසින්
   entry එකක ක්ෂේත්රයක් අභිරුචිකරණය කර ඇත්නම් (`provider:modelId` අනුව key කළ `localOverrides` map එක),
   එම නිශ්චිත ක්ෂේත්රය සඳහා feed එකේ අගය මඟ හරිනු ලැබේ — operatorගේ අගය ජය ගනී.
2. **`enabled: false` මඟින් entry එක අක්රිය කර, එහි මූලාශ්රයද සටහන් කරයි.** entry එකක් අක්රිය කරන
   feed entry එකක් merged ප්රතිඵලයෙහි `enabled: false` සහ `disabledBy: "radar"` සකසයි,
   එවිට entry එකක් ලබාගත හැකි තත්ත්වයෙන් අක්රිය තත්ත්වයට ගියේ _ඇයි_ දැයි UI එකට පැහැදිලි කළ හැක.
3. **Feed එකෙහි නොමැති user විසින් එක් කළ entry එකක් වෙනස් නොවී පවතී.** baseline එකෙහි පමණක් පවතින
   (හෝ local වශයෙන් එක් කළ) සහ අනුරූප feed entry එකක් නොමැති entries වෙනස් නොවී ඉදිරියට යයි.
4. **Tombstone කළ entry එකක් කිසිවිටෙකත් නැවත ප්රතිස්ථාපනය නොවේ.** operator විසින් entry එකක් පැහැදිලිවම මකා ඇත්නම්
   (`tombstones` set එක), පසු version එකකදී feed එක එම `provider:modelId` නැවත එක් කළද
   එය නැවත ගෙන එන්නේ නැත.

සංස්කරණය කළ හැකි ක්ෂේත්ර සහ tombstones
`radar_local_model_state` තුළ පවත්වාගෙන යනු ලැබේ (migration `153_radar_local_model_state.sql`). public DB
adapter එක (`src/lib/db/radar.ts`) එම rows, `applyFeed()` විසින් භාවිත කරන `localOverrides` map එක සහ
`tombstones` set එක බවට පරිවර්තනය කරයි; production `getRadarCatalog()` විසින් flag, cache, සහ schema gates
සමත් වූ පසු එම state එක load කරයි. operatorට සංස්කරණය කළ හැක්කේ `displayName` සහ `enabled` පමණි.

සහ setup දත්ත මෙම මතුපිට හරහා ලිවිය නොහැක.

dashboard එක local actions හතරක් ලබා දෙයි:

- **සංස්කරණය කරන්න** මඟින් local display name එක සහ enabled state එක වෙනස් කරයි.
- **Local වෙනස්කම් යළි සකසන්න** මඟින් tombstone එකක් වෙනස් නොකර සංස්කරණය කළ හැකි ක්ෂේත්ර දෙකම ඉවත් කරයි.
- **සඟවන්න** මඟින් tombstone එකක් නිර්මාණය කරයි, එබැවින් පසුකාලීන feed updates වලට row එක නැවත නිර්මාණය කළ නොහැක.
- **ප්රතිස්ථාපනය කරන්න** මඟින් tombstone එක ඉවත් කරයි; වෙනම save කළ override එකක් තිබේ නම් එය දිගටම ක්රියාත්මක වේ.

## සංග්රහයක් ස්වයං-සත්කාරකත්වය කරන්නේ කෙසේද

නාමාවලිය පිළිබඳ පූර්ණ පාලනය අවශ්ය fork එකකට හෝ ස්වයං-සත්කාරකයෙකුට client කේතය
වෙනස් නොකර තමන්ගේම සංග්රහ සේවාවක් ධාවනය කළ හැකිය:

1. `RadarFeedSchema` (`src/lib/radar/feedSchema.ts`) සපුරාලන JSON body එකක් ආපසු ලබා දෙන
   `GET /v1/catalog/latest` endpoint එකක් සපයන්න — ඉහළ මට්ටමේ `feed:
"omniroute-radar"`, `schemaVersion: 2`, `version`, `tier`, `providers`, `models`,
   `quirks`, සහ `totals`. `x-omniroute-radar-schema: 2` අනුගමනය කරන්න; සංක්රාන්ති-අනුකූල server එකක්
   එය නොමැති ඉල්ලීම් සඳහා වෙනම අත්සන් කළ v1 artifact එකක් පෙරනිමිය ලෙස භාවිත කළ යුතුය.
2. Ed25519 key pair එකකින් නිශ්චිත response bytes අත්සන් කර, base64
   signature එක `x-omniroute-feed-signature` response header එක තුළ ආපසු ලබා දෙන්න.
3. `RADAR_FEED_URL` නව base URL එකටද `RADAR_FEED_PUBKEY` ඊට ගැළපෙන
   public key එකටද (base64-DER SPKI හෝ PEM) සකසන්න —
   [env var යොමුව](../reference/ENVIRONMENT.md#27-radar-feed-self-hosting) බලන්න.
4. `RADAR_ENABLED` සක්රීය කර `POST /api/radar/settings`
   (`{ optIn: true }`) හරහා සහභාගී වීමට තෝරන්න.

වෙනත් කිසිදු කේත වෙනසක් අවශ්ය නොවේ — `verifyFeedBytes()` විසින් override එක
ස්වයංක්රීයව භාවිත කරයි (`src/lib/radar/pinnedKeys.ts` තුළ `getFeedPublicKeys()`), සහ version
සැසඳීම, schema වලංගුකරණය, සහ merge නීති ස්වයං-සත්කාරක සංග්රහයකටද සමාන ලෙස අදාළ වේ.

Referral links (ඉහත [Referral links (නොමිලේ credits)](#referral-links-free-credits)
බලන්න) වෙනම, විකල්ප artifact එකකි: `/v1/catalog/latest` පමණක් සපයන fork එකක්
තවමත් සම්පූර්ණයෙන් ක්රියා කරයි — `/v1/referrals/latest` වෙතින් `404` ලැබුණු විට
