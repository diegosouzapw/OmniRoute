රාමුව පහත ආකාරයෙන් ක්රියාත්මක කර ඇත:

- මතකයේ පවතින අන්තර්නිර්මිත කට්ටල ලියාපදිංචි කරන, අපේක්ෂිත නිර්ණායකවලට සාපේක්ෂව ප්රතිදාන ඇගයීමට ලක් කරන, සහ ලකුණු පත්ර ඒකාබද්ධ කරන පිරිසිදු ධාවකයක් (`src/lib/evals/evalRunner.ts`).
- අභිරුචි (පරිශීලක-නිර්වචිත) කට්ටල සහ ඓතිහාසික ධාවන SQLite තුළ ගබඩා කිරීම සඳහා ස්ථායිතා ස්තරයක් (`src/lib/db/evals.ts`).

### කට්ටලය

කට්ටලයක් යනු `description` එකක් සහ අවස්ථා එකක් හෝ කිහිපයක් සහිත, නමක් ඇති පරීක්ෂණ අවස්ථා එකතුවකි. කට්ටල මූලාශ්ර දෙකකින් පැමිණේ:

| මූලාශ්රය   | නිර්වචනය කර ඇති ස්ථානය                             | ධාවන වේලාවේ වෙනස් කළ හැකිද? |
| ---------- | -------------------------------------------------- | --------------------------- |
| `built-in` | ආරම්භයේදී `registerSuite()` හරහා ලියාපදිංචි කර ඇත  | නැත (කේතයෙන් නිර්වචිතයි)    |
| `custom`   | SQLite `eval_suites` + `eval_cases` තුළ ගබඩා කර ඇත | ඔව් (API/UI හරහා)           |

- `coding-proficiency` — Python/JS/SQL/TS/දෝෂ හඳුනාගැනීම
- `reasoning-logic` — න්යායානුමාන, වාචික ගැටලු, රටා හඳුනාගැනීම

- `instruction-following` — JSON පමණක්, අංකිත ලැයිස්තු, භාෂා සීමා
- `codex-comparison` — සැසඳීමේ ප්රකාරය සඳහා අදහස් කළ සෘජු මුහුණට-මුහුණ කේතීකරණ කාර්යයන්

## ලකුණු ලබාදීමේ නිර්ණායක

`evaluateCase()` (evalRunner.ts) තුළ ක්රියාත්මක කර ඇත:

| උපායමාර්ගය | සමත් වන්නේ…                                                                                |
| ---------- | ------------------------------------------------------------------------------------------ |
| `exact`    | `actualOutput === expected.value`                                                          |
| `contains` | `actualOutput.toLowerCase().includes(expected.value.toLowerCase())`                        |
| `regex`    | `new RegExp(expected.value).test(actualOutput)` සත්ය අගයක් වන විට                          |
| `custom`   | `expected.fn(actualOutput, evalCase)` සත්ය අගයක් ආපසු ලබාදෙන විට (ඇතුළත් කර ඇති ඒවාට පමණි) |

**සටහන:** ශ්රිත API හරහා අනුක්රමිකකරණය කළ නොහැකි බැවින්, අභිරුචි-ශ්රිත ලකුණු ලබාදීම කේතයෙන් අර්ථ දක්වා ඇති (ඇතුළත් කර ඇති)
කට්ටල සඳහා පමණක් වෙන් කර ඇත. පරිශීලකයන් නිර්මාණය කරන කට්ටල සඳහා
`evalCaseBuilderSchema` පිළිගන්නේ `contains | exact | regex` පමණි.

දැනට විනිශ්චයකරුවෙකු ලෙස LLM භාවිත කිරීමක් හෝ embedding-පදනම් වූ සමානතා ලකුණු ලබාදෙන්නෙකු නොමැත — එය
`evaluateCase()` තුළ පහසුවෙන් එක් කළ හැකි විස්තාරණ ලක්ෂ්යයක් වනු ඇත.

## දත්ත සමුදා යෝජනා ක්රමය

වගු තුනකි (`030_create_eval_runs.sql` සහ
`031_create_eval_suites.sql` සංක්රමණ):

| වගුව          | අරමුණ                                                                                                                         |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `eval_suites` | අභිරුචි කට්ටල පාරදත්ත (`id`, `name`, `description`)                                                                           |
| `eval_cases`  | එක් එක් කට්ටලයට අදාළ අවස්ථා — `input_json`, `expected_*`, `tags_json`                                                         |
| `eval_runs`   | ඓතිහාසික ධාවනයන් — `pass_rate`, `total`, `passed`, `failed`, `avg_latency_ms`, `summary_json`, `results_json`, `outputs_json` |

ඇතුළත් කර ඇති කට්ටල DB තුළ ගබඩා **නොකෙරේ**. ඒවා මතකයේ පවතින අතර
`evalRunner.ts` ආයාත කරන සෑම අවස්ථාවකම නැවත ලියාපදිංචි කෙරේ.

සියලුම අන්ත ලක්ෂ්ය සඳහා කළමනාකරණ සත්යාපනය (`requireManagementAuth`) අවශ්ය වේ — ඒවා

### කට්ටලයක් ධාවනය කිරීම

```bash
curl -X POST http://localhost:20128/api/evals \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "suiteId": "golden-set",
    "target": { "type": "combo", "id": "my-combo" },
    "apiKeyId": "optional-api-key-uuid"
  }'
```

විකල්ප ක්ෂේත්ර:

- `outputs` — පෙර ගණනය කළ ප්රතිදාන අඩංගු `Record<caseId, string>` එකකි. මෙය සපයා ඇති විට,
  ධාවකය **යැවීම මඟහරින** අතර හැඹිලිගත ප්රතිදානවලට පමණක් ලකුණු ලබා දෙයි (නොබැඳි
  ඇගයීම සඳහා ප්රයෝජනවත් වේ).
- `compareTarget` — සමාන්තරව ධාවනය කළ යුතු දෙවන ඉලක්කය; මුහුණට-මුහුණ දර්ශනය සඳහා ධාවනයන් දෙකම
  ජනනය කළ `runGroupId` එකක් බෙදා ගනියි.
- `apiKeyId` — යවන ලද
  `/v1/chat/completions` ඇමතුම් සත්යාපනය කිරීමට භාවිත කරන අභ්යන්තර API යතුර. `REQUIRE_API_KEY` සක්රීය කර ඇති විට මෙය අවශ්ය වේ.

### අභිරුචි කට්ටලයක් නිර්මාණය කිරීම

```bash
curl -X POST http://localhost:20128/api/evals/suites \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Production smoke",
    "description": "Quick sanity check before deploy",
    "cases": [
      {
        "name": "JSON shape",
        "model": "gpt-4o",
        "input": { "messages": [{ "role": "user", "content": "Reply with {\"ok\": true}" }] },
        "expected": { "strategy": "regex", "value": "\"ok\"\\s*:\\s*true" }
      }
    ]
  }'
```

## යොමුකිරීමේ නලමාර්ගය

`runEvalSuiteAgainstTarget()` (`src/lib/evals/runtime.ts`):

1. කට්ටලය (අන්තර්ගත හෝ අභිරුචි) නිරාකරණය කරයි.
2. එක් එක් අවස්ථාව සඳහා, එම අවස්ථාවේ `messages`, නිරාකරණය කළ `model`, `stream: false`, සහ `max_tokens: 512` (හෝ එම අවස්ථාව සඳහා ඇති අතික්රමණ අගය) සමඟ `/v1/chat/completions` වෙත `Request` එකක් ගොඩනඟයි.
3. කතාබස් හසුරුවනය සෘජුවම කැඳවයි (ක්රියාවලිය තුළම — අමතර HTTP පැනීමක් නොමැත).
4. ප්රමාදය ග්රහණය කර, `choices[0].message.content` හෝ Responses-API `output[]` දත්තයෙන් පෙළ උපුටා ගනියි.
5. `runSuite()` හරහා සියලු ප්රතිදාන ලකුණු කර, පසුව `saveEvalRun()` හරහා ස්ථිරව සුරකියි.

අවස්ථා **අනුක්රමිකව** ක්රියාත්මක වේ. දැනට සමගාමීත්ව ධජයක් නොමැත.

- ක්රියාත්මක කිරීම් ඉතිහාසය, එක් එක් අවස්ථාවේ සමත්/අසමත් තත්ත්වය, ප්රමාදය සහ ග්රහණය කළ ප්රතිදාන පරීක්ෂා කළ හැක.

එම උපපද්ධතිය Auto Combo එන්ජිම ඉලක්ක කරයි — ඉහළ ප්රවාහයන් අසමත් වූ විට සංයෝජනවලට ස්වයං-ප්රතිසාධනය විය හැකි පරිදි සපයන්නන් සහ ආකෘති ස්වයංක්රීයව ලකුණු කරයි. එය තමන්ගේම ධාවකය, තමන්ගේම වර්ගීකාරකය සහ තමන්ගේම ලකුණුකරණ තර්කනය භාවිත කරයි.

මෙහි ලේඛනගත කර ඇති Evals රාමුව **වඩා පුළුල්, පොදු කාර්ය පරීක්ෂණ පෘෂ්ඨය** වේ. ඕනෑම ප්රතිගමන කට්ටල, A/B සැසඳීම් සහ එක් එක් නිකුතුව සඳහා වන මූලික ක්රියාකාරීත්ව පරීක්ෂණ සඳහා මෙය වඩාත් සුදුසුය. මාර්ගගත කිරීමේ තීරණවලට බලපෑම් කිරීමට තත්ය කාලීන සපයන්නාගේ සෞඛ්ය තත්ත්වය අවශ්ය වූ විට Auto-Assessment උපපද්ධතිය භාවිත කරන්න.

## CI ඒකාබද්ධ කිරීම

දැනට කැපවූ `eval:ci` npm ස්ක්රිප්ට් එකක් නොමැත. ඇගයීම් ප්රතිඵල මත නිකුතු පාලනය කිරීමට අවශ්ය නම් මාර්ග දෙකක් ඇත:

- **HTTP මාර්ගය**: සේවාදායකය ක්රියාත්මක කර, දන්නා `suiteId` + `target` සමඟ `POST /api/evals` වෙත ඉල්ලීමක් යවා, ප්රතිචාරය තුළ `runs[].summary.passRate >= N` බව තහවුරු කරන්න.
- **ක්රියාවලිය-තුළ මාර්ගය**: ස්ක්රිප්ට් එකකින් `@/lib/evals/runtime` වෙතින් `runEvalSuiteAgainstTarget()` ආයාත කර, පරීක්ෂණ DB එකකට එරෙහිව ක්රියාත්මක කර, ආපසු ලැබෙන `PersistedEvalRun.summary` පරීක්ෂා කරන්න.

මාර්ගය සහ ඉතිහාසය ආවරණය කරන පරීක්ෂණ
`tests/unit/evals-route.test.ts` සහ `tests/unit/evals-history.test.ts` හි පිහිටා ඇත.

## විස්තාරණ ලක්ෂ්ය

පොදු වෙනස්කම් සහ ඒවා සිදු කළ යුතු ස්ථාන:

- **නව ලකුණුකරණ උපායමාර්ගයක්** — `evaluateCase()` (`evalRunner.ts`) තුළ ඇති `switch (evalCase.expected.strategy)` කොටස විස්තාරණය කර, `src/lib/db/evals.ts` තුළ `EvalCaseStrategy` සහ `schemas.ts` තුළ `evalCaseBuilderSchema` පුළුල් කරන්න.
- **නව අන්තර්ගත කට්ටලයක්** — කට්ටල වස්තුවක් නිර්වචනය කර `evalRunner.ts` හි පහළින් `registerSuite()` කැඳවන්න. එය `listSuites()` මඟින් ස්වයංක්රීයව සොයාගනු ඇත.
- **සමගාමීත්වය සමඟ ක්රියාත්මක කිරීම** — `runEvalSuiteAgainstTarget()` තුළ ඇති අනුක්රමික `for` ලූපය සීමා කළ `Promise.all` එකකට වෙනස් කරන්න (දැනට සමගාමීත්ව පාලනයක් නොමැත).
- **ප්රවාහ/මෙවලම්-කැඳවීම් අවස්ථා** — දැනට ධාවකය `stream: false` බලහත්කාරයෙන් යොදයි. ප්රවාහ හෝ මෙවලම්-සංවේදී ඇගයීම සඳහා `runtime.ts` තුළ වෙනස්කම් අවශ්ය වේ (ලකුණු කිරීමට පෙර SSE කොටස් ග්රහණය කර සමූහනය කිරීම).
