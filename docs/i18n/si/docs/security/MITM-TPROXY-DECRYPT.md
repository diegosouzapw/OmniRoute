TPROXY පාරදෘශ්ය විකේතනය යනු
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM තොගය සඳහා OmniRoute හි **5 වන ග්රහණ ප්රකාරයයි**. එය kernel TPROXY + policy routing භාවිතයෙන් Linux මත දේශීයව පිටතට යන HTTPS ගමනාගමනය අතරමඟින් අල්ලා **විකේතනය** කරයි — `/etc/hosts` ව්යාජ ලෙස නිරූපණය කිරීමෙන් **තොරව** සහ සමස්ත OS පද්ධතියට බලපාන proxy සැකසුම් වෙනස් කිරීමෙන් **තොරව**. එය headless පරිසර සඳහා හිතකරය (පසුව පිරිසිදු කිරීමට DNS සංස්කරණ නොමැත) සහ firewall රීති නැවත පණගැන්වීමේදී ස්වයංක්රීයව ඉවත් වේ.

අනෙකුත් ග්රහණ ප්රකාර මෙන් නොව, TPROXY සඳහා එක් එක් සත්කාරකයට වෙනම සැකසුමක් අවශ්ය නොවේ: එය ඉලක්ක port එකක ඇති **ඕනෑම** ගමනාන්ත සත්කාරකයකට යන ගමනාගමනය පාරදෘශ්යව අතරමඟින් අල්ලා, එක් එක් SNI සත්කාරක නාමය සඳහා ක්ෂණිකව නිකුත් කරන leaf certificate එකක් සමඟ TLS අවසන් කර, විකේතනය කළ හුවමාරුව ග්රහණය කර, ඉල්ලීම මුල් ගමනාන්තය වෙත නැවත සංකේතනය කර යවයි.

> **Linux සඳහා පමණි, root සඳහා පමණි, කැමැත්තෙන් සක්රිය කළ යුතුය.** මෙම ප්රකාරයට Linux, C toolchain එකකින් ගොඩනැගූ native addon එකක් සහ **CAP_NET_ADMIN** හැකියාව (සාමාන්යයෙන් root) අවශ්ය වේ. එය loopback-only AgentBridge API එක පිටුපසින් සීමා කර ඇති අතර පෙරනිමියෙන් අක්රිය කර ඇත. ඕනෑම සත්කාරකයක් සඳහා අත්සන් කළ හැකි විශ්වාසනීය MITM CA එකක් ප්රබල හැකියාවකි — [§6 ආරක්ෂාව](#6-security) බලන්න.

## §1 මෙය කුමක්ද සහ භාවිත කළ යුත්තේ කවදාද

අනෙකුත් ග්රහණ ප්රකාර හතරටම එක් එක් සීමාවක් ඇත:

| ප්රකාරය            | ගමනාගමනය යොමු කරන ආකාරය                               | සීමාව                                                          |
| ------------------ | ----------------------------------------------------- | -------------------------------------------------------------- |
| AgentBridge        | ස්ථාවර සත්කාරක කට්ටලයක `/etc/hosts` DNS ව්යාජ නිරූපණය | ලියාපදිංචි IDE-agent සත්කාරක පමණි                              |
| අභිරුචි සත්කාරක    | එක් එක් සත්කාරකයට `/etc/hosts` DNS ව්යාජ නිරූපණය      | එක් සත්කාරකයකට එක් ඇතුළත් කිරීමක්; hosts සංස්කරණයට sudo අවශ්යය |
| HTTP_PROXY         | `HTTP_PROXY`/`HTTPS_PROXY` පරිසර විචල්යය              | පරිසර විචල්යයට ගරු කරන යෙදුම් පමණි                             |
| පද්ධතිය-පුරා proxy | OS proxy සැකසුම්                                      | ගෝලීය තත්ත්වය වෙනස් කරයි; ආපසු හැරවීම අවශ්යය                   |

ඒ වෙනුවට TPROXY පාරදෘශ්ය විකේතනය ගමනාගමනය **kernel** ස්තරයේදී යොමු කරයි. එය `mangle OUTPUT` දාමයේදී ඉලක්ක port එකකට (පෙරනිමියෙන් `443`) යන නව දේශීය පිටතට යන TCP සම්බන්ධතා සලකුණු කරයි, `ip rule` එකක් සලකුණු කළ packets දේශීය බෙදාහැරීම වෙත නැවත යොමු කරයි, සහ නැවත ඇතුළු වීමේදී `mangle PREROUTING` හි `TPROXY` ඉලක්කය ඒවා **IP_TRANSPARENT** listener එකකට භාර දෙයි — එය පසුව TLS අවසන් කර plaintext ග්රහණය කරයි.

පහත ලක්ෂණ ඇති ක්රියාවලියක ගමනාගමනය ග්රහණය කර විකේතනය කිරීමට අවශ්ය විට එය භාවිත කරන්න:

- AgentBridge ලියාපදිංචි නොකරන සත්කාරකයක් සමඟ සන්නිවේදනය කරයි, සහ
- `HTTP_PROXY` සඳහා ගරු නොකරයි, සහ
- පද්ධතිය-පුරා proxy වෙනසකින් එයට බාධා කිරීමට ඔබට අවශ්ය නොවේ.

අතරමඟින් ඇල්ලීම kernel තුළ සිදුවන බැවින්, මූලාරම්භක ක්රියාවලියට **කිසිදු වින්යාස වෙනසක්** අවශ්ය නොවේ — නමුත් එම ක්රියාවලිය OmniRoute ස්ථාපනය කරන dynamic CA එක විශ්වාස කළ යුතුය ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) බලන්න).

## §2 අවශ්යතා

| අවශ්යතාව           | විස්තරය                                                                                                                                                                |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**             | Linux පමණි — **IP_TRANSPARENT** යනු Linux සඳහා පමණක් ඇති socket විකල්පයකි. අනෙකුත් සෑම platform එකකදීම loader එක "unavailable" යන්න ආපසු ලබා දෙයි.                     |

## §3 Native IP_TRANSPARENT addon එක

Node හි `net` module එකට `bind()` කිරීමට _පෙර_ `setsockopt(IP_TRANSPARENT)` යෙදිය නොහැක;
TPROXY සඳහා එය අවශ්ය වේ (එසේ නොමැතිනම් kernel එක redirect කළ packets ඉවත දමයි). මෙම addon එක
(`src/mitm/tproxy/native/transparent.c`, `binding.gyp` හරහා build කරනු ලැබේ) යනු
`transparentSocket.ts` හරහා භාවිත කරන functions තුනක් නිරාවරණය කරන කුඩා N-API
module එකකි:

| Addon function                        | Socket ක්රියාව                                                                                      | භාවිතය                                                                                   |
| ------------------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`; raw fd එක ආපසු ලබා දෙයි | transparent capture listener එක (Node විසින් `server.listen({ fd })` හරහා fd එක භාර ගනී) |
| `setSocketMark(fd, mark)`             | පවතින fd එකක් මත `setsockopt` **SO_MARK** යෙදීම                                                     | loop වැළැක්වීම (proxy එකේම sockets සලකුණු කිරීම)                                         |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()` එකකට **පෙර** `socket()` + **SO_MARK** යෙදීම; fd එක ආපසු ලබා දෙයි           | නැවත encrypt කළ upstream forward එක (SYN එක mark එක රැගෙන යයි)                           |

මුල් ගමනාන්තය `socket.localAddress`/`localPort` වෙතින් කියවනු ලැබේ — TPROXY
එය සුරැකිව තබන බැවින් **SO_ORIGINAL_DST**/NAT lookup එකක් අවශ්ය නොවේ.

### Addon එක build කිරීම

```bash
npm run build:native:tproxy      # src/mitm/tproxy/native වෙත cd වී node-gyp rebuild ධාවනය කරන්න
                                 # -> native/build/Release/transparent.node
```

- `npm run build` අතරතුර, `scripts/build/build-tproxy-native.mjs` මඟින් `node-gyp
rebuild` ධාවනය කරයි. එය **Linux සඳහා පමණක් වන අතර අසාර්ථක වුවද ක්රියාවලිය නතර නොකරයි** — toolchain එකක් නොමැති නම්
  capture mode එක ලබාගත නොහැකි ලෙස පමණක් පවතී.
- `assembleStandalone.mjs` මඟින් `build/Release/transparent.node` standalone bundle එකට
  පිටපත් කරයි; `transparentSocket.ts` එය module-relative සහ
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`) යන ආකාර දෙකෙන්ම resolve කරයි.
- `build/` සහ `prebuilds/` git-ignore කර ඇත — binary එක **build කරනු ලබන අතර කිසිවිටෙක
  commit නොකෙරේ**.

Loader එක පහත ප්රමුඛතා අනුපිළිවෙළින් පරීක්ෂා කරයි:
`native/build/Release/transparent.node`, ඉන්පසු `native/prebuilds/transparent.node`
(module-relative ලෙසත් `<cwd>/src/mitm/tproxy/` යටතේත්).

## §4 එක්-SNI ගතික CA සහ විශ්වාස-ගබඩා ස්ථාපකය

> **#6684 යාවත්කාලීනය:** AgentBridge ස්ථිතික සේවාදායකය (`src/mitm/server.cjs`) දැන්
> තනි ස්ථිතික ස්වයං-අත්සන් කළ leaf එකක් වෙනුවට මෙම CA/leaf ගෘහනිර්මාණ රටාවම
> බෙදාගනී. එය **වෙන් වූ** CA අවස්ථාවක්
> (`src/mitm/cert/rootCa.ts`, `<DATA_DIR>/mitm/ca.key`/`ca.crt` හි සුරැකෙන)
> භාවිත කරන අතර, පෙර සිට පැවති `omniroute-mitm.crt` විශ්වාස-ගබඩා ස්ථානය යටතේ
> ස්ථාපනය කරයි (එහි පැරණි තනි leaf එක ප්රතිස්ථාපනය කරන බැවින් ද්විත්ව-විශ්වාස
> පිරිසිදු කිරීමක් අවශ්ය නොවේ). එය පහත දැක්වෙන TPROXY සතු
> `omniroute-tproxy-ca.crt` ස්ථානයෙන් සම්පූර්ණයෙන්ම වෙන්ව තබා ඇත.
> නව AgentBridge ස්ථාපනයන්ට CA ආකෘතිය ස්වයංක්රීයව ලැබේ; පැරණි ස්ථිතික leaf එක
> දැනටමත් විශ්වාස කළ ස්ථාපනයක්, ක්රියාකරු `MITM_ROOT_CA_ENABLED=true` හරහා
> එකඟ වන තෙක් එය දිගටම භාවිත කරයි (`src/mitm/cert/migration.ts` බලන්න) —
> **ඕනෑම** සත්කාරකයක් සඳහා leaf එකක් අත්සන් කළ හැකි විශ්වාසනීය MITM CA එකක්,
> පැරණි ස්ථාවර-SAN leaf එකට වඩා සැලකිය යුතු ලෙස බලවත් බැවින්, දැනටමත්
> විශ්වාස කර ඇති ස්ථාපනයක් සඳහා මෙම මාරුව කිසිවිටෙක නිහඬව සිදු නොවේ.

ඓතිහාසිකව, ස්ථිතික AgentBridge MITM සහතිකය ක්රියා කළේ AgentBridge විසින්
**ස්ථාවර** සත්කාරක කට්ටලයක DNS ව්යාජනය කරන නිසා පමණි (දැන් එය පහත ආකෘතිය සමඟ
ඒකාබද්ධ කර ඇත). TPROXY විසින් **අත්තනෝමතික** සත්කාරක අවහිර කරන බැවින්, එහි
listener එක සේවාලාභියා ඉල්ලන ඕනෑම SNI එකක් සඳහා වලංගු leaf එකක් ඉදිරිපත් කළ
යුතුය — antigravity සත්කාරක 4 සඳහා පමණක් නොව, සම්පූර්ණ `MITM_TOOL_HOSTS`
කට්ටලය (මෙවලම් ඇතුළත් කිරීම් 9ක්) සඳහා දැන් AgentBridge සතුවද ඇත්තේ එම
අවශ්යතාවමයි.

### ගතික CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` විසින් (`selfsigned` dependency එක මත ගොඩනගන ලද) දේශීය CA
එකක් ක්රියාත්මක කරයි, එය:

- `generateMitmCa()` හරහා දිගුකාලීන CA එකක් ජනනය කරයි (CN
  `"OmniRoute MITM CA"`, වසර 10ක වලංගු කාලයක්, `basicConstraints CA=true` +
  `keyUsage keyCertSign,cRLSign`, 2048-bit RSA / SHA-256).
- `issueLeafCert()` හරහා **ඉල්ලුම මත එක් එක් SNI සත්කාරක නාමයට leaf එකක්**
  නිකුත් කරයි (වසර 1ක වලංගු කාලයක්, `subjectAltName` = SNI සත්කාරකය) සහ එක් එක්
  සත්කාරක නාමය සඳහා එක් `tls.SecureContext` එකක් cache කරයි.
- TLS අවසන් කරන සේවාදායකය සඳහා `createSNICallback()` නිරාවරණය කරයි
  ([§5](#5-how-decrypt-and-capture-work) බලන්න).
- නැවත ආරම්භ කිරීම් හරහා CA එක ස්ථාවරව තබාගැනීමට `existingCa` සමඟ නිර්මාණය කළ
  හැකිය (එවිට විශ්වාස ගබඩාව නැවත ස්ථාපනය කිරීමට අවශ්ය නොවේ).

CA පුද්ගලික යතුර **කිසිවිටෙක යන්ත්රයෙන් පිටතට නොයයි**.

### විශ්වාස-ගබඩා ස්ථාපකය (`src/mitm/tproxy/caTrust.ts`)

අවහිර කරන ලද සේවාලාභියා ගතික CA එක විශ්වාස කළ යුතු බැවින්, capture මාදිලිය
ආරම්භ කිරීමේදී CA සහතිකය මෙහෙයුම් පද්ධතියේ විශ්වාස ගබඩාව තුළ
**කැප වූ ස්ථානයක්** යටතේ — `omniroute-tproxy-ca.crt` (`TPROXY_CA_CERT_NAME`

පද්ධතිවල මෙය කිසිදු ක්රියාවක් නොකරයි.

shell එකක් නොමැතිව, string interpolation නොමැතිව** `spawn` භාවිත කරයි

## §5 විකේතනය සහ ග්රහණය ක්රියා කරන ආකාරය

නල මාර්ගය (සියල්ල `src/mitm/tproxy/` යටතේ):

```
දේශීය යෙදුම  ──TCP/443──▶  mangle OUTPUT මඟින් සම්බන්ධතාව සලකුණු කරයි (fwmark)
                            ip rule → දේශීය මාර්ගගත කිරීමේ වගුව → lo
                            mangle PREROUTING TPROXY → IP_TRANSPARENT ශ්රාවකය (port 8443)
                                │  captureMode.ts: socket.localAddress වෙතින් මුල් ගමනාන්තය කියවයි
                                ▼
                            tlsCapture.ts:
                              1. එක් එක් SNI සඳහා වූ leaf එකකින් CLIENT වෙත TLS අවසන් කරයි (dynamicCert)
                              2. අභ්යන්තර http.Server එක විකේතනය කළ සරල පෙළ විග්රහ කරයි
                              3. ග්රහණය → source: "tproxy" සමඟ globalTrafficBuffer.push()
                                 (sanitizeHeaders + maskSecret යොදනු ලැබේ)
                              4. bypass ලෙස සලකුණු කළ socket එකක් හරහා මුල් ගමනාන්තය වෙත
                                 යළි සංකේතනය කර යොමු කරයි (connectMarked, ප්රති-ලූපය)
                                │
                                ▼
                            මුල් upstream එක (api.example.com)
```

- **TLS අවසන් කිරීම** (`createTlsCaptureServer`): dynamic CA හි SNI callback එක භාවිතයෙන් අමු ලෙස අන්තර්ග්රහණය කළ
  socket එක server-side `tls.TLSSocket` එකකින් ආවරණය කර,
  අනතුරුව විකේතනය කළ ප්රවාහය අභ්යන්තර `http.Server` එකකට භාර දෙයි (සම්මත MITM
  අවසන් කිරීමේ උපක්රමය). ප්රතිචාර නොදක්වන tunnel එකකට file descriptors ක්ෂය කළ නොහැකි වන පරිදි socket ආයුකාල
  `MITM_IDLE_TIMEOUT_MS` මඟින් සීමා කර ඇත.
- **ග්රහණය** (`handleDecryptedRequest`): `source: "tproxy"`, `"in-flight"` ලෙස ආරම්භ වන status එකක් සහිත
  `InterceptedRequest` එකක් ඇතුළත් කරයි; buffer එකට ඇතුළු වීමට පෙර headers
  `sanitizeHeaders()` හරහාත් bodies `maskSecret()` හරහාත් යවනු ලැබේ.
  ඉන්පසු response එක, ප්රමාණයන් සහ latency එක සමඟ entry එක යාවත්කාලීන කෙරේ.
- **යළි සංකේතනය කළ යොමු කිරීම** (`createForward` / `realForward`): මුල්
  ගමනාන්තය වෙත යළි සංකේතනය කරයි. `rejectUnauthorized` හි පෙරනිමි අගය **`true`** වේ (පෙරනිමියෙන්
  ආරක්ෂිතයි) — upstream cert එක client විසින් ඉල්ලා සිටි SNI/Host එකට එරෙහිව
  සත්යාපනය වන බැවින්, මුල් client එක ප්රතික්ෂේප කරන දේම proxy එකද ප්රතික්ෂේප කරයි.

### ප්රති-ලූපය (SO_MARK)

නීති මඟින් නව දේශීය outbound සම්බන්ධතා සලකුණු කරන බැවින්, proxy එකේ **ම**
යළි සංකේතනය කළ යොමු කිරීම සාමාන්යයෙන් නැවත අන්තර්ග්රහණය වනු ඇත — එය අනන්ත ලූපයකි. යොමු කිරීමේ
මාර්ගය bypass socket සලකුණක් (**SO_MARK**) භාවිතයෙන් මෙයට එරෙහිව ආරක්ෂා වේ:

- `realForward` විසින් `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` හරහා එහි upstream socket එක විවෘත කරයි
  — `DEFAULT_BYPASS_MARK = 0x539` — එය `connect()` කිරීමට **පෙර** **SO_MARK** සකසන බැවින්,
  යොමු කිරීමේ SYN එක bypass සලකුණ රැගෙන යයි.
- `mangle OUTPUT` නීතිය දැනටමත් bypass සලකුණ රැගෙන යන සම්බන්ධතා
  (`-m mark ! --mark <bypassMark>`) බැහැර කරන බැවින්, proxy එකේ යොමු කිරීම නැවත සලකුණු **නොකරන**
  අතර එය නැවත TPROXY වෙත ඇතුළු නොවේ.

> ක්රියාත්මක කිරීමේ සටහන: bypass ලෙස සලකුණු කළ socket එක agent හි
> `createConnection` මත ස්ථාපනය කළ යුතුය (`https.request({ createConnection })` agent එකක් පවතින විට නිහඬව නොසලකා හරිනු ලැබේ),
> එසේ නොමැතිනම් යොමු කිරීම සලකුණු නොකළ socket එකක් විවෘත කර ලූපය
> නැවත ඇති කරයි. මෙය e2e මඟින් වලංගු කරන ලද ප්රති-ලූප නිවැරදි කිරීම විය.

## §7 ගනුදෙනුමය firewall යෙදීම / ප්රතිවර්තනය

බිඳවැටීමක් නිසා කිසි විටෙකත් `mangle` රීතියක් හෝ යල්පැන ගිය route එකක් ඉතිරි නොවිය යුතුය. විධාන සාදකය
(`src/mitm/tproxy/commands.ts`) සහ ධාවකය (`src/mitm/tproxy/setup.ts`) විසින්
**ප්රතිවර්තනය යනු යෙදීමේ නිශ්චිත ප්රතිලෝමය, ප්රතිවිරුද්ධ අනුපිළිවෙළින් බව** සහතික කරයි.

`applyTproxy(cfg)` විසින් යෙදුම් විධාන අනුපිළිවෙළින් ධාවනය කරයි; **ඕනෑම** අසාර්ථක වීමකදී එය
හැකි උපරිම උත්සාහයෙන් සම්පූර්ණ `revertTproxy(cfg)` එකක් ධාවනය කර නැවත දෝෂය නිකුත් කරයි — එබැවින් firewall එක
සම්පූර්ණයෙන්ම යොදනු ලැබේ හෝ සම්පූර්ණයෙන්ම ප්රතිවර්තනය කෙරේ; කිසි විටෙකත් අර්ධ වශයෙන් යෙදී නොතිබේ. `revertTproxy(cfg)` විසින්
ප්රතිලෝම විධාන ප්රතිවිරුද්ධ අනුපිළිවෙළින් ධාවනය කර අසාර්ථක වීම් නොසලකා හරියි (idempotent — කොන්දේසි විරහිතව ඇමතීම ආරක්ෂිතය,
උදා. AgentBridge `repairMitm()` පිරිසිදු කිරීම තුළින්).

ඕනෑම විධානයකට පෙර `validateTproxyConfig(cfg)` ධාවනය වේ: ports `1–65535` විය යුතුය,
`mark`/`routeTable`/`bypassMark` ධන පූර්ණ සංඛ්යා විය යුතු අතර, `bypassMark` අගය
`mark` වෙතින් වෙනස් විය යුතුය (anti-loop).

### යෙදුම් විධාන (අනුපිළිවෙළින්)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

ප්රතිවර්තනය ඒවා ප්රතිවිරුද්ධ අනුපිළිවෙළින් මකා දමයි: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> MITM භාවිත අවස්ථාව _දේශීය_ පිටතට යන ගමනාගමනය
> (එකම host එකේ ඇති යෙදුම්) වන නිසා මෙම ක්රමය **OUTPUT-පාදක** වේ; `PREROUTING` තුළ ඇති TPROXY පමණක් එය
> නොදකියි — `PREROUTING` දකින්නේ ඉදිරියට යොමු කළ ගමනාගමනය පමණි. `OUTPUT` chain එක නව
> දේශීය සම්බන්ධතා සලකුණු කරයි, `ip rule` ඒවා දේශීය භාරදීමට (`lo`) නැවත මාර්ගගත කරයි, ඉන්පසු
> `PREROUTING` ඒවා transparent listener වෙත පවරයි.

## §8 වින්යාසය

ආරම්භක ඉල්ලීම (`POST /api/tools/agent-bridge/tproxy`) පහත
ක්ෂේත්ර පිළිගනී; ඒවා `StartTproxyBodySchema` (`tproxy/route.ts`) මඟින් වලංගු කෙරේ. සියල්ල විකල්ප
වන අතර ලබා නොදුනහොත් ඒවායේ පෙරනිමි අගයන් භාවිත වේ:

| ක්ෂේත්රය         | වර්ගය              | පෙරනිමිය | සටහන්                                                                                                              |
| ---------------- | ------------------ | -------- | ------------------------------------------------------------------------------------------------------------------ |
| **dport**        | int (1–65535)      | `443`    | transparent ලෙස බාධා කර ගත යුතු ගමනාන්ත TCP port එක                                                                |
| **mark**         | int (≥1)           | `0x2333` | `OUTPUT` මත සකසන, `ip rule` + `PREROUTING` මඟින් ගළපන firewall සලකුණ                                               |
| **onPort**       | int (1–65535)      | `8443`   | transparent (**IP_TRANSPARENT**) listener බැඳෙන port එක                                                            |
| **routeTable**   | int (≥1)           | `233`    | `local 0.0.0.0/0` route එක රඳවා ඇති policy-routing වගුවේ id එක                                                     |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | proxy එක තමන්ගේම upstream සම්බන්ධතා මත සකසන bypass socket සලකුණ (**SO_MARK**); `OUTPUT` තුළ බැහැර කෙරේ (anti-loop) |
| **sudoPassword** | string             | —        | root නොවන desktop සඳහා පමණි: trust-store ස්ථාපනයට අවසර දෙයි; root ලෙස ක්රියා කරන විට නොසලකා හැරේ                   |

TPROXY සඳහා **environment variables කිසිවක් නොමැත** — සියලු වින්යාස කිරීම් සිදුවන්නේ
POST body එක හෝ ඉහත පෙරනිමි අගයන් හරහාය.

   dynamic CA එක ගොඩනඟා, transparent listener එක විවෘත කර, firewall
   රීති යොදවා, OS trust store එකේ CA එක ස්ථාපනය කරයි.
4. ක්රියාත්මක වන විට, toggle එක ඇම්බර් පැහැයට හැරී සජීවී intercept ගණන
   (`· <interceptCount>`) පෙන්වයි. Intercept කළ ඉල්ලීම් request ලැයිස්තුවේ
   `source: "tproxy"` සමඟ දිස් වේ.
5. නැවැත්වීමට නැවත ක්ලික් කරන්න — `stopTproxyCaptureMode()` හරහා
   `DELETE /api/tools/agent-bridge/tproxy` මඟින් listener එක වසා, CA එක අස්ථාපනය කර,
   firewall රීති ආපසු හරවයි.

capture-mode තත්ත්වය (ක්රියාත්මක ද / ලබාගත හැකි ද / intercept ගණන / listener port එක)
`GET /api/tools/agent-bridge/tproxy` වෙතින් ලැබේ (`src/mitm/tproxy/captureManager.ts` හි
`getCaptureStatus()`). වරකට ක්රියාත්මක වන්නේ TPROXY සැසියක් **එකක් පමණි** —
දෙවන සැසියක් ආරම්භ කිරීමට උත්සාහ කළහොත් "TPROXY capture mode is already running" යන පණිවිඩය සමඟ එය ප්රතික්ෂේප වේ.

## §10 දෝෂ නිරාකරණය

### Toggle එක අක්රීයයි

native addon එක load කළ නොහැක. පහත දෑ තහවුරු කරන්න: ඔබ Linux මත සිටින බව, addon එක
(`npm run build:native:tproxy`) build කර ඇති බව, සහ process එකට `transparent.node` load කළ හැකි බව.
`isTransparentSocketAvailable()` මඟින් toggle එක පාලනය කරයි; addon එක නොමැති විට `GET /api/tools/agent-bridge/tproxy`
මඟින් `available: false` ආපසු ලබා දෙයි.

### කිසිවක් capture නොවේ

- intercept කරන ලද process එක සැබවින්ම වින්යාස කළ `dport` වෙත
  (පෙරනිමියෙන් `443`) සම්බන්ධ වන බව තහවුරු කරන්න.
- process එක dynamic CA එක විශ්වාස කරන බව තහවුරු කරන්න. CA එක
  `omniroute-tproxy-ca.crt` යටතේ ස්ථාපනය කර ඇත; තමන්ගේම trust store එකක් ඇති යෙදුම්වලට (Firefox/Chrome NSS)
  එම cert එක එයටත් එක් කිරීමට සිදු විය හැක.
- cert-trusted / server සෞඛ්ය පරීක්ෂණ සඳහා AgentBridge **Diagnose** ස්වයං-පරීක්ෂණය ක්රියාත්මක කරන්න
  ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md) බලන්න).

### බිඳවැටීමකින් පසු ඉතිරි වූ firewall රීති

`revertTproxy()` යනු apply ක්රියාවේ නිශ්චිත ප්රතිලෝමය වන අතර එය idempotent වේ. mode එක නැවැත්වීමෙන්
රීති ආපසු හරවයි; සැසියක් අතරතුර OmniRoute බලහත්කාරයෙන් නවතා දැමුවේ නම්, අනාථ වූ system
තත්ත්වය (DNS spoof, root CA, system proxy) අහෝසි කිරීමට AgentBridge
**Repair** ක්රියාව (`POST /api/tools/agent-bridge/repair`) භාවිත කරන්න. TPROXY `mangle` රීති සහ route එක ද
නැවත ආරම්භ කිරීමේදී ස්වයංක්රීයව ඉවත් වේ.

### අනන්ත loop එකක් / proxy එක තමන්ගේම forward එක intercept කරයි

මෙය anti-loop අවස්ථාවයි. `bypassMark` අගය `mark` අගයට වඩා වෙනස් බව (validation මඟින්
මෙය බලාත්මක කරයි) සහ forward එක `connectMarked` භාවිත කරන බව (එය `realForward` තුළ එසේ කරයි) තහවුරු කරන්න.
[§5 Anti-loop](#anti-loop-so_mark) බලන්න.
