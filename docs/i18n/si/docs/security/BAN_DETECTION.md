OmniRoute විසින් සපයන්නෙකුගේ **ගිණුම ස්ථිරවම අක්රිය වී ඇති බව**
(අත්හිටුවා ඇත / නිෂ්ක්රිය කර ඇත / සේවා කොන්දේසි කඩ කිරීම හේතුවෙන් තහනම් කර ඇත) දැක්වෙන සංඥා සඳහා upstream දෝෂ ප්රතිචාර පරිලෝකනය කරන අතර, ගැළපීමක්
හමු වූ විට, එම සම්බන්ධතාව ඉදිරියේදී ඉල්ලීම් සඳහා තෝරා නොගන්නා ලෙස
**අවසන් `banned` තත්ත්වයකට** මාරු කරයි. **Security → Banned Keywords**
සැකසුම් කාඩ්පත මඟින් වින්යාස කරන්නේ මෙයයි ("ස්ථිර ගිණුම් තහනමක්
හඳුනාගැනීමට හේතු වන අමතර මූලපද. පෙරනිමි මූලපද සැමවිටම අදාළ වේ.").

මෙම පිටුව පෙරනිමි ලැයිස්තුව, හඳුනාගැනීමේ ප්රවාහය, එහි විෂය පථය, අභිරුචි
මූලපද ආරක්ෂිතව එක් කරන ආකාරය සහ සලකුණු කළ සම්බන්ධතාවක් ප්රතිසාධනය කරන ආකාරය
ලේඛනගත කරයි. අවසන් තත්ත්වයම ප්රත්යස්ථතා ආකෘතියේ කොටසකි — "අවසන් තත්ත්ව"
සඳහා [RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) බලන්න.

**සත්යයේ මූලාශ්රය:** `open-sse/services/accountFallback.ts`
(`ACCOUNT_DEACTIVATED_SIGNALS`, `getMergedBannedSignals()`, `isAccountDeactivated()`),
සහ අවසන් නොවන සත්යාපන පන්තිය
(`ACCOUNT_VERIFICATION_REQUIRED_SIGNALS` / `isAccountVerificationRequired()`) හා එය භාවිත කරන
403 ශාඛාව සඳහා `open-sse/services/errorClassifier.ts`.

### තහනමක් නොවේ: ක්රියාකරුට ක්රියාමාර්ග ගත හැකි සත්යාපන විමසුම්

`verify your account to continue` යන්න පෙර ඉහත ලැයිස්තුවේ **තිබුණි**. එය තහනම්
සංඥාවක් නොවන අතර දැන් `ACCOUNT_VERIFICATION_REQUIRED_SIGNALS` තුළ පවතී; එය සම්බන්ධතාව
අවසන් කිරීම වෙනුවට ප්රතිසාධනය කළ හැකි `PROJECT_ROUTE_ERROR` ලෙස වර්ගීකරණය කරයි.

- `ACCOUNT_VERIFICATION_REQUIRED_SIGNALS` — **අවසාන නොවේ**; ක්රියාකරු ඉහළ මට්ටමේ
  සේවාව තුළ ගිණුම නැවත සත්යාපනය කළ යුතුය. `open-sse/services/errorClassifier.ts`
  තුළ පවතී (අනෙක් දෙක `accountFallback.ts` තුළ පවතී). ඉහත කොටස බලන්න.

සටහන: **`rate limit`** / `429` වැනි පොදු තාවකාලික වාක්ය ඛණ්ඩ
අනුපාත-සීමා / සම්බන්ධතා-සිසිලන මාර්ගයෙන් හසුරුවන අතර ඒවා තහනම් සංඥා **නොවේ**.

## හඳුනාගැනීමේ ප්රවාහය

```
upstream දෝෂ ප්රතිචාරය
  → body තන්තුවක් බවට පත් කර කුඩා අකුරුවලට හැරවීම
  → isAccountDeactivated(body): getMergedBannedSignals().some(sig => body.includes(sig))   [උපතන්තු ගැළපීම]
  → ගැළපීමක් තිබේද?
      → සම්බන්ධතාවේ testStatus = "banned"      (ස්ථිරයි — වසර 1ක cooldown එකක්, කිසිවිටෙක ස්වයංක්රීයව ප්රතිසාධනය නොවේ)
      → `autoDisableBannedAccounts` සැකසුම සක්රිය නම් සහ `autoDisableBannedScope`
        තුළ මෙම සම්බන්ධතාව ඇතුළත් නම් (`all`, හෝ OAuth/cookie/session සඳහා `subscription`)
        → isActive = false ද වේ. පරාසය
        `subscription` වන විට පෙරගෙවුම් API යතුරු සක්රියව පවතී.
      → ගිණුම් තේරීමේදී සම්බන්ධතාව මඟ හරිනු ලැබේ (සංයුක්ත QUOTA_BLOCKING තත්ත්ව)
```

- ගැළපීම යනු ප්රතිචාර **body** මත සිදු කරන **අක්ෂරවල විශාල/කුඩා බව නොසලකන උපතන්තු**
  සෙවුමකි (`isAccountDeactivated`, `accountFallback.ts`).
- තහනම්-සංඥාවක් සහිත body එකක් තිබේ නම්, **ඕනෑම
  HTTP තත්ත්වයකදී** ස්ථිර `banned` අවසන්කරණය ක්රියාත්මක වේ (`markAccountUnavailable` → `checkFallbackError` හරහා). වඩා
  පටු **`deactivated`** ලේබලය (සම්බන්ධතාවට අමතර
  API යතුරු නොමැති විට `isActive=false`) inline `chatCore.ts` මාර්ගය මඟින් **HTTP 401 / 403** මත ලියනු ලැබේ
  (`classifyProviderError` → `ACCOUNT_DEACTIVATED` හරහා වර්ගීකරණය කරයි). එහෙත්
  `markAccountUnavailable()` මාර්ගය, එම `ACCOUNT_DEACTIVATED` සංඥාව සඳහා
  (`resolveTerminalConnectionStatus` හරහා) _වෙනස්_ අවසන් තත්ත්වයක් —
  **`expired`** — ලියන බැවින්, ප්රතිචාරය හසුරුවා ඇත්තේ කුමන මාර්ගයෙන්ද යන්න අනුව එම
  තහනම `deactivated` හෝ `expired` ලෙස දිස්විය හැක. (පැරණි
  කේත සටහනෙහි "401 body එකක මෙම තන්තු අඩංගු වූ විට" යැයි සඳහන් වේ — එය
  වත්මන් හැසිරීම සම්පූර්ණයෙන් විස්තර නොකරයි.)
- අවසන් තත්ත්ව පෙරහන් කරන සෑම ස්ථානයකදීම `banned` සම්බන්ධතාවක් තේරීමෙන්
  බැහැර කරයි (`isTerminalConnectionStatus`, සංයුක්ත `QUOTA_BLOCKING_CONNECTION_STATUSES`).

## විෂය පථය — පරිලෝකනය කරනු ලබන සපයන්නන්

**සියලුම සපයන්නන්.** සෑම අසාර්ථක upstream ඉල්ලීමක්ම ගලා යන පොදු දෝෂ-හැසිරවීමේ නල මාර්ගය තුළ මෙම පරීක්ෂාව ක්රියාත්මක වේ — එය OAuth/දායකත්ව scraper වලට **පමණක්** සීමා කර නැත. ප්රතිඵලයක් ලෙස ලැබෙන අවසාන තත්ත්වය අදාළ වන්නේ එක් එක් **සම්බන්ධතාවයට** මිස එක් එක් සපයන්නාට නොවේ.

එසේ වුවද, ඇතුළත් කර ඇති _strings_ සැබෑ තහනම් වීමේ අවදානමක් සහිත දායකත්ව/OAuth සපයන්නන් (ChatGPT Web Codex, Claude Web, Codex, Muse Spark, Antigravity) කෙරෙහි ඉලක්ක කර ඇත. API-key සපයන්නෙකුගේ දෝෂ body එකෙහි එම උපපෙළවලින් එකක් වචනාර්ථයෙන් අඩංගු වුවහොත් පමණක් එම සපයන්නා detector එක සක්රිය කරයි.

`autoDisableBannedScope` (`all` | `subscription`, පෙරනිමිය `all`) ගැළපීමක් නිසා `isActive=false` ලෙසද වෙනස් කළ යුතුද යන්න පාලනය කරයි. `subscription` යන්නෙන් අදහස් වන්නේ login-ආකාරයේ seats (web-cookie sessions ඇතුළුව ගෙවූ දායකත්ව සහ නොමිලේ ගිණුම්) වේ. එය prepaid API keys සඳහා තවමත් `testStatus=banned` ලෙස සටහන් කරන නමුත් ඒවා routing pool එකේ තබයි. දිගුකාලීන සැලසුම එක් එක් සපයන්නා සහ එක් එක් ගිණුම සඳහා override එකකි; global enum එක එහි පළමු ක්රියාත්මක කිරීමයි.

## අභිරුචි තහනම් මූලපද

**Security → Banned Keywords** තුළ මූලපද එක් කරන්න හෝ ඉවත් කරන්න (`PATCH /api/settings` හරහා global `customBannedSignals` සැකසුම ලෙස ස්ථිරව සුරකිනු ලැබේ). ඒවා ඇතුළත් කර ඇති ලැයිස්තුවට **එක් කරනු ලැබේ** — කිසි විටෙකත් එය ප්රතිස්ථාපනය නොකරයි — තවද save කිරීමේදී (සහ startup අවස්ථාවේදී) `setCustomBannedSignals()` හරහා hot-reload වේ. සෑම මූලපදයක්ම අක්ෂර 200කට සීමා වේ; array එකේ දිගට සීමාවක් නොමැත.

**⚠ වැරදි ධනාත්මක ප්රතිඵලවල අවදානම — නිශ්චිත වාක්ය ඛණ්ඩ තෝරන්න.** හඳුනාගැනීම සිදු වන්නේ සම්පූර්ණ response body එක මත කරන raw substring ගැළපීමක් ලෙස වන අතර, ගැළපීමක් **ස්ථිර** වේ (වසර 1ක cooldown එකක්, අතින් ප්රතිසාධනය කිරීම). පුළුල් මූලපදයකට සම්පූර්ණයෙන්ම සෞඛ්ය සම්පන්න සම්බන්ධතාවයක් තහනම් කළ හැක:

- **නරක:** `quota`, `limit`, `error`, `denied` — තාවකාලික දෝෂ බොහොමයක දක්නට ලැබේ.
- **හොඳ:** සම්පූර්ණ තහනම් වාක්ය, උදා. `your account has been suspended for`,
  `account permanently banned`, `violation of our terms`.

සැබෑ තහනමකදී සපයන්නා ලබා දෙන, අපැහැදිලි නොවන දිගම වාක්ය ඛණ්ඩය භාවිත කිරීමට ප්රමුඛත්වය දෙන්න. සැකයක් ඇති විට, පළමුව සම්බන්ධතාවයේ `lastError` නිරීක්ෂණය කර, පසුව එහි නිවැරදි වචන යෙදුම එක් කරන්න.

## සලකුණු කළ සම්බන්ධතාවයක් ප්රතිසාධනය කිරීම

අවසාන `banned` / `deactivated` තත්ත්ව **කිසි විටෙකත් ස්වයංක්රීයව ප්රතිසාධනය නොවේ** (ඒවා proactive-recovery tick එකෙන් බැහැර කර ඇත — ස්වයංක්රීයව ප්රතිසාධනය වන්නේ `unavailable` cooldown පමණි). ක්රියාකරු ඒවා පැහැදිලිව ඉවත් කළ යුතුය:

1. **සම්බන්ධතාවය නැවත පරීක්ෂා කරන්න** — dashboard එකේ **Test** ක්රියාව
   (`POST /api/providers/{id}/test`); සාර්ථක probe එකක් `testStatus` නැවත
   `active` ලෙස සකසා දෝෂ fields හිස් කරයි.
2. **නැවත සත්යාපනය කරන්න / අක්තපත්ර සංස්කරණය කරන්න** — OAuth සපයන්නන් සඳහා, login
   / refresh ප්රවාහය නැවත ක්රියාත්මක කරන්න; provider create/import routes මගින් `isActive = true` ලෙස සකසයි.
3. **සම්බන්ධතාවය නැවත සක්රිය කරන්න** — auto-disable මගින් `isActive = false` ලෙස සකසා ඇත්නම්
   (`all` විෂය පථය, හෝ OAuth/cookie/session සම්බන්ධතාවයක් සඳහා `subscription`),
   ගිණුම නිවැරදි කිරීමෙන් පසු එය නැවත on කරන්න.

වෙනම "clear ban flag" බොත්තමක් නොමැත — ප්රතිසාධනය යනු නැවත පරීක්ෂා කිරීම, නැවත සත්යාපනය කිරීම හෝ නැවත සක්රිය කිරීම වන අතර, එය
[RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) හි පොදු අවසාන-තත්ත්ව රීතියට අනුකූල වේ.

## Probe හුදකලා කිරීම (model test-all)

`runAsProbe` තුළ ක්රියාත්මක කරන ලද **probe-origin failure** එකක් (model test-all / health-check dispatches) කිසි විටෙකත් pool එකෙන් සම්බන්ධතාවයක් ඉවත් නොකරයි (#9817): එය **දෘශ්යතාව සඳහා සටහන් කරනු ලැබේ** (`last_error`, `last_error_type`, `error_code`,
`last_error_at`) නමුත් **සෑම** routing mutation එකක්ම මඟ හරියි — cooldowns, අවසාන තත්ත්ව (`banned` / `deactivated` / `credits_exhausted`), එක් එක් model සඳහා lockouts,
provider circuit breaker එක, මිනිත්තු 5 quota cache එක, OAuth token refresh
සහ auto-disable. අක්රිය කිරීමක් සිදු කරන්නේ සැබෑ request-path failure එකක් පමණි. සටහන් කළ දෝෂය නිසා සලකුණු කළ ගිණුමක් traffic සැපයීම දිගටම සිදු කරන අතරතුර dashboard එකේ දෘශ්ය වේ.

එකම තීරණ ස්ථානය වන්නේ `shouldIsolateProbeFailures()`
(`src/shared/utils/probeOrigin.ts`) වන අතර, probe-origin failure එකකින් routing state වෙනස් කළ හැකි **සෑම** ස්ථානයක්ම එය විමසයි:

- `markAccountUnavailable` (`auth.ts`) — සටහන් කිරීම පමණි (`lastError` raw text,
  `lastErrorType`, `errorCode`, `lastErrorAt`; selection-time auto-decay එක ක්රියාත්මක කර සටහන මකා දමන බැවින්, හිතාමතාම `backoffLevel` **නොමැත**)
- `maybeAutoDisableBannedAccount` — auto-disable නොකරයි
- `chatCore` — FORBIDDEN, ACCOUNT_DEACTIVATED, QUOTA_EXHAUSTED (සටහන් කිරීම පමණි,
  අවසාන `credits_exhausted` නොමැත), GEO_BLOCKED (පැය 24ක exclusion නොමැත),
  MODEL_NOT_FOUND (`lockModel` නොකරයි), codex 429 account-rotation failover එක
  (`markCodexScopeRateLimited` නොකරයි, ස්ථිරව සුරකින `rate_limited_until` නොමැත,
  session-affinity clear කිරීමක් නොමැත), `persistCodexQuotaState` (quota-state ලිවීමක් නොමැත,
  cache invalidation නොමැත), `recordKeyHealthStatus` (key-health rotator එක
  වෙනස් නොකරයි)
- OAuth refresh — executor base එකේ proactive refresh යන දෙකම
  (`base.ts` `execute()`, refresh-token rotation භාවිත නොවේ) සහ
  `chatCore` හි reactive 401/403 path එක (`expired` අක්රිය කිරීමක් නොමැත)
- `chat.ts` — provider circuit breaker එක සහ මිනිත්තු 5 quota cache එක
  (`markAccountExhaustedFrom429`) කිසි විටෙකත් degraded නොවේ

සටහන් කළ දෝෂය නිසා සලකුණු කළ ගිණුමක් traffic සැපයීම දිගටම සිදු කරන අතරතුර dashboard එකේ දෘශ්ය වේ. සටහන: සැබෑ path එකේ `slice(0,100)` කෙටි කිරීමට වෙනස්ව, probe සටහන **raw** (කපා නොදැමූ) දෝෂ පෙළ ගබඩා කරයි.

test-all නඩත්තු මෙවලමක් ලෙස භාවිත කරන ක්රියාකරුවන්ට පහත ඕනෑම ක්රමයකින් ඓතිහාසික හැසිරීම (probe එක සැබෑ generation එකක් ලෙස ගණන් ගැනීම) ප්රතිස්ථාපනය කළ හැක:

- `probeCanDisable` සැකසුම (`{"probeCanDisable": true}` සමඟ
  `POST /api/settings`, හෝ සෘජු `key_value` DB සංස්කරණයක්), හෝ
- feature flag **`PROBE_CAN_DISABLE=true`** (env හෝ DB override; සැකසුමට වඩා ප්රමුඛ වේ).

Fail-safe: flag හෝ settings lookup එක දෝෂයක් නිකුත් කළහොත්, isolation එක ON ලෙසම පවතී.
