## දළ විශ්ලේෂණය

සියලුම OmniRoute කළමනාකරණ API මාර්ග ආරක්ෂණ මට්ටම් තුනෙන් එකකට වර්ගීකරණය කර ඇත. වර්ගීකරණය ස්ථිතික වන අතර, එය `src/server/authz/routeGuard.ts` තුළ අර්ථ දක්වා ඇති අතර වෙනත් ඕනෑම සත්යාපන ශාඛාවක් ක්රියාත්මක වීමට පෙර ඇගයීමට ලක් කෙරේ.

## මට්ටම්

### මට්ටම 1 — LOCAL_ONLY

**බලාත්මක කරන්නේ:** `isLocalOnlyPath(path)` → loopback සත්කාරක පරීක්ෂාව  
**මඟහැරීම:** පෙරනිමියෙන් කිසිවක් නැත. ඉල්ලීමෙහි `manage` විෂය පථය සහිත වලංගු API යතුරක් ඇති විට `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` තුළ ඇති මාර්ග සඳහා පමණක් සීමිත ව්යතිරේකයක් ඇත ([කළමනාකරණ විෂය පථ ව්යතිරේකය](#manage-scope-carve-out) බලන්න).

මෙම මාර්ග අනු ක්රියාවලි ආරම්භ කිරීම හෝ ධාවන කාල කේතය ක්රියාත්මක කිරීම සිදු කරයි. ඒවා loopback නොවන ගමනාගමනයට නිරාවරණය කිරීමෙන් වලංගු JWT එකක් ලබාගත් ප්රහාරකයෙකුට (උදා., Cloudflared/Ngrok උමඟක් හරහා) ක්රියාවලි ආරම්භ කිරීම ක්රියාත්මක කිරීමට හැකි වනු ඇත — මෙය දන්නා CVE පන්තියකි ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj යනු කුමක්ද (ප්රහාර පන්තිය):** කළමනාකරණ/නියෝජිත සේවාදායකයක් අනු ක්රියාවලියක් (`npm install`, `node`, බ්රවුසරයක්, ප්රොක්සියක්, `git`, `tar`, …) දියත් කරන අන්ත ලක්ෂ්යයක් නිරාවරණය කරයි. එම අන්ත ලක්ෂ්යය සත්කාරකයෙන් පිටත සිට ළඟා විය හැකි නම් — ක්රියාකරු OmniRoute nginx/Cloudflare/Tailscale උමඟක් පිටුපස තැබීම සහ JWT එකක් කාන්දු වීම නිසා හෝ සත්යාපනය වැරදි ලෙස වින්යාස කර තිබීම නිසා — ප්රහාරකයාට "API එකක් ඇමතීම" යන්න "සත්කාරකය මත විධානයක් ධාවනය කිරීම" බවට පත් කළ හැකිය (දුරස්ථ කේත ක්රියාත්මක කිරීම). OmniRoute මෙය වළක්වන්නේ අනු ක්රියාවලි ආරම්භ කළ හැකි සෑම මාර්ගයකම **කිසිදු කොන්දේසියකින් තොරව, ඕනෑම සත්යාපන පරීක්ෂාවකට පෙර loopback සත්කාරක පරීක්ෂාවක්** බලාත්මක කිරීමෙනි: උමඟක් හරහා කාන්දු වූ ටෝකනයකට වුවද අනු ක්රියාවලි ආරම්භ කිරීමට ළඟා විය නොහැක.

**සම්පූර්ණ LOCAL_ONLY කට්ටලය.** බලධාරී මූලාශ්රය වන්නේ `src/server/authz/routeGuard.ts` තුළ ඇති `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ය; පහත වගුව වත්මන් තත්ත්වය පිළිබිඹු කරයි. `check-route-guard-membership` ද්වාරය අනු ක්රියාවලි ආරම්භ කළ හැකි උපසර්ග යටතේ ඇති සෑම `route.ts` එකක්ම ලැයිස්තුගත කරන අතර, ඒවායින් එකක් හෝ local-only ලෙස වර්ගීකරණය කර නොමැති නම් CI අසාර්ථක කරයි.

Tunnel, Tailscale, Ngrok) පිටුපස ධාවනය කරන්නේ නම්, loopback පරීක්ෂාව තවමත් ඉහත
ආරම්භ කිරීමේ හැකියාව ඇති මාර්ග ආරක්ෂා කරයි — සේවාදායක ලිපිනය loopback නොවන ඉල්ලීමක්,
`403 LOCAL_ONLY` සමඟ **සත්යාපනය ක්රියාත්මක වීමට පෙර** ප්රතික්ෂේප වන බැවින්, කාන්දු වූ JWT එකකට
ආරම්භ කිරීමක් වෙත ළඟා විය නොහැක. ක්රියාකරුගේ වගකීම් දෙකක් තවමත් පවතී:

- **සේවාදායක IP ලිපිනය loopback ලෙස ව්යාජව සකසා 403 දෝෂයක් "නිවැරදි" නොකරන්න.**
  `X-Forwarded-For: 127.0.0.1` සැකසීම හෝ මූලාශ්ර ලිපිනය
  loopback ලෙස නැවත ලියන proxy එකක් භාවිත කිරීම, මෙම ස්තරය වසා දමන RCE පන්තියම නැවත විවෘත කරයි.
  උපකරණ පුවරුව/API එක proxy එක හරහා නිරාවරණය කරන්න — ආරම්භ කිරීමේ හැකියාව ඇති මාර්ග කිසිවිටෙකත් නිරාවරණය නොකරන්න.
- **කළමනාකරණ-විෂයපථ ව්යතිරේකය අවමව තබා ගන්න.** ව්යතිරේකය ලබා දිය හැක්කේ `/api/mcp/` සඳහා පමණක් වන අතර,
  ඒ සඳහා `manage`-විෂයපථ API යතුරක් තිබිය යුතුය. `SPAWN_CAPABLE_PREFIXES` කිසිවිටෙකත්
  ව්යතිරේක ලැයිස්තුවට එක් කළ නොහැක — zod schema එක ඒවා ප්රතික්ෂේප කරන අතර
  ධාවන වේලාවේදී `isLocalOnlyBypassableByManageScope` ඒවා ප්රතික්ෂේප කරයි (ගැඹුරු-ආරක්ෂණය);
  උපකරණ පුවරුවේ "ව්යතිරේකය ලබා දිය හැකි ලෙස සැකසිය නොහැක" යන්නෙන් අදහස් වන්නේ මෙයයි. `/api/providers/` යටතේ ඇති
  ගතික-ඛණ්ඩ සහ ස්ථිතික-මාර්ග ආරම්භ කිරීමේ හැකියාව ඇති මාර්ග (උදා. `/login`,
  `/refresh-cursor`) ආවරණය කරන්නේ
  `src/shared/constants/spawnCapablePrefixes.ts` තුළ ඇති regex-පාදක `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` සහායකය මඟින් මිස සරල
  `SPAWN_CAPABLE_PREFIXES` අරාව මඟින් නොවේ — ඒවා හසු කර ගැනීමට සරල අරාවට
  සම්පූර්ණ `/api/providers/` උපසර්ගයම ආවරණය කිරීමට සිදු වන අතර, එය දුරස්ථ උපකරණ පුවරු විසින් provider CRUD සඳහා
  නීත්යානුකූලව භාවිත කරන මාර්ග වෘක්ෂයක් අතිශයින් පුළුල් ලෙස සීමා කරනු ඇත.

**ප්රවේශය විගණනය කිරීම** — බාහිර host එකකින් කිසිවක් මෙම මාර්ග වෙත ළඟා නොවන බව තහවුරු කිරීමට:

- `/dashboard/settings/security` හි **Authorization Inventory** විවෘත කරන්න: එය සජීවී LOCAL_ONLY උපසර්ග ලැයිස්තුව, මඟහැරිය හැකි උපසර්ග, සහ සම්පාදන-කාලීනව ක්රියාවලි බිහි කළ හැකි ("මඟහැරිය හැකි ලෙස සැකසිය නොහැකි") කට්ටලය පෙන්වයි.
- ඉහත උපසර්ග loopback නොවන සේවාලාභී ලිපිනයක් සමඟ යුගල වී ඇති දැයි ඔබේ reverse-proxy / ප්රවේශ ලොග්වල Grep කරන්න. `403 LOCAL_ONLY` වෙනුවට `200` ලබා දුන් එවැනි ඕනෑම ප්රතිඵලයක් යනු proxy එක සැබෑ සේවාලාභී IP ලිපිනය සඟවන බවයි — proxy එක නිවැරදි කරන්න.
- මෙම මාර්ගවලින් එකක් සඳහා OmniRoute හි ලොග්වල ඇති `403 LOCAL_ONLY` යනු ආරක්ෂකය අපේක්ෂිත පරිදි ක්රියා කරන බවයි; එය යටපත් කළ යුතු දෝෂයක් නොවේ.

### ස්තරය 2 — ALWAYS_PROTECTED

**බලාත්මක කරන්නේ:** `isAlwaysProtectedPath(path)` → `requireLogin=false` මඟහැරීම නොසලකා හරී

මෙම මාර්ග විනාශකාරී හෝ ආපසු හැරවිය නොහැකි ඒවාය. "මුරපද-රහිත"
ස්ථාපනයකදී ඒවාට ඉඩ දීමෙන් අදහස් වන්නේ එකම LAN එකේ සිටින ඕනෑම අයෙකුට දත්ත සමුදාය මකා දැමීමට හෝ

### නව ස්ථාපනයක bootstrap කිරීම loopback වෙත පමණයි — `Host` මත නොව, සැබෑ peer අනුවයි

කළමනාකරණ මුරපදයක් වින්යාස කර නොමැති විට (සහ `INITIAL_PASSWORD` නොමැති විට),
`src/shared/utils/apiAuth.ts` හි `isAuthRequired()` නිර්නාමික bootstrap ප්රවේශය විවෘතව තබන්නේ **loopback peers සඳහා පමණි**.
විශ්වාසදායක peer සංඥාවලින්, පහත අනුපිළිවෙළට, loopback තීරණය කෙරේ: ටෝකනයෙන් මුද්රා තැබූ සැබෑ TCP peer
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ප්රතිපත්තියට පෙනෙන දේ), නලමාර්ගයේම
`AUTHZ_HEADER_PEER_LOCALITY` තීන්දුව (මාර්ග හසුරුවන්නන්ට පෙනෙන දේ, `OMNIROUTE_PEER_STAMP_TOKEN` සකසා ඇති විට පමණක් විශ්වාස කෙරේ),
හෝ සෘජුව අමතන්නන් සඳහා සැබෑ socket peer එකක්. `Host` /
`nextUrl.hostname` කිසිවිටෙක සලකා නොබලන අතර, පළමු මුරපදය ලිවීම
(`POST /api/settings/require-login`) සෑම ජාල peer එකකටම විවෘත කිරීම වෙනුවට එම සීමාව යටතේම පවතී
(GHSA-7pq4-8pvv-rx7r). `managementPolicy` එහිම `peerContext` තීන්දුව
පහළට පැහැදිලිව ලබා දෙයි; එබැවින් ORIGINAL (ඉවත් කිරීමට පෙර) ඉල්ලීමේ headers කිසිවිටෙක එය තීරණය නොකරයි.

### ස්තරය 3 — MANAGEMENT (පෙරනිමි)

අනෙකුත් සියලුම කළමනාකරණ මාර්ග. `requireLogin=false` වින්යාස කර නොමැති නම් සත්යාපනය අවශ්යයි.
CLI ටෝකනවලට මෙම මාර්ග සත්යාපනය කළ හැකිය (loopback + වලංගු HMAC).

## ඇගයීම් අනුපිළිවෙළ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → ඊළඟ පියවරට යන්න
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → ඉඩ දෙන්න (management_key)
     → එසේ නොමැති නම්                            → ප්රතික්ෂේප කරන්න 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → ඉඩ දෙන්න (system)
  3. hasValidCliToken(headers)?
     → ඉඩ දෙන්න (cli) [loopback + timingSafeEqual HMAC පරීක්ෂාව]
  4. isAlwaysProtectedPath(path) හෝ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ඉඩ දෙන්න (dashboard_session)
     → මඟහැරිය නොහැකි මාර්ගයක manage-scope Bearer තිබේද?
        → ඉඩ දෙන්න (management_key)
     → ප්රතික්ෂේප කරන්න 401/403
  5. requireLogin=false?
     → ඉඩ දෙන්න (anonymous)
```

LOCAL_ONLY මාර්ගයක් සපුරාලිය හැකි එකම සත්යාපිත මාර්ගය වන්නේ පියවර 1 හි manage-scope ශාඛාවයි; කල් ඉකුත් වූ DB එකක් නිහඬව "ප්රතික්ෂේප කරන්න" වෙත පහත හෙළීම වැළැක්වීම සඳහා auth-backend අසාර්ථකත්ව ප්රකාරය 403 නොව 503 ආපසු ලබා දෙයි.

## නව spawn-හැකියාව සහිත මාර්ගයක් එක් කිරීම

1. `src/server/authz/routeGuard.ts` හි `LOCAL_ONLY_API_PREFIXES` වෙත මාර්ග උපසර්ගය එක් කරන්න
2. නව උපසර්ගය සඳහා `isLocalOnlyPath()` true ලබා දෙන බව තහවුරු කරන පරීක්ෂණයක් `tests/unit/authz/routeGuard.test.ts` වෙත එක් කරන්න
3. **මෙම පියවර කිසිවිටෙක මඟ නොහරින්න** — `CLAUDE.md` හි දැඩි රීතිය #15 බලන්න
4. තීරණය කරන්න: මෙම මාර්ගය `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` තුළත් ඇතුළත් විය යුතුද?
   පෙරනිමි පිළිතුර **නැත** යන්නයි. මාර්ගය manage-scope දරන්නෙකුට නිරාවරණය කිරීමට ආරක්ෂිත නම් පමණක් තෝරා ඇතුළත් කරන්න (එනම්, අත්තනෝමතික පරිශීලක-පාලිත කේත spawn නොකරන්නේ නම්).

3. ඉල්ලීම් ආකාර හතරම සඳහා `tests/unit/authz/management-policy.test.ts` හි ආවරණය එක් කරන්න: Bearer නැත (403), manage Bearer (ඉඩ දෙන්න), manage නොවන Bearer (403), සහ manage Bearer එකක් සමඟ වුවද `/api/cli-tools/runtime/*` දැඩි-loopback ලෙස පවතින බව තහවුරු කරන එක් එක් උපසර්ගයට අදාළ ප්රතිගමන පරීක්ෂණය.
