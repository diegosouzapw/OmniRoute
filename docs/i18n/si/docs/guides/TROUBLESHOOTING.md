### නොමිලේ සපයන්නන්ගේ අනුපාත සීමා කිරීම (429 / 400 / 401)

**රෝග ලක්ෂණය**: නොමිලේ/සත්යාපනය අවශ්ය නොවන සපයන්නන් (opencode, auggie, ආදිය) සමඟ `model: "auto"` භාවිත කරන විට, පිළිතුරු වෙනුවට වරින් වර `HTTP 429`, `400`, හෝ `401` ලැබේ. සුළු මොහොතකට පසු එකම prompt එක නැවත උත්සාහ කළ විට ඉල්ලීම් සාර්ථක වන නමුත්, පළමු අසාර්ථක වීමේදීම ස්වයංක්රීයකරණය (cron කාර්යයන්, agents, scripts) බිඳ වැටේ.

**මූලික හේතුව**: ස්වාධීන අසාර්ථක වීමේ ආකාර තුනක් එකට එකතු වේ:

1. **සපයන්නාගේ අනුපාත සීමාව (`429`)**: නොමිලේ මට්ටම්වලට එක් කාල කවුළුවකට අදාළ කෝටාවක් බලාත්මක කළ හැක. සමාන්තර ඇමතුම් රැල්ලක් එය අවසන් කරන බැවින්, කාල කවුළුව යළි සැකසෙන තෙක් ඊළඟ ඉල්ලීම ප්රතික්ෂේප වේ.
2. **Passthrough තුළ බිඳුණු model එක (`400`/`401`)**: `auto/*` pools තුළ catalog එකේ ලියාපදිංචි වී ඇති නමුත් සක්රිය අක්තපත්ර නොමැති `opencode` passthrough models ඇතුළත් විය හැක (උදා. `oc/north-mini-code-free` → `401`). Auto-router එකක් උත්සාහ කර අසාර්ථක වන අතර, fallback ක්රියාත්මක වීමට පෙර දෝෂය ඉදිරියට පැතිරේ.
3. **සමකාලීනතා වර්ධනය (බර යටතේ `429`)**: agent/cron sessions කිහිපයක් එකවර `auto` වෙත ප්රවේශ වන විට, සමස්ත ඉල්ලීම් අනුපාතය නොමිලේ සපයන්නන්ට දරාගත හැකි මට්ටම ඉක්මවන බැවින්, වලංගු ඇමතුම් පවා අනිසි භාවිතයක් ලෙස සලකුණු වේ.

**තහවුරු කළ විසඳුම (ප්රජාව විසින් වාර්තා කරන ලදී, 2026-08-10)**: නොමිලේ මට්ටමේ අස්ථාවරත්වය හේතුවෙන් ක්රියාවලිය බිඳ වැටීම වෙනුවට rotation, concurrency සහ fallback මඟින් එය හසුරුවන ලෙස පරිසර විචල්ය තුනක් සකසන්න:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 මත වෙනත් model/provider එකකට මාරු වන්න (බිඳුණු passthrough models මඟ හරියි)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # heavyweight ඇතුළත් කිරීමේ පැහැදිලි උපරිමය (පෙරනිමියෙන් සකසා නැත: ඉල්ලීම්-ගණන සීමාවක් නැත, පහත සටහන බලන්න)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ක්ෂණිකව නැවත උත්සාහ කළ හැකි 503 එකක් වෙනුවට heavyweight ධාරිතාව සඳහා වඩා දිගු සීමාකළ රැඳී සිටීමක්
```

මේවා OmniRoute ක්රියාවලි පරිසරය තුළ සකසන්න (daemon එක තුළ, උදා. LaunchAgent plist හෝ `systemctl edit` හරහා), ඉන්පසු OmniRoute නැවත ආරම්භ කරන්න. Rotation flag එක තනිවම වැඩිම බලපෑමක් ඇති පාලකයයි: එය දැඩි අසාර්ථක වීමක්, pool එකේ සෞඛ්ය සම්පන්න සපයන්නෙකුට එරෙහිව සිදු කරන විනිවිද පෙනෙන නැවත උත්සාහයක් බවට පරිවර්තනය කරයි.

**සටහන**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` මඟින් එකවර ධාවනය වන heavyweight — දිගු-context — ඉල්ලීම් ගණන සීමා කරයි; මෙම සීමාව ඇතුළත් කිරීමේ දොරටුවක් මිස සපයන්නාගේ අනුපාත සීමාකාරකයක් නොවේ. **#503-fanout යාවත්කාලීනය:** මෙම var එක තවදුරටත් පෙරනිමියෙන් සකසා නැත (දැන් එය ඉහත පරිදි පැහැදිලිව වින්යාස කළ විට පමණක් බැඳේ) — ඒ වෙනුවට heavyweight ඇතුළත් කිරීම, host එකේ සැබෑ මතක උපරිමයට අනුව ස්වයංක්රීයව පරිමාණය වන, ස්වයංක්රීයව ව්යුත්පන්න කළ byte budget එකක් (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) මඟින් පාලනය වේ. එබැවින් නව deployment එකකදී මෙම var එක කිසිසේත් සකස් නොකරම `503 chat_admission_busy` ප්රතික්ෂේප කිරීම් බෙහෙවින් අඩුවෙන් දැකිය යුතුය; මෙහි එය පැහැදිලිව සැකසීම තවමත් ලේඛනගත කර ඇති ආකාරයටම ක්රියා කරයි. පැහැදිලි byte-budget overrides, 8 MiB–2 GiB පරාසයට සීමා වේ. `413 body_exceeds_budget` තාවකාලික නොවේ: එම byte budget එක වැඩි කරන්න, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` අඩු කරන්න, හෝ ක්රියාවලියේ මතක උපරිමය වැඩි කරන්න. `inflight_bytes_budget` shed එකක් තාවකාලික සම්පත් තරගයක් වන අතර නැවත උත්සාහ කළ හැක. එක් එක් සපයන්නා සඳහා වන අනුපාත සීමා කිරීම (`open-sse/services/rateLimitManager.ts`), `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, සහ `RATE_LIMIT_AUTO_ENABLE` මඟින් වෙන වෙනම පාලනය වේ — `.env.example` බලන්න.

**එය ක්රියා කළ බව තහවුරු කරන්නේ කෙසේද**: ඔබේ agent/cron එක ඉක්මනින් පිට පිට දෙවරක් ධාවනය කර, අවස්ථා දෙකම සාර්ථක වන බව තහවුරු කරන්න. නිවැරදි කිරීමට පෙර, දෙවන ධාවනය සාමාන්යයෙන් `429`/`401` දෝෂයක් නිකුත් කරයි. නිවැරදි කිරීමෙන් පසු, අසාර්ථක වීම් (තිබේ නම්) විනිවිද පෙනෙන ලෙස නැවත උත්සාහ කරනු ලබන අතර ඇමතුම සම්පූර්ණ වේ. ඔබට `curl /monitoring/health` ද ධාවනය කර, provider සම්බන්ධතාවල `rateLimitedUntil` ක්ෂේත්රය සහ බලපෑමට ලක් වූ providers සඳහා `circuitBreakers.providerBreakers[].state` නිරීක්ෂණය කළ හැක — state එක `CLOSED`, `DEGRADED`, `OPEN`, හෝ `HALF_OPEN` යන ඒවායින් එකකි (`src/shared/utils/circuitBreaker.ts` බලන්න), දිගින් දිගටම අසාර්ථක වන provider එකක් reset කාල කවුළුව මඟින් probe එකකට ඉඩ දීමට පෙර `CLOSED → DEGRADED → OPEN` ලෙස මාරු වේ (`HALF_OPEN`).

**ඔබ තවමත් 429 දකින්නේ නම්**: එම provider සඳහා ක්රියාකාරී account එක සැබවින්ම එහි _quota_ අවසන් කර ඇත (rate එක පමණක් නොවේ). OmniRoute dashboard → Providers → Accounts තුළ එම provider සඳහාම දෙවන account එකක් එක් කරන්න, නැතහොත් වෙනත් නොමිලේ provider එකක් (උදා. `routeway`, `auggie`) ද මිශ්රව භාවිත කරන්න. Rotation උපකාර වන්නේ තාවකාලික rate/400/401 ගැටලු සඳහා පමණි; quota එක සම්පූර්ණයෙන් අවසන් වී ඇත්නම් දෙවන credential එකක් හෝ වෙනත් provider එකක් අවශ්ය වේ.

## npm install අනතුරු ඇඟවීම් (ERESOLVE / peer / deprecated)

ඔබ `npm install -g omniroute` ක්රියාත්මක කරන විට, `npm warn ERESOLVE`, peer-dependency දැනුම්දීම් සහ `deprecated` පණිවිඩ වැනි අනතුරු ඇඟවීම් විශාල ප්රමාණයක් දැකිය හැක. **මේවා අපේක්ෂිත සහ හානිකර නොවන දේවල් වේ.** ප්රතිදානයේ `added <N> packages` දිස්වන්නේ නම්, ඔබගේ ස්ථාපනය සාර්ථක වී ඇත.

peer-dependency නිරාකරණ අනතුරු ඇඟවීම් යටපත් කිරීමට, OmniRoute විසින් සහාය දක්වන පහත ස්ථාපන ආකාරය භාවිත කරන්න:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` යටපත් කරන්නේ `ERESOLVE` සහ peer-dependency දැනුම්දීම් පමණි. අභාවිත කිරීමේ දැනුම්දීම් තවදුරටත් දිස්වන්නේ ඒවා සංක්රාමී තෙවන පාර්ශ්ව පැකේජවලින් පැමිණෙන බැවිනි; ඒවා ස්ථාපනය අසාර්ථක වූ බවක් නොපෙන්වයි.

මෙම අනතුරු ඇඟවීම් පැමිණෙන්නේ OmniRoute විසින් පාලනය නොකරන තෙවන පාර්ශ්ව පැකේජවල යල් පැන ගිය peer-dependency පරාසයන්ගෙනි:

1. **`marked-terminal` හට `marked >=1 <16` අවශ්ය නමුත් `marked@18` හමු විය** — ප්රායෝගිකව හොඳින් ක්රියා කරයි; upstream peer පරාසය යල් පැන ගොස් ඇත.
2. **`deprecated prebuild-install@7.1.3`** — සංක්රාමී දේශීය ද්විමය ගොනු ලබාගැනීමේ උපකාරකයකි. pin කර ඇති `wreq-js` ප්රවාහන binding එක ස්ථාපනය කිරීමට මෙය
   භාවිත නොකරන අතර, web-cookie සපයන්නාගේ ප්රවාහන සැකසුම අසාර්ථක වූ බවක්ද
   මෙයින් නොපෙන්වයි.

**කිසිදු ක්රියාමාර්ගයක් අවශ්ය නොවේ** — upstream පැකේජ fork කිරීමකින් තොරව මෙම අනතුරු ඇඟවීම් සම්පූර්ණයෙන්ම නිහඬ කළ නොහැක.

## Gemini Web සහ Playwright Chromium

Gemini Web ඉල්ලීමක් Playwright Chromium ස්ථාපනය කර නොමැති බව සඳහන් පණිවිඩයක් සමඟ `503` ආපසු ලබා දෙන්නේ නම්,
npm පැකේජය තිබුණද browser binary එක නොමැත.
Playwright විසින් browser බාගැනීම් හිතාමතාම npm පැකේජ
ස්ථාපනයෙන් වෙන්ව තබන බැවින්, browser එක ස්ථාපනය කරන තෙක් මෙම ප්රතිචාරය අපේක්ෂිතය.

ගෝලීය npm ස්ථාපනයක් සඳහා, browser cache එක එම Playwright ස්ථාපනයටම අයත් වන ලෙස OmniRoute පැකේජයේ
නාමාවලියෙන් Chromium ස්ථාපනය කරන්න:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ස්ථාපනයෙන් පසු OmniRoute නැවත ආරම්භ කර, ඉන්පසු Gemini Web ඉල්ලීම නැවත උත්සාහ කරන්න. ඔබ
Docker image එකකින් OmniRoute ක්රියාත්මක කරන්නේ නම්, Chromium සහ එහි පරායත්තතා ඇතුළත් `-web` image එක (හෝ `runner-web`
build target එක) භාවිත කරන්න; base image එකෙහි
ඒවා අඩංගු නොවේ.

**මෙය සාවද්ය ධනාත්මක හඳුනාගැනීමකි. කිසිවක් ආසාදනය වී නොමැති අතර කිසිදු ක්රියාමාර්ගයක් අවශ්ය නොවේ.**

HTTP ඉල්ලීම් ලෙස පෙනෙන සබැඳි විශාල සංඛ්යාවක් අඩංගු සරල පෙළ/Markdown ගොනු සලකුණු කරන හියුරිස්ටික් ක්රමයක් Avast සහ AVG විසින් ක්රියාත්මක කරයි. OmniRoute හි `README.md`, npm පැකේජය තුළ ඇතුළත් කර බෙදාහරින බැවින් (එය `package.json` → `files` හි ලැයිස්තුගත කර ඇත), ගෝලීය ස්ථාපනයකදී එය `node_modules/omniroute/README.md` වෙත පැමිණේ — තවද එහි `http://localhost:20128/...` උදාහරණ ~15ක් (MCP HTTP/SSE අන්ත ලක්ෂ්ය, A2A `.well-known` URL සහ `curl` කොටස්) අඩංගු වේ. හියුරිස්ටික් ක්රමය සක්රිය කිරීමට එම සබැඳි ඝනත්වය ප්රමාණවත් වේ.

මෙය මෑතකදී පමණක් ආරම්භ වූයේ නම්: ගොනුවේ ස්වභාවය වෙනස් වී නැත. README හි අන්ත ලක්ෂ්ය වගුව පුළුල් වූ අතර (MCP HTTP + SSE + A2A එක් කරන ලදී) තවත් `curl` උදාහරණ ද එක් වූ බැවින්, එය සීමාව ඉක්මවා ගියේය.

මෙම ගොනුව ක්රියාත්මක කළ හැකි අන්තර්ගතයක් කිසිසේත් නොමැති අක්රිය ප්රලේඛනයකි. ඔබට එය නිරෝධායනයෙන් ආරක්ෂිතව ප්රතිසාධනය කළ හැක.

**කළ යුතු දේ:**

1. **දැනුම්දීම් නවත්වන්න** — ඔබේ ප්රතිවෛරසය තුළ ස්ථාපන නාමාවලිය බැහැර කරන්න (Avast: Settings → Exceptions), ඔබේ ගෝලීය `node_modules` මාර්ගය සහ/හෝ OmniRoute දත්ත නාමාවලිය (`~/.omniroute/`) එක් කරන්න.
2. **සාවද්ය ධනාත්මක හඳුනාගැනීම වාර්තා කරන්න** — <https://www.avast.com/false-positive-file-form.php>, නිරෝධායනය කළ `README.md` අමුණමින්. පාඨ ගොනුවකට සැපයුම්කරුගේ හියුරිස්ටික් ක්රමය අධික ලෙස ප්රතිචාර දැක්වීම මෙහි හේතුව වන බැවින්, සියලු දෙනාට උපකාර වන විසඳුම මෙයයි.

**අපගේ පැත්තෙන් මෙය "නිවැරදි" නොකරන්නේ ඇයි:** සියලු උදාහරණ `http://localhost` වන අතර, ස්වයං-අත්සන් කළ සහතිකවලින් ඇති වන අපහසුතා නොමැතිව localhost සඳහා `https` භාවිත කළ නොහැක. එක් සැපයුම්කරුවෙකුගේ හියුරිස්ටික් ක්රමය මඟහැරීමට ප්රලේඛනය විකෘති කිරීම, ස්කෑනරයක දෝෂයක් සතුටු කිරීම සඳහා සෑම පාඨකයෙකුටම අහිතකර වනු ඇත.

### Kaspersky විසින් Desktop යෙදුම `PDM:Trojan.Win32.Generic` ලෙස සලකුණු කිරීම

**මෙය හැසිරීම්මය හියුරිස්ටික් ක්රමයකින් ඇති වූ සාවද්ය ධනාත්මක හඳුනාගැනීමකි. කිසිවක් ආසාදනය වී නොමැත.** Kaspersky හි `PDM:` උපසර්ගයෙන් අදහස් වන්නේ, තීරණය පැමිණෙන්නේ එහි Proactive Defense Module (System Watcher) වෙතින් බවයි. එය ස්ථාපකය දැනට හඳුනාගත් අනිෂ්ට මෘදුකාංග සමඟ ගැළපීම වෙනුවට, ස්ථාපකය _කරන දේ_ විනිශ්චය කරයි. එය සක්රිය වූ විට Kaspersky විසින් සම්පූර්ණ ස්ථාපනයම "ආපසු හරවයි" — දැනටමත් ලියා තිබූ ගොනු මකා දමයි — එම නිසා යෙදුම අවසානයේ බිඳුණු හෝ අස්ථානගත තත්ත්වයට පත්වේ.

එය සලකුණු කරන ගොනු, Desktop යෙදුම සමඟ ඇසුරුම් කර ඇති ප්රකාශිත විවෘත මූලාශ්ර පරායත්තතාවල සම්මත කොටස් වේ. උදාහරණ ලෙස:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` සහ
  `workerProcessEntry.js` — යෙදුම තුළ සැපයුම්කරු වෙත පිවිසීම සහ බ්රවුසරය මත පදනම් වූ කතාබස් සඳහා භාවිත කරන බ්රවුසර ස්වයංක්රීයකරණ පුස්තකාලය වන [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — වෙබ්-කුකී සැපයුම්කරුවන් මත බ්රවුසර ඇඟිලි සලකුණු කළ HTTP සඳහා භාවිත කරන, නිශ්චිත අනුවාදයකට ස්ථිර කළ `wreq-js` ස්වදේශීය බන්ධනය (`<arch>` යනු `x64` හෝ `arm64` වේ).

**එය සක්රිය වන්නේ ඇයි:** Windows ස්ථාපකය **තවමත් කේත-අත්සන් කර නොමැත**, එබැවින් අත්සන් නොකළ NSIS ස්ථාපකයකට කිසිදු කීර්තියක් නොමැති අතර හැසිරීම්මය හියුරිස්ටික් ක්රම උපරිම ආක්රමණශීලීත්වයෙන් ක්රියාත්මක වේ. ඇසුරුම් කළ ස්වදේශීය DLL එකක් සහ `%LOCALAPPDATA%\Programs\OmniRoute` යටතේ ලියන ලද `.js` ගොනු සිය ගණනක් (Next.js ස්වාධීන ගොඩනැගීමෙන් ලැබෙන hash-උපසර්ග සහිත පැකේජ නාමාවලි ඇතුළුව) සමඟ එකතු වූ විට, එය හියුරිස්ටික් ක්රමය සක්රිය කිරීමට ප්රමාණවත් වේ. කේත අත්සන් කිරීම සැලසුම් කර ඇත; එය ක්රියාත්මක වන තෙක් නව නිකුතු සමඟ මෙය නැවත සිදුවිය හැක.

**කළ යුතු දේ:**

1. **පළමුව ඔබේ බාගැනීම සත්යාපනය කරන්න** (ගොනුව අනිසි ලෙස වෙනස් කර නොමැති බව මෙයින් තහවුරු වේ). සෑම නිකුතුවක්ම `latest.yml` පළ කරන අතර, එහි `sha512` ක්ෂේත්රය (base64) `OmniRoute.Setup.<version>.exe` ස්ථාපකය ආවරණය කරයි. PowerShell තුළ, ස්ථාපකය අඩංගු ෆෝල්ඩරයේ සිට:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```

**හේතුව:** ඔබ OmniRoute විසින් අනුමත කළ ආරක්ෂිත ධාවන පරිසරයේ අවම සීමාවෙන් පිටත Node.js අනුවාදයක් ධාවනය කරමින් සිටී. වඩාත් පොදු අවස්ථාව වන්නේ OmniRoute සඳහා අවශ්ය ආරක්ෂිත පැච් අවම සීමාවට වඩා පහළ පැරණි Node 22 හෝ 24 පැච් මට්ටමක් ධාවනය කිරීමයි.

**රෝග ලක්ෂණ:**

   nvm use 24

**විසඳුම (v3.5.5+):** මෙය දැන් නිරාකරණය කර ඇත. සපයන්නා සත්යාපනය `runWithProxyContext` හරහා මාර්ගගත වන අතර, සපයන්නා-මට්ටමේ සහ ගෝලීය ප්රොක්සි සැකසුම් ස්වයංක්රීයව පිළිපදියි.

### SOCKS5 ප්රොක්සිය "invalid onRequestStart method" ලබා දෙයි

**හේතුව:** Node.js 22 මත, undici@8 ඩිස්පැචරය Node හි අන්තර්ගත `fetch()` ක්රියාත්මක කිරීම සමඟ නොගැළපේ.

**විසඳුම (v3.5.5+):** ප්රොක්සි ඩිස්පැචරයක් සක්රියව ඇති විට OmniRoute දැන් undici හිම `fetch()` ශ්රිතය භාවිත කරමින් ස්ථාවර හැසිරීමක් සහතික කරයි. v3.5.5+ වෙත යාවත්කාලීන කරන්න.

### WSL යටතේ MITM ප්රොක්සිය: Windows සත්කාරකයේ ඩෙස්ක්ටොප් යෙදුම් හසු කර නොගනී

**හේතුව:** MITM ප්රොක්සිය සහ එහි CA සහතිකය OmniRoute ක්රියාත්මක වන පරිසරය තුළ ස්ථාපනය වේ. WSL යටතේ එම පරිසරය Linux ආගන්තුක පද්ධතිය වන අතර, AI ඩෙස්ක්ටොප් යෙදුම් (Kiro, Trae, Copilot, Zed, …) Windows සත්කාරකය මත ක්රියාත්මක වේ. සත්කාරක යෙදුම් ආගන්තුක පද්ධතියේ සහතික ගබඩාව විශ්වාස නොකරන අතර ආගන්තුක පද්ධතියේ පද්ධති ප්රොක්සිය හරහා මාර්ගගත නොවන බැවින්, එහිදී ඩෙස්ක්ටොප් හසුකර ගැනීම ක්රියාත්මක නොවේ.

**නිර්දේශය:** ඔබට හසුකර ගැනීමට අවශ්ය ඩෙස්ක්ටොප් යෙදුම් පවතින OS එකේම OmniRoute ස්වදේශීයව ක්රියාත්මක කරන්න (Windows යෙදුම් සඳහා Windows; macOS/Linux සඳහාද එලෙසම). සත්කාරක යෙදුම් ඉලක්ක කරමින් OmniRoute WSL තුළ තබා ගැනීමට, ජනනය කළ CA සහතිකය Windows සත්කාරකය මත අතින් විශ්වාසනීය කළ යුතු අතර එක් එක් සත්කාරක යෙදුමේ ජාල/ප්රොක්සි සැකසුම් WSL ප්රොක්සි අන්ත ලක්ෂ්යය වෙත යොමු කළ යුතුය — මෙය සහාය නොදක්වන, පහසුවෙන් බිඳ වැටිය හැකි සැකසුමකි.

**හේතුව:** client එක JSON අපේක්ෂා කරන අතර upstream එක SSE payload එකක් ලබා දෙයි.

**තාවකාලික විසඳුම:** cloud direct calls සඳහා `stream=true` භාවිත කරන්න. Local runtime එකට SSE→JSON fallback එකක් ඇතුළත් වේ.

### ක්ලවුඩ් සම්බන්ධ වී ඇති බව පෙන්වුවත් "වලංගු නොවන API key" යැයි පවසයි

1. local dashboard එකෙන් (`/api/keys`) නව key එකක් සාදන්න
2. cloud sync ක්රියාත්මක කරන්න: Enable Cloud → Sync Now
3. පැරණි/සමමුහුර්ත නොකළ keys සඳහා cloud එකෙන් තවමත් `401` ලැබිය හැක

## Docker ගැටලු

### Docker IPv6 / සම්බන්ධතාව යළි සැකසීම

<a name="docker-ipv6"></a>

**රෝග ලක්ෂණ:** `curl http://localhost:20128/v1/models` මඟින් `curl: (56) Recv failure: Connection reset by peer` ලැබේ. Dashboard එක සහ authentication අවශ්ය නොවන endpoints ක්රියා කරයි, නමුත් authenticated endpoints අසාර්ථක වේ — මෙය auth ගැටලුවක් ලෙස පෙනුණත් එසේ නොවේ.

**හේතුව:** `docker run -p 20128:20128` මඟින් `0.0.0.0` (IPv4) සහ `::` (IPv6) යන දෙකෙහිම publish කරන නමුත් container එක ඇතුළත ඇති process එක සවන් දෙන්නේ IPv4 මත පමණි. `localhost` පළමුව `::1` ලෙස resolve වන hosts මත, සම්බන්ධතාව පිටුපස listener එකක් නොමැති IPv6 published port එක වෙත ළඟා වේ → සම්බන්ධතාව යළි සැකසේ.

**විසඳුම:**

1. **ඉක්මන් රෝග විනිශ්චය:** `curl -4 http://localhost:20128/v1/models` ක්රියාත්මක කරන්න. එය `-4` සමඟ ක්රියා කරන නමුත් එය නොමැතිව අසාර්ථක වේ නම්, ඔබට IPv6 bind නොගැළපීමක් ඇත.
2. **ස්ථිර විසඳුම:** ඔබගේ `docker run` විධානයෙහි `-p 127.0.0.1:20128:20128` භාවිතයෙන් IPv4 වෙත පැහැදිලිව bind කරන්න:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   මෙය IPv4 bind කිරීම බලගන්වන අතර සියලුම host interfaces මත proxy එක නිරාවරණය වීම ද වළක්වයි.

### Log Files සක්රීය කිරීම

ඔබගේ `.env` ගොනුවෙහි `APP_LOG_TO_FILE=true` සකසන්න. Application logs `logs/` යටතේ ලියනු ලැබේ.
settings තුළ call log pipeline එක සක්රීය කර ඇති විට request artifacts `${DATA_DIR}/call_logs/` යටතේ ගබඩා කෙරේ.
pipeline capture සක්රීය කර ඇති විට stream chunk payloads ඉවත් කිරීමට `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` සකසන්න, නැතහොත් KB වලින් artifact සීමාව වෙනස් කිරීමට `CALL_LOG_PIPELINE_MAX_SIZE_KB` සීරුමාරු කරන්න.

### සැපයුම්කරු OPEN තත්ත්වයේ සිරවී ඇත

සැපයුම්කරුවෙකුගේ පරිපථ බිඳිනය OPEN තත්ත්වයේ ඇති විට, සිසිලන කාලය අවසන් වන තෙක් ඉල්ලීම් අවහිර කරනු ලැබේ.

**විසඳුම:**

1. **උපකරණ පුවරුව → සැකසුම් → ප්රත්යස්ථතාව** වෙත යන්න
2. බලපෑමට ලක් වූ සැපයුම්කරුගේ පරිපථ බිඳින කාඩ්පත පරීක්ෂා කරන්න
3. සියලුම බිඳින ඉවත් කිරීමට **සියල්ල යළි සකසන්න** ක්ලික් කරන්න, නැතහොත් සිසිලන කාලය අවසන් වන තෙක් රැඳී සිටින්න
4. යළි සැකසීමට පෙර සැපයුම්කරු සැබැවින්ම ලබා ගත හැකි බව තහවුරු කරගන්න

### සැපයුම්කරු නැවත නැවතත් පරිපථ බිඳිනය සක්රිය කරයි

සැපයුම්කරුවෙකු නැවත නැවතත් OPEN තත්ත්වයට ඇතුළු වන්නේ නම්:

2. **සැකසුම් → ප්රත්යස්ථතාව → සැපයුම්කරුගේ පැතිකඩ** වෙත ගොස් අසාර්ථකත්ව සීමාව වැඩි කරන්න

### පොදු ආකෘති ගැටලු

- **සිතීමේ ටැග නොපෙන්වීම** — ඉලක්කගත සැපයුම්කරු සිතීමට සහාය දක්වන්නේද සහ සිතීමේ අයවැය සැකසුමද පරීක්ෂා කරන්න
- **මෙවලම් ඇමතුම් ඉවත් වීම** — ඇතැම් ආකෘති පරිවර්තන සහාය නොදක්වන ක්ෂේත්ර ඉවත් කළ හැක; අත්හදා බැලීම් අවකාශ ප්රකාරය තුළ තහවුරු කරගන්න
- **පද්ධති ප්රේරකය අස්ථානගත වීම** — Claude සහ Gemini පද්ධති ප්රේරක වෙනස් ලෙස හසුරුවයි; පරිවර්තන ප්රතිදානය පරීක්ෂා කරන්න
- **SDK මඟින් වස්තුවක් වෙනුවට අමු තන්තුවක් ලබා දීම** — v1.x තුළ විසඳා ඇත; OpenAI SDK Pydantic වලංගුකරණ අසාර්ථකත්වවලට හේතු වන සම්මත නොවන ක්ෂේත්ර (`x_groq`, `usage_breakdown`, ආදිය) ප්රතිචාර පවිත්රකාරකය මඟින් ඉවත් කරයි. ඔබ තවමත් v3.x+ තුළ මෙය දකින්නේ නම්, කරුණාකර ගැටලුවක් ගොනු කරන්න.
- **GLM/ERNIE විසින් `system` භූමිකාව ප්රතික්ෂේප කිරීම** — v1.x තුළ විසඳා ඇත; භූමිකා සාමාන්යකාරකය නොගැළපෙන ආකෘති සඳහා පද්ධති පණිවිඩ ස්වයංක්රීයව පරිශීලක පණිවිඩ සමඟ ඒකාබද්ධ කරයි. ඔබ තවමත් v3.x+ තුළ මෙය දකින්නේ නම්, කරුණාකර ගැටලුවක් ගොනු කරන්න.
- **`developer` භූමිකාව හඳුනා නොගැනීම** — v1.x තුළ විසඳා ඇත; OpenAI නොවන සැපයුම්කරුවන් සඳහා ස්වයංක්රීයව `system` බවට පරිවර්තනය කරයි. ඔබ තවමත් v3.x+ තුළ මෙය දකින්නේ නම්, කරුණාකර ගැටලුවක් ගොනු කරන්න.
- **`json_schema` Gemini සමඟ ක්රියා නොකිරීම** — v1.x තුළ විසඳා ඇත; `response_format` දැන් Gemini හි `responseMimeType` + `responseSchema` බවට පරිවර්තනය කෙරේ. ඔබ තවමත් v3.x+ තුළ මෙය දකින්නේ නම්, කරුණාකර ගැටලුවක් ගොනු කරන්න.

## විකල්ප RAG / LLM අසාර්ථකතා වර්ගීකරණය (ගැටලු 16ක්)

සමහර OmniRoute පරිශීලකයෝ gateway එක RAG හෝ agent stack ඉදිරියේ තබති. එවැනි සැකසුම්වල අමුතු රටාවක් දැකීම සාමාන්ය දෙයකි: OmniRoute සෞඛ්ය සම්පන්න බව පෙනේ (providers ක්රියාත්මකයි, routing profiles නිවැරදියි, rate limit alerts නැත), නමුත් අවසාන පිළිතුර තවමත් වැරදියි.

ප්රායෝගිකව, මෙම සිදුවීම් සාමාන්යයෙන් gateway එකෙන්ම නොව, downstream RAG pipeline එකෙන් ඇති වේ.

එම අසාර්ථකතා විස්තර කිරීමට පොදු වචන මාලාවක් අවශ්ය නම්, නැවත නැවත ඇති වන RAG / LLM අසාර්ථකතා රටා දහසයක් නිර්වචනය කරන, MIT බලපත්රය යටතේ ඇති බාහිර පෙළ සම්පතක් වන WFGY ProblemMap භාවිත කළ හැක. ඉහළ මට්ටමකින් එය පහත දෑ ආවරණය කරයි:

- retrieval drift සහ බිඳුණු context සීමා
- හිස් හෝ යල්පැන ගිය indexes සහ vector stores
- embedding සහ semantic අතර නොගැළපීම
- prompt එකලස් කිරීමේ සහ context window ගැටලු
- logic collapse සහ අධිවිශ්වාසී පිළිතුරු
- දිගු chain සහ agent සම්බන්ධීකරණ අසාර්ථකතා
- multi agent memory සහ role drift
- deployment සහ bootstrap අනුපිළිවෙළ පිළිබඳ ගැටලු

අදහස සරලයි:

1. වැරදි ප්රතිචාරයක් විමර්ශනය කරන විට, පහත දෑ සටහන් කරගන්න:
   - පරිශීලක කාර්යය සහ ඉල්ලීම
   - OmniRoute තුළ භාවිත වූ route හෝ provider combo එක
   - downstream හි භාවිත වූ ඕනෑම RAG context එකක් (ලබාගත් ලේඛන, tool calls ආදිය)
2. සිදුවීම WFGY ProblemMap අංක එකකට හෝ දෙකකට (`No.1` … `No.16`) සිතියම්ගත කරන්න.
3. OmniRoute logs අසල, ඔබේම dashboard, runbook, හෝ incident tracker එකෙහි එම අංකය ගබඩා කරන්න.
4. ඔබේ RAG stack, retriever, හෝ routing strategy වෙනස් කිරීමට අවශ්යදැයි තීරණය කිරීමට අදාළ WFGY පිටුව භාවිත කරන්න.

සම්පූර්ණ පෙළ සහ නිශ්චිත ක්රියාපටිපාටි මෙහි ඇත (MIT බලපත්රය, පෙළ පමණි):

### Responses API: background mode එක synchronous ලෙස පහත හෙළීම

**ලක්ෂණ:**

- සටහන් වන අනතුරු ඇඟවීම: `background mode degraded to synchronous`
- `background: true` ඉල්ලීමක් background job handle එකක් වෙනුවට සාමාන්ය synchronous response එකක් ආපසු ලබා දීම

**හේතුව:** v3.8.0 තුළ Responses API හි `background: true`, අනතුරු ඇඟවීමක් නිකුත් කරමින් හිතාමතාම synchronous ක්රියාත්මක කිරීමකට පහත හෙළයි. සම්පූර්ණ async background ක්රියාත්මක කිරීම අනාගතයේ ලබාදීමට නියමිත විශේෂාංගයකි.

**විසඳුම:**

- `background` නොමැතිව ඇමතුම ලබා දීමට client එක සකසන්න, හෝ
- සම්පූර්ණ async background mode එක ඇතුළත් පසුකාලීන නිකුතුවක් සඳහා රැඳී සිටින්න (changelog එක නිරීක්ෂණය කරන්න)

## මන්දගාමී ආරම්භය / සූදානම් වීමේ කාල සීමාව ඉක්මවීම

CLI එක `⚠ Server did not respond within 60s` ලෙස පෙන්වන නමුත් සේවාදායකය සැබවින්ම ක්රියා කරන්නේ නම්, ඔබේ පරිසරය සඳහා සූදානම් වීම පරීක්ෂා කිරීමට වෙන් කර ඇති කාලය ඉතා කෙටිය.

මෙය සාමාන්යයෙන් Windows මත (ප්රතිවෛරස මෘදුකාංග, ගොනු පද්ධති නිරීක්ෂකයන්) හෝ ආරම්භයේදී අධික කාර්ය භාරයක් ඇති containers තුළ සිදු වේ.

**විසඳුම — කාල සීමාව වැඩි කරන්න:**

```bash
# පරිසර විචල්යයක් හරහා (ආරම්භ කිරීම් අතරතුරද පවතී):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # මිනිත්තු 3
omniroute serve

# CLI flag එකක් හරහා (එක් වරක් පමණි):
omniroute serve --ready-timeout 180000
```

පෙරනිමි අගය 60 000 ms (60 s) වේ. මෙම අනතුරු ඇඟවීම දැනුම් දීම සඳහා පමණි; සේවාදායකය පසුබිමේ දිගටම ආරම්භ වන අතර boot කිරීම සම්පූර්ණ වූ පසු එයට ප්රවේශ විය හැක.

`OMNIROUTE_READY_TIMEOUT_MS` පිළිබඳ සම්පූර්ණ විස්තර සඳහා [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) බලන්න.
