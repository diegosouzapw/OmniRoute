### නොමිලේ සැපයුම්කරුවන්ගේ වේග සීමා කිරීම (429 / 400 / 401)

**ලක්ෂණය**: නොමිලේ/සත්යාපනය අවශ්ය නොවන සැපයුම්කරුවන් (opencode, auggie, ආදිය) සමඟ `model: "auto"` භාවිත කරන විට, පිළිතුරු වෙනුවට කඩින් කඩ `HTTP 429`, `400`, හෝ `401` ලැබේ. මොහොතකට පසුව එම prompt එකම නැවත උත්සාහ කළ විට ඉල්ලීම් සාර්ථක වන නමුත්, පළමු අසාර්ථක වීමේදීම ස්වයංක්රීයකරණය (cron jobs, agents, scripts) බිඳ වැටේ.

**මූලික හේතුව**: ස්වාධීන අසාර්ථකත්ව ආකාර තුනක් එකට එකතු වේ:

1. **සැපයුම්කරුගේ වේග සීමාව (`429`)**: නොමිලේ මට්ටම්වලට එක් කාල කවුළුවකට කෝටාවක් බලාත්මක කළ හැක. සමාන්තර ඇමතුම් සමූහයක් එය අවසන් කරන බැවින්, කවුළුව නැවත සැකසෙන තෙක් ඊළඟ ඉල්ලීම ප්රතික්ෂේප වේ.
2. **Passthrough තුළ බිඳුණු model එකක් (`400`/`401`)**: `auto/*` pools තුළ catalog එකේ ලියාපදිංචි වී ඇති නමුත් සජීවී අක්තපත්ර නොමැති `opencode` වෙතින් passthrough models ඇතුළත් විය හැක (උදා. `oc/north-mini-code-free` → `401`). auto-router එකක් උත්සාහ කර අසාර්ථක වන අතර, fallback ක්රියාත්මක වීමට පෙර දෝෂය ඉදිරියට පැතිරේ.
3. **සමකාලීනත්ව වර්ධනය (බර යටතේ `429`)**: agent/cron sessions කිහිපයක් එකවර `auto` වෙත පිවිසෙන විට, සමස්ත ඉල්ලීම් වේගය නොමිලේ සැපයුම්කරුවන්ට දරාගත හැකි සීමාව ඉක්මවන බැවින්, වලංගු ඇමතුම්ද අනිසි භාවිත ලෙස සලකුණු වේ.

**තහවුරු කළ විසඳුම (ප්රජාව විසින් වාර්තා කරන ලදී, 2026-08-10)**: නොමිලේ මට්ටමේ අස්ථාවරත්වය හේතුවෙන් අසාර්ථක වීම වෙනුවට rotation, concurrency, සහ fallback මඟින් එය අවශෝෂණය කරගැනීමට පරිසර විචල්ය තුනක් සකසන්න:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ලැබුණු විට වෙනත් model/provider එකකට මාරු වන්න (බිඳුණු passthrough models මඟහරී)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # heavyweight admission සඳහා පැහැදිලි උපරිම සීමාව (පෙරනිමියෙන් සකසා නැත: ඉල්ලීම්-ගණන සීමාවක් නැත, පහත සටහන බලන්න)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # මන්දගාමී upstreams සඳහා සීමිත රැඳී සිටීම RATE_LIMIT_MAX_WAIT_MS පෙරනිමියට වඩා ඉහළ නංවන්න
```

මේවා OmniRoute process environment එකේ (daemon එකේ, උදා. LaunchAgent plist හෝ `systemctl edit` හරහා) සකසා, පසුව OmniRoute නැවත ආරම්භ කරන්න. rotation flag එක තනිවම වැඩිම බලපෑමක් ඇති විකල්පයයි: එය දැඩි අසාර්ථකත්වයක් pool එකේ ඇති සෞඛ්ය සම්පන්න සැපයුම්කරුවෙකු වෙත විනිවිද පෙනෙන නැවත උත්සාහයක් බවට පරිවර්තනය කරයි.

**සටහන**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` මඟින් එකවර ධාවනය වන heavyweight — දිගු-context — ඉල්ලීම් ගණන සීමා කරයි; එම සීමාව admission gate එකක් මිස සැපයුම්කරුගේ වේග සීමාකාරකයක් නොවේ. **#503-fanout යාවත්කාලීනය:** මෙම var එක දැන් පෙරනිමියෙන් සකසා නැත (දැන් එය ඉහත පරිදි පැහැදිලිව වින්යාස කළ විට පමණක් බැඳේ) — ඒ වෙනුවට heavyweight admission, host එකේ සැබෑ memory ceiling එක අනුව ස්වයංක්රීයව පරිමාණය වන auto-derived byte budget එකක් (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) මඟින් පාලනය වේ. එබැවින් අලුත් deployment එකකදී මෙම var එක කිසිසේත් සකස් නොකරම `503 chat_admission_busy` ප්රතික්ෂේප කිරීම් බෙහෙවින් අඩුවෙන් දැකිය යුතුය; මෙහි එය පැහැදිලිව සැකසීම තවමත් ලේඛනගත කර ඇති ආකාරයටම ක්රියා කරයි. පැහැදිලි byte-budget overrides 8 MiB–2 GiB අතරට සීමා වේ. `413 body_exceeds_budget` තාවකාලික නොවේ: එම byte budget එක වැඩි කරන්න, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` අඩු කරන්න, හෝ process memory ceiling එක වැඩි කරන්න. `inflight_bytes_budget` shed එකක් තාවකාලික තරගකාරී තත්ත්වයක් වන අතර නැවත උත්සාහ කළ හැක. එක් එක් සැපයුම්කරු සඳහා වන වේග සීමා කිරීම (`open-sse/services/rateLimitManager.ts`) `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, සහ `RATE_LIMIT_AUTO_ENABLE` මඟින් වෙනම පාලනය වේ — `.env.example` බලන්න.

**එය ක්රියා කළ බව තහවුරු කරන්නේ කෙසේද**: ඔබගේ agent/cron එක ඉක්මන් අනුක්රමයකින් දෙවරක් ධාවනය කර, අවස්ථා දෙකම සාර්ථක වන බව තහවුරු කරන්න. නිවැරදි කිරීමට පෙර, දෙවන ධාවනය සාමාන්යයෙන් `429`/`401` දෝෂයක් නිකුත් කරයි. නිවැරදි කිරීමෙන් පසු, අසාර්ථක වීම් (තිබේ නම්) විනිවිද පෙනෙන ලෙස නැවත උත්සාහ කෙරෙන අතර ඇමතුම සම්පූර්ණ වේ. ඔබට `curl /monitoring/health` ද ධාවනය කර provider සම්බන්ධතා මත ඇති `rateLimitedUntil` ක්ෂේත්රය සහ බලපෑමට ලක් වූ providers සඳහා `circuitBreakers.providerBreakers[].state` නිරීක්ෂණය කළ හැක — state එක `CLOSED`, `DEGRADED`, `OPEN`, හෝ `HALF_OPEN` යන ඒවායින් එකකි (`src/shared/utils/circuitBreaker.ts` බලන්න), තවද අඛණ්ඩව අසාර්ථක වන provider එකක් reset window එක මඟින් probe එකකට ඉඩ ලැබීමට පෙර `CLOSED → DEGRADED → OPEN` ලෙස මාරු වේ (`HALF_OPEN`).

**ඔබට තවමත් 429 පෙනේ නම්**: එම provider සඳහා සක්රිය account එකේ _quota_ සත්ය වශයෙන්ම අවසන් වී ඇත (rate එක පමණක් නොවේ). OmniRoute dashboard → Providers → Accounts තුළ එම provider සඳහා දෙවන account එකක් එක් කරන්න, නැතහොත් වෙනත් නොමිලේ provider එකක් (උදා. `routeway`, `auggie`) මිශ්ර කර භාවිත කරන්න. Rotation උපකාරී වන්නේ තාවකාලික rate/400/401 තත්ත්ව සඳහා පමණි; quota එක සම්පූර්ණයෙන් අවසන් වීමකදී දෙවන credential එකක් හෝ වෙනත් provider එකක් අවශ්ය වේ.

**vision models (`auto/vision`, `bazaarlink/*`) මත 403 පෙනේ නම්**: සම්බන්ධිත account එකට vision ඇතුළත් ගෙවීම් සහිත plan එකක් නොමැත, නැතහොත් API key එකට ප්රමාණවත් permissions නොමැත. key scope එකට vision/multimodal ඇතුළත් බව provider dashboard එක තුළ තහවුරු කරන්න, නැතහොත් ගෙවීම් සහිත tier account එකක් සම්බන්ධ කර එය vision target එක ලෙස තබා ගන්න.

## npm install අනතුරු ඇඟවීම් (ERESOLVE / peer / deprecated)

ඔබ `npm install -g omniroute` ධාවනය කරන විට, `npm warn ERESOLVE`, peer dependency දැනුම්දීම් සහ `deprecated` පණිවිඩ වැනි අනතුරු ඇඟවීම් රාශියක් දැකිය හැක. **මේවා බලාපොරොත්තු විය හැකි අතර හානිකර නොවේ.** ප්රතිදානයේ `added <N> packages` දැක්වෙන්නේ නම්, ඔබේ ස්ථාපනය සාර්ථක වී ඇත.

peer dependency නිරාකරණ අනතුරු ඇඟවීම් යටපත් කිරීමට, OmniRoute සහාය දක්වන ස්ථාපන ආකාරය භාවිත කරන්න:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` යටපත් කරන්නේ `ERESOLVE` සහ peer dependency දැනුම්දීම් පමණි. අනුක්රමික තෙවන පාර්ශ්ව පැකේජවලින් ඒවා පැමිණෙන බැවින් අත්හැර දැමීමේ දැනුම්දීම් තවදුරටත් දෘශ්යමාන වේ; ඒවා ස්ථාපනය අසාර්ථක වූ බවක් නොපෙන්වයි.

මෙම අනතුරු ඇඟවීම් පැමිණෙන්නේ OmniRoute විසින් පාලනය නොකරන තෙවන පාර්ශ්ව පැකේජවල යල් පැනගිය peer dependency පරාසවලිනි:

1. **`marked-terminal` හට `marked >=1 <16` අවශ්ය නමුත් `marked@18` හමු විය** — ප්රායෝගිකව නිසි ලෙස ක්රියා කරයි; upstream peer පරාසය යල් පැනගොස් ඇත.
2. **`deprecated prebuild-install@7.1.3`** — අනුක්රමික native binary ලබාගැනීමේ උපකාරකයකි. එය pin කර ඇති `wreq-js` ප්රවාහන binding එක ස්ථාපනය කිරීමට
   භාවිත නොකරන අතර web-cookie සපයන්නාගේ ප්රවාහන සැකසුම අසාර්ථක වූ බවක්
   නොපෙන්වයි.

**කිසිදු ක්රියාමාර්ගයක් අවශ්ය නොවේ** — upstream පැකේජ fork කිරීමකින් තොරව මෙම අනතුරු ඇඟවීම් සම්පූර්ණයෙන්ම නිහඬ කළ නොහැක.

## npm install-scripts අවහිර කළ බවට අනතුරු ඇඟවීම (ගෝලීය ස්ථාපනය)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` ධාවනය කරන විට, නව npm අනුවාද (v11+ සහ v12+) පෙරනිමියෙන් පැකේජ ජීවන චක්ර script අවහිර කර install-scripts අනතුරු ඇඟවීමක් පෙන්වයි:

```
npm warn install-scripts allowScripts මඟින් ආවරණය නොවන බැවින් පැකේජ 7ක install script අවහිර කර ඇත:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### මෙම අනතුරු ඇඟවීම නොසලකා හැරිය හැකිද?

**අර්ධ වශයෙන් හැකි නමුත් script නොමැතිව ධාවනය කිරීම නිර්දේශ නොකෙරේ.** OmniRoute සතුව සුමට fallback ඇත: standalone bundle එකෙන් native `better-sqlite3` binding පූරණය කළ නොහැකි නම්, යෙදුම `node:sqlite` හෝ `sql.js` වැනි විකල්ප driver වෙත fallback වේ ([SQLite ධාවන කාල නිරාකරණය](../ops/SQLITE_RUNTIME.md) බලන්න). සේවාදායකය තවමත් ආරම්භ වනු ඇත, නමුත් `sql.js` වැනි WASM fallback මත ධාවනය කිරීමෙන් SQLite WAL (Write-Ahead Logging) මාදිලිය අක්රිය වන අතර මතක සහ තැටි සමමුහුර්තකරණ අතිරික්තය වැඩි වේ.

### සැබවින්ම අවශ්ය script මොනවාද?

අවහිර කළ සියලුම script OmniRoute ධාවනය කිරීමට අත්යවශ්ය නොවේ:

- **අත්යවශ්ය (`omniroute`, `better-sqlite3`):** OmniRoute ධාවනය වන්නේ Next.js standalone යෙදුම් bundle එකකිනි (`dist/`). ස්ථාපනය අතරතුර, npm විසින් ඉහළම මට්ටමේ `node_modules/better-sqlite3/` තුළ ධාරකයට විශේෂිත native SQLite driver එක බාගැනීම හෝ සම්පාදනය කිරීම සිදු කරයි. ඉන්පසු OmniRoute හි `postinstall` script එක (`scripts/build/postinstall.mjs`) මෙම ධාරකයට විශේෂිත binary සත්යාපනය කර standalone සේවාදායකයට ඒවාට ප්රවේශ විය හැකි වන පරිදි `dist/node_modules/` වෙත පිටපත් කරයි. `omniroute` හි postinstall script එක අවහිර කර ඇත්නම්, මෙම පිටපත් කිරීමේ පියවර මඟ හැරේ.
- **විකල්ප/අනුක්රමික (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** මේවා build උපකාරක, watcher මෙවලම් හෝ පද්ධති keychain උපයෝගිතා වේ. ඒවාට ඉඩ දීමෙන් build අනතුරු ඇඟවීම් වළක්වන නමුත්, මූලික routing ක්රියාකාරීත්වය සඳහා ඒවා අවශ්ය නොවේ.
- **බැහැර කළ (`onnxruntime-node`):** දේශීය AI embedding සඳහා වන විකල්ප dependency එකක් වන අතර OmniRoute ධාවනය කිරීමට එය **අවශ්ය නොවේ**. එහි postinstall script එක NuGet වෙතින් ~300MB ප්රමාණයක CUDA සම්පත් බාගනී; සහාය දක්වන දෘඪාංග මත දේශීය ONNX ත්වරණය භාවිත කිරීමට ඔබ පැහැදිලිවම අදහස් කරන්නේ නම් හැර, එය allow-list එකට ඇතුළත් නොකරන්න.

### නිර්දේශිත විසඳුම

ගෝලීය ස්ථාපනයක් අතරතුර අවශ්ය install script සඳහා අවසර දී අනතුරු ඇඟවීම් නිහඬ කිරීමට, OmniRoute සහ එහි native dependency සඳහා `--allow-scripts` යොදන්න:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

විකල්පයක් ලෙස, ඔබේ පරිශීලක ගිණුමේ සියලුම ගෝලීය ස්ථාපන සඳහා මෙය ස්ථිරව වින්යාස කිරීමට:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### ඔබේ ස්ථාපනය සත්යාපනය කරන්න

ස්ථාපනයෙන් පසු, native binding සහ ධාවන කාල පරිසරය නිසි තත්ත්වයේ පවතින බව තහවුරු කරගැනීමට ඇතුළත් කළ රෝගනිශ්චය මෙවලම ධාවනය කරන්න:

```bash
omniroute doctor
```

## Gemini Web සහ Playwright Chromium

Gemini Web ඉල්ලීමක් Playwright Chromium ස්ථාපනය කර නොමැති බව සඳහන් පණිවිඩයක් සමඟ `503` ප්රතිචාරයක් ලබා දෙන්නේ නම්, npm පැකේජය පවතින නමුත් බ්රවුසර ද්විමය ගොනුව නොමැත. Playwright හිතාමතාම බ්රවුසර බාගැනීම් npm පැකේජ ස්ථාපනයෙන් වෙන්ව තබන බැවින්, බ්රවුසරය ස්ථාපනය කරන තෙක් මෙම ප්රතිචාරය බලාපොරොත්තු විය හැක.

ගෝලීය npm ස්ථාපනයක් සඳහා, බ්රවුසර හැඹිලිය එම Playwright ස්ථාපනයටම අයත් වන පරිදි OmniRoute පැකේජයේ නාමාවලියෙන් Chromium ස්ථාපනය කරන්න:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ස්ථාපනයෙන් පසු OmniRoute නැවත ආරම්භ කර, ඉන්පසු Gemini Web ඉල්ලීම නැවත උත්සාහ කරන්න. ඔබ Docker අනුරුවකින් OmniRoute ධාවනය කරන්නේ නම්, Chromium සහ එහි පරායත්තතා ඇතුළත් `-web` අනුරුව (හෝ `runner-web` ගොඩනැගීමේ ඉලක්කය) භාවිත කරන්න; මූලික අනුරුවේ ඒවා ඇතුළත් නොවේ.

### SOCKS5 ප්රොක්සිය "invalid onRequestStart method" ලබා දෙයි

**හේතුව:** Node.js 22 මත, undici@8 ඩිස්පැචරය Node හි අන්තර්ගත `fetch()` ක්රියාත්මක කිරීම සමඟ නොගැළපේ.

**විසඳුම (v3.5.5+):** ප්රොක්සි ඩිස්පැචරයක් සක්රියව පවතින විට OmniRoute දැන් undici හිම `fetch()` ශ්රිතය භාවිත කරමින් ස්ථාවර හැසිරීමක් සහතික කරයි. v3.5.5+ වෙත යාවත්කාලීන කරන්න.

### WSL යටතේ MITM ප්රොක්සිය: Windows ධාරකයේ ඩෙස්ක්ටොප් යෙදුම් ග්රහණය නොවේ

**හේතුව:** MITM ප්රොක්සිය සහ එහි CA සහතිකය OmniRoute ක්රියාත්මක වන පරිසරය තුළ ස්ථාපනය වේ. WSL යටතේ එම පරිසරය Linux අමුත්තා වන අතර, AI ඩෙස්ක්ටොප් යෙදුම් (Kiro, Trae, Copilot, Zed, …) Windows ධාරකයේ ක්රියාත්මක වේ. ධාරක යෙදුම් අමුත්තාගේ සහතික ගබඩාව විශ්වාස නොකරන අතර අමුත්තාගේ පද්ධති ප්රොක්සිය හරහා යොමු නොවන නිසා, ඩෙස්ක්ටොප් ග්රහණය එහි සක්රිය නොවේ.

**නිර්දේශය:** ඔබට ග්රහණය කිරීමට අවශ්ය ඩෙස්ක්ටොප් යෙදුම් ක්රියාත්මක වන OS එකේම OmniRoute ස්වදේශීයව ක්රියාත්මක කරන්න (Windows යෙදුම් සඳහා Windows; macOS/Linux සඳහාද එලෙසම). ධාරක යෙදුම් ඉලක්ක කරමින් OmniRoute WSL තුළ තබා ගැනීමට නම්, ජනනය කළ CA සහතිකය Windows ධාරකයේ අතින් විශ්වාසදායක කිරීමත්, එක් එක් ධාරක යෙදුමේ ජාල/ප්රොක්සි සැකසුම් WSL ප්රොක්සි අන්ත ලක්ෂ්යය වෙත යොමු කිරීමත් අවශ්ය වේ — මෙය සහය නොදක්වන, පහසුවෙන් බිඳ වැටිය හැකි සැකසුමකි.

## Cloud ගැටලු

### Cloud සමමුහුර්ත කිරීමේ දෝෂ

1. `BASE_URL` ඔබගේ ක්රියාත්මක වන instance එක වෙත යොමු වන බව තහවුරු කරන්න (උදා., `http://localhost:20128`)
2. `CLOUD_URL` ඔබගේ cloud endpoint එක වෙත යොමු වන බව තහවුරු කරන්න (උදා., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` අගයන් server-side අගයන් සමඟ ගැළපෙන ලෙස තබාගන්න

### Cloud හි `stream=false` 500 ප්රතිචාරයක් ලබා දෙයි

**ලක්ෂණය:** streaming නොවන calls සඳහා cloud endpoint එකේ `Unexpected token 'd'...` දර්ශනය වේ.

**හේතුව:** client එක JSON බලාපොරොත්තු වන අතර upstream එක SSE payload එකක් ආපසු ලබා දෙයි.

**තාවකාලික විසඳුම:** cloud direct calls සඳහා `stream=true` භාවිත කරන්න. Local runtime එකට SSE→JSON fallback එකක් ඇතුළත් වේ.

### Cloud සම්බන්ධ වී ඇති බව පෙන්වන නමුත් "වලංගු නොවන API key එකක්" යැයි පවසයි

1. local dashboard එකෙන් (`/api/keys`) නව key එකක් සාදන්න
2. cloud sync එක ධාවනය කරන්න: Cloud සබල කරන්න → දැන් සමමුහුර්ත කරන්න
3. පැරණි/සමමුහුර්ත නොකළ keys සඳහා cloud එකෙන් තවමත් `401` ආපසු ලැබිය හැක

### Docker IPv6 / සම්බන්ධතාව යළි පිහිටුවීම

<a name="docker-ipv6"></a>

**ලක්ෂණ:** `curl http://localhost:20128/v1/models` මඟින් `curl: (56) Recv failure: Connection reset by peer` ආපසු ලබා දෙයි. Dashboard එක සහ සත්යාපනය අවශ්ය නොවන endpoints ක්රියා කරන නමුත් සත්යාපිත endpoints අසාර්ථක වේ — මෙය සත්යාපන ගැටලුවක් මෙන් පෙනුණත් එසේ නොවේ.

**හේතුව:** `docker run -p 20128:20128` මඟින් `0.0.0.0` (IPv4) සහ `::` (IPv6) යන දෙකෙහිම පළ කරන නමුත් container එක තුළ ඇති process එක සවන් දෙන්නේ IPv4 මත පමණි. `localhost` පළමුව `::1` වෙත resolve වන hosts මත, සම්බන්ධතාවය පිටුපස listener එකක් නොමැති IPv6 published port එකට යොමු වේ → සම්බන්ධතාව යළි පිහිටුවේ.

**විසඳුම:**

1. **ඉක්මන් රෝග විනිශ්චය:** `curl -4 http://localhost:20128/v1/models` ධාවනය කරන්න. එය `-4` සමඟ ක්රියා කරන නමුත් එය නොමැතිව අසාර්ථක වන්නේ නම්, ඔබට IPv6 bind නොගැළපීමක් ඇත.
2. **ස්ථිර විසඳුම:** ඔබගේ `docker run` විධානයේ `-p 127.0.0.1:20128:20128` භාවිතයෙන් IPv4 වෙත පැහැදිලිව bind කරන්න:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   මෙය IPv4 bind කිරීම බලගන්වන අතර සියලුම host interfaces මත proxy එක නිරාවරණය වීමද වළක්වයි.

## දෝෂහරණය

### Log Files සබල කරන්න

ඔබගේ `.env` file එකේ `APP_LOG_TO_FILE=true` සකසන්න. Application logs `logs/` යටතේ ලියනු ලැබේ.
settings තුළ call log pipeline එක සබල කර ඇති විට request artifacts `${DATA_DIR}/call_logs/` යටතේ ගබඩා කෙරේ.
pipeline capture එක සබල කර ඇති විට stream chunk payloads මඟ හැරීමට `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` සකසන්න, නැතහොත් KB වලින් artifact සීමාව වෙනස් කිරීමට `CALL_LOG_PIPELINE_MAX_SIZE_KB` සීරුමාරු කරන්න.

### Provider සෞඛ්යය පරීක්ෂා කරන්න

# සෞඛ්ය dashboard එක
http://localhost:20128/dashboard/health

# API සෞඛ්ය පරීක්ෂාව

### Runtime ගබඩාව

- ප්රධාන තත්ත්වය: `${DATA_DIR}/storage.sqlite` (providers, combos, aliases, keys, settings)
- භාවිතය: `storage.sqlite` තුළ SQLite tables (`usage_history`, `call_logs`, `proxy_logs`) + විකල්ප `${DATA_DIR}/call_logs/`
- Application logs: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` වන විට)
- Call log artifacts: call log pipeline එක සබල කර ඇති විට `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs පිටුවේ **ඉතිහාසය පිරිසිදු කරන්න** ක්රියාව මඟින් `call_logs`, පැරණි
`request_detail_logs`, සහ local `${DATA_DIR}/call_logs/` artifact directory එක හිස් කරයි.

## Circuit Breaker ගැටලු

### සපයන්නා OPEN තත්ත්වයේ සිරවී ඇත

සපයන්නෙකුගේ circuit breaker එක OPEN තත්ත්වයේ ඇති විට, cooldown කාලය අවසන් වන තෙක් ඉල්ලීම් අවහිර කෙරේ.

**විසඳුම:**

1. **Dashboard → Settings → Resilience** වෙත යන්න
2. බලපෑමට ලක් වූ සපයන්නා සඳහා ඇති circuit breaker කාඩ්පත පරීක්ෂා කරන්න
3. සියලුම breakers ඉවත් කිරීමට **Reset All** ක්ලික් කරන්න, නැතහොත් cooldown කාලය අවසන් වන තෙක් රැඳී සිටින්න
4. reset කිරීමට පෙර සපයන්නා සැබවින්ම ලබා ගත හැකි බව තහවුරු කරන්න

### සපයන්නා දිගින් දිගටම circuit breaker එක සක්රිය කරයි

සපයන්නෙකු නැවත නැවතත් OPEN තත්ත්වයට පිවිසෙන්නේ නම්:

1. අසාර්ථක වීමේ රටාව සඳහා **Dashboard → Health → Provider Health** පරීක්ෂා කරන්න
2. **Settings → Resilience → Provider Profiles** වෙත ගොස් අසාර්ථක වීමේ සීමාව වැඩි කරන්න
3. සපයන්නා API සීමා වෙනස් කර තිබේද හෝ නැවත සත්යාපනය අවශ්යදැයි පරීක්ෂා කරන්න
4. ප්රමාද telemetry දත්ත සමාලෝචනය කරන්න — ඉහළ ප්රමාදය timeout මත පදනම් වූ අසාර්ථක වීම්වලට හේතු විය හැක

### පොදු ආකෘති ගැටලු

- **Thinking tags නොපෙන්වීම** — ඉලක්කගත සපයන්නා thinking සඳහා සහාය දක්වන්නේද සහ thinking budget සැකසුමද පරීක්ෂා කරන්න
- **Tool calls ඉවත් වීම** — ඇතැම් ආකෘති පරිවර්තන මඟින් සහාය නොදක්වන fields ඉවත් කළ හැක; Playground ප්රකාරය තුළ තහවුරු කරන්න
- **System prompt එක නොමැති වීම** — Claude සහ Gemini system prompts වෙනස් ආකාරයෙන් හසුරුවයි; පරිවර්තන ප්රතිදානය පරීක්ෂා කරන්න
- **SDK එක object එකක් වෙනුවට raw string එකක් ලබා දීම** — v1.x තුළ විසඳා ඇත; OpenAI SDK Pydantic වලංගුකරණ අසාර්ථක වීම් ඇති කරන සම්මත නොවන fields (`x_groq`, `usage_breakdown`, ආදිය) response sanitizer මඟින් ඉවත් කරයි. v3.x+ මත තවමත් මෙය දකින්නේ නම්, කරුණාකර issue එකක් ගොනු කරන්න.
- **GLM/ERNIE විසින් `system` role එක ප්රතික්ෂේප කිරීම** — v1.x තුළ විසඳා ඇත; නොගැළපෙන models සඳහා role normalizer විසින් system messages ස්වයංක්රීයව user messages තුළට ඒකාබද්ධ කරයි. v3.x+ මත තවමත් මෙය දකින්නේ නම්, කරුණාකර issue එකක් ගොනු කරන්න.
- **`developer` role එක හඳුනා නොගැනීම** — v1.x තුළ විසඳා ඇත; OpenAI නොවන සපයන්නන් සඳහා එය ස්වයංක්රීයව `system` බවට පරිවර්තනය කෙරේ. v3.x+ මත තවමත් මෙය දකින්නේ නම්, කරුණාකර issue එකක් ගොනු කරන්න.
- **`json_schema` Gemini සමඟ ක්රියා නොකිරීම** — v1.x තුළ විසඳා ඇත; දැන් `response_format` Gemini හි `responseMimeType` + `responseSchema` බවට පරිවර්තනය කෙරේ. v3.x+ මත තවමත් මෙය දකින්නේ නම්, කරුණාකර issue එකක් ගොනු කරන්න.

- ස්වයංක්රීය අනුපාත සීමාව අදාළ වන්නේ API යතුරු සපයන්නන්ට පමණි (OAuth/දායකත්ව සඳහා නොවේ)
- **Settings → Resilience → Provider Profiles** තුළ ස්වයංක්රීය අනුපාත සීමාව සබල කර ඇති බව තහවුරු කරන්න

### ඝාතීය පසුබැසීම සුසර කිරීම

සපයන්නාගේ පැතිකඩ මෙම සැකසුම් සඳහා සහාය දක්වයි:

- **මූලික ප්රමාදය** — පළමු අසාර්ථක වීමෙන් පසු ආරම්භක පොරොත්තු කාලය (පෙරනිමිය: 1s)
- **උපරිම ප්රමාදය** — උපරිම පොරොත්තු කාල සීමාව (පෙරනිමිය: 30s)
- **ගුණකය** — අනුක්රමික අසාර්ථක වීමකට ප්රමාදය වැඩි කළ යුතු ප්රමාණය (පෙරනිමිය: 2x)

### තදබද රැල්ල වැළැක්වීම

සමකාලීන ඉල්ලීම් බොහොමයක් අනුපාත-සීමා කළ සපයන්නෙකු වෙත ළඟා වන විට, ඉල්ලීම් අනුක්රමික කිරීමට සහ අනුක්රමික අසාර්ථක වීම් වැළැක්වීමට OmniRoute විසින් mutex + ස්වයංක්රීය අනුපාත සීමා කිරීම භාවිත කරයි. API යතුරු සපයන්නන් සඳහා මෙය ස්වයංක්රීය වේ.

### කතාබස් ඉල්ලීම් 503 / chat_admission_busy සමඟ අසාර්ථක වේ

**රෝග ලක්ෂණ:**

- කතාබස් සම්පූර්ණ කිරීම් අන්ත ලක්ෂ්යය, දෝෂ කේතය
  `chat_admission_busy` වන නැවත උත්සාහ කළ හැකි `503` ප්රතිචාරයක් ආපසු ලබා දෙයි.
- ප්රතිචාරයට `Retry-After` ඇතුළත් වේ. #12135 සිට එහි අගය නිරීක්ෂණය කළ
  භාවිත ධාරිතාවෙන් ව්යුත්පන්න වේ — ඉල්ලීම දැනටමත් රැඳී සිටි `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  කවුළුවෙන් සහ වත්මන් බරපතළ ලීස් රඳවාගෙන ඇති කාලයෙන් වඩා විශාල අගය — පූර්ණ
  තත්පර දක්වා ඉහළට වට කර 60කට සීමා කෙරේ. අක්රිය දොරටුවකදී එය ඓතිහාසික අවම සීමා තබාගනී:
  බයිට්-පාදක මාර්ගයේ තත්පර 2ක් සහ ව්යුහ-පාදක මාර්ගයේ තත්පර 1ක් (එයට
  `reason: "structure_limit"` ද ඇතුළත් වේ).
- වෙනත් බරපතළ කතාබස් ඉල්ලීමක් හෝ දිගු වේලාවක් ධාවනය වන ප්රවාහ ප්රතිචාරයක් තවමත්
  ක්රියාත්මක වෙමින් පවතින විට මෙය සිදුවිය හැක.

බයිට්-පාදක ප්රතිචාර අන්තර්ගතය වන්නේ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ව්යුහ-පාදක ප්රතිචාරය, `Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
පණිවිඩය සහ `reason: "structure_limit"` සමඟ එම වර්ගය සහ කේතයම භාවිත කරයි.
පෙරනිමි සීමාවලදී, ඉල්ලීමකට අවම වශයෙන් `200` පණිවිඩ, අවම වශයෙන් `64` මෙවලම්,
හෝ අවම වශයෙන් ඇස්තමේන්තුගත ටෝකන `32,000`ක් ඇති විට, නැතහොත් සීමා කළ ව්යුහ ඇස්තමේන්තුකරණය
පිවිසි නෝඩ් `10,000`ක හෝ ගැඹුර `12`ක සීමා අවසන් කරන විට, එය ව්යුහාත්මකව බරපතළ වේ.

## විකල්ප RAG / LLM අසාර්ථකතා වර්ගීකරණය (ගැටලු 16ක්)

**රෝග ලක්ෂණ:**

- දුරස්ථ production host එකක ධාවනය කරන විට සෑම Codex/Responses WebSocket bridge ඉල්ලීමකටම 401 ලැබීම
- සම්බන්ධ වූ වහාම WebSocket bridge handshake එක වැසී යාම

**හේතුව:** production environment එකෙන් `OMNIROUTE_WS_BRIDGE_SECRET` env var එක අස්ථානගත වී ඇත.

**විසඳුම:**

1. අහඹු secret එකක් ජනනය කරන්න: `openssl rand -hex 32`
2. production server env එකේ (සහ bridge එක සමඟ සන්නිවේදනය කරන ඕනෑම client එකක) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` සකසන්න
3. OmniRoute නැවත ආරම්භ කරන්න

## මන්දගාමී ආරම්භය / සූදානම් වීමේ කාල සීමාව ඉක්මවීම

CLI එක `⚠ Server did not respond within 60s` ලෙස පෙන්වන නමුත් සේවාදායකය
සැබවින්ම ක්රියා කරන්නේ නම්, ඔබේ පරිසරය සඳහා සූදානම් වීමේ පරීක්ෂණ කාල සීමාව ප්රමාණවත් නොවේ.

මෙය සාමාන්යයෙන් Windows මත (ප්රතිවෛරස, ගොනු පද්ධති නිරීක්ෂක) හෝ
ආරම්භයේදී අධික කාර්ය භාරයක් ඇති බහාලුම් තුළ සිදු වේ.

**විසඳුම — කාල සීමාව වැඩි කරන්න:**

```bash
# පරිසර විචල්යයක් හරහා (ආරම්භ කිරීම් අතරතුර පවතී):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # මිනිත්තු 3
omniroute serve

# CLI ධජයක් හරහා (එක් වරක් පමණි):
omniroute serve --ready-timeout 180000
```

පෙරනිමි අගය 60 000 ms (60 s) වේ. අනතුරු ඇඟවීම තොරතුරු සැපයීම සඳහා පමණි; සේවාදායකය
පසුබිමේ දිගටම ආරම්භ වන අතර ආරම්භක ක්රියාවලිය සම්පූර්ණ වූ පසු එයට ප්රවේශ විය හැක.

`OMNIROUTE_READY_TIMEOUT_MS` පිළිබඳ සම්පූර්ණ විස්තර සඳහා
