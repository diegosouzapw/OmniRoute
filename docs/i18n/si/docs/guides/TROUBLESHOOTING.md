### නොමිලේ සපයන්නන්හි අනුපාත සීමා කිරීම (429 / 400 / 401)

**ලක්ෂණය**: නොමිලේ/සත්යාපනය අවශ්ය නොවන සපයන්නන් (opencode, auggie, ආදිය) සමඟ `model: "auto"` භාවිත කරන විට, පිළිතුරු වෙනුවට වරින් වර `HTTP 429`, `400`, හෝ `401` ලැබේ. මොහොතකට පසු එම ප්රේරකයම නැවත උත්සාහ කළ විට ඉල්ලීම් සාර්ථක වුවද, පළමු අසාර්ථකත්වයේදීම ස්වයංක්රීයකරණය (cron කාර්යයන්, නියෝජිතයන්, ස්ක්රිප්ට්) බිඳ වැටේ.

**මූලික හේතුව**: ස්වාධීන අසාර්ථකත්ව ආකාර තුනක් එකට එකතු වේ:

1. **සපයන්නාගේ අනුපාත සීමාව (`429`)**: නොමිලේ ස්තරවලට එක් කාල කවුළුවකට අදාළ කෝටාවක් ක්රියාත්මක කළ හැක. සමාන්තර ඇමතුම් සමූහයක් එය අවසන් කරන නිසා, කාල කවුළුව යළි පිහිටුවන තෙක් ඊළඟ ඉල්ලීම ප්රතික්ෂේප වේ.
2. **සෘජු-හුවමාරුවේ බිඳුණු ආකෘතිය (`400`/`401`)**: `auto/*` සංචිතවල, නාමාවලියෙහි ලියාපදිංචි වී ඇති නමුත් සජීවී අක්තපත්ර නොමැති `opencode` වෙතින් සෘජු-හුවමාරු ආකෘති ඇතුළත් විය හැක (උදා. `oc/north-mini-code-free` → `401`). ස්වයංක්රීය මාර්ගකය එකක් උත්සාහ කර අසාර්ථක වන අතර, පසුබැසීම ක්රියාත්මක වීමට පෙර දෝෂය ඉදිරියට පැතිරේ.
3. **සමගාමීත්ව වර්ධනය (බර යටතේ `429`)**: නියෝජිත/cron සැසි කිහිපයක් එකවර `auto` වෙත ඉල්ලීම් යවන විට, සමස්ත ඉල්ලීම් අනුපාතය නොමිලේ සපයන්නන්ට දරාගත හැකි මට්ටම ඉක්මවන බැවින්, නීත්යානුකූල ඇමතුම් පවා අනිසි භාවිතයක් ලෙස සලකුණු වේ.

**තහවුරු කළ විසඳුම (ප්රජාව විසින් වාර්තා කරන ලදී, 2026-08-10)**: නොමිලේ ස්තරයේ නිතර සිදුවන වෙනස්කම් හේතුවෙන් ක්රියාවලිය අසාර්ථක වීමට ඉඩ නොදී, භ්රමණය, සමගාමීත්වය සහ පසුබැසීම මඟින් ඒවා අවශෝෂණය කරගැනීමට පරිසර විචල්ය තුනක් සකසන්න:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ලැබුණු විට වෙනත් ආකෘතියකට/සපයන්නෙකුට මාරු වන්න (බිඳුණු සෘජු-හුවමාරු ආකෘති මඟහරියි)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # බර ඉල්ලීම් සඳහා පැහැදිලි ඇතුළත් කිරීමේ උපරිම සීමාව (පෙරනිමියෙන් සකසා නැත: ඉල්ලීම් ගණනට සීමාවක් නැත, පහත සටහන බලන්න)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # වහාම නැවත උත්සාහ කළ හැකි 503ක් ලබා දෙනවා වෙනුවට, බර ඉල්ලීම් ධාරිතාව සඳහා වැඩි සීමාකළ පොරොත්තු කාලයක්
```

OmniRoute ක්රියාවලියේ පරිසරය තුළ මේවා සකසන්න (daemon එක, උදා. LaunchAgent plist හෝ `systemctl edit` හරහා), ඉන්පසු OmniRoute නැවත ආරම්භ කරන්න. භ්රමණ ධජය ඉහළම බලපෑමක් ඇති තනි සැකසුමයි: එය දෘඪ අසාර්ථකත්වයක්, සංචිතයේ සෞඛ්ය සම්පන්න සපයන්නෙකුට එරෙහි පාරදෘශ්ය නැවත උත්සාහයක් බවට පරිවර්තනය කරයි.

**සටහන**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` මඟින් එකවර ධාවනය වන බර — දිගු-සන්දර්භ — ඉල්ලීම් සංඛ්යාව සීමා කරයි; මෙම සීමාව ඇතුළත් කිරීමේ දොරටුවක් මිස සපයන්නාගේ අනුපාත සීමාකාරකයක් නොවේ. **#503-fanout යාවත්කාලීනය:** මෙම විචල්යය තවදුරටත් පෙරනිමියෙන් සකසනු නොලැබේ (දැන් එය අදාළ වන්නේ ඉහත ආකාරයට පැහැදිලිව වින්යාස කළ විට පමණි) — ඒ වෙනුවට, ධාරකයේ සැබෑ මතක උපරිම සීමාව අනුව ස්වයංක්රීයව පරිමාණය වන, ස්වයංක්රීයව ව්යුත්පන්න කළ බයිට් අයවැයක් (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) මඟින් බර ඉල්ලීම් ඇතුළත් කිරීම පාලනය කෙරේ. එබැවින් නව යෙදවීමකදී මෙම විචල්යය කිසිසේත් සකස් නොකරම `503 chat_admission_busy` ප්රතික්ෂේප කිරීම් බෙහෙවින් අඩු විය යුතුය; මෙහි එය පැහැදිලිව සැකසීම තවමත් ලේඛනගත කළ ආකාරයටම ක්රියා කරයි. පැහැදිලි බයිට්-අයවැය අතික්රමණ 8 MiB–2 GiB අතරට සීමා කෙරේ. `413 body_exceeds_budget` යනු තාවකාලික තත්ත්වයක් නොවේ: එම බයිට් අයවැය වැඩි කරන්න, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` අඩු කරන්න, හෝ ක්රියාවලියේ මතක උපරිම සීමාව වැඩි කරන්න. `inflight_bytes_budget` හේතුවෙන් ඉල්ලීමක් ඉවත් කිරීම තාවකාලික තරගකාරීත්වයක් වන අතර නැවත උත්සාහ කළ හැක. එක් එක් සපයන්නා සඳහා වන අනුපාත සීමා කිරීම (`open-sse/services/rateLimitManager.ts`) වෙනමම `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, සහ `RATE_LIMIT_AUTO_ENABLE` මඟින් පාලනය වේ — `.env.example` බලන්න.

**එය ක්රියා කළ බව තහවුරු කරන ආකාරය**: ඔබගේ නියෝජිතයා/cron එක ඉක්මන් අනුක්රමයකින් දෙවරක් ධාවනය කර, දෙකම සාර්ථක වන බව තහවුරු කරන්න. විසඳුමට පෙර, දෙවන ධාවනය සාමාන්යයෙන් `429`/`401` ලබා දෙයි. විසඳුමෙන් පසු, අසාර්ථකවීම් (ඇත්නම්) පාරදෘශ්යව නැවත උත්සාහ කෙරෙන අතර ඇමතුම සම්පූර්ණ වේ. ඔබට `curl /monitoring/health` ද ධාවනය කර, සපයන්නාගේ සම්බන්ධතාවල `rateLimitedUntil` ක්ෂේත්රය සහ බලපෑමට ලක් වූ සපයන්නන් සඳහා `circuitBreakers.providerBreakers[].state` නිරීක්ෂණය කළ හැක — තත්ත්වය `CLOSED`, `DEGRADED`, `OPEN`, හෝ `HALF_OPEN` යන ඒවායින් එකකි (`src/shared/utils/circuitBreaker.ts` බලන්න), සහ දිගින් දිගටම අසාර්ථක වන සපයන්නෙකු, යළි පිහිටුවීමේ කාල කවුළුව පරීක්ෂණ ඉල්ලීමකට ඉඩ දීමට පෙර (`HALF_OPEN`), `CLOSED → DEGRADED → OPEN` ලෙස මාරු වේ.

**ඔබට තවමත් 429 දිස්වන්නේ නම්**: එම සැපයුම්කරු සඳහා සක්රිය ගිණුමේ _quota_ සැබවින්ම අවසන් වී ඇත (rate පමණක් නොවේ). OmniRoute dashboard → Providers → Accounts වෙත ගොස් එම සැපයුම්කරු සඳහා දෙවන ගිණුමක් එක් කරන්න, නැතහොත් වෙනත් නොමිලේ සැපයුම්කරුවෙකු (උදා. `routeway`, `auggie`) සමඟ මිශ්රව භාවිත කරන්න. මාරුවෙන් මාරුවට භාවිත කිරීම උපකාරී වන්නේ තාවකාලික rate/400/401 දෝෂ සඳහා පමණි; quota එක සම්පූර්ණයෙන් අවසන් වී ඇත්නම් දෙවන අක්තපත්රයක් හෝ වෙනත් සැපයුම්කරුවෙකු අවශ්ය වේ.

**vision models (`auto/vision`, `bazaarlink/*`) භාවිතයේදී ඔබට 403 දිස්වන්නේ නම්**: සම්බන්ධිත ගිණුමට vision ඇතුළත් ගෙවීම් සැලැස්මක් නොමැති වීම හෝ API key එකට ප්රමාණවත් අවසර නොමැති වීම මෙයට හේතුවයි. key scope එකට vision/multimodal ඇතුළත් බව සැපයුම්කරුගේ dashboard එකෙහි තහවුරු කරන්න, නැතහොත් ගෙවීම් මට්ටමේ ගිණුමක් සම්බන්ධ කර එය vision target එක ලෙස තබා ගන්න.

## npm install අනතුරු ඇඟවීම් (ERESOLVE / peer / deprecated)

ඔබ `npm install -g omniroute` ධාවනය කරන විට, `npm warn ERESOLVE`, peer-dependency දැනුම්දීම් සහ `deprecated` පණිවිඩ වැනි අනතුරු ඇඟවීම් විශාල ප්රමාණයක් දැකිය හැක. **මේවා අපේක්ෂිත අතර හානිකර නොවේ.** ප්රතිදානයේ `added <N> packages` දිස්වන්නේ නම් ඔබේ ස්ථාපනය සාර්ථක වී ඇත.

මෙම අනතුරු ඇඟවීම් පැමිණෙන්නේ OmniRoute විසින් පාලනය නොකරන තෙවන පාර්ශ්ව පැකේජවල යල් පැන ගිය peer-dependency පරාසවලිනි:

1. **`marked-terminal` සඳහා `marked >=1 <16` අවශ්ය නමුත් `marked@18` හමු විය** — ප්රායෝගිකව නිසි ලෙස ක්රියා කරයි; upstream peer පරාසය යල් පැන ගොස් ඇත.
2. **`deprecated prebuild-install@7.1.3`** — transitive native-binary ලබාගැනීමේ උපකාරකයකි. එය pin කර ඇති `wreq-js` transport binding එක ස්ථාපනය කිරීමට
   භාවිත නොකරන අතර web-cookie provider transport සැකසුම අසාර්ථක වූ බවක්
   එයින් නොපෙන්වයි.

**කිසිදු ක්රියාමාර්ගයක් අවශ්ය නොවේ** — upstream පැකේජ fork කිරීමකින් තොරව මෙම අනතුරු ඇඟවීම් සම්පූර්ණයෙන් නිහඬ කළ නොහැක.

### පිවිසුම් පිටුව බිඳ වැටීම හෝ "Module self-registration" දෝෂය පෙන්වීම

**හේතුව:** ඔබ ධාවනය කරන්නේ OmniRoute විසින් අනුමත කරන ලද ආරක්ෂිත ධාවන පරිසරයේ අවම සීමාවෙන් පිටත Node.js අනුවාදයකි. වඩාත්ම පොදු අවස්ථාව වන්නේ OmniRoute හට අවශ්ය යාවත්කාලීන කළ ආරක්ෂක අවම සීමාවට වඩා පහළ පැරණි Node 22 හෝ 24 පැච් මට්ටමක් ධාවනය කිරීමයි.

**රෝග ලක්ෂණ:**

- පිවිසුම් පිටුව හිස් තිරයක් හෝ සේවාදායක දෝෂයක් පෙන්වයි
- කොන්සෝලය `Error: Module did not self-register` හෝ එවැනි ස්වදේශීය බැඳීම් දෝෂ පෙන්වයි
- ධාවන පරිසරය සහාය දක්වන ආරක්ෂිත ප්රතිපත්තියෙන් පිටත නම්, පිවිසුම් පිටුව ඔබේ Node අනුවාදය සහිත **තැඹිලි පැහැති අනතුරු ඇඟවීමේ බැනරයක්** පෙන්වයි

**විසඳුම:**

1. සහාය දක්වන Node.js LTS නිකුතුවක් ස්ථාපනය කරන්න (නිර්දේශිත: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ඔබේ අනුවාදය තහවුරු කරන්න: `node --version` මඟින් 24.x LTS පෙළෙහි `v24.0.0` හෝ ඊට නව අනුවාදයක් පෙන්විය යුතුය
3. OmniRoute නැවත ස්ථාපනය කරන්න: `npm install -g omniroute`
4. නැවත ආරම්භ කරන්න: `omniroute`

> **සහාය දක්වන ආරක්ෂිත අනුවාද:** `>=22.22.2 <23` හෝ `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) සහ Node.js 26 සඳහා පූර්ණ සහාය ඇත.

### npm v11+: `better-sqlite3` ස්ථාපනය වී නැත (මොඩියුලය සොයාගත නොහැක)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**හේතුව:** npm v11 (Node.js 24+ සමඟ සපයනු ලබන) පෙරනිමියෙන් විකල්ප
පරායත්තතා සඳහා ස්ථාපන ස්ක්රිප්ට් අවහිර කරයි. `better-sqlite3` යන්න `optionalDependencies`
තුළ ලැයිස්තුගත කර ඇති අතර ස්වදේශීය සම්පාදනය (`node-gyp rebuild`) අවශ්ය බැවින්, npm එය නිහඬව මඟ හරියි.

**රෝග ලක්ෂණ:**

- ආරම්භයේදී `Cannot find module 'better-sqlite3'` සමඟ සේවාදායකය බිඳ වැටෙයි
- `ls node_modules/better-sqlite3` මඟින් "No such file or directory" පෙන්වයි
- `npm ls better-sqlite3` මඟින් `(empty)` පෙන්වයි

**විසඳුම:**

1. ස්ථාපන ස්ක්රිප්ට් අනුමත කර නැවත ස්ථාපනය කරන්න:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. නැතහොත් පෙර සම්පාදිත පැකේජය අතින් ස්ථාපනය කරන්න:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. එය ක්රියා කරන බව තහවුරු කරන්න: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**හේතුව:** ගෝලීය `npm install -g omniroute` ක්රියාත්මක කිරීමෙන් පසු, පැකේජය තුළ ඇති `better-sqlite3` ස්වදේශීය ද්විමය ගොනුව දේශීයව ධාවනය වන ගෘහනිර්මාණයට හෝ Node.js ABI වෙත වඩා වෙනස් එකක් සඳහා සම්පාදනය වී තිබිය හැකිය. පෙර සම්පාදිත ද්විමය ගොනුව ඔබේ පරිසරයට නොගැළපෙන විට මෙය macOS මත (Apple Silicon සහ Intel යන දෙකෙහිම) බහුලව සිදු වේ.

**රෝග ලක්ෂණ:**

- ආරම්භයේදීම `dlopen` දෝෂයක් සමඟ සේවාදායකය අසාර්ථක වේ
- දෝෂයේ `slice is not valid mach-o file` අඩංගු වේ
- සම්පූර්ණ උදාහරණය:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**විසඳුම — ඔබේ දේශීය පරිසරය සඳහා නැවත සම්පාදනය කරන්න (Node.js පහළ අනුවාදයකට මාරුවීම අවශ්ය නොවේ):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
```

## ක්ලවුඩ් ගැටලු

### ක්ලවුඩ් සමමුහුර්ත කිරීමේ දෝෂ

1. `BASE_URL` ඔබගේ ක්රියාත්මක වන instance එක වෙත යොමු වන බව තහවුරු කරන්න (උදා., `http://localhost:20128`)
2. `CLOUD_URL` ඔබගේ ක්ලවුඩ් endpoint එක වෙත යොමු වන බව තහවුරු කරන්න (උදා., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` අගයන් server-side අගයන් සමඟ ගැළපෙන ලෙස තබා ගන්න

### ක්ලවුඩ් `stream=false` මඟින් 500 ලැබීම

**රෝග ලක්ෂණය:** ප්රවාහ නොවන ඇමතුම් සඳහා ක්ලවුඩ් endpoint එකෙහි `Unexpected token 'd'...` පෙන්වයි.

**හේතුව:** client එක JSON බලාපොරොත්තු වන අතර upstream එක SSE payload එකක් ආපසු ලබා දෙයි.

**තාවකාලික විසඳුම:** ක්ලවුඩ් වෙත සෘජු ඇමතුම් සඳහා `stream=true` භාවිත කරන්න. දේශීය runtime එකෙහි SSE→JSON fallback ඇතුළත් වේ.

### ක්ලවුඩ් සම්බන්ධ වී ඇති බව පෙන්වූවත් "Invalid API key" පෙන්වීම

1. දේශීය dashboard එකෙන් (`/api/keys`) නව key එකක් සාදන්න
2. ක්ලවුඩ් සමමුහුර්ත කිරීම ක්රියාත්මක කරන්න: Enable Cloud → Sync Now
3. පැරණි/සමමුහුර්ත නොකළ keys සඳහා ක්ලවුඩ් එකෙන් තවමත් `401` ලැබිය හැක

## Docker ගැටලු

### Docker IPv6 / සම්බන්ධතාව යළි පිහිටුවීම

<a name="docker-ipv6"></a>

**රෝග ලක්ෂණ:** `curl http://localhost:20128/v1/models` මඟින් `curl: (56) Recv failure: Connection reset by peer` ආපසු ලැබේ. Dashboard එක සහ සත්යාපනය අවශ්ය නොවන endpoints ක්රියා කරයි, නමුත් සත්යාපනය කළ endpoints අසාර්ථක වේ — මෙය සත්යාපන ගැටලුවක් ලෙස පෙනුණද එසේ නොවේ.

**හේතුව:** `docker run -p 20128:20128` මඟින් `0.0.0.0` (IPv4) සහ `::` (IPv6) යන දෙකෙහිම ප්රකාශනය සිදු කරයි, නමුත් container එක තුළ ඇති process එක සවන් දෙන්නේ IPv4 මත පමණි. `localhost` පළමුව `::1` වෙත resolve වන hosts වලදී, සම්බන්ධතාව පිටුපස listener එකක් නොමැතිව IPv6 මත ප්රකාශිත port එක වෙත යොමු වේ → සම්බන්ධතාව යළි පිහිටුවේ.

**විසඳුම:**

1. **ඉක්මන් රෝග විනිශ්චය:** `curl -4 http://localhost:20128/v1/models` ධාවනය කරන්න. එය `-4` සමඟ ක්රියා කර එය නොමැතිව අසාර්ථක වේ නම්, ඔබට IPv6 bind නොගැළපීමක් ඇත.
2. **ස්ථිර විසඳුම:** ඔබගේ `docker run` විධානය තුළ `-p 127.0.0.1:20128:20128` භාවිත කරමින් IPv4 වෙත පැහැදිලිව bind කරන්න:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   මෙය IPv4 bind කිරීම බලගන්වන අතර සියලුම host interfaces මත proxy එක නිරාවරණය වීමද වළක්වයි.

## දෝෂ නිරාකරණය

### Log ගොනු සක්රීය කිරීම

ඔබගේ `.env` ගොනුව තුළ `APP_LOG_TO_FILE=true` සකසන්න. Application logs `logs/` යටතේ ලියනු ලැබේ.
සැකසුම් තුළ call log pipeline එක සක්රීය කර ඇති විට request artifacts `${DATA_DIR}/call_logs/` යටතේ ගබඩා කෙරේ.
Pipeline capture එක සක්රීය කර ඇති විට stream chunk payloads ඉවත් කිරීමට `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` සකසන්න, නැතහොත් KB වලින් artifact සීමාව වෙනස් කිරීමට `CALL_LOG_PIPELINE_MAX_SIZE_KB` සකස් කරන්න.

### Runtime ගබඩාව

- ප්රධාන තත්ත්වය: `${DATA_DIR}/storage.sqlite` (providers, combos, aliases, keys, settings)
- භාවිතය: `storage.sqlite` තුළ ඇති SQLite වගු (`usage_history`, `call_logs`, `proxy_logs`) + විකල්ප `${DATA_DIR}/call_logs/`
- Application logs: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` විට)
- Call log artifacts: call log pipeline එක සක්රීය කර ඇති විට `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs පිටුවේ **Clean history** ක්රියාව මඟින් `call_logs`, පැරණි
`request_detail_logs`, සහ දේශීය `${DATA_DIR}/call_logs/` artifact directory එක හිස් කරයි.

## Circuit Breaker ගැටලු

### සැපයුම්කරු OPEN තත්ත්වයේ සිරවී ඇත

සැපයුම්කරුවෙකුගේ circuit breaker එක OPEN තත්ත්වයේ ඇති විට, cooldown කාලය අවසන් වන තෙක් ඉල්ලීම් අවහිර කෙරේ.

**විසඳුම:**

1. **Dashboard → Settings → Resilience** වෙත යන්න
2. බලපෑමට ලක් වූ සැපයුම්කරුගේ circuit breaker කාඩ්පත පරීක්ෂා කරන්න
3. සියලු breakers ඉවත් කිරීමට **Reset All** ක්ලික් කරන්න, නැතහොත් cooldown කාලය අවසන් වන තෙක් රැඳී සිටින්න
4. reset කිරීමට පෙර සැපයුම්කරු සැබවින්ම ලබා ගත හැකි බව තහවුරු කරගන්න

### සැපයුම්කරු නැවත නැවතත් circuit breaker එක ක්රියාත්මක කරයි

### "Unsupported model" දෝෂය

- පළමු කොටස ඔබට අක්තපත්ර ඇති සැපයුම්කරුවෙකු වන model id එකක් භාවිත කරන්න (`openai/whisper-1`, `openrouter/deepgram/nova-3`). සැපයුම්කරු උපසර්ගය නොමැති `deepgram/nova-3` සඳහා ස්වදේශීය Deepgram යතුරක් අවශ්ය වේ.
- සැපයුම්කරු **Dashboard → Providers** තුළ සම්බන්ධ වී ඇති බව තහවුරු කරන්න

- සහාය දක්වන ශ්රව්ය ආකෘති පරීක්ෂා කරන්න: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ගොනු ප්රමාණය සැපයුම්කරුගේ සීමාවන් තුළ ඇති බව තහවුරු කරන්න (සාමාන්යයෙන් < 25MB)
- සැපයුම්කරුගේ කාඩ්පතේ API යතුරේ වලංගුභාවය පරීක්ෂා කරන්න

### පොදු ආකෘති ගැටලු

- **Thinking tags නොපෙනීම** — ඉලක්ක සැපයුම්කරු thinking සඳහා සහාය දක්වන්නේද සහ thinking budget සැකසුමද පරීක්ෂා කරන්න
- **Tool calls ඉවත් වීම** — ඇතැම් ආකෘති පරිවර්තන සහාය නොදක්වන fields ඉවත් කළ හැක; Playground ප්රකාරය තුළ තහවුරු කරන්න
- **System prompt නොමැති වීම** — Claude සහ Gemini system prompts වෙනස් ලෙස හසුරුවයි; පරිවර්තන ප්රතිදානය පරීක්ෂා කරන්න
- **SDK එක object එකක් වෙනුවට raw string එකක් ලබා දීම** — v1.x තුළ විසඳා ඇත; OpenAI SDK Pydantic වලංගුකරණ අසාර්ථක වීම් ඇති කරන සම්මත නොවන fields (`x_groq`, `usage_breakdown`, ආදිය) response sanitizer මඟින් ඉවත් කරයි. ඔබ තවමත් v3.x+ මත මෙය දකින්නේ නම්, කරුණාකර issue එකක් ගොනු කරන්න.
- **GLM/ERNIE විසින් `system` role එක ප්රතික්ෂේප කිරීම** — v1.x තුළ විසඳා ඇත; නොගැළපෙන models සඳහා role normalizer මඟින් system messages ස්වයංක්රීයව user messages තුළට ඒකාබද්ධ කරයි. ඔබ තවමත් v3.x+ මත මෙය දකින්නේ නම්, කරුණාකර issue එකක් ගොනු කරන්න.
- **`developer` role එක හඳුනා නොගැනීම** — v1.x තුළ විසඳා ඇත; OpenAI නොවන සැපයුම්කරුවන් සඳහා ස්වයංක්රීයව `system` බවට පරිවර්තනය කරයි. ඔබ තවමත් v3.x+ මත මෙය දකින්නේ නම්, කරුණාකර issue එකක් ගොනු කරන්න.
- **`json_schema` Gemini සමඟ ක්රියා නොකිරීම** — v1.x තුළ විසඳා ඇත; `response_format` දැන් Gemini හි `responseMimeType` + `responseSchema` බවට පරිවර්තනය කෙරේ. ඔබ තවමත් v3.x+ මත මෙය දකින්නේ නම්, කරුණාකර issue එකක් ගොනු කරන්න.

### ඝාතීය පසුබැසීම සුසර කිරීම

### සමූහගත සමකාලීන ඉල්ලීම් වැළැක්වීම

## විකල්ප RAG / LLM අසාර්ථකතා වර්ගීකරණය (ගැටලු 16ක්)

සමහර OmniRoute පරිශීලකයින් gateway එක RAG හෝ agent stacks ඉදිරියෙන් ස්ථානගත කරයි. එවැනි සැකසුම්වල අමුතු රටාවක් දැකීම සාමාන්ය දෙයකි: OmniRoute සෞඛ්ය සම්පන්න බව පෙනේ (providers ක්රියාත්මකයි, routing profiles නිවැරදියි, rate limit alerts නැත), නමුත් අවසාන පිළිතුර තවමත් වැරදියි.

ප්රායෝගිකව, මෙම සිදුවීම් සාමාන්යයෙන් gateway එකෙන්ම නොව, downstream RAG pipeline එකෙන් හටගනී.

එම අසාර්ථකතා විස්තර කිරීම සඳහා හවුල් පාරිභාෂික වචන මාලාවක් අවශ්ය නම්, නැවත නැවත ඇතිවන RAG / LLM අසාර්ථකතා රටා දහසයක් නිර්වචනය කරන බාහිර MIT බලපත්රලාභී පාඨ සම්පතක් වන WFGY ProblemMap භාවිත කළ හැකිය. ඉහළ මට්ටමින් එය පහත දෑ ආවරණය කරයි:

- retrieval drift සහ බිඳුණු context සීමා
- හිස් හෝ යල්පැන ගිය indexes සහ vector stores
- embedding සහ අර්ථමය නොගැළපීම්
- prompt එකලස් කිරීමේ සහ context window ගැටලු
- තර්කනය බිඳවැටීම සහ අධිවිශ්වාසී පිළිතුරු
- දිගු chain සහ agent සම්බන්ධීකරණ අසාර්ථකතා
- multi agent මතකය සහ භූමිකා drift
- deployment සහ bootstrap අනුපිළිවෙළ සම්බන්ධ ගැටලු

අදහස සරලයි:

1. නරක ප්රතිචාරයක් විමර්ශනය කරන විට, පහත දෑ ග්රහණය කරගන්න:
   - පරිශීලක කාර්යය සහ ඉල්ලීම
   - OmniRoute හි route හෝ provider combo එක
   - downstream හි භාවිත කළ ඕනෑම RAG context එකක් (ලබාගත් ලේඛන, tool calls ආදිය)
2. සිදුවීම WFGY ProblemMap අංක එකකට හෝ දෙකකට (`No.1` … `No.16`) සිතියම්ගත කරන්න.
3. OmniRoute logs අසල ඔබේම dashboard, runbook, හෝ incident tracker තුළ එම අංකය ගබඩා කරන්න.
4. ඔබේ RAG stack, retriever, හෝ routing strategy වෙනස් කළ යුතුද යන්න තීරණය කිරීමට අදාළ WFGY පිටුව භාවිත කරන්න.

1. අහඹු secret එකක් ජනනය කරන්න: `openssl rand -hex 32`
2. නිෂ්පාදන server env එකෙහි (සහ bridge එක සමඟ සන්නිවේදනය කරන ඕනෑම client එකක) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` සකසන්න
3. OmniRoute නැවත ආරම්භ කරන්න

### Responses API: background mode එක synchronous ආකාරයට පහත හෙළා ඇත

**රෝග ලක්ෂණ:**

- වාර්තා වූ අනතුරු ඇඟවීම: `background mode degraded to synchronous`
- `background: true` request එකක් background job handle එකක් වෙනුවට සාමාන්ය synchronous response එකක් ලබා දෙයි

**හේතුව:** අනතුරු ඇඟවීමක් නිකුත් කරන අතරතුර, v3.8.0 විසින් Responses API හි `background: true` හිතාමතාම synchronous ක්රියාත්මක කිරීමකට පහත හෙළයි. සම්පූර්ණ async background ක්රියාත්මක කිරීම අනාගතයේ ලබා දීමට නියමිත හැකියාවකි.

**විසඳුම:**

- `background` නොමැතිව ඇමතුම සිදු කිරීමට client එක සකසන්න, හෝ
- සම්පූර්ණ async background mode එක ඇතුළත් පසු නිකුතුවක් සඳහා රැඳී සිටින්න (changelog එක නිරීක්ෂණය කරන්න)

## මන්දගාමී ආරම්භය / සූදානම් වීමේ කාල සීමාව ඉක්මවීම

CLI එක `⚠ සේවාදායකය තත්පර 60ක් ඇතුළත ප්රතිචාර නොදැක්වීය` යනුවෙන් පෙන්වන නමුත් සේවාදායකය
සැබැවින්ම ක්රියා කරන්නේ නම්, ඔබේ පරිසරය සඳහා සූදානම් බව පරීක්ෂා කිරීමේ කාල සීමාව ප්රමාණවත් නොවේ.

මෙය සාමාන්යයෙන් Windows මත (ප්රතිවෛරස, ගොනු පද්ධති නිරීක්ෂක) හෝ
ආරම්භයේදී අධික කාර්ය භාරයක් ඇති කන්ටේනර් තුළ සිදු වේ.

**විසඳුම — කාල සීමාව වැඩි කරන්න:**

```bash
# පරිසර විචල්යයක් හරහා (ආරම්භ කිරීම් අතරතුර පවතී):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # මිනිත්තු 3
omniroute serve

# CLI ධජයක් හරහා (එක් වරක් පමණි):
omniroute serve --ready-timeout 180000
```

පෙරනිමි අගය 60 000 ms (60 s) වේ. අනතුරු ඇඟවීම තොරතුරු සැපයීම සඳහා පමණි; සේවාදායකය
පසුබිමේ දිගටම ආරම්භ වන අතර ආරම්භය සම්පූර්ණ වූ පසු එයට ප්රවේශ විය හැක.

`OMNIROUTE_READY_TIMEOUT_MS` පිළිබඳ සම්පූර්ණ
විස්තර සඳහා [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) බලන්න.
