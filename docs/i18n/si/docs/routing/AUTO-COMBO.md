## වින්යාස-රහිත ස්වයංක්රීය රවුටින් (`auto/` උපසර්ගය)

> **නව:** combo එකක් සෑදීම අවශ්ය නොවේ. ඕනෑම client එකක සෘජුවම `auto/` උපසර්ගය භාවිත කරන්න.

### ඉක්මන් උදාහරණ

| ආකෘති ID       | ප්රභේදය | හැසිරීම                                                                          |
| -------------- | ------- | -------------------------------------------------------------------------------- |
| `auto`         | පෙරනිමි | සම්බන්ධිත සියලු providers, LKGP උපායමාර්ගය, සමතුලිත බර                           |
| `auto/coding`  | coding  | ගුණාත්මකභාවයට ප්රමුඛත්වය දෙන බර, කේත ජනනය සඳහා සුදුසුය                           |
| `auto/fast`    | fast    | අඩු ප්රමාදයක් සහිත බරිත තේරීම                                                    |
| `auto/cheap`   | cheap   | පිරිවැය-ප්රශස්ත කළ රවුටින් (අඩුම පිරිවැය පළමුව)                                  |
| `auto/offline` | offline | වැඩිම quota ලබාගත හැකි providers වෙත ප්රමුඛත්වය දෙයි                             |
| `auto/smart`   | smart   | වඩා හොඳ ආකෘති සොයාගැනීම සඳහා ගුණාත්මකභාවයට ප්රමුඛත්වය + ඉහළ ගවේෂණ අනුපාතය (10%)  |
| `auto/lkgp`    | lkgp    | පැහැදිලි LKGP (පෙරනිමි `auto` හා සමානයි)                                         |
| `auto/chaos`   | chaos   | ඔරොත්තු දීමේ හැකියාව පරීක්ෂා කිරීම සඳහා දෝෂ-එන්නත් කිරීමේ බර (chaos engineering) |

### ප්රවර්ගය × ස්තරය සංයෝජනය (`auto/<category>:<tier>`)

OpenRouter-ආකාරයේ suffix මඟින් **කුමන ආකාරයේ මාර්ගයක්ද** (category) යන්න **එය ප්රශස්ත කරන්නේ කෙසේද** (tier) යන්නෙන් වෙන් කරයි. එබැවින් ඒවා නිදහසේ සංයෝජනය කළ හැකිය (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **ප්රවර්ග** (හැකියාව අනුව candidate pool එක පෙරහන් කරන්න): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` මඟින් vision හැකියාව ඇති ආකෘති තබා ගනී; `reasoning` මඟින් reasoning/thinking ආකෘති තබා ගනී.
- **ස්තර** (ලකුණුකරණ බර / pool filter එක තෝරන්න): `fast` (ඉක්මනින් නිකුත් කිරීම) · `cheap` (`floor` යන alias එක, පිරිවැය ඉතිරි කරන්නා) · `reliable` (circuit-breaker සෞඛ්යය + ප්රමාද ස්ථායීතාව) · `free` / `pro` (`classifyTier` හරහා ආකෘති ස්තරය අනුව pool එක පෙරහන් කරන්න — free-tier එදිරිව premium).

| උදාහරණය                | විසඳෙන්නේ                                                         |
| ---------------------- | ----------------------------------------------------------------- |
| `auto/coding:fast`     | coding pool, අඩු-ප්රමාද බර                                        |
| `auto/coding:cheap`    | coding pool, පිරිවැය-ප්රශස්ත කළ (`auto/coding:floor` යන alias එක) |
| `auto/reasoning:pro`   | reasoning/thinking ආකෘති පමණි, premium ස්තරය                      |
| `auto/vision`          | vision හැකියාව ඇති ආකෘති (ස්තරයක් නැත → සමතුලිත බර)               |
| `auto/multimodal:free` | multimodal හැකියාව ඇති ආකෘති, free ස්තරය පමණි                     |

වලංගු ඕනෑම `auto/<category>[:<tier>]` එකක් ඉල්ලුම මත විසඳනු ලැබේ; තෝරා සැකසූ උපකුලකයක් `/v1/models` සහ dashboard එක තුළ ප්රචාරණය කෙරේ (`open-sse/services/autoCombo/builtinCatalog.ts` තුළ `AUTO_SUFFIX_VARIANTS`). පෙරහන් කිරීම **fail-open** වේ — සීමාවකට ගැළපෙන සම්බන්ධිත ආකෘති කිසිවක් නොමැති නම්, රවුටින් කිසිවිටෙක බිඳ නොවැටෙන ලෙස සම්පූර්ණ pool එක භාවිත කෙරේ. මූලික scorer එක (`combo.ts`) වෙනස් කර නොමැත; category/tier filter එක `buildAutoCandidates` තුළ යොදනු ලැබේ.

> **සජීවී ආකෘති බුද්ධිය:** `ARENA_ELO_SYNC_ENABLED` flag එක සක්රිය විට, සජීවී **Arena ELO** ශ්රේණිගත කිරීම් + **models.dev** ස්තර දත්ත මඟින් ස්වයංක්රීය රවුටින් යෝග්යතාව තීරණය කිරීමට සහාය වේ (එසේ නොමැති විට ස්ථිතික fitness map එක භාවිත කරයි).

**භාවිත කරන ආකාරය:**

```bash
# OpenAI ආකෘතියට සහාය දක්වන ඕනෑම IDE හෝ CLI මෙවලමක්
මූලික URL: http://localhost:20128/v1
API යතුර:  <your-endpoint-key>

# ඔබගේ කේතය/වින්යාසය තුළ model එක මෙසේ සකසන්න:
model: "auto"                 # සමතුලිත පෙරනිමිය
model: "auto/coding"          # coding කාර්යයන් සඳහා හොඳම එක
model: "auto/fast"            # ලබාගත හැකි වේගවත්ම එක
model: "auto/cheap"           # token එකකට ලාභම එක
```

**සිදු වන්නේ කුමක්ද:**

1. OmniRoute විසින් `src/sse/handlers/chat.ts` තුළ ඇති `auto/` උපසර්ගය හඳුනා ගනී
2. database එකෙන් සියලුම **සක්රිය provider සම්බන්ධතා** විමසයි
3. වලංගු credentials (API key හෝ OAuth token) ඇති ඒවාට පෙරහන් කරයි
4. එක් එක් සම්බන්ධතාව සඳහා ආකෘතිය තීරණය කරයි (`connection.defaultModel` හෝ providerගේ පළමු ආකෘතිය)
5. memory තුළ **virtual combo** එකක් සාදයි (DB තුළ ගබඩා නොකෙරේ)

### එක් එක් key සඳහා candidate පාලනය (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` ට පසු ඇති suffix එක, හෝ
මූලික channel එක සඳහා භාවිත වන `auto` යන literal එක) යනු `auto/*` channel එකක වත්මන්
candidate pool එක සජීවී ළඟා විය හැකි තත්ත්වය සමඟ ලැයිස්තුගත කරන **කියවීමට-පමණක්** endpoint එකකි.
මෙය පවතින resilience reads නැවත භාවිත කරයි (raw breaker `state` කිසිවිටෙක භාවිත නොකරයි):

- provider circuit breaker — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- connection cooldown — විසඳන ලද `provider_connections` row එකේ `rateLimitedUntil` / `testStatus`

API යතුරකට වෙන් වෙන්ව (`auto_candidate_overrides` වගුව, සංක්රමණය `128`) ගබඩා කෙරේ — OmniRoute යනු
`users` වගුවක් නොමැති තනි-කුලීකරු පද්ධතියක් වන බැවින්, `apiKeyId` යනු සැබෑ ලෙස පවතින ඇමතුම්කරු-විශේෂිත
අනන්යතාවයට ආසන්නතම අගයයි — එමෙන්ම ඒවා pure, ඒකක-පරීක්ෂිත
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) හරහා

## සැබෑ Model Id එකකට ගැළපෙන Combo නම්

හිස් model id එකකට සමාන `name` එකක් ඇති combo එකක් (උදා. `gpt-5.5` නමින් ඇති combo එකක්) යනු දෝෂයක් නොව, **හිතාමතාම සපයන සහය දක්වන රටාවකි**: එය [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) හි ලේඛනගත කර ඇති එක් එක් model id සඳහා provider fallback යාන්ත්රණයයි. හිස්-model-id විසඳීමට පෙර combo විසඳීම පරීක්ෂා කරන බැවින් (`src/sse/services/model.ts` හි `getComboForModel()`), හිස් id එක වන `gpt-5.5` සඳහා ඉල්ලීමක් සෘජුවම තනි provider කෙනෙකු වෙත යැවීම වෙනුවට combo එකේ targets හරහා (උදා. `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) යොමු කරයි — මෙය [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) සඳහා ගොඩනැගූ combo-before-rewrite ප්රමුඛතාව නැවත භාවිත කරන අතර `tests/unit/responses-combo-resolution-3227.test.ts` සහ `tests/unit/combo-name-codex-responses-rewrite.test.ts` මඟින් regression පරීක්ෂාවට ලක් කර ඇත.

සැබෑ model id එකක් සඟවන නමකට combo එකක් සෑදීම හෝ නැවත නම් කිරීම **කිසිවිටෙක ප්රතික්ෂේප නොකෙරේ** — එසේ කිරීමෙන් මෙම ලේඛනගත workflow එක බිඳ වැටෙනු ඇත. ඒ වෙනුවට (#8530), (නව) නම සැබෑ model id එකක් සමඟ ගැටෙන විට `POST /api/combos` සහ `PUT /api/combos/[id]` response එකට ක්රියාකාරිත්වය අවහිර නොකරන `warning` field එකක් එක් කරයි:

```json

    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

Boot වන අවස්ථාවේදී, `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) ද model id එකක් සඟවන සෑම පවතින combo එකක්ම ලැයිස්තුගත කරමින් එක් පේළියක `[STARTUP]` අනතුරු ඇඟවීමක් log කරයි. එමඟින් #6940 අනුව හිතාමතා කරනවාට වඩා අහම්බෙන් මෙයට මුහුණ දෙන operators හට සංඥාවක් ලැබේ. හඳුනාගැනීමේ helper එක `src/lib/combos/modelNameCollision.ts` හි ඇත.

## Client එකකින් Custom Combo එකක් ඇමතීම

Persist කර ඇති combos (Settings → Combos) භාවිත වන්නේ client එක `model` field එකෙහි combo එකේ **නිශ්චිත නම** යවන විට පමණි — combo නම සඳහා fuzzy හෝ partial matching නොමැති අතර `auto/` prefix එකක්ද සම්බන්ධ නොවේ. විසඳීමේ අනුපිළිවෙළ (`src/sse/services/model.ts` හි `getComboForModel()`):

1. නිශ්චිත combo-name ගැළපීම (`model: "my-combo"`),
2. `combo/<name>` prefix එක (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

පොදු වැරදි අවබෝධ දෙකක්:

- **`auto` ඔබගේ combos භාවිත නොකරයි.** `auto`/`auto/*` තමන්ගේම zero-config candidate pool එකක් ගොඩනඟන අතර, `auto` යන නමම ඇති combo එකක් තිබේ නම් පමණක් persist කර ඇති combos සලකා බලයි (නිර්දේශ නොකෙරේ). Combo එකක් හරහා යොමු කිරීමට, `auto` නොව එහි නිශ්චිත නම යවන්න.
- **`openrouter/auto` යනු සැබෑ ගෙවීම් සහිත OpenRouter නිෂ්පාදනයකි** ("Auto Best Available"), OmniRoute alias එකක් නොවේ. එය OpenRouter registry එකේ (`open-sse/config/providers/registry/openrouter/index.ts`) ඇති එකම static model entry එක වන අතර ඒ සඳහා වෙනම ගාස්තු අය කෙරේ. එය `auto` pools වෙතින් ඉවත් කිරීමට Settings → Routing → Hide paid models භාවිත කරන්න.

මෙහි ලේඛනගත කර ඇති මුල් ව්යාකූලතාව සඳහා [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) සහ [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) බලන්න.

`weighted` යනු **එක් එක් ඉල්ලීම සඳහා සමානුපාතික අහඹු තේරීමකි**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), සමකාරකයක් නොවේ:

- එක් එක් ඉල්ලීම `weight / totalWeight` සම්භාවිතාව අනුව **එක්** පියවරක් තෝරා ගනී; ඉතිරි පියවර
  එම ඉල්ලීම සඳහා වන පසුබැසීමේ දාමය ලෙස බරේ අවරෝහණ අනුපිළිවෙළට සකස් කෙරේ.
- බර `0` වන (හෝ බරක් නොමැති) පියවරක්, වෙනත් යම් පියවරක
  බර > 0 වන තාක් **කිසි විටෙක තෝරා නොගනී** — එය භාවිත කළ හැක්කේ තෝරාගත් පියවර අසාර්ථක වූ පසු පසුබැසීමක් ලෙස පමණි. තේරීම ඒකාකාර වන්නේ **සියලු**
  බර 0 වූ විට පමණි.
- සියලු ඉලක්ක ලබාගත නොහැකි පියවර — provider circuit breaker `OPEN`, connection
  cooldown, model lockout — තේරීම සිදුවීමට පෙර ඉවත් කෙරේ
  (`open-sse/services/combo/targetResolution.ts`), එබැවින් සෞඛ්ය සම්පන්න එක් පියවරකට තාවකාලිකව
  සෑම ඉල්ලීමක්ම ජයගත හැක.
- `stickyWeightedLimit` (combo වින්යාසය, පෙරනිමි `1` = අක්රියයි) නැවත තේරීමට පෙර අඛණ්ඩ
  සාර්ථකත්ව ගණනක් සඳහා තෝරාගත් පියවරට ස්ථාවරව තබයි.

දැඩි භ්රමණයක් සඳහා `round-robin` භාවිත කරන්න; `weighted` හි සමාන බර මඟින් ලැබෙන්නේ සංඛ්යානමය — දැඩි
නොවන — සමතුලිතතාවකි.

## Fusion උපායමාර්ගය

`fusion` යනු එක් ඉලක්කයක් තෝරා **නොගන්නා** එකම උපායමාර්ගයයි. එය විමසුම
**සෑම පැනල් මොඩලයකටම සමාන්තරව** යවා, අනතුරුව වින්යාස කළ හැකි **විනිශ්චයකරු මොඩලයක්** මඟින්
සියලු පැනල් ප්රතිචාරවලින් එක් අවසාන පිළිතුරක් සංස්ලේෂණය කරයි. මෙය upstream `decolua/9router`
(OpenRouter හි Fusion සැලසුම) වෙතින් පෝට් කර ඇත; ක්රියාත්මක කිරීම `open-sse/services/fusion.ts` තුළ ඇත.

0. **මෙවලම් සහිත ඉල්ලීම් මඟහැරීම** — හිස් නොවන `tools` අරාවක් සහ
   පැහැදිලිව `"none"` ලෙස සකසා නොමැති `tool_choice` එකක් සහිත ඉල්ලීමක් පැනලය සම්පූර්ණයෙන්ම මඟහරී: එය
   එක් මොඩලයකට (වින්යාස කළ විනිශ්චයකරු හෝ `panel[0]`) සෘජුවම යොමු කෙරෙන අතර `tools`/`tool_choice`
   කිසිදු වෙනසකින් තොරව ඉදිරියට යවනු ලැබේ. පැනල් සාමාජිකයන්ට මෙවලම් ප්රවේශය නොමැති අතර විනිශ්චයකරුගේ
   සංස්ලේෂණ විධානය මෙවලම්-ඇමතුම් නිකුත් කිරීම අධෛර්යමත් කරයි; එම නිසා agentic/මෙවලම්-ඇමතුම් සේවාදායකයන්ට

   කාලගණකයක් ආරම්භ වන අතර, ඉන්පසු එකතු කරගත් ඕනෑම දේ සමඟ fusion ඉදිරියට යයි.

3. **විනිශ්චයකරුගේ සංස්ලේෂණය** — පැනල් පිළිතුරු නිර්නාමික කර (`මූලාශ්රය 1`, `මූලාශ්රය 2`, … — එවිට
   විනිශ්චයකරු මොඩලයේ සන්නාමයට නොව අන්තර්ගතයට බර තබයි) විනිශ්චයකරු වෙත ලබා දෙයි; ඔහු
   එකඟතාව / පරස්පරතා / අර්ධ ආවරණය / අනන්ය අවබෝධයන් / නොපෙනුණු පැති විශ්ලේෂණය කර,
   **එක්** බලයලත් පිළිතුරක් ලියයි. විනිශ්චයකරුගේ ඇමතුම සේවාදායකයාගේ මුල්
   `stream` ධජය + මෙවලම් රඳවා ගනී; එම නිසා streaming සහ පහළ අදියරවල මෙවලම් භාවිතය තවදුරටත් ක්රියා කරයි.

   සෘජුවම ආපසු ලබා දෙයි (ඒකාබද්ධ කිරීමට කිසිවක් නැත); එක් මොඩලයකින් පමණක් සමන්විත පැනලයක් සෘජුවම පිළිතුරු දෙයි.

## අතථ්ය Auto-Combo කර්මාන්තශාලාව

Auto Combo එන්ජිමට පෙර-නිර්වචිත combos අවශ්ය නොවේ. ඒ වෙනුවට, `open-sse/services/autoCombo/virtualFactory.ts` මඟින් අවශ්ය අවස්ථාවේදීම අපේක්ෂකයන් ගොඩනඟයි:

1. `getProviderConnections({ isActive: true })` (සක්රීය කර ඇති සියලු සම්බන්ධතා) ලබාගනී
2. වලංගු අක්තපත්ර ඇති ඒවාට පෙරහන් කරයි (API යතුරක් හෝ `hasUsableOAuthToken()` හරහා කල් ඉකුත් නොවූ OAuth ටෝකනයක්)
3. ආකෘති ලබාගත හැකි බව සහ මිලකරණය සඳහා `getProviderRegistry()` සමඟ හරස්-යොමු කරයි
4. සෑම `(provider, model, connection)` ටියුපලයක් සඳහාම `VirtualAutoComboCandidate` එකක් ගොඩනඟයි
5. යැවීමේ ඉලක්කය ලෙස `connection.defaultModel` (හෝ රෙජිස්ට්රියේ පළමු ආකෘතිය) තෝරයි
6. සාධක 16කින් යුත් `scorePool()` සහ ප්රභේදයේ බර පැකේජය භාවිතයෙන් සෑම අපේක්ෂකයෙකුටම ලකුණු ලබාදෙයි
7. `handleComboChat()` සඳහා ප්රතිඵලයක් ලෙස ලැබෙන මතකය තුළ පවතින `AutoComboConfig` ආපසු ලබාදෙයි — කිසිවිටෙක DB වෙත ස්ථිරව සුරකින්නේ නැත

මෙයින් අදහස් වන්නේ **`auto/*` සක්රීය කර ඇති නව සැපයුම්කරුවෙකු එක් කිරීමෙන් අපේක්ෂක සංචිතය ස්වයංක්රීයව පුළුල් වන බවයි** — combos අතින් සංස්කරණය කිරීමට අවශ්ය නොවේ. එක් එක් ඉල්ලීම සඳහා අතථ්ය combo එක නැවත ගොඩනඟන බැවින්, අලුතින් එක් කළ හෝ නැවත සෞඛ්ය සම්පන්න වූ සම්බන්ධතා වහාම භාවිතයට ගැනේ.

## API

**වෙන්වූ `POST /api/combos/auto` අන්ත ලක්ෂ්යයක් නොමැත** — Auto-Combo පහත ක්රම දෙකෙන් භාවිත කෙරේ:

1. **වින්යාස රහිත (නිර්දේශිත):** `model: "auto"` හෝ `model: "auto/<variant>"` සමඟ ඕනෑම chat completion ඉල්ලීමක් යවන්න. අතථ්ය කර්මාන්තශාලාව එක් එක් ඉල්ලීම සඳහා combo එක ගොඩනඟයි — ස්ථිර සුරැකීමක් හෝ API ඇමතුම් අවශ්ය නොවේ.

2. **`strategy: "auto"` සහිත ස්ථිරව සුරැකි combo එකක්:** `POST /api/combos` හරහා සාමාන්ය combo එකක් සාදා, `strategy: "auto"` සමඟ `config.auto.weights` / `config.auto.candidatePool` සකසන්න. එම ලකුණු ලබාදීමේ එන්ජිමම භාවිත කෙරේ; combo එක `combos` තුළ ගබඩා වන අතර ID මඟින් නැවත භාවිත කළ හැක.

සොයාගැනීම සඳහා, `GET /api/combos/auto` මඟින් විසඳන ලද අපේක්ෂක සංචිතය සහ `context_length` / `max_output_tokens` සමඟ සෑම ප්රභේදයක්ම ලැයිස්තුගත කරයි — ඒවා අපේක්ෂක සංචිතයේ කවුළු අතරින් උපරිම අගයන් වේ. සේවාලාභීන් (උදා. opencode ප්ලගිනය) `0` වෙනුවට මෙම අගයන් ප්රචාරණය කළ යුතුය: ශුන්ය context එකක් opencode හි ස්වයංක්රීය සංකෝචනය සම්පූර්ණයෙන්ම අක්රීය කරයි; එමඟින් gateway හි ඉතිහාස ඉවත් කිරීම context එක විනාශ කරන තෙක් සැසි වර්ධනය වීමට ඉඩ ලැබේ. උපරිම අගය ප්රචාරණය කිරීම ආරක්ෂිතය, මන්ද auto-combo context පෙරහන මඟින් අතිවිශාල ඉල්ලීම් විශාල කවුළු සහිත අපේක්ෂකයන් වෙත යොමු කරන බැවිනි.

### Auto router උපායමාර්ග

ස්ථිරව සුරැකි `strategy: "auto"` combos සඳහා `config.routerStrategy` (හෝ පැරණි
`config.auto.routerStrategy`) පහත ඒවායින් එකකට සැකසිය හැක:

- `rules` — පෙරනිමි බරිත ලකුණු ලබාදීම
- `score` — වින්යාස කර ඇති ඉහළම බරිත ලකුණු අගය තෝරයි. සමාන නිශ්චිත ලකුණු ඇති විට වින්යාස කළ
  අපේක්ෂක අනුපිළිවෙළ රඳවාගනී; පවතින `explorationRate` මඟින් සම්පූර්ණ ශ්රේණිගත සංචිතයෙන් නියැදි ගනී.
- `cost` / `eco` — ලාභම සෞඛ්ය සම්පන්න සැපයුම්කරු
- `latency` / `fast` — විශ්වසනීයත්ව දඬුවමක් සහිත අවම p95 ප්රමාදය
- `sla-aware` / `sla` — p95 ප්රමාදය, දෝෂ අනුපාතය සහ විකල්ප
  පිරිවැය SLOs සපුරාලන අපේක්ෂකයන්ට ප්රමුඛතාව දෙයි
- `lkgp` — අවසන් වරට හොඳ බව දන්නා සැපයුම්කරු පළමුව

### Router උපායමාර්ග සවිස්තරව

Auto-combo එන්ජිම මඟින් `config.routerStrategy` (හෝ පැරණි `config.auto.routerStrategy`)
හරහා මාරු කළ හැකි, ප්ලග් කළ හැකි **RouterStrategy** ක්රියාත්මක කිරීම් 6ක් සපයයි.
එක් එක් උපායමාර්ගය `RoutingContext` එකක් (කාර්ය වර්ගය, tool/vision ඉඟි, ටෝකන් ඇස්තමේන්තුව,
විකල්ප SLA ප්රතිපත්තිය, විකල්ප අවසන් වරට හොඳ බව දන්නා සැපයුම්කරු) මත පදනම්ව
අපේක්ෂක සංචිතයෙන් එක් සැපයුම්කරුවෙකු තෝරයි.

#### 1. `rules` (පෙරනිමි) — සාධක 16ක බරිත ලකුණු ලබාදීම

පවතින ලකුණු ලබාදීමේ එන්ජිම ආවරණය කරයි. `OPEN` circuit-breaker
අපේක්ෂකයන් ඉවත් කර, වත්මන් කාර්ය වර්ගය සහ `getTaskFitness()` සමඟ `scorePool()` ධාවනය කර,
ඉහළම ලකුණු ලැබූ සැපයුම්කරු තෝරයි.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**භාවිත කළ යුත්තේ කවදාද**: පෙරනිමි තේරීමයි. සියලු සංඥා අතර සමබර සම්මුතියක් අවශ්ය විට භාවිත කරන්න.

**අන්වර්ථ නාමය**: `rules` (අන්වර්ථ නාමයක් නැත)

---

#### 2. `cost` / `eco` — ලාභම සෞඛ්ය සම්පන්න සැපයුම්කරු

අපේක්ෂක සංචිතය `costPer1MTokens` අනුව (ආරෝහණව) අනුපිළිවෙළට සකසා ලාභම එක තෝරයි.
පළමුව `OPEN` අපේක්ෂකයන් ඉවත් කරයි.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**භාවිත කළ යුත්තේ කවදාද**: පිරිවැයට සංවේදී කාර්යභාර, කාණ්ඩ සැකසුම් හෝ පසුබිම් කාර්යයන් සඳහා.

**අන්වර්ථ නාම**: `cost`, `eco`

---

#### 3. `latency` / `fast` — විශ්වසනීයත්ව දඬුවමක් සහිත අවම p95 ප්රමාදය

`p95LatencyMs + (errorRate * 1000)` අනුව අනුපිළිවෙළට සකසයි. දෝෂ අනුපාත දඬුවම මඟින්, නාමික ප්රමාදය අඩු වුවද විශ්වාස කළ නොහැකි සැපයුම්කරුවන් පහළින් ශ්රේණිගත කිරීම සහතික කරයි.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**භාවිත කළ යුත්තේ කවදාද**: තත්ය කාලීන කතාබස්, ස්වයංක්රීය සම්පූර්ණ කිරීම, හෝ
අන්තර්ක්රියාකාරී කේතකරණ සහායක වැනි ප්රමාදයට සංවේදී කාර්ය භාර සඳහා.

**අන්වර්ථ නාම**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — ප්රමාද/දෝෂ/පිරිවැය SLO අනුකූලතාව

වින්යාස කර ඇති SLO ප්රතිපත්තිය එක් එක් අපේක්ෂකයා කෙතරම් හොඳින් සපුරාලන්නේද යන්න මත ලකුණු ලබා දෙයි:

| සාධකය         | බර  | සූත්රය                                              |
| ------------- | --- | --------------------------------------------------- |
| ප්රමාද ලකුණ   | 35% | `threshold / max(value, ε)`                         |
| දෝෂ ලකුණ      | 35% | `threshold / max(value, ε)`                         |
| සෞඛ්ය ලකුණ    | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)   |
| පිරිවැය ලකුණ  | 10% | `threshold / max(value, ε)` හෝ ප්රතිලෝම සාමාන්යකරණය |
| ස්ථායිතා ලකුණ | 5%  | ප්රතිලෝම සාමාන්යකරණය කළ ප්රමාද සම්මත අපගමනය         |

`hardConstraints: true` වූ විට, අපේක්ෂකයන් ප්රධාන වශයෙන් **උල්ලංඝන ලකුණ**
(ඔවුන් කිසියම් SLO එකක් කොපමණ ඉක්මවා යන්නේද) අනුවත්, ඉන්පසු සංයුක්ත ලකුණ අනුවත් අනුපිළිවෙළට සකසනු ලැබේ. එසේ නොමැති නම් භාවිත වන්නේ
සංයුක්ත ලකුණ පමණි.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... ප්රතිපත්තියට සාපේක්ෂව එක් එක් අපේක්ෂකයාට ලකුණු ලබා දෙයි: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA ක්ෂේත්ර** (combo වින්යාසය මත සකසන්න):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**භාවිත කළ යුත්තේ කවදාද**: දැඩි ප්රමාද, දෝෂ අනුපාත, හෝ පිරිවැය අයවැය සහිත නිෂ්පාදන කාර්ය භාර සඳහා.

**අන්වර්ථ නාම**: `sla-aware`, `sla`

---

#### 5. `lkgp` — අවසන් වරට හොඳ යැයි දන්නා සැපයුම්කරු පළමුව

පළමුව **අවසන් වරට හොඳ යැයි දන්නා සැපයුම්කරු** (සකසා ඇත්නම්) උත්සාහ කර, ඉන්පසු
`rules` උපායමාර්ගය වෙත පසුබසියි. සැසිය එකම සැපයුම්කරුට බැඳ තැබීම සඳහා මෙය ප්රයෝජනවත් වේ — සංවාදයක
පසු විමසුම් එකම සැපයුම්කරු විසින් හසුරුවනු ලැබේ.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // rules උපායමාර්ගය වෙත පසුබසින්න
    return getStrategy("rules").select(pool, context);
  }
}
```

**භාවිත කළ යුත්තේ කවදාද**: පසු විමසුම් එකම සැපයුම්කරු විසින් හැසිරවීමට ඔබට අවශ්ය බහු-වාර සංවාද සඳහා
(උදා., හැඹිලිගත කිරීම, සන්දර්භ අඛණ්ඩතාව, හෝ මිලකරණ අනුකූලතාව සඳහා).

**අන්වර්ථ නාමය**: `lkgp` (අන්වර්ථ නාමයක් නැත)

### අභිරුචි රවුටර් උපායමාර්ග

පොදු API හරහා ඔබට ඔබේම `RouterStrategy` ක්රියාත්මක කිරීමක් ලියාපදිංචි කළ හැකිය:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // ඔබේ රවුටින් තර්කනය මෙහි යොදන්න
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

ඉන්පසු එය භාවිත කරන්න:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## Auto ප්රභේද සාරාංශය

හිස් `auto` (පෙරනිමි) සහ `autoPrefix.ts` තුළ ප්රකාශිත `AutoVariant` අගයන් 6 ඇතුළුව, **කැඳවිය හැකි model ID 7ක්** ඇත:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` විසින්ම අගයන් 6ක් ලැයිස්තුගත කරයි; 7 වන විකල්පය "ප්රභේදයක් නැත" යන්නයි — හිස් `auto` — එය `parseAutoPrefix()` මඟින් `variant: undefined` ලෙස හසුරුවයි.)

## Tiers Auto-Combo සමඟ ගැළපෙන ආකාරය

සාධක 16කින් යුත් ලකුණු කිරීමේ ශ්රිතය (`open-sse/services/autoCombo/scoring.ts`) tier සාමාජිකත්වය සංඥා දෙකක් ලෙස සලකයි: `tierPriority` (0.0476) සහ `tierAffinity` (0.0476). සම්පූර්ණ `DEFAULT_WEIGHTS` කට්ටලය සඳහා ඉහත ඇති සම්මත [ලකුණු කිරීමේ සාධක වගුව](#how-it-works-persisted-auto-combos) බලන්න — එක් එක් pack සඳහා වන අභිබවා යෙදීම් (ship-fast/cost-saver/quality-first/offline-friendly) "එක් එක් pack සඳහා බර පැතිකඩ" වගුවේ ලැයිස්තුගත කර ඇත.

Tier එක පමණක් Tier 1 පළමුව යෙදීම **බලාත්මක නොකරයි** — Tier 1 ප්රමාදය නරක නම් හෝ පිරිවැයට සාපේක්ෂ ගුණාත්මකභාවය ප්රශස්ත නොවේ නම්, Tier 2 ජය ගනී. Tier අනුපිළිවෙළ බලාත්මක කිරීමට, combo උපායමාර්ගය `priority` ලෙස භාවිත කර සපයන්නන් tier අනුව සකසන්න.

Tier 1 (දායකත්වය) සඳහා දැඩි ප්රමුඛතාවක් ලබා දීමට, `tierPriority` බර වැඩි කරන්න:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

Tier අර්ථ දැක්වීම් සහ සපයන්නන් වර්ගීකරණය සඳහා `docs/marketing/TIERS.md` බලන්න.

## පරීක්ෂණ සහ ආවරණය

### නිශ්චිත routing-තීරණ අනුකෘතිය (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` විසින් mock කළ upstream එකක් සමඟ සැබෑ combo pipeline එක හරහා පොදු උපායමාර්ග 19ම සඳහා routing **තීරණය** ආරම්භයේ සිට අවසානය දක්වා තහවුරු කරයි. ආවරණයට පහත දෑ ඇතුළත් වේ:

- `ROUTING_STRATEGY_VALUES` උපායමාර්ග 19ම (ordered, weighted, cost, context, fusion, …).
- `quota-share` (අභ්යන්තර) ආරම්භයේ සිට අවසානය දක්වා: සැබෑ `selectQuotaShareTarget` seam එක (`registerQuotaFetcher` / `setLKGP` / `__setHeadroomSaturationFetcherForTests`) හරහා DRR සාධාරණත්වය + සංතෘප්ති ප්රමුඛතාව අඩු කිරීම.
- සෑම target සංඛ්යාවක් පුරාම `context-relay` සාර්වත්රික-handoff ආවරණය.

මෙම suite එක CI තුළ (`test:integration` job) `--test-concurrency=1` සහ `--test-force-exit` සමඟ ධාවනය වන බැවින් එය නිශ්චිත වන අතර සජීවී අක්තපත්ර අවශ්ය නොවේ.
