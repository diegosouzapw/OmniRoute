මෙම මාර්ගෝපදේශය භාවිත කර pull request එකක් සඳහා විශ්වාසදායක කුඩාම සංවර්ධන චක්රය තෝරාගන්න. මෙය පහත සබැඳි කර ඇති ක්ෂේත්ර-විශේෂිත ගෘහනිර්මාණ සහ ආරක්ෂක ලේඛන ප්රතිස්ථාපනය නොකරයි; එය සෑම පොදු වෙනස්කම් වර්ගයක්ම එහි ගිවිසුම්, ඉලක්කගත පරීක්ෂා සහ CI ආවරණය සමඟ සම්බන්ධ කරයි.

## සෑම වෙනස්කමක්ම අනුගමනය කරන මාර්ගය

1. **සංස්කරණය කිරීමට පෙර මූලික ශාඛාව තෝරන්න.** ඉහළම සක්රිය `release/v*` ශාඛාව සොයා එහි අගයෙන් නව ශාඛාවක් සාදන්න. `main` නොව, එම ශාඛාව ඉලක්ක කරන්න. නිකුතු අත්හිටුවීමක් සක්රිය නම්, අත්හිටුවා ඇති ශාඛාව ඉලක්ක නොකරන්න; [ශාඛාකරණ සහ නිකුතු ආකෘතිය](BRANCHING_MODEL.md) හි විස්තර කර ඇති මීළඟ සක්රිය චක්රය භාවිත කරන්න.
2. **ගිවිසුම් නම් කරන්න.** වෙනස්කම බලපාන සෑම නාමාවලියක්ම, schema එකක්ම, ජනනය කළ artifact එකක්ම, පොදු API එකක්ම හෝ පරිශීලක අතුරුමුහුණතක්ම හඳුනාගන්න. පහත වගුව අවම ආරම්භක කට්ටලය ලබා දෙයි.
3. **ඉලක්කගත පරීක්ෂණ ලියන්න හෝ යාවත්කාලීන කරන්න.** `src/`, `open-sse/`, `electron/`, හෝ `bin/` තුළ ඇති නිෂ්පාදන වෙනස්කම් සඳහා එම PR එක තුළම ස්වයංක්රීය පරීක්ෂණයක් අවශ්ය වේ. හැසිරීම සනාථ කරන කුඩාම පරීක්ෂණ ගොනු පළමුව ධාවනය කර, පසුව ලැයිස්තුගත කර ඇති ඉලක්කගත gates ධාවනය කරන්න.
4. **පුළුල් matrix එක ධාවනය කිරීමට CI වෙත ඉඩ දෙන්න.** සම්පූර්ණ unit shards, Vitest, coverage ratchet සහ නිෂ්පාදන build එක PR එක මත ධාවනය වේ. ඉලක්කගත අසමත් වීමක් වඩා පුළුල් බලපෑමක් පෙන්වන විට හෝ වෙනස්කම උපපද්ධති කිහිපයක් හරහා විහිදෙන විට පමණක් පුළුල් suite එකක් ස්ථානීයව ධාවනය කරන්න.
5. **සමාලෝචනයට පෙර සමපාත කරන්න.** සක්රිය මූලික ශාඛාව fetch කර, එහි නව commits සහ එයට සාපේක්ෂව ඔබේ diff එක පරීක්ෂා කර, දායකත්ව කාර්ය ප්රවාහයට අනුව මූලික ශාඛාව rebase හෝ merge කරන්න. ජනනය කළ ගොනු සහ නාමාවලි ගැටුම් ඒවායේ මූලාශ්රයෙන් විසඳා, ඒවා නැවත ජනනය කර, ඉලක්කගත චක්රය නැවත ධාවනය කර, PR එක තවමත් සක්රිය නිකුතු ශාඛාව ඉලක්ක කරන බව තහවුරු කරන්න.
6. **සාක්ෂි සටහන් කරන්න.** PR සැකිල්ල තුළ ධාවනය කළ commands, එක් කළ හෝ වෙනස් කළ සෑම පරීක්ෂණ ගොනුවක්ම, migrations හෝ feature flags, සහ තවමත් පොරොත්තුවෙන් ඇති CI-පමණක් වලංගුකිරීම් ලැයිස්තුගත කරන්න.

## වෙනස්කම් වර්ගය අනුව සම්මත මාර්ග

පහත commands අවම ඉලක්කගත පරීක්ෂා වන අතර, ඔබ වෙනස් කළ හැසිරීම සෘජුවම ආවරණය කරන පරීක්ෂණයක් මඟ හැරීමට අවසරයක් නොවේ.

### Provider

**ගිවිසුම්**

- `src/shared/constants/providers/` තුළ ඇති Provider අර්ථදැක්වීම සහ `src/shared/constants/providers.ts` තුළ එහි සංයෝජනය.
- `open-sse/config/providerRegistry.ts` හෝ එයින් වෙන් කරගත් registry ගොනු තුළ ඇති models සහ capabilities.
- අදාළ වන විට executor/translator තේරීම, OAuth හෝ API-key වින්යාසය, dashboard assets සහ ජනනය කළ provider යොමුව.
- පොදු credentials විසින් `resolvePublicCred()` භාවිත කළ යුතුය; දෝෂ ප්රතිචාර විසින් හවුල් sanitized error helpers භාවිත කළ යුතුය. `docs/security/PUBLIC_CREDS.md` (git තුළ ඇත; `/docs` වෙත compile නොවේ) සහ [දෝෂ පිරිසිදුකරණය](../security/ERROR_SANITIZATION.md) බලන්න.

**ඉලක්කගත චක්රය**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # නාමාවලිය වෙනස් වන විට; ජනනය කළ diff එක commit කරන්න
npm run lint
```

බලපෑමට ලක් වූ සෑම request family එකක්ම ද පරීක්ෂා කරන්න: chat, Responses, images, embeddings, audio, හෝ video. ජනනය කළ නාමාවලි සහ golden diffs ගිවිසුම් වෙනස්කම් ලෙස සමාලෝචනය කරන්න; ඒවා අන්ධ ලෙස පිළි නොගන්න.

## දේශීය candidate ලූපය

මූලාශ්ර පරීක්ෂණවලට ඇසුරුම් කළ artifact එක ආරම්භ වන බව තහවුරු කළ නොහැක: ඇසුරුම් ලැයිස්තු, කප්පාදු කළ dependencies,
සහ native binaries අසාර්ථක වන්නේ tarball එක ස්ථාපනය කර ආරම්භ කළ පසුව පමණි. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) යනු RFC #8084 හි එක් වරක් build කිරීම / වලංගු කිරීම / ප්රවර්ධනය කිරීමේ ප්රවාහයේ
දේශීය පැත්තයි: එය එක් candidate එකක් build කරයි, එම නිශ්චිත artifact එක වලංගු කරයි, directory
නැවත නම් කිරීමෙන් එය ප්රවර්ධනය කරයි, සහ ප්රවර්ධිත slot එකේ health check එක අසාර්ථක වූ විට එය ආපසු හරවයි.

```bash
npm run dev:candidate -- run --dry-run --json  # සැලැස්ම මුද්රණය කරන්න, කිසිවක් වෙනස් නොකරන්න
npm run dev:candidate -- run                   # build කිරීම + වලංගු කිරීම + ප්රවර්ධනය කිරීම, ස්වයංක්රීයව ආපසු හැරවීම
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ තුළට ස්ථාපනය කිරීම
npm run dev:candidate -- validate --id <id>    # හිස් port එකක ආරම්භ කර, /api/health + /v1/models පරීක්ෂා කිරීම
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current සහ previous මාරු කිරීම
npm run dev:candidate -- run --from-tarball <file.tgz>  # වෙනත් ස්ථානයක (CI) build කළ tarball එකක් නැවත භාවිත කිරීම
```

- **එක් වරක් build කරන්න.** `build` වත්මන් tree එක pack කරයි (එයට `dist/server.js` අවශ්ය බැවින්, පළමුව
  `npm run build:release` ක්රියාත්මක කරන්න) හෝ `--from-tarball` පිටපත් කරයි, ඉන්පසු tarball එකෙහි
  `node_modules` නොමැති නිසා එය හුදකලා npm prefix එකකට ස්ථාපනය කරයි. id එක කෙටි `HEAD`
  sha එකයි (tree එකෙහි දේශීය වෙනස්කම් තිබේ නම් `-dirty`) හෝ tarball එකක් සඳහා `tgz-<sha256>` වේ. දැනටමත්
  build කර ඇති වෙනස්කම් රහිත id එකක් නැවත build කිරීම වෙනුවට නැවත භාවිත කෙරේ; එය නැවත build කිරීමට `--force` යොදන්න.
- **මූලාශ්රය නොව package එක වලංගු කරන්න.** `validate` නැවුම් `DATA_DIR=<candidate>/data`, ව්යාජ secrets සමඟ
  ස්ථාපිත CLI එක (`serve --port <free port>`) ආරම්භ කරයි, තවද operatorගේ `OMNIROUTE_API_KEY`,
  `STORAGE_ENCRYPTION_KEY` සහ `INITIAL_PASSWORD` environment එකෙන් ඉවත් කරයි; එමඟින් එය නැවුම් ස්ථාපනයක
  යතුරු-රහිත loopback සැකසුම පරීක්ෂා කරයි. එය `GET /api/health` මඟින් 200 ලැබෙන තෙක් රැඳී සිටී,
  `GET /v1/models` මඟින් 200 ලැබීම අනිවාර්ය කරයි, process group එක නවත්වයි, සහ tarball hash එක සමඟ
  තීන්දුව `validation.json` තුළ සටහන් කරයි.
- **එම artifact එකම ප්රවර්ධනය කරන්න.** එහි වත්මන් tarball hash එක සඳහා සාර්ථක validation එකක් නොමැති
  candidate එකක් `promote` විසින් ප්රතික්ෂේප කරයි. පෙරනිමි active slot එක `_artifacts/candidate/current` වේ;
  `--target <dir>` මඟින් එම filesystem එකේ වෙනත් directory එකක් තෝරන අතර, එහි previous slot එක
  `<dir>.previous` වේ. සෑම rename කිරීමක්ම atomic වන අතර, අතරමඟදී අසාර්ථක වුවහොත් දැනටමත් සිදු කළ
  rename කිරීම් ආපසු හරවයි.
- **ආපසු හරවන්න.** `run` ප්රවර්ධිත slot එක නැවත වලංගු කර, එම පරීක්ෂාව අසාර්ථක වූ විට `current` සහ
  `previous` යළි මාරු කරයි. පළමු validation එක අසාර්ථක වන candidate එකක් කිසිවිටෙක ප්රවර්ධනය නොකෙරේ.

සියල්ල gitignore කළ `_artifacts/candidate/` යටතේ ලියනු ලැබේ; පවතින OmniRoute
ස්ථාපනයක් සහ එහි data directory එක කිසිවිටෙක වෙනස් නොකෙරේ. ප්රවර්ධිත CLI එක
`_artifacts/candidate/current/prefix/bin/omniroute` වේ; ඔබ එය භාවිත කරන විට ඔබේම `DATA_DIR` සමඟ
එය ආරම්භ කරන්න. Exit codes: `0` සාර්ථකයි, `1` validation හෝ promotion අසාර්ථකයි, `2` භාවිත දෝෂයක් හෝ build එක නොමැත.

## ප්රතිසන්ධාන පිරික්සුම් ලැයිස්තුව

සමාලෝචනය ඉල්ලා සිටීමට පෙර:

- PR පදනම තවමත් ඉහළම සක්රිය `release/v*` ශාඛාව බව තහවුරු කරන්න.
- එම පදනම fetch කර, ඔබ ශාඛාව නිර්මාණය කළ පසු එක් වූ commit සමාලෝචනය කරන්න.
- අහඹු හෝ ජනනය කළ අනවශ්ය වෙනස්කම් සඳහා `git diff <active-base>...HEAD` සමාලෝචනය කරන්න.
- මූලාශ්රය යාවත්කාලීන කර ප්රතිදානය නැවත ජනනය කිරීමෙන් නාමාවලි සහ ජනනය කළ ලේඛන ගැටුම් විසඳන්න.
- ප්රතිසන්ධානයෙන් පසු PR විස්තරයේ ලැයිස්තුගත කර ඇති සෑම ඉලක්කගත පරීක්ෂණයක්/ද්වාරයක්ම නැවත ධාවනය කරන්න.
- වෙනස් වූ පදනමකට ගැළපීම සඳහා පමණක් කිසිවිටෙක ප්රකාශන දුර්වල කිරීම හෝ අවශ්ය පරීක්ෂණ ඉවත් කිරීම නොකරන්න.
