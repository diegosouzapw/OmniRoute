පුල් රික्वෙස්ට් එකක් සඳහා කුඩාම විශ්වාසදායක සංවර්ධන චක්රය තෝරා ගැනීමට මෙම මාර්ගෝපදේශය භාවිත කරන්න. මෙය
පහත සබැඳි කර ඇති ක්ෂේත්රයට විශේෂිත වාස්තු විද්යා සහ ආරක්ෂක ලේඛන ප්රතිස්ථාපනය නොකරයි; ඒ වෙනුවට, එක් එක් පොදු
වෙනස්කම් වර්ගය එහි ගිවිසුම්, ඉලක්කගත පරීක්ෂණ සහ CI ආවරණය සමඟ සම්බන්ධ කරයි.

## සෑම වෙනස්කමක්ම අනුගමනය කරන මාර්ගය

1. **සංස්කරණය කිරීමට පෙර පාදක ශාඛාව තෝරන්න.** සක්රියව පවතින ඉහළම `release/v*` ශාඛාව සොයා එහි
   අග්රයෙන් නව ශාඛාවක් සාදන්න. `main` නොව, එම ශාඛාව ඉලක්ක කරන්න. නිකුතු අත්හිටුවීමක් ක්රියාත්මක නම්, අත්හිටුවා ඇති
   ශාඛාව ඉලක්ක නොකරන්න; ඒ වෙනුවට
   [ශාඛාකරණ සහ නිකුතු ආකෘතිය](BRANCHING_MODEL.md) හි විස්තර කර ඇති ඊළඟ සක්රිය චක්රය භාවිත කරන්න.
2. **ගිවිසුම් නම් කරන්න.** වෙනස්කම බලපාන සෑම නාමාවලියක්, schema එකක්, ජනනය කළ කෘතියක්, පොදු API එකක් හෝ පරිශීලක
   අතුරුමුහුණතක්ම හඳුනා ගන්න. පහත වගුව අවම ආරම්භක කට්ටලය දක්වයි.
3. **ඉලක්කගත පරීක්ෂණ ලියන්න හෝ යාවත්කාලීන කරන්න.** `src/`, `open-sse/`, `electron/`, හෝ
   `bin/` හි නිෂ්පාදන වෙනස්කම් සඳහා එම PR එක තුළම ස්වයංක්රීය පරීක්ෂණයක් අවශ්ය වේ. හැසිරීම සනාථ කරන කුඩාම
   පරීක්ෂණ ගොනු පළමුව ධාවනය කර, පසුව ලැයිස්තුගත කර ඇති ඉලක්කගත දොරටු ධාවනය කරන්න.
4. **පුළුල් න්යාසය CI මඟින් ධාවනය වීමට ඉඩ දෙන්න.** සම්පූර්ණ unit shards, Vitest, coverage ratchet, සහ
   නිෂ්පාදන build එක PR එක මත ධාවනය වේ. ඉලක්කගත අසමත් වීමක් වඩා පුළුල් බලපෑමක් පෙන්වන විට හෝ වෙනස්කම උපපද්ධති
   කිහිපයක් හරහා විහිදෙන විට පමණක් පුළුල් පරීක්ෂණ කට්ටලයක් දේශීයව ධාවනය කරන්න.
5. **සමාලෝචනයට පෙර සමථයකට පත් කරන්න.** සක්රිය පාදකය fetch කර, එහි නව commits සහ එයට සාපේක්ෂව ඔබේ diff එක පරීක්ෂා කර,
   පසුව දායක කාර්ය ප්රවාහයට අනුව පාදකය rebase හෝ merge කරන්න. ජනනය කළ ගොනු සහ නාමාවලි ගැටුම් ඒවායේ මූලාශ්රයෙන්
   විසඳා, ඒවා නැවත ජනනය කර, ඉලක්කගත චක්රය නැවත ධාවනය කර, PR එක තවමත් සක්රිය නිකුතු ශාඛාව ඉලක්ක කරන බව තහවුරු කරන්න.
6. **සාක්ෂි සටහන් කරන්න.** PR අච්චුව තුළ, ධාවනය කළ commands, එක් කළ හෝ වෙනස් කළ සෑම පරීක්ෂණ ගොනුවක්ම,
   migrations හෝ feature flags, සහ තවමත් අපේක්ෂිත CI-පමණක් වලංගුකරණ සියල්ල ලැයිස්තුගත කරන්න.

## වෙනස්කම් වර්ගය අනුව ප්රධාන මාර්ග

පහත commands අවම ඉලක්කගත පරීක්ෂණ වේ; ඔබ වෙනස් කළ
හැසිරීම සෘජුවම ආවරණය කරන පරීක්ෂණයක් මඟ හැරීමට ඒවා අවසරයක් නොවේ.

### Provider

**ගිවිසුම්**

- `src/shared/constants/providers/` හි Provider අර්ථදැක්වීම සහ
  `src/shared/constants/providers.ts` හි එහි සංයෝජනය.
- `open-sse/config/providerRegistry.ts` හෝ එයින් වෙන් කළ registry ගොනු තුළ ඇති models සහ capabilities.
- අදාළ වන විට executor/translator තේරීම, OAuth හෝ API-key වින්යාසය, dashboard assets, සහ ජනනය කළ
  provider යොමුව.
- පොදු credentials සඳහා `resolvePublicCred()` භාවිත කළ යුතුය; error responses සඳහා හවුල් sanitized
  error helpers භාවිත කළ යුතුය. `docs/security/PUBLIC_CREDS.md` (git තුළ ඇත; `/docs` වෙත compile නොකෙරේ) සහ
  [දෝෂ සනීපාරක්ෂණය](../security/ERROR_SANITIZATION.md) බලන්න.

**ඉලක්කගත චක්රය**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # නාමාවලිය වෙනස් වන විට; ජනනය කළ diff එක commit කරන්න
npm run lint
```

බලපෑමට ලක්වන සෑම request family එකක්ම පරීක්ෂා කරන්න: chat, Responses, images, embeddings, audio, හෝ video.
ජනනය කළ නාමාවලි සහ golden diffs ගිවිසුම් වෙනස්කම් ලෙස සමාලෝචනය කරන්න; ඒවා අන්ධ ලෙස පිළි නොගන්න.

### Routing

**ගිවිසුම්**

- `src/shared/constants/routingStrategies.ts` හි පොදු strategy values සහ UI metadata.
- `open-sse/services/combo.ts` සහ `open-sse/services/combo/` යටතේ dispatch සහ ordering.

- හැසිරීම වෙනස් වන විට [Auto-Combo එන්ජිම](../routing/AUTO-COMBO.md) සහ resilience ලේඛන.

**ඉලක්කගත චක්රය**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy හෝ dispatch වෙනස්කම්
npm run check:known-symbols      # strategy ලියාපදිංචි කිරීමේ වෙනස්කම්
npm run lint
```

දේශීයව නිශ්චිත ප්රතිඵල ලබා දෙන mocked-upstream පරීක්ෂණ භාවිත කරන්න. සජීවී combo smoke පරීක්ෂණ සඳහා credentials අවශ්ය වන අතර ඒවා
අතින් සිදු කළ යුතුය; ඒවා CI සඳහා ආදේශක නොවේ.

### UI / UX

**ගිවිසුම්**

- `src/app/` සහ `src/shared/components/` යටතේ Next.js route/page සහ හවුල් component සීමා.
- API response shapes, loading/empty/error states, keyboard සහ screen-reader හැසිරීම,
  responsive layout, theming, සහ locale expansion.
- `src/i18n/messages/en.json` හි ඉංග්රීසි UI මූලාශ්ර strings; නව user-facing copy hard-code නොකරන්න.

**ඉලක්කගත චක්රය**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

අන්තර්ක්රියා හෝ දෘශ්ය වෙනස්කම් සඳහා app එක ධාවනය කර පටු සහ පුළුල් viewports දෙකම පරීක්ෂා කරන්න. CI මඟින්
නිෂ්පාදන build එක සහ පුළුල් පරීක්ෂණ කට්ටල ධාවනය කරයි; එහෙත් දෘශ්ය හැසිරීම සඳහා වෙනස්කමට සුදුසු ඉලක්කගත component,
Playwright, හෝ ලේඛනගත අතින් කරන පරීක්ෂණයක් තවමත් අවශ්ය වේ.

### i18n

**ගිවිසුම්**

- `src/i18n/messages/en.json` යනු UI මූලාශ්රයයි; `config/i18n.json` යනු locale මූලාශ්රයයි.
- CLI නාමාවලි `bin/cli/locales/` යටතේ වෙන්ව පවතී.
- ICU placeholders සහ tags හරියටම සුරකින්න. product/provider/model නම්,
  protocol සහ header නම්, commands, code/JSON identifiers, URLs, environment variables, හෝ
  `OmniRoute`, `OAuth`, `MCP`, සහ `A2A` වැනි ආරක්ෂිත පද පරිවර්තනය නොකරන්න. වත්මන් මූලාශ්ර ලැයිස්තුව
  `scripts/i18n/glossary/protected-terms.json` වේ.

**ඉලක්කගත චක්රය**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI strings/නාමාවලි වෙනස් වන විට
npm run lint
```

මෙය පවතින පද්ධතිය සඳහා මාර්ගෝපදේශයකි; එහි tooling හෝ key model එක පුළුල් කිරීමට කරන ආරාධනයක් නොවේ.
ප්රතිස්ථාපන පද්ධතිය සැලසුම් කරමින් පවතින අතරතුර i18n patches ඉතා සීමිතව තබා ගන්න. කාර්යය මඟින් ජනනය කළ පරිවර්තන පැහැදිලිවම අවශ්ය කරන්නේ නම් සහ
ප්රතිඵලයක් ලෙස ලැබෙන diff එක ඔබ සමාලෝචනය කර ඇත්නම් මිස, බාහිර සේවා කැඳවන පරිවර්තන
commands ධාවනය නොකරන්න.

### CLI

**ගිවිසුම්**

- `bin/cli/` තුළ ඇති පොදු විධාන සහ flags, ජනනය කළ API විධාන, exit codes, stdout/stderr සහ
  JSON ප්රතිදාන හැඩතල, config/environment හැසිරීම, සහ ඇසුරුම් කළ ගොනු.
- CLI පරිශීලකයාට පෙනෙන පෙළ CLI i18n ස්තරය භාවිත කළ යුතු අතර `en`/`pt-BR` නාමාවලි සමමුහුර්තව තබාගත යුතුය.
- සහාය දක්වන runtime එක ලෙස Node සහ ප්රකාශිත binary ගිවිසුම සුරකින්න.

**ඉලක්කගත චක්රය**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # ජනනය කළ/එක් කළ CLI වෙනස්කම්
npm run check:pack-policy     # package මතුපිට වෙනස්කම්
npm run lint
```

හැසිරීම parsing, ගොනු, හෝ exit status මත රඳා පවතින විට තාවකාලික data directory එකක් තුළ නිශ්චිත විධානයම භාවිත කරන්න. CI මඟින් වඩා පුළුල් package artifact සහ ecosystem පරීක්ෂා සිදු කරයි.

### දත්ත සමුදාය

**ගිවිසුම්**

- `src/lib/db/` යටතේ ඇති domain modules; නිශ්චිත modules සෘජුව import කරන්න (පැරණි `localDb.ts` re-export ස්තරය ඉවත් කර ඇත).
- `src/lib/db/migrations/` යටතේ ඇති අංකිත, idempotent SQL migrations, transaction ආරක්ෂාව, upgrade
  හැසිරීම, indexes, සහ schema එකෙන් බලපෑමට ලක්වන සෑම caller එකක්ම.
- Routes සහ handlers කිසිවිටෙක raw SQL සෘජුව නිකුත් නොකරයි.

**ඉලක්කගත චක්රය**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

migration එකක් එක් කරන විට නව දත්ත සමුදායක් සහ පෙර schema එකෙන් upgrade කිරීම යන දෙකම පරීක්ෂා කරන්න. දත්ත සමුදා පරීක්ෂණ
handles වසා cleanup අතරතුර `resetDbInstance()` ඇමතිය යුතුය. උපරිම උත්සාහයක් ලෙස පවත්වාගෙන යන Bun adapter මාර්ගය වෙනස් වන විට පමණක් `npm run test:bun:db` ධාවනය කරන්න; Node තවදුරටත් ප්රාමාණික වේ.

### Build කිරීම / යෙදවීම

**ගිවිසුම්**

- Root සහ workspace manifests/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/`
  package අන්තර්ගතය, Electron platform metadata, CI workflows, සහ deployment sentinels.
- සහාය දක්වන Node පරාස සහ `CLAUDE.md` තුළ allow-list කර ඇති Bun භාවිතය නොවෙනස්ව පැවතිය යුතුය.
- Build artifacts tracking නොකර තබන්න; dependency, license, workflow, සහ package ප්රතිපත්ති අදාළ වේ.

**ඉලක්කගත චක්රය**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency හෝ lockfile වෙනස්කම්
npm run check:pack-policy      # ප්රකාශිත package මතුපිට වෙනස්කම්
npm run lint
```

වෙනස්කම compilation, standalone assembly, assets,
හෝ runtime bundling වෙත බලපාන විට පමණක් දේශීයව `npm run build` භාවිත කරන්න. Release/deploy validation සඳහා පමණක් `npm run build:release` භාවිත කරන්න. CI හි build එක
අවසාන cross-platform සංඥාවයි; platform-specific Electron වෙනස්කම් සඳහා ගැළපෙන ඉලක්කගත build එක හෝ smoke සාක්ෂි අවශ්ය වේ.

## ප්රතිසන්ධාන පිරික්සුම් ලැයිස්තුව

සමාලෝචනය ඉල්ලීමට පෙර:

- PR පදනම තවමත් ඉහළම සක්රිය `release/v*` ශාඛාව බව තහවුරු කරන්න.
- එම පදනම ලබාගෙන, ඔබ ශාඛාව සෑදූ පසු එක් කළ commit සමාලෝචනය කරන්න.
- අහඹු හෝ ජනනය කළ අනවශ්ය වෙනස්කම් සඳහා `git diff <active-base>...HEAD` සමාලෝචනය කරන්න.
- මූලාශ්රය යාවත්කාලීන කර ප්රතිදානය නැවත ජනනය කිරීමෙන් නාමාවලි සහ ජනනය කළ ලේඛනවල ගැටුම් විසඳන්න.
- ප්රතිසන්ධානයෙන් පසු PR විස්තරයේ ලැයිස්තුගත කර ඇති සෑම කේන්ද්රගත පරීක්ෂණයක්/ද්වාරයක්ම නැවත ධාවනය කරන්න.
- වෙනස් වූ පදනමකට ගැළපීම සඳහා පමණක් කිසිවිටෙකත් තහවුරු කිරීම් දුර්වල නොකරන්න හෝ අවශ්ය පරීක්ෂණ ඉවත් නොකරන්න.
