## 1 වන කොටස — තීන්දුව සහ පරිණතභාව වර්ගීකරණය

**සමස්ත ශ්රේණිය: A− / "උසස්". ව්යාපෘතිවල ඉහළම ~5–10%.** මෙම පද්ධතිය, කර්මාන්තය පැහැදිලිව නම් කරන
රටා කිහිපයක් ස්වාධීනව ක්රියාත්මක කරයි — එය ගැළපීම පිළිබඳ ප්රබලතම
සංඥාවයි (අපි පිරික්සුම් ලැයිස්තුවක් පිටපත් කළේ නැත; නිවැරදි භාවිතයන් වෙත ස්වාධීනව ළඟා වුණෙමු).

## 2 කොටස — විවේචනාත්මක ඇගයීම (ශක්තීන් + අවංක දුර්වලතා)

### ශක්තීන් (සාමාන්යයට වඩා ඉහළ දේවල්)

1. **බහු-මිතික ratchet එන්ජිම.** පද්ධතියේ හදවත. `quality-baseline.json` තුළ metrics 24ක්
   - කැපවූ baselines 4ක්; සෑම එකකටම දිශාව (`up`/`down`), tolerance (`eps`), slack
     (`tightenSlack`) සහ `dedicatedGate` flag එකක් ඇත. නිවැරදි කරන ලද දේවල් **දිගටම**
     නිවැරදිව පවතී — මෙය codebase entropy සඳහා ප්රතිවිෂයයි.
2. **Supply-chain සඳහා බහු-ස්තරීය ආරක්ෂාව.** SAST (CodeQL/Sonar) + secrets (`useDefault`
   සහිත gitleaks) + SCA (osv/npm-audit/Trivy/Dependabot) + licenses + lockfile + SBOM + SLSA
   provenance + Scorecard + workflow hardening (zizmor). මේ තරම් සම්පූර්ණ stack එකක් ඇත්තේ codebase කිහිපයකට පමණි.
3. **Goodhart's Law සඳහා ප්රතිවිෂ.** Coverage එක target එකක් කිරීම සම්භාව්ය anti-pattern එකකි
   ("මිනුමක් ඉලක්කය බවට පත්වූ විට, එය හොඳ මිනුමක් වීම නවතී"). අප සතුව ඇති
   ප්රතිසමතුලිතකාරක: **mutation testing** (test එක bug එක අල්ලාගන්නේදැයි මනින අතර, හුදෙක්
   එය line එක execute කරන්නේදැයි පමණක් නොමනියි), **`check-test-masking`** (pass වීමට asserts දුර්වල කිරීම අවහිර කරයි),
   **module එකකට වෙන් වූ coverage floors** (පහසු කොටස් පමණක් නොව, HIGH-risk code පරීක්ෂා කිරීමට බල කරයි) සහ
   **`check-pr-evidence`** (Hard Rule #18).
4. **Hallucination-විරෝධී / consistency gates.** දුර්ලභ සහ වටිනා කාණ්ඩයකි: `check-known-symbols`,
   `check-fetch-targets`, `check-openapi-routes`, `check-docs-symbols` මඟින් docs, specs සහ
   string dispatches සජීවී symbols වෙත යොමු වන බව තහවුරු කරයි. lint/test මඟින් අල්ලා නොගන්නා "rot" අල්ලා ගනී.
5. **Advisory→blocking ජීවන චක්රය.** නව gates advisory ලෙස ඇතුළත් වේ (පරිණත වන අතරතුර
   merges අවහිර නොකරයි), පසුව cycle එක අවසානයේ blocking බවට පත් වේ. සීමාව අහිමි නොකර ඝර්ෂණය අඩු කරයි.
6. **Infra නොමැති විට ගැටලුවකින් තොරව skip කිරීම.** binary/network එක
   අසාර්ථක වුවහොත් scanners (`--ratchet`) `exit 0` සමඟ අවසන් වේ — නොමැති infra කිසිවිටෙකත් නීත්යානුකූල PR එකක් අවහිර නොකරයි. පරිණත engineering ක්රමවේදයකි.
7. **කේතගත කළ සංස්කෘතිය.** Hard Rules + `trust-but-verify` + stale-allowlist + evidence-gate
   මඟින් විනය ස්වයංක්රීය සත්යාපනයක් බවට පත් කරයි.

### අවංක දුර්වලතා (සැබෑ හිඩැස්)

1. **🔴 Fast-gates බෙදීම තවමත් ව්යුහාත්මක හිඩැසක් ඉතිරි කරයි.** `quality.yml` (PR→`release/**`)
   දැන් code PRs සඳහා typecheck, වේගවත් deterministic tests සහ advisory production build එකක්
   ධාවනය කරයි, නමුත් එය තවමත් `ci.yml` හි සම්පූර්ණ release-PR පරාසය (coverage ratchets,
   package artifact, integration, E2E, SonarQube) ධාවනය නොකරයි. අභිප්රේරණය (වේගය) වලංගු නමුත් gate එක
   merge එක සිදුවන තැන තිබිය යුතුය (shift-left). **අපේක්ෂිත විශාලතම ව්යුහාත්මක නිවැරදි කිරීම.**
2. **🟠 Gate අධික ව්යාප්තිය/වෙහෙස ඇතිවීමේ අවදානම.** gates ~46ක් + jobs 25ක් යනු ඉතා විශාල ප්රමාණයකි. Sonar පවා අනතුරු අඟවන්නේ:
   අධික conditions සංඛ්යාවක් "gate fatigue" සහ ප්රමුඛතා පිළිබඳ විවාද ඇති කරන අතර, gate එකක්
   නොසලකා හැරීමේ අවදානමක් ද පවතී. දැඩි gates නිසා lead-time සඳහා පිරිවැයක් ඇති වන බව DORA අනතුරු අඟවයි. අපි advisory tiers සහ
   non-absolute ratchets මඟින් මෙය අවම කරන නමුත්, **gate එකකට වාරික ROI සමාලෝචනයක්** නොමැත (doc-sync සඳහා ඇති
   ඇතැම් micro-gates ඒකාබද්ධ කළ හැක).
3. **🟠 Mutation score තවමත් ratchet එකක් නොවේ.** Coverage-gaming සඳහා ඇති ශක්තිමත්ම ප්රතිවිෂය
   **advisory** වේ. එය ඉහළම වටිනාකමක් ඇති අපේක්ෂිත අයිතමයයි (සහ දැනටමත් 90%ක් නිම කර ඇත).
4. **🟡 අවහිර කළ යුතු advisories (නිවැරදි scope එක සමඟ).** `osv` (vulnCount) සහ `oasdiff`
   frozen baselines තිබියදීත් advisory වේ. osv-advisory වීම තර්කානුකූලය (පැරණි dep එකක නව CVE එකක්
   සම්බන්ධයක් නැති PR එකක් අවහිර කරනු ඇත) — නමුත් මැද මාවතක් ඇත (අප Trivy සමඟ කළාක් මෙන්,
   CRITICAL+fixable පමණක් අවහිර කිරීම). oasdiff advisory වීමෙන් contract එක බිඳ දමන වෙනසකට pass විය හැක.
5. **🟡 Runtime security රාත්රී ධාවනයට පමණක් සීමා වේ.** schemathesis/garak/promptfoo/chaos/k6 රාත්රියේ ධාවනය වේ.
   මෙය නිවැරදි තීරණයකි (මන්දගාමී වන අතර live server එකක් අවශ්ය වේ), නමුත් PR එකකට ඊළඟ රාත්රියේ පමණක්
   හසු වන injection-guard regression එකක් හඳුන්වා දිය හැක.
6. **🟡 `main` හි branch-protection එක OFF ය.** `BRANCH_LOCK_TOKEN` මඟින් _release_ branches lock කරන නමුත්,
   `main` එකම ආරක්ෂා කර නොමැත. Scorecard/DSOMM වෙතින් අඩු ලකුණු ලැබේ. Owner ක්රියාමාර්ගයක් අවශ්යය.
7. **🟡 CodeQL default-setup; semgrep කේතගත කර නොමැත.** default-setup ක්රියා කරයි (alerts 0ක්), නමුත්
   commit කළ `codeql.yml` එකක් වැඩි පාලනයක් ලබා දෙයි; semgrep repo එක තුළ version කර නොමැතිව,
   external cloud platform එකක් හරහා ධාවනය වේ.

## 3 වන කොටස — තත්ත්ව පරීක්ෂණ ස්ථානවල සම්පූර්ණ නාමාවලිය (අතේ ගෙන යා හැකි)

පහත කාණ්ඩ 12 නැවත භාවිත කළ හැකි ආකාරයෙන් ඇති "තත්ත්ව පද්ධතිය" වේ. සෑම කාණ්ඩයකම
**අරමුණ** (ආරක්ෂා කළ යුත්තේ කුමක්ද), **අප භාවිත කරන මෙවලම්** සහ ඕනෑම තාක්ෂණික ස්ටැක් එකක ප්රතිනිර්මාණය කිරීම සඳහා වන **මෙවලම්-ස්වාධීන සමානකම**
ලැයිස්තුගත කර ඇත.

### 1. ශෛලිය සහ හැඩතල ගැන්වීම (නිර්ණායක, වේගවත්)

- **OmniRoute:** lint-staged හරහා Prettier + ESLint (pre-commit), හිස්තැන් 2ක්/ද්විත්ව උද්ධෘත/තීරු 100ක්.
- **සාමාන්ය:** ස්වයංක්රීයව නිවැරදි කළ හැකි එක් formatter එකක් + එක් linter එකක්, staged ගොනු මත pre-commit අවස්ථාවේ ධාවනය වීම.

### 2. වර්ග

- **OmniRoute:** `typecheck:core` (අවහිර කරන) + `typecheck:noimplicit:core` (උපදේශාත්මක) + `type-coverage` රැචට් 92.17% + එක් ගොනුවකට any-budget.
- **සාමාන්ය:** CI තුළ දැඩි typecheck එකක් + රැචට් කළ type-coverage මිනුමක් + එක් ගොනුවකට `any`/escape-hatch සීමාවක්.

### 3. පරීක්ෂණ (තීව්රතාව)

- **OmniRoute:** එකිනෙක නොඅතිච්ඡාදනය වන runners 2ක් (Node native + vitest), shards 8ක්, සමස්ත coverage 60/60/60/60 + රැචට් ~76% + **තීරණාත්මක modules සඳහා එක්-module අවම සීමා 8ක්** + රාත්රී property tests + රාත්රී **mutation testing**.
- **සාමාන්ය:** test runner(s) + **නිරපේක්ෂ** coverage අවම සීමාවක් (ශූන්ය වීම වැළැක්වීමට) + coverage **රැචට්** එකක් (පසුබැසීම වැළැක්වීමට) + **ඉහළ අවදානම් කේත සඳහා එක්-module අවම සීමා** (Goodhart බලපෑම වැළැක්වීමට) + ශුද්ධ තර්කනය සඳහා property-based පරීක්ෂණ + පරීක්ෂණවල සැබෑ ගුණාත්මකභාවය මැනීමට රාත්රී **mutation testing**.

### 4. පරීක්ෂණ ප්රතිපත්තිය (අයුතු ලෙස ප්රතිඵල හැසිරවීම වැළැක්වීම)

- **OmniRoute:** `pr-test-policy` (නිෂ්පාදන කේතයට පරීක්ෂණයක් අවශ්ය වේ), `check-test-masking` (දුර්වල කළ asserts අවහිර කරයි), `pr-evidence` (සාර්ථකත්ව ප්රකාශයකට සාක්ෂි කොටසක් අවශ්ය වේ), `test-discovery` (සෑම පරීක්ෂණයක්ම runner එකක් මඟින් රැස් කරයි).
- **සාමාන්ය:** "නව කේතය ⇒ නව පරීක්ෂණයක්" ද්වාරය + ඉවත් කළ assert/tautology අනාවරකය + සාක්ෂි අවශ්යතාව (TDD හෝ සජීවී පරීක්ෂණයක්) + globs වලින් පිටත කිසිදු පරීක්ෂණයක් අනාථ නොවන බවට සහතිකයක්.

### 5. සංකීර්ණත්වය සහ කේත සෞඛ්යය (රැචට්)

## 4 වන කොටස — ඕනෑම ව්යාපෘතියක් සඳහා ප්රතිනිර්මාණ සැලැස්ම

තනිවම වටිනාකමක් ලබාදෙන **අදියර** වශයෙන් ගොඩනඟන්න. කාණ්ඩ 12ම එකවර ක්රියාත්මක කිරීමට උත්සාහ නොකරන්න —
එය 2 වන කොටස අනතුරු අඟවන gate විඩාවම ඇති කරයි. සෑම නව gate එකක්ම **උපදේශාත්මක** ලෙස ඇතුළත් වී,
ස්ථාවර වූ විට **අවහිර කරන** තත්ත්වයට පත්වේ.

### නැවත භාවිත කළ හැකි කේන්ද්රීය අංගය: "ratchet gate එකක ව්යුහය"

සමස්ත පද්ධතියම මෙම ගොනු 3 රටාව වටා ක්රියාත්මක වේ. මුලින්ම එය පිටපත් කරන්න:

1. **`baseline.json`** — ස්ථිර කළ මෙට්රික් අගය + `direction` (`up`/`down`) + `eps` (අස්ථාවරත්වයට එරෙහි) + `tightenSlack` + `dedicatedGate`.
2. **`collect-metrics.<ext>`** — මෙවලම ධාවනය කර, සංඛ්යාව උකහාගෙන, `metrics.json` ලියයි.
3. **`check-ratchet.<ext>`** — `metrics.json` සහ `baseline.json` සසඳයි; `eps` ඉක්මවා පසුබැසීමක් සිදුවී ඇත්නම් **පමණක්** `exit 1`; මෙවලම/යටිතල පහසුකම් නොමැති නම් `exit 0` (බාධාවකින් තොරව මඟහැරීම); `--require-tighten` සමඟ, baseline එක යාවත්කාලීන නොකර එය **වැඩිදියුණු** වී ඇත්නම් `exit 1` (ලැබූ ප්රගතිය අගුළු දමයි).

මෙය ස්ථාපිත වූ පසු, **සෑම** නව මෙට්රික් එකක්ම (coverage, complexity, warnings, SAST alerts, bundle size, mutation score…) baseline එකේ එක් පේළියක් පමණි.

### අදියර 0 — පදනම (1 වන සතිය)

CI පවතී; formatter + linter + typecheck + පරීක්ෂණ ධාවක 1ක් + **නිරපේක්ෂ** coverage අවම සීමාවක්
(උදා., 60%). Pre-commit වේගවත්, ස්වයංක්රීයව නිවැරදි කළ හැකි පරීක්ෂා ධාවනය කරයි. _ප්රතිඵලය: කිසිදු PR එකක් මූලික දෑ බිඳ නොදමයි._

### අදියර 1 — ratchet යන්ත්රණය (2 වන සතිය) — **සියල්ලේ පදනම**

ඉහත ගොනු 3 ක්රියාත්මක කරන්න. warnings, coverage, complexity, duplication,
dead code, file size සඳහා baselines ස්ථිර කරන්න. _ප්රතිඵලය: මෙතැන් සිට codebase එකට වැඩිදියුණු වීමට පමණක් හැකිය._

### අදියර 2 — ස්ථිතික ගැඹුර (3 වන සතිය)

alert ratchet එකක් සහිත SAST (CodeQL/Sonar/semgrep); secrets scanner (**පෙරනිමි ruleset එක උරුම කරගන්න**);
SCA (osv/Dependabot) + license allowlist + lockfile-lint. _ප්රතිඵලය: දන්නා දුර්වලතා සහ
කාන්දු වූ secrets සමත් නොවේ._

### අදියර 3 — ගොඩනැඟීමේ සැපයුම් දාමය (4 වන සතිය)

Publish කිරීමේදී SBOM + අත්සන් කළ provenance (SLSA L2) + කාලසටහන්ගත Scorecard + workflow ශක්තිමත් කිරීම
(zizmor: අවම tokens, ස්ථිරව තබාගත් credentials නොමැති වීම, pinned actions). _ප්රතිඵලය: සොයා අනුගමනය කළ හැකි සහ
විකෘති කළ නොහැකි releases._

### අදියර 4 — පරීක්ෂණ තීව්රතාව (5–6 වන සති)

ප්රයෝජනවත් නම් 2 වන runner එකක්; **තීරණාත්මක modules සඳහා module එකකට වෙන් වූ coverage අවම සීමා** (Goodhart-විරෝධී);
ශුද්ධ තර්කනය සඳහා property-based පරීක්ෂණ; **රාත්රී mutation testing** → 1 වන score එක ලැබුණු විට,
`mutationScore` ratchet එකක් බවට පත් කරන්න. _ප්රතිඵලය: coverage නිෂ්ඵල ආටෝප මෙට්රික් එකක් වීම නවතී; පරීක්ෂණ සැබැවින්ම දෝෂ හසුකරන බව සනාථ වේ._

### අදියර 5 — ගිවිසුම් සහ ගතික පරීක්ෂණ (7 වන සතිය)

පොදු API එකක් තිබේ නම්: oasdiff (බිඳවැටෙන වෙනස්කම්, **අවහිර කරන**) + schemathesis (රාත්රී fuzz).
වසමට යෝග්ය පරිදි රාත්රී DAST/red-team. _ප්රතිඵලය: ගිවිසුම් නිහඬව බිඳ නොවැටේ._

### අදියර 6 — hallucination-විරෝධී සහ වසම්-විශේෂිත පරීක්ෂණ (8 වන සතිය)

ව්යාපෘතියේ සෑම "අනුපිටපත් කළ සත්යයක්" සඳහාම එක් consistency gate එකක්. වසමට විශේෂිත failure-mode
gates (AI සඳහා: injection red-team). _ප්රතිඵලය: ව්යුහාත්මක පිරිහීම සහ වසම් අසාර්ථකත්ව සඳහා ආරක්ෂිත ජාලයක් ඇත._

### අදියර 7 — පාලනය (අඛණ්ඩව)

- සෑම නව gate එකක් සඳහාම උපදේශාත්මක→අවහිර කරන චක්රයක්.
- `stale-allowlist`: සෑම suppression එකකටම සාධාරණීකරණයක් + issue එකක් ඇත; කල් ඉකුත් වූ suppression හසුකරගනී.
- `evidence-gate`: PR එකක සාර්ථකත්ව ප්රකාශයකට සාක්ෂි අවශ්ය වේ (test හෝ living test).
- **සෑම gate එකක් සඳහාම ත්රෛමාසික ROI සමාලෝචනයක්** (ප්රතිලාභ නොදෙන ඒවා ඉවත් කරන්න/අරමුදල් නවත්වන්න — විඩාවට එරෙහි වේ).
- ඔබේ ව්යාපෘතියේ Hard Rules ක්රියාත්මක කළ හැකි gates බවට උසස් කරන්න.

### සියල්ලටම අදාළ මූලධර්ම (සාකච්ඡා කළ නොහැකි)

- **නිරපේක්ෂ නොව, ratchet.** ස්ථාවර සංඛ්යාවක් නොව, _පසුබැසීමක් නොවීම_ gate කරන්න (ශුන්ය වීම වළක්වන අවම සීමා හැර).
- **නිරපේක්ෂ අවම සීමාව + ratchet එකට.** අවම සීමාව කඩාවැටීම වළක්වයි; ratchet එක ක්රමික පිරිහීම වළක්වයි.
- **සැලසුමෙන්ම Goodhart-විරෝධී.** සෑම ඉලක්ක මෙට්රික් එකකටම ප්රතිතුලනයක් අවශ්යය (coverage ⇒ mutation + anti-masking; අපහසු code එක පරීක්ෂා කිරීමට බල කිරීම සඳහා module එකකට වෙන් වූ අවම සීමා).
- **බාධාවකින් තොරව මඟහැරීම.** නොමැති යටිතල පහසුකම් කිසිවිටෙක අවහිර නොකරයි; සැබෑ පසුබැසීමක් පමණක් අවහිර කරයි.
- **මිල අධික මෙට්රික් සඳහා `dedicatedGate`.** බාහිර binary එකක් අවශ්ය මෙට්රික්, සමමුහුර්ත මධ්යම ratchet එකෙන් පිටත, තමන්ගේම script එකක් (මඟහැරීමක් සහිතව) ලබාගනී.
- **merge එක සිදුවන තැන gate කරන්න.** වේගවත් gate එක සහ සැබෑ merge එක අතර හිඩැසක් ඉතිරි නොකරන්න (fast-gates බෙදීමෙන් උගත් පාඩම).
- **හොඳින් තෝරාගත් අවහිර කරන gates කිහිපයක්.** Sonar/DORA: කොන්දේසි අධික වීම = විඩාව. අවහිර කරන gates පවුරකට වඩා උපදේශාත්මක + ratchet ක්රමයට ප්රමුඛත්වය දෙන්න.

## 5 වන කොටස — නිර්දේශිත වැඩිදියුණු කිරීම් (ප්රමුඛතාගත, අනුකූල)

**P0 — ඉහළම ROI, සූදානම් වීමට ඉතා ආසන්නයි**

1. **Mutation score ratchet** (පළමු රාත්රී Stryker ධාවනයෙන් අගයන් ලැබුණු පසු). coverage-Goodhart ගැටලුවට එරෙහි ප්රධාන ප්රතිවිෂය; ~90% සම්පූර්ණයි.
2. **ඉතිරි fast-gates හිඩැස වසා දමන්න** — `quality.yml` හි production build එකට එහි
   උපදේශන සතියෙන් පසු උසස් තත්ත්වය ලබා දී, deterministic release-PR-only පරීක්ෂණ PR→release මාර්ගයට අඛණ්ඩව ගෙන යන්න.
3. **`main` මත branch-protection** (හිමිකරුගේ සැකසුම) — Scorecard ඉහළ නංවා, DSOMM හිඩැස වසා දමයි.

**P1 — වටිනා** 4. **osv/oasdiff → නිවැරදි විෂය පථය සමඟ blocking කරන්න** — osv සඳහා CRITICAL+fixable පමණක් (Trivy මෙන් පියවර දෙකකින්); oasdiff breaking-changes අවහිර කරයි. 5. **`require-tighten` → blocking කරන්න** (චක්රය අවසානයේ) — ප්රමිතික වැඩිදියුණු කිරීම් ස්ථාවර කරයි. 6. **`ci-summary` තුළ එක් එක් gate සඳහා ROI/කාල සමාලෝචනය** — මන්දගාමී/අඩු වටිනාකමක් ඇති gates හඳුනාගෙන ඉවත් කරන්න.

**P2 — අඩුවෙමින් යන ප්රතිලාභ** 7. **SLSA L3** — L2 සිට ඉහළට යාමට අවශ්ය නම් hermetic/reproducible builder එකක් (GitHub SLSA generator). 8. **Commit කළ CodeQL config + versioned semgrep** — වැඩි පාලනයක්/ප්රතිනිෂ්පාදන හැකියාවක්. 9. **එක් එක් PR සඳහා DAST smoke** — ඉහළම අවදානම් endpoints මත schemathesis/promptfoo හි වේගවත් උපකට්ටලයක් (රාත්රී ධාවනයට පමණක් සීමා නොවී). 10. **Flakiness dashboard + DORA metrics** — gates නිසා වේගය පිරිහෙන්නේ නැති බව සහතික කරන්න.

## 6 වන කොටස — නිශ්චිත release පාඩම් (Phase 9 තුළ එක් කළ යුතු gates)

> මෙම කොටසේ gate එකක් **නොතිබුණු** release වසා දැමීම්වල සැබෑ සිදුවීම්,
> නිශ්චිත සාක්ෂි සහ යෝජිත gate එක සමඟ සටහන් කරයි. සෑම අයිතමයක්ම 5 වන කොටස සඳහා අපේක්ෂකයකි.

### v3.8.27 පාඩම (2026-06-17) — "fast-gates හිඩැස" නිසා deterministic regressions release දිනය දක්වා ළඟා වේ

**සිදු වූයේ කුමක්ද.** v3.8.27 `/generate-release` අතරතුර, release PR එක (`release/v3.8.27` → `main`)
ඒකාබද්ධ චක්රය තුළ සම්පූර්ණ `ci.yml` matrix එක ක්රියාත්මක වූ **පළමු** අවස්ථාව විය. ප්රතිඵලය: එකවර failures 12ක් —
**deterministic tests 3ක්** + flakes/env ~9ක්. ඒ කිසිවක් සජීවී නිෂ්පාදන regressions නොවූ නමුත්,
cycle PRs **Fast QG
(`quality.yml`)** හරහා `release/**` වෙත ඇතුළු වන බැවින් සියල්ලම හඳුනා නොගෙන පැවතුණි. එය සම්පූර්ණ unit suite එක, `pr-test-policy` (test-masking), සම්පූර්ණ
integration suite එක හෝ schema parity පරීක්ෂාව ක්රියාත්මක නොකරයි. deterministic ඒවා 3 මෙසේය:

1. **UI වෙනස්කමක් නිසා test එක යල්පැනීම** — `permissions modal switch buttons declare button type`:
   #4034 මඟින් 4 වන switch එකක් එක් කරන ලදී (a11y `type="button"` පවත්වා ගන්නා ලදී); test එකේ `=== 3` ගණන
   යල්පැන ගියේය. Static analysis මඟින් මෙය #4034 PR එකේදීම හඳුනාගත යුතුව තිබුණි.
2. **Packaging වෙනස්කමක් නිසා test එක යල්පැනීම** — `findMissingArtifactPaths ... root runtime files`:
   `dist/http-method-guard.cjs` වලංගු required-path එකක් බවට පත් විය; test එකේ expected list එක
   යල්පැන ගියේය.
3. **Lossy modularization divergence (වඩාත්ම බරපතළ)** — `settings schemas accept ... unprefixed
toggle`: **modularized** `updateSettingsSchema` එක (`schemas/settings.ts`, #3988 මඟින් නිර්මාණය කළ) canonical එකෙන් (`settingsSchemas.ts`) වෙනස් විය: **fields 45ක් එදිරිව 85ක් — 40ක් ඉවත් වී + 6ක් වෙනස් වී ඇත (qdrant\*)**. එය
   **dead-code** විය (runtime එක canonical එක භාවිත කරයි), එබැවින් සජීවී බලපෑමක් නොතිබුණද, එය හඳුනාගත්තේ අතින් ලියන ලද parity
   test එකකින් පමණි. #4030 මඟින් #3988/#3993 වෙතින් සිදු වූ සමාන ඉවත් කිරීම් 16ක් ප්රතිස්ථාපනය කළ නමුත්, මෙය මඟහැරී ගියේය.

**යෝජිත gates (Phase 9):**

- **G1 — fast-gates හිඩැස සැබැවින්ම වසා දමන්න (P0 #2 පුළුල් කරයි).** `quality.yml` තුළ (PR→`release/**`),
  typecheck + impacted tests වලට අමතරව, **`pr-test-policy` (test-masking) + සම්පූර්ණ deterministic
  unit suite එක** (හෝ අවම වශයෙන් වේගවත් සහ flake නොවන static/parity files) ක්රියාත්මක කරන්න.
  මෙලෙස, යල්පැන ගිය tests සහ assert ඉවත් කිරීම් ඒවා හඳුන්වා දෙන PR එකේදීම හඳුනාගැනේ — release
  දිනයේදී නොවේ. integration/e2e බැහැරව තබන්න (මන්දගාමී/flake විය හැකි), නමුත් deterministic layer එක PR→main තුළ පමණක්
  පැවතිය **නොහැක**.
- **G2 — Modularization parity gate (අලුත්, අද ආවරණය නොවේ).** Modularized barrel එකකින් (`src/shared/validation/schemas/*`, `providerRegistry`
  modules, ආදිය) නැවත export කරන සෑම symbol එකක් සඳහාම, එහි **shape** එක (`z.object` keys, registry entries) canonical
  source එක සමඟ සසඳා, **divergence මත අසාර්ථක වන** (ඉවත් වූ/අමතර field) පරීක්ෂාවක්. මෙය #3988 හි fields 40ක් ඉවත් වීම
  එම PR එකේදීම හඳුනාගන්නට ඉඩ තිබුණි. අතින් ලියන ලද parity tests (යමෙකුට ඒවා ලිවීමට මතක් වූ තැන්වල පමණක්
  පවතින) සාමාන්යකරණය කරයි. අඩු වියදම්: දෙකම import කර `Object.keys(shape)` diff කරයි.
- **G3 — Deterministic flake triage (සහාය).** LiveWS-startup සහ integration-combo/breaker
  tests CI තුළ server timeout/cascade (env) නිසා අසාර්ථක වේ, logic නිසා නොවේ. ඒවා
  `known-flaky` ලෙස සලකුණු කරන්න (issue එකක් සමඟ quarantine කර), එවිට release-PR හි රතු තත්ත්වය deterministic regressions මැද
  සැඟවෙන ශබ්ද නොවී **සැබෑ signals පමණක්** නියෝජනය කරයි.

**මූලධර්මය:** _merge එක සිදු වන තැනම gate එක ක්රියාත්මක විය යුතුය_ (දැනටමත් "හරස්-කැපුම් මූලධර්ම" තුළ ඇත).
v3.8.27 සිදුවීම පෙන්වන්නේ මෙය lint/typecheck සඳහා පමණක් නොව **deterministic test layer එකටත්** අදාළ වන බවයි —
එසේ නොමැතිනම්, යල්පැන ගිය tests + lossy modularization හි ණය කාණ්ඩ වශයෙන් PR→main තුළ, නරකම
මොහොතේදී පමණක් මතු වේ.
