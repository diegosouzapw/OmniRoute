## npm විශ්වාසනීය ප්රකාශනය (v3.8.51 සිට පෙරනිමි) — ඉල්ලීම මත අදියරගතව, විකල්ප ක්රමය ලෙස සෘජුව

`npm-publish.yml` පෙරනිමියෙන් **npm Trusted Publishing (OIDC)** හරහා ප්රකාශනය කරයි:
`stage-npm` කාර්යය (github-hosted) එම ධාවනය සඳහා කෙටි කාලීන npm
අක්තපත්රයක් ලබාගැනීමට GitHub හි id-token හුවමාරු කරයි — ගබඩාවේ රහස් තුළ දිගුකාලීන npm ටෝකනයක් නැත, 2FA විමසුමක් නැත, ප්රභව සාක්ෂිය අමුණා ඇත.
2FA මඟහැර යන ටෝකන විශ්රාම ගැන්වෙන බැවින් npm දැන් අනුමත කරන මඟහැරීමේ ක්රමය එයයි;
එය WS1.3 සහතිකය රඳවා ගනිමින් ව්යාපෘතියට v3.8.48 දක්වා තිබූ
සම්පූර්ණයෙන්ම ස්වයංක්රීය ප්රවාහය නැවත ලබා දෙයි (කාන්දු වූ ටෝකනයකට තනිව ප්රකාශනය කළ නොහැක — ටෝකනයක්ම නොමැත).

**එක් වරක් පමණක් සිදු කරන සැකසුම (හිමිකරු):** npmjs.com → `omniroute` පැකේජය → Settings → _Trusted
Publisher_ → GitHub: හිමිකරු `diegosouzapw`, ගබඩාව `OmniRoute`, කාර්ය ප්රවාහය `npm-publish.yml`
(පරිසරය: කිසිවක් නැත). එය පවතින තෙක් ස්වයංක්රීය පියවර `ENEEDAUTH` සමඟ අසාර්ථක වේ:
`publish_mode=staged` (පහත) හෝ `direct` සමඟ නැවත dispatch කරන්න.

### අදියරගත ප්රකාශනය (ඉල්ලීම මත — `publish_mode=staged`)

npm-publish කාර්ය ප්රවාහය තවදුරටත් සෘජුව ප්රකාශනය නොකරයි: එය ඇසුරුම් කළ tarball එක
(`check:pack-boot`) ආරම්භ කර පසුව `npm stage publish` ධාවනය කරයි — නියමිත bytes registry එකෙහි රඳවා තබන අතර,
හිමිකරු අනුමත කරන තෙක් ඒවා **ස්ථාපනය කළ නොහැක**. මානව 2FA ද්වාරය
සාක්ෂියට පෙර නොව, ඉන් පසුවට ගෙන ගොස් ඇත.

**කාර්ය ප්රවාහය හරිත වූ පසු හිමිකරුගේ ප්රවාහය:**

1. `npm stage list omniroute` — අදියර id එක සොයා ගන්න (එය කාර්ය ප්රවාහ සාරාංශයේද මුද්රණය වේ).
2. අදියරගත bytes තහවුරු කරන්න (නිර්දේශිතයි): `npm stage download <id>`, ඉන්පසු බාගත කළ
   tarball එක තාවකාලික prefix එකකට ස්ථාපනය කර එය ආරම්භ කරන්න (`npm run check:pack-boot` මඟින්
   CI තුළ එම pack→install→boot තීන්දුවම ස්වයංක්රීය කරයි).
3. `npm stage approve <id>` — 2FA විමසුමම ප්රකාශනය වේ. `npm stage reject <id>` මඟින් එය ඉවත දමයි.
4. ප්රකාශනයෙන් පසු ආරක්ෂණය: ප්රකාශනයෙන් පසු සත්යාපකය (v3.8.49 සැලැස්මේ WS1.4) පිරිසිදු container එකක් තුළ
   පොදු registry එකෙන් ප්රකාශිත අනුවාදය ස්ථාපනය කර එය ආරම්භ කරයි.

**හදිසි විකල්ප ක්රමය:** `publish_mode=direct` සමඟ `workflow_dispatch` භාවිත කිරීමෙන්
පැරණි ක්ෂණික `npm publish` ක්රමය නැවත ලබා ගත හැක (අදියරගත කිරීමම නිසි ලෙස ක්රියා නොකරන්නේ නම් පමණක් භාවිත කර හේතුව සටහන් කරන්න).

**එක් වරක් පමණක් සිදු කරන ශක්තිමත් කිරීම (හිමිකරු, npmjs.com):** `omniroute` සඳහා Trusted Publisher එක
stage-only ප්රකාරයෙන් වින්යාස කරන්න, එවිට කාන්දු වූ දිගුකාලීන ටෝකනයකට කිසිදු ස්ථානයකින් සෘජුව `npm publish`
කළ නොහැක — CI හට අදියරගත කිරීම පමණක් කළ හැකි අතර, නිකුතුව කළ හැක්කේ හිමිකරුගේ 2FA මඟින් පමණි.

**බිඳුණු කෞතුකය සඳහා ක්රියාමාර්ග මාර්ගෝපදේශය (වෙනස් කර නැත):** පෙරනිමි ප්රතිචාරය ලෙස `npm deprecate omniroute@<bad> "<reason> — use <fixed>"`
භාවිත කරන්න (මිනිත්තු කිහිපයක් ගනී, ආපසු හැරවිය හැක); `npm unpublish` භාවිත කළ යුත්තේ පැය 72/යැපෙන්නන්-නොමැති
කාල කවුළුව තුළ පමණක් වන අතර කිසිවිටෙකත් පළමු පියවර ලෙස නොවේ. Docker: අනුවාද ටැගයක් කිසිවිටෙක නැවත ලියන්න එපා — ආපසු හැරවීම යනු
`latest` අවසන් හොඳ digest එක වෙත නැවත යොමු කිරීමයි.

**Docker Hub `latest` (සෑම ස්ථායී SemVer ප්රකාශනයකදීම අනිවාර්යයි):**
`docker-publish` කාර්ය ප්රවාහය විසින් `X.Y.Z` සහ, මෙය ඉහළම ස්ථායී SemVer බවට
`should-promote-latest.sh` එකඟ වන විට, `:latest` යන **දෙකම** එකම
**digest** එකෙන් ටැග් කළ යුතුය. කාර්යය අවසන් වූ පසු: Hub හි `latest` digest එක නව
SemVer digest එකට සමාන වන අතර `last_updated` ඉදිරියට ගොස් තිබිය යුතුය. git තුළ පමණක් පවතින නිවැරදි කිරීම් ගැන නිකුතු සටහන් සඳහන් කරන අතරතුර
`:latest` පැරණි build එකක් මත තබා නොයන්න.
Compose ඉක්මන් ආරම්භක මාර්ගෝපදේශ `:latest` භාවිත කරයි; GitOps විසින් `X.Y.Z` වෙත pin කිරීම දිගටම කළ යුතුය.

## හදිසි නිවැරදි කිරීම් සඳහා වේගවත් මාර්ගය (`hotfix` ලේබලය)

`hotfix` ලෙස ලේබල් කළ PR එකක් බර CI න්යාසය (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) මඟහැර වේගවත්, ඉහළ සංඥා සහිත දොරටු පවත්වා ගනී: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
සහ tarball boot-smoke (`check:pack-boot`). ඉලක්කය: මිනිත්තු ~33ක් වෙනුවට ≤15min තුළ හරිත තත්ත්වයට ළඟා වීම.

**ඇතුළත් වීමේ ප්රතිපත්තිය — හතරම අවශ්යයි (Chromium/VS Code/Node හදිසි මාර්ග ආදර්ශයට ගෙන ඇත):**

1. **බරපතළකම**: නිෂ්පාදන පද්ධතිය ක්රියා විරහිතයි — ප්රකාශිත artifact එකක් ආරම්භයේදී බිඳ වැටීම /
   ආරක්ෂක නිවැරදි කිරීමක් / නිකුතුව භාවිත කරන සෑම පරිශීලකයෙකුම බලපෑමට ලක්වීම. "වැදගත්" යනු "ක්රියා විරහිත" නොවේ.
2. **අධිකාරිය**: `hotfix` ලේබලය යොදන්නේ repository හිමිකරු පමණි. ලේබලයම
   අනුමැතියයි — campaign PR එකකදී කිසිවිටෙක ස්වයං සේවාවක් ලෙස මෙය භාවිත නොකරන්න.
3. **සාක්ෂි**: PR body එකේ පෙර සම්පූර්ණයෙන්ම හරිත වූ බර ධාවනයට (මඟහැරුණු jobs මඟින්
   නැවත වලංගු කිරීමට නියමිත suite එක) සහ නිවැරදි කිරීමේම අසමත්-වී-පසුව-සමත් වූ පරීක්ෂණයට සබැඳි ඇතුළත් වේ.
4. **විෂය පථය**: cherry-pick පමණි — අවම නිවැරදි කිරීම පමණක්; refactor කිරීම් හෝ අමතර වෙනස්කම් නැත.

මඟහැරුණු coverage/ratchet පෘෂ්ඨය release branch එකේ මීළඟ සම්පූර්ණ ධාවනයෙන්
නැවත වලංගු කරයි (අඛණ්ඩ release-green) — මෙම මාර්ගය මඟහරින්නේ රැඳී සිටීම පමණි, වලංගු කිරීම කිසිවිටෙක නොවේ.
පරීක්ෂණ-පමණක් ඇති වෙනස්කම් (`tests/` යටතේ ඇති සියලු ගොනු, `tests/e2e/` යටතේ කිසිවක් නැති විට) කිසිදු ලේබලයක් නොමැතිව
E2E න්යාසය ස්වයංක්රීයව මඟහරී.

### Hooks (Husky මඟින් වලංගු කර ඇත)

Husky hooks `.husky/` තුළ ඇති අතර git මෙහෙයුම්වලදී ස්වයංක්රීයව ධාවනය වේ.

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** වේගවත් නියත දොරටු — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (2026-06-13 දින සක්රිය කරන ලදී). හිතාමතාම `test:unit` බැහැර කරයි (මන්දගාමීයි; CI `test-unit` job එකෙන් ආවරණය වේ).
  - release branches push කිරීමට පෙර `npm run test:unit` අතින් ධාවනය කරන්න.

hook එකක් අසමත් වුවහොත්: මූලික ගැටලුව නිවැරදි කරන්න, `--no-verify` භාවිතයෙන් මඟ නොහරින්න.

> **මෙහෙයුම්කරුගේ සටහන:** දුරස්ථ VPS image directory එක `/usr/lib/node_modules/omniroute/app/` ලෙසම පවතී.
> වෙනස් වූයේ repository එක **තුළ ඇති** build output එක පමණි (`app/` → `dist/`). Deploy skills මඟින්
> `dist/` හි අන්තර්ගතය දුරස්ථ `app/` dir එක වෙත rsync කරයි — VPS path වෙනස්කම් අවශ්ය නොවේ.

**තනි-build ප්රවාහය:**

```
npm run build:release
  └─ rm -rf .build dist          (පිරිසිදු කිරීම)
  └─ next build → .build/next/   (අතරමැදි ගොනු)
  └─ assembleStandalone          (standalone + static + public + natives → dist/ වෙත පිටපත් කරයි)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Deploy කිරීම සඳහා `npm run build` ධාවනය කර ඉන්පසු වෙනම `npm run build:cli` ධාවනය නොකරන්න — එක් command එකකින් පිරිසිදු rebuild එකක් + sentinel එකක් සිදු කරන
`npm run build:release` භාවිත කරන්න.

නිකුතුවේ බරපතළ ගැටලුවක් තිබේ නම්:

1. `gh release edit vX.Y.Z --prerelease` (නවතම නිකුතුව නොවන ලෙස සලකුණු කරයි)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (පරිශීලකයන් විසින් තවම භාවිතයට ගෙන නොමැති නම් පමණි)
3. නැතහොත්: `release/vX.Y.0` මත ක්ෂණික දෝෂ නිවැරදි කිරීමක් → පැච් නිකුතුව `vX.Y.(Z+1)`
4. GitHub Discussions සහ Discord තුළ වහාම දැනුම් දෙන්න
