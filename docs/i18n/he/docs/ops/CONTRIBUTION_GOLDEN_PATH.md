השתמשו במדריך זה כדי לבחור את מחזור הפיתוח האמין והמצומצם ביותר עבור בקשת משיכה. הוא אינו
מחליף את מסמכי הארכיטקטורה והאבטחה הייעודיים לכל תחום, המקושרים להלן; הוא מחבר כל סוג נפוץ של
שינוי לחוזים שלו, לבדיקות ממוקדות ולכיסוי ה-CI.

## הנתיב שבו עובר כל שינוי

1. **בחרו את הבסיס לפני העריכה.** מצאו את ענף `release/v*` הפעיל הגבוה ביותר וצרו ענף מהקצה
   שלו. הגדירו ענף זה כיעד, ולא את `main`. אם חלה הקפאת גרסה, אל תגדירו את הענף המוקפא
   כיעד; השתמשו במחזור הפעיל הבא המתואר במסמך
   [מודל הענפים והגרסאות](BRANCHING_MODEL.md).
2. **ציינו את החוזים.** זהו כל קטלוג, סכמה, ארטיפקט שנוצר, API ציבורי או ממשק
   משתמש שהשינוי משפיע עליו. הטבלה שלהלן מציגה את ערכת ההתחלה המינימלית.
3. **כתבו או עדכנו בדיקות ממוקדות.** שינויים בקוד הייצור תחת `src/`,‏ `open-sse/`,‏ `electron/` או
   `bin/` מחייבים בדיקה אוטומטית באותה בקשת משיכה. הריצו את קובצי הבדיקה המצומצמים ביותר שמוכיחים את
   ההתנהגות, ולאחר מכן את שערי הבדיקה הממוקדים המפורטים.
4. **אפשרו ל-CI להריץ את המטריצה הרחבה.** רסיסי בדיקות היחידה המלאים, Vitest, מנגנון ההחמרה של הכיסוי
   ובניית הייצור רצים בבקשת המשיכה. הריצו חבילת בדיקות רחבה באופן מקומי רק כאשר כשל ממוקד מצביע על
   השפעה רחבה יותר או כאשר השינוי משתרע על פני כמה תתי-מערכות.
5. **סנכרנו לפני הסקירה.** משכו את הבסיס הפעיל, בחנו את ה-commits החדשים שלו ואת ההבדלים שלכם מולו,
   ולאחר מכן בצעו rebase או merge של הבסיס בהתאם לתהליך העבודה של התורמים. פתרו התנגשויות בקבצים
   שנוצרו ובקטלוגים דרך המקור שלהם, צרו אותם מחדש, הריצו שוב את המחזור הממוקד ואשרו שבקשת
   המשיכה עדיין מכוונת לענף הגרסה הפעיל.
6. **תעדו ראיות.** בתבנית בקשת המשיכה, פרטו את הפקודות שהורצו, כל קובץ בדיקה שנוסף או השתנה,
   מיגרציות או דגלי תכונות, וכל אימות שמבוצע ב-CI בלבד ועדיין ממתין.

## נתיבי הזהב לפי סוג שינוי

הפקודות שלהלן הן בדיקות ממוקדות מינימליות, ולא הרשאה לדלג על בדיקה שמכסה ישירות את
ההתנהגות ששיניתם.

### ספק

**חוזים**

- הגדרת הספק ב-`src/shared/constants/providers/` והשילוב שלה בתוך
  `src/shared/constants/providers.ts`.
- מודלים ויכולות ב-`open-sse/config/providerRegistry.ts` או בקובצי הרישום שחולצו ממנו.
- בחירת executor/translator, תצורת OAuth או מפתח API, נכסי לוח המחוונים והפניית
  הספק שנוצרת, כאשר רלוונטי.
- פרטי גישה ציבוריים חייבים להשתמש ב-`resolvePublicCred()`; תגובות שגיאה חייבות להשתמש בעזרי
  השגיאה המשותפים והמסוננים. ראו `docs/security/PUBLIC_CREDS.md` ‏(git; אינו נכלל בהידור אל `/docs`) ואת
  [סינון שגיאות](../security/ERROR_SANITIZATION.md).

**מחזור ממוקד**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # כאשר הקטלוג משתנה; בצעו commit להבדלים שנוצרו
npm run lint
```

בדקו גם כל משפחת בקשות מושפעת: צ'אט, Responses, תמונות, embeddings, שמע או וידאו.
בחנו הבדלים שנוצרו בקטלוג ובבדיקות הזהב כשינויים בחוזה; אל תאשרו אותם באופן עיוור.

### ניתוב

**חוזים**

- ערכי אסטרטגיה ציבוריים ומטא-נתונים של ממשק המשתמש ב-`src/shared/constants/routingStrategies.ts`.
- שיגור וסדר תחת `open-sse/services/combo.ts` ו-`open-sse/services/combo/`.
- סכמות Combo, התמדה, מצב עמידות, יכולות מודלים ופקדי API/ממשק משתמש.
- [מנוע Auto-Combo](../routing/AUTO-COMBO.md) ותיעוד העמידות כאשר ההתנהגות משתנה.

**מחזור ממוקד**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # שינויי אסטרטגיה או שיגור
npm run check:known-symbols      # שינויי רישום אסטרטגיה
npm run lint
```

השתמשו מקומית בבדיקות דטרמיניסטיות עם upstream מדומה. בדיקות smoke חיות של combo דורשות פרטי גישה והן
ידניות, ואינן תחליף ל-CI.

### ממשק משתמש / חוויית משתמש

**חוזים**

- נתיב/דף של Next.js וגבולות רכיבים משותפים תחת `src/app/` ו-
  `src/shared/components/`.
- מבני תגובות API, מצבי טעינה/ריק/שגיאה, התנהגות מקלדת וקורא מסך,
  פריסה רספונסיבית, ערכות נושא והרחבת שפות.
- מחרוזות המקור באנגלית של ממשק המשתמש נמצאות ב-`src/i18n/messages/en.json`; אל תקבעו בקוד טקסט חדש המוצג למשתמש.

**מחזור ממוקד**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

הריצו את היישום עבור שינויי אינטראקציה או תצוגה ובדקו תצוגות צרות ורחבות כאחת. CI מריץ את
בניית הייצור ואת חבילות הבדיקות הרחבות יותר; התנהגות חזותית עדיין מחייבת בדיקת רכיב ממוקדת, Playwright,
או בדיקה ידנית מתועדת המתאימה לשינוי.

### i18n

**חוזים**

- `src/i18n/messages/en.json` הוא מקור ממשק המשתמש; `config/i18n.json` הוא מקור השפות.
- קטלוגי CLI נמצאים בנפרד תחת `bin/cli/locales/`.
- שמרו על מצייני המיקום והתגיות של ICU בדיוק כפי שהם. אל תתרגמו שמות מוצרים/ספקים/מודלים,
  שמות פרוטוקולים וכותרות, פקודות, מזהי קוד/JSON, כתובות URL, משתני סביבה או
  מונחים מוגנים כגון `OmniRoute`,‏ `OAuth`,‏ `MCP` ו-`A2A`. רשימת המקור הנוכחית היא
  `scripts/i18n/glossary/protected-terms.json`.

**מחזור ממוקד**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # כאשר מחרוזות/קטלוגים של CLI משתנים
npm run lint
```

זוהי הנחיה למערכת הקיימת, ולא הזמנה להרחיב את כלי העבודה או את מודל המפתחות שלה.
שמרו על תיקוני i18n ממוקדים בזמן שמתכננים את המערכת החלופית. אל תריצו פקודות תרגום
שפונות לשירותים חיצוניים, אלא אם המשימה דורשת במפורש תרגומים שנוצרו
ובחנתם את ההבדלים שהתקבלו.

### CLI

**חוזים**

- פקודות ודגלים ציבוריים ב-`bin/cli/`, פקודות API שנוצרו, קודי יציאה, stdout/stderr וכן
  מבני פלט JSON, התנהגות תצורה/סביבה וקבצים ארוזים.
- מחרוזות CLI המוצגות למשתמש חייבות להשתמש בשכבת ה-i18n של ה-CLI ולשמור על סנכרון בין הקטלוגים `en`/`pt-BR`.
- יש לשמר את Node כסביבת הריצה הנתמכת ואת חוזה קובצי ההפעלה שפורסמו.

**לולאה ממוקדת**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # שינויים ב-CLI שנוצר/נארז
npm run check:pack-policy     # שינויים בממשק החבילה
npm run lint
```

כאשר ההתנהגות תלויה בניתוח, בקבצים או במצב היציאה, יש להשתמש בפקודה המדויקת בספריית נתונים זמנית.
CI מבצע את הבדיקות הרחבות יותר של ארטיפקטי החבילה ושל המערכת האקולוגית.

### מסד נתונים

**חוזים**

- מודולי תחום תחת `src/lib/db/`; יש לייבא מודולים ספציפיים ישירות (שכבת הייצוא מחדש הישנה `localDb.ts` הוסרה).
- מיגרציות SQL ממוספרות ואידמפוטנטיות תחת `src/lib/db/migrations/`, בטיחות טרנזקציות, התנהגות
  שדרוג, אינדקסים וכל קורא המושפע מהסכמה.
- נתיבים ומטפלים לעולם אינם מריצים SQL גולמי ישירות.

**לולאה ממוקדת**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

בעת הוספת מיגרציה, יש לבדוק הן מסד נתונים חדש והן שדרוג מהסכמה הקודמת. בדיקות מסד הנתונים
חייבות לסגור handles ולקרוא ל-`resetDbInstance()` במהלך הניקוי. יש להריץ את `npm run test:bun:db` רק כאשר
הנתיב של מתאם Bun במתכונת מאמץ מיטבי משתנה; Node נשאר הסמכות הקובעת.

### בנייה / פריסה

**חוזים**

- מניפסטים/קובץ נעילה בשורש ובסביבות העבודה, `scripts/build/`, הרכבה עצמאית של Next.js, תכולת החבילה
  `dist/`, מטא-נתונים של פלטפורמת Electron, תהליכי עבודה של CI וסמני פריסה.
- טווחי Node הנתמכים והשימוש ב-Bun מרשימת ההיתרים ב-`CLAUDE.md` חייבים להישאר ללא שינוי.
- ארטיפקטי בנייה נשארים ללא מעקב; חלות מדיניות תלויות, רישיונות, תהליכי עבודה וחבילות.

**לולאה ממוקדת**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # שינויים בתלויות או בקובץ הנעילה
npm run check:pack-policy      # שינויים בממשק החבילה שפורסמה
npm run lint
```

יש להשתמש ב-`npm run build` באופן מקומי רק כאשר השינוי משפיע על הידור, הרכבה עצמאית, נכסים
או אריזת סביבת הריצה. יש להשתמש ב-`npm run build:release` רק לצורך אימות הפצה/פריסה. הבנייה של CI היא
המדד הסופי לחוצה-פלטפורמות; שינויים ב-Electron הייחודיים לפלטפורמה מחייבים בנייה ממוקדת תואמת
או ראיות מבדיקת עשן.

## לולאה מקומית לעומת CI

| הרצה מקומית עבור כל תיקון                                                   | CI מספק את האינדיקציה הרחבה                                     |
| --------------------------------------------------------------------------- | --------------------------------------------------------------- |
| בדיקות התנהגות ישירות ושערי הקטגוריות שלעיל                                 | חבילת בדיקות יחידה מלאה המחולקת למקטעים ובדיקות סדרתיות         |
| `npm run lint`                                                              | חבילות Vitest ומנגנוני החמרה הדרגתית של כיסוי/איכות             |
| בדיקת טיפוסים או בנייה רק כאשר החוזה המושפע מחייב זאת                       | בניית ייצור, אבטחה, תיעוד, תלויות ושערי מדיניות של PR           |
| אינטראקציה ידנית/בדיקות חיות רק כאשר אוטומציה אינה יכולה להוכיח את ההתנהגות | בדיקות אינטגרציה בין משימות ובדיקות פלטפורמה שהוגדרו ב-workflow |

לולאה ממוקדת שעברה בהצלחה היא ראיה לגבי החוזה שהשתנה, ולא הוכחה לכך שבדיקות CI שאינן קשורות
יעברו. מנגד, אין לגרום לכל עריכה מקומית להמתין למטריצה המלאה של המאגר.

## רשימת בדיקה להתאמה

לפני בקשת סקירה:

- ודאו שבסיס ה-PR הוא עדיין ענף `release/v*` הפעיל הגבוה ביותר.
- משכו את הבסיס הזה ובדקו את ה-commits שנוספו מאז שיצרתם את הענף.
- בדקו את `git diff <active-base>...HEAD` לאיתור שינויים מקריים או שינויים שנוצרו אוטומטית.
- פתרו התנגשויות בקטלוג ובמסמכים שנוצרו אוטומטית באמצעות עדכון המקור ויצירה מחדש של הפלט.
- הריצו מחדש כל בדיקה ממוקדת/שער המפורטים בתיאור ה-PR לאחר ההתאמה.
- לעולם אל תחלישו assertions ואל תשמיטו בדיקות נדרשות רק כדי להתאים לבסיס שהתקדם.

לכללי הקפאת גרסה ומיקוד מחדש, השתמשו ב-
[מודל הסתעפות ושחרור](BRANCHING_MODEL.md). לרשימת ה-CI המלאה, השתמשו ב-
[חומר עזר לשערי איכות](../architecture/QUALITY_GATES.md).
