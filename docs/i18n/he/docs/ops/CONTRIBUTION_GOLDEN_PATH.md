השתמשו במדריך זה כדי לבחור את לולאת הפיתוח האמינה והמצומצמת ביותר עבור בקשת משיכה. הוא אינו
מחליף את מסמכי הארכיטקטורה והאבטחה הספציפיים לתחום המקושרים להלן; הוא מקשר כל סוג שינוי נפוץ
לחוזים שלו, לבדיקות הממוקדות ולכיסוי ה-CI.

## המסלול שכל שינוי עובר

1. **בחרו את ענף הבסיס לפני העריכה.** מצאו את ענף `release/v*` הפעיל הגבוה ביותר וצרו ענף מהקצה
   שלו. הגדירו ענף זה כיעד, ולא את `main`. אם הקפאת גרסה פעילה, אל תגדירו את הענף המוקפא
   כיעד; השתמשו במחזור הפעיל הבא המתואר ב-
   [מודל הסתעפות והפצה](BRANCHING_MODEL.md).
2. **ציינו את החוזים.** זהו כל קטלוג, סכמה, תוצר שנוצר אוטומטית, API ציבורי או ממשק
   משתמש שהשינוי משפיע עליו. הטבלה שלהלן מציגה את קבוצת הפתיחה המינימלית.
3. **כתבו או עדכנו בדיקות ממוקדות.** שינויי ייצור ב-`src/`, ב-`open-sse/`, ב-`electron/` או
   ב-`bin/` מחייבים בדיקה אוטומטית באותה בקשת משיכה. הריצו את קובצי הבדיקה המצומצמים ביותר שמוכיחים את
   ההתנהגות, ולאחר מכן את שערי הבדיקה הממוקדים המפורטים.
4. **אפשרו ל-CI להריץ את המטריצה הרחבה.** כל מקטעי בדיקות היחידה, Vitest, סף הכיסוי המצטבר
   ובניית הייצור מופעלים בבקשת המשיכה. הריצו חבילת בדיקות רחבה באופן מקומי רק כאשר כשל ממוקד מצביע על
   השפעה רחבה יותר או כאשר השינוי משתרע על פני כמה תתי-מערכות.
5. **בצעו התאמה לפני הסקירה.** משכו את ענף הבסיס הפעיל, בדקו את ה-commits החדשים שלו ואת ההבדלים שלכם מולו,
   ולאחר מכן בצעו rebase או merge של ענף הבסיס בהתאם לתהליך העבודה של התורמים. פתרו התנגשויות בקבצים
   שנוצרו אוטומטית ובקטלוגים מתוך המקור שלהם, צרו אותם מחדש, הריצו שוב את הלולאה הממוקדת, וודאו
   שבקשת המשיכה עדיין מכוונת לענף הגרסה הפעיל.
6. **תעדו ראיות.** בתבנית בקשת המשיכה, רשמו את הפקודות שהורצו, כל קובץ בדיקה שנוסף או שונה,
   מיגרציות או דגלי תכונה, וכל אימות שמתבצע ב-CI בלבד ועדיין ממתין.

## מסלולים מומלצים לפי סוג שינוי

הפקודות שלהלן הן בדיקות ממוקדות מינימליות, ולא הרשאה לדלג על בדיקה שמכסה ישירות את
ההתנהגות ששיניתם.

### ספק

**חוזים**

- הגדרת הספק ב-`src/shared/constants/providers/` והשילוב שלה ב-
  `src/shared/constants/providers.ts`.
- מודלים ויכולות ב-`open-sse/config/providerRegistry.ts` או בקובצי ה-registry שחולצו ממנו.
- בחירת executor/translator, תצורת OAuth או מפתח API, נכסי לוח המחוונים ומסמך העזר
  של הספק שנוצר אוטומטית, כאשר רלוונטי.
- פרטי גישה ציבוריים חייבים להשתמש ב-`resolvePublicCred()`; תגובות שגיאה חייבות להשתמש בכלי העזר המשותפים
  להסרת מידע רגיש משגיאות. ראו `docs/security/PUBLIC_CREDS.md` (ב-git; אינו נכלל בהידור אל `/docs`) ואת
  [הסרת מידע רגיש משגיאות](../security/ERROR_SANITIZATION.md).

**לולאה ממוקדת**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # כאשר הקטלוג משתנה; בצעו commit להבדלים שנוצרו
npm run lint
```

בדקו גם כל משפחת בקשות שהושפעה: צ'אט, Responses, תמונות, embeddings, שמע או וידאו.
סקרו את ההבדלים בקטלוג שנוצר ובקובצי ה-golden כשינויי חוזה; אל תאשרו אותם באופן עיוור.

### ניתוב

**חוזים**

- ערכי אסטרטגיה ציבוריים ומטא-נתונים של ממשק המשתמש ב-`src/shared/constants/routingStrategies.ts`.
- שיגור וסדר תחת `open-sse/services/combo.ts` ו-`open-sse/services/combo/`.
- סכמות Combo, שמירה מתמשכת, מצב עמידות, יכולות מודל ואמצעי בקרה ב-API ובממשק המשתמש.
- [מנוע Auto-Combo](../routing/AUTO-COMBO.md) ותיעוד העמידות כאשר ההתנהגות משתנה.

**לולאה ממוקדת**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # שינויי אסטרטגיה או שיגור
npm run check:known-symbols      # שינויי רישום אסטרטגיה
npm run lint
```

השתמשו באופן מקומי בבדיקות דטרמיניסטיות עם שירות upstream מדומה. בדיקות smoke חיות של Combo דורשות פרטי גישה והן
ידניות, ואינן תחליף ל-CI.

### ממשק משתמש / חוויית משתמש

**חוזים**

- נתיב/דף של Next.js וגבולות רכיבים משותפים תחת `src/app/` ו-
  `src/shared/components/`.
- מבני תגובות API, מצבי טעינה/ריק/שגיאה, התנהגות מקלדת וקורא מסך,
  פריסה רספונסיבית, ערכות נושא והרחבת שפות.
- מחרוזות המקור באנגלית של ממשק המשתמש ב-`src/i18n/messages/en.json`; אל תטמיעו ישירות טקסט חדש המוצג למשתמש.

**לולאה ממוקדת**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

הריצו את היישום עבור שינויי אינטראקציה או תצוגה ובדקו תצוגות צרות ורחבות כאחת. ה-CI מריץ את
בניית הייצור ואת חבילות הבדיקות הרחבות יותר; התנהגות חזותית עדיין דורשת רכיב ממוקד, Playwright,
או בדיקה ידנית מתועדת המתאימה לשינוי.

### i18n

**חוזים**

- `src/i18n/messages/en.json` הוא מקור ממשק המשתמש; `config/i18n.json` הוא מקור השפות.
- קטלוגי CLI נמצאים בנפרד תחת `bin/cli/locales/`.
- שמרו על placeholders ותגיות ICU בדיוק כפי שהם. אל תתרגמו שמות של מוצרים/ספקים/מודלים,
  שמות פרוטוקולים וכותרות, פקודות, מזהי קוד/JSON, כתובות URL, משתני סביבה או
  מונחים מוגנים כגון `OmniRoute`, `OAuth`, `MCP` ו-`A2A`. רשימת המקור הנוכחית נמצאת ב-
  `scripts/i18n/glossary/protected-terms.json`.

**לולאה ממוקדת**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # כאשר מחרוזות/קטלוגים של CLI משתנים
npm run lint
```

זוהי הנחיה למערכת הקיימת, ולא הזמנה להרחיב את כלי העבודה או את מודל המפתחות שלה.
שמרו על תיקוני i18n ממוקדים בזמן שהמערכת החלופית מתוכננת. אל תריצו פקודות תרגום
שקוראות לשירותים חיצוניים, אלא אם המשימה דורשת במפורש תרגומים שנוצרו אוטומטית
ובדקתם את ההבדלים שהתקבלו.

### CLI

**חוזים**

- פקודות ודגלים ציבוריים ב-`bin/cli/`, פקודות API שנוצרו, קודי יציאה, stdout/stderr וכן
  מבני פלט JSON, התנהגות תצורה/סביבה וקבצים הנכללים בחבילה.
- מחרוזות CLI המוצגות למשתמש חייבות להשתמש בשכבת ה-i18n של ה-CLI ולשמור על סנכרון בין הקטלוגים `en`/`pt-BR`.
- יש לשמר את Node כסביבת הריצה הנתמכת ואת חוזה הקובץ הבינארי המפורסם.

**לולאה ממוקדת**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # שינויים ב-CLI שנוצר/נארז
npm run check:pack-policy     # שינויים בממשק החבילה
npm run lint
```

יש להשתמש בפקודה המדויקת בספריית נתונים זמנית כאשר ההתנהגות תלויה בניתוח, בקבצים או בסטטוס
היציאה. CI מבצע את הבדיקות הרחבות יותר של ארטיפקט החבילה והמערכת האקולוגית.

### מסד נתונים

**חוזים**

- מודולי תחום תחת `src/lib/db/`; יש לייבא מודולים מסוימים ישירות (שכבת הייצוא מחדש הישנה `localDb.ts` הוסרה).
- מיגרציות SQL ממוספרות ואידמפוטנטיות תחת `src/lib/db/migrations/`, בטיחות טרנזקציות, התנהגות
  שדרוג, אינדקסים וכל רכיב קורא המושפע מהסכמה.
- נתיבים ומטפלים לעולם אינם מריצים SQL גולמי ישירות.

**לולאה ממוקדת**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

בעת הוספת מיגרציה, יש לבדוק הן מסד נתונים חדש והן שדרוג מהסכמה הקודמת. בדיקות מסד הנתונים
חייבות לסגור משאבים ולקרוא ל-`resetDbInstance()` במהלך הניקוי. יש להריץ את `npm run test:bun:db` רק כאשר
נתיב מתאם Bun הפועל על בסיס מאמץ מיטבי משתנה; Node נותר הסמכות הקובעת.

### בנייה / פריסה

**חוזים**

- מניפסטים/קובץ נעילה של השורש וסביבות העבודה, `scripts/build/`, הרכבה עצמאית של Next.js, תוכן
  החבילה `dist/`, מטא-נתוני פלטפורמה של Electron, תהליכי עבודה של CI וסמני פריסה.
- טווחי Node הנתמכים והשימוש המאושר ב-Bun ב-`CLAUDE.md` חייבים להישאר ללא שינוי.
- ארטיפקטים של בנייה נשארים ללא מעקב; חלות מדיניות תלויות, רישיונות, תהליכי עבודה וחבילות.

**לולאה ממוקדת**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # שינויים בתלויות או בקובץ הנעילה
npm run check:pack-policy      # שינויים בממשק החבילה המפורסמת
npm run lint
```

יש להשתמש ב-`npm run build` מקומית רק כאשר השינוי משפיע על הידור, הרכבה עצמאית, נכסים
או אריזה בזמן ריצה. יש להשתמש ב-`npm run build:release` רק לאימות הפצה/פריסה. הבנייה של CI היא
המדד הסופי חוצה-הפלטפורמות; שינויים ב-Electron הייחודיים לפלטפורמה דורשים את הבנייה הממוקדת המתאימה
או הוכחת בדיקת עשן.

## לולאת מועמד מקומית

בדיקות קוד המקור אינן יכולות להוכיח שהתוצר הארוז עולה בהצלחה: רשימות אריזה, תלויות שנוכו וקבצים בינאריים מקוריים נכשלים רק לאחר שקובץ ה-tarball מותקן ומופעל. `npm run dev:candidate`
‏(`scripts/dev/candidate.mjs`) הוא הצד המקומי של תהליך הבנייה-פעם-אחת / אימות / קידום מתוך
RFC #8084: הוא בונה מועמד אחד, מאמת את התוצר המדויק הזה, מקדם אותו באמצעות שינוי שמות של תיקיות ומחזיר אותו לאחור כאשר משבצת היעד שקודמה נכשלת בבדיקת התקינות שלה.

```bash
npm run dev:candidate -- run --dry-run --json  # הדפסת התוכנית, ללא ביצוע שינויים
npm run dev:candidate -- run                   # בנייה + אימות + קידום, עם החזרה אוטומטית לאחור
npm run dev:candidate -- build                 # npm pack + התקנה בתוך _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # הפעלה ביציאה פנויה, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # החלפה בין current ל-previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # שימוש חוזר ב-tarball שנבנה במקום אחר (CI)
```

- **בנייה פעם אחת.** `build` אורז את העץ הנוכחי (הוא זקוק ל-`dist/server.js`, לכן יש להריץ תחילה
  `npm run build:release`) או מעתיק את `--from-tarball`, ולאחר מכן מתקין את ה-tarball בתוך קידומת npm
  מבודדת, משום שה-tarball אינו כולל `node_modules`. המזהה הוא ה-sha המקוצר של `HEAD`
  (עם `-dirty` כאשר יש בעץ שינויים מקומיים) או `tgz-<sha256>` עבור tarball. אם מזהה נקי כבר
  נבנה, נעשה בו שימוש חוזר במקום לבנותו מחדש; העבירו `--force` כדי לבנות אותו מחדש.
- **אימות החבילה, לא קוד המקור.** `validate` מפעיל את ה-CLI המותקן
  (`serve --port <free port>`) עם `DATA_DIR=<candidate>/data` חדש, סודות מדומים, וכאשר
  `OMNIROUTE_API_KEY`,‏ `STORAGE_ENCRYPTION_KEY` ו-`INITIAL_PASSWORD` של המפעיל הוסרו מהסביבה,
  כך שהוא בודק את תצורת הלולאה המקומית ללא מפתח של התקנה חדשה. הוא ממתין עד
  ש-`GET /api/health` יחזיר 200, דורש ש-`GET /v1/models` יחזיר 200, עוצר את קבוצת התהליכים
  ומתעד את התוצאה ב-`validation.json` יחד עם גיבוב ה-tarball.
- **קידום אותו תוצר.** `promote` מסרב למועמד שאין לו אימות מוצלח עבור גיבוב ה-tarball
  הנוכחי שלו. המשבצת הפעילה כברירת מחדל היא `_artifacts/candidate/current`;‏ `--target <dir>`
  בוחר תיקייה אחרת באותה מערכת קבצים, והמשבצת הקודמת שלה היא `<dir>.previous`.
  כל שינוי שם הוא אטומי, וכשל באמצע התהליך מבטל את שינויי השמות שכבר בוצעו.
- **החזרה לאחור.** `run` מאמת שוב את המשבצת שקודמה ומחליף בחזרה בין `current` ל-`previous` כאשר
  בדיקה זו נכשלת. מועמד שנכשל באימות הראשון לעולם אינו מקודם.

הכול נכתב תחת `_artifacts/candidate/`, שמוגדרת להתעלמות על ידי git; התקנת OmniRoute
קיימת ותיקיית הנתונים שלה לעולם אינן משתנות. ה-CLI שקודם נמצא בנתיב
`_artifacts/candidate/current/prefix/bin/omniroute`; הפעילו אותו עם `DATA_DIR` משלכם בעת השימוש
בו. קודי יציאה: `0` הצלחה, `1` אימות או קידום שנכשלו, `2` שגיאת שימוש או בנייה חסרה.

## לולאה מקומית לעומת CI

| להריץ מקומית עבור כל תיקון                                                   | CI מספק תמונת מצב רחבה                                           |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| בדיקות התנהגות ישירות ושערי הקטגוריות שלעיל                                  | חבילת בדיקות היחידה המלאה המחולקת למקטעים ובדיקות טוריות         |
| `npm run lint`                                                               | חבילות בדיקות Vitest ומנגנוני הידוק הדרגתיים לכיסוי ולאיכות      |
| בדיקת טיפוסים או בנייה רק כאשר החוזה המושפע מחייב זאת                        | בניית ייצור, אבטחה, תיעוד, תלויות ושערי מדיניות PR               |
| בדיקות אינטראקציה ידניות/חיות רק כאשר אוטומציה אינה יכולה להוכיח את ההתנהגות | בדיקות אינטגרציה בין משימות ובדיקות פלטפורמה המוגדרות ב-workflow |

לולאה ממוקדת שעברה בהצלחה היא ראיה לגבי החוזה שהשתנה, ולא הוכחה לכך שבדיקות CI שאינן קשורות
יעברו. מנגד, אין לגרום לכל עריכה מקומית להמתין למטריצה המלאה של המאגר.

## רשימת תיוג להתאמה

לפני בקשת סקירה:

- יש לוודא שבסיס ה-PR הוא עדיין ענף `release/v*` הפעיל והגבוה ביותר.
- יש למשוך את הבסיס הזה ולסקור שינויים שנכנסו מאז יצירת הענף.
- יש לסקור את `git diff <active-base>...HEAD` לאיתור שינויים מקריים או שינויים שנוצרו אוטומטית.
- יש לפתור התנגשויות בקטלוג ובמסמכים שנוצרו אוטומטית באמצעות עדכון המקור ויצירה מחדש של הפלט.
- יש להריץ מחדש כל בדיקה/שער ממוקדים המפורטים בתיאור ה-PR לאחר ההתאמה.
- לעולם אין להחליש בדיקות תקינות או להסיר בדיקות נדרשות רק כדי להתאים לבסיס שהשתנה.

לכללי הקפאת גרסה ושינוי יעד, יש לעיין ב-
[מודל הענפים והגרסאות](BRANCHING_MODEL.md). לרשימת ה-CI המלאה, יש לעיין ב-
[מדריך שערי האיכות](../architecture/QUALITY_GATES.md).
