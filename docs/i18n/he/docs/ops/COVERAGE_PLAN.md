## כללים

- יעדי הכיסוי חלים על קובצי קוד מקור, לא על `tests/**`.
- `open-sse/**` הוא חלק מהמוצר וחייב להישאר בהיקף.
- קוד חדש אינו אמור להפחית את הכיסוי באזורים שבהם בוצעו שינויים.
- יש להעדיף בדיקת התנהגות ותוצאות של הסתעפויות על פני פרטי מימוש.
- עבור `src/lib/db/**`, יש להעדיף מסדי נתונים זמניים של SQLite ונתוני בדיקה קטנים על פני הדמיות נרחבות.

## מדיניות Ratchet

יש לעדכן את ערכי הסף של `npm run test:coverage` רק לאחר שהפרויקט חורג בפועל מאבן הדרך הבאה, עם מרווח ביטחון נוח.

**שער נוכחי:** `npm run test:coverage` אוכף **60 הצהרות / 60 שורות / 60 פונקציות / 60 ענפים** (המדד חושב מחדש ב-Quality-Gates Fase 6A.1 — קו הבסיס הקודם של 82.58% היה מנופח משום שהוא כלל קובצי בדיקות ולא כלל את `open-sse`). הפקודה `test:coverage:legacy` משמרת את מדד 50/50/50 הישן לצורך השוואה היסטורית.

לבדיקות סף נקודתיות מול הדוח העדכני ביותר, השתמשו ב:

```bash
node scripts/check/test-report-summary.mjs --threshold 75
```

רצף ה-Ratchet המומלץ (הסדר הוא `הצהרות-שורות / ענפים / פונקציות`):

1. 55/60/55
2. 60/62/58
3. 65/64/62
4. 70/66/66
5. 75/70/72 <-- שער נוכחי (75/70/75)
6. 80/75/78
7. 85/80/84
8. 90/85/88

יעד ה-Ratchet הבא הוא `80/75/78`, לאחר שכיסוי הענפים יישאר מעל 78% בשתי הרצות רצופות.

## פער ידוע

פקודת הכיסוי הנוכחית מודדת את חבילת בדיקות היחידה הראשית של Node וכוללת קוד מקור שאליו היא מגיעה, לרבות `open-sse`. היא עדיין אינה ממזגת את הכיסוי של Vitest לדוח אחוד יחיד. כדאי לבצע את המיזוג הזה בהמשך, אך הוא אינו מהווה חסם להתחלת העלייה מ-60% ל-80%.
