> חסכו 15%-95% מההקשר המתאים באופן אוטומטי. לסקירה מהירה, ראו את [סעיף הדחיסה ב-README](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically).

## סקירה כללית

OmniRoute מממשת צינור מודולרי לדחיסת פרומפטים, שפועל **באופן יזום** לפני שהבקשות מגיעות לספקים במעלה הזרם. פירוש הדבר שהחיסכון בטוקנים מתרחש בשקיפות — ללא צורך בשינויים בתהליך העבודה שלכם.

```
בקשת לקוח
  → בורר אסטרטגיית דחיסה
    → יש דריסה של שילוב? → שימוש בהגדרת השילוב
    → סף הפעלה אוטומטית? → שימוש במצב אוטומטי
    → מצב ברירת מחדל? → שימוש בהגדרה הגלובלית
    → כבוי? → דילוג על הדחיסה
  → מצב הדחיסה שנבחר
    → כבוי: ללא דחיסה
    → קל: ניקוי בטוח של רווחים/עיצוב (~15%)
    → רגיל: הסרת מילות מילוי בסגנון דיבור טלגרפי (~30%)
    → אגרסיבי: יישון היסטוריה + סיכום (~50%)
    → אולטרה: גיזום היוריסטי + דילול בלוקי קוד (~75%)
    → RTK: סינון פלט מסוף/כלים עם מודעות לפקודות (טווח של 60%-90% במעלה הזרם)
    → מוערם: צינור רב-מנועי מסודר, בדרך כלל RTK ואז Caveman (טווח של 78%-95% מהתוכן המתאים)
  → בקשה דחוסה → ספק
```

## מצבי דחיסה

### כבוי

לא מוחלת דחיסה. כל ההודעות עוברות ללא שינוי.

### מצב קל (חיסכון של ~15%, השהיה של <1ms)

המצב הבטוח ביותר — ללא שינוי סמנטי כלל, רק ניקוי עיצוב:

| טכניקה                   | תיאור                                        |
| ------------------------ | -------------------------------------------- |
| `collapseWhitespace`     | מיזוג שורות ריקות רצופות ורווחים בסופי שורות |
| `dedupSystemPrompt`      | הסרת הודעות מערכת כפולות                     |
| `compressToolResults`    | דחיסת פלטים מפורטים של כלים/פונקציות         |
| `removeRedundantContent` | הסרת הוראות חוזרות                           |
| `replaceImageUrls`       | קיצור URI של נתוני תמונה בקידוד base64       |

**מתאים במיוחד עבור:** שימוש קבוע, תהליכי עבודה שבהם הבטיחות קריטית.

### מצב רגיל (חיסכון של ~30%)

בהשראת [Caveman](https://github.com/JuliusBrussee/caveman) — מסיר מילות מילוי וניסוחים ארכניים תוך שימור המשמעות:

- מסיר מילות מילוי ("בבקשה", "אני חושב", "בעיקרון", "למעשה")
- מצמצם ביטויים ארכניים ("על מנת" → "כדי", "כתוצאה מכך ש-" → "כי")
- מסיר הסתייגויות מנומסות ("האם יהיה אכפת לך...", "אם תוכל אולי...")
- יותר מ-30 כללי regex המותאמים לפרומפטים של תכנות

**מתאים במיוחד עבור:** תהליכי תכנות יומיומיים, צוותים שמודעים לעלויות.

### מצב אגרסיבי (חיסכון של ~50%)

ניהול חכם של ההיסטוריה עבור הפעלות ארוכות:

- **יישון הודעות** — הודעות ישנות יותר נדחסות בהדרגה
- **דחיסת תוצאות כלים** — פלטים ארוכים של כלים נקטמים או מושמטים (שורות ראשונות/אחרונות,
  סינון שורות תואמות, דחיסת מפתחות JSON)
- **מנגנוני הגנה על שלמות מבנית** — מוודאים שצמדי `tool_use` + `tool_result` נשארים עקביים
- **מודעות לחלון ההקשר** — מכבדת מגבלות טוקנים לפי מודל

**מתאים במיוחד עבור:** הפעלות ניפוי שגיאות ממושכות, בסיסי קוד גדולים.

### מצב אולטרה (חיסכון של ~75%)

דחיסה מרבית לתרחישים שבהם טוקנים הם משאב קריטי:

- **גיזום היוריסטי** — גיזום טוקנים בטקסט לפי ציון
- **שימור מבנה** — בלוקי קוד מגודרים, קוד בתוך השורה, כתובות URL ומזהים
  מוחלפים זמנית בסמנים ומשולבים מחדש ללא שינוי, ולעולם אינם נגזמים
- **שכבת SLM אופציונלית** — מודל מקומי קטן יכול לעדן את הגיזום כאשר הוא מוגדר
- בלתי תלוי במצב אגרסיבי: הוא אינו מפעיל יישון הודעות, דחיסת תוצאות כלים
  או את מסכם הגיבוי (רק כשל בשכבת SLM יכול לנתב מעבר גיבוי דרך
  המצב האגרסיבי)

**מתאים במיוחד עבור:** מצבים שבהם מגיעים שוב ושוב למגבלות ההקשר.

### מצב RTK (טווח של 60%-90% במעלה הזרם)

מצב RTK ממוטב לפלטים מפורטים של כלים שמופיעים בהפעלות של סוכני תכנות:

- מזהה סוגי פקודות/פלט כגון `git status`, `git diff`, `git log`, מריצי בדיקות,
  תהליכי בנייה של TypeScript/Vite/Webpack,‏ ESLint/Biome/Prettier, ביקורות/התקנות npm, יומני Docker, פלט תשתיות
  ופלט מעטפת כללי
- מחיל חבילות מסנני JSON מתוך `open-sse/services/compression/engines/rtk/filters/`
- מייבא מסננים בסכמת RTK TOML v1 מקובצי `filters.toml` של הפרויקט או מההגדרות הגלובליות, עם אימות
  בדיקות מוטבעות ובקרת אמון עבור קובצי פרויקט
- כולל 55 מסננים מובנים עם דוגמאות אימות מוטבעות
- מסיר רצפי בקרה של ANSI, פסי התקדמות, שורות חוזרות ורעש שאינו בר-פעולה
- משמר כשלים, שגיאות, אזהרות, קבצים שהשתנו, סיכומים ואת החלק האחרון של פלט ארוך
- תומך במסנני פרויקט מבוקרי אמון, במסננים גלובליים ובשחזור אופציונלי של פלט גולמי מושחר

**מתאים במיוחד עבור:** הפעלות סוכן הכוללות תמלילים של מעטפת, בנייה, בדיקות, git,‏ grep ופלט קבצים.

### מצב מוערם (טווח של 78%-95% מהתוכן המתאים)

מצב מוערם מפעיל מספר מנועי דחיסה בסדר דטרמיניסטי. צינור ברירת המחדל הוא:

```txt
RTK -> Caveman
```

סדר זה מכווץ תחילה את פלט המסוף/הכלים, ולאחר מכן מחיל את הצמצום הסמנטי של Caveman על
יתר הפרומפט בשפה טבעית. ניתן להגדיר צינורות מוערמים באופן גלובלי או באמצעות
שילובי דחיסה המוקצים לשילובי ניתוב.

**מתאים במיוחד עבור:** הקשר מעורב הכולל יומני כלים גדולים לצד הוראות אנושיות או סיכומי עוזר.

## חישוב החיסכון ממקורות במעלה הזרם

OmniRoute מתעד את החיסכון באמצעות דחיסה משני מקורות: מדדי ביצועים של פרויקטים במעלה הזרם והרכב המנועים של
OmniRoute עצמו.

| מקור    | הנתון מה-README במעלה הזרם שבו נעשה שימוש כאן                                                                       |
| ------- | ------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` פחות טוקני פלט, חיסכון ממוצע של `65%` בפלט במדדי ביצועים, טווח של `22-87%`, וכלי לדחיסת קלט בשיעור של `~46%` |
| RTK     | חיסכון של `60-90%` בפלט פקודות; הפעלה לדוגמה של `~118,000 -> ~23,900` טוקנים, או חיסכון של `79.7%` (`~80%`)         |

עבור מטענים חופפים של כלים/הקשר, שילוב ברירת המחדל של OmniRoute מערים את המנועים:

```txt
RTK -> Caveman
```

החיסכון המשולב הוא כופלי, לא חיבורי:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

הנתון `78-95%` חל כאשר גם RTK וגם Caveman יכולים לצמצם את אותו מטען קלט/הקשר.
מצב פלט התשובה של Caveman הוא נפרד: כאשר הוא מופעל, יש להשתמש בחיסכון הפלט של Caveman עצמו (`65%`
בממוצע, נתון מוביל של `~75%`, טווח של `22-87%`). החיסכון הכולל בחיוב תלוי בתמהיל הפרומפטים/הפלט שלכם.

### מה המשמעות בפועל של "כשיר"

הטווח המוביל של 15-95% הוא אמיתי, אך הוא חל רק על תוכן **מיותר או מילולי מדי** — שורות
שגיאה חוזרות, יומן בנייה שמציף שוב ושוב את אותה אזהרה, פלט גדול מדי של `grep`/קריאת קובץ. אין
פירוש הדבר שכל בקשה תחסוך בשיעור כזה.

אומת באופן אמפירי (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): הפעלת
`stacked` (RTK + Caveman) על בלוק `tool_result` במבנה של Anthropic, המכיל 300 שורות
שגיאה זהות, הניבה **חיסכון של 95.93% בטוקנים / חיסכון של 96.26% בתווים** — בדיוק בתוך הטווח
המפורסם. אולם הפעלת אותו צינור עיבוד על פלט כלי רגיל שאינו מיותר (רשימת התאמות נקייה של `grep`,
קריאת קובץ קצרה, טקסט שיחה רגיל) מניבה, כצפוי, **חיסכון הקרוב לאפס**, מכיוון
שאין תוכן חוזר להסרה ו-`validateCompression()` (`validation.ts`) מסרבת לשלוח
שכתוב שעלול להסיר או לשנות בלוקי קוד, כתובות URL, כותרות, גרסאות או מזהי קבועים באותיות רישיות בלבד.

זוהי התנהגות צפויה ובטוחה, ולא באג: סשן תכנות שבעיקר קורא קבצים נקיים או מחפש בהם באמצעות grep
יציג חיסכון כולל מתון גם כשהדחיסה מופעלת במלואה, בעוד שסשן שנתקל בלולאה כושלת
או ב-linter פטפטן יציג את מלוא הטווח של 78-95% עבור תעבורה זו. אל תשתמשו באחוז
חיסכון מצטבר נמוך של סשן יחיד כהוכחה לכך שהדחיסה מוגדרת באופן שגוי — בדקו תחילה אם
פלט הכלי הבסיסי אכן היה מיותר.

```
עם Stacked:         10K-2.5K טוקנים נשלחו     (טווח כשיר של 78-95% עבור RTK+Caveman)
```

## הגדרות

### לוח הבקרה

נווטו אל `Dashboard → Context & Cache`:

- **Caveman** — בחירת מצב, חבילות שפה, תצוגה מקדימה וברירות מחדל גלובליות
- **RTK** — תצוגה מקדימה של מסנן פקודות, הגדרות בטיחות של RTK וקטלוג מסננים
- **Compression Combos** — צינורות עיבוד בעלי שמות של מנועי דחיסה, המוקצים לשילובי ניתוב
- **Auto-Trigger Threshold** — הפעלה אוטומטית של דחיסה כאשר מספר הטוקנים חורג מהסף

### דריסה לפי שילוב

ב-`Dashboard → Context & Cache → Compression Combos`, הקצו שילוב דחיסה לשילוב ניתוב:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

כך ניתן להשתמש בדחיסה משולבת אצל ספקים חינמיים או ספקי קידוד, תוך שמירה על מצב lite במינויים
בתשלום.

הקצאת "דריסה לפי שילוב" זו היא פקד נפרד מדריסת **מצב הדחיסה של שילוב הניתוב**
(Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — הסכימה של השדה מקבלת גם את
`rtk`,‏ `stacked` ו-`omniglyph`) — דריסה זו אינה בוחרת צינור עיבוד של שילוב דחיסה בעל שם;
היא רק מגדירה את השדה `compressionMode` שבו משתמש `resolveCompressionPlan`. ניתן להגדיר אותה
בכרטיס השילוב (`Dashboard → Combos`) או, החל מ-#6760, לכל שילוב ניתוב בנפרד ברשימה
"Assign to routing" שב-`Dashboard → Context & Cache → Compression Combos`, ממש לצד תיבת הסימון
להקצאת צינור העיבוד המתועדת לעיל. שני הממשקים שומרים את הנתונים באמצעות אותה נקודת קצה
`PUT /api/combos/{id}`.

### דריסה לפי בקשה

שלחו את כותרת הבקשה `x-omniroute-compression` כדי לדרוס את תוכנית הדחיסה עבור בקשה יחידה.
יש לה את העדיפות הגבוהה ביותר — היא גוברת על דריסת שילוב הניתוב, הפרופיל הפעיל,
ההפעלה האוטומטית וברירת המחדל של הלוח. המערכת מתעלמת מערכים לא מוכרים (הבקשה לעולם אינה נדחית),
והמתג הראשי הגלובלי עדיין שולט בכול: כאשר הדחיסה כבויה באופן גלובלי, הכותרת אינה יכולה
להפעיל אותה. ערכים:

| ערך           | השפעה                                                                                     |
| ------------- | ----------------------------------------------------------------------------------------- |
| `off`         | ללא דחיסה עבור בקשה זו.                                                                   |
| `default`     | פרופיל ברירת המחדל שנגזר מהלוח (מתעלם מהפרופיל הפעיל). מנועים מאבדי מידע נותרים כבויים.   |
| `safe`        | זהה להשמטת הכותרת: הסרת כפילויות וצמצום רווחים בלבד.                                      |
| `allow-lossy` | שימור תוכנית המפעיל של בקשה זו, לרבות סיכומים, מסנני רלוונטיות ושכתובים סגנוניים.         |
| `engine:<id>` | מנוע יחיד, כאשר הוא מופעל, למשל `engine:rtk`. זוהי הסכמה מפורשת לפי בקשה לשימוש במנוע זה. |
| `<combo>`     | שילוב בעל שם, שמותאם תחילה לפי שם (ללא תלות ברישיות) ולאחר מכן לפי מזהה.                  |

ללא `allow-lossy`,‏ `engine:<id>` או שילוב בעל שם, מנועים מאבדי מידע אינם מופעלים. כאשר הדחיסה
פעילה, הבקשה עדיין עוברת הסרת כפילויות ברמת ההפעלה וצמצום רווחים.

התוכנית שהופעלה מוחזרת בכותרת התגובה `X-OmniRoute-Compression: <mode>; source=<source>`,
כאשר `<source>` הוא אחד מהערכים `request-header`,‏ `routing-override`,‏ `active-profile`,
‏`auto-trigger`,‏ `default` או `off`.

## מערכות דחיסה מתקדמות

מעבר ל-7 המצבים שתוארו לעיל (קוד המקור מקבל גם את המצבים `codex-responses` ו-
`omniglyph`, שאינם נידונים במדריך זה), הסעיפים הבאים עוסקים בתכונות שפועלות
בתוך מצבים אלה או לצדם: דחיסת תוצאות כלים והתיישנות הדרגתית הן שלבים 1 ו-2
של המנוע האגרסיבי (מצב Aggressive ושלב `aggressive` בצינור עיבוד מוערם),
צינור העיבוד המוערם הוא האופן שבו מצב Stacked פועל, דחיסה מודעת-מטמון
מורידה את `aggressive` ואת `ultra` ל-`standard` עבור ספקים המשתמשים במטמון
כאשר הדחיסה מופעלת, ומצב הפלט של Caveman וסגנונות הפלט הם הנחיות מערכת
אופציונליות, המושבתות כברירת מחדל, שמעצבות את פלט המודל במקום לדחוס את הבקשה.

### דחיסה מודעת-מטמון

ספקים מסוימים (כמו Anthropic עם אחסון הנחיות במטמון) תומכים ב**אחסון הנחיות במטמון**,
המאפשר להם לשמור חלקים מההנחיה במטמון כדי להפחית עלויות וזמן השהיה. כאשר
האחסון במטמון מופעל, דחיסה אגרסיבית עלולה למעשה **לפגוע** בביצועים
משום שהיא משנה את האסימונים שנשמרו במטמון ובכך מבטלת את תוקפו.

המודול `cachingAware.ts` פותר זאת באמצעות **זיהוי הקשר של אחסון במטמון**
ו**התאמת אסטרטגיית הדחיסה** בהתאם.

#### כיצד זה פועל

1. **זיהוי הקשר של אחסון במטמון** — סורק את גוף הבקשה לאיתור סמני `cache_control`
2. **זיהוי ספקים המשתמשים במטמון** — בודק אם ספק היעד תומך באחסון במטמון
3. **התאמת האסטרטגיה** — מוריד את `aggressive`/`ultra` ל-`standard` עבור ספקים המשתמשים במטמון
4. **דילוג על הנחיית המערכת** — הנחיות מערכת נשמרות בדרך כלל במטמון, ולכן אין לדחוס אותן

מסייע האסטרטגיה מחזיר גם דגל `deterministicOnly`, אך בונה התוכנית משתמש
רק באסטרטגיה — נכון להיום, שום רכיב בהמשך התהליך אינו קורא את הדגל.

#### דוגמת קוד

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← סמן מטמון
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### מתי להשתמש

דחיסה מודעת-מטמון **פועלת תמיד** — אין צורך בהגדרה. היא נכנסת לפעולה בכל פעם
שהדחיסה מופעלת וספק היעד תומך באחסון הנחיות במטמון (Anthropic, OpenAI
וכדומה); סמני `cache_control` מפורשים אינם נדרשים — ספק המשתמש במטמון לבדו
מפעיל את ההורדה, וסמנים לבדם לעולם אינם עושים זאת (זיהוי הסמנים מזין את
נתוני הטלמטריה של המטמון, ולא את החלטת האסטרטגיה).

### התיישנות הדרגתית

שיחות ארוכות צוברות חילופי הודעות רבים, אך חילופים ישנים נעשים פחות
רלוונטיים. המודול `progressiveAging.ts` **מפחית את רמת הפירוט של הודעות לפי מרחקן בתורות**
(המרחק נמדד מסוף השיחה). עם ברירות המחדל שסופקו
(`verbatim: 2, light: 2, moderate: 3`):

- **2 התורות האחרונות (מרחק ≤ 2)**: נשמרות כלשונן
- **מרחק 3**: דחיסת איש מערות (הסרת מילות מילוי)
- **מרחק 4+**: הודעות העוזר מסוכמות; הודעות המשתמש מצטמצמות לשורה הראשונה שלהן,
  ומוגבלות ל-120 תווים; תפקידים אחרים נותרים ללא שינוי. הנחיות מערכת, הודעות שכבר יושנו
  והודעת המשתמש האחרונה נשמרות תמיד כלשונן, ללא קשר למרחק.
  דבר אינו מושמט לחלוטין, ורצועת `light`
  אינה נגישה עם ברירות המחדל המסופקות (`light` שווה ל-`verbatim`).

#### דוגמת קוד

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... עוד 50 תורות ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // 3 התורות האחרונות: כלשונן
  light: 8, // מרחק <= 8: דחיסה קלה
  moderate: 20, // מרחק <= 20: דחיסת איש מערות
  fullSummary: 5, // נדרש על ידי הטיפוס, אך אינו נקרא על ידי קוד החלוקה לרצועות
  // מרחק > 20: סיכום (עוזר) / שמירת השורה הראשונה (משתמש)
});

// saved = מספר האסימונים שנחסכו
```

#### מתי להשתמש

יישון הדרגתי **פעיל תמיד** במצב `aggressive` — זהו שלב 2 של
`compressAggressive()`. מצב Ultra אינו מפעיל אותו. הוא
יעיל במיוחד עבור:

- הפעלות תכנות ממושכות
- שיחות הנמשכות מספר ימים
- תהליכי עבודה סוכניתיים עם קריאות רבות לכלים

### מצב פלט איש מערות

מצב פלט איש מערות מוסיף **הנחיות למערכת** המבקשות מהמודל עצמו להפיק
פלט תמציתי — רמת `lite` מבקשת תשובות תמציתיות השומרות על משפטים מלאים, `full`
מבקשת ממנו "להשיב בתמציתיות כמו איש מערות חכם", ו-`ultra` מבקשת פלט טלגרפי;
ההנחיות רק מבקשות זאת, ואינן יכולות להבטיח זאת. בקשות מקבלות אותן באמצעות
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`):
תחילה, `open-sse/handlers/chatCore.ts` פותר את הבחירה באמצעות שכבת התאימות לאחור
(`resolveOutputStyleSelection()` בתוך
`open-sse/services/compression/outputStyles/backCompat.ts`), אשר, כל עוד `outputStyles`
ריק, ממפה `cavemanOutputMode` מופעל לסגנון הפלט `terse-prose` בעוצמה
`cavemanOutputMode.intensity` (ראו תאימות לאחור להלן); בחירת `outputStyles`
שאינה ריקה משמשת כפי שהיא, ואז ל-`cavemanOutputMode.enabled` ול-`intensity` אין
השפעה, בעוד שמתג `autoClarity` שלו עדיין חל. הקובץ `outputMode.ts` מכיל את
טקסטי ההנחיות (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), את עקיפת התוכן ואת
כלי העזר למיקום שבו משתמשת ההזרקה; למזריק `applyCavemanOutputMode()` שלו עצמו אין
קורא בסביבת הייצור.

#### כיצד זה עובד

מצב זה אינו דוחס את הקלט. הוא מוסיף בלוק הנחיות להנחיית המערכת
(ראו כיצד ההזרקה עובדת להלן), וכל מצב דחיסת קלט שנבחר עבור הבקשה
עדיין מופעל לאחר מכן, על הגוף שמכיל כעת את הבלוק. לפני סעיף
הגבולות המשותף שבו מסתיימת כל רמה, רמת `full` באנגלית אומרת:

> "השב בתמציתיות כמו איש מערות חכם. השמט תוויות (a/an/the), מילות מילוי (just/really/basically/actually/simply), דברי נימוס והסתייגויות. קטעי משפטים מותרים. מילים נרדפות קצרות (big ולא extensive,‏ fix ולא implement). שמור במדויק על כל התוכן הטכני, הקוד, השגיאות, כתובות ה-URL והמזהים."

מצב זה פועל היטב במיוחד עבור:

- יצירת קוד (פלט תמציתי יותר = פחות אסימונים)
- שאלות ותשובות מהירות (אין צורך בהסברים מפורטים)
- עיבוד באצוות (למיצוי מרבי של התפוקה)

#### מתי להשתמש

מצב פלט איש מערות הוא **אופציונלי**. כאשר הדחיסה מופעלת (`enabled: true`, המתג הראשי
בדף הגדרות הדחיסה), הפעילו אותו באמצעות `cavemanOutputMode.enabled`;‏ `intensity`
בוחר `lite`,‏ `full` או `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

מתג **מצב הפלט** של שילוב דחיסה (`outputMode`, כשהרמה נמצאת ב-`outputModeIntensity`)
מגדיר את אותו מתג עבור הבקשות שעליהן חל השילוב, וכלי ה-MCP
`omniroute_set_compression_engine` כותב אותו באמצעות הארגומנט הבוליאני `outputMode`
שלו. בחירת `outputStyles` שאינה ריקה מקבלת עדיפות על פני מתג זה. בלוח
הבקרה, הפעלת סגנון הפלט **פרוזה תמציתית** מזריקה את אותו בלוק (ראו סגנונות
פלט להלן).

### סגנונות פלט (קטלוג)

מצב פלט איש מערות שלעיל הוא **הנתיב הישן לסגנון יחיד**. שלב 4 הכליל אותו
לקטלוג של סגנונות פלט הניתנים לשילוב: `OUTPUT_STYLE_CATALOG` בתוך
`open-sse/services/compression/outputStyles/catalog.ts`. כל סגנון הוא הנחיית מערכת
המבקשת מהמודל עצמו להפיק פלט חסכוני יותר; אפשר להפעיל סגנונות
יחד, והם מוזרקים לפי סדר הקטלוג.

כל סגנון מסופק בשלוש רמות עוצמה — `lite`,‏ `full`,‏ `ultra` — וכל רמה
מסתיימת בסעיף הגבולות המשותף (`SHARED_BOUNDARIES` בתוך `outputMode.ts`), אשר
שומר במדויק על בלוקי קוד, נתיבי קבצים, פקודות, שגיאות וכתובות URL. הטקסטים של רמות
`terse-prose` ו-`terse-cjk` מוסיפים גם מזהים לרשימה זו.

`terse-cjk` מוגבל לפי אזור ל-`zh` בשני מקומות. דף הגדרות הדחיסה מציג
את השורה שלו רק כאשר שפת ממשק המשתמש של לוח הבקרה היא סינית (`zh-CN` או `zh-TW`), ו-
`applyOutputStyles()` מזריק אותו רק כאשר השפה שנקבעה לבקשה (ראו בחירת שפה
להלן) היא `zh`. הסתרת השורה אינה מוחקת בחירת `terse-cjk` שמורה:
ה-API של ההגדרות מקבל כל מזהה סגנון, ושמירת סגנונות אחרים בדף משמרת אותה. בזמן
הבקשה, בדיקת השפה של `applyOutputStyles()` היא מגבלת האזור היחידה.

#### כיצד ההזרקה פועלת

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) פותר
את הבחירה מול הקטלוג (מזהים לא מוכרים וסגנונות שאינם תואמים לאזור
מושמטים, ולעולם אינם גורמים לשגיאה; בחירה שלא נפתרת לשום סגנון משאירה את הגוף
ללא שינוי ומדולגת כ-`no_styles`), משרשר את ההוראות שנבחרו לפי סדר
הקטלוג,
מוסיף את סעיף הגבולות **פעם אחת** (וכן את סעיף הבטיחות, `SAFETY_BOUNDARIES` או
תרגומו, כאשר `less-code` או `ponytail` נבחר), ומתחיל את הבלוק בסמן
אידמפוטנטיות יחיד (`[OmniRoute Output Styles]`), כך שהחלה חוזרת אינה עושה דבר. כאשר
לשפה שנקבעה (ראו בחירת שפה להלן) יש תרגום, ההוראה המתורגמת
מוזרקת במקום האנגלית.

בגוף עם מערך `messages` שאינו ריק, בדיקת האידמפוטנטיות מתבצעת לפני
עקיפת התוכן: כאשר הסמן `[OmniRoute Output Styles]` כבר נמצא בשדה `system`
ברמה העליונה (מחרוזת או מערך בלוקי תוכן) או בהודעת מערכת עם תוכן
מחרוזת, הגוף נשאר ללא שינוי כ-`already_applied` ולא מתבצעת בדיקת מילות מפתח.
אחרת, עקיפת תוכן (`shouldBypassCavemanOutputMode()` בתוך
`open-sse/services/compression/outputMode.ts`) בודקת את הטקסט של שלוש ההודעות
האחרונות, ללא קשר לתפקידן, ומדלגת על הסגנונות במשך כל התור כאשר הטקסט
תואם למילות המפתח של אבטחה, פעולה בלתי הפיכה או הבהרה, או לרצף
תלוי-סדר: `first`,‏ `then`,‏ `after that`,‏ `before`,‏ `rollback` או
`backup`, ואחריהן בתוך 240 תווים `delete`,‏ `drop`,‏ `migrate`,‏ `deploy` או
`release`. העקיפה פועלת כל עוד המתג **עקיפת בהירות אוטומטית**
(`cavemanOutputMode.autoClarity`, מופעל כברירת מחדל) מופעל; כיבוי המתג מדלג על
בדיקת מילות המפתח.

כאשר העקיפה מאפשרת לתור להמשיך, `placeSystemInstruction()` (באותו קובץ), אשר
לעולם אינו יוצר `messages[0]` חדש, ממקם את הבלוק במקום הראשון מבין הבאים שנמצא:

1. הודעת מערכת פותחת עם תוכן מחרוזת: הבלוק נוסף אחרי הטקסט שלה.
2. השדה `system` ברמה העליונה: הבלוק נוסף אחרי הטקסט של מחרוזת, או
   נוסף כבלוק טקסט חדש למערך בלוקי תוכן.
3. הודעת המערכת המאוחרת הראשונה עם תוכן מחרוזת: הבלוק נוסף אחרי
   הטקסט שלה.
4. אף אחד מהאמור לעיל: הבלוק מוכנס להודעת מערכת חדשה בסוף `messages`.

בגוף ללא מערך `messages` (או עם מערך ריק), לא מתבצעת עקיפת תוכן
ולא נבדק שדה `system` ברמה העליונה. הבלוק נוסף אחרי הטקסט של
שדה `instructions` מסוג מחרוזת, אלא אם שדה זה כבר מכיל את הסמן
`[OmniRoute Output Styles]`, ובמקרה כזה הגוף נשאר ללא שינוי כ-
`already_applied`. כאשר לגוף אין שדה `instructions` מסוג מחרוזת אך הוא כולל `input`
(מחרוזת או מערך), הבלוק הופך ל-`instructions` ומחליף כל ערך שאינו מחרוזת
שהיה בשדה זה. גוף שאין בו שדה `instructions` מסוג מחרוזת וגם לא `input` מסוג מחרוזת או
מערך נשאר ללא שינוי ומדולג כ-`no_messages`.

#### כיצד להפעיל

בלוח הבקרה: **Compression Context → Compression Settings**
(`/dashboard/context/settings`), במקטע Output styles: שורה אחת לכל סגנון, עם מתג הפעלה/כיבוי
ובורר רמה. הסגנונות מוזרקים כאשר הדחיסה עצמה מופעלת (המתג הראשי של הדף,
`enabled`). המתג **Auto-Clarity Bypass** נמצא בדף **Caveman**
(`/dashboard/context/caveman`), בכרטיס **Output Mode** שלו. מבחינה תכנותית, תצורת
הדחיסה שומרת את הבחירה כך:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

תאימות לאחור: כל עוד `outputStyles` ריק, ההגדרה הישנה `cavemanOutputMode.enabled`
ממופה אל `terse-prose` בעוצמה `cavemanOutputMode.intensity`. הבלוק מתחיל אז
בסמן `[OmniRoute Output Styles]`, בעוד שהמזריק הישן `applyCavemanOutputMode()`
כתב `[OmniRoute Caveman Output Mode]`. מתחת לסמן, הטקסט תואם להזרקה
הישנה בשפות en, pt-BR, es, de, fr, it, ru, id ו-vi; בשפות ja ו-zh יש בו
רווח נוסף אחד לפני פסוקית הגבולות. `terse-prose` מתורגם לשפות pt-BR, es, de,
fr, it, ru, zh, ja, id ו-vi, ולכן בקשה שהשפה שנקבעה עבורה היא `hu` מקבלת את
הטקסט באנגלית, בעוד שהמזריק הישן השתמש בטקסט ההונגרי שלו.

בחירת השפה לסגנון הפלט (`resolveOutputStyleLanguage()` בתוך
`outputStyles/apply.ts`): כאשר `languageConfig.enabled` מופעל, `autoDetect` דוגם את
הודעת המשתמש האחרונה במערך `messages` של הבקשה שמכילה טקסט (תוכן מסוג מחרוזת, או
ה-`text` של חלקי התוכן שלה), ומריץ עליה את הגלאי של מנוע Caveman
(`detectCompressionLanguage()`). הגלאי מחזיר `zh` עבור טקסט שמכיל תווי Han
ואינו מכיל kana; אחרת הוא מחזיר את השפה בעלת מספר התאמות הרמזים הרב ביותר מבין
`it`,‏ `pt-BR`,‏ `es`,‏ `de`,‏ `fr`,‏ `ru`,‏ `ja`,‏ `hu` ו-`id`, ואת `en` כאשר אין
התאמות — טקסט שלא ניתן לסווג מקבל אנגלית, לעולם לא `defaultLanguage`, ו-`vi`
לעולם אינה מזוהה אף שהסגנונות כוללים טקסט ב-`vi`. גוף של Responses API שומר את
התורות שלו בתוך `input`, שאינו נדגם, ולכן הוא מקבל את `defaultLanguage`, ולאחר
מכן אנגלית. כאשר אף הודעת משתמש בתוך `messages` אינה מכילה טקסט, או כאשר
`autoDetect` כבוי, מוחל `defaultLanguage`, ולאחר מכן אנגלית. כאשר
`languageConfig.enabled` כבוי, השפה היא אנגלית — אלא אם שילוב דחיסה מוחל על
הבקשה (שילוב שהוקצה לשילוב הניתוב של הבקשה, או שילוב הדחיסה המוגדר כברירת מחדל
שאליו chatCore חוזר עבור צינור העיבוד המובנה והמדורג): החלת שילוב מפעילה את
`languageConfig.enabled` עבור אותה בקשה ומגדירה את `defaultLanguage` מחבילות
השפה של השילוב (הערך השמור, אם הוא אחת מחבילות השילוב; אחרת החבילה הראשונה של
השילוב, שברירת המחדל שלה היא `en`), בעוד שההגדרה השמורה של `autoDetect`
(מופעלת כברירת מחדל) עדיין חלה. מנוע הקלט של Caveman בוחר את שפת חבילת הכללים
שלו באופן שונה — עבור כל חלק טקסט בנפרד, וכאשר הזיהוי האוטומטי כבוי, בכפוף
ל-`enabledPacks`.

מטריצת הסגנון × השפה מקובעת באמצעות
`tests/unit/compression/output-styles-i18n-matrix.test.ts`: לכל סגנון בקטלוג חייבת
להיות רשומה ב-`BASELINE_LANGUAGES` של הבדיקה; סגנון שאינו מוגבל לפי אזור חייב
לכלול תרגום ל-pt-BR (הסגנון `terse-cjk`, המוגבל לפי אזור, פטור מכלל זה), אלא אם
הוא מופיע ב-`KNOWN_ENGLISH_ONLY`, שעשוי להכיל רק סגנונות ללא תרגומים כלל —
סגנון שמופיע בו ונמצא עבורו תרגום כלשהו גורם לכישלון הבדיקה; וסגנון גורם
לכישלון הבדיקה כאשר חסרה בו שפה שמופיעה ברשומת `BASELINE_LANGUAGES` שלו. כדי
להוסיף סגנון, ראו
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style).

### דחיסת תוצאות כלים

`compressToolResult()` בתוך `open-sse/services/compression/toolResultCompressor.ts`
דוחסת טקסט של תוצאות כלים באמצעות **5 אסטרטגיות**. היא מנסה אותן בסדר הבא,
והאסטרטגיה המופעלת הראשונה שהבדיקה שלה תואמת לתוכן קובעת את התוצאה:

1. **`fileContent`**: תוכן בן 3 שורות או יותר, שבו לפחות שורה אחת, בהתעלם
   מהזחה בתחילת השורה, מתחילה ב־`import `,‏ `export `,‏ `function `,‏ `class `,
   ‏`const `,‏ `let `,‏ `var ` או `return ` (מילת המפתח בתוספת רווח), או ב־`if`,
   ‏`for` או `while` ואחריהם `(` או ` (`, שומר את 20 השורות הראשונות ואת 5 האחרונות,
   כשהקטע האמצעי שהושמט מסומן.
2. **`grepSearch`**: תוכן הכולל לפחות שורה אחת בתבנית `<path>:<digits>:`,
   שבה הטקסט שלפני הנקודתיים הראשונות אינו מכיל רווחים, שומר רק את השורות האלה, עד
   30 לכל היותר, ואחריהן את מספר ההתאמות הנוספות ואת רשימת הקבצים שנמצאו בהם
   התאמות; כל שורה אחרת מושמטת. די בשורה אחת כזו כדי להפעיל את האסטרטגיה, ולכן גם
   שורת יומן שמתחילה בחותמת זמן כגון `12:30:45` נחשבת.
3. **`shellOutput`**: פלט שמכיל רצף ANSI CSI‏ (`ESC[` ואחריו ספרות או
   נקודה־ופסיק ולאחר מכן אות, כמו בקודי צבע) או `$` שאחריו רווח לבן במקום כלשהו
   בטקסט מאבד את הרצפים האלה (רצפי escape אחרים, כגון `ESC[?25l` או רצף OSC
   לכותרת החלון, נשמרים) ושומר את 50 השורות האחרונות שלו, תוך איחוד שורות זהות
   רצופות. מכיוון שבדיקה זו מתבצעת לפני `json` ו־`errorMessage`, פלט JSON או פלט
   שגיאה שמכילים `$` כזה לעולם אינם מגיעים אליהם כאשר `shellOutput` מופעל.
4. **`json`**: מטען JSON שאורכו יותר מ־2,000 תווים, שמתחיל ב־`{` או `[` (לאחר
   רווח לבן אופציונלי) ושניתן לנתח אותו, מסוכם: מערך הכולל יותר מ־7 פריטים שומר
   את 5 הפריטים הראשונים ואת 2 האחרונים ואת מספר הפריטים הכולל, ואובייקט שומר את
   20 המפתחות הראשונים, כאשר כל ערך של אובייקט או מערך מקונן מוחלף במציין מיקום
   `{…N keys}` (במערך, N הוא אורכו) ובסמן `_remaining_<N>_keys` שסופר את המפתחות
   שהושמטו מעבר ל־20 הראשונים. ערכים סקלריים מועתקים במלואם, ולכן אובייקט בן 20
   מפתחות או פחות, ללא ערכים מקוננים, רק מוזח מחדש — אובייקט ממוזער צובר תווים
   ונשאר ללא שינוי.
5. **`errorMessage`**: פלט שמכיל, במקום כלשהו וללא תלות ברישיות, `error:`,
   ‏`error ` (המילה ואחריה רווח, כמו ב־`no error found`),‏ `[error]`,
   ‏`exception:`,‏ `exception `,‏ `[exception]` או `traceback`, שומר את השורה
   הראשונה, את 10 השורות הבאות ואת 3 האחרונות, כאשר הסמן
   `… [N frames elided] …` מחליף את השורות שביניהן. הסמן מופיע רק כאשר יותר
   מ־13 שורות מופיעות לאחר השורה הראשונה, ולכן פלט שגיאה בן 14 שורות או פחות
   אינו מתקצר (ב־12 או 13 שורות, 3 השורות האחרונות משכפלות שורות שכבר נשמרו).

לאחר התאמה של אסטרטגיה, גם אם היא אינה חוסכת דבר, האסטרטגיות הבאות אינן
נבדקות. כאשר האסטרטגיה התואמת אינה חוסכת טוקנים משוערים (האורך חלקי 4, בעיגול
כלפי מעלה) — לדוגמה, קובץ דמוי קוד בן 25 שורות או פחות, או מערך JSON שאורכו
יותר מ־2,000 תווים ובו 7 פריטים או פחות — המנוע האגרסיבי שומר את תוצאת הכלי
המקורית: שני הקוראים (`compressAggressive()` ו־`compressAnthropicToolResultBlock()`)
שומרים את המקור כאשר `saved` הוא 0 או פחות, בעוד `compressToolResult()` עצמו עדיין
מחזיר את פלט האסטרטגיה. שלב תוצאת הכלי אינו סוף פסוק: מסכם ברירת המחדל של
המנוע עדיין יכול לקצר הודעת `tool` או `function` שאורכה עולה על 8,192 תווים
(`maxTokensPerMessage`,‏ 2,048, כפול 4).

#### מתי להשתמש

דחיסת תוצאות כלי היא שלב 1 במנוע האגרסיבי (`compressAggressive()` בתוך
`open-sse/services/compression/aggressive.ts`), ולכן היא פועלת במצב Aggressive
ובשלב `aggressive` של צינור עיבוד משולב. היא דוחסת הודעות `tool` ו־`function`
במבנה OpenAI ואת הטקסט שבתוך בלוקי `tool_result` של Anthropic. לכל אסטרטגיה יש
מתג משלה תחת `aggressive.toolStrategies`, וכולם מופעלים כברירת מחדל. בלוח
המחוונים, המתגים נמצאים בתצוגת **Advanced** בדף Caveman כאשר הדחיסה מופעלת
ומצב ברירת המחדל הוא Aggressive.

### צינור עיבוד משולב

המצב המשולב מפעיל **מנועים מרובים ברצף** — בדרך כלל RTK תחילה
(חיסכון של 60-90% בפלט כלים), ולאחר מכן Caveman על הטקסט שנותר (חיסכון של
כ־46% בקלט). בשילוב, זהו **טווח זכאות של 78-95%** (ראו חישוב חיסכון במעלה
הזרם לעיל): `1 - (1 - 0.60..0.90) × (1 - 0.46)` הוא כ־89% בממוצע.

#### כיצד זה פועל

```
קלט (1000 טוקנים)
  → RTK (מסנן מודע לפקודות) → 200 טוקנים
    → Caveman (הסרת מילות מילוי) → 108 טוקנים
  → פלט (108 טוקנים, חיסכון של כ־89%)
```

#### מתי להשתמש

השתמשו במצב משולב עבור:

- תהליכי עבודה עתירי כלים (כתיבת קוד סוכנית, מחקר)
- עיבוד אצווה רגיש לעלויות
- כאשר נדרש חיסכון מרבי בטוקנים

צינורות עיבוד משולבים מוגדרים באמצעות הגדרת הדחיסה הגלובלית `stackedPipeline`,
או באמצעות שילוב דחיסה בעל שם שהוקצה לשילוב ניתוב (ראו עקיפה לפי שילוב לעיל) —
ולא באמצעות `modePack` של שילוב אוטומטי (שדה זה רק משנה את המשקולות של בחירת
המודל בשילוב האוטומטי, ו־`stacked` אינו שם חבילה תקין).

## דריסות דחיסה לשילובים

ניתן לדרוס את מצב הדחיסה הגלובלי **עבור כל שילוב בנפרד** כדי לכוונן את ההתנהגות
למקרי שימוש שונים:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

אפשרות זו שימושית עבור:

- **שילובי קידוד**: השתמשו במצב `aggressive` להפעלות ארוכות
- **שילובי שאלות ותשובות מהירות**: השתמשו במצב `lite` לתגובות מהירות
- **שילובים עתירי כלים**: השתמשו במצב `stacked` לחיסכון מרבי
- **שילובי ייצור**: השאירו את הדריסה כבויה עבור ספקים המשתמשים במטמון — ההתאמה
  המודעת למטמון, שפועלת תמיד, משנמכת את `aggressive`/`ultra` ל-`standard` באופן אוטומטי
  (אין מצב `cache-aware` שניתן לבחור בו)
