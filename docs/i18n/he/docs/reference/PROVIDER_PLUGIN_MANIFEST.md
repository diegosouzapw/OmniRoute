`open-sse/config/providerPluginManifest.ts` מגדיר את חוזה התוסף של הספק, המותאם ל-JSON.
`open-sse/config/providerPluginManifestRegistry.ts` מקשר חוזה זה למרשם הספקים הנוכחי עבור תהליכי sidecar כגון Bifrost,
CLIProxyAPI או נתב Go/Rust עתידי. מרשם ה-TypeScript נשאר
מקור האמת, אך תהליכי sidecar יכולים לצרוך את המניפסט בלי לייבא
קוד executor, ברירות מחדל של OAuth, כותרות או מצב של סביבת התהליך.

אותו מניפסט זמין גם דרך HTTP בכתובת
`GET /api/v1/provider-plugin-manifest` עבור תהליכי sidecar שרצים מחוץ לתהליך.

OmniRoute מפרסם את כתובת ה-URL הזו ל-Bifrost ול-CLIProxyAPI באמצעות כותרת הבקשה
`X-OmniRoute-Provider-Manifest-Url`. הגדירו את
`OMNIROUTE_PROVIDER_MANIFEST_URL` כאשר תהליך ה-sidecar זקוק לכתובת URL ציבורית או לכתובת ברשת
של קונטיינרים במקום מקור הבקשה המקומי.

## רענון המניפסט

נקודת הקצה של HTTP מחזירה `Cache-Control: public, max-age=60` ו-`ETag`
חזק. תהליך sidecar צריך לשמור את המניפסט האחרון שאומת ולשלוח את ה-ETag שלו
ב-`If-None-Match` בעת רענון. לתגובת `304 Not Modified` אין גוף;
תהליך ה-sidecar ממשיך להשתמש במניפסט השמור שלו. אם לא קיים מניפסט שמור ומאומת,
תהליך ה-sidecar חייב לשלוח בקשה בלתי מותנית במקום לקבל תגובת `304`.

## מטרה

להעביר את המטא-נתונים של הספקים לכיוון של חוזה תוספים, כך שבסופו של דבר תהליך sidecar בעל
זמן השהיה נמוך יותר יוכל להיות אחראי על נתיב הבקשות החם, בעוד OmniRoute משאיר את
נתיב ה-TypeScript כשער המדיניות וכמנגנון גיבוי. המניפסט הוא תוספתי: הוא
אינו משנה את ניתוב הבקשות בפני עצמו.

## חוזה

המניפסט מכיל:

- מזהה וכינוי של הספק
- פורמט upstream ושם ה-executor
- סוג אימות, כותרת אימות וקידומת אימות אופציונלית
- מטא-נתונים סטטיים של נקודת הקצה
- התאמה ל-sidecar וסיבות מפורשות לכך שספק צריך להישאר בנתיב ה-TS
- מטא-נתונים של מודלים המותאמים ל-JSON, כגון אורך הקשר, דגלי ראייה/הסקה ופרמטרים
  שאינם נתמכים
- תגיות יכולת, כולל `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` ו-`usage-supported`

המניפסט אינו כולל במכוון:

- סודות לקוח של OAuth וערכי סוד המשמשים כברירת מחדל
- פתרון של סביבת זמן הריצה
- כותרות בקשה וכלי עזר ציבוריים לפרטי התחברות
- בוני URL דינמיים
- פונקציות executor
- פרטים פנימיים של מאגרי session

## תגיות יכולת

`capabilities` הוא מערך ממוין של תגיות הנגזרות מרשומת המרשם. על מבצעי אינטגרציה
להתייחס אליו כתשובה הניתנת לקריאה על ידי מכונה לשאלה "מה הספק הזה יכול לעשות", במקום
לקרוא מחדש את מקורות ה-TypeScript.

| תגית                 | משמעות                                                          |
| -------------------- | --------------------------------------------------------------- |
| `apikey`             | מקבל מפתח API (`authType` הוא `apikey` או `optional`).          |
| `oauth`              | משתמש בתהליך OAuth או session.                                  |
| `responses`          | חושף כתובת URL בסיסית של OpenAI Responses-API.                  |
| `passthrough-models` | מספק מודלים ישירות מה-upstream במקום מקטלוג סטטי.               |
| `custom-executor`    | מריץ executor שאינו ברירת המחדל, ולכן נשאר בנתיב ה-TypeScript.  |
| `sidecar-candidate`  | משקף את `sidecar.eligible` — בטוח לשקול אותו לייבוא אל sidecar. |
| `usage-fetch`        | מחובר אליו קורא נתוני שימוש או מכסה (`getUsageForProvider`).    |
| `usage-supported`    | API השימוש מקבל ספק זה (`isSupportedUsageConnection`).          |

`usage-fetch` מיועד לגילוי בלבד. הוא מציין ש-OmniRoute יודע כיצד לקרוא את נתוני השימוש של
הספק; הוא אינו מפעיל אחזור, משנה את סמנטיקת המכסה או מרמז שווידג'ט המכסה
ב-Dashboard מופעל עבור הספק — ווידג'ט זה נשלט בנפרד על ידי
`USAGE_SUPPORTED_PROVIDERS`. מקור האמת הוא `USAGE_FETCHER_PROVIDERS` בקובץ
`open-sse/services/usage/fetcherProviders.ts`.

רשימה זו מסודרת לפי המחרוזות שה-dispatcher של נתוני השימוש מקבל, ולכן היא משלבת מזהים קנוניים
עם כינויים והיא ארוכה מעט יותר ממספר הספקים המתויגים: לרשומות שאינן
ספקי צ'אט במרשם המניפסט (לדוגמה, ספק החיפוש `firecrawl`
וספק ה-ACP בשם `amazon-q`) אין רשומת מניפסט שניתן לתייג.

`usage-supported` מציין אם נתיבי השימוש של השרת וה-Dashboard מקבלים חיבור
עבור הספק. הוא משקף את `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
ואת `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), ששניהם נשלטים על ידי
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). בשונה מ-
`usage-fetch`, הוא מופק לפי מזהה הספק בלבד — בדיקת זמן הריצה מבצעת
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` ללא פתרון כינויים, ולכן המניפסט
שומר על אותו כלל. לשתי התגיות יש תחומי תחולה שונים: 3 ספקים נושאים רק את
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) וספק אחד נושא רק את
`usage-supported` (`xiaomi-mimo-token-plan`), ולכן האחד אינו מרמז על האחר.

## שימוש ב-Sidecar

רכיבי Sidecar צריכים להתייחס ל-`sidecar.eligible` כאל אינדיקציה שמרנית למועמדות, ולא כהחלטת ניתוב בלתי מותנית. יעד הייבוא הראשון צריך להיות ספקים המשתמשים במפתח API ובנקודות קצה סטטיות באמצעות מריץ ברירת המחדל. ספקים עם מריצי Web מותאמים אישית, תהליכי OAuth/Session, בוני URL דינמיים או תצורת מאגר נשארים בנתיב הגיבוי של TypeScript עד ש-Sidecar יממש התנהגות שקולה ונתוני הטלמטריה יוכיחו שקילות.

שלבי הגירה מוצעים:

1. ליצור ולאמת את מניפסט תוספי הספקים מתוך מרשם ה-TS.
2. לאפשר ל-Bifrost או ל-CLIProxyAPI לייבא את המניפסט עבור ספקים המשתמשים במפתח API ובנקודות קצה סטטיות.
3. לנתב ספקים מתאימים דרך ה-Sidecar מאחורי `OMNIROUTE_RELAY_BACKEND`, תוך השארת נתיב הגיבוי של TS פעיל.
4. לקדם ספקים רק כאשר שיעור ההצלחה, השהיית p99, התנהגות ההזרמה והטיפול בפרמטרים שאינם נתמכים תואמים לנתיב ה-TS.
5. להוסיף תוספים מקוריים ל-Sidecar עבור מריצים מותאמים אישית, משפחת ספקים אחת בכל פעם.

## למה לא להטמיע ספקים ישירות ב-Next

ממשק הקצה של Next לא צריך להיות אחראי להפעלת ספקים. עליו לקרוא לגבול ה-API. לאחר מכן, צד השרת יכול להחליט אם להשתמש במריץ TypeScript, ב-Bifrost, ב-CLIProxyAPI או ב-Sidecar מקורי עתידי. כך חתימת בקשות, בדיקות רשימת ההיתרים, מדיניות מסד הנתונים והתנהגות הגיבוי נשארות מרוכזות לפני כל העברה ל-Sidecar.
