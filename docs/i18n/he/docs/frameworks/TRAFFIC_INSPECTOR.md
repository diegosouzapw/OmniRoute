Traffic Inspector הוא מנפה תעבורת HTTPS מובנה של OmniRoute — כלי דמוי Charles Proxy / mitmweb / HTTP Toolkit שהוא **מודע ל-LLM** ו**מודע לסוכנים**. הוא נמצא ב-`/dashboard/tools/traffic-inspector` ומקבל תעבורה בזמן אמת מעד 5 מקורות לכידה בו-זמנית.

**מיקום בלוח הבקרה:** `/dashboard/tools/traffic-inspector`
**קבוצה בסרגל הצד:** כלים (אחרי AgentBridge)
**ראו גם:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge הוא מצב לכידה 1.

### הארכיטקטורה בפסקה אחת

ה-`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) הוא מאגר טבעתי משותף בזיכרון (ברירת המחדל היא 1000 רשומות, וניתן להגדירו באמצעות `INSPECTOR_BUFFER_SIZE`). כל מקורות הלכידה כותבים אליו באמצעות `push()`. מחלקת המאגר מסווגת כל רשומה באמצעות `kindDetector.ts` (וקובעת אם זו בקשת LLM), מחשבת `contextKey` (טביעת אצבע מסוג SHA-256 של הנחיית המערכת), ומשדרת לכל מנויי ה-WebSocket באמצעות `globalTrafficBuffer.subscribe()`. לוח הבקרה מתחבר באמצעות `GET /api/tools/traffic-inspector/ws` ומקבל תמונת מצב בעת ההתחברות, ולאחריה אירועי `new`/`update`/`clear`.

## §2 מצבי לכידה

Traffic Inspector תומך ב-**5 מקורות לכידה בו-זמניים**. ניתן להפעיל ולכבות כל אחד מהם בנפרד. השדה `source` בכל `InterceptedRequest` (`src/mitm/inspector/types.ts`) הוא אחד מהערכים `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"` או `"tproxy"`.

### מצב 1 — AgentBridge (ברירת מחדל, פעיל תמיד)

**מקור:** המטפלים של AgentBridge (`src/mitm/handlers/base.ts`)
**מנגנון:** כל קריאה ל-`intercept()` בתוך `MitmHandlerBase` קוראת ל-`hookBufferStart()` לפני ההעברה ול-`hookBufferUpdate()` עם השלמתה. אין צורך בתצורה נוספת — פועל מיד עם הפעלת AgentBridge.
**טווח:** 9 סוכני ה-IDE המוגדרים ב-AgentBridge
**הערה:** השדה `source` בתוך `InterceptedRequest` = `"agent-bridge"`

### מצב 2 — מארחים מותאמים אישית (הפניית DNS)

**מקור:** רשימת מארחים המוגדרת בידי המשתמש (הטבלה `inspector_custom_hosts`)
**מנגנון:** הוספת מארח דרך ממשק המשתמש מוסיפה את `127.0.0.1 <host>` אל `/etc/hosts` (דורש sudo). שרת ה-MITM הקיים של AgentBridge (יציאה 443) מפיק באופן דינמי אישור SNI עבור המארח החדש.
**טווח:** כל יישום המשתמש במארח שנוסף — ללא צורך בשינוי תצורת היישום
**הערה:** `source` = `"custom-host"`

דוגמאות לתרחישי שימוש:

- ניטור `api.openai.com` מסקריפטים של Python
- ניפוי שגיאות ב-`my-internal-llm.company.com`
- לכידת תעבורה ממכשירים ניידים באותה רשת (באמצעות התחזות ARP — למתקדמים)

### מצב 3 — מאזין HTTP_PROXY (יציאה 8080)

**מקור:** יישומים המשתמשים במשתני הסביבה `HTTP_PROXY`/`HTTPS_PROXY`
**מנגנון:** מאזין משני ביציאה 8080 (`src/mitm/inspector/httpProxyServer.ts`), הפועל כשרת proxy מפורש ותקני עבור HTTP/HTTPS. מקבל מנהרות `CONNECT` ‏(HTTPS) ובקשות HTTP ישירות.
**טווח:** כל יישום המכבד את משתנה הסביבה `HTTP_PROXY` — ללא שינוי DNS וללא sudo
**הערה:** `source` = `"http-proxy"`

```bash
# לכידה מהירה עבור פקודה יחידה:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# לכידה מתמשכת בהפעלת מעטפת:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**מגבלת TLS:** מנהרות `CONNECT` של HTTPS נלכדות כמטא-נתונים בלבד (מארח, יציאה ותזמון) — גוף ה-TLS אינו מפוענח כברירת מחדל. הפעילו את המתג "פענוח HTTPS במצב proxy" (הצטרפות מפורשת, דורש מתן אמון באישור של AgentBridge) כדי לבדוק את הגוף במלואו.

**התנגשות יציאות:** אם יציאה 8080 נמצאת בשימוש, AgentBridge מחזיר 409 עם שגיאה מובנית. שנו את היציאה באמצעות משתנה הסביבה `INSPECTOR_HTTP_PROXY_PORT`.

### מצב 4 — proxy כלל-מערכתי (מתקדם, הצטרפות מפורשת)

**מקור:** הגדרות proxy ברמת מערכת ההפעלה (חלות על כל היישומים במחשב)
**מנגנון:** משתמש בממשקי API של מערכת ההפעלה כדי להפנות את כל תעבורת HTTP/HTTPS דרך המאזין של HTTP_PROXY:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **טווח:** כל יישום במחשב המכבד את הגדרות ה-proxy של המערכת
  **הערה:** `source` = `"system-proxy"`

**מנגנוני בטיחות:**

- טיימר להשבתה אוטומטית (ברירת המחדל היא 30 דקות, ניתן להגדרה באמצעות `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES`)
- המצב הקודם של ה-proxy המערכתי נשמר במסד הנתונים ומשוחזר בעת החזרה לאחור
- לוח הבקרה מציג בקשת אישור "מחזיר את ה-proxy המערכתי למצבו הקודם" אם המשתמש מנווט לדף אחר בזמן שהוא פעיל
- ממשק המשתמש מציג תג `⚠ מתקדם` + תיבת סימון לאישור מפורש

### מצב 5 — פענוח שקוף באמצעות TPROXY ‏(Linux, הרשאות root, הצטרפות מפורשת)

**מקור:** TPROXY בליבה + ניתוב מבוסס מדיניות (`src/mitm/tproxy/`)
**מנגנון:** מסמן חיבורי TCP יוצאים מקומיים חדשים ליציאת יעד (ברירת המחדל היא `443`) בתוך `mangle OUTPUT`; כלל `ip rule` מנתב מחדש את החבילות המסומנות למסירה מקומית; והיעד `TPROXY` של `mangle PREROUTING` מוסר אותן למאזין שקוף (**IP_TRANSPARENT**) (יציאת ברירת המחדל היא `8443`). המאזין מסיים את חיבור ה-TLS באמצעות אישור קצה שמונפק **לפי דרישה עבור כל שם מארח SNI** בידי CA דינמי, לוכד את חילופי המידע המפוענחים ומעביר את הבקשה, כשהיא מוצפנת מחדש, אל היעד המקורי.
**טווח:** מארחי יעד **שרירותיים** ביציאת היעד — ללא התחזות דרך `/etc/hosts`, ללא משתנה הסביבה `HTTP_PROXY` וללא שינוי כלל-מערכתי של ה-proxy. התהליך שיורט אינו דורש שינוי תצורה, אך עליו לתת אמון ב-CA הדינמי.
**הערה:** `source` = `"tproxy"`

**דרישות:** Linux בלבד (**IP_TRANSPARENT** זמין ב-Linux בלבד), יכולת **CAP_NET_ADMIN** ‏(root), ותוסף N-API מקורי שיש לבנות באמצעות שרשרת כלים של C (`npm run build:native:tproxy`). כאשר הוא אינו זמין, המתג בלוח הבקרה מושבת עם תיאור הכלי "פענוח TPROXY דורש Linux + ‏root + התוסף המקורי". כללי חומת האש מוחלים ומבוטלים באופן טרנזקציוני (קריסה לעולם אינה מותירה מאחור כלל `mangle`) ומתאפסים בעת אתחול מחדש. מנגנון מניעת לולאות המבוסס על SO_MARK מונע מההעברה המוצפנת מחדש של ה-proxy עצמו להילכד שוב.

זוהי תת-מערכת משמעותית בעלת מדריך תפעול ייעודי משלה — ראו `docs/security/MITM-TPROXY-DECRYPT.md` ‏(git; אינו מהודר לתוך `/docs`) לקבלת המתכון המלא לחומת האש, מתקין ה-CA הדינמי לפי SNI + מאגר האמון, הנתיב המקומי בלבד, פרטי מניעת הלולאות וסכמת התצורה. המתג נשלט באמצעות `GET / POST / DELETE /api/tools/agent-bridge/tproxy` (שימו לב: הנתיב נמצא תחת התחילית של AgentBridge, ולא תחת התחילית של Traffic Inspector).

### 3.2 רשימת בקשות (חלונית שמאלית)

- **וירטואלית** (`useVirtualList` + `ResizeObserver`): מטפלת ב-1000 פריטים ללא קפיאה
- **גלילה אוטומטית** עם מתג להשהיה בזמן בדיקה
- **קידוד סטטוס לפי צבע**: ירוק (2xx), צהוב (3xx), אדום (4xx/5xx), אפור (בתהליך)
- **אימוג'י סוכן**: 🔵 Antigravity, 🟢 Copilot, 🟠 Kiro, 🟣 Codex, 🔷 Cursor, 🟤 Zed, 🟡 Claude Code, ⚫ Open Code, 🌐 מארח מותאם אישית
- **פס צבע לפי הקשר**: גבול שמאלי ברוחב 1px הצבוע לפי `contextKey` ‏(SHA-256 של הנחיית המערכת) — מקבץ חזותית שיחות קשורות
- **גוף בטעינה עצלה**: רק גוף הבקשה שנבחרה מתממש בלשוניות הפרטים (מונע רינדור של 1000 × גופי נתונים בגודל 1MB)

## §4 תכונות מודעות ל-LLM

### 4.1 מזהה סוג (`src/mitm/inspector/kindDetector.ts`)

מסווג כל בקשה כ-`"llm"`, `"app"` או `"unknown"` באמצעות 4 אותות:

1. **מרשם מארחים** — כ-18 שמות מארחים מוכרים של ממשקי API ל-LLM‏ (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot וכו')
2. **תבניות נתיבים** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses` וכו'
3. **מבנה גוף הבקשה** — מזהה את השדות `messages[]`‏ (OpenAI/Claude),‏ `contents[]`‏ (Gemini),‏ `prompt`,‏ `input`
4. **רמזים מסוכן המשתמש** — `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor` במחרוזת UA

מארחים מותאמים אישית שנוספו דרך מצב 2 יורשים את ה-`kind` שלהם מקלט הטופס (ברירת המחדל היא `"custom"`).

### 4.2 ממזג SSE‏ (`src/mitm/inspector/sseMerger.ts`)

**מימוש עצמאי שנכתב מאפס.** ניתוח האירועים פועל לפי
[אלגוריתם האירועים הנשלחים מהשרת של WHATWG](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream),
ואילו השחזור פועל לפי סכמות ההזרמה הציבוריות של [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) ושל
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent).

משחזר את הודעת העוזר הסופית מאירועי דלתא גולמיים של SSE:

- **Anthropic**: צובר `content_block_delta` לפי אינדקס; מטפל ב-`text_delta`, ב-`input_json_delta` (קריאות לכלים) וב-`thinking_delta`
- **OpenAI**: צובר אפשרויות השלמה/קריאות לכלים של Chat Completions ופריטי פלט של Responses API
  לפי אינדקס
- **Gemini**: צובר `candidates[i].content.parts`
- **לא ידוע**: מחזיר את האירועים הגולמיים כפי שהם

לשונית התגובה מציגה מתג: **"אירועים גולמיים ↔ ממוזג"**.

### 4.3 מנרמל שיחות (`src/mitm/inspector/conversationNormalizer.ts`)

**מימוש עצמאי שנכתב מאפס.** הנרמול מוגדר באמצעות חוזים מקומיים של קופסה שחורה
ובאמצעות סכמות ההודעות הציבוריות של OpenAI,‏ Anthropic ו-Gemini; לא נעשה שימוש
בקוד מימוש ממקור חיצוני.

ממיר את פורמטי ההודעות של OpenAI,‏ Anthropic ו-Gemini ל-`NormalizedConversation` יחיד לפני הרינדור:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // הודעות / תכנים / הנחיה מגוף הבקשה
  response: NormalizedTurn[]; // תגובת העוזר (ממוזגת באמצעות sseMerger)
  contextKey: string | null; // טביעת אצבע SHA-256 של הנחיית המערכת
}
```

סוגי בלוקים: `text`, `tool_use`, `tool_result`. לשונית השיחה משתמשת במבנה הזה ללא תלות בספק.

### 4.4 צביעת מפתח הקשר (`src/mitm/inspector/contextKey.ts`)

- מחשב `SHA-256` של הנחיית המערכת (הודעת `role:system` הראשונה, או השדה `system`, או `systemInstruction` של Gemini)
- מחזיר תחילית הקסדצימלית בת 12 תווים (`"a3f9c2..."`)
- ממשק הקצה ממפה את המפתח לצבע HSL דטרמיניסטי עבור פס הגבול השמאלי
- **מסנן "אותו הקשר"**: לחיצה על התגית `ctx #a3f` מוסיפה מסנן שמציג רק בקשות בעלות אותה טביעת אצבע

כך קל להבחין חזותית בין "פרסונות" או משימות שונות שפועלות באותה הפעלת סוכן.

### 4.5 חילוץ מטא-נתונים של LLM

עבור בקשות LLM, לשונית פרטי ה-LLM מחלצת:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // מגוף הבקשה או מהתגובה
  messages: number; // מספר התורות
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // true אם זו תגובת SSE
  mappedTo: string | null; // כותרת x-omniroute-mapped
  costEstimateUsd: number | null; // עלות משוערת לפי התמחור של OmniRoute
}
```

### 4.6 מסנן חי לבקשות בתהליך

השדה `status` של הבקשה הוא `number | "in-flight" | "error"` — רשומה
נוספת כ-`"in-flight"` ברגע שהבקשה מתחילה ו**מתעדכנת במקום**
כאשר התגובה (או השגיאה) מגיעה. המתג **"חי"** בסרגל הכלים
(`liveOnly`, מפתח i18n‏ `trafficInspector.liveOnly`) מגביל את הרשימה לרשומות
שעבורן `status === "in-flight"`, וכך מאפשר לעקוב אחר חיבורים פתוחים בזמן אמת.

המסנן הוא פרדיקט טהור בצד הלקוח בתוך
`src/lib/inspector/matchesTrafficFilter.ts`:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

מצב המתג נשמר ב-`useTrafficFilters` (ה-hooks של לוח הבקרה של המפקח)
ומשתלב עם המסננים האחרים (פרופיל, מארח, סוכן, מקור, סטטוס, הקשר).

### 4.7 שיוך לתהליך (Linux)

ב-Linux, ניתן לשייך כל בקשה שיורטה ל**תהליך המקומי
שממנו היא הגיעה**. שני שדות אופציונליים מתווספים ל-`InterceptedRequest`:

```ts
pid?: number;          // מזהה התהליך שממנו הגיעה הבקשה (Linux בלבד)
processName?: string;  // שם התהליך שממנו הגיעה הבקשה (Linux בלבד)
```

`src/mitm/inspector/processAttribution.ts` ממפה את הפורט הארעי של _לקוח_
החיבור ל-PID ולשם באמצעות:

1. קריאת `/proc/net/tcp` ו-`/proc/net/tcp6` כדי למצוא את inode שקע הרשת עבור
   הפורט (`parseProcNetTcpForInode`, מנתח טהור שניתן לבדיקה באמצעות נתוני fixture).
2. סריקת `/proc/<pid>/fd/` לאיתור קישור סמלי אל `socket:[<inode>]`.
3. קריאת שם התהליך מתוך `/proc/<pid>/comm`.

מטמון TTL של שנייה אחת מגביל את עלות סריקת procfs תחת עומס. השיוך נעשה
**על בסיס המאמץ המרבי** — כל כשל מחזיר `null` ולעולם אינו חוסם את הלכידה. ב-
macOS/Windows הפונקציה מחזירה `null` (מימוש דמה; תמיכה ב-`lsof`/`GetExtendedTcpTable`
תתווסף בהמשך).

## §5 הפעלות

### 5.1 הקלטת הפעלה

1. לחצו על **"● הקלטת הפעלה"** בסרגל הכלים ← הזינו שם (אופציונלי)
2. המעקב החי ממשיך כרגיל; מחוון אדום מהבהב מציג `◉ הקלטה · <שם> · 00:42 · 23 בקשות`
3. לחצו על **"⏹ עצירה"** ← תמונת המצב של ההפעלה נשמרת ב-`inspector_sessions` + `inspector_session_requests`

### 5.2 הצגת הפעלה מוקלטת

- טוענת את תמונת המצב של ההפעלה (מצב קפוא)
- כרזה מציגה: `מוצגת ההפעלה המוקלטת "<שם>" — [חזרה לתצוגה חיה]`
- הלשונית סטטיסטיקה נעשית זמינה עם נתונים מצטברים של Recharts

| תבנית                     | שימוש                                                                       |

## §6 אבטחה

Traffic Inspector מציג **את כל תעבורת ה-HTTPS שיורטה**, כולל כותרות הרשאה וגופי בקשות. אמצעי הבקרה הבאים מיושמים:

| אמצעי בקרה                | פרטים                                                                                                                                                                 |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LOCAL_ONLY**            | כל הנתיבים ונקודת הקצה של WebSocket נגישים רק דרך ממשק הלולאה החוזרת (נאכף ב-`routeGuard.ts` לפני האימות)                                                             |
| **מיסוך סודות**           | הסורק הליניארי `maskSecret()` מצנזר פרטי הזדהות מסוג Bearer לפי RFC 6750, מפתחות עם תחיליות של ספקים ואסימונים אטומים ארוכים לפני `TrafficBuffer.push()`              |
| **הגבלת גודל הגוף**       | גופים שגודלם עולה על `INSPECTOR_MAX_BODY_KB` (ברירת המחדל היא 1024 KB) נחתכים עם ההודעה `"(נחתך משיקולי ביצועים)"`                                                    |
| **ניקוי כותרות**          | השמות מומרים לאותיות קטנות; כותרות מסגור/דילוג-אחר-דילוג וכותרות אימות של שרת מתווך מושמטות; קובצי Cookie מצונזרים במלואם; ערכי פרטי הזדהות מועברים אל `maskSecret()` |
| **CSP**                   | מדיניות אבטחת תוכן מחמירה בדפי Traffic Inspector למניעת XSS באמצעות גופי תגובה מוזרקים                                                                                |
| **ללא התמדה כברירת מחדל** | ה-`TrafficBuffer` נשמר בזיכרון ואובד בעת הפעלה מחדש של השרת. הפעלות נשמרות באופן מתמשך רק כאשר מקליטים אותן במפורש                                                    |

### כללים קשיחים שהוחלו

| כלל                               | יישום                                                                                             |
| --------------------------------- | ------------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | כל תגובות שגיאת ה-HTTP מנתיבי Traffic Inspector עוברות ניקוי                                      |
| **#15 + #17** `isLocalOnlyPath()` | הנתיב `/api/tools/traffic-inspector/` הוא LOCAL_ONLY + SPAWN_CAPABLE (פקודות שרת מתווך של המערכת) |

### מגבלות ידועות

- **מצב שרת מתווך כלל-מערכתי** משפיע על כל היישומים במחשב, כולל לקוחות VPN ו-SSO. השתמשו בו תמיד עם טיימר ההשבתה האוטומטית. אין להשתמש בו במחשבים משותפים.
- **HTTPS במנהרת CONNECT**: מצב 3 (HTTP_PROXY) לוכד רק מטא-נתונים של המנהרה עבור יעדי HTTPS, אלא אם יירוט TLS מופעל. הדבר נעשה במכוון — לכידה שקופה ללא מתן אמון באישור AgentBridge הייתה משבשת את אימות ה-TLS עבור יישומים אלה.
- **מחרוזות המקודדות ישירות ברכיבים מסוימים**: בחלק מרכיבי ממשק המשתמש (F7/F8) יש מספר קטן של מחרוזות המקודדות ישירות ועדיין אינן מכוסות באמצעות מפתחות i18n. הן מתועדות כמגבלה ידועה בדוח פערי ה-i18n; הן יועברו בסבב המשך. המחרוזות המושפעות הן תוויות עיצוביות בממשק המשתמש שאינן דורשות תרגום לצורך שימוש פונקציונלי.

## §7 פתרון בעיות

### ניתוק WebSocket

אם המעקב בזמן אמת מציג "מנותק":

1. ודאו שהשרת עדיין פועל: `GET /api/tools/traffic-inspector/capture-modes`
2. טענו מחדש את הדף — ה-WebSocket מתחבר מחדש ומקבל תמונת מצב עדכנית
3. אם השרת הופעל מחדש, המאגר בזיכרון נוקה — רשומות ישנות אינן זמינות, אלא אם הוקלט סשן

### התנגשות ביציאה 8080

אם מצב HTTP_PROXY אינו מצליח לפעול:

```bash
lsof -i :8080    # איתור התהליך
```

שנו את היציאה:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### ה-proxy של המערכת לא הוחזר למצבו הקודם

אם OmniRoute קורס בזמן שמצב ה-proxy הכלל-מערכתי פעיל:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

לוח הבקרה יציע גם "החזרת ה-proxy של המערכת למצבו הקודם" בטעינה הבאה, אם יזהה שמצב מסד הנתונים מציין שה-proxy היה פעיל.

### המאגר מלא

כאשר המאגר מגיע לגודל `INSPECTOR_BUFFER_SIZE` (ברירת המחדל היא 1000), רשומות חדשות דוחקות את הרשומות הישנות ביותר. אם בקשות חשובות הולכות לאיבוד:

- הגדילו את `INSPECTOR_BUFFER_SIZE` (לדוגמה, 5000) — צריכת הזיכרון גדלה בתמורה לשמירה ממושכת יותר
- הקליטו סשן כדי לשמור את חלון הזמן הרלוונטי במסד הנתונים

## §8 תיעוד ה-API

כל הנתיבים הם `LOCAL_ONLY` (גישה מ-loopback בלבד) ו-`SPAWN_CAPABLE` (פקודות proxy של המערכת). ראו `src/server/authz/routeGuard.ts`.

נתיב בסיס: `/api/tools/traffic-inspector/`

### ניהול בקשות

| שיטה   | נתיב                        | תיאור                                                                              |
| ------ | --------------------------- | ---------------------------------------------------------------------------------- |
| GET    | `/requests`                 | הצגת בקשות (ניתנות לסינון: `?profile=llm&host=&agent=&status=&source=&sessionId=`) |
| GET    | `/requests/{id}`            | פרטים של בקשה יחידה                                                                |
| DELETE | `/requests`                 | ניקוי המאגר שבזיכרון                                                               |
| POST   | `/requests/{id}/replay`     | ביצוע מחדש של אותה בקשה דרך הנתב של OmniRoute                                      |
| PUT    | `/requests/{id}/annotation` | שמירה או עדכון של הערה על בקשה                                                     |

### WebSocket

| שיטה | נתיב  | תיאור                                                                                         |
| ---- | ----- | --------------------------------------------------------------------------------------------- |
| GET  | `/ws` | זרם WebSocket בזמן אמת. שולח `snapshot` בעת ההתחברות, ולאחר מכן אירועי `new`/`update`/`clear` |

### ייצוא

| שיטה | נתיב          | תיאור                                     |

### מצבי לכידה

| שיטה | נתיב                           | תיאור                                                                                                     |
| ---- | ------------------------------ | --------------------------------------------------------------------------------------------------------- |
| GET  | `/capture-modes`               | מצב המצבים AgentBridge / מארחים מותאמים אישית / HTTP_PROXY / proxy של המערכת, יחד עם המתג `tls-intercept` |
| POST | `/capture-modes/http-proxy`    | הפעלה/עצירה של מאזין HTTP_PROXY (`{action: "start"\|"stop"}`)                                             |
| POST | `/capture-modes/system-proxy`  | החלה/ביטול של proxy כלל-מערכתי (`{action: "apply"\|"revert"}`)                                            |
| POST | `/capture-modes/tls-intercept` | הפעלה או השבתה של פענוח גוף HTTPS במצב proxy (`{enabled: boolean}`)                                       |

> **פענוח TPROXY** (מצב לכידה 5) מופעל באמצעות נתיב **נפרד** תחת
> התחילית של AgentBridge — `GET / POST / DELETE /api/tools/agent-bridge/tproxy` — ולא
> תחת `/api/tools/traffic-inspector/`. ראו
> `docs/security/MITM-TPROXY-DECRYPT.md` (ב-git; אינו מהודר לתוך `/docs`).
