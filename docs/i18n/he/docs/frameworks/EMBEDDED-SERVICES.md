באמצעות מפתחות API), שירותים מוטמעים פועלים באותו מחשב שבו פועל OmniRoute ומתקשרים דרך ממשק הלולאה החוזרת.

## 1. סקירה כללית

### למה שירותים מוטמעים?

שישה שירותים מוטמעים:

| שירות           | חבילת npm                             | פורט ברירת מחדל | מטרה                                                                                                                                                                         |
| --------------- | ------------------------------------- | :-------------: | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **9Router**     | `9router`                             |      20130      | נתב AI שבו OmniRoute יכול להשתמש כספק משנה. המודלים נחשפים בתבנית `9router/{sub}/{model}`                                                                                    |
| **CLIProxyAPI** | קובץ בינארי מגרסת GitHub (`cliproxy`) |      8317       | מתאם פרוקסי מקומי לתהליכי אימות של Anthropic CLI. מספק ניתוב חלופי כאשר פג תוקפם של אסימוני OAuth                                                                            |
| **Mux**         | `mux` (`mux server` ללא ממשק גרפי)    |      8322       | דמון מקומי לתזמור סוכנים (coder/mux). מנוהל רק מבחינת מחזור החיים — אינו יעד לניתוב (ללא תיווך LLM).                                                                         |
| **Bifrost**     | `@maximhq/bifrost`                    |      8080       | מנוע אחורי לממסר שער AI שנכתב ב-Go. בזמן שהוא פועל, הוא נבחר אוטומטית על ידי נתיב הממסר (`/v1/relay/`)                                                                       |
| **Dario**       | `@askalf/dario`                       |      3456       | פרוקסי למינוי Claude — חלופה/גיבוי ל-CLIProxyAPI עבור תעבורה במבנה Claude Code; המפתח המוזרק הופך ל-`DARIO_ADMIN_TOKEN` ומגביל את הגישה למישור הבקרה של OAuth תחת `/admin/*` |
| **open-wa**     | `@open-wa/wa-automate`                |      8323       | אוטומציה של WhatsApp Web (Chromium ללא ממשק גרפי באמצעות Puppeteer). מנוהל רק מבחינת מחזור החיים — אינו יעד לניתוב.                                                          |

כל ששת השירותים פועלים לפי אותו מודל פיקוח:

- OmniRoute מתקין אותם תחת `DATA_DIR/services/{name}/` (בנפרד מקובץ ה-`package.json` של OmniRoute)
- OmniRoute מפעיל ומנטר אותם כתהליכי צאצא
- OmniRoute מזריק מפתח API זמני לסביבת תהליך הצאצא ומחליף אותו ללא זמן השבתה (כאשר הדבר רלוונטי)
- כל נתיבי הניהול (`/api/services/*`) הם **LOCAL_ONLY** — נגישים רק מ-loopback (כלל קשיח מס' 17)

### החלטות מרכזיות (מתוכנית התכנון)

| החלטה                                     | ערך                                                                   |

| מנגנון התקנה                              | `npm install {package}` באמצעות `execFile` (ללא אינטרפולציה של מעטפת) |
| מצב צריכה                                 | הספק נרשם בתבנית `9router/{sub}/{model}` במנוע הניתוב                 |
| ניהול מפתחות API                          | OmniRoute יוצר, מצפין במנוחה (AES-256-GCM) ומזריק באמצעות משתני סביבה |
| מיקום בלוח המחוונים                       | `/dashboard/providers/services` (שלוש לשוניות)                        |
| הפעלה אוטומטית                            | מתג עבור כל שירות, כבוי כברירת מחדל                                   |

## 3. מכונת מצבי מחזור חיים

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
                 בדיקת תקינות עברה │         קריסה / SIGTERM    │
                               ┌────▼─────┐  (יציאה תוך 5 שנ׳)  │
                               │ running  │──── קריסה ──────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

המצבים נשמרים בטבלת מסד הנתונים `version_manager` (בעמודה `status`) ומשוקפים
במצב שבזיכרון של `ServiceSupervisor`. המצב שבזיכרון הוא הסמכותי עבור
תהליך פעיל; מצב מסד הנתונים הוא הגיבוי המתמיד בעת האתחול.

### מעברי מצבים

| ממצב            | אירוע                          | למצב                   |
| --------------- | ------------------------------ | ---------------------- |
| `not_installed` | `install()` מצליחה             | `stopped`              |
| `stopped`       | מתבצעת קריאה ל-`start()`       | `starting`             |
| `starting`      | בדיקת התקינות מחזירה 200       | `running`              |
| `starting`      | התהליך מסתיים לפני שהפך לתקין  | `error`                |
| `running`       | מתבצעת קריאה ל-`stop()`        | `stopping` → `stopped` |
| `running`       | התהליך מסתיים במפתיע (< 5 שנ׳) | `error` (קריסה מהירה)  |
| `running`       | התהליך מסתיים במפתיע (> 5 שנ׳) | `error`                |
| `error`         | מתבצעת קריאה ל-`start()`       | `starting`             |
| כל מצב          | `stop()` בזמן `stopping`       | ללא פעולה              |

### נעילת פעולות

`ServiceSupervisor` מסדר פעולות מחזור חיים באופן טורי באמצעות נעילת פעולה אסינכרונית
(`withLock()`). קריאות מקבילות ל-`start()` באותו מפקח גורמות להפעלה של תהליך אחד
בדיוק; הקורא השני ממתין ומחזיר את המצב הקיים. הדבר מונע
מצבי מרוץ כאשר, לדוגמה, הפעלה אוטומטית וכפתור בממשק המשתמש מופעלים בו-זמנית.

## 4. מדריך API

כל הנתיבים תחת `/api/services/` הם **LOCAL_ONLY** (גישה דרך loopback בלבד, כלל קשיח מס' 17).
בקשות שאינן מ-loopback מקבלות `403 LOCAL_ONLY` ללא תלות באסימון האימות.

### 4.1 נקודות קצה של 9Router (11 נתיבים)

#### `POST /api/services/9router/install`

התקנת 9Router מ-npm. הפעולה יוצרת את `DATA_DIR/services/9router/` עם
`package.json` ו-`node_modules/` משלו. אין התנגשות עם יחסי התלות של OmniRoute עצמו.

**גוף הבקשה** (כל השדות אופציונליים):

```json
{ "version": "latest" }
```

| שדה       | סוג      | ברירת מחדל | תיאור                        |
| --------- | -------- | ---------- | ---------------------------- |
| `version` | `string` | `"latest"` | תג גרסת npm או semver להתקנה |

**תגובות:**

| סטטוס | תיאור                                                  |
| ----- | ------------------------------------------------------ |
| `200` | `{ ok: true, installedVersion: "x.y.z", path: "..." }` |
| `400` | גוף בקשה לא תקין (כשל אימות של Zod)                    |
| `409` | התקנה כבר מתבצעת (הנעילה מוחזקת)                       |
| `500` | התקנת npm נכשלה — לפרטי שגיאה ידידותיים ראו `message`  |

**הערות:** נעשה שימוש ב-`execFile('npm', [...])` — ללא מעטפת וללא אינטרפולציה (כלל קשיח מס' 13).
שגיאות EACCES מוצגות כהודעות ידידותיות.

---

#### `POST /api/services/9router/start`

הפעלת 9Router. הפעולה רושמת supervisor אם עדיין לא נרשם, ולאחר מכן קוראת
ל-`supervisor.start()`. הפעולה אידמפוטנטית כאשר השירות כבר פועל.

**גוף הבקשה:** אין

**תגובות:**

| סטטוס | תיאור                                          |
| ----- | ---------------------------------------------- |
| `200` | אובייקט `ServiceStatus` (ראו סכמה להלן)        |
| `409` | 9Router אינו מותקן (`status: "not_installed"`) |
| `503` | ההפעלה נכשלה (שגיאת תהליך — ראו `lastError`)   |

**סכמת ServiceStatus:**

```json
{
  "tool": "9router",
  "state": "running",
  "pid": 12345,
  "port": 20130,
  "health": "healthy",
  "startedAt": "2026-05-25T10:00:00.000Z",
  "lastError": null
}
```

#### `POST /api/services/9router/stop`

עצירה מבוקרת של 9Router. שליחת SIGTERM, המתנה של 15 שניות, ולאחר מכן SIGKILL אם התהליך עדיין פעיל.
הפעולה אידמפוטנטית כאשר השירות כבר נעצר.

**גוף הבקשה:** אין

**תגובות:**

| סטטוס | תיאור                              |
| ----- | ---------------------------------- |
| `200` | `ServiceStatus` (מצב: `"stopped"`) |
| `503` | העצירה נכשלה באופן בלתי צפוי       |

---

#### `POST /api/services/9router/restart`

שקול להפעלת `stop()` ולאחר מכן `start()` תחת נעילת הפעולה.

**גוף הבקשה:** אין

**תגובות:** זהות לאלו של `start` (מוחזר `ServiceStatus` סופי).

#### `POST /api/services/9router/update`

עדכון 9Router לגרסת npm חדשה יותר. אם השירות פועל, הוא נעצר
תחילה, מתבצעת התקנת npm (הגרסה החדשה יותר מותקנת במקום), ולאחר מכן
השירות מופעל מחדש.

**גוף הבקשה** (כל השדות אופציונליים):

```json
{ "version": "latest" }
```

**תגובות:**

| סטטוס | תיאור                                                           |
| ----- | --------------------------------------------------------------- |
| `200` | `{ ok: true, previousVersion: "...", installedVersion: "..." }` |
| `400` | גוף לא תקין                                                     |
| `500` | עדכון npm נכשל                                                  |

#### `POST /api/services/9router/rotate-key`

יצירת מפתח API חדש עבור 9Router, הצפנתו במנוחה והפעלה מחדש של השירות
(אם הוא פועל), כדי שיטען את המפתח החדש מהסביבה שלו. המפתח הישן
מבוטל באופן מיידי.

**גוף הבקשה:** אין

**תגובות:**

| סטטוס | תיאור                                      |
| ----- | ------------------------------------------ |

**אבטחה:** המפתח החדש לעולם אינו מוחזר בתגובה (אין דליפת פרטי גישה).
הוא נשמר כשהוא מוצפן (AES-256-GCM) בטבלה `version_manager`.

### 4.7 פרוקסי הפוך (הטמעה בלוח הבקרה של 9Router)

לוח הבקרה מטמיע את ממשק המשתמש האינטרנטי של 9Router בתוך iframe באמצעות פרוקסי
הפוך פנימי בכתובת:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

פרוקסי זה:

- מעביר את הבקשה אל `http://127.0.0.1:{port}/{path}` (ממשק לולאה חוזרת בלבד)
- מסיר את הכותרות הנכנסות `cookie` ו-`authorization` (ללא דליפה של הפעלת OmniRoute)
- מזריק `Authorization: Bearer {apiKey}` לצורך אימות מול 9Router
- מסיר מהתגובה את `set-cookie`,‏ `content-security-policy`,‏ `x-frame-options`,‏ `cross-origin-*`
- משכתב תגובות HTML כדי להזריק `<base href>` ולנרמל נתיבים מוחלטים (`/foo` → `/dashboard/.../embed/foo`)

שדרוגי WebSocket עבור לוח הבקרה המוטמע מטופלים בידי שרת נלווה ביציאה
ייעודית (ראו `src/lib/services/embedWsProxy.ts`).

**אבטחה:** נתיבי פרוקסי ההטמעה מסווגים תחת `LOCAL_ONLY_API_PREFIXES`
וניתן לגשת אליהם רק מממשק הלולאה החוזרת. תוקף שמשיג JWT דרך
מנהרת Cloudflare/Ngrok אינו יכול להשתמש בפרוקסי כדי לגשת לשירותים מוטמעים.

## 5. אבטחה

### אכיפת LOCAL_ONLY (כלל קשיח מס' 17)

כל הנתיבים תחת `/api/services/` ו-`/dashboard/providers/services/*/embed/`
מסווגים כ-LOCAL_ONLY בקובץ `src/server/authz/routeGuard.ts`. בדיקת כתובת ה-loopback
מתבצעת ללא תנאי לפני כל ענף אימות:

```
הבקשה מגיעה
  → isLocalOnlyPath(path)?
      → לא loopback → 403 LOCAL_ONLY (תמיד, לפני בדיקת האימות)
      → loopback    → המשך לאימות הרגיל
```

כך נמנע מ-JWT שדלף (למשל, דרך מנהרה) להפעיל `npm install` או
יצירת תהליכים. ראו `docs/security/ROUTE_GUARD_TIERS.md` למטריצת הרמות
המלאה.

### הזרקת מפתח API

9Router ו-Mux דורשים מפתח API/אסימון bearer עבור נקודות הקצה שלהם ב-HTTP.
OmniRoute:

1. יוצר מפתח באמצעות `crypto.randomBytes(32).toString("base64url")` עם
   קידומת ייעודית לשירות (`nr_` עבור 9Router,‏ `mx_` עבור Mux).
2. מצפין אותו במנוחה באמצעות AES-256-GCM (אותו צופן המשמש לפרטי הגישה של הספקים).
3. מפענח ומזריק אותו כמשתנה סביבה בזמן יצירת התהליך —
   `NINEROUTER_API_KEY` עבור 9Router,‏ `MUX_SERVER_AUTH_TOKEN` עבור Mux (לעולם לא כדגל CLI,
   כך שהאסימון לעולם אינו מופיע ב-`ps`/רשימות תהליכים).
4. לעולם אינו מחזיר את המפתח הגלוי בתגובת HTTP כלשהי.

CLIProxyAPI מקבל מפתח ייעודי למישור הנתונים שמוזרק בזמן יצירת התהליך
(`needsApiKey: true` — משמש לסנכרון מודלים מול המתאם).

### הגנה מפני SSRF

פרוקסי ה-HTTP ההפוך (`/dashboard/.../embed/[...path]`) מוגדר באופן קשיח להעביר
בקשות רק אל `http://127.0.0.1:{port}`. הוא לעולם אינו עוקב אחר הפניות מחדש ליעדים
שאינם loopback. הספרייה `ssrf-req-filter` משמשת לדחיית כל כתובת URL במעלה הזרם
שנפתרת לכתובת מחוץ לטווח ה-loopback.

### בטיחות המעטפת (כלל קשיח מס' 13)

`npm install` מופעל באמצעות `execFile('npm', ['install', pkg, '--prefix', dir])` —
ללא template literals, ללא מעטפת וללא אינטרפולציה של נתיבים חיצוניים לתוך מחרוזת
הפקודה. ערכי זמן ריצה (יציאות, מפתחות API) מועברים דרך האובייקט `env` של תהליך הבן.

### טיהור שגיאות (כלל קשיח מס' 12)

כל תגובות השגיאה מ-`/api/services/*` עוברות דרך `buildErrorBody()` או
`sanitizeErrorMessage()`. הערכים הגולמיים של `err.stack` ו-`err.message` לעולם אינם מוחזרים
כלשונם למבקש.

### שלב 1 — יצירת תוכנית ההתקנה

צרו את `src/lib/services/installers/{name}.ts` לפי המבנה של `ninerouter.ts`:

### שלב 2 — רישום באתחול

הוסיפו `ServiceEntry` למערך `SERVICES` בקובץ `src/lib/services/bootstrap.ts`:

```typescript

```

הרחיבו את `buildSpawnArgsFactory()` כדי לטפל ב-`cfg.tool === "myservice"`.

#### חוזה תוסף-ספק הניתן להרחבה (שלב 1, #7333)

`src/lib/services/providerPlugins/` מציג חוזה `ServiceProviderPlugin` שאורז
את שדות ה-`ServiceEntry` של `bootstrap.ts` בצד השרת ואת שדות תבנית המניפסט של
`serviceBackends.ts` באובייקט אחד, במקום שהמבנה של אותו שרת יתואר
בנפרד בשני קבצים שאינם קשורים. נכון למועד כתיבת שורות אלה, **רק `9router`
הועבר** — `bootstrap.ts` גוזר את הרשומה שלו ב-`SERVICES[]` מתוך
`getServiceProviderPlugin("9router")` (`src/lib/services/providerPlugins/registry.ts`),
ומשליך שגיאת הפעלה אם התוסף אי פעם חסר. `cliproxy`,‏ `mux` ו-`bifrost`
נשארים ללא שינוי עם ה-literals הקיימים שלהם בתוך `SERVICES[]`.

אל `open-sse/config/providerPluginManifest.ts` נוסף גם helper מצטבר בשם
`createServiceBackendManifestEntry(pluginId, template)`, שיוצר
`ProviderPluginManifestEntry` תקין מרשומת `SERVICE_BACKEND_MANIFEST_TEMPLATE` — הוא
**עדיין אינו מחובר** לשום נתיב בקשות פעיל (לא ל-`generateProviderPluginManifestFromRegistry()`
ולא ל-`/v1/providers/[provider]/models`); הדבר נותר להמשך לאחר שהחוזה
יוכח עבור שרת שני.

הפריטים הבאים נדחו לבקשות משיכה עתידיות ונמצאים במעקב תחת issue #7333: העברת `cliproxyapi`
דרך אותו registry, הכללת `mux`/`bifrost` ב-union‏ `ServiceBackendPluginId`,
שילוב הטיפול המיוחד בניתוב המבצעים (`open-sse/executors/index.ts`,
`open-sse/handlers/chatCore/executorProxy.ts`) בתוך חוזה התוסף, וחיבור
`createServiceBackendManifestEntry()` לנתיב קוד פעיל של מניפסט/מודלים.

### שלב 3 — הוספת מיגרציה ונתוני אתחול למסד הנתונים

## 7. פתרון בעיות

### השירות אינו מופעל

**תסמינים:** כפתור ההפעלה מחזיר 503, והמצב נשאר `"error"` או `"starting"`.

**רשימת בדיקה:**

1. בדקו את `GET /api/services/{name}/logs` (או את חלונית היומנים בלוח הבקרה). חפשו
   שורות כגון `Error: ENOENT`, `address already in use` או `Cannot find module`.
2. ודאו ש-`npm` נמצא ב-PATH: הריצו `which npm` מאותו חשבון משתמש שמפעיל את OmniRoute.
3. ודאו שהשירות מותקן: בדקו את `GET /api/services/{name}/status` וחפשו את
   `installedVersion`. אם הערך הוא `null`, הפעילו תחילה את ההתקנה.
4. בדקו ש-`DATA_DIR/services/{name}/node_modules/` קיים ואינו ריק.
5. בדקו את השדה `lastError` בתגובת הסטטוס כדי לראות את סיבת היציאה המסוננת.

---

### הפעלה קרה איטית (יותר מ-10 שניות עד להגעה למצב `running`)

**תסמינים:** המצב נשאר `"starting"` למשך זמן רב לפני שהוא משתנה ל-`"running"` או ל-`"error"`.

**הסבר:** ההפעלה הקרה של 9Router כוללת ייבוא של עצי תלויות גדולים (מודולי DNS,
מנהור ו-MITM). מרווח ברירת המחדל לבדיקת תקינות הוא 2 שניות, עם 3 ניסיונות לפני
שהמפקח מכריז על פסק זמן (אך ממשיך לבצע בדיקות).

**פתרון:** ניתן להגדיר את `healthIntervalMs` ואת פסק הזמן של `waitForHealthy`
(`healthIntervalMs * 3`) בקובץ `bootstrap.ts`. עבור שירותים שמשך ההפעלה שלהם ארוך יותר,
הגדילו את `healthIntervalMs` ל-5000 ואת `stopTimeoutMs` ל-30 000.

---

### התנגשות ביציאה (`EADDRINUSE`)

**תסמינים:** ביומנים מופיע `address already in use :::20130`.

**גורמים:**

- תהליך אחר כבר משתמש ביציאה 20130.
- תהליך קודם של 9Router לא נעצר לחלוטין (PID זומבי).

**פתרון:**

1. שנו את יציאת ברירת המחדל באמצעות משתנה הסביבה `NINEROUTER_PORT` בקובץ `.env`.
2. מצאו וסיימו את התהליך המתנגש: `lsof -ti :20130 | xargs kill -9`.
3. ניתן להגדיר את היציאה לכל שירות בנפרד בקובץ `bootstrap.ts` באמצעות השדה `port`.

**הערה:** כברירת מחדל, 9Router משתמש ביציאה 20130 במיוחד כדי להימנע מהתנגשות עם
יציאת ברירת המחדל 20128 של OmniRoute.

---

### ההרשאה נדחתה (EACCES) במהלך ההתקנה

**תסמינים:** ההתקנה מחזירה 500, וביומנים מופיע `EACCES` או `permission denied`.

**גורמים:**

- `DATA_DIR` או ספריית האב שלו אינם ניתנים לכתיבה על ידי התהליך של OmniRoute.
- הפעלה בתוך Docker ללא הרשאות root וללא גישת כתיבה לאמצעי האחסון הממופה.

**פתרון:**

1. בדקו את `DATA_DIR` (ברירת מחדל: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. ודאו שמשתמש התהליך של OmniRoute הוא הבעלים של הספרייה: `chown -R $USER ~/.omniroute/`
3. ב-Docker, ודאו שלעיגון אמצעי האחסון יש הרשאות מתאימות עבור המשתמש במכולה.

---

### העדכון נכשל (פסק זמן של `npm install` או שגיאת רשת)

**תסמינים:** העדכון מחזיר 500 עם `InstallError`, וביומנים מופיע פסק זמן של הרשת.

**רשימת בדיקה:**

1. ודאו שהגישה למאגר npm זמינה: `npm ping`.
2. בדקו אם קיים שרת proxy ארגוני: `npm config get proxy`, `npm config get https-proxy`.
3. נסו לבצע את ההתקנה ידנית: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`.
4. אם המערכת מבודדת מהרשת, הורידו מראש את קובץ ה-tarball והשתמשו ב-`npm install /path/to/tarball.tgz`.

---

### השירות מציג מצב `"error"` מיד לאחר ההפעלה (קריסה מהירה)

**תסמינים:** המצב משתנה מ-`"starting"` ל-`"error"` בתוך פחות מ-5 שניות.
ב-`lastError` מופיע `"Fast crash (exited with code 1)"`.

**רשימת בדיקה:**

1. קראו את זנב היומן המלא: `GET /api/services/{name}/logs?tail=500`.
2. גורם נפוץ: חסרים משתני סביבה שהשירות מצפה להם.
3. עבור 9Router: ודאו ש-`NINEROUTER_DISABLE_MITM=true` ו-
   `NINEROUTER_DISABLE_TUNNEL=true` נמצאים בסביבה שמועברת בעת יצירת התהליך (ראו
   `resolveSpawnArgs` ב-`installers/ninerouter.ts`).

## 8. שאלות נפוצות

**ש: האם ניתן לחשוף את נקודות הקצה של השירותים המוטמעים ללקוחות שאינם loopback?**

לא. רמת LOCAL_ONLY היא מכוונת (כלל קשיח מס' 17). נתיבים שיכולים להפעיל
`npm install` או ליצור תהליכי `node` חייבים שלא להיות נגישים מתעבורה שאינה
loopback, משום ש-JWT שדלף דרך מנהרה (Cloudflare, Ngrok, Tailscale) היה מאפשר
אחרת יצירה שרירותית של תהליכים. אין אפשרות החרגה עבור
`/api/services/` — בניגוד ל-`/api/mcp/`, הוא אינו נכלל ברשימת המעקפים של
תחום הניהול. ראו `docs/security/ROUTE_GUARD_TIERS.md`.

---

**ש: האם 9Router ו-CLIProxyAPI יהיו זמינים בפריסות ייצור/ענן?**

כן. שני השירותים פועלים לפי אותו מודל מקומי-תחילה כמו OmniRoute עצמו. הם פועלים
באותו מחשב ומתקשרים דרך loopback. "ייצור" כאן פירושו ה-VPS
או השרת המקומי שבו OmniRoute פרוס, ולא ספק ענן מרוחק.

---

**ש: כיצד ניתן לנפות שגיאות במפקח?**

1. עקבו אחר זרם יומני ה-SSE: `curl -N http://localhost:20128/api/services/9router/logs`.
2. בדקו את היומנים המובנים בפלט pino של OmniRoute, המסוננים לפי
   מרחב השמות `service:supervisor`.
3. בדקו את השורה במסד הנתונים: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`.
4. השתמשו ב-`GET /api/services/9router/status` כדי לראות בקריאה אחת את המצב הנוכחי בזמן אמת, ה-PID, התקינות
   ו-`lastError`.

---

**ש: המפקח מציג `health: "degraded"` או `health: "unknown"`, אך המצב הוא `"running"`. האם זו בעיה?**

`"degraded"` פירושו שבדיקת התקינות החזירה תגובה שאינה 200. `"unknown"` פירושו שעדיין לא
הושלמה בדיקה (התנגשות תזמון עם התשאול הראשון). שני המצבים זמניים במהלך ההפעלה.
אם התקינות נשארת במצב `"degraded"` במשך יותר מ-`healthIntervalMs * 3` מילישניות לאחר
`"running"`, השירות המוטמע פועל, אך API ה-HTTP שלו אינו מגיב. בדקו
אם הפורט בתגובת המצב נכון ואם השירות אכן
מאזין בפורט זה.

---

**ש: האם ניתן לשנות את מפתח ה-API של 9Router ללא הפעלה מחדש מלאה?**

לא. מפתח ה-API מועבר ל-9Router באמצעות משתנה סביבה בעת יצירת התהליך.
לא ניתן לשנות משתני סביבה בתהליך פעיל. `POST .../rotate-key`
עוצר ומפעיל מחדש את השירות באופן אוטומטי כדי להחיל את המפתח החדש. סבב המפתח
נכנס לתוקף בתוך `stopTimeoutMs` של השירות (ברירת המחדל היא 15 שניות), בתוספת זמן
ההפעלה שלו.

---

**ש: מהי מגבלת המאגר המעגלי ומה קורה כשהוא מתמלא?**

לכל שירות יש מאגר מעגלי ייעודי בגודל 5 MB. כאשר המאגר מלא, שורות
היומן הישנות ביותר מוסרות כדי לפנות מקום לחדשות. אירוע ה-SSE מסוג `snapshot` מחזיר
את השורות העדכניות ביותר במסגרת מגבלת `tail`. היומנים אינם נשמרים בדיסק אלא אם
`logsBufferPath` מוגדר בשורת מסד הנתונים.
