Radar הוא **תוסף אופציונלי** שמוסיף שכבת קטלוג חתומה ועדכנית של מודלים חינמיים
מעל לקו הבסיס של הגרסה (`FREE_MODEL_BUDGETS` בתוך
`open-sse/config/freeModelCatalog.data.ts`). הוא קיים משום שנוף המסלול החינמי משתנה
מהר יותר מקצב ההפצות — ספקים מוסיפים, מצמצמים או מפסיקים מכסות חינמיות בין
גרסאות, וניתן לרענן את קטלוג הבסיס רק כאשר מופצת גרסה חדשה.

**שום דבר שחינמי היום אינו מפסיק להיות חינמי בגלל ההזנה המרוחקת.** Radar לעולם אינו
מציב רשומת בסיס מאחורי חומת תשלום; הוא רק מרענן שדות מגבלות/סטטוס בזמן הקריאה ויכול
להוסיף בשכבות מודלים חינמיים שהתגלו לאחרונה בין גרסאות. מפעיל עדיין יכול להסתיר
מודל באופן מקומי, ויכול לשחזר אותו מאותו לוח בקרה. קטלוג הבסיס עצמו לעולם
אינו משתנה בדיסק — ראו
[כללי מיזוג שכבת-העל בזמן קריאה](#read-time-overlay-merge-rules) להלן.

## קורא ההכרזות הציבוריות

קורא ההכרזות הכללי נפרד מדגל התכונה של Radar. דף הבית של לוח הבקרה ומציג יומן השינויים מאחזרים את `news.json` הציבורי של המאגר באמצעות בקשת `GET` רגילה אל
`NEWS_JSON_URL` (`src/shared/utils/releaseNotes.ts`). הם אינם שולחים הגדרת Radar, הנחיה, תצורת ספק,
רשומת שימוש או מצב דחייה מקומי.

`news.json` משתמש בסכמת v2 הסגורה הממומשת על ידי `parseNewsPayload()`:

- `schemaVersion: 2` ואוסף `items[]` מוגבל;
- ערכי `id` יציבים וייחודיים של הכרזות;
- שדות `active` ו-`publishedAt` בפורמט ISO המוגדרים במפורש;
- טקסט באנגלית שהוא חובה, עם טקסט מקומי אופציונלי;
- קישורי HTTPS אופציונליים שאינם דורשים פרטי גישה וסמל מרשימת היתרים;
- בחירת הפריט הפעיל החדש ביותר תחילה, חזרה לאנגלית כאשר השפה אינה זמינה, ודחייה מקומית לפי מזהה.

המנתח מקבל באופן זמני את המבנה היחידני הקודם `{ active, title, message, ... }`, כדי
שפיצולים ישנים יותר יוכלו לעבור בלי שתצוגת יומן השינויים תישבר. הזנות לא תקינות אינן פעילות. רשומת ההשקה של Radar
מסופקת עם `active: false`; שינוי הערך ל-`true` הוא פעולת הפצה נפרדת לאחר המיזוג ולאחר הפריסה,
ואינו משנה את `RADAR_ENABLED` או את ההסכמה הנפרדת לסנכרון ההזנה.

## דגל: `RADAR_ENABLED` (כבוי כברירת מחדל)

Radar מוגן מקצה לקצה באמצעות דגל התכונה `RADAR_ENABLED`
(`src/shared/constants/featureFlagDefinitions.ts`, קטגוריה `policies`,
`defaultValue: "false"`).

**כאשר הדגל כבוי, הממשק אינו קיים:**

- כל נקודות הקצה `/api/radar/*`, כולל קריאות וכתיבות מקומיות של מצב המודל,
  מחזירות `404` לפני גישה למודול Radar כלשהו.
- מסכי לוח הבקרה (`/dashboard/radar`, `/dashboard/radar/setup`,
  `/dashboard/radar/combos`, `/dashboard/radar/offers`, `/dashboard/radar/intel`) מרנדרים
  `notFound()`.
- `getRadarCatalog()` (`src/lib/radar/index.ts`) מחזירה את קו הבסיס ללא שינוי —
  אותו מספר רשומות, אותם ערכים, כל רשומה מסומנת ב-`origin: "baseline"` — ולעולם אינה
  קוראת את מטמון ההזנה.
- לעולם לא מתבצעת קריאת רשת של Radar; כל מודול סנכרון מחזיר `{ status: "disabled" }`
  לפני גישה ל-`fetch`.

זהו שער מחמיר הכולל את כל התנאים: הפעלת הדגל פותחת את _המסכים_ בלבד,
ולא מעבר לכך. היא אינה מעלה נתונים, אינה מתחילה סנכרון ברקע ואינה משנה
ניתוב או בחירת מודל — ראו את ההסכמה הנפרדת להלן.

## סנכרון נתונים הוא הסכמה נפרדת — הבטחת הפרטיות

הפעלת `RADAR_ENABLED` רק פותחת את ממשק המשתמש. סנכרון ההזנה דורש הסכמה שנייה,
עצמאית, המאוחסנת ב-`radar_settings.opt_in` (`src/lib/db/radar.ts`,
המיגרציה `136_radar_cache_settings.sql`). הפונקציה `syncRadar()` בודקת את הדגל _וגם_ את
ההסכמה לפני ביצוע קריאת רשת כלשהי:

```
הדגל כבוי       → { status: "disabled" }   — אין קריאת רשת
אין הסכמה       → { status: "opt_out" }    — אין קריאת רשת
```

כאשר שניהם מופעלים, נתיב הסנכרון הוא:

1. `GET <feed base URL>/v1/catalog/latest` עם `x-omniroute-radar-schema: 2` וכותרת
   `Authorization: Bearer <supporter key>` אופציונלית (ראו להלן). בהיעדר כותרת הסכמה, השרתים משתמשים כברירת מחדל
   בתוצר המעבר החתום בנפרד של v1, כדי שלקוחות מותקנים ישנים יותר ימשיכו
   לקבל עדכונים.
2. זהו תהליך יישום להורדה בלבד, אך עדיין מדובר בבקשת HTTPS. התשתית
   המתארחת מקבלת מטא-נתוני חיבור רגילים, כגון כתובת ה-IP של המקור. כאשר מוגדר מפתח תומך,
   הסנכרון שולח גם את המפתח הזה בכותרת Bearer, כדי שהשירות יוכל לזהות את
   הזכאות. בגרסה המדויקת של השרת הפרטי שזוהתה בגבול הראיות לעיל,
   רישום בקשות ההזנה משתמש בגיבובי מפתחות, בנתוני שימוש מצטברים וב-HMAC מקוצר של
   כתובת ה-IP, המתחלף מדי יום, לצורך בדיקה ידנית של שימוש לרעה; טבלאות אלה אינן שומרות את המפתח או את כתובת ה-IP
   בצורתם הגולמית. יומני הגישה של התשתית ותיבת המשלוחים היוצאים המוצפנת הם גבולות תפעוליים
   נפרדים.
3. OmniRoute לעולם אינה שולחת לשירות Radar הנחיות, תשובות, שיחות, פרטי גישה של ספקים, תעבורת מודלים,
   זמן פעילות, השהיה או את תצורת הספק המקומית.
4. התגובה מאומתת, נבדקת ונשמרת במטמון המקומי (ראו
   [מודל האבטחה](#security-model)). ל-Radar יש בדיוק ארבעה נתיבי רשת בצד השרת:
   `syncRadar()` עבור הקטלוג, `syncRadarReferrals()` עבור הפניות, וכן
   `syncRadarOffers()` / `syncRadarIntel()` עבור הצעות ו-Intel לתומכים בלבד.

**מפתח התומך** הוא אסימון Bearer אופציונלי (`radar_settings.supporter_key`)
המאפשר לשירות ההזנה להחליט איזו רמה לספק (ראו
[רמות](#tiers-community-and-live)). הוא:

- מאוחסן כשהוא **מוצפן במנוחה** באמצעות אותם כלי עזר של AES-256-GCM,‏ `encrypt()`/`decrypt()`,
  (`src/lib/db/encryption.ts`) המשמשים לפרטי הגישה של ספקים.
- מוגדר באמצעות `POST /api/radar/settings` (`{ supporterKey: "omr_" + 40 hex chars }`) ו**לעולם אינו מוחזר כפי שהוא** — התגובה מחזירה צורה מוסווית (`omr_****abcd`).
- שינויו או מחיקתו מבטלים באופן אטומי את מטמוני הקטלוג, ההפניות, ההצעות ו-Intel. הסנכרון/הקריאה
  הבאים מזהים את הזכאות החדשה בצד השרת; שמירת מפתח אינה מבצעת כשלעצמה
  בקשת רשת ואינה צורכת מפתח הפעלה חד-פעמי.
- נשלח לשירות ההזנה כאסימון Bearer בבקשת ה-GET של הסנכרון — שום מידע אחר על
  המפתח אינו יוצא מהלקוח לעולם.

| תורם במאייה המובילה   | מקומות 11–100 באותו דירוג                                               | 90 ימים של גישה חיה                      | אותו כלל תביעה לפי דרישה ואידמפוטנטי                       |
| רכישת תומך            | רכישה חד־פעמית ל־6 חודשים, לשנה אחת או לכל החיים                        | קטלוג חי, הצעות חיות חתומות ו־Intel      | ללא חידוש אוטומטי                                          |
| תרומה/הענקה ידנית     | תרומה שנבדקה בידי הבעלים או הענקה מהבעלים למספר מפורש של ימים/לכל החיים | אותה זכאות חיה למשך התקופה שהוענקה       | הענקה מבוקרת ואידמפוטנטית                                  |

בקשות משיכה שמוזגו, ביצועי commit ושורות שהשתנו הם **קלט לדירוג בלבד**. התחברות מחוץ למאייה
המובילה אינה מקבלת הענקת תורם, ללא קשר למספר בקשות המשיכה. רכישות לזמן מוגבל, תרומות, תקופות
תורם והענקות ידניות מצטברות החל ממועד התפוגה הנוכחי; זכאות לכל החיים גוברת על כולן. שינוי בדירוג
לעולם אינו מבטל בדיעבד או מקצר זמן שכבר הוענק.

הרישיון המתארח הוא אישי, והכלל המוצג למשתמש הוא התקנה פעילה אחת בכל רגע נתון. גרסה זו
**אינה** טוענת לנעילת חומרה: סנכרון ה־OSS אינו יוצר טביעת אצבע של החומרה ואינו מתחזק
חכירת מכשיר קריפטוגרפית. בגרסת השרת הפרטי המאומתת שלעיל, האכיפה הממומשת כוללת אימות
זכאות וכן אות לבדיקה ידנית כאשר אותו מפתח חי מזוהה מכתובת IP ייחודית רביעית בתוך 24 שעות.
אות זה לעולם אינו חוסם או מבטל מפתח באופן אוטומטי. השחזור מבטל ומחליף את המפתח שאבד תוך
שמירה על מועד התפוגה הקיים; הוא אינו מתחיל מחדש את התקופה שנרכשה או הוענקה.

הצעות חיות נאצרות ידנית ועשויות להשתנות או לפוג. מסך ההצטרפות מציין גם את גבול הפרטיות
המדויק: מטא־נתונים חתומים של קטלוג/הפניה יורדים; מפתח תקף פותח בנוסף גישה להצעות חתומות
ול־Intel; מפתח ה־Bearer ומטא־נתוני חיבור רגילים מגיעים לשירות המתארח; הנחיות, תשובות, שיחות,
פרטי גישה לספקים, תעבורת מודלים, זמן פעילות, השהיה ותצורת ספקים מקומית אינם מגיעים אליו.

## קבלת מפתח תומך

מסך ההפעלה (`/dashboard/radar`) מקשר לשני תהליכים לצורך **קבלת**
מפתח תומך. מאגר ה-OSS עצמו לעולם אינו מנפיק מפתח, אינו מריץ קוד תשלומים,
ו**לעולם אינו מציין מחיר** — התמחור נקבע ומוצג במלואו בדפי היעד,
ולא במאגר זה (החלטת מפרט D14).

- **"אני תורם"** — פותח את `RADAR_CONTRIBUTOR_CLAIM_URL` (ברירת מחדל
  `https://radar.omniroute.online/auth/github`), תהליך דרישה באמצעות GitHub OAuth המתארח
  בשרת Radar הפרטי. הוא בודק את הדירוג השבועי המלא האחרון: עשרת המקומות הראשונים מקבלים 365 ימים,
  והמקומות 11–100 מקבלים 90 ימים. מחוץ למאה המקומות הראשונים, מספר ה-PR-ים לעולם אינו מעניק גישה;
  במקום זאת, התהליך בודק את רמת הכוכב + המעקב הנפרדת, הניתנת לשימוש חד-פעמי.
- **"תמיכה בפרויקט"** — פותח את `RADAR_SUPPORTER_PLANS_URL` (ברירת מחדל
  `https://radar.omniroute.online/planos`), הדף המתארח של אפשרויות התשלום החד-פעמי ל-6 חודשים,
  לשנה ולכל החיים. דף ה-OSS עדיין אינו מציג ערך כספי כלשהו.

שתי כתובות ה-URL נפתרות בצד השרת (`src/lib/radar/links.ts`, לפי אותו דפוס
דריסה באמצעות משתני סביבה כמו `RADAR_FEED_URL`) ומועברות ללוח הבקרה דרך תגובת
`GET /api/radar/settings` הקיימת (`contributorClaimUrl`, `supporterPlansUrl`) — רכיב
הלקוח לעולם אינו קורא את `process.env` בעצמו.

| משתנה                         | מטרה                                                                                         |
| ----------------------------- | -------------------------------------------------------------------------------------------- |
| `RADAR_CONTRIBUTOR_CLAIM_URL` | דורס את כתובת ה-URL לדרישת תורם (ברירת מחדל `https://radar.omniroute.online/auth/github`).   |
| `RADAR_SUPPORTER_PLANS_URL`   | דורס את כתובת ה-URL של תוכניות התומכים (ברירת מחדל `https://radar.omniroute.online/planos`). |

### שחזור מפתח תומך שאבד

נקודת הכניסה לשחזור של השירות המתארח היא `https://radar.omniroute.online/recover`; היא גם
מקושרת מדף התוכניות. השחזור נשאר לחלוטין מחוץ ללקוח ה-OSS, מכיוון שההתקנה המקומית
לעולם אינה מקבלת את כתובת הדוא"ל של הרוכש/התורם ואינה יכולה לשחזר מפתח גולמי מתוך
ההגדרות המוצפנות שלה.

1. שלחו את כתובת הדוא"ל המשויכת למפתח. השירות מחזיר את אותו דף אישור בין אם קיים
   רישיון בר-שחזור ובין אם לאו, כך שהטופס אינו מאפשר למנות חשבונות.
2. אם קיימת זכאות, תהליך המסירה שולח קישור קצר-מועד לשימוש חד-פעמי. פתיחתו מעבירה
   מיד את האסימון לקובץ Cookie מוצפן וזמני מסוג `HttpOnly`/`Secure`, ומפנה לכתובת
   ה-URL הנקייה `/recover`; הדף אינו מכיל אסימון, כתובת דוא"ל, מפתח ישן או מפתח חלופי.
3. אשרו את הביטול. השירות הפרטי מבטל את המפתח הקודם, יוצר מפתח חלופי עם
   אותה תוכנית/תפוגה, ומכניס אותו לתור לשליחה בדוא"ל במסגרת טרנזקציה אחת. המפתח החלופי לעולם
   אינו מוחזר לדפדפן.
4. הדביקו את המפתח החלופי ב-`/dashboard/radar`. המפתח הישן חייב כעת לרדת למצב `community`;
   המפתח החלופי חייב להפיק סנכרון `live` מאומת. פתיחה מחדש של אותו קישור שחזור חייבת להיכשל
   עם תגובה כללית של קישור לא תקף/שפג תוקפו.

נתיב השחזור המתארח ותהליך הדואר יכולים להיות נוכחים בקוד ועדיין לא להיות זמינים בפריסה
מסוימת. אין להגדיר את התהליך כמוכן לייצור עד שהשרת נפרס, ספק המסירה הוגדר עם נמען
מבוקר, וקישור השימוש החד-פעמי המלא נבדק.

לאחר שלמבקר יש מפתח (`omr_` + ‏40 תווים הקסדצימליים), מסך ההפעלה
(`src/app/(dashboard)/dashboard/radar/page.tsx`) כולל שדה להדבקת מפתח כנתיב
הראשי: הדבקת מפתח ושליחתו שולחות `POST /api/radar/settings`
(`{ optIn: true, supporterKey }`) בקריאה אחת — הדבקת מפתח גם מגדירה אותו וגם מצטרפת,
ובכך פותחת את המסך. הפורמט (`omr_` + ‏40 תווים הקסדצימליים) נבדק תחילה בצד הלקוח
באמצעות פונקציית העזר המשותפת `isValidSupporterKeyFormat()` (`src/lib/radar/supporterKey.ts`)
כמחווה לשיפור חוויית המשתמש; סכמת Zod של השרת היא הבדיקה הסמכותית בכל מקרה. לאחר
הגדרת מפתח, מסך ההפעלה מציג את הצורה הממוסכת (`supporterKeyMasked` מתוך
`GET /api/radar/settings`) במקום שדה קלט ריק, עם פקד "שינוי מפתח" להדבקת
מפתח חדש — המפתח הגולמי לעולם אינו מוצג מחדש. שני כפתורי הדרישה/התוכניות שלעיל
נותרים הדרך _לקבל_ מפתח מלכתחילה; שדה קלט זה הוא המקום שבו מפעיל
שכבר מחזיק במפתח מפעיל אותו.

### הפעלה מקצה לקצה והגדרה מודרכת

לשירות הפיד הפרטי וללקוח OSS זה יש גבול צר במכוון: השירות
מנפיק ומאמת את מפתח התומך, בעוד שהתקנת OmniRoute המקומית מצפינה את המפתח,
מסנכרנת פריטים חתומים בצד השרת ומנחה את הגדרת הספק. סדר האימות המסייע הוא:

1. השיגו מפתח חדש שהונפק או שוחזר דרך תביעת התורם, מסלול הרכישה/התוכניות, תהליך השחזור או ממפעיל מורשה של שרת פרטי. אין להדביק את המפתח הגולמי ביומנים,
   בצילומי מסך, בתגובות לבעיות או בארגומנטים של שורת הפקודה.
2. הפעילו את דגל התכונה `RADAR_ENABLED` בהתקנת OmniRoute המקומית. פעולה זו חושפת את ממשק המשתמש,
   אך אינה מפעילה תקשורת רשת עד לשמירת ההצטרפות הנפרדת.
3. פתחו את `/dashboard/radar`, הדביקו את המפתח והפעילו. הדפדפן שולח בקשה מקומית אחת מסוג
   `POST /api/radar/settings` עם `{ optIn: true, supporterKey }`; המפתח מוצפן מקומית
   והתגובה מכילה רק `omr_****<last4>`.
4. אפשרו למסך ההפעלה להשלים את סנכרון הקטלוג, או בחרו **סנכרון כעת**. ודאו שהדף
   מציג `live`, גרסת פיד ומועד אחזור. לצורך אבחון מקומי מאומת,
   `GET /api/radar/status` מדווח על מצב ההצטרפות/נוכחות המפתח ועל ארבעת מצבי המטמון, מבלי להחזיר
   את המפתח. ניתן להשתמש ב-`POST /api/radar/sync-all` כדי לרענן במפורש את הקטלוג, ההפניות, ההצעות ו-Intel.
5. פתחו את `/dashboard/radar/setup?provider=<provider>`. היכנסו לכתובת ה-URL של פרטי הגישה שבבעלות הספק,
   בחרו **הוספת מפתח API**, שמרו באמצעות הטופס האמיתי של הספק, חזרו למדריך והפעילו
   **בדיקת חיבור**. המדריך משתמש בנתיבים הרגילים `/api/providers` ו-
   `/api/providers/<connection-id>/test`; הוא אינו יוצר פרטי גישה מקבילים עבור Radar.
6. פתחו את `/dashboard/radar/combos` לאחר שלפחות שני חיבורי ספק תואמים פעילים.
   בדקו את המשפחה המוצעת וצרו את השילוב באמצעות API השילובים הקיים. ההצעות ו-
   Intel נשארים מטמונים חתומים נפרדים, הזמינים במצב פעיל בלבד, וניתן לבדוק אותם בדפי Radar הייעודיים שלהם.
7. טענו מחדש את `/dashboard/radar` ואת דף ההגדרה. ההצטרפות, מצב המפתח המוסווה, המטמון המאומת, חיבור
   הספק השמור ופעולת הבדיקה חייבים להישמר לאחר הטעינה מחדש. תעדו ראיות רק לאחר
   שהמפתח הגולמי ופרטי הגישה של הספק אינם גלויים עוד.

שמירת מפתח אינה כשלעצמה הוכחה לזכאות פעילה. ההוכחה היא השילוב בין תוצאת
`GET /v1/license/check` של השירות הפרטי, רמת `live` שמספק קטלוג ה-OSS, מטמון חתום
ומאומת ותהליך החיבור/הבדיקה האמיתי של הספק. מפתח לא תקין, שפג תוקפו או שבוטל
מוריד בבטחה את הקטלוג לרמת `community`; אין לדווח עליו כאימות מוצלח של מפתח פעיל.

### קישור ללוח הניהול הפרטי

`RADAR_ADMIN_URL` מוסיף באופן אופציונלי את **ניהול Radar ↗** מיד אחרי פריט Radar המיועד למשתמשים
במקטע העלויות של סרגל הצד. בכוונה אין לו ערך ברירת מחדל: כאשר המשתנה
אינו מוגדר או אינו תקין, סרגל הצד הסטטי, לוח הפקודות ומסך ההתאמה האישית של סרגל הצד אינם מכילים
פריט ניהול או כתובת URL פרטית.

הערך נקבע בצד השרת ומועבר באמצעות תגובת
`GET /api/settings`, המאומתת לניהול, רק להפעלת לוח מחוונים מאומתת או לבעלים המהימן
בלולאה המקומית במהלך אתחול מקומי ללא כניסה. אימות באמצעות CLI, שירות פנימי ומפתח API
בעל היקף ניהול אינו מקבל אותו. הדפדפן מאמת שוב את התגובה לפני יצירת
הקישור החיצוני, שנפתח עם `noopener noreferrer`.

השתמשו בכתובת URL ללא פרטי גישה של מנהרת HTTPS או tailnet. HTTP רגיל מתקבל רק עבור העברת SSH
בלולאה המקומית, כגון `http://127.0.0.1:9351`; סכמות אחרות, פרטי גישה משובצים, כתובות URL פגומות
ויעדי HTTP מרוחקים נכשלים באופן סגור ומשאירים את הניווט לא פעיל.

## מודל אבטחה

### חתימת Ed25519 על הבתים המדויקים

המטען של הפיד חתום באמצעות Ed25519. הפונקציה `verifyFeedBytes()`
(`src/lib/radar/verify.ts`) מאמתת את החתימה מול **בתי התגובה המדויקים**
שהתקבלו ברשת — המטען לעולם אינו עובר סריאליזציה מחדש לפני האימות, כך שקידוד
מחדש בית-אחר-בית אינו יכול לבטל או לעקוף את בדיקת החתימה ללא התרעה.
כשל באימות (`invalid_signature`) מבטל את הסנכרון עוד לפני שהמטען
מנותח או נשמר במטמון.

### מפתח ציבורי מוצמד + החלפה

המפתח הציבורי המשמש לאימות מוצמד בקובץ `src/lib/radar/pinnedKeys.ts`
(`PINNED_FEED_PUBLIC_KEYS`), כמערך המאפשר להוסיף מפתח חדש בתחילתו לקראת
החלפה, בעוד שפידים ישנים במטמון שנחתמו באמצעות מפתח קודם נותרים תקפים עד
לסנכרונם מחדש.

### דריסות באמצעות משתני סביבה המותאמות ל-forks

שני משתני סביבה מאפשרים ל-forks ולמארחים עצמאיים להפנות את הלקוח לפיד משלהם במקום
לשירות OmniRoute המוגדר כברירת מחדל — ראו
[כיצד לארח פיד באופן עצמאי](#how-to-self-host-a-feed) להלן:

| משתנה               | מטרה                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------- |
| `RADAR_FEED_URL`    | דורס את כתובת ה-URL הבסיסית של הפיד (ברירת המחדל היא `https://radar.omniroute.online`).           |
| `RADAR_FEED_PUBKEY` | דורס את המפתח הציבורי המוצמד (SPKI מסוג base64-DER או PEM), ומחליף את המערך המובנה במפתח יחיד זה. |

### סף גרסה

`syncRadar()` דוחה פיד שהורד אם ה-`version` שלו אינו חדש יותר באופן חד-משמעי מהגרסה
השמורה כעת במטמון (השוואת `compareVersions()` בתבנית המנוקדת `YYYY.MM.DD.n`) —
`{ status: "stale" }`. כך נמנע מנקודת קצה של פיד שנפרצה או הוגדרה באופן שגוי
להחזיר לקוח למטען ישן יותר שנחתם בצורה אחרת.

### שני תאריכים, ומדוע שניהם נשמרים

פיד שמור במטמון מכיל שני תאריכים נפרדים, ומניעת הבלבול ביניהם היא בדיוק הסיבה
לשמירת שניהם:

| שדה           | מקור              | על איזו שאלה הוא עונה        |
| ------------- | ----------------- | ---------------------------- |
| `generatedAt` | גוף הפיד החתום    | בני כמה **הנתונים**          |
| `fetchedAt`   | השעון של התקנה זו | מתי התקנה זו **הורידה** אותם |

פיד שהורד לפני דקות ספורות עשוי להכיל נתונים בני שבועות, ולכן `fetchedAt` לבדו אינו
יכול לומר למפעיל אם שכבת-העל עדכנית יותר מקו הבסיס שעליו היא מונחת. שניהם
נשמרים ב-`radar_feed_cache`, מוחזרים על ידי `getRadarCatalog().meta`, ומדווחים
בנפרד על ידי `GET /api/radar/status`. שורה שנשמרה במטמון לפני שהעמודה `generated_at`
הייתה קיימת (מיגרציה 163) נקראת בחזרה כ-`null` — ערך לא ידוע נשאר לא ידוע במקום
להשתמש בזמן ההורדה. `radar_referrals_cache` שומר את `generated_at` שלו מאז
מיגרציה 142.

סף הגרסה שלעיל משווה את `version`, ולא אף אחד מהתאריכים.

נותרו שני פערים, ושניהם מכוונים: לוח המחוונים עדיין מציג רק `Last fetched`, ולכן הצגת
תאריך הבנייה שם מחייבת תווית חדשה (ואת 41 רשומות הלוקליזציה שלה); ומטמוני ההצעות
והמודיעין אינם שומרים כלל תאריך בנייה, אף שסכמות הפיד שלהם כוללות כזה — לכן `GET
/api/radar/status` משמיט את השדה עבור שני אלה במקום לדווח על `null`
שיתפרש כ״לא ידוע״.

### אימות סכמה

הבתים שהורדו מנותחים ומאומתים מול `RadarFeedSchema`
(`src/lib/radar/feedSchema.ts`, סכמת Zod) **לאחר** אימות החתימה. אי-התאמה
לסכמה מחזירה `{ status: "invalid_schema" }`, והמטמון נותר ללא שינוי.
כאמצעי הגנה, המטען השמור במטמון מאומת מחדש בכל קריאה
(`getRadarCatalog()`) — שורת מטמון פגומה או כזו שנערכה ידנית גורמת לחזרה
לקו הבסיס במקום להיות מוגשת.

### מגבלת גודל תגובה (10 MB)

`syncRadar()` אוכפת **מגבלה קשיחה של 10 MB** על גוף תגובת הפיד — הפיד החתום
הוא מסמך JSON בגודל של כמה KB, ולכן כל חריגה מכך מצביעה על `RADAR_FEED_URL`
שהוגדר באופן שגוי או עוין (או על מקור במעלה הזרם שמגיש זבל), ולא על קטלוג לגיטימי.
האכיפה מתבצעת בשתי שכבות:

1. בדיקת קדם של `Content-Length` מדלגת לחלוטין על קריאת הגוף כאשר
   הכותרת כבר מצהירה על ערך החורג מהמגבלה.
2. בדיקת סכום מצטבר במהלך קריאת הגוף אוכפת את המגבלה גם כאשר
   `Content-Length` חסרה או מציגה גודל קטן מהגודל האמיתי — לעולם אין
   להסתמך על הכותרת לבדה. שרשור המקטעים שנצברו משמר את הבתים המדויקים
   הדרושים לבדיקת חתימת Ed25519 לאחר מכן.

חריגה מהמגבלה מחזירה `{ status: "too_large" }` ומותירה את המטמון ללא שינוי,
בהתאם לאותו דפוס לא-הרסני המשמש בכל כשל סנכרון אחר
(`invalid_signature`, `invalid_schema`, `stale`).

## רמות: `community` ו-`live`

סכמת הפיד כוללת שדה `tier: "community" | "live"`, שנקבע **בצד השרת**
על ידי שירות הפיד בהתאם לבקשה (נוכחותו ותקפותו של מפתח התומך)
— הלקוח לעולם אינו קובע את הרמה של עצמו.

- **`community`** — הקטלוג החינמי, המתעכב בכ-30 יום אחרי הנתונים העדכניים
  ביותר. זה מה שמתקבל בבקשה לא מאומתת או בבקשה עם מפתח לא תקף.
- **`live`** — הקטלוג העדכני ביותר, המוגש לבקשות הנושאות מפתח תומך
  תקף.

**מפתח תומך לא תקף או שפג תוקפו מוביל לירידה ל-`community` — הוא לעולם אינו
שגיאה.** נתיב הסנכרון מבחין רק בין כשלי חתימה/סכמה/גרסה (כולם
ניתנים להתאוששות וכולם אינם קטלניים למצב השמור במטמון) לבין `{ status:
"updated", version, tier }` מוצלח. אין נתיב שגיאה ייחודי לרמה שהלקוח צריך
לטפל בו.

### הרמה המוגשת מגיעה מכותרת תגובה, לא מהגוף החתום

השדה `tier` ב**גוף** הפיד החתום הוא תמיד `"live"` — שירות הפיד מפיץ
**שני ארטיפקטים חתומים לכל גרסה**: `live` כולל קמפיינים עדכניים ו-`community`
משמיט אותם. כל ארטיפקט נחתם על גבי הבתים המדויקים שלו. הגוף עדיין אינו
משמש כהחלטת הזכאות; הרמה שנבחרה בפועל עבור בקשה נישאת
ב**כותרת התגובה `x-omniroute-feed-tier`**, ונקבעת בצד השרת לפי מפתח
ה-`Authorization` של הבקשה.

`syncRadar()` (`src/lib/radar/sync.ts::parseServedTierHeader()`) הוא המקום היחיד
שבו נקבעת הרמה שעל הלקוח לתת בה אמון:

1. יש לנתח את `x-omniroute-feed-tier` באמצעות `RadarTierSchema`‏ (Zod) — כותרת חסרה, או
   ערך שאינו בדיוק `"community"` או `"live"`, נחשבים כ**לא
   קיימים** (לעולם אין לתת בהם אמון כפי שהם לצורך המטמון/ממשק המשתמש; הדבר מכסה גם שרתי פיד
   ישנים יותר שקדמו לכותרת).
2. יש לחזור לשדה `tier` של הגוף החתום (שתמיד ערכו `"live"`) רק כאשר שלב 1
   אינו מניב דבר.
3. הרמה שנקבעה היא זו שנשמרת במטמון ומוחזרת בתור `{ status: "updated",
version, tier }` — זהו הערך שמוצג בלוח המחוונים, ולעולם לא שדה הגוף
   הגולמי.

## כללי מיזוג שכבה בזמן קריאה

`applyFeed()` (`src/lib/radar/applyFeed.ts`) ממזגת את הפיד השמור במטמון **מעל**
לקו הבסיס הסטטי **בזמן הקריאה**, בתוך `getRadarCatalog()`. מערך קו הבסיס
(`FREE_MODEL_BUDGETS`) לעולם אינו משתנה — `MergedEntry[]` חדש מחושב בכל
קריאה.

ארבעה כללים, לפי סדר הקדימות:

1. **הפיד לעולם אינו דורס התאמה מקומית.** לפי שדה: אם המפעיל
   התאים אישית שדה ברשומה (`localOverrides` map, keyed `provider:modelId`),
   מדלגים על ערך הפיד עבור אותו שדה מסוים — ערך המפעיל גובר.
2. **`enabled: false` משבית את הרשומה, תוך תיעוד המקור.** רשומת פיד שמכבה
   רשומה מגדירה `enabled: false` ו-`disabledBy: "radar"` בתוצאה הממוזגת,
   כדי שממשק המשתמש יוכל להסביר _מדוע_ רשומה עברה מזמינה למושבתת.
3. **רשומה שהוסיף משתמש ושאינה קיימת בפיד נשמרת ללא שינוי.** רשומות
   שקיימות רק בקו הבסיס (או נוספו מקומית) ושאין להן רשומת פיד תואמת
   עוברות ללא שינוי.
4. **רשומה שסומנה כמצבה לעולם אינה מוחזרת לחיים.** אם המפעיל מחק במפורש
   רשומה (`tombstones` set), הוספה מחדש של אותו `provider:modelId` על ידי הפיד בגרסה
   מאוחרת יותר אינה מחזירה אותה.

השדות הניתנים לעריכה והמצבות נשמרים ב-
`radar_local_model_state` (מיגרציה `153_radar_local_model_state.sql`). מתאם מסד הנתונים
הציבורי (`src/lib/db/radar.ts`) ממיר שורות אלה ל-`localOverrides` map ול-
`tombstones` set שבהם משתמשת `applyFeed()`; בסביבת הייצור, `getRadarCatalog()` טוענת מצב זה
לאחר שמעברי הדגל, המטמון והסכמה מצליחים. רק `displayName` ו-`enabled`
ניתנים לעריכה על ידי המפעיל. זהות הספק/המודל, מקור הפיד, המכסה, היכולות, תנאי השימוש
ונתוני ההגדרה אינם ניתנים לכתיבה דרך ממשק זה.

לוח המחוונים מציע ארבע פעולות מקומיות:

- **עריכה** משנה את שם התצוגה המקומי ואת מצב ההפעלה.
- **איפוס שינויים מקומיים** מנקה את שני השדות הניתנים לעריכה בלי לשנות מצבה.
- **הסתרה** יוצרת מצבה, כך שעדכוני פיד מאוחרים יותר לא יוכלו ליצור מחדש את השורה.
- **שחזור** מסיר את המצבה; כל התאמה שנשמרה בנפרד נשארת בתוקף.

ערך פיד של `enabled: false` נשאר חריג הבטיחות: הוא גובר על
`enabled: true` מקומי ומיושן, משאיר את הרשומה הממוזגת מושבתת ומתעד
`disabledBy: "radar"`.

פרסומי הקטלוג משתמשים ב-`schemaVersion: 2`. ‏`contextWindow` וכל אחד מבין `tools`,‏ `vision` ו-
`thinking` הם, באופן בלתי תלוי, `number | null` / `boolean | null`: ‏`null` פירושו לא ידוע, ואילו
`false` פירושו שמקור ספק רשמי שאומת לפי D16 מציין במפורש שהיכולת אינה קיימת.
דגלים פנימיים של מפרטי הרישום/המודלים של OmniRoute לעולם אינם מקודמים ישירות לעובדות בפיד. הלקוח
עדיין מקבל צילומי מצב מ-v1; מכיוון שהבונה הישן השתמש ב-`false` כמציין מקום להיעדר, `false` של v1
מנורמל ללא ידוע, בעוד `true` של v1 נשאר עובדתי. גרסאות סכמה לא ידועות נכשלות באופן סגור,
והמטמון התקף האחרון נשאר זמין. כל מודל v2 עם הקשר/יכולת שאינם null חייב לכלול
`metadataEvidenceUrls[]` מסוג HTTPS שאינם דורשים פרטי גישה; אחרת אימות הסכמה נכשל והמטמון
אינו מוחלף. טבלת הקטלוג מציגה את כל שלושת המצבים בתור `✓`,‏ `✕` ו-`?`.

### שילובים מודרכים וגישה ל-MCP

ערכי `familyId` מאומתים שורדים את שכבת-העל בזמן הקריאה ומניעים את המודול הטהור
`buildRadarComboSuggestions()` (`src/lib/radar/comboSuggestions.ts`). משפחה מוצעת
רק כאשר לפחות לשני ספקים נפרדים יש חיבורים פעילים והם חושפים את מזהה המודל המדויק
שנבחר מראש. מודלים מושבתים, ספקים לא פעילים, מזהי מודל חסרים, משפחות עם איבר יחיד והתאמות
עמומות של כינוי/תחילית נכשלים באופן סגור. ההצעות משתמשות באסטרטגיית `priority` הקיימת, תוך סידור
התקציב החודשי החוזר הגדול ביותר ראשון; ממשק המשתמש יוצר אותן רק באמצעות `POST /api/combos`.

הממשק הגרפי המונחה נמצא ב-`/dashboard/radar/combos`. הוא קורא רק את נקודות הקצה המקומיות
`GET /api/radar/catalog` ו-`GET /api/combos/builder/options`. הוא לעולם אינו מפעיל סנכרון Radar,
קורא פרטי גישה של ספקים או כותב ישירות למסד הנתונים של הקומבינציות.

לקוחות MCP יכולים לקרוא את אותה תצוגה מקומית באמצעות `omniroute_radar_catalog` (`read:radar`). המסננים
האופציונליים `provider`,‏ `familyId` ו-`enabledOnly` מוערכים לאחר קריאה מקומית אחת של
`GET /api/radar/catalog`. הפלט הסגור שלו כולל מטא-נתונים של הקטלוג וכן ספק/מודל,
שם תצוגה, `familyId`, מכסה, יכולות, מצב הפעלה, מקור ו-`disabledBy`; כתובות URL להגדרה,
שלבים, חיבורים, כתובות דוא״ל, מפתחות ונתוני הפניה אינם מוחזרים לעולם. כלי זה מיועד
לקריאה בלבד ולעולם אינו מפעיל את `/api/radar/sync`.

### סמני מקור

כל רשומה ממוזגת כוללת שדה `origin`, שממשק המשתמש מציג כתג:

- `"baseline"` — ללא שינוי מקטלוג הגרסה הסטטי.
- `"radar"` — שדה אחד או יותר רועננו על ידי הפיד.
- `"local"` — למפעיל יש לפחות דריסה מקומית אחת ברשומה זו (דריסות מקומיות
  תמיד גוברות על הפיד בהתאם לכלל 1, ללא תלות במה שהפיד מציין).

| `/api/radar/local-model-state` | PUT    | יוצר או מסיר סימון מחיקה באמצעות `{ provider, modelId, tombstoned }`.                                      |
| `/api/radar/local-model-state` | DELETE | מנקה שדות דריסה הניתנים לעריכה תוך שימור כל סימון מחיקה.                                                   |

**כלל מחייב: נתיבים אלה לעולם אינם משמשים כפרוקסי לשירות הפיד.** הדפדפן מתקשר אך ורק
עם שרת OmniRoute המקומי. ארבעת המודולים שניגשים לשירות Radar הם
`src/lib/radar/sync.ts` (קטלוג), `src/lib/radar/referralsSync.ts` (הפניות),
`src/lib/radar/offersSync.ts` (הצעות) וכן `src/lib/radar/intelSync.ts` (Intel); כולם פועלים
בצד השרת, ולעולם לא בצד הלקוח. כך כתובת ה-URL של הפיד וכל מפתח תומך נשארים לחלוטין
מחוץ לתעבורת הרשת החשופה ללקוח.

כל נקודות הקצה של Radar מחזירות `404` כאשר `RADAR_ENABLED` כבוי (ראו
[דגל](#flag-radar_enabled-default-off) לעיל), ומעבירות תגובות שגיאה דרך
`buildErrorBody()`/`sanitizeErrorMessage()` בהתאם לכלל ניקוי השגיאות החל על כל המאגר
(`docs/security/ERROR_SANITIZATION.md`).

### אימות

כל נקודות הקצה של Radar דורשות אימות באמצעות `isAuthenticated()`
(`src/shared/utils/apiAuth.ts`) — קובץ cookie של סשן לוח המחוונים או מפתח API
בעל הרשאות ניהול, אותו שער שמגן על שאר `/api/settings/*`. בדיקת `404` כאשר הדגל
כבוי מתבצעת תמיד **לפני** בדיקת האימות, כך שהתקנה שבה `RADAR_ENABLED` כבוי נשארת
זהה ברמת הבתים (אין בקשת אימות רק כדי לגלות שהממשק אינו קיים); לאחר שהדגל מופעל,
בקשה לא מאומתת מקבלת `401` לפני כל קריאה ממסד הנתונים או כתיבה אליו.
`GET /api/radar/settings` לעולם אינו מחזיר את מפתח התומך הגולמי, ללא תלות במצב
האימות — רק את הצורה הממוסכת שלו וערך בוליאני `hasSupporterKey`.

## הצעות לתומכים

הצעות משתמשות בארטיפקט חתום משלהן, `GET /v1/offers/latest`, ולעולם אינן משתפות את מטמון הקטלוג או ההפניות. נקודת הקצה בשרת דורשת מפתח Bearer תקף ופעיל של תומך; אין חלופה קהילתית. לכן `syncRadarOffers()` נעצרת לפני הגישה לרשת כאשר דגל התכונה כבוי, המפעיל לא הביע הסכמה להשתתף, או שלא הוגדר מפתח תומך.

לאחר GET מוצלח, הלקוח מאמת את חתימת Ed25519 על הבתים המדויקים של התגובה, מבצע אימות מול `RadarOffersFeedSchema`, דורש שגם גוף התגובה החתום וגם הכותרת `x-omniroute-feed-tier` יציינו `live`, אוכף גרסה מנוקדת חדשה יותר באופן מחמיר, ורק אז מחליף באופן אטומי את `radar_offers_cache` (מיגרציה `144_radar_offers_cache.sql`). חלה אותה מגבלה של 10 MB לכותרות ולזרם יחד, המשמשת את שאר הפידים. כשלים בחתימה, בסכימה, ברמת השירות, עקב שידור חוזר, בגודל, ב-HTTP או ברשת משמרים כולם את המטמון האחרון שאומת.

מבנה ההצעה הסגור תומך בשלושה סוגי הטבות בני-השוואה: אחוז בנקודות בסיס, זיכוי ביחידות מטבע משניות, או ימי ניסיון. הצעת שותף חייבת לכלול קו בסיס ציבורי מאותו סוג, וההטבה שלה חייבת להיות גדולה ממנו באופן מחמיר; להצעות רשמיות אין קו בסיס של שותף. כתובות URL חייבות להשתמש ב-HTTPS ולהיות ללא פרטי גישה. `getRadarOffers()` מאמתת מחדש באופן הגנתי את המטען השמור במטמון ומסננת רשומות שפג תוקפן בכל קריאה מקומית; `/dashboard/radar/offers` מסננת שוב לפי תפוגה לפני העיבוד, משתמשת בטקסט בפורטוגזית כשהוא זמין עם אנגלית כברירת מחדל, ומסמנת במפורש הצעות של שותפים.

הדפדפן פונה רק לנתיבים מקומיים: הוא קורא את תמונת המצב הממוסכת של ההגדרות, מבקש מ-`POST /api/radar/offers/sync` לבצע רענון בצד השרת, ולאחר מכן קורא את `GET /api/radar/offers`. ללא מפתח, הוא מציג את קישורי התורמים/התמיכה הקיימים במקום לנסות לבצע בקשת פיד. קישורים חיצוניים להצעות נפתחים בכרטיסייה חדשה עם `noopener noreferrer`. בגרסה זו לא נחשף כלי MCP בשם `radar_offers`.

## Radar Intel, תג תומך ו-CLI

Intel הוא ארטיפקט חתום ב-`GET /v1/intel/latest`. הסכימה הסגורה `RadarIntelFeedSchema` מקבלת רק דירוגי ELO בבעלות Radar, שנגזרו בידי האוצר הפרטי מהשוואות מאומתות, וכן הפרשי גיל/כמות עובדתיים של הקטלוג, שנגזרו מתמונות מצב חתומות של הקטלוג. המתודולוגיה קבועה לדירוג התחלתי של 1000 ול-K=32. דירוג ריק תקף כאשר לא אושרה אף השוואה; הלקוח לעולם אינו מייצר דירוג כזה באופן סינתטי.

`syncRadarIntel()` מחילה את אותם מנגנונים כמו בהצעות: Bearer בצד השרת, פסק זמן של 30 שניות, מגבלת זרם של 10 MiB, אימות Ed25519 על הבתים המדויקים, סכימה מחמירה, דרישת `live` בגוף ובכותרת, סף מינימום לגרסה ושימור המטמון התקין האחרון. לאחר שתמונת מצב חיה ומאומתת נשמרת, הלקוח גוזר את `radar:<sha256(supporter key)>`, שומר רק את הזהות החד-כיוונית הזו, ופולט את אירוע ההכרה הייעודי `radar_supporter`. התג `radar-supporter` שלו אידמפוטנטי ומעניק אפס XP; הוא לעולם אינו מעדכן טבלאות מובילים ואינו עושה שימוש חוזר ב-`token_share`. הנתיב `/dashboard/radar/intel` מעבד את התג רק מתוך מטא-נתונים מאומתים במטמון המקומי.

ה-CLI חושף את `omniroute radar status` ואת `omniroute radar sync`. שתי הפקודות מתקשרות רק עם ה-API המקומי של OmniRoute. הפקודה `status` מבצעת `GET /api/radar/status` לקריאה בלבד; הפקודה `sync` שולחת בקשת `POST /api/radar/sync-all` אחת ומדפיסה תוצאה לכל פיד. אף אחת מהפקודות אינה קוראת, מקבלת או מדפיסה את מפתח התומך, ואף אחת אינה פונה ישירות לשירות Radar.

## קישורי הפניה (קרדיטים בחינם)

קישורי הפניה מוגשים מפיד **עצמאי ועדכני תמיד** —
`GET /v1/referrals/latest` — בנפרד מפיד הקטלוג. הדבר נעשה במכוון: פיד
הקטלוג ברמת הקהילה הוא תמונת מצב שעשויה להיות בת עד 30 יום, ולכן
קישור הפניה שחולץ ממנו היה מתעדכן באיחור זהה ביחס לרשימת הקישורים האמיתית של השרת
(קישור הפניה שנוסף זה עתה לא היה מגיע למשתמש חינמי/קהילתי במשך עד חודש).
פיד ההפניות מבטל את העיכוב הזה באמצעות סנכרון בקצב נפרד וקצר בהרבה.

```ts
// גוף התגובה של GET /v1/referrals/latest (חתום באמצעות Ed25519, עם אותו מפתח מוצמד כמו
// פיד הקטלוג):
{
  feed: "omniroute-radar-referrals",
  schemaVersion: 1,
  generatedAt: string,           // ISO — דטרמיניסטי: max(updatedAt) בכל קישורי ההפניה,
                                  // כך ששתי בקשות זהות מפיקות בדיוק את אותם
                                  // בתים חתומים/חתימה
  referrals: {
    fixed: RadarReferral[],      // קיים בכל רמה, כולל ללא אימות/קהילה
    campaigns: RadarReferral[],  // מאוכלס רק עבור מפתח Bearer חי ותקף (תומך);
                                  // בקשות ללא אימות/עם מפתח שפג תוקפו מקבלות []
  },
}
// RadarReferral = { provider, url, kind: "fixo" | "campanha", validUntil,
//                    requiredAction, isDefault }
```

בניגוד לפיד הקטלוג, גוף זה אינו כולל שדה `tier` כלל — השרת מחליט
מה לכלול בכל בקשה על סמך מפתח ה-`Authorization`, ולכן כותרת התגובה
`x-omniroute-feed-tier` היא המקור היחיד לרמה שסופקה
(`referralsSync.ts::syncRadarReferrals`); כותרת חסרה/לא מזוהה מורידה את הרמה
ל-`"community"`, הנחת ברירת המחדל בעלת ההרשאות המצומצמות ביותר. `RadarReferralsFeedSchema`
(`src/lib/radar/referralsFeedSchema.ts`) מאמת את הגוף כולו, תוך שימוש חוזר באותו
`RadarReferralSchema` לכל הפניה שמיוצא מ-`feedSchema.ts`, כך ששני הפידים מאמתים
הפניות בודדות באופן זהה. כל `RadarReferral.url` חייב להיות `https://` — כתובת
`http://` נכשלת באימות הסכמה.

השדה הישן `referrals`, המוטמע בקטלוג, ב-`RadarFeedSchema` (`feedSchema.ts`)
נשמר לצורך תאימות לאחור עם פידי קטלוג שכבר נשמרו במטמון, אך `getRadarReferrals()`
אינו קורא ממנו עוד — ראו [פונקציית גישה](#accessor) להלן.

### סנכרון

`syncRadarReferrals()` (`src/lib/radar/referralsSync.ts`) הוא המודול היחיד שניגש
לרשת עבור הפניות, ומשקף במדויק את החוזה של `syncRadar()`: דגל כבוי
→ `disabled`; הצטרפות מושבתת → `opt_out`; מוריד את `${RADAR_FEED_URL}/v1/referrals/latest`
(עם אותן דריסות הסתעפות `RADAR_FEED_URL`/`RADAR_FEED_PUBKEY` כמו בקטלוג), מאמת את
חתימת Ed25519 על הבתים המדויקים של התגובה (`verifyFeedBytes`), מאמת מול
`RadarReferralsFeedSchema`, ושומר במטמון בטבלה `radar_referrals_cache`
(מיגרציה `142_radar_referrals_cache.sql`) — טבלה נפרדת לחלוטין מ-
`radar_feed_cache` של הקטלוג. מגבלת תגובה של 10 MB וסף תחתון ל-`generatedAt` דוחים
פיד נכנס הישן יותר מזה שבמטמון, ובכך מגינים מפני שידור חוזר של פריט חתום ישן.
חותמת זמן זהה מתקבלת: השרת מעניק במכוון לגרסאות ההפניות של הקהילה ושל משתמשים פעילים
את אותו `generatedAt` דטרמיניסטי, כך שהמטען החתום והרמה שסופקה יכולים להשתנות לאחר
שינוי במפתח תומך, מבלי שקבוצת הקישורים הבסיסית תשתנה. הפונקציה לעולם אינה זורקת
חריגה — היא תמיד מחזירה אובייקט סטטוס; שגיאות לעולם אינן כוללות מעקב מחסנית
ב-`reason`.

שני טריגרים שומרים על מטמון ההפניות מעודכן, ושניהם בלתי תלויים במחזור בן 24 השעות
של הקטלוג:

- **סנכרון בעת קריאה** — `GET /api/radar/referrals` עצמו קורא ל-`syncRadarReferrals()`
  באופן מיידי בכל פעם שהמטמון חסר או ישן יותר מ-`REFERRALS_STALE_MS` (שעה אחת,
  `shouldSyncReferralsOnRead()`), לפני הגשת התגובה. מנגנון זה הופך את הקישורים הקבועים
  ל"עדכניים תמיד" כבר בטעינה הבאה של לוח הבקרה, ללא המתנה לטיימר כלשהו
  ברקע.
- **סנכרון צדדי של המתזמן** — `radarSchedulerTick()` (`scheduler.ts`) מעריך באופן
  עצמאי את התיישנות ההפניות באותו סימון שעתי המשמש את הקטלוג, וקורא
  ל-`syncRadarReferrals()` בעת הצורך. פעולה זו מתבצעת ללא קשר לשאלה אם הקטלוג עצמו
  נדרש לסנכרון באותו סימון, ולעולם אינה משפיעה על המבנה של `RadarTickResult` (תופעת
  לוואי מסוג מיטב-המאמץ בלבד, שנבלעת במקרה של שגיאה).

### פונקציית גישה

`src/lib/radar/index.ts` מייצא שתי פונקציות גישה לקריאה בלבד, ושתיהן לעולם אינן
זורקות חריגה (אותו חוזה הגנתי כמו `getRadarCatalog()` — דגל כבוי, היעדר מטמון או
מטען פגום במטמון, כולם מוחזרים כמבנה ריק במקום כשגיאה):

- `getRadarReferrals()` → `{ fixed: RadarReferral[], campaigns: RadarReferral[] }`,
  קוראת מתוך `radar_referrals_cache` (באמצעות `getRadarReferralsCache()`) ומאמתת
  דרך `RadarReferralsFeedSchema` — **לא** דרך מטמון הקטלוג.
- `getDefaultReferralFor(provider)` → הפניית `fixed` עם `isDefault: true` עבור
  אותו ספק, או `null`. היא בודקת רק את `fixed` — קמפיין לעולם אינו משמש כקישור
  "ברירת המחדל" של ספק.

הכלל בפועל הקובע "איזו הפניה היא ברירת המחדל עבור ספק" נמצא ב-
`findDefaultReferral()` (`src/lib/radar/referrals.ts`), פונקציה טהורה קטנה **ללא
ייבוא DB** — ניתן לייבא אותה בבטחה לתוך רכיב `"use client"`. הפונקציות
`getRadarReferrals`/`getDefaultReferralFor` (ב-`index.ts`) מייבאות את
`@/lib/db/radar` ולכן נשארות בצד השרת בלבד; לוח הבקרה של הספקים מייבא את
`referrals.ts` ישירות במקום את `index.ts` (ראו להלן), כדי להימנע מאריזת
`better-sqlite3` בתוך הדפדפן.

### `GET /api/radar/referrals`

פועל בדיוק לפי אותו סדר שערים כמו כל נתיב Radar אחר: כאשר `RADAR_ENABLED` כבוי →
`404` (נבדק ראשון, תוך שמירה על התנהגות זהה ברמת הבתים); ללא אימות → `401`; אחרת,
מפעיל סנכרון בעת קריאה (ראו לעיל) כאשר המטמון מיושן, ולאחר מכן מחזיר `200` עם
`{ fixed, campaigns, tier }` — הערך `tier` מגיע ישירות משורת המטמון (שייתכן שזה עתה רועננה)
והוא אינפורמטיבי בלבד (משמש להצגת נוסח השדרוג העדין בממשק המשתמש, כמתואר להלן). לעולם אינו
משמש כפרוקסי ישיר לשרת הפיד — קוד המקור של הנתיב עצמו אינו מכיל קריאת `fetch(`;
פעילות הרשת מתרחשת אך ורק בתוך `syncRadarReferrals()`, בהתאם לאותו עיקרון של
מטמון מקומי בלבד כמו ב-`/api/radar/catalog`.

### ממשק לוח הבקרה — הלשונית "קרדיטים בחינם" ב-`/dashboard/radar`

נעשה שימוש חוזר בעמוד Radar הקיים (`src/app/(dashboard)/dashboard/radar/page.tsx`) בתור
לשונית שנייה במקום נתיב חדש — פחות שטח פנים של ניתוב/i18n עבור יכולת שהיא
וריאציה של נתונים שהעמוד כבר מאחזר. לאחר הצטרפות, סרגל הלשוניות מציע
**קטלוג** (הטבלה הקיימת) ו-**קרדיטים בחינם**:

- קישורים קבועים מקובצים לפי ספק, וכל אחד מציג את `requiredAction` (כאשר קיים)
  וכפתור עם `target="_blank" rel="noopener noreferrer"` לכתובת ההפניה.
- קמפיינים מציגים את אותם הפרטים, בתוספת `validUntil` כאשר הוא קיים.
- כאשר `campaigns` ריק **וגם** הרמה שסופקה היא `community`, ממשק המשתמש מציג
  הערת שדרוג קצרה ("קמפיינים לזמן מוגבל הם תוספת לתומכים") — הערה זו **לעולם אינה**
  מסתירה או חוסמת את רשימת הקישורים הקבועים, שנותרת מלאה עבור כל רמה. הודעת
  השדרוג היא מסר עדין בלבד, ולעולם אינה חסימה.

### קישור הפניה בשם הספק (לוח הבקרה של הספקים)

`ProviderPageHeader` (`src/app/(dashboard)/dashboard/providers/[id]/components/`)
כבר קישר את שם הספק אל `providerInfo.website` כאשר הוא קיים, עם תקדים אחד
לקישור ממוסחר: הערת קישור השותפים של Kimi (Moonshot AI)
(מפתח ה-i18n‏ `providers.kimiPartnerLinkNote`). ‏D28 עושה שימוש חוזר בדיוק באותה תבנית
של הערה דיסקרטית עבור הפניות ברירת המחדל של Radar, במקום להוסיף מפתח חדש.

צימוד רופף, במכוון:

- `resolveProviderHeaderLink()` (`src/app/(dashboard)/dashboard/providers/providerPageUtils.ts`)
  היא פונקציה **טהורה** — `(staticWebsite, referralUrl) => { website, isReferralLink }`
  — ללא תלות ב-`@/lib/radar` או ב-`@/lib/db/*`. הקובץ `providerPageUtils.ts`
  כולו נותר ללא הייבואים האלה (כפי שמאומת על ידי
  `tests/unit/provider-header-referral-link.test.ts`).
- `ProviderDetailPageClient.tsx` (רכיב `"use client"`) הוא המקום היחיד שמורשה
  לאחזר נתוני Radar — באמצעות `fetch("/api/radar/referrals")`, אותה תבנית של נתיב
  מקומי שבה משתמש עמוד לוח הבקרה של Radar עצמו — והוא מחשב בצד הלקוח את הפניית ברירת
  המחדל באמצעות `findDefaultReferral()` מתוך `src/lib/radar/referrals.ts`, שאינו תלוי במסד הנתונים.
- כאשר `RADAR_ENABLED` כבוי, האחזור מחזיר 404, הערך `referralUrl` נשאר `null`,
  ו-`resolveProviderHeaderLink()` מחזירה את `website` הסטטי מהקטלוג ללא שינוי — עמוד
  הספק זהה ברמת הבתים למצבו לפני שהיכולת הזו הייתה קיימת. אותה תוצאה מתקבלת כאשר
  עדיין אין מטמון או כאשר אין הפניית ברירת מחדל עבור אותו ספק מסוים.
- כאשר חלה הפניית ברירת מחדל, `ProviderPageHeader` מקבל את `isReferralLink`
  ומציג את אותה הערה/חלונית מידע דיסקרטית כמו קישור השותפים של Kimi (תוך שימוש חוזר
  במפתח `providers.kimiPartnerLinkNote`) — לעולם לא עיצוב חזותי חדש ונפרד.

## כיצד לארח feed באופן עצמאי

Fork או מארח עצמאי שמעוניין בשליטה מלאה בקטלוג יכול להפעיל שירות feed משלו
מבלי לשנות את קוד הלקוח:

1. ספקו נקודת קצה `GET /v1/catalog/latest` שמחזירה גוף JSON התואם ל-
   `RadarFeedSchema` (`src/lib/radar/feedSchema.ts`) — ברמה העליונה `feed:
"omniroute-radar"`, `schemaVersion: 2`, `version`, `tier`, `providers`, `models`,
   `quirks` ו-`totals`. כבדו את `x-omniroute-radar-schema: 2`; שרת התואם לתקופת המעבר
   צריך להפנות כברירת מחדל בקשות שאינן כוללות אותו לפריט v1 שנחתם בנפרד.
2. חתמו על בתי התגובה המדויקים באמצעות זוג מפתחות Ed25519 והחזירו את החתימה בקידוד base64
   בכותרת התגובה `x-omniroute-feed-signature`.
3. הגדירו את `RADAR_FEED_URL` לכתובת ה-URL הבסיסית החדשה ואת `RADAR_FEED_PUBKEY` למפתח
   הציבורי התואם (base64-DER SPKI או PEM) — ראו
   [הפניה למשתני סביבה](../reference/ENVIRONMENT.md#27-radar-feed-self-hosting).
4. הפעילו את `RADAR_ENABLED` ובחרו להצטרף באמצעות `POST /api/radar/settings`
   (`{ optIn: true }`).

אין צורך בשינויי קוד נוספים — `verifyFeedBytes()` משתמש אוטומטית בהגדרה החלופית
(`getFeedPublicKeys()` בתוך `src/lib/radar/pinnedKeys.ts`), והשוואת גרסאות,
אימות הסכימה וכללי המיזוג חלים באופן זהה על feed באירוח עצמי.

קישורי הפניה (ראו [קישורי הפניה (קרדיטים בחינם)](#referral-links-free-credits)
לעיל) הם פריט נפרד ואופציונלי: fork שמספק רק את `/v1/catalog/latest`
עדיין פועל באופן מלא — `syncRadarReferrals()` חוזר באופן מדורג ל-`{ status: "error" }` בעת קבלת `404`
מ-`/v1/referrals/latest`, והמטמון פשוט נשאר ריק, כך ש-
`GET /api/radar/referrals` ממשיך להחזיר `{ fixed: [], campaigns: [], tier: null }`
במקום להכשיל את שאר הדף. כדי להציע גם קישורי הפניה, ספקו
`GET /v1/referrals/latest` התואם ל-`RadarReferralsFeedSchema`
(`src/lib/radar/referralsFeedSchema.ts`) וחתמו עליו באמצעות אותו זוג מפתחות Ed25519 המשמש
ל-feed הקטלוג.

הצעות לתומכים הן פריט אופציונלי נוסף. כדי לספק אותן, ממשו
`GET /v1/offers/latest` עם `RadarOffersFeedSchema` הסגורה
(`src/lib/radar/offersFeedSchema.ts`), דרשו זכאות פעילה, החזירו
`x-omniroute-feed-tier: live`, וחתמו על הבתים המדויקים באמצעות אותו מפתח. ב-fork שמשמיט נקודת קצה זו,
התנהגות הקטלוג וההפניות נשארת ללא שינוי; רענון ההצעות נכשל ללא פגיעה במידע הקיים,
ומטמון ההצעות המקומי האחרון שאומת נשאר זמין.

Intel הוא אופציונלי באותו אופן. מארח עצמאי יכול לספק את `GET /v1/intel/latest` באמצעות
`RadarIntelFeedSchema` (`src/lib/radar/intelFeedSchema.ts`), לדרוש זכאות פעילה, להחזיר
`x-omniroute-feed-tier: live`, ולחתום על הבתים המדויקים באמצעות מפתח Ed25519 המשותף. השמטת
נקודת הקצה משאירה את הקטלוג, ההפניות וההצעות ללא שינוי; רענון Intel משמר כל תמונת מצב מקומית
אחרונה שאומתה.
