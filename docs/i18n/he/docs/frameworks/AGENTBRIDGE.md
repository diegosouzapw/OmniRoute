AgentBridge הוא פרוקסי ה-MITM (אדם בתווך) של OmniRoute, שמיירט תעבורת HTTPS מסוכני AI בסביבות פיתוח משולבות ומנתב אותה מחדש דרך מנוע הניתוב המאוחד של OmniRoute. הוא תומך ב-**10 סוכני IDE** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code ו-Trae (בבדיקה) — ובכך הופך את OmniRoute לפרוקסי ה-MITM בעל הכיסוי הרחב ביותר בשוק עבור עוזרי תכנות מבוססי AI.

**מיקום בלוח הבקרה:** `/dashboard/tools/agent-bridge`
**קבוצה בסרגל הצד:** כלים (אחרי סוכני ענן)
**ראו גם:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — ניטור כל התעבורה המיורטת בזמן אמת; `docs/security/MITM-TPROXY-DECRYPT.md` (ב-git; אינו נכלל בהידור אל `/docs`) — מצב הלכידה לפענוח שקוף באמצעות TPROXY ב-Linux, המופעל דרך הנתיב `/api/tools/agent-bridge/tproxy`.

## §1 סקירה כללית

### מהו AgentBridge?

כאשר סוכן IDE (למשל GitHub Copilot, Cursor או Claude Code) מבצע קריאת API, הוא מתחבר ישירות לספק ה-AI שמעלה הזרם (OpenAI, Anthropic וכדומה). AgentBridge מיירט את החיבור באופן שקוף ברמת TLS — ללא צורך בשינוי כלשהו בתצורת הסוכן — ומשכתב את הבקשה כך שתעבור דרך OmniRoute.

כך ניתן:

- **לנתב מחדש כל סוכן לכל ספק**: Copilot מתקשר עם OpenAI? הפנו אותו אל Anthropic Claude, Gemini או כל אחד מ-352 הספקים של OmniRoute.
- **להחיל מיפויי מודלים**: `gemini-3-flash` → `claude-sonnet-4.7` באופן שקוף ברמת המטפל.
- **לצפות בכל תעבורת הסוכנים**: כל בקשה מיורטת מתפרסמת ב-[מפקח התעבורה](./TRAFFIC_INSPECTOR.md).
- **להחיל את מנגנוני העמידות של OmniRoute**: ניתוב משולב, מפסקי מעגל, חלופות ומעקב עלויות פועלים גם עבור תעבורת סוכני IDE.

## §2 ארכיטקטורה

### 2.1 סקירת הרכיבים

```
סוכן IDE‏ (VS Code / Cursor / וכו׳)
    │  HTTPS (יציאה 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← הפניית DNS
    │
    ▼
src/mitm/server.cjs  (יציאה 443, תהליך צאצא מסוג CJS)
    │  פותר את יעד הבקשה לפי SNI של כותרת Host
    │  יוצר אישור TLS ייעודי לכל SNI, חתום בידי רשות האישורים של AgentBridge
    ├── התאמה לרשימת העקיפה? → העברת TCP ישירה (ללא פענוח)
    ├── התאמה ליעד? → fetch → נתב OmniRoute (יציאה 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() על גוף הבקשה/הכותרות
    │               ├── TrafficBuffer.push() — מפרסם אל Traffic Inspector
    │               └── fetchRouter() → /v1/chat/completions
    └── אין התאמה? → העברת TCP ישירה (ללא פענוח)
```

### 2.2 שרת MITM‏ (`src/mitm/server.cjs`)

שרת ה-MITM המרכזי פועל כתהליך צאצא מסוג CJS של Node.js (כדי להימנע משכתוב בסיס הקוד הקיים ב-CJS). הוא:

- מאזין ביציאה 443 (דורש הרשאות מתאימות או `authbind`/`setcap`)
- מקבל מנהרות CONNECT ממערכת ההפעלה (באמצעות הפניית DNS דרך `/etc/hosts`)
- יוצר אישורי TLS ייעודיים לכל SNI, החתומים בידי רשות האישורים של AgentBridge‏ (`DATA_DIR/mitm/ca.crt`)
- פותר את סוכן היעד לפי כותרת Host באמצעות המרשם `targets/index.ts`
- מעביר לשכבת המטפל של TypeScript באמצעות HTTP אל `http://127.0.0.1:20128`

`TARGET_HOSTS` נטען מתוך `DATA_DIR/mitm/targets.json` (שנכתב בידי `targets/index.ts` בעת האתחול), ובכך מאפשר עדכונים דינמיים ללא הפעלה מחדש של שרת ה-CJS.

> **מודל רשות אישורים בסיסית (#6684).** התיאור לעיל של אישור ייעודי לכל SNI החתום בידי רשות אישורים
> הוא מודל רשות האישורים הבסיסית המתמיד שנוסף ב-#6684 (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, תוך שימוש חוזר בקריפטוגרפיית רשות האישורים/אישור הקצה שכבר
> הוכחה עבור TPROXY ב-`src/mitm/tproxy/dynamicCert.ts`) — הוא מחליף את
> אישור הקצה הסטטי והישן, החתום עצמית (`src/mitm/cert/generate.ts`, שעדיין
> מוגבל רק למארחי antigravity), שעל קיומו מצביע צמד חשוף של `server.crt`/`server.key`
> בדיסק. **התנהגות ההעברה**: התקנה חדשה (ללא `server.crt` קודם)
> מקבלת את מודל רשות האישורים הבסיסית באופן אוטומטי; התקנה שכבר
> נתנה אמון באישור הקצה הסטטי הישן ממשיכה להשתמש בו עד שהמפעיל מגדיר
> `MITM_ROOT_CA_ENABLED=true` ומפעיל מחדש את הגשר (`src/mitm/cert/migration.ts`
> היא פונקציית ההחלטה הטהורה — רשות אישורי MITM מהימנה שיכולה לחתום על אישור קצה עבור
> **כל** מארח היא בעלת עוצמה מהותית רבה יותר מאישור הקצה הישן בעל רשימת ה-SAN הקבועה, ולכן
> המעבר לעולם אינו שקט בהתקנה שכבר נתנה בו אמון). אישור רשות האישורים מותקן
> באותו מיקום `omniroute-mitm.crt` במאגר האישורים המהימנים שבו השתמש אישור הקצה הישן
> (`cert/install.ts::installCaCert`) — אין צורך בניקוי אמון כפול.

### 2.3 בסיס המטפל (`src/mitm/handlers/base.ts`)

כל מטפלי הסוכנים יורשים את `MitmHandlerBase`:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // כלי עזר מוגנים: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

כל מטפל קורא ל-`hookBufferStart()` לפני ביצוע התיווך ול-`hookBufferUpdate()` עם השלמתו. קריאות אלה דוחפות רשומות `InterceptedRequest` אל `globalTrafficBuffer` (ראו [מפקח התעבורה](./TRAFFIC_INSPECTOR.md) §4).

### 2.4 מרשם היעדים (`src/mitm/targets/`)

לכל סוכן יש קובץ יעד הצהרתי:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

המרשם (`targets/index.ts`) מייצא את `ALL_TARGETS` ופולט את `DATA_DIR/mitm/targets.json` בעת האתחול.

### 2.5 העברה ישירה ורשימת עקיפה (`src/mitm/passthrough.ts`)

**רשימת עקיפה** (נבדקת ראשונה ובעדיפות על פני התאמה ליעד):

- דפוסי ברירת מחדל: מארחים בנקאיים, `.gov.`, ספקי OAuth/SSO‏ (Okta, Auth0) וכו׳
- דפוסי משתמש: נשמרים בטבלת מסד הנתונים `agent_bridge_bypass`
- מארחים שנעקפו מקבלים מנהרת TCP שקופה — תעבורת TLS **לעולם אינה מפוענחת**

**ברירת המחדל להעברה ישירה** (אין התאמה ליעד והיעד אינו ברשימת העקיפה):

- גם במקרה זה מתקבלת מנהרת TCP — החיבורים לעולם אינם מנותקים
- מונעת מ-AgentBridge לשבש תעבורת HTTPS כללית של המערכת

סדר העדיפויות בניתוב:

```
רשימת עקיפה → התאמה ליעד → העברה ישירה
```

### 2.6 אישור רשות אישורים במעלה הזרם (`src/mitm/upstreamTrust.ts`)

עבור סביבות רשת ארגוניות עם רשות אישורים מותאמת אישית:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

כאשר משתנה זה מוגדר, הוא מגדיר את המנתב הגלובלי של `undici` עם אישור רשות האישורים הנוסף, וכך מאפשר ל-AgentBridge להגיע לספקים במעלה הזרם דרך שרתי Proxy ארגוניים לסיום TLS.

### 2.7 מיסוך סודות (`src/mitm/maskSecrets.ts`)

הסורק העצמאי, שפותח בגישת clean-room, מוחל על גופי בקשות ועל כותרות המכילות פרטי גישה
**לפני** שהם נכנסים למאגר של Traffic Inspector או ליומן כלשהו. הוא מבצע מעבר ליניארי יחיד:

- אסימונים בעלי הקידומת `sk-` / `ak-` / `pk-` (בסגנון OpenAI/Anthropic)
- פרטי גישה מסוג RFC 6750‏ `Authorization: Bearer <token>`, עם עדיפות לאסימון השלם
- אסימונים אטומים וארוכים כלליים (40 תווים ומעלה), לרבות צורות מנוקדות ומרופדות

`sanitizeHeaders()` ממירה שמות שנשמרו לאותיות קטנות, מצרפת ערכי מערכים באופן דטרמיניסטי, משמיטה את
רשימת החסימה המשותפת של כותרות hop-by-hop/מסגור (כולל אימות Proxy), משחירה לחלוטין את `cookie` ואת
`set-cookie`, ומעבירה את ערכי פרטי הגישה לסורק.

## §3 הגדרה

### 3.1 הפעלה/עצירה של שרת ה-MITM

השתמשו בכרטיס שרת AgentBridge ב-`/dashboard/tools/agent-bridge`:

| פעולה                | תיאור                                                                    |
| -------------------- | ------------------------------------------------------------------------ |
| הפעלת השרת           | מפעילה את `src/mitm/server.cjs` ביציאה 443                               |
| עצירת השרת           | מכבה באופן מסודר את תהליך הבן                                            |
| הפעלה מחדש           | עצירה + הפעלה (מחילה שינויים ביעד)                                       |
| מתן אמון באישור      | מתקינה את `DATA_DIR/mitm/ca.crt` במאגר האישורים המהימנים של מערכת ההפעלה |
| הורדת האישור         | מורידה את `ca.crt` להתקנה ידנית                                          |
| יצירה מחדש של האישור | יוצרת זוג מפתחות CA חדש (כל האישורים הקיימים לכל סוכן מבוטלים)           |

### 3.2 מתן אמון באישור

מערכת ההפעלה חייבת לתת אמון באישור ה-CA של AgentBridge לפני שסביבות הפיתוח יקבלו את חיבור ה-MITM.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

לחלופין, השתמשו בכפתור "מתן אמון באישור" בלוח הבקרה (הוא מריץ את הפקודה המתאימה למערכת ההפעלה שלכם, עם בקשת sudo במקרה הצורך).

#### סביבות פיתוח המבוססות על Electron מתעלמות ממאגר האישורים המהימנים של מערכת ההפעלה (`NODE_EXTRA_CA_CERTS`)

סביבות פיתוח מסוימות — ובמיוחד **Antigravity IDE**, וכן יישומים אחרים המבוססים על Electron / VS Code — כוללות
סביבת ריצה מובנית משלהן של Node.js, אשר **אינה בודקת את מאגר האישורים המהימנים של מערכת ההפעלה** עבור בקשות
`fetch`/HTTPS יוצאות. מתן אמון ב-CA ברמת מערכת ההפעלה/NSS מספיק עבור **הקצה האחורי** המקורי של סביבת הפיתוח
(לדוגמה, שרת שפה ב-Go המשתמש בחבילת ה-CA של מערכת ההפעלה), אך **הממשק הקדמי של Electron** עדיין
ייכשל ב-TLS — הדבר יתבטא בכך שהיישום יוצג כמי ש_נותק ממנו החשבון_ או יציג _"שגיאת חיבור"_,
אף על פי שיומן ה-MITM מראה שקריאות האתחול של הקצה האחורי מחזירות `200`. נדרשים שני שלבים,
ושניהם חשובים:

1. הפנו במפורש את סביבת הריצה אל ה-CA:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **הפעילו את סביבת הפיתוח מתוך אותו shell.** הפעלה מסמל שולחן העבודה / Dock / תפריט ההתחלה
   **אינה** יורשת משתנים שיוצאו ב-shell, ו-`~/.config/environment.d/*.conf` חל רק לאחר
   התחברות גרפית חדשה. תחילה צאו לחלוטין מסביבת הפיתוח — נעילת המופע היחיד של Electron גורמת לכך שהפעלה
   שנייה רק מעבירה את המיקוד לתהליך הקיים, והסביבה החדשה אינה נקלטת.

שלב מתן האמון במערכת ההפעלה + NSS שלעיל עדיין נדרש (מחסנית הרשת של Chromium, המשמשת תהליכי אימות
מסוימים, קוראת את מאגר ה-NSS של המשתמש, ויש לה הצמדות סטטיות משלה עבור `*.googleapis.com` ש-CA
מהימן מקומי עוקף). `NODE_EXTRA_CA_CERTS` מכסה בנוסף לכך את נתיב ה-`fetch` של Node.

### 3.3 ניתוב DNS

עבור כל סוכן שברצונכם ליירט, מארחי ה-API שלו חייבים להיפתר ל-`127.0.0.1`. AgentBridge מנהל אוטומטית רשומות ב-`/etc/hosts` כאשר אתם מפעילים או משביתים DNS עבור סוכן באשף ההגדרה.

דוגמה לרשומות `/etc/hosts` עבור GitHub Copilot:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 מיפוי מודלים

השתמשו בטבלת מיפוי המודלים שבכל כרטיס סוכן כדי להגדיר מיפויי מקור → יעד:

| מודל מקור (מקורי לסוכן) | מודל יעד (OmniRoute) |
| ----------------------- | -------------------- |
| `gpt-4o`                | `claude-sonnet-4.7`  |
| `*` (תו כללי)           | `claude-haiku-4.7`   |

התו הכללי `*` ממפה כל מודל שאינו מזוהה ליעד שצוין. המיפויים נשמרים בטבלה `agent_bridge_mappings`.

> **טיפ — גלו את מזהי המודלים האמיתיים של הסוכן.** סביבת פיתוח עשויה לשלוח שמות מודלים השונים
> מהתוויות בממשק המשתמש שלה, ושמשתנים בין גרסאות עיקריות. לדוגמה, **Antigravity 2** שולחת
> דרך הרשת את `gemini-3.1-pro-low`,‏ `gemini-pro-agent` ו-`gemini-3.1-flash-lite` — ולא את
> `gemini-2.5-pro` המופיע בתיעוד ישן יותר. שלחו הודעת צ'אט אחת ללא מיפוי תואם: ה-MITM
> רושם ביומן את ערך ה-`model:` הנכנס המדויק ומעביר את הבקשה הלאה. מפו את הערך המילולי הזה, ואז
> הבקשה הבאה תיורט ותנותב ליעד שלכם.

### 3.5 הודעת סיכון

AgentBridge מיירט פרטי אימות (אסימוני OAuth, מפתחות API) שבהם סביבת הפיתוח משתמשת כדי לבצע אימות מול ספקים במעלה הזרם. פרטים אלה **ממוסכים לפני הרישום ביומן** (ראו §2.7), אך גלויים לשכבת ה-MITM של OmniRoute. בהפעלה הראשונה של כל סוכן מוצג חלון הודעת סיכון שניתן לסגור.

### 3.6 תחזוקה ואבחון

לוח הבקרה מציג כרטיס **תחזוקה ואבחון** (`AgentBridgeMaintenanceCard`, בתוך `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`) החושף נתיבי MITM תפעוליים שבעבר לא היה להם ממשק משתמש. כותרת המשנה שלו: _"בדקו עצמאית את צינור הלכידה, בטלו מצב מערכת שנותר מאחור והעבירו את ההגדרה שלכם בין מחשבים."_ פונקציות העזר של לקוח הכרטיס נמצאות ב-`src/lib/inspector/agentBridgeMaintenanceApi.ts`.

| כפתור           | נתיב                                   | מה הוא עושה                                                                                                                                                               |
| --------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **אבחון**       | `GET /api/tools/agent-bridge/diagnose` | מריץ את הבדיקה העצמית של צינור הלכידה ומציג דוח לכל בדיקה (✓/✗ + הצעה לתיקון).                                                                                            |
| **תיקון**       | `POST /api/tools/agent-bridge/repair`  | מבטל מצב מערכת יתום של MITM (רשומות התחזות DNS, רשות אישורים בסיסית, פרוקסי מערכת) שנותר לאחר קריסה או SIGKILL. אידמפוטנטי — מדווח "אין מה לתקן" כשהמצב נקי.              |
| **הסרת CA**     | `DELETE /api/tools/agent-bridge/cert`  | מבטל את האמון ברשות האישורים הבסיסית של MITM ומסיר אותה ממאגר האמון של מערכת ההפעלה (מפורש, אידמפוטנטי). מוצג רק כאשר ה-CA מהימן כעת; מחייב אישור מקוון "להסיר את ה-CA?". |
| **ייצוא תצורה** | `GET /api/tools/agent-bridge/config`   | מוריד את קובץ ה-JSON הנייד של התצורה (ראו §3.7).                                                                                                                          |
| **ייבוא תצורה** | `POST /api/tools/agent-bridge/config`  | מעלה קובץ JSON של תצורה שיוצא בעבר (ראו §3.7).                                                                                                                            |

**בדיקות אבחון** (`summarizeDiagnostics()` בתוך `src/mitm/inspector/diagnostics.ts`). הנתיב מריץ את הבדיקה בעלת תופעות הלוואי עבור כל פריט ומעביר את הערכים הבוליאניים למסכם הטהור; מוחזרים פסק דין יחיד של `healthy` וכן הצעה לכל כשל:

| שם הבדיקה          | מה היא מאמתת                                              | הצעה במקרה של כשל                                                                                                                                  |
| ------------------ | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | תהליך שרת ה-MITM פעיל                                     | "שרת ה-MITM אינו פועל. הפעילו אותו מהלשונית AgentBridge."                                                                                          |
| `server-reachable` | שרת ה-MITM מקבל חיבורים ביציאה שלו (בדיקת TCP)            | "שרת ה-MITM אינו מקבל חיבורים ביציאה שלו. ודאו שהיציאה פנויה ושיש לכם הרשאות להיקשר אליה."                                                         |
| `cert-exists`      | אישור ה-MITM נוצר בדיסק                                   | "טרם נוצר אישור MITM. צרו אחד מהלשונית AgentBridge."                                                                                               |
| `cert-trusted`     | רשות האישורים הבסיסית של MITM נמצאת במאגר האמון של המערכת | "מערכת ההפעלה אינה נותנת אמון ברשות האישורים הבסיסית של MITM, ולכן יירוט TLS ייכשל. תנו אמון באישור מהלשונית AgentBridge."                         |
| `dns-configured`   | מתבצעת התחזות לשמות המארחים היעד בתוך `/etc/hosts`        | "לא מתבצעת התחזות לשמות המארחים היעד בתוך /etc/hosts, ולכן התעבורה לעולם אינה מגיעה לפרוקסי. הפעילו DNS עבור הסוכנים שאת התעבורה שלהם תרצו ללכוד." |

**כרזת מצב יתום:** כאשר הדף מזהה מצב שנותר לאחר קריסה (התחזות DNS /‏ CA / פרוקסי מערכת), הכרטיס מציג כרזה בצבע ענבר — _"הפעלה קודמת הותירה מאחור מצב מערכת (התחזות DNS,‏ CA או פרוקסי מערכת). הריצו תיקון כדי לנקות אותו."_ — ומדגיש את הכפתור **תיקון**. `Repair` הוא המקבילה בשכבת היישום לדגל `--cleanup` של ProxyBridge (הוא מעביר את הטיפול אל `repairMitm()` בתוך `src/mitm/manager.ts`).

> רשות האישורים הבסיסית של MITM נשארת מותקנת בין עצירה להפעלה כדי למנוע בקשות sudo
> חוזרות (אותה התנהגות כמו mitmproxy/Charles), ולכן הסרתה היא פעולה מפורשת של
> **הסרת CA** ולא פעולה שמתרחשת אוטומטית בעת עצירה.

### 3.7 ייבוא/ייצוא של תצורה ניידת

AgentBridge יכול לסדר את המצב **הניתן לכוונון בידי המפעיל** בתוך אובייקט JSON בעל גרסה, כדי לאפשר שכפול של התקנה בין מחשבים. הסריאלייזר הוא `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`), והוא מאומת באמצעות `AgentBridgeConfigSchema`.

הייצוא כולל בדיוק שלושה חלקים (ברירות המחדל המובנות **אינן** מיוצאות בכוונה, כך שהייבוא לעולם אינו משכפל אותן או מתנגש בהן):

| שדה              | מקור                                                                 | הערות                                                             |
| ---------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `bypassPatterns` | דפוסי מעקף שהוגדרו בידי המשתמש (`agent_bridge_bypass`)               | דפוסי ברירת המחדל של בנקים/ממשלה/okta אינם נכללים                 |
| `customHosts`    | מארחים מותאמים אישית של Traffic Inspector (`inspector_custom_hosts`) | כל אחד: `{ host, kind: "llm"\|"app"\|"custom", label? }`          |
| `agentMappings`  | מיפויי מודלים לפי סוכן (`agent_bridge_mappings`)                     | `{ [agentId]: [{ source, target }] }` עבור כל סוכן שיש לו מיפויים |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**התנהגות הייבוא** (`POST /api/tools/agent-bridge/config`): דפוסי מעקף ומיפויים לפי סוכן **מוחלפים במלואם**; מארחים מותאמים אישית נוספים באופן **אידמפוטנטי** (`INSERT OR IGNORE`). התגובה מדווחת כמה פריטים מכל סוג הוחלו:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

מה **לא** נכלל בתצורה: מצב פעולת השרת, נתיבי אישורים, מצב DNS לכל סוכן, נתיב ה-CA במעלה הזרם והגדרות TPROXY — אלה הם מצב המארח/זמן הריצה, ולא העדפות ניידות.

### רשימת עקיפה עבור מארחים רגישים

רשימת העקיפה מבטיחה שמוסדות פיננסיים, ספקי OAuth/SSO ומארחים רגישים אחרים **לעולם לא יפוענחו**. תעבורת ה-TLS שלהם עוברת כמנהרת TCP שקופה — OmniRoute לעולם אינו רואה את הטקסט הגלוי.

דפוסי העקיפה המוגדרים כברירת מחדל כוללים:

- `*.bank.*`, `*.gov.*` (פיננסים/ממשל)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/זהות)
- `*.apple.com`, `*.icloud.com` (שירותי מערכת של Apple)

דפוסי עקיפה שהמשתמש הוסיף מאוחסנים בטבלה `agent_bridge_bypass` וגוברים על כל הגדרה אחרת.

### מיסוך סודות

`maskSecrets()` מתוך `src/mitm/maskSecrets.ts` מוחל:

- על כל גוף בקשה לפני `TrafficBuffer.push()`
- על כל כותרת לפני רישום ביומן או שידור

דפוסים: אסימונים עם התחיליות `sk-`/`ak-`/`pk-`, אסימוני `Bearer` ואסימונים כלליים באורך 40 תווים ומעלה.

### אישור CA של השרת במעלה הזרם

כאשר `AGENTBRIDGE_UPSTREAM_CA_CERT` מוגדר, הקובץ נקרא בעת ההפעלה. אם הנתיב קיים אך הקובץ אינו קריא, AgentBridge מתעד שגיאה ברורה ומסרב לפעול (כדי למנוע כשלי TLS שקטים בסביבות ארגוניות).

### מגבלות ידועות

- **פורט 443 דורש הרשאות מיוחדות**: ב-Linux, ‏AgentBridge דורש `setcap 'cap_net_bind_service=+ep'` על הקובץ הבינארי של Node, או הפעלה באמצעות `authbind`. אשף ההגדרה מציג הוראות המותאמות למערכת ההפעלה.
- **נדרשת הפעלה מחדש של ה-IDE**: לאחר הפניית ה-DNS, יש להפעיל מחדש את ה-IDE כדי שרזולוציית המארח החדשה תיכנס לתוקף.
- **אסימוני OAuth מקודדים בקוד**: סוכנים מסוימים (Kiro, Antigravity) מאחסנים באופן מקומי אסימוני רענון של OAuth. אלה שקופים ל-AgentBridge — הוא רואה את אסימון ה-`Bearer` בכל בקשה, והוא ממוסך לפני הרישום ביומן.
- **ממשקי Electron זקוקים ל-`NODE_EXTRA_CA_CERTS`**: סביבות IDE שממשק המשתמש שלהן פועל על סביבת זמן ריצה מובנית של Node/Electron מתעלמות ממאגר האמון של מערכת ההפעלה/NSS, ויש להפעיל אותן ממעטפת שבה `NODE_EXTRA_CA_CERTS` מוגדר (ראו §3.2). התסמין כאשר הוא חסר: הקצה האחורי של ה-IDE עובר אימות (ה-MITM מציג תגובות `200`), אך ממשק המשתמש נשאר מנותק.
- **התקנות מרובות של אותו IDE הן עצמאיות**: התקנת מערכת (למשל `/usr/share/antigravity/antigravity`) והתקנה מקומית למשתמש מסוג "Full" (למשל `~/AntigravityIDE_Full/antigravity-ide`) הן תהליכים נפרדים עם סביבות זמן ריצה משלהם — יש להפעיל מחדש כל אחת מהן עם ה-CA המוזרק. לפני ההפעלה מחדש, זהו איזו מהן פועלת לפי הנתיב לקובץ הבינארי שלה.
- **הזהות נקבעת על ידי הנחיית המערכת של הסוכן, ולא על ידי המודל המנותב**: כאשר ממפים מחדש מודל של סוכן לספק אחר, התשובה עדיין מצהירה על הזהות המקורית של הסוכן (למשל, Antigravity עונה "אני מופעל על ידי Gemini"), מפני שה-IDE מזריק זאת להנחיית המערכת. אמתו את הקצה האחורי בפועל באמצעות `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`), ולא באמצעות שאלה למודל מי הוא.

## §6 פתרון בעיות

### התנגשות ביציאה 443

אם תהליך אחר כבר מאזין ביציאה 443 (שרת אינטרנט, VPN וכו׳):

```bash
lsof -i :443          # איתור התהליך
sudo fuser -k 443/tcp  # סיום כפוי (יש להשתמש בזהירות)
```

לחלופין, הגדירו יציאה שאינה דורשת הרשאות מיוחדות בהגדרות AgentBridge והגדירו כללי הפניה מחדש של `iptables` / `pf`.

### האישור אינו מהימן

אם ה-IDE מציג שגיאות TLS לאחר הפעלת AgentBridge:

1. ודאו שהאישור הותקן: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) או `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. יישומים מסוימים מנהלים מאגר אמון משלהם (Firefox, Chrome ב-Linux). הפעילו שוב את "Trust Cert" ובדקו את מאגר האישורים הייעודי ל-NSS/Firefox.
3. הפעילו מחדש את ה-IDE לאחר מתן האמון — חיבורי TLS פעילים משתמשים במצב האמון הישן.

### ה-IDE מנותק / "שגיאת חיבור" למרות CA מהימן

תסמין: לאחר הפניית DNS ומתן אמון ב-CA, סביבת IDE המבוססת על Electron (למשל Antigravity)
נפתחת במצב **מנותק** או מציגה שגיאת אימות/חיבור, אף שיומן ה-MITM מראה שקריאות
האתחול (`loadCodeAssist`, `fetchAvailableModels`, …) מחזירות `200`.

הסיבה: סביבת זמן הריצה **Node/Electron המצורפת ל-IDE מתעלמת ממאגר האמון של מערכת ההפעלה**. צד השרת
המקורי (שרת שפה ב-Go) נותן אמון ב-CA של מערכת ההפעלה ומבצע אימות, אך ממשק ה-Electron
אינו עושה זאת — ולכן ממשק המשתמש סבור שהוא לא מקוון.

פתרון (שני השלבים): יצאו את `NODE_EXTRA_CA_CERTS=<ca.crt>` **והפעילו מחדש את ה-IDE מאותה
מעטפת**, ולא מסמל שולחן העבודה. תחילה צאו לחלוטין מה-IDE — נעילת המופע היחיד של Electron גורמת
לכך שהפעלה שנייה רק מעבירה את המיקוד לתהליך הקיים, והסביבה החדשה אינה נקראת. ראו §3.2.
מצב זה תואם לדיווח פתוח במעלה הזרם, שבו סוכן עצמאי פועל דרך MITM, אך גרסת ה-IDE
נכשלת באותה תצורה.

### ה-DNS לא הופץ

בדקו ש-`/etc/hosts` עודכן:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

נקו את מטמון ה-DNS:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### ה-IDE לא זוהה

הזיהוי האוטומטי משתמש בנתיבי התקנה נפוצים. אם הזיהוי נכשל אך ה-IDE מותקן:

- בדקו אם הקובץ הבינארי של ה-IDE נמצא במיקום לא תקני
- אשף ההגדרה עדיין פועל — כשל בזיהוי רק אומר שהתג לא יציג את נתיב ההתקנה

### שגיאות מטפל (אחזור ממקור במעלה הזרם נכשל)

אם AgentBridge מיירט אך כל הבקשות נכשלות:

1. ודאו שלפחות ספק אחד מחובר ב-`/dashboard/providers`
2. בדקו את יומני שרת OmniRoute:‏ `APP_LOG_LEVEL=debug` ב-`.env`
3. ודאו ש-`OMNIROUTE_BASE_URL` מצביע על נקודת הקצה הנכונה של הנתב (ברירת מחדל: `http://127.0.0.1:20128`)

## §8 מפת דרכים

### חקירת Trae

Trae הוא עוזר חדש יחסית לכתיבת קוד באמצעות AI. לפני מימוש מטפל:

1. יש לזהות את הקובץ הבינארי/ההרחבה בחנויות של VS Code / JetBrains או כיישום עצמאי
2. יש ללכוד תעבורה באמצעות mitmproxy כדי לגלות מארחי API ומבני נקודות קצה
3. יש לקבוע את מנגנון האימות
4. יש להעריך אם להתקדם או לא, על סמך תנאי השימוש והאפשרות לגלות את ה-API

עד להשלמת החקירה, הכרטיס של Trae בלוח המחוונים מציג תג "בחקירה" עם קישור "דיווח על היתכנות". שלד המטפל שב-`src/mitm/handlers/trae.ts` זורק שגיאת `Not yet implemented` מובנית.

### סוכנים בצבר המשימות (נדרש MITM — אין תמיכה בכתובת URL בסיסית מותאמת אישית)

הכלים הבאים אינם תומכים בכתובות URL בסיסיות מותאמות אישית בגרסאותיהם הנוכחיות, ולכן MITM הוא נתיב היירוט היחיד. הערכת ההיתכנות עדיין ממתינה:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — נפרד מ-Kiro IDE)
- **Cowork** (יישום שולחן העבודה של Anthropic)

הערה: GitHub Copilot CLI ≥v1.0.19 תומך ב-`COPILOT_PROVIDER_BASE_URL` — עבור כלי זה יש להשתמש בתצורה ישירה במקום ב-MITM.
