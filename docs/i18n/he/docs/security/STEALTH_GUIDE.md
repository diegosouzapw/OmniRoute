> **קהל יעד:** מהנדסים המתחזקים שילובי הסוואה ייעודיים לספקים.

OmniRoute משתלב עם ספקים ששירותי הקצה שלהם מבצעים באופן פעיל טביעת אצבע ללקוחות שאינם רשמיים (TLS JA3/JA4, סדר כותרות, מבנה גוף JSON, אסימוני שלמות). דף זה מתעד את משטחי ההסוואה ש-OmniRoute חושף ואת המקומות שבהם הם ממומשים.

## הודעה משפטית ואתית

תכונות ההסוואה קיימות כדי ש-OmniRoute יוכל לשמש כשכבת תאימות בין חשבונות רשמיים שבבעלות המשתמשים (Claude Code CLI, Codex, Antigravity, Cursor וכו׳) לבין ה-API המאוחד של OmniRoute. הן **אינן** מיועדות לעקיפת מנגנוני זיהוי הונאות, לשיתוף פרטי גישה או להפרת תנאי השירות של ספקים. המתחזקים מצפים מהמפעילים לציית ל-ToS של ספק המקור שעליהם הסכימו בעת יצירת החשבונות.

## שכבת טביעת האצבע של TLS

### `open-sse/utils/tlsClient.ts` — wreq-js (Chrome 124)

הפעלות `wreq-js` מתמידות נוצרות באופן עצל לכל תחום חשבון ופרוקסי שנפתר. מאגרי
`TlsClient` הכלל-תהליכיים מכילים לכל היותר 128 הפעלות המתחזות ל-**Chrome 124 ב-macOS** עבור
שירותי מקור הנמצאים מאחורי Cloudflare. הפעולה `TlsClient.fetch()` נכשלת באופן סגור כאשר סביבת הריצה הטבעית
אינה זמינה; קורא רשאי לבחור במפורש חלופה מחוץ למעטפת זו.

- פרופיל הפעלה: `browser: "chrome_124", os: "macos"`
- פתרון פרוקסי (לפי עדיפות): `HTTPS_PROXY` → `HTTP_PROXY` → `ALL_PROXY` (וגם באותיות קטנות)
- זמן קצוב: `TLS_CLIENT_TIMEOUT_MS` (יורש מ-`FETCH_TIMEOUT_MS`, ברירת המחדל היא 600000)
- ה-Response של `wreq-js` תואם ל-fetch (`headers`, `text()`, `json()`, `clone()`, `body`).
- מנגנון השגחה על הבית הראשון (`open-sse/utils/tlsFirstByteWatchdog.ts`, #12656): הפעולה `TlsClient.fetch()`
  נפתרת ברגע שכותרות שירות המקור מגיעות, ולכן `TLS_CLIENT_TIMEOUT_MS` לבדו אינו יכול להגביל גוף
  שלעולם אינו מפיק בית ראשון. `guardTlsFirstByte()` מתחרה בין פעולת ה-`read()` הראשונה של הגוף
  לבין `TLS_FIRST_BYTE_WATCHDOG_MS` (ברירת המחדל היא `10000`, הערך `0` משבית אותו); גוף תקין
  אינו מושפע, בעוד שגוף תקוע גורם לביטול קורא ה-wreq ומאפשר ללוגיקת החלופה הקיימת של TLS
  ב-`proxyFetch` לעבור למנגנון השיגור הישיר/דרך פרוקסי (בקשה שאינה בטוחה להפעלה חוזרת, למשל
  POST עם גוף, עדיין תזרוק שגיאה במקום להתבצע שוב ללא התראה).

### תעבורת ספקים מבוססת עוגיות אינטרנט — wreq-js 3.2.0

`open-sse/services/tlsClientBase.ts` הוא המתאם המשותף לחמש תעבורות עוגיות האינטרנט הייעודיות
המפורטות להלן. כל מעטפת ספק דקה בוחרת פרופיל דפדפן/מערכת הפעלה. המתאם
משתמש בטוען סביבת הריצה היחיד של wreq ובמאגר התעבורה שב-`open-sse/utils/tlsClient.ts`, עם מפתח המבוסס על
פרופיל + מערכת הפעלה + פרוקסי שנפתר, בעוד שכל בקשה משתמשת ב-`cookieMode: "ephemeral"`. לפיכך חשבונות
ובקשות חולקים חיבורים ברמת התעבורה, אך לעולם אינם חולקים הפעלת wreq או מאגר עוגיות.

| ספק        | פרופיל        | מערכת הפעלה מדומה | מדיניות סוף זרם              |
| ---------- | ------------- | ----------------- | ---------------------------- |
| Claude     | `chrome_146`  | Linux             | הכללת `[DONE]`               |
| Perplexity | `firefox_148` | macOS             | הכללת `event: end_of_stream` |
| Grok       | `chrome_146`  | Linux             | אי-הכללת `[DONE]`            |
| Notion     | `chrome_146`  | Windows           | הכללת `[DONE]`               |
| LMArena    | `chrome_146`  | Windows           | ללא סמן; סגירה ב-EOF טבעי    |

- הזרמה צורכת ישירות את `ReadableStream` הטבעי של התגובה; לא נוצרים קובץ זמני או תהליך נלווה.
- עד 256 בתים ראשוניים נבדקים לפני חשיפת זרם. ספקי SSE אוגרים שגיאות שאינן SSE;
  Grok/LMArena ממפים אתגרי Cloudflare ל-`403` ודפי ביניים של HTML ל-`502`.
- הזמן הקצוב הטבעי של הבקשה נותר עטוף במועד אחרון קשיח ומוחלט של JS. תקיעה פוסלת
  וסוגרת רק את תעבורת הפרופיל/מערכת ההפעלה/הפרוקסי שהושפעה, לפני שהבקשה הבאה יוצרת אותה מחדש.
- סדר העדיפות לפתרון פרוקסי הוא `proxyUrl` ברמת הקריאה → הקשר חשבון/לוח מחוונים ברמת הבקשה →
  `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` (כולל גרסאות באותיות קטנות). שגיאות פתרון נכשלות
  באופן סגור במקום לגרום לדליפת חיבור ישיר. LMArena פותר במכוון מול `arena.ai`.
- `byteResponse` מחזיר כתובת URL מסוג `data:` עם סוג תוכן, ללא השחתת UTF-8.
- השגיאות הן `TlsClientUnavailableError` (החבילה/התוסף אינם זמינים), `TlsClientHangError`
  (חריגה מהמועד האחרון) ו-`WreqTransportCapacityError` (קוד שגיאת הקיבולת המשותפת של ההפעלות)
  כאשר כל 128 משבצות הפרופיל/מערכת ההפעלה/הפרוקסי המוגבלות פעילות או נמצאות בתהליך סגירה.

הפעלת `TlsClient` הכללית שלעיל נותרת מותאמת למצב עוגיות מתמיד הנתמך בידי דפדפן.
שני הנתיבים עושים שימוש חוזר בטוען יחיד ומוטמן של מודול wreq וב-hook של מחזור חיי התהליך; המאגרים שלהם נותרים
נפרדים משום שתקופות החיים של העוגיות שלהם שונות במכוון.

הפרופילים נתמכים על ידי החבילה המוצמדת, אך הקבלה בפועל מצד WAF עשויה להשתנות ללא תלות
בבדיקות החוזה המקומיות. יש לאמת שינויים בטביעת האצבע מול חשבון פעיל שהשימוש בו אושר במפורש,
לפני שטוענים לשקילות מול דפדפן של ספק המקור.

## חבילת ההסוואה של Claude Code

כאשר `cliCompatMode` מופעל, OmniRoute מעצב מחדש בקשות Claude יוצאות כך שלא ניתן להבדיל ביניהן לבין תעבורה של `claude-cli`. שלושה מודולים פועלים יחד:

### `claudeCodeFingerprint.ts`

מחשב את טביעת האצבע בת 3 התווים `cc_version`, המוטמעת בכותרת החיוב:

```
SHA256(SALT + msg[4] + msg[7] + msg[20] + version)[:3]
```

- `FINGERPRINT_SALT = "59cf53e54c78"` (מקודד מראש; תואם ללקוח הרשמי)
- קלט: התווים באינדקסים 4, 7 ו-20 בטקסט של הודעת המשתמש הראשונה + מחרוזת הגרסה
- פלט: קידומת הקסדצימלית בת 3 תווים

### `claudeCodeCCH.ts` (גיבוב תוכן לקוח)

בדיקת תקינות בצד השרת, שממשק שורת הפקודה הרשמי של Claude Code מחשב באמצעות Bun/Zig. OmniRoute מממש אותה מחדש באמצעות `xxhash-wasm`:

1. המרת גוף הבקשה לסדרה עם מציין המיקום `cch=00000;`
2. `xxhash64(bytes, seed) & 0xFFFFF`
3. ערך הקסדצימלי באותיות קטנות, בן 5 תווים ומרופד באפסים
4. החלפת `cch=00000;` באסימון המחושב

קבועים:

- ערך התחלתי: `0x6e52736ac806831e`
- תבנית: `/\bcch=([0-9a-f]{5});/`

### `claudeCodeObfuscation.ts`

מוסיף **תו מחבר ברוחב אפס** של Unicode (`U+200D`) לאחר התו הראשון בשמות לקוח "רגישים", כדי שמסננים במעלה הזרם לא יוכלו לאתר אותם באמצעות grep. רשימת המילים המוגדרת כברירת מחדל:

```
opencode, open-code, cline, roo-cline, roo_cline, cursor, windsurf,
aider, continue.dev, copilot, avante, codecompanion
```

מוחל על: בלוקי `system`, כל `messages[].content`, וכן `tools[].description` / `tools[].function.description`. המפעיל יכול לדרוס את ההגדרה באמצעות `setSensitiveWords()`.

### `claudeCodeCompatible.ts` — ספקי `anthropic-compatible-cc-*`

עבור ממסרי Anthropic של צד שלישי שמקבלים רק תעבורה של "Claude Code אמיתי":

- `CLAUDE_CODE_COMPATIBLE_USER_AGENT = "claude-cli/2.1.258 (external, sdk-cli)"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_PACKAGE_VERSION = "0.112.1"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_RUNTIME_VERSION = "v26.3.0"`
- כברירת מחדל, `anthropic-beta = "claude-code-20250219,interleaved-thinking-2025-05-14,effort-2025-11-24"`
- המתג "Enable redact-thinking beta" לכל חיבור מוסיף את `redact-thinking-2026-02-12` כאשר ספק במעלה הזרם התואם ל-CC דורש במפורש זרמי חשיבה מושחרים
- המתג "Enable summarized thinking display" לכל חיבור שומר את `providerSpecificData.requestDefaults.summarizeThinking` ומוסיף `display: "summarized"` לבקשות חשיבה תואמות CC שלא הוגדר בהן קודם מצב תצוגה
- `CONTEXT_1M_BETA_HEADER = "context-1m-2025-08-07"` (משפחת Opus/Sonnet 4.x)
- נתיב ברירת המחדל: `/v1/messages?beta=true`

מודולים נלווים באותה חבילה:

- `claudeCodeConstraints.ts` — כללי טמפרטורה + בקרת מטמון
- `claudeCodeToolRemapper.ts` — מיפוי מחדש של שמות כלים
- `claudeCodeExtraRemap.ts` — נרמול נוסף של מטען הבקשה

## הסוואת Antigravity

בקשות Antigravity משמרות את טקסט הקורא בייט אחר בייט. OmniRoute אינו מוסיף תווים ברוחב אפס להנחיות ואינו משנה שמות של כלים או מזריק כלים כדי לחקות לקוח IDE.

### `antigravityHeaderScrub.ts`

מסיר סמנים של Stainless SDK (`x-stainless-lang`, `x-stainless-package-version`, `x-stainless-os`, `x-stainless-arch`, `x-stainless-runtime`, `x-stainless-runtime-version`, `x-stainless-timeout`, `x-stainless-retry-count`, `x-stainless-helper-method`) לפני ההעברה.

### ⚠️ סיכון: `ANTIGRAVITY_CREDITS=always` (מוקד סיכון לחסימת חשבון)

`ANTIGRAVITY_CREDITS=always` (נצרך על ידי `open-sse/executors/antigravity.ts`) מנתב **כל** בקשה דרך חריגות ממכסת נקודות הזכות של Antigravity AI (נקודות זכות בתשלום של Google), במקום לאפשר למכסת השכבה החינמית של Google להגביל את השימוש. הדבר מתועד כתכונה, אך זהו **הדיווח הנפוץ ביותר שאנו רואים על הפרת תנאי השירות** — מספר חשבונות Google Ultra נחסמו עם `403 / "service disabled for ToS violation" / insufficient_quota` לאחר שפעלו במשך כמה שעות עם `=always`.

האכיפה במעלה הזרם מתבצעת **בצד של Google**, ואינה דבר ש-OmniRoute יכול למנוע. שם משתנה הסביבה והתיעוד הקיים גורמים לאפשרות להישמע כמו מתג בטוח להפעלה; היא אינה כזו.

**מדוע הדבר גורר זיהוי שימוש לרעה באופן אגרסיבי יותר משימוש בשכבה החינמית בלבד:**

- הוצאה אוטומטית ומתמשכת בחשבון Google יחיד מסומנת באופן שונה מפגיעות בשכבה החינמית שמגיעות למכסה ואז נעצרות.
- לחריגות בתשלום אין תקרת קצב, ולכן לקוח שהוגדר באופן שגוי יכול לצרוך מאות דולרים בתוך דקות ולהיראות כמו מכירה מחדש של מפתחות API או תעבורת בוטים.
- מספר משתמשי OmniRoute הצורכים במקביל נקודות זכות מעבר למכסה מאותה כתובת IP חיצונית מחזקים את האות.

**גישה מומלצת:**

1. השאירו את ברירת המחדל `ANTIGRAVITY_CREDITS=off`, אלא אם המפעיל מקבל במפורש את הסיכון הכרוך בנקודות זכות בתשלום ובאכיפת החשבון. `retry` שולח תחילה את הבקשה הרגילה ומזריק נקודות זכות לכל היותר פעם אחת לאחר שגיאת מכסה מתאימה מסוג 429; `always` מזריק נקודות זכות כבר בבקשה הראשונה.
2. **פזרו את העומס בין ספקים באמצעות Auto-Combo** (`model: "auto"` או `kr/glm/etc`-combo), במקום להעמיס עד לרוויה על חשבון Antigravity יחיד.
3. **הגדירו מגבלות RPM לכל חיבור** בדף העריכה של ספק Antigravity (Dashboard → Providers → Antigravity → connection → rate limit). טווח של 30–60 RPM הוא גבול עליון סביר לשימוש מתמשך.
4. **השתמשו ברשת יציבה במעלה הזרם הנשלטת על ידי המפעיל**, והימנעו משיתוף חשבון יחיד בין משתמשים או עומסי עבודה שאינם קשורים זה לזה.
5. **במקרה של חסימה**: הגישו ערעור דרך `support.google.com` → "Restore Workspace/Account access", בצירוף גוף התגובה המדויק של `quota_exceeded` / `service disabled` שנשלח על ידי Google. שחזור החשבון אינו מובטח.

תיעוד משתני הסביבה מפרט את ההשלכות על החשבון ועל ההוצאות עבור כל מצב של נקודות זכות.

נקודות מגע:

- `open-sse/executors/antigravity.ts` — קורא את `process.env.ANTIGRAVITY_CREDITS`
- `src/lib/oauth/providers/antigravity.ts` — תשתית העברת פרטי ההזדהות
- דוח התקרית המקורי: דיון [#1183](https://github.com/diegosouzapw/OmniRoute/discussions/1183)

## מרשם טביעות אצבע של CLI — `open-sse/config/cliFingerprints.ts`

טבלה נפרדת לכל ספק, המקבעת את הסדר **המדויק** של הכותרות ושל שדות גוף ה-JSON כפי שנקלטו מעקבות mitmproxy של כלי ה-CLI הרשמיים. רשומים כעת: `codex`,‏ `claude`, וכן פרופילים הנגזרים בזמן ריצה ב-`providerHeaderProfiles.ts` עבור `antigravity` ו-`github`.

```ts
interface CliFingerprint {
  headerOrder: string[]; // תלוי רישיות
  bodyFieldOrder: string[]; // מפתחות JSON ברמה העליונה
  userAgent?: string | (() => string);
  extraHeaders?: Record<string, string>;
}
```

ניתן להפעיל או להשבית עבור כל ספק באמצעות משתני סביבה (ראו להלן). כאשר האפשרות מושבתת, הכותרות/מפתחות הגוף מופיעים בסדר שבו Node/JSON סיפקו אותם — ולכן קל לזהות את טביעת האצבע.

## פרוקסי MITM ‏(Antigravity,‏ Linux/macOS/Windows)

עבור כלי CLI שלא ניתן להפנות את הקבצים הבינאריים שלהם באמצעות `OPENAI_BASE_URL`,‏ OmniRoute מפעיל פרוקסי מקומי המסיים חיבורי TLS. נקודות הקצה נמצאות תחת `src/app/api/cli-tools/antigravity-mitm/`.

| שיטה   | נקודת קצה                               | מטרה                                         |
| ------ | --------------------------------------- | -------------------------------------------- |
| GET    | `/api/cli-tools/antigravity-mitm`       | מצב — פועל, pid, dnsConfigured, certExists   |
| POST   | `/api/cli-tools/antigravity-mitm`       | הפעלת MITM (דורשת `apiKey` + `sudoPassword`) |
| DELETE | `/api/cli-tools/antigravity-mitm`       | עצירת MITM                                   |
| GET    | `/api/cli-tools/antigravity-mitm/alias` | הצגת כינויי מודלים                           |
| PUT    | `/api/cli-tools/antigravity-mitm/alias` | שמירת כינויי מודלים עבור כלי                 |

המארח המיורט: **`daily-cloudcode-pa.googleapis.com`** (שרת המקור של Antigravity).

### רצף ההפעלה (`src/mitm/manager.ts::startMitm`)

1. יצירת אישור בחתימה עצמית באמצעות `selfsigned`‏ (RSA-2048,‏ SHA-256, שנה אחת) — `cert/generate.ts`
2. התקנת האישור במאגר האמון של המערכת — `cert/install.ts`
3. הוספת רשומת hosts‏ `127.0.0.1 daily-cloudcode-pa.googleapis.com` — `dns/dnsConfig.ts`
4. הפעלת `src/mitm/server.cjs` עם `ROUTER_API_KEY` + `MITM_LOCAL_PORT` (ברירת המחדל היא `443`)
5. שמירת ה-PID ב-`<DATA_DIR>/mitm/.mitm.pid`

### זיהוי דינמי של מאגר האמון ב-Linux — `cert/install.ts`

הפונקציה `getLinuxCertConfig()` עוברת על רשימה לפי סדר עדיפויות ובוחרת את התיקייה הקיימת הראשונה:

| משפחת הפצה               | תיקייה                                      | פקודת עדכון              |
| ------------------------ | ------------------------------------------- | ------------------------ |
| Debian / Ubuntu          | `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| Arch / CachyOS / Manjaro | `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| Fedora / RHEL / CentOS   | `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| openSUSE                 | `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

שם קובץ האישור: `omniroute-mitm.crt`. התאמת טביעת האצבע מתבצעת באמצעות `getCertFingerprint()`‏ (SHA-1 של DER).

בנוסף, `updateNssDatabases()` מתקינה את האישור במסדי נתונים של NSS עבור כל משתמש כאשר `certutil` זמין: `~/.pki/nssdb`,‏ `~/snap/chromium/.../nssdb`, כל פרופילי Firefox (כולל snap), תחת הכינוי **`OmniRoute MITM Root CA`**.

### macOS / Windows

- **macOS:**‏ `security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain`
- **Windows:**‏ PowerShell עם הרשאות מוגברות ← `certutil -addstore Root`

### אימות

כל נקודות הקצה של MITM דורשות אימות ניהולי (`requireCliToolsAuth`). סיסמת sudo נשמרת במטמון ברמת המודול (לעולם לא ב-`globalThis`) ונמחקת בעת `stopMitm()`.

## ניקוי כותרות נכנסות

OmniRoute מסיר כותרות מלקוחות נכנסים לפני ההעברה, כך שבקשה שמגיעה מ-Cursor אינה מדליפה `User-Agent: Cursor/X.Y.Z` לשירות Claude במעלה הזרם. רשימת החסימה נמצאת ב-`src/shared/constants/upstreamHeaders.ts` ונשמרת מסונכרנת עם סכמות Zod ובדיקות היחידה.

## עדכון טביעות אצבע כאשר ספק מבצע החלפה

1. לכידת תעבורת CLI רשמית באמצעות `mitmproxy` (יירוט TLS + שמירה)
2. חילוץ JA3/JA4 וסדר הכותרות המדויק
3. עדכון הרשומה הרלוונטית ב-`CLI_FINGERPRINTS[...]`
4. עדכון ברירת המחדל התואמת של `*_USER_AGENT` ב-`.env.example`
5. אם לחיצת היד של TLS עצמה השתנתה, יש לעדכן את מעטפת הספק הרלוונטית או את האפשרות `browser:` של wreq-js
6. הרצת בדיקות ה-TLS הייעודיות לספק ובדיקת קנרית ידנית מול הספק הפעיל
7. הפצה בגרסת תיקון; תיעוד ב-`CHANGELOG.md`
