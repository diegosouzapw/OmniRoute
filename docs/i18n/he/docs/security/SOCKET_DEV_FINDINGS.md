> **הערת תחולה:** `socket.yml` מגדיר את הסריקה של Socket.dev בצד הרישום לאחר פרסום של ארטיפקט npm (נתיבים שיש להתעלם מהם עבור תוכן שאינו מופץ, כגון `tests/`,‏ `docs/` ודוחות בנייה). הוא אינו מגדיר שער מיזוג של CI/PR — שום תהליך עבודה תחת `.github/workflows`, שום סקריפט ב-`package.json` ושום יעד ב-`Makefile` אינם מפעילים את Socket.dev.

מסמך זה הוא הצהרת האימות שחוברה על ידי המתחזקים עבור ששת הממצאים מסוג
`AI-detected potential malware` שדווחו לגבי `omniroute@3.8.5`, וכן עבור
אמצעי ההפחתה שיושמו ב-`omniroute@3.8.6`. מטרתו היא:

1. לספק למפעילי צינור האבטחה אסמכתה יחידה שיוכלו לצטט כאשר עליהם
   להעריך את הממצאים אל מול קוד המקור בפועל.
2. לאפשר לסורקי AI עתידיים לזהות את הטענה החתומה בידי המתחזקים, שלפיה כל
   נתיב שסומן הוא מכוון, דורש הסכמה מפורשת ומתועד.
3. להחזיק תיעוד כתוב המסביר _מדוע_ כל אתר קריאה בנוי כפי שהוא —
   כדי ששכתוב עתידי לא יציג מחדש בטעות טביעת אצבע
   שהוסרה במכוון.

אם אתם מפעילים סורק שמסמן מחדש אחד מאתרי הקריאה שלהלן לאחר פרסום
אמצעי ההפחתה של v3.8.6, אנא פתחו דיווח עם עקבת הסריקה,
ואנו נרחיב כאן את הצהרת האימות.

## §1 — התקנת רשות אישורים בסיסית לצורך MITM (`77484.js`)

**קובצי מקור**:

- `src/mitm/cert/install.ts` — הפונקציות הציבוריות `installCert()` / `uninstallCert()`,
  וכן `installCertWindows/Mac/Linux` הייעודיות לכל פלטפורמה.
- `src/mitm/systemCommands.ts` — פונקציות עזר משותפות עבור `execFile` / `spawn` / PowerShell
  המשמשות את נתיבי ההתקנה.

**גורם מפעיל**: המשתמש לוחץ על "הפעלת פרוקסי MITM" בלוח המחוונים המקומי בכתובת
`/dashboard/cli-tools/mitm`. הנתיב מוגבל ל-loopback בלבד — ראו כלל קשיח #17 בתוך
`CLAUDE.md` ואת `src/server/authz/routeGuard.ts::isLocalOnlyPath()`. JWT שדלף
ונחשף דרך מנהרה **אינו יכול** להפעיל נתיב קוד זה.

**פעולות מורשות המתבצעות (לפי פלטפורמה)**:

| מערכת הפעלה            | פקודות                                                                                                            |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | `certutil -addstore Root <cert>` באמצעות UAC                                                                      |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | עדכון מסד הנתונים NSS לכל פרופיל באמצעות `certutil -d sql:<profile>`                                              |

אלו אותן פקודות שבהן משתמשים `mitmproxy`,‏ Charles Proxy,‏ Fiddler ו-
Caddy. העובדה שהן קיימות ב-OmniRoute מתועדת ב-
`docs/security/STEALTH_GUIDE.md`.

**הפחתה ב-v3.8.6**:

- `runElevatedPowerShell()` אינה משתמשת עוד ב-`-EncodedCommand <base64utf16le>`.
  המטען המורץ בהרשאות מוגברות נכתב לקובץ `.ps1` זמני ונפרד לכל קריאה (במצב 0o600,
  בתוך ספריית `mkdtempSync` פרטית), ומופנה באמצעות `-File`. הקובץ
  נמחק בבלוק `finally`. שינוי זה מסיר את טביעת האצבע הקלאסית של
  העלאת הרשאות באמצעות PowerShell ו-base64, שסומנה על ידי מסווג ה-AI של
  Socket.dev.
- `installCertWindows` כוללת בלוק `SECURITY-AUDITOR-NOTE:` מוטמע
  שמפנה לכאן.

**מדוע אנו משאירים זאת**: פרוקסי ה-MITM הוא תכונה מתועדת המשמשת את
`docs/security/STEALTH_GUIDE.md` ואת `docs/frameworks/MITM-PROXY.md`. הסרתו
תפגע במכלול היכולות של גשר הסוכנים.

## §2 — ייבוא פרטי גישה מ-Zed (`app/api/providers/zed/import/route.js`)

**קובצי מקור**:

- `src/app/api/providers/zed/discover/route.ts` _(חדש ב-v3.8.6)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(חדש ב-v3.8.6)_

**גורם מפעיל**: המשתמש לוחץ על "ייבוא מ-Zed" בדף הספקים בלוח הבקרה המקומי.
הגישה לנקודת הקצה מוגנת באמצעות `requireManagementAuth`. עורך Zed עצמו
כותב את מפתחות ה-API של הספקים שלו לצרור המפתחות של מערכת ההפעלה תחת שמות
שירות מתועדים — ראו https://zed.dev/docs/ai/llm-providers.

**התנהגות v3.8.5 (זו שסומנה על ידי Socket.dev)**:

`POST /import` גילה את פרטי הגישה ושמר אותם אוטומטית במאגר SQLite המקומי
בסבב בקשה-תגובה יחיד. ללא אישור נפרד לכל חשבון, ללא טביעת אצבע, רק
"נמצאו N אסימונים, כולם יובאו."

**הפחתת הסיכון ב-v3.8.6 — אישור דו-שלבי**:

1. **`POST /api/providers/zed/discover`** מחזיר
   `{ candidates: [{ provider, service, account, fingerprint }] }`. האסימון
   הגולמי **לעולם אינו** מועבר. טביעת האצבע היא
   `sha256(service|account|token).slice(0,16)`.
2. לוח הבקרה מציג את רשימת המועמדים, המפעיל בוחר אילו מהם
   לייבא, ושולח `{ confirmedAccounts: [{ service, account, fingerprint }] }`
   אל **`POST /api/providers/zed/import`**.
3. נקודת הקצה לייבוא **קוראת מחדש את צרור המפתחות בשרת** ומסננת לפי
   `(service, account, fingerprint)`. תגובת גילוי ששובשה או נשלחה מחדש
   אינה יכולה לגרום לנקודת הקצה לייבוא לשמור אסימון שאינו קשור —
   אם האסימון הפעיל השתנה מאז הגילוי, טביעת האצבע כבר אינה
   תואמת ופרטי הגישה מדולגים.

דגל הסביבה `OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` משמר את ההתנהגות של
v3.8.5 עבור מפעילים שטרם עדכנו את האוטומציה שלהם. הוא יוסר ב-v3.9.

**מדוע אנו משאירים זאת**: ייבוא מ-Zed הוא נתיב הקליטה הידידותי ביותר למשתמשים
שכבר משתמשים ב-Zed ורוצים לשקף את מפתחות הספקים שלהם אל OmniRoute
מבלי להדביק אותם מחדש.

## §3 — `execFile` / `spawn` / PowerShell עם הרשאות מוגברות (`21843.js`)

**קובצי מקור**: `src/mitm/systemCommands.ts`.

**מדוע סומן**: המקטע מייצא מחדש את `execFileWithPassword`,
את `runElevatedPowerShell` ואת פונקציית העזר המשותפת `quotePowerShell`. המסווג
מבוסס ה-AI של Socket.dev מזהה אותם כ"ערכת כלים כללית להפעלה במארח ולהעלאת
הרשאות." בתוך OmniRoute הם משמשים רק את נתיב התקנת אישור ה-MITM
(§1) ואת `execFileWithPassword` להפעלת פקודות `sudo`.

**הפחתת הסיכון ב-v3.8.6**:

- ארגון מחדש של `runElevatedPowerShell` (ראו §1).
- בלוק `SECURITY-AUDITOR-NOTE:` מוטמע הן ליד
  `runElevatedPowerShell` והן ליד `execFileWithPassword`, ומתעד את הקוראים
  שברשימת ההיתרים ואת רשימת קובצי ההפעלה המקובעת.
- קריאת `spawn()` של `execFileWithPassword` כוללת סמן `nosemgrep` עם
  רשימת ההיתרים של קובצי ההפעלה שפונקציית העזר רשאית לקבל — **אין
  נתיב מקלט משתמש אל `finalCommand`/`finalArgs`**.

## §4 / §6 — מפקח השירות של 9router (`api/services/9router/{start,restart}/route.js`)

**קובצי מקור**:

- `src/app/api/services/9router/_lib.ts` — מפעל המפקח.
- `src/app/api/services/9router/{start,stop,restart,status,install,update,auto-start}/route.ts`.
- `src/lib/services/ServiceSupervisor.ts` — הפעלה כללית / תשאול תקינות / מאגר יומן.

**גורם מפעיל**: המשתמש לוחץ על "התקנה" / "הפעלה" בדף השירותים המוטמע
בלוח הבקרה המקומי.

**הגנות שכבר קיימות**:

- כל נתיבי `/api/services/*` הם LOCAL_ONLY בהתאם ל-
  `src/server/authz/routeGuard.ts` (כלל קשיח #17). אכיפת ממשק הלולאה החוזרת
  מתבצעת לפני כל בדיקת אימות — JWT שדלף אינו יכול להגיע אליהם.
- רשומת מסד הנתונים של 9router נוצרת עם `status='not_installed', auto_start=0` (ראו
  `src/lib/db/migrations/071_services.sql:19`). השירות **אינו** מופעל
  בהפעלה הראשונה.
- `spawn()` נקראת עם נתיב הקובץ הבינארי שמוחזר על ידי
  `resolveSpawnArgs(apiKey, PORT)` בתוך `src/lib/services/installers/ninerouter.ts`,
  שהוא רשימת היתרים קבועה של קבצים בינאריים נתמכים.
- Stdout/stderr נשמרים במאגר בזיכרון (מגבלה של 5 MB, ראו `_lib.ts`) — אין כתיבה
  לדיסק אלא אם המשתמש מפעיל רישום יומן מלוח הבקרה.

**הפחתת הסיכון ב-v3.8.6**: אין שינוי פונקציונלי. פרופיל הבנייה המינימלי
(`OMNIROUTE_BUILD_PROFILE=minimal`) מחליף את
`src/lib/services/installers/ninerouter.ts` במימוש דמה עבור משתמשים שרוצים
שהנתיבים בעלי ההרשאות המוגברות יוסרו פיזית מהחבילה.

**מדוע אנו משאירים זאת**: 9router הוא שירות נלווה אופציונלי שניתן להתקנה
מקומית (בדומה לתוסף בסגנון WordPress) — הצטרפות מפורשת בלבד.

## §5 — כתיבה חוזרת של פרטי אימות ב-OmniRoute Cloud Sync (`api/keys/[id]/route.js`)

**קובצי מקור**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`.
- `src/app/api/keys/[id]/route.ts` — מפעיל את `syncKeysToCloudIfEnabled()`.

**תנאי הפעלה**: `isCloudEnabled()` מחזירה `true` (מוגדר מלוח הבקרה) **וגם**
`CLOUD_URL` מוגדר. כאשר שניהם כבויים, לא מתבצעת קריאת רשת יוצאת אל נקודת הקצה
של Cloud.

**התנהגות v3.8.5 (הבאג ש-Socket.dev זיהה כראוי)**:

`updateLocalTokens()` החליפה את `accessToken`, את `refreshToken` ואת
`providerSpecificData` מתוך תגובת Cloud כאשר
`cloudUpdatedAt > localUpdatedAt`. ללא HMAC, ללא חתימה וללא סכום ביקורת.
`CLOUD_URL` שהוגדר באופן שגוי או עוין (או תוקף MITM בערוץ) היה יכול להחליף
אסימוני OAuth של ספקים ללא כל התרעה.

**הפחתת הסיכון ב-v3.8.6**:

1. **אימות HMAC**: הפונקציה `verifyCloudSignature(rawBody, sigHeader)` בודקת
   את הכותרת `X-Cloud-Sig` (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`) לפני פענוח ה-JSON. אם הסוד מוגדר, החתימה
   נדרשת. אם אינו מוגדר (מצב תאימות לאחור), נרשמת אזהרה והתגובה
   מתקבלת — הסוד יהיה חובה ב-v3.9.
2. **הפעלה מפורשת של שדות סודיים**: `accessToken` / `refreshToken` /
   `providerSpecificData` מוחלפים **רק** כאשר
   `OMNIROUTE_CLOUD_SYNC_SECRETS=true`. מצב ברירת המחדל מסנכרן רק
   מטא-נתונים שאינם פרטי אימות (`expiresAt`, `status`, `lastError*`,
   `rateLimitedUntil`, `updatedAt`). זהו **שינוי שובר תאימות** עבור משתמשים
   שהסתמכו על סנכרון אסימונים מרוחק — עליהם להפעיל אותו במפורש.

**מדוע אנו משאירים זאת**: Cloud Sync הוא הדרך היחידה שבה דייר של OmniRoute Cloud
יכול לרכז את פרטי האימות של הצוות. התיקון מבהיר בכנות את מודל האיומים:
"השרת חותם, הלקוח מאמת, המפעיל מצטרף במפורש."

## פרופיל בנייה: `minimal`

משתמשים הזקוקים לארטיפקט ידידותי ל-Socket יכולים לבנות באמצעות:

```bash
OMNIROUTE_BUILD_PROFILE=minimal npm run build
```

ה-`NormalModuleReplacementPlugin` של webpack ממפה ארבעה מודולים למימושי דמה:

| מודול                                       | מימוש דמה                                        |
| ------------------------------------------- | ------------------------------------------------ |
| `src/mitm/cert/install.ts`                  | `src/mitm/cert/install.stub.ts`                  |
| `src/lib/zed-oauth/keychain-reader.ts`      | `src/lib/zed-oauth/keychain-reader.stub.ts`      |
| `src/lib/cloudSync.ts`                      | `src/lib/cloudSync.stub.ts`                      |
| `src/lib/services/installers/ninerouter.ts` | `src/lib/services/installers/ninerouter.stub.ts` |

כל מימוש דמה מייצא את אותו ממשק, אך כל פונקציה זורקת
`featureDisabledError(name)` בזמן ריצה. נתיבים התלויים במודול המושבת
מחזירים HTTP 503 עם הודעה ברורה, במקום להפעיל את
נתיב הקוד הרגיש.

החבילה המתקבלת מיועדת לפרסום בשם `omniroute-secure`. עיינו
ב-`docs/ops/PUBLISHING_SECURE.md` לקבלת הוראות הפרסום.
