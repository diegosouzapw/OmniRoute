> **הערת היקף:** הקובץ `socket.yml` מגדיר את הסריקה של Socket.dev בצד הרישום לאחר פרסום של ארטיפקט npm (נתיבים להתעלמות עבור תוכן שאינו מופץ, כגון `tests/`,‏ `docs/` ודוחות בנייה). הוא אינו מגדיר שער מיזוג של CI/PR — אף תהליך עבודה תחת `.github/workflows`, אף סקריפט ב-`package.json` ואף יעד ב-`Makefile` אינם מפעילים את Socket.dev.

מסמך זה הוא הצהרת האימות שחוברה בידי מתחזקי הפרויקט עבור ששת הממצאים מסוג
`AI-detected potential malware` שדווחו כנגד `omniroute@3.8.5`, ועבור
אמצעי ההפחתה שיושמו ב-`omniroute@3.8.6`. הוא קיים כדי:

1. לספק למפעילי צינור האבטחה מקור יחיד שיוכלו לצטט כאשר עליהם
   להעריך את הממצאים מול קוד המקור בפועל.
2. לאפשר לסורקי AI עתידיים לזהות את הטענה החתומה בידי המתחזקים, שלפיה כל
   נתיב שסומן הוא מכוון, דורש הסכמה מפורשת ומתועד.
3. לשמור תיעוד כתוב של _הסיבה_ לכך שכל אתר קריאה בנוי כפי שהוא —
   כדי ששכתוב עתידי לא יחזיר בטעות טביעת אצבע
   שהוסרה במכוון.

אם אתם מפעילים סורק שמסמן מחדש אחד מאתרי הקריאה שלהלן לאחר
פרסום אמצעי ההפחתה של v3.8.6, אנא פתחו דיווח עם עקבת הסריקה,
ואנו נרחיב כאן את הצהרת האימות.

## §1 — התקנת CA בסיסי עבור MITM ‏(`77484.js`)

**קובצי מקור**:

- `src/mitm/cert/install.ts` — הפונקציות הציבוריות `installCert()` / `uninstallCert()`,
  וכן `installCertWindows/Mac/Linux` הייעודיות לכל פלטפורמה.
- `src/mitm/systemCommands.ts` — פונקציות העזר המשותפות של `execFile` / `spawn` / PowerShell
  המשמשות את נתיבי ההתקנה.

**גורם מפעיל**: המשתמש לוחץ על "הפעלת פרוקסי MITM" בלוח הבקרה המקומי בכתובת
`/dashboard/cli-tools/mitm`. הנתיב נגיש דרך ממשק הלולאה החוזרת בלבד — ראו כלל קשיח מס' 17
ב-`CLAUDE.md` וב-`src/server/authz/routeGuard.ts::isLocalOnlyPath()`.‏ JWT שדלף
ונחשף דרך מנהרה **אינו יכול** להפעיל נתיב קוד זה.

**פעולות מיוחסות שבוצעו (לפי פלטפורמה)**:

| מערכת הפעלה            | פקודות                                                                                                            |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | `certutil -addstore Root <cert>` באמצעות UAC                                                                      |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | עדכון מסד הנתונים NSS בכל פרופיל באמצעות `certutil -d sql:<profile>`                                              |

אלה אותן הפקודות שבהן משתמשים `mitmproxy`,‏ Charles Proxy,‏ Fiddler ו-
Caddy. העובדה שהן קיימות ב-OmniRoute מתועדת ב-
`docs/security/STEALTH_GUIDE.md`.

**אמצעי הפחתה ב-v3.8.6**:

- `runElevatedPowerShell()` אינה משתמשת עוד ב-`-EncodedCommand <base64utf16le>`.
  המטען המורם נכתב לקובץ `.ps1` זמני עבור כל קריאה (במצב 0o600,
  בתוך ספריית `mkdtempSync` פרטית), ומופעל באמצעות `-File`. הקובץ
  נמחק ב-`finally`. שינוי זה מסיר את טביעת האצבע הקלאסית של
  הרמת הרשאות באמצעות PowerShell ו-base64, שסומנה בידי מסווג ה-AI של
  Socket.dev.
- `installCertWindows` כוללת בלוק `SECURITY-AUDITOR-NOTE:` מוטבע
  המפנה לכאן.

**מדוע אנו משאירים זאת**: פרוקסי ה-MITM הוא יכולת מתועדת המשמשת את
`docs/security/STEALTH_GUIDE.md` ואת `docs/frameworks/MITM-PROXY.md`. הסרתו
תשבית את מערך היכולות של גשר הסוכנים.

## §2 — ייבוא פרטי גישה מ-Zed (`app/api/providers/zed/import/route.js`)

**קובצי מקור**:

- `src/app/api/providers/zed/discover/route.ts` _(חדש ב-v3.8.6)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(חדש ב-v3.8.6)_

**גורם מפעיל**: המשתמש לוחץ על "ייבוא מ-Zed" בדף הספקים של לוח הבקרה המקומי. נקודת הקצה מוגנת באמצעות `requireManagementAuth`. עורך Zed עצמו כותב את מפתחות ה-API של הספקים אל מחזיק המפתחות של מערכת ההפעלה תחת שמות שירות מתועדים — ראו https://zed.dev/docs/ai/llm-providers.

**ההתנהגות ב-v3.8.5 (זו שסומנה על ידי Socket.dev)**:

`POST /import` איתרה את פרטי הגישה ושמרה אותם אוטומטית במאגר SQLite המקומי, בסבב בקשה-תגובה יחיד. ללא אישור נפרד לכל חשבון וללא טביעת אצבע, אלא רק "נמצאו N אסימונים, כולם יובאו."

**צמצום הסיכון ב-v3.8.6 — אישור דו-שלבי**:

1. **`POST /api/providers/zed/discover`** מחזירה
   `{ candidates: [{ provider, service, account, fingerprint }] }`. האסימון
   הגולמי **לעולם אינו** מועבר. טביעת האצבע היא
   `sha256(service|account|token).slice(0,16)`.
2. לוח הבקרה מציג את רשימת המועמדים, המפעיל בוחר אילו מהם לייבא ושולח
   `{ confirmedAccounts: [{ service, account, fingerprint }] }`
   אל **`POST /api/providers/zed/import`**.
3. נקודת הקצה לייבוא **קוראת מחדש את מחזיק המפתחות בשרת** ומסננת לפי
   `(service, account, fingerprint)`. תגובת גילוי ששונתה בזדון או הופעלה מחדש
   אינה יכולה לגרום לנקודת הקצה לייבוא לשמור אסימון שאינו קשור — אם האסימון
   הפעיל השתנה מאז הגילוי, טביעת האצבע כבר אינה תואמת ופרטי הגישה אינם מיובאים.

דגל הסביבה `OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` משמר את ההתנהגות של
v3.8.5 עבור מפעילים שטרם עדכנו את האוטומציה שלהם. הוא יוסר ב-v3.9.

**מדוע אנו משמרים זאת**: ייבוא מ-Zed הוא מסלול ההצטרפות הידידותי ביותר עבור
משתמשים שכבר משתמשים ב-Zed ורוצים לשקף את מפתחות הספקים שלהם אל OmniRoute
מבלי להדביק אותם מחדש.

## §3 — `execFile` / `spawn` / PowerShell עם הרשאות מוגברות (`21843.js`)

**קובצי מקור**: `src/mitm/systemCommands.ts`.

**מדוע סומן**: המקטע מייצא מחדש את `execFileWithPassword`,
את `runElevatedPowerShell` ואת פונקציית העזר המשותפת `quotePowerShell`. המסווג
מבוסס ה-AI של Socket.dev מזהה אותם כ"ערכת כלים כללית להרצה במחשב המארח
ולהעלאת הרשאות." בתוך OmniRoute הם משמשים רק במסלול התקנת אישור ה-MITM
(§1), וכן את `execFileWithPassword` לביצוע פקודות `sudo`.

**צמצום הסיכון ב-v3.8.6**:

- ארגון מחדש של `runElevatedPowerShell` (ראו §1).
- בלוק `SECURITY-AUDITOR-NOTE:` מוטמע הן ב-`runElevatedPowerShell` והן
  ב-`execFileWithPassword`, ומתעד את הקוראים שברשימת ההיתרים ואת רשימת
  קובצי ההפעלה המקובעת.
- קריאת `spawn()` של `execFileWithPassword` כוללת סמן `nosemgrep` עם רשימת
  ההיתרים של קובצי ההפעלה שפונקציית העזר רשאית לקבל — **אין כל נתיב מקלט
  המשתמש אל `finalCommand`/`finalArgs`**.

## §4 / §6 — מפקח השירות של 9router (`api/services/9router/{start,restart}/route.js`)

**קובצי מקור**:

- `src/app/api/services/9router/_lib.ts` — מפעל המפקח.
- `src/app/api/services/9router/{start,stop,restart,status,install,update,auto-start}/route.ts`.
- `src/lib/services/ServiceSupervisor.ts` — הפעלה כללית / תשאול תקינות / מאגר יומן.

**גורם מפעיל**: המשתמש לוחץ על "התקנה" / "הפעלה" בדף השירותים המוטמע
בלוח הבקרה המקומי.

**הגנות שכבר קיימות**:

- כל נתיבי `/api/services/*` הם LOCAL_ONLY לפי
  `src/server/authz/routeGuard.ts` (כלל קשיח #17). אכיפת loopback מתבצעת
  לפני כל בדיקת אימות — JWT שדלף אינו יכול להגיע אליהם.
- שורת מסד הנתונים של 9router מאותחלת עם `status='not_installed', auto_start=0`
  (ראו `src/lib/db/migrations/071_services.sql:19`). השירות **אינו** מופעל
  בהפעלה הראשונה.
- `spawn()` נקראת עם נתיב קובץ ההפעלה שמוחזר על ידי
  `resolveSpawnArgs(apiKey, PORT)` ב-`src/lib/services/installers/ninerouter.ts`,
  המהווה רשימת היתרים קבועה של קובצי הפעלה נתמכים.
- הפלטים Stdout/stderr נשמרים במאגר בזיכרון (מגבלה של 5 MB, ראו `_lib.ts`) —
  אין כתיבה לדיסק אלא אם המשתמש מפעיל רישום מלוח הבקרה.

**צמצום הסיכון ב-v3.8.6**: ללא שינוי תפקודי. פרופיל הבנייה המינימלי
(`OMNIROUTE_BUILD_PROFILE=minimal`) מחליף את
`src/lib/services/installers/ninerouter.ts` במימוש דמה עבור משתמשים שרוצים
להסיר פיזית מהחבילה את הנתיבים בעלי ההרשאות המוגברות.

**מדוע אנו משמרים זאת**: 9router הוא שירות נלווה אופציונלי שניתן להתקנה
מקומית (בדומה לתוסף בסגנון WordPress) — הצטרפות מפורשת וקפדנית בלבד.

## §5 — כתיבה חוזרת של פרטי גישה בסנכרון OmniRoute Cloud (`api/keys/[id]/route.js`)

**קובצי מקור**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`.
- `src/app/api/keys/[id]/route.ts` — מפעיל את `syncKeysToCloudIfEnabled()`.

**תנאי הפעלה**: `isCloudEnabled()` מחזיר `true` (מוגדר מלוח הבקרה) **וגם**
`CLOUD_URL` מוגדר. כאשר שניהם כבויים, לא מתבצעת קריאת רשת יוצאת אל נקודת הקצה
של Cloud.

**ההתנהגות ב־v3.8.5 (הבאג ש־Socket.dev זיהה בצדק)**:

`updateLocalTokens()` החליף את `accessToken`,‏ `refreshToken` ו־
`providerSpecificData` מתוך תגובת Cloud כאשר
`cloudUpdatedAt > localUpdatedAt`. ללא HMAC, ללא חתימה וללא סיכום ביקורת. ערך
`CLOUD_URL` שהוגדר באופן שגוי או זדוני (או מתקפת MITM בערוץ) יכול היה להחליף
בשקט אסימוני OAuth של ספקים.

**המענה ב־v3.8.6**:

1. **אימות HMAC**: הפונקציה `verifyCloudSignature(rawBody, sigHeader)` בודקת
   את הכותרת `X-Cloud-Sig` (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`) לפני פענוח ה־JSON. אם הסוד מוגדר, החתימה נדרשת.
   אם לא (מצב תאימות לאחור), נרשמת אזהרה והתגובה מתקבלת — הסוד יהיה חובה
   ב־v3.9.
2. **הצטרפות מפורשת לסנכרון שדות סודיים**: הערכים `accessToken` / `refreshToken` /
   `providerSpecificData` מוחלפים **רק** כאשר
   `OMNIROUTE_CLOUD_SYNC_SECRETS=true`. מצב ברירת המחדל מסנכרן רק
   מטא־נתונים שאינם פרטי גישה (`expiresAt`,‏ `status`,‏ `lastError*`,
   `rateLimitedUntil`,‏ `updatedAt`). זהו **שינוי שובר תאימות** עבור משתמשים
   שהסתמכו על סנכרון אסימונים מרוחק — עליהם להצטרף אליו במפורש.

**מדוע אנו משאירים זאת**: Cloud Sync הוא הדרך היחידה שבה דייר של OmniRoute Cloud
יכול לרכז את פרטי הגישה של הצוות. התיקון הופך את מודל האיומים לכנה:
"השרת חותם, הלקוח מאמת, המפעיל מצטרף במפורש."

## פרופיל בנייה: `minimal`

למשתמשים הזקוקים לתוצר ידידותי ל־Socket, יש לבנות באמצעות:

```bash
OMNIROUTE_BUILD_PROFILE=minimal npm run build
```

התוסף `NormalModuleReplacementPlugin` של webpack ממפה ארבעה מודולים למימושי דמה:

| מודול                                       | מימוש דמה                                        |
| ------------------------------------------- | ------------------------------------------------ |
| `src/mitm/cert/install.ts`                  | `src/mitm/cert/install.stub.ts`                  |
| `src/lib/zed-oauth/keychain-reader.ts`      | `src/lib/zed-oauth/keychain-reader.stub.ts`      |
| `src/lib/cloudSync.ts`                      | `src/lib/cloudSync.stub.ts`                      |
| `src/lib/services/installers/ninerouter.ts` | `src/lib/services/installers/ninerouter.stub.ts` |

כל מימוש דמה מייצא את אותו ממשק, אך כל פונקציה זורקת
`featureDisabledError(name)` בזמן ריצה. נתיבים התלויים במודול המושבת
מחזירים HTTP 503 עם הודעה ברורה, במקום להפעיל את נתיב הקוד
הרגיש.

החבילה המתקבלת מיועדת לפרסום בשם `omniroute-secure`. עיינו ב־
`docs/ops/PUBLISHING_SECURE.md` לקבלת הוראות הפרסום.
