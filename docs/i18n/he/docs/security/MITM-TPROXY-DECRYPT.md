פענוח שקוף באמצעות TPROXY הוא **מצב הלכידה החמישי** של OmniRoute עבור מחסנית ה-MITM של
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md).
הוא מיירט ו**מפענח** תעבורת HTTPS מקומית יוצאת ב-Linux באמצעות TPROXY של הליבה + ניתוב מבוסס מדיניות — **מבלי** לזייף את `/etc/hosts`
ו**מבלי** לשנות את הגדרות ה-system-proxy הכלל-מערכתיות של מערכת ההפעלה. הוא מתאים לסביבות ללא ממשק גרפי
(אין שינויי DNS שצריך לנקות), וכללי חומת האש נמחקים אוטומטית בעת אתחול מחדש.

בשונה ממצבי הלכידה האחרים, TPROXY אינו דורש הגדרה נפרדת לכל מארח: הוא מיירט בשקיפות
מארחי יעד **שרירותיים** ביציאת יעד, מסיים TLS באמצעות
אישור עלה שהוא מנפיק בזמן אמת לכל שם מארח SNI, לוכד את התקשורת
המפוענחת ומצפין מחדש את הבקשה אל היעד המקורי.

> **ל-Linux בלבד, ל-root בלבד, ובהפעלה מפורשת.** מצב זה דורש Linux, תוסף מקורי
> שנבנה באמצעות שרשרת כלי C, ואת היכולת **CAP_NET_ADMIN** (בדרך כלל root). הגישה אליו מוגבלת
> באמצעות ה-API של AgentBridge המאזין ל-loopback בלבד, והוא מושבת כברירת מחדל. רשות אישורים
> מהימנה ל-MITM שיכולה לחתום עבור כל מארח היא יכולת רבת-עוצמה — ראו [§6 אבטחה](#6-security).

**מקור:** `src/mitm/tproxy/`
**נתיב API:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**מתג בלוח הבקרה:** Traffic Inspector → סרגל הכלים של מצבי הלכידה → **"פענוח TPROXY"** ⚠
**ראו גם:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 מהו ומתי להשתמש בו

לכל אחד מארבעת מצבי הלכידה האחרים יש מגבלה:

| מצב                  | כיצד התעבורה מנותבת                             | מגבלה                                      |
| -------------------- | ----------------------------------------------- | ------------------------------------------ |
| AgentBridge          | זיוף DNS ב-`/etc/hosts` עבור קבוצת מארחים קבועה | רק מארחי סוכן ה-IDE הרשומים                |
| מארחים מותאמים אישית | זיוף DNS ב-`/etc/hosts` לכל מארח                | רשומה אחת לכל מארח; נדרש sudo לעריכת hosts |
| HTTP_PROXY           | משתני סביבה `HTTP_PROXY`/`HTTPS_PROXY`          | רק יישומים שמכבדים את משתנה הסביבה         |
| Proxy כלל-מערכתי     | הגדרות ה-proxy של מערכת ההפעלה                  | משנה מצב גלובלי; דורש שחזור                |

פענוח שקוף באמצעות TPROXY מנתב את התעבורה בשכבת **הליבה** במקום זאת. הוא
מסמן חיבורי TCP מקומיים יוצאים חדשים ליציאת יעד (ברירת המחדל היא `443`) בשרשרת
`mangle OUTPUT`; כלל `ip rule` מנתב מחדש את החבילות המסומנות למסירה מקומית,
ובכניסה מחדש יעד `TPROXY` שב-`mangle PREROUTING` מעביר אותן למאזין
**IP_TRANSPARENT** — אשר מסיים את חיבור ה-TLS ולוכד את הטקסט הגלוי.

השתמשו בו כאשר ברצונכם ללכוד ולפענח תעבורה מתהליך אשר:

- מתקשר עם מארח ש-AgentBridge אינו רושם, וגם
- אינו מכבד את `HTTP_PROXY`, וגם
- אינכם רוצים להפריע לו באמצעות שינוי proxy כלל-מערכתי.

מכיוון שהיירוט מתבצע בליבה, התהליך המקורי **אינו זקוק לשום
שינוי תצורה** — אך עליו לתת אמון ברשות האישורים הדינמית ש-OmniRoute
מתקין (ראו [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 דרישות

| דרישה           | פירוט                                                                                                                                    |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **מערכת הפעלה** | Linux בלבד — ‏**IP_TRANSPARENT** היא אפשרות socket הזמינה ב-Linux בלבד. ה-loader מחזיר "לא זמין" בכל פלטפורמה אחרת.                      |
| **הרשאות**      | יכולת **CAP_NET_ADMIN** ליצירת ה-socket השקוף ולהחלת כללי `iptables`/`ip` — בפועל, יש להריץ כ-root.                                      |
| **תוסף מקורי**  | יש לבנות תוסף N-API זעיר (`src/mitm/tproxy/native/transparent.c`) או לספק אותו כ-prebuild. ראו [§3](#3-the-native-ip_transparent-addon). |
| **מודולי ליבה** | `iptables` עם תמיכה ב-`TPROXY`, ב-`mangle` ובהתאמת `mark` (אומת מול kernel 6.8.0).                                                       |

**התדרדרות הדרגתית:** אם דרישה כלשהי חסרה (מערכת שאינה Linux, אין toolchain,
התוסף לא נבנה), ה-loader של התוסף (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
מחזיר `null` במקום לזרוק חריגה. לאחר מכן, סטטוס מצב הלכידה מדווח
`available: false`, המתג בלוח הבקרה **מושבת** ומציג את תיאור הכלי
"פענוח TPROXY דורש Linux + root + התוסף המקורי", ושאר חלקי
OmniRoute ממשיכים לפעול.

## §3 התוסף המקורי IP_TRANSPARENT

המודול `net` של Node אינו יכול להפעיל `setsockopt(IP_TRANSPARENT)` _לפני_ `bind()`, כפי
ש-TPROXY דורש (אחרת ה-kernel משליך את החבילות שנותבו מחדש). התוסף
(`src/mitm/tproxy/native/transparent.c`, שנבנה באמצעות `binding.gyp`) הוא מודול N-API
קטן שחושף שלוש פונקציות, הנצרכות דרך `transparentSocket.ts`:

| פונקציית התוסף                        | פעולת socket                                                                                | שימוש                                                                  |
| ------------------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, מחזירה fd גולמי | מאזין הלכידה השקוף (Node מאמץ את ה-fd באמצעות `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | `setsockopt` מסוג **SO_MARK** על fd קיים                                                    | מניעת לולאה (סימון ה-sockets של ה-proxy עצמו)                          |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **לפני** `connect()` לא חוסם, מחזירה fd                            | ההעברה המוצפנת מחדש אל ה-upstream (ה-SYN נושא את הסימון)               |

היעד המקורי נקרא מתוך `socket.localAddress`/`localPort` — ‏TPROXY
משמר אותו, ולכן אין צורך בחיפוש **SO_ORIGINAL_DST**/NAT.

### בניית התוסף

```bash
npm run build:native:tproxy      # מעבר אל src/mitm/tproxy/native והרצת node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- במהלך `npm run build`, הקובץ `scripts/build/build-tproxy-native.mjs` מריץ `node-gyp
rebuild`. הפעולה מיועדת **ל-Linux בלבד ואינה קטלנית** — toolchain חסר פשוט משאיר
  את מצב הלכידה בלתי זמין.
- `assembleStandalone.mjs` מעתיק את `build/Release/transparent.node` אל חבילת
  ה-standalone; הקובץ `transparentSocket.ts` מאתר אותו הן ביחס למודול והן
  ביחס ל-cwd (`<cwd>/src/mitm/tproxy/native/...`).
- הספריות `build/` ו-`prebuilds/` מוחרגות מ-git — הקובץ הבינארי **נבנה ולעולם אינו
  נכלל ב-commit**.

ה-loader בודק, לפי סדר עדיפות:
`native/build/Release/transparent.node`, ולאחר מכן `native/prebuilds/transparent.node`
(שניהם ביחס למודול וגם תחת `<cwd>/src/mitm/tproxy/`).

## §4 רשות האישורים הדינמית לכל SNI ומתקין מאגר האמון

> **עדכון #6684:** השרת הסטטי של AgentBridge‏ (`src/mitm/server.cjs`) משתמש כעת
> באותו דפוס ארכיטקטורה של CA/אישור קצה, במקום באישור קצה סטטי יחיד
> בחתימה עצמית. הוא משתמש במופע CA **נפרד**
> (`src/mitm/cert/rootCa.ts`, הנשמר ב־`<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> ומותקן במשבצת הקיימת מראש `omniroute-mitm.crt` במאגר האמון
> (תוך החלפת אישור הקצה היחיד הישן שהיה בה — אין צורך בניקוי של אמון כפול),
> בנפרד לחלוטין ממשבצת `omniroute-tproxy-ca.crt` של TPROXY המתוארת להלן.
> התקנות חדשות של AgentBridge מקבלות את מודל ה־CA באופן אוטומטי; התקנה שכבר
> נתנה אמון באישור הקצה הסטטי הישן ממשיכה להשתמש בו עד שהמפעיל בוחר להצטרף
> באמצעות `MITM_ROOT_CA_ENABLED=true` (ראו `src/mitm/cert/migration.ts`) —
> CA מהימן ל־MITM, שיכול לחתום על אישור קצה עבור **כל** מארח, הוא בעל יכולות
> משמעותית נרחבות יותר מאישור הקצה הישן בעל רשימת ה־SAN הקבועה, ולכן המעבר
> לעולם אינו מתבצע בשקט בהתקנה שכבר נתנה בו אמון.

מבחינה היסטורית, אישור ה־MITM הסטטי של AgentBridge פעל רק משום ש־AgentBridge
מבצע זיוף DNS עבור קבוצת מארחים **קבועה** (שכעת מאוחדת עם המודל שלהלן). TPROXY
מיירט מארחים **שרירותיים**, ולכן המאזין שלו חייב להציג אישור קצה תקף עבור
כל SNI שהלקוח מבקש — אותה דרישה שחלה כעת גם על AgentBridge עבור הקבוצה המלאה
`MITM_TOOL_HOSTS` (9 רשומות כלים), במקום רק 4 מארחי
antigravity.

### CA דינמי (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` מפעיל CA מקומי (המבוסס על התלות `selfsigned`) אשר:

- יוצר CA ארוך־טווח באמצעות `generateMitmCa()` (ה־CN הוא `"OmniRoute MITM CA"`,
  תוקף של 10 שנים, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  ‏RSA של 2048 סיביות / SHA-256).
- מנפיק **אישור קצה לפי דרישה לכל שם מארח SNI** באמצעות `issueLeafCert()` (תוקף
  של שנה אחת, `subjectAltName` = מארח ה־SNI) ושומר במטמון מופע `tls.SecureContext`
  אחד לכל שם מארח.
- חושף את `createSNICallback()` עבור השרת שמסיים את חיבור ה־TLS (ראו [§5](#5-how-decrypt-and-capture-work)).
- ניתן ליצירה עם `existingCa` כדי לשמור על CA יציב בין הפעלות מחדש
  (כך שאין צורך להתקין מחדש את מאגר האמון).

המפתח הפרטי של ה־CA **לעולם אינו יוצא מהמכונה**.

### מתקין מאגר האמון (`src/mitm/tproxy/caTrust.ts`)

הלקוח המיורט חייב לתת אמון ב־CA הדינמי, ולכן הפעלת מצב הלכידה
מתקינה את אישור ה־CA במאגר האמון של מערכת ההפעלה תחת **משבצת ייעודית** —
`omniroute-tproxy-ca.crt` (הקבוע `TPROXY_CA_CERT_NAME`) — הנשמרת בנפרד
מהמשבצת של אישור ה־MITM הסטטי (`omniroute-mitm.crt`), כך שהשניים לעולם אינם
דורסים זה את זה.

`installTproxyCa(caPem, sudoPassword?)` מזהה את ספריית העוגנים של ההפצה
(לפי הסדר: תחילה בסגנון Debian) ומריץ את פקודת הרענון המתאימה:

| ספריית העוגנים                              | פקודת הרענון             |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

במהלך ההתקנה, קובץ ה־PEM מועתק תחילה לקובץ זמני, לאחר מכן מורצת עם הרשאות
הפקודה `mkdir -p` עבור ספריית העוגנים, הקובץ הזמני מועתק אליה באמצעות `cp`,
ולבסוף מורצת פקודת הרענון. `uninstallTproxyCa()` מסירה רק את המשבצת הייעודית
(ומשאירה את אישור ה־MITM הסטטי ללא שינוי) ומרעננת — במערכות שאינן Linux
לא מתבצעת כל פעולה.

כל הפקודות הדורשות הרשאות מורצות באמצעות `execFileWithPassword` (`src/mitm/systemCommands.ts`)
— שימוש ב־`spawn` עם **מערכי ארגומנטים, ללא מעטפת וללא אינטרפולציית מחרוזות**
(כלל מחייב מס' 13). כאשר התהליך פועל כ־root (למשל ב־VPS), היעד מורץ ישירות
ולא נדרשת סיסמה; במחשב שולחני שאינו פועל כ־root, הערך `sudoPassword` מועבר
באמצעות `sudo -S` דרך stdin.

> הערך `sudoPassword` של המחשב השולחני נמסר בגוף בקשת ה־POST כדי לאשר את
> ההתקנה במאגר האמון; מתעלמים ממנו לחלוטין כאשר התהליך פועל כ־root.

## §5 כיצד הפענוח והלכידה פועלים

צינור העיבוד (כולו תחת `src/mitm/tproxy/`):

```
יישום מקומי  ──TCP/443──▶  ‏mangle OUTPUT מסמן את החיבור (fwmark)
                            ‏ip rule → טבלת ניתוב מקומית → lo
                            ‏mangle PREROUTING TPROXY → מאזין IP_TRANSPARENT (יציאה 8443)
                              │  captureMode.ts: קורא את יעד המקור מתוך socket.localAddress
                              ▼
                          tlsCapture.ts:
                            1. מסיים את חיבור ה-TLS של הלקוח באמצעות אישור קצה ייעודי לכל SNI‏ (dynamicCert)
                            2. ‏http.Server פנימי מנתח את הטקסט הגלוי שפוענח
                            3. לכידה → globalTrafficBuffer.push() עם source: "tproxy"
                               ‏(sanitizeHeaders + maskSecret מופעלות)
                            4. מעביר הלאה, לאחר הצפנה מחדש, אל היעד המקורי
                               דרך socket עם סימון עקיפה (connectMarked, מניעת לולאה)
                              │
                              ▼
                          שרת המקור המקורי (api.example.com)
```

- **סיום TLS** (`createTlsCaptureServer`): עוטף את ה-socket הגולמי שיורט
  ב-`tls.TLSSocket` בצד השרת, באמצעות ה-callback של SNI מרשות האישורים הדינמית,
  ולאחר מכן מוסר את הזרם המפוענח ל-`http.Server` פנימי (הטריק הסטנדרטי לסיום
  MITM). משכי החיים של ה-sockets מוגבלים באמצעות `MITM_IDLE_TIMEOUT_MS`, כך שמנהרה
  תקועה לא תוכל למצות את מתארי הקבצים.
- **לכידה** (`handleDecryptedRequest`): דוחף `InterceptedRequest` עם
  `source: "tproxy"`, סטטוס התחלתי `"in-flight"`, כותרות שעוברות דרך
  `sanitizeHeaders()` וגופים שעוברים דרך `maskSecret()` לפני כניסתם
  למאגר. לאחר מכן הרשומה מתעדכנת בתגובה, בגדלים ובזמן ההשהיה.
- **העברה מוצפנת מחדש** (`createForward` / `realForward`): מצפינה מחדש אל
  היעד המקורי. ברירת המחדל של `rejectUnauthorized` היא **`true`** (מאובטח
  כברירת מחדל) — אישור שרת המקור מאומת מול ה-SNI/Host שהלקוח
  ביקש, כך שה-proxy דוחה בדיוק את מה שהלקוח המקורי היה דוחה.

### מניעת לולאה (SO_MARK)

מכיוון שהכללים מסמנים חיבורים מקומיים יוצאים חדשים, ההעברה המוצפנת מחדש של
ה-proxy **עצמו** הייתה מיורטת מחדש בדרך כלל — לולאה אינסופית. נתיב
ההעברה מתגונן מפני מצב זה באמצעות סימון עקיפה ל-socket‏ (**SO_MARK**):

- `realForward` פותח את ה-socket שלו לשרת המקור באמצעות `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  — `DEFAULT_BYPASS_MARK = 0x539` — שמגדיר את **SO_MARK** **לפני** `connect()`,
  כך שחבילת ה-SYN של ההעברה נושאת את סימון העקיפה.
- כלל `mangle OUTPUT` מחריג חיבורים שכבר נושאים את סימון העקיפה
  (`-m mark ! --mark <bypassMark>`), כך שההעברה של ה-proxy **אינה** מסומנת מחדש
  ואינה נכנסת שוב ל-TPROXY.

> הערת מימוש: יש להתקין את ה-socket המסומן לעקיפה ב-`createConnection` של ה-agent
> (מתבצעת התעלמות שקטה מ-`https.request({ createConnection })` כאשר קיים agent),
> אחרת ההעברה תפתח socket לא מסומן והלולאה תחזור. זה היה התיקון למניעת לולאה
> שאומת מקצה לקצה.

## §7 החלה / ביטול טרנזקציוניים של חומת האש

קריסה לעולם אינה יכולה להשאיר מאחור כלל `mangle` או נתיב מיושן. בונה הפקודות
(`src/mitm/tproxy/commands.ts`) ומריץ הפקודות (`src/mitm/tproxy/setup.ts`) מבטיחים
כי **הביטול הוא ההופכי המדויק של ההחלה, בסדר הפוך**.

`applyTproxy(cfg)` מריצה את פקודות ההחלה לפי הסדר; במקרה של כשל **כלשהו**, היא
מריצה `revertTproxy(cfg)` מלא במתכונת best-effort וזורקת מחדש את השגיאה — כך שחומת
האש מוחלת במלואה או מבוטלת במלואה, ולעולם אינה מוחלת באופן חלקי. `revertTproxy(cfg)`
מריצה את הפקודות ההופכיות בסדר הפוך ומתעלמת מכשלים (אידמפוטנטית — בטוח לקרוא לה
ללא תנאי, למשל מפעולת הניקוי `repairMitm()` של AgentBridge).

`validateTproxyConfig(cfg)` רצה לפני כל פקודה: הפורטים חייבים להיות בטווח `1–65535`,
הערכים `mark`/`routeTable`/`bypassMark` חייבים להיות מספרים שלמים חיוביים, ו-`bypassMark`
חייב להיות שונה מ-`mark` (מניעת לולאה).

### פקודות החלה (לפי הסדר)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

הביטול מוחק אותן בסדר הפוך: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> המתכון מבוסס על **OUTPUT**, מפני שמקרה השימוש של MITM הוא תעבורה יוצאת
> _מקומית_ (יישומים באותו מארח), שאותה TPROXY ב-`PREROUTING` בלבד אינו
> רואה — `PREROUTING` רואה רק תעבורה מועברת. שרשרת `OUTPUT` מסמנת חיבורים
> מקומיים חדשים, `ip rule` מנתב אותם מחדש למסירה מקומית (`lo`), ולאחר מכן
> `PREROUTING` משייך אותם למאזין השקוף.

## §8 תצורה

בקשת ההפעלה (`POST /api/tools/agent-bridge/tproxy`) מקבלת את השדות הבאים,
המאומתים באמצעות `StartTproxyBodySchema` (`tproxy/route.ts`). כולם אופציונליים
וחוזרים לערכי ברירת המחדל שלהם אם לא צוינו:

| שדה              | סוג                | ברירת מחדל | הערות                                                                                                              |
| ---------------- | ------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------ |
| **dport**        | int (1–65535)      | `443`      | פורט היעד של TCP שייורט באופן שקוף                                                                                 |
| **mark**         | int (≥1)           | `0x2333`   | סימון חומת האש שמוגדר ב-`OUTPUT` ומותאם על ידי `ip rule` ו-`PREROUTING`                                            |
| **onPort**       | int (1–65535)      | `8443`     | הפורט שאליו נקשר המאזין השקוף (**IP_TRANSPARENT**)                                                                 |
| **routeTable**   | int (≥1)           | `233`      | מזהה טבלת ניתוב המדיניות שמכילה את הנתיב `local 0.0.0.0/0`                                                         |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`    | סימון המעקף של השקע (**SO_MARK**) שהפרוקסי מגדיר בחיבורים שלו לשרתים במעלה הזרם; מוחרג ב-`OUTPUT` (מניעת לולאה)    |
| **sudoPassword** | string             | —          | במחשבים שולחניים שאינם פועלים כ-root בלבד: מאשר את ההתקנה במאגר האישורים; המערכת מתעלמת ממנו כאשר היא פועלת כ-root |

אין **משתני סביבה** עבור TPROXY — כל התצורה מועברת דרך גוף בקשת ה-POST או באמצעות
ברירות המחדל שלעיל.

## §9 הפעלה מתוך בודק התעבורה

1. פתחו את **בודק התעבורה** (`/dashboard/tools/traffic-inspector`).
2. בסרגל מצבי הלכידה, מצאו את הלחצן ⚠ **"פענוח TPROXY"**
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - אם הוא **מושבת** ומופיע תיאור הכלי "פענוח TPROXY דורש Linux + הרשאות root +
     את התוסף המקורי", התוסף המקורי אינו זמין במארח זה (מערכת שאינה Linux,
     אין בה toolchain, או שהתוסף לא נבנה). ראו [§2](#2-requirements) ו-[§3](#3-the-native-ip_transparent-addon).
3. לחצו על הלחצן. הוא קורא אל `POST /api/tools/agent-bridge/tproxy` באמצעות
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`), אשר:
   בונה את ה-CA הדינמי, פותח את המאזין השקוף, מחיל את כללי חומת האש
   ומתקין את ה-CA במאגר האישורים המהימנים של מערכת ההפעלה.
4. במהלך הפעולה, המתג הופך לכתום ומציג את מספר היירוטים בזמן אמת
   (`· <interceptCount>`). בקשות שיורטו מופיעות ברשימת הבקשות עם
   `source: "tproxy"`.
5. לחצו שוב כדי לעצור — `DELETE /api/tools/agent-bridge/tproxy` באמצעות
   `stopTproxyCaptureMode()` סוגר את המאזין, מסיר את ה-CA ומבטל
   את כללי חומת האש.

מצב הלכידה (פועל / זמין / מספר יירוטים / יציאת המאזין) מתקבל
מ-`GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` בתוך
`src/mitm/tproxy/captureManager.ts`). בכל רגע נתון פועלת הפעלת TPROXY **אחת** בלבד —
ניסיון להפעיל הפעלה שנייה נדחה עם ההודעה "מצב הלכידה של TPROXY כבר פועל".

## §10 פתרון בעיות

### המתג מושבת

לא ניתן לטעון את התוסף המקורי. ודאו: שאתם משתמשים ב-Linux, שבניתם את התוסף
(`npm run build:native:tproxy`) ושהתהליך יכול לטעון את `transparent.node`.
`isTransparentSocketAvailable()` שולט בזמינות המתג; `GET /api/tools/agent-bridge/tproxy`
מחזיר `available: false` כאשר התוסף חסר.

### דבר אינו נלכד

- ודאו שהתהליך המיורט אכן מתחבר אל `dport` שהוגדרה
  (ברירת המחדל היא `443`).
- ודאו שהתהליך נותן אמון ב-CA הדינמי. ה-CA מותקן תחת
  `omniroute-tproxy-ca.crt`; ייתכן שביישומים בעלי מאגר אמון משלהם (Firefox/Chrome NSS)
  יהיה צורך להוסיף את האישור גם לשם.
- הריצו את הבדיקה העצמית **Diagnose** של AgentBridge (ראו
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) לבדיקות אמון באישור / תקינות
  השרת.

### כללי חומת אש מיושנים לאחר קריסה

`revertTproxy()` הוא ההיפוך המדויק של ההחלה והוא אידמפוטנטי. עצירת
המצב מבטלת את הכללים; אם OmniRoute הופסק במהלך הפעלה, השתמשו בפעולת
**Repair** של AgentBridge (`POST /api/tools/agent-bridge/repair`) כדי לבטל מצב מערכת
יתום (זיוף DNS, ‏CA בסיסי, proxy של המערכת). כללי ה-`mangle` והנתיב של TPROXY
נמחקים גם באופן אוטומטי בעת אתחול מחדש.

### לולאה אינסופית / ה-proxy מיירט את ההעברה של עצמו

זהו מקרה מניעת הלולאה. ודאו ש-`bypassMark` שונה מ-`mark` (האימות
אוכף זאת) ושההעברה משתמשת ב-`connectMarked` (כך אכן נעשה ב-`realForward`).
ראו [§5 מניעת לולאה](#anti-loop-so_mark).
