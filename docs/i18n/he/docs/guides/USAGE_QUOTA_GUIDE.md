> **בקצרה**: OmniRoute עוקב אחר צריכת הטוקנים של כל בקשה, מחשב עלויות, אוכף מכסות לפי מפתח API ומציג נתוני ניתוח בלוח הבקרה. מדריך זה מסביר כיצד הכול פועל.

**מקורות:**

- `open-sse/services/usage.ts` (~70KB) — מעקב השימוש העיקרי
- `src/lib/usageAnalytics.ts` (~10KB) — צבירה עבור לוח הבקרה
- `src/lib/db/quotaSnapshots.ts` — נתוני מכסות היסטוריים
- `src/lib/db/usage*.ts` — מספר מודולי מסד נתונים הקשורים לשימוש

---

## סקירה כללית

כל בקשה שעוברת דרך OmniRoute יוצרת **רשומת שימוש** שמתעדת:

- **זהות**: איזה מפתח API, ספק, מודל ושילוב
- **טוקנים**: טוקנים של ההנחיה, טוקנים של ההשלמה, טוקנים מהמטמון וסך הכול
- **עלות**: סכום בדולרים אמריקאיים (מחושב מנתוני התמחור)
- **תזמון**: השהיה וחותמות זמן של התחלה/סיום
- **סטטוס**: הצלחה, שגיאה, הגבלת קצב וכו׳

רשומות אלה נצברות לכדי **נתוני ניתוח**, נשמרות כ**תמונות מצב של מכסות** ומשמשות לאכיפת **מגבלות תקציב לפי מפתח**.

```
בקשה ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    ניתוחים    מכסה    חיוב
                 (לוח הבקרה) (אכיפה)  (ייצוא)
```

## מה מתועד

השירות `usage.ts` מתעד **אירוע שימוש** עבור כל בקשה:

| שדה                | סוג     | מקור                                                       |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | UUID שנוצר בעת התיעוד                                      |
| `apiKeyId`         | string  | מפתח ה-API שיזם את הבקשה                                   |
| `provider`         | string  | מזהה הספק (openai, anthropic וכו׳)                         |
| `model`            | string  | מזהה המודל (gpt-5, claude-opus-4-6 וכו׳)                   |
| `comboId`          | string? | מזהה השילוב, אם הניתוב התבצע דרך שילוב                     |
| `promptTokens`     | number  | מתגובת הספק במעלה הזרם                                     |
| `completionTokens` | number  | מתגובת הספק במעלה הזרם                                     |
| `cachedTokens`     | number  | טוקנים שנמצאו במטמון (מטמון הנחיות של Anthropic וכו׳)      |
| `totalTokens`      | number  | הנחיה + השלמה                                              |
| `costUsd`          | number  | מחושב מנתוני התמחור                                        |
| `latencyMs`        | number  | משך הבקשה מקצה לקצה                                        |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | מחלקת השגיאה אם status != success                          |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | נתונים מותאמים אישית שהוזרקו על ידי תוסף                   |

### מהיכן מגיעים הטוקנים

הטוקנים מחולצים מתגובת הספק במעלה הזרם בתוך **מטפל התגובה**:

```ts
// מתוך open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

עבור ספקים שאינם מחזירים נתוני שימוש (חלק מהספקים המבוססים על קובצי Cookie מהאינטרנט), OmniRoute **מעריך** את מספר הטוקנים באמצעות כלל האצבע `~4 תווים לכל טוקן` (ראו `open-sse/services/autoCombo/pipelineRouter.ts`).

### טוקנים מהמטמון

OmniRoute עוקב אחר `cached_tokens` בנפרד מ-`prompt_tokens` משום ש:

- מטמון ההנחיות של Anthropic גובה תעריף מופחת עבור טוקנים מהמטמון (10% מהתעריף הרגיל)
- ספקים מסוימים מחזירים `cache_read_input_tokens`, שיש לתמחר באופן שונה
- נתוני הניתוח יכולים להציג את **שיעור הפגיעות במטמון** = `cached_tokens / prompt_tokens`

## חישוב עלויות

העלויות מחושבות מתוך **נתוני תמחור** המסונכרנים מ-LiteLLM (`src/lib/pricingSync.ts`):

| מודל              | קלט $/1M | פלט $/1M | מטמון $/1M |
| ----------------- | -------- | -------- | ---------- |
| gpt-5             | $2.50    | $10.00   | —          |
| claude-opus-4-6   | $15.00   | $75.00   | $1.50      |
| claude-sonnet-4-5 | $3.00    | $15.00   | $0.30      |
| gemini-2.5-pro    | $1.25    | $10.00   | —          |

נוסחת העלות (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **מדוע מחסירים את האסימונים שבמטמון מאסימוני הקלט?** החלק שבמטמון מתומחר בנפרד; חיוב במחיר הקלט עבור הקלט כולו יוביל לספירה עודפת.

### סנכרון תמחור

נתוני התמחור מסונכרנים אוטומטית מ-LiteLLM דרך נקודת הקצה `/api/pricing/sync` (מופעלת על ידי משימת cron המובנית, ולא על ידי משתנה סביבה חשוף למשתמש):

```bash
# הפעלה ידנית
curl -X POST http://localhost:20128/api/pricing/sync
```

עבור מודלים שאין להם נתוני תמחור, OmniRoute חוזר ל-**הערכת העלות** באמצעות תעריפים ממוצעים פנימיים (שמקורם בנתוני התמחור של LiteLLM).

## צבירה לפי טווח תאריכים

המודול `usageAnalytics.ts` מחשב רכיבים גרפיים בלוח המחוונים מתוך נתוני שימוש גולמיים. הוא תומך ב-7 טווחי זמן:

| טווח     | חלון זמן                  | שימוש                    |
| -------- | ------------------------- | ------------------------ |
| `1d`     | 24 השעות האחרונות         | זיהוי קפיצות עלות שעתיות |
| `7d`     | 7 הימים האחרונים          | סקירה שבועית             |
| `30d`    | 30 הימים האחרונים         | חיוב חודשי               |
| `90d`    | 90 הימים האחרונים         | ניתוח רבעוני             |
| `ytd`    | מאז 1 בינואר בשנה הנוכחית | מעקב אחר התקציב השנתי    |
| `all`    | כל התקופה                 | נתונים סטטיסטיים מצטברים |
| `custom` | התחלה/סיום בהגדרת המשתמש  | ביקורות, שאילתות אד-הוק  |

### רכיבי לוח המחוונים המחושבים

עבור כל טווח תאריכים, שכבת הניתוח מחשבת:

| רכיב                   | תיאור                                                     |
| ---------------------- | --------------------------------------------------------- |
| **כרטיסי סיכום**       | סך כל הבקשות, העלות הכוללת, סך כל האסימונים, שיעור ההצלחה |
| **תרשים מגמה יומי**    | עלות + אסימונים ליום, בערימה לפי מודל                     |
| **מפת חום של פעילות**  | רשת שעה ביום × יום בשבוע, צבע = מספר הבקשות               |
| **פילוח לפי מודל**     | תרשים עוגה של העלות לפי מודל                              |
| **פילוח לפי ספק**      | תרשים עמודות של בקשות לפי ספק                             |
| **מפתחות API מובילים** | טבלה של 10 המפתחות המובילים לפי עלות                      |
| **ניתוח שגיאות**       | שיעור השגיאות לאורך זמן, סוגי השגיאות הנפוצים ביותר       |

### גישה תכנותית

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // רשומות היסטוריית שימוש
  "7d",                 // טווח זמן: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // מפת חיבורי ספקים (connectionId → שם החשבון)
  {
    startDate: "2025-01-01",  // אופציונלי: עבור הטווח "custom"
    endDate: "2025-06-01",   // אופציונלי: עבור הטווח "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (סנטים)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## אכיפת מכסות

המכסה לכל מפתח API נאכפת בשני מקומות:

1. **מגבלה רכה** (`quotaWarnAt`): אזהרה בלוח הבקרה כאשר השימוש חורג מהסף
2. **מגבלה קשיחה** (`quotaLimit`): הבקשה נדחית עם HTTP 429 כאשר יש חריגה

### תצורה

```ts
// לכל מפתח API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — הצגת אזהרה
  quotaLimit: 10_00,    // $10.00 — עצירה מוחלטת
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### תהליך האכיפה

```
בקשה ──▶ quotaCheck()
              │
              ├── במסגרת המגבלה?  ──▶ אישור
              │
              └── מעבר למגבלה?  ──▶ 429 יותר מדי בקשות
                                   עם כותרת Retry-After
```

### תמונות מצב של המכסה

הטבלה `quotaSnapshots` מאחסנת את **המצב ההיסטורי של המכסה** לצורך ניתוח מגמות:

| שדה | תיאור |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | המפתח שאחריו מתבצע מעקב |
| `window` | "day" | "week" | "month" |
| `used` | העלות שנוצלה בחלון זה (בסנטים) |
| `limit` | המגבלה (בסנטים) |
| `resetAt` | המועד שבו החלון מתאפס |
| `createdAt` | המועד שבו נלקחה תמונת המצב |

תמונות מצב נלקחות **בכל בקשה** שעלותה גדולה מ־0, ומשמשות כדי:

- להציג את סרגל התקדמות המכסה בלוח הבקרה
- להציג תרשימי מגמת מכסה ל־30 יום
- להפעיל התראות כאשר השימוש מתקרב למגבלה

### שאילתת ניתוח נתוני שימוש

הגישה לנתוני השימוש מתבצעת דרך לוח הבקרה או כלי MCP, ולא באמצעות נקודות קצה ישירות לייצוא ב־REST. ניתוחי הנתונים הזמינים:

- **`/api/usage/analytics`** — מדדי שימוש מצטברים (קיבוץ לפי מודל, ספק, מפתח)
- **`/api/usage/quota`** — מצב המכסה הנוכחי לכל מפתח API
- **`/api/usage/history`** — יומני היסטוריית בקשות

## שמירה וניקוי

נתוני השימוש גדלים בכ־1-10KB לכל בקשה. בקנה מידה גדול, נפח זה עשוי להיות משמעותי.

### הגדרות שמירה

שמירת היסטוריית השימוש מוגדרת דרך הגדרות מסד הנתונים בממשק המשתמש או דרך `/api/settings/database`.

כברירת מחדל, היסטוריית השימוש נשמרת למשך **90 ימים**.

### ניקוי

רשומות ישנות מנוקות על ידי `src/lib/db/cleanup.ts`:

- מופעל על ידי תהליך ה-cron ברקע
- מוחק מ־`usage_history` רשומות שגילן עולה על תקופת השמירה שהוגדרה בהגדרת `usageHistory`

### הערכת נפח אחסון

| קצב בקשות         | אחסון ל-30 יום | אחסון ל-90 יום |
| ----------------- | -------------- | -------------- |
| 100 בקשות/יום     | ~3MB           | ~9MB           |
| 1,000 בקשות/יום   | ~30MB          | ~90MB          |
| 10,000 בקשות/יום  | ~300MB         | ~900MB         |
| 100,000 בקשות/יום | ~3GB           | ~9GB           |

לתעבורה גבוהה מאוד, שקלו:

- לקצר את תקופת השמירה דרך הגדרות מסד הנתונים
- להשתמש ב־`aggregated_metrics` במקום ברשומות גולמיות (רק לצורך ניתוח נתונים)

## טיפים למיטוב עלויות

### 1. השתמשו במודל המתאים

```bash
# תשובה מהירה — השתמשו במודל זול ומהיר
curl -d '{"model":"auto/fast","messages":[...]}'

# משימה מורכבת — השתמשו במודל איכותי
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. הפעילו אחסון במטמון

אחסון הנחיות במטמון של Anthropic חוסך **90% בהקשר חוזר**:

```ts
// האחסון במטמון אוטומטי — פשוט כללו את אותה הנחיית מערכת גדולה
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // יישמר אוטומטית במטמון
  messages: [{ role: "user", content: "..." }],
});
```

### 3. השתמשו בדחיסה

דחיסת RTK + Caveman חוסכת **15-95% בהפעלות עתירות כלים**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. הגדירו מכסות לכל מפתח

הגדירו תמיד `quotaLimit` כדי למנוע עלויות בלתי מבוקרות:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // תקרה של $10 לחודש
```

### 5. בדקו את הצרכנים המובילים

השתמשו בלוח הבקרה או ב־**`/api/usage/analytics`** כדי לקבץ לפי מפתח API ולמיין לפי עלות:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## פתרון בעיות

### "העלות גבוהה מהצפוי"

1. בדקו את **`/api/usage/analytics?groupBy=model`** — מצאו את המודל היקר
2. בדקו את **`/api/usage/analytics?groupBy=apiKey`** — מצאו את הצרכן הכבד
3. ודאו שנתוני התמחור מעודכנים: `POST /api/pricing/sync`

### "רשומות חסרות"

- בדקו את הגדרות השמירה של מסד הנתונים תחת לוח הבקרה ← מסד נתונים ← ניקוי — רשומות ישנות נמחקות על ידי משימת הניקוי התקופתית (`src/lib/db/cleanup.ts`)
- בדקו אם קיימות שגיאות ב־`src/lib/db/usage*.ts` — כשלים בכתיבה למסד הנתונים נרשמים ביומן, אך אינם מוצגים
- ודאו שהבקשה אכן הגיעה אל `chatCore` — בדקו את ניתוב ה-combo

### "המכסה אינה נאכפת"

- בדקו את הגדרת `quotaLimit` של המפתח
- ודאו ש־`quotaWindow` מוגדר כהלכה
- חפשו רשומות `quotaSnapshots` — הן אמורות להיווצר בכל בקשה
