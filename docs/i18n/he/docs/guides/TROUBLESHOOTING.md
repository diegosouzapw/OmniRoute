## עיון מהיר

**חדשים ב-OmniRoute?** התחילו כאן — הפתרונות האלה מטפלים ב-90% מהבעיות:

| מה מופיע אצלי              | מה המשמעות                          | מה לעשות                                                                                  |
| -------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------- |
| "לא ניתן להתחבר"           | OmniRoute אינו פועל                 | הפעילו את `omniroute` או את `docker restart omniroute`                                    |
| "מפתח API לא תקין"         | המפתח שלכם שגוי או שפג תוקפו        | העתיקו מחדש את המפתח מאתר הספק                                                            |
| "חריגה ממגבלת הקצב"        | אתם שולחים בקשות רבות מדי           | המתינו דקה אחת, או השתמשו ב-`model: "auto"` למעבר אוטומטי לחלופה                          |
| "חריגה מהמכסה"             | ניצלתם את מלוא המכסה החינמית/בתשלום | חברו ספקים נוספים, או השתמשו בספקים חינמיים (Kiro, Pollinations)                          |
| "תגובות איטיות"            | הספק עמוס או מרוחק                  | השתמשו ב-`model: "auto/fast"` או חברו ספק מהיר יותר (Groq, Cerebras)                      |
| "נעשה שימוש בספק הלא נכון" | `auto` בחר ספק אחר                  | זה תקין! `auto` בוחר את הטוב ביותר. כפו שימוש בספק מסוים באמצעות `model: "openai/gpt-4o"` |
| "502 שער לא תקין"          | הספק אינו זמין                      | המתינו ונסו שוב, או השתמשו ב-`model: "auto"` כדי לעבור בין ספקים                          |
| "401 אין הרשאה"            | פרטי האימות שלכם שגויים             | בדקו את מפתח ה-API או בצעו אימות מחדש באמצעות OAuth                                       |
| "429 בקשות רבות מדי"       | חלה הגבלת קצב                       | המתינו דקה אחת, או חברו ספקים נוספים                                                      |

**עדיין תקועים?** עיינו בסעיף [פתרון הבעיות המפורט](#detailed-troubleshooting) שלהלן, או שאלו ב-[Discord](https://discord.gg/U47eFqAXCn).

## פתרון בעיות מפורט

---

### הגבלת קצב אצל ספקים חינמיים (429 / 400 / 401)

**תסמין**: בעת שימוש ב-`model: "auto"` עם ספקים חינמיים/ללא אימות (opencode, auggie וכו'), מתקבלות לסירוגין שגיאות `HTTP 429`,‏ `400` או `401` במקום תשובות. הבקשות מצליחות כשמנסים שוב את אותה ההנחיה כעבור רגעים ספורים, אך תהליכים אוטומטיים (משימות cron, סוכנים, סקריפטים) נכשלים כבר בשגיאה הראשונה.

**סיבת השורש**: שלושה מצבי כשל בלתי תלויים מצטברים זה על גבי זה:

1. **הגבלת קצב מצד הספק (`429`)**: מסלולים חינמיים עשויים לאכוף מכסה לכל חלון זמן. פרץ של קריאות מקבילות מנצל אותה במלואה, ולכן הבקשה הבאה נדחית עד לאיפוס החלון.
2. **מודל לא תקין במעבר ישיר (`400`/`401`)**: מאגרי `auto/*` עשויים לכלול מודלים במעבר ישיר מ-`opencode` שרשומים בקטלוג אך אין להם אישורי גישה פעילים (לדוגמה, `oc/north-mini-code-free` ← `401`). הנתב האוטומטי מנסה אחד מהם, נכשל, והשגיאה מועברת הלאה לפני שהמעבר לחלופה נכנס לפעולה.
3. **הגברת מקביליות (`429` תחת עומס)**: כאשר כמה הפעלות של סוכנים/משימות cron פונות אל `auto` בו-זמנית, קצב הבקשות המצטבר חורג ממה שספקים חינמיים מסוגלים לספוג, ולכן קריאות לגיטימיות מסומנות כפוגעניות.

**תיקון מאומת (דווח על ידי הקהילה, 2026-08-10)**: כווננו שלושה משתני סביבה כך שסבב ההחלפה, המקביליות והמעבר לחלופה יספגו את התנודתיות של המסלול החינמי במקום להיכשל בגללה:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # מעבר למודל/ספק אחר בתגובה ל-400/401 (דילוג על מודלים לא תקינים במעבר ישיר)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # תקרת קבלה מפורשת לבקשות כבדות (אינה מוגדרת כברירת מחדל: אין מגבלה על מספר הבקשות, ראו הערה להלן)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # המתנה תחומה וארוכה יותר לקיבולת של בקשות כבדות, במקום שגיאת 503 מיידית הניתנת לניסיון חוזר
```

הגדירו אותם בסביבת התהליך של OmniRoute (תהליך הרקע, למשל באמצעות קובץ ה-plist של LaunchAgent או `systemctl edit`), ולאחר מכן הפעילו מחדש את OmniRoute. דגל הסבב הוא המנוף היחיד בעל ההשפעה הגדולה ביותר: הוא הופך כשל מוחלט לניסיון חוזר שקוף מול ספק תקין במאגר.

**הערה**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` מגביל את מספר הבקשות הכבדות — בעלות הקשר ארוך — שיכולות לפעול בו-זמנית; הגבול הוא שער קבלה, ולא מגביל קצב של ספק. **עדכון #503-fanout:** משתנה זה כבר אינו מוגדר כברירת מחדל (כעת הוא נכנס לתוקף רק כאשר מגדירים אותו במפורש, כמו לעיל) — במקום זאת, קבלת בקשות כבדות נשלטת באמצעות תקציב בתים הנגזר אוטומטית (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), שמתאים את עצמו לתקרת הזיכרון האמיתית של המארח. לכן, בפריסה חדשה אמורות להופיע הרבה פחות דחיות מסוג `503 chat_admission_busy`, גם בלי להגדיר כלל את המשתנה הזה; הגדרתו המפורשת כאן עדיין פועלת בדיוק כפי שמתועד. דריסות מפורשות של תקציב הבתים מוגבלות לטווח 8 MiB–2 GiB. שגיאת `413 body_exceeds_budget` אינה זמנית: הגדילו את תקציב הבתים, הקטינו את `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`, או הגדילו את תקרת הזיכרון של התהליך. השלת עומס מסוג `inflight_bytes_budget` נובעת מתחרות זמנית על משאבים ועדיין מאפשרת ניסיון חוזר. הגבלת הקצב לכל ספק (`open-sse/services/rateLimitManager.ts`) נשלטת בנפרד באמצעות `RATE_LIMIT_MAX_WAIT_MS`,‏ `RATE_LIMIT_MAX_QUEUE_DEPTH` ו-`RATE_LIMIT_AUTO_ENABLE` — ראו `.env.example`.

**כיצד לוודא שהתיקון עבד**: הפעילו את הסוכן/משימת ה-cron פעמיים ברצף מהיר וודאו ששתי ההפעלות מצליחות. לפני התיקון, ההפעלה השנייה מחזירה בדרך כלל `429`/`401`. לאחר התיקון, ניסיונות שנכשלים (אם יש כאלה) מתבצעים שוב באופן שקוף והקריאה מושלמת. ניתן גם להריץ `curl /monitoring/health` ולעקוב אחר השדה `rateLimitedUntil` בחיבורי הספקים ואחר `circuitBreakers.providerBreakers[].state` עבור הספקים המושפעים — המצב הוא אחד מהערכים `CLOSED`,‏ `DEGRADED`,‏ `OPEN` או `HALF_OPEN` (ראו `src/shared/utils/circuitBreaker.ts`), וספק שממשיך להיכשל יעבור בין המצבים `CLOSED → DEGRADED → OPEN` לפני שחלון האיפוס יאפשר לבקשת בדיקה לעבור (`HALF_OPEN`).

**אם עדיין מופיעה שגיאת 429**: החשבון הפעיל אצל אותו ספק מיצה בפועל את _המכסה_ שלו (ולא רק את מגבלת הקצב). הוסיפו חשבון נוסף עבור אותו ספק בלוח הבקרה של OmniRoute דרך Providers → Accounts, או שלבו ספק חינמי אחר (למשל `routeway`, `auggie`). רוטציה מסייעת רק במקרים זמניים של מגבלת קצב או שגיאות 400/401; מיצוי מוחלט של המכסה מחייב פרטי גישה נוספים או ספק אחר.

**אם מופיעה שגיאת 403 במודלי ראייה (`auto/vision`, `bazaarlink/*`)**: לחשבון המחובר אין תוכנית בתשלום הכוללת יכולות ראייה, או שלמפתח ה-API אין הרשאות מספיקות. ודאו בלוח הבקרה של הספק שהיקף ההרשאות של המפתח כולל ראייה/מולטימודאליות, או חברו חשבון בתוכנית בתשלום והשאירו אותו כיעד עבור מודלי הראייה.

## אזהרות npm install‏ (ERESOLVE / עמית / הוצא משימוש)

בעת הרצת `npm install -g omniroute`, ייתכן שיופיעו אזהרות רבות כגון `npm warn ERESOLVE`, הודעות על תלויות עמית והודעות `deprecated`. **אזהרות אלה צפויות ואינן מזיקות.** ההתקנה הצליחה אם מופיע בפלט `added <N> packages`.

האזהרות נובעות מטווחים מיושנים של תלויות עמית בחבילות צד שלישי שאינן בשליטת OmniRoute:

1. **`marked-terminal` דורשת `marked >=1 <16`, אך נמצאה `marked@18`** — בפועל היא פועלת היטב; טווח העמית בפרויקט המקור פשוט מיושן.
2. **`deprecated prebuild-install@7.1.3`** — כלי עזר עקיף לאחזור קבצים בינאריים מקוריים. הוא אינו
   משמש להתקנת קישור התעבורה המקובע `wreq-js`, ואינו מעיד על כך שהגדרת התעבורה של ספק קובצי ה-cookie
   נכשלה.

**אין צורך בפעולה** — לא ניתן להשתיק את האזהרות לחלוטין מבלי ליצור פיצול של חבילות המקור.

## זיהויים חיוביים שגויים של אנטי-וירוס

<a name="antivirus-false-positives"></a>

### Avast/AVG מעבירים את `README.md` להסגר עם `MD:HttpRequest-inf[Susp]`

**זהו זיהוי חיובי שגוי. שום דבר אינו נגוע, ולא נדרשת כל פעולה.**

Avast ו-AVG מפעילים היוריסטיקה המסמנת קובצי טקסט רגיל/Markdown המכילים קישורים רבים
שנראים כמו בקשות HTTP. הקובץ `README.md` של OmniRoute כלול בחבילת npm (הוא
מופיע תחת `files` ב-`package.json`), ולכן בהתקנה גלובלית הוא מגיע אל
`node_modules/omniroute/README.md` — והוא מכיל כ-15 דוגמאות של `http://localhost:20128/...`
(נקודות הקצה HTTP/SSE של MCP, כתובת ה-URL מסוג `.well-known` של A2A וקטעי `curl`).
צפיפות קישורים זו מספיקה כדי להפעיל את ההיוריסטיקה.

אם הדבר החל רק לאחרונה: סוג הקובץ לא השתנה. טבלת נקודות הקצה ב-README הורחבה
(MCP HTTP + SSE + A2A נוספו), וכן נוספו דוגמאות `curl`, מה שגרם לו לעבור
את הסף.

הקובץ הוא תיעוד פסיבי ללא שום תוכן בר-הרצה. ניתן לשחזר אותו בבטחה
מההסגר.

**מה לעשות:**

1. **הפסיקו את ההתראות** — החריגו את ספריית ההתקנה באנטי-וירוס שלכם
   (Avast: הגדרות ← חריגים), והוסיפו את הנתיב הגלובלי של `node_modules` ו/או את
   ספריית הנתונים של OmniRoute (`~/.omniroute/`).
2. **דווחו על הזיהוי החיובי השגוי** — <https://www.avast.com/false-positive-file-form.php>,
   וצרפו את `README.md` שהועבר להסגר. זהו התיקון שמסייע לכולם, מכיוון שמדובר
   בתגובת יתר של היוריסטיקת הספק לקובץ טקסט.

**מדוע איננו "מתקנים" זאת בצד שלנו:** כל הדוגמאות משתמשות ב-`http://localhost`,
ולא ניתן להשתמש ב-`https` עבור localhost ללא הסרבול הכרוך באישור בחתימה עצמית.
עיוות התיעוד כדי להתחמק מהיוריסטיקה של ספק יחיד יפגע בכל הקוראים רק כדי לתת מענה
לבאג בסורק.

### Kaspersky מסמן את יישום שולחן העבודה בתור `PDM:Trojan.Win32.Generic`

**זהו זיהוי חיובי שגוי של היוריסטיקה התנהגותית. שום דבר אינו נגוע.** התחילית
`PDM:` של Kaspersky מציינת שהקביעה מגיעה ממודול ההגנה הפרואקטיבית שלו (System Watcher),
אשר שופט את מה שהמתקין _עושה_ במקום להשוות אותו לתוכנות זדוניות מוכרות. כאשר
הזיהוי מופעל, Kaspersky "מחזיר לאחור" את ההתקנה כולה — ומוחק קבצים שכבר
נכתבו — ולכן היישום נותר פגום או נעלם.

הקבצים שהוא מסמן הם רכיבים סטנדרטיים של יחסי תלות מוצהרים בקוד פתוח, המצורפים
ליישום שולחן העבודה, לדוגמה:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` וכן
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ספריית האוטומציה
  לדפדפנים המשמשת להתחברות לספקים מתוך היישום ולצ'אט מבוסס דפדפן.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — הקישור הבינארי המקובע של `wreq-js`, המשמש לבקשות HTTP בעלות טביעת אצבע של דפדפן
  אצל ספקים המבוססים על קובצי Cookie מהאינטרנט (`<arch>` הוא `x64` או `arm64`).

**מדוע הזיהוי מופעל:** מתקין Windows **עדיין אינו חתום בחתימת קוד**, ולכן למתקין
NSIS שאינו חתום אין שום מוניטין, והיוריסטיקות התנהגותיות פועלות ברמת התוקפנות המרבית.
בשילוב עם DLL מקורי המצורף לחבילה ומאות קובצי `.js` הנכתבים תחת
`%LOCALAPPDATA%\Programs\OmniRoute` (כולל ספריות חבילה עם סיומת hash שנוצרו מגרסת
ה-standalone של Next.js), די בכך כדי להפעיל את ההיוריסטיקה. חתימת קוד מתוכננת;
עד שתתווסף, הדבר עשוי לחזור על עצמו בגרסאות חדשות.

**מה לעשות:**

1. **אמתו תחילה את ההורדה שלכם** (כדי לשלול אפשרות של קובץ ששונה בזדון). בכל גרסה מתפרסם
   `latest.yml`, שהשדה `sha512` שלו (base64) מכסה את המתקין
   `OmniRoute.Setup.<version>.exe`. ב-PowerShell, מתוך התיקייה המכילה את המתקין:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   הפלט חייב להתאים ל-`latest.yml` ← `sha512`. אם אין התאמה, מחקו את הקובץ
   והורידו אותו מחדש רק מ[דף הגרסאות של GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **שחזור + החרגה** — שחזרו מההסגר את הפריטים שנמחקו במהלך ההחזרה לאחור והוסיפו החרגה
   עבור `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky ← הגדרות ← איומים והחרגות),
   ולאחר מכן התקינו מחדש.
3. **דווחו על הזיהוי החיובי השגוי** — <https://opentip.kaspersky.com/>. דיווחי זיהוי
   חיובי שגוי שמגישים משתמשים אכן מאיצים את ההוספה לרשימת ההיתרים.

## תאימות ל-Node.js

<a name="nodejs-compatibility"></a>

### דף הכניסה קורס או מציג שגיאת "Module self-registration"

**סיבה:** מופעלת אצלכם גרסת Node.js שאינה עומדת ברף סביבת ההרצה המאובטחת המאושר של OmniRoute. המקרה הנפוץ ביותר הוא שימוש בגרסת תיקון ישנה יותר של Node 22 או 24, הנמוכה מרף תיקוני האבטחה הנדרש על ידי OmniRoute.

**תסמינים:**

- דף הכניסה מציג מסך ריק או שגיאת שרת
- במסוף מופיעה השגיאה `Error: Module did not self-register` או שגיאות דומות של קישור רכיב מקומי
- דף הכניסה מציג **כרזת אזהרה כתומה** עם גרסת ה-Node שלכם, אם סביבת ההרצה אינה עומדת במדיניות המאובטחת הנתמכת

**פתרון:**

1. התקינו מהדורת LTS נתמכת של Node.js (מומלץ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ודאו את הגרסה שלכם: `node --version` אמור להציג `v24.0.0` או גרסה חדשה יותר בקו LTS של 24.x
3. התקינו מחדש את OmniRoute: `npm install -g omniroute`
4. הפעילו מחדש: `omniroute`

> **גרסאות מאובטחות נתמכות:** `>=22.22.2 <23` או `>=24.0.0 <27`. גרסאות Node.js 24.x LTS (Krypton) ו-Node.js 26 נתמכות באופן מלא.

### npm v11+: ‏`better-sqlite3` אינו מותקן (לא ניתן למצוא את המודול)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**סיבה:** npm v11 (המסופק עם Node.js 24 ומעלה) חוסם כברירת מחדל סקריפטים של התקנה עבור
תלויות אופציונליות. מכיוון ש-`better-sqlite3` מופיע תחת `optionalDependencies`
ודורש הידור מקומי (`node-gyp rebuild`), npm מדלג עליו ללא הודעה.

**תסמינים:**

- השרת קורס בעת ההפעלה עם `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` מציג "No such file or directory"
- `npm ls better-sqlite3` מציג `(empty)`

**פתרון:**

1. אשרו את סקריפטי ההתקנה והתקינו מחדש:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. לחלופין, התקינו ידנית את הקובץ הבינארי המוכן מראש:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ודאו שהוא פועל: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: ‏`dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**סיבה:** לאחר `npm install -g omniroute` גלובלי, ייתכן שהקובץ הבינארי המקומי של `better-sqlite3` שבתוך החבילה הודר עבור ארכיטקטורה או ABI של Node.js השונים מאלה שפועלים במחשב המקומי. מצב זה נפוץ ב-macOS (הן ב-Apple Silicon והן ב-Intel) כאשר הקובץ הבינארי שהוכן מראש אינו תואם לסביבה שלכם.

**תסמינים:**

- השרת נכשל מיד בעת ההפעלה עם שגיאת `dlopen`
- השגיאה מכילה `slice is not valid mach-o file`
- דוגמה מלאה:

```

```

**פתרון — בצעו בנייה מחדש עבור הסביבה המקומית שלכם (אין צורך בשדרוג לאחור של Node.js):**

npm rebuild better-sqlite3

## בעיות Proxy

<a name="proxy-issues"></a>

### אימות הספק מציג "fetch failed"

**סיבה:** נקודת הקצה לאימות מפתח ה-API (`POST /api/providers/validate`) עקפה בעבר את תצורת ה-proxy, דבר שגרם לכשלים בסביבות שדורשות ניתוב דרך proxy.

**תיקון (v3.5.5+):** הבעיה תוקנה. אימות הספק מנותב כעת דרך `runWithProxyContext`, תוך כיבוד אוטומטי של הגדרות ה-proxy ברמת הספק וההגדרות הגלובליות.

### בדיקת תקינות האסימון נכשלת עם "fetch failed"

**סיבה:** רענון אסימוני OAuth ברקע לא פתר את תצורת ה-proxy עבור כל חיבור בנפרד.

**תיקון (v3.5.5+):** מתזמן בדיקת תקינות האסימונים פותר כעת את תצורת ה-proxy עבור כל חיבור לפני ניסיון הרענון. יש לעדכן ל-v3.5.5+.

### Proxy מסוג SOCKS5 מחזיר "invalid onRequestStart method"

**סיבה:** ב-Node.js 22, ה-dispatcher של undici@8 אינו תואם למימוש המובנה של `fetch()` ב-Node.

**תיקון (v3.5.5+):** OmniRoute משתמש כעת בפונקציית `fetch()` של undici כאשר dispatcher של proxy פעיל, כדי להבטיח התנהגות עקבית. יש לעדכן ל-v3.5.5+.

### Proxy מסוג MITM תחת WSL: יישומי שולחן עבודה במארח Windows אינם מיורטים

**סיבה:** ה-proxy מסוג MITM ואישור ה-CA שלו מותקנים בסביבה שבה OmniRoute פועל. תחת WSL, סביבה זו היא אורח Linux, בעוד שיישומי הבינה המלאכותית לשולחן העבודה (Kiro, Trae, Copilot, Zed, …) פועלים במארח Windows. יישומי המארח אינם נותנים אמון במאגר האישורים של האורח ואינם מנותבים דרך ה-proxy המערכתי של האורח, ולכן יירוט יישומי שולחן העבודה אינו מופעל שם.

**המלצה:** הפעילו את OmniRoute באופן מקומי באותה מערכת הפעלה שבה פועלים יישומי שולחן העבודה שברצונכם ליירט (Windows עבור יישומי Windows; ובאופן דומה עבור macOS/Linux). השארת OmniRoute בתוך WSL תוך ניסיון ליירט יישומים במארח מחייבת מתן אמון ידני באישור ה-CA שנוצר במארח Windows והפניית הגדרות הרשת/ה-proxy של כל יישום במארח אל נקודת הקצה של ה-proxy ב-WSL — תצורה לא נתמכת ושברירית.

## בעיות Docker

### IPv6 / איפוס חיבור ב־Docker

<a name="docker-ipv6"></a>

**תסמינים:** `curl http://localhost:20128/v1/models` מחזיר `curl: (56) Recv failure: Connection reset by peer`. לוח הבקרה ונקודות קצה שאינן דורשות אימות פועלים, אך נקודות קצה מאומתות נכשלות — הדבר נראה כבעיית אימות, אך אינו כזה.

**סיבה:** הפקודה `docker run -p 20128:20128` מפרסמת הן ב־`0.0.0.0` ‏(IPv4) והן ב־`::` ‏(IPv6), אך התהליך בתוך הקונטיינר מאזין ל־IPv4 בלבד. במארחים שבהם `localhost` מתורגם תחילה ל־`::1`, החיבור מגיע ליציאת IPv6 שפורסמה ללא מאזין מאחוריה → החיבור מאופס.

**תיקון:**

1. **אבחון מהיר:** הריצו `curl -4 http://localhost:20128/v1/models`. אם הפקודה פועלת עם `-4` אך נכשלת בלעדיו, קיימת אי־התאמה בקישור ל־IPv6.
2. **תיקון קבוע:** קשרו במפורש ל־IPv4 באמצעות `-p 127.0.0.1:20128:20128` בפקודת `docker run` שלכם:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   פעולה זו כופה קישור ל־IPv4 וגם מונעת את חשיפת ה־proxy בכל ממשקי המארח.

## ניפוי שגיאות

### הפעלת קובצי יומן

מופעל בהגדרות.
כאשר לכידה בצינור העיבוד מופעלת, הגדירו `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` כדי להשמיט
מטענים של מקטעי הזרמה, או כווננו את `CALL_LOG_PIPELINE_MAX_SIZE_KB` כדי לשנות את מגבלת הארטיפקט ב־KB.

### בדיקת תקינות הספק

```bash
# לוח בקרת תקינות
http://localhost:20128/dashboard/health

# בדיקת תקינות API
curl http://localhost:20128/api/monitoring/health
```

### אחסון סביבת הריצה

- מצב ראשי: `${DATA_DIR}/storage.sqlite` (ספקים, שילובים, כינויים, מפתחות, הגדרות)
- שימוש: טבלאות SQLite ב־`storage.sqlite` ‏(`usage_history`, `call_logs`, `proxy_logs`) + ‏`${DATA_DIR}/call_logs/` אופציונלי

- ארטיפקטים של יומן הקריאות: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` כאשר צינור עיבוד יומן הקריאות מופעל

הפעולה **ניקוי היסטוריה** בדף יומני הבקשות מנקה את `call_logs`, את
`request_detail_logs` הישן ואת ספריית הארטיפקטים המקומית `${DATA_DIR}/call_logs/`.

### הגבלת הקצב האוטומטית אינה מופעלת

- הגבלת קצב אוטומטית חלה רק על ספקים המשתמשים במפתחות API (לא OAuth/מינוי)
- ודאו שבאפשרות **הגדרות → עמידות → פרופילי ספקים** מופעלת הגבלת קצב אוטומטית
- בדקו אם הספק מחזיר קודי מצב `429` או כותרות `Retry-After`

### כוונון השהיה מעריכית

פרופילי ספקים תומכים בהגדרות הבאות:

- **השהיית בסיס** — זמן ההמתנה הראשוני לאחר הכשל הראשון (ברירת מחדל: 1s)
- **השהיה מרבית** — הגבול העליון של זמן ההמתנה (ברירת מחדל: 30s)
- **מכפיל** — בכמה להגדיל את ההשהיה עבור כל כשל רצוף (ברירת מחדל: 2x)

### מניעת עדר רועם

כאשר בקשות מקביליות רבות מגיעות לספק עם הגבלת קצב, OmniRoute משתמש בנעילה הדדית ובהגבלת קצב אוטומטית כדי לבצע את הבקשות באופן סדרתי ולמנוע כשלים מתגלגלים. התהליך מתבצע אוטומטית עבור ספקים המשתמשים במפתחות API.

### בקשות צ'אט נכשלות עם 503 / chat_admission_busy

**תסמינים:**

- נקודת הקצה להשלמות צ'אט מחזירה תגובת `503` שניתן לנסות שוב, שקוד השגיאה שלה הוא
  `chat_admission_busy`.
- התגובה כוללת `Retry-After`. מאז #12135, הערך נגזר מהתפוסה שנצפתה —
  הגבוה מבין חלון `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` שבו הבקשה כבר המתינה לבין משך הזמן
  שבו ההקצאות הכבדות הנוכחיות מוחזקות — מעוגל כלפי מעלה לשניות שלמות ומוגבל ל-60.
  כאשר השער אינו עמוס, נשמרים ערכי הסף ההיסטוריים: 2 שניות בנתיב מבוסס-הבתים,
  ושנייה אחת בנתיב מבוסס-המבנה (הכולל גם `reason: "structure_limit"`).
- מצב זה עשוי להתרחש כאשר צ'אט כבד אחר או תגובת הזרמה ממושכת עדיין
  נמצאים בטיפול.

גוף התגובה מבוססת-הבתים הוא:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

התגובה מבוססת-המבנה משתמשת באותו סוג ובאותו קוד, עם ההודעה
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ועם `reason: "structure_limit"`.
בערכי הסף המוגדרים כברירת מחדל, בקשה נחשבת כבדה מבחינה מבנית כאשר היא מכילה לפחות `200` הודעות,
לפחות `64` כלים או לפחות `32,000` אסימונים משוערים, או כאשר אומדן המבנה המוגבל
ממצה את גבולותיו, שהם `10,000` צמתים שבוקרו או עומק `12`.

**הסיבה:** זוהי הפחתת עומס מכוונת בתוך OmniRoute, ולא כשל של ספק במעלה הזרם.
כל תהליך משתמש במנגנון הגנה מקומי לתהליך כדי לשריין קיבולת מוגבלת לבקשות כבדות לפני שמירת
גוף בקשה גדול וניתוחו. הקצאה כבדה נשארת מוחזקת לאורך כל חייה של תגובת SSE.

**הסתעפות #503:** לפני תיקון זה, מנגנון ההגנה הגביל את המקביליות למספר קבוע של בקשות
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ברירת מחדל `1`) ללא תלות בזיכרון המארח, ולכן
הסתעפות של סוכני תכנות (מספר תת-סוכנים/כלי CLI, עם גופי בקשות שגודלם בדרך כלל מעל 256 KB)
צמצמה את המקביליות האפקטיבית לכ-1 והובילה לשגיאות 503 תחת עומס רגיל לחלוטין.
מנגנון ההגנה מתאים את עצמו כעת באופן אוטומטי: הוא נשלט באמצעות תקציב בתים לקליטה
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), שנגזר אוטומטית ומחושב לפי מגבלת הזיכרון האמיתית
של התהליך, ובנוסף מתחשב באות חי של לחץ על המשאבים — כך שהוא מפחית עומס רק כאשר
המארח אכן נתון ללחץ זיכרון, ולא רק משום שיותר מבקשה כבדה אחת הגיעה בו-זמנית.
מגבלת הספירה הישנה (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) עדיין מכובדת, אך רק אם תגדירו
אותה במפורש.

כאשר הקיבולת תפוסה, בקשה כבדה ממתינה תחילה עד
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ברירת מחדל `2000`; הערך `0` משבית את ההמתנה) לפינוי מקום,
לפני החזרת תגובת `503` שניתן לנסות שוב. ההמתנה המוגבלת קיימת כדי שלקוחות מבוססי-סוכנים
(OpenCode, Claude Code, Cursor), המסתעפים לתת-בקשות כבדות במקביל, יבצעו את פרץ הבקשות
באופן סדרתי במקום לכלות את כל תקציב הניסיונות החוזרים שלהם על דחיות מיידיות ולהיכשל באמצע המשימה.
התפוסה הנוכחית של הקצאות כבדות, תקציב הבתים שחושב וחומרת הלחץ בזמן אמת
מוצגים ב-`GET /api/monitoring/health` ← `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — בדקו אותם לפני שינוי משתנה סביבה כלשהו.
הגדרות → עמידות → תור בקשות → בקשות מקביליות אינן שולטות בכך; הגדרה זו
שולטת במנגנון נפרד של תור בקשות לספק.

**תיקון:**

1. תחילה, נסו שוב. על הלקוחות לכבד את `Retry-After` ולהשתמש בהשהיה במקום לחזור מיד
   על הבקשה.
2. בדקו את `/api/monitoring/health` ← `chatAdmission` לפני כוונון כלשהו. `countCapEnabled:
false` ו-`maxInflightBytes` נדיב פירושם שהתקציב הנגזר אוטומטית כבר מבצע את
   תפקידו; `pressureSeverity` בערך `high`/`critical` פירושו שלמארח אכן חסר זיכרון —
   אי אפשר לתקן זאת באמצעות משתנה סביבת קבלה; נדרש יותר RAM או עומס עבודה קטן יותר.
3. רק אם `/api/monitoring/health` מראה שהתקציב הנגזר אוטומטית אכן קטן מדי עבור
   המארח שלכם (מצב נדיר — הוא כבר מותאם החל מקונטיינר ועד bare-metal), דרסו אותו ישירות באמצעות
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, במקום לחזור למגבלה הישנה המבוססת על מספר בקשות.

עיינו ב[הפניה למשתני הסביבה](../reference/ENVIRONMENT.md#4-security--authentication)
לקבלת הגדרות הקבלה המוסמכות.

## טקסונומיית כשלים אופציונלית עבור RAG / LLM‏ (16 בעיות)

חלק ממשתמשי OmniRoute מציבים את השער לפני מערכי RAG או סוכנים. בתצורות כאלה נפוץ לראות דפוס מוזר: OmniRoute נראה תקין (הספקים פעילים, פרופילי הניתוב תקינים, אין התראות על הגבלת קצב), אך התשובה הסופית עדיין שגויה.

בפועל, תקריות אלה נובעות בדרך כלל מצינור עיבוד ה-RAG שבהמשך המערכת, ולא מהשער עצמו.

אם אתם רוצים אוצר מילים משותף לתיאור כשלים אלה, תוכלו להשתמש ב-WFGY ProblemMap, משאב טקסט חיצוני ברישיון MIT המגדיר שישה-עשר דפוסי כשל חוזרים של RAG / LLM. ברמה כללית, הוא עוסק בנושאים הבאים:

- סטייה באחזור וגבולות הקשר שבורים
- אינדקסים ומאגרי וקטורים ריקים או מיושנים
- חוסר התאמה בין הטמעות לבין סמנטיקה
- בעיות בהרכבת פרומפט ובחלון ההקשר
- קריסה לוגית ותשובות בעלות ביטחון מופרז
- כשלים בשרשראות ארוכות ובתיאום בין סוכנים
- סטייה בזיכרון ובתפקידים במערכות מרובות סוכנים
- בעיות בסדר הפריסה והאתחול הראשוני

הרעיון פשוט:

1. בעת חקירת תשובה שגויה, תעדו:
   - את משימת המשתמש והבקשה
   - את שילוב הנתיב או הספק ב-OmniRoute
   - כל הקשר RAG שבו נעשה שימוש בהמשך המערכת (מסמכים שאוחזרו, קריאות לכלים וכדומה)
2. שייכו את התקרית למספר אחד או שניים ב-WFGY ProblemMap‏ (`No.1` … `No.16`).
3. שמרו את המספר בלוח הבקרה, בספר הנהלים או במערכת מעקב התקריות שלכם, לצד יומני OmniRoute.
4. השתמשו בעמוד WFGY המתאים כדי להחליט אם עליכם לשנות את מערך ה-RAG, את מנגנון האחזור או את אסטרטגיית הניתוב שלכם.

הטקסט המלא ומתכונים מעשיים זמינים כאן (רישיון MIT, טקסט בלבד):

[README של WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

אפשר להתעלם מסעיף זה אם אינכם מפעילים צינורות עיבוד של RAG או סוכנים מאחורי OmniRoute.

## בעיות ידועות ב-v3.8.0

בעיות הייחודיות לגרסת v3.8.0 והפתרונות הזמניים הנוכחיים שלהן. אם תיקון ייכלל בגרסת תיקונים מאוחרת יותר, הרשומה תעודכן או תוסר.

### כשלים באימות Devin CLI

**תסמינים:**

- "Devin CLI לא נמצא" או "האימות נכשל" בעת הפעלת כלים המבוססים על Devin
- בדיקת זמן הריצה של ה-CLI מדווחת `installed=false`

**גורמים:**

- `CLI_DEVIN_BIN` מצביע על נתיב שאינו קיים
- Devin CLI אינו מותקן במארח

**תיקון:**

1. התקינו את Devin CLI עבור הפלטפורמה שלכם
2. הגדירו `CLI_DEVIN_BIN=/usr/local/bin/devin` (או את הנתיב האמיתי) בקובץ `.env`
3. הפעילו מחדש את OmniRoute ובדקו שוב דרך **לוח הבקרה → כלי CLI**

### מצב הצינון של המודל תקוע (איפוס ידני)

**תסמינים:**

- מודל נשאר ברשימת הצינון גם לאחר שזמן התפוגה חלף
- בקשות עדיין מדלגות על המודל בניתוב משולב, אף שחותמת הזמן היא בעבר

**איפוס ידני:**

- **לוח הבקרה:** **הגדרות → זמני צינון של מודלים** → לחצו על **הפעלה מחדש** בכרטיס המושפע
- **API:**‏ `DELETE /api/resilience/model-cooldowns` עם כותרות אימות לניהול

### החיבור לספק Command Code נכשל עם 403

**תסמינים:**

- מתקבלת שגיאת 403 בעת בדיקת החיבור לספק Command Code
- בכרטיס הספק מופיע "לא מורשה" לאחר הוספה חדשה

**גורם:** תהליך OAuth לא הושלם (קריאת החזרה לא התקבלה או שהאסימון לא נשמר).

**תיקון:**

- הריצו `omniroute providers` דרך ה-CLI כדי להפעיל מחדש את תהליך OAuth, או
- הפעילו מחדש את OAuth דרך **לוח הבקרה → ספקים → Command Code → התחברות מחדש**

### ModelScope מחזיר זמני צינון אגרסיביים מסוג 429

**תסמינים:**

- זמני צינון קצרים מאוד או מיידיים ב-ModelScope לאחר רצף קטן של בקשות
- ניתוב משולב מדלג על ModelScope מוקדם מהצפוי

**גורם:** ModelScope שולח כותרות `Retry-After` ייחודיות לספק. v3.8.0 כולל טיפול ייעודי בכותרות אלה, ולכן גרסאות ישנות יותר מפרשות אותן באופן שגוי כרמזים כלליים להגבלת קצב.

**תיקון:**

- ודאו שאתם משתמשים ב-v3.8.0 או בגרסה מאוחרת יותר
- ודאו שהמתג `useUpstream429BreakerHints` מופעל תחת **הגדרות → עמידות**

### OMNIROUTE_WS_BRIDGE_SECRET חסר בסביבת הייצור

**תסמינים:**

- שגיאת 401 בכל בקשת גשר WebSocket של Codex/Responses בעת הפעלה במארח ייצור מרוחק
- לחיצת היד של גשר WebSocket נסגרת מיד לאחר ההתחברות

**גורם:** משתנה הסביבה `OMNIROUTE_WS_BRIDGE_SECRET` חסר בסביבת הייצור.

**תיקון:**

1. צרו סוד אקראי: `openssl rand -hex 32`
2. הגדירו `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` בסביבת שרת הייצור (ובכל לקוח שמתקשר עם הגשר)
3. הפעילו מחדש את OmniRoute

### Responses API: מצב הרקע מופעל באופן סינכרוני מצומצם

**תסמינים:**

- נרשמת האזהרה: `background mode degraded to synchronous`
- בקשה עם `background: true` מחזירה תגובה סינכרונית רגילה במקום מזהה של משימת רקע

**גורם:** ב-v3.8.0, הפעלה עם `background: true` ב-Responses API עוברת בכוונה לביצוע סינכרוני תוך הפקת אזהרה. ביצוע אסינכרוני מלא ברקע מתוכנן לעתיד.

**תיקון:**

- התאימו את הלקוח כך שיבצע את הקריאה ללא `background`, או
- המתינו לגרסה מאוחרת יותר שתכלול מצב רקע אסינכרוני מלא (עקבו אחר יומן השינויים)

## הפעלה איטית / פסק זמן של בדיקת המוכנות

אם ה-CLI מציג `⚠ Server did not respond within 60s` אך השרת פועל
בפועל, משך הזמן שהוקצה לבדיקת המוכנות קצר מדי עבור הסביבה שלך.

מצב זה נפוץ ב-Windows (אנטי-וירוס, מנטרי מערכת קבצים) או בקונטיינרים
עם עומסי עבודה כבדים בעת ההפעלה.

**פתרון — הגדלת משך הזמן המוקצה:**

```bash
# באמצעות משתנה סביבה (נשמר בין הפעלות):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 דקות
omniroute serve

# באמצעות דגל CLI (חד-פעמי):
omniroute serve --ready-timeout 180000
```

ברירת המחדל היא 60 000 מילישניות (60 שניות). האזהרה מיועדת למידע בלבד; השרת
ממשיך לעלות ברקע ויהיה נגיש לאחר השלמת האתחול.

לפרטים מלאים על `OMNIROUTE_READY_TIMEOUT_MS`, ראו
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
