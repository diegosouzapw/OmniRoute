## עיון מהיר

**חדשים ב-OmniRoute?** התחילו כאן — פתרונות אלה מכסים 90% מהבעיות:

| אני רואה את זה             | מה זה אומר                          | מה לעשות                                                                                    |
| -------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------- |
| "לא ניתן להתחבר"           | OmniRoute אינו פועל                 | הפעילו את `omniroute` או את `docker restart omniroute`                                      |
| "מפתח API לא תקין"         | המפתח שלכם שגוי או שפג תוקפו        | העתיקו מחדש את המפתח מאתר הספק                                                              |
| "חריגה ממגבלת הקצב"        | אתם שולחים יותר מדי בקשות           | המתינו דקה אחת, או השתמשו ב-`model: "auto"` למעבר אוטומטי לחלופה                            |
| "חריגה מהמכסה"             | ניצלתם את מלוא המכסה החינמית/בתשלום | חברו ספקים נוספים, או השתמשו בספקים חינמיים (Kiro, Pollinations)                            |
| "תגובות איטיות"            | הספק עמוס או מרוחק                  | השתמשו ב-`model: "auto/fast"` או חברו ספק מהיר יותר (Groq, Cerebras)                        |
| "נעשה שימוש בספק הלא נכון" | `auto` בחר ספק אחר                  | זה תקין! `auto` בוחר את האפשרות הטובה ביותר. כפו ספק מסוים באמצעות `model: "openai/gpt-4o"` |
| "502 שער לא תקין"          | הספק אינו זמין                      | המתינו ונסו שוב, או השתמשו ב-`model: "auto"` כדי לעבור בין ספקים                            |
| "401 לא מורשה"             | פרטי הגישה שלכם שגויים              | בדקו את מפתח ה-API או בצעו אימות מחדש באמצעות OAuth                                         |
| "429 יותר מדי בקשות"       | הקצב הוגבל                          | המתינו דקה אחת, או חברו ספקים נוספים                                                        |

## פתרון בעיות מפורט

---

### הגבלת קצב אצל ספקים חינמיים (429 / 400 / 401)

**תסמין**: בעת שימוש ב-`model: "auto"` עם ספקים חינמיים/ללא אימות (opencode, auggie וכו'), מתקבל לסירוגין `HTTP 429`,‏ `400` או `401` במקום תשובות. הבקשות מצליחות כשמנסים שוב את אותה ההנחיה כעבור רגעים אחדים, אך תהליכים אוטומטיים (משימות cron, סוכנים, סקריפטים) נכשלים בשגיאה הראשונה.

**גורם שורש**: שלושה מצבי כשל בלתי תלויים מצטברים:

1. **הגבלת קצב מצד הספק (`429`)**: מסלולים חינמיים עשויים לאכוף מכסה לכל חלון זמן. פרץ של קריאות מקבילות מנצל אותה במלואה, ולכן הבקשה הבאה נדחית עד לאיפוס החלון.
2. **מודל פגום במעבר ישיר (`400`/`401`)**: מאגרי `auto/*` עשויים לכלול מודלים במעבר ישיר מ-`opencode`, הרשומים בקטלוג אך ללא פרטי גישה פעילים (למשל `oc/north-mini-code-free` ← `401`). הנתב האוטומטי מנסה אחד מהם, נכשל, והשגיאה מועברת הלאה לפני שהמעבר לחלופה נכנס לפעולה.
3. **הגברה עקב מקביליות (`429` תחת עומס)**: כאשר כמה הפעלות של סוכנים/משימות cron פונות אל `auto` בו-זמנית, קצב הבקשות המצטבר חורג ממה שספקים חינמיים מסוגלים לקבל, ולכן קריאות לגיטימיות מסומנות כפוגעניות.

**תיקון מאומת (דווח על ידי הקהילה, 2026-08-10)**: כווננו שלושה משתני סביבה כך שרוטציה, מקביליות ומעבר לחלופה יספגו את התנודתיות של המסלול החינמי במקום להיכשל בגללה:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # מעבר למודל/ספק אחר בתגובת 400/401 (מדלג על מודלים פגומים במעבר ישיר)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # תקרת קבלה מפורשת לבקשות כבדות (אינה מוגדרת כברירת מחדל: אין מגבלה על מספר הבקשות, ראו הערה להלן)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # המתנה מוגבלת ארוכה יותר לקיבולת של בקשות כבדות, במקום שגיאת 503 מיידית שניתנת לניסיון חוזר
```

הגדירו אותם בסביבת התהליך של OmniRoute (הדמון, למשל באמצעות קובץ ה-plist של LaunchAgent או `systemctl edit`), ולאחר מכן הפעילו מחדש את OmniRoute. דגל הרוטציה הוא המנוף היחיד בעל ההשפעה הגדולה ביותר: הוא הופך כשל מוחלט לניסיון חוזר שקוף מול ספק תקין במאגר.

**הערה**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` מגביל את מספר הבקשות הכבדות — בעלות הקשר ארוך — שפועלות בו-זמנית; המגבלה היא שער קבלה ולא מגביל קצב של ספק. **עדכון #503-fanout:** משתנה זה אינו מוגדר עוד כברירת מחדל (כעת הוא נכנס לתוקף רק כאשר הוא מוגדר במפורש, כמו לעיל) — במקום זאת, קבלת בקשות כבדות מוגבלת באמצעות תקציב בתים שנגזר אוטומטית (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), המתאים את עצמו למגבלת הזיכרון האמיתית של המארח. לכן, בפריסה חדשה אמורות להופיע הרבה פחות דחיות `503 chat_admission_busy`, גם בלי להגדיר משתנה זה כלל; הגדרה מפורשת שלו כאן עדיין פועלת בדיוק כפי שמתועד. דריסות מפורשות של תקציב הבתים מוגבלות לטווח של 8 MiB–2 GiB. שגיאת `413 body_exceeds_budget` אינה זמנית: הגדילו את תקציב הבתים, הקטינו את `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`, או הגדילו את מגבלת הזיכרון של התהליך. השלת עומס מסוג `inflight_bytes_budget` היא תחרות זמנית על משאבים וניתן לנסות שוב. הגבלת הקצב לכל ספק (`open-sse/services/rateLimitManager.ts`) נשלטת בנפרד באמצעות `RATE_LIMIT_MAX_WAIT_MS`,‏ `RATE_LIMIT_MAX_QUEUE_DEPTH` ו-`RATE_LIMIT_AUTO_ENABLE` — ראו `.env.example`.

**כיצד לוודא שהתיקון הצליח**: הפעילו את הסוכן/משימת ה-cron שלכם פעמיים ברצף מהיר וודאו ששתי ההפעלות מצליחות. לפני התיקון, ההפעלה השנייה מחזירה בדרך כלל `429`/`401`. לאחר התיקון, ניסיונות שנכשלו (אם יש כאלה) מתבצעים מחדש באופן שקוף והקריאה מסתיימת בהצלחה. תוכלו גם להפעיל `curl /monitoring/health` ולעקוב אחר השדה `rateLimitedUntil` בחיבורי הספקים ואחר `circuitBreakers.providerBreakers[].state` עבור הספקים המושפעים — המצב הוא אחד מהבאים: `CLOSED`,‏ `DEGRADED`,‏ `OPEN` או `HALF_OPEN` (ראו `src/shared/utils/circuitBreaker.ts`), וספק שממשיך להיכשל יעבור בין המצבים `CLOSED → DEGRADED → OPEN` לפני שחלון האיפוס יאפשר לבקשת בדיקה לעבור (`HALF_OPEN`).

**אם עדיין מופיעה שגיאת 429**: החשבון הפעיל של אותו ספק מיצה בפועל את ה_מכסה_ שלו (ולא רק הגיע למגבלת הקצב). הוסיפו חשבון נוסף עבור אותו ספק בלוח הבקרה של OmniRoute ← ספקים ← חשבונות, או שלבו ספק חינמי אחר (למשל `routeway`,‏ `auggie`). רוטציה עוזרת רק בשגיאות זמניות של מגבלת קצב/400/401; מיצוי מוחלט של המכסה מחייב פרטי גישה נוספים או ספק אחר.

**אם מופיעה שגיאת 403 במודלי ראייה (`auto/vision`,‏ `bazaarlink/*`)**: לחשבון המחובר אין תוכנית בתשלום הכוללת יכולות ראייה, או שלמפתח ה-API אין הרשאות מספיקות. ודאו בלוח הבקרה של הספק שהיקף ההרשאות של המפתח כולל ראייה/ריבוי אופנים, או חברו חשבון ברובד בתשלום והגדירו אותו כיעד הראייה.

## אזהרות npm install‏ (ERESOLVE / תלויות עמית / deprecated)

בעת הרצת `npm install -g omniroute`, ייתכן שתראו שורה ארוכה של אזהרות כגון `npm warn ERESOLVE`, הודעות על תלויות עמית והודעות `deprecated`. **אזהרות אלה צפויות ואינן מזיקות.** ההתקנה הצליחה אם מופיע בפלט `added <N> packages`.

כדי להסתיר את אזהרות פתרון תלויות העמית, השתמשו בצורת ההתקנה הנתמכת של OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` מסתיר רק את `ERESOLVE` ואת ההודעות על תלויות עמית. הודעות על הוצאה משימוש יישארו גלויות משום שהן מגיעות מחבילות צד שלישי עקיפות; הן אינן מעידות שההתקנה נכשלה.

האזהרות נובעות מטווחים מיושנים של תלויות עמית בחבילות צד שלישי שאינן בשליטת OmniRoute:

1. **`marked-terminal` דורשת `marked >=1 <16`, אך נמצאה `marked@18`** — בפועל היא פועלת כראוי; טווח תלויות העמית של המקור פשוט מיושן.
2. **`deprecated prebuild-install@7.1.3`** — כלי עזר עקיף לאחזור קבצים בינאריים מקוריים. הוא אינו
   משמש להתקנת קישור התעבורה המקובע `wreq-js` ואינו מעיד שהגדרת התעבורה של ספק קובצי ה-Cookie לאינטרנט
   נכשלה.

**אין צורך בפעולה** — לא ניתן להשתיק לחלוטין את האזהרות ללא פיצול חבילות המקור.

## זיהויים חיוביים שגויים של אנטי-וירוס

<a name="antivirus-false-positives"></a>

### Avast/AVG מעבירים את `README.md` להסגר עם `MD:HttpRequest-inf[Susp]`

**זהו זיהוי חיובי שגוי. דבר אינו נגוע, ואין צורך לבצע שום פעולה.**

Avast ו-AVG מפעילים מנגנון היוריסטי שמסמן קובצי טקסט פשוט/Markdown המכילים קישורים רבים
שנראים כמו בקשות HTTP. הקובץ `README.md` של OmniRoute מופץ בתוך חבילת npm (הוא
מופיע ב-`package.json` ← `files`), ולכן בהתקנה גלובלית הוא נשמר ב-`node_modules/omniroute/README.md`
— והוא מכיל כ-15 דוגמאות של `http://localhost:20128/...` (נקודות הקצה HTTP/SSE של MCP,
כתובת ה-`.well-known` של A2A וקטעי `curl`). צפיפות הקישורים הזאת מספיקה כדי להפעיל
את המנגנון ההיוריסטי.

אם הדבר התחיל רק לאחרונה: סוג הקובץ לא השתנה. טבלת נקודות הקצה בקובץ README הורחבה
(נוספו MCP HTTP‏ + SSE‏ + A2A), ונוספו דוגמאות `curl`, מה שגרם לו לעבור
את סף הזיהוי.

הקובץ הוא תיעוד פסיבי שאינו מכיל תוכן בר-הרצה כלל. ניתן לשחזר אותו בבטחה
מההסגר.

**מה לעשות:**

1. **להפסיק את ההתראות** — החריגו את תיקיית ההתקנה באנטי-וירוס שלכם
   (Avast: הגדרות ← חריגים), והוסיפו את נתיב `node_modules` הגלובלי שלכם ו/או את
   תיקיית הנתונים של OmniRoute‏ (`~/.omniroute/`).
2. **לדווח על הזיהוי החיובי השגוי** — <https://www.avast.com/false-positive-file-form.php>,
   ולצרף את `README.md` שהועבר להסגר. זהו התיקון שמסייע לכולם, מכיוון שהמנגנון
   ההיוריסטי של הספק מגיב בצורה מופרזת לקובץ טקסט.

**מדוע איננו "מתקנים" זאת בצד שלנו:** כל הדוגמאות משתמשות ב-`http://localhost`,
ולא ניתן להשתמש ב-`https` עבור localhost בלי החיכוך הכרוך באישורים בחתימה עצמית.
שיבוש התיעוד כדי להתחמק מהמנגנון ההיוריסטי של ספק אחד יפגע בכל הקוראים רק כדי
לרצות סורק שסובל מבאג.

### Kaspersky מסמן את יישום שולחן העבודה בתור `PDM:Trojan.Win32.Generic`

**זהו זיהוי חיובי שגוי שמקורו במנגנון היוריסטי התנהגותי. דבר אינו נגוע.** התחילית
`PDM:` של Kaspersky מציינת שההכרעה מגיעה ממודול ההגנה היזומה שלו (System Watcher),
אשר בוחן מה תוכנית ההתקנה _עושה_ במקום להשוות אותה לתוכנות זדוניות מוכרות. כאשר
הוא מופעל, Kaspersky "מחזיר לאחור" את ההתקנה כולה — ומוחק קבצים שכבר נכתבו
— ולכן היישום נותר פגום או חסר.

הקבצים שהוא מסמן הם רכיבים רגילים של תלויות מוצהרות בקוד פתוח, המצורפות ליישום
שולחן העבודה, לדוגמה:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ו-
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ספריית האוטומציה לדפדפנים
  המשמשת להתחברות לספקים מתוך היישום ולצ'אט המבוסס על דפדפן.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — הקישור המקומי המקובע של `wreq-js`, המשמש ל-HTTP בעל טביעת אצבע של דפדפן אצל ספקים
  המבוססים על קובצי Cookie מהאינטרנט (`<arch>` הוא `x64` או `arm64`).

**מדוע הוא מופעל:** תוכנית ההתקנה ל-Windows **עדיין אינה חתומה בחתימת קוד**, ולכן
לתוכנית התקנה בלתי חתומה של NSIS אין שום מוניטין, ומנגנונים היוריסטיים התנהגותיים
פועלים ברמת האגרסיביות המרבית. בשילוב עם DLL מקומי מצורף ומאות קובצי `.js` שנכתבים
תחת `%LOCALAPPDATA%\Programs\OmniRoute` (לרבות תיקיות חבילות עם סיומות hash מבניית
ה-standalone של Next.js), די בכך כדי להפעיל את המנגנון ההיוריסטי. חתימת קוד מתוכננת;
עד שהיא תיושם, הבעיה עלולה לחזור במהדורות חדשות.

**מה לעשות:**

1. **אמתו תחילה את ההורדה שלכם** (כדי לשלול אפשרות שהקובץ שונה בזדון). בכל מהדורה מתפרסם
   `latest.yml`, שהשדה `sha512` שלו (base64) מכסה את תוכנית ההתקנה
   `OmniRoute.Setup.<version>.exe`. ב-PowerShell, מתוך התיקייה המכילה את תוכנית ההתקנה:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   הפלט חייב להתאים ל-`latest.yml` ← `sha512`. אם אינו מתאים, מחקו את הקובץ
   והורידו אותו מחדש רק מ[דף המהדורות ב-GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **שחזור + החרגה** — שחזרו מההסגר את הפריטים שנמחקו במהלך ההחזרה לאחור והוסיפו החרגה
   עבור `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky ← הגדרות ← איומים והחרגות),
   ולאחר מכן התקינו מחדש.
3. **דיווח על הזיהוי החיובי השגוי** — <https://opentip.kaspersky.com/>. דוחות על זיהויים
   חיוביים שגויים שמגישים משתמשים אכן מאיצים את ההוספה לרשימת ההיתרים.

## תאימות ל-Node.js

<a name="nodejs-compatibility"></a>

### דף הכניסה קורס או מציג שגיאת "Module self-registration"

**סיבה:** מופעלת גרסת Node.js שאינה עומדת ברף סביבת ההרצה המאובטחת המאושרת של OmniRoute. המקרה הנפוץ ביותר הוא שימוש בגרסת תיקון ישנה יותר של Node 22 או 24, הנמוכה מרף האבטחה המתוקן ש-OmniRoute דורש.

**תסמינים:**

- דף הכניסה מציג מסך ריק או שגיאת שרת
- המסוף מציג `Error: Module did not self-register` או שגיאות דומות של קישור מקורי
- דף הכניסה מציג **כרזת אזהרה כתומה** עם גרסת ה-Node שלכם אם סביבת ההרצה אינה תואמת למדיניות המאובטחת הנתמכת

**פתרון:**

1. התקינו מהדורת LTS נתמכת של Node.js (מומלץ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ודאו את הגרסה שלכם: `node --version` אמורה להציג `v24.0.0` או גרסה חדשה יותר בקו ה-LTS של 24.x
3. התקינו מחדש את OmniRoute: `npm install -g omniroute`
4. הפעילו מחדש: `omniroute`

> **גרסאות מאובטחות נתמכות:** `>=22.22.2 <23` או `>=24.0.0 <27`. קיימת תמיכה מלאה ב-Node.js 24.x LTS (Krypton) וב-Node.js 26.

### npm v11+: ‏`better-sqlite3` אינו מותקן (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**סיבה:** npm v11 (המצורפת ל-Node.js 24+) חוסמת כברירת מחדל סקריפטים להתקנה עבור
תלויות אופציונליות. מכיוון ש-`better-sqlite3` רשומה תחת `optionalDependencies`
ודורשת הידור מקורי (`node-gyp rebuild`), npm מדלגת עליה ללא הודעה.

**תסמינים:**

- השרת קורס בעת ההפעלה עם `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` מציגה "No such file or directory"
- `npm ls better-sqlite3` מציגה `(empty)`

**פתרון:**

1. אשרו את סקריפטי ההתקנה והתקינו מחדש:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. לחלופין, התקינו ידנית את החבילה שהודרה מראש:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ודאו שהיא פועלת: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: ‏`dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**סיבה:** לאחר `npm install -g omniroute` גלובלי, ייתכן שהקובץ הבינארי המקורי של `better-sqlite3` בתוך החבילה הודר עבור ארכיטקטורה או ABI של Node.js השונים מאלה שפועלים באופן מקומי. מצב זה נפוץ ב-macOS (הן ב-Apple Silicon והן ב-Intel) כאשר הקובץ הבינארי שהודר מראש אינו תואם לסביבה שלכם.

**תסמינים:**

- השרת נכשל מיד בעת ההפעלה עם שגיאת `dlopen`
- השגיאה מכילה `slice is not valid mach-o file`
- דוגמה מלאה:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**פתרון — הידור מחדש עבור הסביבה המקומית שלכם (ללא צורך בשנמוך Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **הערה:** פעולה זו מהדרת מחדש את הקישור המקורי מול גרסת ה-Node.js המקומית וארכיטקטורת המעבד שלכם, וכך פותרת את אי-ההתאמה הבינארית. טווח סביבת ההרצה הנתמך רשמית הוא **`>=22.22.2 <23` או `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` בתוך `src/shared/utils/nodeRuntimeSupport.ts`, בהתאמה לשדה `engines` של `package.json`). קיימת תמיכה מלאה ב-Node.js 24.x LTS (Krypton) וב-Node.js 26 עם `better-sqlite3` v12.x.

## בעיות Proxy

<a name="proxy-issues"></a>

### אימות הספק מציג "fetch failed"

**סיבה:** נקודת הקצה לאימות מפתח ה-API (`POST /api/providers/validate`) עקפה בעבר את תצורת ה-Proxy, דבר שגרם לכשלים בסביבות שדורשות ניתוב דרך Proxy.

**תיקון (v3.5.5+):** הבעיה תוקנה. אימות הספק מנותב כעת דרך `runWithProxyContext`, תוך כיבוד אוטומטי של הגדרות ה-Proxy ברמת הספק וברמה הגלובלית.

### בדיקת תקינות האסימון נכשלת עם "fetch failed"

**סיבה:** רענון אסימון OAuth ברקע לא פתר את תצורת ה-Proxy עבור כל חיבור בנפרד.

**תיקון (v3.5.5+):** מתזמן בדיקת תקינות האסימונים פותר כעת את תצורת ה-Proxy עבור כל חיבור לפני ניסיון הרענון. יש לעדכן ל-v3.5.5+.

### Proxy מסוג SOCKS5 מחזיר "invalid onRequestStart method"

**סיבה:** ב-Node.js 22, המנתב של undici@8 אינו תואם למימוש `fetch()` המובנה של Node.

**תיקון (v3.5.5+):** OmniRoute משתמש כעת בפונקציית `fetch()` של undici עצמו כאשר מנתב Proxy פעיל, כדי להבטיח התנהגות עקבית. יש לעדכן ל-v3.5.5+.

### Proxy מסוג MITM תחת WSL: יישומי שולחן עבודה במארח Windows אינם מיורטים

**סיבה:** ה-Proxy מסוג MITM ואישור ה-CA שלו מותקנים בסביבה שבה OmniRoute פועל. תחת WSL, סביבה זו היא אורח ה-Linux, בעוד שיישומי שולחן העבודה מבוססי ה-AI‏ (Kiro, Trae, Copilot, Zed, …) פועלים במארח Windows. יישומי המארח אינם נותנים אמון במאגר האישורים של האורח ואינם מנותבים דרך ה-Proxy המערכתי של האורח, ולכן יירוט תעבורת שולחן העבודה אינו מופעל שם.

**המלצה:** הפעילו את OmniRoute באופן מקומי באותה מערכת הפעלה שבה פועלים יישומי שולחן העבודה שברצונכם ליירט (Windows עבור יישומי Windows; ובדומה לכך macOS/Linux). השארת OmniRoute בתוך WSL תוך ניסיון ליירט יישומים במארח מחייבת לתת אמון ידני באישור ה-CA שנוצר במארח Windows ולהפנות את הגדרות הרשת/Proxy של כל יישום במארח אל נקודת הקצה של ה-Proxy ב-WSL — זוהי תצורה לא נתמכת ושברירית.

1. לוח הבקרה → ספק → התחברות מחדש
2. מחקו והוסיפו מחדש את חיבור הספק

### ריבוי חשבונות Kiro: החשבון השני מבטל את תוקף הראשון

**סיבה:** ה-Backend של Kiro אוכף הפעלה פעילה יחידה לכל רישום לקוח OIDC.
כאשר שני חשבונות חולקים את אותו לקוח רשום (חיבורים שיובאו לפני v3.8.0),
רענון האסימון של חשבון אחד מבטל את התוקף של אסימון הרענון של החשבון האחר.

**תיקון (v3.8.0+):** ייבאו מחדש את החיבורים המושפעים.
החל מ-v3.8.0, כל חיבור Kiro חדש שנוצר באמצעות **ייבוא אסימון**,
**התחברות חברתית באמצעות Google/GitHub**, או **ייבוא אוטומטי**, רושם באופן אוטומטי
לקוח OIDC ייעודי משלו. לכן החיבור מבודד לחלוטין, ורענון של חשבון אחד
אינו משפיע על אף חשבון אחר.

חיבורים שיובאו _לפני_ v3.8.0 אינם כוללים רישום לקוח נפרד לכל חיבור.
חיבורים אלה ממשיכים להשתמש בנקודת הקצה המשותפת לרענון אימות חברתי.
כדי להשיג בידוד, מחקו את החיבור הישן מלוח הבקרה → ספקים והוסיפו אותו מחדש
באמצעות אחד משלושת תהליכי הייבוא.

לפרטים מלאים ולהוראות מפורטות להוספת שני חשבונות Kiro זה לצד זה,
ראו [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## בעיות Docker

### IPv6 / איפוס חיבור ב-Docker

<a name="docker-ipv6"></a>

**תסמינים:** `curl http://localhost:20128/v1/models` מחזיר `curl: (56) Recv failure: Connection reset by peer`. לוח הבקרה ונקודות קצה שאינן דורשות אימות פועלים, אך נקודות קצה מאומתות נכשלות — הדבר נראה כמו בעיית אימות, אך אינו כזה.

**סיבה:** `docker run -p 20128:20128` מפרסם הן ב-`0.0.0.0` ‏(IPv4) והן ב-`::` ‏(IPv6), אך התהליך בתוך הקונטיינר מאזין רק ב-IPv4. במארחים שבהם `localhost` מתורגם תחילה ל-`::1`, החיבור מגיע ליציאה שפורסמה ב-IPv6, בלי תהליך שמאזין מאחוריה ← החיבור מתאפס.

**תיקון:**

1. **אבחון מהיר:** הריצו `curl -4 http://localhost:20128/v1/models`. אם הפקודה פועלת עם `-4` אך נכשלת בלעדיו, קיימת אי-התאמה בקישור ל-IPv6.
2. **תיקון קבוע:** קשרו במפורש ל-IPv4 באמצעות `-p 127.0.0.1:20128:20128` בפקודת `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   פעולה זו מאלצת קישור ל-IPv4 וגם מונעת את חשיפת הפרוקסי בכל ממשקי המארח.

## איתור באגים

### הפעלת קובצי יומן

הגדירו `APP_LOG_TO_FILE=true` בקובץ `.env` שלכם. יומני היישום נכתבים תחת `logs/`.
תוצרי הבקשות נשמרים תחת `${DATA_DIR}/call_logs/` כאשר צינור עיבוד יומן הקריאות
מופעל בהגדרות.
כאשר לכידת צינור העיבוד מופעלת, הגדירו `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` כדי להשמיט
מטענים של מקטעי הזרמה, או התאימו את `CALL_LOG_PIPELINE_MAX_SIZE_KB` כדי לשנות את מגבלת התוצר ב-KB.

### בדיקת תקינות הספק

```bash
# לוח בקרת תקינות
http://localhost:20128/dashboard/health

# בדיקת תקינות API
curl http://localhost:20128/api/monitoring/health
```

### אחסון סביבת הריצה

- מצב ראשי: `${DATA_DIR}/storage.sqlite` (ספקים, שילובים, כינויים, מפתחות, הגדרות)
- שימוש: טבלאות SQLite בתוך `storage.sqlite` ‏(`usage_history`, `call_logs`, `proxy_logs`) + `${DATA_DIR}/call_logs/` אופציונלי
- יומני היישום: `<repo>/logs/...` (כאשר `APP_LOG_TO_FILE=true`)
- תוצרי יומן הקריאות: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` כאשר צינור עיבוד יומן הקריאות מופעל

הפעולה **ניקוי היסטוריה** בדף יומני הבקשות מנקה את `call_logs`, את
`request_detail_logs` הישן ואת ספריית התוצרים המקומית `${DATA_DIR}/call_logs/`.

- **ה-SDK מחזיר מחרוזת גולמית במקום אובייקט** — נפתר ב-v1.x; מנקה התגובות מסיר שדות לא תקניים (`x_groq`, `usage_breakdown` וכו') שגורמים לכשלי אימות Pydantic של OpenAI SDK. אם הבעיה עדיין מופיעה ב-v3.x+, פתחו דיווח על בעיה.
- **GLM/ERNIE דוחה את התפקיד `system`** — נפתר ב-v1.x; מנרמל התפקידים ממזג אוטומטית הודעות מערכת לתוך הודעות משתמש עבור מודלים שאינם תואמים. אם הבעיה עדיין מופיעה ב-v3.x+, פתחו דיווח על בעיה.
- **התפקיד `developer` אינו מזוהה** — נפתר ב-v1.x; מומר אוטומטית ל-`system` עבור ספקים שאינם OpenAI. אם הבעיה עדיין מופיעה ב-v3.x+, פתחו דיווח על בעיה.
- **`json_schema` אינו פועל עם Gemini** — נפתר ב-v1.x; `response_format` מומר כעת ל-`responseMimeType` + `responseSchema` של Gemini. אם הבעיה עדיין מופיעה ב-v3.x+, פתחו דיווח על בעיה.

## הגדרות עמידות

### הגבלת קצב אוטומטית אינה מופעלת

- הגבלת קצב אוטומטית חלה רק על ספקים המשתמשים במפתחות API (לא על OAuth/מינוי)
- ודאו שהאפשרות להגבלת קצב אוטומטית מופעלת תחת **הגדרות → עמידות → פרופילי ספקים**
- בדקו אם הספק מחזיר קודי מצב `429` או כותרות `Retry-After`

### כוונון השהיה מעריכית

פרופילי ספקים תומכים בהגדרות הבאות:

- **השהיית בסיס** — זמן ההמתנה הראשוני לאחר הכשל הראשון (ברירת מחדל: 1s)
- **השהיה מרבית** — הגבול העליון של זמן ההמתנה (ברירת מחדל: 30s)
- **מכפיל** — בכמה להגדיל את ההשהיה בכל כשל רצוף (ברירת מחדל: 2x)

### מניעת עדר רועם

כאשר בקשות מקביליות רבות מגיעות לספק שמוגבל בקצב, OmniRoute משתמש ב-mutex ובהגבלת קצב אוטומטית כדי לסדר את הבקשות באופן טורי ולמנוע כשלים מתגלגלים. הדבר מתבצע אוטומטית עבור ספקים המשתמשים במפתחות API.

### בקשות צ'אט נכשלות עם 503 / chat_admission_busy

**תסמינים:**

- נקודת הקצה להשלמות צ'אט מחזירה תגובת `503` שניתן לנסות שוב, שקוד השגיאה שלה הוא
  `chat_admission_busy`.
- התגובה כוללת `Retry-After`. מאז #12135 הערך נגזר מהתפוסה שנצפתה — הגדול מבין חלון
  `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` שהבקשה כבר המתינה בו לבין משך הזמן שבו ההקצאות הכבדות
  הנוכחיות מוחזקות — כשהוא מעוגל כלפי מעלה לשניות שלמות ומוגבל ל-60. כאשר השער אינו עמוס,
  נשמרים ערכי המינימום ההיסטוריים: 2 שניות במסלול המבוסס על בתים, ושנייה אחת במסלול המבוסס
  על מבנה (הכולל גם `reason: "structure_limit"`).
- הדבר עשוי להתרחש כאשר צ'אט כבד אחר או תגובת הזרמה ממושכת עדיין נמצאים
  בתהליך.

גוף התגובה המבוססת על בתים הוא:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

התגובה המבוססת על מבנה משתמשת באותו סוג ובאותו קוד, עם ההודעה
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ועם `reason: "structure_limit"`.
בספי ברירת המחדל, בקשה נחשבת כבדה מבחינה מבנית כאשר היא כוללת לפחות `200` הודעות,
לפחות `64` כלים או לפחות `32,000` אסימונים משוערים, או כאשר אומדן המבנה המוגבל
ממצה את גבולותיו של `10,000` צמתים שבוקרו או עומק `12`.

**סיבה:** זוהי הפחתת עומס מכוונת בתוך OmniRoute, ולא כשל של ספק upstream.
כל תהליך משתמש במנגנון הגנה מקומי לתהליך כדי לשמור קיבולת מוגבלת לבקשות כבדות לפני שמירת
גוף בקשה גדול ופענוחו. הקצאה כבדה נשארת מוחזקת לכל אורך חייה של תגובת SSE.

**התפשטות #503:** לפני תיקון זה, מנגנון ההגנה הגביל את המקביליות לפי מספר קבוע של בקשות
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ברירת מחדל `1`) ללא תלות בזיכרון המארח, ולכן
התפצלות של סוכני תכנות (מספר סוכני משנה/כלי CLI, עם גופים שגודלם דרך קבע מעל 256 KB)
קרסה למקביליות אפקטיבית של כ-1 והחזירה שגיאות 503 תחת עומס רגיל לחלוטין. מנגנון ההגנה
מכוונן את עצמו כעת: הוא נשלט באמצעות תקציב בתים לקליטה שנגזר אוטומטית
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ומחושב לפי תקרת הזיכרון האמיתית של התהליך, והוא
גם בוחן אות חי של לחץ על המשאבים — כך שהוא מפחית עומס רק כאשר המארח נתון באמת ללחץ
זיכרון, ולא רק משום שהגיעה יותר מבקשה כבדה אחת בו-זמנית. מגבלת הספירה הישנה
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) עדיין מכובדת, אך רק אם הגדרתם אותה במפורש.

כאשר הקיבולת תפוסה, בקשה כבדה ממתינה תחילה עד
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ברירת מחדל `2000`; הערך `0` משבית את ההמתנה) לפינוי מקום,
לפני החזרת תגובת `503` שניתן לנסות שוב. ההמתנה המוגבלת קיימת כדי שלקוחות בסגנון סוכנים
(OpenCode, Claude Code, Cursor), המפצלים במקביל בקשות משנה כבדות, יסדרו את פרץ הבקשות
באופן טורי במקום לבזבז את כל תקציב הניסיונות החוזרים שלהם על דחיות מיידיות ולהיכשל באמצע המשימה.
התפוסה הנוכחית של הקצאות כבדות, תקציב הבתים שנקבע וחומרת הלחץ בזמן אמת
מוצגים ב-`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — בדקו אותם לפני שינוי משתנה סביבה כלשהו.
הגדרות → עמידות → תור בקשות → בקשות מקביליות אינו שולט בכך; הגדרה זו
מנהלת מנגנון נפרד של תור בקשות לספק.

**תיקון:**

1. תחילה, נסו שוב. על הלקוחות לכבד את `Retry-After` ולהשתמש בהשהיה הדרגתית במקום לחזור
   מיד על הבקשה.
2. בדקו את `/api/monitoring/health` → `chatAdmission` לפני כוונון כלשהו. `countCapEnabled:
false` ו-`maxInflightBytes` נדיב מצביעים על כך שהתקציב הנגזר אוטומטית כבר מבצע את
   תפקידו; ערך `pressureSeverity` של `high`/`critical` מצביע על כך שבמארח באמת חסר זיכרון —
   לא ניתן לתקן זאת באמצעות משתנה סביבת קבלה; נדרש יותר RAM או עומס עבודה קטן יותר.
3. רק אם `/api/monitoring/health` מראה שהתקציב הנגזר אוטומטית באמת קטן מדי עבור
   המארח שלכם (מצב נדיר — הוא כבר מתאים את עצמו מסביבה מוכלת ועד bare-metal), דרסו אותו ישירות באמצעות
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` במקום לחזור למגבלה הישנה המבוססת על מספר בקשות.

עיינו ב[הפניה למשתני הסביבה](../reference/ENVIRONMENT.md#4-security--authentication)
לקבלת הגדרות הקבלה המוסמכות.

## טקסונומיית כשלים אופציונלית של RAG / LLM ‏(16 בעיות)

חלק ממשתמשי OmniRoute מציבים את השער לפני מערכי RAG או סוכנים. בתצורות האלה נפוץ לראות דפוס מוזר: OmniRoute נראה תקין (הספקים פעילים, פרופילי הניתוב תקינים ואין התראות על מגבלת קצב), אך התשובה הסופית עדיין שגויה.

בפועל, תקריות אלה נובעות בדרך כלל מתהליך ה-RAG שבהמשך השרשרת, ולא מהשער עצמו.

אם אתם מעוניינים באוצר מילים משותף לתיאור הכשלים האלה, תוכלו להשתמש ב-WFGY ProblemMap, משאב טקסט חיצוני ברישיון MIT המגדיר שישה-עשר דפוסי כשל חוזרים של RAG / LLM. ברמה כללית הוא עוסק בנושאים הבאים:

- סטייה באחזור וגבולות הקשר שבורים
- אינדקסים ומאגרי וקטורים ריקים או מיושנים
- אי-התאמה בין הטמעות למשמעות סמנטית
- בעיות בהרכבת הפרומפט ובחלון ההקשר
- קריסה לוגית ותשובות בעלות ביטחון מופרז
- כשלים בשרשראות ארוכות ובתיאום בין סוכנים
- סטייה בזיכרון ובתפקידים במערכות מרובות סוכנים
- בעיות בסדר הפריסה והאתחול

הרעיון פשוט:

1. בעת חקירת תגובה שגויה, תעדו:
   - את משימת המשתמש ואת הבקשה
   - את צירוף המסלול או הספקים ב-OmniRoute
   - כל הקשר RAG שנעשה בו שימוש בהמשך השרשרת (מסמכים שאוחזרו, קריאות לכלים וכן הלאה)
2. מַפּו את התקרית למספר אחד או שניים ב-WFGY ProblemMap (`No.1` … `No.16`).
3. שמרו את המספר בלוח המחוונים, בספר הנהלים או במערכת מעקב התקריות שלכם לצד יומני OmniRoute.
4. השתמשו בדף WFGY המתאים כדי להחליט אם עליכם לשנות את מערך ה-RAG, את מנגנון האחזור או את אסטרטגיית הניתוב.

הטקסט המלא ומתכונים מעשיים זמינים כאן (רישיון MIT, טקסט בלבד):

[README של WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

אפשר להתעלם מסעיף זה אם אינכם מפעילים תהליכי RAG או סוכנים מאחורי OmniRoute.

## בעיות ידועות ב-v3.8.0

בעיות הייחודיות לגרסת v3.8.0 והפתרונות העוקפים הנוכחיים שלהן. אם תיקון ייכלל בעדכון מאוחר יותר, הרשומה תעודכן או תוסר.

### כשלי אימות ב-Devin CLI

**תסמינים:**

- "Devin CLI לא נמצא" או "האימות נכשל" בעת הפעלת כלים המבוססים על Devin
- בדיקת זמן הריצה של ה-CLI מדווחת `installed=false`

**גורמים:**

- `CLI_DEVIN_BIN` מצביע על נתיב שאינו קיים
- Devin CLI אינו מותקן במארח

**תיקון:**

1. התקינו את Devin CLI עבור הפלטפורמה שלכם
2. הגדירו `CLI_DEVIN_BIN=/usr/local/bin/devin` (או את הנתיב האמיתי) בקובץ `.env`
3. הפעילו מחדש את OmniRoute ובדקו שוב דרך **לוח המחוונים ← כלי CLI**

### תקופת הצינון של המודל תקועה (איפוס ידני)

**תסמינים:**

- מודל נשאר ברשימת תקופות הצינון גם לאחר שחלף מועד התפוגה
- בקשות עדיין מדלגות על המודל בניתוב משולב, אף שחותמת הזמן כבר חלפה

**איפוס ידני:**

- **לוח המחוונים:** **הגדרות ← תקופות צינון של מודלים** ← לחצו על **הפעלה מחדש** בכרטיס הרלוונטי
- **API:** `DELETE /api/resilience/model-cooldowns` עם כותרות אימות לניהול

### חיבור לספק Command Code נכשל עם 403

**תסמינים:**

- מתקבלת שגיאת 403 בעת בדיקת החיבור לספק Command Code
- בכרטיס הספק מופיע "לא מורשה" לאחר הוספה חדשה

**גורם:** תהליך OAuth לא הושלם (קריאת החזרה לא התקבלה או שהאסימון לא נשמר).

**תיקון:**

- הפעילו `omniroute providers` דרך ה-CLI כדי להפעיל מחדש את תהליך OAuth, או
- הפעילו מחדש את OAuth דרך **לוח המחוונים ← ספקים ← Command Code ← התחברות מחדש**

### ModelScope מחזיר תקופות צינון אגרסיביות בעקבות 429

**תסמינים:**

- תקופות צינון קצרות מאוד או מיידיות ב-ModelScope לאחר רצף קטן של בקשות
- ניתוב משולב מדלג על ModelScope מוקדם מהצפוי

**גורם:** ModelScope מפיק כותרות `Retry-After` ייחודיות לספק. v3.8.0 כולל טיפול ייעודי בכותרות האלה, ולכן גרסאות ישנות יותר מפרשות אותן באופן שגוי כרמזים כלליים למגבלת קצב.

**תיקון:**

- ודאו שאתם משתמשים ב-v3.8.0 או בגרסה מאוחרת יותר
- ודאו שהמתג `useUpstream429BreakerHints` מופעל תחת **הגדרות ← עמידות**

### OMNIROUTE_WS_BRIDGE_SECRET חסר בסביבת הייצור

**תסמינים:**

- שגיאת 401 בכל בקשה לגשר WebSocket של Codex/Responses בעת הפעלה במארח ייצור מרוחק
- לחיצת היד של גשר WebSocket נסגרת מיד לאחר ההתחברות

**גורם:** משתנה הסביבה `OMNIROUTE_WS_BRIDGE_SECRET` חסר בסביבת הייצור.

**תיקון:**

1. צרו סוד אקראי: `openssl rand -hex 32`
2. הגדירו `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` בסביבת שרת הייצור (ובכל לקוח שמתקשר עם הגשר)
3. הפעילו מחדש את OmniRoute

### Responses API: מצב רקע הונמך לביצוע סינכרוני

**תסמינים:**

- נרשמת אזהרה: `background mode degraded to synchronous`
- בקשה עם `background: true` מחזירה תגובה סינכרונית רגילה במקום מזהה של משימת רקע

**גורם:** ב-v3.8.0, השימוש ב-`background: true` ב-Responses API מונמך במכוון לביצוע סינכרוני תוך הפקת אזהרה. ביצוע אסינכרוני מלא ברקע מתוכנן לעתיד.

**תיקון:**

- התאימו את הלקוח כך שיבצע קריאה ללא `background`, או
- המתינו לגרסה מאוחרת יותר שתכלול מצב רקע אסינכרוני מלא (עקבו אחר יומן השינויים)

## הפעלה איטית / פסק זמן בהמתנה למוכנות

אם ה-CLI מציג `⚠ Server did not respond within 60s` אך השרת פועל בפועל, תקציב בדיקת המוכנות קצר מדי עבור הסביבה שלכם.

מצב זה מתרחש בדרך כלל ב-Windows (עקב אנטי-וירוס או מנגנוני מעקב אחר מערכת הקבצים) או בקונטיינרים עם עומסי עבודה כבדים בעת ההפעלה.

**פתרון — הגדילו את התקציב:**

```bash
# באמצעות משתנה סביבה (נשמר בין הפעלות):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 דקות
omniroute serve

# באמצעות דגל CLI (לשימוש חד-פעמי):
omniroute serve --ready-timeout 180000
```

ברירת המחדל היא 60 000 מילישניות (60 שניות). האזהרה מיועדת למידע בלבד; השרת ממשיך לעלות ברקע ויהיה נגיש לאחר השלמת האתחול.

לפרטים מלאים על `OMNIROUTE_READY_TIMEOUT_MS`, ראו [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
