## עיון מהיר

**חדשים ב-OmniRoute?** התחילו כאן — פתרונות אלה פותרים 90% מהבעיות:

| מה אני רואה                | מה המשמעות                                | מה לעשות                                                                                      |
| -------------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------- |
| "לא ניתן להתחבר"           | OmniRoute אינו פועל                       | הפעילו את `omniroute` או את `docker restart omniroute`                                        |
| "מפתח API לא תקין"         | המפתח שלכם שגוי או שפג תוקפו              | העתיקו מחדש את המפתח מאתר הספק                                                                |
| "חריגה ממגבלת הקצב"        | אתם שולחים יותר מדי בקשות                 | המתינו דקה אחת, או השתמשו ב-`model: "auto"` למעבר אוטומטי לחלופה                              |
| "חריגה מהמכסה"             | ניצלתם את המכסה החינמית/בתשלום שלכם       | חברו ספקים נוספים, או השתמשו בספקים חינמיים (Kiro, Pollinations)                              |
| "תגובות איטיות"            | הספק עמוס או מרוחק                        | השתמשו ב-`model: "auto/fast"` או חברו ספק מהיר יותר (Groq, Cerebras)                          |
| "נעשה שימוש בספק הלא נכון" | `auto` בחר ספק אחר                        | זה תקין! `auto` בוחר את האפשרות הטובה ביותר. כפו ספק מסוים באמצעות `model: "openai/gpt-4o"`   |
| "502 שער לא תקין"          | הספק אינו זמין                            | המתינו ונסו שוב, או השתמשו ב-`model: "auto"` כדי לעבור בין ספקים                              |
| "401 לא מורשה"             | פרטי ההזדהות שלכם שגויים                  | בדקו את מפתח ה-API או בצעו אימות מחדש באמצעות OAuth                                           |
| "omniroute אינו מזוהה"     | ב-Windows PATH חסרים מודולי node גלובליים | הוסיפו את הקידומת הגלובלית של npm אל Windows PATH. מצאו אותה באמצעות `npm config get prefix`. |
| "429 יותר מדי בקשות"       | הוחלה מגבלת קצב                           | המתינו דקה אחת, או חברו ספקים נוספים                                                          |

**עדיין תקועים?** עיינו ב[פתרון הבעיות המפורט](#detailed-troubleshooting) שבהמשך, או שאלו ב-[Discord](https://discord.gg/U47eFqAXCn).

## פתרון בעיות מפורט

---

### הגבלת קצב אצל ספקים חינמיים (429 / 400 / 401)

**תסמין**: בעת שימוש ב-`model: "auto"` עם ספקים חינמיים/ללא אימות (opencode, auggie וכו'), מתקבלים לסירוגין `HTTP 429`,‏ `400` או `401` במקום תשובות. הבקשות מצליחות כאשר מנסים שוב את אותה הנחיה כעבור כמה רגעים, אך תהליכים אוטומטיים (משימות cron, סוכנים, סקריפטים) נכשלים כבר בשגיאה הראשונה.

**גורם השורש**: שלושה מצבי כשל בלתי תלויים מצטברים:

1. **מגבלת קצב של הספק (`429`)**: מסלולים חינמיים עשויים לאכוף מכסה לכל חלון זמן. פרץ של קריאות מקבילות ממצה אותה, ולכן הבקשה הבאה נדחית עד לאיפוס החלון.
2. **מודל פגום במעבר ישיר (`400`/`401`)**: מאגרי `auto/*` עשויים לכלול מודלים למעבר ישיר מ-`opencode`, הרשומים בקטלוג אך אין להם פרטי הזדהות פעילים (למשל `oc/north-mini-code-free` ← `401`). הנתב האוטומטי מנסה אחד מהם, נכשל, והשגיאה מועברת הלאה לפני שהמעבר לחלופה נכנס לפעולה.
3. **הגברת מקביליות (`429` תחת עומס)**: כאשר כמה הפעלות של סוכנים/cron פונות אל `auto` בו-זמנית, קצב הבקשות המצטבר חורג ממה שספקים חינמיים מסוגלים לסבול, ולכן קריאות לגיטימיות מסומנות כפוגעניות.

**תיקון מאומת (דווח על ידי הקהילה, 2026-08-10)**: כווננו שלושה משתני סביבה כך שהחלפה מחזורית, מקביליות ומעבר לחלופה יספגו את חוסר היציבות של המסלול החינמי במקום להיכשל בגללו:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # מעבר למודל/ספק אחר בעת 400/401 (דילוג על מודלים פגומים במעבר ישיר)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # תקרת קבלה מפורשת לעומסים כבדים (אינה מוגדרת כברירת מחדל: אין מגבלה על מספר הבקשות, ראו הערה בהמשך)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # המתנה תחומה וארוכה יותר לקיבולת לעומסים כבדים במקום שגיאת 503 מיידית הניתנת לניסיון חוזר
```

הגדירו אותם בסביבת התהליך של OmniRoute (הדמון, למשל באמצעות קובץ plist של LaunchAgent או `systemctl edit`), ולאחר מכן הפעילו מחדש את OmniRoute. דגל ההחלפה המחזורית הוא המנוף היחיד בעל ההשפעה הגדולה ביותר: הוא הופך כשל מוחלט לניסיון חוזר ושקוף מול ספק תקין במאגר.

**הערה**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` מגביל את מספר הבקשות הכבדות — בעלות הקשר ארוך — שיכולות לפעול בו-זמנית; הגבול הוא שער קבלה, ולא מגביל קצב של ספק. **עדכון #503-fanout:** משתנה זה אינו מוגדר עוד כברירת מחדל (כעת הוא נכנס לתוקף רק כאשר מגדירים אותו במפורש, כמו לעיל) — במקום זאת, קבלת עומסים כבדים מוגבלת באמצעות תקציב בתים הנגזר אוטומטית (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), שמתאים את עצמו למגבלת הזיכרון האמיתית של המארח. לכן, בפריסה חדשה אמורות להופיע הרבה פחות דחיות `503 chat_admission_busy`, ללא צורך בהגדרת משתנה זה כלל; הגדרתו המפורשת כאן עדיין פועלת בדיוק כמתועד. דריסות מפורשות של תקציב הבתים מוגבלות לטווח 8 MiB–2 GiB. שגיאת `413 body_exceeds_budget` אינה זמנית: הגדילו את תקציב הבתים, הקטינו את `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`, או הגדילו את מגבלת הזיכרון של התהליך. השלת עומס מסוג `inflight_bytes_budget` נובעת מתחרות זמנית על משאבים וניתן להמשיך לנסות אחריה. הגבלת הקצב לכל ספק (`open-sse/services/rateLimitManager.ts`) מנוהלת בנפרד באמצעות `RATE_LIMIT_MAX_WAIT_MS`,‏ `RATE_LIMIT_MAX_QUEUE_DEPTH` ו-`RATE_LIMIT_AUTO_ENABLE` — ראו `.env.example`.

**כיצד לוודא שהתיקון עבד**: הריצו את הסוכן/cron שלכם פעמיים ברצף מהיר וודאו ששתי ההרצות מצליחות. לפני התיקון, ההרצה השנייה בדרך כלל מחזירה `429`/`401`. לאחר התיקון, ניסיונות שנכשלים (אם ישנם) מבוצעים מחדש באופן שקוף והקריאה מושלמת. תוכלו גם להריץ `curl /monitoring/health` ולעקוב אחר השדה `rateLimitedUntil` בחיבורי הספקים ואחר `circuitBreakers.providerBreakers[].state` עבור הספקים המושפעים — המצב הוא אחד מהבאים: `CLOSED`,‏ `DEGRADED`,‏ `OPEN` או `HALF_OPEN` (ראו `src/shared/utils/circuitBreaker.ts`), וספק שממשיך להיכשל יעבור בין המצבים `CLOSED → DEGRADED → OPEN` לפני שחלון האיפוס יאפשר בקשת בדיקה (`HALF_OPEN`).

**אם אתם עדיין רואים 429**: החשבון הפעיל של אותו ספק מיצה בפועל את ה-_quota_ שלו (ולא רק את מגבלת הקצב). הוסיפו חשבון נוסף עבור אותו ספק בלוח הבקרה של OmniRoute דרך Providers → Accounts, או שלבו ספק חינמי אחר (לדוגמה, `routeway`,‏ `auggie`). רוטציה מסייעת רק במקרים זמניים של מגבלת קצב/400/401; מיצוי מוחלט של המכסה דורש פרטי גישה נוספים או ספק אחר.

**אם אתם רואים 403 במודלי ראייה (`auto/vision`,‏ `bazaarlink/*`)**: לחשבון המחובר אין תוכנית בתשלום הכוללת יכולות ראייה, או שלמפתח ה-API אין הרשאות מספיקות. ודאו בלוח הבקרה של הספק שטווח ההרשאות של המפתח כולל ראייה/מולטימודל, או חברו חשבון במסלול בתשלום והשאירו אותו כיעד עבור משימות ראייה.

## אזהרות npm install‏ (ERESOLVE / עמית / הוצא משימוש)

בעת הרצת `npm install -g omniroute`, ייתכן שתראו שורה ארוכה של אזהרות כגון `npm warn ERESOLVE`, הודעות על תלויות עמית והודעות `deprecated`. **אזהרות אלה צפויות ואינן מזיקות.** ההתקנה הצליחה אם מופיע בפלט `added <N> packages`.

כדי להסתיר את אזהרות פתרון תלויות העמית, השתמשו בצורת ההתקנה הנתמכת של OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

האפשרות `--legacy-peer-deps` מסתירה רק את `ERESOLVE` ואת ההודעות על תלויות עמית. הודעות על הוצאה משימוש נשארות גלויות משום שהן מגיעות מחבילות צד שלישי עקיפות; הן אינן מעידות שההתקנה נכשלה.

האזהרות נובעות מטווחים מיושנים של תלויות עמית בחבילות צד שלישי שאינן בשליטת OmniRoute:

1. **`marked-terminal` דורשת `marked >=1 <16`, אך נמצאה `marked@18`** — בפועל היא פועלת כראוי; טווח תלויות העמית של הפרויקט המקורי פשוט מיושן.
2. **`deprecated prebuild-install@7.1.3`** — כלי עזר עקיף לאחזור קבצים בינאריים מקוריים. הוא אינו
   משמש להתקנת קישור התעבורה המקובע `wreq-js`, ואינו מעיד שהגדרת התעבורה של ספק קובצי ה-Cookie
   מהאינטרנט נכשלה.

**אין צורך בפעולה** — לא ניתן להשתיק לחלוטין את האזהרות בלי ליצור פיצול של החבילות המקוריות.

## Gemini Web ו-Playwright Chromium

אם בקשת Gemini Web מחזירה `503` עם הודעה שלפיה Playwright Chromium
אינו מותקן, חבילת npm קיימת אך הקובץ הבינארי של הדפדפן חסר.
Playwright מפריד במכוון בין הורדות הדפדפן לבין התקנת חבילת npm,
ולכן תגובה זו צפויה עד להתקנת הדפדפן.

בהתקנת npm גלובלית, התקינו את Chromium מתוך הספרייה של חבילת OmniRoute
כדי שמטמון הדפדפן ישתייך לאותה התקנה של Playwright:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

לאחר ההתקנה, הפעילו מחדש את OmniRoute ולאחר מכן נסו שוב את בקשת Gemini Web. אם אתם
מריצים את OmniRoute מתוך תמונת Docker, השתמשו בתמונת `-web` (או ביעד הבנייה `runner-web`),
הכוללת את Chromium ואת התלויות שלו; תמונת הבסיס אינה כוללת
אותם.

## זיהויים חיוביים כוזבים של אנטי-וירוס

<a name="antivirus-false-positives"></a>

### Avast/AVG מעבירים את `README.md` להסגר עם `MD:HttpRequest-inf[Susp]`

**זהו זיהוי חיובי כוזב. דבר אינו נגוע, ולא נדרשת כל פעולה.**

Avast ו-AVG מפעילים מנגנון היוריסטי המסמן קובצי טקסט פשוט/Markdown המכילים קישורים רבים
שנראים כמו בקשות HTTP. הקובץ `README.md` של OmniRoute נכלל בחבילת npm (הוא
מופיע תחת `files` ב-`package.json`), ולכן בהתקנה גלובלית הוא מגיע אל
`node_modules/omniroute/README.md` — והוא מכיל כ-15 דוגמאות מסוג
`http://localhost:20128/...` (נקודות הקצה HTTP/SSE של MCP, כתובת ה-URL מסוג
`.well-known` של A2A וקטעי `curl`). צפיפות קישורים זו מספיקה כדי להפעיל את המנגנון
ההיוריסטי.

אם הדבר החל רק לאחרונה: סוג הקובץ לא השתנה. טבלת נקודות הקצה ב-README הורחבה
(MCP HTTP + SSE + A2A נוספו), ונוספו דוגמאות `curl`, מה שגרם לו לעבור
את הסף.

הקובץ הוא תיעוד בלתי פעיל שאין בו שום תוכן בר-הרצה. ניתן לשחזר אותו בבטחה
מההסגר.

**מה לעשות:**

1. **הפסיקו את ההתראות** — החריגו את תיקיית ההתקנה באנטי-וירוס שלכם
   (Avast: הגדרות ← חריגים), על ידי הוספת הנתיב הגלובלי של `node_modules` ו/או
   תיקיית הנתונים של OmniRoute (`~/.omniroute/`).
2. **דווחו על הזיהוי החיובי הכוזב** — <https://www.avast.com/false-positive-file-form.php>,
   וצרפו את `README.md` שהועבר להסגר. זהו התיקון שמסייע לכולם, משום שמדובר
   בתגובת-יתר של המנגנון ההיוריסטי של הספק לקובץ טקסט.

**מדוע איננו "מתקנים" זאת בצד שלנו:** כל הדוגמאות משתמשות ב-`http://localhost`,
ולא ניתן להשתמש ב-`https` עבור localhost ללא החיכוך הכרוך באישורים בחתימה עצמית.
שיבוש התיעוד כדי לחמוק מהמנגנון ההיוריסטי של ספק אחד יפגע בכל הקוראים כדי לרצות
באג בסורק.

### Kaspersky מסמן את יישום שולחן העבודה בתור `PDM:Trojan.Win32.Generic`

**זהו זיהוי חיובי כוזב שמקורו במנגנון היוריסטי התנהגותי. דבר אינו נגוע.** הקידומת
`PDM:` של Kaspersky מציינת שההכרעה מגיעה מ-Proactive Defense Module שלו
(System Watcher), אשר בוחן מה המתקין _עושה_ במקום להשוות אותו לתוכנות זדוניות מוכרות.
כאשר הוא מופעל, Kaspersky "מחזיר לאחור" את ההתקנה כולה — ומוחק קבצים שכבר
נכתבו — כך שהיישום נותר פגום או חסר.

הקבצים שהוא מסמן הם רכיבים תקניים של תלויות מוצהרות בקוד פתוח, המצורפות ליישום
שולחן העבודה, לדוגמה:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ו-
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ספריית האוטומציה
  לדפדפנים המשמשת להתחברות לספקים מתוך היישום ולצ'אט מבוסס-דפדפן.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — הקישור המקורי המקובע של `wreq-js`, המשמש ל-HTTP בעל טביעת אצבע של דפדפן
  אצל ספקים מבוססי עוגיות אינטרנט (`<arch>` הוא `x64` או `arm64`).

**מדוע הוא מופעל:** מתקין Windows **עדיין אינו חתום בחתימת קוד**, ולכן למתקין NSIS
שאינו חתום אין כלל מוניטין, והמנגנונים ההיוריסטיים ההתנהגותיים פועלים ברמת האגרסיביות
המרבית. בשילוב עם DLL מקורי מצורף ומאות קובצי `.js` הנכתבים תחת
`%LOCALAPPDATA%\Programs\OmniRoute` (כולל תיקיות חבילות עם סיומות hash מבניית
ה-standalone של Next.js), די בכך כדי להפעיל את המנגנון ההיוריסטי. חתימת קוד מתוכננת;
עד שתתווסף, הדבר עשוי לחזור על עצמו בגרסאות חדשות.

**מה לעשות:**

1. **אמתו תחילה את ההורדה שלכם** (כדי לשלול קובץ ששונה בזדון). בכל גרסה מתפרסם
   `latest.yml`, שהשדה `sha512` שלו (base64) מכסה את המתקין
   `OmniRoute.Setup.<version>.exe`. ב-PowerShell, מתוך התיקייה המכילה את המתקין:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   הפלט חייב להתאים ל-`latest.yml` ← `sha512`. אם אינו מתאים, מחקו את הקובץ
   והורידו אותו מחדש אך ורק מ[דף הגרסאות ב-GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **שחזרו והחריגו** — שחזרו מההסגר את הפריטים שנמחקו במהלך ההחזרה לאחור והוסיפו
   החרגה עבור `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky ← הגדרות ← איומים והחרגות),
   ולאחר מכן התקינו מחדש.
3. **דווחו על הזיהוי החיובי הכוזב** — <https://opentip.kaspersky.com/>. דיווחי FP
   שנשלחים על ידי משתמשים אכן מאיצים את ההוספה לרשימת ההיתרים.

## תאימות ל-Node.js

<a name="nodejs-compatibility"></a>

### דף ההתחברות קורס או מציג שגיאת "Module self-registration"

**סיבה:** אתם מריצים גרסת Node.js שאינה עומדת ברף סביבת הריצה המאובטחת המאושרת של OmniRoute. המקרה הנפוץ ביותר הוא הרצת רמת תיקון ישנה יותר של Node 22 או 24, הנמוכה מרף האבטחה המתוקן ש-OmniRoute דורש.

**תסמינים:**

- דף ההתחברות מציג מסך ריק או שגיאת שרת
- המסוף מציג `Error: Module did not self-register` או שגיאות דומות של קישור מקורי
- דף ההתחברות מציג **כרזת אזהרה כתומה** עם גרסת ה-Node שלכם אם סביבת הריצה אינה תואמת למדיניות המאובטחת הנתמכת

**פתרון:**

1. התקינו מהדורת LTS נתמכת של Node.js (מומלץ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. אמתו את הגרסה שלכם: `node --version` אמור להציג `v24.0.0` או גרסה חדשה יותר בענף LTS של 24.x
3. התקינו מחדש את OmniRoute: `npm install -g omniroute`
4. הפעילו מחדש: `omniroute`

> **גרסאות מאובטחות נתמכות:** `>=22.22.2 <23` או `>=24.0.0 <27`. קיימת תמיכה מלאה ב-Node.js 24.x LTS (Krypton) וב-Node.js 26.

### npm v11+: ‏`better-sqlite3` אינו מותקן (לא ניתן למצוא את המודול)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**סיבה:** npm v11 (המסופק עם Node.js 24+) חוסם כברירת מחדל סקריפטים להתקנה עבור
תלויות אופציונליות. מכיוון ש-`better-sqlite3` מופיע ב-`optionalDependencies`
ודורש הידור מקורי (`node-gyp rebuild`), npm מדלג עליו ללא הודעה.

**תסמינים:**

- השרת קורס בעת ההפעלה עם `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` מציג "No such file or directory"
- `npm ls better-sqlite3` מציג `(empty)`

**פתרון:**

1. אשרו את סקריפטי ההתקנה והתקינו מחדש:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. לחלופין, התקינו ידנית את החבילה שנבנתה מראש:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ודאו שהיא פועלת: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: ‏`dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**סיבה:** לאחר `npm install -g omniroute` גלובלי, ייתכן שהקובץ הבינארי המקורי של `better-sqlite3` בתוך החבילה הודר עבור ארכיטקטורה או ABI של Node.js השונים מאלה שפועלים באופן מקומי. מצב זה נפוץ ב-macOS (הן ב-Apple Silicon והן ב-Intel) כאשר הקובץ הבינארי שנבנה מראש אינו תואם לסביבה שלכם.

**תסמינים:**

- השרת נכשל מיד בעת ההפעלה עם שגיאת `dlopen`
- השגיאה מכילה `slice is not valid mach-o file`
- דוגמה מלאה:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**פתרון — בנו מחדש עבור הסביבה המקומית שלכם (אין צורך לשנמך את Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **הערה:** פעולה זו מהדרת מחדש את הקישור המקורי מול גרסת Node.js וארכיטקטורת המעבד המקומיות שלכם, ובכך פותרת את אי-ההתאמה הבינארית. טווח סביבת הריצה הנתמך רשמית הוא **`>=22.22.2 <23` או `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` בקובץ `src/shared/utils/nodeRuntimeSupport.ts`, בהתאמה לשדה `engines` בקובץ `package.json`). קיימת תמיכה מלאה ב-Node.js 24.x LTS (Krypton) וב-Node.js 26 עם `better-sqlite3` v12.x.

## בעיות Proxy

<a name="proxy-issues"></a>

### אימות ספק מציג "fetch failed"

**סיבה:** נקודת הקצה לאימות מפתח ה-API (`POST /api/providers/validate`) עקפה בעבר את תצורת ה-proxy, דבר שגרם לכשלים בסביבות המחייבות ניתוב דרך proxy.

**תיקון (v3.5.5+):** הבעיה תוקנה. אימות הספק מנותב כעת דרך `runWithProxyContext`, תוך כיבוד אוטומטי של הגדרות ה-proxy ברמת הספק וההגדרות הגלובליות.

### בדיקת תקינות האסימון נכשלת עם "fetch failed"

**סיבה:** רענון אסימון OAuth ברקע לא פתר את תצורת ה-proxy עבור כל חיבור בנפרד.

**תיקון (v3.5.5+):** מתזמן בדיקת תקינות האסימונים פותר כעת את תצורת ה-proxy עבור כל חיבור לפני ניסיון הרענון. יש לעדכן ל-v3.5.5+.

### Proxy מסוג SOCKS5 מחזיר "invalid onRequestStart method"

**סיבה:** ב-Node.js 22, המנתב של undici@8 אינו תואם למימוש `fetch()` המובנה של Node.

**תיקון (v3.5.5+):** OmniRoute משתמש כעת בפונקציית `fetch()` של undici עצמו כאשר מנתב proxy פעיל, כדי להבטיח התנהגות עקבית. יש לעדכן ל-v3.5.5+.

### Proxy מסוג MITM תחת WSL: אפליקציות שולחן עבודה במארח Windows אינן מיורטות

**סיבה:** ה-proxy מסוג MITM ואישור ה-CA שלו מותקנים בסביבה שבה OmniRoute פועל. תחת WSL, סביבה זו היא מערכת Linux האורחת, בעוד שאפליקציות ה-AI לשולחן העבודה (Kiro, Trae, Copilot, Zed, …) פועלות במארח Windows. אפליקציות המארח אינן נותנות אמון במאגר האישורים של המערכת האורחת ואינן מנותבות דרך ה-proxy המערכתי שלה, ולכן יירוט אפליקציות שולחן העבודה אינו מופעל שם.

**המלצה:** יש להריץ את OmniRoute באופן מקומי באותה מערכת הפעלה שבה פועלות אפליקציות שולחן העבודה שברצונכם ליירט (Windows עבור אפליקציות Windows; ובאופן דומה עבור macOS/Linux). השארת OmniRoute בתוך WSL תוך ניסיון ליירט אפליקציות במארח מחייבת מתן אמון ידני באישור ה-CA שנוצר במארח Windows והפניית הגדרות הרשת/ה-proxy של כל אפליקציה במארח לנקודת הקצה של ה-proxy ב-WSL — תצורה לא נתמכת ושברירית.

חיבורים אלה ממשיכים להשתמש בנקודת הקצה המשותפת לרענון אימות חברתי.

לפרטים מלאים ולהוראות מפורטות להוספת שני חשבונות Kiro זה לצד זה,
ראו [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

### שגיאות סנכרון בענן

1. ודאו ש-`BASE_URL` מצביע על המופע הפעיל שלכם (לדוגמה, `http://localhost:20128`)

**תסמין:** `Unexpected token 'd'...` בנקודת הקצה בענן עבור קריאות שאינן בהזרמה.

**סיבה:** השירות במעלה הזרם מחזיר מטען SSE, בעוד שהלקוח מצפה ל-JSON.

**פתרון עוקף:** השתמשו ב-`stream=true` עבור קריאות ישירות לענן. סביבת הריצה המקומית כוללת מנגנון גיבוי להמרת SSE→JSON.

### הענן מציג חיבור תקין אך מדווח "מפתח API לא תקין"

1. צרו מפתח חדש מלוח הבקרה המקומי (`/api/keys`)
2. הפעילו סנכרון לענן: הפעלת הענן → סנכרון כעת
3. מפתחות ישנים או מפתחות שלא סונכרנו עדיין עשויים להחזיר `401` בענן

## בעיות Docker

### IPv6 / איפוס חיבור ב-Docker

<a name="docker-ipv6"></a>

**תסמינים:** הפקודה `curl http://localhost:20128/v1/models` מחזירה `curl: (56) Recv failure: Connection reset by peer`. לוח הבקרה ונקודות קצה שאינן דורשות אימות פועלים, אך נקודות קצה מאומתות נכשלות — הדבר נראה כמו בעיית אימות, אך אינו כזה.

**סיבה:** הפקודה `docker run -p 20128:20128` מפרסמת הן ב-`0.0.0.0` ‏(IPv4) והן ב-`::` ‏(IPv6), אך התהליך בתוך הקונטיינר מאזין ל-IPv4 בלבד. במארחים שבהם `localhost` מזוהה תחילה כ-`::1`, החיבור מגיע ליציאת IPv6 שפורסמה, אך אין מאחוריה מאזין → החיבור מתאפס.

**תיקון:**

1. **אבחון מהיר:** הריצו `curl -4 http://localhost:20128/v1/models`. אם הפקודה פועלת עם `-4` אך נכשלת בלעדיו, קיימת אי-התאמה באיגוד IPv6.
2. **תיקון קבוע:** אגדו במפורש ל-IPv4 באמצעות `-p 127.0.0.1:20128:20128` בפקודת `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   פעולה זו כופה איגוד ל-IPv4 וגם מונעת את חשיפת הפרוקסי בכל ממשקי המארח.

## איתור באגים

### הפעלת קובצי יומן

הגדירו `APP_LOG_TO_FILE=true` בקובץ `.env` שלכם. יומני היישום נכתבים תחת `logs/`.
ארטיפקטים של בקשות נשמרים תחת `${DATA_DIR}/call_logs/` כאשר צינור עיבוד יומן הקריאות
מופעל בהגדרות.
כאשר לכידה בצינור העיבוד מופעלת, הגדירו `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` כדי להשמיט
מטענים של מקטעי הזרמה, או כווננו את `CALL_LOG_PIPELINE_MAX_SIZE_KB` כדי לשנות את מגבלת הארטיפקטים ב-KB.

### בדיקת תקינות הספק

```bash
# לוח בקרת תקינות
http://localhost:20128/dashboard/health

# בדיקת תקינות API
curl http://localhost:20128/api/monitoring/health
```

### אחסון סביבת הריצה

- מצב ראשי: `${DATA_DIR}/storage.sqlite` (ספקים, שילובים, כינויים, מפתחות, הגדרות)
- שימוש: טבלאות SQLite ב-`storage.sqlite` ‏(`usage_history`, `call_logs`, `proxy_logs`) + `${DATA_DIR}/call_logs/` אופציונלי
- יומני היישום: `<repo>/logs/...` (כאשר `APP_LOG_TO_FILE=true`)
- ארטיפקטים של יומן הקריאות: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` כאשר צינור עיבוד יומן הקריאות מופעל

הפעולה **ניקוי היסטוריה** בדף יומני הבקשות מנקה את `call_logs`, את
`request_detail_logs` מהמערכת הישנה ואת ספריית הארטיפקטים המקומית `${DATA_DIR}/call_logs/`.

## בעיות במפסק הזרם

### הספק תקוע במצב OPEN

כאשר מפסק הזרם של ספק נמצא במצב OPEN, הבקשות נחסמות עד שתסתיים תקופת ההמתנה.

**פתרון:**

1. עברו אל **לוח הבקרה → הגדרות → עמידות**
2. בדקו את כרטיס מפסק הזרם של הספק המושפע
3. לחצו על **איפוס הכול** כדי לאפס את כל מפסקי הזרם, או המתינו עד שתסתיים תקופת ההמתנה
4. ודאו שהספק אכן זמין לפני האיפוס

### הספק ממשיך להפעיל את מפסק הזרם

אם ספק נכנס שוב ושוב למצב OPEN:

1. בדקו את דפוס הכשלים תחת **לוח הבקרה → תקינות → תקינות הספקים**
2. עברו אל **הגדרות → עמידות → פרופילי ספקים** והגדילו את סף הכשלים
3. בדקו אם הספק שינה את מגבלות ה-API או דורש אימות מחדש
4. בדקו את נתוני הטלמטריה של זמני ההשהיה — זמני השהיה גבוהים עלולים לגרום לכשלים עקב חריגה מזמן ההמתנה

- **קריאות לכלים נעלמות** — תרגומים מסוימים בין תבניות עשויים להסיר שדות שאינם נתמכים; ודאו זאת במצב מגרש המשחקים
- **הנחיית המערכת חסרה** — Claude ו-Gemini מטפלים בהנחיות מערכת באופן שונה; בדקו את פלט התרגום

- **GLM/ERNIE דוחה את התפקיד `system`** — נפתר ב-v1.x; מנרמל התפקידים ממזג אוטומטית הודעות מערכת לתוך הודעות משתמש עבור מודלים שאינם תואמים. אם אתם עדיין נתקלים בכך ב-v3.x+, אנא פתחו דיווח על בעיה.
- **התפקיד `developer` אינו מזוהה** — נפתר ב-v1.x; הוא מומר אוטומטית ל-`system` עבור ספקים שאינם OpenAI. אם אתם עדיין נתקלים בכך ב-v3.x+, אנא פתחו דיווח על בעיה.
- **`json_schema` אינו פועל עם Gemini** — נפתר ב-v1.x; `response_format` מומר כעת ל-`responseMimeType` + `responseSchema` של Gemini. אם אתם עדיין נתקלים בכך ב-v3.x+, אנא פתחו דיווח על בעיה.

## הגדרות עמידות

### הגבלת הקצב האוטומטית אינה מופעלת

- הגבלת קצב אוטומטית חלה רק על ספקים המשתמשים במפתחות API (לא OAuth/מינוי)
- ודאו שבאפשרות **הגדרות → עמידות → פרופילי ספקים** מופעלת הגבלת קצב אוטומטית
- בדקו אם הספק מחזיר קודי מצב `429` או כותרות `Retry-After`

### כוונון השהיה מעריכית

פרופילי ספקים תומכים בהגדרות הבאות:

- **השהיה בסיסית** — זמן ההמתנה הראשוני לאחר הכשל הראשון (ברירת מחדל: 1s)
- **השהיה מרבית** — הגבול העליון של זמן ההמתנה (ברירת מחדל: 30s)
- **מכפיל** — בכמה להגדיל את ההשהיה בכל כשל רצוף (ברירת מחדל: 2x)

### מניעת עדר רועם

כאשר בקשות מקביליות רבות מגיעות לספק שקצבו מוגבל, OmniRoute משתמש ב-mutex ובהגבלת קצב אוטומטית כדי להעביר את הבקשות באופן סדרתי ולמנוע כשלים מתגלגלים. פעולה זו מתבצעת אוטומטית עבור ספקים המשתמשים במפתחות API.

### בקשות צ'אט נכשלות עם 503 / chat_admission_busy

**תסמינים:**

- נקודת הקצה של השלמות הצ'אט מחזירה תגובת `503` שניתן לנסות שוב, שקוד השגיאה שלה הוא
  `chat_admission_busy`.
- התגובה כוללת `Retry-After`. מאז #12135, הערך נגזר מהתפוסה שנצפתה —
  הערך הגדול מבין חלון `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` שהבקשה כבר המתינה בו
  לבין משך הזמן שבו ההקצאות הכבדות הנוכחיות מוחזקות — מעוגל כלפי מעלה לשניות שלמות
  ומוגבל ל-60. כאשר השער אינו פעיל, נשמרים ערכי המינימום ההיסטוריים: 2 שניות בנתיב
  המבוסס על בתים, ושנייה אחת בנתיב המבוסס על מבנה (הכולל גם
  `reason: "structure_limit"`).
- מצב זה עשוי להתרחש כאשר צ'אט כבד אחר או תגובת הזרמה ארוכת-טווח עדיין
  נמצאים בתהליך.

גוף התגובה המבוססת על בתים הוא:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

התגובה המבוססת על מבנה משתמשת באותו סוג ובאותו קוד, עם ההודעה
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ועם `reason: "structure_limit"`.
בספי ברירת המחדל, בקשה נחשבת כבדה מבחינה מבנית כאשר היא כוללת לפחות `200` הודעות,
לפחות `64` כלים, או לפחות `32,000` אסימונים משוערים, או כאשר אומדן המבנה התחום
ממצה את גבולותיו: `10,000` צמתים שבהם ביקר או עומק `12`.

**סיבה:** זוהי הפחתת עומס מכוונת בתוך OmniRoute, ולא כשל של ספק במעלה הזרם.
כל תהליך משתמש במנגנון הגנה מקומי לתהליך כדי לשריין קיבולת מוגבלת לבקשות כבדות לפני שמירת
גוף בקשה גדול וניתוחו. הקצאה כבדה נשארת מוחזקת לכל אורך חייה של תגובת SSE.

**#503-fanout:** לפני תיקון זה, מנגנון ההגנה הגביל את המקביליות לפי מספר קבוע של בקשות
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ברירת מחדל `1`) ללא קשר לזיכרון המארח, ולכן
הסתעפות של סוכני תכנות (מספר תת-סוכנים/ממשקי CLI, עם גופים שגודלם לרוב > 256 KB) צמצמה את
המקביליות האפקטיבית לכ-1 וגרמה לשגיאות 503 תחת עומס רגיל לחלוטין. כעת מנגנון ההגנה מכוונן
את עצמו: הוא נשלט באמצעות תקציב בתים לקליטה הנגזר אוטומטית
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), שגודלו נקבע לפי תקרת הזיכרון האמיתית של
התהליך, והוא גם בוחן אות חי של לחץ על המשאבים — כך שהוא מפחית עומס רק כאשר המארח
נתון באמת ללחץ זיכרון, ולא רק מפני שהגיעה יותר מבקשה כבדה אחת בו-זמנית. מגבלת הכמות הישנה
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) עדיין מכובדת, אך רק אם תגדירו אותה במפורש.

כאשר הקיבולת תפוסה, בקשה כבדה ממתינה תחילה עד
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ברירת מחדל `2000`; הערך `0` מבטל את ההמתנה) לשחרור מקום
לפני החזרת `503` שניתן לנסות שוב. ההמתנה התחומה קיימת כדי שלקוחות בסגנון סוכן
(OpenCode, Claude Code, Cursor), המפצלים במקביל בקשות-משנה כבדות, יעבירו את פרץ הבקשות
באופן סדרתי במקום לבזבז את כל מכסת הניסיונות החוזרים שלהם על דחיות מיידיות ולהיכשל באמצע המשימה.
תפוסת ההקצאות הכבדות הנוכחית, תקציב הבתים שנקבע וחומרת הלחץ בזמן אמת
מוצגים ב-`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — בדקו אותם לפני שינוי משתנה סביבה כלשהו.
הגדרות → עמידות → תור בקשות → בקשות מקביליות אינה שולטת בכך; הגדרה זו
מנהלת מנגנון נפרד של תור בקשות לספק.

**תיקון:**

1. תחילה נסו שוב. על הלקוחות לכבד את `Retry-After` ולהשתמש בהשהיה במקום לחזור מיד
   על הבקשה.
2. בדקו את `/api/monitoring/health` → `chatAdmission` לפני כל כוונון. `countCapEnabled:
false` ו-`maxInflightBytes` נדיב משמעם שהתקציב הנגזר אוטומטית כבר מבצע את
   תפקידו; `pressureSeverity` בערך `high`/`critical` משמעו שבמארח באמת חסר זיכרון —
   לא ניתן לפתור זאת באמצעות משתנה סביבת קבלה; נדרש יותר RAM או עומס עבודה קטן יותר.
3. רק אם `/api/monitoring/health` מראה שהתקציב הנגזר אוטומטית אכן קטן מדי עבור
   המארח שלכם (נדיר — הוא כבר מותאם החל מקונטיינר ועד bare-metal), דרסו אותו ישירות באמצעות
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` במקום לחזור למגבלת כמות הבקשות הישנה.

עיינו ב[הפניית משתני הסביבה](../reference/ENVIRONMENT.md#4-security--authentication)
לקבלת הגדרות הקבלה המוסמכות.

## טקסונומיית כשלים אופציונלית עבור RAG / LLM ‏(16 בעיות)

חלק ממשתמשי OmniRoute מציבים את השער לפני מערכי RAG או סוכנים. בתצורות כאלה נפוץ לראות דפוס מוזר: OmniRoute נראה תקין (הספקים פעילים, פרופילי הניתוב תקינים, אין התראות על הגבלת קצב), אך התשובה הסופית עדיין שגויה.

בפועל, תקריות אלה נובעות בדרך כלל מצינור עיבוד ה-RAG שבמורד הזרם, ולא מהשער עצמו.

אם אתם מעוניינים באוצר מילים משותף לתיאור כשלים אלה, תוכלו להשתמש ב-WFGY ProblemMap, משאב טקסט חיצוני ברישיון MIT שמגדיר שישה-עשר דפוסי כשל חוזרים של RAG / LLM. ברמה כללית הוא מכסה:

- סטייה באחזור וגבולות הקשר שבורים
- אינדקסים ומאגרי וקטורים ריקים או מיושנים
- אי-התאמה בין הטמעות לבין משמעות סמנטית
- בעיות בהרכבת פרומפטים ובחלון ההקשר
- קריסה לוגית ותשובות בעלות ביטחון מופרז
- כשלים בשרשראות ארוכות ובתיאום בין סוכנים
- סטייה בזיכרון ובתפקידים במערכים מרובי-סוכנים
- בעיות בסדר הפריסה והאתחול

הרעיון פשוט:

1. כאשר אתם חוקרים תשובה שגויה, תעדו:
   - את משימת המשתמש והבקשה
   - את צירוף הנתיב או הספק ב-OmniRoute
   - כל הקשר RAG שנעשה בו שימוש במורד הזרם (מסמכים שאוחזרו, קריאות לכלים וכדומה)
2. שייכו את התקרית למספר אחד או שניים ב-WFGY ProblemMap ‏(`No.1` … `No.16`).
3. שמרו את המספר בלוח הבקרה, בספר הנהלים או במערכת מעקב התקריות שלכם, לצד יומני OmniRoute.
4. השתמשו בעמוד WFGY המתאים כדי להחליט אם עליכם לשנות את מערך ה-RAG, את מנגנון האחזור או את אסטרטגיית הניתוב שלכם.

הטקסט המלא והמתכונים המעשיים זמינים כאן (רישיון MIT, טקסט בלבד):

[README של WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

אפשר להתעלם מסעיף זה אם אינכם מפעילים צינורות עיבוד של RAG או סוכנים מאחורי OmniRoute.

## בעיות ידועות ב-v3.8.0

בעיות הייחודיות לגרסת v3.8.0 והדרכים הנוכחיות לעקיפתן. אם תיקון ייכלל בעדכון מאוחר יותר, הרשומה תעודכן או תוסר.

### כשלי אימות ב-Devin CLI

**תסמינים:**

- "Devin CLI לא נמצא" או "האימות נכשל" בעת הפעלת כלים המבוססים על Devin
- בדיקת זמן הריצה של ה-CLI מדווחת על `installed=false`

**גורמים:**

- `CLI_DEVIN_BIN` מצביע על נתיב שאינו קיים
- Devin CLI אינו מותקן במארח

**תיקון:**

1. התקינו את Devin CLI עבור הפלטפורמה שלכם
2. הגדירו `CLI_DEVIN_BIN=/usr/local/bin/devin` (או את הנתיב האמיתי) בקובץ `.env`
3. הפעילו מחדש את OmniRoute ובצעו בדיקה חוזרת דרך **לוח הבקרה ← כלי CLI**

### תקופת הצינון של המודל תקועה (איפוס ידני)

**תסמינים:**

- מודל נשאר ברשימת תקופות הצינון גם לאחר שזמן התפוגה חלף
- בקשות עדיין מדלגות על המודל בניתוב משולב, אף שחותמת הזמן נמצאת בעבר

**איפוס ידני:**

- **לוח הבקרה:** **הגדרות ← תקופות צינון של מודלים** ← לחצו על **הפעלה מחדש** בכרטיס הרלוונטי
- **API:** `DELETE /api/resilience/model-cooldowns` עם כותרות אימות ניהול

### החיבור לספק Command Code נכשל עם 403

**תסמינים:**

- מתקבל 403 בעת בדיקת החיבור לספק Command Code
- כרטיס הספק מציג "לא מורשה" לאחר הוספה חדשה

**גורם:** תהליך OAuth לא הושלם (קריאת החזרה לא התקבלה או שהאסימון לא נשמר).

**תיקון:**

- הפעילו `omniroute providers` דרך ה-CLI כדי להפעיל מחדש את תהליך OAuth, או
- הפעילו מחדש את OAuth דרך **לוח הבקרה ← ספקים ← Command Code ← התחברות מחדש**

### ModelScope מחזיר תקופות צינון אגרסיביות מסוג 429

**תסמינים:**

- תקופות צינון קצרות מאוד או מיידיות ב-ModelScope לאחר פרץ קטן של בקשות
- ניתוב משולב מדלג על ModelScope מוקדם מהצפוי

**גורם:** ModelScope מפיק כותרות `Retry-After` ייחודיות לספק. v3.8.0 כוללת טיפול ייעודי בכותרות אלה, ולכן גרסאות ישנות יותר מפרשות אותן באופן שגוי כרמזים כלליים להגבלת קצב.

**תיקון:**

- ודאו שאתם משתמשים ב-v3.8.0 או בגרסה מאוחרת יותר
- ודאו שהמתג `useUpstream429BreakerHints` מופעל תחת **הגדרות ← עמידות**

### OMNIROUTE_WS_BRIDGE_SECRET חסר בסביבת הייצור

**תסמינים:**

- מתקבל 401 בכל בקשת גשר WebSocket של Codex/Responses בעת הפעלה במארח ייצור מרוחק
- לחיצת היד של גשר WebSocket נסגרת מיד לאחר ההתחברות

**גורם:** משתנה הסביבה `OMNIROUTE_WS_BRIDGE_SECRET` חסר בסביבת הייצור.

**תיקון:**

1. צרו סוד אקראי: `openssl rand -hex 32`
2. הגדירו `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` בסביבת שרת הייצור (ובכל לקוח שמתקשר עם הגשר)
3. הפעילו מחדש את OmniRoute

### Responses API: מצב הרקע מופחת לביצוע סינכרוני

**תסמינים:**

- נרשמת אזהרה: `background mode degraded to synchronous`
- בקשה עם `background: true` מחזירה תגובה סינכרונית רגילה במקום מזהה של משימת רקע

**גורם:** v3.8.0 מפחיתה במכוון את `background: true` ב-Responses API לביצוע סינכרוני, תוך הפקת אזהרה. ביצוע אסינכרוני מלא ברקע מתוכנן לעתיד.

**תיקון:**

- התאימו את הלקוח כך שיבצע קריאה ללא `background`, או
- המתינו לגרסה מאוחרת יותר שתכלול מצב רקע אסינכרוני מלא (עקבו אחר יומן השינויים)

## הפעלה איטית / פסק זמן של בדיקת המוכנות

אם ה-CLI מציג `⚠ Server did not respond within 60s` אך השרת פועל בפועל, פרק הזמן שהוקצה לבדיקת המוכנות קצר מדי עבור הסביבה שלכם.

מצב זה מתרחש לעיתים קרובות ב-Windows (בגלל אנטי-וירוס או מנטרי מערכת קבצים) או בקונטיינרים עם עומסי עבודה כבדים בזמן ההפעלה.

**פתרון — הגדילו את פרק הזמן המוקצה:**

```bash
# באמצעות משתנה סביבה (נשמר בין הפעלות):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 דקות
omniroute serve

# באמצעות דגל CLI (באופן חד-פעמי):
omniroute serve --ready-timeout 180000
```

ברירת המחדל היא 60 000 מילישניות (60 שניות). האזהרה נועדה למידע בלבד; השרת ממשיך לעלות ברקע ויהיה נגיש לאחר השלמת האתחול.

לפרטים מלאים על `OMNIROUTE_READY_TIMEOUT_MS`, ראו [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
