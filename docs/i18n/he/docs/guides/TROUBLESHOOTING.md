## מדריך מהיר

**חדשים ב-OmniRoute?** התחילו כאן — הפתרונות האלה פותרים 90% מהבעיות:

| אני רואה את זה             | מה זה אומר                                | מה לעשות                                                                                     |
| -------------------------- | ----------------------------------------- | -------------------------------------------------------------------------------------------- |
| "לא ניתן להתחבר"           | OmniRoute אינו פועל                       | הפעילו את `omniroute` או את `docker restart omniroute`                                       |
| "מפתח API לא תקין"         | המפתח שלכם שגוי או שפג תוקפו              | העתיקו מחדש את המפתח מאתר הספק                                                               |
| "חריגה ממגבלת הקצב"        | אתם שולחים יותר מדי בקשות                 | המתינו דקה אחת, או השתמשו ב-`model: "auto"` למעבר אוטומטי לחלופה                             |
| "חריגה מהמכסה"             | ניצלתם את המכסה החינמית/בתשלום שלכם       | חברו ספקים נוספים, או השתמשו בספקים חינמיים (Kiro, Pollinations)                             |
| "תגובות איטיות"            | הספק עמוס או מרוחק                        | השתמשו ב-`model: "auto/fast"` או חברו ספק מהיר יותר (Groq, Cerebras)                         |
| "נעשה שימוש בספק הלא נכון" | `auto` בחר ספק אחר                        | זה תקין! `auto` בוחר את האפשרות הטובה ביותר. כפו ספק מסוים באמצעות `model: "openai/gpt-4o"`  |
| "502 שער לא תקין"          | הספק אינו זמין                            | המתינו ונסו שוב, או השתמשו ב-`model: "auto"` כדי לעבור בין ספקים                             |
| "401 אין הרשאה"            | פרטי ההזדהות שלכם שגויים                  | בדקו את מפתח ה-API או בצעו אימות מחדש באמצעות OAuth                                          |
| "omniroute אינו מזוהה"     | ב-Windows PATH חסרים מודולי node גלובליים | הוסיפו את התחילית הגלובלית של npm ל-Windows PATH. מצאו אותה באמצעות `npm config get prefix`. |
| "429 יותר מדי בקשות"       | קצב הבקשות הוגבל                          | המתינו דקה אחת, או חברו ספקים נוספים                                                         |

## פתרון בעיות מפורט

---

### הגבלת קצב אצל ספקים חינמיים (429 / 400 / 401)

**תסמין**: בעת שימוש ב-`model: "auto"` עם ספקים חינמיים/ללא אימות (opencode, auggie וכו'), מתקבלות לסירוגין שגיאות `HTTP 429`,‏ `400` או `401` במקום תשובות. הבקשות מצליחות כאשר מנסים שוב את אותה ההנחיה כעבור כמה רגעים, אך תהליכים אוטומטיים (משימות cron, סוכנים, סקריפטים) נכשלים כבר בשגיאה הראשונה.

**גורם השורש**: שלושה מצבי כשל בלתי תלויים מצטברים:

1. **הגבלת קצב מצד הספק (`429`)**: מסלולים חינמיים עשויים לאכוף מכסה לכל חלון זמן. פרץ של קריאות מקבילות מנצל אותה במלואה, ולכן הבקשה הבאה נדחית עד לאיפוס החלון.
2. **מודל לא תקין במצב מעבר ישיר (`400`/`401`)**: מאגרי `auto/*` עשויים לכלול מודלים במעבר ישיר מ-`opencode`, הרשומים בקטלוג אך ללא פרטי הזדהות פעילים (לדוגמה, `oc/north-mini-code-free` ← `401`). הנתב האוטומטי מנסה אחד מהם, נכשל, והשגיאה מועברת הלאה לפני שהמעבר לחלופה נכנס לפעולה.
3. **הגברת עומס עקב מקביליות (`429` תחת עומס)**: כאשר כמה הפעלות של סוכנים/cron פונות אל `auto` בו-זמנית, קצב הבקשות המצטבר חורג ממה שספקים חינמיים מסוגלים לסבול, ולכן קריאות תקינות מסומנות כפוגעניות.

**תיקון מאומת (דווח על ידי הקהילה, 2026-08-10)**: כווננו שלושה משתני סביבה כך שהחלפת ספקים, המקביליות והמעבר לחלופה יספגו את חוסר היציבות של המסלול החינמי במקום להיכשל בגללו:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # מעבר למודל/ספק אחר במקרה של 400/401 (מדלג על מודלים לא תקינים במעבר ישיר)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # תקרת כניסה מפורשת לבקשות כבדות (לא מוגדרת כברירת מחדל: אין מגבלה על מספר הבקשות, ראו הערה בהמשך)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # הגדלת ההמתנה המוגבלת מעבר לברירת המחדל של RATE_LIMIT_MAX_WAIT_MS עבור מקורות איטיים
```

הגדירו אותם בסביבת התהליך של OmniRoute (תהליך הרקע, למשל באמצעות קובץ plist של LaunchAgent או `systemctl edit`), ולאחר מכן הפעילו מחדש את OmniRoute. דגל ההחלפה הוא האפשרות היחידה בעלת ההשפעה הגדולה ביותר: הוא הופך כשל מוחלט לניסיון חוזר ושקוף מול ספק תקין במאגר.

**הערה**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` מגביל את מספר הבקשות הכבדות — בעלות הקשר ארוך — שרצות בו-זמנית; המגבלה היא שער כניסה, ולא מגביל קצב של ספק. **עדכון #503-fanout:** משתנה זה אינו מוגדר עוד כברירת מחדל (כעת הוא נכנס לתוקף רק כאשר מגדירים אותו במפורש, כפי שנעשה לעיל) — במקום זאת, כניסת בקשות כבדות נשלטת באמצעות תקציב בתים הנגזר אוטומטית (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), שמתאים את עצמו למגבלת הזיכרון האמיתית של המארח. לכן, בפריסה חדשה אמורות להופיע הרבה פחות דחיות מסוג `503 chat_admission_busy`, גם בלי להגדיר משתנה זה כלל; הגדרתו המפורשת כאן עדיין פועלת בדיוק כמתועד. דריסות מפורשות של תקציב הבתים מוגבלות לטווח של 8 MiB–2 GiB. שגיאת `413 body_exceeds_budget` אינה זמנית: הגדילו את תקציב הבתים, הקטינו את `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`, או הגדילו את מגבלת הזיכרון של התהליך. השמטה מסוג `inflight_bytes_budget` נובעת מתחרות זמנית על משאבים, ועדיין ניתן לנסות אותה מחדש. הגבלת הקצב לכל ספק (`open-sse/services/rateLimitManager.ts`) מנוהלת בנפרד באמצעות `RATE_LIMIT_MAX_WAIT_MS`,‏ `RATE_LIMIT_MAX_QUEUE_DEPTH` ו-`RATE_LIMIT_AUTO_ENABLE` — ראו `.env.example`.

**כיצד לוודא שהתיקון פועל**: הפעילו את הסוכן/cron שלכם פעמיים ברצף מהיר וודאו ששתי ההרצות מצליחות. לפני התיקון, ההרצה השנייה בדרך כלל מחזירה `429`/`401`. לאחר התיקון, ניסיונות שנכשלים (אם ישנם) מתבצעים מחדש באופן שקוף והקריאה מושלמת. ניתן גם להריץ `curl /monitoring/health` ולעקוב אחר השדה `rateLimitedUntil` בחיבורי הספקים ואחר `circuitBreakers.providerBreakers[].state` עבור הספקים המושפעים — המצב הוא אחד מבין `CLOSED`,‏ `DEGRADED`,‏ `OPEN` או `HALF_OPEN` (ראו `src/shared/utils/circuitBreaker.ts`), וספק שממשיך להיכשל יעבור מ־`CLOSED → DEGRADED → OPEN` לפני שחלון האיפוס יאפשר בקשת בדיקה (`HALF_OPEN`).

**אם עדיין מופיעה שגיאת 429**: החשבון הפעיל של אותו ספק אכן מיצה את ה_מכסה_ שלו (ולא רק את מגבלת הקצב). הוסיפו חשבון שני עבור אותו ספק בלוח הבקרה של OmniRoute ← Providers ← Accounts, או שלבו ספק חינמי אחר (למשל `routeway`,‏ `auggie`). הרוטציה מסייעת רק במקרים זמניים של הגבלת קצב/400/401; מיצוי מוחלט של המכסה מחייב פרטי גישה נוספים או ספק אחר.

**אם מופיעה שגיאת 403 במודלי ראייה (`auto/vision`,‏ `bazaarlink/*`)**: לחשבון המחובר אין תוכנית בתשלום הכוללת יכולות ראייה, או שלמפתח ה־API אין הרשאות מספיקות. ודאו בלוח הבקרה של הספק שטווח ההרשאות של המפתח כולל ראייה/ריבוי אופנים, או חברו חשבון ברמה בתשלום והשאירו אותו כיעד הראייה.

## אזהרות `npm install` ‏(ERESOLVE / peer / deprecated)

בעת הרצת `npm install -g omniroute`, ייתכן שתראו אוסף גדול של אזהרות כגון `npm warn ERESOLVE`, הודעות על תלויות עמית (peer dependencies) והודעות `deprecated`. **אזהרות אלה צפויות ואינן מזיקות.** ההתקנה הצליחה אם מופיע בפלט `added <N> packages`.

כדי להסתיר את האזהרות הנוגעות לפתרון תלויות עמית, השתמשו בצורת ההתקנה הנתמכת של OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

האפשרות `--legacy-peer-deps` מסתירה רק את `ERESOLVE` ואת ההודעות על תלויות עמית. הודעות על הוצאה משימוש נשארות גלויות מכיוון שהן מגיעות מחבילות צד שלישי טרנזיטיביות; הן אינן מעידות שההתקנה נכשלה.

האזהרות נובעות מטווחים מיושנים של תלויות עמית בחבילות צד שלישי שאינן בשליטת OmniRoute:

1. **`marked-terminal` דורשת `marked >=1 <16`, אך נמצאה `marked@18`** — בפועל היא פועלת היטב; טווח תלות העמית בפרויקט המקור פשוט מיושן.
2. **`deprecated prebuild-install@7.1.3`** — כלי עזר טרנזיטיבי להורדת קבצים בינאריים מקוריים. הוא אינו
   משמש להתקנת קישור התעבורה המקובע `wreq-js` ואינו מעיד שהגדרת התעבורה של ספק קובצי ה-Cookie
   מהאינטרנט נכשלה.

**לא נדרשת כל פעולה** — לא ניתן להשתיק לחלוטין את האזהרות ללא יצירת פיצול של חבילות המקור.

## אזהרת חסימת סקריפטים של `npm install` (התקנה גלובלית)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

בעת הרצת `npm install -g omniroute`, גרסאות חדשות יותר של npm ‏(v11+ ו-v12+) חוסמות כברירת מחדל סקריפטים של מחזור חיי החבילה ומציגות אזהרה על סקריפטי התקנה:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### האם ניתן להתעלם מאזהרה זו?

**באופן חלקי, אך הפעלה ללא סקריפטים אינה מומלצת.** OmniRoute כוללת מנגנוני גיבוי תקינים: אם לא ניתן לטעון את קישורי `better-sqlite3` המקוריים מהחבילה העצמאית, היישום עובר למנהלי התקן חלופיים כגון `node:sqlite` או `sql.js` (ראו [פתרון סביבת הריצה של SQLite](../ops/SQLITE_RUNTIME.md)). השרת עדיין יופעל, אך שימוש במנגנוני גיבוי מבוססי WASM כגון `sql.js` משבית את מצב WAL ‏(Write-Ahead Logging) של SQLite ומגדיל את תקורת הזיכרון וסנכרון הדיסק.

### אילו סקריפטים נדרשים בפועל?

לא כל הסקריפטים החסומים חיוניים להפעלת OmniRoute:

- **חיוניים (`omniroute`, `better-sqlite3`):** OmniRoute פועלת מחבילת יישום עצמאית של Next.js ‏(`dist/`). במהלך ההתקנה, npm מורידה או מהדרת את מנהל ההתקן המקורי של SQLite המותאם למארח בתוך `node_modules/better-sqlite3/` ברמה העליונה. לאחר מכן, סקריפט `postinstall` של OmniRoute ‏(`scripts/build/postinstall.mjs`) מאמת ומעתיק את הקבצים הבינאריים המותאמים למארח אל `dist/node_modules/`, כדי שהשרת העצמאי יוכל לגשת אליהם. אם סקריפט ה-postinstall של `omniroute` חסום, שלב ההעתקה הזה אינו מתבצע.
- **אופציונליים/טרנזיטיביים (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** אלה כלי עזר לבנייה, כלי ניטור או כלי שירות עבור צרור המפתחות של המערכת. מתן הרשאה עבורם מונע אזהרות בנייה, אך הם אינם נדרשים לפונקציונליות הניתוב העיקרית.
- **לא נכלל (`onnxruntime-node`):** תלות אופציונלית עבור שיכוני AI מקומיים, אשר **אינה** נדרשת להפעלת OmniRoute. סקריפט ה-postinstall שלה מוריד מ-NuGet כ-300MB של משאבי CUDA; אל תכללו אותה ברשימת ההרשאות אלא אם בכוונתכם להשתמש במפורש בהאצת ONNX מקומית בחומרה נתמכת.

### פתרון מומלץ

כדי להתיר את סקריפטי ההתקנה הנדרשים במהלך התקנה גלובלית ולהשתיק את האזהרות, העבירו את `--allow-scripts` עבור OmniRoute והתלויות המקוריות שלה:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

לחלופין, כדי להגדיר זאת באופן קבוע עבור כל ההתקנות הגלובליות בחשבון המשתמש שלכם:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### אימות ההתקנה

לאחר ההתקנה, הפעילו את כלי האבחון המובנה כדי לוודא שהקישורים המקוריים וסביבת הריצה תקינים:

```bash
omniroute doctor
```

## Gemini Web ו-Playwright Chromium

אם בקשת Gemini Web מחזירה `503` עם הודעה שלפיה Playwright Chromium
אינו מותקן, חבילת npm קיימת אך הקובץ הבינארי של הדפדפן חסר.
Playwright מפריד בכוונה את הורדות הדפדפנים מהתקנת חבילת
npm, ולכן תגובה זו צפויה עד להתקנת הדפדפן.

עבור התקנת npm גלובלית, התקינו את Chromium מתוך התיקייה של חבילת
OmniRoute, כך שמטמון הדפדפן יהיה שייך לאותה התקנת Playwright:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

הפעילו מחדש את OmniRoute לאחר ההתקנה, ולאחר מכן נסו שוב את בקשת Gemini Web. אם אתם
מריצים את OmniRoute מתמונת Docker, השתמשו בתמונת `-web` (או ביעד הבנייה `runner-web`),
הכוללת את Chromium ואת יחסי התלות שלו; תמונת הבסיס אינה
כוללת אותם.

## זיהויים חיוביים שגויים של אנטי-וירוס

<a name="antivirus-false-positives"></a>

### Avast/AVG מעבירים את `README.md` להסגר עם `MD:HttpRequest-inf[Susp]`

**זהו זיהוי חיובי שגוי. שום דבר אינו נגוע, ולא נדרשת כל פעולה.**

Avast ו-AVG מפעילים מנגנון היוריסטי שמסמן קובצי טקסט רגיל/Markdown המכילים קישורים רבים
שנראים כמו בקשות HTTP. הקובץ `README.md` של OmniRoute כלול בחבילת npm (הוא
מופיע ב-`package.json` ← `files`), ולכן בהתקנה גלובלית הוא מגיע אל
`node_modules/omniroute/README.md` — והוא מכיל כ-15 דוגמאות של `http://localhost:20128/...`
(נקודות הקצה HTTP/SSE של MCP, כתובת ה-URL מסוג `.well-known` של A2A וקטעי `curl`).
צפיפות הקישורים הזו מספיקה כדי להפעיל את המנגנון ההיוריסטי.

אם זה החל רק לאחרונה: אופי הקובץ לא השתנה. טבלת נקודות הקצה בקובץ README הורחבה
(MCP HTTP + SSE + A2A נוספו), וכן נוספו דוגמאות `curl`, מה שגרם לו לעבור את הסף.

הקובץ הוא תיעוד בלתי פעיל, ללא כל תוכן בר-הרצה. ניתן לשחזר אותו בבטחה
מההסגר.

**מה לעשות:**

1. **הפסיקו את ההתראות** — החריגו את ספריית ההתקנה באנטי-וירוס שלכם
   (Avast: הגדרות ← חריגים), והוסיפו את נתיב `node_modules` הגלובלי שלכם ו/או את
   ספריית הנתונים של OmniRoute (`~/.omniroute/`).
2. **דווחו על הזיהוי החיובי השגוי** — <https://www.avast.com/false-positive-file-form.php>,
   וצרפו את `README.md` שהועבר להסגר. זהו התיקון שמסייע לכולם, מכיוון שמדובר
   בתגובת יתר של המנגנון ההיוריסטי של הספק לקובץ טקסט.

**מדוע איננו "מתקנים" זאת בצד שלנו:** כל הדוגמאות הן `http://localhost`, ולא ניתן
להשתמש ב-`https` עבור localhost ללא הסרבול הכרוך באישור בחתימה עצמית. עיוות התיעוד כדי
לעקוף את המנגנון ההיוריסטי של ספק אחד יפגע בכל הקוראים רק כדי לרצות באג בסורק.

### Kaspersky מסמן את יישום שולחן העבודה בתור `PDM:Trojan.Win32.Generic`

**זהו זיהוי חיובי שגוי שמקורו במנגנון היוריסטי התנהגותי. שום דבר אינו נגוע.** התחילית
`PDM:` של Kaspersky פירושה שהקביעה מגיעה מ-Proactive Defense Module (System Watcher),
אשר שופט מה תוכנית ההתקנה _עושה_, במקום להשוות אותה לתוכנות זדוניות מוכרות. כאשר
המנגנון מופעל, Kaspersky "מחזיר לאחור" את ההתקנה כולה — ומוחק קבצים שכבר נכתבו —
כך שהיישום נותר פגום או חסר.

הקבצים שהוא מסמן הם רכיבים רגילים של תלויות מוצהרות בקוד פתוח המצורפות ליישום
שולחן העבודה, לדוגמה:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ו-
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ספריית אוטומציית הדפדפן
  המשמשת להתחברות לספקים מתוך היישום ולצ'אט מבוסס דפדפן.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — הקישור הטבעי המקובע של `wreq-js`, המשמש ל-HTTP עם טביעת אצבע של דפדפן אצל ספקים
  המבוססים על קובצי Cookie מהאינטרנט (`<arch>` הוא `x64` או `arm64`).

**מדוע הוא מופעל:** תוכנית ההתקנה של Windows **עדיין אינה חתומה דיגיטלית**, ולכן
לתוכנית התקנה לא חתומה מסוג NSIS אין כלל מוניטין, והמנגנונים ההיוריסטיים ההתנהגותיים
פועלים ברמת האגרסיביות המרבית. בשילוב עם DLL טבעי מצורף ומאות קובצי `.js` שנכתבים תחת
`%LOCALAPPDATA%\Programs\OmniRoute` (כולל ספריות חבילות עם סיומות גיבוב מבניית
ה-standalone של Next.js), די בכך כדי להפעיל את המנגנון ההיוריסטי. חתימת קוד מתוכננת;
עד שתיושם, הדבר עלול לחזור על עצמו במהדורות חדשות.

**מה לעשות:**

1. **אמתו תחילה את ההורדה שלכם** (כדי לשלול קובץ שעבר שינוי זדוני). כל מהדורה מפרסמת
   את `latest.yml`, שהשדה `sha512` שלו (base64) מכסה את תוכנית ההתקנה
   `OmniRoute.Setup.<version>.exe`. ב-PowerShell, מתוך התיקייה שמכילה את תוכנית ההתקנה:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   הפלט חייב להתאים אל `latest.yml` ← `sha512`. אם הוא אינו תואם, מחקו את הקובץ
   והורידו אותו מחדש רק מ[דף המהדורות ב-GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **שחזרו + החריגו** — שחזרו מההסגר את הפריטים שהוסרו במהלך ההחזרה לאחור והוסיפו החרגה
   עבור `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky ← הגדרות ← איומים והחרגות),
   ולאחר מכן התקינו מחדש.
3. **דווחו על הזיהוי החיובי השגוי** — <https://opentip.kaspersky.com/>. דוחות על זיהויים
   חיוביים שגויים שנשלחים על ידי משתמשים אכן מאיצים את ההוספה לרשימת ההיתרים.

## תאימות ל-Node.js

<a name="nodejs-compatibility"></a>

### דף הכניסה קורס או מציג שגיאת "Module self-registration"

**הסיבה:** אתם מריצים גרסת Node.js שאינה עומדת ברף זמן הריצה המאובטח המאושר של OmniRoute. המקרה הנפוץ ביותר הוא הפעלת גרסת תיקון ישנה יותר של Node 22 או 24, הנמוכה מרף האבטחה המתוקן הנדרש על ידי OmniRoute.

**תסמינים:**

- דף הכניסה מציג מסך ריק או שגיאת שרת
- המסוף מציג `Error: Module did not self-register` או שגיאות דומות של קישור מקורי
- דף הכניסה מציג **כרזת אזהרה כתומה** עם גרסת ה-Node שלכם אם סביבת זמן הריצה אינה עומדת במדיניות המאובטחת הנתמכת

**תיקון:**

1. התקינו מהדורת LTS נתמכת של Node.js (מומלץ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. אמתו את הגרסה שלכם: `node --version` אמור להציג `v24.0.0` או גרסה חדשה יותר בסדרת LTS של 24.x
3. התקינו מחדש את OmniRoute: `npm install -g omniroute`
4. הפעילו מחדש: `omniroute`

> **גרסאות מאובטחות נתמכות:** `>=22.22.2 <23` או `>=24.0.0 <27`. קיימת תמיכה מלאה ב-Node.js 24.x LTS (Krypton) וב-Node.js 26.

### npm v11+: ‏`better-sqlite3` אינו מותקן (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**הסיבה:** npm v11 (המסופק עם Node.js 24 ומעלה) חוסם כברירת מחדל סקריפטים להתקנה עבור
תלויות אופציונליות. מכיוון ש-`better-sqlite3` מופיע ב-`optionalDependencies`
ודורש הידור מקורי (`node-gyp rebuild`), npm מדלג עליו ללא הודעה.

**תסמינים:**

- השרת קורס בעת ההפעלה עם `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` מציג "No such file or directory"
- `npm ls better-sqlite3` מציג `(empty)`

**תיקון:**

1. אשרו את סקריפטי ההתקנה והתקינו מחדש:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. לחלופין, התקינו ידנית את הגרסה שהודרה מראש:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ודאו שההתקנה פועלת: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: ‏`dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**הסיבה:** לאחר `npm install -g omniroute` גלובלי, ייתכן שהקובץ הבינארי המקורי של `better-sqlite3` שבתוך החבילה הודר עבור ארכיטקטורה או ABI של Node.js השונים מאלה שפועלים באופן מקומי. מצב זה נפוץ ב-macOS (הן ב-Apple Silicon והן ב-Intel) כאשר הקובץ הבינארי שהודר מראש אינו תואם לסביבה שלכם.

**תסמינים:**

- השרת נכשל מיד בעת ההפעלה עם שגיאת `dlopen`
- השגיאה מכילה `slice is not valid mach-o file`
- דוגמה מלאה:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**תיקון — הדרו מחדש עבור הסביבה המקומית שלכם (אין צורך בשדרוג לאחור של Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **הערה:** פעולה זו מהדרת מחדש את הקישור המקורי בהתאם לגרסת Node.js ולארכיטקטורת המעבד המקומיות שלכם, וכך פותרת את אי-ההתאמה הבינארית. טווח זמן הריצה הנתמך רשמית הוא **`>=22.22.2 <23` או `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` בתוך `src/shared/utils/nodeRuntimeSupport.ts`, בהתאמה לשדה `engines` של `package.json`). קיימת תמיכה מלאה ב-Node.js 24.x LTS (Krypton) וב-Node.js 26 עם `better-sqlite3` v12.x.

## בעיות Proxy

<a name="proxy-issues"></a>

### אימות הספק מציג "fetch failed"

**סיבה:** נקודת הקצה לאימות מפתח ה-API (`POST /api/providers/validate`) עקפה בעבר את תצורת ה-proxy, דבר שגרם לכשלים בסביבות הדורשות ניתוב דרך proxy.

**תיקון (v3.5.5+):** הבעיה תוקנה. אימות הספק מנותב כעת דרך `runWithProxyContext`, תוך כיבוד אוטומטי של הגדרות proxy ברמת הספק וההגדרות הגלובליות.

### בדיקת תקינות האסימון נכשלת עם "fetch failed"

**סיבה:** רענון אסימוני OAuth ברקע לא פתר את תצורת ה-proxy עבור כל חיבור בנפרד.

**תיקון (v3.5.5+):** מתזמן בדיקת תקינות האסימונים פותר כעת את תצורת ה-proxy עבור כל חיבור לפני ניסיון הרענון. יש לעדכן ל-v3.5.5+.

### Proxy מסוג SOCKS5 מחזיר "invalid onRequestStart method"

**סיבה:** ב-Node.js 22, ה-dispatcher של undici@8 אינו תואם למימוש `fetch()` המובנה של Node.

**תיקון (v3.5.5+):** OmniRoute משתמש כעת בפונקציית `fetch()` של undici עצמו כאשר dispatcher של proxy פעיל, כדי להבטיח התנהגות עקבית. יש לעדכן ל-v3.5.5+.

### Proxy מסוג MITM תחת WSL: יישומי שולחן עבודה במארח Windows אינם מיורטים

**סיבה:** ה-proxy מסוג MITM ואישור ה-CA שלו מותקנים בסביבה שבה OmniRoute פועל. תחת WSL, סביבה זו היא האורח Linux, בעוד שיישומי שולחן העבודה מבוססי ה-AI (Kiro, Trae, Copilot, Zed, …) פועלים במארח Windows. יישומי המארח אינם נותנים אמון במאגר האישורים של האורח ואינם מנותבים דרך ה-proxy של מערכת האורח, ולכן יירוט יישומי שולחן העבודה אינו מופעל שם.

**המלצה:** הפעילו את OmniRoute באופן מקומי באותה מערכת הפעלה שבה פועלים יישומי שולחן העבודה שברצונכם ליירט (Windows עבור יישומי Windows; ובהתאם גם macOS/Linux). השארת OmniRoute בתוך WSL תוך ניסיון ליירט יישומים במארח מחייבת מתן אמון ידני באישור ה-CA שנוצר במארח Windows והפניית הגדרות הרשת/proxy של כל יישום במארח אל נקודת הקצה של ה-proxy ב-WSL — תצורה שאינה נתמכת ושאינה יציבה.

רענון האסימון של חשבון אחד מבטל את תוקף אסימון הרענון של החשבון האחר.

**תיקון (v3.8.0+):** ייבאו מחדש את החיבורים המושפעים.
החל מ-v3.8.0, כל חיבור Kiro חדש שנוצר באמצעות **ייבוא אסימון**,

ייעודי משלו. כתוצאה מכך, החיבור מבודד לחלוטין, ורענון של חשבון אחד
אינו משפיע על אף חשבון אחר.

חיבורים שיובאו _לפני_ v3.8.0 אינם כוללים רישום לקוח נפרד לכל חיבור.
חיבורים אלה ממשיכים להשתמש בנקודת הקצה המשותפת לרענון של אימות חברתי.
כדי להשיג בידוד, מחקו את החיבור הישן דרך לוח הבקרה → ספקים והוסיפו אותו מחדש
באמצעות אחד משלושת תהליכי הייבוא.

לפרטים מלאים ולהוראות מפורטות להוספת שני חשבונות Kiro זה לצד זה,
ראו [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## בעיות Docker

### IPv6 / איפוס חיבור ב־Docker

<a name="docker-ipv6"></a>

**תסמינים:** `curl http://localhost:20128/v1/models` מחזיר `curl: (56) Recv failure: Connection reset by peer`. לוח הבקרה ונקודות קצה שאינן דורשות אימות פועלים, אך נקודות קצה מאומתות נכשלות — הדבר נראה כמו בעיית אימות, אך אינו כזה.

**סיבה:** הפקודה `docker run -p 20128:20128` מפרסמת הן ב־`0.0.0.0`‏ (IPv4) והן ב־`::`‏ (IPv6), אך התהליך בתוך הקונטיינר מאזין ל־IPv4 בלבד. במארחים שבהם `localhost` נפתר תחילה ל־`::1`, החיבור מגיע ליציאת IPv6 שפורסמה, אך אין מאחוריה מאזין ← החיבור מאופס.

**תיקון:**

1. **אבחון מהיר:** הריצו `curl -4 http://localhost:20128/v1/models`. אם הפקודה פועלת עם `-4` אך נכשלת בלעדיו, קיימת אי־התאמה באיגוד IPv6.
2. **תיקון קבוע:** אגדו במפורש ל־IPv4 באמצעות `-p 127.0.0.1:20128:20128` בפקודת `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   פעולה זו כופה איגוד ל־IPv4 וגם מונעת את חשיפת הפרוקסי בכל ממשקי המארח.

- מצב ראשי: `${DATA_DIR}/storage.sqlite` (ספקים, שילובים, כינויים, מפתחות, הגדרות)
- שימוש: טבלאות SQLite ב־`storage.sqlite`‏ (`usage_history`, `call_logs`, `proxy_logs`) + `${DATA_DIR}/call_logs/` אופציונלי
- יומני יישום: `<repo>/logs/...` (כאשר `APP_LOG_TO_FILE=true`)
- ארטיפקטים של יומן קריאות: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` כאשר צינור עיבוד יומן הקריאות מופעל

הפעולה **ניקוי היסטוריה** בדף יומני הבקשות מנקה את `call_logs`, את
`request_detail_logs` מהגרסה הישנה ואת ספריית הארטיפקטים המקומית `${DATA_DIR}/call_logs/`.

## בעיות במפסק הזרם

### הספק תקוע במצב OPEN

כאשר מפסק הזרם של ספק נמצא במצב OPEN, הבקשות נחסמות עד לסיום תקופת ההמתנה.

**תיקון:**

1. עברו אל **לוח הבקרה → הגדרות → עמידות**
2. בדקו את כרטיס מפסק הזרם של הספק המושפע
3. לחצו על **איפוס הכול** כדי לאפס את כל מפסקי הזרם, או המתינו לסיום תקופת ההמתנה
4. ודאו שהספק אכן זמין לפני האיפוס

### הספק ממשיך להפעיל את מפסק הזרם

אם ספק נכנס שוב ושוב למצב OPEN:

1. בדקו ב-**לוח הבקרה → תקינות → תקינות הספקים** את דפוס הכשלים
2. עברו אל **הגדרות → עמידות → פרופילי ספקים** והגדילו את סף הכשלים
3. בדקו אם הספק שינה את מגבלות ה-API או דורש אימות מחדש
4. בדקו את נתוני הטלמטריה של זמן ההשהיה — זמן השהיה גבוה עלול לגרום לכשלים עקב חריגה ממגבלת הזמן

## ניפוי שגיאות במתרגם

השתמשו ב-**לוח הבקרה → מתרגם** כדי לנפות בעיות בתרגום תבניות:

| מצב                | מתי להשתמש                                                                           |
| ------------------ | ------------------------------------------------------------------------------------ |
| **סביבת ניסוי**    | השוו בין תבניות הקלט והפלט זו לצד זו — הדביקו בקשה שנכשלה כדי לראות כיצד היא מתורגמת |
| **בודק צ'אט**      | שלחו הודעות בזמן אמת ובדקו את מלוא מטען הבקשה/תגובה, כולל הכותרות                    |
| **ספסל בדיקות**    | הריצו בדיקות אצווה על שילובי תבניות כדי לגלות אילו תרגומים אינם תקינים               |
| **ניטור בזמן אמת** | צפו בזרימת הבקשות בזמן אמת כדי לאתר בעיות תרגום לסירוגין                             |

### בעיות תבנית נפוצות

- **תגי חשיבה אינם מופיעים** — בדקו אם ספק היעד תומך בחשיבה ואת הגדרת תקציב החשיבה
- **קריאות לכלים נשמטות** — תרגומי תבניות מסוימים עשויים להסיר שדות שאינם נתמכים; ודאו זאת במצב סביבת הניסוי
- **הנחיית המערכת חסרה** — Claude ו-Gemini מטפלים בהנחיות מערכת באופן שונה; בדקו את פלט התרגום
- **ה-SDK מחזיר מחרוזת גולמית במקום אובייקט** — נפתר ב-v1.x; מנקה התגובות מסיר שדות שאינם תקניים (`x_groq`, `usage_breakdown` וכו') שגורמים לכשלי אימות Pydantic ב-OpenAI SDK. אם הבעיה עדיין מופיעה ב-v3.x+, אנא פתחו דיווח על בעיה.
- **GLM/ERNIE דוחה את התפקיד `system`** — נפתר ב-v1.x; מנרמל התפקידים ממזג אוטומטית הודעות מערכת לתוך הודעות משתמש עבור מודלים שאינם תואמים. אם הבעיה עדיין מופיעה ב-v3.x+, אנא פתחו דיווח על בעיה.
- **התפקיד `developer` אינו מזוהה** — נפתר ב-v1.x; מומר אוטומטית ל-`system` עבור ספקים שאינם OpenAI. אם הבעיה עדיין מופיעה ב-v3.x+, אנא פתחו דיווח על בעיה.
- **`json_schema` אינו פועל עם Gemini** — נפתר ב-v1.x; `response_format` מומר כעת ל-`responseMimeType` + `responseSchema` של Gemini. אם הבעיה עדיין מופיעה ב-v3.x+, אנא פתחו דיווח על בעיה.

## הגדרות עמידות

### הגבלת הקצב האוטומטית אינה מופעלת

- הגבלת קצב אוטומטית חלה רק על ספקים המשתמשים במפתח API (לא OAuth/מינוי)
- ודאו שהגבלת הקצב האוטומטית מופעלת תחת **הגדרות → עמידות → פרופילי ספקים**
- בדקו אם הספק מחזיר קודי מצב `429` או כותרות `Retry-After`

### כוונון השהיה מעריכית

פרופילי ספקים תומכים בהגדרות הבאות:

- **השהיית בסיס** — זמן ההמתנה הראשוני לאחר הכשל הראשון (ברירת מחדל: 1 שנייה)
- **השהיה מרבית** — הגבול העליון של זמן ההמתנה (ברירת מחדל: 30 שניות)
- **מכפיל** — בכמה להגדיל את ההשהיה בכל כשל רצוף (ברירת מחדל: פי 2)

### מניעת עומס מתפרץ

כאשר בקשות מקביליות רבות מגיעות לספק שקצב הבקשות אליו מוגבל, OmniRoute משתמש בנעילה הדדית ובהגבלת קצב אוטומטית כדי לטפל בבקשות באופן סדרתי ולמנוע כשלים מתגלגלים. הדבר מתבצע אוטומטית עבור ספקים המשתמשים במפתח API.

### בקשות צ'אט נכשלות עם 503 / chat_admission_busy

**תסמינים:**

- נקודת הקצה של השלמות הצ'אט מחזירה תגובת `503` שניתנת לניסיון חוזר, שקוד השגיאה שלה הוא
  `chat_admission_busy`.
- התגובה כוללת `Retry-After`. מאז #12135, הערך נגזר מהתפוסה שנצפתה —
  הגדול מבין חלון `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` שבו הבקשה כבר המתינה, לבין משך הזמן
  שבו ההקצאות הכבדות הנוכחיות מוחזקות — מעוגל כלפי מעלה לשניות שלמות ומוגבל ל-60.
  בשער שאינו עמוס נשמרים ערכי המינימום ההיסטוריים: 2 שניות במסלול מבוסס-הבתים,
  ושנייה אחת במסלול מבוסס-המבנה (הכולל גם `reason: "structure_limit"`).
- הדבר עשוי להתרחש כאשר צ'אט כבד אחר או תגובת הזרמה ממושכת עדיין נמצאים
  בעיבוד.

גוף התגובה מבוססת-הבתים הוא:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

התגובה מבוססת-המבנה משתמשת באותו סוג ובאותו קוד, עם ההודעה
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ועם `reason: "structure_limit"`.
בספי ברירת המחדל, בקשה נחשבת כבדה מבחינה מבנית כאשר היא כוללת לפחות `200` הודעות,
לפחות `64` כלים, או לפחות `32,000` אסימונים משוערים, או כאשר אומדן המבנה התחום
ממצה את גבולותיו של `10,000` צמתים שבהם בוצע ביקור או עומק `12`.

**סיבה:** זוהי הפחתת עומס מכוונת בתוך OmniRoute, ולא כשל של ספק במעלה הזרם.
כל תהליך משתמש במנגנון הגנה מקומי לתהליך כדי לשמור קיבולת מוגבלת לעומסים כבדים לפני שמירת
גוף בקשה גדול וניתוחו. הקצאה כבדה נשארת מוחזקת לכל אורך חייה של תגובת SSE.

**התפצלות-#503:** לפני תיקון זה, מנגנון ההגנה הגביל את המקביליות לפי מספר בקשות קבוע
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ברירת מחדל `1`) ללא קשר לזיכרון המארח, ולכן
התפצלות של סוכני תכנות (מספר סוכני משנה/ממשקי CLI, עם גופים שגודלם בדרך כלל מעל 256 KB)
צמצמה את המקביליות בפועל לכ-1 והובילה לשגיאות 503 תחת עומס רגיל לחלוטין. כעת מנגנון ההגנה
מכוונן את עצמו: הוא נשלט באמצעות תקציב בתים לקליטה הנגזר אוטומטית
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), שמחושב לפי מגבלת הזיכרון בפועל של התהליך, ובנוסף
מתחשב באות חי של לחץ על משאבים — כך שהוא מפחית עומס רק כאשר המארח נתון באמת ללחץ זיכרון,
ולא רק משום שיותר מבקשה כבדה אחת הגיעה בו-זמנית. מגבלת הספירה הישנה
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) עדיין מכובדת, אך רק אם מגדירים אותה במפורש.

כאשר הקיבולת עמוסה, בקשה כבדה ממתינה תחילה עד
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ברירת המחדל היא `RATE_LIMIT_MAX_WAIT_MS`; הערך `0` משבית את ההמתנה) להתפנות מקום,
לפני שהיא מקבלת בתגובה את שגיאת `503` שניתנת לניסיון חוזר. ההמתנה התחומה קיימת כדי שלקוחות
בסגנון סוכן (OpenCode, Claude Code, Cursor), שמפצלים במקביל בקשות משנה כבדות, יעבדו את
ההתפרצות באופן סדרתי במקום לבזבז את כל תקציב הניסיונות החוזרים שלהם על דחיות מיידיות
ולהיכשל באמצע המשימה. תפוסת ההקצאות הכבדות הנוכחית, תקציב הבתים שחושב וחומרת הלחץ בזמן אמת
מוצגים ב-`GET /api/monitoring/health` ← `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — בדקו אותם לפני שינוי משתנה סביבה כלשהו.
הגדרות ← עמידות ← תור בקשות ← בקשות מקביליות אינו שולט בכך; הגדרה זו
שולטת במנגנון נפרד של תור בקשות לספק.

**תיקון:**

1. תחילה, נסו שוב. לקוחות צריכים לכבד את `Retry-After` ולהשתמש בהשהיה הדרגתית במקום לחזור
   מיד על הבקשה.
2. בדקו את `/api/monitoring/health` ← `chatAdmission` לפני כוונון כלשהו. `countCapEnabled:
false` ו-`maxInflightBytes` נדיב פירושם שהתקציב הנגזר אוטומטית כבר ממלא את
   תפקידו; `pressureSeverity` בערך `high`/`critical` פירושו שבמארח באמת חסר זיכרון —
   לא ניתן לתקן זאת באמצעות משתנה סביבת קבלה; נדרש יותר RAM או עומס עבודה קטן יותר.
3. רק אם `/api/monitoring/health` מראה שהתקציב הנגזר אוטומטית באמת קטן מדי עבור
   המארח שלכם (מצב נדיר — הוא כבר מתאים את עצמו ממכולות ועד שרתי bare-metal), דרסו אותו ישירות באמצעות
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` במקום לחזור למגבלה הישנה המבוססת על מספר בקשות.

עיינו ב[הפניה למשתני הסביבה](../reference/ENVIRONMENT.md#4-security--authentication)
לקבלת הגדרות הקבלה המוסמכות.

## טקסונומיה אופציונלית לכשלי RAG / LLM ‏(16 בעיות)

חלק ממשתמשי OmniRoute מציבים את השער לפני מערכי RAG או סוכנים. בתצורות אלה נפוץ לראות דפוס מוזר: OmniRoute נראה תקין (הספקים פעילים, פרופילי הניתוב תקינים ואין התראות על מגבלת קצב), אך התשובה הסופית עדיין שגויה.

בפועל, תקריות אלה נובעות בדרך כלל מצינור העיבוד של RAG במורד הזרם, ולא מהשער עצמו.

אם אתם רוצים אוצר מילים משותף לתיאור כשלים אלה, תוכלו להשתמש ב-WFGY ProblemMap, משאב טקסט חיצוני ברישיון MIT המגדיר שישה-עשר דפוסי כשל חוזרים של RAG / LLM. ברמה הכללית הוא מכסה:

- סטייה באחזור וגבולות הקשר שבורים
- אינדקסים ומאגרי וקטורים ריקים או מיושנים
- אי-התאמה בין embeddings למשמעות הסמנטית
- בעיות בהרכבת הנחיות ובחלון ההקשר
- קריסה לוגית ותשובות בעלות ביטחון מופרז
- כשלים בשרשראות ארוכות ובתיאום בין סוכנים
- סטייה בזיכרון ובתפקידים במערכות מרובות סוכנים
- בעיות בסדר הפריסה והאתחול

הרעיון פשוט:

1. כאשר אתם חוקרים תשובה שגויה, תעדו:
   - את משימת המשתמש ואת הבקשה
   - את שילוב המסלול או הספק ב-OmniRoute
   - כל הקשר RAG שנעשה בו שימוש במורד הזרם (מסמכים שאוחזרו, קריאות לכלים וכדומה)
2. מפו את התקרית למספר אחד או שניים ב-WFGY ProblemMap (`No.1` … `No.16`).
3. שמרו את המספר בלוח המחוונים, בספר הנהלים או במערכת מעקב התקריות שלכם, לצד יומני OmniRoute.
4. השתמשו בדף WFGY המתאים כדי להחליט אם עליכם לשנות את מערך ה-RAG, את מנגנון האחזור או את אסטרטגיית הניתוב שלכם.

הטקסט המלא ומתכונים מעשיים זמינים כאן (רישיון MIT, טקסט בלבד):

[README של WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

תוכלו להתעלם מסעיף זה אם אינכם מפעילים צינורות RAG או סוכנים מאחורי OmniRoute.

## בעיות ידועות ב-v3.8.0

בעיות הייחודיות לגרסת v3.8.0 והפתרונות העקיפים הזמינים להן כעת. אם תיקון ייכלל בעדכון מאוחר יותר, הרשומה תעודכן או תוסר.

### כשלי אימות ב-Devin CLI

**תסמינים:**

- "Devin CLI לא נמצא" או "האימות נכשל" בעת הפעלת כלים המבוססים על Devin
- בדיקת זמן הריצה של ה-CLI מדווחת על `installed=false`

**גורמים:**

- `CLI_DEVIN_BIN` מצביע על נתיב שאינו קיים
- Devin CLI אינו מותקן במארח

**תיקון:**

1. התקינו את Devin CLI עבור הפלטפורמה שלכם
2. הגדירו `CLI_DEVIN_BIN=/usr/local/bin/devin` (או את הנתיב האמיתי) בקובץ `.env`
3. הפעילו מחדש את OmniRoute ובדקו שוב דרך **לוח המחוונים → כלי CLI**

### מצב הצינון של מודל נתקע (איפוס ידני)

**תסמינים:**

- מודל ממשיך להופיע במצב צינון גם לאחר שזמן התפוגה חלף
- בקשות עדיין מדלגות על המודל בניתוב משולב, אף שחותמת הזמן כבר חלפה

**איפוס ידני:**

- **לוח המחוונים:** **הגדרות → זמני צינון של מודלים** → לחצו על **הפעלה מחדש** בכרטיס המושפע
- **API:**‏ `DELETE /api/resilience/model-cooldowns` עם כותרות אימות ניהוליות

### החיבור לספק Command Code נכשל עם 403

**תסמינים:**

- מתקבלת שגיאת 403 בעת בדיקת החיבור לספק Command Code
- בכרטיס הספק מופיע "לא מורשה" לאחר הוספה חדשה

**גורם:** תהליך OAuth לא הושלם (ה-callback לא התקבל או שה-token לא נשמר).

**תיקון:**

- הפעילו `omniroute providers` דרך ה-CLI כדי להפעיל מחדש את תהליך OAuth, או
- הפעילו מחדש את OAuth דרך **לוח המחוונים → ספקים → Command Code → התחברות מחדש**

### ModelScope מחזיר זמני צינון אגרסיביים של 429

**תסמינים:**

- זמני צינון קצרים מאוד או מיידיים ב-ModelScope לאחר פרץ קטן של בקשות
- ניתוב משולב מדלג על ModelScope מוקדם מהצפוי

**גורם:** ModelScope שולח כותרות `Retry-After` ייחודיות לספק. v3.8.0 כוללת טיפול ייעודי בכותרות אלה, ולכן גרסאות ישנות יותר מפרשות אותן באופן שגוי כרמזים כלליים למגבלת קצב.

**תיקון:**

- ודאו שאתם משתמשים ב-v3.8.0 או בגרסה מאוחרת יותר
- ודאו שהמתג `useUpstream429BreakerHints` מופעל תחת **הגדרות → עמידות**

### OMNIROUTE_WS_BRIDGE_SECRET חסר בסביבת הייצור

**תסמינים:**

- שגיאת 401 בכל בקשת גשר WebSocket של Codex/Responses בעת הפעלה במארח ייצור מרוחק
- לחיצת היד של גשר WebSocket נסגרת מיד לאחר ההתחברות

**גורם:** משתנה הסביבה `OMNIROUTE_WS_BRIDGE_SECRET` חסר בסביבת הייצור.

**תיקון:**

1. צרו סוד אקראי: `openssl rand -hex 32`
2. הגדירו `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` בסביבת שרת הייצור (ובכל לקוח שמתקשר עם הגשר)
3. הפעילו מחדש את OmniRoute

### Responses API: מצב רקע מצטמצם לביצוע סינכרוני

**תסמינים:**

- נרשמת אזהרה: `background mode degraded to synchronous`
- בקשת `background: true` מחזירה תגובה סינכרונית רגילה במקום מזהה של משימת רקע

**גורם:** v3.8.0 מצמצמת בכוונה את `background: true` ב-Responses API לביצוע סינכרוני, תוך הפקת אזהרה. ביצוע אסינכרוני מלא ברקע מתוכנן לעתיד.

**תיקון:**

- התאימו את הלקוח כך שיבצע קריאה ללא `background`, או
- המתינו לגרסה מאוחרת יותר שתכלול מצב רקע אסינכרוני מלא (עקבו אחר יומן השינויים)

## הפעלה איטית / פסק זמן של בדיקת המוכנות

אם ה-CLI מציג `⚠ Server did not respond within 60s` אך השרת פועל בפועל, פרק הזמן שהוקצה לבדיקת המוכנות קצר מדי עבור הסביבה שלכם.

מצב זה מתרחש בדרך כלל ב-Windows (עקב אנטי-וירוס או מנטרי מערכת קבצים) או בקונטיינרים עם עומסי עבודה כבדים בעת ההפעלה.

**פתרון — הגדילו את פרק הזמן המוקצה:**

```bash
# באמצעות משתנה סביבה (נשמר בין הפעלות):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 דקות
omniroute serve

# באמצעות דגל CLI (לשימוש חד-פעמי):
omniroute serve --ready-timeout 180000
```

ברירת המחדל היא 60,000 אלפיות השנייה (60 שניות). האזהרה מיועדת למידע בלבד; השרת ממשיך לפעול ברקע ויהיה נגיש לאחר השלמת האתחול.

לפרטים מלאים על `OMNIROUTE_READY_TIMEOUT_MS`, ראו [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
