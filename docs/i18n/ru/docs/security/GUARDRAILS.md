> но пока не проверяется сервером — уточнено согласно #11661)

Защитные механизмы обеспечивают безопасность, соблюдение политик и преобразование содержимого на границе
между OmniRoute и вышестоящими провайдерами. Каждый защитный механизм может проверять (и
при необходимости отклонять, преобразовывать или аннотировать) полезную нагрузку запросов (`preCall`) и
ответы вышестоящих провайдеров (`postCall`).

Система работает по принципу **fail-open**: если при выполнении защитного механизма возникает исключение, реестр
регистрирует ошибку и переходит к следующему защитному механизму, не прерывая
запрос. Блокировка всегда является явным решением (`block: true`), а не случайностью.

## Встроенные защитные механизмы

При импорте реестр автоматически загружает шесть защитных механизмов в порядке приоритета
(см. `registry.ts` → `registerDefaultGuardrails()`):

| Приоритет | Имя                 | Этап(ы)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Меньшие значения приоритета выполняются **раньше**.

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

Перехватывает запросы с изображениями, направленные к **моделям без поддержки изображений**, и либо
перенаправляет весь запрос модели с поддержкой изображений, либо перед
вызовом вышестоящего провайдера заменяет части с изображениями текстовыми описаниями, созданными настраиваемой моделью обработки изображений. Это позволяет провайдерам, работающим только с текстом, прозрачно обрабатывать
мультимодальную полезную нагрузку.

Процесс:

1. Пропустить обработку, если целевая модель уже поддерживает изображения (кроме случаев, когда она присутствует в
   списке принудительного использования моста `isVisionBridgeForcedModel`).
2. Извлечь части с изображениями через `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), который делегирует работу **унифицированному детектору
   медиа** `detectMediaParts()` из `open-sse/utils/mediaParts.ts` — единому
   источнику истины, совместно используемому с фильтром совместимости комбинаций.
   Извлечение ограничено разрешённым списком частей верхнего уровня тех форматов,
   которые `replaceImageParts` может вставить обратно (контракт extract↔replace): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` и Responses API `input_image`. Вложенные совпадения и
   формы, содержащие только индикаторы, относятся к материалу для фильтра комбинаций и никогда не извлекаются.
   Пропустить обработку, если ничего не найдено.
3. Определить конфигурацию времени выполнения через `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): новые ключи настроек `modalityBridge*`
   имеют приоритет; устаревшие ключи `visionBridge*` сохраняются как **резервный вариант
   на один цикл** (окно отката). Если мост отключён, пропустить обработку до обхода каких-либо медиаданных.
4. Селектор режима (`modalityBridgeVisionMode`, см. таблицу ниже) выбирает
   перенаправление или описание. При перенаправлении возвращается `modifiedPayload`, где заменено только поле `model`,
   а также метаданные `{ rerouted, fromModel, toModel, imagesKept }`.
5. Путь описания: ограничить количество изображений значением `maxImages`, сформировать промпт с учётом задачи,
   проверить кэш описаний, вызвать модель обработки изображений **параллельно**
   (`Promise.allSettled`) и подставить вместо изображений текстовые части `[Image N]: <description>`.
   При ошибке описания возвращается `null`, а исходная часть с изображением
   **сохраняется** (#4012) — кроме пути описания для комбинации, когда не удалось получить ни одного
   описания: в этом случае для подтверждённого вышестоящего провайдера без поддержки изображений вместо изображения подставляется
   заглушка `(unavailable — no vision-capable provider connected)` (#8430).
6. Вернуть `modifiedPayload` и метаданные (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режима (`modalityBridgeVisionMode`)

| Режим      | По умолчанию | Поведение                                                                                                                                                                                                                                                                                                                                                        |
| ---------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔            | Прежняя эвристика без изменений (#6640/#7204): модели, не относящиеся к комбинациям, и модели `auto/` перенаправляются к лучшей модели с поддержкой изображений, если у исходной модели нет пригодных учётных данных (при их наличии используется описание); для целей-комбинаций всегда используется описание.                                                  |
| `describe` |              | Всегда использовать описание — блок перенаправления полностью пропускается; ответ всегда генерирует выбранная пользователем модель.                                                                                                                                                                                                                              |
| `reroute`  |              | Принудительное перенаправление: проверка сохранения модели с учётными данными обходится. Проверка учётных данных **целевой модели** перенаправления по-прежнему применяется — если подходящая целевая модель с поддержкой изображений отсутствует, запрос переходит к описанию, чтобы необработанные изображения никогда не попадали в текстовый бэкенд (#8430). |

Принудительные режимы завершают выбор **до** запуска автоматической эвристики; поведение `auto`
побайтово идентично защитному механизму до PR-1.

#### Промпт описания с учётом задачи (`modalityBridgeVisionTaskAware`)

По умолчанию — **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) добавляет
текст **последнего сообщения пользователя** (сокращённый до 500 символов) к базовому
промпту описания, направляя описание на фактический запрос пользователя
(паттерн codex-vision-proxy) и предлагая модели обработки изображений транскрибировать видимый
текст. Если флаг отключён или пользовательский текст отсутствует, базовый промпт используется без изменений.

Собственный OpenAI-совместимый запрос self-loop для describe (`callVisionModelSingle()`
в `visionBridgeHelpers.ts`) всегда запрашивает `image_url.detail: "high"` —
безусловно, для любого вызывающего компонента/провайдера и независимо от каких-либо
сигналов клиента. Выбор низкого уровня детализации снижает точность OCR именно для
задачи транскрибирования текста, указанной в этом промпте, поэтому сам вызов describe
всегда запрашивает высокий уровень детализации независимо от того, какой уровень
детализации использовался в исходном входящем запросе. Это влияет только на тело
внутреннего запроса describe; способ, которым OmniRoute передаёт собственное значение
`image_url.detail` вызывающей стороны в основном запросе, не изменяется — значение
по умолчанию применяется отдельно и только для обнаруженных клиентов OpenCode в
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Ветка
wire-формата Anthropic в self-loop describe не имеет поля `detail` и не затрагивается
ни одним из этих значений по умолчанию.

#### Ограничение вывода describe (`modalityBridgeVisionMaxChars`)

| Ключ                           | По умолчанию | Диапазон          |
| ------------------------------ | ------------ | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` или 100–50000 |

`0` (по умолчанию) означает **без ограничения** — описание, возвращаемое
`callVisionModel()`, передаётся без изменений, сохраняя существующее
поведение. Любое значение в диапазоне 100–50000 обрезает описание, добавляя
суффикс `…`, прежде чем оно будет вставлено обратно в виде
`[Image N]: <description>` (`VisionBridgeGuardrail.preCall()` в
`src/lib/guardrails/visionBridge.ts`). Увеличьте это значение для задач OCR
с большим объёмом деталей, где последующей модели требуется полная
транскрипция; уменьшите его, чтобы ограничить расход токенов многословными
моделями машинного зрения. Поле панели управления находится в разделе
«Дополнительно» вкладки Vision (`modality-bridge-max-chars` в
`ModalityBridgeVisionTab.tsx`) и повышает любое значение от 1 до 99 до
минимального порога 100, оставляя явно заданный `0` без изменений — `0`
сам по себе является допустимым значением Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не
просто значением по умолчанию для состояния «не задано».

#### Кеш describe (`modalityBridge/bridgeCache.ts`)

Общий для всего процесса кеш в памяти с LRU + TTL для результатов describe.
Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` с
префиксами длины (без коллизий на границах полей). Компонент модели — это
**настроенная** bridge-модель, а не модель, которая фактически ответила:
`callVisionModel` может внутренне переключиться на резервную модель, а
формирование ключа для каждой попытки фрагментировало бы кеш. Неудачные
вызовы describe никогда не кешируются. Настройки:

| Ключ                            | По умолчанию | Диапазон |
| ------------------------------- | ------------ | -------- |
| `modalityBridgeCacheEnabled`    | `true`       | —        |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000  |

#### Нормализация удалённых изображений (self-loop describe/получение base64)

Когда bridge самостоятельно получает **удалённое** изображение — для
self-вызова Anthropic describe и преобразования в base64 для claude-wire-format
(`ensureBase64ImagesForClaudeWire`), в обоих случаях через
`fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts` — полученный URI данных
перед встраиванием в запрос к модели машинного зрения передаётся через
`normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`). Изображения
слишком большого размера уменьшаются до **2048px по длинной стороне** (в
соответствии с ограничением изменения размера, которое OpenAI/Anthropic уже
применяют на стороне сервера), что сокращает объём отправляемых данных и
задержку, не изменяя того, что видит модель машинного зрения. Для изменения
размера используется `sharp`, загружаемый посредством динамического импорта:
на платформе, где не удаётся загрузить его нативный бинарный файл,
`normalizeDataUri()` **никогда не выбрасывает исключение** — вместо этого
исходные байты передаются без изменений, поэтому путь describe/преобразования
в base64 продолжает работать всегда. Данные, не являющиеся изображением
(если результат загрузки не оказался декодируемым изображением), также
передаются без изменений. Эта нормализация применяется только к изображениям,
которые bridge получает для собственного self-вызова, — она никогда не
применяется к исходной полезной нагрузке вызывающей стороны, передаваемой
напрямую, в соответствии с принципом изменения только при явном согласии
(жёсткое правило №20).

#### Схема настроек + миграция

Новые ключи `modalityBridge*` проверяются с помощью Zod в
`updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`):
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, три ключа
`modalityBridgeCache*` и группа `modalityBridgeAudio*`, используемая Audio
Bridge. Миграция `141_modality_bridge_settings.sql` копирует существующие
устаревшие значения `visionBridge*` в соответствующие новые ключи
(идемпотентно и без перезаписи значений `modalityBridge*`, заданных
оператором); устаревшие ключи продолжают приниматься в качестве резервного
источника при чтении в течение одного цикла выпуска.

#### Заголовок прозрачности + статистика

Ответы, преобразованные с помощью describe, содержат
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(создаётся `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`
и добавляется `withModalityBridgeHeader()` в
`src/sse/handlers/chatHelpers.ts`). Перенаправленные запросы **не** получают
этот заголовок — полезная нагрузка не изменялась, а замена модели уже видна
в поле `model` тела ответа.

`GET /api/modality-bridge/stats` (с аутентификацией управления, того же уровня,
что и `GET /api/settings`) возвращает хранящиеся в памяти счётчики для каждой
модальности `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` и
`video`. В качестве знаменателя для `averageLatencyMs` используется
`latencySamples`, а не все попытки; операция без замера времени не создаёт
фиктивный образец с нулевой задержкой. `bridged` остаётся обратно совместимым
псевдонимом для успешных преобразований; неудачные попытки не увеличивают его.
Счётчики намеренно сбрасываются при перезапуске процесса
(это телеметрия, а не учёт).

#### Конфигурация панели управления

Специальная страница панели управления находится по адресу
`/dashboard/settings/modality-bridge`. Доступные по URL вкладки `Vision`, `Audio`
и `Video` сохраняют параметры запроса при переключении значения `tab`.
Вкладка Vision предоставляет настройки включения, режима, выбора модели (включая
автоматическое значение по умолчанию), подсказок с учётом задачи, расширенных
ограничений времени ожидания, изображений, длины описания и кеша, счётчики среды
выполнения и защищённый тестовый запрос. Вкладка Audio также работает: она
предоставляет настройки включения, выбор модели только для STT с вариантом Auto,
ограничения времени ожидания и максимальной длительности клипа, счётчики аудио
и тестовый запрос `input_audio`. Вкладка Video полностью функциональна: она
отображает состояние FFmpeg/ffprobe в среде выполнения — одно из четырёх явно
заданных состояний интерфейса (`unknown`, пока проверка выполняется или не может
быть завершена; `restricted`, если панель управления размещена не на loopback-хосте
и проверка пропускается на стороне клиента; `unavailable`, если проверка завершена
и подтвердила отсутствие компонентов; или `available` с версиями FFmpeg/ffprobe) —
сохраняет настройки включения, модели, кадров, видео и времени ожидания, фильтрует
список моделей, оставляя модели с поддержкой зрения, и предоставляет счётчики
видео.

Прежняя карточка Vision Bridge в настройках ИИ теперь является ссылкой для
совместимости, ведущей на новую страницу; она больше не содержит вторую копию
формы. Раздел Media Providers также связывает рабочие процессы Image-to-Text и
Speech-to-Text с соответствующими вкладками Modality Bridge, не удаляя
существующую тестовую площадку Speech-to-Text.

**Обход контроля допуска для self-loop:** когда вызов описания направляется через
собственный self-loop OmniRoute `/v1` (модель нестандартного провайдера),
подзапрос отправляет `x-omniroute-admission-bypass: internal` и аутентифицируется
с помощью разрешённых учётных данных self-loop — локального маркера
`sk_omniroute` в локальном режиме либо настроенного оператором ключа окружения
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), чтобы развёртывания с
`REQUIRE_API_KEY=true` по-прежнему могли выполнять вызов описания. Обход
разрешён только для этих точных учётных данных, поэтому внешние клиенты не могут
использовать этот заголовок для пропуска контроля допуска.

Устаревшие значения по умолчанию находятся в
`src/shared/constants/visionBridgeDefaults.ts`; новые значения по умолчанию для
режима, учёта задачи и кеша, а также функция разрешения настроек находятся в
`src/shared/constants/modalityBridgeDefaults.ts`. Защитный механизм предоставляет
параметр конструктора `deps`, чтобы тесты могли внедрять фиктивные реализации
`getSettings` и `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехватывает содержащие аудио запросы чата до того, как они достигнут целевого
объекта, для которого не подтверждена поддержка аудиовхода. Он никогда не
перенаправляет сам запрос чата: аудиофрагменты транскрибируются через
существующую OpenAI-совместимую multipart-точку доступа, после чего выбранная
модель чата продолжает работу с текстовыми расшифровками.

Процесс:

1. Определить `supportsAudio` через `getResolvedModelCapabilities()`. Приоритет
   имеют явные метаданные реестра провайдеров, затем статические метаданные
   модели, а затем синхронизированное значение `modalities_input`. Объявленный
   список входных данных без `audio` даёт `false`; отсутствие сведений о
   возможности даёт `null`. И `false`, и `null` активируют консервативный мост,
   тогда как `true` обходит его.
2. Разрешить настройки `modalityBridgeAudio*` и извлечь допускающие замену
   аудиофрагменты верхнего уровня из каждого сообщения с помощью общего
   детектора `detectMediaParts()`. Поддерживаются форматы передачи OpenAI
   `input_audio`, `audio_url` и `source.media_type: "audio/*"`. Вложенное аудио
   обнаруживается для маршрутизации, но не удаляется путём замены. Объём работы
   ограничивается значением `modalityBridgeAudioMaxClips`; последующие фрагменты
   остаются без изменений.
3. Использовать настроенное значение `provider/model` либо позволить
   `selectAudioBridgeModel()` перебрать `AUDIO_TRANSCRIPTION_PROVIDERS` в
   стабильном порядке каталога и выбрать первую модель с пригодными активными
   учётными данными провайдера.
4. `callAudioTranscription()` преобразует аудио в формате base64/data URI в
   multipart-файл `file` либо загружает удалённый `audio_url` через ограничитель
   исходящих подключений только к публичным адресам с фиксацией DNS и лимитом
   25 МБ. Затем функция отправляет POST-запрос с файлом и выбранной моделью в
   локальный self-loop `/v1/audio/transcriptions`, аутентифицируясь с помощью
   `resolveSelfLoopBearer()`. Существующий маршрут транскрибирования выполняет
   обычный поиск учётных данных, обработку периода восстановления и ограничений
   частоты запросов, а также диспетчеризацию провайдера.
5. Успешные вызовы заменяют соответствующие фрагменты на
   `[Audio N]: <transcript>`. Вызовы выполняются через `Promise.allSettled`:
   отдельный сбой сохраняет исходный аудиофрагмент (контракт #4012). Если все
   вызовы завершаются с ошибкой и для целевого объекта доказано
   `supportsAudio === false`, фрагменты заменяются на
   `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430). Для
   неизвестного целевого объекта (`null`) при сбое всех вызовов фрагменты
   остаются без изменений. Целевой объект, для которого подтверждена поддержка
   только текста и отсутствуют пригодные учётные данные STT, получает ту же
   явную заглушку без выполнения сетевого вызова.

Успешные расшифровки используют общий для всего процесса LRU/TTL-кеш Modality
Bridge. Ключ объединяет ссылку на аудио, стабильную метку операции
`audio-transcription` и выбранную модель STT; ошибки никогда не кешируются.
Попытки обработки аудио обновляют общие счётчики `bridged`, `cacheHits`,
`failures` и `lastUsedAt`. Преобразованные ответы содержат
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; запросы,
оставшиеся без изменений, не получают сегмент Audio Bridge.

Настройки среды выполнения хранятся в БД и проверяются с помощью Zod:

| Ключ                          | По умолчанию | Диапазон        |
| ----------------------------- | ------------ | --------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —               |
| `modalityBridgeAudioModel`    | `""`         | Auto или STT ID |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10            |

Управление общим кешем по-прежнему осуществляется через
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и
`modalityBridgeCacheMaxEntries`.

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехватывает части видео верхнего уровня в `messages` Chat Completions и `input`
Responses API перед вызовом целевой системы без известной встроенной поддержки
видео. Поддерживаются форматы `input_video`, `video_url`, `video_source`, URL-адреса
HTTPS и URI данных `data:video/*;base64,...`. Обычные имена файлов в тексте не
считаются видео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) отвечает за обход запроса,
проверку возможностей и политик, агрегацию на уровне запроса и полезную нагрузку
ответа. Обработка каждого видео — получение данных, кэширование полного
результата, описание последовательности кадров (с объединением любой заявленной
вызывающей стороной расшифровки аудио), а также метрики, прерывание и очистка
для каждой попытки — скрыта за `processVideoPart` в `videoBridgePipeline.ts`,
которая вызывается один раз для каждой части видео внутри цикла `preCall`.
Этот модуль также определяет явные границы портов `VideoMediaBrokerPort`
(получение байтов и извлечение выбранных кадров), `VideoAudioTranscriptionPort`
(объединение заявленной вызывающей стороной расшифровки аудио с подписями к
выбранным кадрам) и `VideoDrilldownPort` (граница хранения данных детального
анализа кадров; пока не подключена к `processVideoPart` — на сегодняшний день
записи детального анализа создаёт только отдельный маршрут
`/api/modality-bridge/video/drilldown`).

Публичный путь запросов `/v1` никогда не импортирует и не запускает подпроцессы.
Удалённые видео загружаются с ограничением в 50 МиБ; для встроенных видео в
base64 установлен консервативный лимит в 36 МиБ декодированных данных на видео,
чтобы оболочка модели, сообщений и фрейминга могла оставаться в пределах
публичного лимита допуска JSON-запросов в 50 МиБ. Длина встроенных данных и
оценка декодированного размера проверяются до выделения памяти. HTTPS обязателен
как для исходного удалённого URL-адреса, так и для каждого перенаправления;
используется существующая защита исходящих запросов только к публичным адресам
с фиксацией DNS. Затем байты пересекают строго определённую внутреннюю границу
брокера `POST /api/modality-bridge/video/extract`. Этот маршрут одновременно
имеет категории `LOCAL_ONLY` и `SPAWN_CAPABLE`, принимает только
аутентифицированный запрос от доверенного loopback-интерфейса в рамках процесса
и никогда не принимает URL-адрес, путь в файловой системе, исполняемый файл или
список аргументов. Конвейер ограничения размера тела API и инкрементальный
считыватель тела обработчика независимо друг от друга обеспечивают лимит входных
данных брокера в 50 МиБ. Его ограниченная очередь выполняет по одному извлечению
за раз, допускает четыре ожидающих задания и ограничивает совокупный объём
ожидающих входных данных до 100 МиБ.

Внутри брокера `ffprobe` читает закрытый локальный файл; фиксированный список
разрешённых форматов исключает форматы плейлистов и манифестов. Для разрешённых
контейнеров семейства MOV внешние ссылки MOV на данные по умолчанию остаются
отключёнными, а фиксированная команда их не включает. И `ffprobe`, и `ffmpeg`
используют список разрешённых протоколов, содержащий только `file`, один поток,
фиксированные массивы аргументов, не используют оболочку, а исполняемые файлы
разрешаются через `PATH`. Потоки обложек типа attached picture не считаются
кандидатами на воспроизведение. Все воспроизводимые потоки должны соответствовать
ограничениям; явный поток по умолчанию имеет приоритет перед детерминированным
резервным выбором потока с наименьшим индексом. Продолжительность видео ограничена
600 секундами, каждый размер — 8 192 пикселями, а общее количество исходных
пикселей — 33 554 432. FFmpeg выбирает 1–16 промежуточных JPEG-кадров, уменьшает
длинную сторону максимум до 1 024 пикселей, не увеличивая изображения меньшего
размера, и никогда не получает URL-адрес. По умолчанию используется политика
выборки `uniform`. Необязательная политика `scene_aware` и экспериментальная
политика `segment_aware` выполняют один дополнительный фиксированный проход
FFmpeg по уже проверенному локальному потоку, выбирают ограниченный набор временных
меток сцен `showinfo` и детерминированно возвращаются к тем же равномерным
серединам интервалов при сбое детектора, истечении времени ожидания, некорректном
выводе или пустом наборе кандидатов. Режим segment-aware распределяет выборки
средних точек пропорционально проверенным интервалам сцен; свидетельства
segment-aware и поведение при резервном переходе подробно описаны ниже. Жёсткое
ограничение в 16 кадров применяется после выбора при любой политике. Если у
запроса scene-aware бюджет составляет только один кадр, используется равномерная
середина активного окна полного видео или фокуса и сообщается
`policyEffective: uniform`: один выбранный кадр сцены не может сохранить оба
временных края. Вызывающая сторона может при необходимости предоставить конечное
окно фокуса (`start`/`end` в секундах); границы ограничиваются длительностью
медиа, перевёрнутые окна или окна с неконечными значениями отклоняются, а все
политики выборки применяются только внутри нормализованного интервала.
Полученное окно включается в метаданные выборки и в префикс недоверенного
описания, чтобы последующие модели могли отличать сфокусированный фрагмент от
полной временной шкалы.

Семантический фокус подписей — отдельная явная настройка. Режим анализа `full`,
используемый по умолчанию, сохраняет существующий промпт для кадров и никогда не
передаёт текст запроса модели подписей. В режиме `focused` мост считывает только
последний непустой пользовательский `text`/`input_text` из того же контейнера
Chat или Responses, нормализует его в NFC, сворачивает управляющие символы и
пробельные последовательности и ограничивает длину 500 кодовыми точками Unicode.
Если результат пуст, используется в точности промпт `full`. Пригодная подсказка
сериализуется в JSON в выделенном блоке недоверенного пользовательского контекста
и может лишь задавать приоритет наблюдаемым деталям; она не может переопределить
отдельное предупреждение о недопустимости следования инструкциям, видимым или
слышимым в медиа. Текстовый фокус никогда не выводит `start`/`end` и не изменяет
временной семплер.

#### FU-07 структурные свидетельства сегментов

`segment_aware` выполняет один ограниченный проход предварительного анализа по
уже проверенному локальному видеопотоку. Фиксированная цепочка фильтров сначала
масштабирует видео до ширины не более 320 пикселей, обнаруживает смены сцен и
замороженные интервалы, а затем выполняет выборку с частотой 1 кадр в секунду
для оценки размытия, средней яркости и пространственной/временной информации.
Проход ограничен 600 структурными выборками, одним потоком FFmpeg/фильтра, теми
же списками разрешённых протоколов только с `file` и разрешённых контейнеров,
ограничением вывода процесса в 1 МиБ и максимум 30 секундами в рамках общего
механизма прерывания/крайнего срока брокера. Он никогда не принимает из запроса
команду, фильтр, путь или URL-адрес.

Структурные значения представляют собой детерминированные данные выборки, а не семантическое понимание видео. Они не позволяют делать выводы о субъектах, действиях, субтитрах, речи или намерениях пользователя. Границы сцен и зависаний формируют сегменты; охват зависаний, размытие, экспозиция, пространственная детализация и временные изменения влияют только на распределение существующего бюджета в 1–16 кадров. Полностью зависший сегмент ограничивается одним кадром, тогда как независшие сегменты конкурируют за оставшийся бюджет. Когда количество границ превышает количество кадров, сохраняется равномерный охват временной шкалы, чтобы быстрые монтажные склейки в начале не могли скрыть длинный завершающий сегмент. Границы сцен, находящиеся в пределах 1-секундного разрешения анализа от границы зависания, объединяются.

Отсутствующие фильтры, некорректные или пустые данные, ошибка детектора либо истечение ограниченного времени предварительного анализа приводят к точному откату на политику равномерного выбора кадров в серединах интервалов. Прерывание со стороны вызывающего кода или истечение срока выполнения брокера не приводят к такому откату: они завершают выполняющийся подпроцесс, предотвращают последующее извлечение кадров, а приватное временное дерево удаляется в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` создаёт детерминированные реальные фикстуры FFmpeg для оценки сокращения числа вызовов создания подписей после дедупликации, распределения бюджета при интенсивном движении, данных о размытии, экспозиции и SI-TI, быстрых монтажных склеек с длинным хвостом и ложноположительных срабатываний при постепенном затемнении. Скрипт записывает полное время предварительного анализа и, если доступен `/usr/bin/time`, процессорное время дочернего процесса и пиковое значение RSS. Его проверки качества используют только структурные эталоны. Качество реальной модели создания подписей остаётся в состоянии `HOLD`, поскольку у этого тестового стенда нет авторизованной конечной точки или зафиксированного оценщика. Денежная экономия также остаётся в состоянии `HOLD`, если параметр `--caption-cost-per-call-usd` не задаёт явную положительную оценку стоимости одного вызова; скрипт никогда не фабрикует ни один из этих результатов.

Размер каждого кадра ограничен 4 МиБ, совокупный размер всех необработанных кадров — 23 МиБ, а размер сериализованного ответа брокера — 32 МиБ. Приватный временный каталог удаляется в `finally`. OmniRoute не включает FFmpeg в комплект поставки и не принимает пользовательский путь к исполняемому файлу. Перед созданием подписей мост выполняет консервативную визуальную дедупликацию: каждый JPEG преобразуется в буфер оттенков серого размером 16×16 и сравнивается только с последним сохранённым кадром. Если запрошенный бюджет подписей превышает один кадр, при извлечении формируется ограниченный пул кандидатов размером не более удвоенного бюджета и никогда не более 16 кадров. Запрошенное ограничение применяется только после дедупликации; при окончательном прореживании сохраняются первый и последний выбранные кандидаты, если бюджет составляет не менее двух кадров. Версионированная политика `grayscale-16x16-mean-cells-v2` использует большее из двух значений: среднюю разницу яркости либо долю ячеек миниатюры, нормализованная разница которых составляет не менее 0.05. Порог дубликата задан константой 0.04: это сделано ради предсказуемости, а не для предоставления настройки времени выполнения. Этот дополнительный сигнал высокой контрастности сохраняет небольшие движения и изменения видимого текста, которые может скрыть сравнение только по среднему значению. При ошибках компаратора или декодера сохраняется полный охват. Метаданные результата раздельно отражают извлечённых кандидатов, успешно использованные кадры и отброшенные визуальные дубликаты.

Явно помеченная видеочасть может запросить контактный лист с временными метками. Мост создаёт JPEG-сетку не более чем из 4 столбцов и 16 кадров. В каждой 512-пиксельной ячейке временная метка исходного кадра впечатывается в высококонтрастную нижнюю полосу, при этом те же временные метки сохраняются в текстовых метаданных для последующего сопоставления и аудита. Размер готового JPEG по-прежнему ограничен 32 МиБ. Если `sharp` не удаётся декодировать или скомпоновать сетку, мост возвращается к отдельным JPEG-кадрам; прерывание со стороны клиента по-прежнему распространяется на операцию создания листа.

Данные для принятия решения о продвижении намеренно отделены от синтетического микротеста производительности компоновки. `scripts/perf/video-bridge-contact-sheet-eval.ts` определяет версионированный по схеме стенд A/B-тестирования для реальных моделей компьютерного зрения с API, совместимым с OpenAI. Он измеряет заявленное поставщиком количество токенов, полную задержку от начала до конца, включая компоновку листа, количество вызовов модели и сохранение фактов, определённых манифестом. Необработанные ответы модели не записываются в отчёт; сохраняются только дайджесты SHA-256 и идентификаторы совпавших фактов. Стенд не выполняет сетевых запросов или платных вызовов модели, если не передан параметр `--execute-real` и не настроены `--model`, `OMNIROUTE_BASE_URL` и `OMNIROUTE_API_KEY`. Без такого явно запрошенного реального запуска его машиночитаемый вердикт остаётся `HOLD`; одни лишь синтетические измерения размера полезной нагрузки и количества вызовов не являются основанием для продвижения.

Вызывающий код может добавить необязательный массив `transcript.cues` к поддерживаемой видеочасти, если у него уже имеется синхронизированный текст. Каждая реплика должна содержать `text`, конечный интервал `start`/`end` в пределах установленной длительности и значение `source` из разрешённого списка (`client`, `embedded` или `audio-bridge`); значение `confidence` по умолчанию равно `1` и должно оставаться в диапазоне от `0` до `1`. Полностью совпадающие реплики объединяются. OmniRoute никогда не запускает транскрибацию на основе этих метаданных: проверенные реплики копируются в описанный результат вместе с источником, уровнем уверенности и интервалом и отображаются рядом с подписями к кадрам как недоверенные наблюдения. Некорректный текст, текст за пределами допустимого диапазона или текст без сведений о происхождении отклоняется, а не смешивается с потоком подписей. В настоящее время поле `source` объявляется вызывающей стороной, а не проверяется сервером: OmniRoute проверяет, что значение является одной из трёх разрешённых строк, но пока не подтверждает криптографически, что метка `embedded` или `audio-bridge` действительно была получена в результате извлечения, выполненного подконтрольным серверу компонентом. Считайте `source` недоверенной подсказкой до появления такой проверки; не основывайте на нём решения об авторизации.

Продвинутый вызывающий код может предоставить уже авторизованную дорожку `audioTranscript`
для того же видео. Узел объединения выполняет обработку визуальных и аудионаблюдений с единым
сроком выполнения и сигналом прерывания, упорядочивает их на общей временной шкале, сворачивает
полные дубликаты и возвращает частичный результат, если успешно обработана только одна сторона.
Недопустимый `audioTranscript` приводит к возврату такого частичного результата — визуальное
описание сохраняется, а аудиоветвь записывает очищенный код ошибки — вместо сбоя обработки всего
видео. Доступность каждой ветви, флаг частичного результата и очищенные коды ошибок сохраняются
в описанном результате, в метаданных защитных механизмов (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), в метаданных кэша результатов и в счётчиках объединения моста.
Стандартный путь Video Bridge не вызывает преобразование речи в текст и не загружает вторую
копию медиаданных; без явно предоставленной дорожки он продолжает обрабатывать только видео.

**Хранение расшифровок (#12150 P1).** Это применяется автоматически всякий раз, когда
Video Bridge (который сам является опциональным) визуализирует реплику расшифровки — отдельного
флага хранения нет. Когда запрос визуализирует любую реплику расшифровки (объявленный вызывающим
кодом `transcript` или объединённый `audioTranscript`), защитный механизм помечает её как
`videoBridgeObserved` и создаёт отредактированную теневую копию описания видео —
идентичное представление, в котором произвольный текст каждой реплики заменён на
`[redacted-video-transcript]`; копия создаётся путём подстановки значения структурированного поля
реплики до сборки строки (а не путём разбора сведённого текста, поэтому никакое содержимое реплики —
вредоносное или обычное, включая текст с символом `]`, например
`[inaudible]`/`[music]`, — сохраниться не может). В сохраняемом теле запроса журнала вызовов каждая
текстовая часть, полученная из видео, заменяется этой отредактированной теневой копией посредством
сопоставления по равенству содержимого; привязка `fullText` повторно считывается из завершённой
полезной нагрузки защитного механизма перед вызовом, поэтому сопоставление остаётся успешным даже
после того, как последующие цепочечные защитные механизмы (маскировщики персональных данных и
учётных данных с приоритетами 10/95) изменят текст описания на месте, а внедрение системной
инструкции, передачи контекста и памяти преобразует массив сообщений. Тело, отправляемое модели,
остаётся неизменным. Наблюдаемый запрос также не заполняет долговременную Memory (извлечение как
из запроса, так и из ответа пропускается), поэтому собственный ответ модели не может перенести
текст расшифровки в Memory.

Поверхности хранения, которые пока остаются открытыми и отслеживаются для последующей работы
(**P2**, #12430): необработанный снимок клиентского запроса до применения защитных механизмов
в артефакте подробного журнала; продолжение через `previous_response_id` с отказом по умолчанию;
внутренние отправки производных инструкций, встраивающие расшифровку в синтезированную строковую
инструкцию (этапы конвейера, передача контекста); а также тело ответа и копия ответа модели
в семантическом кэше, если модель цитирует расшифровку. Это необработанные поверхности или
поверхности класса ответов либо опциональные поверхности, находящиеся за пределами области P1,
которая охватывает сохраняемое тело запроса и Memory.

Жизненный цикл внутреннего `/api/modality-bridge/video/drilldown` представляет собой отдельную,
аутентифицированную с помощью токена инфраструктуру кэша с доступом через loopback-интерфейс.
Для каждой операции также требуется канонический непрозрачный идентификатор субъекта. Прежде чем
разрешить доступ производственному вызывающему коду, он должен получать этот идентификатор из
аутентифицированного арендатора и ни в коем случае не передавать значение, выбранное клиентом.
Ключи кэша связывают этого субъекта с каноническими идентификаторами сеанса и ссылки на видео,
хранят только производные от них ключи SHA-256 и ограничивают как чтение, так и удаление тем же
субъектом. Кэш хранит не более 16 производных JPEG-кадров на запись, удаляет их через десять минут
и поддерживает ограниченное чтение с помощью `start`/`end` либо явное удаление сеанса.

Для каждого субъекта установлено ограничение в 16 записей и 64 MiB канонических JPEG-данных. Эти
ограничения не зависят от общего предела в 64 записи/256 MiB: при исчерпании квоты субъекта сначала
удаляются только его записи, использовавшиеся дольше всего назад, и лишь затем рассматривается
глобальное вытеснение LRU. Во время операций с кэшем просроченные записи удаляются как из учёта
субъекта, так и из глобального учёта, тогда как при отмене или ошибке проверки частичная замена
не фиксируется.

Кэш отклоняет неканонический Base64, избыточное заполнение, данные не в формате JPEG, повреждённые
или усечённые JPEG-файлы, а также JPEG-файлы, при ограниченном полном декодировании которых с помощью
`sharp` возникает предупреждение. Каждое принятое изображение повторно кодируется как канонический
JPEG; ширина и высота определяются по декодированным байтам, а не по полям вызывающего кода;
любые замыкающие полиглотные байты отбрасываются, а не сохраняются. В обе квоты засчитывается только
ограниченный канонический сжатый буфер. Ограничение размера данных JSON учитывает накладные расходы
Base64 для предельного объёма декодированных входных данных в 32 MiB. Для каждого
сохранённого производного объекта записываются проверенные формат и разрешение JPEG, политика
выборки, версия формирования производного объекта, время создания, вычисленный сервером хеш
содержимого, хешированная ссылка на родительский объект и хеш содержимого родительского объекта
от доверенного вызывающего кода. Наличие отмены проверяется между асинхронными этапами
декодирования и хеширования до атомарной фиксации в кэше.

Эта часть работы пока не подключает производственный источник данных к маршруту и не
предоставляет выбор вариантов с разным разрешением. Поэтому прозрачный путь запросов Video Bridge
не создаёт дополнительной нагрузки, а получение привязанного к арендатору идентификатора субъекта
и полный жизненный цикл FU-08 с несколькими разрешениями остаются явно обозначенной последующей
работой, а не документируются как уже реализованное поведение.

Кадры последовательно снабжаются описаниями с помощью настроенной модели Video. Пустое
переопределение Video наследует настройку Vision; если обе настройки пусты, автоматический
маршрутизатор Vision выбирает фактически используемую модель с поддержкой визуальных данных. Успешно созданные описания
заменяют исходную часть текстом со стабильным префиксом `[Video description:`, который также
помечает этот текст как ненадёжное наблюдение, полученное из медиаданных, и указывает последующим
моделям не выполнять инструкции, обнаруженные в медиа. Ключи кеша описаний кадров
включают байты JPEG, запрос, временную метку и фактически используемую модель; кешируются только успешно
созданные описания. Записи кеша сохраняют модель, действительно успешно создавшую описание,
включая резервную модель; мост сообщает `mixed`, если разные кадры
были обработаны разными моделями. При попадании в кеш повторно используется идентификатор создавшей описание модели,
а не идентификатор запрошенного плана маршрутизации. Ключ кеша результата для всего видео
формируется из всех входных данных, изменяющих результат: запроса, фактически используемой
модели, политики выборки, количества кадров, режима семантического анализа, отпечатка SHA-256
нормализованной подсказки фокуса, окна фокуса, `transcript`,
`audioTranscript` и флага контактного листа, — поэтому изменение любого из этих
параметров приводит к промаху кеша, а не к повторному использованию устаревшего результата. Версия политики
визуальной дедупликации, пороговое значение и ограниченное количество кадров-кандидатов также явно включаются в
ключ и метаданные кеша результата; поэтому изменение политики не позволяет повторно использовать устаревшее
описание всего видео. Метаданные кеша результатов v4 сохраняют режим и
отпечаток, но никогда не сохраняют исходную пользовательскую задачу. Метаданные защитного механизма содержат как
запрошенный, так и фактический режимы анализа; если режим `focused` запрошен без
пригодного пользовательского текста, в качестве фактического режима указывается `full`.

Защитный механизм извлекает все поддерживаемые видеочасти, но описывает не более
`modalityBridgeVideoMaxVideos`. Для целевой модели, о которой достоверно известно, что
`supportsVideo === false`, видео, обработка которых завершилась ошибкой, и видео сверх лимита заменяются явными безопасными
текстовыми маркерами, чтобы исходное видео не сохранилось. Если возможность неизвестна, эти части
остаются без изменений. Целевые модели с `supportsVideo === true` обходят мост.
Сигнал прерывания клиентского запроса распространяется на скачивание, очередь брокера,
подпроцессы и вызовы создания описаний; прерывания останавливают обработку между видео и никогда не приводят к
небезопасному пропуску исходных медиаданных.

Настройки среды выполнения хранятся в БД и проверяются с помощью Zod:

| Ключ                                | Значение по умолчанию | Диапазон / поведение                                                                                           |
| ----------------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`               | Необязательная функция среды выполнения, включаемая явно                                                       |
| `modalityBridgeVideoAnalysisMode`   | `"full"`              | `full` сохраняет общие описания; `focused` использует ограниченный ненадёжный контекст последнего пользователя |
| `modalityBridgeVideoModel`          | `""`                  | Наследует модель Vision Bridge                                                                                 |
| `modalityBridgeVideoFrameCount`     | `8`                   | 1–16                                                                                                           |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`           | `uniform`, `scene_aware` или пропорциональный `segment_aware`; при сбое детектора используется `uniform`       |
| `modalityBridgeVideoMaxVideos`      | `1`                   | 1–4                                                                                                            |
| `modalityBridgeVideoTimeout`        | `120000`              | 1000–120000 мс                                                                                                 |

Ранее сохранённые значения тайм-аута Video свыше 120 секунд ограничиваются
предельным сроком брокера; запись новых настроек выше этого предела отклоняется.
`GET /api/modality-bridge/video/runtime` до аутентификации или проверки среды выполнения
требует доверенного подтверждённого локального loopback-подключения, а затем — авторизации
для управления. Он возвращает только `available`, очищенные версии FFmpeg/ffprobe и фиксированную
причину недоступности среды выполнения. Внутренняя конечная точка извлечения не является
публичным API загрузки: при переполнении очереди возвращаются `503` и `Retry-After`, при отключении
вызывающей стороны — `499`, а при достижении фиксированного предельного срока брокера — `504`. В преобразованные ответы
в центральный заголовок `x-omniroute-modality-bridge` добавляется
`video->text;model=<visionModel>;parts=<videos>` без удаления сегментов Vision или Audio.

### Маскировщик PII (`piiMasker.ts`)

Выполняется на **обоих** этапах.

- **`preCall`** клонирует полезную нагрузку, обходит `system`, `messages`, `input` и
  `prompt` (включая элементы, являющиеся обычными строками) и применяет `processPII()` (из
  `@/shared/utils/inputSanitizer`) к строковым полям `content`/`text`. Когда
  `PII_REDACTION_ENABLED=true`, обнаруженные PII редактируются в исходящей
  полезной нагрузке. Это не зависит от `INPUT_SANITIZER_MODE` (который управляет только
  политикой защиты от инъекций в запросы). Когда редактирование отключено, вызов записывает количество
  обнаружений, не изменяя содержимое.
- **`postCall`** выполняет глубокое клонирование ответа, запускает `sanitizePIIResponse()`, а также
  маскировщик структуры Responses API (`maskResponsesOutput` — охватывает
  `output_text` и `output[].content[].text`). Если выполнено хотя бы одно редактирование,
  изменённый ответ заменяет исходный.

Защитный механизм никогда не блокирует данные; он только добавляет аннотации (`meta.detections`,
`meta.redacted`) или изменяет содержимое.

### Инъекция в запрос (`promptInjection.ts`)

Обнаруживает вредоносные структуры в пользовательском содержимом и применяет
настроенную политику. Поведение определяется переменными среды и параметрами
конструктора:

| Настройка        | Переменная окружения                                                                                        | Значение по умолчанию | Эффект                                                                                                                                                                                                                   |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Включение        | `INPUT_SANITIZER_ENABLED`                                                                                   | `true`                | При значении `false` защитный механизм немедленно завершает обработку.                                                                                                                                                   |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                             | `warn`                | Политика обработки инъекций: `block`, `warn` или `log`. (`redact` поддерживается для обратной совместимости, но **не** удаляет текст инъекции; перезапись PII в запросе управляется параметром `PII_REDACTION_ENABLED`.) |
| Порог блокировки | параметр `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдоним `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`                | Минимальная степень серьёзности, необходимая для блокировки. При значении по умолчанию средняя степень только отслеживается.                                                                                             |

**Приоритет режима** (`getMode`): переданный вызывающей стороной `options.mode` →
**переопределение флагом функции из БД** для `INJECTION_GUARD_MODE` (Панель управления → Настройки →
Флаги функций) → переменная окружения `INJECTION_GUARD_MODE` → переменная окружения `INPUT_SANITIZER_MODE` →
`warn`. Таким образом, переопределение на панели управления имеет приоритет над переменными окружения, поэтому
интерфейс «Флаги функций» управляет работающим защитным механизмом в реальном времени (без перезапуска). Чтение
из БД отказоустойчиво: при возникновении ошибки защитный механизм возвращается к поведению на основе переменных
окружения, а если переопределение не задано, поведение совпадает с разрешением только через переменные окружения.

Источники обнаружения:

1. `sanitizeRequest()` из `@/shared/utils/inputSanitizer` (общий набор детекторов,
   используемый в других частях конвейера).
2. Встроенные `DEFAULT_GUARD_PATTERNS` (в настоящее время `system_override_inline` и
   `markdown_system_block`, оба со степенью серьёзности `high`).
3. Необязательные `customPatterns`, передаваемые через параметры конструктора (строки, регулярные выражения
   или записи `{ name, pattern, severity }`).

Когда `mode === "block"` **и** хотя бы одно обнаружение соответствует порогу
серьёзности, `preCall` возвращает `{ block: true, message: "Request rejected:
suspicious content detected" }`. В режимах `warn`/`log` защитный механизм записывает событие в журнал, но
разрешает вызов. Общая вспомогательная функция `evaluatePromptInjection()` также экспортируется
для вызывающих сторон, которым необходимо оценивать промпты без использования реестра.

**Ограничение сканирования (v3.8.20):** детектор проверяет только **первые 16 КБ**
объединённого текста промпта — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байта) в
`src/shared/utils/inputSanitizer.ts`. И `detectInjection()`, и
`evaluatePromptInjection()` выполняют `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском
цикла по шаблонам. Директивы инъекции располагаются ближе к началу входных данных, поэтому это
ограничивает нагрузку регулярных выражений на ЦП и сборщик мусора при обработке полезных нагрузок размером
в несколько сотен КБ, не ослабляя обнаружение (см.
#3932, #4041).

### Маскирование учётных данных (`credentialMasker.ts`)

Выполняется на **обоих** этапах и последним в стандартной цепочке (приоритет `95`). Скрывает
известные шаблоны API-ключей и секретных токенов в исходящей полезной нагрузке (содержимом
сообщений, аргументах вызовов инструментов и результатах инструментов), **а также** в ответе провайдера, чтобы
учётные данные, вставленные в промпт (или возвращённые в результате работы инструмента), не утекли
вышестоящему провайдеру или обратно клиенту.

- **Только явное включение**, по тому же принципу, что и скрытие PII (смежно с жёстким правилом № 20):
  отключено, если только `settings.credentialRedactionEnabled === true` **или**
  `CREDENTIAL_REDACTION_ENABLED=true`. Если функция отключена, защитный механизм ничего не делает —
  он никогда не блокирует и не перезаписывает данные.
- `redactCredentials()` обходит всё дерево полезной нагрузки/ответа (`walkValue()`;
  с защитой от загрязнения прототипа и циклов посредством `WeakSet`) и заменяет совпадения
  заполнителем `[REDACTED:<type>]`, клонируя только те ветви, которые фактически
  изменились.
- `CREDENTIAL_PATTERNS` охватывает ключи провайдеров LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токены VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платёжные ключи (Stripe, Square), облачные
  ключи (ключ доступа AWS, Twilio, SendGrid, Mailgun), закрытые ключи/JWT,
  строки подключения с учётными данными (`mongodb://user:pass@...` и т. п.), а также
  универсальный шаблон значений заголовков `Authorization`/`x-api-key`/`api-key`/`apikey`.
  Ключи, имеющие форму заголовков (`authorization`, `x-api-key`, `api-key`,
  `apikey`), скрываются структурно (только значение, с сохранением префикса схемы, например
  `Bearer `/`Basic `), а не с помощью универсального текстового регулярного выражения.
- Защитный механизм никогда не блокирует; он только перезаписывает (`modifiedPayload` /
  `modifiedResponse`) и добавляет аннотации (`meta.credentialsRedacted`, `meta.count`).

Защита от регрессий: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовый контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true прерывает цепочку
  message?: string; // отображается при блокировке
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // возвращается preCall для изменения запроса
  modifiedResponse?: TValue; // возвращается postCall для изменения ответа
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Ограничитель сигнализирует об «отсутствии изменений», возвращая `void`, `{}` или
`{ block: false }`. Возврат `modifiedPayload`/`modifiedResponse` заменяет
значение, передаваемое по цепочке последующим ограничителям.
`signal?: AbortSignal` передаёт жизненный цикл вызывающей стороны в ограничители. Прерывание запроса — это преднамеренное исключение из принципа fail-open: мосты для медиаданных прекращают работу и выполняют очистку, не восстанавливая исходные медиаданные для целевой системы, которая заведомо их не поддерживает.

## Реестр (`registry.ts`)

Одиночка `guardrailRegistry` предоставляет:

- `register(guardrail)` — добавляет ограничитель (или заменяет его по нормализованному имени) и
  повторно сортирует ограничители по `priority` в порядке возрастания.
- `clear()` / `list()` — вспомогательные административные методы.
- `runPreCallHooks(payload, context)` — перебирает активные ограничители, передаёт
  полезную нагрузку через `modifiedPayload` и останавливается при первом `block: true`.
- `runPostCallHooks(response, context)` — выполняет тот же процесс для ответа.
- `resetGuardrailsForTests({ registerDefaults })` — очищает состояние и при необходимости
  повторно регистрирует ограничители по умолчанию для полной изоляции тестов.

Оба обработчика возвращают `{ blocked, payload|response, results, guardrail?, message? }`,
где `results` — массив записей `GuardrailExecutionResult`, включающих поля
`blocked`, `skipped`, `modified`, `error` и `meta` для каждого ограничителя,
что удобно для трассировки.

### Отключение ограничителей для отдельных запросов

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` формирует
дедуплицированный список имён ограничителей, которые должны быть пропущены для текущего
запроса. Источники (все необязательны и объединяются):

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` в теле запроса (на верхнем уровне)
- `metadata.disabledGuardrails` в теле запроса
- Заголовок `x-omniroute-disabled-guardrails` (или устаревший
  `x-disabled-guardrails`)

Значения могут быть массивами строк или строкой с элементами, разделёнными запятыми; имена
нормализуются в нижний регистр в формате kebab-case (`pii_masker` → `pii-masker`). Результат
передаётся реестру через `context.disabledGuardrails`, после чего реестр пропускает
соответствующие ограничители (`skipped: true` в `results`).

## Порядок выполнения

Для каждого запроса, проходящего через `src/sse/handlers/chat.ts` и
`open-sse/handlers/chatCore.ts`:

1. `resolveDisabledGuardrails(...)` формирует список пропускаемых защитных механизмов на основе API-ключа, тела запроса
   и заголовков.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` запускает защитные механизмы в порядке возрастания
   приоритета:
   - Отключённые защитные механизмы записываются как `skipped`.
   - Метод `preCall` каждого защитного механизма может изменить полезную нагрузку через `modifiedPayload`.
   - Первый результат `block: true` прерывает цепочку, после чего обработчик возвращает
     ответ об отклонении запроса защитным механизмом.
3. Полезная нагрузка (возможно, изменённая) передаётся в комбинированную маршрутизацию и отправляется
   вышестоящему сервису.
4. После формирования ответа `guardrailRegistry.runPostCallHooks(...)`
   запускает ту же цепочку для ответа. В этом случае `block: true` отбрасывает ответ
   вышестоящего сервиса.

Защитные механизмы, генерирующие исключения, записываются с `error: <message>`, а сообщения о них регистрируются через
`logger.warn`, однако выполнение цепочки продолжается — по умолчанию используется принцип fail-open.

## Конфигурация

Переменные среды, используемые встроенными защитными механизмами:

| Переменная                            | Используется в                | Эффект                                                                                                           |
| ------------------------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`            | Установите значение `false`, чтобы полностью отключить обнаружение.                                              |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`            | Политика обработки инъекций: `warn`, `block` или `log`. Устаревшее значение `redact` не изменяет текст инъекции. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`            | Режим защиты от инъекций; также флаг функции в БД, который **переопределяет** переменные среды (БД > ENV).       |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`            | Минимальная серьёзность, отклоняемая при `MODE=block`: `high` (по умолчанию), `medium` или `low`.                |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`            | Устаревший псевдоним для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                      |
| `PII_REDACTION_ENABLED`               | `pii-masker`                  | При значении `true` персональные данные в запросе редактируются (независимо от режима обработки инъекций).       |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ниже по потоку) | Управляет поведением маскировщика на стороне ответа.                                                             |

Защитные механизмы Modality Bridge считывают конфигурацию времени выполнения из хранилища
настроек на основе БД (`getSettings()`), а не из переменных среды. Основные ключи для изображений:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и
`modalityBridgeCacheMaxEntries`. Устаревшие ключи
`visionBridge*` принимаются только как документированный резервный вариант чтения на один цикл;
панель управления записывает основные ключи. Значения по умолчанию и логика выбора резервного
варианта находятся в `src/shared/constants/modalityBridgeDefaults.ts`, а устаревшие
константы сохранены в `src/shared/constants/visionBridgeDefaults.ts`.

Для аудио используются `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` и `modalityBridgeAudioMaxClips`, а также общие
настройки `modalityBridgeCache*`. Для аудио нет резервного варианта с устаревшими ключами, поскольку эти
ключи были введены вместе со схемой Modality Bridge.

Для видео используются `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` и
`modalityBridgeVideoTimeout`, а также общие настройки `modalityBridgeCache*`.
По умолчанию эта функция отключена, поскольку FFmpeg/ffprobe являются необязательными эксплуатационными
зависимостями, а создание описаний кадров увеличивает задержку и стоимость использования модели.

## Пользовательские защитные механизмы

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Шаги:

1. Создайте `src/lib/guardrails/myGuardrail.ts`, расширяющий `BaseGuardrail`.
2. Реализуйте `preCall` и/или `postCall`.
3. Зарегистрируйте при импорте (добавив в `registerDefaultGuardrails`) либо
   вызовите `guardrailRegistry.register(...)` во время выполнения — реестр заменяет
   любой ранее зарегистрированный защитный механизм с тем же нормализованным именем.
4. Добавьте тесты в `tests/unit/` (существующие примеры:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## Тестирование

Используйте `resetGuardrailsForTests()` между тестами, чтобы начинать с известного состояния.
Передайте `{ registerDefaults: false }`, чтобы начать с пустого реестра и
зарегистрировать только тестируемые защитные механизмы. Vision Bridge поддерживает внедрение
зависимостей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge предоставляет
аналогичные точки расширения для настроек, возможностей, выбора модели STT, проверки
учётных данных и транскрипции. Поэтому тесты могут проверять оба потока без доступа
к БД или сети.

## Покрытие маршрутов защитой от инъекций и red-team-тестирование (этап 8 · блок D)

Защита от инъекций (`createInjectionGuard` / `withInjectionGuard`) охватывает все маршруты,
принимающие пользовательские промпты. Она учитывает `INJECTION_GUARD_MODE` (по умолчанию `warn` = только журналирование;
`block` = возвращает HTTP 400 `SECURITY_001`).

| Тип               | Маршруты                                                                                                                                             | Режим по умолчанию |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| Текст (имеющиеся) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn               |
| Генеративные      | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn               |
| Данные            | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn               |

Извлечение текста (`extractMessageContents`) охватывает `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team-тестирование (еженочно, `nightly-llm-security.yml`):** promptfoo проверяет, что каждый маршрут блокирует
корпус OWASP-LLM в режиме `INJECTION_GUARD_MODE=block`; garak запускает проверки (пропускаются при отсутствии секрета).
`moderations` включён для единообразия — операторы в режиме блокировки могут исключить его через
`resolveDisabledGuardrails`.

Еженочный рабочий процесс (`.github/workflows/nightly-llm-security.yml`, cron + ручной
запуск) содержит две задачи:

- **`promptfoo-guard` (блокирующая)** — запускает `promptfoo eval -c promptfooconfig.yaml`
  с `INJECTION_GUARD_MODE=block`. Каждый состязательный случай (например, «игнорируй все
  предыдущие инструкции…», джейлбрейки в стиле DAN) проверяет, что ответ содержит
  `error.code === "SECURITY_001"`, то есть защита действительно отклонила запрос.
- **`garak` (рекомендательная)** — запускает garak с `--probes promptinject,dan,leakreplay`
  для локального экземпляра OmniRoute (`http://localhost:20128/v1`). Запуск зависит от наличия
  секрета провайдера (`PROMPTFOO_PROVIDER_KEY`); при его отсутствии задача корректно пропускается, а команда дополнена
  `|| true`, поэтому она формирует отчёт, не вызывая сбой CI.

Покрытие вспомогательного средства защиты (`createInjectionGuard` / `withInjectionGuard`)
распространяется на каждый маршрут `/v1`, принимающий промпты; текст промпта извлекается из
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` функцией
`extractMessageContents()` в `src/shared/utils/inputSanitizer.ts`.
