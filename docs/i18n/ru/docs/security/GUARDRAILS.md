> **Последнее обновление:** 2026-08-29 — v3.8.51 (Происхождение стенограммы Video Bridge объявляется вызывающей стороной,
> еще не проверено сервером — уточнено согласно #11661)

Защитные механизмы (guardrails) обеспечивают безопасность, соблюдение политик и преобразования контента на границе между OmniRoute и вышестоящими провайдерами. Каждый защитный механизм может проверять (и опционально отклонять, преобразовывать или аннотировать) полезные данные запросов (`preCall`) и ответы вышестоящих систем (`postCall`).

Система является **открытой при сбое (fail-open)**: если защитный механизм выдает ошибку во время выполнения, реестр записывает ошибку и продолжает работу со следующим защитным механизмом, вместо того чтобы отклонять запрос. Блокировка — это явное решение (`block: true`), а не случайность.

## Встроенные защитные механизмы

Реестр автоматически загружает шесть защитных механизмов в порядке приоритета при импорте (см. `registry.ts` → `registerDefaultGuardrails()`):

| Приоритет | Имя                 | Этап(ы)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Меньшие номера приоритета выполняются **первыми**.

### Vision Bridge (`visionBridge.ts`) — Мост модальностей PR-1

Перехватывает запросы, содержащие изображения, предназначенные для **моделей без поддержки зрения**, и либо перенаправляет весь запрос на модель с поддержкой зрения, либо заменяет части изображений текстовыми описаниями, созданными настраиваемой моделью зрения, перед вызовом вышестоящей системы. Это позволяет текстовым провайдерам прозрачно обрабатывать мультимодальные полезные данные.

Порядок выполнения:

1. Пропустить, если целевая модель уже поддерживает зрение (если только она не указана в списке принудительного моста `isVisionBridgeForcedModel`).
2. Извлечь части изображений с помощью `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), который делегирует задачу **унифицированному детектору медиа**
   `detectMediaParts()` в `open-sse/utils/mediaParts.ts` — единственному источнику истины,
   используемому совместно с фильтром совместимости комбинаций.
   Извлечение разрешено для частей верхнего уровня форм, которые
   `replaceImageParts` может вставить обратно (контракт извлечения↔замены): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` и Responses API `input_image`. Вложенные совпадения и
   формы, содержащие только индикаторы, являются материалом для комбинированного фильтра и никогда не извлекаются.
   Пропустить, если ничего не найдено.
3. Разрешить конфигурацию времени выполнения с помощью `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): новые ключи настроек `modalityBridge*`
   имеют приоритет; устаревшие ключи `visionBridge*` остаются **одноцикловым резервом**
   (окно отката). Пропустить перед любым обходом медиа, если мост отключен.
4. Селектор режима (`modalityBridgeVisionMode`, см. таблицу ниже) решает,
   перенаправлять или описывать. Перенаправление возвращает `modifiedPayload`
   только с замененной `model`, плюс метаданные `{ rerouted, fromModel, toModel, imagesKept }`.
5. Путь описания: ограничить количество изображений до `maxImages`, составить
   подсказку, учитывающую задачу, обратиться к кэшу описаний, вызвать модель зрения
   **параллельно** (`Promise.allSettled`) и вставить текстовые части
   `[Image N]: <description>` на их место. Неудачное описание возвращает `null`,
   и исходная часть изображения **сохраняется** (#4012) — за исключением
   пути комбинированного описания, когда каждое описание завершилось неудачей,
   в этом случае подтвержденная вышестоящая система без поддержки зрения
   получает заглушку `(unavailable — no vision-capable provider connected)` вместо этого (#8430).
6. Вернуть `modifiedPayload` + метаданные (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режима (`modalityBridgeVisionMode`)

| Режим      | По умолчанию | Поведение                                                                                                                                                                                                                                                                                                                      |
| ---------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔            | Устаревшая эвристика, без изменений (#6640/#7204): модели без комбинаций/`auto/` перенаправляются на лучшую модель зрения, если только исходная модель уже не имеет пригодных учетных данных (тогда описывается); комбинированные цели всегда описываются.                                                                     |
| `describe` |              | Всегда описывать — блок перенаправления полностью пропускается; выбранная пользователем модель всегда отвечает.                                                                                                                                                                                                                |
| `reroute`  |              | Принудительное перенаправление: обход защитного механизма сохранения учетных данных модели. Защитный механизм учетных данных **цели** перенаправления по-прежнему применяется — если нет доступной цели зрения, запрос переходит к описанию, чтобы необработанные изображения никогда не достигали текстового бэкенда (#8430). |

Принудительные режимы выполняются **до** запуска автоматической эвристики; поведение `auto`
идентично побайтно защитному механизму до PR-1.

#### Подсказка для описания с учетом задачи (`modalityBridgeVisionTaskAware`)

По умолчанию **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) добавляет
текст **последнего сообщения пользователя** (обрезанный до 500 символов) к базовой
подсказке описания, направляя описание к тому, что пользователь фактически
спросил (шаблон codex-vision-proxy), и просит модель зрения транскрибировать видимый
текст. Если флаг отключен — или нет пользовательского текста — базовая подсказка
используется без изменений.

Собственный запрос самоцикла описания, совместимый с OpenAI (`callVisionModelSingle()` в `visionBridgeHelpers.ts`), всегда запрашивает `image_url.detail: "high"` — безусловно, для каждого вызывающего/провайдера, без привязки к какому-либо клиентскому сигналу. Сэмплирование с низкой детализацией ухудшает точность OCR именно для задачи транскрипции текста, которую запрашивает этот промпт, поэтому сам вызов описания всегда запрашивает высокую детализацию, независимо от того, какой уровень детализации использовался в исходном входящем запросе. Это влияет только на внутреннее тело запроса описания; это не меняет того, как OmniRoute пересылает собственный `image_url.detail` вызывающего абонента в основном запросе — это значение по умолчанию применяется отдельно и только для обнаруженных клиентов OpenCode в `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). В ветви Anthropic wire-format самоцикла описания нет поля `detail`, и на нее не влияют никакие значения по умолчанию.

#### Ограничение вывода описания (`modalityBridgeVisionMaxChars`)

| Ключ                           | По умолчанию | Диапазон          |
| :----------------------------- | :----------- | :---------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` или 100–50000 |

`0` (по умолчанию) означает **без ограничения** — описание, возвращаемое `callVisionModel()`, передается без изменений, сохраняя существующее поведение. Любое значение в диапазоне 100–50000 усекает описание с суффиксом `…` перед тем, как оно будет вставлено обратно как `[Image N]: <description>` (`VisionBridgeGuardrail.preCall()` в `src/lib/guardrails/visionBridge.ts`). Увеличьте это значение для задач OCR, требующих высокой детализации, где нижестоящей модели нужна полная транскрипция; уменьшите его, чтобы ограничить использование токенов в многословных моделях зрения. Поле на панели управления находится на вкладке Vision, в разделе Advanced (`modality-bridge-max-chars` в `ModalityBridgeVisionTab.tsx`) и прижимает любое значение от 1 до 99 к нижней границе 100, оставляя явный `0` нетронутым — `0` является допустимым значением Zod сам по себе (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто "неустановленным" значением по умолчанию.

#### Кэш описания (`modalityBridge/bridgeCache.ts`)

Кэш LRU + TTL в памяти для результатов описания, общий для всего процесса.
Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` с кадрированием по длине префикса (без коллизий границ полей). Компонент модели — это **сконфигурированная** модель моста, а не модель, которая фактически ответила — `callVisionModel` может внутренне использовать резервные варианты, и кэширование по каждой попытке фрагментировало бы кэш. Неудачные описания никогда не кэшируются. Настройки:

| Ключ                            | По умолчанию | Диапазон |
| :------------------------------ | :----------- | :------- |
| `modalityBridgeCacheEnabled`    | `true`       | —        |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000  |

#### Нормализация удаленных изображений (самоцикл описания/получение base64)

Когда мост сам получает **удаленное** изображение — самовызов описания Anthropic и преобразование base64 в формате claude-wire-format (`ensureBase64ImagesForClaudeWire`), оба через `fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts` — полученный URI данных передается через `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) перед встраиванием в запрос модели зрения. Слишком большие изображения уменьшаются до **длинной стороны в 2048px** (что соответствует ограничению изменения размера, которое OpenAI/Anthropic уже применяют на стороне сервера), что сокращает объем загружаемых байтов/задержку без изменения того, что видит модель зрения. Изменение размера использует `sharp`, загружаемый через динамический импорт: на платформе, где его нативный бинарный файл не загружается, `normalizeDataUri()` **никогда не выбрасывает исключение** — он возвращается к сквозной передаче исходных байтов, поэтому путь описания/преобразования base64 всегда продолжает работать. Неизобразительные байты (запрос, который не вернул декодируемое изображение) также передаются без изменений. Эта нормализация применяется только к изображениям, которые мост получает для своего собственного самовызова — она никогда не применяется к необработанной полезной нагрузке вызывающего абонента, что соответствует принципу мутации только по выбору (Жесткое правило #20).

#### Схема настроек + миграция

Новые ключи `modalityBridge*` проверяются Zod в `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, трио `modalityBridgeCache*` и группа `modalityBridgeAudio*`, используемая Audio Bridge. Миграция `141_modality_bridge_settings.sql` копирует существующие устаревшие значения `visionBridge*` в соответствующие новые ключи (идемпотентно, никогда не перезаписывает значение `modalityBridge*`, установленное оператором); устаревшие ключи остаются принятыми в качестве резервного варианта чтения в течение одного цикла выпуска.

#### Заголовок прозрачности + статистика

Ответы, преобразованные описанием, содержат `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (создается `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`, помечается `withModalityBridgeHeader()` в `src/sse/handlers/chatHelpers.ts`). Перенаправленные запросы **не** получают заголовок — полезная нагрузка не была изменена, и замена модели уже видна в поле `model` тела ответа.

`GET /api/modality-bridge/stats` (управление аутентификацией, тот же уровень, что и `GET /api/settings`) возвращает счетчики в памяти для каждой модальности `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` и `video`. `averageLatencyMs` использует `latencySamples`, а не все попытки, в качестве знаменателя; операция без измерения времени не создает выборку с нулевой миллисекундой. `bridged` остается обратно совместимым псевдонимом для успешных преобразований; неудачные попытки не увеличивают его. Счетчики сбрасываются при перезапуске процесса по замыслу (телеметрия, а не учет).

#### Конфигурация панели управления

Специальная страница панели управления — `/dashboard/settings/modality-bridge`. Ее URL-адресуемые вкладки `Vision`, `Audio` и `Video` сохраняют параметры запроса при переключении значения `tab`. Вкладка Vision предоставляет функции включения, выбора режима и модели (включая автоматический по умолчанию), подсказки с учетом задачи, расширенные лимиты по таймауту/изображению/длине описания/кэшу, счетчики времени выполнения и защищенный пример запроса. Вкладка Audio также активна: она предоставляет функции включения, выбор модели только для STT с опцией Auto, лимиты по таймауту/максимальной длине клипа, аудиосчетчики и тестовый пример `input_audio`. Вкладка Video функциональна: она сообщает о состоянии выполнения FFmpeg/ffprobe — одном из четырех явных состояний пользовательского интерфейса (`unknown`, пока зонд выполняется или не может завершиться; `restricted` на хосте панели управления, не являющемся loopback, где зондирование пропускается на стороне клиента; `unavailable` после зондирования и подтверждения отсутствия; или `available` с версиями FFmpeg/ffprobe) — сохраняет лимиты включения/модели/кадра/видео/таймаута, фильтрует выбор модели до моделей, поддерживающих зрение, и предоставляет видеосчетчики.

Прежняя карточка Vision Bridge в настройках ИИ является ссылкой совместимости на новую страницу; она больше не содержит второй копии формы. Поставщики медиа также связывают рабочие процессы Image-to-Text и Speech-to-Text с соответствующими вкладками Modality Bridge, не удаляя существующую песочницу Speech-to-Text.

**Обход проверки доступа для самозацикливания:** когда вызов describe маршрутизируется через собственный самозацикливающийся `/v1` OmniRoute (нестандартная модель провайдера), подзапрос отправляет `x-omniroute-admission-bypass: internal` и аутентифицируется с помощью разрешенных учетных данных самозацикливания — локального `sk_omniroute` в локальном режиме или настроенного оператором ключа среды `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), чтобы развертывания с `REQUIRE_API_KEY=true` могли по-прежнему выполнять вызов describe. Обход учитывается только для этих точных учетных данных, поэтому внешние клиенты не могут использовать заголовок для пропуска проверки доступа.

Устаревшие значения по умолчанию находятся в `src/shared/constants/visionBridgeDefaults.ts`; новые значения по умолчанию для режима/учета задач/кэша и резолвер настроек находятся в `src/shared/constants/modalityBridgeDefaults.ts`. Защитный механизм предоставляет опцию конструктора `deps`, чтобы тесты могли внедрять фиктивные реализации `getSettings` и `callVisionModel`.

### Аудиомост (`audioBridge.ts`) — Modality Bridge PR-3

Перехватывает чат-запросы, содержащие аудио, прежде чем они достигнут цели, которая, как известно, не принимает аудиовход. Он никогда не перенаправляет чат-запрос: аудиочасти транскрибируются через существующую многокомпонентную конечную точку, совместимую с OpenAI, а выбранная модель чата продолжает работу с текстовыми транскриптами.

Поток:

1.  Разрешить `supportsAudio` через `getResolvedModelCapabilities()`. Явные метаданные реестра провайдеров имеют приоритет, затем статические метаданные модели, затем синхронизированный `modalities_input`. Объявленный список входных данных без `audio` равен `false`; отсутствие доказательств возможности остается `null`. И `false`, и `null` активируют консервативный мост, тогда как `true` обходит его.
2.  Разрешить настройки `modalityBridgeAudio*` и извлечь подлежащие вставке аудиочасти верхнего уровня из каждого сообщения с помощью общего детектора `detectMediaParts()`. Поддерживаемые форматы данных: OpenAI `input_audio`, `audio_url` и `source.media_type: "audio/*"`. Вложенное аудио обнаруживается для маршрутизации, но не удаляется путем вставки. Работа ограничена `modalityBridgeAudioMaxClips`; последующие части остаются нетронутыми.
3.  Учитывать настроенный `provider/model` или позволить `selectAudioBridgeModel()` пройти по `AUDIO_TRANSCRIPTION_PROVIDERS` в стабильном порядке каталога и выбрать первую модель с пригодными активными учетными данными провайдера.
4.  `callAudioTranscription()` преобразует аудио в формате base64/data-URI в многокомпонентный `file` или загружает удаленный `audio_url` через исходящий защитный механизм только для публичного доступа с привязкой DNS и ограничением в 25 МБ. Затем он отправляет файл и выбранную модель POST-запросом на локальный самозацикливающийся `/v1/audio/transcriptions`, аутентифицированный с помощью `resolveSelfLoopBearer()`. Существующий маршрут транскрипции выполняет обычный поиск учетных данных, обработку задержек/ограничений скорости и диспетчеризацию провайдера.
5.  Успешные вызовы заменяют свои части на `[Audio N]: <transcript>`. Вызовы выполняются с `Promise.allSettled`: индивидуальный сбой сохраняет исходную аудиочасть (контракт #4012). Если каждый вызов завершается неудачей и цель доказана как `supportsAudio === false`, части становятся `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430). Для неизвестной цели (`null`) результат всех сбоев остается нетронутым. Доказанная текстовая цель без пригодных учетных данных STT получает тот же явный заглушку без выполнения сетевого вызова.

Успешные транскрипты используют кэш LRU/TTL Modality Bridge в рамках всего процесса. Ключ объединяет ссылку на аудио, стабильную метку операции `audio-transcription` и выбранную модель STT; сбои никогда не кэшируются. Попытки аудио обновляют общие счетчики `bridged`, `cacheHits`, `failures` и `lastUsedAt`. Преобразованные ответы содержат `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; нетронутые запросы не получают сегмент Audio Bridge.

Настройки времени выполнения хранятся в БД и валидируются Zod:

| Key                           | Default | Range          |
| ----------------------------- | ------- | -------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —              |
| `modalityBridgeAudioModel`    | `""`    | Auto or STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000    |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10           |

Общий кэш по-прежнему контролируется параметрами `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и `modalityBridgeCacheMaxEntries`.

### Видеомост (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехватывает видеофрагменты верхнего уровня в `messages` Chat Completions и `input` Responses API до вызова целевого объекта без известной нативной поддержки видео. Поддерживаемые форматы: `input_video`, `video_url`, `video_source`, HTTPS URL и URI данных `data:video/*;base64,...`. Обычные имена файлов в тексте не рассматриваются как видео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) отвечает за обход запросов, проверку возможностей/политик, агрегацию по запросам и полезную нагрузку ответа. Работа с каждым видео — получение, кэш полных результатов, описание последовательности кадров (которая объединяет любую объявленную вызывающей стороной аудиозапись) и метрики/прерывание/очистка для каждой попытки — скрыта за `processVideoPart` в `videoBridgePipeline.ts`, вызываемым один раз для каждой части видео внутри цикла `preCall`. Этот модуль также определяет явные границы портов: `VideoMediaBrokerPort` (получение байтов и извлечение дискретизированных кадров), `VideoAudioTranscriptionPort` (объединение объявленной вызывающей стороной аудиозаписи с дискретизированными субтитрами) и `VideoDrilldownPort` (граница сохранения детализации кадров; пока не подключен к `processVideoPart` — только отдельный маршрут `/api/modality-bridge/video/drilldown` записывает записи детализации сегодня).

Публичный путь запроса `/v1` никогда не импортирует и не вызывает подпроцесс. Удаленные видео загружаются с ограничением в 50 МиБ; встроенные видео base64 имеют консервативное ограничение в 36 МиБ декодированного видео на каждое видео, чтобы модель/сообщения/оболочка кадрирования могли оставаться в пределах публичного лимита приема JSON-запросов в 50 МиБ. Оценки встроенной длины и декодированного размера проверяются перед выделением памяти. HTTPS требуется для исходного удаленного URL и каждого перенаправления, с использованием существующей публичной исходящей защиты с привязкой DNS. Затем байты пересекают точную внутреннюю границу брокера `POST /api/modality-bridge/video/extract`. Этот маршрут является одновременно `LOCAL_ONLY` и `SPAWN_CAPABLE`, принимает только аутентифицированный, доверенный запрос обратной связи для каждого процесса и никогда не принимает URL, путь файловой системы, исполняемый файл или список аргументов. Конвейер ограничения размера тела API и инкрементальный считыватель тела обработчика независимо обеспечивают ограничение входных данных брокера в 50 МиБ. Его ограниченная очередь выполняет одно извлечение за раз, допускает четыре ожидающие задачи и ограничивает ожидающие входные данные 100 МиБ.

Внутри брокера `ffprobe` читает приватный локальный файл; фиксированный список разрешенных форматов исключает форматы плейлистов и манифестов. Для разрешенных контейнеров семейства MOV внешние ссылки на данные MOV остаются отключенными по умолчанию, и фиксированная команда не включает их. И `ffprobe`, и `ffmpeg` используют белый список протоколов только для `file`, один поток, фиксированные массивы аргументов, без оболочки и исполняемые файлы, разрешаемые из `PATH`. Потоки обложек с прикрепленными изображениями не являются кандидатами для воспроизведения. Все воспроизводимые потоки должны соответствовать ограничениям, и явный поток по умолчанию предпочтительнее детерминированного отката к наименьшему индексу. Видео ограничены 600 секундами, 8192 пикселями на измерение и 33 554 432 исходными пикселями. FFmpeg выбирает 1–16 срединных JPEG-кадров, уменьшает длинную сторону до максимум 1024 пикселей без увеличения меньших входных данных и никогда не получает URL. Выборка по умолчанию `uniform`. Дополнительные политики `scene_aware` (с учетом сцен) и экспериментальная `segment_aware` (с учетом сегментов) выполняют один дополнительный фиксированный проход FFmpeg по уже проверенному локальному потоку, выбирают ограниченные временные метки сцен `showinfo` и детерминированно возвращаются к тем же равномерным срединным точкам при сбое детектора, тайм-ауте, некорректном выводе или пустом наборе кандидатов. Режим с учетом сегментов распределяет срединные выборки пропорционально проверенным интервалам сцен; доказательства с учетом сегментов и поведение при откате подробно описаны ниже. Жесткое ограничение в 16 кадров применяется после выбора в каждой политике. Когда запрос с учетом сцен имеет бюджет только в один кадр, он использует равномерную срединную точку активного полного видео или окна фокусировки и сообщает `policyEffective: uniform`: один выбранный кадр сцены не может сохранить оба временных конца. Вызывающая сторона может опционально предоставить конечное окно фокусировки (`start`/`end` секунд); границы привязываются к длительности медиа, обратные или бесконечные окна отклоняются, и все политики выборки выполняются только внутри нормализованного интервала. Полученное окно включается в метаданные выборки и в ненадежный префикс описания, чтобы нижестоящие модели могли отличить сфокусированный отрывок от полной временной шкалы.

Семантическая фокусировка субтитров — это отдельная, явная настройка. Режим анализа по умолчанию `full` сохраняет существующий запрос кадра и никогда не пересылает текст запроса модели субтитров. В режиме `focused` мост считывает только последний непустой текст `text`/`input_text`, созданный пользователем, из того же контейнера Chat или Responses, нормализует его до NFC, сворачивает управляющие символы и пробелы и ограничивает его 500 кодовыми точками Unicode. Пустой результат возвращается к точному запросу `full`. Используемая подсказка сериализуется как JSON в выделенном блоке контекста ненадежного пользователя и может только приоритизировать наблюдаемые детали; она не может отменить отдельное предупреждение о следовании инструкциям, видимым или слышимым в медиа. Текстовая фокусировка никогда не выводит `start`/`end` или не изменяет временной сэмплер.

#### FU-07 доказательства структурных сегментов

`segment_aware` использует один ограниченный проход предварительного анализа по уже проверенному локальному видеопотоку. Фиксированная цепочка фильтров сначала масштабирует изображение до максимум 320 пикселей в ширину, обнаруживает изменения сцен и замороженные интервалы, затем производит выборку с частотой 1 кадр в секунду для определения размытия, средней яркости и пространственно-временной информации. Проход ограничен 600 структурными выборками, одним потоком FFmpeg/фильтра, теми же списками разрешенных протоколов и контейнеров только для `file`, ограничением вывода процесса в 1 МиБ и максимум 30 секундами внутри общего прерывания/дедлайна брокера. Он никогда не принимает команду, фильтр, путь или URL из запроса.

Структурные значения представляют собой детерминированные данные выборки, а не семантическое понимание видео. Они не выводят субъекты, действия, подписи, речь или намерения пользователя. Границы сцен и стоп-кадров образуют сегменты; охват стоп-кадров, размытие, экспозиция, пространственная детализация и временные изменения влияют только на то, как распределяется существующий бюджет в 1–16 кадров. Полностью замороженный сегмент ограничен одним кадром, в то время как незамороженные сегменты конкурируют за оставшийся бюджет. Когда количество границ превышает количество кадров, сохраняется равномерное покрытие временной шкалы, чтобы быстрые ранние склейки не могли скрыть длинный завершающий сегмент. Границы сцен в пределах 1-секундного разрешения анализа границы стоп-кадра объединяются.

Отсутствующие фильтры, некорректные/пустые данные, ошибка детектора или ограниченный тайм-аут предварительного анализа приводят к открытому сбою с применением точной политики равномерной средней точки. Прерывание вызывающей стороной или истечение срока брокера не приводит к открытому сбою: это завершает выполняющийся подпроцесс, предотвращает последующее извлечение кадров, а частное временное дерево удаляется в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерирует детерминированные реальные фикстуры FFmpeg для экономии вызовов подписей после дедупликации, распределения бюджета плотного движения, данных о размытии/экспозиции/SI-TI, быстрых склеек с длинным хвостом и ложных срабатываний при постепенном затухании. Он записывает реальное время до анализа и, если доступен `/usr/bin/time`, загрузку ЦП дочернего процесса и пиковое значение RSS. Его проверки качества являются исключительно структурными оракулами. Качество реальной модели подписей остается в состоянии `HOLD`, поскольку этот тестовый стенд не имеет авторизованной конечной точки или фиксированного оценщика. Денежная экономия также остается в состоянии `HOLD`, если только `--caption-cost-per-call-usd` не предоставляет явную положительную оценку стоимости за вызов; скрипт никогда не фальсифицирует ни один из результатов.

Каждый кадр ограничен 4 МиБ, все необработанные кадры вместе — 23 МиБ, а сериализованный ответ брокера — 32 МиБ. Приватный временный каталог удаляется в `finally`. OmniRoute не включает FFmpeg и не принимает пользовательский путь к исполняемому файлу. Перед созданием подписей мост применяет консервативный проход визуальной дедупликации: каждый JPEG уменьшается до буфера оттенков серого 16×16 и сравнивается только с последним сохраненным кадром. Для запрошенного бюджета подписей, превышающего один кадр, извлечение предоставляет ограниченный пул кандидатов, до двух раз превышающий этот бюджет, и никогда не более 16 кадров. Запрошенное ограничение применяется только после дедупликации, при этом первый и последний выбранные кандидаты сохраняются во время окончательного прореживания, когда бюджет составляет не менее двух. Версионированная политика `grayscale-16x16-mean-cells-v2` использует большее из среднего значения дельты яркости и отношения ячеек миниатюр, чья нормализованная дельта составляет не менее 0,05. Порог дублирования составляет константу 0,04, выбранную для предсказуемости, а не вынесенную в качестве настройки времени выполнения. Этот вторичный высококонтрастный сигнал сохраняет небольшие движения и видимые изменения текста, которые может скрыть сравнение только по среднему значению. Ошибки компаратора или декодера приводят к открытому сбою и сохраняют покрытие. Выходные метаданные разделяют извлеченные кандидаты, успешно использованные кадры и отброшенные визуальные дубликаты.

Явно отмеченная часть видео может запросить контактный лист с отметками времени. Мост создает сетку JPEG размером не более 4 столбцов и 16 кадров. Каждая ячейка размером 512 пикселей записывает свою исходную отметку времени в высококонтрастную нижнюю полосу, в то время как те же отметки времени остаются в текстовых метаданных для последующей привязки и аудита. Полный JPEG остается ограниченным 32 МиБ. Если `sharp` не может декодировать или скомпоновать сетку, мост возвращается к отдельным кадрам JPEG; прерывание клиентом по-прежнему распространяется на операцию с листом.

Данные для продвижения намеренно отделены от синтетического микротеста композиции. `scripts/perf/video-bridge-contact-sheet-eval.ts` определяет тестовый стенд A/B с версионированной схемой для реальных моделей зрения, совместимых с OpenAI. Он измеряет токены, сообщаемые провайдером, сквозную задержку (включая композицию листа), количество вызовов модели и сохранение фактов, определенных манифестом. Необработанные ответы модели не записываются в отчет; сохраняются только дайджесты SHA-256 и совпадающие идентификаторы фактов. Тестовый стенд не выполняет сетевых или платных вызовов модели, если не передан `--execute-real` и не настроены `--model`, `OMNIROUTE_BASE_URL` и `OMNIROUTE_API_KEY`. Без этого явного реального запуска его машиночитаемый вердикт остается `HOLD`; одни только измерения синтетической нагрузки/количества вызовов не являются доказательством для продвижения.

Вызывающие стороны могут прикрепить необязательный массив `transcript.cues` к поддерживаемой части видео, если у них уже есть выровненный текст. Каждая метка должна содержать `text`, конечный интервал `start`/`end` внутри исследуемой длительности и разрешенный `source` (`client`, `embedded` или `audio-bridge`); `confidence` по умолчанию равен `1` и должен находиться в диапазоне от `0` до `1`. Точные дубликаты меток сворачиваются. OmniRoute никогда не начинает транскрипцию из этих метаданных: проверенные метки копируются в описанный результат с источником, достоверностью и интервалом, и отображаются как недоверенные наблюдения рядом с подписями кадров. Недействительный, выходящий за пределы диапазона или текст без указания происхождения отклоняется, а не смешивается с потоком подписей. Поле `source` в настоящее время объявляется вызывающей стороной, а не проверяется сервером: OmniRoute гарантирует, что значение является одной из трех разрешенных строк, но еще не подтверждает криптографически, что метка `embedded` или `audio-bridge` действительно получена из извлечения, принадлежащего серверу. Рассматривайте `source` как недоверенную подсказку, пока эта проверка не будет реализована; не основывайте на ней решения об авторизации.

Продвинутый вызывающий абонент может предоставить уже авторизованную дорожку `audioTranscript` для того же видео. Стык слияния обрабатывает визуальные и аудио наблюдения в рамках одного крайнего срока и сигнала прерывания, упорядочивает их на общей временной шкале, схлопывает точные дубликаты и сообщает о частичном результате, когда успешна только одна сторона. Недействительный `audioTranscript` приводит к частичному результату — визуальное описание сохраняется, а аудиоветвь записывает очищенный код ошибки — вместо того, чтобы приводить к сбою всего видео. Доступность по ветвям, флаг частичности и очищенные коды ошибок сохраняются в описанном результате, в метаданных защитного барьера (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), в метаданных кэша результатов и в счетчиках слияния моста. Путь Video Bridge по умолчанию не вызывает преобразование речи в текст и не загружает вторую копию медиа; без этой явной дорожки он остается только видео.

**Сохранение стенограммы (#12150 P1).** Это применяется автоматически всякий раз, когда Video Bridge (который сам является необязательным) отображает реплику стенограммы — отдельного флага сохранения нет. Когда запрос отображает любую реплику стенограммы (объявленную вызывающим абонентом `transcript` или объединенную `audioTranscript`), защитный барьер помечает ее как `videoBridgeObserved` и создает отредактированную тень описания видео — идентичное отображение, в котором свободный текстовый блок каждой реплики заменяется на `[redacted-video-transcript]`, созданное путем подстановки структурированного поля реплики до сборки строки (никогда не путем парсинга плоского текста, поэтому никакое содержимое реплики — вредоносное или обычное, включая блоки, содержащие `]`, такие как `[inaudible]`/`[music]` — не может сохраниться). Сохраненное тело запроса журнала вызовов заменяет каждую текстовую часть, полученную из видео, на эту отредактированную тень, сопоставляемую по равенству содержимого; якорь `fullText` повторно считывается из готовой полезной нагрузки защитного барьера перед вызовом, поэтому сопоставление по-прежнему успешно после того, как последующие цепочки защитных барьеров (маскировщики PII и учетных данных, приоритеты 10/95) перезаписывают текст описания на месте и после того, как внедрение системных подсказок/передачи/памяти изменяет массив сообщений. Тело, отправленное вышестоящему модулю, остается неизменным. Наблюдаемый запрос также не заполняет постоянную Память (пропускается как извлечение, полученное из запроса, так и из ответа), поэтому собственный ответ модели не может повторять текст стенограммы в Памяти.

Дополнительные сохраненные копии используют тот же сигнал наблюдаемого запроса. Необработанный снимок клиентского запроса до защитного барьера, находящийся в памяти ожидающий запрос и журнал рано отклоненных запросов структурно заменяют поля стенограммы в частях видео; строковые подсказки, синтезированные этапами конвейера и передачей контекста, редактируются в приемнике сохраненного тела запроса. Сохраненный маркер `video_content_removed` заставляет продолжение `previous_response_id` завершаться с ошибкой, а не восстанавливать текст, который был намеренно отброшен. Если наблюдаемый запрос теряет свою теневую копию с частичным редактированием до логирования, или даже одна из нескольких теневых копий видео не совпадает после последующих изменений запроса, сохраненное тело запроса полностью опускается вместо сохранения частично отредактированной стенограммы.

Для наблюдаемого запроса ответ модели может цитировать любую часть стенограммы без границы структурированной реплики. Его сохраненное `responseBody` журнала вызовов поэтому заменяется маркером пропуска; подробный артефакт конвейера (который может включать тела вышестоящих/клиентских систем и фрагменты потока) не сохраняется. Кэши семантики, идемпотентности и воспроизведения рассуждений обходят операции чтения и записи для этого запроса. Запрос поставщика и видимый клиенту ответ остаются неизменными. Ранние байты keepalive сбрасываются из временного буфера, когда подробный артефакт опускается. Предупреждение Kiro о некорректном EventStream сообщает только количество байтов полезной нагрузки, но никогда не ее содержимое или необработанную ошибку JSON-парсера. Это не означает, что каждый несвязанный диагностический инструмент поставщика/плагина был проверен; более широкая проверка сохраненных приемников отслеживается в #11658.

Внутренний жизненный цикл `/api/modality-bridge/video/drilldown` представляет собой отдельную подсистему кэша с обратной связью/аутентификацией по токену. Каждая операция также требует канонического непрозрачного идентификатора субъекта. Прежде чем производственный вызывающий абонент будет включен, он должен получить этот идентификатор от аутентифицированного арендатора и никогда не должен передавать значение, выбранное клиентом. Ключи кэша связывают этот субъект с каноническими идентификаторами сеанса и видеоссылки, хранят только их ключи, полученные с помощью SHA-256, и ограничивают как чтение, так и удаление тем же субъектом. Кэш хранит не более 16 производных JPEG-кадров на запись, истекает их срок действия через десять минут и поддерживает ограниченные операции чтения `start`/`end` или явное удаление сеанса.

Каждый субъект ограничен 16 записями и 64 МиБ канонических JPEG-данных. Эти ограничения не зависят от глобального потолка в 64 записи/256 МиБ: давление квоты субъекта вытесняет только наименее недавно использованные записи этого субъекта до того, как будет рассмотрено глобальное вытеснение по LRU. Истекшие записи удаляются как из учета субъекта, так и из глобального учета при активности кэша, в то время как отмена и сбой валидации не приводят к частичной замене.

Кэш отклоняет неканонический Base64, избыточное заполнение, не-JPEG медиа, некорректные или усеченные JPEG-файлы, а также JPEG-файлы, которые вызывают предупреждение во время ограниченного декодирования полного изображения с помощью `sharp`. Он перекодирует каждое принятое изображение как канонический JPEG, извлекает ширину и высоту из декодированных байтов вместо того, чтобы доверять полям вызывающего абонента, и отбрасывает любые завершающие полиглотные байты вместо их сохранения. Только ограниченный канонический сжатый буфер учитывается в обеих квотах. Лимит JSON-протокола включает накладные расходы Base64 для потолка декодированного ввода в 32 МиБ. Каждая сохраненная производная запись содержит свой проверенный формат/разрешение JPEG, политику выборки, версию производной, время создания, хеш содержимого, вычисленный сервером, и хешированную родительскую ссылку плюс хеш родительского содержимого доверенного вызывающего абонента. Отмена проверяется между асинхронными фазами декодирования/хеширования перед атомарной фиксацией кэша.

Этот транш пока не подключает производственный продюсер к маршруту и не предоставляет выбор вариантов с несколькими разрешениями. Таким образом, прозрачный путь запроса Video Bridge не влечет за собой дополнительной работы, в то время как вывод принципа, привязанного к арендатору, и полный жизненный цикл FU-08 с несколькими разрешениями остаются явной последующей работой, а не документируются как завершенное поведение.

Кадры последовательно подписываются с использованием настроенной модели Video. Пустое переопределение Video наследует настройку Vision; если оба пусты, автомаршрутизатор Vision выбирает эффективную модель, способную к зрению. Успешные подписи заменяют исходную часть стабильным префиксом `[Video description:`, который также помечает текст как ненадежное наблюдение, полученное из медиа, и указывает нижестоящим моделям не следовать инструкциям, найденным в медиа. Ключи кэша подписей кадров включают байты JPEG, запрос, метку времени и эффективную модель; кэшируются только успешные подписи. Записи кэша сохраняют фактическую успешную модель-производитель, включая резервную модель; мост сообщает `mixed`, когда разные кадры были произведены разными моделями. Попадание в кэш повторно использует эту идентификацию производителя вместо того, чтобы переименовывать ее как запрошенный план маршрутизации. Кэш результатов для всего видео индексируется по каждому входному параметру, который изменяет вывод — запросу, эффективной модели, политике выборки, количеству кадров, режиму семантического анализа, отпечатку SHA-256 нормализованной подсказки фокуса, окну фокуса, `transcript`, `audioTranscript` и флагу контактного листа — поэтому изменение любого из этих измерений приводит к промаху кэша, а не к устаревшему повторному использованию. Версия политики визуальной дедупликации, порог и ограниченное количество кадров-кандидатов также явно указаны в ключе кэша результатов и метаданных; изменение политики, следовательно, не может повторно использовать устаревшее описание всего видео. Метаданные кэша результатов v4 сохраняют режим и отпечаток, но никогда не сохраняют необработанную задачу пользователя. Метаданные Guardrail сообщают как запрошенный, так и эффективный режимы анализа; запрошенный режим `focused` без пригодного для использования пользовательского текста сообщается как фактически `full`.

Guardrail извлекает каждую поддерживаемую часть видео, но описывает не более `modalityBridgeVideoMaxVideos`. Для цели, для которой доказано, что `supportsVideo === false`, неудачные и превышающие лимит видео становятся явными безопасными текстовыми маркерами, так что необработанное видео не сохраняется. Когда возможность неизвестна, эти части остаются нетронутыми. Цели с `supportsVideo === true` обходят мост. Сигнал прерывания запроса клиента распространяется через загрузку, очередь брокера, подпроцессы и вызовы подписей; прерывания останавливаются между видео и никогда не приводят к открытому доступу к необработанным медиа.

Настройки среды выполнения хранятся в БД и проверяются Zod:

| Key                                 | Default     | Range / behavior                                                                                               |
| :---------------------------------- | :---------- | :------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | Необязательная среда выполнения, добровольное включение                                                        |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` сохраняет общие подписи; `focused` использует ограниченный, ненадежный контекст последнего пользователя |
| `modalityBridgeVideoModel`          | `""`        | Наследует модель Vision Bridge                                                                                 |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                           |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware` или пропорциональный `segment_aware`; сбой детектора возвращается к `uniform`         |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                            |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 мс                                                                                                 |

Устаревшие сохраненные значения тайм-аута видео более 120 секунд ограничиваются крайним сроком брокера; новые записи настроек, превышающие этот лимит, отклоняются. `GET /api/modality-bridge/video/runtime` требует доверенной локальности обратной связи с меткой времени перед аутентификацией или проверкой среды выполнения, затем требует аутентификации управления. Он возвращает только `available`, очищенные версии FFmpeg/ffprobe и фиксированную причину, когда среда выполнения недоступна. Внутренняя конечная точка извлечения не является публичным API загрузки: переполнение очереди возвращает `503` плюс `Retry-After`, отключение вызывающего абонента возвращает `499`, а фиксированный крайний срок брокера возвращает `504`. Преобразованные ответы добавляют `video->text;model=<visionModel>;parts=<videos>` в центральный заголовок `x-omniroute-modality-bridge` без удаления сегментов Vision или Audio.

### Маскировщик PII (`piiMasker.ts`)

Работает на **обоих** этапах.

- **`preCall`** клонирует полезную нагрузку, обходит `system`, `messages`, `input` и `prompt` (включая простые строковые элементы) и применяет `processPII()` (из `@/shared/utils/inputSanitizer`) к строковым полям `content`/`text`. Когда `PII_REDACTION_ENABLED=true`, обнаруженная PII редактируется в исходящей полезной нагрузке. Это не зависит от `INPUT_SANITIZER_MODE` (который контролирует только политику внедрения запросов). Когда редактирование отключено, вызов записывает количество обнаружений без перезаписи содержимого.
- **`postCall`** глубоко клонирует ответ, запускает `sanitizePIIResponse()` плюс маскировщик формы Responses-API (`maskResponsesOutput` — охватывает `output_text` и `output[].content[].text`). Если происходит какое-либо редактирование, измененный ответ заменяет исходный.

Guardrail никогда не блокирует; он только аннотирует (`meta.detections`, `meta.redacted`) или перезаписывает.

### Внедрение запросов (`promptInjection.ts`)

Обнаруживает враждебные структуры в предоставленном пользователем контенте и обеспечивает соблюдение настроенной политики. Поведение определяется переменными среды и параметрами конструктора:

| Настройка        | Env var                                                                                               | По умолчанию | Эффект                                                                                                                                                                                                                                       |
| ---------------- | ----------------------------------------------------------------------------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Включено         | `INPUT_SANITIZER_ENABLED`                                                                             | `true`       | Если `false`, защитный механизм отключается.                                                                                                                                                                                                 |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`       | Политика инъекций: `block` (блокировать), `warn` (предупреждать) или `log` (логировать). (`redact` принимается для обратной совместимости, но **не** удаляет текст инъекции; перезапись PII запроса контролируется `PII_REDACTION_ENABLED`.) |
| Порог блокировки | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | Минимальная серьезность, необходимая для блокировки. Средняя серьезность по умолчанию только для наблюдения.                                                                                                                                 |

**Приоритет режима** (`getMode`): `options.mode` вызывающего объекта →
**переопределение флагом функции БД** `INJECTION_GUARD_MODE` (Панель управления → Настройки →
Флаги функций) → переменная среды `INJECTION_GUARD_MODE` → переменная среды `INPUT_SANITIZER_MODE` →
`warn`. Таким образом, переопределение через панель управления имеет приоритет над переменными среды, поэтому пользовательский интерфейс флагов функций контролирует работающий защитный механизм в реальном времени (без перезапуска). Чтение из БД отказоустойчиво:
если происходит ошибка, защитный механизм возвращается к поведению, основанному на переменных среды, а если переопределение не установлено, поведение идентично разрешению только на основе переменных среды.

Источники обнаружения:

1.  `sanitizeRequest()` из `@/shared/utils/inputSanitizer` (общий набор детекторов, используемый в других частях конвейера).
2.  Встроенные `DEFAULT_GUARD_PATTERNS` (в настоящее время `system_override_inline` и
    `markdown_system_block`, оба с `high` серьезностью).
3.  Опциональные `customPatterns`, передаваемые через параметры конструктора (строки, регулярные выражения или записи `{ name, pattern, severity }`).

Когда `mode === "block"` **и** хотя бы одно обнаружение соответствует порогу серьезности,
`preCall` возвращает `{ block: true, message: "Request rejected:
suspicious content detected" }`. В режимах `warn`/`log` защитный механизм логирует, но разрешает вызов. Общая вспомогательная функция `evaluatePromptInjection()` также экспортируется для вызывающих объектов, которым необходимо оценивать промпты без обращения к реестру.

**Граница сканирования (v3.8.20):** детектор проверяет только **первые 16 КБ**
объединенного текста промпта — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байта) в
`src/shared/utils/inputSanitizer.ts`. Обе функции `detectInjection()` и
`evaluatePromptInjection()` используют `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском цикла сопоставления с образцом. Директивы инъекции обычно находятся в начале ввода, поэтому это ограничивает нагрузку на ЦП/сборщик мусора регулярных выражений для полезных нагрузок в сотни килобайт без ослабления обнаружения (см. #3932, #4041).

### Маскировщик учетных данных (`credentialMasker.ts`)

Работает на **обоих** этапах, последний в цепочке по умолчанию (приоритет `95`). Удаляет
известные шаблоны ключей API / секретных токенов из исходящей полезной нагрузки (содержимое сообщения, аргументы вызова инструмента, результаты инструмента) **и** ответа провайдера, чтобы учетные данные, вставленные в промпт (или возвращенные результатом инструмента), не просочились к вышестоящему провайдеру или обратно клиенту.

- **Только по согласию**, та же конвенция, что и для удаления PII (смежно с Жестким Правилом #20):
  отключено, если только `settings.credentialRedactionEnabled === true` **или**
  `CREDENTIAL_REDACTION_ENABLED=true`. Если оно отключено, защитный механизм неактивен —
  он никогда не блокирует и никогда не перезаписывает.
- `redactCredentials()` обходит полное дерево полезной нагрузки/ответа (`walkValue()`,
  безопасно от загрязнения прототипов, безопасно от циклов через `WeakSet`) и заменяет совпадения
  заглушкой `[REDACTED:<type>]`, клонируя только те ветви, которые фактически изменились.
- `CREDENTIAL_PATTERNS` охватывает ключи провайдеров LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токены VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платежные ключи (Stripe, Square),
  облачные ключи (AWS access key, Twilio, SendGrid, Mailgun), приватные ключи / JWT,
  строки подключения, содержащие учетные данные (`mongodb://user:pass@...` и т.д.), и
  общий шаблон значения заголовка `Authorization`/`x-api-key`/`api-key`/`apikey`.
  Ключи в форме заголовков (`authorization`, `x-api-key`, `api-key`, `apikey`)
  редактируются структурно (только значение, префикс схемы, такой как
  `Bearer `/`Basic `, сохраняется), а не с помощью общего текстового регулярного выражения.
- Защитный механизм никогда не блокирует; он только перезаписывает (`modifiedPayload` /
  `modifiedResponse`) и аннотирует (`meta.credentialsRedacted`, `meta.count`).

Защита от регрессии: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовый контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true short-circuits the chain
  message?: string; // surfaced when blocking
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // returned by preCall to rewrite the request
  modifiedResponse?: TValue; // returned by postCall to rewrite the response
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Защитный механизм сигнализирует об "отсутствии изменений", возвращая `void`, `{}`, или
`{ block: false }`. Возврат `modifiedPayload`/`modifiedResponse` заменяет
значение, проходящее по цепочке, для последующих защитных механизмов.
`signal?: AbortSignal` передает жизненный цикл вызывающей стороны в защитные механизмы. Прерывание запроса является преднамеренным исключением "fail-open": медиа-мосты прекращают работу и очищаются, не восстанавливая необработанные медиаданные для цели, которая, как известно, их не поддерживает.

## Реестр (`registry.ts`)

Синглтон `guardrailRegistry` предоставляет:

- `register(guardrail)` — добавляет (или заменяет по нормализованному имени) защитный механизм и
  повторно сортирует по возрастанию `priority`.
- `clear()` / `list()` — вспомогательные функции администрирования.
- `runPreCallHooks(payload, context)` — итерирует активные защитные механизмы, пропускает
  полезную нагрузку через `modifiedPayload` и останавливается на первом `block: true`.
- `runPostCallHooks(response, context)` — тот же поток на стороне ответа.
- `resetGuardrailsForTests({ registerDefaults })` — очищает состояние и опционально
  повторно регистрирует значения по умолчанию для чистой изоляции тестов.

Оба запускатора возвращают `{ blocked, payload|response, results, guardrail?, message? }`,
где `results` — это массив записей `GuardrailExecutionResult`, которые включают
поля `blocked`, `skipped`, `modified`, `error` и `meta` для каждого защитного механизма,
полезные для трассировки.

### Отключение защитных механизмов для каждого запроса

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегирует
дедуплицированный список имен защитных механизмов, которые должны быть пропущены для текущего
запроса. Источники (все опциональные, все объединенные):

- `apiKeyInfo.disabledGuardrails`
- Тело запроса `disabledGuardrails` (верхний уровень)
- Тело запроса `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (или устаревший
  `x-disabled-guardrails`)

Значения могут быть массивами строк или строкой, разделенной запятыми; имена
нормализуются в нижний регистр kebab-case (`pii_masker` → `pii-masker`). Результат
передается через `context.disabledGuardrails` в реестр, который пропускает
соответствующие защитные механизмы (`skipped: true` в `results`).

## Порядок выполнения

Для каждого запроса, проходящего через `src/sse/handlers/chat.ts` и
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` формирует список исключений из ключа API, тела запроса
    и заголовков.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускает защитные механизмы в порядке
    возрастания приоритета:
    - Отключенные защитные механизмы записываются как `skipped`.
    - Метод `preCall` каждого защитного механизма может переписывать полезную нагрузку через `modifiedPayload`.
    - Первый `block: true` прерывает цепочку, и обработчик возвращает
      ответ об отклонении защитным механизмом.
3.  (Потенциально переписанная) полезная нагрузка поступает в комбинированную маршрутизацию и
    диспетчеризацию вышестоящему сервису.
4.  После сборки ответа `guardrailRegistry.runPostCallHooks(...)`
    запускает ту же цепочку для ответа. `block: true` здесь отбрасывает
    ответ вышестоящего сервиса.

Защитные механизмы, которые выбрасывают исключения, записываются с `error: <message>` и
логируются через `logger.warn`, но цепочка продолжается — по замыслу, система
открыта к сбоям.

## Конфигурация

Переменные окружения, считываемые встроенными защитными механизмами:

| Переменная                            | Используется                  | Эффект                                                                                                                 |
| :------------------------------------ | :---------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`            | Установите `false`, чтобы полностью отключить обнаружение.                                                             |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`            | Политика инъекций: `warn`, `block` или `log`. Устаревшее значение `redact` не переписывает текст инъекции.             |
| `INJECTION_GUARD_MODE`                | `prompt-injection`            | Режим для защиты от инъекций; также флаг функции БД, который **переопределяет** переменные окружения (БД > ОКРУЖЕНИЕ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`            | Минимальная серьезность, при которой `MODE=block` отклоняет: `high` (по умолчанию), `medium` или `low`.                |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`            | Устаревший псевдоним для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                            |
| `PII_REDACTION_ENABLED`               | `pii-masker`                  | Если `true`, PII запроса скрывается (независимо от режима инъекции).                                                   |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ниже по потоку) | Управляет поведением маскировщика на стороне ответа.                                                                   |

Защитные механизмы Modality Bridge считывают конфигурацию времени выполнения из хранилища настроек,
поддерживаемого БД (`getSettings()`), а не из переменных окружения. Основные ключи Vision:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и
`modalityBridgeCacheMaxEntries`. Устаревшие ключи
`visionBridge*` принимаются только в качестве документированного одноциклового
резервного чтения; записи с панели управления используют основные ключи. Значения по умолчанию и
резервный резолвер находятся в `src/shared/constants/modalityBridgeDefaults.ts`,
при этом устаревшие константы сохранены в `src/shared/constants/visionBridgeDefaults.ts`.

Аудио использует `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` и `modalityBridgeAudioMaxClips`, а также общие
настройки `modalityBridgeCache*`. У Аудио нет резервного варианта для устаревших ключей,
поскольку эти ключи были введены со схемой Modality Bridge.

Видео использует `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` и
`modalityBridgeVideoTimeout`, а также общие настройки `modalityBridgeCache*`.
По умолчанию оно отключено, поскольку FFmpeg/ffprobe являются необязательными
операционными зависимостями, а создание подписей к кадрам увеличивает задержку и
стоимость модели.

## Пользовательские Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Шаги:

1.  Создайте `src/lib/guardrails/myGuardrail.ts`, расширяющий `BaseGuardrail`.
2.  Реализуйте `preCall` и/или `postCall`.
3.  Либо зарегистрируйте во время импорта (push из `registerDefaultGuardrails`), либо
    вызовите `guardrailRegistry.register(...)` во время выполнения — реестр заменяет
    любой предыдущий guardrail с тем же нормализованным именем.
4.  Добавьте тесты в `tests/unit/` (существующие примеры:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестирование

Используйте `resetGuardrailsForTests()` между тестами, чтобы начать с известного состояния.
Передайте `{ registerDefaults: false }`, чтобы начать с пустого реестра и
зарегистрировать только тестируемые guardrails. Vision Bridge принимает внедрение зависимостей
(`deps.getSettings`, `deps.callVisionModel`); Audio Bridge предоставляет эквивалентные точки расширения
для настроек, возможностей, выбора модели STT, проверки учетных данных и транскрипции.
Таким образом, тесты могут проверять оба потока без доступа к БД или сети.

## Покрытие маршрутов защитой от инъекций и red-team (Фаза 8 · Блок D)

Защита от инъекций (`createInjectionGuard` / `withInjectionGuard`) охватывает все маршруты,
которые принимают пользовательские промпты. Она учитывает `INJECTION_GUARD_MODE` (по умолчанию `warn` = только логирование;
`block` = возвращает HTTP 400 `SECURITY_001`).

| Тип                  | Маршруты                                                                                                                                             | Режим по умолчанию |
| :------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------- |
| Текст (существующий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn               |
| Генеративный         | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn               |
| Данные               | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn               |

Извлечение текста (`extractMessageContents`) охватывает `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (ночной, `nightly-llm-security.yml`):** promptfoo проверяет, что каждый маршрут блокирует
корпус OWASP-LLM в режиме `INJECTION_GUARD_MODE=block`; garak запускает зонды (пропускает без секрета).
`moderations` включен для согласованности — операторы в режиме блокировки могут исключить его через
`resolveDisabledGuardrails`.

Ночной рабочий процесс (`.github/workflows/nightly-llm-security.yml`, cron + ручной
запуск) состоит из двух задач:

- **`promptfoo-guard` (блокирующий)** — запускает `promptfoo eval -c promptfooconfig.yaml`
  с `INJECTION_GUARD_MODE=block`. Каждый adversarial-кейс (например, "игнорировать все
  предыдущие инструкции...", джейлбрейки в стиле DAN) подтверждает, что ответ содержит
  `error.code === "SECURITY_001"`, то есть защита фактически отклонила запрос.
- **`garak` (консультативный)** — запускает garak `--probes promptinject,dan,leakreplay`
  против локального экземпляра OmniRoute (`http://localhost:20128/v1`). Ограничен
  секретом провайдера (`PROMPTFOO_PROVIDER_KEY`); корректно пропускается и имеет суффикс
  `|| true`, поэтому он сообщает о результатах, не приводя к сбою CI.

Покрытие вспомогательной функции защиты (`createInjectionGuard` / `withInjectionGuard`)
охватывает каждый маршрут `/v1`, содержащий промпты; текст промпта извлекается из
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` с помощью
`extractMessageContents()` в `src/shared/utils/inputSanitizer.ts`.
