## Обзор

Все маршруты API управления OmniRoute относятся к одному из трёх уровней
защиты. Классификация статична, определена в `src/server/authz/routeGuard.ts`
и проверяется до выполнения любой другой ветви аутентификации.

## Уровни

### Уровень 1 — LOCAL_ONLY

**Обеспечивается:** `isLocalOnlyPath(path)` → проверка loopback-адреса хоста
**Обход:** По умолчанию отсутствует. Узкое исключение предусмотрено для путей из
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, когда запрос содержит действительный
API-ключ с областью действия `manage` (см. [Исключение для области действия manage](#manage-scope-carve-out)).

Эти маршруты порождают дочерние процессы или выполняют код среды исполнения. Если
сделать их доступными для трафика не через loopback-интерфейс, злоумышленник,
получивший действительный JWT (например, через туннель Cloudflared/Ngrok), сможет
запускать процессы — это известный класс CVE
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Что представляет собой GHSA-fhh6-4qxv-rpqj (класс атаки):** сервер управления
или агент предоставляет конечную точку, запускающую подпроцесс (`npm install`,
`node`, браузер, прокси, `git`, `tar`, …). Если эта конечная точка доступна извне
хоста — например, потому что оператор разместил OmniRoute за туннелем
nginx/Cloudflare/Tailscale и произошла утечка JWT либо аутентификация была
настроена неправильно, — злоумышленник превращает «вызов API» в «выполнение
команды на хосте» (удалённое выполнение кода). OmniRoute предотвращает это,
**безусловно проверяя loopback-адрес хоста до любой проверки аутентификации**
для каждого маршрута, способного порождать процессы: украденный токен,
используемый через туннель, всё равно не позволяет запустить процесс.

**Полный набор LOCAL_ONLY.** Авторитетным источником являются
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` в
`src/server/authz/routeGuard.ts`; приведённая ниже таблица отражает текущее
состояние. Проверка `check-route-guard-membership` перечисляет все файлы
`route.ts` в префиксах, способных порождать процессы, и приводит к сбою CI,
если какой-либо из них не классифицирован как доступный только локально.

#### Исключение для области manage

К подмножеству путей LOCAL_ONLY ТАКЖЕ МОЖНО обращаться не через loopback-интерфейс, если и
только если запрос содержит `Authorization: Bearer <api-key>`, метаданные
которого включают область `manage` (или `admin`). Это исключение включается
явно для каждого пути через `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, поэтому
для любого нового пути LOCAL_ONLY по умолчанию сохраняется строгое требование loopback-интерфейса. Неаутентифицированные
запросы и запросы с ключами без области manage по-прежнему отклоняются с ответом
`403 LOCAL_ONLY`.

В настоящее время единственный префикс, допускающий обход, — `/api/mcp/`. `/api/cli-tools/runtime/` и
`/api/services/` намеренно исключены, поскольку они могут запускать произвольные
подпроцессы (`npm install`, `node`), что соответствует именно тому классу CVE,
для предотвращения которого существует уровень LOCAL_ONLY.

**#7895 — узкая область `mcp:connect`:** исключение для `/api/mcp/` ТАКЖЕ принимает
Bearer-ключ с узкой областью `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), проверяемой через
`hasMcpConnectOrManageScope()` в `src/server/authz/policies/management.ts`.
Она распространяется ТОЛЬКО на `/api/mcp/` — `mcp:connect` не предоставляет никаких прав ни для каких других
маршрутов управления (включая любой другой префикс обхода LOCAL_ONLY, если такой
когда-либо будет добавлен) и намеренно исключена из
`MANAGEMENT_API_KEY_SCOPES`. Ключ с областью `manage`/`admin` по-прежнему позволяет
обойти ограничение точно так же, как и раньше; `mcp:connect` — это альтернатива с меньшими привилегиями
для удалённых клиентов, использующих только MCP и не нуждающихся в широком доступе к управлению.

| Запрос                                               | Путь                       | Результат                     |
| ---------------------------------------------------- | -------------------------- | ----------------------------- |
| Не через loopback, без Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY                |
| Не через loopback, Bearer с областью `manage`        | `/api/mcp/*`               | Разрешить                     |
| Не через loopback, Bearer с областью `mcp:connect`   | `/api/mcp/*`               | Разрешить                     |
| Не через loopback, Bearer без `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                |
| Не через loopback, Bearer с областью `mcp:connect`   | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                |
| Не через loopback, Bearer с областью `manage`        | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                |
| Через loopback, с любым Bearer или без него          | любой LOCAL_ONLY           | Разрешить (проверка пройдена) |

#### Рекомендации для операторов и аудит

Если вы запускаете OmniRoute за обратным прокси или туннелем (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), проверка loopback-интерфейса по-прежнему защищает перечисленные выше маршруты,
способные запускать процессы: запрос, адрес клиента которого не относится к loopback-интерфейсу, отклоняется с
ответом `403 LOCAL_ONLY` **до выполнения аутентификации**, поэтому утёкший JWT не позволит
запустить процесс. При этом у оператора остаются две обязанности:

- **Не «исправляйте» ошибку 403, подделывая IP-адрес клиента как loopback.** Установка
  `X-Forwarded-For: 127.0.0.1` или использование прокси, который переписывает адрес источника
  на loopback-адрес, вновь открывает именно тот класс RCE, от которого защищает этот уровень. Предоставляйте
  доступ через прокси к панели управления/API, но никогда — к маршрутам, способным запускать процессы.
- **Сохраняйте обход через область manage минимальным.** Обход разрешён только для `/api/mcp/` и
  только с API-ключом, имеющим область `manage`. `SPAWN_CAPABLE_PREFIXES` ни при каких условиях нельзя
  добавлять в список обхода — схема zod отклоняет их, а
  `isLocalOnlyBypassableByManageScope` блокирует их во время выполнения (эшелонированная защита);
  именно это имеет в виду панель управления под формулировкой «нельзя сделать доступным для обхода». Маршруты с динамическими сегментами
  и статическими путями, способные запускать процессы, в `/api/providers/` (например, `/login`,
  `/refresh-cursor`) охватываются сопутствующими регулярными выражениями `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` в
  `src/shared/constants/spawnCapablePrefixes.ts`, а не плоским массивом
  `SPAWN_CAPABLE_PREFIXES` — для их охвата плоскому массиву пришлось бы включить
  весь префикс `/api/providers/`, что сделало бы ограничения для дерева маршрутов
  чрезмерно широкими, хотя удалённые панели управления правомерно используют его для CRUD-операций с провайдерами.

**Аудит доступа** — чтобы убедиться, что никакие внешние запросы не достигают этих маршрутов:

- Откройте **Authorization Inventory** по адресу `/dashboard/settings/security`: там отображаются
  актуальный список префиксов LOCAL_ONLY, префиксы, для которых возможен обход, и заданный при
  компиляции набор маршрутов с возможностью запуска процессов («обход для них невозможен»).
- Выполните поиск с помощью grep в журналах обратного прокси / доступа по указанным выше префиксам
  в сочетании с адресом клиента, не относящимся к loopback. Любой такой запрос, вернувший `200`
  вместо `403 LOCAL_ONLY`, означает, что прокси скрывает реальный IP-адрес клиента — исправьте
  конфигурацию прокси.
- Запись `403 LOCAL_ONLY` в журналах OmniRoute для одного из этих путей означает, что защита
  работает как предусмотрено, а не ошибку, которую следует подавлять.

### Уровень 2 — ALWAYS_PROTECTED

**Обеспечивается:** `isAlwaysProtectedPath(path)` → пропуск обхода `requireLogin=false`
**Обход:** отсутствует при `requireLogin=false`; JWT требуется всегда

Эти маршруты выполняют разрушительные или необратимые действия. Если разрешить их в установке
«без пароля», любой пользователь в той же локальной сети сможет стереть базу данных или завершить
серверный процесс.

| Путь                                      | Причина                                                                          |
| ----------------------------------------- | -------------------------------------------------------------------------------- |
| `/api/shutdown`                           | Завершает серверный процесс                                                      |
| `/api/settings/database`                  | Экспорт, импорт и очистка базы данных                                            |
| `/api/db-backups`                         | Доступ к полному архиву резервной копии базы данных                              |
| `/api/settings/export-json`               | Экспортирует полный набор настроек (включая секреты)                             |
| `/api/settings/import-json`               | Заменяет полный набор настроек                                                   |
| `/api/providers/health-autopilot/actions` | Выполняет корректирующие действия автопилота                                     |
| `/api/settings/obsidian`                  | Выпускает повторно используемые учетные данные WebDAV для любого корня хранилища |

**Ответ при нарушении:** `401 Authentication required`

`/api/settings/obsidian` также охватывает дочерний маршрут `/webdav`: `POST` направляет файловую
службу WebDAV — обслуживаемую пользовательским слоем Node перед Next.js, вне этого конвейера —
на корень, выбранный вызывающей стороной, и возвращает только что выпущенные учетные данные Basic;
`DELETE` обновляет их, а родительский `POST` сохраняет токен REST API Obsidian. GHSA-62vw лишь
скрывал раскрытие пароля через `GET`; выпуск учетных данных по-прежнему оставался на уровне,
допускающем доступ при отказе проверки (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()`
дополнительно отклоняет хранилище, которое является каталогом данных, находится внутри него
или содержит его.

### Первоначальная настройка новой установки доступна только через loopback — по реальному узлу, а не по `Host`

Если пароль управления не настроен (и отсутствует `INITIAL_PASSWORD`), `isAuthRequired()` в
`src/shared/utils/apiAuth.ts` оставляет анонимную первоначальную настройку доступной **только для
loopback-узлов**. Принадлежность к loopback определяется по доверенным сигналам узла в следующем
порядке: реальный TCP-узел, помеченный токеном (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, то, что
видит политика), собственный вердикт конвейера `AUTHZ_HEADER_PEER_LOCALITY` (то, что видят
обработчики маршрутов; ему доверяют только при заданном `OMNIROUTE_PEER_STAMP_TOKEN`) или реальный
сокетный узел для прямых вызовов. `Host` / `nextUrl.hostname` никогда не учитываются, а первичная
запись пароля (`POST /api/settings/require-login`) подчиняется тому же ограничению, а не открыта
для каждого сетевого узла (GHSA-7pq4-8pvv-rx7r). `managementPolicy` явно передает ниже собственный
вердикт `peerContext`, поэтому заголовки ИСХОДНОГО (до удаления заголовков) запроса никогда не
влияют на решение.

### Уровень 3 — MANAGEMENT (по умолчанию)

Все остальные маршруты управления. Аутентификация обязательна, если не настроено
`requireLogin=false`. CLI-токены могут использоваться для аутентификации на этих маршрутах
(loopback + действительный HMAC).

## Порядок проверки

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → перейти к следующей проверке
     → не loopback, Bearer с областью manage
        И isLocalOnlyBypassableByManageScope     → разрешить (management_key)
     → иначе                                     → отклонить с 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → разрешить (system)
  3. hasValidCliToken(headers)?
     → разрешить (cli) [loopback + проверка HMAC через timingSafeEqual]
  4. isAlwaysProtectedPath(path) или requireLogin=true?
     → isDashboardSessionAuthenticated?
        → разрешить (dashboard_session)
     → Bearer с областью manage для пути, не допускающего обход?
        → разрешить (management_key)
     → отклонить с 401/403
  5. requireLogin=false?
     → разрешить (anonymous)
```

Ветвь с областью manage на шаге 1 — единственный аутентифицированный способ получить доступ к маршруту
LOCAL_ONLY; при сбое бэкенда аутентификации возвращается 503 (а не 403), поэтому
истёкшая БД не приводит незаметно к режиму «запретить».

## Добавление нового маршрута, способного запускать процессы

1. Добавьте префикс пути в `LOCAL_ONLY_API_PREFIXES` в
   `src/server/authz/routeGuard.ts`
2. Добавьте тест в `tests/unit/authz/routeGuard.test.ts`, проверяющий, что
   `isLocalOnlyPath()` возвращает true для нового префикса
3. **Никогда не пропускайте этот шаг** — см. строгое правило №15 в `CLAUDE.md`
4. Решите: должен ли этот маршрут ТАКЖЕ входить в `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Ответ по умолчанию — **нет**. Добавляйте его только тогда, когда маршрут безопасно предоставлять
   обладателю области manage (то есть он НЕ запускает произвольный код, управляемый пользователем).

## Добавление пути, допускающего обход с областью manage

1. Убедитесь, что маршрут не выполняет предоставленный пользователем код или команды. Если
   выполняет, остановитесь — это исключение здесь неприменимо.
2. Добавьте префикс в `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` в
   `src/server/authz/routeGuard.ts`
3. Добавьте покрытие в `tests/unit/authz/management-policy.test.ts` для всех четырёх
   вариантов запроса: без Bearer (403), Bearer с областью manage (разрешить), Bearer без области manage
   (403), а также отдельный регрессионный тест для префикса, подтверждающий, что `/api/cli-tools/runtime/*` остаётся
   доступным строго через loopback даже при наличии Bearer с областью manage.

## Документирование уровней безопасности в OpenAPI

При добавлении нового маршрута в `docs/openapi.yaml` примените соответствующее
пользовательское расширение, если маршрут классифицирован в `routeGuard.ts`:

| Классификация routeGuard.ts                  | Аннотация YAML             | Применяемое ограничение                                   |
| -------------------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                    | `x-loopback-only: true`    | Безусловно блокируется для запросов не через loopback     |
| `ALWAYS_PROTECTED_API_PATHS`                 | `x-always-protected: true` | Аутентификация обязательна даже при `requireLogin=false`  |
| Внутренний маршрут администрирования/отладки | `x-internal: true`         | По умолчанию скрыт из /dashboard/api-endpoints            |
| Нет (публичный / стандартная аутентификация) | (аннотация не требуется)   | Стандартный доступ, управляемый параметром `requireLogin` |

### Проверка

Два скрипта обеспечивают согласованность аннотаций YAML с `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — завершается с ошибкой, если покрытие < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — завершается с ошибкой, если аннотации `x-loopback-only` или
  `x-always-protected` расходятся с константами времени компиляции

Оба скрипта запускаются в хуке перед коммитом и в CI.

### Правило ложноположительного срабатывания

Если маршрут аннотирован `x-always-protected` или `x-loopback-only`, но НЕ входит в
соответствующую константу `routeGuard.ts`, скрипт проверки покрытия завершается с ошибкой. Исправление всегда заключается в том, чтобы привести
YAML в соответствие с тем, что фактически контролирует `routeGuard.ts`, а не добавлять маршруты в `routeGuard.ts`
без одновременной реализации логики ограничения доступа.
