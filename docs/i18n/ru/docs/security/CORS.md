OmniRoute контролирует, какие **источники браузера** могут читать ответы на междоменные запросы,
с помощью единого централизованного списка разрешённых источников. Модель **по умолчанию запрещает доступ**:
ни один источник не разрешён, пока вы явно не добавите его. На этой странице описано, как применяется список разрешённых источников,
к чему фактически открывает доступ `CORS_ALLOW_ALL=true` (и, что особенно важно, к чему
он **не** открывает доступ), как безопасно настроить среду разработки и рабочую среду, а также предупреждение времени выполнения,
которое отображается на панели управления при активном подстановочном значении.

**Источник истины:** `src/server/cors/origins.ts` (`resolveAllowedOrigin`,
`applyCorsHeaders`, `getCorsStatus`). Список разрешённых источников применяется один раз
в промежуточном ПО (`src/server/authz/pipeline.ts`) — обработчики отдельных маршрутов не задают
`Access-Control-Allow-Origin` самостоятельно.

## Как определяется источник

Для каждого запроса промежуточное ПО вычисляет значение `Access-Control-Allow-Origin`
в следующем порядке:

1. **`CORS_ALLOW_ALL=true`** (или устаревшая переменная `CORS_ORIGIN=*`) → источник вызывающей стороны
   из заголовка `Origin` возвращается в ответе (или используется `*`, если заголовок `Origin` отсутствует), вместе с `Vary: Origin`,
   чтобы кэши работали корректно. Та же единая точка `applyCorsHeaders()` также добавляет
   `Vary: Accept-Encoding` к каждому ответу 2xx с телом на маршрутах
   `/v1*`/`/v1beta*`, использующих аутентификацию по токену (`relaxForTokenAuth`, RFC 9110 §12.5.5, задача #6737), чтобы
   нижестоящие и общие кэши могли правильно различать сжатые и несжатые
   варианты.
2. В противном случае источник запроса `Origin` нормализуется (приводится к нижнему регистру,
   завершающая косая черта удаляется) и сопоставляется с **объединённым списком разрешённых источников**:
   - переменная среды **`CORS_ALLOWED_ORIGINS`** — список, разделённый запятыми, и
   - параметр времени выполнения **`corsOrigins`** (Панель управления → Безопасность → _Разрешённые
     источники CORS_), передаваемый через `setRuntimeAllowedOrigins()` из
     `src/lib/config/runtimeSettings.ts`.
3. Совпадение отсутствует → **заголовок `Access-Control-Allow-Origin` не отправляется**. Браузер
   блокирует чтение междоменного ответа. Это и есть предполагаемое поведение с запретом по умолчанию.

| Переменная среды       | Значение                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------- |
| `CORS_ALLOWED_ORIGINS` | CSV-список точных источников, которые следует разрешить (рекомендуется).                                        |
| `CORS_ALLOW_ALL`       | `true`/`1` → возвращать любой источник (подстановочное значение). Только для разработки.                        |
| `CORS_ORIGIN`          | Устаревшая. `*` действует как `CORS_ALLOW_ALL`; одиночное значение добавляется в список разрешённых источников. |

## Модель угроз — к чему фактически открывает доступ `CORS_ALLOW_ALL=true`

К общему предупреждению OWASP («подстановочный CORS = любой сайт может вызывать ваш API») стоит
относиться серьёзно, однако область воздействия в OmniRoute **уже, чем в общем случае**,
из-за одного конкретного аспекта реализации:

> **Централизованная функция `applyCorsHeaders()` никогда не отправляет
> `Access-Control-Allow-Credentials`.** Браузер не предоставит доступ к _аутентифицированному_
> междоменному ответу (содержащему cookie), если сервер не отправит
> `Access-Control-Allow-Credentials: true`. Общий механизм CORS в OmniRoute никогда
> этого не делает.

Вот что это означает для каждой поверхности API, даже при `CORS_ALLOW_ALL=true`:

| Поверхность                                                 | Механизм аутентификации        | Влияние подстановочного CORS                                                                                                                                                                                                                                |
| ----------------------------------------------------------- | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Панель управления / MANAGEMENT `/api/*`                     | Сеанс на основе cookie         | Источник возвращается в ответе, но **без `Allow-Credentials`** браузер **блокирует** чтение аутентифицированного ответа. Вредоносный междоменный сайт **не может прочитать** аутентифицированные ответы панели управления, а cookie сеанса не раскрывается. |
| Клиентский API `/v1/*`, `/v1beta/*`                         | Заголовок Bearer / `x-api-key` | Уже имеет разрешительную политику **по замыслу** (`relaxForTokenAuth`): браузеры никогда не добавляют `Authorization`/`x-api-key` автоматически, поэтому страница злоумышленника не может передать ваш ключ. `CORS_ALLOW_ALL` не расширяет этот доступ.     |
| Общедоступные маршруты только для чтения (`/api/health`, …) | Отсутствует                    | Данные не являются конфиденциальными; подстановочное значение безвредно.                                                                                                                                                                                    |

Таким образом, **остаточное** воздействие `CORS_ALLOW_ALL=true` ограничивается следующим: (a)
неаутентифицированное междоменное **чтение** уже общедоступных данных и (b)
разрешение **предварительных CORS-запросов** на маршрутах управления, которые по-прежнему требуют аутентификацию,
недоступную междоменной странице. В общем механизме CORS это **не** создаёт
вектор перехвата сеанса или кражи учётных данных.

### Одно реальное исключение — `/api/v1/agents/`

Маршруты Cloud-Agent (`/api/v1/agents/{health,credentials,tasks,tasks/[id]}`) задают
**собственные** заголовки CORS
(`src/lib/cloudAgent/api.ts`, `getCloudAgentCorsHeaders`) и **действительно** отправляют
`Access-Control-Allow-Origin: <origin>|*` вместе с
`Access-Control-Allow-Credentials: true`. Это единственная поверхность, где
возврат источника и учётные данные используются одновременно, и она **не зависит от
`CORS_ALLOW_ALL`**. Эти маршруты требуют аутентификацию управления
(`requireManagementAuth`); операторам, открывающим доступ к панели управления за пределами локального узла, следует
учитывать, что это единственное место, где заголовки ответа разрешают междоменное чтение
с учётными данными. Переход к явному списку разрешённых источников отслеживается
отдельно от этого руководства по CORS.

## Контрольный список для продакшена

- **Никогда не устанавливайте `CORS_ALLOW_ALL=true` в продакшене.** Оставьте эту переменную не заданной.
- Задайте **явный** список источников — с помощью переменной окружения или поля на вкладке Security:

  ```bash
  CORS_ALLOWED_ORIGINS="https://app.example.com, https://admin.example.com"
  ```

- Если OmniRoute работает за обратным прокси-сервером или туннелем (nginx, Caddy, Cloudflare
  Tunnel, Tailscale), CORS — **не** единственный механизм контроля: защита маршрутов
  с доступом только через loopback по-прежнему защищает маршруты, способные запускать процессы (см.
  [ROUTE_GUARD_TIERS](./ROUTE_GUARD_TIERS.md)). Не подделывайте
  `X-Forwarded-For: 127.0.0.1`, чтобы «исправить» ошибку 403: это вновь открывает класс уязвимостей RCE,
  который блокирует защита маршрутов.
- Проверьте состояние среды выполнения: когда активно
  `CORS_ALLOW_ALL=true`, на панели управления в разделе Dashboard → Security → Authorization Inventory
  отображается **постоянный янтарный баннер**, а `/api/settings/authz-inventory` возвращает
  объект `cors: { allowAll, allowedOrigins }`, который могут опрашивать инструменты мониторинга.

## Удобство разработки — разрешение определённых локальных источников

Даже при разработке wildcard требуется редко. Разрешите только используемые серверы разработки:

```bash
# Серверы разработки Vite (5173) и Next.js (3000), обращающиеся к локальному OmniRoute
CORS_ALLOWED_ORIGINS="http://localhost:5173, http://localhost:3000"
```

Источники сопоставляются без учёта регистра, а завершающий слеш игнорируется, поэтому
`http://localhost:3000` и `http://localhost:3000/` эквивалентны. Тот же CSV-список
можно задать во время выполнения в разделе **Dashboard → Security → CORS Allowed Origins** без
перезапуска.

## API-ключи и сеансы с cookie

- **Bearer / `x-api-key` (поверхность инференса `/v1/*`):** браузеры никогда не добавляют
  их автоматически. CORS здесь не является значимым барьером — барьером служит API-ключ,
  поэтому эта поверхность намеренно допускает запросы, чтобы браузерные клиенты и
  клиенты Electron могли читать ответы, к которым у них уже есть доступ.
- **Сеанс с cookie (панель управления):** защищён политикой запрета по умолчанию **и**
  отсутствием `Access-Control-Allow-Credentials` на общем пути. Не включайте
  источники управления и панели управления в разрешающие конфигурации: для них должна строго
  сохраняться политика запрета по умолчанию.

## Пример: обратный прокси-сервер перед OmniRoute

CORS применяется самим OmniRoute, поэтому прокси-сервер, как правило, **не** должен добавлять или
перезаписывать заголовки `Access-Control-*` (дублирующиеся заголовки нарушают работу браузеров). Завершайте TLS
и перенаправляйте запросы — пусть OmniRoute отвечает на предварительные запросы:

```nginx
# nginx — перенаправляйте запросы в OmniRoute; НЕ добавляйте сюда Access-Control-*
location / {
    proxy_pass http://127.0.0.1:20128;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    # НЕ устанавливайте X-Forwarded-For в 127.0.0.1 — это обходит защиту маршрутов с доступом только через loopback.
}
```

Задавайте разрешённые источники браузера в OmniRoute (`CORS_ALLOWED_ORIGINS` или на
вкладке Security), а не в прокси-сервере.
