OmniRoute публикует артефакты npm и Docker. Эти проверки обеспечивают подтверждение происхождения,
инвентаризацию (SBOM) и сканирование CVE, полностью на базе OSS и встроены в процессы выпуска.
Подход **сначала рекомендации** — сейчас они только формируют отчёты, а после первого
успешного выпуска становятся блокирующими.

| Проверка                  | Инструмент                                     | Где                            | Блокирует?                 | Результат                                         |
| ------------------------- | ---------------------------------------------- | ------------------------------ | -------------------------- | ------------------------------------------------- |
| Происхождение SLSA (npm)  | `npm --provenance` (OIDC)                      | `npm-publish.yml`              | только при сбое публикации | значок npmjs / `npm audit signatures`             |
| SBOM npm                  | `@cyclonedx/cyclonedx-npm`                     | `npm-publish.yml`              | только при сбое генерации  | ресурс релиза + артефакт                          |
| SBOM образа               | `anchore/sbom-action` (syft)                   | `docker-publish.yml` (слияние) | рекомендательная           | артефакт CycloneDX                                |
| CVE Trivy (SARIF)         | `aquasecurity/trivy-action`                    | `docker-publish.yml` (слияние) | рекомендательная           | SARIF (HIGH+CRITICAL) → вкладка Security          |
| Проверка CRITICAL в Trivy | `aquasecurity/trivy-action`                    | `docker-publish.yml` (слияние) | **блокирующая**            | `exit-code: '1'` при исправимых CRITICAL          |
| vulnCount osv             | `osv-scanner` (`check:vuln-ratchet --ratchet`) | `ci.yml` (`quality-extended`)  | **блокирующая**            | ограничивает `metrics.vulnCount` (direction:down) |
| OpenSSF Scorecard         | `ossf/scorecard-action`                        | `scorecard.yml` (cron)         | рекомендательная           | SARIF → Security + значок                         |

Ограничитель CVE образа использует **два шага** в `docker-publish.yml`: шаг SARIF
(`HIGH,CRITICAL`, `exit-code: 0`) сохраняет видимость HIGH+CRITICAL на вкладке Security,
не блокируя выпуск; шаг _проверки CRITICAL_ (`severity: CRITICAL`, `ignore-unfixed: true`,
`exit-code: 1`) прерывает выпуск при наличии CVE уровня CRITICAL, **для которой доступно исправление**. `ignore-unfixed`
предотвращает блокировку выпуска из-за CVE базового образа, для которой ещё нет исправления от вышестоящего проекта.

## ⚠️ Изменчивость CVE (блокирующие проверки osv/Trivy)

osv и Trivy сопоставляют зависимости с базами данных CVE, которые **непрерывно пополняются**. PR,
который **не изменяет зависимости**, может внезапно стать красным из-за публикации новой CVE
в существующей зависимости (osv: измеренное значение `vulnCount` > базового; Trivy: новая
исправимая CRITICAL в образе). **Это ОЖИДАЕМОЕ эксплуатационное поведение блокирующей
проверки CVE, а не регрессия продукта.**

Если osv или Trivy становятся красными из-за недавно опубликованной CVE, необходимо:

1. **Обновить затронутую зависимость** (предпочтительно) — перейти на исправленную версию через
   `overrides` в `package.json` (для транзитивных зависимостей) или пересобрать образ на основе исправленного базового образа.
2. **Если исправления от вышестоящего проекта нет:**
   - **osv:** обновить базовое значение `metrics.vulnCount` в `config/quality/quality-baseline.json`
     (`npm run quality:ratchet -- --update` не охватывает отдельные проверки — измените значение
     вручную, `direction:down`), добавив обоснование и ссылку на задачу отслеживания.
   - **Trivy:** добавить запись в `.trivyignore` (по одному CVE-ID на строку), указав обоснование
     в комментарии и ссылку на задачу отслеживания. `ignore-unfixed: true` уже автоматически
     обрабатывает CVE без исправлений.

Обе проверки **корректно ПРОПУСКАЮТСЯ** (код завершения 0), если инструмент отсутствует или измерение
завершается с ошибкой (osv-scanner отсутствует в PATH, osv.dev/сеть недоступны, некорректный JSON) —
сбой **измерения** никогда не приводит к блокировке; блокируется только **измеренная** регрессия.

## В плане: рекомендательная проверка Scorecard → блокирующая

После первого успешного выпуска с отчётом Scorecard:

- Scorecard: ограничитель оценки (фиксирует измеренную оценку; она не может уменьшаться).

Дополняет проверки этапа 7 (osv-scanner, gitleaks, actionlint+zizmor): zizmor
проверяет сами рабочие процессы; Scorecard измеряет состояние репозитория в целом.
