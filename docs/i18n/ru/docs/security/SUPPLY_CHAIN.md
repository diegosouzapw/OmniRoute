OmniRoute публикует артефакты npm и Docker. Эти проверки обеспечивают происхождение,
инвентаризацию (SBOM) и сканирование CVE; все инструменты имеют открытый исходный код
и интегрированы в процессы выпуска.
Позиция **сначала рекомендации** — сейчас проверки только формируют отчёты, а после
первого успешного выпуска станут блокирующими.

| Проверка                 | Инструмент                                     | Где                           | Блокирует?                 | Результат                                      |
| ------------------------ | ---------------------------------------------- | ----------------------------- | -------------------------- | ---------------------------------------------- |
| Происхождение SLSA (npm) | `npm --provenance` (OIDC)                      | `npm-publish.yml`             | только при сбое публикации | значок npmjs / `npm audit signatures`          |
| SBOM npm                 | `@cyclonedx/cyclonedx-npm`                     | `npm-publish.yml`             | только при сбое создания   | ресурс выпуска + артефакт                      |
| SBOM образа              | `anchore/sbom-action` (syft)                   | `docker-publish.yml` (merge)  | рекомендательная           | артефакт CycloneDX                             |
| CVE Trivy (SARIF)        | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | рекомендательная           | SARIF (HIGH+CRITICAL) → вкладка Security       |
| Проверка CRITICAL Trivy  | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | **блокирующая**            | `exit-code: '1'` для исправимых CRITICAL       |
| vulnCount osv            | `osv-scanner` (`check:vuln-ratchet --ratchet`) | `ci.yml` (`quality-extended`) | **блокирующая**            | фиксирует `metrics.vulnCount` (direction:down) |
| OpenSSF Scorecard        | `ossf/scorecard-action`                        | `scorecard.yml` (cron)        | рекомендательная           | SARIF → Security + значок                      |

Пороговая проверка CVE образа использует **два шага** в `docker-publish.yml`: шаг SARIF
(`HIGH,CRITICAL`, `exit-code: 0`) сохраняет видимость HIGH+CRITICAL на вкладке Security,
не блокируя выпуск; шаг _проверки CRITICAL_ (`severity: CRITICAL`, `ignore-unfixed: true`,
`exit-code: 1`) завершает выпуск с ошибкой при наличии CVE уровня CRITICAL, **для которой
доступно исправление**. `ignore-unfixed` предотвращает блокировку выпуска из-за CVE
базового образа, для которой ещё нет исправления от вышестоящего поставщика.

## ⚠️ Вариативность CVE (блокирующие проверки osv/Trivy)

osv и Trivy сопоставляют зависимости с базами данных CVE, которые **постоянно
пополняются**. PR, **не затрагивающий зависимости**, может внезапно стать красным,
поскольку в существующей зависимости была обнаружена новая CVE (osv: измеренное
значение `vulnCount` > базового; Trivy: новая исправимая CRITICAL в образе).
**Это ОЖИДАЕМОЕ рабочее поведение блокирующей проверки CVE, а не регрессия продукта.**

Если osv или Trivy становятся красными из-за недавно опубликованной CVE, выполните
следующее:

1. **Обновите затронутую зависимость** (предпочтительно) — перейдите на исправленную
   версию через `overrides` в `package.json` (для транзитивных зависимостей) или
   пересоберите образ на базе исправленного базового образа.
2. **Если исправления от вышестоящего поставщика нет:**
   - **osv:** обновите базовое значение `metrics.vulnCount` в
     `config/quality/quality-baseline.json` (`npm run quality:ratchet -- --update`
     не распространяется на отдельные проверки — измените значение вручную,
     сохранив `direction:down`), добавив обоснование и ссылку на отслеживающую задачу.
   - **Trivy:** добавьте запись в `.trivyignore` (по одному CVE-ID на строку) с
     комментарием-обоснованием и ссылкой на отслеживающую задачу. `ignore-unfixed: true`
     уже автоматически охватывает CVE, для которых нет исправлений.

Обе проверки **корректно ПРОПУСКАЮТСЯ** (код выхода 0), если инструмент отсутствует
или измерение завершается с ошибкой (`osv-scanner` отсутствует в PATH,
osv.dev/сеть недоступны, недопустимый JSON): сбой **измерения** никогда не блокирует,
блокирует только **измеренная** регрессия.

## Известные принятые риски

### extract-zip 2.0.1 — GHSA-7pqw-9j4j-h8q3 / GHSA-jmr9-qjv8-65gv (#14482)

Для `extract-zip@2.0.1` опубликованы два неисправленных предупреждения высокой степени серьёзности об обходе путей через символические ссылки.
Согласно описанной выше ветви «нет исправления от разработчиков» процедуры обработки отклонений CVE, это
**принятый риск**, а не обновление версии:

- **Цепочка:** `promptfoo` (devDependency) → `@openai/codex-security` → `extract-zip@2.0.1`.
  Подтверждено через `package-lock.json`: ровно один пакет во всём дереве зависимостей
  (`@openai/codex-security`) объявляет `extract-zip`, и ровно один пакет
  (`promptfoo`) объявляет `@openai/codex-security`.
- **Ни для одного звена цепочки не существует выпуска с исправлением.** `extract-zip@2.0.1` (опубликован в 2020 году) — последний выпуск пакета, который больше не поддерживается. Текущая версия npm-latest пакета `@openai/codex-security` (`0.1.29`) по-прежнему подтягивает `extract-zip@2.0.1`.
- **Недоступно из рабочей среды.** `promptfoo` используется только как devDependency (и никогда не указывается
  в разделе `dependencies`), а ни один файл в `src/`, `open-sse/` или `bin/` не импортирует
  npm-пакет `extract-zip` — собственная вспомогательная функция OmniRoute `extractZip()`
  (`src/lib/versionManager/binaryManager.ts:93`) запускает нативные `unzip`/`tar`
  через оболочку и не связана с ним. `@openai/codex-security` также предоставляет собственную защиту
  от обхода путей через символические ссылки поверх обратного вызова onEntry из extract-zip.
- **Не создавайте** псевдоним для `extract-zip` через `overrides` в `package.json` — единственная подходящая
  замена без изменения интерфейса является внутренним пакетом организации Electron и несовместима по API
  с собственными проверками onEntry/defaultDirMode/defaultFileMode пакета `@openai/codex-security`;
  такое переопределение незаметно нарушило бы проверки безопасности этого пакета.
- **Базовый уровень:** измеренное osv значение `vulnCount` (3) уже значительно ниже зафиксированного
  базового уровня (27) из `config/quality/quality-baseline.json` — изменять порог не требуется.
- **Защита от регрессий:** `tests/unit/extract-zip-14482-exposure.test.ts` проверяет указанную выше
  цепочку и инвариант отсутствия импорта в рабочей среде; проверка CI завершится ошибкой, если любой из них
  когда-либо нарушится (например, если будущий PR сделает `extract-zip` доступным из рабочей среды).
- **Отслеживание:** задача #14482.

## Бэклог: предупреждение Scorecard → блокировка

После первого успешного выпуска с отчётом Scorecard:

- Scorecard: порог оценки (фиксирует измеренную оценку; она не может снижаться).

Дополняет проверки этапа 7 (osv-scanner, gitleaks, actionlint+zizmor): zizmor
проверяет сами рабочие процессы; Scorecard измеряет совокупное состояние репозитория.
