OmniRoute публикует артефакты npm + Docker. Эти шлюзы обеспечивают происхождение (provenance), инвентаризацию (SBOM) и сканирование CVE, все они являются OSS и интегрированы в рабочие процессы выпуска. **Принцип "сначала предупреждение"** — они сообщают о проблемах сейчас, а переводят их в блокирующие после первого успешного выпуска.

| Шлюз                  | Инструмент                                     | Где                           | Блокирует?                        | Вывод                                             |
| :-------------------- | :--------------------------------------------- | :---------------------------- | :-------------------------------- | :------------------------------------------------ |
| SLSA provenance (npm) | `npm --provenance` (OIDC)                      | `npm-publish.yml`             | только если публикация не удалась | badge npmjs / `npm audit signatures`              |
| SBOM npm              | `@cyclonedx/cyclonedx-npm`                     | `npm-publish.yml`             | только если генерация не удалась  | Release asset + artifact                          |
| SBOM образа           | `anchore/sbom-action` (syft)                   | `docker-publish.yml` (merge)  | рекомендательный                  | CycloneDX artifact                                |
| Trivy CVE (SARIF)     | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | рекомендательный                  | SARIF (HIGH+CRITICAL) → Security tab              |
| Шлюз Trivy CRITICAL   | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | **блокирующий**                   | `exit-code: '1'` при устранимых CRITICAL          |
| osv vulnCount         | `osv-scanner` (`check:vuln-ratchet --ratchet`) | `ci.yml` (`quality-extended`) | **блокирующий**                   | контролирует `metrics.vulnCount` (direction:down) |
| OpenSSF Scorecard     | `ossf/scorecard-action`                        | `scorecard.yml` (cron)        | рекомендательный                  | SARIF → Security + badge                          |

Механизм контроля CVE для образов использует **два шага** в `docker-publish.yml`: шаг SARIF (`HIGH,CRITICAL`, `exit-code: 0`) делает HIGH+CRITICAL видимыми на вкладке Security, не блокируя выпуск; шаг _CRITICAL gate_ (`severity: CRITICAL`, `ignore-unfixed: true`, `exit-code: 1`) прерывает выпуск при обнаружении CRITICAL CVE **с доступным исправлением**. `ignore-unfixed` предотвращает блокировку выпуска из-за CVE в базовом образе, для которого нет патча от вышестоящего поставщика.

## ⚠️ Отклонения CVE (блокирующие шлюзы osv/Trivy)

osv и Trivy сравнивают зависимости с базами данных CVE, которые **постоянно пополняются**. PR, который **не затрагивает зависимости**, может внезапно стать "красным" из-за нового CVE, обнаруженного в существующей зависимости (osv: измеренный `vulnCount` > базового уровня; Trivy: новый устранимый CRITICAL в образе). **Это ОЖИДАЕМОЕ рабочее поведение блокирующего шлюза CVE, а не регрессия продукта.**

Когда osv или Trivy становятся "красными" из-за недавно обнаруженного CVE, решение следующее:

1.  **Обновить затронутую зависимость** (предпочтительно) — обновить до пропатченной версии через `package.json` `overrides` (для транзитивных зависимостей) или пересобрать образ на пропатченной основе.
2.  **Если нет исправления от вышестоящего поставщика:**
    - **osv:** переустановить базовый уровень `metrics.vulnCount` в `config/quality/quality-baseline.json` (`npm run quality:ratchet -- --update` не охватывает выделенные шлюзы — отредактируйте значение вручную, `direction:down`) с примечанием-обоснованием + задачей отслеживания.
    - **Trivy:** добавить запись в `.trivyignore` (CVE-ID на строку) с комментарием-обоснованием + задачей отслеживания. `ignore-unfixed: true` уже автоматически обрабатывает CVE без патчей.

Оба шлюза **корректно пропускаются** (exit 0), если инструмент отсутствует или измерение не удалось (osv-scanner отсутствует в PATH, osv.dev/network недоступен, неверный JSON) — сбой **измерения** никогда не блокирует, блокирует только **измеренная** регрессия.

## Известные принятые риски

### `extract-zip` 2.0.1 — GHSA-7pqw-9j4j-h8q3 / GHSA-jmr9-qjv8-65gv (#14482)

`extract-zip@2.0.1` содержит две неустраненные уязвимости высокой степени серьезности, связанные с обходом символических ссылок.
В соответствии с веткой "нет исправления от upstream" из вышеупомянутого решения CVE Variance, это **принятый риск**, а не обновление:

- **Цепочка:** `promptfoo` (devDependency) → `@openai/codex-security` → `extract-zip@2.0.1`.
  Подтверждено через `package-lock.json` — ровно один пакет во всем дереве зависимостей
  (`@openai/codex-security`) объявляет `extract-zip`, и ровно один пакет
  (`promptfoo`) объявляет `@openai/codex-security`.
- **Во всей цепочке нет исправленного релиза.** `extract-zip@2.0.1` (опубликован в 2020 году) является последним релизом пакета — он не поддерживается. Текущий `npm-latest` (`0.1.29`) `@openai/codex-security` по-прежнему использует `extract-zip@2.0.1`.
- **Недоступно из production.** `promptfoo` является только devDependency (никогда не указывается
  в `dependencies`), и ни один файл в `src/`, `open-sse/` или `bin/` не импортирует
  npm-пакет `extract-zip` — собственный вспомогательный метод `extractZip()` OmniRoute
  (`src/lib/versionManager/binaryManager.ts:93`) вызывает нативные `unzip`/`tar`
  и не связан с этим. `@openai/codex-security` также поставляет собственную защиту от обхода символических ссылок
  поверх колбэка `onEntry` `extract-zip`.
- **Не следует** использовать псевдоним для `extract-zip` через `overrides` в `package.json` — единственная жизнеспособная
  замена является внутренней для Electron-org и несовместима по API с
  собственными проверками `onEntry`/`defaultDirMode`/`defaultFileMode` `@openai/codex-security`;
  переопределение привело бы к незаметному нарушению проверок безопасности этого пакета.
- **Базовый уровень:** измеренное значение `vulnCount` (3) `osv` уже значительно ниже замороженного
  базового уровня `config/quality/quality-baseline.json` (27) — изменение "храповика" не требуется.
- **Защита от регрессии:** `tests/unit/extract-zip-14482-exposure.test.ts` подтверждает
  цепочку и вышеупомянутый инвариант отсутствия импорта в production; он приводит к сбою CI, если что-либо из этого
  когда-либо нарушается (например, будущий PR делает `extract-zip` доступным из production).
- **Отслеживание:** issue #14482.

## Бэклог: Рекомендация Scorecard → блокировка

После первого "зеленого" релиза с отчетами Scorecard:

- Scorecard: фиксация оценки (замораживает измеренную оценку; не может уменьшаться).

Дополняет шлюзы Фазы 7 (osv-scanner, gitleaks, actionlint+zizmor): zizmor
проверяет сами рабочие процессы; Scorecard измеряет общее состояние репозитория.
