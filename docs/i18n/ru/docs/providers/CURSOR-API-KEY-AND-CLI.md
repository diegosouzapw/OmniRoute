Два способа использовать Cursor через OmniRoute без сессии IDE:

1. **Провайдер `cursor-api`** (карточка «Cursor API», псевдоним `cua`): провайдер
   с API-ключом, который хранит пользовательский API-ключ Cursor (`crsr_…`,
   созданный на странице `https://cursor.com/dashboard/api`). После этого любой
   клиент OmniRoute может обращаться к моделям Cursor через
   `/v1/chat/completions` как к `cursor-api/<model>` или `cua/<model>`, используя
   стандартные механизмы квот, резервного переключения и журналирования.
   Провайдер IDE (`cursor`, OAuth/сессия IDE) остаётся без изменений.
2. **Сквозное проксирование Cursor CLI**: настройте Cursor CLI (`agent`) на
   работу через OmniRoute, чтобы каждый RPC-вызов CLI аутентифицировался
   API-ключом OmniRoute, перенаправлялся в Cursor с учётными данными подключения
   `cursor-api` и записывался на странице журналов.

## Зачем выполняется обмен ключа

`api2.cursor.sh` отклоняет необработанный ключ `crsr_…`, переданный как Bearer-токен
(401). Сначала Cursor CLI отправляет ключ методом POST на
`/auth/exchange_user_api_key` и получает JWT сеанса, срок действия которого
истекает через один час; возвращаемый `refreshToken` содержит такое же значение
`exp`, поэтому для обновления необходимо повторно обменять ключ.
`open-sse/services/cursorApiKeyAuth.ts` выполняет этот обмен, кэширует один токен
сеанса для каждого ключа, повторно обменивает его за пять минут до истечения
срока действия и удаляет кэшированный токен, когда Cursor отвечает кодом 401.
`CursorExecutor` вызывает его непосредственно перед открытием восходящего потока
для подключений `cursor-api`.

## Провайдер `cursor-api`

Реестр: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"`, те же `format`, `baseUrl` и
`models`, что и у `cursor`). Карточка каталога:
`src/shared/constants/providers/apikey/specialty-media.ts`. Карта исполнителей:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`).

Панель управления: Провайдеры → Cursor API → Добавить API-ключ.

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

Затем:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

Примечания:

- Список моделей для `cursor-api` берётся из статического реестра Cursor (того
  же списка, который провайдер IDE использует в качестве резервного); установка
  `cursor-agent` на хосте OmniRoute не требуется.
- `POST /api/providers/{id}/refresh-cursor` предназначен только для провайдера
  Cursor IDE `cursor`; у подключений `cursor-api` нет сессии IDE, которую нужно
  продлевать.

## Сквозное проксирование Cursor CLI

Маршрут: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`. Префикс `/api/cursor-cli/`
зарегистрирован в `src/shared/constants/publicApiRoutes.ts`, поскольку обработчик
самостоятельно обеспечивает аутентификацию:

| Путь                                                                                                                          | Ожидаемая от CLI аутентификация | Действия OmniRoute                                                                                                                                                                           |
| ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                            | `Bearer <OmniRoute API key>`    | Проверяет ключ, выпускает JWT HS256 со сроком действия 1 час (подписанный с помощью `JWT_SECRET`) и возвращает его                                                                           |
| любой другой путь (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`             | Проверяет издателя, аудиторию и срок действия, выбирает активное подключение `cursor-api`, заменяет заголовок Authorization на обменянный токен Cursor и возвращает ответ в потоковом режиме |

CLI декодирует `exp` из любого полученного токена, поэтому при передаче ему
непрозрачного токена он будет выполнять повторный обмен почти перед каждым
запросом; выпущенный JWT позволяет этого избежать. Ответ 401 от OmniRoute
заставляет CLI снова выполнить обмен.

### Настройка

1. Создайте API-ключ OmniRoute (Панель управления → API-ключи) и подключение
   `cursor-api`.
2. Настройте CLI на использование HTTP/1.1 для потока агента. В файле
   `~/.cursor/cli-config.json`:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   Без этой настройки CLI открывает обращение к агенту по HTTP/2 через отдельно
   настроенный хост агента, и через конечную точку проходят только RPC-вызовы
   управляющего уровня.

3. Запустите CLI через OmniRoute:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

Каждый переход попадает в журналы с провайдером `cursor-api`, типом запроса
`cursor-cli` и путём `/api/cursor-cli/<rpc>`, с привязкой к API-ключу OmniRoute
и обслужившему запрос подключению.

### Режимы отказа

| Ситуация                                            | Ответ для CLI                                        |
| --------------------------------------------------- | ---------------------------------------------------- |
| Неизвестный ключ OmniRoute и `REQUIRE_API_KEY=true` | 401 `unauthenticated` при обмене                     |
| `REQUIRE_API_KEY=false`                             | анонимная сессия (аналогично поведению `/v1/*`)      |
| Истёкший / сторонний / изменённый JWT сессии        | 401, CLI повторно выполняет обмен                    |
| API-ключ OmniRoute отозван после обмена             | 401 при следующем RPC                                |
| Нет активного подключения `cursor-api`              | 503 `unavailable`                                    |
| Cursor отклоняет ключ подключения                   | 401 `unauthenticated`, кешированная сессия удаляется |
| Вышестоящий сервис недоступен                       | 502 `unavailable` (сообщение очищено)                |
| `JWT_SECRET` не задан                               | 503 при обмене                                       |
