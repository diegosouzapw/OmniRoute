## Автоматическая маршрутизация без настройки (префикс `auto/`)

> **НОВОЕ:** Создавать комбинацию не требуется. Используйте префикс `auto/` напрямую в любом клиенте.

### Краткие примеры

| ID модели      | Вариант | Поведение                                                                               |
| -------------- | ------- | --------------------------------------------------------------------------------------- |
| `auto`         | default | Все подключённые провайдеры, стратегия LKGP, сбалансированные веса                      |
| `auto/coding`  | coding  | Приоритет качества, подходит для генерации кода                                         |
| `auto/fast`    | fast    | Взвешенный выбор с низкой задержкой                                                     |
| `auto/cheap`   | cheap   | Маршрутизация с оптимизацией стоимости (сначала минимальная стоимость)                  |
| `auto/offline` | offline | Предпочтение провайдерам с наибольшим доступным объёмом квоты                           |
| `auto/smart`   | smart   | Приоритет качества + повышенная доля исследования (10%) для лучшего обнаружения моделей |
| `auto/lkgp`    | lkgp    | Явный LKGP (аналогично `auto` по умолчанию)                                             |
| `auto/chaos`   | chaos   | Веса для внедрения сбоев при тестировании отказоустойчивости (хаос-инжиниринг)          |

### Композиция «категория × уровень» (`auto/<category>:<tier>`)

Суффиксы в стиле OpenRouter отделяют **тип маршрута** (категорию) от **способа его оптимизации** (уровня), позволяя свободно комбинировать их (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **Категории** (фильтруют пул кандидатов по возможностям): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` оставляют модели с поддержкой изображений; `reasoning` оставляет модели с возможностями рассуждения/мышления.
- **Уровни** (задают веса оценки / фильтр пула): `fast` (максимальная скорость) · `cheap` (псевдоним `floor`, экономия затрат) · `reliable` (состояние автоматического выключателя + стабильность задержки) · `free` / `pro` (фильтрация пула по уровню модели с помощью `classifyTier` — бесплатный или премиальный уровень).

| Пример                 | Результат разрешения                                                            |
| ---------------------- | ------------------------------------------------------------------------------- |
| `auto/coding:fast`     | пул для программирования, веса с приоритетом низкой задержки                    |
| `auto/coding:cheap`    | пул для программирования, оптимизация стоимости (псевдоним `auto/coding:floor`) |
| `auto/reasoning:pro`   | только модели рассуждения/мышления, премиальный уровень                         |
| `auto/vision`          | модели с поддержкой изображений (без уровня → сбалансированные веса)            |
| `auto/multimodal:free` | модели с мультимодальными возможностями, только бесплатный уровень              |

Любой допустимый `auto/<category>[:<tier>]` разрешается по запросу; тщательно отобранное подмножество публикуется в `/v1/models` и на панели управления (`AUTO_SUFFIX_VARIANTS` в `open-sse/services/autoCombo/builtinCatalog.ts`). Фильтрация работает по принципу **fail-open** — если ограничению не соответствует ни одна подключённая модель, используется полный пул, поэтому маршрутизация никогда не нарушается. Основной механизм оценки (`combo.ts`) остаётся неизменным; фильтр категории/уровня применяется в `buildAutoCandidates`.

> **Актуальные сведения о моделях:** пригодность моделей для автоматической маршрутизации определяется с учётом актуальных рейтингов **Arena ELO** и данных об уровнях из **models.dev**, когда включён флаг `ARENA_ELO_SYNC_ENABLED` (иначе используется статическая карта пригодности).

**Как использовать:**

```bash
# Любая IDE или инструмент CLI, поддерживающий формат OpenAI
Базовый URL: http://localhost:20128/v1
Ключ API:    <your-endpoint-key>

# В коде/конфигурации задайте модель:
model: "auto"                 # сбалансированный вариант по умолчанию
model: "auto/coding"          # лучший вариант для задач программирования
model: "auto/fast"            # самый быстрый из доступных
model: "auto/cheap"           # самый дешёвый на токен
```

**Что происходит:**

1. OmniRoute обнаруживает префикс `auto/` в `src/sse/handlers/chat.ts`
2. Запрашивает из базы данных все **активные подключения к провайдерам**
3. Оставляет только подключения с действительными учётными данными (ключом API или токеном OAuth)
4. Определяет модель для каждого подключения (`connection.defaultModel` или первая модель провайдера)
5. Создаёт **виртуальную комбинацию** в памяти (без сохранения в БД)
6. Выполняет маршрутизацию с использованием профиля весов выбранного варианта и стратегии LKGP

**Ключевые свойства:**

- ✅ **Всегда включено:** Не требуются переключатель, создание комбинации или настройка
- ✅ **Динамичность:** Автоматически учитывает текущих подключённых провайдеров
- ✅ **Привязка к сеансу:** LKGP обеспечивает приоритет последнего успешно использованного провайдера
- ✅ **Поддержка нескольких учётных записей:** Каждое подключение к провайдеру становится отдельным кандидатом
- ✅ **Без записи в БД:** Виртуальная комбинация существует только в рамках запроса, без накладных расходов на постоянное хранение

### Управление кандидатами для отдельных ключей (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = суффикс после `auto/` или
буквальное значение `auto` для базового канала) — это конечная точка **только для чтения**, которая выводит
текущий пул кандидатов канала `auto/*` вместе с актуальными данными о доступности, повторно используя
существующие механизмы чтения состояния отказоустойчивости (но не необработанное поле `state` автоматического выключателя):

- автоматический выключатель провайдера — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- период ожидания подключения — `rateLimitedUntil` / `testStatus` в разрешённой строке
  `provider_connections`
- блокировка модели — `isModelLocked(provider, connectionId, model)`

Каждый кандидат также содержит флаг `excluded` для данного ключа API. Исключения сохраняются
отдельно для каждого ключа API (таблица `auto_candidate_overrides`, миграция `128`) — OmniRoute
является однопользовательской системой без таблицы `users`, поэтому `apiKeyId` служит ближайшим реальным
идентификатором вызывающей стороны — и применяются в точке ограничения пула кандидатов в
`open-sse/services/autoCombo/virtualFactory.ts` через чистую, покрытую модульными тестами функцию
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`).
Фильтр работает по принципу **fail-open**: отсутствие apiKeyId/канала или ошибка запроса к БД
оставляют пул неотфильтрованным, поэтому для оператора без настроенных переопределений результат маршрутизации
побайтово идентичен поведению до появления этой функции.

**Отложено до следующей задачи:** веса для отдельных кандидатов + явное упорядочивание (уровень 3
— интегрируется с существующими путями взвешенной/приоритетной стратегии), а также закрепление конкретной
стратегии `combo.ts` за каждым каналом `auto/*` (уровень 4). В плане #7819 рассматривается открытый
вопрос о том, должны ли переопределения оставаться привязанными к API-ключу или стать глобальными с учётом
однотенантной модели.

**Внутреннее устройство:**

```txt
Запрос: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts обнаруживает префикс
   ↓
createVirtualAutoCombo('coding') → candidatePool из активных подключений
   ↓
handleComboChat (тот же механизм, что и для сохранённых комбинаций)
   ↓
Автоматическая оценка выбирает лучшего провайдера/модель для каждого запроса
```

## Имена комбинаций, совпадающие с идентификатором реальной модели

Комбинация, `name` которой совпадает с простым идентификатором модели (например, комбинация с именем
`gpt-5.5`), — это **предусмотренный и поддерживаемый шаблон**, а не ошибка: это
механизм резервного переключения между провайдерами для конкретного идентификатора модели, описанный в
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940). Поскольку разрешение
комбинаций проверяется до разрешения простого идентификатора модели
(`getComboForModel()` в `src/sse/services/model.ts`), запрос к простому
идентификатору `gpt-5.5` направляется через целевые модели комбинации (например,
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`), а не напрямую
к одному провайдеру — при этом повторно используется приоритет комбинации перед перезаписью, реализованный для
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) и
покрытый регрессионными тестами `tests/unit/responses-combo-resolution-3227.test.ts` и
`tests/unit/combo-name-codex-responses-rewrite.test.ts`.

Создание или переименование комбинации таким образом, что её имя затеняет идентификатор реальной модели,
**никогда не отклоняется** — это нарушило бы работу описанного процесса. Вместо этого
(#8530) `POST /api/combos` и `PUT /api/combos/[id]` добавляют в ответ неблокирующее
поле `warning`, когда новое имя конфликтует с идентификатором реальной
модели:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

При запуске `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) также записывает в журнал однострочное предупреждение `[STARTUP]`,
перечисляющее все существующие комбинации, затеняющие идентификатор модели, чтобы операторы,
столкнувшиеся с этим случайно (а не намеренно, как описано в #6940), получили соответствующий сигнал.
Вспомогательная функция обнаружения находится в `src/lib/combos/modelNameCollision.ts`.

## Вызов пользовательской комбинации из клиента

Сохранённые комбинации (Настройки → Комбинации) используются только в том случае, если клиент передаёт **точное имя** комбинации в поле `model` — нечёткое или частичное сопоставление имени комбинации не выполняется, и префикс `auto/` не используется. Порядок разрешения (`getComboForModel()` в `src/sse/services/model.ts`):

1. точное совпадение с именем комбинации (`model: "my-combo"`),
2. префикс `combo/<name>` (`model: "combo/my-combo"`),
3. сопоставления моделей с комбинациями по glob-шаблонам (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

Две распространённые ошибки:

- **`auto` не использует ваши комбинации.** `auto`/`auto/*` формирует собственный пул кандидатов, не требующий настройки, и обращается к сохранённым комбинациям, только если одна из них буквально называется `auto` (не рекомендуется). Чтобы направить запрос через комбинацию, передавайте её точное имя, а не `auto`.
- **`openrouter/auto` — это реальный платный продукт OpenRouter** («Автоматический выбор лучшей доступной модели»), а не псевдоним OmniRoute. Это единственная статическая запись модели в реестре OpenRouter (`open-sse/config/providers/registry/openrouter/index.ts`), и она оплачивается отдельно. Используйте Настройки → Маршрутизация → Скрывать платные модели, чтобы исключить её из пулов `auto`.

См. [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) и [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111), где описана исходная путаница, проясняемая этой документацией.

## Как это работает (сохраняемые автокомбинации)

Механизм Auto-Combo динамически выбирает лучшего поставщика и модель для каждого запроса с помощью **16-факторной функции оценки** (определённой в `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`). Сумма весов по умолчанию равна `1.0`; пользовательские веса повторно нормализуются функцией `normalizeScoringWeights()`. Два фактора из шестнадцати — `cacheAffinity` и `resetWindowAffinity` — имеют вес по умолчанию `0`; вес `reliability` равен `0` в `DEFAULT_WEIGHTS`, но составляет `0.03` в общих наборах и `0.04` в `reliability-first`, а вес `quality` в наборах составляет `0.02` (`0.03` в `quality-first`). При этом они всё равно вычисляются для каждого кандидата, а `cacheAffinity` управляет дедупликацией кэша промптов вне функции оценки, поэтому факторы с нулевым весом по умолчанию просто не влияют на итоговую оценку, тогда как в наборах они учитываются.

![16-факторная оценка Auto-Combo](../diagrams/exported/auto-combo-scoring.svg)

> Источник: [diagrams/auto-combo-scoring.mmd](../diagrams/auto-combo-scoring.mmd) (для повторной генерации выполните `npm run docs:render-diagrams`). Имя файла сохранено по историческим причинам; в исходном и отрисованном вариантах диаграммы показаны все 16 факторов, объявленных в `DEFAULT_WEIGHTS`.

| Фактор                | Вес по умолчанию | Описание                                                                                                                                                                                                                                                                                |

### Семантика `weighted`

`weighted` выполняет **пропорциональный случайный выбор для каждого запроса**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), а не выравнивание:

- Для каждого запроса выбирается **один** этап с вероятностью `weight / totalWeight`; остальные этапы
  упорядочиваются по убыванию веса и образуют резервную цепочку для этого запроса.
- Этап с весом `0` (или без указанного веса) **никогда не выбирается**, пока у любого другого этапа
  вес > 0 — он может использоваться только как резервный вариант после сбоя выбранного этапа. Выбор
  становится равномерным, только когда **все** веса равны 0.
- Этапы, все цели которых недоступны — автоматический выключатель провайдера находится в состоянии `OPEN`,
  подключение временно заблокировано или модель заблокирована, — удаляются из выборки до выполнения выбора
  (`open-sse/services/combo/targetResolution.ts`), поэтому единственный работоспособный этап может временно
  выбираться для каждого запроса.
- `stickyWeightedLimit` (настройка комбинации, по умолчанию `1` = отключено) закрепляет выбранный этап
  на указанное количество последовательных успешных запросов перед повторным выбором.

Для строгого чередования используйте `round-robin`; одинаковые веса при использовании `weighted`
обеспечивают статистический, а не строгий баланс.

## Стратегия Fusion

`fusion` — единственная стратегия, которая **не** выбирает одну целевую модель. Она параллельно отправляет запрос **каждой модели панели**, после чего настраиваемая **модель-судья** синтезирует единый окончательный ответ из всех ответов панели. Перенесена из исходного проекта `decolua/9router` (реализация Fusion от OpenRouter); реализация находится в `open-sse/services/fusion.ts`.

Как это работает:

0. **Обход панели для запросов с инструментами** — запрос, содержащий непустой массив `tools`, если `tool_choice` явно не задан как `"none"`, полностью минует панель: он направляется непосредственно одной модели (настроенному судье или `panel[0]`) с передачей `tools`/`tool_choice` без изменений. Участники панели не имеют доступа к инструментам, а инструкция судье по синтезу не рекомендует генерировать вызовы инструментов, поэтому агентные клиенты и клиенты, вызывающие инструменты, получают настоящее решение о вызове инструмента вместо синтезированного текста (#6771).
1. **Параллельная рассылка** (только для запросов без инструментов) — запрос одновременно отправляется каждой модели панели в принудительно непотоковом режиме и без инструментов (для синтеза судье необходимы полные текстовые ответы).
2. **Сбор с кворумом и льготным периодом** — как только поступает `minPanel` ответов, запускается короткий таймер льготного периода для отстающих моделей, после чего объединение продолжается со всеми ответами, которые удалось собрать. Это ограничивает влияние самой медленной модели на общее время выполнения, которое также ограничено жёстким тайм-аутом.
3. **Синтез судьёй** — ответы панели анонимизируются (`Source 1`, `Source 2`, … — чтобы судья оценивал содержание, а не бренд модели) и передаются судье, который анализирует консенсус / противоречия / частичный охват / уникальные выводы / слепые зоны, а затем формирует **один** авторитетный ответ. Вызов судьи сохраняет исходный флаг клиента `stream` и инструменты, поэтому потоковая передача и последующее использование инструментов продолжают работать.
4. **Плавная деградация** — 0 ответов панели → `503`; ровно 1 уцелевший ответ → он возвращается напрямую (объединять нечего); панель из одной модели отвечает напрямую.

Участником панели также может быть шаг `combo-ref` (`{kind: "combo-ref", comboName: "..."}`), ссылающийся на другую комбинацию, — он обрабатывается как **один изолированный голос панели** (полная рекурсивная диспетчеризация в указанную комбинацию, а не параллельная рассылка по собственным целевым моделям этой комбинации) с той же защитой от чрезмерной глубины и циклов, которая уже применяется всеми другими стратегиями, использующими combo-ref (#6764).

### Конфигурация

Настраивается в объекте `config` комбинации (миграция схемы не требуется — повторно используется существующая таблица `combos`):

| Поле                                     | Тип      | Значение по умолчанию | Назначение                                                                                                          |
| :--------------------------------------- | :------- | :-------------------- | :------------------------------------------------------------------------------------------------------------------ |
| `config.judgeModel`                      | `string` | первая модель панели  | Модель, синтезирующая окончательный ответ                                                                           |
| `config.fusionTuning.minPanel`           | `number` | `2`                   | Количество успешных ответов, необходимое для запуска льготного таймера (ограничивается диапазоном `[2, panelSize]`) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`                | Время ожидания отстающих моделей после достижения кворума                                                           |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`               | Абсолютный предел, не позволяющий одной зависшей модели задержать запрос                                            |

Значения по умолчанию находятся в `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`).

## Виртуальная фабрика Auto-Combo

Движок Auto Combo не требует предварительно определённых комбо. Вместо этого `open-sse/services/autoCombo/virtualFactory.ts` формирует кандидатов на лету:

1. Получает `getProviderConnections({ isActive: true })` (все включённые подключения)
2. Оставляет подключения с действительными учётными данными (API-ключом или непросроченным OAuth-токеном, проверяемым через `hasUsableOAuthToken()`)
3. Сопоставляет их с `getProviderRegistry()` для определения доступности моделей и цен
4. Для каждого кортежа `(provider, model, connection)` создаёт `VirtualAutoComboCandidate`
5. Выбирает `connection.defaultModel` (или первую модель из реестра) в качестве цели маршрутизации
6. Оценивает каждого кандидата с помощью 16-факторной функции `scorePool()` и набора весов варианта
7. Возвращает получившуюся хранящуюся в памяти конфигурацию `AutoComboConfig` для `handleComboChat()` — она никогда не сохраняется в БД

Это означает, что **добавление нового провайдера с включённым `auto/*` автоматически расширяет пул кандидатов** — вручную редактировать комбо не требуется. Виртуальный комбо создаётся заново для каждого запроса, поэтому недавно добавленные или восстановившие работоспособность подключения используются немедленно.

## Самовосстановление

- **Временное исключение**: оценка < 0.2 → исключение на 5 мин (прогрессивная задержка, максимум 30 мин)
- **Учёт автоматического выключателя**: OPEN → автоматическое исключение; HALF_OPEN → пробные запросы
- **Режим инцидента**: >50% OPEN → отключить исследование, максимизировать стабильность
- **Восстановление после периода ожидания**: после исключения первый запрос является «пробным» и выполняется с уменьшенным тайм-аутом

## Исследование методом многорукого бандита

5% запросов (значение настраивается) направляются случайным провайдерам для исследования. Отключается в режиме инцидента.

## API

**Выделенной конечной точки `POST /api/combos/auto` не существует** — Auto-Combo используется двумя способами:

1. **Без конфигурации (рекомендуется):** отправьте любой запрос на генерацию ответа в чате с `model: "auto"` или `model: "auto/<variant>"`. Виртуальная фабрика создаёт комбо для каждого запроса — сохранение и вызовы API не требуются.

2. **Сохраняемый комбо со `strategy: "auto"`:** создайте обычный комбо через `POST /api/combos` и задайте `strategy: "auto"`, а также `config.auto.weights` / `config.auto.candidatePool`. Используется тот же механизм оценки; комбо сохраняется в `combos` и может повторно использоваться по идентификатору.

Для обнаружения `GET /api/combos/auto` выводит каждый вариант вместе с разрешённым пулом кандидатов, а также `context_length` / `max_output_tokens` — МАКСИМАЛЬНЫЕ значения среди контекстных окон пула кандидатов. Клиенты (например, плагин opencode) должны указывать эти значения вместо `0`: нулевой размер контекста полностью отключает автоматическое уплотнение в opencode, позволяя сессиям расти до тех пор, пока очистка истории на шлюзе не уничтожит контекст. Указывать МАКСИМАЛЬНОЕ значение безопасно, поскольку предварительный фильтр контекста auto-combo направляет слишком большие запросы кандидатам с большим контекстным окном.

```bash
# Использование без конфигурации (создание комбо не требуется)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Сохраняемый автоматический комбо через обычную конечную точку combos
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Стратегии автоматического маршрутизатора

Сохраняемые комбо со `strategy: "auto"` могут задавать для `config.routerStrategy` (или устаревшего
`config.auto.routerStrategy`) одно из следующих значений:

- `rules` — взвешенная оценка по умолчанию
- `score` — выбирает наивысшую настроенную взвешенную оценку. При полном равенстве сохраняется настроенный
  порядок кандидатов; существующий параметр `explorationRate` выполняет выборку из полного ранжированного пула.
- `cost` / `eco` — самый дешёвый работоспособный провайдер
- `latency` / `fast` — самая низкая задержка p95 со штрафом за ненадёжность
- `sla-aware` / `sla` — отдаёт предпочтение кандидатам, удовлетворяющим целевым показателям SLO по задержке p95, частоте ошибок и, при необходимости,
  стоимости
- `lkgp` — сначала последний известный работоспособный провайдер

### Подробное описание стратегий маршрутизатора

Движок auto-combo предоставляет 6 подключаемых реализаций **RouterStrategy**, которые
можно переключать через `config.routerStrategy` (или устаревший `config.auto.routerStrategy`).
Каждая стратегия выбирает одного провайдера из пула кандидатов с учётом `RoutingContext`
(типа задачи, признаков использования инструментов/изображений, оценки количества токенов, необязательной политики SLA и необязательного
последнего известного работоспособного провайдера).

#### 1. `rules` (по умолчанию) — 16-факторная взвешенная оценка

Оборачивает существующий механизм оценки. Отфильтровывает кандидатов с автоматическим выключателем в состоянии `OPEN`,
затем запускает `scorePool()` с текущим типом задачи и `getTaskFitness()`,
выбирая провайдера с наивысшей оценкой.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**Когда использовать**: по умолчанию. Используйте, если требуется сбалансированный компромисс между всеми сигналами.

**Псевдоним**: `rules` (без псевдонима)

---

#### 2. `cost` / `eco` — самый дешёвый работоспособный провайдер

Сортирует пул кандидатов по `costPer1MTokens` (по возрастанию) и выбирает самого дешёвого.
Сначала отфильтровывает кандидатов в состоянии `OPEN`.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Когда использовать**: чувствительные к стоимости рабочие нагрузки, пакетная обработка или фоновые задачи.

**Псевдонимы**: `cost`, `eco`

---

#### 3. `latency` / `fast` — самая низкая задержка p95 со штрафом за ненадёжность

Сортирует по `p95LatencyMs + (errorRate * 1000)`. Штраф за частоту ошибок гарантирует,
что ненадёжные провайдеры ранжируются ниже, даже если их номинальная задержка мала.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Когда использовать**: рабочие нагрузки, чувствительные к задержке, такие как чаты в реальном времени, автодополнение или
интерактивные ассистенты для программирования.

**Псевдонимы**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — соответствие SLO по задержке/ошибкам/стоимости

Оценивает каждого кандидата по тому, насколько хорошо он соответствует настроенной политике SLO:

| Фактор                   | Вес | Формула                                                           |
| ------------------------ | --- | ----------------------------------------------------------------- |
| Оценка задержки          | 35% | `threshold / max(value, ε)`                                       |
| Оценка ошибок            | 35% | `threshold / max(value, ε)`                                       |
| Оценка работоспособности | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)                 |
| Оценка стоимости         | 10% | `threshold / max(value, ε)` или обратная нормализованная величина |
| Оценка стабильности      | 5%  | обратное нормализованное стандартное отклонение задержки          |

При `hardConstraints: true` кандидаты сортируются в первую очередь по **оценке нарушения**
(насколько сильно они превышают какой-либо SLO), а затем по составной оценке. В противном случае используется только
составная оценка.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... оценивает каждого кандидата в соответствии с политикой: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**Поля SLA** (задаются в конфигурации комбинации):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**Когда использовать**: производственные рабочие нагрузки со строгими ограничениями по задержке, частоте ошибок или стоимости.

**Псевдонимы**: `sla-aware`, `sla`

---

#### 5. `lkgp` — последний успешно работавший провайдер в первую очередь

Сначала пробует **последнего успешно работавшего провайдера** (если он задан), а затем переключается на
стратегию `rules`. Полезно для привязки сеанса — один и тот же провайдер обрабатывает
последующие запросы в диалоге.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Переключение на стратегию rules
    return getStrategy("rules").select(pool, context);
  }
}
```

**Когда использовать**: многоходовые диалоги, в которых один и тот же провайдер должен обрабатывать
последующие запросы (например, для кэширования, непрерывности контекста или согласованности ценообразования).

**Псевдоним**: `lkgp` (без псевдонима)

### Пользовательские стратегии маршрутизации

Через публичный API можно зарегистрировать собственную реализацию `RouterStrategy`:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Здесь находится ваша логика маршрутизации
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

Затем используйте её:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## Обзор вариантов Auto

Включая базовый `auto` (по умолчанию) и 6 значений `AutoVariant`, объявленных в `autoPrefix.ts`, существует **7 доступных для вызова идентификаторов моделей**:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` перечисляет 6 значений; 7-й вариант — «без варианта», то есть базовый `auto`, — обрабатывается `parseAutoPrefix()` как `variant: undefined`.)

## Как уровни связаны с Auto-Combo

Функция оценки с 16 факторами (`open-sse/services/autoCombo/scoring.ts`) рассматривает принадлежность к уровню как два сигнала: `tierPriority` (0.0476) и `tierAffinity` (0.0476). Полный набор `DEFAULT_WEIGHTS` приведён выше в канонической [таблице факторов оценки](#how-it-works-persisted-auto-combos), а переопределения для каждого набора (ship-fast/cost-saver/quality-first/offline-friendly) перечислены в таблице «Профили весов для каждого набора».

Сам по себе уровень **не** гарантирует, что Tier 1 будет выбран первым: если задержка Tier 1 слишком велика или соотношение стоимости и качества неоптимально, побеждает Tier 2. Чтобы принудительно задать порядок уровней, используйте стратегию комбинации `priority` и расположите провайдеров в соответствии с уровнями.

Чтобы явно отдать предпочтение Tier 1 (подписка), увеличьте вес `tierPriority`:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

Определения уровней и классификацию провайдеров см. в `docs/marketing/TIERS.md`.

Эти проверки работоспособности тестируют реальный сетевой путь (комбинация → провайдер → завершение). Они намеренно исключены из CI, поскольку требуют действующих учётных данных и доступа к VPS.
