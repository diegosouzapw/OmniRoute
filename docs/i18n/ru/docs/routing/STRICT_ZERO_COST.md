> Требует явного включения, по умолчанию отключено (`settings.freeAccessPolicy !== "strict"` оставляет каждый
> пул кандидатов `auto/*` побайтово идентичным). Более строгий аналог `hidePaidModels`
> (`open-sse/services/autoCombo/paidModelFilter.ts`, #6512) для операторов, которым нужна жёсткая
> гарантия отсутствия ЛЮБЫХ дополнительных денежных расходов, а не только статуса «задокументировано как бесплатное».

## Зачем это нужно и почему одного `hidePaidModels` недостаточно

`hidePaidModels` отвечает на вопрос «классифицируется ли эта модель как бесплатная в `FREE_MODEL_BUDGETS` прямо сейчас?» —
это факт каталога на конкретный момент времени, проверяемый через `isFreeModel()`/`providerHasFreeModels()`
(`src/shared/utils/freeModels.ts`). Он ничего не говорит о двух реальных рисках:

1. Лимит бесплатного тарифа `recurring-*`/`one-time-initial` может быть **исчерпан** — в каталоге
   модель по-прежнему указана как бесплатная, но у связанной с ней учётной записи больше нет доступного остатка.
2. Превышение лимита бесплатного тарифа не всегда приводит к жёсткой блокировке. Некоторые провайдеры прямо
   указывают, что способ оплаты вообще невозможно привязать («кредитная карта не требуется»); другие ничего
   об этом не говорят, а некоторые автоматически выставляют счёт после исчерпания бесплатного лимита.

`hidePaidModels` не может различать эти случаи — он никогда для этого и не предназначался. STRICT_ZERO_COST добавляет именно
эти две проверки, выполняемые для каждого кандидата **до** ранжирования по категории/уровню и **до**
отправки запроса — и никогда после того, как запрос уже был отправлен.

## Классификация кандидатов

Для каждого кандидата в пуле (`open-sse/services/autoCombo/virtualFactory.ts::buildPreparedPool`,
сразу после `filterPaidOnlyCandidates`):

1. **Полностью отсутствует в `FREE_MODEL_BUDGETS`** → исключается. Это относится к действительно платным моделям и любым
   провайдерам/моделям, которые OmniRoute ещё не классифицировал, — новые кандидаты изначально исключаются, а не включаются.
2. **`freeType: "keyless"`** → сразу проходит, **но только если кандидат действительно
   поступил через путь без аутентификации** (`connectionId === SYNTHETIC_NOAUTH_CONNECTION_ID`,
   `open-sse/services/autoCombo/resilienceCandidateFilter.ts`). У такого
   кандидата нет учётных данных, поэтому запрос к нему никогда не может повлечь оплату — проверка во время выполнения не нужна
   и невозможна. Тот же указанный в каталоге провайдер/модель с типом `keyless`, доступ к которому осуществляется через **реальное**
   подключение из БД (`connectionId` содержит фактический идентификатор подключения либо кандидат содержит
   `allowedConnectionIds`), **не** получает этого послабления — метаданные `keyless` описывают
   именно путь без аутентификации, а не провайдера в целом, и никогда не разрешают использование реальной
   учётной записи с учётными данными. Такой кандидат переходит к проверке 3, как и любой другой, где он
   исключается, если только запись каталога отдельно не содержит `hardStopGuaranteed: true` (реальные
   записи `keyless` никогда его не содержат — это послабление было для них единственным способом считаться безопасными).
3. **Любой другой `freeType`** (`recurring-daily`, `recurring-monthly`, `recurring-credit`,
   `recurring-uncapped`, `one-time-initial` и любой будущий тип, который этот модуль не
   обрабатывает отдельно) → проходит, только если выполняются **все** следующие условия:
   - В записи каталога установлено `hardStopGuaranteed: true` (`FreeModelBudget.hardStopGuaranteed`,
     `open-sse/config/freeModelCatalog.ts`) — это **отобранный и заданный вручную факт** об опубликованных самим провайдером
     условиях (например, явное заявление «кредитная карта не требуется»), который никогда не выводится из
     `freeType` или ответа API в реальном времени. Неустановленное значение (`undefined`) и `false` одинаково трактуются как
     «гарантии нет».
   - Для провайдера существует адаптер использования в `USAGE_FETCHER_PROVIDERS`
     (`open-sse/services/usage.ts`) — том же реестре, который уже используется панелью квот и
     `getUsageForProvider()`. Нет адаптера → кандидат исключается безусловно, пока адаптер не будет добавлен.
   - Текущее кэшированное значение `FreeAccessState` для **конкретного фактически
     проверяемого подключения** имеет `status: "SAFE"`, было проверено в течение
     `settings.autoRefreshProviderQuotaInterval` (по умолчанию 180s — используется существующая настройка, а не новое
     значение) и сообщает, что `remainingFreeAllowance` превышает небольшой резерв безопасности.
4. **`freeType: "discontinued"`** → всегда исключается.

## Безопасность подключений (проверка каждого подключения, а не каждого кандидата)

Кандидат в пуле автокомбинации не всегда привязан к одному подключению. «Логический» кандидат
(`connectionId: null`) содержит список разрешённых подключений `allowedConnectionIds` — одно или несколько фактических
подключений/аккаунтов провайдера, любое из которых может обслужить запрос, — а фактически используемый аккаунт
определяется позднее, во время отправки, в `open-sse/services/combo/autoStrategy.ts`
(путём пересечения `allowedConnectionIds` с собственной логикой выбора подключения, примерно строки 315–331).

STRICT_ZERO_COST проверяет состояние бесплатного доступа **каждого подключения в этом списке разрешённых
подключений по отдельности** (`evaluateCandidateConnections()` в `strictZeroCostFilter.ts`) и сокращает
`allowedConnectionIds` ровно до того подмножества, для которого был получен результат `SAFE`, — никогда не сохраняя
полный исходный список и не выбирая одного произвольного участника. А именно:

- Аккаунт A — `SAFE`, аккаунт B — `UNKNOWN`/лимит исчерпан/платный → доступным для выбора остаётся только A.
- Все аккаунты — `UNKNOWN` → кандидат полностью исключается (безопасное множество пусто).
- Кандидат с одним подключением (`connectionId` задан напрямую, без списка разрешённых подключений), не прошедший проверку,
  исключается полностью и никогда не возвращается с пустым `allowedConnectionIds`.

Поскольку `autoStrategy.ts` уже обеспечивает применение `allowedConnectionIds` как обязательного списка разрешённых подключений перед
выбором подключения для отправки запроса, сокращения его до проверенного подмножества со статусом `SAFE` достаточно, чтобы
гарантировать: фактически используемое при отправке подключение всегда было проверено самим этим фильтром —
это никогда не будет другой, непроверенный аккаунт того же кандидата. Регрессионное доказательство см. в
`tests/unit/autoCombo/strict-zero-cost-connection-safety.test.ts`
(случаи A/B/C с обходом без ключа, случаи 1–5 с несколькими аккаунтами).

`обнаруживается автоматически`: провайдер/модель, выпущенные завтра с подходящими метаданными (присутствующие в
каталоге, имеющие адаптер учёта использования и `hardStopGuaranteed: true`), становятся доступными сразу после того, как OmniRoute
узнаёт о них, — без изменения кода, без добавления в белый список и без необходимости что-либо редактировать в этом модуле. Удалённый из
каталога элемент исчезает таким же образом. Регрессионное доказательство см. в
`tests/unit/autoCombo/strict-zero-cost-autodiscovery.test.ts` (с использованием
внедряемых фикстур, без изменения реального каталога).

## Кэширование квоты (`open-sse/services/autoCombo/freeAccessQuota.ts`)

Повторно использует `getUsageForProvider()` — без второй системы квот. Перед ним расположен кратковременный,
хранящийся в памяти на протяжении жизненного цикла процесса кэш (TTL равен значению по умолчанию
`autoRefreshProviderQuotaInterval`), поэтому даже частота запросов масштаба Telegram никогда не приводит к выполнению реального
вызова API биллинга для каждого кандидата при каждом запросе. Чтение выполняется синхронно: при промахе кэша возвращается
`undefined` (→ кандидат исключается, безопасный отказ), а в фоновом режиме запускается обновление для _следующего_ чтения —
в процессе построения пула кандидатов нигде не ожидается завершение сетевого вызова.

`invalidateFreeAccessState(provider, connectionId)` вызывается из
`src/sse/services/auth.ts::markAccountUnavailable()` сразу же, как только подключение завершается с ошибкой по любой
причине, поэтому уже при следующем построении пула будет зафиксирован чистый промах кэша, а не устаревшая запись `SAFE`, —
после ответа 402/403/об исчерпании квоты не требуется ждать истечения TTL.

## Защита ToS (независимо от экономической безопасности)

`excludeTosAvoid` (по умолчанию `false`) отбрасывает любого кандидата, для которого вручную задан вердикт `tos`
(`FreeModelBudget.tos`) со значением `"avoid"`, — при этом повторно используется то же поле, которое уже заполняется
в документации, связанной с `hidePaidModels`
(`docs/reference/FREE_TIERS.md`). Эта защита намеренно отделена от
`freeAccessPolicy`: кандидат может быть экономически `SAFE` и всё равно быть исключён здесь
по договорным причинам либо оставлен, когда эта защита отключена, даже если включён параметр `freeAccessPolicy: "strict"`.

## Как увидеть, что исключает защита

`GET /v1/auto-combo/{channel}/candidates` выводит всех кандидатов, включая тех, которых эта защита
не допустила бы к диспетчеризации, и каждый из них содержит `freeAccessExclusion` — `null`, если требования защиты
выполнены, иначе причину исключения. Этот список только сообщает информацию и никогда не применяет ограничения. При отключении политики
поле везде имеет значение `null`, а сама проверка не требует затрат.

| `freeAccessExclusion`  | Что это означает                                                                                                                      | Что с этим делать                                                                                                                        |
| :--------------------- | :------------------------------------------------------------------------------------------------------------------------------------ | :--------------------------------------------------------------------------------------------------------------------------------------- |
| `not-in-catalog`       | Пара «провайдер/модель» отсутствует в `FREE_MODEL_BUDGETS`.                                                                           | Добавьте вручную проверенную запись или примите тот факт, что новые пары изначально исключаются — так и задумано.                        |
| `regime-not-free`      | Пара есть в каталоге, но её `freeType` не предоставляет бесплатного доступа (например, тариф прекращён).                              | Исправлять нечего. Модель стоит денег.                                                                                                   |
| `no-hard-stop`         | Режим бесплатный, но `hardStopGuaranteed` не равно `true`, поэтому превышение лимита может незаметно привести к списанию средств.     | Проверьте условия провайдера и установите флаг, указав источник в комментарии, — но не ради расширения каталога.                         |
| `contradictory-noauth` | Кандидат без аутентификации, запись которого в каталоге не помечена как `keyless`. При несогласованных метаданных доступ блокируется. | Исправьте запись в каталоге: эти два факта противоречат друг другу.                                                                      |
| `exhausted`            | Актуальные данные показывают, что лимит исчерпан.                                                                                     | Дождитесь сброса. Эта проблема разрешится сама собой.                                                                                    |
| `state-unknown`        | Данные о квоте отсутствуют либо слишком устарели, чтобы им доверять.                                                                  | Проверьте: возможно, для провайдера не зарегистрирован адаптер использования или при получении квоты происходит ошибка.                  |
| `no-connection`        | У кандидата вообще нет учётной записи, которую можно проверить.                                                                       | Это не проблема квоты: кандидат был создан без подключения, поэтому никакая проверка не выполнялась. Проверьте, как был сформирован пул. |

Особенно важно различать последние два случая. Исчерпанный лимит сбросится самостоятельно; если же
данные так и не поступают, нарушена сама процедура их получения. До сих пор снаружи оба случая
выглядели одинаково — кандидат просто исчезал.

**Один пробел остаётся, и это сделано намеренно.** `excludeTosAvoid` по-прежнему удаляет кандидатов до того,
как формируется список, поэтому модель с вручную заданным значением `tos: "avoid"` отсутствует без указания причины —
это та же непрозрачность, которая только что была устранена в этом разделе для защиты нулевой стоимости. Чтобы устранить
и её, необходимо решить, какую причину следует сообщать при исключении по ToS, а это отдельный вопрос, не относящийся
к экономической безопасности; на этой странице пробел обозначен явно, а не замалчивается.

Для автономного сравнения состояния до и после по-прежнему можно использовать `npx tsx scripts/ad-hoc/dry-run-strict-zero-cost.ts`
с выводом кандидатов работающего экземпляра; скрипт считывает реальный `connectionId` каждого кандидата, поэтому
также проверяет путь обеспечения безопасности подключения. Кандидаты `keyless` должны поступать с синтетическим
`connectionId` без аутентификации, а не с реальным подключением. Текущий встроенный автоматический путь `keyless` — OpenCode Free; точное количество кандидатов
по-прежнему зависит от динамического обнаружения моделей, поэтому его следует измерять в целевом развёртывании, а не
копировать из результатов предыдущего запуска. Кандидат `recurring-*` проходит проверку только при наличии
зарегистрированного адаптера использования и `hardStopGuaranteed: true`; при неполных метаданных доступ по-прежнему блокируется.

При `excludeTosAvoid: true` удаляется каждый кандидат, для которого вручную задано `tos: "avoid"`. В настоящее время
OpenCode Free имеет именно такой вердикт, поэтому включение защиты может полностью опустошить оставшийся в развёртывании
пул `keyless`. Это ожидаемый компромисс при включении защиты ToS, а не ошибка: именно поэтому по умолчанию защита имеет
значение `false` (см. раздел «Защита ToS» выше).

## Включение

```json
PUT /api/settings
{ "freeAccessPolicy": "strict", "excludeTosAvoid": false }
```

Обе новые настройки по умолчанию имеют значения, использовавшиеся до появления этой функции (`"off"` / `false`), поэтому без включения этих настроек существующее поведение маршрутизации `auto/*` не изменяется.
