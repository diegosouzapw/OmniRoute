> Автоматически экономьте 15–95% токенов подходящего контекста. Краткий обзор см. в [разделе README о сжатии](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically).

## Обзор

OmniRoute реализует модульный конвейер сжатия промптов, который запускается **заблаговременно**, до того как запросы поступают к вышестоящим провайдерам. Это означает, что экономия токенов происходит прозрачно — изменять рабочий процесс не требуется.

```
Запрос клиента
  → Выбор стратегии сжатия
    → Есть переопределение для комбинации? → Использовать настройку комбинации
    → Достигнут порог автозапуска? → Использовать автоматический режим
    → Режим по умолчанию? → Использовать глобальную настройку
    → Отключено? → Пропустить сжатие
  → Выбранный режим сжатия
    → Off: Без сжатия
    → Lite: Безопасная очистка пробелов и форматирования (~15%)
    → Standard: Удаление слов-паразитов в телеграфном стиле (~30%)
    → Aggressive: Устаревание истории + суммаризация (~50%)
    → Ultra: Эвристическое сокращение + прореживание блоков кода (~75%)
    → RTK: Фильтрация вывода терминала и инструментов с учётом команд (диапазон 60–90% для вышестоящего провайдера)
    → Stacked: Упорядоченный многоуровневый конвейер, обычно RTK, затем Caveman (диапазон 78–95% для подходящего содержимого)
  → Сжатый запрос → Провайдер
```

## Режимы сжатия

### Off

Сжатие не применяется. Все сообщения передаются без изменений.

### Режим Lite (экономия ~15%, задержка <1 мс)

Самый безопасный режим — никаких семантических изменений, только очистка форматирования:

| Метод                    | Описание                                                                    |
| ------------------------ | --------------------------------------------------------------------------- |
| `collapseWhitespace`     | Объединение последовательных пустых строк и удаление пробелов в конце строк |
| `dedupSystemPrompt`      | Удаление дублирующихся системных сообщений                                  |
| `compressToolResults`    | Сжатие многословного вывода инструментов/функций                            |
| `removeRedundantContent` | Удаление повторяющихся инструкций                                           |
| `replaceImageUrls`       | Сокращение URI с данными изображений в формате base64                       |

**Лучше всего подходит для:** Постоянного использования и критически важных рабочих процессов.

### Режим Standard (экономия ~30%)

Вдохновлён [Caveman](https://github.com/JuliusBrussee/caveman) — удаляет слова-паразиты и многословные формулировки, сохраняя смысл:

- Удаляет слова-паразиты («пожалуйста», «я думаю», «в основном», «на самом деле»)
- Сокращает многословные фразы («для того чтобы» → «чтобы», «в результате» → «из-за»)
- Убирает избыточно вежливые и уклончивые формулировки («Не могли бы вы...», «Если бы вы могли...»)
- Более 30 правил на основе регулярных выражений, настроенных для промптов, связанных с программированием

**Лучше всего подходит для:** Ежедневных задач программирования и команд, стремящихся снизить расходы.

### Режим Aggressive (экономия ~50%)

Интеллектуальное управление историей для длительных сеансов:

- **Устаревание сообщений** — старые сообщения постепенно сжимаются всё сильнее
- **Сжатие результатов инструментов** — длинный вывод инструментов обрезается или опускается (первые/последние строки,
  фильтрация строк с совпадениями, уплотнение ключей JSON)
- **Средства контроля структурной целостности** — обеспечивают согласованность пар `tool_use` + `tool_result`
- **Учёт контекстного окна** — соблюдает ограничения на количество токенов для каждой модели

**Лучше всего подходит для:** Длительных сеансов отладки и больших кодовых баз.

### Режим Ultra (экономия ~75%)

Максимальное сжатие для сценариев, где критически важно сократить количество токенов:

- **Эвристическое сокращение** — сокращение токенов в тексте на основе оценки
- **Сохранение структуры** — блоки кода с ограждениями, встроенный код, URL-адреса и идентификаторы
  заменяются маркерами и затем дословно восстанавливаются, никогда не подвергаясь сокращению
- **Необязательный уровень SLM** — при соответствующей настройке небольшая локальная модель может улучшить результат сокращения
- Не зависит от режима Aggressive: не выполняет устаревание сообщений, сжатие результатов инструментов
  или резервную суммаризацию (только сбой на уровне SLM может направить резервный проход через
  aggressive)

**Лучше всего подходит для:** Случаев, когда вы регулярно достигаете пределов контекстного окна.

### Режим RTK (диапазон 60–90% для вышестоящего провайдера)

Режим RTK оптимизирован для многословного вывода инструментов, возникающего в сеансах агентов программирования:

- Распознаёт классы команд и вывода, такие как `git status`, `git diff`, `git log`, средства запуска тестов,
  сборки TypeScript/Vite/Webpack, ESLint/Biome/Prettier, аудит/установки npm, журналы Docker, вывод
  инфраструктурных инструментов и общий вывод оболочки
- Применяет наборы JSON-фильтров из `open-sse/services/compression/engines/rtk/filters/`
- Импортирует фильтры схемы RTK TOML v1 из проектных или глобальных файлов `filters.toml` с проверкой
  встроенных тестов и контролем доверия для проектных файлов
- Включает 55 встроенных фильтров с примерами встроенной проверки
- Удаляет управляющие последовательности ANSI, индикаторы выполнения, повторяющиеся строки и несущественный шум
- Сохраняет сбои, ошибки, предупреждения, изменённые файлы, сводки и окончание длинного вывода
- Поддерживает проектные фильтры с контролем доверия, глобальные фильтры и необязательное восстановление необработанного вывода с редактированием конфиденциальных данных

**Лучше всего подходит для:** Сеансов агентов с расшифровками вывода оболочки, сборки, тестов, git, grep и файлов.

### Режим Stacked (диапазон 78–95% для подходящего содержимого)

Режим Stacked запускает несколько механизмов сжатия в детерминированном порядке. Конвейер по умолчанию:

```txt
RTK -> Caveman
```

Такой порядок сначала делает вывод терминала/инструментов компактным, а затем применяет семантическое уплотнение Caveman к
оставшемуся промпту на естественном языке. Конвейеры Stacked можно настраивать глобально или через
комбинации сжатия, назначенные комбинациям маршрутизации.

**Лучше всего подходит для:** Смешанного контекста с большими журналами инструментов, а также инструкциями пользователя или сводками ассистента.

## Расчёт экономии при восходящей передаче

OmniRoute приводит данные об экономии за счёт сжатия из двух источников: бенчмарков вышестоящих проектов и
собственной комбинации движков OmniRoute.

| Источник | Число из README вышестоящего проекта, используемое здесь                                                                                                  |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman  | на `~75%` меньше выходных токенов, средняя экономия выходных токенов в бенчмарках — `65%`, диапазон — `22-87%`, инструмент сжатия входных данных — `~46%` |
| RTK      | экономия вывода команд — `60-90%`; пример сеанса: `~118,000 -> ~23,900` токенов, или экономия `79.7%` (`~80%`)                                            |

Для пересекающихся полезных нагрузок инструментов/контекста стандартная комбинация OmniRoute последовательно применяет движки:

```txt
RTK -> Caveman
```

Совокупная экономия вычисляется мультипликативно, а не аддитивно:

```txt
совокупная = 1 - (1 - экономия RTK) * (1 - экономия входных данных Caveman)
средняя    = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
диапазон   = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

Показатель `78-95%` применим, когда и RTK, и Caveman могут уменьшить одну и ту же полезную нагрузку входных данных/контекста.
Режим выходных ответов Caveman рассматривается отдельно: когда он включён, используйте собственные показатели экономии выходных данных Caveman (`65%`
в среднем, заявленные `~75%`, диапазон `22-87%`). Общая экономия на оплате зависит от соотношения промптов и выходных данных.

### Что на самом деле означает «подходящий для сжатия»

Заявленный диапазон 15-95% реален, но он применим только к **избыточному или многословному** содержимому — повторяющимся
строкам ошибок, журналу сборки, многократно выводящему одно и то же предупреждение, чрезмерно большому выводу `grep`/чтения файла. Это
**не** означает, что каждый запрос обеспечивает такую экономию.

Проверено эмпирически (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): запуск
`stacked` (RTK + Caveman) для блока `tool_result` в формате Anthropic, содержащего 300 одинаковых
строк ошибок, обеспечил **экономию токенов 95.93% / экономию символов 96.26%** — точно в пределах заявленного
диапазона. Однако запуск того же конвейера для обычного, неизбыточного вывода инструмента (чистого списка совпадений `grep`,
результата чтения короткого файла, обычного диалогового текста) ожидаемо даёт **почти нулевую экономию**, поскольку
удалять нечего, а `validateCompression()` (`validation.ts`) не допускает отправку
переписанного содержимого, если при этом удаляются или изменяются блоки кода, URL-адреса, заголовки, версии или идентификаторы констант в ВЕРХНЕМ РЕГИСТРЕ.

Это ожидаемое и безопасное поведение, а не ошибка: сеанс программирования, в котором в основном читаются или просматриваются через `grep` обычные файлы,
даст умеренную общую экономию даже при полностью включённом сжатии, тогда как сеанс, столкнувшийся с циклически повторяющейся ошибкой
или многословным линтером, обеспечит полный диапазон 78-95% экономии для такого трафика. Не используйте низкий
совокупный процент экономии одного сеанса как доказательство неправильной настройки сжатия — сначала проверьте, действительно ли
исходный вывод инструмента был избыточным.

## Визуализация экономии токенов

```
Без сжатия:          47K токенов отправлено в LLM
С Lite:              40K токенов отправлено          (экономия 15% — безопасный режим, включён всегда)
С Standard:          33K токенов отправлено          (экономия 30% — правила Caveman-speak)
С Aggressive:        24K токенов отправлено          (экономия 50% — устаревание + суммаризация)
С Ultra:             12K токенов отправлено          (экономия 75% — эвристическое отсечение)
С RTK:               19K-5K токенов отправлено       (экономия 60-90% на выводе команд/инструментов)
С Stacked:           10K-2.5K токенов отправлено     (диапазон экономии 78-95% для данных, подходящих для RTK+Caveman)
```

## Конфигурация

### Панель управления

Перейдите в `Dashboard → Context & Cache`:

- **Caveman** — выбор режима, языковые пакеты, предварительный просмотр и глобальные настройки по умолчанию
- **RTK** — предварительный просмотр фильтрации команд, настройки безопасности RTK и каталог фильтров
- **Комбинации сжатия** — именованные конвейеры движков, назначенные комбинациям маршрутизации
- **Порог автозапуска** — автоматическое включение сжатия, когда количество токенов превышает пороговое значение

### Переопределение для отдельной комбинации

В разделе `Dashboard → Context & Cache → Compression Combos` назначьте комбинацию сжатия комбинации
маршрутизации:

```txt
Комбинация: "free-tier-fallback"
  Комбинация сжатия: "coding-agent-stack"
  Конвейер: RTK -> Caveman
  Целевые модели:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

Это позволяет использовать многоступенчатое сжатие для бесплатных провайдеров и провайдеров для
программирования, сохраняя облегчённый режим для платных подписок.

Это назначение «Переопределение для отдельной комбинации» является отдельным элементом управления и
отличается от переопределения **режима сжатия комбинации маршрутизации** (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — схема этого поля
также принимает `rtk`, `stacked` и `omniglyph`): это переопределение не выбирает именованный
конвейер комбинации сжатия, а лишь задаёт поле `compressionMode`, учитываемое функцией
`resolveCompressionPlan`. Его можно задать либо на карточке комбинации (`Dashboard → Combos`), либо,
начиная с #6760, для отдельной комбинации маршрутизации в списке «Assign to routing» в разделе
`Dashboard → Context & Cache → Compression Combos`, рядом с флажком назначения конвейера,
описанным выше. Изменения в обоих интерфейсах сохраняются через один и тот же эндпоинт `PUT /api/combos/{id}`.

### Переопределение для отдельного запроса

Передайте заголовок запроса `x-omniroute-compression`, чтобы переопределить план сжатия для одного
запроса. Он имеет наивысший приоритет — выше переопределения комбинации маршрутизации, активного
профиля, автозапуска и значения Default на панели. Неизвестные значения игнорируются (запрос никогда
не отклоняется), а глобальный главный переключатель по-прежнему управляет всем: если сжатие глобально
отключено, заголовок не может его включить. Значения:

| Значение      | Эффект                                                                                                                     |
| ------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `off`         | Не применять сжатие к этому запросу.                                                                                       |
| `default`     | Профиль Default, определяемый настройками панели (активный профиль игнорируется). Движки с потерями остаются выключенными. |
| `safe`        | То же, что и отсутствие заголовка: только дедупликация и свёртывание пробелов.                                             |
| `allow-lossy` | Сохранить операторский план этого запроса, включая сводки, фильтры релевантности и перезапись стиля.                       |
| `engine:<id>` | Один движок, если он включён, например `engine:rtk`. Это включение данного движка для отдельного запроса.                  |
| `<combo>`     | Именованная комбинация: сначала выполняется сопоставление по имени без учёта регистра, затем по id.                        |

Без `allow-lossy`, `engine:<id>` или именованной комбинации движки с потерями не применяются. Если
сжатие включено, к запросу по-прежнему применяются дедупликация сеанса и свёртывание пробелов.

Применённый план возвращается в заголовке ответа `X-OmniRoute-Compression: <mode>; source=<source>`,
где `<source>` — одно из значений: `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default` или `off`.

## Продвинутые системы сжатия

Помимо 7 описанных выше режимов (исходный код также поддерживает режимы `codex-responses` и
`omniglyph`, которые не рассматриваются в этом руководстве), в следующих разделах описаны функции,
работающие внутри этих режимов или совместно с ними: сжатие результатов инструментов и прогрессивное старение
являются этапами 1 и 2 агрессивного движка (режим Aggressive и этап `aggressive` в
составном конвейере), составной конвейер определяет работу режима Stacked, сжатие с учётом кеша
понижает `aggressive` и `ultra` до `standard` для провайдеров с кешированием, пока сжатие
включено, а режим вывода Caveman и стили вывода представляют собой опциональные инструкции системного промпта,
по умолчанию отключённые, которые формируют вывод модели вместо сжатия запроса.

### Сжатие с учётом кеша

Некоторые провайдеры (например, Anthropic с кешированием промптов) поддерживают **кеширование промптов**,
позволяющее кешировать части промпта для снижения затрат и задержки. Когда
кеширование включено, агрессивное сжатие может фактически **ухудшить** производительность,
поскольку оно изменяет кешированные токены и тем самым делает кеш недействительным.

Модуль `cachingAware.ts` решает эту проблему, **обнаруживая контекст кеширования** и
**соответствующим образом корректируя стратегию сжатия**.

#### Как это работает

1. **Обнаружение контекста кеширования** — сканирует тело запроса на наличие маркеров `cache_control`
2. **Определение провайдеров с кешированием** — проверяет, поддерживает ли целевой провайдер кеширование
3. **Корректировка стратегии** — понижает `aggressive`/`ultra` до `standard` для провайдеров с кешированием
4. **Пропуск системного промпта** — системные промпты обычно кешируются, поэтому не следует их сжимать

Вспомогательная функция стратегии также возвращает флаг `deterministicOnly`, однако построитель плана использует
только стратегию — в настоящее время никакие последующие компоненты этот флаг не считывают.

#### Пример кода

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Маркер кеша
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### Когда использовать

Сжатие с учётом кеша **включено всегда** — настройка не требуется. Оно активируется всякий раз,
когда сжатие включено и целевой провайдер поддерживает кеширование промптов (Anthropic, OpenAI
и т. д.); явные маркеры `cache_control` не требуются — одного лишь провайдера с кешированием
достаточно для понижения режима, тогда как одни лишь маркеры никогда его не вызывают (обнаружение маркеров используется для
телеметрии кеша, а не для выбора стратегии).

### Прогрессивное старение

В длительных диалогах накапливается множество реплик, однако более старые реплики становятся менее
релевантными. Модуль `progressiveAging.ts` **снижает детализацию сообщений в зависимости от расстояния в репликах**
(расстояние измеряется от конца диалога). При поставляемых настройках по умолчанию
(`verbatim: 2, light: 2, moderate: 3`):

- **Последние 2 хода (расстояние ≤ 2)**: сохраняются дословно
- **Расстояние 3**: пещерное сжатие (удаление слов-паразитов)
- **Расстояние 4+**: сообщения ассистента суммируются; сообщения пользователя сокращаются до первой
  строки с ограничением в 120 символов; сообщения других ролей не изменяются. Системные промпты, уже состаренные
  сообщения и последнее сообщение пользователя всегда сохраняются дословно независимо от расстояния.
  Ничего не удаляется полностью, а диапазон `light`
  недостижим с настройками по умолчанию (`light` равен `verbatim`).

#### Пример кода

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... ещё 50 ходов ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // последние 3 хода: дословно
  light: 8, // расстояние <= 8: лёгкое сжатие
  moderate: 20, // расстояние <= 20: пещерное сжатие
  fullSummary: 5, // требуется типом, но не считывается кодом распределения по диапазонам
  // расстояние > 20: суммируется (ассистент) / сохраняется первая строка (пользователь)
});

// saved = количество сэкономленных токенов
```

#### Когда использовать

Прогрессивное состаривание **всегда включено** в режиме `aggressive` — это шаг 2 функции
`compressAggressive()`. Режим Ultra его не запускает. Оно особенно эффективно для:

- Длительных сеансов программирования
- Многодневных диалогов
- Агентных рабочих процессов с большим количеством вызовов инструментов

### Режим пещерного вывода

Режим пещерного вывода добавляет **инструкции в системный промпт**, предлагающие самой модели
выдавать лаконичный результат: уровень `lite` требует кратких ответов с сохранением полных предложений, `full`
просит её «отвечать кратко, как умный пещерный человек», а `ultra` требует телеграфного стиля;
инструкции лишь содержат просьбу и не могут гарантировать результат. Запросы получают их через
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`):
`open-sse/handlers/chatCore.ts` сначала определяет выбранный вариант с помощью слоя обратной совместимости
(`resolveOutputStyleSelection()` в
`open-sse/services/compression/outputStyles/backCompat.ts`), который, пока `outputStyles`
пуст, сопоставляет включённый `cavemanOutputMode` со стилем вывода `terse-prose` на уровне
`cavemanOutputMode.intensity` (см. раздел об обратной совместимости ниже); непустой набор
`outputStyles` используется как есть, после чего `cavemanOutputMode.enabled` и `intensity` больше ни на что
не влияют, тогда как переключатель `autoClarity` продолжает применяться. В `outputMode.ts` находятся
тексты инструкций (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), обход по содержимому и вспомогательная
функция размещения, используемая при внедрении; собственный инжектор `applyCavemanOutputMode()` не имеет
вызывающего его производственного кода.

#### Как это работает

Этот режим не сжимает входные данные. Он добавляет блок инструкций в системный промпт
(см. описание механизма внедрения ниже), а любой режим сжатия входных данных, выбранный для запроса,
после этого по-прежнему применяется к телу, которое теперь содержит этот блок. Перед общим
положением об ограничениях, которым заканчивается каждый уровень, английский уровень `full` гласит:

> «Отвечай кратко, как умный пещерный человек. Опускай артикли (a/an/the), слова-паразиты (just/really/basically/actually/simply), любезности, уклончивые формулировки. Фрагменты допустимы. Используй короткие синонимы (big, а не extensive; fix, а не implement). Сохраняй без изменений всю техническую информацию, код, ошибки, URL-адреса и идентификаторы».

Это особенно хорошо подходит для:

- Генерации кода (более лаконичный вывод = меньше токенов)
- Быстрых вопросов и ответов (не нужны подробные объяснения)
- Пакетной обработки (максимальная пропускная способность)

#### Когда использовать

Режим пещерного вывода **включается явно**. При включённом сжатии (`enabled: true`, главный переключатель
на странице настроек сжатия) активируйте его с помощью `cavemanOutputMode.enabled`; параметр `intensity`
выбирает `lite`, `full` или `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

Переключатель **Режим вывода** (`outputMode`, уровень задаётся в `outputModeIntensity`) в комбинации настроек сжатия
устанавливает тот же параметр для запросов, к которым применяется эта комбинация, а MCP-инструмент
`omniroute_set_compression_engine` записывает его через свой логический аргумент `outputMode`.
Непустой набор `outputStyles` имеет приоритет над этим переключателем. На панели управления включение
стиля вывода **Лаконичная проза** внедряет тот же блок (см. раздел «Стили вывода» ниже).

### Стили вывода (каталог)

Описанный выше режим пещерного вывода — это **устаревший путь с одним стилем**. На этапе 4 он был обобщён
в каталог комбинируемых стилей вывода: `OUTPUT_STYLE_CATALOG` в
`open-sse/services/compression/outputStyles/catalog.ts`. Каждый стиль представляет собой инструкцию системного промпта,
которая просит саму модель выдавать менее затратный результат; стили можно включать
одновременно, и они внедряются в порядке каталога.

| Стиль                      | `id`          | Что делает                                                                                                                                                                                                                                             | Языки инструкций                              |
| -------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| Лаконичная проза           | `terse-prose` | Убирает слова-паразиты, артикли и оговорки; точно сохраняет техническую суть. Тот же текст, что и в устаревшем режиме вывода caveman (ссылка без повторного приведения текста).                                                                        | en, pt-BR, es, de, fr, it, ru, zh, ja, id, vi |
| Меньше кода                | `less-code`   | Лестница YAGNI: минимальное работающее изменение без незапрошенных абстракций.                                                                                                                                                                         | en, pt-BR, es, de, fr, it, ru, zh, ja, id, vi |
| Хвостик (ленивый сеньор)   | `ponytail`    | «Лучший код — тот, который никогда не был написан»: повторное использование > переписывание, первопричина > симптом, минимальный работающий diff.                                                                                                      | en, pt-BR, es, de, fr, it, ru, zh, ja, id, vi |
| У меня СДВГ (сразу к делу) | `i-have-adhd` | Сначала действие (команда/путь/фрагмент кода перед пояснением), нумерованные ограниченные шаги, ОДИН конкретный следующий шаг, без вступлений, итогов и заключений. Адаптировано из [ayghri/i-have-adhd](https://github.com/ayghri/i-have-adhd) (MIT). | en, pt-BR, es, de, fr, it, ru, zh, ja, id, vi |
| Лаконичный CJK (文言)      | `terse-cjk`   | Ответ `full`/`ultra` на классическом китайском (文言); `lite` лишь предписывает давать краткие ответы без служебных слов, любезностей и украшательств.                                                                                                 | zh (с ограничением по локали, см. ниже)       |

Каждый стиль поставляется с тремя уровнями интенсивности — `lite`, `full`, `ultra` — и каждый уровень
заканчивается общей оговоркой об ограничениях (`SHARED_BOUNDARIES` в `outputMode.ts`), которая
сохраняет блоки кода, пути к файлам, команды, ошибки и URL без изменений. Тексты уровней `terse-prose` и
`terse-cjk` также добавляют в этот список идентификаторы.

Для `terse-cjk` в двух местах действует ограничение локалью `zh`. На странице настроек сжатия
его строка отображается только тогда, когда язык интерфейса панели управления — китайский (`zh-CN` или `zh-TW`), а
`applyOutputStyles()` внедряет его только тогда, когда определённый язык запроса (см. раздел «Выбор языка»
ниже) — `zh`. Скрытие строки не очищает сохранённый выбор `terse-cjk`:
API настроек принимает любой идентификатор стиля, а сохранение других стилей на странице не удаляет его. Во
время запроса проверка языка в `applyOutputStyles()` является единственным ограничением по локали.

#### Как работает внедрение

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) сопоставляет
выбор с каталогом (неизвестные идентификаторы и стили с несовпадающей локалью
отбрасываются без ошибки; если после сопоставления не остаётся ни одного стиля, тело
не изменяется, а обработка пропускается со статусом `no_styles`), объединяет выбранные инструкции в порядке
каталога,
однократно добавляет оговорку об ограничениях **один раз** (а также оговорку о безопасности, `SAFETY_BOUNDARIES` или её
перевод, если выбран `less-code` или `ponytail`) и начинает блок с
единственного маркера идемпотентности (`[OmniRoute Output Styles]`), поэтому повторное применение ничего не меняет. Если
для определённого языка (см. раздел «Выбор языка» ниже) имеется перевод, вместо английской
инструкции внедряется локализованная.

Если тело содержит непустой массив `messages`, проверка идемпотентности выполняется до
проверки обхода по содержимому: когда маркер `[OmniRoute Output Styles]` уже присутствует в поле
верхнего уровня `system` (строке или массиве блоков содержимого) либо в системном сообщении со строковым
содержимым, тело остаётся неизменным со статусом `already_applied`, и проверка ключевых слов не выполняется.
В противном случае обход по содержимому (`shouldBypassCavemanOutputMode()` в
`open-sse/services/compression/outputMode.ts`) проверяет текст трёх последних
сообщений независимо от их роли и пропускает применение стилей ко всему ходу, если этот текст
соответствует ключевым словам, связанным с безопасностью, необратимыми действиями или уточнениями, либо
последовательности с учётом порядка: за `first`, `then`, `after that`, `before`, `rollback` или
`backup` в пределах 240 символов следует `delete`, `drop`, `migrate`, `deploy` или
`release`. Обход выполняется, пока включён переключатель **Auto-Clarity Bypass**
(`cavemanOutputMode.autoClarity`, включён по умолчанию); отключение переключателя пропускает
проверку ключевых слов.

Когда обход разрешает обработку хода, `placeSystemInstruction()` (тот же файл), который
никогда не создаёт новый `messages[0]`, размещает блок в первом найденном месте из следующих:

1. Начальное системное сообщение со строковым содержимым: блок добавляется после его текста.
2. Поле верхнего уровня `system`: блок добавляется после текста строки или
   как новый текстовый блок в массив блоков содержимого.
3. Первое последующее системное сообщение со строковым содержимым: блок добавляется после его
   текста.
4. Ничего из вышеперечисленного: блок помещается в новое системное сообщение в конце `messages`.

Если тело не содержит массива `messages` (или он пуст), обход по содержимому не выполняется, а
поле верхнего уровня `system` не учитывается. Блок добавляется после текста строкового
поля `instructions`, если только это поле уже не содержит маркер
`[OmniRoute Output Styles]`: в таком случае тело остаётся неизменным со статусом
`already_applied`. Если в теле нет строкового поля `instructions`, но присутствует `input`
(строка или массив), блок становится значением `instructions`, заменяя любое нестроковое значение,
которое ранее содержало это поле. Тело, не содержащее ни строкового поля `instructions`, ни строкового значения или массива
`input`, остаётся неизменным, а обработка пропускается со статусом `no_messages`.

#### Как включить

На панели управления: **Контекст сжатия → Настройки сжатия**
(`/dashboard/context/settings`), раздел стилей вывода: по одной строке на каждый стиль с
переключателем вкл./выкл. и выбором уровня. Стили внедряются, пока включено само сжатие
(главный переключатель страницы, `enabled`). Переключатель **Автоматический обход Clarity**
находится на странице **Caveman** (`/dashboard/context/caveman`), в карточке **Режим вывода**.
Программно конфигурация сжатия сохраняет выбор следующим образом:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

Обратная совместимость: пока `outputStyles` пуст, устаревшая настройка
`cavemanOutputMode.enabled` сопоставляется с `terse-prose` на уровне
`cavemanOutputMode.intensity`. Затем блок начинается с маркера
`[OmniRoute Output Styles]`, тогда как устаревший инжектор `applyCavemanOutputMode()`
добавлял `[OmniRoute Caveman Output Mode]`. Под маркером текст совпадает с устаревшей
вставкой для en, pt-BR, es, de, fr, it, ru, id и vi; в ja и zh перед положением о границах
добавлен один лишний пробел. `terse-prose` переведён на pt-BR, es, de, fr, it, ru, zh, ja,
id и vi, поэтому запрос, для которого определён язык `hu`, получает английский текст,
тогда как устаревший инжектор использовал венгерский.

Выбор языка стиля вывода (`resolveOutputStyleLanguage()` в
`outputStyles/apply.ts`): если `languageConfig.enabled` включён, `autoDetect` берёт
последнее пользовательское сообщение с текстом в массиве `messages` запроса
(строковое содержимое или `text` его частей содержимого) и запускает для него детектор
движка Caveman (`detectCompressionLanguage()`). Детектор возвращает `zh` для текста с
иероглифами хань и без каны; в остальных случаях он возвращает тот из языков `it`,
`pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` и `id`, для которого найдено больше всего
подсказок, и `en`, если совпадений нет, — текст, который он не может классифицировать,
получает английский язык, но никогда не `defaultLanguage`, а `vi` никогда не
определяется, хотя стили содержат текст на `vi`. Тело Responses API хранит свои реплики
в `input`, который не анализируется, поэтому для него используется `defaultLanguage`,
а затем английский. Если ни одно пользовательское сообщение в `messages` не содержит
текста или если `autoDetect` выключен, применяется `defaultLanguage`, а затем английский.
Если `languageConfig.enabled` выключен, используется английский язык — за исключением
случая, когда к запросу применяется комбинация сжатия (комбинация, назначенная
маршрутизирующей комбинации запроса, или комбинация сжатия по умолчанию, к которой
chatCore прибегает для встроенного составного конвейера): применение комбинации включает
`languageConfig.enabled` для этого запроса и задаёт `defaultLanguage` на основе языковых
пакетов комбинации (сохранённое значение, если оно входит в число пакетов комбинации,
иначе первый пакет комбинации, который по умолчанию равен `en`), при этом по-прежнему
применяется сохранённое значение `autoDetect` (по умолчанию включено). Движок ввода
Caveman выбирает язык пакета правил иначе — отдельно для каждой текстовой части, а при
выключенном автоматическом определении — только с учётом `enabledPacks`.

Матрица «стиль × язык» закреплена тестом
`tests/unit/compression/output-styles-i18n-matrix.test.ts`: для каждого стиля каталога
должна существовать запись в `BASELINE_LANGUAGES`; стиль, не ограниченный локалью,
должен иметь перевод на pt-BR (ограниченный локалью `terse-cjk` освобождён от этого
правила), если он не указан в `KNOWN_ENGLISH_ONLY`, где могут находиться только стили
без каких-либо переводов — указанный там стиль с любым переводом приводит к сбою теста;
кроме того, стиль не проходит тест, если теряет язык, перечисленный в соответствующей
записи `BASELINE_LANGUAGES`. Инструкции по добавлению стиля см. в
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style).

### Сжатие результатов инструментов

`compressToolResult()` в `open-sse/services/compression/toolResultCompressor.ts`
сжимает текст результатов инструментов с помощью **5 стратегий**. Они проверяются в
следующем порядке, и результат определяет первая включённая стратегия, проверка которой
соответствует содержимому:

1. **`fileContent`**: содержимое из 3 или более строк, в котором хотя бы одна строка, если не учитывать
   начальный отступ, начинается с `import `, `export `, `function `, `class `,
   `const `, `let `, `var ` или `return ` (ключевое слово и пробел) либо с `if`,
   `for` или `while`, после которых следует `(` или ` (`, сохраняет первые 20 и последние 5 строк,
   а пропущенная середина отмечается.
2. **`grepSearch`**: содержимое хотя бы с одной строкой вида `<path>:<digits>:`,
   где текст до первого двоеточия не содержит пробелов, сохраняет только такие строки —
   не более 30, после чего указывает количество остальных совпадений и список файлов с совпадениями;
   все прочие строки отбрасываются. Для срабатывания стратегии достаточно одной такой строки, поэтому
   строка журнала, начинающаяся с временной метки вроде `12:30:45`, также учитывается.
3. **`shellOutput`**: из вывода, содержащего последовательность ANSI CSI (`ESC[`, затем цифры или
   точки с запятой, а затем букву, как в кодах цвета) либо символ `$`, за которым в любом месте
   текста следует пробельный символ, удаляются такие последовательности (другие управляющие последовательности,
   например `ESC[?25l` или OSC-последовательность заголовка окна, сохраняются) и оставляются последние
   50 строк, при этом последовательные повторяющиеся строки сворачиваются. Поскольку эта проверка выполняется
   перед `json` и `errorMessage`, вывод JSON или ошибки, содержащий такой `$`, никогда не доходит до них,
   пока включена `shellOutput`.
4. **`json`**: JSON-данные длиной более 2 000 символов, которые начинаются с `{` или `[` (после
   необязательных пробельных символов) и успешно разбираются, сокращаются: для массива из более чем 7 элементов
   сохраняются первые 5 и последние 2 элемента, а также их общее количество; для объекта сохраняются первые
   20 ключей, при этом каждое значение в виде вложенного объекта или массива заменяется заполнителем `{…N keys}`
   (для массива N — его длина), а маркер `_remaining_<N>_keys` указывает количество ключей,
   отброшенных после первых 20. Скалярные значения копируются целиком, поэтому объект с 20 ключами
   или менее без вложенных значений только форматируется с отступами — минифицированный объект становится длиннее
   и остаётся без изменений.
5. **`errorMessage`**: вывод, который в любом месте и в любом регистре содержит `error:`,
   `error ` (слово, за которым следует пробел, как в `no error found`), `[error]`,
   `exception:`, `exception `, `[exception]` или `traceback`, сохраняет первую строку,
   следующие 10 строк и последние 3, а строки между ними заменяются маркером
   `… [N frames elided] …`. Маркер появляется, только если после первой строки следует более
   13 строк, поэтому вывод ошибки из 14 строк или менее не сокращается (при 12 или 13 строках
   последние 3 повторяют уже сохранённые строки).

После совпадения со стратегией, даже если она ничего не экономит, последующие стратегии
не проверяются. Если совпавшая стратегия не даёт расчётной экономии токенов (длина ÷ 4 с округлением вверх) —
например, файл с кодоподобным содержимым из 25 строк или менее либо JSON-массив длиной более 2 000
символов с 7 элементами или менее, — агрессивный движок сохраняет исходный результат инструмента:
оба вызывающих компонента (`compressAggressive()` и `compressAnthropicToolResultBlock()`)
сохраняют оригинал, если `saved` равен 0 или меньше, тогда как сам `compressToolResult()`
по-прежнему возвращает результат этой стратегии. Этап обработки результата инструмента — не последнее слово:
резервный суммаризатор движка всё ещё может сократить сообщение `tool` или `function` длиннее
8 192 символов (`maxTokensPerMessage`, 2 048, умноженное на 4).

#### Когда использовать

Сжатие результатов инструментов — это шаг 1 агрессивного движка (`compressAggressive()` в
`open-sse/services/compression/aggressive.ts`), поэтому оно выполняется в режиме Aggressive и на
шаге `aggressive` составного конвейера. Оно сжимает сообщения `tool` и `function`
в формате OpenAI, а также текст внутри блоков Anthropic `tool_result`. У каждой стратегии есть
собственный переключатель в `aggressive.toolStrategies`; по умолчанию все они включены. На панели управления
переключатели находятся в представлении **Advanced** страницы Caveman, когда сжатие включено,
а режимом по умолчанию выбран Aggressive.

### Составной конвейер

Составной режим запускает **несколько движков последовательно** — обычно сначала RTK
(экономия 60–90% для вывода инструментов), затем Caveman для оставшегося текста (экономия
входных данных ~46%). В сочетании это даёт **диапазон экономии 78–95% для подходящих данных**
(см. расчёт экономии на вышестоящем уровне выше): `1 - (1 - 0.60..0.90) × (1 - 0.46)`
в среднем составляет ≈89%.

#### Как это работает

```
Входные данные (1000 токенов)
  → RTK (фильтр с учётом команд) → 200 токенов
    → Caveman (удаление избыточного текста) → 108 токенов
  → Выходные данные (108 токенов, экономия ~89%)
```

#### Когда использовать

Используйте составной режим для:

- Рабочих процессов с интенсивным использованием инструментов (агентное программирование, исследования)
- Пакетной обработки, чувствительной к стоимости
- Случаев, когда требуется максимальная экономия токенов

Составные конвейеры настраиваются с помощью глобального параметра сжатия `stackedPipeline`
либо через именованную комбинацию сжатия, назначенную комбинации маршрутизации (см.
переопределение для отдельных комбинаций выше), — но не через `modePack` автоматической комбинации
(это поле лишь перераспределяет веса при выборе модели автоматической комбинацией, а `stacked`
не является допустимым именем пакета).

## Переопределение комбинаций сжатия

Вы можете переопределить глобальный режим сжатия **для каждой комбинации**, чтобы точно настроить поведение
для различных сценариев использования:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

Это полезно для:

- **Комбинаций для программирования**: используйте режим `aggressive` для длительных сессий
- **Комбинаций для быстрых вопросов и ответов**: используйте режим `lite` для быстрых ответов
- **Комбинаций с интенсивным использованием инструментов**: используйте режим `stacked` для максимальной экономии
- **Комбинаций для промышленной эксплуатации**: не включайте переопределение для провайдеров с кэшированием — постоянно активная
  корректировка с учётом кэша автоматически понижает `aggressive`/`ultra` до `standard`
  (режим `cache-aware` нельзя выбрать)
