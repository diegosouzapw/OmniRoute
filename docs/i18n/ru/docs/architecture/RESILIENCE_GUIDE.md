В OmniRoute есть три различных, но связанных между собой механизма отказоустойчивости. У каждого своя область действия и назначение. Не смешивайте их при отладке поведения маршрутизации.

## 1. Circuit Breaker провайдера

**Область действия:** провайдер целиком (например, `glm`, `openai`, `anthropic`).

**Назначение:** прекратить отправку трафика провайдеру, который повторно даёт сбои на уровне upstream/сервиса.

**Реализация:**

- Основной класс: `src/shared/utils/circuitBreaker.ts`
- Подключение: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- API статуса: `GET /api/monitoring/health`
- API сброса: `POST /api/resilience/reset`
- Обёртки: `open-sse/services/accountFallback.ts`
- Таблица БД: `domain_circuit_breakers`

**Состояния:**

- `CLOSED` — обычный трафик разрешён
- `DEGRADED` — трафик по-прежнему разрешён, но отслеживается повышенное число сбоев провайдера; возврат в `CLOSED` происходит после достаточного числа успешных запросов, после успешной проверки соединения либо по истечении самого длительного удержания в `OPEN` для последнего типа сбоя (его значение `cooldownByKind`, иначе `resetTimeout`, умноженное на `maxBackoffMultiplier`, но не менее одного периода cooldown) при отсутствии нового сбоя
- `OPEN` — провайдер временно заблокирован; комбо-маршрутизация пропускает его
- `HALF_OPEN` — таймаут сброса истёк; разрешён пробный запрос

**Настраиваемые значения по умолчанию (`open-sse/config/constants.ts`, доступны в разделе Dashboard → Settings → Resilience панели управления):**

| Класс     | Переход в DEGRADED | Открытие (OPEN) | Таймаут сброса |
| --------- | ------------------ | --------------- | -------------- |
| OAuth     | 5 сбоев            | 8 сбоев         | 60s            |
| API-ключ  | 7 сбоев            | 12 сбоев        | 30s            |
| Локальный | вычисляется        | 2 сбоя          | 15s            |

`degradationThreshold` определяет, когда провайдер переходит в `DEGRADED`; `failureThreshold` — когда он открывается и начинает пропускаться. Профили локальных провайдеров пока не отображаются на странице настроек Resilience.

**Коды срабатывания:** только статусы уровня провайдера `[408, 500, 502, 503, 504]`. НЕ срабатывает на ошибки уровня аккаунта (большинство 401/403/429 — они относятся к cooldown или блокировке).

**Ленивое восстановление:** когда срок `OPEN` истекает, `getStatus()`, `canExecute()`, `getRetryAfterMs()` обновляют состояние до `HALF_OPEN`. Те же операции чтения (и следующий сбой) постепенно возвращают устаревшее `DEGRADED` обратно в `CLOSED`. Фоновый таймер не требуется.

### Опциональный глобальный Provider Cooldown (оконный фильтр)

Четвёртый, **опциональный** уровень (`PROVIDER_COOLDOWN_ENABLED`, по умолчанию **выключен**) хранит межзапросную память о сбоящих провайдерах в `open-sse/services/providerCooldownTracker.ts`; её учитывает механизм выбора целей комбо-маршрутизации, чтобы последовательные комбо-запросы не обращались повторно к провайдеру, который только что дал сбой. Записи уровня провайдера подчиняются оконному фильтру `PROVIDER_PROFILES`:

| Профиль  | Срабатывает после (`providerFailureThreshold`) | В пределах (`providerFailureWindowMs`) | Cooldown (`providerCooldownMs`) |
| -------- | ---------------------------------------------: | -------------------------------------: | ------------------------------: |
| OAuth    |                                           `10` |                                `15min` |                          `5min` |
| API-ключ |                                           `15` |                                `30min` |                         `10min` |

Ниже порога провайдер **не** считается находящимся в cooldown; успешный запрос очищает окно. Записи уровня соединения (`provider:connectionId`) вместо этого используют экспоненциальный backoff `minRetryCooldownMs → maxRetryCooldownMs`. Переопределения: `OMNIROUTE_PROVIDER_BREAKER_{OAUTH,API_KEY}_{FAILURE_THRESHOLD,FAILURE_WINDOW_MS,COOLDOWN_MS}`. Регрессионный тест: `tests/unit/provider-cooldown-window-gate.test.ts`.

## 2. Кулдаун соединения

**Область действия:** одно соединение/аккаунт/ключ провайдера.

**Назначение:** пропустить один нерабочий ключ, пока другие соединения того же провайдера продолжают обслуживать запросы.

**Реализация:**

- Пометка недоступности: `src/sse/services/auth.ts::markAccountUnavailable()`
- Выбор: `getProviderCredentials*` в том же файле
- Расчёт кулдауна: `open-sse/services/accountFallback.ts::checkFallbackError()`
- Настройки: `src/lib/resilience/settings.ts`

**Поля для каждого соединения:**

- `rateLimitedUntil` — метка времени, до которой действует кулдаун
- `testStatus: "unavailable"`
- `lastError`, `lastErrorType`, `errorCode`
- `backoffLevel` — счётчик экспоненциальной задержки

**Кулдауны по умолчанию:**

- Базовый для OAuth: 5 с
- Базовый для API-ключа: 3 с
- API-ключ, 429: предпочтение отдаётся апстрим-заголовкам `Retry-After`/заголовкам сброса либо тексту о сбросе, который можно распарсить
- Экспоненциальная задержка: `baseCooldownMs * 2 ** failureIndex`

**Защита от "thundering herd" (стадного эффекта):** предотвращает чрезмерное продление кулдауна или двойное увеличение `backoffLevel` при одновременных сбоях.

**Ответы 429 из-за лимита параллелизма не поднимаются по лестнице задержки.** Ответ `429`, в теле которого сообщается о лимите параллелизма ("too many concurrent requests", "concurrency limit", "parallel request limit", GLM `并发数过高`), означает, что аккаунт исправен, но занят.
`checkFallbackError()` возвращает причину `concurrency_limited`: немедленно переключиться на следующее соединение, охладить текущее на фиксированное время `CONCURRENCY_LIMIT_COOLDOWN_MS` (1 с) или на время, указанное апстримом в подсказке о повторе, оставить `backoffLevel` без изменений и установить `skipProviderBreaker`.
Явное сообщение о квоте в теле всё равно имеет приоритет, поэтому тело, которое также совпадает с шаблоном квоты, остаётся вердиктом о квоте. Обнаружение: `looksLikeConcurrencyLimit()` в `src/shared/utils/classify429.ts`; вердикт: `open-sse/services/accountFallback/concurrencyLimit429.ts`. `classify429()` (`FailureKind` прерывателя) не изменился и по-прежнему возвращает `rate_limit` для таких тел.

**Зависания потокового контента не охлаждают аккаунт.** Когда watchdog зависания контента
(`open-sse/utils/streamHandler.ts`) прекращает ожидание потока, который вовремя не прислал вывод модели, `markAccountUnavailable()` записывает ошибку на соединение, но не устанавливает кулдаун: зависание относится к этому запросу — чаще всего это долгий рассуждающий ход, ещё не выдавший результата. Операторы могут вернуть прежнее поведение через `resilienceSettings.streamStallCooldown.enabled` (по умолчанию `false`).

**Кадры рассуждения перезапускают бюджет ожидания контента.** Рассуждающая модель может думать минутами до первого видимого токена: Claude передаёт кадры `thinking_delta`, текст рассуждения в которых может быть пустым, а Responses API передаёт один элемент рассуждения за другим. `isReasoningProgressFrame()` (`open-sse/utils/streamReadiness.ts`) распознаёт эти кадры, и watchdog перезапускает свой бюджет на каждом из них вместо отмены хода. Они всё же не являются выводом модели, поэтому ход, завершившийся одними рассуждениями, по-прежнему считается пустым, а ход, который прекратил рассуждать и отправляет только heartbeat-сигналы, всё равно активирует watchdog.

Бинарные кадры `reasoningContentEvent` от Kiro с непустой подписью сохраняют эту активность рассуждения при проходе через исполнитель в виде пустой дельты `reasoning_content`. Подпись дальше не пересылается. Метаданные, неполные кадры и пустые подписи не перезапускают бюджет контента; независимый таймаут активного потока и отмена клиентом продолжают действовать (`open-sse/executors/kiro/reasoning.ts`).

**Терминальные состояния (НЕ кулдауны):**

- `banned` — устанавливается механизмом обнаружения запрещённых ключевых слов / бана аккаунта (см. [BAN_DETECTION](../security/BAN_DETECTION.md)), а также тремя подряд отказами апстрима на уровне запроса (`request_rejected`, например Anthropic OAuth 403 "Request not allowed" — `open-sse/services/requestRejectedStreak.ts`); одиночный отказ лишь отправляет соединение в кулдаун
- `expired` (переходит в терминальное состояние после ограниченного числа повторных попыток — `EXPIRED_RETRY_MAX = 3` с экспоненциальной задержкой, — так что временные ошибки OAuth могут самоустраниться до окончательной деактивации аккаунта)
- `credits_exhausted`

Эти состояния сохраняются, пока не изменятся учётные данные или оператор не сбросит их. Не перезаписывайте терминальные состояния временным состоянием кулдауна.

**Ленивое восстановление:** когда момент `rateLimitedUntil` прошёл, соединение снова становится кандидатом на выбор. При успешном использовании `clearAccountError()` очищает все поля ошибок.

### Стена лимита использования Claude OAuth: полоса пониженного приоритета + сброс лимита сессии

**Область действия:** одно соединение с подпиской Claude (OAuth). Обе функции **включаются индивидуально для каждого соединения** (Изменить соединение → раздел Claude → `lowPriorityMode` / `autoLimitReset` в `providerSpecificData`, обе по умолчанию выключены) и зеркалируют команды `/low-priority` и `/limit-reset` из Claude Code (сетевой контракт снят с Claude Code 2.1.263).

**Реализация:**

- Конечный автомат + классификация ответов: `open-sse/services/claudeLowPriority.ts`
- Клиент статуса/запроса сброса: `open-sse/services/claudeLimitReset.ts`
- Хук исполнителя (подстановка заголовков + повтор на том же аккаунте): `open-sse/executors/base.ts::execute()`
- Сохранение opt-in: `src/lib/providers/requestDefaults.ts::normalizeProviderSpecificData()`

**Триггер:** 5-часовая стена использования — ответ `429`, в заголовках которого присутствуют `anthropic-ratelimit-unified-status: rejected` и, если аккаунт имеет право, `anthropic-ratelimit-unified-slow-offer: treatment`. До этого первого 429 «стены» ничего не отправляется; всплесковый 429 без unified-заголовков идёт по обычному пути кулдауна.

**Полоса пониженного приоритета** (`lowPriorityMode`):

- При 429-ответе «стены» исполнитель принимает предложение и немедленно повторяет запрос через **тот же** аккаунт с `anthropic-usage-limit: slow`; канал остаётся активным до объявленного момента `anthropic-ratelimit-unified-reset` (+60 с допуска), и каждый запрос в этом окне несёт этот заголовок. Перехваченный 429 никогда не доходит до `handleChatCore`, поэтому соединение **не** переводится в кулдаун и не выводится из ротации.
- `anthropic-ratelimit-unified-slow-status` в последующих ответах: `active` / `not_needed` сохраняют канал; при `slot_busy` (429) или `529` исполнитель ждёт указанное сервером `anthropic-ratelimit-unified-slow-retry-after` (по умолчанию 20 с, ограничение 5–600 с, джиттер ±30%) и повторяет попытку, но не дольше `anthropic-ratelimit-unified-slow-max-wait` (по умолчанию 20 мин, ограничение 1 мин–6 ч) — по истечении этого срока канал завершается, и 10-минутное охлаждение блокирует повторное принятие. Ожидание дополнительно ограничивается остатком собственного тайм-аута запуска апстрима данного запроса (`resolveFetchStartTimeout`, по умолчанию 10 мин) минус запас 5 с: без этого ограничения 20-минутный max-wait по умолчанию переживал бы сам запрос, и сон прерывался бы посреди ожидания, приводя к `TimeoutError` вместо корректного завершения по `max_wait` + охлаждения.
- `weekly_limit` / `budget_exhausted` / `off` / `ineligible`, переключение 5-часового окна или `ineligible` + `anthropic-ratelimit-unified-overage-in-use: true` (что завершает канал как `extra_usage` при любом статусе, поскольку платный оверейдж теперь покрывает стену) завершают канал; после этого ответ направляется в обычный путь кулдауна. `budget_exhausted` запоминается до объявленного сброса бюджета (≤ 8 дней).
- Проверка стены выполняется после собственных повторов исполнителя в рамках одной попытки, инициируемых ответами 400 (редактирование контекста, ограничения thinking/effort, автообучение параметров), поэтому 429 «стены», проявляющийся только на одном из этих повторов, по-прежнему перехватывается и не попадает на путь кулдауна.
- Состояние хранится в памяти отдельно для каждого соединения (перезапуск обходится в один дополнительный 429 «стены» для повторного принятия).

**Сброс лимита сессии** (`autoLimitReset`, выполняется перед каналом, когда включены оба механизма):

- `GET https://api.anthropic.com/api/oauth/usage?at_wall=1&skip_spend=1` → блок `juniper_tide`; когда `arm: "reset"` и `available: true`, выполняется `POST https://api.anthropic.com/api/organizations/{orgUUID}/reset_rate_limits` с `{ "program": "juniper_tide" }` (UUID организации берётся из `providerSpecificData.organizationUUID`, запасной вариант — bootstrap).
- `result: reset|not_limited` → запрос повторяется на полной скорости (без slow-заголовка). `already_used` / `not_offered` запоминают `next_available_at` (по умолчанию одна неделя); при любой ошибке делается отсрочка на 15 минут. Сброс доступен раз в неделю и по-прежнему учитывается в недельном лимите.

Регрессионные тесты: `tests/unit/claude-low-priority-mode.test.ts`,
`tests/unit/claude-limit-reset.test.ts`, `tests/unit/claude-low-priority-executor.test.ts`.

### Привязка сессий (#7274)

**Область действия:** одна клиентская сессия (заголовок `X-Session-Id` / `x-codex-session-id` / `x-omniroute-session`), закреплённая за одним соединением, для **любого** провайдера.

**Назначение:** удерживать многошагового агента (Claude Code, aider, пользовательские агенты) на одном аккаунте между запросами, уменьшая потерю контекста при смене аккаунта и повторные 429 «холодного старта» у провайдеров с сессионным состоянием на уровне аккаунта.

**Реализация:**

- Вычисление TTL: `src/sse/services/sessionAffinityPin.ts::resolveSessionAffinityTtlMs()`
- Выбор/создание закрепления: `src/sse/services/sessionAffinityPin.ts::selectSessionAffinityConnection()`
- Извлечение заголовков (универсальное, для любого провайдера): `src/sse/services/auth.ts::extractSessionAffinityKey()`
- Хранимая таблица закреплений: `sessionAccountAffinity` (`src/lib/db/sessionAccountAffinity.ts`)
- Настройка: `sessionAffinityTtlMs` (глобальный TTL в мс, `0` отключает) — `src/lib/db/settings.ts`. Переименована из `codexSessionAffinityTtlMs`, действовавшей только для Codex, миграцией `124_generic_session_affinity_ttl.sql`, которая переносит любой ранее настроенный TTL Codex в качестве нового значения по умолчанию.

До #7274 `resolveSessionAffinityTtlMs()` безусловно возвращала `0` для всех провайдеров, кроме `codex`, поэтому настройка TTL (и заголовки сессий) не имела эффекта нигде больше, хотя механизм закрепления и извлечение заголовков уже были независимы от провайдера. Исправление убрало этот ранний возврат; теперь TTL применяется единообразно ко всем провайдерам, как только глобально задано значение выше `0`.

Три заголовка привязки сессий никогда не передаются в апстрим — исполнители формируют собственные заголовки апстрима с нуля, а не пробрасывают клиентские заголовки, поэтому это остаётся исключительно внутренним идентификатором корреляции.

### Эксклюзивная аренда соединений для управляемых сессий

**Область действия:** один активный управляемый HTTP-клиент/сессия владеет одним подходящим соединением OmniRoute.

**Назначение:** обеспечить долговечное эксклюзивное владение соединением для клиентов, которым требуется жёсткий барьер маршрутизации между запросами. Это отличается от привязки сессий, которая является мягким предпочтением непрерывности: эксклюзивная аренда сохраняет состояние жизненного цикла в SQLite, обеспечивает глобальную уникальность активного владельца и активного соединения и отклоняет устаревшее поколение до отправки провайдеру.

Функция включается явно (opt-in) для каждого API-ключа. Управляемый ключ должен иметь область `lease:exclusive` и явно заданный непустой список `allowedConnections`. Любой HTTP-клиент может использовать эндпоинт жизненного цикла; не требуется ни имя клиента, ни user-agent, ни провайдер, ни метод OAuth, ни модель. Аренда владеет соединением, а не моделью, поэтому смена модели сохраняет привязку, пока соединение остаётся подходящим по обычным правилам. Обычные правила модели, квот, работоспособности, кулдауна и списков разрешённых остаются приоритетными и могут перевести то же поколение на другое свободное подходящее соединение.

Жизненный цикл — это `POST /api/v1/session-leases` с JSON-действиями `acquire`, `renew` и `release`.
Управляемые запросы инференса предъявляют непрозрачное значение `X-OmniRoute-Lease-Owner` и точное значение
`X-OmniRoute-Lease-Generation`. Идентификатор владельца начинается с `vlo_`, за которым следуют 43 символа
base64url; хранится только его хэш SHA-256. Каждый финальный барьер диспетчеризации также привязывает
идентификатор аутентифицированного API-ключа и идентификатор активного соединения. Заголовки управления
арендой удаляются из журналов, сохранённых снимков запросов и заголовков вышестоящего исполнителя.

Если при обычной маршрутизации есть подходящие управляемые кандидаты, но каждый свободный кандидат занят
чужой активной арендой, OmniRoute возвращает HTTP `429`, код lease-capacity-unavailable, состояние
waiting-for-capacity и ограниченное значение `Retry-After`, производное от ближайшего соответствующего
истечения срока. Обычное отсутствие подходящих кандидатов не является конфликтом аренд и сохраняет
существующую семантику ошибок маршрутизации.

Связанные механизмы остаются раздельными:

- Занятость OAuth-сессий — это локальное для процесса мягкое распределение для OAuth-аккаунтов.
- Семафоры аккаунтов выдают разрешения на параллелизм запросов и завершаются по окончании запроса.
- Эксклюзивные аренды управляемых сессий — это долговременное владение жизненным циклом с барьером поколения.

## 3. Блокировка модели

**Область действия:** тройка provider + connection + model.

**Область ключа по статусу:** статус сбоя определяет, в какой ключ записывается блокировка (`resolveLockoutScope()` в `open-sse/services/accountFallback/exactModelLock.ts`):

- `429` / `403` / `402` — сигнал о квоте или правах доступа — блокируется **семейство квот**:
  для codex — вся область `codex` / `spark` (каждая модель `gpt-5*` соединения),
  для остальных провайдеров — `getQuotaScopedModelForProvider()`.
- `404` блокирует конкретную модель (`getModelLockKey()` сужает `not_found`).
- Любой другой статус — транспортные/серверные сбои `5xx` и собственный
  синтезированный `502` OmniRoute из валидации качества — блокирует только
  **точную** тройку provider/connection/model. Плохой поток на одной модели —
  не свидетельство о квоте аккаунта; до этого правила один пустой ответ на
  `codex/gpt-5.6-luna` исключал каждую модель `gpt-5*` этого соединения из
  маршрутизации на 2–30 мин (с эскалацией), хотя её квота оставалась нетронутой.
- Явная опция `scope` вызывающей стороны всегда имеет приоритет (Antigravity передаёт `"exact"`).

**Назначение:** не отключать целое соединение, когда недоступна или ограничена по квоте только одна модель.

**Примеры:**

- Провайдеры с помодельными квотами, возвращающие 429
- Локальные провайдеры, возвращающие 404 для одной отсутствующей модели
- Специфичные для провайдера ошибки прав доступа к режимам/моделям (например, режимы Grok)

**Реализация:** `open-sse/services/accountFallback.ts` — `lockModel()`, `clearModelLock()`, `getAllModelLockouts()`.

### Панель Model Cooldowns (v3.8.0)

UI: Settings → Model Cooldowns (`src/app/(dashboard)/dashboard/settings/components/ModelCooldownsCard.tsx`)

Перечисляет активные блокировки с полями: provider, connection, model, reason, expiresAt. Операторы могут вручную повторно включить модель из карточки.

**REST API:**

- `GET /api/resilience/model-cooldowns` — список активных блокировок
- `DELETE /api/resilience/model-cooldowns` — ручное повторное включение. Тело: `{provider, connection, model}`. Авторизация: management.

### Cooldown Manager

UI: Monitoring → Cooldown Manager (`src/app/(dashboard)/dashboard/resilience/cooldowns/`).

Одна страница для всех соединений, выведенных из маршрутизации по временной причине,
вместо открытия страницы каждого провайдера. Она перечисляет cooldown'ы соединений,
блокировки моделей и терминальные состояния, очищает их для отдельного соединения,
для выборки или для всех соединений провайдера, а также редактирует наиболее часто

(сохраняются через `PATCH /api/resilience`). Терминальные состояния (`banned`,
`expired`, `credits_exhausted`) отображаются, но никогда не очищаются здесь.

**REST API** (`src/lib/resilience/cooldownManager.ts`, авторизация: management):

- `GET /api/resilience/cooldowns[?provider=]` — соединения со статусом, оставшимся
  cooldown, уровнем backoff, типом последней ошибки и блокировками моделей
  (без учётных данных)
- `POST /api/resilience/cooldowns` — тело `{connectionIds: string[]}` или
  `{all: true, provider?}`; возвращает `{cleared, unchanged, skippedTerminal, lockoutsCleared}`

### Настройки блокировки в UI + восстановление с затуханием при успехе (v3.8.23)

Блокировка модели превратилась из всегда включённого жёстко зашитого поведения в
полностью настраиваемую, включаемую по желанию функцию с собственной карточкой
настроек и самовосстанавливающимся путём восстановления.

**Карточка настроек:** Settings → Model Lockout
(`src/app/(dashboard)/dashboard/settings/components/ModelLockoutCard.tsx`).
Она **отличается** от read-only карточки `ModelCooldownsCard` выше (которая только
_перечисляет_ активные блокировки) — новая карточка _настраивает параметры_.
Значения по умолчанию находятся в `DEFAULT_MODEL_LOCKOUT_SETTINGS`
(`src/lib/resilience/modelLockoutSettings.ts`):

| Параметр                | По умолчанию                     | Значение                                                              |
| ----------------------- | -------------------------------- | --------------------------------------------------------------------- |
| `enabled`               | `false`                          | Главный переключатель — блокировка модели **по умолчанию выключена**. |
| `errorCodes`            | `[403, 404, 429, 502, 503, 504]` | Статусы upstream, считающиеся сбоем на уровне модели.                 |
| `baseCooldownMs`        | `120_000` (120 с)                | Начальная длительность блокировки при первом сбое.                    |
| `maxCooldownMs`         | `1_800_000` (30 мин)             | Верхний предел эскалированного cooldown.                              |
| `maxBackoffSteps`       | `10`                             | Максимальное число шагов эскалации экспоненциального backoff.         |
| `useExponentialBackoff` | `true`                           | Эскалировать ли cooldown экспоненциально при повторных сбоях.         |

Настройки сохраняются через обычное хранилище настроек и валидируются схемой
настроек resilience; карточка ограничивает `baseCooldownMs`/`maxCooldownMs`
(при условии `maxCooldownMs ≥ baseCooldownMs`) и `maxBackoffSteps`.

**Восстановление с затуханием при успехе:** восстановление — это **не** только
истечение таймера. Успешный ответ снижает счётчик сбоев модели, так что модель,
восстановившаяся в середине окна, перестаёт эскалироваться (и снимается с
блокировки) раньше, чем истечёт её таймер. При успешном запросе к цели combo
`open-sse/services/combo.ts` вызывает `decayModelFailureCount()`
(`open-sse/services/accountFallback.ts`), которая **уменьшает вдвое** сохранённый
`failureCount` (`Math.floor(failureCount / 2)`); когда он достигает `0`, запись
блокировки удаляется полностью. Парная функция `recordModelLockoutFailure()`
увеличивает счётчик (и эскалирует cooldown) при сбоях внутри окна эскалации.
Это затухание при успехе дополняет обычное истечение таймера — любой из двух
путей может повторно включить модель.

**Состояние:** блокировки хранятся **в памяти** (процессные `Map` с записями
`ModelLockoutEntry` с ключами `provider:connectionId:model`, блокировки точной
области — с ключами `provider:connectionId:exact:model`), а не сохраняются в
БД — они теряются при перезапуске. _Настройки_ сохраняются; активное
_состояние_ блокировок эфемерно.

## 4. Управление параллелизмом quota-share (v3.8.36)

Подписочные аккаунты (GLM, MiniMax и т. п.) часто принимают лишь ~1–3
одновременных запроса; превышение вызывает ошибки 429 и кулдауны. Проблема
особенно остра в комбо **quota-share** (`qtSd/…`), где несколько API-ключей
используют один апстрим-аккаунт. Три уровня защиты не дают перегрузить общий
аккаунт.

### Ограничение параллелизма на уровне подключения (`max_concurrent`)

Каждое подключение провайдера может объявлять потолок `max_concurrent`
(`provider_connections.max_concurrent`, задаётся в модальном окне подключения /
через API / в БД). Оставьте поле пустым, чтобы снять ограничение. Это
единственный параметр, управляющий уровнем сериализации, описанным ниже, —
установите его равным реальному параллелизму аккаунта (например, GLM ~1,
MiniMax ~2).

### Ограничения параллелизма по моделям (`modelConcurrency`)

Подключение может дополнительно объявлять точные потолки параллелизма для
отдельных моделей внутри карты `rateLimitOverrides`:

```json
{
  "rateLimitOverrides": {
    "maxConcurrent": 4,
    "modelConcurrency": { "glm-5": 1, "glm-4.7": 3 }
  }
}
```

Задаётся в модальном окне подключения (**Rate limit overrides → Per-model
concurrency caps**, по одной паре `model=cap` на строку) или через
`PATCH /api/providers/[id]` с той же структурой JSON. Семантика ключей:

- **На уровне подключения и по моделям:** `maxConcurrent` остаётся общим
  потолком для всего подключения. Когда действуют оба, оба шлюза
  захватываются атомарно в одном составном шлюзе
  (`global → provider → account → model`); фактическое поведение
  определяется более строгим из применимых лимитов.
- **Точное совпадение ключа модели:** ключ — это строка модели,
  передаваемая исполнителю после разрешения маршрутизации, — обычно
  «голый» апстрим-идентификатор модели (`glm-5`), а не клиентский алиас
  `provider/model` (`zai/glm-5` не совпадает с `glm-5`). Значения —
  положительные целые числа, задающие потолок одновременных запросов.
- **Локальная очередь, без автообнаружения:** избыточные запросы ставятся в
  локальную очередь с существующей семантикой очереди/таймаута
  (типизированные ошибки допуска `SEMAPHORE_TIMEOUT` /
  `SEMAPHORE_QUEUE_FULL`). OmniRoute не обнаруживает и не выводит политику
  апстрима — он применяет ровно те потолки, которые задал оператор.
  Насыщенный шлюз модели никогда не отключает провайдера и не создаёт
  постоянную блокировку модели; поведение апстрима при
  429/кулдауне/фолбэке остаётся последней линией защиты от ошибок.
- **Область действия — подключение и процесс:** потолки задаются для
  каждого подключения из базы данных и хранятся в памяти, поэтому два
  подключения, использующие один и тот же апстрим API-ключ, не
  координируются между собой.
- **Без настройки — без изменений:** если карта не задана (или поле в
  дашборде оставлено пустым), шлюз модели не добавляется. Пример
  конфигурации, не утверждающей никакого универсального лимита провайдера:

```text
glm-5=1
glm-4.7=3
```

### Сериализация запросов quota-share

Когда диспетчеризация quota-share нацелена на подключение, объявляющее
положительный `max_concurrent`, параллельные запросы к этому **аккаунту**
сериализуются через семафор на уровне подключения (ключ
`qsconn:<connectionId>`): избыточные запросы **ждут в очереди**, а не
перегружают аккаунт. Механизм работает в режиме **fail-open** — при
насыщенной очереди или таймауте запрос продолжается без слота, а не
отклоняется, если его вообще можно отправить. Переключается в **Настройки →
Устойчивость → Quota-share per-connection concurrency**
(`resilienceSettings.quotaShareConcurrencyLimit.enabled`, по умолчанию
включено). Без потолка `max_concurrent` поведение не меняется.

> Шлюз маршрутизации quota-share (`selectQuotaShareTarget`, DRR + P2C) сам
> по себе fail-open и лишь _понижает приоритет_ подключения, достигшего
> предела, — при пуле из одного подключения он не может жёстко ограничить
> поток, поэтому именно этот семафор реально сдерживает наплыв запросов.

### Повтор с учётом кулдауна для комбо

Для каждой стратегии комбо (если включено) запрос, который привёл бы к
фиксации 429 из-за КОРОТКОГО временного кулдауна, выжидает его и
отправляется повторно вместо возврата 429 — это покрывает окна TPM/RPM
уровня Gemini (~60 с retry-after) в мультимодельных комбо, например, когда
обе цели 2-модельного комбо упираются в rate limit на модель.
Ограничивается параметрами `comboCooldownWait` (`enabled`, `maxWaitMs`,
`maxAttempts`, `budgetMs`) в **Настройки → Устойчивость**. Ожидание никогда
не применяется при `quota_exhausted` (блокировка до полуночи) или причинах
auth/not-found.

Тот же шлюз покрывает случай до диспетчеризации (#16319): когда все цели
комбо пропускаются ещё до первой попытки, потому что их модели находятся в
короткой временной блокировке, путь с нулём попыток выжидает блокировку в
рамках тех же потолков и отправляет запрос повторно, вместо ответа
`503 ALL_TARGETS_SKIPPED` без подсказок. Когда ожидание недопустимо
(исчерпан потолок, попытки или бюджет, либо функция выключена), финальный
ответ повышается до `429 rate_limit_error` с `retry_after` / `reset_at` от
ближайшего истечения временной блокировки; блокировки quota, auth и
not-found сохраняют 503 без подсказок.

```text
#16319 · comboCooldownWait · pre-dispatch (attempts = 0)
all targets skipped + transient model lockout:
  enabled ∧ 0 < waitMs ≤ maxWaitMs ∧ attempt < maxAttempts ∧ budgetLeftMs ≥ waitMs
    → wait → re-dispatch
  wait = false → HTTP 429 rate_limit_error
  retry_after / reset_at ← earliest transient lock expiry
quota_exhausted / auth_error / not_found / not_found_local:
  no transient hint → HTTP 503 ALL_TARGETS_SKIPPED
```

## 5. Контроль приёма очереди запросов (v3.8.49 · issue #6593)

**Область применения**: локальная очередь ограничения частоты запросов на уровне пары «провайдер+подключение» (`open-sse/services/rateLimitManager.ts`, на основе Bottleneck), на один уровень ниже трёх механизмов, описанных выше.

**`maxWaitMs` ограничивает ожидание в очереди; `executionMaxWaitMs` ограничивает выполнение.**
Эти два параметра намеренно разделены, и ни один не подпитывает другой.

`resilienceSettings.requestQueue.maxWaitMs` — это **бюджет ожидания в очереди**: он покрывает ожидание слота у провайдера и последующее пребывание в состоянии QUEUED, а его таймер сбрасывается в тот момент, когда задание покидает QUEUED и начинает выполняться (`rateLimitManager.ts`, `wrappedFn`). Запрос, превысивший этот бюджет, никогда не доходит до апстрима. Значение по умолчанию — 30000 мс, задаётся константой `DEFAULT_REQUEST_QUEUE_MAX_WAIT_MS` в `src/lib/resilience/settings.ts` и фиксируется тестом `tests/unit/ratelimit-admission-control-6593.test.ts`, так что изменение этого значения окрасит тест в красный, а не оставит этот абзац незаметно устаревшим.

`resilienceSettings.requestQueue.executionMaxWaitMs` — это то, что Bottleneck получает как `expiration` задания, таймер которого запускается только после диспетчеризации. Это страховка для исполнителей без собственного таймаута апстрима; если собственный таймаут начала fetch у исполнителя больше, значение повышается до него, поэтому оно не может оборвать корректный ответ, уже находящийся в процессе получения. Значение по умолчанию — 600000 мс (10 мин).

Передача бюджета очереди в `expiration` — именно то, что раньше убивало неинкрементальные шлюзы посреди выполнения: они законно работают минутами до получения первых байтов. Именно поэтому истечение expiration выдаётся как `code: "RATE_LIMIT_EXECUTION_TIMEOUT"` (HTTP 504), тогда как бюджет очереди несёт код таймаута очереди. Любой из них можно переопределить через `RATE_LIMIT_MAX_WAIT_MS` / `RATE_LIMIT_EXECUTION_MAX_WAIT_MS` (переменные окружения) или панель управления (**Настройки → Resilience**). При нормализации оба значения ограничиваются диапазоном 1 мс – 24 ч.

**Приоритет для обоих параметров:** переменная окружения задаёт лишь значение _по умолчанию_. Значение, сохранённое в `resilienceSettings.requestQueue` (через панель управления / API-патч, хранится в `key_value`), имеет приоритет над ним, а заданные для конкретного подключения `rateLimitOverrides.maxWaitMs` / `.executionMaxWaitMs` — над ним. Поэтому установка переменной окружения на развёртывании, где уже есть сохранённое значение, ничего не меняет — вместо этого очистите или обновите сохранённую настройку.

Время пребывания в очереди ограничено `maxWaitMs`; а `maxQueueDepth` (ниже) ограничивает, сколько вызывающих сторон может одновременно находиться в очереди.

**Повторы, указанные в теле ответа: пейсинг или блокировка.** Тело ответа 429 может само указывать время ожидания (Gemini `RetryInfo.retryDelay`, текст «retry after Ns»), которое считывает `updateFromResponseBody`. Ожидание, укладывающееся в `maxWaitMs` подключения, — это пейсинг: лимитер опустошает свой резервуар на это время, и вызовы из очереди диспетчеризуются, когда он пополняется. Ожидание дольше `maxWaitMs` — не то, что очередь может «отсидеть»: на исчерпанную дневную квоту Gemini отвечает `retryDelay: "86399s"`. Передаваемый дальше заголовок `Retry-After` на пересобранном ответе 429 (#16528) уже заставляет движок фолбэка блокировать модель на это окно, но пауза лимитера на то же время всё равно затормозила бы любой вызов, попавший к ключу раньше времени (например, после сброса устойчивости), на весь `maxWaitMs`. Когда такое ожидание приходит из типизированной детали Google `RetryInfo` (с происхождением `google_rpc_retry_info`), а лимитер ключа уже привязан к модели (см. `getLimiterKey`), ответ 429 вместо этого превращается в блокировку модели на этом подключении (`lockModelForLongBodyRetry` в `open-sse/services/rateLimitManager/bodyRetryPause.ts`, с потолком в 24 ч), а лимитер остаётся без паузы. Выбор аккаунта пропускает такую модель через `isModelLocked()`, как и преддиспетчерская проверка комбо для целей, закреплённых за этим подключением. В antigravity, где лимитер работает на семейство квот, блокировка ставится на конкретную модель — как и остальные его квотные блокировки. Имя, запрошенное клиентом, тоже блокируется, если алиас разрешил его в эту модель, поскольку эти проверки используют запрошенное имя; блокируется оно точечно (`lockExactModel`), так что алиас, пересекающий границу семейства квот antigravity или области codex, никогда не заблокирует своё собственное. Подсказка в свободной форме, нетипизированный `retryDelay` или лимитер, общий для всего подключения, сохраняют паузу. Когда лимитер, только что пересобранный на пути обработки 429, всё же уходит на паузу, вызывающая сторона, у которой оставшееся время в очереди истекает раньше, чем пауза, немедленно отклоняется с кодом таймаута очереди (`checkLimiterPause`), а не ждёт истечения этого времени; зафиксированный момент окончания привязан к точке до создания лимитера — там, где Bottleneck запускает свой таймер пополнения, — и любое последующее изменение резервуара о нём «забывает». Покрыто тестами `tests/unit/rate-limit-long-body-retry-lockout.test.ts` и `tests/unit/rate-limit-body-retry-pause.test.ts`.

**`maxQueueDepth` — опциональный лимит приёма (новое).** `resilienceSettings.requestQueue.maxQueueDepth` ограничивает, сколько запросов может одновременно находиться в очереди (ещё не диспетчеризованных) для одной пары «провайдер+подключение». Когда очередь уже содержит `maxQueueDepth` запросов, новый запрос быстро отклоняется с типизированной ошибкой `code: "RATE_LIMIT_QUEUE_FULL"` **до того**, как он достигнет `limiter.schedule()`, — поэтому отказ обходится дёшево и происходит раньше любой последующей работы по сжатию промпта / трансляции для этого запроса. По умолчанию `0` = отключено, что сохраняет прежнее поведение с неограниченной очередью; допустимый диапазон 0–100000. Переопределяется через `RATE_LIMIT_MAX_QUEUE_DEPTH` (переменная окружения) или `resilienceSettings.requestQueue.maxQueueDepth` (панель управления / API-патч).

Сама проверка приёма — чистая функция (`open-sse/services/rateLimitManager/admission.ts::checkQueueAdmission`), поэтому её можно покрыть модульными тестами без реального лимитера Bottleneck.

> RFC, из которого возникло #6593, также предлагал флаг
> `bypassCompressionOnRateLimit`. Конвейер `open-sse/services/compression/` в

### Защитный механизм автоматического включения rate-limit и защита подключений (`rateLimitProtection`)

**Защитный механизм автоматического включения** (`resilienceSettings.requestQueue.autoEnableApiKeyProviders`, по умолчанию `true`):
По умолчанию OmniRoute автоматически включает защиту очередью от превышения лимита запросов для всех активных подключений провайдеров с API-ключом (`getProviderCategory(provider) === "apikey"`). Это гарантирует, что входящие запросы к чувствительным к лимитам upstream-ключам API ставятся в очередь и троттлятся через Bottleneck, а не приводят к всплеску upstream-ошибок 429. Защитный механизм можно переопределить через переменную окружения `RATE_LIMIT_AUTO_ENABLE` (`false`/`0`/`off` отключает, `true`/`1`/`on` принудительно включает), которая имеет приоритет над сохранённой настройкой дашборда (**Настройки → Отказоустойчивость** / `PATCH /api/resilience`).

**Семантика `rateLimitProtection` для отдельного подключения:**
Защита от rate-limit для отдельных подключений отслеживается через булево поле `rateLimitProtection` на подключениях провайдеров (сохраняется как `rate_limit_protection` в SQLite):

- **Явно включено (`rateLimitProtection === true`)**: Защита от rate-limit явно включена для этого подключения, независимо от категории провайдера и от того, активен ли защитный механизм автоматического включения.
- **Явно выключено (`rateLimitProtection === false`)**: Отключает явную защиту, но **не** выводит активное подключение с API-ключом из-под действия глобального защитного механизма автоматического включения. В `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) значения `false` и `undefined` эквивалентны: только `rateLimitProtection === true` трактуется как явное переопределение. Если `rateLimitProtection` равен `false` (или не задан), активное подключение с API-ключом всё равно соответствует условию автоматического включения и остаётся под защитой от rate-limit.
- **Отсутствие отказа для отдельного подключения**: Оператор в настоящее время не может задать «это конкретное активное подключение с API-ключом должно работать без защиты очередью от rate-limit», сохраняя автоматическое включение активным для остальных. Чтобы полностью работать с подключениями с API-ключами без очередей rate-limit, защитный механизм необходимо отключить глобально (`RATE_LIMIT_AUTO_ENABLE=false` или `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`).

**Поддерживаемые пути записи:**

- **`POST /api/rate-limits`**: Поддерживаемый путь записи для управления — переключение `rateLimitProtection` для подключения (`{ connectionId: string, enabled: boolean }`). Вызов с `enabled: true` включает явную защиту; вызов с `enabled: false` снимает явную защиту (при этом активные подключения с API-ключами остаются под действием глобального защитного механизма, если автоматическое включение активно).
- **`PUT /api/providers/[id]`**: Намеренно **не** принимает и не переключает `rateLimitProtection` (#11278). Обновление метаданных подключения провайдера через `PUT /api/providers/[id]` никогда не изменит сохранённое состояние защиты от rate-limit.

## 6. Сторожевой таймер пропускной способности медленного потока (#9709)

Опциональная защита `resilienceSettings.streamRecovery.throughputWatchdog` обнаруживает
апстрим, который всё ещё отправляет чанки, но выдаёт ответы ассистента со скоростью
ниже заданной скорости полезного вывода. Она намеренно отделена от таймаута простоя:
heartbeat-сообщения и метаданные не сбрасывают ни один из таймеров и не засчитываются
как прогресс. Она также отличается от жёсткого дедлайна попытки (#9153), который
остаётся абсолютным пределом безопасности независимо от качества вывода.

Сторожевому таймеру требуется период прогрева, за которым следует полное скользящее
окно, прежде чем он сможет прервать попытку. Он подсчитывает текстовые дельты из
событий вывода Chat Completions и Responses API (консервативная приближённая оценка
по байтам UTF-8), игнорирует события, содержащие только usage, и пустые события, а
также приостанавливает оценку, пока в обработке находятся события вызова инструментов
или рассуждений. По умолчанию он отключён и может быть включён с помощью
`STREAM_THROUGHPUT_WATCHDOG_ENABLED=true`; окно, прогрев, минимальная скорость и
минимальный измеримый вывод ограничиваются обычным слоем нормализации настроек
устойчивости.

Когда таймер включён, его прерывание применяется только к активной попытке апстрима.
До того как клиенту станут видны какие-либо байты, существующий путь раннего
восстановления в рамках того же аккаунта может переоткрыть попытку. После коммита
поток никогда не воспроизводится вслепую; только существующий безопасный контракт
продолжения в середине потока может сшить суффикс. Финализация остаётся однократной,
поэтому учёт usage и освобождение семафора не дублируются.

## 7. Переопределение статуса апстрима (неверно указанные ошибки квоты)

**Область:** один апстрим-шлюз, который сообщает о временном исчерпании квоты с неверным HTTP-статусом.

**Цель:** исправить вводящий в заблуждение статус ДО классификации, чтобы нижестоящие потребители (движок фолбэка, агрегация комбо, ответ клиенту) видели истинную, допускающую повтор природу сбоя.

Некоторые шлюзы сигнализируют о ВРЕМЕННОМ исчерпании квоты HTTP-статусом,
не допускающим повтор. `agentrouter.org` возвращает `403` (иногда `400`) с
телом на китайском (`用户额度不足` / `额度不足`) вместо стандартного `429`.
Клиенты вроде Claude Code трактуют `403` как постоянную ошибку и прерывают
сессию, а без исправления движок фолбэка классифицировал бы её как
`AUTH_ERROR` вместо события квоты.

**Реализация:**

- Реестр + матчер: `open-sse/config/upstreamStatusRestatement.ts` — список
  правил по провайдерам (`{id, fromStatuses, toStatus, textMarkers,
excludeMarkers, defaultRetryAfterMs}`), сопоставляемых через
  `applyStatusRestatement()`.
- Точка вызова: блок `providerFailure:` в `open-sse/handlers/chatCore.ts`
  (около строки 3654), сразу после того, как `parseUpstreamError()` разбирает
  ответ апстрима с ошибочным HTTP-статусом (`!providerResponse.ok`), и до
  запуска любой классификации, чтобы каждый нижестоящий потребитель видел
  исправленный статус. Ошибки, встроенные внутрь SSE-потока со статусом
  `200`, идут отдельным, более поздним путём разбора потока и **не**
  покрываются этим хуком на сегодня — известное ограничение, пока не нужное
  для неверного статуса agentrouter (который проявляется как ошибочный
  HTTP-статус).
- Допустимость повтора: `429` входит в `RETRY_AFTER_ELIGIBLE_STATUSES`
  (`open-sse/services/combo/unavailableRetryGate.ts`), поэтому
  переопределённая ошибка несёт реальное окно повтора вместо того, чтобы
  всплывать как мёртвый `403`.
- Синтетическое значение `60s` `defaultRetryAfterMs`
  (`upstreamStatusRestatement.ts`) — это только то, что переопределённый
  ответ сообщает **клиенту**; само по себе оно не является внутренней
  длительностью кулдауна/блокировки соединения — она управляется отдельно
  тем механизмом, который фактически обрабатывает переопределённую ошибку
  (эскалирующий бэкофф Connection Cooldown, §2, базовый `3s` для провайдеров
  с API-ключами; или Model Lockout, §3, для провайдеров с квотой на модель,
  как agentrouter). Роутер может стать допустимым к повтору внутри раньше,
  чем истечёт окно 60 секунд, которое он сообщает клиенту, — намеренный
  запас, а не баг.

Постоянные ошибки (`无权访问模型` у agentrouter — нет доступа к этой модели)
НИКОГДА не переопределяются: `excludeMarkers` накладывает вето на правило,
даже когда `textMarkers` совпадают, поэтому ошибка сохраняет исходный
статус, и ничто не повторяет её бесконечно. Соответствующее правило
классификации провайдера (`agentrouter-model-access-denied` в
`open-sse/config/providerErrorRules.ts`: `reason: "auth_error"`,
`scope: "model"`, объявленный базовый кулдаун `6h`) опрашивается
`checkFallbackError` (`open-sse/services/accountFallback.ts`) _до_ общего
раннего возврата `FORBIDDEN` категории apikey, с гейтом на
`honorsRuleLockScope(provider)` (#10334 — в настоящее время эксклюзивно для
agentrouter через allowlist `HONORS_RULE_LOCK_SCOPE_PROVIDERS` в
`providerErrorRules.ts`). Объявленный кулдаун 6 часов правила проходит как
`fallbackResult.baseCooldownMs`, но он по-прежнему питает существовавший
ранее путь блокировки по квоте на модель (`lockModelIfPerModelQuota()` /
`recordModelLockoutFailure()`, не изменённый #10334, кроме источника
кулдауна): он ограничивается сверху операторским `mlSettings.maxCooldownMs`
(по умолчанию `1_800_000ms` / 30 мин), как и любая другая блокировка модели,
а _сохранённая причина блокировки_ остаётся прежней захардкоженной
`"forbidden"`, а не `"auth_error"` правила — сквозным образом учитывается
только длительность кулдауна, а не строка причины. Само соединение остаётся
активным; соседние модели на том же соединении не затрагиваются.

Переопределённые ошибки квоты (`额度不足`) в продакшене доходят до правила
провайдера (`agentrouter-user-quota-exhausted`: `reason: "quota_exhausted"`,
`scope: "connection"`, собственный объявленный кулдаун отсутствует —
применяется масштабируемый бэкофф по умолчанию слоя персистентности).
Начиная с #10334, `scope` в `ProviderErrorRuleMatch` ДЕЙСТВИТЕЛЬНО
потребляется сквозным образом, но **только** для провайдеров из allowlist
`HONORS_RULE_LOCK_SCOPE_PROVIDERS` (`providerErrorRules.ts` — на сегодня
только `"agentrouter"`, с гейтом через `honorsRuleLockScope()`). Для любого
другого провайдера `scope` остаётся информационным, точно как до #10334.
`checkFallbackError` выставляет scope совпавшего правила как
`fallbackResult.ruleScope`; `isAgentrouterConnectionQuotaScope()`
(`src/sse/services/auth.ts`) — общий гард, который подтверждает, что
`ruleScope` действительно безопасно учитывать как сигнал на уровне всего
соединения с самовосстановлением (scope `"connection"`, reason
`quota_exhausted`, никогда `permanent`, никогда `creditsExhausted` — защита
от будущего правила, сочетающего scope `"connection"` с постоянным
состоянием аккаунта). Два потребителя вызывают его:

- **Персистентность** (`markAccountUnavailable()`, `src/sse/services/auth.ts`):
  вместо перехода в ветку **помодельной** блокировки passthrough-провайдера
  (у agentrouter `passthroughModels: true` → `hasPerModelQuota()`
  возвращает `true`) применяется **временное охлаждение соединения** —
  `testStatus: "unavailable"` + `rateLimitedUntil`, никогда не терминальный статус
  (`credits_exhausted`/`banned`/`expired`) — так что соединение самовосстанавливается
  по истечении охлаждения, а не требует ручного сброса учётных данных.
  Пропускается для соединений с `disableCooling: true` (#2997): такой отказ
  (opt-out) вместо этого проваливается в помодельную блокировку (задокументированный
  компромисс — см. комментарий в коде над этой веткой).
- **Маршрутизация комбо в рамках того же запроса** (`applyComboTargetExhaustion()`,
  `open-sse/services/combo/targetExhaustion.ts`): та же защитная проверка помечает
  соединение в хранящемся в памяти множестве `exhaustedConnections` с ключом
  `${provider}:${connectionId}`. Это пропускает только оставшуюся цель ТОГО ЖЕ ЗАПРОСА,
  которая _сама уже содержит именно этот `connectionId`_ в своём собственном
  объекте цели (`getExhaustedTargetSkipReason()`,
  `open-sse/services/combo/comboPredicates.ts`, `if (provider &&
connectionId)` перед поиском в `exhaustedConnections`) — обычное комбо
  из списка моделей, где соседние цели не имеют собственного закреплённого
  `connectionId`, а он разрешается лишь при каждой отправке из заголовка ответа
  `X-OmniRoute-Selected-Connection-Id`, никогда не попадает в это совпадение по ключу. Для
  этого распространённого случая настоящая защита от повторного использования оставшейся
  ветвью только что исчерпанного аккаунта — НЕ это множество Set, а слой персистентности,
  описанный выше (`rateLimitedUntil` соединения теперь указывает на момент в будущем), в
  сочетании с тем, что та же защитная проверка подавляет `transientRateLimitedProviders`
  для этой ошибки (см. «Двухступенчатая схема» и комментарий в коде к ветке
  `isAgentrouterConnectionQuotaScope` в `targetExhaustion.ts`): поскольку
  это множество Set остаётся непомеченным, принудительное разрешение
  `allowRateLimitedConnection` из `combo.ts`
  (`open-sse/services/combo.ts:1005-1013`, `:2734-2738`) НЕ срабатывает для
  оставшихся ветвей провайдера, поэтому фильтр `rateLimitedUntil` при выборе учётных
  данных (`src/sse/services/auth.ts:1238`) соблюдается как обычно, и
  оставшаяся ветвь либо выбирает другое, всё ещё подходящее соединение
  agentrouter, либо завершается ошибкой из-за отсутствия доступных учётных
  данных — она не пробивается обратно на соединение, которое эта ветка только что охладила.

### Двухступенчатая схема: переопределение статуса, затем классификация

Переопределение статуса (`upstreamStatusRestatement.ts`) и правила
классификации провайдеров (`open-sse/config/providerErrorRules.ts`,
`providerRuleRegistry`) — это отдельные реестры, оба используют в качестве ключей
идентификатор провайдера и текстовые маркеры, но они выполняются в разных местах и
служат разным целям: переопределение перезаписывает HTTP-статус на раннем этапе в `chatCore.ts`;
правила классификации выбирают `reason` фолбэка и фиксируют `scope`
(`model` / `provider` / `connection`) внутри `checkFallbackError()`
(`open-sse/services/accountFallback.ts`).

Правила классификации видят полный **текст** ошибки (необходимый для сопоставления маркеров
тела ответа, таких как `额度不足`) только для провайдеров, перечисленных в
списке разрешённых `FULL_TEXT_RULE_PROVIDERS` в `providerErrorRules.ts` — в настоящее время это только `"agentrouter"`. Для
каждого другого провайдера **встроенного каталога** `checkFallbackError` передаёт
`getProviderErrorRuleMatch` лишь структурированную ошибку (`{code, type}`), которой
достаточно для правил на основе заголовков/статуса/кодов, но которая не видит маркеров текста тела.
Хелпер `resolveRuleMatchBody()` выполняет этот выбор: полный текст ошибки
для провайдеров из списка разрешённых, структурированная ошибка — во всех остальных случаях. Добавление
**встроенного** провайдера в `FULL_TEXT_RULE_PROVIDERS` — это явное включение (opt-in) для каждого
конкретного провайдера — оно существует для того, чтобы путь по умолчанию для каждого провайдера,
не входящего в список, оставался неизменным с точностью до байта.

`scope` правила (`model` / `provider` / `connection`) — это отдельный opt-in,
независимый от `FULL_TEXT_RULE_PROVIDERS`: `checkFallbackError` лишь выставляет его как
`fallbackResult.ruleScope`, а нижестоящие потребители учитывают его как
нечто большее, чем информационная метка, только для провайдеров из
списка разрешённых `HONORS_RULE_LOCK_SCOPE_PROVIDERS` в том же файле (управляется через `honorsRuleLockScope()` — на сегодня только `"agentrouter"`). О том, что фактически делает совпадение
`scope: "connection"`, когда провайдер находится в этом списке разрешённых,
см. «Переопределённые ошибки квоты» выше.

**#11104 — правила, объявленные оператором, обходят оба списка разрешённых.** Оператор может
объявить правило для конкретного провайдера во время выполнения через `settings.providerErrorRules`
(`open-sse/config/providerErrorRules.ts::setOperatorProviderErrorRules`),
не редактируя этот файл. Ограничение операторского правила списками
`FULL_TEXT_RULE_PROVIDERS`/`HONORS_RULE_LOCK_SCOPE_PROVIDERS` — списками,
предназначенными для защиты поведения **по умолчанию** правил встроенного каталога — сделало
бы механизм настроек инертным для каждого провайдера, кроме уже
перечисленных там, поскольку само объявление правила уже является явным
opt-in оператора. `resolveRuleMatchBody()` и `honorsRuleLockScope()` обе сначала проверяют
`hasOperatorRuleForProvider()`: провайдер с операторским правилом получает
сырой текст ошибки, и его объявленный `scope` соблюдается, независимо от
того, присутствует ли он также в каком-либо из списков разрешённых.

**Известный пробел — `providerRuleRegistry` никогда не задействуется для HTTP 400.**
Ветка `BAD_REQUEST` в `checkFallbackError` классифицирует статус 400 целиком
через собственные массивы паттернов (`MODEL_ACCESS_DENIED_PATTERNS`,
`CONTEXT_OVERFLOW_PATTERNS` и т. д. в `accountFallback.ts`) и возвращает управление до того,
как будет достигнута расположенная выше ветка `configuredRule`/`getProviderErrorRuleMatch`.
Правило встроенного каталога (или операторское правило) со `status: 400`
синтаксически корректно, но никогда не сработает. Сегодня ни одно из существующих правил не нацелено на 400,
поэтому в продакшене ничего не затрагивается — но будущее правило для 400 потребует сначала доработать эту
ветку, что является более масштабным изменением, чем добавление правила (оно
переклассифицирует 400 для каждого провайдера, уже полагающегося на поведение массивов
паттернов), и выходит за рамки добавления правила для одного провайдера.

### Добавление нового шлюза, искажающего статус квоты

1. Зарегистрируйте один массив правил в `statusRestatementRegistry`
   (`open-sse/config/upstreamStatusRestatement.ts`). Делайте `textMarkers`
   специфичными для провайдера; никогда не используйте повторно общие
   английские фразы, которые пересекаются с
   `CREDITS_EXHAUSTED_SIGNALS` (`open-sse/services/accountFallback.ts`).
2. При необходимости зарегистрируйте правила классификации в
   `open-sse/config/providerErrorRules.ts` (`providerRuleRegistry`), чтобы
   выбрать правильную область блокировки (`connection` — для квоты на уровне
   аккаунта, `model` — для ошибок на уровне отдельной модели). В продакшене
   этот шаг действует только для провайдеров, чьим правилам нужен полный
   текст ошибки (маркеры тела): добавьте идентификатор провайдера в
   `FULL_TEXT_RULE_PROVIDERS` в том же файле — иначе `checkFallbackError`
   всегда передаёт правилу лишь структурированную ошибку `{code, type}`, и
   правило по тексту тела никогда не сработает на живом трафике. Правилам,
   которые срабатывают строго по `status`/`headers` (как у Opencode или
   Minimax), такое включение не требуется. Отдельно: если правило объявляет
   `scope: "connection"` и подразумевается реальное охлаждение на уровне
   всего соединения плюс пропуск комбо в рамках того же запроса (а не просто
   информационная метка), добавьте идентификатор провайдера в
   `HONORS_RULE_LOCK_SCOPE_PROVIDERS` в том же файле — именно этот список
   управляет применением логики вида `isAgentrouterConnectionQuotaScope()` в
   `markAccountUnavailable()` (`src/sse/services/auth.ts`) и
   `applyComboTargetExhaustion()`
   (`open-sse/services/combo/targetExhaustion.ts`); без него `scope`
   по-прежнему проходит через `fallbackResult.ruleScope`, но никакой логики
   на него не завязано.
3. Добавьте юнит-тесты по образцу
   `tests/unit/upstream-status-restatement.test.ts` и
   `tests/unit/agentrouter-error-rules.test.ts` (включая защитные проверки
   not-permanent / not-creditsExhausted, а также — если провайдеру нужен
   allowlist — тест, подтверждающий, что `resolveRuleMatchBody()` возвращает
   полный текст только для этого провайдера).

Изменения в `chatCore.ts`, `classifyError` или комбо не требуются.

#### Блокировка с бакетированием по egress-IP (#10880)

Провайдеры из `EGRESS_BUCKETED_LOCK_PROVIDERS` (семейство opencode)
рассматриваются как upstream с бакетированием по IP (бесплатный тариф
opencode бакетируется по IP, а не по аккаунту — см. #9611): ошибка со
статусом 429, классифицированная как `quota_exhausted` **или**
`rate_limit_exceeded`, охлаждает каждое соединение семейства из allowlist,
чей последний известный egress-IP совпадает с IP отказавшего соединения,
прежде чем ротация успеет их опробовать — это избавляет от N-1
гарантированно неудачных вызовов upstream (та же схема, что в
#10460/#10525). `rate_limit_exceeded` включён сюда намеренно: на пути
`markAccountUnavailable` специфичные для opencode правила никогда не
срабатывают (заголовки/тело не передаются в `checkFallbackError`, opencode
отсутствует в `FULL_TEXT_RULE_PROVIDERS`), поэтому ошибка 429, тело которой
содержит текст о квоте подписки ("monthly usage limit reached"),
классифицируется как `quota_exhausted` фолбэком по тексту квоты
(`buildSubscriptionQuotaFallback`, `accountFallback.ts`; охлаждение на 1
час) ещё до того, как будет достигнуто правило `status_429` — тогда как
ошибка 429 без текста о квоте (обычное ограничение частоты запросов)
классифицируется по правилу `status_429` как `rate_limit_exceeded` и всё
равно охлаждает семейство IP. Для провайдера из allowlist ограничение
частоты с бакетированием по IP — тот же сигнал, что и исчерпанная квота.
Честные ограничения:

- **Максимум усилий (best-effort)**: блокировка определяет последний известный `egress_ip` соединения из `proxy_logs` (окно 24 ч, синхронно, без кэша). Холодный кэш (egress-IP ни разу не проверялся) или отсутствие строки → отказавшее соединение всё равно охлаждается этой веткой (записывается, как и сегодня), просто ни одно соседнее соединение не блокируется.
- **Никогда не терминально**: кулдаун — это возобновляемое квотное окно (`testStatus: "unavailable"`); постоянное состояние никогда не выводится из сигнала уровня IP. Соединения с `disableCooling` полностью пропускают эту ветку.
- **Гранулярность блокировки меняется для семейства из allowlist**: это изменение области действия, а не только оптимизация для соседних соединений. opencode — провайдер с `passthroughModels`, поэтому до этой ветки ошибка 429 приводила к блокировке на уровне МОДЕЛИ; теперь она приводит к кулдауну соединения — в том числе для оператора с единственным соединением вообще без соседних. Именно такую гранулярность таблица правил opencode уже объявляет корректной (`scope: "connection"`, `providerErrorRules.ts`), но до сих пор она не применялась, потому что opencode не входит в `HONORS_RULE_LOCK_SCOPE_PROVIDERS`. Ветка сама записывает кулдаун отказавшего соединения и `backoffLevel`, зеркаля ветку agentrouter с областью на уровне соединения, и возвращает управление — блокировка на уровне модели и общий путь ниже никогда не достигаются.
- **Combo включён**: как и ветка agentrouter, эта область намеренно игнорирует понижение `persistUnavailableState`/`isCombo`, которое combo-вызывающий применяет к 429. Блокировка на уровне модели — не более слабая форма этой области, а неправильная единица: она ничего не говорит об исчерпанном IP, поэтому combo-ротация продолжала бы сжигать один гарантированно неудачный вызов на каждое соседнее соединение.
- **Безопасность соседних соединений**: соседнее соединение, уже находящееся в терминальном состоянии (banned/credits_exhausted) или уже имеющее более длинный кулдаун, никогда не перезаписывается.
- **Эксклюзивный allowlist**: расширение `EGRESS_BUCKETED_LOCK_PROVIDERS` — явное решение владельца; никакой общей разводки (паттерн #10334/#10419). Запрос соседних соединений привязывается к тому же allowlist, а не повторяет его как SQL-литерал, поэтому его расширение остаётся изменением в одну строку.
- **Ротация egress-IP, в обоих направлениях**: окно поиска (24 ч) значительно шире TTL кэша egress-IP (5 мин), поэтому «последний известный IP» — это история, а не текущее состояние. Если прокси соединения сменился в пределах окна, блокировка может **пропустить** действительно общий IP (записанный IP — новый, не исчерпанный) — и симметрично может **охладить соседнее соединение, которое с тех пор уже ушло** с исчерпанного IP. Второй случай стоит этому соседнему соединению одного окна кулдауна; оба — принятые ограничения поиска по истории в режиме best-effort.
- **Стоимость**: два ограниченных сканирования `proxy_logs` (с фильтрацией по окну через `idx_pl_timestamp`), только с частотой ошибок 429. Новый индекс не нужен (миграция 134 — YAGNI). Замерено на копии БД с реальным трафиком умеренного размера; экземпляр с высокой пропускной способностью хранит пропорционально больше строк в том же окне.

## Отладка

- Взвешенное комбо отвечает `503 all_targets_cooling_down` (заголовок `Retry-After` установлен, `diagnostics.excluded` перечисляет каждую цель с `model_lockout` / `circuit_open` / `provider_cooldown` / `unavailable`) → пул настроен и подключён, просто каждая цель исключена таймером отказоустойчивости; предупреждение `[COMBO] Weighted selection: every target excluded before dispatch — …` указывает причины и оставшиеся секунды. Ответ `404 no_executable_targets` от того же комбо означает, что таймер отказоустойчивости не участвовал (нечего запускать, или каждый аккаунт не прошёл проверку доступности). Реализовано в `open-sse/services/combo/pinRecovery.ts` на основе исключений, собранных в `targetResolution.ts`.
- Все ключи провайдера пропущены → проверьте и состояние circuit breaker, И `rateLimitedUntil`/`testStatus` каждого подключения.
- Провайдер навсегда исключён после окна сброса → код читает сырой `state` вместо `getStatus()`/`canExecute()`.
- Один ключ отказал, остальные должны работать → предпочтите cooldown подключения вместо circuit breaker.
- Отказывает только одна модель → предпочтите блокировку модели (model lockout) вместо cooldown подключения.
- Состояние должно самовосстанавливаться, но не восстанавливается → проверьте метку времени в будущем и путь чтения, который обновляет истёкшее состояние. Постоянные статусы требуют ручного изменения.

## Состояние во время выполнения — краткая справка для агента

> Перенесено дословно из `AGENTS.md` → раздел "Resilience Runtime State" (PR #12743), чтобы
> руководство для агента оставалось в пределах бюджета контекста в 40 тыс. Это сжатое,
> ориентированное на агента представление разделов выше; пронумерованные разделы остаются
> полным справочником.

В OmniRoute есть три связанных, но различных механизма обработки временных сбоев. При
отладке поведения маршрутизации разделяйте их области действия. См.
[диаграмму 3-уровневой отказоустойчивости](../diagrams/exported/resilience-3layers.svg)
(источник: [diagrams/resilience-3layers.mmd](../diagrams/resilience-3layers.mmd))
для наглядной карты.

### Circuit Breaker провайдера

**Область действия**: весь провайдер, например `glm`, `openai`, `anthropic`.

**Назначение**: прекратить отправку трафика провайдеру, который неоднократно даёт сбои на
уровне апстрима/сервиса, чтобы один нездоровый провайдер не замедлял каждый запрос.

**Реализация**:

- Основной класс: `src/shared/utils/circuitBreaker.ts`
- Связка гейта/выполнения чата: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- API статуса во время выполнения: `src/app/api/monitoring/health/route.ts`
- Общие обёртки: `open-sse/services/accountFallback.ts`
- Таблица сохраняемого состояния: `domain_circuit_breakers`

**Состояния** (4 — `src/shared/utils/circuitBreaker.ts`):

- `CLOSED`: обычный трафик разрешён.
- `DEGRADED`: зона раннего предупреждения — сбои пересекли порог деградации, но ещё не
  порог размыкания; трафик по-прежнему идёт, дашборды показывают предупреждение.
  Успешный тест подключения или тихое окно без новых сбоев возвращает его в `CLOSED`
  (окно описано в `docs/architecture/RESILIENCE_GUIDE.md`).
- `OPEN`: провайдер временно заблокирован; вызывающие получают ответ provider-circuit-open,
  либо комбо-маршрутизация переходит к другой цели.
- `HALF_OPEN`: таймаут сброса истёк; разрешается пробный запрос. Успех замыкает
  breaker, сбой снова размыкает его.

**Значения по умолчанию** (`open-sse/config/constants.ts` → `PROVIDER_PROFILES`, используются через
`DEFAULT_RESILIENCE_SETTINGS.providerBreaker` в `src/lib/resilience/settings.ts` →
`getCircuitBreaker(provider, …)` в `src/sse/handlers/chatHelpers.ts`). Breaker всего
провайдера работает на `circuitBreakerThreshold` / `circuitBreakerReset`:

| Профиль   | деградирует при | размыкается при (`circuitBreakerThreshold`) | сброс (`circuitBreakerReset`) |
| --------- | --------------: | ------------------------------------------: | ----------------------------: |
| OAuth     |             `5` |                                         `8` |                         `60s` |
| API-ключ  |             `7` |                                        `12` |                         `30s` |
| Локальный |   (вычисляется) |                                         `2` |                         `15s` |

`PROVIDER_PROFILES` также определяет `providerFailureThreshold` (10/15/2),
`providerFailureWindowMs` (15/30/5 мин) и `providerCooldownMs` (5/10/1 мин): они питают
**оконный гейт опционального глобального Provider Cooldown** (`PROVIDER_COOLDOWN_ENABLED`, по умолчанию
выключен) — запись уровня провайдера в `open-sse/services/providerCooldownTracker.ts` считается
охлаждающейся только после `providerFailureThreshold` сбоев внутри `providerFailureWindowMs`, а затем
охлаждается в течение `providerCooldownMs`. Это НЕ пороги живого breaker — не настраивайте их,
ожидая поведения breaker. Каждое значение по умолчанию можно переопределить через
переменные окружения `OMNIROUTE_PROVIDER_BREAKER_*` и `OMNIROUTE_CIRCUIT_BREAKER_*`;
точная для времени выполнения справочная таблица находится в `docs/architecture/RESILIENCE_GUIDE.md`.

Только статусы сбоев уровня провайдера должны приводить к срабатыванию breaker провайдера:

```ts
(408, 500, 502, 503, 504);
```

Не размыкайте breaker всего провайдера из-за обычных ошибок аккаунта/ключа/модели, как
большинство случаев `401`, `403` или `429`. Обычно они относятся к cooldown подключения или
блокировке модели. Обычный `403` провайдера с API-ключом должен быть восстановимым, если
только он не классифицирован как терминальная ошибка провайдера/аккаунта.

Прерыватель использует ленивое восстановление, а не фоновый таймер. Когда срок состояния `OPEN` истекает, операции чтения, такие как `getStatus()`, `canExecute()` и `getRetryAfterMs()`, обновляют состояние до `HALF_OPEN`, поэтому дашборды и построители кандидатов для комбо не продолжают бесконечно исключать провайдера с истёкшим сроком.

### Кулдаун соединения

**Область действия**: одно соединение/аккаунт/ключ провайдера.

**Назначение**: временно пропускать один неисправный ключ/аккаунт, позволяя другим соединениям того же провайдера продолжать обслуживать запросы.

**Реализация**:

- Путь записи/обновления: `src/sse/services/auth.ts::markAccountUnavailable()`
- Выбор/фильтрация аккаунтов: `src/sse/services/auth.ts::getProviderCredentials...`
- Расчёт кулдауна: `open-sse/services/accountFallback.ts::checkFallbackError()`
- Настройки: `src/lib/resilience/settings.ts`

Важные поля соединений провайдера:

```ts
rateLimitedUntil;
testStatus: "unavailable";
lastError;
lastErrorType;
errorCode;
backoffLevel;
```

Во время выбора аккаунта соединение пропускается, пока:

```ts
new Date(rateLimitedUntil).getTime() > Date.now();
```

Кулдауны тоже ленивые: когда `rateLimitedUntil` оказывается в прошлом, соединение снова становится доступным для выбора. При успешном использовании `clearAccountError()` очищает `testStatus`, `rateLimitedUntil`, поля ошибок и `backoffLevel`.

Поведение кулдауна соединения по умолчанию:

- Базовый кулдаун OAuth: `5s`.
- Базовый кулдаун API-ключа: `3s`.
- При ответе `429` для API-ключа следует отдавать предпочтение подсказкам о повторе от апстрима (`Retry-After`, заголовки сброса или парсируемый текст сброса), когда они доступны.
- Повторные устранимые сбои используют экспоненциальную задержку:

```ts
baseCooldownMs * 2 ** failureIndex;
```

Механизм защиты от эффекта лавинообразных запросов (thundering herd) не даёт параллельным сбоям на одном соединении многократно продлевать кулдаун или дважды увеличивать `backoffLevel`.

Терминальные состояния — это не кулдауны. Состояния `banned`, `expired` (которое становится терминальным только после N ограниченных повторных попыток через `EXPIRED_RETRY_MAX`) и `credits_exhausted` должны оставаться недоступными, пока не изменятся учётные данные/настройки или оператор не сбросит их вручную. Не перезаписывайте терминальные состояния временным состоянием кулдауна.

### Блокировка модели

**Область действия**: провайдер + соединение + модель.

**Назначение**: не отключать всё соединение, когда недоступна или ограничена квотой только одна модель для этого соединения.

Примеры:

- Провайдеры с квотами на отдельные модели, возвращающие `429`.
- Локальные провайдеры, возвращающие `404` для одной отсутствующей модели.
- Специфичные для провайдера ошибки прав доступа к режимам/моделям, например отдельные режимы Grok.

Блокировка модели реализована в `open-sse/services/accountFallback.ts` и позволяет тому же соединению продолжать обслуживать другие модели.

### Рекомендации по отладке

- Если все ключи провайдера пропускаются, проверьте как состояние прерывателя провайдера, так и `rateLimitedUntil`/`testStatus` каждого соединения.
- Если провайдер остаётся исключённым навсегда после окна сброса, проверьте, не читает ли код сырое значение `state` вместо использования `getStatus()`/`canExecute()`.
- Если один ключ провайдера не работает, но остальные должны работать, предпочитайте кулдаун соединения прерывателю провайдера.
- Если не работает только одна модель, предпочитайте блокировку модели кулдауну соединения.
- Если состояние должно восстанавливаться самостоятельно, у него должна быть временная метка в будущем/таймаут сброса и путь чтения, который обновляет истёкшее состояние. Постоянные статусы требуют ручного изменения учётных данных или конфигурации.

## Тестирование устойчивости (фаза 8 · блок C)

Помимо юнит-тестов логики устойчивости, три теста проверяют среду выполнения
в реальных условиях стресса/сбоев (все интеграционные/ночные — ни один не блокирует PR):

| Тест        | Что                                                                                                                                                                                                  | Запуск                                   |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| Chaos       | Фейковый апстрим-узел вносит реальные задержки/сбросы/таймауты/503; проверяет, что circuit breaker открывается/восстанавливается и `checkFallbackError` классифицирует 503 как восстановимый фолбэк. | `RUN_CHAOS_INT=1 npm run test:chaos`     |
| Heap-growth | ~500 потоков на `createSSEStream` под `--expose-gc`; падает, если куча растёт сверх лимита (защита от OOM #3069).                                                                                    | `npm run test:heap`                      |
| k6 soak     | Длительная нагрузка на `/api/monitoring/health`; пороги p95/ошибок.                                                                                                                                  | `k6 run tests/load/k6-soak.js` (nightly) |

Оркестрируется `.github/workflows/nightly-resilience.yml` (cron + dispatch). В
стандартном `test:integration` chaos и heap самопропускаются (без `RUN_CHAOS_INT`/`--expose-gc`).
