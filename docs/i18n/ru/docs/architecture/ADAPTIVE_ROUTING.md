Этот документ описывает основу адаптивной маршрутизации на базе обратной связи, добавленную в
OmniRoute. Она намеренно невелика: вводит типизированный канал результатов
маршрутизации, онлайн-сигнал качества, поступающий в существующий оценщик auto-combo,
необязательный экспортёр OpenTelemetry и эндпоинт объяснимости. Она **не**
заменяет существующий стек отказоустойчивости (circuit breaker, задержка повторного подключения,
блокировка модели, матрица состояния, autopilot) — она дополняет его.

## 1. Архитектурный контекст

OmniRoute — это плоскость данных с **горячим путём запросов** и **плоскостью
управления/аналитики**. Горячий путь должен оставаться быстрым, эффективным по памяти, асинхронным, отказоустойчивым и
предсказуемым. Оценивание, вычисление показателей качества, эксперименты и исторический анализ относятся
к плоскости управления.

```
ИИ-агент / IDE
      │
      ▼
┌─────────────────────┐
│    OmniRoute        │   плоскость данных (быстрая, синхронная, в памяти)
│  маршрутизация /    │
│  переключение при   │
│  отказе             │
│  состояние /        │
│  ограничения        │
│  кэш / потоковая    │
│  передача           │
└──────────┬──────────┘
           │ RoutingEvent (без ожидания результата, ~0.2µs)
           ▼
┌─────────────────────┐
│  Приёмники обратной │   плоскость управления (асинхронная, best-effort)
│  связи              │
│  трекер качества    │
│  экспортёр OTel     │
│  хранилище          │
│  объяснений         │
└──────────┬──────────┘
           ▼  оценка качества
      оценщик auto-combo
```

### Что уже существовало (проверено, не дублируется)

| Концепция                                     | Существующая реализация                                                                                                |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Доступность (можно ли направить трафик?)      | Circuit breaker (CLOSED/DEGRADED/OPEN/HALF_OPEN, сохраняется в БД), задержка повторного подключения, блокировка модели |
| Отчётность о состоянии                        | `providerHealthMatrix.ts`, `providerHealthAutopilot.ts`                                                                |
| Теневой трафик                                | `open-sse/services/combo/shadowRouting.ts`                                                                             |
| Ограничения                                   | `src/lib/guardrails/` (перехватчики до/после)                                                                          |
| Точный кэш                                    | `src/lib/semanticCache.ts` (на основе сигнатур)                                                                        |
| Оценщики / маршрутизация на основе оценок     | `src/lib/evals/`, `open-sse/services/evalRouting.ts`                                                                   |
| Объяснимость решений combo                    | `open-sse/services/combo/decisionTrace.ts`                                                                             |
| События панели мониторинга в реальном времени | `src/lib/events/eventBus.ts` (канал уведомлений UI, полезные нагрузки `unknown`, история из 100 записей)               |

Слой событий маршрутизации **не** является повторной реализацией `eventBus`: эта шина —
канал уведомлений панели мониторинга в реальном времени (типизированные _имена событий_, непрозрачные
полезные нагрузки, потребители UI). `RoutingEvent` — это типизированная структура _результата_
(задержка/токены/стоимость/исход/причина завершения), используемая приёмниками
обратной связи плоскости управления (трекером качества, экспортёром OTel, хранилищем объяснений).

### Чего не хватало (добавлено здесь)

1. **Типизированного события результата маршрутизации и абстракции приёмника** (`RoutingEvent` /
   `RoutingEventSink`). `decisionTrace` ограничен combo и существует только в памяти;
   `comboMetrics` — это накопительные счётчики; `call_logs` — необработанное асинхронное хранилище.
   Ни один из них не является типизированным каналом результатов на основе приёмников, на который могут подписаться трекер качества, экспортёр OTel
   или оценщик в стиле Future-AGI.
2. **Онлайн-сигнала качества** (EWMA) для качества вывода — ранее оценщик
   аппроксимировал «качество» только через статическое соответствие задаче и доли успешного прохождения оценок, включаемых явно.
3. **Необязательного экспортёра OTel без зависимостей**, использующего семантические соглашения GenAI.
4. **Эндпоинта объяснимости**, возвращающего фактические решения маршрутизации и состояние качества.

## 2. События маршрутизации (основа обратной связи)

Файлы: `open-sse/services/routing/events.ts`, `.../index.ts`

`RoutingEvent` содержит только метаданные маршрутизации:

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ...
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // объединение с разрешёнными значениями
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

`RoutingEventSink` — это аналог типажа `Send+Sync` в TypeScript:

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // должно выполняться за O(1), без синхронного ввода-вывода
}
```

Горячий путь вызывает `emitRoutingEvent(event)` один раз для каждого завершённого запроса
(обратный вызов завершения потоковой передачи, путь успешного выполнения без потоковой
передачи и путь ошибки из-за некорректного ответа 200 в `handleChatCore`). Диспетчеризация
представляет собой синхронную рассылку всем зарегистрированным приёмникам, но каждый
приёмник лишь добавляет данные в очередь или обновляет состояние в памяти. **Никаких
синхронных операций записи в базу данных и никакого сетевого ввода-вывода на горячем пути.**

Приёмники по умолчанию:

- `MemoryRoutingEventStore` — ограниченный (500) кольцевой буфер с новейшими
  записями в начале для конечной точки объяснения.
- Потребитель `QualityTracker` — обновляет оценку качества EWMA.
- `OtlpHttpsEventSink` — необязательный, включается только при заданной переменной
  `OMNIROUTE_OTEL_ENDPOINT` (или `OTEL_EXPORTER_OTLP_ENDPOINT`).

### Измеренные накладные расходы (честное сравнение)

`npm run bench:routing-events` на этой рабочей станции (100 тыс. итераций; операции
длительностью менее одной мкс измерялись в агрегированном виде в мкс/операцию,
поскольку процентили отдельных операций ниже разрешения таймера
`performance.now()`):

| Сценарий                                              | мкс/операцию | операций/с |
| ----------------------------------------------------- | ------------ | ---------- |
| базовый вариант (только оценка)                       | ~0.045       | ~22 млн    |
| базовый вариант + RoutingEvent (2 приёмника)          | ~0.168       | ~5.9 млн   |
| базовый вариант + событие + постановка OTel в очередь | ~0.163       | ~6.1 млн   |
| параллельное выполнение (8 чередующихся пакетов)      | ~0.18        | —          |

Дополнительные затраты на диспетчеризацию событий по сравнению с базовой оценкой
составляют ~0.12 мкс/запрос; приёмник OTel только добавляет данные в очередь
(добавление в буфер за O(1)) и не вносит измеримых затрат. Эти значения зависят
от конкретной машины и являются относительными — это не гарантия для
промышленной среды. Показатель «~0.2 мкс» в v1 был агрегированной оценкой;
эта методика отделяет базовые затраты на оценку от затрат на диспетчеризацию
событий.

## 3. Сигнал качества (состояние провайдера на основе обратной связи)

Файлы: `open-sse/services/routing/quality.ts`

В v2 **операционное** качество отделено от **семантического**:

- **Операционное** — определяется на горячем пути маршрутизации (HTTP 4xx/5xx,
  ошибки подключения, ответы 429, некорректные ответы, прерывания потока,
  `finish_reason=length`, успешные ответы с нулевым выводом, EWMA задержки/TTFT).
  Ответ 200 НЕ считается показателем семантического качества.
- **Семантическое** — фактическая ценность сгенерированного результата. Оно может
  быть получено ТОЛЬКО от оценщика через `setSemanticQuality()`. Его значение
  остаётся `null`, пока оценщик его не предоставит, и оно никогда не влияет
  на операционную оценку.

Состояние для каждой пары (провайдер, модель) (EWMA + ограниченные счётчики):

- `successEwma` — EWMA (α=0.2) успешности результата.
- `latencyEwma` / `ttftEwma` — EWMA задержки (α=0.1).
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`.
- `recencyMs` — насколько недавно модель наблюдалась в последний раз.

### Учёт достоверности / количества выборок

`confidence = clamp01(samples / 50)`, а оценка, возвращаемая механизму оценивания,
смещается к нейтральной средней точке:

```
score = 0.5 + confidence * (operational - 0.5)
```

Следствия (проверенные тестами):

- Холодный провайдер (0 выборок) получает оценку **0.5** — он не подвергается
  несправедливому штрафу, но и не может превзойти провайдера с тысячами надёжных
  наблюдений.
- Провайдер с 7 случайными успешными результатами смещается к 0.5 (он никогда
  не доминирует благодаря оптимистической инициализации).
- Провайдер с 50 и более выборками сходится к своей фактической операционной
  оценке.
- Деградация и восстановление происходят постепенно (EWMA), а один единичный
  сбой не разрушает оценку исправного провайдера.

`ProviderQuality` предоставляет `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }`.

Эти данные передаются механизму оценки auto-combo в качестве фактора оценки
`quality`:

- `ScoringFactors.quality` / `ScoringWeights.quality` в
  `open-sse/services/autoCombo/scoring.ts`.
- `DEFAULT_WEIGHTS`: `health` 0.1905 → 0.1605, `quality` 0.03. Сумма остаётся равной 1.0.
- `buildAutoCandidates` заполняет `candidate.quality` данными из трекера;
  для кандидатов без данных по умолчанию используется нейтральное значение
  **0.5** (холодный кандидат не получает ни преимуществ, ни штрафов).

Замкнутый цикл:

```
RoutingEvent → QualityTracker → getQualityScore → фактор качества auto-combo
      ↑                                                    │
      └────── результат запроса (handleChatCore) ←─────────┘
```

### Жёсткое исключение и мягкий штраф

Сигнал качества представляет собой только **мягкое адаптивное предпочтение**.
Жёсткое исключение остаётся за существующим стеком обеспечения отказоустойчивости:
разомкнутый автоматический выключатель, исчерпание квоты, ошибка аутентификации,
блокировка модели — оценка качества не влияет ни на один из этих факторов.
Провайдер, чья оценка качества временно снижается, получает более низкий
приоритет, но никогда не отключается полностью.

## 3b. Канонические временные метрики потока (TTFT / ITL)

Файлы: `open-sse/utils/streamTiming.ts`

`createStreamTiming()` — единая точка инструментирования потоковой обработки,
подключённая к `createSSEStream` (`open-sse/utils/stream.ts`):

- `markByte()` — получение первого фрагмента от вышестоящего сервиса.
- `markForward()` — отправка первого фрагмента клиенту (используется для TTFT).
- `markInterrupted()` — тайм-аут/прерывание/ошибка потока до его штатного завершения.
- `ttft()` = задержка до первого отправленного SSE-фрагмента. **Это НЕ TTFT на уровне токенов** —
  один SSE-фрагмент может содержать ноль, один или несколько токенов. Это точно
  отражено в документации.
- `avgItlMs()` = средний интервал между фрагментами (прокси-метрика задержки ITL).

TTFT/ITL и признак прерывания передаются в `RoutingEvent` (`ttftMs`, `itlMs`) и
экспортируются приёмником OTel как атрибуты спанов GenAI/OmniRoute.

## 4. Наблюдаемость OpenTelemetry / GenAI

Файлы: `open-sse/services/routing/otel.ts`

- Экспортёр OTLP/HTTP JSON без зависимостей (использует глобальный `fetch`, без
  SDK `@opentelemetry/*`).
- Спаны соответствуют семантическим соглашениям GenAI (`gen_ai.provider.name`,
  `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`,
  `gen_ai.completion.finish_reason`, `gen_ai.system`), а также содержат атрибуты
  маршрутизации OmniRoute (результат, статус, TTFT, повторные попытки, резервное
  переключение).
- `record()` только помещает данные в ограниченный буфер (O(1)); фоновый таймер
  асинхронно выполняет сброс через `POST {endpoint}/v1/traces`. При перегрузке
  самые старые события удаляются (счётчик `dropped`) — без обратного давления на
  плоскость данных.
- **Отключено, если не настроено.** Необходимо задать
  `OMNIROUTE_OTEL_ENDPOINT` (или `OTEL_EXPORTER_OTLP_ENDPOINT`); в противном
  случае приёмник не регистрируется и код OTel вообще не выполняется.

## 5. Объяснимость

- `GET /v1/explain/routing` возвращает последние `RoutingEvent` (фактические
  решения, сначала самые новые) и снимок качества по провайдерам/моделям.
- Аутентификация соответствует `/v1/combos` (Bearer API key или сессия панели
  управления; анонимный доступ в локальных однопользовательских развёртываниях
  с `REQUIRE_API_KEY=false`).
- Трассировки отдельных вызовов на уровне комбинаций по-прежнему доступны через
  существующий `decisionTrace.ts` (заголовок `X-OmniRoute-Combo-Trace`).
- Безопасность: события содержат только метаданные маршрутизации, но никогда не
  содержат запросы, тела сообщений или учётные данные.

## 6. Интеграция плоскости оценки (готовность к Future AGI)

OmniRoute рассматривает Future AGI (или любой другой оценщик) как **потенциальный
бэкенд интеллектуальной обработки/оценки, а не как зависимость**. Предусмотрены
следующие точки интеграции:

- `RoutingEventSink` может асинхронно пересылать события оценщику.
- `MemoryRoutingEventStore` и снимок качества предоставляют оценщику исходный
  поток решений.
- Будущий `Evaluator` (детерминированный, локальная модель-судья, HTTP, WASM)
  сможет получать события/трассировки и возвращать `QualityScore`, который
  поступает в тот же путь `getQualityScore`/коэффициента качества.
- Существующая маршрутизация на основе оценок
  (`open-sse/services/evalRouting.ts`) уже меняет порядок целей комбинации по
  долям успешных прохождений `eval_runs`, когда эта функция включена.

Оценка не выполняется синхронно в пути обработки запроса, а шлюз полностью
работоспособен без оценщика.

## 7. Итоговый архитектурный обзор

1. **Что остаётся в синхронном горячем пути?** Маршрутизация/оценка,
   предварительные проверки защитных ограничений, поиск в кэше и одна веерная
   отправка `emitRoutingEvent` (~0,12 мкс сверх базового времени оценки) в
   приёмники в памяти.
2. **Что перенесено в асинхронную обработку?** Экспорт OTel (таймер + fetch),
   сохранение `call_logs`/данных об использовании, запись в семантический кэш;
   расчёт качества выполняется в памяти за O(1) (асинхронность не требуется).
3. **Как результат маршрутизации превращается в обратную связь?**
   `handleChatCore` генерирует `RoutingEvent` → `QualityTracker` обновляет
   состояние EWMA → `getQualityScore` передаёт значение коэффициенту `quality`
   автоматической комбинации.
4. **Как качество влияет на последующую маршрутизацию?** Низкая оценка качества
   уменьшает взвешенную оценку соответствующего провайдера/модели в
   `scoreAutoTargets`, поэтому модели с ухудшившимися показателями постепенно
   получают меньший приоритет и восстанавливают его по мере улучшения EWMA.
5. **Как Future AGI может интегрироваться, не становясь зависимостью?** Через
   интерфейс `RoutingEventSink` / будущий адаптер `Evaluator` — без жёстко
   заданной зависимости.
6. **Что происходит, когда оценщик недоступен?** Маршрутизация не затрагивается;
   для моделей без наблюдаемого сигнала используется нейтральная оценка качества
   (1.0).
7. **Что происходит, когда телеметрия недоступна?** Приёмник OTel просто не
   регистрируется; остальная часть слоя маршрутизации работает без изменений.
8. **Что происходит при перегрузке?** Буфер OTel удаляет самые старые события;
   размер хранилища качества и кольцевого буфера ограничен конструктивно;
   обратное давление отсутствует.
9. **Как состояние провайдера восстанавливается после ухудшения?** EWMA снова
   сходится по мере накопления успешных результатов; механизм прогрева сохраняет
   нейтральную оценку для ещё не прогретых моделей; автоматический выключатель
   независимо восстанавливается посредством пробных запросов в состоянии
   HALF_OPEN.
10. **Какие предложенные функции намеренно НЕ были реализованы и почему?**
    - Теневой трафик / эксперименты — уже реализованы
      (`combo/shadowRouting.ts`); повторно не создавались.
    - Защитные ограничения — уже реализованы (`src/lib/guardrails/`); не
      дублировались.
    - Семантический кэш — уже реализован (`src/lib/semanticCache.ts`); не
      дублировался.
    - Полноценная платформа управления экспериментами, инструменты для работы с
      наборами данных, платформа оптимизации запросов, векторная БД или
      обязательная внешняя инфраструктура OTel — выходят за рамки компактной
      плоскости данных.
    - Структура Rust `RoutingEvent` — плоскость данных реализована на TypeScript;
      тип TS является адаптированным эквивалентом.

## 9. Тесты

- `tests/unit/routing-events.test.ts` — нормализация событий, классификация
  статусов, ограниченный кольцевой буфер, рассылка по приёмникам + изоляция.
- `tests/unit/routing-quality.test.ts` — прогрев EWMA, восстановление после сбоев/успехов,
  штрафы за аномалии, обработка временного статуса 429, снимок состояния, сброс.
- `tests/unit/routing-scoring-quality.test.ts` — корректность весов, нейтральное
  значение по умолчанию, ранжирование по коэффициенту качества.
- `tests/unit/routing-otel.test.ts` — управление включением, содержимое диапазона GenAI, асинхронная
  отправка, отбрасывание при перегрузке.
- `tests/unit/routing-events-concurrency.test.ts` — тысячи событий, соблюдение ограничения
  кольцевого буфера, изоляция приёмника, выбрасывающего исключения, чередующиеся асинхронные всплески,
  сброс во время вставок.
- `tests/unit/routing-adaptive-e2e.test.ts` — детерминированный сквозной цикл через
  реальную функцию оценки `scoreAutoTargets`: исправное состояние → деградация → восстановление → кратковременный сбой, а также
  сценарии холодного запуска и случайно успешного холодного провайдера.
- `tests/unit/stream-timing.test.ts` — TTFT (первый перенаправленный фрагмент), ITL,
  первый байт в сравнении с первой пересылкой, прерывание, безопасная обработка некорректных/пустых фрагментов.
