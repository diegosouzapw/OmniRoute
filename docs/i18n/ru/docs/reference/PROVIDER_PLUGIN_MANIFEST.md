`open-sse/config/providerPluginManifest.ts` определяет JSON-совместимый контракт
плагина провайдера. `open-sse/config/providerPluginManifestRegistry.ts` связывает этот
контракт с текущим реестром провайдеров для сайдкаров, таких как Bifrost,
CLIProxyAPI или будущий маршрутизатор на Go/Rust. Реестр TypeScript остаётся
источником истины, однако сайдкары могут использовать манифест без импорта
кода исполнителей, настроек OAuth по умолчанию, заголовков или состояния окружения процесса.

Тот же манифест доступен по HTTP через
`GET /api/v1/provider-plugin-manifest` для сайдкаров, работающих вне процесса.

OmniRoute сообщает этот URL Bifrost и CLIProxyAPI через заголовок запроса
`X-OmniRoute-Provider-Manifest-Url`. Задайте
`OMNIROUTE_PROVIDER_MANIFEST_URL`, если сайдкару нужен публичный URL или URL в сети
контейнеров вместо источника локального запроса.

## Обновление манифеста

Конечная точка HTTP возвращает `Cache-Control: public, max-age=60` и строгий
`ETag`. Сайдкар должен сохранять последний проверенный манифест и отправлять его ETag
в `If-None-Match` при обновлении. Ответ `304 Not Modified` не содержит тела;
сайдкар продолжает использовать кэшированный манифест. Если проверенного кэшированного манифеста нет,
сайдкар должен выполнить безусловный запрос, а не принимать ответ `304`.

## Цель

Перевести метаданные провайдеров на плагинный контракт, чтобы в перспективе
горячий путь обработки запросов мог обслуживаться сайдкаром с меньшей задержкой, в то время как OmniRoute сохранит
маршрут TypeScript в качестве шлюза политик и резервного варианта. Манифест носит аддитивный характер: сам по себе он
не меняет маршрутизацию запросов.

## Контракт

Манифест содержит:

- идентификатор и псевдоним провайдера
- формат вышестоящего сервиса и имя исполнителя
- тип аутентификации, заголовок аутентификации и необязательный префикс аутентификации
- статические метаданные конечной точки
- пригодность для сайдкара и явные причины, по которым провайдер должен оставаться на пути TS
- JSON-совместимые метаданные моделей, такие как длина контекста, флаги поддержки изображений/рассуждений и
  неподдерживаемые параметры
- теги возможностей, включая `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` и `usage-supported`

Манифест намеренно исключает:

- секреты клиентов OAuth и секретные значения по умолчанию
- разрешение окружения во время выполнения
- заголовки запросов и публичные вспомогательные средства для учётных данных
- динамические построители URL
- функции исполнителей
- внутреннее устройство пула сессий

## Теги возможностей

`capabilities` — это отсортированный массив тегов, полученных из записи реестра. Интеграциям
следует использовать его как машиночитаемый ответ на вопрос «что умеет этот провайдер» вместо
повторного анализа исходного кода TypeScript.

| Тег                  | Значение                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| `apikey`             | Принимает ключ API (`authType` имеет значение `apikey` или `optional`).                          |
| `oauth`              | Использует поток OAuth или сеанса.                                                               |
| `responses`          | Предоставляет базовый URL OpenAI Responses API.                                                  |
| `passthrough-models` | Предоставляет модели напрямую из вышестоящего сервиса вместо статического каталога.              |
| `custom-executor`    | Запускает нестандартный исполнитель, поэтому остаётся на пути TypeScript.                        |
| `sidecar-candidate`  | Отражает `sidecar.eligible` — можно безопасно рассматривать для импорта в сайдкар.               |
| `usage-fetch`        | Имеет подключённый механизм получения данных об использовании или квоте (`getUsageForProvider`). |
| `usage-supported`    | API использования принимает этого провайдера (`isSupportedUsageConnection`).                     |

`usage-fetch` предназначен только для обнаружения. Он сообщает, что OmniRoute умеет получать данные об использовании для
провайдера; он не активирует получение данных, не изменяет семантику квот и не означает, что
виджет квоты на панели управления включён для этого провайдера — этот виджет отдельно управляется
`USAGE_SUPPORTED_PROVIDERS`. Источником истины является `USAGE_FETCHER_PROVIDERS` в
`open-sse/services/usage/fetcherProviders.ts`.

Этот список индексируется строками, которые принимает диспетчер данных об использовании, поэтому в нём смешаны канонические идентификаторы
и псевдонимы, и он немного длиннее числа провайдеров с тегами: записи,
не являющиеся чат-провайдерами в реестре манифеста (например, поисковый провайдер `firecrawl`
и ACP-провайдер `amazon-q`), не имеют записи манифеста, к которой можно было бы добавить тег.

`usage-supported` указывает, принимают ли серверные маршруты и маршруты панели управления для данных об использовании подключение
этого провайдера. Он отражает `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
и `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), оба из которых управляются
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). В отличие от
`usage-fetch`, он выдаётся только на основе идентификатора провайдера — проверка во время выполнения использует
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` без разрешения псевдонимов, поэтому манифест
сохраняет то же правило. У этих двух тегов разные области применения: 3 провайдера имеют только
`usage-fetch` (`opencode`, `opencode-zen`, `xai`), а 1 — только
`usage-supported` (`xiaomi-mimo-token-plan`), поэтому один тег не подразумевает другой.

## Использование sidecar-компонентов

Sidecar-компоненты должны рассматривать `sidecar.eligible` как консервативный сигнал о потенциальной применимости, а не как безусловное решение о маршрутизации. Первыми целевыми кандидатами для импорта должны быть провайдеры, использующие API-ключи, статические конечные точки и исполнитель по умолчанию. Провайдеры с пользовательскими веб-исполнителями, потоками OAuth/сеансов, динамическими построителями URL или конфигурацией пула должны оставаться на резервном пути TypeScript до тех пор, пока sidecar-компонент не реализует эквивалентное поведение, а телеметрия не подтвердит паритет.

Предлагаемые этапы миграции:

1. Сгенерировать и проверить манифест плагинов провайдеров на основе реестра TS.
2. Научить Bifrost или CLIProxyAPI импортировать манифест для провайдеров с API-ключами и статическими конечными точками.
3. Маршрутизировать подходящих провайдеров через sidecar-компонент под управлением `OMNIROUTE_RELAY_BACKEND`, сохраняя включенным резервный путь TS.
4. Переводить провайдеров только после того, как доля успешных запросов, задержка p99, потоковая передача и обработка неподдерживаемых параметров будут соответствовать пути TS.
5. Добавлять нативные для sidecar-компонента плагины для пользовательских исполнителей по одному семейству провайдеров за раз.

## Почему не следует встраивать провайдеров непосредственно в Next

Фронтенд Next не должен отвечать за выполнение запросов к провайдерам. Он должен обращаться к границе API. Затем бэкенд может решить, использовать ли исполнитель TypeScript, Bifrost, CLIProxyAPI или будущий нативный sidecar-компонент. Это позволяет централизовать подписание запросов, проверки по спискам разрешений, политики БД и резервное поведение до передачи управления какому-либо sidecar-компоненту.
