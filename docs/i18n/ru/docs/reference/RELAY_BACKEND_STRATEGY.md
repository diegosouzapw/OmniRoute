## Краткое описание

OmniRoute теперь поддерживает три режима ретрансляции для `/api/v1/relay/chat/completions`:

- `ts`: использовать внутрипроцессный ретранслятор TypeScript.
- `bifrost`: принудительно использовать шлюз Bifrost.
- `auto`: по возможности предпочитать Bifrost, а при сбое переключаться на TypeScript.

При высокой частоте запросов (большом количестве токенов в день и практически постоянной пропускной нагрузке) оптимальная стратегия — сделать путь резервного переключения явным и быстрым, чтобы основной путь никогда не блокировался из-за неработающего сайдкара.

## Поведение режимов

- `ts`
  - Минимальная эксплуатационная сложность.
  - Вся маршрутизация и валидация выполняются в Node.
  - Доступность не зависит от сайдкара.
- `bifrost`
  - Принудительно направляет все запросы через шлюз-сайдкар.
  - Автоматическое резервное переключение отсутствует.
  - Полезен только в тех случаях, когда работоспособность и задержка сайдкара гарантированы.
- `auto`
  - Сайдкар используется, когда он доступен и включён.
  - Неудачные попытки приводят к установке заголовков резервного переключения и возврату трафика в TS, чтобы успешность запросов оставалась гарантированной в заданных пределах.
  - Этот режим — наиболее безопасный выбор для рабочей среды, когда время безотказной работы важнее строгой маршрутизации исключительно через сайдкар.

## 9router и CLIPROXYAPI сегодня

9router и CLIPROXYAPI — это интеграции, которые исторически предоставляли пути совместимости для вышестоящих провайдеров.

- 9router — это встроенный путь для оркестрации вышестоящих сервисов и обеспечения совместимости.
- CLIPROXYAPI — это мост прокси-API для трафика в стиле CLI / SDK.
- Bifrost стабилизируется как вынесенный во внешний процесс путь для случаев, когда требуется отдельный переход через сайдкар и локальная диспетчеризация с низкой задержкой.

Если вы сейчас сравниваете 9router/CLIPROXYAPI:

- Выполняйте проверку подписи запросов, списков разрешений и политик БД в маршруте API до передачи запроса.
- Если рабочему процессу требуется строгое использование сайдкара и меньший разброс времени обработки отдельных запросов, задайте `OMNIROUTE_RELAY_BACKEND=bifrost`.
- Если вам нужна устойчивость сайдкара с постепенной деградацией при инцидентах, задайте `OMNIROUTE_RELAY_BACKEND=auto`.

## Контракт границы бэкенда

Стабильной продуктовой границей является API ретрансляции OmniRoute, а не реализация панели управления. Панель управления Next.js может устанавливать, настраивать и контролировать локальные сервисы, однако маршрутизация запросов должна начинаться через API ретрансляции, а передача запросов должна происходить за этой границей.

Долгосрочные варианты бэкенда:

- Сохраните ретранслятор TypeScript в качестве внутрипроцессного пути применения политик и резервного переключения. Аутентификация, списки разрешений, нормализация запросов, учёт и проверки безопасности остаются здесь и выполняются до передачи любому бэкенду.
- Используйте Bifrost в качестве предпочтительного высокопроизводительного сайдкара уровня Tier-1, когда развёртыванию требуется меньший разброс времени маршрутизации, централизованная ротация провайдеров или горизонтальное масштабирование между несколькими репликами OmniRoute.
- Сохраните 9router и CLIPROXYAPI в качестве встроенных сервисов совместимости. Они выполняются как контролируемые локальные процессы и полезны, когда их поведение в отношении провайдеров/CLI является необходимым адаптером, но не должны становиться стандартным механизмом маршрутизации уровня Tier-1.
- Не позволяйте панели управления передавать произвольные URL-адреса сервисов в основной путь. URL-адреса, указанные через пользовательский интерфейс, являются входными параметрами конфигурации; код маршрутизации должен находить зарегистрированные бэкенды, прошедшие проверку работоспособности, на основании серверных настроек и состояния диспетчера процессов.
- На данный момент для контролируемых сервисов предпочтительнее использовать HTTP через loopback-интерфейс, поскольку управляемые процессы уже предоставляют API, совместимые с HTTP, защитный механизм маршрута может проводить аудит этой границы, а поведение при сбоях и резервном переключении отображается в журналах запросов. Добавление транспорта на основе SDK или сокетов в будущем оправдано только в том случае, если оно заметно снижает задержку маршрутизации p99, не ослабляя изоляцию или семантику резервного переключения.

Таким образом, для развёртывания с очень высокой пропускной способностью стандартным выбором является `auto` с включённым Bifrost: используйте сайдкар на Go в основном пути, сохраняя резервное переключение на TypeScript для поддержания высокой доли успешных запросов. Используйте `bifrost` только в том случае, если строгое использование исключительно сайдкара важнее постепенной деградации.

## Рекомендации для высокой пропускной способности

Для стабильно высоких RPM/RPS и строгого SLO успешности:

1. Используйте `auto` с практичным периодом ожидания и телеметрией сбоев.
2. Выполняйте валидацию вышестоящих сервисов и проверку API-ключей на границе маршрута TypeScript.
3. Включите явные заголовки/счётчики, чтобы система оповещения отслеживала частоту и причины резервных переключений.
4. Настройте тайм-ауты сайдкара так, чтобы сбои происходили быстро, а ожидание не продолжалось бесконечно.
5. Поддерживайте исправную работу автоматического перезапуска сервисов и цикла телеметрии состояния, чтобы резервное переключение действительно оставалось исключительной ситуацией.

## Рекомендуемая базовая конфигурация

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- Оставьте включёнными проверки API-ключей, списков разрешений, санитайзера и ограничений частоты в обработчиках маршрутов (они всегда выполняются до перенаправления запросов нижестоящим сервисам).
- Экспортируйте метрики резервного переключения из обратного прокси и журналов запросов, чтобы сбои сайдкара становились видимыми в течение одной минуты.

## Контракт плагина провайдера

Сайдкары должны импортировать метаданные провайдеров через JSON-совместимый манифест
плагина провайдера, а не зависеть от внутренних компонентов исполнителя TypeScript. Условия
допуска сайдкаров и этапы миграции описаны в документе
[Манифест плагина провайдера](./PROVIDER_PLUGIN_MANIFEST.md).
