## Быстрый запуск

> **Самостоятельное размещение одной командой?** См.
> [руководство по самостоятельному размещению](../getting-started/SELF_HOST_GUIDE.md) —
> `docker compose -f docker-compose.selfhost.yml up -d` (опубликованный образ +
> Redis, доступ только через loopback-интерфейс, без выбора профиля). Приведенный ниже быстрый запуск —
> это вариант с одним контейнером для пользователей, у которых Redis уже запущен отдельно.

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## С файлом переменных окружения

```bash
# Сначала скопируйте и отредактируйте .env

  --stop-timeout 40 \
  --env-file .env \
  -p 20128:20128 \
  -v omniroute-data:/app/data \

```

## Docker Compose

```bash
# Базовый профиль (без CLI-инструментов)
docker compose --profile base up -d

# Профиль CLI (встроенные Claude Code, Codex и OpenClaw)
docker compose --profile cli up -d

# Профиль хоста (прежде всего для Linux; монтирует CLI-файлы хоста в режиме только для чтения)
docker compose --profile host up -d

# Веб-профиль (Chromium/Playwright для провайдеров веб-сессий)
docker compose --profile web up -d

# Объединение CLI и сопутствующего контейнера CLIProxyAPI
docker compose --profile cli --profile cliproxyapi up -d
```

## Доступные профили

OmniRoute поставляется с профилями Compose для основных вариантов развертывания. Выберите профиль, соответствующий вашей среде.

| Профиль               | Сервис           | Когда использовать                                                                                                                                                             | Команда                                      |
| --------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| `base` (по умолчанию) | `omniroute-base` | Сервер без графического интерфейса / минимальная среда выполнения, без встроенных CLI провайдеров                                                                              | `docker compose --profile base up -d`        |
| `cli`                 | `omniroute-cli`  | Агентные рабочие процессы, вызывающие `omniroute providers/setup/doctor`, и встроенные CLI (Codex, Claude Code, Droid, OpenClaw)                                               | `docker compose --profile cli up -d`         |
| `host`                | `omniroute-host` | Хосты Linux, которым нужен доступ к CLI хоста, аналогичный `network_mode`, посредством монтирования `~/.local/bin`, `~/.codex`, `~/.claude` и т. д. в режиме только для чтения | `docker compose --profile host up -d`        |
| `cliproxyapi`         | `cliproxyapi`    | Запуск сопутствующего контейнера [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) на порту `8317` для проксирования к вышестоящим CLI                               | `docker compose --profile cliproxyapi up -d` |
| `web`                 | `omniroute-web`  | Провайдеры веб-сессий, которым требуется браузер: `gemini-web`, `claude-web`, `claude-turnstile` (собирает `runner-web`, Chromium включен)                                     | `docker compose --profile web up -d`         |

> Можно объединять несколько профилей: `docker compose --profile cli --profile cliproxyapi up -d`.

## Настройка CLI-инструментов хоста при запуске OmniRoute в Docker

`omniroute setup-codex`, `setup-claude`, `config set <tool>` и кнопка
**Сохранить конфигурацию** на панели управления записывают файлы вроде `~/.codex/*.config.toml`. Эти пути
имеют смысл только на машине, где фактически работает CLI. Если запустить
эти команды внутри контейнера, запись будет выполнена в собственный домашний каталог контейнера (`/home/node` —
образ работает с `USER node`), откуда ни один CLI на хосте никогда не будет читать файлы и где они
будут удалены при пересоздании контейнера.

OmniRoute обнаруживает это и отказывается выполнять запись, предоставляя инструкции вместо
сообщения об успехе, результатом которого невозможно воспользоваться: CLI завершается с кодом `2`, а API отвечает `422`
с `containerEphemeralTarget: true`.

### Рекомендуемый вариант: запускать CLI на хосте, а OmniRoute — в Docker

Контейнер предоставляет API, а CLI настраивает инструменты на хосте.

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # направить CLI на контейнер
omniroute setup-codex                      # записывает реальные файлы в ~/.codex на вашем хосте
```

Это правильный вариант, когда Codex, Claude Code, Cursor или аналогичные инструменты работают на вашем
ноутбуке, — а это наиболее распространённая конфигурация.

### Альтернатива: bind-монтирование каталогов конфигурации хоста (профиль `host`)

Если вы хотите, чтобы контейнер самостоятельно записывал конфигурацию на хост, смонтируйте
каталоги внутрь контейнера и задайте в `CLI_CONFIG_HOME` корень точки монтирования. В профиле `host`
это уже настроено:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

Именно bind-монтирование делает путь доверенным: OmniRoute читает
`/proc/self/mountinfo` и разрешает запись в смонтированные пути (а также в каталоги,
дочерние элементы которых являются точками монтирования, что точно соответствует приведённой выше структуре `/host-home`), при этом
по-прежнему запрещая запись в несмонтированные пути.

### Аварийный вариант: настройка собственных CLI контейнера (используйте с осторожностью)

Когда CLI действительно находятся внутри контейнера (профиль `cli`), запись
выполняется намеренно. Передайте `--allow-container-write` любой команде `setup-*` или задайте
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` для сервера. Запись будет выполнена
с предупреждением о том, что данные не сохранятся после удаления контейнера.

> **Предупреждение о безопасности — профиль `cli` + монтирование `docker.sock`.**
> Профиль `cli` bind-монтирует `/var/run/docker.sock`, чтобы встроенный в контейнер
> модуль автоматического обновления мог пересоздавать стек через демон хоста
> (`src/lib/system/autoUpdate.ts` проверяет наличие этого сокета и пропускает
> путь Docker, когда сокет отсутствует). Этот сокет представляет собой **границу доверия с правами root на
> хосте**: всё, что может обращаться к нему, управляет демоном Docker на хосте с
> правами root — оно может создавать, просматривать, останавливать и удалять любые контейнеры на хосте.
> Последствия:
>
> 1. **Никогда не открывайте порт профиля `cli` для сети.** Публикуйте
>    его на `127.0.0.1` (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — доступный из локальной сети профиль `cli` превращает любую RCE на уровне панели управления в
>    полную компрометацию хоста.
> 2. **Не подключайте дополнительные каталоги хоста к профилю `cli`.**
>    Сокет Docker в сочетании с любым дополнительным монтированием предоставляет контейнеру полный
>    доступ на чтение и запись к вашей файловой системе и конфигурации хоста. Если инструменту нужен
>    доступ к проекту, запускайте его локально через исполняемый файл CLI — не монтируйте проект
>    в контейнер `cli`.
>
> Если автоматическое обновление внутри контейнера вам не нужно, не включайте профиль `cli`
> (`COMPOSE_PROFILES=core,redis` или более короткий вариант). Остальные профили не
> монтируют сокет Docker.
>
> См. `docs/security/MITM-TPROXY-DECRYPT.md` (в git; не включается в `/docs`) для ознакомления с соответствующей моделью угроз
> для MITM, а также `docs/security/SUPPLY_CHAIN.md` для описания
> цепочки происхождения бинарных файлов `codex`/`claude-code`/`droid`/`openclaw`.

## Сайдкар Redis

OmniRoute использует Redis для работы распределённого ограничителя частоты запросов и общего кеша. Сервис `redis` **всегда определён** в `docker-compose.yml` (он не привязан к профилю) и запускается вместе с любым другим профилем.

| Параметр                       | Значение                                     |
| ------------------------------ | -------------------------------------------- |
| Образ                          | `redis:7-alpine`                             |
| Имя контейнера                 | `omniroute-redis`                            |
| Внутренний порт                | `6379`                                       |
| Порт хоста (переопределяемый)  | `REDIS_PORT` (по умолчанию `6379`)           |
| Адрес хоста (переопределяемый) | `REDIS_BIND_HOST` (по умолчанию `127.0.0.1`) |
| Том                            | `omniroute-redis-data` → `/data`             |
| Проверка работоспособности     | `redis-cli ping` (интервал 10 с)             |

Связанные переменные окружения:

- `REDIS_URL` — строка подключения, передаваемая приложению (по умолчанию `redis://redis:6379`).
- `REDIS_PORT` — сопоставление порта контейнера Redis с портом хоста.
- `REDIS_BIND_HOST` — сетевой интерфейс хоста, на котором публикуется порт. По умолчанию — `127.0.0.1`.

> **Почему по умолчанию используется loopback-интерфейс:** сайдкар запускается без `requirepass`, а контейнеры
> приложения обращаются к нему через сеть compose (`redis:6379`) — опубликованный порт нужен
> только для инструментов на стороне хоста (`redis-cli`, локальный `npm run dev`). Публикация на
> `0.0.0.0` открыла бы доступ к Redis без аутентификации всем узлам вашей локальной сети. Если вы задаёте
> `REDIS_BIND_HOST=0.0.0.0`, также добавьте `--requirepass` в `command:` сервиса.

**Отключать Redis** не рекомендуется (ограничитель частоты запросов будет использовать резервный вариант в памяти с ограниченными возможностями). Если это необходимо, удалите или закомментируйте блок сервиса `redis:` в `docker-compose.yml` либо установите для него нулевой масштаб:

```bash
docker compose up -d --scale redis=0
```

## Compose для рабочей среды

Для изолированного снимка рабочей среды, работающего параллельно со средой разработки, используйте `docker-compose.prod.yml`.

| Параметр                            | Значение                                                                             |
| ----------------------------------- | ------------------------------------------------------------------------------------ |
| Файл                                | `docker-compose.prod.yml`                                                            |
| Порт панели управления по умолчанию | `PROD_DASHBOARD_PORT=20130` (сопоставляется с внутренним `${DASHBOARD_PORT:-20128}`) |
| Порт API по умолчанию               | `PROD_API_PORT=20131`                                                                |
| Образ                               | `omniroute:prod` (собирается из цели `runner-cli`)                                   |
| Контейнер Redis                     | `omniroute-redis-prod` (`redis:8.6.2`, отдельный том `redis-prod-data`)              |
| Том данных                          | `omniroute-prod-data` (именованный, сохраняется между пересборками)                  |
| Проверки работоспособности          | `node healthcheck.mjs` + `redis-cli ping`, а `depends_on` зависит от состояния Redis |

Использование:

```bash
# Собрать и запустить стек рабочей среды
docker compose -f docker-compose.prod.yml up -d --build

# Выводить журналы в реальном времени
docker compose -f docker-compose.prod.yml logs -f

# Остановить стек (сохранить тома)
docker compose -f docker-compose.prod.yml down
```

Стек рабочей среды работает параллельно со стеком compose для разработки (имена контейнеров, порты и тома различаются), поэтому вы можете продолжать локальную разработку, пока рабочая среда остаётся запущенной.

## Этапы Dockerfile

Репозиторий содержит многоэтапный Dockerfile (`Dockerfile`). Доступны четыре этапа; выберите подходящий `target` для вашего сценария использования.

| Этап          | Базовый образ         | Назначение                                                                                                                                                                                                                                                                                                                |
| ------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `builder`     | `node:26-trixie-slim` | Устанавливает зависимости (`npm ci --legacy-peer-deps`) и запускает `npm run build` (по умолчанию используется Turbopack — см. раздел «Ресурсы во время сборки» ниже)                                                                                                                                                     |
| `runner-base` | `node:26-trixie-slim` | Среда выполнения для продакшена с автономным выводом Next.js. **CLI провайдеров не включены.**                                                                                                                                                                                                                            |
| `runner-cli`  | `runner-base`         | Добавляет `git`, `docker.io`, `docker-compose` и глобальные CLI: `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw`. **Выберите этот вариант для агентных рабочих процессов.**                                                                                                                             |
| `runner-web`  | `runner-base`         | Добавляет Playwright и браузер Chromium (`--with-deps`) для провайдеров веб-сеансов: `gemini-web`, `claude-web`, `claude-turnstile`. **Выберите этот вариант при использовании этих провайдеров** — обычный образ завершится ошибкой при выполнении запроса без них (см. примечание о `-web` в разделе «Каналы выпуска»). |

Соберите конкретный целевой этап вручную:

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### Ресурсы во время сборки

Три аргумента сборки определяют потребление ресурсов этапом `builder`. Они действуют только во время сборки —
`OMNIROUTE_MEMORY_MB` (см. ниже) является отдельным параметром среды выполнения.

| Аргумент сборки             | По умолчанию | Эффект                                                                                                       |
| --------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------ |
| `OMNIROUTE_USE_TURBOPACK`   | `0`          | `0` выполняет сборку с webpack: меньше пиковое потребление памяти, но ниже скорость. `1` включает Turbopack. |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144`       | Ограничение кучи V8 (`--max-old-space-size`) для запущенного процесса `next build`.                          |
| `OMNIROUTE_BUILD_WORKERS`   | `2`          | Передаёт значение в `CIRCLE_NODE_TOTAL`; Next вычисляет `workers = N - 1` для сбора данных страниц.          |

`OMNIROUTE_BUILD_WORKERS` следует увеличивать на мощной машине сборки и проверять
в первую очередь, если сборка с ограниченными ресурсами завершается **после**
`✓ Compiled successfully`. Каждый воркер обработки данных страниц является
отдельным процессом, как и сам родительский процесс `next build`;
при воспроизведении на работающем VPS (проблема #7518) было измерено пиковое RSS
каждого процесса на уровне ~4.5 GB независимо от флага кучи `NODE_OPTIONS`
(Turbopack выполняет компиляцию в нативной памяти/Rust за пределами кучи V8).
Значение по умолчанию `2` (→ 1 воркер, всего 2 процесса) рассчитано на
исполнители GitHub с 16 GB / 4 vCPU, которые используются конвейером публикации.
При значении `8` (→ 7 воркеров) у такого исполнителя закончилась память, и
buildkit завершил этап с ошибкой `ResourceExhausted: ... cannot allocate memory`;
даже значение `3` (→ 2 воркера) не укладывалось в доступную память после того,
как RSS каждого процесса было измерено напрямую, а не рассчитано косвенно.
`tests/unit/docker-build-memory-budget.test.ts` выполняет расчёты на основе
измеренного значения и завершается ошибкой, если любой из параметров превышает
возможности исполнителя.

Turbopack выполняет компиляцию в нативной памяти Rust, которая находится
**за пределами** кучи V8, поэтому `OMNIROUTE_BUILD_MEMORY_MB` её не ограничивает.
На узле с ограничением памяти сборка в этом случае принудительно завершается
OOM-киллером через SIGKILL без какого-либо текста ошибки — она просто
останавливается посреди этапа `Creating an optimized production build`, что
выглядит скорее как зависание, чем как нехватка памяти. Поэтому в `Dockerfile`
по умолчанию используется webpack (`OMNIROUTE_USE_TURBOPACK=0`), в отличие от
`npm run dev` / `npm run build`, где Turbopack используется кодом по умолчанию:
обычная команда `docker build .` без аргументов сборки (именно её запускают
Railway и другие платформы с развёртыванием в один клик) не должна молча
завершаться с ошибкой на машине сборки с ограниченной памятью. Для опубликованных
образов значение `OMNIROUTE_USE_TURBOPACK=0` уже передаётся явно в
`docker-publish.yml`. На машине сборки с большим объёмом оперативной памяти
включите Turbopack для ускорения сборки:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

Параметр `webpackBuildWorker` включён, поэтому `next build` запускает родительский
процесс **и** процесс-воркер, каждый из которых отдельно учитывает
`OMNIROUTE_BUILD_MEMORY_MB`. Задавайте лимит контейнера примерно вдвое выше этого
значения, а не равным ему.

Результаты измерений для этого дерева (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| Сборщик   | Лимит контейнера | Результат                                                             |
| --------- | ---------------- | --------------------------------------------------------------------- |
| Turbopack | 8 GiB / 16 GiB   | принудительно завершён OOM-киллером в обоих случаях без вывода ошибки |
| webpack   | 8 GiB            | воркер сборки принудительно завершён через SIGKILL                    |
| webpack   | 12 GiB           | сборка выполнена успешно, пиковое потребление составило 11.1 GiB      |

### Значения по умолчанию во время выполнения

Значения по умолчанию, экспортируемые `runner-base`: `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`.

Поведение памяти в Docker:

- Образ задаёт `OMNIROUTE_MEMORY_MB=1024` и на его основе формирует `NODE_OPTIONS=--max-old-space-size=1024`.
- Фактический серверный процесс запускается автономным лаунчером, который считывает `OMNIROUTE_MEMORY_MB` и добавляет `--max-old-space-size=<OMNIROUTE_MEMORY_MB>`.
- Node использует последнее из повторяющихся значений `--max-old-space-size`, поэтому настройка `OMNIROUTE_MEMORY_MB` определяет фактический лимит кучи в Docker.
- Поскольку образ всегда задаёт это значение, собственный резервный механизм лаунчера с калибровкой по объёму ОЗУ в Docker никогда не применяется. Явно увеличьте его с учётом рабочей нагрузки (см. таблицу ниже). `2048` всё ещё недостаточно для `/v1/responses` агентов программирования.

### Оперативная память для агентов программирования во время выполнения

Значение Docker по умолчанию в 1 ГиБ — это минимум для панели управления и лёгких чатов, а не конфигурация для рабочей среды. Длинные тела запросов `POST /v1/responses` (сотни сообщений, десятки инструментов) во время сжатия удерживают в памяти несколько графов. Два перекрывающихся запроса объёмом около 3 МиБ / 750 тыс. токенов приводили к аварийному завершению V8 при **12 ГиБ** old-space (`FATAL ERROR: Reached heap limit`), а также к OOM в cgroup с лимитом 16 ГиБ. См. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849).

Устанавливайте лимит **cgroup `--memory` выше размера кучи** — нативные буферы, SQLite и промежуточные данные сжатия находятся за пределами V8.

| Рабочая нагрузка                                | `OMNIROUTE_MEMORY_MB`          | Контейнер / cgroup        | Примечания                                                                                                                                            |
| ----------------------------------------------- | ------------------------------ | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Панель управления, один лёгкий чат              | `1024` (значение образа)       | ≥2 ГиБ                    |                                                                                                                                                       |
| Один агент программирования (Claude/Codex/Grok) | `8192`                         | ≥10 ГиБ                   | Типичный одиночный сеанс `/v1/responses`                                                                                                              |
| Два параллельных длинных `/v1/responses`        | `10240`–`12288`                | ≥12–16 ГиБ                | Зафиксировано аварийное завершение V8 при размере кучи около 12 ГиБ                                                                                   |
| Три и более длинных контекста одновременно      | не запускайте в одном процессе | сериализация / больше ОЗУ | По умолчанию допускается 1 выполняющийся ресурсоёмкий запрос; увеличение этого значения без дополнительной ОЗУ снова приведёт к аварийному завершению |

При запуске `omniroute serve` непосредственно на хосте лимит калибруется примерно на уровне 35% ОЗУ (в диапазоне `[512, 4096]`), если `OMNIROUTE_MEMORY_MB` **не задана**. Docker всегда задаёт `1024`, поэтому в официальном образе эта калибровка никогда не выполняется.

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

## Обратный прокси на подпути (Traefik / nginx)

`basePath` Next.js компилируется в автономный пакет. OmniRoute сохраняет встроенное
значение в файле-маркере в корне приложения (записывается во время `npm run build`;
читается `scripts/docker/ensure-docker-base-path.mjs`) и сравнивает его с
`OMNIROUTE_BASE_PATH` при запуске контейнера. Если значения различаются, а образ был
собран для корня домена, точка входа перезаписывает автономные манифесты, встроенные
литералы `basePath`/`assetPrefix` (Next 16 формирует URL ресурсов SSR исключительно из
`assetPrefix`, поэтому патчер дублирует в нём подпуть), встроенные URL ресурсов
`/_next/static` (манифесты клиентских ссылок, импорты медиафайлов, предварительно
отрендеренные страницы ошибок), а также клиентскую прослойку `process.env` до запуска
`node dev/run-standalone.mjs`.

### Сборка с помощью Compose (рекомендуется)

Задайте обе переменные в `.env`, а затем повторно соберите образ, чтобы настройки образа
и среды выполнения совпадали:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml` передаёт `OMNIROUTE_BASE_PATH` как аргумент сборки Docker и как
переменную окружения среды выполнения.

### Предварительно собранный корневой образ + подпуть среды выполнения

Опубликованные образы `diegosouzapw/omniroute:*` собраны для корня домена. Тем не менее
можно задать `OMNIROUTE_BASE_PATH` во время выполнения: при запуске контейнер однократно
исправит пакет. Укажите также соответствующий публичный источник:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

Настройте обратный прокси так, чтобы он передавал **полный** внешний путь (не удаляйте
префикс). Traefik должен направлять `PathPrefix(`/omniroute`)` в контейнер без
`StripPrefix`, чтобы Next.js получал `/omniroute/...` и отдавал ресурсы из
`/omniroute/_next/...`.

Проверка работоспособности Docker обращается к облегчённой конечной точке жизненного
цикла `/healthz` с префиксом активного значения `OMNIROUTE_BASE_PATH`.
`/api/monitoring/health` остаётся доступной для диагностики вручную или через панель
мониторинга. Чтобы снова направить контейнерную проверку HEALTHCHECK на неё (например,
для углублённой проверки работоспособности), задайте
`OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health`. Этот путь выполняет
**углублённую** проверку (БД + сводка мониторинга): он подходит для редких проверок
Docker `HEALTHCHECK`, если вы решите снова его использовать, но **не** для коротких
интервалов `livenessProbe` в Kubernetes.

Для оркестраторов (Kubernetes, Nomad и т. д.):

| Проверка              | Предпочтительно                                                            | Избегайте                                                                  |
| --------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Жизнеспособность      | HTTP `GET /livez` или TCP на основном порту (`PORT`, по умолчанию `20128`) | Использования `/api/monitoring/health` для проверки жизнеспособности       |
| Готовность            | HTTP `GET /healthz`                                                        | Коротких тайм-аутов, при которых занятость цикла событий считается отказом |
| Углублённая / внешняя | `/api/monitoring/health`                                                   | —                                                                          |

`/healthz` сообщает о состоянии жизненного цикла процесса (`ok` / `starting` /
`stopping`). `/livez` проверяет только работоспособность процесса (возвращает 200
всякий раз, когда обработчик может выполниться; ожидания готовности не происходит).
Обе конечные точки работают в том же цикле событий Node, что и обработка запросов,
поэтому ресурсоёмкая работа с каталогом или сжатием может задерживать ответы —
занятость ≠ отказ. Если HTTP-проверки завершаются по тайм-ауту, отдавайте предпочтение
проверке жизнеспособности по TCP. Полные рекомендации по проверкам:
[Руководство по мониторингу — рекомендации по проверкам Kubernetes](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations).

## Docker Compose с Caddy (автоматический TLS для HTTPS)

OmniRoute можно безопасно опубликовать с помощью автоматического выпуска SSL-сертификатов Caddy. Убедитесь, что DNS-запись A вашего домена указывает на IP-адрес вашего сервера.

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # Внешний origin для обратных вызовов OAuth, ссылок панели управления и создаваемых публичных URL.
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # Внутренний URL для взаимодействия между серверами, запланированных задач и запросов к самому сервису.
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

Caddy задаёт стандартные заголовки переадресации для вышестоящего контейнера. OmniRoute использует
`NEXT_PUBLIC_BASE_URL` как канонический публичный origin для обратных вызовов OAuth и создаваемых публичных
ссылок; аутентифицированные операции записи из панели управления используют запросы к тому же origin вместе с привязанной к сеансу защитой CSRF.
Включайте `OMNIROUTE_TRUST_PROXY` только в сложных конфигурациях, где вы намеренно
хотите, чтобы OmniRoute определял публичный origin по доверенным переадресованным заголовкам вместо явной
конфигурации.

## Быстрый туннель Cloudflare

Поддержка панели управления для развёртываний Docker включает запускаемый одним щелчком **быстрый туннель Cloudflare** на странице `Dashboard → Endpoints`. При первом включении `cloudflared` загружается только при необходимости, запускается временный туннель к вашему текущему эндпоинту `/v1`, а созданный URL `https://*.trycloudflare.com/v1` отображается непосредственно под вашим обычным публичным URL.

Панели туннелей эндпоинта (Cloudflare, Tailscale, ngrok) можно отображать или скрывать через `Settings → Appearance`, не изменяя состояние активного туннеля.

### Примечания о туннелях

- URL быстрых туннелей являются временными и изменяются после каждого перезапуска.
- Быстрые туннели не восстанавливаются автоматически после перезапуска OmniRoute или контейнера. При необходимости повторно включите их из панели управления.
- Управляемая установка в настоящее время поддерживает Linux, macOS и Windows на `x64` / `arm64`.
- Управляемые быстрые туннели по умолчанию используют транспорт HTTP/2, чтобы избежать многочисленных предупреждений QUIC о буфере UDP в контейнерных средах с ограниченными ресурсами. Установите `CLOUDFLARED_PROTOCOL=quic` или `auto`, если хотите использовать другой транспорт.
- Образы Docker включают системные корневые сертификаты центров сертификации и передают их управляемому `cloudflared`, что предотвращает ошибки доверия TLS при инициализации туннеля внутри контейнера.
- Установите `CLOUDFLARED_BIN=/absolute/path/to/cloudflared`, если хотите, чтобы OmniRoute использовал существующий исполняемый файл вместо его загрузки.

| `diegosouzapw/omniroute` | `3.8.0`  | ~250MB | Зафиксируйте тег этого типа для GitOps                           |

Мультиплатформенный манифест: нативные `linux/amd64` + `linux/arm64` (Apple Silicon, AWS Graviton, Raspberry Pi). Docker автоматически выбирает подходящую архитектуру; передайте `--platform linux/amd64`, если необходимо принудительно включить эмуляцию AMD64 на хостах ARM.

### Каналы выпусков

OmniRoute публикует отдельные каналы Docker для стабильных выпусков, тестирования активной ветки выпуска и сборок для разработки.

| Канал                           | Источник                                         | Изменяемость                                   | Рекомендуемое использование                                                                                                           |
| ------------------------------- | ------------------------------------------------ | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `:<version>` / `:<version>-web` | Подписанный выпуск с версией                     | Неизменяемый                                   | Рабочие развёртывания с фиксацией точного выпуска                                                                                     |
| `:latest` / `:latest-web`       | Самая новая **опубликованная** стабильная SemVer | Изменяемый указатель на стабильную версию      | Следует за стабильными выпусками **после** задачи публикации SemVer — **не** отслеживает `main` или невыпущенные коммиты `release/v*` |
| `:next` / `:next-web`           | Текущая ветка `release/v*` по умолчанию          | Изменяемый указатель на предварительный выпуск | Тестирование исправлений, добавленных в активную ветку выпуска, но ещё не вошедших в стабильный выпуск                                |
| `:main` / `:main-web`           | Ветка `main`                                     | Изменяемый указатель на версию для разработки  | Только для разработки и интеграционного тестирования                                                                                  |

#### Провайдеры веб-сеансов: образы `-web`

Каждый указанный выше канал также доступен в виде тега `-web` (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`), собранного из этапа `runner-web` — это тот же образ, дополненный Playwright и браузером Chromium. Обычный образ поставляется **без** Chromium; он необходим для `gemini-web`, `claude-web` и `claude-turnstile`.

Ошибка возникает отложенно, а не при запуске: эти провайдеры перечисляют свои модели и отображаются в панели управления как подключённые, но первый же запрос завершается ошибкой

```
[500]: Failed to load external module playwright: Error: Cannot find module
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

Если вы используете эти провайдеры, загрузите тег `-web` того канала, который уже используете, — больше ничего менять не нужно. При установке через npm/CLI (без образа Docker) отсутствует эквивалентный компонент — исполняемый файл браузера: выполните `npx playwright install chromium` на хосте.

#### Использование канала предварительных выпусков

Канал `next` пересобирается при каждой отправке изменений в текущую ветку по умолчанию `release/v*` и публикуется для архитектур AMD64 и ARM64. Старые ветки сопровождения не могут его перезаписать. Канал предоставляет доступный для скачивания образ с исправлениями, которые были влиты в активную ветку выпуска до создания следующего стабильного тега.

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Для Docker Compose переопределите тег образа, используемый выбранным профилем, затем скачайте образ и пересоздайте сервис:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### Безопасность и откат

`next` — это плавающий канал предварительных выпусков. Он может изменяться при каждой отправке изменений в активную ветку выпуска и **не поддерживается для использования в продакшене**. При оценке конкретной сборки закрепите дайджест образа:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

Перед тестированием создайте резервную копию тома данных OmniRoute или каталога данных, подключённого через bind mount. Чтобы выполнить откат, восстановите ранее использовавшуюся стабильную версию или дайджест и пересоздайте контейнер:

```bash
docker pull diegosouzapw/omniroute:<stable-version>
docker compose up -d
```

Сборка из ветки выпуска ни при каких обстоятельствах не может переместить `latest`; стабильный указатель может быть обновлён только подходящей стабильной семантической версией. Образы `next` сохраняют проверку образа выпуска и блокирующий порог для уязвимостей уровня CRITICAL.

**`latest` не гарантирует актуальность относительно git.** Влитые исправления из `main` или активной ветки `release/v*` **не** попадают в `:latest`, пока не будет опубликован образ со стабильной версией SemVer и задание публикации не обновит `:latest` (с тем же дайджестом, что и у этой версии SemVer). Если `latest` выглядит неизменным, хотя исправление уже отображается на GitHub, скачайте `:next`, чтобы протестировать ветку выпуска, или дождитесь тега SemVer.

| Что вам нужно                                                                            | Что использовать                         |
| ---------------------------------------------------------------------------------------- | ---------------------------------------- |
| GitOps / продакшен, где недопустимы непредвиденные изменения                             | Закрепить `:X.Y.Z` (или дайджест образа) |
| Следовать опубликованным стабильным версиям и пересоздавать контейнер при каждом выпуске | `:latest`                                |
| Тестировать невыпущенные коммиты `release/v*`                                            | `:next` (не для продакшена)              |
| Тестировать `main`                                                                       | `:main` (не для продакшена)              |

## Доступность: SQLite по умолчанию работает с одной репликой

Стандартная конфигурация OmniRoute в Docker / Kubernetes — это **один процесс Node + один писатель SQLite**. Высокая доступность в такой топологии **не поддерживается**.

| Ограничение                                              | Последствие                                                                                                                                                                                                                                                                                                                                                    |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Единственный писатель                                    | **Не запускайте** несколько реплик, использующих один и тот же файл SQLite. Это приводит к повреждению БД.                                                                                                                                                                                                                                                     |
| Пересоздание / перезапуск / завершение из-за HEALTHCHECK | **Полная недоступность** активных SSE-соединений, сессий панели управления и состояния в памяти. Соединение каждого подключённого клиента прерывается. Новые запросы в период отсутствия конечных точек получают от обратного прокси **`502 Bad Gateway: Unknown error`**, а не JSON от OmniRoute — клиенты не могут отличить это от сбоя провайдера (#11015). |
| Один цикл событий с `/healthz`                           | Загруженная операция с каталогом или цикл сжатия могут задержать проверки; короткий тайм-аут после этого приводит к перезапуску **единственной** реплики.                                                                                                                                                                                                      |

**Матрица проверок** (см. также [рекомендации по проверкам Kubernetes](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations)):

| Проверка          | Цель                                                                     | Не используйте                                                              |
| ----------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| Работоспособность | TCP на `PORT` (по умолчанию `20128`) или мягкая HTTP-проверка `/healthz` | `/api/monitoring/health`                                                    |
| Готовность        | HTTP `GET /healthz`                                                      | Короткие тайм-ауты, при которых занятый цикл событий считается неработающим |
| Глубокая / ручная | `/api/monitoring/health`                                                 | Автоматическую проверку работоспособности kubelet                           |

**Обновления:** будьте готовы к разрыву каждой сессии. По возможности сначала отключите клиентов; при использовании SQLite по умолчанию обновление без остановки недоступно. Compose с `restart: unless-stopped` в сочетании с Docker `HEALTHCHECK` также заменит единственный процесс, если контейнер перейдёт в состояние Unhealthy, — с теми же последствиями.

Фрагмент конфигурации Kubernetes для **одной реплики** (требуется Recreate; не увеличивайте `replicas` при использовании одного файла SQLite):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

Задержка `preStop` позволяет kube удалить конечные точки Service до отправки SIGTERM, чтобы **новый** трафик перестал поступать в завершающийся процесс. Активные SSE-соединения `/v1/responses` обслуживаются до завершения в течение не более `SHUTDOWN_TIMEOUT_MS` (по умолчанию 30 с) с помощью тяжеловесных разрешающих аренд (#11015). Новые запросы, которые всё же достигают процесса, получают `503` + `Retry-After: 5`. Период отсутствия конечных точек при Recreate до перехода замены в состояние Ready остаётся полной недоступностью — это свойство топологии SQLite, а не ошибка настройки проверок.

Внешний Postgres / высокая доступность с несколькими писателями **не являются** документированным стандартным вариантом. Если вам нужна высокая доступность, сохраняйте одну реплику либо используйте топологию, которую проект протестировал и отдельно задокументировал. Работа над Postgres/MySQL ведётся в [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075). Пока эта возможность не реализована, единственный поддерживаемый способ увеличить пропускную способность **крупных** запросов `/v1/responses` — N независимых процессов (см. следующий раздел), а не `replicas > 1` на одном томе.

## Горизонтальное масштабирование: N независимых процессов

Один процесс Node — это **одна куча V8**. Два перекрывающихся запроса coding-agent `POST /v1/responses` размером ~3 MiB / ~750 тыс. токенов (RTK + Caveman) аварийно завершают работу этой кучи примерно при 12 Gi (`FATAL ERROR: Reached heap limit`) и могут привести к OOM в cgroup размером 16 Gi. См. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849). Этот результат измерения — предупреждение о **бюджете памяти**, а не жёсткое продуктовое ограничение на два одновременных длинных запроса `/v1/responses`. Допуск ресурсоёмких чат-запросов ограничивается автоматически вычисляемым бюджетом байтов входящих данных (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`), рассчитанным исходя из того же предела V8/cgroup. Увеличение этого значения вручную (или настройка устаревшего ограничения количества запросов `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) для процесса с уже рассчитанными ресурсами снова приведёт к аварийному завершению. Небольшие чат-запросы, `/healthz`, `/v1/models` и MCP **не** входят в это ограничение.

### Один процесс: более двух длинных `/v1/responses`

**Исправный** процесс (куча ниже `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO`, по умолчанию `0.75`) **может** обрабатывать более двух одновременных длинных запросов `POST /v1/responses`, если в общепроцессном бюджете байтов выполняющихся запросов (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) ещё есть место. Тела запросов размером не менее `OMNIROUTE_CHAT_LARGE_BODY_BYTES` (по умолчанию 256 KiB) получают ту же ресурсоёмкую квоту, что и структурно сложные запросы, и используют тот же механизм обхода `tryAcquireHealthyHeadroom` из [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`). Десятки одновременных длительных SSE-подключений (операторам часто требуется 40–50) — это вопрос **бюджета памяти**: необходимо подобрать размер кучи, количество основных и резервных слотов и значение `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, — а не жёсткое продуктовое ограничение «максимум 2». При нехватке памяти процесс по-прежнему отклоняет нагрузку с повторяемым ответом `503`, чтобы проблема #7849 не возникла снова.

Чтобы **умножить количество куч** (независимых старых пространств V8) **уже сейчас**:

| Делайте                                                                                                                                                                                                                     | Не делайте                                                                                   |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Запускайте **N контейнеров/подов**, каждый со своим **собственным** `DATA_DIR` / томом                                                                                                                                      | Не задавайте `replicas > 1` для одного файла SQLite                                          |
| Рассчитывайте количество ресурсоёмких выполняющихся запросов и резервных слотов исходя из бюджета кучи / байтов выполняющихся запросов; 1–2 — консервативное значение по умолчанию из #7849, а не жёсткий максимум продукта | Не выделяйте одному процессу в 8 раз больше RAM с неограниченным лимитом количества запросов |
| При необходимости используйте `QUOTA_STORE_DRIVER=redis` + `QUOTA_STORE_REDIS_URL` для **общих счётчиков квот**                                                                                                             | Не считайте Redis общей SQLite — это не так                                                  |
| Дублируйте секреты провайдеров в каждом экземпляре (либо согласитесь с раздельными панелями мониторинга)                                                                                                                    | Не ожидайте единую панель мониторинга / единый журнал вызовов для всех экземпляров           |
| Разместите любой балансировщик нагрузки перед экземплярами; достаточно привязки по API-ключу или сессии                                                                                                                     | Не требуйте специфичного для поставщика промежуточного ПО, учитывающего размер запросов      |

Оборудование: количество одновременных длинных запросов `/v1/responses` на один экземпляр — это вопрос **бюджета памяти** (куча + бюджет байтов выполняющихся запросов / #10110). `N` независимых `DATA_DIR` по-прежнему умножают количество куч: RAM хоста должна покрывать `N × cgroup`, а не «один под на 16 Gi с N=8». Никогда не используйте `replicas > 1` для одного файла SQLite.

Пример Compose (две кучи, два тома — не `deploy.replicas: 2`):

```yaml
services:
  omniroute-a:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

Повышение плотности внутри процесса (вынесение сжатия за пределы HTTP-изолята) отслеживается в [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023). Единый логический кластер с общим долговременным состоянием отслеживается в [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075).

## Региональные ошибки Gemini внутри Docker

Google AI Studio / Gemini API может возвращать HTTP 400 с FAILED_PRECONDITION и сообщением
`Местоположение пользователя не поддерживается для использования API.` Успешный запрос на хосте
не доказывает, что контейнер использует тот же исходящий маршрут. Порядок DNS-записей,
доступность IPv4/IPv6, маршрутизация VPN и настроенные прокси могут различаться. Проверьте
[поддерживаемые Google регионы](https://ai.google.dev/gemini-api/docs/available-regions),
а также фактический маршрут соединения; сама по себе эта ошибка не указывает на недействительный API-ключ.

### Предпочтительно использовать прокси для конкретного соединения

Используйте [настройку прокси для отдельного соединения](../ops/PROXY_GUIDE.md#4-level-proxy-system)
OmniRoute для проблемного соединения Gemini, затем повторите **Проверку соединения** и небольшой запрос
с той же моделью. Так изменение маршрутизации будет ограничено только этим соединением. Убедитесь,
что прокси доступен из контейнера и что соединение действительно использует
его. Изменение маршрута не гарантирует соответствия региональным требованиям вышестоящего сервиса.

### Сравнение сети хоста и контейнера

При сравнении результатов запросов с аутентификацией не меняйте ключ, модель и запрос; никогда
не публикуйте в задаче учётные данные, пароли прокси или полные заголовки авторизации.
Сначала проверьте, какие семейства адресов предоставляет системный резолвер, используя одну и ту же команду
на хосте и внутри контейнера:

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

Замените `omniroute` на используемый вами сервис (например, `omniroute-web`). Эти
команды выводят семейства адресов без учётных данных или IP-адресов. Возвращённое значение `6`
показывает только наличие результата DNS для IPv6: оно **не** доказывает наличие рабочего маршрута IPv6 или доступа к API.
Если установлен `curl`, сравните `curl -4 -I https://generativelanguage.googleapis.com`
с `curl -6 -I https://generativelanguage.googleapis.com` в обеих средах.
HTTP-ответ подтверждает доступность соединения для этой проверки, даже если это ошибка запроса
без аутентификации; соответствие требованиям Gemini проверяет только запрос к модели с аутентификацией.

### Альтернатива на уровне хоста: рабочий IPv6 и политика резолвера

Автор сообщения [#12762](https://github.com/diegosouzapw/OmniRoute/issues/12762) восстановил
доступ в своей среде, включив IPv6 для контейнеров и изменив порядок выбора адресов glibc.
Рассматривайте это как решение для конкретной среды. Перед изменением настроек резолвера убедитесь
в работоспособности IPv6 на хосте, исходящей маршрутизации контейнера и правил межсетевого экрана.
Само по себе наличие частного ULA-адреса не подтверждает доступность общедоступного IPv6.

Для сервисов, уже подключённых к сети Compose по умолчанию, следующий фрагмент включает
IPv6 в этой сети; сохраните остальные настройки сервиса, портов, томов и конфигурации:

```yaml
networks:
  default:
    enable_ipv6: true
```

Для именованной сети включите его в той сети, к которой фактически подключён сервис. Docker может
выделить ULA-подсеть; явно задавайте непересекающуюся подсеть, только если это требуется вашей
сетью. См. [работу с IPv6 в Docker](https://docs.docker.com/engine/daemon/ipv6/)
и [параметры сетей Compose](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6).

В **образе на основе glibc** файл `/etc/gai.conf` позволяет изменить порядок выбора адресов. Текущий
Dockerfile репозитория использует Debian; для пользовательских образов на основе musl этот механизм неприменим.
Описанное изменение заменяет метку ULA с `label fc00::/7 6` на
`label fc00::/7 1`. Возьмите за основу полную таблицу политик из образа и сохраните остальные
её записи: добавление записи `label` или `precedence` заменяет соответствующую таблицу по умолчанию, поэтому файла,
содержащего только изменённую строку, недостаточно.
[Справочник по конфигурации glibc](https://github.com/bminor/glibc/blob/master/posix/gai.conf)
описывает эту семантику. Подключите проверенный файл как доступный только для чтения по пути `/etc/gai.conf`
и пересоздайте сервис, чтобы применить его.

Это изменяет выбор адресов ОС для **всего исходящего трафика в этом контейнере**.
Это не заставляет каждое приложение выбирать IPv6: порядок DNS в Node и логика
выбора соединения также имеют значение. В частности, `--dns-result-order=ipv4first` отдаёт предпочтение IPv4 и
не устраняет сбой, связанный с использованием только IPv4. См. [порядок DNS в Node](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder).

После любых изменений на уровне хоста повторно проверьте Gemini и других поставщиков. Для отката
удалите подключение пользовательского файла `gai.conf`, восстановите прежнюю конфигурацию сети и
пересоздайте затронутый сервис или сеть во время окна технического обслуживания. Пересоздание сети
может прервать работу других подключённых к ней контейнеров; не удаляйте том с постоянными данными.

## Важные примечания

- **Режим WAL в SQLite:** необходимо дождаться завершения `docker stop`, чтобы OmniRoute успел выполнить checkpoint последних изменений обратно в `storage.sqlite`. Входящие в комплект файлы Compose уже задают 40-секундный льготный период остановки. Если вы запускаете образ напрямую, сохраняйте параметр `--stop-timeout 40`.
- **`DISABLE_SQLITE_AUTO_BACKUP`:** установите значение `true`, если регулярные резервные копии и резервные копии перед записью создаются внешними средствами. Для миграций существующей базы данных по-прежнему требуется отдельный надёжный снимок для обеспечения безопасности и механизм защиты при массовой миграции.
- **Сохранение данных:** всегда подключайте том к `/app/data`, чтобы сохранять базу данных, ключи и конфигурации между перезапусками контейнера.
- **Настройка порта:** переопределите переменную окружения `PORT`, чтобы изменить порт по умолчанию `20128`.
