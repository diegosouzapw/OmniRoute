## Проблема, которую это решает

**Полный набор проверок** (`.github/workflows/ci.yml` — сегменты модульных тестов, vitest, ratchets,
`package-artifact`, SonarQube, E2E) запускается **только для релизного PR** (PR → `main`). PR, нацеленные
на `release/**`, проходят **быстрые проверки** (`quality.yml`: тесты, затронутые согласно TIA, + проверка типов + линтинг),
а при изменениях кода — также **рекомендательную** production-сборку. Как следствие, ошибки, проявляющиеся только при релизе, могут
незаметно накапливаться в релизной ветке и **обрушиваться слоями примерно по 40 минут** во время релиза,
по одной за раз.

Семейство «release-green» предназначено для **заблаговременного выявления** таких ошибок — эквивалент полного
набора проверок можно запускать **локально / вне процесса релиза** в любое время, чтобы релизный PR
успешно прошёл уже первый запуск CI.

> **Принцип, не подлежащий обсуждению:** ничто из этого не блокирует контрибьютора. Мы не добавляем обязательную
> проверку, из-за которой его PR может завершиться ошибкой. **Расхождения** (ratchets) должен актуализировать мейнтейнер при релизе —
> они никогда не должны быть заботой контрибьютора. Ни один компонент не **закрывает** PR (присваивая авторство)
> и не **ослабляет** тест ради успешного прохождения.

## Семейство (4 компонента) — и как каждый из них запускается независимо

| Компонент                                                                 | Что это                                                                                    | Когда запускать                                                         | Область действия              |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- | ----------------------------- |
| **`/green-prs`** (Решение A)                                              | Запускаемое по запросу мейнтейнером сканирование **очереди открытых PR**                   | **Независимо, периодически** — и особенно **перед** `/generate-release` | Вся очередь PR → `release/**` |
| **`/validate-release-green`** (Решение C — `npm run check:release-green`) | Механизм валидации: воспроизводит полный набор проверок для ветки ИЛИ кандидата на слияние | Независимо, в любое время                                               | Конкретная ветка или merge-PR |
| **`/babysit <PR#>`**                                                      | Доводит **текущий CI** **одного** PR до успешного состояния                                | Независимо, для каждого PR                                              | Один PR                       |
| **`nightly-release-green.yml`** (Решение D)                               | Автоматизированный ночной workflow; создаёт issue при HARD-ошибке                          | Автоматически (cron)                                                    | Активная релизная ветка       |

**Краткий ответ на вопрос «это только для релизов?»:** **нет.** `/green-prs` изначально предназначен для
**периодического запуска между релизами**. Независимый запуск — это штатный режим работы; релиз — лишь
момент, когда такой запуск приносит максимальную пользу.

## Рекомендительная сборка от PR до релиза

`quality.yml` теперь включает `Build (advisory)` для PR с кодом, не являющихся черновиками, и веток очереди Mergify.
Она повторяет рецепт производственной сборки из `ci.yml`: Node 24, `npm-ci-retry`,
`check:node-runtime` и `npm run build` с `OMNIROUTE_USE_TURBOPACK=1`. Артефакт сборки намеренно
не загружается, поскольку в этом рабочем процессе его не использует ни одна последующая задача проверки качества.
Удалите `continue-on-error` после одной недели стабильных запусков PR релиза, чтобы этот сигнал стал
блокирующим барьером на пути от PR к релизу.

## Решение C — `npm run check:release-green` (движок)

Воспроизводит проверку, эквивалентную релизной, для текущего рабочего дерева и классифицирует каждую неуспешную проверку:

- **HARD** (проверка типов, ошибки линтинга, модульные тесты, vitest, db-rules, public-creds, необязательная
  `package-artifact`) → **реальный дефект**; `exit 1`. Исправляется в исходной ветке (TDD, правило №18).
- **DRIFT** (**предупреждения** eslint, когнитивная сложность, размер файла) → отклонение от контрольных значений,
  накопившееся за цикл, **возникшее не по вине участника**; оно лишь выводится в отчёте, а **сопровождающий обновляет
  контрольные значения при релизе**. DRIFT **никогда** не меняет код завершения — поэтому никого не блокирует.

```bash
npm run check:release-green                 # текущая ветка (рабочее дерево)
node scripts/quality/validate-release-green.mjs --json   # структурированный вывод
node scripts/quality/validate-release-green.mjs --quick  # пропускает unit+vitest (только drift+typecheck+lint)
node scripts/quality/validate-release-green.mjs --with-build  # включает package-artifact (медленно)
```

Только диагностирует и **формирует отчёт** (без автоматических исправлений). Оркестрация исправлений до успешного состояния находится в
`/green-prs` и `/review-prs`.

## Решение A — `/green-prs` (сканирование очереди)

Процедура (краткое описание — подробности см. в навыке `green-prs`):

1. **Инвентаризировать** очередь открытых PR относительно активной релизной ветки.
2. **Классифицировать** каждый PR (пригоден / следует отклонить / требуется участие автора) — PR, которые следует отклонить или для которых требуется участие автора,
   **указываются в отчёте, но не закрываются** (решение принимает автор).
3. Для каждого пригодного PR в **изолированном рабочем дереве** (правило №19) привести PR к вершине релизной ветки и выполнить
   `npm run check:release-green`:
   - **HARD** → исправить **в ветке участника** с указанием соавторства (это сохраняет для автора статус «Merged»),
     повторяя запуск до устранения всех HARD.
   - **DRIFT** → оставить без изменений; контрольные значения будут обновлены при релизе.
4. **Сформировать отчёт** в виде таблицы PR × (вердикт, ошибки HARD, исправлено?, DRIFT, готово к релизу сейчас?).

Может **подготовить** очередь без слияния; выполняет слияние только по явному запросу — и никогда не закрывает PR.

## Рекомендуемая периодичность

- Запускайте **`/green-prs` периодически** (например, еженедельно) и **обязательно перед
  `/generate-release`**.
- Сохраняйте **`nightly-release-green.yml`** (решение D) как источник непрерывного сигнала: когда он создаёт
  задачу о сбое HARD, пора выполнить сканирование.
- Используйте **`/validate-release-green`** по необходимости для проверки ветки или конкретного кандидата на слияние.
- Используйте **`/babysit <PR#>`**, когда конкретный PR необходимо довести до успешного состояния в действующей CI.

## Связь с релизом

- `/generate-release` вызывает проверку на **этапе 0 (предварительная проверка)**: обновляет контрольные значения DRIFT и исправляет
  HARD перед созданием PR релиза.
- `/review-prs` использует барьер готовности к релизу на этапе принятия решения о слиянии (успешные проверки перед слиянием).

Цель всех компонентов одинакова: **успешный PR релиза при первом запуске CI**, вместо последовательного разбора
сбоев 40-минутными слоями в день релиза.
