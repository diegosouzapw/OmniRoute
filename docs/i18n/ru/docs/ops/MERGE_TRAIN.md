Начиная с v3.8.49 (WS3.2/WS3.4 плана качества/скорости), стандартным путём слияния
проверенных PR в `release/vX.Y.Z` является **очередь слияния Mergify** (`.mergify.yml`);
описанный ниже **ручной merge-train** является РЕЗЕРВНЫМ вариантом — он используется во время инцидентов,
заморозок релиза или если условия плана Mergify Open Source когда-либо изменятся.

## Стандартный путь: очередь Mergify

1. PR проверен/доведён до зелёного состояния кампаниями и одобрен владельцем через предшествующий слиянию шлюз ⭐
   (отчёт + решение по каждому пункту — см. `/merge-prs`, шаг 0.75).
2. Владелец (или сессия, действующая на основании решения владельца) применяет метку **`queue`**.
   Эта метка И ЕСТЬ одобрение слияния; Mergify лишь исполняет его.
3. Mergify группирует до 10 PR из очереди, проверяет пакет по быстрым шлюзам
   и выполняет слияние (squash). Красный пакет **автоматически делится пополам** — проблемный PR
   изолируется примерно за log2(N) повторных проверок и удаляется из очереди; остальные продолжают обработку.
4. После слияния непрерывный процесс проверки готовности релиза проверяет новую вершину при push
   и создаёт задачу с указанием источника, если комбинация вызвала регрессию (автоматический откат не выполняется).

Ограничения (соответствуют строгим правилам #21/#22 из `CLAUDE.md`):

- **Открыта заморозка релиза** → НЕ добавляйте метки к PR, нацеленным на замороженную ветку; сначала перенаправьте их
  на активную `release/vX+1`.
- **PR другой сессии в процессе работы** → никогда не добавляйте к нему метку; только владеющая сессия ставит
  свою работу в очередь.
- Изменения только в тестах и PR с меткой `hotfix` уже выполняют сокращённый CI (см.
  `RELEASE_CHECKLIST.md` → ускоренный путь исправлений); условия очереди принимают любой
  фактически выполненный набор проверок (`#check-failure=0` + `#check-pending=0`).

## Резервный вариант: ручной merge-train

Используется, когда очередь недоступна. Здесь формализована практика, с помощью которой за один день
цикла v3.8.47 были обработаны 33 PR:

1. **Соберите пакет** (примерно 10–30 проверенных и одобренных PR). Проверьте коллизии `linked:`
   (одинаковые `tap.testFiles`, одинаковые фрагменты CHANGELOG) и обрабатывайте такие PR последовательно.
2. **Выполните проверку ОДИН РАЗ**: в изолированном worktree от вершины релизной ветки локально слейте все
   головные ветки пакета, затем запустите набор проверок, эквивалентный релизному
   (`npm run check:release-green`; перед релизом добавьте `--with-build`).
   `scripts/release/merge-train.sh <base> <PR#>…` автоматизирует шаги 1–2 (конфликтующие
   PR исключаются, обработка продолжается). В полном режиме выполняется `npm run test:unit` —
   настроенный под машину исполнитель (`--test-concurrency=20`), **а не** два последовательных 4-ядерных шарда CI,
   из-за которых основной этап использовал лишь около 25% ресурсов 16-ядерной машины (исправлено
   2026-07-18). `--fast` (для обработки крупных merge-train в течение дня, одобрено владельцем 2026-07-18)
   сохраняет все статические шлюзы + vitest, но запускает только изменённые включёнными PR файлы node:test;
   при этом ПОЛНЫЙ набор всё равно должен запускаться не реже одного раза в день на
   накопленной вершине (один запуск без `--fast`).
3. **Зелёный результат** → последовательно слейте PR (перед каждым повторно проверяя `state,headRefOid` —
   PR с изменившейся головной веткой возвращается на проверку). Убедитесь, что итоговые изменения каждого слияния
   содержат только собственные изменения PR (никаких откатов при автоматическом разрешении конфликтов: проверяйте
   `git diff --stat` на удаления за пределами области изменений).
4. **Красный результат** → делите пакет пополам (проверяя каждую половину), а не перепроверяйте PR
   по одному; верните проблемный PR в очередь проверки вместе с подтверждающими данными.
5. **Никогда не делайте следующее**: не выполняйте слияние в замороженную ветку во время заморозки; не используйте `git stash`;
   не перезапускайте весь CI в надежде, что красный результат исчезнет (правило: красный результат — это информация).

## Уровни проверок (почему очередь безопасна при использовании только быстрых шлюзов)

- **Для каждого PR** (быстрые шлюзы quality.yml): затронутые по TIA тесты + полный набор модульных тестов в 4 шардах +
  vitest + набор проверок lint + проверка типов + проверка целостности документации/журнала изменений.
- **Для каждого пакета/вершины** (непрерывная проверка готовности релиза): ОБЯЗАТЕЛЬНЫЕ шлюзы `--quick` при каждом push в
  релизную ветку; полные прогоны `--with-build --full-ci` 3 раза в день.
- **Для каждого релиза** (ci.yml в релизном PR): полная матрица, включая E2E ×9,
  артефакт пакета + дымовой тест запуска tarball, покрытие/пороговые ограничения.

Ничто не проверяется в меньшем объёме, чем раньше — тяжёлые проверки просто выполняются для каждого пакета/вершины,
а не для каждого PR, что и устраняет O(N) циклов ожидания.
