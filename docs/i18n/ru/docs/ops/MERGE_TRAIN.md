Начиная с v3.8.49 (WS3.2/WS3.4 плана качества/скорости), стандартным способом слияния
проверенных PR в `release/vX.Y.Z` является **очередь слияния Mergify** (`.mergify.yml`);
описанный ниже **ручной merge train** — это РЕЗЕРВНЫЙ ВАРИАНТ, используемый во время инцидентов,
заморозки релиза или если условия плана Mergify Open Source когда-либо изменятся.

## Путь по умолчанию: очередь Mergify

1. PR проходит проверку/получает зелёный статус в рамках кампаний и одобряется на этапе предслияния ⭐
   владельцем (отчёт + решение по каждому элементу — см. `/merge-prs`, шаг 0.75).
2. Владелец (или сессия, действующая на основании решения владельца) добавляет метку **`queue`**.
   Эта метка ЯВЛЯЕТСЯ одобрением слияния; Mergify лишь выполняет его.
3. Mergify проверяет поставленные в очередь PR **последовательно** (по одному) с помощью быстрых проверок
   и выполняет слияние (squash). Пакетная обработка + автоматическая бисекция доступны на платном тарифе Mergify
   («Cannot use Merge Queue batch» на бесплатном тарифе, #7220), поэтому в `.mergify.yml` не задан
   `batch_size`; пакетная обработка остаётся задачей описанного ниже ручного конвейера слияния. PR, проверки которого
   всё ещё не завершены по истечении `checks_timeout` (240 мин = 2× измеренного p95 для
   `quality.yml`), удаляется из очереди, чтобы не блокировать её.
4. После слияния непрерывный рабочий процесс проверки готовности релиза проверяет новую вершину при push
   и создаёт задачу с указанием источника изменений, если их сочетание вызвало регрессию (автоматический откат не выполняется).

Ограничения (соответствуют жёстким правилам #21/#22 из `CLAUDE.md`):

- **Активна заморозка релиза** → НЕ добавляйте метки к PR, нацеленным на замороженную ветку; сначала перенаправьте их
  в активную ветку `release/vX+1`.
- **PR другой сессии находится в работе** → никогда не добавляйте к нему метку; только владеющая сессия ставит
  собственную работу в очередь.
- PR, содержащие только изменения тестов, и PR с меткой `hotfix` уже выполняют сокращённый набор CI-проверок (см.
  `RELEASE_CHECKLIST.md` → ускоренный процесс для срочных исправлений); условия очереди принимают любой
  фактически выполненный набор проверок (`#check-failure=0` + `#check-pending=0`).

## Резервный вариант: ручной merge train

Используется, когда очередь недоступна. Здесь формализована практика, с помощью которой за один день
в рамках цикла v3.8.47 были обработаны 33 PR:

1. **Сформируйте пакет** (~10–30 проверенных и одобренных PR). Проверьте конфликты `linked:`
   (одинаковые `tap.testFiles`, одинаковые фрагменты CHANGELOG) и обрабатывайте такие PR последовательно.
2. **Выполните проверку ОДИН РАЗ**: в изолированном worktree от вершины релизной ветки локально слейте
   все головные ветки пакета, затем запустите набор проверок, эквивалентный релизному
   (`npm run check:release-green`; перед релизом добавьте `--with-build`).
   `scripts/release/merge-train.sh <base> <PR#>…` автоматизирует шаги 1–2 (конфликтующие
   PR исключаются, train продолжает работу). В полном режиме запускается `npm run test:unit` —
   runner, настроенный под машину (`--test-concurrency=20`), **а не** два последовательных 4-ядерных
   шарда CI, из-за которых доминирующая фаза использовала лишь ~25% ресурсов 16-ядерной машины
   (исправлено 2026-07-18). `--fast` (для обработки крупных внутридневных mega-train, одобрено владельцем 2026-07-18)
   сохраняет все статические гейты + vitest, но запускает только файлы node:test, изменённые
   включёнными PR; ПОЛНЫЙ набор всё равно должен запускаться хотя бы раз в день на
   накопленной вершине (один train без `--fast`).
3. **Зелёный результат** → последовательно слейте PR (перед каждым слиянием повторно проверяя
   `state,headRefOid` — PR, головная ветка которого изменилась, возвращается на проверку).
   Убедитесь, что итоговая разница каждого слияния содержит только собственные изменения
   соответствующего PR (никаких откатов через автоматическое разрешение конфликтов: проверяйте
   `git diff --stat` на наличие удалений вне области изменений).
4. **Красный результат** → делите пакет пополам (проверяя каждую половину), а не выполняйте
   повторную проверку PR по одному; верните проблемный PR в очередь проверки вместе с подтверждающими данными.
5. **Никогда**: не выполняйте слияние в замороженную ветку во время заморозки; не используйте
   `git stash` где-либо; не перезапускайте весь CI в надежде, что красный результат исчезнет
   (правило: красный результат — это информация).

## Уровни проверок (почему очередь безопасна только с быстрыми гейтами)

- **На каждый PR** (быстрые гейты quality.yml): тесты, затронутые согласно TIA, + полный набор unit-тестов
  в 4 шардах + vitest + набор lint-проверок + проверка типов + проверка целостности документации/журнала изменений.
- **На каждый пакет/вершину** (непрерывный release-green): ЖЁСТКИЕ гейты `--quick` при каждом push в
  релизную ветку; полные прогоны `--with-build --full-ci` 3 раза в день.
- **На каждый релиз** (ci.yml для релизного PR): полная матрица, включая E2E ×9,
  артефакт пакета + проверку запуска из tarball, покрытие/ratchet-проверки.

Объём проверок не стал меньше — тяжёлые проверки просто выполняются на каждый пакет/вершину,
а не на каждый PR, что и устраняет O(N) циклов ожидания.

## Предварительные требования для `merge-train.sh` в свежем checkout

Скрипт выполняет быстропрерываемую **предварительную проверку** корневого checkout (до любых операций
с worktree), чтобы неисправная установка никогда не могла быть ошибочно принята за красный train:

1. Выполните `npm ci`, затем запустите postinstall для `bun`, который блокирует npm:
   `(cd node_modules/bun && node install.js)` — иначе `check:provider-consistency`
   и `check:known-symbols` (оба используют `bun scripts/…`) завершаются с ошибкой и для train, И для базы,
   не выводя строку с нарушением.
2. Не должно быть постороннего `node_modules/node_modules` (дублирующего дерева зависимостей; React загружается
   дважды, и UI-наборы vitest мгновенно завершаются с ошибкой).
3. `node_modules/.bin/tsc` должен присутствовать и быть исполняемым (при частичной установке он отсутствует).

Train запускает блокирующую проверку `npm run check:cycles:ratchet`; обычная `npm run check:cycles`
носит информационный характер (она выводит список SCC и завершается с ненулевым кодом даже для исправной базы).
