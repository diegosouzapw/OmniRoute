Используйте это руководство, чтобы выбрать самый короткий надёжный цикл разработки для пул-реквеста. Оно не
заменяет приведённые ниже документы по архитектуре и безопасности для отдельных областей, а связывает каждый распространённый
тип изменения с его контрактами, целевыми проверками и покрытием CI.

## Путь, который проходит каждое изменение

1. **Выберите базовую ветку до начала редактирования.** Найдите самую новую активную ветку `release/v*` и создайте ветку от
   её вершины. Указывайте её как целевую, а не `main`. Если действует заморозка релиза, не выбирайте замороженную
   ветку в качестве целевой; используйте следующий активный цикл, описанный в
   [модели ветвления и релизов](BRANCHING_MODEL.md).
2. **Перечислите контракты.** Определите все каталоги, схемы, сгенерированные артефакты, публичные API и пользовательские
   интерфейсы, на которые влияет изменение. В таблице ниже приведён минимальный начальный набор.
3. **Напишите или обновите целевые тесты.** Изменения рабочего кода в `src/`, `open-sse/`, `electron/` или
   `bin/` требуют автоматизированного теста в том же PR. Запустите минимальный набор файлов тестов, подтверждающих
   поведение, а затем перечисленные целевые проверки.
4. **Позвольте CI запустить широкую матрицу.** Полный набор сегментов модульных тестов, Vitest, контроль покрытия и
   производственная сборка запускаются для PR. Запускайте широкий набор тестов локально только тогда, когда целевой сбой указывает на
   более широкое влияние или когда изменение затрагивает несколько подсистем.
5. **Синхронизируйтесь перед ревью.** Получите активную базовую ветку, изучите её новые коммиты и отличия вашей ветки
   от неё, затем выполните rebase или merge базовой ветки в соответствии с процессом для участников. Устраняйте конфликты сгенерированных файлов
   и каталогов в их исходных файлах, повторно генерируйте их, снова запускайте целевой цикл и убедитесь, что
   PR по-прежнему нацелен на активную релизную ветку.
6. **Зафиксируйте подтверждения.** В шаблоне PR перечислите выполненные команды, все добавленные или изменённые файлы тестов,
   миграции или флаги функций, а также все проверки, выполняемые только в CI, которые ещё ожидаются.

## Эталонные процессы по типам изменений

Приведённые ниже команды являются минимальными целевыми проверками, а не разрешением пропустить тест, который непосредственно проверяет
изменённое вами поведение.

### Провайдер

**Контракты**

- Определение провайдера в `src/shared/constants/providers/` и его композиция в
  `src/shared/constants/providers.ts`.
- Модели и возможности в `open-sse/config/providerRegistry.ts` или вынесенных из него файлах реестра.
- Выбор исполнителя/транслятора, конфигурация OAuth или API-ключа, ресурсы панели управления и сгенерированная
  справка по провайдеру, где это применимо.
- Публичные учётные данные должны использовать `resolvePublicCred()`; ответы с ошибками должны использовать общие вспомогательные функции
  очистки ошибок. См. `docs/security/PUBLIC_CREDS.md` (git; не включается в `/docs`) и
  [очистку ошибок](../security/ERROR_SANITIZATION.md).

**Целевой цикл**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # при изменении каталога; закоммитьте сгенерированные изменения
npm run lint
```

Также протестируйте каждое затронутое семейство запросов: chat, Responses, images, embeddings, audio или video.
Рассматривайте изменения сгенерированного каталога и эталонных файлов как изменения контрактов; не принимайте их без проверки.

### Маршрутизация

**Контракты**

- Публичные значения стратегий и метаданные UI в `src/shared/constants/routingStrategies.ts`.
- Диспетчеризация и упорядочивание в `open-sse/services/combo.ts` и `open-sse/services/combo/`.
- Схемы combo, хранение данных, состояние отказоустойчивости, возможности моделей и элементы управления API/UI.
- [Движок Auto-Combo](../routing/AUTO-COMBO.md) и документация по отказоустойчивости при изменении поведения.

**Целевой цикл**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # изменения стратегии или диспетчеризации
npm run check:known-symbols      # изменения регистрации стратегии
npm run lint
```

Локально используйте детерминированные тесты с имитацией вышестоящих сервисов. Проверочные тесты combo с реальными сервисами требуют учётных данных и выполняются
вручную, а не вместо CI.

### UI / UX

**Контракты**

- Границы маршрутов/страниц Next.js и общих компонентов в `src/app/` и
  `src/shared/components/`.
- Форматы ответов API, состояния загрузки/отсутствия данных/ошибок, поведение клавиатуры и программ экранного доступа,
  адаптивная компоновка, темы оформления и расширение локалей.
- Исходные английские строки UI в `src/i18n/messages/en.json`; не добавляйте новые пользовательские тексты непосредственно в код.

**Целевой цикл**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Для изменений взаимодействия или внешнего вида запустите приложение и проверьте как узкие, так и широкие области просмотра. CI запускает
производственную сборку и более широкие наборы тестов; визуальное поведение всё равно требует целевого компонентного теста, Playwright
или документированной ручной проверки, соответствующей изменению.

### i18n

**Контракты**

- `src/i18n/messages/en.json` является источником строк UI; `config/i18n.json` является источником локалей.
- Каталоги CLI хранятся отдельно в `bin/cli/locales/`.
- Сохраняйте заполнители и теги ICU без изменений. Не переводите названия продуктов/провайдеров/моделей,
  названия протоколов и заголовков, команды, идентификаторы кода/JSON, URL, переменные окружения и
  защищённые термины, такие как `OmniRoute`, `OAuth`, `MCP` и `A2A`. Текущий исходный список находится в
  `scripts/i18n/glossary/protected-terms.json`.

**Целевой цикл**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # при изменении строк/каталогов CLI
npm run lint
```

Это руководство для существующей системы, а не предложение расширять её инструментарий или модель ключей.
Пока проектируется новая система, вносите в i18n только точечные изменения. Не запускайте команды перевода,
обращающиеся к внешним сервисам, если только задача явно не требует сгенерированных переводов и
вы не проверили получившиеся изменения.

### CLI

**Контракты**

- Публичные команды и флаги в `bin/cli/`, сгенерированные команды API, коды завершения, stdout/stderr и
  структура вывода JSON, поведение конфигурации/окружения и файлы, включённые в пакет.
- Строки CLI, отображаемые пользователю, должны использовать слой i18n CLI, а каталоги `en`/`pt-BR` должны оставаться согласованными.
- Сохраняйте Node в качестве поддерживаемой среды выполнения и соблюдайте опубликованный контракт бинарного файла.

**Целевой цикл**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # изменения в сгенерированном/собранном CLI
npm run check:pack-policy     # изменения публичной поверхности пакета
npm run lint
```

Используйте точную команду во временном каталоге данных, когда поведение зависит от синтаксического анализа, файлов или
статуса завершения. CI выполняет более широкие проверки артефактов пакета и экосистемы.

### База данных

**Контракты**

- Доменные модули находятся в `src/lib/db/`; импортируйте конкретные модули напрямую (старый слой реэкспорта `localDb.ts` был удалён).
- Нумерованные идемпотентные SQL-миграции в `src/lib/db/migrations/`, безопасность транзакций, поведение
  при обновлении, индексы и все вызывающие компоненты, затронутые схемой.
- Маршруты и обработчики никогда не выполняют необработанные SQL-запросы напрямую.

**Целевой цикл**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

При добавлении миграции тестируйте как новую базу данных, так и обновление с предыдущей схемы. Тесты базы данных
должны закрывать дескрипторы и вызывать `resetDbInstance()` во время очистки. Запускайте `npm run test:bun:db` только тогда,
когда изменяется необязательный путь адаптера Bun; Node остаётся эталонной средой.

### Сборка / развёртывание

**Контракты**

- Корневой манифест и манифесты рабочих пространств/файл блокировки, `scripts/build/`, автономная сборка Next.js, содержимое пакета
  `dist/`, метаданные платформ Electron, рабочие процессы CI и контрольные маркеры развёртывания.
- Поддерживаемые диапазоны версий Node и разрешённое использование Bun, указанное в `CLAUDE.md`, должны оставаться без изменений.
- Артефакты сборки не должны отслеживаться; применяются политики зависимостей, лицензий, рабочих процессов и пакетов.

**Целевой цикл**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # изменения зависимостей или файла блокировки
npm run check:pack-policy      # изменения публичной поверхности опубликованного пакета
npm run lint
```

Используйте `npm run build` локально только тогда, когда изменение влияет на компиляцию, автономную сборку, ресурсы
или формирование пакета среды выполнения. Используйте `npm run build:release` только для проверки релиза/развёртывания. Сборка CI —
окончательный кроссплатформенный сигнал; для платформозависимых изменений Electron требуется соответствующая целевая сборка
или подтверждение проверкой работоспособности.

## Локальный цикл и CI

| Запускать локально для каждого патча                                                                                | CI предоставляет общую картину                                                       |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Прямые тесты поведения и указанные выше проверки категорий                                                          | Разделённый на сегменты полный набор модульных и последовательных тестов             |
| `npm run lint`                                                                                                      | Наборы тестов Vitest и пороговые проверки покрытия/качества                          |
| Проверка типов или сборка, только если этого требует затронутый контракт                                            | Продукционная сборка, проверки безопасности, документации, зависимостей и политик PR |
| Ручные интерактивные проверки/проверки в реальном времени, только если автоматизация не может подтвердить поведение | Межзадачные интеграционные и платформенные проверки, настроенные в рабочем процессе  |

Успешный целевой локальный цикл служит подтверждением корректности изменённого контракта, но не доказывает, что не связанные с ним проверки CI
будут пройдены. И наоборот, не заставляйте каждое локальное изменение ждать выполнения полной матрицы репозитория.

## Контрольный список согласования

Перед запросом на проверку:

- Убедитесь, что базовой веткой PR по-прежнему является самая старшая активная ветка `release/v*`.
- Получите изменения из этой базовой ветки и просмотрите коммиты, добавленные после создания вашей ветки.
- Проверьте `git diff <active-base>...HEAD` на наличие случайных или сгенерированных изменений.
- Разрешайте конфликты в каталогах и сгенерированных документах, обновляя исходные данные и повторно генерируя результат.
- После согласования повторно запустите каждый целевой тест и каждую проверку, указанные в описании PR.
- Никогда не ослабляйте утверждения и не удаляйте обязательные тесты только ради соответствия изменившейся базовой ветке.

Правила заморозки релиза и смены целевой ветки см. в документе
[Модель ветвления и релизов](BRANCHING_MODEL.md). Полный перечень проверок CI см. в документе
[Справочник по проверкам качества](../architecture/QUALITY_GATES.md).
