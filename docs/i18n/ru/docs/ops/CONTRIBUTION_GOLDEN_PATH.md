Используйте это руководство, чтобы выбрать минимальный надёжный цикл разработки для запроса на
слияние. Оно не заменяет приведённые ниже документы по архитектуре и безопасности для конкретных
областей, а связывает каждый распространённый тип изменений с его контрактами, целевыми проверками
и покрытием CI.

## Путь, который проходит каждое изменение

1. **Выберите базовую ветку до начала редактирования.** Найдите самую старшую активную ветку
   `release/v*` и создайте свою ветку от её вершины. Целевой должна быть эта ветка, а не `main`.
   Если действует заморозка релиза, не выбирайте замороженную ветку в качестве целевой; используйте
   следующий активный цикл, описанный в
   [Модели ветвления и релизов](BRANCHING_MODEL.md).
2. **Укажите контракты.** Определите каждый каталог, схему, сгенерированный артефакт, публичный API
   или пользовательский интерфейс, которых касается изменение. В таблице ниже приведён минимальный
   начальный набор.
3. **Напишите или обновите целевые тесты.** Изменения рабочего кода в `src/`, `open-sse/`,
   `electron/` или `bin/` требуют автоматизированного теста в том же PR. Запустите минимальный набор
   файлов тестов, подтверждающих нужное поведение, а затем перечисленные целевые проверки.
4. **Позвольте CI выполнить широкую матрицу проверок.** Полный набор сегментов модульных тестов,
   Vitest, контроль порога покрытия и рабочая сборка выполняются для PR. Запускайте широкий набор
   тестов локально только тогда, когда сбой целевой проверки указывает на более обширное влияние или
   когда изменение затрагивает несколько подсистем.
5. **Синхронизируйте изменения перед проверкой.** Получите актуальное состояние активной базовой
   ветки, изучите её новые коммиты и отличия вашей ветки от неё, затем перебазируйте ветку или
   выполните слияние с базовой веткой в соответствии с процессом для участников проекта. Устраняйте
   конфликты в сгенерированных файлах и каталогах через их исходные данные, повторно генерируйте их,
   заново запускайте целевой цикл и убедитесь, что PR по-прежнему направлен в активную релизную ветку.
6. **Зафиксируйте подтверждения.** В шаблоне PR перечислите выполненные команды, все добавленные или
   изменённые файлы тестов, миграции или флаги функций, а также все проверки, которые ещё предстоит
   выполнить только в CI.

## Рекомендуемые пути по типам изменений

Приведённые ниже команды — это минимальные целевые проверки, а не разрешение пропускать тест,
непосредственно покрывающий изменённое вами поведение.

### Провайдер

**Контракты**

- Определение провайдера в `src/shared/constants/providers/` и его подключение в
  `src/shared/constants/providers.ts`.
- Модели и возможности в `open-sse/config/providerRegistry.ts` или в выделенных из него файлах
  реестра.
- Выбор исполнителя/транслятора, настройка OAuth или ключа API, ресурсы панели управления и
  сгенерированный справочник провайдеров, когда применимо.
- Публичные учётные данные должны использовать `resolvePublicCred()`; ответы с ошибками должны
  использовать общие вспомогательные функции очистки ошибок. См. `docs/security/PUBLIC_CREDS.md`
  (git; не включается в сборку `/docs`) и
  [Очистка ошибок](../security/ERROR_SANITIZATION.md).

**Целевой цикл**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # при изменении каталога; включите сгенерированные изменения в коммит
npm run lint
```

Также протестируйте каждое затронутое семейство запросов: chat, Responses, images, embeddings, audio
или video. Рассматривайте изменения сгенерированного каталога и эталонных данных как изменения
контракта; не принимайте их без проверки.

### Маршрутизация

**Контракты**

- Публичные значения стратегий и метаданные пользовательского интерфейса в
  `src/shared/constants/routingStrategies.ts`.
- Диспетчеризация и порядок выполнения в `open-sse/services/combo.ts` и
  `open-sse/services/combo/`.
- Схемы combo, хранение данных, состояние отказоустойчивости, возможности моделей и элементы
  управления API/интерфейса.
- [Механизм Auto-Combo](../routing/AUTO-COMBO.md) и документация по отказоустойчивости при изменении
  поведения.

**Целевой цикл**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # изменения стратегии или диспетчеризации
npm run check:known-symbols      # изменения регистрации стратегии
npm run lint
```

Локально используйте детерминированные тесты с имитацией вышестоящих сервисов. Проверочные тесты
combo с реальными сервисами требуют учётных данных и выполняются вручную; они не заменяют CI.

### UI / UX

**Контракты**

- Маршрут/страница Next.js и границы общих компонентов в `src/app/` и
  `src/shared/components/`.
- Форматы ответов API, состояния загрузки/отсутствия данных/ошибки, поведение при использовании
  клавиатуры и программы экранного доступа, адаптивная компоновка, темы оформления и расширение
  локалей.
- Исходные строки английского интерфейса в `src/i18n/messages/en.json`; не добавляйте новые
  пользовательские тексты непосредственно в код.

**Целевой цикл**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Для изменений взаимодействия или визуального представления запустите приложение и проверьте узкие
и широкие области просмотра. CI выполняет рабочую сборку и более широкие наборы тестов; визуальное
поведение всё равно требует целевой проверки компонента, проверки Playwright или документированной
ручной проверки, соответствующей изменению.

### i18n

**Контракты**

- `src/i18n/messages/en.json` — источник строк пользовательского интерфейса;
  `config/i18n.json` — источник списка локалей.
- Каталоги CLI хранятся отдельно в `bin/cli/locales/`.
- Сохраняйте заполнители и теги ICU в точности. Не переводите названия продуктов, провайдеров и
  моделей, названия протоколов и заголовков, команды, идентификаторы кода/JSON, URL, переменные
  окружения и защищённые термины, такие как `OmniRoute`, `OAuth`, `MCP` и `A2A`. Текущий исходный
  список находится в `scripts/i18n/glossary/protected-terms.json`.

**Целевой цикл**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # при изменении строк или каталогов CLI
npm run lint
```

Это руководство по существующей системе, а не предложение расширять её инструментарий или модель
ключей. Пока проектируется новая система, изменения i18n должны быть точечными. Не запускайте
команды перевода, обращающиеся к внешним сервисам, если задача явно не требует сгенерированных
переводов и вы не проверили получившиеся изменения.

### CLI

**Контракты**

- Публичные команды и флаги в `bin/cli/`, сгенерированные команды API, коды завершения, stdout/stderr и
  структуры выходных данных JSON, поведение конфигурации/окружения и файлы, включённые в пакет.
- Строки CLI, видимые пользователю, должны использовать слой интернационализации CLI, а каталоги `en`/`pt-BR` должны оставаться синхронизированными.
- Сохраняйте Node в качестве поддерживаемой среды выполнения и соблюдайте контракт опубликованных бинарных файлов.

**Фокусный цикл**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # изменения сгенерированного/собранного CLI
npm run check:pack-policy     # изменения состава пакета
npm run lint
```

Используйте точную команду во временном каталоге данных, если поведение зависит от синтаксического анализа, файлов или
статуса завершения. CI выполняет более широкие проверки артефактов пакета и экосистемы.

### База данных

**Контракты**

- Доменные модули находятся в `src/lib/db/`; импортируйте конкретные модули напрямую (старый слой реэкспорта `localDb.ts` был удалён).
- Нумерованные идемпотентные SQL-миграции находятся в `src/lib/db/migrations/`; учитывайте безопасность транзакций, поведение
  при обновлении, индексы и всех вызывающих потребителей, затронутых схемой.
- Маршруты и обработчики никогда не выполняют необработанные SQL-запросы напрямую.

**Фокусный цикл**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

При добавлении миграции тестируйте как новую базу данных, так и обновление с предыдущей схемы. Тесты базы данных
должны закрывать дескрипторы и вызывать `resetDbInstance()` во время очистки. Запускайте `npm run test:bun:db`, только если
изменяется экспериментальный путь адаптера Bun; Node остаётся эталонной средой.

### Сборка / развёртывание

**Контракты**

- Корневые манифесты и манифесты рабочих пространств/lock-файл, `scripts/build/`, автономная сборка Next.js, содержимое пакета `dist/`,
  метаданные платформ Electron, рабочие процессы CI и контрольные маркеры развёртывания.
- Поддерживаемые диапазоны Node и разрешённое использование Bun, перечисленное в `CLAUDE.md`, должны оставаться неизменными.
- Артефакты сборки не должны отслеживаться; применяются политики зависимостей, лицензий, рабочих процессов и пакетов.

**Фокусный цикл**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # изменения зависимостей или lock-файла
npm run check:pack-policy      # изменения состава опубликованного пакета
npm run lint
```

Используйте `npm run build` локально, только если изменение затрагивает компиляцию, автономную сборку, ресурсы
или объединение среды выполнения в пакет. Используйте `npm run build:release` только для проверки релиза/развёртывания. Сборка CI
является окончательным кроссплатформенным индикатором; изменения Electron для конкретной платформы требуют соответствующей целевой сборки
или подтверждения посредством smoke-тестов.

## Локальный цикл работы с кандидатом

Тесты исходного кода не могут доказать, что упакованный артефакт запускается: ошибки в списках упаковки, удалённых зависимостях
и нативных бинарных файлах проявляются только после установки и запуска tarball. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) — это локальная часть описанного в RFC #8084 процесса «однократная сборка / проверка / продвижение»:
она собирает одного кандидата, проверяет именно этот артефакт, продвигает его путём переименования
каталогов и откатывает, если продвинутый слот не проходит проверку работоспособности.

```bash
npm run dev:candidate -- run --dry-run --json  # вывести план, ничего не изменяя
npm run dev:candidate -- run                   # собрать + проверить + продвинуть, автоматически откатить при ошибке
npm run dev:candidate -- build                 # npm pack + установка в _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # запустить на свободном порте, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # поменять местами current и previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # повторно использовать tarball, собранный в другом месте (CI)
```

- **Однократная сборка.** `build` упаковывает текущее дерево (для этого требуется `dist/server.js`, поэтому сначала выполните
  `npm run build:release`) или копирует `--from-tarball`, а затем устанавливает tarball в
  изолированный префикс npm, поскольку tarball не содержит `node_modules`. Идентификатором служит сокращённый SHA `HEAD`
  (`-dirty`, если в дереве есть локальные изменения) или `tgz-<sha256>` для tarball. Если кандидат с чистым идентификатором
  уже собран, он используется повторно вместо повторной сборки; передайте `--force`, чтобы пересобрать его.
- **Проверяйте пакет, а не исходный код.** `validate` запускает установленный CLI
  (`serve --port <free port>`) со свежим `DATA_DIR=<candidate>/data`, фиктивными секретами и удалёнными из
  окружения значениями оператора `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` и `INITIAL_PASSWORD`,
  чтобы проверить режим loopback без ключа для новой установки. Команда ожидает, пока
  `GET /api/health` вернёт 200, требует, чтобы `GET /v1/models` вернул 200, останавливает группу процессов
  и записывает результат в `validation.json` вместе с хешем tarball.
- **Продвигайте тот же артефакт.** `promote` отклоняет кандидата без успешной проверки для
  текущего хеша его tarball. Активный слот по умолчанию — `_artifacts/candidate/current`; `--target <dir>`
  выбирает другой каталог в той же файловой системе, а его предыдущим слотом становится `<dir>.previous`.
  Каждое переименование атомарно, а при ошибке в процессе уже выполненные переименования обращаются вспять.
- **Откат.** `run` повторно проверяет продвинутый слот и меняет `current` и `previous` обратно, если
  эта проверка завершается неудачно. Кандидат, не прошедший первую проверку, никогда не продвигается.

Всё записывается в игнорируемый Git каталог `_artifacts/candidate/`; существующая установка OmniRoute
и её каталог данных никогда не затрагиваются. CLI продвинутой версии находится по пути
`_artifacts/candidate/current/prefix/bin/omniroute`; при использовании запускайте его со своим `DATA_DIR`.
Коды завершения: `0` — успех, `1` — ошибка проверки или продвижения, `2` — ошибка использования или отсутствующая сборка.

## Локальный цикл и CI

| Запускается локально для каждого патча                                                        | CI предоставляет общую картину                                                       |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Прямые тесты поведения и указанные выше проверки категорий                                    | Разделённый на сегменты полный набор модульных и последовательных тестов             |
| `npm run lint`                                                                                | Наборы тестов Vitest и пороговые проверки покрытия/качества                          |
| Проверка типов или сборка — только когда этого требует затронутый контракт                    | Продукционная сборка, проверки безопасности, документации, зависимостей и политик PR |
| Ручные проверки взаимодействия/работы — только когда поведение нельзя проверить автоматически | Межзадачные интеграционные и платформенные проверки, настроенные в workflow          |

Успешный целевой локальный цикл подтверждает корректность изменённого контракта, но не гарантирует,
что пройдут не связанные с ним проверки CI. С другой стороны, не следует заставлять каждое локальное
изменение ждать выполнения полной матрицы репозитория.

## Контрольный список согласования

Перед запросом на ревью:

- Убедитесь, что базовой веткой PR по-прежнему является самая новая активная ветка `release/v*`.
- Получите изменения из этой базовой ветки и просмотрите коммиты, добавленные после создания вашей ветки.
- Проверьте `git diff <active-base>...HEAD` на наличие случайных или автоматически сгенерированных изменений.
- Разрешайте конфликты в каталогах и сгенерированных документах, обновляя исходные данные и повторно генерируя результат.
- После согласования повторно запустите все целевые тесты/проверки, перечисленные в описании PR.
- Никогда не ослабляйте утверждения и не удаляйте обязательные тесты только ради соответствия изменившейся базовой ветке.

Правила заморозки релиза и смены целевой ветки см. в документе
[Модель ветвления и релизов](BRANCHING_MODEL.md). Полный перечень проверок CI см. в документе
[Справочник по проверкам качества](../architecture/QUALITY_GATES.md).
