`news.json` በ`parseNewsPayload()` የተተገበረውን ዝግ v2 መርሐግብር ይጠቀማል፦

- `schemaVersion: 2` እና የተገደበ `items[]` ስብስብ፤
- የማይቀያየሩ፣ ልዩ የማስታወቂያ `id` እሴቶች፤
- በግልጽ የተገለጹ `active` እና ISO `publishedAt` መስኮች፤
- አስገዳጅ የእንግሊዝኛ ጽሑፍ ከአማራጭ አካባቢያዊ ትርጉሞች ጋር፤
- አማራጭ፣ ማረጋገጫ መረጃ የማይጠይቁ HTTPS አገናኞች እና በተፈቀደው ዝርዝር ውስጥ ያለ አዶ፤
- አዲሱን ንቁ ንጥል በቅድሚያ መምረጥ፣ አካባቢያዊ ቋንቋ ካልተገኘ ወደ እንግሊዝኛ መመለስ እና ለእያንዳንዱ ID አካባቢያዊ ማሰናበት።

ተንታኙ የቆዩ forks የተበላሸ Changelog እይታ ሳያጋጥማቸው እንዲሸጋገሩ፣ የቀድሞውን ነጠላ
`{ active, title, message, ... }` ቅርጽ ለጊዜው ይቀበላል። ልክ ያልሆኑ feeds ምንም ተጽዕኖ አያሳድሩም። የRadar ማስጀመሪያ
ግቤት `active: false` ሆኖ ይላካል፤ ይህንን ወደ `true` መቀየር ከውህደትና ከስምሪት በኋላ
የሚከናወን የተለየ የልቀት እርምጃ ሲሆን `RADAR_ENABLED`ን ወይም ራሱን የቻለውን የfeed-sync ፈቃድ አይቀይርም።

## ማብሪያ፦ `RADAR_ENABLED` (በነባሪ ጠፍቷል)

Radar ከጫፍ እስከ ጫፍ በ`RADAR_ENABLED` የባህሪ ማብሪያ
(`src/shared/constants/featureFlagDefinitions.ts`፣ ምድብ `policies`፣
`defaultValue: "false"`) ይገደባል።

**ማብሪያው ሲጠፋ በይነገጹ ፈጽሞ አይኖርም፦**

- የአካባቢያዊ ሞዴል ሁኔታ ንባብና ጽሑፍን ጨምሮ ሁሉም `/api/radar/*` endpoints፣
  ማንኛውንም የRadar ሞጁል ከመንካታቸው በፊት `404` ይመልሳሉ።
- የዳሽቦርድ ገጾቹ (`/dashboard/radar`፣ `/dashboard/radar/setup`፣
  `/dashboard/radar/combos`፣ `/dashboard/radar/offers`፣ `/dashboard/radar/intel`) `notFound()`ን ያሳያሉ።
- `getRadarCatalog()` (`src/lib/radar/index.ts`) ሳይነካ የቀረውን መሠረታዊ ስብስብ —
  ተመሳሳይ የግቤት ብዛት፣ ተመሳሳይ እሴቶች፣ እያንዳንዱ ግቤት `origin: "baseline"` የሚል መለያ ያለው — ይመልሳል፣ እንዲሁም
  የfeed cacheን ፈጽሞ አያነብም።
- ምንም የRadar የአውታረ መረብ ጥሪ ፈጽሞ አይደረግም፤ እያንዳንዱ የsync ሞጁል `fetch`ን
  ከመንካቱ በፊት `{ status: "disabled" }`ን ይመልሳል።

ይህ ጥብቅ የበላይ ደረጃ መግቢያ ነው፦ ማብሪያውን ማብራት _ገጾቹን_ ብቻ ይከፍታል፣ ከዚያ የበለጠ
ምንም አያደርግም። ውሂብ አይሰቅልም፣ የጀርባ sync አያስጀምርም፣ እንዲሁም
routingን ወይም የሞዴል ምርጫን አይቀይርም — ከታች ያለውን የተለየ ፈቃድ ይመልከቱ።

## የውሂብ sync የተለየ ፈቃድ ይፈልጋል — የግላዊነት ቃል ኪዳኑ

`RADAR_ENABLED`ን ማብራት UIን ብቻ ይከፍታል። feedን sync ማድረግ በ`radar_settings.opt_in` ውስጥ የሚከማች
ሁለተኛ፣ ራሱን የቻለ ፈቃድ ይፈልጋል (`src/lib/db/radar.ts`፣
migration `136_radar_cache_settings.sql`)። `syncRadar()` ማንኛውንም የአውታረ መረብ ጥሪ ከማድረጉ በፊት ማብሪያውን _እና_
ፈቃዱን ይፈትሻል፦

```
ማብሪያው ጠፍቷል → { status: "disabled" }   — የአውታረ መረብ ጥሪ የለም
ፈቃዱ false ነው  → { status: "opt_out" }    — የአውታረ መረብ ጥሪ የለም
```

ሁለቱም ሲበሩ የsync ሂደቱ እንደሚከተለው ነው፦

1. `GET <feed base URL>/v1/catalog/latest` ከ`x-omniroute-radar-schema: 2` እና ከአማራጭ
   `Authorization: Bearer <supporter key>` header ጋር (ከታች ይመልከቱ)። የschema header በማይኖርበት ጊዜ servers በነባሪ የተለየ
   ፊርማ ያለውን v1 የሽግግር artifact ይጠቀማሉ፣ በዚህም የቆዩ የተጫኑ clients ዝማኔዎችን
   መቀበላቸውን ይቀጥላሉ።
2. ይህ ማውረድ ብቻ የሚደረግበት የመተግበሪያ ፍሰት ነው፣ ነገር ግን አሁንም HTTPS ጥያቄ ነው። የሚስተናገደው
   መሠረተ ልማት እንደ ምንጭ IP ያሉ የተለመዱ የግንኙነት metadataዎችን ይቀበላል። supporter
   key ሲዋቀር፣ sync አገልግሎቱ መብቱን እንዲወስን ያንን key በBearer header ውስጥ ይልካል።
   ከላይ ባለው የማስረጃ ወሰን ውስጥ በተገለጸው ትክክለኛው የprivate-server revision ላይ፣
   የfeed-request ሒሳብ አያያዝ ለእጅ የስነምግባር ጥሰት ግምገማ key hashesን፣ የተጠቃለለ አጠቃቀምን እና በየቀኑ የሚቀያየር
   የIP truncated HMACን ይጠቀማል፤ እነዚያ tables keyንም ሆነ IPውን በጥሬ ቅርጽ አያከማቹም።
   የመሠረተ ልማት access logs እና encrypted delivery outbox የተለያዩ የአሠራር
   ወሰኖች ናቸው።
3. OmniRoute ጥያቄዎችን፣ ምላሾችን፣ ውይይቶችን፣ የአቅራቢ ማረጋገጫ መረጃዎችን፣ የሞዴል ትራፊክን፣
   uptimeን፣ latencyን ወይም የአካባቢያዊ አቅራቢውን ውቅር ወደRadar አገልግሎት ፈጽሞ አይልክም።
4. ምላሹ ይረጋገጣል፣ ትክክለኛነቱ ይፈተሻል፣ እንዲሁም በአካባቢው cache ይደረጋል (
   [የደህንነት ሞዴል](#security-model)ን ይመልከቱ)። Radar በትክክል አራት server-side የአውታረ መረብ መንገዶች አሉት፦
   `syncRadar()` ለcatalog፣ `syncRadarReferrals()` ለreferrals፣ እና
   `syncRadarOffers()` / `syncRadarIntel()` ለsupporter-only offers እና Intel።

**supporter key** የfeed አገልግሎቱ የትኛውን ደረጃ ማቅረብ እንዳለበት እንዲወስን የሚያስችል አማራጭ Bearer token
(`radar_settings.supporter_key`) ነው (
[ደረጃዎች](#tiers-community-and-live)ን ይመልከቱ)። ይህ፦

- ለአቅራቢ ማረጋገጫ መረጃዎች ከሚጠቀሙት ተመሳሳይ AES-256-GCM `encrypt()`/`decrypt()`
  helpers (`src/lib/db/encryption.ts`) ጋር **በማከማቻ ላይ encrypted** ሆኖ ይቀመጣል።
- በ`POST /api/radar/settings` (`{ supporterKey: "omr_" + 40 hex chars }`) በኩል ይቀናበራል፣ እና
  **ፈጽሞ ተመልሶ አይታይም** — ምላሹ የተሸፈነ ቅርጽ (`omr_****abcd`) ይመልሳል።
- እሱን መቀየር ወይም ማጽዳት catalog፣ referrals፣ offers እና Intel cachesን በአንድ የማይከፋፈል እርምጃ ዋጋ አልባ ያደርጋል።
  ቀጣዩ sync/read አዲሱን መብት server-side ይወስናል፤ keyን ማስቀመጥ በራሱ
  የአውታረ መረብ ጥያቄ አያደርግም ወይም single-use activation keyን አይጠቀምም።
- በsync GET ላይ እንደ Bearer token ወደfeed አገልግሎቱ ይላካል — ስለ
  keyው ሌላ ምንም ነገር ከclient አይወጣም።

`http://127.0.0.1:9351` ላለ loopback SSH ማስተላለፊያ ብቻ ነው፤ ሌሎች መርሃግብሮች፣ የተካተቱ ምስክርነት መረጃዎች፣ የተበላሹ URLs እና
የርቀት HTTP መዳረሻዎች በደህንነት ሁኔታ እንዳይሰሩ ይደረጋሉ እና አሰሳውን እንቅስቃሴ-አልባ ያደርጋሉ።

## የደህንነት ሞዴል

### በትክክለኛዎቹ ባይቶች ላይ የEd25519 ፊርማ

የፊዱ ይዘት በEd25519 ይፈረማል። `verifyFeedBytes()`
(`src/lib/radar/verify.ts`) በአውታረ መረቡ ላይ በተቀበላቸው **ትክክለኛ የምላሽ ባይቶች**
ላይ ፊርማውን ያረጋግጣል — ይዘቱ ከማረጋገጡ በፊት ፈጽሞ እንደገና አይሰራጭም፤ ስለዚህ
ባይት-በ-ባይት እንደገና ኢንኮድ ማድረግ በድብቅ የፊርማ ማረጋገጫውን ማሰናከል ወይም ማለፍ
አይችልም። የማረጋገጫ ውድቀት (`invalid_signature`) ይዘቱ ከመተንተኑ ወይም
ከመሸጎጡ በፊት ማመሳሰሉን ያቋርጣል።

### የተወሰነ የሕዝብ ቁልፍ + ማዞር

ማረጋገጫውን የሚያከናውነው የሕዝብ ቁልፍ በ`src/lib/radar/pinnedKeys.ts`
(`PINNED_FEED_PUBLIC_KEYS`) ውስጥ ተወስኗል፤ ይህም አዲስ ቁልፍ ከማዞር በፊት ከፊት
እንዲታከልና በቀድሞ ቁልፍ የተፈረሙ አሮጌ የተሸጎጡ ፊዶች እንደገና
እስኪመሳሰሉ ድረስ ትክክለኛ ሆነው እንዲቆዩ በድርድር መልክ ተቀምጧል።

### ለፎርክ ምቹ የenv መሻሪያዎች

ሁለት የenv ተለዋዋጮች ፎርኮችና በራሳቸው የሚያስተናግዱ ተጠቃሚዎች ነባሪውን
የOmniRoute አገልግሎት ከመጠቀም ይልቅ ደንበኛውን ወደ ራሳቸው ፊድ እንዲያመለክቱ ያስችላሉ —
ከታች [ፊድን በራስዎ እንዴት እንደሚያስተናግዱ](#how-to-self-host-a-feed) ይመልከቱ፦

| ተለዋዋጭ               | ዓላማ                                                                                 |
| ------------------- | ----------------------------------------------------------------------------------- |
| `RADAR_FEED_URL`    | የፊዱን መሠረታዊ URL ይተካል (ነባሪ `https://radar.omniroute.online`)።                         |
| `RADAR_FEED_PUBKEY` | የተወሰነውን የሕዝብ ቁልፍ (base64-DER SPKI ወይም PEM) በመተካት አብሮ የተካተተውን ድርድር በዚህ አንድ ቁልፍ ይተካል። |

### የስሪት ዝቅተኛ ገደብ

`syncRadar()` የወረደው ፊድ `version` አሁን ከተሸጎጠው ስሪት በጥብቅ የበለጠ ካልሆነ
ውድቅ ያደርገዋል (`compareVersions()`፣ በነጥብ የተለየ `YYYY.MM.DD.n` ንጽጽር) —
`{ status: "stale" }`። ይህ የተጠለፈ ወይም በስህተት የተዋቀረ የፊድ መጨረሻ ነጥብ ደንበኛን
ወደ ቀድሞ፣ በተለየ መንገድ ወደተፈረመ ይዘት መመለስ እንዳይችል ይከላከላል።

### ሁለት ቀኖች፣ እና ሁለቱም ለምን እንደሚቀመጡ

የተሸጎጠ ፊድ ሁለት የተለያዩ ቀኖችን ይይዛል፤ ሁለቱን ማምታታት ሁለቱም
የሚቀመጡበት ዋና ምክንያት ነው፦

| መስክ           | የመጣበት          | የሚመልሰው ጥያቄ               |
| ------------- | -------------- | ------------------------ |
| `generatedAt` | የተፈረመው የፊድ ይዘት | **ውሂቡ** ምን ያህል ያረጀ እንደሆነ |
| `fetchedAt`   | የዚህ ጭነት ሰዓት    | ይህ ጭነት መቼ **እንዳወረደው**    |

ከደቂቃዎች በፊት የወረደ ፊድ ከሳምንታት በፊት የተዘጋጁ አሃዞችን ሊይዝ ይችላል፤ ስለዚህ
`fetchedAt` ብቻውን ተደራቢው ከተቀመጠበት መሠረታዊ ውሂብ የበለጠ ወቅታዊ መሆኑን
ለአስተዳዳሪው ሊገልጽ አይችልም። ሁለቱም በ`radar_feed_cache` ውስጥ ይቀመጣሉ፣
በ`getRadarCatalog().meta` ይመለሳሉ፣ እና በ`GET /api/radar/status` ለየብቻ
ሪፖርት ይደረጋሉ። የ`generated_at` ዓምድ ከመኖሩ በፊት (migration 163) የተሸጎጠ ረድፍ
እንደ`null` ይነበባል — ያልታወቀው የማውረጃ ጊዜን ከመዋስ ይልቅ ያልታወቀ ሆኖ
ይቆያል። `radar_referrals_cache` ከmigration 142 ጀምሮ የራሱን `generated_at` ይዞ ቆይቷል።

ከላይ ያለው የስሪት ዝቅተኛ ገደብ የሚያነጻጽረው `version`ን እንጂ ከሁለቱ ቀኖች
አንዱን አይደለም።

ሁለት ክፍተቶች አሁንም አሉ፣ ሁለቱም ሆን ተብለው የተተዉ ናቸው፦ ዳሽቦርዱ አሁንም
`Last fetched`ን ብቻ ያሳያል፤ ስለዚህ የግንባታ ቀኑን በዚያ ለማንበብ አዲስ መለያ
(እና 41 የአካባቢ ቋንቋ ግቤቶቹ) ያስፈልጋል፤ እንዲሁም የቅናሾችና የመረጃ መሸጎጫዎች
የፊድ ንድፎቻቸው የግንባታ ቀን ቢይዙም እንኳ ምንም የግንባታ ቀን አያስቀምጡም —
ስለዚህ `GET
/api/radar/status` እንደ "ያልታወቀ" ሊነበብ የሚችል `null` ከማሳወቅ ይልቅ ለእነዚህ
ሁለት መስኩን ይተወዋል።

### የንድፍ ማረጋገጫ

የወረዱት ባይቶች የፊርማ ማረጋገጫው **ከተከናወነ በኋላ** በ`RadarFeedSchema`
(`src/lib/radar/feedSchema.ts`፣ የZod ንድፍ) መሠረት ይተነተናሉ እና ይረጋገጣሉ።
የንድፍ አለመዛመድ `{ status: "invalid_schema" }`ን ይመልሳል፣ መሸጎጫውም
ሳይነካ ይቀራል። የተሸጎጠው ይዘት በእያንዳንዱ ንባብ (`getRadarCatalog()`) ላይ
ለመከላከያ እንደገና ይረጋገጣል — የተበላሸ ወይም በእጅ የተስተካከለ የመሸጎጫ ረድፍ
ከመቅረብ ይልቅ ወደ መሠረታዊው ውሂብ ይመለሳል።

### የምላሽ መጠን ገደብ (10 MB)

`syncRadar()` በፊዱ ምላሽ አካል ላይ **የ10 MB ጥብቅ ገደብ** ያስፈጽማል — የተፈረመው
ፊድ በKB መጠን ያለ JSON ሰነድ ነው፤ ስለዚህ ከዚህ በላይ ያለ ማንኛውም ነገር
ህጋዊ ካታሎግን ሳይሆን በስህተት የተዋቀረ ወይም ጎጂ `RADAR_FEED_URL`ን
(ወይም ከላይኛው ምንጭ የሚቀርብ ቆሻሻ ውሂብን) ያመለክታል። አፈጻጸሙ ሁለት ደረጃዎች አሉት፦

1. ራስጌው ከገደቡ በላይ የሆነ ዋጋ ሲገልጽ የ`Content-Length` ቅድመ ምርመራ
   የምላሽ አካሉን ማንበብ ሙሉ በሙሉ ይዘላል።
2. የምላሽ አካሉን በማንበብ ጊዜ የሚደረግ የጠቅላላ መጠን ክትትል `Content-Length`
   ባይኖርም ወይም እውነተኛውን መጠን አሳንሶ ቢገልጽም ገደቡን ያስፈጽማል —
   ራስጌው በራሱ ፈጽሞ አይታመንም። የተሰበሰቡትን ክፍሎች ማገናኘት በኋላ
   ለሚደረገው የEd25519 ፊርማ ማረጋገጫ የሚያስፈልጉትን ትክክለኛ ባይቶች ይጠብቃል።

ገደቡን ማለፍ `{ status: "too_large" }`ን ይመልሳል እና መሸጎጫውን ሳይነካ ይተወዋል፤
ይህም ከሌሎች የማመሳሰል ውድቀቶች (`invalid_signature`፣ `invalid_schema`፣ `stale`)
ጋር ተመሳሳይ የማያጠፋ አሠራርን ይከተላል።

## በንባብ ጊዜ የተደራቢ ውህደት ደንቦች

`applyFeed()` (`src/lib/radar/applyFeed.ts`) በመሸጎጫ ያለውን ፊድ በስታቲክ
መሠረታዊ ውሂቡ **ላይ** በ**ንባብ ጊዜ**፣ በ`getRadarCatalog()` ውስጥ ያዋህዳል።
የመሠረታዊ ውሂቡ ድርድር (`FREE_MODEL_BUDGETS`) ፈጽሞ አይቀየርም — በእያንዳንዱ
ጥሪ ላይ አዲስ `MergedEntry[]` ይሰላል።

በቅድሚያ ቅደም ተከተል አራት ደንቦች፦

1. **ፊዱ የአካባቢ ማሻሻያን ፈጽሞ አይተካም።** በየመስኩ፦ ኦፕሬተሩ
   በአንድ ግቤት ላይ ያለ መስክን ካበጀ (`localOverrides` ካርታ፣ ቁልፉ
   `provider:modelId`)፣ ለዚያ የተወሰነ መስክ የፊዱ እሴት ይዘለላል — የኦፕሬተሩ
   እሴት ያሸንፋል።
2. **`enabled: false` ግቤቱን ከምንጩ መረጃ ጋር ያሰናክለዋል።** አንድን ግቤት
   የሚያጠፋ የፊድ ግቤት በተዋሃደው ውጤት ላይ `enabled: false` እና
   `disabledBy: "radar"` ያስቀምጣል፤ በዚህም UI አንድ ግቤት ከሚገኝ ወደ ተሰናከለ
   _ለምን_ እንደተቀየረ ማብራራት ይችላል።
3. **በፊዱ ውስጥ የሌለ በተጠቃሚ የታከለ ግቤት ሳይነካ ይቆያል።** በመሠረታዊ
   ውሂቡ ውስጥ ብቻ ያሉ (ወይም በአካባቢው የታከሉ) እና ተጓዳኝ የፊድ ግቤት
   የሌላቸው ግቤቶች ሳይቀየሩ ያልፋሉ።
4. **በማጥፋት ምልክት የተደረገበት ግቤት ፈጽሞ እንደገና አይመለስም።** ኦፕሬተሩ
   አንድን ግቤት በግልጽ ከሰረዘ (`tombstones` ስብስብ)፣ ፊዱ ያንን
   `provider:modelId` በኋለኛ ስሪት እንደገና ቢያክለውም መልሶ አያመጣውም።

ሊስተካከሉ የሚችሉ መስኮችና የማጥፋት ምልክቶች በ
`radar_local_model_state` (ማይግሬሽን `153_radar_local_model_state.sql`) ውስጥ
በቋሚነት ይቀመጣሉ። ይፋዊው የDB አስማሚ (`src/lib/db/radar.ts`) እነዚያን ረድፎች
በ`applyFeed()` ወደሚጠቀምባቸው `localOverrides` ካርታ እና `tombstones` ስብስብ
ይቀይራል፤ የምርት `getRadarCatalog()` የባንዲራ፣ የመሸጎጫ እና የንድፍ መግቢያ
ቁጥጥሮች ካለፉ በኋላ ያንን ሁኔታ ይጭናል። በኦፕሬተሩ ሊስተካከሉ የሚችሉት
`displayName` እና `enabled` ብቻ ናቸው። የአቅራቢ/ሞዴል ማንነት፣ የፊድ ምንጭ
መረጃ፣ ኮታ፣ ችሎታዎች፣ ToS እና የማዋቀሪያ ውሂብ በዚህ በይነገጽ በኩል
ሊጻፉ አይችሉም።

ዳሽቦርዱ አራት የአካባቢ ድርጊቶችን ያቀርባል፦

- **አርትዕ** የአካባቢውን የማሳያ ስምና የነቃ/የጠፋ ሁኔታ ይቀይራል።
- **የአካባቢ ለውጦችን ዳግም አስጀምር** የማጥፋት ምልክቱን ሳይቀይር ሁለቱንም
  ሊስተካከሉ የሚችሉ መስኮች ያጸዳል።
- **ደብቅ** የማጥፋት ምልክት ይፈጥራል፤ ስለዚህ በኋላ የሚመጡ የፊድ ዝማኔዎች
  ረድፉን እንደገና መፍጠር አይችሉም።
- **መልስ** የማጥፋት ምልክቱን ያስወግዳል፤ በተናጠል የተቀመጠ ማሻሻያ ካለ
  አሁንም ተግባራዊ ሆኖ ይቆያል።

የፊድ `enabled: false` የደህንነት ልዩ ሁኔታ ሆኖ ይቆያል፦ ጊዜ ያለፈበትን
የአካባቢ `enabled: true` ያሸንፋል፣ የተዋሃደውን ግቤት እንደተሰናከለ ያቆያል፣
እና `disabledBy: "radar"` ይመዘግባል።

የካታሎግ ህትመቶች `schemaVersion: 2` ይጠቀማሉ። `contextWindow` እና እያንዳንዱ
`tools`፣ `vision` እና `thinking` በተናጠል `number | null` / `boolean | null` ናቸው፦
`null` ማለት ያልታወቀ ማለት ሲሆን፣ `false` ማለት ግን በD16 የተረጋገጠ ይፋዊ
የአቅራቢ ምንጭ ችሎታው እንደሌለ በግልጽ ይገልጻል ማለት ነው። የውስጥ
OmniRoute ሬጅስትሪ/ሞዴል-ዝርዝር ባንዲራዎች በቀጥታ ወደ ፊድ እውነታዎች ፈጽሞ
አያድጉም። ክላይንቱ አሁንም v1 ቅጽበታዊ ቅጂዎችን ይቀበላል፤ የቀድሞው
መገንቢያ `false`ን እንደ አለመኖር ቦታ ያዥ ስለተጠቀመ፣ v1 `false` ወደ
ያልታወቀ ይደበኛል፣ v1 `true` ግን እንደ እውነታ ይቆያል። ያልታወቁ የንድፍ
ስሪቶች በነባሪ ይከለከላሉ፣ እና የመጨረሻው ትክክለኛ መሸጎጫ እንደሚገኝ
ይቆያል። ባዶ ያልሆነ አውድ/ችሎታ ያለው እያንዳንዱ v2 ሞዴል ማረጋገጫ
የማይጠይቅ HTTPS `metadataEvidenceUrls[]` ሊኖረው ይገባል፤ አለበለዚያ የንድፍ
ማረጋገጫው አይሳካም እና መሸጎጫው አይተካም። የካታሎጉ ሰንጠረዥ ሦስቱንም
ሁኔታዎች እንደ `✓`፣ `✕` እና `?` ያሳያል።

መመሪያ ያለው UI በ`/dashboard/radar/combos` ይገኛል። የሚያነበው የአካባቢውን
`GET /api/radar/catalog` እና `GET /api/combos/builder/options` መጨረሻ ነጥቦች ብቻ ነው። የRadar ማመሳሰልን ፈጽሞ አያስጀምርም፣
የአቅራቢ ማረጋገጫዎችን አያነብም፣ ወይም በቀጥታ ወደ combo የውሂብ ጎታ አይጽፍም።

የMCP ደንበኞች ተመሳሳዩን የአካባቢ ትንበያ በ`omniroute_radar_catalog` (`read:radar`) ማንበብ ይችላሉ።
አማራጭ የሆኑት `provider`፣ `familyId` እና `enabledOnly` ማጣሪያዎች አንድ የአካባቢ
`GET /api/radar/catalog` ንባብ ከተከናወነ በኋላ ይገመገማሉ። የተገደበው ውጤቱ የካታሎግ ሜታዳታን ከአቅራቢ/ሞዴል፣
ከማሳያ ስም፣ `familyId`፣ ኮታ፣ ችሎታዎች፣ የነቃ/የጠፋ ሁኔታ፣ ምንጭ እና `disabledBy` ጋር ያካትታል፤ የማዋቀሪያ URLs፣
ደረጃዎች፣ ግንኙነቶች፣ የኢ-ሜይል አድራሻዎች፣ ቁልፎች እና የሪፈራል ውሂብ ፈጽሞ አይመለሱም። ይህ መሣሪያ
ለንባብ ብቻ ሲሆን `/api/radar/sync`ን ፈጽሞ አይጠራም።

### የመነሻ ምልክቶች

እያንዳንዱ የተዋሃደ ግቤት UIው እንደ ባጅ የሚያሳየው `origin` መስክ አለው፦

በ`buildErrorBody()`/`sanitizeErrorMessage()` በኩል ያስተላልፋሉ።

### ማረጋገጫ

ሁሉም የRadar የመገልገያ ጫፎች `isAuthenticated()`
(`src/shared/utils/apiAuth.ts`)ን በመጠቀም ማረጋገጫ ይጠይቃሉ — የዳሽቦርድ ክፍለ-ጊዜ ኩኪ ወይም የአስተዳደር ወሰን ያለው
API ቁልፍ፤ ይህም የቀረውን `/api/settings/*` የሚጠብቀው ተመሳሳይ መግቢያ ነው። የሰንደቅ-መጥፋት
`404` ማረጋገጫው ሁልጊዜ ከማረጋገጫው **በፊት** ይከናወናል፤ ስለዚህ `RADAR_ENABLED`
የጠፋበት ጭነት በባይት ደረጃ አንድ ዓይነት ሆኖ ይቆያል (በይነገጹ እንደሌለ ለማወቅ ብቻ የማረጋገጫ ጥያቄ አይቀርብም)፤
ሰንደቁ አንዴ ከበራ፣ ማረጋገጫ የሌለው ጥያቄ ከማንኛውም የውሂብ ጎታ ንባብ ወይም
ጽሕፈት በፊት `401` ያገኛል። `GET /api/radar/settings` የማረጋገጫው ሁኔታ ምንም ይሁን ምን ጥሬውን የደጋፊ ቁልፍ ፈጽሞ አይመልስም —
የተሸፈነውን ቅርጽ እና `hasSupporterKey` ቡሊያን ብቻ ይመልሳል።

## የደጋፊ ቅናሾች

ቅናሾች የራሳቸውን የተፈረመ አርቲፋክት፣ `GET /v1/offers/latest`፣ ይጠቀማሉ፤ እንዲሁም ካታሎጉን ወይም የሪፈራል መሸጎጫውን በፍጹም አይጋሩም። የሰርቨሩ መዳረሻ ነጥብ ትክክለኛ እና ገቢር የደጋፊ Bearer ቁልፍ ይፈልጋል፤ የማህበረሰብ አማራጭ የለም። ስለዚህ `syncRadarOffers()` የባህሪ ጠቋሚው ሲጠፋ፣ ኦፕሬተሩ ለመሳተፍ ሳይመርጥ፣ ወይም ምንም የደጋፊ ቁልፍ ሳይዋቀር ከአውታረ መረቡ በፊት ይቆማል።

ከተሳካ GET በኋላ ደንበኛው በትክክለኛዎቹ የምላሽ ባይቶች ላይ ያለውን የEd25519 ፊርማ ያረጋግጣል፣ `RadarOffersFeedSchema`ን ያረጋግጣል፣ የተፈረመው የይዘት ክፍል እና የ`x-omniroute-feed-tier` ራስጌ ሁለቱም `live` እንዲሉ ይጠይቃል፣ በነጥቦች የተለየ በጥብቅ አዲስ ስሪት መሆኑን ያስፈጽማል፣ እና ከዚያ በኋላ ብቻ `radar_offers_cache`ን በአቶማዊነት ይተካል (ማይግሬሽን `144_radar_offers_cache.sql`)። ሌሎቹ ፊዶች የሚጠቀሙበት ተመሳሳይ የ10 MB ራስጌ-እና-ዥረት ገደብ ተፈጻሚ ይሆናል። የፊርማ፣ የስኪማ፣ የደረጃ፣ የድጋሚ ማጫወት፣ የመጠን፣ የHTTP እና የአውታረ መረብ አለመሳካቶች በሙሉ ለመጨረሻ ጊዜ የተረጋገጠውን መሸጎጫ ይጠብቃሉ።

ዝግ የቅናሽ ቅርጹ ሦስት ሊነጻጸሩ የሚችሉ የጥቅም አይነቶችን ይደግፋል፦ መቶኛ በመሠረታዊ ነጥቦች፣ ክሬዲት በአነስተኛ የገንዘብ አሃዶች፣ ወይም የሙከራ ቀናት። የአጋር ቅናሽ ከተመሳሳይ አይነት የሆነ ይፋዊ መነሻ መለኪያን ማካተት አለበት፣ እና ጥቅሙ በጥብቅ ከዚያ መብለጥ አለበት፤ ይፋዊ ቅናሾች የአጋር መነሻ መለኪያ የላቸውም። URLs የማረጋገጫ መረጃ የሌላቸው HTTPS መሆን አለባቸው። `getRadarOffers()` የተሸጎጠውን ጭነት በመከላከያዊነት እንደገና ያረጋግጣል እና በእያንዳንዱ አካባቢያዊ ንባብ ጊዜ ጊዜያቸው ያለፈባቸውን ግቤቶች ያጣራል፤ `/dashboard/radar/offers` ከማሳየቱ በፊት የጊዜ ማለፍን እንደገና ያጣራል፣ ሲገኝ የፖርቱጋልኛ ጽሑፍን በእንግሊዝኛ አማራጭ ይጠቀማል፣ እና የአጋር ቅናሾችን በግልጽ ይሰይማል።

አሳሹ የሚጠራው አካባቢያዊ መስመሮችን ብቻ ነው፦ የተሸፈነውን የቅንብሮች ቅጽበታዊ ገጽታ ያነባል፣ በሰርቨር በኩል ለማደስ `POST /api/radar/offers/sync`ን ይጠይቃል፣ ከዚያም `GET /api/radar/offers`ን ያነባል። ቁልፍ ከሌለ የፊድ ጥያቄ ለመላክ ከመሞከር ይልቅ ነባር የአስተዋጽዖ አድራጊ/ድጋፍ አገናኞችን ያሳያል። ውጫዊ የቅናሽ አገናኞች `noopener noreferrer`ን በመጠቀም በአዲስ ትር ይከፈታሉ። በዚህ ልቀት ምንም `radar_offers` MCP መሣሪያ አልቀረበም።

## Radar Intel፣ የደጋፊ ባጅ እና CLI

Intel በ`GET /v1/intel/latest` ላይ የሚገኝ የተፈረመ አርቲፋክት ነው። ዝግ `RadarIntelFeedSchema` በግል አስተዳዳሪው ከተረጋገጡ ንጽጽሮች የተዘጋጁ በRadar ባለቤትነት የሚያዙ የELO ደረጃዎችን እና ከተፈረሙ የካታሎግ ቅጽበታዊ ገጽታዎች የተገኙ እውነታዊ የካታሎግ እድሜ/ብዛት ልዩነቶችን ብቻ ይቀበላል። ዘዴው በመነሻ ደረጃ 1000 እና K=32 ላይ ተወስኗል። ምንም ንጽጽር ካልተረጋገጠ ባዶ የደረጃ ዝርዝር ትክክለኛ ነው፤ ደንበኛው በፍጹም ራሱ አያመነጭም።

`syncRadarIntel()` እንደ ቅናሾች ተመሳሳይ የሰርቨር-ወገን Bearer፣ የ30 ሰከንድ የጊዜ ገደብ፣ የ10 MiB የዥረት ገደብ፣ የትክክለኛ-ባይት Ed25519 ማረጋገጫ፣ ጥብቅ ስኪማ፣ የ`live` የይዘት ክፍል/ራስጌ መስፈርት፣ የስሪት ዝቅተኛ ወሰን እና የመጨረሻውን-ጥሩ-መሸጎጫ ጥበቃ ይተገብራል። የተረጋገጠ የቀጥታ ቅጽበታዊ ገጽታ ከተከማቸ በኋላ ደንበኛው `radar:<sha256(supporter key)>`ን ይፈጥራል፣ ያንን የአንድ-አቅጣጫ ማንነት ብቻ ያከማቻል፣ እና የተወሰነውን `radar_supporter` የእውቅና ክስተት ያወጣል። የእሱ `radar-supporter` ባጅ በተደጋጋሚ ሲተገበር ውጤቱ አይለወጥም እና ዜሮ XP ይሰጣል፤ የደረጃ ሰሌዳዎችን በፍጹም አያዘምንም ወይም `token_share`ን እንደገና አይጠቀምም። `/dashboard/radar/intel` ባጁን የሚያሳየው ከተረጋገጠ አካባቢያዊ የመሸጎጫ ሜታዳታ ብቻ ነው።

CLI `omniroute radar status`ን እና `omniroute radar sync`ን ያቀርባል። ሁለቱም ከአካባቢያዊ OmniRoute API ጋር ብቻ ይገናኛሉ። `status` ለንባብ ብቻ የሆነ `GET /api/radar/status`ን ያከናውናል፤ `sync` አንድ `POST /api/radar/sync-all` ይልካል እና ለእያንዳንዱ ፊድ ውጤት ያትማል። ሁለቱም ትዕዛዞች የደጋፊ ቁልፉን አያነቡም፣ አይቀበሉም ወይም አያትሙም፣ እንዲሁም የRadar አገልግሎትን በቀጥታ አያገኙም።

### ማመሳሰል

`syncRadarReferrals()` (`src/lib/radar/referralsSync.ts`) ለሪፈራሎች አውታረ መረቡን

`${RADAR_FEED_URL}/v1/referrals/latest`ን ያወርዳል (ከካታሎጉ ጋር ተመሳሳይ

የEd25519 ፊርማ ያረጋግጣል (`verifyFeedBytes`)፣ በ`RadarReferralsFeedSchema` ላይ

(ፍልሰት `142_radar_referrals_cache.sql`) — ይህም ከካታሎጉ `radar_feed_cache` ሙሉ
በሙሉ የተለየ ሰንጠረዥ ነው። የ10 MB የምላሽ ገደብ እና የ`generatedAt` ዝቅተኛ
ገደብ ከመሸጎጫው የቆየ ገቢ ፊድን ውድቅ በማድረግ፣ የቆየ የተፈረመ አርቲፋክት
እንደገና ከመጫወት ይከላከላሉ። እኩል የጊዜ ማህተም ተቀባይነት አለው፦ አገልጋዩ
ሆን ብሎ ለማህበረሰብ እና ቀጥታ የሪፈራል ልዩነቶች ተመሳሳይ ቆራጥ `generatedAt`
ይሰጣል፣ ስለዚህ ከsupporter-ቁልፍ ለውጥ በኋላ መሠረታዊው የአገናኞች ስብስብ
ሳይለወጥ የተፈረመው ጭነት እና የቀረበው ደረጃ ሊለወጡ ይችላሉ። ፈጽሞ
exception አይጥልም — ሁልጊዜ የሁኔታ ኦብጀክት ይመልሳል፤ ስህተቶች በ`reason`
ውስጥ stack trace ፈጽሞ አይይዙም።

ሁለት አስነሺዎች የሪፈራሎች መሸጎጫ ወቅታዊ እንዲሆን ያደርጋሉ፣ ሁለቱም ከካታሎጉ
የ24h ድግግሞሽ ነፃ ናቸው፦

- **በማንበብ ጊዜ ማመሳሰል** — መሸጎጫው በሌለበት ወይም ከ`REFERRALS_STALE_MS`
  (1h፣ `shouldSyncReferralsOnRead()`) በላይ ባረጀ ጊዜ፣ ምላሹን ከማቅረቡ በፊት
  `GET /api/radar/referrals` ራሱ `syncRadarReferrals()`ን በቦታው ይጠራል። የትኛውንም
  የበስተጀርባ ጊዜ ቆጣሪ ሳይጠብቁ፣ ቋሚ አገናኞችን ለሚቀጥለው የዳሽቦርድ ጭነት
  "ሁልጊዜ ወቅታዊ" የሚያደርጋቸው ይህ ነው።
- **የጊዜ ሰሌዳ አስኪያጅ የጎን ማመሳሰል** — `radarSchedulerTick()` (`scheduler.ts`)
  ለካታሎጉ በሚጠቀምበት ተመሳሳይ የሰዓት ምት ላይ የሪፈራሎችን መርጀት ለብቻው
  ይገመግማል፣ ጊዜው ሲደርስ `syncRadarReferrals()`ን ይጠራል። ይህ በዚያ ምት ላይ
  የካታሎጉ ጊዜ ደርሶም ይሁን አይደርስ ይሰራል፣ እና የ`RadarTickResult`ን ቅርጽ
  ፈጽሞ አይነካም (በተቻለ መጠን የሚከናወን የጎን ተጽዕኖ ብቻ ሲሆን፣ ስህተት
  ቢከሰት ችላ ይባላል)።

### መዳረሻ

`src/lib/radar/index.ts` ሁለት ለንባብ-ብቻ የሆኑ መዳረሻዎችን ይልካል፣ ሁለቱም
ፈጽሞ exception አይጥሉም (ከ`getRadarCatalog()` ጋር ተመሳሳይ የመከላከያ ውል —
ጠቋሚው ጠፍቷል፣ መሸጎጫ የለም፣ ወይም የተበላሸ በመሸጎጫ የተቀመጠ ጭነት
አለ፤ ሁሉም ከስህተት ይልቅ ወደ ባዶው ቅርጽ ይፈታሉ)፦

- `getRadarReferrals()` → `{ fixed: RadarReferral[], campaigns: RadarReferral[] }`፣
  ከ`radar_referrals_cache` (በ`getRadarReferralsCache()` በኩል) በማንበብ እና
  በ`RadarReferralsFeedSchema` በኩል በማረጋገጥ — ከካታሎግ መሸጎጫው **አይደለም**።
- `getDefaultReferralFor(provider)` → ለዚያ provider `isDefault: true` ያለውን
  `fixed` ሪፈራል፣ ወይም `null`። `fixed`ን ብቻ ይመለከታል — campaign ፈጽሞ
  እንደ provider "ነባሪ" አገናኝ ጥቅም ላይ አይውልም።

ትክክለኛው "ለአንድ provider የትኛው ሪፈራል ነባሪ ነው" የሚለው ደንብ
በ`findDefaultReferral()` (`src/lib/radar/referrals.ts`) ውስጥ ይገኛል፤ ይህም
**ምንም DB import የሌለው** አነስተኛ pure function ነው — ወደ `"use client"`
component ለማስገባት ደህንነቱ የተጠበቀ ነው። `getRadarReferrals`/
`getDefaultReferralFor` (`index.ts` ውስጥ) `@/lib/db/radar`ን ይጭናሉ፣ ስለዚህ
በserver-only ይቆያሉ፤ የproviders ዳሽቦርድ `better-sqlite3`ን ወደ አሳሹ
እንዳያቀናጅ፣ ከ`index.ts` ይልቅ `referrals.ts`ን በቀጥታ ያስገባል (ከታች ይመልከቱ)።

### `GET /api/radar/referrals`

ልክ እንደ ሌሎቹ የRadar route ሁሉ ተመሳሳይ የgate ቅደም ተከተልን ይከተላል፦ `RADAR_ENABLED` ጠፍቶ ከሆነ →
`404` (መጀመሪያ ይፈተሻል፣ ባይት-ለ-ባይት ተመሳሳይ የሆነ inertia)፤ ማንነቱ ያልተረጋገጠ → `401`፤ ካልሆነ፣
ጊዜ ያለፈበት ሲሆን sync-on-read ያስነሳል (ከላይ ይመልከቱ)፣ ከዚያም
`{ fixed, campaigns, tier }` ያለውን `200` ይመልሳል — `tier` በቀጥታ ከ(ምናልባት አሁን ከታደሰው)
የcache row ይመጣል፣ ለመረጃ ብቻ ነው (ከታች ያለውን የUI ለስላሳ upsell ጽሑፍ ይመራል)።
የfeed serverን በቀጥታ proxy አያደርግም — የrouteው የራሱ source ምንም `fetch(` call የለውም፤
network የሚከሰተው በ`syncRadarReferrals()` ውስጥ ብቻ ነው፣ ልክ እንደ `/api/radar/catalog`
ተመሳሳይ የlocal-cache-only መርህን ይከተላል።

### የDashboard UI — በ`/dashboard/radar` ላይ ያለው "ነፃ credits" tab

አዲስ route ከመፍጠር ይልቅ ነባሩን የRadar ገጽ (`src/app/(dashboard)/dashboard/radar/page.tsx`)

  የቋሚ links ዝርዝርን አይደብቅም ወይም አይገድብም፤ ዝርዝሩ ለእያንዳንዱ tier ሙሉ ሆኖ ይቆያል።

  keyን እንደገና በመጠቀም) — በፍጹም አዲስ፣ የተለየ visual treatment አይጠቀምም።

## ፊድን እራስዎ እንዴት ማስተናገድ እንደሚችሉ

በካታሎጉ ላይ ሙሉ ቁጥጥር ማድረግ የሚፈልግ fork ወይም እራሱ አስተናጋጅ የደንበኛ ኮድን ሳይነካ የራሱን ፊድ
አገልግሎት ማስኬድ ይችላል፦

1. `RadarFeedSchema` (`src/lib/radar/feedSchema.ts`)ን የሚያሟላ JSON ይዘት የሚመልስ `GET /v1/catalog/latest` endpoint ያቅርቡ — ከፍተኛ ደረጃ `feed:
"omniroute-radar"`፣ `schemaVersion: 2`፣ `version`፣ `tier`፣ `providers`፣ `models`፣
   `quirks` እና `totals`። `x-omniroute-radar-schema: 2`ን ያክብሩ፤ ከሽግግር ጋር ተኳሃኝ የሆነ አገልጋይ
   ይህን ያላካተቱ ጥያቄዎችን በነባሪነት በተለየ ሁኔታ ወደተፈረመ v1 artifact መምራት አለበት።
2. ትክክለኛዎቹን የምላሽ bytes በEd25519 የቁልፍ ጥንድ ይፈርሙ እና base64
   ፊርማውን በ`x-omniroute-feed-signature` የምላሽ header ውስጥ ይመልሱ።
3. `RADAR_FEED_URL`ን ወደ አዲሱ base URL እና `RADAR_FEED_PUBKEY`ን ወደ ተዛማጁ
   ይፋዊ ቁልፍ (base64-DER SPKI ወይም PEM) ያዘጋጁ —
   [የenv var ማጣቀሻውን](../reference/ENVIRONMENT.md#27-radar-feed-self-hosting) ይመልከቱ።
4. `RADAR_ENABLED`ን ያንቁ እና በ`POST /api/radar/settings`
   (`{ optIn: true }`) በኩል መርጠው ይግቡ።

ሌላ ምንም የኮድ ለውጥ አያስፈልግም — `verifyFeedBytes()` ማሻሻያውን
በራስ-ሰር ይወስዳል (`getFeedPublicKeys()` በ`src/lib/radar/pinnedKeys.ts` ውስጥ)፣ እና የversion
ንጽጽር፣ የschema ማረጋገጫ እና የማዋሃድ ደንቦቹ በራስ-አስተናጋጅ
ፊድ ላይም በተመሳሳይ ሁኔታ ይተገበራሉ።

የReferral አገናኞች (ከላይ [የReferral አገናኞች (ነፃ ክሬዲቶች)](#referral-links-free-credits)ን
ይመልከቱ) የተለየና አማራጭ artifact ናቸው፦ `/v1/catalog/latest`ን ብቻ
የሚያቀርብ fork አሁንም ሙሉ በሙሉ ይሠራል — `syncRadarReferrals()` ከ`/v1/referrals/latest`
በሚመጣ `404` ጊዜ ወደ `{ status: "error" }` ዝቅ ይላል፣ እና cacheው ባዶ ሆኖ ስለሚቆይ
`GET /api/radar/referrals` ቀሪውን ገጽ ከማሳካት ይልቅ `{ fixed: [], campaigns: [], tier: null }`ን
መመለሱን ይቀጥላል። የReferral አገናኞችንም ለማቅረብ፣
`RadarReferralsFeedSchema` (`src/lib/radar/referralsFeedSchema.ts`)ን የሚያሟላ
`GET /v1/referrals/latest` ያቅርቡ እና ከካታሎግ ፊዱ ጋር በተመሳሳይ Ed25519 የቁልፍ ጥንድ
ይፈርሙት።

የSupporter ቅናሾች ሌላ አማራጭ artifact ናቸው። እነሱን ለማቅረብ፣
`GET /v1/offers/latest`ን በተዘጋው `RadarOffersFeedSchema`
(`src/lib/radar/offersFeedSchema.ts`) ይተግብሩ፣ ቀጥታ entitlement ይጠይቁ፣
`x-omniroute-feed-tier: live`ን ይመልሱ እና ትክክለኛዎቹን bytes በተመሳሳዩ ቁልፍ ይፈርሙ። ይህን
endpoint ያላካተተ fork የካታሎግ/Referral ባህሪውን ሳይቀይር ያቆያል፤ የቅናሽ ማደስ አጥፊ ባልሆነ ሁኔታ ይሳናል፣ እና
ለመጨረሻ ጊዜ የተረጋገጠው አካባቢያዊ የቅናሽ cache እንደተገኘ ይቆያል።

Intelም በተመሳሳይ ሁኔታ አማራጭ ነው። እራሱ አስተናጋጅ `RadarIntelFeedSchema`
(`src/lib/radar/intelFeedSchema.ts`)ን በመጠቀም `GET /v1/intel/latest`ን ማቅረብ፣ ቀጥታ entitlement መጠየቅ፣
`x-omniroute-feed-tier: live`ን መመለስ እና ትክክለኛዎቹን bytes በጋራው Ed25519 ቁልፍ መፈረም ይችላል። endpointን
አለማካተት ካታሎግን፣ Referralsን እና ቅናሾችን ሳይቀይር ያቆያል፤ የIntel ማደስ ለመጨረሻ ጊዜ የተረጋገጠውን
አካባቢያዊ snapshot ይጠብቃል።
