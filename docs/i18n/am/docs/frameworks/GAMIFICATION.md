## አጠቃላይ እይታ

### ዓላማ

የሚታይ እድገትን (XP፣
ደረጃዎች፣ ባጆች)፣ ማህበራዊ ማረጋገጫን (የደረጃ ሰንጠረዦች) እና ኢኮኖሚያዊ ማበረታቻዎችን (ቶከን
ማጋራት፣ የግብዣ ሽልማቶች) በማቅረብ የተጠቃሚ ተሳትፎን እና ቆይታን ማሳደግ።

### የንድፍ መርሆዎች

1. **አካባቢያዊነትን ቅድሚያ የሚሰጥ** — ሁሉም ሁኔታ በSQLite ውስጥ ይገኛል፣ ምንም ውጫዊ አገልግሎት አያስፈልግም።
2. **የማያግድ** — ክስተቶች ምላሽ ሳይጠብቁ ይላካሉ፤ የLLM ምላሽ መንገድ
   በጨዋታ ማበረታቻ አመክንዮ ፈጽሞ አይዘገይም።
3. **በሰርቨር የሚተዳደር** — XP የሚሰላው በሰርቨር ወገን ብቻ ነው፤ ደንበኞች
   ነጥቦችን በማጋነን ማሳደግ አይችሉም።
4. **ግላዊነትን የሚያከብር** — በደረጃ ሰንጠረዥ ውስጥ መሳተፍ በምርጫ ነው፤ ተጠቃሚዎች
   መገለጫቸውን መደበቅ ይችላሉ።
5. **ለፌዴሬሽን ዝግጁ** — የማህበረሰብ ሰርቨሮች በተፈረመ API አማካኝነት ነጥቦችን መግፋት ይችላሉ፤
   ማመሳሰል የሚተካ እንጂ የሚደመር አይደለም።

## አርክቴክቸር

### ከፍተኛ-ደረጃ ፍሰት

```
የደንበኛ ጥያቄ
  → /v1/chat/completions
    → handleChatCore()                      [open-sse/handlers/chatCore.ts]
      → ... (ነባር ሂደት) ...
      → ወደ ላይኛው አቅጣጫ የተላከው ምላሽ ለደንበኛው ተላከ
      → setImmediate (ምላሽ ሳይጠብቅ):
        → emitGamificationEvent()           [src/lib/gamification/events.ts]
          → awardXp()                       [src/lib/gamification/xp.ts]
          → updateStreak()                  [src/lib/gamification/streaks.ts]
          → evaluateBadges()                [src/lib/gamification/badges.ts]
          → updateLeaderboard()             [src/lib/gamification/leaderboard.ts]
          → checkAnomalies()                [src/lib/gamification/antiCheat.ts]
```

### የሽልማት ፍሰት

```typescript
export async function awardXp(
  apiKeyId: string,
  action: XpAction,
  metadata?: Record<string, unknown>
): Promise<{ xp: number; level: number; title: string; levelUp: boolean }>;
```

1. የXP መጠኑን ለማግኘት `XP_REWARDS[action]`ን ይፈልጉ።
2. በ`checkRateLimit()` ውስጥ ያሳልፉ (ማጭበርበርን ለመከላከል፦ ለእያንዳንዱ ቁልፍ በደቂቃ ከፍተኛው 1000 XP)።
3. ግብይት ይክፈቱ፦
   - የአሁኑን `user_levels` ረድፍ ያንብቡ።
   - XP ይጨምሩ፤ `levelFromXp(totalXp)`ን በመጠቀም ደረጃውን እንደገና ያስሉ።
   - ደረጃው ከተቀየረ፣ `levelUp = true` ያድርጉ።
   - የ`user_levels` ረድፉን ያዘምኑ።
   - ወደ `xp_audit_log` ያስገቡ።
4. ውጤቱን ይመልሱ። ጠሪው ማሳወቂያዎችን ያስተናግዳል።

### ረዳት፦ `levelFromXp(totalXp)`

በደረጃ 1..100 ውስጥ እየዞረ፣ ድምር XPው `totalXp`ን
እስኪያልፍ ድረስ `xp_for_level(n)`ን ይደምራል። መጠነ-ገደቡን ያሟላውን ከፍተኛውን ደረጃ ይመልሳል።
ይህ O(100) ነው — ደረጃዎች በ100 ስለሚገደቡ ተቀባይነት አለው።

### የግምገማ ፍሰት

```
emitGamificationEvent(event)
  → evaluateBadges(apiKeyId, event)
    → getBadgeDefinitions()           # ሁሉም ትርጓሜዎች
    → getUserBadges(apiKeyId)         # አስቀድሞ የተገኙ (ዝለል)
    → ላልተገኘ ለእያንዳንዱ ባጅ፦
       → matchesCriteria(badge, event, userState)
       → ከተዛመደ፦ awardBadge(apiKeyId, badgeId)
         → የማሳወቂያውን payload መልስ
```

ግምገማው **በክስተት የሚነሳ** ነው — ከእያንዳንዱ የጨዋታ ማበረታቻ ክስተት በኋላ ይሰራል፣ ነገር ግን
`criteria.type`ቸው ከክስተቱ ድርጊት ጋር የሚዛመዱ ባጆችን ብቻ ይፈትሻል። ይህ
ግምገማውን ፈጣን ያደርገዋል (ለአብዛኛዎቹ ክስተቶች < 5ms)።

## ተከታታይነት መከታተያ

**ፋይል:** `src/lib/gamification/streaks.ts`

### የውሂብ ሞዴል

ተከታታይነቶች በስም ክልል በተለዩ ቁልፎች ስር በ`key_value` ሰንጠረዥ
(የጋራ መገልገያ ሰንጠረዥ) ውስጥ ይቀመጣሉ፦

| ቁልፍ                           | ዋጋ                               | መግለጫ            |
| ----------------------------- | -------------------------------- | --------------- |
| `gamification:streak:{keyId}` | `{current},{longest},{lastDate}` | የንቁ ተከታታይነት ውሂብ |

### አመክንዮ

```typescript
export async function updateStreak(
  apiKeyId: string
): Promise<{ current: number; longest: number; milestone: boolean }>;
```

1. የተከታታይነት መዝገቡን ከ`key_value` ያንብቡ።
2. `{current}`ን፣ `{longest}`ን እና `{lastDate}`ን (የISO ቀን ሕብረቁምፊ) ይተንትኑ።
3. `lastDate === today` ከሆነ — ምንም ለውጥ የለም (ዛሬ አስቀድሞ ተቆጥሯል)።
4. `lastDate === yesterday` ከሆነ — `current`ን በአንድ ይጨምሩ፤ አስፈላጊ ከሆነ `longest`ን ያዘምኑ።
5. `lastDate < yesterday` ከሆነ — `current = 1` በማድረግ ዳግም ያስጀምሩ (ተከታታይነቱ ተቋርጧል)።
6. የዘመነውን መዝገብ ይጻፉ።
7. የደረጃ ምዕራፎችን ያረጋግጡ፦ 7፣ 14፣ 30፣ 60፣ 90፣ 180፣ 365 ቀናት። ከእነዚህ አንዱ ከታለፈ
   `milestone = true` ያድርጉ (ጠሪው XP ይሰጣል እና ባጆችን ያረጋግጣል)።

### ልዩ ሁኔታዎች

- **የሰዓት ሰቅ**፦ ተከታታይነቶች UTC ቀናትን (`new Date().toISOString().slice(0, 10)`) ይጠቀማሉ።
  ይህ ሆን ተብሎ የተደረገ ነው — አንድ መደበኛ የሰዓት ሰቅ በሰዓት ሰቆች መካከል
  በመዘዋወር ስርዓቱን መጠቀሚያ እንዳይሆን ይከላከላል።
- **አዲስ ተጠቃሚዎች**፦ ምንም የተከታታይነት መዝገብ የለም፤ የመጀመሪያው ጥያቄ
  `current=1, longest=1, lastDate=today` ያለው መዝገብ ይፈጥራል።
- **በቀን ውስጥ ብዙ ጥያቄዎች**፦ ተከታታይነቱን የሚጨምረው በUTC ቀን
  የመጀመሪያው ጥያቄ ብቻ ነው።

## ቶከን ማጋራት

**ፋይል:** `src/lib/gamification/sharing.ts`

### ድርብ-ግቤት ሂሳብ መዝገብ

እያንዳንዱ ዝውውር በ`token_ledger` ውስጥ ሁለት ረድፎችን ይፈጥራል፦

| ረድፍ  | `from_key_id` | `to_key_id` | `amount` |
| ---- | ------------- | ----------- | -------- |
| ዴቢት  | ላኪ            | ተቀባይ        | +መጠን     |
| ክሬዲት | ተቀባይ          | ላኪ          | -መጠን     |

ይቆዩ — መደበኛው አሠራር ይህ ነው፦

| ረድፍ  | `from_key_id` | `to_key_id` | `amount` | ትርጉም              |
| ---- | ------------- | ----------- | -------- | ----------------- |
| መላክ  | ላኪ            | ተቀባይ        | +መጠን     | ከላኪው የሚወጣ ገንዘብ    |
| መቀበል | ተቀባይ          | ላኪ          | +መጠን     | ወደ ተቀባዩ የሚገባ ገንዘብ |

ቀሪ ሂሳቡ እንደሚከተለው ይሰላል፦

```sql
SELECT
  COALESCE(SUM(CASE WHEN to_key_id = ? THEN amount ELSE 0 END), 0)
  - COALESCE(SUM(CASE WHEN from_key_id = ? THEN amount ELSE 0 END), 0)
  AS balance
FROM token_ledger
WHERE from_key_id = ? OR to_key_id = ?
```

### የዝውውር ፍሰት

```typescript
export async function transferTokens(
  fromKeyId: string,
  toKeyId: string,
  amount: number,
  idempotencyKey: string
): Promise<{ success: boolean; balance: number }>;
```

1. **አረጋግጥ**፦ `amount > 0`፣ `fromKeyId !== toKeyId`።
2. **Idempotency**፦ `idempotency_key` አስቀድሞ በሂሳብ መዝገቡ ውስጥ መኖሩን ያረጋግጡ።
   ካለ፣ በመሸጎጫ የተቀመጠውን ውጤት ይመልሱ።
3. **ግብይት** (አንድ የSQLite ግብይት)፦
   a. የላኪውን ቀሪ ሂሳብ ያስሉ።
   b. `balance < amount` ከሆነ፣ ያቋርጡ (በቂ ገንዘብ የለም)።
   c. የመላኪያ ረድፍ ያስገቡ (`from=sender,` ይመልሱ።

### የፍጥነት ገደብ

- ለእያንዳንዱ API ቁልፍ በደቂቃ ቢበዛ 10 ዝውውሮች።
- በአንድ ዝውውር ቢበዛ 10,000 ቶከኖች።
- ለእያንዳንዱ API ቁልፍ በቀን ቢበዛ 100,000 ቶከኖች ይዘዋወራሉ።

### የኮድ ቅርጸት

- **ኮድ**፦ ባለ8-ቁምፊ ፊደላዊ-ቁጥራዊ ኮድ (ለምሳሌ፣ `A3K9-X7M2`)፣ ለሰው ልጅ ለማንበብ ቀላል የሆነ፣
  ለተጠቃሚው የሚታይ።
- **ቶከን**፦ ባለ32-ባይት የዘፈቀደ ቶከን፣ እንደ SHA-256 ሃሽ የሚከማች። ለፕሮግራማዊ
  መቤዠት (ለምሳሌ፣ የURL አገናኞች) ያገለግላል።

### ማከማቻ

| ዓምድ          | እሴት                          |
| ------------ | ---------------------------- |
| `code`       | `A3K9X7M2` (ልዩ፣ ኢንዴክስ የተደረገ) |
| `token_hash` | SHA-256(raw_token)           |

ጥሬው ቶከን በሚፈጠርበት ጊዜ በትክክል አንድ ጊዜ ለተጠቃሚው ይመለሳል። OmniRoute
ከዚያ በኋላ ፈጽሞ አያከማቸውም ወይም አያሳየውም — የሚቆየው ሃሹ ብቻ ነው።

### ራስን ሪፈር ማድረግን መከላከል

አንድ ተጠቃሚ ኮድን ሲቤዥ፣ ሥርዓቱ የሚከተሉትን ያረጋግጣል፦

1. ኮዱ የተለየ `api_key_id` ንብረት ነው።
2. ቶከኑን የሚቤዠው ተጠቃሚ ከዚያው ሪፈር አድራጊ የመጣ ማንኛውንም ኮድ
   ከዚህ በፊት አልተጠቀመም (`invite_tokens` + የመቤዠት መዝገብ ላይ በማገናኘት)።

ከሁለቱ ማረጋገጫዎች አንዱ ካልተሳካ፣ መቤዠቱ ግልጽ የስህተት መልዕክት በመስጠት ውድቅ ይደረጋል።

### የማለቂያ ጊዜ እና ገደቦች

- ነባሪ `max_uses`፦ 10 (በሚፈጠርበት ጊዜ ሊዋቀር ይችላል)።
- ነባሪ `expires_at`፦ ከተፈጠረበት ጊዜ ጀምሮ 30 ቀናት።
- ጊዜያቸው ያለፈ ወይም የአጠቃቀም ገደባቸው ያለቀ ኮዶች HTTP 410 Gone ይመልሳሉ።

## የማህበረሰብ አገልጋይ ፌዴሬሽን

**ፋይል፦** `src/lib/gamification/servers.ts`

### ማገናኘት

የማህበረሰብ አገልጋይ በርቀት አገልጋዩ በሚሰጥ የግብዣ ቶከን አማካኝነት ይመዘገባል። የአካባቢው ኢንስታንስ፦

1. የግብዣ ቶከኑን ይቀበላል (ለምሳሌ፣ በዳሽቦርዱ ውስጥ የተለጠፈ)።
2. ቶከኑን ለማረጋገጥና የአሁኑን የደረጃ ሰንጠረዥ ለማምጣት በርቀት አገልጋዩ ላይ `POST /api/gamification/federation/leaderboard`ን ይጠራል።
3. የአገልጋዩን መዝገብ ከ`status: connected` ጋር ያከማቻል።

### የማመሳሰል ሞዴል

ፌዴሬሽኑ መደመርን ሳይሆን **በላዩ ላይ የመጻፍ ማመሳሰልን** ይጠቀማል፦

```
የአካባቢ ኢንስታንስ                    የማህበረሰብ አገልጋይ
     │                              │
     ├── ውጤት ግፋ ─────────────────►│  POST /federation/score
     │   { api_key_id, score }      │  (አገልጋዩ የቶከኑን ሃሽ ያረጋግጣል)
     │                              │
     ├── የደረጃ ሰንጠረዥ ሳብ ─────────►│  GET /federation/leaderboard
     │◄── ከፍተኛ-N ግቤቶች ────────────┤  (በአካባቢው መሸጎጫ ላይ ደርቦ ይጽፋል)
     │                              │
     └── የጤና ፍተሻ ────────────────►│  GET /federation/health
         (በየ60 ሰከንዱ፣ የጊዜ ገደብ 5 ሰከንድ) │
```

### ማረጋገጫ

የፌዴሬሽን ጥያቄዎች የሚከተሉትን ያካትታሉ፦

```
Authorization: Bearer <raw_token>
X-Federation-Version: 1
```

በርቀት ያለው አገልጋይ ቶከኑን ወደ ሃሽ በመቀየር ተመሳሳዩን የ`community_servers` ረድፍ ይፈልጋል። ይህም የተከማቸውን ሃሽ ከማስተላለፍ ያስወግዳል።

### የጤና ክትትል

እያንዳንዱ የአገልጋይ መዝገብ የሚከተሉትን ይከታተላል፦

| መስክ         | መግለጫ                                   |
| ----------- | -------------------------------------- |
| `status`    | `connected`፣ `degraded`፣ `unreachable` |
| `last_sync` | የመጨረሻው የተሳካ ማመሳሰል ISO የጊዜ ማኅተም         |
| `failures`  | ተከታታይ የጤና ፍተሻ ውድቀቶች                    |

ከ5 ተከታታይ ውድቀቶች በኋላ ሁኔታው ወደ `unreachable` ይቀየራል፣ እናም በእጅ የሚደረግ የጤና ፍተሻ እስኪሳካ ድረስ ማመሳሰሉ ይቆማል።

## ማጭበርበርን መከላከል

**ፋይል፦** `src/lib/gamification/antiCheat.ts`

### በአገልጋይ በኩል የሚደረግ ውጤት ስሌት

ሁሉም የXP ስሌቶች በ`src/lib/gamification/xp.ts` ውስጥ ይከናወናሉ። ደንበኞች ውጤት ፈጽሞ አያስገቡም — እርምጃዎችን ያስገባሉ፣ አገልጋዩም XPን ያሰላል። የ`leaderboard.score` ዓምድ ሊጻፍበት የሚችለው በአገልጋይ-በኩል ባለ ኮድ ብቻ ነው።

### የፍጥነት ገደብ

| ገደብ             | ዋጋ      | ወሰን             |
| --------------- | ------- | --------------- |
| ከፍተኛው XP በደቂቃ   | 1,000   | በእያንዳንዱ API ቁልፍ |
| ከፍተኛው ዝውውር በደቂቃ | 10      | በእያንዳንዱ API ቁልፍ |
| ከፍተኛው የዝውውር መጠን | 10,000  | በእያንዳንዱ ዝውውር    |
| ከፍተኛው የዕለት ዝውውር | 100,000 | በእያንዳንዱ API ቁልፍ |

የፍጥነት ገደቦች በማህደረ ትውስታ ውስጥ ያለ ተንሸራታች መስኮትን (በ`open-sse/services/` ውስጥ ካለው `RateLimitManager` ጋር ተመሳሳይ ንድፍ) ይጠቀማሉ። ሂደቱ እንደገና ከተጀመረ በSQLite የሚደገፉ ቆጣሪዎችን እንደ አማራጭ ይጠቀማል።

### የZ-ውጤት የእንግዳ ሁኔታ ማወቂያ

ለእያንዳንዱ API ቁልፍ፣ ስርዓቱ በሰዓት የተገኘውን XP የያዘ ተንሸራታች የ7-ቀን መስኮት ያቆያል። በእያንዳንዱ የXP ሽልማት፦

1. የተጠቃሚውን የአሁኑ የሰዓት XP መጠን አስላ።
2. የሕዝቡን አማካይ እና መደበኛ ልዩነት አስላ።
3. `z = (user_rate - mean) / stddev`ን አስላ።
4. `z > 3.0` ከሆነ (3 መደበኛ ልዩነቶች)፣ እንደ እንግዳ ሁኔታ ምልክት አድርግበት።

እንግዳ ሁኔታዎች በ`xp_audit_log` ውስጥ ከ`action = 'anomaly_detected'` ጋር ይመዘገባሉ፣ እናም በአስተዳዳሪው ዳሽቦርድ ላይ ይታያሉ።

### የኦዲት መከታተያ

እያንዳንዱ የXP ሽልማት፣ ዝውውር፣ የባጅ ማግኘት እና የእንግዳ ሁኔታ ማወቂያ በ`xp_audit_log` ውስጥ ከሚከተሉት ጋር ይመዘገባል፦

| መስክ          | መግለጫ                                        |
| ------------ | ------------------------------------------- |
| `api_key_id` | ማን                                          |
| `action`     | የተከሰተው ነገር (xp_award፣ transfer፣ anomaly፣ …) |
| `xp_awarded` | መጠን (XP ላልሆኑ ክስተቶች 0)                       |
| `metadata`   | ዐውድ ያለው JSON (የእርምጃ ዓይነት፣ ዒላማ፣ …)           |
| `created_at` | መቼ (ISO 8601)                               |

አስተዳዳሪዎች `GET /api/gamification/anomalies`ን በመጠቀም ሙሉውን የኦዲት መከታተያ መጠየቅ ይችላሉ።

## የAPI መስመሮች

ሁሉም መስመሮች መደበኛውን የOmniRoute ንድፍ ይከተላሉ፦


### የውህደት ነጥብ

የጨዋታ ማበረታቻ በ`open-sse/handlers/chatCore.ts` ውስጥ ካለው የጥያቄ ፓይፕላይን ጋር በአንድ ነጥብ ላይ

```typescript
  emitGamificationEvent({
    type: "request.completed",

      provider: selectedProvider,
      model: selectedModel,

    // አስጀምርና-ርሳ፦ ይመዝግቡ፣ ነገር ግን ወደ ደንበኛው ፈጽሞ አያስተላልፉ
```
