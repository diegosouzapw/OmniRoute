ሪሌዎች (Vercel, Deno, Cloudflare) የupstream ግንኙነቱን serverless backend ላይ ያቋርጣሉ፤ ይህም OmniRoute የprovider API key-ን በserver-side እያቆየ ከተረጋጋ ክልል የወጪ ግንኙነት እንዲፈጽም ያስችለዋል። ይህ ሰነድ ኦፕሬተሮች በproduction የሚያጋጥሟቸውን ሁለት የብልሽት ሁነታዎች እና OmniRoute ለእያንዳንዳቸው የሚያቀርባቸውን የመልሶ ማግኛ መንገዶች ይሸፍናል።

## የሪሌይ ማረጋገጫ እንዴት እንደሚከማች

ከ**Settings → Proxy Pool → Deploy Relay** ሪሌይ ሲያሰማሩ፣ የማሰማራቱ ሂደት የሪሌዩን የማረጋገጫ ቶከን በፕሮክሲው `notes` JSON መስክ ውስጥ ያከማቻል፦

- `STORAGE_ENCRYPTION_KEY` ከተዋቀረ፣ ቶከኑ እንደ `relayAuthEnc`
  (በማከማቻ ላይ በAES የተመሰጠረ) ይጻፋል።
- ካልሆነ እንደ ግልጽ ጽሑፍ `relayAuth` ይጻፋል።

ጥያቄ በሚቀርብበት ጊዜ `extractRelayAuth(notes)` ከሁለቱ ያለውን ቅጽ ይመልሳል፤ ስለዚህ ሪሌዩ ዳግም ከተጀመረም በኋላ መስራቱን ይቀጥላል።

## የብልሽት ሁነታ 1 — ቁልፍ ከተቀየረ በኋላ ዲክሪፕት ሊደረግ የማይችል ቶከን

**ምልክት፦** ቀደም ሲል ይሰሩ የነበሩ ሪሌዎች፣ የ`STORAGE_ENCRYPTION_KEY` environment ወይም secret-manager ቁልፍ ከተቀየረ በኋላ፣ አሁን የupstream `401`/የማረጋገጫ ስህተቶችን ይመልሳሉ። የተከማቸው `relayAuthEnc` blob ከእንግዲህ ዲክሪፕት ሊደረግ አይችልም፤ ስለዚህ `extractRelayAuth` ባዶ ሕብረቁምፊ ይመልሳል እና ሪሌዩ ምንም ማረጋገጫ አይልክም።

**መልሶ ማግኛ — እንደተሰማራ ሳይቀየር ጥገና (ዳግም ማሰማራት አያስፈልግም)፦**

1. **Settings → Proxy Pool** ይክፈቱ።
2. ማረጋገጫቸው የጎደለ የሪሌይ ረድፎች ቢጫ `auth missing` ባጅ እና
   **Repair** አዝራር ያሳያሉ።
3. **Repair** የሚለውን ጠቅ ያድርጉ። OmniRoute
   `POST /api/settings/proxies/[id]/repair-relay` ይጠራል፤ ይህም፦
   - `relayAuthEnc`-ን በ**አሁኑ** ቁልፍ ዲክሪፕት ያደርጋል፣
   - ግልጽ ጽሑፉን `relayAuth` መልሶ ወደ `notes` ይጽፋል፣
   - `{ repaired: true, mode: "recovered" }` ይመልሳል።

ሪሌዩ ምንም የማሰማራት ምስክርነቶችን እንደገና ሳያስገቡ አገልግሎት መስጠቱን ይቀጥላል።

ይህ የሚሰራው አሁን ያለው `STORAGE_ENCRYPTION_KEY` blob-ን አሁንም ዲክሪፕት ማድረግ ከቻለ ብቻ ነው። ቁልፉን ያለምንም ማዛወር **ከቀየሩት**፣ blob-ውን መልሶ ማግኘት አይቻልም።

## የብልሽት ሁነታ 2 — መልሶ ሊገኝ የማይችል ቶከን (ቁልፉ ወደ ሌላ ተቀይሯል)

**ምልክት፦** **Repair** የሚለውን ጠቅ አድርገው
`{ repaired: false, mode: "redeploy", status: 409 }` ተመልሶልዎታል።

**መልሶ ማግኛ — ዳግም ማሰማራት፦**

የተከማቸው ቶከን በአሁኑ ቁልፍ መልሶ ሊገኝ አይችልም። መጀመሪያ ከተጠቀሙበት ተመሳሳይ ሞዳል (**Deploy Relay** ምናሌ → Vercel / Deno / Cloudflare) ሪሌዩን ዳግም ያሰማሩ። የማሰማራቱ ሂደት አዲስ ቶከን (በአሁኑ ቁልፍ የተመሰጠረ) ይጽፋል እና በረድፉ ላይ ያለው `auth missing` ባጅ ይጠፋል።

በUI ውስጥ ቶከኑ መልሶ ሊገኝ በማይችልበት ጊዜ **Repair** አዝራሩ ራሱ የዳግም ማሰማራት ሞዳሉን ያስጀምራል፤ ስለዚህ በእጅ መፈለግ አያስፈልግዎትም።

## የብልሽት ሁነታ 3 — ሪሌዩ ተደራሽ ነው ነገር ግን ጤናማ አይደለም

**ምልክት፦** የፕሮክሲ ሙከራው (`speed` አዝራር) ሪሌዩ እየሰራ መሆኑን ያሳያል፣ ነገር ግን ጥያቄዎች አሁንም አልፎ አልፎ አይሳኩም።

በOmniRoute ራስ-ሰር የሙከራ probe የሚመለሱትን የሪሌይ ግንዛቤ ራስጌዎች ያረጋግጡ
(**Settings → Proxy Pool** እና `relayTested` / `relayAlive` ቆጣሪዎችን ይመልከቱ)፦

- `x-relay-url` — የትኛው የሪሌይ backend እንደመለሰ።
- `x-relay-mode` — ለዚያ ጥያቄ `ts` | `bifrost` | `auto`።
- `x-relay-attempts` — ከመሳካቱ በፊት ስንት የሪሌይ ዝላይዎች እንደተሞከሩ።
- `x-relay-fallback` — ጥያቄው ከተመረጠው
  backend ወደ TypeScript ሪሌይ ተመልሶ ሲያገለግል `true`።

ከዝቅተኛ `relayAlive` ጋር ከፍተኛ የ`x-relay-fallback` መጠን ካለ፣ sidecar
backend-ው ጤናማ አይደለም ማለት ነው፤ ስለዚህ ሊጠግኑት ወይም የሪሌይ backend
ስትራቴጂውን ወደ `ts` ሊቀይሩት ይገባል (`RELAY_BACKEND_STRATEGY.md` ይመልከቱ)።

## የAPI ማጣቀሻ

| ዘዴ     | ዱካ                                        | ይዘት                     | ስኬት                                                                                                              | ብልሽት                                                                        |
| ------ | ----------------------------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | እንደገና ሲመነጭ `200 { repaired: true, mode: "recovered" }`፤ ግልጽ ጽሑፍ አስቀድሞ ካለ `200 { repaired: false, mode: "noop" }` | መልሶ ሊገኝ የማይችል `409 { mode: "redeploy" }`፤ የሪሌይ ዓይነት ካልሆነ `400`፤ ካልተገኘ `404` |

የዝርዝር መንገዱ `GET /api/settings/proxies` ዳሽቦርዱ ቶከኑን በፍጹም ሳያጋልጥ የጥገና አማራጩን ማሳየት እንዲችል፣ ምስጢር-አልባ የሆነ `relayInfo: { isRelay, authMissing, repairMode }` ከእያንዳንዱ ንጥል ጋር ያያይዛል።
