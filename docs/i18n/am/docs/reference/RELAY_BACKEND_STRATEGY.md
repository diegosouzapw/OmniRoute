## ማጠቃለያ

OmniRoute አሁን ለ`/api/v1/relay/chat/completions` ሦስት የrelay ሁነታዎችን ይደግፋል፦

- `ts`፦ የTypeScript relayን በሂደቱ ውስጥ ይጠቀሙ።
- `bifrost`፦ የBifrost gatewayን በግድ ይጠቀሙ።
- `auto`፦ Bifrost ሲገኝ ቅድሚያ ይስጡት፤ ሲከሽፍ ወደ TypeScript ይመለሱ።

ከፍተኛ የጥያቄ መጠን (በቀን ብዙ tokens፣ ያለማቋረጥ የሚቀጥል የሥራ ፍሰት) ሲኖር፣ ዋናው የሥራ መንገድ ምላሽ በማይሰጥ sidecar ምክንያት ፈጽሞ እንዳይታገድ የመመለሻ መንገዱን ግልጽና ፈጣን ማድረግ ከሁሉ የተሻለው ስልት ነው።

## የሁነታዎች ባህሪ

- `ts`
  - ዝቅተኛው የክንውን ውስብስብነት።
  - ሁሉም routing እና validation በNode ውስጥ ይከናወናሉ።
  - ለተገኝነት በsidecar ላይ ጥገኝነት የለም።
- `bifrost`
  - ሁሉም ጥያቄዎች በsidecar gateway በኩል እንዲያልፉ ያስገድዱ።
  - ራስ-ሰር የመመለሻ መንገድ የለም።
  - የsidecar ጤና እና መዘግየት ዋስትና ሲኖራቸው ብቻ ጠቃሚ ነው።
- `auto`
  - Sidecar ሊደረስበት ሲቻል እና የነቃ ሲሆን ጥቅም ላይ ይውላል።
  - ያልተሳኩ ሙከራዎች የመመለሻ headersን ያስነሳሉ፣ እና የጥያቄው ስኬት በተወሰነ ገደብ ውስጥ እንዲቆይ የትራፊክ ፍሰቱን ወደ TS ይመልሳሉ።
  - ያለመቋረጥ መሥራት በsidecar ብቻ ላይ ከተመሠረተ ጥብቅ routing ይልቅ ይበልጥ አስፈላጊ ሲሆን፣ ይህ ሁነታ ለproduction ከሁሉ የተሻለው ምርጫ ነው።

## 9router ከ CLIPROXYAPI ጋር ዛሬ

9router እና CLIPROXYAPI ሁለቱም በታሪክ ለupstream providers የተኳኋኝነት መንገዶችን ያቀረቡ integrations ናቸው።

- 9router ለupstream orchestration እና ለተኳኋኝነት ባህሪ የተካተተ መንገድ ነው።
- CLIPROXYAPI ለCLI / SDK ቅርጽ ያለው ትራፊክ የproxy API ድልድይ ነው።
- የተወሰነ sidecar-መሰል መሸጋገሪያ እና ዝቅተኛ መዘግየት ያለው አካባቢያዊ dispatch ሲያስፈልግዎት፣ Bifrost እንደ ውጫዊ መንገድ እየተረጋጋ ነው።

በአሁኑ ጊዜ 9router/CLIPROXYAPIን እያወዳደሩ ከሆነ፦

- የጥያቄ ፊርማ፣ የallowlist ማረጋገጫዎች እና የDB ፖሊሲ መቆጣጠሪያዎችን ከማስረከብዎ በፊት በAPI route ውስጥ ያስቀምጡ።
- የሥራ ፍሰት ጥብቅ የsidecar ባህሪ እና በእያንዳንዱ ጥያቄ ላይ ያነሰ ልዩነት ካስፈለገው፣ `OMNIROUTE_RELAY_BACKEND=bifrost`ን ይጠቀሙ።
- በክስተት ሁኔታዎች ውስጥ አገልግሎቱ ቀስ በቀስ እየቀነሰ እንዲቀጥል ከsidecar ጽናት ጋር ካስፈለገዎት፣ `OMNIROUTE_RELAY_BACKEND=auto`ን ይጠቀሙ።

## የbackend ድንበር ውል

የተረጋጋው የምርት ድንበር የdashboard አተገባበር ሳይሆን የOmniRoute relay API ነው። የNext.js dashboard አካባቢያዊ አገልግሎቶችን ሊጭን፣ ሊያዋቅር እና ሊቆጣጠር ይችላል፤ ነገር ግን request routing በrelay API በኩል ገብቶ ከዚያ ድንበር በስተጀርባ መተላለፍ አለበት።

የረጅም ጊዜ የbackend ምርጫዎች፦

- የTypeScript relayን በሂደቱ ውስጥ እንደ policy እና መመለሻ መንገድ ያቆዩ። Auth፣ allowlists፣ request normalization፣ accounting እና safety checks ማንኛውም የbackend ማስረከብ ከመከናወኑ በፊት እዚህ ይቆያሉ።
- Deploymentው ያነሰ የrouting ልዩነት፣ ማዕከላዊ የprovider rotation ወይም በብዙ OmniRoute replicas ላይ scale-out ሲፈልግ፣ Bifrostን እንደ ተመራጭ ከፍተኛ-throughput Tier-1 sidecar ይጠቀሙ።
- 9router እና CLIPROXYAPIን እንደ የተካተቱ የተኳኋኝነት አገልግሎቶች ያቆዩ። እንደሚቆጣጠሩ አካባቢያዊ processes ሆነው ይሠራሉ፣ እና የእነሱ provider/CLI ባህሪ የሚፈለገው adapter ሲሆን ጠቃሚ ናቸው፤ ሆኖም ነባሪው Tier-1 routing engine መሆን የለባቸውም።
- Dashboardው የዘፈቀደ service URLsን ወደ ዋናው የሥራ መንገድ እንዲያስተላልፍ አያድርጉ። በUI የሚቀርቡ URLs የconfiguration inputs ናቸው፤ routing code የተመዘገቡና ጤናቸው የተረጋገጠ backendsን ከserver-side settings እና supervisor state መፍታት አለበት።
- የሚተዳደሩ processes አስቀድመው HTTP-compatible APIsን ስለሚያቀርቡ፣ route guard ድንበሩን audit ማድረግ ስለሚችል፣ እና የfailure/fallback ባህሪ በrequest logs ውስጥ ስለሚታይ፣ በአሁኑ ጊዜ ለሚቆጣጠሩ አገልግሎቶች loopback HTTPን ይምረጡ። ወደፊት SDK ወይም socket transport መጨመር ጠቃሚ የሚሆነው isolation ወይም fallback semanticsን ሳያዳክም p99 routing latencyን በሚለካ መጠን ከቀነሰ ብቻ ነው።

ስለዚህ፣ በጣም ከፍተኛ throughput ላለው deployment ነባሪው መልስ Bifrost የነቃበት `auto` ነው፦ ለስኬት መጠን የTypeScript መመለሻ መንገዱን እያስጠበቁ የGo sidecarን በዋናው የሥራ መንገድ ላይ ይጠቀሙ። ከአገልግሎቱ ቀስ በቀስ መቀነስ ይልቅ በsidecar ብቻ ላይ የተመሠረተ ጥብቅ ባህሪ ይበልጥ አስፈላጊ ሲሆን ብቻ `bifrost`ን ይጠቀሙ።

## ለከፍተኛ throughput መመሪያ

ለቀጣይነት ያለው ከፍተኛ RPM/RPS እና ጥብቅ የስኬት SLO፦

1. `auto`ን ከተግባራዊ cooldown እና failure telemetry ጋር ይጠቀሙ።
2. Upstream validation እና API-key checksን በTypeScript route ድንበር ላይ ያቆዩ።
3. የማስጠንቀቂያ ሥርዓትዎ የመመለሻ ድግግሞሽን እና ምክንያቶችን እንዲያይ explicit headers/countersን ያንቁ።
4. ለዘላለም ከመጠበቅ ይልቅ በፍጥነት እንዲከሽፉ የsidecar timeoutsን ያስተካክሉ።
5. መመለሻው በእውነት ልዩ ሁኔታ ሆኖ እንዲቆይ፣ የservice auto-restart እና health telemetry loopን ጤናማ አድርገው ያቆዩ።

## የሚመከር መነሻ ውቅር

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- API keys፣ allowlist፣ sanitizer እና rate-limit checksን በroute handlers ውስጥ እንደነቁ ያቆዩ (እነዚህ ወደ downstream ከመላኩ በፊት ሁልጊዜ ይከናወናሉ)።
- የsidecar መቋረጦች በአንድ ደቂቃ ውስጥ እንዲታዩ፣ fallback metricsን ከreverse proxy እና request logs ወደ ውጭ ይላኩ።

## የprovider plugin ውል
