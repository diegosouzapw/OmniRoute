`open-sse/config/providerPluginManifest.ts` ለJSON ተስማሚ የሆነውን የአቅራቢ plugin ውል ይገልጻል። `open-sse/config/providerPluginManifestRegistry.ts` ደግሞ ያንን ውል እንደ Bifrost፣ CLIProxyAPI ወይም ወደፊት ሊኖር የሚችል Go/Rust router ላሉ sidecar-ዎች ከአሁኑ የአቅራቢ registry ጋር ያስተሳስራል። የTypeScript registry የእውነት ምንጭ ሆኖ ይቀጥላል፣ ነገር ግን sidecar-ዎች executor code፣ OAuth defaults፣ headers ወይም የprocess environment state ሳያስገቡ manifest-ን መጠቀም ይችላሉ።

ተመሳሳዩ manifest ከprocess ውጭ ለሚሰሩ sidecar-ዎች በHTTP
`GET /api/v1/provider-plugin-manifest` ላይም ይገኛል።

OmniRoute ያንን URL በ`X-OmniRoute-Provider-Manifest-Url` የጥያቄ header በኩል ለBifrost እና CLIProxyAPI ያሳውቃል። sidecar-ው ከአካባቢያዊው የጥያቄ origin ይልቅ public ወይም container network URL ሲያስፈልገው `OMNIROUTE_PROVIDER_MANIFEST_URL`ን ያዘጋጁ።

## Manifest-ን ማደስ

የHTTP endpoint-ው `Cache-Control: public, max-age=60` እና ጠንካራ
`ETag` ይመልሳል። sidecar ለመጨረሻ ጊዜ የተረጋገጠውን manifest ማቆየት እና ሲያድስ ETag-ውን በ`If-None-Match` ውስጥ መላክ አለበት። የ`304 Not Modified` ምላሽ body የለውም፤ sidecar-ው በcache የተቀመጠውን manifest ይይዛል። የተረጋገጠ በcache የተቀመጠ manifest ከሌለ፣ sidecar-ው `304`ን ከመቀበል ይልቅ ያለምንም ቅድመ ሁኔታ ጥያቄ ማቅረብ አለበት።

## ግብ

የአቅራቢ metadata-ን ወደ plugin ውል ማሸጋገር፣ ይህም ወደፊት hot request path-ው ዝቅተኛ latency ባለው sidecar እንዲያዝ ሲያስችል OmniRoute የTypeScript route-ን እንደ policy gate እና fallback እንዲያቆይ ነው። manifest-ው ተጨማሪ ነው፤ በራሱ የጥያቄ routing-ን አይለውጥም።

## ውል

manifest-ው የሚከተሉትን ይይዛል፦

- የአቅራቢ id እና alias
- upstream format እና executor name
- auth type፣ auth header እና አማራጭ auth prefix
- static endpoint metadata
- ለsidecar ብቁነት እና አቅራቢው በTS ላይ መቆየት ሲገባው ግልጽ ምክንያቶች
- እንደ context length፣ vision/reasoning flags እና unsupported params ያሉ ለJSON ተስማሚ model metadata
- `apikey`፣ `oauth`፣ `custom-executor`፣
  `passthrough-models`፣ `responses`፣ `sidecar-candidate`፣ `usage-fetch` እና `usage-supported`ን ጨምሮ capability tags

manifest-ው ሆን ብሎ የሚከተሉትን አያካትትም፦

- የOAuth client secrets እና default secret values
- runtime environment resolution
- request headers እና public credential helpers
- dynamic URL builders
- executor functions
- የsession pool ውስጣዊ ዝርዝሮች

## Capability Tags

`capabilities` ከregistry entry-ው የተገኘ የተደረደረ የtag-ዎች array ነው። Integrator-ዎች የTypeScript ምንጮችን እንደገና ከማንበብ ይልቅ፣ “ይህ አቅራቢ ምን ማድረግ ይችላል” ለሚለው በማሽን የሚነበብ መልስ አድርገው ሊወስዱት ይገባል።

| Tag                  | ትርጉም                                                                |
| -------------------- | ------------------------------------------------------------------- |
| `apikey`             | API key ይቀበላል (`authType` `apikey` ወይም `optional` ነው)።              |
| `oauth`              | OAuth ወይም session flow ይጠቀማል።                                       |
| `responses`          | የOpenAI Responses-API base URL ያቀርባል።                               |
| `passthrough-models` | ከstatic catalog ይልቅ model-ዎችን በቀጥታ ከupstream ያቀርባል።                 |
| `custom-executor`    | default ያልሆነ executor ያስኬዳል፣ ስለዚህ በTypeScript path ላይ ይቆያል።         |
| `sidecar-candidate`  | `sidecar.eligible`ን ያንጸባርቃል — ለsidecar import መገምገም ደህንነቱ የተጠበቀ ነው። |
| `usage-fetch`        | የተገናኘ usage ወይም quota fetcher (`getUsageForProvider`) አለው።          |
| `usage-supported`    | usage API-ው ይህን አቅራቢ ይቀበላል (`isSupportedUsageConnection`)።          |

`usage-fetch` ለማግኘት ብቻ ነው። OmniRoute ለአቅራቢው usage-ን እንዴት ማንበብ እንደሚችል እንደሚያውቅ ይገልጻል፤ fetching-ን አያነቃም፣ የquota semantics-ን አይለውጥም፣ ወይም የDashboard quota widget ለአቅራቢው እንደነቃ አያመለክትም — ያ widget በተናጠል በ`USAGE_SUPPORTED_PROVIDERS` ይገደባል። የእውነት ምንጩ በ`open-sse/services/usage/fetcherProviders.ts` ውስጥ ያለው `USAGE_FETCHER_PROVIDERS` ነው።

ያ ዝርዝር usage dispatcher-ው በሚቀበላቸው string-ዎች የተመደበ ስለሆነ canonical idsን ከaliases ጋር ያቀላቅላል፣ እና ከtag ከተደረጉ አቅራቢዎች ቁጥር በጥቂቱ ይረዝማል፦ በmanifest registry ውስጥ chat provider ያልሆኑ entries (ለምሳሌ `firecrawl` search provider እና `amazon-q` ACP provider) tag የሚደረግበት manifest entry የላቸውም።

`usage-supported` server-ው እና የDashboard usage routes ለአቅራቢው connection ይቀበሉ እንደሆነ ይመልሳል። ሁለቱም በ`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`) የተገደቡትን `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`) እና `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`) ያንጸባርቃል። ከ`usage-fetch` በተለየ ሁኔታ፣ በአቅራቢ id ላይ ብቻ ይወጣል — runtime guard-ው ያለ alias resolution `USAGE_SUPPORTED_PROVIDERS.includes(providerId)`ን ያከናውናል፣ ስለዚህ manifest-ው ተመሳሳዩን ደንብ ይጠብቃል። ሁለቱ tag-ዎች የተለያዩ ወሰኖች አሏቸው፦ 3 አቅራቢዎች `usage-fetch`ን ብቻ (`opencode`፣ `opencode-zen`፣ `xai`) እና 1 አቅራቢ `usage-supported`ን ብቻ (`xiaomi-mimo-token-plan`) ይይዛሉ፣ ስለዚህ አንዱ ሌላውን አያመለክትም።

## Sidecar አጠቃቀም

Sidecar-ዎች `sidecar.eligible`ን እንደ ያለገደብ የማዞሪያ ውሳኔ ሳይሆን፣ ጥንቃቄ የተደረገበት የዕጩነት ምልክት አድርገው ሊመለከቱት ይገባል። የመጀመሪያው የማስመጣት ዒላማ ነባሪውን አስፈጻሚ የሚጠቀሙ
API-key፣ static-endpoint አቅራቢዎች መሆን አለባቸው። ብጁ web executors፣ OAuth/session ፍሰቶች፣ ተለዋዋጭ URL builders ወይም pool config ያላቸው አቅራቢዎች፣ sidecar ተመጣጣኝ ባህሪን እስኪተገብር እና telemetry እኩልነትን እስኪያረጋግጥ ድረስ በTypeScript fallback መንገድ ላይ ይቆያሉ።

የተጠቆሙ የሽግግር ደረጃዎች፦

1. የአቅራቢ plugin manifestን ከTS registry ያመንጩ እና ያረጋግጡ።
2. Bifrost ወይም CLIProxyAPI API-key/static አቅራቢዎችን ለመጠቀም manifestን እንዲያስመጣ ያድርጉ።
3. TS fallbackን እንደነቃ በማቆየት፣ ብቁ አቅራቢዎችን ከ`OMNIROUTE_RELAY_BACKEND` በስተጀርባ ባለው sidecar በኩል ያዙሩ።
4. የስኬት መጠን፣ p99 latency፣ streaming ባህሪ እና unsupported-param አያያዝ ከTS መንገድ ጋር ሲዛመዱ ብቻ አቅራቢዎችን ወደ ሙሉ አገልግሎት ያሳድጉ።
5. ለብጁ executors ቤተሰብ በቤተሰብ sidecar-native plugins ያክሉ።
