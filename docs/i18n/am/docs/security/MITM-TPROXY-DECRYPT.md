TPROXY ግልጽ ዲክሪፕት ለ
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM ስታክ የOmniRoute **5ኛው የቀረጻ ሁነታ** ነው። በLinux ላይ የአካባቢ ወጪ HTTPS ትራፊክን
kernel TPROXY + policy routing በመጠቀም — `/etc/hosts`ን **ሳያስመስል** እና
የመላ OS የስርዓት-proxy ቅንብሮችን **ሳይቀይር** ይጠልፍና **ዲክሪፕት** ያደርጋል። ለheadless አጠቃቀም ምቹ ነው
(ለማጽዳት የDNS ለውጦች የሉም)፣ እንዲሁም የfirewall ደንቦቹ ሲስተሙ እንደገና ሲነሳ በራስ-ሰር ይወገዳሉ።

ከሌሎቹ የቀረጻ ሁነታዎች በተለየ፣ TPROXY ለእያንዳንዱ host የተለየ ዝግጅት አያስፈልገውም፤
በታለመ ወደብ ላይ ያሉ **ማናቸውንም** መድረሻ hosts በግልጽነት ይጠልፋል፣ ለእያንዳንዱ SNI hostname
በቅጽበት በሚያወጣው leaf certificate TLSን ያቋርጣል፣ ዲክሪፕት የተደረገውን
ልውውጥ ይቀርጻል፣ እና ጥያቄውን ወደ መጀመሪያው መድረሻ እንደገና ኢንክሪፕት አድርጎ ይልካል።

> **ለLinux ብቻ፣ ለroot ብቻ፣ በፈቃድ የሚነቃ።** ይህ ሁነታ Linuxን፣ በC toolchain
> የተገነባ native addonን፣ እና የ**CAP_NET_ADMIN** ችሎታን (በተለምዶ root) ይፈልጋል። መዳረሻው
> loopback-only በሆነው AgentBridge API የተገደበ ሲሆን በነባሪነት ተሰናክሏል። ማንኛውንም host
> መፈረም የሚችል የታመነ MITM CA ኃይለኛ ችሎታ ነው — [§6 ደህንነት](#6-security)ን ይመልከቱ።

## §1 ምንድን ነው እና መቼ መጠቀም ይገባል

ሌሎቹ አራት የቀረጻ ሁነታዎች እያንዳንዳቸው አንድ ገደብ አላቸው፦

| ሁነታ            | ትራፊክ የሚመራበት መንገድ                         | ገደብ                                     |
| -------------- | ---------------------------------------- | --------------------------------------- |
| AgentBridge    | ለተወሰነ የhost ስብስብ የ`/etc/hosts` DNS ማስመሰል | የተመዘገቡት IDE-agent hosts ብቻ              |
| ብጁ Hosts       | ለእያንዳንዱ host የ`/etc/hosts` DNS ማስመሰል     | ለእያንዳንዱ host አንድ ግቤት፤ hostsን ለማርትዕ sudo |
| HTTP_PROXY     | `HTTP_PROXY`/`HTTPS_PROXY` env           | env varን የሚያከብሩ apps ብቻ                 |
| የመላ ስርዓት proxy | የOS proxy ቅንብሮች                          | ዓለም አቀፍ ሁኔታን ይቀይራል፤ መመለስ ያስፈልገዋል        |

በምትኩ TPROXY ግልጽ ዲክሪፕት ትራፊክን በ**kernel** ንብርብር ላይ ይመራል። በ
`mangle OUTPUT` chain ውስጥ ወደ ታለመ ወደብ (ነባሪ `443`) የሚሄዱ አዲስ የአካባቢ ወጪ TCP ግንኙነቶችን
ምልክት ያደርጋል፣ አንድ `ip rule` ምልክት የተደረገባቸውን packets ወደ አካባቢያዊ መድረሻ እንዲደርሱ እንደገና ይመራቸዋል፣
እና እንደገና ሲገቡ `mangle PREROUTING` `TPROXY` target ለ
**IP_TRANSPARENT** listener ያስረክባቸዋል — እሱም TLSን አቋርጦ plaintextን ይቀርጻል።

ከሚከተሉት ባህሪያት ያለውን process ትራፊክ ለመቅረጽና ዲክሪፕት ለማድረግ ሲፈልጉ ይጠቀሙበት፦

- AgentBridge ከማይመዘግበው host ጋር የሚገናኝ፣ እና
- `HTTP_PROXY`ን የማያከብር፣ እና
- በመላ ስርዓቱ የproxy ለውጥ ማወክ የማይፈልጉት።

መጥለፉ በkernel ውስጥ ስለሚከናወን፣ ግንኙነቱን የጀመረው process **ምንም
የውቅረት ለውጥ** አያስፈልገውም — ነገር ግን processው OmniRoute የሚጭነውን dynamic CA
ማመን አለበት ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)ን ይመልከቱ)።

## §2 መስፈርቶች

| መስፈርት               | ዝርዝር                                                                                                                                          |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**              | Linux ብቻ — **IP_TRANSPARENT** በLinux ላይ ብቻ የሚገኝ የsocket አማራጭ ነው። loader በሌሎች መድረኮች ሁሉ "አይገኝም" ብሎ ይመልሳል።                                       |
| **ልዩ ፈቃድ**          | ግልጽ socket ለመፍጠር እና የ`iptables`/`ip` ደንቦችን ለመተግበር የ**CAP_NET_ADMIN** ችሎታ ያስፈልጋል — በተግባር እንደ root ያሂዱት።                                        |
| **Native addon**    | አነስተኛ N-API addon (`src/mitm/tproxy/native/transparent.c`) መገንባት ወይም እንደ prebuild መቅረብ አለበት። [§3](#3-the-native-ip_transparent-addon)ን ይመልከቱ። |
| **የKernel modules** | የ`TPROXY`፣ `mangle` እና `mark` ማዛመጃ ድጋፍ ያለው `iptables` (ከkernel 6.8.0 ጋር ተረጋግጧል)።                                                              |

**ለስላሳ የችሎታ መቀነስ፦** ማንኛውም መስፈርት ከጎደለ (Linux ካልሆነ፣ toolchain
ከሌለ፣ addon ካልተገነባ)፣ addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
ስህተት ከመወርወር ይልቅ `null` ይመልሳል። ከዚያም የcapture-mode ሁኔታ
`available: false` ብሎ ያሳያል፣ የdashboard toggle ደግሞ
"TPROXY decrypt Linux + root + native addon ያስፈልገዋል" በሚለው tooltip
**ይሰናከላል**፣ የቀረው OmniRoute ግን መስራቱን ይቀጥላል።

## §3 Native IP_TRANSPARENT addon

የNode `net` module ከ`bind()` _በፊት_ `setsockopt(IP_TRANSPARENT)`ን ማስኬድ አይችልም፤
TPROXY ግን ይህን ይፈልጋል (አለበለዚያ kernel አቅጣጫቸው የተቀየረውን packets ያስወግዳል)። addon
(`src/mitm/tproxy/native/transparent.c`፣ በ`binding.gyp` የሚገነባ) ሦስት functionsን
የሚያቀርብ አነስተኛ N-API module ሲሆን፣ እነዚህም በ`transparentSocket.ts` በኩል ጥቅም ላይ ይውላሉ፦

| የAddon function                       | የSocket ሥራ                                                                                | ጥቅም ላይ የሚውልበት                                                        |
| ------------------------------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`፣ raw fdን ይመልሳል | ለግልጽ capture listener (Node fdውን በ`server.listen({ fd })` በኩል ይቀበላል) |
| `setSocketMark(fd, mark)`             | በነባር fd ላይ `setsockopt` **SO_MARK**                                                       | anti-loop (የproxyውን የራሱን sockets ምልክት ማድረግ)                          |
| `connectMarked(ip, port, mark)`       | ከnon-blocking `connect()` **በፊት** `socket()` + **SO_MARK**፣ fdን ይመልሳል                     | እንደገና የተመሰጠረው upstream forward (SYN ምልክቱን ይይዛል)                      |

የመጀመሪያው መድረሻ ከ`socket.localAddress`/`localPort` ይነበባል — TPROXY
እሱን እንዳለ ይጠብቃል፣ ስለዚህ **SO_ORIGINAL_DST**/NAT lookup አያስፈልግም።

### Addonን መገንባት

```bash
npm run build:native:tproxy      # ወደ src/mitm/tproxy/native ይግቡ እና node-gyp rebuildን ያሂዱ
                                 # -> native/build/Release/transparent.node
```

- `npm run build` በሚካሄድበት ጊዜ፣ `scripts/build/build-tproxy-native.mjs` `node-gyp

## §4 በየ-SNI የሚለዋወጥ CA እና የtrust-store ጫኝ

> **#6684 ዝማኔ፦** የAgentBridge የማይለዋወጥ አገልጋይ (`src/mitm/server.cjs`) አሁን
> አንድ የማይለዋወጥ በራሱ የተፈረመ leaf ከመጠቀም ይልቅ ይህንኑ የCA/leaf አርክቴክቸር
> ንድፍ ይጋራል። **የተለየ** የCA ኢንስታንስ
> (`src/mitm/cert/rootCa.ts`፣ በ`<DATA_DIR>/mitm/ca.key`/`ca.crt` የሚቀመጥ)
> ይጠቀማል፤ እንዲሁም ቀድሞ በነበረው `omniroute-mitm.crt` የtrust-store ቦታ ስር
> ይጫናል (እዚያ የነበረውን ነጠላ leaf በመተካት — የሁለት-እምነት ማጽዳት አያስፈልግም)፤
> ከዚህ በታች ካለው የTPROXY የራሱ `omniroute-tproxy-ca.crt` ቦታ ሙሉ በሙሉ
> ተለይቶ ይቆያል። አዲስ የAgentBridge ጭነቶች የCA ሞዴሉን በራስ-ሰር
> ያገኛሉ፤ አሮጌውን የማይለዋወጥ leaf አስቀድሞ የሚያምን ጭነት ኦፕሬተሩ
> በ`MITM_ROOT_CA_ENABLED=true` በኩል ለመጠቀም እስኪመርጥ ድረስ እሱን
> መጠቀሙን ይቀጥላል (`src/mitm/cert/migration.ts`ን ይመልከቱ) — ለ**ማንኛውም**
> አስተናጋጅ leaf መፈረም የሚችል የታመነ MITM CA ከቀድሞው ቋሚ-SAN leaf
> በእጅጉ የበለጠ ኃይል አለው፤ ስለዚህ አስቀድሞ እምነት በተሰጠው ጭነት ላይ
> ሽግግሩ ፈጽሞ በድብቅ አይከናወንም።

በታሪክ፣ የAgentBridge የማይለዋወጥ MITM cert ይሠራ የነበረው AgentBridge
**ቋሚ** የአስተናጋጅ ስብስብን በDNS ስለሚያጭበረብር ብቻ ነበር (አሁን ከታች ካለው
ሞዴል ጋር ተዋህዷል)። TPROXY **የዘፈቀደ** አስተናጋጆችን ስለሚያቋርጥ፣
listener ደንበኛው ለሚጠይቀው ማንኛውም SNI ትክክለኛ leaf ማቅረብ አለበት —
AgentBridgeም ከ4ቱ antigravity አስተናጋጆች ብቻ ይልቅ ለሙሉው
`MITM_TOOL_HOSTS` ስብስብ (9 የመሣሪያ ግቤቶች) አሁን ያለበት ተመሳሳይ መስፈርት ነው።

### ተለዋዋጭ CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` በአካባቢው ያለ CA (`selfsigned` dependency ላይ የተገነባ) ያስኬዳል፤ ይህም፦

- በ`generateMitmCa()` አማካኝነት ረጅም ጊዜ የሚቆይ CA ያመነጫል (CN `"OmniRoute MITM CA"`፣
  የ10 ዓመት የሚሠራበት ጊዜ፣ `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`፣
  2048-bit RSA / SHA-256)።
- በ`issueLeafCert()` አማካኝነት **ለእያንዳንዱ የSNI አስተናጋጅ ስም በተጠየቀ ጊዜ leaf**
  ያወጣል (የ1 ዓመት የሚሠራበት ጊዜ፣ `subjectAltName` = የSNI አስተናጋጅ)፣ እንዲሁም
  ለእያንዳንዱ የአስተናጋጅ ስም አንድ `tls.SecureContext` በcache ያስቀምጣል።
- ለTLS-terminating አገልጋይ `createSNICallback()`ን ያቀርባል ([§5](#5-how-decrypt-and-capture-work)ን ይመልከቱ)።
- CAው ከዳግም ማስጀመሮች በኋላም የማይለወጥ እንዲሆን `existingCa`ን በመጠቀም
  ሊፈጠር ይችላል (በዚህም trust storeን እንደገና መጫን አያስፈልግም)።

የCA የግል ቁልፍ **ፈጽሞ ከማሽኑ አይወጣም**።

### የTrust-store ጫኝ (`src/mitm/tproxy/caTrust.ts`)

የተቋረጠው ደንበኛ ተለዋዋጩን CA ማመን አለበት፤ ስለዚህ capture modeን
ማስጀመር CA certን በOS trust store ውስጥ በ**ራሱን የቻለ ቦታ** —
`omniroute-tproxy-ca.crt` (constant `TPROXY_CA_CERT_NAME`) — ስር ይጭነዋል፤
ሁለቱ ፈጽሞ እንዳይደራረቡ ይህ ከማይለዋወጠው MITM cert ቦታ
(`omniroute-mitm.crt`) ተለይቶ ይቀመጣል።

`installTproxyCa(caPem, sudoPassword?)` የdistroውን anchor directory
ይለያል (በቅደም ተከተል፦ በመጀመሪያ Debian-style)፣ ከዚያም ተጓዳኙን
የማደሻ command ያስኬዳል፦

| Anchor directory                            | የማደሻ command             |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

ጭነቱ PEMን ወደ temp file ያዘጋጃል፤ ከዚያም (በልዩ ፈቃድ) anchor
dirን በ`mkdir -p` ይፈጥራል፣ የተዘጋጀውን file በ`cp` ወደዚያ ይቀዳል፣
ከዚያም የማደሻ commandን ያስኬዳል። `uninstallTproxyCa()` የራሱን ቦታ ብቻ
ያስወግዳል (የማይለዋወጠውን MITM cert ሳይነካ) እና ያድሳል — Linux ባልሆኑ
ስርዓቶች ላይ ምንም አያደርግም።

ሁሉም ልዩ ፈቃድ የሚጠይቁ commands በ`execFileWithPassword`
(`src/mitm/systemCommands.ts`) በኩል ይሰራሉ — `spawn` ከ**arg arrays ጋር፣
ያለ shell፣ ያለ string interpolation** (Hard Rule #13)። ሂደቱ root ሆኖ
ሲሠራ (ለምሳሌ VPS ላይ) targetው በቀጥታ ይሠራል እና password አያስፈልግም፤
root ባልሆነ desktop ላይ `sudoPassword` በstdin በኩል ለ`sudo -S` ይተላለፋል።

> የdesktop `sudoPassword` የtrust-store ጭነቱን ለመፍቀድ በPOST body
> ውስጥ ይቀርባል፤ ሂደቱ root ሲሆን ሙሉ በሙሉ ችላ ይባላል።

## §5 ዲክሪፕት ማድረግና መያዝ እንዴት እንደሚሠሩ

ፓይፕላይኑ (ሁሉም በ`src/mitm/tproxy/` ስር):

```
የአካባቢ መተግበሪያ  ──TCP/443──▶  mangle OUTPUT ግንኙነቱን ምልክት ያደርጋል (fwmark)
                          ip rule → የአካባቢ ራውቲንግ ሰንጠረዥ → lo
                          mangle PREROUTING TPROXY → IP_TRANSPARENT አዳማጭ (ፖርት 8443)
                              │  captureMode.ts: የመጀመሪያውን መድረሻ ከsocket.localAddress ያነባል
                              ▼
                          tlsCapture.ts:
                            1. በእያንዳንዱ SNI የleaf ሰርተፊኬት (dynamicCert) CLIENTን TLS-terminate ያደርጋል
                            2. ውስጣዊው http.Server ዲክሪፕት የተደረገውን plaintext ይተነትናል
                            3. መያዝ → globalTrafficBuffer.push() ከsource: "tproxy" ጋር
                               (sanitizeHeaders + maskSecret ተተግብሯል)
                            4. እንደገና ኢንክሪፕት ተደርጎ ወደ መጀመሪያው መድረሻ ይተላለፋል
                               በbypass ምልክት በተደረገ socket በኩል (connectMarked, የloop መከላከያ)
                              │
                              ▼
                          የመጀመሪያው upstream (api.example.com)
```

- **TLS ማቋረጥ** (`createTlsCaptureServer`): የdynamic CAን SNI callback በመጠቀም በserver-side `tls.TLSSocket` ውስጥ በቀጥታ የተያዘውን socket ይጠቀልለዋል፤ ከዚያም ዲክሪፕት የተደረገውን stream ለውስጣዊ `http.Server` ያስተላልፋል (መደበኛው የMITM ማቋረጫ ዘዴ)። የsocket የሕይወት ጊዜዎች በ`MITM_IDLE_TIMEOUT_MS` የተገደቡ ስለሆኑ፣ የተንጠለጠለ tunnel የfile descriptor ሀብቶችን ማሟጠጥ አይችልም።
- **መያዝ** (`handleDecryptedRequest`): `source: "tproxy"`፣ በ`"in-flight"` የሚጀምር status፣ በ`sanitizeHeaders()` ውስጥ የሚያልፉ headers እና ወደ buffer ከመግባታቸው በፊት በ`maskSecret()` ውስጥ የሚያልፉ bodies ያሉትን `InterceptedRequest` ወደ buffer ይገፋል። ከዚያም entryው በresponse፣ sizes እና latency ይዘምናል።
- **እንደገና ኢንክሪፕት የተደረገ ማስተላለፍ** (`createForward` / `realForward`): እንደገና ኢንክሪፕት በማድረግ ወደ መጀመሪያው መድረሻ ያስተላልፋል። `rejectUnauthorized` ነባሪው **`true`** ነው (በነባሪነት ደህንነቱ የተጠበቀ) — የupstream cert ደንበኛው በጠየቀው SNI/Host ላይ ተመስርቶ ይረጋገጣል፤ ስለዚህ proxyው የመጀመሪያው ደንበኛ ውድቅ የሚያደርገውን በትክክል ውድቅ ያደርጋል።

### የLoop መከላከያ (SO_MARK)

ሕጎቹ አዲስ የአካባቢ outbound ግንኙነቶችን ምልክት ስለሚያደርጉ፣ proxyው **ራሱ** እንደገና ኢንክሪፕት አድርጎ የሚያስተላልፈው በተለምዶ እንደገና ይያዛል — ይህም ማብቂያ የሌለው loop ይፈጥራል። የforward መንገዱ የbypass socket ምልክት (**SO_MARK**) በመጠቀም ከዚህ ይከላከላል፦

- `realForward` የupstream socketን በ`connectMarked(ip, port, DEFAULT_BYPASS_MARK)` በኩል ይከፍታል — `DEFAULT_BYPASS_MARK = 0x539` — ይህም **SO_MARK**ን ከ`connect()` **በፊት** ያዘጋጃል፤ ስለዚህ የforward SYN የbypass ምልክቱን ይይዛል።
- የ`mangle OUTPUT` ሕግ አስቀድመው የbypass ምልክቱን የያዙ ግንኙነቶችን (`-m mark ! --mark <bypassMark>`) ያስቀራል፤ ስለዚህ የproxyው forward እንደገና ምልክት **አይደረግበትም** እና እንደገና ወደ TPROXY አይገባም።

> የአተገባበር ማስታወሻ፦ በbypass ምልክት የተደረገው socket በagentው `createConnection` ላይ መጫን አለበት (`https.request({ createConnection })` agent ባለበት ጊዜ ያለማስጠንቀቂያ ችላ ይባላል)፤ አለበለዚያ forwardው ምልክት ያልተደረገበት socket ይከፍታል እና loopው ይመለሳል። ይህ በe2e የተረጋገጠው የloop መከላከያ ማስተካከያ ነበር።

## §7 የፋየርዎል ትራንዛክሽናዊ ተግብር / መልስ

ብልሽት የ`mangle` ደንብን ወይም ጊዜው ያለፈበትን መስመር በፍጹም ትቶ መሄድ የለበትም። የትዕዛዝ ገንቢው
(`src/mitm/tproxy/commands.ts`) እና አስኪያጁ (`src/mitm/tproxy/setup.ts`)
**መመለስ በተቃራኒ ቅደም ተከተል የመተግበር ትክክለኛ ተቃራኒ መሆኑን** ዋስትና ይሰጣሉ።

`applyTproxy(cfg)` የመተግበሪያ ትዕዛዞቹን በቅደም ተከተል ያስኬዳል፤ **ማንኛውም** ውድቀት ሲከሰት
በተቻለ መጠን ሙሉ `revertTproxy(cfg)` ያስኬዳል እና ስህተቱን እንደገና ይጥላል — ስለዚህ ፋየርዎሉ
ሙሉ በሙሉ ይተገበራል ወይም ሙሉ በሙሉ ይመለሳል፤ በከፊል ተተግብሮ ፈጽሞ አይቀርም። `revertTproxy(cfg)`
ተቃራኒ ትዕዛዞቹን በተቃራኒ ቅደም ተከተል ያስኬዳል እና ውድቀቶችን ችላ ይላል (idempotent — ያለምንም ቅድመ ሁኔታ
ለመጥራት ደህንነቱ የተጠበቀ፤ ለምሳሌ ከAgentBridge `repairMitm()` ማጽዳት)።

`validateTproxyConfig(cfg)` ከማንኛውም ትዕዛዝ በፊት ይሰራል፦ ወደቦች `1–65535` መሆን አለባቸው፣
`mark`/`routeTable`/`bypassMark` አዎንታዊ ኢንቲጀሮች መሆን አለባቸው፣ እና `bypassMark`
ከ`mark` የተለየ መሆን አለበት (ዑደትን ለመከላከል)።

### የመተግበሪያ ትዕዛዞች (በቅደም ተከተል)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

መመለስ እነዚህን በተቃራኒ ቅደም ተከተል ይሰርዛል፦ `PREROUTING -D`፣ `OUTPUT -D`፣ `ip route del`፣ `ip rule del`።

> ይህ አሰራር **OUTPUT-based** ነው፤ ምክንያቱም የMITM አጠቃቀም ሁኔታው _አካባቢያዊ_ ወደ ውጭ የሚወጣ
> ትራፊክ (በተመሳሳይ አስተናጋጅ ላይ ያሉ መተግበሪያዎች) ሲሆን፣ በ`PREROUTING` ውስጥ ያለ TPROXY ብቻውን ይህን
> አያይም — `PREROUTING` የተላለፈ ትራፊክን ብቻ ያያል። የ`OUTPUT` ሰንሰለት አዳዲስ
> አካባቢያዊ ግንኙነቶችን ምልክት ያደርጋል፣ `ip rule` ወደ አካባቢያዊ መድረሻ (`lo`) እንደገና ይመራቸዋል፣ እና
> ከዚያ `PREROUTING` ለግልጽ አዳማጩ ይመድባቸዋል።

   `source: "tproxy"` በሚለው በጥያቄዎች ዝርዝር ውስጥ ይታያሉ።
5. ለማቆም እንደገና ጠቅ ያድርጉ — `stopTproxyCaptureMode()`ን በመጠቀም
   `DELETE /api/tools/agent-bridge/tproxy` listener-ውን ይዘጋል፣ CA-ውን ያራግፋል፣ እና
   የfirewall ደንቦቹን ይመልሳል።

የመቅረጫ ሁነታ ሁኔታው (እየሠራ / ይገኛል / የመጥለፍ ብዛት / የlistener ወደብ)
ከ`GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` በ
`src/mitm/tproxy/captureManager.ts`) ይመጣል። በአንድ ጊዜ **አንድ** TPROXY session ብቻ ይሠራል —
ሁለተኛ ለማስጀመር መሞከር "TPROXY capture mode is already running" በሚል ውድቅ ይደረጋል።

## §10 መላ ፍለጋ

### Toggle-ው ተሰናክሏል

native addon-ውን መጫን አይቻልም። የሚከተሉትን ያረጋግጡ፦ Linux ላይ መሆንዎን፣ addon-ውን
(`npm run build:native:tproxy`) መገንባትዎን፣ እና process-ው `transparent.node`ን መጫን
መቻሉን። `isTransparentSocketAvailable()` toggle-ውን ይቆጣጠራል፤ addon-ው ሲጎድል
`GET /api/tools/agent-bridge/tproxy` `available: false`ን ይመልሳል።

### ምንም ነገር አይቀረጽም

- የተጠለፈው process በእርግጥ ከተዋቀረው `dport`
  (ነባሪ `443`) ጋር መገናኘቱን ያረጋግጡ።
- process-ው ተለዋዋጩን CA እንደሚያምን ያረጋግጡ። CA-ው በ
  `omniroute-tproxy-ca.crt` ስር ይጫናል፤ የራሳቸው trust store ያላቸው መተግበሪያዎች (Firefox/Chrome NSS)
  cert-ው እዚያም እንዲጨመር ሊያስፈልጋቸው ይችላል።
- ለcert-trusted / server የጤና ምርመራዎች የAgentBridge **Diagnose** ራስ-ምርመራን ያስኪዱ
  ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)ን ይመልከቱ)።

### ከመበላሸት በኋላ የቀሩ የfirewall ደንቦች

`revertTproxy()` የapply ትክክለኛ ተቃራኒ ሲሆን idempotent ነው። ሁነታውን ማቆም
ደንቦቹን ይመልሳል፤ OmniRoute በsession መካከል ከተቋረጠ፣ ወላጅ አልባ የsystem
ሁኔታን (DNS spoof፣ root CA፣ system proxy) ለመቀልበስ የAgentBridge
**Repair** እርምጃን (`POST /api/tools/agent-bridge/repair`) ይጠቀሙ። የTPROXY `mangle`
ደንቦች እና route-ውም እንደገና ሲነሳ በራስ-ሰር ይጸዳሉ።

### ማለቂያ የሌለው loop / proxy-ው የራሱን forward ይጠልፋል

ይህ የanti-loop ሁኔታ ነው። `bypassMark` ከ`mark` የተለየ መሆኑን (validation
ይህን ያስገድዳል) እና forward-ው `connectMarked`ን እንደሚጠቀም (በ`realForward`
ውስጥ ይጠቀማል) ያረጋግጡ። [§5 Anti-loop](#anti-loop-so_mark)ን ይመልከቱ።
