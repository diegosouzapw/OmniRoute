ይህ ሰነድ በ`omniroute@3.8.5` ላይ ለተነሱት ስድስት
`AI-detected potential malware` ግኝቶች እና በ`omniroute@3.8.6` ላይ
ለተተገበሩት ማቃለያዎች በጥገና አስተዳዳሪው የተዘጋጀ ማረጋገጫ ነው። የሚከተሉትን ለማስቻል ተዘጋጅቷል፦

1. የደህንነት ፓይፕላይን ኦፕሬተሮች ግኝቶቹን ከትክክለኛው ምንጭ ጋር
   ማገናዘብ ሲያስፈልጋቸው የሚጠቅሱት አንድ ወጥ ማጣቀሻ እንዲኖራቸው።
2. ወደፊት የሚመጡ የAI ስካነሮች ምልክት የተደረገበት እያንዳንዱ
   ዱካ ሆን ተብሎ የተሰራ፣ በምርጫ ብቻ የሚነቃ እና በሰነድ የተብራራ መሆኑን የሚገልጸውን በጥገና አስተዳዳሪው የተፈረመ ማረጋገጫ እንዲለዩ።
3. እያንዳንዱ የጥሪ ቦታ በዚህ መልኩ የተቀረጸበትን _ምክንያት_ የሚገልጽ የጽሑፍ መዝገብ እንዲኖረን —
   በዚህም ወደፊት የሚደረግ የኮድ መልሶ ማዋቀር ሆን ተብሎ የተወገደን የመለያ ንድፍ
   በስህተት ዳግም እንዳያስገባ።

የv3.8.6 ማቃለያዎች ከተለቀቁ በኋላ ከታች ካሉት የጥሪ ቦታዎች ውስጥ

  ለእያንዳንዱ ፕላትፎርም `installCertWindows/Mac/Linux`።
- `src/mitm/systemCommands.ts` — በጭነት ዱካዎቹ የሚጠቀሙባቸው የጋራ `execFile` / `spawn` / PowerShell
  ረዳቶች።

**ማስነሻ**፦ ተጠቃሚው በአካባቢያዊው dashboard ውስጥ በ
`/dashboard/cli-tools/mitm` ላይ "Enable MITM proxy" የሚለውን ጠቅ ሲያደርግ። route የloopback ብቻ ነው — በ
`CLAUDE.md` ውስጥ ያለውን ጥብቅ ደንብ #17 እና `src/server/authz/routeGuard.ts::isLocalOnlyPath()` ይመልከቱ። በtunnel በኩል የተጋለጠ
JWT ይህን የኮድ ዱካ **ማስነሳት አይችልም**።

**የሚከናወኑ ልዩ ፈቃድ የሚጠይቁ ክወናዎች (በየፕላትፎርሙ)**፦

| OS                     | ትዕዛዝ(ዞች)                                                                                                          |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | `certutil -addstore Root <cert>` በUAC በኩል                                                                         |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | ለእያንዳንዱ profile የNSS DB ዝማኔ በ`certutil -d sql:<profile>` በኩል                                                      |

እነዚህ `mitmproxy`፣ Charles Proxy፣ Fiddler እና
Caddy የሚጠቀሙባቸው ተመሳሳይ ትዕዛዞች ናቸው። በOmniRoute ውስጥ መኖራቸው በ
`docs/security/STEALTH_GUIDE.md` ተመዝግቧል።

- `runElevatedPowerShell()` ከእንግዲህ `-EncodedCommand <base64utf16le>` አይጠቀምም።

## §2 — የZed ማረጋገጫ መረጃ ማስመጣት (`app/api/providers/zed/import/route.js`)

**የምንጭ ፋይሎች**:

- `src/app/api/providers/zed/discover/route.ts` _(በv3.8.6 አዲስ)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(በv3.8.6 አዲስ)_

**አስጀማሪ**: ተጠቃሚው በአካባቢያዊው ዳሽቦርድ የአቅራቢዎች ገጽ ላይ "ከZed አስመጣ" የሚለውን ጠቅ ያደርጋል። የመጨረሻ ነጥቡ በ`requireManagementAuth` የተገደበ ነው። የZed አርታዒው ራሱ የአቅራቢዎቹን API ቁልፎች በሰነድ ከተገለጹ የአገልግሎት ስሞች ስር ወደ OS keychain ይጽፋል — https://zed.dev/docs/ai/llm-providers ይመልከቱ።

**የv3.8.5 ባህሪ (Socket.dev ምልክት ያደረገበት)**:

`POST /import` የማረጋገጫ መረጃዎቹን ፈልጎ በአንድ የጥያቄ-ምላሽ ዙር ውስጥ በራስ-ሰር ወደ አካባቢያዊው SQLite ማከማቻ ያስቀምጣቸው ነበር። ለእያንዳንዱ መለያ ማረጋገጫ የለም፣ fingerprint የለም፣ "N tokens ተገኝተዋል፣ ሁሉም ገብተዋል" የሚል ብቻ ነበር።

**የv3.8.6 ማሻሻያ — ባለ2-ደረጃ ማረጋገጫ**:

1. **`POST /api/providers/zed/discover`**
   `{ candidates: [{ provider, service, account, fingerprint }] }` ይመልሳል። ጥሬው token **በፍጹም** አይተላለፍም። fingerprint የሚሰላው
   `sha256(service|account|token).slice(0,16)` በሚለው ነው።
2. ዳሽቦርዱ የcandidate ዝርዝሩን ያሳያል፣ ኦፕሬተሩ የትኞቹ እንደሚገቡ ይመርጣል፣ እና `{ confirmedAccounts: [{ service, account, fingerprint }] }`ን ወደ **`POST /api/providers/zed/import`** ይልካል።
3. የማስመጣት የመጨረሻ ነጥቡ **በሰርቨሩ ላይ keychainን እንደገና ያነባል** እና በ
   `(service, account, fingerprint)` ያጣራል። የተቀየረ ወይም እንደገና የተጫወተ discover ምላሽ የማስመጣት የመጨረሻ ነጥቡ የማይዛመድ token እንዲያስቀምጥ ማታለል አይችልም — ከdiscover በኋላ ቀጥታው token ከተለወጠ፣ fingerprint ከዚያ በኋላ ስለማይዛመድ የማረጋገጫ መረጃው ይዘለላል።

የ`OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` env ጠቋሚ አውቶሜሽናቸውን ገና ላላዘመኑ ኦፕሬተሮች የv3.8.5 ባህሪን ያቆያል። በv3.9 ይወገዳል።

**የምናቆየው ለምንድን ነው**: Zedን አስቀድመው ለሚጠቀሙ እና የአቅራቢ ቁልፎቻቸውን እንደገና ሳይለጥፉ ወደ OmniRoute ማንጸባረቅ ለሚፈልጉ ተጠቃሚዎች፣ የZed ማስመጣት እጅግ ቀላሉ የመጀመሪያ ማዋቀሪያ መንገድ ነው።

**ምልክት የተደረገበት ምክንያት**: chunkው `execFileWithPassword`ን፣ `runElevatedPowerShell`ን እና የጋራውን `quotePowerShell` አጋዥ በድጋሚ ወደ ውጭ ይልካል። የSocket.dev AI መድብ እነዚህን እንደ አጠቃላይ "የhost አፈጻጸም + የፈቃድ ደረጃ ማሳደጊያ መሣሪያ ስብስብ" ያያቸዋል። በOmniRoute ውስጥ ግን በMITM cert መጫኛ መንገድ (§1) እና ለ`sudo` ትዕዛዝ አፈጻጸም በ`execFileWithPassword` ብቻ ጥቅም ላይ ይውላሉ።

**የv3.8.6 ማሻሻያ**:

- የ`runElevatedPowerShell` መልሶ ማዋቀር (§1ን ይመልከቱ)።
- በ`runElevatedPowerShell` እና በ`execFileWithPassword` ላይ ያለው የውስጥ `SECURITY-AUDITOR-NOTE:` ብሎክ፣ በallowlist የተፈቀዱትን callers እና ቋሚ የተደረገውን executable ዝርዝር ይመዘግባል።
- የ`execFileWithPassword` `spawn()` ጥሪ፣ አጋዡ እንዲቀበላቸው ከተፈቀዱት executableዎች allowlist ጋር `nosemgrep` ምልክት ይዟል — ከተጠቃሚ ግብዓት ወደ `finalCommand`/`finalArgs` **ምንም መንገድ የለም**።

## §5 — የOmniRoute Cloud Sync ማረጋገጫ መረጃ መልሶ መጻፍ (`api/keys/[id]/route.js`)

- `src/app/api/keys/[id]/route.ts` — `syncKeysToCloudIfEnabled()`ን ይጠራል።

**ማስጀመሪያ**: `isCloudEnabled()` `true`ን ይመልሳል (ከዳሽቦርዱ የሚዋቀር) **እና**
`CLOUD_URL` ተዋቅሯል። ሁለቱም ጠፍተው ሲሆኑ፣ ወደ Cloud መጨረሻ ነጥብ ምንም የውጭ
የአውታረ መረብ ጥሪ አይደረግም።

**የv3.8.5 ባህሪ (Socket.dev በትክክል የደረሰበት ሳንካ)**:

`cloudUpdatedAt > localUpdatedAt` በሚሆንበት ጊዜ፣ `updateLocalTokens()` ከCloud ምላሽ የተገኙትን
`accessToken`፣ `refreshToken` እና `providerSpecificData` እሴቶች
ይተካ ነበር። HMAC፣ ፊርማ ወይም checksum አልነበረም። በስህተት የተዋቀረ ወይም ጎጂ
`CLOUD_URL` (ወይም በሰርጡ ላይ ያለ MITM) የአቅራቢ OAuth ቶከኖችን ያለማሳወቅ
ሊቀይር ይችል ነበር።

**የv3.8.6 የስጋት ቅነሳ**:

1. **የHMAC ማረጋገጫ**: `verifyCloudSignature(rawBody, sigHeader)` JSONን
   ከመተንተኑ በፊት የ`X-Cloud-Sig` ራስጌን (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`) ይፈትሻል። ሚስጥሩ ከተዋቀረ፣ ፊርማው ያስፈልጋል። ካልተዋቀረ (የቆየ ሁነታ)፣
   ማስጠንቀቂያ ይመዘገባል እና ምላሹ ተቀባይነት ያገኛል — በv3.9 ሚስጥሩ አስፈላጊ
   ይሆናል።
2. **ለሚስጥራዊ መስኮች በፈቃደኝነት መምረጥ**: `accessToken` / `refreshToken` /
   `providerSpecificData` የሚተኩት `OMNIROUTE_CLOUD_SYNC_SECRETS=true`
   ሲሆን **ብቻ** ነው። ነባሪው ሁነታ የሚያመሳስለው ማረጋገጫ መረጃ ያልሆነውን ሜታዳታ
   (`expiresAt`, `status`, `lastError*`, `rateLimitedUntil`, `updatedAt`) ብቻ ነው።
   ይህ በርቀት ቶከን ማመሳሰል ላይ ለተመሰረቱ ተጠቃሚዎች **ተኳሃኝነትን የሚያፈርስ ለውጥ** ነው
   — በግልጽ በፈቃዳቸው መምረጥ አለባቸው።

**የምንጠብቀው ለምንድን ነው**: Cloud Sync የOmniRoute Cloud ተከራይ
የቡድን ማረጋገጫ መረጃዎችን ማዕከላዊ ለማድረግ ያለው ብቸኛ መንገድ ነው። ማስተካከያው የስጋት ሞዴሉን
ግልጽ ያደርገዋል፦ "ሰርቨሩ ይፈርማል፣ ደንበኛው ያረጋግጣል፣ ኦፕሬተሩ በፈቃዱ ይመርጣል።"
