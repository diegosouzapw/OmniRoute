ይህ መመሪያ Kiro (በAWS የሚስተናገድ AI የኮድ ረዳት) መለያዎችን ወደ OmniRoute ማከልን፣
በክፍለ-ጊዜ ግጭት ሳይኖር በርካታ መለያዎችን በአንድ ጊዜ ማስኬድ ላይ በማተኮር ይሸፍናል።

## ዳራ፦ የKiro መለያዎች ለምን ሊጋጩ ይችላሉ

የKiro የጀርባ ስርዓት ንቁ ክፍለ-ጊዜዎችን ለመከታተል የAWS SSO OIDC ደንበኛ ምዝገባዎችን ይጠቀማል።
ወሳኙ ገደብ፦ **እያንዳንዱ የOIDC ደንበኛ ምዝገባ በአንድ ጊዜ አንድ ንቁ
ክፍለ-ጊዜ ብቻ ይደግፋል**። ሁለተኛ መሣሪያ ወይም ተጠቃሚ በተመሳሳይ
የተመዘገበ ደንበኛ ሲረጋገጥ፣ የጀርባ ስርዓቱ የመጀመሪያውን መለያ የማደሻ ቶከን ውድቅ ያደርገዋል።

ይህ፣ ሌላ የKiro መለያ አስቀድሞ በገባበት ማሽን ላይ `kiro-cli login` ሲያስኬዱ
ችግር የሚፈጥረው ያው ዘዴ ነው — አዲሱ መግቢያ የመጀመሪያውን
መለያ ቶከን ይሽራል።

---

## OmniRoute ይህን እንዴት እንደሚፈታው (v3.8.0+)

ከv3.8.0 ጀምሮ፣ OmniRoute በእያንዳንዱ የKiro ግንኙነት ማስመጣት ወቅት
`registerClient()` (AWS SSO OIDC) ይጠራል። ይህ ለእያንዳንዱ የOmniRoute ግንኙነት የራሱን የተወሰነ የOIDC
ደንበኛ ምዝገባ ይሰጣል። እያንዳንዱ የደንበኛ ምዝገባ ራሱን የቻለ ስለሆነ፣ አንድ መለያን ማደስ ወይም
እንደገና ማረጋገጥ በማንኛውም ሌላ መለያ የማደሻ ቶከን ላይ ተጽዕኖ አያሳድርም።

ማግለሉ በማደሻ-ቶከን ማስመጣት ዘዴዎች ላይ የሚተገበር ሲሆን፣ የAPI-ቁልፍ ማረጋገጫ
የOIDC ማደሻ ክፍለ-ጊዜዎችን ሙሉ በሙሉ ያስወግዳል፦

| የማስመጣት ዘዴ                               | የማግለል ሁኔታ                                                                   |
| --------------------------------------- | --------------------------------------------------------------------------- |
| AWS Builder ID / IDC የመሣሪያ-ኮድ ፍሰት       | የመሣሪያ-ኮድ ፍሰቱ ከተዋወቀ ጀምሮ የተገለለ                                                |
| **ቶከን አስመጣ** (የማደሻ ቶከንን በእጅ መለጠፍ)       | ከv3.8.0 ጀምሮ የተገለለ                                                           |
| **የGoogle / GitHub ማኅበራዊ መግቢያ**         | ከv3.8.0 ጀምሮ የተገለለ                                                           |
| **ራስ-ሰር ማስመጣት** (kiro-cli SQLite)       | ከv3.8.0 ጀምሮ የተገለለ (የSQLite ዱካ አስቀድሞ የተገለለ ነበር፤ የSSO-መሸጎጫ ተተኪ አሁን ደግሞ ተገልሏል) |
| **API ቁልፍ** (የረጅም ጊዜ CodeWhisperer ቁልፍ) | የማደሻ ክፍለ-ጊዜ የለም፤ ቁልፉ ተረጋግጦ እንደ ተሸካሚ ማረጋገጫ ይከማቻል                             |

## ከv3.8.0 በፊት ለተፈጠሩ ግንኙነቶች የሽግግር ማስታወሻ

ከv3.8.0 በፊት የገቡ ግንኙነቶች በ`providerSpecificData` ውስጥ የተከማቸ
የተወሰነ የOIDC ደንበኛ ምዝገባ የላቸውም። እነዚህ ግንኙነቶች መስራታቸውን ይቀጥላሉ፣ ነገር ግን የጋራ
የማኅበራዊ-ማረጋገጫ ማደሻ መዳረሻን ይጠቀማሉ፤ ይህም ማለት እንዲህ ያሉ ሁለት ግንኙነቶች አሁንም እርስ በርሳቸውን
ውድቅ ሊያደርጉ ይችላሉ።

**ማግለልን ለማግኘት፦** የድሮውን ግንኙነት ከ**ዳሽቦርድ → አቅራቢዎች** ይሰርዙ እና
ከሚደገፉት የማስመጣት ፍሰቶች ማንኛውንም በመጠቀም እንደገና ያስመጡት። ሁሉም አዲስ የተፈጠሩ ግንኙነቶች
የራሳቸውን የደንበኛ ምዝገባ በራስ-ሰር ያገኛሉ።

## ሁለት የKiro መለያዎችን ጎን ለጎን ማከል

### ቅድመ ሁኔታዎች

- OmniRoute v3.8.0 ወይም ከዚያ በኋላ።
- የሚሰራ የKiro መለያ (ኢሜይል + የይለፍ ቃል፣ Google፣ ወይም GitHub መግቢያ)።
- እንደ አማራጭ ሁለተኛ የKiro መለያ።

### ደረጃ 1፦ የመጀመሪያውን መለያ ያስመጡ

1. **ዳሽቦርድ → አቅራቢዎች → አቅራቢ አክል → Kiro** ይክፈቱ።
2. ከሚከተሉት አንዱን ይምረጡ፦
   - **ቶከን አስመጣ** — በ`aorAAAAAG` የሚጀምር የማደሻ ቶከን ይለጥፉ።
   - **API ቁልፍ** — የረጅም ጊዜ የKiro / CodeWhisperer API ቁልፍ ይለጥፉ።
   - **የGoogle / GitHub መግቢያ** — የOAuth ፍሰቱን በአሳሹ ውስጥ ያጠናቅቁ።
   - **ራስ-ሰር ማስመጣት** — አዝራሩን ጠቅ ያድርጉ፤ OmniRoute ማረጋገጫዎችን ከአካባቢያዊው
     የkiro-cli የውሂብ ጎታ ወይም `~/.aws/sso/cache` ያነባል።
3. ግንኙነቱ ይቀመጣል። የማደሻ-ቶከን ፍሰቶች የተወሰነ
   የOIDC ደንበኛን በራስ-ሰር ይመዘግባሉ። የAPI-ቁልፍ ፍሰቶች ቁልፉን በAWS ያረጋግጣሉ እና የማደሻ ቶከን አያከማቹም።

### ደረጃ 2፦ ሁለተኛውን መለያ ያስመጡ

ለሁለተኛው መለያ ደረጃ 1ን ይድገሙ። እያንዳንዱ ማስመጣት የተለየ የOIDC
ደንበኛ ምዝገባ ስለሚፈጥር፣ ሁለቱ ግንኙነቶች ሙሉ በሙሉ የተገለሉ ናቸው።

### ደረጃ 3፦ ሁለቱም ግንኙነቶች ንቁ መሆናቸውን ያረጋግጡ

1. **ዳሽቦርድ → አቅራቢዎች** — ሁለቱም የKiro ግንኙነቶች **ንቁ** ሁኔታን ማሳየት አለባቸው።
2. **ዳሽቦርድ → ጤና** — ሁለቱም ግንኙነቶች የቶከን ጤና ፍተሻቸውን ማለፍ አለባቸው።

### ደረጃ 4፦ በመለያዎቹ መካከል ለማስተላለፍ ጥምረት ይጠቀሙ

ጭነትን ለማመጣጠን ወይም በአንዱ ላይ ችግር ሲኖር ወደ ሌላው ለመሸጋገር፣ ሁለቱንም ግንኙነቶች እንደ ዒላማ ያካተተ ጥምረት ይፍጠሩ፦

```
kiro/kiro-dev → kiro/kiro-pro
```

## የድርጅት / IDC ተጠቃሚዎች

ለAWS IAM Identity Center (IDC) መለያዎች፣ በ**Dashboard → Providers → Kiro → Device Code** ውስጥ ያለውን **AWS Builder ID / IDC device-code**
ፍሰት ይጠቀሙ። የdevice-code ፍሰቱ ሁልጊዜም ሙሉ በሙሉ የተነጠለ ነው። ለእነዚህ ግንኙነቶች እንደገና ማስመጣት አያስፈልግም።

ነባሪ ባልሆነ AWS ክልል ውስጥ የሚሰሩ የድርጅት ተጠቃሚዎች፣ በImport Token API በኩል
ሲያስመጡ ክልሉን መግለጽ ይችላሉ፦

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

የ`region` መስክ ካልተገለጸ ነባሪው `us-east-1` ነው።

## የAPI ቁልፍ ማስመጣት ፍሰት

የAPI ቁልፍ ማረጋገጫ ለረጅም ጊዜ የሚያገለግሉ Kiro / AWS CodeWhisperer bearer ምስክርነቶች ነው።
የOAuth እድሳትን አይጠቀምም፣ ስለዚህ የጋራ OIDC ክፍለ-ጊዜ ዋጋ መሰረዝን ያስወግዳል።

### Dashboard

1. **Dashboard -> Providers -> Kiro**ን ይክፈቱ።
2. **API Key**ን ይምረጡ።
3. የAPI ቁልፉን እና አማራጭ የAWS ክልልን ይለጥፉ (በነባሪ `us-east-1`)።
4. OmniRoute ቁልፉን ያረጋግጣል እና ግንኙነቱን ያስቀምጣል።

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### ውስጣዊ ውል

የAPI መስመሩ `KiroService.validateApiKey()`ን በመጥራት ቁልፉን ያረጋግጣል፤ ይህም
ከክልሉ ጋር በሚዛመደው CodeWhisperer/Amazon Q endpoint ላይ `ListAvailableProfiles`ን በመጠቀም `profileArn`ን ይፈታል።

የተቀመጠው ግንኙነት የሚከተለውን ይጠቀማል፦

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

በruntime ጊዜ፣ `KiroExecutor.buildHeaders()` ቁልፉን እንደ
`Authorization: Bearer <key>` ይልካል እና `tokentype: API_KEY`ን ይጨምራል። የኮታ/መገለጫ ጥሪዎች
ተመሳሳዩን ምልክት ይጠቀማሉ፤ በዚህም AWS bearer-ን እንደ OIDC ወይም የማህበራዊ መዳረሻ token ሳይሆን
እንደ ረጅም ጊዜ የሚያገለግል API ቁልፍ ይቆጥረዋል።

## የOIDC ደንበኛ ጊዜ ማብቃት

የAWS SSO OIDC የሕዝብ ደንበኞች በአብዛኛው ከ90 ቀናት በኋላ ጊዜያቸው ያበቃል
(`clientSecretExpiresAt`)። OmniRoute ይህን የጊዜ ማህተም ለታዛቢነት በ`providerSpecificData`
ውስጥ ያከማቻል። አንድ ግንኙነት ከ~90 ቀናት በኋላ መታደስ ካቆመ፣
አዲስ የOIDC ደንበኛ ምዝገባ ለማግኘት ግንኙነቱን እንደገና ያስመጡ። ጊዜው ሲያበቃ በራስ-ሰር እንደገና መመዝገብ
እንደ ወደፊት ማሻሻያ ተመዝግቧል።

የAPI ቁልፍ ግንኙነቶች በAWS SSO OIDC በኩል ስለማይታደሱ፣
የOIDC ደንበኛ ጊዜ ማብቂያ የላቸውም።

## መላ ፍለጋ

### ሁለተኛው መለያ በተደጋጋሚ ከስርዓቱ ይወጣል

- ሁለቱንም ግንኙነቶች በ**Dashboard → Providers** ውስጥ ይፈትሹ እና እያንዳንዳቸው በጥሬ JSON ውስጥ null ያልሆነ
  `clientId` እንደሚያሳዩ ያረጋግጡ (በመረጃ አዶው በኩል ይታያል)። ከግንኙነቶቹ አንዱ `clientId` ከሌለው፣
  ከv3.8.0 በፊት የገባ ነው — እንደገና ያስመጡት።

### ማስመጣት በ"Token validation failed" ይከሽፋል

- የrefresh token በ`aorAAAAAG` መጀመሩን ያረጋግጡ።
- OmniRoute ወደ `https://oidc.us-east-1.amazonaws.com` (ወይም ወደ ተዋቀረው
  ክልል) መድረስ መቻሉን ያረጋግጡ። ከድርጅት proxy ጀርባ ከሆኑ፣
  በ**Dashboard → Settings → Proxies** ውስጥ የprovider ደረጃ proxy ያቀናብሩ።

### የAPI ቁልፍ ማስመጣት ይከሽፋል

- ቁልፉ የKiro / CodeWhisperer API ቁልፍ እንጂ refresh token አለመሆኑን ያረጋግጡ።
- የAWS ክልሉ ከቁልፉ/መለያው ጋር መዛመዱን ያረጋግጡ። `us-east-1` ነባሪው ነው።
- ቁልፉ `ListAvailableProfiles`ን መጥራት መቻል አለበት፤ አለበለዚያ OmniRoute
  አስፈላጊውን `profileArn` መፍታት አይችልም።
