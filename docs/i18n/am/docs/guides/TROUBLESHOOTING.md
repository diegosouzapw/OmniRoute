## ፈጣን ማጣቀሻ

**OmniRouteን አዲስ ነዎት?** ከዚህ ይጀምሩ — እነዚህ 90% ችግሮችን ይፈታሉ፦

| ይህን አያለሁ                      | ትርጉሙ                                    | ምን ማድረግ እንዳለብዎ                                                                          |
| ----------------------------- | --------------------------------------- | --------------------------------------------------------------------------------------- |
| "Can't connect"               | OmniRoute እየሰራ አይደለም                    | `omniroute` ወይም `docker restart omniroute` ያስኪዱ                                         |
| "Invalid API key"             | ቁልፍዎ የተሳሳተ ወይም ጊዜው ያለፈበት ነው             | ቁልፉን ከአቅራቢው ድረ ገጽ እንደገና ይቅዱ                                                             |
| "Rate limit exceeded"         | በጣም ብዙ ጥያቄዎችን እየላኩ ነው                   | 1 ደቂቃ ይጠብቁ፣ ወይም ለራስ-ሰር ተለዋጭ ምርጫ `model: "auto"`ን ይጠቀሙ                                   |
| "Quota exceeded"              | ነፃ/የተከፈለበት ኮታዎን ጨርሰዋል                   | ተጨማሪ አቅራቢዎችን ያገናኙ፣ ወይም ነፃ አቅራቢዎችን (Kiro፣ Pollinations) ይጠቀሙ                             |
| "Slow responses"              | አቅራቢው ሥራ የበዛበት ወይም ሩቅ ነው                | `model: "auto/fast"`ን ይጠቀሙ ወይም ፈጣን አቅራቢን (Groq፣ Cerebras) ያገናኙ                          |
| "Wrong provider used"         | `auto` የተለየ አቅራቢ መርጧል                   | ይህ የተለመደ ነው! `auto` ምርጡን ይመርጣል። `model: "openai/gpt-4o"`ን በመጠቀም የተወሰነ አቅራቢ እንዲጠቀም ያስገድዱ |
| "502 Bad Gateway"             | አቅራቢው አይሰራም                             | ይጠብቁና እንደገና ይሞክሩ፣ ወይም አቅራቢዎችን ለመቀየር `model: "auto"`ን ይጠቀሙ                               |
| "401 Unauthorized"            | የመግቢያ ማረጋገጫዎችዎ የተሳሳቱ ናቸው                | የAPI ቁልፍዎን ያረጋግጡ ወይም በOAuth እንደገና ማንነትዎን ያረጋግጡ                                          |
| "omniroute is not recognized" | በWindows PATH ውስጥ ዓለም አቀፍ node ሞጁሎች የሉም | የnpm ዓለም አቀፍ ቅድመ መንገድዎን ወደ Windows PATH ያክሉ። በ`npm config get prefix` ያግኙት።             |
| "429 Too Many Requests"       | የጥያቄ መጠን ተገድቧል                          | 1 ደቂቃ ይጠብቁ፣ ወይም ተጨማሪ አቅራቢዎችን ያገናኙ                                                       |

**አሁንም ችግሩ አልተፈታም?** ከታች ያለውን [ዝርዝር የችግር መፍቻ](#detailed-troubleshooting) ይመልከቱ፣ ወይም በ[Discord](https://discord.gg/U47eFqAXCn) ላይ ይጠይቁ።

## ዝርዝር የችግር መፍቻ

### በነፃ አቅራቢዎች ላይ የጥያቄ መጠን ገደብ (429 / 400 / 401)

**ምልክት**፦ `model: "auto"`ን ከነፃ/ማረጋገጫ-አልባ አቅራቢዎች (opencode፣ auggie፣ ወዘተ) ጋር ሲጠቀሙ፣ ከመልሶች ይልቅ አልፎ አልፎ `HTTP 429`፣ `400` ወይም `401` ያገኛሉ። ተመሳሳዩን ጥያቄ ከጥቂት ጊዜ በኋላ እንደገና ሲሞክሩ ጥያቄዎቹ ይሳካሉ፣ ነገር ግን ራስ-ሰር ሂደቶች (cron jobs፣ agents፣ scripts) በመጀመሪያው ውድቀት ይቋረጣሉ።

**ዋና ምክንያት**፦ ሦስት ነፃ የሆኑ የውድቀት ዓይነቶች አንድ ላይ ይደራረባሉ፦

1. **የአቅራቢ የጥያቄ መጠን ገደብ (`429`)**፦ ነፃ ደረጃዎች በእያንዳንዱ የጊዜ መስኮት ላይ ኮታ ሊያስፈጽሙ ይችላሉ። በአንድ ጊዜ የሚላኩ ብዙ ተጓዳኝ ጥሪዎች ኮታውን ያሟጥጣሉ፣ ስለዚህ የጊዜ መስኮቱ ዳግም እስኪጀምር ድረስ ቀጣዩ ጥያቄ ውድቅ ይደረጋል።
2. **በቀጥታ ማሳለፊያ ውስጥ የተበላሸ ሞዴል (`400`/`401`)**፦ `auto/*` ስብስቦች በካታሎጉ ውስጥ የተመዘገቡ ነገር ግን የሚሰሩ የመግቢያ ማረጋገጫዎች የሌሏቸውን ከ`opencode` የመጡ ቀጥታ ማሳለፊያ ሞዴሎችን ሊያካትቱ ይችላሉ (ለምሳሌ `oc/north-mini-code-free` → `401`)። ራስ-ሰር ራውተሩ አንዱን ይሞክራል፣ ይወድቃል፣ እና ተለዋጭ ምርጫው ከመጀመሩ በፊት ስህተቱ ይተላለፋል።
3. **የተጓዳኝነት ማጉላት (ጫና ሲኖር `429`)**፦ በርካታ agent/cron sessions `auto`ን በአንድ ጊዜ ሲጠቀሙ፣ አጠቃላይ የጥያቄ ፍጥነቱ ነፃ አቅራቢዎች ሊቋቋሙት ከሚችሉት መጠን ይበልጣል፤ በዚህም ትክክለኛ ጥሪዎች እንደ አላግባብ አጠቃቀም ምልክት ይደረግባቸዋል።

**የተረጋገጠ መፍትሔ (በማህበረሰቡ የተዘገበ፣ 2026-08-10)**፦ ሽክርክር፣ ተጓዳኝነት እና ተለዋጭ ምርጫ በነፃው ደረጃ ላይ የሚኖረውን መለዋወጥ በስህተት ከመቋረጥ ይልቅ እንዲቋቋሙት ሦስት የአካባቢ ተለዋዋጮችን ያስተካክሉ፦

```bash
export OMNIROUTE_ROTATE_ON_400=true           # በ400/401 ጊዜ ወደ ሌላ ሞዴል/አቅራቢ ይለፉ (የተበላሹ ቀጥታ ማሳለፊያ ሞዴሎችን ይዘላል)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ለከባድ ጥያቄዎች ግልጽ የመግቢያ ከፍተኛ ገደብ (በነባሪ አልተዋቀረም፦ የጥያቄ ብዛት ገደብ የለም፣ ከታች ያለውን ማስታወሻ ይመልከቱ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ወዲያውኑ እንደገና ሊሞከር የሚችል 503 ከመመለስ ይልቅ ለከባድ ጥያቄዎች አቅም ረዘም ያለ የተገደበ ጥበቃ
```

እነዚህን በOmniRoute ሂደት አካባቢ (daemon፣ ለምሳሌ በLaunchAgent plist ወይም `systemctl edit`) ውስጥ ያዘጋጁ፣ ከዚያ OmniRouteን እንደገና ያስጀምሩ። የሽክርክር ምልክቱ ከፍተኛውን ውጤት የሚያመጣ ነጠላ መቆጣጠሪያ ነው፦ ከባድ ውድቀትን በስብስቡ ውስጥ ካለ ጤናማ አቅራቢ ጋር ወደሚደረግ ግልጽ ዳግም ሙከራ ይቀይረዋል።

**ማስታወሻ**፦ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` በአንድ ጊዜ የሚሰሩ ከባድ — ረጅም-አውድ — ጥያቄዎችን ብዛት ይገድባል፤ ይህ ገደብ የመግቢያ በር እንጂ የአቅራቢ የጥያቄ መጠን ገደብ አይደለም። **#503-fanout ዝማኔ፦** ይህ ተለዋዋጭ ከእንግዲህ በነባሪ አይዋቀርም (አሁን የሚተገበረው ከላይ እንደታየው በግልጽ ሲዋቀር ብቻ ነው) — በምትኩ የከባድ ጥያቄዎች መግቢያ ከአስተናጋጁ ትክክለኛ የማህደረ ትውስታ ጣሪያ አንጻር ራሱን በሚያመጣጥን፣ በራስ-ሰር በሚወሰን የባይት በጀት (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ይገደባል። ስለዚህ አዲስ ማሰማራት ይህን ተለዋዋጭ ምንም ሳያዘጋጅ በጣም ያነሱ `503 chat_admission_busy` ውድቅ ማድረጎችን ማየት አለበት፤ እዚህ ላይ በግልጽ ማዋቀሩ አሁንም በሰነዱ እንደተገለጸው በትክክል ይሰራል። ግልጽ የባይት-በጀት መተኪያዎች ከ8 MiB–2 GiB ውስጥ ይገደባሉ። `413 body_exceeds_budget` ጊዜያዊ አይደለም፦ ያንን የባይት በጀት ይጨምሩ፣ `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`ን ይቀንሱ፣ ወይም የሂደቱን የማህደረ ትውስታ ጣሪያ ይጨምሩ። የ`inflight_bytes_budget` መቀነስ ጊዜያዊ የሀብት ፉክክር ሲሆን እንደገና መሞከር ይቻላል። የእያንዳንዱ አቅራቢ የጥያቄ መጠን ገደብ (`open-sse/services/rateLimitManager.ts`) በ`RATE_LIMIT_MAX_WAIT_MS`፣ `RATE_LIMIT_MAX_QUEUE_DEPTH` እና `RATE_LIMIT_AUTO_ENABLE` ተለይቶ ይተዳደራል — `.env.example`ን ይመልከቱ።

**መሥራቱን እንዴት ማረጋገጥ እንደሚቻል**፦ agent/cronዎን በፍጥነት በተከታታይ ሁለት ጊዜ ያሂዱና ሁለቱም በተሳካ ሁኔታ መጠናቀቃቸውን ያረጋግጡ። ከማስተካከያው በፊት፣ ሁለተኛው ማስኬድ በተለምዶ `429`/`401` ስህተት ያስከትላል። ከማስተካከያው በኋላ፣ ውድቀቶች (ካሉ) በማይታይ ሁኔታ እንደገና ይሞከራሉ እና ጥሪው ይጠናቀቃል። እንዲሁም `curl /monitoring/health` ማስኬድ እና በአቅራቢ ግንኙነቶች ላይ ያለውን `rateLimitedUntil` መስክ እንዲሁም ለተጎዱት አቅራቢዎች `circuitBreakers.providerBreakers[].state`ን መከታተል ይችላሉ — ሁኔታው `CLOSED`፣ `DEGRADED`፣ `OPEN` ወይም `HALF_OPEN` ከሚሉት አንዱ ነው (`src/shared/utils/circuitBreaker.ts`ን ይመልከቱ)፤ ውድቀቱ የቀጠለበት አቅራቢ፣ ዳግም ማስጀመሪያ ጊዜው የሙከራ ጥሪ (`HALF_OPEN`) እንዲያልፍ ከመፍቀዱ በፊት `CLOSED → DEGRADED → OPEN` በሚል ይቀየራል።

**አሁንም 429 ካዩ**፦ ለዚያ አቅራቢ ንቁ የሆነው መለያ _quota_ውን (የጥሪ ፍጥነት ገደቡን ብቻ ሳይሆን) በእርግጥ ጨርሷል። በOmniRoute ዳሽቦርድ → Providers → Accounts ውስጥ ለተመሳሳዩ አቅራቢ ሁለተኛ መለያ ያክሉ፣ ወይም ሌላ ነፃ አቅራቢ (ለምሳሌ `routeway`፣ `auggie`) ያካትቱ። ማፈራረቅ የሚያግዘው ጊዜያዊ የጥሪ ፍጥነት/400/401 ስህተቶችን ብቻ ነው፤ ሙሉ የኮታ መሟጠጥ ሁለተኛ credential ወይም የተለየ አቅራቢ ያስፈልገዋል።

**በvision ሞዴሎች (`auto/vision`፣ `bazaarlink/*`) ላይ 403 ካዩ**፦ የተገናኘው መለያ visionን የሚያካትት የሚከፈልበት ዕቅድ የለውም፣ ወይም API keyው በቂ ፈቃዶች የሉትም። በአቅራቢው ዳሽቦርድ ውስጥ የkeyው scope vision/multimodalን እንደሚያካትት ያረጋግጡ፣ ወይም የሚከፈልበት ደረጃ ያለውን መለያ ያገናኙና የvision ዒላማ አድርገው ያቆዩት።

## የ npm install ማስጠንቀቂያዎች (ERESOLVE / peer / deprecated)

`npm install -g omniroute` ሲያስኬዱ፣ እንደ `npm warn ERESOLVE`፣ የ peer-dependency ማሳወቂያዎች እና `deprecated` መልዕክቶች ያሉ ብዙ ማስጠንቀቂያዎችን ሊያዩ ይችላሉ። **እነዚህ የሚጠበቁ እና ምንም ጉዳት የሌላቸው ናቸው።** በውጤቱ ውስጥ `added <N> packages` ካዩ ጭነቱ በትክክል ተጠናቋል።

የ peer-dependency መፍታት ማስጠንቀቂያዎችን ለማፈን፣ በ OmniRoute የሚደገፈውን የመጫኛ ቅጽ ይጠቀሙ፦

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` የሚያፍነው `ERESOLVE` እና የ peer-dependency ማሳወቂያዎችን ብቻ ነው። የማቋረጥ ማሳወቂያዎች ከተዘዋዋሪ የሶስተኛ ወገን ጥቅሎች ስለሚመጡ እንደታዩ ይቆያሉ፤ ጭነቱ እንዳልተሳካ አያመለክቱም።

ማስጠንቀቂያዎቹ OmniRoute ሊቆጣጠራቸው በማይችላቸው የሶስተኛ ወገን ጥቅሎች ውስጥ ካሉ ጊዜ ያለፈባቸው የ peer-dependency ክልሎች የሚመጡ ናቸው፦

1. **`marked-terminal`፣ `marked >=1 <16` ይፈልጋል፤ `marked@18` ተገኝቷል** — በተግባር ያለችግር ይሠራል፤ የ upstream peer ክልሉ ጊዜ ያለፈበት ብቻ ነው።
2. **`deprecated prebuild-install@7.1.3`** — ተዘዋዋሪ የ native-binary ማውረጃ ረዳት ነው። የተወሰነውን `wreq-js` የመጓጓዣ ማያያዣ ለመጫን
   ጥቅም ላይ አይውልም፣ እንዲሁም የ web-cookie አቅራቢ መጓጓዣ
   ማዋቀሩ እንዳልተሳካ አያመለክትም።

**ምንም እርምጃ አያስፈልግም** — የ upstream ጥቅሎችን fork ሳያደርጉ ማስጠንቀቂያዎቹን ሙሉ በሙሉ ማፈን አይቻልም።

እንዳልተጫነ ከሚገልጽ መልዕክት ጋር `503` ከመለሰ፣ የ npm ጥቅሉ አለ ነገር ግን የአሳሹ binary የለም።
Playwright ሆን ብሎ የአሳሽ ውርዶችን ከ npm ጥቅል
ጭነት ለይቶ ያስቀምጣል፣ ስለዚህ አሳሹ እስኪጫን ድረስ ይህ ምላሽ የሚጠበቅ ነው።

ለዓለም አቀፍ npm ጭነት፣ የአሳሹ cache የዚያው Playwright ጭነት
እንዲሆን Chromiumን ከ OmniRoute ጥቅል ማውጫ
ውስጥ ይጫኑ፦

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ከጭነቱ በኋላ OmniRouteን እንደገና ያስጀምሩ፣ ከዚያ የ Gemini Web ጥያቄውን እንደገና ይሞክሩ።
OmniRouteን ከ Docker image የሚያስኬዱ ከሆነ፣ Chromiumን እና ጥገኞቹን አካቶ የያዘውን `-web` image (ወይም `runner-web`
የ build target) ይጠቀሙ፤ base image እነዚህን
አያካትትም።

## የጸረ-ቫይረስ የተሳሳቱ ማስጠንቀቂያዎች

### Avast/AVG `README.md`ን በ`MD:HttpRequest-inf[Susp]` ወደ ማግለያ ያስገባል

**ይህ የተሳሳተ ማስጠንቀቂያ ነው። ምንም የተበከለ ነገር የለም፣ እና ምንም እርምጃ አያስፈልግም።**

Avast እና AVG ብዙ HTTP ጥያቄ የሚመስሉ አገናኞችን የያዙ ተራ-ጽሑፍ/Markdown ፋይሎችን
የሚጠቁም ሂዩሪስቲክ ያስኬዳሉ። የOmniRoute `README.md` በnpm ጥቅል ውስጥ አብሮ ይቀርባል (`package.json` → `files`
ውስጥ ተዘርዝሯል)፣ ስለዚህ በዓለም አቀፍ ጭነት ጊዜ `node_modules/omniroute/README.md` ላይ ይቀመጣል —
እንዲሁም ~15 የ`http://localhost:20128/...` ምሳሌዎችን (የMCP HTTP/SSE መዳረሻዎች፣ የA2A
`.well-known` URL፣ እና የ`curl` ቁርጥራጮች) ይዟል። ይህ የአገናኝ ጥግግት
ሂዩሪስቲኩን ለማስነሳት በቂ ነው።

ይህ በቅርቡ ብቻ ከጀመረ፦ የፋይሉ ዓይነት አልተቀየረም። README የመዳረሻዎቹን
ሰንጠረዥ አስፋፍቷል (MCP HTTP + SSE + A2A ተጨምረዋል) እና ተጨማሪ የ`curl` ምሳሌዎች ታክለዋል፣ ይህም
ከገደቡ በላይ እንዲያልፍ አድርጎታል።

ፋይሉ ምንም የሚፈጸም ይዘት የሌለው ሥራ-አልባ ሰነድ ነው። ከማግለያው
በደህና መልሰው ማስቀመጥ ይችላሉ።

**ማድረግ ያለብዎት፦**

1. **ማሳወቂያዎቹን ያቁሙ** — የጭነት ማውጫውን ከጸረ-ቫይረስዎ ፍተሻ
   ያግልሉ (Avast፦ Settings → Exceptions)፣ የዓለም አቀፍ `node_modules` ዱካዎን እና/ወይም
   የOmniRoute ውሂብ ማውጫን (`~/.omniroute/`) ያክሉ።
2. **የተሳሳተውን ማስጠንቀቂያ ሪፖርት ያድርጉ** — <https://www.avast.com/false-positive-file-form.php>፣
   በማግለያ ያለውን `README.md` በማያያዝ። ችግሩ የአቅራቢው ሂዩሪስቲክ ለጽሑፍ ፋይል
   ከመጠን በላይ ምላሽ መስጠቱ ስለሆነ፣ ይህ ሁሉንም የሚጠቅም መፍትሔ ነው።

**ይህን በእኛ በኩል "የማናስተካክለው" ለምንድን ነው፦** ምሳሌዎቹ በሙሉ `http://localhost` ናቸው፣ እና
localhost ራስ-የተፈረመ ሰርቲፊኬት ከሚያስከትለው ችግር ውጭ `https` ሊሆን አይችልም። የአንድ አቅራቢን ሂዩሪስቲክ
ለማለፍ ሰነዶቹን ማበላሸት፣ የስካነር ስህተትን ለማርካት ሲባል እያንዳንዱን አንባቢ ይጎዳል።

### Kaspersky የዴስክቶፕ መተግበሪያውን `PDM:Trojan.Win32.Generic` ብሎ ይጠቁማል

**ይህ ከባህሪ ሂዩሪስቲክ የመጣ የተሳሳተ ማስጠንቀቂያ ነው። ምንም የተበከለ ነገር የለም።** የKaspersky
`PDM:` ቅድመ ቅጥያ ውሳኔው ከProactive Defense Module (System Watcher) እንደመጣ ያመለክታል፤
ይህም ጫኚው ከሚታወቅ ማልዌር ጋር ይዛመዳል ወይስ አይዛመድም ብሎ ከመፈተሽ ይልቅ _የሚያደርገውን_ ይገመግማል።
ሲነሳ Kaspersky መላውን ጭነት "ወደ ኋላ ይመልሳል" — አስቀድሞ የጻፋቸውን ፋይሎች ይሰርዛል —
ስለዚህ መተግበሪያው ተበላሽቶ ወይም ጠፍቶ ይቀራል።

የሚጠቁማቸው ፋይሎች ከዴስክቶፕ መተግበሪያው ጋር የታሸጉ የታወጁ ክፍት-ምንጭ ጥገኞች
መደበኛ ክፍሎች ናቸው፣ ለምሳሌ፦

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` እና
  `workerProcessEntry.js` — [Playwright](https://playwright.dev)፣ በመተግበሪያ ውስጥ ለአቅራቢ መግቢያ እና
  በአሳሽ ለሚደገፍ ውይይት ጥቅም ላይ የሚውለው የአሳሽ-አውቶሜሽን ላይብረሪ።
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — የአሳሽ አሻራ ያለውን HTTP በድር-ኩኪ አቅራቢዎች ላይ ለመጠቀም የሚያስችለው በተወሰነ ስሪት ላይ የተቆለፈ
  የ`wreq-js` ቤተኛ ማያያዣ (`<arch>` `x64` ወይም `arm64` ነው)።

**የሚነሳበት ምክንያት፦** የWindows ጫኚው **ገና በኮድ አልተፈረመም**፣ ስለዚህ ያልተፈረመ NSIS
ጫኚ ምንም ዝና የለውም፣ እና የባህሪ ሂዩሪስቲኮች በከፍተኛ ጥብቅነት ይሠራሉ። ይህ ከታሸገ
ቤተኛ DLL እና በ`%LOCALAPPDATA%\Programs\OmniRoute` ስር ከሚጻፉ በመቶዎች ከሚቆጠሩ `.js` ፋይሎች
(ከNext.js ራሱን የቻለ ግንባታ የመጡ በሃሽ ቅጥያ ያላቸው የጥቅል ማውጫዎችን ጨምሮ)
ጋር ሲደመር፣ ሂዩሪስቲኩን ለማስነሳት በቂ ነው። የኮድ ፊርማ ታቅዷል፤
እስኪተገበር ድረስ አዳዲስ ልቀቶች ይህን ሊደግሙ ይችላሉ።

**ማድረግ ያለብዎት፦**

1. **መጀመሪያ የወረደውን ፋይል ያረጋግጡ** (ፋይሉ እንዳልተነካ ያረጋግጣል)። እያንዳንዱ ልቀት
   `latest.yml`ን ያትማል፣ በውስጡ ያለው የ`sha512` መስክ (base64) የ`OmniRoute.Setup.<version>.exe`
   ጫኚን ይሸፍናል። በPowerShell ውስጥ፣ ጫኚውን ከያዘው አቃፊ፦
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ውጤቱ ከ`latest.yml` → `sha512` ጋር መመሳሰል አለበት። ካልተመሳሰለ ፋይሉን ይሰርዙ እና
   ከ[GitHub የልቀቶች ገጽ](https://github.com/diegosouzapw/OmniRoute/releases) ብቻ እንደገና ያውርዱ።
2. **ይመልሱ + ያግልሉ** — ወደ ኋላ የተመለሱትን ንጥሎች ከማግለያ ይመልሱ እና
   `%LOCALAPPDATA%\Programs\OmniRoute`ን ከፍተሻ ለማግለል ያክሉ (Kaspersky → Settings → Threats and Exclusions)፣
   ከዚያ እንደገና ይጫኑ።

## የNode.js ተኳኋኝነት

### የመግቢያ ገጹ ይበላሻል ወይም የ"Module self-registration" ስህተት ያሳያል

**ምክንያት፦** ከOmniRoute የተፈቀደው ደህንነቱ የተጠበቀ ዝቅተኛው የማስኬጃ ስሪት ውጭ የሆነ የNode.js ስሪት እያስኬዱ ነው። በተለምዶ ይህ የሚከሰተው OmniRoute ከሚፈልገው የደህንነት ማስተካከያ ዝቅተኛ ገደብ በታች የሆነ የቆየ Node 22 ወይም 24 የማስተካከያ ደረጃ ሲያስኬዱ ነው።

**ምልክቶች፦**

- የመግቢያ ገጹ ባዶ ማያ ወይም የአገልጋይ ስህተት ያሳያል
- ኮንሶሉ `Error: Module did not self-register` ወይም ተመሳሳይ የቤተኛ ማያያዣ ስህተቶችን ያሳያል
- ማስኬጃው ከሚደገፈው ደህንነቱ የተጠበቀ መመሪያ ውጭ ከሆነ፣ የመግቢያ ገጹ የNode ስሪትዎን የያዘ **ብርቱካናማ የማስጠንቀቂያ ሰንደቅ** ያሳያል

**መፍትሔ፦**

1. የሚደገፍ የNode.js LTS ልቀት ይጫኑ (የሚመከረው፦ Node.js 24.x)፦
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ስሪትዎን ያረጋግጡ፦ `node --version` በ24.x LTS መስመር ላይ `v24.0.0` ወይም ከዚያ አዲስ ስሪት ማሳየት አለበት
3. OmniRouteን እንደገና ይጫኑ፦ `npm install -g omniroute`
4. እንደገና ያስጀምሩ፦ `omniroute`

> **የሚደገፉ ደህንነታቸው የተጠበቁ ስሪቶች፦** `>=22.22.2 <23` ወይም `>=24.0.0 <27`። Node.js 24.x LTS (Krypton) እና Node.js 26 ሙሉ በሙሉ ይደገፋሉ።

### npm v11+፦ `better-sqlite3` አልተጫነም (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**ምክንያት፦** npm v11 (ከNode.js 24+ ጋር የሚቀርብ) ለአማራጭ
ጥገኛዎች የመጫኛ ስክሪፕቶችን በነባሪነት ያግዳል። `better-sqlite3` በ`optionalDependencies`
ውስጥ ስለተዘረዘረ እና ቤተኛ ማጠናቀር (`node-gyp rebuild`) ስለሚፈልግ፣ npm ያለምንም ማሳወቂያ ይዘለዋል።

**ምልክቶች፦**

- አገልጋዩ ሲጀምር `Cannot find module 'better-sqlite3'` በሚል ስህተት ይበላሻል
- `ls node_modules/better-sqlite3` "No such file or directory" ያሳያል
- `npm ls better-sqlite3` `(empty)` ያሳያል

**መፍትሔ፦**

1. የመጫኛ ስክሪፕቶቹን ያጽድቁና እንደገና ይጫኑ፦
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ወይም ቀድሞ የተጠናቀረውን በእጅ ይጫኑ፦
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. እንደሚሠራ ያረጋግጡ፦ `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS፦ `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**ምክንያት፦** ዓለም አቀፍ `npm install -g omniroute` ከተከናወነ በኋላ፣ በጥቅሉ ውስጥ ያለው የ`better-sqlite3` ቤተኛ ሁለትዮሽ ፋይል በአካባቢው ከሚሠራው የተለየ የስርዓት አወቃቀር ወይም የNode.js ABI የተጠናቀረ ሊሆን ይችላል። ቀድሞ የተገነባው ሁለትዮሽ ፋይል ከአካባቢዎ ጋር በማይዛመድበት ጊዜ፣ ይህ በmacOS (በApple Silicon እና Intel ላይ) የተለመደ ነው።

**ምልክቶች፦**

- አገልጋዩ ሲጀምር ወዲያውኑ በ`dlopen` ስህተት ይቋረጣል
- ስህተቱ `slice is not valid mach-o file` ይዟል
- ሙሉ ምሳሌ፦

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**መፍትሔ — ለአካባቢያዊ ስርዓትዎ እንደገና ይገንቡ (የNode.js ስሪትን ዝቅ ማድረግ አያስፈልግም)፦**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ማስታወሻ፦** ይህ ቤተኛውን ማያያዣ ከአካባቢያዊ የNode.js ስሪትዎ እና የCPU ስርዓት አወቃቀርዎ ጋር በማጣጣም እንደገና ያጠናቅረዋል፣ በዚህም የሁለትዮሽ ፋይሉን አለመዛመድ ይፈታል። በይፋ የሚደገፈው የማስኬጃ ክልል **`>=22.22.2 <23` ወይም `>=24.0.0 <27`** ነው (`SUPPORTED_NODE_RANGE` በ`src/shared/utils/nodeRuntimeSupport.ts` ውስጥ፣ ከ`package.json` `engines` መስክ ጋር የተጣጣመ)። Node.js 24.x LTS (Krypton) እና Node.js 26 ከ`better-sqlite3` v12.x ጋር ሙሉ በሙሉ ይደገፋሉ።

### የአቅራቢ ማረጋገጫ "fetch failed" ያሳያል

**ምክንያት:** የAPI ቁልፍ ማረጋገጫ መጨረሻ ነጥብ (`POST /api/providers/validate`) ቀደም ሲል የፕሮክሲ ውቅረትን ያልፍ ስለነበር፣ የፕሮክሲ ማዞሪያ በሚያስፈልጋቸው አካባቢዎች ውድቀት ያስከትል ነበር።

**መፍትሔ (v3.5.5+):** ይህ አሁን ተስተካክሏል። የአቅራቢ ማረጋገጫ በ`runWithProxyContext` በኩል ይመራል፣ የአቅራቢ-ደረጃ እና ዓለም አቀፍ የፕሮክሲ ቅንብሮችንም በራስ-ሰር ያከብራል።

### የቶከን ጤንነት ማረጋገጫ "fetch failed" በሚል ይወድቃል

**ምክንያት:** የጀርባ OAuth ቶከን እድሳት ለእያንዳንዱ ግንኙነት የፕሮክሲ ውቅረትን አይፈታም ነበር።

**መፍትሔ (v3.5.5+):** የቶከን ጤንነት ማረጋገጫ መርሐግብር አውጪው አሁን እድሳትን ከመሞከሩ በፊት ለእያንዳንዱ ግንኙነት የፕሮክሲ ውቅረትን ይፈታል። ወደ v3.5.5+ ያዘምኑ።

### SOCKS5 ፕሮክሲ "invalid onRequestStart method" ይመልሳል

**ምክንያት:** በNode.js 22 ላይ፣ undici@8 dispatcher ከNode አብሮገነብ `fetch()` አተገባበር ጋር ተኳሃኝ አይደለም።

**መፍትሔ (v3.5.5+):** OmniRoute አሁን የፕሮክሲ dispatcher ገቢር ሲሆን የundiciን የራሱን `fetch()` ተግባር ይጠቀማል፣ ይህም ወጥነት ያለው ባህሪ ያረጋግጣል። ወደ v3.5.5+ ያዘምኑ።

### በWSL ስር ያለ MITM ፕሮክሲ፦ በWindows አስተናጋጅ ላይ ያሉ የዴስክቶፕ መተግበሪያዎች አይጠለፉም

## የCloud ችግሮች

### የCloud Sync ስህተቶች

1. `BASE_URL` ወደ እየሰራ ያለው instanceዎ መጠቆሙን ያረጋግጡ (ለምሳሌ፣ `http://localhost:20128`)
2. `CLOUD_URL` ወደ cloud endpointዎ መጠቆሙን ያረጋግጡ (ለምሳሌ፣ `https://omniroute.dev`)
3. የ`NEXT_PUBLIC_*` እሴቶችን ከserver-side እሴቶች ጋር የተመሳሰሉ አድርገው ያቆዩ

### የCloud `stream=false` ጥያቄ 500 ይመልሳል

**ምልክት፦** streaming ለማይጠቀሙ ጥሪዎች cloud endpoint ላይ `Unexpected token 'd'...` ይታያል።

**ምክንያት፦** client JSON እየጠበቀ ሳለ upstream የSSE payload ይመልሳል።

**ጊዜያዊ መፍትሔ፦** ለቀጥታ የcloud ጥሪዎች `stream=true` ይጠቀሙ። Local runtime የSSE→JSON fallback ያካትታል።

### Cloud እንደተገናኘ ይገልጻል፣ ነገር ግን "Invalid API key" ይላል

1. ከlocal dashboard (`/api/keys`) አዲስ key ይፍጠሩ
2. Cloud syncን ያስኪዱ፦ Enable Cloud → Sync Now
3. የቆዩ/ያልተመሳሰሉ keys አሁንም cloud ላይ `401` ሊመልሱ ይችላሉ

## የDocker ችግሮች

### የDocker IPv6 / ግንኙነት ዳግም መጀመር

<a name="docker-ipv6"></a>

**ምልክቶች፦** `curl http://localhost:20128/v1/models` ሲያስኬዱ `curl: (56) Recv failure: Connection reset by peer` ይመልሳል። Dashboard እና ማረጋገጫ የማይጠይቁ endpoints ይሰራሉ፣ ነገር ግን ማረጋገጫ የሚጠይቁ endpoints አይሰሩም — የauth ችግር ይመስላል፣ ግን አይደለም።

**ምክንያት፦** `docker run -p 20128:20128` በሁለቱም `0.0.0.0` (IPv4) እና `::` (IPv6) ላይ ያትማል፣ ነገር ግን በcontainerው ውስጥ ያለው process በIPv4 ላይ ብቻ ያዳምጣል። `localhost` መጀመሪያ ወደ `::1` በሚፈታባቸው hosts ላይ ግንኙነቱ ከኋላው listener በሌለበት የታተመ IPv6 port ላይ ያርፋል → ግንኙነቱ ዳግም ይጀመራል።

**መፍትሔ፦**

1. **ፈጣን ምርመራ፦** `curl -4 http://localhost:20128/v1/models` ያስኪዱ። ከ`-4` ጋር የሚሰራ ነገር ግን ያለሱ የማይሰራ ከሆነ፣ የIPv6 bind አለመመሳሰል አለዎት።
2. **ቋሚ መፍትሔ፦** በ`docker run` commandዎ ውስጥ `-p 127.0.0.1:20128:20128` በመጠቀም በግልጽ ወደ IPv4 bind ያድርጉ፦
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ይህ IPv4 bindን ያስገድዳል፣ እንዲሁም proxyውን በሁሉም የhost interfaces ላይ ከማጋለጥ ይቆጠባል።

## ማረም

### የLog ፋይሎችን ያንቁ

በ`.env` ፋይልዎ ውስጥ `APP_LOG_TO_FILE=true` ያዘጋጁ። የapplication logs በ`logs/` ስር ይጻፋሉ።
የcall log pipeline በsettings ውስጥ ሲነቃ የrequest artifacts በ`${DATA_DIR}/call_logs/` ስር ይቀመጣሉ።
የpipeline capture ሲነቃ stream chunk payloadsን ለማስቀረት `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` ያዘጋጁ፣ ወይም የartifact መጠን ገደቡን በKB ለመቀየር `CALL_LOG_PIPELINE_MAX_SIZE_KB`ን ያስተካክሉ።

### የProvider ጤናን ያረጋግጡ

```bash
# የጤና dashboard
http://localhost:20128/dashboard/health

# የAPI ጤና ማረጋገጫ
curl http://localhost:20128/api/monitoring/health
```

### የRuntime ማከማቻ

- ዋና state፦ `${DATA_DIR}/storage.sqlite` (providers, combos, aliases, keys, settings)
- አጠቃቀም፦ በ`storage.sqlite` ውስጥ ያሉ SQLite tables (`usage_history`, `call_logs`, `proxy_logs`) + እንደ አማራጭ `${DATA_DIR}/call_logs/`
- የapplication logs፦ `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ሲሆን)
- የcall log artifacts፦ የcall log pipeline ሲነቃ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

በRequest Logs ገጽ ላይ ያለው **Clean history** action `call_logs`ን፣ የቀድሞውን
`request_detail_logs`ን እና local `${DATA_DIR}/call_logs/` artifact directoryን ያጸዳል።

## የCircuit Breaker ችግሮች

### አቅራቢው በOPEN ሁኔታ ላይ ተጣብቋል

የአቅራቢው circuit breaker OPEN ሲሆን፣ የመቆያ ጊዜው እስኪያበቃ ድረስ ጥያቄዎች ይታገዳሉ።

**መፍትሔ፦**

1. ወደ **Dashboard → Settings → Resilience** ይሂዱ
2. ለተጎዳው አቅራቢ የcircuit breaker ካርዱን ያረጋግጡ
3. ሁሉንም breakers ለማጽዳት **Reset All** ን ጠቅ ያድርጉ፣ ወይም የመቆያ ጊዜው እስኪያበቃ ይጠብቁ
4. ዳግም ከማስጀመርዎ በፊት አቅራቢው በእርግጥ ዝግጁ መሆኑን ያረጋግጡ

### አቅራቢው circuit breaker ን በተደጋጋሚ ያስነሳል

አንድ አቅራቢ በተደጋጋሚ ወደ OPEN ሁኔታ ከገባ፦

1. የውድቀት ንድፉን ለማየት **Dashboard → Health → Provider Health** ን ያረጋግጡ
2. ወደ **Settings → Resilience → Provider Profiles** ይሂዱና የውድቀት ገደቡን ይጨምሩ
3. አቅራቢው የAPI ገደቦቹን እንደቀየረ ወይም ዳግም ማረጋገጫ እንደሚፈልግ ያረጋግጡ
4. የlatency telemetry ን ይገምግሙ — ከፍተኛ latency በጊዜ ማብቂያ ምክንያት የሚከሰቱ ውድቀቶችን ሊያስከትል ይችላል

### የተለመዱ የቅርጸት ችግሮች

- **የThinking tags አይታዩም** — ዒላማው አቅራቢ thinking ን የሚደግፍ መሆኑንና የthinking budget ቅንብሩን ያረጋግጡ

- **የ`developer` role አይታወቅም** — በv1.x ተፈትቷል፤ OpenAI ላልሆኑ አቅራቢዎች በራስ-ሰር ወደ `system` ይቀየራል። ይህን አሁንም በv3.x+ ላይ ካዩ፣ እባክዎ issue ያስገቡ።

`budgetSource`, `pressureSeverity`, `countCapEnabled`) ይታያሉ — ማንኛውንም env var ከመንካትዎ በፊት እነዚህን ያረጋግጡ።
Settings → Resilience → Request Queue → Concurrent Requests ይህን አይቆጣጠርም፤ ያ ቅንብር
የተለየ የአቅራቢ ጥያቄ-ወረፋ ዘዴን ይቆጣጠራል።

**ማስተካከያ፦**

1. መጀመሪያ እንደገና ይሞክሩ። ደንበኞች ጥያቄውን ወዲያውኑ
   ከመድገም ይልቅ `Retry-After`ን ማክበር እና የመልሶ መሞከሪያ መዘግየትን መጠቀም አለባቸው።
2. ማንኛውንም ነገር ከማስተካከልዎ በፊት `/api/monitoring/health` → `chatAdmission`ን ያረጋግጡ። `countCapEnabled:
false` እና ሰፊ `maxInflightBytes` ማለት በራስ-ሰር የተሰላው በጀት አስቀድሞ ተግባሩን
   እየፈጸመ ነው ማለት ነው፤ `high`/`critical` የሆነ `pressureSeverity` ማለት አስተናጋጁ በእውነት ማህደረ ትውስታ አንሶታል ማለት ነው —
   ይህ በመግቢያ env var ሊስተካከል አይችልም፤ ተጨማሪ RAM ወይም አነስተኛ የሥራ ጫና ያስፈልገዋል።
3. `/api/monitoring/health` በራስ-ሰር የተሰላው በጀት ለአስተናጋጅዎ በእውነት በጣም አነስተኛ መሆኑን
   ካሳየ ብቻ (ይህ ብርቅ ነው — ቀድሞውኑ ከኮንቴነር እስከ bare-metal ድረስ ይመጣጠናል)፣ ወደ አሮጌው የጥያቄ-ብዛት ገደብ ከመመለስ ይልቅ
   በቀጥታ `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` በመጠቀም ይቀይሩት።

ለዋናዎቹ የመግቢያ ቅንብሮች [የአካባቢ-ተለዋዋጭ ማጣቀሻውን](../reference/ENVIRONMENT.md#4-security--authentication)
ይመልከቱ።

## አማራጭ RAG / LLM የውድቀት ምደባ (16 ችግሮች)

አንዳንድ OmniRoute ተጠቃሚዎች gateway-ውን ከRAG ወይም agent stack-ዎች ፊት ያስቀምጣሉ። በእነዚህ ውቅሮች እንግዳ የሆነ ሁኔታ ማየት የተለመደ ነው፦ OmniRoute ጤናማ ይመስላል (provider-ዎች እየሠሩ ናቸው፣ የrouting profile-ዎች ትክክል ናቸው፣ የrate limit ማንቂያዎች የሉም)፣ ነገር ግን የመጨረሻው መልስ አሁንም የተሳሳተ ነው።

በተግባር እነዚህ ክስተቶች ብዙውን ጊዜ የሚመጡት ከgateway-ው ራሱ ሳይሆን ከታችኛው RAG pipeline ነው።

እነዚያን ውድቀቶች ለመግለጽ የጋራ ቃላትን መጠቀም ከፈለጉ፣ ተደጋጋሚ የሆኑ አሥራ ስድስት RAG / LLM የውድቀት ንድፎችን የሚገልጽ ውጫዊ የMIT ፈቃድ ያለው የጽሑፍ ምንጭ የሆነውን WFGY ProblemMap መጠቀም ይችላሉ። በአጠቃላይ የሚከተሉትን ይሸፍናል፦

- የretrieval መዛባት እና የተበላሹ የcontext ወሰኖች
- ባዶ ወይም ጊዜ ያለፈባቸው index-ዎች እና vector store-ዎች
- በembedding እና semantics መካከል አለመጣጣም
- የprompt ማቀናበር እና የcontext window ችግሮች
- የሎጂክ መፈራረስ እና ከልክ በላይ እርግጠኛ የሆኑ መልሶች
- የረጅም chain እና የagent ቅንጅት ውድቀቶች
- የmulti-agent ማህደረ ትውስታ እና የሚና መዛባት
- የdeployment እና የbootstrap ቅደም ተከተል ችግሮች

ሐሳቡ ቀላል ነው፦

1. የተሳሳተ ምላሽን ሲመረምሩ የሚከተሉትን ይመዝግቡ፦
   - የተጠቃሚውን ተግባር እና ጥያቄ
   - በOmniRoute ውስጥ ያለውን የroute ወይም provider combo
   - በታችኛው ሂደት ላይ ጥቅም ላይ የዋለ ማንኛውንም RAG context (የተገኙ ሰነዶች፣ የtool ጥሪዎች፣ ወዘተ)
2. ክስተቱን ከአንድ ወይም ሁለት WFGY ProblemMap ቁጥሮች (`No.1` … `No.16`) ጋር ያዛምዱ።
3. ቁጥሩን ከOmniRoute log-ዎች አጠገብ በራስዎ dashboard፣ runbook ወይም incident tracker ውስጥ ያስቀምጡ።
4. የRAG stack፣ retriever ወይም routing strategyዎን መቀየር እንዳለብዎት ለመወሰን ተዛማጁን የWFGY ገጽ ይጠቀሙ።

ሙሉው ጽሑፍ እና ተግባራዊ መመሪያዎች እዚህ ይገኛሉ (MIT ፈቃድ፣ ጽሑፍ ብቻ)፦

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

ከOmniRoute በስተጀርባ RAG ወይም agent pipeline-ዎችን የማያስኬዱ ከሆነ ይህን ክፍል ችላ ማለት ይችላሉ።

### የDevin CLI auth ውድቀቶች

**ምልክቶች፦**

- በDevin የሚደገፉ tool-ዎችን ሲጠሩ "Devin CLI አልተገኘም" ወይም "auth አልተሳካም" የሚል መልዕክት
- የCLI runtime ምርመራ `installed=false` የሚል ሪፖርት ያደርጋል

**መንስኤዎች፦**

- `CLI_DEVIN_BIN` ወደሌለ path ያመለክታል
- Devin CLI በhost-ው ላይ አልተጫነም

**መፍትሔ፦**

1. ለplatformዎ Devin CLIን ይጫኑ
2. በ`.env` ውስጥ `CLI_DEVIN_BIN=/usr/local/bin/devin` (ወይም ትክክለኛውን path) ያዘጋጁ
3. OmniRouteን እንደገና ያስጀምሩ እና ከ**Dashboard → CLI Tools** ዳግም ይፈትሹ

### የModel cooldown አለመለቀቅ (በእጅ ዳግም ማስጀመር)

**ምልክቶች፦**

- የማብቂያው ጊዜ ካለፈ በኋላም model በcooldown ውስጥ እንዳለ ተዘርዝሮ ይቆያል
- timestamp-ው ያለፈ ቢሆንም ጥያቄዎች በcombo routing ውስጥ model-ውን አሁንም ይዘሉታል

**በእጅ ዳግም ማስጀመር፦**

- **API፦** ከmanagement auth header-ዎች ጋር `DELETE /api/resilience/model-cooldowns`

### የCommand Code provider ግንኙነት በ403 ይወድቃል

**ምልክቶች፦**

- የCommand Code provider ግንኙነትን ሲፈትሹ 403 ይመለሳል
- provider card-ው አዲስ ከታከለ በኋላ "ያልተፈቀደ" የሚል ያሳያል

**መንስኤ፦** የOAuth ሂደቱ አልተጠናቀቀም (callback አልደረሰም ወይም token-ው አልተቀመጠም)።

**መፍትሔ፦**

### ModelScope ከባድ የ429 cooldown-ዎችን ይመልሳል

**ምልክቶች፦**

- combo routing ከተጠበቀው ቀደም ብሎ ModelScopeን ይዘላል

**መንስኤ፦** ModelScope ለprovider-ው የተለዩ `Retry-After` header-ዎችን ያወጣል። v3.8.0 ለእነዚያ header-ዎች ልዩ አያያዝን ይዞ ይመጣል፤ ስለዚህ የቆዩ version-ዎች እንደ አጠቃላይ የrate-limit ፍንጮች በስህተት ያነቧቸዋል።

**መፍትሔ፦**

- v3.8.0 ወይም ከዚያ በኋላ ባለው version ላይ መሆንዎን ያረጋግጡ
- በ**Settings → Resilience** ስር ያለው `useUpstream429BreakerHints` toggle እንደነቃ ያረጋግጡ

### OMNIROUTE_WS_BRIDGE_SECRET በproduction ውስጥ የለም

**ምልክቶች፦**

- በርቀት production host ላይ ሲያስኬዱ በእያንዳንዱ Codex/Responses WebSocket bridge ጥያቄ ላይ 401 ይመለሳል
- የWebSocket bridge handshake ከግንኙነት በኋላ ወዲያውኑ ይዘጋል

**መንስኤ፦** የ`OMNIROUTE_WS_BRIDGE_SECRET` env var ከproduction environment ጠፍቷል።

**መፍትሔ፦**

1. የዘፈቀደ secret ይፍጠሩ፦ `openssl rand -hex 32`
2. በproduction server env ውስጥ `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>`ን ያዘጋጁ (እንዲሁም ከbridge-ው ጋር በሚገናኝ ማንኛውም client ውስጥ)
3. OmniRouteን እንደገና ያስጀምሩ

### Responses API፦ background mode ወደ synchronous ዝቅ ብሏል

**ምልክቶች፦**

- የሚመዘገብ ማስጠንቀቂያ፦ `background mode degraded to synchronous`
- የ`background: true` ጥያቄ የbackground job handle ከመመለስ ይልቅ መደበኛ synchronous ምላሽ ይመልሳል

**መንስኤ፦** v3.8.0 በResponses API ላይ `background: true`ን ማስጠንቀቂያ እያወጣ ሆን ብሎ ወደ synchronous execution ዝቅ ያደርገዋል። ሙሉ async background execution ወደፊት የሚቀርብ ባህሪ ነው።

**መፍትሔ፦**

- client-ውን `background` ሳይጠቀም እንዲጠራ ያስተካክሉ፣ ወይም
- ሙሉ async background modeን የሚያቀርብ በኋላ የሚወጣ release ይጠብቁ (changelog-ውን ይከታተሉ)

## የዘገየ መነሳት / የዝግጁነት ጊዜ ማብቂያ

CLIው `⚠ Server did not respond within 60s` ብሎ ካሳየ፣ ነገር ግን አገልጋዩ
በትክክል እየሰራ ከሆነ፣ የዝግጁነት ማረጋገጫው የጊዜ ገደብ ለአካባቢዎ በጣም አጭር ነው።

ይህ በWindows (ጸረ-ቫይረስ፣ የፋይል ስርዓት ተከታታዮች) ወይም በመነሳት ጊዜ
ከባድ የሥራ ጫና ባለባቸው ኮንቴይነሮች ላይ በተለምዶ ይከሰታል።

**መፍትሔ — የጊዜ ገደቡን ይጨምሩ፦**

```bash
# በአካባቢ ተለዋዋጭ በኩል (በተደጋጋሚ ማስጀመሮች ላይ ይቆያል)፦
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 ደቂቃዎች
omniroute serve

# በCLI ጥቆማ በኩል (ለአንድ ጊዜ)፦
omniroute serve --ready-timeout 180000
```

ነባሪው 60 000 ms (60 s) ነው። ማስጠንቀቂያው ለመረጃ ብቻ ነው፤ አገልጋዩ
ከበስተጀርባ መነሳቱን ይቀጥላል፣ እና የማስነሳት ሂደቱ ሲጠናቀቅ ተደራሽ ይሆናል።

ስለ `OMNIROUTE_READY_TIMEOUT_MS` ሙሉ ዝርዝሮች [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md)ን
ይመልከቱ።
