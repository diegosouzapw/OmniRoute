### በነፃ አቅራቢዎች ላይ የጥያቄ መጠን ገደብ (429 / 400 / 401)

**ምልክት**፦ `model: "auto"`ን ከነፃ/ማረጋገጫ ከማይጠይቁ አቅራቢዎች (opencode, auggie, ወዘተ) ጋር ሲጠቀሙ፣ ከመልሶች ይልቅ አልፎ አልፎ `HTTP 429`፣ `400` ወይም `401` ያገኛሉ። ተመሳሳዩን መጠየቂያ ከጥቂት ጊዜ በኋላ እንደገና ሲሞክሩ ጥያቄዎቹ ይሳካሉ፣ ነገር ግን አውቶሜሽን (cron ስራዎች፣ ወኪሎች፣ ስክሪፕቶች) በመጀመሪያው ውድቀት ይቋረጣል።

**ዋና መንስኤ**፦ ሦስት እርስ በርሳቸው ገለልተኛ የውድቀት ዓይነቶች ተደራርበው ይከሰታሉ፦

1. **የአቅራቢ የጥያቄ መጠን ገደብ (`429`)**፦ ነፃ ደረጃዎች በእያንዳንዱ የጊዜ መስኮት የኮታ ገደብ ሊያስፈጽሙ ይችላሉ። ብዙ ትይዩ ጥሪዎች በአንድ ጊዜ ሲላኩ ኮታውን ያሟጥጣሉ፤ ስለዚህ የጊዜ መስኮቱ ዳግም እስኪጀመር ድረስ ቀጣዩ ጥያቄ ውድቅ ይደረጋል።
2. **በቀጥታ ማሳለፊያ ውስጥ የተበላሸ ሞዴል (`400`/`401`)**፦ `auto/*` ስብስቦች በካታሎጉ ውስጥ የተመዘገቡ ነገር ግን ንቁ የመግቢያ ማረጋገጫ የሌላቸውን የ`opencode` ቀጥታ ማሳለፊያ ሞዴሎች ሊያካትቱ ይችላሉ (ለምሳሌ `oc/north-mini-code-free` → `401`)። ራስ-ሰር ራውተሩ አንዱን ይሞክራል፣ ይወድቃል፣ እና ወደ አማራጭ መቀየሩ ከመጀመሩ በፊት ስህተቱ ወደ ላይ ይተላለፋል።
3. **የትይዩነት ማጉላት (ጫና ሲኖር `429`)**፦ በርካታ የወኪል/cron ክፍለ ጊዜዎች `auto`ን በአንድ ጊዜ ሲጠቀሙ፣ ጠቅላላ የጥያቄ መጠኑ ነፃ አቅራቢዎች ሊቋቋሙት ከሚችሉት ይበልጣል፤ በዚህም ምክንያት ትክክለኛ ጥሪዎች እንደ አላግባብ አጠቃቀም ምልክት ይደረግባቸዋል።

**የተረጋገጠ መፍትሔ (በማህበረሰቡ የተዘገበ፣ 2026-08-10)**፦ ማዞር፣ ትይዩነት እና ወደ አማራጭ መቀየር በነፃው ደረጃ ላይ ያለውን መለዋወጥ ከውድቀት ይልቅ እንዲቋቋሙ ሦስት የአካባቢ ተለዋዋጮችን ያስተካክሉ፦

```bash
export OMNIROUTE_ROTATE_ON_400=true           # በ400/401 ጊዜ ወደ ሌላ ሞዴል/አቅራቢ ይዝለሉ (የተበላሹ የቀጥታ ማሳለፊያ ሞዴሎችን ይዘላል)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ለከባድ ስራዎች ግልጽ ከፍተኛ የመቀበያ ገደብ (በነባሪ አልተዋቀረም፦ የጥያቄ ብዛት ገደብ የለም፣ ከታች ያለውን ማስታወሻ ይመልከቱ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # ለዝግተኛ የላይኛው ፍሰት አቅራቢዎች የተገደበውን መጠበቂያ ከRATE_LIMIT_MAX_WAIT_MS ነባሪ በላይ ያሳድጉ
```

እነዚህን በOmniRoute የሂደት አካባቢ ውስጥ (daemon፣ ለምሳሌ በLaunchAgent plist ወይም `systemctl edit`) ያዋቅሩ፣ ከዚያ OmniRouteን ዳግም ያስጀምሩ። የማዞሪያ ጠቋሚው ከሁሉ የበለጠ ተጽዕኖ ያለው መቆጣጠሪያ ነው፦ ከባድ ውድቀትን በስብስቡ ውስጥ ባለ ጤናማ አቅራቢ ላይ ወደሚደረግ ግልጽነት ያለው ዳግም ሙከራ ይቀይረዋል።

**ማስታወሻ**፦ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ምን ያህል ከባድ — ረጅም አውድ ያላቸው — ጥያቄዎች በአንድ ጊዜ እንደሚሰሩ ይገድባል፤ ገደቡ የመቀበያ በር እንጂ የአቅራቢ የጥያቄ መጠን ገዳቢ አይደለም። **#503-fanout ማሻሻያ፦** ይህ var ከአሁን በኋላ በነባሪ አይዋቀርም (አሁን የሚተገበረው ከላይ እንደተገለጸው በግልጽ ሲዋቀር ብቻ ነው) — በምትኩ የከባድ ስራዎች መቀበያ ከአስተናጋጁ ትክክለኛ የማህደረ ትውስታ ገደብ ጋር ራሱን በሚመጥን፣ በራስ-ሰር በሚወጣ የባይት በጀት (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ይገደባል፤ ስለዚህ አዲስ ጭነት ይህን var ምንም ሳያዋቅር በጣም ያነሱ `503 chat_admission_busy` ውድቅ ማድረጎችን ማየት ይገባዋል፤ እዚህ በግልጽ ማዋቀሩ አሁንም በሰነዱ እንደተገለጸው በትክክል ይሰራል። ግልጽ የባይት በጀት ለውጦች ከ8 MiB–2 GiB ባለው ክልል ውስጥ ይገደባሉ። `413 body_exceeds_budget` ጊዜያዊ አይደለም፦ ያንን የባይት በጀት ያሳድጉ፣ `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`ን ይቀንሱ፣ ወይም የሂደቱን የማህደረ ትውስታ ገደብ ያሳድጉ። የ`inflight_bytes_budget` ጫና መቀነስ ጊዜያዊ የሀብት ፉክክር ሲሆን እንደገና ሊሞከር ይችላል። በእያንዳንዱ አቅራቢ ላይ ያለው የጥያቄ መጠን ገደብ (`open-sse/services/rateLimitManager.ts`) በተናጠል በ`RATE_LIMIT_MAX_WAIT_MS`፣ `RATE_LIMIT_MAX_QUEUE_DEPTH` እና `RATE_LIMIT_AUTO_ENABLE` ይተዳደራል — `.env.example`ን ይመልከቱ።

**መስራቱን እንዴት ማረጋገጥ እንደሚቻል**፦ agent/cronዎን በፈጣን ቅደም ተከተል ሁለት ጊዜ ያስኪዱትና ሁለቱም በተሳካ ሁኔታ መጠናቀቃቸውን ያረጋግጡ። ከማስተካከያው በፊት፣ ሁለተኛው ማስኬድ በተለምዶ `429`/`401` ስህተት ይፈጥራል። ከማስተካከያው በኋላ፣ ውድቀቶች (ካሉ) ተጠቃሚው ሳያስተውል እንደገና ይሞከራሉ፣ ጥሪውም ይጠናቀቃል። እንዲሁም `curl /monitoring/health` በማስኬድ በአቅራቢ ግንኙነቶች ላይ ያለውን `rateLimitedUntil` መስክ እና ለተጎዱት አቅራቢዎች `circuitBreakers.providerBreakers[].state`ን መከታተል ይችላሉ — ሁኔታው ከ`CLOSED`፣ `DEGRADED`፣ `OPEN` ወይም `HALF_OPEN` አንዱ ነው (`src/shared/utils/circuitBreaker.ts`ን ይመልከቱ)፤ ደጋግሞ የሚወድቅ አቅራቢ፣ ዳግም ማስጀመሪያ ጊዜው የሙከራ ጥሪን እስኪፈቅድ (`HALF_OPEN`) ድረስ፣ ከ`CLOSED → DEGRADED → OPEN` ይሸጋገራል።

**አሁንም 429 ካዩ**፦ ለዚያ አቅራቢ ገቢር የሆነው መለያ _ኮታውን_ በእውነት አሟጧል (የጥያቄ ፍጥነት ገደቡን ብቻ አይደለም)። በOmniRoute ዳሽቦርድ → Providers → Accounts ውስጥ ለተመሳሳዩ አቅራቢ ሁለተኛ መለያ ያክሉ፣ ወይም ሌላ ነፃ አቅራቢን (ለምሳሌ `routeway`፣ `auggie`) ይቀላቅሉ። ማዞር የሚረዳው ጊዜያዊ የጥያቄ ፍጥነት/400/401 ስህተቶችን ለመቋቋም ብቻ ነው፤ የኮታ ሙሉ በሙሉ መሟጠጥ ሁለተኛ ማረጋገጫ ወይም የተለየ አቅራቢ ይፈልጋል።

**በምስል ሞዴሎች (`auto/vision`፣ `bazaarlink/*`) ላይ 403 ካዩ**፦ የተገናኘው መለያ ምስልን የሚያካትት የሚከፈልበት ዕቅድ የለውም፣ ወይም API keyው በቂ ፈቃዶች የሉትም። በአቅራቢው ዳሽቦርድ ውስጥ የkeyው ወሰን ምስል/መልቲሞዳልን እንደሚያካትት ያረጋግጡ፣ ወይም የሚከፈልበት ደረጃ ያለው መለያ ያገናኙና የምስል መድረሻ አድርገው ያቆዩት።

## የ npm install ማስጠንቀቂያዎች (ERESOLVE / peer / deprecated)

`npm install -g omniroute` ሲያስኬዱ እንደ `npm warn ERESOLVE`፣ የ peer-dependency ማሳወቂያዎች እና `deprecated` መልዕክቶች ያሉ ብዙ ማስጠንቀቂያዎችን ሊያዩ ይችላሉ። **እነዚህ የሚጠበቁ እና ጉዳት የሌላቸው ናቸው።** በውጤቱ ውስጥ `added <N> packages` ካዩ ጭነቱ በተሳካ ሁኔታ ተጠናቋል።

የ peer-dependency መፍትሔ ማስጠንቀቂያዎችን ለማስቀረት፣ በ OmniRoute የሚደገፈውን የጭነት ቅርጸት ይጠቀሙ፦

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` የሚያስቀረው `ERESOLVE` እና የ peer-dependency ማሳወቂያዎችን ብቻ ነው። የማቋረጥ ማሳወቂያዎች ከተዘዋዋሪ የሶስተኛ ወገን ፓኬጆች ስለሚመጡ መታየታቸውን ይቀጥላሉ፤ እነዚህም ጭነቱ እንዳልተሳካ አያመለክቱም።

ማስጠንቀቂያዎቹ የሚመጡት OmniRoute በማይቆጣጠራቸው የሶስተኛ ወገን ፓኬጆች ውስጥ ካሉ ጊዜ ያለፈባቸው የ peer-dependency ክልሎች ነው፦

1. **`marked-terminal`፣ `marked >=1 <16`ን ይፈልጋል፣ `marked@18` ግን ተገኝቷል** — በተግባር በሚገባ ይሠራል፤ የ upstream peer ክልሉ ጊዜ ያለፈበት ብቻ ነው።
2. **`deprecated prebuild-install@7.1.3`** — ተዘዋዋሪ የ native-binary ማውረጃ ረዳት ነው። የተወሰነውን `wreq-js` transport binding ለመጫን
   ጥቅም ላይ አይውልም፣ እንዲሁም የ web-cookie provider transport ማዋቀር
   እንዳልተሳካ አያመለክትም።

**ምንም እርምጃ አያስፈልግም** — የ upstream ፓኬጆችን fork ሳያደርጉ ማስጠንቀቂያዎቹን ሙሉ በሙሉ ማስቀረት አይቻልም።

## የታገዱ npm install-scripts ማስጠንቀቂያ (ዓለም አቀፍ ጭነት)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` ሲያስኬዱ፣ አዳዲስ የ npm ስሪቶች (v11+ እና v12+) የፓኬጅ lifecycle scriptsን በነባሪነት ያግዳሉ፣ እንዲሁም የ install-scripts ማስጠንቀቂያ ያሳያሉ፦

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### ይህን ማስጠንቀቂያ ችላ ማለት ይቻላል?

**በከፊል፣ ነገር ግን scripts ሳይኖሩ ማስኬድ አይመከርም።** OmniRoute ችግርን በሰላም የሚቋቋሙ አማራጮችን ያካትታል፦ native `better-sqlite3` bindings ከ standalone bundle መጫን ካልቻሉ፣ መተግበሪያው እንደ `node:sqlite` ወይም `sql.js` ያሉ አማራጭ driversን ይጠቀማል ([የ SQLite Runtime መፍትሔ](../ops/SQLITE_RUNTIME.md)ን ይመልከቱ)። server አሁንም ይጀምራል፣ ነገር ግን እንደ `sql.js` ባሉ የ WASM አማራጮች ላይ ማስኬድ የ SQLite WAL (Write-Ahead Logging) ሁነታን ያሰናክላል፣ እንዲሁም የማህደረ ትውስታ እና የ disk-sync ተጨማሪ ወጪን ይጨምራል።

### በእርግጥ የሚያስፈልጉት scripts የትኞቹ ናቸው?

ሁሉም የታገዱ scripts OmniRouteን ለማስኬድ አስፈላጊ አይደሉም፦

- **አስፈላጊ (`omniroute`፣ `better-sqlite3`)፦** OmniRoute ከ Next.js standalone application bundle (`dist/`) ይሠራል። በጭነት ጊዜ፣ npm ከ host ጋር የሚስማማውን native SQLite driver ወደ ከፍተኛ ደረጃው `node_modules/better-sqlite3/` ያወርዳል ወይም ያጠናቅራል። ከዚያም የ OmniRoute `postinstall` script (`scripts/build/postinstall.mjs`) እነዚህን ከ host ጋር የሚስማሙ binaries ያረጋግጣል እና standalone server ሊደርስባቸው እንዲችል ወደ `dist/node_modules/` ይቀዳቸዋል። የ `omniroute` postinstall script ከታገደ፣ ይህ የመቅዳት ደረጃ ይዘለላል።
- **አማራጭ/ተዘዋዋሪ (`keytar`፣ `@parcel/watcher`፣ `@swc/core`፣ `protobufjs`፣ `esbuild`)፦** እነዚህ የ build ረዳቶች፣ watcher መሣሪያዎች ወይም የስርዓት keychain መገልገያዎች ናቸው። መፍቀድ የ build ማስጠንቀቂያዎችን ይከላከላል፣ ነገር ግን ለዋናው የ routing ተግባር አያስፈልጉም።
- **የተገለለ (`onnxruntime-node`)፦** ለአካባቢያዊ AI embeddings አማራጭ dependency ሲሆን OmniRoute እንዲሠራ **አያስፈልግም**። የእሱ postinstall script ከ NuGet ወደ ~300MB የሚሆኑ የ CUDA ግብዓቶችን ያወርዳል፤ በሚደገፍ hardware ላይ አካባቢያዊ ONNX accelerationን ለመጠቀም በግልጽ ካላሰቡ በ allow-list ውስጥ አያካትቱት።

### የሚመከር መፍትሔ

በዓለም አቀፍ ጭነት ወቅት አስፈላጊዎቹን install scripts ለመፍቀድ እና ማስጠንቀቂያዎችን ለማስቀረት፣ ለ OmniRoute እና ለ native dependenciesዎቹ `--allow-scripts`ን ያስተላልፉ፦

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

በአማራጭ፣ ይህን በተጠቃሚ መለያዎ ላይ ለሁሉም ዓለም አቀፍ ጭነቶች በቋሚነት ለማዋቀር፦

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### ጭነትዎን ያረጋግጡ

ከጭነት በኋላ native bindings እና runtime environment ጤናማ መሆናቸውን ለማረጋገጥ አብሮገነብ diagnostic toolን ያስኪዱ፦

```bash
omniroute doctor
```

## የጸረ-ቫይረስ የተሳሳቱ ማስጠንቀቂያዎች

### Avast/AVG `README.md`ን በ`MD:HttpRequest-inf[Susp]` ምክንያት ማግለያ ውስጥ ያስገባል

**ይህ የተሳሳተ ማስጠንቀቂያ ነው። ምንም ነገር በቫይረስ አልተበከለም፣ እና ምንም እርምጃ አያስፈልግም።**

Avast እና AVG ብዙ HTTP ጥያቄዎችን የሚመስሉ አገናኞችን የያዙ ግልጽ-ጽሑፍ/Markdown ፋይሎችን የሚጠቁም ሂዩሪስቲክ ያስኬዳሉ። የOmniRoute `README.md` በnpm ጥቅሉ ውስጥ ተካትቶ ይላካል (በ`package.json` → `files` ውስጥ ተዘርዝሯል)፣ ስለዚህ በዓለም አቀፍ ጭነት ጊዜ በ`node_modules/omniroute/README.md` ላይ ይቀመጣል — እንዲሁም ~15 የ`http://localhost:20128/...` ምሳሌዎችን (የMCP HTTP/SSE የመዳረሻ ነጥቦችን፣ የA2A `.well-known` URLን፣ እና የ`curl` ቅንጥቦችን) ይዟል። ይህ የአገናኞች ጥግግት ሂዩሪስቲኩን ለማስነሳት በቂ ነው።

ይህ በቅርቡ ብቻ የጀመረ ከሆነ፦ የፋይሉ ዓይነት አልተለወጠም። README የመዳረሻ ነጥቦች ሰንጠረዡን አስፋፍቷል (MCP HTTP + SSE + A2A ተጨምረዋል) እና ተጨማሪ የ`curl` ምሳሌዎች ተካትተዋል፣ ይህም ከገደቡ እንዲያልፍ አድርጎታል።

ፋይሉ ምንም ሊፈጸም የሚችል ይዘት የሌለው ንቁ ያልሆነ ሰነድ ነው። ከማግለያው በደህና መመለስ ይችላሉ።

**ማድረግ ያለብዎት፦**

1. **ማሳወቂያዎቹን ያቁሙ** — የጭነት ማውጫውን በጸረ-ቫይረስዎ ውስጥ ከቅኝት ያስቀሩ (Avast፦ Settings → Exceptions)፣ የዓለም አቀፍ `node_modules` ዱካዎን እና/ወይም የOmniRoute ውሂብ ማውጫን (`~/.omniroute/`) ያክሉ።
2. **የተሳሳተውን ማስጠንቀቂያ ሪፖርት ያድርጉ** — <https://www.avast.com/false-positive-file-form.php>፣ ማግለያ ውስጥ የገባውን `README.md` በማያያዝ። ችግሩ የአቅራቢው ሂዩሪስቲክ ለጽሑፍ ፋይል ከመጠን በላይ ምላሽ መስጠቱ ስለሆነ፣ ይህ ሁሉንም ሰው የሚጠቅም መፍትሔ ነው።

**ይህን በእኛ በኩል ለምን “አናስተካክለውም”፦** ምሳሌዎቹ በሙሉ `http://localhost` ናቸው፣ እና localhost ከራስ-የተፈረሙ ሰርተፊኬቶች ችግር ውጭ `https` መሆን አይችልም። የአንድን አቅራቢ ሂዩሪስቲክ ለማለፍ ሰነዶቹን ማዛባት፣ የቅኝት መሣሪያውን ስህተት ለማርካት ሲባል ሁሉንም አንባቢ ይጎዳል።

### Kaspersky የDesktop መተግበሪያውን `PDM:Trojan.Win32.Generic` ብሎ ይጠቁማል

**ይህ ከባህሪያዊ ሂዩሪስቲክ የመጣ የተሳሳተ ማስጠንቀቂያ ነው። ምንም ነገር በቫይረስ አልተበከለም።** የKaspersky `PDM:` ቅድመ ቅጥያ፣ ውሳኔው ከሚታወቁ ማልዌሮች ጋር በማዛመድ ሳይሆን ጫኚው _ምን እንደሚያደርግ_ ከሚገመግመው Proactive Defense Module (System Watcher) መምጣቱን ያመለክታል። ሲነሳ Kaspersky መላውን ጭነት “ወደኋላ ይመልሳል” — አስቀድሞ የጻፋቸውን ፋይሎች ይሰርዛል — በዚህም ምክንያት መተግበሪያው የተበላሸ ወይም የጠፋ ይሆናል።

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` እና
  `workerProcessEntry.js` — [Playwright](https://playwright.dev)፣ በመተግበሪያ ውስጥ ለአቅራቢ መግቢያ እና በአሳሽ ለሚደገፍ ውይይት የሚያገለግለው የአሳሽ ራስ-ሰር አሠራር ቤተ-መጻሕፍት።

**ማድረግ ያለብዎት፦**

1. **መጀመሪያ ማውረድዎን ያረጋግጡ** (ፋይሉ እንዳልተቀየረ ያረጋግጣል)። እያንዳንዱ ልቀት `latest.yml`ን ያትማል፣ በውስጡ ያለው `sha512` መስክ (base64) የ`OmniRoute.Setup.<version>.exe` ጫኚን ይሸፍናል። በPowerShell፣ ጫኚውን ከያዘው አቃፊ ውስጥ፦
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ውጤቱ ከ`latest.yml` → `sha512` ጋር መመሳሰል አለበት። ካልተመሳሰለ ፋይሉን ይሰርዙ እና ከ[GitHub ልቀቶች ገጽ](https://github.com/diegosouzapw/OmniRoute/releases) ብቻ እንደገና ያውርዱ።
2. **ይመልሱ + ከቅኝት ያስቀሩ** — ወደኋላ የተመለሱትን ንጥሎች ከማግለያው ይመልሱ እና ለ`%LOCALAPPDATA%\Programs\OmniRoute` ከቅኝት ማስቀሪያ ያክሉ (Kaspersky → Settings → Threats and Exclusions)፣ ከዚያ እንደገና ይጫኑ።
3. **የተሳሳተውን ማስጠንቀቂያ ሪፖርት ያድርጉ** — <https://opentip.kaspersky.com/>። በተጠቃሚዎች የሚቀርቡ የተሳሳተ ማስጠንቀቂያ ሪፖርቶች ወደ የተፈቀዱ ዝርዝር የመጨመሩን ሂደት በእርግጥ ያፋጥናሉ።

### የመግቢያ ገጹ ይበላሻል ወይም "Module self-registration" ስህተት ያሳያል

**ምክንያት፦** ከOmniRoute ከተፈቀደው የደህንነት ማስኬጃ ዝቅተኛ ገደብ ውጪ የሆነ የNode.js ስሪት እያስኬዱ ነው። በጣም የተለመደው ሁኔታ፣ OmniRoute ከሚጠይቀው የታረመ የደህንነት ዝቅተኛ ገደብ በታች የሆነ የቆየ የNode 22 ወይም 24 ጥገና ስሪት ማስኬድ ነው።

**ምልክቶች፦**

- የመግቢያ ገጹ ባዶ ማያ ገጽ ወይም የአገልጋይ ስህተት ያሳያል
- ኮንሶሉ `Error: Module did not self-register` ወይም ተመሳሳይ የኔቲቭ ባይንዲንግ ስህተቶችን ያሳያል
- ማስኬጃው ከሚደገፈው የደህንነት ፖሊሲ ውጪ ከሆነ፣ የመግቢያ ገጹ የNode ስሪትዎን የያዘ **ብርቱካናማ የማስጠንቀቂያ ሰንደቅ** ያሳያል

**መፍትሔ፦**

1. የሚደገፍ የNode.js LTS ልቀት ይጫኑ (የሚመከረው፦ Node.js 24.x)፦
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ስሪትዎን ያረጋግጡ፦ `node --version` በ24.x LTS መስመር ላይ `v24.0.0` ወይም ከዚያ በላይ ማሳየት አለበት
3. OmniRouteን እንደገና ይጫኑ፦ `npm install -g omniroute`
4. እንደገና ያስጀምሩ፦ `omniroute`

> **የሚደገፉ ደህንነታቸው የተጠበቁ ስሪቶች፦** `>=22.22.2 <23` ወይም `>=24.0.0 <27`። Node.js 24.x LTS (Krypton) እና Node.js 26 ሙሉ በሙሉ ይደገፋሉ።

### npm v11+፦ `better-sqlite3` አልተጫነም (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**ምክንያት፦** npm v11 (ከNode.js 24+ ጋር የሚቀርብ) እንደ ነባሪ ለአማራጭ
ጥገኞች የመጫኛ ስክሪፕቶችን ያግዳል። `better-sqlite3` በ`optionalDependencies`
ውስጥ ስለተዘረዘረ እና ኔቲቭ ማጠናቀር (`node-gyp rebuild`) ስለሚያስፈልገው፣ npm ያለምንም ማሳወቂያ ይዘለዋል።

**ምልክቶች፦**

- አገልጋዩ ሲጀምር `Cannot find module 'better-sqlite3'` በሚለው ስህተት ይበላሻል
- `ls node_modules/better-sqlite3` "No such file or directory" ያሳያል
- `npm ls better-sqlite3` `(empty)` ያሳያል

**መፍትሔ፦**

1. የመጫኛ ስክሪፕቶቹን ያጽድቁ እና እንደገና ይጫኑ፦
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ወይም ቀድሞ የተገነባውን ጥቅል በእጅ ይጫኑ፦
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. እንደሚሠራ ያረጋግጡ፦ `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS፦ `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**ምክንያት፦** ዓለም አቀፍ `npm install -g omniroute` ከተከናወነ በኋላ፣ በጥቅሉ ውስጥ ያለው የ`better-sqlite3` ኔቲቭ ባይነሪ በአካባቢው እየሰራ ካለው የተለየ የስርዓት አወቃቀር ወይም የNode.js ABI ሊኖረው ይችላል። ቀድሞ የተገነባው ባይነሪ ከአካባቢዎ ጋር በማይዛመድበት ጊዜ ይህ በmacOS (በApple Silicon እና Intel ላይ) የተለመደ ነው።

**ምልክቶች፦**

- አገልጋዩ ሲጀምር ወዲያውኑ በ`dlopen` ስህተት ይቋረጣል
- ስህተቱ `slice is not valid mach-o file` የሚለውን ይዟል
- ሙሉ ምሳሌ፦

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**መፍትሔ — ለአካባቢዎ እንደገና ይገንቡ (የNode.js ስሪትን ዝቅ ማድረግ አያስፈልግም)፦**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ማስታወሻ፦** ይህ ኔቲቭ ባይንዲንጉን ከአካባቢያዊው የNode.js ስሪት እና CPU አወቃቀር ጋር እንደገና ያጠናቅረዋል፣ በዚህም የባይነሪ አለመዛመዱን ይፈታል። በይፋ የሚደገፈው የማስኬጃ ክልል **`>=22.22.2 <23` ወይም `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` በ`src/shared/utils/nodeRuntimeSupport.ts` ውስጥ፣ ከ`package.json` `engines` መስክ ጋር የተጣጣመ) ነው። Node.js 24.x LTS (Krypton) እና Node.js 26 ከ`better-sqlite3` v12.x ጋር ሙሉ በሙሉ ይደገፋሉ።

### የአቅራቢ ማረጋገጫ "fetch failed" ያሳያል

**ምክንያት፦** የAPI ቁልፍ ማረጋገጫ መጨረሻ ነጥብ (`POST /api/providers/validate`) ከዚህ ቀደም የፕሮክሲ ውቅረትን ያልፍ ነበር፤ ይህም በፕሮክሲ በኩል ማስተላለፍን በሚፈልጉ አካባቢዎች ውስጥ ብልሽት ያስከትል ነበር።

**መፍትሔ (v3.5.5+)፦** ይህ አሁን ተስተካክሏል። የአቅራቢ ማረጋገጫ በ`runWithProxyContext` በኩል የሚተላለፍ ሲሆን፣ የአቅራቢ-ደረጃ እና ዓለም አቀፍ የፕሮክሲ ቅንብሮችን በራስ-ሰር ያከብራል።

### የቶከን ጤና ፍተሻ "fetch failed" በሚል ይሳካል

**ምክንያት፦** የጀርባ OAuth ቶከን እድሳት ለእያንዳንዱ ግንኙነት የፕሮክሲ ውቅረትን አይወስንም ነበር።

**መፍትሔ (v3.5.5+)፦** የቶከን ጤና ፍተሻ መርሐግብር አስኪያጁ አሁን ለማደስ ከመሞከሩ በፊት ለእያንዳንዱ ግንኙነት የፕሮክሲ ውቅረትን ይወስናል። ወደ v3.5.5+ ያዘምኑ።

### SOCKS5 ፕሮክሲ "invalid onRequestStart method" ይመልሳል

**ምክንያት፦** በNode.js 22 ላይ፣ የundici@8 ማሰራጫ ከNode አብሮገነብ `fetch()` አተገባበር ጋር ተኳሃኝ አይደለም።

## የCloud ችግሮች

### የCloud ማመሳሰል ስህተቶች

1. `BASE_URL` ወደ እየሰራ ያለው instanceዎ መጠቆሙን ያረጋግጡ (ለምሳሌ፣ `http://localhost:20128`)
2. `CLOUD_URL` ወደ cloud endpointዎ መጠቆሙን ያረጋግጡ (ለምሳሌ፣ `https://omniroute.dev`)
3. የ`NEXT_PUBLIC_*` እሴቶችን ከserver-side እሴቶች ጋር አመሳስለው ያቆዩ

### የCloud `stream=false` ጥሪ 500 ይመልሳል

**ምልክት፦** በcloud endpoint ላይ streaming ላልሆኑ ጥሪዎች `Unexpected token 'd'...` የሚል ስህተት ይታያል።

**ምክንያት፦** clientው JSON ሲጠብቅ upstreamው የSSE payload ይመልሳል።

**ጊዜያዊ መፍትሔ፦** ለቀጥታ የcloud ጥሪዎች `stream=true` ይጠቀሙ። የአካባቢው runtime የSSE→JSON fallback ያካትታል።

### Cloud እንደተገናኘ ይገልጻል፣ ግን "ልክ ያልሆነ API key" ይላል

## የDocker ችግሮች

### የDocker IPv6 / የግንኙነት ዳግም መጀመር

<a name="docker-ipv6"></a>

**ምልክቶች፦** `curl http://localhost:20128/v1/models` ትዕዛዙ `curl: (56) Recv failure: Connection reset by peer` ይመልሳል። Dashboardውና ማረጋገጫ የማይጠይቁ endpoints ይሰራሉ፣ ነገር ግን ማረጋገጫ የሚጠይቁ endpoints አይሰሩም — የማረጋገጫ ችግር ይመስላል፣ ግን አይደለም።

**ምክንያት፦** `docker run -p 20128:20128` በሁለቱም `0.0.0.0` (IPv4) እና `::` (IPv6) ላይ ያትማል፣ ነገር ግን containerው ውስጥ ያለው process በIPv4 ላይ ብቻ ያዳምጣል። `localhost` መጀመሪያ ወደ `::1` በሚፈታባቸው hosts ላይ፣ ግንኙነቱ ከኋላው listener በሌለበት የታተመው IPv6 port ላይ ይደርሳል → ግንኙነቱ ዳግም ይጀመራል።

**መፍትሔ፦**

1. **ፈጣን ምርመራ፦** `curl -4 http://localhost:20128/v1/models` ያስኪዱ። ከ`-4` ጋር የሚሰራ ነገር ግን ያለሱ የማይሰራ ከሆነ፣ የIPv6 bind አለመዛመድ አለብዎት።
2. **ቋሚ መፍትሔ፦** በ`docker run` ትዕዛዝዎ ውስጥ `-p 127.0.0.1:20128:20128` በመጠቀም IPv4ን በግልጽ bind ያድርጉ፦
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ይህ IPv4 bindን ያስገድዳል፣ እንዲሁም proxyው በሁሉም የhost interfaces ላይ እንዳይጋለጥ ያደርጋል።

## ማረም

### የLog ፋይሎችን ማንቃት

በ`.env` ፋይልዎ ውስጥ `APP_LOG_TO_FILE=true`ን ያዘጋጁ። የመተግበሪያ logs በ`logs/` ሥር ይጻፋሉ።
የcall log pipeline በቅንብሮች ውስጥ ሲነቃ፣ የጥያቄ artifacts በ`${DATA_DIR}/call_logs/` ሥር ይከማቻሉ።
የpipeline capture ሲነቃ፣ የstream chunk payloadsን ለማስቀረት `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false`ን ያዘጋጁ፣ ወይም የartifact ገደቡን በKB ለመቀየር `CALL_LOG_PIPELINE_MAX_SIZE_KB`ን ያስተካክሉ።

### የProvider ጤንነትን መፈተሽ

```bash
# የጤንነት dashboard
http://localhost:20128/dashboard/health

# የAPI ጤንነት ማረጋገጫ
curl http://localhost:20128/api/monitoring/health
```

### የRuntime ማከማቻ

- ዋና ሁኔታ፦ `${DATA_DIR}/storage.sqlite` (providers, combos, aliases, keys, settings)
- አጠቃቀም፦ በ`storage.sqlite` ውስጥ ያሉ SQLite tables (`usage_history`, `call_logs`, `proxy_logs`) + አማራጭ `${DATA_DIR}/call_logs/`
- የመተግበሪያ logs፦ `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ሲሆን)
- የcall log artifacts፦ የcall log pipeline ሲነቃ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

በRequest Logs ገጽ ላይ ያለው **ታሪክን አጽዳ** ድርጊት `call_logs`ን፣ የቆየውን
`request_detail_logs`ን እና የአካባቢውን `${DATA_DIR}/call_logs/` artifact directory ያጸዳል።

## የCircuit Breaker ችግሮች

### አቅራቢው በOPEN ሁኔታ ላይ ተጣብቋል

የአቅራቢው circuit breaker OPEN በሚሆንበት ጊዜ፣ የማቀዝቀዣ ጊዜው እስኪያበቃ ድረስ ጥያቄዎች ይታገዳሉ።

**መፍትሔ፦**

1. ወደ **ዳሽቦርድ → ቅንብሮች → ጥንካሬ** ይሂዱ
2. ለችግሩ የተጋለጠውን አቅራቢ የcircuit breaker ካርድ ይመልከቱ
3. ሁሉንም breaker-ዎች ለማጽዳት **ሁሉንም ዳግም አስጀምር** የሚለውን ጠቅ ያድርጉ፣ ወይም የማቀዝቀዣ ጊዜው እስኪያበቃ ይጠብቁ
4. ዳግም ከማስጀመርዎ በፊት አቅራቢው በእርግጥ እንደሚገኝ ያረጋግጡ

### አቅራቢው circuit breaker-ን በተደጋጋሚ ያስነሳል

አቅራቢው በተደጋጋሚ ወደ OPEN ሁኔታ የሚገባ ከሆነ፦

1. የውድቀቱን ንድፍ ለማየት **ዳሽቦርድ → ጤና → የአቅራቢ ጤና**ን ይመልከቱ
2. ወደ **ቅንብሮች → ጥንካሬ → የአቅራቢ መገለጫዎች** በመሄድ የውድቀት ገደቡን ይጨምሩ
3. አቅራቢው የAPI ገደቦችን እንደቀየረ ወይም እንደገና ማረጋገጫ እንደሚፈልግ ያረጋግጡ
4. የመዘግየት ቴሌሜትሪውን ይገምግሙ — ከፍተኛ መዘግየት በጊዜ ማብቂያ ላይ የተመሰረቱ ውድቀቶችን ሊያስከትል ይችላል

- **የ`developer` ሚና አይታወቅም** — በv1.x ውስጥ ተፈትቷል፤ OpenAI ላልሆኑ አቅራቢዎች በራስ-ሰር ወደ `system` ይቀየራል። ይህን በv3.x+ ላይ አሁንም የሚያዩ ከሆነ፣ እባክዎ ችግር ሪፖርት ያቅርቡ።
- **`json_schema` ከGemini ጋር አይሰራም** — በv1.x ውስጥ ተፈትቷል፤ `response_format` አሁን ወደ የGemini `responseMimeType` + `responseSchema` ይቀየራል። ይህን በv3.x+ ላይ አሁንም የሚያዩ ከሆነ፣ እባክዎ ችግር ሪፖርት ያቅርቡ።

## የጽናት ቅንብሮች

### ራስ-ሰር የፍጥነት ገደብ አለመጀመር

- ራስ-ሰር የፍጥነት ገደብ የሚተገበረው በAPI ቁልፍ አቅራቢዎች ላይ ብቻ ነው (በOAuth/የደንበኝነት ምዝገባ ላይ አይደለም)
- **ቅንብሮች → ጽናት → የአቅራቢ መገለጫዎች** ውስጥ ራስ-ሰር የፍጥነት ገደብ መንቃቱን ያረጋግጡ
- አቅራቢው `429` የሁኔታ ኮዶችን ወይም `Retry-After` ራስጌዎችን ይመልስ እንደሆነ ያረጋግጡ

### ኤክስፖነንሻል የድጋሚ ሙከራ መዘግየትን ማስተካከል

የአቅራቢ መገለጫዎች እነዚህን ቅንብሮች ይደግፋሉ፦

- **መሠረታዊ መዘግየት** — ከመጀመሪያው ውድቀት በኋላ ያለው የመጀመሪያ የመጠበቂያ ጊዜ (ነባሪ፦ 1s)
- **ከፍተኛ መዘግየት** — ከፍተኛው የመጠበቂያ ጊዜ ገደብ (ነባሪ፦ 30s)
- **ማባዣ** — በእያንዳንዱ ተከታታይ ውድቀት መዘግየቱ በምን ያህል እንደሚጨምር (ነባሪ፦ 2x)

### የተመሳሳይ ጊዜ ጥያቄዎች መጨናነቅን መከላከል

ብዙ በአንድ ጊዜ የሚከናወኑ ጥያቄዎች የፍጥነት ገደብ የተጣለበትን አቅራቢ ሲደርሱ፣ OmniRoute ጥያቄዎችን በተራ ለማስኬድና ተከታታይ ውድቀቶችን ለመከላከል mutex + ራስ-ሰር የፍጥነት ገደብን ይጠቀማል። ይህ ለAPI ቁልፍ አቅራቢዎች በራስ-ሰር ይከናወናል።

### የውይይት ጥያቄዎች በ503 / chat_admission_busy ይወድቃሉ

**ምልክቶች፦**

- የውይይት ማጠናቀቂያዎች endpoint የስህተት ኮዱ
  `chat_admission_busy` የሆነ እንደገና ሊሞከር የሚችል `503` ምላሽ ይመልሳል።
- ምላሹ `Retry-After`ን ያካትታል። ከ#12135 ጀምሮ እሴቱ ከታየው
  የአቅም አጠቃቀም ይወሰዳል — ጥያቄው አስቀድሞ ከጠበቀው `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` መስኮት
  እና አሁን ያሉት ከባድ የአቅም ፈቃዶች ከተያዙበት ጊዜ መካከል ትልቁ ነው — ወደ ሙሉ
  ሰከንዶች ወደ ላይ ተጠጋግቶ በ60 ይገደባል። ምንም ሥራ በሌለበት መግቢያ ላይ ታሪካዊዎቹን ዝቅተኛ ገደቦች ይጠብቃል፦ በ
  byte-ተኮር መንገድ 2 ሰከንዶች፣ በመዋቅር-ተኮር መንገድ 1 ሰከንድ (ይህም
  `reason: "structure_limit"`ን ያካትታል)።
- ይህ ሌላ ከባድ የውይይት ጥያቄ ወይም ረጅም ጊዜ የሚወስድ የstreaming ምላሽ አሁንም
  በሂደት ላይ እያለ ሊከሰት ይችላል።

byte-ተኮር የምላሽ አካሉ፦

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

መዋቅር-ተኮር ምላሹ ተመሳሳይ type እና codeን ከመልዕክቱ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
እና `reason: "structure_limit"` ጋር ይጠቀማል።
በነባሪ ገደቦች፣ አንድ ጥያቄ ቢያንስ `200` መልዕክቶች፣
ቢያንስ `64` መሣሪያዎች፣ ወይም ቢያንስ `32,000` የተገመቱ tokens ሲኖሩት፣ ወይም የተገደበ መዋቅር ግምቱ
የ`10,000` የተጎበኙ nodes ወይም የ`12` ጥልቀት ገደቦቹን ሲያሟጥጥ በመዋቅር ደረጃ ከባድ ነው።

**ምክንያት፦** ይህ በOmniRoute ውስጥ ሆን ተብሎ የሚደረግ የጭነት ቅነሳ እንጂ የupstream አቅራቢ ውድቀት አይደለም።
እያንዳንዱ process አንድን ትልቅ የጥያቄ አካል ከማቆየቱና ከመተንተኑ በፊት የተገደበ የከባድ ጥያቄ አቅምን ለማስያዝ
process-አካባቢያዊ guard ይጠቀማል። የከባድ ጥያቄ ፈቃድ ለSSE
ምላሽ የሕይወት ዘመን ሙሉ እንደተያዘ ይቆያል።

**#503-fanout፦** ከዚህ ማስተካከያ በፊት፣ guard የhost ማህደረ ትውስታን ሳያገናዝብ በቋሚ የጥያቄ COUNT
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`፣ ነባሪ `1`) የበአንድ ጊዜ አፈጻጸምን ይገድብ ነበር፤ በመሆኑም የcoding-agent
fan-out (በርካታ subagents/CLIs፣ በተደጋጋሚ > 256 KB የሆኑ አካላት) ውጤታማውን
የበአንድ ጊዜ አፈጻጸም ወደ ~1 ዝቅ አድርጎ ሙሉ በሙሉ በተለመደ ጭነት ውስጥ 503 እንዲመልስ አድርጎት ነበር። guard አሁን ራሱን ያስተካክላል፦ ከ
process እውነተኛ የማህደረ ትውስታ ጣሪያ መጠኑ በሚወሰን በራስ-ሰር በተገኘ የingest BYTE በጀት (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ይገደባል፣ እንዲሁም
ቀጥታ የresource-pressure ምልክትን ይመለከታል — ስለዚህ ጭነትን የሚቀንሰው host በእውነት የማህደረ ትውስታ ጫና ስር ሲሆን ብቻ እንጂ፣ ከአንድ በላይ
ከባድ ጥያቄዎች በአንድ ጊዜ ስለደረሱ ብቻ አይደለም። የድሮው የብዛት ገደብ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
አሁንም ይከበራል፣ ግን እርስዎ በግልጽ ካዘጋጁት ብቻ ነው።

አቅሙ ሥራ ላይ ሲሆን፣ አንድ ከባድ ጥያቄ እንደገና ሊሞከር የሚችለውን `503` ከመመለሱ በፊት
ቦታ እስኪለቀቅ ድረስ መጀመሪያ እስከ
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ይጠብቃል (ነባሪው `RATE_LIMIT_MAX_WAIT_MS` ነው፤ `0` መጠበቁን ያሰናክላል)። ይህ የተገደበ መጠበቅ የሚኖረው ከባድ ንዑስ ጥያቄዎችን በአንድ ጊዜ fan out የሚያደርጉ agent-ቅጥ ደንበኞች
(OpenCode, Claude Code, Cursor) ሙሉውን የድጋሚ ሙከራ በጀታቸውን በፈጣን ውድቅ ምላሾች አቃጥለው በሥራ መሃል ከመቋረጥ ይልቅ የጥያቄውን ጎርፍ
በተራ እንዲያስኬዱ ነው።
አሁን ያለው የከባድ ጥያቄ ፈቃድ አጠቃቀም፣ የተወሰነው byte በጀት እና የቀጥታ ጫና ክብደት
በ`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) ላይ ይታያሉ — ማንኛውንም env var ከመቀየርዎ በፊት እነዚህን ያረጋግጡ።
ቅንብሮች → ጽናት → የጥያቄ ወረፋ → በአንድ ጊዜ የሚከናወኑ ጥያቄዎች ይህን አይቆጣጠርም፤ ያ ቅንብር
የተለየ የአቅራቢ ጥያቄ-ወረፋ ስልትን ይቆጣጠራል።

**መፍትሔ፦**

1. መጀመሪያ እንደገና ይሞክሩ። ደንበኞች ጥያቄውን ወዲያውኑ
   ከመድገም ይልቅ `Retry-After`ን ማክበር እና የድጋሚ ሙከራ መዘግየትን መጠቀም አለባቸው።
2. ማንኛውንም ነገር ከማስተካከልዎ በፊት `/api/monitoring/health` → `chatAdmission`ን ያረጋግጡ። `countCapEnabled:
false` እና ሰፊ `maxInflightBytes` ማለት በራስ-ሰር የተገኘው በጀት አስቀድሞ ሥራውን
   እየሠራ ነው ማለት ነው፤ `high`/`critical` የሆነ `pressureSeverity` ማለት host በእውነት የማህደረ ትውስታ እጥረት አለበት ማለት ነው —
   ይህን በadmission env var ማስተካከል አይቻልም፤ ተጨማሪ RAM ወይም አነስተኛ የሥራ ጫና ያስፈልገዋል።
3. `/api/monitoring/health` በራስ-ሰር የተገኘው በጀት ለ
   hostዎ በእውነት በጣም አነስተኛ መሆኑን ካሳየ ብቻ (ይህ አልፎ አልፎ ነው — አስቀድሞ ከcontainer እስከ bare-metal ድረስ ይመጣጠናል)፣ ወደ ቆየው የጥያቄ-ብዛት ገደብ ከመመለስ ይልቅ
   በቀጥታ በ`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ይተኩት።

ሥልጣን ያላቸውን የadmission ቅንብሮች ለማየት [የአካባቢ-ተለዋዋጭ ማጣቀሻውን](../reference/ENVIRONMENT.md#4-security--authentication)
ይመልከቱ።

## አማራጭ RAG / LLM የብልሽት ምደባ (16 ችግሮች)

አንዳንድ OmniRoute ተጠቃሚዎች gateway-ውን ከRAG ወይም agent stacks ፊት ያስቀምጣሉ። በእነዚህ አወቃቀሮች ውስጥ አንድ እንግዳ ሁኔታ ማየት የተለመደ ነው፦ OmniRoute ጤናማ ይመስላል (providers እየሰሩ ነው፣ routing profiles ትክክል ናቸው፣ የrate limit ማንቂያዎች የሉም)፣ ነገር ግን የመጨረሻው መልስ አሁንም የተሳሳተ ነው።

በተግባር እነዚህ ክስተቶች ብዙውን ጊዜ የሚመጡት ከgateway-ው ራሱ ሳይሆን ከታችኛው RAG pipeline ነው።

እነዚያን ብልሽቶች ለመግለጽ የጋራ ቃላትን መጠቀም ከፈለጉ፣ ተደጋጋሚ የሆኑ አሥራ ስድስት RAG / LLM የብልሽት ቅጦችን የሚገልጽ ውጫዊ የMIT license የጽሑፍ ምንጭ የሆነውን WFGY ProblemMap መጠቀም ይችላሉ። በአጠቃላይ የሚከተሉትን ይሸፍናል፦

- የretrieval መዛባት እና የተበላሹ የcontext ድንበሮች
- ባዶ ወይም ጊዜ ያለፈባቸው indexes እና vector stores
- የembedding እና semantic አለመጣጣም
- የprompt ማቀናበር እና የcontext window ችግሮች
- የሎጂክ መፍረስ እና ከመጠን በላይ እርግጠኛ የሆኑ መልሶች
- ረጅም chain እና የagent ማስተባበር ብልሽቶች
- የmulti agent ማህደረ ትውስታ እና የሚና መዛባት
- የdeployment እና bootstrap ቅደም ተከተል ችግሮች

ሐሳቡ ቀላል ነው፦

1. መጥፎ ምላሽን ሲመረምሩ፣ የሚከተሉትን ይመዝግቡ፦
   - የተጠቃሚውን ተግባር እና ጥያቄ
   - በOmniRoute ውስጥ ያለውን route ወይም provider combo
   - በታችኛው ሂደት ጥቅም ላይ የዋለ ማንኛውንም RAG context (የተገኙ ሰነዶች፣ tool calls፣ ወዘተ)
2. ክስተቱን ከአንድ ወይም ከሁለት WFGY ProblemMap ቁጥሮች (`No.1` … `No.16`) ጋር ያዛምዱ።
3. ቁጥሩን ከOmniRoute logs አጠገብ በራስዎ dashboard፣ runbook ወይም incident tracker ውስጥ ያስቀምጡ።
4. የRAG stack፣ retriever ወይም routing strategyዎን መቀየር እንዳለብዎት ለመወሰን ተዛማጁን WFGY ገጽ ይጠቀሙ።

ሙሉው ጽሑፍ እና ተግባራዊ መመሪያዎች እዚህ ይገኛሉ (MIT license፣ ጽሑፍ ብቻ)፦

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

ከOmniRoute በስተጀርባ RAG ወይም agent pipelines የማያስኬዱ ከሆነ ይህን ክፍል ችላ ማለት ይችላሉ።

### የDevin CLI የauth ብልሽቶች

**ምልክቶች፦**

- በDevin የሚደገፉ toolsን ሲጠሩ "Devin CLI አልተገኘም" ወይም "auth አልተሳካም" የሚል መልዕክት ይታያል
- የCLI runtime ምርመራ `installed=false` ይላል

**ምክንያቶች፦**

- `CLI_DEVIN_BIN` ወደሌለ ዱካ ያመለክታል
- Devin CLI በhost ላይ አልተጫነም

**መፍትሔ፦**

1. ለplatformዎ Devin CLIን ይጫኑ
2. በ`.env` ውስጥ `CLI_DEVIN_BIN=/usr/local/bin/devin` (ወይም ትክክለኛውን ዱካ) ያዘጋጁ
3. OmniRouteን እንደገና ያስጀምሩ እና ከ**Dashboard → CLI Tools** እንደገና ይፈትሹ

### የModel cooldown ተጣብቆ መቆየት (በእጅ ዳግም ማስጀመር)

**ምልክቶች፦**

- የማብቂያ ጊዜው ካለፈ በኋላም model በcooldown ዝርዝር ውስጥ ይቆያል
- timestamp-ው ያለፈ ጊዜን ቢያሳይም ጥያቄዎች በcombo routing ውስጥ model-ውን አሁንም ይዘሉታል

**በእጅ ዳግም ማስጀመር፦**

- **Dashboard፦** **Settings → Model Cooldowns** → ችግሩ ባለበት card ላይ **Re-enable**ን ጠቅ ያድርጉ
- **API፦** ከmanagement auth headers ጋር `DELETE /api/resilience/model-cooldowns`

### የCommand Code provider ግንኙነት በ403 ይከሽፋል

**ምልክቶች፦**

- የCommand Code provider ግንኙነትን ሲፈትሹ 403 ይመለሳል
- provider-ው አዲስ ከታከለ በኋላ card-ው "ፈቃድ የለውም" የሚል ያሳያል

**ምክንያት፦** የOAuth flow አልተጠናቀቀም (callback አልደረሰም ወይም token አልተቀመጠም)።

**መፍትሔ፦**

- የOAuth flowን እንደገና ለማስጀመር ከCLI `omniroute providers`ን ያሂዱ፣ ወይም
- OAuthን ከ**Dashboard → Providers → Command Code → Reconnect** እንደገና ያሂዱ

### ModelScope ከፍተኛ የሆኑ 429 cooldowns ይመልሳል

**ምልክቶች፦**

- ከጥቂት ተከታታይ ጥያቄዎች በኋላ በModelScope ላይ በጣም አጭር ወይም ወዲያውኑ የሚጀምሩ cooldowns
- Combo routing ከተጠበቀው ቀደም ብሎ ModelScopeን ይዘላል

**ምክንያት፦** ModelScope ለprovider-ው የተለዩ `Retry-After` headersን ያወጣል። v3.8.0 ለእነዚያ headers የተለየ አያያዝን ይዞ ይመጣል፣ ስለዚህ የቆዩ versions እንደ አጠቃላይ የrate-limit ፍንጮች በስህተት ያነቧቸዋል።

**መፍትሔ፦**

- v3.8.0 ወይም ከዚያ በኋላ ባለ version ላይ መሆንዎን ያረጋግጡ
- በ**Settings → Resilience** ስር ያለው `useUpstream429BreakerHints` toggle መንቃቱን ያረጋግጡ

### OMNIROUTE_WS_BRIDGE_SECRET በproduction ውስጥ የለም

**ምልክቶች፦**

- በርቀት production host ላይ ሲሰራ በእያንዳንዱ Codex/Responses WebSocket bridge ጥያቄ ላይ 401 ይመለሳል
- የWebSocket bridge handshake ከተገናኘ ወዲያውኑ ይዘጋል

**ምክንያት፦** የ`OMNIROUTE_WS_BRIDGE_SECRET` env var ከproduction environment ጠፍቷል።

**መፍትሔ፦**

1. የዘፈቀደ secret ይፍጠሩ፦ `openssl rand -hex 32`
2. በproduction server env ውስጥ (እና ከbridge-ው ጋር በሚገናኝ ማንኛውም client ውስጥ) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ያዘጋጁ
3. OmniRouteን እንደገና ያስጀምሩ

### Responses API፦ background mode ወደ synchronous ዝቅ ብሏል

**ምልክቶች፦**

- የተመዘገበ ማስጠንቀቂያ፦ `background mode degraded to synchronous`
- የ`background: true` ጥያቄ ከbackground job handle ይልቅ መደበኛ synchronous ምላሽ ይመልሳል

**ምክንያት፦** v3.8.0 ማስጠንቀቂያ እያወጣ በResponses API ላይ `background: true`ን ሆን ብሎ ወደ synchronous execution ዝቅ ያደርጋል። ሙሉ async background execution ወደፊት የሚቀርብ ባህሪ ነው።

**መፍትሔ፦**

- client-ውን `background` ሳይጠቀም እንዲጠራ ያስተካክሉ፣ ወይም
- ሙሉ async background modeን ይዞ የሚመጣ በኋላ ያለ release ይጠብቁ (changelog-ውን ይከታተሉ)

## የዝግታ ጅምር / የዝግጁነት ጊዜ ማብቂያ

CLIው `⚠ Server did not respond within 60s` ብሎ ካተመ፣ ነገር ግን ሰርቨሩ
በትክክል እየሰራ ከሆነ፣ የዝግጁነት ምርመራው የጊዜ ገደብ ለአካባቢዎ በጣም አጭር ነው።

ይህ በWindows (ጸረ-ቫይረስ፣ የፋይል ስርዓት ተከታታዮች) ወይም ከባድ የጅምር
የሥራ ጫና ባለባቸው ኮንቴይነሮች ላይ በተለምዶ ይከሰታል።

**መፍትሔ — የጊዜ ገደቡን ይጨምሩ፦**

```bash
# በአካባቢ ተለዋዋጭ በኩል (በተከታታይ ጅምሮች መካከል ይቆያል)፦
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 ደቂቃዎች
omniroute serve

# በCLI ጥቆማ በኩል (ለአንድ ጊዜ)፦
omniroute serve --ready-timeout 180000
```

ነባሪው 60 000 ms (60 s) ነው። ማስጠንቀቂያው ለመረጃ ብቻ ነው፤ ሰርቨሩ
ከበስተጀርባ መጀመሩን ይቀጥላል፣ እና ማስነሳቱ ሲጠናቀቅ ተደራሽ ይሆናል።

ስለ `OMNIROUTE_READY_TIMEOUT_MS` ሙሉ ዝርዝሮችን ለማግኘት
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md)ን ይመልከቱ።
