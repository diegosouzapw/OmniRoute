### በነጻ አቅራቢዎች ላይ የጥያቄ መጠን ገደብ (429 / 400 / 401)

**ምልክት**፦ `model: "auto"`ን ከነጻ/ማረጋገጫ ከማይፈልጉ አቅራቢዎች (opencode፣ auggie፣ ወዘተ) ጋር ሲጠቀሙ፣ በምላሾች ፈንታ አልፎ አልፎ `HTTP 429`፣ `400` ወይም `401` ያገኛሉ። ከጥቂት ጊዜ በኋላ ያንኑ ጥያቄ እንደገና ሲሞክሩ ጥያቄዎቹ ይሳካሉ፣ ነገር ግን ራስ-ሰር ሂደቶች (cron ስራዎች፣ ወኪሎች፣ ስክሪፕቶች) በመጀመሪያው ውድቀት ይቋረጣሉ።

**ዋና መንስኤ**፦ ሦስት እርስ በርሳቸው ነጻ የሆኑ የውድቀት ሁኔታዎች ተደራርበው ይከሰታሉ፦

1. **የአቅራቢ የጥያቄ መጠን ገደብ (`429`)**፦ ነጻ ደረጃዎች በእያንዳንዱ የጊዜ መስኮት ላይ ኮታ ሊያስገድዱ ይችላሉ። በአንድ ጊዜ የሚላኩ በርካታ ጥሪዎች ኮታውን ያሟጥጣሉ፣ ስለዚህ የጊዜ መስኮቱ ዳግም እስኪጀመር ድረስ ቀጣዩ ጥያቄ ውድቅ ይደረጋል።
2. **በቀጥታ ማስተላለፍ ውስጥ ያልተስተካከለ ሞዴል (`400`/`401`)**፦ የ`auto/*` ስብስቦች ከ`opencode` የመጡ፣ በካታሎጉ ውስጥ የተመዘገቡ ነገር ግን ንቁ የመግቢያ ማረጋገጫዎች የሌሏቸው በቀጥታ የሚተላለፉ ሞዴሎችን ሊያካትቱ ይችላሉ (ለምሳሌ፦ `oc/north-mini-code-free` → `401`)። ራስ-ሰር ራውተሩ አንዱን ይሞክራል፣ ይወድቃል፣ እና ወደ አማራጭ መመለስ ከመጀመሩ በፊት ስህተቱ ወደ ተጠቃሚው ይተላለፋል።
3. **በተመሳሳይ ጊዜ መከናወን የሚፈጥረው ማባባስ (ጫና ሲኖር `429`)**፦ በርካታ የወኪል/cron ክፍለ ጊዜዎች `auto`ን በአንድ ጊዜ ሲጠቀሙ፣ አጠቃላይ የጥያቄ ፍጥነቱ ነጻ አቅራቢዎች መቋቋም ከሚችሉት መጠን በላይ ይሆናል፣ ስለዚህ ትክክለኛ ጥሪዎች እንደ አላግባብ አጠቃቀም ይመደባሉ።

**የተረጋገጠ መፍትሔ (በማህበረሰቡ የተዘገበ፣ 2026-08-10)**፦ የነጻ ደረጃውን ተለዋዋጭነት በውድቀት ከማቋረጥ ይልቅ ማዞር፣ በተመሳሳይ ጊዜ መከናወን እና ወደ አማራጭ መመለስ እንዲቋቋሙት ሦስት የአካባቢ ተለዋዋጮችን ያስተካክሉ፦

```bash
export OMNIROUTE_ROTATE_ON_400=true           # በ400/401 ጊዜ ወደ ሌላ ሞዴል/አቅራቢ ይዝለሉ (ያልተስተካከሉ በቀጥታ የሚተላለፉ ሞዴሎችን ይዘላል)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ግልጽ የከባድ ጥያቄዎች መቀበያ ከፍተኛ ገደብ (በነባሪ አልተዋቀረም፦ የጥያቄ ብዛት ገደብ የለም፣ ከታች ያለውን ማስታወሻ ይመልከቱ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ወዲያውኑ እንደገና ሊሞከር የሚችል 503 ከመመለስ ይልቅ የከባድ ጥያቄዎች አቅም እስኪገኝ ረዘም ያለ የተገደበ ጥበቃ
```

እነዚህን በOmniRoute ሂደት አካባቢ (በዴሞኑ ውስጥ፣ ለምሳሌ በLaunchAgent plist ወይም `systemctl edit` በኩል) ያዋቅሩ፣ ከዚያ OmniRouteን ዳግም ያስጀምሩ። የማዞሪያ ጠቋሚው ከሁሉ ከፍተኛ ተጽዕኖ ያለው መቆጣጠሪያ ነው፦ ጽኑ ውድቀትን በስብስቡ ውስጥ ባለ ጤናማ አቅራቢ ላይ ወደሚደረግ ግልጽ ዳግም ሙከራ ይቀይረዋል።

**ማስታወሻ**፦ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ምን ያህል ከባድ — ረጅም አውድ ያላቸው — ጥያቄዎች በአንድ ጊዜ እንደሚከናወኑ ይገድባል፤ ገደቡ የመቀበያ በር እንጂ የአቅራቢ የጥያቄ መጠን ገደብ አይደለም። **#503-fanout ማሻሻያ፦** ይህ ተለዋዋጭ ከእንግዲህ በነባሪ አይዋቀርም (አሁን የሚተገበረው ከላይ እንደተደረገው በግልጽ ሲዋቀር ብቻ ነው) — በምትኩ የከባድ ጥያቄዎች መቀበያ ከአስተናጋጁ እውነተኛ የማህደረ ትውስታ ከፍተኛ ገደብ በመነሳት ራሱን በሚያመጣጥን፣ በራስ-ሰር በሚወሰን የባይት በጀት (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ይገደባል፤ ስለዚህ አዲስ ስርጭት ይህን ተለዋዋጭ ጨርሶ ሳያዋቅር እጅግ ያነሱ `503 chat_admission_busy` ውድቅ ማድረጎችን ማየት ይገባዋል፤ እዚህ ላይ በግልጽ ማዋቀሩ አሁንም በተመዘገበው መንገድ በትክክል ይሰራል። ግልጽ የባይት በጀት ማሻሻያዎች በ8 MiB–2 GiB መካከል ይገደባሉ። `413 body_exceeds_budget` ጊዜያዊ አይደለም፦ ያንን የባይት በጀት ይጨምሩ፣ `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`ን ይቀንሱ፣ ወይም የሂደቱን የማህደረ ትውስታ ከፍተኛ ገደብ ይጨምሩ። `inflight_bytes_budget` ጥያቄን መቀነስ ጊዜያዊ የአቅም ፉክክር ሲሆን እንደገና ሊሞከር የሚችል ሆኖ ይቆያል። የእያንዳንዱ አቅራቢ የጥያቄ መጠን ገደብ (`open-sse/services/rateLimitManager.ts`) በተናጠል በ`RATE_LIMIT_MAX_WAIT_MS`፣ `RATE_LIMIT_MAX_QUEUE_DEPTH` እና `RATE_LIMIT_AUTO_ENABLE` ይተዳደራል — `.env.example`ን ይመልከቱ።

**መፍትሔው መስራቱን እንዴት ማረጋገጥ እንደሚቻል**፦ ወኪልዎን/cronን በፍጥነት ሁለት ጊዜ ያስኪዱና ሁለቱም መሳካታቸውን ያረጋግጡ። ከመፍትሔው በፊት፣ ሁለተኛው አስኬድ በተለምዶ `429`/`401` ይመልሳል። ከመፍትሔው በኋላ፣ ውድቀቶች (ካሉ) በግልጽነት እንደገና ይሞከራሉ እና ጥሪው ይጠናቀቃል። እንዲሁም `curl /monitoring/health`ን ማስኬድና በአቅራቢ ግንኙነቶች ላይ ያለውን `rateLimitedUntil` መስክ እና ለተጎዱት አቅራቢዎች `circuitBreakers.providerBreakers[].state`ን መከታተል ይችላሉ — ሁኔታው `CLOSED`፣ `DEGRADED`፣ `OPEN` ወይም `HALF_OPEN` ከሚሉት አንዱ ነው (`src/shared/utils/circuitBreaker.ts`ን ይመልከቱ)፣ እና በተደጋጋሚ የሚወድቅ አቅራቢ የዳግም ማስጀመሪያ ጊዜ መስኮቱ የሙከራ ጥሪ እንዲያልፍ (`HALF_OPEN`) ከመፍቀዱ በፊት `CLOSED → DEGRADED → OPEN` ይሆናል።

**አሁንም 429 ካዩ**፦ ለዚያ አቅራቢ ገቢር የሆነው መለያ _quota_ውን በእርግጥ ጨርሷል (የጥያቄ ፍጥነት ገደብን ብቻ አይደለም)። በOmniRoute ዳሽቦርድ → Providers → Accounts ውስጥ ለተመሳሳዩ አቅራቢ ሁለተኛ መለያ ያክሉ፣ ወይም ሌላ ነፃ አቅራቢ (ለምሳሌ `routeway`፣ `auggie`) ያካትቱ። ማዞር የሚጠቅመው ለጊዜያዊ የጥያቄ ፍጥነት ገደብ/400/401 ችግሮች ብቻ ነው፤ የquota ሙሉ በሙሉ ማለቅ ሁለተኛ የመግቢያ ማረጋገጫ ወይም የተለየ አቅራቢ ይፈልጋል።

**በምስል ሞዴሎች (`auto/vision`፣ `bazaarlink/*`) ላይ 403 ካዩ**፦ የተገናኘው መለያ ምስልን የሚያካትት የሚከፈልበት ዕቅድ የለውም፣ ወይም API keyው በቂ ፈቃዶች የሉትም። በአቅራቢው ዳሽቦርድ ውስጥ የቁልፉ scope ምስል/ባለብዙ ሞዳሊቲን እንደሚያካትት ያረጋግጡ፣ ወይም የሚከፈልበት tier መለያ ያገናኙና የምስል ዒላማ አድርገው ያቆዩት።

## የ npm install ማስጠንቀቂያዎች (ERESOLVE / peer / deprecated)

`npm install -g omniroute` ሲያስኬዱ፣ እንደ `npm warn ERESOLVE`፣ የ peer-dependency ማሳወቂያዎች እና `deprecated` መልዕክቶች ያሉ ብዙ ማስጠንቀቂያዎችን ሊያዩ ይችላሉ። **እነዚህ የሚጠበቁ እና ጉዳት የሌላቸው ናቸው።** በውጤቱ ውስጥ `added <N> packages` ካዩ፣ ጭነቱ በተሳካ ሁኔታ ተጠናቋል።

የ peer-dependency መፍቻ ማስጠንቀቂያዎችን ለማፈን፣ በ OmniRoute የሚደገፈውን የጭነት ቅርጽ ይጠቀሙ፦

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` የሚያፍነው `ERESOLVE` እና የ peer-dependency ማሳወቂያዎችን ብቻ ነው። የተቋረጠ ድጋፍ ማሳወቂያዎች ከተዘዋዋሪ የሦስተኛ ወገን packages ስለሚመጡ እንደታዩ ይቆያሉ፤ እነዚህም ጭነቱ እንዳልተሳካ አያመለክቱም።

ማስጠንቀቂያዎቹ የሚመጡት OmniRoute በማይቆጣጠራቸው የሦስተኛ ወገን packages ውስጥ ካሉ ጊዜ ያለፈባቸው የ peer-dependency ክልሎች ነው፦

1. **`marked-terminal` `marked >=1 <16` ይፈልጋል፣ `marked@18` ግን ተገኝቷል** — በተግባር በትክክል ይሠራል፤ የ upstream peer ክልሉ ጊዜ ያለፈበት ብቻ ነው።
2. **`deprecated prebuild-install@7.1.3`** — ተዘዋዋሪ የ native-binary ማውረጃ አጋዥ ነው። የተወሰነውን `wreq-js` transport binding ለመጫን
   ጥቅም ላይ አይውልም፣ እንዲሁም የ web-cookie provider transport ዝግጅት

## የጸረ-ቫይረስ የተሳሳቱ ማስጠንቀቂያዎች

### Avast/AVG `README.md`ን በ`MD:HttpRequest-inf[Susp]` ወደ ማግለያ ያስገባል

**ይህ የተሳሳተ ማስጠንቀቂያ ነው። ምንም የተበከለ ነገር የለም፣ እና ምንም እርምጃ አያስፈልግም።**

Avast እና AVG ብዙ HTTP ጥያቄ የሚመስሉ አገናኞችን የያዙ ተራ ጽሑፍ/Markdown ፋይሎችን ምልክት የሚያደርግ ግምታዊ የፍተሻ ዘዴ ይጠቀማሉ። የOmniRoute `README.md` በnpm package ውስጥ ተካቶ ይላካል (በ`package.json` → `files` ውስጥ ተዘርዝሯል)፣ ስለዚህ በglobal install ጊዜ `node_modules/omniroute/README.md` ላይ ይቀመጣል — እንዲሁም ~15 የ`http://localhost:20128/...` ምሳሌዎችን (የMCP HTTP/SSE endpoints፣ የA2A `.well-known` URL እና የ`curl` ቅንጣቢዎችን) ይዟል። ይህ የአገናኝ ብዛት ግምታዊ ፍተሻውን ለማስነሳት በቂ ነው።

ይህ በቅርቡ ብቻ የጀመረ ከሆነ፦ የፋይሉ ዓይነት አልተቀየረም። README የendpoints ሰንጠረዡን አስፋፍቷል (MCP HTTP + SSE + A2A ተጨምረዋል)፣ እንዲሁም ተጨማሪ የ`curl` ምሳሌዎች ተካተዋል፤ ይህም ከገደቡ እንዲያልፍ አድርጎታል።

ፋይሉ ምንም ሊፈጸም የሚችል ይዘት የሌለው የማይንቀሳቀስ ሰነድ ነው። ከማግለያው በደህና መመለስ ይችላሉ።

**ማድረግ ያለብዎት፦**

1. **ማሳወቂያዎቹን ያቁሙ** — በጸረ-ቫይረስዎ ውስጥ የመጫኛ ማውጫውን ከፍተሻ ያስወግዱ
   (Avast፦ Settings → Exceptions)፣ የglobal `node_modules` pathዎን እና/ወይም የ
   OmniRoute data dir (`~/.omniroute/`) ያክሉ።
2. **የተሳሳተውን ማስጠንቀቂያ ሪፖርት ያድርጉ** — <https://www.avast.com/false-positive-file-form.php>፣
   ወደ ማግለያ የገባውን `README.md` በማያያዝ። ችግሩ አቅራቢው በጽሑፍ ፋይል ላይ ከመጠን በላይ ምላሽ የሚሰጥ ግምታዊ ፍተሻ ስለሆነ፣ ለሁሉም የሚጠቅመው መፍትሔ ይህ ነው።

**ይህን በእኛ በኩል ለምን “አናስተካክለውም”፦** ምሳሌዎቹ ሁሉ `http://localhost` ናቸው፣ እና localhost ከself-signed certificate ውስብስብነት ውጪ `https` ሊሆን አይችልም። ከአንድ አቅራቢ ግምታዊ ፍተሻ ለማምለጥ ሰነዶቹን ማበላሸት፣ የscanner ስህተትን ለማርካት ሲባል እያንዳንዱን አንባቢ ይጎዳል።

### Kaspersky የDesktop appን እንደ `PDM:Trojan.Win32.Generic` ምልክት ያደርጋል

**ይህ ከባህሪ ላይ ከተመሠረተ ግምታዊ ፍተሻ የመጣ የተሳሳተ ማስጠንቀቂያ ነው። ምንም የተበከለ ነገር የለም።** የKaspersky `PDM:` prefix ውሳኔው ከProactive Defense Module (System Watcher) እንደመጣ ያመለክታል፤ ይህም ጫኚውን ከሚታወቅ malware ጋር ከማዛመድ ይልቅ _የሚያደርገውን_ ይገመግማል። ፍተሻው ሲነሳ Kaspersky ሙሉ መጫኑን “ወደነበረበት ይመልሳል” — ቀደም ሲል የጻፋቸውን ፋይሎች ይሰርዛል — በዚህም appው ተበላሽቶ ወይም ጠፍቶ ይቀራል።

ምልክት የሚያደርግባቸው ፋይሎች ከdesktop app ጋር የታሸጉ በይፋ የተገለጹ open-source dependencies መደበኛ ክፍሎች ናቸው፣ ለምሳሌ፦

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` እና
  `workerProcessEntry.js` — [Playwright](https://playwright.dev)፣ በapp ውስጥ ለሚደረግ provider login እና browser-backed chat የሚያገለግል የbrowser automation library።
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — በweb-cookie providers ላይ browser-fingerprinted HTTP ለመጠቀም የሚያገለግል፣ ስሪቱ የተወሰነው `wreq-js` native binding

**ለምን ይነሳል፦** የWindows ጫኚው **እስካሁን code-signed አይደለም**፣ ስለዚህ ያልተፈረመ NSIS ጫኚ ምንም ዕውቅና የለውም፣ እና የባህሪ ግምታዊ ፍተሻዎች በከፍተኛ ጥብቅነት ይሠራሉ። ከታሸገ native DLL እና በ`%LOCALAPPDATA%\Programs\OmniRoute` ስር ከሚጻፉ በመቶዎች ከሚቆጠሩ `.js` ፋይሎች (ከNext.js standalone build የመጡ hash-suffixed package directoriesን ጨምሮ) ጋር ሲደመር፣ ይህ ግምታዊ ፍተሻውን ለማስነሳት በቂ ነው። Code signing ታቅዷል፤ እስኪተገበር ድረስ አዳዲስ ልቀቶች ይህን ሊደግሙት ይችላሉ።

   ```powershell

     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```

   ውጤቱ ከ`latest.yml` → `sha512` ጋር መመሳሰል አለበት። ካልተመሳሰለ ፋይሉን ይሰርዙ እና ከ[GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) ብቻ እንደገና ያውርዱ።

   ከዚያ እንደገና ይጫኑ።

- የመግቢያ ገጹ ባዶ ማያ ገጽ ወይም የserver ስህተት ያሳያል
- Console ላይ `Error: Module did not self-register` ወይም ተመሳሳይ የnative binding ስህተቶች ይታያሉ
- Runtime-ው ከሚደገፈው የደህንነት ፖሊሲ ውጪ ከሆነ፣ የመግቢያ ገጹ የNode ስሪትዎን የያዘ **ብርቱካናማ የማስጠንቀቂያ ሰንደቅ** ያሳያል

**መፍትሔ፦**

1. የሚደገፍ የNode.js LTS ልቀት ይጫኑ (የሚመከር፦ Node.js 24.x)፦
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ስሪትዎን ያረጋግጡ፦ `node --version` በ24.x LTS መስመር ላይ `v24.0.0` ወይም ከዚያ አዲስ ማሳየት አለበት
3. OmniRouteን እንደገና ይጫኑ፦ `npm install -g omniroute`
4. እንደገና ያስጀምሩ፦ `omniroute`

> **የሚደገፉ ደህንነታቸው የተጠበቁ ስሪቶች፦** `>=22.22.2 <23` ወይም `>=24.0.0 <27`። Node.js 24.x LTS (Krypton) እና Node.js 26 ሙሉ በሙሉ ይደገፋሉ።

### npm v11+፦ `better-sqlite3` አልተጫነም (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**ምክንያት፦** npm v11 (ከNode.js 24+ ጋር የሚቀርብ) በነባሪነት ለአማራጭ
ጥገኞች የመጫኛ scriptsን ይከለክላል። `better-sqlite3` በ`optionalDependencies`
ውስጥ የተዘረዘረ እና native compilation (`node-gyp rebuild`) የሚፈልግ በመሆኑ፣ npm ያለምንም ማሳወቂያ ይዘለዋል።

**ምልክቶች፦**

- Server-ው ሲጀምር `Cannot find module 'better-sqlite3'` በሚል ስህተት ይበላሻል
- `ls node_modules/better-sqlite3` "No such file or directory" ያሳያል
- `npm ls better-sqlite3` `(empty)` ያሳያል

**መፍትሔ፦**

1. የመጫኛ scriptsን ያጽድቁና እንደገና ይጫኑ፦
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ወይም ቀድሞ የተገነባውን በእጅ ይጫኑ፦
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. እንደሚሠራ ያረጋግጡ፦ `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS፦ `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**ምክንያት፦** ዓለም አቀፍ `npm install -g omniroute` ከተከናወነ በኋላ፣ በpackage-ው ውስጥ ያለው የ`better-sqlite3` native binary በአካባቢው እየሄደ ካለው የተለየ architecture ወይም Node.js ABI ለመሥራት ተጠናቅሮ ሊሆን ይችላል። ቀድሞ የተገነባው binary ከአካባቢዎ ጋር በማይዛመድበት ጊዜ፣ ይህ በmacOS (በApple Silicon እና Intel ላይ) የተለመደ ነው።

**ምልክቶች፦**

- Server-ው ሲጀምር ወዲያውኑ በ`dlopen` ስህተት ይቋረጣል
- ስህተቱ `slice is not valid mach-o file` ይዟል
- ሙሉ ምሳሌ፦

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**መፍትሔ — ለአካባቢዎ እንደገና ይገንቡ (የNode.js ስሪትን ዝቅ ማድረግ አያስፈልግም)፦**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ማስታወሻ፦** ይህ native binding-ውን ከአካባቢያዊው የNode.js ስሪትዎ እና CPU architecture ጋር እንዲስማማ እንደገና በማጠናቀር የbinary አለመዛመዱን ይፈታል። በይፋ የሚደገፈው የruntime ክልል **`>=22.22.2 <23` ወይም `>=24.0.0 <27`** ነው (`SUPPORTED_NODE_RANGE` በ`src/shared/utils/nodeRuntimeSupport.ts` ውስጥ፣ ከ`package.json` `engines` field ጋር የተዛመደ)። Node.js 24.x LTS (Krypton) እና Node.js 26 ከ`better-sqlite3` v12.x ጋር ሙሉ በሙሉ ይደገፋሉ።

### የአቅራቢ ማረጋገጫ "fetch failed" ያሳያል

**ምክንያት፦** የAPI ቁልፍ ማረጋገጫ መጨረሻ ነጥብ (`POST /api/providers/validate`) ቀደም ሲል የፕሮክሲ ውቅረትን እያለፈ ስለነበር፣ የፕሮክሲ ማዘዋወርን በሚፈልጉ አካባቢዎች ውድቀቶችን ያስከትል ነበር።

**መፍትሔ (v3.5.5+)፦** ይህ አሁን ተስተካክሏል። የአቅራቢ ማረጋገጫ የአቅራቢ ደረጃ እና ዓለም አቀፍ የፕሮክሲ ቅንብሮችን በራስ-ሰር በማክበር በ`runWithProxyContext` በኩል ይመራል።

### የቶከን ጤንነት ማረጋገጫ "fetch failed" በሚል ይወድቃል

**ምክንያት፦** ከበስተጀርባ የሚከናወነው የOAuth ቶከን እድሳት ለእያንዳንዱ ግንኙነት የፕሮክሲ ውቅረትን አይወስንም ነበር።

**መፍትሔ (v3.5.5+)፦** የቶከን ጤንነት ማረጋገጫ መርሐግብር አስያዡ አሁን እድሳትን ከመሞከሩ በፊት ለእያንዳንዱ ግንኙነት የፕሮክሲ ውቅረትን ይወስናል። ወደ v3.5.5+ ያዘምኑ።

### የSOCKS5 ፕሮክሲ "invalid onRequestStart method" ይመልሳል

## የCloud ችግሮች

### የCloud Sync ስህተቶች

1. `BASE_URL` እየሰራ ወዳለው instance መጠቆሙን ያረጋግጡ (ለምሳሌ፣ `http://localhost:20128`)
2. `CLOUD_URL` ወደ cloud endpoint መጠቆሙን ያረጋግጡ (ለምሳሌ፣ `https://omniroute.dev`)
3. የ`NEXT_PUBLIC_*` እሴቶችን ከserver-side እሴቶች ጋር የተጣጣሙ አድርገው ያቆዩ

### የCloud `stream=false` ጥሪ 500 ይመልሳል

**ምልክት፦** streaming ላልሆኑ ጥሪዎች በcloud endpoint ላይ `Unexpected token 'd'...` ይታያል።

**ምክንያት፦** client JSON ሲጠብቅ upstream የSSE payload ይመልሳል።

**ጊዜያዊ መፍትሔ፦** ለቀጥታ የcloud ጥሪዎች `stream=true` ይጠቀሙ። የአካባቢው runtime የSSE→JSON fallback ያካትታል።

### Cloud እንደተገናኘ ይገልጻል፣ ነገር ግን "Invalid API key" ይላል

1. ከአካባቢያዊ dashboard (`/api/keys`) አዲስ key ይፍጠሩ
2. cloud sync ያስኪዱ፦ Enable Cloud → Sync Now
3. የቆዩ ወይም sync ያልተደረጉ keys አሁንም በcloud ላይ `401` ሊመልሱ ይችላሉ

## የDocker ችግሮች

### የDocker IPv6 / ግንኙነት ዳግም ማስጀመር

<a name="docker-ipv6"></a>

**ምልክቶች፦** `curl http://localhost:20128/v1/models` የሚለው `curl: (56) Recv failure: Connection reset by peer` ይመልሳል። Dashboard እና ማረጋገጫ የማይፈልጉ endpoints ይሰራሉ፣ ነገር ግን ማረጋገጫ የሚፈልጉ endpoints አይሰሩም — የauth ችግር ይመስላል፣ ግን አይደለም።

**ምክንያት፦** `docker run -p 20128:20128` በሁለቱም `0.0.0.0` (IPv4) እና `::` (IPv6) ላይ ያሳትማል፣ ነገር ግን በcontainer ውስጥ ያለው process በIPv4 ላይ ብቻ ያዳምጣል። `localhost` መጀመሪያ ወደ `::1` በሚፈታባቸው hosts ላይ፣ ግንኙነቱ ከጀርባው listener በሌለው የIPv6 published port ላይ ያርፋል → ግንኙነቱ ዳግም ይጀመራል።

**መፍትሔ፦**

1. **ፈጣን ምርመራ፦** `curl -4 http://localhost:20128/v1/models` ያስኪዱ። ከ`-4` ጋር ከሰራ፣ ያለእሱ ግን ካልሰራ፣ የIPv6 bind አለመጣጣም አለብዎት።
2. **ቋሚ መፍትሔ፦** በ`docker run` command ውስጥ `-p 127.0.0.1:20128:20128` በመጠቀም በግልጽ ሁኔታ ወደ IPv4 bind ያድርጉ፦
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ይህ የIPv4 bind እንዲደረግ ያስገድዳል፣ እንዲሁም proxyው በሁሉም የhost interfaces ላይ እንዳይጋለጥ ያደርጋል።

### የLog Filesን ማንቃት

በ`.env` fileዎ ውስጥ `APP_LOG_TO_FILE=true` ያዘጋጁ። የapplication logs በ`logs/` ስር ይጻፋሉ።
የcall log pipeline በsettings ውስጥ ሲነቃ፣ የrequest artifacts በ`${DATA_DIR}/call_logs/` ስር ይቀመጣሉ።
የpipeline capture ሲነቃ፣ የstream chunk payloadsን ለመተው `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false`ን ያዘጋጁ፤ ወይም የartifact capን በKB ለመቀየር `CALL_LOG_PIPELINE_MAX_SIZE_KB`ን ያስተካክሉ።

### የProvider ጤንነትን ይፈትሹ

```bash
# የጤንነት dashboard
http://localhost:20128/dashboard/health

# የAPI ጤንነት ምርመራ
curl http://localhost:20128/api/monitoring/health
```

### የRuntime ማከማቻ

- ዋና ሁኔታ፦ `${DATA_DIR}/storage.sqlite` (providers, combos, aliases, keys, settings)
- አጠቃቀም፦ በ`storage.sqlite` ውስጥ ያሉ የSQLite tables (`usage_history`, `call_logs`, `proxy_logs`) + አማራጭ `${DATA_DIR}/call_logs/`
- የApplication logs፦ `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ሲሆን)
- የCall log artifacts፦ የcall log pipeline ሲነቃ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

በRequest Logs page ላይ ያለው **Clean history** action `call_logs`ን፣ legacy
`request_detail_logs`ን እና የአካባቢውን `${DATA_DIR}/call_logs/` artifact directory ያጸዳል።

## የCircuit Breaker ችግሮች

### Provider በOPEN ሁኔታ ላይ ተጣብቆ ቆይቷል

የprovider circuit breaker OPEN ሲሆን፣ cooldown እስኪያበቃ ድረስ ጥያቄዎች ይታገዳሉ።

**መፍትሔ፦**

1. ወደ **Dashboard → Settings → Resilience** ይሂዱ
2. ለተጎዳው provider የcircuit breaker ካርዱን ይመልከቱ
3. ሁሉንም breakers ለማጽዳት **Reset All** ን ጠቅ ያድርጉ፣ ወይም cooldown እስኪያበቃ ይጠብቁ
4. Reset ከማድረግዎ በፊት provider በእርግጥ መገኘቱን ያረጋግጡ

### Provider circuit breaker ን ደጋግሞ ያስነሳል

አንድ provider በተደጋጋሚ ወደ OPEN ሁኔታ ከገባ፦

1. የውድቀቱን ንድፍ ለማየት **Dashboard → Health → Provider Health** ን ይመልከቱ
2. ወደ **Settings → Resilience → Provider Profiles** ይሂዱና የውድቀት ገደቡን ይጨምሩ
3. Provider የAPI ገደቦቹን ቀይሮ እንደሆነ ወይም ዳግም ማረጋገጫ እንደሚፈልግ ያረጋግጡ
4. የlatency telemetry ን ይገምግሙ — ከፍተኛ latency በtimeout ላይ የተመሠረቱ ውድቀቶችን ሊያስከትል ይችላል

- **የSystem prompt ጠፍቷል** — Claude እና Gemini የsystem prompts ን በተለያየ መንገድ ይይዛሉ፤ የትርጉም ውጤቱን ያረጋግጡ
- **SDK በobject ምትክ raw string ይመልሳል** — በv1.x ተፈትቷል፤ response sanitizer የOpenAI SDK Pydantic ማረጋገጫ ውድቀቶችን የሚያስከትሉ መደበኛ ያልሆኑ መስኮችን (`x_groq`፣ `usage_breakdown`፣ ወዘተ) ያስወግዳል። ይህን በv3.x+ ላይ አሁንም ካዩ፣ እባክዎ issue ያስገቡ።
- **GLM/ERNIE የ`system` role ን አይቀበልም** — በv1.x ተፈትቷል፤ role normalizer የsystem መልዕክቶችን ተኳዃኝ ላልሆኑ models በራስ-ሰር ወደ user መልዕክቶች ያዋህዳል። ይህን በv3.x+ ላይ አሁንም ካዩ፣ እባክዎ issue ያስገቡ።
- **የ`developer` role አይታወቅም** — በv1.x ተፈትቷል፤ OpenAI ላልሆኑ providers በራስ-ሰር ወደ `system` ይቀየራል። ይህን በv3.x+ ላይ አሁንም ካዩ፣ እባክዎ issue ያስገቡ።
- **`json_schema` ከGemini ጋር አይሠራም** — በv1.x ተፈትቷል፤ `response_format` አሁን ወደ Gemini `responseMimeType` + `responseSchema` ይቀየራል። ይህን በv3.x+ ላይ አሁንም ካዩ፣ እባክዎ issue ያስገቡ።

## የመቋቋም ቅንብሮች

### ራስ-ሰር የፍጥነት ገደብ አለመጀመር

- ራስ-ሰር የፍጥነት ገደብ የሚተገበረው በAPI ቁልፍ አቅራቢዎች ላይ ብቻ ነው (በOAuth/የደንበኝነት ምዝገባ ላይ አይደለም)
- **ቅንብሮች → መቋቋም → የአቅራቢ መገለጫዎች** ውስጥ ራስ-ሰር የፍጥነት ገደብ መንቃቱን ያረጋግጡ
- አቅራቢው `429` የሁኔታ ኮዶችን ወይም `Retry-After` ራስጌዎችን የሚመልስ መሆኑን ያረጋግጡ

### ኤክስፖነንሺያል የድጋሚ ሙከራ መዘግየትን ማስተካከል

የአቅራቢ መገለጫዎች እነዚህን ቅንብሮች ይደግፋሉ፦

- **መሠረታዊ መዘግየት** — ከመጀመሪያው ውድቀት በኋላ ያለው የመጀመሪያ የጥበቃ ጊዜ (ነባሪ፦ 1s)
- **ከፍተኛው መዘግየት** — የመጠበቂያ ጊዜ ከፍተኛው ገደብ (ነባሪ፦ 30s)
- **ማባዣ** — በእያንዳንዱ ተከታታይ ውድቀት መዘግየቱ ምን ያህል እንደሚጨምር (ነባሪ፦ 2x)

### የተቀናጀ የጥያቄ መጉረፍን መከላከል

ብዙ በአንድ ጊዜ የሚከናወኑ ጥያቄዎች የፍጥነት ገደብ ያለበትን አቅራቢ ሲመቱ፣ OmniRoute ጥያቄዎቹን በተከታታይ ለማስኬድ እና ተከታታይ ውድቀቶችን ለመከላከል mutex + ራስ-ሰር የፍጥነት ገደብን ይጠቀማል። ይህ ለAPI ቁልፍ አቅራቢዎች በራስ-ሰር ይከናወናል።

### የውይይት ጥያቄዎች በ503 / chat_admission_busy ይወድቃሉ

**ምልክቶች፦**

- የውይይት ማጠናቀቂያዎች endpoint የስህተት ኮዱ
  `chat_admission_busy` የሆነ፣ ድጋሚ ሊሞከር የሚችል `503` ምላሽ ይመልሳል።
- ምላሹ `Retry-After` ያካትታል። ከ#12135 ጀምሮ እሴቱ ከተስተዋለው
  የመያዣ መጠን ይወሰዳል — ጥያቄው አስቀድሞ ከጠበቀበት የ`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` የጊዜ መስኮት
  እና የአሁኖቹ ከባድ የአቅም ፈቃዶች ከተያዙበት ጊዜ መካከል ትልቁ ነው — ወደ ሙሉ
  ሰከንዶች ወደ ላይ ተጠጋግቶ በ60 ይገደባል። ባዶ gate ላይ ታሪካዊዎቹን ዝቅተኛ ገደቦች ይጠብቃል፦ በ
  byte ላይ በተመሠረተው መንገድ 2 ሰከንዶች፣ በመዋቅር ላይ በተመሠረተው መንገድ 1 ሰከንድ (ይህም
  `reason: "structure_limit"` ያካትታል)።
- ይህ ሌላ ከባድ የውይይት ጥያቄ ወይም ለረጅም ጊዜ የሚሠራ streaming ምላሽ አሁንም
  በሂደት ላይ እያለ ሊከሰት ይችላል።

በbyte ላይ የተመሠረተው የምላሽ ይዘት፦

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

በመዋቅር ላይ የተመሠረተው ምላሽ ተመሳሳዩን ዓይነት እና ኮድ ይጠቀማል፣ መልእክቱም
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
እና `reason: "structure_limit"` ነው።
በነባሪ ገደቦች፣ አንድ ጥያቄ ቢያንስ `200` መልእክቶች፣
ቢያንስ `64` መሣሪያዎች ወይም ቢያንስ `32,000` የተገመቱ tokens ሲኖሩት፣ ወይም የተገደበው የመዋቅር ግምት
የ`10,000` የተጎበኙ nodes ወይም የ`12` ጥልቀት ገደቦቹን ሲጨርስ፣ በመዋቅር ከባድ ነው።

**ምክንያት፦** ይህ በOmniRoute ውስጥ ሆን ተብሎ የሚደረግ የጭነት ቅነሳ እንጂ የupstream አቅራቢ ውድቀት አይደለም።
እያንዳንዱ process ትልቅ የጥያቄ ይዘትን ይዞ ከማቆየቱ እና ከመተንተኑ በፊት ውስን የከባድ ጥያቄዎች አቅምን ለማስያዝ
process-local guard ይጠቀማል። አንድ የከባድ ጥያቄ የአቅም ፈቃድ በSSE
ምላሽ የሕይወት ዘመን በሙሉ ተይዞ ይቆያል።

**#503-መስፋፋት፦** ከዚህ ማስተካከያ በፊት፣ guard የhost memory መጠንን ሳያገናዝብ concurrencyን በቋሚ የጥያቄ COUNT
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`፣ ነባሪ `1`) ይገድብ ነበር፤ ስለዚህ የcoding-agent
fan-out (በርካታ subagents/CLIs፣ በተለምዶ > 256 KB የሆኑ ይዘቶች) ውጤታማውን
concurrency ወደ ~1 እንዲወርድ አድርጎ በሙሉ መደበኛ ጭነት ስር 503 ያስከትል ነበር። guard አሁን ራሱን ያስተካክላል፦ ከ
process እውነተኛ የmemory ጣሪያ መጠን የሚወሰን፣ በራስ-ሰር የተገኘ የingest BYTE በጀት (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ይገድበዋል፣
እንዲሁም ቀጥታ የresource-pressure ምልክትን ይመለከታል — ስለዚህ ጭነትን የሚቀንሰው
host በእውነት የmemory ጫና ስር ሲሆን ብቻ ነው፣ ከአንድ በላይ
ከባድ ጥያቄዎች በአንድ ጊዜ ስለደረሱ ብቻ አይደለም። የቀድሞው የቁጥር ገደብ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
አሁንም ይከበራል፣ ነገር ግን በግልጽ ካዋቀሩት ብቻ ነው።

አቅሙ በተያዘበት ጊዜ፣ አንድ ከባድ ጥያቄ ድጋሚ ሊሞከር የሚችል `503` ከመመለሱ በፊት
አንድ ቦታ እስኪለቀቅ ድረስ በመጀመሪያ እስከ
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ነባሪ `2000`፣ `0` መጠበቅን ያሰናክላል) ይጠብቃል። የተገደበው ጥበቃ የሚኖረው agent-ቅርጽ ያላቸው clients
(OpenCode, Claude Code, Cursor) ከባድ ንዑስ ጥያቄዎችን በአንድ ጊዜ fan-out ሲያደርጉ፣
በፈጣን ውድቅ ማድረጎች ሙሉ የድጋሚ ሙከራ በጀታቸውን ከማቃጠል እና በሥራው መሃል ከመቋረጥ ይልቅ የጥያቄዎቹን መጉረፍ
በተከታታይ እንዲያስኬዱ ነው።
የአሁኑ የከባድ ጥያቄ የአቅም ፈቃድ መያዣ፣ የተወሰነው የbyte በጀት እና የቀጥታ ጫና ክብደት
በ`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) ላይ ይታያሉ — ማንኛውንም env var ከመቀየርዎ በፊት እነዚህን ያረጋግጡ።
ቅንብሮች → መቋቋም → የጥያቄ ወረፋ → በአንድ ጊዜ የሚከናወኑ ጥያቄዎች ይህን አይቆጣጠርም፤ ያ ቅንብር
የተለየ የአቅራቢ ጥያቄ-ወረፋ ዘዴን ይቆጣጠራል።

**መፍትሔ፦**

1. መጀመሪያ ድጋሚ ይሞክሩ። Clients ጥያቄውን ወዲያውኑ
   ከመድገም ይልቅ `Retry-After`ን ማክበር እና backoff መጠቀም አለባቸው።
2. ማንኛውንም ነገር ከማስተካከልዎ በፊት `/api/monitoring/health` → `chatAdmission`ን ያረጋግጡ። `countCapEnabled:
false` እና ሰፊ `maxInflightBytes` ማለት በራስ-ሰር የተገኘው በጀት አስቀድሞ ሥራውን
   እየሠራ ነው ማለት ነው፤ `high`/`critical` የሆነ `pressureSeverity` ማለት host በእውነት memory አንሶታል ማለት ነው —
   ይህ በadmission env var ሊስተካከል አይችልም፤ ተጨማሪ RAM ወይም አነስተኛ የሥራ ጫና ያስፈልገዋል።
3. `/api/monitoring/health` በራስ-ሰር የተገኘው በጀት ለ
   hostዎ በእውነት በጣም ትንሽ መሆኑን ካሳየ ብቻ (ይህ ብርቅ ነው — አስቀድሞ ከcontainer እስከ bare-metal ድረስ ይመጠናል)፣
   ወደ ቀድሞው በጥያቄ ቁጥር ላይ የተመሠረተ ገደብ ከመመለስ ይልቅ በ`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` በቀጥታ ይሻሩት።

ለዋናዎቹ የadmission ቅንብሮች [የenvironment variable ማጣቀሻውን](../reference/ENVIRONMENT.md#4-security--authentication)
ይመልከቱ።

## አማራጭ RAG / LLM የብልሽት ምደባ (16 ችግሮች)

አንዳንድ OmniRoute ተጠቃሚዎች gateway-ውን ከRAG ወይም agent stack-ዎች ፊት ያስቀምጣሉ። በእነዚህ አወቃቀሮች አንድ እንግዳ ሁኔታ ማየት የተለመደ ነው፦ OmniRoute ጤናማ ይመስላል (provider-ዎች እየሠሩ ናቸው፣ የrouting profile-ዎች ደህና ናቸው፣ የrate limit ማንቂያዎች የሉም)፣ ነገር ግን የመጨረሻው መልስ አሁንም የተሳሳተ ይሆናል።

በተግባር እነዚህ ክስተቶች ብዙውን ጊዜ የሚመጡት ከgateway-ው ራሱ ሳይሆን ከታችኛው RAG pipeline ነው።

እነዚያን ብልሽቶች ለመግለጽ የጋራ ቃላትን መጠቀም ከፈለጉ፣ በተደጋጋሚ የሚከሰቱ አሥራ ስድስት የRAG / LLM ብልሽት ቅጦችን የሚገልጽ ውጫዊ የMIT license የጽሑፍ ምንጭ የሆነውን WFGY ProblemMap መጠቀም ይችላሉ። በአጠቃላይ የሚከተሉትን ይሸፍናል፦

- የretrieval መዛባት እና የተበላሹ የcontext ድንበሮች
- ባዶ ወይም ጊዜ ያለፈባቸው index-ዎች እና vector store-ዎች
- የembedding እና semantic አለመጣጣም
- የprompt አሰባሰብ እና የcontext window ችግሮች
- የlogic መፍረስ እና ከልክ በላይ እርግጠኛ የሆኑ መልሶች
- ረጅም chain እና የagent ማስተባበር ብልሽቶች
- የmulti agent memory እና የrole መዛባት
- የdeployment እና bootstrap ቅደም ተከተል ችግሮች

ሐሳቡ ቀላል ነው፦

1. መጥፎ ምላሽን ሲመረምሩ፣ የሚከተሉትን ይመዝግቡ፦
   - የተጠቃሚው ተግባር እና ጥያቄ
   - በOmniRoute ውስጥ ያለው route ወይም የprovider ጥምረት
   - በታችኛው ክፍል ጥቅም ላይ የዋለ ማንኛውም የRAG context (የተገኙ ሰነዶች፣ tool call-ዎች፣ ወዘተ)
2. ክስተቱን ከአንድ ወይም ሁለት የWFGY ProblemMap ቁጥሮች (`No.1` … `No.16`) ጋር ያዛምዱ።
3. ቁጥሩን ከOmniRoute log-ዎች አጠገብ በራስዎ dashboard፣ runbook ወይም incident tracker ውስጥ ያከማቹ።
4. የRAG stack፣ retriever ወይም routing strategyዎን መቀየር እንዳለብዎት ለመወሰን ተዛማጁን የWFGY ገጽ ይጠቀሙ።

ሙሉው ጽሑፍ እና ተግባራዊ መመሪያዎች እዚህ ይገኛሉ (MIT license፣ ጽሑፍ ብቻ)፦

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

ከOmniRoute በስተጀርባ RAG ወይም agent pipeline-ዎችን የማያስኬዱ ከሆነ ይህን ክፍል ችላ ማለት ይችላሉ።

## v3.8.0 የታወቁ ችግሮች

ለv3.8.0 release የተለዩ ችግሮች እና አሁን ያሉ ጊዜያዊ መፍትሔዎቻቸው። መፍትሔ በኋለኛ patch ውስጥ ከተካተተ፣ ግቤቱ ይዘመናል ወይም ይወገዳል።

### የDevin CLI auth ብልሽቶች

**ምልክቶች፦**

- በDevin የሚደገፉ tool-ዎችን ሲጠሩ "Devin CLI አልተገኘም" ወይም "auth አልተሳካም"
- የCLI runtime ምርመራ `installed=false` ያሳያል

**ምክንያቶች፦**

- `CLI_DEVIN_BIN` ወደሌለ ዱካ ያመለክታል
- Devin CLI በhost ላይ አልተጫነም

**መፍትሔ፦**

1. ለplatformዎ Devin CLIን ይጫኑ
2. በ`.env` ውስጥ `CLI_DEVIN_BIN=/usr/local/bin/devin` (ወይም ትክክለኛውን ዱካ) ያዘጋጁ
3. OmniRouteን ዳግም ያስጀምሩ እና ከ**Dashboard → CLI Tools** ዳግም ይፈትሹ

### የModel cooldown ተጣብቋል (በእጅ ዳግም ማስጀመር)

**ምልክቶች፦**

- የማብቂያ ጊዜው ካለፈ በኋላም model በcooldown ውስጥ እንዳለ ተዘርዝሮ ይቆያል
- timestamp-ው ያለፈ ቢሆንም ጥያቄዎች በcombo routing ውስጥ model-ውን አሁንም ይዘሉታል

**በእጅ ዳግም ማስጀመር፦**

- **Dashboard፦** **Settings → Model Cooldowns** → በችግሩ የተጎዳው ካርድ ላይ **Re-enable**ን ጠቅ ያድርጉ
- **API፦** ከmanagement auth header-ዎች ጋር `DELETE /api/resilience/model-cooldowns`

### የCommand Code provider ግንኙነት በ403 ይሳናል

**ምልክቶች፦**

- የCommand Code provider ግንኙነትን ሲፈትሹ 403 ይመለሳል
- አዲስ ከታከለ በኋላ የprovider ካርዱ "ፈቃድ የለውም" ያሳያል

**ምክንያት፦** የOAuth flow አልተጠናቀቀም (callback አልተቀበለም ወይም token አልተቀመጠም)።

**መፍትሔ፦**

- የOAuth flowን ዳግም ለማስጀመር ከCLI `omniroute providers`ን ያስኪዱ፣ ወይም
- OAuthን ከ**Dashboard → Providers → Command Code → Reconnect** ዳግም ያስኪዱ

### ModelScope ከባድ የ429 cooldown-ዎችን ይመልሳል

**ምልክቶች፦**

- ከአነስተኛ ተከታታይ ጥያቄዎች በኋላ በModelScope ላይ በጣም አጭር ወይም ወዲያውኑ የሚጀምሩ cooldown-ዎች
- Combo routing ከተጠበቀው ቀደም ብሎ ModelScopeን ይዘላል

**ምክንያት፦** ModelScope ለprovider-ው የተለዩ `Retry-After` header-ዎችን ያወጣል። v3.8.0 ለእነዚያ header-ዎች የተለየ አያያዝን ይዞ ይመጣል፣ ስለዚህ የቆዩ ስሪቶች እንደ አጠቃላይ የrate-limit ፍንጮች በስህተት ያነቧቸዋል።

**መፍትሔ፦**

- v3.8.0 ወይም ከዚያ በኋላ ባለ ስሪት ላይ መሆንዎን ያረጋግጡ
- በ**Settings → Resilience** ስር ያለው `useUpstream429BreakerHints` toggle መንቃቱን ያረጋግጡ

### OMNIROUTE_WS_BRIDGE_SECRET በproduction ውስጥ የለም

**ምልክቶች፦**

- በርቀት ባለ production host ላይ ሲያስኬዱ በእያንዳንዱ የCodex/Responses WebSocket bridge ጥያቄ ላይ 401 ይመለሳል
- የWebSocket bridge handshake ከተገናኘ በኋላ ወዲያውኑ ይዘጋል

**ምክንያት፦** የ`OMNIROUTE_WS_BRIDGE_SECRET` env var ከproduction environment ውስጥ የለም።

**መፍትሔ፦**

1. የዘፈቀደ secret ይፍጠሩ፦ `openssl rand -hex 32`
2. በproduction server env ውስጥ `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>`ን ያዘጋጁ (እና ከbridge-ው ጋር በሚገናኝ ማንኛውም client ውስጥ)
3. OmniRouteን ዳግም ያስጀምሩ

### Responses API፦ background mode ወደ synchronous ዝቅ ብሏል

**ምልክቶች፦**

- የተመዘገበ ማስጠንቀቂያ፦ `background mode degraded to synchronous`
- የ`background: true` ጥያቄ ከbackground job handle ይልቅ መደበኛ synchronous ምላሽ ይመልሳል

**ምክንያት፦** v3.8.0 ማስጠንቀቂያ እያወጣ በResponses API ላይ `background: true`ን ሆን ብሎ ወደ synchronous execution ዝቅ ያደርገዋል። ሙሉ async background execution ወደፊት የሚቀርብ ባህሪ ነው።

**መፍትሔ፦**

- client-ውን `background` ሳይጠቀም እንዲጠራ ያስተካክሉ፣ ወይም
- ሙሉ async background modeን የሚያቀርብ የኋለኛ release ይጠብቁ (changelog-ውን ይከታተሉ)

## የዝግታ ማስጀመር / የዝግጁነት ጊዜ ማብቂያ

CLIው `⚠ ሰርቨሩ በ60 ሰከንድ ውስጥ ምላሽ አልሰጠም` ብሎ ቢያሳይ፣ ነገር ግን ሰርቨሩ
በትክክል እየሰራ ከሆነ፣ የዝግጁነት ምርመራው የጊዜ ገደብ ለአካባቢዎ በጣም አጭር ነው።

ይህ በተለምዶ Windows ላይ (በጸረ-ቫይረስ፣ በፋይል ስርዓት ተከታታዮች) ወይም ከባድ
የማስጀመሪያ የሥራ ጫና ባለባቸው ኮንቴይነሮች ውስጥ ይከሰታል።

**መፍትሔ — የጊዜ ገደቡን ያሳድጉ፦**

```bash
# በአካባቢ ተለዋዋጭ በኩል (በማስጀመሮች መካከል ይቆያል)፦
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 ደቂቃዎች
omniroute serve

# በCLI አማራጭ በኩል (ለአንድ ጊዜ)፦
omniroute serve --ready-timeout 180000
```

ነባሪው 60 000 ms (60 s) ነው። ማስጠንቀቂያው ለመረጃ ብቻ ነው፤ ሰርቨሩ
ከበስተጀርባ መጀመሩን ይቀጥላል፣ እና ማስነሳቱ እንደተጠናቀቀ ተደራሽ ይሆናል።

ስለ `OMNIROUTE_READY_TIMEOUT_MS` ሙሉ ዝርዝሮች [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md)ን
ይመልከቱ።
