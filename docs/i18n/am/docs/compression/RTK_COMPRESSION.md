RTK compression ለተርሚናል እና ለመሣሪያ ውጤት የተዘጋጀ የOmniRoute ትዕዛዝ-ተኮር የማመቅ ሞተር ነው። አብዛኛው የአውድ እድገት ከሙከራ ምዝግቦች፣ ከግንባታ ውጤት፣ ከፓኬጅ አስተዳዳሪ የተትረፈረፈ ውጤት፣ ከሼል ግልባጮች፣ ከDocker ውጤት፣ ከgit ውጤት እና ከቁልል ዱካዎች ለሚመጣባቸው የኮዲንግ-ወኪል ክፍለ ጊዜዎች የተነደፈ ነው።

RTK በቀጥታ በ`defaultMode: "rtk"` ወይም በተደራራቢ ቧንቧ መስመር ውስጥ እንደ መጀመሪያው ደረጃ ሊሠራ ይችላል፤ በተለምዶ፦

```txt
rtk -> caveman
```

ይህ ቅደም ተከተል በመጀመሪያ የተትረፈረፈውን የማሽን ውጤት ያመቃል፣ ከዚያም Caveman የቀረውን ጽሑፍ እንዲያጠቃልል ያስችለዋል።

የላይኛው ምንጭ RTK በትዕዛዝ ውጤት ላይ `60-90%` ቁጠባ እንዳለ ዘግቧል። በREADME ውስጥ ያለው የናሙና ክፍለ ጊዜ ከ`~118,000` መደበኛ ቶከኖች ወደ `~23,900` RTK ቶከኖች ይቀንሳል፤ ይህም `79.7%` ቁጠባ (`~80%`) ነው። OmniRoute ያንን የላይኛው ምንጭ አማካይ ከCaveman የግቤት ማመቅ ጋር ለተደራራቢው የቁጠባ ስሌት ይጠቀማል፦

```txt
የRTK አማካይ፦    80% ተቆጥቧል
የCaveman ግቤት፦ 46% ተቆጥቧል
የተደራረበ፦       1 - (1 - 0.80) * (1 - 0.46) = 89.2% ተቆጥቧል
ክልል፦             1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

## የማጣሪያ መፍትሔ ሂደት

RTK ማጣሪያዎችን በዚህ ቅደም ተከተል ይጭናል፦

1. የፕሮጀክት ማጣሪያዎች ከ`.rtk/filters.toml` እና `.rtk/filters.json`፣ የታመኑ ሲሆኑ ብቻ።
2. ዓለም አቀፍ ማጣሪያዎች ከ`DATA_DIR/rtk/filters.toml` እና `DATA_DIR/rtk/filters.json`።
3. አብሮገነብ ማጣሪያዎች ከ`open-sse/services/compression/engines/rtk/filters/`።

በተመሳሳይ ወሰን ውስጥ፣ የRTK TOML schema v1 ማጣሪያዎች ከOmniRoute JSON ማጣሪያዎች ቅድሚያ ያገኛሉ። ከውጭ የመጣ ትዕዛዝ-ተኮር ማጣሪያ በዚያ ወሰን ውስጥ ያለን ይበልጥ ሰፊ ማጣሪያ እንዲተካ፣ የTOML `match_command` አገላለጾች ከትዕዛዝ-ዓይነት ማዛመድ በፊት ይፈተሻሉ። የፕሮጀክት ወሰን የፋይል ቅርጸቱ ምንም ይሁን ምን ከዓለም አቀፍ ወሰን ቅድሚያ ያገኛል።

የregex ማጣሪያዎች የመሣሪያ ውጤት ለወኪሎች የሚታይበትን መንገድ ሊቀይሩ ስለሚችሉ፣ የፕሮጀክት ማጣሪያዎች ሆን ተብሎ በእምነት ማረጋገጫ ተገድበዋል። ከእነዚህ አንዱ እውነት ሲሆን የፕሮጀክት ማጣሪያ ፋይል ተቀባይነት ያገኛል፦

- `rtkConfig.trustProjectFilters` `true` ነው።
- `OMNIROUTE_RTK_TRUST_PROJECT_FILTERS=1` ተቀናብሯል።
- `.rtk/trust.json` ለፕሮጀክቱ ማጣሪያ ፋይል ተዛማጅ የSHA-256 hash ይዟል።

የእምነት ፋይል ምሳሌ፦

```json
{
  "filtersSha256": "0123456789abcdef...",
  "filtersTomlSha256": "fedcba9876543210..."
}
```

hash-ዎቹ የተለያዩ ናቸው፦ `filtersSha256` `.rtk/filters.json`ን ያምናል፣ `filtersTomlSha256` ደግሞ `.rtk/filters.toml`ን ያምናል። ከሁለቱ ፋይሎች አንዱን ማርትዕ የራሱን የእምነት ግቤት ብቻ ዋጋ ያሳጣል። ዓለም አቀፍ ፋይሎች በአስተዳዳሪ የተጫኑ ሲሆኑ ነባሩን የዓለም አቀፍ ማጣሪያ የእምነት ባህሪ ይጠቀማሉ።

ብጁ ማጣሪያዎች አንድ የማጣሪያ ነገር ወይም የማጣሪያ ነገሮች ድርድር ሊሆኑ ይችላሉ። ልክ ያልሆኑ ብጁ ማጣሪያዎች ይዘለላሉ እና በ`/api/context/rtk/filters` ምርመራዎች ሪፖርት ይደረጋሉ። ልክ ያልሆኑ አብሮገነብ ማጣሪያዎች ወዲያውኑ እንዲቋረጥ ያደርጋሉ።

## RTK TOML schema v1 ተኳኋኝነት

OmniRoute RTK TOML schema v1ን የሚጠቀሙ መግለጫዊ የማጣሪያ ፋይሎችን መተንተን፣ ማረጋገጥ፣ መፈተሽ እና መጫን ይችላል።
የሚደገፉት መስኮች `description`፣ `match_command`፣ `strip_ansi`፣ `filter_stderr`፣
`strip_lines_matching`፣ `keep_lines_matching`፣ `replace`፣ `match_output`፣ `truncate_lines_at`፣
`head_lines`፣ `tail_lines`፣ `max_lines`፣ `on_empty` እና `[[tests.<filter>]]` የውስጥ መስመር ፈተናዎች ናቸው።
ያልታወቁ መስኮች፣ ልክ ያልሆኑ ወይም ደህንነታቸው ያልተጠበቀ መደበኛ አገላለጾች፣ በአንድ ጊዜ የሚገለጹ የማስወገጃ/ማቆያ ደንቦች፣
ከ1 MiB በላይ የሆኑ ፋይሎች እና ያልታወቁ ማጣሪያዎችን የሚጠቅሱ ማጣቀሻዎች ውድቅ ይደረጋሉ። የውስጥ መስመር ፈተናዎቹ ያልተሳኩበት ፋይል ለምርመራ
ሊረጋገጥ ይችላል፣ ነገር ግን ሊጫን ወይም ወደ ስርዓቱ ሊገባ አይችልም። ብጁ ፋይልን ወደ ስርዓቱ ማስገባት ሲሳነው
ሁኔታው fail-open ሆኖ ይቀጥላል፦ ልክ ያልሆነው ፋይል ይዘለላል፣ ቀሪዎቹ ማጣሪያዎችም መስራታቸውን ይቀጥላሉ።

OmniRoute የመሣሪያውን ውፅዓት የሚቀበለው ደንበኛው አስቀድሞ ከያዘው በኋላ ስለሆነ፣ `filter_stderr = true`
የሂደቱን መያዝ ሊለውጥ አይችልም። መስኩ ምንም እርምጃ እንደማይወስድ ሆኖ ተቀባይነት ያገኛል፣ ማረጋገጡም ማስጠንቀቂያ ይመልሳል።
ይህ ሆን ተብሎ **RTK TOML schema v1 ተኳኋኝነት** ተብሎ ይገለጻል፤ ከRTK አስፈጻሚ ፋይል፣ shell hooks፣ Rust የትዕዛዝ ትግበራዎች ወይም የtrust-store አቀማመጡ ጋር ሙሉ ተኳኋኝነት እንዳለው አይገልጽም።

የዳሽቦርዱ የላቀ RTK እይታ የተለጠፈ ወይም የተሰቀለ TOML ይቀበላል። ማረጋገጡ ለንባብ ብቻ ነው።
መጫኑ `DATA_DIR/rtk/filters.toml`ን በጥብቅ ፈቃዶች በአቶሚክ መንገድ ይጽፋል፣ እንደገና ማስጀመር ሳያስፈልግም
ቀጥታ የሚሰራውን የማጣሪያ ካታሎግ ያድሳል። ነባር ፋይልን ለመተካት ግልጽ የ`overwrite`
ማረጋገጫ ያስፈልጋል፣ እንዲሁም በመጀመሪያ `DATA_DIR/rtk/filters.toml.bak`ን ይፈጥራል።

## የማጣሪያ DSL

ማጣሪያዎች በ[Compression Rules Format](./COMPRESSION_RULES_FORMAT.md) የተገለጸውን JSON schema ይጠቀማሉ።
runtime እነዚህን ደረጃዎች በቅደም ተከተል ይተገብራል፦

```txt
stripAnsi -> filterStderr -> replace -> matchOutput -> drop/include lines
  -> truncateLineAt -> head/tail/maxLines -> onEmpty
```

አስፈላጊ መስኮች፦

| መስክ                          | ዓላማ                                              |
| ---------------------------- | ------------------------------------------------ |
| `rules.stripAnsi`            | ከማዛመድ በፊት የተርሚናል ቀለም/መቆጣጠሪያ ተከታታዮችን ማስወገድ        |
| `rules.filterStderr`         | ከማዛመድ/ማጣራት በፊት የተለመዱ stderr ቅድመ ቅጥያዎችን ወጥ ማድረግ   |
| `rules.replace`              | በቅደም ተከተል የተቀመጡ የregex ምትክ ለውጦችን መተግበር           |
| `rules.matchOutput`          | ውፅዓቱ ከታወቀ ሁኔታ ጋር ሲዛመድ የታመቀ ማጠቃለያ መመለስ            |
| `rules.matchOutput[].unless` | የስህተት/ውድቀት ጥለት ሲኖር አቋራጩን መዝለል                    |
| `rules.dropPatterns`         | ጫጫታ የበዛባቸውን መስመሮች ማስወገድ                          |
| `rules.includePatterns`      | ተግባራዊ እርምጃ ሊወሰድባቸው ለሚችሉ መስመሮች ቅድሚያ መስጠት          |
| `rules.collapsePatterns`     | ተደጋጋሚ የሚዛመዱ መስመሮችን ማጠቃለል                         |
| `rules.deduplicate`          | ለእያንዳንዱ ማጣሪያ በተናጠል የሚነቃ፦ ተከታታይ የተባዙ መስመሮችን ማጠቃለል |
| `rules.truncateLineAt`       | Unicodeን በማይጎዳ መንገድ እያንዳንዱን መስመር መቁረጥ            |
| `rules.onEmpty`              | ሁሉም መስመሮች ከተጣሩ የሚታይ አማራጭ መልዕክት                   |
| `tests[]`                    | በማረጋገጫ ደረጃው የሚጠቀሙ የውስጥ መስመር ናሙናዎች                |

አብረው የተካተቱ ማጣሪያዎች የውስጥ መስመር `tests[]` ናሙናዎችን እንዲያካትቱ ይጠበቃል። ብጁ ማጣሪያዎችም
እነዚህን ማካተት አለባቸው፣ በተለይም በተለያዩ ፕሮጀክቶች መካከል ሲጋሩ።

## የመስመር ብዜት ማስወገድ (ሁለት ደረጃዎች)

RTK የተደጋገሙ መስመሮችን በሁለት እርስ በርሳቸው ነጻ በሆኑ ደረጃዎች ያጣምራል፦

1. **በእያንዳንዱ ማጣሪያ `deduplicate` (በምርጫ የሚነቃ፣ ነባሪው `false`)።** አንድ ማጣሪያ `rules.deduplicate: true`
   በማዘጋጀት፣ ከመቆረጡ በፊት _ከዚያ ማጣሪያ ጋር በተዛመደው ውጤት ውስጥ_ ያሉ ተከታታይ የተባዙ መስመሮችን ማጣመር ይችላል።
   ይህ በ`lineFilter.ts` ውስጥ ይከናወናል። ለቀድሞ ማጣሪያዎች፣ ማጣሪያው
   `collapsePatterns` ን ሲገልጽ በራስ-ሰር ይነቃል። መርሃግብር፦ `deduplicate: z.boolean().default(false)` በ
   `open-sse/services/compression/engines/rtk/filterSchema.ts` ውስጥ።
2. **የመተግበሪያ ሞተሩ አጠቃላይ `deduplicateThreshold` (ነባሪው `3`)።** ሁሉም ማጣሪያዎች ከተከናወኑ በኋላ፣ ሞተሩ
   በጠቅላላው ውጤት ውስጥ `>= deduplicateThreshold` ተመሳሳይ ተከታታይ መስመሮች ያሉበትን
   ማንኛውንም ተከታታይ ስብስብ ያጣምራል
   (`deduplicateRepeatedLines`፣ በ`engines/rtk/index.ts` ውስጥ የሚተገበር)። በመደበኛነት ሲዋቀር እሴቱ ከ2–100 ባለው ክልል ይገደባል።

የእያንዳንዱ ማጣሪያ ሂደት መጀመሪያ ይከናወናል (በማጣሪያው ውስጥ)፣ የመተግበሪያ ሞተሩ አጠቃላይ ሂደት ደግሞ መጨረሻ ይከናወናል (በተቀላቀለው
ውጤት ላይ)፤ ስለዚህ ሁለቱ ድርብ ቆጠራ ሳይፈጥሩ ተደራርበው ይሰራሉ።

## የመስመር ማቧደን (`enableGrouping`)

`rtkConfig.enableGrouping` `true` ሲሆን (ነባሪው `false`)፣ RTK ከብዜት ማስወገድ በኋላ ባለው ውጤት ላይ ተጨማሪ
`groupSimilarLines` ሂደትን ያከናውናል፤ ይህም _እጅግ ተቀራራቢ_ (በባይት ደረጃ ፍጹም ተመሳሳይ ያልሆኑ)
ተከታታይ መስመሮችን ያጣምራል። `rtkConfig.groupingThreshold` (ነባሪው `3`) ማቧደንን ለማስጀመር
የሚያስፈልገው ዝቅተኛው ተከታታይ መስመሮች ብዛት ነው። ይህ የ`deduplicateThreshold` መዋቅራዊ አቻ ነው፦ ብዜት ማስወገድ ፍጹም ተመሳሳይ ድግግሞሾችን ያስተናግዳል፣
ማቧደን ደግሞ "ተመሳሳይ ቅርጽ ያላቸው ጥቃቅን ልዩነቶች" ያሉባቸውን ያስተናግዳል። ሁለቱም ማመልከቻዎች በ`key_value` ሰንጠረዥ ውስጥ የሚቀመጠው
የ`rtkConfig` JSON አካል ናቸው (ከላይ ያለውን ውቅር ይመልከቱ)፤ ስለዚህ ቅንብሩ ዳግም ከተጀመረ በኋላም ይቆያል።

## የኮድ አስተያየቶችን ማስወገድ (`stripCodeComments` / `preserveDocstrings`)

`rtkConfig.applyToCodeBlocks` ሲነቃ፣ RTK በአጥር ከተከበቡ የኮድ ብሎኮች ውስጥ ያሉ አስተያየቶችንም ማስወገድ ይችላል፦

- `stripCodeComments` (ነባሪው `false`) — በምርጫ የሚነቃ። `true` ሲሆን፣ RTK በJavaScript
  እና TypeScript የኮድ ብሎኮች ውስጥ ያሉ አስተያየቶችን ያስወግዳል። ከታሪክ አንጻር ማመልከቻው ይነበብ ነበር እንጂ ተግባራዊ አልነበረም፤ ስለዚህ በምርት አካባቢ ያለማሳወቅ ለውጥ እንዳይኖር
  ነባሪው "ማቆየት" ሆኖ ይቀጥላል።
- `preserveDocstrings` (ነባሪው `true`) — አስተያየቶችን በሚያስወግድበት ጊዜ፣ የJSDoc/`/** … */` ብሎክ አስተያየቶች
  ይቀመጣሉ (ከሚወስዱት ባይቶች የበለጠ ዋጋ ያለው የAPI ሰነድ ይይዛሉ)። እነዚያንም ለማስወገድ
  `false` ያድርጉት።

አስተያየት ማስወገድ በ`open-sse/services/compression/engines/rtk/codeStripper.ts` ውስጥ ተግባራዊ ተደርጓል። የጽሑፍ፣ የአብነት እና የመደበኛ አገላለጽ ሊተራሎች በስህተት እንደ
አስተያየት እንዳይወሰዱ **የTypeScript ተንታኝን** (መደበኛ አገላለጽን ሳይሆን) ይጠቀማል፤ እንዲሁም JSX ሲገኝ ሂደቱን ሙሉ በሙሉ ያቋርጣል (በዚህም በJSX የአገላለጽ ማስቀመጫዎች ውስጥ ያሉ አስተያየቶች
ፈጽሞ አይበላሹም)። በአሁኑ ጊዜ አስተያየት ማስወገድ የሚተገበረው **በJavaScript እና TypeScript ላይ ብቻ** ነው — በማስወገጃው `CodeLanguage` ስብስብ ውስጥ ያሉ ሌሎች
ቋንቋዎች (Python፣ Rust፣ Go፣ Ruby፣ Java) ባዶ መስመሮችን እና
ነጭ ቦታዎችን ማጣመር ይደረግባቸዋል፣ ነገር ግን አስተያየቶች አይወገዱም። የተወገደው ብሎክ ሂደት በ`rulesApplied` ውስጥ `rtk:code-strip` የሚል መለያ ይሰጠዋል።

> **ማስታወሻ — GCF / ሰንጠረዣዊ ኢንኮዲንግ የተለየ ሞተር ነው።** RTK የ"GCF"
> (Graph Compact Format) ሰንጠረዣዊ/አምዳዊ JSON ኢንኮደርን **አያካትትም**። ያ ኢንኮደር — የቀድሞውን
> `omni-tabular` ኢንኮደር የተካው — በ**headroom** ሞተር ውስጥ ይገኛል
> (`open-sse/services/compression/engines/headroom/`፣ አብሮ የተካተተው ኮዴክ ደግሞ በ
> `headroom/gcf/` ስር ይገኛል)። እዚህ ከተመዘገበው የRTK ማጣሪያ ሂደት ጋር ግንኙነት የለውም።

## ውቅር

አጠቃላይ ቅንብሮች በ `/api/settings/compression` በኩል ይገኛሉ። ለ-RTK የተለዩ ቅንብሮችም
በ `/api/context/rtk/config` በኩል ይገኛሉ።

```json
{
  "defaultMode": "stacked",
  "autoTriggerMode": "stacked",
  "autoTriggerTokens": 32000,
  "stackedPipeline": [
    { "engine": "rtk", "intensity": "standard" },
    { "engine": "caveman", "intensity": "full" }
  ],
  "rtkConfig": {
    "enabled": true,
    "intensity": "standard",
    "applyToToolResults": true,
    "applyToCodeBlocks": false,
    "applyToAssistantMessages": false,
    "enabledFilters": [],
    "disabledFilters": [],
    "maxLinesPerResult": 120,
    "maxCharsPerResult": 12000,
    "deduplicateThreshold": 3,
    "customFiltersEnabled": true,
    "trustProjectFilters": false,
    "rawOutputRetention": "never",
    "rawOutputMaxBytes": 1048576,
    "enableGrouping": false,
    "groupingThreshold": 3,
    "stripCodeComments": false,
    "preserveDocstrings": true
  }
}
```

`enabledFilters` እና `disabledFilters` እንደ `test-vitest` ወይም `git-diff` ያሉ የማጣሪያ መለያዎችን ይጠቀማሉ።

ሙሉው የ `rtkConfig` አወቃቀር በ
`open-sse/services/compression/types.ts` ውስጥ ባሉት `RtkConfig` / `DEFAULT_RTK_CONFIG` ይገለጻል። ሙሉው ኦብጀክት በ
SQLite `key_value` ሰንጠረዥ ውስጥ በ `namespace = "compression"`፣ `key = "rtkConfig"`
(`src/lib/db/compression.ts`) ስር እንደ አንድ JSON እሴት በቋሚነት ይቀመጣል፣ እና ሲነበብ በ `normalizeRtkConfig` ደረጃውን የጠበቀ ይደረጋል። ስለዚህ ከታች ያለው እያንዳንዱ መስክ
— `enableGrouping`፣ `groupingThreshold`፣ `stripCodeComments` እና `preserveDocstrings`ን ጨምሮ —
በተመሳሳዩ ማከማቻ በኩል ተጽፎ እንደገና ይነበባል፣ እንዲሁም ዳግም ከተጀመረ በኋላም ይቆያል።

| ቁልፍ                    | ነባሪ     | ዓላማ                                                                    |
| ---------------------- | ------- | ---------------------------------------------------------------------- |
| `deduplicateThreshold` | `3`     | በመላው ሞተሩ፦ ለማጠቃለል የሚያስፈልጉ በተከታታይ ያሉ ተመሳሳይ መስመሮች ዝቅተኛ ብዛት (በ2–100 የተገደበ) |
| `enableGrouping`       | `false` | በምርጫ የሚነቃ፦ በተከታታይ ያሉ በጣም ተመሳሳይ መስመሮችን ማጠቃለል                            |
| `groupingThreshold`    | `3`     | ማቧደንን የሚያስጀምር የተከታታይ ተመሳሳይ መስመሮች ዝቅተኛ ብዛት                              |
| `stripCodeComments`    | `false` | በምርጫ የሚነቃ፦ ከታጠሩ የኮድ ብሎኮች አስተያየቶችን ማስወገድ (`applyToCodeBlocks` ያስፈልገዋል)  |
| `preserveDocstrings`   | `true`  | አስተያየቶችን ሲያስወግድ፣ የJSDoc/`/** … */` ብሎኮችን ማቆየት                          |

## API

| መስመር                               | ዘዴ   | ዓላማ                                     |
| ---------------------------------- | ---- | --------------------------------------- |
| `/api/context/rtk/config`          | GET  | የRTK ውቅርን ማንበብ                          |
| `/api/context/rtk/config`          | PUT  | የRTK ውቅርን ማዘመን                          |
| `/api/context/rtk/filters`         | GET  | የማጣሪያ ካታሎግን እና የመጫን ምርመራ መረጃን መዘርዘር     |
| `/api/context/rtk/import`          | POST | የRTK TOML schema v1 ፋይሎችን ማረጋገጥ ወይም መጫን |
| `/api/context/rtk/test`            | POST | ለአንድ የጽሑፍ ውሂብ የRTK መጭመቅን ቅድመ ዕይታ ማሳየት   |
| `/api/context/rtk/raw-output/[id]` | GET  | ተይዞ የቆየ ስሱ መረጃው የተሸፈነ ጥሬ ውጤትን ማንበብ      |
| `/api/compression/preview`         | POST | ማንኛውንም የመጭመቅ ሁነታ ቅድመ ዕይታ ማሳየት           |

የRTK ሙከራ ውሂብ፦

```json
{
  "command": "npm test",
  "text": "FAIL tests/example.test.ts\nAssertionError: expected true\nTest Files 1 failed",
  "config": {
    "intensity": "standard"
  }
}
```

የመጭመቅ ቅድመ ዕይታ ውሂብ፦

```json
{
  "mode": "stacked",
  "messages": [
    {
      "role": "tool",
      "content": "FAIL tests/example.test.ts\nAssertionError: expected true\nTest Files 1 failed"
    }
  ],
  "config": {
    "rtkConfig": {
      "rawOutputRetention": "failures"
    }
  }
}
```

የአስተዳደር መስመሮች የዳሽቦርድ አስተዳደር ማረጋገጫ ወይም ተዛማጅ የAPI ቁልፍ ፖሊሲ ያስፈልጋቸዋል።

የRTK TOML ማረጋገጫ ውሂብ፦

```json
{
  "action": "validate",
  "content": "schema_version = 1\n\n[filters.my-tool]\nmatch_command = \"^my-tool\\\\b\"\nmax_lines = 20\n"
}
```

የተረጋገጠውን ፋይል በሁሉም ቦታ ለመጫን `"action": "install"`ን ይጠቀሙ። ነባር አጠቃላይ ፋይል መተካቱን
ከገመገሙና ካረጋገጡ በኋላ ብቻ `"overwrite": true`ን ያክሉ።

## ጥሬ ውጤትን መልሶ ማግኘት

RTK በመደበኛነት የታመቀ ጽሑፍን ብቻ ይመልሳል። ለማረም፣ `rawOutputRetention` የተሸሸገ
ጥሬ ውጤትን ሊያቆይ ይችላል፦

| እሴት        | ባህሪ                                    |
| ---------- | -------------------------------------- |
| `never`    | ጥሬ ውጤትን አታቆይ                           |
| `failures` | የመክሸፍ ዕድሉ ያለውን ውጤት ብቻ አቆይ              |
| `always`   | ከመሸሸግ በኋላ እያንዳንዱን የታመቀ የRTK ጥሬ ውጤት አቆይ |

የተቀመጡ ፋይሎች በሚከተለው ስር ይጻፋሉ፦

```txt
DATA_DIR/rtk/raw-output/
```

ሚስጥሮች በቋሚነት ከመቀመጣቸው በፊት ይሸሸጋሉ፤ ይህም የተለመዱ bearer tokens፣ API keys፣ Slack tokens፣
AWS access keys፣ እና በምደባ ቅርጽ የተጻፉ `token=...`፣ `secret=...`፣ `password=...` እሴቶችን ያካትታል። ትንታኔዎች
የማመሳከሪያ id፣ መጠን እና hash metadata ብቻ ያከማቻሉ።

## RTKን ማስፋት

1. የfilter JSON ፋይል ያክሉ ወይም ያዘምኑ።
2. አስፈላጊውን ባህሪ የሚያረጋግጥ ቢያንስ አንድ `tests[]` ናሙና ያካትቱ።
3. ለአዳዲስ የትዕዛዝ ቤተሰቦች በ`tests/unit/compression/fixtures/rtk/` ስር fixture ያክሉ።
4. አዲስ የውጤት ምድብ ሲያስገቡ የትዕዛዝ ማወቂያ ሽፋን ያክሉ።
5. የማረጋገጫውን እና ሰፊውን የRTK በሮች ያስኪዱ።
6. filterው ለፕሮጀክቱ ብቻ የሚውል ከሆነ፣ `.rtk/filters.json`ን commit ያድርጉ እና `.rtk/trust.json`ን ከግምገማ በኋላ ብቻ ያድሱ።

## የጥንካሬ ደረጃዎች (v3.8.16+)

RTK በ**ማመቅ ጥብቅነት** እና **ደህንነት** መካከል ሚዛን የሚጠብቁ **3 የጥንካሬ ደረጃዎችን** ይደግፋል። ደረጃው በengine config ውስጥ ባለው `config.intensity` በኩል ይዘጋጃል።

### 3ቱ ደረጃዎች

| ደረጃ              | የመቁረጫ ገደብ     | የtoken ቁጠባ | አደጋ      | በጣም የሚመችበት                 |
| ---------------- | ------------- | ---------- | -------- | -------------------------- |
| `minimal`        | በክፍል 24 መስመሮች | ~20-40%    | በጣም ዝቅተኛ | ወሳኝ context ያለው production |
| `standard` (ነባሪ) | በክፍል 24 መስመሮች | ~50-70%    | ዝቅተኛ     | ዕለታዊ የኮድ አጻጻፍ sessions     |
| `aggressive`     | በክፍል 16 መስመሮች | ~70-90%    | መካከለኛ    | ረጅም sessions፣ ከፍተኛ ቁጠባ     |

### ብጁ ማጣሪያዎችን መጫን

ፋይሉን በታወቀ አካባቢ ያስቀምጡ፦

```
~/.omniroute/rtk/filters/my-filter.json     # የተጠቃሚ ደረጃ
<project>/.rtk/filters/my-filter.json      # የፕሮጀክት ደረጃ
```

ማጣሪያዎች ሲጀመር በ`open-sse/services/compression/engines/rtk/filterLoader.ts` ውስጥ ባለው `loadRtkFilters()` በኩል በራስ-ሰር ይጫናሉ። ጫኚው ማጣሪያዎችን ከሚከተሉት ቦታዎች ያገኛል፦

- አብሮገነብ ካታሎግ፦ `open-sse/services/compression/engines/rtk/filters/`
- የተጠቃሚ ማውጫ፦ `~/.omniroute/rtk/filters/`
- የፕሮጀክት ማውጫ፦ `<project>/.rtk/filters/`

### ማረጋገጫ

ማጣሪያዎች በሚጫኑበት ጊዜ ከZod መዋቅር ጋር እንዲጣጣሙ ይረጋገጣሉ። መዋቅሩ የተሳሳተ ማጣሪያ መጫን ይሳነዋል እና ስህተት ይመዘገባል፦

```
RTK_FILTER_LOADER: የ"my-filter" ማጣሪያ ማረጋገጫውን አላለፈም፦
  - rules.replace.0.pattern: ልክ ያልሆነ regex
  - match.commands: ባዶ መሆን የለበትም
```

ሁሉንም የተጫኑ ማጣሪያዎች ለማረጋገጥ፣ ከ`open-sse/services/compression/engines/rtk/verify.ts` የሚላከውን `runRtkFilterTests()` ይጥሩ።

### ምርጥ ልምዶች

1. **ሁልጊዜ `tests[]`ን ያካትቱ** — ማጣሪያዎ እንደሚሠራ ያረጋግጣሉ፣ የቀድሞ ችግሮች ዳግም እንዳይከሰቱም ይከላከላሉ
2. **ለአጭር ማቋረጫዎች `matchOutput`ን ይጠቀሙ** — አንድ መስመር ብቻ ሁኔታውን በቂ ሁኔታ የሚገልጽ ከሆነ፣ ሙሉውን ብሎክ ይተኩ
3. **ከ`strip` ይልቅ `keep`ን ይምረጡ** — ግልጽ የሆኑ “ሁልጊዜ አቆይ” ደንቦች ከ“ሁልጊዜ አስወግድ” ደንቦች የበለጠ ደኅንነታቸው የተጠበቀ ነው
4. **በሁሉም 3 የጥንካሬ ደረጃዎች ይፈትሹ** — `minimal` ምንም ለውጥ ማድረግ የለበትም፤ `aggressive`ም አሁንም ስህተቶችን መጠበቅ አለበት
5. **የ`unless` መስኩን ይጠቀሙ** — አጭር ማቋረጫዎችን “X ካለ እንዳይነሳሱ” በሚል ቅድመ ሁኔታ ይጠብቁ

### ጥሬ ውጤትን መልሶ ማግኘት እንዴት እንደሚሠራ


### ዋናውን ውጤት መልሶ ማግኘት
