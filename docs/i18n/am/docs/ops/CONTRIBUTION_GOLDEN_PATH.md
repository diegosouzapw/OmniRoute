ይህን መመሪያ በመጠቀም ለአንድ pull request አነስተኛውንና አስተማማኝ የልማት ዑደት ይምረጡ። ይህ ከዚህ በታች
የተገናኙትን ለየአካባቢው የተለዩ የአርክቴክቸርና የደህንነት ሰነዶች አይተካም፤ እያንዳንዱን የተለመደ
የለውጥ ዓይነት ከውሎቹ፣ ከተኮሩ ፍተሻዎቹና ከCI ሽፋኑ ጋር ያገናኛል።

## እያንዳንዱ ለውጥ የሚከተለው መንገድ

1. **አርትዖት ከመጀመርዎ በፊት base-ውን ይምረጡ።** ከፍተኛውን ንቁ `release/v*` branch ያግኙና
   ከጫፉ branch ይፍጠሩ። `main`ን ሳይሆን ያንን branch ዒላማ ያድርጉ። የrelease freeze ተግባራዊ ከሆነ፣ የታገደውን
   branch ዒላማ አያድርጉ፤ በ
   [Branching & Release Model](BRANCHING_MODEL.md) የተገለጸውን ቀጣዩን ንቁ ዑደት ይጠቀሙ።
2. **ውሎቹን ይሰይሙ።** ለውጡ የሚነካቸውን እያንዳንዱን catalog፣ schema፣ የተፈጠረ artifact፣ public API ወይም የተጠቃሚ
   interface ይለዩ። ከታች ያለው ሰንጠረዥ ዝቅተኛውን የመነሻ ስብስብ ያቀርባል።
3. **የተኮሩ tests ይጻፉ ወይም ያዘምኑ።** በ`src/`፣ `open-sse/`፣ `electron/` ወይም
   `bin/` ውስጥ የሚደረጉ የproduction ለውጦች በዚያው PR ውስጥ automated test ያስፈልጋቸዋል። ባህሪውን
   የሚያረጋግጡ አነስተኛዎቹን test files ያስኪዱ፣ ከዚያም የተዘረዘሩትን የተኮሩ gates ያስኪዱ።
4. **CI ሰፊውን matrix እንዲያስኬድ ይፍቀዱ።** ሙሉዎቹ unit shards፣ Vitest፣ coverage ratchet እና
   production build በPR ላይ ይሰራሉ። የተኮረ ውድቀት ሰፊ ተጽዕኖ እንዳለ ሲያመለክት
   ወይም ለውጡ በበርካታ subsystems ላይ ሲዘረጋ ብቻ ሰፊ suiteን በአካባቢዎ ያስኪዱ።
5. **ከreview በፊት ያስማሙ።** ንቁውን base fetch ያድርጉ፣ አዲሶቹን commits እና ከእሱ አንጻር ያለውን
   diffዎን ይመርምሩ፣ ከዚያም በcontributor workflow መሠረት base-ውን rebase ወይም merge ያድርጉ። የgenerated-file
   እና catalog conflictsን ከምንጫቸው ይፍቱ፣ እንደገና ያመንጩዋቸው፣ የተኮረውን ዑደት እንደገና ያስኪዱ፣ እና
   PR-ው አሁንም ንቁውን release branch ዒላማ ማድረጉን ያረጋግጡ።
6. **ማስረጃ ይመዝግቡ።** በPR template ውስጥ ያስኬዷቸውን commands፣ የተጨመሩ ወይም የተቀየሩ እያንዳንዱን test file፣
   migrations ወይም feature flags፣ እና ገና ያልተጠናቀቀ CI-only validation ይዘርዝሩ።

## በለውጥ ዓይነት የተደራጁ ዋና መንገዶች

ከታች ያሉት commands ዝቅተኛዎቹ የተኮሩ ፍተሻዎች ናቸው፤ የቀየሩትን ባህሪ በቀጥታ የሚሸፍን test
ለመዝለል ፈቃድ አይደሉም።

### Provider

**ውሎች**

- በ`src/shared/constants/providers/` ውስጥ ያለው Provider definition እና በ
  `src/shared/constants/providers.ts` ውስጥ ያለው composition።
- በ`open-sse/config/providerRegistry.ts` ወይም በተለዩት registry files ውስጥ ያሉ models እና capabilities።
- Executor/translator selection፣ OAuth ወይም API-key configuration፣ dashboard assets፣ እና ተፈጻሚ ሲሆን የተፈጠረ
  provider reference።
- Public credentials `resolvePublicCred()`ን መጠቀም አለባቸው፤ error responses የጋራ sanitized
  error helpersን መጠቀም አለባቸው። `docs/security/PUBLIC_CREDS.md`ን (git፤ ወደ`/docs` አይcompiledም) እና
  [Error Sanitization](../security/ERROR_SANITIZATION.md)ን ይመልከቱ።

**የተኮረ ዑደት**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog-ው ሲቀየር፤ የተፈጠረውን diff commit ያድርጉ
npm run lint
```

እያንዳንዱን የተነካ request familyም test ያድርጉ፦ chat፣ Responses፣ images፣ embeddings፣ audio ወይም video።
የተፈጠሩ catalog እና golden diffsን እንደ contract changes ይገምግሙ፤ ያለምርመራ አይቀበሏቸው።

### Routing

**ውሎች**

- በ`src/shared/constants/routingStrategies.ts` ውስጥ ያሉ public strategy values እና UI metadata።
- በ`open-sse/services/combo.ts` እና `open-sse/services/combo/` ስር ያሉ dispatch እና ordering።
- Combo schemas፣ persistence፣ resilience state፣ model capabilities፣ እና API/UI controls።
- ባህሪ ሲቀየር [Auto-Combo Engine](../routing/AUTO-COMBO.md) እና resilience documentation።

**የተኮረ ዑደት**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # የstrategy ወይም dispatch ለውጦች
npm run check:known-symbols      # የstrategy registration ለውጦች
npm run lint
```

በአካባቢዎ deterministic mocked-upstream testsን ይጠቀሙ። Live combo smokes credentials ያስፈልጋቸዋል፣ እና
በእጅ የሚከናወኑ እንጂ የCI ምትክ አይደሉም።

### UI / UX

**ውሎች**

- በ`src/app/` እና
  `src/shared/components/` ስር ያሉ Next.js route/page እና የጋራ component boundaries።
- API response shapes፣ loading/empty/error states፣ የkeyboard እና screen-reader ባህሪ፣
  responsive layout፣ theming፣ እና locale expansion።
- በ`src/i18n/messages/en.json` ውስጥ ያሉ የእንግሊዝኛ UI source strings፤ አዲስ user-facing copyን hard-code አያድርጉ።

**የተኮረ ዑደት**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

ለinteraction ወይም visual changes app-ውን ያስኪዱ፣ እና ጠባብና ሰፊ viewportsን ይፈትሹ። CI
production buildን እና ሰፋፊ suitesን ያስኬዳል፤ visual behavior ግን አሁንም ከለውጡ ጋር የሚስማማ focused component፣ Playwright፣
ወይም በሰነድ የተመዘገበ manual check ያስፈልገዋል።

### i18n

**ውሎች**

- `src/i18n/messages/en.json` የUI source ነው፤ `config/i18n.json` ደግሞ የlocale source ነው።
- የCLI catalogs በ`bin/cli/locales/` ስር ለብቻቸው ይገኛሉ።
- ICU placeholders እና tagsን በትክክል ያቆዩ። የproduct/provider/model ስሞችን፣
  የprotocol እና header ስሞችን፣ commands፣ code/JSON identifiers፣ URLs፣ environment variables፣ ወይም
  እንደ `OmniRoute`፣ `OAuth`፣ `MCP` እና `A2A` ያሉ protected termsን አይተርጉሙ። የአሁኑ source list
  `scripts/i18n/glossary/protected-terms.json` ነው።

**የተኮረ ዑደት**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # የCLI strings/catalogs ሲቀየሩ
npm run lint
```

ይህ ለነባሩ system መመሪያ እንጂ toolingውን ወይም key modelን ለማስፋፋት ግብዣ አይደለም።
ምትክ system-ው እየተነደፈ ባለበት ጊዜ i18n patchesን በጥንቃቄና በውስን መልኩ ያድርጉ። ሥራው generated translationsን በግልጽ ካልጠየቀ
እና የተፈጠረውን diff ካልገመገሙ፣ external servicesን የሚጠሩ translation
commandsን አያስኪዱ።

### CLI

**ውሎች**

- በ`bin/cli/` ውስጥ ያሉ ይፋዊ ትዕዛዞችና flags፣ የሚመነጩ API ትዕዛዞች፣ exit codes፣ stdout/stderr እና
  የJSON ውጤት ቅርጾች፣ የconfig/environment ባህሪ፣ እና በጥቅል የሚካተቱ ፋይሎች።
- ለCLI ተጠቃሚ የሚታዩ ሕብረቁምፊዎች የCLI i18n layerን መጠቀም እና የ`en`/`pt-BR` catalogsን የተመሳሰሉ አድርገው ማቆየት አለባቸው።
- Nodeን እንደሚደገፈው runtime እና የታተመውን binary contract ጠብቁ።

**ያተኮረ ዑደት**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # የሚመነጩ/በጥቅል የሚሰበሰቡ የCLI ለውጦች
npm run check:pack-policy     # የpackage surface ለውጦች
npm run lint
```

ባህሪው በparsing፣ በፋይሎች ወይም በexit status ላይ ሲመሠረት ትክክለኛውን ትዕዛዝ በጊዜያዊ data directory ውስጥ ይጠቀሙ።
CI ይበልጥ ሰፊዎቹን የpackage artifact እና ecosystem ማረጋገጫዎች ያከናውናል።

### የውሂብ ጎታ

**ውሎች**

- በ`src/lib/db/` ስር ያሉ domain modules፤ የተወሰኑ modulesን በቀጥታ import ያድርጉ (የቀድሞው `localDb.ts` re-export layer ተወግዷል)።
- በ`src/lib/db/migrations/` ስር ያሉ ቁጥር የተሰጣቸው፣ idempotent የSQL migrations፣ የtransaction ደህንነት፣ የupgrade
  ባህሪ፣ indexes፣ እና በschemaው የሚነካ እያንዳንዱ caller።
- Routes እና handlers በቀጥታ raw SQL ፈጽሞ አያስኬዱም።

**ያተኮረ ዑደት**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

migration ሲጨምሩ አዲስ የውሂብ ጎታን እና ከቀዳሚው schema የሚደረግ upgradeን ሁለቱንም ይፈትኑ። የውሂብ ጎታ ሙከራዎች
handlesን መዝጋት እና በcleanup ጊዜ `resetDbInstance()`ን መጥራት አለባቸው። `npm run test:bun:db`ን ያስኪዱት
የbest-effort Bun adapter path ሲለወጥ ብቻ ነው፤ Node ዋናው ማጣቀሻ ሆኖ ይቀጥላል።

### Build / deploy

**ውሎች**

- Root እና workspace manifests/lockfile፣ `scripts/build/`፣ Next.js standalone assembly፣ የ`dist/`
  package ይዘቶች፣ የElectron platform metadata፣ የCI workflows፣ እና deployment sentinels።
- የሚደገፉ የNode ranges እና በ`CLAUDE.md` ውስጥ allow-list የተደረገው የBun አጠቃቀም ሳይበላሹ መቆየት አለባቸው።
- Build artifacts ክትትል ሳይደረግባቸው ይቆያሉ፤ የdependency፣ license፣ workflow፣ እና package policies ተፈጻሚ ናቸው።

**ያተኮረ ዑደት**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # የdependency ወይም lockfile ለውጦች
npm run check:pack-policy      # የታተመው package surface ለውጦች
npm run lint
```

ለውጡ compilation፣ standalone assembly፣ assets ወይም runtime bundlingን ሲነካ ብቻ `npm run build`ን በአካባቢዎ ይጠቀሙ።
`npm run build:release`ን ለrelease/deploy validation ብቻ ይጠቀሙ። የCI build የመጨረሻው cross-platform ምልክት ነው፤
platform-specific የElectron ለውጦች ተዛማጅ የሆነ focused build ወይም smoke evidence ያስፈልጋቸዋል።

## የአካባቢያዊ ዙር ከCI ጋር ሲነጻጸር

| ለእያንዳንዱ ማሻሻያ በአካባቢው ያስኪዱ                               | CI ሰፊውን ምልክት ያቀርባል                                 |
| ------------------------------------------------------ | -------------------------------------------------- |
| ከላይ ያሉት የባህሪ ቀጥተኛ ሙከራዎች እና የምድብ መግቢያዎች                 | የተከፋፈለ ሙሉ የአሃድ ሙከራ ስብስብ እና ተከታታይ ሙከራዎች             |
| `npm run lint`                                         | የVitest ሙከራ ስብስቦች እና የሽፋን/ጥራት ደረጃን የሚያጠናክሩ ፍተሻዎች   |
| የተነካው ውል ሲጠይቅ ብቻ የዓይነት ፍተሻ ወይም ግንባታ                    | የምርት ግንባታ፣ የደህንነት፣ የሰነዶች፣ የጥገኝነት እና የPR ፖሊሲ መግቢያዎች |
| ራስ-ሰር ሂደት ባህሪውን ማረጋገጥ ሳይችል ሲቀር ብቻ በእጅ መስተጋብር/ቀጥታ ፍተሻዎች | በየስራ ፍሰቱ የተዋቀሩ የተለያዩ ስራዎች ውህደት እና የመድረክ ፍተሻዎች      |

የተሳካ ያተኮረ ዙር ስለተቀየረው ውል ማስረጃ ነው፤ ነገር ግን ያልተዛመዱ የCI ፍተሻዎች
እንደሚያልፉ ማረጋገጫ አይደለም። በተቃራኒው፣ እያንዳንዱን የአካባቢ ማስተካከያ ሙሉውን የማከማቻ ማትሪክስ እንዲጠብቅ አያድርጉ።

## የማስታረቂያ ማረጋገጫ ዝርዝር

ግምገማ ከመጠየቅዎ በፊት፦

- የPR መሠረቱ አሁንም ከፍተኛው ንቁ `release/v*` ቅርንጫፍ መሆኑን ያረጋግጡ።
- ያንን መሠረት ያምጡ እና ቅርንጫፍዎን ከፈጠሩ በኋላ የገቡትን commits ይገምግሙ።
- ያልታሰቡ ወይም በራስ-ሰር የተፈጠሩ ለውጦችን ለማግኘት `git diff <active-base>...HEAD`ን ይገምግሙ።
- ምንጩን በማዘመን እና ውጤቱን እንደገና በማመንጨት የካታሎግ እና በራስ-ሰር የተፈጠሩ ሰነዶች ግጭቶችን ይፍቱ።
- ከማስታረቁ በኋላ በPR መግለጫው ውስጥ የተዘረዘሩትን እያንዳንዱን ያተኮረ ሙከራ/መግቢያ እንደገና ያስኪዱ።
- ከተቀየረ መሠረት ጋር ለማዛመድ ብቻ assertionsን በፍጹም አያላሉ ወይም አስፈላጊ ሙከራዎችን አያስወግዱ።

ለልቀት እገዳ እና የመድረሻ ቅርንጫፍን እንደገና ለመወሰን ደንቦች፣
