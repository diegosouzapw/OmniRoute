ይህን መመሪያ በመጠቀም ለpull request አነስተኛውን አስተማማኝ የልማት ዑደት ይምረጡ። ይህ ከታች የተገናኙትን
ለእያንዳንዱ ዘርፍ የተወሰኑ የአርክቴክቸርና የደህንነት ሰነዶች አይተካም፤ እያንዳንዱን የተለመደ
የለውጥ አይነት ከውሎቹ፣ ተኮር ማረጋገጫዎቹ እና የCI ሽፋኑ ጋር ያገናኛል።

## እያንዳንዱ ለውጥ የሚከተለው መንገድ

1. **ማርትዕ ከመጀመርዎ በፊት baseን ይምረጡ።** ከፍተኛውን ንቁ `release/v*` branch ያግኙና ከእሱ
   tip branch ይፍጠሩ። `main`ን ሳይሆን ያንን branch ዒላማ ያድርጉ። የrelease freeze ንቁ ከሆነ፣ የታገደውን
   branch ዒላማ አያድርጉ፤ በ
   [Branching & Release Model](BRANCHING_MODEL.md) የተገለጸውን ቀጣዩን ንቁ ዑደት ይጠቀሙ።
2. **ውሎቹን ይሰይሙ።** ለውጡ የሚነካውን እያንዳንዱን catalog፣ schema፣ የተፈጠረ artifact፣ ይፋዊ API ወይም የተጠቃሚ
   interface ይለዩ። ከታች ያለው ሰንጠረዥ ዝቅተኛውን የመነሻ ስብስብ ያሳያል።
3. **ተኮር ሙከራዎችን ይጻፉ ወይም ያዘምኑ።** በ`src/`፣ `open-sse/`፣ `electron/` ወይም
   `bin/` ውስጥ ያሉ የproduction ለውጦች በዚያው PR ውስጥ አውቶማቲክ ሙከራ ይፈልጋሉ። ባህሪውን የሚያረጋግጡትን ትንሹን የሙከራ ፋይሎች
   ያስኪዱ፣ ከዚያም የተዘረዘሩትን ተኮር gates ያስኪዱ።
4. **CI ሰፊውን matrix እንዲያስኬድ ያድርጉ።** ሙሉዎቹ unit shards፣ Vitest፣ coverage ratchet እና
   production build በPR ላይ ይሰራሉ። ተኮር ውድቀት ሰፋ ያለ ተጽዕኖ እንዳለ ሲያመለክት
   ወይም ለውጡ በበርካታ subsystems ላይ ሲዘረጋ ብቻ ሰፊ suiteን በአካባቢዎ ያስኪዱ።
5. **ከግምገማ በፊት ያስታርቁ።** ንቁውን base fetch ያድርጉ፣ አዲሶቹን commits እና ከእሱ አንጻር ያለውን diffዎን
   ይመርምሩ፣ ከዚያም በአበርካቹ workflow መሠረት baseን rebase ወይም merge ያድርጉ። የተፈጠሩ ፋይሎችን
   እና catalog conflictsን ከምንጫቸው ይፍቱ፣ እንደገና ይፍጠሯቸው፣ ተኮሩን ዑደት እንደገና ያስኪዱ፣ እና
   PRው አሁንም ንቁውን release branch ዒላማ ማድረጉን ያረጋግጡ።
6. **ማስረጃ ይመዝግቡ።** በPR template ውስጥ ያስኬዷቸውን commands፣ የታከለ ወይም የተቀየረ እያንዳንዱን የሙከራ ፋይል፣
   migrations ወይም feature flags፣ እና ገና ያልተጠናቀቀ ማንኛውንም በCI ብቻ የሚከናወን validation ይዘርዝሩ።

## በለውጥ አይነት የተደራጁ መደበኛ መንገዶች

ከታች ያሉት commands ዝቅተኛ ተኮር ማረጋገጫዎች ናቸው፤ የቀየሩትን ባህሪ በቀጥታ የሚሸፍን ሙከራ
ለመዝለል ፈቃድ አይደሉም።

### Provider

**ውሎች**

- በ`src/shared/constants/providers/` ውስጥ ያለው የprovider ትርጉም እና በ
  `src/shared/constants/providers.ts` ውስጥ ያለው composition።
- በ`open-sse/config/providerRegistry.ts` ወይም በተነጠሉት registry ፋይሎቹ ውስጥ ያሉ models እና capabilities።
- Executor/translator ምርጫ፣ OAuth ወይም API-key configuration፣ dashboard assets፣ እና ተፈጻሚ በሚሆንበት ጊዜ የተፈጠረ
  provider reference።
- ይፋዊ credentials `resolvePublicCred()`ን መጠቀም አለባቸው፤ error responses የጋራ sanitized
  error helpersን መጠቀም አለባቸው። `docs/security/PUBLIC_CREDS.md`ን (git፤ ወደ `/docs` አይጠናቀርም) እና
  [የስህተት ማጽዳት](../security/ERROR_SANITIZATION.md)ን ይመልከቱ።

**ተኮር ዑደት**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalogው ሲቀየር፤ የተፈጠረውን diff commit ያድርጉ
npm run lint
```

የተነካውን እያንዳንዱን request familyም ይሞክሩ፦ chat፣ Responses፣ images፣ embeddings፣ audio ወይም video።
የተፈጠሩትን catalog እና golden diffs እንደ የውል ለውጦች ይገምግሙ፤ ሳይመረምሩ አይቀበሏቸው።

### Routing

**ውሎች**

- በ`src/shared/constants/routingStrategies.ts` ውስጥ ያሉ ይፋዊ strategy values እና UI metadata።
- በ`open-sse/services/combo.ts` እና `open-sse/services/combo/` ስር ያሉ dispatch እና ordering።
- Combo schemas፣ persistence፣ resilience state፣ model capabilities፣ እና API/UI controls።
- ባህሪ ሲቀየር [Auto-Combo Engine](../routing/AUTO-COMBO.md) እና resilience documentation።

**ተኮር ዑደት**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy ወይም dispatch ለውጦች
npm run check:known-symbols      # የstrategy registration ለውጦች
npm run lint
```

በአካባቢዎ deterministic mocked-upstream ሙከራዎችን ይጠቀሙ። Live combo smokes credentials ይፈልጋሉ እና
በእጅ የሚከናወኑ ናቸው፤ የCI ምትክ አይደሉም።

### UI / UX

**ውሎች**

- በ`src/app/` እና
  `src/shared/components/` ስር ያሉ የNext.js route/page እና የጋራ component boundaries።
- API response shapes፣ loading/empty/error states፣ የkeyboard እና screen-reader ባህሪ፣
  responsive layout፣ theming፣ እና locale expansion።
- በ`src/i18n/messages/en.json` ውስጥ ያሉ የእንግሊዝኛ UI source strings፤ ለተጠቃሚ የሚታይ አዲስ ጽሑፍ hard-code አያድርጉ።

**ተኮር ዑደት**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

ለinteraction ወይም visual ለውጦች appውን ያስኪዱ እና ጠባብና ሰፊ viewportsን ያረጋግጡ። CI
production buildን እና ሰፊ የሙከራ suitesን ያስኬዳል፤ visual behavior አሁንም ለለውጡ ተስማሚ የሆነ ተኮር component፣ Playwright፣
ወይም በሰነድ የተመዘገበ በእጅ ማረጋገጫ ያስፈልገዋል።

### i18n

**ውሎች**

- `src/i18n/messages/en.json` የUI source ነው፤ `config/i18n.json` የlocale source ነው።
- የCLI catalogs በ`bin/cli/locales/` ስር ለየት ብለው ይገኛሉ።
- ICU placeholders እና tagsን በትክክል ያቆዩ። የproduct/provider/model ስሞችን፣
  protocol እና header ስሞችን፣ commandsን፣ code/JSON identifiersን፣ URLsን፣ environment variablesን ወይም
  እንደ `OmniRoute`፣ `OAuth`፣ `MCP` እና `A2A` ያሉ የተጠበቁ termsን አይተርጉሙ። የአሁኑ source list
  `scripts/i18n/glossary/protected-terms.json` ነው።

**ተኮር ዑደት**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # የCLI strings/catalogs ሲቀየሩ
npm run lint
```

ይህ ለነባሩ system መመሪያ እንጂ tooling ወይም key modelን ለማስፋት ግብዣ አይደለም።
ተተኪው system በመንደፍ ላይ ሳለ i18n patchesን ጥቃቅንና ተኮር ያድርጉ። ተግባሩ የተፈጠሩ translationsን በግልጽ ካልጠየቀ
እና የተገኘውን diff ካልገመገሙ በስተቀር external servicesን የሚጠሩ translation
commandsን አያስኪዱ።

### CLI

**ውሎች**

- በ`bin/cli/` ውስጥ ያሉ ይፋዊ ትዕዛዞችና flags፣ የተመነጩ API ትዕዛዞች፣ exit codes፣ stdout/stderr እና
  የJSON ውጤት ቅርጾች፣ የconfig/environment ባህሪ እና በጥቅል የተካተቱ ፋይሎች።
- ለCLI ተጠቃሚዎች የሚታዩ ሕብረቁምፊዎች የCLI i18n ንብርብርን መጠቀም እና የ`en`/`pt-BR` ካታሎጎችን የተጣጣሙ አድርገው ማቆየት አለባቸው።
- Nodeን እንደሚደገፍ runtime እና ይፋ የተደረገውን binary ውል ጠብቁ።

**ያተኮረ ዙር**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # የተመነጩ/በጥቅል የተዋሃዱ የCLI ለውጦች
npm run check:pack-policy     # የpackage-surface ለውጦች
npm run lint
```

ባህሪው በመተንተን፣ በፋይሎች ወይም በexit status ላይ በሚመሠረትበት ጊዜ ትክክለኛውን ትዕዛዝ በጊዜያዊ data directory ውስጥ ይጠቀሙ። CI ሰፋ ያሉትን የpackage artifact እና ecosystem ፍተሻዎች ያከናውናል።

### የውሂብ ጎታ

**ውሎች**

- በ`src/lib/db/` ሥር ያሉ domain modules፤ የተወሰኑ modulesን በቀጥታ import ያድርጉ (የድሮው የ`localDb.ts` re-export ንብርብር ተወግዷል)።
- በ`src/lib/db/migrations/` ሥር ያሉ ቁጥር የተሰጣቸው፣ idempotent የSQL migrations፣ የtransaction ደኅንነት፣ የupgrade
  ባህሪ፣ indexes እና በschemaው ተጽዕኖ የሚያድርባቸው ሁሉም callers።
- Routes እና handlers በቀጥታ raw SQL ፈጽሞ አያስኬዱም።

**ያተኮረ ዙር**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

migration ሲጨምሩ ሁለቱንም አዲስ የውሂብ ጎታ እና ከቀደመው schema የሚደረግ upgrade ይፈትሹ። የውሂብ ጎታ ፈተናዎች በcleanup ወቅት handlesን መዝጋት እና `resetDbInstance()`ን መጥራት አለባቸው። የbest-effort Bun adapter path ሲለወጥ ብቻ `npm run test:bun:db`ን ያስኪዱ፤ Node ዋና ማጣቀሻ ሆኖ ይቆያል።

### Build / deploy

**ውሎች**

- Root እና workspace manifests/lockfile፣ `scripts/build/`፣ የNext.js standalone ስብጥር፣ የ`dist/`
  package ይዘቶች፣ የElectron platform metadata፣ የCI workflows እና deployment sentinels።
- የሚደገፉ የNode ranges እና በ`CLAUDE.md` ውስጥ ያለው allow-listed Bun አጠቃቀም ሳይበላሽ መቆየት አለባቸው።
- Build artifacts ክትትል ሳይደረግባቸው ይቆያሉ፤ የdependency፣ license፣ workflow እና package ፖሊሲዎች ተፈጻሚ ናቸው።

**ያተኮረ ዙር**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # የdependency ወይም lockfile ለውጦች
npm run check:pack-policy      # ይፋ የተደረጉ የpackage surface ለውጦች
npm run lint
```

ለውጡ compilation፣ standalone assembly፣ assets ወይም runtime bundlingን በሚነካበት ጊዜ ብቻ `npm run build`ን በአካባቢዎ ያስኪዱ። `npm run build:release`ን ለrelease/deploy validation ብቻ ይጠቀሙ። የCI build የመጨረሻው cross-platform ምልክት ነው፤ platform-specific የElectron ለውጦች ተዛማጅ ያተኮረ build ወይም smoke evidence ያስፈልጋቸዋል።

## የአካባቢ እጩ ዑደት

የምንጭ ሙከራዎች የታሸገው አርቲፋክት መነሳቱን ማረጋገጥ አይችሉም፦ የማሸጊያ ዝርዝሮች፣ የተቀነሱ ጥገኞች፣
እና ቤተኛ ባይነሪዎች የሚከሽፉት tarball-ው ከተጫነና ከተጀመረ በኋላ ብቻ ነው። `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) በRFC #8084 የተገለጸው አንድ ጊዜ መገንባት / ማረጋገጥ / ማስተዋወቅ ፍሰት
የአካባቢ ክፍል ነው፦ አንድ እጩ ይገነባል፣ ያንኑ አርቲፋክት ያረጋግጣል፣ በማውጫ
ስም-ለውጦች ያስተዋውቀዋል፣ እና የተዋወቀው ቦታ የጤና ምርመራውን ሳያልፍ ሲቀር ወደ ኋላ ይመልሰዋል።

```bash
npm run dev:candidate -- run --dry-run --json  # ዕቅዱን አትም፣ ምንም አትቀይር
npm run dev:candidate -- run                   # ገንባ + አረጋግጥ + አስተዋውቅ፣ በራስ-ሰር ወደ ኋላ መመለስ
npm run dev:candidate -- build                 # npm pack + ወደ _artifacts/candidate/<id>/ ጫን
npm run dev:candidate -- validate --id <id>    # በነፃ ወደብ ላይ አስነሳ፣ /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current፣ current → previous
npm run dev:candidate -- rollback              # current እና previous ቀያይር
npm run dev:candidate -- run --from-tarball <file.tgz>  # ሌላ ቦታ (CI) የተገነባ tarball እንደገና ተጠቀም
```

- **አንድ ጊዜ ገንባ።** `build` የአሁኑን ዛፍ ያሽጋል (`dist/server.js` ስለሚያስፈልገው መጀመሪያ
  `npm run build:release` ያስኪዱ) ወይም `--from-tarball`ን ይቀዳል፤ ከዚያም tarball-ው
  `node_modules` ስለማይይዝ ወደ ተነጠለ npm ቅድመ-ቅጥያ ይጭነዋል። id-ው አጭሩ `HEAD`
  sha (ዛፉ የአካባቢ ለውጦች ሲኖሩት `-dirty`) ወይም ለtarball `tgz-<sha256>` ነው። አስቀድሞ
  የተገነባ ንጹህ id ዳግም ከመገንባት ይልቅ እንደገና ጥቅም ላይ ይውላል፤ እንደገና ለመገንባት `--force`ን ያስተላልፉ።
- **ምንጩን ሳይሆን ጥቅሉን አረጋግጥ።** `validate` የተጫነውን CLI
  (`serve --port <free port>`) በአዲስ `DATA_DIR=<candidate>/data`፣ በሐሰት ሚስጥሮች፣ እና
  የኦፕሬተሩ `OMNIROUTE_API_KEY`፣ `STORAGE_ENCRYPTION_KEY` እና `INITIAL_PASSWORD` ከአካባቢው
  ተወግደው ያስጀምራል፤ በዚህም የአዲስ ጭነትን ቁልፍ-አልባ የloopback አቋም ይፈትሻል።
  `GET /api/health` 200 እስኪመልስ ይጠብቃል፣ `GET /v1/models` 200 እንዲመልስ ይጠይቃል፣ የሂደት ቡድኑን ያቆማል፣
  እና ውሳኔውን ከtarball hash ጋር በ`validation.json` ውስጥ ይመዘግባል።
- **ያንኑ አርቲፋክት አስተዋውቅ።** `promote` ለአሁኑ tarball hash የተሳካ ማረጋገጫ የሌለውን እጩ
  አይቀበልም። ነባሪው ንቁ ቦታ `_artifacts/candidate/current` ነው፤ `--target <dir>`
  በዚያው የፋይል ስርዓት ላይ ሌላ ማውጫ ይመርጣል፣ እና የቀድሞ ቦታው `<dir>.previous` ነው።
  እያንዳንዱ የስም ለውጥ አቶሚክ ነው፣ እና በመሃል የሚከሰት ውድቀት ቀድሞውኑ የተከናወኑትን የስም ለውጦች ይቀለብሳል።
- **ወደ ኋላ መልስ።** `run` የተዋወቀውን ቦታ እንደገና ያረጋግጣል፣ እና ያ ምርመራ ሳይሳካ ሲቀር
  `current` እና `previous`ን መልሶ ይቀያይራል። የመጀመሪያውን ማረጋገጫ ያላለፈ እጩ ፈጽሞ አይተዋወቅም።

ሁሉም ነገር gitignored በሆነው `_artifacts/candidate/` ስር ይጻፋል፤ ነባር የOmniRoute
ጭነትና የውሂብ ማውጫው ፈጽሞ አይነኩም። የተዋወቀው CLI
`_artifacts/candidate/current/prefix/bin/omniroute` ነው፤ ሲጠቀሙበት በራስዎ `DATA_DIR` ያስጀምሩት።
የመውጫ ኮዶች፦ `0` ስኬት፣ `1` ያልተሳካ ማረጋገጫ ወይም ማስተዋወቅ፣ `2` የአጠቃቀም ስህተት ወይም የጎደለ ግንባታ።
