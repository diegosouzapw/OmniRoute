## ክፍል 1 — ውሳኔ እና የብስለት ምደባ

**አጠቃላይ ደረጃ፦ A− / "የላቀ"። ከፕሮጀክቶች ከፍተኛው ~5–10%።** ስርዓቱ ኢንዱስትሪው በግልጽ ስም የሚጠራቸውን
በርካታ ንድፎች በራሱ ተግባራዊ ያደርጋል — ይህም እጅግ ጠንካራው የመጣጣም
ምልክት ነው (የማረጋገጫ ዝርዝር አልቀዳንም፤ ትክክለኛዎቹ ልምዶች ላይ በተናጥል ደርሰናል)።

## ክፍል 2 — ወሳኝ ግምገማ (ጥንካሬዎች + ሐቀኛ ድክመቶች)

### ጥንካሬዎች (ከአማካይ በላይ የሆኑ)

1. **ባለብዙ-መለኪያ ratchet engine።** የስርዓቱ ዋና እምብርት። በ`quality-baseline.json` ውስጥ 24 መለኪያዎች
   - 4 የተለዩ baselines፣ እያንዳንዳቸው አቅጣጫ (`up`/`down`)፣ የስህተት ወሰን (`eps`)፣ የመፍትሔ ክፍተት
     (`tightenSlack`) እና `dedicatedGate` flag ያላቸው። የተስተካከሉ ነገሮች **እንደተስተካከሉ ይቆያሉ** — ይህ
     ለcodebase entropy መድኃኒት ነው።
2. **ለsupply-chain ጥልቀት ያለው መከላከያ።** SAST (CodeQL/Sonar) + secrets (gitleaks ከ
   `useDefault` ጋር) + SCA (osv/npm-audit/Trivy/Dependabot) + licenses + lockfile + SBOM + SLSA
   provenance + Scorecard + workflow hardening (zizmor)። ይህን ያህል የተሟላ stack ያላቸው codebases ጥቂት ናቸው።
3. **የGoodhart's Law መድኃኒቶች።** Coverageን እንደ ግብ መጠቀም የተለመደ anti-pattern ነው
   ("መለኪያው ግብ በሚሆንበት ጊዜ፣ ጥሩ መለኪያ መሆኑን ያቆማል")። እኛ የማመጣጠኛ መንገዶቹ አሉን፦
   **mutation testing** (testው bugን ይይዝ እንደሆነ እንጂ lineን ብቻ ያስኬዳል እንደሆነ አይለካም)፣
   **`check-test-masking`** (እንዲያልፉ assertsን ማዳከምን ይከለክላል)፣
   **በእያንዳንዱ module የcoverage ዝቅተኛ ገደቦች** (ቀላል ክፍሎችን ብቻ ሳይሆን HIGH-risk codeን መፈተሽን ያስገድዳሉ) እና
   **`check-pr-evidence`** (Hard Rule #18)።
4. **Anti-hallucination / consistency gates።** አልፎ አልፎ የሚገኝ እና ጠቃሚ ምድብ፦ `check-known-symbols`፣
   `check-fetch-targets`፣ `check-openapi-routes`፣ `check-docs-symbols` docs፣ specs እና
   string dispatches በሕይወት ያሉ symbolsን እንዲያመለክቱ ያረጋግጣሉ። lint/test የማይይዘውን "rot" ይይዛል።
5. **Advisory→blocking lifecycle።** አዳዲስ gates እንደ advisory ይገባሉ (እየበሰሉ ሳሉ
   mergesን አያግዱም)፣ ከዚያም በcycle መጨረሻ blocking ይሆናሉ። ጣሪያውን ሳያሳንስ ውዝግብን ይቀንሳል።
6. **Infra ሲጎድል በአግባቡ መዝለል።** Scanners (`--ratchet`) binary/network
   ካልተሳካ `exit 0` በማድረግ ይወጣሉ — የinfra እጥረት ሕጋዊ PRን ፈጽሞ አያግድም። የበሰለ engineering ነው።
7. **በደንብ የተደነገገ ባህል።** Hard Rules + `trust-but-verify` + stale-allowlist + evidence-gate
   ሥነ-ሥርዓትን ወደ ራስ-ሰር ማረጋገጫ ይቀይራሉ።

### ሐቀኛ ድክመቶች (እውነተኛ ክፍተቶች)

1. **🔴 የfast-gates ክፍፍሉ አሁንም መዋቅራዊ ክፍተት ይተዋል።** `quality.yml` (PR→`release/**`)
   አሁን typecheck፣ ፈጣን deterministic tests እና ለcode PRs advisory production buildን ያስኬዳል፣
   ነገር ግን አሁንም ከ`ci.yml` የሚመጣውን ሙሉ የrelease-PR ወሰን (coverage ratchets፣
   package artifact፣ integration፣ E2E፣ SonarQube) አያስኬድም። ምክንያቱ (ፍጥነት) ትክክለኛ ነው፣ ነገር ግን gateው
   merge በሚደረግበት ቦታ መሆን አለበት (shift-left)። **ትልቁ በመጠባበቅ ላይ ያለ መዋቅራዊ ማስተካከያ።**
2. **🟠 የGate መብዛት/ድካም አደጋ።** ~46 gates + 25 jobs እጅግ ብዙ ናቸው። Sonar ራሱ እንዲህ ሲል ያስጠነቅቃል፦
   ከመጠን በላይ conditions "gate fatigue" እና የቅድሚያ ክርክሮችን ያስከትላሉ፣ gate ችላ ሊባል
   የሚችልበት አደጋም አለ። DORA ከባድ gates lead-timeን እንደሚጨምሩ ያስጠነቅቃል። በadvisory tiers እና
   non-absolute ratchets እናቃልለዋለን፣ ነገር ግን **ለእያንዳንዱ gate ወቅታዊ የROI ግምገማ** የለም (አንዳንድ የ
   doc-sync micro-gates ሊዋሃዱ ይችላሉ)።
3. **🟠 Mutation score እስካሁን ratchet አይደለም።** coverage-gamingን ለመከላከል በጣም ጠንካራው መድኃኒት
   **advisory** ነው። ከሚጠባበቁ ንጥሎች ከፍተኛው ዋጋ ያለው ነው (እና ቀድሞውኑ 90% ተገንብቷል)።
4. **🟡 መከልከል ያለባቸው Advisories (በትክክለኛው ወሰን)።** `osv` (vulnCount) እና `oasdiff`
   baselines የቀዘቀዙ ቢሆኑም advisory ናቸው። osv-advisory ትርጉም አለው (በድሮ dep ላይ አዲስ CVE ከመጣ
   ያልተዛመደ PRን ሊያግድ ይችላል) — ነገር ግን መካከለኛ መንገድ አለ (በTrivy እንዳደረግነው
   CRITICAL+fixable ብቻ ማገድ)። oasdiff advisory መሆኑ ውልን የሚሰብር ለውጥ ሊያልፍ ይችላል ማለት ነው።
5. **🟡 Runtime security በሌሊት ብቻ ይካሄዳል።** schemathesis/garak/promptfoo/chaos/k6 በሌሊት ይሰራሉ።
   ትክክለኛ ውሳኔ ነው (ዝግ ናቸው፣ live server ያስፈልጋቸዋል)፣ ነገር ግን PR የinjection-guard regressionን
   ሊያስገባ ይችላል፣ ይህም በቀጣዩ ሌሊት ብቻ ይገኛል።
6. **🟡 በ`main` ላይ branch-protection OFF ነው።** `BRANCH_LOCK_TOKEN` የ_release_ branchesን ይቆልፋል፣ ነገር ግን
   `main` ራሱ ያልተጠበቀ ነው። Scorecard/DSOMM ነጥብ ይቀንሳሉ። የOwner እርምጃ ያስፈልጋል።
7. **🟡 CodeQL default-setup፤ semgrep በrepoው ውስጥ አልተደነገገም።** default-setup ይሰራል (0 alerts)፣ ነገር ግን
   committed `codeql.yml` የበለጠ ቁጥጥር ይሰጣል፤ semgrep በrepoው ውስጥ versioned ከመሆን ይልቅ
   በexternal cloud platform በኩል ይሰራል።

## ክፍል 3 — የጥራት ማረጋገጫ ነጥቦች የተሟላ ካታሎግ (በማንኛውም ስታክ ላይ የሚሠራ)

ከታች ያሉት 12 ምድቦች እንደገና ጥቅም ላይ ሊውል በሚችል መልኩ የቀረበው "የጥራት ሥርዓት" ናቸው። እያንዳንዱ ምድብ
**ዓላማውን** (ምንን መጠበቅ እንዳለበት)፣ **የምንጠቀምባቸውን መሣሪያዎች** እና በማንኛውም ስታክ ላይ ተመሳሳዩን ለመተግበር የሚያስችለውን **ከመሣሪያ ነፃ የሆነ አቻ አቀራረብ**
ይዘረዝራል።

### 1. ቅጥ እና ቅርጸት (ውጤቱ የማይለዋወጥ፣ ፈጣን)

- **OmniRoute:** Prettier + ESLint በ lint-staged (pre-commit) በኩል፣ 2-spaces/double-quotes/100col።
- **አጠቃላይ:** በራስ-ሰር ሊያስተካክል የሚችል አንድ formatter + አንድ linter፣ በ staged files ላይ በ pre-commit የሚሠሩ።

### 2. ዓይነቶች

- **OmniRoute:** `typecheck:core` (አጋጅ) + `typecheck:noimplicit:core` (አማካሪ) + `type-coverage` ratchet 92.17% + የእያንዳንዱ ፋይል any-budget።
- **አጠቃላይ:** በ CI ውስጥ ጥብቅ typecheck + ወደኋላ እንዳይመለስ የተገደበ type-coverage መለኪያ + የእያንዳንዱ ፋይል `any`/escape-hatch በጀት።

### 3. ሙከራዎች (ጥንካሬ)

- **OmniRoute:** 2 የማይደራረቡ runners (Node native + vitest)፣ 8 shards፣ አጠቃላይ coverage 60/60/60/60 + ratchet ~76% + **ለወሳኝ modules 8 የእያንዳንዱ module ዝቅተኛ ወሰኖች** + የምሽት property tests + የምሽት **mutation testing**።
- **አጠቃላይ:** test runner(s) + **ፍጹም** coverage ዝቅተኛ ወሰን (ዜሮ እንዳይሆን) + coverage **ratchet** (ወደኋላ እንዳይመለስ) + **ከፍተኛ አደጋ ላለው ኮድ የእያንዳንዱ module ዝቅተኛ ወሰኖች** (የGoodhart ችግርን ለመከላከል) + ለንጹሕ logic property-based ሙከራ + የሙከራ ጥራት ትክክለኛ መለኪያ የሆነ የምሽት **mutation testing**።

### 4. የሙከራ ፖሊሲ (ሥርዓቱን እንዳይጭበረበር)

- **OmniRoute:** `pr-test-policy` (የምርት ኮድ ሙከራ ይፈልጋል)፣ `check-test-masking` (የተዳከሙ asserts ያግዳል)፣ `pr-evidence` (የስኬት መግለጫ የማስረጃ block ይፈልጋል)፣ `test-discovery` (እያንዳንዱ ሙከራ በ runner እንዲሰበሰብ ያደርጋል)።
- **አጠቃላይ:** "አዲስ ኮድ ⇒ አዲስ ሙከራ" gate + assert-removed/tautology detector + የማስረጃ መስፈርት (TDD ወይም living test) + ከ globs ውጭ የተተወ ሙከራ እንዳይኖር ዋስትና።

### 5. ውስብስብነት እና የኮድ ጤንነት (ratchets)

- **OmniRoute:** ESLint-warnings (3769↓)፣ jscpd duplication (5.72%↓)፣ cyclomatic+max-lines complexity (1800↓)፣ cognitive complexity sonarjs (753↓)፣ dead-code/unused-exports knip (339↓)፣ የእያንዳንዱ ፋይል file-size (የተቆለፈ፣ መቀነስ ብቻ)፣ circular-deps (ብጁ Tarjan፣ አጋጅ)።
- **አጠቃላይ:** እያንዳንዱን የጤንነት መለኪያ ratchet ማድረግ (ማስጠንቀቂያዎች፣ ድግግሞሽ፣ cyclomatic **እና** cognitive complexity፣ dead code፣ file size፣ import cycles)። አቅጣጫው ሁልጊዜ "ወደኋላ አትመለስ" ነው።

### 6. የማይንቀሳቀስ ደኅንነት (SAST + ሚስጥሮች)

- **OmniRoute:** CodeQL (ratchet alerts = 0)፣ gitleaks (`[extend] useDefault=true` — ወሳኝ!)፣ SonarQube፣ ብጁ የደኅንነት ደንቦች (public-creds፣ error-helper፣ route-guard-membership፣ route-validation)።
- **አጠቃላይ:** SAST (CodeQL/Sonar/semgrep) ከ alert ratchet ጋር + **የተወረሰ default ruleset** ያለው secrets scanner (default ን የሚተካ custom config = እውርነት) + ለፕሮጀክቱ የተለዩ Hard Rule የደኅንነት gates።

### 7. የአቅርቦት ሰንሰለት (ጥገኞች)

- **OmniRoute:** osv-scanner + npm-audit + Trivy + Dependabot (SCA)፣ license-checker (SPDX allowlist)፣ lockfile-lint (HTTPS+sha512+registry)፣ `check-deps` anti-slopsquatting (allowlist + ዕድሜ ≥72h)።
- **አጠቃላይ:** ከብዙ ምንጮች የሚመጣ SCA + license allowlist + lockfile integrity check + የዕድሜ/typosquatting ማረጋገጫ ያለው dependency allowlist + ዝማኔዎችን በቡድን የሚያቀርብ bot።

### 8. የአቅርቦት ሰንሰለት (ግንባታ እና ልቀት)

- **OmniRoute:** SBOM (CycloneDX + syft)፣ SLSA provenance (`--provenance`)፣ OpenSSF Scorecard (በየሳምንቱ)፣ workflow ማጠናከር (zizmor: artipacked→`persist-credentials:false`፣ cache-poisoning፣ token-permissions)።
- **አጠቃላይ:** በ publish ጊዜ SBOM ማመንጨት + የተፈረመ provenance (SLSA L2+) + በመርሐግብር የሚሠራ Scorecard + ሁሉንም workflows ማጠናከር (ዝቅተኛ-መብት tokens፣ non-pusher checkout ላይ የተቀመጡ credentials እንዳይኖሩ፣ actions በ SHA እንዲቆለፉ)።

### 9. ውሎች እና API

- **OmniRoute:** oasdiff (breaking-change OpenAPI)፣ schemathesis (የምሽት contract fuzz)፣ openapi-coverage (% የተመዘገቡ routes፣ ratchet 38.3%)፣ openapi-security-tiers (spec ከ route-guard ጋር)።
- **አጠቃላይ:** breaking-change contract diff (oasdiff/buf) + በ spec ላይ የሚደረግ property-based fuzz (schemathesis) + ወደኋላ እንዳይመለስ የተገደበ የሰነድ coverage + spec↔code ወጥነት።

### 10. ሰነዶች እና i18n (እንዳያረጁ)

- **OmniRoute:** docs-sync (የተንጸባረቁ versions)፣ docs-counts-sync (በሰነዶች ውስጥ ያሉ numbers ከ code ጋር)፣ env-doc-sync፣ doc-links፣ fabricated-docs፣ cli-i18n፣ i18n-ui-coverage (`--threshold=65` + ratchet 80.1%)።
- **አጠቃላይ:** versions/counts/env-vars በ docs እና code መካከል ማመሳሰል (gate እንጂ መተማመን አይደለም) + internal links ማረጋገጥ + ወደኋላ እንዳይመለስ የተገደበ i18n coverage።

### 11. ቅዠትን መከላከል / ወጥነት (እምብዛም የማይገኘው ምድብ)

- **OmniRoute:** known-symbols (string dispatch ⇒ በእውን ያለ symbol)፣ provider-consistency፣ fetch-targets (client fetch ⇒ በእውን ያለ route)፣ docs-symbols፣ db-rules (Hard Rules #2/#5)፣ migration-numbering።
- **አጠቃላይ:** ለእያንዳንዱ "የተደገመ የእውነት ምንጭ" (registry፣ string dispatch፣ cross-layer references)፣ ሁለቱ ወገኖች እንደሚዛመዱ የሚያረጋግጥ gate። typecheck/test የማይይዙትን መበላሸት ይይዛል።

### 12. የመቋቋም ችሎታ እና ዶሜይን (ለምርቱ የተለየ)

- **OmniRoute:** chaos (fault-injection)፣ heap-growth (leak)፣ k6 (soak)፣ promptfoo+garak (LLM red-team OWASP LLM Top 10)፣ 3ቱ የመቋቋም ችሎታ ሕጎች (circuit-breaker/cooldown/lockout)።
- **አጠቃላይ:** የ**እርስዎን** ዶሜይን የብልሽት ሁኔታዎች ለይተው ለእያንዳንዳቸው gate (የምሽት ቢሆንም እንኳ) ይኑርዎት። ለ AI apps፦ injection red-team። ለ distributed systems፦ chaos + leak + soak።

## ክፍል 4 — ለማንኛውም ፕሮጀክት የማባዛት ዕቅድ

በ**ደረጃዎች** ይገንቡ፤ እያንዳንዱ ደረጃ ለብቻው ጥቅም የሚሰጥ ይሁን። ሁሉንም 12 ምድቦች በአንድ ጊዜ ለመተግበር አይሞክሩ —
ይህ ክፍል 2 የሚያስጠነቅቀውን የጌት ድካም በትክክል ያስከትላል። እያንዳንዱ አዲስ ጌት በ**ምክር ሰጪ** ሁኔታ ይጀምርና የተረጋጋ ሲሆን **አጋጅ** ይሆናል።

### እንደገና ጥቅም ላይ የሚውለው ዋና ክፍል፦ የ«ራቼት ጌት አወቃቀር»

መላው ሥርዓት በዚህ ባለ3-ፋይል ንድፍ ዙሪያ ይሽከረከራል። መጀመሪያ ይህን ይቅዱ፦

1. **`baseline.json`** — የተቆለፈው የመለኪያ እሴት + `direction` (`up`/`down`) + `eps` (መዋዠቅን መከላከያ) + `tightenSlack` + `dedicatedGate`።
2. **`collect-metrics.<ext>`** — መሣሪያውን ያስኬዳል፣ ቁጥሩን ያወጣል፣ `metrics.json`ን ይጽፋል።
3. **`check-ratchet.<ext>`** — `metrics.json`ን ከ`baseline.json` ጋር ያነጻጽራል፤ ከ`eps` በላይ መቀነስ ካለ **ብቻ** `exit 1`፤ መሣሪያው/መሠረተ ልማቱ ከሌለ `exit 0` (በሰላም መዝለል)፤ `--require-tighten` ካለ፣ መነሻውን ሳያዘምኑ **መሻሻል** ከተገኘ `exit 1` (የተገኘውን ማሻሻያ ይቆልፋል)።

ይህ ከተዘጋጀ፣ **እያንዳንዱ** አዲስ መለኪያ (ሽፋን፣ ውስብስብነት፣ ማስጠንቀቂያዎች፣ SAST ማንቂያዎች፣ የቅርቅብ መጠን፣ የሚውቴሽን ነጥብ…) በመነሻው ውስጥ አንድ መስመር ብቻ ይሆናል።

### ደረጃ 0 — መሠረት (1ኛ ሳምንት)

CI አለ፤ ቅርጸት አስተካካይ + ሊንተር + የዓይነት ማረጋገጫ + 1 የሙከራ አስኪያጅ + **ፍጹም** የሽፋን ዝቅተኛ ገደብ
(ለምሳሌ፣ 60%)። Pre-commit ፈጣንና በራስ-ሰር ሊስተካከሉ የሚችሉ ፍተሻዎችን ያስኬዳል። _ውጤት፦ የትኛውም PR መሠረታዊ ነገሮችን አያበላሽም።_

### ደረጃ 1 — የራቼት ሞተር (2ኛ ሳምንት) — **የሁሉም ነገር መሠረት**

ከላይ ያሉትን 3 ፋይሎች ይተግብሩ። ለማስጠንቀቂያዎች፣ ሽፋን፣ ውስብስብነት፣ ድግግሞሽ፣
ጥቅም ላይ የማይውል ኮድ እና የፋይል መጠን መነሻዎችን ይቆልፉ። _ውጤት፦ ከዚህ በኋላ የኮድ ማከማቻው መሻሻል ብቻ ይችላል።_

### ደረጃ 2 — ጥልቅ የማይንቀሳቀስ ትንተና (3ኛ ሳምንት)

SAST (CodeQL/Sonar/semgrep) ከማንቂያ ራቼት ጋር፤ የምስጢር መረጃ ቃኚ (**ነባሪውን ደንብ ስብስብ ይውረስ**)፤
SCA (osv/Dependabot) + የፈቃድ ዝርዝር + lockfile-lint። _ውጤት፦ የታወቁ ተጋላጭነቶች እና የወጡ ምስጢሮች አያልፉም።_

### ደረጃ 3 — የግንባታ አቅርቦት ሰንሰለት (4ኛ ሳምንት)

በሕትመት ጊዜ SBOM + የተፈረመ የምንጭ ማረጋገጫ (SLSA L2) + በጊዜ ሰሌዳ የሚካሄድ Scorecard + የሥራ ፍሰት ማጠናከር
(zizmor፦ አነስተኛ ቶከኖች፣ ያልተቀመጡ ማረጋገጫዎች፣ የተቸነከሩ ድርጊቶች)። _ውጤት፦ ሊከታተሉ የሚችሉና ከመነካካት የተጠበቁ ልቀቶች።_

### ደረጃ 4 — የሙከራ ጥንካሬ (5–6ኛ ሳምንት)

ጠቃሚ ከሆነ 2ኛ የሙከራ አስኪያጅ፤ **ለወሳኝ ሞጁሎች የሞጁል-ተኮር የሽፋን ዝቅተኛ ገደቦች** (Goodhartን ለመከላከል)፤
ለንጹህ ሎጂክ ባህሪ-ተኮር ሙከራ፤ **በየሌሊቱ የሚውቴሽን ሙከራ** → 1ኛው ነጥብ ሲመጣ፣
`mutationScore`ን ራቼት ያድርጉ። _ውጤት፦ ሽፋን የከንቱ ውበት መለኪያ መሆኑን ያቆማል፤ ሙከራዎች ሳንካዎችን እንደሚይዙ በማስረጃ ይረጋገጣል።_

### ደረጃ 5 — ውል እና ተለዋዋጭ ትንተና (7ኛ ሳምንት)

ይፋዊ API ካለ፦ oasdiff (ለውጥን የሚሰብር፣ **አጋጅ**) + schemathesis (በየሌሊቱ ፋዝ ሙከራ)።
እንደ ዘርፉ ተገቢነት DAST/የቀይ-ቡድን ሙከራ በየሌሊቱ። _ውጤት፦ ውሎች በጸጥታ አይሰበሩም።_

### ደረጃ 6 — ቅዠትን መከላከል እና የዘርፍ ፍተሻ (8ኛ ሳምንት)

በፕሮጀክቱ ውስጥ ላለ እያንዳንዱ «የተደገመ እውነት» አንድ የወጥነት ጌት። ለዘርፉ የተለዩ የውድቀት-ሁነታ
ጌቶች (ለAI፦ የመርፌ ጥቃት የቀይ-ቡድን ሙከራ)። _ውጤት፦ መዋቅራዊ መበስበስ እና የዘርፍ ውድቀቶች የደኅንነት መረብ ይኖራቸዋል።_

### ደረጃ 7 — አስተዳደር (ቀጣይነት ያለው)

- ለእያንዳንዱ አዲስ ጌት የምክር ሰጪ→አጋጅ ዑደት።
- `stale-allowlist`፦ እያንዳንዱ ማፈኛ ምክንያት + issue ይኖረዋል፤ ጊዜው ያለፈበት ማፈኛ ይገኛል።
- `evidence-gate`፦ በPR ውስጥ ያለ የስኬት ይገባኛል ጥያቄ ማስረጃ ይፈልጋል (ሙከራ ወይም ቀጣይነት ያለው ሙከራ)።
- **በየሩብ ዓመቱ ለእያንዳንዱ ጌት የROI ግምገማ** (ተመላሽ የማያስገኙትን ያስወግዱ/በጀት ይንሷቸው — ድካምን ይከላከላል)።
- የፕሮጀክትዎን ጥብቅ ደንቦች ወደ ሊተገበሩ የሚችሉ ጌቶች ያሳድጉ።

### ሁሉን አቋርጠው የሚሠሩ መርሆች (ለድርድር የማይቀርቡ)

- **ራቼት እንጂ ፍጹም እሴት አይደለም።** ቋሚ ቁጥርን ሳይሆን _አለመቀነስን_ በጌት ይቆጣጠሩ (ከዜሮ በላይ እንዲሆን ከሚያስገድዱ ዝቅተኛ ገደቦች በስተቀር)።
- **ፍጹም ዝቅተኛ ገደብ + ራቼት በአንድነት።** ዝቅተኛው ገደብ መፍረስን ይከላከላል፤ ራቼቱ ቀስ በቀስ መሸርሸርን ይከላከላል።
- **Goodhartን በንድፍ ይከላከሉ።** እያንዳንዱ የታለመ መለኪያ ሚዛን የሚጠብቅ ተቃራኒ መለኪያ ያስፈልገዋል (ሽፋን ⇒ ሚውቴሽን + መሸፈንን መከላከል፤ አስቸጋሪውን ኮድ ለመፈተሽ የሚያስገድዱ የሞጁል-ተኮር ዝቅተኛ ገደቦች)።
- **በሰላም መዝለል።** የጎደለ መሠረተ ልማት ፈጽሞ አያግድም፤ እውነተኛ መቀነስ ብቻ ያግዳል።
- **ውድ ለሆኑ መለኪያዎች `dedicatedGate`።** ውጫዊ binary የሚፈልጉ መለኪያዎች፣ ከተመሳሳይ ጊዜ ማዕከላዊ ራቼት ውጭ፣ የራሳቸው ስክሪፕት (ከመዝለል ጋር) ይኖራቸው።
- **ውህደቱ በሚከናወንበት ቦታ ጌት ያድርጉ።** በፈጣኑ ጌት እና በትክክለኛው ውህደት መካከል ክፍተት አይተዉ (ከfast-gates መከፈል የተገኘው ትምህርት)።
- **ጥቂትና በጥንቃቄ የተመረጡ አጋጅ ጌቶች።** Sonar/DORA፦ በጣም ብዙ ሁኔታዎች = ድካም። ከአጋጅ ጌቶች ግድግዳ ይልቅ ምክር ሰጪ + ራቼትን ይምረጡ።

## ክፍል 5 — የሚመከሩ ማሻሻያዎች (በቅድሚያ የተደረደሩ፣ ተኳኋኝ)

**P0 — ከፍተኛው ROI፣ ለመጠቀም ከሞላ ጎደል ዝግጁ**

1. **የMutation score ratchet** (የመጀመሪያው የምሽት Stryker ውጤቶችን ካመነጨ በኋላ)። የcoverage-Goodhart ችግርን ለመከላከል ቁልፍ መፍትሔ፤ ~90% ተጠናቋል።
2. **የቀረውን የfast-gates ክፍተት ዝጉ** — የማማከር ሳምንቱ ካለቀ በኋላ በ`quality.yml` ያለውን የproduction build ወደ አስገዳጅ ደረጃ ከፍ ያድርጉ፣ እና የተወሰኑ release-PR-only ማረጋገጫዎችን ወደ PR→release መንገድ ማዛወርዎን ይቀጥሉ።
3. **በ`main` ላይ Branch-protection** (የባለቤት ቅንብር) — Scorecardን ያሳድጋል፣ የDSOMM ክፍተቱንም ይዘጋል።

**P1 — ጠቃሚ** 4. **osv/oasdiff → በትክክለኛው ወሰን አስገዳጅ** — osv CRITICAL+fixableን ብቻ (እንደ Trivy ባለ ሁለት ደረጃ አካሄድ)፤ oasdiff ደግሞ breaking-changesን ያግዳል። 5. **`require-tighten` → አስገዳጅ** (በዑደቱ መጨረሻ) — የልኬቶችን መሻሻል ያጸናል። 6. **ለእያንዳንዱ gate የROI/ጊዜ ግምገማ** በ`ci-summary` ውስጥ — ዘገምተኛ/ዝቅተኛ ዋጋ ያላቸውን gates ፈልጎ ለማስወገድ።

**P2 — እየቀነሰ የሚሄድ ጥቅም** 7. **SLSA L3** — ከL2 ወደ ላይ መሄድ ከፈለጉ hermetic/reproducible builder (GitHub SLSA generator)። 8. **በሪፖዚቶሪው የተቀመጠ CodeQL config + versioned semgrep** — የበለጠ ቁጥጥር/ውጤትን የመድገም ችሎታ። 9. **ለእያንዳንዱ PR የDAST smoke** — ከፍተኛ ስጋት ባላቸው endpoints ላይ ፈጣን የschemathesis/promptfoo ንዑስ ስብስብ (በምሽት ብቻ ሳይሆን)። 10. **የFlakiness dashboard + DORA metrics** — gates ፍጥነትን እየሸረሸሩ አለመሆናቸውን ለማረጋገጥ።

## ክፍል 6 — ከrelease የተገኙ ተጨባጭ ትምህርቶች (በPhase 9 የሚጨመሩ gates)

> ይህ ክፍል gate **የጎደለባቸውን** በrelease መዝጊያዎች ወቅት የተከሰቱ እውነተኛ ክስተቶች፣
> ከተጨባጭ ማስረጃና ከታቀደው gate ጋር ይመዘግባል። እያንዳንዱ ንጥል ለክፍል 5 እጩ ነው።

### ትምህርት v3.8.27 (2026-06-17) — የ"fast-gates hole" የተወሰኑ regressions እስከ release ቀን እንዲደርሱ ያደርጋል

**ምን ተከሰተ።** በv3.8.27 `/generate-release` ወቅት፣ release PR (`release/v3.8.27` → `main`)
በተቀናጀው ዑደት ውስጥ ሙሉው `ci.yml` matrix ሲሠራ ይህ **የመጀመሪያው** ጊዜ ነበር። ውጤቱ፦ በአንድ ጊዜ 12 ውድቀቶች —
**3 የተወሰኑ tests** + ~9 flakes/env። አንዳቸውም በቀጥታ የሚሠራው ምርት regressions አልነበሩም፣
ነገር ግን የዑደቱ PRዎች ወደ `release/**` የሚገቡት ሙሉውን unit suite፣ `pr-test-policy`ን (test-masking)፣
ሙሉውን integration suite ወይም schema parity checkingን በማያስኬደው **Fast QG
(`quality.yml`)** በኩል ስለሆነ ሁሉም ሳይታወቁ ቀርተዋል። 3ቱ የተወሰኑ ችግሮች፦

1. **በUI ለውጥ ምክንያት ያረጀ test** — `permissions modal switch buttons declare button type`፦
   #4034 4ኛ switch ጨመረ (a11y `type="button"` እንደተጠበቀ ነበር)፤ የtest `=== 3` ቆጠራ ጊዜ ያለፈበት
   ሆነ። Static analysis ይህንን በ#4034 PR ውስጥ መያዝ ነበረበት።
2. **በpackaging ለውጥ ምክንያት ያረጀ test** — `findMissingArtifactPaths ... root runtime files`፦
   `dist/http-method-guard.cjs` ሕጋዊ required-path ሆነ፤ የtest የሚጠበቀው ዝርዝር ጊዜ ያለፈበት
   ሆነ።
3. **መረጃ የሚያጣ modularization divergence (ከሁሉም የከፋው)** — `settings schemas accept ... unprefixed
toggle`፦ **modularized** የሆነው `updateSettingsSchema` (`schemas/settings.ts`፣ በ#3988 የተፈጠረ) ከcanonical
   ምንጩ (`settingsSchemas.ts`) ተለየ፦ **45 fields vs 85 — 40 dropped + 6 divergent (qdrant\*)**።
   ይህ **dead-code** ነበር (runtime canonical የሆነውን ይጠቀማል)፣ ስለዚህ በቀጥታ ተጽዕኖ አልነበረውም፤ ነገር ግን በእጅ የተጻፈ parity
   test ብቻ ያዘው። #4030 ከ#3988/#3993 የመጡ 16 ተመሳሳይ የተጣሉ ነገሮችን መልሷል፣ ይህኛው ግን አምልጧል።

**የታቀዱ gates (Phase 9)፦**

- **G1 — የfast-gates ክፍተቱን በእርግጥ ዝጉ (P0 #2ን ያስፋፋል)።** በ`quality.yml` (PR→`release/**`) ውስጥ፣
  ከtypecheck + impacted tests በተጨማሪ **`pr-test-policy` (test-masking) + ሙሉውን የተወሰነ
  unit suite** (ወይም ቢያንስ ፈጣንና non-flaky የሆኑትን static/parity files) ያስኪዱ።
  በዚህ መንገድ ጊዜ ያለፈባቸው tests እና assert removal የሚያስገባቸው PR ውስጥ ይያዛሉ — በ
  release ቀን ሳይሆን። integration/e2eን ከዚህ ውጭ ያድርጉ (ዘገምተኛ/flaky)፣ ነገር ግን የተወሰነው ንብርብር በ
  PR→main ውስጥ ብቻ ሊቀር **አይችልም**።
- **G2 — Modularization parity gate (አዲስ፣ በአሁኑ ጊዜ ያልተሸፈነ)።** በmodularized barrel (`src/shared/validation/schemas/*`፣ `providerRegistry`
  modules፣ ወዘተ.) እንደገና export ለተደረገ ለእያንዳንዱ symbol፣ **shape**ን (`z.object` keys፣ registry entries) ከcanonical
  ምንጩ ጋር የሚያነጻጽር እና divergence (የተጣለ/ተጨማሪ field) ሲኖር **የሚያወድቅ** ማረጋገጫ። ይህ ከ
  #3988 የመጣውን የ40-field መጥፋት በዚያው PR ውስጥ ይይዘው ነበር። በእጅ የተጻፉ parity testsን ወደ አጠቃላይ መፍትሔ ያሰፋል (እነዚህም አንድ ሰው
  ለመጻፍ ባስታወሰባቸው ቦታዎች ብቻ ይገኛሉ)። ወጪው ዝቅተኛ ነው፦ ሁለቱንም import በማድረግ `Object.keys(shape)`ን diff ያደርጋል።
- **G3 — የተወሰነ flake triage (ድጋፍ)።** LiveWS-startup እና integration-combo/breaker
  tests የሚወድቁት በCI ውስጥ ባለ server timeout/cascade (env) ምክንያት እንጂ በlogic ምክንያት አይደለም። release-PR ቀይ ምልክት
  **እውነተኛ signalsን ብቻ** እንዲያሳይ እንጂ በመካከል ያሉትን የተወሰኑ regressions የሚሸፍን noise እንዳይሆን፣ እነዚህን
  `known-flaky` (ከissue ጋር quarantined) ብለው ምልክት ያድርጉ።

**መርህ፦** _gate የmerge ሂደቱ በሚከናወንበት ቦታ መሥራት አለበት_ (በ"Cross-cutting principles" ውስጥ ቀድሞውኑ ተጠቅሷል)።
የv3.8.27 ክስተት ይህ በlint/typecheck ላይ ብቻ ሳይሆን በ**የተወሰነ test layer** ላይም እንደሚሠራ ያሳያል —
አለበለዚያ ጊዜ ያለፈባቸው tests + መረጃ የሚያጣ modularization ዕዳ የሚታየው በPR→main ውስጥ፣ በጅምላ፣
ከሁሉም በከፋው ጊዜ ብቻ ነው።
