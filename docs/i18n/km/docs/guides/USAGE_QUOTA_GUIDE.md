## ទិដ្ឋភាពទូទៅ

រាល់សំណើដែលឆ្លងកាត់ OmniRoute បង្កើត **កំណត់ត្រាការប្រើប្រាស់** មួយ ដែលកត់ត្រា៖

- **អត្តសញ្ញាណ**៖ API key, provider, model និង combo មួយណាដែលត្រូវបានប្រើ
- **ថូខឹន**៖ ថូខឹន prompt, ថូខឹន completion, ថូខឹន cached និងចំនួនសរុប
- **ថ្លៃដើម**៖ ចំនួនទឹកប្រាក់ជា USD (គណនាពីទិន្នន័យតម្លៃ)
- **ពេលវេលា**៖ latency និង timestamp ចាប់ផ្តើម/បញ្ចប់
- **ស្ថានភាព**៖ ជោគជ័យ កំហុស ត្រូវបានកម្រិតអត្រា ជាដើម។

កំណត់ត្រាទាំងនេះត្រូវបានប្រមូលផ្តុំទៅជា **ទិន្នន័យវិភាគ** រក្សាទុកជា **snapshot កូតា** និងប្រើដើម្បីអនុវត្ត **ដែនកំណត់ថវិកាសម្រាប់ key នីមួយៗ**។

```
សំណើ ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    ការវិភាគ   កូតា   ការគិតថ្លៃ
                 (ផ្ទាំងគ្រប់គ្រង) (អនុវត្ត) (នាំចេញ)
```

## អ្វីខ្លះដែលត្រូវបានកត់ត្រា

សេវា `usage.ts` កត់ត្រា **ព្រឹត្តិការណ៍ប្រើប្រាស់** មួយសម្រាប់រាល់សំណើ៖

| វាល                | ប្រភេទ  | ប្រភព                                                      |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | UUID ដែលបានបង្កើតនៅពេលកត់ត្រា                              |
| `apiKeyId`         | string  | API key ដែលបានផ្តួចផ្តើមសំណើ                               |
| `provider`         | string  | Provider ID (openai, anthropic ជាដើម)                      |
| `model`            | string  | Model ID (gpt-5, claude-opus-4-6 ជាដើម)                    |
| `comboId`          | string? | Combo ID ប្រសិនបើត្រូវបានកំណត់ផ្លូវតាមរយៈ combo            |
| `promptTokens`     | number  | មកពីការឆ្លើយតប upstream                                    |
| `completionTokens` | number  | មកពីការឆ្លើយតប upstream                                    |
| `cachedTokens`     | number  | ថូខឹនដែលបាន cache hit (Anthropic prompt caching ជាដើម)     |
| `totalTokens`      | number  | prompt + completion                                        |
| `costUsd`          | number  | គណនាពីទិន្នន័យតម្លៃ                                        |
| `latencyMs`        | number  | រយៈពេលសំណើពីដើមដល់ចប់                                      |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | ថ្នាក់កំហុស ប្រសិនបើ status != success                     |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | ទិន្នន័យផ្ទាល់ខ្លួនដែលបានបញ្ចូលដោយ plugin                  |

### ប្រភពនៃថូខឹន

ថូខឹនត្រូវបានស្រង់ចេញពីការឆ្លើយតបរបស់ provider upstream នៅក្នុង **កម្មវិធីដោះស្រាយការឆ្លើយតប**៖

```ts
// មកពី open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

សម្រាប់ provider ដែលមិនផ្តល់ទិន្នន័យការប្រើប្រាស់ត្រឡប់មកវិញ (provider មួយចំនួនដែលប្រើ web-cookie) OmniRoute **ប៉ាន់ស្មាន** ថូខឹនដោយប្រើវិធីសាស្ត្រ `~4 chars per token` (សូមមើល `open-sse/services/autoCombo/pipelineRouter.ts`)។

### ថូខឹនដែលបាន Cache

OmniRoute តាមដាន `cached_tokens` ដាច់ដោយឡែកពី `prompt_tokens` ពីព្រោះ៖

- Anthropic prompt caching គិតថ្លៃក្នុងអត្រាទាបជាងសម្រាប់ថូខឹនដែលបាន cache (10% នៃអត្រាធម្មតា)
- Provider មួយចំនួនផ្តល់ `cache_read_input_tokens` ត្រឡប់មកវិញ ដែលគួរត្រូវបានកំណត់តម្លៃខុសគ្នា
- ទិន្នន័យវិភាគអាចបង្ហាញ **អត្រា cache hit** = `cached_tokens / prompt_tokens`

## ការគណនាថ្លៃចំណាយ

ថ្លៃចំណាយត្រូវបានគណនាពី **ទិន្នន័យតម្លៃ** ដែលបានធ្វើសមកាលកម្មពី LiteLLM (`src/lib/pricingSync.ts`)៖

| ម៉ូដែល            | បញ្ចូល $/1M | បញ្ចេញ $/1M | ឃ្លាំងសម្ងាត់ $/1M |
| ----------------- | ----------- | ----------- | ------------------ |
| gpt-5             | $2.50       | $10.00      | —                  |
| claude-opus-4-6   | $15.00      | $75.00      | $1.50              |
| claude-sonnet-4-5 | $3.00       | $15.00      | $0.30              |
| gemini-2.5-pro    | $1.25       | $10.00      | —                  |

រូបមន្តគណនាថ្លៃចំណាយ (`src/lib/usage/costCalculator.ts`)៖

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **ហេតុអ្វីត្រូវដកចំនួនថូខឹនក្នុងឃ្លាំងសម្ងាត់ចេញពីប្រូម?** ផ្នែកដែលបានរក្សាទុកក្នុងឃ្លាំងសម្ងាត់មានតម្លៃគិតដោយឡែកពីគ្នា។ ការគិតតម្លៃបញ្ចូលលើប្រូមទាំងមូលនឹងធ្វើឱ្យគិតថ្លៃលើស។

### ការធ្វើសមកាលកម្មតម្លៃ

ទិន្នន័យតម្លៃត្រូវបានធ្វើសមកាលកម្មដោយស្វ័យប្រវត្តិពី LiteLLM តាមរយៈចំណុចចុង `/api/pricing/sync` (ដំណើរការដោយកិច្ចការ cron ដែលមានស្រាប់ មិនមែនអថេរបរិស្ថានសម្រាប់អ្នកប្រើទេ)៖

```bash
# ដំណើរការដោយដៃ
curl -X POST http://localhost:20128/api/pricing/sync
```

សម្រាប់ម៉ូដែលដែលមិនមានទិន្នន័យតម្លៃ OmniRoute នឹងប្រើ **ការប៉ាន់ស្មានថ្លៃចំណាយ** ជំនួសវិញ ដោយផ្អែកលើអត្រាមធ្យមខាងក្នុង (បានមកពីទិន្នន័យតម្លៃរបស់ LiteLLM)។

### ធាតុបង្ហាញក្នុងផ្ទាំងគ្រប់គ្រងដែលបានគណនា

សម្រាប់ចន្លោះកាលបរិច្ឆេទណាមួយ ស្រទាប់វិភាគនឹងគណនា៖

| ធាតុបង្ហាញ                      | សេចក្ដីពណ៌នា                                                 |
| ------------------------------- | ------------------------------------------------------------ |
| **កាតសង្ខេប**                   | សំណើសរុប ថ្លៃចំណាយសរុប ថូខឹនសរុប និងអត្រាជោគជ័យ              |

| **ការបែងចែកតាមអ្នកផ្ដល់សេវា**   | គំនូសតាងរបារនៃសំណើតាមអ្នកផ្ដល់សេវា                           |
| **API key កំពូល**               | តារាងនៃ key កំពូលទាំង 10 តាមថ្លៃចំណាយ                        |
| **ការវិភាគកំហុស**               | អត្រាកំហុសតាមពេលវេលា និងក្រុមកំហុសកំពូល                      |

````ts
## ការអនុវត្តកូតា

កូតាសម្រាប់ API key នីមួយៗត្រូវបានអនុវត្តនៅពីរកន្លែង៖

1. **កម្រិតទន់** (`quotaWarnAt`)៖ ការព្រមានលើផ្ទាំងគ្រប់គ្រង នៅពេលការប្រើប្រាស់លើសកម្រិតកំណត់
2. **កម្រិតរឹង** (`quotaLimit`)៖ សំណើត្រូវបានបដិសេធដោយ HTTP 429 នៅពេលលើសកម្រិត

### ការកំណត់រចនាសម្ព័ន្ធ

```ts
// សម្រាប់ API key នីមួយៗ
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — បង្ហាញការព្រមាន
  quotaLimit: 10_00,    // $10.00 — បញ្ឈប់ទាំងស្រុង
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### លំហូរនៃការអនុវត្ត

```
សំណើ ──▶ quotaCheck()
              │
              ├── ស្ថិតក្នុងកម្រិត?  ──▶ អនុញ្ញាត
              │
              └── លើសកម្រិត?  ──▶ 429 សំណើច្រើនពេក
                                   ជាមួយបឋមកថា Retry-After
```

### រូបថតស្ថានភាពកូតា

តារាង `quotaSnapshots` រក្សាទុក **ស្ថានភាពកូតាប្រវត្តិសាស្ត្រ** សម្រាប់ការវិភាគនិន្នាការ៖

| វាល | សេចក្ដីពិពណ៌នា |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | key ដែលកំពុងត្រូវបានតាមដាន |
| `window` | "day" | "week" | "month" |
| `used` | ថ្លៃចំណាយដែលបានប្រើក្នុងចន្លោះពេលនេះ (សេន) |
| `limit` | កម្រិតកំណត់ (សេន) |
| `resetAt` | ពេលដែលចន្លោះពេលត្រូវបានកំណត់ឡើងវិញ |
| `createdAt` | ពេលដែលរូបថតស្ថានភាពត្រូវបានថត |

រូបថតស្ថានភាពត្រូវបានថត **នៅរាល់សំណើ** ដែលប្រើថ្លៃចំណាយ > 0 ហើយត្រូវបានប្រើដើម្បី៖

- បង្ហាញរបារវឌ្ឍនភាពកូតានៅលើផ្ទាំងគ្រប់គ្រង
- បង្ហាញគំនូសតាងនិន្នាការកូតារយៈពេល 30 ថ្ងៃ
- បង្កឱ្យមានការជូនដំណឹង នៅពេលការប្រើប្រាស់ខិតជិតដល់កម្រិតកំណត់

## ការរក្សាទុក និងការសម្អាត

ទិន្នន័យការប្រើប្រាស់កើនឡើងប្រហែល ~1-10KB ក្នុងមួយសំណើ។ នៅពេលប្រើប្រាស់ក្នុងទ្រង់ទ្រាយធំ វាអាចមានទំហំគួរឱ្យកត់សម្គាល់។

### ការកំណត់ការរក្សាទុក

ការរក្សាទុកប្រវត្តិការប្រើប្រាស់ត្រូវបានកំណត់តាមរយៈ Database Settings ក្នុង UI ឬតាមរយៈ `/api/settings/database`។

### ការសម្អាត

កំណត់ត្រាចាស់ៗត្រូវបានសម្អាតដោយ `src/lib/db/cleanup.ts`៖

- ត្រូវបានកេះដោយដំណើរការ cron នៅផ្ទៃខាងក្រោយ
- លុបកំណត់ត្រាពី `usage_history` ដែលចាស់ជាងការកំណត់ការរក្សាទុក `usageHistory` ដែលបានកំណត់

### ការប៉ាន់ស្មានទំហំផ្ទុក

សម្រាប់ចរាចរណ៍ខ្ពស់ខ្លាំង សូមពិចារណា៖


### 4. កំណត់កូតាសម្រាប់ key នីមួយៗ

ត្រូវកំណត់ `quotaLimit` ជានិច្ច ដើម្បីការពារការចំណាយដែលកើនឡើងដោយមិនអាចគ្រប់គ្រងបាន៖

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // កម្រិតអតិបរមា $10/ខែ
```

### 5. សវនកម្មអ្នកប្រើប្រាស់ច្រើនបំផុត

ប្រើ dashboard ឬ **`/api/usage/analytics`** ដើម្បីដាក់ជាក្រុមតាម API key និងតម្រៀបតាមចំណាយ៖

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## ការដោះស្រាយបញ្ហា

### "ចំណាយខ្ពស់ជាងការរំពឹងទុក"

1. ពិនិត្យ **`/api/usage/analytics?groupBy=model`** — ស្វែងរកម៉ូដែលដែលមានតម្លៃថ្លៃ
2. ពិនិត្យ **`/api/usage/analytics?groupBy=apiKey`** — ស្វែងរកអ្នកប្រើប្រាស់ច្រើន
3. ផ្ទៀងផ្ទាត់ថាទិន្នន័យតម្លៃមានភាពទាន់សម័យ៖ `POST /api/pricing/sync`

### "បាត់កំណត់ត្រា"

- ពិនិត្យការកំណត់ការរក្សាទុក DB នៅក្រោម Dashboard → Database → Cleanup — កំណត់ត្រាចាស់ៗត្រូវបានលុបដោយកិច្ចការសម្អាតតាមកាលកំណត់ (`src/lib/db/cleanup.ts`)
- ពិនិត្យរកកំហុសក្នុង `src/lib/db/usage*.ts` — ភាពបរាជ័យក្នុងការសរសេរទៅ DB ត្រូវបានកត់ត្រា ប៉ុន្តែមិនត្រូវបានបង្ហាញឡើយ
- ផ្ទៀងផ្ទាត់ថាសំណើពិតជាបានទៅដល់ `chatCore` — ពិនិត្យ combo routing

### "កូតាមិនត្រូវបានអនុវត្ត"

- ពិនិត្យការកំណត់ `quotaLimit` របស់ key
- ផ្ទៀងផ្ទាត់ថា `quotaWindow` ត្រូវបានកំណត់ត្រឹមត្រូវ
- រកមើលកំណត់ត្រា `quotaSnapshots` — កំណត់ត្រាទាំងនេះគួរតែត្រូវបានបង្កើតនៅគ្រប់សំណើ
