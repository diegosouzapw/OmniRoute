## ការដោះស្រាយបញ្ហាលម្អិត

---

### ការកំណត់អត្រាលើអ្នកផ្តល់សេវាឥតគិតថ្លៃ (429 / 400 / 401)

**រោគសញ្ញា**៖ នៅពេលប្រើ `model: "auto"` ជាមួយអ្នកផ្តល់សេវាឥតគិតថ្លៃ/មិនទាមទារការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ (opencode, auggie ជាដើម) អ្នកនឹងទទួលបាន `HTTP 429`, `400` ឬ `401` ជាបណ្តោះអាសន្នជំនួសឱ្យចម្លើយ។ សំណើទទួលបានជោគជ័យ នៅពេលសាកល្បង prompt ដដែលម្តងទៀតបន្ទាប់ពីបន្តិច ប៉ុន្តែស្វ័យប្រវត្តិកម្ម (cron jobs, agents, scripts) ឈប់ដំណើរការនៅពេលបរាជ័យលើកដំបូង។

**មូលហេតុដើម**៖ របៀបបរាជ័យឯករាជ្យចំនួនបីកើតឡើងត្រួតគ្នា៖

1. **ដែនកំណត់អត្រារបស់អ្នកផ្តល់សេវា (`429`)**៖ កម្រិតឥតគិតថ្លៃអាចដាក់កូតាតាមចន្លោះពេល។ ការហៅស្របគ្នាជាច្រើនក្នុងពេលតែមួយធ្វើឱ្យកូតានោះអស់ ដូច្នេះសំណើបន្ទាប់ត្រូវបានបដិសេធរហូតដល់ចន្លោះពេលត្រូវបានកំណត់ឡើងវិញ។
2. **ម៉ូដែលខូចក្នុង passthrough (`400`/`401`)**៖ pool របស់ `auto/*` អាចរួមបញ្ចូលម៉ូដែល passthrough ពី `opencode` ដែលបានចុះបញ្ជីក្នុង catalog ប៉ុន្តែមិនមានព័ត៌មានសម្គាល់អត្តសញ្ញាណដែលនៅមានសុពលភាព (ឧ. `oc/north-mini-code-free` → `401`)។ auto-router សាកល្បងម៉ូដែលមួយ បរាជ័យ ហើយកំហុសត្រូវបានបញ្ជូនបន្ត មុនពេល fallback ចាប់ផ្តើមដំណើរការ។
3. **ការកើនឡើងដោយសារដំណើរការស្របគ្នា (`429` ក្រោមបន្ទុក)**៖ នៅពេល agent/cron sessions ច្រើនចូលប្រើ `auto` ក្នុងពេលតែមួយ អត្រាសំណើសរុបលើសពីអ្វីដែលអ្នកផ្តល់សេវាឥតគិតថ្លៃអាចទ្រាំទ្របាន ដូច្នេះការហៅត្រឹមត្រូវត្រូវបានសម្គាល់ថាជាការបំពាន។

**ដំណោះស្រាយដែលបានផ្ទៀងផ្ទាត់ (រាយការណ៍ដោយសហគមន៍, 2026-08-10)**៖ កែសម្រួល environment variables ចំនួនបី ដើម្បីឱ្យការប្តូរវេន ដំណើរការស្របគ្នា និង fallback ទប់ទល់នឹងភាពប្រែប្រួលរបស់កម្រិតឥតគិតថ្លៃ ជំនួសឱ្យបរាជ័យដោយសារវា៖

```bash
export OMNIROUTE_ROTATE_ON_400=true           # ប្តូរទៅម៉ូដែល/អ្នកផ្តល់សេវាផ្សេងទៀតនៅពេលទទួលបាន 400/401 (រំលងម៉ូដែល passthrough ដែលខូច)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ដែនកំណត់ជាក់លាក់សម្រាប់ការទទួលយកបន្ទុកធ្ងន់ (តាមលំនាំដើមមិនបានកំណត់៖ គ្មានដែនកំណត់ចំនួនសំណើ សូមមើលកំណត់សម្គាល់ខាងក្រោម)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # បង្កើនការរង់ចាំដែលមានដែនកំណត់ឱ្យលើសតម្លៃលំនាំដើម RATE_LIMIT_MAX_WAIT_MS សម្រាប់ upstreams ដែលយឺត
```

កំណត់តម្លៃទាំងនេះនៅក្នុង environment របស់ process OmniRoute (daemon ឧ. តាមរយៈ LaunchAgent plist ឬ `systemctl edit`) បន្ទាប់មកចាប់ផ្តើម OmniRoute ឡើងវិញ។ rotation flag គឺជាឧបករណ៍ដែលមានប្រសិទ្ធភាពខ្ពស់បំផុតតែមួយ៖ វាបំប្លែងការបរាជ័យទាំងស្រុងទៅជាការព្យាយាមម្តងទៀតដោយមិនរំខាន តាមរយៈអ្នកផ្តល់សេវាដែលដំណើរការល្អនៅក្នុង pool។

**ចំណាំ**៖ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` កំណត់ចំនួនសំណើដែលមានបន្ទុកធ្ងន់ — long-context — ដែលអាចដំណើរការក្នុងពេលតែមួយ។ ដែនកំណត់នេះជាច្រកទទួលយក មិនមែនជាឧបករណ៍កំណត់អត្រារបស់អ្នកផ្តល់សេវាទេ។ **បច្ចុប្បន្នភាព #503-fanout៖** var នេះលែងត្រូវបានកំណត់តាមលំនាំដើមទៀតហើយ (ឥឡូវនេះវាអនុវត្តតែពេលបានកំណត់ជាក់លាក់ ដូចខាងលើប៉ុណ្ណោះ) — ផ្ទុយទៅវិញ ការទទួលយកបន្ទុកធ្ងន់ត្រូវបានគ្រប់គ្រងដោយ byte budget ដែលទាញយកដោយស្វ័យប្រវត្តិ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ដែលធ្វើមាត្រដ្ឋានដោយខ្លួនឯងតាមដែនកំណត់ memory ពិតប្រាកដរបស់ host ដូច្នេះ deployment ថ្មីគួរជួបការបដិសេធ `503 chat_admission_busy` តិចជាងមុនយ៉ាងច្រើន ដោយមិនចាំបាច់កំណត់ var នេះទាល់តែសោះ។ ការកំណត់វាជាក់លាក់នៅទីនេះនៅតែដំណើរការដូចដែលបានចងក្រងជាឯកសារ។ ការកំណត់ជំនួស byte-budget ជាក់លាក់ត្រូវបានកំហិតចន្លោះពី 8 MiB–2 GiB។ `413 body_exceeds_budget` មិនមែនជាបញ្ហាបណ្តោះអាសន្នទេ៖ បង្កើន byte budget នោះ បន្ថយ `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ឬបង្កើនដែនកំណត់ memory របស់ process។ ការកាត់បន្ថយដោយសារ `inflight_bytes_budget` គឺជាការប្រជែងធនធានបណ្តោះអាសន្ន ហើយនៅតែអាចព្យាយាមម្តងទៀតបាន។ ការកំណត់អត្រាតាមអ្នកផ្តល់សេវានីមួយៗ (`open-sse/services/rateLimitManager.ts`) ត្រូវបានគ្រប់គ្រងដោយឡែកតាមរយៈ `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` និង `RATE_LIMIT_AUTO_ENABLE` — សូមមើល `.env.example`។

**វិធីផ្ទៀងផ្ទាត់ថាវាដំណើរការ**៖ ដំណើរការ agent/cron របស់អ្នកពីរដងជាប់ៗគ្នាក្នុងរយៈពេលខ្លី ហើយបញ្ជាក់ថាទាំងពីរដំណើរការបានជោគជ័យ។ មុនពេលកែបញ្ហា ការដំណើរការលើកទីពីរជាធម្មតានឹងបង្ហាញកំហុស `429`/`401`។ បន្ទាប់ពីកែបញ្ហា ការបរាជ័យ (ប្រសិនបើមាន) នឹងត្រូវបានសាកល្បងឡើងវិញដោយស្វ័យប្រវត្តិដោយមិនរំខាន ហើយការហៅនឹងបញ្ចប់ដោយជោគជ័យ។ អ្នកក៏អាចប្រើ `curl /monitoring/health` ហើយតាមដាន field `rateLimitedUntil` នៅលើការតភ្ជាប់ទៅកាន់អ្នកផ្តល់សេវា និង `circuitBreakers.providerBreakers[].state` សម្រាប់អ្នកផ្តល់សេវាដែលរងផលប៉ះពាល់ផងដែរ — state អាចជា `CLOSED`, `DEGRADED`, `OPEN` ឬ `HALF_OPEN` (សូមមើល `src/shared/utils/circuitBreaker.ts`) ហើយអ្នកផ្តល់សេវាដែលបន្តបរាជ័យនឹងប្តូរពី `CLOSED → DEGRADED → OPEN` មុនពេលចន្លោះពេលកំណត់ឡើងវិញអនុញ្ញាតឱ្យការសាកល្បងមួយឆ្លងកាត់ (`HALF_OPEN`)។

**ប្រសិនបើអ្នកនៅតែឃើញ 429**៖ គណនីសកម្មសម្រាប់អ្នកផ្តល់សេវានោះពិតជាបានប្រើអស់ _កូតា_ របស់វា (មិនមែនគ្រាន់តែដល់កម្រិតអត្រាប៉ុណ្ណោះទេ)។ បន្ថែមគណនីទីពីរសម្រាប់អ្នកផ្តល់សេវាដូចគ្នានៅក្នុង OmniRoute dashboard → Providers → Accounts ឬបន្ថែមអ្នកផ្តល់សេវាឥតគិតថ្លៃផ្សេងទៀត (ឧ. `routeway`, `auggie`)។ ការបង្វិលប្រើគណនីជួយបានតែចំពោះកំហុសបណ្តោះអាសន្នទាក់ទងនឹងអត្រា/400/401 ប៉ុណ្ណោះ។ ការប្រើអស់កូតាទាំងស្រុងតម្រូវឱ្យមានព័ត៌មានសម្គាល់អត្តសញ្ញាណទីពីរ ឬអ្នកផ្តល់សេវាផ្សេងទៀត។

**ប្រសិនបើអ្នកឃើញ 403 នៅលើម៉ូដែល vision (`auto/vision`, `bazaarlink/*`)**៖ គណនីដែលបានតភ្ជាប់មិនមានគម្រោងបង់ប្រាក់ដែលរួមបញ្ចូល vision ឬ API key មានសិទ្ធិមិនគ្រប់គ្រាន់។ សូមផ្ទៀងផ្ទាត់នៅក្នុង dashboard របស់អ្នកផ្តល់សេវាថា scope របស់ key រួមបញ្ចូល vision/multimodal ឬភ្ជាប់គណនីកម្រិតបង់ប្រាក់ ហើយរក្សាវាទុកជាគោលដៅ vision។

## ការព្រមានពី npm install (ERESOLVE / peer / deprecated)

នៅពេលអ្នកដំណើរការ `npm install -g omniroute` អ្នកអាចឃើញការព្រមានជាច្រើន ដូចជា `npm warn ERESOLVE` សេចក្តីជូនដំណឹងអំពី peer dependency និងសារ `deprecated`។ **ទាំងនេះគឺជាអ្វីដែលរំពឹងទុក និងមិនបង្កគ្រោះថ្នាក់ទេ។** ការដំឡើងរបស់អ្នកបានជោគជ័យ ប្រសិនបើអ្នកឃើញ `added <N> packages` នៅក្នុងលទ្ធផល។

ដើម្បីលាក់ការព្រមានអំពីការដោះស្រាយ peer dependency សូមប្រើទម្រង់ដំឡើងដែល OmniRoute គាំទ្រ៖

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` លាក់តែសេចក្តីជូនដំណឹង `ERESOLVE` និង peer dependency ប៉ុណ្ណោះ។ សេចក្តីជូនដំណឹងអំពីការឈប់គាំទ្រនៅតែបង្ហាញ ព្រោះវាមកពីកញ្ចប់ភាគីទីបីបន្តបន្ទាប់ ហើយវាមិនមានន័យថាការដំឡើងបានបរាជ័យនោះទេ។

ការព្រមានទាំងនេះកើតចេញពីជួរកំណែ peer dependency ដែលហួសសម័យនៅក្នុងកញ្ចប់ភាគីទីបី ដែល OmniRoute មិនអាចគ្រប់គ្រងបាន៖

1. **`marked-terminal` ត្រូវការ `marked >=1 <16` ប៉ុន្តែបានរកឃើញ `marked@18`** — ក្នុងការប្រើប្រាស់ជាក់ស្តែង វាដំណើរការបានល្អ។ ជួរកំណែ peer របស់គម្រោងដើមគ្រាន់តែហួសសម័យប៉ុណ្ណោះ។
2. **`deprecated prebuild-install@7.1.3`** — ជាឧបករណ៍ជំនួយសម្រាប់ទាញយកឯកសារគោលពីរដើមកំណើត ដែលជាភាពអាស្រ័យបន្តបន្ទាប់។ វាមិនត្រូវបាន
   ប្រើដើម្បីដំឡើង transport binding `wreq-js` ដែលបានចាក់សោកំណែទេ ហើយក៏មិនបង្ហាញថាការរៀបចំ transport
   របស់អ្នកផ្តល់សេវា web-cookie បានបរាជ័យដែរ។

**មិនចាំបាច់ធ្វើអ្វីទេ** — ការព្រមានទាំងនេះមិនអាចលាក់ទាំងស្រុងបានទេ លុះត្រាតែធ្វើ fork កញ្ចប់ដើម។

## ការព្រមានថា npm install-scripts ត្រូវបានទប់ស្កាត់ (ការដំឡើងជាសកល)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

នៅពេលដំណើរការ `npm install -g omniroute` កំណែ npm ថ្មីៗ (v11+ និង v12+) ទប់ស្កាត់ស្គ្រីបវដ្តជីវិតរបស់កញ្ចប់តាមលំនាំដើម និងបង្ហាញការព្រមានអំពី install-scripts៖

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### តើអាចមិនអើពើនឹងការព្រមាននេះបានទេ?

**បានមួយផ្នែក ប៉ុន្តែមិនណែនាំឱ្យដំណើរការដោយគ្មានស្គ្រីបទេ។** OmniRoute មានយន្តការបម្រុងដែលអាចប្តូរទៅជម្រើសផ្សេងដោយរលូន៖ ប្រសិនបើមិនអាចផ្ទុក binding ដើមកំណើត `better-sqlite3` ពីកញ្ចប់ standalone បាន កម្មវិធីនឹងប្តូរទៅប្រើ driver ជំនួស ដូចជា `node:sqlite` ឬ `sql.js` (សូមមើល [ការដោះស្រាយ SQLite Runtime](../ops/SQLITE_RUNTIME.md))។ ម៉ាស៊ីនមេនៅតែអាចចាប់ផ្តើមបាន ប៉ុន្តែការដំណើរការលើជម្រើសបម្រុង WASM ដូចជា `sql.js` នឹងបិទមុខងារ SQLite WAL (Write-Ahead Logging) ហើយបង្កើនការប្រើប្រាស់អង្គចងចាំ និងបន្ទុកការធ្វើសមកាលកម្មថាស។

### តើស្គ្រីបណាខ្លះដែលចាំបាច់ពិតប្រាកដ?

មិនមែនស្គ្រីបដែលត្រូវបានទប់ស្កាត់ទាំងអស់សុទ្ធតែចាំបាច់សម្រាប់ដំណើរការ OmniRoute នោះទេ៖

- **ចាំបាច់ (`omniroute`, `better-sqlite3`)៖** OmniRoute ដំណើរការពីកញ្ចប់កម្មវិធី standalone របស់ Next.js (`dist/`)។ អំឡុងពេលដំឡើង npm នឹងទាញយក ឬចងក្រង driver SQLite ដើមកំណើតសម្រាប់ម៉ាស៊ីនកំពុងប្រើ ទៅក្នុង `node_modules/better-sqlite3/` កម្រិតកំពូល។ បន្ទាប់មក ស្គ្រីប `postinstall` របស់ OmniRoute (`scripts/build/postinstall.mjs`) នឹងផ្ទៀងផ្ទាត់ និងចម្លងឯកសារគោលពីរសម្រាប់ម៉ាស៊ីនទាំងនេះទៅក្នុង `dist/node_modules/` ដើម្បីឱ្យម៉ាស៊ីនមេ standalone អាចចូលប្រើពួកវាបាន។ ប្រសិនបើស្គ្រីប postinstall របស់ `omniroute` ត្រូវបានទប់ស្កាត់ ជំហានចម្លងនេះនឹងត្រូវបានរំលង។
- **ជាជម្រើស/បន្តបន្ទាប់ (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`)៖** ទាំងនេះជាឧបករណ៍ជំនួយសម្រាប់ build ឧបករណ៍តាមដានការផ្លាស់ប្តូរ ឬឧបករណ៍ keychain របស់ប្រព័ន្ធ។ ការអនុញ្ញាតឱ្យពួកវាដំណើរការនឹងការពារការព្រមានអំពី build ប៉ុន្តែវាមិនចាំបាច់សម្រាប់មុខងារ routing ស្នូលទេ។
- **មិនរាប់បញ្ចូល (`onnxruntime-node`)៖** ជាភាពអាស្រ័យជាជម្រើសសម្រាប់ AI embeddings មូលដ្ឋាន ហើយវា **មិន** ចាំបាច់សម្រាប់ដំណើរការ OmniRoute ទេ។ ស្គ្រីប postinstall របស់វាទាញយកទិន្នន័យ CUDA ប្រហែល ~300MB ពី NuGet។ កុំបញ្ចូលវាក្នុងបញ្ជីអនុញ្ញាត លុះត្រាតែអ្នកមានបំណងប្រើការបង្កើនល្បឿន ONNX មូលដ្ឋានលើផ្នែករឹងដែលគាំទ្រយ៉ាងច្បាស់លាស់។

### ដំណោះស្រាយដែលបានណែនាំ

ដើម្បីអនុញ្ញាតឱ្យស្គ្រីបដំឡើងចាំបាច់ដំណើរការ ក្នុងពេលដំឡើងជាសកល និងលាក់ការព្រមាន សូមបញ្ជូន `--allow-scripts` សម្រាប់ OmniRoute និងភាពអាស្រ័យដើមកំណើតរបស់វា៖

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

ជាជម្រើសមួយទៀត ដើម្បីកំណត់រចនាសម្ព័ន្ធនេះជាអចិន្ត្រៃយ៍សម្រាប់ការដំឡើងជាសកលទាំងអស់នៅលើគណនីអ្នកប្រើរបស់អ្នក៖

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### ផ្ទៀងផ្ទាត់ការដំឡើងរបស់អ្នក

បន្ទាប់ពីដំឡើង សូមដំណើរការឧបករណ៍វិនិច្ឆ័យដែលមានស្រាប់ ដើម្បីធានាថា binding ដើមកំណើត និងបរិស្ថាន runtime មានស្ថានភាពល្អ៖

```bash
omniroute doctor
```

## Gemini Web និង Playwright Chromium

ប្រសិនបើសំណើ Gemini Web ត្រឡប់ `503` ជាមួយសារថា Playwright Chromium

សម្រាប់ការដំឡើង npm ជាសកល សូមដំឡើង Chromium ពីថតរបស់កញ្ចប់ OmniRoute

```bash
cd "$(npm root -g)/omniroute"
```

ដែលរួមបញ្ចូល Chromium និង dependencies របស់វា។ base image
មិនរួមបញ្ចូលពួកវាទេ។

- ទំព័រចូលប្រើបង្ហាញ **ផ្ទាំងព្រមានពណ៌ទឹកក្រូច** ជាមួយកំណែ Node របស់អ្នក ប្រសិនបើ runtime ស្ថិតនៅក្រៅគោលការណ៍សុវត្ថិភាពដែលបានគាំទ្រ

1. ដំឡើង Node.js LTS ដែលបានគាំទ្រ (ណែនាំ៖ Node.js 24.x)៖

## បញ្ហា Proxy

<a name="proxy-issues"></a>

### ការផ្ទៀងផ្ទាត់ Provider បង្ហាញ "fetch failed"

**មូលហេតុ៖** Endpoint សម្រាប់ផ្ទៀងផ្ទាត់ API key (`POST /api/providers/validate`) ពីមុនបានរំលងការកំណត់រចនាសម្ព័ន្ធ proxy ដែលបណ្ដាលឱ្យមានការបរាជ័យនៅក្នុងបរិស្ថានដែលតម្រូវឱ្យបញ្ជូនតាម proxy។

**ដំណោះស្រាយ (v3.5.5+)៖** ឥឡូវនេះបញ្ហានេះត្រូវបានដោះស្រាយហើយ។ ការផ្ទៀងផ្ទាត់ Provider ត្រូវបានបញ្ជូនតាម `runWithProxyContext` ដោយគោរពតាមការកំណត់ proxy កម្រិត Provider និងជាសកលដោយស្វ័យប្រវត្តិ។

### ការពិនិត្យស្ថានភាព Token បរាជ័យជាមួយ "fetch failed"

**មូលហេតុ៖** ការធ្វើឱ្យ OAuth token ថ្មីឡើងវិញនៅផ្ទៃខាងក្រោយ មិនបានកំណត់ការកំណត់រចនាសម្ព័ន្ធ proxy ដាច់ដោយឡែកសម្រាប់ connection នីមួយៗទេ។

**ដំណោះស្រាយ (v3.5.5+)៖** ឥឡូវនេះ scheduler សម្រាប់ពិនិត្យស្ថានភាព token នឹងកំណត់រចនាសម្ព័ន្ធ proxy ដាច់ដោយឡែកសម្រាប់ connection នីមួយៗ មុនពេលព្យាយាមធ្វើឱ្យ token ថ្មីឡើងវិញ។ សូមធ្វើបច្ចុប្បន្នភាពទៅ v3.5.5+។

### SOCKS5 proxy ត្រឡប់ "invalid onRequestStart method"

**មូលហេតុ៖** នៅលើ Node.js 22, dispatcher របស់ undici@8 មិនត្រូវគ្នាជាមួយការអនុវត្ត `fetch()` ដែលភ្ជាប់មកជាមួយ Node ទេ។

**ដំណោះស្រាយ (v3.5.5+)៖** ឥឡូវនេះ OmniRoute ប្រើមុខងារ `fetch()` របស់ undici ផ្ទាល់ នៅពេល proxy dispatcher សកម្ម ដើម្បីធានាឱ្យមានឥរិយាបថស្របគ្នា។ សូមធ្វើបច្ចុប្បន្នភាពទៅ v3.5.5+។

### MITM proxy ក្រោម WSL៖ កម្មវិធី desktop នៅលើ Windows host មិនត្រូវបានស្ទាក់ចាប់

**មូលហេតុ៖** MITM proxy និង CA certificate របស់វាត្រូវបានដំឡើងនៅក្នុងបរិស្ថានដែល OmniRoute ដំណើរការ។ ក្រោម WSL បរិស្ថាននោះគឺជា Linux guest ខណៈដែលកម្មវិធី AI desktop (Kiro, Trae, Copilot, Zed, …) ដំណើរការនៅលើ Windows host។ កម្មវិធីនៅលើ host មិនទុកចិត្ត certificate store របស់ guest និងមិនបញ្ជូនចរាចរណ៍តាម system proxy របស់ guest ទេ ដូច្នេះការស្ទាក់ចាប់កម្មវិធី desktop មិនដំណើរការនៅទីនោះឡើយ។

**អនុសាសន៍៖** ដំណើរការ OmniRoute ដោយផ្ទាល់នៅលើ OS ដូចគ្នានឹងកម្មវិធី desktop ដែលអ្នកចង់ស្ទាក់ចាប់ (Windows សម្រាប់កម្មវិធី Windows; macOS/Linux ក៏ដូចគ្នា)។ ការរក្សា OmniRoute នៅក្នុង WSL ខណៈពេលកំណត់គោលដៅទៅកម្មវិធីនៅលើ host តម្រូវឱ្យអ្នកទុកចិត្ត CA certificate ដែលបានបង្កើតនៅលើ Windows host ដោយដៃ និងកំណត់ network/proxy របស់កម្មវិធីនីមួយៗនៅលើ host ឱ្យចង្អុលទៅ WSL proxy endpoint — នេះជាការកំណត់ដែលមិនត្រូវបានគាំទ្រ និងងាយមានបញ្ហា។

## បញ្ហា Cloud

### កំហុស Cloud Sync

1. ផ្ទៀងផ្ទាត់ថា `BASE_URL` ចង្អុលទៅ instance ដែលកំពុងដំណើរការរបស់អ្នក (ឧ., `http://localhost:20128`)
2. ផ្ទៀងផ្ទាត់ថា `CLOUD_URL` ចង្អុលទៅ cloud endpoint របស់អ្នក (ឧ., `https://omniroute.dev`)
3. រក្សាតម្លៃ `NEXT_PUBLIC_*` ឱ្យស្របគ្នាជាមួយតម្លៃនៅផ្នែក server

### Cloud `stream=false` ត្រឡប់ 500

**រោគសញ្ញា៖** `Unexpected token 'd'...` នៅលើ cloud endpoint សម្រាប់ការហៅដែលមិនមែនជា streaming។

**មូលហេតុ៖** Upstream ត្រឡប់ payload ជា SSE ខណៈ client រំពឹងទុក JSON។

**ដំណោះស្រាយបណ្ដោះអាសន្ន៖** ប្រើ `stream=true` សម្រាប់ការហៅទៅ cloud ដោយផ្ទាល់។ Runtime មូលដ្ឋានរួមបញ្ចូល fallback ពី SSE→JSON។

### Cloud បង្ហាញថាបានភ្ជាប់ ប៉ុន្តែ "Invalid API key"

1. បង្កើត key ថ្មីពី dashboard មូលដ្ឋាន (`/api/keys`)
2. ដំណើរការ cloud sync៖ បើក Cloud → Sync Now
3. Key ចាស់ ឬ key ដែលមិនទាន់បាន sync នៅតែអាចត្រឡប់ `401` នៅលើ cloud

## បញ្ហា Docker

### Docker IPv6 / ការតភ្ជាប់ត្រូវបានកំណត់ឡើងវិញ

<a name="docker-ipv6"></a>

**រោគសញ្ញា៖** `curl http://localhost:20128/v1/models` ត្រឡប់ `curl: (56) Recv failure: Connection reset by peer`។ Dashboard និង endpoint ដែលមិនតម្រូវឱ្យផ្ទៀងផ្ទាត់អត្តសញ្ញាណដំណើរការធម្មតា ប៉ុន្តែ endpoint ដែលតម្រូវឱ្យផ្ទៀងផ្ទាត់អត្តសញ្ញាណបរាជ័យ — វាមើលទៅដូចជាបញ្ហា auth ប៉ុន្តែតាមពិតមិនមែនទេ។

**មូលហេតុ៖** `docker run -p 20128:20128` បើកផ្សាយលើទាំង `0.0.0.0` (IPv4) និង `::` (IPv6) ប៉ុន្តែ process នៅខាងក្នុង container ស្ដាប់តែលើ IPv4 ប៉ុណ្ណោះ។ នៅលើ host ដែល `localhost` resolve ទៅ `::1` ជាមុន ការតភ្ជាប់នឹងទៅដល់ port IPv6 ដែលបានបើកផ្សាយ ដោយគ្មាន listener នៅពីក្រោយវា → ការតភ្ជាប់ត្រូវបានកំណត់ឡើងវិញ។

**ដំណោះស្រាយ៖**

1. **ការធ្វើរោគវិនិច្ឆ័យរហ័ស៖** ដំណើរការ `curl -4 http://localhost:20128/v1/models`។ ប្រសិនបើវាដំណើរការជាមួយ `-4` ប៉ុន្តែបរាជ័យបើគ្មានវា នោះអ្នកមាន bind មិនត្រូវគ្នារវាង IPv6។
2. **ដំណោះស្រាយអចិន្ត្រៃយ៍៖** Bind ទៅ IPv4 ជាក់លាក់ដោយប្រើ `-p 127.0.0.1:20128:20128` នៅក្នុង command `docker run` របស់អ្នក៖
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   វាបង្ខំឱ្យ bind ទៅ IPv4 ហើយក៏ជៀសវាងការបង្ហាញ proxy នៅលើ interface ទាំងអស់របស់ host ផងដែរ។

## បញ្ហា Circuit Breaker

### Provider ជាប់គាំងក្នុងស្ថានភាព OPEN

នៅពេល circuit breaker របស់ provider ស្ថិតក្នុងស្ថានភាព OPEN សំណើនានានឹងត្រូវបានរារាំងរហូតដល់រយៈពេល cooldown ផុតកំណត់។

**ដំណោះស្រាយ៖**

1. ចូលទៅកាន់ **ផ្ទាំងគ្រប់គ្រង → ការកំណត់ → ភាពធន់**
2. ពិនិត្យមើលកាត circuit breaker របស់ provider ដែលរងផលប៉ះពាល់
3. ចុច **កំណត់ឡើងវិញទាំងអស់** ដើម្បីសម្អាត breaker ទាំងអស់ ឬរង់ចាំរហូតដល់រយៈពេល cooldown ផុតកំណត់
4. ផ្ទៀងផ្ទាត់ថា provider ពិតជាអាចប្រើបាន មុនពេលកំណត់ឡើងវិញ

### Provider បន្តធ្វើឱ្យ circuit breaker ដំណើរការ

ប្រសិនបើ provider ចូលទៅក្នុងស្ថានភាព OPEN ដដែលៗ៖

1. ពិនិត្យមើលលំនាំនៃការបរាជ័យនៅ **ផ្ទាំងគ្រប់គ្រង → សុខភាព → សុខភាព Provider**
2. ចូលទៅកាន់ **ការកំណត់ → ភាពធន់ → ទម្រង់ Provider** ហើយបង្កើនកម្រិតកំណត់នៃការបរាជ័យ
3. ពិនិត្យមើលថាតើ provider បានផ្លាស់ប្តូរដែនកំណត់ API ឬតម្រូវឱ្យផ្ទៀងផ្ទាត់អត្តសញ្ញាណឡើងវិញដែរឬទេ
4. ពិនិត្យ telemetry នៃ latency — latency ខ្ពស់អាចបណ្តាលឱ្យមានការបរាជ័យដោយសារ timeout

## ការកំណត់ភាពធន់

### ការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិមិនដំណើរការ

- ការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិអនុវត្តចំពោះតែអ្នកផ្តល់សេវាដែលប្រើ API key ប៉ុណ្ណោះ (មិនមែន OAuth/ការជាវទេ)
- ផ្ទៀងផ្ទាត់ថា **ការកំណត់ → ភាពធន់ → ទម្រង់អ្នកផ្តល់សេវា** បានបើកការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិ
- ពិនិត្យមើលថាតើអ្នកផ្តល់សេវាត្រឡប់ status code `429` ឬ header `Retry-After` ដែរឬទេ

### ការកែសម្រួល exponential backoff

ទម្រង់អ្នកផ្តល់សេវាគាំទ្រការកំណត់ទាំងនេះ៖

- **ពេលពន្យារមូលដ្ឋាន** — រយៈពេលរង់ចាំដំបូងបន្ទាប់ពីបរាជ័យលើកទីមួយ (លំនាំដើម៖ 1s)
- **ពេលពន្យារអតិបរមា** — ដែនកំណត់អតិបរមានៃពេលរង់ចាំ (លំនាំដើម៖ 30s)
- **មេគុណ** — កម្រិតដែលត្រូវបង្កើនពេលពន្យារសម្រាប់ការបរាជ័យជាប់ៗគ្នានីមួយៗ (លំនាំដើម៖ 2x)

### ការទប់ស្កាត់ thundering herd

នៅពេលសំណើស្របគ្នាជាច្រើនទៅដល់អ្នកផ្តល់សេវាដែលបានកំណត់កម្រិតអត្រា OmniRoute ប្រើ mutex + ការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិ ដើម្បីរៀបសំណើឱ្យដំណើរការតាមលំដាប់ និងទប់ស្កាត់ការបរាជ័យបន្តបន្ទាប់។ វាដំណើរការដោយស្វ័យប្រវត្តិសម្រាប់អ្នកផ្តល់សេវាដែលប្រើ API key។

   មុខងាររបស់វារួចហើយ; `pressureSeverity` ដែលមានតម្លៃ `high`/`critical` មានន័យថា host ពិតជាខ្វះ memory —

## វចនានុក្រមកំហុស RAG / LLM ជាជម្រើស (បញ្ហា 16 ប្រភេទ)

អ្នកប្រើ OmniRoute មួយចំនួនដាក់ gateway នៅពីមុខ RAG ឬ agent stacks។ ក្នុងការរៀបចំបែបនេះ គេតែងតែឃើញលំនាំចម្លែកមួយ៖ OmniRoute មើលទៅដំណើរការល្អ (providers សកម្ម, routing profiles ត្រឹមត្រូវ, គ្មានការជូនដំណឹងអំពី rate limit) ប៉ុន្តែចម្លើយចុងក្រោយនៅតែខុស។

នៅក្នុងការអនុវត្ត ជាធម្មតាឧប្បត្តិហេតុទាំងនេះកើតចេញពី RAG pipeline ខាងក្រោម មិនមែនពី gateway ខ្លួនវាទេ។

ប្រសិនបើអ្នកចង់បានវាក្យសព្ទរួមសម្រាប់ពិពណ៌នាអំពីកំហុសទាំងនោះ អ្នកអាចប្រើ WFGY ProblemMap ដែលជាធនធានអត្ថបទខាងក្រៅក្រោមអាជ្ញាបណ្ណ MIT ហើយកំណត់លំនាំកំហុស RAG / LLM ដែលកើតឡើងញឹកញាប់ចំនួនដប់ប្រាំមួយ។ ជាទូទៅ វាគ្របដណ្តប់លើ៖

- ការរសាត់នៃ retrieval និងព្រំដែន context ដែលខូច
- indexes និង vector stores ដែលទទេ ឬហួសសម័យ
- ភាពមិនត្រូវគ្នារវាង embedding និងអត្ថន័យ
- បញ្ហាក្នុងការផ្គុំ prompt និង context window
- ការដួលរលំនៃតក្កវិជ្ជា និងចម្លើយដែលមានទំនុកចិត្តហួសហេតុ
- កំហុសក្នុង long chain និងការសម្របសម្រួល agent
- ការរសាត់នៃ memory និងតួនាទីរបស់ multi agent
- បញ្ហាលំដាប់ក្នុង deployment និង bootstrap

   - route ឬ provider combo ក្នុង OmniRoute

2. ផ្គូផ្គងឧប្បត្តិហេតុនេះទៅនឹងលេខ WFGY ProblemMap មួយ ឬពីរ (`No.1` … `No.16`)។

- Devin CLI មិនត្រូវបានដំឡើងលើ host

**ដំណោះស្រាយ៖**

### បាត់ OMNIROUTE_WS_BRIDGE_SECRET ក្នុង production

**រោគសញ្ញា៖**

- មាន 401 លើរាល់សំណើ Codex/Responses WebSocket bridge នៅពេលដំណើរការលើ remote production host

**មូលហេតុ៖** env var `OMNIROUTE_WS_BRIDGE_SECRET` បាត់ពី production environment។

**ដំណោះស្រាយ៖**

1. បង្កើត secret ចៃដន្យមួយ៖ `openssl rand -hex 32`
2. កំណត់ `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ក្នុង env របស់ production server (និង client ណាមួយដែលទាក់ទងជាមួយ bridge)
3. ចាប់ផ្តើម OmniRoute ឡើងវិញ

### Responses API៖ background mode ត្រូវបានបន្ថយទៅជា synchronous

**រោគសញ្ញា៖**

- សំណើ `background: true` ត្រឡប់ synchronous response ធម្មតា ជំនួសឱ្យ background job handle

**មូលហេតុ៖** v3.8.0 បន្ថយ `background: true` នៅលើ Responses API ទៅជាការប្រតិបត្តិបែប synchronous ដោយចេតនា ខណៈពេលបញ្ចេញការព្រមាន។ ការប្រតិបត្តិ async background ពេញលេញគឺជាមុខងារដែលនឹងផ្តល់ជូននាពេលអនាគត។

**ដំណោះស្រាយ៖**

- កែសម្រួល client ឱ្យហៅដោយគ្មាន `background` ឬ
- រង់ចាំការចេញផ្សាយនៅពេលក្រោយដែលមាន async background mode ពេញលេញ (តាមដាន changelog)

```bash
# តាមរយៈទង់ CLI (ប្រើតែម្តង)៖
omniroute serve --ready-timeout 180000
```

តម្លៃលំនាំដើមគឺ 60 000 ms (60 s)។ ការព្រមាននេះគ្រាន់តែជាព័ត៌មានប៉ុណ្ណោះ ម៉ាស៊ីនមេ
នឹងបន្តចាប់ផ្ដើមនៅផ្ទៃខាងក្រោយ ហើយអាចចូលប្រើបាននៅពេលការចាប់ផ្ដើមបានបញ្ចប់។

សូមមើល [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) សម្រាប់ព័ត៌មានលម្អិតពេញលេញ
អំពី `OMNIROUTE_READY_TIMEOUT_MS`។
