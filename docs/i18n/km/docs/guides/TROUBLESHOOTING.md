## ឯកសារយោងរហ័ស

**ទើបតែចាប់ផ្តើមប្រើ OmniRoute មែនទេ?** ចាប់ផ្តើមពីទីនេះ — ដំណោះស្រាយទាំងនេះអាចដោះស្រាយបញ្ហាបាន 90%៖

| ខ្ញុំឃើញសារនេះ            | អត្ថន័យរបស់វា                                    | អ្វីដែលត្រូវធ្វើ                                                                                                |
| ------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| "មិនអាចតភ្ជាប់បាន"        | OmniRoute មិនកំពុងដំណើរការ                       | ដំណើរការ `omniroute` ឬ `docker restart omniroute`                                                               |
| "API key មិនត្រឹមត្រូវ"   | key របស់អ្នកមិនត្រឹមត្រូវ ឬផុតកំណត់              | ចម្លង key ម្តងទៀតពីគេហទំព័ររបស់អ្នកផ្តល់សេវា                                                                    |
| "លើសដែនកំណត់អត្រា"        | អ្នកកំពុងផ្ញើសំណើច្រើនពេក                        | រង់ចាំ 1 នាទី ឬប្រើ `model: "auto"` សម្រាប់ការប្តូរជំនួសដោយស្វ័យប្រវត្តិ                                        |
| "លើសកូតា"                 | អ្នកបានប្រើកូតាឥតគិតថ្លៃ/បង់ប្រាក់របស់អ្នកអស់ហើយ | ភ្ជាប់អ្នកផ្តល់សេវាបន្ថែម ឬប្រើអ្នកផ្តល់សេវាឥតគិតថ្លៃ (Kiro, Pollinations)                                      |
| "ការឆ្លើយតបយឺត"           | អ្នកផ្តល់សេវាកំពុងរវល់ ឬនៅឆ្ងាយ                  | ប្រើ `model: "auto/fast"` ឬភ្ជាប់អ្នកផ្តល់សេវាដែលលឿនជាងនេះ (Groq, Cerebras)                                     |
| "បានប្រើអ្នកផ្តល់សេវាខុស" | `auto` បានជ្រើសរើសអ្នកផ្តល់សេវាផ្សេង             | វាជារឿងធម្មតា! `auto` ជ្រើសរើសជម្រើសល្អបំផុត។ បង្ខំឱ្យប្រើអ្នកផ្តល់សេវាជាក់លាក់ដោយប្រើ `model: "openai/gpt-4o"` |
| "502 Bad Gateway"         | អ្នកផ្តល់សេវាមិនដំណើរការ                         | រង់ចាំ ហើយព្យាយាមម្តងទៀត ឬប្រើ `model: "auto"` ដើម្បីប្តូរអ្នកផ្តល់សេវា                                         |
| "401 Unauthorized"        | ព័ត៌មានសម្គាល់អត្តសញ្ញាណរបស់អ្នកមិនត្រឹមត្រូវ    | ពិនិត្យ API key របស់អ្នក ឬផ្ទៀងផ្ទាត់អត្តសញ្ញាណម្តងទៀតតាម OAuth                                                 |
| "មិនស្គាល់ omniroute"     | Windows PATH ខ្វះម៉ូឌុល node សកល                 | បន្ថែម npm global prefix របស់អ្នកទៅក្នុង Windows PATH។ ស្វែងរកវាដោយប្រើ `npm config get prefix`។                |
| "429 Too Many Requests"   | ត្រូវបានកំណត់អត្រា                               | រង់ចាំ 1 នាទី ឬភ្ជាប់អ្នកផ្តល់សេវាបន្ថែម                                                                        |

### ការកំណត់អត្រាលើអ្នកផ្តល់សេវាឥតគិតថ្លៃ (429 / 400 / 401)

**រោគសញ្ញា**៖ នៅពេលប្រើ `model: "auto"` ជាមួយអ្នកផ្តល់សេវាឥតគិតថ្លៃ/មិនតម្រូវឱ្យផ្ទៀងផ្ទាត់អត្តសញ្ញាណ (opencode, auggie ជាដើម) អ្នកអាចទទួលបាន `HTTP 429`, `400` ឬ `401` ជាបណ្តោះអាសន្ន ជំនួសឱ្យចម្លើយ។ សំណើអាចជោគជ័យនៅពេលព្យាយាម prompt ដដែលម្តងទៀតបន្តិចក្រោយមក ប៉ុន្តែស្វ័យប្រវត្តិកម្ម (cron jobs, agents, scripts) នឹងបរាជ័យនៅពេលជួបបញ្ហាលើកដំបូង។

**មូលហេតុដើម**៖ របៀបបរាជ័យឯករាជ្យចំនួនបីកើតឡើងត្រួតគ្នា៖

1. **ដែនកំណត់អត្រារបស់អ្នកផ្តល់សេវា (`429`)**៖ កម្រិតប្រើប្រាស់ឥតគិតថ្លៃអាចអនុវត្តកូតាសម្រាប់ចន្លោះពេលនីមួយៗ។ ការផ្ញើសំណើច្រើនព្រមគ្នានឹងប្រើកូតាអស់ ដូច្នេះសំណើបន្ទាប់ត្រូវបានបដិសេធរហូតដល់ចន្លោះពេលត្រូវបានកំណត់ឡើងវិញ។
2. **ម៉ូដែលខូចក្នុងការបញ្ជូនផ្ទាល់ (`400`/`401`)**៖ pool `auto/*` អាចរួមបញ្ចូលម៉ូដែលបញ្ជូនផ្ទាល់ពី `opencode` ដែលបានចុះឈ្មោះក្នុងកាតាឡុក ប៉ុន្តែមិនមានព័ត៌មានសម្គាល់អត្តសញ្ញាណដែលកំពុងដំណើរការ (ឧ. `oc/north-mini-code-free` → `401`)។ auto-router សាកល្បងម៉ូដែលមួយ បរាជ័យ ហើយកំហុសត្រូវបានបញ្ជូនបន្ត មុនពេលការប្តូរជំនួសចាប់ផ្តើម។
3. **ការកើនឡើងដោយសារសំណើស្របពេល (`429` ក្រោមបន្ទុក)**៖ នៅពេល session របស់ agent/cron ច្រើនចូលប្រើ `auto` ក្នុងពេលតែមួយ អត្រាសំណើសរុបនឹងលើសកម្រិតដែលអ្នកផ្តល់សេវាឥតគិតថ្លៃអាចទ្រាំទ្របាន ដូច្នេះការហៅស្របច្បាប់ត្រូវបានសម្គាល់ថាជាការបំពាន។

**ដំណោះស្រាយដែលបានផ្ទៀងផ្ទាត់ (រាយការណ៍ដោយសហគមន៍, 2026-08-10)**៖ កែតម្រូវ environment variable ចំនួនបី ដើម្បីឱ្យការបង្វិល សំណើស្របពេល និងការប្តូរជំនួស អាចទប់ទល់នឹងការប្រែប្រួលនៃកម្រិតប្រើប្រាស់ឥតគិតថ្លៃ ជំនួសឱ្យបរាជ័យដោយសារវា៖

```bash
export OMNIROUTE_ROTATE_ON_400=true           # ប្តូរទៅម៉ូដែល/អ្នកផ្តល់សេវាផ្សេងនៅពេលមាន 400/401 (រំលងម៉ូដែលបញ្ជូនផ្ទាល់ដែលខូច)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # កម្រិតអតិបរមាច្បាស់លាស់សម្រាប់ការទទួលយកសំណើដែលប្រើធនធានច្រើន (តាមលំនាំដើមមិនបានកំណត់៖ មិនមានដែនកំណត់ចំនួនសំណើទេ សូមមើលកំណត់សម្គាល់ខាងក្រោម)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # រង់ចាំក្នុងដែនកំណត់យូរជាងមុន ដើម្បីឱ្យមានសមត្ថភាពសម្រាប់សំណើដែលប្រើធនធានច្រើន ជំនួសឱ្យ 503 ដែលអាចសាកល្បងឡើងវិញភ្លាមៗ
```

កំណត់តម្លៃទាំងនេះក្នុង environment របស់ process OmniRoute (daemon ឧ. តាមរយៈ LaunchAgent plist ឬ `systemctl edit`) បន្ទាប់មកចាប់ផ្តើម OmniRoute ឡើងវិញ។ rotation flag គឺជាយន្តការដែលមានឥទ្ធិពលខ្ពស់បំផុត៖ វាបម្លែងការបរាជ័យទាំងស្រុងទៅជាការសាកល្បងម្តងទៀតដោយស្វ័យប្រវត្តិជាមួយអ្នកផ្តល់សេវាដែលដំណើរការល្អនៅក្នុង pool។

**កំណត់សម្គាល់**៖ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` កំណត់ចំនួនសំណើដែលប្រើធនធានច្រើន — មាន context វែង — ដែលអាចដំណើរការក្នុងពេលតែមួយ។ ដែនកំណត់នេះជាច្រកត្រួតពិនិត្យការទទួលយក មិនមែនជាឧបករណ៍កំណត់អត្រារបស់អ្នកផ្តល់សេវាទេ។ **បច្ចុប្បន្នភាព #503-fanout៖** var នេះលែងត្រូវបានកំណត់តាមលំនាំដើមទៀតហើយ (ឥឡូវនេះវាអនុវត្តតែនៅពេលត្រូវបានកំណត់យ៉ាងច្បាស់ ដូចខាងលើ) — ផ្ទុយទៅវិញ ការទទួលយកសំណើដែលប្រើធនធានច្រើនត្រូវបានគ្រប់គ្រងដោយថវិកា byte ដែលបានគណនាដោយស្វ័យប្រវត្តិ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ហើយវាកែសម្រួលទំហំរបស់ខ្លួនដោយផ្អែកលើកម្រិតអង្គចងចាំពិតប្រាកដរបស់ host។ ដូច្នេះ deployment ថ្មីគួរតែជួបការបដិសេធ `503 chat_admission_busy` តិចជាងមុនយ៉ាងច្រើន ដោយមិនចាំបាច់កំណត់ var នេះទាល់តែសោះ។ ការកំណត់វាយ៉ាងច្បាស់នៅទីនេះនៅតែដំណើរការត្រឹមត្រូវដូចដែលបានចងក្រងជាឯកសារ។ ការកំណត់ជំនួសថវិកា byte យ៉ាងច្បាស់ត្រូវបានកម្រិតនៅចន្លោះ 8 MiB–2 GiB។ `413 body_exceeds_budget` មិនមែនជាបញ្ហាបណ្តោះអាសន្នទេ៖ បង្កើនថវិកា byte នោះ បន្ថយ `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ឬបង្កើនកម្រិតអង្គចងចាំរបស់ process។ ការកាត់បន្ថយ `inflight_bytes_budget` គឺជាការប្រជែងធនធានបណ្តោះអាសន្ន ហើយនៅតែអាចសាកល្បងឡើងវិញបាន។ ការកំណត់អត្រាសម្រាប់អ្នកផ្តល់សេវានីមួយៗ (`open-sse/services/rateLimitManager.ts`) ត្រូវបានគ្រប់គ្រងដាច់ដោយឡែកដោយ `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` និង `RATE_LIMIT_AUTO_ENABLE` — សូមមើល `.env.example`។

**របៀបផ្ទៀងផ្ទាត់ថាវាដំណើរការ**៖ ដំណើរការ agent/cron របស់អ្នកពីរដងជាប់ៗគ្នាក្នុងរយៈពេលខ្លី ហើយបញ្ជាក់ថាទាំងពីរដំណើរការដោយជោគជ័យ។ មុនពេលកែបញ្ហា ការដំណើរការលើកទីពីរជាធម្មតានឹងបញ្ចេញកំហុស `429`/`401`។ បន្ទាប់ពីកែបញ្ហា ការបរាជ័យ (ប្រសិនបើមាន) នឹងត្រូវបានព្យាយាមឡើងវិញដោយស្វ័យប្រវត្តិដោយមិនរំខាន ហើយការហៅនឹងបញ្ចប់ដោយជោគជ័យ។ អ្នកក៏អាចប្រើ `curl /monitoring/health` ហើយតាមដាន field `rateLimitedUntil` នៅលើការតភ្ជាប់របស់ provider និង `circuitBreakers.providerBreakers[].state` សម្រាប់ provider ដែលរងផលប៉ះពាល់ផងដែរ — state នឹងជាតម្លៃមួយក្នុងចំណោម `CLOSED`, `DEGRADED`, `OPEN` ឬ `HALF_OPEN` (សូមមើល `src/shared/utils/circuitBreaker.ts`) ហើយ provider ដែលបន្តបរាជ័យនឹងប្ដូរស្ថានភាពពី `CLOSED → DEGRADED → OPEN` មុនពេលចន្លោះពេលកំណត់ឡើងវិញអនុញ្ញាតឱ្យការសាកល្បងមួយឆ្លងកាត់ (`HALF_OPEN`)។

**ប្រសិនបើអ្នកនៅតែឃើញ 429**៖ គណនីសកម្មសម្រាប់ provider នោះពិតជាបានប្រើអស់ _កូតា_ របស់វា (មិនមែនត្រឹមតែដល់កម្រិតអត្រាប៉ុណ្ណោះទេ)។ បន្ថែមគណនីទីពីរសម្រាប់ provider ដដែលនៅក្នុងផ្ទាំងគ្រប់គ្រង OmniRoute → Providers → Accounts ឬបញ្ចូល provider ឥតគិតថ្លៃមួយផ្សេងទៀត (ឧ. `routeway`, `auggie`)។ ការប្ដូរវេនជួយបានតែចំពោះបញ្ហាបណ្ដោះអាសន្ននៃអត្រា/400/401 ប៉ុណ្ណោះ។ ការប្រើអស់កូតាទាំងស្រុងតម្រូវឱ្យមានព័ត៌មានសម្ងាត់ទីពីរ ឬ provider ផ្សេង។

**ប្រសិនបើអ្នកឃើញ 403 លើម៉ូដែល vision (`auto/vision`, `bazaarlink/*`)**៖ គណនីដែលបានតភ្ជាប់មិនមានគម្រោងបង់ប្រាក់ដែលរួមបញ្ចូល vision ឬ API key មានសិទ្ធិមិនគ្រប់គ្រាន់។ ផ្ទៀងផ្ទាត់នៅក្នុងផ្ទាំងគ្រប់គ្រងរបស់ provider ថា scope របស់ key រួមបញ្ចូល vision/multimodal ឬតភ្ជាប់គណនីកម្រិតបង់ប្រាក់ ហើយរក្សាវាទុកជាគោលដៅ vision។

## ការព្រមានពេល npm install (ERESOLVE / peer / deprecated)

នៅពេលអ្នកដំណើរការ `npm install -g omniroute` អ្នកអាចឃើញការព្រមានជាច្រើនដូចជា `npm warn ERESOLVE` សេចក្តីជូនដំណឹងអំពី peer dependency និងសារ `deprecated`។ **ទាំងនេះជាអ្វីដែលបានរំពឹងទុក និងមិនបង្កគ្រោះថ្នាក់ទេ។** ការដំឡើងរបស់អ្នកបានជោគជ័យ ប្រសិនបើអ្នកឃើញ `added <N> packages` នៅក្នុងលទ្ធផល។

ដើម្បីលាក់ការព្រមានអំពីការដោះស្រាយ peer dependency សូមប្រើទម្រង់ដំឡើងដែល OmniRoute គាំទ្រ៖

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` លាក់តែ `ERESOLVE` និងសេចក្តីជូនដំណឹងអំពី peer dependency ប៉ុណ្ណោះ។ សេចក្តីជូនដំណឹងអំពីការឈប់គាំទ្រនៅតែបង្ហាញ ព្រោះវាមកពីកញ្ចប់ភាគីទីបីដែលជាភាពអាស្រ័យបន្តបន្ទាប់។ វាមិនមានន័យថាការដំឡើងបានបរាជ័យនោះទេ។

ការព្រមានទាំងនេះបណ្តាលមកពីជួរ peer dependency ដែលហួសសម័យនៅក្នុងកញ្ចប់ភាគីទីបី ដែល OmniRoute មិនអាចគ្រប់គ្រងបាន៖

1. **`marked-terminal` ត្រូវការ `marked >=1 <16` ប៉ុន្តែបានរកឃើញ `marked@18`** — ជាក់ស្តែង វាដំណើរការបានល្អ។ ជួរ peer dependency របស់គម្រោងដើមគ្រាន់តែហួសសម័យប៉ុណ្ណោះ។
2. **`deprecated prebuild-install@7.1.3`** — ជាកម្មវិធីជំនួយសម្រាប់ទាញយក binary ដើម ដែលជាភាពអាស្រ័យបន្តបន្ទាប់។ វាមិនត្រូវបាន
   ប្រើដើម្បីដំឡើង transport binding `wreq-js` ដែលបានកំណត់កំណែជាក់លាក់ទេ ហើយវាក៏មិនបង្ហាញថាការរៀបចំ transport របស់អ្នកផ្តល់សេវា web-cookie
   បានបរាជ័យនោះដែរ។

**មិនចាំបាច់ធ្វើអ្វីទេ** — មិនអាចលាក់ការព្រមានទាំងនេះទាំងស្រុងបានទេ លុះត្រាតែធ្វើ fork កញ្ចប់ពីគម្រោងដើម។

## Gemini Web និង Playwright Chromium

ប្រសិនបើសំណើ Gemini Web ត្រឡប់ `503` ជាមួយសារថា Playwright Chromium
មិនត្រូវបានដំឡើង នោះមានន័យថាកញ្ចប់ npm មានរួចហើយ ប៉ុន្តែខ្វះ browser binary។
Playwright មានចេតនារក្សាការទាញយក browser ឱ្យដាច់ដោយឡែកពីការដំឡើងកញ្ចប់ npm
ដូច្នេះការឆ្លើយតបនេះជាអ្វីដែលបានរំពឹងទុក រហូតដល់ browser ត្រូវបានដំឡើង។

សម្រាប់ការដំឡើង npm ជាសកល សូមដំឡើង Chromium ពីថតរបស់កញ្ចប់ OmniRoute
ដើម្បីឱ្យ browser cache ជាកម្មសិទ្ធិរបស់ការដំឡើង Playwright ដូចគ្នា៖

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ចាប់ផ្តើម OmniRoute ឡើងវិញបន្ទាប់ពីដំឡើង រួចសាកល្បងសំណើ Gemini Web ម្តងទៀត។ ប្រសិនបើអ្នក
ដំណើរការ OmniRoute ពី Docker image សូមប្រើ image `-web` (ឬ build target `runner-web`)
ដែលមាន Chromium និងភាពអាស្រ័យរបស់វាភ្ជាប់មកជាមួយ។ base image
មិនមានពួកវាទេ។

### Avast/AVG ដាក់ `README.md` ឱ្យនៅដាច់ដោយឡែក ដោយសារ `MD:HttpRequest-inf[Susp]`

Avast និង AVG ដំណើរការវិធីសាស្ត្រសន្និដ្ឋានដែលដាក់ទង់សម្គាល់ឯកសារអត្ថបទធម្មតា/Markdown ដែលមានតំណភ្ជាប់ជាច្រើនមើលទៅដូចជាសំណើ HTTP។ `README.md` របស់ OmniRoute ត្រូវបានដាក់បញ្ចូលក្នុងកញ្ចប់ npm (វាត្រូវបានរាយក្នុង `package.json` → `files`) ដូច្នេះ នៅពេលដំឡើងជាសកល វានឹងស្ថិតនៅ `node_modules/omniroute/README.md` — ហើយវាមានឧទាហរណ៍ `http://localhost:20128/...` ប្រហែល 15 (ចំណុចបញ្ចប់ HTTP/SSE របស់ MCP, URL `.well-known` របស់ A2A និងអត្ថបទខ្លីៗប្រើ `curl`)។ ដង់ស៊ីតេតំណភ្ជាប់នេះគ្រប់គ្រាន់ឱ្យវិធីសាស្ត្រសន្និដ្ឋាននោះបញ្ចេញការព្រមាន។

**ហេតុអ្វីបានជាយើងមិន «កែ» បញ្ហានេះពីខាងយើង៖** ឧទាហរណ៍ទាំងអស់គឺ `http://localhost` ហើយ localhost មិនអាចប្រើ `https` បានទេដោយមិនជួបភាពស្មុគស្មាញនៃវិញ្ញាបនបត្រដែលចុះហត្ថលេខាដោយខ្លួនឯង។ ការកែប្រែឯកសារណែនាំឱ្យខុសពីធម្មតា ដើម្បីគេចពីវិធីសាស្ត្រសន្និដ្ឋានរបស់ក្រុមហ៊ុនផ្គត់ផ្គង់តែមួយ នឹងធ្វើឱ្យអ្នកអានគ្រប់រូបរងផលប៉ះពាល់ ដើម្បីបំពេញចិត្តកំហុសរបស់កម្មវិធីស្កេនប៉ុណ្ណោះ។

**នេះជាលទ្ធផលវិជ្ជមានក្លែងក្លាយពីវិធីសាស្ត្រសន្និដ្ឋានតាមឥរិយាបថ។ គ្មានអ្វីត្រូវបានឆ្លងមេរោគទេ។** បុព្វបទ `PDM:` របស់ Kaspersky មានន័យថា ការវិនិច្ឆ័យនេះមកពី Proactive Defense Module (System Watcher) របស់វា ដែលវាយតម្លៃសកម្មភាពដែលកម្មវិធីដំឡើង _ធ្វើ_ ជាជាងផ្គូផ្គងវាជាមួយមេរោគដែលស្គាល់រួច។ នៅពេលវាបញ្ចេញការព្រមាន Kaspersky នឹង «ត្រឡប់ថយក្រោយ» ការដំឡើងទាំងមូល — ដោយលុបឯកសារដែលវាបានសរសេររួច — ដូច្នេះកម្មវិធីនឹងខូច ឬបាត់។

ឯកសារដែលវាដាក់ទង់សម្គាល់ គឺជាផ្នែកស្តង់ដារនៃ dependency ប្រភពបើកចំហដែលបានប្រកាស និងដាក់បញ្ចូលជាមួយកម្មវិធី desktop ឧទាហរណ៍៖

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` និង
  `workerProcessEntry.js` — [Playwright](https://playwright.dev) ជាបណ្ណាល័យស្វ័យប្រវត្តិកម្មកម្មវិធីរុករក ដែលប្រើសម្រាប់ការចូលទៅកាន់អ្នកផ្ដល់សេវាក្នុងកម្មវិធី និងការជជែកដែលដំណើរការតាមកម្មវិធីរុករក។
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — native binding `wreq-js` ដែលបានចាក់សោជំនាន់ សម្រាប់ HTTP ដែលមានស្នាមសម្គាល់កម្មវិធីរុករកលើអ្នកផ្ដល់សេវាដែលប្រើ web-cookie
  (`<arch>` គឺ `x64` ឬ `arm64`)។

**ហេតុអ្វីបានជាវាបញ្ចេញការព្រមាន៖** កម្មវិធីដំឡើងសម្រាប់ Windows **មិនទាន់ត្រូវបានចុះហត្ថលេខាលើកូដទេ** ដូច្នេះកម្មវិធីដំឡើង NSIS ដែលគ្មានហត្ថលេខា មិនមានកេរ្តិ៍ឈ្មោះទុកចិត្ត ហើយវិធីសាស្ត្រសន្និដ្ឋានតាមឥរិយាបថនឹងដំណើរការក្នុងកម្រិតតឹងរ៉ឹងបំផុត។ នៅពេលរួមបញ្ចូលជាមួយ DLL ដើមដែលបានខ្ចប់មកជាមួយ និងឯកសារ `.js` រាប់រយដែលត្រូវបានសរសេរក្រោម
`%LOCALAPPDATA%\Programs\OmniRoute` (រួមទាំងថតកញ្ចប់ដែលមាន hash ជាបច្ច័យពី standalone build របស់ Next.js) វាគ្រប់គ្រាន់ឱ្យវិធីសាស្ត្រសន្និដ្ឋាននេះបញ្ចេញការព្រមាន។ ការចុះហត្ថលេខាលើកូដត្រូវបានគ្រោងទុករួចហើយ។ រហូតដល់វាត្រូវបានអនុវត្ត កំណែចេញផ្សាយថ្មីៗអាចជួបបញ្ហានេះម្ដងទៀត។

**អ្វីដែលត្រូវធ្វើ៖**

1. **ផ្ទៀងផ្ទាត់ឯកសារទាញយករបស់អ្នកជាមុនសិន** (ដើម្បីបញ្ជាក់ថាឯកសារមិនត្រូវបានកែប្រែដោយគ្មានការអនុញ្ញាត)។ រាល់ការចេញផ្សាយសុទ្ធតែបោះពុម្ព `latest.yml` ដែលវាល `sha512` (base64) របស់វាគ្របដណ្ដប់លើកម្មវិធីដំឡើង `OmniRoute.Setup.<version>.exe`។ ក្នុង PowerShell ពីថតដែលមានកម្មវិធីដំឡើង៖
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   លទ្ធផលត្រូវតែផ្គូផ្គងនឹង `latest.yml` → `sha512`។ ប្រសិនបើមិនផ្គូផ្គងទេ សូមលុបឯកសារ ហើយទាញយកម្ដងទៀតតែពី [ទំព័រការចេញផ្សាយ GitHub](https://github.com/diegosouzapw/OmniRoute/releases) ប៉ុណ្ណោះ។
2. **ស្ដារ + ដាក់ក្នុងបញ្ជីលើកលែង** — ស្ដារធាតុដែលត្រូវបានត្រឡប់ថយក្រោយពីកន្លែងដាក់ឱ្យនៅដាច់ដោយឡែក ហើយបន្ថែមការលើកលែងសម្រាប់ `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions) បន្ទាប់មកដំឡើងឡើងវិញ។
3. **រាយការណ៍លទ្ធផលវិជ្ជមានក្លែងក្លាយ** — <https://opentip.kaspersky.com/>។ របាយការណ៍លទ្ធផលវិជ្ជមានក្លែងក្លាយដែលអ្នកប្រើប្រាស់ដាក់ស្នើ ពិតជាជួយពន្លឿនការបញ្ចូលទៅក្នុងបញ្ជីអនុញ្ញាត។

## ភាពឆបគ្នាជាមួយ Node.js

<a name="nodejs-compatibility"></a>

### ទំព័រចូលប្រើគាំង ឬបង្ហាញកំហុស "Module self-registration"

**មូលហេតុ:** អ្នកកំពុងដំណើរការកំណែ Node.js ដែលស្ថិតនៅក្រៅកម្រិតអប្បបរមានៃ runtime សុវត្ថិភាពដែល OmniRoute បានអនុម័ត។ ករណីទូទៅបំផុតគឺការដំណើរការកម្រិត patch ចាស់ជាងរបស់ Node 22 ឬ 24 ដែលទាបជាងកម្រិត patch សុវត្ថិភាពអប្បបរមាដែល OmniRoute តម្រូវ។

**រោគសញ្ញា:**

- ទំព័រចូលប្រើបង្ហាញអេក្រង់ទទេ ឬកំហុសម៉ាស៊ីនមេ
- Console បង្ហាញ `Error: Module did not self-register` ឬកំហុស native binding ស្រដៀងគ្នា
- ទំព័រចូលប្រើបង្ហាញ **បដាព្រមានពណ៌ទឹកក្រូច** ជាមួយកំណែ Node របស់អ្នក ប្រសិនបើ runtime ស្ថិតនៅក្រៅគោលការណ៍សុវត្ថិភាពដែលគាំទ្រ

**ដំណោះស្រាយ:**

1. ដំឡើងកំណែ Node.js LTS ដែលគាំទ្រ (បានណែនាំ៖ Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ផ្ទៀងផ្ទាត់កំណែរបស់អ្នក៖ `node --version` គួរតែបង្ហាញ `v24.0.0` ឬថ្មីជាងនេះក្នុងខ្សែ LTS 24.x
3. ដំឡើង OmniRoute ឡើងវិញ៖ `npm install -g omniroute`
4. ចាប់ផ្ដើមឡើងវិញ៖ `omniroute`

> **កំណែសុវត្ថិភាពដែលគាំទ្រ:** `>=22.22.2 <23` ឬ `>=24.0.0 <27`។ Node.js 24.x LTS (Krypton) និង Node.js 26 ត្រូវបានគាំទ្រយ៉ាងពេញលេញ។

### npm v11+: `better-sqlite3` មិនត្រូវបានដំឡើង (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**មូលហេតុ:** តាមលំនាំដើម npm v11 (ដែលភ្ជាប់មកជាមួយ Node.js 24+) រារាំងស្គ្រីបដំឡើងសម្រាប់ dependency ដែលជាជម្រើស។
ដោយសារ `better-sqlite3` ត្រូវបានរាយក្នុង `optionalDependencies`
ហើយតម្រូវឱ្យ compile ជា native (`node-gyp rebuild`) npm នឹងរំលងវាដោយស្ងាត់ស្ងៀម។

**រោគសញ្ញា:**

- ម៉ាស៊ីនមេគាំងនៅពេលចាប់ផ្ដើម ដោយមាន `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` បង្ហាញ "No such file or directory"
- `npm ls better-sqlite3` បង្ហាញ `(empty)`

**ដំណោះស្រាយ:**

1. អនុម័តស្គ្រីបដំឡើង ហើយដំឡើងឡើងវិញ៖
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ឬដំឡើងកញ្ចប់ដែលបាន build ជាមុនដោយដៃ៖
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ផ្ទៀងផ្ទាត់ថាវាដំណើរការ៖ `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**មូលហេតុ:** បន្ទាប់ពីការដំឡើង global ដោយ `npm install -g omniroute` ឯកសារ binary native របស់ `better-sqlite3` នៅក្នុងកញ្ចប់អាចត្រូវបាន compile សម្រាប់ architecture ឬ Node.js ABI ផ្សេងពីអ្វីដែលកំពុងដំណើរការនៅលើម៉ាស៊ីនមូលដ្ឋាន។ បញ្ហានេះកើតឡើងជាទូទៅនៅលើ macOS (ទាំង Apple Silicon និង Intel) នៅពេលឯកសារ binary ដែលបាន build ជាមុនមិនត្រូវគ្នានឹង environment របស់អ្នក។

**រោគសញ្ញា:**

- ម៉ាស៊ីនមេបរាជ័យភ្លាមៗនៅពេលចាប់ផ្ដើម ដោយមានកំហុស `dlopen`
- កំហុសមាន `slice is not valid mach-o file`
- ឧទាហរណ៍ពេញលេញ៖

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ដំណោះស្រាយ — build ឡើងវិញសម្រាប់ environment មូលដ្ឋានរបស់អ្នក (មិនតម្រូវឱ្យបន្ទាបកំណែ Node.js ទេ):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
```

## បញ្ហា Proxy

### ការផ្ទៀងផ្ទាត់ Provider បង្ហាញ "fetch failed"

**មូលហេតុ៖** ពីមុន endpoint សម្រាប់ផ្ទៀងផ្ទាត់ API key (`POST /api/providers/validate`) បានរំលងការកំណត់រចនាសម្ព័ន្ធ proxy ដែលបណ្ដាលឱ្យបរាជ័យនៅក្នុងបរិស្ថានដែលតម្រូវឱ្យបញ្ជូនតាម proxy។

**ដំណោះស្រាយ (v3.5.5+)៖** បញ្ហានេះត្រូវបានដោះស្រាយហើយ។ ការផ្ទៀងផ្ទាត់ Provider ឥឡូវនេះត្រូវបានបញ្ជូនតាម `runWithProxyContext` ដោយគោរពការកំណត់ proxy នៅកម្រិត Provider និងជាសកលដោយស្វ័យប្រវត្តិ។

### ការពិនិត្យស្ថានភាព Token បរាជ័យដោយមានសារ "fetch failed"

**មូលហេតុ៖** ដំណើរការ refresh OAuth token នៅផ្ទៃខាងក្រោយ មិនបានកំណត់រចនាសម្ព័ន្ធ proxy ដាច់ដោយឡែកសម្រាប់ connection នីមួយៗទេ។

**ដំណោះស្រាយ (v3.5.5+)៖** ឥឡូវនេះ scheduler សម្រាប់ពិនិត្យស្ថានភាព token នឹងកំណត់ proxy config សម្រាប់ connection នីមួយៗ មុនពេលព្យាយាម refresh។ សូមអាប់ដេតទៅ v3.5.5+។

### SOCKS5 proxy បង្ហាញ "invalid onRequestStart method"

**មូលហេតុ៖** នៅលើ Node.js 22 dispatcher របស់ undici@8 មិនឆបគ្នាជាមួយការអនុវត្ត `fetch()` ដែលភ្ជាប់មកជាមួយ Node ទេ។

**ដំណោះស្រាយ (v3.5.5+)៖** ឥឡូវនេះ OmniRoute ប្រើមុខងារ `fetch()` ផ្ទាល់របស់ undici នៅពេលដែល proxy dispatcher សកម្ម ដើម្បីធានាឱ្យមានឥរិយាបថស្របគ្នា។ សូមអាប់ដេតទៅ v3.5.5+។

### MITM proxy នៅក្រោម WSL៖ កម្មវិធី desktop នៅលើ Windows host មិនត្រូវបានស្ទាក់ចាប់

**មូលហេតុ៖** MITM proxy និង CA certificate របស់វាត្រូវបានដំឡើងនៅក្នុងបរិស្ថានដែល OmniRoute ដំណើរការ។ នៅក្រោម WSL បរិស្ថាននោះគឺជា Linux guest ខណៈដែលកម្មវិធី AI desktop (Kiro, Trae, Copilot, Zed, …) ដំណើរការនៅលើ Windows host។ កម្មវិធីលើ host មិនទុកចិត្ត certificate store របស់ guest ហើយក៏មិនបញ្ជូនទិន្នន័យតាម system proxy របស់ guest ដែរ ដូច្នេះការស្ទាក់ចាប់កម្មវិធី desktop មិនដំណើរការនៅទីនោះទេ។

**អនុសាសន៍៖** ដំណើរការ OmniRoute ដោយផ្ទាល់លើ OS ដូចគ្នានឹងកម្មវិធី desktop ដែលអ្នកចង់ស្ទាក់ចាប់ (Windows សម្រាប់កម្មវិធី Windows; macOS/Linux ក៏ដូចគ្នា)។ ការរក្សា OmniRoute នៅក្នុង WSL ខណៈពេលកំណត់គោលដៅទៅកម្មវិធីលើ host តម្រូវឱ្យទុកចិត្ត CA certificate ដែលបានបង្កើតនៅលើ Windows host ដោយដៃ និងកំណត់ network/proxy settings របស់កម្មវិធី host នីមួយៗឱ្យចង្អុលទៅ WSL proxy endpoint — នេះជាការកំណត់ដែលមិនត្រូវបានគាំទ្រ និងងាយមានបញ្ហា។

**ការកែសម្រួល:**

1. **ការវិនិច្ឆ័យរហ័ស:** ដំណើរការ `curl -4 http://localhost:20128/v1/models`។ ប្រសិនបើវាដំណើរការជាមួយ `-4` ប៉ុន្តែបរាជ័យដោយគ្មានវា នោះអ្នកមានបញ្ហាការចង IPv6 មិនស៊ីគ្នា។
2. **ការកែសម្រួលអចិន្ត្រៃយ៍:** ចងទៅ IPv4 ដោយជាក់លាក់ តាមរយៈការប្រើ `-p 127.0.0.1:20128:20128` ក្នុង command `docker run` របស់អ្នក៖

   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```

   វាបង្ខំឱ្យចង IPv4 ហើយក៏ជៀសវាងការបង្ហាញ proxy នៅលើ interface ទាំងអស់របស់ host ផងដែរ។

## ការបំបាត់កំហុស

### បើកប្រើឯកសារ Log

កំណត់ `APP_LOG_TO_FILE=true` នៅក្នុងឯកសារ `.env` របស់អ្នក។ Log របស់កម្មវិធីត្រូវបានសរសេរនៅក្រោម `logs/`។
Artifact របស់ request ត្រូវបានរក្សាទុកនៅក្រោម `${DATA_DIR}/call_logs/` នៅពេល call log pipeline
ត្រូវបានបើកក្នុង settings។
នៅពេល pipeline capture ត្រូវបានបើក កំណត់ `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` ដើម្បីមិនរាប់បញ្ចូល
payload របស់ stream chunk ឬកែតម្រូវ `CALL_LOG_PIPELINE_MAX_SIZE_KB` ដើម្បីផ្លាស់ប្ដូរទំហំអតិបរមារបស់ artifact គិតជា KB។

### ពិនិត្យស្ថានភាព Provider

```bash
# Dashboard សម្រាប់ពិនិត្យស្ថានភាព
http://localhost:20128/dashboard/health

# ការពិនិត្យស្ថានភាព API
curl http://localhost:20128/api/monitoring/health
```

### កន្លែងផ្ទុក Runtime

- ស្ថានភាពចម្បង៖ `${DATA_DIR}/storage.sqlite` (provider, combo, alias, key, settings)
- ការប្រើប្រាស់៖ តារាង SQLite ក្នុង `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + `${DATA_DIR}/call_logs/` ជាជម្រើស
- Log របស់កម្មវិធី៖ `<repo>/logs/...` (នៅពេល `APP_LOG_TO_FILE=true`)
- Artifact របស់ call log៖ `${DATA_DIR}/call_logs/YYYY-MM-DD/...` នៅពេល call log pipeline ត្រូវបានបើក

សកម្មភាព **Clean history** នៅលើទំព័រ Request Logs នឹងសម្អាត `call_logs`, `request_detail_logs`
ចាស់ៗ និង directory artifact មូលដ្ឋាន `${DATA_DIR}/call_logs/`។

## បញ្ហា Circuit Breaker

### អ្នកផ្តល់សេវាជាប់គាំងក្នុងស្ថានភាព OPEN

នៅពេល circuit breaker របស់អ្នកផ្តល់សេវាស្ថិតក្នុងស្ថានភាព OPEN សំណើនានានឹងត្រូវបានរារាំងរហូតដល់រយៈពេល cooldown ផុតកំណត់។

**វិធីដោះស្រាយ៖**

1. ចូលទៅកាន់ **Dashboard → Settings → Resilience**
2. ពិនិត្យមើលកាត circuit breaker របស់អ្នកផ្តល់សេវាដែលរងផលប៉ះពាល់
3. ចុច **Reset All** ដើម្បីសម្អាត breaker ទាំងអស់ ឬរង់ចាំរហូតដល់រយៈពេល cooldown ផុតកំណត់
4. ផ្ទៀងផ្ទាត់ថាអ្នកផ្តល់សេវាពិតជាអាចប្រើបាន មុនពេលកំណត់ឡើងវិញ

### អ្នកផ្តល់សេវាបន្តបង្កឱ្យ circuit breaker ដំណើរការ

ប្រសិនបើអ្នកផ្តល់សេវាចូលក្នុងស្ថានភាព OPEN ម្តងហើយម្តងទៀត៖

1. ពិនិត្យមើលលំនាំនៃការបរាជ័យនៅក្នុង **Dashboard → Health → Provider Health**
2. ចូលទៅកាន់ **Settings → Resilience → Provider Profiles** ហើយបង្កើនកម្រិតកំណត់នៃការបរាជ័យ
3. ពិនិត្យមើលថាតើអ្នកផ្តល់សេវាបានផ្លាស់ប្តូរដែនកំណត់ API ឬតម្រូវឱ្យផ្ទៀងផ្ទាត់អត្តសញ្ញាណឡើងវិញដែរឬទេ
4. ពិនិត្យមើល telemetry នៃ latency — latency ខ្ពស់អាចបង្កឱ្យមានការបរាជ័យដោយសារ timeout

### បញ្ហាទម្រង់ទូទៅ

- **Thinking tags មិនបង្ហាញ** — ពិនិត្យមើលថាតើអ្នកផ្តល់សេវាគោលដៅគាំទ្រការគិត និងការកំណត់ថវិកាសម្រាប់ការគិតដែរឬទេ
- **Tool calls ត្រូវបានបាត់បង់** — ការបកប្រែទម្រង់មួយចំនួនអាចដកវាលដែលមិនគាំទ្រចេញ។ សូមផ្ទៀងផ្ទាត់ក្នុងរបៀប Playground
- **System prompt បាត់** — Claude និង Gemini គ្រប់គ្រង system prompts ខុសគ្នា។ សូមពិនិត្យមើលលទ្ធផលនៃការបកប្រែ
- **SDK ផ្តល់ raw string ជំនួសឱ្យ object** — ត្រូវបានដោះស្រាយក្នុង v1.x; response sanitizer ដកវាលមិនស្តង់ដារ (`x_groq`, `usage_breakdown`, ជាដើម) ដែលបង្កឱ្យការផ្ទៀងផ្ទាត់ OpenAI SDK Pydantic បរាជ័យ។ ប្រសិនបើអ្នកនៅតែឃើញបញ្ហានេះនៅលើ v3.x+ សូមរាយការណ៍បញ្ហា។
- **GLM/ERNIE បដិសេធតួនាទី `system`** — ត្រូវបានដោះស្រាយក្នុង v1.x; role normalizer បញ្ចូលសារ system ទៅក្នុងសារ user ដោយស្វ័យប្រវត្តិសម្រាប់ម៉ូដែលដែលមិនឆបគ្នា។ ប្រសិនបើអ្នកនៅតែឃើញបញ្ហានេះនៅលើ v3.x+ សូមរាយការណ៍បញ្ហា។
- **តួនាទី `developer` មិនត្រូវបានស្គាល់** — ត្រូវបានដោះស្រាយក្នុង v1.x; ត្រូវបានបម្លែងទៅជា `system` ដោយស្វ័យប្រវត្តិសម្រាប់អ្នកផ្តល់សេវាដែលមិនមែនជា OpenAI។ ប្រសិនបើអ្នកនៅតែឃើញបញ្ហានេះនៅលើ v3.x+ សូមរាយការណ៍បញ្ហា។
- **`json_schema` មិនដំណើរការជាមួយ Gemini** — ត្រូវបានដោះស្រាយក្នុង v1.x; ឥឡូវនេះ `response_format` ត្រូវបានបម្លែងទៅជា `responseMimeType` + `responseSchema` របស់ Gemini។ ប្រសិនបើអ្នកនៅតែឃើញបញ្ហានេះនៅលើ v3.x+ សូមរាយការណ៍បញ្ហា។

## ការកំណត់ភាពធន់

### ការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិមិនដំណើរការ

- ការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិអនុវត្តតែចំពោះអ្នកផ្តល់សេវាដែលប្រើ API key ប៉ុណ្ណោះ (មិនអនុវត្តចំពោះ OAuth/ការជាវទេ)
- ផ្ទៀងផ្ទាត់ថា **Settings → Resilience → Provider Profiles** បានបើកការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិ
- ពិនិត្យមើលថាតើអ្នកផ្តល់សេវាបញ្ជូនត្រឡប់កូដស្ថានភាព `429` ឬបឋមកថា `Retry-After` ដែរឬទេ

### ការកែសម្រួល exponential backoff

ប្រវត្តិរូបអ្នកផ្តល់សេវាគាំទ្រការកំណត់ទាំងនេះ៖

- **រយៈពេលពន្យារមូលដ្ឋាន** — រយៈពេលរង់ចាំដំបូងបន្ទាប់ពីបរាជ័យលើកទីមួយ (លំនាំដើម៖ 1s)
- **រយៈពេលពន្យារអតិបរមា** — ដែនកំណត់រយៈពេលរង់ចាំអតិបរមា (លំនាំដើម៖ 30s)
- **មេគុណ** — កម្រិតបង្កើនរយៈពេលពន្យារសម្រាប់ការបរាជ័យជាប់ៗគ្នានីមួយៗ (លំនាំដើម៖ 2x)

### ការទប់ស្កាត់ thundering herd

នៅពេលសំណើដំណាលគ្នាជាច្រើនបញ្ជូនទៅអ្នកផ្តល់សេវាដែលបានកំណត់កម្រិតអត្រា OmniRoute ប្រើ mutex + ការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិ ដើម្បីតម្រៀបសំណើឱ្យដំណើរការម្តងមួយៗ និងទប់ស្កាត់ការបរាជ័យបន្តបន្ទាប់។ វាដំណើរការដោយស្វ័យប្រវត្តិសម្រាប់អ្នកផ្តល់សេវាដែលប្រើ API key។

- endpoint សម្រាប់ chat completions បញ្ជូនការឆ្លើយតប `503` ដែលអាចព្យាយាមម្តងទៀតបាន ហើយមានកូដកំហុស
  `chat_admission_busy`។
- ការឆ្លើយតបរួមបញ្ចូល `Retry-After`។ ចាប់តាំងពី #12135 តម្លៃនេះត្រូវបានគណនាចេញពី
  កម្រិតប្រើប្រាស់ដែលបានសង្កេត — ដោយយកតម្លៃធំជាងរវាងរយៈពេល `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ដែលសំណើបាន
  រង់ចាំរួចហើយ និងរយៈពេលដែល heavyweight leases បច្ចុប្បន្នត្រូវបានកាន់កាប់ — ដោយបង្គត់ឡើងទៅជា
  វិនាទីពេញ និងកំណត់អតិបរមាត្រឹម 60។ នៅពេល gate ទំនេរ វារក្សាកម្រិតអប្បបរមាដើម៖ 2 វិនាទីនៅលើ
  ផ្លូវដែលផ្អែកលើ byte និង 1 វិនាទីនៅលើផ្លូវដែលផ្អែកលើរចនាសម្ព័ន្ធ (ដែលរួមបញ្ចូលផងដែរ
  `reason: "structure_limit"`)។
- បញ្ហានេះអាចកើតឡើង ខណៈដែលការជជែកប្រភេទ heavyweight មួយផ្សេងទៀត ឬការឆ្លើយតប streaming ដែលដំណើរការយូរ នៅតែ
  កំពុងដំណើរការ។

តួការឆ្លើយតបដែលផ្អែកលើ byte គឺ៖

```json
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"

```

`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
និង `reason: "structure_limit"`។
នៅកម្រិតកំណត់លំនាំដើម សំណើមួយត្រូវបានចាត់ទុកថាមានរចនាសម្ព័ន្ធធ្ងន់ នៅពេលវាមានសារយ៉ាងហោចណាស់ `200`,
ឧបករណ៍យ៉ាងហោចណាស់ `64` ឬ token ដែលបានប៉ាន់ស្មានយ៉ាងហោចណាស់ `32,000` ឬនៅពេលការប៉ាន់ស្មានរចនាសម្ព័ន្ធដែលមានដែនកំណត់
ប្រើដែនកំណត់របស់វាអស់ គឺ node ដែលបានឆ្លងកាត់ចំនួន `10,000` ឬជម្រៅ `12`។

**មូលហេតុ៖** នេះគឺជាការកាត់បន្ថយបន្ទុកដោយចេតនានៅក្នុង OmniRoute មិនមែនជាការបរាជ័យរបស់អ្នកផ្តល់សេវា upstream ទេ។
process នីមួយៗប្រើ guard មូលដ្ឋានក្នុង process ដើម្បីបម្រុងសមត្ថភាព heavyweight ដែលមានកម្រិត មុនពេលរក្សាទុក
និងញែកតួសំណើធំមួយ។ heavyweight lease នៅតែត្រូវបានកាន់កាប់ពេញមួយអាយុកាលនៃការឆ្លើយតប SSE។

**#503-fanout៖** មុនពេលការកែបញ្ហានេះ guard បានកំណត់ concurrency ត្រឹមចំនួនសំណើថេរ

(subagent/CLI ច្រើន ហើយតួសំណើជាប្រចាំ > 256 KB) បានធ្លាក់ចុះទៅ concurrency ជាក់ស្តែង
ប្រហែល 1 និងទទួលបាន 503 ក្រោមបន្ទុកធម្មតាទាំងស្រុង។ ឥឡូវនេះ guard កែតម្រូវដោយខ្លួនឯង៖ វាត្រូវបានគ្រប់គ្រង
ដោយថវិកា BYTE សម្រាប់ ingest ដែលគណនាដោយស្វ័យប្រវត្តិ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) និងកំណត់ទំហំតាម
កម្រិត memory ពិតប្រាកដរបស់ process ហើយវាក៏ពិនិត្យសញ្ញាសម្ពាធធនធានបច្ចុប្បន្នផងដែរ — ដូច្នេះវា
កាត់បន្ថយបន្ទុកតែនៅពេល host កំពុងស្ថិតក្រោមសម្ពាធ memory ពិតប្រាកដប៉ុណ្ណោះ មិនមែនគ្រាន់តែដោយសារសំណើធ្ងន់ច្រើនជាងមួយ
បានមកដល់ក្នុងពេលតែមួយនោះទេ។ កម្រិតចំនួនចាស់ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) នៅតែ
ត្រូវបានគោរព ប៉ុន្តែតែនៅពេលអ្នកកំណត់វាដោយច្បាស់លាស់ប៉ុណ្ណោះ។

នៅពេលសមត្ថភាពកំពុងជាប់រវល់ សំណើ heavyweight នឹងរង់ចាំជាមុនរហូតដល់
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (លំនាំដើម `2000`, `0` បិទការរង់ចាំ) ដើម្បីឱ្យ slot មួយទំនេរ

(OpenCode, Claude Code, Cursor) ដែលបំបែកសំណើរងធ្ងន់ៗឱ្យដំណើរការដំណាលគ្នា អាចតម្រៀបការកើនឡើងភ្លាមៗនេះ

## ចំណាត់ថ្នាក់កំហុស RAG / LLM ជាជម្រើស (បញ្ហា 16 ប្រភេទ)

អ្នកប្រើ OmniRoute មួយចំនួនដាក់ gateway នៅពីមុខ RAG ឬ agent stacks។ នៅក្នុងការរៀបចំបែបនេះ ជាទូទៅគេអាចឃើញលំនាំចម្លែកមួយ៖ OmniRoute ហាក់ដូចជាដំណើរការល្អ (providers ដំណើរការ, routing profiles ត្រឹមត្រូវ, គ្មានការជូនដំណឹងអំពី rate limit) ប៉ុន្តែចម្លើយចុងក្រោយនៅតែខុស។

នៅក្នុងការអនុវត្តជាក់ស្តែង ឧប្បត្តិហេតុទាំងនេះជាធម្មតាបណ្តាលមកពី downstream RAG pipeline មិនមែនពី gateway ខ្លួនវាទេ។

ប្រសិនបើអ្នកចង់បានវាក្យសព្ទរួមសម្រាប់ពណ៌នាអំពីកំហុសទាំងនោះ អ្នកអាចប្រើ WFGY ProblemMap ដែលជាធនធានអត្ថបទខាងក្រៅមានអាជ្ញាបណ្ណ MIT ហើយកំណត់និយមន័យលំនាំកំហុស RAG / LLM ដែលកើតឡើងញឹកញាប់ចំនួនដប់ប្រាំមួយ។ ជាទូទៅ វាគ្របដណ្តប់លើ៖

- ការងាកចេញនៃការទាញយកព័ត៌មាន និងព្រំដែនបរិបទដែលខូច
- indexes និង vector stores ដែលទទេ ឬហួសសម័យ
- ភាពមិនស៊ីគ្នារវាង embedding និងអត្ថន័យ
- បញ្ហាក្នុងការផ្គុំ prompt និង context window
- ការបរាជ័យនៃតក្កវិជ្ជា និងចម្លើយដែលមានទំនុកចិត្តហួសហេតុ
- ការបរាជ័យនៃខ្សែសង្វាក់វែង និងការសម្របសម្រួល agent
- ការងាកចេញនៃអង្គចងចាំ និងតួនាទីរបស់ multi agent
- បញ្ហាក្នុងលំដាប់ deployment និង bootstrap

   - បរិបទ RAG ណាមួយដែលបានប្រើនៅ downstream (ឯកសារដែលបានទាញយក, tool calls ជាដើម)
2. ផ្គូផ្គងឧប្បត្តិហេតុនោះទៅនឹងលេខ WFGY ProblemMap មួយ ឬពីរ (`No.1` … `No.16`)។
3. រក្សាទុកលេខនោះក្នុង dashboard, runbook ឬ incident tracker ផ្ទាល់ខ្លួនរបស់អ្នក នៅក្បែរ logs របស់ OmniRoute។
4. ប្រើទំព័រ WFGY ដែលត្រូវគ្នា ដើម្បីសម្រេចថាតើអ្នកត្រូវផ្លាស់ប្តូរ RAG stack, retriever ឬយុទ្ធសាស្ត្រ routing របស់អ្នកដែរឬទេ។

អត្ថបទពេញលេញ និងរូបមន្តអនុវត្តជាក់ស្តែងមាននៅទីនេះ (អាជ្ញាបណ្ណ MIT, មានតែអត្ថបទប៉ុណ្ណោះ)៖

## បញ្ហាដែលបានដឹងនៅក្នុង v3.8.0

បញ្ហាដែលពាក់ព័ន្ធជាក់លាក់នឹងការចេញផ្សាយ v3.8.0 និងដំណោះស្រាយបណ្តោះអាសន្នបច្ចុប្បន្នរបស់វា។ ប្រសិនបើការកែតម្រូវត្រូវបានដាក់បញ្ចូលក្នុង patch ក្រោយ ធាតុនេះនឹងត្រូវបានធ្វើបច្ចុប្បន្នភាព ឬលុបចេញ។

### ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ Devin CLI បរាជ័យ

**រោគសញ្ញា៖**

- "រកមិនឃើញ Devin CLI" ឬ "ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណបានបរាជ័យ" នៅពេលហៅប្រើ tools ដែលគាំទ្រដោយ Devin
- ការត្រួតពិនិត្យ CLI runtime រាយការណ៍ថា `installed=false`

**មូលហេតុ៖**

- `CLI_DEVIN_BIN` ចង្អុលទៅ path ដែលមិនមាន
- Devin CLI មិនត្រូវបានដំឡើងនៅលើ host

**ដំណោះស្រាយ៖**

1. ដំឡើង Devin CLI សម្រាប់ platform របស់អ្នក
2. កំណត់ `CLI_DEVIN_BIN=/usr/local/bin/devin` (ឬ path ពិតប្រាកដ) ក្នុង `.env`
3. ចាប់ផ្តើម OmniRoute ឡើងវិញ ហើយធ្វើតេស្តម្តងទៀតពី **Dashboard → ឧបករណ៍ CLI**

### Model cooldown ជាប់គាំង (កំណត់ឡើងវិញដោយដៃ)

**រោគសញ្ញា៖**

- model មួយនៅតែបង្ហាញក្នុង cooldown ទោះបីជាពេលវេលាផុតកំណត់បានកន្លងផុតទៅហើយក៏ដោយ
- សំណើនៅតែរំលង model ក្នុង combo routing ទោះបីជា timestamp ស្ថិតនៅក្នុងអតីតកាលក៏ដោយ

**កំណត់ឡើងវិញដោយដៃ៖**

- **Dashboard៖** **ការកំណត់ → Model Cooldowns** → ចុច **បើកដំណើរការឡើងវិញ** លើ card ដែលរងផលប៉ះពាល់
- **API៖** `DELETE /api/resilience/model-cooldowns` ជាមួយ management auth headers

### ការតភ្ជាប់ Command Code provider បរាជ័យដោយមាន 403

**រោគសញ្ញា៖**

- ទទួលបាន 403 នៅពេលសាកល្បងការតភ្ជាប់ Command Code provider
- provider card បង្ហាញ "គ្មានសិទ្ធិ" បន្ទាប់ពីបន្ថែមថ្មី

**មូលហេតុ៖** លំហូរ OAuth មិនបានបញ្ចប់ (មិនបានទទួល callback ឬ token មិនត្រូវបានរក្សាទុក)។

**ដំណោះស្រាយ៖**

- ដំណើរការ `omniroute providers` ពី CLI ដើម្បីចាប់ផ្តើមលំហូរ OAuth ឡើងវិញ ឬ
- ដំណើរការ OAuth ឡើងវិញពី **Dashboard → Providers → Command Code → តភ្ជាប់ឡើងវិញ**

### ModelScope ផ្តល់ cooldowns 429 យ៉ាងខ្លាំង

**រោគសញ្ញា៖**

- cooldowns ខ្លីខ្លាំង ឬកើតឡើងភ្លាមៗនៅលើ ModelScope បន្ទាប់ពីសំណើមួយចំនួនតូចផ្ទុះឡើងក្នុងរយៈពេលខ្លី
- Combo routing រំលង ModelScope លឿនជាងការរំពឹងទុក

**មូលហេតុ៖** ModelScope បញ្ចេញ headers `Retry-After` ជាក់លាក់សម្រាប់ provider។ v3.8.0 ភ្ជាប់មកជាមួយការគ្រប់គ្រងជាក់លាក់សម្រាប់ headers ទាំងនោះ ដូច្នេះកំណែចាស់ៗបានបកស្រាយពួកវាខុសថាជាសញ្ញា rate-limit ទូទៅ។

**ដំណោះស្រាយ៖**

- ត្រូវប្រាកដថាអ្នកកំពុងប្រើ v3.8.0 ឬកំណែក្រោយ
- ផ្ទៀងផ្ទាត់ថា toggle `useUpstream429BreakerHints` ត្រូវបានបើកនៅក្រោម **ការកំណត់ → ភាពធន់**

### បាត់ OMNIROUTE_WS_BRIDGE_SECRET ក្នុង production

**រោគសញ្ញា៖**

- ទទួលបាន 401 លើគ្រប់សំណើ Codex/Responses WebSocket bridge នៅពេលដំណើរការលើ remote production host
- WebSocket bridge handshake បិទភ្លាមៗបន្ទាប់ពីតភ្ជាប់

**មូលហេតុ៖** env var `OMNIROUTE_WS_BRIDGE_SECRET` បាត់ពី production environment។

**ដំណោះស្រាយ៖**

1. បង្កើត secret ចៃដន្យមួយ៖ `openssl rand -hex 32`
2. កំណត់ `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ក្នុង env របស់ production server (និង client ណាមួយដែលទាក់ទងជាមួយ bridge)
3. ចាប់ផ្តើម OmniRoute ឡើងវិញ

### Responses API៖ background mode ត្រូវបានបន្ថយទៅជា synchronous

**រោគសញ្ញា៖**

- មានការកត់ត្រាព្រមាន៖ `background mode degraded to synchronous`
- សំណើ `background: true` ត្រឡប់ចម្លើយ synchronous ធម្មតា ជំនួសឱ្យ background job handle

**មូលហេតុ៖** v3.8.0 បន្ថយ `background: true` នៅលើ Responses API ទៅជាការប្រតិបត្តិ synchronous ដោយចេតនា ខណៈពេលបញ្ចេញការព្រមាន។ ការប្រតិបត្តិ async background ពេញលេញគឺជាមុខងារដែលនឹងផ្តល់ជូននាពេលអនាគត។

**ដំណោះស្រាយ៖**

- កែសម្រួល client ឱ្យហៅដោយមិនប្រើ `background` ឬ
- រង់ចាំការចេញផ្សាយកំណែក្រោយដែលភ្ជាប់មកជាមួយ async background mode ពេញលេញ (តាមដាន changelog)

## ការចាប់ផ្ដើមយឺត / អស់ពេលរង់ចាំភាពរួចរាល់

ប្រសិនបើ CLI បង្ហាញ `⚠ Server did not respond within 60s` ប៉ុន្តែម៉ាស៊ីនមេពិតជាដំណើរការ នោះកម្រិតពេលវេលាសម្រាប់ការត្រួតពិនិត្យភាពរួចរាល់គឺខ្លីពេកសម្រាប់បរិស្ថានរបស់អ្នក។

បញ្ហានេះកើតឡើងជាញឹកញាប់នៅលើ Windows (កម្មវិធីកម្ចាត់មេរោគ កម្មវិធីតាមដានប្រព័ន្ធឯកសារ) ឬកុងតឺន័រដែលមានបន្ទុកការងារធ្ងន់នៅពេលចាប់ផ្ដើម។

**ដំណោះស្រាយ — បង្កើនកម្រិតពេលវេលា៖**

```bash
# តាមរយៈអថេរបរិស្ថាន (បន្តមានប្រសិទ្ធភាពនៅរាល់ការចាប់ផ្ដើម)៖
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 នាទី
omniroute serve

# តាមរយៈទង់ CLI (ប្រើតែម្ដង)៖
omniroute serve --ready-timeout 180000
```

តម្លៃលំនាំដើមគឺ 60 000 ms (60 s)។ ការព្រមាននេះគ្រាន់តែជាព័ត៌មានប៉ុណ្ណោះ; ម៉ាស៊ីនមេនឹងបន្តចាប់ផ្ដើមនៅផ្ទៃខាងក្រោយ ហើយនឹងអាចចូលប្រើបាននៅពេលការចាប់ផ្ដើមបានបញ្ចប់។

សូមមើល [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) សម្រាប់ព័ត៌មានលម្អិតទាំងស្រុងអំពី `OMNIROUTE_READY_TIMEOUT_MS`។
