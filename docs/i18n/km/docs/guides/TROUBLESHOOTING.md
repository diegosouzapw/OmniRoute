### ការកម្រិតអត្រាលើអ្នកផ្តល់សេវាឥតគិតថ្លៃ (429 / 400 / 401)

**រោគសញ្ញា**៖ នៅពេលប្រើ `model: "auto"` ជាមួយអ្នកផ្តល់សេវាឥតគិតថ្លៃ/មិនតម្រូវឱ្យផ្ទៀងផ្ទាត់អត្តសញ្ញាណ (opencode, auggie ជាដើម) អ្នកទទួលបាន `HTTP 429`, `400` ឬ `401` ម្តងម្កាល ជំនួសឱ្យចម្លើយ។ សំណើនឹងជោគជ័យ នៅពេលព្យាយាមប្រើ prompt ដដែលម្តងទៀតបន្តិចក្រោយមក ប៉ុន្តែដំណើរការស្វ័យប្រវត្តិ (cron jobs, agents, scripts) នឹងខូចនៅពេលមានការបរាជ័យលើកដំបូង។

**មូលហេតុចម្បង**៖ របៀបបរាជ័យឯករាជ្យចំនួនបីកើតឡើងត្រួតគ្នា៖

1. **ការកម្រិតអត្រារបស់អ្នកផ្តល់សេវា (`429`)**៖ កម្រិតប្រើប្រាស់ឥតគិតថ្លៃអាចអនុវត្តកូតាតាមចន្លោះពេល។ ការហៅស្របគ្នាជាច្រើនក្នុងរយៈពេលខ្លីនឹងប្រើកូតានោះអស់ ដូច្នេះសំណើបន្ទាប់ត្រូវបានបដិសេធរហូតដល់ចន្លោះពេលត្រូវបានកំណត់ឡើងវិញ។
2. **ម៉ូដែលខូចនៅក្នុង passthrough (`400`/`401`)**៖ ក្រុម `auto/*` អាចរួមបញ្ចូលម៉ូដែល passthrough ពី `opencode` ដែលបានចុះឈ្មោះនៅក្នុងកាតាឡុក ប៉ុន្តែមិនមានព័ត៌មានសម្គាល់អត្តសញ្ញាណដែលអាចប្រើបាន (ឧ. `oc/north-mini-code-free` → `401`)។ auto-router សាកល្បងម៉ូដែលមួយ ហើយបរាជ័យ រួចកំហុសត្រូវបានបញ្ជូនបន្ត មុនពេលយន្តការ fallback ចាប់ផ្តើមដំណើរការ។
3. **ការពង្រីកដោយសារដំណើរការស្របគ្នា (`429` ក្រោមបន្ទុក)**៖ នៅពេលសម័យ agent/cron ច្រើនហៅ `auto` ក្នុងពេលតែមួយ អត្រាសំណើសរុបនឹងលើសពីកម្រិតដែលអ្នកផ្តល់សេវាឥតគិតថ្លៃអាចទទួលបាន ដូច្នេះការហៅត្រឹមត្រូវត្រូវបានចាត់ទុកថាជាការបំពាន។

**ដំណោះស្រាយដែលបានផ្ទៀងផ្ទាត់ (រាយការណ៍ដោយសហគមន៍, 2026-08-10)**៖ កែសម្រួល environment variables ចំនួនបី ដើម្បីឱ្យការបង្វិល ការដំណើរការស្របគ្នា និង fallback អាចសម្របខ្លួននឹងការប្រែប្រួលនៃកម្រិតឥតគិតថ្លៃ ជំនួសឱ្យការបរាជ័យដោយសារវា៖

```bash
export OMNIROUTE_ROTATE_ON_400=true           # ប្តូរទៅម៉ូដែល/អ្នកផ្តល់សេវាផ្សេងនៅពេលមាន 400/401 (រំលងម៉ូដែល passthrough ដែលខូច)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # កម្រិតអតិបរមាជាក់លាក់នៃការអនុញ្ញាតសំណើធ្ងន់ (តាមលំនាំដើមមិនបានកំណត់៖ គ្មានការកំណត់ចំនួនសំណើ សូមមើលកំណត់សម្គាល់ខាងក្រោម)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # រង់ចាំក្នុងដែនកំណត់យូរជាងមុនសម្រាប់សមត្ថភាពសំណើធ្ងន់ ជំនួសឱ្យ 503 ដែលអាចព្យាយាមឡើងវិញបានភ្លាមៗ
```

កំណត់តម្លៃទាំងនេះនៅក្នុងបរិស្ថាននៃដំណើរការ OmniRoute (daemon ឧ. តាមរយៈ LaunchAgent plist ឬ `systemctl edit`) បន្ទាប់មកចាប់ផ្តើម OmniRoute ឡើងវិញ។ rotation flag គឺជាឧបករណ៍ដែលមានប្រសិទ្ធភាពខ្ពស់បំផុតតែមួយ៖ វាបម្លែងការបរាជ័យទាំងស្រុង ទៅជាការព្យាយាមឡើងវិញដោយស្វ័យប្រវត្តិជាមួយអ្នកផ្តល់សេវាដែលដំណើរការល្អនៅក្នុងក្រុម។

**កំណត់សម្គាល់**៖ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` កំណត់ចំនួនសំណើធ្ងន់ — ដែលមាន context វែង — ដែលអាចដំណើរការក្នុងពេលតែមួយ។ ដែនកំណត់នេះគឺជា admission gate មិនមែនជាកម្មវិធីកម្រិតអត្រារបស់អ្នកផ្តល់សេវាទេ។ **បច្ចុប្បន្នភាព #503-fanout៖** var នេះលែងត្រូវបានកំណត់តាមលំនាំដើមទៀតហើយ (ឥឡូវនេះ វានឹងមានប្រសិទ្ធភាពតែនៅពេលត្រូវបានកំណត់យ៉ាងជាក់លាក់ ដូចខាងលើប៉ុណ្ណោះ) — ផ្ទុយទៅវិញ ការអនុញ្ញាតសំណើធ្ងន់ត្រូវបានគ្រប់គ្រងដោយ byte budget ដែលគណនាដោយស្វ័យប្រវត្តិ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ហើយវាសម្របខ្លួនតាមកម្រិតអង្គចងចាំពិតប្រាកដរបស់ host។ ដូច្នេះ deployment ថ្មីគួរតែជួបការបដិសេធ `503 chat_admission_busy` តិចជាងមុនយ៉ាងច្រើន ដោយមិនចាំបាច់កំណត់ var នេះសោះ។ ការកំណត់វាយ៉ាងជាក់លាក់នៅទីនេះ នៅតែដំណើរការត្រឹមត្រូវដូចដែលបានចងក្រងជាឯកសារ។ ការកំណត់ byte-budget ដោយផ្ទាល់ត្រូវបានកម្រិតចន្លោះ 8 MiB–2 GiB។ `413 body_exceeds_budget` មិនមែនជាបញ្ហាបណ្តោះអាសន្នទេ៖ បង្កើន byte budget នោះ បន្ថយ `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ឬបង្កើនកម្រិតអង្គចងចាំរបស់ដំណើរការ។ ការបោះបង់ `inflight_bytes_budget` គឺជាការប្រជែងធនធានបណ្តោះអាសន្ន ហើយនៅតែអាចព្យាយាមឡើងវិញបាន។ ការកម្រិតអត្រាសម្រាប់អ្នកផ្តល់សេវានីមួយៗ (`open-sse/services/rateLimitManager.ts`) ត្រូវបានគ្រប់គ្រងដោយឡែកពីគ្នាតាមរយៈ `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` និង `RATE_LIMIT_AUTO_ENABLE` — សូមមើល `.env.example`។

**របៀបផ្ទៀងផ្ទាត់ថាវាដំណើរការ**៖ ដំណើរការ agent/cron របស់អ្នកពីរដងជាប់ៗគ្នាក្នុងរយៈពេលខ្លី ហើយបញ្ជាក់ថាទាំងពីរជោគជ័យ។ មុនពេលអនុវត្តដំណោះស្រាយ ការដំណើរការលើកទីពីរជាធម្មតាបង្ហាញ `429`/`401`។ បន្ទាប់ពីអនុវត្តដំណោះស្រាយ ការបរាជ័យ (ប្រសិនបើមាន) នឹងត្រូវបានព្យាយាមឡើងវិញដោយស្វ័យប្រវត្តិ ហើយការហៅនឹងបញ្ចប់។ អ្នកក៏អាចប្រើ `curl /monitoring/health` ហើយតាមដាន field `rateLimitedUntil` នៅលើការតភ្ជាប់របស់អ្នកផ្តល់សេវា និង `circuitBreakers.providerBreakers[].state` សម្រាប់អ្នកផ្តល់សេវាដែលរងផលប៉ះពាល់ — state នឹងជាតម្លៃមួយក្នុងចំណោម `CLOSED`, `DEGRADED`, `OPEN` ឬ `HALF_OPEN` (សូមមើល `src/shared/utils/circuitBreaker.ts`) ហើយអ្នកផ្តល់សេវាដែលបន្តបរាជ័យនឹងប្តូរ `CLOSED → DEGRADED → OPEN` មុនពេលចន្លោះពេលកំណត់ឡើងវិញអនុញ្ញាតឱ្យការសាកល្បងមួយឆ្លងកាត់ (`HALF_OPEN`)។

**ប្រសិនបើអ្នកនៅតែឃើញ 429**៖ គណនីសកម្មសម្រាប់អ្នកផ្តល់សេវានោះពិតជាបានប្រើអស់ _កូតា_ របស់វា (មិនមែនត្រឹមតែកម្រិតអត្រាប៉ុណ្ណោះទេ)។ បន្ថែមគណនីទីពីរសម្រាប់អ្នកផ្តល់សេវាដូចគ្នានៅក្នុងផ្ទាំងគ្រប់គ្រង OmniRoute → Providers → Accounts ឬប្រើអ្នកផ្តល់សេវាឥតគិតថ្លៃផ្សេងទៀតរួមគ្នា (ឧ. `routeway`, `auggie`)។ ការប្តូរវេនមានប្រសិទ្ធភាពតែចំពោះកម្រិតអត្រាបណ្តោះអាសន្ន/400/401 ប៉ុណ្ណោះ។ ការប្រើអស់កូតាទាំងស្រុងតម្រូវឱ្យមានព័ត៌មានសម្គាល់អត្តសញ្ញាណទីពីរ ឬអ្នកផ្តល់សេវាផ្សេង។

**ប្រសិនបើអ្នកឃើញ 403 នៅលើម៉ូដែលចក្ខុវិស័យ (`auto/vision`, `bazaarlink/*`)**៖ គណនីដែលបានភ្ជាប់មិនមានគម្រោងបង់ប្រាក់ដែលរួមបញ្ចូលមុខងារចក្ខុវិស័យ ឬ API key មានសិទ្ធិមិនគ្រប់គ្រាន់។ ផ្ទៀងផ្ទាត់នៅក្នុងផ្ទាំងគ្រប់គ្រងរបស់អ្នកផ្តល់សេវាថា វិសាលភាពរបស់ key រួមបញ្ចូលចក្ខុវិស័យ/ពហុមធ្យោបាយ ឬភ្ជាប់គណនីកម្រិតបង់ប្រាក់ ហើយរក្សាវាទុកជាគោលដៅសម្រាប់ចក្ខុវិស័យ។

## ការព្រមានរបស់ npm install (ERESOLVE / peer / deprecated)

នៅពេលអ្នកដំណើរការ `npm install -g omniroute` អ្នកអាចឃើញការព្រមានជាច្រើនដូចជា `npm warn ERESOLVE` ការជូនដំណឹងអំពី peer dependency និងសារ `deprecated`។ **ទាំងនេះជាអ្វីដែលរំពឹងទុក ហើយមិនបង្កបញ្ហាទេ។** ការដំឡើងរបស់អ្នកបានជោគជ័យ ប្រសិនបើអ្នកឃើញ `added <N> packages` នៅក្នុងលទ្ធផល។

ការព្រមានទាំងនេះកើតចេញពីជួរ peer dependency ដែលហួសសម័យនៅក្នុងកញ្ចប់របស់ភាគីទីបី ដែល OmniRoute មិនអាចគ្រប់គ្រងបាន៖

1. **`marked-terminal` ត្រូវការ `marked >=1 <16` ប៉ុន្តែបានរកឃើញ `marked@18`** — ជាក់ស្តែងវាដំណើរការល្អធម្មតា; ជួរ peer របស់ upstream គ្រាន់តែហួសសម័យប៉ុណ្ណោះ។

### Avast/AVG ដាក់ `README.md` ឱ្យនៅដាច់ដោយឡែកដោយសារ `MD:HttpRequest-inf[Susp]`

**នេះគឺជាការរកឃើញវិជ្ជមានក្លែងក្លាយ។ គ្មានអ្វីមួយត្រូវបានឆ្លងមេរោគទេ ហើយក៏មិនតម្រូវឱ្យធ្វើសកម្មភាពអ្វីឡើយ។**

Avast និង AVG ដំណើរការវិធីសាស្ត្រវិនិច្ឆ័យ heuristic ដែលដាក់ទង់សម្គាល់ឯកសារអត្ថបទធម្មតា/Markdown ដែលមានតំណភ្ជាប់ជាច្រើនមើលទៅដូចជាសំណើ HTTP។ `README.md` របស់ OmniRoute ត្រូវបានដាក់បញ្ចូលក្នុងកញ្ចប់ npm (វាត្រូវបានរាយក្នុង `package.json` → `files`) ដូច្នេះ នៅពេលដំឡើងជាសកល វានឹងស្ថិតនៅ `node_modules/omniroute/README.md` — ហើយវាមានឧទាហរណ៍ `http://localhost:20128/...` ប្រហែល 15 (ចំណុចបញ្ចប់ HTTP/SSE របស់ MCP, URL `.well-known` របស់ A2A និងឃ្លាបញ្ជា `curl`)។ ដង់ស៊ីតេតំណភ្ជាប់នេះគឺគ្រប់គ្រាន់ដើម្បីឱ្យ heuristic នោះដំណើរការជូនដំណឹង។

ប្រសិនបើបញ្ហានេះទើបតែចាប់ផ្តើមកើតឡើងនាពេលថ្មីៗនេះ៖ លក្ខណៈនៃឯកសារមិនបានផ្លាស់ប្តូរទេ។ README បានពង្រីកតារាងចំណុចបញ្ចប់របស់វា (MCP HTTP + SSE + A2A ត្រូវបានបន្ថែម) និងបន្ថែមឧទាហរណ៍ `curl` ជាច្រើនទៀត ដែលធ្វើឱ្យវាលើសកម្រិតកំណត់។

ឯកសារនេះគ្រាន់តែជាឯកសារណែនាំអសកម្ម ដែលគ្មានខ្លឹមសារអាចប្រតិបត្តិបានឡើយ។ អ្នកអាចស្ដារវាពីកន្លែងដាក់ឱ្យនៅដាច់ដោយឡែកវិញដោយសុវត្ថិភាព។

**ហេតុអ្វីយើងមិន “កែបញ្ហា” នេះពីខាងយើង៖** ឧទាហរណ៍ទាំងអស់សុទ្ធតែជា `http://localhost` ហើយ localhost មិនអាចប្រើ `https` បានទេ បើគ្មានភាពស្មុគស្មាញពីវិញ្ញាបនបត្រដែលចុះហត្ថលេខាដោយខ្លួនឯង។ ការកែប្រែឯកសារណែនាំឱ្យខុសពីធម្មតាដើម្បីគេចពី heuristic របស់អ្នកផ្គត់ផ្គង់តែមួយ នឹងបង្កការលំបាកដល់អ្នកអានគ្រប់រូប ដើម្បីតែបំពេញចិត្តកំហុសរបស់កម្មវិធីស្កេនប៉ុណ្ណោះ។

**ហេតុអ្វីវាដំណើរការជូនដំណឹង៖** កម្មវិធីដំឡើង Windows **មិនទាន់ត្រូវបានចុះហត្ថលេខាលើកូដទេ** ដូច្នេះ កម្មវិធីដំឡើង NSIS ដែលគ្មានហត្ថលេខាមានកេរ្តិ៍ឈ្មោះសូន្យ ហើយ heuristic ផ្អែកលើឥរិយាបថដំណើរការក្នុងកម្រិតតឹងរ៉ឹងបំផុត។ នៅពេលរួមបញ្ចូលគ្នាជាមួយ DLL ដើមកំណើតដែលបានដាក់បញ្ចូល និងឯកសារ `.js` រាប់រយដែលត្រូវបានសរសេរនៅក្រោម `%LOCALAPPDATA%\Programs\OmniRoute` (រួមទាំងថតកញ្ចប់ដែលមានបច្ច័យ hash ពី standalone build របស់ Next.js) វាគ្រប់គ្រាន់ដើម្បីឱ្យ heuristic នោះដំណើរការជូនដំណឹង។ ការចុះហត្ថលេខាលើកូដត្រូវបានគ្រោងទុករួចហើយ។ រហូតដល់ពេលវាត្រូវបានអនុវត្ត កំណែចេញផ្សាយថ្មីៗអាចបង្កបញ្ហានេះឡើងវិញ។

1. **ផ្ទៀងផ្ទាត់ឯកសារទាញយករបស់អ្នកជាមុនសិន** (ដើម្បីដកចេញនូវលទ្ធភាពដែលឯកសារត្រូវបានកែបន្លំ)។ រាល់កំណែចេញផ្សាយទាំងអស់មាន `latest.yml` ដែលវាល `sha512` (base64) របស់វាគ្របដណ្ដប់លើកម្មវិធីដំឡើង `OmniRoute.Setup.<version>.exe`។ នៅក្នុង PowerShell ពីថតដែលមានកម្មវិធីដំឡើង៖
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   លទ្ធផលត្រូវតែផ្គូផ្គងនឹង `latest.yml` → `sha512`។ ប្រសិនបើវាមិនផ្គូផ្គងទេ សូមលុបឯកសារ ហើយទាញយកម្ដងទៀតពី [ទំព័រកំណែចេញផ្សាយ GitHub](https://github.com/diegosouzapw/OmniRoute/releases) ប៉ុណ្ណោះ។
2. **ស្ដារ + មិនរាប់បញ្ចូល** — ស្ដារធាតុដែលត្រូវបានត្រឡប់ក្រោយពីកន្លែងដាក់ឱ្យនៅដាច់ដោយឡែក ហើយបន្ថែមការមិនរាប់បញ្ចូលសម្រាប់ `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions) បន្ទាប់មកដំឡើងឡើងវិញ។
3. **រាយការណ៍ការរកឃើញវិជ្ជមានក្លែងក្លាយ** — <https://opentip.kaspersky.com/>។ របាយការណ៍ FP ដែលអ្នកប្រើប្រាស់បានដាក់ស្នើ ពិតជាជួយពន្លឿនការដាក់បញ្ចូលទៅក្នុងបញ្ជីអនុញ្ញាត។

## ភាពឆបគ្នាជាមួយ Node.js

<a name="nodejs-compatibility"></a>

### ទំព័រចូលគាំង ឬបង្ហាញកំហុស "Module self-registration"

**មូលហេតុ៖** អ្នកកំពុងដំណើរការកំណែ Node.js ដែលនៅក្រៅកម្រិតអប្បបរមានៃបរិស្ថានដំណើរការដែលមានសុវត្ថិភាព និងត្រូវបានអនុម័តដោយ OmniRoute។ ករណីដែលកើតមានញឹកញាប់បំផុតគឺការប្រើកំណែបំណះចាស់របស់ Node 22 ឬ 24 ដែលទាបជាងកម្រិតបំណះសុវត្ថិភាពដែល OmniRoute តម្រូវ។

**រោគសញ្ញា៖**

- ទំព័រចូលបង្ហាញអេក្រង់ទទេ ឬកំហុសម៉ាស៊ីនមេ
- កុងសូលបង្ហាញ `Error: Module did not self-register` ឬកំហុស native binding ស្រដៀងគ្នា
- ទំព័រចូលបង្ហាញ **បដាព្រមានពណ៌ទឹកក្រូច** ដែលមានកំណែ Node របស់អ្នក ប្រសិនបើបរិស្ថានដំណើរការនៅក្រៅគោលការណ៍សុវត្ថិភាពដែលបានគាំទ្រ

**ដំណោះស្រាយ៖**

1. ដំឡើងកំណែ Node.js LTS ដែលបានគាំទ្រ (ណែនាំ៖ Node.js 24.x)៖
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ផ្ទៀងផ្ទាត់កំណែរបស់អ្នក៖ `node --version` គួរតែបង្ហាញ `v24.0.0` ឬថ្មីជាងនេះនៅលើជួរ 24.x LTS
3. ដំឡើង OmniRoute ឡើងវិញ៖ `npm install -g omniroute`
4. ចាប់ផ្ដើមឡើងវិញ៖ `omniroute`

> **កំណែមានសុវត្ថិភាពដែលបានគាំទ្រ៖** `>=22.22.2 <23` ឬ `>=24.0.0 <27`។ Node.js 24.x LTS (Krypton) និង Node.js 26 ត្រូវបានគាំទ្រពេញលេញ។

### npm v11+៖ `better-sqlite3` មិនត្រូវបានដំឡើង (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**មូលហេតុ៖** តាមលំនាំដើម npm v11 (ដែលភ្ជាប់មកជាមួយ Node.js 24+) ទប់ស្កាត់ស្គ្រីបដំឡើងសម្រាប់
dependency ជាជម្រើស។ ដោយសារ `better-sqlite3` ត្រូវបានរាយក្នុង `optionalDependencies`
ហើយតម្រូវឱ្យមានការចងក្រង native (`node-gyp rebuild`) ដូច្នេះ npm នឹងរំលងវាដោយមិនបង្ហាញសារ។

**រោគសញ្ញា៖**

- ម៉ាស៊ីនមេគាំងនៅពេលចាប់ផ្ដើមជាមួយ `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` បង្ហាញ "No such file or directory"
- `npm ls better-sqlite3` បង្ហាញ `(empty)`

**ដំណោះស្រាយ៖**

1. អនុម័តស្គ្រីបដំឡើង ហើយដំឡើងឡើងវិញ៖
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ឬដំឡើងកញ្ចប់ដែលបាន build រួចជាមុនដោយដៃ៖
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ផ្ទៀងផ្ទាត់ថាវាដំណើរការ៖ `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS៖ `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**មូលហេតុ៖** បន្ទាប់ពី `npm install -g omniroute` ជាសកល ឯកសារ binary native របស់ `better-sqlite3` នៅក្នុង package អាចត្រូវបានចងក្រងសម្រាប់ស្ថាបត្យកម្ម ឬ Node.js ABI ខុសពីអ្វីដែលកំពុងដំណើរការក្នុងម៉ាស៊ីន។ បញ្ហានេះកើតមានជាទូទៅនៅលើ macOS (ទាំង Apple Silicon និង Intel) នៅពេលឯកសារ binary ដែលបាន build រួចជាមុនមិនត្រូវគ្នានឹងបរិស្ថានរបស់អ្នក។

**រោគសញ្ញា៖**

- ម៉ាស៊ីនមេបរាជ័យភ្លាមៗនៅពេលចាប់ផ្ដើមជាមួយកំហុស `dlopen`
- កំហុសមាន `slice is not valid mach-o file`
- ឧទាហរណ៍ពេញលេញ៖

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ដំណោះស្រាយ — build ឡើងវិញសម្រាប់បរិស្ថានក្នុងម៉ាស៊ីនរបស់អ្នក (មិនចាំបាច់ទម្លាក់កំណែ Node.js)៖**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ចំណាំ៖** វានឹងចងក្រង native binding ឡើងវិញឱ្យត្រូវនឹងកំណែ Node.js និងស្ថាបត្យកម្ម CPU ក្នុងម៉ាស៊ីនរបស់អ្នក ដើម្បីដោះស្រាយភាពមិនត្រូវគ្នានៃឯកសារ binary។ ជួរបរិស្ថានដំណើរការដែលបានគាំទ្រជាផ្លូវការគឺ **`>=22.22.2 <23` ឬ `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` ក្នុង `src/shared/utils/nodeRuntimeSupport.ts` ដែលស្របគ្នានឹង field `engines` របស់ `package.json`)។ Node.js 24.x LTS (Krypton) និង Node.js 26 ត្រូវបានគាំទ្រពេញលេញជាមួយ `better-sqlite3` v12.x។

## បញ្ហា Proxy

<a name="proxy-issues"></a>

### ការផ្ទៀងផ្ទាត់ Provider បង្ហាញ "fetch failed"

**មូលហេតុ៖** Endpoint សម្រាប់ផ្ទៀងផ្ទាត់ API key (`POST /api/providers/validate`) ពីមុនបានរំលងការកំណត់រចនាសម្ព័ន្ធ proxy ដែលបណ្តាលឱ្យមានបញ្ហានៅក្នុងបរិស្ថានដែលតម្រូវឱ្យបញ្ជូនតាម proxy។

**ការកែតម្រូវ (v3.5.5+)៖** បញ្ហានេះត្រូវបានកែតម្រូវរួចហើយ។ ការផ្ទៀងផ្ទាត់ Provider ឥឡូវនេះត្រូវបានបញ្ជូនតាម `runWithProxyContext` ដោយគោរពតាមការកំណត់ proxy កម្រិត Provider និងកម្រិតសកលដោយស្វ័យប្រវត្តិ។

### ការត្រួតពិនិត្យស្ថានភាព Token បរាជ័យដោយបង្ហាញ "fetch failed"

**មូលហេតុ៖** ការធ្វើឱ្យ OAuth token ស្រស់នៅផ្ទៃខាងក្រោយ មិនបានកំណត់ការកំណត់រចនាសម្ព័ន្ធ proxy សម្រាប់ការតភ្ជាប់នីមួយៗទេ។

**ការកែតម្រូវ (v3.5.5+)៖** កម្មវិធីកំណត់ពេលត្រួតពិនិត្យស្ថានភាព token ឥឡូវនេះកំណត់រចនាសម្ព័ន្ធ proxy សម្រាប់ការតភ្ជាប់នីមួយៗ មុនពេលព្យាយាមធ្វើឱ្យ token ស្រស់។ សូមធ្វើបច្ចុប្បន្នភាពទៅ v3.5.5+។

### SOCKS5 proxy ត្រឡប់ "invalid onRequestStart method"

**មូលហេតុ៖** នៅលើ Node.js 22, dispatcher របស់ undici@8 មិនត្រូវគ្នាជាមួយការអនុវត្ត `fetch()` ដែលមានស្រាប់ក្នុង Node ទេ។

**ការកែតម្រូវ (v3.5.5+)៖** ឥឡូវនេះ OmniRoute ប្រើមុខងារ `fetch()` ផ្ទាល់របស់ undici នៅពេល proxy dispatcher សកម្ម ដើម្បីធានាបាននូវឥរិយាបថស្របគ្នា។ សូមធ្វើបច្ចុប្បន្នភាពទៅ v3.5.5+។

### MITM proxy ក្រោម WSL៖ កម្មវិធី Desktop នៅលើ Windows host មិនត្រូវបានស្ទាក់ចាប់

**មូលហេតុ៖** MITM proxy និងវិញ្ញាបនបត្រ CA របស់វាត្រូវបានដំឡើងក្នុងបរិស្ថានដែល OmniRoute ដំណើរការ។ នៅក្រោម WSL បរិស្ថាននោះគឺជា Linux guest ខណៈដែលកម្មវិធី AI desktop (Kiro, Trae, Copilot, Zed, …) ដំណើរការនៅលើ Windows host។ កម្មវិធីនៅលើ host មិនទុកចិត្ត certificate store របស់ guest ហើយក៏មិនបញ្ជូនចរាចរណ៍តាម system proxy របស់ guest ដែរ ដូច្នេះការស្ទាក់ចាប់កម្មវិធី Desktop មិនដំណើរការនៅទីនោះទេ។

**អនុសាសន៍៖** ដំណើរការ OmniRoute ដោយផ្ទាល់នៅលើប្រព័ន្ធប្រតិបត្តិការដូចគ្នានឹងកម្មវិធី Desktop ដែលអ្នកចង់ស្ទាក់ចាប់ (Windows សម្រាប់កម្មវិធី Windows; ដូចគ្នានេះដែរសម្រាប់ macOS/Linux)។ ការរក្សា OmniRoute នៅក្នុង WSL ខណៈពេលកំណត់គោលដៅលើកម្មវិធីរបស់ host តម្រូវឱ្យអ្នកទុកចិត្តវិញ្ញាបនបត្រ CA ដែលបានបង្កើតនៅលើ Windows host ដោយដៃ ហើយកំណត់ការកំណត់ network/proxy របស់កម្មវិធីនីមួយៗនៅលើ host ឱ្យចង្អុលទៅ endpoint របស់ WSL proxy — នេះជាការកំណត់ដែលមិនត្រូវបានគាំទ្រ និងងាយមានបញ្ហា។

### កំហុសក្នុងការធ្វើសមកាលកម្ម Cloud

1. ផ្ទៀងផ្ទាត់ថា `BASE_URL` ចង្អុលទៅកាន់ instance ដែលកំពុងដំណើរការរបស់អ្នក (ឧ., `http://localhost:20128`)
2. ផ្ទៀងផ្ទាត់ថា `CLOUD_URL` ចង្អុលទៅកាន់ endpoint Cloud របស់អ្នក (ឧ., `https://omniroute.dev`)
3. រក្សាតម្លៃ `NEXT_PUBLIC_*` ឱ្យស្របគ្នាជាមួយតម្លៃនៅផ្នែក server

### Cloud `stream=false` ត្រឡប់ 500

**រោគសញ្ញា:** `Unexpected token 'd'...` នៅលើ endpoint Cloud សម្រាប់ការហៅដែលមិនមែនជា streaming។

**មូលហេតុ:** Upstream ត្រឡប់ payload ជា SSE ខណៈដែល client រំពឹងទុក JSON។

**ដំណោះស្រាយបណ្ដោះអាសន្ន:** ប្រើ `stream=true` សម្រាប់ការហៅដោយផ្ទាល់ទៅ Cloud។ Runtime មូលដ្ឋានមានយន្តការ fallback ពី SSE→JSON។

### Cloud បង្ហាញថាបានភ្ជាប់ ប៉ុន្តែ "Invalid API key"

1. បង្កើត key ថ្មីពី dashboard មូលដ្ឋាន (`/api/keys`)
2. ដំណើរការ Cloud sync៖ Enable Cloud → Sync Now
3. Key ចាស់ ឬមិនទាន់បានធ្វើសមកាលកម្ម នៅតែអាចត្រឡប់ `401` នៅលើ Cloud

### Docker IPv6 / ការតភ្ជាប់ត្រូវបានកំណត់ឡើងវិញ

<a name="docker-ipv6"></a>

**រោគសញ្ញា:** `curl http://localhost:20128/v1/models` ត្រឡប់ `curl: (56) Recv failure: Connection reset by peer`។ Dashboard និង endpoint ដែលមិនទាមទារការផ្ទៀងផ្ទាត់ដំណើរការ ប៉ុន្តែ endpoint ដែលទាមទារការផ្ទៀងផ្ទាត់បរាជ័យ — វាមើលទៅដូចជាបញ្ហានៃការផ្ទៀងផ្ទាត់ ប៉ុន្តែមិនមែនទេ។

**មូលហេតុ:** `docker run -p 20128:20128` បើកផ្សាយនៅលើទាំង `0.0.0.0` (IPv4) និង `::` (IPv6) ប៉ុន្តែ process នៅក្នុង container ស្ដាប់តែលើ IPv4 ប៉ុណ្ណោះ។ នៅលើ host ដែល `localhost` ត្រូវបាន resolve ទៅ `::1` ជាមុន ការតភ្ជាប់នឹងចូលទៅកាន់ port IPv6 ដែលបានបើកផ្សាយ ប៉ុន្តែគ្មាន listener នៅពីក្រោយវា → ការតភ្ជាប់ត្រូវបានកំណត់ឡើងវិញ។

**ការជួសជុល:**

1. **ការធ្វើរោគវិនិច្ឆ័យរហ័ស:** ដំណើរការ `curl -4 http://localhost:20128/v1/models`។ ប្រសិនបើវាដំណើរការជាមួយ `-4` ប៉ុន្តែបរាជ័យបើគ្មានវា នោះអ្នកមានភាពមិនត្រូវគ្នានៃ IPv6 bind។
2. **ការជួសជុលជាអចិន្ត្រៃយ៍:** Bind ទៅ IPv4 ដោយជាក់លាក់ តាមរយៈការប្រើ `-p 127.0.0.1:20128:20128` ក្នុង command `docker run` របស់អ្នក៖
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   វាបង្ខំឱ្យ bind ទៅ IPv4 ហើយក៏ជៀសវាងការបើក proxy នៅលើ interface ទាំងអស់របស់ host ផងដែរ។

### ការកែតម្រូវ exponential backoff

ប្រវត្តិរូបអ្នកផ្តល់សេវាគាំទ្រការកំណត់ទាំងនេះ៖

- **ការពន្យារមូលដ្ឋាន** — រយៈពេលរង់ចាំដំបូងបន្ទាប់ពីបរាជ័យលើកទីមួយ (លំនាំដើម៖ 1s)
- **ការពន្យារអតិបរមា** — កម្រិតអតិបរមានៃរយៈពេលរង់ចាំ (លំនាំដើម៖ 30s)
- **មេគុណ** — កម្រិតបង្កើនការពន្យារសម្រាប់ការបរាជ័យជាប់ៗគ្នានីមួយៗ (លំនាំដើម៖ 2x)

### ការទប់ស្កាត់ thundering herd

នៅពេលសំណើស្របពេលជាច្រើនទៅដល់អ្នកផ្តល់សេវាដែលត្រូវបានកំណត់កម្រិតអត្រា OmniRoute ប្រើ mutex + ការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិ ដើម្បីតម្រៀបសំណើឱ្យដំណើរការតាមលំដាប់ និងទប់ស្កាត់ការបរាជ័យជាបន្តបន្ទាប់។ វាដំណើរការដោយស្វ័យប្រវត្តិសម្រាប់អ្នកផ្តល់សេវាដែលប្រើ API key។

## ចំណាត់ថ្នាក់កំហុស RAG / LLM ជាជម្រើស (បញ្ហា 16 ប្រភេទ)

អ្នកប្រើ OmniRoute មួយចំនួនដាក់ gateway នៅពីមុខប្រព័ន្ធ RAG ឬ agent។ ក្នុងការរៀបចំបែបនេះ គេតែងឃើញលំនាំចម្លែកមួយ៖ OmniRoute មើលទៅដំណើរការល្អ (providers ដំណើរការ, routing profiles ត្រឹមត្រូវ, គ្មានការជូនដំណឹងអំពី rate limit) ប៉ុន្តែចម្លើយចុងក្រោយនៅតែខុស។

ជាក់ស្តែង ឧប្បត្តិហេតុទាំងនេះជាទូទៅកើតចេញពី RAG pipeline ខាងក្រោម មិនមែនពី gateway ខ្លួនវាទេ។

ប្រសិនបើអ្នកចង់បានវាក្យសព្ទរួមសម្រាប់ពិពណ៌នាអំពីកំហុសទាំងនោះ អ្នកអាចប្រើ WFGY ProblemMap ដែលជាធនធានអត្ថបទខាងក្រៅក្រោមអាជ្ញាបណ្ណ MIT និងកំណត់និយមន័យលំនាំកំហុស RAG / LLM ដែលកើតឡើងញឹកញាប់ចំនួនដប់ប្រាំមួយ។ ជាទូទៅ វាគ្របដណ្ដប់លើ៖

- ការប្រែប្រួលគោលដៅនៃការទាញយក និងព្រំដែនបរិបទដែលខូច
- index និង vector store ដែលទទេ ឬហួសសម័យ
- ភាពមិនត្រូវគ្នារវាង embedding និងអត្ថន័យ
- បញ្ហានៃការផ្គុំ prompt និង context window
- ការដួលរលំនៃតក្កវិជ្ជា និងចម្លើយដែលមានទំនុកចិត្តហួសហេតុ
- កំហុសក្នុងខ្សែសង្វាក់វែង និងការសម្របសម្រួល agent
- ការប្រែប្រួល memory និងតួនាទីក្នុងប្រព័ន្ធ multi-agent
- បញ្ហាលំដាប់នៃ deployment និង bootstrap

3. ចាប់ផ្ដើម OmniRoute ឡើងវិញ ហើយសាកល្បងម្ដងទៀតពី **Dashboard → CLI Tools**

### Model cooldown ជាប់គាំង (កំណត់ឡើងវិញដោយដៃ)

**រោគសញ្ញា៖**

- model មួយនៅតែបង្ហាញក្នុង cooldown ទោះបីជាពេលផុតកំណត់បានកន្លងហួសទៅហើយក៏ដោយ
- សំណើនៅតែរំលង model ក្នុង combo routing ទោះបី timestamp ស្ថិតនៅក្នុងអតីតកាលក៏ដោយ

**ការកំណត់ឡើងវិញដោយដៃ៖**

- **Dashboard:** **Settings → Model Cooldowns** → ចុច **Re-enable** លើ card ដែលរងផលប៉ះពាល់
- **API:** `DELETE /api/resilience/model-cooldowns` ជាមួយ management auth headers

### ការភ្ជាប់ Command Code provider បរាជ័យដោយមាន 403

**រោគសញ្ញា៖**

- ទទួលបាន 403 នៅពេលសាកល្បងការភ្ជាប់ Command Code provider
- provider card បង្ហាញ "គ្មានសិទ្ធិ" បន្ទាប់ពីបន្ថែមថ្មី

**មូលហេតុ៖** លំហូរ OAuth មិនបានបញ្ចប់ (មិនបានទទួល callback ឬ token មិនត្រូវបានរក្សាទុក)។

**ដំណោះស្រាយ៖**

- ដំណើរការ `omniroute providers` ពី CLI ដើម្បីចាប់ផ្ដើមលំហូរ OAuth ម្ដងទៀត ឬ
- ដំណើរការ OAuth ឡើងវិញពី **Dashboard → Providers → Command Code → Reconnect**

### ModelScope ត្រឡប់ cooldown 429 ដ៏តឹងរ៉ឹង

**រោគសញ្ញា៖**

- cooldown ខ្លីខ្លាំង ឬកើតឡើងភ្លាមៗលើ ModelScope បន្ទាប់ពីមានសំណើជាបន្តបន្ទាប់តិចតួច
- combo routing រំលង ModelScope លឿនជាងការរំពឹងទុក

**មូលហេតុ៖** ModelScope បញ្ចេញ headers `Retry-After` ជាក់លាក់សម្រាប់ provider។ v3.8.0 ផ្ដល់នូវការគ្រប់គ្រងជាក់លាក់សម្រាប់ headers ទាំងនោះ ដូច្នេះកំណែចាស់អានពួកវាខុសថាជាសញ្ញាប្រាប់អំពី rate-limit ទូទៅ។

**ដំណោះស្រាយ៖**

- ត្រូវប្រាកដថាអ្នកកំពុងប្រើ v3.8.0 ឬថ្មីជាងនេះ
- ផ្ទៀងផ្ទាត់ថា toggle `useUpstream429BreakerHints` ត្រូវបានបើកនៅក្រោម **Settings → Resilience**

### បាត់ OMNIROUTE_WS_BRIDGE_SECRET ក្នុង production

**រោគសញ្ញា៖**

- ទទួលបាន 401 លើរាល់សំណើ Codex/Responses WebSocket bridge នៅពេលដំណើរការលើ remote production host
- WebSocket bridge handshake បិទភ្លាមៗបន្ទាប់ពីភ្ជាប់

**មូលហេតុ៖** env var `OMNIROUTE_WS_BRIDGE_SECRET` បាត់ពី production environment។

**ដំណោះស្រាយ៖**

1. បង្កើត secret ចៃដន្យ៖ `openssl rand -hex 32`
2. កំណត់ `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ក្នុង env របស់ production server (និង client ណាមួយដែលទាក់ទងជាមួយ bridge)
3. ចាប់ផ្ដើម OmniRoute ឡើងវិញ

### Responses API៖ background mode ត្រូវបានបន្ថយទៅជា synchronous

**រោគសញ្ញា៖**

- មានការកត់ត្រាការព្រមាន៖ `background mode degraded to synchronous`
- សំណើ `background: true` ត្រឡប់ synchronous response ធម្មតា ជំនួសឱ្យ background job handle

**មូលហេតុ៖** v3.8.0 បន្ថយ `background: true` នៅលើ Responses API ទៅជាការប្រតិបត្តិបែប synchronous ដោយចេតនា ខណៈពេលបញ្ចេញការព្រមាន។ ការប្រតិបត្តិ background បែប async ពេញលេញគឺជាមុខងារដែលនឹងផ្ដល់ជូននៅពេលអនាគត។

**ដំណោះស្រាយ៖**

- កែសម្រួល client ឱ្យហៅដោយគ្មាន `background` ឬ
- រង់ចាំការចេញផ្សាយនៅពេលក្រោយដែលផ្ដល់ background mode បែប async ពេញលេញ (តាមដាន changelog)

## ការចាប់ផ្ដើមយឺត / អស់ពេលរង់ចាំភាពរួចរាល់

ប្រសិនបើ CLI បង្ហាញ `⚠ Server did not respond within 60s` ប៉ុន្តែម៉ាស៊ីនមេ
កំពុងដំណើរការជាក់ស្ដែង នោះរយៈពេលកំណត់សម្រាប់ការត្រួតពិនិត្យភាពរួចរាល់ខ្លីពេកសម្រាប់បរិស្ថានរបស់អ្នក។

បញ្ហានេះកើតឡើងជាញឹកញាប់នៅលើ Windows (កម្មវិធីកម្ចាត់មេរោគ កម្មវិធីតាមដានប្រព័ន្ធឯកសារ) ឬកុងតឺន័រ
ដែលមានបន្ទុកការងារធ្ងន់នៅពេលចាប់ផ្ដើម។

**ដំណោះស្រាយ — បង្កើនរយៈពេលកំណត់៖**

```bash
# តាមរយៈអថេរបរិស្ថាន (រក្សាទុកនៅរាល់ការចាប់ផ្ដើម):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 នាទី
omniroute serve

# តាមរយៈទង់ CLI (ប្រើតែម្ដង):
omniroute serve --ready-timeout 180000
```

តម្លៃលំនាំដើមគឺ 60 000 ms (60 s)។ ការព្រមាននេះគ្រាន់តែជាព័ត៌មានប៉ុណ្ណោះ ម៉ាស៊ីនមេ
នៅតែបន្តចាប់ផ្ដើមនៅផ្ទៃខាងក្រោយ ហើយនឹងអាចចូលប្រើបាននៅពេលការចាប់ផ្ដើមបញ្ចប់។

សូមមើល [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) សម្រាប់ព័ត៌មានលម្អិតទាំងស្រុង
អំពី `OMNIROUTE_READY_TIMEOUT_MS`។
