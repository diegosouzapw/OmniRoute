មគ្គុទ្ទេសក៍នេះរៀបរាប់អំពីការបន្ថែមគណនី Kiro (ជំនួយការសរសេរកូដ AI ដែលបង្ហោះដោយ AWS) ទៅក្នុង OmniRoute
ដោយផ្តោតលើការដំណើរការគណនីច្រើនក្នុងពេលដំណាលគ្នា ដោយមិនមានការប៉ះទង្គិចរវាងសម័យ។

## មូលហេតុ៖ ហេតុអ្វីបានជាគណនី Kiro អាចប៉ះទង្គិចគ្នា

ប្រព័ន្ធ backend របស់ Kiro ប្រើការចុះឈ្មោះ client របស់ AWS SSO OIDC ដើម្បីតាមដានសម័យសកម្ម។
លក្ខខណ្ឌកំណត់សំខាន់គឺ៖ **ការចុះឈ្មោះ OIDC client នីមួយៗគាំទ្រសម័យសកម្មបានតែមួយ
ក្នុងពេលតែមួយប៉ុណ្ណោះ**។ នៅពេលឧបករណ៍ ឬអ្នកប្រើទីពីរផ្ទៀងផ្ទាត់អត្តសញ្ញាណដោយប្រើ
client ដែលបានចុះឈ្មោះដូចគ្នា ប្រព័ន្ធ backend នឹងធ្វើឱ្យ refresh token របស់គណនីទីមួយអស់សុពលភាព។

នេះជាយន្តការដូចគ្នាដែលបង្កបញ្ហានៅពេលដំណើរការ `kiro-cli login` លើ
ម៉ាស៊ីនដែលមានគណនី Kiro មួយផ្សេងទៀតបានចូលប្រើរួចហើយ — ការចូលថ្មីនឹងដកហូត
token របស់គណនីទីមួយ។

## របៀបដែល OmniRoute ដោះស្រាយបញ្ហានេះ (v3.8.0+)

ចាប់ពី v3.8.0 តទៅ OmniRoute ហៅ `registerClient()` (AWS SSO OIDC) ក្នុងអំឡុងពេលនាំចូល
ការតភ្ជាប់ Kiro រាល់លើក។ វាផ្តល់ឱ្យការតភ្ជាប់ OmniRoute នីមួយៗនូវការចុះឈ្មោះ OIDC
client ផ្ទាល់ខ្លួន។ ដោយសារការចុះឈ្មោះ client នីមួយៗឯករាជ្យពីគ្នា ការធ្វើ refresh ឬ
ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណឡើងវិញសម្រាប់គណនីមួយ នឹងមិនប៉ះពាល់ដល់ refresh token របស់គណនីផ្សេងទៀតទេ។

ភាពដាច់ដោយឡែកនេះអនុវត្តចំពោះវិធីនាំចូល refresh-token ខណៈដែលការផ្ទៀងផ្ទាត់អត្តសញ្ញាណតាម API-key
មិនប្រើសម័យ OIDC refresh ទាំងស្រុង៖

| វិធីនាំចូល                                       | ស្ថានភាពនៃភាពដាច់ដោយឡែក                                                                                          |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| លំហូរ device-code របស់ AWS Builder ID / IDC      | ដាច់ដោយឡែកចាប់តាំងពីលំហូរ device-code ត្រូវបានដាក់ឱ្យប្រើ                                                        |
| **នាំចូល Token** (បិទភ្ជាប់ refresh token ដោយដៃ) | ដាច់ដោយឡែកចាប់ពី v3.8.0                                                                                          |
| **ការចូលតាម Google / GitHub**                    | ដាច់ដោយឡែកចាប់ពី v3.8.0                                                                                          |
| **នាំចូលដោយស្វ័យប្រវត្តិ** (kiro-cli SQLite)     | ដាច់ដោយឡែកចាប់ពី v3.8.0 (ផ្លូវ SQLite ត្រូវបានបំបែករួចហើយ ហើយជម្រើសបម្រុង SSO-cache ឥឡូវនេះក៏ត្រូវបានបំបែកផងដែរ) |
| **API Key** (សោ CodeWhisperer ដែលមានអាយុកាលវែង)  | គ្មានសម័យ refresh ទេ; សោត្រូវបានផ្ទៀងផ្ទាត់ និងរក្សាទុកជាព័ត៌មានសម្គាល់អត្តសញ្ញាណប្រភេទ bearer                   |

## កំណត់ចំណាំអំពីការផ្ទេរសម្រាប់ការតភ្ជាប់ដែលបានបង្កើតមុន v3.8.0

ការតភ្ជាប់ដែលបាននាំចូលមុន v3.8.0 មិនមានការចុះឈ្មោះ OIDC client ផ្ទាល់ខ្លួន
ដែលបានរក្សាទុកក្នុង `providerSpecificData` ទេ។ ការតភ្ជាប់ទាំងនេះនៅតែបន្តដំណើរការ ប៉ុន្តែប្រើ
endpoint សម្រាប់ refresh នៃ social-auth រួមគ្នា ដែលមានន័យថាការតភ្ជាប់ពីរបែបនេះនៅតែអាចធ្វើឱ្យ
គ្នាទៅវិញទៅមកអស់សុពលភាពបាន។

**ដើម្បីទទួលបានភាពដាច់ដោយឡែក៖** លុបការតភ្ជាប់ចាស់ចេញពី **ផ្ទាំងគ្រប់គ្រង → អ្នកផ្តល់សេវា** ហើយ
នាំចូលវាឡើងវិញដោយប្រើលំហូរនាំចូលណាមួយដែលគាំទ្រ។ ការតភ្ជាប់ដែលបានបង្កើតថ្មីទាំងអស់នឹង
ទទួលបានការចុះឈ្មោះ client ផ្ទាល់ខ្លួនដោយស្វ័យប្រវត្តិ។

## ការបន្ថែមគណនី Kiro ពីរឱ្យដំណើរការទន្ទឹមគ្នា

### តម្រូវការជាមុន

- OmniRoute v3.8.0 ឬថ្មីជាងនេះ។
- គណនី Kiro ដែលដំណើរការ (អ៊ីមែល + ពាក្យសម្ងាត់ ឬការចូលតាម Google ឬ GitHub)។
- គណនី Kiro ទីពីរមួយទៀតជាជម្រើស។

### ជំហានទី 1៖ នាំចូលគណនីទីមួយ

1. បើក **ផ្ទាំងគ្រប់គ្រង → អ្នកផ្តល់សេវា → បន្ថែមអ្នកផ្តល់សេវា → Kiro**។
2. ជ្រើសរើសជម្រើសមួយក្នុងចំណោម៖
   - **នាំចូល Token** — បិទភ្ជាប់ refresh token ដែលចាប់ផ្តើមដោយ `aorAAAAAG`។
   - **API Key** — បិទភ្ជាប់ Kiro / CodeWhisperer API key ដែលមានអាយុកាលវែង។
   - **ការចូលតាម Google / GitHub** — បញ្ចប់លំហូរ OAuth ក្នុងកម្មវិធីរុករក។
   - **នាំចូលដោយស្វ័យប្រវត្តិ** — ចុចប៊ូតុង; OmniRoute អានព័ត៌មានសម្គាល់អត្តសញ្ញាណពី
     មូលដ្ឋានទិន្នន័យ kiro-cli ក្នុងម៉ាស៊ីន ឬ `~/.aws/sso/cache`។
3. ការតភ្ជាប់ត្រូវបានរក្សាទុក។ លំហូរ refresh-token នឹងចុះឈ្មោះ OIDC client
   ផ្ទាល់ខ្លួនដោយស្វ័យប្រវត្តិ។ លំហូរ API-key នឹងផ្ទៀងផ្ទាត់សោជាមួយ AWS ហើយមិនរក្សាទុក refresh token ទេ។

### ជំហានទី 2៖ នាំចូលគណនីទីពីរ

ធ្វើជំហានទី 1 ម្តងទៀតសម្រាប់គណនីទីពីរ។ ដោយសារការនាំចូលនីមួយៗបង្កើតការចុះឈ្មោះ OIDC
client ដាច់ដោយឡែក ការតភ្ជាប់ទាំងពីរត្រូវបានបំបែកពីគ្នាទាំងស្រុង។

### ជំហានទី 3៖ ផ្ទៀងផ្ទាត់ថាការតភ្ជាប់ទាំងពីរសកម្ម

1. **ផ្ទាំងគ្រប់គ្រង → អ្នកផ្តល់សេវា** — ការតភ្ជាប់ Kiro ទាំងពីរគួរបង្ហាញស្ថានភាព **សកម្ម**។
2. **ផ្ទាំងគ្រប់គ្រង → សុខភាពប្រព័ន្ធ** — ការតភ្ជាប់ទាំងពីរគួរឆ្លងកាត់ការត្រួតពិនិត្យសុខភាព token របស់វា។

### ជំហានទី 4៖ ប្រើ combo ដើម្បីបញ្ជូនរវាងគណនី

បង្កើត combo ដែលមានការតភ្ជាប់ទាំងពីរជាគោលដៅ ដើម្បីធ្វើតុល្យកម្មបន្ទុក ឬប្តូរទៅប្រើមួយទៀតនៅពេលមានបញ្ហា៖

```
kiro/kiro-dev → kiro/kiro-pro
```

## អ្នកប្រើប្រាស់សហគ្រាស / IDC

សម្រាប់គណនី AWS IAM Identity Center (IDC) សូមប្រើលំហូរ **AWS Builder ID / IDC device-code**
ពី **ផ្ទាំងគ្រប់គ្រង → អ្នកផ្តល់សេវា → Kiro → កូដឧបករណ៍**។ លំហូរ device-code
តែងតែត្រូវបានដាក់ឱ្យដំណើរការដាច់ដោយឡែកទាំងស្រុង។ មិនចាំបាច់នាំចូលឡើងវិញសម្រាប់ការតភ្ជាប់ទាំងនេះទេ។

អ្នកប្រើប្រាស់សហគ្រាសដែលដំណើរការនៅក្នុង AWS region ដែលមិនមែនជា region លំនាំដើម អាចបញ្ជាក់ region នៅពេល
នាំចូលតាមរយៈ Import Token API៖

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

វាល `region` មានតម្លៃលំនាំដើមជា `us-east-1` នៅពេលមិនបានបញ្ជាក់។

## លំហូរនាំចូលសោ API

ការផ្ទៀងផ្ទាត់ដោយសោ API គឺសម្រាប់ព័ត៌មានសម្ងាត់ bearer របស់ Kiro / AWS CodeWhisperer ដែលមានអាយុកាលវែង។ វា
មិនប្រើការធ្វើឱ្យ OAuth ស្រស់ឡើងវិញទេ ដូច្នេះវាជៀសវាងការធ្វើឱ្យ shared OIDC session អសុពលភាព។

### ផ្ទាំងគ្រប់គ្រង

1. បើក **ផ្ទាំងគ្រប់គ្រង -> អ្នកផ្តល់សេវា -> Kiro**។
2. ជ្រើសរើស **សោ API**។
3. បិទភ្ជាប់សោ API និង AWS region ដែលជាជម្រើស (`us-east-1` ជាលំនាំដើម)។
4. OmniRoute ផ្ទៀងផ្ទាត់សោ និងរក្សាទុកការតភ្ជាប់។

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### កិច្ចសន្យាផ្ទៃក្នុង

API route ផ្ទៀងផ្ទាត់សោដោយហៅ `KiroService.validateApiKey()` ដែល
ប្រើ `ListAvailableProfiles` ជាមួយ endpoint របស់ CodeWhisperer/Amazon Q ដែលត្រូវគ្នានឹង region និងកំណត់ `profileArn` មួយ។

ការតភ្ជាប់ដែលបានរក្សាទុកប្រើ៖

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

នៅពេលដំណើរការ `KiroExecutor.buildHeaders()` ផ្ញើសោជា
`Authorization: Bearer <key>` និងបន្ថែម `tokentype: API_KEY`។ ការហៅ quota/profile
ប្រើសញ្ញាសម្គាល់ដូចគ្នា ដើម្បីឱ្យ AWS ចាត់ទុក bearer នោះជាសោ API ដែលមានអាយុកាលវែង ជាជាង
OIDC ឬ social access token។

## ការផុតកំណត់របស់ OIDC Client

AWS SSO OIDC public clients ជាទូទៅផុតកំណត់បន្ទាប់ពី 90 ថ្ងៃ
(`clientSecretExpiresAt`)។ OmniRoute រក្សាទុក timestamp នេះក្នុង `providerSpecificData`
ដើម្បីងាយស្រួលតាមដាន។ ប្រសិនបើការតភ្ជាប់ឈប់ធ្វើឱ្យស្រស់ឡើងវិញបន្ទាប់ពីប្រហែល 90 ថ្ងៃ សូមនាំចូល
ការតភ្ជាប់ឡើងវិញ ដើម្បីទទួលបានការចុះឈ្មោះ OIDC client ថ្មី។ ការចុះឈ្មោះឡើងវិញដោយស្វ័យប្រវត្តិនៅពេល
ផុតកំណត់ ត្រូវបានកត់ត្រាទុកជាការកែលម្អនាពេលអនាគត។

ការតភ្ជាប់ដោយសោ API មិនមានការផុតកំណត់របស់ OIDC client ទេ ព្រោះវាមិនធ្វើឱ្យស្រស់ឡើងវិញ
តាមរយៈ AWS SSO OIDC។

## ការដោះស្រាយបញ្ហា

### គណនីទីពីរបន្តត្រូវបានដកចេញពីប្រព័ន្ធ

- ពិនិត្យការតភ្ជាប់ទាំងពីរក្នុង **ផ្ទាំងគ្រប់គ្រង → អ្នកផ្តល់សេវា** ហើយបញ្ជាក់ថា ការតភ្ជាប់នីមួយៗបង្ហាញ
  `clientId` ដែលមិនមែនជា null ក្នុង raw JSON របស់វា (អាចមើលឃើញតាមរយៈរូបតំណាងព័ត៌មាន)។ ប្រសិនបើការតភ្ជាប់ណាមួយខ្វះ
  `clientId` នោះវាត្រូវបាននាំចូលមុន v3.8.0 — សូមនាំចូលវាឡើងវិញ។

### ការនាំចូលបរាជ័យដោយសារ "ការផ្ទៀងផ្ទាត់ token បានបរាជ័យ"

- ត្រូវប្រាកដថា refresh token ចាប់ផ្តើមដោយ `aorAAAAAG`។
- ត្រូវប្រាកដថា OmniRoute អាចចូលដំណើរការ `https://oidc.us-east-1.amazonaws.com` (ឬ region ដែលបានកំណត់រចនាសម្ព័ន្ធ)។
  ប្រសិនបើអ្នកនៅពីក្រោយ corporate proxy សូមកំណត់ proxy នៅកម្រិតអ្នកផ្តល់សេវាក្នុង
  **ផ្ទាំងគ្រប់គ្រង → ការកំណត់ → Proxy**។

### ការនាំចូលសោ API បរាជ័យ

- បញ្ជាក់ថាសោនេះជាសោ API របស់ Kiro / CodeWhisperer មិនមែនជា refresh token ទេ។
- បញ្ជាក់ថា AWS region ត្រូវគ្នានឹងសោ/គណនី។ `us-east-1` គឺជាតម្លៃលំនាំដើម។
- សោត្រូវតែអាចហៅ `ListAvailableProfiles` បាន បើមិនដូច្នោះទេ OmniRoute មិនអាច
  កំណត់ `profileArn` ដែលត្រូវការបានទេ។

សម្រាប់បញ្ហាផ្សេងទៀត សូមមើលឯកសារចម្បង [TROUBLESHOOTING.md](./TROUBLESHOOTING.md)។
