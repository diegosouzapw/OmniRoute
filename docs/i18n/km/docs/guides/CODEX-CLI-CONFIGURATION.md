មគ្គុទ្ទេសក៍ពេញលេញសម្រាប់ការប្រើប្រាស់ Codex CLI ដែលភ្ជាប់ទៅ OmniRoute ជា backend ដែលឆបគ្នាជាមួយ OpenAI។

---

> **TOML គឺជាទម្រង់តែមួយគត់ដែលមានប្រសិទ្ធភាព។** Codex សម័យថ្មីអាន `~/.codex/config.toml`
> តែប៉ុណ្ណោះ (បានផ្ទៀងផ្ទាត់ជាមួយ codex-cli 0.147.0៖ `codex --help` ពណ៌នាថា
> `-c/--config` ជំនួសការកំណត់ដែល "បានផ្ទុកពី `~/.codex/config.toml`")។ ឯកសារចាស់
> `~/.codex/config.yaml` ជារបស់ npm CLI ជំនាន់ចាស់ ហើយត្រូវបានមិនអើពើដោយគ្មានការជូនដំណឹង។
> កម្មវិធីបង្កើតការកំណត់នៅលើ dashboard (`/api/cli-tools/apply`, ឧបករណ៍ `codex`) សរសេរ TOML
> ដោយប្រើការបញ្ចូលចូលគ្នាបែបប្រុងប្រយ័ត្ន — key ដែលមានស្រាប់ និង block របស់ provider ផ្សេងៗត្រូវបានរក្សាទុក,
> API key នៅតែស្ថិតក្នុង `OMNIROUTE_API_KEY` (មិនដែលដាក់ក្នុងឯកសារឡើយ) ហើយឯកសារចាស់
> `config.yaml` ដែលនៅសល់ នឹងត្រូវបានរាយការណ៍ជាកំណត់សម្គាល់អំពីការផ្លាស់ប្តូរ ដោយមិនប៉ះពាល់ដល់វា។

## config.toml ដែលអាចចម្លងទៅប្រើបានភ្លាមៗ

ជំនួស `<YOUR_HOST>` និង `<YOUR_KEY>` ដោយតម្លៃរបស់អ្នក៖

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # ចំនួនអតិបរមាសម្រាប់ការរក្សាទុកប្រវត្តិក្នុងការហៅឧបករណ៍នីមួយៗ

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc ឬ ~/.zshrc — តម្លៃ key ពិតប្រាកដ មិនត្រូវដាក់ក្នុង config.toml ឡើយ
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS៖ Codex ដែលបានរួមបញ្ចូលនៅក្នុងកម្មវិធី ChatGPT

ប្រសិនបើអ្នកបានដំឡើង Codex តាមរយៈកម្មវិធី ChatGPT លើ desktop នោះ binary `codex` អាច
មានតែនៅក្នុង app bundle ប៉ុណ្ណោះ ហើយមិនទាន់មាននៅលើ `PATH` របស់ shell អ្នកទេ។ បន្ថែម
ថត resources ទៅឯកសារចាប់ផ្ដើម shell របស់អ្នក៖

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

បើក shell ថ្មី បន្ទាប់មកផ្ទៀងផ្ទាត់៖

```bash
command -v codex
codex --version
```

### OmniRoute មូលដ្ឋានដែលមិនទាមទារការផ្ទៀងផ្ទាត់៖ key ជំនួសគឺគ្រប់គ្រាន់

Codex ផ្ទៀងផ្ទាត់ថា environment variable ដែលកំណត់ដោយ `env_key` មានវត្តមាន
**មុនពេល** request ដំបូងចាកចេញពី CLI។ ប្រសិនបើ instance OmniRoute **មូលដ្ឋាន** របស់អ្នក
មិនទាមទារការផ្ទៀងផ្ទាត់ទេ តម្លៃជំនួសណាមួយដែលមិនទទេនឹងដំណើរការ៖

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

ប្រើ key ពិតប្រាកដជំនួសវិញ នៅពេលម៉ាស៊ីនមេ OmniRoute របស់អ្នកត្រូវបានការពារ ឬស្ថិតនៅពីចម្ងាយ។

> **ជម្រើស host ទូទៅ**
>
> | ការចូលប្រើ     | URL                           |
> | -------------- | ----------------------------- |
> | បណ្តាញមូលដ្ឋាន | `http://192.168.0.1:20128/v1` |
> | Tailscale      | `http://100.x.x.x:20128/v1`   |
> | Loopback       | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — ហេតុអ្វីវាដំណើរការជាមួយគ្រប់ model

Codex CLI បានប្រកាសឈប់គាំទ្រ `wire_api = "chat"` (Chat Completions) នៅខែកុម្ភៈ ឆ្នាំ 2026 ហើយឥឡូវនេះ **ទាមទារ** `wire_api = "responses"` (OpenAI Responses API)។ ការកំណត់ `wire_api = "chat"` បណ្តាលឱ្យកម្មវិធីគាំងភ្លាមៗនៅពេលចាប់ផ្ដើម ចាប់តាំងពី v0.138។

Provider ជាច្រើន រួមទាំង GLM និង Kimi នៅតែផ្តល់តែ endpoint របស់ Chat Completions ប៉ុណ្ណោះ។ ឥឡូវនេះ DeepSeek V4 ផ្តល់ទាំង Responses API ដើម និង endpoint ដែលឆបគ្នាជាមួយ Anthropic ផងដែរ។ OmniRoute ប្រើ Responses ជាលំនាំដើម ហើយអនុញ្ញាតឱ្យ connection DeepSeek នីមួយៗជ្រើសរើសភាពឆបគ្នាជាមួយ Anthropic។

**OmniRoute ដោះស្រាយបញ្ហានេះដោយស្វ័យប្រវត្តិ និងដោយតម្លាភាព៖**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute ជ្រើសរើស protocol ដើមរបស់ provider ហើយបកប្រែនៅពេលចាំបាច់
    → POST /responses (DeepSeek V4) ឬ /chat/completions (Mistral / GLM / Kimi / ផ្សេងៗ)
```

អ្នកមិនចាំបាច់ប្រើ translation proxy ដាច់ដោយឡែកឡើយ នៅពេលប្រើ OmniRoute។ **គ្រប់ model ទាំងអស់ប្រើ `wire_api = "responses"`** — OmniRoute គ្រប់គ្រងផ្នែកដែលនៅសល់។

> **`wire_api` គឺជាតម្លៃលំនាំដើម** — field នេះមានតម្លៃលំនាំដើមជា `"responses"` ហើយអាចដកចេញទាំងស្រុងពី `config.toml`។ កំណត់វាឱ្យបានច្បាស់លាស់តែក្នុងករណីដែលអ្នកចង់ចងក្រងឯកសារបញ្ជាក់ពីគោលបំណងប៉ុណ្ណោះ។

## ផ្ទាំងបរិបទ និងការបង្រួម

### វាលកំណត់រចនាសម្ព័ន្ធថូខិន

| វាល                              | ការពិពណ៌នា                                                                                                                                                                                                  |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | ថវិកាថូខិនសរុបសម្រាប់ម៉ូដែលដែលកំពុងសកម្ម។ កំណត់ទៅតាមដែនកំណត់ដែលម៉ូដែលបានប្រកាស។                                                                                                                             |
| `model_auto_compact_token_limit` | កម្រិតដែលបង្កឱ្យមានការបង្រួមប្រវត្តិដោយស្វ័យប្រវត្តិ។ **អតិបរមា៖ 90% នៃ `model_context_window`** — តម្លៃលើសពី 90% នឹងត្រូវបានមិនអើពើដោយស្ងៀមស្ងាត់។                                                         |
| `tool_output_token_limit`        | កម្រិតថូខិនដែលត្រូវរក្សាទុកក្នុងប្រវត្តិសម្រាប់លទ្ធផលនៃការហៅឧបករណ៍នីមួយៗ។ វារារាំងមិនឱ្យការឆ្លើយតបដ៏ធំមួយពីឧបករណ៍បំពេញផ្ទាំងបរិបទទាំងមូល។ **នេះមិនមែនជាលទ្ធផលអតិបរមាទេ** — វាជាកម្រិតរក្សាទុកក្នុងប្រវត្តិ។ |
| `compact_prompt`                 | ការកំណត់ជំនួសក្នុងបន្ទាត់សម្រាប់ប្រអប់បញ្ចូលប្រព័ន្ធដែលប្រើអំឡុងពេលបង្រួម (v0.138+)។                                                                                                                        |

> **ចំណាំអំពី `model_max_output_tokens`**៖ វាលនេះ **មិនមែនជាផ្នែកនៃគ្រោងការកំណត់រចនាសម្ព័ន្ធ Codex CLI ទេ** (មិនមានក្នុងមូលដ្ឋានកូដ Codex Rust)។ ប្រសិនបើកំណត់វា វានឹងត្រូវបានមិនអើពើដោយស្ងៀមស្ងាត់។ កុំពឹងផ្អែកលើវា — ប្រើ `tool_output_token_limit` ដើម្បីគ្រប់គ្រងបរិមាណលទ្ធផលរបស់ឧបករណ៍ដែលត្រូវរក្សាទុកក្នុងប្រវត្តិ។

## កម្រិតប្រឹងប្រែងគិតវែកញែក

គ្រប់គ្រងថាតើម៉ូដែល «គិត» ច្រើនប៉ុនណាមុនពេលឆ្លើយតប។

| តម្លៃ    | ប្រើសម្រាប់                                      |
| -------- | ------------------------------------------------ |
| `none`   | គ្មានការគិតវែកញែក — ឆ្លើយតបដោយផ្ទាល់             |
| `low`    | កិច្ចការសាមញ្ញ (ប្តូរឈ្មោះ រៀបចំទ្រង់ទ្រាយ)      |
| `medium` | **លំនាំដើមរបស់ម៉ាស៊ីនមេ** នៅពេលមិនបានបញ្ជាក់     |
| `high`   | កិច្ចការកម្រិតមធ្យម (រៀបចំកូដឡើងវិញ បំបាត់កំហុស) |
| `xhigh`  | ស្ថាបត្យកម្ម ការវិភាគស៊ីជម្រៅ បញ្ហាស្មុគស្មាញ    |

```bash
# កំណត់ជំនួសសម្រាប់ការហៅម្តងៗ
codex -c model_reasoning_effort=low "ប្តូរឈ្មោះអថេរ x ទៅជា count"
codex -c model_reasoning_effort=xhigh "រចនាម៉ូឌុលផ្ទៀងផ្ទាត់អត្តសញ្ញាណ"
```

កំណត់ **សេចក្តីសង្ខេប** នៃការគិតវែកញែកផងដែរ ដើម្បីឱ្យ Desktop អាចបង្ហាញអត្ថបទនៃការគិតបាន (មិនមែនតែទិន្នន័យប្លុកដែលបានអ៊ិនគ្រីបប៉ុណ្ណោះ)៖

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # ឬ ultra នៅពេលមានការគាំទ្រ
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### ថវិកាការគិតរបស់ OmniRoute (ការកំណត់ម៉ាស៊ីនមេ)

នៅលើម៉ាស៊ីន OmniRoute **Settings → AI → Thinking Budget** ត្រូវតែកំណត់ជា **`passthrough`** ដើម្បីឱ្យកម្រិតប្រឹងប្រែង/សេចក្តីសង្ខេបរបស់ Codex បញ្ជូនទៅដល់សេវាខាងលើ។ របៀប **`auto` ដកចេញ** វាល `reasoning` / `reasoning_effort` ទាំងអស់ពីម៉ាស៊ីនភ្ញៀវ ហើយនឹងធ្វើឱ្យផ្ទាំងការគិតទទេ ទោះបីជា Codex ត្រូវបានកំណត់រចនាសម្ព័ន្ធត្រឹមត្រូវក៏ដោយ។

មគ្គុទ្ទេសក៍ពេញលេញ៖ [THINKING_BUDGET.md](./THINKING_BUDGET.md)។

ការបង្ហាប់ និងឃ្លាំងសម្ងាត់ prompt ឯករាជ្យពីគ្នា ហើយនៅតែដំណើរការក្រោម `passthrough`។

## បង្កើតប្រូហ្វាល់ដោយស្វ័យប្រវត្តិជាមួយ `omniroute setup-codex`

ប្រសិនបើអ្នកដំណើរការ OmniRoute លើ VPS អ្នកអាចបង្កើតឯកសារប្រូហ្វាល់ដោយស្វ័យប្រវត្តិពីកាតាឡុកម៉ូដែលដែលកំពុងប្រើប្រាស់ផ្ទាល់៖

```bash
# ពី VPS (ប្រើ OmniRoute មូលដ្ឋាននៅលើច្រក 20128)
omniroute setup-codex

# ពីម៉ាស៊ីនណាមួយ — ចង្អុលទៅ VPS របស់អ្នក
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# មើលជាមុនដោយមិនសរសេរឯកសារ
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# បង្កើតតែប្រូហ្វាល់ GLM និង Kimi
omniroute setup-codex --only glm,kimi

# សរសេរទៅកាន់ថតផ្ទាល់ខ្លួន
omniroute setup-codex --codex-home /path/to/.codex
```

ពាក្យបញ្ជានេះទាញយក `/v1/models` ប្រើប្រូហ្វាល់ដែលបានកែតម្រូវសម្រាប់ម៉ូដែលដែលស្គាល់ ប្រើទិន្នន័យមេតារបស់កាតាឡុកជំនួសសម្រាប់ម៉ូដែលអត្ថបទឆបគ្នាផ្សេងទៀត ហើយសរសេរ `~/.codex/<name>.config.toml` សម្រាប់ម៉ូដែលនីមួយៗ។ វាមានលក្ខណៈ idempotent — អាចដំណើរការម្តងទៀតបានដោយសុវត្ថិភាព។

OmniRoute ក៏អាចធ្វើ **សមកាលកម្មដោយស្វ័យប្រវត្តិ** លើឯកសារប្រូហ្វាល់ដូចគ្នាទាំងនេះ បន្ទាប់ពីការស្វែងរក/នាំចូលម៉ូដែលពីអ្នកផ្តល់សេវាបានជោគជ័យ និងធ្វើឱ្យកាតាឡុកដែលកំពុងប្រើប្រាស់ផ្ទាល់មានការផ្លាស់ប្តូរ។ មុខងារនេះត្រូវតែ **បើកប្រើដោយចេតនា ហើយបិទតាមលំនាំដើម**៖ បិទបើកវាពីផ្ទាំងគ្រប់គ្រង **CLI Code** ("CLI profile auto-sync" → Codex) ឬកំណត់ `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (វាក៏គោរពតាម `CLI_ALLOW_CONFIG_WRITES` ដែលបើកតាមលំនាំដើមផងដែរ)។ នៅពេលបើក វាសរសេរតែឯកសារប្រូហ្វាល់ `~/.codex/*.config.toml` ដាច់ដោយឡែកប៉ុណ្ណោះ។ វាមិនដែលផ្លាស់ប្តូរ `~/.codex/config.toml` ដែលសកម្ម/ជាលំនាំដើម ការកំណត់ Codex-lb ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ ឬការជ្រើសរើសអ្នកផ្តល់សេវាឡើយ។

### 1. ភាពស្និទ្ធសម័យ — ភ្ជាប់ការសន្ទនាមួយទៅគណនីមួយជាអចិន្ត្រៃយ៍

**លំនាំដើម៖** `sessionAffinityTtlMs = 0` (បានបិទ)។

**កន្លែងកំណត់វា**

- ផ្ទាំងគ្រប់គ្រង → **ការកំណត់ → ការកំណត់ផ្លូវ** → **ភាពស្និទ្ធសម័យ** → **TTL នៃភាពស្និទ្ធ (វិនាទី)** (`ComboDefaultsTab`)
- ឬ PATCH ការកំណត់ដោយប្រើ `sessionAffinityTtlMs` ជា **មិល្លីវិនាទី** (ជួរ Zod `0`–`86_400_000` ពោលគឺរហូតដល់ 24 ម៉ោង)

> បានប្តូរឈ្មោះក្នុង #7274 ពី `codexSessionAffinityTtlMs` ដែលសម្រាប់តែ Codex។ សោចាស់នៅតែត្រូវបានទទួលយកជាឈ្មោះក្លែងក្លាយសម្រាប់តែអានប៉ុណ្ណោះ; ការកំណត់រចនាសម្ព័ន្ធថ្មីគួរប្រើ `sessionAffinityTtlMs`។ ឥឡូវនេះ ភាពស្និទ្ធអនុវត្តចំពោះអ្នកផ្តល់សេវា **ណាមួយ** នៅពេល TTL ធំជាង `0` មិនមែនតែ Codex ទេ — មើល [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → ភាពស្និទ្ធសម័យ។

**អ្វីដែលខូចនៅពេលវានៅតែជា 0**

វេននីមួយៗនៃការសន្ទនា Codex ដែលមានច្រើនវេន ត្រូវបានកំណត់ផ្លូវដោយឯករាជ្យតាមយុទ្ធសាស្ត្របន្សំដែលសកម្ម ហើយអាចទៅដល់ **គណនីផ្សេងគ្នាក្នុងមួយវេន**។ វាធ្វើឱ្យភាពបន្តនៃសម័យ / ឃ្លាំងសម្ងាត់ប្រូមនៅខាងលើខូច។ OmniRoute ពិនិត្យមើលតែបឋមកថាសម័យ Codex (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) និងវាលក្នុងតួដូចជា `prompt_cache_key` / `session_id` នៅពេល TTL ធំជាង `0` (`extractSessionAffinityKey` ក្នុង `src/sse/services/auth.ts`)។

**បានណែនាំសម្រាប់កិច្ចការតែមួយដែលមានរយៈពេលច្រើនម៉ោង**

កំណត់ TTL ឱ្យ **លើសរយៈពេលជាក់ស្តែងដែលរំពឹងទុករបស់កិច្ចការ** (អតិបរមាក្នុង UI គឺ **86400 វិនាទី** = 24 ម៉ោង)៖

| រយៈពេលកិច្ចការដែលរំពឹងទុក | TTL នៃភាពស្និទ្ធ (UI, វិនាទី) | `sessionAffinityTtlMs` |
| ------------------------- | ----------------------------- | ---------------------- |
| ពីរបីម៉ោង                 | `14400` (4 ម៉ោង)              | `14400000`             |
| ពេញមួយយប់ / ~12 ម៉ោង      | `43200` (12 ម៉ោង)             | `43200000`             |
| ពេញមួយថ្ងៃ                | `86400` (24 ម៉ោង, អតិបរមា)    | `86400000`             |

ការជ្រើសចូលគឺធ្វើឡើងដោយចេតនា៖ ការបិទភាពស្និទ្ធផ្តល់អាទិភាពដល់ការធ្វើតុល្យកម្មបន្ទុកឆ្លងកាត់គណនីនានា; ការបើកវាផ្តល់អាទិភាពដល់ភាពបន្តសម្រាប់សម័យភ្នាក់ងារយូរមួយ។ មគ្គុទ្ទេសក៍នេះ **មិន** ផ្លាស់ប្តូរតម្លៃលំនាំដើមទេ — ប្រតិបត្តិករដែលដំណើរការកិច្ចការ Codex យូរ ត្រូវតែជ្រើសចូល។

### 2. អស់ពេលដោយសារស្ទ្រីមទំនេរ — កុំបញ្ឈប់វេនវិភាគដែលស្ងាត់

**លំនាំដើម៖** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 នាទី)។ វាទទួលតម្លៃបន្តពី `REQUEST_TIMEOUT_MS` នៅពេលមិនបានកំណត់; តម្លៃមូលដ្ឋានរួមក៏ជា 600000 ដែរ។ មើល [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → ការអស់ពេល។

**អ្វីដែលខូចនៅតម្លៃលំនាំដើម**

វេន reasoning / tool របស់ Codex ដែលស្ងាត់លើសពី 10 នាទីដោយ **មិនមាន upstream chunk ពិតប្រាកដ** នឹងត្រូវបានបិទដោយបង្ខំដោយ SSE idle watchdog (`open-sse/utils/stream.ts`)។ ជាញឹកញាប់ client ឃើញត្រឹមតែការផ្ដាច់ connection ដោយគ្មានសារអ្វីទាំងអស់ — ស្របគ្នានឹងរោគសញ្ញា “បានឈប់ដោយស្វ័យប្រវត្តិដោយគ្មានការជូនដំណឹងណាមួយ”។

ចំណុចសំខាន់៖ SSE **heartbeat សិប្បនិម្មិតរបស់ OmniRoute មិនកំណត់ idle clock ឡើងវិញទេ**។ មានតែ upstream body chunk ពិតប្រាកដប៉ុណ្ណោះដែលធ្វើបច្ចុប្បន្នភាព `lastChunkTime`។ តាមទស្សនៈរបស់ watchdog ម៉ូដែលស្ងាត់មួយដែលនៅតែ “កំពុងគិត” មើលទៅដូចគ្នាទាំងស្រុងនឹង upstream ដែលជាប់គាំង។

ទាក់ទងនឹង body inactivity របស់ Undici៖ `FETCH_BODY_TIMEOUT_MS` (តាមលំនាំដើម ក៏ប្រើ baseline 10 នាទីដូចគ្នាដែរ; `0` បិទវា)។ សម្រាប់ streaming, `FETCH_TIMEOUT_MS` គ្របដណ្ដប់តែលើការរៀបចំ connection / headers ដំបូងប៉ុណ្ណោះ — នៅពេល stream ដំណើរការ ការជាប់គាំងត្រូវបានគ្រប់គ្រងដោយ `STREAM_IDLE_TIMEOUT_MS` និង `FETCH_BODY_TIMEOUT_MS`។

**ការកំណត់ដែលបានណែនាំសម្រាប់ task តែមួយដែលដំណើរការច្រើនម៉ោង**

នៅក្នុង environment របស់ process OmniRoute (`.env` / compose / systemd)៖

```bash
# បិទការកាត់ផ្ដាច់ដោយសារ stream idle + body inactivity សម្រាប់វេន reasoning ដែលមានរយៈពេលយូរ
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

ឬដំឡើងតម្លៃទាំងនោះឱ្យខ្ពស់ជាងចន្លោះពេលស្ងាត់យូរបំផុតដែលអ្នករំពឹងទុក (តម្លៃគិតជា milliseconds)៖

```bash
# ឧទាហរណ៍៖ អនុញ្ញាតភាពស្ងាត់រហូតដល់ 2 ម៉ោងរវាង upstream chunks
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

ចាប់ផ្ដើម OmniRoute ឡើងវិញ បន្ទាប់ពីផ្លាស់ប្ដូរ env vars ទាំងនេះ។

### រូបមន្តជាក់លាក់ — task Codex ដែលដំណើរការច្រើនម៉ោង

1. **ចាក់សោ account៖** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12h) ឬ `86400` (អតិបរមា 24h)។
2. **ដំឡើង / បិទ idle cutoffs** នៅក្នុង environment របស់ OmniRoute៖

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. រក្សា Codex `config.toml` ធម្មតា (`wire_api = "responses"`, `base_url` ត្រឹមត្រូវ, `OMNIROUTE_API_KEY`) — មិនមានការកំណត់ affinity/idle នៅខាង Codex សម្រាប់ឥរិយាបថទាំងពីរនេះទេ។
4. ចាប់ផ្ដើម OmniRoute ឡើងវិញ បន្ទាប់មកចាប់ផ្ដើម task Codex ដែលដំណើរការយូរ។

### ការសម្រេចចិត្តអំពីតម្លៃលំនាំដើម (#7287)

### ការធ្វើរោគវិនិច្ឆ័យ idle cuts

នៅពេល idle watchdog ត្រូវបានកេះ OmniRoute កត់ត្រា log មួយបន្ទាត់ដែលមានទម្រង់ដូចនេះ៖

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

ប្រើ grep សម្រាប់ `Idle timeout: no data from` (ឬ code `stream_idle_timeout` / ឈ្មោះ error `StreamIdleTimeoutError`)។ ផ្នែក provider គឺជាអ្វីដែល OmniRoute បានប្រើសម្រាប់ request នោះ (`codex`, provider id ផ្សេងទៀត ឬ `provider` ប្រសិនបើមិនស្គាល់) — វាមិនមែនតែងតែជា string `codex` ដូចសរសេរនេះទេ។

Codex ផ្ទៀងផ្ទាត់ថា env var មាន មុនពេលធ្វើសំណើដំបូង។ Export
key ពិតប្រាកដសម្រាប់ server ដែលមានការការពារ ឬតម្លៃជំនួសដែលមិនទទេ ដូចជា
`OMNIROUTE_API_KEY=local` នៅពេល instance OmniRoute **local** របស់អ្នកមិន
តម្រូវឱ្យមានការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ។ ចាប់ផ្ដើម shell ឡើងវិញ ប្រសិនបើអ្នកបានបន្ថែមវាទៅក្នុង `~/.bashrc` ឬ `~/.zshrc`។

**`Connection refused`**
ផ្ទៀងផ្ទាត់ថា OmniRoute កំពុងដំណើរការ ហើយ host/port របស់ `base_url` ត្រឹមត្រូវសម្រាប់បណ្ដាញរបស់អ្នក (local ទល់នឹង Tailscale ទល់នឹង VPS)។

**Session គាំងនៅជិតកម្រិត context**
កំណត់ `model_context_window` និង `model_auto_compact_token_limit` ឱ្យច្បាស់លាស់។ មើលតារាង context window ខាងលើ។

**ការបង្រួមកើតឡើងយឺតពេក**
បន្ថយ `model_auto_compact_token_limit` មកត្រឹម 80–85% នៃ window។ កុំកំណត់លើសពី 90%។

**Profile មិនត្រូវបានផ្ទុក (`-p <name>` ត្រូវបានមិនអើពើដោយគ្មានសារ)**
បញ្ជាក់ថា file មាននៅ `~/.codex/<name>.config.toml` (គ្មាន prefix `profile-`)។ ដំណើរការ `ls ~/.codex/*.config.toml`។

**Task Codex ដែលដំណើរការយូរត្រូវបានផ្ដាច់ពាក់កណ្ដាល / ប្ដូរ account រវាង turn**
មើល [Task ដែលដំណើរការយូរ](#long-running-tasks)។ បើក session affinity (TTL ឱ្យវែងជាងរយៈពេល task) ហើយបង្កើន ឬបិទ `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`។ ប្រើ grep លើ log របស់ OmniRoute ដើម្បីស្វែងរក `Idle timeout: no data from`។
