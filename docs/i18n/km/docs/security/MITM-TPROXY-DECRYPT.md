ដោយប្រើ TPROXY របស់ kernel + policy routing — **ដោយមិន** ក្លែងបន្លំ `/etc/hosts` និង
**ដោយមិន** កែប្រែការកំណត់ system proxy ទូទាំង OS។ វាស័ក្តិសមសម្រាប់ការដំណើរការដោយគ្មានផ្ទៃអន្តរកម្ម
(មិនមានការកែប្រែ DNS ដែលត្រូវសម្អាត) ហើយច្បាប់ firewall នឹងត្រូវបានលុបដោយស្វ័យប្រវត្តិនៅពេលចាប់ផ្ដើមម៉ាស៊ីនឡើងវិញ។

ខុសពីរបៀបចាប់យកផ្សេងទៀត TPROXY មិនត្រូវការការរៀបចំដាច់ដោយឡែកសម្រាប់ host នីមួយៗទេ៖ វាស្ទាក់ចាប់ដោយតម្លាភាព
នូវ host គោលដៅ **ណាមួយ** នៅលើ port គោលដៅ បញ្ចប់ TLS ដោយប្រើ
leaf certificate ដែលវាចេញភ្លាមៗសម្រាប់ SNI hostname នីមួយៗ ចាប់យកការផ្លាស់ប្ដូរទិន្នន័យដែលបានឌិគ្រីប
ហើយអ៊ិនគ្រីប request ឡើងវិញទៅកាន់គោលដៅដើម។

> **សម្រាប់តែ Linux, សម្រាប់តែ root និងត្រូវជ្រើសបើក។** របៀបនេះត្រូវការ Linux, native addon

> នៅពីក្រោយ AgentBridge API ដែលអនុញ្ញាតតែ loopback និងត្រូវបានបិទតាមលំនាំដើម។ MITM CA ដែលគួរឱ្យទុកចិត្ត
> និងអាចចុះហត្ថលេខាឱ្យ host ណាមួយបាន គឺជាសមត្ថភាពដ៏មានឥទ្ធិពល — សូមមើល [§6 សុវត្ថិភាព](#6-security)។

## §1 វាជាអ្វី និងពេលណាត្រូវប្រើវា

របៀបចាប់យកបួនផ្សេងទៀត សុទ្ធតែមានដែនកំណត់រៀងៗខ្លួន៖

| របៀប              | របៀបបញ្ជូនទិសចរាចរណ៍                                     | ដែនកំណត់                                                        |
| ----------------- | -------------------------------------------------------- | --------------------------------------------------------------- |
| AgentBridge       | ការក្លែងបន្លំ DNS តាម `/etc/hosts` សម្រាប់ក្រុម host ថេរ | សម្រាប់តែ IDE-agent host ដែលបានចុះឈ្មោះ                         |
| Custom Hosts      | ការក្លែងបន្លំ DNS តាម `/etc/hosts` សម្រាប់ host នីមួយៗ   | មួយ entry សម្រាប់ host នីមួយៗ; ត្រូវការ sudo ដើម្បីកែប្រែ hosts |
| HTTP_PROXY        | env `HTTP_PROXY`/`HTTPS_PROXY`                           | សម្រាប់តែ app ដែលគោរពតាម env var                                |
| System-wide proxy | ការកំណត់ proxy របស់ OS                                   | កែប្រែ global state; ត្រូវការត្រឡប់ការកំណត់ដើម                  |

TPROXY transparent decrypt បញ្ជូនទិសចរាចរណ៍នៅស្រទាប់ **kernel** ជំនួសវិញ។ វា
ដាក់សម្គាល់ការតភ្ជាប់ TCP ចេញពីម៉ាស៊ីនមូលដ្ឋានថ្មីៗទៅកាន់ port គោលដៅ (លំនាំដើម `443`) នៅក្នុង
`mangle OUTPUT` chain ហើយ `ip rule` មួយបញ្ជូន packet ដែលបានដាក់សម្គាល់ទៅកាន់ការបញ្ជូនក្នុងម៉ាស៊ីនមូលដ្ឋានឡើងវិញ
និងនៅពេលចូលឡើងវិញ `TPROXY` target របស់ `mangle PREROUTING` នឹងប្រគល់វាទៅកាន់
listener **IP_TRANSPARENT** — ដែលបន្ទាប់មកបញ្ចប់ TLS និងចាប់យក plaintext។

ប្រើវានៅពេលអ្នកចង់ចាប់យក និងឌិគ្រីបចរាចរណ៍ពី process ដែល៖

- ទាក់ទងទៅកាន់ host ដែល AgentBridge មិនបានចុះឈ្មោះ និង
- មិនគោរពតាម `HTTP_PROXY` និង
- អ្នកមិនចង់រំខានវាដោយការផ្លាស់ប្ដូរ system-wide proxy។

ដោយសារការស្ទាក់ចាប់កើតឡើងក្នុង kernel process ដើម **មិនត្រូវការ
ការផ្លាស់ប្ដូរការកំណត់រចនាសម្ព័ន្ធ** ទេ — ប៉ុន្តែ process នោះត្រូវតែទុកចិត្ត dynamic CA ដែល OmniRoute
ដំឡើង (សូមមើល [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer))។

## §3 Native IP_TRANSPARENT addon

ម៉ូឌុល `net` របស់ Node មិនអាចហៅ `setsockopt(IP_TRANSPARENT)` _មុនពេល_ `bind()` បានទេ ដែល
TPROXY តម្រូវឱ្យធ្វើដូច្នោះ (បើមិនដូច្នេះទេ kernel នឹងទម្លាក់ packet ដែលបានបញ្ជូនប្ដូរទិស)។ Addon
(`src/mitm/tproxy/native/transparent.c` ដែល build តាមរយៈ `binding.gyp`) គឺជាម៉ូឌុល N-API
តូចមួយដែលបញ្ចេញ function ចំនួនបី ហើយត្រូវបានប្រើតាមរយៈ `transparentSocket.ts`៖

| Function របស់ addon                   | ប្រតិបត្តិការ socket                                                                        | ប្រើសម្រាប់                                                                  |
| ------------------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()` ហើយត្រឡប់ raw fd | transparent capture listener (Node ទទួលយក fd តាមរយៈ `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | `setsockopt` **SO_MARK** លើ fd ដែលមានស្រាប់                                                 | ការទប់ស្កាត់ loop (ដាក់ mark លើ socket របស់ proxy ផ្ទាល់)                    |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **មុនពេល** `connect()` ដែលមិនបិទខ្ទប់ ហើយត្រឡប់ fd                 | ការបញ្ជូនបន្តទៅ upstream ដែលបានអ៊ិនគ្រីបឡើងវិញ (SYN ផ្ទុក mark)              |

គោលដៅដើមត្រូវបានអានពី `socket.localAddress`/`localPort` — TPROXY
រក្សាវាទុក ដូច្នេះមិនត្រូវការការស្វែងរក **SO_ORIGINAL_DST**/NAT ទេ។

## §4 CA ឌីណាមិកតាម SNI និងកម្មវិធីដំឡើង trust store

> **បច្ចុប្បន្នភាព #6684:** ម៉ាស៊ីនមេស្ថិតិរបស់ AgentBridge (`src/mitm/server.cjs`) ឥឡូវនេះ
> ប្រើគំរូស្ថាបត្យកម្ម CA/leaf ដូចគ្នានេះ ជំនួសឱ្យ leaf ដែលចុះហត្ថលេខាដោយខ្លួនឯង
> និងមានលក្ខណៈស្ថិតិតែមួយ។ វាប្រើអង្គភាព CA **ដាច់ដោយឡែក**
> (`src/mitm/cert/rootCa.ts` ដែលរក្សាទុកនៅ `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> ហើយដំឡើងនៅក្នុងចន្លោះ trust store ដែលមានស្រាប់ឈ្មោះ `omniroute-mitm.crt`
> (ជំនួស leaf តែមួយចាស់នៅទីនោះ — មិនចាំបាច់សម្អាតការជឿទុកចិត្តពីរទេ)
> ដោយរក្សាវាឱ្យដាច់ដោយឡែកទាំងស្រុងពីចន្លោះ `omniroute-tproxy-ca.crt` ផ្ទាល់របស់ TPROXY
> ដែលមាននៅខាងក្រោម។ ការដំឡើង AgentBridge ថ្មីទទួលបានម៉ូដែល CA ដោយស្វ័យប្រវត្តិ;
> ការដំឡើងដែលបានជឿទុកចិត្តលើ leaf ស្ថិតិចាស់រួចហើយ នឹងបន្តប្រើវារហូតដល់
> អ្នកប្រតិបត្តិការជ្រើសរើសចូលប្រើតាមរយៈ `MITM_ROOT_CA_ENABLED=true`
> (មើល `src/mitm/cert/migration.ts`) — MITM CA ដែលត្រូវបានជឿទុកចិត្ត និងអាច
> ចុះហត្ថលេខាលើ leaf សម្រាប់ម៉ាស៊ីន **ណាមួយ** មានអំណាចខ្លាំងជាង leaf ដែលមាន
> SAN ថេរចាស់យ៉ាងសំខាន់ ដូច្នេះការប្តូរនេះមិនដែលកើតឡើងដោយស្ងាត់ស្ងៀមឡើយ
> សម្រាប់ការដំឡើងដែលបានជឿទុកចិត្តរួចហើយ។

ជាប្រវត្តិសាស្ត្រ វិញ្ញាបនបត្រ MITM ស្ថិតិរបស់ AgentBridge ដំណើរការបានតែដោយសារ
AgentBridge ក្លែងបន្លំ DNS សម្រាប់សំណុំ host **ថេរ** មួយ (ឥឡូវបានបង្រួមបញ្ចូល
ជាមួយម៉ូដែលខាងក្រោម)។ TPROXY ស្ទាក់ចាប់ host **ដោយសេរី** ដូច្នេះ listener របស់វា
ត្រូវតែបង្ហាញ leaf ដែលមានសុពលភាពសម្រាប់ SNI ណាមួយដែល client ស្នើសុំ —
ដែលជាតម្រូវការដូចគ្នាដែល AgentBridge មាននៅពេលនេះ សម្រាប់សំណុំ
`MITM_TOOL_HOSTS` ទាំងមូល (ធាតុឧបករណ៍ចំនួន 9) ជំនួសឱ្យត្រឹមតែ host
antigravity ចំនួន 4។

### CA ឌីណាមិក (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` ដំណើរការ CA មូលដ្ឋានមួយ (បង្កើតឡើងដោយផ្អែកលើ dependency
`selfsigned`) ដែល៖

- បង្កើត CA ដែលមានអាយុកាលវែងតាមរយៈ `generateMitmCa()` (CN `"OmniRoute MITM CA"`,
  សុពលភាព 10 ឆ្នាំ, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  RSA 2048-bit / SHA-256)។
- ចេញ **leaf មួយសម្រាប់ hostname SNI នីមួយៗតាមតម្រូវការ** តាមរយៈ
  `issueLeafCert()` (សុពលភាព 1 ឆ្នាំ, `subjectAltName` = host SNI) និងរក្សាទុក
  `tls.SecureContext` មួយក្នុង cache សម្រាប់ hostname នីមួយៗ។
- ផ្តល់ `createSNICallback()` សម្រាប់ម៉ាស៊ីនមេដែលបញ្ចប់ TLS
  (មើល [§5](#5-how-decrypt-and-capture-work))។
- អាចត្រូវបានបង្កើតជាមួយ `existingCa` ដើម្បីរក្សា CA ឱ្យមានស្ថិរភាពក្រោយពេល
  ចាប់ផ្តើមឡើងវិញ (ដូច្នេះ trust store មិនចាំបាច់ដំឡើងឡើងវិញទេ)។

សោឯកជនរបស់ CA **មិនដែលចាកចេញពីម៉ាស៊ីនឡើយ**។

### កម្មវិធីដំឡើង trust store (`src/mitm/tproxy/caTrust.ts`)

client ដែលត្រូវបានស្ទាក់ចាប់ ត្រូវតែជឿទុកចិត្តលើ CA ឌីណាមិក ដូច្នេះការចាប់ផ្តើម
របៀប capture នឹងដំឡើងវិញ្ញាបនបត្រ CA ទៅក្នុង trust store របស់ OS ក្រោម
**ចន្លោះដាច់ដោយឡែក** — `omniroute-tproxy-ca.crt` (ថេរ
`TPROXY_CA_CERT_NAME`) — ដែលត្រូវបានរក្សាឱ្យដាច់ពីចន្លោះវិញ្ញាបនបត្រ MITM ស្ថិតិ
(`omniroute-mitm.crt`) ដើម្បីកុំឱ្យទាំងពីរសរសេរជាន់គ្នា។

`installTproxyCa(caPem, sudoPassword?)` រកឃើញថត anchor របស់ distro
(តាមលំដាប់៖ រចនាប័ទ្ម Debian មុន) ហើយដំណើរការពាក្យបញ្ជា refresh ដែលត្រូវគ្នា៖

| ថត Anchor                                   | ពាក្យបញ្ជា Refresh       |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

ការដំឡើងដាក់ PEM ជាបណ្តោះអាសន្នទៅក្នុងឯកសារ temp បន្ទាប់មកប្រើសិទ្ធិខ្ពស់
ដើម្បីដំណើរការ `mkdir -p` លើថត anchor, ប្រើ `cp` ដើម្បីចម្លងឯកសារដែលបានរៀបចំ
ចូលទៅក្នុងនោះ ហើយដំណើរការពាក្យបញ្ជា refresh។ `uninstallTproxyCa()`
លុបតែចន្លោះដាច់ដោយឡែកប៉ុណ្ណោះ (ដោយទុកវិញ្ញាបនបត្រ MITM ស្ថិតិឱ្យនៅដដែល)
ហើយធ្វើ refresh — វាមិនធ្វើអ្វីទាំងអស់នៅលើប្រព័ន្ធដែលមិនមែនជា Linux។

ពាក្យបញ្ជាដែលត្រូវការសិទ្ធិខ្ពស់ទាំងអស់ ដំណើរការតាមរយៈ `execFileWithPassword`
(`src/mitm/systemCommands.ts`) — `spawn` ជាមួយ **អារេ argument, គ្មាន shell,
គ្មាន string interpolation** (វិធានតឹងរ៉ឹង #13)។ នៅពេល process ដំណើរការជា root
(ឧ. VPS) target នឹងដំណើរការដោយផ្ទាល់ ហើយមិនត្រូវការពាក្យសម្ងាត់ទេ;

`sudo -S` នៅលើ stdin។

## §5 របៀបដែលការឌិគ្រីប និងការចាប់យកដំណើរការ

បំពង់ដំណើរការ (ទាំងអស់ស្ថិតនៅក្រោម `src/mitm/tproxy/`)៖

```
កម្មវិធីមូលដ្ឋាន  ──TCP/443──▶  mangle OUTPUT ដាក់សញ្ញាសម្គាល់លើការតភ្ជាប់ (fwmark)
                                 ip rule → តារាងផ្លូវមូលដ្ឋាន → lo
                                 mangle PREROUTING TPROXY → IP_TRANSPARENT listener (port 8443)
                                     │  captureMode.ts: អានគោលដៅដើមពី socket.localAddress
                                     ▼
                                 tlsCapture.ts:
                                   1. បញ្ចប់ TLS របស់ CLIENT ដោយប្រើ leaf តាម SNI នីមួយៗ (dynamicCert)
                                   2. http.Server ខាងក្នុងញែកទិន្នន័យ plaintext ដែលបានឌិគ្រីប
                                   3. ចាប់យក → globalTrafficBuffer.push() ជាមួយ source: "tproxy"
                                      (បានអនុវត្ត sanitizeHeaders + maskSecret)
                                   4. បញ្ជូនបន្តដោយអ៊ិនគ្រីបឡើងវិញទៅគោលដៅដើម
                                      តាមរយៈ socket ដែលមានសញ្ញាសម្គាល់រំលង (connectMarked, ប្រឆាំងរង្វិលជុំ)
                                     │
                                     ▼
                                 upstream ដើម (api.example.com)
```

- **ការបញ្ចប់ TLS** (`createTlsCaptureServer`)៖ រុំ socket ឆៅដែលបានស្ទាក់ចាប់
  ក្នុង `tls.TLSSocket` ផ្នែកម៉ាស៊ីនមេ ដោយប្រើ callback SNI របស់ CA ថាមវន្ត
  បន្ទាប់មកប្រគល់ស្ទ្រីមដែលបានឌិគ្រីបទៅឱ្យ `http.Server` ខាងក្នុង (បច្ចេកទេសបញ្ចប់ MITM
  ស្តង់ដារ)។ អាយុកាលរបស់ socket ត្រូវបានកំណត់ដោយ `MITM_IDLE_TIMEOUT_MS` ដើម្បីកុំឱ្យ
  tunnel ដែលជាប់គាំងអាចប្រើ file descriptor អស់។
- **ការចាប់យក** (`handleDecryptedRequest`)៖ បញ្ចូល `InterceptedRequest` មួយដែលមាន
  `source: "tproxy"` ស្ថានភាពចាប់ផ្ដើមជា `"in-flight"` ហើយ headers ត្រូវបានដំណើរការតាម
  `sanitizeHeaders()` និង bodies តាម `maskSecret()` មុនពេលវាចូលទៅក្នុង
  buffer។ បន្ទាប់មក ធាតុនោះត្រូវបានធ្វើបច្ចុប្បន្នភាពជាមួយ response ទំហំ និង latency។
- **ការបញ្ជូនបន្តដែលបានអ៊ិនគ្រីបឡើងវិញ** (`createForward` / `realForward`)៖ អ៊ិនគ្រីបឡើងវិញទៅកាន់
  គោលដៅដើម។ `rejectUnauthorized` មានតម្លៃលំនាំដើមជា **`true`** (មានសុវត្ថិភាពតាម
  លំនាំដើម) — cert របស់ upstream ត្រូវបានផ្ទៀងផ្ទាត់ធៀបនឹង SNI/Host ដែល client
  បានស្នើ ដូច្នេះ proxy នឹងបដិសេធអ្វីដែល client ដើមក៏នឹងបដិសេធដូចគ្នា។

### ការប្រឆាំងរង្វិលជុំ (SO_MARK)

ដោយសារតែ rules ដាក់សញ្ញាសម្គាល់លើការតភ្ជាប់ outbound មូលដ្ឋានថ្មី ការបញ្ជូនបន្តដែលបាន
អ៊ិនគ្រីបឡើងវិញរបស់ proxy **ផ្ទាល់** ជាធម្មតានឹងត្រូវបានស្ទាក់ចាប់ម្ដងទៀត — បង្កើតជា
រង្វិលជុំគ្មានទីបញ្ចប់។ ផ្លូវបញ្ជូនបន្តការពារបញ្ហានេះដោយប្រើសញ្ញាសម្គាល់ socket សម្រាប់រំលង
(**SO_MARK**)៖

- `realForward` បើក socket ទៅ upstream តាមរយៈ `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  — `DEFAULT_BYPASS_MARK = 0x539` — ដែលកំណត់ **SO_MARK** **មុនពេល** `connect()`
  ដូច្នេះ SYN របស់ការបញ្ជូនបន្តមានសញ្ញាសម្គាល់រំលង។
- rule `mangle OUTPUT` មិនរាប់បញ្ចូលការតភ្ជាប់ដែលមានសញ្ញាសម្គាល់រំលងរួចហើយ
  (`-m mark ! --mark <bypassMark>`) ដូច្នេះការបញ្ជូនបន្តរបស់ proxy **មិន** ត្រូវបានដាក់សញ្ញាសម្គាល់
  ម្ដងទៀត ហើយក៏មិនចូលទៅក្នុង TPROXY ឡើងវិញដែរ។

> កំណត់សម្គាល់អំពីការអនុវត្ត៖ socket ដែលមានសញ្ញាសម្គាល់រំលងត្រូវតែដំឡើងលើ
> `createConnection` របស់ agent (`https.request({ createConnection })` ត្រូវបានមិនអើពើ
> ដោយស្ងៀមស្ងាត់ នៅពេលមាន agent) បើមិនដូច្នោះទេ ការបញ្ជូនបន្តនឹងបើក socket ដែលគ្មាន
> សញ្ញាសម្គាល់ ហើយរង្វិលជុំនឹងត្រឡប់មកវិញ។ នេះជាការកែបញ្ហាប្រឆាំងរង្វិលជុំដែលបានផ្ទៀងផ្ទាត់ដោយ e2e។

## §7 ការអនុវត្ត / ត្រឡប់វិញនៃ firewall ជាប្រតិបត្តិការ

ការគាំងមិនត្រូវបន្សល់ទុក rule `mangle` ឬ route ចាស់ណាមួយឡើយ។ កម្មវិធីបង្កើត command
(`src/mitm/tproxy/commands.ts`) និងកម្មវិធីដំណើរការ (`src/mitm/tproxy/setup.ts`) ធានាថា
**ការត្រឡប់វិញគឺជាប្រតិបត្តិការបញ្ច្រាសពិតប្រាកដនៃការអនុវត្ត តាមលំដាប់បញ្ច្រាស**។

`applyTproxy(cfg)` ដំណើរការ command អនុវត្តតាមលំដាប់។ នៅពេលមានការបរាជ័យ **ណាមួយ** វានឹងដំណើរការ
`revertTproxy(cfg)` ពេញលេញតាមដែលអាចធ្វើបាន ហើយបោះកំហុសឡើងវិញ — ដូច្នេះ firewall នឹងត្រូវបាន
អនុវត្តទាំងស្រុង ឬត្រឡប់វិញទាំងស្រុង មិនដែលអនុវត្តបានត្រឹមពាក់កណ្ដាលឡើយ។ `revertTproxy(cfg)` ដំណើរការ
command បញ្ច្រាសតាមលំដាប់បញ្ច្រាស ហើយមិនបញ្ជូនការបរាជ័យបន្តទេ (មានលក្ខណៈ idempotent — អាចហៅបាន
ដោយគ្មានលក្ខខណ្ឌ ឧ. ពីការសម្អាត `repairMitm()` របស់ AgentBridge)។

`validateTproxyConfig(cfg)` ដំណើរការមុន command ណាមួយ៖ port ត្រូវស្ថិតក្នុងចន្លោះ `1–65535`,
`mark`/`routeTable`/`bypassMark` ត្រូវតែជាចំនួនគត់វិជ្ជមាន ហើយ `bypassMark` ត្រូវតែ
ខុសពី `mark` (ការពារ loop)។

### Command សម្រាប់អនុវត្ត (តាមលំដាប់)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

ការត្រឡប់វិញលុបពួកវាតាមលំដាប់បញ្ច្រាស៖ `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`។

> រូបមន្តនេះផ្អែកលើ **OUTPUT** ព្រោះករណីប្រើប្រាស់ MITM គឺជា traffic ចេញ _មូលដ្ឋាន_
> (កម្មវិធីនៅលើ host ដូចគ្នា) ដែល TPROXY នៅក្នុង `PREROUTING` តែឯងមិនអាចមើលឃើញ
> បានទេ — `PREROUTING` មើលឃើញតែ traffic ដែលត្រូវបានបញ្ជូនបន្តប៉ុណ្ណោះ។ chain `OUTPUT` ដាក់សញ្ញាសម្គាល់
> លើ connection មូលដ្ឋានថ្មីៗ `ip rule` បង្វែរផ្លូវពួកវាទៅការបញ្ជូនមូលដ្ឋាន (`lo`) ហើយ
> បន្ទាប់មក `PREROUTING` កំណត់ពួកវាទៅ listener ថ្លា។

   - ប្រសិនបើវាត្រូវបាន **បិទ** ដោយមាន tooltip "ការឌិគ្រីប TPROXY តម្រូវឱ្យមាន Linux + root +
     native addon" នោះ native addon មិនមាននៅលើម៉ាស៊ីននេះទេ (មិនមែន Linux,
     គ្មាន toolchain ឬ addon មិនទាន់បាន build)។ សូមមើល [§2](#2-requirements) និង [§3](#3-the-native-ip_transparent-addon)។
3. ចុចប៊ូតុង។ វាហៅ `POST /api/tools/agent-bridge/tproxy` តាមរយៈ
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`) ដែល៖
   បង្កើត CA ថាមវន្ត បើក listener ថ្លា អនុវត្តច្បាប់ firewall
   និងដំឡើង CA ទៅក្នុង trust store របស់ OS។
4. នៅពេលកំពុងដំណើរការ toggle នឹងប្រែជាពណ៌លឿងទុំ ហើយបង្ហាញចំនួន intercept ផ្ទាល់
   (`· <interceptCount>`)។ សំណើដែលបាន intercept នឹងបង្ហាញក្នុងបញ្ជីសំណើជាមួយ
   `source: "tproxy"`។
5. ចុចម្ដងទៀតដើម្បីបញ្ឈប់ — `DELETE /api/tools/agent-bridge/tproxy` តាមរយៈ
   `stopTproxyCaptureMode()` នឹងបិទ listener លុបការដំឡើង CA និងត្រឡប់
   ច្បាប់ firewall ទៅសភាពដើមវិញ។

ស្ថានភាព capture-mode (កំពុងដំណើរការ / អាចប្រើបាន / ចំនួន intercept / port របស់ listener) មកពី
`GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` នៅក្នុង
`src/mitm/tproxy/captureManager.ts`)។ អាចមាន session TPROXY តែ **មួយ** ប៉ុណ្ណោះដែលដំណើរការក្នុងពេលតែមួយ —
ការចាប់ផ្ដើម session ទីពីរនឹងត្រូវបានបដិសេធជាមួយសារ "capture mode របស់ TPROXY កំពុងដំណើរការរួចហើយ"។

## §10 ការដោះស្រាយបញ្ហា

### Toggle ត្រូវបានបិទ

មិនអាច load native addon បានទេ។ សូមបញ្ជាក់ថា៖ អ្នកកំពុងប្រើ Linux, អ្នកបាន build addon
(`npm run build:native:tproxy`) ហើយ process អាច load `transparent.node` បាន។
`isTransparentSocketAvailable()` គ្រប់គ្រង toggle; `GET /api/tools/agent-bridge/tproxy`
ត្រឡប់ `available: false` នៅពេល addon បាត់។

### គ្មានអ្វីត្រូវបាន capture

- បញ្ជាក់ថា process ដែលត្រូវបាន intercept ពិតជាភ្ជាប់ទៅ `dport` ដែលបានកំណត់
  (លំនាំដើម `443`)។
- បញ្ជាក់ថា process ជឿទុកចិត្ត CA ថាមវន្ត។ CA ត្រូវបានដំឡើងក្រោមឈ្មោះ
  `omniroute-tproxy-ca.crt`; កម្មវិធីដែលមាន trust store ផ្ទាល់ខ្លួន (Firefox/Chrome NSS)
  ប្រហែលជាត្រូវបន្ថែមវិញ្ញាបនបត្រនៅទីនោះផងដែរ។
- ដំណើរការ self-test **Diagnose** របស់ AgentBridge (សូមមើល
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) សម្រាប់ការពិនិត្យវិញ្ញាបនបត្រដែលបានទុកចិត្ត / សុខភាព
  server។

### ច្បាប់ firewall ចាស់ៗនៅសល់បន្ទាប់ពី crash

`revertTproxy()` គឺជាប្រតិបត្តិការបញ្ច្រាសទាំងស្រុងនៃការអនុវត្ត ហើយមានលក្ខណៈ idempotent។ ការបញ្ឈប់
mode នឹងត្រឡប់ច្បាប់ទៅសភាពដើមវិញ; ប្រសិនបើ OmniRoute ត្រូវបានបញ្ឈប់ដោយបង្ខំនៅពាក់កណ្ដាល session សូមប្រើសកម្មភាព
**Repair** របស់ AgentBridge (`POST /api/tools/agent-bridge/repair`) ដើម្បីមិនធ្វើសភាពប្រព័ន្ធ
ដែលនៅសេសសល់ (DNS spoof, root CA, system proxy)។ ច្បាប់ `mangle` និង route របស់ TPROXY ក៏
ត្រូវបានសម្អាតដោយស្វ័យប្រវត្តិផងដែរនៅពេល reboot។

### រង្វិលជុំគ្មានទីបញ្ចប់ / proxy intercept ការ forward របស់ខ្លួនឯង

នេះគឺជាករណី anti-loop។ បញ្ជាក់ថា `bypassMark` ខុសពី `mark` (validation
តម្រូវឱ្យដូច្នេះ) ហើយការ forward ប្រើ `connectMarked` (វាប្រើនៅក្នុង `realForward`)។
សូមមើល [§5 Anti-loop](#anti-loop-so_mark)។
