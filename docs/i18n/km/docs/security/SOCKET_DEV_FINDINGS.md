1. ឱ្យប្រតិបត្តិករបំពង់ដំណើរការសុវត្ថិភាពមានឯកសារយោងតែមួយសម្រាប់ដកស្រង់ នៅពេលពួកគេត្រូវការ
   វាយតម្លៃលទ្ធផលរកឃើញទាំងនេះធៀបនឹងកូដប្រភពជាក់ស្តែង។
2. ឱ្យម៉ាស៊ីនស្កេន AI នាពេលអនាគតអាចរកឃើញការអះអាងដែលចុះហត្ថលេខាដោយអ្នកថែទាំថា
   ផ្លូវដែលត្រូវបានសម្គាល់នីមួយៗគឺមានចេតនា ជាជម្រើសដែលត្រូវបើកប្រើ និងមានឯកសារពន្យល់ច្បាស់លាស់។
3. ឱ្យយើងមានកំណត់ត្រាជាលាយលក្ខណ៍អក្សរអំពី _មូលហេតុ_ ដែលទីតាំងហៅនីមួយៗត្រូវបានរៀបចំតាមរបៀបនេះ —
   ដើម្បីកុំឱ្យការកែលម្អរចនាសម្ព័ន្ធកូដនាពេលអនាគតបង្កើតលក្ខណៈសម្គាល់ដែល
   ត្រូវបានដកចេញដោយចេតនាឡើងវិញដោយអចេតនា។

ប្រសិនបើអ្នកដំណើរការម៉ាស៊ីនស្កេនដែលសម្គាល់ទីតាំងហៅណាមួយខាងក្រោមឡើងវិញ បន្ទាប់ពី

## §1 — ការដំឡើង root-CA សម្រាប់ MITM (`77484.js`)

**ឯកសារប្រភព**៖

- `src/mitm/cert/install.ts` — `installCert()` / `uninstallCert()` សាធារណៈ
  និង `installCertWindows/Mac/Linux` សម្រាប់វេទិកានីមួយៗ។
- `src/mitm/systemCommands.ts` — កម្មវិធីជំនួយ `execFile` / `spawn` / PowerShell រួម
  ដែលប្រើដោយផ្លូវដំឡើងទាំងនេះ។

**ការបង្កឱ្យដំណើរការ**៖ អ្នកប្រើចុច "បើកប្រូកស៊ី MITM" ក្នុងផ្ទាំងគ្រប់គ្រងមូលដ្ឋាននៅ
`/dashboard/cli-tools/mitm`។ ផ្លូវនេះអាចចូលប្រើបានតែតាម loopback ប៉ុណ្ណោះ — សូមមើលច្បាប់តឹងរ៉ឹងលេខ 17 ក្នុង
`CLAUDE.md` និង `src/server/authz/routeGuard.ts::isLocalOnlyPath()`។ JWT ដែលលេចធ្លាយ
តាមរយៈ tunnel **មិនអាច** បង្កឱ្យផ្លូវកូដនេះដំណើរការបានទេ។

**ប្រតិបត្តិការដែលទាមទារសិទ្ធិខ្ពស់ (តាមវេទិកានីមួយៗ)**៖

| ប្រព័ន្ធប្រតិបត្តិការ  | ពាក្យបញ្ជា                                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | `certutil -addstore Root <cert>` តាមរយៈ UAC                                                                       |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | ការធ្វើបច្ចុប្បន្នភាព NSS DB តាម profile នីមួយៗ តាមរយៈ `certutil -d sql:<profile>`                                |

ទាំងនេះគឺជាពាក្យបញ្ជាដូចគ្នាដែលប្រើដោយ `mitmproxy`, Charles Proxy, Fiddler និង
Caddy។ ការដែលពាក្យបញ្ជាទាំងនេះមានក្នុង OmniRoute ត្រូវបានកត់ត្រានៅ
`docs/security/STEALTH_GUIDE.md`។

**វិធានការកាត់បន្ថយក្នុង v3.8.6**៖

- `runElevatedPowerShell()` លែងប្រើ `-EncodedCommand <base64utf16le>` ទៀតហើយ។
  payload ដែលត្រូវដំណើរការដោយសិទ្ធិខ្ពស់ ត្រូវបានសរសេរទៅក្នុងឯកសារ `.ps1` បណ្ដោះអាសន្នសម្រាប់ការហៅនីមួយៗ (mode 0o600,
  នៅក្នុងថតឯកជន `mkdtempSync`) ហើយត្រូវបានយោងតាមរយៈ `-File`។ ឯកសារ
  ត្រូវបានលុបតំណក្នុង `finally`។ ការនេះដកចេញនូវលក្ខណៈសម្គាល់បែបគំរូស្តង់ដារនៃ
  ការដំឡើងសិទ្ធិខ្ពស់តាមរយៈ PowerShell ដោយប្រើ base64 ដែលត្រូវបានសម្គាល់ដោយកម្មវិធីចាត់ថ្នាក់ AI របស់ Socket.dev។
- `installCertWindows` មានប្លុក `SECURITY-AUDITOR-NOTE:` ក្នុងបន្ទាត់កូដ
  ដែលចង្អុលមកទីនេះ។

**មូលហេតុដែលយើងរក្សាវាទុក**៖ ប្រូកស៊ី MITM គឺជាមុខងារដែលមានឯកសារពន្យល់ និងត្រូវបានប្រើដោយ
`docs/security/STEALTH_GUIDE.md` និង `docs/frameworks/MITM-PROXY.md`។ ការដកវាចេញ

## §2 — ការនាំចូលព័ត៌មានសម្ងាត់ពី Zed (`app/api/providers/zed/import/route.js`)

**ឯកសារប្រភព**៖

- `src/app/api/providers/zed/discover/route.ts` _(ថ្មីក្នុង v3.8.6)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(ថ្មីក្នុង v3.8.6)_

**ការកេះដំណើរការ**៖ អ្នកប្រើចុច "នាំចូលពី Zed" នៅលើទំព័រ Providers ក្នុងផ្ទាំងគ្រប់គ្រងមូលដ្ឋាន។ Endpoint នេះត្រូវបានការពារដោយ `requireManagementAuth`។ កម្មវិធីកែសម្រួល Zed ខ្លួនវាផ្ទាល់សរសេរ provider API keys របស់វាទៅកាន់ keychain របស់ OS ក្រោមឈ្មោះ service ដែលមានឯកសារបញ្ជាក់ — សូមមើល https://zed.dev/docs/ai/llm-providers។

**ឥរិយាបថរបស់ v3.8.5 (កំណែដែល Socket.dev បានដាក់ទង់សម្គាល់)**៖

`POST /import` បានស្វែងរកព័ត៌មានសម្ងាត់ និងរក្សាទុកពួកវាដោយស្វ័យប្រវត្តិទៅក្នុងឃ្លាំង SQLite មូលដ្ឋាន ដោយប្រើការផ្ញើ-ត្រឡប់តែមួយលើក។ មិនមានការបញ្ជាក់តាមគណនីនីមួយៗ មិនមាន fingerprint ទេ មានតែ "បានរកឃើញ token ចំនួន N ហើយបាននាំចូលទាំងអស់។"

**ការកាត់បន្ថយហានិភ័យក្នុង v3.8.6 — ការបញ្ជាក់ 2 ជំហាន**៖

1. **`POST /api/providers/zed/discover`** ត្រឡប់
   `{ candidates: [{ provider, service, account, fingerprint }] }`។ token ដើម
   **មិនដែល** ត្រូវបានបញ្ជូនឡើយ។ fingerprint គឺ
   `sha256(service|account|token).slice(0,16)`។
2. ផ្ទាំងគ្រប់គ្រងបង្ហាញបញ្ជី candidate ហើយប្រតិបត្តិករជ្រើសរើសអ្វីដែលត្រូវ
   នាំចូល រួចផ្ញើ `{ confirmedAccounts: [{ service, account, fingerprint }] }`
   ទៅកាន់ **`POST /api/providers/zed/import`**។
3. Endpoint សម្រាប់នាំចូល **អាន keychain ឡើងវិញនៅលើ server** និងត្រងតាម
   `(service, account, fingerprint)`។ response របស់ discover ដែលត្រូវបានកែបន្លំ
   ឬចាក់ឡើងវិញ មិនអាចបញ្ឆោត endpoint សម្រាប់នាំចូលឱ្យរក្សាទុក token ដែលមិនពាក់ព័ន្ធបានទេ —
   ប្រសិនបើ token បច្ចុប្បន្នបានផ្លាស់ប្តូរចាប់តាំងពីការស្វែងរក នោះ fingerprint នឹងលែង
   ត្រូវគ្នា ហើយព័ត៌មានសម្ងាត់នោះនឹងត្រូវបានរំលង។

env flag `OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` រក្សាឥរិយាបថរបស់ v3.8.5
សម្រាប់ប្រតិបត្តិករដែលមិនទាន់បានធ្វើបច្ចុប្បន្នភាពស្វ័យប្រវត្តិកម្មរបស់ពួកគេ។ វានឹងត្រូវបាន
ដកចេញក្នុង v3.9។

**មូលហេតុដែលយើងរក្សាវាទុក**៖ ការនាំចូលពី Zed គឺជាវិធីចាប់ផ្ដើមប្រើប្រាស់ដែលងាយស្រួលបំផុតសម្រាប់អ្នកប្រើ

## §5 — ការសរសេរព័ត៌មានសម្ងាត់ត្រឡប់ទៅ OmniRoute Cloud Sync (`api/keys/[id]/route.js`)

**ឯកសារប្រភព**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`។
- `src/app/api/keys/[id]/route.ts` — ហៅ `syncKeysToCloudIfEnabled()`។

**លក្ខខណ្ឌបង្ក**: `isCloudEnabled()` ត្រឡប់ `true` (កំណត់ពីផ្ទាំងគ្រប់គ្រង) **និង**
`CLOUD_URL` ត្រូវបានកំណត់រចនាសម្ព័ន្ធ។ នៅពេលទាំងពីរត្រូវបានបិទ វាមិនធ្វើការហៅបណ្ដាញចេញទៅកាន់
Cloud endpoint ទេ។

**ឥរិយាបថ v3.8.5 (កំហុសដែល Socket.dev បានរកឃើញតាមវិធីត្រឹមត្រូវ)**:

`updateLocalTokens()` បានសរសេរជាន់លើ `accessToken`, `refreshToken` និង
`providerSpecificData` ពីការឆ្លើយតបរបស់ Cloud នៅពេល
`cloudUpdatedAt > localUpdatedAt`។ គ្មាន HMAC គ្មានហត្ថលេខា និងគ្មាន checksum។ `CLOUD_URL`
ដែលបានកំណត់រចនាសម្ព័ន្ធខុស ឬមានចេតនាព្យាបាទ (ឬ MITM នៅលើឆានែល) អាចប្ដូរ
OAuth token របស់ provider ដោយស្ងៀមស្ងាត់។

**ការកាត់បន្ថយហានិភ័យក្នុង v3.8.6**:

1. **ការផ្ទៀងផ្ទាត់ HMAC**: `verifyCloudSignature(rawBody, sigHeader)` ផ្ទៀងផ្ទាត់
   header `X-Cloud-Sig` (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`) មុនពេល parse JSON។ ប្រសិនបើ secret ត្រូវបានកំណត់ ហត្ថលេខាគឺជា
   តម្រូវការចាំបាច់។ បើមិនបានកំណត់ទេ (របៀប legacy) ការព្រមានមួយនឹងត្រូវបានកត់ត្រា ហើយការឆ្លើយតបនឹងត្រូវបាន
   ទទួលយក — secret នឹងក្លាយជាតម្រូវការចាំបាច់ក្នុង v3.9។
2. **ការជ្រើសរើសចូលសម្រាប់វាលសម្ងាត់**: `accessToken` / `refreshToken` /
   `providerSpecificData` ត្រូវបានសរសេរជាន់លើ **តែនៅពេល**
   `OMNIROUTE_CLOUD_SYNC_SECRETS=true` ប៉ុណ្ណោះ។ របៀបលំនាំដើមធ្វើសមកាលកម្មតែ
   metadata ដែលមិនមែនជាព័ត៌មានសម្ងាត់ (`expiresAt`, `status`, `lastError*`,
   `rateLimitedUntil`, `updatedAt`)។ នេះគឺជា **ការផ្លាស់ប្ដូរដែលមិនឆបគ្នាជាមួយកំណែមុន** សម្រាប់អ្នកប្រើ
   ដែលបានពឹងផ្អែកលើការធ្វើសមកាលកម្ម token ពីចម្ងាយ — ពួកគេត្រូវតែជ្រើសរើសចូលដោយជាក់លាក់។

**ហេតុអ្វីយើងរក្សាវា**: Cloud Sync គឺជាមធ្យោបាយតែមួយគត់សម្រាប់ OmniRoute Cloud tenant
ក្នុងការប្រមូលផ្ដុំព័ត៌មានសម្ងាត់របស់ក្រុមនៅកន្លែងតែមួយ។ ការកែតម្រូវនេះធ្វើឱ្យគំរូគំរាមកំហែងមានភាពត្រឹមត្រូវ៖
"server ចុះហត្ថលេខា, client ផ្ទៀងផ្ទាត់, operator ជ្រើសរើសចូល។"
