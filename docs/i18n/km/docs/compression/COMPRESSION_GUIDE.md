## ទិដ្ឋភាពទូទៅ

OmniRoute អនុវត្ត pipeline បង្ហាប់ prompt បែបម៉ូឌុល ដែលដំណើរការ **ជាមុន** មុនពេលសំណើទៅដល់ provider ខាងលើ។ នេះមានន័យថា ការសន្សំ token របស់អ្នកកើតឡើងដោយតម្លាភាព — មិនចាំបាច់ផ្លាស់ប្តូរ workflow របស់អ្នកទេ។

```
សំណើរបស់ Client
  → កម្មវិធីជ្រើសរើសយុទ្ធសាស្ត្របង្ហាប់
    → មានការកំណត់ combo ជំនួសឬ? → ប្រើការកំណត់ combo
    → ដល់កម្រិតកេះស្វ័យប្រវត្តិឬ? → ប្រើ mode ស្វ័យប្រវត្តិ
    → mode លំនាំដើមឬ? → ប្រើការកំណត់សកល
    → បិទឬ? → រំលងការបង្ហាប់
  → Mode បង្ហាប់ដែលបានជ្រើសរើស
    → បិទ: គ្មានការបង្ហាប់
    → ស្រាល: សម្អាតចន្លោះ/ទ្រង់ទ្រាយដោយសុវត្ថិភាព (~15%)
    → ស្តង់ដារ: លុបពាក្យបំពេញបែប Caveman (~30%)
    → ខ្លាំង: ធ្វើឱ្យប្រវត្តិចាស់ + សង្ខេប (~50%)
    → អតិបរមា: កាត់ចេញដោយ heuristic + សម្រួល code block (~75%)
    → RTK: ចម្រោះលទ្ធផល terminal/tool ដោយយល់ដឹងពី command (ចន្លោះ 60-90% ខាង upstream)
    → ជង់: pipeline ម៉ាស៊ីនច្រើនតាមលំដាប់ ជាធម្មតា RTK បន្ទាប់មក Caveman (ចន្លោះ 78-95% សម្រាប់ទិន្នន័យដែលមានសិទ្ធិ)
  → សំណើដែលបានបង្ហាប់ → Provider
```

## Mode បង្ហាប់

### បិទ

មិនអនុវត្តការបង្ហាប់ទេ។ សារទាំងអស់ឆ្លងកាត់ដោយមិនមានការផ្លាស់ប្តូរ។

### Mode ស្រាល (សន្សំ ~15%, latency <1ms)

Mode ដែលមានសុវត្ថិភាពបំផុត — គ្មានការផ្លាស់ប្តូរអត្ថន័យទេ មានតែការសម្អាតទ្រង់ទ្រាយប៉ុណ្ណោះ៖

| បច្ចេកទេស                | ការពិពណ៌នា                                     |
| ------------------------ | ---------------------------------------------- |
| `collapseWhitespace`     | បញ្ចូលបន្ទាត់ទទេជាប់ៗគ្នា និងលុបចន្លោះនៅខាងចុង |
| `dedupSystemPrompt`      | លុបសារ system ដែលស្ទួន                         |
| `compressToolResults`    | បង្ហាប់លទ្ធផល tool/function ដែលវែងអន្លាយ       |
| `removeRedundantContent` | ដកការណែនាំដែលសរសេរដដែលៗ                        |
| `replaceImageUrls`       | បង្រួម URI ទិន្នន័យរូបភាព base64               |

**ស័ក្តិសមបំផុតសម្រាប់៖** ការប្រើប្រាស់ជាប់ជានិច្ច និង workflow ដែលផ្តោតសំខាន់លើសុវត្ថិភាព។

### Mode ស្តង់ដារ (សន្សំ ~30%)

បានបំផុសគំនិតដោយ [Caveman](https://github.com/JuliusBrussee/caveman) — លុបពាក្យបំពេញ និងឃ្លាវែងអន្លាយ ខណៈពេលរក្សាអត្ថន័យ៖

- លុបពាក្យបំពេញ ("សូម", "ខ្ញុំគិតថា", "ជាទូទៅ", "តាមពិត")
- បង្រួមឃ្លាវែងអន្លាយ ("ដើម្បីធ្វើការ" → "ដើម្បី", "ជាលទ្ធផលនៃ" → "ព្រោះ")
- ដកឃ្លាបន្ធូរបន្ថយបែបគួរសម ("តើអ្នកយល់ទាស់ទេ...", "ប្រសិនបើអ្នកអាចធ្វើបាន...")
- ច្បាប់ regex ច្រើនជាង 30 ដែលបានសម្រួលសម្រាប់ prompt សរសេរកូដ

**ស័ក្តិសមបំផុតសម្រាប់៖** workflow សរសេរកូដប្រចាំថ្ងៃ និងក្រុមដែលយកចិត្តទុកដាក់លើការចំណាយ។

### Mode ខ្លាំង (សន្សំ ~50%)

ការគ្រប់គ្រងប្រវត្តិឆ្លាតវៃសម្រាប់ session រយៈពេលវែង៖

- **ការធ្វើឱ្យសារចាស់** — សារចាស់ៗត្រូវបានបង្ហាប់កាន់តែច្រើនជាបន្តបន្ទាប់
- **ការបង្ហាប់លទ្ធផល Tool** — លទ្ធផល tool វែងៗត្រូវបានកាត់ឱ្យខ្លី ឬលុបចេញ (បន្ទាត់ដំបូង/ចុងក្រោយ,
  ការចម្រោះបន្ទាត់ដែលត្រូវគ្នា និងការបង្រួម key របស់ JSON)
- **របាំងការពារសុចរិតភាពរចនាសម្ព័ន្ធ** — ធានាថាគូ `tool_use` + `tool_result` នៅតែស៊ីសង្វាក់គ្នា
- **ការយល់ដឹងអំពី Context Window** — គោរពដែនកំណត់ token របស់ model នីមួយៗ

**ស័ក្តិសមបំផុតសម្រាប់៖** session បំបាត់កំហុសរយៈពេលវែង និង codebase ធំៗ។

### Mode អតិបរមា (សន្សំ ~75%)

ការបង្ហាប់អតិបរមាសម្រាប់ស្ថានភាពដែល token មានសារៈសំខាន់ខ្លាំង៖

- **ការកាត់ចេញដោយ Heuristic** — កាត់ token ចេញពីអត្ថបទពិពណ៌នា ដោយផ្អែកលើពិន្ទុ
- **ការរក្សារចនាសម្ព័ន្ធ** — fenced code block, inline code, URL និង identifier ត្រូវបាន
  ដាក់ជំនួសដោយសញ្ញាសម្គាល់ ហើយផ្គុំត្រឡប់វិញទាំងស្រុង ដោយមិនត្រូវបានកាត់ចេញឡើយ
- **ថ្នាក់ SLM ជាជម្រើស** — model មូលដ្ឋានតូចមួយអាចកែលម្អការកាត់ចេញ នៅពេលបានកំណត់រចនាសម្ព័ន្ធ
- ឯករាជ្យពី mode ខ្លាំង៖ វាមិនដំណើរការការធ្វើឱ្យសារចាស់ ការបង្ហាប់លទ្ធផល tool
  ឬកម្មវិធីសង្ខេប fallback ទេ (មានតែកំហុសនៅថ្នាក់ SLM ប៉ុណ្ណោះដែលអាចបញ្ជូន fallback pass តាម
  mode ខ្លាំង)

**ស័ក្តិសមបំផុតសម្រាប់៖** នៅពេលអ្នកឈានដល់ដែនកំណត់ context ម្តងហើយម្តងទៀត។

### Mode RTK (ចន្លោះ 60-90% ខាង upstream)

Mode RTK ត្រូវបានធ្វើឱ្យប្រសើរសម្រាប់លទ្ធផល tool វែងអន្លាយ ដែលបង្ហាញក្នុង session របស់ coding agent៖

- រកឃើញប្រភេទ command/output ដូចជា `git status`, `git diff`, `git log`, test runner,
  build របស់ TypeScript/Vite/Webpack, ESLint/Biome/Prettier, npm audit/ការដំឡើង, log របស់ Docker, លទ្ធផល infra
  និងលទ្ធផល shell ទូទៅ
- អនុវត្តកញ្ចប់ចម្រោះ JSON ពី `open-sse/services/compression/engines/rtk/filters/`
- នាំចូល filter របស់ RTK TOML schema v1 ពីឯកសារ `filters.toml` របស់ project ឬសកល ដោយមាន
  ការផ្ទៀងផ្ទាត់ inline test និងការគ្រប់គ្រងតាមកម្រិតទុកចិត្តសម្រាប់ឯកសារ project
- ភ្ជាប់មកជាមួយ filter ស្រាប់ចំនួន 55 ដែលមានគំរូផ្ទៀងផ្ទាត់ inline
- លុប sequence គ្រប់គ្រង ANSI, progress bar, បន្ទាត់ស្ទួន និងទិន្នន័យរំខានដែលមិនអាចអនុវត្តសកម្មភាពបាន
- រក្សាទុកភាពបរាជ័យ កំហុស ការព្រមាន ឯកសារដែលបានផ្លាស់ប្តូរ សេចក្តីសង្ខេប និងផ្នែកចុងនៃលទ្ធផលវែងៗ

## គណនាវិធីសាស្ត្រសន្សំ Upstream

OmniRoute កត់ត្រាការសន្សំពីការបង្ហាប់ដែលបានមកពីប្រភពពីរ៖ លទ្ធផលសាកល្បងសមត្ថភាពរបស់គម្រោង upstream និង
ការផ្គុំ engine ផ្ទាល់របស់ OmniRoute។

| ប្រភព   | លេខពី README របស់ upstream ដែលប្រើនៅទីនេះ                                                                                     |
| ------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Caveman | output token តិចជាង `~75%`, ការសន្សំ output ជាមធ្យម `65%` ពីការសាកល្បងសមត្ថភាព, ចន្លោះ `22-87%` និងឧបករណ៍បង្ហាប់ input `~46%` |
| RTK     | ការសន្សំ command-output `60-90%`; session គំរូ `~118,000 -> ~23,900` tokens ឬសន្សំបាន `79.7%` (`~80%`)                        |

សម្រាប់ payload របស់ tool/context ដែលត្រួតស៊ីគ្នា combo លំនាំដើមរបស់ OmniRoute ដាក់ engine បន្តគ្នា៖

```txt
RTK -> Caveman
```

ការសន្សំរួមត្រូវគុណគ្នា មិនមែនបូកគ្នាទេ៖

```txt
រួម     = 1 - (1 - ការសន្សំ RTK) * (1 - ការសន្សំ input របស់ Caveman)
មធ្យម   = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
ចន្លោះ  = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

លេខ `78-95%` នោះអនុវត្តនៅពេលដែលទាំង RTK និង Caveman អាចកាត់បន្ថយ input/context payload ដូចគ្នា។
របៀប response output របស់ Caveman គឺដាច់ដោយឡែក៖ នៅពេលបើកវា សូមប្រើការសន្សំ output ផ្ទាល់របស់ Caveman (`65%`
ជាមធ្យម, `~75%` ជាតួលេខសំខាន់, ចន្លោះ `22-87%`)។ ការសន្សំថ្លៃប្រើប្រាស់សរុបអាស្រ័យលើសមាមាត្រ prompt/output របស់អ្នក។

វាមានអាទិភាពខ្ពស់បំផុត — វាមានអាទិភាពលើការកំណត់ជំនួសរបស់បន្សំការកំណត់ទិស profile ដែលសកម្ម
ការចាប់ផ្តើមស្វ័យប្រវត្តិ និង Default របស់ panel។ តម្លៃមិនស្គាល់ត្រូវបានមិនអើពើ (សំណើមិនត្រូវបានបដិសេធឡើយ) ហើយ
កុងតាក់មេសកលនៅតែគ្រប់គ្រងអ្វីៗទាំងអស់៖ នៅពេលការបង្ហាប់ត្រូវបានបិទជាសកល header មិនអាច
បើកវាបានទេ។ តម្លៃ៖

| តម្លៃ         | ផលប៉ះពាល់                                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------- |
| `off`         | មិនមានការបង្ហាប់សម្រាប់សំណើនេះទេ។                                                                          |
| `default`     | profile Default ដែលបានមកពី panel (មិនអើពើ profile ដែលសកម្ម)។ engine ដែលបាត់បង់ទិន្នន័យត្រូវបានបិទ។         |
| `safe`        | ដូចគ្នានឹងការមិនបញ្ចូល header៖ មានតែការលុបទិន្នន័យស្ទួន និងការបង្រួមចន្លោះទទេប៉ុណ្ណោះ។                     |
| `allow-lossy` | រក្សាផែនការរបស់ operator សម្រាប់សំណើនេះ រួមទាំងសេចក្តីសង្ខេប តម្រងភាពពាក់ព័ន្ធ និងការសរសេររចនាប័ទ្មឡើងវិញ។ |
| `engine:<id>` | engine តែមួយនៅពេលបានបើក ឧ. `engine:rtk`។ នេះគឺជាការយល់ព្រមប្រើ engine នោះតាមសំណើ។                          |
| `<combo>`     | បន្សំដែលមានឈ្មោះ ដោយផ្គូផ្គងតាមឈ្មោះជាមុនសិន (មិនប្រកាន់តួអក្សរធំតូច) បន្ទាប់មកតាម id។                     |

បើគ្មាន `allow-lossy`, `engine:<id>` ឬបន្សំដែលមានឈ្មោះទេ engine ដែលបាត់បង់ទិន្នន័យនឹងមិនត្រូវបានអនុវត្តឡើយ។
សំណើនៅតែទទួលបានការលុបទិន្នន័យស្ទួនតាម session និងការបង្រួមចន្លោះទទេ នៅពេលការបង្ហាប់ត្រូវបានបើក។

ផែនការដែលបានអនុវត្តត្រូវបានឆ្លុះតបវិញនៅក្នុង header ឆ្លើយតប `X-OmniRoute-Compression: <mode>; source=<source>`
ដែល `<source>` គឺជាតម្លៃមួយក្នុងចំណោម `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default` ឬ `off`។

### ការបង្ហាប់ដែលយល់ដឹងអំពីឃ្លាំងសម្ងាត់

Providers មួយចំនួន (ដូចជា Anthropic ដែលមាន prompt caching) គាំទ្រ **prompt caching**
ដែលអនុញ្ញាតឱ្យពួកគេរក្សាទុកផ្នែកខ្លះនៃ prompt ក្នុង cache ដើម្បីកាត់បន្ថយការចំណាយ និងភាពយឺតយ៉ាវ។ នៅពេល
បើក caching ការបង្ហាប់បែប aggressive អាចធ្វើឱ្យប្រសិទ្ធភាព **អន់ថយ** បាន
ព្រោះវាផ្លាស់ប្ដូរថូខឹនដែលបានរក្សាទុកក្នុង cache ដែលធ្វើឱ្យ cache លែងមានសុពលភាព។

ម៉ូឌុល `cachingAware.ts` ដោះស្រាយបញ្ហានេះដោយ **រកឃើញបរិបទ caching** និង
**កែសម្រួលយុទ្ធសាស្ត្របង្ហាប់** ឱ្យសមស្រប។

#### របៀបដែលវាដំណើរការ

1. **រកឃើញបរិបទ caching** — ស្កេន request body ដើម្បីរកសញ្ញាសម្គាល់ `cache_control`
2. **កំណត់អត្តសញ្ញាណ caching providers** — ពិនិត្យថាតើ provider គោលដៅគាំទ្រ caching ដែរឬទេ
3. **កែសម្រួលយុទ្ធសាស្ត្រ** — បន្ថយ `aggressive`/`ultra` ទៅជា `standard` សម្រាប់ caching providers
4. **រំលង system prompt** — ជាទូទៅ system prompts ត្រូវបានរក្សាទុកក្នុង cache ដូច្នេះកុំបង្ហាប់វា

Strategy helper ក៏ត្រឡប់ flag `deterministicOnly` ផងដែរ ប៉ុន្តែ plan builder ប្រើ
តែ strategy ប៉ុណ្ណោះ — បច្ចុប្បន្នគ្មានអ្វីនៅផ្នែកបន្ទាប់ដែលអាន flag នេះទេ។

#### ឧទាហរណ៍កូដ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← សញ្ញាសម្គាល់ cache
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

ការបង្ហាប់កំពុងបើក ហើយ provider គោលដៅគាំទ្រ prompt caching (Anthropic, OpenAI,
ជាដើម); សញ្ញាសម្គាល់ `cache_control` ជាក់លាក់មិនត្រូវបានទាមទារទេ — គ្រាន់តែជា caching provider មួយ
ក៏បង្កឱ្យមានការបន្ថយរួចហើយ ខណៈដែលសញ្ញាសម្គាល់តែឯងមិនដែលបង្កឱ្យវាកើតឡើងទេ (ការរកឃើញសញ្ញាសម្គាល់ផ្ដល់ទិន្នន័យទៅឱ្យ cache
telemetry មិនមែនការសម្រេចចិត្តខាងយុទ្ធសាស្ត្រទេ)។

### ការកាត់បន្ថយតាមអាយុកាលជាបន្តបន្ទាប់

ការសន្ទនាដ៏វែងប្រមូលផ្ដុំ message turns ជាច្រើន ប៉ុន្តែ turns ចាស់ៗកាន់តែ
មិនសូវពាក់ព័ន្ធ។ ម៉ូឌុល `progressiveAging.ts` **បន្ថយគុណភាពសារតាមចម្ងាយនៃ turn**
(ចម្ងាយត្រូវបានវាស់ពីចុងបញ្ចប់នៃការសន្ទនា)។ ជាមួយតម្លៃលំនាំដើមដែលបានចេញផ្សាយ
(`verbatim: 2, light: 2, moderate: 3`)៖

- **2 វេនចុងក្រោយ (ចម្ងាយ ≤ 2)**៖ រក្សាទុកដដែលទាំងស្រុង
- **ចម្ងាយ 3**៖ ការបង្ហាប់បែប Caveman (លុបពាក្យបំពេញ)
- **ចម្ងាយ 4+**៖ សាររបស់ជំនួយការត្រូវបានសង្ខេប; សាររបស់អ្នកប្រើត្រូវបានកាត់ឱ្យនៅត្រឹមបន្ទាត់ទីមួយ
  ដោយកំណត់អតិបរមា 120 តួអក្សរ; តួនាទីផ្សេងទៀតត្រូវបានរក្សាទុកដដែល។ System prompts សារ
  ដែលបានចាស់រួចហើយ និងសារចុងក្រោយបំផុតរបស់អ្នកប្រើ តែងតែត្រូវបានរក្សាទុកដដែលទាំងស្រុង ដោយមិនគិតពីចម្ងាយ។
  គ្មានអ្វីត្រូវបានលុបចោលទាំងស្រុងទេ ហើយ band `light`
  មិនអាចឈានដល់បានជាមួយតម្លៃលំនាំដើមដែលបានផ្ដល់មក (`light` ស្មើនឹង `verbatim`)។

#### ឧទាហរណ៍កូដ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 វេនទៀត ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // 3 វេនចុងក្រោយ៖ រក្សាទុកដដែលទាំងស្រុង
  light: 8, // ចម្ងាយ <= 8៖ ការបង្ហាប់កម្រិតស្រាល
  moderate: 20, // ចម្ងាយ <= 20៖ ការបង្ហាប់បែប caveman
  fullSummary: 5, // តម្រូវដោយ type ប៉ុន្តែមិនត្រូវបានអានដោយកូដកំណត់ band
  // ចម្ងាយ > 20៖ សង្ខេប (ជំនួយការ) / រក្សាទុកបន្ទាត់ទីមួយ (អ្នកប្រើ)
});

// saved = ចំនួន token ដែលបានសន្សំ
```

`compressAggressive()`។ Ultra mode មិនដំណើរការវាទេ។ វាមានប្រសិទ្ធភាពជាពិសេសសម្រាប់៖

រក្សាទុកលទ្ធផលដើម នៅពេល `saved` ស្មើ 0 ឬទាបជាង ខណៈដែល `compressToolResult()` ខ្លួនវានៅតែ
ត្រឡប់លទ្ធផលរបស់យុទ្ធសាស្ត្រនោះ។ ជំហានលទ្ធផល tool មិនមែនជាដំណាក់កាលចុងក្រោយទេ៖
កម្មវិធីសង្ខេប fallback របស់ម៉ាស៊ីន នៅតែអាចកាត់សារ `tool` ឬ `function` ដែលវែងជាង
8,192 តួអក្សរ (`maxTokensPerMessage`, 2,048, គុណនឹង 4) ឱ្យខ្លីបាន។

#### ពេលណាត្រូវប្រើ

ការបង្ហាប់លទ្ធផល tool គឺជាជំហានទី 1 របស់ម៉ាស៊ីន aggressive (`compressAggressive()` ក្នុង
`open-sse/services/compression/aggressive.ts`) ដូច្នេះវាដំណើរការក្នុងមុខងារ Aggressive និងក្នុង
ជំហាន `aggressive` នៃ pipeline ជាជង់។ វាបង្ហាប់សារ `tool` និង `function`
ដែលមានទម្រង់ OpenAI និងអត្ថបទនៅខាងក្នុង block `tool_result` របស់ Anthropic។ យុទ្ធសាស្ត្រនីមួយៗមាន
កុងតាក់រៀងៗខ្លួននៅក្រោម `aggressive.toolStrategies` ដែលទាំងអស់បើកជាលំនាំដើម។ ក្នុង dashboard
កុងតាក់ទាំងនេះស្ថិតនៅក្នុងទិដ្ឋភាព **Advanced** នៃទំព័រ Caveman ខណៈការបង្ហាប់បើក ហើយ
មុខងារលំនាំដើមគឺ Aggressive។

### Pipeline ជាជង់

មុខងារ stacked ដំណើរការ **ម៉ាស៊ីនច្រើនតាមលំដាប់** — ជាធម្មតា RTK មុន
(សន្សំ 60-90% លើលទ្ធផល tool) បន្ទាប់មក Caveman លើអត្ថបទដែលនៅសល់ (សន្សំ input
ប្រហែល 46%)។ នៅពេលផ្សំគ្នា វាគឺជា **ចន្លោះដែលអាចសន្សំបាន 78-95%** (សូមមើលគណនាសន្សំ Upstream
ខាងលើ)៖ `1 - (1 - 0.60..0.90) × (1 - 0.46)` មានមធ្យមភាគ ≈89%។

#### របៀបដែលវាដំណើរការ

```
Input (1000 tokens)
  → RTK (តម្រងដែលយល់ដឹងអំពី command) → 200 tokens
    → Caveman (ការដកពាក្យបំពេញ) → 108 tokens
  → Output (108 tokens, សន្សំ ~89%)
```

#### ពេលណាត្រូវប្រើ

ប្រើមុខងារ stacked សម្រាប់៖

- លំហូរការងារដែលប្រើ tool ច្រើន (ការសរសេរកូដបែប agentic, ការស្រាវជ្រាវ)
- ដំណើរការជាបាច់ដែលយកចិត្តទុកដាក់លើការចំណាយ
- នៅពេលអ្នកត្រូវការសន្សំ token ជាអតិបរមា

Pipeline ជាជង់ត្រូវបានកំណត់រចនាសម្ព័ន្ធតាមរយៈការកំណត់ការបង្ហាប់ `stackedPipeline`
សកល ឬតាមរយៈ combo ការបង្ហាប់ដែលមានឈ្មោះ និងត្រូវបានកំណត់ទៅឱ្យ routing combo (សូមមើល
ការកំណត់ជំនួសតាម Combo ខាងលើ) — មិនមែនតាមរយៈ `modePack` របស់ auto-combo ទេ (field នោះគ្រាន់តែ
កំណត់ទម្ងន់ឡើងវិញសម្រាប់ការជ្រើសរើស model របស់ auto-combo ហើយ `stacked` មិនមែនជាឈ្មោះ pack ដែលត្រឹមត្រូវទេ)។

## ការកំណត់ជាន់លើនៃការបង្ហាប់តាម Combo

អ្នកអាចកំណត់ជាន់លើរបៀបបង្ហាប់សកល **សម្រាប់ combo នីមួយៗ** ដើម្បីកែសម្រួលឥរិយាបថឱ្យសមស្រប
សម្រាប់ករណីប្រើប្រាស់ផ្សេងៗ៖

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

វាមានប្រយោជន៍សម្រាប់៖

- **Combo សរសេរកូដ**៖ ប្រើរបៀប `aggressive` សម្រាប់សម័យការងារយូរ
- **Combo សំណួរ និងចម្លើយរហ័ស**៖ ប្រើរបៀប `lite` សម្រាប់ការឆ្លើយតបរហ័ស
- **Combo ដែលប្រើឧបករណ៍ច្រើន**៖ ប្រើរបៀប `stacked` ដើម្បីសន្សំបានអតិបរមា
- **Combo សម្រាប់បរិស្ថានផលិតកម្ម**៖ កុំបើកការកំណត់ជាន់លើសម្រាប់អ្នកផ្តល់សេវាដែលប្រើឃ្លាំងសម្ងាត់ — ការកែសម្រួល
  ដែលគិតគូរពីឃ្លាំងសម្ងាត់ និងបើកជានិច្ច នឹងបន្ថយកម្រិត `aggressive`/`ultra` ទៅជា `standard` ដោយស្វ័យប្រវត្តិ
  (មិនមានរបៀប `cache-aware` ដែលអាចជ្រើសរើសបានទេ)
