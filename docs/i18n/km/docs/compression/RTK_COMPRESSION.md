ការបង្ហាប់ RTK គឺជាម៉ាស៊ីនបង្ហាប់របស់ OmniRoute ដែលយល់ដឹងអំពី command សម្រាប់ output របស់ terminal និង tool។ វាត្រូវបាន
រចនាឡើងសម្រាប់ session របស់ coding-agent ដែលការកើនឡើងនៃ context ភាគច្រើនកើតចេញពី test logs, build output,
សំឡេងរំខានពី package manager, shell transcripts, Docker output, git output និង stack traces។

RTK អាចដំណើរការដោយផ្ទាល់ជាមួយ `defaultMode: "rtk"` ឬជាជំហានដំបូងក្នុង pipeline ដែលដាក់តគ្នា ជាទូទៅ៖

```txt
rtk -> caveman
```

លំដាប់នេះបង្ហាប់ machine output ដែលមានសំឡេងរំខានជាមុនសិន បន្ទាប់មកអនុញ្ញាតឱ្យ Caveman សង្ខេប prose ដែលនៅសល់។

RTK ដើមរាយការណ៍ពីការសន្សំ command-output ចំនួន `60-90%`។ session គំរូក្នុង README របស់វាបានថយចុះពី
standard tokens ប្រហែល `~118,000` មកនៅ RTK tokens ប្រហែល `~23,900` ដែលសន្សំបាន `79.7%` (`~80%`)។ OmniRoute ប្រើ
មធ្យមភាគដើមនោះសម្រាប់ការគណនាការសន្សំរួមជាមួយការបង្ហាប់ input របស់ Caveman៖

```txt
មធ្យមភាគ RTK:    សន្សំបាន 80%
input របស់ Caveman: សន្សំបាន 46%
ដាក់តគ្នា:       1 - (1 - 0.80) * (1 - 0.46) = សន្សំបាន 89.2%
ចន្លោះ:         1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

## ការកំណត់ Filter

RTK ផ្ទុក filter តាមលំដាប់នេះ៖

1. Project filters ពី `.rtk/filters.toml` និង `.rtk/filters.json` តែនៅពេលត្រូវបានទុកចិត្តប៉ុណ្ណោះ។
2. Global filters ពី `DATA_DIR/rtk/filters.toml` និង `DATA_DIR/rtk/filters.json`។
3. Built-in filters ពី `open-sse/services/compression/engines/rtk/filters/`។

នៅក្នុង scope ដូចគ្នា RTK TOML schema v1 filters មានអាទិភាពលើ OmniRoute JSON filters។ TOML
`match_command` expressions ត្រូវបានពិនិត្យមុន command-type matching ដូច្នេះ filter ជាក់លាក់សម្រាប់ command
ដែលបាន import អាច override filter ដែលទូលំទូលាយជាងនៅក្នុង scope នោះ។ Project scope នៅតែមានអាទិភាពលើ global
scope ដោយមិនគិតពី file format។

Project filters ត្រូវបានកម្រិតដោយការទុកចិត្តដោយចេតនា ពីព្រោះ regex filters អាចផ្លាស់ប្តូររបៀបដែល tool output ត្រូវបាន
បង្ហាញទៅកាន់ agents។ project filter file ត្រូវបានទទួលយកនៅពេលលក្ខខណ្ឌមួយក្នុងចំណោមលក្ខខណ្ឌខាងក្រោមជាការពិត៖

- `rtkConfig.trustProjectFilters` គឺ `true`។
- `OMNIROUTE_RTK_TRUST_PROJECT_FILTERS=1` ត្រូវបានកំណត់។
- `.rtk/trust.json` មាន SHA-256 hash ដែលត្រូវគ្នាសម្រាប់ project filter file។

ឧទាហរណ៍ trust file៖

```json
{
  "filtersSha256": "0123456789abcdef...",
  "filtersTomlSha256": "fedcba9876543210..."
}
```

hash ទាំងនេះដាច់ដោយឡែកពីគ្នា៖ `filtersSha256` ទុកចិត្ត `.rtk/filters.json` ខណៈដែល `filtersTomlSha256`
ទុកចិត្ត `.rtk/filters.toml`។ ការកែសម្រួល file ណាមួយនឹងធ្វើឱ្យតែ trust entry របស់វាផ្ទាល់អស់សុពលភាពប៉ុណ្ណោះ។ Global files
ត្រូវបានដំឡើងដោយ administrator ហើយប្រើ behavior នៃការទុកចិត្ត global-filter ដែលមានស្រាប់។

Custom filters អាចជា filter object មួយ ឬ array នៃ filter objects។ Custom filters ដែលមិនត្រឹមត្រូវត្រូវបាន
រំលង និងរាយការណ៍ដោយ diagnostics របស់ `/api/context/rtk/filters`។ Built-in filters ដែលមិនត្រឹមត្រូវបញ្ឈប់ដំណើរការភ្លាមៗ។

## ភាពត្រូវគ្នាជាមួយ RTK TOML schema v1

OmniRoute អាចញែក វាយតម្លៃសុពលភាព សាកល្បង និងដំឡើងឯកសារតម្រងបែបប្រកាសដោយប្រើ RTK TOML schema v1។
វាលដែលគាំទ្ររួមមាន `description`, `match_command`, `strip_ansi`, `filter_stderr`,
`strip_lines_matching`, `keep_lines_matching`, `replace`, `match_output`, `truncate_lines_at`,
`head_lines`, `tail_lines`, `max_lines`, `on_empty` និងការធ្វើតេស្តក្នុងបន្ទាត់ `[[tests.<filter>]]`។
វាលដែលមិនស្គាល់ កន្សោមធម្មតាដែលមិនត្រឹមត្រូវ ឬមិនមានសុវត្ថិភាព ការប្រើច្បាប់ដកចេញ/រក្សាទុកក្នុងពេលដំណាលគ្នា ឯកសារដែលមានទំហំលើស
1 MiB និងសេចក្ដីយោងទៅតម្រងដែលមិនស្គាល់ នឹងត្រូវបានបដិសេធ។ ឯកសារដែលការធ្វើតេស្តក្នុងបន្ទាត់របស់វាបរាជ័យ អាចត្រូវបាន
វាយតម្លៃសុពលភាពដើម្បីពិនិត្យមើល ប៉ុន្តែមិនអាចដំឡើង ឬផ្ទុកបានទេ។ ការបរាជ័យក្នុងការផ្ទុកឯកសារផ្ទាល់ខ្លួននៅតែមានលក្ខណៈ
fail-open៖ ឯកសារមិនត្រឹមត្រូវត្រូវបានរំលង ហើយតម្រងដែលនៅសល់បន្តដំណើរការ។

មិនអាចផ្លាស់ប្ដូរការចាប់យក process បានទេ។ វាលនេះត្រូវបានទទួលយកដោយគ្មានប្រតិបត្តិការ ហើយការវាយតម្លៃសុពលភាពនឹងបញ្ជូនការព្រមានត្រឡប់មកវិញ។
វាត្រូវបានពិពណ៌នាដោយចេតនាថាជា **ភាពត្រូវគ្នាជាមួយ RTK TOML schema v1** មិនមែនជាភាពត្រូវគ្នាពេញលេញ

## DSL របស់តម្រង

តម្រងប្រើ JSON schema ដែលបានពិពណ៌នានៅក្នុង [ទម្រង់ច្បាប់បង្ហាប់](./COMPRESSION_RULES_FORMAT.md)។
runtime អនុវត្តដំណាក់កាលទាំងនេះតាមលំដាប់៖

```txt
stripAnsi -> filterStderr -> replace -> matchOutput -> ដកចេញ/រួមបញ្ចូលបន្ទាត់
  -> truncateLineAt -> head/tail/maxLines -> onEmpty
```

## ការលុបបន្ទាត់ស្ទួន (ពីរស្រទាប់)

RTK បង្រួមបន្ទាត់ស្ទួននៅស្រទាប់ឯករាជ្យពីរ៖

1. **`deduplicate` តាម filter នីមួយៗ (ត្រូវបើកប្រើដោយចេតនា, លំនាំដើម `false`)។** Filter មួយអាចកំណត់ `rules.deduplicate: true`
   ដើម្បីបង្រួមបន្ទាត់ស្ទួនជាប់គ្នា _នៅក្នុងលទ្ធផលដែលត្រូវគ្នារបស់ filter នោះ_ មុនពេលកាត់ខ្លី។
   ដំណើរការនេះប្រព្រឹត្តទៅនៅក្នុង `lineFilter.ts`។ សម្រាប់ filter ចាស់ៗ វាត្រូវបានបើកដោយស្វ័យប្រវត្តិ នៅពេល filter កំណត់
   `collapsePatterns`។ Schema៖ `deduplicate: z.boolean().default(false)` នៅក្នុង
   `open-sse/services/compression/engines/rtk/filterSchema.ts`។
2. **`deduplicateThreshold` ទូទាំង engine (លំនាំដើម `3`)។** បន្ទាប់ពី filter ទាំងអស់ដំណើរការ engine នឹងបង្រួម
   លំដាប់បន្ទាត់ដូចគ្នាជាប់គ្នាណាមួយដែលមានចំនួន `>= deduplicateThreshold` នៅទូទាំងលទ្ធផលទាំងមូល
   (`deduplicateRepeatedLines` ដែលត្រូវបានអនុវត្តនៅក្នុង `engines/rtk/index.ts`)។ តម្លៃនេះត្រូវបានកម្រិតចន្លោះ 2–100 នៅពេល
   ធ្វើ normalization។

ការដំណើរការតាម filter ធ្វើឡើងមុន (នៅខាងក្នុង filter) ចំណែកការដំណើរការទូទាំង engine ធ្វើឡើងចុងក្រោយ (លើលទ្ធផលដែលបានតភ្ជាប់)
ដូច្នេះទាំងពីរអាចដំណើរការរួមគ្នាដោយមិនរាប់ស្ទួនពីរដង។

## ការដាក់បន្ទាត់ជាក្រុម (`enableGrouping`)

នៅពេល `rtkConfig.enableGrouping` មានតម្លៃជា `true` (លំនាំដើម `false`) RTK ដំណើរការ `groupSimilarLines`
បន្ថែមទៀតលើលទ្ធផលក្រោយការលុបស្ទួន ដើម្បីបង្រួមលំដាប់បន្ទាត់ជាប់គ្នាដែល _ប្រហាក់ប្រហែលគ្នា_ (មិនមែនដូចគ្នាគ្រប់ byte)
។ `rtkConfig.groupingThreshold` (លំនាំដើម `3`) គឺជាប្រវែងអប្បបរមានៃលំដាប់ដែលធ្វើឱ្យការដាក់ជាក្រុម
ចាប់ផ្តើម។ នេះគឺជាសមភាគីផ្នែករចនាសម្ព័ន្ធរបស់ `deduplicateThreshold`៖ ការលុបស្ទួនដោះស្រាយការកើតឡើងម្តងទៀតដែលដូចគ្នាបេះបិទ
ចំណែកការដាក់ជាក្រុមដោះស្រាយ «ទម្រង់ដូចគ្នា ប៉ុន្តែមានភាពខុសគ្នាបន្តិចបន្តួច»។ Flag ទាំងពីរគឺជាផ្នែកនៃ JSON `rtkConfig`
ដែលត្រូវបានរក្សាទុកក្នុងតារាង `key_value` (សូមមើលការកំណត់រចនាសម្ព័ន្ធខាងលើ) ដូច្នេះការកំណត់នេះនៅតែមានក្រោយការចាប់ផ្តើមឡើងវិញ។

## ការដក Comment របស់កូដ (`stripCodeComments` / `preserveDocstrings`)

នៅពេល `rtkConfig.applyToCodeBlocks` ត្រូវបានបើក RTK ក៏អាចដក comment ចេញពី fenced code block ផងដែរ៖

- `stripCodeComments` (លំនាំដើម `false`) — ត្រូវបើកប្រើដោយចេតនា។ នៅពេលមានតម្លៃជា `true` RTK នឹងដក comment ចេញពី fenced block របស់ JavaScript
  និង TypeScript។ ជាប្រវត្តិសាស្ត្រ flag នេះត្រូវបានអាន ប៉ុន្តែមិនដែលត្រូវបានអនុវត្តទេ ដូច្នេះលំនាំដើមនៅតែជា
  «រក្សាទុក» ដើម្បីចៀសវាងការផ្លាស់ប្តូរក្នុង production ដោយមិនមានការជូនដំណឹង។
- `preserveDocstrings` (លំនាំដើម `true`) — នៅពេលដក comment ចេញ block comment ប្រភេទ JSDoc/`/** … */` ត្រូវបាន
  រក្សាទុក (ពួកវាផ្ទុកឯកសារ API ដែលមានតម្លៃលើសពីចំនួន byte ដែលពួកវាប្រើ)។ កំណត់ជា `false` ដើម្បីដក
  comment ទាំងនោះចេញផងដែរ។

ការដក comment ត្រូវបានអនុវត្តនៅក្នុង `open-sse/services/compression/engines/rtk/codeStripper.ts`។ វាប្រើ
**TypeScript parser** (មិនមែន regex ទេ) ដូច្នេះ string literal, template literal និង regex literal មិនត្រូវបានយល់ច្រឡំ
ថាជា comment ឡើយ ហើយវានឹងបោះបង់ដំណើរការទាំងស្រុងនៅពេលរកឃើញ JSX (ដូច្នេះ comment ក្នុង JSX expression container
មិនត្រូវបានធ្វើឱ្យខូចឡើយ)។ បច្ចុប្បន្ន ការដក comment អនុវត្តតែចំពោះ **JavaScript និង TypeScript ប៉ុណ្ណោះ** — ភាសាផ្សេងទៀត
នៅក្នុងសំណុំ `CodeLanguage` របស់ stripper (Python, Rust, Go, Ruby, Java) មានការបង្រួមបន្ទាត់ទទេ និង
ចន្លោះទទេ ប៉ុន្តែមិនមានការដក comment ទេ។ ការដំណើរការលើ block ដែលត្រូវបានដក comment ត្រូវបានដាក់ស្លាក `rtk:code-strip` នៅក្នុង
`rulesApplied`។

> **ចំណាំ — GCF / ការអ៊ិនកូដជាតារាងគឺជា engine ដាច់ដោយឡែក។** RTK **មិន** មាន encoder JSON ជាទម្រង់តារាង/ជួរឈរ "GCF"
> (Graph Compact Format) ទេ។ Encoder នោះ — ដែលបានជំនួស encoder `omni-tabular` ចាស់ជាង —
> ស្ថិតនៅក្នុង engine **headroom**
> (`open-sse/services/compression/engines/headroom/` ដោយមាន codec ដែលបានបញ្ចូលមកជាមួយនៅក្រោម
> `headroom/gcf/`)។ វាមិនទាក់ទងនឹង pipeline របស់ filter RTK ដែលបានចងក្រងជាឯកសារនៅទីនេះទេ។

`open-sse/services/compression/types.ts`។ អាប់ជិកទាំងមូលត្រូវបានរក្សាទុកជាតម្លៃ JSON តែមួយនៅក្នុង

| `preserveDocstrings`   | `true`   | នៅពេលដកមតិយោបល់ចេញ រក្សាទុកប្លុក JSDoc/`/** … */`                                      |

## API

| ផ្លូវ                              | វិធីសាស្ត្រ | គោលបំណង                                           |
| ---------------------------------- | ----------- | ------------------------------------------------- |
| `/api/context/rtk/config`          | GET         | អានការកំណត់ RTK                                   |
| `/api/context/rtk/config`          | PUT         | ធ្វើបច្ចុប្បន្នភាពការកំណត់ RTK                    |
| `/api/context/rtk/filters`         | GET         | រាយបញ្ជីកាតាឡុកតម្រង និងព័ត៌មានវិនិច្ឆ័យការផ្ទុក  |
| `/api/context/rtk/import`          | POST        | ផ្ទៀងផ្ទាត់ ឬដំឡើងឯកសារគ្រោងការណ៍ RTK TOML v1     |
| `/api/context/rtk/test`            | POST        | មើលការបង្រួម RTK ជាមុនសម្រាប់ទិន្នន័យអត្ថបទមួយ    |
| `/api/context/rtk/raw-output/[id]` | GET         | អានលទ្ធផលដើមដែលបានកែសម្រួលលាក់ព័ត៌មាន និងរក្សាទុក |
| `/api/compression/preview`         | POST        | មើលជាមុននូវរបៀបបង្រួមណាមួយ                        |

ទិន្នន័យផ្ញើសាកល្បង RTK៖

```json
{
  "command": "npm test",
  "text": "FAIL tests/example.test.ts\nAssertionError: expected true\nTest Files 1 failed",
  "config": {
    "intensity": "standard"
  }
}
```

ទិន្នន័យផ្ញើសម្រាប់មើលការបង្រួមជាមុន៖

```json
{
  "mode": "stacked",
  "messages": [
    {
      "role": "tool",
      "content": "FAIL tests/example.test.ts\nAssertionError: expected true\nTest Files 1 failed"
    }
  ],
  "config": {
    "rtkConfig": {
      "rawOutputRetention": "failures"
    }
  }
}
```

ផ្លូវគ្រប់គ្រងតម្រូវឱ្យមានការផ្ទៀងផ្ទាត់សិទ្ធិគ្រប់គ្រងផ្ទាំងបញ្ជា ឬគោលការណ៍ API-key ដែលត្រូវគ្នា។

ទិន្នន័យផ្ញើសម្រាប់ផ្ទៀងផ្ទាត់ RTK TOML៖

```json
{
  "action": "validate",
  "content": "schema_version = 1\n\n[filters.my-tool]\nmatch_command = \"^my-tool\\\\b\"\nmax_lines = 20\n"
}
```

ប្រើ `"action": "install"` ដើម្បីដំឡើងឯកសារដែលបានផ្ទៀងផ្ទាត់ជាសកល។ បន្ថែម `"overwrite": true` តែបន្ទាប់ពី
បានពិនិត្យ និងបញ្ជាក់ការជំនួសឯកសារសកលដែលមានស្រាប់រួចហើយប៉ុណ្ណោះ។

## ការសង្គ្រោះលទ្ធផលដើម

ជាធម្មតា RTK ត្រឡប់តែអត្ថបទដែលបានបង្ហាប់ប៉ុណ្ណោះ។ សម្រាប់ការបំបាត់កំហុស `rawOutputRetention` អាចរក្សាទុក
លទ្ធផលដើមដែលបានលាក់ព័ត៌មានរសើប៖

| តម្លៃ      | ឥរិយាបថ                                                          |
| ---------- | ---------------------------------------------------------------- |
| `never`    | មិនរក្សាទុកលទ្ធផលដើម                                             |
| `failures` | រក្សាទុកតែលទ្ធផលដែលទំនងជាបរាជ័យ                                  |
| `always`   | រក្សាទុករាល់លទ្ធផលដើម RTK ដែលបានបង្ហាប់ បន្ទាប់ពីលាក់ព័ត៌មានរសើប |

ឯកសារដែលបានរក្សាទុកត្រូវបានសរសេរនៅក្រោម៖

```txt
DATA_DIR/rtk/raw-output/
```

ព័ត៌មានសម្ងាត់ត្រូវបានលាក់មុនពេលរក្សាទុកជាអចិន្ត្រៃយ៍ រួមទាំង bearer token ទូទៅ, API key, Slack token,
AWS access key និងតម្លៃក្នុងទម្រង់កំណត់ `token=...`, `secret=...`, `password=...`។ ទិន្នន័យវិភាគ
រក្សាទុកតែ pointer id, ទំហំ និង metadata របស់ hash ប៉ុណ្ណោះ។

## ច្រកផ្ទៀងផ្ទាត់

ច្រកផ្ទៀងផ្ទាត់ដែលផ្តោតជាក់លាក់ ដំណើរការការធ្វើតេស្ត filter inline ដែលមានស្រាប់ ដោយមិនហៅពាក្យបញ្ជាខាងក្រៅតាម shell៖

ដំណើរការច្រកបង្ហាប់ទូលំទូលាយ មុនពេលចេញផ្សាយ៖

## ការពង្រីក RTK

1. បន្ថែម ឬធ្វើបច្ចុប្បន្នភាពឯកសារ JSON របស់ filter។
2. រួមបញ្ចូលគំរូ `tests[]` យ៉ាងហោចណាស់មួយ ដែលបញ្ជាក់ពីឥរិយាបថសំខាន់។
3. បន្ថែម fixture នៅក្រោម `tests/unit/compression/fixtures/rtk/` សម្រាប់ក្រុមពាក្យបញ្ជាថ្មី។
4. បន្ថែមការគ្របដណ្តប់លើការរកឃើញពាក្យបញ្ជា នៅពេលណែនាំថ្នាក់លទ្ធផលថ្មី។
5. ដំណើរការច្រកផ្ទៀងផ្ទាត់ និងច្រក RTK ទូលំទូលាយ។
6. ប្រសិនបើ filter ជារបស់គម្រោងមូលដ្ឋាន សូម commit `.rtk/filters.json` ហើយធ្វើឱ្យ `.rtk/trust.json` ស្រស់ឡើងវិញ តែបន្ទាប់ពីការពិនិត្យប៉ុណ្ណោះ។

const result = runRtkFilterTests({ intensity: "aggressive" });

ថត `engines/rtk/filters/` មាន **ឯកសារ JSON តម្រងដែលភ្ជាប់មកជាមួយចំនួន 49+**។ អ្នកអាចបន្ថែមតម្រងផ្ទាល់ខ្លួនរបស់អ្នក ដើម្បីបង្រួមលទ្ធផលពីឧបករណ៍ផ្ទាល់ខ្លួនដែលមិនត្រូវបានគ្របដណ្ដប់ដោយលំនាំដើម។

### គ្រោងការណ៍តម្រង (Zod)

```ts

```
~/.omniroute/rtk/filters/my-filter.json     # កម្រិតអ្នកប្រើប្រាស់

- កាតាឡុកដែលភ្ជាប់មកជាមួយ៖ `open-sse/services/compression/engines/rtk/filters/`
- ថតអ្នកប្រើប្រាស់៖ `~/.omniroute/rtk/filters/`
- ថតគម្រោង៖ `<project>/.rtk/filters/`

### ការផ្ទៀងផ្ទាត់សុពលភាព

តម្រងត្រូវបានផ្ទៀងផ្ទាត់ធៀបនឹងគ្រោងការណ៍ Zod នៅពេលផ្ទុក។ តម្រងដែលមានរចនាសម្ព័ន្ធមិនត្រឹមត្រូវនឹងផ្ទុកបរាជ័យ ហើយកត់ត្រាកំហុស៖

```
RTK_FILTER_LOADER: filter "my-filter" failed validation:
  - rules.replace.0.pattern: Invalid regex
  - match.commands: must not be empty
```

ដើម្បីផ្ទៀងផ្ទាត់តម្រងដែលបានដំឡើងទាំងអស់ សូមហៅ `runRtkFilterTests()` ដែលត្រូវបាននាំចេញពី `open-sse/services/compression/engines/rtk/verify.ts`។

### ការអនុវត្តល្អបំផុត

1. **តែងតែបញ្ចូល `tests[]`** — វាបញ្ជាក់ថាតម្រងរបស់អ្នកដំណើរការ និងការពារកុំឱ្យបញ្ហាចាស់កើតឡើងវិញ
2. **ប្រើ `matchOutput` សម្រាប់ការបញ្ចប់មុនកំណត់** — ប្រសិនបើបន្ទាត់តែមួយអាចបង្ហាញខ្លឹមសារបានគ្រប់គ្រាន់ សូមជំនួសប្លុកទាំងមូល
3. **ផ្តល់អាទិភាពដល់ `keep` ជាង `strip`** — ច្បាប់ជាក់លាក់ដែលកំណត់ថា "រក្សាទុកជានិច្ច" មានសុវត្ថិភាពជាងច្បាប់ដែលកំណត់ថា "លុបចេញជានិច្ច"
4. **សាកល្បងនៅកម្រិតអាំងតង់ស៊ីតេទាំង 3** — `minimal` មិនគួរធ្វើការផ្លាស់ប្តូរអ្វីឡើយ ហើយ `aggressive` នៅតែគួររក្សាទុកកំហុស
5. **ប្រើវាល `unless`** — ការពារការបញ្ចប់មុនកំណត់ដោយលក្ខខណ្ឌ "កុំដំណើរការ ប្រសិនបើមាន X"

## ការសង្គ្រោះលទ្ធផលដើម និងច្រកផ្ទៀងផ្ទាត់

នៅពេល RTK បង្ហាប់លទ្ធផលយ៉ាងខ្លាំង អ្នកអាច **សង្គ្រោះអត្ថបទដើម** សម្រាប់ការបំបាត់កំហុស សវនកម្ម ឬការចាក់ឡើងវិញ។

### របៀបដែលការសង្គ្រោះលទ្ធផលដើមដំណើរការ

```
លទ្ធផលដើម (10K tokens)
        │
        ▼
RTK បង្ហាប់ (ដោយប្រើ rawOutput.enabled=true)
        │
        ├─▶ លទ្ធផលដែលបានបង្ហាប់ (2K tokens)  ──▶ ទៅកាន់ LLM
        │
        └─▶ លទ្ធផលដើម (10K tokens)           ──▶ រក្សាទុកក្នុង DB
                                                  (ភ្ជាប់ដោយ request_id)
```

**លំនាំដើម**: `rawOutput.enabled: false` (សន្សំទំហំផ្ទុក)។

### ថ្លៃដើមនៃការរក្សាទុក

| ក្នុងមួយសំណើ               | ពិដាន 1MB     | ពិដាន 10MB     |
| -------------------------- | ------------- | -------------- |
| លទ្ធផលដែលបានបង្ហាប់ជាមធ្យម | ~5KB          | ~5KB           |
| លទ្ធផលដើមដែលបានរក្សាទុក    | ~50-500KB     | ~500KB-5MB     |
| ជាមួយ 1000 សំណើ/ថ្ងៃ       | 50-500MB/ថ្ងៃ | 500MB-5GB/ថ្ងៃ |

> **អនុសាសន៍**: បើកលទ្ធផលដើមសម្រាប់តែ **វគ្គបំបាត់កំហុស** ឬ **សវនកម្មដោយការយកសំណាក** ប៉ុណ្ណោះ មិនត្រូវបើកជាប់ជានិច្ចឡើយ។

### ការសង្គ្រោះលទ្ធផលដើម

const raw = readRtkRawOutput(pointerId); // pointerId ពីស្ថិតិនៃការបង្ហាប់

`pointerId` ត្រូវបានត្រឡប់មកវិញក្នុង `CompressionStats.rtkRawOutputPointers[]` បន្ទាប់ពីការបង្ហាប់។

### ច្រកផ្ទៀងផ្ទាត់

**ការផ្ទៀងផ្ទាត់តម្រង RTK** (`open-sse/services/compression/engines/rtk/verify.ts`) ផ្ទៀងផ្ទាត់តម្រងទាំងអស់ធៀបនឹង `tests[]` របស់ពួកវា ហើយធានាថាឥរិយាបថត្រឹមត្រូវនៅគ្រប់កម្រិតអាំងតង់ស៊ីតេទាំង 3។

**ហៅ `runRtkFilterTests()`** ដើម្បីដំណើរការការផ្ទៀងផ្ទាត់៖

```ts
import { runRtkFilterTests } from "open-sse/services/compression/engines/rtk/verify";

const result = runRtkFilterTests();
console.log(`Passed: ${result.outcomes.filter((o) => o.passed).length}`);
console.log(`Failed: ${result.outcomes.filter((o) => !o.passed).length}`);
if (!result.passed) {
  console.error("Filters failed verification");
  result.outcomes
    .filter((o) => !o.passed)
    .forEach((o) => {
      console.error(
        `  - ${o.filterId} / ${o.testName}: expected "${o.expected}", got "${o.actual}"`
      );
    });
}
```
