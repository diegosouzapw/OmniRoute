> `auto/*` id ថ្មីចំនួនពីរ — `auto/subscription` និង `auto/thrifty`។ ទាំងពីរតម្រូវឱ្យជ្រើសរើសប្រើដោយការស្នើសុំ៖ គ្មានអ្វីត្រូវបានបញ្ជូនឆ្លងកាត់វាទេ លុះត្រាតែអ្នកហៅស្នើសុំ id តាមឈ្មោះ ហើយគ្មាន pool, strategy ឬ default ដែលមានស្រាប់ណាមួយត្រូវបានផ្លាស់ប្ដូរឡើយ។

## ហេតុអ្វីបានជាវាមាន

OmniRoute ឆ្លើយសំណួរអំពីថ្លៃដើមពីររួចហើយ ប៉ុន្តែគ្មានសំណួរណាមួយជាសំណួរដែលប្រតិបត្តិករភាគច្រើនសួរនោះទេ។

| យន្តការដែលមានស្រាប់                                      | សំណួរដែលវាឆ្លើយ                                     |
| -------------------------------------------------------- | --------------------------------------------------- |
| `hidePaidModels` (`autoCombo/paidModelFilter.ts`)        | "តើ model នេះត្រូវបានដាក់ក្នុងកាតាឡុកថាឥតគិតថ្លៃឬ?" |
| `freeAccessPolicy: "strict"` (`strictZeroCostFilter.ts`) | "តើ connection នេះអាចគិតថ្លៃខ្ញុំបានដែរឬទេ?"        |
| `quotaPreflight` (`combo/quotaExhaustionCutoff.ts`)      | "តើ connection នេះជិតដល់ដែនកំណត់របស់វាឬ?"           |
| `budgetCap` / `budgetFallback` (`autoCombo/engine.ts`)   | "កំណត់ពិដានចំណាយ ហើយបន្ថយទៅជម្រើសថោកបំផុត"          |

យន្តការសម្រាប់តែការប្រើប្រាស់ឥតគិតថ្លៃទាំងអស់ **បរាជ័យដោយបិទ** — pool ឥតគិតថ្លៃដែលបានប្រើអស់ គឺជា pool ទទេ មិនមែនជាការឡើងទៅជម្រើសបង់ប្រាក់ទេ — ហើយយន្តការខាងបង់ប្រាក់ទាំងអស់មិនគិតពីកម្រិតថ្នាក់ទេ។ ទាំងពីរមិនឆ្លើយសំណួរនេះទេ៖

> "ប្រើ quota ដែលខ្ញុំបានបង់ប្រាក់រួចហើយ។ នៅពេលវាអស់ សូមបញ្ឈប់ ឬឡើងមួយកម្រិតម្ដងៗតាមជម្រើសបង់ប្រាក់ដែលថោកបំផុត — ហើយត្រឡប់មកវិញភ្លាមៗនៅពេលវាត្រូវបានកំណត់ឡើងវិញ។"

## ការគិតថ្លៃគឺជាលក្ខណៈរបស់ connection មិនមែនរបស់ model ទេ

`classifyTier()` (`open-sse/services/tierResolver.ts`) ប្រើ `(provider, model)` ជាគន្លឹះ ហើយត្រឡប់ `free | cheap | premium` ពីតម្លៃក្នុងកាតាឡុក។ ប៉ុន្តែថាតើសំណើមួយបង្កើតថ្លៃបន្ថែមឬអត់ គឺអាស្រ័យលើ **connection ដែលបម្រើវា**៖ model ដូចគ្នាត្រូវបានរួមបញ្ចូលក្នុងគម្រោងតាមរយៈ Claude Code OAuth connection ប៉ុន្តែត្រូវបានគិតថ្លៃតាម token តាមរយៈ API-key connection។

`provider_connections.auth_type` មិនមែនជាតម្លៃជំនួសដែលអាចទុកចិត្តបានក្នុងទិសណាមួយទេ — មាន metered OAuth connections ហើយក៏មាន plan-included API-key connections ផងដែរ (Copilot seat token មិនមែនជា metered API key ទេ)។ ដូច្នេះ billing class មកពី **កាតាឡុកដែលបានរៀបចំដោយប្រុងប្រយ័ត្ន** គឺ `open-sse/config/connectionBillingCatalog.ts` ដែលកំណត់ដោយដៃដោយផ្អែកលើលក្ខខណ្ឌដែលបានផ្សព្វផ្សាយរបស់ provider នីមួយៗ — ជាលំនាំដូចគ្នាដែល `FreeModelBudget.hardStopGuaranteed` បានបង្កើតរួចហើយសម្រាប់ free models។

```ts
type ConnectionBillingClass = "subscription" | "metered" | "keyless" | "unknown";
type ConnectionOverageBehavior = "hard-stop" | "meters-to-paid" | "unknown";
```

លំដាប់នៃការដោះស្រាយ (`autoCombo/connectionBilling.ts`)៖ synthetic no-auth sentinel → `keyless`; ធាតុក្នុងកាតាឡុកដែលផ្គូផ្គងទាំង provider **និង** `authType`; ធាតុសម្រាប់ provider ទាំងមូល; បើមិនដូច្នោះទេ `unknown`។ **អ្វីដែលមិនបានរៀបចំក្នុងកាតាឡុក មិនមែនឥតគិតថ្លៃទេ** — `unknown` ត្រូវបានចាត់ទុកជា `metered` នៅគ្រប់ទីកន្លែង ដូច្នេះ provider ដែលត្រូវបានបន្ថែមនៅថ្ងៃស្អែកនឹងចាប់ផ្ដើមនៅក្រៅកម្រិត subscription ហើយត្រូវបញ្ចូលក្នុងកាតាឡុកដោយចេតនា។

## ម៉ូដែលកាំជណ្ដើរ

មានប្រាំកាំតាមលំដាប់នៃការឡើងកម្រិត។ ភាពខុសគ្នារបស់វាមិនមែនមានតែតម្លៃទេ — កាំនីមួយៗមានសញ្ញានៃការអស់ **ផ្ទាល់ខ្លួន** ដែលជាមូលហេតុថាហេតុអ្វីវាមិនមែនគ្រាន់តែជាការតម្រៀបនោះទេ។

| #   | កាំ            | សមាជិកភាព                                          | ចាត់ទុកថាអស់នៅពេល                  |
| --- | -------------- | -------------------------------------------------- | ---------------------------------- |
| 0   | `subscription` | `billing: "subscription"` ដែលបានរៀបចំក្នុងកាតាឡុក  | quota window ស្ថិតនៅ ឬក្រោម cutoff |
| 1   | `keyless`      | synthetic no-auth path                             | connection cooldown / breaker      |
| 2   | `free`         | metered connection, `classifyTier() === "free"`    | free allowance ត្រូវបានប្រើអស់     |
| 3   | `cheap`        | metered connection, `classifyTier() === "cheap"`   | per-rung budget ត្រូវបានប្រើអស់    |
| 4   | `premium`      | metered connection, `classifyTier() === "premium"` | per-rung budget ត្រូវបានប្រើអស់    |

កាំ 0-2 អស់ដោយសារ **quota** ដែលអាចសង្កេតបាន និងត្រូវបានតាមដានរួចហើយ។ កាំ 3-4 មិនមាន quota ទេ — paid connection មួយអាចបម្រើជាបន្តបន្ទាប់ដោយគ្មានទីបញ្ចប់ — ដូច្នេះសញ្ញានៃការអស់តែមួយគត់ដែលសមហេតុផលគឺ **budget** សម្រាប់កាំនីមួយៗ។ បើគ្មានវាទេ "ឡើងកម្រិតនៅពេល cheap អស់" នឹងគ្មានកត្តាជំរុញឱ្យកើតឡើងទេ។

## `auto/subscription` — បិទជាសុវត្ថិភាពនៅពេលបរាជ័យ

Pool = តែថ្នាក់ទី 0 ប៉ុណ្ណោះ ដោយកំណត់ចំពោះការតភ្ជាប់ដែលការប្រើលើសកម្រិតរបស់វាត្រូវបានកត់ត្រាទុកថាជា `hard-stop` ហើយការតភ្ជាប់នីមួយៗត្រូវបានផ្ទៀងផ្ទាត់ដោយផ្ទាល់ថានៅមានកូតាគ្រប់គ្រាន់។ អ្វីៗដែលមិនច្បាស់លាស់ត្រូវបានដកចេញ៖ provider ដែលមិនទាន់ត្រូវបានរៀបចំជ្រើសរើស ការអានកូតាដែលមិនអាចផ្ទៀងផ្ទាត់បាន ការអានដែលហួសសុពលភាព ឬការប្រើលើសកម្រិតដែលត្រូវបានវាស់គិតថ្លៃ។

Pool ទទេគឺជាចម្លើយដែល **បានគ្រោងទុក** មិនមែនជាកំហុសទេ — ផ្លូវដោះស្រាយ pool ទទេដែលមានស្រាប់របស់អ្នកហៅ បម្លែងវាទៅជាកំហុសច្បាស់លាស់ ជំនួសឱ្យការប្រើជម្រើសបម្រុងដែលអាចគិតថ្លៃដោយស្ងាត់ៗ។ នេះជាការធានាទាំងមូលរបស់ id នេះ។

`keyless` ត្រូវបានកំណត់ដោយចេតនាថា **មិន** មានលក្ខណៈសម្បត្តិគ្រប់គ្រាន់ទេ៖ ការដាក់ជាក្រុមនេះមានន័យថា "គម្រោងដែលខ្ញុំបង់ប្រាក់" ដូច្នេះ backend ដែលមិនត្រូវការ authentication មិនស្ថិតក្នុងក្រុមនេះទេ។ ប្រើ `auto/thrifty` (ឬ `auto/best-free`) សម្រាប់ករណីនោះ។

## `auto/thrifty` — ឡើងម្តងមួយថ្នាក់

Pool = គ្រប់ថ្នាក់ទាំងអស់ ដោយតម្រៀបតាមលិបិក្រមថ្នាក់ ហើយ candidate ដែលអស់កូតាត្រូវបានរារាំងមិនឱ្យចូល។ Engine `auto` នៅតែដាក់ពិន្ទុ **នៅក្នុង** pool ដែលនៅសល់៖ ជណ្ដើរកំណត់ថាតើថ្នាក់ណាខ្លះត្រូវប្រើ ខណៈការដាក់ពិន្ទុកំណត់ថា candidate ណាឈ្នះនៅក្នុងថ្នាក់ទាំងនោះ។ លំដាប់នៅក្នុងថ្នាក់នីមួយៗមានស្ថិរភាព ដូច្នេះលំដាប់ចំណាត់ថ្នាក់ផ្ទាល់របស់ scorer មិនត្រូវបានតម្រៀបឡើងវិញដោយ overlay នេះទេ។

នេះជា overlay សម្រាប់ការតម្រៀបលំដាប់ + ការរារាំង **មិនមែន** ជា dispatcher ថ្មីទេ៖ loop សាកល្បងជាមុនរបស់ `combo.ts` ដើរឆ្លងកាត់ target តាមលំដាប់ និងបន្តទៅមុខនៅពេលបរាជ័យរួចហើយ ដូច្នេះការអស់កូតានៅ runtime ដែល preflight មិនបានរកឃើញ នឹងនៅតែឡើងទៅថ្នាក់បន្ទាប់ក្នុង request ដដែល។

ខណៈដែល `auto/subscription` បិទជាសុវត្ថិភាពនៅពេលបរាជ័យ `auto/thrifty` បើកបន្ត **ដោយសុវត្ថិភាព**៖ ការតភ្ជាប់ដែលរួមបញ្ចូលក្នុងគម្រោង ប៉ុន្តែមិនមានការអានកូតាដែលអាចប្រើបាន នៅតែត្រូវបានសាកល្បងមុន។ ការសាកល្បងវាមិនចំណាយអ្វីទេ ហើយប្រសិនបើវាអស់កូតាពិតប្រាកដ ផ្លូវបន្តនៅពេលបរាជ័យនឹងទៅដល់ថ្នាក់បន្ទាប់ដដែល — ផ្ទុយទៅវិញ ការបដិសេធមិនសាកល្បងវានឹងបញ្ជូន request ទៅកាន់ថ្នាក់គិតថ្លៃនៅពេល telemetry បាត់ ដែលជាលទ្ធផលពិតប្រាកដដែលការដាក់ជាក្រុមនេះត្រូវបានបង្កើតឡើងដើម្បីជៀសវាង។

## ការត្រឡប់ទៅគម្រោងវិញបន្ទាប់ពីការកំណត់ឡើងវិញ

មានបីចំណុចឯករាជ្យពីគ្នាដែលត្រូវតែផុតកំណត់ មុនពេល routing ត្រឡប់ទៅថ្នាក់ទី 0 វិញ។ ការកែតែមួយចំណុចនឹងធ្វើឱ្យជណ្ដើរជាប់គាំងលើថ្នាក់គិតថ្លៃយូរបន្ទាប់ពីគម្រោងបានបំពេញឡើងវិញ។

1. **Cache ស្ថានភាពកូតា** — `freeAccessQuota.ts` ធ្វើ cache សម្រាប់ `(provider, connection)` នីមួយៗដោយមាន TTL 180s។ ធាតុក្នុង cache ដែល `resetAt` របស់វាបានកន្លងផុតទៅហើយ ពិពណ៌នាអំពី window ដែលលែងមាន ដូច្នេះឥឡូវនេះវាត្រូវបានចាត់ទុកថាហួសសុពលភាព **ដោយមិនគិតពីអាយុ** ហើយបង្ខំឱ្យ refresh។ បើគ្មានចំណុចនេះទេ គម្រោងដែលបានបំពេញឡើងវិញនៅពាក់កណ្ដាលអធ្រាត្រ នឹងនៅតែបង្ហាញថាអស់កូតារហូតដល់ TTL ផុតកំណត់ដោយចៃដន្យ។
2. **ស្ថានភាពផ្ទាល់របស់ជណ្ដើរ** — តាមការរចនា វាមិនមានទេ។ សិទ្ធិមានលក្ខណៈគ្រប់គ្រាន់របស់ថ្នាក់ត្រូវបានគណនាឡើងវិញពីស្ថានភាពកូតាបច្ចុប្បន្ន រាល់ពេលស្ថាបនា pool។ គ្មានកំណត់ត្រា "បច្ចុប្បន្ននៅថ្នាក់ទី 3" ដែលត្រូវបានរក្សាទុក ហើយអាចបន្តមានក្រោយការកំណត់ឡើងវិញ និងធ្វើឱ្យ routing ជាប់គាំងទេ។
3. **រយៈពេល cooldown របស់ការតភ្ជាប់** — 429 ដែលកើតឡើងនៅពេលអស់កូតា កំណត់ `rateLimitedUntil` ពី exponential backoff ដែលសម្រាប់ការតភ្ជាប់របស់គម្រោង អាចលើសពេលកំណត់ឡើងវិញពិតប្រាកដ។ `clampCooldownToReset()`
   (`subscriptionLadder.ts`) បង្រួម cooldown ឱ្យត្រឹមពេលកំណត់ឡើងវិញផ្ទាល់របស់ upstream ហើយមិនអាចពន្យារវាបានទេ។ **វាត្រូវបានអនុវត្ត និងសាកល្បងរួចហើយ ប៉ុន្តែមិនទាន់បានភ្ជាប់ឱ្យដំណើរការទេ**៖ quota cache ត្រូវបាន invalidated នៅក្នុង `src/sse/services/auth.ts` _មុនពេល_ cooldown ណាមួយត្រូវបានសរសេរ ដូច្នេះ `resetAt` ត្រូវតែត្រូវបានចាប់យកមុនជាងនេះនៅក្នុង function នោះ — ជាការផ្លាស់ប្តូរលើផ្លូវ resilience ដ៏សំខាន់ ដែលគួរតែស្ថិតក្នុង PR ដាច់ដោយឡែកដែលឆ្លងកាត់ការពិនិត្យ។ រហូតដល់ពេលនោះ ការចូលប្រើឡើងវិញត្រូវរង់ចាំឱ្យ cooldown របស់ការតភ្ជាប់ផុតកំណត់ (ដែលមានស្រាប់ហើយក្នុងការផ្ដល់អាទិភាពដល់ការណែនាំ `Retry-After` ពី upstream នៅពេល provider ផ្ញើវា)។

### ការទប់ស្កាត់ការប្រែប្រួលញឹកញាប់

ថ្នាក់ដែលទើបតែកំណត់ឡើងវិញ ត្រូវបានអនុញ្ញាតឱ្យចូលវិញតែនៅពេលវាលើស `reentryMinRemainingPercent` (លំនាំដើម 5) ខណៈដែលការតភ្ជាប់ដែលកំពុងប្រើ ត្រូវការតែរក្សាឱ្យនៅលើស `exitCutoffPercent` (លំនាំដើម 2 ដែលត្រូវគ្នានឹង `quotaPreflight.defaultThresholdPercent`)។ គម្លាតនេះគឺជា hysteresis band — បើគ្មានវាទេ ការតភ្ជាប់ដែលស្ថិតនៅជិតកម្រិតកាត់ផ្តាច់ នឹងលោតទៅមករវាងថ្នាក់នៅរាល់ request បន្តបន្ទាប់។

## ការផ្សំ

`subscription` និង `thrifty` ជាតម្លៃ `AutoTier` ដូច្នេះពួកវាអាចផ្សំជាមួយគ្រប់ប្រភេទ៖
`auto/coding:thrifty`, `auto/reasoning:subscription` និងផ្សេងៗទៀត។ id រាបស្មើទាំងពីរ
(`auto/subscription`, `auto/thrifty`) ត្រូវបានបង្ហាញនៅក្នុង `/v1/models` និង dashboard។

id ទាំងពីរមិនមែនជា paid-tier ទេ ដូច្នេះ `isPaidTierAutoId()` ត្រឡប់ `false` សម្រាប់ទាំងពីរ ហើយ
`auto/subscription` នៅតែមានបន្ទាប់ពី `hidePaidModels`។
