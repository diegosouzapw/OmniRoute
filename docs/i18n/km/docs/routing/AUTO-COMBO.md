### ការផ្សំ Category × Tier (`auto/<category>:<tier>`)

suffix បែប OpenRouter បំបែក **ប្រភេទផ្លូវ** (category) ចេញពី **របៀបបង្កើនប្រសិទ្ធភាពរបស់វា** (tier) ដូច្នេះអ្នកអាចផ្សំពួកវាបានដោយសេរី (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`)៖

- **Category** (ត្រងបណ្តុំ candidate តាមសមត្ថភាព)៖ `coding` · `reasoning` · `vision` · `chat` · `multimodal`។ `vision`/`multimodal` រក្សាទុក model ដែលគាំទ្រ vision; `reasoning` រក្សាទុក model សម្រាប់ reasoning/thinking។
- **Tier** (ជ្រើសរើសទម្ងន់ដាក់ពិន្ទុ / តម្រងបណ្តុំ)៖ `fast` (ដាក់ឱ្យប្រើបានរហ័ស) · `cheap` (alias `floor` ដែលសន្សំថ្លៃដើម) · `reliable` (សុខភាព circuit-breaker + ស្ថិរភាព latency) · `free` / `pro` (ត្រងបណ្តុំតាម tier របស់ model តាមរយៈ `classifyTier` — free-tier ទល់នឹង premium)។

| ឧទាហរណ៍                | ត្រូវបានដោះស្រាយទៅជា                                                  |
| ---------------------- | --------------------------------------------------------------------- |
| `auto/coding:fast`     | បណ្តុំ coding និងទម្ងន់ latency ទាប                                   |
| `auto/coding:cheap`    | បណ្តុំ coding ដែលបង្កើនប្រសិទ្ធភាពថ្លៃដើម (alias `auto/coding:floor`) |
| `auto/reasoning:pro`   | តែ model សម្រាប់ reasoning/thinking និង premium tier                  |
| `auto/vision`          | model ដែលគាំទ្រ vision (គ្មាន tier → ទម្ងន់មានតុល្យភាព)               |
| `auto/multimodal:free` | model ដែលគាំទ្រ multimodal និងមានតែ free tier                         |

`auto/<category>[:<tier>]` ដែលត្រឹមត្រូវណាមួយត្រូវបានដោះស្រាយតាមតម្រូវការ; សំណុំរងដែលបានជ្រើសរើសដោយប្រុងប្រយ័ត្នត្រូវបានបង្ហាញនៅក្នុង `/v1/models` និង dashboard (`AUTO_SUFFIX_VARIANTS` ក្នុង `open-sse/services/autoCombo/builtinCatalog.ts`)។ ការត្រងគឺ **fail-open** — ប្រសិនបើលក្ខខណ្ឌមួយមិនត្រូវនឹង model ដែលបានភ្ជាប់ណាមួយទេ បណ្តុំពេញលេញនឹងត្រូវបានប្រើ ដើម្បីកុំឱ្យការកំណត់ផ្លូវខូច។ core scorer (`combo.ts`) មិនត្រូវបានផ្លាស់ប្តូរទេ; តម្រង category/tier ត្រូវបានអនុវត្តក្នុង `buildAutoCandidates`។

> **ទិន្នន័យឆ្លាតវៃរបស់ model ជាក់ស្តែង៖** ភាពសមស្របនៃការកំណត់ផ្លូវដោយស្វ័យប្រវត្តិ ទទួលព័ត៌មានពីចំណាត់ថ្នាក់ **Arena ELO** ជាក់ស្តែង + ទិន្នន័យ tier របស់ **models.dev** នៅពេល flag `ARENA_ELO_SYNC_ENABLED` បើក (បើមិនដូច្នោះទេ នឹងត្រឡប់ទៅប្រើផែនទី fitness ថេរ)។

**របៀបប្រើ៖**

```bash
# IDE ឬឧបករណ៍ CLI ណាមួយដែលគាំទ្រទម្រង់ OpenAI
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# ក្នុងកូដ/ការកំណត់រចនាសម្ព័ន្ធរបស់អ្នក កំណត់ model ទៅជា៖
model: "auto"                 # លំនាំដើមមានតុល្យភាព
model: "auto/coding"          # ល្អបំផុតសម្រាប់កិច្ចការសរសេរកូដ
model: "auto/fast"            # ជម្រើសលឿនបំផុតដែលអាចប្រើបាន
model: "auto/cheap"           # ថោកបំផុតក្នុងមួយ token
```

**អ្វីដែលកើតឡើង៖**

1. OmniRoute រកឃើញ `auto/` prefix ក្នុង `src/sse/handlers/chat.ts`
2. ស្វែងរក **ការតភ្ជាប់ provider សកម្ម** ទាំងអស់ពី database
3. ត្រងយកការតភ្ជាប់ដែលមាន credential ត្រឹមត្រូវ (API key ឬ OAuth token)
4. កំណត់ model ក្នុងមួយការតភ្ជាប់ (`connection.defaultModel` ឬ model ដំបូងរបស់ provider)
5. បង្កើត **virtual combo** ក្នុង memory (មិនត្រូវបានរក្សាទុកក្នុង DB)
6. កំណត់ផ្លូវដោយប្រើប្រវត្តិរូបទម្ងន់របស់វ៉ារ្យ៉ង់ដែលបានជ្រើសរើស + យុទ្ធសាស្ត្រ LKGP

**លក្ខណៈសម្បត្តិសំខាន់ៗ៖**

- ✅ **ដំណើរការជានិច្ច៖** មិនចាំបាច់មាន toggle មិនចាំបាច់បង្កើត combo និងមិនចាំបាច់កំណត់រចនាសម្ព័ន្ធ
- ✅ **Dynamic៖** ឆ្លុះបញ្ចាំង provider ដែលបានភ្ជាប់បច្ចុប្បន្នដោយស្វ័យប្រវត្តិ
- ✅ **ភាពជាប់លាប់នៃ session៖** LKGP ធានាថា provider ដែលជោគជ័យចុងក្រោយត្រូវបានផ្តល់អាទិភាព
- ✅ **គាំទ្រគណនីច្រើន៖** ការតភ្ជាប់ provider នីមួយៗក្លាយជា candidate ដាច់ដោយឡែក
- ✅ **មិនសរសេរទៅ DB៖** Virtual combo មានតែសម្រាប់ request ប៉ុណ្ណោះ ដោយគ្មានបន្ទុកលើសពីការរក្សាទុក

### ការគ្រប់គ្រង candidate តាម key នីមួយៗ (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = suffix ដែលនៅបន្ទាប់ពី `auto/` ឬ
ពាក្យ `auto` ផ្ទាល់សម្រាប់ channel មូលដ្ឋាន) គឺជា endpoint **បានតែអាន** ដែលរាយបញ្ជី
បណ្តុំ candidate បច្ចុប្បន្នរបស់ channel `auto/*` ដោយភ្ជាប់ជាមួយស្ថានភាពអាចចូលដល់បានជាក់ស្តែង និងប្រើឡើងវិញនូវ
ការអាន resilience ដែលមានស្រាប់ (មិនដែលអាន breaker `state` ដោយផ្ទាល់ទេ)៖

## ការហៅ Custom Combo ពី Client

Combo ដែលបានរក្សាទុក (Settings → Combos) ត្រូវបានប្រើតែនៅពេល client ផ្ញើ **ឈ្មោះពិតប្រាកដ** របស់ combo នៅក្នុង field `model` ប៉ុណ្ណោះ — មិនមានការផ្គូផ្គងឈ្មោះ combo ដោយប្រហាក់ប្រហែល ឬដោយផ្នែកទេ ហើយក៏មិនពាក់ព័ន្ធនឹង prefix `auto/` ដែរ។ លំដាប់នៃការដោះស្រាយ (`getComboForModel()` នៅក្នុង `src/sse/services/model.ts`)៖

1. ផ្គូផ្គងឈ្មោះ combo ដូចគ្នាបេះបិទ (`model: "my-combo"`),
2. prefix `combo/<name>` (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`)។

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

ចំណុចងាយច្រឡំដែលជួបញឹកញាប់ពីរ៖

- **`auto` មិនប្រើ combos របស់អ្នកទេ។** `auto`/`auto/*` បង្កើត candidate pool ដែលមិនត្រូវការការកំណត់រចនាសម្ព័ន្ធដោយខ្លួនឯង ហើយពិគ្រោះ combo ដែលបានរក្សាទុកតែក្នុងករណីដែលមាន combo មួយឈ្មោះ `auto` ពិតប្រាកដប៉ុណ្ណោះ (មិនត្រូវបានណែនាំ)។ ដើម្បី route តាមរយៈ combo សូមផ្ញើឈ្មោះពិតប្រាកដរបស់វា — មិនមែន `auto` ទេ។
- **`openrouter/auto` គឺជាផលិតផល OpenRouter បង់ប្រាក់ពិតប្រាកដ** ("Auto Best Available") មិនមែនជា alias របស់ OmniRoute ទេ។ វាគឺជាធាតុ static model តែមួយគត់នៃ OpenRouter registry (`open-sse/config/providers/registry/openrouter/index.ts`) ហើយត្រូវបានគិតថ្លៃដោយឡែក។ ប្រើ Settings → Routing → Hide paid models ដើម្បីដកវាចេញពី `auto` pools។

សូមមើល [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) និង [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) សម្រាប់ភាពច្រឡំដំបូងដែលឯកសារនេះពន្យល់។

## របៀបដែលវាដំណើរការ (Auto-Combos ដែលត្រូវបានរក្សាទុក)

Auto-Combo Engine ជ្រើសរើស provider/model ដែលល្អបំផុតដោយថាមវន្តសម្រាប់សំណើនីមួយៗ ដោយប្រើ **អនុគមន៍ដាក់ពិន្ទុដែលមាន 16 កត្តា** (កំណត់នៅក្នុង `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`)។ ទម្ងន់លំនាំដើមមានផលបូកស្មើនឹង `1.0`; ទម្ងន់ផ្ទាល់ខ្លួនត្រូវបានធ្វើឱ្យមានលក្ខណៈស្តង់ដារឡើងវិញដោយ `normalizeScoringWeights()`។ កត្តាពីរក្នុងចំណោមកត្តាទាំងដប់ប្រាំមួយ — `cacheAffinity` និង `resetWindowAffinity` — មានទម្ងន់លំនាំដើម `0`; `reliability` មានទម្ងន់ `0` នៅក្នុង `DEFAULT_WEIGHTS` ប៉ុន្តែមាន `0.03` នៅក្នុងកញ្ចប់ទូទៅ និង `0.04` នៅក្នុង `reliability-first` ហើយ `quality` មានទម្ងន់ `0.02` នៅក្នុងកញ្ចប់ (`0.03` នៅក្នុង `quality-first`)៖ កត្តាទាំងនេះនៅតែត្រូវបានគណនាសម្រាប់បេក្ខជននីមួយៗ ហើយ `cacheAffinity` គ្រប់គ្រងការលុបទិន្នន័យស្ទួននៃឃ្លាំងសម្ងាត់ prompt នៅក្រៅពិន្ទុ ដូច្នេះកត្តាដែលមានទម្ងន់លំនាំដើមសូន្យគ្រាន់តែមិនចូលរួមបោះឆ្នោតតាមលំនាំដើម ខណៈដែលកញ្ចប់នានាចូលរួម។

  ស្មើនឹង 0។

  (`open-sse/services/combo/targetResolution.ts`) ដូច្នេះ ជំហានតែមួយដែលដំណើរការល្អអាចឈ្នះគ្រប់សំណើជាបណ្តោះអាសន្ន។

  ចំនួនជោគជ័យជាប់ៗគ្នាតាមការកំណត់ មុនពេលចាប់ឆ្នោតឡើងវិញ។

### របៀប pipeline បែប Agentic

បន្សំ `pipeline` ដែលមានម៉ូដែលយ៉ាងហោចណាស់ពីរ អាចជ្រើសប្រើការបញ្ជូនទិសដៅតាម planner/executor ដោយប្រើ
`config.agenticOrchestration.enabled`។ គោលដៅទីមួយទទួលខុសត្រូវលើការរៀបចំផែនការ និងចម្លើយចុងក្រោយ;
គោលដៅទីពីរបញ្ចេញការហៅឧបករណ៍តាមទម្រង់ដើមរបស់ client។ OmniRoute រកឃើញការបន្ត
ពីលទ្ធផលឧបករណ៍តាម protocol នៃសំណើ សួរ planner ថាតើត្រូវការជុំឧបករណ៍មួយទៀតឬអត់
ហើយជ្រើស executor ឬ planner យ៉ាងថាមវន្តឱ្យធ្វើជាជំហានចុងក្រោយដែលបង្ហាញទៅ client។

ម៉ូដែលបន្ថែមបន្ទាប់ពីគោលដៅទីពីរ ត្រូវបានតម្រៀបជាម៉ូដែលបម្រុងរបស់ executor។ ការឆ្លើយតប
HTTP ដែលបរាជ័យ ឬ transport exception នឹងបន្តទៅ executor បន្ទាប់ ដោយរក្សា
ការសម្រេចចិត្តដដែលរបស់ planner និងឧបករណ៍ដើម ប៉ុន្តែប្រើ step prompt និង
ការតភ្ជាប់ដែលបានដោះស្រាយរបស់ executor នោះផ្ទាល់។ ការឆ្លើយតបជោគជ័យដំបូងត្រូវបានបញ្ជូនត្រឡប់ដោយមិនកែប្រែ រួមទាំង
ការផ្សាយ SSE; ការបរាជ័យបន្ទាប់ពីការផ្សាយជោគជ័យបានចាប់ផ្តើម មិនអាចសាកល្បងឡើងវិញនៅទីនេះបានទេ។
ប្រសិនបើ executor ទាំងអស់បរាជ័យ ការបរាជ័យចុងក្រោយនឹងត្រូវបានបញ្ជូនត្រឡប់។ ការបោះបង់ដោយ client នឹងបញ្ឈប់ការបញ្ជូន។

## យុទ្ធសាស្ត្រ Fusion

   វាកំណត់ផលប៉ះពាល់របស់ម៉ូដែលយឺតបំផុតលើពេលវេលាជាក់ស្តែង ដោយមាន hard timeout ជាព្រំដែន។
3. **ការសំយោគដោយ judge** — ចម្លើយរបស់ panel ត្រូវបានលាក់អត្តសញ្ញាណ (`Source 1`, `Source 2`, … — ដើម្បីឱ្យ
   judge ថ្លឹងថ្លែងលើខ្លឹមសារ មិនមែនម៉ាកម៉ូដែល) ហើយប្រគល់ទៅ judge ដែលនឹងវិភាគ
   មតិស្របគ្នា / ភាពផ្ទុយគ្នា / វិសាលភាពគ្របដណ្តប់មិនពេញលេញ / ការយល់ដឹងពិសេស / ចំណុចខ្វះខាត បន្ទាប់មក
   សរសេរចម្លើយដែលមានសិទ្ធិអំណាច **តែមួយ**។ ការហៅ judge រក្សាទុក
   flag `stream` ដើមរបស់ client + tools ដូច្នេះ streaming និងការប្រើ tool នៅដំណាក់កាលបន្ទាប់នៅតែដំណើរការ។
4. **ការបន្ថយសមត្ថភាពដោយរលូន** — គ្មានចម្លើយពី panel → `503`; មានតែអ្នកនៅសល់ 1 → ចម្លើយនោះ
   ត្រូវបានត្រឡប់ដោយផ្ទាល់ (គ្មានអ្វីត្រូវបញ្ចូលគ្នា); panel ដែលមានម៉ូដែលតែមួយឆ្លើយតបដោយផ្ទាល់។

combo ដែលបានយោង មិនមែនការបញ្ជូនទៅគ្រប់គោលដៅរបស់ combo នោះទេ) ជាមួយការការពារជម្រៅ/cycle ដូចគ្នា

## រោងចក្រ Auto-Combo និម្មិត

ម៉ាស៊ីន Auto Combo មិនតម្រូវឱ្យមាន combo ដែលបានកំណត់ជាមុនទេ។ ផ្ទុយទៅវិញ `open-sse/services/autoCombo/virtualFactory.ts` បង្កើត candidate ភ្លាមៗតាមតម្រូវការ៖

1. ទាញយក `getProviderConnections({ isActive: true })` (connection ទាំងអស់ដែលបានបើកដំណើរការ)
2. ច្រោះយកតែ connection ដែលមាន credential ត្រឹមត្រូវ (API key ឬ OAuth token ដែលមិនទាន់ផុតកំណត់ តាមរយៈ `hasUsableOAuthToken()`)
3. ផ្ទៀងផ្ទាត់ជាមួយ `getProviderRegistry()` សម្រាប់ភាពអាចប្រើបាននៃ model និងតម្លៃ
4. សម្រាប់ tuple នីមួយៗ `(provider, model, connection)` បង្កើត `VirtualAutoComboCandidate`
5. ជ្រើសរើស `connection.defaultModel` (ឬ model ដំបូងរបស់ registry) ជាគោលដៅ dispatch
6. ដាក់ពិន្ទុ candidate នីមួយៗដោយប្រើ `scorePool()` ដែលមាន 16 កត្តា និងកញ្ចប់ weight របស់ variant
7. ត្រឡប់ `AutoComboConfig` ក្នុង memory ដែលទទួលបានសម្រាប់ `handleComboChat()` — មិនដែលរក្សាទុកទៅ DB ទេ

នេះមានន័យថា **ការបន្ថែម provider ថ្មីដែលបានបើក `auto/*` នឹងពង្រីក candidate pool ដោយស្វ័យប្រវត្តិ** — មិនចាំបាច់កែសម្រួល combo ដោយដៃទេ។ Virtual combo ត្រូវបានបង្កើតឡើងវិញសម្រាប់ request នីមួយៗ ដូច្នេះ connection ដែលទើបបន្ថែមថ្មី ឬទើបមានស្ថានភាពល្អឡើងវិញ នឹងត្រូវបានយកមកប្រើភ្លាមៗ។

## ការស្ដារឡើងវិញដោយស្វ័យប្រវត្តិ

- **ការដកចេញបណ្ដោះអាសន្ន**៖ ពិន្ទុ < 0.2 → ដកចេញរយៈពេល 5 នាទី (progressive backoff អតិបរមា 30 នាទី)
- **ការយល់ដឹងអំពី circuit breaker**៖ OPEN → ដកចេញដោយស្វ័យប្រវត្តិ; HALF_OPEN → request សាកល្បង
- **Incident mode**៖ >50% OPEN → បិទ exploration និងបង្កើនស្ថិរភាពឱ្យដល់អតិបរមា
- **ការស្ដារឡើងវិញក្រោយ cooldown**៖ បន្ទាប់ពីការដកចេញ request ដំបូងគឺជា "probe" ដែលមាន timeout តិចជាងមុន

## Bandit Exploration

5% នៃ request (អាចកំណត់បាន) ត្រូវបាន route ទៅ provider ចៃដន្យសម្រាប់ exploration។ វាត្រូវបានបិទនៅក្នុង incident mode។

## API

**មិនមាន endpoint `POST /api/combos/auto` ដាច់ដោយឡែកទេ** — Auto-Combo ត្រូវបានប្រើប្រាស់តាមពីរវិធី៖

1. **គ្មានការកំណត់រចនាសម្ព័ន្ធ (ត្រូវបានណែនាំ):** ផ្ញើសំណើ chat completion ណាមួយដោយប្រើ `model: "auto"` ឬ `model: "auto/<variant>"`។ virtual factory បង្កើត combo សម្រាប់សំណើនីមួយៗ — មិនត្រូវការការរក្សាទុកជាអចិន្ត្រៃយ៍ ហើយក៏មិនត្រូវការការហៅ API ដែរ។

2. **Combo ដែលបានរក្សាទុកជាមួយ `strategy: "auto"`:** បង្កើត combo ធម្មតាតាមរយៈ `POST /api/combos` ហើយកំណត់ `strategy: "auto"` រួមជាមួយ `config.auto.weights` / `config.auto.candidatePool`។ វាប្រើ scoring engine ដូចគ្នា; combo ត្រូវបានរក្សាទុកក្នុង `combos` ហើយអាចប្រើឡើងវិញតាម ID។

សម្រាប់ការស្វែងរក `GET /api/combos/auto` បង្ហាញ variant ទាំងអស់ជាមួយ candidate pool ដែលបានដោះស្រាយ ព្រមទាំង `context_length` / `max_output_tokens` — តម្លៃ MAX ក្នុងចំណោម window របស់ candidate pool។ Client (ឧ. opencode plugin) ត្រូវតែប្រកាសតម្លៃទាំងនេះជំនួសឱ្យ `0`៖ context សូន្យនឹងបិទ auto-compaction របស់ opencode ទាំងស្រុង ដែលអនុញ្ញាតឱ្យ session កើនឡើងរហូតដល់ការសម្អាត history របស់ gateway បំផ្លាញ context។ ការប្រកាស MAX មានសុវត្ថិភាព ព្រោះ context pre-filter របស់ auto-combo នឹងបញ្ជូនសំណើដែលមានទំហំធំពេកទៅកាន់ candidate ដែលមាន window ធំ។

### យុទ្ធសាស្ត្រ auto router

Combo `strategy: "auto"` ដែលបានរក្សាទុកអាចកំណត់ `config.routerStrategy` (ឬ
`config.auto.routerStrategy` ចាស់) ទៅជាមួយក្នុងចំណោម៖

- `rules` — weighted scoring លំនាំដើម
- `score` — ជ្រើសរើស weighted score ដែលបានកំណត់រចនាសម្ព័ន្ធខ្ពស់បំផុត។ នៅពេលពិន្ទុស្មើគ្នាទាំងស្រុង វារក្សាលំដាប់
  candidate ដែលបានកំណត់រចនាសម្ព័ន្ធ; `explorationRate` ដែលមានស្រាប់យក sample ពី ranked pool ទាំងមូល។
- `cost` / `eco` — provider ដែលមានស្ថានភាពល្អ និងថោកបំផុត
- `latency` / `fast` — p95 latency ទាបបំផុត ដោយមានពិន័យលើភាពអាចទុកចិត្តបាន
- `sla-aware` / `sla` — ផ្តល់អាទិភាពដល់ candidate ដែលបំពេញតាម p95 latency, error-rate និង
  cost SLO ជាជម្រើស
- `lkgp` — provider ដែលបានដឹងថាល្អចុងក្រោយជាមុន
- `nadir` — ស្នើឱ្យ decision API របស់ [Nadir](https://getnadir.com) កំណត់ថាតើ prompt ត្រូវការ model មួយណាក្នុង pool;
  ត្រូវជ្រើសរើសបើកប្រើ និង fail-open ទៅ `rules`

យុទ្ធសាស្ត្រនីមួយៗជ្រើសរើស provider មួយពី candidate pool ដោយផ្អែកលើ `RoutingContext`
(ប្រភេទ task, សញ្ញាបង្ហាញ tool/vision, ការប៉ាន់ស្មាន token, គោលការណ៍ SLA ជាជម្រើស និង
provider ដែលបានដឹងថាល្អចុងក្រោយជាជម្រើស)។

#### 1. `rules` (លំនាំដើម) — weighted scoring ដែលមាន 16 កត្តា

រុំ scoring engine ដែលមានស្រាប់។ ច្រោះ candidate ដែលមាន circuit-breaker
`OPEN` ចេញ បន្ទាប់មកដំណើរការ `scorePool()` ជាមួយប្រភេទ task បច្ចុប្បន្ន និង `getTaskFitness()`
ហើយជ្រើសរើស provider ដែលមានពិន្ទុខ្ពស់បំផុត។

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**ពេលគួរប្រើ**: លំនាំដើម។ ប្រើនៅពេលអ្នកចង់បានតុល្យភាពរវាងសញ្ញាទាំងអស់។

**ឈ្មោះជំនួស**: `rules` (គ្មានឈ្មោះជំនួស)

#### 2. `cost` / `eco` — provider ដែលមានស្ថានភាពល្អ និងថោកបំផុត

តម្រៀប candidate pool តាម `costPer1MTokens` (ពីតូចទៅធំ) ហើយជ្រើសរើសតម្លៃថោកបំផុត។
ច្រោះ candidate ដែលមាន `OPEN` ចេញជាមុន។

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ពេលគួរប្រើ**: Workload ដែលផ្តោតលើការសន្សំចំណាយ, batch processing ឬ background job។

**ឈ្មោះជំនួស**: `cost`, `eco`

#### 3. `latency` / `fast` — p95 latency ទាបបំផុត ដោយមានពិន័យលើភាពអាចទុកចិត្តបាន

តម្រៀបតាម `p95LatencyMs + (errorRate * 1000)`។ ការពិន័យលើ error-rate ធានាថា
provider ដែលមិនអាចទុកចិត្តបាននឹងមានចំណាត់ថ្នាក់ទាបជាង ទោះបី latency ដែលបានប្រកាសរបស់ពួកវាទាបក៏ដោយ។

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ពេលគួរប្រើ**: Workload ដែលផ្តោតលើ latency ដូចជា chat ពេលវេលាជាក់ស្តែង, autocomplete ឬ
ជំនួយការសរសេរកូដអន្តរកម្ម។

**ឈ្មោះជំនួស**: `latency`, `fast`

#### 4. `sla-aware` / `sla` — ការអនុលោមតាម latency/error/cost SLO

ផ្តល់ពិន្ទុឱ្យ candidate នីមួយៗដោយផ្អែកលើកម្រិតដែលវាបំពេញតាមគោលការណ៍ SLO ដែលបានកំណត់រចនាសម្ព័ន្ធ៖

| កត្តា          | ទម្ងន់ | រូបមន្ត                                           |
| -------------- | ------ | ------------------------------------------------- |
| ពិន្ទុ latency | 35%    | `threshold / max(value, ε)`                       |
| ពិន្ទុកំហុស    | 35%    | `threshold / max(value, ε)`                       |
| ពិន្ទុសុខភាព   | 15%    | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| ពិន្ទុតម្លៃ    | 10%    | `threshold / max(value, ε)` ឬ inverse normalized  |
| ពិន្ទុស្ថិរភាព | 5%     | inverse normalized latency stddev                 |

នៅពេល `hardConstraints: true` បេក្ខជនត្រូវបានតម្រៀបជាចម្បងតាម **ពិន្ទុបំពាន**
(កម្រិតដែលពួកគេលើសពី SLO ណាមួយ) បន្ទាប់មកតាមពិន្ទុសមាស។ បើមិនដូច្នោះទេ វាគ្រាន់តែ
តម្រៀបតាមពិន្ទុសមាសប៉ុណ្ណោះ។

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... ដាក់ពិន្ទុឱ្យបេក្ខជននីមួយៗធៀបនឹងគោលការណ៍៖ { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**វាល SLA** (កំណត់នៅក្នុង combo config)៖

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**ពេលណាត្រូវប្រើ**៖ បន្ទុកការងារ production ដែលមានកម្រិតកំណត់តឹងរ៉ឹងលើ latency, អត្រាកំហុស ឬថវិកាចំណាយ។

**ឈ្មោះហៅក្រៅ**៖ `sla-aware`, `sla`

#### 5. `lkgp` — សាកល្បង provider ល្អដែលស្គាល់ចុងក្រោយជាមុន

សាកល្បង **provider ល្អដែលស្គាល់ចុងក្រោយ** (ប្រសិនបើបានកំណត់) ជាមុន បន្ទាប់មកប្ដូរទៅប្រើ
យុទ្ធសាស្ត្រ `rules`។ មានប្រយោជន៍សម្រាប់ការរក្សាភាពជាប់លាប់នៃ session — provider ដដែលគ្រប់គ្រង
សំណើបន្តនៅក្នុងកិច្ចសន្ទនា។

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // ប្ដូរទៅប្រើយុទ្ធសាស្ត្រ rules
    return getStrategy("rules").select(pool, context);
  }
}
```

**ពេលណាត្រូវប្រើ**៖ កិច្ចសន្ទនាច្រើនវេន ដែលអ្នកចង់ឱ្យ provider ដដែលគ្រប់គ្រង
សំណើបន្ត (ឧ. សម្រាប់ caching, ភាពបន្តនៃ context ឬភាពស្របគ្នានៃតម្លៃ)។

**ឈ្មោះហៅក្រៅ**៖ `lkgp` (គ្មានឈ្មោះហៅក្រៅ)

#### 6. `nadir` — ជ្រើសរើស model ដោយយល់ដឹងពី prompt តាមរយៈ Nadir

យុទ្ធសាស្ត្រទាំងអស់ខាងលើដាក់ចំណាត់ថ្នាក់បេក្ខជនតាម telemetry ផ្ទាល់ខ្លួនរបស់ពួកគេ ហើយគ្មានយុទ្ធសាស្ត្រណាមួយអាន
សំណើនោះទេ។ `nadir` ផ្ញើវេនចុងក្រោយរបស់អ្នកប្រើ ព្រមទាំង model ids របស់ pool ទៅកាន់
API សម្រេចចិត្តរបស់ [Nadir](https://getnadir.com) (`POST /v1/bucket`) ហើយបញ្ជូនទៅកាន់ model
ដែល Nadir ជ្រើសរើសពីបញ្ជីនោះ (`simple` → model ដែលមានសមត្ថភាពគ្រប់គ្រាន់ និងថោកបំផុត, `complex` →
model កម្រិត frontier)។ connection ដែលបម្រើ model នោះនៅតែត្រូវបានជ្រើសរើសដោយ `rules` ដូច្នេះ quota,
សុខភាព និងតម្លៃនៅតែជាកត្តាកំណត់ថាត្រូវប្រើ account មួយណា។

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` និង `OMNIROUTE_NADIR_BASE_URL` ជា env fallback សម្រាប់ string ទាំងពីរ។
`baseUrl` ត្រូវការតែសម្រាប់ Nadir ដែល self-hosted ប៉ុណ្ណោះ (អាចមាន `/v1` នៅខាងចុងបាន)។
ការហៅដោយគ្មាន key នឹងចូលទៅកាន់កម្រិត anonymous របស់ Nadir ដែលត្រូវបានកំណត់អត្រាតាម IP។

អ្វីដែលចាកចេញពីប្រព័ន្ធ៖ អត្ថបទសារចុងក្រោយរបស់អ្នកប្រើ (16k តួអក្សរដំបូង), model ids
របស់បេក្ខជន និងស្លាក channel `source: "omniroute"`។ គ្មាន system prompt, history, tools ឬ
headers ទេ។

ឥរិយាបថពេលបរាជ័យគឺ fail-open៖ timeout (លំនាំដើម 2000 ms), non-2xx, host ដែលមិនអាចតភ្ជាប់បាន,
response ដែលមានទម្រង់មិនត្រឹមត្រូវ ឬជម្រើសដែលនៅក្រៅ pool នឹងប្ដូរទៅការសម្រេចចិត្តរបស់ `rules`
ហើយ reason នឹងមានបុព្វបទ `NadirStrategy: fallback (…)`។ បន្ទាប់ពីការហៅបរាជ័យ យុទ្ធសាស្ត្រនេះ
រំលង network រយៈពេល 30 s ដូច្នេះការដាច់ដំណើរការមួយចំណាយត្រឹមមួយ timeout ក្នុងរៀងរាល់ 30 s ជាជាង
មួយក្នុងមួយសំណើ។ routing events រាយការណ៍ `strategy: "nadir"` តែនៅពេល Nadir ពិតជាបាន
ធ្វើការជ្រើសរើសប៉ុណ្ណោះ។

**ពេលណាត្រូវប្រើ**៖ traffic ដែលមានកម្រិតលំបាកចម្រុះនៅលើ pool ដែលមាន model ជាច្រើនកម្រិត (model តូច មធ្យម
និង frontier) ដែលអ្នកចង់កាត់បន្ថយការចំណាយពីការប្រើ frontier ជានិច្ច។

**ឈ្មោះហៅក្រៅ**៖ `nadir` (គ្មានឈ្មោះហៅក្រៅ)

### យុទ្ធសាស្ត្រ router ផ្ទាល់ខ្លួន

អ្នកអាចចុះឈ្មោះ implementation `RouterStrategy` ផ្ទាល់ខ្លួនតាមរយៈ API សាធារណៈ៖

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // ឡូជីខល routing របស់អ្នកនៅទីនេះ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

បន្ទាប់មកប្រើវា៖

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## ភាពសមស្របតាមកិច្ចការ

ម៉ូដែលជាង 30 ត្រូវបានវាយតម្លៃលើកិច្ចការ 6 ប្រភេទ (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`)។ គាំទ្រលំនាំ wildcard (ឧ. `*-coder` → ពិន្ទុខ្ពស់សម្រាប់ការសរសេរកូដ)។

## សង្ខេបអំពី Auto Variants

ដោយរាប់បញ្ចូលទាំង `auto` ដាច់ដោយឡែក (លំនាំដើម) និងតម្លៃ `AutoVariant` ទាំង 6 ដែលបានប្រកាសក្នុង `autoPrefix.ts` មាន **លេខសម្គាល់ម៉ូដែលដែលអាចហៅប្រើបានចំនួន 7**៖

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ផ្ទាល់រាយតម្លៃចំនួន 6; ជម្រើសទី 7 គឺ "គ្មានវ៉ារ្យ៉ង់" — `auto` ដាច់ដោយឡែក — ដែលត្រូវបានដោះស្រាយដោយ `parseAutoPrefix()` ជា `variant: undefined`។)

## របៀបដែលកម្រិតត្រូវគ្នាជាមួយ Auto-Combo

មុខងារដាក់ពិន្ទុដែលមាន 16 កត្តា (`open-sse/services/autoCombo/scoring.ts`) ចាត់ទុកសមាជិកភាពកម្រិតជាសញ្ញាពីរ៖ `tierPriority` (0.0476) និង `tierAffinity` (0.0476)។ សូមមើល[តារាងកត្តាដាក់ពិន្ទុគោល](#how-it-works-persisted-auto-combos)ខាងលើ សម្រាប់សំណុំ `DEFAULT_WEIGHTS` ពេញលេញ — ការកំណត់ជំនួសតាមកញ្ចប់នីមួយៗ (ship-fast/cost-saver/quality-first/
offline-friendly) ត្រូវបានរាយក្នុងតារាង "ទម្រង់ទម្ងន់តាមកញ្ចប់"។

កម្រិតតែមួយមុខ **មិន**បង្ខំឱ្យកម្រិតទី 1 មកមុនទេ — ប្រសិនបើភាពយឺតយ៉ាវរបស់កម្រិតទី 1 មិនល្អ ឬតម្លៃធៀបនឹងគុណភាពមិនល្អប្រសើរ នោះកម្រិតទី 2 នឹងឈ្នះ។ ដើម្បីបង្ខំលំដាប់កម្រិត សូមប្រើយុទ្ធសាស្ត្របន្សំ `priority` ហើយរៀបចំអ្នកផ្តល់សេវាតាមកម្រិត។

ដើម្បីផ្តល់អាទិភាពខ្លាំងដល់កម្រិតទី 1 (ការជាវ) សូមបង្កើនទម្ងន់ `tierPriority`៖

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

សូមមើល [`docs/guides/TIERS.md`](../guides/TIERS.md) សម្រាប់និយមន័យកម្រិត និងការចាត់ថ្នាក់អ្នកផ្តល់សេវា។

## ការធ្វើតេស្ត និងវិសាលភាពគ្របដណ្តប់

### ម៉ាទ្រីសការសម្រេចចិត្តបញ្ជូនតាមផ្លូវបែបកំណត់ជាមុន (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` បញ្ជាក់អំពី **ការសម្រេចចិត្ត** បញ្ជូនតាមផ្លូវរបស់យុទ្ធសាស្ត្រសាធារណៈទាំង 19
ពីដើមដល់ចប់ តាមរយៈ pipeline combo ពិតប្រាកដ ដោយប្រើ upstream ក្លែងធ្វើ។
វិសាលភាពគ្របដណ្តប់រួមមាន៖

- យុទ្ធសាស្ត្រ `ROUTING_STRATEGY_VALUES` ទាំង 19 (ordered, weighted, cost, context, fusion, …)។
- `quota-share` (ខាងក្នុង) ពីដើមដល់ចប់៖ ភាពយុត្តិធម៌ DRR + ការបន្ថយអាទិភាពពេលឆ្អែត តាមរយៈ
  seam `selectQuotaShareTarget` ពិតប្រាកដ (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`)។
- វិសាលភាពគ្របដណ្តប់នៃការប្រគល់បន្តជាសកល `context-relay` នៅគ្រប់ចំនួនគោលដៅ។

សំណុំតេស្តនេះដំណើរការក្នុង CI (job `test:integration`) ជាមួយ `--test-concurrency=1` និង
`--test-force-exit` ដូច្នេះវាមានលទ្ធផលកំណត់ជាមុន និងមិនត្រូវការព័ត៌មានសម្ងាត់ពិតប្រាកដទេ។

### Smoke test ផ្ទាល់ដែលមានលក្ខខណ្ឌ (មិនមានក្នុង CI — providers ពិតប្រាកដ)

| ពាក្យបញ្ជា                             | អ្វីដែលវាធ្វើ                                                                                  |
| :------------------------------------- | :--------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | ការបញ្ជូនតាមផ្លូវពិតក្នុង process ជាមួយ `RUN_COMBO_LIVE=1`; ថត snapshot នៃ OmniRoute DB ផ្ទាល់ |
| `npm run test:combo:live:vps`          | ការហៅ HTTP ទៅកាន់ server OmniRoute ផ្ទាល់ (កំណត់ `COMBO_LIVE_BASE_URL`)                        |
| `npm run test:combo:live:vps:failover` | ដូចគ្នា ប៉ុន្តែមានសេណារីយ៉ូ failover ដែលបានបង្កើតឡើងដោយចេតនា                                   |

Smoke test ទាំងនេះសាកល្បងផ្លូវទំនាក់ទំនងពិតប្រាកដ (combo → provider → completion)។ ពួកវាត្រូវបាន
ដកចេញពី CI ដោយចេតនា ព្រោះវាត្រូវការព័ត៌មានសម្ងាត់ពិតប្រាកដ និងសិទ្ធិចូលប្រើ VPS។
