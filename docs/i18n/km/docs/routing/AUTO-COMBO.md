### សមាសភាពប្រភេទ × ថ្នាក់ (`auto/<category>:<tier>`)

បច្ច័យបែប OpenRouter បំបែក **ប្រភេទផ្លូវ** (ប្រភេទ) ចេញពី **របៀបបង្កើនប្រសិទ្ធភាពវា** (ថ្នាក់) ដូច្នេះអ្នកអាចផ្គុំវាបញ្ចូលគ្នាដោយសេរី (#4235 ដំណាក់កាល B, `open-sse/services/autoCombo/suffixComposition.ts`)៖

- **ប្រភេទ** (ច្រោះក្រុម candidate តាមសមត្ថភាព)៖ `coding` · `reasoning` · `vision` · `chat` · `multimodal`។ `vision`/`multimodal` រក្សាទុកម៉ូដែលដែលមានសមត្ថភាព vision; `reasoning` រក្សាទុកម៉ូដែល reasoning/thinking។
- **ថ្នាក់** (ជ្រើសរើសទម្ងន់នៃការដាក់ពិន្ទុ / តម្រងក្រុម)៖ `fast` (ដាក់ឱ្យប្រើបានរហ័ស) · `cheap` (ឈ្មោះក្លែងកាត់ `floor`, សន្សំថ្លៃដើម) · `reliable` (សុខភាព circuit-breaker + ស្ថិរភាព latency) · `free` / `pro` (ច្រោះក្រុមតាមថ្នាក់ម៉ូដែលតាមរយៈ `classifyTier` — ថ្នាក់ឥតគិតថ្លៃ ទល់នឹងថ្នាក់ premium)។

| ឧទាហរណ៍                | ដោះស្រាយទៅជា                                                                |
| ---------------------- | --------------------------------------------------------------------------- |
| `auto/coding:fast`     | ក្រុម coding, ទម្ងន់ latency ទាប                                            |
| `auto/coding:cheap`    | ក្រុម coding, បង្កើនប្រសិទ្ធភាពថ្លៃដើម (ឈ្មោះក្លែងកាត់ `auto/coding:floor`) |
| `auto/reasoning:pro`   | តែម៉ូដែល reasoning/thinking ប៉ុណ្ណោះ, ថ្នាក់ premium                        |
| `auto/vision`          | ម៉ូដែលដែលមានសមត្ថភាព vision (គ្មានថ្នាក់ → ទម្ងន់មានតុល្យភាព)               |
| `auto/multimodal:free` | ម៉ូដែលដែលមានសមត្ថភាព multimodal, តែថ្នាក់ឥតគិតថ្លៃប៉ុណ្ណោះ                  |

`auto/<category>[:<tier>]` ត្រឹមត្រូវណាមួយត្រូវបានដោះស្រាយតាមតម្រូវការ; សំណុំរងដែលត្រូវបានជ្រើសសម្រិតសម្រាំងត្រូវបានផ្សព្វផ្សាយក្នុង `/v1/models` និង dashboard (`AUTO_SUFFIX_VARIANTS` ក្នុង `open-sse/services/autoCombo/builtinCatalog.ts`)។ ការច្រោះគឺ **fail-open** — ប្រសិនបើលក្ខខណ្ឌមួយមិនត្រូវនឹងម៉ូដែលដែលបានភ្ជាប់ណាមួយទេ ក្រុមទាំងមូលនឹងត្រូវបានប្រើ ដើម្បីកុំឱ្យការកំណត់ផ្លូវខូចដំណើរការ។ កម្មវិធីដាក់ពិន្ទុស្នូល (`combo.ts`) មិនផ្លាស់ប្តូរទេ; តម្រងប្រភេទ/ថ្នាក់ត្រូវបានអនុវត្តក្នុង `buildAutoCandidates`។

> **ព័ត៌មានឆ្លាតវៃអំពីម៉ូដែលតាមពេលជាក់ស្តែង៖** ភាពសមស្របនៃការកំណត់ផ្លូវដោយស្វ័យប្រវត្តិទទួលព័ត៌មានពីចំណាត់ថ្នាក់ **Arena ELO** តាមពេលជាក់ស្តែង + ទិន្នន័យថ្នាក់ពី **models.dev** នៅពេល flag `ARENA_ELO_SYNC_ENABLED` បើក (បើមិនដូច្នោះទេ វានឹងត្រឡប់ទៅប្រើផែនទីភាពសមស្របថេរ)។

**របៀបប្រើ៖**

```bash
# IDE ឬឧបករណ៍ CLI ណាមួយដែលគាំទ្រទម្រង់ OpenAI
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# ក្នុងកូដ/ការកំណត់រចនាសម្ព័ន្ធរបស់អ្នក កំណត់ model ជា៖
model: "auto"                 # លំនាំដើមមានតុល្យភាព
model: "auto/coding"          # ល្អបំផុតសម្រាប់កិច្ចការសរសេរកូដ
model: "auto/fast"            # លឿនបំផុតដែលអាចប្រើបាន
model: "auto/cheap"           # ថោកបំផុតក្នុងមួយ token
```

**អ្វីដែលកើតឡើង៖**

1. OmniRoute រកឃើញបុព្វបទ `auto/` ក្នុង `src/sse/handlers/chat.ts`
2. សាកសួរ **ការតភ្ជាប់ provider ដែលសកម្ម** ទាំងអស់ពី database
3. ច្រោះយកតែការតភ្ជាប់ដែលមានព័ត៌មានសម្ងាត់ត្រឹមត្រូវ (API key ឬ OAuth token)
4. កំណត់ម៉ូដែលសម្រាប់ការតភ្ជាប់នីមួយៗ (`connection.defaultModel` ឬម៉ូដែលទីមួយរបស់ provider)
5. បង្កើត **combo និម្មិត** ក្នុងអង្គចងចាំ (មិនរក្សាទុកក្នុង DB)
6. កំណត់ផ្លូវដោយប្រើប្រវត្តិរូបទម្ងន់របស់វ៉ារ្យ៉ង់ដែលបានជ្រើសរើស + យុទ្ធសាស្ត្រ LKGP

**លក្ខណៈសម្បត្តិសំខាន់ៗ៖**

- ✅ **បើកជានិច្ច៖** មិនត្រូវការ toggle មិនត្រូវការបង្កើត combo និងមិនត្រូវការការកំណត់រចនាសម្ព័ន្ធ
- ✅ **ថាមវន្ត៖** ឆ្លុះបញ្ចាំង provider ដែលបានភ្ជាប់បច្ចុប្បន្នដោយស្វ័យប្រវត្តិ
- ✅ **ភាពជាប់លាប់នៃ session៖** LKGP ធានាថា provider ដែលបានជោគជ័យចុងក្រោយត្រូវបានផ្តល់អាទិភាព
- ✅ **យល់ដឹងអំពីគណនីច្រើន៖** ការតភ្ជាប់ provider នីមួយៗក្លាយជា candidate ដាច់ដោយឡែក
- ✅ **មិនសរសេរទៅ DB៖** combo និម្មិតមានសម្រាប់តែ request ប៉ុណ្ណោះ ដោយគ្មានបន្ទុក persistence

## ការហៅ Custom Combo ពី Client

Combo ដែលបានរក្សាទុក (Settings → Combos) ត្រូវបានប្រើតែនៅពេល client ផ្ញើ **ឈ្មោះពិតប្រាកដ** របស់ combo នៅក្នុង field `model` ប៉ុណ្ណោះ — មិនមានការផ្គូផ្គងឈ្មោះ combo ដោយប្រហាក់ប្រហែល ឬដោយផ្នែកទេ ហើយក៏មិនពាក់ព័ន្ធនឹង prefix `auto/` ដែរ។ លំដាប់នៃការដោះស្រាយ (`getComboForModel()` នៅក្នុង `src/sse/services/model.ts`)៖

1. ផ្គូផ្គងឈ្មោះ combo ដូចគ្នាបេះបិទ (`model: "my-combo"`),
2. prefix `combo/<name>` (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`)។

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

ចំណុចងាយច្រឡំដែលជួបញឹកញាប់ពីរ៖

- **`auto` មិនប្រើ combos របស់អ្នកទេ។** `auto`/`auto/*` បង្កើត candidate pool ដែលមិនត្រូវការការកំណត់រចនាសម្ព័ន្ធដោយខ្លួនឯង ហើយពិគ្រោះ combo ដែលបានរក្សាទុកតែក្នុងករណីដែលមាន combo មួយឈ្មោះ `auto` ពិតប្រាកដប៉ុណ្ណោះ (មិនត្រូវបានណែនាំ)។ ដើម្បី route តាមរយៈ combo សូមផ្ញើឈ្មោះពិតប្រាកដរបស់វា — មិនមែន `auto` ទេ។
- **`openrouter/auto` គឺជាផលិតផល OpenRouter បង់ប្រាក់ពិតប្រាកដ** ("Auto Best Available") មិនមែនជា alias របស់ OmniRoute ទេ។ វាគឺជាធាតុ static model តែមួយគត់នៃ OpenRouter registry (`open-sse/config/providers/registry/openrouter/index.ts`) ហើយត្រូវបានគិតថ្លៃដោយឡែក។ ប្រើ Settings → Routing → Hide paid models ដើម្បីដកវាចេញពី `auto` pools។

សូមមើល [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) និង [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) សម្រាប់ភាពច្រឡំដំបូងដែលឯកសារនេះពន្យល់។

## របៀបដែលវាដំណើរការ (Auto-Combos ដែលត្រូវបានរក្សាទុក)

Auto-Combo Engine ជ្រើសរើស provider/model ដែលល្អបំផុតដោយថាមវន្តសម្រាប់សំណើនីមួយៗ ដោយប្រើ **អនុគមន៍ដាក់ពិន្ទុដែលមាន 16 កត្តា** (កំណត់នៅក្នុង `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`)។ ទម្ងន់លំនាំដើមមានផលបូកស្មើនឹង `1.0`; ទម្ងន់ផ្ទាល់ខ្លួនត្រូវបានធ្វើឱ្យមានលក្ខណៈស្តង់ដារឡើងវិញដោយ `normalizeScoringWeights()`។ កត្តាពីរក្នុងចំណោមកត្តាទាំងដប់ប្រាំមួយ — `cacheAffinity` និង `resetWindowAffinity` — មានទម្ងន់លំនាំដើម `0`; `reliability` មានទម្ងន់ `0` នៅក្នុង `DEFAULT_WEIGHTS` ប៉ុន្តែមាន `0.03` នៅក្នុងកញ្ចប់ទូទៅ និង `0.04` នៅក្នុង `reliability-first` ហើយ `quality` មានទម្ងន់ `0.02` នៅក្នុងកញ្ចប់ (`0.03` នៅក្នុង `quality-first`)៖ កត្តាទាំងនេះនៅតែត្រូវបានគណនាសម្រាប់បេក្ខជននីមួយៗ ហើយ `cacheAffinity` គ្រប់គ្រងការលុបទិន្នន័យស្ទួននៃឃ្លាំងសម្ងាត់ prompt នៅក្រៅពិន្ទុ ដូច្នេះកត្តាដែលមានទម្ងន់លំនាំដើមសូន្យគ្រាន់តែមិនចូលរួមបោះឆ្នោតតាមលំនាំដើម ខណៈដែលកញ្ចប់នានាចូលរួម។

### អត្ថន័យរបស់ `weighted`

`weighted` គឺជា **ការចាប់យកដោយចៃដន្យតាមសមាមាត្រសម្រាប់សំណើនីមួយៗ**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`) មិនមែនជាយន្តការធ្វើឱ្យស្មើគ្នាទេ៖

- សំណើនីមួយៗចាប់យក **មួយ** ជំហានដោយមានប្រូបាប៊ីលីតេ `weight / totalWeight`; ជំហានដែលនៅសល់
  ត្រូវបានរៀបតាមទម្ងន់ពីធំទៅតូច ដើម្បីធ្វើជាខ្សែសង្រ្គោះបម្រុងសម្រាប់សំណើនោះ។
- ជំហានដែលមានទម្ងន់ `0` (ឬមិនបានកំណត់) **នឹងមិនត្រូវបានចាប់យកឡើយ** ខណៈដែលមានជំហានផ្សេងទៀត
  មានទម្ងន់ > 0 — វាអាចដំណើរការបានត្រឹមជាជម្រើសបម្រុង បន្ទាប់ពីជំហានដែលបានចាប់យកបរាជ័យប៉ុណ្ណោះ។ ការជ្រើសរើសនឹងក្លាយជាស្មើៗគ្នា លុះត្រាតែទម្ងន់ **ទាំងអស់**
  ស្មើនឹង 0។
- ជំហានដែលគោលដៅទាំងអស់មិនអាចប្រើបាន — circuit breaker របស់អ្នកផ្ដល់សេវាស្ថិតក្នុងស្ថានភាព `OPEN`, ការតភ្ជាប់
  កំពុងស្ថិតក្នុងរយៈពេលផ្អាក, ម៉ូដែលត្រូវបានចាក់សោមិនឱ្យប្រើ — នឹងត្រូវបានដកចេញពីការចាប់យក មុនពេលវាកើតឡើង
  (`open-sse/services/combo/targetResolution.ts`) ដូច្នេះជំហានដែលមានសុខភាពល្អតែមួយអាចឈ្នះគ្រប់សំណើជាបណ្ដោះអាសន្ន។
- `stickyWeightedLimit` (ការកំណត់រចនាសម្ព័ន្ធ combo, លំនាំដើម `1` = បិទ) ភ្ជាប់ទៅជំហានដែលបានចាប់យកសម្រាប់ចំនួនជោគជ័យជាប់ៗគ្នានោះ
  មុននឹងចាប់យកម្ដងទៀត។

សម្រាប់ការប្ដូរវេនយ៉ាងតឹងរ៉ឹង សូមប្រើ `round-robin`; ទម្ងន់ស្មើគ្នានៅលើ `weighted` ផ្ដល់តុល្យភាពបែបស្ថិតិ — មិនមែន
តុល្យភាពយ៉ាងតឹងរ៉ឹងទេ។

## យុទ្ធសាស្ត្រ Fusion

`fusion` គឺជាយុទ្ធសាស្ត្រតែមួយគត់ដែល **មិន** ជ្រើសរើសគោលដៅតែមួយ។ វាបញ្ជូន prompt
ទៅកាន់ **គ្រប់ម៉ូដែលក្នុង panel ស្របពេលគ្នា** បន្ទាប់មក **judge model** ដែលអាចកំណត់រចនាសម្ព័ន្ធបាន នឹងសំយោគ
ចម្លើយចុងក្រោយតែមួយពីចម្លើយទាំងអស់របស់ panel។ បានផ្ទេរមកពី upstream `decolua/9router`
(ការរចនា Fusion របស់ OpenRouter); ការអនុវត្តស្ថិតនៅក្នុង `open-sse/services/fusion.ts`។

របៀបដែលវាដំណើរការ៖

0. **ការរំលងសម្រាប់សំណើដែលមាន tool** — សំណើដែលមាន array `tools` មិនទទេ ហើយ
   `tool_choice` មិនត្រូវបានកំណត់យ៉ាងច្បាស់ជា `"none"` នឹងរំលង panel ទាំងស្រុង៖ វាត្រូវបានបញ្ជូនដោយផ្ទាល់ទៅ
   ម៉ូដែលតែមួយ (judge ដែលបានកំណត់ ឬ `panel[0]`) ដោយបញ្ជូន `tools`/`tool_choice`
   បន្តដោយមិនកែប្រែ។ សមាជិក panel មិនអាចចូលប្រើ tool បានទេ ហើយសេចក្តីណែនាំសំយោគរបស់ judge
   រារាំងការបញ្ចេញ tool-call ដូច្នេះ client ប្រភេទ agentic/tool-calling
   ទទួលបានការសម្រេចចិត្ត tool-call ពិតប្រាកដ ជំនួសឱ្យអត្ថបទដែលបានសំយោគ (#6771)។
1. **ការបញ្ជូនទៅច្រើនគោលដៅ** (សម្រាប់តែសំណើដែលគ្មាន tool) — prompt ត្រូវបានបញ្ជូនទៅគ្រប់ម៉ូដែលក្នុង panel
   ក្នុងពេលតែមួយ ដោយបង្ខំឱ្យមិនប្រើ streaming និងដក tools ចេញ (judge ត្រូវការអត្ថបទពេញលេញ
   ដើម្បីសំយោគ)។
2. **ការប្រមូលតាម quorum និងរយៈពេលអនុគ្រោះ** — នៅពេលចម្លើយចំនួន `minPanel` មកដល់ កម្មវិធីកំណត់ពេល
   អនុគ្រោះខ្លីមួយនឹងចាប់ផ្តើមសម្រាប់ចម្លើយដែលមកយឺត បន្ទាប់មក fusion នឹងបន្តជាមួយអ្វីៗដែលបានប្រមូល។
   វាកំណត់ផលប៉ះពាល់របស់ម៉ូដែលយឺតបំផុតលើពេលវេលាជាក់ស្តែង ដោយមាន hard timeout ជាព្រំដែន។
3. **ការសំយោគដោយ judge** — ចម្លើយរបស់ panel ត្រូវបានលាក់អត្តសញ្ញាណ (`Source 1`, `Source 2`, … — ដើម្បីឱ្យ
   judge ថ្លឹងថ្លែងលើខ្លឹមសារ មិនមែនម៉ាកម៉ូដែល) ហើយប្រគល់ទៅ judge ដែលនឹងវិភាគ
   មតិស្របគ្នា / ភាពផ្ទុយគ្នា / វិសាលភាពគ្របដណ្តប់មិនពេញលេញ / ការយល់ដឹងពិសេស / ចំណុចខ្វះខាត បន្ទាប់មក
   សរសេរចម្លើយដែលមានសិទ្ធិអំណាច **តែមួយ**។ ការហៅ judge រក្សាទុក
   flag `stream` ដើមរបស់ client + tools ដូច្នេះ streaming និងការប្រើ tool នៅដំណាក់កាលបន្ទាប់នៅតែដំណើរការ។
4. **ការបន្ថយសមត្ថភាពដោយរលូន** — គ្មានចម្លើយពី panel → `503`; មានតែអ្នកនៅសល់ 1 → ចម្លើយនោះ
   ត្រូវបានត្រឡប់ដោយផ្ទាល់ (គ្មានអ្វីត្រូវបញ្ចូលគ្នា); panel ដែលមានម៉ូដែលតែមួយឆ្លើយតបដោយផ្ទាល់។

សមាជិក panel ម្នាក់ក៏អាចជាជំហាន `combo-ref` (`{kind: "combo-ref", comboName: "..."}`) ដែលយោងទៅ
combo មួយផ្សេងទៀត — វាត្រូវបានដោះស្រាយជា **សំឡេង panel black-box តែមួយ** (ការបញ្ជូន recursive ពេញលេញទៅក្នុង
combo ដែលបានយោង មិនមែនការបញ្ជូនទៅគ្រប់គោលដៅរបស់ combo នោះទេ) ជាមួយការការពារជម្រៅ/cycle ដូចគ្នា
ដែលយុទ្ធសាស្ត្រផ្សេងៗទាំងអស់ដែលប្រើប្រាស់ combo-ref កំពុងប្រើរួចហើយ (#6764)។

### ការកំណត់រចនាសម្ព័ន្ធ

កំណត់នៅលើ blob `config` របស់ combo (មិនត្រូវការធ្វើ schema migration ទេ — វាប្រើតារាង
`combos` ដែលមានស្រាប់ឡើងវិញ)៖

| Field                                    | Type     | Default                | Purpose                                                                                                  |
| :--------------------------------------- | :------- | :--------------------- | :------------------------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | ម៉ូដែលដំបូងក្នុង panel | ម៉ូដែលដែលសំយោគចម្លើយចុងក្រោយ                                                                             |
| `config.fusionTuning.minPanel`           | `number` | `2`                    | ចំនួនចម្លើយជោគជ័យដែលត្រូវការ មុនពេលកម្មវិធីកំណត់ពេលអនុគ្រោះចាប់ផ្តើម (កំណត់ក្នុងចន្លោះ `[2, panelSize]`) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`                 | រយៈពេលរង់ចាំអ្នកដែលមកយឺត បន្ទាប់ពីឈានដល់ quorum                                                          |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`                | ដែនកំណត់ដាច់ខាត ដើម្បីកុំឱ្យម៉ូដែលមួយដែលជាប់គាំងអាចរារាំងសំណើ                                            |

តម្លៃលំនាំដើមស្ថិតនៅក្នុង `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`)។

## រោងចក្រ Auto-Combo និម្មិត

ម៉ាស៊ីន Auto Combo មិនតម្រូវឱ្យមាន combo ដែលបានកំណត់ជាមុនទេ។ ផ្ទុយទៅវិញ `open-sse/services/autoCombo/virtualFactory.ts` បង្កើត candidate ភ្លាមៗតាមតម្រូវការ៖

1. ទាញយក `getProviderConnections({ isActive: true })` (connection ទាំងអស់ដែលបានបើកដំណើរការ)
2. ច្រោះយកតែ connection ដែលមាន credential ត្រឹមត្រូវ (API key ឬ OAuth token ដែលមិនទាន់ផុតកំណត់ តាមរយៈ `hasUsableOAuthToken()`)
3. ផ្ទៀងផ្ទាត់ជាមួយ `getProviderRegistry()` សម្រាប់ភាពអាចប្រើបាននៃ model និងតម្លៃ
4. សម្រាប់ tuple នីមួយៗ `(provider, model, connection)` បង្កើត `VirtualAutoComboCandidate`
5. ជ្រើសរើស `connection.defaultModel` (ឬ model ដំបូងរបស់ registry) ជាគោលដៅ dispatch
6. ដាក់ពិន្ទុ candidate នីមួយៗដោយប្រើ `scorePool()` ដែលមាន 16 កត្តា និងកញ្ចប់ weight របស់ variant
7. ត្រឡប់ `AutoComboConfig` ក្នុង memory ដែលទទួលបានសម្រាប់ `handleComboChat()` — មិនដែលរក្សាទុកទៅ DB ទេ

នេះមានន័យថា **ការបន្ថែម provider ថ្មីដែលបានបើក `auto/*` នឹងពង្រីក candidate pool ដោយស្វ័យប្រវត្តិ** — មិនចាំបាច់កែសម្រួល combo ដោយដៃទេ។ Virtual combo ត្រូវបានបង្កើតឡើងវិញសម្រាប់ request នីមួយៗ ដូច្នេះ connection ដែលទើបបន្ថែមថ្មី ឬទើបមានស្ថានភាពល្អឡើងវិញ នឹងត្រូវបានយកមកប្រើភ្លាមៗ។

## ការស្ដារឡើងវិញដោយស្វ័យប្រវត្តិ

- **ការដកចេញបណ្ដោះអាសន្ន**៖ ពិន្ទុ < 0.2 → ដកចេញរយៈពេល 5 នាទី (progressive backoff អតិបរមា 30 នាទី)
- **ការយល់ដឹងអំពី circuit breaker**៖ OPEN → ដកចេញដោយស្វ័យប្រវត្តិ; HALF_OPEN → request សាកល្បង
- **Incident mode**៖ >50% OPEN → បិទ exploration និងបង្កើនស្ថិរភាពឱ្យដល់អតិបរមា
- **ការស្ដារឡើងវិញក្រោយ cooldown**៖ បន្ទាប់ពីការដកចេញ request ដំបូងគឺជា "probe" ដែលមាន timeout តិចជាងមុន

## Bandit Exploration

5% នៃ request (អាចកំណត់បាន) ត្រូវបាន route ទៅ provider ចៃដន្យសម្រាប់ exploration។ វាត្រូវបានបិទនៅក្នុង incident mode។

## API

**មិនមាន endpoint `POST /api/combos/auto` ដាច់ដោយឡែកទេ** — Auto-Combo ត្រូវបានប្រើតាមពីរវិធី៖

1. **មិនចាំបាច់កំណត់រចនាសម្ព័ន្ធ (បានណែនាំ)៖** ផ្ញើ chat completion request ណាមួយជាមួយ `model: "auto"` ឬ `model: "auto/<variant>"`។ Virtual factory នឹងបង្កើត combo សម្រាប់ request នីមួយៗ — មិនមាន persistence និងមិនចាំបាច់ហៅ API ទេ។

2. **Combo ដែលបានរក្សាទុកជាមួយ `strategy: "auto"`៖** បង្កើត combo ធម្មតាតាមរយៈ `POST /api/combos` ហើយកំណត់ `strategy: "auto"` រួមជាមួយ `config.auto.weights` / `config.auto.candidatePool`។ ម៉ាស៊ីនដាក់ពិន្ទុដូចគ្នានឹងត្រូវបានប្រើ; combo ត្រូវបានរក្សាទុកក្នុង `combos` និងអាចប្រើឡើងវិញតាម ID។

សម្រាប់ការស្វែងរក `GET /api/combos/auto` រាយ variant ទាំងអស់ រួមជាមួយ candidate pool ដែលបាន resolve និង `context_length` / `max_output_tokens` របស់វា — ជាតម្លៃ MAX ក្នុងចំណោម window របស់ candidate pool។ Client (ឧ. opencode plugin) ត្រូវតែប្រកាសតម្លៃទាំងនេះជំនួសឱ្យ `0`៖ context ដែលមានតម្លៃសូន្យនឹងបិទ auto-compaction របស់ opencode ទាំងស្រុង ដែលអនុញ្ញាតឱ្យ session កើនឡើងរហូតដល់ការសម្អាត history របស់ gateway បំផ្លាញ context។ ការប្រកាស MAX គឺមានសុវត្ថិភាព ពីព្រោះ context pre-filter របស់ auto-combo នឹង route request ដែលមានទំហំធំពេកទៅកាន់ candidate ដែលមាន window ធំ។

```bash
# ការប្រើប្រាស់ដោយមិនចាំបាច់កំណត់រចនាសម្ព័ន្ធ (មិនបង្កើត combo)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Combo ស្វ័យប្រវត្តិដែលបានរក្សាទុក តាមរយៈ combos endpoint ធម្មតា
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Strategy របស់ auto router

Combo ដែលបានរក្សាទុកជាមួយ `strategy: "auto"` អាចកំណត់ `config.routerStrategy` (ឬ
`config.auto.routerStrategy` ចាស់) ទៅជាតម្លៃមួយក្នុងចំណោម៖

- `rules` — ការដាក់ពិន្ទុដោយមាន weight លំនាំដើម
- `score` — ជ្រើសរើសពិន្ទុដែលបានកំណត់ weight ខ្ពស់បំផុត។ ក្នុងករណីពិន្ទុស្មើគ្នាទាំងស្រុង លំដាប់
  candidate ដែលបានកំណត់នឹងត្រូវបានរក្សាទុក; `explorationRate` ដែលមានស្រាប់នឹង sample ពី ranked pool ទាំងមូល។
- `cost` / `eco` — provider ដែលមានស្ថានភាពល្អ និងតម្លៃទាបបំផុត
- `latency` / `fast` — latency p95 ទាបបំផុត ជាមួយ reliability penalty
- `sla-aware` / `sla` — ផ្ដល់អាទិភាពដល់ candidate ដែលបំពេញតាម latency p95, error-rate និង
  cost SLO ដែលជាជម្រើស
- `lkgp` — ដាក់ provider ដែលមានស្ថានភាពល្អចុងក្រោយនៅមុនគេ

### ព័ត៌មានលម្អិតអំពី router strategy

ម៉ាស៊ីន auto-combo ផ្ដល់ implementation **RouterStrategy** ដែលអាចដោតប្រើបានចំនួន 6 ដែល
អ្នកអាចប្ដូរតាមរយៈ `config.routerStrategy` (ឬ `config.auto.routerStrategy` ចាស់)។
Strategy នីមួយៗជ្រើសរើស provider មួយពី candidate pool ដោយផ្អែកលើ `RoutingContext`
(ប្រភេទ task, សញ្ញាបង្ហាញ tool/vision, ការប៉ាន់ប្រមាណ token, គោលការណ៍ SLA ជាជម្រើស និង
provider ដែលមានស្ថានភាពល្អចុងក្រោយជាជម្រើស)។

#### 1. `rules` (លំនាំដើម) — ការដាក់ពិន្ទុដោយមាន weight ចំនួន 16 កត្តា

រុំជុំវិញម៉ាស៊ីនដាក់ពិន្ទុដែលមានស្រាប់។ ច្រោះ candidate របស់ circuit-breaker ដែលមានស្ថានភាព `OPEN`
ចេញ បន្ទាប់មកដំណើរការ `scorePool()` ជាមួយប្រភេទ task បច្ចុប្បន្ន និង `getTaskFitness()`
ហើយជ្រើសរើស provider ដែលមានពិន្ទុខ្ពស់បំផុត។

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**ពេលដែលគួរប្រើ**៖ លំនាំដើម។ ប្រើនៅពេលអ្នកចង់បានតុល្យភាពរវាង signal ទាំងអស់។

**Alias**៖ `rules` (គ្មាន alias)

---

#### 2. `cost` / `eco` — provider ដែលមានស្ថានភាពល្អ និងតម្លៃទាបបំផុត

តម្រៀប candidate pool តាម `costPer1MTokens` (ពីតូចទៅធំ) ហើយជ្រើសរើសមួយដែលមានតម្លៃទាបបំផុត។
ច្រោះ candidate ដែលមានស្ថានភាព `OPEN` ចេញជាមុន។

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ពេលដែលគួរប្រើ**៖ Workload ដែលផ្ដោតលើការសន្សំថ្លៃដើម, batch processing ឬ background job។

**Alias**៖ `cost`, `eco`

---

#### 3. `latency` / `fast` — latency p95 ទាបបំផុត ជាមួយ reliability penalty

តម្រៀបតាម `p95LatencyMs + (errorRate * 1000)`។ ពិន័យអត្រាកំហុសធានាថា
អ្នកផ្តល់សេវាដែលមិនគួរឱ្យទុកចិត្តត្រូវបានដាក់ចំណាត់ថ្នាក់ទាបជាង ទោះបីជាឡាតង់ស៊ីដែលបានបញ្ជាក់របស់ពួកគេទាបក៏ដោយ។

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ពេលណាគួរប្រើ**៖ បន្ទុកការងារដែលប្រកាន់ខ្ជាប់ឡាតង់ស៊ី ដូចជា ការជជែកតាមពេលវេលាជាក់ស្តែង ការបំពេញដោយស្វ័យប្រវត្តិ ឬ
ជំនួយការសរសេរកូដអន្តរកម្ម។

**ឈ្មោះហៅក្រៅ**៖ `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — ការអនុលោមតាម SLO នៃឡាតង់ស៊ី/កំហុស/ថ្លៃចំណាយ

ដាក់ពិន្ទុបេក្ខជននីមួយៗដោយផ្អែកលើកម្រិតដែលវាបំពេញគោលការណ៍ SLO ដែលបានកំណត់៖

| កត្តា           | ទម្ងន់ | រូបមន្ត                                            |
| --------------- | ------ | -------------------------------------------------- |
| ពិន្ទុឡាតង់ស៊ី  | 35%    | `threshold / max(value, ε)`                        |
| ពិន្ទុកំហុស     | 35%    | `threshold / max(value, ε)`                        |
| ពិន្ទុសុខភាព    | 15%    | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)  |
| ពិន្ទុថ្លៃចំណាយ | 10%    | `threshold / max(value, ε)` ឬធ្វើឱ្យធម្មតាបញ្ច្រាស |
| ពិន្ទុស្ថិរភាព  | 5%     | គម្លាតស្តង់ដារឡាតង់ស៊ីដែលបានធ្វើឱ្យធម្មតាបញ្ច្រាស  |

នៅពេល `hardConstraints: true` បេក្ខជនត្រូវបានតម្រៀបជាចម្បងតាម **ពិន្ទុការបំពាន**
(កម្រិតដែលពួកគេលើសពី SLO ណាមួយ) បន្ទាប់មកតាមពិន្ទុសមាសធាតុ។ បើមិនដូច្នោះទេ វាប្រើតែ
ពិន្ទុសមាសធាតុប៉ុណ្ណោះ។

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... ដាក់ពិន្ទុបេក្ខជននីមួយៗធៀបនឹងគោលការណ៍៖ { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**វាល SLA** (កំណត់នៅលើការកំណត់រចនាសម្ព័ន្ធបន្សំ)៖

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**ពេលណាគួរប្រើ**៖ បន្ទុកការងារផលិតកម្មដែលមានថវិកាឡាតង់ស៊ី អត្រាកំហុស ឬថ្លៃចំណាយតឹងរ៉ឹង។

**ឈ្មោះហៅក្រៅ**៖ `sla-aware`, `sla`

#### 5. `lkgp` — អ្នកផ្តល់សេវាដែលបានដឹងថាល្អចុងក្រោយជាមុន

សាកល្បង **អ្នកផ្តល់សេវាដែលបានដឹងថាល្អចុងក្រោយ** (ប្រសិនបើបានកំណត់) ជាមុន បន្ទាប់មកប្រើយុទ្ធសាស្ត្រ
`rules` ជាជម្រើសបម្រុង។ មានប្រយោជន៍សម្រាប់ការរក្សាសម័យជាប់លាប់ — អ្នកផ្តល់សេវាដដែលដោះស្រាយ
សំណើបន្តបន្ទាប់នៅក្នុងការសន្ទនា។

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // ប្រើយុទ្ធសាស្ត្រ rules ជាជម្រើសបម្រុង
    return getStrategy("rules").select(pool, context);
  }
}
```

**ពេលណាគួរប្រើ**៖ ការសន្ទនាច្រើនវេនដែលអ្នកចង់ឱ្យអ្នកផ្តល់សេវាដដែលដោះស្រាយ
សំណើបន្តបន្ទាប់ (ឧ. សម្រាប់ការរក្សាទុកក្នុងឃ្លាំងសម្ងាត់ ភាពបន្តនៃបរិបទ ឬស្ថិរភាពនៃតម្លៃ)។

**ឈ្មោះហៅក្រៅ**៖ `lkgp` (គ្មានឈ្មោះហៅក្រៅ)

---

### យុទ្ធសាស្ត្ររ៉ោតទ័រផ្ទាល់ខ្លួន

អ្នកអាចចុះឈ្មោះការអនុវត្ត `RouterStrategy` ផ្ទាល់ខ្លួនរបស់អ្នកតាមរយៈ API សាធារណៈ៖

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // តក្កវិជ្ជាកំណត់ផ្លូវរបស់អ្នកនៅទីនេះ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

បន្ទាប់មកប្រើវា៖

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## សង្ខេបអំពី Auto Variants

ដោយរាប់បញ្ចូលទាំង `auto` ដាច់ដោយឡែក (លំនាំដើម) និងតម្លៃ `AutoVariant` ទាំង 6 ដែលបានប្រកាសក្នុង `autoPrefix.ts` មាន **លេខសម្គាល់ម៉ូដែលដែលអាចហៅប្រើបានចំនួន 7**៖

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ផ្ទាល់រាយតម្លៃចំនួន 6; ជម្រើសទី 7 គឺ "គ្មានវ៉ារ្យ៉ង់" — `auto` ដាច់ដោយឡែក — ដែលត្រូវបានដោះស្រាយដោយ `parseAutoPrefix()` ជា `variant: undefined`។)

## របៀបដែលកម្រិតសម្របជាមួយ Auto-Combo

អនុគមន៍ដាក់ពិន្ទុដែលមានកត្តា 16 (`open-sse/services/autoCombo/scoring.ts`) ចាត់ទុកសមាជិកភាពតាមកម្រិតជាសញ្ញាពីរ៖ `tierPriority` (0.0476) និង `tierAffinity` (0.0476)។ សូមមើល
[តារាងកត្តាដាក់ពិន្ទុ](#how-it-works-persisted-auto-combos) ស្តង់ដារខាងលើ សម្រាប់សំណុំ
`DEFAULT_WEIGHTS` ពេញលេញ — ការកំណត់ជំនួសតាមកញ្ចប់នីមួយៗ (ship-fast/cost-saver/quality-first/
offline-friendly) ត្រូវបានរាយក្នុងតារាង "ទម្រង់ទម្ងន់តាមកញ្ចប់"។

កម្រិតតែមួយមុខ **មិន** បង្ខំឱ្យ Tier 1 មកមុនទេ — ប្រសិនបើ latency របស់ Tier 1 មិនល្អ ឬ
តម្លៃធៀបនឹងគុណភាពមិនសមស្រប នោះ Tier 2 នឹងឈ្នះ។ ដើម្បីបង្ខំលំដាប់កម្រិត សូមប្រើយុទ្ធសាស្ត្រ combo
`priority` ហើយរៀបចំ providers តាមកម្រិត។

ដើម្បីផ្តល់អាទិភាពខ្លាំងដល់ Tier 1 (ការជាវ) សូមបង្កើនទម្ងន់ `tierPriority`៖

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

សូមមើល `docs/marketing/TIERS.md` សម្រាប់និយមន័យកម្រិត និងការចាត់ថ្នាក់ provider។

## ការធ្វើតេស្ត និងវិសាលភាពគ្របដណ្តប់

### ម៉ាទ្រីសការសម្រេចចិត្តបញ្ជូនតាមផ្លូវបែបកំណត់ជាមុន (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` បញ្ជាក់អំពី **ការសម្រេចចិត្ត** បញ្ជូនតាមផ្លូវរបស់យុទ្ធសាស្ត្រសាធារណៈទាំង 19
ពីដើមដល់ចប់ តាមរយៈ pipeline combo ពិតប្រាកដ ដោយប្រើ upstream ក្លែងធ្វើ។
វិសាលភាពគ្របដណ្តប់រួមមាន៖

- យុទ្ធសាស្ត្រ `ROUTING_STRATEGY_VALUES` ទាំង 19 (ordered, weighted, cost, context, fusion, …)។
- `quota-share` (ខាងក្នុង) ពីដើមដល់ចប់៖ ភាពយុត្តិធម៌ DRR + ការបន្ថយអាទិភាពពេលឆ្អែត តាមរយៈ
  seam `selectQuotaShareTarget` ពិតប្រាកដ (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`)។
- វិសាលភាពគ្របដណ្តប់នៃការប្រគល់បន្តជាសកល `context-relay` នៅគ្រប់ចំនួនគោលដៅ។

សំណុំតេស្តនេះដំណើរការក្នុង CI (job `test:integration`) ជាមួយ `--test-concurrency=1` និង
`--test-force-exit` ដូច្នេះវាមានលទ្ធផលកំណត់ជាមុន និងមិនត្រូវការព័ត៌មានសម្ងាត់ពិតប្រាកដទេ។

### Smoke test ផ្ទាល់ដែលមានលក្ខខណ្ឌ (មិនមានក្នុង CI — providers ពិតប្រាកដ)

| ពាក្យបញ្ជា                             | អ្វីដែលវាធ្វើ                                                                                  |
| :------------------------------------- | :--------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | ការបញ្ជូនតាមផ្លូវពិតក្នុង process ជាមួយ `RUN_COMBO_LIVE=1`; ថត snapshot នៃ OmniRoute DB ផ្ទាល់ |
| `npm run test:combo:live:vps`          | ការហៅ HTTP ទៅកាន់ server OmniRoute ផ្ទាល់ (កំណត់ `COMBO_LIVE_BASE_URL`)                        |
| `npm run test:combo:live:vps:failover` | ដូចគ្នា ប៉ុន្តែមានសេណារីយ៉ូ failover ដែលបានបង្កើតឡើងដោយចេតនា                                   |

Smoke test ទាំងនេះសាកល្បងផ្លូវទំនាក់ទំនងពិតប្រាកដ (combo → provider → completion)។ ពួកវាត្រូវបាន
ដកចេញពី CI ដោយចេតនា ព្រោះវាត្រូវការព័ត៌មានសម្ងាត់ពិតប្រាកដ និងសិទ្ធិចូលប្រើ VPS។
