## ទិដ្ឋភាពទូទៅ

ម៉ាស៊ីនចែករំលែកកូតា (Quota Sharing Engine) បែងចែកកូតាផ្អែកលើពេលវេលារបស់អ្នកផ្តល់សេវា (ឧ. ចន្លោះពេល 5 ម៉ោងរបស់ Codex, Kimi 1500 សំណើ/ម៉ោង) ដោយយុត្តិធម៌រវាង API key ជាច្រើនដែលប្រើការតភ្ជាប់ដូចគ្នា។

**បញ្ហាដែលវាដោះស្រាយ:** OmniRoute ធ្វើប្រូកស៊ី API key ជាច្រើនទៅកាន់គណនីអ្នកផ្តល់សេវាខាងលើដូចគ្នា។ បើគ្មានតក្កវិជ្ជាចែករំលែកទេ សំណើដ៏ច្រើនភ្លាមៗពី key A អាចប្រើកូតារបស់អ្នកផ្តល់សេវាអស់សម្រាប់ម៉ោងនោះ ដែលធ្វើឱ្យ key B និង C ត្រូវបានទប់ស្កាត់រហូតដល់ចន្លោះពេលកំណត់ឡើងវិញ។ ម៉ាស៊ីននេះទប់ស្កាត់បញ្ហានេះដោយ៖

1. តាមដានការប្រើប្រាស់រំកិលរបស់ key នីមួយៗតាមវិមាត្រ (%, សំណើ, token, $)។
2. អនុវត្តក្បួនចែករំលែកដោយយុត្តិធម៌ដែលរក្សាការប្រើប្រាស់ធនធាន៖ key មួយអាចខ្ចីពីចំណែកដែលនៅទំនេរ ខណៈពេលដែលធនធានរួមមិនទាន់ឈានដល់កម្រិតឆ្អែត។
3. អនុវត្តលទ្ធផលនៅក្នុងផ្លូវដំណើរការសំខាន់ (`chatCore.ts`) មុនពេលសំណើទៅដល់កម្មវិធីប្រតិបត្តិខាងលើ។

## ក្បួនដោះស្រាយ៖ ការចែករំលែកដោយយុត្តិធម៌ដែលរក្សាការប្រើប្រាស់ធនធាន

ត្រូវបានអនុវត្តនៅក្នុង `src/lib/quota/fairShare.ts`។

### របៀប

| លក្ខខណ្ឌ                                   | របៀប        | ឥរិយាបថ                                              |
| ------------------------------------------ | ----------- | ---------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **ទូលាយ**   | Key អាចខ្ចីបានរហូតដល់ដែនកំណត់សកល ដកការប្រើប្រាស់សរុប |
| `globalUsedPercent >= saturationThreshold` | **តឹងរ៉ឹង** | អនុវត្តចំណែកយុត្តិធម៌នីមួយៗយ៉ាងតឹងរ៉ឹង               |

តម្លៃលំនាំដើម `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`)។

### ការសម្រេចចិត្តតាមវិមាត្រ

សម្រាប់វិមាត្រសកម្មនីមួយៗនៅក្នុងធនធានរួម ម៉ាស៊ីនគណនាដូចខាងក្រោម៖

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = តម្លៃរំកិលបច្ចុប្បន្នសម្រាប់ key នេះ (ពី QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

បន្ទាប់មក៖

- **`policy = hard`**៖ ប្រសិនបើ `consumed > fairShareAllowed` ហើយរបៀបគឺតឹងរ៉ឹង → **ទប់ស្កាត់**។
- **`policy = soft`**៖ ប្រសិនបើ `consumed > fairShareAllowed` ហើយរបៀបគឺតឹងរ៉ឹង → **ដាក់ទណ្ឌកម្ម** (បន្ថយអាទិភាពនៅក្នុង combo; មិនដែលទប់ស្កាត់ទាំងស្រុងទេ)។
- **`policy = burst`**៖ អនុញ្ញាតដរាបណានៅមានសមត្ថភាពសកល មិនថាចំណែកយុត្តិធម៌មានកម្រិតប៉ុនណាក៏ដោយ។

### កម្រិតអតិបរមាដាច់ខាត

`capValue` + `capUnit` នៅលើការបែងចែកមួយ គឺជាកម្រិតអតិបរមាដាច់ខាតដែលមិនអាស្រ័យលើរបៀប ឬគោលការណ៍។ វិមាត្រណាមួយដែល `consumed >= capValue` នឹង **ទប់ស្កាត់** សំណើជានិច្ច។

### ការត្រួតពិនិត្យពហុវិមាត្រ

សំណើមួយត្រូវបានទប់ស្កាត់ ប្រសិនបើវិមាត្រ **ណាមួយ** នៅក្នុងធនធានរួមត្រូវទប់ស្កាត់វា។ វិមាត្រនីមួយៗឯករាជ្យពីគ្នា — ការប្រើ 5h% អស់ មិនប៉ះពាល់ដល់វិមាត្រ weekly% ទេ។

### ការខ្ចី

ក្នុងរបៀបទូលាយ key ដែលមិនទាន់ប្រើការបែងចែករបស់ខ្លួនអស់ អាចប្រើចំណែកលើសដែលមិនបានប្រើរបស់ key ផ្សេងទៀត។ រូបមន្តគឺ៖

```
maxAllowed = globalLimit - consumedByOtherKeys
```

ដែល `consumedByOtherKeys = consumedTotal - consumedByThisKey`។ កម្រិតអតិបរមាសកល (`limit` របស់ធនធានរួមសម្រាប់វិមាត្រនោះ) គឺជាពិដានដាច់ខាតជានិច្ច។

## កម្មវិធីរាប់ចន្លោះពេលរំកិល

ត្រូវបានអនុវត្តនៅក្នុង `src/lib/quota/sqliteQuotaStore.ts` និង `redisQuotaStore.ts`។

មាន bucket ពីរសម្រាប់ `(apiKeyId, dimensionKey)` នីមួយៗ៖

- `curr`៖ bucket បច្ចុប្បន្ន (`floor(nowMs / windowMs)`)
- `prev`៖ bucket មុន (`curr - 1`)

តម្លៃរំកិលជាក់ស្តែង៖

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**ភាពជាក់លាក់**៖ ត្រឹមត្រូវប្រហែល 99%។ កំហុសមានច្រើនបំផុត 1% នៃទំហំចន្លោះពេល នៅត្រង់ព្រំដែនរវាង bucket (ជាលក្ខណៈដែលជៀសមិនរួចនៃការប៉ាន់ស្មានដោយប្រើ bucket 2)។

### ភាពដំណាលគ្នា

កម្មវិធីបញ្ជា SQLite៖ mutex ក្នុងអង្គចងចាំសម្រាប់ key `(apiKeyId | dimensionKey)` នីមួយៗ ទប់ស្កាត់ស្ថានភាពប្រណាំង read-modify-write។ លំនាំនេះដូចគ្នានឹងវិធីប្រឆាំង anti-thundering-herd របស់ `src/sse/services/auth.ts`។

កម្មវិធីបញ្ជា Redis៖ ស្គ្រីប Lua EVAL សម្រាប់ការបង្កើនតម្លៃបែប atomic — ដំណើរការជាពាក្យបញ្ជា Redis តែមួយ។

## កម្មវិធីបញ្ជា

### SQLite (លំនាំដើម, មិនចាំបាច់ដំឡើង)

- តារាង៖ `quota_consumption` (សូមមើល migration `073_quota_pools.sql` / `074_quota_consumption.sql`)។
- សមស្របបំផុតសម្រាប់ការដាក់ឱ្យដំណើរការតែមួយ instance។
- ទិន្នន័យអចិន្ត្រៃយ៍ទាំងអស់ស្ថិតនៅក្នុង OmniRoute SQLite DB ដែលមានស្រាប់ (`DATA_DIR/storage.sqlite`)។

### Redis (ជាជម្រើស, ច្រើន instance)

- តម្រូវឱ្យមានកញ្ចប់ npm `ioredis`។
- Counter ត្រូវបានរក្សាទុកក្នុង Redis ខណៈ metadata (pool/allocation) នៅតែស្ថិតក្នុង SQLite។
- សមស្របបំផុតសម្រាប់ការដាក់ឱ្យដំណើរការច្រើន replica ដែល counter ត្រូវតែប្រើរួមគ្នា។

### ការប្ដូរកម្មវិធីបញ្ជា

តាមរយៈ UI ការកំណត់ (`/dashboard/settings` → Quota Store) ឬតាមរយៈ env vars៖

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

ការកំណត់ DB មានអាទិភាពជាង env។ ប្រសិនបើ `driver=redis` ប៉ុន្តែគ្មាន URL ឬ
មិនបានដំឡើង `ioredis` ទេ factory នឹងត្រឡប់ទៅប្រើ SQLite ហើយកត់ត្រាការព្រមាន។

លំដាប់នៃការជ្រើសរើសកម្មវិធីបញ្ជា៖

1. ការកំណត់ DB `quotaStore.driver`
2. Env `QUOTA_STORE_DRIVER`
3. លំនាំដើម៖ `sqlite`

## ពហុវិមាត្រ

Pool មួយអាចមានវិមាត្រច្រើន។ វិមាត្រនីមួយៗដំណើរការដោយឯករាជ្យ៖

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
```

## ការរួមបញ្ចូលជាមួយ Pipeline

### PRE hook (`open-sse/handlers/chatCore.ts`)

ដំណើរការមុន upstream executor បន្ទាប់ពីការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ និងការត្រួតពិនិត្យគោលការណ៍៖

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek() តាមវិមាត្រនីមួយៗ
      → fairShare.decideFairShare()
      → ប្រសិនបើ block → ត្រឡប់ 429 (buildErrorBody, Hard Rule #12)
      → ប្រសិនបើ allow + deprioritize → កំណត់ quotaSoftPenalty=true លើ candidate
  → executor.execute()
```

**អនុញ្ញាតឱ្យឆ្លងកាត់ពេលមានកំហុស**៖ ប្រសិនបើ `enforceQuotaShare` បង្កើតកំហុស សំណើត្រូវបានអនុញ្ញាតឱ្យឆ្លងកាត់
ដោយមានកំណត់ត្រា `pino.warn`។ វាការពារកុំឱ្យកំហុសរបស់ quota engine រារាំង
ចរាចរណ៍ទាំងអស់។

### POST hook (កត់ត្រាការប្រើប្រាស់)

បន្ទាប់ពីការឆ្លើយតបដោយជោគជ័យ៖

```
executor ត្រឡប់ភាពជោគជ័យ
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume() តាមវិមាត្រនីមួយៗ
      → អនុញ្ញាតឱ្យឆ្លងកាត់ពេលមានកំហុស៖ កំហុសត្រូវបានកត់ត្រាជា pino.warn ហើយមិនដែលបញ្ជូនបន្តទៅ client
```

**ចំណាំអំពីភាពលម្អៀង**៖ ប្រសិនបើ `consume` បរាជ័យក្រោយការឆ្លើយតប rolling counter នឹងរាប់ខ្វះ។
សញ្ញាឈានដល់កម្រិតអតិបរមាពីអ្នកផ្ដល់សេវា (ឧ. `anthropic-ratelimit-unified-5h-utilization`)
នឹងកែតម្រូវការប៉ាន់ស្មានសកលនៅសំណើបន្ទាប់។

### Combo soft penalty (`open-sse/services/combo.ts`)

នៅពេល `decision.deprioritize === true`៖

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // លំនាំដើម 0.7
}
```

Penalty ត្រូវបានអនុវត្តបន្ទាប់ពីកត្តាដាក់ពិន្ទុផ្សេងទៀតទាំងអស់។ វាបន្ថយប្រូបាប៊ីលីតេរបស់ auto-combo
ក្នុងការជ្រើសរើស key ដែលបានឈានដល់កម្រិតអតិបរមា ដោយមិនរារាំងវាទាំងស្រុង។

## ការដោះស្រាយបញ្ហា

### បានកំណត់ Redis ប៉ុន្តែមិនអាចតភ្ជាប់បាន

(កត់ត្រាក្នុង log នៅកម្រិត `warn`)។

### `peek` ត្រឡប់ទិន្នន័យចាស់ / fail-open

ប្រសិនបើ `peek` បង្កើត exception នោះ `enforceQuotaShare` នឹងចាត់ទុកលទ្ធផលថា "អនុញ្ញាត"
(fail-open)។ ពិនិត្យ logs របស់ `pino` សម្រាប់ធាតុ `quota:enforce` និង `quota:factory`
ដើម្បីកំណត់រកមូលហេតុដើម។

### ភាពលម្អៀងនៃកម្មវិធីរាប់ការប្រើប្រាស់

ប្រសិនបើការប្រើប្រាស់ provider ជាក់ស្ដែងខុសពីកម្មវិធីរាប់ នោះគឺជាអ្វីដែលបានរំពឹងទុក —
2-bucket sliding window មានកំហុសប្រហែល 1% នៅត្រង់ព្រំដែន window ហើយ `consume`
ដំណើរការបែប fire-and-forget បន្ទាប់ពី response។ សញ្ញា saturation (`saturationSignals.ts`)
អាន utilization ពិតប្រាកដរបស់ provider ដោយមាន TTL 30 វិនាទី និងកែសម្រួល
`globalUsedPercent` ឱ្យសមស្រប។

### Pool បង្ហាញ "គ្មានទិន្នន័យ" សម្រាប់អត្រាប្រើប្រាស់
