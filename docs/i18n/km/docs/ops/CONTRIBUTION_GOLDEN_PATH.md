ប្រើមគ្គុទ្ទេសក៍នេះ ដើម្បីជ្រើសរើសវដ្តអភិវឌ្ឍន៍ដែលតូចបំផុត និងអាចទុកចិត្តបានសម្រាប់ pull request មួយ។ វាមិន
ជំនួសឯកសារស្ថាបត្យកម្ម និងសុវត្ថិភាពជាក់លាក់តាមផ្នែកដែលបានភ្ជាប់ខាងក្រោមទេ; វាភ្ជាប់ប្រភេទ
ការផ្លាស់ប្តូរទូទៅនីមួយៗទៅនឹងកិច្ចសន្យា ការត្រួតពិនិត្យផ្តោតជាក់លាក់ និងការគ្របដណ្តប់របស់ CI របស់វា។

## ផ្លូវដែលរាល់ការផ្លាស់ប្តូរត្រូវអនុវត្តតាម

1. **ជ្រើសរើសមូលដ្ឋានមុនពេលកែសម្រួល។** ស្វែងរក branch `release/v*` សកម្មខ្ពស់បំផុត ហើយបង្កើត branch ពី
   tip របស់វា។ កំណត់ branch នោះជាគោលដៅ មិនមែន `main` ទេ។ ប្រសិនបើការបង្កក release កំពុងសកម្ម កុំកំណត់ branch ដែលបានបង្កក
   ជាគោលដៅ; ប្រើវដ្តសកម្មបន្ទាប់ដែលបានពិពណ៌នានៅក្នុង
   [គំរូ Branching និង Release](BRANCHING_MODEL.md)។
2. **កំណត់ឈ្មោះកិច្ចសន្យា។** កំណត់អត្តសញ្ញាណ catalog, schema, artifact ដែលបានបង្កើត, public API ឬចំណុចប្រទាក់អ្នកប្រើប្រាស់
   ទាំងអស់ដែលការផ្លាស់ប្តូរប៉ះពាល់។ តារាងខាងក្រោមផ្តល់សំណុំចាប់ផ្តើមអប្បបរមា។
3. **សរសេរ ឬធ្វើបច្ចុប្បន្នភាពការធ្វើតេស្តដែលផ្តោតជាក់លាក់។** ការផ្លាស់ប្តូរ production នៅក្នុង `src/`, `open-sse/`, `electron/` ឬ
   `bin/` តម្រូវឱ្យមានការធ្វើតេស្តស្វ័យប្រវត្តិនៅក្នុង PR ដូចគ្នា។ ដំណើរការឯកសារតេស្តតិចបំផុតដែលបញ្ជាក់
   ឥរិយាបថ បន្ទាប់មកដំណើរការ gate ដែលផ្តោតជាក់លាក់ដូចបានរាយបញ្ជី។
4. **អនុញ្ញាតឱ្យ CI ដំណើរការ matrix ទូលំទូលាយ។** Unit shard ពេញលេញ, Vitest, coverage ratchet និង
   production build ដំណើរការនៅលើ PR។ ដំណើរការ suite ទូលំទូលាយក្នុង local តែនៅពេល failure ជាក់លាក់បង្ហាញថាមាន
   ផលប៉ះពាល់កាន់តែទូលំទូលាយ ឬនៅពេលការផ្លាស់ប្តូរគ្របដណ្តប់ subsystem ច្រើន។
5. **ធ្វើឱ្យស្របគ្នាមុនពេល review។** Fetch មូលដ្ឋានសកម្ម ពិនិត្យ commit ថ្មីរបស់វា និង diff របស់អ្នកធៀបនឹង
   វា បន្ទាប់មក rebase ឬ merge មូលដ្ឋានស្របតាម workflow របស់អ្នករួមចំណែក។ ដោះស្រាយ conflict របស់ generated-file
   និង catalog ពីប្រភពរបស់វា បង្កើតពួកវាឡើងវិញ ដំណើរការវដ្តផ្តោតជាក់លាក់ឡើងវិញ ហើយបញ្ជាក់ថា
   PR នៅតែកំណត់ branch release សកម្មជាគោលដៅ។
6. **កត់ត្រាភស្តុតាង។** នៅក្នុង template របស់ PR រាយបញ្ជី command ដែលបានដំណើរការ រាល់ឯកសារតេស្តដែលបានបន្ថែម ឬផ្លាស់ប្តូរ
   migration ឬ feature flag និង validation សម្រាប់តែ CI ណាមួយដែលនៅរង់ចាំ។

## ផ្លូវដែលបានណែនាំតាមប្រភេទការផ្លាស់ប្តូរ

Command ខាងក្រោមគឺជាការត្រួតពិនិត្យផ្តោតជាក់លាក់អប្បបរមា មិនមែនជាការអនុញ្ញាតឱ្យរំលងការធ្វើតេស្តដែលគ្របដណ្តប់ដោយផ្ទាល់លើ
ឥរិយាបថដែលអ្នកបានផ្លាស់ប្តូរនោះទេ។

### Provider

**កិច្ចសន្យា**

- និយមន័យ Provider នៅក្នុង `src/shared/constants/providers/` និងការផ្គុំរបស់វានៅក្នុង
  `src/shared/constants/providers.ts`។
- Model និង capability នៅក្នុង `open-sse/config/providerRegistry.ts` ឬឯកសារ registry ដែលបានបំបែកចេញ។
- ការជ្រើសរើស executor/translator, ការកំណត់រចនាសម្ព័ន្ធ OAuth ឬ API-key, asset របស់ dashboard និងឯកសារយោង
  provider ដែលបានបង្កើត នៅពេលអាចអនុវត្តបាន។
- Credential សាធារណៈត្រូវតែប្រើ `resolvePublicCred()`; response កំហុសត្រូវតែប្រើ helper
  កំហុសដែលបានសម្អាតរួម។ សូមមើល `docs/security/PUBLIC_CREDS.md` (git; មិនបាន compile ចូលក្នុង `/docs`) និង
  [ការសម្អាតកំហុស](../security/ERROR_SANITIZATION.md)។

**វដ្តផ្តោតជាក់លាក់**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # នៅពេល catalog ផ្លាស់ប្តូរ; commit diff ដែលបានបង្កើត
npm run lint
```

ធ្វើតេស្តផងដែរលើគ្រប់ក្រុម request ដែលរងផលប៉ះពាល់៖ chat, Responses, images, embeddings, audio ឬ video។
ពិនិត្យ catalog ដែលបានបង្កើត និង golden diff ជាការផ្លាស់ប្តូរកិច្ចសន្យា; កុំទទួលយកពួកវាដោយមិនពិនិត្យ។

### Routing

**កិច្ចសន្យា**

- តម្លៃ strategy សាធារណៈ និង metadata របស់ UI នៅក្នុង `src/shared/constants/routingStrategies.ts`។
- Dispatch និងលំដាប់នៅក្រោម `open-sse/services/combo.ts` និង `open-sse/services/combo/`។
- Combo schema, persistence, resilience state, model capability និង control របស់ API/UI។
- [ម៉ាស៊ីន Auto-Combo](../routing/AUTO-COMBO.md) និងឯកសារ resilience នៅពេលឥរិយាបថផ្លាស់ប្តូរ។

**វដ្តផ្តោតជាក់លាក់**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ការផ្លាស់ប្តូរ strategy ឬ dispatch
npm run check:known-symbols      # ការផ្លាស់ប្តូរការចុះឈ្មោះ strategy
npm run lint
```

ប្រើការធ្វើតេស្ត mocked-upstream ដែលមានលទ្ធផលកំណត់ច្បាស់លាស់ក្នុង local។ Live combo smoke តម្រូវឱ្យមាន credential និងត្រូវបាន
អនុវត្តដោយដៃ មិនមែនជាការជំនួស CI ទេ។

### UI / UX

**កិច្ចសន្យា**

- Route/page របស់ Next.js និងព្រំដែន shared component នៅក្រោម `src/app/` និង
  `src/shared/components/`។
- ទម្រង់ response របស់ API, state កំពុងផ្ទុក/ទទេ/កំហុស, ឥរិយាបថ keyboard និង screen-reader,
  responsive layout, theming និងការពង្រីក locale។
- String ប្រភព UI ជាភាសាអង់គ្លេសនៅក្នុង `src/i18n/messages/en.json`; កុំ hard-code ខ្លឹមសារថ្មីដែលបង្ហាញដល់អ្នកប្រើប្រាស់។

**វដ្តផ្តោតជាក់លាក់**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

ដំណើរការ app សម្រាប់ការផ្លាស់ប្តូរផ្នែក interaction ឬ visual ហើយពិនិត្យទាំង viewport តូច និងធំ។ CI ដំណើរការ
production build និង suite ទូលំទូលាយជាងនេះ; ឥរិយាបថ visual នៅតែត្រូវការការត្រួតពិនិត្យតាម component ដែលផ្តោតជាក់លាក់, Playwright
ឬការត្រួតពិនិត្យដោយដៃដែលបានចងក្រងជាឯកសារ និងសមស្របនឹងការផ្លាស់ប្តូរ។

### i18n

**កិច្ចសន្យា**

- `src/i18n/messages/en.json` គឺជាប្រភព UI; `config/i18n.json` គឺជាប្រភព locale។
- Catalog របស់ CLI ស្ថិតនៅដាច់ដោយឡែកក្រោម `bin/cli/locales/`។
- រក្សាទុក placeholder និង tag របស់ ICU ឱ្យដូចដើមទាំងស្រុង។ កុំបកប្រែឈ្មោះ product/provider/model,
  ឈ្មោះ protocol និង header, command, identifier របស់ code/JSON, URL, environment variable ឬ
  ពាក្យការពារដូចជា `OmniRoute`, `OAuth`, `MCP` និង `A2A`។ បញ្ជីប្រភពបច្ចុប្បន្នគឺ
  `scripts/i18n/glossary/protected-terms.json`។

**វដ្តផ្តោតជាក់លាក់**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # នៅពេល string/catalog របស់ CLI ផ្លាស់ប្តូរ
npm run lint
```

នេះគឺជាការណែនាំសម្រាប់ប្រព័ន្ធដែលមានស្រាប់ មិនមែនជាការអញ្ជើញឱ្យពង្រីក tooling ឬ key model របស់វាទេ។
រក្សា patch របស់ i18n ឱ្យមានលក្ខណៈជាក់លាក់ និងតូច ខណៈដែលប្រព័ន្ធជំនួសកំពុងត្រូវបានរចនា។ កុំដំណើរការ command បកប្រែ
ដែលហៅ external service លុះត្រាតែ task តម្រូវឱ្យមានការបកប្រែដែលបានបង្កើតយ៉ាងជាក់លាក់ ហើយ
អ្នកបានពិនិត្យ diff ដែលបានបង្កើតនោះ។

### CLI

**កិច្ចសន្យា**

- ពាក្យបញ្ជា និង flags សាធារណៈនៅក្នុង `bin/cli/`, ពាក្យបញ្ជា API ដែលបានបង្កើត, exit codes, stdout/stderr និង
  ទម្រង់លទ្ធផល JSON, ឥរិយាបថ config/environment និងឯកសារដែលបានវេចខ្ចប់។
- ខ្សែអក្សរដែលបង្ហាញដល់អ្នកប្រើ CLI ត្រូវតែប្រើស្រទាប់ i18n របស់ CLI ហើយរក្សា catalogs `en`/`pt-BR` ឱ្យស្របគ្នា។
- រក្សា Node ជា runtime ដែលគាំទ្រ និងរក្សាកិច្ចសន្យា binary ដែលបានបោះពុម្ពផ្សាយ។

**រង្វិលជុំផ្តោតជាក់លាក់**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # ការផ្លាស់ប្តូរ CLI ដែលបានបង្កើត/វេចខ្ចប់ជាបណ្តុំ
npm run check:pack-policy     # ការផ្លាស់ប្តូរផ្ទៃ package
npm run lint
```

ប្រើពាក្យបញ្ជាដូចដែលបានបញ្ជាក់ឱ្យពិតប្រាកដ នៅក្នុងថតទិន្នន័យបណ្តោះអាសន្ន នៅពេលដែលឥរិយាបថពឹងផ្អែកលើការញែក ឯកសារ ឬស្ថានភាព
ចាកចេញ។ CI អនុវត្តការត្រួតពិនិត្យកាន់តែទូលំទូលាយលើ artifact របស់ package និងប្រព័ន្ធអេកូ។

### មូលដ្ឋានទិន្នន័យ

**កិច្ចសន្យា**

- ម៉ូឌុល domain នៅក្រោម `src/lib/db/`; import ម៉ូឌុលជាក់លាក់ដោយផ្ទាល់ (ស្រទាប់ re-export ចាស់ `localDb.ts` ត្រូវបានដកចេញ)។
- SQL migrations ដែលមានលេខរៀង និងអាចដំណើរការឡើងវិញដោយសុវត្ថិភាព នៅក្រោម `src/lib/db/migrations/`, សុវត្ថិភាព transaction, ឥរិយាបថ
  នៃការធ្វើ upgrade, indexes និងគ្រប់ caller ទាំងអស់ដែលរងផលប៉ះពាល់ដោយ schema។
- Routes និង handlers មិនត្រូវប្រើ raw SQL ដោយផ្ទាល់ឡើយ។

**រង្វិលជុំផ្តោតជាក់លាក់**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

នៅពេលបន្ថែម migration ត្រូវសាកល្បងទាំងមូលដ្ឋានទិន្នន័យថ្មី និងការធ្វើ upgrade ពី schema មុន។ ការធ្វើតេស្តមូលដ្ឋានទិន្នន័យ
ត្រូវតែបិទ handles និងហៅ `resetDbInstance()` ក្នុងអំឡុងពេលសម្អាត។ ដំណើរការ `npm run test:bun:db` តែនៅពេល
ផ្លូវ Bun adapter ដែលជាការខិតខំប្រឹងប្រែងតាមលទ្ធភាពមានការផ្លាស់ប្តូរ; Node នៅតែជាប្រភពសម្រេចដែលមានអាទិភាព។

### ការបង្កើត / ការដាក់ឱ្យដំណើរការ

**កិច្ចសន្យា**

- Manifests/lockfile នៅ root និង workspace, `scripts/build/`, ការផ្គុំ standalone របស់ Next.js, មាតិកា package ក្នុង `dist/`,
  metadata តាម platform របស់ Electron, workflows របស់ CI និង deployment sentinels។
- ជួរកំណែ Node ដែលគាំទ្រ និងការប្រើ Bun ដែលបានអនុញ្ញាតក្នុងបញ្ជីនៅក្នុង `CLAUDE.md` ត្រូវតែរក្សាទុកដដែល។
- Build artifacts ត្រូវតែមិនត្រូវបានតាមដាន; គោលការណ៍សម្រាប់ dependency, license, workflow និង package ត្រូវអនុវត្ត។

**រង្វិលជុំផ្តោតជាក់លាក់**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # ការផ្លាស់ប្តូរ dependency ឬ lockfile
npm run check:pack-policy      # ការផ្លាស់ប្តូរផ្ទៃ package ដែលបានបោះពុម្ពផ្សាយ
npm run lint
```

ប្រើ `npm run build` ក្នុងម៉ាស៊ីនផ្ទាល់ខ្លួន តែនៅពេលការផ្លាស់ប្តូរប៉ះពាល់ដល់ការចងក្រង ការផ្គុំ standalone, assets
ឬការវេចខ្ចប់ runtime ជាបណ្តុំ។ ប្រើ `npm run build:release` សម្រាប់តែការផ្ទៀងផ្ទាត់ release/deploy ប៉ុណ្ណោះ។ Build របស់ CI គឺជា
សញ្ញា cross-platform ចុងក្រោយ; ការផ្លាស់ប្តូរ Electron ជាក់លាក់តាម platform ត្រូវការភស្តុតាងពី focused build
ឬ smoke test ដែលត្រូវគ្នា។

## បញ្ជីត្រួតពិនិត្យការផ្គូផ្គងឡើងវិញ

មុនពេលស្នើសុំការពិនិត្យឡើងវិញ៖

- បញ្ជាក់ថា PR base នៅតែជា branch `release/v*` សកម្មដែលខ្ពស់បំផុត។
- Fetch base នោះ ហើយពិនិត្យ commit ដែលបានបញ្ចូលចាប់តាំងពីអ្នកបង្កើត branch។
- ពិនិត្យ `git diff <active-base>...HEAD` ដើម្បីរកការផ្លាស់ប្តូរដោយអចេតនា ឬដែលបានបង្កើតដោយស្វ័យប្រវត្តិ។
- ដោះស្រាយ conflict នៃ catalog និង generated-document ដោយធ្វើបច្ចុប្បន្នភាពប្រភព ហើយបង្កើត output ឡើងវិញ។
- ដំណើរការឡើងវិញនូវរាល់ test/gate ផ្តោតជាក់លាក់ដែលបានរាយក្នុងសេចក្តីពិពណ៌នា PR បន្ទាប់ពីការផ្គូផ្គងឡើងវិញ។
- កុំបន្ថយភាពតឹងរ៉ឹងនៃ assertion ឬដក test ដែលតម្រូវចេញ ដោយគ្រាន់តែដើម្បីផ្គូផ្គងនឹង base ដែលបានផ្លាស់ទី។

សម្រាប់ច្បាប់អំពី release-freeze និងការកំណត់គោលដៅឡើងវិញ សូមប្រើ
