ប្រើមគ្គុទ្ទេសក៍នេះ ដើម្បីជ្រើសរើសវដ្តអភិវឌ្ឍន៍ដែលតូចបំផុត និងអាចទុកចិត្តបានសម្រាប់ pull request មួយ។ វាមិន
ជំនួសឯកសារស្ថាបត្យកម្ម និងសុវត្ថិភាពតាមផ្នែកជាក់លាក់ដែលបានភ្ជាប់ខាងក្រោមទេ; វាភ្ជាប់ប្រភេទ
ការផ្លាស់ប្តូរទូទៅនីមួយៗទៅនឹងកិច្ចសន្យា ការត្រួតពិនិត្យផ្តោតជាក់លាក់ និងវិសាលភាព CI របស់វា។

## ដំណើរការដែលរាល់ការផ្លាស់ប្តូរត្រូវអនុវត្តតាម

1. **ជ្រើសរើសមូលដ្ឋានមុនពេលកែសម្រួល។** ស្វែងរក branch `release/v*` សកម្មដែលខ្ពស់បំផុត ហើយបង្កើត branch ចេញពី
   tip របស់វា។ កំណត់ branch នោះជាគោលដៅ មិនមែន `main` ទេ។ ប្រសិនបើការផ្អាកចេញផ្សាយកំពុងមានប្រសិទ្ធភាព កុំកំណត់ branch ដែលបានផ្អាកនោះ
   ជាគោលដៅ; ប្រើវដ្តសកម្មបន្ទាប់ដែលបានពិពណ៌នាក្នុង
   [គំរូ Branching និងការចេញផ្សាយ](BRANCHING_MODEL.md)។
2. **កំណត់ឈ្មោះកិច្ចសន្យា។** កំណត់អត្តសញ្ញាណ catalog, schema, artifact ដែលបានបង្កើតដោយស្វ័យប្រវត្តិ, API សាធារណៈ ឬចំណុចប្រទាក់អ្នកប្រើ
   ទាំងអស់ដែលការផ្លាស់ប្តូរនេះប៉ះពាល់។ តារាងខាងក្រោមផ្តល់សំណុំចាប់ផ្តើមអប្បបរមា។
3. **សរសេរ ឬធ្វើបច្ចុប្បន្នភាពតេស្តដែលផ្តោតជាក់លាក់។** ការផ្លាស់ប្តូរកូដ production ក្នុង `src/`, `open-sse/`, `electron/` ឬ
   `bin/` តម្រូវឱ្យមានតេស្តស្វ័យប្រវត្តិក្នុង PR ដូចគ្នា។ ដំណើរការឯកសារតេស្តតិចបំផុតដែលបញ្ជាក់ពី
   ឥរិយាបថ បន្ទាប់មកដំណើរការច្រកត្រួតពិនិត្យផ្តោតជាក់លាក់ដែលបានរាយ។
4. **អនុញ្ញាតឱ្យ CI ដំណើរការ matrix ទូលំទូលាយ។** unit shards ពេញលេញ, Vitest, coverage ratchet និង
   production build ដំណើរការលើ PR។ ដំណើរការ suite ទូលំទូលាយនៅមូលដ្ឋានតែក្នុងករណីដែល failure ជាក់លាក់បង្ហាញថា
   មានផលប៉ះពាល់កាន់តែទូលំទូលាយ ឬនៅពេលការផ្លាស់ប្តូរគ្របដណ្តប់ប្រព័ន្ធរងជាច្រើន។
5. **ធ្វើសមកាលកម្មមុនពេល review។** Fetch មូលដ្ឋានសកម្ម ពិនិត្យ commit ថ្មីៗរបស់វា និង diff របស់អ្នកធៀបនឹង
   វា បន្ទាប់មក rebase ឬ merge មូលដ្ឋានតាម workflow របស់អ្នកចូលរួមចំណែក។ ដោះស្រាយ conflict របស់ឯកសារ
   ដែលបានបង្កើតដោយស្វ័យប្រវត្តិ និង catalog ពីប្រភពរបស់វា បង្កើតពួកវាឡើងវិញ ដំណើរការវដ្តផ្តោតជាក់លាក់ម្តងទៀត ហើយបញ្ជាក់ថា
   PR នៅតែកំណត់គោលដៅទៅ branch ចេញផ្សាយសកម្ម។
6. **កត់ត្រាភស្តុតាង។** ក្នុង template របស់ PR សូមរាយ command ដែលបានដំណើរការ ឯកសារតេស្តទាំងអស់ដែលបានបន្ថែម ឬផ្លាស់ប្តូរ
   migration ឬ feature flag និង validation សម្រាប់តែ CI ណាមួយដែលនៅរង់ចាំ។

## ផ្លូវស្តង់ដារតាមប្រភេទការផ្លាស់ប្តូរ

Command ខាងក្រោមគឺជាការត្រួតពិនិត្យផ្តោតជាក់លាក់អប្បបរមា មិនមែនជាការអនុញ្ញាតឱ្យរំលងតេស្តដែលគ្របដណ្តប់ដោយផ្ទាល់លើ
ឥរិយាបថដែលអ្នកបានផ្លាស់ប្តូរនោះទេ។

### Provider

**កិច្ចសន្យា**

- និយមន័យ Provider ក្នុង `src/shared/constants/providers/` និងការផ្សំរបស់វាក្នុង
  `src/shared/constants/providers.ts`។
- Model និងសមត្ថភាពក្នុង `open-sse/config/providerRegistry.ts` ឬឯកសារ registry ដែលបានបំបែកចេញពីវា។
- ការជ្រើសរើស executor/translator, ការកំណត់រចនាសម្ព័ន្ធ OAuth ឬ API-key, asset របស់ dashboard និងឯកសារយោង
  provider ដែលបានបង្កើតដោយស្វ័យប្រវត្តិ នៅពេលអាចអនុវត្តបាន។
- Credential សាធារណៈត្រូវប្រើ `resolvePublicCred()`; response ដែលមាន error ត្រូវប្រើ helper រួមសម្រាប់
  សម្អាត error។ សូមមើល `docs/security/PUBLIC_CREDS.md` (git; មិនត្រូវបាន compile ទៅក្នុង `/docs`) និង
  [ការសម្អាត Error](../security/ERROR_SANITIZATION.md)។

**វដ្តផ្តោតជាក់លាក់**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # នៅពេល catalog ផ្លាស់ប្តូរ; commit diff ដែលបានបង្កើត
npm run lint
```

សូមធ្វើតេស្តគ្រប់ family នៃ request ដែលរងផលប៉ះពាល់ផងដែរ៖ chat, Responses, images, embeddings, audio ឬ video។
ពិនិត្យមើល catalog ដែលបានបង្កើត និង golden diff ក្នុងនាមជាការផ្លាស់ប្តូរកិច្ចសន្យា; កុំទទួលយកវាដោយមិនបានពិនិត្យ។

### Routing

**កិច្ចសន្យា**

- តម្លៃ strategy សាធារណៈ និង metadata របស់ UI ក្នុង `src/shared/constants/routingStrategies.ts`។
- Dispatch និងលំដាប់ក្រោម `open-sse/services/combo.ts` និង `open-sse/services/combo/`។
- Combo schema, persistence, ស្ថានភាព resilience, សមត្ថភាព model និង control របស់ API/UI។
- [ម៉ាស៊ីន Auto-Combo](../routing/AUTO-COMBO.md) និងឯកសារ resilience នៅពេលឥរិយាបថផ្លាស់ប្តូរ។

**វដ្តផ្តោតជាក់លាក់**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ការផ្លាស់ប្តូរ strategy ឬ dispatch
npm run check:known-symbols      # ការផ្លាស់ប្តូរការចុះឈ្មោះ strategy
npm run lint
```

ប្រើតេស្តដែលបាន mock upstream ដោយមានលទ្ធផលកំណត់ច្បាស់លាស់នៅមូលដ្ឋាន។ Live combo smoke test តម្រូវឱ្យមាន credential និងជាការធ្វើដោយដៃ
មិនមែនជាការជំនួស CI ទេ។

### UI / UX

**កិច្ចសន្យា**

- Route/page របស់ Next.js និងព្រំដែន component រួមនៅក្រោម `src/app/` និង
  `src/shared/components/`។
- ទម្រង់ response របស់ API, ស្ថានភាព loading/empty/error, ឥរិយាបថ keyboard និង screen reader,
  layout ដែលឆ្លើយតបតាមទំហំអេក្រង់, theming និងការពង្រីក locale។
- String ប្រភព UI ជាភាសាអង់គ្លេសក្នុង `src/i18n/messages/en.json`; កុំ hard-code អត្ថបទថ្មីដែលបង្ហាញទៅកាន់អ្នកប្រើ។

**វដ្តផ្តោតជាក់លាក់**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

ដំណើរការ app សម្រាប់ការផ្លាស់ប្តូរអន្តរកម្ម ឬរូបភាព ហើយពិនិត្យទាំង viewport តូច និងធំ។ CI ដំណើរការ

## រង្វិលជុំ candidate មូលដ្ឋាន

ការធ្វើតេស្ត source មិនអាចបញ្ជាក់បានថា artifact ដែលបានវេចខ្ចប់អាចចាប់ផ្ដើមដំណើរការបានទេ៖ បញ្ជីវេចខ្ចប់ dependencies ដែលបានកាត់ចេញ
និង native binaries នឹងបរាជ័យតែនៅពេល tarball ត្រូវបានដំឡើង និងចាប់ផ្ដើមប៉ុណ្ណោះ។ `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) គឺជាផ្នែកមូលដ្ឋាននៃលំហូរ build-once / validate / promote ពី
RFC #8084៖ វាបង្កើត candidate មួយ ផ្ទៀងផ្ទាត់ artifact ជាក់លាក់នោះ ដំឡើងវាជា active ដោយប្ដូរឈ្មោះ
directory ហើយ rollback វា នៅពេល slot ដែលបានដំឡើងជា active មិនឆ្លងកាត់ health check។

```bash
npm run dev:candidate -- run --dry-run --json  # បង្ហាញផែនការ ដោយមិនផ្លាស់ប្ដូរអ្វីទាំងអស់
npm run dev:candidate -- run                   # build + validate + promote និង rollback ដោយស្វ័យប្រវត្តិ
npm run dev:candidate -- build                 # npm pack + ដំឡើងទៅក្នុង _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # ចាប់ផ្ដើមលើ port ទំនេរ ហើយពិនិត្យ /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # ប្ដូរ current និង previous គ្នា
npm run dev:candidate -- run --from-tarball <file.tgz>  # ប្រើឡើងវិញនូវ tarball ដែលបាន build នៅកន្លែងផ្សេង (CI)
```

- **Build តែម្ដង។** `build` វេចខ្ចប់ tree បច្ចុប្បន្ន (វាត្រូវការ `dist/server.js` ដូច្នេះត្រូវដំណើរការ
  `npm run build:release` ជាមុន) ឬចម្លង `--from-tarball` បន្ទាប់មកដំឡើង tarball ទៅក្នុង
  npm prefix ដាច់ដោយឡែក ព្រោះ tarball មិនមាន `node_modules` ទេ។ id គឺជា sha ខ្លីរបស់ `HEAD`
  (`-dirty` នៅពេល tree មានការផ្លាស់ប្ដូរមូលដ្ឋាន) ឬ `tgz-<sha256>` សម្រាប់ tarball មួយ។ id ស្អាតដែល
  បាន build រួចហើយ នឹងត្រូវបានប្រើឡើងវិញជំនួសឱ្យការ build ឡើងវិញ។ ប្រើ `--force` ដើម្បី build វាឡើងវិញ។
- **ផ្ទៀងផ្ទាត់ package មិនមែន source។** `validate` ចាប់ផ្ដើម CLI ដែលបានដំឡើង
  (`serve --port <free port>`) ជាមួយ `DATA_DIR=<candidate>/data` ថ្មី secrets ក្លែងក្លាយ និងដក
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` និង `INITIAL_PASSWORD` របស់អ្នកប្រតិបត្តិចេញពី
  environment ដើម្បីឱ្យវាពិនិត្យស្ថានភាព keyless loopback របស់ការដំឡើងថ្មី។ វារង់ចាំឱ្យ
  `GET /api/health` ត្រឡប់ 200 តម្រូវឱ្យ `GET /v1/models` ត្រឡប់ 200 បញ្ឈប់ process group
  ហើយកត់ត្រាលទ្ធផលនៅក្នុង `validation.json` រួមជាមួយ hash របស់ tarball។
- **ដំឡើង artifact ដដែលជា active។** `promote` បដិសេធ candidate ដែលមិនមានការផ្ទៀងផ្ទាត់ជោគជ័យសម្រាប់
  hash របស់ tarball បច្ចុប្បន្នរបស់វា។ active slot លំនាំដើមគឺ `_artifacts/candidate/current`; `--target <dir>`
  ជ្រើសរើស directory ផ្សេងទៀតនៅលើ filesystem ដូចគ្នា ហើយ previous slot របស់វាគឺ `<dir>.previous`។
  ការប្ដូរឈ្មោះនីមួយៗមានលក្ខណៈ atomic ហើយការបរាជ័យនៅពាក់កណ្ដាលដំណើរការ នឹងត្រឡប់ការប្ដូរឈ្មោះដែលបានអនុវត្តរួចវិញ។
- **Rollback។** `run` ផ្ទៀងផ្ទាត់ slot ដែលបានដំឡើងជា active ម្ដងទៀត ហើយប្ដូរ `current` និង `previous` ត្រឡប់វិញ នៅពេល
  ការពិនិត្យនោះបរាជ័យ។ candidate ដែលបរាជ័យក្នុងការផ្ទៀងផ្ទាត់លើកដំបូង នឹងមិនត្រូវបានដំឡើងជា active ឡើយ។

អ្វីៗទាំងអស់ត្រូវបានសរសេរនៅក្រោម `_artifacts/candidate/` ដែល git មិនអើពើ។ ការដំឡើង OmniRoute

## បញ្ជីត្រួតពិនិត្យការផ្គូផ្គង

មុនពេលស្នើសុំការពិនិត្យ៖

- បញ្ជាក់ថា base របស់ PR នៅតែជា branch `release/v*` សកម្មដែលខ្ពស់បំផុត។
- Fetch base នោះ ហើយពិនិត្យ commits ដែលបានបញ្ចូលចាប់តាំងពីអ្នកបានបង្កើត branch។
- ពិនិត្យ `git diff <active-base>...HEAD` ដើម្បីរកការផ្លាស់ប្តូរដែលកើតឡើងដោយចៃដន្យ ឬត្រូវបានបង្កើតដោយស្វ័យប្រវត្តិ។
- ដោះស្រាយ conflict របស់ catalog និងឯកសារដែលបានបង្កើតដោយស្វ័យប្រវត្តិ តាមរយៈការធ្វើបច្ចុប្បន្នភាពប្រភព និងបង្កើត output ឡើងវិញ។
- ដំណើរការឡើងវិញនូវរាល់តេស្ត/ច្រកត្រួតពិនិត្យដែលផ្តោតជាក់លាក់ និងបានរាយក្នុងសេចក្តីពិពណ៌នា PR បន្ទាប់ពីការផ្គូផ្គង។
- កុំបន្ធូរបន្ថយ assertions ឬដកតេស្តដែលតម្រូវឱ្យមាន គ្រាន់តែដើម្បីឱ្យត្រូវនឹង base ដែលបានផ្លាស់ទី។
