- ការដាក់គម្រោងបច្ចុប្បន្នឱ្យដំណើរការនៅលើ Fly.io ជាលើកដំបូង
- ការចេញផ្សាយបច្ចុប្បន្នភាពកូដជាបន្តបន្ទាប់
- គម្រោងថ្មីៗដែលអនុវត្តតាមលំហូរការងារដាក់ឱ្យដំណើរការដូចគ្នា

មគ្គុទ្ទេសក៍នេះផ្អែកលើការកំណត់រចនាសម្ព័ន្ធដែលបានផ្ទៀងផ្ទាត់ថាដំណើរការត្រឹមត្រូវសម្រាប់គម្រោងបច្ចុប្បន្ន។ ឈ្មោះកម្មវិធីគឺ `omniroute`។

## 1. គោលដៅនៃការដាក់ពង្រាយ

- វេទិកា៖ Fly.io
- វិធីសាស្ត្រដាក់ពង្រាយ៖ ផ្សព្វផ្សាយដោយផ្ទាល់ពីម៉ាស៊ីនមូលដ្ឋានដោយប្រើ `flyctl`
- បរិស្ថានដំណើរការ៖ ប្រើ `Dockerfile` និង `fly.toml` ដែលមានស្រាប់ក្នុងឃ្លាំងកូដ
- ការរក្សាទុកទិន្នន័យជាអចិន្ត្រៃយ៍៖ Fly Volume ត្រូវបានម៉ោនទៅកាន់ `/data`
- URL សម្រាប់ចូលប្រើ៖ `https://omniroute.fly.dev/`

## 2. ការកំណត់រចនាសម្ព័ន្ធសំខាន់ៗរបស់គម្រោងបច្ចុប្បន្ន

`fly.toml` នៅក្នុងឃ្លាំងកូដបច្ចុប្បន្នត្រូវបានបញ្ជាក់ថាមានធាតុសំខាន់ៗដូចខាងក្រោម៖

```toml
app = 'omniroute'
primary_region = 'sin'

[[mounts]]
  source = 'data'
  destination = '/data'

[processes]
  app = 'node run-standalone.mjs'

[http_service]
  internal_port = 20128

[env]
  TZ = "Asia/Shanghai"
  HOST = "0.0.0.0"
  HOSTNAME = "0.0.0.0"
  BIND = "0.0.0.0"
```

កំណត់សម្គាល់៖

- `app = 'omniroute'` កំណត់ថាការដាក់ពង្រាយត្រូវផ្តោតទៅលើកម្មវិធី Fly មួយណា
- `destination = '/data'` កំណត់ថតម៉ោនរបស់វ៉ូលូមរក្សាទុកជាអចិន្ត្រៃយ៍
- គម្រោងនេះត្រូវតែកំណត់ `DATA_DIR=/data` បើមិនដូច្នោះទេ មូលដ្ឋានទិន្នន័យ និងសោនឹងត្រូវបានសរសេរទៅក្នុងថតបណ្តោះអាសន្នរបស់កុងតឺន័រ

## 3. តម្រូវការជាមុន

### 3.1 ការដំឡើង Fly CLI

Windows PowerShell៖

```powershell
pwsh -Command "iwr https://fly.io/install.ps1 -useb | iex"
```

ប្រសិនបើស្គ្រីបដំឡើងបរាជ័យនៅក្នុងបរិស្ថានរបស់អ្នក អ្នកក៏អាចទាញយកឯកសារប្រតិបត្តិ `flyctl` ដោយដៃ ហើយបន្ថែមវាទៅក្នុង `PATH` របស់អ្នក។

### 3.2 ការចូលគណនី Fly របស់អ្នក

```powershell
flyctl auth login
```

### 3.3 ការផ្ទៀងផ្ទាត់ស្ថានភាពចូលគណនី

```powershell
flyctl auth whoami
flyctl version
```

## 4. ការដាក់ពង្រាយគម្រោងបច្ចុប្បន្នជាលើកដំបូង

### 4.1 ក្លូនកូដ និងចូលទៅក្នុងថត

```powershell
git clone https://github.com/diegosouzapw/OmniRoute.git
cd OmniRoute
```

### 4.2 បញ្ជាក់ឈ្មោះកម្មវិធី

បើក `fly.toml` ហើយផ្ទៀងផ្ទាត់បន្ទាត់ខាងក្រោម៖

```toml
app = 'omniroute'
```

ប្រសិនបើអ្នកកំពុងដាក់ពង្រាយទៅកាន់កម្មវិធីថ្មីផ្ទាល់ខ្លួន អ្នកអាចប្តូរវាទៅជាឈ្មោះដែលមិនស្ទួនទូទាំងសកល ឧទាហរណ៍៖

```toml
app = 'omniroute-yourname'
```

កំណត់សម្គាល់៖

- ត្រូវប្រាកដថាកម្មវិធីដែលអ្នកឃើញនៅក្នុងកុងសូលត្រូវគ្នានឹងតម្លៃ `app` ក្នុង `fly.toml`
- ប្រសិនបើអ្នកធ្លាប់ប្រើឈ្មោះផ្សេងពីមុន ដូចជា `oroute` សូមកុំច្រឡំវាជាមួយ `omniroute`

### 4.3 បង្កើតកម្មវិធី

ប្រសិនបើកម្មវិធីមិនទាន់មាននៅឡើយ៖

```powershell
flyctl apps create omniroute
```

ប្រសិនបើអ្នកបានប្តូរឈ្មោះកម្មវិធី សូមជំនួស `omniroute` ដោយឈ្មោះដែលអ្នកបានជ្រើសរើស។

### 4.4 ដាក់ពង្រាយជាលើកដំបូង

```powershell
flyctl deploy
```

## 5. ប៉ារ៉ាម៉ែត្រចាំបាច់

គម្រោងនេះណែនាំឱ្យកំណត់យ៉ាងហោចណាស់ប៉ារ៉ាម៉ែត្រខាងក្រោមនៅលើ Fly.io។

### 5.1 ប៉ារ៉ាម៉ែត្រដែលបានផ្ទៀងផ្ទាត់

ប៉ារ៉ាម៉ែត្រទាំងនេះត្រូវបានប្រើប្រាស់ក្នុងការដាក់ពង្រាយជាក់ស្តែងលើកម្មវិធី `omniroute` បច្ចុប្បន្ន៖

- `API_KEY_SECRET`
- `DATA_DIR`
- `JWT_SECRET`
- `MACHINE_ID_SALT`
- `NEXT_PUBLIC_BASE_URL`
- `OMNIROUTE_WS_BRIDGE_SECRET` (ចាំបាច់នៅក្នុងបរិស្ថានផលិតកម្ម — ប្រើសម្រាប់ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ WebSocket bridge)
- `STORAGE_ENCRYPTION_KEY`

### 5.2 អំពី `INITIAL_PASSWORD`

គម្រោងបច្ចុប្បន្នមិនកំណត់ `INITIAL_PASSWORD` ទេ ពីព្រោះការដាក់ពង្រាយនេះមិនត្រូវការវា។

ប្រសិនបើវាមិនត្រូវបានកំណត់៖

- កំណត់ហេតុពេលចាប់ផ្តើមនឹងបង្ហាញថាពាក្យសម្ងាត់លំនាំដើមគឺ `CHANGEME`
- អ្នកគួរតែប្តូរពាក្យសម្ងាត់សម្រាប់ចូលនៅក្នុងការកំណត់ប្រព័ន្ធឱ្យបានឆាប់តាមដែលអាចធ្វើទៅបាន បន្ទាប់ពីដាក់ពង្រាយ

ប្រសិនបើអ្នកចង់ចាប់ផ្តើមកំណត់ពាក្យសម្ងាត់ផ្នែកខាងក្រោយដោយស្វ័យប្រវត្តិ អ្នកអាចបន្ថែមវានៅពេលក្រោយ៖

- `INITIAL_PASSWORD`

## 6. ប៉ារ៉ាម៉ែត្រដែលបានណែនាំ

### 6.1 ការកំណត់រចនាសម្ព័ន្ធ Secrets

អថេរខាងក្រោមត្រូវបានណែនាំសម្រាប់ Fly Secrets៖

| អថេរ                         | ការណែនាំ                  | សេចក្តីពិពណ៌នា                                              |
| ---------------------------- | ------------------------- | ----------------------------------------------------------- |
| `API_KEY_SECRET`             | ចាំបាច់                   | ប្រើសម្រាប់បង្កើត និងផ្ទៀងផ្ទាត់ API Key                    |
| `JWT_SECRET`                 | ចាំបាច់                   | ប្រើសម្រាប់សម័យចូលប្រើ និងការចុះហត្ថលេខា JWT                |
| `OMNIROUTE_WS_BRIDGE_SECRET` | ចាំបាច់នៅក្នុង production | Secret សម្រាប់ការផ្ទៀងផ្ទាត់ WebSocket bridge               |
| `STORAGE_ENCRYPTION_KEY`     | ត្រូវបានណែនាំយ៉ាងខ្លាំង   | អ៊ិនគ្រីបព័ត៌មានការតភ្ជាប់រសើបដែលរក្សាទុកនៅពេលមិនប្រើប្រាស់ |
| `MACHINE_ID_SALT`            | ត្រូវបានណែនាំ             | បង្កើតអត្តសញ្ញាណម៉ាស៊ីនដែលមានស្ថិរភាព                       |
| `INITIAL_PASSWORD`           | ជាជម្រើស                  | កំណត់ពាក្យសម្ងាត់ backend ដំបូងនៅពេល deploy លើកដំបូង        |
| ព័ត៌មានសម្ងាត់ឯកជន OAuth/API | តាមតម្រូវការ              | ការកំណត់រចនាសម្ព័ន្ធការផ្ទៀងផ្ទាត់របស់ platform ខាងក្រៅ     |

### 6.2 តម្លៃដែលបានណែនាំសម្រាប់គម្រោងបច្ចុប្បន្ន

| អថេរ                   | តម្លៃដែលបានណែនាំ            |
| ---------------------- | --------------------------- |
| `DATA_DIR`             | `/data`                     |
| `NEXT_PUBLIC_BASE_URL` | `https://omniroute.fly.dev` |

ចំណាំ៖

- `DATA_DIR=/data` មានសារៈសំខាន់ខ្លាំង ហើយត្រូវតែត្រូវគ្នានឹងចំណុច mount របស់ Fly Volume
- `NEXT_PUBLIC_BASE_URL` ត្រូវបានប្រើដោយ scheduler, frontend callbacks និងសេណារីយ៉ូស្រដៀងគ្នា

### 6.3 ការកំណត់រចនាសម្ព័ន្ធ OAuth Callback URL

ប្រសិនបើអ្នកត្រូវការបើកប្រើ providers ដែលផ្អែកលើ OAuth (ឧ. Antigravity, Gemini, Cursor) នៅលើ Fly.io deployment សូមប្រាកដថាបានអនុវត្តចំណុចទាំងពីរខាងក្រោម៖

1. **កំណត់ `NEXT_PUBLIC_BASE_URL` ទៅជា HTTPS domain សាធារណៈរបស់អ្នក**

   ```powershell
   flyctl secrets set NEXT_PUBLIC_BASE_URL=https://omniroute.fly.dev -a omniroute
   ```

   ប្រសិនបើអ្នកកំពុងប្រើ custom domain សូមជំនួសវាដោយ domain ដែលត្រូវគ្នា (ឧ. `https://omniroute.yourdomain.com`)។

2. **កំណត់ callback URL នៅលើ console របស់ provider**

   OAuth providers ទាំងអស់ប្រើ callback path តែមួយគឺ `/callback` — មិនមាន callback route ដាច់ដោយឡែកសម្រាប់ provider នីមួយៗទេ៖

   ```text
   <NEXT_PUBLIC_BASE_URL>/callback
   ```

   ឧទាហរណ៍ មិនថា Gemini, Antigravity, Cursor ឬ GitLab Duo ទេ៖
   - `https://omniroute.fly.dev/callback`

   ប្រសិនបើ `NEXT_PUBLIC_BASE_URL` មិនត្រូវគ្នានឹង callback URL ដែលបានចុះឈ្មោះជាមួយ provider ទេ ដំណើរការ OAuth នឹងបរាជ័យនៅដំណាក់កាល browser redirect។

## 7. ការដំឡើង Secret ដោយប្រើពាក្យបញ្ជាតែមួយ

ពាក្យបញ្ជាខាងក្រោមបង្កើតតម្លៃចៃដន្យដែលមានសុវត្ថិភាព និងសរសេរប៉ារ៉ាម៉ែត្រចាំបាច់ទាំងអស់សម្រាប់គម្រោងបច្ចុប្បន្នទៅកាន់ Fly Secrets ក្នុងមួយជំហាន។

ចំណាំ៖

- មិនរួមបញ្ចូល `INITIAL_PASSWORD`
- មានគោលបំណងប្រើសម្រាប់គម្រោងបច្ចុប្បន្ន `omniroute`

```powershell
$apiKeySecret = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$jwtSecret = [Convert]::ToHexString((1..64 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$machineIdSalt = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$storageKey = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$wsBridgeSecret = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()

flyctl secrets set `
  API_KEY_SECRET=$apiKeySecret `
  JWT_SECRET=$jwtSecret `
  MACHINE_ID_SALT=$machineIdSalt `
  STORAGE_ENCRYPTION_KEY=$storageKey `
  OMNIROUTE_WS_BRIDGE_SECRET=$wsBridgeSecret `
  DATA_DIR=/data `
  NEXT_PUBLIC_BASE_URL=https://omniroute.fly.dev `
  -a omniroute
```

នៅលើ Linux / macOS អ្នកក៏អាចប្រើ `openssl rand -hex 32` បានដែរ៖

```bash
flyctl secrets set OMNIROUTE_WS_BRIDGE_SECRET=$(openssl rand -hex 32) -a omniroute
```

ចំណាំ៖

- `OMNIROUTE_WS_BRIDGE_SECRET` គឺចាំបាច់នៅក្នុង production; ការខ្វះវានឹងធ្វើឱ្យ WebSocket bridge handshake មិនដំណើរការ

ប្រសិនបើអ្នកចង់កំណត់ពាក្យសម្ងាត់ដំបូងផងដែរ៖

```powershell
flyctl secrets set INITIAL_PASSWORD=your-strong-password -a omniroute
```

## 9. ការធ្វើបច្ចុប្បន្នភាព និងការចេញផ្សាយជាបន្តបន្ទាប់

បន្ទាប់ពីធ្វើបច្ចុប្បន្នភាពកូដ ដំណើរការចេញផ្សាយគឺសាមញ្ញ៖

```powershell
git pull
flyctl deploy
```

ប្រសិនបើអ្នកគ្រាន់តែត្រូវការធ្វើបច្ចុប្បន្នភាពប៉ារ៉ាម៉ែត្រដោយមិនផ្លាស់ប្តូរកូដ៖

```powershell
flyctl secrets set KEY=value -a omniroute
```

Fly នឹងធ្វើបច្ចុប្បន្នភាពម៉ាស៊ីនជាបណ្តើរៗដោយស្វ័យប្រវត្តិ។

### 9.1 ការតាមដានបច្ចុប្បន្នភាពរបស់ឃ្លាំងដើម ខណៈពេលរក្សាទុក `fly.toml` របស់ Fork របស់អ្នក

ប្រសិនបើឃ្លាំងបច្ចុប្បន្នគឺជា fork ហើយអ្នកចង់ធ្វើសមកាលកម្មបច្ចុប្បន្នភាពពីឃ្លាំងដើម `https://github.com/diegosouzapw/OmniRoute` សូមអនុវត្តតាមលំហូរការងារខាងក្រោម។

ដំបូង សូមផ្ទៀងផ្ទាត់ remote របស់អ្នក៖

```powershell
git remote -v
```

អ្នកគួរតែឃើញយ៉ាងហោចណាស់៖

- `origin` ចង្អុលទៅកាន់ fork ផ្ទាល់ខ្លួនរបស់អ្នក
- `upstream` ចង្អុលទៅកាន់ឃ្លាំងដើម

ប្រសិនបើ `upstream` មិនទាន់ត្រូវបានកំណត់រចនាសម្ព័ន្ធទេ សូមបន្ថែមវា៖

```powershell
git remote add upstream https://github.com/diegosouzapw/OmniRoute.git
```

មុនពេលធ្វើសមកាលកម្មជាមួយ upstream សូមទាញយក commit និង tag ចុងក្រោយបំផុត៖

```powershell
git fetch upstream --tags
```

ពិនិត្យមើលកំណែបច្ចុប្បន្ន និង tag របស់ upstream៖

```powershell
git describe --tags --always
git show --no-patch --oneline v3.4.7
```

> ចំណាំ៖ កំណែបច្ចុប្បន្នរបស់គម្រោងគឺ `v3.8.0`។ សេចក្តីយោងទៅ `v3.4.7` ខាងក្រោមត្រូវបានរក្សាទុកសម្រាប់ជាឧទាហរណ៍ប្រវត្តិសាស្ត្រប៉ុណ្ណោះ។ សម្រាប់ការចេញផ្សាយជាក់ស្តែង សូមប្រើ `:latest` ឬ tag កំណែបច្ចុប្បន្ន (ឧ. `:v3.8.0`)។

ប្រសិនបើអ្នកចង់បញ្ចូល upstream `main` ចុងក្រោយបំផុត ខណៈពេលបង្ខំឱ្យរក្សាទុក `fly.toml` របស់ fork អ្នក សូមអនុវត្តតាមលំហូរការងារនេះ៖

```powershell
git merge upstream/main
git checkout HEAD~1 -- fly.toml
git add -- fly.toml
git commit -m "chore(deploy): keep fork fly.toml"
git push origin main
```

ចំណាំ៖

- `git merge upstream/main` ធ្វើសមកាលកម្មកូដចុងក្រោយបំផុតពីឃ្លាំងដើម
- `git checkout HEAD~1 -- fly.toml` ស្តារ `fly.toml` ផ្ទាល់ខ្លួនរបស់ fork អ្នកពីមុនពេលបញ្ចូលគ្នា
- ប្រសិនបើ upstream មិនបានកែប្រែ `fly.toml` ទេ ជំហាននេះនឹងមិនបង្កើតភាពខុសគ្នាណាមួយឡើយ
- ប្រសិនបើ upstream បានកែប្រែ `fly.toml` ជំហាននេះធានាថា ឈ្មោះកម្មវិធី Fly របស់អ្នក ការម៉ោន volume តំបន់ និងការកំណត់រចនាសម្ព័ន្ធដាក់ឱ្យដំណើរការផ្សេងទៀតដែលជាក់លាក់ចំពោះ fork នឹងមិនត្រូវបានសរសេរជាន់លើទេ

ប្រសិនបើអ្នកចង់តម្រឹមទៅតាម tag នៃការចេញផ្សាយជាក់លាក់មួយ (ឧ. `v3.4.7`) ជាដំបូង សូមផ្ទៀងផ្ទាត់ថា tag នោះត្រូវបានដាក់បញ្ចូលរួចហើយនៅក្នុង `upstream/main`៖

```powershell
git merge-base --is-ancestor v3.4.7 upstream/main
```

ប្រសិនបើពាក្យបញ្ជាត្រឡប់មកដោយជោគជ័យ នោះមានន័យថា `upstream/main` មានកំណែនោះរួចហើយ។ អ្នកអាចបញ្ចូល `upstream/main` បានដោយផ្ទាល់។

### 9.2 លំដាប់នៃការចេញផ្សាយស្តង់ដារ បន្ទាប់ពីធ្វើសមកាលកម្ម Upstream

បន្ទាប់ពីធ្វើសមកាលកម្មជាមួយឃ្លាំងដើម សូមអនុវត្តតាមលំដាប់នៃការចេញផ្សាយដែលបានណែនាំនេះ៖

1. `git fetch upstream --tags`
2. `git merge upstream/main`
3. ស្តារ `fly.toml` របស់ fork
4. `git push origin main`
5. `flyctl deploy`
6. `flyctl status -a omniroute`
7. `flyctl logs --no-tail -a omniroute`

នេះគឺជាលំហូរការងារជាក់ស្តែងដែលបានប្រើនៅពេលដំឡើងកំណែគម្រោងបច្ចុប្បន្នទៅ `v3.4.7` (ឧទាហរណ៍នេះសំដៅទៅកំណែប្រវត្តិសាស្ត្រ ចំណែកឯកំណែជាក់ស្តែងបច្ចុប្បន្នគឺ `v3.8.0`)។

## 11. សញ្ញាបង្ហាញភាពជោគជ័យ

បន្ទាប់ពីដាក់ឱ្យដំណើរការដោយជោគជ័យ កំណត់ហេតុគួរតែបង្ហាញខ្លឹមសារស្រដៀងនឹង៖

```text
[bootstrap] Secrets persisted to: /data/server.env
[DB] SQLite database ready: /data/storage.sqlite
```

ចំណុចទាំងពីរនេះមានសារៈសំខាន់ខ្លាំង៖

- `/data/server.env` បញ្ជាក់ថាទិន្នន័យសម្ងាត់ពេលដំណើរការត្រូវបានសរសេរទៅកាន់ volume អចិន្ត្រៃយ៍
- `/data/storage.sqlite` បញ្ជាក់ថាមូលដ្ឋានទិន្នន័យត្រូវបានសរសេរទៅកាន់ volume អចិន្ត្រៃយ៍

ប្រសិនបើអ្នកឃើញ `/app/data/...` ជំនួសវិញ នោះ `DATA_DIR` ត្រូវបានកំណត់រចនាសម្ព័ន្ធមិនត្រឹមត្រូវ ហើយត្រូវតែកែតម្រូវភ្លាមៗ។

## 12. បញ្ហាទូទៅ

### 12.1 ទំព័រ `Secrets` ទទេ

ជាធម្មតា មានមូលហេតុពីរ៖

- អ្នកមិនទាន់បានដំណើរការ `flyctl secrets set`
- អ្នកកំពុងមើលកម្មវិធីផ្សេងមួយ (ឧ. `oroute` ជំនួសឱ្យ `omniroute`)

### 12.2 `flyctl deploy` រាយការណ៍ថា `app not found`

បង្កើតកម្មវិធីជាមុនសិន៖

```powershell
flyctl apps create omniroute
```

### 12.3 ការញែក `fly.toml` បរាជ័យ

ពិនិត្យចំណុចខាងក្រោម៖

- ថាតើមានតួអក្សរខូចនៅក្នុងសេចក្ដីអធិប្បាយឬអត់
- ថាតើសញ្ញាសម្រង់ និងការចូលបន្ទាត់របស់ TOML ត្រឹមត្រូវឬអត់

### 12.4 ទិន្នន័យមិនត្រូវបានរក្សាទុកជាអចិន្ត្រៃយ៍

ផ្ទៀងផ្ទាត់ចំណុចទាំងពីរខាងក្រោម៖

- `fly.toml` មាន `destination = '/data'`
- `DATA_DIR` ត្រូវបានកំណត់ជា `/data`

### 12.5 តើវាអាចដំណើរការដោយគ្មាន `INITIAL_PASSWORD` បានទេ?

បាន វាអាចដំណើរការបាន។ វានឹងប្រើពាក្យសម្ងាត់លំនាំដើម `CHANGEME` ជំនួសវិញ។ សម្រាប់បរិស្ថានផលិតកម្ម សូមណែនាំឱ្យប្ដូរពាក្យសម្ងាត់ backend ឱ្យបានឆាប់តាមដែលអាចធ្វើទៅបាន។

## 13. ការប្រើឡើងវិញសម្រាប់គម្រោងថ្មី

ប្រសិនបើអ្នកកំពុងដាក់ឱ្យដំណើរការគម្រោងថ្មីដោយអនុវត្តតាមឯកសារនេះ អ្នកគ្រាន់តែត្រូវផ្លាស់ប្ដូរធាតុទាំងនេះ៖

1. ផ្លាស់ប្ដូរតម្លៃ `app` នៅក្នុង `fly.toml`
2. ផ្លាស់ប្ដូរ `NEXT_PUBLIC_BASE_URL`
3. រក្សា `DATA_DIR=/data`
4. បង្កើត `API_KEY_SECRET`, `JWT_SECRET`, `MACHINE_ID_SALT` និង `STORAGE_ENCRYPTION_KEY` ឡើងវិញ
5. បន្ទាប់ពីដាក់ឱ្យដំណើរការលើកដំបូង សូមផ្ទៀងផ្ទាត់ថាកំណត់ហេតុត្រូវបានសរសេរទៅកាន់ `/data`

កុំប្រើសោពីគម្រោងមុនឡើងវិញ។

## 14. បញ្ជីត្រួតពិនិត្យការចេញផ្សាយអប្បបរមាសម្រាប់គម្រោងបច្ចុប្បន្ន

ពាក្យបញ្ជាដែលប្រើញឹកញាប់បំផុតសម្រាប់ការចេញផ្សាយបន្ទាប់ៗគឺ៖

```powershell
flyctl auth whoami
flyctl status -a omniroute
flyctl secrets list -a omniroute
flyctl deploy
flyctl logs --no-tail -a omniroute
```

សម្រាប់ការចេញផ្សាយធម្មតា ពាក្យបញ្ជាស្នូលគឺ៖

```powershell
flyctl deploy
```

សម្រាប់ការដាក់ឱ្យដំណើរការជាលើកដំបូងនៅក្នុងបរិស្ថានថ្មី ជំហានស្នូលគឺ៖

1. `flyctl auth login`
2. `flyctl apps create omniroute`
3. `flyctl secrets set ... -a omniroute`
4. `flyctl deploy`
5. `flyctl logs --no-tail -a omniroute`
