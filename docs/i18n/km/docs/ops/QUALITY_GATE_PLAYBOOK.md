## ផ្នែកទី 1 — សេចក្តីសន្និដ្ឋាន និងចំណាត់ថ្នាក់កម្រិតភាពចាស់ទុំ

**និទ្ទេសរួម៖ A− / "កម្រិតខ្ពស់"។ ស្ថិតក្នុងចំណោមគម្រោងកំពូលប្រមាណ ~5–10%។** ប្រព័ន្ធនេះអនុវត្ត
លំនាំជាច្រើនដោយឯករាជ្យ ដែលឧស្សាហកម្មបានកំណត់ឈ្មោះយ៉ាងច្បាស់ — នេះគឺជាសញ្ញានៃភាពស្របគ្នាដ៏ខ្លាំងបំផុត
(យើងមិនបានចម្លងបញ្ជីត្រួតពិនិត្យទេ ប៉ុន្តែយើងបានឈានទៅដល់ឧត្តមានុវត្តន៍ត្រឹមត្រូវដូចគ្នា)។

## ផ្នែកទី 2 — ការវាយតម្លៃយ៉ាងម៉ត់ចត់ (ចំណុចខ្លាំង + ចំណុចខ្សោយដោយស្មោះត្រង់)

### ចំណុចខ្លាំង (អ្វីដែលលើសពីមធ្យម)

1. **ម៉ាស៊ីន ratchet ពហុរង្វាស់។** ជាស្នូលនៃប្រព័ន្ធ។ មានរង្វាស់ចំនួន 24 នៅក្នុង `quality-baseline.json`
   - baseline ជាក់លាក់ចំនួន 4 ដែលនីមួយៗមានទិសដៅ (`up`/`down`), កម្រិតអត់ឱន (`eps`), slack
     (`tightenSlack`) និងទង់ `dedicatedGate`។ អ្វីដែលត្រូវបានកែរួច **នៅតែ** រក្សាភាពត្រឹមត្រូវ — វាជា
     ថ្នាំបន្សាបការធ្លាក់ចុះគុណភាពជាបន្តបន្ទាប់របស់ codebase។
2. **ការការពារជាច្រើនស្រទាប់សម្រាប់ខ្សែច្រវាក់ផ្គត់ផ្គង់។** SAST (CodeQL/Sonar) + ការស្វែងរកព័ត៌មានសម្ងាត់ (gitleaks ជាមួយ
   `useDefault`) + SCA (osv/npm-audit/Trivy/Dependabot) + អាជ្ញាបណ្ណ + lockfile + SBOM + SLSA
   provenance + Scorecard + ការពង្រឹងសុវត្ថិភាព workflow (zizmor)។ មាន codebase តិចតួចណាស់ដែលមានបណ្ដុំឧបករណ៍ពេញលេញបែបនេះ។
3. **ថ្នាំបន្សាបច្បាប់របស់ Goodhart។** ការកំណត់ coverage ជាគោលដៅគឺជា anti-pattern បែបបុរាណ
   ("នៅពេលរង្វាស់ក្លាយជាគោលដៅ វាលែងជារង្វាស់ល្អទៀតហើយ")។ យើងមាន
   យន្តការតុល្យភាព៖ **mutation testing** (វាស់ថាតើតេស្តចាប់បាន bug ដែរឬទេ មិនមែនគ្រាន់តែ
   វាដំណើរការឆ្លងកាត់បន្ទាត់កូដនោះឬអត់ទេ), **`check-test-masking`** (ទប់ស្កាត់ការធ្វើឱ្យ assert ខ្សោយដើម្បីឱ្យតេស្តជាប់),
   **កម្រិត coverage អប្បបរមាតាម module** (បង្ខំឱ្យធ្វើតេស្តកូដដែលមានហានិភ័យ HIGH មិនមែនតែផ្នែកងាយៗទេ) និង
   **`check-pr-evidence`** (Hard Rule #18)។
4. **ច្រកត្រួតពិនិត្យប្រឆាំង hallucination / ភាពមិនស៊ីសង្វាក់គ្នា។** ជាប្រភេទដែលកម្រ និងមានតម្លៃ៖ `check-known-symbols`,
   `check-fetch-targets`, `check-openapi-routes`, `check-docs-symbols` ធានាថា docs, specs និង
   string dispatches ចង្អុលទៅកាន់ symbols ដែលនៅមានសុពលភាព។ វាចាប់បាន "ការពុកផុយ" ដែល lint/test មិនអាចចាប់បាន។
5. **វដ្តជីវិតពីការណែនាំ→ការទប់ស្កាត់។** ច្រកត្រួតពិនិត្យថ្មីៗចាប់ផ្តើមក្នុងស្ថានភាពជាការណែនាំ (មិនទប់ស្កាត់ការ merge ខណៈកំពុង
   ឈានទៅរកភាពពេញលេញ) បន្ទាប់មកក្លាយជាច្រកទប់ស្កាត់នៅចុងវដ្ត។ កាត់បន្ថយឧបសគ្គដោយមិនបាត់បង់កម្រិតគុណភាពអតិបរមា។
6. **ការរំលងដោយរលូននៅពេលខ្វះហេដ្ឋារចនាសម្ព័ន្ធ។** Scanners (`--ratchet`) បញ្ចប់ជាមួយ `exit 0` ប្រសិនបើ binary/network
   បរាជ័យ — ការខ្វះហេដ្ឋារចនាសម្ព័ន្ធមិនដែលទប់ស្កាត់ PR ដែលត្រឹមត្រូវឡើយ។ នេះជាវិស្វកម្មដែលមានភាពចាស់ទុំ។
7. **វប្បធម៌ដែលត្រូវបានកំណត់ជាកូដ។** Hard Rules + `trust-but-verify` + stale-allowlist + evidence-gate
   បម្លែងវិន័យទៅជាការផ្ទៀងផ្ទាត់ដោយស្វ័យប្រវត្តិ។

### ចំណុចខ្សោយដោយស្មោះត្រង់ (ចន្លោះប្រហោងពិតប្រាកដ)

1. **🔴 ការបែងចែក fast-gates នៅតែបន្សល់ចន្លោះប្រហោងផ្នែករចនាសម្ព័ន្ធ។** `quality.yml` (PR→`release/**`)
   ឥឡូវនេះដំណើរការ typecheck, តេស្តកំណត់បានរហ័ស និង production build ក្នុងស្ថានភាពជាការណែនាំសម្រាប់ code PRs
   ប៉ុន្តែវានៅតែមិនដំណើរការវិសាលភាពពេញលេញនៃ release-PR ពី `ci.yml` ទេ (coverage ratchets,
   package artifact, integration, E2E, SonarQube)។ ហេតុផល (ល្បឿន) គឺសមហេតុផល ប៉ុន្តែច្រកត្រួតពិនិត្យ
   គួរតែស្ថិតនៅកន្លែងដែលការ merge កើតឡើង (shift-left)។ **ការកែលម្អរចនាសម្ព័ន្ធដែលនៅសល់ និងធំបំផុត។**
2. **🟠 ហានិភ័យនៃការរីករាលដាល/ភាពនឿយហត់ដោយសារច្រកត្រួតពិនិត្យ។** ~46 gates + 25 jobs គឺច្រើនខ្លាំងណាស់។ Sonar ផ្ទាល់ព្រមានថា៖
   លក្ខខណ្ឌច្រើនពេកបង្កឱ្យមាន "ភាពនឿយហត់ដោយសារច្រកត្រួតពិនិត្យ" និងការជជែកដេញដោលអំពីអាទិភាព ដោយមានហានិភ័យដែលច្រកត្រួតពិនិត្យមួយ
   ត្រូវបានមិនអើពើ។ DORA ព្រមានថាច្រកត្រួតពិនិត្យដ៏ធ្ងន់ធ្ងរធ្វើឱ្យខាតបង់ lead-time។ យើងកាត់បន្ថយបញ្ហានេះតាមរយៈកម្រិតជាការណែនាំ និង
   ratchets ដែលមិនដាច់ខាត ប៉ុន្តែយើងនៅខ្វះ **ការពិនិត្យ ROI ជាប្រចាំសម្រាប់ច្រកត្រួតពិនិត្យនីមួយៗ** (micro-gates មួយចំនួនសម្រាប់
   doc-sync អាចត្រូវបានបញ្ចូលគ្នា)។
3. **🟠 ពិន្ទុ mutation មិនទាន់ជា ratchet នៅឡើយ។** ថ្នាំបន្សាបដែលខ្លាំងបំផុតប្រឆាំងនឹងការកេងបន្លំ coverage

   PR ដែលមិនពាក់ព័ន្ធ) — ប៉ុន្តែមានដំណោះស្រាយកណ្ដាល (ទប់ស្កាត់តែ CRITICAL+fixable ដូចដែលយើងបានធ្វើជាមួយ
   Trivy)។ ការដាក់ oasdiff ជាការណែនាំមានន័យថាការផ្លាស់ប្តូរដែលបំបែក contract អាចឆ្លងផុតបាន។

## ផ្នែកទី 3 — កាតាឡុកពេញលេញនៃចំណុចត្រួតពិនិត្យគុណភាព (អាចយកទៅប្រើឡើងវិញបាន)

ប្រភេទទាំង 12 ខាងក្រោមគឺជា "ប្រព័ន្ធគុណភាព" ក្នុងទម្រង់ដែលអាចយកទៅប្រើឡើងវិញបាន។ ប្រភេទនីមួយៗរាយបញ្ជី
**គោលបំណង** (អ្វីដែលត្រូវការពារ), **ឧបករណ៍ដែលយើងប្រើ** និង **ជម្រើសសមមូលដែលមិនអាស្រ័យលើឧបករណ៍ជាក់លាក់**
ដើម្បីអនុវត្តដូចគ្នានៅលើ stack ណាមួយ។

### 1. រចនាប័ទ្ម និងការធ្វើទ្រង់ទ្រាយ (មានលទ្ធផលកំណត់ច្បាស់លាស់ និងលឿន)

- **OmniRoute:** Prettier + ESLint តាមរយៈ lint-staged (pre-commit), 2-spaces/double-quotes/100col។
- **ទូទៅ:** formatter មួយដែលអាចកែតម្រូវដោយស្វ័យប្រវត្តិបាន + linter មួយ ដែលដំណើរការនៅក្នុង pre-commit លើឯកសារដែលបាន staged។

### 2. ប្រភេទទិន្នន័យ

- **OmniRoute:** `typecheck:core` (រារាំង) + `typecheck:noimplicit:core` (ផ្តល់អនុសាសន៍) + រង្វាស់ `type-coverage` ដែលមានកម្រិត ratchet 92.17% + ថវិកា any សម្រាប់ឯកសារនីមួយៗ។
- **ទូទៅ:** ការត្រួតពិនិត្យប្រភេទយ៉ាងតឹងរ៉ឹងក្នុង CI + រង្វាស់ type-coverage ដែលមានកម្រិត ratchet + ថវិកា `any`/ច្រកគេចវេះសម្រាប់ឯកសារនីមួយៗ។

### 3. ការធ្វើតេស្ត (កម្រិតខ្លាំង)

- **OmniRoute:** កម្មវិធីដំណើរការតេស្ត 2 ដែលមិនត្រួតស៊ីគ្នា (Node native + vitest), 8 shards, កម្រិតអប្បបរមានៃ coverage សកល 60/60/60/60 + កម្រិត ratchet ~76% + **កម្រិតអប្បបរមាតាមម៉ូឌុលចំនួន 8 សម្រាប់ម៉ូឌុលសំខាន់ៗ** + ការធ្វើ property tests រៀងរាល់យប់ + **ការធ្វើ mutation testing** រៀងរាល់យប់។
- **ទូទៅ:** កម្មវិធីដំណើរការតេស្ត + កម្រិតអប្បបរមានៃ coverage បែប **ដាច់ខាត** (ទប់ស្កាត់ការធ្លាក់ដល់សូន្យ) + កម្រិត **ratchet** នៃ coverage (ទប់ស្កាត់ការថយក្រោយ) + **កម្រិតអប្បបរមាតាមម៉ូឌុលសម្រាប់កូដដែលមានហានិភ័យខ្ពស់** (ទប់ស្កាត់ Goodhart) + ការធ្វើតេស្តផ្អែកលើ property សម្រាប់ logic សុទ្ធ + **ការធ្វើ mutation testing** រៀងរាល់យប់ ជារង្វាស់ពិតប្រាកដនៃគុណភាពតេស្ត។

### 4. គោលការណ៍តេស្ត (ទប់ស្កាត់ការបន្លំ)

- **OmniRoute:** `pr-test-policy` (កូដ production តម្រូវឱ្យមានតេស្ត), `check-test-masking` (រារាំង assert ដែលត្រូវបានធ្វើឱ្យខ្សោយ), `pr-evidence` (ការអះអាងថាជោគជ័យតម្រូវឱ្យមានប្លុកភស្តុតាង), `test-discovery` (តេស្តនីមួយៗត្រូវបានប្រមូលដោយកម្មវិធីដំណើរការតេស្ត)។
- **ទូទៅ:** ច្រកត្រួតពិនិត្យ "កូដថ្មី ⇒ តេស្តថ្មី" + ឧបករណ៍រកឃើញ assert ដែលត្រូវបានដកចេញ/តក្កវិជ្ជាដែលតែងតែពិត + តម្រូវការភស្តុតាង (TDD ឬ living test) + ការធានាថាគ្មានតេស្តណាមួយត្រូវបានទុកឯកោនៅខាងក្រៅ globs។

### 5. ភាពស្មុគស្មាញ និងសុខភាពកូដ (ratchets)

- **OmniRoute:** ការព្រមាន ESLint (3769↓), កូដស្ទួន jscpd (5.72%↓), ភាពស្មុគស្មាញ cyclomatic+max-lines (1800↓), ភាពស្មុគស្មាញផ្នែកការគិត sonarjs (753↓), កូដដែលមិនប្រើ/exports ដែលមិនប្រើ knip (339↓), ទំហំឯកសារតាមឯកសារនីមួយៗ (បង្កក ហើយអាចតែបង្រួម), ភាពអាស្រ័យជារង្វង់ (Tarjan ផ្ទាល់ខ្លួន, រារាំង)។
- **ទូទៅ:** អនុវត្ត ratchet លើរង្វាស់សុខភាពទាំងអស់ (ការព្រមាន, កូដស្ទួន, ភាពស្មុគស្មាញ cyclomatic **និង** cognitive, កូដដែលមិនប្រើ, ទំហំឯកសារ, វដ្ត import)។ ទិសដៅតែងតែជា "កុំឱ្យថយក្រោយ"។

### 6. សុវត្ថិភាពស្ថិតិ (SAST + ទិន្នន័យសម្ងាត់)

- **OmniRoute:** CodeQL (កម្រិត ratchet នៃការជូនដំណឹង = 0), gitleaks (`[extend] useDefault=true` — សំខាន់បំផុត!), SonarQube, ច្បាប់សុវត្ថិភាពផ្ទាល់ខ្លួន (public-creds, error-helper, route-guard-membership, route-validation)។
- **ទូទៅ:** SAST (CodeQL/Sonar/semgrep) ដែលមានកម្រិត ratchet សម្រាប់ការជូនដំណឹង + កម្មវិធីស្កេនទិន្នន័យសម្ងាត់ដែលមាន **សំណុំច្បាប់លំនាំដើមដែលទទួលមរតក** (ការកំណត់រចនាសម្ព័ន្ធផ្ទាល់ខ្លួនដែលសរសេរជាន់លើលំនាំដើម = ចំណុចខ្វាក់) + ច្រកត្រួតពិនិត្យសុវត្ថិភាព Hard Rule ជាក់លាក់សម្រាប់គម្រោង។

### 7. ខ្សែសង្វាក់ផ្គត់ផ្គង់ (ភាពអាស្រ័យ)

- **OmniRoute:** osv-scanner + npm-audit + Trivy + Dependabot (SCA), license-checker (បញ្ជីអនុញ្ញាត SPDX), lockfile-lint (HTTPS+sha512+registry), `check-deps` ទប់ស្កាត់ slopsquatting (បញ្ជីអនុញ្ញាត + អាយុ ≥72h)។
- **ទូទៅ:** SCA ពីប្រភពច្រើន + បញ្ជីអនុញ្ញាតអាជ្ញាបណ្ណ + ការត្រួតពិនិត្យសុចរិតភាព lockfile + បញ្ជីអនុញ្ញាតភាពអាស្រ័យដែលមានការត្រួតពិនិត្យអាយុ/typosquatting + bot ធ្វើបច្ចុប្បន្នភាពជាក្រុម។

### 8. ខ្សែសង្វាក់ផ្គត់ផ្គង់ (ការបង្កើត និងការចេញផ្សាយ)

- **OmniRoute:** SBOM (CycloneDX + syft), SLSA provenance (`--provenance`), OpenSSF Scorecard (ប្រចាំសប្តាហ៍), ការពង្រឹង workflow (zizmor: artipacked→`persist-credentials:false`, cache-poisoning, token-permissions)។
- **ទូទៅ:** បង្កើត SBOM នៅពេល publish + provenance ដែលបានចុះហត្ថលេខា (SLSA L2+) + Scorecard តាមកាលវិភាគ + ពង្រឹង workflow ទាំងអស់ (token ដែលមានសិទ្ធិអប្បបរមា, មិនរក្សាទុក credentials សម្រាប់ checkout ដែលមិនមែនជា pusher, actions ត្រូវបានចាក់សោដោយ SHA)។

### 9. កិច្ចសន្យា និង API

- **OmniRoute:** oasdiff (ការផ្លាស់ប្តូរ OpenAPI ដែលបំបែកភាពឆបគ្នា), schemathesis (contract fuzz រៀងរាល់យប់), openapi-coverage (% នៃ routes ដែលមានឯកសារ, កម្រិត ratchet 38.3%), openapi-security-tiers (spec ទល់នឹង route-guard)។
- **ទូទៅ:** contract diff សម្រាប់ការផ្លាស់ប្តូរដែលបំបែកភាពឆបគ្នា (oasdiff/buf) + property-based fuzz ធៀបនឹង spec (schemathesis) + coverage ឯកសារដែលមានកម្រិត ratchet + ភាពស្របគ្នារវាង spec↔code។

### 10. ឯកសារ និង i18n (ទប់ស្កាត់ការចាស់ខូច)

- **OmniRoute:** docs-sync (កំណែដែលបានឆ្លុះគ្នា), docs-counts-sync (លេខក្នុងឯកសារធៀបនឹងកូដ), env-doc-sync, doc-links, fabricated-docs, cli-i18n, i18n-ui-coverage (`--threshold=65` + កម្រិត ratchet 80.1%)។
- **ទូទៅ:** ធ្វើសមកាលកម្មកំណែ/ចំនួន/env-vars រវាងឯកសារ និងកូដ (ប្រើជាច្រកត្រួតពិនិត្យ មិនមែនគ្រាន់តែជឿទុកចិត្ត) + ផ្ទៀងផ្ទាត់តំណខាងក្នុង + coverage នៃ i18n ដែលមានកម្រិត ratchet។

### 11. ការទប់ស្កាត់ការប្រឌិតព័ត៌មាន / ភាពស្របគ្នា (ប្រភេទដែលកម្រមាន)

- **OmniRoute:** known-symbols (string dispatch ⇒ living symbol), provider-consistency, fetch-targets (client fetch ⇒ route ពិតប្រាកដ), docs-symbols, db-rules (Hard Rules #2/#5), migration-numbering។
- **ទូទៅ:** សម្រាប់រាល់ "ប្រភពនៃការពិតដែលបានចម្លងស្ទួន" (registry, string dispatch, ឯកសារយោងឆ្លង layer) ត្រូវមានច្រកត្រួតពិនិត្យដែលបញ្ជាក់ថាភាគីទាំងពីរត្រូវគ្នា។ វារកឃើញការចាស់ខូចដែល typecheck/test មិនអាចរកឃើញ។

### 12. ភាពធន់ និង domain (ជាក់លាក់ចំពោះផលិតផល)

- **OmniRoute:** chaos (ការបញ្ចូលកំហុសដោយចេតនា), heap-growth (ការលេចធ្លាយ), k6 (soak), promptfoo+garak (ការធ្វើ red-team លើ LLM តាម OWASP LLM Top 10), ច្បាប់ភាពធន់ទាំង 3 (circuit-breaker/cooldown/lockout)។
- **ទូទៅ:** កំណត់អត្តសញ្ញាណរបៀបបរាជ័យនៃ domain **របស់អ្នក** ហើយមានច្រកត្រួតពិនិត្យមួយ (ទោះបីធ្វើតែរៀងរាល់យប់ក៏ដោយ) សម្រាប់របៀបនីមួយៗ។ សម្រាប់កម្មវិធី AI៖ ការធ្វើ red-team លើ injection។ សម្រាប់ប្រព័ន្ធចែកចាយ៖ chaos + leak + soak។

## ផ្នែកទី 4 — ផែនការចម្លងអនុវត្តសម្រាប់គម្រោងណាមួយ

ស្ថាបនាជា **ដំណាក់កាល** ដោយដំណាក់កាលនីមួយៗផ្តល់តម្លៃដោយឯករាជ្យ។ កុំព្យាយាមអនុវត្តទាំង 12 ប្រភេទក្នុងពេលតែមួយ —
វាបង្កឱ្យមានភាពនឿយហត់ពីរបាំងត្រួតពិនិត្យ ដូចដែលផ្នែកទី 2 បានព្រមាន។ រាល់របាំងត្រួតពិនិត្យថ្មី ត្រូវចាប់ផ្តើមក្នុងស្ថានភាព **ផ្តល់ដំបូន្មាន** ហើយ
ក្លាយជា **រារាំង** នៅពេលមានស្ថិរភាព។

### ចំណុចស្នូលដែលអាចប្រើឡើងវិញបាន៖ "កាយវិភាគរបស់របាំងត្រួតពិនិត្យ ratchet"

ប្រព័ន្ធទាំងមូលដំណើរការជុំវិញគំរូឯកសារ 3 នេះ។ ចម្លងវាជាមុនសិន៖

1. **`baseline.json`** — តម្លៃម៉ែត្រដែលបានបង្កក + `direction` (`up`/`down`) + `eps` (ការពារភាពមិនថេរ) + `tightenSlack` + `dedicatedGate`។
2. **`collect-metrics.<ext>`** — ដំណើរការឧបករណ៍ ទាញយកតម្លៃលេខ ហើយសរសេរ `metrics.json`។
3. **`check-ratchet.<ext>`** — ប្រៀបធៀប `metrics.json` ជាមួយ `baseline.json`; `exit 1` **តែ** នៅពេលថយចុះលើសពី `eps`; `exit 0` (រំលងដោយសមរម្យ) ប្រសិនបើខ្វះឧបករណ៍/ហេដ្ឋារចនាសម្ព័ន្ធ; ជាមួយ `--require-tighten`, `exit 1` ប្រសិនបើវា **បានប្រសើរឡើង** ដោយមិនបានធ្វើបច្ចុប្បន្នភាព baseline (រក្សាឱ្យបាននូវភាពប្រសើរឡើងនោះ)។

នៅពេលគំរូនេះត្រូវបានដាក់ឱ្យប្រើ **រាល់** ម៉ែត្រថ្មី (coverage, complexity, warnings, SAST alerts, bundle size, mutation score…) គ្រាន់តែជាបន្ទាត់មួយនៅក្នុង baseline ប៉ុណ្ណោះ។

### ដំណាក់កាលទី 0 — មូលដ្ឋានគ្រឹះ (សប្តាហ៍ទី 1)

មាន CI; formatter + linter + typecheck + test runner 1 + កម្រិតអប្បបរមា coverage **ដាច់ខាត**
(ឧ. 60%)។ Pre-commit ដំណើរការការត្រួតពិនិត្យរហ័សដែលអាចកែដោយស្វ័យប្រវត្តិបាន។ _លទ្ធផល៖ គ្មាន PR ណាមួយធ្វើឱ្យមូលដ្ឋានគ្រឹះខូចឡើយ។_

### ដំណាក់កាលទី 1 — ម៉ាស៊ីន ratchet (សប្តាហ៍ទី 2) — **មូលដ្ឋានគ្រឹះនៃអ្វីៗទាំងអស់**

អនុវត្តឯកសារ 3 ខាងលើ។ បង្កក baselines សម្រាប់៖ warnings, coverage, complexity, duplication,
dead code, file size។ _លទ្ធផល៖ ចាប់ពីពេលនេះទៅ codebase អាចតែប្រសើរឡើងប៉ុណ្ណោះ។_

### ដំណាក់កាលទី 2 — ការវិភាគស្ថិតិឱ្យស៊ីជម្រៅ (សប្តាហ៍ទី 3)

SAST (CodeQL/Sonar/semgrep) ជាមួយ alert ratchet; secrets scanner (**ទទួលបន្ត ruleset លំនាំដើម**);
SCA (osv/Dependabot) + license allowlist + lockfile-lint។ _លទ្ធផល៖ ភាពងាយរងគ្រោះដែលបានដឹង និង
ព័ត៌មានសម្ងាត់ដែលបានលេចធ្លាយ មិនអាចឆ្លងកាត់បានឡើយ។_

### ដំណាក់កាលទី 3 — ខ្សែសង្វាក់ផ្គត់ផ្គង់សម្រាប់ការស្ថាបនា (សប្តាហ៍ទី 4)

SBOM នៅពេល publish + provenance ដែលបានចុះហត្ថលេខា (SLSA L2) + Scorecard តាមកាលវិភាគ + ការពង្រឹងសុវត្ថិភាព workflow
(zizmor: tokens អប្បបរមា, គ្មាន credentials ដែលបានរក្សាទុក, actions ដែលបានភ្ជាប់ជាប់នឹងកំណែជាក់លាក់)។ _លទ្ធផល៖ ការចេញផ្សាយដែលអាចតាមដានបាន និង
មិនអាចកែបន្លំបាន។_

### ដំណាក់កាលទី 4 — អាំងតង់ស៊ីតេនៃការធ្វើតេស្ត (សប្តាហ៍ទី 5–6)

runner ទី 2 ប្រសិនបើមានប្រយោជន៍; **កម្រិតអប្បបរមា coverage តាម module សម្រាប់ modules សំខាន់ៗ** (ការពារ Goodhart);
property-based សម្រាប់ logic សុទ្ធ; **mutation testing រៀងរាល់យប់** → នៅពេលទទួលបាន score ទី 1 សូមធ្វើឱ្យ
`mutationScore` ក្លាយជា ratchet។ _លទ្ធផល៖ coverage លែងជាម៉ែត្រសម្រាប់តែលម្អមុខមាត់; តេស្តត្រូវបានបញ្ជាក់ថាអាចចាប់កំហុសបាន។_

### ដំណាក់កាលទី 5 — កិច្ចសន្យា និងការវិភាគឌីណាមិក (សប្តាហ៍ទី 7)

ប្រសិនបើមាន API សាធារណៈ៖ oasdiff (ការផ្លាស់ប្តូរដែលបំបែកភាពត្រូវគ្នា, **រារាំង**) + schemathesis (fuzz រៀងរាល់យប់)។
DAST/red-team រៀងរាល់យប់ តាមភាពសមស្របសម្រាប់ដែននោះ។ _លទ្ធផល៖ កិច្ចសន្យាមិនខូចដោយស្ងៀមស្ងាត់ឡើយ។_

### ដំណាក់កាលទី 6 — ការប្រឆាំងការប្រឌិតព័ត៌មាន និងតម្រូវការតាមដែន (សប្តាហ៍ទី 8)

របាំងត្រួតពិនិត្យភាពស៊ីសង្វាក់គ្នាមួយ សម្រាប់ "ការពិតដែលបានចម្លងស្ទួន" នីមួយៗនៅក្នុងគម្រោង។ របាំងត្រួតពិនិត្យ
របៀបបរាជ័យតាមដែនជាក់លាក់ (សម្រាប់ AI៖ injection red-team)។ _លទ្ធផល៖ ការពុកផុយនៃរចនាសម្ព័ន្ធ និងការបរាជ័យតាមដែន មានសំណាញ់សុវត្ថិភាព។_

### ដំណាក់កាលទី 7 — អភិបាលកិច្ច (ជាបន្តបន្ទាប់)

- វដ្តពីការផ្តល់ដំបូន្មាន→ការរារាំង សម្រាប់រាល់របាំងត្រួតពិនិត្យថ្មី។
- `stale-allowlist`: រាល់ការលើកលែងត្រូវមានហេតុផលពន្យល់ + issue; ការលើកលែងហួសសម័យត្រូវបានរកឃើញ។
- `evidence-gate`: ការអះអាងថាជោគជ័យក្នុង PR តម្រូវឱ្យមានភស្តុតាង (តេស្ត ឬ living test)។
- **ការពិនិត្យ ROI ប្រចាំត្រីមាសសម្រាប់របាំងត្រួតពិនិត្យនីមួយៗ** (បញ្ឈប់/ដកថវិកាពីអ្វីដែលមិនផ្តល់ផលតបស្នង — ប្រឆាំងភាពនឿយហត់)។
- លើកកម្ពស់ Hard Rules របស់គម្រោងអ្នកទៅជារបាំងត្រួតពិនិត្យដែលអាចប្រតិបត្តិបាន។

### គោលការណ៍អនុវត្តគ្រប់ផ្នែក (មិនអាចចរចាបាន)

- **Ratchet មិនមែនតម្លៃដាច់ខាត។** ដាក់របាំងត្រួតពិនិត្យលើ _ការមិនថយចុះ_ មិនមែនលើតម្លៃថេរទេ (លើកលែងតែកម្រិតអប្បបរមាការពារតម្លៃសូន្យ)។
- **កម្រិតអប្បបរមាដាច់ខាត + ratchet រួមគ្នា។** កម្រិតអប្បបរមាការពារការដួលរលំ; ratchet ការពារការថយចុះយឺតៗ។
- **ការពារ Goodhart តាំងពីការរចនា។** រាល់ម៉ែត្រគោលដៅត្រូវមានតុល្យភាពប្រឆាំង (coverage ⇒ mutation + anti-masking; កម្រិតអប្បបរមាតាម module ដើម្បីបង្ខំឱ្យធ្វើតេស្តលើកូដពិបាក)។
- **រំលងដោយសមរម្យ។** ការខ្វះហេដ្ឋារចនាសម្ព័ន្ធមិនត្រូវរារាំងឡើយ; មានតែការថយចុះពិតប្រាកដប៉ុណ្ណោះដែលរារាំង។
- **`dedicatedGate` សម្រាប់ម៉ែត្រដែលចំណាយធនធានច្រើន។** ម៉ែត្រដែលត្រូវការ binary ខាងក្រៅ ទទួលបាន script ផ្ទាល់ខ្លួន (ជាមួយការរំលង) នៅក្រៅ ratchet កណ្តាលដែលដំណើរការសមកាលកម្ម។
- **ដាក់របាំងត្រួតពិនិត្យនៅកន្លែងដែល merge កើតឡើង។** កុំទុកចន្លោះរវាងរបាំងត្រួតពិនិត្យរហ័ស និងការ merge ពិតប្រាកដ (មេរៀនពីការបំបែក fast-gates)។
- **របាំងត្រួតពិនិត្យដែលរារាំងតិចតួច ប៉ុន្តែជ្រើសរើសបានល្អ។** Sonar/DORA៖ លក្ខខណ្ឌច្រើនពេក = ភាពនឿយហត់។ ផ្តល់អាទិភាពដល់ការផ្តល់ដំបូន្មាន + ratchet ជាជាងជញ្ជាំងនៃរបាំងត្រួតពិនិត្យដែលរារាំង។

## ផ្នែកទី 5 — ការកែលម្អដែលបានណែនាំ (តាមលំដាប់អាទិភាព និងអាចប្រើរួមគ្នាបាន)

**P0 — ROI ខ្ពស់បំផុត និងស្ទើរតែរួចរាល់**

1. **ការដំឡើងកម្រិតពិន្ទុ mutation ជាបន្តបន្ទាប់** (បន្ទាប់ពី Stryker ដំណើរការរាល់យប់លើកទី 1 ផ្ដល់តម្លៃ)។ ជាវិធានការសំខាន់ប្រឆាំងនឹង coverage-Goodhart; រួចរាល់ប្រហែល 90%។
2. **បិទចន្លោះខ្វះខាតនៃ fast-gates ដែលនៅសល់** — ដំឡើង production build របស់ `quality.yml` បន្ទាប់ពីរយៈពេល advisory មួយសប្ដាហ៍របស់វា ហើយបន្តផ្លាស់ទីការត្រួតពិនិត្យកំណត់បានជាក់លាក់ដែលអនុវត្តតែលើ release-PR ទៅក្នុងផ្លូវ PR→release។
3. **ការការពារ branch លើ `main`** (ការកំណត់របស់ម្ចាស់) — បង្កើន Scorecard និងបិទចន្លោះខ្វះខាត DSOMM។

**P1 — មានតម្លៃ** 4. **osv/oasdiff → blocking ជាមួយវិសាលភាពត្រឹមត្រូវ** — osv សម្រាប់តែ CRITICAL+fixable ប៉ុណ្ណោះ (ពីរជំហានដូច Trivy); oasdiff ទប់ស្កាត់ breaking-changes។ 5. **`require-tighten` → blocking** (ចុងបញ្ចប់នៃវដ្ដ) — រក្សាឱ្យបាននូវការកើនឡើងនៃម៉ែត្រ។ 6. **ការពិនិត្យ ROI/ពេលវេលាសម្រាប់ gate នីមួយៗ** នៅក្នុង `ci-summary` — ស្វែងរក និងដកចេញ gate ដែលយឺត/មានតម្លៃទាប។

**P2 — ផលតបស្នងថយចុះ** 7. **SLSA L3** — builder ដែល hermetic/អាចបង្កើតឡើងវិញបាន (GitHub SLSA generator) ប្រសិនបើអ្នកចង់ឡើងពី L2។ 8. **ការកំណត់រចនាសម្ព័ន្ធ CodeQL ដែលបាន commit + semgrep ដែលមានកំណែ** — ការគ្រប់គ្រង/លទ្ធភាពបង្កើតឡើងវិញកាន់តែប្រសើរ។ 9. **DAST smoke ក្នុងមួយ PR** — សំណុំរងរហ័សនៃ schemathesis/promptfoo លើ endpoint ដែលមានហានិភ័យខ្ពស់បំផុត (មិនមែនតែរាល់យប់ទេ)។ 10. **ផ្ទាំងព័ត៌មានភាពមិនស្ថិរភាព + ម៉ែត្រ DORA** — ធានាថា gate មិនកំពុងបន្ថយល្បឿន។

  modules ជាដើម) ប្រៀបធៀប **ទម្រង់** (`z.object` keys, registry entries) ជាមួយប្រភព canonical
  ហើយ **បរាជ័យនៅពេលមានភាពខុសគ្នា** (field ដែលបាត់/លើស)។ វាអាចរកឃើញការបាត់ field ចំនួន 40 ពី

  ចងចាំថាត្រូវសរសេរវា)។ ចំណាយតិច៖ import ទាំងពីរ ហើយប្រៀបធៀបភាពខុសគ្នារបស់ `Object.keys(shape)`។
