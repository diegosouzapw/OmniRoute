ការនាំចេញជាបន្តបន្ទាប់ និងជាបណ្ដើរៗនូវកំណត់ហេតុការហៅរបស់ OmniRoute ទៅកាន់ឃ្លាំងវិភាគខាងក្រៅ។

ផ្ទាំងផ្ទាំងគ្រប់គ្រង Logs រក្សាទុកប្រវត្តិសំណើនៅក្នុង SQLite (`call_logs`) ដែលត្រូវបានកំណត់ព្រំដែនដោយ
ការបង្វិលកំណត់ហេតុ និងរយៈពេលរក្សាទុក។ ការនាំចេញកំណត់ហេតុបញ្ជូនសំណុំកំណត់ត្រាដូចគ្នានេះចេញតាមកាលវិភាគ ដើម្បីឱ្យវាអាចរក្សាទុកបានយូរជាង
មូលដ្ឋានទិន្នន័យមូលដ្ឋាន និងអាចភ្ជាប់ជាមួយទិន្នន័យផ្សេងទៀត។ BigQuery គឺជាគោលដៅដំបូង; ខ្សែដំណើរការនេះជាបញ្ជីចុះឈ្មោះ ដូច្នេះអាចបន្ថែម
គោលដៅផ្សេងទៀតបាន។

## 1. របៀបដំណើរការ

```
call_logs (SQLite)
  → callLogExportSource.getCallLogsForExport(cursor, batchSize)
    → LogExportRecord[]  (សំណុំវាលរបស់ផ្ទាំង Logs)
      → destination client.send(batch)
        → advanceLogExportCursor(id, lastRowId, count)
```

- **កាលវិភាគ** — cron job មួយរបស់ `JobRegistry` ឈ្មោះ `log_export` ដែលមានលំនាំដើមជា `0 * * * *` (រៀងរាល់ម៉ោង,
  UTC)។ វាត្រូវបានចុះឈ្មោះនៅក្នុង `src/lib/initCloudSync.ts`; អាចកំណត់ជំនួសបានដោយប្រើ `OMNIROUTE_LOG_EXPORT_CRON`។
  នៅរាល់ tick វានឹងបង្ហូរទិន្នន័យទៅកាន់គោលដៅដែលបាន **បើកប្រើ** ទាំងអស់ តាមលំដាប់លំដោយ។
- **ទស្សន៍ទ្រនិច** — `call_logs.rowid` ដែល SQLite បង្កើតដោយស្វ័យប្រវត្តិ ត្រូវបានរក្សាទុកសម្រាប់គោលដៅនីមួយៗនៅក្នុង
  `log_export_destinations.cursor_row_id`។ `timestamp` មិនត្រូវបានប្រើជាទស្សន៍ទ្រនិចដោយចេតនា៖ អ្នកហៅ
  អាចផ្ដល់តម្លៃផ្ទាល់ខ្លួន ដូច្នេះសំណើយឺតមួយអាចត្រូវបានសរសេរបន្ទាប់ពីសំណើលឿនជាងដែលបានចាប់ផ្ដើម
  នៅពេលក្រោយ ហើយទស្សន៍ទ្រនិចផ្អែកលើពេលវេលានឹងរំលងវា។
- **ការបែងចែកជាបាច់** — `batch_size` ជួរដេកក្នុងមួយសំណើ (លំនាំដើម 500), `max_rows_per_run` ជួរដេកក្នុងមួយការដំណើរការ
  (លំនាំដើម 10000) ដើម្បីឱ្យទិន្នន័យកកស្ទះច្រើនត្រូវបានបង្ហូរឆ្លងកាត់ tick ច្រើន ជំនួសឱ្យការរាំងស្ទះក្នុងការដំណើរការតែមួយ។
- **ការបញ្ជូន** — ទស្សន៍ទ្រនិចផ្លាស់ទីទៅមុខតែបន្ទាប់ពី `send()` បានបញ្ចប់ប៉ុណ្ណោះ។ បាច់ដែលបរាជ័យទុកឱ្យ
  ទស្សន៍ទ្រនិចនៅទីតាំងដដែល ដូច្នេះជួរដេកដដែលនឹងត្រូវបានព្យាយាមម្ដងទៀតក្នុងការដំណើរការបន្ទាប់។ ការធានាគឺជា
  ការបញ្ជូនយ៉ាងហោចណាស់ម្ដង បូកនឹងការលុបទិន្នន័យស្ទួននៅខាងគោលដៅ មិនមែនការបញ្ជូនត្រឹមតែម្ដងពិតប្រាកដទេ៖ BigQuery កំណត់អត្តសញ្ញាណ
  ជួរដេកនីមួយៗដោយ id របស់កំណត់ហេតុការហៅ ដែលវាអនុវត្តតាមសមត្ថភាពល្អបំផុតនៅក្នុងចន្លោះពេលលុបទិន្នន័យស្ទួនរបស់វា។
- **យន្តការការពារការត្រួតស៊ីគ្នា** — cron tick និង `POST .../run` អាចដំណើរការក្នុងពេលតែមួយ។ គោលដៅ
  ដែលកំពុងត្រូវបានបង្ហូរទិន្នន័យរួចហើយ នឹងត្រូវរំលង ជំនួសឱ្យការបង្ហូរពីរដង (`skipped: true` នៅក្នុងលទ្ធផលដំណើរការ)
  ដូច្នេះការដំណើរការស្របគ្នាមិនអាចបញ្ជូនបាច់ឡើងវិញ ឬសរសេរទស្សន៍ទ្រនិចថយក្រោយបានទេ។
- **ការស្ដារឡើងវិញបន្ទាប់ពីការលុបសម្អាត** — ប្រសិនបើ `cursor_row_id` ឡើងខ្ពស់ជាង `MAX(rowid)` (តារាងទាំងមូលត្រូវបាន
  លុបសម្អាត ហើយ rowid បានចាប់ផ្ដើមឡើងវិញ) កម្មវិធីដំណើរការនឹងត្រឡប់ទៅ 0 វិញ ជំនួសឱ្យការមិនអាចមើលឃើញទិន្នន័យជារៀងរហូត។

### ទិន្នន័យបញ្ជូន (ប្រូម និងការបំពេញ)

តាមលំនាំដើម ការនាំចេញរួមបញ្ចូលតែវាលសង្ខេបដែលបញ្ជី Logs បង្ហាញប៉ុណ្ណោះ។ ការបើក
**នាំចេញប្រូម និងការឆ្លើយតប** (`includeBodies`) នឹងបញ្ជូនបន្ថែមនូវអ្វីដែលផ្ទាំង **ព័ត៌មានលម្អិត**
របស់ Logs បង្ហាញសម្រាប់ការហៅនីមួយៗ៖

| វាល                              | អ្វីដែលវាផ្ទុក                                                |
| -------------------------------- | ------------------------------------------------------------- |
| `request_body` / `response_body` | ទិន្នន័យការហៅតាមរបៀបដែលផ្ទាំងគ្រប់គ្រងបង្ហាញវា                |
| `pipeline_route_decision`        | គោលដៅ និងម៉ូដែលដែលកម្មវិធីកំណត់ផ្លូវបានជ្រើសរើស               |
| `pipeline_client_request`        | សំណើដើមទាំងស្រុងតាមដែលម៉ាស៊ីនភ្ញៀវបានផ្ញើវា                   |
| `pipeline_openai_request`        | បន្ទាប់ពីការបម្លែងទៅជាទម្រង់ OpenAI ខាងក្នុង                  |
| `pipeline_provider_request`      | តាមដែលបានផ្ញើទៅខាងលើជាក់ស្ដែង ក្នុងគ្រាមភាសារបស់អ្នកផ្ដល់សេវា |
| `pipeline_provider_response`     | ការឆ្លើយតបដើមពីខាងលើ                                          |
| `pipeline_client_response`       | អ្វីដែលត្រូវបានប្រគល់ត្រឡប់ទៅអ្នកហៅ                           |
| `pipeline_error`                 | ព័ត៌មានលម្អិតអំពីកំហុសកម្រិតខ្សែដំណើរការសម្រាប់ការហៅដែលបរាជ័យ |
| `bodies_truncated`               | True នៅពេលវាលណាមួយខាងលើដល់កម្រិត `maxBodyBytes`               |

នេះជាខ្លឹមសារប្រូម ដូច្នេះវា **បិទតាមលំនាំដើម** ហើយត្រូវបានកំណត់ដោយចេតនាជាជម្រើសសម្រាប់គោលដៅនីមួយៗ។
អ្វីដែលត្រូវបានបញ្ជូនគឺដូចគ្នានឹងអ្វីដែលផ្ទាំងគ្រប់គ្រងបង្ហាញ ពីព្រោះទាំងពីរអានតាមរយៈ `getCallLogById`៖ ទិន្នន័យ
ត្រូវបានសម្អាត PII និងលាក់ព័ត៌មានសម្ងាត់រួចហើយនៅពេលវាត្រូវបានសរសេរ ហើយការហៅដែលធ្វើឡើងដោយប្រើ

  អាចកាត់ចេញបាន ខណៈដែល filter លើ `status` តែមួយមិនអាចធ្វើបានទេ។
- **ការរក្សាទុក partition ជាជម្រើស** តាមរយៈ `partitionExpirationDays` (0 រក្សាទុកទាំងអស់) ដែលត្រូវបានអនុវត្ត
  នៅពេលតារាងត្រូវបានបង្កើត។

ការកំណត់ទាំងពីរត្រូវបានអនុវត្តនៅពេលបង្កើត។ តារាងដែលមានស្រាប់រក្សាប្លង់ដែលវាមានរួចហើយ ដូច្នេះ
សូមកំណត់ទិសដៅទៅកាន់ ID តារាងថ្មី ប្រសិនបើអ្នកចង់ប្រើការកំណត់ទាំងនេះ។

`tests/unit/log-export-bigquery.test.ts` ផ្ទៀងផ្ទាត់ថា mapper និង schema របស់តារាងនៅតែស្របគ្នា
ដូច្នេះ column ថ្មីរបស់ call-log មិនអាចត្រូវបានលុបចោលដោយស្ងាត់ស្ងៀមនៅពេលនាំចេញនោះទេ។

Batch ត្រូវបានបែងចែកជា chunk ដោយផ្អែកលើ **ទាំង** ចំនួន row និងចំនួន byte ដែលបាន serialize។ ចំនួន row តែមួយមុខគឺមិនគ្រប់គ្រាន់ទេ
នៅពេល payload ត្រូវបាននាំចេញ៖ row ចំនួន 500 ដែលផ្ទុក prompt អាចមានទំហំរាប់សិប megabyte ហើយ insertAll
បដិសេធ request ដែលមានទំហំលើសពី 10 MB។ Chunk ត្រូវបានបិទនៅពេលដល់ 500 row ឬ 9 MB ដោយយកលក្ខខណ្ឌណាដែលកើតឡើងមុន។

នោះគឺជាការផ្លាស់ប្តូរទាំងមូល៖ ការរក្សាទុកទិន្នន័យ, cron job, ស្រទាប់ REST, ការអ៊ិនគ្រីបព័ត៌មានសម្ងាត់ និង

- គោលដៅដែលទទួល URL ផ្តល់ដោយអ្នកប្រើ ត្រូវតែ validate វាតាមរយៈ

  ដូចគ្នានឹងរបៀបដែល webhook ធ្វើ។ BigQuery មិនត្រូវការវាទេ៖ host របស់វាជាតម្លៃថេរ។
