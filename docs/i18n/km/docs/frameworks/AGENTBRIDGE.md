**ទីតាំងផ្ទាំងគ្រប់គ្រង:** `/dashboard/tools/agent-bridge`

## §1 ទិដ្ឋភាពទូទៅ

### តើ AgentBridge ជាអ្វី?

នៅពេល IDE agent មួយ (ឧ. GitHub Copilot, Cursor, Claude Code) ធ្វើការហៅ API វានឹងភ្ជាប់ដោយផ្ទាល់ទៅកាន់អ្នកផ្តល់សេវា AI ខ្សែខាងលើ (OpenAI, Anthropic ជាដើម)។ AgentBridge ស្ទាក់ចាប់ការតភ្ជាប់នោះដោយថ្លានៅកម្រិត TLS — ដោយមិនតម្រូវឱ្យមានការផ្លាស់ប្តូរការកំណត់រចនាសម្ព័ន្ធណាមួយរបស់ agent — ហើយសរសេរសំណើឡើងវិញតាមរយៈ OmniRoute។

នេះមានន័យថា អ្នកអាច៖

- **ប្តូរទិស agent ណាមួយទៅកាន់អ្នកផ្តល់សេវាណាមួយ**: Copilot កំពុងទាក់ទងជាមួយ OpenAI មែនទេ? ប្តូរទិសវាទៅ Anthropic Claude, Gemini ឬអ្នកផ្តល់សេវាណាមួយក្នុងចំណោមអ្នកផ្តល់សេវា 352 របស់ OmniRoute។
- **អនុវត្តការផ្គូផ្គងម៉ូដែល**: `gemini-3-flash` → `claude-sonnet-4.7` ដោយថ្លានៅកម្រិត handler។
- **សង្កេតមើលចរាចរណ៍ទាំងអស់របស់ agent**: រាល់សំណើដែលត្រូវបានស្ទាក់ចាប់ត្រូវបានផ្សព្វផ្សាយទៅកាន់ [កម្មវិធីត្រួតពិនិត្យចរាចរណ៍](./TRAFFIC_INSPECTOR.md)។
- **អនុវត្តភាពធន់របស់ OmniRoute**: ការកំណត់ផ្លូវបែប combo, circuit breakers, fallbacks និងការតាមដានថ្លៃចំណាយ ក៏ដំណើរការសម្រាប់ចរាចរណ៍ IDE agent ផងដែរ។

```
    ▼
```

### 2.2 ម៉ាស៊ីនបម្រើ MITM (`src/mitm/server.cjs`)

ម៉ាស៊ីនបម្រើ MITM ស្នូលដំណើរការជាដំណើរការរង Node.js CJS (ដើម្បីជៀសវាងការសរសេរមូលដ្ឋានកូដ CJS ដែលមានស្រាប់ឡើងវិញ)។ វា៖

- ស្តាប់នៅលើច្រក 443 (ទាមទារសិទ្ធិពិសេស ឬ `authbind`/`setcap`)
- ទទួលរូង CONNECT ពីប្រព័ន្ធប្រតិបត្តិការ (តាមរយៈការបញ្ជូនបន្ត DNS របស់ `/etc/hosts`)
- បង្កើតវិញ្ញាបនបត្រ TLS សម្រាប់ SNI នីមួយៗ ដែលចុះហត្ថលេខាដោយ AgentBridge CA (`DATA_DIR/mitm/ca.crt`)
- កំណត់ភ្នាក់ងារគោលដៅតាមបឋមកថា Host តាមរយៈបញ្ជីឈ្មោះ `targets/index.ts`
- បញ្ជូនទៅស្រទាប់កម្មវិធីដោះស្រាយ TypeScript តាមរយៈ HTTP ទៅ `http://127.0.0.1:20128`

`TARGET_HOSTS` ត្រូវបានផ្ទុកពី `DATA_DIR/mitm/targets.json` (សរសេរដោយ `targets/index.ts` នៅពេលចាប់ផ្ដើម) ដែលអនុញ្ញាតឱ្យធ្វើបច្ចុប្បន្នភាពដោយថាមវន្តដោយមិនចាំបាច់ចាប់ផ្ដើមម៉ាស៊ីនបម្រើ CJS ឡើងវិញ។

> **គំរូ Root-CA (#6684)។** ការពិពណ៌នាខាងលើអំពីវិញ្ញាបនបត្រសម្រាប់ SNI នីមួយៗដែលចុះហត្ថលេខាដោយ CA
> គឺជាគំរូ root-CA ដែលរក្សាទុកជាប់លាប់ ដែលបានបន្ថែមនៅក្នុង #6684 (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs` ដោយប្រើឡើងវិញនូវគ្រីបតូ CA/leaf ដែលបាន
> បញ្ជាក់ប្រសិទ្ធភាពរួចហើយសម្រាប់ TPROXY នៅក្នុង `src/mitm/tproxy/dynamicCert.ts`) — វាជំនួស
> leaf ដែលចុះហត្ថលេខាដោយខ្លួនឯង និងឋិតិវន្តតែមួយចាស់ (`src/mitm/cert/generate.ts` ដែលនៅតែ
> កំណត់វិសាលភាពត្រឹមតែម៉ាស៊ីន antigravity) ដែលគូ `server.crt`/`server.key`
> ធម្មតានៅលើថាសបង្ហាញ។ **ឥរិយាបថនៃការផ្លាស់ប្ដូរ**៖ ការដំឡើងថ្មី (គ្មាន
> `server.crt` ពីមុន) ទទួលបានគំរូ root-CA ដោយស្វ័យប្រវត្តិ។ ការដំឡើងដែលបាន
> ទុកចិត្ត leaf ឋិតិវន្តចាស់រួចហើយ នឹងបន្តប្រើវា រហូតដល់ប្រតិបត្តិករកំណត់
> `MITM_ROOT_CA_ENABLED=true` ហើយចាប់ផ្ដើម bridge ឡើងវិញ (`src/mitm/cert/migration.ts`
> គឺជាអនុគមន៍សម្រេចចិត្តសុទ្ធ — MITM CA ដែលបានទុកចិត្ត និងអាចចុះហត្ថលេខា leaf សម្រាប់
> ម៉ាស៊ីន **ណាមួយ** មានអំណាចខ្លាំងជាង leaf ដែលមាន SAN ថេរចាស់យ៉ាងសំខាន់ ដូច្នេះ
> ការប្ដូរនេះមិនដែលកើតឡើងដោយស្ងាត់ស្ងៀមសម្រាប់ការដំឡើងដែលបានទុកចិត្តរួចហើយឡើយ)។ វិញ្ញាបនបត្រ CA ត្រូវបានដំឡើង
> ទៅក្នុងរន្ធឃ្លាំងទុកចិត្ត `omniroute-mitm.crt` ដូចគ្នាដែល leaf ចាស់បានប្រើ
> (`cert/install.ts::installCaCert`) — មិនចាំបាច់សម្អាតការទុកចិត្តពីរដងទេ។

### 2.3 មូលដ្ឋានកម្មវិធីដោះស្រាយ (`src/mitm/handlers/base.ts`)

កម្មវិធីដោះស្រាយភ្នាក់ងារទាំងអស់ពង្រីកពី `MitmHandlerBase`៖

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // កម្មវិធីជំនួយដែលបានការពារ៖ fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

កម្មវិធីដោះស្រាយនីមួយៗហៅ `hookBufferStart()` មុនពេលធ្វើប្រូកស៊ី និង `hookBufferUpdate()` នៅពេលបញ្ចប់។ វាទាំងនេះបញ្ចូលធាតុ `InterceptedRequest` ទៅក្នុង `globalTrafficBuffer` (សូមមើល [Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4)។

### 2.4 បញ្ជីឈ្មោះគោលដៅ (`src/mitm/targets/`)

ភ្នាក់ងារនីមួយៗមានឯកសារគោលដៅបែបប្រកាស៖

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

បញ្ជីឈ្មោះ (`targets/index.ts`) នាំចេញ `ALL_TARGETS` និងបង្កើត `DATA_DIR/mitm/targets.json` នៅពេលចាប់ផ្ដើម។

### 2.5 ការបញ្ជូនឆ្លងកាត់ និងបញ្ជីរំលង (`src/mitm/passthrough.ts`)

**បញ្ជីរំលង** (ត្រូវបានពិនិត្យមុនគេ និងមានអាទិភាពលើការត្រូវគ្នានឹងគោលដៅ)៖

- លំនាំលំនាំដើម៖ ម៉ាស៊ីនធនាគារ, `.gov.`, ក្រុមហ៊ុនផ្ដល់ OAuth/SSO (Okta, Auth0) ។ល។
- លំនាំរបស់អ្នកប្រើ៖ រក្សាទុកក្នុងតារាងមូលដ្ឋានទិន្នន័យ `agent_bridge_bypass`
- ម៉ាស៊ីនដែលត្រូវបានរំលង ទទួលបានរូង TCP ថ្លា — TLS **មិនត្រូវបានឌិគ្រីបឡើយ**

**លំនាំដើមនៃការបញ្ជូនឆ្លងកាត់** (មិនត្រូវគ្នានឹងគោលដៅ និងមិនស្ថិតក្នុងបញ្ជីរំលង)៖

- ក៏ទទួលបានរូង TCP ផងដែរ — ការតភ្ជាប់មិនត្រូវបានផ្ដាច់ឡើយ
- ការពារ AgentBridge មិនឱ្យរំខានដល់ចរាចរណ៍ HTTPS ទូទៅរបស់ប្រព័ន្ធ

លំដាប់អាទិភាពនៃការកំណត់ផ្លូវ៖

```
បញ្ជីរំលង → ត្រូវគ្នានឹងគោលដៅ → បញ្ជូនឆ្លងកាត់
```

### 2.6 វិញ្ញាបនបត្រ CA ខ្សែខាងលើ (`src/mitm/upstreamTrust.ts`)

សម្រាប់បរិស្ថានបណ្ដាញសាជីវកម្មដែលមាន CA ផ្ទាល់ខ្លួន៖

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

នៅពេលកំណត់ វាកំណត់រចនាសម្ព័ន្ធកម្មវិធីបញ្ជូនសកលរបស់ `undici` ជាមួយវិញ្ញាបនបត្រ CA បន្ថែម ដើម្បីអនុញ្ញាតឱ្យ AgentBridge អាចចូលដល់ក្រុមហ៊ុនផ្ដល់ខ្សែខាងលើតាមរយៈប្រូកស៊ីបញ្ចប់ TLS របស់សាជីវកម្ម។

### 2.7 ការបិទបាំងព័ត៌មានសម្ងាត់ (`src/mitm/maskSecrets.ts`)

កម្មវិធីស្កេន clean-room ឯករាជ្យ ត្រូវបានអនុវត្តទៅលើតួខ្លួនសំណើ និងបឋមកថាព័ត៌មានបញ្ជាក់អត្តសញ្ញាណ
**មុនពេល** ពួកវាចូលទៅក្នុងសតិបណ្ដោះអាសន្ន Traffic Inspector ឬកំណត់ហេតុណាមួយ។ វាធ្វើការឆ្លងកាត់ជាលីនេអ៊ែរតែមួយដង៖

- ថូខឹនដែលមានបុព្វបទ `sk-` / `ak-` / `pk-` (រចនាប័ទ្ម OpenAI/Anthropic)
- ព័ត៌មានបញ្ជាក់អត្តសញ្ញាណ RFC 6750 `Authorization: Bearer <token>` ដោយផ្ដល់អាទិភាពដល់ថូខឹនទាំងមូល
- ថូខឹនទូទៅវែងៗដែលមិនអាចស្គាល់ខ្លឹមសារ (≥40 តួអក្សរ) រួមទាំងទម្រង់ដែលមានចំណុច និងទម្រង់ដែលបានបំពេញបន្ថែម

`sanitizeHeaders()` បម្លែងឈ្មោះដែលរក្សាទុកទៅជាអក្សរតូច ភ្ជាប់តម្លៃអារេតាមរបៀបកំណត់ច្បាស់លាស់ លុប
បញ្ជីហាមឃាត់រួមសម្រាប់ hop-by-hop/framing (រួមទាំងការផ្ទៀងផ្ទាត់អត្តសញ្ញាណប្រូកស៊ី) កែសម្រួលលាក់ `cookie` និង
`set-cookie` ទាំងស្រុង ហើយផ្ទេរតម្លៃព័ត៌មានបញ្ជាក់អត្តសញ្ញាណទៅឱ្យកម្មវិធីស្កេន។

### 3.2 ទុកចិត្តវិញ្ញាបនបត្រ

វិញ្ញាបនបត្រ CA របស់ AgentBridge ត្រូវតែទទួលបានការទុកចិត្តពី OS មុនពេល IDE ទទួលយកការតភ្ជាប់ MITM។

**Linux (NSS — Chrome/Firefox)៖**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain)៖**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr)៖**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

ឬប្រើប៊ូតុង "ទុកចិត្តវិញ្ញាបនបត្រ" នៅក្នុងផ្ទាំងគ្រប់គ្រង (វាដំណើរការពាក្យបញ្ជាសមស្របសម្រាប់ OS របស់អ្នក ជាមួយនឹងការស្នើសុំ sudo ប្រសិនបើចាំបាច់)។

#### IDE ដែលផ្អែកលើ Electron មិនប្រើឃ្លាំងទុកចិត្តរបស់ OS ទេ (`NODE_EXTRA_CA_CERTS`)

IDE មួយចំនួន — ជាពិសេស **Antigravity IDE** និងកម្មវិធីផ្សេងទៀតដែលកែសម្រួលចេញពី Electron / VS Code — រួមបញ្ចូល
runtime Node.js ផ្ទាល់ខ្លួនរបស់ពួកវា ដែល **មិនពិនិត្យឃ្លាំងទុកចិត្តរបស់ OS** សម្រាប់ការតភ្ជាប់ចេញ
តាម `fetch`/HTTPS ទេ។ ការទុកចិត្ត CA នៅកម្រិត OS/NSS គឺគ្រប់គ្រាន់សម្រាប់ **backend** ដើមរបស់ IDE
(ឧ. ម៉ាស៊ីនមេភាសា Go ដែលប្រើបណ្ដុំ CA របស់ OS) ប៉ុន្តែ **frontend របស់ Electron** នឹង
នៅតែបរាជ័យ TLS — វាបង្ហាញក្នុងទម្រង់ជាកម្មវិធីត្រូវបាន _ចាកចេញពីគណនី_ ឬបង្ហាញ _"កំហុសការតភ្ជាប់"_
ទោះបីជាកំណត់ហេតុ MITM បង្ហាញថាការហៅ bootstrap របស់ backend ត្រឡប់ `200` ក៏ដោយ។ តម្រូវឱ្យមានពីរជំហាន
ហើយជំហានទាំងពីរសុទ្ធតែសំខាន់៖

1. ចង្អុល runtime ទៅកាន់ CA ដោយផ្ទាល់៖
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **បើកដំណើរការ IDE ពី shell នោះ។** ការចាប់ផ្ដើមវាពីរូបតំណាងលើ desktop / Dock / Start menu
   **មិន**ទទួលមរតក shell exports ទេ ហើយ `~/.config/environment.d/*.conf` នឹងអនុវត្តបានតែបន្ទាប់ពី
   ចូលប្រើ graphical session ថ្មីប៉ុណ្ណោះ។ ដំបូងត្រូវបិទ IDE ទាំងស្រុង — singleton lock របស់ Electron មានន័យថា ការចាប់ផ្ដើម
   លើកទីពីរគ្រាន់តែផ្ដោតទៅលើដំណើរការដែលមានស្រាប់ ហើយ environment ថ្មីត្រូវបានមិនអើពើ។

ជំហាន OS-trust + NSS ខាងលើនៅតែចាំបាច់ (network stack របស់ Chromium ដែលប្រើដោយលំហូរផ្ទៀងផ្ទាត់មួយចំនួន
អានឃ្លាំង NSS តាមអ្នកប្រើប្រាស់ និងមាន static pins ផ្ទាល់ខ្លួនសម្រាប់ `*.googleapis.com` ដែល CA
ដែលបានទុកចិត្តក្នុងមូលដ្ឋាននឹងលុបលើស)។ `NODE_EXTRA_CA_CERTS` គ្របដណ្ដប់លើផ្លូវ Node `fetch` បន្ថែមពីលើវា។

### 3.3 ការនាំផ្លូវ DNS

សម្រាប់ agent នីមួយៗដែលអ្នកចង់ស្ទាក់ចាប់ API host របស់វាត្រូវតែ resolve ទៅ `127.0.0.1`។ AgentBridge គ្រប់គ្រងធាតុ `/etc/hosts` ដោយស្វ័យប្រវត្តិ នៅពេលអ្នកបិទ/បើក DNS សម្រាប់ agent មួយនៅក្នុងកម្មវិធីជំនួយការដំឡើង។

ឧទាហរណ៍ធាតុ `/etc/hosts` សម្រាប់ GitHub Copilot៖

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.5 សេចក្ដីជូនដំណឹងអំពីហានិភ័យ

AgentBridge ស្ទាក់ចាប់ព័ត៌មានសម្ងាត់ (OAuth tokens, API keys) ដែល IDE ប្រើដើម្បីផ្ទៀងផ្ទាត់អត្តសញ្ញាណជាមួយក្រុមហ៊ុនផ្ដល់សេវាខាងដើម។ ព័ត៌មានទាំងនេះត្រូវបាន **បិទបាំងមុនពេលកត់ត្រា** (សូមមើល §2.7) ប៉ុន្តែស្រទាប់ MITM របស់ OmniRoute អាចមើលឃើញវា។ ការធ្វើឱ្យ agent នីមួយៗសកម្មជាលើកដំបូង នឹងបង្ហាញ modal ជូនដំណឹងអំពីហានិភ័យដែលអាចបិទបាន។

**បដាស្ថានភាពនៅសេសសល់៖** នៅពេលទំព័ររកឃើញស្ថានភាពដែលបន្សល់ទុកដោយការគាំង (ការក្លែងបន្លំ DNS / CA / ប្រូកស៊ីប្រព័ន្ធ) កាតនឹងបង្ហាញបដាពណ៌លឿងទុំ — _"សម័យដំណើរការមុនបានបន្សល់ទុកស្ថានភាពប្រព័ន្ធ (ការក្លែងបន្លំ DNS, CA ឬប្រូកស៊ីប្រព័ន្ធ)។ ដំណើរការ «ជួសជុល» ដើម្បីសម្អាតវា។"_ — ហើយរំលេចប៊ូតុង **ជួសជុល**។ `Repair` គឺជាសមមូលនៅស្រទាប់កម្មវិធីរបស់ flag `--cleanup` នៃ ProxyBridge (វាផ្ទេរភារកិច្ចទៅ `repairMitm()` ក្នុង `src/mitm/manager.ts`)។

> MITM root CA ត្រូវបានរក្សាឱ្យនៅដំឡើងឆ្លងកាត់ការបញ្ឈប់/ចាប់ផ្ដើម ដើម្បីជៀសវាង prompt របស់ sudo
> ម្តងហើយម្តងទៀត (មានឥរិយាបថដូចគ្នានឹង mitmproxy/Charles) ដូច្នេះការលុបវាគឺជាសកម្មភាព
> **លុប CA** ដោយច្បាស់លាស់ ជាជាងអ្វីដែលកើតឡើងដោយស្វ័យប្រវត្តិនៅពេលបញ្ឈប់។

### 3.7 ការនាំចូល/នាំចេញការកំណត់រចនាសម្ព័ន្ធចល័ត

AgentBridge អាចបម្លែងស្ថានភាពដែល **ប្រតិបត្តិករអាចកែសម្រួលបាន** ទៅជា blob JSON ដែលមានកំណែ ដើម្បីឱ្យការដំឡើងមួយអាចត្រូវបានចម្លងទៅកាន់ម៉ាស៊ីនផ្សេងៗ។ Serializer គឺ `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`) ដែលត្រូវបានផ្ទៀងផ្ទាត់ដោយ `AgentBridgeConfigSchema`។

ការនាំចេញរួមបញ្ចូលតែបីផ្នែកប៉ុណ្ណោះ (លំនាំដើមដែលមានស្រាប់ **មិន** ត្រូវបាននាំចេញដោយចេតនា ដូច្នេះការនាំចូលមិនចម្លងស្ទួន ឬបង្កជម្លោះជាមួយពួកវាឡើយ)៖

| វាល              | ប្រភព                                                             | កំណត់សម្គាល់                                                               |
| ---------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `bypassPatterns` | លំនាំរំលងដែលកំណត់ដោយអ្នកប្រើ (`agent_bridge_bypass`)              | លំនាំលំនាំដើម bank/gov/okta ត្រូវបានដកចេញ                                  |
| `customHosts`    | host ផ្ទាល់ខ្លួនរបស់ Traffic Inspector (`inspector_custom_hosts`) | នីមួយៗ៖ `{ host, kind: "llm"\|"app"\|"custom", label? }`                   |
| `agentMappings`  | ការផ្គូផ្គងម៉ូដែលតាម agent នីមួយៗ (`agent_bridge_mappings`)       | `{ [agentId]: [{ source, target }] }` សម្រាប់គ្រប់ agent ដែលមានការផ្គូផ្គង |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**ឥរិយាបថនៃការនាំចូល** (`POST /api/tools/agent-bridge/config`)៖ លំនាំរំលង និងការផ្គូផ្គងតាម agent នីមួយៗ **ជំនួសទាំងស្រុង**; host ផ្ទាល់ខ្លួនត្រូវបានបន្ថែមដោយ **មាន idempotence** (`INSERT OR IGNORE`)។ ការឆ្លើយតបរាយការណ៍ពីចំនួនធាតុនីមួយៗដែលត្រូវបានអនុវត្ត៖

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

អ្វីដែល **មិនមាន** នៅក្នុងការកំណត់រចនាសម្ព័ន្ធ៖ ស្ថានភាពដំណើរការរបស់ server, path របស់ cert, ស្ថានភាព DNS តាម agent នីមួយៗ, path របស់ upstream CA និងការកំណត់ TPROXY — ទាំងនេះគឺជាស្ថានភាពរបស់ host/runtime មិនមែនជាចំណូលចិត្តដែលអាចផ្ទេរបានទេ។

### ជំហាននៃកម្មវិធីជំនួយការរៀបចំ (សម្រាប់ agent នីមួយៗ)

កាត agent នីមួយៗមានកម្មវិធីជំនួយការរៀបចំ 3 ជំហាន៖

1. **ផ្ទៀងផ្ទាត់តម្រូវការជាមុន** — Server កំពុងដំណើរការ? Cert ត្រូវបានទុកចិត្ត? IDE បានដំឡើង (រកឃើញដោយស្វ័យប្រវត្តិ)?
2. **បើក DNS** — បន្ថែមធាតុទៅ `/etc/hosts` (តម្រូវឱ្យមាន sudo)។ បង្ហាញយ៉ាងច្បាស់ថាបន្ទាត់ណាខ្លះនឹងត្រូវបានបន្ថែម។
3. **ផ្គូផ្គង model** — តារាងផ្គូផ្គង model ជាជម្រើស។ អាចប្រើ Wildcard បាន។

```ts
export async function detectAgent(agentId: AgentId): Promise<DetectionResult>;
// ត្រឡប់៖ { installed: boolean, version?: string, path?: string }
```

ការរកឃើញប្រើផ្លូវតាមប្រព័ន្ធប្រតិបត្តិការ និងការត្រួតពិនិត្យ binary (ឧទាហរណ៍ `code --list-extensions | grep github.copilot` សម្រាប់ Copilot, `~/.config/antigravity/` សម្រាប់ Antigravity)។

### បញ្ជី bypass សម្រាប់ host ដែលមានលក្ខណៈរសើប

បញ្ជី bypass ធានាថា ស្ថាប័នហិរញ្ញវត្ថុ អ្នកផ្តល់សេវា OAuth/SSO និង host រសើបផ្សេងទៀត **មិនត្រូវបានឌិគ្រីបជាដាច់ខាត**។ ចរាចរណ៍ TLS របស់ពួកវាឆ្លងកាត់ជាផ្លូវរូង TCP ថ្លា — OmniRoute មិនដែលឃើញ plaintext ទេ។

លំនាំ bypass លំនាំដើមរួមមាន៖

- `*.bank.*`, `*.gov.*` (ហិរញ្ញវត្ថុ/រដ្ឋាភិបាល)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/អត្តសញ្ញាណ)
- `*.apple.com`, `*.icloud.com` (សេវាប្រព័ន្ធ Apple)

លំនាំ bypass ដែលអ្នកប្រើបន្ថែមត្រូវបានរក្សាទុកក្នុងតារាង `agent_bridge_bypass` និងមានអាទិភាពលើអ្វីៗទាំងអស់។

### ការបិទបាំងព័ត៌មានសម្ងាត់

`maskSecrets()` ពី `src/mitm/maskSecrets.ts` ត្រូវបានអនុវត្ត៖

- លើ body នៃ request នីមួយៗ មុន `TrafficBuffer.push()`
- លើ header នីមួយៗ មុនពេល logging ឬ broadcasting

លំនាំ៖ token ដែលមានបុព្វបទ `sk-`/`ak-`/`pk-`, token ប្រភេទ `Bearer` និង token ទូទៅដែលមាន ≥40 តួអក្សរ។

### CA cert របស់ upstream

នៅពេល `AGENTBRIDGE_UPSTREAM_CA_CERT` ត្រូវបានកំណត់ ឯកសារនឹងត្រូវបានអាននៅពេលចាប់ផ្ដើម។ ប្រសិនបើ path មាន ប៉ុន្តែមិនអាចអានឯកសារបាន AgentBridge នឹងកត់ត្រាកំហុសច្បាស់លាស់ ហើយបដិសេធមិនចាប់ផ្ដើម (ការពារការបរាជ័យ TLS ដោយស្ងាត់ស្ងៀមក្នុងបរិស្ថានសាជីវកម្ម)។

### ដែនកំណត់ដែលបានដឹង

- **Port 443 តម្រូវឱ្យមានសិទ្ធិពិសេស**៖ នៅលើ Linux, AgentBridge ត្រូវការ `setcap 'cap_net_bind_service=+ep'` លើ Node binary ឬដំណើរការតាមរយៈ `authbind`។ កម្មវិធីជំនួយការរៀបចំបង្ហាញការណែនាំជាក់លាក់តាមប្រព័ន្ធប្រតិបត្តិការ។
- **តម្រូវឱ្យចាប់ផ្ដើម IDE ឡើងវិញ**៖ បន្ទាប់ពីប្ដូរទិស DNS ត្រូវតែចាប់ផ្ដើម IDE ឡើងវិញ ដើម្បីឱ្យការដោះស្រាយ host ថ្មីមានប្រសិទ្ធភាព។
- **OAuth token ដែលបានសរសេរថេរក្នុងកូដ**៖ agent មួយចំនួន (Kiro, Antigravity) រក្សាទុក OAuth refresh token នៅក្នុងម៉ាស៊ីន។ ទាំងនេះមានភាពថ្លាសម្រាប់ AgentBridge — វាឃើញ Bearer token ក្នុង request នីមួយៗ ដែលត្រូវបានបិទបាំងមុនពេល logging។
- **Frontend ប្រភេទ Electron ត្រូវការ `NODE_EXTRA_CA_CERTS`**៖ IDE ដែល frontend របស់វាដំណើរការលើ Node/Electron runtime ដែលភ្ជាប់មកជាមួយ នឹងមិនអើពើ trust store របស់ OS/NSS ហើយត្រូវតែបើកដំណើរការពី shell ដែលបានកំណត់ `NODE_EXTRA_CA_CERTS` (មើល §3.2)។ រោគសញ្ញានៅពេលខ្វះ៖ backend របស់ IDE ផ្ទៀងផ្ទាត់អត្តសញ្ញាណបាន (MITM បង្ហាញ `200`) ប៉ុន្តែ UI នៅតែស្ថិតក្នុងស្ថានភាពមិនបានចូល។
- **ការដំឡើង IDE ដូចគ្នាច្រើនគឺឯករាជ្យពីគ្នា**៖ ការដំឡើងកម្រិតប្រព័ន្ធ (ឧទាហរណ៍ `/usr/share/antigravity/antigravity`) និងការដំឡើង "Full" ក្នុងថតអ្នកប្រើ (ឧទាហរណ៍ `~/AntigravityIDE_Full/antigravity-ide`) គឺជាដំណើរការដាច់ដោយឡែក ដែលមាន runtime ផ្ទាល់ខ្លួន — នីមួយៗត្រូវតែចាប់ផ្ដើមឡើងវិញជាមួយ CA ដែលបានបញ្ចូល។ កំណត់ថាមួយណាកំពុងដំណើរការ ដោយពិនិត្យ binary path របស់វា មុនពេលចាប់ផ្ដើមឡើងវិញ។
- **អត្តសញ្ញាណត្រូវបានកំណត់ដោយ system prompt របស់ agent មិនមែនដោយ model ដែលត្រូវបានបញ្ជូនទិសទេ**៖ នៅពេលអ្នកផ្គូផ្គង model របស់ agent ទៅអ្នកផ្តល់សេវាផ្សេង ចម្លើយនៅតែអះអាងពីអត្តសញ្ញាណដើមរបស់ agent (ឧទាហរណ៍ Antigravity ឆ្លើយថា "ខ្ញុំដំណើរការដោយ Gemini") ពីព្រោះ IDE បញ្ចូលព័ត៌មាននោះទៅក្នុង system prompt។ បញ្ជាក់ backend ពិតប្រាកដក្នុង `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`) មិនមែនដោយសួរ model ថាវាជានរណានោះទេ។

## §6 ការដោះស្រាយបញ្ហា

### ជម្លោះច្រក 443

ប្រសិនបើដំណើរការផ្សេងទៀតកំពុងស្តាប់នៅលើច្រក 443 រួចហើយ (ម៉ាស៊ីនបម្រើវេប VPN ជាដើម)៖

```bash
lsof -i :443          # ស្វែងរកដំណើរការ
sudo fuser -k 443/tcp  # បង្ខំឱ្យបញ្ឈប់ (ប្រើដោយប្រុងប្រយ័ត្ន)
```

ជាជម្រើស អ្នកអាចកំណត់រចនាសម្ព័ន្ធច្រកដែលមិនត្រូវការសិទ្ធិពិសេសនៅក្នុងការកំណត់ AgentBridge ហើយដំឡើងច្បាប់បញ្ជូនបន្ត `iptables` / `pf`។

### វិញ្ញាបនបត្រមិនត្រូវបានទុកចិត្ត

ប្រសិនបើ IDE បង្ហាញកំហុស TLS បន្ទាប់ពីចាប់ផ្ដើម AgentBridge៖

1. ផ្ទៀងផ្ទាត់ថាវិញ្ញាបនបត្រត្រូវបានដំឡើង៖ `security find-certificate -c "OmniRoute AgentBridge"` (macOS) ឬ `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. កម្មវិធីមួយចំនួនរក្សាទុកឃ្លាំងទុកចិត្តផ្ទាល់ខ្លួន (Firefox, Chrome នៅលើ Linux)។ ដំណើរការ "Trust Cert" ម្ដងទៀត ហើយពិនិត្យឃ្លាំងវិញ្ញាបនបត្រជាក់លាក់សម្រាប់ NSS/Firefox។
3. ចាប់ផ្ដើម IDE ឡើងវិញបន្ទាប់ពីកំណត់ការទុកចិត្ត — សម័យ TLS ដែលកំពុងដំណើរការប្រើស្ថានភាពទុកចិត្តចាស់។

### IDE បានចេញពីគណនី / "កំហុសការតភ្ជាប់" ទោះបីជា CA ត្រូវបានទុកចិត្តក៏ដោយ

រោគសញ្ញា៖ បន្ទាប់ពីបញ្ជូន DNS បន្ត និងកំណត់ឱ្យទុកចិត្ត CA រួច IDE ដែលផ្អែកលើ Electron (ឧ. Antigravity)
បើកឡើងក្នុងស្ថានភាព **បានចេញពីគណនី** ឬបង្ហាញកំហុសការផ្ទៀងផ្ទាត់/ការតភ្ជាប់ ប៉ុន្តែកំណត់ហេតុ MITM បង្ហាញថា
ការហៅពេលចាប់ផ្ដើម (`loadCodeAssist`, `fetchAvailableModels`, …) ត្រឡប់ `200`។

មូលហេតុ៖ **Node/Electron runtime ដែលភ្ជាប់មកជាមួយ IDE មិនអើពើឃ្លាំងទុកចិត្តរបស់ប្រព័ន្ធប្រតិបត្តិការ**។ កម្មវិធីផ្នែកខាងក្រោយ
ដើម (ម៉ាស៊ីនបម្រើភាសា Go) ទុកចិត្ត OS CA និងផ្ទៀងផ្ទាត់បាន ប៉ុន្តែផ្នែកខាងមុខ Electron
មិនទុកចិត្តទេ — ដូច្នេះ UI គិតថាវាស្ថិតក្រៅបណ្ដាញ។

ដំណោះស្រាយ (ទាំងពីរជំហាន)៖ export `NODE_EXTRA_CA_CERTS=<ca.crt>` **ហើយបើក IDE ឡើងវិញពី
shell នោះ** មិនមែនពីរូបតំណាងលើផ្ទៃតុទេ។ ដំបូងត្រូវបិទ IDE ទាំងស្រុង — សោ singleton របស់ Electron មានន័យថា
ការបើកលើកទីពីរគ្រាន់តែផ្ដោតទៅលើដំណើរការដែលមានស្រាប់ ហើយបរិស្ថានថ្មីត្រូវបានមិនអើពើ។ សូមមើល §3.2។
នេះស្រដៀងនឹងរបាយការណ៍ upstream ដែលនៅតែបើក ដែលក្នុងនោះ agent ឯករាជ្យដំណើរការតាមរយៈ MITM ប៉ុន្តែកំណែ IDE
បរាជ័យក្រោមការរៀបចំដូចគ្នា។

### DNS មិនបានផ្សព្វផ្សាយ

ពិនិត្យថា `/etc/hosts` ត្រូវបានធ្វើបច្ចុប្បន្នភាព៖

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

សម្អាតឃ្លាំងសម្ងាត់ DNS៖

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### រកមិនឃើញ IDE

ការរកឃើញដោយស្វ័យប្រវត្តិប្រើទីតាំងដំឡើងទូទៅ។ ប្រសិនបើការរកឃើញបរាជ័យ ប៉ុន្តែ IDE ត្រូវបានដំឡើង៖

- ពិនិត្យថាតើឯកសារប្រតិបត្តិ IDE ស្ថិតនៅទីតាំងមិនស្តង់ដារឬអត់
- អ្នកជំនួយការរៀបចំនៅតែដំណើរការ — ការរកឃើញបរាជ័យគ្រាន់តែមានន័យថា ផ្លាកសញ្ញានឹងមិនបង្ហាញផ្លូវដំឡើងទេ

### កំហុស Handler (ការទាញយកពី upstream បរាជ័យ)

ប្រសិនបើ AgentBridge ស្ទាក់ចាប់បាន ប៉ុន្តែសំណើទាំងអស់បរាជ័យ៖

1. ផ្ទៀងផ្ទាត់ថាយ៉ាងហោចណាស់មានអ្នកផ្ដល់សេវាមួយត្រូវបានភ្ជាប់នៅ `/dashboard/providers`
2. ពិនិត្យកំណត់ហេតុម៉ាស៊ីនបម្រើ OmniRoute៖ `APP_LOG_LEVEL=debug` នៅក្នុង `.env`
3. ផ្ទៀងផ្ទាត់ថា `OMNIROUTE_BASE_URL` ចង្អុលទៅចំណុចបញ្ចប់ router ត្រឹមត្រូវ (លំនាំដើម៖ `http://127.0.0.1:20128`)

## §8 ផែនទីបង្ហាញផ្លូវ

### ការស៊ើបអង្កេត Trae

Trae គឺជាជំនួយការសរសេរកូដ AI ថ្មីមួយ។ មុនពេលអនុវត្ត handler៖

1. កំណត់អត្តសញ្ញាណ binary/extension នៅក្នុង marketplace របស់ VS Code / JetBrains ឬជាកម្មវិធីឯករាជ្យ
2. ចាប់យក traffic ដោយប្រើ mitmproxy ដើម្បីស្វែងរក API host និងទម្រង់ endpoint
3. កំណត់យន្តការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ
4. វាយតម្លៃថាតើត្រូវបន្ត ឬមិនបន្ត ដោយផ្អែកលើ TOS និងលទ្ធភាពស្វែងរក API

រហូតដល់ការស៊ើបអង្កេតត្រូវបានបញ្ចប់ កាត Trae នៅក្នុង dashboard នឹងបង្ហាញស្លាក "កំពុងស៊ើបអង្កេត" ជាមួយតំណ "រាយការណ៍ពីលទ្ធភាពអនុវត្តបាន"។ handler stub នៅ `src/mitm/handlers/trae.ts` បញ្ចេញកំហុសដែលមានរចនាសម្ព័ន្ធ `មិនទាន់ត្រូវបានអនុវត្ត`។

### ភ្នាក់ងារក្នុងបញ្ជីការងាររង់ចាំ (តម្រូវឱ្យមាន MITM — មិនគាំទ្រ base URL ផ្ទាល់ខ្លួន)
