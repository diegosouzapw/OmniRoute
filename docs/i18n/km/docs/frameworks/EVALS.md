## គោលគំនិត

### សំណុំតេស្ត

សំណុំតេស្តគឺជាបណ្តុំនៃករណីតេស្តដែលមានឈ្មោះ និងមាន `description` ព្រមទាំងករណីមួយ ឬច្រើន។ សំណុំតេស្តមកពីប្រភពពីរ៖

| ប្រភព      | កន្លែងកំណត់                                       | អាចកែប្រែពេលកំពុងដំណើរការបានទេ? |
| ---------- | ------------------------------------------------- | ------------------------------- |
| `built-in` | ចុះបញ្ជីតាមរយៈ `registerSuite()` នៅពេលចាប់ផ្តើម   | ទេ (កំណត់ក្នុងកូដ)              |
| `custom`   | រក្សាទុកក្នុង SQLite `eval_suites` + `eval_cases` | បាទ/ចាស (តាម API/UI)            |

សំណុំតេស្តភ្ជាប់មកជាមួយបច្ចុប្បន្ន (សូមមើល `src/lib/evals/evalRunner.ts`)៖

- `golden-set` — ករណីគោល 10 ដែលគ្របដណ្តប់លើការស្វាគមន៍/គណិតវិទ្យា/ការបកប្រែ/សុវត្ថិភាព
- `coding-proficiency` — Python/JS/SQL/TS/ការរកឃើញកំហុស
- `reasoning-logic` — តក្កវិជ្ជាសន្និដ្ឋាន លំហាត់ពាក្យ និងការសម្គាល់លំនាំ
- `multilingual` — ការបកប្រែ និងការកំណត់អត្តសញ្ញាណភាសា
- `safety-guardrails` — PII, jailbreak, ការបដិសេធ និងការយល់ដឹងអំពីភាពលម្អៀង
- `instruction-following` — តែ JSON បញ្ជីមានលេខរៀង និងកម្រិតកំណត់ភាសា
- `codex-comparison` — កិច្ចការសរសេរកូដប្រៀបធៀបគ្នាដោយផ្ទាល់ ដែលរៀបចំសម្រាប់របៀបប្រៀបធៀប

## លក្ខណៈវិនិច្ឆ័យនៃការដាក់ពិន្ទុ

បានអនុវត្តនៅក្នុង `evaluateCase()` (evalRunner.ts)៖

| យុទ្ធសាស្ត្រ | ជាប់នៅពេល…                                                                               |
| ------------ | ---------------------------------------------------------------------------------------- |
| `exact`      | `actualOutput === expected.value`                                                        |
| `contains`   | `actualOutput.toLowerCase().includes(expected.value.toLowerCase())`                      |
| `regex`      | `new RegExp(expected.value).test(actualOutput)` មានតម្លៃជា truthy                        |
| `custom`     | `expected.fn(actualOutput, evalCase)` ត្រឡប់តម្លៃជា truthy (សម្រាប់តែ built-in ប៉ុណ្ណោះ) |

**ចំណាំ៖** ការដាក់ពិន្ទុតាមអនុគមន៍ផ្ទាល់ខ្លួនត្រូវបានទុកសម្រាប់ suite ដែលកំណត់ដោយកូដ
(built-in) ពីព្រោះអនុគមន៍មិនអាចត្រូវបាន serialized តាមរយៈ API បានទេ។
`evalCaseBuilderSchema` ទទួលយកតែ `contains | exact | regex` សម្រាប់
suite ដែលបង្កើតដោយអ្នកប្រើប្រាស់។

បច្ចុប្បន្នមិនមាន LLM-as-judge ឬឧបករណ៍ដាក់ពិន្ទុភាពស្រដៀងគ្នាដែលផ្អែកលើ embedding ទេ — វាអាចជា
ចំណុចពង្រីកដ៏សមស្របមួយនៅក្នុង `evaluateCase()`។

## គ្រោងការណ៍មូលដ្ឋានទិន្នន័យ

មានតារាងបី (migrations `030_create_eval_runs.sql` និង
`031_create_eval_suites.sql`)៖

| តារាង         | គោលបំណង                                                                                                                            |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `eval_suites` | Metadata របស់ suite ផ្ទាល់ខ្លួន (`id`, `name`, `description`)                                                                      |
| `eval_cases`  | ករណីតាម suite — `input_json`, `expected_*`, `tags_json`                                                                            |
| `eval_runs`   | ប្រវត្តិនៃការដំណើរការ — `pass_rate`, `total`, `passed`, `failed`, `avg_latency_ms`, `summary_json`, `results_json`, `outputs_json` |

Suite ដែលជា built-in **មិន** ត្រូវបានរក្សាទុកក្នុង DB ទេ។ ពួកវាស្ថិតនៅក្នុងអង្គចងចាំ ហើយត្រូវបាន
ចុះឈ្មោះឡើងវិញរាល់ពេលដែល `evalRunner.ts` ត្រូវបាន import។

### ការដំណើរការ suite មួយ

```bash
curl -X POST http://localhost:20128/api/evals \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "suiteId": "golden-set",
    "target": { "type": "combo", "id": "my-combo" },
    "apiKeyId": "optional-api-key-uuid"
  }'
```

វាលជាជម្រើស៖

- `outputs` — `Record<caseId, string>` នៃ output ដែលបានគណនាជាមុន។ នៅពេលផ្តល់វា
  runner នឹង **រំលង dispatch** ហើយដាក់ពិន្ទុតែ output ដែលបាន cache ប៉ុណ្ណោះ (មានប្រយោជន៍សម្រាប់
  ការវាយតម្លៃ offline)។
- `compareTarget` — គោលដៅទីពីរសម្រាប់ដំណើរការស្របគ្នា; ការដំណើរការទាំងពីរចែករំលែក
  `runGroupId` ដែលបានបង្កើត សម្រាប់ការមើលប្រៀបធៀបដោយផ្ទាល់។
- `apiKeyId` — API key ខាងក្នុងដែលប្រើដើម្បីផ្ទៀងផ្ទាត់ការហៅ
  `/v1/chat/completions` ដែលបាន dispatch។ តម្រូវឱ្យមាននៅពេលបើក `REQUIRE_API_KEY`។

### ការបង្កើត suite ផ្ទាល់ខ្លួន

```bash
curl -X POST http://localhost:20128/api/evals/suites \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Production smoke",
    "description": "Quick sanity check before deploy",
    "cases": [
      {
        "name": "JSON shape",
        "model": "gpt-4o",
        "input": { "messages": [{ "role": "user", "content": "Reply with {\"ok\": true}" }] },
        "expected": { "strategy": "regex", "value": "\"ok\"\\s*:\\s*true" }
      }
    ]
  }'
```

## បំពង់ដំណើរការបញ្ជូន

`runEvalSuiteAgainstTarget()` (`src/lib/evals/runtime.ts`):

1. ដោះស្រាយសំណុំតេស្ត (ដែលមានស្រាប់ ឬផ្ទាល់ខ្លួន)។
2. សម្រាប់ករណីនីមួយៗ បង្កើត `Request` ទៅកាន់ `/v1/chat/completions` ជាមួយ
   `messages` របស់ករណីនោះ `model` ដែលបានដោះស្រាយ `stream: false` និង `max_tokens: 512`
   (ឬតម្លៃជំនួសរបស់ករណី)។
3. ហៅកម្មវិធីដោះស្រាយការជជែកដោយផ្ទាល់ (ក្នុងដំណើរការតែមួយ — មិនមានការឆ្លងកាត់ HTTP បន្ថែម)។
4. កត់ត្រារយៈពេលឆ្លើយតប និងស្រង់អត្ថបទចេញពី `choices[0].message.content`
   ឬ payload `output[]` របស់ Responses-API។
5. ដាក់ពិន្ទុលទ្ធផលទាំងអស់តាមរយៈ `runSuite()` បន្ទាប់មករក្សាទុកតាមរយៈ `saveEvalRun()`។

ករណីតេស្តដំណើរការ **តាមលំដាប់លំដោយ**។ បច្ចុប្បន្នមិនមានទង់សម្រាប់ដំណើរការស្របគ្នាទេ។

## ទំនាក់ទំនងជាមួយ Auto-Assessment RFC

ប្រព័ន្ធរងសម្រាប់ការវាយតម្លៃដាច់ដោយឡែក និងមានវិសាលភាពចង្អៀតជាងនេះ ស្ថិតនៅ `src/domain/assessment/`
(សូមមើលផងដែរ [AUTO-COMBO.md](../routing/AUTO-COMBO.md) សម្រាប់ម៉ាស៊ីនដាក់ពិន្ទុផ្ទាល់)។
ប្រព័ន្ធរងនោះផ្តោតលើម៉ាស៊ីន Auto Combo — ដោយដាក់ពិន្ទុដោយស្វ័យប្រវត្តិដល់អ្នកផ្តល់សេវា និង
ម៉ូដែល ដើម្បីឱ្យបន្សំអាចស្តារខ្លួនឯងបាន នៅពេលប្រភពខាងលើបរាជ័យ។ វាប្រើកម្មវិធីដំណើរការ
កម្មវិធីចាត់ប្រភេទ និងតក្កវិជ្ជាដាក់ពិន្ទុផ្ទាល់ខ្លួនរបស់វា។

ក្របខណ្ឌ Evals ដែលបានចងក្រងជាឯកសារនៅទីនេះ គឺជា **ផ្ទៃសាកល្បងទូទៅដែលមាន
វិសាលភាពទូលំទូលាយជាង**។ គួរប្រើវាសម្រាប់សំណុំតេស្ត regression ទូទៅ ការប្រៀបធៀប A/B
និងការធ្វើ smoke test តាម release នីមួយៗ។ ប្រើប្រព័ន្ធរង Auto-Assessment នៅពេលអ្នកត្រូវការ
ឱ្យស្ថានភាពរបស់អ្នកផ្តល់សេវាតាមពេលវេលាជាក់ស្តែង មានឥទ្ធិពលលើការសម្រេចចិត្តបញ្ជូនផ្លូវ។

## ការរួមបញ្ចូល CI

បច្ចុប្បន្នមិនមានស្គ្រីប npm `eval:ci` ជាក់លាក់ទេ។ មានពីរវិធី ប្រសិនបើអ្នកចង់
កំណត់ឱ្យការចេញផ្សាយអាស្រ័យលើលទ្ធផលវាយតម្លៃ៖

- **វិធី HTTP**៖ ដំណើរការ server ផ្ញើសំណើទៅ `POST /api/evals` ជាមួយ
  `suiteId` + `target` ដែលបានដឹង ហើយផ្ទៀងផ្ទាត់ថា `runs[].summary.passRate >= N` ក្នុង
  response។
- **វិធីក្នុងដំណើរការ**៖ import `runEvalSuiteAgainstTarget()` ពី
  `@/lib/evals/runtime` ក្នុងស្គ្រីបមួយ ដំណើរការជាមួយ DB សាកល្បង ហើយពិនិត្យ
  `PersistedEvalRun.summary` ដែលបានបញ្ជូនត្រឡប់មកវិញ។

តេស្តដែលគ្របដណ្តប់ route និងប្រវត្តិ ស្ថិតនៅ
`tests/unit/evals-route.test.ts` និង `tests/unit/evals-history.test.ts`។

## ចំណុចសម្រាប់ពង្រីក

ការផ្លាស់ប្តូរទូទៅ និងទីតាំងដែលត្រូវអនុវត្ត៖

- **យុទ្ធសាស្ត្រដាក់ពិន្ទុថ្មី** — ពង្រីកប្លុក `switch (evalCase.expected.strategy)`
  ក្នុង `evaluateCase()` (`evalRunner.ts`) និងពង្រីក `EvalCaseStrategy` ក្នុង
  `src/lib/db/evals.ts` ព្រមទាំង `evalCaseBuilderSchema` ក្នុង `schemas.ts`។
- **សំណុំតេស្តដែលមានស្រាប់ថ្មី** — កំណត់ suite object ហើយហៅ `registerSuite()` នៅ
  ផ្នែកខាងក្រោមនៃ `evalRunner.ts`។ វានឹងត្រូវបានរកឃើញដោយស្វ័យប្រវត្តិដោយ `listSuites()`។
- **ដំណើរការស្របគ្នា** — ប្តូរ loop `for` ដែលដំណើរការតាមលំដាប់លំដោយក្នុង
  `runEvalSuiteAgainstTarget()` ទៅជា `Promise.all` ដែលមានដែនកំណត់ (បច្ចុប្បន្នមិនមាន
  ការគ្រប់គ្រងការដំណើរការស្របគ្នាទេ)។
- **ករណី stream/tool-call** — បច្ចុប្បន្នកម្មវិធីដំណើរការបង្ខំឱ្យប្រើ `stream: false`។
  ការវាយតម្លៃដែលគាំទ្រ streaming ឬ tool នឹងតម្រូវឱ្យមានការផ្លាស់ប្តូរក្នុង `runtime.ts`
  (កត់ត្រា និងប្រមូលផ្តុំផ្នែក SSE មុនពេលដាក់ពិន្ទុ)។
