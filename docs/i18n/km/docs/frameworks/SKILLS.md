## Agent Skills និង Omni Skills

OmniRoute មានប្រព័ន្ធ skill ពីរដាច់ដោយឡែកពីគ្នា ប៉ុន្តែបំពេញបន្ថែមគ្នា៖

| ទិដ្ឋភាព         | **Omni Skills** (ឯកសារនេះ)                                      | **Agent Skills**                                                                             |
| :--------------- | :-------------------------------------------------------------- | :------------------------------------------------------------------------------------------- |
| គោលបំណង          | ការបញ្ចូលឧបករណ៍ LLM + ការប្រតិបត្តិក្នុងបរិស្ថានដាច់ដោយឡែក      | កាតាឡុក SKILL.md សម្រាប់ឱ្យ agent ខាងក្រៅស្វែងរក និងប្រើប្រាស់                               |
| ប្រភពយោងផ្លូវការ | `src/lib/skills/` + ទីផ្សារ                                     | `src/lib/agentSkills/` + ថត `skills/`                                                        |
| របៀបដំណើរការ     | បញ្ចូលទៅក្នុងសំណើចេញ និងប្រតិបត្តិនៅពេលមានព្រឹត្តិការណ៍ហៅឧបករណ៍ | កាតាឡុក markdown ឋិតិវន្ត + endpoint សម្រាប់ការស្វែងរកតាម REST/MCP/A2A                       |
| អ្នកប្រើប្រាស់   | OmniRoute ខ្លួនឯង (ការកំណត់ផ្លូវបញ្ចូលគ្នា និងការហៅ LLM ចូល)    | agent ខាងក្រៅ កម្មវិធីភ្ញៀវ MCP និងកម្មវិធីសម្របសម្រួល A2A                                   |
| ចំនួន            | អថេរ (កំណត់ដោយទីផ្សារ)                                          | ធាតុកាតាឡុក 45 (23 API + 21 CLI + 1 ការកំណត់រចនាសម្ព័ន្ធ)                                    |
| ទម្រង់           | `SkillDefinition` ដែលមាន schema ឧបករណ៍ + handler                | frontmatter របស់ `SKILL.md` + ខ្លឹមសារ markdown                                              |
| ការស្វែងរក       | REST `/api/skills/*` + ឧបករណ៍ MCP `omniroute_skills_*`          | REST `/api/agent-skills/*` + ឧបករណ៍ MCP `omniroute_agent_skills_*` + A2A `list-capabilities` |

**Omni Skills** គឺជាម៉ាស៊ីនប្រតិបត្តិ — វាកំណត់អ្វីដែល OmniRoute _អាចធ្វើបាន_ នៅពេល LLM ហៅឧបករណ៍មួយ។

**Agent Skills** គឺជាកាតាឡុកឯកសារ — វាពន្យល់ដល់ agent ខាងក្រៅអំពី _របៀបប្រើ_ REST API និង CLI របស់ OmniRoute ដោយប្រើឯកសារ SKILL.md ដែលមានរចនាសម្ព័ន្ធ និងអាចបញ្ចូលដោយផ្ទាល់ទៅក្នុង prompt របស់ agent។

សម្រាប់កាតាឡុក Agent Skills កម្មវិធីបង្កើត ឧបករណ៍ MCP និង skill A2A សូមមើល [docs/frameworks/AGENT-SKILLS.md](./AGENT-SKILLS.md)។

## គោលគំនិត

### ប្រភព Skill

ប្រភព skill ចំនួនបីប្រើប្រាស់ registry តែមួយរួមគ្នា៖

1. **Skills ដែលមានស្រាប់** (`src/lib/skills/builtins.ts`) — ភ្ជាប់មកជាមួយ OmniRoute។ គ្របដណ្តប់ករណីប្រើប្រាស់ទូទៅ៖
   - `file_read`, `file_write` — workspace ដាច់ដោយឡែកតាម API key នីមួយៗ នៅក្រោម `<DATA_DIR>/skills/workspaces/<hashed-key>/`
   - `http_request` — HTTP ចេញតាមរយៈ `safeOutboundFetch` ដោយប្រើ `guard: "public-only"`
   - `web_search` — អ្នកផ្តល់សេវាស្វែងរកដែលអាចប្តូរបាន ជាមួយ caching (`executeWebSearch`)
   - `eval_code` — ការប្រតិបត្តិ `node` ឬ `python` ដែលដាក់ក្នុងបរិស្ថានដាច់ដោយឡែក Docker
   - `execute_command` — ពាក្យបញ្ជា shell ដែលដាក់ក្នុងបរិស្ថានដាច់ដោយឡែក Docker
   - `browser` — គ្រោងការងារដែលគាំទ្រដោយ Playwright និងត្រូវបានបិទតាមលំនាំដើម (`builtin/browser.ts`)
2. **SkillsMP** (ទីផ្សារ OmniRoute) — ទាញយកពី `https://skillsmp.com/api/v1/skills/search`។ តម្រូវឱ្យមាន `skillsmpApiKey` ក្នុងការកំណត់។
3. **SkillsSH** (កាតាឡុកសហគមន៍ `skills.sh`) — ទាញយកពី `https://skills.sh/api/search`។ មិនត្រូវការការផ្ទៀងផ្ទាត់ទេ; ខ្លឹមសារ SKILL.md ត្រូវបានទាញយកពី GitHub raw។

"អ្នកផ្តល់សេវាសកម្ម" តែមួយគ្រប់គ្រងថាកាតាឡុកណាដែល dashboard ប្រើសម្រាប់ដំឡើង (`src/lib/skills/providerSettings.ts`)។ ប្តូរវានៅក្រោម **ការកំណត់ → អង្គចងចាំ និង Skills**។ លំនាំដើម៖ `skillsmp`។

### អត្តសញ្ញាណ Skill

Skills ត្រូវបានកំណត់ដោយ `name@version` នៅក្នុង registry ក្នុងអង្គចងចាំ (`src/lib/skills/registry.ts`)។ កំណែត្រូវតែជា semver (`^\d+\.\d+\.\d+$`)។ `resolveVersion()` អាចយល់អំពីលក្ខខណ្ឌ `^`, `~`, `>`, `>=`, `<`, `<=`, `==` និងការផ្គូផ្គងជាក់លាក់។

### របៀប Skill

Skill នីមួយៗមានរបៀប runtime ដែលគ្រប់គ្រងពេលវាត្រូវបានបញ្ចូល៖

| របៀប   | ឥរិយាបថ                                                                                         |
| ------ | ----------------------------------------------------------------------------------------------- |
| `on`   | តែងតែត្រូវបានបញ្ចូលជានិយមន័យឧបករណ៍                                                              |
| `off`  | មិនត្រូវបានបញ្ចូល និងមិនអាចប្រតិបត្តិបាន                                                        |
| `auto` | ត្រូវបានដាក់ពិន្ទុដោយផ្អែកលើសំណើចូល; បញ្ចូលតែក្នុងករណីដែលពិន្ទុ ≥ `AUTO_MIN_SCORE` (លំនាំដើម 3) |

`auto` គឺជាលំនាំដើមសម្រាប់ skills ដែលបានដំឡើងពីទីផ្សារ។ `enabled=true` និង `mode="off"` រួមគ្នាមានន័យថា "បានចុះបញ្ជី ប៉ុន្តែមិនសកម្ម" — ការបិទបើក `enabled` តាមរយៈជួរឈរចាស់ ក៏ធ្វើបច្ចុប្បន្នភាព `mode` ផងដែរ ដើម្បីឱ្យ codepath ចាស់ៗនៅតែមានភាពស៊ីគ្នា (`src/app/api/skills/[id]/route.ts`)។

### ស្ថានភាព (ការប្រតិបត្តិ)

ការប្រតិបត្តិ skill ត្រូវបានតាមដានក្នុងតារាង `skill_executions` ដោយមានស្ថានភាពខាងក្រោម (`src/lib/skills/types.ts`)៖

```ts
enum SkillStatus {
  PENDING = "pending",
  RUNNING = "running",
  SUCCESS = "success",
  ERROR = "error",
  TIMEOUT = "timeout",
}
```

### Cache របស់ Registry

`SkillRegistry` គឺជា singleton ដែលមាន cache TTL រយៈពេល 60 វិនាទី (`registry.ts:14`)។ `loadFromDatabase()` គឺ idempotent និងលុបការហៅដំណាលគ្នាដែលស្ទួនតាមរយៈ `pendingLoad`។ រាល់ការសរសេរ (`register`/`unregister`/`unregisterById`) នឹងធ្វើឱ្យ cache អសុពលភាព។ ស្វែងរកកំណែតាមរយៈ `getSkillVersions(name)` និង `resolveVersion(name, constraint)`។

### ការបញ្ចូលដែលយល់ដឹងអំពី Provider

`injectSkills()` ក្នុង `src/lib/skills/injection.ts` គឺជាចំណុចចូលដែលបំប្លែង skills ដែលបានចុះបញ្ជីទៅជានិយមន័យឧបករណ៍ជាក់លាក់សម្រាប់ provider៖

- **OpenAI** — `{ type: "function", function: { name, description, parameters } }`
- **Anthropic** — `{ name, description, input_schema }`
- **Google (Gemini)** — `{ name, description, parameters }`

ឈ្មោះឧបករណ៍ត្រូវបានអ៊ិនកូដជា `name@version` ដើម្បីឱ្យ handler អាចជ្រើសរើសកំណែត្រឹមត្រូវ នៅពេលម៉ូដែលហៅវាត្រឡប់មកវិញ។

### ការដាក់ពិន្ទុ AUTO

នៅពេល `mode="auto"` ជំនាញបេក្ខជននីមួយៗត្រូវបានដាក់ពិន្ទុធៀបនឹងបរិបទនៃសំណើ (`scoreAutoSkill()` ក្នុង `injection.ts`)៖

| សញ្ញា                                                   | ពិន្ទុ            |
| ------------------------------------------------------- | ----------------- |
| ឈ្មោះជំនាញបង្ហាញដូចដើមទាំងស្រុងក្នុងបរិបទ               | +6                |

| token នីមួយៗនៃសេចក្តីពិពណ៌នាត្រូវគ្នានឹងបរិបទ           | +1                |
| មូលហេតុផ្ទៃខាងក្រោយត្រូវគ្នានឹង token នៃឈ្មោះ           | +2 ក្នុងមួយ token |

### ការស្ទាក់ចាប់ Tool Call

`handleToolCallExecution()` ក្នុង `src/lib/skills/interception.ts` ត្រូវបានហៅដោយ chat handler បន្ទាប់ពី upstream ត្រឡប់ response ដែលមានការហៅឧបករណ៍៖

1. `extractToolCalls()` អានទម្រង់ជាក់លាក់របស់ provider (OpenAI `tool_calls` / Responses `function_call`, Anthropic `tool_use`, Gemini `functionCalls`)។
2. alias របស់ឧបករណ៍ដែលមានស្រាប់ (ឧ. `omniroute_web_search` → `web_search`) ត្រូវបានដោះស្រាយជាមុន។ handler ដែលមានស្រាប់ដំណើរការ inline។
3. អ្វីផ្សេងទៀតទាំងអស់ត្រូវបានបញ្ជូនតាម `skillExecutor.execute(name@version, args, { apiKeyId, sessionId })`។
4. លទ្ធផលត្រូវបានបញ្ចូលត្រឡប់ទៅក្នុង response — ជា `tool_results`, ធាតុ `function_call_output` ឬ block `tool_result` របស់ Anthropic តាមភាពសមស្រប។

`customSkillExecutionEnabled` ក្នុងបរិបទនៃការប្រតិបត្តិអាចត្រូវបានកំណត់ជា `false` ដើម្បីអនុញ្ញាតតែការស្ទាក់ចាប់ដែលមានស្រាប់ប៉ុណ្ណោះ (ប្រើដោយ request path ដែលបិទ handler កំណត់ដោយអ្នកប្រើប្រាស់យ៉ាងជាក់លាក់)។

## Docker Sandbox

ផ្លូវកូដដែលមិនមែនជា builtin (`eval_code`, `execute_command`) ដំណើរការនៅក្នុង Docker តាមរយៈ `SandboxRunner` (`src/lib/skills/sandbox.ts`)។ container នីមួយៗត្រូវបានបើកដំណើរការជាមួយ៖

```
--rm --network none|bridge --cap-drop ALL
--security-opt no-new-privileges --pids-limit 100
--cpus <cpuLimit/1000> --memory <memoryLimit>m
--tmpfs /tmp:rw,noexec,nosuid,size=64m
--tmpfs /workspace:rw,noexec,nosuid,size=64m
--read-only (នៅពេល readOnly=true)
```

តម្លៃលំនាំដើម (`SandboxRunner.DEFAULT_CONFIG`)៖

| វាល              | តម្លៃលំនាំដើម   | កំណត់សម្គាល់                                       |
| ---------------- | --------------- | -------------------------------------------------- |
| `cpuLimit`       | 100 (= 0.1 CPU) | ត្រូវបានចែកនឹង 1000 មុនពេលបញ្ជូនទៅ `--cpus`        |
| `memoryLimit`    | 256 MB          | ដែនកំណត់តឹងរ៉ឹង                                    |
| `timeout`        | 30000 ms        | បញ្ឈប់ដោយទន់ភ្លន់តាមរយៈ `SIGTERM` + `docker kill`  |
| `networkEnabled` | `false`         | ក្លាយជា `--network none`                           |
| `readOnly`       | `true`          | Root FS បានតែអាន; `/tmp` និង `/workspace` ជា tmpfs |

`SandboxRunner.kill(id)` និង `killAll()` ត្រូវបានបង្ហាញឱ្យប្រើសម្រាប់ការបិទដំណើរការ; container ដែលកំពុងដំណើរការត្រូវបានតាមដានក្នុង `runningContainers: Map<string, ChildProcess>`។

### អថេរបរិស្ថានរបស់ Sandbox

បានកំណត់រចនាសម្ព័ន្ធតាមរយៈ `process.env` ក្នុង `src/lib/skills/builtins.ts`៖

| អថេរបរិស្ថាន                      | តម្លៃលំនាំដើម    | គោលបំណង                                                                             |
| --------------------------------- | ---------------- | ----------------------------------------------------------------------------------- |
| `SKILLS_MAX_FILE_BYTES`           | `1048576` (1 MB) | ដែនកំណត់សម្រាប់ `file_read` និង `file_write`                                        |
| `SKILLS_MAX_HTTP_RESPONSE_BYTES`  | `256000`         | ដែនកំណត់សម្រាប់តួការឆ្លើយតបរបស់ `http_request`                                      |
| `SKILLS_MAX_SANDBOX_OUTPUT_CHARS` | `100000`         | ដែនកំណត់សម្រាប់ stdout/stderr ដែលបញ្ជូនត្រឡប់ទៅអ្នកហៅ                               |
| `SKILLS_SANDBOX_TIMEOUT_MS`       | `10000`          | timeout លំនាំដើមសម្រាប់ command ក្នុង sandbox; កំណត់អតិបរមាត្រឹម 60 s               |
| `SKILLS_SANDBOX_NETWORK_ENABLED`  | `false`          | ច្រកមេសម្រាប់ egress។ កំណត់ជា `1` ឬ `true` ដើម្បីអនុញ្ញាតការជ្រើសប្រើតាមការហៅនីមួយៗ |
| `SKILLS_ALLOWED_SANDBOX_IMAGES`   | (មើលខាងក្រោម)    | បញ្ជី Docker image ដែលអនុញ្ញាត ដោយបំបែកដោយសញ្ញាក្បៀស                                |

image ដែលត្រូវបានអនុញ្ញាតតាមលំនាំដើម៖ `alpine:3.20`, `node:22-alpine`, `python:3.12-alpine`។ ការបន្ថែមណាមួយតាមរយៈ `SKILLS_ALLOWED_SANDBOX_IMAGES` ត្រូវបានបញ្ចូលរួមជាមួយតម្លៃលំនាំដើម; image ដែលមិនស្គាល់ត្រូវបានបដិសេធដោយ `normalizeImage()`។

> កំណត់សម្គាល់៖ មិនមានអថេរបរិស្ថាន `SKILLS_EXECUTION_TIMEOUT_MS` ដាច់ដោយឡែកទេ។ timeout របស់ handler ដែលមិនមែនជា sandbox ត្រូវបានកំណត់ថេរជា 30 s ក្នុង `SkillExecutor` (`executor.ts:13`) ប៉ុន្តែអាចត្រូវបានសរសេរជាន់លើនៅពេលដំណើរការ តាមរយៈ `skillExecutor.setTimeout(ms)`។

### ការញែក Workspace ឱ្យដាច់ដោយឡែក

`file_read` និង `file_write` ដោះស្រាយរាល់ path ធៀបទៅនឹង workspace សម្រាប់ API key នីមួយៗនៅ `<DATA_DIR>/skills/workspaces/<sha256(apiKeyId).slice(0,24)>/`។ ការឆ្លងកាត់ path (`..`) និង segment ដែលត្រូវបានហាមឃាត់ (`.env`, `.git`, `.ssh`, `.omniroute`, `.codex`, `secrets`) ត្រូវបានបដិសេធ មុនពេលធ្វើ disk I/O ណាមួយ។

### ការពង្រឹងសុវត្ថិភាព HTTP

`http_request` (`builtins.ts:257`)៖

- បញ្ជី method ដែលអនុញ្ញាត៖ `GET, HEAD, POST, PUT, PATCH, DELETE`
- header ចេញក្រៅដែលត្រូវបានទប់ស្កាត់៖ `host, connection, content-length, cookie, set-cookie, authorization, proxy-authorization`
- បានបិទ redirect (`allowRedirect: false`)
- ត្រូវបានបញ្ជូនតាម `safeOutboundFetch` ជាមួយ `guard: "public-only"` (range ឯកជន/loopback ត្រូវបានទប់ស្កាត់)
- ការឆ្លើយតបត្រូវបានកាត់ត្រឹម `SKILLS_MAX_HTTP_RESPONSE_BYTES`; client ឃើញ `truncated: true`

## កម្មវិធីប្រតិបត្តិ Hybrid (មើលជាមុន)

`src/lib/skills/hybrid.ts` កំណត់ `HybridExecutor` ដែលសម្រេចជ្រើសរើសរវាងការប្រតិបត្តិ `direct` (នៅក្នុងដំណើរការតែមួយ) និង `sandbox` សម្រាប់ការហៅនីមួយៗ ដោយមានផ្លូវសាកល្បងឡើងវិញ `autoUpgrade` នៅពេលមានកំហុសអស់ពេល ឬអង្គចងចាំ។ ការអនុវត្ត `directExecutor` / `sandboxRunner` ដែលបានភ្ជាប់មកជាមួយគឺជាគំរូបណ្ដោះអាសន្ន (`executeDirect`, `executeInSandbox` ត្រឡប់វត្ថុជំនួសបណ្ដោះអាសន្ន) — សូមចាត់ទុកម៉ូឌុលនេះជាកិច្ចសន្យាដែលកំពុងស្ថិតក្រោមការអភិវឌ្ឍ។ ការប្រតិបត្តិពិតប្រាកដនៅតែដំណើរការតាមរយៈ `skillExecutor` + `SandboxRunner`។

```bash
  -d '{
    "name": "reverse-text",
    "version": "1.0.0",
    "description": "Reverses a string",
    "schema": {
      "input":  { "type": "object", "properties": { "text": { "type": "string" } }, "required": ["text"] },
      "output": { "type": "object", "properties": { "reversed": { "type": "string" } } }
    },
    "handlerCode": "echo-handler",
    "apiKeyId": "your-api-key-id"
  }'
```

ខ្សែអក្សរ `handlerCode` គឺជា **ការស្វែងរកតាមឈ្មោះ handler** — មិនមែនជាកូដដែលអាចប្រតិបត្តិបានទេ។ កម្មវិធីប្រតិបត្តិផ្គូផ្គងវាតាមរយៈ `skillExecutor.registerHandler(name, fn)` (`executor.ts:25`)។ ការដំឡើងពី Marketplace រក្សាទុកអត្ថបទ SKILL.md នៅក្នុងវាលនេះជាឯកសារពន្យល់ ហើយបញ្ជូនការប្រតិបត្តិតាមរយៈការហៅ tool ដែលបង្កើតដោយម៉ូដែល។ ប្រភពដែលផ្ដល់ដោយអ្នកប្រើប្រាស់តាមអំពើចិត្ត មិនត្រូវបាន eval ទេ។

## ការបន្ថែមសមត្ថភាពដែលភ្ជាប់មកជាមួយថ្មី

1. **កំណត់ handler** នៅក្នុង `src/lib/skills/builtins.ts` (ឬឯកសារដែលនៅកម្រិតដូចគ្នាក្រោម `src/lib/skills/builtin/`)។ ទម្រង់ហត្ថលេខា៖ `(input, { apiKeyId, sessionId }) => Promise<output>`។
2. **ផ្លូវកូដដែលដំណើរការក្នុង sandbox?** ហៅ `sandboxRunner.run(image, command, env, sandboxConfig({...}))`។ ប្រើ `normalizeImage()` ផ្ទៀងផ្ទាត់នឹងបញ្ជីអនុញ្ញាត។
3. **ផ្លូវប្រព័ន្ធឯកសារ?** ត្រូវឆ្លងកាត់ `resolveWorkspacePath(input, context)` ជានិច្ច មុនពេលចូលប្រើថាស។
4. **ការហៅបណ្តាញ?** ប្រើ `safeOutboundFetch` ជាមួយ `guard: "public-only"`; សម្អាត headers តាមរយៈ `sanitizeHeaders()`។
5. **ចុះឈ្មោះ** ដោយបន្ថែមធាតុទៅ `builtinSkills` (ឬហៅតាមរចនាប័ទ្ម `registerBrowserSkill(executor)` នៅពេលចាប់ផ្តើមដំណើរការ)។
6. **ភ្ជាប់ឈ្មោះហៅក្រៅរបស់ឧបករណ៍ដែលភ្ជាប់មកជាមួយ** (ជាជម្រើស) នៅក្នុង `BUILTIN_TOOL_ALIASES` (`interception.ts:23`) ប្រសិនបើម៉ូដែលខាងលើបញ្ចេញឈ្មោះផ្សេង។
7. **ការធ្វើតេស្ត** នៅក្នុង `src/lib/skills/__tests__/` (Vitest)។

## គន្លឹះប្រតិបត្តិការ

- **កុងតាក់មេ៖** `settings.skillsEnabled = false` រារាំងការប្រតិបត្តិទាំងអស់ និងត្រឡប់ HTTP `503` នៅលើ `/api/skills/executions`។ registry នៅតែបន្តផ្ទុក។
- **រឹតបន្តឹងចរាចរចេញ៖** ទុក `SKILLS_SANDBOX_NETWORK_ENABLED` មិនបានកំណត់ (លំនាំដើម) សម្រាប់ sandbox ដែលផ្តាច់ពីបណ្តាញទាំងស្រុង។ `networkEnabled: true` ក្នុងការហៅនីមួយៗ នៅតែទាមទារការអនុញ្ញាតពីកុងតាក់មេ។
- **អនុញ្ញាត image ជាក់លាក់៖** កំណត់ `SKILLS_ALLOWED_SANDBOX_IMAGES="myorg/sandbox:1.0,node:22-alpine"` ដើម្បីពង្រីកបញ្ជីអនុញ្ញាត។
- **សវនកម្មការប្រតិបត្តិ៖** `/dashboard/skills/executions` និង `omniroute_skills_executions` ទាំងពីរសួរទិន្នន័យពី `skill_executions`។ ការដំណើរការដែលជោគជ័យរួមមាន `durationMs`; ការបរាជ័យរួមមាន `errorMessage`។
- **ការធ្វើឱ្យ cache អសុពលភាព៖** ហៅ `skillRegistry.invalidateCache()` បន្ទាប់ពីកែសម្រួល DB ដោយដៃ; បើមិនដូច្នោះទេ សូមរង់ចាំ 60 វិនាទី។
- **workspace អនាមិក៖** នៅពេល `apiKeyId` ទទេ ការហៅទាំងអស់នឹងត្រូវបាន hash ទៅកាន់ workspace `"anonymous"` ដូចគ្នា — កូដដែលគិតគូរអំពីការចែករំលែកគួរតែបញ្ជូន key ពិតប្រាកដជានិច្ច។

## វដ្តជីវិតនៃការប្រតិបត្តិ (v3.8.16+)

`SkillExecutor` (`src/lib/skills/executor.ts`) គឺជា **singleton** ដែលគ្រប់គ្រងរាល់ការហៅប្រើ skill។ ការយល់ដឹងអំពីវដ្តជីវិតរបស់វាមានសារៈសំខាន់ខ្លាំងសម្រាប់ការបំបាត់កំហុសទាក់ទងនឹងការអស់ពេលកំណត់ ការព្យាយាមឡើងវិញ និងស្ថានភាពប្រតិបត្តិការ។

### វដ្តជីវិត 5 ដំណាក់កាល

```
   execute() ត្រូវបានហៅ
        │
        ▼
  ┌─────────────┐
  │  PENDING    │  ← បានដាក់ក្នុងជួរ មិនទាន់ចាប់ផ្ដើម (បានបង្កើតជួរដេក DB)
  └──────┬──────┘
         │ ចាប់ផ្ដើម handler
         ▼
  ┌─────────────┐
  │  RUNNING    │  ← បានហៅ handler ជាមួយពេលកំណត់
  └──────┬──────┘
         │
    ┌────┴────┬──────────┬──────────┐
    │         │          │          │
    ▼         ▼          ▼          ▼
  SUCCESS   ERROR     TIMEOUT   (គ្មានផ្លូវផ្សេងទៀតទេ — ត្រូវបានបញ្ឈប់ដោយ parent)
    │         │          │
    └────┬────┴──────────┘
         │
         ▼
   ជួរដេក DB ត្រូវបានធ្វើបច្ចុប្បន្នភាពជាមួយ status, output, durationMs
```

### ការកំណត់រចនាសម្ព័ន្ធលំនាំដើម

| ការកំណត់     | លំនាំដើម            | អាចកំណត់រចនាសម្ព័ន្ធតាមរយៈ           |
| ------------ | ------------------- | ------------------------------------ |
| `timeout`    | `30000` (30 វិនាទី) | `skillExecutor.setTimeout(ms)`       |
| `maxRetries` | `3`                 | `skillExecutor.setMaxRetries(count)` |

> **សំខាន់**៖ executor គឺជា singleton — ការហៅ `setTimeout()` ប៉ះពាល់ជាសកលដល់ការហៅប្រើទាំងអស់ជាបន្តបន្ទាប់។ ពេលកំណត់សម្រាប់ skill នីមួយៗបច្ចុប្បន្នមិនត្រូវបានគាំទ្រទេ។ ប្រសិនបើអ្នកត្រូវការពេលកំណត់ខុសៗគ្នាសម្រាប់ skill នីមួយៗ សូមដាក់ស្នើ process ដាច់ដោយឡែក ឬ fork executor។

### តម្លៃស្ថានភាព

ពី `src/lib/skills/types.ts`៖

```ts
enum SkillStatus {
  PENDING = "pending", // បានដាក់ក្នុងជួរ មិនទាន់ចាប់ផ្ដើម
  RUNNING = "running", // បានហៅ Handler
  SUCCESS = "success", // Handler បានត្រឡប់ output ត្រឹមត្រូវ
  ERROR = "error", // Handler បានបោះ exception
  TIMEOUT = "timeout", // បានលើសពេលកំណត់របស់ executor
}
```

> **ចំណាំ**៖ ស្ថានភាព `TIMEOUT` ត្រូវបានកំណត់នៅក្នុង enum ប៉ុន្តែ **មិនត្រូវបានសរសេរទៅក្នុង DB ជាក់ស្ដែងទេ** ដោយការអនុវត្ត executor បច្ចុប្បន្ន — ការអស់ពេលកំណត់បង្ហាញជា `ERROR` ជាមួយសារ `"Skill execution timed out"`។ enum ស្ថានភាពនេះត្រូវបានរក្សាទុកសម្រាប់ការប្រើប្រាស់នាពេលអនាគត។

### ការត្រួតពិនិត្យការប្រតិបត្តិ

```ts
import { skillExecutor } from "omniroute/skills/executor";

// ទទួលយកការប្រតិបត្តិជាក់លាក់មួយតាម ID
const exec = skillExecutor.getExecution("exec-uuid-123");
if (exec) {
  console.log(`${exec.skillName}: ${exec.status} in ${exec.durationMs}ms`);
}

// រាយបញ្ជីការប្រតិបត្តិថ្មីៗសម្រាប់ API key មួយ
const recent = skillExecutor.listExecutions("api-key-id", 50, 0);
for (const e of recent) {
  console.log(`${e.skillName} → ${e.status} (${e.durationMs}ms)`);
}

// រាប់ចំនួនការប្រតិបត្តិសរុប
const total = skillExecutor.countExecutions("api-key-id");
```

### ឥរិយាបថនៃការព្យាយាមឡើងវិញ

ការកំណត់ `maxRetries` ត្រូវបានរក្សាទុក ប៉ុន្តែ **បច្ចុប្បន្នមិនត្រូវបានប្រើប្រាស់ទេ** ដោយ method `execute()` របស់ executor — វាធ្វើការព្យាយាមតែមួយដងប៉ុណ្ណោះ។ តម្លៃ `maxRetries` ត្រូវបានបង្ហាញសម្រាប់ការអនុវត្តនាពេលអនាគត និងសម្រាប់ hook ដែលចង់អានវា។

សម្រាប់ពេលនេះ ការព្យាយាមឡើងវិញត្រូវតែអនុវត្តនៅខាងក្នុង skill handler ផ្ទាល់។ skill
ដែលមានស្រាប់ត្រូវបានចុះឈ្មោះជាមួយ executor (ឧ. `registerBuiltinSkills(executor)`
/ `registerBrowserSkill(executor)` នៅក្នុង `src/lib/skills/builtin/`)។ handler ណាមួយ
ដែលអ្នកចុះឈ្មោះ អាចរុំ retry loop ផ្ទាល់ខ្លួនរបស់វា៖

```ts
// នៅខាងក្នុង skill handler
async function handler(input, ctx) {
  const maxRetries = 3;
  let lastError: Error | null = null;

  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      return await fetchSomething(input);
    } catch (err) {
      lastError = err as Error;
      if (attempt < maxRetries) {
        await new Promise((r) => setTimeout(r, 1000 * attempt));
      }
    }
  }
  throw lastError;
}
```

## SkillMode លម្អិត

enum `SkillMode` (`src/lib/skills/types.ts`) គ្រប់គ្រង **ពេលណា និងរបៀបណា** ដែល skill ត្រូវបានហៅប្រើ៖

```ts
enum SkillMode {
  AUTO = "auto", // LLM សម្រេចចិត្តថាពេលណាត្រូវហៅ skill
  MANUAL = "manual", // ត្រូវបានហៅប្រើតែតាមសំណើជាក់លាក់របស់អ្នកប្រើប៉ុណ្ណោះ
  HYBRID = "hybrid", // ការដាក់ពិន្ទុ AUTO + ការកំណត់ជាន់លើដោយដៃ
}
```

> **ចំណាំ**៖ codebase កំណត់ `SkillMode` (AUTO/MANUAL/HYBRID) ខណៈពេលដែល field `Skill.mode` ប្រើទម្រង់ផ្សេង (`"on" | "off" | "auto"`)។ ពួកវាមានទំនាក់ទំនងគ្នា ប៉ុន្តែមិនដូចគ្នាទាំងស្រុងទេ — `SkillMode` ប្រើសម្រាប់គោលការណ៍របស់ executor រីឯ `Skill.mode` ប្រើសម្រាប់ការបើកដំណើរការ skill នីមួយៗ។

### ពេលណាគួរប្រើ Mode នីមួយៗ

| Mode     | ឥរិយាបថរបស់ LLM                                                                           | ករណីប្រើប្រាស់                                             |
| -------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `AUTO`   | LLM អាចហៅ skill នៅពេលវាយល់ថាចាំបាច់                                                       | Skill សម្រាប់គោលបំណងទូទៅ (ការអាន file, សំណើ HTTP)          |
| `MANUAL` | LLM មិនអាចហៅ skill បានទេ; មានតែការហៅ API `executeSkill` យ៉ាងជាក់លាក់ប៉ុណ្ណោះដែលអាចហៅវាបាន | ប្រតិបត្តិការរសើប (ការសរសេរ database, ការទូទាត់)           |
| `HYBRID` | LLM អាចស្នើឱ្យប្រើ skill; អ្នកប្រើត្រូវតែបញ្ជាក់                                          | Skill ដែលមានផលប៉ះពាល់បន្ទាប់បន្សំ ប៉ុន្តែមិនមានគ្រោះថ្នាក់ |

### ការដាក់ពិន្ទុ AUTO

នៅពេល mode `AUTO` សកម្ម skill ដែលជាបេក្ខភាពនីមួយៗត្រូវបានដាក់ពិន្ទុធៀបនឹង context របស់សំណើ
ដោយ `scoreAutoSkill()` ក្នុង `src/lib/skills/injection.ts` — ជាប្រព័ន្ធពិន្ទុចំនួនគត់
ដែលបូកបន្ថែម (ការផ្គូផ្គងឈ្មោះ skill, ភាពត្រួតគ្នានៃ token ក្នុងឈ្មោះ/tag/សេចក្ដីពិពណ៌នា,
តម្រុយអំពីមូលហេតុផ្ទៃខាងក្រោយ, ប្រាក់បន្ថែម/ការកាត់ពិន្ទុពីតម្រុយរបស់ provider)។ Skill `AUTO_MAX_SKILLS = 5`
លំដាប់កំពូលដែលមាន `score >= AUTO_MIN_SCORE = 3` ត្រូវបានបញ្ចូលជា
tool ដែលអាចហៅប្រើបាន ដោយភាពស្មើគ្នាត្រូវបានសម្រេចតាម `installCount` រួចតាមឈ្មោះ។ សូមមើលតារាងពិន្ទុពេញលេញ
ក្នុង [**ការបង្កើត Tool Schema → ការដាក់ពិន្ទុ AUTO**](#auto-scoring) នៅផ្នែកមុននៃឯកសារនេះ;
មិនមាន threshold ជា float បែប `0.6` និងគ្មានការដាក់ពិន្ទុក្នុង `registry.ts` ទេ។

## កាតាឡុក Skill ដែលភ្ជាប់មកជាមួយ

OmniRoute ផ្ដល់ជូនសំណុំ skill ដែលភ្ជាប់មកជាមួយ និងត្រូវបានជ្រើសរើសយ៉ាងយកចិត្តទុកដាក់ក្នុង `src/lib/skills/builtin/`។ Skill ដែលប្រើញឹកញាប់បំផុតរួមមាន៖

### Skill ស្វ័យប្រវត្តិកម្ម Browser

Skill សម្រាប់ browser (`src/lib/skills/builtin/browser.ts`) ផ្ដល់ស្វ័យប្រវត្តិកម្ម browser ដោយគ្មាន UI តាមរយៈ Playwright/Puppeteer។ **វាត្រូវបានអនុវត្តរួចហើយ ប៉ុន្តែមិនស្ថិតនៅក្នុងកាតាឡុក skill លំនាំដើមទេ** — ដើម្បីប្រើវា សូមដំឡើង plugin ផ្នែកបន្ថែម browser ដោយឡែក។

```ts
// បើកដំណើរការក្នុង config របស់អ្នក
const config: SkillConfig = {
  enabled: true,
  mode: SkillMode.MANUAL, // តម្រូវឱ្យហៅប្រើយ៉ាងជាក់លាក់ជានិច្ច
  allowedSkills: ["browser"],
  timeout: 60000, // 60s សម្រាប់ការផ្ទុកទំព័រ
  maxRetries: 1,
};
```

| ------------------ | --------------------------------------------------- | ------ |
| File I/O           | `file_read`, `file_write`                           | AUTO   |
| HTTP               | `http_request`                                      | AUTO   |
| ការស្វែងរក         | `web_search`                                        | AUTO   |
| ការប្រតិបត្តិ Code | `eval_code` (JavaScript/Python ក្នុង sandbox)       | HYBRID |
| System             | `execute_command` (ការប្រតិបត្តិ CLI ក្នុង sandbox) | MANUAL |
