`open-sse/config/providerPluginManifest.ts` កំណត់កិច្ចសន្យា plugin របស់ provider ដែលមានសុវត្ថិភាពសម្រាប់ JSON។
`open-sse/config/providerPluginManifestRegistry.ts` ភ្ជាប់កិច្ចសន្យានោះទៅនឹង registry របស់ provider បច្ចុប្បន្ន សម្រាប់ sidecar ដូចជា Bifrost,
CLIProxyAPI ឬ router ដែលសរសេរដោយ Go/Rust នាពេលអនាគត។ Registry របស់ TypeScript នៅតែជា
ប្រភពពិតតែមួយ ប៉ុន្តែ sidecar អាចប្រើប្រាស់ manifest ដោយមិនចាំបាច់ import
កូដ executor, តម្លៃលំនាំដើម OAuth, header ឬស្ថានភាព environment របស់ process ឡើយ។

Manifest ដូចគ្នានេះក៏អាចប្រើបានតាមរយៈ HTTP នៅ
`GET /api/v1/provider-plugin-manifest` សម្រាប់ sidecar ដែលដំណើរការនៅក្រៅ process។

OmniRoute ប្រកាស URL នោះទៅកាន់ Bifrost និង CLIProxyAPI តាមរយៈ
request header `X-OmniRoute-Provider-Manifest-Url`។ កំណត់
`OMNIROUTE_PROVIDER_MANIFEST_URL` នៅពេល sidecar ត្រូវការ URL សាធារណៈ ឬ URL បណ្តាញ
container ជំនួសឱ្យ origin របស់ request មូលដ្ឋាន។

## ការធ្វើឱ្យ Manifest ថ្មី

HTTP endpoint ត្រឡប់ `Cache-Control: public, max-age=60` និង
`ETag` ខ្លាំងមួយ។ Sidecar គួររក្សាទុក manifest ដែលបានផ្ទៀងផ្ទាត់ចុងក្រោយ ហើយផ្ញើ ETag របស់វា
ក្នុង `If-None-Match` នៅពេលធ្វើឱ្យថ្មី។ Response `304 Not Modified` មិនមាន body ទេ;
sidecar បន្តរក្សាទុក manifest ដែលបាន cache របស់វា។ ប្រសិនបើមិនមាន manifest ដែលបាន cache និងផ្ទៀងផ្ទាត់ទេ
sidecar ត្រូវតែផ្ញើ request ដោយគ្មានលក្ខខណ្ឌ ជំនួសឱ្យការទទួលយក `304`។

## គោលដៅ

ផ្លាស់ទី metadata របស់ provider ឆ្ពោះទៅរកកិច្ចសន្យា plugin ដើម្បីឱ្យ hot request path
នៅទីបំផុតអាចត្រូវបានគ្រប់គ្រងដោយ sidecar ដែលមាន latency ទាបជាង ខណៈដែល OmniRoute រក្សា
route របស់ TypeScript ជាច្រកគោលការណ៍ និង fallback។ Manifest មានលក្ខណៈបន្ថែម៖ វា
មិនផ្លាស់ប្តូរ request routing ដោយខ្លួនឯងទេ។

## កិច្ចសន្យា

Manifest មាន៖

- id និង alias របស់ provider
- format upstream និងឈ្មោះ executor
- ប្រភេទ auth, auth header និង auth prefix ដែលមិនតម្រូវ
- metadata របស់ endpoint ថេរ
- សិទ្ធិអាចប្រើ sidecar និងហេតុផលច្បាស់លាស់ នៅពេល provider គួរបន្តស្ថិតលើ TS
- metadata របស់ model ដែលមានសុវត្ថិភាពសម្រាប់ JSON ដូចជា ប្រវែង context, flag សម្រាប់ vision/reasoning និង
  param ដែលមិនគាំទ្រ
- capability tag រួមមាន `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` និង `usage-supported`

Manifest មិនរួមបញ្ចូលដោយចេតនានូវ៖

- secret របស់ OAuth client និងតម្លៃ secret លំនាំដើម
- ការដោះស្រាយ runtime environment
- request header និង helper សម្រាប់ credential សាធារណៈ
- URL builder បែប dynamic
- function របស់ executor
- ផ្នែកខាងក្នុងនៃ session pool

## Capability Tag

`capabilities` គឺជា array នៃ tag ដែលបានតម្រៀប និងទាញយកពី entry របស់ registry។ អ្នកធ្វើសមាហរណកម្ម
គួរចាត់ទុកវាជាចម្លើយដែលម៉ាស៊ីនអាចអានបានចំពោះសំណួរ "តើ provider នេះអាចធ្វើអ្វីបានខ្លះ" ជំនួសឱ្យ
ការអាន source របស់ TypeScript ឡើងវិញ។

| Tag                  | អត្ថន័យ                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------- |
| `apikey`             | ទទួលយក API key (`authType` គឺ `apikey` ឬ `optional`)។                                       |
| `oauth`              | ប្រើ flow របស់ OAuth ឬ session។                                                             |
| `responses`          | ផ្តល់ OpenAI Responses-API base URL។                                                        |
| `passthrough-models` | ផ្តល់ model ដោយផ្ទាល់ពី upstream ជំនួសឱ្យ catalog ថេរ។                                      |
| `custom-executor`    | ដំណើរការ executor ដែលមិនមែនជាលំនាំដើម ដូច្នេះវាបន្តស្ថិតនៅលើ path របស់ TypeScript។          |
| `sidecar-candidate`  | ឆ្លុះបញ្ចាំង `sidecar.eligible` — មានសុវត្ថិភាពក្នុងការពិចារណាសម្រាប់ការ import ទៅ sidecar។ |
| `usage-fetch`        | មាន usage ឬ quota fetcher ដែលបានភ្ជាប់រួច (`getUsageForProvider`)។                          |
| `usage-supported`    | Usage API ទទួលយក provider នេះ (`isSupportedUsageConnection`)។                               |

`usage-fetch` គឺសម្រាប់តែការរកឃើញប៉ុណ្ណោះ។ វារាយការណ៍ថា OmniRoute ដឹងពីរបៀបអាន usage សម្រាប់
provider នេះ; វាមិនបើកដំណើរការការទាញយក មិនផ្លាស់ប្តូរ semantics របស់ quota ឬបញ្ជាក់ថា
widget quota របស់ Dashboard ត្រូវបានបើកសម្រាប់ provider នេះទេ — widget នោះត្រូវបានគ្រប់គ្រងដោយឡែកតាម
`USAGE_SUPPORTED_PROVIDERS`។ ប្រភពពិតតែមួយគឺ `USAGE_FETCHER_PROVIDERS` ក្នុង
`open-sse/services/usage/fetcherProviders.ts`។

បញ្ជីនោះត្រូវបានកំណត់ key ដោយ string ដែល usage dispatcher ទទួលយក ដូច្នេះវាលាយបញ្ចូល canonical id
ជាមួយ alias ហើយវែងជាងចំនួន provider ដែលមាន tag បន្តិច៖ entry ដែលមិនមែនជា
chat provider ក្នុង manifest registry (ឧទាហរណ៍ search provider `firecrawl`
និង ACP provider `amazon-q`) មិនមាន manifest entry សម្រាប់ដាក់ tag ទេ។

`usage-supported` ឆ្លើយថាតើ route សម្រាប់ usage របស់ server និង Dashboard ទទួលយក connection
សម្រាប់ provider នេះឬអត់។ វាឆ្លុះបញ្ចាំង `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
និង `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`) ដែលទាំងពីរត្រូវបានគ្រប់គ្រងដោយ
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`)។ ខុសពី
`usage-fetch` វាត្រូវបានបញ្ចេញដោយផ្អែកលើ id របស់ provider តែប៉ុណ្ណោះ — runtime guard អនុវត្ត
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` ដោយគ្មានការដោះស្រាយ alias ដូច្នេះ manifest
រក្សាច្បាប់ដូចគ្នា។ Tag ទាំងពីរមានដែនកំណត់ខុសគ្នា៖ provider 3 មានតែ
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) ហើយ 1 មានតែ
`usage-supported` (`xiaomi-mimo-token-plan`) ដូច្នេះមួយមិនបញ្ជាក់ថាមានមួយទៀតឡើយ។

## ការប្រើប្រាស់ Sidecar

Sidecar គួរចាត់ទុក `sidecar.eligible` ជាសញ្ញាបេក្ខភាពបែបប្រុងប្រយ័ត្ន មិនមែនជាការសម្រេចចិត្តកំណត់ផ្លូវដោយគ្មានលក្ខខណ្ឌនោះទេ។ គោលដៅនាំចូលដំបូងគួរតែជាអ្នកផ្តល់សេវាដែលប្រើ API key និង static endpoint ដោយប្រើ executor លំនាំដើម។ អ្នកផ្តល់សេវាដែលមាន web executor ផ្ទាល់ខ្លួន, OAuth/session flow, dynamic URL builder ឬ pool config គួរបន្តនៅលើផ្លូវ TypeScript fallback រហូតដល់ sidecar មួយអនុវត្តឥរិយាបថសមមូល ហើយ telemetry បញ្ជាក់ថាមានភាពស្មើគ្នា។

ដំណាក់កាល migration ដែលបានណែនាំ៖

1. បង្កើត និងផ្ទៀងផ្ទាត់ provider plugin manifest ពី TS registry។
2. បង្រៀន Bifrost ឬ CLIProxyAPI ឱ្យនាំចូល manifest សម្រាប់អ្នកផ្តល់សេវាប្រភេទ API-key/static។
3. កំណត់ផ្លូវអ្នកផ្តល់សេវាដែលមានលក្ខណៈសម្បត្តិសមស្របឱ្យឆ្លងកាត់ sidecar នៅពីក្រោយ `OMNIROUTE_RELAY_BACKEND` ខណៈដែលនៅតែបើកប្រើ TS fallback។
4. ដំឡើងអ្នកផ្តល់សេវាទៅកម្រិតប្រើប្រាស់ពេញលេញ លុះត្រាតែអត្រាជោគជ័យ, p99 latency, streaming behavior និង unsupported-param handling ត្រូវគ្នានឹងផ្លូវ TS។
5. បន្ថែម plugin ដែលជា sidecar-native សម្រាប់ custom executor ម្តងមួយគ្រួសារអ្នកផ្តល់សេវា។

## ហេតុអ្វីមិនបង្កប់អ្នកផ្តល់សេវាដោយផ្ទាល់នៅក្នុង Next
