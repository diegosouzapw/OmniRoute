## សេចក្តីសង្ខេប

ឥឡូវនេះ OmniRoute គាំទ្ររបៀប relay ចំនួនបីសម្រាប់ `/api/v1/relay/chat/completions`៖

- `ts`៖ ប្រើ TypeScript relay នៅក្នុង process តែមួយ។
- `bifrost`៖ បង្ខំឱ្យប្រើ Bifrost gateway។
- `auto`៖ ផ្តល់អាទិភាពដល់ Bifrost នៅពេលអាចប្រើបាន ហើយប្តូរទៅ TypeScript ជំនួសនៅពេលបរាជ័យ។

នៅពេលអ្នកដំណើរការក្នុងអត្រាសំណើខ្ពស់ (ចំនួន token ច្រើនក្នុងមួយថ្ងៃ និង throughput ស្ទើរតែថេរ) យុទ្ធសាស្ត្រដ៏ល្អបំផុតគឺរក្សាផ្លូវ fallback ឱ្យច្បាស់លាស់ និងរហ័ស ដើម្បីកុំឱ្យ hot path ត្រូវបានរាំងខ្ទប់ដោយ sidecar ដែលមិនដំណើរការ។

## ឥរិយាបថរបស់របៀប

- `ts`
  - មានភាពស្មុគស្មាញផ្នែកប្រតិបត្តិការទាបបំផុត។
  - រាល់ការកំណត់ផ្លូវ និងការផ្ទៀងផ្ទាត់ដំណើរការនៅក្នុង Node។
  - មិនពឹងផ្អែកលើ sidecar សម្រាប់ភាពអាចប្រើបាន។
- `bifrost`
  - បង្ខំឱ្យសំណើទាំងអស់ឆ្លងកាត់ sidecar gateway។
  - មិនមាន fallback ដោយស្វ័យប្រវត្តិ។
  - មានប្រយោជន៍តែនៅពេលដែលសុខភាព និង latency របស់ sidecar ត្រូវបានធានា។
- `auto`
  - ប្រើ sidecar នៅពេលអាចភ្ជាប់ទៅវាបាន និងវាត្រូវបានបើក។
  - ការព្យាយាមដែលបរាជ័យនឹងបង្កើត fallback headers ហើយបញ្ជូន traffic ត្រឡប់ទៅ TS ដើម្បីធានាថាភាពជោគជ័យនៃសំណើនៅតែស្ថិតក្នុងដែនកំណត់។
  - របៀបនេះជាជម្រើសដែលមានសុវត្ថិភាពបំផុតសម្រាប់ production នៅពេល uptime សំខាន់ជាងការកំណត់ផ្លូវដែលប្រើតែ sidecar យ៉ាងតឹងរ៉ឹង។

## 9router ទល់នឹង CLIPROXYAPI នាពេលបច្ចុប្បន្ន

9router និង CLIPROXYAPI សុទ្ធតែជាការរួមបញ្ចូលដែលជាប្រវត្តិសាស្ត្របានផ្តល់ compatibility paths សម្រាប់ upstream providers។

- 9router គឺជាផ្លូវដែលបានបង្កប់សម្រាប់ upstream orchestration និងឥរិយាបថ compatibility។
- CLIPROXYAPI គឺជា proxy API bridge សម្រាប់ traffic បែប CLI / SDK។
- Bifrost កំពុងត្រូវបានធ្វើឱ្យមានស្ថិរភាពជាផ្លូវខាងក្រៅ នៅពេលអ្នកត្រូវការ hop ដាច់ដោយឡែកដែលមានលក្ខណៈដូច sidecar និងការបញ្ជូនមូលដ្ឋានដែលមាន latency ទាប។

ប្រសិនបើបច្ចុប្បន្នអ្នកកំពុងប្រៀបធៀប 9router/CLIPROXYAPI៖

- រក្សាការចុះហត្ថលេខាលើសំណើ ការត្រួតពិនិត្យ allowlist និង DB policy gates នៅក្នុង API route មុនពេល handoff។
- ប្រសិនបើ workflow ត្រូវការឥរិយាបថ sidecar យ៉ាងតឹងរ៉ឹង និងភាពប្រែប្រួលក្នុងមួយសំណើទាបជាង សូមប្រើ `OMNIROUTE_RELAY_BACKEND=bifrost`។
- ប្រសិនបើអ្នកត្រូវការភាពធន់របស់ sidecar ជាមួយនឹងការថយចុះសមត្ថភាពដោយរលូននៅក្រោមលក្ខខណ្ឌ incident សូមប្រើ `OMNIROUTE_RELAY_BACKEND=auto`។

## កិច្ចសន្យាព្រំដែន backend

ព្រំដែនផលិតផលដែលមានស្ថិរភាពគឺ OmniRoute relay API មិនមែនការអនុវត្ត dashboard ទេ។ Next.js dashboard អាចដំឡើង កំណត់រចនាសម្ព័ន្ធ និងត្រួតពិនិត្យសេវាកម្មមូលដ្ឋាន ប៉ុន្តែការកំណត់ផ្លូវសំណើគួរតែចូលតាម relay API ហើយធ្វើ handoff នៅខាងក្រោយព្រំដែននោះ។

ជម្រើស backend រយៈពេលវែង៖

- រក្សា TypeScript relay ជា policy ក្នុង process និងជាផ្លូវ fallback។ Auth, allowlists, ការធ្វើឱ្យសំណើមានទម្រង់ស្តង់ដារ, accounting និងការត្រួតពិនិត្យសុវត្ថិភាព ត្រូវស្ថិតនៅទីនេះមុនពេល handoff ទៅ backend ណាមួយ។
- ប្រើ Bifrost ជា Tier-1 sidecar ដែលមាន throughput ខ្ពស់ និងត្រូវបានផ្តល់អាទិភាព នៅពេល deployment ត្រូវការភាពប្រែប្រួលនៃការកំណត់ផ្លូវទាបជាង ការប្តូរ provider ដែលគ្រប់គ្រងពីកណ្តាល ឬការពង្រីកទៅកាន់ OmniRoute replicas ច្រើន។
- រក្សា 9router និង CLIPROXYAPI ជាសេវាកម្ម compatibility ដែលបានបង្កប់។ ពួកវាដំណើរការជា local processes ដែលត្រូវបានត្រួតពិនិត្យ និងមានប្រយោជន៍នៅពេលឥរិយាបថ provider/CLI របស់ពួកវាគឺជា adapter ដែលចង់បាន ប៉ុន្តែពួកវាមិនគួរក្លាយជា Tier-1 routing engine លំនាំដើមទេ។
- កុំឱ្យ dashboard បញ្ជូន service URLs តាមអំពើចិត្តចូលក្នុង hot path។ URLs ដែលផ្តល់ដោយ UI គឺជា configuration inputs; routing code គួរតែដោះស្រាយ backends ដែលបានចុះបញ្ជី និងពិនិត្យសុខភាពរួច ពី server-side settings និង supervisor state។
- បច្ចុប្បន្ន គួរផ្តល់អាទិភាពដល់ loopback HTTP សម្រាប់សេវាកម្មដែលត្រូវបានត្រួតពិនិត្យ ពីព្រោះ managed processes បានផ្តល់ APIs ដែលឆបគ្នាជាមួយ HTTP រួចហើយ route guard អាចធ្វើសវនកម្មលើព្រំដែន ហើយឥរិយាបថ failure/fallback អាចមើលឃើញនៅក្នុង request logs។ SDK ឬ socket transport នាពេលអនាគត គួរបន្ថែមតែក្នុងករណីដែលវាកាត់បន្ថយ p99 routing latency បានជាក់ស្តែង ដោយមិនធ្វើឱ្យ isolation ឬ fallback semantics ចុះខ្សោយ។

ដូច្នេះ សម្រាប់ deployment ដែលមាន throughput ខ្ពស់ខ្លាំង ចម្លើយលំនាំដើមគឺ `auto` ដោយបើក Bifrost៖ ប្រើ Go sidecar នៅលើ hot path ខណៈពេលរក្សា TypeScript fallback ដើម្បីធានាអត្រាជោគជ័យ។ ប្រើ `bifrost` តែនៅពេលឥរិយាបថដែលប្រើតែ sidecar យ៉ាងតឹងរ៉ឹង សំខាន់ជាងការថយចុះសមត្ថភាពដោយរលូន។

## ការណែនាំសម្រាប់ throughput ខ្ពស់

សម្រាប់ RPM/RPS ខ្ពស់ជាបន្តបន្ទាប់ និង success SLO យ៉ាងតឹងរ៉ឹង៖

1. ប្រើ `auto` ជាមួយ cooldown ដែលសមស្រប និង telemetry សម្រាប់ failure។
2. រក្សាការផ្ទៀងផ្ទាត់ upstream និងការត្រួតពិនិត្យ API-key នៅព្រំដែន TypeScript route។
3. បើក headers/counters ឱ្យបានច្បាស់លាស់ ដើម្បីឱ្យប្រព័ន្ធជូនដំណឹងរបស់អ្នកអាចមើលឃើញប្រេកង់ និងមូលហេតុរបស់ fallback។
4. កំណត់ sidecar timeouts ឱ្យបរាជ័យឆាប់រហ័ស មិនមែនរង់ចាំជារៀងរហូតទេ។
5. រក្សាការ auto-restart សេវាកម្ម និង health telemetry loop ឱ្យមានសុខភាពល្អ ដើម្បីឱ្យ fallback ពិតជាករណីពិសេស។

## មូលដ្ឋានដែលបានណែនាំ

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- រក្សា API keys, allowlist, sanitizer និងការត្រួតពិនិត្យ rate-limit ឱ្យនៅបើកក្នុង route handlers (ពួកវាតែងតែដំណើរការមុនពេលបញ្ជូនបន្តទៅ downstream)។
- Export fallback metrics ពី reverse proxy និង request logs របស់អ្នក ដើម្បីឱ្យ sidecar outages អាចត្រូវបានមើលឃើញក្នុងរយៈពេលមួយនាទី។
