Pomocí tohoto průvodce zvolte pro pull request co nejmenší spolehlivý vývojový cyklus. Nenahrazuje
dokumenty o architektuře a zabezpečení pro konkrétní oblasti, na které jsou níže uvedeny odkazy;
propojuje jednotlivé běžné typy změn s jejich kontrakty, cílenými kontrolami a pokrytím v CI.

## Postup, kterým prochází každá změna

1. **Před zahájením úprav zvolte základní větev.** Najděte nejvyšší aktivní větev `release/v*` a
   vytvořte větev z jejího nejnovějšího commitu. Jako cílovou větev použijte tuto větev, nikoli
   `main`. Pokud je aktivní zmrazení vydání, necílujte na zmrazenou větev; použijte následující
   aktivní cyklus popsaný v dokumentu
   [Model větvení a vydávání](BRANCHING_MODEL.md).
2. **Určete kontrakty.** Identifikujte každý katalog, schéma, generovaný artefakt, veřejné API nebo
   uživatelské rozhraní, kterého se změna týká. Níže uvedená tabulka poskytuje minimální výchozí
   sadu.
3. **Napište nebo aktualizujte cílené testy.** Změny produkčního kódu v `src/`, `open-sse/`,
   `electron/` nebo `bin/` vyžadují automatizovaný test ve stejném PR. Spusťte nejmenší sadu
   testovacích souborů, která dané chování ověří, a poté uvedené cílené kontroly.
4. **Nechte CI spustit širokou matici.** V PR se spustí úplné jednotkové segmenty, Vitest, kontrola
   minimálního pokrytí a produkční sestavení. Širokou sadu testů spouštějte lokálně pouze tehdy,
   když cílené selhání poukazuje na širší dopad nebo když změna zasahuje několik subsystémů.
5. **Před kontrolou změny slaďte.** Načtěte aktivní základní větev, zkontrolujte její nové commity
   a rozdíl své větve vůči ní a poté podle pracovního postupu přispěvatelů proveďte rebase nebo
   sloučení základní větve. Konflikty v generovaných souborech a katalozích vyřešte v jejich zdroji,
   znovu je vygenerujte, opakujte cílený cyklus a potvrďte, že PR stále cílí na aktivní větev
   vydání.
6. **Zaznamenejte důkazy.** V šabloně PR uveďte spuštěné příkazy, všechny přidané nebo změněné
   testovací soubory, migrace nebo příznaky funkcí a veškeré dosud neprovedené ověření dostupné
   pouze v CI.

## Doporučené postupy podle typu změny

Níže uvedené příkazy představují minimální cílené kontroly, nikoli oprávnění vynechat test, který
přímo pokrývá změněné chování.

### Poskytovatel

**Kontrakty**

- Definice poskytovatele v `src/shared/constants/providers/` a její složení v
  `src/shared/constants/providers.ts`.
- Modely a možnosti v `open-sse/config/providerRegistry.ts` nebo v příslušných oddělených
  souborech registru.
- Výběr vykonavatele/překladače, konfigurace OAuth nebo klíče API, prostředky dashboardu a případně
  generovaná referenční dokumentace poskytovatelů.
- Veřejné přihlašovací údaje musí používat `resolvePublicCred()`; chybové odpovědi musí používat
  sdílené pomocné funkce pro sanitizaci chyb. Viz `docs/security/PUBLIC_CREDS.md` (git; nekompiluje
  se do `/docs`) a [Sanitizace chyb](../security/ERROR_SANITIZATION.md).

**Cílený cyklus**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # při změně katalogu; zahrňte vygenerovaný rozdíl do commitu
npm run lint
```

Otestujte také všechny dotčené skupiny požadavků: chat, Responses, obrázky, embeddingy, zvuk nebo
video. Rozdíly v generovaném katalogu a referenčních výstupech kontrolujte jako změny kontraktů;
nepřijímejte je bez kontroly.

### Směrování

**Kontrakty**

- Veřejné hodnoty strategií a metadata uživatelského rozhraní v
  `src/shared/constants/routingStrategies.ts`.
- Distribuce a řazení v `open-sse/services/combo.ts` a `open-sse/services/combo/`.
- Schémata combo, perzistence, stav odolnosti, možnosti modelů a ovládací prvky API/UI.
- [Modul Auto-Combo](../routing/AUTO-COMBO.md) a dokumentace odolnosti při změně chování.

**Cílený cyklus**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # změny strategie nebo distribuce
npm run check:known-symbols      # změny registrace strategie
npm run lint
```

Lokálně používejte deterministické testy s napodobeným upstreamem. Živé základní testy combo
vyžadují přihlašovací údaje a provádějí se ručně; nenahrazují testy CI.

### UI / UX

**Kontrakty**

- Hranice tras/stránek Next.js a sdílených komponent v `src/app/` a
  `src/shared/components/`.
- Tvary odpovědí API, stavy načítání/prázdného obsahu/chyb, chování klávesnice a čteček obrazovky,
  responzivní rozvržení, motivy a rozšíření lokalizací.
- Zdrojové anglické řetězce uživatelského rozhraní v `src/i18n/messages/en.json`; nové texty
  zobrazované uživatelům nevkládejte napevno do kódu.

**Cílený cyklus**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Při změnách interakcí nebo vizuálního vzhledu spusťte aplikaci a zkontrolujte úzké i široké
zobrazení. CI spouští produkční sestavení a širší sady testů; vizuální chování přesto vyžaduje
cílený test komponenty, test Playwright nebo zdokumentovanou ruční kontrolu odpovídající dané
změně.

### i18n

**Kontrakty**

- `src/i18n/messages/en.json` je zdrojem uživatelského rozhraní; `config/i18n.json` je zdrojem
  lokalizací.
- Katalogy CLI jsou uloženy samostatně v `bin/cli/locales/`.
- Zachovejte zástupné symboly a značky ICU přesně beze změny. Nepřekládejte názvy
  produktů/poskytovatelů/modelů, názvy protokolů a hlaviček, příkazy, identifikátory kódu/JSON,
  adresy URL, proměnné prostředí ani chráněné výrazy, jako jsou `OmniRoute`, `OAuth`, `MCP` a
  `A2A`. Aktuální zdrojový seznam se nachází v
  `scripts/i18n/glossary/protected-terms.json`.

**Cílený cyklus**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # při změně řetězců/katalogů CLI
npm run lint
```

Jde o pokyny pro stávající systém, nikoli o výzvu k rozšiřování jeho nástrojů nebo modelu klíčů.
Dokud se navrhuje náhradní systém, udržujte změny i18n přesně cílené. Nespouštějte překladové
příkazy, které volají externí služby, pokud úloha výslovně nevyžaduje generované překlady a pokud
jste nezkontrolovali výsledný rozdíl.

### CLI

**Kontrakty**

- Veřejné příkazy a příznaky v `bin/cli/`, generované příkazy API, návratové kódy, stdout/stderr a
  struktury výstupu JSON, chování konfigurace/prostředí a soubory zahrnuté v balíčku.
- Řetězce CLI určené uživatelům musí používat vrstvu i18n CLI a katalogy `en`/`pt-BR` musí zůstat synchronizované.
- Zachovejte Node jako podporované běhové prostředí a dodržujte kontrakt publikovaného binárního souboru.

**Cílený cyklus**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # změny generovaného/sbaleného CLI
npm run check:pack-policy     # změny veřejného rozhraní balíčku
npm run lint
```

Pokud chování závisí na parsování, souborech nebo návratovém stavu, použijte přesný příkaz v dočasném datovém adresáři.
CI provádí širší kontroly artefaktů balíčku a ekosystému.

### Databáze

**Kontrakty**

- Doménové moduly v `src/lib/db/`; konkrétní moduly importujte přímo (stará vrstva pro opětovný export `localDb.ts` byla odstraněna).
- Číslované, idempotentní migrace SQL v `src/lib/db/migrations/`, bezpečnost transakcí, chování při upgradu,
  indexy a všichni volající ovlivnění schématem.
- Trasy a obslužné rutiny nikdy nespouštějí nezpracované SQL přímo.

**Cílený cyklus**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Při přidávání migrace otestujte jak novou databázi, tak upgrade z předchozího schématu. Databázové testy
musí zavřít popisovače a během úklidu zavolat `resetDbInstance()`. Příkaz `npm run test:bun:db` spusťte pouze tehdy,
když se změní cesta adaptéru Bun poskytovaná bez záruky; rozhodující zůstává Node.

### Sestavení / nasazení

**Kontrakty**

- Kořenové manifesty a manifesty pracovních prostorů / lockfile, `scripts/build/`, samostatné sestavení Next.js, obsah balíčku
  `dist/`, metadata platforem Electron, pracovní postupy CI a kontrolní mechanismy nasazení.
- Podporované rozsahy verzí Node a použití Bun ze seznamu povolených výjimek v `CLAUDE.md` musí zůstat zachovány.
- Artefakty sestavení zůstávají nesledované; platí zásady pro závislosti, licence, pracovní postupy a balíčky.

**Cílený cyklus**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # změny závislostí nebo lockfile
npm run check:pack-policy      # změny veřejného rozhraní publikovaného balíčku
npm run lint
```

Příkaz `npm run build` používejte lokálně pouze tehdy, když změna ovlivňuje kompilaci, samostatné sestavení, assety
nebo přibalení běhového prostředí. Příkaz `npm run build:release` používejte pouze k ověření vydání/nasazení. Sestavení v CI je
konečným signálem napříč platformami; změny Electron specifické pro určitou platformu vyžadují odpovídající cílené sestavení
nebo doklad z rychlého ověřovacího testu.

## Lokální smyčka versus CI

| Spouštět lokálně pro každou úpravu                                                | CI poskytuje širší zpětnou vazbu                                                   |
| --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Přímé testy chování a výše uvedené kontroly kategorií                             | Úplná sada jednotkových testů rozdělená do částí a sériové testy                   |
| `npm run lint`                                                                    | Sady Vitest a postupně zpřísňované požadavky na pokrytí a kvalitu                  |
| Kontrola typů nebo sestavení pouze tehdy, když to vyžaduje dotčený kontrakt       | Produkční sestavení a kontroly zabezpečení, dokumentace, závislostí a zásad pro PR |
| Ruční interakce/živé kontroly pouze tehdy, když chování nelze ověřit automatizací | Kontroly integrace mezi úlohami a platforem nakonfigurované pracovním postupem     |

Úspěšná cílená smyčka je dokladem o změněném kontraktu, nikoli důkazem, že projdou nesouvisející kontroly CI.
Naopak nenechávejte každou lokální úpravu čekat na dokončení celé matice repozitáře.

## Kontrolní seznam pro sladění změn

Před požádáním o kontrolu:

- Ověřte, že základem PR je stále nejvyšší aktivní větev `release/v*`.
- Načtěte tento základ a zkontrolujte commity, které byly začleněny od vytvoření vaší větve.
- Zkontrolujte `git diff <active-base>...HEAD`, zda neobsahuje neúmyslné nebo generované změny.
- Konflikty v katalogu a generované dokumentaci vyřešte aktualizací zdroje a opětovným vygenerováním výstupu.
- Po sladění změn znovu spusťte všechny cílené testy/kontroly uvedené v popisu PR.
- Nikdy neoslabujte aserce ani neodstraňujte povinné testy pouze kvůli přizpůsobení posunutému základu.

Pravidla pro zmrazení vydání a změnu cílové větve najdete v dokumentu
[Model větvení a vydávání](BRANCHING_MODEL.md). Úplný přehled CI najdete v dokumentu
[Referenční přehled kontrol kvality](../architecture/QUALITY_GATES.md).
