## Shrnutí

OmniRoute nyní podporuje tři režimy předávání pro `/api/v1/relay/chat/completions`:

- `ts`: Použije zpracování v TypeScriptu v rámci procesu.
- `bifrost`: Vynutí použití brány Bifrost.
- `auto`: Upřednostní Bifrost, pokud je dostupný, a při selhání přejde na TypeScript.

Při vysoké frekvenci požadavků (velké množství tokenů za den, téměř konstantní propustnost) je nejlepší strategií zachovat záložní cestu explicitní a rychlou, aby se kritická cesta nikdy nezablokovala kvůli nefunkčnímu sidecaru.

## Chování režimů

- `ts`
  - Nejnižší provozní složitost.
  - Veškeré směrování a ověřování probíhá v Node.
  - Dostupnost není závislá na sidecaru.
- `bifrost`
  - Vynutí směrování všech požadavků přes bránu sidecaru.
  - Bez automatického přechodu na záložní řešení.
  - Užitečné pouze tehdy, když je zaručen stav a latence sidecaru.
- `auto`
  - Sidecar se použije, pokud je dostupný a povolený.
  - Neúspěšné pokusy aktivují hlavičky informující o přechodu na záložní řešení a vrátí provoz do TS, aby doba úspěšného vyřízení požadavku zůstala omezená.
  - Tento režim je nejbezpečnější volbou pro produkční prostředí, pokud je dostupnost důležitější než striktní směrování výhradně přes sidecar.

## Aktuální stav 9router a CLIPROXYAPI

9router a CLIPROXYAPI jsou integrace, které historicky poskytovaly cesty kompatibility pro upstream poskytovatele.

- 9router je vestavěná cesta pro orchestraci upstreamů a zajištění kompatibility.
- CLIPROXYAPI je proxy API most pro provoz ve stylu CLI / SDK.
- Bifrost se stabilizuje jako externí cesta pro případy, kdy potřebujete samostatný mezikrok podobný sidecaru a lokální směrování s nízkou latencí.

Pokud aktuálně porovnáváte 9router/CLIPROXYAPI:

- Před předáním zachovejte podepisování požadavků, kontroly seznamu povolených položek a brány zásad databáze v API trase.
- Pokud pracovní postup vyžaduje striktní chování sidecaru a nižší variabilitu jednotlivých požadavků, použijte `OMNIROUTE_RELAY_BACKEND=bifrost`.
- Pokud potřebujete odolnost sidecaru s plynulou degradací během incidentů, použijte `OMNIROUTE_RELAY_BACKEND=auto`.

## Kontrakt hranice backendu

Stabilní hranicí produktu je předávací API OmniRoute, nikoli implementace řídicího panelu. Řídicí panel Next.js může instalovat, konfigurovat a monitorovat lokální služby, ale směrování požadavků by mělo vstupovat přes předávací API a za touto hranicí se předat dál.

Dlouhodobé možnosti backendu:

- Zachovejte zpracování v TypeScriptu jako cestu pro zásady a záložní řešení v rámci procesu. Ověřování identity, seznamy povolených položek, normalizace požadavků, účtování a bezpečnostní kontroly zůstávají před jakýmkoli předáním backendu zde.
- Používejte Bifrost jako preferovaný sidecar úrovně Tier-1 s vysokou propustností, pokud nasazení vyžaduje nižší variabilitu směrování, centralizované střídání poskytovatelů nebo škálování napříč více replikami OmniRoute.
- Zachovejte 9router a CLIPROXYAPI jako vestavěné služby kompatibility. Běží jako monitorované lokální procesy a jsou užitečné, pokud je jejich chování poskytovatele/CLI požadovaným adaptérem, neměly by se však stát výchozím směrovacím modulem úrovně Tier-1.
- Nedovolte řídicímu panelu předávat do kritické cesty libovolné adresy URL služeb. Adresy URL poskytnuté uživatelským rozhraním jsou konfigurační vstupy; směrovací kód by měl z nastavení na straně serveru a ze stavu správce procesů načítat registrované backendy s ověřeným stavem.
- Pro monitorované služby v současnosti upřednostňujte HTTP přes loopback, protože spravované procesy již poskytují API kompatibilní s HTTP, ochrana trasy může tuto hranici auditovat a chování při selhání nebo přechodu na záložní řešení je viditelné v protokolech požadavků. Přidání budoucího přenosu přes SDK nebo socket má smysl pouze tehdy, pokud měřitelně sníží latenci směrování p99, aniž by oslabilo izolaci nebo sémantiku přechodu na záložní řešení.

Pro nasazení s velmi vysokou propustností je proto výchozí volbou `auto` s povoleným Bifrostem: na kritické cestě používejte sidecar v Go a současně zachovejte záložní řešení v TypeScriptu pro zajištění vysoké úspěšnosti. Režim `bifrost` používejte pouze tehdy, když je striktní provoz výhradně přes sidecar důležitější než plynulá degradace.

## Doporučení pro vysokou propustnost

Pro trvale vysoké RPM/RPS a striktní SLO úspěšnosti:

1. Používejte `auto` s prakticky nastavenou dobou blokování po selhání a telemetrií selhání.
2. Zachovejte upstream ověřování a kontroly API klíčů na hranici trasy v TypeScriptu.
3. Povolte explicitní hlavičky/čítače, aby váš výstražný systém sledoval četnost a důvody přechodů na záložní řešení.
4. Nastavte časové limity sidecaru tak, aby selhal rychle a nečekal donekonečna.
5. Udržujte automatické restartování služby a smyčku telemetrie stavu funkční, aby byl přechod na záložní řešení skutečně výjimečný.

## Doporučené výchozí nastavení

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- V obslužných rutinách tras ponechte povolené API klíče, seznam povolených položek, sanitizer a kontroly limitu požadavků (spouštějí se vždy před předáním dále).
- Exportujte metriky přechodu na záložní řešení z reverzní proxy a protokolů požadavků, aby byly výpadky sidecaru viditelné do jedné minuty.
