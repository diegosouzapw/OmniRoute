`open-sse/config/providerPluginManifest.ts` definuje kontrakt pluginu poskytovatele bezpečný pro JSON.
`open-sse/config/providerPluginManifestRegistry.ts` propojuje tento kontrakt
s aktuálním registrem poskytovatelů pro sidecary, jako jsou Bifrost,
CLIProxyAPI nebo budoucí router v Go/Rust. Registr v TypeScriptu zůstává
zdrojem pravdy, ale sidecary mohou manifest používat bez importování
kódu executorů, výchozích hodnot OAuth, hlaviček nebo stavu prostředí procesu.

Stejný manifest je dostupný také přes HTTP na adrese
`GET /api/v1/provider-plugin-manifest` pro sidecary, které běží mimo proces.

OmniRoute oznamuje tuto URL systémům Bifrost a CLIProxyAPI prostřednictvím
hlavičky požadavku `X-OmniRoute-Provider-Manifest-Url`. Nastavte
`OMNIROUTE_PROVIDER_MANIFEST_URL`, pokud sidecar potřebuje veřejnou URL nebo URL
kontejnerové sítě namísto místního původu požadavku.

## Aktualizace manifestu

Koncový bod HTTP vrací `Cache-Control: public, max-age=60` a silný
`ETag`. Sidecar by měl uchovat poslední ověřený manifest a při aktualizaci odeslat
jeho ETag v `If-None-Match`. Odpověď `304 Not Modified` nemá tělo;
sidecar si ponechá manifest uložený v mezipaměti. Pokud neexistuje žádný ověřený
manifest v mezipaměti, musí sidecar namísto přijetí odpovědi `304` odeslat
bezpodmínečný požadavek.

## Cíl

Posunout metadata poskytovatelů směrem ke kontraktu pluginu, aby kritickou cestu
požadavků mohl nakonec obsluhovat sidecar s nižší latencí, zatímco OmniRoute
zachová trasu v TypeScriptu jako bránu pro uplatňování zásad a záložní řešení.
Manifest je pouze doplňkový: sám o sobě směrování požadavků nemění.

## Kontrakt

Manifest obsahuje:

- ID a alias poskytovatele
- upstreamový formát a název executoru
- typ autentizace, autentizační hlavičku a volitelný prefix autentizace
- statická metadata koncového bodu
- způsobilost pro sidecar a explicitní důvody, proč by měl poskytovatel zůstat na cestě TS
- metadata modelu bezpečná pro JSON, například délku kontextu, příznaky podpory obrazu/uvažování a
  nepodporované parametry
- značky schopností včetně `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` a `usage-supported`

Manifest záměrně vylučuje:

- klientská tajemství OAuth a výchozí tajné hodnoty
- vyhodnocování běhového prostředí
- hlavičky požadavků a veřejné pomocné funkce pro přihlašovací údaje
- dynamické generátory URL
- funkce executorů
- interní části fondu relací

## Značky schopností

`capabilities` je seřazené pole značek odvozených ze záznamu v registru. Integrátoři
by jej měli považovat za strojově čitelnou odpověď na otázku „co tento poskytovatel umí“,
namísto opětovného procházení zdrojových kódů v TypeScriptu.

| Značka               | Význam                                                                       |
| -------------------- | ---------------------------------------------------------------------------- |
| `apikey`             | Přijímá klíč API (`authType` je `apikey` nebo `optional`).                   |
| `oauth`              | Používá tok OAuth nebo relace.                                               |
| `responses`          | Zpřístupňuje základní URL rozhraní OpenAI Responses API.                     |
| `passthrough-models` | Poskytuje modely přímo z upstreamu namísto statického katalogu.              |
| `custom-executor`    | Spouští jiný než výchozí executor, takže zůstává na cestě TypeScriptu.       |
| `sidecar-candidate`  | Odráží `sidecar.eligible` — lze jej bezpečně zvážit pro import do sidecaru.  |
| `usage-fetch`        | Má zapojený mechanismus načítání využití nebo kvóty (`getUsageForProvider`). |
| `usage-supported`    | API pro využití přijímá tohoto poskytovatele (`isSupportedUsageConnection`). |

`usage-fetch` slouží pouze ke zjišťování. Oznamuje, že OmniRoute umí načíst údaje o využití
poskytovatele; neaktivuje načítání, nemění sémantiku kvót ani neznamená, že je
widget kvóty na Dashboardu pro daného poskytovatele povolen — tento widget je samostatně řízen
pomocí `USAGE_SUPPORTED_PROVIDERS`. Zdrojem pravdy je `USAGE_FETCHER_PROVIDERS` v
`open-sse/services/usage/fetcherProviders.ts`.

Tento seznam používá jako klíče řetězce přijímané dispečerem využití, takže kombinuje kanonická ID
s aliasy a je o něco delší než počet označených poskytovatelů: položky, které
nejsou poskytovateli chatu v registru manifestu (například poskytovatel vyhledávání `firecrawl`
a poskytovatel ACP `amazon-q`), nemají žádnou položku manifestu, kterou by bylo možné označit.

`usage-supported` odpovídá na otázku, zda serverové trasy a trasy využití Dashboardu přijímají připojení
pro daného poskytovatele. Odráží `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
a `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), přičemž obě funkce jsou řízeny
pomocí `USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). Na rozdíl od
`usage-fetch` se vydává pouze pro ID poskytovatele — běhová kontrola provádí
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` bez vyhodnocování aliasů, takže manifest
zachovává stejné pravidlo. Tyto dvě značky mají odlišný rozsah: 3 poskytovatelé nesou pouze
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) a 1 nese pouze
`usage-supported` (`xiaomi-mimo-token-plan`), takže jedna značku druhou neimplikuje.

## Použití sidecaru

Sidecary by měly považovat `sidecar.eligible` za konzervativní signál kandidáta, nikoli za bezpodmínečné rozhodnutí o směrování. Prvním cílem importu by měli být poskytovatelé používající API klíč, statický koncový bod a výchozí executor. Poskytovatelé s vlastními webovými executory, postupy OAuth/relací, dynamickými generátory URL nebo konfigurací poolu zůstávají na záložní cestě TypeScriptu, dokud sidecar neimplementuje ekvivalentní chování a telemetrie nepotvrdí paritu.

Navrhované fáze migrace:

1. Vygenerovat a ověřit manifest pluginů poskytovatelů z registru TS.
2. Naučit Bifrost nebo CLIProxyAPI importovat manifest pro poskytovatele používající API klíč a statický koncový bod.
3. Směrovat způsobilé poskytovatele přes sidecar za `OMNIROUTE_RELAY_BACKEND` a zároveň ponechat aktivní záložní cestu TS.
4. Povýšit poskytovatele pouze tehdy, když míra úspěšnosti, latence p99, chování streamování a zpracování nepodporovaných parametrů odpovídají cestě TS.
5. Přidávat nativní pluginy sidecaru pro vlastní executory postupně, vždy pro jednu rodinu poskytovatelů.

## Proč nevkládat poskytovatele přímo do Nextu

Frontend Nextu by neměl zajišťovat provádění požadavků na poskytovatele. Měl by volat rozhraní API. Backend pak může rozhodnout, zda použije executor TypeScriptu, Bifrost, CLIProxyAPI, nebo budoucí nativní sidecar. Díky tomu zůstávají podepisování požadavků, kontroly seznamu povolených položek, zásady databáze a záložní chování centralizované před jakýmkoli předáním sidecaru.
