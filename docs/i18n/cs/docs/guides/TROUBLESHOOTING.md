## Rychlý přehled

**Začínáte s OmniRoute?** Začněte zde — toto řeší 90 % problémů:

| Zobrazuje se mi                 | Co to znamená                                 | Co dělat                                                                                                    |
| ------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| „Nelze se připojit“             | OmniRoute není spuštěný                       | Spusťte `omniroute` nebo `docker restart omniroute`                                                         |
| „Neplatný klíč API“             | Váš klíč je nesprávný nebo vypršel            | Zkopírujte klíč znovu z webu poskytovatele                                                                  |
| „Překročen limit požadavků“     | Odesíláte příliš mnoho požadavků              | Počkejte 1 minutu nebo použijte `model: "auto"` pro automatické záložní přepnutí                            |
| „Překročena kvóta“              | Vyčerpali jste bezplatnou či placenou kvótu   | Připojte další poskytovatele nebo použijte bezplatné poskytovatele (Kiro, Pollinations)                     |
| „Pomalé odpovědi“               | Poskytovatel je vytížený nebo příliš vzdálený | Použijte `model: "auto/fast"` nebo připojte rychlejšího poskytovatele (Groq, Cerebras)                      |
| „Použit nesprávný poskytovatel“ | `auto` vybralo jiného poskytovatele           | To je normální! `auto` vybírá nejlepšího. Konkrétního poskytovatele vynuťte pomocí `model: "openai/gpt-4o"` |
| „502 Bad Gateway“               | Poskytovatel má výpadek                       | Počkejte a zkuste to znovu nebo použijte `model: "auto"` k přepnutí poskytovatele                           |
| „401 Unauthorized“              | Vaše přihlašovací údaje jsou nesprávné        | Zkontrolujte klíč API nebo se znovu ověřte pomocí OAuth                                                     |
| „429 Too Many Requests“         | Byl uplatněn limit požadavků                  | Počkejte 1 minutu nebo připojte další poskytovatele                                                         |

**Stále se vám nedaří problém vyřešit?** Podívejte se níže na [podrobné řešení problémů](#podrobné-řešení-problémů) nebo se zeptejte na [Discordu](https://discord.gg/U47eFqAXCn).

## Podrobné řešení problémů

---

### Omezování požadavků u bezplatných poskytovatelů (429 / 400 / 401)

**Příznak**: Při použití `model: "auto"` s bezplatnými poskytovateli nebo poskytovateli bez ověřování (opencode, auggie atd.) se místo odpovědí občas zobrazí `HTTP 429`, `400` nebo `401`. Když stejný dotaz o chvíli později zopakujete, požadavek uspěje, ale automatizace (úlohy cron, agenti, skripty) se při prvním selhání přeruší.

**Hlavní příčina**: Souběh tří nezávislých režimů selhání:

1. **Limit požadavků poskytovatele (`429`)**: Bezplatné tarify mohou vynucovat kvótu pro určité časové okno. Dávka souběžných volání ji vyčerpá, takže další požadavek je odmítnut, dokud se okno neobnoví.
2. **Nefunkční model při přímém předávání (`400`/`401`)**: Fondy `auto/*` mohou obsahovat přímo předávané modely od `opencode`, které jsou zaregistrované v katalogu, ale nemají platné přihlašovací údaje (např. `oc/north-mini-code-free` → `401`). Automatický směrovač jeden z nich vyzkouší, selže a chyba se rozšíří dříve, než dojde k záložnímu přepnutí.
3. **Zesílení souběžností (`429` při zatížení)**: Když `auto` současně využívá více relací agentů nebo úloh cron, souhrnná rychlost požadavků překročí míru tolerovanou bezplatnými poskytovateli, takže jsou legitimní volání označena jako zneužívající.

**Ověřené řešení (nahlášené komunitou, 2026-08-10)**: nastavte tři proměnné prostředí tak, aby rotace, souběžnost a záložní přepnutí absorbovaly nestabilitu bezplatných tarifů namísto toho, aby kvůli ní selhaly:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # při 400/401 přejít na jiný model či poskytovatele (přeskočí nefunkční přímo předávané modely)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # explicitní limit přijímání náročných požadavků (ve výchozím nastavení nenastaven: bez limitu počtu požadavků, viz poznámka níže)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # delší omezené čekání na kapacitu pro náročné požadavky namísto okamžité opakovatelné chyby 503
```

Nastavte je v prostředí procesu OmniRoute (démona, například prostřednictvím souboru plist LaunchAgent nebo `systemctl edit`) a poté OmniRoute restartujte. Příznak rotace má ze všech nastavení největší účinek: převede úplné selhání na transparentní opakování požadavku u funkčního poskytovatele ve fondu.

**Poznámka**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` omezuje počet souběžně zpracovávaných náročných požadavků s dlouhým kontextem; toto omezení představuje vstupní bránu, nikoli omezovač rychlosti požadavků poskytovatele. **Aktualizace k řetězení chyb #503:** tato proměnná již není nastavena ve výchozím nastavení (nyní se použije pouze tehdy, když je explicitně nakonfigurována jako výše) — přijímání náročných požadavků je namísto toho řízeno automaticky odvozeným rozpočtem v bajtech (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), který se přizpůsobuje skutečnému limitu paměti hostitele. Nové nasazení by proto mělo zaznamenat podstatně méně odmítnutí `503 chat_admission_busy`, aniž by bylo nutné tuto proměnnou vůbec nastavovat; její explicitní nastavení zde stále funguje přesně tak, jak je popsáno. Explicitní přepsání rozpočtu v bajtech je omezeno na 8 MiB–2 GiB. Chyba `413 body_exceeds_budget` není dočasná: zvyšte daný rozpočet v bajtech, snižte `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` nebo zvyšte limit paměti procesu. Odmítnutí `inflight_bytes_budget` znamená dočasné soupeření o prostředky a požadavek lze nadále opakovat. Omezení rychlosti pro jednotlivé poskytovatele (`open-sse/services/rateLimitManager.ts`) je samostatně řízeno proměnnými `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` a `RATE_LIMIT_AUTO_ENABLE` — viz `.env.example`.

**Jak ověřit, že řešení funguje**: spusťte svého agenta nebo úlohu cron dvakrát rychle po sobě a ověřte, že obě spuštění uspějí. Před opravou druhé spuštění obvykle vyvolá chybu `429`/`401`. Po opravě jsou selhání (pokud nějaká nastanou) transparentně opakována a volání se dokončí. Můžete také zavolat `curl /monitoring/health` a sledovat pole `rateLimitedUntil` u připojení poskytovatelů a `circuitBreakers.providerBreakers[].state` u dotčených poskytovatelů — stav je jedním z `CLOSED`, `DEGRADED`, `OPEN` nebo `HALF_OPEN` (viz `src/shared/utils/circuitBreaker.ts`) a poskytovatel, který opakovaně selhává, přejde ze stavu `CLOSED → DEGRADED → OPEN`, než okno pro obnovení umožní průchod kontrolnímu požadavku (`HALF_OPEN`).

**Pokud se vám stále zobrazuje chyba 429**: aktivní účet daného poskytovatele skutečně vyčerpal svou _kvótu_ (nejde jen o omezení frekvence požadavků). Přidejte druhý účet stejného poskytovatele na řídicím panelu OmniRoute → Providers → Accounts nebo zapojte jiného bezplatného poskytovatele (např. `routeway`, `auggie`). Rotace pomáhá pouze s dočasnými chybami omezení frekvence požadavků/400/401; úplné vyčerpání kvóty vyžaduje druhé přihlašovací údaje nebo jiného poskytovatele.

**Pokud se vám u modelů pro zpracování obrazu (`auto/vision`, `bazaarlink/*`) zobrazuje chyba 403**: připojený účet nemá placený tarif zahrnující zpracování obrazu nebo API klíč nemá dostatečná oprávnění. Na řídicím panelu poskytovatele ověřte, že rozsah oprávnění klíče zahrnuje zpracování obrazu / multimodální funkce, nebo připojte účet s placeným tarifem a ponechte jej jako cílový účet pro zpracování obrazu.

## Varování při npm install (ERESOLVE / peer / deprecated)

Při spuštění `npm install -g omniroute` se může zobrazit záplava varování, například `npm warn ERESOLVE`, upozornění na partnerské závislosti a zprávy `deprecated`. **Tato varování jsou očekávaná a neškodná.** Instalace proběhla úspěšně, pokud se ve výstupu zobrazí `added <N> packages`.

Chcete-li potlačit varování při řešení partnerských závislostí, použijte podporovaný způsob instalace OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` potlačí pouze upozornění `ERESOLVE` a upozornění na partnerské závislosti. Upozornění na zastaralé balíčky zůstanou viditelná, protože pocházejí z tranzitivních balíčků třetích stran; neznamenají, že instalace selhala.

Varování pocházejí ze zastaralých rozsahů partnerských závislostí v balíčcích třetích stran, které OmniRoute nemůže ovlivnit:

1. **`marked-terminal` vyžaduje `marked >=1 <16`, ale byla nalezena verze `marked@18`** — v praxi funguje bez problémů; rozsah partnerské závislosti v upstream balíčku je pouze zastaralý.
2. **`deprecated prebuild-install@7.1.3`** — tranzitivní pomocný nástroj pro načítání nativních binárních souborů. Nepoužívá se
   k instalaci připnuté transportní vazby `wreq-js` a neznamená, že nastavení transportu poskytovatele
   webových cookies selhalo.

**Není nutná žádná akce** — bez vytvoření vlastních forků upstream balíčků nelze tato varování zcela potlačit.

## Rychlá řešení

| Problém                                                    | Řešení                                                                                                                                                                      |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| První přihlášení nefunguje                                 | Nastavte `INITIAL_PASSWORD` v `.env` (žádná výchozí hodnota není pevně zakódována)                                                                                          |
| Ovládací panel se otevírá na nesprávném portu              | Nastavte `PORT=20128` a `NEXT_PUBLIC_BASE_URL=http://localhost:20128`                                                                                                       |

## Falešné poplachy antiviru

<a name="antivirus-false-positives"></a>

### Avast/AVG přesouvá `README.md` do karantény s detekcí `MD:HttpRequest-inf[Susp]`

**Jedná se o falešný poplach. Nic není infikováno a není třeba provádět žádnou akci.**

Avast a AVG používají heuristiku, která označuje prosté textové soubory nebo soubory Markdown obsahující mnoho
odkazů připomínajících HTTP požadavky. Soubor `README.md` projektu OmniRoute je součástí npm balíčku (je
uveden v `package.json` → `files`), takže při globální instalaci skončí v
`node_modules/omniroute/README.md` — a obsahuje přibližně 15 příkladů `http://localhost:20128/...` (koncové
body MCP HTTP/SSE, adresu URL A2A `.well-known` a ukázky použití `curl`). Tato hustota odkazů
stačí ke spuštění heuristiky.

Pokud k tomu začalo docházet teprve nedávno: povaha souboru se nezměnila. V README se rozšířila
tabulka koncových bodů (byly přidány MCP HTTP + SSE + A2A) a přibyly další příklady `curl`, čímž
soubor překročil prahovou hodnotu.

Soubor je neaktivní dokumentace bez jakéhokoli spustitelného obsahu. Můžete jej bezpečně obnovit
z karantény.

**Co dělat:**

1. **Zastavte oznámení** — přidejte instalační adresář do výjimek antiviru
   (Avast: Nastavení → Výjimky), konkrétně globální cestu k `node_modules` a/nebo datový
   adresář OmniRoute (`~/.omniroute/`).
2. **Nahlaste falešný poplach** — <https://www.avast.com/false-positive-file-form.php>,
   přičemž přiložte soubor `README.md` z karantény. Toto řešení pomůže všem, protože se jedná
   o přehnanou reakci heuristiky výrobce na textový soubor.

**Proč to „neopravujeme“ na naší straně:** všechny příklady používají `http://localhost` a
localhost nemůže používat `https` bez komplikací se sebou podepsanými certifikáty. Znehodnocení
dokumentace kvůli obejití heuristiky jednoho výrobce by poškodilo všechny čtenáře jen kvůli chybě
skeneru.

### Kaspersky označuje desktopovou aplikaci jako `PDM:Trojan.Win32.Generic`

**Jedná se o falešný poplach behaviorální heuristiky. Nic není infikováno.** Předpona
`PDM:` společnosti Kaspersky znamená, že verdikt pochází z jejího modulu Proactive Defense Module (System Watcher),
který posuzuje, co instalátor _dělá_, namísto porovnávání se známým malwarem. Když
se detekce spustí, Kaspersky „vrátí zpět“ celou instalaci — odstraní soubory, které již
zapsal — takže aplikace nakonec nefunguje nebo zcela chybí.

Označené soubory jsou standardními součástmi deklarovaných open-source závislostí přibalených
k desktopové aplikaci, například:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` a
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), knihovna pro automatizaci
  prohlížeče používaná k přihlašování k poskytovatelům přímo v aplikaci a ke konverzacím využívajícím prohlížeč.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — připnutá nativní vazba `wreq-js` používaná pro HTTP s otiskem prohlížeče u poskytovatelů
  využívajících webové cookies (`<arch>` je `x64` nebo `arm64`).

**Proč se detekce spouští:** instalátor pro Windows **zatím není digitálně podepsán**, takže nepodepsaný instalátor NSIS
nemá žádnou reputaci a behaviorální heuristiky pracují s maximální agresivitou. V kombinaci
s přibalenou nativní knihovnou DLL a stovkami souborů `.js` zapisovaných do
`%LOCALAPPDATA%\Programs\OmniRoute` (včetně adresářů balíčků s příponami tvořenými hashem ze
samostatného sestavení Next.js) to stačí ke spuštění heuristiky. Podepisování kódu je plánováno;
dokud nebude zavedeno, může se problém opakovat u každé nové verze.

**Co dělat:**

1. **Nejprve ověřte stažený soubor** (tím vyloučíte, že byl pozměněn). Každé vydání obsahuje
   `latest.yml`, jehož pole `sha512` (base64) pokrývá instalátor
   `OmniRoute.Setup.<version>.exe`. V PowerShellu spusťte ve složce obsahující instalátor:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Výstup se musí shodovat s hodnotou `latest.yml` → `sha512`. Pokud se neshoduje, soubor
   odstraňte a stáhněte jej znovu výhradně ze [stránky vydání na GitHubu](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Obnovte soubory a přidejte výjimku** — obnovte položky odstraněné při vrácení instalace z karantény a přidejte výjimku
   pro `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Nastavení → Hrozby a výjimky),
   poté aplikaci znovu nainstalujte.
3. **Nahlaste falešný poplach** — <https://opentip.kaspersky.com/>. Hlášení falešných poplachů
   odeslaná uživateli skutečně urychlují přidání na seznam povolených položek.

## Kompatibilita s Node.js

<a name="nodejs-compatibility"></a>

### Přihlašovací stránka padá nebo zobrazuje chybu „Module self-registration“

**Příčina:** Používáte verzi Node.js mimo schválený bezpečný rozsah běhového prostředí OmniRoute. Nejčastěji jde o použití starší dílčí verze Node 22 nebo 24, která je nižší než opravená minimální bezpečná verze vyžadovaná OmniRoute.

**Příznaky:**

- Přihlašovací stránka zobrazuje prázdnou obrazovku nebo chybu serveru
- Konzole zobrazuje `Error: Module did not self-register` nebo podobné chyby nativních vazeb
- Pokud běhové prostředí nevyhovuje podporovaným bezpečnostním zásadám, přihlašovací stránka zobrazuje **oranžový výstražný banner** s vaší verzí Node

**Řešení:**

1. Nainstalujte podporovanou verzi Node.js LTS (doporučeno: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Ověřte svou verzi: `node --version` by měl na řadě 24.x LTS zobrazit `v24.0.0` nebo novější
3. Znovu nainstalujte OmniRoute: `npm install -g omniroute`
4. Restartujte aplikaci: `omniroute`

> **Podporované bezpečné verze:** `>=22.22.2 <23` nebo `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) a Node.js 26 jsou plně podporovány.

### npm v11+: `better-sqlite3` není nainstalován (modul nelze najít)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Příčina:** npm v11 (dodávaný s Node.js 24+) ve výchozím nastavení blokuje instalační skripty volitelných
závislostí. Protože je `better-sqlite3` uveden v `optionalDependencies`
a vyžaduje nativní kompilaci (`node-gyp rebuild`), npm jej bez upozornění přeskočí.

**Příznaky:**

- Server při spuštění spadne s chybou `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` zobrazí „No such file or directory“
- `npm ls better-sqlite3` zobrazí `(empty)`

**Řešení:**

1. Povolte instalační skripty a proveďte instalaci znovu:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Nebo předem sestavený balíček nainstalujte ručně:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Ověřte jeho funkčnost: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file“

<a name="macos-native-module-rebuild"></a>

**Příčina:** Po globálním spuštění `npm install -g omniroute` mohl být nativní binární soubor `better-sqlite3` uvnitř balíčku zkompilován pro jinou architekturu nebo ABI Node.js, než jaké se používají lokálně. To je běžné v systému macOS (na Apple Silicon i Intel), pokud předem sestavený binární soubor neodpovídá vašemu prostředí.

**Příznaky:**

- Server při spuštění okamžitě selže s chybou `dlopen`
- Chyba obsahuje `slice is not valid mach-o file`
- Úplný příklad:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Řešení — sestavte modul znovu pro své lokální prostředí (není nutný downgrade Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Poznámka:** Tím se nativní vazba znovu zkompiluje pro vaši lokální verzi Node.js a architekturu procesoru, čímž se vyřeší nesoulad binárních souborů. Oficiálně podporovaný rozsah běhového prostředí je **`>=22.22.2 <23` nebo `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` v `src/shared/utils/nodeRuntimeSupport.ts`, v souladu s polem `engines` v `package.json`). Node.js 24.x LTS (Krypton) a Node.js 26 jsou s `better-sqlite3` v12.x plně podporovány.

## Problémy s proxy

<a name="proxy-issues"></a>

### Ověření poskytovatele zobrazuje „fetch failed“

**Příčina:** Koncový bod pro ověření API klíče (`POST /api/providers/validate`) dříve obcházel konfiguraci proxy, což způsobovalo selhání v prostředích, která vyžadují směrování přes proxy.

**Oprava (v3.5.5+):** Problém je nyní opraven. Ověření poskytovatele je směrováno přes `runWithProxyContext` a automaticky respektuje globální nastavení proxy i nastavení na úrovni poskytovatele.

### Kontrola stavu tokenu selhává s chybou „fetch failed“

**Příčina:** Obnovení OAuth tokenu na pozadí neurčovalo konfiguraci proxy pro jednotlivá připojení.

**Oprava (v3.5.5+):** Plánovač kontroly stavu tokenů nyní před pokusem o obnovení určí konfiguraci proxy pro každé připojení. Aktualizujte na v3.5.5+.

### SOCKS5 proxy vrací chybu „invalid onRequestStart method“

**Příčina:** V Node.js 22 není dispatcher z undici@8 kompatibilní s vestavěnou implementací `fetch()` v Node.js.

**Oprava (v3.5.5+):** Když je aktivní proxy dispatcher, OmniRoute nyní používá vlastní funkci `fetch()` z undici, čímž zajišťuje konzistentní chování. Aktualizujte na v3.5.5+.

### MITM proxy ve WSL: desktopové aplikace v hostitelském systému Windows nejsou zachycovány

**Příčina:** MITM proxy a její certifikát CA se instalují do prostředí, ve kterém běží OmniRoute. Ve WSL je tímto prostředím linuxový host, zatímco desktopové AI aplikace (Kiro, Trae, Copilot, Zed, …) běží v hostitelském systému Windows. Hostitelské aplikace nedůvěřují úložišti certifikátů hosta a nesměrují provoz přes systémovou proxy hosta, takže u nich k zachytávání desktopového provozu nedochází.

**Doporučení:** Spusťte OmniRoute nativně ve stejném operačním systému jako desktopové aplikace, jejichž provoz chcete zachytávat (Windows pro aplikace ve Windows; obdobně pro macOS/Linux). Pokud ponecháte OmniRoute ve WSL a chcete zachytávat provoz hostitelských aplikací, musíte ručně nastavit důvěryhodnost vygenerovaného certifikátu CA v hostitelském systému Windows a nasměrovat síťová/proxy nastavení každé hostitelské aplikace na koncový bod proxy ve WSL — jde o nepodporované a nespolehlivé řešení.

## Problémy s cloudem

### Chyby synchronizace s cloudem

1. Ověřte, že `BASE_URL` odkazuje na vaši spuštěnou instanci (např. `http://localhost:20128`)
2. Ověřte, že `CLOUD_URL` odkazuje na váš cloudový koncový bod (např. `https://omniroute.dev`)
3. Udržujte hodnoty `NEXT_PUBLIC_*` v souladu s hodnotami na straně serveru

### Cloud s `stream=false` vrací 500

**Příznak:** `Unexpected token 'd'...` na cloudovém koncovém bodu při voláních bez streamování.

**Příčina:** Nadřazená služba vrací datovou část SSE, zatímco klient očekává JSON.

**Řešení:** Pro přímá volání cloudu použijte `stream=true`. Lokální běhové prostředí obsahuje záložní převod SSE→JSON.

### Cloud hlásí připojení, ale také „Neplatný API klíč“

1. Vytvořte nový klíč v lokálním ovládacím panelu (`/api/keys`)
2. Spusťte synchronizaci s cloudem: Povolit cloud → Synchronizovat nyní
3. Staré nebo nesynchronizované klíče mohou v cloudu stále vracet `401`

## Problémy s Dockerem

### Docker IPv6 / resetování připojení

<a name="docker-ipv6"></a>

**Příznaky:** `curl http://localhost:20128/v1/models` vrací `curl: (56) Recv failure: Connection reset by peer`. Ovládací panel a koncové body bez ověření fungují, ale ověřené koncové body selhávají — vypadá to jako problém s ověřováním, ale není tomu tak.

**Příčina:** `docker run -p 20128:20128` publikuje na `0.0.0.0` (IPv4) i `::` (IPv6), ale proces uvnitř kontejneru naslouchá pouze na IPv4. Na hostitelích, kde se `localhost` nejprve přeloží na `::1`, připojení směřuje na publikovaný port IPv6, za kterým nic nenaslouchá → připojení je resetováno.

**Oprava:**

1. **Rychlá diagnostika:** Spusťte `curl -4 http://localhost:20128/v1/models`. Pokud příkaz s `-4` funguje, ale bez něj selže, jde o neshodu vazby IPv6.
2. **Trvalá oprava:** Navažte port explicitně na IPv4 použitím `-p 127.0.0.1:20128:20128` v příkazu `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Tím se vynutí vazba na IPv4 a zároveň se zabrání zpřístupnění proxy na všech rozhraních hostitele.

## Ladění

### Povolení souborů protokolu

Nastavte `APP_LOG_TO_FILE=true` v souboru `.env`. Protokoly aplikace se zapisují do `logs/`.
Artefakty požadavků se ukládají do `${DATA_DIR}/call_logs/`, pokud je v nastavení
povolen kanál protokolování volání.
Pokud je povoleno zachytávání kanálu, nastavte `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false`, chcete-li vynechat
datové části streamovaných bloků, nebo upravte `CALL_LOG_PIPELINE_MAX_SIZE_KB`, chcete-li změnit limit velikosti artefaktů v KB.

### Kontrola stavu poskytovatele

```bash
# Ovládací panel stavu
http://localhost:20128/dashboard/health

# Kontrola stavu API
curl http://localhost:20128/api/monitoring/health
```

### Úložiště běhového prostředí

- Hlavní stav: `${DATA_DIR}/storage.sqlite` (poskytovatelé, kombinace, aliasy, klíče, nastavení)
- Využití: tabulky SQLite v `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + volitelně `${DATA_DIR}/call_logs/`
- Protokoly aplikace: `<repo>/logs/...` (pokud platí `APP_LOG_TO_FILE=true`)
- Artefakty protokolu volání: `${DATA_DIR}/call_logs/YYYY-MM-DD/...`, pokud je povolen kanál protokolování volání

Akce **Vyčistit historii** na stránce Protokoly požadavků vymaže `call_logs`, starší
`request_detail_logs` a lokální adresář artefaktů `${DATA_DIR}/call_logs/`.

## Problémy s jističem okruhu

### Poskytovatel uvízl ve stavu OPEN

Když je jistič okruhu poskytovatele ve stavu OPEN, požadavky jsou blokovány až do uplynutí doby čekání.

**Řešení:**

1. Přejděte na **Dashboard → Settings → Resilience**
2. Zkontrolujte kartu jističe okruhu příslušného poskytovatele
3. Kliknutím na **Reset All** resetujte všechny jističe, nebo počkejte na uplynutí doby čekání
4. Před resetováním ověřte, že je poskytovatel skutečně dostupný

### Poskytovatel opakovaně aktivuje jistič okruhu

Pokud poskytovatel opakovaně přechází do stavu OPEN:

1. V části **Dashboard → Health → Provider Health** zkontrolujte vzorec selhání
2. Přejděte na **Settings → Resilience → Provider Profiles** a zvyšte prahovou hodnotu počtu selhání
3. Zkontrolujte, zda poskytovatel nezměnil limity API nebo nevyžaduje opětovné ověření
4. Zkontrolujte telemetrii latence — vysoká latence může způsobovat selhání kvůli vypršení časového limitu

## Problémy s přepisem zvuku

### Chyba „Unsupported model“

- Použijte ID modelu, jehož první částí je poskytovatel, pro kterého máte přihlašovací údaje (`openai/whisper-1`, `openrouter/deepgram/nova-3`). Samotné `deepgram/nova-3` vyžaduje nativní klíč Deepgram.
- Ověřte, že je poskytovatel připojen v části **Dashboard → Providers**

### Přepis je prázdný nebo selže

- Zkontrolujte podporované zvukové formáty: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- Ověřte, že velikost souboru nepřekračuje limity poskytovatele (obvykle < 25MB)
- Na kartě poskytovatele zkontrolujte platnost klíče API

| **Playground**   | Porovnejte vstupní a výstupní formát vedle sebe — vložte selhávající požadavek a zjistěte, jak se převede |

### Běžné problémy s formátem

- **Nezobrazují se značky pro přemýšlení** — Zkontrolujte, zda cílový poskytovatel podporuje přemýšlení, a ověřte nastavení rozpočtu pro přemýšlení
- **Volání nástrojů se ztrácejí** — Některé převody formátů mohou odstraňovat nepodporovaná pole; ověřte to v režimu Playground
- **Chybí systémový prompt** — Claude a Gemini zpracovávají systémové prompty odlišně; zkontrolujte výstup převodu
- **SDK vrací nezpracovaný řetězec namísto objektu** — Vyřešeno ve v1.x; nástroj pro sanitaci odpovědí odstraňuje nestandardní pole (`x_groq`, `usage_breakdown` atd.), která způsobují selhání validace Pydantic v OpenAI SDK. Pokud se s tím stále setkáváte ve v3.x+, nahlaste prosím problém.
- **GLM/ERNIE odmítá roli `system`** — Vyřešeno ve v1.x; normalizátor rolí automaticky slučuje systémové zprávy se zprávami uživatele u nekompatibilních modelů. Pokud se s tím stále setkáváte ve v3.x+, nahlaste prosím problém.
- **Role `developer` není rozpoznána** — Vyřešeno ve v1.x; u poskytovatelů jiných než OpenAI se automaticky převádí na `system`. Pokud se s tím stále setkáváte ve v3.x+, nahlaste prosím problém.
- **`json_schema` nefunguje s Gemini** — Vyřešeno ve v1.x; `response_format` se nyní převádí na `responseMimeType` + `responseSchema` Gemini. Pokud se s tím stále setkáváte ve v3.x+, nahlaste prosím problém.

## Nastavení odolnosti

### Automatické omezení rychlosti se nespouští

- Automatické omezení rychlosti se vztahuje pouze na poskytovatele využívající klíče API (nikoli OAuth/předplatné)
- Ověřte, že je v části **Nastavení → Odolnost → Profily poskytovatelů** povoleno automatické omezení rychlosti
- Zkontrolujte, zda poskytovatel vrací stavové kódy `429` nebo hlavičky `Retry-After`

### Ladění exponenciálního prodlužování prodlevy

Profily poskytovatelů podporují tato nastavení:

- **Základní prodleva** — Počáteční doba čekání po prvním selhání (výchozí: 1s)
- **Maximální prodleva** — Horní limit doby čekání (výchozí: 30s)
- **Násobitel** — O kolik se má prodleva zvýšit při každém po sobě jdoucím selhání (výchozí: 2x)

### Ochrana proti nárazovému souběhu požadavků

Když mnoho souběžných požadavků zasáhne poskytovatele s omezenou rychlostí, OmniRoute používá mutex a automatické omezení rychlosti k serializaci požadavků a zabránění kaskádovým selháním. U poskytovatelů využívajících klíče API je toto chování automatické.

### Požadavky chatu selhávají s 503 / chat_admission_busy

**Příznaky:**

- Endpoint pro dokončování chatu vrací opakovatelnou odpověď `503`, jejíž chybový kód je
  `chat_admission_busy`.
- Odpověď obsahuje `Retry-After`. Od změny #12135 je hodnota odvozena z pozorovaného
  vytížení — použije se vyšší hodnota z okna `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`, po které již požadavek
  čekal, a doby, po kterou jsou drženy aktuální pronájmy pro náročné požadavky — zaokrouhlená nahoru na celé
  sekundy a omezená na maximálně 60. U nevyužité brány zůstávají zachovány historické minimální hodnoty: 2 sekundy u
  cesty založené na bajtech, 1 sekunda u cesty založené na struktuře (která také obsahuje
  `reason: "structure_limit"`).
- K tomu může dojít, zatímco stále probíhá jiný náročný chat nebo dlouhotrvající streamovaná odpověď.

Tělo odpovědi založené na bajtech je:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Odpověď založená na struktuře používá stejný typ a kód se zprávou
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
a hodnotou `reason: "structure_limit"`.
Při výchozích prahových hodnotách je požadavek strukturálně náročný, pokud obsahuje alespoň `200` zpráv,
alespoň `64` nástrojů nebo alespoň `32,000` odhadovaných tokenů, případně pokud omezený odhad struktury
vyčerpá své limity `10,000` navštívených uzlů nebo hloubky `12`.

**Příčina:** Jedná se o záměrné odlehčení zátěže uvnitř OmniRoute, nikoli o selhání nadřazeného poskytovatele.
Každý proces používá lokální ochranu procesu k rezervaci omezené kapacity pro náročné požadavky před uchováním
a analýzou velkého těla požadavku. Pronájem pro náročný požadavek zůstává zachován po celou dobu životnosti odpovědi SSE.

**#503-fanout:** před touto opravou ochrana omezovala souběžnost na pevný POČET požadavků
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, výchozí `1`) bez ohledu na paměť hostitele, takže rozvětvení
programovacích agentů (více podřízených agentů/CLI, těla běžně > 256 KB) vedlo k efektivní
souběžnosti přibližně 1 a k chybám 503 při zcela běžné zátěži. Ochrana se nyní ladí automaticky: je řízena
automaticky odvozeným BAJTOVÝM rozpočtem pro příjem (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) dimenzovaným podle
skutečného paměťového limitu procesu a také zohledňuje aktuální signál zatížení prostředků — takže
požadavky odmítá pouze tehdy, když je hostitel skutečně pod tlakem kvůli nedostatku paměti, nikoli pouze proto, že dorazil více než jeden
náročný požadavek současně. Starý limit počtu (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) je
stále respektován, ale pouze pokud jej explicitně nastavíte.

Když je kapacita vytížena, náročný požadavek nejprve čeká až
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (výchozí `2000`, hodnota `0` čekání zakáže), než se uvolní místo,
a teprve poté odpoví opakovatelnou chybou `503`. Omezené čekání existuje proto, aby klienti ve stylu agentů
(OpenCode, Claude Code, Cursor), kteří souběžně rozvětvují náročné dílčí požadavky, tuto nárazovou zátěž serializovali,
namísto toho, aby vyčerpali celý svůj rozpočet opakovaných pokusů okamžitými odmítnutími a selhali uprostřed úlohy.
Aktuální využití pronájmů pro náročné požadavky, výsledný bajtový rozpočet a aktuální závažnost zatížení jsou
k dispozici na `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — zkontrolujte je před změnou jakékoli proměnné prostředí.
Nastavení → Odolnost → Fronta požadavků → Souběžné požadavky toto neřídí; toto nastavení
ovládá samostatný mechanismus fronty požadavků poskytovatele.

**Oprava:**

1. Nejprve požadavek zopakujte. Klienti by měli respektovat `Retry-After` a použít prodlužování prodlevy namísto okamžitého
   opakování požadavku.
2. Před jakýmkoli laděním zkontrolujte `/api/monitoring/health` → `chatAdmission`. Hodnota `countCapEnabled:
false` a dostatečně velká hodnota `maxInflightBytes` znamenají, že automaticky odvozený rozpočet již funguje
   správně; hodnota `pressureSeverity` nastavená na `high`/`critical` znamená, že hostitel má skutečně málo paměti —
   to nelze opravit proměnnou prostředí pro řízení příjmu, je potřeba více paměti RAM nebo menší pracovní zátěž.
3. Pouze pokud `/api/monitoring/health` ukazuje, že je automaticky odvozený rozpočet pro
   vašeho hostitele skutečně příliš malý (což je vzácné — již se škáluje od kontejnerů po fyzické servery), přepište jej přímo pomocí
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` namísto návratu ke staršímu limitu počtu požadavků.

Autoritativní nastavení řízení příjmu najdete v [referenci proměnných prostředí](../reference/ENVIRONMENT.md#4-security--authentication).

## Volitelná taxonomie selhání RAG / LLM (16 problémů)

Někteří uživatelé OmniRoute umisťují bránu před systémy RAG nebo agenty. V těchto konfiguracích se běžně objevuje zvláštní situace: OmniRoute vypadá v pořádku (poskytovatelé jsou dostupní, směrovací profily jsou v pořádku, žádná upozornění na omezení rychlosti), ale výsledná odpověď je přesto chybná.

V praxi tyto incidenty obvykle pocházejí z navazujícího kanálu RAG, nikoli ze samotné brány.

Pokud chcete používat společnou terminologii k popisu těchto selhání, můžete využít WFGY ProblemMap, externí textový zdroj s licencí MIT, který definuje šestnáct opakujících se vzorců selhání RAG / LLM. Na obecné úrovni zahrnuje:

- odchylky při vyhledávání a narušené hranice kontextu
- prázdné nebo zastaralé indexy a vektorová úložiště
- nesoulad mezi embeddingy a sémantikou
- problémy se sestavováním promptů a kontextovým oknem
- zhroucení logiky a příliš sebejisté odpovědi
- selhání dlouhých řetězců a koordinace agentů
- problémy s pamětí více agentů a odchylky rolí
- problémy s pořadím nasazení a inicializace

Princip je jednoduchý:

1. Při vyšetřování chybné odpovědi zaznamenejte:
   - úlohu a požadavek uživatele
   - trasu nebo kombinaci poskytovatelů v OmniRoute
   - veškerý kontext RAG použitý v navazujících systémech (načtené dokumenty, volání nástrojů atd.)
2. Přiřaďte incident k jednomu nebo dvěma číslům WFGY ProblemMap (`No.1` … `No.16`).
3. Uložte číslo ve vlastním dashboardu, provozní příručce nebo systému pro sledování incidentů vedle protokolů OmniRoute.
4. Pomocí odpovídající stránky WFGY rozhodněte, zda je potřeba změnit systém RAG, vyhledávací komponentu nebo strategii směrování.

Úplný text a konkrétní postupy najdete zde (licence MIT, pouze text):

[README WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Pokud za OmniRoute neprovozujete kanály RAG ani agenty, můžete tuto část ignorovat.

## Známé problémy ve v3.8.0

Problémy specifické pro vydání v3.8.0 a jejich aktuální náhradní řešení. Pokud bude oprava zahrnuta v pozdější opravné verzi, položka bude aktualizována nebo odstraněna.

### Selhání ověřování Devin CLI

**Příznaky:**

- „Devin CLI not found“ nebo „auth failed“ při spouštění nástrojů využívajících Devin
- Kontrola běhového prostředí CLI hlásí `installed=false`

**Příčiny:**

- `CLI_DEVIN_BIN` odkazuje na cestu, která neexistuje
- Devin CLI není na hostiteli nainstalováno

**Oprava:**

1. Nainstalujte Devin CLI pro svou platformu
2. Nastavte `CLI_DEVIN_BIN=/usr/local/bin/devin` (nebo skutečnou cestu) v souboru `.env`
3. Restartujte OmniRoute a znovu proveďte test v části **Dashboard → Nástroje CLI**

### Model zůstal ve stavu cooldown (ruční resetování)

**Příznaky:**

- Model zůstává uveden ve stavu cooldown i po uplynutí doby platnosti
- Požadavky při kombinovaném směrování nadále model přeskakují, přestože je časové razítko v minulosti

**Ruční resetování:**

- **Dashboard:** **Nastavení → Cooldowny modelů** → na kartě příslušného modelu klikněte na **Znovu povolit**
- **API:** `DELETE /api/resilience/model-cooldowns` s ověřovacími hlavičkami pro správu

### Připojení k poskytovateli Command Code selže s chybou 403

**Příznaky:**

- Chyba 403 při testování připojení k poskytovateli Command Code
- Karta poskytovatele po novém přidání zobrazuje „unauthorized“

**Příčina:** Tok OAuth nebyl dokončen (zpětné volání nebylo přijato nebo token nebyl trvale uložen).

**Oprava:**

- Spusťte `omniroute providers` z CLI, čímž znovu aktivujete tok OAuth, nebo
- Spusťte OAuth znovu v části **Dashboard → Poskytovatelé → Command Code → Znovu připojit**

### ModelScope vrací agresivní cooldowny 429

**Příznaky:**

- Velmi krátké nebo okamžité cooldowny v ModelScope po malé dávce požadavků
- Kombinované směrování přeskakuje ModelScope dříve, než se očekávalo

**Příčina:** ModelScope odesílá hlavičky `Retry-After` specifické pro poskytovatele. Verze v3.8.0 obsahuje vyhrazené zpracování těchto hlaviček, takže je starší verze nesprávně interpretují jako obecné indikátory omezení rychlosti.

**Oprava:**

- Ověřte, že používáte verzi v3.8.0 nebo novější
- Ověřte, že je přepínač `useUpstream429BreakerHints` povolen v části **Nastavení → Odolnost**

### V produkčním prostředí chybí OMNIROUTE_WS_BRIDGE_SECRET

**Příznaky:**

- Chyba 401 u každého požadavku mostu WebSocket pro Codex/Responses při provozu na vzdáleném produkčním hostiteli
- Navázání spojení mostu WebSocket se ihned po připojení ukončí

**Příčina:** V produkčním prostředí chybí proměnná prostředí `OMNIROUTE_WS_BRIDGE_SECRET`.

**Oprava:**

1. Vygenerujte náhodný tajný klíč: `openssl rand -hex 32`
2. Nastavte `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` v prostředí produkčního serveru (a v každém klientovi, který komunikuje s mostem)
3. Restartujte OmniRoute

### Responses API: režim na pozadí omezen na synchronní režim

**Příznaky:**

- Zaznamenané upozornění: `background mode degraded to synchronous`
- Požadavek s `background: true` vrátí běžnou synchronní odpověď namísto popisovače úlohy na pozadí

**Příčina:** Verze v3.8.0 záměrně převádí `background: true` v Responses API na synchronní provádění a současně vydává upozornění. Plné asynchronní provádění na pozadí je plánováno do budoucna.

**Oprava:**

- Upravte klienta tak, aby volání prováděl bez `background`, nebo
- Počkejte na pozdější vydání, které bude obsahovat plný asynchronní režim na pozadí (sledujte seznam změn)

## Pomalé spuštění / vypršení časového limitu připravenosti

Pokud CLI vypíše `⚠ Server neodpověděl do 60 s`, ale server ve skutečnosti
funguje, je časový limit kontroly připravenosti pro vaše prostředí příliš krátký.

K tomu běžně dochází ve Windows (kvůli antiviru nebo sledování souborového systému) nebo v kontejnerech
s vysokou zátěží při spuštění.

**Řešení — zvyšte časový limit:**

```bash
# Pomocí proměnné prostředí (platí i při dalších spuštěních):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuty
omniroute serve

# Pomocí příznaku CLI (jednorázově):
omniroute serve --ready-timeout 180000
```

Výchozí hodnota je 60 000 ms (60 s). Varování je pouze informativní; server
se nadále spouští na pozadí a po dokončení spuštění bude dostupný.

Úplné podrobnosti o `OMNIROUTE_READY_TIMEOUT_MS` najdete v souboru
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
