> **TL;DR**: OmniRoute sleduje využití tokenů u každého požadavku, vypočítává náklady, vynucuje kvóty pro jednotlivé API klíče a zobrazuje analytická data na řídicím panelu. Tato příručka vysvětluje, jak vše funguje.

**Zdroje:**

- `open-sse/services/usage.ts` (~70KB) — hlavní sledování využití
- `src/lib/usageAnalytics.ts` (~10KB) — agregace pro řídicí panel
- `src/lib/db/quotaSnapshots.ts` — historická data kvót
- `src/lib/db/usage*.ts` — několik databázových modulů souvisejících s využitím

---

## Přehled

Každý požadavek, který prochází přes OmniRoute, generuje **záznam o využití**, který zachycuje:

- **Identitu**: který API klíč, poskytovatel, model a kombinace
- **Tokeny**: tokeny promptu, tokeny dokončení, tokeny z mezipaměti a celkový počet
- **Náklady**: částku v USD (vypočítanou z cenových údajů)
- **Časování**: latenci a časová razítka začátku/konce
- **Stav**: úspěch, chyba, omezení rychlosti atd.

Tyto záznamy se agregují do **analytických dat**, ukládají se jako **snímky kvót** a používají se k vynucování **rozpočtových limitů pro jednotlivé klíče**.

```
Požadavek ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    analytika  kvóta   účtování
                    (panel)     (vynucení) (export)
```

## Co se zaznamenává

Služba `usage.ts` zachycuje **událost využití** pro každý požadavek:

| Pole               | Typ     | Zdroj                                                                        |
| ------------------ | ------- | ---------------------------------------------------------------------------- |
| `id`               | string  | UUID vygenerované při záznamu                                                |
| `apiKeyId`         | string  | API klíč, který požadavek inicioval                                          |
| `provider`         | string  | ID poskytovatele (openai, anthropic atd.)                                    |
| `model`            | string  | ID modelu (gpt-5, claude-opus-4-6 atd.)                                      |
| `comboId`          | string? | ID kombinace, pokud byl požadavek směrován přes kombinaci                    |
| `promptTokens`     | number  | Z odpovědi nadřazeného poskytovatele                                         |
| `completionTokens` | number  | Z odpovědi nadřazeného poskytovatele                                         |
| `cachedTokens`     | number  | Tokeny nalezené v mezipaměti (ukládání promptů Anthropic do mezipaměti atd.) |
| `totalTokens`      | number  | prompt + dokončení                                                           |
| `costUsd`          | number  | Vypočítáno z cenových údajů                                                  |
| `latencyMs`        | number  | Celková doba trvání požadavku                                                |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`                   |
| `errorClass`       | string? | Třída chyby, pokud status != success                                         |
| `timestamp`        | string  | ISO 8601 UTC                                                                 |
| `metadata`         | object  | Vlastní data vložená pluginem                                                |

### Odkud tokeny pocházejí

Tokeny se extrahují z odpovědi nadřazeného poskytovatele v **obslužné rutině odpovědi**:

```ts
// Z open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

U poskytovatelů, kteří údaje o využití nevracejí (někteří poskytovatelé využívající webové soubory cookie), OmniRoute tokeny **odhaduje** pomocí heuristiky `~4 chars per token` (viz `open-sse/services/autoCombo/pipelineRouter.ts`).

### Tokeny z mezipaměti

OmniRoute sleduje `cached_tokens` odděleně od `prompt_tokens`, protože:

- Ukládání promptů Anthropic do mezipaměti účtuje za tokeny z mezipaměti sníženou sazbu (10 % běžné ceny)
- Někteří poskytovatelé vracejí `cache_read_input_tokens`, jejichž cena by měla být stanovena odlišně
- Analytika může zobrazit **míru zásahů do mezipaměti** = `cached_tokens / prompt_tokens`

## Výpočet nákladů

Náklady se počítají z **cenových dat** synchronizovaných z LiteLLM (`src/lib/pricingSync.ts`):

| Model             | Vstup $/1M | Výstup $/1M | Mezipaměť $/1M |
| ----------------- | ---------- | ----------- | -------------- |
| gpt-5             | $2.50      | $10.00      | —              |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50          |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30          |
| gemini-2.5-pro    | $1.25      | $10.00      | —              |

Vzorec pro výpočet nákladů (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Proč se tokeny z mezipaměti odečítají od tokenů promptu?** Část z mezipaměti je účtována samostatně; účtování vstupní ceny za celý prompt by vedlo k započítání příliš vysoké částky.

### Synchronizace cen

Cenová data se automaticky synchronizují z LiteLLM prostřednictvím koncového bodu `/api/pricing/sync` (spouští jej vestavěná úloha cron, nikoli uživatelská proměnná prostředí):

```bash
# Ruční spuštění
curl -X POST http://localhost:20128/api/pricing/sync
```

U modelů bez cenových dat OmniRoute přejde na **odhad nákladů** pomocí interních průměrných sazeb (získaných z cenových dat LiteLLM).

## Agregace podle časového období

Modul `usageAnalytics.ts` počítá widgety řídicího panelu z nezpracovaných dat o využití. Podporuje 7 časových období:

| Období   | Časový rozsah                       | Případ použití                     |
| -------- | ----------------------------------- | ---------------------------------- |
| `1d`     | Posledních 24 hodin                 | Detekce hodinových nárůstů nákladů |
| `7d`     | Posledních 7 dní                    | Týdenní kontrola                   |
| `30d`    | Posledních 30 dní                   | Měsíční fakturace                  |
| `90d`    | Posledních 90 dní                   | Čtvrtletní analýza                 |
| `ytd`    | Od 1. ledna aktuálního roku         | Sledování ročního rozpočtu         |
| `all`    | Za celou dobu                       | Celkové statistiky                 |
| `custom` | Uživatelem definovaný začátek/konec | Audity, jednorázové dotazy         |

### Vypočítané widgety řídicího panelu

Pro libovolné časové období analytická vrstva počítá:

| Widget                            | Popis                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------- |
| **Souhrnné karty**                | Celkový počet požadavků, celkové náklady, celkový počet tokenů, míra úspěšnosti |
| **Graf denního trendu**           | Náklady + tokeny za den, skládané podle modelu                                  |
| **Teplotní mapa aktivity**        | Mřížka hodina dne × den v týdnu, barva = počet požadavků                        |
| **Rozdělení podle modelu**        | Výsečový graf nákladů podle modelu                                              |
| **Rozdělení podle poskytovatele** | Sloupcový graf požadavků podle poskytovatele                                    |
| **Nejčastější klíče API**         | Tabulka 10 klíčů s nejvyššími náklady                                           |
| **Analýza chyb**                  | Míra chyb v průběhu času, nejčastější třídy chyb                                |

### Programový přístup

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // záznamy historie využití
  "7d",                 // časové období: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // mapa připojení poskytovatelů (connectionId → název účtu)
  {
    startDate: "2025-01-01",  // volitelné: pro období "custom"
    endDate: "2025-06-01",   // volitelné: pro období "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (centů)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Vynucování kvót

Kvóta pro jednotlivé klíče API se vynucuje na dvou místech:

1. **Měkký limit** (`quotaWarnAt`): upozornění na řídicím panelu, když využití překročí prahovou hodnotu
2. **Pevný limit** (`quotaLimit`): požadavek je při překročení odmítnut se stavem HTTP 429

### Konfigurace

```ts
// Pro jednotlivý klíč API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — zobrazit upozornění
  quotaLimit: 10_00,    // $10.00 — pevné zastavení
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Průběh vynucování

```
Požadavek ──▶ quotaCheck()
                │
                ├── V rámci limitu?  ──▶ povolit
                │
                └── Nad limitem?  ──▶ 429 Too Many Requests
                                      s hlavičkou Retry-After
```

### Snímky kvót

Tabulka `quotaSnapshots` uchovává **historický stav kvót** pro analýzu trendů:

| Pole | Popis |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | Sledovaný klíč |
| `window` | "day" | "week" | "month" |
| `used` | Náklady využité v tomto okně (centy) |
| `limit` | Limit (centy) |
| `resetAt` | Kdy se okno resetuje |
| `createdAt` | Kdy byl snímek pořízen |

Snímky se pořizují **při každém požadavku**, který má náklady > 0, a používají se k následujícím účelům:

- Vykreslení ukazatele průběhu kvóty na řídicím panelu
- Zobrazení grafů trendu kvót za 30 dní
- Spouštění upozornění, když se využití blíží limitu

## Uchovávání a čištění

Objem dat o využití roste přibližně o 1–10 KB na požadavek. Ve velkém měřítku může jít o významné množství.

### Nastavení uchovávání

Doba uchovávání historie využití se konfiguruje prostřednictvím nastavení databáze v uživatelském rozhraní nebo přes `/api/settings/database`.

Ve výchozím nastavení se historie využití uchovává po dobu **90 dnů**.

### Čištění

Staré záznamy čistí `src/lib/db/cleanup.ts`:

- Čištění spouští proces cron běžící na pozadí
- Odstraňuje záznamy z `usage_history`, které jsou starší než nakonfigurovaná doba uchovávání `usageHistory`

### Odhad úložiště

| Frekvence požadavků   | Úložiště za 30 dní | Úložiště za 90 dní |
| --------------------- | ------------------ | ------------------ |
| 100 požadavků/den     | ~3 MB              | ~9 MB              |
| 1 000 požadavků/den   | ~30 MB             | ~90 MB             |
| 10 000 požadavků/den  | ~300 MB            | ~900 MB            |
| 100 000 požadavků/den | ~3 GB              | ~9 GB              |

Při velmi vysokém provozu zvažte:

- Zkrácení doby uchovávání prostřednictvím nastavení databáze
- Použití `aggregated_metrics` namísto nezpracovaných záznamů (pouze pro analytiku)

## Tipy pro optimalizaci nákladů

### 1. Používejte správný model

```bash
# Rychlá odpověď — použijte levný a rychlý model
curl -d '{"model":"auto/fast","messages":[...]}'

# Složitá úloha — použijte kvalitní model
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Povolte ukládání do mezipaměti

Ukládání promptů Anthropic do mezipaměti ušetří **90 % nákladů na opakovaný kontext**:

```ts
// Ukládání do mezipaměti je automatické — stačí použít stejný rozsáhlý systémový prompt
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Automaticky se uloží do mezipaměti
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Používejte kompresi

Komprese RTK + Caveman ušetří **15–95 % u relací s intenzivním využitím nástrojů**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Nastavte kvóty pro jednotlivé klíče

Vždy nastavte `quotaLimit`, abyste zabránili nekontrolovanému růstu nákladů:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Limit 10 USD/měsíc
```

### 5. Zkontrolujte největší spotřebitele

Pomocí řídicího panelu nebo **`/api/usage/analytics`** seskupte data podle klíče API a seřaďte je podle nákladů:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Řešení problémů

### „Náklady jsou vyšší, než se očekávalo“

1. Zkontrolujte **`/api/usage/analytics?groupBy=model`** — vyhledejte nákladný model
2. Zkontrolujte **`/api/usage/analytics?groupBy=apiKey`** — vyhledejte největšího spotřebitele
3. Ověřte, že jsou údaje o cenách aktuální: `POST /api/pricing/sync`

### „Záznamy chybí“

- Zkontrolujte nastavení uchovávání v databázi v části Řídicí panel → Databáze → Čištění — staré záznamy odstraňuje pravidelná úloha čištění (`src/lib/db/cleanup.ts`)
- Zkontrolujte chyby v `src/lib/db/usage*.ts` — selhání zápisu do databáze se zaznamenávají do protokolu, ale nezobrazují se
- Ověřte, že požadavek skutečně dorazil do `chatCore` — zkontrolujte kombinované směrování

### „Kvóta se nevynucuje“

- Zkontrolujte nastavení `quotaLimit` daného klíče
- Ověřte, že je `quotaWindow` nastaveno správně
- Vyhledejte záznamy `quotaSnapshots` — měly by se vytvářet při každém požadavku
