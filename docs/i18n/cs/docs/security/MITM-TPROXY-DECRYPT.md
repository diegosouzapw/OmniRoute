Transparentní dešifrování TPROXY je **5. režim zachytávání** OmniRoute pro MITM stack
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md).
Na Linuxu zachytává a **dešifruje** místní odchozí provoz HTTPS pomocí kernelového
TPROXY + směrování na základě zásad — **bez** podvržení `/etc/hosts` a
**bez** změny systémového nastavení proxy v celém OS. Je vhodné pro bezobslužný provoz
(není třeba odstraňovat změny DNS) a pravidla firewallu se při restartu automaticky vymažou.

Na rozdíl od ostatních režimů zachytávání nevyžaduje TPROXY žádné nastavení pro jednotlivé hostitele:
transparentně zachytává **libovolné** cílové hostitele na cílovém portu, ukončuje TLS pomocí
koncového certifikátu, který za běhu vystavuje pro každý název hostitele SNI, zachytává dešifrovanou
komunikaci a požadavek znovu zašifruje pro původní cíl.

> **Pouze Linux, pouze root, nutné výslovné zapnutí.** Tento režim vyžaduje Linux, nativní doplněk
> sestavený pomocí nástrojů jazyka C a oprávnění **CAP_NET_ADMIN** (obvykle root). Je dostupný
> pouze prostřednictvím API AgentBridge vázaného na loopback a ve výchozím nastavení je zakázán. Důvěryhodná
> MITM CA, která může podepisovat certifikáty pro libovolného hostitele, představuje významné oprávnění — viz [§6 Zabezpečení](#6-security).

**Zdroj:** `src/mitm/tproxy/`
**Trasa API:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**Přepínač na řídicím panelu:** Traffic Inspector → panel nástrojů režimů zachytávání → **„Dešifrování TPROXY“** ⚠
**Viz také:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 Co to je a kdy to použít

Každý z ostatních čtyř režimů zachytávání má určité omezení:

| Režim               | Jak je provoz směrován                                 | Omezení                                         |
| ------------------- | ------------------------------------------------------ | ----------------------------------------------- |
| AgentBridge         | Podvržení DNS v `/etc/hosts` pro pevnou sadu hostitelů | pouze registrovaní hostitelé agentů IDE         |
| Vlastní hostitelé   | Podvržení DNS v `/etc/hosts` pro každého hostitele     | jeden záznam na hostitele; úprava vyžaduje sudo |
| HTTP_PROXY          | Proměnné prostředí `HTTP_PROXY`/`HTTPS_PROXY`          | pouze aplikace, které tuto proměnnou respektují |
| Celosystémová proxy | Nastavení proxy v OS                                   | mění globální stav; změnu je nutné vrátit       |

Transparentní dešifrování TPROXY místo toho směruje provoz na úrovni **kernelu**.
V řetězci `mangle OUTPUT` označí nová místní odchozí připojení TCP na cílový port
(výchozí `443`), `ip rule` přesměruje označené pakety k místnímu doručení
a při opětovném vstupu je cíl `TPROXY` v `mangle PREROUTING` předá
naslouchajícímu socketu **IP_TRANSPARENT** — který poté ukončí TLS a zachytí nešifrovaný obsah.

Použijte jej, pokud chcete zachytávat a dešifrovat provoz procesu, který:

- komunikuje s hostitelem, jehož AgentBridge neregistruje, a
- nerespektuje `HTTP_PROXY`, a
- nechcete narušit změnou celosystémové proxy.

Protože k zachytávání dochází v kernelu, původní proces **nevyžaduje žádnou
změnu konfigurace** — musí však důvěřovat dynamické CA, kterou OmniRoute
nainstaluje (viz [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 Požadavky

| Požadavek         | Podrobnosti                                                                                                                                                     |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**            | Pouze Linux — **IP_TRANSPARENT** je volba socketu dostupná pouze v Linuxu. Na všech ostatních platformách loader vrací stav „nedostupné“.                       |
| **Oprávnění**     | Schopnost **CAP_NET_ADMIN** pro vytvoření transparentního socketu a použití pravidel `iptables`/`ip` — v praxi je nutné spuštění jako root.                     |
| **Nativní addon** | Je nutné sestavit malý N-API addon (`src/mitm/tproxy/native/transparent.c`) nebo jej dodat jako předem sestavený. Viz [§3](#3-the-native-ip_transparent-addon). |
| **Moduly jádra**  | `iptables` s podporou cílů `TPROXY`, `mangle` a shody `mark` (ověřeno s jádrem 6.8.0).                                                                          |

**Bezproblémová degradace:** pokud některý požadavek není splněn (jiný systém než Linux, chybějící toolchain,
nesestavený addon), loader addonu (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
vrátí `null` namísto vyvolání výjimky. Stav režimu zachytávání poté uvádí
`available: false`, přepínač na řídicím panelu je **deaktivován** a zobrazuje tooltip
„Dešifrování TPROXY vyžaduje Linux + root + nativní addon“ a zbytek
OmniRoute funguje dál.

## §3 Nativní addon IP_TRANSPARENT

Modul `net` v Node nemůže zavolat `setsockopt(IP_TRANSPARENT)` _před_ `bind()`, což
TPROXY vyžaduje (jinak jádro přesměrované pakety zahodí). Addon
(`src/mitm/tproxy/native/transparent.c`, sestavený pomocí `binding.gyp`) je malý modul N-API,
který zpřístupňuje tři funkce používané prostřednictvím `transparentSocket.ts`:

| Funkce addonu                         | Operace se socketem                                                                               | Použití                                                                              |
| ------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, vrací nezpracovaný fd | transparentní listener zachytávání (Node převezme fd pomocí `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | `setsockopt` **SO_MARK** na existujícím fd                                                        | prevence smyčky (označení vlastních socketů proxy)                                   |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **před** neblokujícím `connect()`, vrací fd                              | znovu zašifrované předání upstreamu (SYN nese značku)                                |

Původní cílová adresa se načítá z `socket.localAddress`/`localPort` — TPROXY
ji zachovává, takže není potřeba vyhledávání pomocí **SO_ORIGINAL_DST**/NAT.

### Sestavení addonu

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- Během `npm run build` spustí `scripts/build/build-tproxy-native.mjs` příkaz `node-gyp
rebuild`. Probíhá **pouze v Linuxu a případné selhání není fatální** — chybějící toolchain pouze způsobí,
  že režim zachytávání nebude dostupný.
- `assembleStandalone.mjs` zkopíruje `build/Release/transparent.node` do
  samostatného balíčku; `transparentSocket.ts` jej vyhledává jak relativně k modulu, tak
  relativně k cwd (`<cwd>/src/mitm/tproxy/native/...`).
- `build/` a `prebuilds/` jsou ignorovány systémem git — binární soubor se **sestavuje, ale nikdy
  se necommitne**.

Loader prohledává v pořadí podle priority:
`native/build/Release/transparent.node`, poté `native/prebuilds/transparent.node`
(jak relativně k modulu, tak pod `<cwd>/src/mitm/tproxy/`).

## §4 Dynamická CA pro jednotlivé SNI a instalátor úložiště důvěryhodných certifikátů

> **Aktualizace #6684:** statický server AgentBridge (`src/mitm/server.cjs`) nyní
> používá stejný architektonický vzor CA/listových certifikátů namísto jediného statického
> listového certifikátu podepsaného sebou samým. Používá **samostatnou** instanci CA
> (`src/mitm/cert/rootCa.ts`, uloženou v `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> a instaluje ji do již existujícího slotu úložiště důvěryhodných certifikátů
> `omniroute-mitm.crt` (kde nahrazuje starý jediný listový certifikát — není potřeba
> čistit dvojí důvěru), který zůstává zcela oddělený od vlastního slotu TPROXY
> `omniroute-tproxy-ca.crt` popsaného níže.
> Nové instalace AgentBridge získají model CA automaticky; instalace, která
> již důvěřovala starému statickému listovému certifikátu, jej nadále používá,
> dokud se provozovatel výslovně nerozhodne přejít nastavením
> `MITM_ROOT_CA_ENABLED=true` (viz `src/mitm/cert/migration.ts`) — důvěryhodná
> MITM CA, která může podepsat listový certifikát pro **libovolného** hostitele,
> má podstatně větší oprávnění než starý listový certifikát s pevně danými SAN,
> takže u již důvěryhodné instalace k přechodu nikdy nedojde bez upozornění.

Historicky statický MITM certifikát AgentBridge fungoval pouze proto, že AgentBridge
podvrhuje DNS pro **pevnou** sadu hostitelů (nyní sjednocenou s níže uvedeným
modelem). TPROXY zachytává **libovolné** hostitele, takže jeho naslouchající server
musí předložit platný listový certifikát pro jakékoli SNI požadované klientem —
stejný požadavek nyní platí i pro AgentBridge pro úplnou sadu `MITM_TOOL_HOSTS`
(9 položek nástrojů) namísto pouhých 4 hostitelů antigravity.

### Dynamická CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` provozuje místní CA (postavenou na závislosti `selfsigned`), která:

- Generuje CA s dlouhou platností prostřednictvím `generateMitmCa()` (CN
  `"OmniRoute MITM CA"`, platnost 10 let, `basicConstraints CA=true` +
  `keyUsage keyCertSign,cRLSign`, 2048bitové RSA / SHA-256).
- Vydává **listový certifikát pro každý název hostitele SNI na vyžádání**
  prostřednictvím `issueLeafCert()` (platnost 1 rok, `subjectAltName` = hostitel
  SNI) a ukládá do mezipaměti jeden `tls.SecureContext` pro každý název hostitele.
- Zpřístupňuje `createSNICallback()` pro server ukončující TLS (viz [§5](#5-how-decrypt-and-capture-work)).
- Lze jej vytvořit s `existingCa`, aby CA zůstala stabilní i po restartech
  (takže úložiště důvěryhodných certifikátů není nutné znovu aktualizovat).

Soukromý klíč CA **nikdy neopustí daný počítač**.

### Instalátor úložiště důvěryhodných certifikátů (`src/mitm/tproxy/caTrust.ts`)

Zachytávaný klient musí dynamické CA důvěřovat, takže spuštění režimu zachytávání
nainstaluje certifikát CA do systémového úložiště důvěryhodných certifikátů ve
**vyhrazeném slotu** — `omniroute-tproxy-ca.crt` (konstanta
`TPROXY_CA_CERT_NAME`) — který je oddělený od slotu statického MITM certifikátu
(`omniroute-mitm.crt`), aby se navzájem nikdy nepřepisovaly.

`installTproxyCa(caPem, sudoPassword?)` detekuje adresář kotev dané distribuce
(v pořadí: nejprve styl Debianu) a spustí odpovídající příkaz pro aktualizaci:

| Adresář kotev                               | Příkaz pro aktualizaci   |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Při instalaci se PEM nejprve uloží do dočasného souboru, poté se s vyššími
oprávněními pomocí `mkdir -p` vytvoří adresář kotev, příkazem `cp` se do něj
zkopíruje připravený soubor a spustí se příkaz pro aktualizaci.
`uninstallTproxyCa()` odstraní pouze vyhrazený slot (statický MITM certifikát
ponechá beze změny) a provede aktualizaci — na systémech jiných než Linux
neudělá nic.

Všechny privilegované příkazy se spouštějí prostřednictvím
`execFileWithPassword` (`src/mitm/systemCommands.ts`) — `spawn` s **poli
argumentů, bez shellu a bez interpolace řetězců** (Pevné pravidlo č. 13).
Pokud proces běží jako root (např. na VPS), cílový příkaz se spustí přímo
a není potřeba žádné heslo; na desktopu bez oprávnění root se `sudoPassword`
předá přes `sudo -S` na standardní vstup.

> `sudoPassword` z desktopu se předává v těle požadavku POST za účelem autorizace
> instalace do úložiště důvěryhodných certifikátů; pokud proces běží jako root,
> je zcela ignorováno.

## §5 Jak funguje dešifrování a zachytávání

Tok zpracování (vše pod `src/mitm/tproxy/`):

```
místní aplikace  ──TCP/443──▶  mangle OUTPUT označí spojení (fwmark)
                                ip rule → místní směrovací tabulka → lo
                                mangle PREROUTING TPROXY → posluchač IP_TRANSPARENT (port 8443)
                                    │  captureMode.ts: načte původní cíl ze socket.localAddress
                                    ▼
                                tlsCapture.ts:
                                  1. ukončí TLS KLIENTA pomocí certifikátu pro jednotlivé SNI (dynamicCert)
                                  2. interní http.Server analyzuje dešifrovaný prostý text
                                  3. zachycení → globalTrafficBuffer.push() se source: "tproxy"
                                     (použity sanitizeHeaders + maskSecret)
                                  4. přepošle data znovu zašifrovaná do původního cíle
                                     přes socket označený pro obejití (connectMarked, ochrana proti smyčce)
                                    │
                                    ▼
                                původní upstream (api.example.com)
```

- **Ukončení TLS** (`createTlsCaptureServer`): zapouzdří nezpracovaný zachycený
  socket do serverového `tls.TLSSocket` pomocí zpětného volání SNI dynamické CA
  a poté předá dešifrovaný proud internímu `http.Server` (standardní technika
  ukončení MITM). Životnost socketů je omezena pomocí `MITM_IDLE_TIMEOUT_MS`, aby
  zablokovaný tunel nemohl vyčerpat deskriptory souborů.
- **Zachycení** (`handleDecryptedRequest`): vloží `InterceptedRequest` se
  `source: "tproxy"`, stavem začínajícím jako `"in-flight"`, hlavičkami zpracovanými
  pomocí `sanitizeHeaders()` a těly zpracovanými pomocí `maskSecret()` předtím, než
  vstoupí do vyrovnávací paměti. Položka je následně aktualizována o odpověď,
  velikosti a latenci.
- **Znovu zašifrované přeposlání** (`createForward` / `realForward`): znovu zašifruje
  data pro původní cíl. `rejectUnauthorized` má ve výchozím nastavení hodnotu
  **`true`** (ve výchozím nastavení zabezpečeno) — certifikát upstreamu je ověřen
  vůči SNI/Host požadovanému klientem, takže proxy odmítne přesně to, co by odmítl
  původní klient.

### Ochrana proti smyčce (SO_MARK)

Protože pravidla označují nová místní odchozí spojení, **vlastní** znovu zašifrované
přeposlání proxy by za normálních okolností bylo znovu zachyceno — vznikla by
nekonečná smyčka. Cesta přeposlání se tomu brání pomocí značky socketu pro obejití
(**SO_MARK**):

- `realForward` otevře svůj upstreamový socket prostřednictvím
  `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` — `DEFAULT_BYPASS_MARK = 0x539`
  — což nastaví **SO_MARK** **před** `connect()`, takže SYN přeposlání nese značku
  pro obejití.
- Pravidlo `mangle OUTPUT` vylučuje spojení, která již nesou značku pro obejití
  (`-m mark ! --mark <bypassMark>`), takže přeposlání proxy **není** znovu
  označeno a nevstoupí znovu do TPROXY.

> Poznámka k implementaci: socket označený pro obejití musí být nainstalován do
> `createConnection` agenta (`https.request({ createConnection })` je v přítomnosti
> agenta bez upozornění ignorováno), jinak by přeposlání otevřelo neoznačený socket
> a smyčka by se vrátila. Toto byla oprava ochrany proti smyčce ověřená e2e testy.

## §6 Zabezpečení

| Kontrolní mechanismus                | Podrobnosti                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API pouze pro loopback**           | Na `/api/tools/agent-bridge/tproxy` se vztahuje prefix `/api/tools/agent-bridge/` v `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`). Vynucení přístupu přes loopback probíhá **před** autentizací (Pevná pravidla č. 15 + č. 17) — uniklý JWT nemůže přes tunel spustit zachytávání TPROXY, které používá pravidla `iptables` a prostřednictvím podřízených procesů instaluje certifikační autoritu do úložiště důvěryhodných certifikátů. |
| **Vyhrazený slot pro CA**            | Dynamická CA se instaluje jako `omniroute-tproxy-ca.crt`, takže nikdy nepřepíše statický certifikát MITM.                                                                                                                                                                                                                                                                                                                                               |
| **Klíč CA nikdy neopustí hostitele** | `DynamicCertStore` uchovává klíč CA v paměti; klíč se neexportuje.                                                                                                                                                                                                                                                                                                                                                                                      |
| **Maskování tajných údajů**          | Funkce `maskSecret()` pro těla požadavků/odpovědí a `sanitizeHeaders()` pro hlavičky se spouštějí **před** `globalTrafficBuffer.push()`.                                                                                                                                                                                                                                                                                                                |
| **Žádná interpolace shellu**         | Všechny příkazy `iptables`/`ip`/příkazy pro úložiště důvěryhodných certifikátů se spouštějí pomocí `execFile`/`execFileWithPassword` s poli argumentů (Pevné pravidlo č. 13).                                                                                                                                                                                                                                                                           |
| **Ověření certifikátu upstreamu**    | Přesměrované připojení s opětovným šifrováním ve výchozím nastavení ověřuje certifikát upstreamu (`rejectUnauthorized: true`).                                                                                                                                                                                                                                                                                                                          |
| **Sanitizace chyb**                  | Chybové odpovědi této trasy procházejí funkcí `sanitizeErrorMessage()` (Pevné pravidlo č. 12).                                                                                                                                                                                                                                                                                                                                                          |

**CA pro MITM představuje mocný nástroj.** CA, které operační systém důvěřuje a které může podepsat certifikát pro libovolného
hostitele, znamená, že lze dešifrovat vše, co OmniRoute zachytí. Je dostupná pouze v rámci
explicitního režimu zachytávání TPROXY omezeného na místní přístup, který je ve výchozím nastavení vypnutý, a položka v úložišti
důvěryhodných certifikátů se při zastavení tohoto režimu odstraní.

## §7 Transakční použití / vrácení konfigurace firewallu

Pád nesmí nikdy zanechat pravidlo `mangle` ani zastaralou trasu. Tvůrce příkazů
(`src/mitm/tproxy/commands.ts`) a spouštěč (`src/mitm/tproxy/setup.ts`) zaručují,
že **vrácení je přesným opakem použití, provedeným v opačném pořadí**.

`applyTproxy(cfg)` spouští příkazy pro použití v daném pořadí; při **jakémkoli** selhání spustí
v režimu best-effort úplný `revertTproxy(cfg)` a chybu znovu vyvolá — firewall je tedy buď
plně nakonfigurován, nebo je konfigurace zcela vrácena, nikdy nezůstane aplikována jen částečně.
`revertTproxy(cfg)` spouští opačné příkazy v opačném pořadí a ignoruje selhání
(je idempotentní — lze jej bezpečně volat bezpodmínečně, např. při čištění pomocí
AgentBridge `repairMitm()`).

`validateTproxyConfig(cfg)` se spouští před jakýmkoli příkazem: porty musí být v rozsahu `1–65535`,
`mark`/`routeTable`/`bypassMark` musí být kladná celá čísla a `bypassMark` se musí
lišit od `mark` (ochrana proti smyčce).

### Příkazy pro použití (v daném pořadí)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Vrácení je odstraňuje v opačném pořadí: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> Tento postup je založen na **OUTPUT**, protože případem použití MITM je _místní_ odchozí
> provoz (aplikace na stejném hostiteli), který samotný TPROXY v `PREROUTING`
> nevidí — `PREROUTING` vidí pouze přeposílaný provoz. Řetězec `OUTPUT` označuje nová
> místní připojení, `ip rule` je přesměruje k místnímu doručení (`lo`) a
> `PREROUTING` je následně přiřadí transparentnímu listeneru.

## §8 Konfigurace

Požadavek na spuštění (`POST /api/tools/agent-bridge/tproxy`) přijímá následující
pole ověřovaná pomocí `StartTproxyBodySchema` (`tproxy/route.ts`). Všechna jsou volitelná
a pokud nejsou zadána, použijí se jejich výchozí hodnoty:

| Pole             | Typ                | Výchozí  | Poznámky                                                                                                                                                   |
| ---------------- | ------------------ | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`    | Cílový port TCP, který má být transparentně zachytáván                                                                                                     |
| **mark**         | int (≥1)           | `0x2333` | Značka firewallu nastavená v `OUTPUT`, podle níž porovnávají `ip rule` + `PREROUTING`                                                                      |
| **onPort**       | int (1–65535)      | `8443`   | Port, na který se váže transparentní listener (**IP_TRANSPARENT**)                                                                                         |
| **routeTable**   | int (≥1)           | `233`    | ID tabulky směrování podle zásad obsahující trasu `local 0.0.0.0/0`                                                                                        |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | Značka socketu pro obejití (**SO_MARK**), kterou proxy nastavuje na svých vlastních upstream připojeních; v `OUTPUT` jsou vyloučena (ochrana proti smyčce) |
| **sudoPassword** | string             | —        | Pouze desktopy bez oprávnění root: autorizuje instalaci do úložiště důvěryhodných certifikátů; při spuštění jako root je ignorováno                        |

Pro TPROXY neexistují **žádné proměnné prostředí** — veškerá konfigurace se provádí
prostřednictvím těla požadavku POST nebo výše uvedených výchozích hodnot.

## §9 Povolení v nástroji Traffic Inspector

1. Otevřete **Traffic Inspector** (`/dashboard/tools/traffic-inspector`).
2. Na panelu režimů zachytávání najděte tlačítko **„TPROXY Decrypt“** ⚠
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Pokud je **zakázané** a zobrazuje popisek „Dešifrování TPROXY vyžaduje Linux + uživatele root +
     nativní doplněk“, není nativní doplněk na tomto hostiteli dostupný (nejde o Linux,
     není k dispozici sada nástrojů nebo doplněk nebyl sestaven). Viz [§2](#2-requirements) a [§3](#3-the-native-ip_transparent-addon).
3. Klikněte na tlačítko. Zavolá `POST /api/tools/agent-bridge/tproxy` prostřednictvím
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`), což:
   sestaví dynamickou CA, otevře transparentní naslouchací službu, použije pravidla
   firewallu a nainstaluje CA do úložiště důvěryhodných certifikátů operačního systému.
4. Když je režim spuštěný, přepínač se zbarví oranžově a zobrazuje aktuální počet zachycení
   (`· <interceptCount>`). Zachycené požadavky se zobrazí v seznamu požadavků s
   `source: "tproxy"`.
5. Opětovným kliknutím režim zastavíte — `DELETE /api/tools/agent-bridge/tproxy` prostřednictvím
   `stopTproxyCaptureMode()` zavře naslouchací službu, odinstaluje CA a vrátí zpět
   pravidla firewallu.

Stav režimu zachytávání (spuštěno / dostupné / počet zachycení / port naslouchací služby) pochází
z `GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` v
`src/mitm/tproxy/captureManager.ts`). V jednu chvíli může být spuštěna pouze **jedna** relace TPROXY —
pokus o spuštění druhé je odmítnut se zprávou „Režim zachytávání TPROXY je již spuštěný“.

## §10 Řešení problémů

### Přepínač je zakázaný

Nativní doplněk nelze načíst. Ověřte, že používáte Linux, sestavili jste doplněk
(`npm run build:native:tproxy`) a proces může načíst `transparent.node`.
`isTransparentSocketAvailable()` řídí dostupnost přepínače; pokud doplněk chybí,
`GET /api/tools/agent-bridge/tproxy` vrátí `available: false`.

### Nic se nezachytává

- Ověřte, že zachytávaný proces skutečně navazuje spojení s nakonfigurovaným `dport`
  (výchozí hodnota je `443`).
- Ověřte, že proces důvěřuje dynamické CA. CA je nainstalována jako
  `omniroute-tproxy-ca.crt`; aplikace s vlastním úložištěm důvěryhodných certifikátů (Firefox/Chrome NSS)
  mohou vyžadovat, aby byl certifikát přidán také do něj.
- Spusťte diagnostický samočinný test **Diagnose** služby AgentBridge (viz
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) pro kontrolu důvěryhodnosti certifikátu /
  stavu serveru.

### Zastaralá pravidla firewallu po pádu

`revertTproxy()` je přesným opakem použití pravidel a je idempotentní. Zastavení
režimu vrátí pravidla zpět; pokud byl OmniRoute ukončen během relace, použijte akci
**Repair** služby AgentBridge (`POST /api/tools/agent-bridge/repair`), která vrátí zpět osiřelý stav
systému (podvržení DNS, kořenovou CA, systémový proxy server). Pravidla `mangle` TPROXY a trasa se také
automaticky vyprázdní při restartu systému.

### Nekonečná smyčka / proxy server zachytává vlastní předávání

Jde o případ ochrany proti smyčce. Ověřte, že se `bypassMark` liší od `mark` (validace
to vynucuje) a že předávání používá `connectMarked` (v `realForward` tomu tak je).
Viz [§5 Ochrana proti smyčce](#anti-loop-so_mark).
