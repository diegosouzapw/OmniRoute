> **TL;DR**: `open-sse/` je hlavní streamovací engine, který zajišťuje všechny požadavky na LLM v OmniRoute. Obsahuje přibližně 1 400 souborů implementujících zpracování požadavků, exekutory, služby, server MCP a překladovou vrstvu. Tato příručka vysvětluje, jak jednotlivé části zapadají do sebe.

**Zdroj:** `open-sse/` (balíček pracovního prostoru, přibližně 1 440 netestovacích souborů `.ts`)

---

## Proč samostatný balíček pracovního prostoru?

`open-sse/` je **samostatný pracovní prostor** v monorepozitáři OmniRoute, a to z několika důvodů:

1. **Opakovaná použitelnost** — `open-sse` je publikován na npm jako `@omniroute/open-sse`, takže jej mohou nezávisle používat i jiné projekty
2. **Jasné hranice** — streamovací engine je oddělen od vrstvy uživatelského rozhraní/databáze specifické pro OmniRoute
3. **Výkon** — engine nemá žádné závislosti na Next.js, což umožňuje rychlejší studené starty v prostředích CLI/serverless
4. **Verzování** — `open-sse` může vydávat verze vlastním tempem

```json
// package.json
"workspaces": ["open-sse"]
```

## Zpracování požadavku

Každý požadavek na LLM prochází **5fázovým zpracováním**:

```
                              ┌──────────────┐
   Požadavek HTTP              │  1. SMĚROVAT │   vyhodnocení kombinace, výběr modelu
   (trasa Next.js)             └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. PŘELOŽIT │   převod formátu (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. PROVÉST  │   exekutor poskytovatele, HTTP, opakování, jistič
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAMOVAT│   transformace SSE, zpětný tlak
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. ZAZNAMENAT│   sledování využití, protokol volání, klasifikace chyb
                              └──────┬───────┘
                                     │
                                     ▼
                              Odpověď HTTP (SSE nebo JSON)
```

### Fáze 1: Směrování (services/combo.ts)

**Vstupní bod**: `handleComboChat()` v `services/combo.ts`

Převede požadavek na konkrétní n-tici `(provider, model, account, credentials)`:

- Vyhledá kombinaci podle ID (nebo vytvoří virtuální kombinaci pro modely `auto/*`)
- Použije strategii směrování (prioritní, váženou, round-robin atd.)
- Odfiltruje poskytovatele, kteří nejsou v pořádku (jistič)
- Vybere další životaschopný cíl

Pro modely `auto/*` tato fáze také:

- Spouští **16faktorový bodovací** algoritmus (`services/autoCombo/`)
- Vybírá dvojici `provider+model` na základě stavu, ceny, latence atd.

### Fáze 2: Překlad (translator/)

Pokud se zdrojový formát (např. OpenAI) liší od cílového formátu (např. Claude), požadavek je **přeložen**:

- Systémový prompt → systémová zpráva
- Definice nástrojů → formát nástrojů specifický pro poskytovatele
- Parametry uvažování/přemýšlení → ekvivalenty specifické pro poskytovatele
- Normalizace rolí zpráv (`developer` → `system` pro jiné poskytovatele než OpenAI)

`translator/index.ts` zpřístupňuje:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Fáze 3: Provedení (executors/)

**Vstupní bod**: `getExecutor(providerId).execute(request, options)`

Všichni poskytovatelé používají `DefaultExecutor` (`executors/default.ts`) prostřednictvím záložního mechanismu továrny `getExecutor()`. Exekutor:

- Sestaví upstreamovou URL (`buildUrl()`)
- Přidá hlavičky specifické pro poskytovatele (`buildHeaders()`)
- Transformuje tělo požadavku (`transformRequest()`)
- Odešle požadavek HTTP s opakováním a exponenciálním prodlužováním prodlevy
- V případě potřeby zpracuje obnovení ověření (poskytovatelé OAuth)

Všechny exekutory rozšiřují `BaseExecutor` (`executors/base.ts`, 1170 řádků kódu), který poskytuje:

- Společnou logiku opakování
- Integraci proxy
- Integraci jističe
- Hooky pro zaznamenávání využití

### Fáze 4: Streamování (utils/stream.ts)

U streamovaných odpovědí exekutor vrací **ReadableStream**. Obslužná rutina:

- Provede průchod transformací SSE (`createSSETransformStreamWithLogger`)
- Používá heartbeat pingy k detekci neaktivních připojení
- Korektně zpracuje odpojení klienta (`pipeWithDisconnect`)
- Transformuje SSE → JSON pro klienty bez podpory streamování

U nestreamovaných odpovědí exekutor vrací analyzovaný objekt JSON, který je beze změny předán dál.

### Fáze 5: Záznam (services/usage.ts)

Po obdržení odpovědi (úspěšné či neúspěšné) se zaznamenají údaje o využití:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` z odpovědi
- `cost_usd` vypočítané z cenových údajů
- `latency_ms`, `status`, `error_class` v případě selhání
- Uloženo do tabulky `usage_history`

Artefakty protokolu volání (pokud jsou povoleny) se zapisují do `${DATA_DIR}/call_logs/`.

## Podrobný pohled na klíčové soubory

### chatCore.ts (5977 řádků)

**Hlavní obsluha požadavků**. Navzdory své velikosti má jasnou strukturu:

```ts
// Pseudostruktura souboru chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Autentizace + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Validace těla požadavku
  const body = await parseRequestBody(request);

  // 3. Detekce formátu + překlad
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Směrování combo
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Pokračovat na další cíl
    }
  }

  // 5. Nouzový fallback
  return await emergencyFallback(body);
}
```

Přestože jde o jednu obří funkci, je organizována do **komentovaných sekcí**, které odpovídají 5stupňovému pipeline.

### combo.ts (4456 LOC)

**Směrovací engine**, který pro combo určuje seřazené cíle.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

Podporuje **21 směrovacích strategií** (viz `src/shared/constants/routingStrategies.ts`):

| Strategie           | Chování                                                                                  |

| `round-robin`       | Cyklické střídání cílů v pořadí                                                          |
| `context-relay`     | Předávání kontextu mezi cíli                                                             |
| `fill-first`        | Nejdřív vyplní kvótu, pak přejde na další                                                |
| `p2c`               | Power of two choices (výběr ze dvou možností)                                            |
| `random`            | Rovnoměrně náhodný výběr                                                                 |
| `least-used`        | Vybere cíl s nejmenším počtem nedávných použití                                          |
| `cost-optimized`    | Nejprve nejlevnější funkční cíl                                                          |
| `reset-aware`       | Zohledňuje okna resetu poskytovatele                                                     |
| `reset-window`      | Směrování na základě oken resetu                                                         |

### base.ts (1170 LOC)

**Abstraktní exekutor**, od kterého dědí každá třída exekutoru (přímo nebo prostřednictvím `DefaultExecutor` a dalších podtříd). Obsahuje:

- `buildUrl()` — výchozí sestavení URL (podtřídy přepisují pro vlastní)
- `buildHeaders()` — výchozí hlavičky (autentizace, content-type)
- `transformRequest()` — ve výchozím nastavení pouze předává dál
- `execute()` — hlavní HTTP smyčka s retry/backoff/breaker

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Zpracovává všechny poskytovatele kompatibilní s OpenAI/Anthropic
  // Poskytovatelé registrují konfigurace (URL, autentizace, hlavičky), ale sdílejí logiku exekutoru
}
```

Chování specifické pro poskytovatele (autentizační hlavičky, základní URL, hlavičky verzí) se konfiguruje prostřednictvím registru poskytovatelů, nikoli samostatnými třídami exekutorů.

````

## Exekutory (150 modulů)

Většinou jeden soubor na poskytovatele. Všechny třídy exekutorů rozšiřují `BaseExecutor` a přepisují to, co se liší; ostatní moduly jsou pomocníci pro jednotlivé poskytovatele (schémata nástrojů, adaptéry fetch/TTS, handlery specifik).

### Běžné vzory

Poskytovatelé se překládají prostřednictvím `getExecutor(providerId)`, který vrací nakonfigurovaného exekutora. Poskytovatelé kompatibilní s OpenAI/Anthropic používají `DefaultExecutor` (`executors/default.ts`). Chování specifické pro poskytovatele (základní URL, autentizační hlavičky, verze API) se konfiguruje v `open-sse/config/providers/`, zatímco transformace těla požadavku se řeší v `open-sse/translator/`.

**Vlastní URL** se nastavuje v konfiguraci poskytovatele:

```ts
// Konfigurace poskytovatele v open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Vlastní autentizace** se řeší prostřednictvím konfigurace autentizace v registru poskytovatelů (API klíč, OAuth, profily hlaviček).

Transformace **vlastního těla požadavku** (např. Anthropic oddělující `system` od `messages`) se registrují pro každého poskytovatele zvlášť v `open-sse/translator/`.

````

### Továrna exekutorů

`executors/index.ts` exportuje `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Překlad probíhá přes `ExecutorRegistry` (`executors/registry.ts`): každý specializovaný exekutor je deklarován ve vestavěné tabulce `executors/index.ts` a při načtení modulu registrován pomocí `registerExecutor(alias, instance)`; `getExecutor()` se dotazuje registru a u každého poskytovatele bez specializovaného záznamu se vrátí k memoizovanému `DefaultExecutor`. Kompletní mapování alias → exekutor vymezuje golden test `tests/unit/executor-map-golden.test.ts`.

## Překladače

Překládejte mezi **3 formáty**: OpenAI, Anthropic, Gemini a také nové Responses API.

### Kdy dochází k překladu

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Běžné překlady:

- `OpenAI → Anthropic`: samostatné pole `system`, hlavička `x-api-key`
- `OpenAI → Gemini`: `contents` namísto `messages`, `systemInstruction`
- `OpenAI → Responses API`: pole `input`, stav `previous_response_id`

### Ošetřené okrajové případy

- Role `developer` → `system` pro jiné poskytovatele než OpenAI
- Role `system` → sloučena do první uživatelské zprávy pro GLM/ERNIE
- `json_schema` → `responseMimeType` + `responseSchema` v Gemini
- `tools` → formát nástrojů specifický pro poskytovatele
- Parametry uvažování (o1, Claude) → ekvivalenty specifické pro poskytovatele

## Server MCP

`open-sse/mcp-server/` implementuje server **Model Context Protocol**:

- **110 nástrojů** (správa poskytovatelů, kombinace, paměť, mezipaměť, komprese, proxy, dovednosti, gamifikace, pluginy, Notion, Obsidian, místní korpus)
- **3 transporty**: stdio, SSE, Streamable HTTP
- **33 rozsahů oprávnění** pro podrobné řízení přístupu

### Registrace nástrojů

Nástroje jsou registrovány jako samostatné soubory v `open-sse/mcp-server/tools/`, přičemž každý exportuje název, schéma, obslužnou funkci a rozsah oprávnění:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Získat snímek stavu systému",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transporty

```ts
// stdio (použití v CLI)
startMcpStdio(server);

// SSE (streamování založené na HTTP)
startMcpSse(server, port);

// Streamable HTTP (moderní MCP)
startMcpStreamable(server, port);
```

### Autorizace

Každé volání nástroje prochází kontrolami rozsahů oprávnění (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Nedostatečný rozsah oprávnění");
}
```

## Transformátory

`open-sse/transformer/` převádí mezi formáty **Chat Completions** a **Responses API**.

### Proč samostatný transformátor?

Responses API je nový formát OpenAI se **stavovými konverzacemi** (`previous_response_id`). Když klient odešle požadavek Responses, OmniRoute:

1. Interně převede Responses → Chat Completions
2. Odešle jej poskytovateli (libovolnému poskytovateli, který podporuje Chat Completions)
3. Převede odpověď zpět do formátu Responses
4. Streamuje převedenou odpověď klientovi

Transformátor (`transformer/responsesTransformer.ts`) poskytuje:

```ts
createResponsesApiTransformStream(): TransformStream
```

Zpracovává:

- Události `response.output_item.added`
- Události `response.output_text.delta`
- Událost `response.completed`
- Mapování volání nástrojů (`function_call` ↔ `tool_calls`)

## Konfigurace

`open-sse/config/` obsahuje konfigurační vrstvu:

| Soubor                        | Účel                                                       |
| ----------------------------- | ---------------------------------------------------------- |
| `providerRegistry.ts`         | Registr chatovacích modelů nad katalogem 375 poskytovatelů |
| `providerModels.ts`           | Aliasy modelů, mapování formátů                            |
| `constants.ts`                | Časové limity, omezení, stavové kódy                       |
| `defaultThinkingSignature.ts` | Výchozí podpis myšlení Claude                              |
| `modelStrip.ts` (v services)  | Odstraňování polí podle poskytovatele                      |

### Schéma registru poskytovatelů

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Validace pomocí Zod při načtení modulu zajišťuje, že všechny konfigurace poskytovatelů jsou platné.

## Výkonnostní omezení

Směrovací modul má striktní výkonnostní limity:

| Operace                                            | Cíl   | Měření                      |
| -------------------------------------------------- | ----- | --------------------------- |
| Vyhodnocení kombinace                              | <10ms | Pro 50 cílů                 |
| Kontrola omezení rychlosti                         | <1ms  | Token bucket v paměti       |
| Přechod na záložní rodinu modelů                   | <5ms  | Definice rodin v mezipaměti |
| Předání požadavku ke směrování                     | <2ms  | Kritická cesta              |
| **Žádné blokující I/O v kritické cestě směrování** | —     | Vše asynchronně             |

## Antivzory

❌ **Synchronní volání databáze v `combo.ts`** — předpočítejte je a uložte do mezipaměti
❌ **Logika opakovaných pokusů v handlerech** — použijte `retry()` ze služby odolnosti
❌ **Přímý přístup ke konfiguraci poskytovatele** — použijte gettery `providerRegistry`
❌ **Natvrdo definované řetězce záložních variant** — definujte je v `modelFamilyFallback.ts`
❌ **Mutace stavu napříč souběžnými požadavky** — používejte pouze kontext s rozsahem požadavku

## Přidání nové komponenty

### Přidání nové služby

1. Vytvořte `open-sse/services/[serviceName].ts` s jasně vymezenou odpovědností
2. Exportujte hlavní obslužnou funkci a všechny konstanty
3. Přidejte jednotkové testy do `tests/unit/services/[serviceName].test.mjs`
4. Integrujte službu do zpracování požadavků v `handlers/chatCore.ts` (pokud souvisí se směrováním)
5. Pokud služba ovlivňuje výběr cíle, aktualizujte logiku směrování v `combo.ts`
6. Zdokumentujte ji v tomto souboru

### Přidání nového exekutoru

1. Vytvořte `open-sse/executors/[provider].ts` rozšiřující `BaseExecutor`
2. Zaregistrujte jej v `config/providerRegistry.ts`
3. Přidejte jej do továrny v `executors/index.ts`
4. Přidejte jednotkové testy pro exekutor
5. Zdokumentujte jej v `docs/architecture/ARCHITECTURE.md`

### Přidání nového nástroje MCP

1. Vytvořte nebo aktualizujte `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definujte schéma Zod pro vstupy
3. Zaregistrujte nástroj v `mcp-server/index.ts`
4. Přidejte jej do matice rozsahů v `mcp-server/auth/`
5. Přidejte jednotkové testy
