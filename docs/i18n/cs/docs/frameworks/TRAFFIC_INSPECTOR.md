Traffic Inspector je integrovaný ladicí nástroj OmniRoute pro provoz HTTPS — nástroj podobný Charles Proxy / mitmweb / HTTP Toolkit, který **rozpoznává LLM** a **rozpoznává agenty**. Nachází se na adrese `/dashboard/tools/traffic-inspector` a přijímá živý provoz až z 5 souběžných zdrojů zachytávání.

**Umístění v dashboardu:** `/dashboard/tools/traffic-inspector`
**Skupina v postranním panelu:** Nástroje (za AgentBridge)
**Viz také:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge je režim zachytávání 1.

### Architektura v jednom odstavci

`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) je sdílený kruhový buffer v paměti (ve výchozím nastavení 1000 záznamů, konfigurovatelný pomocí `INSPECTOR_BUFFER_SIZE`). Všechny zdroje zachytávání do něj zapisují prostřednictvím `push()`. Třída bufferu klasifikuje každý záznam pomocí `kindDetector.ts` (určuje, zda jde o požadavek LLM), vypočítá `contextKey` (otisk systémového promptu pomocí SHA-256) a vysílá data všem odběratelům WebSocketu prostřednictvím `globalTrafficBuffer.subscribe()`. Dashboard se připojuje prostřednictvím `GET /api/tools/traffic-inspector/ws`, při připojení obdrží snímek a následně události `new`/`update`/`clear`.

## §2 Režimy zachytávání

Traffic Inspector podporuje **5 souběžných zdrojů zachytávání**. Každý z nich lze nezávisle zapnout či vypnout. Pole `source` každého objektu `InterceptedRequest` (`src/mitm/inspector/types.ts`) obsahuje jednu z hodnot `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"` nebo `"tproxy"`.

### Režim 1 — AgentBridge (výchozí, vždy zapnutý)

**Zdroj:** Obslužné rutiny AgentBridge (`src/mitm/handlers/base.ts`)
**Mechanismus:** Každé volání `intercept()` v `MitmHandlerBase` zavolá před předáním požadavku `hookBufferStart()` a po dokončení `hookBufferUpdate()`. Není potřeba žádná další konfigurace — funguje ihned po spuštění AgentBridge.
**Dosah:** 9 agentů IDE nakonfigurovaných v AgentBridge
**Poznámka:** Pole `source` v `InterceptedRequest` = `"agent-bridge"`

### Režim 2 — Vlastní hostitelé (přesměrování DNS)

**Zdroj:** Uživatelsky definovaný seznam hostitelů (tabulka `inspector_custom_hosts`)
**Mechanismus:** Přidání hostitele prostřednictvím uživatelského rozhraní přidá do `/etc/hosts` záznam `127.0.0.1 <host>` (vyžaduje sudo). Stávající server MITM AgentBridge (port 443) dynamicky vygeneruje certifikát SNI pro nového hostitele.
**Dosah:** Jakákoli aplikace používající přidaného hostitele — není nutná žádná změna konfigurace aplikace
**Poznámka:** `source` = `"custom-host"`

Příklady použití:

- Monitorování `api.openai.com` ze skriptů Pythonu
- Ladění `my-internal-llm.company.com`
- Zachytávání provozu z mobilních zařízení ve stejné síti (prostřednictvím podvržení ARP — pokročilé)

### Režim 3 — Naslouchání HTTP_PROXY (port 8080)

**Zdroj:** Aplikace používající proměnné prostředí `HTTP_PROXY`/`HTTPS_PROXY`
**Mechanismus:** Sekundární naslouchací služba na portu 8080 (`src/mitm/inspector/httpProxyServer.ts`), která funguje jako standardní explicitní proxy HTTP/HTTPS. Přijímá tunely `CONNECT` (HTTPS) i přímé požadavky HTTP.
**Dosah:** Jakákoli aplikace, která respektuje proměnnou prostředí `HTTP_PROXY` — bez změny DNS a bez sudo
**Poznámka:** `source` = `"http-proxy"`

```bash
# Rychlé zachycení pro jeden příkaz:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# Trvalé zachytávání v relaci shellu:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**Omezení TLS:** Tunely HTTPS `CONNECT` se ve výchozím nastavení zachytávají pouze jako metadata (hostitel, port, časování) — tělo TLS se nedešifruje. Chcete-li kontrolovat celé tělo, zapněte přepínač „Dešifrovat HTTPS v režimu proxy“ (volitelná funkce, vyžaduje důvěryhodný certifikát AgentBridge).

**Konflikt portu:** Pokud se port 8080 již používá, AgentBridge vrátí stav 409 se strukturovanou chybou. Port změňte pomocí proměnné prostředí `INSPECTOR_HTTP_PROXY_PORT`.

### Režim 4 — Celosystémová proxy (pokročilé, volitelné)

**Zdroj:** Nastavení proxy na úrovni operačního systému (platí pro všechny aplikace v počítači)
**Mechanismus:** Pomocí rozhraní API operačního systému přesměruje veškerý provoz HTTP/HTTPS přes naslouchací službu HTTP_PROXY:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **Dosah:** Každá aplikace v počítači, která respektuje systémové nastavení proxy
  **Poznámka:** `source` = `"system-proxy"`

**Bezpečnostní mechanismy:**

- Časovač automatického vypnutí (výchozí hodnota 30 min, konfigurovatelná pomocí `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES`)
- Předchozí stav systémové proxy se uloží do databáze a při vrácení změn se obnoví
- Pokud uživatel přejde jinam, zatímco je proxy aktivní, ovládací panel zobrazí výzvu „Obnovování systémové proxy“
- Uživatelské rozhraní zobrazuje odznak `⚠ Pokročilé` a zaškrtávací políčko pro výslovné potvrzení

### Režim 5 — Transparentní dešifrování TPROXY (Linux, root, volitelné)

**Zdroj:** TPROXY jádra + směrování podle zásad (`src/mitm/tproxy/`)
**Mechanismus:** Označí nová místní odchozí připojení TCP k cílovému portu (výchozí `443`) v řetězci `mangle OUTPUT`, pravidlo `ip rule` přesměruje označené pakety k místnímu doručení a cíl `TPROXY` řetězce `mangle PREROUTING` je předá transparentní naslouchací službě (**IP_TRANSPARENT**) na výchozím portu `8443`. Naslouchací služba ukončí TLS pomocí koncového certifikátu vydaného dynamickou certifikační autoritou **na vyžádání pro každý název hostitele SNI**, zachytí dešifrovanou komunikaci a předá požadavek znovu zašifrovaný původnímu cíli.
**Dosah:** **Libovolní** cíloví hostitelé na cílovém portu — bez podvržení `/etc/hosts`, bez proměnné prostředí `HTTP_PROXY` a bez úpravy celosystémové proxy. Zachytávaný proces nevyžaduje žádnou změnu konfigurace, musí však důvěřovat dynamické certifikační autoritě.
**Poznámka:** `source` = `"tproxy"`

**Požadavky:** Pouze Linux (**IP_TRANSPARENT** je k dispozici pouze v Linuxu), oprávnění **CAP_NET_ADMIN** (root) a nativní doplněk N-API, který je nutné sestavit pomocí sady nástrojů jazyka C (`npm run build:native:tproxy`). Pokud nejsou požadavky splněny, je přepínač na ovládacím panelu deaktivován a zobrazí se popisek „Dešifrování TPROXY vyžaduje Linux + root + nativní doplněk“. Pravidla brány firewall se aplikují a vracejí zpět transakčně (pád nikdy nezanechá pravidlo `mangle`) a při restartu se odstraní. Ochrana proti smyčce založená na SO_MARK zabraňuje opětovnému zachycení vlastního znovu zašifrovaného předávání proxy.

Jde o rozsáhlý subsystém s vlastní specializovanou příručkou pro správce — úplný postup konfigurace brány firewall, dynamickou certifikační autoritu pro jednotlivá SNI a instalační program úložiště důvěryhodných certifikátů, místní směrování, podrobnosti ochrany proti smyčce a schéma konfigurace naleznete v `docs/security/MITM-TPROXY-DECRYPT.md` (git; nekompiluje se do `/docs`). Přepínač se ovládá prostřednictvím `GET / POST / DELETE /api/tools/agent-bridge/tproxy` (poznámka: trasa se nachází pod prefixem AgentBridge, nikoli pod prefixem Traffic Inspector).

### 3.2 Seznam požadavků (levý panel)

- **Virtualizovaný** (`useVirtualList` + `ResizeObserver`): zvládne 1 000 položek bez zamrznutí
- **Automatické posouvání** s přepínačem pro pozastavení během kontroly
- **Barevně odlišený stav**: zelená (2xx), žlutá (3xx), červená (4xx/5xx), šedá (probíhá)
- **Emoji agenta**: 🔵 Antigravity, 🟢 Copilot, 🟠 Kiro, 🟣 Codex, 🔷 Cursor, 🟤 Zed, 🟡 Claude Code, ⚫ Open Code, 🌐 vlastní hostitel
- **Barevný pruh kontextu**: levý okraj o šířce 1 px obarvený podle `contextKey` (SHA-256 systémového promptu) — vizuálně seskupuje související konverzace
- **Odložené načítání těla**: v kartách podrobností se zpracuje pouze tělo vybraného požadavku (zabraňuje vykreslování 1 000 × 1 MB těl)

| Filtr **Živě**      | Zobrazí pouze probíhající (otevřené) požadavky — přepínač `liveOnly` (viz §4.6)     |

- Šířka seznamu: minimálně 280 px, maximálně 720 px, uložena v `localStorage` (`inspector.listWidth`)

## §4 Funkce zohledňující LLM

### 4.1 Detektor druhu (`src/mitm/inspector/kindDetector.ts`)

Klasifikuje každý požadavek jako `"llm"`, `"app"` nebo `"unknown"` pomocí 4 signálů:

1. **Registr hostitelů** — přibližně 18 známých názvů hostitelů API LLM (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot atd.)
2. **Vzory cest** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses` atd.
3. **Struktura těla** — detekuje pole `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input`
4. **Indicie z user-agentu** — `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor` v řetězci UA

Vlastní hostitelé přidaní prostřednictvím režimu 2 převezmou svou hodnotu `kind` ze vstupu formuláře (výchozí hodnota je `"custom"`).

### 4.2 Slučovač SSE (`src/mitm/inspector/sseMerger.ts`)

**Nezávislá implementace vytvořená metodou clean-room.** Analýza událostí se řídí
[algoritmem WHATWG pro události odesílané serverem](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream),
zatímco rekonstrukce se řídí veřejnými schématy streamování služeb [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) a
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent).

Rekonstruuje výslednou zprávu asistenta ze surových rozdílových událostí SSE:

- **Anthropic**: shromažďuje `content_block_delta` podle indexu; zpracovává `text_delta`, `input_json_delta` (volání nástrojů), `thinking_delta`
- **OpenAI**: shromažďuje volby a volání nástrojů Chat Completions a výstupní položky Responses API
  podle indexu
- **Gemini**: shromažďuje `candidates[i].content.parts`
- **Neznámé**: vrací surové události beze změny

Karta Response zobrazuje přepínač: **„Surové události ↔ Sloučené“**.

### 4.3 Normalizátor konverzací (`src/mitm/inspector/conversationNormalizer.ts`)

**Nezávislá implementace vytvořená metodou clean-room.** Normalizace je definována místními
black-box kontrakty a veřejnými schématy zpráv OpenAI, Anthropic a Gemini; není použit
žádný zdrojový kód implementace z upstreamu.

Před vykreslením převádí formáty zpráv OpenAI, Anthropic a Gemini do jednotného typu `NormalizedConversation`:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // zprávy / obsah / výzva z těla požadavku
  response: NormalizedTurn[]; // odpověď asistenta (sloučená pomocí sseMerger)
  contextKey: string | null; // otisk systémové výzvy SHA-256
}
```

Typy bloků: `text`, `tool_use`, `tool_result`. Karta Conversation používá tuto strukturu bez ohledu na poskytovatele.

### 4.4 Barevné rozlišení klíče kontextu (`src/mitm/inspector/contextKey.ts`)

- Vypočítá `SHA-256` systémové výzvy (první zprávy `role:system`, pole `system` nebo `systemInstruction` služby Gemini)
- Vrátí 12znakový hexadecimální prefix (`"a3f9c2..."`)
- Frontend mapuje klíč na deterministickou barvu HSL pro pruh levého okraje
- **Filtr „stejný kontext“**: kliknutí na štítek `ctx #a3f` přidá filtr, který zobrazí pouze požadavky se stejným otiskem

Díky tomu lze snadno vizuálně rozlišit různé „persony“ nebo úlohy spuštěné v rámci stejné relace agenta.

### 4.5 Extrakce metadat LLM

U požadavků LLM karta LLM Details extrahuje:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // z těla požadavku nebo odpovědi
  messages: number; // počet tahů
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // true, pokud jde o odpověď SSE
  mappedTo: string | null; // hlavička x-omniroute-mapped
  costEstimateUsd: number | null; // odhadované náklady podle cen OmniRoute
}
```

### 4.6 Živý filtr probíhajících požadavků

Pole `status` požadavku je typu `number | "in-flight" | "error"` — záznam je
přidán jako `"in-flight"` v okamžiku zahájení požadavku a po přijetí odpovědi
(nebo chyby) je **aktualizován na místě**. Přepínač **„Živě“** na panelu nástrojů
(`liveOnly`, klíč i18n `trafficInspector.liveOnly`) omezuje seznam na záznamy,
jejichž `status === "in-flight"`, což umožňuje sledovat otevřená připojení v reálném čase.

Filtr je čistý predikát na straně klienta v souboru
`src/lib/inspector/matchesTrafficFilter.ts`:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

Stav přepínače se nachází v `useTrafficFilters` (hooky řídicího panelu inspektoru) a
kombinuje se s ostatními filtry (profil, hostitel, agent, zdroj, stav, kontext).

### 4.7 Přiřazení procesu (Linux)

V systému Linux lze každý zachycený požadavek přiřadit k **místnímu procesu,
ze kterého pochází**. Do `InterceptedRequest` jsou přidána dvě volitelná pole:

```ts
pid?: number;          // ID zdrojového procesu (pouze Linux)
processName?: string;  // název zdrojového procesu (pouze Linux)
```

`src/mitm/inspector/processAttribution.ts` mapuje dočasný port _klienta_
daného připojení na PID a název následujícím způsobem:

1. Načte `/proc/net/tcp` a `/proc/net/tcp6`, aby nalezl inode socketu daného
   portu (`parseProcNetTcpForInode`, čistý parser testovatelný pomocí fixtures).
2. Prohledá `/proc/<pid>/fd/` a hledá symbolický odkaz na `socket:[<inode>]`.
3. Načte název procesu z `/proc/<pid>/comm`.

Mezipaměť s TTL 1 sekunda omezuje při zátěži náklady na prohledávání procfs. Přiřazení
funguje na principu **best-effort** — jakékoli selhání vede k hodnotě `null` a nikdy
neblokuje zachytávání. V systémech macOS/Windows funkce vrací `null` (zástupná
implementace; podpora `lsof`/`GetExtendedTcpTable` bude doplněna později).

## §6 Zabezpečení

Traffic Inspector zobrazuje **veškerý zachycený provoz HTTPS**, včetně autorizačních hlaviček a těl požadavků. Jsou zavedena následující opatření:

| Opatření                                  | Podrobnosti                                                                                                                                                                                                                           |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LOCAL_ONLY**                            | Všechny trasy a koncový bod WebSocketu jsou dostupné pouze přes rozhraní loopback (vynuceno v `routeGuard.ts` před ověřením identity)                                                                                                 |
| **Maskování tajných údajů**               | Lineární skener `maskSecret()` rediguje přihlašovací údaje Bearer podle RFC 6750, klíče s prefixem poskytovatele a dlouhé neprůhledné tokeny před voláním `TrafficBuffer.push()`                                                      |
| **Limit velikosti těla**                  | Těla větší než `INSPECTOR_MAX_BODY_KB` (výchozí hodnota 1024 KB) jsou zkrácena s upozorněním `„(zkráceno kvůli výkonu)“`                                                                                                              |
| **Sanitizace hlaviček**                   | Názvy se převádějí na malá písmena; hlavičky pro rámování, hlavičky typu hop-by-hop a hlavičky ověřování proxy jsou odstraněny; soubory cookie jsou zcela redigovány; hodnoty přihlašovacích údajů jsou předány funkci `maskSecret()` |
| **CSP**                                   | Striktní zásady Content Security Policy na stránkách Traffic Inspectoru zabraňují XSS prostřednictvím vložených těl odpovědí                                                                                                          |
| **Ve výchozím nastavení bez persistence** | `TrafficBuffer` je uložen v paměti a při restartu serveru se ztratí. Relace jsou trvale uloženy pouze tehdy, když je jejich záznam výslovně spuštěn                                                                                   |

### Použitá závazná pravidla

| Pravidlo                          | Použití                                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | Všechny chybové odpovědi HTTP z tras Traffic Inspectoru jsou sanitizovány                         |
| **#15 + #17** `isLocalOnlyPath()` | `/api/tools/traffic-inspector/` je LOCAL_ONLY + SPAWN_CAPABLE (příkazy systémového proxy serveru) |

### Známá omezení

- **Režim systémového proxy serveru** ovlivňuje všechny aplikace v počítači, včetně klientů VPN a SSO. Vždy jej používejte s časovačem automatického vypnutí. Nepoužívejte jej na sdílených počítačích.
- **Tunel CONNECT pro HTTPS**: Režim 3 (HTTP_PROXY) zachycuje u cílů HTTPS pouze metadata tunelu, pokud není povoleno zachytávání TLS. Toto chování je záměrné — transparentní zachytávání bez důvěryhodného certifikátu AgentBridge by u těchto aplikací narušilo ověřování TLS.
- **Řetězce natvrdo zadané v některých komponentách**: Některé komponenty uživatelského rozhraní (F7/F8) obsahují malý počet řetězců zadaných natvrdo, které dosud nejsou pokryty klíči i18n. Ty jsou zdokumentovány jako známé omezení ve zprávě o nedostatcích i18n; budou migrovány v následné úpravě. Dotčené řetězce jsou dekorativní popisky uživatelského rozhraní, které pro funkční použití nevyžadují překlad.

## §7 Řešení problémů

### Odpojení WebSocketu

Pokud živý výpis zobrazuje „Odpojeno“:

1. Zkontrolujte, zda server stále běží: `GET /api/tools/traffic-inspector/capture-modes`
2. Znovu načtěte stránku — WebSocket se znovu připojí a obdrží nový snímek
3. Pokud byl server restartován, vyrovnávací paměť v operační paměti byla vymazána — staré záznamy jsou ztraceny, pokud nebyla relace zaznamenána

### Konflikt portu 8080

Pokud se režim HTTP_PROXY nepodaří spustit:

```bash
lsof -i :8080    # najděte proces
```

Změňte port:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### Systémový proxy server nebyl vrácen do původního stavu

Pokud OmniRoute selže, zatímco je aktivní celosystémový režim proxy:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

Pokud řídicí panel zjistí, že stav v DB označuje proxy jako aktivní, při příštím načtení také nabídne možnost „Vrátit systémový proxy server do původního stavu“.

### Plná vyrovnávací paměť

Když vyrovnávací paměť dosáhne hodnoty `INSPECTOR_BUFFER_SIZE` (výchozí hodnota je 1000), nové záznamy postupně nahrazují nejstarší. Pokud dochází ke ztrátě důležitých požadavků:

- Zvyšte `INSPECTOR_BUFFER_SIZE` (např. na 5000) — vyšší spotřeba paměti výměnou za delší uchování
- Zaznamenejte relaci, aby se příslušný úsek trvale uložil do DB
