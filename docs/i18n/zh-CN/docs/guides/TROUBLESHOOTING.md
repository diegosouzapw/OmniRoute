| -------------------- | --------------------------------- | --------------------------------------------------------------------------------------- |
| "无法连接"           | OmniRoute 未运行                  | 运行 `omniroute` 或 `docker restart omniroute`                                          |
| "API 密钥无效"       | 你的密钥错误或已过期              | 从提供者网站重新复制密钥                                                                |

## 详细故障排除

---

### 免费提供者的速率限制（429 / 400 / 401）

**症状**：将 `model: "auto"` 与免费/无需身份验证的提供者（opencode、auggie 等）一起使用时，会间歇性收到 `HTTP 429`、`400` 或 `401`，而不是正常响应。稍后使用相同提示词重试时，请求能够成功，但自动化任务（cron 作业、智能体、脚本）会在首次失败时中断。

**根本原因**：三个相互独立的故障模式叠加在一起：

1. **提供者速率限制（`429`）**：免费套餐可能会实施按时间窗口计算的配额。一批并行调用会耗尽该配额，因此在窗口重置之前，后续请求会被拒绝。
2. **透传中的故障模型（`400`/`401`）**：`auto/*` 池可能包含来自 `opencode` 的透传模型，这些模型已在目录中注册，但没有有效凭据（例如 `oc/north-mini-code-free` → `401`）。自动路由器尝试其中一个模型后失败，而错误会在回退生效前向上传播。
3. **并发放大效应（负载下出现 `429`）**：当多个智能体/cron 会话同时请求 `auto` 时，总请求速率会超过免费提供者所能承受的范围，导致正常调用也被标记为滥用。

**已验证的修复方法（社区报告，2026-08-10）**：调整三个环境变量，让轮换、并发控制和回退机制吸收免费套餐的不稳定性，而不是因此直接失败：

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 遇到 400/401 时跳转到其他模型/提供者（跳过故障的透传模型）
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # 明确设置重量级请求的准入上限（默认未设置：不限制请求数量，请参阅下方说明）
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # 将有界等待时间提高到超过慢速上游所使用的 RATE_LIMIT_MAX_WAIT_MS 默认值
```

请在 OmniRoute 进程环境中设置这些变量（即守护进程，例如通过 LaunchAgent plist 或 `systemctl edit`），然后重启 OmniRoute。轮换标志是效果最显著的单项设置：它会将硬性失败转化为对池中健康提供者的透明重试。

**注意**：`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` 会限制可同时运行的重量级（长上下文）请求数量；该限制是准入门控，而不是提供者速率限制器。**#503-fanout 更新：** 此变量不再默认设置（现在仅在显式配置时生效，如上所示）——重量级请求的准入改由自动推导的字节预算（`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`）进行门控，该预算会根据主机的实际内存上限自动调整，因此全新部署即使完全不设置此变量，也应显著减少 `503 chat_admission_busy` 拒绝；在此处显式设置它仍会完全按照文档所述生效。显式字节预算覆盖值会被限制在 8 MiB–2 GiB 之间。`413 body_exceeds_budget` 并非暂时性错误：请增加该字节预算、降低 `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`，或提高进程内存上限。`inflight_bytes_budget` 卸载表示暂时性资源争用，仍可重试。每个提供者的速率限制（`open-sse/services/rateLimitManager.ts`）由 `RATE_LIMIT_MAX_WAIT_MS`、`RATE_LIMIT_MAX_QUEUE_DEPTH` 和 `RATE_LIMIT_AUTO_ENABLE` 单独控制——请参阅 `.env.example`。

**如何验证修复是否生效**：快速连续运行两次你的代理/cron，并确认两次都成功。修复前，第二次运行通常会抛出 `429`/`401`。修复后，失败（如果有）会自动重试，并最终完成调用。你也可以执行 `curl /monitoring/health`，观察提供者连接上的 `rateLimitedUntil` 字段，以及受影响提供者对应的 `circuitBreakers.providerBreakers[].state`——状态可能是 `CLOSED`、`DEGRADED`、`OPEN` 或 `HALF_OPEN`（参见 `src/shared/utils/circuitBreaker.ts`）；持续失败的提供者会依次从 `CLOSED → DEGRADED → OPEN` 切换，直到重置窗口允许一次探测请求通过（`HALF_OPEN`）。

**如果仍然看到 429**：该提供者的当前活动账户确实已经耗尽了其_配额_（而不只是触发了速率限制）。请在 OmniRoute 控制面板的 Providers → Accounts 中为同一提供者添加第二个账户，或混用另一个免费提供者（例如 `routeway`、`auggie`）。轮换只对临时性的速率限制/400/401 有帮助；配额彻底耗尽时，需要第二组凭据或其他提供者。

**如果在视觉模型（`auto/vision`、`bazaarlink/*`）上看到 403**：已连接的账户缺少包含视觉功能的付费套餐，或 API 密钥权限不足。请在提供者控制面板中确认该密钥的权限范围包含视觉/多模态功能，或连接一个付费层级账户，并将其保留为视觉请求的目标账户。

## npm install 警告（ERESOLVE / peer / deprecated）

运行 `npm install -g omniroute` 时，你可能会看到大量警告，例如 `npm warn ERESOLVE`、对等依赖通知和 `deprecated` 消息。**这些都是预期行为，不会造成影响。** 如果输出中出现 `added <N> packages`，则表示安装已成功。

要抑制对等依赖解析警告，请使用 OmniRoute 支持的安装方式：

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` 只会抑制 `ERESOLVE` 和对等依赖通知。弃用通知仍然可见，因为它们来自传递依赖的第三方包；这些通知并不表示安装失败。

这些警告源于 OmniRoute 无法控制的第三方包中已过时的对等依赖版本范围：

1. **`marked-terminal` 要求 `marked >=1 <16`，但实际找到 `marked@18`** — 实际使用中运行正常；只是上游的对等依赖范围已过时。
2. **`deprecated prebuild-install@7.1.3`** — 这是一个传递依赖的原生二进制文件获取辅助工具。它不用于
   安装已固定版本的 `wreq-js` 传输绑定，也不表示 Web Cookie
   提供程序的传输配置失败。

**无需采取任何操作** — 除非对上游包进行分叉，否则无法完全消除这些警告。

## npm 安装脚本被阻止警告（全局安装）

<a name="npm-install-scripts-blocked-warning-global-install"></a>

运行 `npm install -g omniroute` 时，较新版本的 npm（v11+ 和 v12+）默认会阻止包生命周期脚本，并显示安装脚本警告：

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### 可以忽略此警告吗？

**可以部分忽略，但不建议在不运行脚本的情况下使用。** OmniRoute 提供了平稳降级机制：如果无法从独立应用程序包中加载原生 `better-sqlite3` 绑定，应用程序会依次回退到 `node:sqlite` 或 `sql.js` 等替代驱动程序（请参阅 [SQLite 运行时解析](../ops/SQLITE_RUNTIME.md)）。服务器仍然可以启动，但使用 `sql.js` 之类的 WASM 回退方案会禁用 SQLite WAL（预写式日志）模式，并增加内存和磁盘同步开销。

### 实际需要哪些脚本？

并非所有被阻止的脚本都是运行 OmniRoute 所必需的：

- **必需（`omniroute`、`better-sqlite3`）：** OmniRoute 从 Next.js 独立应用程序包（`dist/`）运行。在安装期间，npm 会在顶层 `node_modules/better-sqlite3/` 中下载或编译特定于主机的原生 SQLite 驱动程序。随后，OmniRoute 的 `postinstall` 脚本（`scripts/build/postinstall.mjs`）会验证这些特定于主机的二进制文件并将其复制到 `dist/node_modules/`，以便独立服务器可以访问它们。如果 `omniroute` 的 postinstall 脚本被阻止，则会跳过此复制步骤。
- **可选/传递依赖（`keytar`、`@parcel/watcher`、`@swc/core`、`protobufjs`、`esbuild`）：** 这些是构建辅助工具、监视工具或系统密钥链实用工具。允许其运行可避免构建警告，但核心路由功能并不依赖它们。
- **排除（`onnxruntime-node`）：** 这是用于本地 AI 嵌入的可选依赖，OmniRoute 的运行**不需要**它。其 postinstall 脚本会从 NuGet 下载约 300MB 的 CUDA 资源；除非你明确打算在受支持的硬件上使用本地 ONNX 加速，否则请勿将其加入允许列表。

### 推荐的修复方式

要在全局安装期间允许所需的安装脚本并消除警告，请通过 `--allow-scripts` 允许 OmniRoute 及其原生依赖：

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

或者，要为你的用户账户永久配置此设置，使其应用于所有全局安装，请运行：

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### 验证安装

安装完成后，运行内置诊断工具，以确保原生绑定和运行时环境均正常：

```bash
omniroute doctor
```

## Gemini Web 和 Playwright Chromium

如果 Gemini Web 请求返回 `503`，并提示未安装 Playwright Chromium，则表示 npm 软件包已存在，但缺少浏览器二进制文件。Playwright 有意将浏览器下载与 npm 软件包安装分开，因此在安装浏览器之前，出现此响应属于预期行为。

对于全局 npm 安装，请从 OmniRoute 软件包的目录中安装 Chromium，以便浏览器缓存归属于同一个 Playwright 安装：

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

安装后重启 OmniRoute，然后重试 Gemini Web 请求。如果通过 Docker 镜像运行 OmniRoute，请使用 `-web` 镜像（或 `runner-web` 构建目标），其中已包含 Chromium 及其依赖项；基础镜像不包含这些内容。

## 杀毒软件误报

<a name="antivirus-false-positives"></a>

### Avast/AVG 以 `MD:HttpRequest-inf[Susp]` 为由隔离 `README.md`

**这是误报。没有任何内容受到感染，也无需采取任何操作。**

Avast 和 AVG 会运行一种启发式检测，将包含大量类似 HTTP 请求链接的纯文本/Markdown 文件标记为可疑。OmniRoute 的 `README.md` 包含在 npm 包中（它列在 `package.json` → `files` 中），因此全局安装后会位于 `node_modules/omniroute/README.md`；其中包含约 15 个 `http://localhost:20128/...` 示例（MCP HTTP/SSE 端点、A2A `.well-known` URL 和 `curl` 代码片段）。这样的链接密度足以触发该启发式检测。

如果此问题近期才开始出现：文件的性质并未发生变化。README 扩充了端点表（新增了 MCP HTTP + SSE + A2A）并加入了更多 `curl` 示例，从而超过了检测阈值。

该文件只是静态文档，不包含任何可执行内容。您可以安全地将其从隔离区恢复。

**处理方法：**

1. **停止通知** — 在杀毒软件中排除安装目录（Avast：设置 → 例外），添加全局 `node_modules` 路径和/或 OmniRoute 数据目录（`~/.omniroute/`）。
2. **报告误报** — <https://www.avast.com/false-positive-file-form.php>，并附上被隔离的 `README.md`。这才是能帮助所有人的解决方式，因为问题在于厂商的启发式检测对文本文件反应过度。

**为什么我们不在自身这一侧“修复”此问题：**所有示例都使用 `http://localhost`，而 localhost 若不引入自签名证书带来的麻烦，就无法使用 `https`。为了规避某一家厂商的启发式检测而篡改文档，会损害所有读者的体验，只为迁就扫描器的缺陷。

### Kaspersky 将桌面应用标记为 `PDM:Trojan.Win32.Generic`

**这是行为启发式检测造成的误报。没有任何内容受到感染。** Kaspersky 的 `PDM:` 前缀表示该判定来自其主动防御模块（System Watcher），该模块会判断安装程序执行了哪些操作，而不是将其与已知恶意软件进行匹配。触发检测时，Kaspersky 会“回滚”整个安装过程，即删除已经写入的文件，导致应用损坏或缺失。

被标记的文件是桌面应用所捆绑的、已声明的开源依赖项中的标准组成部分，例如：

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` 和
  `workerProcessEntry.js` — [Playwright](https://playwright.dev)，用于应用内提供者登录和浏览器支持的聊天功能的浏览器自动化库。
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — 固定版本的 `wreq-js` 原生绑定，用于在基于 Web Cookie 的提供者中发送带有浏览器指纹的 HTTP 请求（`<arch>` 为 `x64` 或 `arm64`）。

**触发原因：**Windows 安装程序**尚未进行代码签名**，因此未签名的 NSIS 安装程序没有任何信誉记录，行为启发式检测会以最高强度运行。再加上捆绑的原生 DLL，以及写入 `%LOCALAPPDATA%\Programs\OmniRoute` 下的数百个 `.js` 文件（包括 Next.js 独立构建生成的、带哈希后缀的包目录），这些因素足以触发该启发式检测。代码签名已在计划中；在完成之前，新版本仍可能重复出现此问题。

**处理方法：**

1. **首先验证下载文件**（排除文件遭到篡改的可能）。每个发行版都会发布 `latest.yml`，其中的 `sha512` 字段（base64）涵盖 `OmniRoute.Setup.<version>.exe` 安装程序。在 PowerShell 中，从包含安装程序的文件夹运行：
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   输出必须与 `latest.yml` → `sha512` 一致。如果不一致，请删除该文件，并仅从 [GitHub 发行版页面](https://github.com/diegosouzapw/OmniRoute/releases)重新下载。
2. **恢复并排除** — 从隔离区恢复被回滚的项目，并为 `%LOCALAPPDATA%\Programs\OmniRoute` 添加排除项（Kaspersky → 设置 → 威胁和排除项），然后重新安装。
3. **报告误报** — <https://opentip.kaspersky.com/>。用户提交的误报报告确实能够加快加入允许列表的速度。

## Node.js 兼容性

<a name="nodejs-compatibility"></a>

### 登录页面崩溃或显示“Module self-registration”错误

**原因：** 您正在运行的 Node.js 版本不符合 OmniRoute 批准的安全运行时最低要求。最常见的情况是，正在运行的旧版 Node 22 或 24 补丁版本低于 OmniRoute 要求的安全补丁最低版本。

**症状：**

- 登录页面显示空白屏幕或服务器错误
- 控制台显示 `Error: Module did not self-register` 或类似的原生绑定错误
- 如果运行时不符合支持的安全策略，登录页面会显示一个包含您 Node 版本的**橙色警告横幅**

**修复方法：**

1. 安装受支持的 Node.js LTS 版本（推荐：Node.js 24.x）：
   ```bash
   nvm install 24
   nvm use 24
   ```
2. 验证版本：`node --version` 应显示 `v24.0.0` 或 24.x LTS 系列中的更新版本
3. 重新安装 OmniRoute：`npm install -g omniroute`
4. 重新启动：`omniroute`

> **受支持的安全版本：** `>=22.22.2 <23` 或 `>=24.0.0 <27`。完全支持 Node.js 24.x LTS (Krypton) 和 Node.js 26。

### npm v11+：未安装 `better-sqlite3`（Cannot find module）

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**原因：** npm v11（随 Node.js 24+ 提供）默认阻止可选
依赖项的安装脚本。由于 `better-sqlite3` 列在 `optionalDependencies`
中并且需要原生编译（`node-gyp rebuild`），npm 会静默跳过它。

**症状：**

- 服务器启动时崩溃，并显示 `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` 显示“No such file or directory”
- `npm ls better-sqlite3` 显示 `(empty)`

**修复方法：**

1. 批准安装脚本并重新安装：
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. 或者手动安装预构建包：
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. 验证其是否正常工作：`node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS：`dlopen` / “slice is not valid mach-o file”

<a name="macos-native-module-rebuild"></a>

**原因：** 全局执行 `npm install -g omniroute` 后，包内的 `better-sqlite3` 原生二进制文件可能是针对与本地运行环境不同的架构或 Node.js ABI 编译的。当预构建二进制文件与您的环境不匹配时，这种情况在 macOS（包括 Apple Silicon 和 Intel）上很常见。

**症状：**

- 服务器启动后立即失败，并显示 `dlopen` 错误
- 错误包含 `slice is not valid mach-o file`
- 完整示例：

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**修复方法——针对您的本地环境重新构建（无需降级 Node.js）：**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **注意：** 此操作会根据您的本地 Node.js 版本和 CPU 架构重新编译原生绑定，从而解决二进制文件不匹配问题。官方支持的运行时范围是 **`>=22.22.2 <23` 或 `>=24.0.0 <27`**（位于 `src/shared/utils/nodeRuntimeSupport.ts` 中的 `SUPPORTED_NODE_RANGE`，与 `package.json` 的 `engines` 字段保持一致）。使用 `better-sqlite3` v12.x 时，完全支持 Node.js 24.x LTS (Krypton) 和 Node.js 26。

## 代理问题

<a name="proxy-issues"></a>

### 提供者验证显示“fetch failed”

**原因：** API 密钥验证端点（`POST /api/providers/validate`）此前会绕过代理配置，导致在必须通过代理路由的环境中验证失败。

**修复（v3.5.5+）：** 此问题现已修复。提供者验证现在通过 `runWithProxyContext` 路由，并自动遵循提供者级别和全局代理设置。

### 令牌健康检查失败并显示“fetch failed”

**原因：** 后台 OAuth 令牌刷新未按连接解析代理配置。

**修复（v3.5.5+）：** 令牌健康检查调度程序现在会在尝试刷新之前，按连接解析代理配置。请更新到 v3.5.5+。

### SOCKS5 代理返回“invalid onRequestStart method”

**原因：** 在 Node.js 22 上，undici@8 调度器与 Node 内置的 `fetch()` 实现不兼容。

**修复（v3.5.5+）：** 当代理调度器处于活动状态时，OmniRoute 现在会使用 undici 自身的 `fetch()` 函数，以确保行为一致。请更新到 v3.5.5+。

### WSL 下的 MITM 代理：Windows 主机上的桌面应用未被拦截

**原因：** MITM 代理及其 CA 证书会安装到 OmniRoute 的运行环境中。在 WSL 下，该环境是 Linux 客户机，而 AI 桌面应用（Kiro、Trae、Copilot、Zed 等）则运行在 Windows 主机上。主机应用不信任客户机的证书存储，也不会通过客户机的系统代理进行路由，因此无法对桌面应用启用拦截。

**建议：** 请在与要拦截的桌面应用相同的操作系统上原生运行 OmniRoute（Windows 应用使用 Windows；macOS/Linux 同理）。如果将 OmniRoute 保留在 WSL 中并以主机应用为目标，则需要在 Windows 主机上手动信任生成的 CA 证书，并将每个主机应用的网络/代理设置指向 WSL 代理端点——这是一种不受支持且不稳定的配置。

## 提供者问题

### “Language model did not provide messages”

**原因：** 提供者配额已耗尽。

**修复：**

1. 检查控制面板中的配额跟踪器
2. 使用带有回退层级的组合
3. 切换到更便宜或免费的层级

### 速率限制

**原因：** 订阅配额已耗尽。

**修复：**

- 添加回退：`cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- 使用 GLM/MiniMax 作为低成本备用方案

### OAuth 令牌已过期

OmniRoute 会自动刷新令牌。如果问题仍然存在：

1. 控制面板 → 提供者 → 重新连接
2. 删除并重新添加提供者连接

### Kiro 多账户：第二个账户会使第一个账户失效

**原因：** Kiro 的后端对每个 OIDC 客户端注册仅允许一个活动会话。
当两个账户共享同一个已注册客户端时（v3.8.0 之前导入的连接），
刷新其中一个账户的令牌会使另一个账户的刷新令牌失效。

**修复（v3.8.0+）：** 重新导入受影响的连接。
从 v3.8.0 开始，每个通过**导入令牌**、
**Google/GitHub 社交登录**或**自动导入**创建的新 Kiro 连接都会自动注册自己
专用的 OIDC 客户端。因此，该连接将完全隔离，刷新一个
账户不会影响任何其他账户。

在 v3.8.0 _之前_导入的连接没有按连接单独设置的客户端
注册。这些连接仍会使用共享的社交身份验证刷新端点。
要实现隔离，请从控制面板 → 提供者中删除旧连接，然后通过
上述三种导入流程中的任意一种重新添加。

有关完整详情以及并排添加两个 Kiro 账户的分步说明，
请参阅 [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md)。

## 云端问题

### 云同步错误

1. 确认 `BASE_URL` 指向正在运行的实例（例如 `http://localhost:20128`）
2. 确认 `CLOUD_URL` 指向云端端点（例如 `https://omniroute.dev`）
3. 确保 `NEXT_PUBLIC_*` 的值与服务端的值保持一致

### 云端 `stream=false` 返回 500

**症状：** 对云端端点进行非流式调用时出现 `Unexpected token 'd'...`。

**原因：** 上游返回 SSE 载荷，而客户端期望 JSON。

**临时解决方案：** 对云端直连调用使用 `stream=true`。本地运行时包含 SSE→JSON 回退机制。

### 云端显示已连接但提示“API 密钥无效”

1. 从本地仪表板 (`/api/keys`) 创建一个新密钥
2. 执行云同步：启用云端 → 立即同步
3. 旧密钥或未同步的密钥在云端仍可能返回 `401`

## Docker 问题

### Docker IPv6 / 连接重置

<a name="docker-ipv6"></a>

**症状：** `curl http://localhost:20128/v1/models` 返回 `curl: (56) Recv failure: Connection reset by peer`。仪表板和无需身份验证的端点可以正常工作，但需要身份验证的端点会失败——这看起来像身份验证问题，但实际上并不是。

**原因：** `docker run -p 20128:20128` 会同时发布到 `0.0.0.0`（IPv4）和 `::`（IPv6），但容器内的进程仅监听 IPv4。在 `localhost` 优先解析为 `::1` 的主机上，连接会到达已发布的 IPv6 端口，但其后没有监听器 → 连接被重置。

**修复方法：**

1. **快速诊断：** 运行 `curl -4 http://localhost:20128/v1/models`。如果添加 `-4` 后可以正常工作，而不添加时失败，则存在 IPv6 绑定不匹配的问题。
2. **永久修复：** 在 `docker run` 命令中使用 `-p 127.0.0.1:20128:20128`，显式绑定到 IPv4：
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   这会强制使用 IPv4 绑定，同时避免将代理暴露在主机的所有网络接口上。

## 弹性设置

### 自动速率限制未触发

- 自动速率限制仅适用于 API 密钥提供者（不适用于 OAuth/订阅）
- 验证 **设置 → 弹性 → 提供者配置文件** 是否已启用自动速率限制
- 检查提供者是否返回 `429` 状态码或 `Retry-After` 标头

### 调整指数退避

提供者配置文件支持以下设置：

- **基础延迟** — 首次失败后的初始等待时间（默认：1s）
- **最大延迟** — 等待时间的上限（默认：30s）
- **倍数** — 每次连续失败时延迟增加的倍数（默认：2x）

### 防止惊群效应

当大量并发请求访问受速率限制的提供者时，OmniRoute 会使用互斥锁 + 自动速率限制来串行化请求并防止级联故障。对于 API 密钥提供者，此机制会自动启用。

### 聊天请求失败并返回 503 / chat_admission_busy

**症状：**

- 聊天补全端点返回可重试的 `503` 响应，其错误代码为
  `chat_admission_busy`。
- 响应包含 `Retry-After`。自 #12135 起，该值根据观测到的
  占用情况计算得出——取请求已等待的 `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` 窗口与当前重量级租约已持有时间中的较大值——向上取整到
  整秒，并以 60 秒为上限。在空闲门控状态下，它会保留历史下限：基于
  字节的路径为 2 秒，基于结构的路径为 1 秒（后者还包含
  `reason: "structure_limit"`）。
- 当另一个重量级聊天请求或长时间运行的流式响应仍在
  处理中时，可能会发生这种情况。

基于字节的响应正文为：

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

基于结构的响应使用相同的类型和代码，其消息为
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
并包含 `reason: "structure_limit"`。
在默认阈值下，如果请求至少包含 `200` 条消息、
至少 `64` 个工具或至少 `32,000` 个估算令牌，或者有界结构估算
耗尽了 `10,000` 个已访问节点或深度 `12` 的边界，则该请求属于结构重量级请求。

**原因：** 这是 OmniRoute 内部有意执行的负载卸除，而不是上游提供者故障。
每个进程都使用进程本地防护机制，在保留并解析大型请求正文之前预留有限的
重量级容量。重量级租约会在 SSE 响应的整个生命周期内保持占用。

**#503 扇出：** 在此修复之前，防护机制使用固定的请求数量
（`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`，默认值为 `1`）限制并发，而不考虑主机内存，因此编码代理的
扇出（多个子代理/CLI，正文通常 > 256 KB）会使有效
并发数降至约 1，并在完全正常的负载下返回 503。防护机制现在会自我调节：它由根据
进程实际内存上限自动推导出的摄取字节预算（`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`）进行门控，
同时还会参考实时资源压力信号——因此，它只会在主机确实承受内存压力时
卸除负载，而不会仅仅因为同时到达了多个重量级请求就这样做。旧的数量上限（`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`）
仍会生效，但仅限于你显式设置它的情况。

当容量繁忙时，重量级请求会先等待最多
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`（默认为 `RATE_LIMIT_MAX_WAIT_MS`；`0` 表示禁用等待），以便有槽位释放，
然后才返回可重试的 `503`。设置有界等待是为了让会并发扇出重量级子请求的代理式客户端
（OpenCode、Claude Code、Cursor）将突发请求串行化，
而不是在立即被拒绝时耗尽其全部重试预算并在任务中途失败。
当前重量级租约占用情况、解析后的字节预算和实时压力严重程度会显示在
`GET /api/monitoring/health` → `chatAdmission`（`inflightBytes`、`maxInflightBytes`、
`budgetSource`、`pressureSeverity`、`countCapEnabled`）中——请在修改任何环境变量之前检查这些值。
设置 → 弹性 → 请求队列 → 并发请求并不控制此机制；该设置
控制的是另一套独立的提供者请求队列机制。

**修复方法：**

1. 首先重试。客户端应遵循 `Retry-After` 并使用退避，而不是立即
   重复请求。
2. 在调整任何参数之前，检查 `/api/monitoring/health` → `chatAdmission`。`countCapEnabled:
false` 和充足的 `maxInflightBytes` 表明自动推导的预算已在正常
   工作；如果 `pressureSeverity` 为 `high`/`critical`，则表示主机确实内存不足——
   这无法通过准入环境变量解决，需要增加 RAM 或减小工作负载。
3. 仅当 `/api/monitoring/health` 显示自动推导的预算对于
   你的主机确实过小时（这种情况很少见——它已能从容器扩展到裸机），才应直接使用
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` 覆盖它，而不是退回使用旧版请求数量上限。

有关权威的准入设置，请参阅[环境变量参考](../reference/ENVIRONMENT.md#4-security--authentication)。

## 可选的 RAG / LLM 故障分类（16 个问题）

一些 OmniRoute 用户会将网关部署在 RAG 或智能体技术栈之前。在这些配置中，经常会出现一种奇怪的现象：OmniRoute 看起来运行正常（提供者在线、路由配置正常、没有速率限制警报），但最终答案仍然是错误的。

实际上，这些事故通常源于下游 RAG 流水线，而不是网关本身。

如果你希望使用一套通用术语来描述这些故障，可以使用 WFGY ProblemMap。这是一个采用 MIT 许可证的外部文本资源，定义了十六种反复出现的 RAG / LLM 故障模式。概括来说，它涵盖：

- 检索漂移和上下文边界破坏
- 空索引或过期索引及向量存储
- 嵌入与语义不匹配
- 提示词组装和上下文窗口问题
- 逻辑崩溃和过度自信的回答
- 长链路和智能体协调故障
- 多智能体记忆和角色漂移
- 部署和引导启动顺序问题

思路很简单：

1. 调查错误响应时，记录：
   - 用户任务和请求
   - OmniRoute 中的路由或提供者组合
   - 下游使用的任何 RAG 上下文（检索到的文档、工具调用等）
2. 将事故映射到一两个 WFGY ProblemMap 编号（`No.1` … `No.16`）。
3. 将编号与 OmniRoute 日志一起存储在你自己的仪表板、运行手册或事故跟踪器中。
4. 使用对应的 WFGY 页面来判断是否需要更改 RAG 技术栈、检索器或路由策略。

完整文本和具体方案位于此处（MIT 许可证，纯文本）：

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

如果你没有在 OmniRoute 后面运行 RAG 或智能体流水线，可以忽略本节。

## v3.8.0 已知问题

以下是 v3.8.0 版本特有的问题及其当前解决方法。如果后续补丁中提供了修复，此条目将被更新或删除。

### Devin CLI 身份验证失败

**症状：**

- 调用由 Devin 支持的工具时出现“Devin CLI not found”或“auth failed”
- CLI 运行时检查报告 `installed=false`

**原因：**

- `CLI_DEVIN_BIN` 指向不存在的路径
- 主机上未安装 Devin CLI

**修复方法：**

1. 安装适用于你平台的 Devin CLI
2. 在 `.env` 中设置 `CLI_DEVIN_BIN=/usr/local/bin/devin`（或实际路径）
3. 重启 OmniRoute，并从 **仪表板 → CLI 工具**重新测试

### 模型冷却状态卡住（手动重置）

**症状：**

- 即使过期时间已经过去，模型仍显示为处于冷却状态
- 尽管时间戳已是过去时间，组合路由仍会跳过该模型

**手动重置：**

- **仪表板：****设置 → 模型冷却** → 在受影响的卡片上单击**重新启用**
- **API：**使用管理身份验证标头调用 `DELETE /api/resilience/model-cooldowns`

### Command Code 提供者连接失败并返回 403

**症状：**

- 测试 Command Code 提供者连接时返回 403
- 新增提供者后，其卡片显示“unauthorized”

**原因：**OAuth 流程未完成（未收到回调或令牌未持久化）。

**修复方法：**

- 从 CLI 运行 `omniroute providers` 以重新触发 OAuth 流程，或者
- 从**仪表板 → 提供者 → Command Code → 重新连接**重新运行 OAuth

### ModelScope 返回激进的 429 冷却

**症状：**

- 少量突发请求后，ModelScope 出现非常短或立即生效的冷却
- 组合路由比预期更早跳过 ModelScope

**原因：**ModelScope 会发出提供者特有的 `Retry-After` 标头。v3.8.0 针对这些标头提供了专门处理，因此较旧版本会将其误读为通用速率限制提示。

**修复方法：**

- 确保使用的是 v3.8.0 或更高版本
- 验证**设置 → 弹性**下的 `useUpstream429BreakerHints` 开关已启用

### 生产环境中缺少 OMNIROUTE_WS_BRIDGE_SECRET

**症状：**

- 在远程生产主机上运行时，每个 Codex/Responses WebSocket 桥接请求都返回 401
- WebSocket 桥接握手在连接后立即关闭

**原因：**生产环境中缺少 `OMNIROUTE_WS_BRIDGE_SECRET` 环境变量。

**修复方法：**

1. 生成随机密钥：`openssl rand -hex 32`
2. 在生产服务器环境中设置 `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>`（以及在任何与该桥接通信的客户端中设置）
3. 重启 OmniRoute

### Responses API：后台模式降级为同步模式

**症状：**

- 日志中记录警告：`background mode degraded to synchronous`
- `background: true` 请求返回普通同步响应，而不是后台作业句柄

**原因：**v3.8.0 有意将 Responses API 上的 `background: true` 降级为同步执行，并同时发出警告。完整的异步后台执行将在未来提供。

**修复方法：**

- 调整客户端，使其调用时不带 `background`，或者
- 等待提供完整异步后台模式的后续版本（关注变更日志）

## 启动缓慢 / 就绪超时

如果 CLI 输出 `⚠ Server did not respond within 60s`，但服务器实际上正常工作，则说明就绪探测的超时预算对于你的环境而言过短。

这种情况常见于 Windows（杀毒软件、文件系统监视器）或启动工作负载较重的容器中。

**解决方法 — 增加超时预算：**

```bash
# 通过环境变量（在多次启动之间持续生效）：
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 分钟
omniroute serve

# 通过 CLI 标志（仅本次生效）：
omniroute serve --ready-timeout 180000
```

默认值为 60 000 ms（60 秒）。该警告仅供参考；服务器会继续在后台启动，并将在启动完成后可供访问。

有关 `OMNIROUTE_READY_TIMEOUT_MS` 的完整详情，请参阅 [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md)。
