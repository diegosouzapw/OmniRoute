`open-sse/config/providerPluginManifest.ts` 定义了 JSON 安全的提供者插件契约。`open-sse/config/providerPluginManifestRegistry.ts` 将该契约绑定到当前的提供者注册表，供 Bifrost、CLIProxyAPI 或未来的 Go/Rust 路由器等 sidecar 使用。TypeScript 注册表仍然是事实来源，但 sidecar 可以使用该清单，而无需导入执行器代码、OAuth 默认值、请求头或进程环境状态。

对于在进程外运行的 sidecar，也可以通过 HTTP 的
`GET /api/v1/provider-plugin-manifest` 获取同一份清单。

OmniRoute 通过 `X-OmniRoute-Provider-Manifest-Url` 请求头向 Bifrost 和 CLIProxyAPI 提供该 URL。当 sidecar 需要使用公共 URL 或容器网络 URL，而不是本地请求来源时，请设置 `OMNIROUTE_PROVIDER_MANIFEST_URL`。

## 刷新清单

该 HTTP 端点返回 `Cache-Control: public, max-age=60` 和强 `ETag`。sidecar 应保留最近一次验证通过的清单，并在刷新时通过 `If-None-Match` 发送其 ETag。`304 Not Modified` 响应没有响应体；sidecar 应继续使用其缓存的清单。如果不存在经过验证的缓存清单，sidecar 必须发送无条件请求，而不是接受 `304`。

## 目标

推动提供者元数据逐步转向插件契约，使低延迟 sidecar 最终能够接管高频请求路径，同时 OmniRoute 继续将 TypeScript 路由作为策略网关和回退方案。该清单是增量式扩展：它本身不会改变请求路由。

## 契约

该清单包含：

- 提供者 id 和别名
- 上游格式和执行器名称
- 认证类型、认证请求头和可选的认证前缀
- 静态端点元数据
- sidecar 适用性，以及提供者应继续使用 TS 路径时的明确原因
- JSON 安全的模型元数据，例如上下文长度、视觉/推理标志以及不支持的参数
- 能力标签，包括 `apikey`、`oauth`、`custom-executor`、
  `passthrough-models`、`responses`、`sidecar-candidate`、`usage-fetch` 和 `usage-supported`

该清单有意排除：

- OAuth 客户端密钥和默认密钥值
- 运行时环境解析
- 请求头和公共凭据辅助函数
- 动态 URL 构建器
- 执行器函数
- 会话池内部实现

## 能力标签

`capabilities` 是从注册表条目派生并经过排序的标签数组。集成方应将其视为“此提供者能做什么”这一问题的机器可读答案，而不是重新读取 TypeScript 源代码。

| 标签                 | 含义                                                    |
| -------------------- | ------------------------------------------------------- |
| `apikey`             | 接受 API 密钥（`authType` 为 `apikey` 或 `optional`）。 |
| `oauth`              | 使用 OAuth 或会话流程。                                 |
| `responses`          | 提供 OpenAI Responses API 基础 URL。                    |
| `passthrough-models` | 直接提供上游模型，而不是使用静态目录。                  |
| `custom-executor`    | 运行非默认执行器，因此继续使用 TypeScript 路径。        |
| `sidecar-candidate`  | 映射 `sidecar.eligible`——可安全考虑导入 sidecar。       |
| `usage-fetch`        | 已接入用量或配额获取器（`getUsageForProvider`）。       |
| `usage-supported`    | 用量 API 接受此提供者（`isSupportedUsageConnection`）。 |

`usage-fetch` 仅用于发现。它表示 OmniRoute 知道如何读取该提供者的用量；它不会启用获取操作、改变配额语义，也不意味着已为该提供者启用 Dashboard 配额组件——该组件由 `USAGE_SUPPORTED_PROVIDERS` 单独控制。事实来源是 `open-sse/services/usage/fetcherProviders.ts` 中的 `USAGE_FETCHER_PROVIDERS`。

该列表以用量分发器所接受的字符串为键，因此混合使用了规范 id 和别名，其长度略大于带标签的提供者数量：未包含在清单注册表中的聊天提供者条目（例如 `firecrawl` 搜索提供者和 `amazon-q` ACP 提供者）没有可供添加标签的清单条目。

`usage-supported` 表示服务器和 Dashboard 的用量路由是否接受该提供者的连接。它映射 `isSupportedUsageConnection()`（`src/lib/usage/providerLimits.ts`）和 `supportsProviderQuota()`（`src/shared/utils/providerQuotaVisibility.ts`），二者均由 `USAGE_SUPPORTED_PROVIDERS`（`open-sse/services/usage/supportedProviders.ts`）控制。与 `usage-fetch` 不同，它仅根据提供者 id 生成——运行时守卫执行 `USAGE_SUPPORTED_PROVIDERS.includes(providerId)`，不进行别名解析，因此清单保持相同规则。这两个标签的覆盖范围不同：3 个提供者仅带有 `usage-fetch`（`opencode`、`opencode-zen`、`xai`），1 个提供者仅带有 `usage-supported`（`xiaomi-mimo-token-plan`），因此二者互不蕴含。

## Sidecar 使用

Sidecar 应将 `sidecar.eligible` 视为保守的候选信号，而不是无条件的路由决策。首批导入目标应是使用默认执行器且采用 API 密钥和静态端点的提供者。具有自定义 Web 执行器、OAuth/会话流程、动态 URL 构建器或池配置的提供者，应继续使用 TypeScript 回退路径，直到某个 Sidecar 实现等效行为，且遥测数据证明两者表现一致。

建议的迁移阶段：

1. 从 TS 注册表生成并验证提供者插件清单。
2. 让 Bifrost 或 CLIProxyAPI 为使用 API 密钥和静态端点的提供者导入该清单。
3. 在保持启用 TS 回退机制的同时，通过 `OMNIROUTE_RELAY_BACKEND` 后面的 Sidecar 路由符合条件的提供者。
4. 仅当成功率、p99 延迟、流式传输行为和不支持参数的处理方式与 TS 路径一致时，才提升提供者。
5. 逐个提供者系列添加 Sidecar 原生插件，以支持自定义执行器。

## 为什么不直接在 Next 中嵌入提供者

Next 前端不应负责执行提供者请求，而应调用 API 边界。然后，后端可以决定使用 TypeScript 执行器、Bifrost、CLIProxyAPI，还是未来的原生 Sidecar。这样可以在移交给任何 Sidecar 之前，集中处理请求签名、允许列表检查、数据库策略和回退行为。
