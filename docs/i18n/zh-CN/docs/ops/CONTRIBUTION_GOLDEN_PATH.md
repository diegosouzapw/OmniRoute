使用本指南为拉取请求选择最小且可靠的开发循环。本指南不会取代下方链接的特定领域架构和安全文档；它将每种常见的变更类型与其契约、针对性检查和 CI 覆盖范围关联起来。

## 每项变更都遵循的路径

1. **编辑前选择基础分支。** 找到版本号最高的活跃 `release/v*` 分支，并基于其最新提交创建分支。将该分支作为目标，而不是 `main`。如果某个发布分支正处于冻结期，请勿将其作为目标；请使用 [分支与发布模型](BRANCHING_MODEL.md) 中所述的下一个活跃周期。
2. **明确契约。** 识别变更影响的每个目录、模式、生成产物、公共 API 或用户界面。下表给出了最小起始集合。
3. **编写或更新针对性测试。** 对 `src/`、`open-sse/`、`electron/` 或 `bin/` 的生产代码变更，必须在同一个 PR 中包含自动化测试。先运行能够证明相关行为的最小测试文件集，然后运行列出的针对性门禁检查。
4. **让 CI 运行广泛的测试矩阵。** 完整的单元测试分片、Vitest、覆盖率渐进门槛和生产构建会在 PR 上运行。仅当针对性测试失败表明影响范围更广，或变更横跨多个子系统时，才在本地运行广泛的测试套件。
5. **评审前完成同步。** 获取活跃基础分支，检查其新增提交以及你的分支相对于它的差异，然后按照贡献者工作流，通过变基或合并来同步基础分支。应从源文件解决生成文件和目录的冲突，重新生成它们，再次运行针对性循环，并确认 PR 的目标仍是活跃发布分支。
6. **记录证据。** 在 PR 模板中列出已运行的命令、所有新增或变更的测试文件、迁移或功能标志，以及仍待完成的所有仅限 CI 的验证。

## 按变更类型划分的标准路径

以下命令是最低限度的针对性检查，并不表示可以跳过直接覆盖你所变更行为的测试。

### 提供者

**契约**

- `src/shared/constants/providers/` 中的提供者定义，以及其在 `src/shared/constants/providers.ts` 中的组合。
- `open-sse/config/providerRegistry.ts` 或其拆分出的注册表文件中的模型和能力。
- 执行器/转换器选择、OAuth 或 API 密钥配置、仪表板资源，以及适用时生成的提供者参考文档。
- 公共凭据必须使用 `resolvePublicCred()`；错误响应必须使用共享的脱敏错误辅助函数。请参阅 `docs/security/PUBLIC_CREDS.md`（位于 git 中；不会编译到 `/docs`）和[错误脱敏](../security/ERROR_SANITIZATION.md)。

**针对性循环**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # 当目录发生变化时；提交生成的差异
npm run lint
```

还要测试每个受影响的请求类别：聊天、Responses、图像、嵌入、音频或视频。将生成的目录和基准差异作为契约变更进行审查；不要盲目接受它们。

### 路由

**契约**

- `src/shared/constants/routingStrategies.ts` 中的公共策略值和 UI 元数据。
- `open-sse/services/combo.ts` 和 `open-sse/services/combo/` 下的分派与排序逻辑。
- Combo 模式、持久化、弹性状态、模型能力，以及 API/UI 控件。
- 行为发生变化时，请参阅 [Auto-Combo 引擎](../routing/AUTO-COMBO.md)和弹性相关文档。

**针对性循环**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # 策略或分派逻辑发生变化时
npm run check:known-symbols      # 策略注册发生变化时
npm run lint
```

在本地使用确定性的模拟上游测试。实时 Combo 冒烟测试需要凭据，并且属于手动测试，不能替代 CI。

### UI / UX

**契约**

- `src/app/` 和 `src/shared/components/` 下的 Next.js 路由/页面与共享组件边界。
- API 响应结构、加载/空/错误状态、键盘和屏幕阅读器行为、响应式布局、主题，以及语言区域扩展。
- `src/i18n/messages/en.json` 中的英文 UI 源字符串；不要硬编码面向用户的新文案。

**针对性循环**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

对于交互或视觉变更，请运行应用，并检查窄视口和宽视口。CI 会运行生产构建和更广泛的测试套件；视觉行为仍需要适合该变更的针对性组件测试、Playwright 测试或有记录的手动检查。

### i18n

**契约**

- `src/i18n/messages/en.json` 是 UI 源；`config/i18n.json` 是语言区域源。
- CLI 目录单独位于 `bin/cli/locales/` 下。
- 必须完整保留 ICU 占位符和标签。不要翻译产品/提供者/模型名称、协议和标头名称、命令、代码/JSON 标识符、URL、环境变量，或 `OmniRoute`、`OAuth`、`MCP` 和 `A2A` 等受保护术语。当前源列表为 `scripts/i18n/glossary/protected-terms.json`。

**针对性循环**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # 当 CLI 字符串/目录发生变化时
npm run lint
```

这是针对现有系统的指导，并非扩展其工具或键模型的邀请。在替代系统的设计过程中，应保持 i18n 补丁范围精准。除非任务明确要求生成翻译，并且你已经审查了生成的差异，否则不要运行会调用外部服务的翻译命令。

### CLI

**契约**

- `bin/cli/` 中的公共命令和标志、生成的 API 命令、退出代码、stdout/stderr 和
  JSON 输出结构、配置/环境行为以及打包文件。
- CLI 面向用户的字符串必须使用 CLI i18n 层，并保持 `en`/`pt-BR` 目录同步。
- 保持 Node 作为受支持的运行时，并维持已发布的二进制契约。

**聚焦循环**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # 生成的/捆绑的 CLI 变更
npm run check:pack-policy     # 软件包公开范围变更
npm run lint
```

当行为取决于解析、文件或退出状态时，请在临时数据目录中使用完全一致的命令。CI 会执行更广泛的软件包产物和生态系统检查。

### 数据库

**契约**

- `src/lib/db/` 下的领域模块；直接导入特定模块（旧的 `localDb.ts` 重新导出层已移除）。
- `src/lib/db/migrations/` 下带编号、可幂等执行的 SQL 迁移、事务安全性、升级行为、索引，以及受架构影响的每个调用方。
- 路由和处理程序绝不能直接执行原始 SQL。

**聚焦循环**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

添加迁移时，请同时测试全新数据库和从先前架构升级的情况。数据库测试必须关闭句柄，并在清理期间调用 `resetDbInstance()`。仅当尽力支持的 Bun 适配器路径发生变化时才运行 `npm run test:bun:db`；Node 仍是权威运行时。

### 构建 / 部署

**契约**

- 根目录和工作区清单/锁文件、`scripts/build/`、Next.js 独立程序集、`dist/` 软件包内容、Electron 平台元数据、CI 工作流以及部署哨兵。
- 必须保持受支持的 Node 版本范围以及 `CLAUDE.md` 中列入允许列表的 Bun 用法不变。
- 构建产物保持不被跟踪；依赖项、许可证、工作流和软件包策略均适用。

**聚焦循环**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # 依赖项或锁文件变更
npm run check:pack-policy      # 已发布软件包公开范围变更
npm run lint
```

仅当变更影响编译、独立程序集、资源或运行时捆绑时，才在本地使用 `npm run build`。仅将 `npm run build:release` 用于发布/部署验证。CI 的构建是最终的跨平台信号；平台特定的 Electron 变更需要相应的聚焦构建或冒烟测试证据。

## 本地候选版本循环

源代码测试无法证明打包后的产物能够启动：打包清单、裁剪后的依赖项和原生二进制文件相关的问题，只有在 tarball 被安装并启动后才会暴露。`npm run dev:candidate`
（`scripts/dev/candidate.mjs`）是 RFC #8084 中“一次构建 / 验证 / 提升”流程的本地实现：它构建一个候选版本，验证该确切产物，通过目录重命名将其提升，并在提升后的槽位未通过健康检查时将其回滚。

```bash
npm run dev:candidate -- run --dry-run --json  # 输出计划，不进行任何更改
npm run dev:candidate -- run                   # 构建 + 验证 + 提升，自动回滚
npm run dev:candidate -- build                 # npm pack + 安装到 _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # 在空闲端口上启动，检查 /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current，current → previous
npm run dev:candidate -- rollback              # 交换 current 和 previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # 复用在其他位置（CI）构建的 tarball
```

- **只构建一次。** `build` 会打包当前工作树（它需要 `dist/server.js`，因此请先运行
  `npm run build:release`），或复制 `--from-tarball` 指定的文件，然后将 tarball 安装到一个隔离的 npm 前缀目录中，因为 tarball 不包含 `node_modules`。id 是简短的 `HEAD`
  sha（当工作树存在本地更改时带有 `-dirty`），对于 tarball 则为 `tgz-<sha256>`。如果一个干净的 id 已经构建，则会直接复用而非重新构建；传入 `--force` 可强制重新构建。
- **验证软件包，而非源代码。** `validate` 使用全新的 `DATA_DIR=<candidate>/data`、伪造的密钥启动已安装的 CLI
  （`serve --port <free port>`），并从环境中移除操作者的 `OMNIROUTE_API_KEY`、`STORAGE_ENCRYPTION_KEY` 和 `INITIAL_PASSWORD`，从而检查全新安装在无密钥回环配置下的行为。它会等待
  `GET /api/health` 返回 200，要求 `GET /v1/models` 返回 200，停止进程组，并将判定结果与 tarball 哈希一起记录在 `validation.json` 中。
- **提升同一个产物。** 如果候选版本没有针对其当前 tarball 哈希的成功验证记录，`promote` 会拒绝提升。默认活动槽位为 `_artifacts/candidate/current`；`--target <dir>`
  可选择同一文件系统中的其他目录，其上一版本槽位为 `<dir>.previous`。每次重命名都是原子的；如果执行过程中失败，则会反向撤销已经完成的重命名。
- **回滚。** `run` 会再次验证提升后的槽位；如果该检查失败，则将 `current` 和 `previous` 交换回来。首次验证失败的候选版本绝不会被提升。

所有内容都写入已被 git 忽略的 `_artifacts/candidate/`；现有的 OmniRoute 安装及其数据目录绝不会被改动。提升后的 CLI 位于
`_artifacts/candidate/current/prefix/bin/omniroute`；使用它时，请通过你自己的 `DATA_DIR` 启动。退出码：`0` 表示成功，`1` 表示验证或提升失败，`2` 表示用法错误或缺少构建。

## 本地循环与 CI

| 每个补丁都在本地运行                            | CI 提供广泛的信号                          |
| ----------------------------------------------- | ------------------------------------------ |
| 上述直接行为测试和类别门禁                      | 分片的完整单元测试套件和串行测试           |
| `npm run lint`                                  | Vitest 测试套件以及覆盖率/质量渐进门槛     |
| 仅当受影响的契约有要求时才进行类型检查或构建    | 生产构建、安全、文档、依赖项和 PR 策略门禁 |
| 仅当自动化无法验证行为时才进行手动交互/实时检查 | 工作流配置的跨作业集成和平台检查           |

聚焦的本地循环通过，只能作为已更改契约的有效证据，并不能证明不相关的 CI 检查
也会通过。反之，也不要让每次本地编辑都等待完整的仓库测试矩阵。

## 协调检查清单

请求评审前：

- 确认 PR 的基础分支仍是最高版本的活跃 `release/v*` 分支。
- 拉取该基础分支，并审查自创建分支以来新合入的提交。
- 检查 `git diff <active-base>...HEAD`，确认没有意外变更或生成内容的无关变动。
- 通过更新源文件并重新生成输出来解决目录和生成文档的冲突。
- 完成协调后，重新运行 PR 描述中列出的每项聚焦测试/门禁。
- 切勿仅为适配发生变化的基础分支而削弱断言或删除必需的测试。

有关发布冻结和变更目标分支的规则，请参阅
[分支与发布模型](BRANCHING_MODEL.md)。有关完整的 CI 清单，请参阅
[质量门禁参考](../architecture/QUALITY_GATES.md)。
