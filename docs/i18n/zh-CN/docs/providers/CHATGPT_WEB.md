`chatgpt-web-codex`（别名 `cgpt-codex`）通过经过身份验证的 ChatGPT 浏览器会话桥接 Codex Responses 交互轮次。它独立于已停用的通用 `chatgpt-web` 提供者，并使用 `open-sse/vendor/codex-chatgpt-web/` 下带有 MIT 声明的实现；该实现已更新至上游 v4.0.7 提交 `b59d7dc51b84fb1f465ff1d00f5207f3b2b4a494`。

## 通用提供者停用

先前的通用提供者 ID `chatgpt-web` 和 `cgpt-web` 已不再提供，因为无法确认其 pre-key/工作量证明实现的来源合规性。对任一 ID 的显式请求（包括带斜杠前缀的模型 ID 和持久化别名）都会在向上游发送任何请求之前以 HTTP `410` 和代码 **PROVIDER_RETIRED** 关闭并失败。

迁移 `168_retire_chatgpt_web.sql` 会将匹配的提供者连接标记为已废弃，并使其活跃会话租约失效。它会保留连接历史记录和 API 密钥允许列表；不会向允许列表添加替代访问权限。Codex 提供者及其连接不在此次停用的匹配范围内。

## 前置条件

- 已登录 ChatGPT 会话的完整 Cookie 标头；
- 对于 npm、systemd 和 PM2 安装，需要 Chrome 或 Chromium，以及图形会话或 Xvfb 显示；
- 使用 Docker `web` 配置文件时，需要 `docker-compose.yml` 中的内部 Chromium 服务；
- 本地 Codex 工具需要 OpenAI `tunnel-client` v0.0.13 和 ChatGPT 自定义连接器。

仅工具交互轮次需要隧道。配置好隧道和连接器后，列出的每个路由（包括 `pro`）都可以使用同一种绑定到交互轮次的本地工具能力。

## 控制面板设置

1. 打开 **ChatGPT Web (Codex)** 提供者并添加连接。
2. 粘贴完整的 ChatGPT Cookie 标头、隧道 ID、运行时密钥和自定义连接器名称。新的工具能力设置必须使用新创建且名称恰好为 `OmniRoute Codex v2` 的连接器，并将 Authentication 设置为 None，将 Permissions 设置为 Allow all actions。
3. 运行连接检查。OmniRoute 会打开由浏览器支持的 Temporary Chat，并检测账户是否可使用 Sol 和 Pro。
4. 保存连接。OmniRoute 会将粘贴的 Cookie 替换为经过验证的 Playwright 存储状态，并通过加密凭据抽象层将其与运行时密钥一起存储。

成功保存后不会保留原始 Cookie。当会话过期时，打开该连接，粘贴新的完整 Cookie 标头，然后重新运行检查。编辑对话框中的诊断状态会分别报告浏览器、存储状态、登录、Temporary Chat、隧道、连接器和工具往返情况。

> 切勿提交真实的 Cookie、运行时密钥、存储状态或能力令牌。测试和
> 文档中的值必须始终使用占位符。

## 模型和组合

固定模型路由如下：

- `chatgpt-web-codex/luna` — GPT-5.6 Luna，低推理强度
- `chatgpt-web-codex/think` — GPT-5.6 Luna，中等推理强度
- `chatgpt-web-codex/instant`
- `chatgpt-web-codex/medium`
- `chatgpt-web-codex/high`
- `chatgpt-web-codex/extra-high`
- `chatgpt-web-codex/pro`

可以像添加其他模型一样，将其中任一模型添加到组合中。Codex 应用会将组合名称作为 `model` 发送到常规 Responses 端点 `/v1/responses`；不存在单独的 Codex 端点或模式开关。

Free/Go 账户提供 Luna 路由。具备 Sol 能力的账户提供从 Instant 到 High 的路由，而具备 Pro 能力的账户还会提供 Extra High 和 Pro。每个路由都有固定的后端模型和推理强度；如果显式指定的 Responses 推理强度与其冲突，请求将关闭并失败，而不会静默更改所选的浏览器模式。

请勿重命名或重复使用旧的 `Codex Native` 或 `OmniRoute Codex` 连接器。ChatGPT 会根据连接器身份缓存公共 MCP 合约，而更新后的桥接器使用新的直接交互轮次令牌合约。运行时会拒绝这些旧身份，并要求使用新的 `OmniRoute Codex v2` 连接器。

## 安全模型

- 原生路径要求使用 Responses 请求、可识别的 Codex 客户端，并且线程和轮次标识必须匹配。
- 工作区、沙箱、审批策略和工具目录来自原生 Codex shell；自由形式的提示文本无权控制这些内容。
- ChatGPT 每轮只接收一个短期有效的能力令牌。MCP 代理仅接受 Codex 在该轮中明确提供的工具。
- 自动确认 **仅允许一次** 只会将工具请求返回给 Codex。只有 Codex 决定是否批准和执行。
- 在首次输出之前，一个组合可以回退到另一个兼容目标。输出开始后，提供者、模型、连接和浏览器轮次将保持固定，直到该轮完成。
- Cookie、运行时密钥、存储状态和能力令牌不会出现在提供者响应或请求日志中。

## 无显示器的 VPS 和 Docker

对于 npm、systemd 和 PM2 安装，OmniRoute 会检测常见的 Chrome 和 Chromium 路径。
或者，也可以设置 `CHATGPT_WEB_CODEX_CHROME_PATH`。运行时轮次会特意使用有界面的
Chrome，因为 ChatGPT 会拒绝真正的无头浏览器形态。因此，无显示器主机必须通过私有
Xvfb 显示运行 OmniRoute；仅设置 Chrome 路径并不能提供显示环境。

Docker `web` 配置文件会在内部 Compose 网络上启动 `chatgpt-web-codex-browser`。
该边车容器在 Xvfb 内运行有界面的 Chrome，因此不需要物理显示器。其 CDP
端口不会发布到主机。受保护的浏览器配置文件卷与 OmniRoute 数据卷相互独立，
并且浏览器会获得足够的共享内存。内部 CDP 代理仅侦听 Compose 网络内的端口
`9223`；Chrome 在边车容器中仍仅绑定到回环地址。

`DATA_DIR` 下的监督器租约可防止多个 OmniRoute 进程同时持有相同的隧道和代理状态。
doctor 会报告冲突。

## 交互式恢复

自动化 Docker 路径没有主机可见窗口，但 Chrome 本身在私有 Xvfb 显示中以有界面模式运行。
当 ChatGPT 要求交互式登录或验证时，可以使用现有的 VNC 浏览器基础设施进行恢复。浏览器
UI 和 CDP 必须仅能通过回环地址、经过身份验证的管理连接或 SSH 隧道访问；正常运行期间
noVNC 保持禁用。

## WebSocket 回退

当组合中包含 ChatGPT Web (Codex) 时，Responses WebSocket 桥接器会在连接上游之前请求
HTTP/SSE 回退。随后，请求将通过 `/v1/responses` 传输。
