OmniRoute 发布 npm + Docker 工件。这些门禁提供溯源、清单 (SBOM) 和 CVE 扫描，所有这些都是开源的，并集成到发布工作流中。
**咨询优先**的姿态——它们现在报告，在第一次绿色发布后提升为阻塞。

| 门禁                | 工具                                           | 位置                          | 阻塞？         | 输出                                    |
| ------------------- | ---------------------------------------------- | ----------------------------- | -------------- | --------------------------------------- |
| SLSA 溯源 (npm)     | `npm --provenance` (OIDC)                      | `npm-publish.yml`             | 仅当发布失败时 | npmjs 徽章 / `npm audit signatures`     |
| SBOM npm            | `@cyclonedx/cyclonedx-npm`                     | `npm-publish.yml`             | 仅当生成失败时 | 发布资产 + 工件                         |
| SBOM 镜像           | `anchore/sbom-action` (syft)                   | `docker-publish.yml` (合并)   | 咨询           | CycloneDX 工件                          |
| Trivy CVE (SARIF)   | `aquasecurity/trivy-action`                    | `docker-publish.yml` (合并)   | 咨询           | SARIF (HIGH+CRITICAL) → 安全选项卡      |
| Trivy CRITICAL 门禁 | `aquasecurity/trivy-action`                    | `docker-publish.yml` (合并)   | **阻塞**       | `exit-code: '1'` 在可修复的 CRITICAL 上 |
| osv vulnCount       | `osv-scanner` (`check:vuln-ratchet --ratchet`) | `ci.yml` (`quality-extended`) | **阻塞**       | 棘轮 `metrics.vulnCount` (方向:down)    |
| OpenSSF Scorecard   | `ossf/scorecard-action`                        | `scorecard.yml` (cron)        | 咨询           | SARIF → 安全 + 徽章                     |

镜像 CVE 棘轮在 `docker-publish.yml` 中使用**两个步骤**：SARIF 步骤
(`HIGH,CRITICAL`, `exit-code: 0`) 使 HIGH+CRITICAL 在安全选项卡中可见而不阻塞；
_CRITICAL 门禁_ 步骤 (`severity: CRITICAL`, `ignore-unfixed: true`,
`exit-code: 1`) 在存在**可用修复**的 CRITICAL CVE 时使发布失败。`ignore-unfixed`
防止因没有上游补丁的基础镜像 CVE 而阻塞发布。

## ⚠️ CVE 差异（阻塞 osv/Trivy 门禁）

osv 和 Trivy 将依赖项与**持续增长**的 CVE 数据库进行比较。一个**不触及任何依赖项**的 PR
可能会突然变红，因为现有依赖项中披露了新的 CVE（osv：测量的 `vulnCount` > 基线；Trivy：镜像中出现新的可修复 CRITICAL）。
**这是阻塞 CVE 门禁的预期操作行为，而不是产品回归。**

当 osv 或 Trivy 因新披露的 CVE 而变红时，补救措施是：

1. **升级受影响的依赖项**（首选）——通过 `package.json` `overrides` 升级到已打补丁的版本
   （传递依赖项）或在已打补丁的基础镜像上重建镜像。
2. **如果没有上游修复：**
   - **osv：** 在 `config/quality/quality-baseline.json` 中重新设置 `metrics.vulnCount` 的基线
     （`npm run quality:ratchet -- --update` 不涵盖专用门禁——手动编辑值，
     `direction:down`），并附上理由说明 + 跟踪问题。
   - **Trivy：** 在 `.trivyignore` 中添加一个条目（每行一个 CVE-ID），并附上理由
     注释 + 跟踪问题。`ignore-unfixed: true` 已经自动涵盖没有补丁的 CVE。

当工具不存在或测量失败时（osv-scanner 不在 PATH 中，osv.dev/网络无法访问，无效 JSON），
这两个门禁都会**优雅地跳过**（退出 0）——**测量**失败永远不会阻塞，只有**测量的**回归才会阻塞。

## 已知接受的风险

### extract-zip 2.0.1 — GHSA-7pqw-9j4j-h8q3 / GHSA-jmr9-qjv8-65gv (#14482)

`extract-zip@2.0.1` 带有两个未修补的高危符号链接遍历漏洞。
根据上述 CVE 差异补救措施中的“无上游修复”分支，这是一个**已接受的风险**，而不是一个升级：

- **链条：** `promptfoo` (devDependency) → `@openai/codex-security` → `extract-zip@2.0.1`。
  通过 `package-lock.json` 确认 — 整个依赖树中只有一个包 (`@openai/codex-security`) 声明了 `extract-zip`，并且只有一个包 (`promptfoo`) 声明了 `@openai/codex-security`。
- **链条中不存在任何已修复的版本。** `extract-zip@2.0.1`（2020 年发布）是该包的最终版本 — 它已不再维护。`@openai/codex-security` 的
  当前 npm-latest (`0.1.29`) 仍然拉取 `extract-zip@2.0.1`。
- **无法从生产环境访问。** `promptfoo` 仅作为开发依赖（从不列在 `dependencies` 下），并且 `src/`、`open-sse/` 或 `bin/` 下的文件都没有导入
  `extract-zip` npm 包 — OmniRoute 自己的 `extractZip()` 辅助函数
  (`src/lib/versionManager/binaryManager.ts:93`) 调用原生 `unzip`/`tar`
  并且与此无关。`@openai/codex-security` 还在 extract-zip 的 onEntry 回调之上提供了自己的符号链接遍历保护。
- **请勿**通过 `package.json` `overrides` 别名 `extract-zip` — 唯一可行的
  替代品是 Electron-org-internal，并且与
  `@openai/codex-security` 自己的 onEntry/defaultDirMode/defaultFileMode 检查 API 不兼容；
  覆盖它将悄无声息地破坏该包的安全检查。
- **基线：** 测量的 osv `vulnCount` (3) 已经远低于冻结的
  `config/quality/quality-baseline.json` 基线 (27) — 无需棘轮更改。
- **回归防护：** `tests/unit/extract-zip-14482-exposure.test.ts` 断言了
  上述链条和非生产导入不变性；如果其中任何一个被破坏（例如，未来的 PR 使 `extract-zip` 可从生产环境访问），它将导致 CI 失败。
- **跟踪：** 问题 #14482。
