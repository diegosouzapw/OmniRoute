## 概述

所有 OmniRoute 管理 API 路由均被划分为三个保护层级之一。分类是静态的，定义于 `src/server/authz/routeGuard.ts` 中，并在运行任何其他身份验证分支之前进行评估。

## 层级

### 层级 1 — LOCAL_ONLY

**强制执行方式：** `isLocalOnlyPath(path)` → 回环主机检查  
**绕过：** 默认情况下不可绕过。对于 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 中的路径，仅当请求携带具有 `manage` 作用域的有效 API 密钥时，才提供有限的例外（参见[管理作用域例外](#manage-scope-carve-out)）。

这些路由会生成子进程或执行运行时代码。向非回环流量开放这些路由，将使获取了有效 JWT 的攻击者（例如通过 Cloudflared/Ngrok 隧道）能够触发进程生成——这是一类已知的 CVE（[GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)）。

**GHSA-fhh6-4qxv-rpqj 的含义（攻击类别）：** 管理/代理服务器暴露了一个可启动子进程（`npm install`、`node`、浏览器、代理、`git`、`tar` 等）的端点。如果该端点可从主机外部访问——例如运维人员将 OmniRoute 放在 nginx/Cloudflare/Tailscale 隧道之后且 JWT 泄露，或身份验证配置错误——攻击者便可将“调用 API”转化为“在主机上运行命令”（远程代码执行）。OmniRoute 通过对每个具备进程生成能力的路由，在任何身份验证检查之前无条件执行**回环主机检查**来阻止此类攻击：即使令牌通过隧道泄露，仍然无法访问进程生成端点。

**完整的 LOCAL_ONLY 集合。** 权威来源是 `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`；下表反映了当前状态。`check-route-guard-membership` 门禁会枚举具备进程生成能力的前缀下的每个 `route.ts`，如果其中任何一个未被分类为仅限本地访问，CI 将失败。

#### 管理作用域例外

如果且仅当请求携带 `Authorization: Bearer <api-key>`，且其元数据包含
`manage` 作用域（或 `admin`），部分 LOCAL_ONLY 路径也可以从非环回地址访问。
此例外通过 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 针对每条路径显式启用，
因此任何新增 LOCAL_ONLY 路径默认仍严格限制为仅环回访问。未经身份验证的
请求以及使用非管理密钥的请求仍会被拒绝，并返回 `403 LOCAL_ONLY`。

目前唯一可绕过限制的前缀是 `/api/mcp/`。`/api/cli-tools/runtime/` 和
`/api/services/` 被有意排除，因为它们可以启动任意子进程（`npm install`、
`node`），而这正是 LOCAL_ONLY 层旨在防范的 CVE 类别。

**#7895 — `mcp:connect` 窄作用域：** `/api/mcp/` 例外还接受持有窄作用域
`mcp:connect` 的 Bearer 密钥
（`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`），该作用域通过
`src/server/authz/policies/management.ts` 中的 `hasMcpConnectOrManageScope()`
进行检查。此作用域**仅限** `/api/mcp/` — `mcp:connect` 不会授予对任何其他
管理路由的权限（包括将来可能添加的任何其他 LOCAL_ONLY 绕过前缀），并且它被
刻意排除在 `MANAGEMENT_API_KEY_SCOPES` 之外。持有 `manage`/`admin` 的密钥
仍会与之前完全一样通过此例外；对于只需远程调用 MCP、但不应获得广泛管理权限的
调用方，`mcp:connect` 是一种权限更低的替代方案。

| 请求                                         | 路径                       | 结果             |
| -------------------------------------------- | -------------------------- | ---------------- |
| 非环回，无 Bearer                            | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非环回，Bearer 具有 `manage` 作用域          | `/api/mcp/*`               | 允许             |
| 非环回，Bearer 具有 `mcp:connect` 作用域     | `/api/mcp/*`               | 允许             |
| 非环回，Bearer 不具有 `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非环回，Bearer 具有 `mcp:connect` 作用域     | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 非环回，Bearer 具有 `manage` 作用域          | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 环回，具有任意 Bearer 或无 Bearer            | 任意 LOCAL_ONLY            | 允许（通过关卡） |

#### 运维人员指南与审计

如果您在反向代理或隧道（nginx、Caddy、Cloudflare Tunnel、Tailscale、Ngrok）
后面运行 OmniRoute，环回检查仍会保护上述可启动进程的路由 — 客户端地址为非环回的
请求会在**身份验证运行之前**以 `403 LOCAL_ONLY` 被拒绝，因此即使 JWT 泄露，
也无法触发进程启动。运维人员仍需承担两项责任：

- **不要通过伪造环回客户端 IP 来“修复” 403。** 设置
  `X-Forwarded-For: 127.0.0.1`，或使用将源地址重写为环回地址的代理，会重新引入
  此层原本要阻止的 RCE 类漏洞。请通过代理公开仪表板/API — 切勿公开可启动进程的
  路由。
- **将管理作用域例外保持在最小范围。** 只有 `/api/mcp/` 可以绕过限制，并且只能
  使用具有 `manage` 作用域的 API 密钥。`SPAWN_CAPABLE_PREFIXES` 绝不能添加到
  绕过列表中 — zod schema 会拒绝它们，并且
  `isLocalOnlyBypassableByManageScope` 会在运行时拒绝它们（纵深防御），
  这就是仪表板所说的“无法设为可绕过”的含义。`/api/providers/` 下包含动态段和
  静态路径的可启动进程路由（例如 `/login`、`/refresh-cursor`）由
  `src/shared/constants/spawnCapablePrefixes.ts` 中基于正则表达式的
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` 配套机制覆盖，
  而不是由扁平的 `SPAWN_CAPABLE_PREFIXES` 数组覆盖 — 若要通过该扁平数组捕获
  这些路由，就必须覆盖整个 `/api/providers/` 前缀，这会过度扩大限制范围，
  而远程仪表板确实需要使用该路由树执行提供者 CRUD 操作。

**访问审计** — 要验证没有来自主机外部的请求访问这些路由：

- 打开 `/dashboard/settings/security` 中的 **授权清单**：它会显示实时的 LOCAL_ONLY 前缀列表、哪些前缀可绕过，以及编译时确定的具备进程生成能力（“不可设为可绕过”）的集合。
- 在反向代理/访问日志中搜索上述前缀，并检查是否与非环回客户端地址配对。任何返回 `200` 而非 `403 LOCAL_ONLY` 的此类请求，都意味着代理掩盖了真实客户端 IP——请修复代理。
- 对于这些路径之一，OmniRoute 日志中出现 `403 LOCAL_ONLY` 表示防护机制正在按预期工作，而不是应被忽略的错误。

### 第 2 层 — ALWAYS_PROTECTED

**强制执行方式：** `isAlwaysProtectedPath(path)` → 跳过 `requireLogin=false` 绕过逻辑  
**绕过：** 当 `requireLogin=false` 时也无法绕过；始终需要 JWT

这些路由具有破坏性或不可逆性。如果在“无密码”安装中允许访问这些路由，则同一局域网中的任何人都可以清空数据库或终止服务器进程。

| 路径                                      | 原因                                         |
| ----------------------------------------- | -------------------------------------------- |
| `/api/shutdown`                           | 终止服务器进程                               |
| `/api/settings/database`                  | 数据库导出、导入和清空                       |
| `/api/db-backups`                         | 访问完整的数据库备份归档                     |
| `/api/settings/export-json`               | 导出完整的设置数据块（包括机密信息）         |
| `/api/settings/import-json`               | 替换完整的设置数据块                         |
| `/api/providers/health-autopilot/actions` | 执行自动驾驶修复操作                         |
| `/api/settings/obsidian`                  | 为任意仓库根目录签发可重复使用的 WebDAV 凭据 |

**违规时的响应：** `401 Authentication required`

`/api/settings/obsidian` 也涵盖其 `/webdav` 子路径：`POST` 会将 WebDAV 文件服务指向调用方选择的根目录，并回显新签发的 Basic 凭据；该文件服务由自定义 Node 层在 Next.js 之前提供，位于此管线之外；`DELETE` 会轮换这些凭据，而父路径的 `POST` 会存储 Obsidian REST API 令牌。GHSA-62vw 仅屏蔽了 `GET` 响应中的密码泄露；凭据签发仍处于故障时开放的层级（GHSA-7pq4-8pvv-rx7r）。`enableObsidianVaultSync()` 还会拒绝以下仓库：其本身就是数据目录、位于数据目录内部，或包含数据目录。

### 全新安装的引导仅限环回地址——依据真实对等端，而非 `Host`

如果未配置管理密码（且没有 `INITIAL_PASSWORD`），`src/shared/utils/apiAuth.ts` 中的 `isAuthRequired()` 将仅对环回对等端开放匿名引导。环回身份依次根据以下可信对等端信号判定：带令牌标记的真实 TCP 对等端（`PEER_IP_HEADER` + `VIA_PROXY_HEADER`，即策略所见的信息）、管线自身的 `AUTHZ_HEADER_PEER_LOCALITY` 判定结果（即路由处理程序所见的信息，仅在设置了 `OMNIROUTE_PEER_STAMP_TOKEN` 时可信），或者直接调用方的真实套接字对等端。系统绝不会查询 `Host` / `nextUrl.hostname`，首次密码写入（`POST /api/settings/require-login`）也受相同约束，而不是向所有网络对等端开放（GHSA-7pq4-8pvv-rx7r）。`managementPolicy` 会显式向下传递其自身的 `peerContext` 判定结果，因此 ORIGINAL（剥离前）请求的标头永远不会参与该判定。

### 第 3 层 — MANAGEMENT（默认）

所有其他管理路由。除非配置了 `requireLogin=false`，否则需要身份验证。CLI 令牌可以对这些路由进行身份验证（环回地址 + 有效 HMAC）。

## 评估顺序

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → 回环地址                                  → 继续执行
     → 非回环地址、具有 manage 作用域的 Bearer
        且 isLocalOnlyBypassableByManageScope   → 允许 (management_key)
     → 否则                                      → 拒绝 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → 允许 (system)
  3. hasValidCliToken(headers)?
     → 允许 (cli) [回环地址 + timingSafeEqual HMAC 检查]
  4. isAlwaysProtectedPath(path) 或 requireLogin=true?
     → isDashboardSessionAuthenticated?
        → 允许 (dashboard_session)
     → 不可绕过路径上的具有 manage 作用域的 Bearer?
        → 允许 (management_key)
     → 拒绝 401/403
  5. requireLogin=false?
     → 允许 (anonymous)
```

步骤 1 中的 manage 作用域分支是唯一能够满足 LOCAL_ONLY 路由要求的认证路径；认证后端故障时返回 503（而不是 403），因此数据库过期不会静默降级为“拒绝”。

## 添加具有进程启动能力的新路由

1. 将路径前缀添加到
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_API_PREFIXES`
2. 在 `tests/unit/authz/routeGuard.test.ts` 中添加测试，断言
   `isLocalOnlyPath()` 对新前缀返回 true
3. **绝不要跳过此步骤** — 请参阅 `CLAUDE.md` 中的硬性规则 #15
4. 决定：此路由是否也应属于 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`？
   默认答案是**否**。仅当该路由可以安全地向 manage 作用域持有者公开时才选择加入（即不会启动任意用户控制的代码）。

## 添加可由 manage 作用域绕过的路径

1. 确认该路由不会执行用户提供的代码或命令。如果会，请停止 — 此例外机制并不适用。
2. 将前缀追加到
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`
3. 在 `tests/unit/authz/management-policy.test.ts` 中为全部四种请求形式添加覆盖：无 Bearer（403）、manage Bearer（允许）、非 manage Bearer（403），以及针对每个前缀的回归测试，确保 `/api/cli-tools/runtime/*` 即使带有 manage Bearer 也始终严格限制为回环地址。

## 在 OpenAPI 中记录安全层级

向 `docs/openapi.yaml` 添加新路由时，如果该路由已由 `routeGuard.ts` 分类，请应用对应的供应商扩展：

| routeGuard.ts 分类           | YAML 注解                  | 强制执行规则                             |
| ---------------------------- | -------------------------- | ---------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | 无条件阻止来自非回环地址的访问           |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | 即使 `requireLogin=false` 也要求认证     |
| 内部管理/调试路由            | `x-internal: true`         | 默认不在 /dashboard/api-endpoints 中显示 |
| 无（公开/标准认证）          | （无需注解）               | 由标准 `requireLogin` 控制的访问         |

### 验证

以下两个脚本用于确保 YAML 注解与 `routeGuard.ts` 之间的一致性：

- `scripts/check/check-openapi-coverage.mjs` — 覆盖率低于 99% 时失败
- `scripts/check/check-openapi-security-tiers.mjs` — 当 `x-loopback-only` 或
  `x-always-protected` 注解与编译时常量不一致时失败

这两个脚本都会在预提交钩子和 CI 中运行。

### 误报规则

如果某个路由带有 `x-always-protected` 或 `x-loopback-only` 注解，但并不在
`routeGuard.ts` 常量中，覆盖率脚本将失败。正确的修复方式始终是让 YAML 与
`routeGuard.ts` 实际强制执行的规则保持一致 — 而不是在尚未实现相应强制执行逻辑的情况下，将路由添加到 `routeGuard.ts`。
