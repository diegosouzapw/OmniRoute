> 选择启用，默认关闭（当 `settings.freeAccessPolicy !== "strict"` 时，每个 `auto/*`
> 候选池均保持字节级完全一致）。它是 `hidePaidModels`
> （`open-sse/services/autoCombo/paidModelFilter.ts`，#6512）的更严格版本，适用于需要硬性
> 保证不会产生任何增量费用，而不只是“标注为免费”的运营方。

## 为什么需要此功能，以及为什么仅靠 `hidePaidModels` 还不够

`hidePaidModels` 回答的是“此模型目前是否在 `FREE_MODEL_BUDGETS` 中被归类为免费？”——
这是一个特定时间点的目录事实，通过 `isFreeModel()`/`providerHasFreeModels()`
（`src/shared/utils/freeModels.ts`）进行检查。它无法涵盖以下两个真实风险：

1. `recurring-*`/`one-time-initial` 免费套餐的额度可能已经**耗尽**——目录中仍将该模型
   列为免费，但其背后的账户已无剩余额度。
2. 超出免费套餐额度并不一定会触发硬性停止。某些提供者明确声明永远无法绑定付款
   方式（“无需信用卡”）；其他提供者则没有说明，还有少数提供者会在超出免费额度后
   自动计费。

`hidePaidModels` 无法区分这些情况——它从来就不是为此设计的。STRICT_ZERO_COST 恰好
增加了这两项检查，并针对每个候选项，在类别/层级排序**之前**以及分派**之前**进行
评估——绝不会在请求已经发出后才进行检查。

## 候选项分类

对于候选池中的每个候选项（`open-sse/services/autoCombo/virtualFactory.ts::buildPreparedPool`，
紧接在 `filterPaidOnlyCandidates` 之后）：

1. **完全不在 `FREE_MODEL_BUDGETS` 中** → 排除。这涵盖了真正的付费模型，以及
   OmniRoute 尚未分类的任何提供者/模型——新的候选项默认被排除，而不是被纳入。
2. **`freeType: "keyless"`** → 立即通过，**但仅限于确实通过无身份验证路径进入的
   候选项**（`connectionId === SYNTHETIC_NOAUTH_CONNECTION_ID`，
   `open-sse/services/autoCombo/resilienceCandidateFilter.ts`）。该候选项不存在凭据，
   因此针对它的请求永远不可能产生费用——既不需要也无法进行运行时检查。通过
   **真实**数据库连接访问同一个目录中标记为 `keyless` 的提供者/模型时
   （`connectionId` 是实际连接 ID，或者候选项带有 `allowedConnectionIds`），则
   **不**能使用此快捷路径——`keyless` 元数据专门描述无身份验证路径，而不是提供者的
   一般属性，并且绝不会授权真实的、有凭据的账户。此类候选项会像其他候选项一样
   继续执行检查 3；除非目录条目另行带有 `hardStopGuaranteed: true`，否则会被排除
   （真实的 `keyless` 条目从不具备该属性——此快捷路径是它们确保安全的唯一途径）。
3. **任何其他 `freeType`**（`recurring-daily`、`recurring-monthly`、
   `recurring-credit`、`recurring-uncapped`、`one-time-initial`，以及此模块未进行
   特殊处理的任何未来类型）→ 仅当**以下所有条件**均满足时才通过：
   - 目录条目上设置了 `hardStopGuaranteed: true`
     （`FreeModelBudget.hardStopGuaranteed`，
     `open-sse/config/freeModelCatalog.ts`）——这是根据提供者自身发布的条款
     （例如明确声明“无需信用卡”）**人工筛选并手动设置的事实**，绝不会根据
     `freeType` 或实时 API 响应推导得出。未设置（`undefined`）和 `false` 均视为
     “不保证”。
   - `USAGE_FETCHER_PROVIDERS` 中存在该提供者的用量适配器
     （`open-sse/services/usage.ts`）——这与现有配额仪表板和
     `getUsageForProvider()` 使用的是同一个注册表。若无适配器，则永久排除，直到
     添加适配器为止。
   - **当前实际评估的特定连接**所对应的实时缓存 `FreeAccessState` 为
     `status: "SAFE"`，检查时间在 `settings.autoRefreshProviderQuotaInterval`
     范围内（默认为 180 秒——使用现有设置，而非新增数值），并且报告的
     `remainingFreeAllowance` 高于一个较小的安全余量。
4. **`freeType: "discontinued"`** → 始终排除。

## 连接安全性（按连接验证，绝不按候选项验证）

自动组合池中的候选项并不总是绑定到某一个连接。“逻辑”候选项
（`connectionId: null`）带有一个 `allowedConnectionIds` 允许列表——其中包含一个或多个实际的
提供者连接/账户，任意一个都可以处理该请求——而实际使用的账户将在稍后的分发阶段由
`open-sse/services/combo/autoStrategy.ts` 决定
（将 `allowedConnectionIds` 与其自身的连接选择逻辑取交集，约第 315-331 行）。

STRICT_ZERO_COST 会逐一验证该允许列表中**每个连接**的免费访问状态
（`strictZeroCostFilter.ts` 中的 `evaluateCandidateConnections()`），并将
`allowedConnectionIds` 重写为恰好由返回 `SAFE` 的连接组成的子集——绝不会保留完整的
原始列表，也绝不会任意选择其中一个成员。具体来说：

- 账户 A 为 `SAFE`，账户 B 为 `UNKNOWN`/配额耗尽/需计费 → 只有 A 仍可被选择。
- 所有账户均为 `UNKNOWN` → 该候选项会被完全丢弃（安全集合为空）。
- 如果单连接候选项（直接设置了 `connectionId`，没有允许列表）验证失败，则会被
  直接丢弃，绝不会带着空的 `allowedConnectionIds` 返回。

由于 `autoStrategy.ts` 在选择用于分发的连接之前，已经将 `allowedConnectionIds` 作为硬性
允许列表进行强制约束，因此将其重写为经验证为 `SAFE` 的子集，就足以保证分发时实际使用的
连接始终是该过滤器亲自验证过的连接——绝不会是在同一候选项上的另一个未经验证的账户。回归
验证见 `tests/unit/autoCombo/strict-zero-cost-connection-safety.test.ts`
（无密钥绕过场景 A/B/C、多账户场景 1-5）。

`discovered automatically`：如果明天发布的某个提供者/模型具备正确的元数据（存在于目录中、
带有用量适配器且 `hardStopGuaranteed: true`），那么 OmniRoute 一旦获知它，就可以立即使用——
无需修改代码、无需添加允许列表条目，也无需编辑此模块。某个提供者/模型一旦从目录中移除，也会
以同样的方式消失。回归验证见
`tests/unit/autoCombo/strict-zero-cost-autodiscovery.test.ts`（通过可注入的测试夹具实现，
而非修改真实目录）。

## 配额缓存（`open-sse/services/autoCombo/freeAccessQuota.ts`）

复用 `getUsageForProvider()`——不引入第二套配额系统。其前方设置了一个短期的、进程生命周期内
有效的内存缓存（TTL 等于默认的 `autoRefreshProviderQuotaInterval`），因此，即使请求速率达到
Telegram 的规模，也绝不会导致每个请求中的每个候选项都触发一次实时的计费 API 调用。读取操作
是同步的：缓存未命中时返回 `undefined`（→ 排除，故障时默认拒绝），并在后台触发刷新，供
_下一次_读取使用——候选池构建路径中的任何部分都不会等待网络调用。

当连接因任何原因失败时，`src/sse/services/auth.ts::markAccountUnavailable()` 会立即调用
`invalidateFreeAccessState(provider, connectionId)`，因此下一次构建池时读取到的是干净的
缓存未命中，而不是过期的 `SAFE` 条目——在收到 402/403/配额耗尽响应后，无需等待 TTL 到期。

## ToS 防护（独立于经济安全性）

`excludeTosAvoid`（默认为 `false`）会丢弃人工审核的 `tos` 结论
（`FreeModelBudget.tos`）为 `"avoid"` 的所有候选项——它复用了 `hidePaidModels` 的同级文档
（`docs/reference/FREE_TIERS.md`）已经填充的同一字段。此防护刻意与
`freeAccessPolicy` 分离：候选项可能在经济上属于 `SAFE`，但仍会因合同原因在此处被排除；
而当此防护关闭时，即使启用了 `freeAccessPolicy: "strict"`，该候选项也可以保留。

## 查看防护排除了哪些内容

`GET /v1/auto-combo/{channel}/candidates` 会列出所有候选项，包括此防护原本会阻止进入调度的候选项，
并且每个候选项都带有 `freeAccessExclusion`——满足防护条件时为 `null`，否则为具体原因。
该列表只负责报告，绝不执行排除。关闭此策略后，该字段在所有候选项上均为 `null`，且不会产生任何开销。

| `freeAccessExclusion`  | 含义                                                                                                | 处理方式                                                                                           |
| :--------------------- | :-------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------- |
| `not-in-catalog`       | `FREE_MODEL_BUDGETS` 中不存在该提供者/模型组合。                                                    | 添加人工审核的条目，或接受新组合默认被排除——这是有意为之的设计。                                   |
| `regime-not-free`      | 已收录在目录中，但其 `freeType` 不属于可授予免费访问权限的类型（例如已终止的套餐）。                | 无需修复。该模型需要付费。                                                                         |
| `no-hard-stop`         | 属于免费机制，但 `hardStopGuaranteed` 不为 `true`，因此超出配额后可能会在不作提示的情况下开始计费。 | 核实提供者的条款，并在注释中注明来源后设置该标志——绝不能仅仅为了扩大目录而设置。                   |
| `contradictory-noauth` | 无需身份验证的候选项，其目录条目却不是 `keyless`。元数据不一致时按失败关闭处理。                    | 修复目录条目；这两项事实相互矛盾。                                                                 |
| `exhausted`            | 最新读数表明配额已用尽。                                                                            | 等待重置。此问题会自行解决。                                                                       |
| `state-unknown`        | 没有配额读数，或读数过旧而不可信。                                                                  | 进行检查：提供者可能尚未注册用量适配器，或配额获取操作可能失败。                                   |
| `no-connection`        | 候选项完全没有可供检查的账户。                                                                      | 这不是配额问题：候选项是在没有连接的情况下构建的，因此从未执行过任何查询。请检查候选池的组装方式。 |

最后两个原因尤其值得区分。已耗尽的配额会自行重置；而始终没有读数则意味着查询本身已损坏。
此前，从外部看这两种情况完全相同——候选项只会直接消失。

**仍有一个缺口，而且这是有意保留的。** `excludeTosAvoid` 仍会在构建列表之前移除候选项，
因此人工审核为 `tos: "avoid"` 的模型会在不提供任何原因的情况下消失——这与本节刚刚为零成本防护解决的不可见性问题相同。
若也要弥补此缺口，就必须决定 ToS 排除应报告什么内容；这是一个独立于经济安全性的问题。
本页明确指出此缺口，而不是假装它不存在。

如需进行离线前后对比，`npx tsx scripts/ad-hoc/dry-run-strict-zero-cost.ts` 仍可针对运行中实例的候选项输出使用；
它会读取每个候选项的真实 `connectionId`，因此也会覆盖连接安全路径。无密钥候选项必须使用合成的无需身份验证
`connectionId`，绝不能使用真实连接。目前内置的无密钥自动路径是 OpenCode Free；确切的候选项数量仍取决于实时模型发现，
应在目标部署上进行测量，而不应从旧的运行结果中复制。`recurring-*` 候选项仅在同时具有已注册的用量适配器和
`hardStopGuaranteed: true` 时才会通过；元数据不完整时仍按失败关闭处理。

启用 `excludeTosAvoid: true` 后，所有人工审核为 `tos: "avoid"` 的候选项都会被移除。OpenCode Free
目前带有该结论，因此启用此防护可能会清空某个部署中剩余的无密钥候选池。这是启用 ToS 防护时预期的权衡，而不是错误：
正因如此，该防护默认设置为 `false`（请参阅上文的“ToS 防护”）。

## 启用

```json
PUT /api/settings
{ "freeAccessPolicy": "strict", "excludeTosAvoid": false }
```

这两项新设置均默认采用该功能推出前的值（`"off"` / `false`）——两者均未启用时，不会改变任何现有的 `auto/*` 路由行为。
