पुल अनुरोध के लिए सबसे छोटा विश्वसनीय विकास चक्र चुनने हेतु इस मार्गदर्शिका का उपयोग करें। यह नीचे लिंक किए गए क्षेत्र-विशिष्ट आर्किटेक्चर और सुरक्षा दस्तावेज़ों का
स्थान नहीं लेती; यह प्रत्येक सामान्य परिवर्तन प्रकार को उसके अनुबंधों, केंद्रित जाँचों और CI कवरेज से जोड़ती है।

## प्रत्येक परिवर्तन द्वारा अपनाया जाने वाला मार्ग

1. **संपादन से पहले आधार चुनें।** सबसे ऊँची सक्रिय `release/v*` शाखा खोजें और उसके
   नवीनतम सिरे से शाखा बनाएँ। `main` को नहीं, बल्कि उसी शाखा को लक्षित करें। यदि रिलीज़ फ़्रीज़ सक्रिय है, तो फ़्रीज़ की गई
   शाखा को लक्षित न करें; इसके बजाय
   [शाखाकरण और रिलीज़ मॉडल](BRANCHING_MODEL.md) में वर्णित अगले सक्रिय चक्र का उपयोग करें।
2. **अनुबंधों के नाम दर्ज करें।** ऐसे प्रत्येक कैटलॉग, स्कीमा, जनरेट की गई कलाकृति, सार्वजनिक API या उपयोगकर्ता
   इंटरफ़ेस की पहचान करें जिसे परिवर्तन प्रभावित करता है। नीचे दी गई तालिका न्यूनतम प्रारंभिक सेट बताती है।
3. **केंद्रित परीक्षण लिखें या अपडेट करें।** `src/`, `open-sse/`, `electron/`, या
   `bin/` में उत्पादन परिवर्तनों के लिए उसी PR में एक स्वचालित परीक्षण आवश्यक है। व्यवहार को प्रमाणित करने वाली सबसे छोटी
   परीक्षण फ़ाइलें चलाएँ, फिर सूचीबद्ध केंद्रित गेट चलाएँ।
4. **CI को विस्तृत मैट्रिक्स चलाने दें।** पूर्ण यूनिट शार्ड, Vitest, कवरेज रैचेट और
   उत्पादन बिल्ड PR पर चलते हैं। स्थानीय रूप से विस्तृत सुइट केवल तभी चलाएँ जब कोई केंद्रित विफलता
   व्यापक प्रभाव की ओर संकेत करे या परिवर्तन कई उप-प्रणालियों में फैला हो।
5. **समीक्षा से पहले समन्वय करें।** सक्रिय आधार फ़ेच करें, उसके नए कमिट और उसके सापेक्ष अपने डिफ़ का
   निरीक्षण करें, फिर योगदानकर्ता वर्कफ़्लो के अनुसार आधार को रीबेस या मर्ज करें। जनरेट की गई फ़ाइल और
   कैटलॉग के टकरावों को उनके स्रोत से हल करें, उन्हें फिर से जनरेट करें, केंद्रित चक्र दोबारा चलाएँ और पुष्टि करें कि
   PR अब भी सक्रिय रिलीज़ शाखा को लक्षित करता है।
6. **साक्ष्य दर्ज करें।** PR टेम्पलेट में चलाए गए कमांड, जोड़ी या बदली गई प्रत्येक परीक्षण फ़ाइल,
   माइग्रेशन या फ़ीचर फ़्लैग और अभी लंबित कोई भी केवल-CI सत्यापन सूचीबद्ध करें।

## परिवर्तन प्रकार के अनुसार गोल्डन पाथ

नीचे दिए गए कमांड न्यूनतम केंद्रित जाँचें हैं; वे आपके द्वारा बदले गए व्यवहार को सीधे कवर करने वाले परीक्षण को
छोड़ने की अनुमति नहीं देते।

### प्रदाता

**अनुबंध**

- `src/shared/constants/providers/` में प्रदाता की परिभाषा और
  `src/shared/constants/providers.ts` में उसका संयोजन।
- `open-sse/config/providerRegistry.ts` या उसकी निकाली गई रजिस्ट्री फ़ाइलों में मॉडल और क्षमताएँ।
- लागू होने पर एक्ज़ीक्यूटर/ट्रांसलेटर चयन, OAuth या API-कुंजी कॉन्फ़िगरेशन, डैशबोर्ड एसेट और जनरेट किया गया
  प्रदाता संदर्भ।
- सार्वजनिक क्रेडेंशियल के लिए `resolvePublicCred()` का उपयोग अनिवार्य है; त्रुटि प्रतिक्रियाओं को साझा सैनिटाइज़ किए गए
  त्रुटि हेल्पर का उपयोग करना होगा। `docs/security/PUBLIC_CREDS.md` (git; `/docs` में संकलित नहीं) और
  [त्रुटि सैनिटाइज़ेशन](../security/ERROR_SANITIZATION.md) देखें।

**केंद्रित चक्र**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # जब कैटलॉग बदलता है; जनरेट किया गया डिफ़ कमिट करें
npm run lint
```

प्रभावित प्रत्येक अनुरोध परिवार का भी परीक्षण करें: चैट, Responses, इमेज, एम्बेडिंग, ऑडियो या वीडियो।
जनरेट किए गए कैटलॉग और गोल्डन डिफ़ की समीक्षा अनुबंध परिवर्तनों के रूप में करें; उन्हें बिना जाँच के स्वीकार न करें।

### रूटिंग

**अनुबंध**

- `src/shared/constants/routingStrategies.ts` में सार्वजनिक रणनीति मान और UI मेटाडेटा।
- `open-sse/services/combo.ts` और `open-sse/services/combo/` के अंतर्गत डिस्पैच और क्रम निर्धारण।
- कॉम्बो स्कीमा, स्थायित्व, रेज़िलिएंस स्थिति, मॉडल क्षमताएँ और API/UI नियंत्रण।
- व्यवहार बदलने पर [ऑटो-कॉम्बो इंजन](../routing/AUTO-COMBO.md) और रेज़िलिएंस दस्तावेज़।

**केंद्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # रणनीति या डिस्पैच परिवर्तन
npm run check:known-symbols      # रणनीति पंजीकरण परिवर्तन
npm run lint
```

स्थानीय रूप से नियतात्मक मॉक-अपस्ट्रीम परीक्षणों का उपयोग करें। लाइव कॉम्बो स्मोक परीक्षणों के लिए क्रेडेंशियल आवश्यक हैं और वे
मैन्युअल हैं, CI के विकल्प नहीं।

### UI / UX

**अनुबंध**

- `src/app/` और `src/shared/components/` के अंतर्गत Next.js रूट/पेज और साझा कंपोनेंट सीमाएँ।
- API प्रतिक्रिया आकार, लोडिंग/रिक्त/त्रुटि स्थितियाँ, कीबोर्ड और स्क्रीन-रीडर व्यवहार,
  रिस्पॉन्सिव लेआउट, थीमिंग और लोकेल विस्तार।
- `src/i18n/messages/en.json` में अंग्रेज़ी UI स्रोत स्ट्रिंग; उपयोगकर्ता को दिखाई देने वाला नया टेक्स्ट हार्ड-कोड न करें।

**केंद्रित चक्र**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

इंटरैक्शन या दृश्य परिवर्तनों के लिए ऐप चलाएँ और संकरे तथा चौड़े, दोनों व्यूपोर्ट जाँचें। CI
उत्पादन बिल्ड और व्यापक सुइट चलाता है; दृश्य व्यवहार के लिए अब भी परिवर्तन के अनुरूप केंद्रित कंपोनेंट, Playwright
या दस्तावेज़ीकृत मैन्युअल जाँच आवश्यक है।

### i18n

**अनुबंध**

- `src/i18n/messages/en.json` UI स्रोत है; `config/i18n.json` लोकेल स्रोत है।
- CLI कैटलॉग अलग से `bin/cli/locales/` के अंतर्गत रहते हैं।
- ICU प्लेसहोल्डर और टैग बिल्कुल सुरक्षित रखें। उत्पाद/प्रदाता/मॉडल नाम,
  प्रोटोकॉल और हेडर नाम, कमांड, कोड/JSON आइडेंटिफ़ायर, URL, एनवायरनमेंट वेरिएबल या
  `OmniRoute`, `OAuth`, `MCP`, और `A2A` जैसे संरक्षित शब्दों का अनुवाद न करें। वर्तमान स्रोत सूची
  `scripts/i18n/glossary/protected-terms.json` है।

**केंद्रित चक्र**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # जब CLI स्ट्रिंग/कैटलॉग बदलते हैं
npm run lint
```

यह मौजूदा प्रणाली के लिए मार्गदर्शन है, इसके टूलिंग या कुंजी मॉडल का विस्तार करने का आमंत्रण नहीं।
प्रतिस्थापन प्रणाली डिज़ाइन किए जाने के दौरान i18n पैच को सीमित और सटीक रखें। बाहरी सेवाओं को कॉल करने वाले अनुवाद
कमांड तब तक न चलाएँ, जब तक कार्य में स्पष्ट रूप से जनरेट किए गए अनुवादों की आवश्यकता न हो और
आपने परिणामी डिफ़ की समीक्षा न कर ली हो।

### CLI

**अनुबंध**

- `bin/cli/` में सार्वजनिक commands और flags, जनरेट किए गए API commands, exit codes, stdout/stderr और
  JSON आउटपुट संरचनाएँ, config/environment व्यवहार और पैकेज की गई फ़ाइलें।
- CLI की उपयोगकर्ता-दृश्य strings को CLI i18n layer का उपयोग करना चाहिए और `en`/`pt-BR` catalogs को समन्वित रखना चाहिए।
- Node को समर्थित runtime और प्रकाशित binary contract के रूप में बनाए रखें।

**केंद्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # जनरेट किए गए/बंडल किए गए CLI परिवर्तन
npm run check:pack-policy     # package surface में परिवर्तन
npm run lint
```

जब व्यवहार parsing, फ़ाइलों या exit status पर निर्भर हो, तो किसी अस्थायी data directory में सटीक command का उपयोग करें। CI व्यापक package artifact और ecosystem जाँच करता है।

### डेटाबेस

**अनुबंध**

- `src/lib/db/` के अंतर्गत domain modules; विशिष्ट modules को सीधे import करें (पुरानी `localDb.ts` re-export layer हटा दी गई थी)।
- `src/lib/db/migrations/` के अंतर्गत क्रमांकित, idempotent SQL migrations, transaction सुरक्षा, upgrade
  व्यवहार, indexes और schema से प्रभावित प्रत्येक caller।
- Routes और handlers कभी भी सीधे raw SQL जारी नहीं करते।

**केंद्रित चक्र**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

migration जोड़ते समय नए database और पिछले schema से upgrade, दोनों का परीक्षण करें। Database tests को cleanup के दौरान handles बंद करने और `resetDbInstance()` को call करने की आवश्यकता है। `npm run test:bun:db` केवल तभी चलाएँ, जब best-effort Bun adapter path बदलता है; Node प्रामाणिक बना रहता है।

### बिल्ड / डिप्लॉय

**अनुबंध**

- Root और workspace manifests/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/`
  package contents, Electron platform metadata, CI workflows और deployment sentinels।
- समर्थित Node ranges और `CLAUDE.md` में allow-listed Bun उपयोग को अक्षुण्ण रहना चाहिए।
- Build artifacts untracked रहते हैं; dependency, license, workflow और package policies लागू होती हैं।

**केंद्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency या lockfile में परिवर्तन
npm run check:pack-policy      # प्रकाशित package surface में परिवर्तन
npm run lint
```

स्थानीय रूप से `npm run build` का उपयोग केवल तभी करें, जब परिवर्तन compilation, standalone assembly, assets या runtime bundling को प्रभावित करता हो। `npm run build:release` का उपयोग केवल release/deploy validation के लिए करें। CI का build अंतिम cross-platform संकेत है; platform-specific Electron परिवर्तनों के लिए संबंधित focused build या smoke evidence आवश्यक है।

## स्थानीय कैंडिडेट लूप

सोर्स परीक्षण यह साबित नहीं कर सकते कि पैकेज किया गया आर्टिफ़ैक्ट बूट होता है: पैकेजिंग सूचियाँ, हटाई गई डिपेंडेंसियाँ,
और नेटिव बाइनरी केवल तभी विफल होती हैं, जब tarball को इंस्टॉल करके शुरू किया जाता है। `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) RFC #8084 के एक बार बिल्ड करने / सत्यापित करने / प्रमोट करने वाले प्रवाह का स्थानीय
भाग है: यह एक कैंडिडेट बिल्ड करता है, ठीक उसी आर्टिफ़ैक्ट को सत्यापित करता है, डायरेक्टरी का नाम बदलकर उसे
प्रमोट करता है, और प्रमोट किए गए स्लॉट की स्वास्थ्य जाँच विफल होने पर उसे रोल बैक करता है।

```bash
npm run dev:candidate -- run --dry-run --json  # योजना प्रिंट करें, कुछ भी न बदलें
npm run dev:candidate -- run                   # बिल्ड + सत्यापन + प्रमोशन, स्वतः रोल बैक
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ में इंस्टॉल
npm run dev:candidate -- validate --id <id>    # किसी खाली पोर्ट पर बूट करें, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current और previous की अदला-बदली करें
npm run dev:candidate -- run --from-tarball <file.tgz>  # कहीं और (CI में) बने tarball का फिर से उपयोग करें
```

- **एक बार बिल्ड करें।** `build` मौजूदा ट्री को पैक करता है (इसे `dist/server.js` चाहिए, इसलिए पहले
  `npm run build:release` चलाएँ) या `--from-tarball` की प्रतिलिपि बनाता है, फिर tarball को एक अलग
  npm prefix में इंस्टॉल करता है, क्योंकि tarball में `node_modules` शामिल नहीं होता। आईडी छोटा `HEAD`
  sha होता है (जब ट्री में स्थानीय बदलाव हों तो `-dirty`) या किसी tarball के लिए `tgz-<sha256>` होता है।
  पहले से बिल्ड की गई स्वच्छ आईडी को दोबारा बिल्ड करने के बजाय पुनः उपयोग किया जाता है; उसे फिर से बिल्ड
  करने के लिए `--force` दें।
- **सोर्स को नहीं, पैकेज को सत्यापित करें।** `validate` इंस्टॉल किए गए CLI को
  (`serve --port <free port>`) नए `DATA_DIR=<candidate>/data`, नकली सीक्रेट्स, और ऑपरेटर के
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` तथा `INITIAL_PASSWORD` को एनवायरनमेंट से हटाकर शुरू करता
  है, ताकि यह नए इंस्टॉलेशन की बिना कुंजी वाली लूपबैक स्थिति की जाँच करे। यह `GET /api/health` द्वारा
  200 लौटाए जाने की प्रतीक्षा करता है, `GET /v1/models` द्वारा 200 लौटाना आवश्यक बनाता है, प्रोसेस समूह
  को रोकता है, और निर्णय को tarball हैश के साथ `validation.json` में दर्ज करता है।
- **उसी आर्टिफ़ैक्ट को प्रमोट करें।** `promote` ऐसे कैंडिडेट को स्वीकार नहीं करता जिसके मौजूदा tarball
  हैश के लिए सफल सत्यापन मौजूद न हो। डिफ़ॉल्ट सक्रिय स्लॉट `_artifacts/candidate/current` है;
  `--target <dir>` उसी फ़ाइल सिस्टम पर दूसरी डायरेक्टरी चुनता है, और उसका पिछला स्लॉट `<dir>.previous`
  होता है। नाम बदलने की प्रत्येक कार्रवाई एटॉमिक होती है, और बीच में विफलता होने पर पहले से किए गए
  नाम परिवर्तनों को उलट दिया जाता है।
- **रोल बैक करें।** `run` प्रमोट किए गए स्लॉट को फिर से सत्यापित करता है और वह जाँच विफल होने पर
  `current` तथा `previous` की वापस अदला-बदली कर देता है। पहले सत्यापन में विफल होने वाले कैंडिडेट को
  कभी प्रमोट नहीं किया जाता।

सब कुछ git द्वारा अनदेखी की जाने वाली `_artifacts/candidate/` के अंतर्गत लिखा जाता है; किसी मौजूदा
OmniRoute इंस्टॉलेशन और उसकी डेटा डायरेक्टरी को कभी नहीं छुआ जाता। प्रमोट किया गया CLI
`_artifacts/candidate/current/prefix/bin/omniroute` है; इसका उपयोग करते समय इसे अपने `DATA_DIR` के साथ
शुरू करें। एग्ज़िट कोड: `0` सफलता, `1` विफल सत्यापन या प्रमोशन, `2` उपयोग संबंधी त्रुटि या अनुपलब्ध बिल्ड।

| प्रत्येक पैच के लिए स्थानीय रूप से चलाएँ                                    | CI व्यापक संकेत प्रदान करता है                                            |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| ऊपर दिए गए प्रत्यक्ष व्यवहार परीक्षण और श्रेणी गेट                          | शार्ड किया गया पूर्ण यूनिट सुइट और सीरियल परीक्षण                         |

एक सफल केंद्रित लूप बदले गए कॉन्ट्रैक्ट के बारे में प्रमाण है, यह इस बात का प्रमाण नहीं है कि असंबंधित CI जाँचें
सफल होंगी। इसके विपरीत, प्रत्येक स्थानीय संपादन को पूर्ण रिपॉज़िटरी मैट्रिक्स की प्रतीक्षा न कराएँ।

## समन्वय चेकलिस्ट

समीक्षा का अनुरोध करने से पहले:

- पुष्टि करें कि PR का बेस अब भी सबसे उच्च सक्रिय `release/v*` ब्रांच है।
- उस बेस को फ़ेच करें और आपके ब्रांच बनाने के बाद जोड़े गए कमिट की समीक्षा करें।
- अनजाने या जनरेट किए गए अनावश्यक बदलावों के लिए `git diff <active-base>...HEAD` की समीक्षा करें।
- स्रोत को अपडेट करके और आउटपुट को फिर से जनरेट करके कैटलॉग और जनरेट किए गए दस्तावेज़ों के टकराव हल करें।
- समन्वय के बाद PR विवरण में सूचीबद्ध प्रत्येक केंद्रित परीक्षण/गेट को फिर से चलाएँ।
- बदले हुए बेस से मेल खाने के लिए कभी भी अभिकथनों को कमजोर न करें या आवश्यक परीक्षणों को न हटाएँ।

रिलीज़-फ़्रीज़ और रीटार्गेटिंग नियमों के लिए,
[ब्रांचिंग और रिलीज़ मॉडल](BRANCHING_MODEL.md) देखें। संपूर्ण CI सूची के लिए,
[गुणवत्ता गेट संदर्भ](../architecture/QUALITY_GATES.md) देखें।
