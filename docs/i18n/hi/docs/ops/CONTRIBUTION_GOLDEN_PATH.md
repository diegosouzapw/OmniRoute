पुल रिक्वेस्ट के लिए सबसे छोटा विश्वसनीय डेवलपमेंट लूप चुनने हेतु इस गाइड का उपयोग करें। यह नीचे लिंक किए गए क्षेत्र-विशिष्ट आर्किटेक्चर और सुरक्षा दस्तावेज़ों का
स्थान नहीं लेता; यह प्रत्येक सामान्य परिवर्तन प्रकार को उसके कॉन्ट्रैक्ट, केंद्रित जाँचों और CI कवरेज से जोड़ता है।

## प्रत्येक परिवर्तन द्वारा अपनाया जाने वाला पथ

1. **संपादन से पहले बेस चुनें।** सबसे उच्च सक्रिय `release/v*` ब्रांच खोजें और उसके नवीनतम सिरे से
   ब्रांच बनाएँ। उस ब्रांच को लक्षित करें, `main` को नहीं। यदि रिलीज़ फ़्रीज़ सक्रिय है, तो फ़्रीज़ की गई
   ब्रांच को लक्षित न करें; इसके बजाय
   [ब्रांचिंग और रिलीज़ मॉडल](BRANCHING_MODEL.md) में वर्णित अगले सक्रिय चक्र का उपयोग करें।
2. **कॉन्ट्रैक्ट के नाम बताएँ।** ऐसे प्रत्येक कैटलॉग, स्कीमा, जनरेट किए गए आर्टिफ़ैक्ट, सार्वजनिक API या उपयोगकर्ता
   इंटरफ़ेस की पहचान करें जिसे परिवर्तन प्रभावित करता है। नीचे दी गई तालिका न्यूनतम प्रारंभिक सेट बताती है।
3. **केंद्रित टेस्ट लिखें या अपडेट करें।** `src/`, `open-sse/`, `electron/` या
   `bin/` में प्रोडक्शन परिवर्तनों के लिए उसी PR में एक स्वचालित टेस्ट आवश्यक है। व्यवहार को प्रमाणित करने वाली सबसे छोटी
   टेस्ट फ़ाइलें चलाएँ, फिर सूचीबद्ध केंद्रित गेट चलाएँ।
4. **CI को व्यापक मैट्रिक्स चलाने दें।** पूर्ण यूनिट शार्ड, Vitest, कवरेज रैचेट और
   प्रोडक्शन बिल्ड PR पर चलते हैं। स्थानीय रूप से व्यापक सूट केवल तभी चलाएँ जब कोई केंद्रित विफलता
   व्यापक प्रभाव की ओर संकेत करे या जब परिवर्तन कई सबसिस्टम में फैला हो।
5. **समीक्षा से पहले समन्वय करें।** सक्रिय बेस को फ़ेच करें, उसके नए कमिट और उसके सापेक्ष अपने डिफ़ को
   जाँचें, फिर योगदानकर्ता वर्कफ़्लो के अनुसार बेस को रीबेस या मर्ज करें। जनरेट की गई फ़ाइलों
   और कैटलॉग के टकरावों को उनके स्रोत से हल करें, उन्हें दोबारा जनरेट करें, केंद्रित लूप फिर से चलाएँ और पुष्टि करें कि
   PR अब भी सक्रिय रिलीज़ ब्रांच को लक्षित करता है।
6. **साक्ष्य दर्ज करें।** PR टेम्पलेट में चलाए गए कमांड, जोड़ी या बदली गई प्रत्येक टेस्ट फ़ाइल,
   माइग्रेशन या फ़ीचर फ़्लैग और अभी लंबित कोई भी केवल-CI सत्यापन सूचीबद्ध करें।

## परिवर्तन प्रकार के अनुसार आदर्श पथ

नीचे दिए गए कमांड न्यूनतम केंद्रित जाँचें हैं, आपके द्वारा बदले गए व्यवहार को सीधे कवर करने वाला टेस्ट छोड़ने की
अनुमति नहीं।

### प्रोवाइडर

**कॉन्ट्रैक्ट**

- `src/shared/constants/providers/` में प्रोवाइडर परिभाषा और
  `src/shared/constants/providers.ts` में उसका संयोजन।
- `open-sse/config/providerRegistry.ts` या इसकी निकाली गई रजिस्ट्री फ़ाइलों में मॉडल और क्षमताएँ।
- लागू होने पर एक्ज़ीक्यूटर/ट्रांसलेटर चयन, OAuth या API-की कॉन्फ़िगरेशन, डैशबोर्ड एसेट और जनरेट किया गया
  प्रोवाइडर संदर्भ।
- सार्वजनिक क्रेडेंशियल को `resolvePublicCred()` का उपयोग करना चाहिए; त्रुटि प्रतिक्रियाओं को साझा सैनिटाइज़ किए गए
  त्रुटि हेल्पर का उपयोग करना चाहिए। `docs/security/PUBLIC_CREDS.md` (git; `/docs` में कंपाइल नहीं किया गया) और
  [त्रुटि सैनिटाइज़ेशन](../security/ERROR_SANITIZATION.md) देखें।

**केंद्रित लूप**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # जब कैटलॉग बदलता है; जनरेट किए गए डिफ़ को कमिट करें
npm run lint
```

प्रत्येक प्रभावित रिक्वेस्ट फ़ैमिली का भी परीक्षण करें: चैट, Responses, इमेज, एम्बेडिंग, ऑडियो या वीडियो।
जनरेट किए गए कैटलॉग और गोल्डन डिफ़ की समीक्षा कॉन्ट्रैक्ट परिवर्तनों के रूप में करें; उन्हें आँख बंद करके स्वीकार न करें।

### रूटिंग

**कॉन्ट्रैक्ट**

- `src/shared/constants/routingStrategies.ts` में सार्वजनिक स्ट्रैटेजी मान और UI मेटाडेटा।
- `open-sse/services/combo.ts` और `open-sse/services/combo/` के अंतर्गत डिस्पैच और क्रम निर्धारण।
- कॉम्बो स्कीमा, स्थायित्व, रेज़िलिएंस स्थिति, मॉडल क्षमताएँ और API/UI नियंत्रण।
- व्यवहार बदलने पर [ऑटो-कॉम्बो इंजन](../routing/AUTO-COMBO.md) और रेज़िलिएंस दस्तावेज़।

**केंद्रित लूप**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # स्ट्रैटेजी या डिस्पैच परिवर्तन
npm run check:known-symbols      # स्ट्रैटेजी पंजीकरण परिवर्तन
npm run lint
```

स्थानीय रूप से नियतात्मक मॉक-अपस्ट्रीम टेस्ट का उपयोग करें। लाइव कॉम्बो स्मोक टेस्ट के लिए क्रेडेंशियल आवश्यक हैं और वे
मैन्युअल हैं, CI के विकल्प नहीं।

### UI / UX

**कॉन्ट्रैक्ट**

- `src/app/` और `src/shared/components/` के अंतर्गत Next.js रूट/पेज और साझा कंपोनेंट सीमाएँ।
- API प्रतिक्रिया आकार, लोडिंग/रिक्त/त्रुटि स्थितियाँ, कीबोर्ड और स्क्रीन-रीडर व्यवहार,
  रिस्पॉन्सिव लेआउट, थीमिंग और लोकेल विस्तार।
- `src/i18n/messages/en.json` में अंग्रेज़ी UI स्रोत स्ट्रिंग; उपयोगकर्ता को दिखाई देने वाला नया टेक्स्ट हार्ड-कोड न करें।

**केंद्रित लूप**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

इंटरैक्शन या विज़ुअल परिवर्तनों के लिए ऐप चलाएँ और संकीर्ण तथा चौड़े, दोनों व्यूपोर्ट जाँचें। CI
प्रोडक्शन बिल्ड और व्यापक सूट चलाता है; विज़ुअल व्यवहार के लिए अभी भी परिवर्तन के अनुरूप केंद्रित कंपोनेंट, Playwright
या दस्तावेज़ीकृत मैन्युअल जाँच आवश्यक है।

### i18n

**कॉन्ट्रैक्ट**

- `src/i18n/messages/en.json` UI स्रोत है; `config/i18n.json` लोकेल स्रोत है।
- CLI कैटलॉग अलग से `bin/cli/locales/` के अंतर्गत स्थित हैं।
- ICU प्लेसहोल्डर और टैग को हूबहू बनाए रखें। प्रोडक्ट/प्रोवाइडर/मॉडल नाम,
  प्रोटोकॉल और हेडर नाम, कमांड, कोड/JSON आइडेंटिफ़ायर, URL, एनवायरनमेंट वेरिएबल या
  `OmniRoute`, `OAuth`, `MCP` और `A2A` जैसे संरक्षित शब्दों का अनुवाद न करें। वर्तमान स्रोत सूची
  `scripts/i18n/glossary/protected-terms.json` है।

**केंद्रित लूप**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # जब CLI स्ट्रिंग/कैटलॉग बदलते हैं
npm run lint
```

यह मौजूदा सिस्टम के लिए मार्गदर्शन है, इसकी टूलिंग या की मॉडल का विस्तार करने का आमंत्रण नहीं।
जब तक प्रतिस्थापन सिस्टम डिज़ाइन किया जा रहा है, i18n पैच को सीमित और सटीक रखें। बाहरी सेवाओं को कॉल करने वाले अनुवाद
कमांड तब तक न चलाएँ, जब तक कार्य में जनरेट किए गए अनुवाद स्पष्ट रूप से आवश्यक न हों और
आपने परिणामी डिफ़ की समीक्षा न कर ली हो।

### CLI

**कॉन्ट्रैक्ट**

- `bin/cli/` में सार्वजनिक कमांड और फ़्लैग, जनरेट किए गए API कमांड, एग्ज़िट कोड, stdout/stderr और
  JSON आउटपुट संरचनाएँ, कॉन्फ़िगरेशन/एनवायरनमेंट व्यवहार, तथा पैकेज की गई फ़ाइलें।
- CLI में उपयोगकर्ता को दिखाई देने वाली स्ट्रिंग्स को CLI i18n लेयर का उपयोग करना चाहिए और `en`/`pt-BR` कैटलॉग को समन्वयित रखना चाहिए।
- समर्थित रनटाइम के रूप में Node और प्रकाशित बाइनरी अनुबंध को बनाए रखें।

**केंद्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # जनरेट किए गए/बंडल किए गए CLI परिवर्तन
npm run check:pack-policy     # पैकेज-सतह परिवर्तन
npm run lint
```

जब व्यवहार पार्सिंग, फ़ाइलों या एग्ज़िट स्थिति पर निर्भर हो, तब किसी अस्थायी डेटा डायरेक्टरी में सटीक कमांड का उपयोग करें। CI व्यापक पैकेज आर्टिफ़ैक्ट और इकोसिस्टम जाँच करता है।

### डेटाबेस

**अनुबंध**

- `src/lib/db/` के अंतर्गत डोमेन मॉड्यूल; विशिष्ट मॉड्यूल को सीधे इंपोर्ट करें (पुरानी `localDb.ts` री-एक्सपोर्ट लेयर हटा दी गई थी)।
- `src/lib/db/migrations/` के अंतर्गत क्रमांकित, आइडेम्पोटेंट SQL माइग्रेशन, ट्रांज़ैक्शन सुरक्षा, अपग्रेड
  व्यवहार, इंडेक्स और स्कीमा से प्रभावित प्रत्येक कॉलर।
- रूट और हैंडलर कभी भी सीधे रॉ SQL जारी नहीं करते।

**केंद्रित चक्र**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

माइग्रेशन जोड़ते समय नए डेटाबेस और पिछले स्कीमा से अपग्रेड, दोनों का परीक्षण करें। डेटाबेस परीक्षणों को क्लीनअप के दौरान हैंडल बंद करने और `resetDbInstance()` कॉल करने चाहिए। `npm run test:bun:db` केवल तभी चलाएँ जब सर्वोत्तम-प्रयास वाला Bun अडैप्टर पथ बदलता है; Node प्रामाणिक बना रहता है।

### बिल्ड / डिप्लॉय

**अनुबंध**

- रूट और वर्कस्पेस मैनिफ़ेस्ट/लॉकफ़ाइल, `scripts/build/`, Next.js स्टैंडअलोन असेंबली, `dist/`
  पैकेज की सामग्री, Electron प्लेटफ़ॉर्म मेटाडेटा, CI वर्कफ़्लो और डिप्लॉयमेंट सेंटिनल।
- समर्थित Node रेंज और `CLAUDE.md` में अनुमति-सूचीबद्ध Bun उपयोग अक्षुण्ण रहने चाहिए।
- बिल्ड आर्टिफ़ैक्ट ट्रैक नहीं किए जाते; डिपेंडेंसी, लाइसेंस, वर्कफ़्लो और पैकेज नीतियाँ लागू होती हैं।

**केंद्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # डिपेंडेंसी या लॉकफ़ाइल परिवर्तन
npm run check:pack-policy      # प्रकाशित पैकेज सतह में परिवर्तन
npm run lint
```

स्थानीय रूप से `npm run build` का उपयोग केवल तभी करें जब परिवर्तन कंपाइलेशन, स्टैंडअलोन असेंबली, एसेट्स या रनटाइम बंडलिंग को प्रभावित करता हो। `npm run build:release` का उपयोग केवल रिलीज़/डिप्लॉय सत्यापन के लिए करें। CI का बिल्ड अंतिम क्रॉस-प्लेटफ़ॉर्म संकेत है; प्लेटफ़ॉर्म-विशिष्ट Electron परिवर्तनों के लिए संबंधित केंद्रित बिल्ड या स्मोक साक्ष्य आवश्यक है।

## स्थानीय लूप बनाम CI

| प्रत्येक पैच के लिए स्थानीय रूप से चलाएँ                                    | CI व्यापक संकेत प्रदान करता है                                            |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| ऊपर दिए गए प्रत्यक्ष व्यवहार परीक्षण और श्रेणी गेट                          | शार्ड किया गया संपूर्ण यूनिट सुइट और क्रमिक परीक्षण                       |
| `npm run lint`                                                              | Vitest सुइट और कवरेज/गुणवत्ता रैचेट                                       |
| टाइपचेक या बिल्ड केवल तभी, जब प्रभावित कॉन्ट्रैक्ट में इसकी आवश्यकता हो     | प्रोडक्शन बिल्ड, सुरक्षा, दस्तावेज़, डिपेंडेंसी और PR-नीति गेट            |
| मैन्युअल इंटरैक्शन/लाइव जाँच केवल तभी, जब ऑटोमेशन व्यवहार को सिद्ध न कर सके | वर्कफ़्लो द्वारा कॉन्फ़िगर की गई क्रॉस-जॉब इंटीग्रेशन और प्लेटफ़ॉर्म जाँच |

एक सफल केंद्रित लूप बदले गए कॉन्ट्रैक्ट के बारे में प्रमाण है, न कि इस बात का सबूत कि असंबंधित CI जाँच
पास होंगी। इसके विपरीत, प्रत्येक स्थानीय संपादन के लिए संपूर्ण रिपॉज़िटरी मैट्रिक्स की प्रतीक्षा न करें।

## सामंजस्य चेकलिस्ट

समीक्षा का अनुरोध करने से पहले:

- पुष्टि करें कि PR का आधार अभी भी सर्वोच्च सक्रिय `release/v*` ब्रांच है।
- उस आधार को फ़ेच करें और अपनी ब्रांच बनाने के बाद से शामिल हुए कमिट की समीक्षा करें।
- अनजाने या जनरेट किए गए बदलावों के लिए `git diff <active-base>...HEAD` की समीक्षा करें।
- स्रोत को अपडेट करके और आउटपुट को दोबारा जनरेट करके कैटलॉग तथा जनरेट किए गए दस्तावेज़ों के टकराव हल करें।
- सामंजस्य के बाद PR विवरण में सूचीबद्ध प्रत्येक केंद्रित परीक्षण/गेट को दोबारा चलाएँ।
- बदले हुए आधार से मेल कराने के लिए कभी भी असर्शन को कमज़ोर न करें या आवश्यक परीक्षण न हटाएँ।

रिलीज़-फ़्रीज़ और पुनः लक्ष्यीकरण नियमों के लिए,
[ब्रांचिंग और रिलीज़ मॉडल](BRANCHING_MODEL.md) का उपयोग करें। संपूर्ण CI इन्वेंट्री के लिए,
[गुणवत्ता गेट संदर्भ](../architecture/QUALITY_GATES.md) का उपयोग करें।
