## npm विश्वसनीय प्रकाशन (v3.8.51 से डिफ़ॉल्ट) — अनुरोध पर स्टेज्ड, फ़ॉलबैक के रूप में डायरेक्ट

`npm-publish.yml` डिफ़ॉल्ट रूप से **npm Trusted Publishing (OIDC)** के माध्यम से प्रकाशित करता है:
`stage-npm` जॉब (github-hosted) उस रन के लिए GitHub के id-token को अल्पकालिक npm
क्रेडेंशियल से बदलता है — रिपॉज़िटरी सीक्रेट्स में कोई दीर्घकालिक npm टोकन नहीं, कोई 2FA प्रॉम्प्ट नहीं, और प्रोवेनेंस संलग्न रहता है।
अब जब 2FA को छोड़ने वाले टोकन हटाए जा रहे हैं, यही npm द्वारा स्वीकृत बाइपास है;
यह WS1.3 गारंटी बनाए रखते हुए प्रोजेक्ट के v3.8.48 तक के पूर्णतः स्वचालित प्रवाह को
पुनर्स्थापित करता है (लीक हुआ टोकन अकेले प्रकाशित नहीं कर सकता — क्योंकि कोई टोकन है ही नहीं)।

**एक-बार का सेटअप (स्वामी):** npmjs.com → पैकेज `omniroute` → Settings → _Trusted
Publisher_ → GitHub: स्वामी `diegosouzapw`, रेपो `OmniRoute`, वर्कफ़्लो `npm-publish.yml`
(एनवायरनमेंट: कोई नहीं)। इसके मौजूद होने तक स्वचालित चरण `ENEEDAUTH` के साथ विफल होता है:
`publish_mode=staged` (नीचे) या `direct` के साथ दोबारा डिस्पैच करें।

### स्टेज्ड प्रकाशन (अनुरोध पर — `publish_mode=staged`)

npm-publish वर्कफ़्लो अब सीधे प्रकाशित नहीं करता: यह पैक किए गए टारबॉल को
बूट करता है (`check:pack-boot`) और फिर `npm stage publish` चलाता है — ठीक वही बाइट्स
रजिस्ट्री पर रखे जाते हैं, लेकिन स्वामी की मंज़ूरी मिलने तक वे **इंस्टॉल करने योग्य नहीं** होते।
मानवीय 2FA गेट को प्रमाण से पहले के बजाय उसके बाद स्थानांतरित कर दिया गया है।

**वर्कफ़्लो के ग्रीन होने के बाद स्वामी का प्रवाह:**

1. `npm stage list omniroute` — स्टेज id खोजें (यह वर्कफ़्लो सारांश में भी प्रिंट होती है)।
2. स्टेज्ड बाइट्स सत्यापित करें (अनुशंसित): `npm stage download <id>`, फिर डाउनलोड किए गए
   टारबॉल को अस्थायी प्रीफ़िक्स में इंस्टॉल करके बूट करें (`npm run check:pack-boot` CI में
   उसी pack→install→boot निर्णय को स्वचालित करता है)।
3. `npm stage approve <id>` — 2FA प्रॉम्प्ट ही प्रकाशन है। `npm stage reject <id>` इसे त्याग देता है।
4. प्रकाशन-पश्चात सुरक्षा-जाल: प्रकाशन-पश्चात सत्यापनकर्ता (v3.8.49 योजना का WS1.4)
   सार्वजनिक रजिस्ट्री से प्रकाशित वर्ज़न को एक साफ़ कंटेनर में इंस्टॉल करके बूट करता है।

**आपातकालीन फ़ॉलबैक:** `publish_mode=direct` के साथ `workflow_dispatch` पुराने
तत्काल `npm publish` को पुनर्स्थापित करता है (केवल तभी उपयोग करें जब स्टेजिंग स्वयं ठीक से काम न करे; कारण दर्ज करें)।

**एक-बार की सुरक्षा-मज़बूती (स्वामी, npmjs.com):** `omniroute` के लिए Trusted Publisher को
केवल-स्टेज मोड में कॉन्फ़िगर करें, ताकि लीक हुआ दीर्घकालिक टोकन कहीं से भी सीधे `npm publish`
न कर सके — CI केवल स्टेज कर सकता है; केवल स्वामी का 2FA रिलीज़ कर सकता है।

**टूटे हुए आर्टिफ़ैक्ट की कार्यपुस्तिका (अपरिवर्तित):** डिफ़ॉल्ट त्वरित प्रतिक्रिया के रूप में
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` (मिनटों में, वापस बदला जा सकता है);
`npm unpublish` केवल 72h/कोई-आश्रित-नहीं विंडो के भीतर और कभी भी पहले कदम के रूप में नहीं।
Docker: किसी वर्ज़न टैग को कभी दोबारा न लिखें — रोलबैक का अर्थ `latest` को अंतिम अच्छे डाइजेस्ट पर पुनः इंगित करना है।

**Docker Hub `latest` (प्रत्येक स्थिर SemVer प्रकाशन पर आवश्यक):**
`docker-publish` वर्कफ़्लो को **दोनों** `X.Y.Z` और, जब
`should-promote-latest.sh` सहमत हो कि यह उच्चतम स्थिर SemVer है, `:latest`
को **समान डाइजेस्ट** के साथ टैग करना होगा। जॉब के बाद: Hub का `latest` डाइजेस्ट नए
SemVer डाइजेस्ट के बराबर हो और `last_updated` आगे बढ़ा हो। `:latest` को किसी पुराने
बिल्ड पर न छोड़ें, जबकि रिलीज़ नोट्स उन सुधारों की चर्चा करें जो केवल git पर मौजूद हैं।
Compose क्विकस्टार्ट `:latest` का उपयोग करते हैं; GitOps को `X.Y.Z` पिन करना जारी रखना चाहिए।
[Docker रिलीज़ चैनल](../guides/DOCKER_GUIDE.md#release-channels) और #10317 देखें।

## हॉटफ़िक्स फ़ास्ट-लेन (लेबल `hotfix`)

`hotfix` लेबल वाला PR भारी CI मैट्रिक्स (9-शार्ड E2E, कवरेज रैचेट,
क्वालिटी-गेट, क्वालिटी-एक्सटेंडेड) को छोड़ देता है और तेज़, उच्च-संकेत वाले गेट बनाए रखता है: बिल्ड,
यूनिट शार्ड, इंटीग्रेशन, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
और टारबॉल बूट-स्मोक (`check:pack-boot`)। लक्ष्य: ~33 मिनट के बजाय ≤15 मिनट में सफल स्थिति।

**प्रवेश नीति — चारों आवश्यक (Chromium/VS Code/Node की आपातकालीन लेन के अनुरूप):**

1. **गंभीरता**: प्रोडक्शन काम नहीं कर रहा है — प्रकाशित आर्टिफ़ैक्ट बूट पर क्रैश होता है /
   सुरक्षा सुधार / रिलीज़ का प्रत्येक उपयोगकर्ता प्रभावित है। "महत्वपूर्ण" का अर्थ "काम न करना" नहीं है।
2. **प्राधिकार**: केवल रिपॉज़िटरी स्वामी ही `hotfix` लेबल लगाता है। लेबल ही
   स्वीकृति है — किसी कैंपेन PR पर इसे स्वयं कभी न लगाएँ।
3. **साक्ष्य**: PR बॉडी में पिछली पूरी तरह सफल भारी रन (वह सुइट जिसे
   छोड़े गए जॉब दोबारा सत्यापित करते) के साथ-साथ सुधार के अपने पहले-विफल-फिर-सफल परीक्षण का लिंक होता है।
4. **दायरा**: केवल cherry-pick — न्यूनतम सुधार, कोई रिफ़ैक्टर नहीं, कोई असंबंधित बदलाव नहीं।

छोड़ी गई कवरेज/रैचेट सतह को रिलीज़ ब्रांच पर अगली पूर्ण रन द्वारा
दोबारा सत्यापित किया जाता है (निरंतर रिलीज़-सफलता) — यह लेन केवल प्रतीक्षा छोड़ती है, सत्यापन कभी नहीं।
केवल-परीक्षण डिफ़ (सभी फ़ाइलें `tests/` के अंतर्गत, कोई भी `tests/e2e/` के अंतर्गत नहीं) बिना किसी
लेबल के E2E मैट्रिक्स को स्वचालित रूप से छोड़ देते हैं।

### बिल्ड लेआउट

Repository तीन अलग-अलग output directories का उपयोग करती है — इन्हें कभी भी आपस में न मिलाएँ:

| Directory | Purpose                                                      | Tracked?          |
| --------- | ------------------------------------------------------------ | ----------------- |
| `src/`    | एप्लिकेशन स्रोत (TypeScript / TSX)                           | हाँ               |
| `.build/` | बिल्ड के मध्यवर्ती परिणाम — `next build` output (`distDir`)  | नहीं (gitignored) |
| `dist/`   | वितरण योग्य npm bundle — `assembleStandalone` द्वारा संयोजित | नहीं (gitignored) |

> **ऑपरेटर नोट:** रिमोट VPS image directory अब भी `/usr/lib/node_modules/omniroute/app/` ही है।
> केवल **repository के भीतर का** build output बदला है (`app/` → `dist/`)। Deploy skills, `dist/`
> की सामग्री को रिमोट `app/` directory में rsync करते हैं — VPS path में किसी बदलाव की आवश्यकता नहीं है।

**एकल-बिल्ड प्रवाह:**

```
npm run build:release
  └─ rm -rf .build dist          (सफ़ाई)
  └─ next build → .build/next/   (मध्यवर्ती परिणाम)
  └─ assembleStandalone          (standalone + static + public + natives को dist/ में कॉपी करता है)
  └─ writes dist/BUILD_SHA       (HEAD संकेतक)
```

Deploy के लिए `npm run build` के बाद अलग से `npm run build:cli` न चलाएँ — इसके बजाय
`npm run build:release` का उपयोग करें, जो एक ही command में स्वच्छ पुनर्निर्माण + संकेतक तैयार करता है।

## रोलबैक

यदि रिलीज़ में कोई गंभीर समस्या हो:

1. `gh release edit vX.Y.Z --prerelease` (इसे नवीनतम नहीं के रूप में चिह्नित करता है)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (केवल तब, जब उपयोगकर्ताओं ने इसे अभी तक अपनाया न हो)
3. या: `release/vX.Y.0` पर हॉटफ़िक्स → पैच रिलीज़ `vX.Y.(Z+1)`
4. GitHub Discussions और Discord में तुरंत सूचना दें

## सख्त नियम

- कभी भी सीधे `main` में कमिट न करें
- `main` या `release/*` ब्रांचों पर कभी भी `git push --force` का उपयोग न करें
- Husky हुक (`--no-verify`) को कभी भी न छोड़ें
- सीक्रेट्स, क्रेडेंशियल्स या `.env` फ़ाइलें कभी भी कमिट न करें
- कवरेज ≥60/60/60/60 (स्टेटमेंट्स/लाइन्स/फ़ंक्शन्स/ब्रांचेज़) रहनी चाहिए
- `src/`, `open-sse/`, `electron/` या `bin/` में प्रोडक्शन कोड बदलते समय हमेशा टेस्ट शामिल या अपडेट करें
