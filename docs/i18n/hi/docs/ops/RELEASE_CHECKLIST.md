## npm Trusted Publishing (v3.8.51 से डिफ़ॉल्ट) — अनुरोध पर चरणबद्ध, फ़ॉलबैक के रूप में प्रत्यक्ष

`npm-publish.yml` डिफ़ॉल्ट रूप से **npm Trusted Publishing (OIDC)** के माध्यम से प्रकाशित करता है:
`stage-npm` जॉब (github-hosted) उस रन के लिए GitHub के id-token को अल्पकालिक npm
क्रेडेंशियल से बदलता है — रिपॉज़िटरी सीक्रेट्स में कोई दीर्घकालिक npm टोकन नहीं, कोई 2FA प्रॉम्प्ट नहीं, और प्रोवेनेंस संलग्न रहता है।
अब जब 2FA को छोड़ने वाले टोकन हटाए जा रहे हैं, तो npm द्वारा स्वीकृत बायपास यही है;
यह WS1.3 की गारंटी बनाए रखते हुए प्रोजेक्ट के v3.8.48 तक मौजूद पूर्णतः स्वचालित प्रवाह को
पुनर्स्थापित करता है (लीक हुआ टोकन अकेले प्रकाशित नहीं कर सकता — क्योंकि कोई टोकन है ही नहीं)।

**एक बार का सेटअप (स्वामी):** npmjs.com → पैकेज `omniroute` → Settings → _Trusted
Publisher_ → GitHub: स्वामी `diegosouzapw`, रिपॉज़िटरी `OmniRoute`, वर्कफ़्लो `npm-publish.yml`
(एनवायरनमेंट: कोई नहीं)। इसके मौजूद होने तक स्वचालित चरण `ENEEDAUTH` के साथ विफल होगा:
`publish_mode=staged` (नीचे) या `direct` के साथ फिर से डिस्पैच करें।

### चरणबद्ध प्रकाशन (अनुरोध पर — `publish_mode=staged`)

npm-publish वर्कफ़्लो अब सीधे प्रकाशित नहीं करता: यह पैक किए गए टारबॉल को
बूट करता है (`check:pack-boot`) और फिर `npm stage publish` चलाता है — वही सटीक बाइट्स
रजिस्ट्री पर रखे जाते हैं, लेकिन स्वामी की स्वीकृति मिलने तक **इंस्टॉल नहीं किए जा सकते**।
मानवीय 2FA गेट को प्रमाण से पहले के बजाय उसके बाद स्थानांतरित कर दिया गया है।

**वर्कफ़्लो के ग्रीन होने के बाद स्वामी का प्रवाह:**

1. `npm stage list omniroute` — स्टेज id खोजें (यह वर्कफ़्लो सारांश में भी प्रिंट होती है)।
2. चरणबद्ध बाइट्स सत्यापित करें (अनुशंसित): `npm stage download <id>`, फिर डाउनलोड किए गए
   टारबॉल को एक अस्थायी प्रीफ़िक्स में इंस्टॉल करके बूट करें (`npm run check:pack-boot`, CI में
   उसी pack→install→boot निर्णय को स्वचालित करता है)।
3. `npm stage approve <id>` — 2FA प्रॉम्प्ट ही प्रकाशन है। `npm stage reject <id>` इसे त्याग देता है।
4. प्रकाशन-पश्चात सुरक्षा-जाल: प्रकाशन-पश्चात सत्यापक (v3.8.49 योजना का WS1.4) एक स्वच्छ
   कंटेनर में सार्वजनिक रजिस्ट्री से प्रकाशित वर्ज़न इंस्टॉल करके उसे बूट करता है।

**आपातकालीन फ़ॉलबैक:** `publish_mode=direct` के साथ `workflow_dispatch`, पुराने
तत्काल `npm publish` को पुनर्स्थापित करता है (केवल तभी उपयोग करें जब स्टेजिंग स्वयं ठीक से काम न करे; कारण दर्ज करें)।

**एक बार की सुरक्षा-सुदृढ़ता (स्वामी, npmjs.com):** `omniroute` के लिए Trusted Publisher को
केवल-स्टेज मोड में कॉन्फ़िगर करें, ताकि लीक हुआ दीर्घकालिक टोकन कहीं से भी सीधे `npm publish`
न कर सके — CI केवल स्टेज कर सकता है; केवल स्वामी का 2FA ही रिलीज़ कर सकता है।

**दोषपूर्ण-आर्टिफ़ैक्ट कार्यपद्धति (अपरिवर्तित):** डिफ़ॉल्ट त्वरित कार्रवाई के रूप में
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` चलाएँ (कुछ मिनट लगते हैं, प्रत्यावर्तनीय);
`npm unpublish` केवल 72h/कोई-निर्भर-नहीं विंडो के भीतर चलाएँ और इसे कभी भी पहला कदम न बनाएँ।
Docker: किसी वर्ज़न टैग को कभी दोबारा न लिखें — रोलबैक का अर्थ `latest` को अंतिम सही डाइजेस्ट पर पुनः इंगित करना है।

**Docker Hub `latest` (प्रत्येक स्थिर SemVer प्रकाशन पर आवश्यक):**
`docker-publish` वर्कफ़्लो को **दोनों** `X.Y.Z` और, जब
`should-promote-latest.sh` इसे उच्चतम स्थिर SemVer मानता है, उसी **डाइजेस्ट** के साथ `:latest`
को टैग करना होगा। जॉब के बाद: Hub के `latest` का डाइजेस्ट नए
SemVer डाइजेस्ट के बराबर हो और `last_updated` आगे बढ़ा हो। `:latest` को किसी पुराने
बिल्ड पर न छोड़ें, जबकि रिलीज़ नोट्स उन सुधारों की बात कर रहे हों जो केवल git पर मौजूद हैं।
Compose क्विकस्टार्ट `:latest` का उपयोग करते हैं; GitOps को `X.Y.Z` पर पिन करना जारी रखना चाहिए।
[Docker रिलीज़ चैनल](../guides/DOCKER_GUIDE.md#release-channels) और #10317 देखें।

## हॉटफिक्स फ़ास्ट-लेन (लेबल `hotfix`)

`hotfix` लेबल वाला PR भारी CI मैट्रिक्स (9-शार्ड E2E, कवरेज रैचेट,
क्वालिटी-गेट, क्वालिटी-एक्सटेंडेड) को छोड़ देता है और तेज़, उच्च-संकेत वाले गेट बनाए रखता है: बिल्ड,
यूनिट शार्ड, इंटीग्रेशन, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
और टारबॉल बूट-स्मोक (`check:pack-boot`)। लक्ष्य: ~33 मिनट के बजाय ≤15 मिनट में सफल परिणाम।

**प्रवेश नीति — चारों आवश्यक (Chromium/VS Code/Node की आपातकालीन लेन के अनुरूप):**

1. **गंभीरता**: प्रोडक्शन बाधित है — प्रकाशित आर्टिफ़ैक्ट बूट होते समय क्रैश होता है /
   कोई सुरक्षा सुधार / रिलीज़ का प्रत्येक उपयोगकर्ता प्रभावित है। "महत्वपूर्ण" का अर्थ "बाधित" नहीं है।
2. **प्राधिकार**: केवल रिपॉज़िटरी स्वामी ही `hotfix` लेबल लगाता है। लेबल ही
   स्वीकृति है — किसी कैंपेन PR पर इसे स्वयं लागू न करें।
3. **साक्ष्य**: PR बॉडी में पिछली पूरी तरह सफल भारी रन (वह सुइट जिसे
   छोड़े गए जॉब फिर से सत्यापित करते) के साथ-साथ सुधार के अपने पहले विफल और फिर सफल हुए टेस्ट का लिंक होता है।
4. **दायरा**: केवल चेरी-पिक — न्यूनतम सुधार, कोई रीफ़ैक्टर नहीं, कोई असंबंधित बदलाव नहीं।

छोड़ी गई कवरेज/रैचेट सतह को रिलीज़ ब्रांच पर अगली पूर्ण रन
(निरंतर रिलीज़-सफलता) द्वारा फिर से सत्यापित किया जाता है — यह लेन केवल प्रतीक्षा छोड़ती है, सत्यापन कभी नहीं।
केवल टेस्ट वाले अंतर (`tests/` के अंतर्गत सभी फ़ाइलें, `tests/e2e/` के अंतर्गत कोई नहीं) बिना किसी लेबल के
E2E मैट्रिक्स को स्वचालित रूप से छोड़ देते हैं।

### बिल्ड लेआउट

Repository तीन अलग-अलग output directories का उपयोग करती है — उन्हें कभी भी आपस में न मिलाएँ:

| डायरेक्टरी | उद्देश्य                                                   | ट्रैक किया गया?   |
| ---------- | ---------------------------------------------------------- | ----------------- |
| `src/`     | Application source (TypeScript / TSX)                      | हाँ               |
| `.build/`  | Build intermediates — `next build` output (`distDir`)      | नहीं (gitignored) |
| `dist/`    | Shippable npm bundle — `assembleStandalone` द्वारा संयोजित | नहीं (gitignored) |

> **ऑपरेटर नोट:** remote VPS image directory अब भी `/usr/lib/node_modules/omniroute/app/` ही है।
> केवल **in-repo** build output बदला है (`app/` → `dist/`)। Deploy skills, `dist/` की सामग्री को
> remote `app/` dir में rsync करते हैं — VPS path में किसी बदलाव की आवश्यकता नहीं है।

**एकल-बिल्ड प्रवाह:**

```
npm run build:release
  └─ rm -rf .build dist          (सफ़ाई)
  └─ next build → .build/next/   (मध्यवर्ती फ़ाइलें)
  └─ assembleStandalone          (standalone + static + public + natives को dist/ में कॉपी करता है)
  └─ writes dist/BUILD_SHA       (HEAD प्रहरी)
```

Deploy के लिए `npm run build` के बाद अलग से `npm run build:cli` न चलाएँ — इसके बजाय
`npm run build:release` का उपयोग करें, जो एक ही command में clean rebuild + sentinel करता है।

3.8.58 में फ़ोर्क पर इसका शुरू से अंत तक पूर्वाभ्यास होता है, और 3.8.59
[GO/NO-GO चेकलिस्ट](./LTS_GO_NO_GO.md) के साथ समाप्त होता है।

### ड्राई-रन (केवल पढ़ने योग्य, किसी भी समय सुरक्षित)

```bash
npm run release:dry-run-lts-cut                       # वास्तविक कट: HEAD से 3.9.0, पिछला टैग v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # स्रोत कमिट को पिन करें
```

`scripts/release/dry-run-lts-cut.mjs` कुछ भी निष्पादित नहीं करता: यह git और `gh` को पढ़ता है और
पूरा क्रम प्रिंट करता है — पूर्वशर्तें (स्रोत रिज़ॉल्व होता है, पिछला टैग मौजूद है, `package.json`
लक्षित संस्करण है, एक `release-freeze` इश्यू खुला है, किसी मौजूदा रिलीज़ ब्रांच पर कोई खुला
`Release branch not green` इश्यू नहीं है — जो ब्रांच मौजूद नहीं है, वह `?` अज्ञात रिपोर्ट करती है,
कभी भी हरी नहीं — Mergify `release` कतार कॉन्फ़िगर है (G11: `queue_rules`, `checks_timeout`,
लेबल `queue`), `release/*` रूलसेट अब भी हटाने और फ़ोर्स-पुश को रोकता है, और
`stable/v3` तथा `develop` अभी मौजूद नहीं हैं), ब्रांच के दो चरण, कौन-से निष्क्रिय वर्कफ़्लो
ट्रिगर और `if:` शर्तें सत्य होती हैं (और कौन-सी रिपॉज़िटरी वेरिएबल द्वारा गेटेड रहती हैं या
कैनोनिकल रिपॉज़िटरी पर पिन रहती हैं), अपेक्षित dist-tags (`latest` → 3.9.0, `next` और
`nightly` रिक्त) और रोलबैक। एग्ज़िट `0` = `RESULT: READY`, `1` = कोई अवरोधक पूर्वशर्त
विफल हुई (`✗`), `2` = उपयोग त्रुटि। `--advisory <id,...>` किसी जाँच को छिपाए बिना चेतावनी (`!`)
में डाउनग्रेड करता है।

वास्तविक कट का ड्राई-रन तब चलाएँ जब 3.9.0 रिलीज़ फ़्रीज़ अभी भी खुला हो — ब्रांच
टैग के बाद और चरण 12c द्वारा फ़्रीज़ हटाए जाने से पहले बनाई जाती हैं।

### PR प्रीव्यू आर्टिफ़ैक्ट (एक बार बिल्ड करें, उन्हीं बाइट्स को प्रमोट करें)

`.github/workflows/preview-artifact.yml` किसी PR हेड से एक प्रोडक्शन टारबॉल बनाता है और
ठीक उसी बिल्ड को सत्यापित करता है (#8084 खंड (a))। केवल समान-रिपॉज़िटरी PR; कुछ भी प्रकाशित नहीं होता।

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # या `preview-artifact` लेबल जोड़ें
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # प्रीव्यू इंस्टॉल
```

रन `npm ci`, `npm run build:release`, `npm run check:pack-artifact` निष्पादित करता है, टारबॉल
पैक करता है, `npm run check:pack-boot` (नकली सीक्रेट्स, अस्थायी डेटा डायरेक्टरी) चलाता है, दोबारा पैक करता है और
यदि डाइजेस्ट समान न हो तो विफल हो जाता है, फिर `artifact-identity.json` (हेड SHA, बेस
SHA, लॉकफ़ाइल हैश, प्लेटफ़ॉर्म, आर्किटेक्चर, node ABI, बंडलर, बिल्ड नीति —
`scripts/release/artifact-identity.mjs`) रिकॉर्ड करता है और एक अलग जॉब में टारबॉल को प्रमाणित करता है। किसी
प्रीव्यू को प्रमोट करने का अर्थ उस टारबॉल को इंस्टॉल करना है: स्रोत से कभी भी दोबारा बिल्ड न करें।

### कट (3.9.0, GO के बाद)

1. GO को [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md) में दर्ज किया गया।
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` प्रिंट करता है: `RESULT: READY`।
3. ड्राई-रन द्वारा प्रिंट किए गए कमांड से `origin` पर ब्रांच हाथ से बनाएँ — स्क्रिप्ट
   `origin` पर पुश करने से इनकार करती है। समीक्षा किए गए develop कमिट का पुनः उपयोग करने के लिए,
   पहले अपने फ़ोर्क के विरुद्ध 3.9.0 टिप पर `--execute` पूर्वाभ्यास चलाएँ; यह दोनों SHA प्रिंट करता है, और
   उन्हीं कमिट को पुश किया जा सकता है:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. पहली PR मर्ज होने से पहले `stable/v3` और `develop` को सुरक्षित करें (रूलसेट + मर्ज कतार)।
5. निष्क्रिय वर्कफ़्लो ब्रांच की मौजूदगी से चालू होते हैं: `forward-port.yml` (`stable/v3` पर
   पुश), `validate-stable-pr.yml` (`stable/v3` के लिए PR) और `nightly-v4-build.yml`
   (`develop` को बिल्ड करता है)। गो-लाइव से पहले, `secrets.FORWARD_PORT_TOKEN` रिपॉज़िटरी सीक्रेट सेट करें (ताकि CI
   फ़ॉरवर्ड-पोर्ट PR पर चले); नाइटली प्रकाशन तब तक बंद रहता है जब तक स्वामी रिपॉज़िटरी
   वेरिएबल `vars.NIGHTLY_PUBLISH` को `true` पर सेट नहीं करता और npm Trusted Publishing
   `nightly-v4-build.yml` को स्वीकार नहीं करता। चैनल रिज़ॉल्यूशन `scripts/release/dist-tag.mjs` है, वही
   रिज़ॉल्वर जिसका उपयोग `npm-publish.yml` करता है।
6. चैनल सत्यापित करें: `npm view omniroute dist-tags --json` में `latest` = 3.9.0 दिखता है और

7. आवश्यकता होने पर रोलबैक करें: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   और `npm dist-tag add omniroute@3.8.59 latest`।

## रोलबैक

यदि रिलीज़ में कोई गंभीर समस्या हो:

1. `gh release edit vX.Y.Z --prerelease` (इसे नवीनतम नहीं के रूप में चिह्नित करता है)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (केवल तभी, जब उपयोगकर्ताओं ने इसे अभी तक अपनाया न हो)

4. GitHub Discussions और Discord में तुरंत सूचना दें

## सख्त नियम

- `main` में कभी भी सीधे कमिट न करें
- `main` या `release/*` ब्रांचों पर कभी भी `git push --force` का उपयोग न करें
- Husky हुक्स (`--no-verify`) को कभी भी न छोड़ें
- सीक्रेट्स, क्रेडेंशियल्स या `.env` फ़ाइलों को कभी भी कमिट न करें
- कवरेज ≥60/60/60/60 (स्टेटमेंट्स/लाइन्स/फ़ंक्शन्स/ब्रांचेस) रहना चाहिए
- `src/`, `open-sse/`, `electron/` या `bin/` में प्रोडक्शन कोड बदलते समय हमेशा टेस्ट शामिल करें या अपडेट करें

## स्वचालित सिंक जाँच

PR खोलने से पहले डॉक्स सिंक गार्ड को स्थानीय रूप से चलाएँ:

```bash
npm run check:docs-sync
```

CI भी इस जाँच को `.github/workflows/ci.yml` (लिंट जॉब) में चलाता है।
