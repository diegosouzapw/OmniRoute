> **TL;DR**: `open-sse/` मुख्य स्ट्रीमिंग इंजन है, जो OmniRoute में प्रत्येक LLM अनुरोध को संचालित करता है। इसमें अनुरोध पाइपलाइन, एक्ज़ीक्यूटर्स, सेवाएँ, MCP सर्वर और अनुवाद परत को कार्यान्वित करने वाली ~1,400 फ़ाइलें हैं। यह मार्गदर्शिका बताती है कि ये घटक एक साथ कैसे काम करते हैं।

**स्रोत:** `open-sse/` (वर्कस्पेस पैकेज, ~1,440 गैर-परीक्षण `.ts` फ़ाइलें)

## अलग वर्कस्पेस पैकेज क्यों?

`open-sse/`, OmniRoute मोनोरेपो में एक **स्वतंत्र वर्कस्पेस** है, जिसके कई कारण हैं:

1. **पुन: उपयोग की क्षमता** — `open-sse` को npm पर `@omniroute/open-sse` के रूप में प्रकाशित किया जाता है, ताकि अन्य प्रोजेक्ट इसे स्वतंत्र रूप से उपयोग कर सकें
2. **स्पष्ट सीमाएँ** — स्ट्रीमिंग इंजन को OmniRoute-विशिष्ट UI/DB परत से अलग रखा गया है
3. **प्रदर्शन** — इंजन में कोई Next.js निर्भरता नहीं है, जिससे CLI/serverless संदर्भों में कोल्ड स्टार्ट तेज़ होते हैं
4. **संस्करण प्रबंधन** — `open-sse` अपनी समय-सारणी के अनुसार रिलीज़ हो सकता है

```json
// package.json
"workspaces": ["open-sse"]
```

## अनुरोध पाइपलाइन

प्रत्येक LLM अनुरोध एक **5-चरणीय पाइपलाइन** से होकर गुजरता है:

```
                              ┌──────────────┐
   HTTP अनुरोध                │  1. रूट      │   कॉम्बो समाधान, मॉडल चयन
   (Next.js रूट)              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. अनुवाद   │   प्रारूप रूपांतरण (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. निष्पादन │   प्रदाता एक्ज़ीक्यूटर, HTTP, पुनः प्रयास, ब्रेकर
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. स्ट्रीम   │   SSE रूपांतरण, बैकप्रेशर
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. रिकॉर्ड  │   उपयोग ट्रैकिंग, कॉल लॉग, त्रुटि वर्गीकरण
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP प्रतिक्रिया (SSE या JSON)
```

### चरण 1: रूट (services/combo.ts)

**प्रवेश बिंदु**: `services/combo.ts` में `handleComboChat()`

अनुरोध को एक ठोस `(provider, model, account, credentials)` टपल में समाधान करता है:

- ID द्वारा कॉम्बो खोजें (या `auto/*` मॉडल के लिए एक वर्चुअल कॉम्बो बनाएँ)
- रूटिंग रणनीति लागू करें (प्राथमिकता, भारित, राउंड-रॉबिन आदि)
- अस्वस्थ प्रदाताओं को फ़िल्टर करें (सर्किट ब्रेकर)
- अगला व्यवहार्य लक्ष्य चुनें

`auto/*` मॉडल के लिए यह चरण निम्न कार्य भी करता है:

- **16-कारक स्कोरिंग** एल्गोरिदम (`services/autoCombo/`) चलाता है
- स्वास्थ्य, लागत, विलंबता आदि के आधार पर एक `provider+model` जोड़ी चुनता है

### चरण 2: अनुवाद (translator/)

यदि स्रोत प्रारूप (जैसे OpenAI) लक्ष्य प्रारूप (जैसे Claude) से अलग है, तो अनुरोध का **अनुवाद** किया जाता है:

- सिस्टम प्रॉम्प्ट → सिस्टम संदेश
- टूल परिभाषाएँ → प्रदाता-विशिष्ट टूल प्रारूप
- रीजनिंग/थिंकिंग पैरामीटर → प्रदाता-विशिष्ट समकक्ष
- संदेश भूमिका सामान्यीकरण (गैर-OpenAI के लिए `developer` → `system`)

`translator/index.ts` निम्नलिखित को एक्सपोज़ करता है:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### चरण 3: निष्पादन (executors/)

**प्रवेश बिंदु**: `getExecutor(providerId).execute(request, options)`

सभी प्रदाता `getExecutor()` फ़ैक्टरी फ़ॉलबैक के माध्यम से `DefaultExecutor` (`executors/default.ts`) का उपयोग करते हैं। एक्ज़ीक्यूटर:

- अपस्ट्रीम URL बनाता है (`buildUrl()`)
- प्रदाता-विशिष्ट हेडर जोड़ता है (`buildHeaders()`)
- अनुरोध बॉडी को रूपांतरित करता है (`transformRequest()`)
- पुनः प्रयास + एक्सपोनेंशियल बैकऑफ़ के साथ HTTP अनुरोध भेजता है
- आवश्यकता होने पर प्रमाणीकरण रीफ़्रेश संभालता है (OAuth प्रदाता)

सभी एक्ज़ीक्यूटर `BaseExecutor` (`executors/base.ts`, 1170 LOC) को एक्सटेंड करते हैं, जो निम्नलिखित प्रदान करता है:

- सामान्य पुनः प्रयास लॉजिक
- प्रॉक्सी एकीकरण
- सर्किट ब्रेकर एकीकरण
- उपयोग रिकॉर्डिंग हुक

### चरण 4: स्ट्रीम (utils/stream.ts)

स्ट्रीमिंग प्रतिक्रियाओं के लिए, एक्ज़ीक्यूटर एक **ReadableStream** लौटाता है। हैंडलर:

- SSE ट्रांसफ़ॉर्म (`createSSETransformStreamWithLogger`) के माध्यम से पाइप करता है
- निष्क्रिय कनेक्शन का पता लगाने के लिए हार्टबीट पिंग लागू करता है
- क्लाइंट डिस्कनेक्ट को सुचारु रूप से संभालता है (`pipeWithDisconnect`)
- गैर-स्ट्रीमिंग क्लाइंट के लिए SSE → JSON रूपांतरण करता है

गैर-स्ट्रीमिंग प्रतिक्रियाओं के लिए, एक्ज़ीक्यूटर पार्स किया हुआ JSON ऑब्जेक्ट लौटाता है, जिसे बिना बदलाव के आगे भेज दिया जाता है।

### चरण 5: रिकॉर्ड (services/usage.ts)

प्रतिक्रिया (सफलता या विफलता) के बाद, उपयोग दर्ज किया जाता है:

- प्रतिक्रिया से `prompt_tokens`, `completion_tokens`, `cached_tokens`
- मूल्य निर्धारण डेटा से परिकलित `cost_usd`
- विफल होने पर `latency_ms`, `status`, `error_class`
- `usage_history` तालिका में स्थायी रूप से संग्रहीत

कॉल लॉग आर्टिफ़ैक्ट (यदि सक्षम हों) `${DATA_DIR}/call_logs/` में लिखे जाते हैं।

## मुख्य फ़ाइलें: गहन विश्लेषण

### chatCore.ts (5977 पंक्तियाँ)

**मुख्य रिक्वेस्ट हैंडलर**। अपने आकार के बावजूद, इसकी संरचना स्पष्ट है:

```ts
// chatCore.ts की छद्म-संरचना
export async function handleChat(request: NextRequest) {
  // 1. ऑथ + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. बॉडी सत्यापन
  const body = await parseRequestBody(request);

  // 3. फ़ॉर्मेट पहचान + अनुवाद
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. कॉम्बो राउटिंग
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // अगले टारगेट पर जारी रखें
    }
  }

  // 5. आपातकालीन फ़ॉलबैक
  return await emergencyFallback(body);
}
```

एक विशाल फ़ंक्शन होने के बावजूद, यह **टिप्पणीकृत सेक्शनों** में व्यवस्थित है जो 5-चरणीय पाइपलाइन से मेल खाते हैं।

### combo.ts (4456 LOC)

**राउटिंग इंजन** जो एक कॉम्बो को क्रमबद्ध टारगेट्स में रिज़ॉल्व करता है।

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

**21 राउटिंग रणनीतियों** का समर्थन करता है (देखें `src/shared/constants/routingStrategies.ts`):

| रणनीति              | व्यवहार                                                                                         |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| `priority`          | पहले-टारगेट वाली क्रमबद्ध सूची                                                                  |
| `weighted`          | प्रति-टारगेट वज़न के आधार पर संभाव्यता-आधारित                                                   |
| `round-robin`       | क्रम से टारगेट्स के बीच चक्रण                                                                   |
| `context-relay`     | टारगेट्स के बीच कॉन्टेक्स्ट हस्तांतरण                                                           |
| `fill-first`        | अगले पर जाने से पहले कोटा भरें                                                                  |
| `p2c`               | दो विकल्पों की शक्ति (power of two choices)                                                     |
| `random`            | समान यादृच्छिक                                                                                  |
| `least-used`        | सबसे कम हालिया उपयोग वाला चुनें                                                                 |
| `cost-optimized`    | सबसे सस्ता स्वस्थ टारगेट पहले                                                                   |
| `reset-aware`       | प्रोवाइडर रीसेट विंडो से अवगत                                                                   |

````
## एक्ज़िक्यूटर (150 मॉड्यूल)

ज़्यादातर प्रति प्रोवाइडर एक फ़ाइल होती है। सभी एक्ज़िक्यूटर क्लास `BaseExecutor` को एक्सटेंड करती हैं और जो चीज़ अलग होती है उसे ओवरराइड करती हैं; अन्य मॉड्यूल प्रति-प्रोवाइडर हेल्पर हैं (टूल स्कीमा, fetch/TTS एडाप्टर, क्वर्क हैंडलर)।

### सामान्य पैटर्न

प्रोवाइडर `getExecutor(providerId)` के माध्यम से रिज़ॉल्व होते हैं, जो कॉन्फ़िगर किया गया एक्ज़िक्यूटर लौटाता है। OpenAI/Anthropic-संगत प्रोवाइडर `DefaultExecutor` (`executors/default.ts`) का उपयोग करते हैं। प्रोवाइडर-विशिष्ट व्यवहार (बेस URL, ऑथ हेडर, API वर्ज़न) `open-sse/config/providers/` में कॉन्फ़िगर किया जाता है, जबकि अनुरोध बॉडी ट्रांसफ़ॉर्मेशन `open-sse/translator/` में संभाले जाते हैं।

**कस्टम URL** प्रोवाइडर कॉन्फ़िगरेशन के माध्यम से सेट किया जाता है:

```ts
// open-sse/config/providers/ में प्रोवाइडर कॉन्फ़िगरेशन
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**कस्टम ऑथ** प्रोवाइडर रजिस्ट्री के ऑथ कॉन्फ़िगरेशन (API key, OAuth, हेडर प्रोफ़ाइल) के माध्यम से संभाला जाता है।

**कस्टम अनुरोध बॉडी** ट्रांसफ़ॉर्मेशन (उदाहरण के लिए, Anthropic द्वारा `system` को `messages` से अलग करना) `open-sse/translator/` में प्रति-प्रोवाइडर पंजीकृत होते हैं।

````

### एक्ज़िक्यूटर फ़ैक्टरी

`executors/index.ts`, `getExecutor(providerId)` एक्सपोर्ट करता है:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const result = await executor.execute({
  model: "claude-sonnet-4-5",
````

## अनुवादक

**3 प्रारूपों** के बीच अनुवाद करें: OpenAI, Anthropic, Gemini, साथ ही नया Responses API।

### अनुवाद कब होता है

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

सामान्य अनुवाद:

- `OpenAI → Anthropic`: अलग `system` फ़ील्ड, `x-api-key` हेडर
- `OpenAI → Gemini`: `messages` के बजाय `contents`, `systemInstruction`
- `OpenAI → Responses API`: `input` ऐरे, `previous_response_id` स्थिति

### संभाले गए विशेष मामले

- `developer` भूमिका → गैर-OpenAI के लिए `system`
- `system` भूमिका → GLM/ERNIE के लिए पहले उपयोगकर्ता संदेश में मर्ज की जाती है
- `json_schema` → Gemini का `responseMimeType` + `responseSchema`
- `tools` → प्रदाता-विशिष्ट टूल प्रारूप
- थिंकिंग पैरामीटर (o1, Claude) → प्रदाता-विशिष्ट समकक्ष

## MCP सर्वर

`open-sse/mcp-server/` **Model Context Protocol** सर्वर को कार्यान्वित करता है:

- **110 टूल** (प्रदाता प्रबंधन, कॉम्बो, मेमोरी, कैश, संपीड़न, प्रॉक्सी, कौशल, गेमिफ़िकेशन, प्लगइन, Notion, Obsidian, स्थानीय कॉर्पस)
- **3 ट्रांसपोर्ट**: stdio, SSE, Streamable HTTP
- सूक्ष्म-स्तरीय प्राधिकरण के लिए **33 स्कोप**

### टूल पंजीकरण

टूल `open-sse/mcp-server/tools/` में स्वतंत्र फ़ाइलों के रूप में पंजीकृत होते हैं, जिनमें से प्रत्येक एक नाम, स्कीमा, हैंडलर और स्कोप निर्यात करती है:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### ट्रांसपोर्ट

```ts
// stdio (CLI उपयोग)
startMcpStdio(server);

// SSE (HTTP-आधारित स्ट्रीमिंग)
startMcpSse(server, port);

// Streamable HTTP (आधुनिक MCP)

```

## ट्रांसफ़ॉर्मर

`open-sse/transformer/`, **Chat Completions** और **Responses API** प्रारूपों के बीच रूपांतरण करता है।

### अलग ट्रांसफ़ॉर्मर क्यों?

Responses API, **स्टेटफ़ुल वार्तालापों** (`previous_response_id`) वाला OpenAI का नया प्रारूप है। जब कोई क्लाइंट Responses अनुरोध भेजता है, तो OmniRoute:

1. आंतरिक रूप से Responses → Chat Completions में रूपांतरित करता है
2. प्रदाता को भेजता है (Chat Completions का समर्थन करने वाला कोई भी प्रदाता)
3. प्रतिक्रिया को वापस Responses प्रारूप में रूपांतरित करता है
4. रूपांतरित प्रतिक्रिया को क्लाइंट तक स्ट्रीम करता है

ट्रांसफ़ॉर्मर (`transformer/responsesTransformer.ts`) यह प्रदान करता है:

```ts
createResponsesApiTransformStream(): TransformStream
```

यह इन्हें संभालता है:

- `response.output_item.added` इवेंट
- `response.output_text.delta` इवेंट
- `response.completed` इवेंट
- टूल कॉल मैपिंग (`function_call` ↔ `tool_calls`)

## नया कंपोनेंट जोड़ना

### नई सेवा जोड़ना

1. केंद्रित उत्तरदायित्व के साथ `open-sse/services/[serviceName].ts` बनाएँ
2. मुख्य हैंडलर फ़ंक्शन और सभी कॉन्स्टेंट्स एक्सपोर्ट करें
3. `tests/unit/services/[serviceName].test.mjs` में यूनिट टेस्ट जोड़ें
4. अनुरोध पाइपलाइन के `handlers/chatCore.ts` में एकीकृत करें (यदि रूटिंग से संबंधित हो)
5. यदि सेवा लक्ष्य चयन को प्रभावित करती है, तो `combo.ts` में रूटिंग लॉजिक अपडेट करें
6. इस फ़ाइल में दस्तावेज़ीकरण करें

### नया एक्ज़ीक्यूटर जोड़ना

1. `BaseExecutor` को एक्सटेंड करते हुए `open-sse/executors/[provider].ts` बनाएँ
2. `config/providerRegistry.ts` में रजिस्टर करें
3. `executors/index.ts` फ़ैक्टरी में जोड़ें
4. एक्ज़ीक्यूटर के लिए यूनिट टेस्ट जोड़ें
5. `docs/architecture/ARCHITECTURE.md` में दस्तावेज़ीकरण करें

### नया MCP टूल जोड़ना

1. `open-sse/mcp-server/tools/[category]Tools.ts` बनाएँ या अपडेट करें
2. इनपुट के लिए Zod स्कीमा परिभाषित करें
3. टूल को `mcp-server/index.ts` में रजिस्टर करें
4. `mcp-server/auth/` की स्कोप मैट्रिक्स में जोड़ें
5. यूनिट टेस्ट जोड़ें
