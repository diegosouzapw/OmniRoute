AgentBridge OmniRoute का MITM (Man-in-the-Middle) प्रॉक्सी है, जो IDE AI एजेंटों से आने वाले HTTPS ट्रैफ़िक को इंटरसेप्ट करता है और उसे OmniRoute के एकीकृत रूटिंग इंजन के माध्यम से पुनः रूट करता है। यह **10 IDE एजेंटों** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code, और Trae (जाँच जारी है) — का समर्थन करता है, जिससे OmniRoute बाज़ार में AI कोडिंग सहायकों के लिए सबसे व्यापक कवरेज वाला MITM प्रॉक्सी बन जाता है।

**डैशबोर्ड स्थान:** `/dashboard/tools/agent-bridge`
**साइडबार समूह:** Tools (Cloud Agents के बाद)
**यह भी देखें:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — इंटरसेप्ट किए गए सभी ट्रैफ़िक की रीयल-टाइम निगरानी करें; `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs` में संकलित नहीं) — `/api/tools/agent-bridge/tproxy` रूट द्वारा संचालित Linux TPROXY पारदर्शी-डिक्रिप्ट कैप्चर मोड।

## §1 अवलोकन

### AgentBridge क्या है?

जब कोई IDE एजेंट (जैसे GitHub Copilot, Cursor, Claude Code) API कॉल करता है, तो वह सीधे अपस्ट्रीम AI प्रदाता (OpenAI, Anthropic, आदि) से कनेक्ट होता है। AgentBridge उस कनेक्शन को TLS स्तर पर पारदर्शी रूप से इंटरसेप्ट करता है — इसके लिए एजेंट के कॉन्फ़िगरेशन में किसी बदलाव की आवश्यकता नहीं होती — और अनुरोध को OmniRoute के माध्यम से पुनः लिखता है।

इसका अर्थ है कि आप:

- **किसी भी एजेंट को किसी भी प्रदाता पर पुनः रूट कर सकते हैं**: Copilot OpenAI से संचार कर रहा है? उसे Anthropic Claude, Gemini, या OmniRoute के 352 प्रदाताओं में से किसी पर रीडायरेक्ट करें।
- **मॉडल मैपिंग लागू कर सकते हैं**: हैंडलर स्तर पर पारदर्शी रूप से `gemini-3-flash` → `claude-sonnet-4.7`।
- **सभी एजेंट ट्रैफ़िक का निरीक्षण कर सकते हैं**: इंटरसेप्ट किया गया प्रत्येक अनुरोध [Traffic Inspector](./TRAFFIC_INSPECTOR.md) पर प्रकाशित किया जाता है।
- **OmniRoute की रेज़िलिएंस लागू कर सकते हैं**: कॉम्बो रूटिंग, सर्किट ब्रेकर, फ़ॉलबैक और लागत ट्रैकिंग IDE एजेंट ट्रैफ़िक के लिए भी काम करते हैं।

## §2 आर्किटेक्चर

### 2.1 कंपोनेंट्स का अवलोकन

```
IDE एजेंट (VS Code / Cursor / आदि)
    │  HTTPS (पोर्ट 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← DNS रीडायरेक्ट
    │
    ▼
src/mitm/server.cjs  (पोर्ट 443, CJS चाइल्ड प्रोसेस)
    │  Host हेडर SNI द्वारा लक्ष्य का समाधान करता है
    │  AgentBridge CA द्वारा हस्ताक्षरित प्रति-SNI TLS प्रमाणपत्र जनरेट करता है
    ├── बायपास सूची से मेल? → TCP पासथ्रू (कोई डिक्रिप्शन नहीं)
    ├── लक्ष्य से मेल? → fetch → OmniRoute राउटर (पोर्ट 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── अनुरोध की बॉडी/हेडर पर maskSecrets()
    │               ├── TrafficBuffer.push() — Traffic Inspector पर प्रकाशित करता है
    │               └── fetchRouter() → /v1/chat/completions
    └── कोई मेल नहीं? → TCP पासथ्रू (कोई डिक्रिप्शन नहीं)
```

### 2.2 MITM सर्वर (`src/mitm/server.cjs`)

मुख्य MITM सर्वर Node.js CJS चाइल्ड प्रोसेस के रूप में चलता है (मौजूदा CJS कोडबेस को दोबारा लिखने से बचने के लिए)। यह:

- पोर्ट 443 पर सुनता है (विशेषाधिकार या `authbind`/`setcap` आवश्यक है)
- OS से CONNECT टनल प्राप्त करता है (`/etc/hosts` DNS रीडायरेक्ट के माध्यम से)
- AgentBridge CA (`DATA_DIR/mitm/ca.crt`) द्वारा हस्ताक्षरित प्रति-SNI TLS प्रमाणपत्र जनरेट करता है
- `targets/index.ts` रजिस्ट्री के माध्यम से Host हेडर द्वारा लक्षित एजेंट का समाधान करता है
- HTTP के माध्यम से `http://127.0.0.1:20128` पर TypeScript हैंडलर लेयर को डिस्पैच करता है

`TARGET_HOSTS` को `DATA_DIR/mitm/targets.json` से लोड किया जाता है (जिसे बूट के समय `targets/index.ts` लिखता है), जिससे CJS सर्वर को रीस्टार्ट किए बिना डायनेमिक अपडेट संभव होते हैं।

> **रूट-CA मॉडल (#6684)।** ऊपर दिया गया प्रति-SNI-प्रमाणपत्र-जिसे-CA-द्वारा-हस्ताक्षरित-किया-गया है विवरण
> #6684 में जोड़ा गया स्थायी रूट-CA मॉडल है (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, जो `src/mitm/tproxy/dynamicCert.ts` में
> TPROXY के लिए पहले से प्रमाणित CA/लीफ़ क्रिप्टोग्राफ़ी का पुनः उपयोग करता है) — यह
> पुराने एकल स्थिर स्व-हस्ताक्षरित लीफ़ (`src/mitm/cert/generate.ts`, जो अभी भी
> केवल antigravity होस्ट तक सीमित है) को प्रतिस्थापित करता है, जिसकी ओर डिस्क पर मौजूद
> एक सामान्य `server.crt`/`server.key` जोड़ी संकेत करती है। **माइग्रेशन व्यवहार**: एक नए इंस्टॉल (कोई पूर्व
> `server.crt` नहीं) को रूट-CA मॉडल स्वचालित रूप से मिलता है; ऐसा इंस्टॉल जो पहले से
> पुराने स्थिर लीफ़ पर भरोसा करता है, उसका उपयोग तब तक जारी रखता है जब तक ऑपरेटर
> `MITM_ROOT_CA_ENABLED=true` सेट करके ब्रिज को रीस्टार्ट नहीं करता (`src/mitm/cert/migration.ts`
> शुद्ध निर्णय फ़ंक्शन है — ऐसा विश्वसनीय MITM CA जो **किसी भी** होस्ट के लिए लीफ़ पर हस्ताक्षर कर सकता है,
> पुराने निश्चित-SAN लीफ़ की तुलना में काफ़ी अधिक शक्तिशाली है, इसलिए
> पहले से विश्वसनीय इंस्टॉल के लिए यह बदलाव कभी भी बिना सूचना के नहीं होता)। CA प्रमाणपत्र
> उसी `omniroute-mitm.crt` ट्रस्ट-स्टोर स्लॉट में इंस्टॉल होता है जिसका उपयोग पुराना लीफ़ करता था
> (`cert/install.ts::installCaCert`) — दोहरे-विश्वास की सफ़ाई आवश्यक नहीं है।

### 2.3 हैंडलर बेस (`src/mitm/handlers/base.ts`)

सभी एजेंट हैंडलर `MitmHandlerBase` को एक्सटेंड करते हैं:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // संरक्षित सहायक: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

प्रत्येक हैंडलर प्रॉक्सी करने से पहले `hookBufferStart()` और पूर्ण होने पर `hookBufferUpdate()` को कॉल करता है। ये `InterceptedRequest` प्रविष्टियों को `globalTrafficBuffer` में पुश करते हैं ([Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4 देखें)।

### 2.4 लक्ष्य रजिस्ट्री (`src/mitm/targets/`)

प्रत्येक एजेंट की एक घोषणात्मक लक्ष्य फ़ाइल होती है:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

रजिस्ट्री (`targets/index.ts`) `ALL_TARGETS` को एक्सपोर्ट करती है और बूट के समय `DATA_DIR/mitm/targets.json` उत्सर्जित करती है।

### 2.5 पासथ्रू और बायपास सूची (`src/mitm/passthrough.ts`)

**बायपास सूची** (पहले जाँची जाती है, लक्ष्य मिलान से अधिक प्राथमिकता के साथ):

- डिफ़ॉल्ट पैटर्न: बैंकिंग होस्ट, `.gov.`, OAuth/SSO प्रदाता (Okta, Auth0), आदि।
- उपयोगकर्ता पैटर्न: DB टेबल `agent_bridge_bypass` में संग्रहीत
- बायपास किए गए होस्ट को एक पारदर्शी TCP टनल मिलती है — TLS को **कभी डिक्रिप्ट नहीं किया जाता**

**पासथ्रू डिफ़ॉल्ट** (लक्ष्य से कोई मेल नहीं और बायपास में भी नहीं):

- इसे भी एक TCP टनल मिलती है — कनेक्शन कभी नहीं तोड़े जाते
- AgentBridge को सामान्य सिस्टम HTTPS ट्रैफ़िक बाधित करने से रोकता है

रूटिंग प्राथमिकता:

```
बायपास सूची → लक्ष्य मिलान → पासथ्रू
```

### 2.6 अपस्ट्रीम CA प्रमाणपत्र (`src/mitm/upstreamTrust.ts`)

कस्टम CA वाले कॉर्पोरेट नेटवर्क परिवेशों के लिए:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

सेट किए जाने पर, अतिरिक्त CA प्रमाणपत्र के साथ `undici` के ग्लोबल डिस्पैचर को कॉन्फ़िगर करता है, जिससे AgentBridge कॉर्पोरेट TLS टर्मिनेशन प्रॉक्सी के माध्यम से अपस्ट्रीम प्रदाताओं तक पहुँच सकता है।

### 2.7 सीक्रेट मास्किंग (`src/mitm/maskSecrets.ts`)

स्वतंत्र क्लीन-रूम स्कैनर को अनुरोध बॉडी और क्रेडेंशियल हेडर पर,
Traffic Inspector बफ़र या किसी भी लॉग में उनके प्रवेश करने से **पहले** लागू किया जाता है। यह एकल रैखिक पास करता है:

- `sk-` / `ak-` / `pk-` प्रीफ़िक्स वाले टोकन (OpenAI/Anthropic-शैली)
- RFC 6750 `Authorization: Bearer <token>` क्रेडेंशियल, पूरे टोकन की प्राथमिकता के साथ
- सामान्य लंबे अपारदर्शी टोकन (≥40 वर्ण), जिनमें डॉट वाले और पैड किए गए रूप शामिल हैं

`sanitizeHeaders()` बनाए रखे गए नामों को लोअरकेस करता है, ऐरे मानों को नियतात्मक रूप से जोड़ता है,
साझा हॉप-बाय-हॉप/फ़्रेमिंग डिनायलिस्ट (प्रॉक्सी प्रमाणीकरण सहित) को हटाता है, `cookie` और
`set-cookie` को पूरी तरह रिडैक्ट करता है और क्रेडेंशियल मानों को स्कैनर को सौंपता है।

## §3 सेटअप

### 3.1 MITM सर्वर शुरू/बंद करें

`/dashboard/tools/agent-bridge` पर उपलब्ध AgentBridge Server Card का उपयोग करें:

| कार्रवाई                   | विवरण                                                                             |
| -------------------------- | --------------------------------------------------------------------------------- |
| सर्वर शुरू करें            | पोर्ट 443 पर `src/mitm/server.cjs` प्रारंभ करता है                                |
| सर्वर बंद करें             | चाइल्ड प्रोसेस को सुचारु रूप से बंद करता है                                       |
| सर्वर पुनः शुरू करें       | बंद + शुरू करता है (टार्गेट में हुए बदलाव लागू करता है)                           |
| प्रमाणपत्र पर विश्वास करें | `DATA_DIR/mitm/ca.crt` को OS ट्रस्ट स्टोर में इंस्टॉल करता है                     |
| प्रमाणपत्र डाउनलोड करें    | मैन्युअल इंस्टॉलेशन के लिए `ca.crt` डाउनलोड करता है                               |
| प्रमाणपत्र पुनः जनरेट करें | एक नया CA की-पेयर बनाता है (सभी मौजूदा प्रति-एजेंट प्रमाणपत्र अमान्य हो जाते हैं) |

### 3.2 प्रमाणपत्र पर विश्वास करें

IDE द्वारा MITM कनेक्शन स्वीकार किए जाने से पहले AgentBridge CA प्रमाणपत्र पर OS द्वारा विश्वास किया जाना आवश्यक है।

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

या डैशबोर्ड में "प्रमाणपत्र पर विश्वास करें" बटन का उपयोग करें (यह आपके OS के लिए उपयुक्त कमांड चलाता है और आवश्यकता होने पर sudo प्रॉम्प्ट दिखाता है)।

#### Electron-आधारित IDE, OS ट्रस्ट स्टोर को अनदेखा करते हैं (`NODE_EXTRA_CA_CERTS`)

कुछ IDE — विशेष रूप से **Antigravity IDE**, और अन्य Electron / VS Code-आधारित ऐप — अपना स्वयं का Node.js रनटाइम बंडल करते हैं, जो आउटबाउंड `fetch`/HTTPS के लिए **OS ट्रस्ट स्टोर का उपयोग नहीं करता**। OS/NSS स्तर पर CA पर विश्वास करना IDE के मूल **बैकएंड** के लिए पर्याप्त है (उदाहरण के लिए, एक Go लैंग्वेज सर्वर, जो OS CA बंडल का उपयोग करता है), लेकिन **Electron फ्रंटएंड** में फिर भी TLS विफल होगा — यह ऐप के _लॉग आउट_ दिखाई देने या _"कनेक्शन त्रुटि"_ दिखाने के रूप में सामने आता है, भले ही MITM लॉग में बैकएंड की बूटस्ट्रैप कॉल `200` लौटाती दिखाई दें। दो चरण आवश्यक हैं, और दोनों महत्वपूर्ण हैं:

1. रनटाइम को स्पष्ट रूप से CA की ओर इंगित करें:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **उसी शेल से IDE लॉन्च करें।** इसे डेस्कटॉप आइकन / Dock / Start मेन्यू से शुरू करने पर शेल एक्सपोर्ट इनहेरिट **नहीं** होते, और `~/.config/environment.d/*.conf` केवल नए ग्राफ़िकल लॉगिन के बाद लागू होता है। पहले IDE को पूरी तरह बंद करें — Electron के सिंगलटन लॉक के कारण दूसरा लॉन्च केवल मौजूदा प्रोसेस पर फ़ोकस करता है और नए एनवायरनमेंट को अनदेखा कर दिया जाता है।

ऊपर दिया गया OS-ट्रस्ट + NSS चरण फिर भी आवश्यक है (कुछ प्रमाणीकरण फ़्लो द्वारा उपयोग किया जाने वाला Chromium नेटवर्क स्टैक प्रति-उपयोगकर्ता NSS स्टोर को पढ़ता है, और `*.googleapis.com` के लिए उसके अपने स्टैटिक पिन होते हैं, जिन्हें स्थानीय रूप से विश्वसनीय CA ओवरराइड करता है)। इसके अतिरिक्त, `NODE_EXTRA_CA_CERTS` Node के `fetch` पाथ को कवर करता है।

### 3.3 DNS रूटिंग

जिस प्रत्येक एजेंट को आप इंटरसेप्ट करना चाहते हैं, उसके API होस्ट को `127.0.0.1` पर रिज़ॉल्व होना चाहिए। जब आप Setup Wizard में किसी एजेंट के लिए DNS टॉगल करते हैं, तो AgentBridge `/etc/hosts` प्रविष्टियों को स्वचालित रूप से प्रबंधित करता है।

GitHub Copilot के लिए `/etc/hosts` प्रविष्टियों का उदाहरण:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 मॉडल मैपिंग

स्रोत → टार्गेट मैपिंग परिभाषित करने के लिए प्रत्येक एजेंट कार्ड में Model Mapping Table का उपयोग करें:

| स्रोत मॉडल (एजेंट का मूल मॉडल) | टार्गेट मॉडल (OmniRoute) |
| ------------------------------ | ------------------------ |
| `gpt-4o`                       | `claude-sonnet-4.7`      |
| `*` (वाइल्डकार्ड)              | `claude-haiku-4.7`       |

वाइल्डकार्ड `*` किसी भी अपरिचित मॉडल को निर्दिष्ट टार्गेट पर मैप करता है। इसे `agent_bridge_mappings` तालिका में स्थायी रूप से सहेजा जाता है।

> **सुझाव — एजेंट की वास्तविक मॉडल ID खोजें।** कोई IDE ऐसे मॉडल नाम भेज सकता है जो
> उसके UI लेबल से भिन्न हों और प्रमुख संस्करणों के बीच बदलते हों। उदाहरण के लिए, **Antigravity 2**
> नेटवर्क पर `gemini-3.1-pro-low`, `gemini-pro-agent`, और `gemini-3.1-flash-lite` भेजता है —
> पुराने दस्तावेज़ों में दिखाया गया `gemini-2.5-pro` नहीं। कोई मेल खाती मैपिंग रखे बिना एक चैट
> भेजें: MITM सटीक इनकमिंग `model:` को लॉग करता है और अनुरोध को आगे जाने देता है। उस शाब्दिक
> मान को मैप करें; फिर अगला अनुरोध इंटरसेप्ट होकर आपके टार्गेट पर रूट किया जाएगा।

### 3.5 जोखिम सूचना

AgentBridge उन क्रेडेंशियल (OAuth टोकन, API कुंजियाँ) को इंटरसेप्ट करता है जिनका उपयोग IDE अपस्ट्रीम प्रदाताओं के साथ प्रमाणीकरण के लिए करता है। इन्हें **लॉग करने से पहले मास्क किया जाता है** (§2.7 देखें), लेकिन ये OmniRoute की MITM लेयर को दिखाई देते हैं। प्रत्येक एजेंट के पहले सक्रियण पर बंद की जा सकने वाली जोखिम सूचना वाला मोडल दिखाया जाता है।

### 3.6 रखरखाव और निदान

डैशबोर्ड एक **Maintenance & Diagnostics** कार्ड (`AgentBridgeMaintenanceCard`, `src/app/(dashboard)/dashboard/tools/agent-bridge/components/` में) उपलब्ध कराता है, जो उन परिचालन MITM रूट को प्रदर्शित करता है जिनके लिए पहले कोई UI नहीं था। इसका उपशीर्षक है: _"कैप्चर पाइपलाइन का स्वयं परीक्षण करें, बची हुई सिस्टम स्थिति को पूर्ववत करें और अपना सेटअप मशीनों के बीच स्थानांतरित करें।"_ कार्ड के क्लाइंट हेल्पर `src/lib/inspector/agentBridgeMaintenanceApi.ts` में मौजूद हैं।

| बटन                       | रूट                                    | यह क्या करता है                                                                                                                                                                                                  |
| ------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **निदान**                 | `GET /api/tools/agent-bridge/diagnose` | कैप्चर-पाइपलाइन का स्व-परीक्षण चलाता है और प्रत्येक जाँच की रिपोर्ट दिखाता है (✓/✗ + सुधार का संकेत)।                                                                                                            |
| **मरम्मत**                | `POST /api/tools/agent-bridge/repair`  | क्रैश या SIGKILL के कारण छूटी हुई अनाथ MITM सिस्टम स्थिति (DNS स्पूफ़ प्रविष्टियाँ, रूट CA, सिस्टम प्रॉक्सी) को पूर्ववत करता है। आइडेम्पोटेंट — स्थिति साफ़ होने पर "मरम्मत के लिए कुछ नहीं है" रिपोर्ट करता है। |
| **CA हटाएँ**              | `DELETE /api/tools/agent-bridge/cert`  | OS ट्रस्ट स्टोर से MITM रूट CA का भरोसा हटाता है और उसे निकालता है (स्पष्ट, आइडेम्पोटेंट)। केवल तभी दिखाया जाता है जब CA वर्तमान में विश्वसनीय हो; इसके लिए इनलाइन "CA हटाएँ?" पुष्टि आवश्यक है।                 |
| **कॉन्फ़िग निर्यात करें** | `GET /api/tools/agent-bridge/config`   | पोर्टेबल कॉन्फ़िग JSON डाउनलोड करता है (§3.7 देखें)।                                                                                                                                                             |
| **कॉन्फ़िग आयात करें**    | `POST /api/tools/agent-bridge/config`  | पहले निर्यात किया गया कॉन्फ़िग JSON अपलोड करता है (§3.7 देखें)।                                                                                                                                                  |

**निदान जाँचें** (`src/mitm/inspector/diagnostics.ts` में `summarizeDiagnostics()`)। रूट प्रत्येक के लिए प्रभावकारी प्रोब चलाता है और बूलियन मानों को शुद्ध सारांशकर्ता में भेजता है; एकल `healthy` निर्णय के साथ प्रत्येक विफलता के लिए एक संकेत लौटाया जाता है:

| जाँच का नाम        | यह क्या सत्यापित करता है                                     | विफलता पर संकेत                                                                                                                                                                   |
| ------------------ | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | MITM सर्वर प्रक्रिया सक्रिय है                               | "MITM सर्वर नहीं चल रहा है। इसे AgentBridge टैब से शुरू करें।"                                                                                                                    |
| `server-reachable` | MITM सर्वर अपने पोर्ट पर कनेक्शन स्वीकार करता है (TCP प्रोब) | "MITM सर्वर अपने पोर्ट पर कनेक्शन स्वीकार नहीं कर रहा है। जाँचें कि पोर्ट उपलब्ध है और आपके पास उससे बाइंड करने के विशेषाधिकार हैं।"                                              |
| `cert-exists`      | MITM प्रमाणपत्र डिस्क पर जनरेट किया गया है                   | "अभी तक कोई MITM प्रमाणपत्र जनरेट नहीं किया गया है। AgentBridge टैब से एक जनरेट करें।"                                                                                            |
| `cert-trusted`     | MITM रूट CA OS ट्रस्ट स्टोर में है                           | "MITM रूट CA पर OS स्टोर द्वारा भरोसा नहीं किया गया है, इसलिए TLS इंटरसेप्शन विफल होगा। AgentBridge टैब से प्रमाणपत्र पर भरोसा करें।"                                             |
| `dns-configured`   | लक्षित होस्टनाम `/etc/hosts` में स्पूफ़ किए गए हैं           | "लक्षित होस्टनाम /etc/hosts में स्पूफ़ नहीं किए गए हैं, इसलिए ट्रैफ़िक कभी प्रॉक्सी तक नहीं पहुँचता। जिन एजेंट के ट्रैफ़िक को आप कैप्चर करना चाहते हैं, उनके लिए DNS सक्षम करें।" |

**अनाथ-स्थिति बैनर:** जब पृष्ठ किसी क्रैश से छूटी हुई स्थिति (DNS स्पूफ़ / CA / सिस्टम प्रॉक्सी) का पता लगाता है, तो कार्ड एक एम्बर बैनर दिखाता है — _"पिछले सत्र ने सिस्टम स्थिति पीछे छोड़ दी है (DNS स्पूफ़, CA या सिस्टम प्रॉक्सी)। इसे साफ़ करने के लिए मरम्मत चलाएँ।"_ — और **मरम्मत** बटन को हाइलाइट करता है। `Repair`, ProxyBridge के `--cleanup` फ़्लैग का एप्लिकेशन-लेयर समकक्ष है (यह `src/mitm/manager.ts` में `repairMitm()` को कार्य सौंपता है)।

> बार-बार sudo प्रॉम्प्ट से बचने के लिए MITM रूट CA को रोकने/शुरू करने के दौरान इंस्टॉल रखा जाता है
> (mitmproxy/Charles जैसा ही व्यवहार), इसलिए उसे हटाना एक स्पष्ट
> **CA हटाएँ** क्रिया है, न कि ऐसा कुछ जो रोकने पर अपने आप होता है।

### 3.7 पोर्टेबल कॉन्फ़िग आयात/निर्यात

AgentBridge **ऑपरेटर द्वारा समायोज्य** स्थिति को एक संस्करणयुक्त JSON ब्लॉब में क्रमबद्ध कर सकता है, ताकि किसी सेटअप को कई मशीनों पर दोहराया जा सके। सीरियलाइज़र `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`) है, जिसे `AgentBridgeConfigSchema` द्वारा सत्यापित किया जाता है।

निर्यात में ठीक तीन हिस्से शामिल होते हैं (अंतर्निहित डिफ़ॉल्ट जानबूझकर **निर्यात नहीं** किए जाते, ताकि आयात करने पर वे कभी डुप्लिकेट न हों या उनसे टकराव न हो):

| फ़ील्ड           | स्रोत                                                     | टिप्पणियाँ                                                              |
| ---------------- | --------------------------------------------------------- | ----------------------------------------------------------------------- |
| `bypassPatterns` | उपयोगकर्ता-परिभाषित बायपास पैटर्न (`agent_bridge_bypass`) | डिफ़ॉल्ट bank/gov/okta पैटर्न शामिल नहीं किए जाते                       |
| `customHosts`    | Traffic Inspector कस्टम होस्ट (`inspector_custom_hosts`)  | प्रत्येक: `{ host, kind: "llm"\|"app"\|"custom", label? }`              |
| `agentMappings`  | प्रत्येक एजेंट के मॉडल मैपिंग (`agent_bridge_mappings`)   | मैपिंग वाले प्रत्येक एजेंट के लिए `{ [agentId]: [{ source, target }] }` |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**आयात व्यवहार** (`POST /api/tools/agent-bridge/config`): बायपास पैटर्न और प्रत्येक एजेंट की मैपिंग **पूरी तरह बदल दी जाती हैं**; कस्टम होस्ट **आइडेम्पोटेंट रूप से** जोड़े जाते हैं (`INSERT OR IGNORE`)। प्रतिक्रिया बताती है कि प्रत्येक में से कितने लागू किए गए:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

कॉन्फ़िगरेशन में क्या **नहीं** है: सर्वर के चलने की स्थिति, सर्टिफ़िकेट पाथ, प्रत्येक एजेंट की DNS स्थिति, अपस्ट्रीम CA पाथ और TPROXY सेटिंग्स — ये होस्ट/रनटाइम स्थिति हैं, पोर्टेबल प्राथमिकताएँ नहीं।

### संवेदनशील होस्ट के लिए बायपास सूची

बायपास सूची सुनिश्चित करती है कि वित्तीय संस्थानों, OAuth/SSO प्रदाताओं और अन्य संवेदनशील होस्ट का डेटा **कभी डिक्रिप्ट नहीं किया जाता**। उनका TLS ट्रैफ़िक एक पारदर्शी TCP टनल से होकर गुजरता है — OmniRoute कभी भी प्लेनटेक्स्ट नहीं देखता।

डिफ़ॉल्ट बायपास पैटर्न में शामिल हैं:

- `*.bank.*`, `*.gov.*` (वित्तीय/सरकारी)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/पहचान)
- `*.apple.com`, `*.icloud.com` (Apple सिस्टम सेवाएँ)

उपयोगकर्ता द्वारा जोड़े गए बायपास पैटर्न `agent_bridge_bypass` तालिका में संग्रहीत होते हैं और बाकी सभी चीज़ों पर प्राथमिकता रखते हैं।

### सीक्रेट मास्किंग

`src/mitm/maskSecrets.ts` से `maskSecrets()` लागू किया जाता है:

- `TrafficBuffer.push()` से पहले प्रत्येक अनुरोध बॉडी पर
- लॉगिंग या ब्रॉडकास्टिंग से पहले प्रत्येक हेडर पर

पैटर्न: `sk-`/`ak-`/`pk-` प्रीफ़िक्स वाले टोकन, `Bearer` टोकन और ≥40 वर्णों वाले सामान्य टोकन।

### अपस्ट्रीम CA प्रमाणपत्र

जब `AGENTBRIDGE_UPSTREAM_CA_CERT` सेट होता है, तो स्टार्टअप पर फ़ाइल पढ़ी जाती है। यदि पाथ मौजूद है लेकिन फ़ाइल पढ़ी नहीं जा सकती, तो AgentBridge एक स्पष्ट त्रुटि लॉग करता है और प्रारंभ होने से इनकार कर देता है (कॉर्पोरेट परिवेशों में बिना सूचना वाली TLS विफलताओं को रोकता है)।

### ज्ञात सीमाएँ

- **पोर्ट 443 के लिए विशेषाधिकार आवश्यक है**: Linux पर, AgentBridge को Node बाइनरी पर `setcap 'cap_net_bind_service=+ep'` की आवश्यकता होती है, या इसे `authbind` के माध्यम से चलाएँ। सेटअप विज़ार्ड OS-विशिष्ट निर्देश प्रदर्शित करता है।
- **IDE को पुनः प्रारंभ करना आवश्यक है**: DNS रीडायरेक्ट के बाद, नए होस्ट रिज़ॉल्यूशन को प्रभावी बनाने के लिए IDE को पुनः प्रारंभ करना आवश्यक है।
- **हार्डकोड किए गए OAuth टोकन**: कुछ एजेंट (Kiro, Antigravity) OAuth रिफ़्रेश टोकन स्थानीय रूप से संग्रहीत करते हैं। ये AgentBridge के लिए पारदर्शी होते हैं — यह प्रत्येक अनुरोध में Bearer टोकन देखता है, जिसे लॉगिंग से पहले मास्क कर दिया जाता है।
- **Electron फ़्रंटएंड को `NODE_EXTRA_CA_CERTS` की आवश्यकता होती है**: जिन IDE का फ़्रंटएंड बंडल किए गए Node/Electron रनटाइम पर चलता है, वे OS/NSS ट्रस्ट स्टोर को अनदेखा करते हैं और उन्हें ऐसे शेल से लॉन्च करना आवश्यक है जिसमें `NODE_EXTRA_CA_CERTS` सेट हो (§3.2 देखें)। इसके अनुपस्थित होने का लक्षण: IDE बैकएंड प्रमाणीकरण कर लेता है (MITM में `200` दिखाई देते हैं), लेकिन UI लॉग आउट ही रहता है।
- **एक ही IDE के एकाधिक इंस्टॉलेशन स्वतंत्र होते हैं**: एक सिस्टम इंस्टॉलेशन (उदाहरण के लिए, `/usr/share/antigravity/antigravity`) और उपयोगकर्ता-स्थानीय "Full" इंस्टॉलेशन (उदाहरण के लिए, `~/AntigravityIDE_Full/antigravity-ide`) अपनी-अपनी रनटाइम वाली अलग प्रक्रियाएँ हैं — प्रत्येक को CA इंजेक्ट करके दोबारा लॉन्च करना आवश्यक है। दोबारा लॉन्च करने से पहले उसके बाइनरी पाथ से पहचानें कि कौन-सा इंस्टॉलेशन चल रहा है।
- **पहचान एजेंट के सिस्टम प्रॉम्प्ट द्वारा सेट की जाती है, रूट किए गए मॉडल द्वारा नहीं**: जब आप किसी एजेंट के मॉडल को किसी भिन्न प्रदाता पर रीमैप करते हैं, तब भी उत्तर एजेंट की मूल पहचान का दावा करता है (उदाहरण के लिए, Antigravity उत्तर देता है "मैं Gemini द्वारा संचालित हूँ"), क्योंकि IDE इसे सिस्टम प्रॉम्प्ट में इंजेक्ट करता है। वास्तविक बैकएंड की पुष्टि मॉडल से यह पूछकर न करें कि वह कौन है, बल्कि `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`) में करें।

## §6 समस्या निवारण

### पोर्ट 443 का टकराव

यदि कोई अन्य प्रक्रिया पहले से ही पोर्ट 443 पर सुन रही है (वेब सर्वर, VPN, आदि):

```bash
lsof -i :443          # प्रक्रिया खोजें
sudo fuser -k 443/tcp  # बलपूर्वक समाप्त करें (सावधानी से उपयोग करें)
```

वैकल्पिक रूप से, AgentBridge सेटिंग्स में एक गैर-विशेषाधिकार प्राप्त पोर्ट कॉन्फ़िगर करें और `iptables` / `pf` रीडायरेक्ट नियम सेट करें।

### प्रमाणपत्र विश्वसनीय नहीं है

यदि AgentBridge शुरू करने के बाद IDE में TLS त्रुटियाँ दिखाई देती हैं:

1. सत्यापित करें कि प्रमाणपत्र इंस्टॉल किया गया था: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) या `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. कुछ ऐप अपने स्वयं के ट्रस्ट स्टोर बनाए रखते हैं (Firefox, Linux पर Chrome)। "Trust Cert" फिर से चलाएँ और NSS/Firefox-विशिष्ट प्रमाणपत्र स्टोर जाँचें।
3. विश्वास स्थापित करने के बाद IDE को पुनः आरंभ करें — जारी TLS सत्र पुरानी ट्रस्ट स्थिति का उपयोग करते हैं।

### विश्वसनीय CA के बावजूद IDE लॉग आउट है / "connection error"

लक्षण: DNS को रीडायरेक्ट करने और CA पर विश्वास स्थापित करने के बाद, कोई Electron-आधारित IDE (जैसे Antigravity)
**लॉग आउट** अवस्था में खुलता है या प्रमाणीकरण/कनेक्शन त्रुटि दिखाता है, जबकि MITM लॉग में
बूटस्ट्रैप कॉल (`loadCodeAssist`, `fetchAvailableModels`, …) `200` लौटाती दिखाई देती हैं।

कारण: IDE का **बंडल किया गया Node/Electron रनटाइम OS ट्रस्ट स्टोर को अनदेखा करता है**। मूल
बैकएंड (एक Go भाषा सर्वर) OS CA पर विश्वास करता है और प्रमाणीकरण करता है, लेकिन Electron फ़्रंटएंड
ऐसा नहीं करता — इसलिए UI मानता है कि वह ऑफ़लाइन है।

समाधान (दोनों चरण): `NODE_EXTRA_CA_CERTS=<ca.crt>` एक्सपोर्ट करें **और IDE को उसी
शेल से पुनः लॉन्च करें**, डेस्कटॉप आइकन से नहीं। पहले IDE को पूरी तरह बंद करें — Electron के सिंगलटन लॉक के कारण
दूसरा लॉन्च केवल मौजूदा प्रक्रिया को फ़ोकस करता है और नया परिवेश अनदेखा कर दिया जाता है। §3.2 देखें।
यह एक खुली अपस्ट्रीम रिपोर्ट के अनुरूप है, जिसमें एक स्वतंत्र एजेंट MITM के माध्यम से काम करता है, लेकिन IDE
संस्करण समान सेटअप के अंतर्गत विफल हो जाता है।

### DNS प्रसारित नहीं हुआ

जाँचें कि `/etc/hosts` अपडेट किया गया था:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

DNS कैश साफ़ करें:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE का पता नहीं चला

स्वचालित पहचान सामान्य इंस्टॉलेशन पथों का उपयोग करती है। यदि पहचान विफल हो जाती है, लेकिन IDE इंस्टॉल है:

- जाँचें कि IDE बाइनरी किसी गैर-मानक स्थान पर तो नहीं है
- Setup Wizard फिर भी काम करता है — पहचान की विफलता का अर्थ केवल यह है कि बैज इंस्टॉलेशन पथ नहीं दिखाएगा

### हैंडलर त्रुटियाँ (अपस्ट्रीम फ़ेच विफल)

यदि AgentBridge अनुरोधों को इंटरसेप्ट करता है, लेकिन सभी अनुरोध विफल हो जाते हैं:

1. सत्यापित करें कि `/dashboard/providers` पर कम-से-कम एक प्रदाता कनेक्टेड है
2. OmniRoute सर्वर लॉग जाँचें: `.env` में `APP_LOG_LEVEL=debug`
3. सत्यापित करें कि `OMNIROUTE_BASE_URL` सही राउटर एंडपॉइंट की ओर इंगित करता है (डिफ़ॉल्ट: `http://127.0.0.1:20128`)

## §8 रोडमैप

### Trae की जाँच

Trae एक अपेक्षाकृत नया AI कोडिंग सहायक है। हैंडलर लागू करने से पहले:

1. VS Code / JetBrains मार्केटप्लेस में या एक स्टैंडअलोन ऐप के रूप में बाइनरी/एक्सटेंशन की पहचान करें
2. API होस्ट और एंडपॉइंट संरचनाओं का पता लगाने के लिए mitmproxy से ट्रैफ़िक कैप्चर करें
3. प्रमाणीकरण तंत्र निर्धारित करें
4. TOS और API की खोज-क्षमता के आधार पर आगे बढ़ने या न बढ़ने का आकलन करें

जाँच पूरी होने तक, डैशबोर्ड में Trae कार्ड एक "जाँच जारी है" बैज के साथ "व्यवहार्यता रिपोर्ट करें" लिंक दिखाता है। `src/mitm/handlers/trae.ts` में मौजूद हैंडलर स्टब एक संरचित `अभी तक लागू नहीं किया गया` त्रुटि उत्पन्न करता है।

### बैकलॉग एजेंट (MITM आवश्यक — कस्टम बेस URL समर्थन नहीं)

निम्नलिखित टूल अपने वर्तमान संस्करणों में कस्टम बेस URL का समर्थन नहीं करते हैं, जिससे MITM ही एकमात्र इंटरसेप्शन मार्ग बनता है। व्यवहार्यता का आकलन लंबित है:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — Kiro IDE से अलग)
- **Cowork** (Anthropic डेस्कटॉप)

नोट: GitHub Copilot CLI ≥v1.0.19 `COPILOT_PROVIDER_BASE_URL` का समर्थन करता है — उस टूल के लिए MITM के बजाय प्रत्यक्ष कॉन्फ़िगरेशन का उपयोग करें।
