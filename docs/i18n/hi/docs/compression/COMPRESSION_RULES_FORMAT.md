> **प्रामाणिक स्कीमा (सत्य का स्रोत):** [`open-sse/services/compression/rules/_schema.json`](../../open-sse/services/compression/rules/_schema.json) (JSON Schema ड्राफ़्ट 2020-12)।
> नीचे दिए गए उदाहरण केवल स्पष्टीकरण के लिए हैं — संदेह होने पर अपने पैक को `_schema.json` के विरुद्ध सत्यापित करें।

## Caveman नियम पैक

Caveman नियम पैक यहाँ स्थित होते हैं:

```txt
open-sse/services/compression/rules/<language>/<pack>.json
```

प्रत्येक पैक में ऐसे प्रतिस्थापन होते हैं जो संरक्षित क्षेत्रों को अलग करने के बाद सामान्य गद्य पर लागू होते हैं।

```json
{
  "language": "en",
  "category": "filler",
  "rules": [
    {
      "name": "question_to_directive",
      "pattern": "\\b(?:Can you explain why|Could you show me how)\\b\\s*",
      "replacement": "Explain why ",
      "replacementMap": {
        "can you explain why": "Explain why ",
        "could you show me how": "Show how "
      },
      "flags": "gi",
      "context": "all",
      "category": "context",
      "minIntensity": "lite",
      "description": "Convert verbose questions into direct requests."
    }
  ]
}
```

### Caveman फ़ील्ड

| फ़ील्ड                   | आवश्यक | विवरण                                                                        |
| ------------------------ | ------ | ---------------------------------------------------------------------------- |
| `language`               | हाँ    | BCP-47-जैसी भाषा कुंजी, जैसे `en`, `pt-BR`, `es`                             |
| `category`               | हाँ    | पैक श्रेणी का फ़ाइल नाम/श्रेणी, उदाहरण के लिए `filler` या `dedup`            |
| `rules`                  | हाँ    | रेगुलर एक्सप्रेशन प्रतिस्थापन नियमों की सरणी                                 |
| `rules[].name`           | हाँ    | स्थिर नियम नाम                                                               |
| `rules[].pattern`        | हाँ    | JavaScript रेगुलर एक्सप्रेशन स्रोत                                           |
| `rules[].flags`          | नहीं   | JavaScript रेगुलर एक्सप्रेशन फ़्लैग; डिफ़ॉल्ट `gi`                           |
| `rules[].replacement`    | नहीं   | प्रतिस्थापन स्ट्रिंग या `replacementMap` में मिलान न मिलने पर फ़ॉलबैक        |
| `rules[].replacementMap` | नहीं   | सामान्यीकृत मिलान किए गए टेक्स्ट द्वारा कुंजीबद्ध, मिलान-विशिष्ट प्रतिस्थापन |
| `rules[].context`        | नहीं   | `all`, `user`, `assistant`, या `system`; डिफ़ॉल्ट `all`                      |
| `rules[].category`       | नहीं   | `filler`, `context`, `structural`, `dedup`, `terse`, या `ultra`              |
| `rules[].minIntensity`   | नहीं   | `lite`, `full`, या `ultra`; डिफ़ॉल्ट `lite`                                  |
| `rules[].description`    | नहीं   | मनुष्यों द्वारा पढ़ा जा सकने वाला नियम सारांश                                |

जब केस-संवेदी मिलान महत्वपूर्ण हो, तब `flags` का उपयोग करें; उदाहरण के लिए, छोटे अक्षरों वाले गद्य से पहले आर्टिकल हटाना
लेकिन `the OpenAI API` को न हटाना। जब किसी एक रेगुलर एक्सप्रेशन में कई विकल्प हों
जिनके लिए अलग-अलग आउटपुट आवश्यक हों, तब `replacementMap` का उपयोग करें; इससे अधिक समृद्ध
अंतर्निहित TypeScript प्रतिस्थापन फ़ंक्शनों के व्यवहार को बनाए रखते हुए JSON नियम पैक केवल डेटा तक सीमित रहते हैं।

## RTK फ़िल्टर पैक

RTK फ़िल्टर यहाँ स्थित होते हैं:

```txt
open-sse/services/compression/engines/rtk/filters/<filter>.json
```

प्रत्येक फ़िल्टर बताता है कि किसी कमांड-आउटपुट परिवार को कैसे पहचाना और संपीड़ित किया जाए।

```json
{
  "id": "test-vitest",
  "label": "Vitest output",
  "category": "test",
  "priority": 92,
  "match": {
    "outputTypes": ["test-vitest"],
    "commands": ["vitest", "npm test", "npm run test"],
    "patterns": ["\\bFAIL\\b", "\\bPASS\\b", "\\bTest Files\\b"]
  },
  "rules": {
    "stripAnsi": true,
    "replace": [{ "pattern": "\\s+\\[[0-9]+ms\\]", "replacement": "" }],
    "matchOutput": [
      {
        "pattern": "All tests passed",
        "message": "vitest: ok",
        "unless": "FAIL|Error:"
      }
    ],
    "includePatterns": ["FAIL", "Error:", "Test Files", "Tests"],
    "dropPatterns": ["^\\s*$", "Duration\\s+\\d+"],
    "collapsePatterns": ["^\\s+at "],
    "deduplicate": true,
    "truncateLineAt": 240,
    "maxLines": 160,
    "headLines": 24,
    "tailLines": 40,
    "onEmpty": "vitest: ok",
    "filterStderr": false
  },
  "preserve": {
    "errorPatterns": ["FAIL", "Error:", "AssertionError"],
    "summaryPatterns": ["Test Files", "Tests", "Snapshots"]
  },
  "tests": [
    {
      "name": "keeps failing tests",
      "command": "vitest",
      "input": "FAIL test/a.test.ts\\nError: boom\\nTest Files 1 failed",
      "expected": "FAIL test/a.test.ts\\nError: boom\\nTest Files 1 failed"
    }
  ]
}
```

### RTK फ़ील्ड

| फ़ील्ड                     | आवश्यक | विवरण                                                                             |
| -------------------------- | ------ | --------------------------------------------------------------------------------- |
| `id`                       | हाँ    | स्थिर फ़िल्टर आईडी                                                                |
| `label`                    | हाँ    | डैशबोर्ड पर पढ़े जाने योग्य नाम                                                   |
| `category`                 | हाँ    | फ़िल्टर परिवार: git, test, build, shell, docker, package, infra, cloud, generic   |
| `priority`                 | नहीं   | एकाधिक फ़िल्टर मेल खाने पर उच्च प्राथमिकता वाला फ़िल्टर चुना जाता है              |
| `match.outputTypes`        | नहीं   | इस फ़िल्टर को चुनने वाली डिटेक्टर आउटपुट आईडी                                     |
| `match.commands`           | नहीं   | इस फ़िल्टर को चुनने वाले कमांड टोकन                                               |
| `match.patterns`           | नहीं   | आउटपुट टेक्स्ट से इस फ़िल्टर को चुनने वाले रेगुलर एक्सप्रेशन पैटर्न               |
| `rules.stripAnsi`          | नहीं   | रेगुलर एक्सप्रेशन चरणों से पहले ANSI एस्केप अनुक्रम हटाएँ                         |
| `rules.replace`            | नहीं   | पंक्ति-दर-पंक्ति लागू किए जाने वाले क्रमबद्ध रेगुलर एक्सप्रेशन प्रतिस्थापन        |
| `rules.matchOutput`        | नहीं   | वैकल्पिक `unless` गार्ड वाले शॉर्ट-सर्किट आउटपुट नियम                             |
| `rules.includePatterns`    | नहीं   | वे पंक्तियाँ जिन्हें संरक्षित रखने को प्राथमिकता दी जानी चाहिए                    |
| `rules.dropPatterns`       | नहीं   | अवांछित सामग्री के रूप में हटाई जाने वाली पंक्तियाँ                               |
| `rules.collapsePatterns`   | नहीं   | बार-बार मेल खाने वाली पंक्तियाँ जिन्हें संक्षिप्त किया जा सकता है                 |
| `rules.deduplicate`        | नहीं   | डुप्लिकेट सामान्यीकृत पंक्तियों को संक्षिप्त करें                                 |
| `rules.truncateLineAt`     | नहीं   | प्रत्येक पंक्ति के लिए Unicode-सुरक्षित वर्ण सीमा                                 |
| `rules.maxLines`           | नहीं   | अंतिम पंक्तियों को संरक्षित करने से पहले रखी जाने वाली पंक्तियों की अधिकतम संख्या |
| `rules.headLines`          | नहीं   | ट्रंकेशन के दौरान रखी जाने वाली आरंभिक पंक्तियाँ                                  |
| `rules.tailLines`          | नहीं   | हालिया संदर्भ के लिए रखी जाने वाली अंतिम पंक्तियाँ                                |
| `rules.onEmpty`            | नहीं   | फ़िल्टरिंग द्वारा सारी सामग्री हटाए जाने पर फ़ॉलबैक संदेश                         |
| `rules.filterStderr`       | नहीं   | बाद के फ़िल्टरिंग चरणों से पहले सामान्य stderr उपसर्गों को सामान्यीकृत करें       |
| `preserve.errorPatterns`   | नहीं   | वे त्रुटि पंक्तियाँ जिन्हें ट्रंकेशन के बाद भी बने रहना चाहिए                     |
| `preserve.summaryPatterns` | नहीं   | वे सारांश पंक्तियाँ जिन्हें ट्रंकेशन के बाद भी बने रहना चाहिए                     |
| `tests[]`                  | नहीं   | RTK सत्यापन गेट द्वारा उपयोग किए जाने वाले इनलाइन सत्यापन नमूने                   |

RTK घोषणात्मक चरणों को इस क्रम में लागू करता है: `stripAnsi`, `filterStderr`, `replace`,
`matchOutput`, `dropPatterns`/`includePatterns`, `truncateLineAt`, `headLines`/`tailLines`,
`maxLines`, और `onEmpty`।

कस्टम फ़िल्टर निम्न स्थानों से लोड किए जा सकते हैं:

1. प्रोजेक्ट की `.rtk/filters.json` फ़ाइलें केवल तभी, जब मेल खाने वाला `.rtk/trust.json` हैश मौजूद हो या
   `trustProjectFilters` सक्षम हो।
2. वैश्विक `DATA_DIR/rtk/filters.json`।
3. अंतर्निहित फ़िल्टर।

प्रोजेक्ट/वैश्विक कस्टम फ़ाइलों में एक फ़िल्टर ऑब्जेक्ट या फ़िल्टर ऑब्जेक्ट की एक सरणी हो सकती है। अमान्य
कस्टम फ़िल्टर डायग्नोस्टिक्स के साथ छोड़ दिए जाते हैं; अमान्य अंतर्निहित फ़िल्टर सत्यापन को विफल कर देते हैं।

प्रोजेक्ट ट्रस्ट फ़ाइल:

```json
{
  "filtersSha256": "0123456789abcdef..."
}
```

एनवायरनमेंट ओवरराइड `OMNIROUTE_RTK_TRUST_PROJECT_FILTERS=1` बिना हैश के प्रोजेक्ट फ़िल्टरों पर भरोसा करता है और
इसे नियंत्रित स्थानीय डेवलपमेंट तक सीमित रखा जाना चाहिए।

## सुरक्षा नियम

- नियमों को इडेम्पोटेंट रखें: एक ही फ़िल्टर को दो बार चलाने पर आउटपुट दूषित नहीं होना चाहिए।
- जहाँ संभव हो, सटीक त्रुटि टेक्स्ट, फ़ाइल पथ, लाइन नंबर और कमांड सारांश सुरक्षित रखें।
- ऐसे नियमों से बचें जो कोड ब्लॉक, JSON पेलोड, URLs या सीक्रेट्स को संशोधित करते हों।
- डिटेक्टर/फ़िल्टर परीक्षणों में नई कमांड फ़ैमिली के लिए यूनिट कवरेज जोड़ें।
- प्रत्येक बिल्ट-इन फ़िल्टर और साझा कस्टम फ़िल्टर में `tests[]` नमूने जोड़ें।

## सत्यापन

नियम पैक उपयोग से पहले सत्यापित किए जाते हैं। बिल्ट-इन Caveman पैक और बिल्ट-इन RTK फ़िल्टर सत्यापन के दौरान तुरंत विफल हो जाते हैं, ताकि खराब रिलीज़ एसेट्स को शिपमेंट से पहले पकड़ा जा सके। पार्सिंग या ट्रस्ट सत्यापन विफल होने पर कस्टम RTK फ़िल्टर को डायग्नोस्टिक्स के साथ छोड़ दिया जाता है।

केंद्रित सत्यापन:
