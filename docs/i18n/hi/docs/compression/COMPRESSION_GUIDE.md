> योग्य कॉन्टेक्स्ट पर स्वचालित रूप से 15-95% बचाएँ। त्वरित अवलोकन के लिए, [README का कम्प्रेशन अनुभाग](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) देखें।

## अवलोकन

OmniRoute एक मॉड्यूलर प्रॉम्प्ट कम्प्रेशन पाइपलाइन लागू करता है, जो अनुरोधों के अपस्ट्रीम प्रदाताओं तक पहुँचने से **पहले ही सक्रिय रूप से** चलती है। इसका अर्थ है कि आपके टोकन की बचत पारदर्शी रूप से होती है — आपके वर्कफ़्लो में किसी बदलाव की आवश्यकता नहीं है।

```
क्लाइंट अनुरोध
  → कम्प्रेशन रणनीति चयनकर्ता
    → कॉम्बो ओवरराइड? → कॉम्बो सेटिंग का उपयोग करें
    → ऑटो-ट्रिगर थ्रेशोल्ड? → ऑटो मोड का उपयोग करें
    → डिफ़ॉल्ट मोड? → ग्लोबल सेटिंग का उपयोग करें
    → बंद? → कम्प्रेशन छोड़ें
  → चयनित कम्प्रेशन मोड
    → बंद: कोई कम्प्रेशन नहीं
    → लाइट: सुरक्षित व्हाइटस्पेस/फ़ॉर्मेटिंग क्लीनअप (~15%)
    → स्टैंडर्ड: Caveman-शैली में फ़िलर हटाना (~30%)
    → एग्रेसिव: हिस्ट्री एजिंग + सारांशीकरण (~50%)
    → अल्ट्रा: ह्यूरिस्टिक प्रूनिंग + कोड-ब्लॉक थिनिंग (~75%)
    → RTK: कमांड-सचेत टर्मिनल/टूल-आउटपुट फ़िल्टरिंग (60-90% अपस्ट्रीम सीमा)
    → स्टैक्ड: क्रमबद्ध मल्टी-इंजन पाइपलाइन, आम तौर पर पहले RTK फिर Caveman (78-95% योग्य सीमा)
  → कम्प्रेस किया गया अनुरोध → प्रदाता
```

## कम्प्रेशन मोड

### बंद

कोई कम्प्रेशन लागू नहीं किया जाता। सभी संदेश बिना बदलाव के भेजे जाते हैं।

### लाइट मोड (~15% बचत, <1ms विलंबता)

सबसे सुरक्षित मोड — कोई अर्थगत बदलाव नहीं, केवल फ़ॉर्मेटिंग क्लीनअप:

| तकनीक                    | विवरण                                              |
| ------------------------ | -------------------------------------------------- |
| `collapseWhitespace`     | लगातार खाली पंक्तियों और अंत के स्पेस को मर्ज करें |
| `dedupSystemPrompt`      | डुप्लिकेट सिस्टम संदेश हटाएँ                       |
| `compressToolResults`    | विस्तृत टूल/फ़ंक्शन आउटपुट कम्प्रेस करें           |
| `removeRedundantContent` | दोहराए गए निर्देश हटाएँ                            |
| `replaceImageUrls`       | base64 इमेज डेटा URI को छोटा करें                  |

**इनके लिए सर्वोत्तम:** हमेशा चालू रहने वाला उपयोग, सुरक्षा-महत्वपूर्ण वर्कफ़्लो।

### स्टैंडर्ड मोड (~30% बचत)

[Caveman](https://github.com/JuliusBrussee/caveman) से प्रेरित — अर्थ को सुरक्षित रखते हुए फ़िलर शब्दों और अनावश्यक रूप से विस्तृत वाक्यांशों को हटाता है:

- फ़िलर शब्द हटाता है ("कृपया", "मुझे लगता है", "मूल रूप से", "वास्तव में")
- विस्तृत वाक्यांशों को संक्षिप्त करता है ("ऐसा करने के लिए" → "के लिए", "के परिणामस्वरूप" → "क्योंकि")
- विनम्र अनिश्चितता वाले वाक्यांश हटाता है ("क्या आपको आपत्ति होगी...", "यदि आप संभवतः ऐसा कर सकें...")
- कोडिंग प्रॉम्प्ट के लिए अनुकूलित 30+ regex नियम

**इनके लिए सर्वोत्तम:** दैनिक कोडिंग वर्कफ़्लो, लागत के प्रति सजग टीमें।

### एग्रेसिव मोड (~50% बचत)

लंबे सत्रों के लिए स्मार्ट हिस्ट्री प्रबंधन:

- **संदेश एजिंग** — पुराने संदेश क्रमिक रूप से अधिक कम्प्रेस किए जाते हैं
- **टूल परिणाम कम्प्रेशन** — लंबे टूल आउटपुट को छोटा किया जाता है या हटाया जाता है (पहली/अंतिम पंक्तियाँ,
  मेल खाने वाली पंक्तियों की फ़िल्टरिंग, JSON कुंजी संकुचन)
- **संरचनात्मक अखंडता गार्ड** — सुनिश्चित करते हैं कि `tool_use` + `tool_result` युग्म संगत रहें
- **कॉन्टेक्स्ट विंडो जागरूकता** — प्रत्येक मॉडल की टोकन सीमा का पालन करती है

**इनके लिए सर्वोत्तम:** विस्तारित डीबगिंग सत्र, बड़े कोडबेस।

### अल्ट्रा मोड (~75% बचत)

टोकन-महत्वपूर्ण परिदृश्यों के लिए अधिकतम कम्प्रेशन:

- **ह्यूरिस्टिक प्रूनिंग** — गद्य की स्कोर-आधारित टोकन प्रूनिंग
- **संरचना संरक्षण** — फ़ेंस किए गए कोड ब्लॉक, इनलाइन कोड, URL और आइडेंटिफ़ायर को
  टूम्बस्टोन करके ज्यों का त्यों दोबारा जोड़ा जाता है, उन्हें कभी प्रून नहीं किया जाता
- **वैकल्पिक SLM स्तर** — कॉन्फ़िगर किए जाने पर एक छोटा लोकल मॉडल प्रूनिंग को परिष्कृत कर सकता है
- एग्रेसिव मोड से स्वतंत्र: यह संदेश एजिंग, टूल-परिणाम कम्प्रेशन
  या फ़ॉलबैक सारांशक नहीं चलाता (केवल SLM-स्तर की विफलता ही किसी फ़ॉलबैक पास को
  एग्रेसिव के माध्यम से रूट कर सकती है)

**इनके लिए सर्वोत्तम:** जब आप बार-बार कॉन्टेक्स्ट सीमा तक पहुँच रहे हों।

### RTK मोड (60-90% अपस्ट्रीम सीमा)

RTK मोड को कोडिंग-एजेंट सत्रों में दिखाई देने वाले विस्तृत टूल आउटपुट के लिए अनुकूलित किया गया है:

- `git status`, `git diff`, `git log`, टेस्ट रनर,
  TypeScript/Vite/Webpack बिल्ड, ESLint/Biome/Prettier, npm ऑडिट/इंस्टॉलेशन, Docker लॉग, इन्फ़्रा
  आउटपुट और सामान्य शेल आउटपुट जैसे कमांड/आउटपुट वर्गों का पता लगाता है
- `open-sse/services/compression/engines/rtk/filters/` से JSON फ़िल्टर पैक लागू करता है
- प्रोजेक्ट या ग्लोबल `filters.toml` फ़ाइलों से RTK TOML schema v1 फ़िल्टर आयात करता है, जिसमें इनलाइन-टेस्ट
  सत्यापन और प्रोजेक्ट फ़ाइलों के लिए ट्रस्ट-गेटिंग शामिल है
- इनलाइन सत्यापन नमूनों के साथ 55 अंतर्निहित फ़िल्टर प्रदान करता है
- ANSI नियंत्रण अनुक्रम, प्रोग्रेस बार, दोहराई गई पंक्तियाँ और गैर-कार्रवाई योग्य शोर हटाता है
- विफलताओं, त्रुटियों, चेतावनियों, बदली गई फ़ाइलों, सारांशों और लंबे आउटपुट के अंतिम भाग को सुरक्षित रखता है
- ट्रस्ट-गेटेड प्रोजेक्ट फ़िल्टर, ग्लोबल फ़िल्टर और वैकल्पिक रूप से संपादित रॉ-आउटपुट रिकवरी का समर्थन करता है

**इनके लिए सर्वोत्तम:** शेल, बिल्ड, टेस्ट, git, grep और फ़ाइल-आउटपुट ट्रांसक्रिप्ट वाले एजेंट सत्र।

### स्टैक्ड मोड (78-95% योग्य सीमा)

स्टैक्ड मोड एक नियतात्मक क्रम में कई कम्प्रेशन इंजन चलाता है। डिफ़ॉल्ट पाइपलाइन है:

```txt
RTK -> Caveman
```

यह क्रम पहले टर्मिनल/टूल आउटपुट को संक्षिप्त रखता है, फिर शेष प्राकृतिक-भाषा प्रॉम्प्ट पर Caveman अर्थगत संक्षेपण लागू करता है। स्टैक्ड पाइपलाइन को ग्लोबल रूप से या रूटिंग कॉम्बो को असाइन किए गए कम्प्रेशन कॉम्बो के माध्यम से कॉन्फ़िगर किया जा सकता है।

**इनके लिए सर्वोत्तम:** बड़े टूल लॉग के साथ मानवीय निर्देशों या सहायक सारांशों वाला मिश्रित कॉन्टेक्स्ट।

## अपस्ट्रीम बचत का गणित

OmniRoute दो स्रोतों से प्राप्त कम्प्रेशन बचत का दस्तावेज़ीकरण करता है: अपस्ट्रीम प्रोजेक्ट बेंचमार्क और
OmniRoute की अपनी इंजन संरचना।

| स्रोत   | यहाँ उपयोग की गई अपस्ट्रीम README संख्या                                                            |
| ------- | --------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` कम आउटपुट टोकन, `65%` बेंचमार्क औसत आउटपुट बचत, `22-87%` सीमा, और `~46%` इनपुट कम्प्रेशन टूल |
| RTK     | `60-90%` कमांड-आउटपुट बचत; नमूना सत्र में `~118,000 -> ~23,900` टोकन, या `79.7%` बचत (`~80%`)       |

ओवरलैप होने वाले टूल/कॉन्टेक्स्ट पेलोड के लिए, डिफ़ॉल्ट OmniRoute कॉम्बो इंजनों को क्रमबद्ध करता है:

```txt
RTK -> Caveman
```

संयुक्त बचत गुणात्मक होती है, योगात्मक नहीं:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

यह `78-95%` संख्या तब लागू होती है, जब RTK और Caveman दोनों समान इनपुट/कॉन्टेक्स्ट पेलोड को कम कर सकते हैं।
Caveman प्रतिक्रिया आउटपुट मोड अलग है: सक्षम होने पर, Caveman की अपनी आउटपुट बचत (`65%`
औसत, `~75%` प्रमुख आँकड़ा, `22-87%` सीमा) का उपयोग करें। कुल बिलिंग बचत आपके प्रॉम्प्ट/आउटपुट मिश्रण पर निर्भर करती है।

### "पात्र" का वास्तव में क्या अर्थ है

15-95% की प्रमुख सीमा वास्तविक है, लेकिन यह केवल **अनावश्यक रूप से दोहराई गई या अत्यधिक विस्तृत** सामग्री पर लागू होती है — बार-बार आने वाली
त्रुटि पंक्तियाँ, एक बिल्ड लॉग जो उसी चेतावनी को बार-बार दिखाता है, या बहुत बड़ा `grep`/फ़ाइल-रीड डंप। इसका
अर्थ यह **नहीं** है कि प्रत्येक अनुरोध में इतनी बचत होगी।

प्रायोगिक रूप से सत्यापित (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300 समान
त्रुटि पंक्तियों वाले Anthropic-आकार के `tool_result` ब्लॉक पर चलाए गए
`stacked` (RTK + Caveman) रन ने **95.93% टोकन बचत / 96.26% कैरेक्टर बचत** दी — जो विज्ञापित
सीमा के ठीक भीतर है। लेकिन सामान्य, गैर-दोहराव वाले टूल आउटपुट (एक साफ़ `grep` मिलान सूची,
एक छोटी फ़ाइल रीड, सामान्य संवादात्मक टेक्स्ट) पर चलाई गई वही पाइपलाइन सही रूप से **लगभग शून्य बचत** देती है, क्योंकि
हटाने के लिए कुछ भी दोहराव वाला नहीं होता और `validateCompression()` (`validation.ts`) ऐसे
पुनर्लेखन को भेजने से मना कर देता है जो कोड ब्लॉक, URLs, शीर्षक, संस्करण, या ALL-CAPS स्थिरांक पहचानकर्ताओं को हटा या बदल सकता हो।

यह अपेक्षित और सुरक्षित व्यवहार है, कोई बग नहीं: ऐसा कोडिंग सत्र जो मुख्यतः साफ़ फ़ाइलों को पढ़ता/grep करता है,
पूर्ण रूप से सक्षम कम्प्रेशन के बावजूद मामूली कुल बचत दिखाएगा, जबकि विफल
लूप या अत्यधिक आउटपुट देने वाले लिंटर का सामना करने वाला सत्र उस ट्रैफ़िक पर पूरी 78-95% सीमा देखेगा। किसी एक सत्र की
कम समग्र बचत प्रतिशत को इस बात का प्रमाण न मानें कि कम्प्रेशन गलत तरीके से कॉन्फ़िगर किया गया है — पहले जाँचें कि
अंतर्निहित टूल आउटपुट वास्तव में दोहराव वाला था या नहीं।

## कॉन्फ़िगरेशन

### डैशबोर्ड

`Dashboard → Context & Cache` पर जाएँ:

- **Caveman** — मोड चयन, भाषा पैक, पूर्वावलोकन और वैश्विक डिफ़ॉल्ट
- **RTK** — कमांड-फ़िल्टर पूर्वावलोकन, RTK सुरक्षा सेटिंग्स और फ़िल्टर कैटलॉग
- **Compression Combos** — रूटिंग कॉम्बो को असाइन की गई नामित इंजन पाइपलाइन
- **Auto-Trigger Threshold** — टोकन की संख्या थ्रेशोल्ड से अधिक होने पर कम्प्रेशन को स्वचालित रूप से सक्रिय करना

### प्रति-कॉम्बो ओवरराइड

`Dashboard → Context & Cache → Compression Combos` में, किसी रूटिंग कॉम्बो को कम्प्रेशन कॉम्बो असाइन करें:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

इससे आप सशुल्क सब्सक्रिप्शन पर लाइट मोड बनाए रखते हुए मुफ़्त/कोडिंग प्रोवाइडर पर स्टैक्ड कम्प्रेशन का उपयोग कर सकते हैं।

यह "Per-Combo Override" असाइनमेंट **routing-combo compression mode** ओवरराइड (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — फ़ील्ड का स्कीमा `rtk`, `stacked` और `omniglyph` को भी स्वीकार करता है) से अलग नियंत्रण है — वह ओवरराइड किसी नामित कम्प्रेशन-कॉम्बो पाइपलाइन को नहीं चुनता; वह केवल `resolveCompressionPlan` द्वारा उपयोग किए जाने वाले `compressionMode` फ़ील्ड को सेट करता है। इसे कॉम्बो कार्ड (`Dashboard → Combos`) पर या, #6760 से, `Dashboard → Context & Cache → Compression Combos` की "Assign to routing" सूची में प्रति रूटिंग कॉम्बो, ऊपर दस्तावेज़ीकृत पाइपलाइन-असाइनमेंट चेकबॉक्स के ठीक बगल में सेट किया जा सकता है। दोनों इंटरफ़ेस एक ही `PUT /api/combos/{id}` एंडपॉइंट के माध्यम से सेव किए जाते हैं।

### प्रति-अनुरोध ओवरराइड

किसी एक अनुरोध के लिए कम्प्रेशन प्लान को ओवरराइड करने हेतु `x-omniroute-compression` अनुरोध हेडर भेजें। इसकी प्राथमिकता सबसे अधिक होती है — यह रूटिंग-कॉम्बो ओवरराइड, सक्रिय प्रोफ़ाइल, ऑटो-ट्रिगर और पैनल के Default पर प्राथमिकता लेता है। अज्ञात मानों को अनदेखा कर दिया जाता है (अनुरोध कभी अस्वीकार नहीं होता) और वैश्विक मास्टर स्विच अभी भी सब कुछ नियंत्रित करता है: जब कम्प्रेशन वैश्विक रूप से बंद हो, तो हेडर उसे चालू नहीं कर सकता। मान:

| मान           | प्रभाव                                                                                          |
| ------------- | ----------------------------------------------------------------------------------------------- |
| `off`         | इस अनुरोध के लिए कोई कम्प्रेशन नहीं।                                                            |
| `default`     | पैनल से प्राप्त Default प्रोफ़ाइल (सक्रिय प्रोफ़ाइल को अनदेखा करता है)। लॉसी इंजन बंद रहते हैं। |
| `safe`        | हेडर को छोड़ देने के समान: केवल डीडुप और व्हाइटस्पेस फ़ोल्डिंग।                                 |
| `allow-lossy` | सारांश, प्रासंगिकता फ़िल्टर और शैली पुनर्लेखन सहित इस अनुरोध के ऑपरेटर प्लान को बनाए रखें।      |
| `engine:<id>` | सक्षम होने पर एक इंजन, जैसे `engine:rtk`। यह उस इंजन के लिए प्रति-अनुरोध ऑप्ट-इन है।            |
| `<combo>`     | एक नामित कॉम्बो, जिसका मिलान पहले नाम (केस-असंवेदी) से और फिर id से किया जाता है।               |

`allow-lossy`, `engine:<id>` या किसी नामित कॉम्बो के बिना, लॉसी इंजन लागू नहीं किए जाते। कम्प्रेशन चालू होने पर अनुरोध पर अभी भी सेशन डीडुप और व्हाइटस्पेस फ़ोल्डिंग लागू होती है।

लागू किया गया प्लान `X-OmniRoute-Compression: <mode>; source=<source>` रिस्पॉन्स हेडर में वापस भेजा जाता है, जहाँ `<source>`, `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` या `off` में से एक होता है।

## उन्नत कंप्रेशन सिस्टम

ऊपर वर्णित 7 मोड के अतिरिक्त (स्रोत `codex-responses` और
`omniglyph` मोड भी स्वीकार करता है, जिन्हें यह गाइड कवर नहीं करती), नीचे दिए गए अनुभाग उन सुविधाओं को कवर करते हैं
जो उन मोड के भीतर या उनके साथ काम करती हैं: टूल रिज़ल्ट कंप्रेशन और प्रोग्रेसिव एजिंग,
एग्रेसिव इंजन के चरण 1 और 2 हैं (एग्रेसिव मोड और स्टैक्ड पाइपलाइन का एक `aggressive` चरण), स्टैक्ड पाइपलाइन
वह तरीका है जिससे स्टैक्ड मोड चलता है, कैश-अवेयर कंप्रेशन, कंप्रेशन चालू रहने के दौरान कैशिंग प्रदाताओं के लिए
`aggressive` और `ultra` को `standard` में डाउनग्रेड करता है, और Caveman आउटपुट मोड तथा आउटपुट स्टाइल्स वैकल्पिक सिस्टम-प्रॉम्प्ट निर्देश हैं,
जो डिफ़ॉल्ट रूप से बंद रहते हैं और अनुरोध को कंप्रेस करने के बजाय मॉडल के आउटपुट को आकार देते हैं।

### कैश-अवेयर कंप्रेशन

कुछ प्रदाता (जैसे प्रॉम्प्ट कैशिंग के साथ Anthropic) **प्रॉम्प्ट कैशिंग** का समर्थन करते हैं,
जो लागत और विलंबता कम करने के लिए उन्हें प्रॉम्प्ट के कुछ हिस्सों को कैश करने देता है। जब
कैशिंग सक्षम होती है, तो एग्रेसिव कंप्रेशन वास्तव में प्रदर्शन को **नुकसान** पहुँचा सकता है
क्योंकि यह कैश किए गए टोकन बदल देता है, जिससे कैश अमान्य हो जाता है।

`cachingAware.ts` मॉड्यूल **कैशिंग कॉन्टेक्स्ट का पता लगाकर** और
उसके अनुसार **कंप्रेशन रणनीति समायोजित करके** इस समस्या को हल करता है।

#### यह कैसे काम करता है

1. **कैशिंग कॉन्टेक्स्ट का पता लगाएँ** — `cache_control` मार्करों के लिए अनुरोध बॉडी को स्कैन करता है
2. **कैशिंग प्रदाताओं की पहचान करें** — जाँचता है कि लक्षित प्रदाता कैशिंग का समर्थन करता है या नहीं
3. **रणनीति समायोजित करें** — कैशिंग प्रदाताओं के लिए `aggressive`/`ultra` को `standard` में डाउनग्रेड करता है
4. **सिस्टम प्रॉम्प्ट छोड़ें** — सिस्टम प्रॉम्प्ट आमतौर पर कैश किए जाते हैं, इसलिए उन्हें कंप्रेस न करें

रणनीति हेल्पर एक `deterministicOnly` फ़्लैग भी लौटाता है, लेकिन प्लान बिल्डर केवल
रणनीति का उपयोग करता है — वर्तमान में डाउनस्ट्रीम में कोई भी उस फ़्लैग को नहीं पढ़ता।

#### कोड उदाहरण

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← कैश मार्कर
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### कब उपयोग करें

कैश-अवेयर कंप्रेशन **हमेशा चालू रहता है** — किसी कॉन्फ़िगरेशन की आवश्यकता नहीं है। यह तब सक्रिय होता है जब
कंप्रेशन चालू हो और लक्षित प्रदाता प्रॉम्प्ट कैशिंग (Anthropic, OpenAI,
आदि) का समर्थन करता हो; स्पष्ट `cache_control` मार्करों की आवश्यकता नहीं होती — केवल कैशिंग प्रदाता ही
डाउनग्रेड ट्रिगर कर देता है, और केवल मार्कर ऐसा कभी नहीं करते (मार्कर डिटेक्शन कैश
टेलीमेट्री को फ़ीड करता है, रणनीति के निर्णय को नहीं)।

### प्रोग्रेसिव एजिंग

लंबी बातचीत में संदेशों के कई टर्न जमा हो जाते हैं, लेकिन पुराने टर्न कम
प्रासंगिक हो जाते हैं। `progressiveAging.ts` मॉड्यूल **टर्न दूरी के अनुसार संदेशों को डिग्रेड करता है**
(दूरी को बातचीत के अंत से मापा जाता है)। जारी किए गए डिफ़ॉल्ट
(`verbatim: 2, light: 2, moderate: 3`) के साथ:

- **अंतिम 2 टर्न (दूरी ≤ 2)**: ज्यों-का-त्यों रखे जाते हैं
- **दूरी 3**: केवमैन संपीड़न (अनावश्यक शब्द हटाना)
- **दूरी 4+**: सहायक संदेशों का सारांश बनाया जाता है; उपयोगकर्ता संदेशों को उनकी पहली
  पंक्ति तक सीमित किया जाता है, जिसकी अधिकतम सीमा 120 वर्ण है; अन्य भूमिकाएँ अपरिवर्तित रहती हैं। सिस्टम प्रॉम्प्ट, पहले से पुराने किए गए
  संदेश और नवीनतम उपयोगकर्ता संदेश को दूरी की परवाह किए बिना हमेशा ज्यों-का-त्यों रखा जाता है।
  कुछ भी पूरी तरह हटाया नहीं जाता, और उपलब्ध डिफ़ॉल्ट के साथ `light`
  बैंड तक पहुँचना संभव नहीं है (`light`, `verbatim` के बराबर है)।

#### कोड उदाहरण

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 और टर्न ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // अंतिम 3 टर्न: ज्यों-के-त्यों
  light: 8, // दूरी <= 8: हल्का संपीड़न
  moderate: 20, // दूरी <= 20: केवमैन संपीड़न
  fullSummary: 5, // प्रकार के लिए आवश्यक, बैंडिंग कोड द्वारा नहीं पढ़ा जाता
  // दूरी > 20: सारांशित (सहायक) / पहली पंक्ति रखी जाती है (उपयोगकर्ता)
});

// saved = बचाए गए टोकन की संख्या
```

#### कब उपयोग करें

`aggressive` मोड के लिए प्रगतिशील एजिंग **हमेशा चालू** रहती है — यह
`compressAggressive()` का चरण 2 है। Ultra मोड इसे नहीं चलाता। यह
इनके लिए विशेष रूप से प्रभावी है:

- लंबे समय तक चलने वाले कोडिंग सत्र
- कई दिनों तक चलने वाली बातचीत
- कई टूल कॉल वाले एजेंटिक वर्कफ़्लो

### केवमैन आउटपुट मोड

केवमैन आउटपुट मोड ऐसे **सिस्टम प्रॉम्प्ट निर्देश** जोड़ता है जो मॉडल से ही
संक्षिप्त आउटपुट देने के लिए कहते हैं — `lite` स्तर पूर्ण वाक्यों को बनाए रखते हुए संक्षिप्त उत्तर माँगता है, `full`
उसे "स्मार्ट केवमैन की तरह संक्षिप्त उत्तर देने" के लिए कहता है, और `ultra` टेलीग्राफिक आउटपुट माँगता है;
निर्देश केवल अनुरोध कर सकते हैं, इसकी गारंटी नहीं दे सकते। अनुरोध इन्हें
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) के माध्यम से प्राप्त करते हैं:
`open-sse/handlers/chatCore.ts` पहले बैक-कम्पैट शिम के साथ चयन को निर्धारित करता है
(`open-sse/services/compression/outputStyles/backCompat.ts` में
`resolveOutputStyleSelection()`), जो `outputStyles`
के खाली होने पर सक्षम `cavemanOutputMode` को
`cavemanOutputMode.intensity` पर `terse-prose` आउटपुट शैली में मैप करता है (नीचे बैक-कम्पैट देखें); गैर-रिक्त `outputStyles`
चयन को उसी रूप में उपयोग किया जाता है, और इसके बाद `cavemanOutputMode.enabled` तथा `intensity` का कोई
प्रभाव नहीं पड़ता, जबकि इसका `autoClarity` टॉगल फिर भी लागू होता है। `outputMode.ts` में
निर्देश टेक्स्ट (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), सामग्री बायपास और
इंजेक्शन द्वारा उपयोग किया जाने वाला प्लेसमेंट सहायक मौजूद है; इसके अपने `applyCavemanOutputMode()` इंजेक्टर का कोई
प्रोडक्शन कॉलर नहीं है।

#### यह कैसे काम करता है

यह मोड इनपुट को संपीड़ित नहीं करता। यह सिस्टम प्रॉम्प्ट में एक निर्देश ब्लॉक जोड़ता है
(नीचे इंजेक्शन कैसे काम करता है देखें), और अनुरोध के लिए चुना गया कोई भी इनपुट संपीड़न मोड
इसके बाद भी उस बॉडी पर चलता है जिसमें अब यह ब्लॉक मौजूद है। प्रत्येक स्तर के अंत में आने वाले साझा
सीमा क्लॉज़ से पहले, अंग्रेज़ी `full` स्तर में यह लिखा है:

> "स्मार्ट केवमैन की तरह संक्षिप्त उत्तर दें। आर्टिकल (a/an/the), अनावश्यक शब्द (just/really/basically/actually/simply), शिष्टाचार और अनिश्चितता दर्शाने वाले शब्द हटाएँ। वाक्यांश स्वीकार्य हैं। छोटे पर्यायवाची शब्द उपयोग करें (extensive के बजाय big, implement के बजाय fix)। सभी तकनीकी तथ्य, कोड, त्रुटियाँ, URLs और पहचानकर्ता हूबहू रखें।"

यह इनके लिए विशेष रूप से अच्छा काम करता है:

- कोड जनरेशन (अधिक संक्षिप्त आउटपुट = कम टोकन)
- त्वरित प्रश्नोत्तर (विस्तृत व्याख्याओं की आवश्यकता नहीं)
- बैच प्रोसेसिंग (थ्रूपुट अधिकतम करना)

#### कब उपयोग करें

केवमैन आउटपुट मोड **ऑप्ट-इन** है। संपीड़न चालू होने पर (`enabled: true`, Compression Settings पृष्ठ पर मास्टर टॉगल),
इसे `cavemanOutputMode.enabled` से चालू करें; `intensity`
`lite`, `full` या `ultra` चुनता है:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

संपीड़न कॉम्बो का **Output Mode** टॉगल (`outputMode`, `outputModeIntensity` में स्तर)
उन अनुरोधों के लिए वही स्विच सेट करता है जिन पर वह कॉम्बो लागू होता है, और
`omniroute_set_compression_engine` MCP टूल इसे अपने बूलियन `outputMode`
आर्ग्युमेंट के माध्यम से लिखता है। गैर-रिक्त `outputStyles` चयन इस स्विच पर प्राथमिकता लेता है। डैशबोर्ड में,
**Terse prose** आउटपुट शैली को सक्षम करने पर वही ब्लॉक इंजेक्ट होता है (नीचे Output
Styles देखें)।

### आउटपुट शैलियाँ (कैटलॉग)

ऊपर दिया गया केवमैन आउटपुट मोड **पुराना एकल-शैली पथ** है। चरण 4 ने इसे
संयोज्य आउटपुट शैलियों के एक कैटलॉग में सामान्यीकृत किया: `open-sse/services/compression/outputStyles/catalog.ts`
में `OUTPUT_STYLE_CATALOG`। प्रत्येक शैली एक सिस्टम-प्रॉम्प्ट
निर्देश है जो मॉडल से ही कम लागत वाला आउटपुट माँगता है; शैलियों को एक साथ सक्षम
किया जा सकता है और उन्हें कैटलॉग क्रम में इंजेक्ट किया जाता है।

| शैली                         | `id`          | यह क्या करती है                                                                                                                                                                                                 | निर्देश की भाषाएँ                             |
| ---------------------------- | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| संक्षिप्त गद्य               | `terse-prose` | अनावश्यक शब्द/उपपद/अनिश्चितता हटाएँ; तकनीकी सार को सटीक रखें। पुराने caveman आउटपुट मोड के समान टेक्स्ट (संदर्भित, दोबारा टाइप नहीं किया गया)।                                                                  | en, pt-BR, es, de, fr, it, ru, zh, ja, id, vi |

हर शैली तीन तीव्रता स्तरों — `lite`, `full`, `ultra` — के साथ आती है, और हर स्तर
साझा सीमा खंड (`outputMode.ts` में `SHARED_BOUNDARIES`) पर समाप्त होता है, जो
कोड ब्लॉक, फ़ाइल पथ, कमांड, त्रुटियाँ और URLs को यथावत रखता है। `terse-prose` और
`terse-cjk` स्तरों के टेक्स्ट उस सूची में पहचानकर्ता भी जोड़ते हैं।

`terse-cjk` दो स्थानों पर लोकेल द्वारा `zh` तक सीमित है। Compression Settings पृष्ठ
इसकी पंक्ति केवल तब सूचीबद्ध करता है जब डैशबोर्ड UI की भाषा चीनी (`zh-CN` या `zh-TW`) हो, और
`applyOutputStyles()` इसे केवल तब इंजेक्ट करता है जब अनुरोध की निर्धारित भाषा (नीचे भाषा
चयन देखें) `zh` हो। पंक्ति छिपाने से सहेजा गया `terse-cjk` चयन साफ़ नहीं होता:
सेटिंग्स API किसी भी शैली id को स्वीकार करता है, और पृष्ठ पर अन्य शैलियाँ सहेजने से यह बना रहता है। अनुरोध
के समय, `applyOutputStyles()` की भाषा जाँच ही एकमात्र लोकेल द्वार है।

#### इंजेक्शन कैसे काम करता है

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) चयन को
कैटलॉग के विरुद्ध निर्धारित करता है (अज्ञात ids और लोकेल से मेल न खाने वाली शैलियाँ
हटा दी जाती हैं, कभी त्रुटि नहीं होती; जिस चयन से कोई शैली निर्धारित नहीं होती, वह बॉडी को
अपरिवर्तित छोड़ देता है और `no_styles` के रूप में छोड़ दिया जाता है), चयनित निर्देशों को कैटलॉग
क्रम में जोड़ता है,
सीमा खंड को **एक बार** जोड़ता है (साथ ही सुरक्षा खंड, `SAFETY_BOUNDARIES` या उसका
अनुवाद, जब `less-code` या `ponytail` चयनित हो), और ब्लॉक को एक
एकल पुनरावृत्ति-सुरक्षा मार्कर (`[OmniRoute Output Styles]`) से शुरू करता है, इसलिए इसे दोबारा लागू करना निष्प्रभावी होता है। जब
निर्धारित भाषा (नीचे भाषा चयन देखें) का अनुवाद उपलब्ध होता है, तो अंग्रेज़ी के बजाय स्थानीयकृत
निर्देश इंजेक्ट किया जाता है।

गैर-रिक्त `messages` सरणी वाली बॉडी पर, पुनरावृत्ति-सुरक्षा जाँच
कंटेंट बायपास से पहले चलती है: जब `[OmniRoute Output Styles]` मार्कर पहले से शीर्ष-स्तरीय
`system` फ़ील्ड (एक स्ट्रिंग या कंटेंट-ब्लॉक सरणी) में या स्ट्रिंग
कंटेंट वाले सिस्टम संदेश में मौजूद हो, तो बॉडी को `already_applied` के रूप में अपरिवर्तित छोड़ दिया जाता है और कोई कीवर्ड जाँच नहीं चलती।
अन्यथा एक कंटेंट बायपास (`open-sse/services/compression/outputMode.ts` में
`shouldBypassCavemanOutputMode()`) अंतिम तीन
संदेशों के टेक्स्ट की जाँच करता है, चाहे उनकी भूमिका कुछ भी हो, और जब वह टेक्स्ट इसके सुरक्षा, अपरिवर्तनीय-कार्रवाई या स्पष्टीकरण कीवर्ड से मेल खाता है, या किसी
क्रम-संवेदी अनुक्रम से मेल खाता है, तो पूरे टर्न के लिए शैलियाँ छोड़ देता है: `first`, `then`, `after that`, `before`, `rollback` या
`backup`, जिसके बाद 240 वर्णों के भीतर `delete`, `drop`, `migrate`, `deploy` या
`release` आता हो। बायपास तब चलता है जब **Auto-Clarity Bypass** टॉगल
(`cavemanOutputMode.autoClarity`, डिफ़ॉल्ट रूप से चालू) चालू हो; टॉगल बंद करने से
कीवर्ड जाँच छोड़ दी जाती है।

जब बायपास टर्न को आगे बढ़ने देता है, तो `placeSystemInstruction()` (उसी फ़ाइल में), जो
कभी नया `messages[0]` नहीं बनाता, ब्लॉक को इनमें से मिलने वाले पहले स्थान पर रखता है:

1. स्ट्रिंग कंटेंट वाला आरंभिक सिस्टम संदेश: ब्लॉक उसके टेक्स्ट के बाद जोड़ा जाता है।
2. शीर्ष-स्तरीय `system` फ़ील्ड: ब्लॉक किसी स्ट्रिंग के टेक्स्ट के बाद जोड़ा जाता है, या
   कंटेंट-ब्लॉक सरणी में एक नए टेक्स्ट ब्लॉक के रूप में जोड़ा जाता है।
3. स्ट्रिंग कंटेंट वाला बाद का पहला सिस्टम संदेश: ब्लॉक उसके टेक्स्ट के बाद जोड़ा जाता है।
4. उपरोक्त में से कोई नहीं: ब्लॉक `messages` के अंत में एक नए सिस्टम संदेश में जाता है।

`messages` सरणी के बिना (या रिक्त सरणी वाली) बॉडी पर, कोई कंटेंट बायपास नहीं चलता और
शीर्ष-स्तरीय `system` फ़ील्ड पर विचार नहीं किया जाता। ब्लॉक को स्ट्रिंग
`instructions` फ़ील्ड के टेक्स्ट के बाद जोड़ा जाता है, जब तक कि उस फ़ील्ड में पहले से
`[OmniRoute Output Styles]` मार्कर न हो; ऐसी स्थिति में बॉडी को
`already_applied` के रूप में अपरिवर्तित छोड़ दिया जाता है। जब बॉडी में स्ट्रिंग `instructions` फ़ील्ड नहीं होती, लेकिन उसमें `input`
(एक स्ट्रिंग या सरणी) होता है, तो ब्लॉक `instructions` बन जाता है और उस फ़ील्ड में मौजूद किसी भी गैर-स्ट्रिंग मान को
प्रतिस्थापित कर देता है। ऐसी बॉडी जिसमें न तो स्ट्रिंग `instructions` फ़ील्ड हो, न ही स्ट्रिंग या सरणी
`input`, अपरिवर्तित छोड़ दी जाती है और `no_messages` के रूप में छोड़ दी जाती है।

#### सक्षम करने का तरीका

डैशबोर्ड में: **Compression Context → Compression Settings**
(`/dashboard/context/settings`), Output styles अनुभाग: प्रत्येक शैली के लिए एक पंक्ति, जिसमें on/off
टॉगल और स्तर चयनकर्ता होता है। शैलियाँ तब इंजेक्ट होती हैं, जब कंप्रेशन स्वयं चालू हो (पृष्ठ का
मास्टर टॉगल, `enabled`)। **Auto-Clarity Bypass** टॉगल **Caveman**
पृष्ठ (`/dashboard/context/caveman`) पर, उसके **Output Mode** कार्ड में है। प्रोग्रामेटिक रूप से,
कंप्रेशन कॉन्फ़िगरेशन चयन को इस रूप में सहेजता है:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

पिछड़ी संगतता: जब तक `outputStyles` खाली है, लेगेसी `cavemanOutputMode.enabled`
सेटिंग `cavemanOutputMode.intensity` पर `terse-prose` से मैप होती है। इसके बाद ब्लॉक
`[OmniRoute Output Styles]` मार्कर से शुरू होता है, जबकि लेगेसी `applyCavemanOutputMode()`
इंजेक्टर `[OmniRoute Caveman Output Mode]` लिखता था। मार्कर के नीचे, पाठ en, pt-BR, es, de, fr, it, ru, id और vi में
लेगेसी इंजेक्शन से मेल खाता है; ja और zh में सीमाओं वाले क्लॉज़ से पहले एक
अतिरिक्त स्पेस होता है। `terse-prose` का अनुवाद pt-BR, es, de,
fr, it, ru, zh, ja, id और vi में होता है, इसलिए जिस अनुरोध की निर्धारित भाषा `hu` है, उसे
अंग्रेज़ी पाठ मिलता है, जबकि लेगेसी इंजेक्टर उसके हंगेरियन पाठ का उपयोग करता था।

Output-style भाषा चयन (`outputStyles/apply.ts` में
`resolveOutputStyleLanguage()`): `languageConfig.enabled` चालू होने पर, `autoDetect` अनुरोध की
`messages` सरणी में पाठ वाले नवीनतम उपयोगकर्ता संदेश (स्ट्रिंग सामग्री, या
उसकी सामग्री के हिस्सों का `text`) का नमूना लेता है और उस पर Caveman इंजन का डिटेक्टर
(`detectCompressionLanguage()`) चलाता है। डिटेक्टर Han
वर्णों और बिना kana वाले पाठ के लिए `zh` लौटाता है; अन्यथा यह `it`, `pt-BR`, `es`, `de`,
`fr`, `ru`, `ja`, `hu` और `id` में से सबसे अधिक संकेत-मिलान वाली भाषा लौटाता है, और कोई मिलान न होने पर `en`
लौटाता है — जिस पाठ को यह वर्गीकृत नहीं कर सकता, उसे अंग्रेज़ी मिलती है, `defaultLanguage` कभी नहीं, और `vi` का
पता कभी नहीं लगाया जाता, भले ही शैलियों में `vi` पाठ शामिल हो। Responses API बॉडी अपने टर्न
`input` में रखती है, जिसका नमूना नहीं लिया जाता, इसलिए उसे `defaultLanguage`, फिर अंग्रेज़ी मिलती है।
जब `messages` में किसी उपयोगकर्ता संदेश में पाठ नहीं होता, या `autoDetect` बंद होता है, तब
`defaultLanguage` लागू होता है, फिर अंग्रेज़ी। `languageConfig.enabled` बंद होने पर भाषा अंग्रेज़ी होती है — जब तक कि
अनुरोध पर कोई कंप्रेशन कॉम्बो लागू न हो (अनुरोध के रूटिंग
कॉम्बो को असाइन किया गया कॉम्बो, या वह डिफ़ॉल्ट कंप्रेशन कॉम्बो जिस पर बिल्ट-इन स्टैक्ड
पाइपलाइन के लिए chatCore फ़ॉलबैक करता है): किसी कॉम्बो को लागू करने पर उस अनुरोध के लिए `languageConfig.enabled` चालू हो जाता है और
कॉम्बो के भाषा पैक से `defaultLanguage` सेट होता है (यदि सहेजा गया मान कॉम्बो के पैक में से एक है
तो वही, अन्यथा कॉम्बो का पहला पैक, जो डिफ़ॉल्ट रूप से `en` होता है), जबकि
सहेजा गया `autoDetect` (डिफ़ॉल्ट रूप से चालू) फिर भी लागू होता है। Caveman इनपुट इंजन अपनी
रूल-पैक भाषा अलग तरीके से चुनता है — प्रत्येक पाठ भाग के अनुसार और, auto-detect बंद होने पर,
`enabledPacks` पर निर्भर होकर।

शैली × भाषा मैट्रिक्स को
`tests/unit/compression/output-styles-i18n-matrix.test.ts` द्वारा निर्धारित किया गया है: प्रत्येक कैटलॉग शैली के लिए
परीक्षण के `BASELINE_LANGUAGES` में एक प्रविष्टि आवश्यक है; locale-gated न होने वाली शैली में
pt-BR अनुवाद होना चाहिए (locale-gated `terse-cjk` को इस नियम से छूट है), जब तक कि वह
`KNOWN_ENGLISH_ONLY` में सूचीबद्ध न हो, जिसमें केवल ऐसी शैलियाँ हो सकती हैं जिनका कोई अनुवाद नहीं है —
यदि किसी सूचीबद्ध शैली का कोई भी अनुवाद है, तो परीक्षण विफल हो जाता है; और यदि कोई शैली ऐसी भाषा खो देती है
जो उसकी `BASELINE_LANGUAGES` प्रविष्टि में सूचीबद्ध है, तो वह परीक्षण में विफल हो जाती है। शैली जोड़ने के लिए,
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) देखें।

### टूल परिणाम कंप्रेशन

`open-sse/services/compression/toolResultCompressor.ts` में `compressToolResult()`
टूल-परिणाम पाठ को **5 रणनीतियों** से कंप्रेस करता है। यह उन्हें इसी क्रम में आज़माता है, और
पहली सक्षम रणनीति, जिसकी जाँच सामग्री से मेल खाती है, परिणाम निर्धारित करती है:

1. **`fileContent`**: 3 या अधिक पंक्तियों वाली सामग्री, जिसमें कम-से-कम एक पंक्ति, आरंभिक
   इंडेंटेशन को अनदेखा करने पर, `import `, `export `, `function `, `class `,
   `const `, `let `, `var ` या `return ` (कीवर्ड और उसके बाद एक स्पेस) से, अथवा `if`,
   `for` या `while` के बाद `(` या ` (` से शुरू होती है, उसकी पहली 20 और अंतिम 5 पंक्तियाँ
   रखी जाती हैं और हटाए गए मध्य भाग को चिह्नित किया जाता है।
2. **`grepSearch`**: ऐसी सामग्री जिसमें `<path>:<digits>:` स्वरूप की कम-से-कम एक पंक्ति हो,
   जहाँ पहले कोलन से पहले के टेक्स्ट में कोई व्हाइटस्पेस न हो, केवल उन्हीं पंक्तियों को रखती
   है, अधिकतम 30, और उनके बाद शेष मिलानों की संख्या तथा मिलान वाली फ़ाइलों की सूची देती है;
   प्रत्येक अन्य पंक्ति हटा दी जाती है। रणनीति को ट्रिगर करने के लिए ऐसी एक पंक्ति पर्याप्त
   है, इसलिए `12:30:45` जैसे टाइमस्टैम्प से शुरू होने वाली लॉग पंक्ति भी गिनी जाती है।
3. **`shellOutput`**: ऐसा आउटपुट जिसमें कोई ANSI CSI अनुक्रम (`ESC[` के बाद अंक या
   सेमीकोलन और फिर कोई अक्षर, जैसा कि रंग कोड में होता है) या टेक्स्ट में कहीं भी `$` के
   बाद व्हाइटस्पेस हो, उन अनुक्रमों को खो देता है (अन्य एस्केप, जैसे `ESC[?25l` या कोई
   OSC विंडो-शीर्षक अनुक्रम, रखे जाते हैं) और उसकी अंतिम 50 पंक्तियाँ रखी जाती हैं, जबकि
   लगातार दोहराई गई पंक्तियों को समेट दिया जाता है। चूँकि यह जाँच `json` और `errorMessage`
   से पहले चलती है, इसलिए ऐसा `$` रखने वाला JSON या त्रुटि आउटपुट, `shellOutput` चालू होने
   पर, उन तक कभी नहीं पहुँचता।
4. **`json`**: 2,000 से अधिक वर्णों वाला JSON पेलोड, जो वैकल्पिक व्हाइटस्पेस के बाद `{`
   या `[` से शुरू होता है और सफलतापूर्वक पार्स होता है, सारांशित किया जाता है: 7 से अधिक
   आइटम वाली सरणी के पहले 5 और अंतिम 2 आइटम तथा उसकी कुल संख्या रखी जाती है, और ऑब्जेक्ट
   की पहली 20 कुंजियाँ रखी जाती हैं, जहाँ प्रत्येक नेस्टेड ऑब्जेक्ट या सरणी मान को
   `{…N keys}` प्लेसहोल्डर से बदल दिया जाता है (किसी सरणी के लिए, N उसकी लंबाई है) और
   `_remaining_<N>_keys` मार्कर पहली 20 के बाद हटाई गई कुंजियों की संख्या बताता है।
   स्केलर मान पूरे कॉपी किए जाते हैं, इसलिए बिना नेस्टेड मानों वाला 20 या उससे कम कुंजियों
   का ऑब्जेक्ट केवल दोबारा इंडेंट किया जाता है — मिनिफ़ाई किए गए ऑब्जेक्ट में वर्ण बढ़ जाते
   हैं और वह अपरिवर्तित रहता है।
5. **`errorMessage`**: ऐसा आउटपुट जिसमें कहीं भी और किसी भी लेटर केस में `error:`,
   `error ` (शब्द के बाद एक स्पेस, जैसे `no error found` में), `[error]`,
   `exception:`, `exception `, `[exception]` या `traceback` हो, उसकी पहली पंक्ति,
   अगली 10 पंक्तियाँ और अंतिम 3 पंक्तियाँ रखी जाती हैं तथा उनके बीच की पंक्तियों की जगह
   `… [N frames elided] …` मार्कर लगाया जाता है। मार्कर केवल तभी दिखाई देता है जब पहली
   पंक्ति के बाद 13 से अधिक पंक्तियाँ हों, इसलिए 14 या उससे कम पंक्तियों वाला त्रुटि
   आउटपुट छोटा नहीं किया जाता (12 या 13 पंक्तियों पर अंतिम 3 पंक्तियाँ पहले से रखी गई
   पंक्तियों को दोहराती हैं)।

किसी रणनीति के मेल खाने के बाद, भले ही उससे कुछ भी बचत न हो, बाद की रणनीतियाँ नहीं
आजमाई जातीं। जब मेल खाने वाली रणनीति कोई अनुमानित टोकन नहीं बचाती (लंबाई ÷ 4, ऊपर की ओर
पूर्णांकित) — उदाहरण के लिए 25 या उससे कम पंक्तियों वाली कोड-जैसी फ़ाइल, या 2,000 से अधिक
वर्णों वाली ऐसी JSON सरणी जिसमें 7 या उससे कम आइटम हों — तब आक्रामक इंजन मूल टूल परिणाम
रखता है: दोनों कॉलर (`compressAggressive()` और `compressAnthropicToolResultBlock()`)
`saved` के 0 या उससे कम होने पर मूल सामग्री रखते हैं, जबकि `compressToolResult()` स्वयं
अब भी उस रणनीति का आउटपुट लौटाता है। टूल-परिणाम चरण अंतिम निर्णय नहीं है: इंजन का
फ़ॉलबैक सारांशकर्ता अब भी 8,192 वर्णों से लंबे `tool` या `function` संदेश को छोटा कर
सकता है (`maxTokensPerMessage`, 2,048, गुणा 4)।

#### कब उपयोग करें

टूल परिणाम संपीड़न आक्रामक इंजन का चरण 1 है (`compressAggressive()` में
`open-sse/services/compression/aggressive.ts`), इसलिए यह Aggressive मोड में और स्टैक्ड
पाइपलाइन के किसी `aggressive` चरण में चलता है। यह OpenAI-आकार वाले `tool` और `function`
संदेशों तथा Anthropic के `tool_result` ब्लॉक के भीतर के टेक्स्ट को संपीड़ित करता है।
प्रत्येक रणनीति का `aggressive.toolStrategies` के अंतर्गत अपना स्विच है और सभी डिफ़ॉल्ट
रूप से चालू होते हैं। डैशबोर्ड में, संपीड़न चालू होने और डिफ़ॉल्ट मोड Aggressive होने पर
ये स्विच Caveman पृष्ठ के **Advanced** दृश्य में होते हैं।

### स्टैक्ड पाइपलाइन

स्टैक्ड मोड **कई इंजनों को क्रम में** चलाता है — आम तौर पर पहले RTK
(टूल आउटपुट पर 60-90% बचत), फिर शेष टेक्स्ट पर Caveman (~46% इनपुट
बचत)। संयुक्त रूप से, यह **78-95% पात्र सीमा** है (ऊपर Upstream Savings Math
देखें): `1 - (1 - 0.60..0.90) × (1 - 0.46)` का औसत ≈89% है।

#### यह कैसे काम करता है

```
इनपुट (1000 टोकन)
  → RTK (कमांड-जागरूक फ़िल्टर) → 200 टोकन
    → Caveman (अनावश्यक सामग्री हटाना) → 108 टोकन
  → आउटपुट (108 टोकन, ~89% बचत)
```

#### कब उपयोग करें

स्टैक्ड मोड का उपयोग इनके लिए करें:

- टूल-प्रधान वर्कफ़्लो (एजेंटिक कोडिंग, शोध)
- लागत-संवेदनशील बैच प्रोसेसिंग
- जब आपको अधिकतम टोकन बचत चाहिए

स्टैक्ड पाइपलाइन को वैश्विक `stackedPipeline` संपीड़न सेटिंग के माध्यम से, या किसी
रूटिंग कॉम्बो को असाइन किए गए नामित संपीड़न कॉम्बो के माध्यम से कॉन्फ़िगर किया जाता है
(ऊपर Per-Combo Override देखें) — किसी ऑटो-कॉम्बो `modePack` के माध्यम से नहीं (वह फ़ील्ड
केवल ऑटो-कॉम्बो मॉडल चयन के भार को दोबारा समायोजित करता है और `stacked` कोई मान्य पैक
नाम नहीं है)।

## कंप्रेशन कॉम्बो ओवरराइड

अलग-अलग उपयोग मामलों के लिए व्यवहार को बेहतर ढंग से समायोजित करने हेतु, आप वैश्विक कंप्रेशन मोड को **प्रत्येक कॉम्बो के लिए** ओवरराइड कर सकते हैं:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

यह इनके लिए उपयोगी है:

- **कोडिंग कॉम्बो**: लंबे सत्रों के लिए `aggressive` मोड का उपयोग करें
- **त्वरित प्रश्नोत्तर कॉम्बो**: तेज़ प्रतिक्रियाओं के लिए `lite` मोड का उपयोग करें
- **अधिक टूल वाले कॉम्बो**: अधिकतम बचत के लिए `stacked` मोड का उपयोग करें
- **प्रोडक्शन कॉम्बो**: कैशिंग प्रदाताओं के लिए ओवरराइड बंद रखें — हमेशा सक्रिय
  कैश-जागरूक समायोजन `aggressive`/`ultra` को स्वचालित रूप से `standard` में डाउनग्रेड कर देता है
  (चयन योग्य `cache-aware` मोड उपलब्ध नहीं है)
