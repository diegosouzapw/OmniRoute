`open-sse/config/providerPluginManifest.ts` JSON-सुरक्षित प्रोवाइडर
प्लगइन कॉन्ट्रैक्ट को परिभाषित करता है। `open-sse/config/providerPluginManifestRegistry.ts` उस
कॉन्ट्रैक्ट को Bifrost, CLIProxyAPI, या भविष्य के किसी Go/Rust राउटर जैसे साइडकारों के लिए
वर्तमान प्रोवाइडर रजिस्ट्री से जोड़ता है। TypeScript रजिस्ट्री सत्य का
स्रोत बनी रहती है, लेकिन साइडकार executor कोड, OAuth डिफ़ॉल्ट, हेडर, या प्रोसेस
एनवायरनमेंट स्टेट को इंपोर्ट किए बिना मैनिफ़ेस्ट का उपयोग कर सकते हैं।

यही मैनिफ़ेस्ट HTTP पर
`GET /api/v1/provider-plugin-manifest` के माध्यम से उन साइडकारों के लिए उपलब्ध है जो आउट-ऑफ़-प्रोसेस चलते हैं।

OmniRoute उस URL को Bifrost और CLIProxyAPI के समक्ष
`X-OmniRoute-Provider-Manifest-Url` अनुरोध हेडर के माध्यम से विज्ञापित करता है। जब साइडकार को स्थानीय अनुरोध
ओरिजिन के बजाय किसी सार्वजनिक या कंटेनर नेटवर्क URL की आवश्यकता हो, तो
`OMNIROUTE_PROVIDER_MANIFEST_URL` सेट करें।

## मैनिफ़ेस्ट रीफ़्रेश करना

HTTP एंडपॉइंट `Cache-Control: public, max-age=60` और एक स्ट्रॉन्ग
`ETag` लौटाता है। साइडकार को अंतिम सत्यापित मैनिफ़ेस्ट बनाए रखना चाहिए और रीफ़्रेश करते समय उसका ETag
`If-None-Match` में भेजना चाहिए। `304 Not Modified` प्रतिक्रिया में कोई बॉडी नहीं होती;
साइडकार अपने कैश किए गए मैनिफ़ेस्ट को बनाए रखता है। यदि कोई सत्यापित कैश किया हुआ मैनिफ़ेस्ट मौजूद नहीं है,
तो साइडकार को `304` स्वीकार करने के बजाय एक बिना शर्त अनुरोध करना चाहिए।

## लक्ष्य

प्रोवाइडर मेटाडेटा को प्लगइन कॉन्ट्रैक्ट की ओर ले जाना, ताकि हॉट अनुरोध पथ का
स्वामित्व अंततः कम लेटेंसी वाले साइडकार के पास हो सके, जबकि OmniRoute
TypeScript रूट को पॉलिसी गेट और फ़ॉलबैक के रूप में बनाए रखे। मैनिफ़ेस्ट एडिटिव है: यह
स्वयं अनुरोध रूटिंग को नहीं बदलता।

## कॉन्ट्रैक्ट

मैनिफ़ेस्ट में शामिल हैं:

- प्रोवाइडर id और एलियस
- अपस्ट्रीम फ़ॉर्मेट और executor नाम
- प्रमाणीकरण प्रकार, प्रमाणीकरण हेडर, और वैकल्पिक प्रमाणीकरण प्रीफ़िक्स
- स्थिर एंडपॉइंट मेटाडेटा
- साइडकार पात्रता और जब किसी प्रोवाइडर को TS पर बने रहना चाहिए, तब उसके स्पष्ट कारण
- JSON-सुरक्षित मॉडल मेटाडेटा, जैसे कॉन्टेक्स्ट लंबाई, विज़न/रीज़निंग फ़्लैग, और
  असमर्थित पैरामीटर
- `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch`, और `usage-supported` सहित क्षमता टैग

मैनिफ़ेस्ट जानबूझकर निम्नलिखित को शामिल नहीं करता:

- OAuth क्लाइंट सीक्रेट और डिफ़ॉल्ट सीक्रेट मान
- रनटाइम एनवायरनमेंट रिज़ॉल्यूशन
- अनुरोध हेडर और सार्वजनिक क्रेडेंशियल हेल्पर
- डायनेमिक URL बिल्डर
- executor फ़ंक्शन
- सेशन पूल की आंतरिक जानकारी

## क्षमता टैग

`capabilities` रजिस्ट्री एंट्री से प्राप्त टैगों की एक क्रमबद्ध ऐरे है। इंटीग्रेटरों को
TypeScript स्रोतों को दोबारा पढ़ने के बजाय इसे "यह प्रोवाइडर क्या कर सकता है" के मशीन-पठनीय उत्तर के रूप में
मानना चाहिए।

| टैग                  | अर्थ                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------ |
| `apikey`             | API कुंजी स्वीकार करता है (`authType`, `apikey` या `optional` है)।                         |
| `oauth`              | OAuth या सेशन फ़्लो का उपयोग करता है।                                                      |
| `responses`          | OpenAI Responses-API बेस URL उपलब्ध कराता है।                                              |
| `passthrough-models` | स्थिर कैटलॉग के बजाय सीधे अपस्ट्रीम से मॉडल प्रदान करता है।                                |
| `custom-executor`    | गैर-डिफ़ॉल्ट executor चलाता है, इसलिए यह TypeScript पथ पर रहता है।                         |
| `sidecar-candidate`  | `sidecar.eligible` को प्रतिबिंबित करता है — साइडकार इंपोर्ट के लिए विचार करना सुरक्षित है। |
| `usage-fetch`        | इसमें कॉन्फ़िगर किया हुआ उपयोग या कोटा फ़ेचर (`getUsageForProvider`) है।                   |
| `usage-supported`    | उपयोग API इस प्रोवाइडर को स्वीकार करता है (`isSupportedUsageConnection`)।                  |

`usage-fetch` केवल डिस्कवरी के लिए है। यह बताता है कि OmniRoute प्रोवाइडर का
उपयोग डेटा पढ़ना जानता है; यह फ़ेचिंग सक्रिय नहीं करता, कोटा सिमेंटिक्स नहीं बदलता, और न ही इसका अर्थ यह है कि
प्रोवाइडर के लिए Dashboard कोटा विजेट सक्षम है — उस विजेट को अलग से
`USAGE_SUPPORTED_PROVIDERS` द्वारा नियंत्रित किया जाता है। सत्य का स्रोत
`open-sse/services/usage/fetcherProviders.ts` में `USAGE_FETCHER_PROVIDERS` है।

वह सूची उपयोग डिस्पैचर द्वारा स्वीकार की जाने वाली स्ट्रिंग के आधार पर कुंजीबद्ध है, इसलिए उसमें कैनोनिकल id
और एलियस दोनों शामिल हैं तथा वह टैग किए गए प्रोवाइडरों की संख्या से थोड़ी लंबी है: जो एंट्रियाँ
मैनिफ़ेस्ट रजिस्ट्री में चैट प्रोवाइडर नहीं हैं (उदाहरण के लिए `firecrawl` सर्च प्रोवाइडर
और `amazon-q` ACP प्रोवाइडर), उनके पास टैग करने के लिए कोई मैनिफ़ेस्ट एंट्री नहीं है।

`usage-supported` बताता है कि सर्वर और Dashboard के उपयोग रूट प्रोवाइडर के लिए किसी कनेक्शन को
स्वीकार करते हैं या नहीं। यह `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
और `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`) को प्रतिबिंबित करता है, दोनों
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`) द्वारा नियंत्रित हैं।
`usage-fetch` के विपरीत, यह केवल प्रोवाइडर id पर उत्सर्जित होता है — रनटाइम गार्ड
बिना एलियस रिज़ॉल्यूशन के `USAGE_SUPPORTED_PROVIDERS.includes(providerId)` करता है, इसलिए मैनिफ़ेस्ट
उसी नियम को बनाए रखता है। दोनों टैग की सीमाएँ अलग-अलग हैं: 3 प्रोवाइडरों में केवल
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) है और 1 में केवल
`usage-supported` (`xiaomi-mimo-token-plan`) है, इसलिए एक का होना दूसरे को इंगित नहीं करता।

## साइडकार का उपयोग

साइडकार को `sidecar.eligible` को एक रूढ़िवादी संभावित संकेत के रूप में मानना चाहिए, न कि बिना शर्त रूटिंग निर्णय के रूप में। आयात का पहला लक्ष्य डिफ़ॉल्ट executor का उपयोग करने वाले API-key, static-endpoint providers होने चाहिए। custom web executors, OAuth/session flows, dynamic URL builders या pool config वाले providers तब तक TypeScript fallback path पर बने रहेंगे, जब तक कोई साइडकार समकक्ष व्यवहार लागू नहीं करता और telemetry समानता प्रमाणित नहीं करती।

सुझाए गए माइग्रेशन चरण:

1. TS registry से provider plugin manifest जनरेट और सत्यापित करें।
2. Bifrost या CLIProxyAPI को API-key/static providers के लिए manifest आयात करना सिखाएँ।
3. TS fallback को सक्षम रखते हुए `OMNIROUTE_RELAY_BACKEND` के पीछे साइडकार के माध्यम से योग्य providers को रूट करें।
4. providers को केवल तभी पदोन्नत करें, जब सफलता दर, p99 latency, streaming behavior और unsupported-param handling TS path से मेल खाते हों।
5. एक समय में एक provider family के custom executors के लिए sidecar-native plugins जोड़ें।

## Providers को सीधे Next में एम्बेड क्यों न करें

Next frontend को provider execution का स्वामित्व नहीं लेना चाहिए। इसे API boundary को कॉल करना चाहिए। इसके बाद backend यह तय कर सकता है कि TypeScript executor, Bifrost, CLIProxyAPI या भविष्य के किसी native sidecar का उपयोग करना है। इससे किसी भी sidecar handoff से पहले request signing, allowlist checks, DB policy और fallback behavior केंद्रीकृत रहते हैं।
