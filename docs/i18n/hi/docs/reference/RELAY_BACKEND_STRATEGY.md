## सारांश

OmniRoute अब `/api/v1/relay/chat/completions` के लिए तीन रिले मोड का समर्थन करता है:

- `ts`: TypeScript रिले का इन-प्रोसेस उपयोग करें।
- `bifrost`: Bifrost गेटवे का उपयोग अनिवार्य करें।
- `auto`: उपलब्ध होने पर Bifrost को प्राथमिकता दें और विफलता पर TypeScript पर वापस जाएँ।

जब आप उच्च अनुरोध दर (प्रतिदिन बड़ी संख्या में टोकन, लगभग निरंतर थ्रूपुट) पर चला रहे हों, तो सर्वोत्तम रणनीति फ़ॉलबैक पथ को स्पष्ट और तेज़ रखना है, ताकि हॉट पथ कभी भी निष्क्रिय साइडकार के कारण अवरुद्ध न हो।

## मोड का व्यवहार

- `ts`
  - न्यूनतम परिचालन जटिलता।
  - सभी रूटिंग और सत्यापन Node में चलते हैं।
  - उपलब्धता के लिए साइडकार पर कोई निर्भरता नहीं।
- `bifrost`
  - सभी अनुरोधों को साइडकार गेटवे के माध्यम से भेजना अनिवार्य करता है।
  - कोई स्वचालित फ़ॉलबैक नहीं।
  - केवल तब उपयोगी है, जब साइडकार की स्थिति और विलंबता की गारंटी हो।
- `auto`
  - साइडकार सक्षम और पहुँच योग्य होने पर उसका उपयोग किया जाता है।
  - विफल प्रयास फ़ॉलबैक हेडर ट्रिगर करते हैं और ट्रैफ़िक को TS पर वापस भेजते हैं, ताकि अनुरोध की सफलता सीमाबद्ध बनी रहे।
  - जब अपटाइम, केवल-साइडकार रूटिंग की कठोरता से अधिक महत्वपूर्ण हो, तब यह मोड प्रोडक्शन के लिए सबसे सुरक्षित विकल्प है।

## वर्तमान में 9router बनाम CLIPROXYAPI

9router और CLIPROXYAPI दोनों ऐसे एकीकरण हैं, जिन्होंने ऐतिहासिक रूप से अपस्ट्रीम प्रदाताओं के लिए संगतता पथ उपलब्ध कराए हैं।

- 9router अपस्ट्रीम ऑर्केस्ट्रेशन और संगतता व्यवहार के लिए एक एम्बेडेड पथ है।
- CLIPROXYAPI, CLI / SDK शैली के ट्रैफ़िक के लिए एक प्रॉक्सी API ब्रिज है।
- जब आपको एक समर्पित साइडकार-जैसे हॉप और कम-विलंबता वाला स्थानीय डिस्पैच चाहिए, तब Bifrost को बाहरीकृत पथ के रूप में स्थिर किया जा रहा है।

यदि आप वर्तमान में 9router/CLIPROXYAPI की तुलना कर रहे हैं:

- हैंडऑफ़ से पहले API रूट में अनुरोध हस्ताक्षर, अलाउलिस्ट जाँच और DB नीति गेट बनाए रखें।
- यदि किसी वर्कफ़्लो को कठोर साइडकार व्यवहार और प्रत्येक अनुरोध में कम भिन्नता चाहिए, तो `OMNIROUTE_RELAY_BACKEND=bifrost` का उपयोग करें।
- यदि आपको घटना की परिस्थितियों में सुचारु अवक्रमण के साथ साइडकार प्रत्यास्थता चाहिए, तो `OMNIROUTE_RELAY_BACKEND=auto` का उपयोग करें।

## बैकएंड सीमा अनुबंध

स्थिर उत्पाद सीमा OmniRoute रिले API है, डैशबोर्ड कार्यान्वयन नहीं। Next.js डैशबोर्ड स्थानीय सेवाओं को इंस्टॉल, कॉन्फ़िगर और पर्यवेक्षित कर सकता है, लेकिन अनुरोध रूटिंग को रिले API के माध्यम से प्रवेश करना चाहिए और उस सीमा के पीछे हैंडऑफ़ करना चाहिए।

दीर्घकालिक बैकएंड विकल्प:

- TypeScript रिले को इन-प्रोसेस नीति और फ़ॉलबैक पथ के रूप में बनाए रखें। किसी भी बैकएंड हैंडऑफ़ से पहले प्रमाणीकरण, अलाउलिस्ट, अनुरोध सामान्यीकरण, लेखांकन और सुरक्षा जाँच यहीं रहें।
- जब परिनियोजन को कम रूटिंग भिन्नता, केंद्रीकृत प्रदाता रोटेशन या कई OmniRoute प्रतिकृतियों में स्केल-आउट की आवश्यकता हो, तब Bifrost को पसंदीदा उच्च-थ्रूपुट Tier-1 साइडकार के रूप में उपयोग करें।
- 9router और CLIPROXYAPI को एम्बेडेड संगतता सेवाओं के रूप में बनाए रखें। वे पर्यवेक्षित स्थानीय प्रक्रियाओं के रूप में चलते हैं और तब उपयोगी होते हैं, जब उनका प्रदाता/CLI व्यवहार वांछित एडाप्टर हो, लेकिन उन्हें डिफ़ॉल्ट Tier-1 रूटिंग इंजन नहीं बनना चाहिए।
- डैशबोर्ड को हॉट पथ में मनमाने सेवा URL पास न करने दें। UI द्वारा दिए गए URL कॉन्फ़िगरेशन इनपुट हैं; रूटिंग कोड को सर्वर-साइड सेटिंग्स और सुपरवाइज़र स्थिति से पंजीकृत, स्वास्थ्य-जाँचे गए बैकएंड का समाधान करना चाहिए।
- वर्तमान में पर्यवेक्षित सेवाओं के लिए लूपबैक HTTP को प्राथमिकता दें, क्योंकि प्रबंधित प्रक्रियाएँ पहले से ही HTTP-संगत API उपलब्ध कराती हैं, रूट गार्ड सीमा का ऑडिट कर सकता है, और विफलता/फ़ॉलबैक व्यवहार अनुरोध लॉग में दिखाई देता है। भविष्य का SDK या सॉकेट ट्रांसपोर्ट केवल तभी जोड़ने योग्य है, जब वह पृथक्करण या फ़ॉलबैक सिमेंटिक्स को कमजोर किए बिना p99 रूटिंग विलंबता को मापने योग्य रूप से कम करे।

इसलिए अत्यंत उच्च-थ्रूपुट परिनियोजन के लिए डिफ़ॉल्ट उत्तर Bifrost सक्षम होने के साथ `auto` है: सफलता दर बनाए रखने के लिए TypeScript फ़ॉलबैक को सुरक्षित रखते हुए हॉट पथ पर Go साइडकार का उपयोग करें। `bifrost` का उपयोग केवल तभी करें, जब कठोर केवल-साइडकार व्यवहार, सुचारु अवक्रमण से अधिक महत्वपूर्ण हो।

## उच्च-थ्रूपुट मार्गदर्शन

निरंतर उच्च RPM/RPS और कठोर सफलता SLO के लिए:

1. व्यावहारिक कूलडाउन और विफलता टेलीमेट्री के साथ `auto` का उपयोग करें।
2. अपस्ट्रीम सत्यापन और API-कुंजी जाँच को TypeScript रूट सीमा पर रखें।
3. स्पष्ट हेडर/काउंटर सक्षम करें, ताकि आपकी चेतावनी प्रणाली फ़ॉलबैक की आवृत्ति और कारण देख सके।
4. साइडकार टाइमआउट को अनंत प्रतीक्षा के बजाय शीघ्र विफल होने के लिए ट्यून करें।
5. सेवा का स्वचालित पुनःआरंभ और स्वास्थ्य टेलीमेट्री लूप स्वस्थ रखें, ताकि फ़ॉलबैक वास्तव में अपवादस्वरूप ही हो।

## सुझाया गया आधारभूत कॉन्फ़िगरेशन

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- रूट हैंडलर में API कुंजियाँ, अलाउलिस्ट, सैनिटाइज़र और दर-सीमा जाँच सक्षम रखें (वे हमेशा डाउनस्ट्रीम फ़ॉरवर्डिंग से पहले चलती हैं)।
- अपने रिवर्स प्रॉक्सी और अनुरोध लॉग से फ़ॉलबैक मेट्रिक्स निर्यात करें, ताकि साइडकार आउटेज एक मिनट के भीतर दिखाई दें।
