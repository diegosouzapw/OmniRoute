OmniRoute को OpenAI-संगत बैकएंड के रूप में उपयोग करने के लिए Codex CLI की संपूर्ण मार्गदर्शिका।

---

> **TOML ही एकमात्र प्रभावी प्रारूप है।** आधुनिक Codex केवल `~/.codex/config.toml`
> को पढ़ता है (codex-cli 0.147.0 के साथ सत्यापित: `codex --help` में
> `-c/--config` ओवरराइड को "`~/.codex/config.toml` से लोड किया गया" बताया गया है)। पुरानी
> `~/.codex/config.yaml` लेगेसी npm CLI से संबंधित थी और उसे बिना किसी सूचना के अनदेखा कर दिया जाता है।
> डैशबोर्ड जनरेटर (`/api/cli-tools/apply`, टूल `codex`) एक
> सतर्क मर्ज के साथ TOML लिखता है — मौजूदा कुंजियाँ और अन्य प्रोवाइडर ब्लॉक सुरक्षित रहते हैं,
> API कुंजी `OMNIROUTE_API_KEY` में रहती है (फ़ाइल में कभी नहीं), और बची हुई लेगेसी
> `config.yaml` को बिना छुए माइग्रेशन नोट के रूप में रिपोर्ट किया जाता है।

## सीधे पेस्ट करने योग्य config.toml

`<YOUR_HOST>` और `<YOUR_KEY>` को अपने मानों से बदलें:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # प्रत्येक टूल कॉल के लिए इतिहास संग्रहण सीमा

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc या ~/.zshrc — वास्तविक कुंजी मान, config.toml में कभी नहीं
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT ऐप के भीतर बंडल किया गया Codex

यदि आपने ChatGPT डेस्कटॉप ऐप के माध्यम से Codex इंस्टॉल किया है, तो `codex` बाइनरी
केवल ऐप बंडल के भीतर मौजूद हो सकती है और अभी आपके शेल `PATH` में उपलब्ध नहीं हो सकती। अपने
शेल स्टार्टअप फ़ाइल में resources डायरेक्टरी जोड़ें:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

नया शेल खोलें, फिर सत्यापित करें:

```bash
command -v codex
codex --version
```

### स्थानीय अप्रमाणित OmniRoute: प्लेसहोल्डर कुंजी पर्याप्त है

Codex यह सत्यापित करता है कि `env_key` द्वारा नामित पर्यावरण चर
CLI से पहला अनुरोध बाहर जाने के **पहले** मौजूद है। यदि आपके **स्थानीय** OmniRoute
इंस्टेंस को प्रमाणीकरण की आवश्यकता नहीं है, तो कोई भी गैर-रिक्त प्लेसहोल्डर काम करेगा:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

यदि आपका OmniRoute सर्वर सुरक्षित या रिमोट है, तो इसके बजाय वास्तविक कुंजी का उपयोग करें।

> **सामान्य होस्ट विकल्प**
>
> | पहुँच           | URL                           |
> | --------------- | ----------------------------- |
> | स्थानीय नेटवर्क | `http://192.168.0.1:20128/v1` |
> | Tailscale       | `http://100.x.x.x:20128/v1`   |
> | लूपबैक          | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — यह सभी मॉडलों के लिए क्यों काम करता है

Codex CLI ने फ़रवरी 2026 में `wire_api = "chat"` (Chat Completions) को बहिष्कृत कर दिया और अब `wire_api = "responses"` (OpenAI Responses API) की **आवश्यकता** है। `wire_api = "chat"` सेट करने से v0.138 के बाद तुरंत स्टार्टअप क्रैश होता है।

GLM और Kimi सहित कई प्रोवाइडर अभी भी केवल Chat Completions एंडपॉइंट उपलब्ध कराते हैं। DeepSeek V4 अब Anthropic-संगत एंडपॉइंट के साथ-साथ एक नेटिव Responses API भी उपलब्ध कराता है; OmniRoute डिफ़ॉल्ट रूप से Responses का उपयोग करता है और प्रत्येक DeepSeek कनेक्शन को Anthropic संगतता चुनने देता है।

**OmniRoute इसे पारदर्शी ढंग से हल करता है:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute प्रोवाइडर के नेटिव प्रोटोकॉल का चयन करता है और आवश्यकता होने पर अनुवाद करता है
    → POST /responses (DeepSeek V4) या /chat/completions (Mistral / GLM / Kimi / अन्य)
```

OmniRoute का उपयोग करते समय आपको कभी भी अलग अनुवाद प्रॉक्सी की आवश्यकता नहीं होती। **सभी मॉडल `wire_api = "responses"` का उपयोग करते हैं** — बाकी सब OmniRoute संभालता है।

> **`wire_api` डिफ़ॉल्ट है** — फ़ील्ड का डिफ़ॉल्ट मान `"responses"` है और इसे `config.toml` से पूरी तरह छोड़ा जा सकता है। इसे स्पष्ट रूप से केवल तभी सेट करें, जब आप उद्देश्य का दस्तावेज़ीकरण कर रहे हों।

## कॉन्टेक्स्ट विंडो और कॉम्पैक्शन

### टोकन कॉन्फ़िगरेशन फ़ील्ड

| फ़ील्ड                           | विवरण                                                                                                                                                                                                 |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | सक्रिय मॉडल के लिए कुल टोकन बजट। इसे मॉडल की घोषित सीमा पर सेट करें।                                                                                                                                  |
| `model_auto_compact_token_limit` | वह थ्रेशोल्ड जो स्वचालित हिस्ट्री कॉम्पैक्शन को ट्रिगर करता है। **अधिकतम: `model_context_window` का 90%** — 90% से अधिक मानों को बिना सूचना के अनदेखा कर दिया जाता है।                                |
| `tool_output_token_limit`        | हिस्ट्री में प्रति टूल कॉल आउटपुट संग्रहीत किए जाने वाले टोकनों की सीमा। यह किसी एक बड़े टूल रिस्पॉन्स को पूरी विंडो भरने से रोकता है। **यह अधिकतम आउटपुट नहीं है** — यह हिस्ट्री स्टोरेज की सीमा है। |
| `compact_prompt`                 | कॉम्पैक्शन के दौरान उपयोग किए जाने वाले सिस्टम प्रॉम्प्ट के लिए इनलाइन ओवरराइड (v0.138+)।                                                                                                             |

> **`model_max_output_tokens` पर टिप्पणी**: यह फ़ील्ड **Codex CLI कॉन्फ़िग स्कीमा का भाग नहीं है** (Codex Rust कोडबेस में अनुपस्थित)। सेट किए जाने पर इसे बिना सूचना के अनदेखा कर दिया जाता है। इस पर निर्भर न रहें — हिस्ट्री में कितना टूल आउटपुट संग्रहीत हो, इसे नियंत्रित करने के लिए `tool_output_token_limit` का उपयोग करें।

## रीजनिंग प्रयास

यह नियंत्रित करता है कि प्रतिक्रिया देने से पहले मॉडल कितना "सोचता" है।

| मान      | इसके लिए उपयोग करें                      |
| -------- | ---------------------------------------- |
| `none`   | कोई रीजनिंग नहीं — सीधे प्रतिक्रिया      |
| `low`    | साधारण कार्य (नाम बदलना, फ़ॉर्मैट करना)  |
| `medium` | निर्दिष्ट न होने पर **सर्वर डिफ़ॉल्ट**   |
| `high`   | मध्यवर्ती कार्य (रीफ़ैक्टरिंग, डीबगिंग)  |
| `xhigh`  | आर्किटेक्चर, गहन विश्लेषण, जटिल समस्याएँ |

```bash
# प्रत्येक आह्वान के लिए ओवरराइड
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

रीजनिंग **सारांश** भी सेट करें, ताकि Desktop सोच संबंधी टेक्स्ट रेंडर कर सके (केवल एन्क्रिप्टेड ब्लॉब नहीं):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # या समर्थित होने पर ultra
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute थिंकिंग बजट (सर्वर सेटिंग)

OmniRoute होस्ट पर, Codex प्रयास/सारांश को अपस्ट्रीम तक पहुँचाने के लिए **Settings → AI → Thinking Budget** को **`passthrough`** पर सेट करना आवश्यक है। **`auto` मोड** क्लाइंट के सभी `reasoning` / `reasoning_effort` फ़ील्ड हटा देता है और Codex सही ढंग से कॉन्फ़िगर होने पर भी थिंकिंग पैनल खाली कर देगा।

पूरी गाइड: [THINKING_BUDGET.md](./THINKING_BUDGET.md)।

कंप्रेशन और प्रॉम्प्ट कैश स्वतंत्र हैं और `passthrough` के अंतर्गत काम करते रहते हैं।

## प्रोफ़ाइल — प्रत्येक मॉडल/वर्कफ़्लो के लिए नामित कॉन्फ़िगरेशन

प्रोफ़ाइल आपको एक ही फ़्लैग से मॉडल + कॉन्टेक्स्ट विंडो बदलने देते हैं। प्रत्येक प्रोफ़ाइल एक सपाट
`~/.codex/<name>.config.toml` फ़ाइल है, जो आधारभूत `config.toml` के ऊपर ओवरले होती है।

> **नामकरण नियम (Codex CLI v0.137+):** फ़ाइल `~/.codex/<name>.config.toml` ही होनी चाहिए — **`profile-` प्रीफ़िक्स नहीं होना चाहिए**।
> CLI `-p kimi-k27` को → `~/.codex/kimi-k27.config.toml` के रूप में रिज़ॉल्व करता है। यदि फ़ाइल नहीं मिलती, तो डिफ़ॉल्ट बिना किसी सूचना के लागू हो जाता है।

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # तेज़, सस्ता
```

## `omniroute setup-codex` के साथ प्रोफ़ाइल अपने-आप जनरेट करना

यदि आप OmniRoute को किसी VPS पर चलाते हैं, तो आप लाइव मॉडल कैटलॉग से प्रोफ़ाइल फ़ाइलें अपने-आप जनरेट कर सकते हैं:

```bash
# किसी VPS से (पोर्ट 20128 पर स्थानीय OmniRoute का उपयोग करता है)
omniroute setup-codex

# किसी भी मशीन से — अपने VPS को निर्दिष्ट करें
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# फ़ाइलें लिखे बिना पूर्वावलोकन करें
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# केवल GLM और Kimi प्रोफ़ाइल जनरेट करें
omniroute setup-codex --only glm,kimi

# किसी कस्टम डायरेक्टरी में लिखें
omniroute setup-codex --codex-home /path/to/.codex
```

यह कमांड `/v1/models` को फ़ेच करता है, ज्ञात मॉडलों के लिए ट्यून की गई प्रोफ़ाइल का उपयोग करता है, अन्य संगत टेक्स्ट मॉडलों के लिए कैटलॉग मेटाडेटा पर फ़ॉलबैक करता है और प्रत्येक के लिए `~/.codex/<name>.config.toml` लिखता है। यह आइडेम्पोटेंट है — इसे दोबारा चलाना सुरक्षित है।

सफल प्रोवाइडर मॉडल डिस्कवरी/इम्पोर्ट द्वारा लाइव कैटलॉग में बदलाव किए जाने के बाद OmniRoute इन्हीं प्रोफ़ाइल फ़ाइलों को **अपने-आप सिंक** भी कर सकता है। यह **वैकल्पिक है और डिफ़ॉल्ट रूप से बंद रहता है**: इसे **CLI Code डैशबोर्ड** ("CLI profile auto-sync" → Codex) से चालू करें, या `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` सेट करें (यह `CLI_ALLOW_CONFIG_WRITES` का भी पालन करता है, जो डिफ़ॉल्ट रूप से चालू रहता है)। सक्षम होने पर यह केवल अलग-अलग `~/.codex/*.config.toml` प्रोफ़ाइल फ़ाइलें लिखता है; यह सक्रिय/डिफ़ॉल्ट `~/.codex/config.toml`, Codex-lb सेटिंग्स, प्रमाणीकरण या प्रोवाइडर चयन को कभी नहीं बदलता।

## `omniroute launch-codex` के साथ Codex लॉन्च करना

Codex लॉन्च करने से पहले आपके OmniRoute इंस्टेंस की स्वास्थ्य-जाँच करता है:

```bash
# स्थानीय OmniRoute के विरुद्ध लॉन्च करें (डिफ़ॉल्ट पोर्ट 20128)
omniroute launch-codex

# किसी विशिष्ट प्रोफ़ाइल के साथ लॉन्च करें
omniroute launch-codex --profile kimi-k27

# किसी रिमोट VPS के विरुद्ध लॉन्च करें
omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# codex को अतिरिक्त आर्ग्युमेंट पास करें
omniroute launch-codex --profile glm52 -- --yolo "fix this bug"
```

Codex दो सामान्य मैनिफ़ेस्ट-संचालित एंट्री पॉइंट्स का भी एक लक्ष्य है
(`bin/cli/cli-manifest.mjs`):

```bash
# इंटरैक्टिव मॉडल पिकर → ~/.codex/<name>.config.toml लिखता है (TOML, env_key)
omniroute configure codex

# -c फ़्लैग के माध्यम से omniroute प्रोवाइडर इंजेक्ट करके codex लॉन्च करें (कोई कॉन्फ़िगरेशन नहीं लिखा जाता)
omniroute run codex
```

## लंबे समय तक चलने वाले कार्य

OmniRoute के दो डिफ़ॉल्ट कई घंटों तक चलने वाले Codex CLI सत्रों को बिना किसी स्पष्ट संकेत के बाधित कर सकते हैं। इनमें से कोई भी Codex CLI सेटिंग नहीं है — दोनों OmniRoute की ओर स्थित हैं। ऐसे अपस्ट्रीम प्रॉक्सी से कॉन्फ़िगरेशन माइग्रेट करने वाले उपयोगकर्ता, जो अकाउंट को पिन करते हैं और निष्क्रियता कटऑफ़ अक्षम रखते हैं, अक्सर दोनों समस्याओं का सामना करते हैं और निष्कर्ष निकालते हैं कि OmniRoute “लंबे सत्र को बनाए नहीं रख सकता।”

| लक्षण                                                                           | संभावित कारण                                                                  | नियंत्रण                 |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------ |
| सत्र बार-बार अकाउंट बदलता है / टर्न के बीच प्रॉम्प्ट-कैश निरंतरता खो जाती है    | सत्र एफ़िनिटी TTL `0` (अक्षम) है                                              | `sessionAffinityTtlMs`   |
| क्लाइंट को कोई प्रॉम्प्ट दिखे बिना रीजनिंग के बीच में कनेक्शन समाप्त हो जाता है | 10 मिनट तक कोई अपस्ट्रीम चंक न मिलने पर स्ट्रीम निष्क्रियता वॉचडॉग सक्रिय हुआ | `STREAM_IDLE_TIMEOUT_MS` |

संबंधित चर्चाएँ: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (लंबे कार्य का बाधित होना), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (एफ़िनिटी डिफ़ॉल्ट रूप से बंद क्यों है)। ट्रैकिंग: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287)।

### 1. सत्र एफ़िनिटी — एक वार्तालाप को एक अकाउंट से पिन करें

**डिफ़ॉल्ट:** `sessionAffinityTtlMs = 0` (अक्षम)।

**इसे कहाँ सेट करें**

- डैशबोर्ड → **सेटिंग्स → रूटिंग** → **सत्र एफ़िनिटी** → **एफ़िनिटी TTL (सेकंड)** (`ComboDefaultsTab`)
- या **मिलीसेकंड** में `sessionAffinityTtlMs` के साथ सेटिंग्स को PATCH करें (Zod सीमा `0`–`86_400_000`, अर्थात अधिकतम 24 घंटे)

> #7274 में इसका नाम केवल Codex के लिए प्रयुक्त `codexSessionAffinityTtlMs` से बदला गया। पुरानी कुंजी अब भी केवल-पठन उपनाम के रूप में स्वीकार की जाती है; नए कॉन्फ़िगरेशन को `sessionAffinityTtlMs` का उपयोग करना चाहिए। TTL के `0` से अधिक होने पर एफ़िनिटी अब केवल Codex ही नहीं, बल्कि **किसी भी** प्रदाता पर लागू होती है — [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → सत्र एफ़िनिटी देखें।

**इसे 0 पर बनाए रखने से क्या बिगड़ता है**

कई टर्न वाली Codex बातचीत के प्रत्येक टर्न को सक्रिय कॉम्बो रणनीति द्वारा स्वतंत्र रूप से रूट किया जाता है और वह **हर टर्न पर किसी अलग अकाउंट** तक पहुँच सकता है। इससे अपस्ट्रीम सत्र / प्रॉम्प्ट-कैश निरंतरता टूट जाती है। OmniRoute केवल तभी Codex सत्र हेडर (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) और `prompt_cache_key` / `session_id` जैसे बॉडी फ़ील्ड देखता है, जब TTL `0` से अधिक हो (`src/sse/services/auth.ts` में `extractSessionAffinityKey`)।

**कई घंटों वाले एकल कार्य के लिए अनुशंसित**

TTL को **कार्य की अपेक्षित वास्तविक अवधि से अधिक** सेट करें (UI की अधिकतम सीमा **86400 सेकंड** = 24 घंटे है):

| अपेक्षित कार्य अवधि | एफ़िनिटी TTL (UI, सेकंड)  | `sessionAffinityTtlMs` |
| ------------------- | ------------------------- | ---------------------- |
| कुछ घंटे            | `14400` (4 घंटे)          | `14400000`             |
| रात भर / ~12 घंटे   | `43200` (12 घंटे)         | `43200000`             |
| पूरा दिन            | `86400` (24 घंटे, अधिकतम) | `86400000`             |

ऑप्ट-इन करना जानबूझकर आवश्यक है: एफ़िनिटी अक्षम करने से अकाउंट के बीच लोड-बैलेंसिंग को प्राथमिकता मिलती है; इसे सक्षम करने से एक लंबे एजेंट सत्र की निरंतरता को प्राथमिकता मिलती है। यह मार्गदर्शिका डिफ़ॉल्ट को **नहीं** बदलती — लंबे Codex कार्य चलाने वाले ऑपरेटरों को स्वयं ऑप्ट-इन करना होगा।

### 2. स्ट्रीम निष्क्रियता टाइमआउट — शांत रीजनिंग टर्न को समाप्त न करें

**डिफ़ॉल्ट:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 मिनट)। सेट न होने पर यह `REQUEST_TIMEOUT_MS` से मान प्राप्त करता है; साझा आधार मान भी 600000 है। [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → टाइमआउट देखें।

**डिफ़ॉल्ट पर क्या बिगड़ता है**

कोई Codex रीजनिंग / टूल टर्न, जो **किसी वास्तविक अपस्ट्रीम चंक के बिना** 10 मिनट से अधिक समय तक मौन रहता है, SSE निष्क्रियता वॉचडॉग (`open-sse/utils/stream.ts`) द्वारा जबरन बंद कर दिया जाता है। क्लाइंट को अक्सर केवल कनेक्शन टूटता हुआ दिखाई देता है — जो “बिना किसी सूचना के अपने-आप रुक गया” से मेल खाता है।

महत्वपूर्ण विवरण: OmniRoute का सिंथेटिक SSE **हार्टबीट निष्क्रियता घड़ी को रीसेट नहीं करता**। केवल वास्तविक अपस्ट्रीम बॉडी चंक ही `lastChunkTime` को अपडेट करता है। एक शांत मॉडल जो अभी भी “सोच” रहा है, वॉचडॉग के दृष्टिकोण से रुके हुए अपस्ट्रीम जैसा ही दिखाई देता है।

संबंधित Undici बॉडी निष्क्रियता: `FETCH_BODY_TIMEOUT_MS` (यह भी डिफ़ॉल्ट रूप से उसी 10-मिनट की आधार सीमा का उपयोग करता है; `0` इसे अक्षम कर देता है)। स्ट्रीमिंग के लिए, `FETCH_TIMEOUT_MS` केवल कनेक्शन सेटअप / शुरुआती हेडर तक लागू होता है — स्ट्रीम सक्रिय हो जाने के बाद, रुकावटें `STREAM_IDLE_TIMEOUT_MS` और `FETCH_BODY_TIMEOUT_MS` द्वारा नियंत्रित होती हैं।

**कई घंटों वाले एकल कार्य के लिए अनुशंसित**

OmniRoute प्रोसेस एनवायरनमेंट (`.env` / compose / systemd) में:

```bash
# लंबे रीजनिंग टर्न के लिए स्ट्रीम निष्क्रियता + बॉडी निष्क्रियता कटऑफ अक्षम करें
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

या उन्हें आपकी अपेक्षित सबसे लंबी मौन अवधि से अधिक बढ़ा दें (मान मिलीसेकंड में हैं):

```bash
# उदाहरण: अपस्ट्रीम चंक्स के बीच अधिकतम 2 घंटे की मौन अवधि की अनुमति दें
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

इन env vars को बदलने के बाद OmniRoute को पुनः आरंभ करें।

### ठोस विधि — कई घंटों वाला Codex कार्य

1. **अकाउंट पिन करें:** डैशबोर्ड → सेटिंग्स → रूटिंग → सेशन एफ़िनिटी → एफ़िनिटी TTL = `43200` (12 घंटे) या `86400` (अधिकतम 24 घंटे)।
2. OmniRoute के एनवायरनमेंट में **निष्क्रियता कटऑफ बढ़ाएँ / अक्षम करें**:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. सामान्य Codex `config.toml` (`wire_api = "responses"`, सही `base_url`, `OMNIROUTE_API_KEY`) बनाए रखें — इन दोनों व्यवहारों के लिए Codex की ओर से कोई एफ़िनिटी/निष्क्रियता सेटिंग उपलब्ध नहीं है।
4. OmniRoute को पुनः आरंभ करें, फिर लंबा Codex कार्य शुरू करें।

### डिफ़ॉल्ट संबंधी निर्णय (#7287)

| सेटिंग                   | जारी किया गया डिफ़ॉल्ट | इस गाइड में बदलाव?                                                                                         |
| ------------------------ | ---------------------- | ---------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (बंद)              | **नहीं** — ऑप्ट-इन ही रहेगा (लोड-बैलेंसिंग बनाम निरंतरता; Discussion #5718 देखें)                          |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 मिनट)     | **नहीं** — सामान्य ट्रैफ़िक के लिए 10 मिनट ही रहेगा; लंबे Codex कार्यों के ऑपरेटर इसे बढ़ाएँ या अक्षम करें |

इनमें से किसी भी डिफ़ॉल्ट को वैश्विक रूप से बदलने पर किसी इंस्टेंस के प्रत्येक क्लाइंट का व्यवहार बदल जाएगा, केवल Codex का नहीं। सेटिंग्स का दस्तावेज़ीकरण करें; जब तक कोई स्पष्ट ऑपरेटर निर्णय अन्यथा न कहे, डिफ़ॉल्ट को यथावत रखें।

### निष्क्रियता कटऑफ का निदान

जब निष्क्रियता वॉचडॉग सक्रिय होता है, तो OmniRoute इस स्वरूप की एक पंक्ति लॉग करता है:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

`Idle timeout: no data from` (या कोड `stream_idle_timeout` / त्रुटि नाम `StreamIdleTimeoutError`) के लिए grep करें। प्रोवाइडर सेगमेंट वही होता है जिसे OmniRoute ने उस अनुरोध के लिए उपयोग किया था (`codex`, कोई अन्य प्रोवाइडर id, या अज्ञात होने पर `provider`) — यह हमेशा शाब्दिक स्ट्रिंग `codex` नहीं होता।

## समस्या निवारण

**`Error: wire_api = "chat" अब समर्थित नहीं है`**
अपने कॉन्फ़िगरेशन से `wire_api = "chat"` हटाएँ। `wire_api = "responses"` सेट करें या फ़ील्ड को छोड़ दें (v0.138 से डिफ़ॉल्ट मान `"responses"` है)।

**`Error: model नहीं मिला`**
सत्यापित करें कि सही प्रीफ़िक्स के साथ मॉडल OmniRoute में मौजूद है। `omniroute models list` का उपयोग करें या `/dashboard/providers/<provider>` खोलें।

**`Authentication error`**
पुष्टि करें कि `OMNIROUTE_API_KEY` एक्सपोर्ट किया गया है: `echo $OMNIROUTE_API_KEY`।

**`ERROR: अनुपलब्ध एनवायरनमेंट वेरिएबल: OMNIROUTE_API_KEY`**
Codex पहला अनुरोध करने से पहले सत्यापित करता है कि एनवायरनमेंट वेरिएबल मौजूद है। सुरक्षित सर्वरों के लिए
वास्तविक कुंजी एक्सपोर्ट करें, या जब आपके **स्थानीय** OmniRoute इंस्टेंस को
प्रमाणीकरण की आवश्यकता न हो, तब `OMNIROUTE_API_KEY=local` जैसा कोई गैर-रिक्त प्लेसहोल्डर इस्तेमाल करें।
यदि आपने इसे `~/.bashrc` या `~/.zshrc` में जोड़ा है, तो शेल को पुनः आरंभ करें।

**`Connection refused`**
सत्यापित करें कि OmniRoute चल रहा है और `base_url` होस्ट/पोर्ट आपके नेटवर्क (स्थानीय बनाम Tailscale बनाम VPS) के लिए सही है।

**कॉन्टेक्स्ट सीमा के पास सेशन क्रैश हो जाता है**
`model_context_window` और `model_auto_compact_token_limit` को स्पष्ट रूप से सेट करें। ऊपर दी गई कॉन्टेक्स्ट विंडो तालिका देखें।

**कॉम्पैक्शन बहुत देर से शुरू होता है**
`model_auto_compact_token_limit` को विंडो के 80–85% तक कम करें। इसे कभी भी 90% से अधिक सेट न करें।

**प्रोफ़ाइल लोड नहीं हो रही (`-p <name>` को बिना किसी सूचना के अनदेखा किया जा रहा है)**
पुष्टि करें कि फ़ाइल `~/.codex/<name>.config.toml` पर मौजूद है (`profile-` प्रीफ़िक्स के बिना)। `ls ~/.codex/*.config.toml` चलाएँ।

**लंबा Codex कार्य बीच में रुक जाता है / टर्न के बीच खाते बदल जाते हैं**
[लंबे समय तक चलने वाले कार्य](#long-running-tasks) देखें। सेशन एफ़िनिटी सक्षम करें (TTL कार्य की अवधि से अधिक हो) और `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS` बढ़ाएँ या अक्षम करें। `Idle timeout: no data from` के लिए OmniRoute लॉग में grep करें।
