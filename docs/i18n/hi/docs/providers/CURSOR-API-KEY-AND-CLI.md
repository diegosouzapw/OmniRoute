IDE सत्र के बिना Cursor को OmniRoute के पीछे रखने के दो तरीके:

1. **`cursor-api` प्रदाता** (कार्ड "Cursor API", उपनाम `cua`): एक API-कुंजी
   प्रदाता, जो Cursor उपयोगकर्ता API कुंजी (`crsr_…`, जिसे
   `https://cursor.com/dashboard/api` पर जनरेट किया जाता है) रखता है। इसके बाद कोई भी OmniRoute क्लाइंट
   सामान्य कोटा, फ़ॉलबैक और लॉगिंग परतों के साथ `/v1/chat/completions` के माध्यम से
   Cursor मॉडल तक `cursor-api/<model>` या `cua/<model>` के रूप में पहुँचता है। IDE
   प्रदाता (`cursor`, OAuth/IDE सत्र) अपरिवर्तित रहता है।
2. **Cursor CLI पासथ्रू**: Cursor CLI (`agent`) को OmniRoute की ओर इंगित करें, ताकि
   CLI द्वारा की जाने वाली प्रत्येक RPC को OmniRoute API कुंजी से प्रमाणित किया जाए,
   `cursor-api` कनेक्शन के क्रेडेंशियल का उपयोग करके Cursor को फ़ॉरवर्ड किया जाए, और
   Logs पृष्ठ में रिकॉर्ड किया जाए।

## कुंजी का विनिमय क्यों किया जाता है

`api2.cursor.sh` किसी अपरिष्कृत `crsr_…` कुंजी को Bearer टोकन के रूप में अस्वीकार करता है (401)। Cursor
CLI पहले कुंजी को `/auth/exchange_user_api_key` पर POST करता है और एक सत्र
JWT प्राप्त करता है, जिसकी समय-सीमा एक घंटे बाद समाप्त हो जाती है; लौटाए गए `refreshToken` में वही
`exp` होता है, इसलिए रीफ़्रेश करने का अर्थ कुंजी का पुनः विनिमय करना है।
`open-sse/services/cursorApiKeyAuth.ts` यह विनिमय करता है, प्रत्येक कुंजी के लिए एक सत्र
टोकन कैश करता है, समय-सीमा समाप्त होने से पाँच मिनट पहले पुनः विनिमय करता है और Cursor से 401
उत्तर मिलने पर कैश किया गया टोकन हटा देता है। `CursorExecutor`, `cursor-api`
कनेक्शन के लिए अपस्ट्रीम स्ट्रीम खोलने से ठीक पहले इसे कॉल करता है।

## `cursor-api` प्रदाता

रजिस्ट्री: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"`, वही `format`, `baseUrl` और
`models` जो `cursor` के हैं)। कैटलॉग कार्ड:
`src/shared/constants/providers/apikey/specialty-media.ts`। एक्ज़ीक्यूटर मैप:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`)।

डैशबोर्ड: Providers → Cursor API → Add API key।

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

फिर:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

नोट्स:

- `cursor-api` के लिए मॉडल सूची स्थिर Cursor रजिस्ट्री से आती है (वही
  सूची जिस पर IDE प्रदाता फ़ॉलबैक करता है); OmniRoute होस्ट पर `cursor-agent`
  इंस्टॉल करने की आवश्यकता नहीं है।
- `POST /api/providers/{id}/refresh-cursor` केवल `cursor` IDE प्रदाता के
  लिए है; `cursor-api` कनेक्शन में नवीनीकृत करने के लिए कोई IDE सत्र नहीं होता।

## नेटिव मॉडल ID और प्रयास

`cursor` / `cu` और `cursor-api` / `cua` के लिए, साझा Claude-प्रयास नॉर्मलाइज़र
अनुरोधित मॉडल ID को यथावत छोड़ देता है। Cursor किसी वास्तविक मॉडल ID के भाग के रूप में
`-low` जैसा प्रत्यय प्रदर्शित कर सकता है, न कि OmniRoute प्रयास उपनाम के रूप में।
Cursor एक्ज़ीक्यूटर सटीक लाइव-कैटलॉग मिलान को बनाए रखता है; जब कोई
मिलान नहीं होता, तो उसका मौजूदा मॉडल रिज़ॉल्वर प्रत्यय-से-पैरामीटर फ़ॉलबैक संभालता है।

इससे प्रत्यक्ष Claude, Claude-संगत,
या Vertex रूटों के लिए प्रयास नॉर्मलाइज़ेशन नहीं बदलता। उपलब्धता अब भी चुने गए Cursor खाते के
कैटलॉग और अधिकार पर निर्भर करती है।

## Cursor CLI पासथ्रू

रूट: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`। प्रीफ़िक्स `/api/cursor-cli/` को
`src/shared/constants/publicApiRoutes.ts` में पंजीकृत किया गया है, क्योंकि हैंडलर
स्वयं अपना प्रमाणीकरण लागू करता है:

| पाथ                                                                                                                      | CLI से अपेक्षित प्रमाणीकरण   | OmniRoute क्या करता है                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                       | `Bearer <OmniRoute API key>` | कुंजी को सत्यापित करता है, 1 घंटे का HS256 JWT (`JWT_SECRET` से हस्ताक्षरित) जारी करता है और उसे लौटाता है                                                                                  |
| अन्य सभी पाथ (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`          | जारीकर्ता/ऑडियंस/समाप्ति को सत्यापित करता है, एक सक्रिय `cursor-api` कनेक्शन चुनता है, Authorization हेडर को एक्सचेंज किए गए Cursor टोकन से बदलता है और प्रत्युत्तर को वापस स्ट्रीम करता है |

CLI प्राप्त होने वाले किसी भी टोकन से `exp` को डीकोड करता है, इसलिए उसे कोई अपारदर्शी
टोकन देने पर वह लगभग हर अनुरोध से पहले फिर से एक्सचेंज करता है; जारी किया गया JWT इससे
बचाता है। OmniRoute से मिलने वाला 401 CLI को फिर से एक्सचेंज करने के लिए प्रेरित करता है।

### सेटअप

1. एक OmniRoute API कुंजी (Dashboard → API keys) और एक `cursor-api`
   कनेक्शन बनाएँ।
2. CLI को एजेंट स्ट्रीम के लिए HTTP/1.1 उपयोग करने के लिए कहें।
   `~/.cursor/cli-config.json` में:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   इसके बिना CLI एजेंट टर्न को HTTP/2 के माध्यम से अलग से
   कॉन्फ़िगर किए गए एजेंट होस्ट पर खोलता है और केवल कंट्रोल-प्लेन RPCs ही
   एंडपॉइंट से होकर जाते हैं।

3. CLI को OmniRoute के विरुद्ध चलाएँ:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

प्रत्येक हॉप Logs में प्रदाता `cursor-api`, अनुरोध प्रकार `cursor-cli`,
पाथ `/api/cursor-cli/<rpc>` के रूप में दर्ज होता है और उसे OmniRoute API कुंजी तथा
उसे सेवा देने वाले कनेक्शन से संबद्ध किया जाता है।

### विफलता के प्रकार

| स्थिति                                           | CLI को प्रत्युत्तर                                        |
| ------------------------------------------------ | --------------------------------------------------------- |
| अज्ञात OmniRoute कुंजी और `REQUIRE_API_KEY=true` | एक्सचेंज पर 401 `unauthenticated`                         |
| `REQUIRE_API_KEY=false`                          | अनाम सत्र (`/v1/*` के व्यवहार के समान)                    |
| समाप्त / बाहरी / छेड़छाड़ किया गया सत्र JWT      | 401, CLI फिर से एक्सचेंज करता है                          |
| एक्सचेंज के बाद OmniRoute API कुंजी निरस्त       | अगले RPC पर 401                                           |
| कोई सक्रिय `cursor-api` कनेक्शन नहीं             | 503 `unavailable`                                         |
| Cursor कनेक्शन की कुंजी को अस्वीकार करता है      | 401 `unauthenticated`, कैश किया गया सत्र हटा दिया जाता है |
| अपस्ट्रीम तक नहीं पहुँचा जा सकता                 | 502 `unavailable` (सैनिटाइज़ किया गया संदेश)              |
| `JWT_SECRET` सेट नहीं है                         | एक्सचेंज पर 503                                           |
