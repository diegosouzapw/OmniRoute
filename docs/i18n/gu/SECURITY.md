## નબળાઈઓની જાણ કરવી

જો તમને OmniRoute માં કોઈ સુરક્ષા નબળાઈ મળે, તો કૃપા કરીને જવાબદારીપૂર્વક તેની જાણ કરો:

1. સાર્વજનિક GitHub ઇશ્યૂ **ખોલશો નહીં**
2. [GitHub Security Advisories](https://github.com/diegosouzapw/OmniRoute/security/advisories/new) નો ઉપયોગ કરો
3. આ વિગતો સામેલ કરો: વર્ણન, પુનઃઉત્પાદનનાં પગલાં અને સંભવિત અસર

## LTS સમર્થન અવધિ (v3.9.x)

3.8.59 પછીનું આગામી વર્ઝન **3.9.0** છે, જે
`stable/v3` બ્રાન્ચ પર લાંબા ગાળાની સમર્થન શાખા શરૂ કરે છે ([`ROADMAP.md`](ROADMAP.md) → "તબક્કો 3 — v3.9.0 LTS" જુઓ).

- **`stable/v3` ને શું મળે છે:** બગ સુધારાઓ, સુરક્ષા પૅચ અને પ્રદાતાનાં અપડેટ. નવી
  સુવિધાઓ v4 ચૅનલમાં જાય છે; LTS શાખા સ્થિરતાને પ્રાથમિકતા આપે છે. `npm install omniroute`
  (`latest` dist-tag) સમગ્ર v4 ચક્ર દરમિયાન v3 પર રહે છે.
- **અવધિની લંબાઈ:** `<T-GAP-3: માલિકનો નિર્ણય બાકી છે — ROADMAP.md જુઓ>`. v4.0 GA પછી
  (`latest` જ્યારે v4 પર સ્વિચ થાય છે ત્યારે) અવધિની લંબાઈ અંગે **હજુ નિર્ણય લેવાયો નથી**;
  જાળવણીકર્તા તેની જાહેરાત કરે ત્યારે આ વિભાગ અપડેટ કરવામાં આવે છે. ત્યાં સુધી અંતિમ તારીખ ધારશો નહીં.
- **LTS શાખામાં નબળાઈની જાણ કરવી:** અન્ય કોઈપણ વર્ઝન જેવી જ ચૅનલ —
  ખાનગી [GitHub Security Advisory](https://github.com/diegosouzapw/OmniRoute/security/advisories/new),
  ક્યારેય સાર્વજનિક ઇશ્યૂ નહીં. તમે કયા વર્ઝનનું પરીક્ષણ કર્યું હતું તે જણાવો (ઉદાહરણ તરીકે `3.9.2`);
  સુધારાઓ `stable/v3` પર લાગુ થાય છે અને v4 પર ફૉર્વર્ડ-પોર્ટ કરવામાં આવે છે.
- **LTS વિભાજન વખતે સુરક્ષા આધારરેખા:** માપવામાં આવેલી સ્કૅનરની સ્થિતિ, રૂટ-ગાર્ડ અને
  સાર્વજનિક-ક્રેડેન્શિયલના પુરાવા
  [`docs/security/LTS_SECURITY_BASELINE.md`](docs/security/LTS_SECURITY_BASELINE.md) માં નોંધાયેલા છે.

## સુરક્ષા આર્કિટેક્ચર

OmniRoute બહુ-સ્તરીય સુરક્ષા મૉડલ અમલમાં મૂકે છે:

```
વિનંતી → CORS → Authz પાઇપલાઇન (વર્ગીકરણ → નીતિઓ → અમલીકરણ)
       → સુરક્ષા મર્યાદાઓ (PII માસ્કર, પ્રૉમ્પ્ટ ઇન્જેક્શન, વિઝન બ્રિજ)
       → દર મર્યાદક → સર્કિટ બ્રેકર → કૂલડાઉન → મૉડલ લૉકઆઉટ → પ્રદાતા
```

### 🔐 પ્રમાણીકરણ અને અધિકૃતતા

| સુવિધા                | અમલીકરણ                                                                                                                                              |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ડૅશબોર્ડ લૉગિન**    | JWT ટોકન (HttpOnly કૂકીઝ) સાથે પાસવર્ડ-આધારિત પ્રમાણીકરણ                                                                                             |
| **API કી પ્રમાણીકરણ** | CRC માન્યતા સાથે HMAC-હસ્તાક્ષરિત કી                                                                                                                 |
| **OAuth 2.0 + PKCE**  | પ્રદાતા-વિશિષ્ટ બ્રાઉઝર/ડિવાઇસ OAuth, જ્યાં સમર્થિત હોય ત્યાં PKCE નો ઉપયોગ કરે છે; ફક્ત આયાત માટેનાં Devin ક્રેડેન્શિયલ અલગથી સંચાલિત થાય છે.       |
| **ટોકન રિફ્રેશ**      | સમાપ્તિ પહેલાં OAuth ટોકનનું આપમેળે રિફ્રેશ                                                                                                          |
| **સુરક્ષિત કૂકીઝ**    | HTTPS એન્વાયર્નમેન્ટ માટે `AUTH_COOKIE_SECURE=true`                                                                                                  |
| **Authz પાઇપલાઇન**    | રૂટ વર્ગીકરણ (PUBLIC / CLIENT_API / MANAGEMENT) — `docs/architecture/AUTHZ_GUIDE.md` જુઓ                                                             |
| **રૂટ ગાર્ડ સ્તરો**   | મેનેજમેન્ટ રૂટ માટે 3-સ્તરીય મૉડલ (LOCAL_ONLY / ALWAYS_PROTECTED / MANAGEMENT) — `docs/security/ROUTE_GUARD_TIERS.md` જુઓ                            |
| **મેનેજ-સ્કોપ MCP**   | દૂરસ્થ `/api/mcp/*` ઍક્સેસ `manage` સ્કોપ ધરાવતી API કી દ્વારા નિયંત્રિત થાય છે; `/api/cli-tools/runtime/*` કડક-લૂપબૅક રહે છે. ROUTE_GUARD_TIERS જુઓ |
| **MCP સ્કોપ**         | 32 સૂક્ષ્મ સ્કોપ (read:health, write:combos, execute:completions વગેરે) — `docs/frameworks/MCP-SERVER.md` જુઓ                                        |

### 🛡️ સંગ્રહિત ડેટાનું એન્ક્રિપ્શન

SQLite માં સંગ્રહિત તમામ સંવેદનશીલ ડેટા scrypt કી ડેરિવેશન સાથે **AES-256-GCM** નો ઉપયોગ કરીને એન્ક્રિપ્ટ કરવામાં આવે છે:

- API કી, ઍક્સેસ ટોકન, રિફ્રેશ ટોકન અને ID ટોકન
- વર્ઝનવાળું ફૉર્મેટ: `enc:v1:<iv>:<ciphertext>:<authTag>`
- જ્યારે `STORAGE_ENCRYPTION_KEY` સેટ ન હોય ત્યારે પાસથ્રૂ મૉડ (પ્લેનટેક્સ્ટ)

```bash
# એન્ક્રિપ્શન કી બનાવો:
STORAGE_ENCRYPTION_KEY=$(openssl rand -hex 32)
```

### 🛡️ સુરક્ષા મર્યાદાઓનું ફ્રેમવર્ક

OmniRoute પ્રાથમિકતા અનુસાર ગોઠવેલી 3 બિલ્ટ-ઇન સુરક્ષા મર્યાદાઓ સાથે હૉટ-રીલોડ કરી શકાય તેવી **સુરક્ષા મર્યાદાઓની રજિસ્ટ્રી** (`src/lib/guardrails/`) પ્રદાન કરે છે:

| સુરક્ષા મર્યાદા    | પ્રાથમિકતા | હેતુ                                                                        |
| ------------------ | ---------- | --------------------------------------------------------------------------- |
| `vision-bridge`    | 5          | નૉન-વિઝન મૉડલને ઇમેજ-જાગૃત વર્ણનો સાથે જોડે છે; ઇમેજ URL માટે SSRF સુરક્ષા  |
| `pii-masker`       | 10         | કૉલ પહેલાં અને પછી PII રીડૅક્શન (ઇમેઇલ, ફોન, CPF, CNPJ, ક્રેડિટ કાર્ડ, SSN) |
| `prompt-injection` | 20         | ઓવરરાઇડ/ભૂમિકા-હાઇજૅક/જેલબ્રેક/લીક પૅટર્ન શોધે છે                           |

કસ્ટમ સુરક્ષા મર્યાદાઓ `registerGuardrail(new MyGuardrail())` દ્વારા રજિસ્ટર થાય છે. આ મૉડલ ફેઇલ-ઓપન છે (અપવાદો ક્યારેય ટ્રાફિકને અવરોધતા નથી). `x-omniroute-disabled-guardrails` હેડર દ્વારા દરેક વિનંતી માટે અલગથી નાપસંદ કરવાની સુવિધા ઉપલબ્ધ છે. → [`docs/security/GUARDRAILS.md`](docs/security/GUARDRAILS.md) જુઓ.

### 🧠 પ્રૉમ્પ્ટ ઇન્જેક્શન ગાર્ડ

LLM વિનંતીઓમાં પ્રોમ્પ્ટ ઇન્જેક્શન પેટર્ન શોધતું શ્રેષ્ઠ-પ્રયાસ આધારિત હ્યુરિસ્ટિક મિડલવેર.
**સંપૂર્ણ પ્રોમ્પ્ટ-ઇન્જેક્શન ફાયરવૉલ નથી** — ખોટા પોઝિટિવ (નિર્દોષ
પર્સોના/RPG પ્રોમ્પ્ટ) અને ખોટા નેગેટિવ (લીટસ્પીક, સ્પેસિંગ, બિન-અંગ્રેજી પેટર્ન) ઉત્પન્ન કરી શકે છે.

| પેટર્નનો પ્રકાર    | ગંભીરતા | ઉદાહરણ                                         |
| ------------------ | ------- | ---------------------------------------------- |
| સિસ્ટમ ઓવરરાઇડ     | ઉચ્ચ    | "અગાઉની બધી સૂચનાઓ અવગણો"                      |
| ભૂમિકા હાઇજેક      | મધ્યમ   | "હવે તમે DAN છો, તમે કંઈપણ કરી શકો છો"         |
| ડિલિમિટર ઇન્જેક્શન | ઉચ્ચ    | સંદર્ભની સીમાઓ તોડવા માટે એન્કોડ કરેલા વિભાજકો |
| DAN/જેલબ્રેક       | મધ્યમ   | જાણીતા જેલબ્રેક પ્રોમ્પ્ટ પેટર્ન               |
| સૂચના લીક          | ઉચ્ચ    | "મને તમારો સિસ્ટમ પ્રોમ્પ્ટ બતાવો"             |
| એન્કોડિંગથી બચાવ   | મધ્યમ   | base64/rot13/hex ડિકોડ + સૂચના કીવર્ડ્સ        |

`block` મોડમાં માત્ર **ઉચ્ચ** ગંભીરતાવાળી શોધને અવરોધવામાં આવે છે. મધ્યમ-ગંભીરતાવાળા
પરિવારો લૉગ થાય છે પરંતુ `sanitizeRequest` દ્વારા ક્યારેય અવરોધાતા નથી.

ડૅશબોર્ડ (Settings → Security) અથવા `.env` દ્વારા ગોઠવો:

```env
INPUT_SANITIZER_ENABLED=true
INPUT_SANITIZER_MODE=block    # ચેતવણી | અવરોધ (ઇન્જેક્શન નીતિ; લેગસી "redact" ઇન્જેક્શન ટેક્સ્ટને દૂર કરતું નથી)
INPUT_SANITIZER_BLOCK_THRESHOLD=high  # ઉચ્ચ (ડિફૉલ્ટ) | મધ્યમ | નીચું — આ અથવા તેનાથી વધુ ગંભીરતાવાળી શોધ block મોડમાં અવરોધાય છે
```

## આવશ્યક એન્વાયરમેન્ટ વેરિએબલ્સ

સર્વર શરૂ કરતાં પહેલાં તમામ સિક્રેટ્સ સેટ કરેલા હોવા આવશ્યક છે. જો તેઓ ઉપલબ્ધ ન હોય અથવા નબળા હોય, તો સર્વર **તરત જ નિષ્ફળ થશે**.

```bash
# આવશ્યક — આના વિના સર્વર શરૂ થશે નહીં:
JWT_SECRET=$(openssl rand -base64 48)     # ઓછામાં ઓછા 32 અક્ષરો
API_KEY_SECRET=$(openssl rand -hex 32)    # ઓછામાં ઓછા 16 અક્ષરો

# ભલામણ કરેલ — સંગ્રહિત ડેટાનું એન્ક્રિપ્શન સક્ષમ કરે છે:
STORAGE_ENCRYPTION_KEY=$(openssl rand -hex 32)
```

સર્વર `changeme`, `secret` અથવા `password` જેવા જાણીતા નબળા મૂલ્યોને સક્રિય રીતે નકારે છે.

## કડક સુરક્ષા નિયમો

આ નિયમો ટૂલિંગ અને સમીક્ષકો દ્વારા લાગુ કરવામાં આવે છે:

1. **સિક્રેટ્સ ક્યારેય commit કરશો નહીં** — `.env` gitignore કરેલું છે; `.env.example` ટેમ્પલેટ છે (કોઈ લિટરલ્સ નહીં, માત્ર કૉમેન્ટ્સ — નીચે PUBLIC_CREDS.md જુઓ)
2. **`eval()`, `new Function()` અથવા implied eval નો ક્યારેય ઉપયોગ કરશો નહીં** — ESLint આ નિયમ લાગુ કરે છે
3. **સ્પષ્ટ ઑપરેટર મંજૂરી વિના Husky hooks ને ક્યારેય બાયપાસ કરશો નહીં** (`--no-verify`, `--no-gpg-sign`)
4. **routes માં ક્યારેય raw SQL લખશો નહીં** — હંમેશાં `src/lib/db/` મારફતે જાઓ (પેરામીટરાઇઝ્ડ)
5. **ઇનપુટ્સને હંમેશાં Zod વડે માન્ય કરો** — `src/shared/validation/schemas.ts`
6. **upstream headers ને હંમેશાં sanitize કરો** — `src/shared/constants/upstreamHeaders.ts` માં denylist
7. **સંગ્રહિત credentials ને એન્ક્રિપ્ટ કરો** — `src/lib/db/encryption.ts` મારફતે AES-256-GCM
8. **`resolvePublicCred()` મારફતે જાહેર upstream OAuth identifiers** — સોર્સમાં ક્યારેય `AIza…` / `GOCSPX-…` / `…apps.googleusercontent.com` લિટરલ્સ એમ્બેડ કરશો નહીં. [`docs/security/PUBLIC_CREDS.md`](docs/security/PUBLIC_CREDS.md) જુઓ.
9. **`buildErrorBody()` / `sanitizeErrorMessage()` મારફતે error responses** — HTTP / SSE / executor / MCP response bodies માં ક્યારેય raw `err.stack` / `err.message` મૂકશો નહીં. [`docs/security/ERROR_SANITIZATION.md`](docs/security/ERROR_SANITIZATION.md) જુઓ.
10. **`env` વિકલ્પ મારફતે `exec()` / `spawn()` runtime values** — shell ને મોકલાતી સ્ક્રિપ્ટ્સમાં external paths અથવા અવિશ્વસનીય મૂલ્યોને ક્યારેય string-interpolate કરશો નહીં. સંદર્ભ: `src/mitm/cert/install.ts::updateNssDatabases`.
11. **secure-by-default લાઇબ્રેરીઓને પ્રાધાન્ય આપો** — [tldrsec/awesome-secure-defaults](https://github.com/tldrsec/awesome-secure-defaults) જુઓ (Helmet.js, DOMPurify, ssrf-req-filter, safe-regex, Google Tink). પોતાનું સોલ્યુશન બનાવતા પહેલાં તેમનો ઉપયોગ કરો.

## સપ્લાય-ચેઇન સ્કેનરના તારણો (Socket.dev / Snyk / સમાન)

> **વ્યાપ નોંધ:** રિપોઝિટરીના રૂટ પરની `socket.yml` માત્ર પ્રકાશિત npm આર્ટિફેક્ટના Socket.devના રજિસ્ટ્રી-સાઇડ પોસ્ટ-પબ્લિશ સ્કેન માટે `projectIgnorePaths`ને આકાર આપે છે — તે અમલમાં મુકાયેલ CI/PR મર્જ ગેટ નથી. `.github/workflows`માં કોઈ workflow, કોઈ `package.json` script અને કોઈ `Makefile` target Socket.devને ચલાવતું નથી.

પ્રકાશિત `omniroute` npm આર્ટિફેક્ટ Next.jsના `output: "standalone"`
બિલ્ડને બંડલ કરે છે, જેનો અર્થ એ છે કે દરેક route handler — દસ્તાવેજીકૃત વિશેષાધિકારપ્રાપ્ત
સુવિધાઓ (MITM, Zed import, Cloud Sync, embedded service supervisor) સહિત — અંતે
`.next/server/*.js`ની minified chunksમાં આવે છે. હ્યુરિસ્ટિક સપ્લાય-ચેઇન સ્કેનર્સ
ઘણી વાર એ chunksને malware signatures સાથે pattern-match કરે છે.

અમે ઉપયોગ કરીએ છીએ તે scanner configuration રિપોના રૂટમાં [`socket.yml`](socket.yml) ખાતે છે
(Socket.dev GitHub App format v2 — જુઓ
<https://docs.socket.dev/docs/socket-yml>). તે સ્પષ્ટપણે
શિપ ન થતી directories (`tests/`, `_tasks/`, `_references/`, `_ideia/`,
`_mono_repo/`, `docs/`, વગેરે)ને બાકાત રાખે છે, જેથી scanner ફક્ત વાસ્તવમાં
પ્રકાશિત વપરાશકર્તાઓ સુધી પહોંચતા code paths અંગે જ અહેવાલ આપે — scan પોતે આ file વાંચતી Socket
GitHub App દ્વારા સંચાલિત થાય છે, આ repositoryમાંના કોઈ workflow દ્વારા નહીં.

દરેક finding category માટે અમે finding-દીઠ maintainer attestation જાળવીએ છીએ:

- **[`docs/security/SOCKET_DEV_FINDINGS.md`](docs/security/SOCKET_DEV_FINDINGS.md)** —
  finding-દીઠ નકશો: source file ↔ flagged chunk ↔ વર્તન ↔ v3.8.6માં લાગુ કરાયેલ
  mitigation.
- દરેક flagged function ખાતેના in-source `SECURITY-AUDITOR-NOTE:` blocks
  એ જ document તરફ પાછો સંદર્ભ આપે છે.

જે વપરાશકર્તાઓની pipeline alertને શિથિલ કરી શકતી નથી તેમના માટે:
`OMNIROUTE_BUILD_PROFILE=minimal npm run build` વડે build કરો. આ ચાર
સંવેદનશીલ modulesને એવા stubsથી બદલે છે જે runtime સમયે HTTP 503
`feature-disabled` પરત કરે છે, તેથી વિશેષાધિકારપ્રાપ્ત code paths bundleમાં ભૌતિક રીતે હાજર રહેતા નથી.
Publishing recipe માટે [`docs/security/SOCKET_DEV_FINDINGS.md`](docs/security/SOCKET_DEV_FINDINGS.md)
જુઓ.
