TPROXY પારદર્શક ડિક્રિપ્ટ એ OmniRouteના
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM સ્ટૅક માટેનો **5મો કૅપ્ચર મોડ** છે. તે kernel TPROXY + policy routingનો ઉપયોગ કરીને Linux
પર સ્થાનિક આઉટબાઉન્ડ HTTPS ટ્રાફિકને ઇન્ટરસેપ્ટ અને **ડિક્રિપ્ટ** કરે છે — `/etc/hosts`ને
સ્પૂફ કર્યા **વિના** અને સમગ્ર OS પર લાગુ થતી system-proxy સેટિંગ્સમાં ફેરફાર કર્યા
**વિના**. તે headless વાતાવરણ માટે અનુકૂળ છે
(સાફ કરવા માટે કોઈ DNS ફેરફારો નથી) અને રીબૂટ વખતે firewall નિયમો આપમેળે ફ્લશ થઈ જાય છે.

અન્ય કૅપ્ચર મોડ્સથી વિપરીત, TPROXYને દરેક હોસ્ટ માટે અલગ સેટઅપની જરૂર નથી: તે લક્ષ્ય પોર્ટ પરના
**કોઈપણ** ગંતવ્ય હોસ્ટને પારદર્શક રીતે ઇન્ટરસેપ્ટ કરે છે, દરેક SNI હોસ્ટનેમ માટે તત્કાળ જારી કરેલા
leaf certificate વડે TLS સમાપ્ત કરે છે, ડિક્રિપ્ટ થયેલા
આદાનપ્રદાનને કૅપ્ચર કરે છે અને વિનંતીને મૂળ ગંતવ્ય માટે ફરીથી એન્ક્રિપ્ટ કરે છે.

> **માત્ર Linux, માત્ર root, opt-in.** આ મોડ માટે Linux, C toolchain વડે બનાવેલું native addon
> અને **CAP_NET_ADMIN** capability (સામાન્ય રીતે root) જરૂરી છે. તેની ઍક્સેસ
> માત્ર loopback માટેની AgentBridge API સુધી મર્યાદિત છે અને તે ડિફૉલ્ટ રૂપે અક્ષમ છે. કોઈપણ
> હોસ્ટ માટે સહી કરી શકતું વિશ્વસનીય MITM CA એક શક્તિશાળી capability છે — [§6 સુરક્ષા](#6-security) જુઓ.

**સોર્સ:** `src/mitm/tproxy/`
**API રૂટ:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**ડૅશબોર્ડ ટૉગલ:** Traffic Inspector → capture-modes ટૂલબાર → **"TPROXY ડિક્રિપ્ટ"** ⚠
**આ પણ જુઓ:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 આ શું છે અને તેનો ઉપયોગ ક્યારે કરવો

અન્ય ચાર કૅપ્ચર મોડ્સમાંના દરેકની એક મર્યાદા છે:

| મોડ               | ટ્રાફિક કેવી રીતે દોરવામાં આવે છે              | મર્યાદા                                               |
| ----------------- | ---------------------------------------------- | ----------------------------------------------------- |
| AgentBridge       | નિશ્ચિત હોસ્ટ સેટનું `/etc/hosts` DNS સ્પૂફિંગ | માત્ર નોંધાયેલા IDE-agent હોસ્ટ્સ                     |
| Custom Hosts      | દરેક હોસ્ટ માટે `/etc/hosts` DNS સ્પૂફિંગ      | દરેક હોસ્ટ માટે એક એન્ટ્રી; hostsમાં ફેરફાર કરવા sudo |
| HTTP_PROXY        | `HTTP_PROXY`/`HTTPS_PROXY` env                 | માત્ર env varનું પાલન કરતી ઍપ્સ                       |
| System-wide proxy | OS proxy સેટિંગ્સ                              | વૈશ્વિક સ્થિતિમાં ફેરફાર કરે છે; પૂર્વવત્ કરવું જરૂરી |

તેના બદલે TPROXY પારદર્શક ડિક્રિપ્ટ ટ્રાફિકને **kernel** સ્તરે દોરે છે. તે
`mangle OUTPUT` chainમાં લક્ષ્ય પોર્ટ (ડિફૉલ્ટ `443`) તરફનાં નવાં સ્થાનિક આઉટબાઉન્ડ TCP કનેક્શન્સને
ચિહ્નિત કરે છે, એક `ip rule` ચિહ્નિત પૅકેટ્સને સ્થાનિક ડિલિવરી તરફ ફરીથી રૂટ કરે છે
અને ફરીથી પ્રવેશ વખતે `mangle PREROUTING`નું `TPROXY` target તેમને
**IP_TRANSPARENT** listenerને સોંપે છે — જે પછી TLS સમાપ્ત કરે છે અને plaintext કૅપ્ચર કરે છે.

તેનો ઉપયોગ ત્યારે કરો જ્યારે તમે એવી processમાંથી આવતા ટ્રાફિકને કૅપ્ચર અને ડિક્રિપ્ટ કરવા માંગતા હો જે:

- AgentBridge દ્વારા નોંધાયેલ ન હોય તેવા હોસ્ટ સાથે સંચાર કરે છે, અને
- `HTTP_PROXY`નું પાલન કરતી નથી, અને
- જેમાં તમે system-wide proxy ફેરફારથી ખલેલ પહોંચાડવા માંગતા નથી.

ઇન્ટરસેપ્શન kernelમાં થતું હોવાથી, મૂળ processમાં **કોઈ
configuration ફેરફારની** જરૂર નથી — પરંતુ processએ OmniRoute દ્વારા ઇન્સ્ટૉલ કરાયેલા dynamic CA પર
વિશ્વાસ કરવો આવશ્યક છે ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) જુઓ).

## §2 આવશ્યકતાઓ

| આવશ્યકતા           | વિગત                                                                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**             | માત્ર Linux — **IP_TRANSPARENT** એ માત્ર Linux માટેનો socket વિકલ્પ છે. અન્ય દરેક પ્લેટફોર્મ પર loader "અનુપલબ્ધ" પરત કરે છે.                                             |
| **વિશેષાધિકાર**    | પારદર્શક socket બનાવવા અને `iptables`/`ip` નિયમો લાગુ કરવા માટે **CAP_NET_ADMIN** capability — વ્યવહારમાં, root તરીકે ચલાવો.                                              |
| **મૂળ addon**      | નાનું N-API addon (`src/mitm/tproxy/native/transparent.c`) build કરેલું હોવું જોઈએ અથવા prebuild તરીકે મોકલેલું હોવું જોઈએ. [§3](#3-the-native-ip_transparent-addon) જુઓ. |
| **Kernel modules** | `TPROXY`, `mangle`, અને `mark` match સપોર્ટ સાથેનું `iptables` (kernel 6.8.0 સામે માન્ય કરેલું).                                                                          |

**સુવ્યવસ્થિત અવક્રમણ:** જો કોઈ આવશ્યકતા ઉપલબ્ધ ન હોય (બિન-Linux, toolchain ન હોય,
addon build ન થયું હોય), તો addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
exception ફેંકવાને બદલે `null` પરત કરે છે. ત્યારબાદ capture-mode સ્થિતિ
`available: false` દર્શાવે છે, dashboard toggle **અક્ષમ** રહે છે અને tooltipમાં
"TPROXY decrypt માટે Linux + root + native addon જરૂરી છે" દેખાય છે, જ્યારે
OmniRouteનો બાકીનો ભાગ કાર્યરત રહે છે.

## §3 મૂળ IP_TRANSPARENT addon

Nodeનું `net` module `bind()` કરતાં _પહેલાં_ `setsockopt(IP_TRANSPARENT)` કરી શકતું
નથી, જે TPROXY માટે જરૂરી છે (અન્યથા kernel પુનઃદિશામાન કરેલા packetsને છોડી દે છે). આ addon
(`src/mitm/tproxy/native/transparent.c`, `binding.gyp` દ્વારા build કરાયેલું) એક નાનું N-API
module છે, જે ત્રણ functions ઉપલબ્ધ કરાવે છે અને જેનો ઉપયોગ `transparentSocket.ts` મારફતે થાય છે:

| Addon function                        | Socket કાર્ય                                                                                  | આ માટે વપરાય છે                                                              |
| ------------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, મૂળ fd પરત કરે છે | પારદર્શક capture listener (Node `server.listen({ fd })` મારફતે fd અપનાવે છે) |
| `setSocketMark(fd, mark)`             | હાલના fd પર `setsockopt` **SO_MARK**                                                          | anti-loop (proxyના પોતાના socketsને mark કરવા)                               |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()` કરતાં **પહેલાં** `socket()` + **SO_MARK**, fd પરત કરે છે             | ફરીથી encrypted કરેલું upstream forward (SYN mark ધરાવે છે)                  |

મૂળ destination `socket.localAddress`/`localPort`માંથી વાંચવામાં આવે છે — TPROXY
તેને જાળવી રાખે છે, તેથી **SO_ORIGINAL_DST**/NAT lookupની જરૂર નથી.

### Addon build કરવું

```bash
npm run build:native:tproxy      # src/mitm/tproxy/nativeમાં cd કરો અને node-gyp rebuild ચલાવો
                                 # -> native/build/Release/transparent.node
```

- `npm run build` દરમિયાન, `scripts/build/build-tproxy-native.mjs` `node-gyp
rebuild` ચલાવે છે. તે **માત્ર Linux માટે અને non-fatal** છે — toolchain ન હોય તો
  capture mode ફક્ત અનુપલબ્ધ રહે છે.
- `assembleStandalone.mjs`, `build/Release/transparent.node`ને
  standalone bundleમાં copy કરે છે; `transparentSocket.ts` તેને module-relative અને
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`) એમ બંને રીતે resolve કરે છે.
- `build/` અને `prebuilds/` git-ignored છે — binary **build કરવામાં આવે છે, ક્યારેય
  commit કરવામાં આવતી નથી**.

Loader પ્રાથમિકતાના ક્રમમાં આ સ્થાનોને તપાસે છે:
`native/build/Release/transparent.node`, પછી `native/prebuilds/transparent.node`
(બંને module-relative અને `<cwd>/src/mitm/tproxy/` હેઠળ).

## §4 પ્રતિ-SNI ડાયનેમિક CA અને ટ્રસ્ટ-સ્ટોર ઇન્સ્ટોલર

> **#6684 અપડેટ:** AgentBridge સ્ટેટિક સર્વર (`src/mitm/server.cjs`) હવે
> એક જ સ્ટેટિક સ્વ-હસ્તાક્ષરિત લીફને બદલે આ જ CA/લીફ આર્કિટેક્ચર પેટર્ન
> શેર કરે છે. તે એક **અલગ** CA ઇન્સ્ટન્સનો ઉપયોગ કરે છે
> (`src/mitm/cert/rootCa.ts`, જે `<DATA_DIR>/mitm/ca.key`/`ca.crt` પર સંગ્રહિત રહે છે)
> અને પહેલેથી અસ્તિત્વમાં રહેલા `omniroute-mitm.crt` ટ્રસ્ટ-સ્ટોર સ્લોટ હેઠળ
> ઇન્સ્ટોલ થાય છે (ત્યાંના જૂના એકમાત્ર લીફને બદલીને — દ્વિ-ટ્રસ્ટ ક્લીનઅપની
> જરૂર નથી), તથા નીચે આપેલા TPROXYના પોતાના `omniroute-tproxy-ca.crt` સ્લોટથી
> સંપૂર્ણપણે અલગ રાખવામાં આવે છે. નવા AgentBridge ઇન્સ્ટોલેશનને CA મોડલ
> આપમેળે મળે છે; જે ઇન્સ્ટોલેશન જૂના સ્ટેટિક લીફ પર પહેલેથી વિશ્વાસ કરે છે
> તે ઓપરેટર `MITM_ROOT_CA_ENABLED=true` દ્વારા સ્પષ્ટપણે પસંદગી ન કરે ત્યાં સુધી
> તેનો જ ઉપયોગ કરવાનું ચાલુ રાખે છે (`src/mitm/cert/migration.ts` જુઓ) —
> **કોઈપણ** હોસ્ટ માટે લીફ સાઇન કરી શકતું વિશ્વસનીય MITM CA જૂના નિશ્ચિત-SAN
> લીફ કરતાં નોંધપાત્ર રીતે વધુ શક્તિશાળી છે, તેથી પહેલેથી વિશ્વસનીય
> ઇન્સ્ટોલેશન માટે આ ફેરફાર ક્યારેય નિઃશબ્દ રીતે થતો નથી.

ઐતિહાસિક રીતે, સ્ટેટિક AgentBridge MITM પ્રમાણપત્ર માત્ર એટલા માટે કાર્ય કરતું
હતું કારણ કે AgentBridge **નિશ્ચિત** હોસ્ટ સમૂહ માટે DNS સ્પૂફિંગ કરે છે
(હવે તે નીચેના મોડલ સાથે એકીકૃત છે). TPROXY **મનસ્વી** હોસ્ટને ઇન્ટરસેપ્ટ
કરે છે, તેથી તેના લિસનરે ક્લાયન્ટ જે પણ SNI માંગે તેના માટે માન્ય લીફ
રજૂ કરવું આવશ્યક છે — આ જ જરૂરિયાત હવે AgentBridge માટે પણ માત્ર 4
antigravity હોસ્ટને બદલે સંપૂર્ણ `MITM_TOOL_HOSTS` સમૂહ (9 ટૂલ એન્ટ્રીઓ)
માટે લાગુ પડે છે.

### ડાયનેમિક CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` સ્થાનિક CA ચલાવે છે (`selfsigned` ડિપેન્ડન્સી પર આધારિત), જે:

- `generateMitmCa()` દ્વારા લાંબા સમય સુધી માન્ય CA જનરેટ કરે છે (CN `"OmniRoute MITM CA"`,
  10 વર્ષની માન્યતા, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-bit RSA / SHA-256).
- `issueLeafCert()` દ્વારા **દરેક SNI હોસ્ટનામ માટે માંગ મુજબ લીફ** જારી કરે છે
  (1 વર્ષની માન્યતા, `subjectAltName` = SNI હોસ્ટ) અને દરેક હોસ્ટનામ દીઠ એક
  `tls.SecureContext` કૅશ કરે છે.
- TLS-ટર્મિનેટિંગ સર્વર માટે `createSNICallback()` ઉપલબ્ધ કરાવે છે ([§5](#5-how-decrypt-and-capture-work) જુઓ).
- રીસ્ટાર્ટ વચ્ચે CAને સ્થિર રાખવા માટે `existingCa` સાથે બનાવી શકાય છે
  (જેથી ટ્રસ્ટ સ્ટોર ફરીથી ઇન્સ્ટોલ કરવાની જરૂર ન પડે).

CA પ્રાઇવેટ કી **ક્યારેય મશીનની બહાર જતી નથી**.

### ટ્રસ્ટ-સ્ટોર ઇન્સ્ટોલર (`src/mitm/tproxy/caTrust.ts`)

ઇન્ટરસેપ્ટ થયેલા ક્લાયન્ટે ડાયનેમિક CA પર વિશ્વાસ કરવો જરૂરી છે, તેથી કૅપ્ચર
મોડ શરૂ કરવાથી CA પ્રમાણપત્ર OS ટ્રસ્ટ સ્ટોરમાં એક **સમર્પિત સ્લોટ** હેઠળ
ઇન્સ્ટોલ થાય છે — `omniroute-tproxy-ca.crt` (કોન્સ્ટન્ટ `TPROXY_CA_CERT_NAME`) —
જેને સ્ટેટિક MITM પ્રમાણપત્રના સ્લોટ (`omniroute-mitm.crt`)થી અલગ રાખવામાં
આવે છે, જેથી બંને ક્યારેય એકબીજાને ઓવરરાઇટ ન કરે.

`installTproxyCa(caPem, sudoPassword?)` ડિસ્ટ્રિબ્યુશનની ઍન્કર ડિરેક્ટરી
(ક્રમમાં: પ્રથમ Debian-શૈલી) શોધે છે અને તેને અનુરૂપ રિફ્રેશ કમાન્ડ ચલાવે છે:

| ઍન્કર ડિરેક્ટરી                             | રિફ્રેશ કમાન્ડ           |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

ઇન્સ્ટોલેશન પહેલાં PEMને અસ્થાયી ફાઇલમાં સ્ટેજ કરે છે, ત્યારબાદ (વિશેષાધિકાર
સાથે) ઍન્કર ડિરેક્ટરી માટે `mkdir -p` ચલાવે છે, સ્ટેજ કરેલી ફાઇલને તેમાં
`cp` કરે છે અને રિફ્રેશ કમાન્ડ ચલાવે છે. `uninstallTproxyCa()` માત્ર સમર્પિત
સ્લોટ દૂર કરે છે (સ્ટેટિક MITM પ્રમાણપત્રને અસ્પર્શિત રાખીને) અને રિફ્રેશ
કરે છે — non-Linux પર તે કોઈ ક્રિયા કરતું નથી.

બધી વિશેષાધિકારવાળી કમાન્ડ `execFileWithPassword` (`src/mitm/systemCommands.ts`)
દ્વારા ચાલે છે — **આર્ગ્યુમેન્ટ ઍરે સાથે `spawn`, કોઈ shell નહીં, કોઈ string
interpolation નહીં** (સખત નિયમ #13). જ્યારે પ્રોસેસ root હોય (દા.ત. VPS),
ત્યારે લક્ષ્ય સીધું ચાલે છે અને પાસવર્ડની જરૂર પડતી નથી; non-root ડેસ્કટોપ
પર `sudoPassword`, stdin મારફતે `sudo -S`ને આપવામાં આવે છે.

> ડેસ્કટોપનું `sudoPassword` ટ્રસ્ટ-સ્ટોર ઇન્સ્ટોલેશનને અધિકૃત કરવા માટે
> POST બોડીમાં પૂરું પાડવામાં આવે છે; જ્યારે પ્રોસેસ root હોય ત્યારે તેને
> સંપૂર્ણપણે અવગણવામાં આવે છે.

## §5 ડિક્રિપ્શન અને કૅપ્ચર કેવી રીતે કાર્ય કરે છે

પાઇપલાઇન (આખી `src/mitm/tproxy/` હેઠળ):

```
સ્થાનિક ઍપ  ──TCP/443──▶  mangle OUTPUT કનેક્શનને ચિહ્નિત કરે છે (fwmark)
                           ip rule → સ્થાનિક રૂટ ટેબલ → lo
                           mangle PREROUTING TPROXY → IP_TRANSPARENT લિસનર (પોર્ટ 8443)
                               │  captureMode.ts: socket.localAddressમાંથી મૂળ ગંતવ્ય વાંચે છે
                               ▼
                           tlsCapture.ts:
                             1. પ્રતિ-SNI લીફ (dynamicCert) વડે CLIENTનું TLS સમાપ્ત કરે છે
                             2. આંતરિક http.Server ડિક્રિપ્ટ થયેલ પ્લેઇનટેક્સ્ટને પાર્સ કરે છે
                             3. કૅપ્ચર → source: "tproxy" સાથે globalTrafficBuffer.push()
                                (sanitizeHeaders + maskSecret લાગુ કરેલ)
                             4. બાયપાસ-ચિહ્નિત સૉકેટ (connectMarked, ઍન્ટિ-લૂપ) મારફતે
                                મૂળ ગંતવ્ય પર ફરીથી એન્ક્રિપ્ટ કરીને ફૉર્વર્ડ કરે છે
                               │
                               ▼
                           મૂળ અપસ્ટ્રીમ (api.example.com)
```

- **TLS સમાપ્તિ** (`createTlsCaptureServer`): ડાયનેમિક CAના SNI કૉલબૅકનો ઉપયોગ કરીને કાચા ઇન્ટરસેપ્ટ કરાયેલા
  સૉકેટને સર્વર-સાઇડ `tls.TLSSocket`માં રૅપ કરે છે,
  ત્યારબાદ ડિક્રિપ્ટ થયેલ સ્ટ્રીમને આંતરિક `http.Server`ને સોંપે છે (માનક MITM
  સમાપ્તિ યુક્તિ). સૉકેટનું આયુષ્ય `MITM_IDLE_TIMEOUT_MS` દ્વારા મર્યાદિત છે, જેથી
  અટવાયેલી ટનલ ફાઇલ ડિસ્ક્રિપ્ટરો ખાલી ન કરી શકે.
- **કૅપ્ચર** (`handleDecryptedRequest`): `source: "tproxy"`,
  `"in-flight"`થી શરૂ થતું સ્ટેટસ, `sanitizeHeaders()`માંથી પસાર કરેલા હેડર્સ
  અને બફરમાં પ્રવેશે તે પહેલાં `maskSecret()`માંથી પસાર કરેલી બૉડીઝ સાથે
  `InterceptedRequest` પુશ કરે છે. ત્યારબાદ એન્ટ્રીને પ્રતિસાદ, સાઇઝ અને લેટન્સી સાથે અપડેટ કરવામાં આવે છે.
- **ફરીથી એન્ક્રિપ્ટ કરેલ ફૉર્વર્ડ** (`createForward` / `realForward`): મૂળ
  ગંતવ્ય સુધી ફરીથી એન્ક્રિપ્ટ કરે છે. `rejectUnauthorized`નું ડિફૉલ્ટ મૂલ્ય **`true`** છે (ડિફૉલ્ટ રૂપે
  સુરક્ષિત) — અપસ્ટ્રીમ સર્ટિફિકેટને ક્લાયન્ટ દ્વારા વિનંતી કરાયેલા SNI/Host સામે
  ચકાસવામાં આવે છે, તેથી પ્રૉક્સી બરાબર એ જ નકારે છે જે મૂળ ક્લાયન્ટ નકારત.

### ઍન્ટિ-લૂપ (SO_MARK)

નિયમો નવા સ્થાનિક આઉટબાઉન્ડ કનેક્શનોને ચિહ્નિત કરતા હોવાથી, પ્રૉક્સીનું **પોતાનું**
ફરીથી એન્ક્રિપ્ટ કરેલ ફૉર્વર્ડ સામાન્ય રીતે ફરી ઇન્ટરસેપ્ટ થાય — એટલે અનંત લૂપ બને. ફૉર્વર્ડ
પાથ બાયપાસ સૉકેટ માર્ક (**SO_MARK**) વડે આની સામે રક્ષણ આપે છે:

- `realForward` પોતાનું અપસ્ટ્રીમ સૉકેટ `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  દ્વારા ખોલે છે — `DEFAULT_BYPASS_MARK = 0x539` — જે `connect()` **પહેલાં**
  **SO_MARK** સેટ કરે છે, જેથી ફૉર્વર્ડનું SYN બાયપાસ માર્ક ધરાવે છે.
- `mangle OUTPUT` નિયમ પહેલેથી બાયપાસ માર્ક ધરાવતા કનેક્શનોને બાકાત રાખે છે
  (`-m mark ! --mark <bypassMark>`), તેથી પ્રૉક્સીનું ફૉર્વર્ડ ફરીથી ચિહ્નિત
  **થતું નથી** અને TPROXYમાં ફરી પ્રવેશતું નથી.

> અમલીકરણ નોંધ: બાયપાસ-ચિહ્નિત સૉકેટને એજન્ટના
> `createConnection` પર ઇન્સ્ટૉલ કરવું આવશ્યક છે (`https.request({ createConnection })`ને એજન્ટ
> હાજર હોય ત્યારે કોઈ સૂચના વિના અવગણવામાં આવે છે), નહિતર ફૉર્વર્ડ અચિહ્નિત સૉકેટ ખોલશે અને
> લૂપ પાછું આવશે. આ e2e-ચકાસાયેલ ઍન્ટિ-લૂપ સુધારો હતો.

| **માત્ર લૂપબૅક API**                   | `/api/tools/agent-bridge/tproxy`, `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`) માંના `/api/tools/agent-bridge/` પ્રીફિક્સ હેઠળ આવરી લેવાયેલ છે. લૂપબૅક અમલીકરણ auth **પહેલાં** ચાલે છે (કડક નિયમો #15 + #17) — ટનલ મારફતે લીક થયેલું JWT, TPROXY કૅપ્ચર શરૂ કરી શકતું નથી, જે `iptables` નિયમો લાગુ કરે છે અને ચાઇલ્ડ પ્રોસેસ મારફતે ટ્રસ્ટ-સ્ટોર CA ઇન્સ્ટૉલ કરે છે. |

| **અપસ્ટ્રીમ સર્ટિફિકેટ ચકાસણી**        | ફરીથી એન્ક્રિપ્ટ કરાયેલ ફૉર્વર્ડ, ડિફૉલ્ટ રૂપે અપસ્ટ્રીમ સર્ટિફિકેટની ચકાસણી કરે છે (`rejectUnauthorized: true`).                                                                                                                                                                                                                                                                     |

**MITM CA એક શક્તિશાળી ક્ષમતા છે.** OS દ્વારા વિશ્વસનીય ગણાતું અને કોઈપણ
હોસ્ટ માટે સહી કરી શકતું CA હોવાનો અર્થ એ છે કે OmniRoute જે કંઈ ઇન્ટરસેપ્ટ કરે તેને ડિક્રિપ્ટ કરી શકાય છે. તે
સ્પષ્ટ, માત્ર-લોકલ TPROXY કૅપ્ચર મોડ પાછળ નિયંત્રિત છે, ડિફૉલ્ટ રૂપે બંધ છે અને તમે મોડ
બંધ કરો ત્યારે ટ્રસ્ટ-સ્ટોર એન્ટ્રી દૂર કરવામાં આવે છે.

## §7 ટ્રાન્ઝેક્શનલ ફાયરવૉલ લાગુ કરવું / પાછું ફેરવવું

ક્રેશ થવાથી ક્યારેય કોઈ `mangle` નિયમ અથવા જૂનો રૂટ બાકી રહેવો જોઈએ નહીં. કમાન્ડ બિલ્ડર
(`src/mitm/tproxy/commands.ts`) અને રનર (`src/mitm/tproxy/setup.ts`) ખાતરી આપે છે કે
**પાછું ફેરવવું એ લાગુ કરવાની પ્રક્રિયાનું ચોક્કસ વિપરીત છે અને તે વિપરીત ક્રમમાં થાય છે**.

`applyTproxy(cfg)` લાગુ કરવાના કમાન્ડ્સને ક્રમમાં ચલાવે છે; **કોઈપણ** નિષ્ફળતા આવે ત્યારે તે
શ્રેષ્ઠ પ્રયાસ તરીકે સંપૂર્ણ `revertTproxy(cfg)` ચલાવે છે અને ભૂલને ફરીથી થ્રો કરે છે — તેથી
ફાયરવૉલ કાં તો સંપૂર્ણપણે લાગુ થયેલું હોય છે અથવા સંપૂર્ણપણે પાછું ફેરવાયેલું હોય છે, ક્યારેય
અડધું લાગુ થયેલું નહીં. `revertTproxy(cfg)` વિપરીત કમાન્ડ્સને વિપરીત ક્રમમાં ચલાવે છે અને
નિષ્ફળતાઓને અવગણે છે (આઇડેમ્પોટન્ટ — કોઈ શરત વિના કૉલ કરવું સલામત છે, ઉદાહરણ તરીકે
AgentBridgeના `repairMitm()` ક્લીનઅપમાંથી).

કોઈપણ કમાન્ડ પહેલાં `validateTproxyConfig(cfg)` ચાલે છે: પોર્ટ્સ `1–65535` હોવા જોઈએ,
`mark`/`routeTable`/`bypassMark` ધન પૂર્ણાંકો હોવા જોઈએ અને `bypassMark`, `mark`થી
અલગ હોવું જોઈએ (લૂપ-વિરોધી).

### લાગુ કરવાના કમાન્ડ્સ (ક્રમમાં)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

પાછું ફેરવવાની પ્રક્રિયા તેમને વિપરીત ક્રમમાં કાઢી નાખે છે: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> આ રેસિપી **OUTPUT-આધારિત** છે, કારણ કે MITMનો ઉપયોગ-પ્રસંગ _સ્થાનિક_ આઉટબાઉન્ડ
> ટ્રાફિક (એ જ હોસ્ટ પરની ઍપ્સ) માટે છે, જેને માત્ર `PREROUTING`માં રહેલું TPROXY
> જોઈ શકતું નથી — `PREROUTING` માત્ર ફોરવર્ડ થયેલો ટ્રાફિક જ જુએ છે. `OUTPUT` ચેઇન નવા
> સ્થાનિક કનેક્શન્સને માર્ક કરે છે, `ip rule` તેમને સ્થાનિક ડિલિવરી (`lo`) તરફ ફરી રૂટ કરે છે અને
> ત્યારબાદ `PREROUTING` તેમને ટ્રાન્સપેરન્ટ લિસનરને સોંપે છે.

## §8 કન્ફિગરેશન

સ્ટાર્ટ રિક્વેસ્ટ (`POST /api/tools/agent-bridge/tproxy`) નીચેના ફીલ્ડ્સ સ્વીકારે છે,
જે `StartTproxyBodySchema` (`tproxy/route.ts`) દ્વારા માન્ય કરવામાં આવે છે. બધા વૈકલ્પિક
છે અને આપેલા ન હોય તો તેમના ડિફૉલ્ટ મૂલ્યોનો ઉપયોગ થાય છે:

| ફીલ્ડ            | પ્રકાર             | ડિફૉલ્ટ  | નોંધ                                                                                                                                      |
| ---------------- | ------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`    | ટ્રાન્સપેરન્ટ રીતે ઇન્ટરસેપ્ટ કરવાનો ગંતવ્ય TCP પોર્ટ                                                                                     |
| **mark**         | int (≥1)           | `0x2333` | `OUTPUT` પર સેટ થતું ફાયરવૉલ માર્ક, જેનું `ip rule` + `PREROUTING` દ્વારા મેચિંગ થાય છે                                                   |
| **onPort**       | int (1–65535)      | `8443`   | ટ્રાન્સપેરન્ટ (**IP_TRANSPARENT**) લિસનર જે પોર્ટ સાથે બાઇન્ડ થાય છે                                                                      |
| **routeTable**   | int (≥1)           | `233`    | `local 0.0.0.0/0` રૂટ ધરાવતું પૉલિસી-રાઉટિંગ ટેબલ id                                                                                      |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | પ્રૉક્સી તેના પોતાના અપસ્ટ્રીમ કનેક્શન્સ પર સેટ કરે તે બાયપાસ સૉકેટ માર્ક (**SO_MARK**); `OUTPUT`માંથી બાકાત રાખવામાં આવે છે (લૂપ-વિરોધી) |
| **sudoPassword** | string             | —        | માત્ર નોન-રૂટ ડેસ્કટોપ્સ માટે: ટ્રસ્ટ-સ્ટોર ઇન્સ્ટોલને અધિકૃત કરે છે; રૂટ તરીકે ચાલતી વખતે અવગણવામાં આવે છે                               |

TPROXY માટે **કોઈ એન્વાયર્નમેન્ટ વેરિએબલ્સ નથી** — તમામ કન્ફિગરેશન POST બૉડી અથવા
ઉપર આપેલા ડિફૉલ્ટ્સ દ્વારા થાય છે.

## §9 Traffic Inspectorમાંથી સક્ષમ કરવું

1. **Traffic Inspector** (`/dashboard/tools/traffic-inspector`) ખોલો.
2. કૅપ્ચર-મોડ્સ ટૂલબારમાં **"TPROXY Decrypt"** ⚠ બટન શોધો
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - જો તે "TPROXY decrypt requires Linux + root +
     the native addon" ટૂલટિપ સાથે **નિષ્ક્રિય** હોય, તો આ હોસ્ટ પર નેટિવ ઍડઑન ઉપલબ્ધ નથી (Linux ન હોય,
     ટૂલચેઇન ન હોય અથવા ઍડઑન બિલ્ડ ન થયું હોય). [§2](#2-requirements) અને [§3](#3-the-native-ip_transparent-addon) જુઓ.
3. બટન ક્લિક કરો. તે `startTproxyCaptureMode()` મારફતે
   `POST /api/tools/agent-bridge/tproxy`ને કૉલ કરે છે
   (`src/lib/inspector/tproxyCaptureApi.ts`), જે:
   ડાયનેમિક CA બનાવે છે, ટ્રાન્સપરન્ટ લિસનર ખોલે છે, ફાયરવૉલ
   નિયમો લાગુ કરે છે અને OS ટ્રસ્ટ સ્ટોરમાં CA ઇન્સ્ટૉલ કરે છે.
4. ચાલુ હોય ત્યારે, ટૉગલ એમ્બર રંગનું થાય છે અને લાઇવ ઇન્ટરસેપ્ટ સંખ્યા
   (`· <interceptCount>`) બતાવે છે. ઇન્ટરસેપ્ટ કરેલી રિક્વેસ્ટ્સ રિક્વેસ્ટ સૂચિમાં
   `source: "tproxy"` સાથે દેખાય છે.
5. બંધ કરવા માટે ફરી ક્લિક કરો — `stopTproxyCaptureMode()` મારફતે
   `DELETE /api/tools/agent-bridge/tproxy` લિસનરને બંધ કરે છે, CA અનઇન્સ્ટૉલ કરે છે અને
   ફાયરવૉલ નિયમોને પૂર્વવત્ કરે છે.

કૅપ્ચર-મોડની સ્થિતિ (ચાલુ / ઉપલબ્ધ / ઇન્ટરસેપ્ટ સંખ્યા / લિસનર પોર્ટ)
`GET /api/tools/agent-bridge/tproxy`માંથી આવે છે (`src/mitm/tproxy/captureManager.ts`માં
`getCaptureStatus()`). એક સમયે માત્ર **એક** TPROXY સેશન ચાલે છે —
બીજું શરૂ કરવાનો પ્રયાસ "TPROXY capture mode is already running" સાથે નકારવામાં આવે છે.

## §10 સમસ્યાનિવારણ

### ટૉગલ નિષ્ક્રિય છે

નેટિવ ઍડઑન લોડ થઈ શકતું નથી. ખાતરી કરો: તમે Linux પર છો, તમે ઍડઑન
બિલ્ડ કર્યું છે (`npm run build:native:tproxy`) અને પ્રોસેસ `transparent.node`
લોડ કરી શકે છે. `isTransparentSocketAvailable()` ટૉગલની ઉપલબ્ધતા નિયંત્રિત કરે છે; ઍડઑન ન હોય ત્યારે
`GET /api/tools/agent-bridge/tproxy` `available: false` પરત કરે છે.

### કંઈપણ કૅપ્ચર થતું નથી

- ખાતરી કરો કે ઇન્ટરસેપ્ટ કરેલી પ્રોસેસ ખરેખર કૉન્ફિગર કરેલા `dport`
  (ડિફૉલ્ટ `443`) સાથે કનેક્ટ થાય છે.
- ખાતરી કરો કે પ્રોસેસ ડાયનેમિક CA પર વિશ્વાસ કરે છે. CA
  `omniroute-tproxy-ca.crt` હેઠળ ઇન્સ્ટૉલ થાય છે; પોતાનો ટ્રસ્ટ સ્ટોર ધરાવતી ઍપ્સ (Firefox/Chrome NSS)
  માટે સર્ટિફિકેટ ત્યાં પણ ઉમેરવું પડી શકે છે.
- સર્ટિફિકેટ-વિશ્વસનીયતા / સર્વર
  હેલ્થ ચેક્સ માટે AgentBridge **Diagnose** સ્વ-પરીક્ષણ ચલાવો
  ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md) જુઓ).

### ક્રૅશ પછી રહી ગયેલા ફાયરવૉલ નિયમો

`revertTproxy()` લાગુ કરવાની પ્રક્રિયાનું ચોક્કસ વિપરીત છે અને આઇડેમ્પોટન્ટ છે. મોડ બંધ કરવાથી
નિયમો પૂર્વવત્ થાય છે; જો OmniRoute સેશનની વચ્ચે બંધ થઈ ગયું હોય, તો અનાથ રહી ગયેલી સિસ્ટમ
સ્થિતિ (DNS સ્પૂફ, root CA, સિસ્ટમ પ્રૉક્સી) પૂર્વવત્ કરવા AgentBridge
**Repair** ક્રિયા (`POST /api/tools/agent-bridge/repair`) વાપરો. TPROXY `mangle` નિયમો અને રૂટ પણ
રીબૂટ વખતે આપમેળે ફ્લશ થઈ જાય છે.

### અનંત લૂપ / પ્રૉક્સી પોતાના ફૉર્વર્ડને ઇન્ટરસેપ્ટ કરે છે

આ ઍન્ટિ-લૂપ સ્થિતિ છે. ખાતરી કરો કે `bypassMark`, `mark`થી અલગ છે (વૅલિડેશન
આને ફરજિયાત બનાવે છે) અને ફૉર્વર્ડ `connectMarked`નો ઉપયોગ કરે છે (`realForward`માં તે કરે છે).
[§5 ઍન્ટિ-લૂપ](#anti-loop-so_mark) જુઓ.
