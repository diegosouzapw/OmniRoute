> **છેલ્લે અપડેટ કરેલું:** 2026-08-29 — v3.8.51 (Video Bridge ટ્રાન્સક્રિપ્ટનું મૂળ કૉલર દ્વારા જાહેર કરવામાં આવે છે,
> હજી સર્વર દ્વારા ચકાસાયેલું નથી — #11661 અનુસાર સ્પષ્ટ કરવામાં આવ્યું)

Guardrails, OmniRoute અને અપસ્ટ્રીમ પ્રદાતાઓ વચ્ચેની સીમા પર સુરક્ષા, નીતિ અને કન્ટેન્ટ રૂપાંતરણો લાગુ કરે છે. દરેક guardrail વિનંતીના payloads (`preCall`) અને અપસ્ટ્રીમ પ્રતિસાદો (`postCall`)નું નિરીક્ષણ કરી શકે છે (અને વૈકલ્પિક રીતે તેમને નકારી, રૂપાંતરિત અથવા ઍનોટેટ કરી શકે છે).

સિસ્ટમ **fail-open** છે: જો કોઈ guardrail કાર્યરત હોય ત્યારે અપવાદ ફેંકે, તો registry ભૂલ નોંધે છે અને વિનંતીને નિષ્ફળ કરવાને બદલે આગામી guardrail સાથે ચાલુ રહે છે. બ્લૉક કરવું હંમેશાં સ્પષ્ટ નિર્ણય (`block: true`) હોય છે, ક્યારેય આકસ્મિક ઘટના નહીં.

### વિઝન બ્રિજ (`visionBridge.ts`) — મોડાલિટી બ્રિજ PR-1

**નોન-વિઝન મોડેલ્સ**ને લક્ષ્ય બનાવતી ઇમેજ-બેરિંગ વિનંતીઓને અટકાવે છે અને કાં તો આખી વિનંતીને વિઝન-સક્ષમ મોડેલ પર રીરાઉટ કરે છે અથવા અપસ્ટ્રીમ કૉલ પહેલાં રૂપરેખાંકિત વિઝન મોડેલ દ્વારા ઉત્પાદિત ટેક્સ્ટ વર્ણનો સાથે ઇમેજ ભાગોને બદલે છે. આ ફક્ત-ટેક્સ્ટ પ્રદાતાઓને મલ્ટિમોડલ પેલોડ્સને પારદર્શક રીતે હેન્ડલ કરવાની મંજૂરી આપે છે.

પ્રવાહ:

1.  જો લક્ષ્ય મોડેલ પહેલેથી જ વિઝનને સપોર્ટ કરતું હોય તો છોડી દો (સિવાય કે તે ફરજિયાત-બ્રિજ સૂચિ `isVisionBridgeForcedModel` માં દેખાય).
2.  `extractImageParts(messages)` (`visionBridgeHelpers.ts`) દ્વારા ઇમેજ ભાગોને બહાર કાઢો, જે `open-sse/utils/mediaParts.ts` માં **યુનિફાઇડ મીડિયા ડિટેક્ટર** `detectMediaParts()` ને સોંપે છે — કોમ્બો સુસંગતતા ફિલ્ટર સાથે શેર કરાયેલ સત્યનો એકમાત્ર સ્ત્રોત. નિષ્કર્ષણ `replaceImageParts` પાછા જોડી શકે તેવા આકારોના ટોચના-સ્તરના ભાગોમાં (નિષ્કર્ષણ↔બદલવાનો કરાર) મંજૂર છે: OpenAI `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL `source.type:"url"`, અને Responses API `input_image`. નેસ્ટેડ હિટ્સ અને સૂચક-માત્ર આકારો કોમ્બો-ફિલ્ટર સામગ્રી છે અને ક્યારેય બહાર કાઢવામાં આવતા નથી. જો કોઈ ન મળે તો છોડી દો.
3.  `resolveVisionBridgeRuntimeSettings()` (`src/shared/constants/modalityBridgeDefaults.ts`) દ્વારા રનટાઇમ કન્ફિગને ઉકેલો: નવી `modalityBridge*` સેટિંગ્સ કી જીતે છે; લેગસી `visionBridge*` કી **એક-ચક્ર ફોલબેક** (રોલબેક વિન્ડો) રહે છે. જ્યારે બ્રિજ અક્ષમ હોય ત્યારે કોઈપણ મીડિયા ટ્રાવર્સલ પહેલાં છોડી દો.
4.  મોડ સિલેક્ટર (`modalityBridgeVisionMode`, નીચેનું કોષ્ટક જુઓ) રીરાઉટ વિરુદ્ધ વર્ણન કરવાનું નક્કી કરે છે. રીરાઉટ ફક્ત `model` સ્વેપ કરેલા `modifiedPayload` ને પરત કરે છે, ઉપરાંત મેટા `{ rerouted, fromModel, toModel, imagesKept }`.
5.  વર્ણન પાથ: `maxImages` પર છબીઓને કેપ કરો, કાર્ય-જાગૃત પ્રોમ્પ્ટ કંપોઝ કરો, વર્ણન કેશનો સંપર્ક કરો, વિઝન મોડેલને **સમાંતર** (`Promise.allSettled`) કૉલ કરો, અને તેમના સ્થાને `[Image N]: <description>` ટેક્સ્ટ ભાગો દાખલ કરો. નિષ્ફળ વર્ણન `null` આપે છે અને મૂળ ઇમેજ ભાગ **જાળવી રાખવામાં આવે છે** (#4012) — સિવાય કે કોમ્બો વર્ણન પાથ પર જ્યારે દરેક વર્ણન નિષ્ફળ જાય, જ્યાં પુષ્ટિ થયેલ નોન-વિઝન અપસ્ટ્રીમને તેના બદલે `(unavailable — no vision-capable provider connected)` સ્ટબ મળે છે (#8430).
6.  `modifiedPayload` + મેટા (`imagesProcessed`, `descriptions`, `processingTimeMs`, `visionModel`) પરત કરો.

#### મોડ સિલેક્ટર (`modalityBridgeVisionMode`)

| મોડ        | ડિફોલ્ટ | વર્તન                                                                                                                                                                                                                                                                                                          |
| ---------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | લેગસી હ્યુરિસ્ટિક, અસ્પૃશ્ય (#6640/#7204): નોન-કોમ્બો/`auto`/ મોડેલ્સ શ્રેષ્ઠ વિઝન મોડેલ પર રીરાઉટ થાય છે સિવાય કે મૂળ મોડેલ પાસે પહેલેથી જ ઉપયોગ કરી શકાય તેવી ઓળખપત્રો હોય (પછી વર્ણન કરો); કોમ્બો લક્ષ્યો હંમેશા વર્ણન કરે છે.                                                                              |
| `describe` |         | હંમેશા વર્ણન કરો — રીરાઉટ બ્લોક સંપૂર્ણપણે છોડી દેવામાં આવે છે; વપરાશકર્તા દ્વારા પસંદ કરાયેલ મોડેલ હંમેશા જવાબ આપે છે.                                                                                                                                                                                        |
| `reroute`  |         | ફરજિયાત રીરાઉટ: કીપ-ક્રેડેન્શિયલ-મોડેલ ગાર્ડને બાયપાસ કરવામાં આવે છે. રીરાઉટ-**લક્ષ્ય** ક્રેડેન્શિયલ ગાર્ડ હજુ પણ લાગુ પડે છે — જ્યારે કોઈ ઉપયોગ કરી શકાય તેવું વિઝન લક્ષ્ય અસ્તિત્વમાં ન હોય, ત્યારે વિનંતી વર્ણન કરવા માટે પસાર થાય છે જેથી કાચી છબીઓ ક્યારેય ફક્ત-ટેક્સ્ટ બેકએન્ડ સુધી પહોંચે નહીં (#8430). |

ફરજિયાત મોડ્સ ઓટો હ્યુરિસ્ટિક ચાલે તે **પહેલાં** શોર્ટ-સર્કિટ થાય છે; `auto` વર્તન PR-1 પહેલાંના ગાર્ડ્રેલ જેવું જ બાઇટ-આઇડેન્ટિકલ છે.

#### કાર્ય-જાગૃત વર્ણન પ્રોમ્પ્ટ (`modalityBridgeVisionTaskAware`)

ડિફોલ્ટ **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) **છેલ્લા વપરાશકર્તા સંદેશ** (500 અક્ષરો સુધી ટૂંકા કરાયેલ) ના ટેક્સ્ટને મૂળ વર્ણન પ્રોમ્પ્ટમાં ઉમેરે છે, વર્ણનને વપરાશકર્તાએ ખરેખર શું પૂછ્યું હતું (કોડેક્સ-વિઝન-પ્રોક્સી પેટર્ન) તે તરફ દોરે છે અને વિઝન મોડેલને દૃશ્યમાન ટેક્સ્ટને ટ્રાન્સક્રાઇબ કરવા કહે છે. ફ્લેગ બંધ હોય — અથવા કોઈ વપરાશકર્તા ટેક્સ્ટ ન હોય — ત્યારે મૂળ પ્રોમ્પ્ટ યથાવત ઉપયોગમાં લેવાય છે.

વર્ણન સેલ્ફ-લૂપની પોતાની OpenAI-સુસંગત વિનંતી (`visionBridgeHelpers.ts` માં `callVisionModelSingle()`) હંમેશા `image_url.detail: "high"` ની વિનંતી કરે છે — બિનશરતી, દરેક કોલર/પ્રોવાઇડર માટે, કોઈપણ ક્લાયન્ટ સિગ્નલ પર આધારિત નથી. ઓછી-વિગતવાર સેમ્પલિંગ OCR ચોકસાઈને બગાડે છે, ખાસ કરીને આ પ્રોમ્પ્ટ દ્વારા માંગવામાં આવેલા ટેક્સ્ટ-ટ્રાન્સક્રિપ્શન કાર્ય માટે, તેથી વર્ણન કૉલ પોતે હંમેશા ઉચ્ચ વિગતો માંગે છે, ભલે મૂળ ઇનબાઉન્ડ વિનંતીમાં કયા વિગત સ્તરનો ઉપયોગ થયો હોય. આ ફક્ત આંતરિક વર્ણન વિનંતી બોડીને અસર કરે છે; તે OmniRoute કેવી રીતે કોલરના પોતાના `image_url.detail` ને પ્રાથમિક વિનંતી પર ફોરવર્ડ કરે છે તેમાં ફેરફાર કરતું નથી — તે ડિફોલ્ટ અલગથી લાગુ પડે છે, અને ફક્ત શોધાયેલા OpenCode ક્લાયન્ટ્સ માટે, `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) માં. વર્ણન સેલ્ફ-લૂપની Anthropic વાયર-ફોર્મેટ શાખામાં કોઈ `detail` ફિલ્ડ નથી અને તે કોઈપણ ડિફોલ્ટથી અપ્રભાવિત છે.

#### વર્ણન આઉટપુટ કેપ (`modalityBridgeVisionMaxChars`)

| Key                            | Default | Range            |
| ------------------------------ | ------- | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`     | `0` or 100–50000 |

`0` (ડિફોલ્ટ) નો અર્થ છે **કોઈ કેપ નથી** — `callVisionModel()` દ્વારા પરત કરાયેલ વર્ણન યથાવત પસાર થાય છે, હાલના વર્તનને જાળવી રાખે છે. 100–50000 રેન્જમાં કોઈપણ મૂલ્ય વર્ણનને `…` સફિક્સ સાથે ટૂંકાવે છે તે પહેલાં તેને `[Image N]: <description>` (`src/lib/guardrails/visionBridge.ts` માં `VisionBridgeGuardrail.preCall()`) તરીકે પાછું જોડવામાં આવે છે. વિગત-ભારે OCR કાર્યો માટે આને વધારો જ્યાં ડાઉનસ્ટ્રીમ મોડેલને સંપૂર્ણ ટ્રાન્સક્રિપ્શનની જરૂર હોય; ચેટ્ટી વિઝન મોડેલ્સ પર ટોકન વપરાશને મર્યાદિત કરવા માટે તેને ઘટાડો. ડેશબોર્ડ ફિલ્ડ વિઝન ટેબના એડવાન્સ્ડ પેનલ પર રહે છે (`ModalityBridgeVisionTab.tsx` માં `modality-bridge-max-chars`) અને 1 થી 99 વચ્ચેના કોઈપણ મૂલ્યને 100 ફ્લોર સુધી ક્લેમ્પ કરે છે જ્યારે સ્પષ્ટ `0` ને અસ્પૃશ્ય છોડી દે છે — `0` તેના પોતાના અધિકારમાં એક માન્ય Zod મૂલ્ય છે (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), માત્ર "અનસેટ" ડિફોલ્ટ નથી.

#### વર્ણન કેશ (`modalityBridge/bridgeCache.ts`)

વર્ણન આઉટપુટ માટે ઇન-મેમરી LRU + TTL કેશ, પ્રક્રિયા-વ્યાપી શેર કરેલ.
Key = `sha256(imageRef + composedPrompt + configuredBridgeModel)` લંબાઈ-પ્રીફિક્સ ફ્રેમિંગ સાથે (કોઈ ફિલ્ડ-બાઉન્ડ્રી અથડામણ નથી). મોડેલ ઘટક એ **કન્ફિગર કરેલ** બ્રિજ મોડેલ છે, તે મોડેલ નથી જેણે ખરેખર જવાબ આપ્યો — `callVisionModel` આંતરિક રીતે પાછળ પડી શકે છે, અને દરેક પ્રયાસ દીઠ કીઇંગ કેશને વિભાજિત કરશે. નિષ્ફળ વર્ણનો ક્યારેય કેશ થતા નથી. સેટિંગ્સ:

| Key                             | Default | Range   |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### રિમોટ ઇમેજ નોર્મલાઇઝેશન (સેલ્ફ-લૂપ વર્ણન/base64 ફેચ)

જ્યારે બ્રિજ પોતે **રિમોટ** ઇમેજ ફેચ કરે છે — Anthropic વર્ણન સેલ્ફ-કોલ અને claude-વાયર-ફોર્મેટ base64 રૂપાંતરણ (`ensureBase64ImagesForClaudeWire`), બંને `visionBridgeHelpers.ts` માં `fetchRemoteImageAsDataUri()` દ્વારા — પરિણામી ડેટા URI ને વિઝન-મોડેલ વિનંતીમાં એમ્બેડ કરતા પહેલા `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) દ્વારા પસાર કરવામાં આવે છે. ઓવરસાઇઝ્ડ ઇમેજીસને **2048px લાંબી ધાર** સુધી ડાઉનસ્કેલ કરવામાં આવે છે (OpenAI/Anthropic સર્વર-સાઇડ પહેલેથી જ લાગુ કરે છે તે રિસાઇઝ કેપ સાથે મેળ ખાય છે), જે વિઝન મોડેલ જે જુએ છે તેને બદલ્યા વિના અપલોડ બાઇટ્સ/લેટન્સી ઘટાડે છે. રિસાઇઝિંગ `sharp` નો ઉપયોગ કરે છે, જે ડાયનેમિક ઇમ્પોર્ટ દ્વારા લોડ થાય છે: એવા પ્લેટફોર્મ પર જ્યાં તેની નેટિવ બાઇનરી લોડ થવામાં નિષ્ફળ જાય છે, `normalizeDataUri()` **ક્યારેય ભૂલ ફેંકતું નથી** — તે મૂળ બાઇટ્સના પાસથ્રુ પર પાછું ફરે છે, જેથી વર્ણન/base64-રૂપાંતરણ પાથ હંમેશા કાર્યરત રહે છે. નોન-ઇમેજ બાઇટ્સ (એક ફેચ જે ડીકોડ કરી શકાય તેવી ઇમેજ પરત કરતું નથી) પણ અસ્પૃશ્ય પસાર થાય છે. આ નોર્મલાઇઝેશન બ્રિજ તેના પોતાના સેલ્ફ-કોલ માટે ફેચ કરે છે તે ઇમેજીસ સુધી મર્યાદિત છે — તે કોલરના કાચા પાસથ્રુ પેલોડ પર ક્યારેય લાગુ પડતું નથી, જે ઓપ્ટ-ઇન-ઓન્લી મ્યુટેશન સિદ્ધાંત (હાર્ડ રૂલ #20) સાથે સુસંગત છે.

#### સેટિંગ્સ સ્કીમા + માઇગ્રેશન

નવી `modalityBridge*` કીઝ `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`) માં Zod-વેલિડેટેડ છે: `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCache*` ત્રિપુટી, અને Audio Bridge દ્વારા ઉપયોગમાં લેવાતો `modalityBridgeAudio*` જૂથ. માઇગ્રેશન `141_modality_bridge_settings.sql` હાલના લેગસી `visionBridge*` મૂલ્યોને મેચિંગ નવી કીઝમાં કોપી કરે છે (આઇડેમ્પોટન્ટ, ઓપરેટર-સેટ `modalityBridge*` મૂલ્યને ક્યારેય ઓવરરાઇટ કરતું નથી); લેગસી કીઝ એક રિલીઝ સાયકલ માટે રીડ ફોલબેક તરીકે સ્વીકૃત રહે છે.

#### પારદર્શિતા હેડર + આંકડા

વર્ણન-રૂપાંતરિત પ્રતિભાવો `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` ધરાવે છે (જે `modalityBridge/bridgeStats.ts` માં `buildModalityBridgeHeader()` દ્વારા બનાવવામાં આવે છે, `src/sse/handlers/chatHelpers.ts` માં `withModalityBridgeHeader()` દ્વારા સ્ટેમ્પ કરવામાં આવે છે). રીરાઉટ કરેલી વિનંતીઓને **કોઈ** હેડર મળતું નથી — પેલોડ અસ્પૃશ્ય હતો અને મોડેલ સ્વેપ પ્રતિભાવ બોડીના `model` ફિલ્ડમાં પહેલેથી જ દૃશ્યમાન છે.

`GET /api/modality-bridge/stats` (મેનેજમેન્ટ ઓથ, `GET /api/settings` જેવું જ સ્તર) `vision`, `audio`, અને `video` માટે ઇન-મેમરી પ્રતિ-મોડાલિટી કાઉન્ટર્સ `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` પરત કરે છે. `averageLatencyMs` તેના છેદ તરીકે `latencySamples` નો ઉપયોગ કરે છે, બધા પ્રયાસોનો નહીં; સમય વિનાની કામગીરી શૂન્ય-મિલિસેકન્ડ નમૂના બનાવતી નથી. `bridged` સફળ રૂપાંતરણો માટે બેકવર્ડ-કોમ્પેટીબલ ઉપનામ રહે છે; નિષ્ફળ પ્રયાસો તેને વધારતા નથી. કાઉન્ટર્સ ડિઝાઇન દ્વારા પ્રક્રિયા પુનઃપ્રારંભ પર રીસેટ થાય છે (ટેલિમેટ્રી, એકાઉન્ટિંગ નહીં).

#### ડેશબોર્ડ કન્ફિગરેશન

સમર્પિત ડેશબોર્ડ પૃષ્ઠ `/dashboard/settings/modality-bridge` છે. તેના URL-એડ્રેસેબલ `Vision`, `Audio`, અને `Video` ટેબ્સ `tab` મૂલ્ય સ્વિચ કરતી વખતે ક્વેરી પેરામીટર્સ જાળવી રાખે છે. વિઝન ટેબ સક્ષમતા, મોડ, મોડેલ પસંદગી (સ્વચાલિત ડિફોલ્ટ સહિત), કાર્ય-જાગૃત પ્રોમ્પ્ટિંગ, અદ્યતન ટાઈમઆઉટ/ઈમેજ/વર્ણન-લંબાઈ/કેશ મર્યાદાઓ, રનટાઈમ કાઉન્ટર્સ અને સુરક્ષિત નમૂના વિનંતીને ખુલ્લી પાડે છે. ઑડિયો ટેબ પણ લાઇવ છે: તે સક્ષમતા, ઑટો સાથે STT-માત્ર મોડેલ પીકર, ટાઈમઆઉટ/મહત્તમ-ક્લિપ મર્યાદાઓ, ઑડિયો કાઉન્ટર્સ અને `input_audio` નમૂના પરીક્ષણને ખુલ્લી પાડે છે. વિડિઓ ટેબ કાર્યરત છે: તે FFmpeg/ffprobe રનટાઈમ સ્થિતિની જાણ કરે છે — ચાર સ્પષ્ટ UI સ્થિતિઓમાંથી એક (`unknown` જ્યારે પ્રોબ ચાલી રહ્યું હોય અથવા પૂર્ણ ન થઈ શકે, `restricted` નોન-લૂપબેક ડેશબોર્ડ હોસ્ટ પર જ્યાં પ્રોબ ક્લાયંટ-સાઇડ છોડવામાં આવે છે, `unavailable` એકવાર પ્રોબ કર્યા પછી અને ગુમ થયેલ હોવાની પુષ્ટિ થાય, અથવા FFmpeg/ffprobe વર્ઝન સાથે `available`) — સક્ષમ/મોડેલ/ફ્રેમ/વિડિઓ/ટાઈમઆઉટ મર્યાદાઓ જાળવી રાખે છે, મોડેલ પીકરને વિઝન-સક્ષમ મોડેલ્સ પર ફિલ્ટર કરે છે, અને વિડિઓ કાઉન્ટર્સને ખુલ્લા પાડે છે.

AI સેટિંગ્સ હેઠળનું ભૂતપૂર્વ વિઝન બ્રિજ કાર્ડ નવા પૃષ્ઠની સુસંગતતા લિંક છે; તે હવે ફોર્મની બીજી નકલ ધરાવતું નથી. મીડિયા પ્રોવાઈડર્સ હાલના સ્પીચ-ટુ-ટેક્સ્ટ પ્લેગ્રાઉન્ડને દૂર કર્યા વિના ઇમેજ-ટુ-ટેક્સ્ટ અને સ્પીચ-ટુ-ટેક્સ્ટ વર્કફ્લોને અનુરૂપ મોડાલિટી બ્રિજ ટેબ્સ સાથે પણ જોડે છે.

**સેલ્ફ-લૂપ એડમિશન બાયપાસ:** જ્યારે વર્ણન કૉલ OmniRoute ના પોતાના `/v1` સેલ્ફ-લૂપ (નોન-સ્ટાન્ડર્ડ પ્રોવાઈડર મોડેલ) દ્વારા રૂટ થાય છે, ત્યારે સબ-રિક્વેસ્ટ `x-omniroute-admission-bypass: internal` મોકલે છે અને રિઝોલ્વ્ડ સેલ્ફ-લૂપ ક્રેડેન્શિયલ સાથે પ્રમાણિત થાય છે — સ્થાનિક મોડમાં સ્થાનિક `sk_omniroute` સેન્ટિનેલ, અથવા ઑપરેટર-કન્ફિગર કરેલ `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env કી (#1350) જેથી `REQUIRE_API_KEY=true` ડિપ્લોયમેન્ટ્સ હજુ પણ વર્ણન કૉલ ચલાવી શકે. બાયપાસ ફક્ત તે ચોક્કસ ક્રેડેન્શિયલ્સ માટે જ માન્ય છે, તેથી બાહ્ય ક્લાયંટ્સ એડમિશન છોડવા માટે હેડરનો ઉપયોગ કરી શકતા નથી.

લેગસી ડિફોલ્ટ્સ `src/shared/constants/visionBridgeDefaults.ts` માં રહે છે; નવા મોડ/ટાસ્ક-અવેર/કેશ ડિફોલ્ટ્સ અને સેટિંગ્સ રિઝોલ્વર `src/shared/constants/modalityBridgeDefaults.ts` માં રહે છે. ગાર્ડ્રેલ `deps` કન્સ્ટ્રક્ટર વિકલ્પને ખુલ્લો પાડે છે જેથી પરીક્ષણો નકલી `getSettings` અને `callVisionModel` અમલીકરણોને ઇન્જેક્ટ કરી શકે.

### ઑડિયો બ્રિજ (`audioBridge.ts`) — મોડાલિટી બ્રિજ PR-3

ઑડિયો-બેરિંગ ચેટ વિનંતીઓને તે લક્ષ્ય સુધી પહોંચતા પહેલા અટકાવે છે જે ઑડિયો ઇનપુટ સ્વીકારવા માટે જાણીતું નથી. તે ક્યારેય ચેટ વિનંતીને રીરૂટ કરતું નથી: ઑડિયો ભાગો હાલના OpenAI-સુસંગત મલ્ટિપાર્ટ એન્ડપોઇન્ટ દ્વારા ટ્રાન્સક્રાઇબ કરવામાં આવે છે અને પસંદ કરેલ ચેટ મોડેલ ટેક્સ્ટ ટ્રાન્સક્રિપ્ટ્સ સાથે ચાલુ રહે છે.

પ્રવાહ:

1. `getResolvedModelCapabilities()` દ્વારા `supportsAudio` ને રિઝોલ્વ કરો. સ્પષ્ટ પ્રદાતા-રજિસ્ટ્રી મેટાડેટા જીતે છે, પછી સ્થિર મોડેલ મેટાડેટા, પછી સિંક કરેલ `modalities_input`. `audio` વિનાની જાહેર કરેલ ઇનપુટ સૂચિ `false` છે; કોઈ ક્ષમતાનો પુરાવો `null` રહેતો નથી. `false` અને `null` બંને કન્ઝર્વેટિવ બ્રિજને સક્રિય કરે છે, જ્યારે `true` તેને બાયપાસ કરે છે.
2. `modalityBridgeAudio*` સેટિંગ્સને રિઝોલ્વ કરો અને શેર કરેલ `detectMediaParts()` ડિટેક્ટર દ્વારા દરેક સંદેશમાંથી સ્પ્લાઈસેબલ ટોપ-લેવલ ઑડિયો ભાગોને બહાર કાઢો. સપોર્ટેડ વાયર શેપ્સ OpenAI `input_audio`, `audio_url`, અને `source.media_type: "audio/*"` છે. નેસ્ટેડ ઑડિયો રૂટિંગ માટે શોધાય છે પરંતુ સ્પ્લાઈસ પાથ દ્વારા દૂર કરવામાં આવતો નથી. કાર્ય `modalityBridgeAudioMaxClips` દ્વારા મર્યાદિત છે; પછીના ભાગો અસ્પૃશ્ય રહે છે.
3. કન્ફિગર કરેલ `provider/model` ને માન આપો, અથવા `selectAudioBridgeModel()` ને સ્થિર કેટલોગ ક્રમમાં `AUDIO_TRANSCRIPTION_PROVIDERS` માં ચાલવા દો અને ઉપયોગી સક્રિય પ્રદાતા ક્રેડેન્શિયલ સાથેનું પ્રથમ મોડેલ પસંદ કરવા દો.
4. `callAudioTranscription()` base64/ડેટા-URI ઑડિયોને મલ્ટિપાર્ટ `file` માં રૂપાંતરિત કરે છે, અથવા DNS પિનિંગ અને 25 MB બાઉન્ડ સાથે પબ્લિક-ઓન્લી આઉટબાઉન્ડ ગાર્ડ દ્વારા રિમોટ `audio_url` ડાઉનલોડ કરે છે. તે પછી ફાઇલ અને પસંદ કરેલ મોડેલને સ્થાનિક `/v1/audio/transcriptions` સેલ્ફ-લૂપ પર POST કરે છે, જે `resolveSelfLoopBearer()` સાથે પ્રમાણિત થાય છે. હાલનો ટ્રાન્સક્રિપ્શન રૂટ સામાન્ય ક્રેડેન્શિયલ લુકઅપ, કૂલડાઉન/રેટ-લિમિટ હેન્ડલિંગ અને પ્રદાતા ડિસ્પેચ કરે છે.
5. સફળ કૉલ્સ તેમના ભાગોને `[Audio N]: <transcript>` સાથે બદલે છે. કૉલ્સ `Promise.allSettled` સાથે ચાલે છે: વ્યક્તિગત નિષ્ફળતા તે મૂળ ઑડિયો ભાગને જાળવી રાખે છે (#4012 કરાર). જો દરેક કૉલ નિષ્ફળ જાય અને લક્ષ્ય `supportsAudio === false` સાબિત થાય, તો ભાગો `[Audio N]: (unavailable — no STT provider connected)` (#8430 કરાર) બની જાય છે. અજાણ્યા લક્ષ્ય (`null`) માટે, સર્વ-નિષ્ફળતા પરિણામ અસ્પૃશ્ય રહે છે. ઉપયોગી STT ક્રેડેન્શિયલ વિનાનું સાબિત ટેક્સ્ટ-ઓન્લી લક્ષ્ય નેટવર્ક કૉલ કર્યા વિના સમાન સ્પષ્ટ સ્ટબ મેળવે છે.

સફળ ટ્રાન્સક્રિપ્ટ્સ પ્રક્રિયા-વ્યાપી મોડાલિટી બ્રિજ LRU/TTL કેશનો ઉપયોગ કરે છે. કી ઑડિયો સંદર્ભ, સ્થિર `audio-transcription` ઑપરેશન લેબલ અને પસંદ કરેલ STT મોડેલને જોડે છે; નિષ્ફળતાઓને ક્યારેય કેશ કરવામાં આવતી નથી. ઑડિયો પ્રયાસો શેર કરેલ `bridged`, `cacheHits`, `failures`, અને `lastUsedAt` કાઉન્ટર્સને અપડેટ કરે છે. રૂપાંતરિત પ્રતિભાવો `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ધરાવે છે; અસ્પૃશ્ય વિનંતીઓને ઑડિયો બ્રિજ સેગમેન્ટ મળતો નથી.

રનટાઈમ સેટિંગ્સ DB-બેક્ડ અને Zod-માન્ય છે:

| Key                           | Default | Range          |
| ----------------------------- | ------- | -------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —              |
| `modalityBridgeAudioModel`    | `""`    | Auto or STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000    |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10           |

શેર કરેલ કેશ `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, અને `modalityBridgeCacheMaxEntries` દ્વારા નિયંત્રિત રહે છે.

### વિડિઓ બ્રિજ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ચેટ કમ્પ્લીશન્સ `messages` અને રિસ્પોન્સ API `input` માં ટોચના સ્તરના વિડિયો ભાગોને લક્ષ્ય પહેલાં અટકાવે છે જેમાં મૂળ વિડિયો સપોર્ટ નથી.
સપોર્ટેડ આકારો `input_video`, `video_url`, `video_source`, HTTPS URLs,
અને `data:video/*;base64,...` ડેટા URIs છે. ટેક્સ્ટમાં સાદા ફાઇલનામોને વિડિયો તરીકે ગણવામાં આવતા નથી.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) વિનંતી ટ્રેવર્સલ,
ક્ષમતા/નીતિ તપાસ, પ્રતિ-વિનંતી એકત્રીકરણ અને પ્રતિભાવ પેલોડની માલિકી ધરાવે છે.
પ્રતિ-વિડિયો કાર્ય — પ્રાપ્તિ, સંપૂર્ણ-પરિણામ કેશ, ફ્રેમ સિક્વન્સનું વર્ણન
(જે કોઈપણ કોલર-ઘોષિત ઑડિઓ ટ્રાન્સક્રિપ્ટને ફ્યુઝ કરે છે), અને પ્રતિ-પ્રયાસ મેટ્રિક્સ/એબોર્ટ/ક્લીનઅપ —
`preCall` ના લૂપની અંદર પ્રતિ વિડિયો ભાગ એકવાર બોલાવવામાં આવતા `videoBridgePipeline.ts` માં `processVideoPart` પાછળ છુપાયેલું છે.
તે મોડ્યુલ સ્પષ્ટ પોર્ટ સીમાઓ `VideoMediaBrokerPort` (બાઇટ્સ મેળવવા અને નમૂનાવાળી ફ્રેમ્સ કાઢવા),
`VideoAudioTranscriptionPort` (કોલર-ઘોષિત ઑડિઓ ટ્રાન્સક્રિપ્ટને નમૂનાવાળી કૅપ્શન્સ સાથે ફ્યુઝ કરવું), અને
`VideoDrilldownPort` (ફ્રેમ ડ્રિલ-ડાઉન પર્સિસ્ટન્સ સીમા; હજુ સુધી `processVideoPart` માં વાયર થયેલ નથી —
આજે ફક્ત અલગ `/api/modality-bridge/video/drilldown` રૂટ ડ્રિલ-ડાઉન એન્ટ્રીઓ લખે છે) ને પણ વ્યાખ્યાયિત કરે છે.

સાર્વજનિક `/v1` વિનંતી પાથ ક્યારેય સબપ્રોસેસને આયાત કરતો નથી અથવા બોલાવતો નથી.
રિમોટ વિડિયો 50 MiB બાઉન્ડ હેઠળ ડાઉનલોડ થાય છે; ઇનલાઇન બેઝ64 વિડિયોમાં
પ્રતિ-વિડિયો 36 MiB ડીકોડેડની રૂઢિચુસ્ત મર્યાદા હોય છે જેથી મોડેલ/મેસેજીસ/ફ્રેમિંગ એન્વેલપ
50 MiB ની સાર્વજનિક JSON વિનંતી પ્રવેશ મર્યાદાની અંદર રહી શકે.
ઇનલાઇન લંબાઈ અને ડીકોડેડ-સાઇઝના અંદાજો ફાળવણી પહેલાં તપાસવામાં આવે છે.
પ્રારંભિક રિમોટ URL અને દરેક રીડાયરેક્ટ પર HTTPS જરૂરી છે,
DNS પિનિંગ સાથે હાલના સાર્વજનિક-માત્ર આઉટબાઉન્ડ ગાર્ડનો ઉપયોગ કરીને.
પછી બાઇટ્સ ચોક્કસ આંતરિક `POST /api/modality-bridge/video/extract` બ્રોકર સીમાને પાર કરે છે.
તે રૂટ `LOCAL_ONLY` અને `SPAWN_CAPABLE` બંને છે,
ફક્ત પ્રતિ-પ્રક્રિયા પ્રમાણિત, વિશ્વસનીય-લૂપબેક વિનંતી સ્વીકારે છે,
અને ક્યારેય URL, ફાઇલસિસ્ટમ પાથ, એક્ઝેક્યુટેબલ અથવા આર્ગ્યુમેન્ટ સૂચિ સ્વીકારતો નથી.
API બોડી-સાઇઝ પાઇપલાઇન અને હેન્ડલરનો ઇન્ક્રીમેન્ટલ બોડી રીડર સ્વતંત્ર રીતે 50 MiB બ્રોકર ઇનપુટ મર્યાદા લાગુ કરે છે.
તેની બાઉન્ડેડ કતાર એક સમયે એક નિષ્કર્ષણ ચલાવે છે, ચાર બાકી નોકરીઓને મંજૂરી આપે છે,
અને બાકી ઇનપુટને 100 MiB પર મર્યાદિત કરે છે.

બ્રોકરની અંદર, `ffprobe` એક ખાનગી સ્થાનિક ફાઇલ વાંચે છે;
નિશ્ચિત ફોર્મેટ એલોલિસ્ટ પ્લેલિસ્ટ અને મેનિફેસ્ટ ફોર્મેટને બાકાત રાખે છે.
મંજૂર MOV-ફેમિલી કન્ટેનર માટે, બાહ્ય MOV ડેટા સંદર્ભો ડિફોલ્ટ રૂપે અક્ષમ રહે છે,
અને નિશ્ચિત આદેશ તેમને પસંદ કરતો નથી.
`ffprobe` અને `ffmpeg` બંને `file`-માત્ર પ્રોટોકોલ વ્હાઇટલિસ્ટ, એક થ્રેડ,
નિશ્ચિત આર્ગ્યુમેન્ટ એરે, કોઈ શેલ નહીં, અને `PATH` માંથી ઉકેલાયેલા એક્ઝેક્યુટેબલ્સનો ઉપયોગ કરે છે.
જોડાયેલ-ચિત્ર કવર સ્ટ્રીમ્સ પ્લે કરી શકાય તેવા ઉમેદવારો નથી.
બધી પ્લે કરી શકાય તેવી સ્ટ્રીમ્સ મર્યાદાઓને સંતોષવી જોઈએ,
અને નિશ્ચિત નીચલા-ઇન્ડેક્સ ફોલબેક પહેલાં સ્પષ્ટ ડિફોલ્ટ સ્ટ્રીમને પ્રાધાન્ય આપવામાં આવે છે.
વિડિયો 600 સેકન્ડ, પ્રતિ પરિમાણ 8,192 પિક્સેલ, અને 33,554,432 સ્રોત પિક્સેલ સુધી મર્યાદિત છે.
FFmpeg 1-16 મધ્યબિંદુ JPEG ફ્રેમ્સનું નમૂના લે છે,
નાના ઇનપુટ્સને અપસ્કેલ કર્યા વિના લાંબી ધારને વધુમાં વધુ 1,024 પિક્સેલ સુધી ઘટાડે છે,
અને ક્યારેય URL પ્રાપ્ત કરતું નથી.
નમૂના લેવાનું ડિફોલ્ટ રૂપે `uniform` છે.
વૈકલ્પિક `scene_aware` અને પ્રાયોગિક `segment_aware` નીતિઓ
પહેલેથી જ માન્ય સ્થાનિક સ્ટ્રીમ પર એક વધારાનો નિશ્ચિત FFmpeg પાસ કરે છે,
બાઉન્ડેડ `showinfo` દ્રશ્ય ટાઇમસ્ટેમ્પ્સ પસંદ કરે છે,
અને ડિટેક્ટર નિષ્ફળતા, સમયસમાપ્તિ, ખોટા આઉટપુટ અથવા ખાલી ઉમેદવાર સેટ પર
સમાન યુનિફોર્મ મધ્યબિંદુઓ પર નિર્ણાયક રીતે પાછા ફરે છે.
સેગમેન્ટ-અવેર મોડ માન્ય દ્રશ્ય અંતરાલોના પ્રમાણમાં મધ્યબિંદુ નમૂનાઓ ફાળવે છે;
સેગમેન્ટ-અવેર પુરાવા અને ફોલબેક વર્તન નીચે વિગતવાર છે.
દરેક નીતિમાં પસંદગી પછી સખત 16-ફ્રેમ કેપ લાગુ કરવામાં આવે છે.
જ્યારે દ્રશ્ય-અવેર વિનંતીમાં ફક્ત એક-ફ્રેમ બજેટ હોય છે,
ત્યારે તે સક્રિય સંપૂર્ણ-વિડિયો અથવા ફોકસ વિન્ડોના યુનિફોર્મ મધ્યબિંદુનો ઉપયોગ કરે છે
અને `policyEffective: uniform` રિપોર્ટ કરે છે:
એક પસંદ કરેલી દ્રશ્ય ફ્રેમ બંને ટેમ્પોરલ છેડાને સાચવી શકતી નથી.
કોલર વૈકલ્પિક રીતે મર્યાદિત ફોકસ વિન્ડો (`start`/`end` સેકન્ડ) પ્રદાન કરી શકે છે;
બાઉન્ડ્સ મીડિયા અવધિ સુધી ક્લેમ્પ કરવામાં આવે છે,
ઉલટાવેલી અથવા બિન-મર્યાદિત વિન્ડોઝ નકારવામાં આવે છે,
અને બધી નમૂના લેવાની નીતિઓ ફક્ત સામાન્યકૃત અંતરાલની અંદર જ કરવામાં આવે છે.
પરિણામી વિન્ડો નમૂના લેવાના મેટાડેટામાં અને અવિશ્વસનીય વર્ણન ઉપસર્ગમાં શામેલ છે
જેથી ડાઉનસ્ટ્રીમ મોડેલો સંપૂર્ણ સમયરેખામાંથી કેન્દ્રિત અંશને અલગ પાડી શકે.

સિમેન્ટીક કૅપ્શન ફોકસ એક અલગ, સ્પષ્ટ સેટિંગ છે.
ડિફોલ્ટ `full` વિશ્લેષણ મોડ હાલના ફ્રેમ પ્રોમ્પ્ટને સાચવે છે
અને ક્યારેય વિનંતી ટેક્સ્ટને કૅપ્શન મોડેલ પર ફોરવર્ડ કરતું નથી.
`focused` મોડમાં, બ્રિજ સમાન ચેટ અથવા રિસ્પોન્સ કન્ટેનરમાંથી
ફક્ત નવીનતમ બિન-ખાલી વપરાશકર્તા-લેખિત `text`/`input_text` વાંચે છે,
તેને NFC માં સામાન્યકૃત કરે છે, નિયંત્રણ અક્ષરો અને ખાલી જગ્યાને સંકુચિત કરે છે,
અને તેને 500 યુનિકોડ કોડ પોઇન્ટ્સ સુધી મર્યાદિત કરે છે.
ખાલી પરિણામ ચોક્કસ `full` પ્રોમ્પ્ટ પર પાછું ફરે છે.
એક ઉપયોગી સંકેત સમર્પિત અવિશ્વસનીય-વપરાશકર્તા-સંદર્ભ બ્લોકમાં JSON તરીકે સીરીયલાઇઝ કરવામાં આવે છે
અને ફક્ત અવલોકન કરી શકાય તેવી વિગતોને પ્રાધાન્ય આપી શકે છે;
તે મીડિયામાં દૃશ્યમાન અથવા શ્રાવ્ય સૂચનાઓને અનુસરવા સામેની અલગ ચેતવણીને ઓવરરાઇડ કરી શકતું નથી.
ટેક્સ્ચ્યુઅલ ફોકસ ક્યારેય `start`/`end` ને અનુમાન કરતું નથી અથવા ટેમ્પોરલ સેમ્પલરને બદલતું નથી.

#### FU-07 માળખાકીય સેગમેન્ટ પુરાવા

`segment_aware` પહેલેથી જ માન્ય સ્થાનિક વિડિયો સ્ટ્રીમ પર એક બાઉન્ડેડ પૂર્વ-વિશ્લેષણ પાસનો ઉપયોગ કરે છે.
નિશ્ચિત ફિલ્ટર ચેઇન પ્રથમ વધુમાં વધુ 320 પિક્સેલ પહોળી થાય છે,
દ્રશ્ય ફેરફારો અને સ્થિર અંતરાલોને શોધી કાઢે છે,
પછી બ્લર, સરેરાશ લ્યુમા અને અવકાશી/ટેમ્પોરલ માહિતી માટે પ્રતિ સેકન્ડ 1 ફ્રેમ પર નમૂના લે છે.
પાસ 600 માળખાકીય નમૂનાઓ, એક FFmpeg/ફિલ્ટર થ્રેડ,
સમાન `file`-માત્ર પ્રોટોકોલ અને કન્ટેનર એલોલિસ્ટ્સ,
1 MiB પ્રક્રિયા-આઉટપુટ બાઉન્ડ,
અને બ્રોકરના શેર કરેલા એબોર્ટ/ડેડલાઇનની અંદર વધુમાં વધુ 30 સેકન્ડ સુધી મર્યાદિત છે.
તે ક્યારેય વિનંતીમાંથી આદેશ, ફિલ્ટર, પાથ અથવા URL સ્વીકારતું નથી.

માળખાકીય મૂલ્યો નિર્ધારિત સેમ્પલિંગ પુરાવા છે, સિમેન્ટીક વિડિયો સમજણ નથી. તેઓ વિષયો, ક્રિયાઓ, કૅપ્શન્સ, વાણી અથવા વપરાશકર્તાના ઇરાદાને અનુમાનિત કરતા નથી. દ્રશ્ય અને ફ્રીઝ સીમાઓ સેગમેન્ટ્સ બનાવે છે; ફ્રીઝ કવરેજ, બ્લર, એક્સપોઝર, અવકાશી વિગત અને ટેમ્પોરલ ફેરફાર ફક્ત હાલના 1-16 ફ્રેમ બજેટને કેવી રીતે ફાળવવામાં આવે છે તેને પ્રભાવિત કરે છે. સંપૂર્ણપણે ફ્રોઝન સેગમેન્ટ એક ફ્રેમ પર મર્યાદિત છે, જ્યારે નોન-ફ્રોઝન સેગમેન્ટ્સ બાકીના બજેટ માટે સ્પર્ધા કરે છે. જ્યારે સીમાઓ ફ્રેમ્સ કરતાં વધુ હોય છે, ત્યારે સમાન સમયરેખા કવરેજ જાળવી રાખવામાં આવે છે જેથી ઝડપી પ્રારંભિક કટ લાંબા ટ્રેઇલિંગ સેગમેન્ટને છુપાવી ન શકે. ફ્રીઝ સીમાના 1-સેકન્ડના વિશ્લેષણ રિઝોલ્યુશનમાં દ્રશ્ય સીમાઓ એકત્રિત કરવામાં આવે છે.

ગુમ થયેલા ફિલ્ટર્સ, ખોટા/ખાલી પુરાવા, ડિટેક્ટર ભૂલ, અથવા બાઉન્ડેડ પ્રી-એનાલિસિસ ટાઈમઆઉટ ચોક્કસ સમાન મધ્યબિંદુ નીતિ પર ખુલ્લા પડે છે. કૉલર એબોર્ટ અથવા બ્રોકર ડેડલાઇન ખુલ્લી પડતી નથી: તે ઇન-ફ્લાઇટ સબપ્રોસેસને સમાપ્ત કરે છે, પછીથી ફ્રેમ નિષ્કર્ષણને અટકાવે છે, અને ખાનગી અસ્થાયી વૃક્ષ `finally` માં દૂર કરવામાં આવે છે.

`scripts/perf/video-bridge-fu07-eval.ts` પોસ્ટ-ડિડુપ કૅપ્શન-કૉલ બચત, ડેન્સ-મોશન બજેટ ફાળવણી, બ્લર/એક્સપોઝર/SI-TI પુરાવા, લાંબી પૂંછડી સાથે ઝડપી કટ અને ધીમે ધીમે-ફેડ ખોટા પોઝિટિવ્સ માટે નિર્ધારિત વાસ્તવિક FFmpeg ફિક્સ્ચર જનરેટ કરે છે. તે પ્રી-એનાલિસિસ વોલ ટાઈમ રેકોર્ડ કરે છે અને, જ્યાં `/usr/bin/time` ઉપલબ્ધ હોય ત્યાં, ચાઈલ્ડ CPU અને પીક RSS. તેની ગુણવત્તા તપાસ ફક્ત માળખાકીય ઓરેકલ્સ છે. વાસ્તવિક કૅપ્શન-મોડેલ ગુણવત્તા `HOLD` રહે છે કારણ કે આ હાર્નેસ પાસે કોઈ અધિકૃત એન્ડપોઈન્ટ અથવા ફ્રોઝન જજ નથી. નાણાકીય બચત પણ `HOLD` રહે છે સિવાય કે `--caption-cost-per-call-usd` સ્પષ્ટ હકારાત્મક પ્રતિ-કૉલ અંદાજ પૂરો પાડે; સ્ક્રિપ્ટ ક્યારેય બંને પરિણામો બનાવતી નથી.

દરેક ફ્રેમ 4 MiB સુધી મર્યાદિત છે, બધી કાચી ફ્રેમ્સ એકસાથે 23 MiB સુધી, અને સીરીયલાઇઝ્ડ બ્રોકર પ્રતિભાવ 32 MiB સુધી. એક ખાનગી અસ્થાયી ડિરેક્ટરી `finally` માં દૂર કરવામાં આવે છે. OmniRoute FFmpeg ને બંડલ કરતું નથી અને કસ્ટમ એક્ઝેક્યુટેબલ પાથ સ્વીકારતું નથી. કૅપ્શનિંગ પહેલાં, બ્રિજ રૂઢિચુસ્ત વિઝ્યુઅલ ડિડુપ્લિકેશન પાસ લાગુ કરે છે: દરેક JPEG ને 16×16 ગ્રેસ્કેલ બફરમાં ઘટાડવામાં આવે છે અને ફક્ત છેલ્લી જાળવી રાખેલી ફ્રેમ સાથે સરખાવવામાં આવે છે. એક ફ્રેમથી ઉપરના વિનંતી કરેલા કૅપ્શન બજેટ માટે, નિષ્કર્ષણ તે બજેટના બમણા સુધી અને ક્યારેય 16 ફ્રેમ્સથી વધુ નહીંનો બાઉન્ડેડ ઉમેદવાર પૂલ પૂરો પાડે છે. વિનંતી કરેલ કેપ ફક્ત ડિડુપ્લિકેશન પછી લાગુ કરવામાં આવે છે, જેમાં પ્રથમ અને અંતિમ પસંદ કરેલા ઉમેદવારોને અંતિમ પાતળાકરણ દરમિયાન સાચવવામાં આવે છે જ્યારે બજેટ ઓછામાં ઓછું બે હોય. વર્ઝનવાળી `grayscale-16x16-mean-cells-v2` નીતિ સરેરાશ લ્યુમા ડેલ્ટા અને થમ્બનેલ સેલ્સના ગુણોત્તરનો ઉપયોગ કરે છે જેનો નોર્મલાઇઝ્ડ ડેલ્ટા ઓછામાં ઓછો 0.05 છે. ડુપ્લિકેટ થ્રેશોલ્ડ સ્થિર 0.04 છે, જે રનટાઈમ સેટિંગ તરીકે ખુલ્લું પાડવાને બદલે અનુમાનિતતા માટે પસંદ કરવામાં આવ્યું છે. આ ગૌણ ઉચ્ચ-કોન્ટ્રાસ્ટ સિગ્નલ નાની ગતિ અને દૃશ્યમાન-ટેક્સ્ટ ફેરફારોને સાચવે છે જે સરેરાશ-માત્ર સરખામણી છુપાવી શકે છે. કમ્પેરેટર અથવા ડીકોડર ભૂલો ખુલ્લી પડે છે અને કવરેજ જાળવી રાખે છે. આઉટપુટ મેટાડેટા કાઢેલા ઉમેદવારો, સફળતાપૂર્વક ઉપયોગમાં લેવાયેલી ફ્રેમ્સ અને છોડી દેવાયેલા વિઝ્યુઅલ ડુપ્લિકેટ્સને અલગ પાડે છે.

સ્પષ્ટપણે ચિહ્નિત વિડિઓ ભાગ ટાઈમસ્ટેમ્પ્ડ સંપર્ક શીટની વિનંતી કરી શકે છે. બ્રિજ વધુમાં વધુ 4-કૉલમ, 16-ફ્રેમ JPEG ગ્રીડ બનાવે છે. દરેક 512-પિક્સેલ સેલ તેના સ્રોત ટાઈમસ્ટેમ્પને ઉચ્ચ-કોન્ટ્રાસ્ટ બોટમ બેન્ડમાં બર્ન કરે છે, જ્યારે તે જ ટાઈમસ્ટેમ્પ્સ ડાઉનસ્ટ્રીમ એસોસિએશન અને ઓડિટ માટે ટેક્સ્ટ્યુઅલ મેટાડેટામાં રહે છે. સંપૂર્ણ JPEG 32 MiB પર મર્યાદિત રહે છે. જો `sharp` ગ્રીડને ડીકોડ અથવા કમ્પોઝ કરી શકતું નથી, તો બ્રિજ વ્યક્તિગત JPEG ફ્રેમ્સ પર પાછો ફરે છે; ક્લાયંટ એબોર્ટ હજુ પણ શીટ ઑપરેશન દ્વારા પ્રસારિત થાય છે.

પ્રમોશન પુરાવા ઇરાદાપૂર્વક સિન્થેટિક કમ્પોઝિશન માઇક્રોબેન્ચમાર્કથી અલગ છે. `scripts/perf/video-bridge-contact-sheet-eval.ts` વાસ્તવિક OpenAI-સુસંગત વિઝન મોડેલ્સ માટે સ્કીમા-વર્ઝનવાળી A/B હાર્નેસ વ્યાખ્યાયિત કરે છે. તે પ્રદાતા-રિપોર્ટેડ ટોકન્સ, એન્ડ-ટુ-એન્ડ વોલ લેટન્સી (શીટ કમ્પોઝિશન સહિત), મોડેલ-કૉલ કાઉન્ટ અને મેનિફેસ્ટ-વ્યાખ્યાયિત હકીકત જાળવણીને માપે છે. કાચા મોડેલ પ્રતિભાવો રિપોર્ટમાં લખવામાં આવતા નથી; ફક્ત SHA-256 ડાયજેસ્ટ્સ અને મેચ થયેલ હકીકત ID જાળવી રાખવામાં આવે છે. હાર્નેસ કોઈ નેટવર્ક અથવા પેઇડ મોડેલ કૉલ કરતું નથી સિવાય કે `--execute-real` પસાર કરવામાં આવે અને `--model`, `OMNIROUTE_BASE_URL`, અને `OMNIROUTE_API_KEY` ગોઠવેલા હોય. તે સ્પષ્ટ વાસ્તવિક રન વિના, તેનો મશીન-વાંચી શકાય તેવો ચુકાદો `HOLD` રહે છે; સિન્થેટિક પેલોડ/કૉલ-કાઉન્ટ માપન એકલા પ્રમોશન પુરાવા નથી.

કૉલર્સ સપોર્ટેડ વિડિઓ ભાગ સાથે વૈકલ્પિક `transcript.cues` એરે જોડી શકે છે જ્યારે તેમની પાસે પહેલેથી જ સંરેખિત ટેક્સ્ટ હોય. દરેક ક્યુમાં `text`, પ્રોબ્ડ અવધિની અંદર એક મર્યાદિત `start`/`end` અંતરાલ, અને વ્હાઇટલિસ્ટ કરેલ `source` (`client`, `embedded`, અથવા `audio-bridge`) હોવું આવશ્યક છે; `confidence` ડિફોલ્ટ `1` પર હોય છે અને `0` અને `1` ની વચ્ચે રહેવું આવશ્યક છે. ચોક્કસ ડુપ્લિકેટ ક્યુઝ કોલેપ્સ થાય છે. OmniRoute ક્યારેય આ મેટાડેટામાંથી ટ્રાન્સક્રિપ્શન શરૂ કરતું નથી: માન્ય ક્યુઝને સ્રોત, આત્મવિશ્વાસ અને અંતરાલ સાથે વર્ણવેલ પરિણામમાં કૉપિ કરવામાં આવે છે, અને ફ્રેમ કૅપ્શન્સની સાથે અવિશ્વસનીય અવલોકનો તરીકે રેન્ડર કરવામાં આવે છે. અમાન્ય, શ્રેણીની બહાર, અથવા પ્રોવેનન્સ-મુક્ત ટેક્સ્ટને કૅપ્શન સ્ટ્રીમમાં મિશ્રિત કરવાને બદલે નકારવામાં આવે છે. `source` ફીલ્ડ હાલમાં કૉલર-ઘોષિત છે, સર્વર-ચકાસાયેલ નથી: OmniRoute ખાતરી કરે છે કે મૂલ્ય ત્રણ માન્ય સ્ટ્રિંગ્સમાંથી એક છે, પરંતુ હજુ સુધી ક્રિપ્ટોગ્રાફિકલી પુષ્ટિ કરતું નથી કે `embedded` અથવા `audio-bridge` લેબલ ખરેખર સર્વર-માલિકીના નિષ્કર્ષણમાંથી આવ્યું છે. જ્યાં સુધી તે ચકાસણી ન થાય ત્યાં સુધી `source` ને અવિશ્વસનીય સંકેત તરીકે ગણો; તેના પર અધિકૃતતાના નિર્ણયો ન બનાવો.

એક અદ્યતન કૉલર સમાન વિડિઓ માટે પહેલેથી જ અધિકૃત `audioTranscript` ટ્રૅક પ્રદાન કરી શકે છે. ફ્યુઝન સીમ એક ડેડલાઇન અને એબોર્ટ સિગ્નલ હેઠળ વિઝ્યુઅલ અને ઑડિઓ અવલોકનો ચલાવે છે, તેમને સામાન્ય સમયરેખા પર ગોઠવે છે, ચોક્કસ ડુપ્લિકેટ્સને કોલેપ્સ કરે છે, અને જ્યારે ફક્ત એક બાજુ સફળ થાય ત્યારે આંશિક પરિણામની જાણ કરે છે. એક અમાન્ય `audioTranscript` તે આંશિક પરિણામમાં અધોગતિ પામે છે — વિઝ્યુઅલ વર્ણન રાખવામાં આવે છે અને ઑડિઓ શાખા સેનિટાઇઝ્ડ નિષ્ફળતા કોડ રેકોર્ડ કરે છે — આખી વિડિઓને નિષ્ફળ કરવાને બદલે. શાખા દીઠ ઉપલબ્ધતા, આંશિક ફ્લેગ, અને સેનિટાઇઝ્ડ નિષ્ફળતા કોડ્સ વર્ણવેલ પરિણામમાં, ગાર્ડરેલ મેટાડેટા (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`) માં, પરિણામ-કેશ મેટાડેટામાં, અને બ્રિજ ફ્યુઝન કાઉન્ટર્સમાં સાચવવામાં આવે છે. ડિફોલ્ટ વિડિઓ બ્રિજ પાથ સ્પીચ-ટુ-ટેક્સ્ટને આમંત્રિત કરતો નથી અથવા બીજી મીડિયા કૉપિ ડાઉનલોડ કરતો નથી; તે સ્પષ્ટ ટ્રૅક વિના, તે ફક્ત વિડિઓ-માત્ર રહે છે.

**ટ્રાન્સક્રિપ્ટ રીટેન્શન (#12150 P1).** આ આપમેળે લાગુ પડે છે જ્યારે પણ વિડિઓ બ્રિજ (પોતે ઑપ્ટ-ઇન) ટ્રાન્સક્રિપ્ટ ક્યુ રેન્ડર કરે છે — ત્યાં કોઈ અલગ રીટેન્શન ફ્લેગ નથી. જ્યારે કોઈ વિનંતી કોઈપણ ટ્રાન્સક્રિપ્ટ ક્યુ (કૉલર-ઘોષિત `transcript` અથવા ફ્યુઝ્ડ `audioTranscript`) રેન્ડર કરે છે, ત્યારે ગાર્ડરેલ તેને `videoBridgeObserved` તરીકે ચિહ્નિત કરે છે અને વિડિઓ વર્ણનનો એક સુધારેલો પડછાયો બનાવે છે — એક સમાન રેન્ડરિંગ જેમાં દરેક ક્યુનો ફ્રી-ટેક્સ્ટ બોડી `[redacted-video-transcript]` દ્વારા બદલવામાં આવે છે, જે સ્ટ્રિંગ એસેમ્બલ થાય તે પહેલાં સ્ટ્રક્ચર્ડ ક્યુ ફિલ્ડને બદલીને બનાવવામાં આવે છે (ક્યારેય ફ્લેટન્ડ ટેક્સ્ટને પાર્સ કરીને નહીં, તેથી કોઈ ક્યુ સામગ્રી — પ્રતિકૂળ અથવા સામાન્ય, જેમાં `]` જેવા બોડીઝ શામેલ હોય જેમ કે `[inaudible]`/`[music]` — ટકી શકતી નથી). પર્સિસ્ટેડ કૉલ-લૉગ વિનંતી બોડી તે સુધારેલા પડછાયા માટે દરેક વિડિઓ-વ્યુત્પન્ન ટેક્સ્ટ ભાગને બદલે છે, જે સામગ્રી સમાનતા દ્વારા મેળ ખાય છે; `fullText` એન્કર સમાપ્ત થયેલ પ્રી-કૉલ ગાર્ડરેલ પેલોડમાંથી ફરીથી વાંચવામાં આવે છે, તેથી પછીના ચેઇન ગાર્ડરેલ્સ (PII અને ઓળખપત્ર માસ્કર્સ, પ્રાથમિકતાઓ 10/95) વર્ણન ટેક્સ્ટને સ્થાને ફરીથી લખે અને સિસ્ટમ-પ્રોમ્પ્ટ/હેન્ડઓફ/મેમરી ઇન્જેક્શન સંદેશ એરેને ફરીથી આકાર આપે પછી પણ મેચ સફળ થાય છે. મોડેલને અપસ્ટ્રીમ મોકલેલ બોડી અપરિવર્તિત રહે છે. એક અવલોકન કરેલ વિનંતી કોઈ ટકાઉ મેમરી પણ પોપ્યુલેટ કરતી નથી (વિનંતી- અને પ્રતિભાવ-વ્યુત્પન્ન નિષ્કર્ષણ બંને છોડી દેવામાં આવે છે), તેથી મોડેલનો પોતાનો જવાબ મેમરીમાં ટ્રાન્સક્રિપ્ટ ટેક્સ્ટને ઇકો કરી શકતો નથી.

વધારાની જાળવી રાખેલી નકલો સમાન અવલોકન-વિનંતી સિગ્નલનો ઉપયોગ કરે છે. કાચો પ્રી-ગાર્ડરેલ ક્લાયંટ-વિનંતી સ્નેપશોટ, ઇન-મેમરી પેન્ડિંગ વિનંતી, અને પ્રારંભિક નકારી કાઢેલ-વિનંતી લૉગ વિડિઓ ભાગોમાં ટ્રાન્સક્રિપ્ટ ફિલ્ડ્સને માળખાકીય રીતે બદલે છે; પાઇપલાઇન તબક્કાઓ દ્વારા સંશ્લેષિત સ્ટ્રિંગ પ્રોમ્પ્ટ્સ અને સંદર્ભ હેન્ડઓફ પર્સિસ્ટેડ-વિનંતી-બોડી સિંક પર સુધારવામાં આવે છે. પર્સિસ્ટેડ `video_content_removed` માર્કર `previous_response_id` ચાલુ રાખવાને ઇરાદાપૂર્વક કાઢી નાખવામાં આવેલ ટેક્સ્ટને ફરીથી બનાવવાની જગ્યાએ બંધ કરવામાં નિષ્ફળ બનાવે છે. જો અવલોકન કરેલ વિનંતી લૉગિંગ પહેલાં તેના પ્રતિ-ભાગ સુધારણા પડછાયાને ગુમાવે છે, અથવા પછીના વિનંતી પરિવર્તનો પછી ઘણા વિડિઓ પડછાયાઓમાંથી એક પણ મેળ ખાતો નથી, તો જાળવી રાખેલ વિનંતી બોડી આંશિક રીતે સુધારેલ ટ્રાન્સક્રિપ્ટને જાળવી રાખવાને બદલે સંપૂર્ણપણે છોડી દેવામાં આવે છે.

અવલોકન કરેલ વિનંતી માટે, મોડેલ પ્રતિભાવ સ્ટ્રક્ચર્ડ ક્યુ સીમા વિના ટ્રાન્સક્રિપ્ટના કોઈપણ ભાગને ટાંકવી શકે છે. તેથી તેની પર્સિસ્ટેડ કૉલ-લૉગ `responseBody` ને ઓમિશન માર્કર દ્વારા બદલવામાં આવે છે; વિગતવાર પાઇપલાઇન આર્ટિફેક્ટ (જેમાં અપસ્ટ્રીમ/ક્લાયંટ બોડીઝ અને સ્ટ્રીમ ચંક્સ શામેલ હોઈ શકે છે) જાળવી રાખવામાં આવતું નથી. સિમેન્ટીક, આઇડેમ્પોટેન્સી, અને રીઝનિંગ-રીપ્લે કેશ તે વિનંતી માટે વાંચન અને લેખનને બાયપાસ કરે છે. પ્રદાતા વિનંતી અને ક્લાયંટ-દૃશ્યમાન પ્રતિભાવ અપરિવર્તિત રહે છે. જ્યારે વિગતવાર આર્ટિફેક્ટ છોડી દેવામાં આવે છે ત્યારે પ્રારંભિક કીપલાઇવ બાઇટ્સ કામચલાઉ બફરમાંથી ડ્રેઇન કરવામાં આવે છે. કિરોની ખોટી રીતે રચાયેલ EventStream ચેતવણી ફક્ત પેલોડ બાઇટ કાઉન્ટની જાણ કરે છે, ક્યારેય તેની સામગ્રી અથવા JSON પાર્સરની કાચી ભૂલની નહીં.
આ દાવો કરતું નથી કે દરેક અસંબંધિત પ્રદાતા/પ્લગઇન ડાયગ્નોસ્ટિકનું ઑડિટ કરવામાં આવ્યું છે; વ્યાપક જાળવી રાખેલ-સિંક સ્વીપ #11658 માં ટ્રૅક કરવામાં આવે છે.

આંતરિક `/api/modality-bridge/video/drilldown` જીવનચક્ર એક અલગ, લૂપબેક/ટોકન-પ્રમાણિત કેશ સબસ્ટ્રેટ છે. દરેક ઑપરેશનને કેનોનિકલ અપારદર્શક પ્રિન્સિપાલ ID પણ જરૂરી છે. ઉત્પાદન કૉલર સક્ષમ થાય તે પહેલાં, તેણે પ્રમાણિત ભાડૂત પાસેથી તે ID મેળવવું આવશ્યક છે અને ક્લાયંટ-પસંદ કરેલ મૂલ્યને ક્યારેય ફોરવર્ડ કરવું જોઈએ નહીં. કેશ કીઝ તે પ્રિન્સિપાલને કેનોનિકલ સેશન અને વિડિઓ-સંદર્ભ ID સાથે બાંધે છે, ફક્ત તેમની SHA-256-વ્યુત્પન્ન કીઝ સ્ટોર કરે છે, અને વાંચન અને કાઢી નાખવા બંનેને સમાન પ્રિન્સિપાલ સુધી મર્યાદિત કરે છે. કેશ પ્રતિ એન્ટ્રી વધુમાં વધુ 16 વ્યુત્પન્ન JPEG ફ્રેમ્સ સ્ટોર કરે છે, તેમને દસ મિનિટ પછી સમાપ્ત કરે છે, અને બાઉન્ડેડ `start`/`end` વાંચન અથવા સ્પષ્ટ સેશન કાઢી નાખવાને સપોર્ટ કરે છે.

દરેક પ્રિન્સિપાલ 16 એન્ટ્રીઓ અને 64 MiB કેનોનિકલ JPEG ડેટા સુધી મર્યાદિત છે. તે મર્યાદાઓ વૈશ્વિક 64-એન્ટ્રી/256 MiB સીલિંગથી સ્વતંત્ર છે: પ્રિન્સિપાલ ક્વોટા દબાણ વૈશ્વિક LRU ઇવિક્શન ધ્યાનમાં લેવાય તે પહેલાં ફક્ત તે પ્રિન્સિપાલની સૌથી ઓછી તાજેતરમાં ઉપયોગમાં લેવાયેલી એન્ટ્રીઓને બહાર કાઢે છે. સમાપ્ત થયેલ એન્ટ્રીઓ કેશ પ્રવૃત્તિ પર પ્રિન્સિપાલ અને વૈશ્વિક એકાઉન્ટિંગ બંનેમાંથી દૂર કરવામાં આવે છે, જ્યારે રદ અને માન્યતા નિષ્ફળતા આંશિક રિપ્લેસમેન્ટને પ્રતિબદ્ધ કરતી નથી.

કેશ નોન-કેનોનિકલ Base64, વધારાની પેડિંગ, નોન-JPEG મીડિયા, ખોટી રીતે રચાયેલ અથવા ટ્રંકેટેડ JPEGs, અને JPEGs કે જે બાઉન્ડેડ ફુલ-ઇમેજ `sharp` ડીકોડ દરમિયાન ચેતવણી આપે છે તેને નકારે છે. તે દરેક સ્વીકૃત છબીને કેનોનિકલ JPEG તરીકે ફરીથી એન્કોડ કરે છે, કૉલર ફિલ્ડ્સ પર વિશ્વાસ કરવાને બદલે ડીકોડેડ બાઇટ્સમાંથી પહોળાઈ અને ઊંચાઈ મેળવે છે, અને કોઈપણ ટ્રેઇલિંગ પોલીગ્લોટ બાઇટ્સને જાળવી રાખવાને બદલે કાઢી નાખે છે. ફક્ત બાઉન્ડેડ કેનોનિકલ કમ્પ્રેસ્ડ બફર બંને ક્વોટામાં ચાર્જ કરવામાં આવે છે. JSON વાયર મર્યાદામાં 32 MiB ડીકોડેડ-ઇનપુટ સીલિંગ માટે Base64 ઓવરહેડ શામેલ છે. દરેક સ્ટોર કરેલ વ્યુત્પત્તિ તેની માન્ય JPEG ફોર્મેટ/રિઝોલ્યુશન, સેમ્પલિંગ નીતિ, વ્યુત્પત્તિ સંસ્કરણ, બનાવટનો સમય, સર્વર-ગણતરી કરેલ સામગ્રી હેશ, અને હેશ કરેલ પેરેન્ટ સંદર્ભ ઉપરાંત વિશ્વસનીય કૉલરના પેરેન્ટ-સામગ્રી હેશને રેકોર્ડ કરે છે. અણુ કેશ કમિટ પહેલાં અસુમેળ ડીકોડ/હેશ તબક્કાઓ વચ્ચે રદ તપાસવામાં આવે છે.

આ ટ્રાન્ચ હજુ સુધી ઉત્પાદન પ્રોડ્યુસરને રૂટ સાથે જોડતું નથી અને
મલ્ટી-રિઝોલ્યુશન વેરિઅન્ટ પસંદગી પ્રદાન કરતું નથી. પારદર્શક વિડિઓ બ્રિજ વિનંતી
પાથ તેથી કોઈ વધારાનું કાર્ય કરતું નથી, જ્યારે ટેનન્ટ-બાઉન્ડ પ્રિન્સિપલ ડેરિવેશન અને
સંપૂર્ણ FU-08 મલ્ટી-રિઝોલ્યુશન લાઇફસાયકલ સ્પષ્ટ ફોલો-અપ કાર્ય રહે છે
સંપૂર્ણ વર્તન તરીકે દસ્તાવેજીકૃત કરવાને બદલે.

ફ્રેમ્સને ગોઠવેલા વિડિઓ મોડેલ સાથે ક્રમિક રીતે કૅપ્શન કરવામાં આવે છે. ખાલી
વિડિઓ ઓવરરાઇડ વિઝન સેટિંગને વારસામાં મેળવે છે; જો બંને ખાલી હોય, તો વિઝન
ઓટો-રાઉટર અસરકારક વિઝન-સક્ષમ મોડેલ પસંદ કરે છે. સફળ કૅપ્શન્સ
મૂળ ભાગને સ્થિર `[Video description:` ઉપસર્ગ સાથે બદલે છે જે
ટેક્સ્ટને અવિશ્વસનીય મીડિયા-ડેરિવેડ અવલોકન તરીકે પણ ચિહ્નિત કરે છે અને ડાઉનસ્ટ્રીમ મોડેલોને

JPEG બાઇટ્સ, પ્રોમ્પ્ટ, ટાઇમસ્ટેમ્પ અને અસરકારક મોડેલ શામેલ છે; ફક્ત સફળ
કૅપ્શન્સ કેશ કરવામાં આવે છે. કેશ એન્ટ્રીઓ વાસ્તવિક સફળ પ્રોડ્યુસર મોડેલને જાળવી રાખે છે,
ફોલબેક મોડેલ સહિત; જ્યારે જુદા જુદા મોડેલો દ્વારા જુદી જુદી ફ્રેમ્સ બનાવવામાં આવી હોય ત્યારે બ્રિજ `mixed` રિપોર્ટ કરે છે.
કેશ હિટ તે પ્રોડ્યુસર ઓળખનો ફરીથી ઉપયોગ કરે છે
તેને વિનંતી કરેલ રૂટિંગ યોજના તરીકે ફરીથી લેબલ કરવાને બદલે. સંપૂર્ણ-વિડિઓ પરિણામ
કેશ દરેક ઇનપુટ પર કી કરવામાં આવે છે જે આઉટપુટને બદલે છે — પ્રોમ્પ્ટ, અસરકારક
મોડેલ, સેમ્પલિંગ નીતિ, ફ્રેમ ગણતરી, સિમેન્ટીક વિશ્લેષણ મોડ,

પરિણામ-કેશ v4 મેટાડેટા મોડ અને ફિંગરપ્રિન્ટ રાખે છે, ક્યારેય કાચું વપરાશકર્તા કાર્ય નહીં.
ગાર્ડ્રેલ મેટાડેટા વિનંતી કરેલ અને અસરકારક વિશ્લેષણ મોડ બંનેની જાણ કરે છે;
ઉપયોગી વપરાશકર્તા ટેક્સ્ટ વિના વિનંતી કરેલ `focused` મોડ અસરકારક રીતે `full` તરીકે જાણ કરવામાં આવે છે.

ગાર્ડ્રેલ દરેક સપોર્ટેડ વિડિઓ ભાગને બહાર કાઢે છે પરંતુ `modalityBridgeVideoMaxVideos` કરતાં વધુ વર્ણન કરતું નથી.
`supportsVideo === false` હોવાનું સાબિત થયેલ લક્ષ્ય માટે, નિષ્ફળ અને મર્યાદાથી વધુ વિડિઓઝ સ્પષ્ટ સલામત ટેક્સ્ટ માર્કર્સ બની જાય છે જેથી કોઈ કાચો વિડિઓ ટકી ન શકે.
જ્યારે ક્ષમતા અજ્ઞાત હોય, ત્યારે તે ભાગો અસ્પૃશ્ય રહે છે.
`supportsVideo === true` ધરાવતા લક્ષ્યો બ્રિજને બાયપાસ કરે છે.
ક્લાયંટ વિનંતી એબોર્ટ સિગ્નલ ડાઉનલોડ, બ્રોકર કતાર, સબપ્રોસેસ અને કૅપ્શન કૉલ્સ દ્વારા પ્રસારિત થાય છે;

| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` સામાન્ય કૅપ્શન્સ જાળવી રાખે છે; `focused` બાઉન્ડેડ, અવિશ્વસનીય નવીનતમ-વપરાશકર્તા સંદર્ભનો ઉપયોગ કરે છે |
| `modalityBridgeVideoModel`          | `""`        | વિઝન બ્રિજ મોડેલ વારસામાં મેળવો                                                                               |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                          |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, અથવા પ્રમાણસર `segment_aware`; ડિટેક્ટર નિષ્ફળતા `uniform` પર પાછા ફરે છે           |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                           |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                                |

120 સેકન્ડથી વધુના લેગસી પર્સિસ્ટેડ વિડિઓ ટાઇમઆઉટ મૂલ્યો બ્રોકર ડેડલાઇન પર ક્લેમ્પ કરવામાં આવે છે;
તે મર્યાદાથી ઉપરના નવા સેટિંગ્સ લખવાને નકારવામાં આવે છે.
`GET /api/modality-bridge/video/runtime` ને પ્રમાણીકરણ અથવા રનટાઇમ પ્રોબિંગ પહેલાં વિશ્વસનીય સ્ટેમ્પ્ડ લૂપબેક લોકેલિટીની જરૂર છે,
પછી મેનેજમેન્ટ પ્રમાણીકરણની જરૂર છે.
તે ફક્ત `available`, સેનિટાઇઝ્ડ FFmpeg/ffprobe સંસ્કરણો, અને જ્યારે રનટાઇમ અનુપલબ્ધ હોય ત્યારે એક નિશ્ચિત કારણ પરત કરે છે.
આંતરિક નિષ્કર્ષણ એન્ડપોઇન્ટ સાર્વજનિક અપલોડ API નથી:
કતાર સંતૃપ્તિ `503` વત્તા `Retry-After` પરત કરે છે,
કોલર ડિસ્કનેક્ટ `499` પરત કરે છે, અને નિશ્ચિત બ્રોકર ડેડલાઇન `504` પરત કરે છે.
રૂપાંતરિત પ્રતિભાવો વિઝન અથવા ઑડિઓ સેગમેન્ટ્સને દૂર કર્યા વિના કેન્દ્રીય `x-omniroute-modality-bridge` હેડરમાં `video->text;model=<visionModel>;parts=<videos>` ઉમેરે છે.

### PII માસ્કર (`piiMasker.ts`)

**બંને** તબક્કાઓ પર ચાલે છે.

- **`preCall`** પેલોડને ક્લોન કરે છે, `system`, `messages`, `input`, અને
  `prompt` (સામાન્ય સ્ટ્રિંગ આઇટમ્સ સહિત) ને વોક કરે છે, અને `processPII()` (માંથી
  `@/shared/utils/inputSanitizer`) ને સ્ટ્રિંગ `content`/`text` ફીલ્ડ્સ પર લાગુ કરે છે. જ્યારે
  `PII_REDACTION_ENABLED=true` હોય, ત્યારે આઉટબાઉન્ડ પેલોડમાં શોધાયેલ PII ને રેડક્ટ કરવામાં આવે છે.
  આ `INPUT_SANITIZER_MODE` (જે ફક્ત પ્રોમ્પ્ટ-ઇન્જેક્શન નીતિને નિયંત્રિત કરે છે) થી સ્વતંત્ર છે.
  જ્યારે રેડક્શન બંધ હોય, ત્યારે કૉલ સામગ્રીને ફરીથી લખ્યા વિના શોધ ગણતરીઓ રેકોર્ડ કરે છે.
- **`postCall`** પ્રતિભાવને ડીપ-ક્લોન કરે છે, `sanitizePIIResponse()` વત્તા
  Responses-API-આકાર માસ્કર (`maskResponsesOutput` — `output_text` અને
  `output[].content[].text` ને આવરી લે છે) ચલાવે છે. જો કોઈ રેડક્શન થાય, તો
  સંશોધિત પ્રતિભાવ મૂળને બદલે છે.

ગાર્ડ્રેલ ક્યારેય અવરોધિત કરતું નથી; તે ફક્ત ટીકા કરે છે (`meta.detections`,
`meta.redacted`) અથવા ફરીથી લખે છે.

### પ્રોમ્પ્ટ ઇન્જેક્શન (`promptInjection.ts`)

વપરાશકર્તા દ્વારા પૂરી પાડવામાં આવેલી સામગ્રીમાં પ્રતિકૂળ રચનાઓ શોધી કાઢે છે અને
ગોઠવેલી નીતિ લાગુ કરે છે. વર્તન પર્યાવરણ ચલો અને કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા સંચાલિત થાય છે:

| સેટિંગ          | Env var                                                                                               | ડિફોલ્ટ | અસર                                                                                                                                                                                                         |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| સક્ષમ           | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | જ્યારે `false` હોય, ત્યારે ગાર્ડરેલ શોર્ટ-સર્કિટ થાય છે.                                                                                                                                                    |
| મોડ             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | ઇન્જેક્શન નીતિ: `block`, `warn`, અથવા `log`. (`redact` બેક-કોમ્પેટ માટે સ્વીકાર્ય છે પરંતુ ઇન્જેક્શન ટેક્સ્ટને દૂર કરતું **નથી**; PII ફરીથી લખવાની વિનંતી `PII_REDACTION_ENABLED` દ્વારા નિયંત્રિત થાય છે.) |
| બ્લોક થ્રેશોલ્ડ | `blockThreshold` વિકલ્પ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ઉપનામ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | બ્લોક કરવા માટે જરૂરી ન્યૂનતમ ગંભીરતા. ડિફોલ્ટ પર મધ્યમ માત્ર અવલોકન-માત્ર છે.                                                                                                                              |

**મોડ અગ્રતા** (`getMode`): કોલર `options.mode` →
`INJECTION_GUARD_MODE` **DB ફીચર-ફ્લેગ ઓવરરાઇડ** (ડેશબોર્ડ → સેટિંગ્સ →
ફીચર ફ્લેગ્સ) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. તેથી ડેશબોર્ડ ઓવરરાઇડ env વેરીએબલ્સ પર જીત મેળવે છે, જેથી ફીચર ફ્લેગ્સ UI
ચાલતા ગાર્ડને લાઇવ નિયંત્રિત કરે છે (કોઈ રીસ્ટાર્ટ નહીં). DB રીડ ફેલ-સેફ છે:
જો તેમાં ભૂલ આવે, તો ગાર્ડ env-આધારિત વર્તન પર પાછો ફરે છે, અને જ્યારે કોઈ
ઓવરરાઇડ સેટ ન હોય ત્યારે વર્તન env-માત્ર રિઝોલ્યુશન જેવું જ હોય છે.

શોધ સ્ત્રોતો:

1.  `sanitizeRequest()` `@/shared/utils/inputSanitizer` માંથી (પાઇપલાઇનમાં અન્યત્ર વપરાયેલ શેર કરેલ ડિટેક્ટર સેટ).
2.  બિલ્ટ-ઇન `DEFAULT_GUARD_PATTERNS` (હાલમાં `system_override_inline` અને
    `markdown_system_block`, બંને `high` ગંભીરતાના).
3.  કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા પસાર કરાયેલ વૈકલ્પિક `customPatterns` (સ્ટ્રિંગ્સ, રેજેક્સ,
    અથવા `{ name, pattern, severity }` રેકોર્ડ્સ).

જ્યારે `mode === "block"` **અને** ઓછામાં ઓછું એક ડિટેક્શન ગંભીરતા થ્રેશોલ્ડને પૂર્ણ કરે છે,
ત્યારે `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` પરત કરે છે. `warn`/`log` મોડ્સમાં ગાર્ડરેલ લોગ કરે છે પરંતુ
કોલને મંજૂરી આપે છે. શેર કરેલ હેલ્પર `evaluatePromptInjection()` પણ કોલર્સ માટે
નિકાસ કરવામાં આવે છે જેમને રજિસ્ટ્રીમાંથી પસાર થયા વિના પ્રોમ્પ્ટ્સનું મૂલ્યાંકન કરવાની જરૂર હોય છે.

**સ્કેન બાઉન્ડ (v3.8.20):** ડિટેક્ટર ફક્ત જોડાયેલા પ્રોમ્પ્ટ ટેક્સ્ટના **પ્રથમ 16 KB** નું નિરીક્ષણ કરે છે —
`src/shared/utils/inputSanitizer.ts` માં `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 બાઇટ્સ).
`detectInjection()` અને `evaluatePromptInjection()` બંને પેટર્ન લૂપ ચલાવતા પહેલા
`slice(0, MAX_INJECTION_SCAN_BYTES)` કરે છે. ઇન્જેક્શન નિર્દેશો ઇનપુટની ટોચની નજીક હોય છે,
તેથી આ સેંકડો-KB પેલોડ્સ પર રેજેક્સ CPU/GC ને મર્યાદિત કરે છે અને શોધને નબળી પાડતું નથી (cf.
#3932, #4041).

### ક્રેડેન્શિયલ માસ્કર (`credentialMasker.ts`)

**બંને** તબક્કાઓ પર ચાલે છે, ડિફોલ્ટ ચેઇનમાં છેલ્લું (પ્રાધાન્યતા `95`). આઉટબાઉન્ડ પેલોડ (સંદેશ સામગ્રી,
ટૂલ-કોલ આર્ગ્યુમેન્ટ્સ, ટૂલ પરિણામો) **અને** પ્રદાતા પ્રતિભાવમાંથી જાણીતા API-કી / સિક્રેટ-ટોકન પેટર્નને
રેડેક્ટ કરે છે, જેથી પ્રોમ્પ્ટમાં પેસ્ટ કરાયેલ ક્રેડેન્શિયલ (અથવા ટૂલ પરિણામ દ્વારા પાછું ઇકો કરાયેલ)
ઉપસ્ટ્રીમ પ્રદાતા અથવા ક્લાયંટને લીક ન થાય.

- **માત્ર ઓપ્ટ-ઇન**, PII રેડેક્શન જેવી જ પરંપરા (હાર્ડ રૂલ #20-સંલગ્ન):
  જ્યાં સુધી `settings.credentialRedactionEnabled === true` **અથવા**
  `CREDENTIAL_REDACTION_ENABLED=true` ન હોય ત્યાં સુધી અક્ષમ. તે બંધ હોય ત્યારે, ગાર્ડરેલ નો-ઓપ છે —
  તે ક્યારેય બ્લોક કરતું નથી અને ક્યારેય ફરીથી લખતું નથી.
- `redactCredentials()` સંપૂર્ણ પેલોડ/પ્રતિભાવ ટ્રી (`walkValue()`,
  પ્રોટોટાઇપ-પોલ્યુશન-સેફ, `WeakSet` દ્વારા સાયકલ-સેફ) ને વોક કરે છે અને મેચોને
  `[REDACTED:<type>]` પ્લેસહોલ્ડરથી બદલે છે, ફક્ત તે શાખાઓને ક્લોન કરે છે જે ખરેખર બદલાઈ છે.
- `CREDENTIAL_PATTERNS` LLM પ્રદાતા કીઝ (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ટોકન્સ (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), પેમેન્ટ કીઝ (Stripe, Square), ક્લાઉડ
  કીઝ (AWS એક્સેસ કી, Twilio, SendGrid, Mailgun), પ્રાઇવેટ કીઝ / JWTs,
  ક્રેડેન્શિયલ-બેરિંગ કનેક્શન સ્ટ્રિંગ્સ (`mongodb://user:pass@...`, વગેરે), અને
  એક સામાન્ય `Authorization`/`x-api-key`/`api-key`/`apikey` હેડર-વેલ્યુ
  પેટર્નને આવરી લે છે. હેડર-આકારની કીઝ (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ને માળખાકીય રીતે રેડેક્ટ કરવામાં આવે છે (માત્ર વેલ્યુ, `Bearer `/`Basic `
  જેવા સ્કીમ પ્રીફિક્સ જાળવી રાખવામાં આવે છે) સામાન્ય ટેક્સ્ટ રેજેક્સ દ્વારા નહીં.
- ગાર્ડરેલ ક્યારેય બ્લોક કરતું નથી; તે ફક્ત ફરીથી લખે છે (`modifiedPayload` /
  `modifiedResponse`) અને એનોટેટ કરે છે (`meta.credentialsRedacted`, `meta.count`).

રીગ્રેશન ગાર્ડ: `tests/unit/credential-masker-guardrail.test.ts`.

## મૂળભૂત કરાર (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ચેઇનને તરત જ અટકાવે છે
  message?: string; // અવરોધિત કરતી વખતે દર્શાવવામાં આવે છે
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // વિનંતીને ફરી લખવા માટે preCall દ્વારા પરત કરવામાં આવે છે
  modifiedResponse?: TValue; // પ્રતિસાદને ફરી લખવા માટે postCall દ્વારા પરત કરવામાં આવે છે
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ગાર્ડરેલ `void`, `{}`, અથવા `{ block: false }` પરત કરીને "કોઈ ફેરફાર નહીં"નો સંકેત આપે છે. `modifiedPayload`/`modifiedResponse` પરત કરવાથી ચેઇનમાં આગળના ગાર્ડરેલ્સ તરફ વહેતું મૂલ્ય બદલાઈ જાય છે.
`signal?: AbortSignal` કૉલરની લાઇફસાઇકલને ગાર્ડરેલ્સ સુધી લઈ જાય છે. વિનંતી રદ થવી એ ઇરાદાપૂર્વકનો fail-open અપવાદ છે: મીડિયા બ્રિજ કામ અટકાવે છે અને જે લક્ષ્ય તેને સપોર્ટ કરતું નથી તે જાણીતું હોવા છતાં તેમાં મૂળ મીડિયા પુનઃસ્થાપિત કર્યા વિના ક્લીનઅપ કરે છે.

## રજિસ્ટ્રી (`registry.ts`)

સિંગલટન `guardrailRegistry` નીચેની સુવિધાઓ પ્રદાન કરે છે:

- `register(guardrail)` — ગાર્ડરેલ ઉમેરે છે (અથવા સામાન્યકૃત નામ દ્વારા બદલે છે) અને
  ચઢતા `priority` મુજબ ફરીથી ગોઠવે છે.
- `clear()` / `list()` — વહીવટી સહાયકો.
- `runPreCallHooks(payload, context)` — સક્રિય ગાર્ડરેલ્સ પર ક્રમશઃ ફરે છે, પેલોડને
  `modifiedPayload` મારફતે આગળ ધપાવે છે અને પ્રથમ `block: true` પર અટકે છે.
- `runPostCallHooks(response, context)` — પ્રતિસાદની બાજુએ સમાન પ્રવાહ.
- `resetGuardrailsForTests({ registerDefaults })` — સ્વચ્છ ટેસ્ટ અલગીકરણ માટે સ્ટેટ સાફ કરે છે અને વૈકલ્પિક રીતે
  ડિફૉલ્ટ્સને ફરીથી રજિસ્ટર કરે છે.

બંને રનર્સ `{ blocked, payload|response, results, guardrail?, message? }`
પરત કરે છે, જ્યાં `results` એ `GuardrailExecutionResult` રેકોર્ડ્સની એરે છે, જેમાં
દરેક ગાર્ડરેલ માટેના `blocked`, `skipped`, `modified`, `error`, અને `meta` ફીલ્ડ્સ
સમાવિષ્ટ હોય છે, જે ટ્રેસિંગ માટે ઉપયોગી છે.

### દરેક વિનંતી માટે ગાર્ડરેલ્સ અક્ષમ કરવા

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` વર્તમાન
વિનંતી માટે છોડવામાં આવનાર ગાર્ડરેલ નામોની ડુપ્લિકેટ-રહિત યાદી એકત્રિત કરે છે.
સ્ત્રોતો (બધા વૈકલ્પિક, બધા મર્જ કરવામાં આવે છે):

- `apiKeyInfo.disabledGuardrails`
- વિનંતી બોડીનું `disabledGuardrails` (ટોચના સ્તરે)
- વિનંતી બોડીનું `metadata.disabledGuardrails`
- હેડર `x-omniroute-disabled-guardrails` (અથવા જૂનું
  `x-disabled-guardrails`)

મૂલ્યો સ્ટ્રિંગ્સની એરે અથવા કૉમાથી અલગ કરેલી સ્ટ્રિંગ હોઈ શકે છે; નામોને
લોઅરકેસ kebab-caseમાં સામાન્યકૃત કરવામાં આવે છે (`pii_masker` → `pii-masker`). પરિણામ
`context.disabledGuardrails` મારફતે રજિસ્ટ્રીને આપવામાં આવે છે, જે
મેળ ખાતા ગાર્ડરેલ્સને છોડી દે છે (`results`માં `skipped: true`).

## અમલીકરણ ક્રમ

`src/sse/handlers/chat.ts` અને
`open-sse/handlers/chatCore.ts`માંથી પસાર થતી દરેક વિનંતી માટે:

1. `resolveDisabledGuardrails(...)` API કી, બોડી અને હેડર્સમાંથી સ્કિપ સૂચિ બનાવે છે.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ચડતા પ્રાથમિકતા ક્રમમાં ગાર્ડરેલ્સ ચલાવે છે:
   - અક્ષમ કરેલા ગાર્ડરેલ્સ `skipped` તરીકે નોંધાય છે.
   - દરેક ગાર્ડરેલનું `preCall`, `modifiedPayload` મારફતે પેલોડને ફરી લખી શકે છે.
   - પ્રથમ `block: true` ચેઇનને શોર્ટ-સર્કિટ કરે છે અને હેન્ડલર
     ગાર્ડરેલ અસ્વીકાર પ્રતિસાદ પરત કરે છે.
3. (સંભવિત રીતે ફરી લખાયેલો) પેલોડ કોમ્બો રાઉટિંગ અને અપસ્ટ્રીમ
   ડિસ્પેચમાં જાય છે.
4. પ્રતિસાદ તૈયાર થયા પછી, `guardrailRegistry.runPostCallHooks(...)`
   પ્રતિસાદ પર એ જ ચેઇન ચલાવે છે. અહીં `block: true` અપસ્ટ્રીમ
   પ્રતિસાદને કાઢી નાખે છે.

જે ગાર્ડરેલ્સ અપવાદ ફેંકે છે તે `error: <message>` સાથે નોંધાય છે અને
`logger.warn` મારફતે લૉગ થાય છે, પરંતુ ચેઇન ચાલુ રહે છે — ડિઝાઇન મુજબ ફેઇલ-ઓપન.

## કસ્ટમ ગાર્ડરેલ્સ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

પગલાં:

1. `BaseGuardrail`ને વિસ્તૃત કરતી `src/lib/guardrails/myGuardrail.ts` બનાવો.
2. `preCall` અને/અથવા `postCall` અમલમાં મૂકો.
3. કાં તો ઇમ્પોર્ટ સમયે નોંધણી કરો (`registerDefaultGuardrails`માંથી પુશ કરો) અથવા
   રનટાઇમ પર `guardrailRegistry.register(...)` કૉલ કરો — રજિસ્ટ્રી સમાન સામાન્યકૃત
   નામ ધરાવતા કોઈપણ અગાઉના ગાર્ડરેલને બદલી નાખે છે.
4. `tests/unit/` હેઠળ પરીક્ષણો ઉમેરો (હાલનાં ઉદાહરણો:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## પરીક્ષણ

જાણીતી સ્થિતિથી શરૂઆત કરવા માટે પરીક્ષણો વચ્ચે `resetGuardrailsForTests()`નો ઉપયોગ કરો.
ખાલી રજિસ્ટ્રીથી શરૂઆત કરવા માટે `{ registerDefaults: false }` પાસ કરો અને
માત્ર પરીક્ષણ હેઠળના ગાર્ડરેલ્સની નોંધણી કરો. Vision Bridge ડિપેન્ડન્સી
ઇન્જેક્શન (`deps.getSettings`, `deps.callVisionModel`) સ્વીકારે છે; Audio Bridge
સેટિંગ્સ, ક્ષમતાઓ, STT મોડેલ પસંદગી, ક્રેડેન્શિયલ તપાસો અને ટ્રાન્સક્રિપ્શન માટે
સમકક્ષ સીમ્સ ઉપલબ્ધ કરાવે છે. તેથી પરીક્ષણો DB અથવા નેટવર્ક ઍક્સેસ વિના બંને
પ્રવાહોને ચકાસી શકે છે.

ટેક્સ્ટ નિષ્કર્ષણ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`ને આવરી લે છે.

**રેડ-ટીમ (દરરોજ રાત્રે, `nightly-llm-security.yml`):** promptfoo ચકાસે છે કે દરેક રૂટ
`INJECTION_GUARD_MODE=block`માં OWASP-LLM કોર્પસને બ્લૉક કરે છે; garak પ્રોબ્સ ચલાવે છે
(સિક્રેટ વિના સ્કિપ કરે છે). સુસંગતતા માટે `moderations`નો સમાવેશ કરવામાં આવ્યો છે —
બ્લૉક-મોડમાં ઑપરેટર્સ `resolveDisabledGuardrails` મારફતે તેને મુક્તિ આપી શકે છે.

રાત્રિકાલીન વર્કફ્લો (`.github/workflows/nightly-llm-security.yml`, cron + મેન્યુઅલ
ડિસ્પેચ)માં બે જૉબ્સ છે:

- **`promptfoo-guard` (બ્લૉકિંગ)** — `INJECTION_GUARD_MODE=block` સાથે
  `promptfoo eval -c promptfooconfig.yaml` ચલાવે છે. દરેક પ્રતિકૂળ કેસ (દા.ત. "અગાઉની
  તમામ સૂચનાઓ અવગણો…", DAN-શૈલીના જેલબ્રેક્સ) ખાતરી કરે છે કે પ્રતિસાદમાં
  `error.code === "SECURITY_001"` હોય, એટલે કે ગાર્ડે વિનંતીને ખરેખર નકારી હતી.
- **`garak` (સલાહકારી)** — સ્થાનિક OmniRoute ઇન્સ્ટન્સ
  (`http://localhost:20128/v1`) સામે garak `--probes promptinject,dan,leakreplay`
  ચલાવે છે. તે પ્રોવાઇડર સિક્રેટ (`PROMPTFOO_PROVIDER_KEY`) પર આધારિત છે; સિક્રેટ
  ન હોય તો સરળતાથી સ્કિપ કરે છે અને તેની પાછળ `|| true` જોડાયેલું છે, તેથી તે CIને
  નિષ્ફળ કર્યા વિના રિપોર્ટ કરે છે.

ગાર્ડ હેલ્પર (`createInjectionGuard` / `withInjectionGuard`)નું કવરેજ પ્રોમ્પ્ટ ધરાવતા
દરેક `/v1` રૂટ સુધી વિસ્તરે છે; પ્રોમ્પ્ટ ટેક્સ્ટને
`src/shared/utils/inputSanitizer.ts`માંના `extractMessageContents()` દ્વારા
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`માંથી
લેવામાં આવે છે.
