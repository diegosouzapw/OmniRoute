> **છેલ્લે અપડેટ કરેલું:** 2026-08-29 — v3.8.51 (Video Bridge ટ્રાન્સક્રિપ્ટનું મૂળ કૉલર દ્વારા જાહેર કરવામાં આવે છે,
> હજી સર્વર દ્વારા ચકાસાયેલું નથી — #11661 અનુસાર સ્પષ્ટ કરવામાં આવ્યું)

Guardrails, OmniRoute અને અપસ્ટ્રીમ પ્રદાતાઓ વચ્ચેની સીમા પર સુરક્ષા, નીતિ અને કન્ટેન્ટ રૂપાંતરણો લાગુ કરે છે. દરેક guardrail વિનંતીના payloads (`preCall`) અને અપસ્ટ્રીમ પ્રતિસાદો (`postCall`)નું નિરીક્ષણ કરી શકે છે (અને વૈકલ્પિક રીતે તેમને નકારી, રૂપાંતરિત અથવા ઍનોટેટ કરી શકે છે).

સિસ્ટમ **fail-open** છે: જો કોઈ guardrail કાર્યરત હોય ત્યારે અપવાદ ફેંકે, તો registry ભૂલ નોંધે છે અને વિનંતીને નિષ્ફળ કરવાને બદલે આગામી guardrail સાથે ચાલુ રહે છે. બ્લૉક કરવું હંમેશાં સ્પષ્ટ નિર્ણય (`block: true`) હોય છે, ક્યારેય આકસ્મિક ઘટના નહીં.

## બિલ્ટ-ઇન Guardrails

ઇમ્પોર્ટ વખતે registry પ્રાથમિકતાના ક્રમમાં છ guardrails આપમેળે લોડ કરે છે
(`registry.ts` → `registerDefaultGuardrails()` જુઓ):

| પ્રાથમિકતા | નામ                 | તબક્કો/તબક્કાઓ | ફાઇલ                  |
| ---------- | ------------------- | -------------- | --------------------- |
| `5`        | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`        | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`        | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`       | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`       | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`       | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ઓછી પ્રાથમિકતા સંખ્યાઓ **પહેલાં** ચાલે છે.

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

**નોન-વિઝન મોડલ્સ** તરફ લક્ષિત, ઇમેજ ધરાવતી વિનંતીઓને ઇન્ટરસેપ્ટ કરે છે અને સમગ્ર વિનંતીને વિઝન-સક્ષમ મોડલ તરફ ફરીથી રૂટ કરે છે અથવા અપસ્ટ્રીમ કૉલ પહેલાં ઇમેજના ભાગોને કૉન્ફિગર કરી શકાય તેવા વિઝન મોડલ દ્વારા બનાવવામાં આવેલા ટેક્સ્ટ વર્ણનોથી બદલે છે. આનાથી ફક્ત-ટેક્સ્ટ પ્રદાતાઓ મલ્ટિમોડલ payloads ને પારદર્શક રીતે હૅન્ડલ કરી શકે છે.

પ્રવાહ:

1. જો લક્ષ્ય મોડલ પહેલેથી જ વિઝનને સપોર્ટ કરતું હોય તો તેને છોડી દો (સિવાય કે તે
   ફરજિયાત-બ્રિજ સૂચિ `isVisionBridgeForcedModel`માં હોય).
2. `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`) દ્વારા ઇમેજના ભાગો એક્સટ્રેક્ટ કરો, જે `open-sse/utils/mediaParts.ts`માંના **એકીકૃત મીડિયા
   ડિટેક્ટર** `detectMediaParts()`ને કાર્ય સોંપે છે — આ combo સુસંગતતા ફિલ્ટર સાથે વહેંચાયેલો
   સત્યનો એકમાત્ર અધિકૃત સ્રોત છે.
   એક્સટ્રેક્શન ફક્ત એવા ટોચના-સ્તરના ભાગોના આકારો માટે મંજૂર છે, જેમને
   `replaceImageParts` પાછા splice કરી શકે છે (extract↔replace કરાર): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, અને Responses API `input_image`. નેસ્ટેડ મેળ અને
   માત્ર-સૂચક આકારો combo-filter માટેની સામગ્રી છે અને ક્યારેય એક્સટ્રેક્ટ થતા નથી.
   જો કોઈ ન મળે, તો છોડી દો.
3. `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`) દ્વારા runtime config ઉકેલો: નવી `modalityBridge*`
   settings keys ને પ્રાથમિકતા મળે છે; જૂની `visionBridge*` keys **એક-ચક્ર
   fallback** (rollback window) તરીકે ચાલુ રહે છે. જ્યારે bridge અક્ષમ હોય, ત્યારે
   કોઈપણ મીડિયા ટ્રાવર્સલ પહેલાં જ છોડી દો.
4. મોડ સિલેક્ટર (`modalityBridgeVisionMode`, નીચેનું કોષ્ટક જુઓ)
   reroute કે describe નક્કી કરે છે. Reroute માત્ર `model`
   બદલેલ હોય તેવું `modifiedPayload`, તેમજ meta `{ rerouted, fromModel, toModel, imagesKept }` પરત કરે છે.
5. Describe પાથ: ઇમેજોની સંખ્યા `maxImages` સુધી મર્યાદિત કરો, કાર્ય-સંદર્ભિત prompt તૈયાર કરો,
   describe cache તપાસો, વિઝન મોડલને **સમાંતર રીતે**
   (`Promise.allSettled`) કૉલ કરો અને તેમની જગ્યાએ `[Image N]: <description>` ટેક્સ્ટ ભાગો
   ઉમેરો. નિષ્ફળ describe `null` આપે છે અને મૂળ ઇમેજ ભાગ
   **જાળવવામાં આવે છે** (#4012) — જોકે combo describe પાથમાં જ્યારે દરેક
   describe નિષ્ફળ જાય, ત્યારે પુષ્ટિ કરેલું નોન-વિઝન અપસ્ટ્રીમ તેના બદલે
   `(અનુપલબ્ધ — કોઈ વિઝન-સક્ષમ પ્રદાતા જોડાયેલો નથી)` stub મેળવે છે (#8430).
6. `modifiedPayload` + meta (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) પરત કરો.

#### મોડ સિલેક્ટર (`modalityBridgeVisionMode`)

| મોડ        | ડિફૉલ્ટ | વર્તણૂક                                                                                                                                                                                                                                                                                      |
| ---------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | જૂની heuristic, અપરિવર્તિત (#6640/#7204): non-combo/`auto/` મોડલ્સ શ્રેષ્ઠ વિઝન મોડલ તરફ reroute થાય છે, સિવાય કે મૂળ મોડલ પાસે પહેલેથી જ ઉપયોગી credentials હોય (ત્યારે describe થાય છે); combo લક્ષ્યો હંમેશાં describe થાય છે.                                                            |
| `describe` |         | હંમેશાં describe કરો — reroute બ્લૉક સંપૂર્ણપણે છોડી દેવામાં આવે છે; વપરાશકર્તાએ પસંદ કરેલું મોડલ હંમેશાં જવાબ આપે છે.                                                                                                                                                                       |
| `reroute`  |         | બળજબરીથી reroute કરો: keep-credentialed-model guardને બાયપાસ કરવામાં આવે છે. reroute-**target** credential guard હજુ પણ લાગુ પડે છે — જ્યારે કોઈ ઉપયોગી વિઝન લક્ષ્ય ઉપલબ્ધ ન હોય, ત્યારે વિનંતી describe તરફ આગળ વધે છે, જેથી કાચી ઇમેજો ક્યારેય ફક્ત-ટેક્સ્ટ backend સુધી ન પહોંચે (#8430). |

ફરજિયાત મોડ્સ, auto heuristic ચાલે તે **પહેલાં** જ short-circuit થાય છે; `auto` વર્તણૂક
PR-1 પહેલાંના guardrail સાથે byte-identical છે.

#### કાર્ય-સંદર્ભિત describe prompt (`modalityBridgeVisionTaskAware`)

ડિફૉલ્ટ **true** છે. `composeVisionPrompt()` (`visionBridgeHelpers.ts`)
બેઝ describe promptમાં **છેલ્લા user message**નું ટેક્સ્ટ (500 chars સુધી ટૂંકાવેલું)
ઉમેરે છે, જેથી વર્ણન વપરાશકર્તાએ ખરેખર શું પૂછ્યું હતું તે તરફ દોરાય
(codex-vision-proxy pattern) અને વિઝન મોડલને દૃશ્યમાન ટેક્સ્ટનું ટ્રાન્સક્રિપ્શન કરવા કહેવામાં આવે છે.
ફ્લૅગ બંધ હોય — અથવા કોઈ user text ન હોય — ત્યારે બેઝ promptનો કોઈ ફેરફાર વિના ઉપયોગ થાય છે.

describe સેલ્ફ-લૂપની પોતાની OpenAI-સુસંગત વિનંતી (`callVisionModelSingle()`
`visionBridgeHelpers.ts`માં) હંમેશાં `image_url.detail: "high"`ની વિનંતી કરે છે —
કોઈ પણ શરત વિના, દરેક કોલર/પ્રોવાઇડર માટે, અને કોઈ ક્લાયન્ટ સંકેતના આધારે નિયંત્રિત નહીં.
આ પ્રોમ્પ્ટ જે ટેક્સ્ટ-ટ્રાન્સક્રિપ્શન કાર્ય માટે કહે છે તેમાં લો-ડિટેલ સેમ્પલિંગ OCRની
ચોકસાઈ ઘટાડે છે, તેથી મૂળ ઇનબાઉન્ડ વિનંતીમાં જે કોઈ ડિટેલ લેવલ વપરાયું હોય તેને ધ્યાનમાં
લીધા વિના describe કૉલ પોતે હંમેશાં હાઈ ડિટેલની વિનંતી કરે છે. આ માત્ર આંતરિક describe
વિનંતી બોડીને અસર કરે છે; પ્રાથમિક વિનંતી પર OmniRoute કોલરનું પોતાનું
`image_url.detail` કેવી રીતે ફોરવર્ડ કરે છે તેમાં તે ફેરફાર કરતું નથી —
તે ડિફૉલ્ટ અલગથી લાગુ થાય છે, અને માત્ર શોધાયેલા OpenCode ક્લાયન્ટ્સ માટે,
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`)માં.
describe સેલ્ફ-લૂપની Anthropic વાયર-ફોર્મેટ શાખામાં કોઈ `detail` ફીલ્ડ નથી
અને તે બંને ડિફૉલ્ટથી અપ્રભાવિત રહે છે.

#### Describe આઉટપુટ મર્યાદા (`modalityBridgeVisionMaxChars`)

| કી                             | ડિફૉલ્ટ | શ્રેણી             |
| ------------------------------ | ------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`     | `0` અથવા 100–50000 |

`0` (ડિફૉલ્ટ)નો અર્થ **કોઈ મર્યાદા નહીં** છે — `callVisionModel()` દ્વારા પરત કરાયેલું
વર્ણન કોઈ ફેરફાર વિના પસાર કરવામાં આવે છે, જેથી હાલનું વર્તન જળવાઈ રહે છે.
100–50000ની શ્રેણીમાં આવતી કોઈપણ કિંમત વર્ણનને `[Image N]: <description>`
તરીકે પાછું જોડવામાં આવે તે પહેલાં `…` પ્રત્યય સાથે ટૂંકાવે છે
(`src/lib/guardrails/visionBridge.ts`માં `VisionBridgeGuardrail.preCall()`).
ડાઉનસ્ટ્રીમ મોડલને સંપૂર્ણ ટ્રાન્સક્રિપ્શનની જરૂર હોય તેવા વધુ ડિટેલવાળા OCR કાર્યો માટે
આ વધારો; વધુ વર્ણન આપતા વિઝન મોડલ્સમાં ટોકન વપરાશ મર્યાદિત કરવા માટે તેને ઘટાડો.
ડૅશબોર્ડ ફીલ્ડ Vision ટૅબની Advanced પેનલમાં છે
(`ModalityBridgeVisionTab.tsx`માં `modality-bridge-max-chars`) અને સ્પષ્ટ રીતે આપેલા
`0`ને અસ્પર્શિત રાખીને 1થી 99 વચ્ચેની કોઈપણ કિંમતને ન્યૂનતમ 100 સુધી વધારે છે —
`0` માત્ર "સેટ ન કરેલું" ડિફૉલ્ટ નથી, પરંતુ પોતાની રીતે માન્ય Zod કિંમત છે
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`).

કૅશ વિભાજિત થઈ જાય. નિષ્ફળ describes ક્યારેય કૅશ થતા નથી. સેટિંગ્સ:

#### રિમોટ ઇમેજ નોર્મલાઇઝેશન (સેલ્ફ-લૂપ describe/base64 ફેચ)

જ્યારે બ્રિજ પોતે કોઈ **રિમોટ** ઇમેજ ફેચ કરે છે — Anthropic describe
સેલ્ફ-કૉલ અને claude-વાયર-ફોર્મેટ base64 રૂપાંતરણ
(`ensureBase64ImagesForClaudeWire`), બંને `visionBridgeHelpers.ts`માં રહેલા
`fetchRemoteImageAsDataUri()` મારફતે — ત્યારે પરિણામી ડેટા URIને વિઝન-મોડલની
વિનંતીમાં એમ્બેડ કરતા પહેલાં `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`)માંથી પસાર કરવામાં આવે છે. વધુ પડતી મોટી
ઇમેજને **2048px લાંબી ધાર** સુધી ડાઉનસ્કેલ કરવામાં આવે છે (OpenAI/Anthropic
પહેલેથી સર્વર-સાઇડ પર લાગુ કરતા રિસાઇઝ મર્યાદા સાથે મેળ ખાતું), જે વિઝન મોડલ શું
જુએ છે તેમાં ફેરફાર કર્યા વિના અપલોડ બાઇટ્સ/લેટન્સી ઘટાડે છે. રિસાઇઝિંગ
ડાયનેમિક ઇમ્પોર્ટ દ્વારા લોડ થતા `sharp`નો ઉપયોગ કરે છે: જે પ્લેટફોર્મ પર તેનું
નેટિવ બાઇનરી લોડ ન થઈ શકે, ત્યાં `normalizeDataUri()` **ક્યારેય થ્રો કરતું નથી** —
તે મૂળ બાઇટ્સને જેમના તેમ પસાર કરવા પર ફૉલબૅક કરે છે, જેથી describe/base64-રૂપાંતરણ
પાથ હંમેશાં કાર્યરત રહે. નોન-ઇમેજ બાઇટ્સ (એવું ફેચ જેણે ડિકોડ કરી શકાય તેવી ઇમેજ
પરત ન કરી હોય) પણ કોઈ ફેરફાર વિના પસાર કરવામાં આવે છે. આ નોર્મલાઇઝેશન માત્ર
બ્રિજ પોતાના સેલ્ફ-કૉલ માટે ફેચ કરે તેવી ઇમેજ સુધી મર્યાદિત છે — કોલરના મૂળ
પાસથ્રૂ પેલોડ પર તે ક્યારેય લાગુ પડતું નથી, જે ફક્ત ઑપ્ટ-ઇન હોય ત્યારે જ ફેરફાર
કરવાના સિદ્ધાંત (Hard Rule #20) સાથે સુસંગત છે.

`callVisionModel` અમલીકરણો ઇન્જેક્ટ કરી શકે.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ઑડિયો ઇનપુટ સ્વીકારવા માટે જાણીતું ન હોય એવા લક્ષ્ય સુધી પહોંચે તે પહેલાં
ઑડિયો ધરાવતી ચૅટ વિનંતીઓને ઇન્ટરસેપ્ટ કરે છે. તે ચૅટ વિનંતીને ક્યારેય ફરીથી રૂટ કરતું નથી: ઑડિયો ભાગોનું
હાલના OpenAI-સુસંગત મલ્ટિપાર્ટ એન્ડપોઇન્ટ દ્વારા ટ્રાન્સક્રિપ્શન થાય છે અને
પસંદ કરેલું ચૅટ મોડેલ ટેક્સ્ટ ટ્રાન્સક્રિપ્ટ્સ સાથે ચાલુ રહે છે.

પ્રવાહ:

1. `getResolvedModelCapabilities()` દ્વારા `supportsAudio` રિઝૉલ્વ કરો. સ્પષ્ટ
   પ્રોવાઇડર-રજિસ્ટ્રી મેટાડેટાને પ્રાથમિકતા મળે છે, ત્યારબાદ સ્થિર મોડેલ મેટાડેટા અને પછી સિંક કરેલું
   `modalities_input`. `audio` વિનાની જાહેર કરેલી ઇનપુટ સૂચિ `false` છે; ક્ષમતાનો કોઈ
   પુરાવો ન હોય તો મૂલ્ય `null` રહે છે. `false` અને `null` બંને
   રૂઢિચુસ્ત બ્રિજને સક્રિય કરે છે, જ્યારે `true` તેને બાયપાસ કરે છે.
2. `modalityBridgeAudio*` સેટિંગ્સ રિઝૉલ્વ કરો અને વહેંચાયેલ `detectMediaParts()`
   ડિટેક્ટર દ્વારા દરેક સંદેશમાંથી સ્પ્લાઇસ કરી શકાય એવા ટૉપ-લેવલ
   ઑડિયો ભાગો કાઢો. સમર્થિત વાયર સ્વરૂપો OpenAI `input_audio`, `audio_url` અને
   `source.media_type: "audio/*"` છે. નેસ્ટેડ ઑડિયો રૂટિંગ માટે શોધવામાં આવે છે, પરંતુ
   સ્પ્લાઇસ પાથ દ્વારા દૂર કરાતો નથી. કાર્ય `modalityBridgeAudioMaxClips` દ્વારા મર્યાદિત છે;
   પછીના ભાગો અસ્પર્શિત રહે છે.
3. ગોઠવેલા `provider/model`ને માન આપો, અથવા `selectAudioBridgeModel()`ને
   સ્થિર કૅટલૉગ ક્રમમાં `AUDIO_TRANSCRIPTION_PROVIDERS`માંથી પસાર થઈને ઉપયોગયોગ્ય સક્રિય પ્રોવાઇડર ક્રેડેન્શિયલ ધરાવતું પ્રથમ
   મોડેલ પસંદ કરવા દો.
4. `callAudioTranscription()` base64/data-URI ઑડિયોને મલ્ટિપાર્ટ
   `file`માં રૂપાંતરિત કરે છે, અથવા DNS પિનિંગ અને 25 MB મર્યાદા ધરાવતા માત્ર-સાર્વજનિક આઉટબાઉન્ડ
   ગાર્ડ દ્વારા દૂરસ્થ `audio_url` ડાઉનલોડ કરે છે. ત્યારબાદ તે `resolveSelfLoopBearer()` વડે પ્રમાણિત
   સ્થાનિક `/v1/audio/transcriptions` સેલ્ફ-લૂપ પર ફાઇલ અને પસંદ કરેલું
   મોડેલ POST કરે છે. હાલનો ટ્રાન્સક્રિપ્શન રૂટ સામાન્ય
   ક્રેડેન્શિયલ લુકઅપ, કૂલડાઉન/રેટ-લિમિટ હેન્ડલિંગ અને પ્રોવાઇડર ડિસ્પૅચ કરે છે.
5. સફળ કૉલ્સ પોતાના ભાગોને `[Audio N]: <transcript>`થી બદલે છે. કૉલ્સ
   `Promise.allSettled` સાથે ચાલે છે: કોઈ એક નિષ્ફળતા તે મૂળ
   ઑડિયો ભાગને જાળવી રાખે છે (#4012 કરાર). જો દરેક કૉલ નિષ્ફળ જાય અને લક્ષ્ય માટે
   `supportsAudio === false` સાબિત થયેલું હોય, તો ભાગો
   `[Audio N]: (unavailable — no STT provider connected)` બને છે (#8430 કરાર). અજ્ઞાત
   લક્ષ્ય (`null`) માટે, તમામ કૉલ નિષ્ફળ જાય તો પરિણામ અસ્પર્શિત રહે છે. કોઈ ઉપયોગયોગ્ય STT ક્રેડેન્શિયલ ન ધરાવતા
   સાબિત ટેક્સ્ટ-માત્ર લક્ષ્યને નેટવર્ક કૉલ કર્યા વિના સમાન સ્પષ્ટ
   સ્ટબ મળે છે.

સફળ ટ્રાન્સક્રિપ્ટ્સ પ્રક્રિયા-વ્યાપી Modality Bridge LRU/TTL કૅશનો ઉપયોગ કરે છે.
કી ઑડિયો સંદર્ભ, સ્થિર `audio-transcription` ઑપરેશન
લેબલ અને પસંદ કરેલું STT મોડેલ જોડે છે; નિષ્ફળતાઓ ક્યારેય કૅશ થતી નથી. ઑડિયો પ્રયાસો
વહેંચાયેલા `bridged`, `cacheHits`, `failures` અને `lastUsedAt` કાઉન્ટર્સ અપડેટ કરે છે.
રૂપાંતરિત પ્રતિસાદોમાં
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` હોય છે; અસ્પર્શિત
વિનંતીઓને Audio Bridge સેગમેન્ટ મળતું નથી.

રનટાઇમ સેટિંગ્સ DB-સમર્થિત અને Zod-માન્યકૃત છે:

| કી                            | ડિફૉલ્ટ | શ્રેણી           |
| ----------------------------- | ------- | ---------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                |
| `modalityBridgeAudioModel`    | `""`    | Auto અથવા STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000      |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10             |

વહેંચાયેલ કૅશ હજી પણ `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` અને `modalityBridgeCacheMaxEntries` દ્વારા નિયંત્રિત થાય છે.

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

જાણીતા મૂળ વિડિયો સપોર્ટ વિનાના લક્ષ્યને કૉલ કરવામાં આવે તે પહેલાં Chat Completions `messages` અને Responses
API `input` માં ટોચના સ્તરના વિડિયો ભાગોને ઇન્ટરસેપ્ટ કરે છે.
સપોર્ટેડ આકારો `input_video`, `video_url`, `video_source`, HTTPS URLs,
અને `data:video/*;base64,...` data URIs છે. ટેક્સ્ટમાં રહેલાં સાદાં ફાઇલનામોને
વિડિયો તરીકે ગણવામાં આવતાં નથી.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) વિનંતીનું ટ્રાવર્સલ,
ક્ષમતા/નીતિ ચકાસણી, પ્રતિ-વિનંતી એકત્રીકરણ અને પ્રતિસાદ પેલોડ સંભાળે છે.
પ્રતિ-વિડિયો કાર્ય — પ્રાપ્તિ, સંપૂર્ણ-પરિણામ કૅશ, ફ્રેમ
ક્રમનું વર્ણન કરવું (જે કૉલર દ્વારા જાહેર કરાયેલી કોઈપણ ઑડિયો ટ્રાન્સક્રિપ્ટને જોડે છે), અને પ્રતિ-પ્રયાસ
મેટ્રિક્સ/અબોર્ટ/ક્લીનઅપ — `videoBridgePipeline.ts` માં `processVideoPart` પાછળ
છુપાયેલું છે, જેને `preCall` ના લૂપની અંદર દરેક વિડિયો ભાગ માટે એક વખત કૉલ કરવામાં આવે છે.
તે મોડ્યુલ સ્પષ્ટ પોર્ટ સીમાઓ `VideoMediaBrokerPort`
(બાઇટ્સ મેળવવા અને નમૂના લેવાયેલી ફ્રેમ્સ કાઢવા), `VideoAudioTranscriptionPort`
(કૉલર દ્વારા જાહેર કરાયેલી ઑડિયો ટ્રાન્સક્રિપ્ટને નમૂના લેવાયેલા કૅપ્શન્સ સાથે જોડવા), અને
`VideoDrilldownPort` (ફ્રેમ ડ્રિલ-ડાઉન ટકાઉપણાની સીમા; હજી
`processVideoPart` સાથે જોડાયેલ નથી — આજે માત્ર અલગ `/api/modality-bridge/video/drilldown`
રૂટ જ ડ્રિલ-ડાઉન એન્ટ્રીઓ લખે છે) પણ વ્યાખ્યાયિત કરે છે.

જાહેર `/v1` વિનંતી પાથ ક્યારેય સબપ્રોસેસને ઇમ્પોર્ટ કરતો કે ચલાવતો નથી. રિમોટ
વિડિયો 50 MiB ની મર્યાદા હેઠળ ડાઉનલોડ કરવામાં આવે છે; ઇનલાઇન base64 વિડિયો માટે
પ્રતિ-વિડિયો ડિકોડેડ કદની રૂઢિચુસ્ત 36 MiB મર્યાદા છે, જેથી મોડેલ/સંદેશાઓ/ફ્રેમિંગ એન્વલોપ
50 MiB ની જાહેર JSON વિનંતી સ્વીકાર મર્યાદાની અંદર રહી શકે. ફાળવણી પહેલાં ઇનલાઇન
લંબાઈ અને ડિકોડેડ-કદના અંદાજોની ચકાસણી કરવામાં આવે છે. પ્રારંભિક રિમોટ URL અને
દરેક રીડાયરેક્ટ પર HTTPS જરૂરી છે, જેમાં DNS પિનિંગ સાથેના હાલના
માત્ર-જાહેર આઉટબાઉન્ડ ગાર્ડનો ઉપયોગ થાય છે. ત્યારબાદ બાઇટ્સ ચોક્કસ આંતરિક
`POST /api/modality-bridge/video/extract` બ્રોકર સીમાને પાર કરે છે. તે રૂટ
`LOCAL_ONLY` અને `SPAWN_CAPABLE` બંને છે, માત્ર પ્રતિ-પ્રક્રિયા પ્રમાણિત,
વિશ્વસનીય-લૂપબૅક વિનંતી સ્વીકારે છે અને ક્યારેય URL, ફાઇલસિસ્ટમ પાથ, એક્ઝિક્યુટેબલ
અથવા આર્ગ્યુમેન્ટ સૂચિ સ્વીકારતો નથી. API બોડી-કદ પાઇપલાઇન અને હેન્ડલરનું ક્રમિક બોડી
રીડર સ્વતંત્ર રીતે 50 MiB ની બ્રોકર ઇનપુટ મર્યાદા લાગુ કરે છે. તેની મર્યાદિત કતાર
એક સમયે એક એક્સટ્રૅક્શન ચલાવે છે, ચાર બાકી રહેલી જોબ્સને મંજૂરી આપે છે અને બાકી
ઇનપુટને 100 MiB સુધી મર્યાદિત કરે છે.

બ્રોકરની અંદર, `ffprobe` ખાનગી સ્થાનિક ફાઇલ વાંચે છે; નિશ્ચિત ફોર્મેટ
અનુમતિસૂચિ પ્લેલિસ્ટ અને મેનિફેસ્ટ ફોર્મેટ્સને બાકાત રાખે છે. મંજૂર MOV-ફેમિલી
કન્ટેનર્સ માટે બાહ્ય MOV ડેટા રેફરન્સ ડિફૉલ્ટ રૂપે અક્ષમ રહે છે અને નિશ્ચિત
કમાન્ડ તેમને સક્ષમ કરવાનું પસંદ કરતી નથી. `ffprobe` અને `ffmpeg` બંને
માત્ર-`file` પ્રોટોકોલ અનુમતિસૂચિ, એક થ્રેડ, નિશ્ચિત આર્ગ્યુમેન્ટ ઍરે, કોઈ શેલ નહીં,
અને `PATH` માંથી રિઝોલ્વ કરાયેલા એક્ઝિક્યુટેબલ્સનો ઉપયોગ કરે છે. જોડાયેલા-ચિત્રવાળા કવર
સ્ટ્રીમ્સ ચલાવી શકાય એવા ઉમેદવારો નથી. ચલાવી શકાય એવા તમામ સ્ટ્રીમ્સે મર્યાદાઓ
સંતોષવી આવશ્યક છે અને નિર્ધારિત સૌથી નીચા-ઇન્ડેક્સ ફૉલબૅક પહેલાં સ્પષ્ટ ડિફૉલ્ટ
સ્ટ્રીમને પ્રાધાન્ય આપવામાં આવે છે. વિડિયો 600 સેકન્ડ, પ્રતિ પરિમાણ 8,192 પિક્સેલ
અને 33,554,432 સ્રોત પિક્સેલ સુધી મર્યાદિત છે. FFmpeg 1–16 મધ્યબિંદુ JPEG ફ્રેમ્સના
નમૂના લે છે, નાનાં ઇનપુટ્સને અપસ્કેલ કર્યા વિના લાંબી ધારને વધુમાં વધુ 1,024 પિક્સેલ

#### FU-07 માળખાકીય સેગમેન્ટ પુરાવા

`segment_aware` પહેલેથી માન્ય કરાયેલા સ્થાનિક વિડિયો સ્ટ્રીમ પર એક મર્યાદિત
પૂર્વ-વિશ્લેષણ પાસનો ઉપયોગ કરે છે. નિશ્ચિત ફિલ્ટર ચેઇન પહેલાં પહોળાઈને વધુમાં વધુ

બ્લર, સરેરાશ લ્યુમા તથા અવકાશીય/સમયગત માહિતી માટે પ્રતિ સેકન્ડ 1 ફ્રેમનો નમૂનો

`audioFusionFailureCodes`), પરિણામ-કૅશ મેટાડેટામાં અને બ્રિજ ફ્યુઝન કાઉન્ટર્સમાં જાળવવામાં આવે છે. ડિફૉલ્ટ Video Bridge પાથ સ્પીચ-ટુ-ટેક્સ્ટ ચલાવતો નથી અથવા મીડિયાની બીજી નકલ ડાઉનલોડ કરતો નથી; તે સ્પષ્ટ ટ્રૅક વિના, માત્ર-વિડિયો જ રહે છે.

**ટ્રાન્સક્રિપ્ટ જાળવણી (#12150 P1).** જ્યારે પણ Video Bridge (જે પોતે ઑપ્ટ-ઇન છે) ટ્રાન્સક્રિપ્ટ ક્યૂ રેન્ડર કરે છે ત્યારે આ આપમેળે લાગુ પડે છે — તેના માટે કોઈ અલગ જાળવણી ફ્લૅગ નથી. જ્યારે કોઈ વિનંતી કોઈપણ ટ્રાન્સક્રિપ્ટ ક્યૂ (કૉલર દ્વારા જાહેર કરાયેલ `transcript` અથવા ફ્યુઝ કરાયેલ `audioTranscript`) રેન્ડર કરે છે, ત્યારે ગાર્ડરેલ તેને `videoBridgeObserved` તરીકે ચિહ્નિત કરે છે અને વિડિયો વર્ણનની રિડૅક્ટ કરેલી શેડો નકલ બનાવે છે — એકસરખું રેન્ડરિંગ જેમાં દરેક ક્યૂનો મુક્ત-ટેક્સ્ટ ભાગ `[redacted-video-transcript]` વડે બદલવામાં આવે છે, જે સ્ટ્રિંગ એસેમ્બલ થાય તે પહેલાં સ્ટ્રક્ચર્ડ ક્યૂ ફીલ્ડને બદલીને બનાવવામાં આવે છે (સપાટ કરાયેલા ટેક્સ્ટને પાર્સ કરીને ક્યારેય નહીં, જેથી કોઈ ક્યૂ સામગ્રી — વિરોધી કે સામાન્ય, જેમાં `]` ધરાવતા ભાગો જેમ કે `[inaudible]`/`[music]` પણ સામેલ છે — ટકી ન શકે). સંગ્રહિત કૉલ-લૉગ વિનંતી બૉડીમાં દરેક વિડિયો-ઉદ્ભવિત ટેક્સ્ટ ભાગને સામગ્રીની સમાનતા દ્વારા મેળ ખાતી તે રિડૅક્ટ કરેલી શેડો નકલથી બદલવામાં આવે છે; `fullText` ઍન્કરને પૂર્ણ થયેલા પ્રી-કૉલ ગાર્ડરેલ પેલોડમાંથી ફરી વાંચવામાં આવે છે, તેથી પછીના ચેઇન ગાર્ડરેલ્સ (PII અને ક્રેડેન્શિયલ માસ્કર્સ, પ્રાથમિકતાઓ 10/95) વર્ણન ટેક્સ્ટને તેની જ જગ્યાએ ફરી લખે અને સિસ્ટમ-પ્રૉમ્પ્ટ/હૅન્ડઑફ/મેમરી ઇન્જેક્શન મેસેજ એરેનું સ્વરૂપ બદલે તે પછી પણ મેળ સફળ રહે છે. મૉડલને અપસ્ટ્રીમ મોકલાતી બૉડી અપરિવર્તિત રહે છે. અવલોકિત વિનંતી કોઈ ટકાઉ Memory પણ ભરતી નથી (વિનંતી- અને પ્રતિસાદ-ઉદ્ભવિત એમ બંને પ્રકારનું એક્સ્ટ્રૅક્શન છોડવામાં આવે છે), તેથી મૉડલનો પોતાનો જવાબ ટ્રાન્સક્રિપ્ટ ટેક્સ્ટને Memoryમાં પ્રતિધ્વનિત કરી શકતો નથી.

જાળવણીના હજુ ખુલ્લા રહેલા સપાટીઓ, અનુવર્તી કાર્ય માટે ટ્રૅક કરાયેલા (**P2**, #12430): વિગતવાર-લૉગ આર્ટિફૅક્ટમાં રહેલો કાચો પ્રી-ગાર્ડરેલ ક્લાયન્ટ-વિનંતી સ્નૅપશૉટ; `previous_response_id` ચાલુ રાખવામાં ફેલ-ક્લોઝ્ડ વર્તન; સંશ્લેષિત સ્ટ્રિંગ પ્રૉમ્પ્ટમાં ટ્રાન્સક્રિપ્ટ એમ્બેડ કરતા ડિરાઇવ્ડ-પ્રૉમ્પ્ટ આંતરિક ડિસ્પૅચ (પાઇપલાઇન તબક્કાઓ, કૉન્ટેક્સ્ટ-હૅન્ડઑફ); અને ટ્રાન્સક્રિપ્ટને ઉદ્ધૃત કરતા મૉડલ જવાબની પ્રતિસાદ બૉડી / સિમેન્ટિક-કૅશ નકલ. આ P1ના સંગ્રહિત-વિનંતી-બૉડી + Memory કાર્યક્ષેત્રની બહારની કાચી/પ્રતિસાદ-વર્ગ અથવા ઑપ્ટ-ઇન સપાટીઓ છે.

આંતરિક `/api/modality-bridge/video/drilldown` લાઇફસાઇકલ એક અલગ, લૂપબૅક/ટોકન-પ્રમાણિત કૅશ સબસ્ટ્રેટ છે. દરેક ઑપરેશન માટે પ્રમાણભૂત અસ્પષ્ટ પ્રિન્સિપલ ID પણ જરૂરી છે. કોઈ પ્રોડક્શન કૉલરને સક્ષમ કરતાં પહેલાં, તેણે પ્રમાણિત ટેનન્ટમાંથી તે ID મેળવવું આવશ્યક છે અને ક્લાયન્ટ દ્વારા પસંદ કરાયેલ મૂલ્ય ક્યારેય ફૉર્વર્ડ કરવું જોઈએ નહીં. કૅશ કીઝ તે પ્રિન્સિપલને પ્રમાણભૂત સેશન અને વિડિયો-રેફરન્સ IDs સાથે બાઇન્ડ કરે છે, તેમની માત્ર SHA-256-ઉદ્ભવિત કીઝ સંગ્રહે છે અને વાંચન તથા ડિલીશન બંનેને એ જ પ્રિન્સિપલ સુધી મર્યાદિત કરે છે. કૅશ દરેક એન્ટ્રીમાં મહત્તમ 16 ડિરાઇવ્ડ JPEG ફ્રેમ્સ સંગ્રહે છે, દસ મિનિટ પછી તેમને સમાપ્ત કરે છે અને મર્યાદિત `start`/`end` વાંચન અથવા સ્પષ્ટ સેશન ડિલીશનને સપોર્ટ કરે છે.

દરેક પ્રિન્સિપલ 16 એન્ટ્રીઓ અને 64 MiB પ્રમાણભૂત JPEG ડેટા સુધી મર્યાદિત છે. આ મર્યાદાઓ વૈશ્વિક 64-એન્ટ્રી/256 MiB મર્યાદાથી સ્વતંત્ર છે: પ્રિન્સિપલ ક્વોટાનું દબાણ વૈશ્વિક LRU એવિક્શન ધ્યાનમાં લેવાય તે પહેલાં માત્ર તે પ્રિન્સિપલની સૌથી ઓછી તાજેતરમાં વપરાયેલી એન્ટ્રીઓને દૂર કરે છે. કૅશ પ્રવૃત્તિ દરમિયાન સમયસમાપ્ત એન્ટ્રીઓને પ્રિન્સિપલ અને વૈશ્વિક એમ બંને એકાઉન્ટિંગમાંથી દૂર કરવામાં આવે છે, જ્યારે રદ્દીકરણ અને માન્યતા નિષ્ફળતા આંશિક રિપ્લેસમેન્ટ કમિટ કરતા નથી.

કૅશ બિન-પ્રમાણભૂત Base64, અતિરિક્ત પૅડિંગ, બિન-JPEG મીડિયા, ખામીયુક્ત અથવા અધૂરા JPEGs અને મર્યાદિત પૂર્ણ-ઇમેજ `sharp` ડિકોડ દરમિયાન ચેતવણી ઉત્પન્ન કરતા JPEGsને નકારે છે. તે દરેક સ્વીકૃત ઇમેજને પ્રમાણભૂત JPEG તરીકે ફરી એન્કોડ કરે છે, કૉલરના ફીલ્ડ્સ પર વિશ્વાસ કરવાને બદલે ડિકોડ કરાયેલા બાઇટ્સમાંથી પહોળાઈ અને ઊંચાઈ મેળવે છે અને અંતમાં જોડાયેલા કોઈપણ પૉલિગ્લૉટ બાઇટ્સ જાળવવાને બદલે કાઢી નાખે છે. માત્ર મર્યાદિત પ્રમાણભૂત કમ્પ્રેસ્ડ બફરનો જ બંને ક્વોટામાં હિસાબ થાય છે. સંખ્યા, સેમેન્ટિક વિશ્લેષણ મોડ, સામાન્યકૃત ફોકસ હિન્ટનું SHA-256 ફિંગરપ્રિન્ટ,
ફોકસ વિન્ડો, `transcript`, `audioTranscript` અને કૉન્ટેક્ટ-શીટ ફ્લૅગ — તેથી આમાંથી
કોઈપણ પરિમાણ બદલવાથી કૅશ મિસ થાય છે, જૂના પરિણામનો પુનઃઉપયોગ ક્યારેય થતો નથી.
વિઝ્યુઅલ ડિડુપ નીતિનું વર્ઝન, થ્રેશોલ્ડ અને મર્યાદિત ઉમેદવાર-ફ્રેમની સંખ્યા પણ
પરિણામ-કૅશ કી અને મેટાડેટામાં સ્પષ્ટ હોય છે; તેથી નીતિમાં થયેલો ફેરફાર આખા વિડિયોના
જૂના વર્ણનનો પુનઃઉપયોગ કરી શકતો નથી. પરિણામ-કૅશ v4 મેટાડેટા મોડ અને ફિંગરપ્રિન્ટ
જાળવે છે, પરંતુ વપરાશકર્તાનું કાચું કાર્ય ક્યારેય નહીં. ગાર્ડરેલ મેટાડેટા વિનંતી
કરાયેલ અને અસરકારક બંને વિશ્લેષણ મોડ રિપોર્ટ કરે છે; ઉપયોગી વપરાશકર્તા ટેક્સ્ટ
વિના વિનંતી કરાયેલ `focused` મોડ અસરકારક રીતે `full` તરીકે રિપોર્ટ થાય છે.

ગાર્ડરેલ દરેક સમર્થિત વિડિયો ભાગને એક્સ્ટ્રૅક્ટ કરે છે, પરંતુ
`modalityBridgeVideoMaxVideos` કરતાં વધુનું વર્ણન કરતું નથી. જે ટાર્ગેટ માટે
`supportsVideo === false` હોવાનું સાબિત થયું હોય, તેમાં નિષ્ફળ અને મર્યાદાથી વધુ
વિડિયો સ્પષ્ટ સુરક્ષિત ટેક્સ્ટ માર્કર્સમાં ફેરવાય છે, જેથી કોઈ કાચો વિડિયો બાકી
ન રહે. ક્ષમતા અજ્ઞાત હોય ત્યારે તે ભાગો અસ્પર્શિત રહે છે.
`supportsVideo === true` ધરાવતા ટાર્ગેટ્સ બ્રિજને બાયપાસ કરે છે. ક્લાયન્ટ રિક્વેસ્ટનું
અબોર્ટ સિગ્નલ ડાઉનલોડ, બ્રોકર ક્યૂ, સબપ્રોસેસ અને કૅપ્શન કૉલ્સમાં આગળ પ્રસારિત
થાય છે; અબોર્ટ્સ વિડિયો વચ્ચે પ્રક્રિયા અટકાવે છે અને ક્યારેય કાચા મીડિયાને
ફેઇલ-ઓપન કરતા નથી.

રનટાઇમ સેટિંગ્સ DB-સમર્થિત અને Zod-વૅલિડેટેડ છે:

| કી                                  | ડિફૉલ્ટ     | શ્રેણી / વર્તન                                                                                            |
| ----------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | વૈકલ્પિક રનટાઇમ, ઑપ્ટ-ઇન                                                                                  |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` સામાન્ય કૅપ્શન્સ જાળવે છે; `focused` મર્યાદિત, અવિશ્વસનીય નવીનતમ-વપરાશકર્તા સંદર્ભ વાપરે છે        |
| `modalityBridgeVideoModel`          | `""`        | Vision Bridge મોડેલ વારસામાં મેળવે છે                                                                     |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                      |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware` અથવા પ્રમાણસર `segment_aware`; ડિટેક્ટર નિષ્ફળ થાય તો `uniform` પર ફૉલબૅક થાય છે |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                       |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                            |

120 સેકન્ડથી વધુના લેગસી પર્સિસ્ટેડ Video ટાઇમઆઉટ મૂલ્યોને બ્રોકર ડેડલાઇન સુધી
ક્લૅમ્પ કરવામાં આવે છે; તે મર્યાદાથી વધુના નવા સેટિંગ્સ રાઇટ્સ નકારવામાં આવે છે.
`GET /api/modality-bridge/video/runtime` માટે ઑથેન્ટિકેશન અથવા રનટાઇમ પ્રોબિંગ પહેલાં
વિશ્વસનીય સ્ટૅમ્પ કરેલી લૂપબૅક લોકૅલિટી જરૂરી છે અને ત્યારબાદ મૅનેજમેન્ટ ઑથ જરૂરી
છે. તે ફક્ત `available`, સૅનિટાઇઝ કરેલા FFmpeg/ffprobe વર્ઝન્સ અને રનટાઇમ અનુપલબ્ધ
હોય ત્યારે નિશ્ચિત કારણ પરત કરે છે. આંતરિક એક્સ્ટ્રૅક્શન એન્ડપોઇન્ટ જાહેર અપલોડ API
નથી: ક્યૂ સૅચ્યુરેશન `503` સાથે `Retry-After` પરત કરે છે, કૉલર ડિસકનેક્ટ `499`
પરત કરે છે અને નિશ્ચિત બ્રોકર ડેડલાઇન `504` પરત કરે છે. રૂપાંતરિત રિસ્પોન્સિસ
Vision અથવા Audio સેગમેન્ટ્સ દૂર કર્યા વિના કેન્દ્રીય `x-omniroute-modality-bridge`
હેડરમાં `video->text;model=<visionModel>;parts=<videos>` ઉમેરે છે.

### PII માસ્કર (`piiMasker.ts`)

**બંને** સ્ટેજ પર ચાલે છે.

- **`preCall`** પેલોડને ક્લોન કરે છે, `system`, `messages`, `input` અને
  `prompt` (સાદા સ્ટ્રિંગ આઇટમ્સ સહિત) પર ચાલે છે અને સ્ટ્રિંગ `content`/`text`
  ફીલ્ડ્સ પર `processPII()` (`@/shared/utils/inputSanitizer`માંથી) લાગુ કરે છે. જ્યારે
  `PII_REDACTION_ENABLED=true` હોય ત્યારે ઓળખાયેલ PII આઉટબાઉન્ડ પેલોડમાં રિડેક્ટ
  કરવામાં આવે છે. આ `INPUT_SANITIZER_MODE`થી સ્વતંત્ર છે (જે ફક્ત પ્રોમ્પ્ટ-ઇન્જેક્શન
  નીતિને નિયંત્રિત કરે છે). જ્યારે રિડૅક્શન બંધ હોય ત્યારે કૉલ કન્ટેન્ટ ફરીથી
  લખ્યા વિના ડિટેક્શન કાઉન્ટ્સ રેકોર્ડ કરે છે.
- **`postCall`** રિસ્પોન્સને ડીપ-ક્લોન કરે છે અને `sanitizePIIResponse()` તથા
  Responses-API-શેપ માસ્કર (`maskResponsesOutput` — `output_text` અને
  `output[].content[].text`ને આવરી લે છે) ચલાવે છે. જો કોઈ રિડૅક્શન થાય, તો
  સંશોધિત રિસ્પોન્સ મૂળ રિસ્પોન્સને બદલે છે.

ગાર્ડરેલ ક્યારેય બ્લૉક કરતું નથી; તે ફક્ત ઍનોટેટ (`meta.detections`,
`meta.redacted`) કરે છે અથવા ફરીથી લખે છે.

### પ્રોમ્પ્ટ ઇન્જેક્શન (`promptInjection.ts`)

વપરાશકર્તા દ્વારા પૂરી પાડવામાં આવેલી સામગ્રીમાં વિરોધાત્મક રચનાઓ શોધે છે અને
રૂપરેખાંકિત નીતિ લાગુ કરે છે. વર્તન એન્વાયર્નમેન્ટ વેરિએબલ્સ અને કન્સ્ટ્રક્ટર
વિકલ્પો દ્વારા સંચાલિત થાય છે:

| સેટિંગ          | પર્યાવરણ ચલ                                                                                           | ડિફૉલ્ટ | અસર                                                                                                                                                                                                                    |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| સક્ષમ કરેલ      | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | જ્યારે `false` હોય, ત્યારે ગાર્ડરેલ શૉર્ટ-સર્કિટ થાય છે.                                                                                                                                                               |
| મોડ             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | ઇન્જેક્શન નીતિ: `block`, `warn`, અથવા `log`. (પાછલી સુસંગતતા માટે `redact` સ્વીકારવામાં આવે છે, પરંતુ તે ઇન્જેક્શન ટેક્સ્ટને દૂર કરતું **નથી**; વિનંતી PII પુનર્લેખન `PII_REDACTION_ENABLED` દ્વારા નિયંત્રિત થાય છે.) |
| બ્લૉક થ્રેશોલ્ડ | `blockThreshold` વિકલ્પ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ઉપનામ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | બ્લૉક કરવા માટે જરૂરી ન્યૂનતમ ગંભીરતા. ડિફૉલ્ટ રૂપે મધ્યમ ગંભીરતા ફક્ત અવલોકન માટે છે.                                                                                                                                 |

**મોડની અગ્રતા** (`getMode`): કૉલરનું `options.mode` →
`INJECTION_GUARD_MODE` **DB ફીચર-ફ્લૅગ ઓવરરાઇડ** (ડૅશબોર્ડ → સેટિંગ્સ →
ફીચર ફ્લૅગ્સ) → `INJECTION_GUARD_MODE` પર્યાવરણ ચલ → `INPUT_SANITIZER_MODE` પર્યાવરણ ચલ →
`warn`. તેથી ડૅશબોર્ડ ઓવરરાઇડ પર્યાવરણ ચલો કરતાં અગ્રતા મેળવે છે, જેથી ફીચર
ફ્લૅગ્સ UI ચાલુ ગાર્ડને લાઇવ નિયંત્રિત કરે છે (પુનઃપ્રારંભ જરૂરી નથી). DB વાંચન નિષ્ફળતા-સુરક્ષિત છે:
જો તેમાં ભૂલ થાય, તો ગાર્ડ પર્યાવરણ-આધારિત વર્તન પર પાછું ફરે છે, અને જ્યારે કોઈ
ઓવરરાઇડ સેટ ન હોય ત્યારે વર્તન માત્ર-પર્યાવરણ રિઝોલ્યુશન જેવું જ રહે છે.

શોધના સ્ત્રોતો:

1. `@/shared/utils/inputSanitizer` માંથી `sanitizeRequest()` (પાઇપલાઇનમાં
   અન્યત્ર ઉપયોગમાં લેવાતો સહિયારો ડિટેક્ટર સમૂહ).
2. બિલ્ટ-ઇન `DEFAULT_GUARD_PATTERNS` (હાલમાં `system_override_inline` અને
   `markdown_system_block`, બંને `high` ગંભીરતાવાળા).
3. કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા પસાર કરાયેલા વૈકલ્પિક `customPatterns` (સ્ટ્રિંગ્સ, regex,
   અથવા `{ name, pattern, severity }` રેકોર્ડ્સ).

જ્યારે `mode === "block"` હોય **અને** ઓછામાં ઓછી એક શોધ ગંભીરતા
થ્રેશોલ્ડને પૂર્ણ કરતી હોય, ત્યારે `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` પરત કરે છે. `warn`/`log` મોડ્સમાં ગાર્ડરેલ લૉગ કરે છે પરંતુ
કૉલને મંજૂરી આપે છે. રજિસ્ટ્રી મારફતે ગયા વિના પ્રોમ્પ્ટ્સનું મૂલ્યાંકન કરવાની જરૂર હોય તેવા
કૉલર્સ માટે સહિયારો હેલ્પર `evaluatePromptInjection()` પણ એક્સપોર્ટ કરવામાં આવ્યો છે.

**સ્કૅન મર્યાદા (v3.8.20):** ડિટેક્ટર જોડાયેલા પ્રોમ્પ્ટ ટેક્સ્ટના ફક્ત **પ્રથમ 16 KB**નું
નિરીક્ષણ કરે છે — `src/shared/utils/inputSanitizer.ts` માં
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 બાઇટ્સ). પેટર્ન લૂપ ચલાવતા પહેલાં
`detectInjection()` અને `evaluatePromptInjection()` બંને
`slice(0, MAX_INJECTION_SCAN_BYTES)` કરે છે. ઇન્જેક્શન નિર્દેશો ઇનપુટની શરૂઆતની નજીક હોય છે, તેથી આ
બહુવિધ-સો-KB પેલોડ્સ પર regex CPU/GC ને શોધ નબળી પાડ્યા વિના મર્યાદિત કરે છે (જુઓ
#3932, #4041).

### ક્રેડેન્શિયલ માસ્કર (`credentialMasker.ts`)

ડિફૉલ્ટ ચેઇનમાં છેલ્લે (પ્રાથમિકતા `95`) રહીને **બંને** તબક્કાઓ પર ચાલે છે. આઉટબાઉન્ડ પેલોડ
(સંદેશ સામગ્રી, ટૂલ-કૉલ આર્ગ્યુમેન્ટ્સ, ટૂલ પરિણામો) **અને** પ્રોવાઇડરના પ્રતિસાદમાંથી
જાણીતી API-key / secret-token પેટર્ન્સને ઢાંકે છે, જેથી પ્રોમ્પ્ટમાં પેસ્ટ કરાયેલું
ક્રેડેન્શિયલ (અથવા ટૂલ પરિણામ દ્વારા પાછું પડઘાયેલું) અપસ્ટ્રીમ પ્રોવાઇડર અથવા
ક્લાયંટ સુધી પાછું લીક ન થાય.

- **ફક્ત ઑપ્ટ-ઇન**, PII રીડેક્શન જેવી જ રૂઢિ (હાર્ડ નિયમ #20-સંલગ્ન):
  જ્યાં સુધી `settings.credentialRedactionEnabled === true` **અથવા**
  `CREDENTIAL_REDACTION_ENABLED=true` ન હોય ત્યાં સુધી નિષ્ક્રિય. તે બંધ હોય ત્યારે ગાર્ડરેલ
  કોઈ ક્રિયા કરતું નથી — તે ક્યારેય બ્લૉક કે પુનર્લેખન કરતું નથી.
- `redactCredentials()` સંપૂર્ણ પેલોડ/પ્રતિસાદ ટ્રીમાં ફરે છે (`walkValue()`,
  પ્રોટોટાઇપ-પોલ્યુશન-સુરક્ષિત, `WeakSet` દ્વારા સાઇકલ-સુરક્ષિત) અને મેળ ખાતા ભાગોને
  `[REDACTED:<type>]` પ્લેસહોલ્ડરથી બદલે છે, માત્ર ખરેખર બદલાયેલી શાખાઓનું
  ક્લોનિંગ કરે છે.
- `CREDENTIAL_PATTERNS` LLM પ્રોવાઇડર કીઝ (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ટોકન્સ (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), પેમેન્ટ કીઝ (Stripe, Square), ક્લાઉડ
  કીઝ (AWS access key, Twilio, SendGrid, Mailgun), પ્રાઇવેટ કીઝ / JWTs,
  ક્રેડેન્શિયલ ધરાવતી કનેક્શન સ્ટ્રિંગ્સ (`mongodb://user:pass@...`, વગેરે), અને
  સામાન્ય `Authorization`/`x-api-key`/`api-key`/`apikey` હેડર-વેલ્યૂ
  પેટર્નને આવરી લે છે. હેડર જેવા આકારવાળી કીઝ (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ને સામાન્ય ટેક્સ્ટ regex દ્વારા નહીં, પરંતુ રચનાત્મક રીતે ઢાંકવામાં આવે છે
  (ફક્ત વેલ્યૂ, `Bearer `/`Basic ` જેવા સ્કીમ પ્રીફિક્સ જાળવી રાખીને).
- ગાર્ડરેલ ક્યારેય બ્લૉક કરતું નથી; તે ફક્ત પુનર્લેખન (`modifiedPayload` /
  `modifiedResponse`) અને ઍનોટેશન (`meta.credentialsRedacted`, `meta.count`) કરે છે.

રિગ્રેશન ગાર્ડ: `tests/unit/credential-masker-guardrail.test.ts`.

## મૂળભૂત કરાર (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ચેઇનને તરત જ અટકાવે છે
  message?: string; // અવરોધિત કરતી વખતે દર્શાવવામાં આવે છે
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // વિનંતીને ફરી લખવા માટે preCall દ્વારા પરત કરવામાં આવે છે
  modifiedResponse?: TValue; // પ્રતિસાદને ફરી લખવા માટે postCall દ્વારા પરત કરવામાં આવે છે
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ગાર્ડરેલ `void`, `{}`, અથવા `{ block: false }` પરત કરીને "કોઈ ફેરફાર નહીં"નો સંકેત આપે છે. `modifiedPayload`/`modifiedResponse` પરત કરવાથી ચેઇનમાં આગળના ગાર્ડરેલ્સ તરફ વહેતું મૂલ્ય બદલાઈ જાય છે.
`signal?: AbortSignal` કૉલરની લાઇફસાઇકલને ગાર્ડરેલ્સ સુધી લઈ જાય છે. વિનંતી રદ થવી એ ઇરાદાપૂર્વકનો fail-open અપવાદ છે: મીડિયા બ્રિજ કામ અટકાવે છે અને જે લક્ષ્ય તેને સપોર્ટ કરતું નથી તે જાણીતું હોવા છતાં તેમાં મૂળ મીડિયા પુનઃસ્થાપિત કર્યા વિના ક્લીનઅપ કરે છે.

## રજિસ્ટ્રી (`registry.ts`)

સિંગલટન `guardrailRegistry` નીચેની સુવિધાઓ પ્રદાન કરે છે:

- `register(guardrail)` — ગાર્ડરેલ ઉમેરે છે (અથવા સામાન્યકૃત નામ દ્વારા બદલે છે) અને
  ચઢતા `priority` મુજબ ફરીથી ગોઠવે છે.
- `clear()` / `list()` — વહીવટી સહાયકો.
- `runPreCallHooks(payload, context)` — સક્રિય ગાર્ડરેલ્સ પર ક્રમશઃ ફરે છે, પેલોડને
  `modifiedPayload` મારફતે આગળ ધપાવે છે અને પ્રથમ `block: true` પર અટકે છે.
- `runPostCallHooks(response, context)` — પ્રતિસાદની બાજુએ સમાન પ્રવાહ.
- `resetGuardrailsForTests({ registerDefaults })` — સ્વચ્છ ટેસ્ટ અલગીકરણ માટે સ્ટેટ સાફ કરે છે અને વૈકલ્પિક રીતે
  ડિફૉલ્ટ્સને ફરીથી રજિસ્ટર કરે છે.

બંને રનર્સ `{ blocked, payload|response, results, guardrail?, message? }`
પરત કરે છે, જ્યાં `results` એ `GuardrailExecutionResult` રેકોર્ડ્સની એરે છે, જેમાં
દરેક ગાર્ડરેલ માટેના `blocked`, `skipped`, `modified`, `error`, અને `meta` ફીલ્ડ્સ
સમાવિષ્ટ હોય છે, જે ટ્રેસિંગ માટે ઉપયોગી છે.

### દરેક વિનંતી માટે ગાર્ડરેલ્સ અક્ષમ કરવા

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` વર્તમાન
વિનંતી માટે છોડવામાં આવનાર ગાર્ડરેલ નામોની ડુપ્લિકેટ-રહિત યાદી એકત્રિત કરે છે.
સ્ત્રોતો (બધા વૈકલ્પિક, બધા મર્જ કરવામાં આવે છે):

- `apiKeyInfo.disabledGuardrails`
- વિનંતી બોડીનું `disabledGuardrails` (ટોચના સ્તરે)
- વિનંતી બોડીનું `metadata.disabledGuardrails`
- હેડર `x-omniroute-disabled-guardrails` (અથવા જૂનું
  `x-disabled-guardrails`)

મૂલ્યો સ્ટ્રિંગ્સની એરે અથવા કૉમાથી અલગ કરેલી સ્ટ્રિંગ હોઈ શકે છે; નામોને
લોઅરકેસ kebab-caseમાં સામાન્યકૃત કરવામાં આવે છે (`pii_masker` → `pii-masker`). પરિણામ
`context.disabledGuardrails` મારફતે રજિસ્ટ્રીને આપવામાં આવે છે, જે
મેળ ખાતા ગાર્ડરેલ્સને છોડી દે છે (`results`માં `skipped: true`).

## અમલીકરણ ક્રમ

`src/sse/handlers/chat.ts` અને
`open-sse/handlers/chatCore.ts`માંથી પસાર થતી દરેક વિનંતી માટે:

1. `resolveDisabledGuardrails(...)` API કી, બોડી અને હેડર્સમાંથી સ્કિપ સૂચિ બનાવે છે.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ચડતા પ્રાથમિકતા ક્રમમાં ગાર્ડરેલ્સ ચલાવે છે:
   - અક્ષમ કરેલા ગાર્ડરેલ્સ `skipped` તરીકે નોંધાય છે.
   - દરેક ગાર્ડરેલનું `preCall`, `modifiedPayload` મારફતે પેલોડને ફરી લખી શકે છે.
   - પ્રથમ `block: true` ચેઇનને શોર્ટ-સર્કિટ કરે છે અને હેન્ડલર
     ગાર્ડરેલ અસ્વીકાર પ્રતિસાદ પરત કરે છે.
3. (સંભવિત રીતે ફરી લખાયેલો) પેલોડ કોમ્બો રાઉટિંગ અને અપસ્ટ્રીમ
   ડિસ્પેચમાં જાય છે.
4. પ્રતિસાદ તૈયાર થયા પછી, `guardrailRegistry.runPostCallHooks(...)`
   પ્રતિસાદ પર એ જ ચેઇન ચલાવે છે. અહીં `block: true` અપસ્ટ્રીમ
   પ્રતિસાદને કાઢી નાખે છે.

જે ગાર્ડરેલ્સ અપવાદ ફેંકે છે તે `error: <message>` સાથે નોંધાય છે અને
`logger.warn` મારફતે લૉગ થાય છે, પરંતુ ચેઇન ચાલુ રહે છે — ડિઝાઇન મુજબ ફેઇલ-ઓપન.

| વેરિએબલ                               | આના દ્વારા વપરાય છે        | અસર                                                                                                             |
| ------------------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | શોધને સંપૂર્ણપણે અક્ષમ કરવા માટે `false` સેટ કરો.                                                               |

| `INJECTION_GUARD_MODE`                | `prompt-injection`         | ઇન્જેક્શન ગાર્ડ માટેનો મોડ; આ DB ફીચર ફ્લેગ પણ છે, જે એન્વાયર્નમેન્ટ વેરિએબલ્સને **ઓવરરાઇડ** કરે છે (DB > ENV). |

| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` માટેનો લેગસી ઉપનામ.                                                           |

`modalityBridgeVideoTimeout`, તેમજ શેર કરેલ `modalityBridgeCache*` સેટિંગ્સનો ઉપયોગ કરે છે.

ડિપેન્ડન્સીઝ છે અને ફ્રેમ કૅપ્શનિંગ લેટન્સી અને મોડેલ ખર્ચ વધારે છે.

## કસ્ટમ ગાર્ડરેલ્સ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

પગલાં:

1. `BaseGuardrail`ને વિસ્તૃત કરતી `src/lib/guardrails/myGuardrail.ts` બનાવો.
2. `preCall` અને/અથવા `postCall` અમલમાં મૂકો.
3. કાં તો ઇમ્પોર્ટ સમયે નોંધણી કરો (`registerDefaultGuardrails`માંથી પુશ કરો) અથવા
   રનટાઇમ પર `guardrailRegistry.register(...)` કૉલ કરો — રજિસ્ટ્રી સમાન સામાન્યકૃત
   નામ ધરાવતા કોઈપણ અગાઉના ગાર્ડરેલને બદલી નાખે છે.
4. `tests/unit/` હેઠળ પરીક્ષણો ઉમેરો (હાલનાં ઉદાહરણો:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## પરીક્ષણ

જાણીતી સ્થિતિથી શરૂઆત કરવા માટે પરીક્ષણો વચ્ચે `resetGuardrailsForTests()`નો ઉપયોગ કરો.
ખાલી રજિસ્ટ્રીથી શરૂઆત કરવા માટે `{ registerDefaults: false }` પાસ કરો અને
માત્ર પરીક્ષણ હેઠળના ગાર્ડરેલ્સની નોંધણી કરો. Vision Bridge ડિપેન્ડન્સી
ઇન્જેક્શન (`deps.getSettings`, `deps.callVisionModel`) સ્વીકારે છે; Audio Bridge
સેટિંગ્સ, ક્ષમતાઓ, STT મોડેલ પસંદગી, ક્રેડેન્શિયલ તપાસો અને ટ્રાન્સક્રિપ્શન માટે
સમકક્ષ સીમ્સ ઉપલબ્ધ કરાવે છે. તેથી પરીક્ષણો DB અથવા નેટવર્ક ઍક્સેસ વિના બંને
પ્રવાહોને ચકાસી શકે છે.

## ઇન્જેક્શન-ગાર્ડ રૂટ કવરેજ અને રેડ-ટીમ (તબક્કો 8 · બ્લૉક D)

ઇન્જેક્શન-ગાર્ડ (`createInjectionGuard` / `withInjectionGuard`) વપરાશકર્તા પ્રોમ્પ્ટ્સ
સ્વીકારતા તમામ રૂટ્સને આવરી લે છે. તે `INJECTION_GUARD_MODE`નું પાલન કરે છે (ડિફૉલ્ટ
`warn` = ફક્ત લૉગ; `block` = HTTP 400 `SECURITY_001` પરત કરે છે).

| પ્રકાર           | રૂટ્સ                                                                                                                                                | ડિફૉલ્ટ મોડ |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| ટેક્સ્ટ (હાલનું) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| જનરેટિવ          | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| ડેટા             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

ટેક્સ્ટ નિષ્કર્ષણ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`ને આવરી લે છે.

**રેડ-ટીમ (દરરોજ રાત્રે, `nightly-llm-security.yml`):** promptfoo ચકાસે છે કે દરેક રૂટ
`INJECTION_GUARD_MODE=block`માં OWASP-LLM કોર્પસને બ્લૉક કરે છે; garak પ્રોબ્સ ચલાવે છે
(સિક્રેટ વિના સ્કિપ કરે છે). સુસંગતતા માટે `moderations`નો સમાવેશ કરવામાં આવ્યો છે —
બ્લૉક-મોડમાં ઑપરેટર્સ `resolveDisabledGuardrails` મારફતે તેને મુક્તિ આપી શકે છે.

રાત્રિકાલીન વર્કફ્લો (`.github/workflows/nightly-llm-security.yml`, cron + મેન્યુઅલ
ડિસ્પેચ)માં બે જૉબ્સ છે:

- **`promptfoo-guard` (બ્લૉકિંગ)** — `INJECTION_GUARD_MODE=block` સાથે
  `promptfoo eval -c promptfooconfig.yaml` ચલાવે છે. દરેક પ્રતિકૂળ કેસ (દા.ત. "અગાઉની
  તમામ સૂચનાઓ અવગણો…", DAN-શૈલીના જેલબ્રેક્સ) ખાતરી કરે છે કે પ્રતિસાદમાં
  `error.code === "SECURITY_001"` હોય, એટલે કે ગાર્ડે વિનંતીને ખરેખર નકારી હતી.
- **`garak` (સલાહકારી)** — સ્થાનિક OmniRoute ઇન્સ્ટન્સ
  (`http://localhost:20128/v1`) સામે garak `--probes promptinject,dan,leakreplay`
  ચલાવે છે. તે પ્રોવાઇડર સિક્રેટ (`PROMPTFOO_PROVIDER_KEY`) પર આધારિત છે; સિક્રેટ
  ન હોય તો સરળતાથી સ્કિપ કરે છે અને તેની પાછળ `|| true` જોડાયેલું છે, તેથી તે CIને
  નિષ્ફળ કર્યા વિના રિપોર્ટ કરે છે.

ગાર્ડ હેલ્પર (`createInjectionGuard` / `withInjectionGuard`)નું કવરેજ પ્રોમ્પ્ટ ધરાવતા
દરેક `/v1` રૂટ સુધી વિસ્તરે છે; પ્રોમ્પ્ટ ટેક્સ્ટને
`src/shared/utils/inputSanitizer.ts`માંના `extractMessageContents()` દ્વારા
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`માંથી
લેવામાં આવે છે.
