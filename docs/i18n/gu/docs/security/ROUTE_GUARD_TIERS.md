## અવલોકન

તમામ OmniRoute મેનેજમેન્ટ API રૂટને સુરક્ષાના ત્રણ સ્તરોમાંથી એકમાં
વર્ગીકૃત કરવામાં આવે છે. વર્ગીકરણ સ્થિર છે, `src/server/authz/routeGuard.ts`માં
વ્યાખ્યાયિત છે અને કોઈપણ અન્ય auth શાખા ચાલે તે પહેલાં તેનું મૂલ્યાંકન કરવામાં આવે છે.

## સ્તરો

### સ્તર 1 — LOCAL_ONLY

**આના દ્વારા અમલમાં મૂકાયેલ:** `isLocalOnlyPath(path)` → લૂપબેક હોસ્ટ તપાસ
**બાયપાસ:** ડિફૉલ્ટ રૂપે કોઈ નહીં. જ્યારે વિનંતીમાં `manage` સ્કોપ ધરાવતી માન્ય
API કી હોય ત્યારે `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`માં રહેલા પાથ માટે
મર્યાદિત અપવાદ (જુઓ [Manage-scope અપવાદ](#manage-scope-carve-out)).

આ રૂટ ચાઇલ્ડ પ્રોસેસ શરૂ કરે છે અથવા રનટાઇમ કોડ ચલાવે છે. તેમને
નોન-લૂપબેક ટ્રાફિક માટે ખુલ્લા રાખવાથી માન્ય JWT મેળવી ચૂકેલો હુમલાખોર (દા.ત.,
Cloudflared/Ngrok ટનલ મારફતે) પ્રોસેસ શરૂ કરાવી શકે — જે એક જાણીતી CVE
શ્રેણી છે ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj શું છે (હુમલાની શ્રેણી):** મેનેજમેન્ટ/એજન્ટ સર્વર
એવો એન્ડપોઇન્ટ ખુલ્લો મૂકે છે જે સબપ્રોસેસ શરૂ કરે છે (`npm install`, `node`, બ્રાઉઝર,
પ્રોક્સી, `git`, `tar`, …). જો તે એન્ડપોઇન્ટ હોસ્ટની બહારથી પહોંચી શકાય તેવો હોય — કારણ કે
ઓપરેટરે OmniRouteને nginx/Cloudflare/Tailscale ટનલ પાછળ મૂક્યું હોય અને JWT
લીક થઈ ગયું હોય, અથવા auth ખોટી રીતે ગોઠવેલું હોય — તો હુમલાખોર "APIને કૉલ કરવું"ને
"હોસ્ટ પર કમાન્ડ ચલાવવી"માં ફેરવી દે છે (રિમોટ કોડ એક્ઝિક્યુશન). OmniRoute દરેક
પ્રોસેસ શરૂ કરી શકતા રૂટ પર **કોઈપણ auth તપાસ પહેલાં, બિનશરતી રીતે લૂપબેક હોસ્ટ
તપાસ લાગુ કરીને** આ જોખમ બંધ કરે છે: ટનલ મારફતે લીક થયેલું ટોકન હજી પણ પ્રોસેસ
શરૂ કરાવતા રૂટ સુધી પહોંચી શકતું નથી.

**સંપૂર્ણ LOCAL_ONLY સમૂહ.** અધિકૃત સ્રોત
`src/server/authz/routeGuard.ts`માં રહેલા `LOCAL_ONLY_API_PREFIXES` /
`LOCAL_ONLY_API_PATTERNS` છે; નીચેનું કોષ્ટક વર્તમાન સ્થિતિને પ્રતિબિંબિત કરે છે.
`check-route-guard-membership` ગેટ પ્રોસેસ શરૂ કરી શકતા પ્રિફિક્સ હેઠળના દરેક
`route.ts`ને સૂચિબદ્ધ કરે છે અને જો કોઈપણ રૂટ local-only તરીકે વર્ગીકૃત ન હોય તો CIને નિષ્ફળ કરે છે.

#### Manage-scope અપવાદ

LOCAL_ONLY પાથના ઉપસમૂહને non-loopback પરથી પણ ઍક્સેસ કરી શકાય છે, પરંતુ માત્ર ત્યારે જ જ્યારે વિનંતીમાં એવું `Authorization: Bearer <api-key>` હોય જેના metadataમાં `manage` scope (અથવા `admin`) સામેલ હોય. આ અપવાદને દરેક પાથ માટે `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` મારફતે સ્પષ્ટ રીતે નિયંત્રિત કરવામાં આવે છે, જેથી કોઈપણ નવા LOCAL_ONLY પાથ માટે મૂળભૂત વર્તન strict-loopback જ રહે. અધિકૃતતા વિનાની વિનંતીઓ અને non-manage keys ધરાવતી વિનંતીઓ હજી પણ `403 LOCAL_ONLY` સાથે નકારવામાં આવે છે.

હાલમાં bypass કરી શકાય તેવો એકમાત્ર prefix `/api/mcp/` છે. `/api/cli-tools/runtime/` અને `/api/services/` ને ઇરાદાપૂર્વક બાકાત રાખવામાં આવ્યા છે, કારણ કે તેઓ મનસ્વી subprocesses (`npm install`, `node`) શરૂ કરી શકે છે, અને LOCAL_ONLY tier જે ચોક્કસ CVE વર્ગને અટકાવવા માટે અસ્તિત્વમાં છે તે આ જ છે.

**#7895 — `mcp:connect` સંકુચિત scope:** `/api/mcp/` અપવાદ સંકુચિત `mcp:connect` scope ધરાવતી Bearer key પણ સ્વીકારે છે (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), જેની તપાસ `src/server/authz/policies/management.ts` માં `hasMcpConnectOrManageScope()` દ્વારા થાય છે. આ માત્ર `/api/mcp/` પૂરતું મર્યાદિત છે — `mcp:connect` અન્ય કોઈપણ management route પર કોઈ અધિકાર આપતું નથી (ભવિષ્યમાં ઉમેરવામાં આવે તો અન્ય દરેક LOCAL_ONLY bypass prefix સહિત), અને તેને ઇરાદાપૂર્વક `MANAGEMENT_API_KEY_SCOPES` માંથી બાકાત રાખવામાં આવ્યું છે. `manage`/`admin` ધરાવતી key પહેલાંની જેમ જ અપવાદમાંથી પસાર થાય છે; `mcp:connect` એવા remote MCP-only callers માટે ઓછા વિશેષાધિકારવાળો વિકલ્પ છે, જેમને વ્યાપક management accessની જરૂર ન હોવી જોઈએ.

| વિનંતી                                           | પાથ                        | પરિણામ                    |
| ------------------------------------------------ | -------------------------- | ------------------------- |
| Non-loopback, Bearer નહીં                        | `/api/mcp/*`               | 403 LOCAL_ONLY            |
| Non-loopback, `manage` scope સાથે Bearer         | `/api/mcp/*`               | મંજૂરી                    |
| Non-loopback, `mcp:connect` scope સાથે Bearer    | `/api/mcp/*`               | મંજૂરી                    |
| Non-loopback, `manage`/`mcp:connect` વિના Bearer | `/api/mcp/*`               | 403 LOCAL_ONLY            |
| Non-loopback, `mcp:connect` scope સાથે Bearer    | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY            |
| Non-loopback, `manage` scope સાથે Bearer         | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY            |
| Loopback, કોઈપણ/Bearer નહીં                      | કોઈપણ LOCAL_ONLY           | મંજૂરી (gate પસાર થાય છે) |

#### ઑપરેટર માર્ગદર્શન અને ઑડિટિંગ

જો તમે OmniRoute ને reverse proxy અથવા tunnel (nginx, Caddy, Cloudflare Tunnel, Tailscale, Ngrok) પાછળ ચલાવો છો, તો loopback તપાસ ઉપરના spawn-capable routes ને હજી પણ સુરક્ષિત રાખે છે — જે વિનંતીનું client address non-loopback હોય તેને `403 LOCAL_ONLY` સાથે **auth ચાલે તે પહેલાં** નકારવામાં આવે છે, તેથી લીક થયેલું JWT spawn સુધી પહોંચી શકતું નથી. ઑપરેટરની બે જવાબદારીઓ યથાવત્ રહે છે:

- **client IP ને loopback તરીકે બનાવટી રીતે દર્શાવીને 403 ને "ઠીક" કરશો નહીં.** `X-Forwarded-For: 127.0.0.1` સેટ કરવું, અથવા source address ને loopback તરીકે ફરી લખતો proxy વાપરવો, આ tier જે RCE વર્ગને બંધ કરે છે તેને ફરીથી ખુલ્લો મૂકે છે. Proxy મારફતે dashboard/API ને ઉપલબ્ધ કરો — spawn-capable routes ને ક્યારેય નહીં.
- **Manage-scope bypass ને ન્યૂનતમ રાખો.** માત્ર `/api/mcp/` ને bypass કરી શકાય છે, અને તે પણ માત્ર `manage`-scoped API key વડે. `SPAWN_CAPABLE_PREFIXES` ને bypass list માં ક્યારેય ઉમેરી શકાતા નથી — zod schema તેમને નકારે છે અને `isLocalOnlyBypassableByManageScope` runtime પર તેમને નકારે છે (defence-in-depth), અને dashboard પર "cannot be made bypassable" નો આ જ અર્થ છે. `/api/providers/` હેઠળના dynamic-segment અને static-path spawn-capable routes (દા.ત. `/login`, `/refresh-cursor`) `src/shared/constants/spawnCapablePrefixes.ts` માં regex-આધારિત `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` સહાયક દ્વારા આવરી લેવાય છે, સપાટ `SPAWN_CAPABLE_PREFIXES` array દ્વારા નહીં — તેમને પકડવા માટે સપાટ array એ સમગ્ર `/api/providers/` prefix ને આવરી લેવો પડે, જેનો ઉપયોગ remote dashboards કાયદેસર રીતે provider CRUD માટે કરે છે તે route tree ને અતિશય વ્યાપક બનાવી દેશે.

**ઍક્સેસનું ઑડિટિંગ** — કોઈપણ off-host વિનંતી આ routes સુધી પહોંચી રહી નથી તેની ચકાસણી કરવા માટે:

- `/dashboard/settings/security` પર **Authorization Inventory** ખોલો: તે સક્રિય LOCAL_ONLY prefix list, કયા prefixes bypass કરી શકાય છે અને compile-time spawn-capable ("cannot be made bypassable") set દર્શાવે છે.
- ઉપરના prefixes સાથે non-loopback client address ધરાવતી એન્ટ્રીઓ માટે તમારા reverse-proxy / access logs માં Grep કરો. આવી કોઈપણ વિનંતીએ `403 LOCAL_ONLY` ને બદલે `200` પરત કર્યું હોય, તો તેનો અર્થ proxy વાસ્તવિક client IP ને છુપાવી રહ્યો છે — proxy ને ઠીક કરો.
- આમાંથી કોઈ એક પાથ માટે OmniRoute ના logs માં `403 LOCAL_ONLY` આવવું એ guard ઇચ્છિત રીતે કાર્ય કરી રહ્યો હોવાનું દર્શાવે છે, દબાવી દેવાની ભૂલ નથી.

**Bypass:** `requireLogin=false` હોય ત્યારે કોઈ નહીં; JWT હંમેશાં આવશ્યક છે

### નવા ઇન્સ્ટોલનું બુટસ્ટ્રૅપ માત્ર લૂપબૅક માટે છે — વાસ્તવિક પીઅર દ્વારા, `Host` દ્વારા નહીં

કોઈ મેનેજમેન્ટ પાસવર્ડ કન્ફિગર ન હોય (અને `INITIAL_PASSWORD` પણ ન હોય) ત્યારે,
`src/shared/utils/apiAuth.ts` માંનું `isAuthRequired()` અનામી બુટસ્ટ્રૅપને **માત્ર લૂપબૅક પીઅર્સ માટે** ખુલ્લું રાખે છે.
વિશ્વસનીય પીઅર સિગ્નલ્સના આધારે, નીચેના ક્રમમાં લૂપબૅક નક્કી થાય છે: ટોકન-સ્ટૅમ્પ કરાયેલ વાસ્તવિક TCP પીઅર
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, જે નીતિને દેખાય છે), પાઇપલાઇનનો પોતાનો
`AUTHZ_HEADER_PEER_LOCALITY` નિર્ણય (જે રૂટ હૅન્ડલર્સને દેખાય છે અને માત્ર
`OMNIROUTE_PEER_STAMP_TOKEN` સેટ હોય ત્યારે જ વિશ્વસનીય ગણાય છે), અથવા સીધા કૉલર્સ માટે વાસ્તવિક સૉકેટ પીઅર. `Host` /
`nextUrl.hostname` ક્યારેય તપાસવામાં આવતા નથી, અને પ્રથમ પાસવર્ડ લખવાની ક્રિયા
(`POST /api/settings/require-login`) પણ દરેક નેટવર્ક પીઅર માટે ખુલ્લી હોવાને બદલે આ જ નિયંત્રણ હેઠળ છે
(GHSA-7pq4-8pvv-rx7r). `managementPolicy` તેનો પોતાનો `peerContext` નિર્ણય
સ્પષ્ટ રીતે આગળ મોકલે છે, જેથી ORIGINAL (સ્ટ્રિપ કરતાં પહેલાંની) રિક્વેસ્ટના હેડર્સ ક્યારેય તેનો નિર્ણય લેતા નથી.

### ટિયર 3 — MANAGEMENT (ડિફૉલ્ટ)

અન્ય તમામ મેનેજમેન્ટ રૂટ્સ. `requireLogin=false` કન્ફિગર કરેલું ન હોય ત્યાં સુધી ઑથેન્ટિકેશન જરૂરી છે.
CLI ટોકન્સ આ રૂટ્સને ઑથેન્ટિકેટ કરી શકે છે (લૂપબૅક + માન્ય HMAC).

## મૂલ્યાંકનનો ક્રમ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → આગળ વધો
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → મંજૂરી આપો (management_key)
     → અન્યથા                                    → 403 LOCAL_ONLY સાથે નકારો
  2. isInternalModelSyncRequest(ctx)?
     → મંજૂરી આપો (system)
  3. hasValidCliToken(headers)?
     → મંજૂરી આપો (cli) [loopback + timingSafeEqual HMAC ચકાસણી]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → મંજૂરી આપો (dashboard_session)
     → બાયપાસ ન કરી શકાય તેવા પાથ પર manage-scope Bearer?
        → મંજૂરી આપો (management_key)
     → 401/403 સાથે નકારો
  5. requireLogin=false?
     → મંજૂરી આપો (anonymous)
```

પગલું 1ની manage-scope શાખા એકમાત્ર પ્રમાણિત પાથ છે જે
LOCAL_ONLY રૂટને સંતોષી શકે છે; auth-backend નિષ્ફળતા મોડ 503 પરત કરે છે (403 નહીં), જેથી
સમાપ્ત થયેલો DB નિઃશબ્દ રીતે "નકારો" પર ડાઉનગ્રેડ ન થાય.

## spawn કરી શકે એવો નવો રૂટ ઉમેરવો

1. `src/server/authz/routeGuard.ts`માં પાથ પ્રીફિક્સને
   `LOCAL_ONLY_API_PREFIXES`માં ઉમેરો
2. `tests/unit/authz/routeGuard.test.ts`માં એવો ટેસ્ટ ઉમેરો જે ખાતરી કરે કે
   નવા પ્રીફિક્સ માટે `isLocalOnlyPath()` true પરત કરે છે
3. **આ પગલું ક્યારેય છોડશો નહીં** — `CLAUDE.md`માં Hard Rule #15 જુઓ
4. નક્કી કરો: શું આ રૂટ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`માં પણ આવવો જોઈએ?
   ડિફૉલ્ટ જવાબ **ના** છે. રૂટને manage-scope ધારક સમક્ષ ખુલ્લો મૂકવો સુરક્ષિત હોય
   ત્યારે જ opt-in કરો (એટલે કે તે મનસ્વી વપરાશકર્તા-નિયંત્રિત કોડ spawn કરતો ન હોય).

## manage-scope દ્વારા બાયપાસ કરી શકાય એવો પાથ ઉમેરવો

1. ખાતરી કરો કે રૂટ વપરાશકર્તા દ્વારા પૂરો પાડવામાં આવેલ કોડ અથવા commands ચલાવતો નથી. જો
   ચલાવતો હોય, તો થોભો — આ carve-out તેના માટે યોગ્ય સાધન નથી.
2. `src/server/authz/routeGuard.ts`માં પ્રીફિક્સને
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`માં ઉમેરો
3. `tests/unit/authz/management-policy.test.ts`માં વિનંતીના ચારેય
   સ્વરૂપો માટે coverage ઉમેરો: Bearer નહીં (403), manage Bearer (મંજૂરી), non-manage Bearer
   (403), અને દરેક પ્રીફિક્સ માટેનું regression કે manage Bearer હોવા છતાં
   `/api/cli-tools/runtime/*` strict-loopback જ રહે છે.

## OpenAPIમાં સુરક્ષા Tiersનું દસ્તાવેજીકરણ

`docs/openapi.yaml`માં નવો રૂટ ઉમેરતી વખતે, જો રૂટનું વર્ગીકરણ
`routeGuard.ts` દ્વારા કરાયું હોય તો તેને અનુરૂપ vendor extension લાગુ કરો:

| routeGuard.ts વર્ગીકરણ       | YAML annotation            | અમલીકરણ                                          |
| ---------------------------- | -------------------------- | ------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | non-loopbackમાંથી બિનશરતી રીતે અવરોધિત           |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | `requireLogin=false` હોય ત્યારે પણ auth આવશ્યક   |
| આંતરિક admin/debug રૂટ       | `x-internal: true`         | ડિફૉલ્ટ રીતે /dashboard/api-endpointsથી છુપાયેલો |
| કોઈ નહીં (જાહેર / માનક auth) | (કોઈ annotation જરૂરી નથી) | માનક `requireLogin` દ્વારા નિયંત્રિત ઍક્સેસ      |

### માન્યતા

બે scripts YAML annotations અને `routeGuard.ts` વચ્ચેની સુસંગતતા લાગુ કરે છે:

- `scripts/check/check-openapi-coverage.mjs` — coverage < 99% હોય તો નિષ્ફળ જાય છે
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` અથવા
  `x-always-protected` annotations compile-time constantsથી અલગ હોય તો નિષ્ફળ જાય છે

બંને scripts pre-commit hook અને CIમાં ચાલે છે.

### False Positive નિયમ

જો `routeGuard.ts` constantમાં ન હોય એવા રૂટ પર `x-always-protected` અથવા
`x-loopback-only` annotation કરેલું હોય, તો coverage script નિષ્ફળ જાય છે. તેનો ઉકેલ હંમેશાં
YAMLને `routeGuard.ts` ખરેખર જે અમલમાં મૂકે છે તેની સાથે સુસંગત કરવાનો છે — enforcement logic
પણ અમલમાં મૂક્યા વિના `routeGuard.ts`માં રૂટ ઉમેરવાનો નથી.
