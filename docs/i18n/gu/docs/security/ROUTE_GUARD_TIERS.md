## અવલોકન

તમામ OmniRoute મેનેજમેન્ટ API રૂટને સુરક્ષાના ત્રણ સ્તરોમાંથી એકમાં વર્ગીકૃત કરવામાં આવે છે. વર્ગીકરણ સ્થિર છે, `src/server/authz/routeGuard.ts`માં વ્યાખ્યાયિત છે અને અન્ય કોઈપણ પ્રમાણીકરણ શાખા ચાલે તે પહેલાં તેનું મૂલ્યાંકન કરવામાં આવે છે.

## સ્તરો

### સ્તર 1 — LOCAL_ONLY

**દ્વારા લાગુ કરાયેલ:** `isLocalOnlyPath(path)` → લૂપબૅક હોસ્ટ ચકાસણી  
**બાયપાસ:** ડિફૉલ્ટ રૂપે કોઈ નહીં. જ્યારે વિનંતીમાં `manage` સ્કોપ ધરાવતી માન્ય API કી હોય ત્યારે `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`માંના પાથ માટે મર્યાદિત અપવાદ (જુઓ [મેનેજ-સ્કોપ અપવાદ](#manage-scope-carve-out)).

આ રૂટ ચાઇલ્ડ પ્રોસેસ શરૂ કરે છે અથવા રનટાઇમ કોડ ચલાવે છે. તેમને નોન-લૂપબૅક ટ્રાફિક માટે ઉપલબ્ધ કરવાથી માન્ય JWT મેળવનાર હુમલાખોર (દા.ત., Cloudflared/Ngrok ટનલ મારફતે) પ્રોસેસ શરૂ કરી શકે છે — જે એક જાણીતી CVE શ્રેણી છે ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj શું છે (હુમલાની શ્રેણી):** મેનેજમેન્ટ/એજન્ટ સર્વર એવું એન્ડપૉઇન્ટ ઉપલબ્ધ કરાવે છે જે સબપ્રોસેસ (`npm install`, `node`, બ્રાઉઝર, પ્રૉક્સી, `git`, `tar`, …) શરૂ કરે છે. જો એ એન્ડપૉઇન્ટને હોસ્ટની બહારથી ઍક્સેસ કરી શકાય — કારણ કે ઑપરેટરે OmniRouteને nginx/Cloudflare/Tailscale ટનલની પાછળ મૂક્યું હોય અને JWT લીક થયું હોય, અથવા પ્રમાણીકરણ ખોટી રીતે ગોઠવાયેલું હોય — તો હુમલાખોર "API કૉલ કરવા"ને "હોસ્ટ પર કમાન્ડ ચલાવવા"માં ફેરવી શકે છે (રિમોટ કોડ એક્ઝિક્યુશન). OmniRoute દરેક પ્રોસેસ શરૂ કરી શકતા રૂટ પર **કોઈપણ પ્રમાણીકરણ ચકાસણી પહેલાં, બિનશરતી રીતે લૂપબૅક હોસ્ટ ચકાસણી** લાગુ કરીને આ ખામી દૂર કરે છે: ટનલ પર લીક થયેલું ટોકન પણ પ્રોસેસ શરૂ કરવાની કાર્યક્ષમતા સુધી પહોંચી શકતું નથી.

**સંપૂર્ણ LOCAL_ONLY સમૂહ.** અધિકૃત સ્રોત `src/server/authz/routeGuard.ts`માં રહેલા `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` છે; નીચેનું કોષ્ટક વર્તમાન સ્થિતિ દર્શાવે છે. `check-route-guard-membership` ગેટ પ્રોસેસ શરૂ કરી શકતા પ્રિફિક્સ હેઠળની દરેક `route.ts`ની ગણતરી કરે છે અને જો કોઈપણ રૂટને માત્ર લોકલ તરીકે વર્ગીકૃત ન કરવામાં આવ્યો હોય તો CIને નિષ્ફળ કરે છે.

| `/api/providers/{id}/chatgpt-web-codex-doctor` (regex)                                                   | સ્થાનિક Codex CLI ઇન્સ્ટૉલેશનનું નિદાન કરે છે (બાઇનરી શરૂ કરે છે)                                                |

**ઉલ્લંઘન પર પ્રતિસાદ:** `403 LOCAL_ONLY`

#### મેનેજ-સ્કોપ અપવાદ

LOCAL_ONLY પાથનો એક ઉપસમૂહ નૉન-લૂપબૅક પરથી પણ ઍક્સેસ કરી શકાય છે, પરંતુ માત્ર
ત્યારે જ જ્યારે વિનંતીમાં `Authorization: Bearer <api-key>` હોય અને તેના
મેટાડેટામાં `manage` સ્કોપ (અથવા `admin`) સામેલ હોય. આ અપવાદને
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` દ્વારા દરેક પાથ માટે સ્પષ્ટ રીતે નિયંત્રિત
કરવામાં આવે છે, જેથી કોઈપણ નવા LOCAL_ONLY પાથ માટે ડિફૉલ્ટ કડક-લૂપબૅક જ રહે.
પ્રમાણિત ન થયેલી વિનંતીઓ અને નૉન-મેનેજ કી ધરાવતી વિનંતીઓ હજુ પણ
`403 LOCAL_ONLY` સાથે નકારવામાં આવે છે.

હાલમાં બાયપાસ કરી શકાય એવો એકમાત્ર પ્રિફિક્સ `/api/mcp/` છે. `/api/cli-tools/runtime/` અને
`/api/services/`ને ઇરાદાપૂર્વક બાકાત રાખવામાં આવ્યા છે, કારણ કે તેઓ મનસ્વી
સબપ્રોસેસ (`npm install`, `node`) શરૂ કરી શકે છે, અને LOCAL_ONLY સ્તર
જે CVE વર્ગને રોકવા માટે અસ્તિત્વમાં છે તે ચોક્કસ આ જ છે.

#### ઑપરેટર માર્ગદર્શન અને ઑડિટિંગ

જો તમે OmniRouteને રિવર્સ પ્રૉક્સી અથવા ટનલ (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) પાછળ ચલાવો છો, તો પણ લૂપબૅક તપાસ ઉપરના શરૂ કરવાની
ક્ષમતા ધરાવતા રૂટ્સને સુરક્ષિત રાખે છે — જે વિનંતીનું ક્લાયન્ટ ઍડ્રેસ નૉન-લૂપબૅક
હોય તેને **ઑથેન્ટિકેશન ચાલે તે પહેલાં** `403 LOCAL_ONLY` સાથે નકારવામાં આવે છે,
જેથી લીક થયેલું JWT પણ કોઈ પ્રોસેસ શરૂ કરવા સુધી પહોંચી શકતું નથી. ઑપરેટરની બે
જવાબદારીઓ હજુ પણ રહે છે:

- **ક્લાયન્ટ IPને લૂપબૅક તરીકે બનાવટી દર્શાવીને 403ને "ઠીક" કરશો નહીં.**
  `X-Forwarded-For: 127.0.0.1` સેટ કરવાથી, અથવા સોર્સ ઍડ્રેસને
  લૂપબૅક તરીકે ફરી લખતી પ્રૉક્સી વાપરવાથી, આ સ્તર જે RCE વર્ગને બંધ કરે છે તે જ
  ફરીથી ખુલ્લો થઈ જાય છે. ડૅશબોર્ડ/APIને પ્રૉક્સી મારફતે એક્સપોઝ કરો — શરૂ કરવાની
  ક્ષમતા ધરાવતા રૂટ્સને ક્યારેય નહીં.
- **મેનેજ-સ્કોપ બાયપાસને ન્યૂનતમ રાખો.** માત્ર `/api/mcp/`ને બાયપાસ કરી શકાય છે,
  અને તે પણ માત્ર `manage`-સ્કોપ ધરાવતી API કીથી. `SPAWN_CAPABLE_PREFIXES`ને
  બાયપાસ સૂચિમાં ક્યારેય ઉમેરી શકાતા નથી — zod સ્કીમા તેમને નકારે છે અને
  `isLocalOnlyBypassableByManageScope` તેમને રનટાઇમ પર નકારે છે (સ્તરીય સુરક્ષા),
  અને ડૅશબોર્ડમાં "બાયપાસ કરી શકાય તેવું બનાવી શકાતું નથી"નો અર્થ આ જ છે.
  `/api/providers/` હેઠળના ડાયનેમિક-સેગમેન્ટ અને સ્ટૅટિક-પાથ ધરાવતા શરૂ કરવાની
  ક્ષમતાવાળા રૂટ્સ (દા.ત. `/login`, `/refresh-cursor`)ને
  `src/shared/constants/spawnCapablePrefixes.ts`માં regex-આધારિત
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` સાથી દ્વારા
  આવરી લેવામાં આવે છે, સપાટ `SPAWN_CAPABLE_PREFIXES` ઍરે દ્વારા નહીં — તેમને
  પકડવા માટે સપાટ ઍરેમાં આખા `/api/providers/` પ્રિફિક્સને આવરી લેવો પડે,
  જે દૂરસ્થ ડૅશબોર્ડ દ્વારા પ્રોવાઇડર CRUD માટે યોગ્ય રીતે વપરાતા રૂટ ટ્રીને
  અતિશય વ્યાપક રીતે મર્યાદિત કરી દેશે.

**ઍક્સેસનું ઑડિટિંગ** — આ રૂટ્સ સુધી હોસ્ટની બહારથી કશું પહોંચી રહ્યું નથી તેની ખાતરી કરવા માટે:

- `/dashboard/settings/security` પર **અધિકૃતતા ઇન્વેન્ટરી** ખોલો: તે
  જીવંત LOCAL_ONLY પ્રીફિક્સ સૂચિ, કયા પ્રીફિક્સને બાયપાસ કરી શકાય છે અને કમ્પાઇલ-ટાઇમ
  spawn-સક્ષમ ("બાયપાસ કરી શકાય તેવા બનાવી શકાતા નથી") સમૂહ દર્શાવે છે.
- ઉપરના પ્રીફિક્સ સાથે નોન-લૂપબૅક ક્લાયન્ટ સરનામું જોડાયેલું હોય તે માટે તમારા રિવર્સ-પ્રોક્સી / ઍક્સેસ લૉગ્સમાં
  Grep કરો. આવી કોઈ પણ હિટે `403 LOCAL_ONLY`ને બદલે `200` પરત કર્યું હોય,
  તો તેનો અર્થ એ છે કે પ્રોક્સી વાસ્તવિક ક્લાયન્ટ IPને છુપાવી રહી છે — પ્રોક્સીને સુધારો.
- આમાંના કોઈ એક પાથ માટે OmniRouteના લૉગ્સમાં `403 LOCAL_ONLY` આવવું એ ગાર્ડ
  અપેક્ષા મુજબ કામ કરી રહ્યો છે તેનો સંકેત છે, દબાવી દેવાની ભૂલ નથી.

### નવા ઇન્સ્ટોલનું બૂટસ્ટ્રૅપ માત્ર લૂપબૅક માટે છે — વાસ્તવિક પિયર મુજબ, `Host` મુજબ નહીં

કોઈ મેનેજમેન્ટ પાસવર્ડ કૉન્ફિગર ન હોય (અને `INITIAL_PASSWORD` પણ ન હોય) ત્યારે,
`src/shared/utils/apiAuth.ts`માં `isAuthRequired()` અનામી બૂટસ્ટ્રૅપને **માત્ર લૂપબૅક પિયર્સ માટે** ખુલ્લું રાખે છે.
લૂપબૅકનો નિર્ણય વિશ્વસનીય પિયર સંકેતો પરથી, આ ક્રમમાં લેવાય છે: ટોકન-સ્ટૅમ્પ કરાયેલ વાસ્તવિક TCP પિયર
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, જેને નીતિ જુએ છે), પાઇપલાઇનનો પોતાનો
`AUTHZ_HEADER_PEER_LOCALITY` ચુકાદો (જે રૂટ હૅન્ડલર્સ જુએ છે અને ફક્ત
`OMNIROUTE_PEER_STAMP_TOKEN` સેટ હોય ત્યારે જ વિશ્વસનીય છે), અથવા સીધા કૉલર્સ માટે વાસ્તવિક સૉકેટ પિયર. `Host` /
`nextUrl.hostname`નો ક્યારેય વિચાર કરવામાં આવતો નથી અને પ્રથમ પાસવર્ડ લખવાની ક્રિયા
(`POST /api/settings/require-login`) દરેક નેટવર્ક પિયર માટે ખુલ્લી હોવાને બદલે સમાન
મર્યાદા હેઠળ છે (GHSA-7pq4-8pvv-rx7r). `managementPolicy` તેનો પોતાનો `peerContext` ચુકાદો
સ્પષ્ટ રીતે નીચે મોકલે છે, જેથી ORIGINAL (સ્ટ્રિપ કરતાં પહેલાંની) વિનંતીના હેડર્સ તેનો નિર્ણય ક્યારેય ન કરે.

### ટિયર 3 — MANAGEMENT (ડિફૉલ્ટ)

અન્ય તમામ મેનેજમેન્ટ રૂટ્સ. `requireLogin=false`
કૉન્ફિગર ન હોય ત્યાં સુધી પ્રમાણીકરણ જરૂરી છે. CLI ટોકન્સ આ રૂટ્સને પ્રમાણિત કરી શકે છે (લૂપબૅક + માન્ય HMAC).

## મૂલ્યાંકન ક્રમ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → લૂપબૅક                                  → આગળ વધો
     → નોન-લૂપબૅક, manage-સ્કોપ Bearer
        AND isLocalOnlyBypassableByManageScope   → મંજૂરી આપો (management_key)
     → અન્યથા                                    → 403 LOCAL_ONLY સાથે નકારો
  2. isInternalModelSyncRequest(ctx)?
     → મંજૂરી આપો (system)
  3. hasValidCliToken(headers)?
     → મંજૂરી આપો (cli) [લૂપબૅક + timingSafeEqual HMAC ચકાસણી]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → મંજૂરી આપો (dashboard_session)
     → બાયપાસ ન કરી શકાય તેવા પાથ પર manage-સ્કોપ Bearer?
        → મંજૂરી આપો (management_key)
     → 401/403 સાથે નકારો
  5. requireLogin=false?
     → મંજૂરી આપો (anonymous)
```

પગલું 1ની manage-સ્કોપ શાખા એકમાત્ર પ્રમાણિત પાથ છે જે
LOCAL_ONLY રૂટને સંતોષી શકે છે; auth-backend નિષ્ફળતા મોડ 503 પરત કરે છે (403 નહીં), જેથી
સમાપ્ત થયેલ DB મૌન રીતે "નકારો" પર ડાઉનગ્રેડ ન થાય.

## નવો spawn-સક્ષમ રૂટ ઉમેરવો

1. `src/server/authz/routeGuard.ts`માં `LOCAL_ONLY_API_PREFIXES`માં પાથ પ્રીફિક્સ ઉમેરો
2. `tests/unit/authz/routeGuard.test.ts`માં એક ટેસ્ટ ઉમેરો જે ખાતરી કરે કે
   નવા પ્રીફિક્સ માટે `isLocalOnlyPath()` true પરત કરે છે
3. **આ પગલું ક્યારેય છોડશો નહીં** — `CLAUDE.md`માં કડક નિયમ #15 જુઓ
4. નક્કી કરો: શું આ રૂટ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`માં પણ સામેલ થવો જોઈએ?
   ડિફૉલ્ટ જવાબ **ના** છે. રૂટને manage-સ્કોપ ધારક માટે ખુલ્લો મૂકવો સુરક્ષિત હોય
   ત્યારે જ ઑપ્ટ-ઇન કરો (એટલે કે તે વપરાશકર્તા દ્વારા નિયંત્રિત મનસ્વી કોડ spawn કરતો ન હોય).

## manage-સ્કોપ દ્વારા બાયપાસ કરી શકાય તેવો પાથ ઉમેરવો

1. ખાતરી કરો કે રૂટ વપરાશકર્તા દ્વારા પૂરો પાડવામાં આવેલ કોડ અથવા કમાન્ડ ચલાવતો નથી. જો તે
   ચલાવતો હોય, તો અટકો — આ અપવાદ તે માટે યોગ્ય સાધન નથી.
2. `src/server/authz/routeGuard.ts`માં `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` સાથે પ્રીફિક્સ જોડો
3. `tests/unit/authz/management-policy.test.ts`માં ચારેય
   રિક્વેસ્ટ સ્વરૂપો માટે કવરેજ ઉમેરો: Bearer વગર (403), manage Bearer (મંજૂરી), non-manage Bearer
   (403), અને પ્રતિ-પ્રીફિક્સ રિગ્રેશન કે manage Bearer હોવા છતાં `/api/cli-tools/runtime/*`
   strict-loopback જ રહે છે.

## OpenAPIમાં સુરક્ષા ટિયર્સનું દસ્તાવેજીકરણ

`docs/openapi.yaml`માં નવો રૂટ ઉમેરતી વખતે, જો રૂટને `routeGuard.ts` દ્વારા વર્ગીકૃત
કરવામાં આવ્યો હોય, તો અનુરૂપ vendor extension લાગુ કરો:

| routeGuard.ts વર્ગીકરણ       | YAML ઍનોટેશન               | અમલીકરણ                                         |
| ---------------------------- | -------------------------- | ----------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | નોન-લૂપબૅકથી બિનશરતી અવરોધિત                    |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | `requireLogin=false` હોવા છતાં auth આવશ્યક      |
| આંતરિક admin/debug રૂટ       | `x-internal: true`         | ડિફૉલ્ટ રૂપે /dashboard/api-endpointsથી છુપાયેલ |
| કોઈ નહીં (જાહેર / માનક auth) | (કોઈ ઍનોટેશન જરૂરી નથી)    | માનક `requireLogin`-નિયંત્રિત ઍક્સેસ            |

### માન્યતા

બે સ્ક્રિપ્ટ્સ YAML ઍનોટેશન્સ અને `routeGuard.ts` વચ્ચે સુસંગતતા લાગુ કરે છે:

- `scripts/check/check-openapi-coverage.mjs` — કવરેજ < 99% હોય તો નિષ્ફળ થાય છે
- `scripts/check/check-openapi-security-tiers.mjs` — જો `x-loopback-only` અથવા
  `x-always-protected` ઍનોટેશન્સ compile-time કૉન્સ્ટન્ટ્સથી અલગ હોય તો નિષ્ફળ થાય છે

બંને સ્ક્રિપ્ટ્સ pre-commit hook અને CIમાં ચાલે છે.

### False Positive નિયમ

જો `routeGuard.ts` કૉન્સ્ટન્ટમાં ન હોય તેવા રૂટ પર `x-always-protected` અથવા `x-loopback-only`
ઍનોટેટ કરવામાં આવે, તો કવરેજ સ્ક્રિપ્ટ નિષ્ફળ થાય છે. ઉકેલ હંમેશાં YAMLને
`routeGuard.ts` ખરેખર જે લાગુ કરે છે તેની સાથે સંરેખિત કરવાનો છે — અમલીકરણ લૉજિક પણ લાગુ કર્યા વિના
રૂટ્સને `routeGuard.ts`માં ઉમેરવાનો નથી.
