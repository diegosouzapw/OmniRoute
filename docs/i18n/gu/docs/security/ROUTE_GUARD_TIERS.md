## અવલોકન

તમામ OmniRoute મેનેજમેન્ટ API રૂટને સુરક્ષાના ત્રણ સ્તરોમાંથી એકમાં
વર્ગીકૃત કરવામાં આવે છે. વર્ગીકરણ સ્થિર છે, `src/server/authz/routeGuard.ts`માં
વ્યાખ્યાયિત છે અને કોઈપણ અન્ય auth શાખા ચાલે તે પહેલાં તેનું મૂલ્યાંકન કરવામાં આવે છે.

## ટિયર્સ

### ટિયર 1 — LOCAL_ONLY

**દ્વારા લાગુ કરાયેલ:** `isLocalOnlyPath(path)` → લૂપબેક હોસ્ટ ચેક
**બાયપાસ:** ડિફૉલ્ટ રૂપે કોઈ નહીં. `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` માં પાથ માટે સાંકડો કાર્વ-આઉટ જ્યારે વિનંતી `manage` સ્કોપ સાથે માન્ય API કી ધરાવે છે (જુઓ [મેનેજ-સ્કોપ કાર્વ-આઉટ](#manage-scope-carve-out)).

આ રૂટ્સ ચાઈલ્ડ પ્રક્રિયાઓ શરૂ કરે છે અથવા રનટાઈમ કોડ એક્ઝિક્યુટ કરે છે. તેમને નોન-લૂપબેક ટ્રાફિક પર ખુલ્લા કરવાથી હુમલાખોરને માન્ય JWT (દા.ત., Cloudflared/Ngrok ટનલ દ્વારા) મેળવનારને પ્રક્રિયા શરૂ કરવા દેશે — એક જાણીતો CVE ક્લાસ ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj શું છે (હુમલાનો વર્ગ):** એક મેનેજમેન્ટ/એજન્ટ સર્વર એક એન્ડપોઇન્ટને ખુલ્લો પાડે છે જે સબપ્રોસેસ શરૂ કરે છે (`npm install`, `node`, એક બ્રાઉઝર, એક પ્રોક્સી, `git`, `tar`, …). જો તે એન્ડપોઇન્ટ ઑફ-હોસ્ટથી પહોંચી શકાય તેવું હોય — કારણ કે ઑપરેટરે OmniRoute ને nginx/Cloudflare/Tailscale ટનલ પાછળ મૂક્યું હતું અને એક JWT લીક થયું હતું, અથવા ઑથ ખોટી રીતે ગોઠવેલું હતું — તો હુમલાખોર "API કૉલ કરો" ને "હોસ્ટ પર કમાન્ડ ચલાવો" (રિમોટ કોડ એક્ઝિક્યુશન) માં ફેરવે છે. OmniRoute આને દરેક સ્પૉન-સક્ષમ રૂટ પર **કોઈપણ ઑથ ચેક પહેલાં, બિનશરતી રીતે લૂપબેક હોસ્ટ ચેક** લાગુ કરીને બંધ કરે છે: ટનલ પર લીક થયેલું ટોકન હજુ પણ સ્પૉન સુધી પહોંચી શકતું નથી.

**સંપૂર્ણ LOCAL_ONLY સેટ.** અધિકૃત સ્ત્રોત `src/server/authz/routeGuard.ts` માં `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` છે; નીચેનું કોષ્ટક વર્તમાન સ્થિતિને પ્રતિબિંબિત કરે છે. `check-route-guard-membership` ગેટ સ્પૉન-સક્ષમ પ્રિફિક્સ હેઠળના દરેક `route.ts` ને ગણે છે અને જો કોઈ સ્થાનિક-માત્ર વર્ગીકૃત ન હોય તો CI નિષ્ફળ જાય છે.

#### મેનેજ-સ્કોપ કાર્વ-આઉટ

`LOCAL_ONLY` પાથનો એક સબસેટ નોન-લૂપબેકથી પણ ઍક્સેસ કરી શકાય છે જો અને ફક્ત જો વિનંતી `Authorization: Bearer <api-key>` ધરાવતી હોય જેના મેટાડેટામાં `manage` સ્કોપ (અથવા `admin`) શામેલ હોય. કાર્વ-આઉટ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` દ્વારા સ્પષ્ટપણે પ્રતિ-પાથ ગેટ કરવામાં આવે છે જેથી કોઈપણ નવા `LOCAL_ONLY` પાથ માટે ડિફોલ્ટ સ્ટ્રિક્ટ-લૂપબેક રહે. અપ્રમાણિત વિનંતીઓ અને નોન-મેનેજ કી સાથેની વિનંતીઓ હજુ પણ `403 LOCAL_ONLY` સાથે નકારવામાં આવે છે.

આજે એકમાત્ર બાયપાસ કરી શકાય તેવું પ્રિફિક્સ `/api/mcp/` છે. `/api/cli-tools/runtime/` અને `/api/services/` ને ઇરાદાપૂર્વક બાકાત રાખવામાં આવ્યા છે કારણ કે તેઓ મનસ્વી સબપ્રોસેસ (જેમ કે `npm install`, `node`) શરૂ કરી શકે છે, જે `LOCAL_ONLY` ટિયર અટકાવવા માટે અસ્તિત્વમાં છે તે ચોક્કસ `CVE` ક્લાસ છે.

**#7895 — `mcp:connect` નેરો સ્કોપ:** `/api/mcp/` કાર્વ-આઉટ `mcp:connect` નેરો સ્કોપ (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`) ધરાવતી બેરર કી પણ સ્વીકારે છે, જે `src/server/authz/policies/management.ts` માં `hasMcpConnectOrManageScope()` દ્વારા તપાસવામાં આવે છે. આ ફક્ત `/api/mcp/` સુધી જ સ્કોપ થયેલું છે — `mcp:connect` અન્ય કોઈપણ મેનેજમેન્ટ રૂટ પર કંઈપણ મંજૂર કરતું નથી (અન્ય દરેક `LOCAL_ONLY` બાયપાસ પ્રિફિક્સ સહિત, જો ક્યારેય ઉમેરવામાં આવે તો), અને તેને `MANAGEMENT_API_KEY_SCOPES` માંથી ઇરાદાપૂર્વક બાકાત રાખવામાં આવ્યું છે. `manage`/`admin` ધરાવતી કી પહેલાની જેમ જ કાર્વ-આઉટમાંથી પસાર થાય છે; `mcp:connect` એ રિમોટ `MCP`-માત્ર કૉલર્સ માટે ઓછો-વિશેષાધિકાર ધરાવતો વિકલ્પ છે જેમને વ્યાપક મેનેજમેન્ટ ઍક્સેસની જરૂર ન હોવી જોઈએ.

| Request                                             | Path                       | Result                  |
| --------------------------------------------------- | -------------------------- | ----------------------- |
| Non-loopback, no Bearer                             | `/api/mcp/*`               | 403 LOCAL_ONLY          |
| Non-loopback, Bearer with `manage` scope            | `/api/mcp/*`               | મંજૂર                   |
| Non-loopback, Bearer with `mcp:connect` scope       | `/api/mcp/*`               | મંજૂર                   |
| Non-loopback, Bearer without `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY          |
| Non-loopback, Bearer with `mcp:connect` scope       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY          |
| Non-loopback, Bearer with `manage` scope            | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY          |
| Loopback, any/no Bearer                             | any LOCAL_ONLY             | મંજૂર (ગેટ પસાર થાય છે) |

#### ઑપરેટર માર્ગદર્શન અને ઑડિટિંગ

જો તમે રિવર્સ પ્રોક્સી અથવા ટનલ (જેમ કે `nginx`, `Caddy`, `Cloudflare Tunnel`, `Tailscale`, `Ngrok`) પાછળ `OmniRoute` ચલાવો છો, તો લૂપબેક ચેક હજુ પણ ઉપરના સ્પૉન-સક્ષમ રૂટ્સને સુરક્ષિત કરે છે — જે વિનંતીનું ક્લાયંટ સરનામું નોન-લૂપબેક હોય તેને ઑથ રન થાય તે પહેલાં `403 LOCAL_ONLY` સાથે નકારવામાં આવે છે, જેથી લીક થયેલ `JWT` સ્પૉન સુધી પહોંચી ન શકે. બે ઑપરેટર જવાબદારીઓ બાકી રહે છે:

- **ક્લાયંટ IP ને લૂપબેક તરીકે ફોર્જ કરીને 403 ને "ફિક્સ" કરશો નહીં.** `X-Forwarded-For: 127.0.0.1` સેટ કરવું, અથવા સોર્સ એડ્રેસને લૂપબેકમાં ફરીથી લખતી પ્રોક્સી, આ ટિયર બંધ કરે છે તે જ `RCE` ક્લાસને ફરીથી ખોલે છે. ડેશબોર્ડ/API ને પ્રોક્સી દ્વારા એક્સપોઝ કરો — સ્પૉન-સક્ષમ રૂટ્સને ક્યારેય નહીં.
- **મેનેજ-સ્કોપ બાયપાસને ન્યૂનતમ રાખો.** ફક્ત `/api/mcp/` જ બાયપાસ કરી શકાય તેવું છે, અને તે પણ ફક્ત `manage`-સ્કોપવાળી API કી સાથે. `SPAWN_CAPABLE_PREFIXES` ને ક્યારેય બાયપાસ સૂચિમાં ઉમેરી શકાતા નથી — `zod` સ્કીમા તેમને નકારે છે અને `isLocalOnlyBypassableByManageScope` તેમને રનટાઇમ પર નકારે છે (ડિફેન્સ-ઇન-ડેપ્થ), જેનો અર્થ ડેશબોર્ડ "બાયપાસ કરી શકાતું નથી" દ્વારા થાય છે. `/api/providers/` હેઠળના ડાયનેમિક-સેગમેન્ટ અને સ્ટેટિક-પાથ સ્પૉન-સક્ષમ રૂટ્સ (દા.ત. `/login`, `/refresh-cursor`) `src/shared/constants/spawnCapablePrefixes.ts` માં `regex`-આધારિત `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` કમ્પેનિયન દ્વારા આવરી લેવામાં આવે છે, ફ્લેટ `SPAWN_CAPABLE_PREFIXES` એરે દ્વારા નહીં — ફ્લેટ એરેને તેમને પકડવા માટે સમગ્ર `/api/providers/` પ્રિફિક્સને આવરી લેવો પડશે, જે રિમોટ ડેશબોર્ડ્સ પ્રદાતા `CRUD` માટે કાયદેસર રીતે ઉપયોગ કરે છે તે રૂટ ટ્રીને વધુ પડતું વિસ્તૃત કરશે.

**ઍક્સેસનું ઑડિટિંગ** — એ ચકાસવા માટે કે હોસ્ટની બહાર કંઈપણ આ રૂટ્સ સુધી પહોંચી રહ્યું નથી:

- `/dashboard/settings/security` પર **ઓથોરાઇઝેશન ઇન્વેન્ટરી** ખોલો: તે લાઇવ LOCAL_ONLY પ્રીફિક્સ સૂચિ દર્શાવે છે, કયા પ્રીફિક્સ બાયપાસ કરી શકાય તેવા છે, અને કમ્પાઇલ-ટાઇમ સ્પૉન-કેપેબલ ("બાયપાસ કરી શકાય તેવા બનાવી શકાતા નથી") સેટ.
- ઉપરના પ્રીફિક્સને નોન-લૂપબેક ક્લાયંટ એડ્રેસ સાથે જોડીને તમારા રિવર્સ-પ્રોક્સી / એક્સેસ લોગ્સમાં ગ્રેપ કરો. `403 LOCAL_ONLY` ને બદલે `200` પરત કરનાર કોઈપણ આવી હિટનો અર્થ એ છે કે પ્રોક્સી વાસ્તવિક ક્લાયંટ IP ને માસ્ક કરી રહી છે — પ્રોક્સીને ઠીક કરો.
- આમાંથી કોઈ એક પાથ માટે OmniRoute ના લોગ્સમાં `403 LOCAL_ONLY` એ ગાર્ડ અપેક્ષા મુજબ કામ કરી રહ્યો છે, તેને દબાવવાની ભૂલ નથી.

`/api/settings/obsidian` તેના `/webdav` ચાઇલ્ડને આવરી લે છે: `POST` WebDAV ફાઇલ સેવાને — Next.js પહેલાં કસ્ટમ Node લેયર દ્વારા સેવા અપાય છે, આ પાઇપલાઇનની બહાર — કૉલર-પસંદ કરેલા રૂટ પર નિર્દેશ કરે છે અને તાજી બનાવેલી મૂળભૂત ઓળખપત્રોને ઇકો કરે છે, `DELETE` તેમને ફેરવે છે, અને પેરેન્ટ `POST` Obsidian REST API ટોકન સ્ટોર કરે છે. GHSA-62vw એ ફક્ત `GET` પાસવર્ડના ખુલાસાને માસ્ક કર્યો હતો; ઇશ્યુઅન્સ હજુ પણ ફેલ-ઓપન ટિયર પર હતું (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` વધુમાં એવા વૉલ્ટને નકારે છે જે ડેટા ડિરેક્ટરી છે, તેની અંદર છે, અથવા તેમાં ડેટા ડિરેક્ટરી શામેલ છે.

### તાજા ઇન્સ્ટોલનું બુટસ્ટ્રેપ ફક્ત લૂપબેક-ઓન્લી છે — વાસ્તવિક પીઅર દ્વારા, `Host` દ્વારા નહીં

કોઈ મેનેજમેન્ટ પાસવર્ડ કન્ફિગર ન હોય (અને કોઈ `INITIAL_PASSWORD` ન હોય) ત્યારે, `src/shared/utils/apiAuth.ts` માં `isAuthRequired()` અનામી બુટસ્ટ્રેપને **ફક્ત લૂપબેક પીઅર્સ માટે** ખુલ્લું રાખે છે. લૂપબેક વિશ્વસનીય પીઅર સિગ્નલો પરથી નક્કી થાય છે, ક્રમમાં: ટોકન-સ્ટેમ્પ્ડ વાસ્તવિક TCP પીઅર (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, જે પોલિસી જુએ છે), પાઇપલાઇનનો પોતાનો `AUTHZ_HEADER_PEER_LOCALITY` ચુકાદો (જે રૂટ હેન્ડલર્સ જુએ છે, `OMNIROUTE_PEER_STAMP_TOKEN` સેટ હોય ત્યારે જ વિશ્વસનીય), અથવા સીધા કૉલર્સ માટે વાસ્તવિક સોકેટ પીઅર. `Host` / `nextUrl.hostname` ક્યારેય સલાહ લેવામાં આવતી નથી, અને પ્રથમ-પાસવર્ડ લખવું (`POST /api/settings/require-login`) દરેક નેટવર્ક પીઅર માટે ખુલ્લું રાખવાને બદલે સમાન અવરોધ હેઠળ છે (GHSA-7pq4-8pvv-rx7r). `managementPolicy` તેના પોતાના `peerContext` ચુકાદાને સ્પષ્ટપણે નીચે પસાર કરે છે, જેથી ORIGINAL (પ્રી-સ્ટ્રીપ) વિનંતીના હેડર્સ ક્યારેય તે નક્કી કરતા નથી.

### ટિયર 3 — મેનેજમેન્ટ (ડિફોલ્ટ)

અન્ય તમામ મેનેજમેન્ટ રૂટ્સ. `requireLogin=false` કન્ફિગર ન હોય ત્યાં સુધી પ્રમાણીકરણ જરૂરી છે. CLI ટોકન્સ આ રૂટ્સને પ્રમાણિત કરી શકે છે (લૂપબેક + માન્ય HMAC).

```

     → loopback                                  → આગળ વધો
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → મંજૂરી આપો (management_key)
     → અન્યથા                                    → 403 LOCAL_ONLY સાથે નકારો
  2. isInternalModelSyncRequest(ctx)?
     → મંજૂરી આપો (system)
  3. hasValidCliToken(headers)?
     → મંજૂરી આપો (cli) [loopback + timingSafeEqual HMAC ચકાસણી]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → મંજૂરી આપો (dashboard_session)
     → બાયપાસ ન કરી શકાય તેવા પાથ પર manage-scope Bearer?
        → મંજૂરી આપો (management_key)
     → 401/403 સાથે નકારો
  5. requireLogin=false?
     → મંજૂરી આપો (anonymous)
```

પગલું 1ની manage-scope શાખા એકમાત્ર પ્રમાણિત પાથ છે જે
LOCAL_ONLY રૂટને સંતોષી શકે છે; auth-backend નિષ્ફળતા મોડ 503 પરત કરે છે (403 નહીં), જેથી
સમાપ્ત થયેલો DB નિઃશબ્દ રીતે "નકારો" પર ડાઉનગ્રેડ ન થાય.

## spawn કરી શકે એવો નવો રૂટ ઉમેરવો

1. `src/server/authz/routeGuard.ts`માં પાથ પ્રીફિક્સને
   `LOCAL_ONLY_API_PREFIXES`માં ઉમેરો
2. `tests/unit/authz/routeGuard.test.ts`માં એવો ટેસ્ટ ઉમેરો જે ખાતરી કરે કે
   નવા પ્રીફિક્સ માટે `isLocalOnlyPath()` true પરત કરે છે
3. **આ પગલું ક્યારેય છોડશો નહીં** — `CLAUDE.md`માં Hard Rule #15 જુઓ
4. નક્કી કરો: શું આ રૂટ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`માં પણ આવવો જોઈએ?
   ડિફૉલ્ટ જવાબ **ના** છે. રૂટને manage-scope ધારક સમક્ષ ખુલ્લો મૂકવો સુરક્ષિત હોય
   ત્યારે જ opt-in કરો (એટલે કે તે મનસ્વી વપરાશકર્તા-નિયંત્રિત કોડ spawn કરતો ન હોય).

## manage-scope દ્વારા બાયપાસ કરી શકાય એવો પાથ ઉમેરવો

1. ખાતરી કરો કે રૂટ વપરાશકર્તા દ્વારા પૂરો પાડવામાં આવેલ કોડ અથવા commands ચલાવતો નથી. જો
   ચલાવતો હોય, તો થોભો — આ carve-out તેના માટે યોગ્ય સાધન નથી.
2. `src/server/authz/routeGuard.ts`માં પ્રીફિક્સને
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`માં ઉમેરો
3. `tests/unit/authz/management-policy.test.ts`માં વિનંતીના ચારેય
   સ્વરૂપો માટે coverage ઉમેરો: Bearer નહીં (403), manage Bearer (મંજૂરી), non-manage Bearer
   (403), અને દરેક પ્રીફિક્સ માટેનું regression કે manage Bearer હોવા છતાં
   `/api/cli-tools/runtime/*` strict-loopback જ રહે છે.

## OpenAPIમાં સુરક્ષા Tiersનું દસ્તાવેજીકરણ

`docs/openapi.yaml`માં નવો રૂટ ઉમેરતી વખતે, જો રૂટનું વર્ગીકરણ
`routeGuard.ts` દ્વારા કરાયું હોય તો તેને અનુરૂપ vendor extension લાગુ કરો:

| routeGuard.ts વર્ગીકરણ       | YAML annotation            | અમલીકરણ                                          |
| ---------------------------- | -------------------------- | ------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | non-loopbackમાંથી બિનશરતી રીતે અવરોધિત           |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | `requireLogin=false` હોય ત્યારે પણ auth આવશ્યક   |
| આંતરિક admin/debug રૂટ       | `x-internal: true`         | ડિફૉલ્ટ રીતે /dashboard/api-endpointsથી છુપાયેલો |
| કોઈ નહીં (જાહેર / માનક auth) | (કોઈ annotation જરૂરી નથી) | માનક `requireLogin` દ્વારા નિયંત્રિત ઍક્સેસ      |

### માન્યતા

બે scripts YAML annotations અને `routeGuard.ts` વચ્ચેની સુસંગતતા લાગુ કરે છે:

- `scripts/check/check-openapi-coverage.mjs` — coverage < 99% હોય તો નિષ્ફળ જાય છે
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` અથવા
  `x-always-protected` annotations compile-time constantsથી અલગ હોય તો નિષ્ફળ જાય છે

બંને scripts pre-commit hook અને CIમાં ચાલે છે.

### False Positive નિયમ

જો `routeGuard.ts` constantમાં ન હોય એવા રૂટ પર `x-always-protected` અથવા
`x-loopback-only` annotation કરેલું હોય, તો coverage script નિષ્ફળ જાય છે. તેનો ઉકેલ હંમેશાં
YAMLને `routeGuard.ts` ખરેખર જે અમલમાં મૂકે છે તેની સાથે સુસંગત કરવાનો છે — enforcement logic
પણ અમલમાં મૂક્યા વિના `routeGuard.ts`માં રૂટ ઉમેરવાનો નથી.
