> **TL;DR**: OmniRoute દરેક વિનંતીના ટોકન વપરાશને ટ્રૅક કરે છે, ખર્ચની ગણતરી કરે છે, દરેક API કી માટેનો ક્વોટા લાગુ કરે છે અને ડૅશબોર્ડમાં એનાલિટિક્સ દર્શાવે છે. આ માર્ગદર્શિકા સમજાવે છે કે આ બધું કેવી રીતે કાર્ય કરે છે.

**સ્રોતો:**

- `open-sse/services/usage.ts` (~70KB) — મુખ્ય વપરાશ ટ્રૅકિંગ
- `src/lib/usageAnalytics.ts` (~10KB) — ડૅશબોર્ડ માટે એકત્રીકરણ
- `src/lib/db/quotaSnapshots.ts` — ઐતિહાસિક ક્વોટા ડેટા
- `src/lib/db/usage*.ts` — વપરાશ-સંબંધિત અનેક DB મોડ્યુલો

## અવલોકન

OmniRouteમાંથી પસાર થતી દરેક વિનંતી એક **વપરાશ રેકોર્ડ** બનાવે છે, જેમાં નીચેની વિગતો સામેલ હોય છે:

- **ઓળખ**: કઈ API કી, પ્રદાતા, મોડેલ અને કોમ્બો
- **ટોકન્સ**: પ્રોમ્પ્ટ ટોકન્સ, કમ્પ્લીશન ટોકન્સ, કૅશ કરેલા ટોકન્સ અને કુલ
- **ખર્ચ**: USD રકમ (કિંમતના ડેટામાંથી ગણવામાં આવેલી)
- **સમય**: વિલંબ, શરૂઆત/સમાપ્તિના ટાઇમસ્ટૅમ્પ
- **સ્થિતિ**: સફળતા, ભૂલ, રેટ-લિમિટેડ વગેરે

આ રેકોર્ડ્સને એકત્રિત કરીને **એનાલિટિક્સ** બનાવવામાં આવે છે, **ક્વોટા સ્નૅપશૉટ્સ** તરીકે સંગ્રહિત કરવામાં આવે છે અને **દરેક કી માટેની બજેટ મર્યાદાઓ** લાગુ કરવા માટે ઉપયોગમાં લેવામાં આવે છે.

```
વિનંતી ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    એનાલિટિક્સ  ક્વોટા   બિલિંગ
                    (ડૅશબોર્ડ) (અમલ) (નિકાસ)
```

## શું રેકોર્ડ કરવામાં આવે છે

`usage.ts` સેવા દરેક વિનંતી માટે એક **વપરાશ ઇવેન્ટ** કૅપ્ચર કરે છે:

| ફીલ્ડ              | પ્રકાર  | સ્રોત                                                      |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | રેકોર્ડ કરતી વખતે જનરેટ થયેલ UUID                          |
| `apiKeyId`         | string  | વિનંતી શરૂ કરનાર API કી                                    |
| `provider`         | string  | પ્રદાતા ID (openai, anthropic વગેરે)                       |
| `model`            | string  | મોડેલ ID (gpt-5, claude-opus-4-6 વગેરે)                    |
| `comboId`          | string? | કોમ્બો મારફતે રૂટ કરવામાં આવી હોય તો કોમ્બો ID             |
| `promptTokens`     | number  | અપસ્ટ્રીમ પ્રતિસાદમાંથી                                    |
| `completionTokens` | number  | અપસ્ટ્રીમ પ્રતિસાદમાંથી                                    |
| `cachedTokens`     | number  | કૅશ હિટ ટોકન્સ (Anthropic પ્રોમ્પ્ટ કૅશિંગ વગેરે)          |
| `totalTokens`      | number  | પ્રોમ્પ્ટ + કમ્પ્લીશન                                      |
| `costUsd`          | number  | કિંમતના ડેટામાંથી ગણવામાં આવેલ                             |
| `latencyMs`        | number  | વિનંતીનો શરૂઆતથી અંત સુધીનો સમયગાળો                        |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | status != success હોય તો ભૂલનો વર્ગ                        |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | કસ્ટમ પ્લગઇન દ્વારા ઉમેરવામાં આવેલ ડેટા                    |

### ટોકન્સ ક્યાંથી આવે છે

અપસ્ટ્રીમ પ્રદાતાના પ્રતિસાદમાંથી **પ્રતિસાદ હૅન્ડલર**માં ટોકન્સ કાઢવામાં આવે છે:

```ts
// open-sse/handlers/chatCore.tsમાંથી
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

જે પ્રદાતાઓ વપરાશની માહિતી પરત કરતા નથી (કેટલાક વેબ-કૂકી પ્રદાતાઓ), તેમના માટે OmniRoute `~4 chars per token` હ્યુરિસ્ટિકનો ઉપયોગ કરીને ટોકન્સનો **અંદાજ** લગાવે છે (`open-sse/services/autoCombo/pipelineRouter.ts` જુઓ).

### કૅશ કરેલા ટોકન્સ

OmniRoute `cached_tokens`ને `prompt_tokens`થી અલગ ટ્રૅક કરે છે, કારણ કે:

- Anthropic પ્રોમ્પ્ટ કૅશિંગમાં કૅશ કરેલા ટોકન્સ માટે ઓછો દર વસૂલવામાં આવે છે (સામાન્ય દરના 10%)
- કેટલાક પ્રદાતાઓ `cache_read_input_tokens` પરત કરે છે, જેની કિંમત અલગ રીતે ગણવી જોઈએ
- એનાલિટિક્સ **કૅશ હિટ દર** = `cached_tokens / prompt_tokens` દર્શાવી શકે છે

## ખર્ચની ગણતરી

ખર્ચની ગણતરી LiteLLMમાંથી સિંક કરાયેલા **કિંમત-નિર્ધારણ ડેટા** (`src/lib/pricingSync.ts`) પરથી કરવામાં આવે છે:

| મોડેલ             | ઇનપુટ $/1M | આઉટપુટ $/1M | કૅશ કરેલ $/1M |
| ----------------- | ---------- | ----------- | ------------- |
| gpt-5             | $2.50      | $10.00      | —             |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50         |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30         |
| gemini-2.5-pro    | $1.25      | $10.00      | —             |

ખર્ચનું સૂત્ર (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **પ્રોમ્પ્ટમાંથી કૅશ કરેલ ટોકન્સ શા માટે બાદ કરવામાં આવે છે?** કૅશ કરેલા ભાગની કિંમત અલગથી ગણવામાં આવે છે; સમગ્ર પ્રોમ્પ્ટ પર ઇનપુટ કિંમત વસૂલવાથી ખર્ચ વધારે ગણાઈ જશે.

### કિંમત-નિર્ધારણ સિંક

કિંમત-નિર્ધારણ ડેટા `/api/pricing/sync` એન્ડપોઇન્ટ દ્વારા LiteLLMમાંથી આપમેળે સિંક થાય છે (તે બિલ્ટ-ઇન cron કાર્ય દ્વારા ટ્રિગર થાય છે, વપરાશકર્તા માટે ઉપલબ્ધ env var દ્વારા નહીં):

```bash
# મેન્યુઅલ ટ્રિગર
curl -X POST http://localhost:20128/api/pricing/sync
```

જે મોડેલો માટે કિંમત-નિર્ધારણ ડેટા ઉપલબ્ધ નથી, તેમના માટે OmniRoute આંતરિક સરેરાશ દરો (LiteLLMના કિંમત-નિર્ધારણ ડેટામાંથી મેળવેલા) વડે **ખર્ચનો અંદાજ** લગાવે છે.

## તારીખ-શ્રેણીનું એકત્રીકરણ

`usageAnalytics.ts` મોડ્યુલ કાચા વપરાશ ડેટામાંથી ડૅશબોર્ડ વિજેટ્સની ગણતરી કરે છે. તે 7 સમય-શ્રેણીઓને સપોર્ટ કરે છે:

| શ્રેણી   | સમયગાળો                        | ઉપયોગનો કેસ                 |
| -------- | ------------------------------ | --------------------------- |
| `1d`     | છેલ્લા 24 કલાક                 | કલાકવાર ખર્ચમાં ઉછાળાની શોધ |
| `7d`     | છેલ્લા 7 દિવસ                  | સાપ્તાહિક સમીક્ષા           |
| `30d`    | છેલ્લા 30 દિવસ                 | માસિક બિલિંગ                |
| `90d`    | છેલ્લા 90 દિવસ                 | ત્રિમાસિક વિશ્લેષણ          |
| `ytd`    | વર્તમાન વર્ષના 1 જાન્યુઆરીથી   | વાર્ષિક બજેટ ટ્રૅકિંગ       |
| `all`    | સંપૂર્ણ સમય                    | સમગ્ર સમયગાળાના આંકડા       |
| `custom` | વપરાશકર્તા-નિર્ધારિત શરૂઆત/અંત | ઑડિટ, તાત્કાલિક ક્વેરીઓ     |

### ગણતરી કરાયેલા ડૅશબોર્ડ વિજેટ્સ

કોઈપણ તારીખ-શ્રેણી માટે, ઍનલિટિક્સ સ્તર નીચેની ગણતરી કરે છે:

| વિજેટ                | વર્ણન                                                       |
| -------------------- | ----------------------------------------------------------- |
| **સારાંશ કાર્ડ્સ**   | કુલ વિનંતીઓ, કુલ ખર્ચ, કુલ ટોકન્સ, સફળતાનો દર               |
| **દૈનિક વલણ ચાર્ટ**  | દરરોજનો ખર્ચ + ટોકન્સ, મોડેલ મુજબ સ્ટૅક કરેલા               |
| **પ્રવૃત્તિ હીટમૅપ** | દિવસનો કલાક × અઠવાડિયાનો દિવસ ગ્રિડ, રંગ = વિનંતીઓની સંખ્યા |
| **મોડેલ વિભાજન**     | મોડેલ મુજબ ખર્ચનો પાઇ ચાર્ટ                                 |
| **પ્રદાતા વિભાજન**   | પ્રદાતા મુજબ વિનંતીઓનો બાર ચાર્ટ                            |
| **ટોચની API કીઝ**    | ખર્ચ મુજબ ટોચની 10 કીઝનું કોષ્ટક                            |
| **ભૂલ વિશ્લેષણ**     | સમય સાથે ભૂલનો દર, ટોચના ભૂલ વર્ગો                          |

### પ્રોગ્રામેટિક ઍક્સેસ

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // વપરાશ ઇતિહાસના રેકોર્ડ્સ
  "7d",                 // સમય-શ્રેણી: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // પ્રદાતા કનેક્શન મૅપ (connectionId → ખાતાનું નામ)
  {
    startDate: "2025-01-01",  // વૈકલ્પિક: "custom" શ્રેણી માટે
    endDate: "2025-06-01",   // વૈકલ્પિક: "custom" શ્રેણી માટે
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (સેન્ટ)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## ક્વોટાનું અમલીકરણ

પ્રતિ-API-કી ક્વોટા બે સ્થળે લાગુ કરવામાં આવે છે:

1. **સોફ્ટ મર્યાદા** (`quotaWarnAt`): વપરાશ થ્રેશોલ્ડને વટાવે ત્યારે ડેશબોર્ડ ચેતવણી
2. **હાર્ડ મર્યાદા** (`quotaLimit`): મર્યાદા વટાવાય ત્યારે વિનંતી HTTP 429 સાથે નકારવામાં આવે છે

### રૂપરેખાંકન

```ts
// પ્રતિ API કી
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — ચેતવણી બતાવો
  quotaLimit: 10_00,    // $10.00 — સંપૂર્ણપણે રોકો
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### અમલીકરણ પ્રવાહ

```
વિનંતી ──▶ quotaCheck()
              │
              ├── મર્યાદાની અંદર?  ──▶ મંજૂરી આપો
              │
              └── મર્યાદાથી વધુ?  ──▶ 429 ઘણી બધી વિનંતીઓ
                                   Retry-After હેડર સાથે
```

### ક્વોટા સ્નેપશોટ્સ

`quotaSnapshots` ટેબલ વલણ વિશ્લેષણ માટે **ઐતિહાસિક ક્વોટા સ્થિતિ** સંગ્રહિત કરે છે:

| ફીલ્ડ | વર્ણન |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | ટ્રૅક કરવામાં આવી રહેલી કી |
| `window` | "day" | "week" | "month" |
| `used` | આ વિન્ડોમાં વપરાયેલ ખર્ચ (સેન્ટમાં) |
| `limit` | મર્યાદા (સેન્ટમાં) |
| `resetAt` | વિન્ડો ક્યારે રીસેટ થાય છે |
| `createdAt` | સ્નેપશોટ ક્યારે લેવામાં આવ્યો હતો |

> 0 ખર્ચનો ઉપયોગ કરતી **દરેક વિનંતી વખતે** સ્નેપશોટ લેવામાં આવે છે અને તેનો ઉપયોગ આ માટે થાય છે:

- ડેશબોર્ડમાં ક્વોટા પ્રગતિ બાર રેન્ડર કરવા
- 30-દિવસના ક્વોટા વલણ ચાર્ટ બતાવવા
- વપરાશ મર્યાદાની નજીક પહોંચે ત્યારે ચેતવણીઓ ટ્રિગર કરવા

## જાળવણી અને સફાઈ

ઉપયોગ ડેટા પ્રતિ વિનંતી આશરે ~1-10KB જેટલો વધે છે. મોટા પાયે, આ નોંધપાત્ર હોઈ શકે છે.

### જાળવણી સેટિંગ્સ

ઉપયોગ ઇતિહાસની જાળવણી UIમાં Database Settings દ્વારા અથવા `/api/settings/database` દ્વારા ગોઠવવામાં આવે છે.

મૂળભૂત રીતે, ઉપયોગ ઇતિહાસ **90 દિવસ** સુધી જાળવવામાં આવે છે.

### સફાઈ

જૂના રેકોર્ડ્સને `src/lib/db/cleanup.ts` દ્વારા સાફ કરવામાં આવે છે:

- બેકગ્રાઉન્ડ cron પ્રક્રિયા દ્વારા ટ્રિગર થાય છે
- ગોઠવેલ `usageHistory` જાળવણી સેટિંગ કરતાં જૂના રેકોર્ડ્સને `usage_history`માંથી કાઢી નાખે છે

### સ્ટોરેજ અંદાજ

| વિનંતી દર           | 30-દિવસનું સ્ટોરેજ | 90-દિવસનું સ્ટોરેજ |
| ------------------- | ------------------ | ------------------ |
| 100 વિનંતી/દિવસ     | ~3MB               | ~9MB               |
| 1,000 વિનંતી/દિવસ   | ~30MB              | ~90MB              |
| 10,000 વિનંતી/દિવસ  | ~300MB             | ~900MB             |
| 100,000 વિનંતી/દિવસ | ~3GB               | ~9GB               |

ખૂબ વધારે ટ્રાફિક માટે, આ બાબતો ધ્યાનમાં લો:

- Database Settings દ્વારા જાળવણી અવધિ ઘટાડવી
- કાચા રેકોર્ડ્સને બદલે `aggregated_metrics`નો ઉપયોગ કરવો (ફક્ત એનાલિટિક્સ માટે)

## ખર્ચ ઑપ્ટિમાઇઝેશન ટિપ્સ

### 1. યોગ્ય મોડેલનો ઉપયોગ કરો

```bash
# ઝડપી જવાબ — સસ્તું + ઝડપી વાપરો
curl -d '{"model":"auto/fast","messages":[...]}'

# જટિલ કાર્ય — ગુણવત્તાનો ઉપયોગ કરો
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. કૅશિંગ સક્ષમ કરો

Anthropic prompt caching પુનરાવર્તિત સંદર્ભ પર **90% બચત કરે છે**:

```ts
// કૅશિંગ આપમેળે થાય છે — ફક્ત એ જ મોટો system prompt સામેલ કરો
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // આપમેળે કૅશ કરવામાં આવશે
  messages: [{ role: "user", content: "..." }],
});
```

### 3. કમ્પ્રેશનનો ઉપયોગ કરો

RTK + Caveman compression ટૂલ-આધારિત સત્રોમાં **15-95% બચત કરે છે**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. દરેક કી માટે ક્વોટા સેટ કરો

અનિયંત્રિત ખર્ચ અટકાવવા માટે હંમેશાં `quotaLimit` સેટ કરો:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // $10/મહિનાની મર્યાદા
```

### 5. સૌથી વધુ વપરાશકર્તાઓનું ઑડિટ કરો

API કી મુજબ જૂથબદ્ધ કરવા અને ખર્ચ મુજબ સૉર્ટ કરવા માટે ડૅશબોર્ડ અથવા **`/api/usage/analytics`**નો ઉપયોગ કરો:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## સમસ્યાનિવારણ

### "ખર્ચ અપેક્ષા કરતાં વધારે છે"

1. **`/api/usage/analytics?groupBy=model`** તપાસો — મોંઘું મોડેલ શોધો
2. **`/api/usage/analytics?groupBy=apiKey`** તપાસો — વધારે વપરાશ કરનારને શોધો
3. કિંમતનો ડેટા અદ્યતન છે તેની ખાતરી કરો: `POST /api/pricing/sync`

### "રેકોર્ડ્સ ખૂટે છે"

- Dashboard → Database → Cleanup હેઠળ DB જાળવણી સેટિંગ્સ તપાસો — જૂના રેકોર્ડ્સને સામયિક સફાઈ કાર્ય (`src/lib/db/cleanup.ts`) દ્વારા કાઢી નાખવામાં આવે છે
- `src/lib/db/usage*.ts`માં ભૂલો તપાસો — DB લેખન નિષ્ફળતાઓ લૉગ થાય છે, પરંતુ દર્શાવવામાં આવતી નથી
- ખાતરી કરો કે વિનંતી ખરેખર `chatCore` સુધી પહોંચી હતી — combo routing તપાસો

### "ક્વોટા લાગુ પડતો નથી"

- કીનું `quotaLimit` સેટિંગ તપાસો
- ખાતરી કરો કે `quotaWindow` યોગ્ય રીતે સેટ થયેલું છે
- `quotaSnapshots` રેકોર્ડ્સ શોધો — તે દરેક વિનંતી પર બનાવવામાં આવવા જોઈએ
