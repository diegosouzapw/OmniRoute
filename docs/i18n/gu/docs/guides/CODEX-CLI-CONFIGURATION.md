OmniRoute ને OpenAI-સુસંગત બૅકએન્ડ તરીકે નિર્દેશિત કરીને Codex CLI નો ઉપયોગ કરવા માટેની સંપૂર્ણ માર્ગદર્શિકા.

---

> **TOML એકમાત્ર અસરકારક ફોર્મેટ છે.** આધુનિક Codex ફક્ત `~/.codex/config.toml`
> વાંચે છે (codex-cli 0.147.0 સાથે ચકાસાયેલ: `codex --help` મુજબ
> `-c/--config` ઓવરરાઇડ્સ "`~/.codex/config.toml` માંથી લોડ થાય છે"). જૂની
> `~/.codex/config.yaml` લેગસી npm CLI ની હતી અને તેને કોઈ સૂચના વિના અવગણવામાં આવે છે.
> ડૅશબોર્ડ જનરેટર (`/api/cli-tools/apply`, ટૂલ `codex`) સંયમિત મર્જ સાથે TOML લખે છે —
> હાલની કીઓ અને અન્ય પ્રોવાઇડર બ્લૉક્સ જાળવી રાખવામાં આવે છે,
> API કી `OMNIROUTE_API_KEY` માં રહે છે (ફાઇલમાં ક્યારેય નહીં), અને બચી ગયેલી લેગસી
> `config.yaml` ને સ્પર્શ કર્યા વિના માઇગ્રેશન નોંધ તરીકે દર્શાવવામાં આવે છે.

## સીધું પેસ્ટ કરવા માટે તૈયાર config.toml

`<YOUR_HOST>` અને `<YOUR_KEY>` ને તમારા મૂલ્યોથી બદલો:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # દરેક ટૂલ કૉલ દીઠ હિસ્ટ્રી સ્ટોરેજ મર્યાદા

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc અથવા ~/.zshrc — વાસ્તવિક કી મૂલ્ય, config.toml માં ક્યારેય નહીં
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT ઍપની અંદર બંડલ કરાયેલ Codex

જો તમે ChatGPT ડેસ્કટૉપ ઍપ મારફતે Codex ઇન્સ્ટૉલ કર્યું હોય, તો `codex` બાઇનરી
ફક્ત ઍપ બંડલની અંદર હોઈ શકે છે અને હજી તમારા શેલ `PATH` પર ન હોઈ શકે. તમારી
શેલ સ્ટાર્ટઅપ ફાઇલમાં રિસોર્સિસ ડિરેક્ટરી ઉમેરો:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

નવું શેલ ખોલો, પછી ચકાસો:

```bash
command -v codex
codex --version
```

### સ્થાનિક બિન-પ્રમાણિત OmniRoute: પ્લેસહોલ્ડર કી પૂરતી છે

પ્રથમ રિક્વેસ્ટ CLI માંથી બહાર જાય તે **પહેલાં** Codex ચકાસે છે કે `env_key` દ્વારા
નામિત એન્વાયર્નમેન્ટ વેરિએબલ અસ્તિત્વમાં છે કે નહીં. જો તમારા **સ્થાનિક** OmniRoute
ઇન્સ્ટન્સને ઑથેન્ટિકેશનની જરૂર ન હોય, તો કોઈપણ ખાલી ન હોય એવો પ્લેસહોલ્ડર કામ કરશે:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

જો તમારું OmniRoute સર્વર સુરક્ષિત અથવા રિમોટ હોય, તો તેના બદલે વાસ્તવિક કીનો ઉપયોગ કરો.

> **સામાન્ય હોસ્ટ વિકલ્પો**
>
> | ઍક્સેસ          | URL                           |
> | --------------- | ----------------------------- |
> | સ્થાનિક નેટવર્ક | `http://192.168.0.1:20128/v1` |
> | Tailscale       | `http://100.x.x.x:20128/v1`   |
> | લૂપબૅક          | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — તે બધા મૉડલ્સ માટે શા માટે કાર્ય કરે છે

Codex CLI એ ફેબ્રુઆરી 2026 માં `wire_api = "chat"` (Chat Completions) ને ડિપ્રિકેટ કર્યું અને હવે `wire_api = "responses"` (OpenAI Responses API) **આવશ્યક** છે. v0.138 થી `wire_api = "chat"` સેટ કરવાથી સ્ટાર્ટઅપ વખતે તરત જ ક્રૅશ થાય છે.

GLM અને Kimi સહિતના ઘણા પ્રોવાઇડર્સ હજી પણ ફક્ત Chat Completions એન્ડપૉઇન્ટ ઉપલબ્ધ કરાવે છે. DeepSeek V4 હવે મૂળ Responses API તેમજ Anthropic-સુસંગત એન્ડપૉઇન્ટ ઉપલબ્ધ કરાવે છે; OmniRoute ડિફૉલ્ટ રૂપે Responses નો ઉપયોગ કરે છે અને દરેક DeepSeek કનેક્શનને Anthropic સુસંગતતા પસંદ કરવાની મંજૂરી આપે છે.

**OmniRoute આને પારદર્શક રીતે ઉકેલે છે:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute પ્રોવાઇડરનો મૂળ પ્રોટોકૉલ પસંદ કરે છે અને જરૂર પડે ત્યારે રૂપાંતર કરે છે
    → POST /responses (DeepSeek V4) અથવા /chat/completions (Mistral / GLM / Kimi / અન્ય)
```

OmniRoute નો ઉપયોગ કરતી વખતે તમને ક્યારેય અલગ ટ્રાન્સલેશન પ્રૉક્સીની જરૂર પડતી નથી. **બધા મૉડલ્સ `wire_api = "responses"` નો ઉપયોગ કરે છે** — બાકીનું OmniRoute સંભાળે છે.

> **`wire_api` ડિફૉલ્ટ છે** — આ ફીલ્ડનું ડિફૉલ્ટ મૂલ્ય `"responses"` છે અને તેને `config.toml` માંથી સંપૂર્ણપણે છોડી શકાય છે. માત્ર ઇરાદાનું દસ્તાવેજીકરણ કરતા હો ત્યારે જ તેને સ્પષ્ટ રીતે સેટ કરો.

## સંદર્ભ વિન્ડો અને સંક્ષિપ્તીકરણ

### ટોકન રૂપરેખાંકન ફીલ્ડ્સ

| ફીલ્ડ                            | વર્ણન                                                                                                                                                                               |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | સક્રિય મોડેલ માટેનું કુલ ટોકન બજેટ. તેને મોડેલની જાહેર કરેલી મર્યાદા પર સેટ કરો.                                                                                                    |
| `model_auto_compact_token_limit` | સ્વચાલિત ઇતિહાસ સંક્ષિપ્તીકરણ શરૂ કરતી થ્રેશોલ્ડ. **મહત્તમ: `model_context_window`ના 90%** — 90%થી વધુ મૂલ્યોને કોઈ સૂચના વિના અવગણવામાં આવે છે.                                    |
| `tool_output_token_limit`        | ઇતિહાસમાં દરેક ટૂલ કૉલના આઉટપુટ માટે સંગ્રહિત ટોકનની મર્યાદા. એક મોટો ટૂલ પ્રતિસાદ આખી વિન્ડો ભરી ન દે તે સુનિશ્ચિત કરે છે. **આ મહત્તમ આઉટપુટ નથી** — આ ઇતિહાસની સંગ્રહ મર્યાદા છે. |
| `compact_prompt`                 | સંક્ષિપ્તીકરણ દરમિયાન વપરાતા સિસ્ટમ પ્રોમ્પ્ટ માટે ઇનલાઇન ઓવરરાઇડ (v0.138+).                                                                                                        |

> **`model_max_output_tokens` અંગે નોંધ**: આ ફીલ્ડ **Codex CLI રૂપરેખાંકન સ્કીમાનો ભાગ નથી** (Codex Rust કોડબેઝમાં ગેરહાજર છે). તેને સેટ કરવામાં આવે તો કોઈ સૂચના વિના અવગણવામાં આવે છે. તેના પર આધાર રાખશો નહીં — ઇતિહાસમાં કેટલું ટૂલ આઉટપુટ સંગ્રહિત થાય છે તે નિયંત્રિત કરવા માટે `tool_output_token_limit`નો ઉપયોગ કરો.

> **સંક્ષિપ્તીકરણ સૂત્ર:** `effective_window = model_context_window - min(tool_output_token_limit, 20000)`. 20kથી વધુ મૂલ્યો સંક્ષિપ્તીકરણ શરૂ થવાના બિંદુને બદલતા નથી.

> **સામાન્ય માર્ગદર્શિકા:** `model_auto_compact_token_limit`ને `model_context_window`ના 85–88% પર સેટ કરો. ક્યારેય 90%થી વધુ ન રાખો — તેને કોઈ સૂચના વિના અવગણવામાં આવે છે.

## રીઝનિંગ એફર્ટ

પ્રતિસાદ આપતા પહેલાં મોડેલ કેટલું "વિચારે" છે તે નિયંત્રિત કરે છે.

| મૂલ્ય    | આ માટે ઉપયોગ કરો                          |
| -------- | ----------------------------------------- |
| `none`   | કોઈ તર્ક નહીં — સીધો પ્રતિસાદ             |
| `low`    | સરળ કાર્યો (નામ બદલવું, ફોર્મેટ કરવું)    |
| `medium` | ઉલ્લેખિત ન હોય ત્યારે **સર્વર ડિફૉલ્ટ**   |
| `high`   | મધ્યમ સ્તરના કાર્યો (રિફેક્ટરિંગ, ડિબગ)   |
| `xhigh`  | આર્કિટેક્ચર, ઊંડું વિશ્લેષણ, જટિલ સમસ્યાઓ |

```bash
# દરેક આમંત્રણ માટે ઓવરરાઇડ
codex -c model_reasoning_effort=low "ચલ xનું નામ બદલીને count કરો"
codex -c model_reasoning_effort=xhigh "auth મોડ્યુલની રચના કરો"
```

રીઝનિંગનો **સારાંશ** પણ સેટ કરો જેથી Desktop વિચારનું લખાણ રેન્ડર કરી શકે (માત્ર એન્ક્રિપ્ટ કરેલા બ્લૉબ્સ નહીં):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # અથવા જ્યારે સપોર્ટેડ હોય ત્યારે ultra
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute થિંકિંગ બજેટ (સર્વર સેટિંગ)

OmniRoute હોસ્ટ પર, Codex એફર્ટ/સારાંશ અપસ્ટ્રીમ સુધી પહોંચે તે માટે **Settings → AI → Thinking Budget**નું મૂલ્ય **`passthrough`** હોવું આવશ્યક છે. **`auto` મોડ** ક્લાયન્ટના બધા `reasoning` / `reasoning_effort` ફીલ્ડ દૂર કરે છે અને Codex યોગ્ય રીતે કૉન્ફિગર કરેલું હોય ત્યારે પણ થિંકિંગ પેનલ ખાલી રાખશે.

સંપૂર્ણ માર્ગદર્શિકા: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

કમ્પ્રેશન અને પ્રોમ્પ્ટ કૅશ સ્વતંત્ર છે અને `passthrough` હેઠળ કાર્ય કરવાનું ચાલુ રાખે છે.

`~/.codex/<name>.config.toml` છે, જે મૂળ `config.toml`ની ઉપર ઓવરલે થાય છે.

## `omniroute setup-codex` વડે આપમેળે પ્રોફાઇલ્સ બનાવવી

જો તમે VPS પર OmniRoute ચલાવતા હો, તો તમે લાઇવ મોડેલ કેટલોગમાંથી પ્રોફાઇલ ફાઇલો આપમેળે બનાવી શકો છો:

```bash
# VPS પરથી (પોર્ટ 20128 પર સ્થાનિક OmniRouteનો ઉપયોગ કરે છે)
omniroute setup-codex

# કોઈપણ મશીન પરથી — તમારા VPS તરફ નિર્દેશ કરો
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# ફાઇલો લખ્યા વિના પૂર્વાવલોકન કરો
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# ફક્ત GLM અને Kimi પ્રોફાઇલ્સ બનાવો
omniroute setup-codex --only glm,kimi

# કસ્ટમ ડિરેક્ટરીમાં લખો
omniroute setup-codex --codex-home /path/to/.codex
```

આ કમાન્ડ `/v1/models` મેળવે છે, જાણીતા મોડેલ્સ માટે સુસંગત બનાવેલી પ્રોફાઇલ્સનો ઉપયોગ કરે છે, અન્ય સુસંગત ટેક્સ્ટ મોડેલ્સ માટે કેટલોગ મેટાડેટાનો વૈકલ્પિક રીતે ઉપયોગ કરે છે અને દરેક માટે `~/.codex/<name>.config.toml` લખે છે. આ ઇડેમ્પોટન્ટ છે — તેને ફરી ચલાવવું સુરક્ષિત છે.

પ્રોવાઇડરના સફળ મોડેલ ડિસ્કવરી/ઇમ્પોર્ટથી લાઇવ કેટલોગ બદલાયા પછી OmniRoute આ જ પ્રોફાઇલ ફાઇલોને **આપમેળે સિંક** પણ કરી શકે છે. આ **વૈકલ્પિક છે અને ડિફૉલ્ટ રૂપે બંધ હોય છે**: તેને **CLI Code dashboard** પરથી ("CLI profile auto-sync" → Codex) ટૉગલ કરો અથવા `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` સેટ કરો (તે `CLI_ALLOW_CONFIG_WRITES`નું પણ પાલન કરે છે, જે ડિફૉલ્ટ રૂપે ચાલુ હોય છે). સક્ષમ હોય ત્યારે તે ફક્ત અલગ `~/.codex/*.config.toml` પ્રોફાઇલ ફાઇલો લખે છે; તે સક્રિય/ડિફૉલ્ટ `~/.codex/config.toml`, Codex-lb સેટિંગ્સ, ઑથ અથવા પ્રોવાઇડરની પસંદગીમાં ક્યારેય ફેરફાર કરતું નથી.

## `omniroute launch-codex` વડે Codex લૉન્ચ કરવું

Codex લૉન્ચ કરતાં પહેલાં તમારા OmniRoute ઇન્સ્ટન્સનું હેલ્થ-ચેક કરે છે:

```bash
# સ્થાનિક OmniRoute સામે લૉન્ચ કરો (ડિફૉલ્ટ પોર્ટ 20128)
omniroute launch-codex

# ચોક્કસ પ્રોફાઇલ સાથે લૉન્ચ કરો
omniroute launch-codex --profile kimi-k27

# રિમોટ VPS સામે લૉન્ચ કરો
omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# codexને વધારાની આર્ગ્યુમેન્ટ્સ આપો
omniroute launch-codex --profile glm52 -- --yolo "fix this bug"
```

Codex એ બે સામાન્ય મેનિફેસ્ટ-આધારિત એન્ટ્રી પોઇન્ટ્સનું પણ લક્ષ્ય છે
(`bin/cli/cli-manifest.mjs`):

```bash
# ઇન્ટરેક્ટિવ મોડેલ પિકર → ~/.codex/<name>.config.toml લખે છે (TOML, env_key)
omniroute configure codex

# -c ફ્લૅગ્સ દ્વારા omniroute પ્રોવાઇડર દાખલ કરીને codex લૉન્ચ કરો (કોઈ કૉન્ફિગ લખાતું નથી)
omniroute run codex
```

## લાંબા સમય સુધી ચાલતાં કાર્યો

OmniRoute ના બે ડિફૉલ્ટ બહુ-કલાકીય Codex CLI સત્રોને ચૂપચાપ નિષ્ફળ બનાવી શકે છે. બંનેમાંથી કોઈ પણ Codex CLI સેટિંગ નથી — બંને OmniRoute તરફ રહે છે. એકાઉન્ટને પિન કરતા અને નિષ્ક્રિયતા કટઑફને અક્ષમ કરતા અપસ્ટ્રીમ પ્રૉક્સીઓમાંથી રૂપરેખાંકન સ્થળાંતરિત કરતા વપરાશકર્તાઓ ઘણીવાર બંને સમસ્યાનો સામનો કરે છે અને એવું તારણ કાઢે છે કે OmniRoute “લાંબું સત્ર જાળવી શકતું નથી.”

| લક્ષણ                                                                      | સંભવિત કારણ                                                                | નિયંત્રણ                 |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------ |
| સત્ર સતત એકાઉન્ટ બદલે છે / ટર્ન્સ વચ્ચે પ્રૉમ્પ્ટ-કૅશ સાતત્ય ખોવાઈ જાય છે  | સત્ર અફિનિટી TTL `0` છે (અક્ષમ)                                            | `sessionAffinityTtlMs`   |
| ક્લાયન્ટને કોઈ પ્રૉમ્પ્ટ દેખાયા વિના રિઝનિંગની વચ્ચે કનેક્શન બંધ થઈ જાય છે | કોઈ અપસ્ટ્રીમ ચંક વિના 10 મિનિટ પછી સ્ટ્રીમ નિષ્ક્રિયતા વૉચડૉગ સક્રિય થયું | `STREAM_IDLE_TIMEOUT_MS` |

સંબંધિત ચર્ચાઓ: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (લાંબા કાર્યો અટકી જાય છે), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (અફિનિટી ડિફૉલ્ટ રૂપે શા માટે બંધ છે). ટ્રૅકિંગ: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. સત્ર અફિનિટી — એક વાતચીતને એક એકાઉન્ટ સાથે પિન કરો

**ડિફૉલ્ટ:** `sessionAffinityTtlMs = 0` (અક્ષમ).

**તે ક્યાં સેટ કરવું**

- ડૅશબોર્ડ → **સેટિંગ્સ → રાઉટિંગ** → **સત્ર અફિનિટી** → **અફિનિટી TTL (સેકન્ડ)** (`ComboDefaultsTab`)
- અથવા **મિલિસેકન્ડ**માં `sessionAffinityTtlMs` વડે PATCH સેટિંગ્સ (Zod શ્રેણી `0`–`86_400_000`, એટલે કે મહત્તમ 24 કલાક)

> #7274 માં ફક્ત Codex માટેના `codexSessionAffinityTtlMs` માંથી નામ બદલવામાં આવ્યું. જૂની કી હજુ પણ ફક્ત વાંચવા માટેના ઉપનામ તરીકે સ્વીકારવામાં આવે છે; નવા રૂપરેખાંકનોએ `sessionAffinityTtlMs` નો ઉપયોગ કરવો જોઈએ. હવે TTL `0` કરતાં વધુ હોય ત્યારે અફિનિટી ફક્ત Codex જ નહીં, પરંતુ **કોઈપણ** પ્રદાતા પર લાગુ પડે છે — [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → સત્ર અફિનિટી જુઓ.

**તે 0 પર રહે ત્યારે શું બગડે છે**

બહુવિધ ટર્નવાળી Codex વાતચીતના દરેક ટર્નને સક્રિય કૉમ્બો વ્યૂહરચના દ્વારા સ્વતંત્ર રીતે રાઉટ કરવામાં આવે છે અને દરેક ટર્ન **અલગ એકાઉન્ટ** પર જઈ શકે છે. તે અપસ્ટ્રીમ સત્ર / પ્રૉમ્પ્ટ-કૅશ સાતત્યને તોડે છે. TTL `0` કરતાં વધુ હોય ત્યારે જ OmniRoute Codex સત્ર હેડર્સ (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) અને `prompt_cache_key` / `session_id` જેવા બૉડી ફીલ્ડ્સનો ઉપયોગ કરે છે (`src/sse/services/auth.ts` માં `extractSessionAffinityKey`).

**બહુ-કલાકીય એકલ કાર્ય માટે ભલામણ**

TTL ને **કાર્યની અપેક્ષિત વાસ્તવિક સમયગાળા કરતાં વધુ** સેટ કરો (UI મહત્તમ **86400 સેકન્ડ** = 24 કલાક છે):

| અપેક્ષિત કાર્ય અવધિ | અફિનિટી TTL (UI, સેકન્ડ) | `sessionAffinityTtlMs` |
| ------------------- | ------------------------ | ---------------------- |
| થોડા કલાકો          | `14400` (4h)             | `14400000`             |
| રાતોરાત / ~12h      | `43200` (12h)            | `43200000`             |
| આખો દિવસ            | `86400` (24h, મહત્તમ)    | `86400000`             |

ઑપ્ટ-ઇન ઇરાદાપૂર્વક છે: અફિનિટી અક્ષમ કરવાથી એકાઉન્ટ્સ વચ્ચે લોડ-બૅલેન્સિંગને પ્રાથમિકતા મળે છે; તેને સક્ષમ કરવાથી એક લાંબા એજન્ટ સત્ર માટે સાતત્યને પ્રાથમિકતા મળે છે. આ માર્ગદર્શિકા ડિફૉલ્ટને બદલતી **નથી** — લાંબા Codex કાર્યો ચલાવતા ઑપરેટર્સે ઑપ્ટ-ઇન કરવું આવશ્યક છે.

### 2. સ્ટ્રીમ નિષ્ક્રિયતા સમયસમાપ્તિ — શાંત રિઝનિંગ ટર્ન્સને બંધ ન કરો

**ડિફૉલ્ટ:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 મિનિટ). સેટ ન કરેલું હોય ત્યારે તે `REQUEST_TIMEOUT_MS` માંથી વારસામાં મળે છે; સહિયારો આધાર પણ 600000 છે. [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → સમયસમાપ્તિઓ જુઓ.

**ડિફૉલ્ટ પર શું બગડે છે**

કોઈ Codex રીઝનિંગ / ટૂલ ટર્ન જો **કોઈ વાસ્તવિક અપસ્ટ્રીમ ચંક વિના** 10 મિનિટથી વધુ સમય સુધી મૌન રહે, તો SSE આઇડલ વૉચડૉગ (`open-sse/utils/stream.ts`) તેને બળજબરીથી બંધ કરી દે છે. ક્લાયન્ટને ઘણી વાર માત્ર કનેક્શન તૂટી ગયેલું દેખાય છે — જે “કોઈ સૂચના વિના આપમેળે બંધ થઈ ગયું” સાથે મેળ ખાય છે.

મહત્ત્વપૂર્ણ વિગત: OmniRouteનું સિન્થેટિક SSE **હાર્ટબીટ આઇડલ ઘડિયાળને રીસેટ કરતું નથી**. ફક્ત વાસ્તવિક અપસ્ટ્રીમ બૉડી ચંક જ `lastChunkTime`ને અપડેટ કરે છે. હજી પણ “વિચારી” રહેલું શાંત મોડલ વૉચડૉગના દૃષ્ટિકોણથી અટકી ગયેલા અપસ્ટ્રીમ જેવું જ દેખાય છે.

સંબંધિત Undici બૉડી નિષ્ક્રિયતા: `FETCH_BODY_TIMEOUT_MS` (ડિફૉલ્ટ પણ એ જ 10-મિનિટની બેઝલાઇન છે; `0` તેને અક્ષમ કરે છે). સ્ટ્રીમિંગ માટે, `FETCH_TIMEOUT_MS` ફક્ત કનેક્શન સેટઅપ / પ્રથમ હેડર્સ સુધી લાગુ પડે છે — સ્ટ્રીમ સક્રિય થયા પછી, સ્ટૉલ્સ `STREAM_IDLE_TIMEOUT_MS` અને `FETCH_BODY_TIMEOUT_MS` દ્વારા નિયંત્રિત થાય છે.

**કેટલાક કલાકો ચાલતા એકમાત્ર ટાસ્ક માટે ભલામણ**

OmniRoute પ્રોસેસ એન્વાયરમેન્ટમાં (`.env` / compose / systemd):

```bash
# લાંબા રીઝનિંગ ટર્ન માટે સ્ટ્રીમ આઇડલ + બૉડી નિષ્ક્રિયતા કટઑફ્સ અક્ષમ કરો
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

અથવા તમે અપેક્ષા રાખતા સૌથી લાંબા શાંત અંતરાલ કરતાં તેમને વધારે સેટ કરો (મૂલ્યો મિલિસેકન્ડમાં છે):

```bash
# ઉદાહરણ: અપસ્ટ્રીમ ચંક્સ વચ્ચે 2 કલાક સુધીના મૌનને મંજૂરી આપો
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

આ env vars બદલ્યા પછી OmniRouteને રીસ્ટાર્ટ કરો.

### ચોક્કસ રીત — કેટલાક કલાકો ચાલતો Codex ટાસ્ક

1. **એકાઉન્ટ પિન કરો:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12h) અથવા `86400` (મહત્તમ 24h).
2. OmniRouteના એન્વાયરમેન્ટમાં **આઇડલ કટઑફ્સ વધારો / અક્ષમ કરો**:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. સામાન્ય Codex `config.toml` (`wire_api = "responses"`, યોગ્ય `base_url`, `OMNIROUTE_API_KEY`) જ રાખો — આ બે વર્તનો માટે Codex તરફના કોઈ affinity/idle નૉબ્સ ઉપલબ્ધ નથી.
4. OmniRouteને રીસ્ટાર્ટ કરો, પછી લાંબો Codex ટાસ્ક શરૂ કરો.

### ડિફૉલ્ટ્સ અંગેનો નિર્ણય (#7287)

| નૉબ                      | શિપ કરેલો ડિફૉલ્ટ   | આ માર્ગદર્શિકામાં ફેરફાર?                                                                              |
| ------------------------ | ------------------- | ------------------------------------------------------------------------------------------------------ |
| `sessionAffinityTtlMs`   | `0` (બંધ)           | **ના** — opt-in જ રહેશે (લોડ-બેલેન્સિંગ વિરુદ્ધ સાતત્ય; Discussion #5718 જુઓ)                          |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 મિનિટ) | **ના** — સામાન્ય ટ્રાફિક માટે 10 મિનિટ જ રહેશે; લાંબા Codex ઑપરેટર્સ તેને વધારે સેટ કરે અથવા અક્ષમ કરે |

કોઈપણ ડિફૉલ્ટને વૈશ્વિક સ્તરે બદલવાથી ફક્ત Codex નહીં, પરંતુ ઇન્સ્ટન્સના દરેક ક્લાયન્ટ માટે વર્તન બદલાશે. નૉબ્સનું દસ્તાવેજીકરણ કરો; કોઈ સ્પષ્ટ ઑપરેટર નિર્ણય અન્યથા ન કહે ત્યાં સુધી ડિફૉલ્ટ્સને યથાવત્ રાખો.

### આઇડલ કટ્સનું નિદાન

આઇડલ વૉચડૉગ ટ્રિગર થાય ત્યારે, OmniRoute નીચેના આકારની લાઇન લૉગ કરે છે:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

`Idle timeout: no data from` માટે grep કરો (અથવા કોડ `stream_idle_timeout` / એરર નામ `StreamIdleTimeoutError`). પ્રોવાઇડર સેગમેન્ટ એ હોય છે જે OmniRouteએ તે રિક્વેસ્ટ માટે ઉપયોગમાં લીધો હતો (`codex`, અન્ય provider id, અથવા અજ્ઞાત હોય તો `provider`) — તે હંમેશાં શાબ્દિક સ્ટ્રિંગ `codex` જ હોતું નથી.

## સમસ્યાનિવારણ

**`Error: wire_api = "chat" હવે સમર્થિત નથી`**
તમારા configમાંથી `wire_api = "chat"` દૂર કરો. `wire_api = "responses"` સેટ કરો અથવા આ fieldને છોડી દો (v0.138થી ડિફૉલ્ટ `"responses"` છે).

**`Error: model not found`**
ચકાસો કે યોગ્ય prefix સાથે model OmniRouteમાં ઉપલબ્ધ છે. `omniroute models list`નો ઉપયોગ કરો અથવા `/dashboard/providers/<provider>` ખોલો.

**`Authentication error`**
ખાતરી કરો કે `OMNIROUTE_API_KEY` export કરેલ છે: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
પ્રથમ request કરતાં પહેલાં Codex ચકાસે છે કે env var અસ્તિત્વમાં છે. સુરક્ષિત servers માટે
વાસ્તવિક key export કરો અથવા જ્યારે તમારી **સ્થાનિક** OmniRoute instanceને
authની જરૂર ન હોય ત્યારે `OMNIROUTE_API_KEY=local` જેવું ખાલી ન હોય તેવું placeholder વાપરો.
જો તમે તેને `~/.bashrc` અથવા `~/.zshrc`માં ઉમેર્યું હોય, તો shell પુનઃપ્રારંભ કરો.

**`Connection refused`**
ખાતરી કરો કે OmniRoute ચાલી રહ્યું છે અને `base_url`નું host/port તમારા network (local વિ. Tailscale વિ. VPS) માટે યોગ્ય છે.

**Context limitની નજીક session crash થાય છે**
`model_context_window` અને `model_auto_compact_token_limit` સ્પષ્ટ રીતે સેટ કરો. ઉપર આપેલું context window table જુઓ.

**Compaction ખૂબ મોડું શરૂ થાય છે**
`model_auto_compact_token_limit`ને windowના 80–85% સુધી ઘટાડો. તેને ક્યારેય 90%થી ઉપર સેટ ન કરો.

**Profile લોડ થતું નથી (`-p <name>` શાંતિથી અવગણવામાં આવે છે)**
ખાતરી કરો કે file `~/.codex/<name>.config.toml` પર અસ્તિત્વમાં છે (`profile-` prefix વિના). `ls ~/.codex/*.config.toml` ચલાવો.

**લાંબું Codex task ચાલતી વખતે અધવચ્ચે બંધ થઈ જાય છે / turns વચ્ચે accounts બદલાય છે**
[લાંબા સમય સુધી ચાલતાં tasks](#long-running-tasks) જુઓ. session affinity સક્ષમ કરો (TTL taskની અવધિ કરતાં વધારે રાખો) અને `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS` વધારો અથવા અક્ષમ કરો. `Idle timeout: no data from` માટે OmniRoute logsમાં grep કરો.
