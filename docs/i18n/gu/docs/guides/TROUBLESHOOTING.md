## ઝડપી સંદર્ભ

**OmniRoute માટે નવા છો?** અહીંથી શરૂ કરો — આ 90% સમસ્યાઓ ઉકેલે છે:

| મને આ દેખાય છે          | તેનો અર્થ શું છે                              | શું કરવું                                                                                                 |
| ----------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| "કનેક્ટ થઈ શકતું નથી"   | OmniRoute ચાલી રહ્યું નથી                     | `omniroute` ચલાવો અથવા `docker restart omniroute` ચલાવો                                                   |
| "અમાન્ય API કી"         | તમારી કી ખોટી છે અથવા તેની મુદત પૂરી થઈ ગઈ છે | પ્રદાતાની વેબસાઇટ પરથી કી ફરીથી કૉપિ કરો                                                                  |
| "રેટ મર્યાદા વટાવી ગઈ"  | તમે ઘણા બધા અનુરોધ મોકલી રહ્યા છો             | 1 મિનિટ રાહ જુઓ, અથવા આપમેળે ફૉલબૅક માટે `model: "auto"` વાપરો                                            |
| "ક્વોટા વટાવી ગયો"      | તમે તમારો મફત/ચૂકવેલ ક્વોટા વાપરી લીધો છે     | વધુ પ્રદાતાઓ કનેક્ટ કરો, અથવા મફત પ્રદાતાઓ (Kiro, Pollinations) વાપરો                                     |
| "ધીમા પ્રતિસાદો"        | પ્રદાતા વ્યસ્ત છે અથવા ઘણો દૂર છે             | `model: "auto/fast"` વાપરો અથવા વધુ ઝડપી પ્રદાતા (Groq, Cerebras) કનેક્ટ કરો                              |
| "ખોટો પ્રદાતા વપરાયો"   | `auto`એ અલગ પ્રદાતા પસંદ કર્યો                | આ સામાન્ય છે! `auto` શ્રેષ્ઠ પ્રદાતા પસંદ કરે છે. `model: "openai/gpt-4o"` વડે ચોક્કસ પ્રદાતા ફરજિયાત કરો |
| "502 ખરાબ ગેટવે"        | પ્રદાતા બંધ છે                                | રાહ જોઈને ફરી પ્રયાસ કરો, અથવા પ્રદાતા બદલવા માટે `model: "auto"` વાપરો                                   |
| "401 અનધિકૃત"           | તમારા ઓળખપત્રો ખોટા છે                        | તમારી API કી તપાસો અથવા OAuth વડે ફરીથી પ્રમાણિત કરો                                                      |
| "omniroute ઓળખાતું નથી" | Windows PATHમાં વૈશ્વિક node મોડ્યુલો નથી     | તમારો npm વૈશ્વિક પ્રીફિક્સ Windows PATHમાં ઉમેરો. તેને `npm config get prefix` વડે શોધો.                 |
| "429 ઘણા બધા અનુરોધો"   | રેટ મર્યાદા લાગુ થઈ છે                        | 1 મિનિટ રાહ જુઓ, અથવા વધુ પ્રદાતાઓ કનેક્ટ કરો                                                             |

### મફત પ્રદાતાઓ પર રેટ મર્યાદા (429 / 400 / 401)

**લક્ષણ**: મફત/પ્રમાણીકરણ-વિહોણા પ્રદાતાઓ (opencode, auggie, વગેરે) સાથે `model: "auto"` વાપરતી વખતે, તમને ક્યારેક જવાબોની જગ્યાએ `HTTP 429`, `400`, અથવા `401` મળે છે. થોડી ક્ષણો પછી એ જ પ્રોમ્પ્ટનો ફરી પ્રયાસ કરતાં અનુરોધો સફળ થાય છે, પરંતુ સ્વચાલન (cron jobs, agents, scripts) પહેલી નિષ્ફળતા પર જ તૂટી જાય છે.

**મૂળ કારણ**: ત્રણ સ્વતંત્ર નિષ્ફળતા સ્થિતિઓ એકસાથે સર્જાય છે:

1. **પ્રદાતાની રેટ મર્યાદા (`429`)**: મફત ટિયરમાં દરેક સમય-વિન્ડો માટે ક્વોટા લાગુ થઈ શકે છે. સમાંતર કૉલ્સનો અચાનક ધસારો તેને ખતમ કરી દે છે, તેથી વિન્ડો રીસેટ ન થાય ત્યાં સુધી આગળનો અનુરોધ નકારવામાં આવે છે.
2. **પાસથ્રૂમાં ખામીયુક્ત મોડલ (`400`/`401`)**: `auto/*` પૂલમાં `opencode`નાં એવા પાસથ્રૂ મોડલો સામેલ હોઈ શકે છે, જે કૅટલોગમાં નોંધાયેલા છે પરંતુ તેમની પાસે સક્રિય ઓળખપત્રો નથી (દા.ત. `oc/north-mini-code-free` → `401`). ઑટો-રાઉટર એકનો પ્રયાસ કરે છે, નિષ્ફળ જાય છે અને ફૉલબૅક સક્રિય થાય તે પહેલાં ભૂલ આગળ પ્રસારિત થઈ જાય છે.
3. **સમવર્તિતાનું પ્રવર્ધન (લોડ હેઠળ `429`)**: જ્યારે અનેક agent/cron સત્રો એકસાથે `auto`ને ઍક્સેસ કરે છે, ત્યારે કુલ અનુરોધ દર મફત પ્રદાતાઓ સહન કરી શકે તેનાથી વધી જાય છે, તેથી માન્ય કૉલ્સને પણ દુરુપયોગી તરીકે ચિહ્નિત કરવામાં આવે છે.

**ચકાસાયેલ ઉકેલ (સમુદાય દ્વારા અહેવાલિત, 2026-08-10)**: ત્રણ પર્યાવરણ ચલોને એવી રીતે સમાયોજિત કરો કે રોટેશન, સમવર્તિતા અને ફૉલબૅક મફત ટિયરની અસ્થિરતાને સંભાળી લે, તેના કારણે નિષ્ફળ ન થાય:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 પર બીજા મોડલ/પ્રદાતા પર જાઓ (ખામીયુક્ત પાસથ્રૂ મોડલોને છોડી દે છે)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # હેવીવેઇટ પ્રવેશ માટે સ્પષ્ટ મહત્તમ મર્યાદા (ડિફૉલ્ટ રૂપે અનસેટ: અનુરોધ-સંખ્યાની કોઈ મર્યાદા નહીં, નીચેની નોંધ જુઓ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # ધીમા અપસ્ટ્રીમ માટે મર્યાદિત રાહને RATE_LIMIT_MAX_WAIT_MSના ડિફૉલ્ટથી આગળ વધારો
```

આને OmniRoute પ્રોસેસના પર્યાવરણમાં સેટ કરો (ડિમન, દા.ત. LaunchAgent plist અથવા `systemctl edit` મારફતે), પછી OmniRoute ફરી શરૂ કરો. રોટેશન ફ્લૅગ સૌથી વધુ અસરકારક એકલ ઉપાય છે: તે પૂલમાંના સ્વસ્થ પ્રદાતા સામે પારદર્શક પુનઃપ્રયાસ કરીને કઠોર નિષ્ફળતાને સફળતામાં ફેરવે છે.

**નોંધ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` એક સમયે કેટલા હેવીવેઇટ — લાંબા-સંદર્ભવાળા — અનુરોધો ચાલે છે તેની મર્યાદા નક્કી કરે છે; આ સીમા પ્રવેશ દ્વાર છે, પ્રદાતાની રેટ મર્યાદા નથી. **#503-fanout અપડેટ:** આ ચલ હવે ડિફૉલ્ટ રૂપે સેટ થતો નથી (હવે તે ઉપર મુજબ સ્પષ્ટ રીતે ગોઠવવામાં આવે ત્યારે જ લાગુ થાય છે) — તેના બદલે હેવીવેઇટ પ્રવેશને આપમેળે નિર્ધારિત બાઇટ બજેટ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) દ્વારા નિયંત્રિત કરવામાં આવે છે, જે હોસ્ટની વાસ્તવિક મેમરી મર્યાદા અનુસાર પોતાને સ્કેલ કરે છે; તેથી નવી ડિપ્લોયમેન્ટમાં આ ચલ બિલકુલ સેટ કર્યા વિના પણ ઘણા ઓછા `503 chat_admission_busy` નકાર જોવા મળવા જોઈએ; અહીં તેને સ્પષ્ટ રીતે સેટ કરવાનું હજી પણ દસ્તાવેજીકરણમાં દર્શાવ્યા પ્રમાણે જ કાર્ય કરે છે. સ્પષ્ટ બાઇટ-બજેટ ઓવરરાઇડ્સને 8 MiB–2 GiB સુધી મર્યાદિત કરવામાં આવે છે. `413 body_exceeds_budget` ક્ષણિક નથી: તે બાઇટ બજેટ વધારો, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ઘટાડો, અથવા પ્રોસેસની મેમરી મર્યાદા વધારો. `inflight_bytes_budget` શેડ અસ્થાયી સંસાધન-સ્પર્ધા છે અને તેનો ફરી પ્રયાસ કરી શકાય છે. દરેક પ્રદાતા દીઠ રેટ મર્યાદા (`open-sse/services/rateLimitManager.ts`) અલગથી `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, અને `RATE_LIMIT_AUTO_ENABLE` દ્વારા સંચાલિત થાય છે — `.env.example` જુઓ.

**તે કાર્યરત થયું છે કે નહીં તેની ચકાસણી કેવી રીતે કરવી**: તમારા agent/cron ને ઝડપથી સતત બે વખત ચલાવો અને ખાતરી કરો કે બંને વખત સફળ થાય છે. સુધારા પહેલાં, બીજી વખત ચલાવતાં સામાન્ય રીતે `429`/`401` ભૂલ આવે છે. સુધારા પછી, નિષ્ફળતાઓ (જો કોઈ હોય તો) માટે પારદર્શક રીતે ફરી પ્રયાસ કરવામાં આવે છે અને call પૂર્ણ થાય છે. તમે `curl /monitoring/health` પણ ચલાવી શકો છો અને provider connections પરનું `rateLimitedUntil` field તેમજ અસરગ્રસ્ત providers માટે `circuitBreakers.providerBreakers[].state` જોઈ શકો છો — state `CLOSED`, `DEGRADED`, `OPEN`, અથવા `HALF_OPEN` માંથી એક હોય છે (`src/shared/utils/circuitBreaker.ts` જુઓ), અને સતત નિષ્ફળ થતો provider reset window દ્વારા probe પસાર થવા દેવામાં આવે તે પહેલાં `CLOSED → DEGRADED → OPEN` સ્થિતિમાં બદલાશે (`HALF_OPEN`).

**જો તમને હજુ પણ 429 દેખાય**: તે provider માટેના active account નો _quota_ ખરેખર સમાપ્ત થઈ ગયો છે (માત્ર rate નહીં). OmniRoute dashboard → Providers → Accounts માં સમાન provider માટે બીજું account ઉમેરો અથવા અન્ય કોઈ free provider (દા.ત. `routeway`, `auggie`) સામેલ કરો. Rotation ફક્ત ક્ષણિક rate/400/401 માટે મદદરૂપ થાય છે; સંપૂર્ણ quota exhaustion માટે બીજા credential અથવા અલગ provider ની જરૂર પડે છે.

**જો તમને vision models (`auto/vision`, `bazaarlink/*`) પર 403 દેખાય**: જોડાયેલા account પાસે vision નો સમાવેશ કરતો paid plan નથી અથવા API key પાસે પૂરતી permissions નથી. provider dashboard માં ચકાસો કે key scope માં vision/multimodal નો સમાવેશ થાય છે અથવા paid tier account જોડો અને તેને vision target તરીકે રાખો.

## npm install ચેતવણીઓ (ERESOLVE / peer / deprecated)

જ્યારે તમે `npm install -g omniroute` ચલાવો છો, ત્યારે તમને `npm warn ERESOLVE`, peer-dependency સૂચનાઓ અને `deprecated` સંદેશાઓ જેવી ઘણી ચેતવણીઓ દેખાઈ શકે છે. **આ અપેક્ષિત અને હાનિરહિત છે.** જો આઉટપુટમાં `added <N> packages` દેખાય, તો તમારું ઇન્સ્ટોલેશન સફળ થયું છે.

peer-dependency resolution ચેતવણીઓને દબાવવા માટે, OmniRouteનું સમર્થિત ઇન્સ્ટોલેશન સ્વરૂપ વાપરો:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` માત્ર `ERESOLVE` અને peer-dependency સૂચનાઓને દબાવે છે. Deprecation સૂચનાઓ દેખાતી રહે છે, કારણ કે તે transitive third-party packagesમાંથી આવે છે; તે ઇન્સ્ટોલેશન નિષ્ફળ ગયું હોવાનું સૂચવતી નથી.

આ ચેતવણીઓ એવા third-party packagesમાં રહેલી જૂની peer-dependency rangesને કારણે આવે છે, જેને OmniRoute નિયંત્રિત કરતું નથી:

1. **`marked-terminal`ને `marked >=1 <16` જોઈએ છે, પરંતુ `marked@18` મળ્યું** — વ્યવહારમાં યોગ્ય રીતે કાર્ય કરે છે; upstream peer range માત્ર જૂની છે.
2. **`deprecated prebuild-install@7.1.3`** — transitive native-binary fetch helper. તેનો ઉપયોગ
   pinned `wreq-js` transport binding ઇન્સ્ટોલ કરવા માટે થતો નથી અને તે web-cookie
   provider transport setup નિષ્ફળ ગયું હોવાનું સૂચવતું નથી.

**કોઈ કાર્યવાહી જરૂરી નથી** — upstream packagesને fork કર્યા વિના આ ચેતવણીઓને સંપૂર્ણપણે નિષ્ક્રિય કરી શકાતી નથી.

## npm install-scripts અવરોધિત હોવાની ચેતવણી (global install)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` ચલાવતી વખતે, npmનાં નવા versions (v11+ અને v12+) મૂળભૂત રીતે package lifecycle scriptsને અવરોધે છે અને install-scripts ચેતવણી દર્શાવે છે:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### શું આ ચેતવણી અવગણી શકાય છે?

**આંશિક રીતે, પરંતુ scripts વિના ચલાવવાની ભલામણ કરવામાં આવતી નથી.** OmniRouteમાં સુવ્યવસ્થિત fallbacks સામેલ છે: જો native `better-sqlite3` bindingsને standalone bundleમાંથી લોડ ન કરી શકાય, તો application `node:sqlite` અથવા `sql.js` જેવા વૈકલ્પિક driversનો ઉપયોગ કરે છે (જુઓ [SQLite Runtime Resolution](../ops/SQLITE_RUNTIME.md)). Server તેમ છતાં શરૂ થશે, પરંતુ `sql.js` જેવા WASM fallbacks પર ચલાવવાથી SQLite WAL (Write-Ahead Logging) mode નિષ્ક્રિય થાય છે અને memory તથા disk-sync overhead વધે છે.

### વાસ્તવમાં કયા scripts જરૂરી છે?

અવરોધિત થયેલા બધા scripts OmniRoute ચલાવવા માટે આવશ્યક નથી:

- **આવશ્યક (`omniroute`, `better-sqlite3`):** OmniRoute Next.js standalone application bundle (`dist/`)માંથી ચાલે છે. ઇન્સ્ટોલેશન દરમિયાન, npm top-level `node_modules/better-sqlite3/`માં host-specific native SQLite driver ડાઉનલોડ અથવા compile કરે છે. ત્યારબાદ OmniRouteનું `postinstall` script (`scripts/build/postinstall.mjs`) આ host-specific binariesને ચકાસે છે અને `dist/node_modules/`માં copy કરે છે, જેથી standalone server તેમને ઍક્સેસ કરી શકે. જો `omniroute`નું postinstall script અવરોધિત હોય, તો આ copy step છોડી દેવામાં આવે છે.
- **વૈકલ્પિક/transitive (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** આ build helpers, watcher tools અથવા system keychain utilities છે. તેમને મંજૂરી આપવાથી build ચેતવણીઓ અટકે છે, પરંતુ core routing functionality માટે તેઓ જરૂરી નથી.
- **બાકાત (`onnxruntime-node`):** local AI embeddings માટેની વૈકલ્પિક dependency છે અને OmniRoute ચલાવવા માટે **જરૂરી નથી**. તેનું postinstall script NuGetમાંથી આશરે 300MB CUDA assets ડાઉનલોડ કરે છે; જ્યાં સુધી તમે સમર્થિત hardware પર local ONNX accelerationનો સ્પષ્ટપણે ઉપયોગ કરવા માંગતા ન હો, ત્યાં સુધી તેને allow-listમાં સામેલ કરશો નહીં.

### ભલામણ કરેલો ઉકેલ

global install દરમિયાન જરૂરી install scriptsને મંજૂરી આપવા અને ચેતવણીઓને નિષ્ક્રિય કરવા માટે, OmniRoute અને તેની native dependencies માટે `--allow-scripts` આપો:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

વૈકલ્પિક રીતે, તમારા user account પર તમામ global installations માટે આને કાયમી રીતે configure કરવા માટે:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### તમારું ઇન્સ્ટોલેશન ચકાસો

ઇન્સ્ટોલેશન પછી, native bindings અને runtime environment યોગ્ય સ્થિતિમાં છે તેની ખાતરી કરવા માટે built-in diagnostic tool ચલાવો:

```bash
omniroute doctor
```

## Gemini Web અને Playwright Chromium

જો Gemini Web વિનંતી `503` સાથે એવો સંદેશ પરત કરે કે Playwright Chromium
ઇન્સ્ટૉલ થયેલું નથી, તો npm પૅકેજ હાજર છે પરંતુ બ્રાઉઝર બાઇનરી ખૂટે છે.
Playwright ઇરાદાપૂર્વક બ્રાઉઝર ડાઉનલોડને npm પૅકેજના
ઇન્સ્ટૉલેશનથી અલગ રાખે છે, તેથી બ્રાઉઝર ઇન્સ્ટૉલ ન થાય ત્યાં સુધી આ પ્રતિસાદ અપેક્ષિત છે.

વૈશ્વિક npm ઇન્સ્ટૉલેશન માટે, OmniRoute પૅકેજની
ડિરેક્ટરીમાંથી Chromium ઇન્સ્ટૉલ કરો, જેથી બ્રાઉઝર કૅશ એ જ Playwright ઇન્સ્ટૉલેશન સાથે સંકળાયેલ રહે:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ઇન્સ્ટૉલેશન પછી OmniRoute પુનઃપ્રારંભ કરો, ત્યારબાદ Gemini Web વિનંતીનો ફરી પ્રયાસ કરો. જો તમે
Docker ઇમેજમાંથી OmniRoute ચલાવતા હો, તો `-web` ઇમેજ (અથવા `runner-web`
બિલ્ડ ટાર્ગેટ) વાપરો, જેમાં Chromium અને તેની નિર્ભરતાઓ સમાવિષ્ટ છે; બેઝ ઇમેજમાં
તે સામેલ નથી.

## એન્ટિવાયરસના ખોટા પોઝિટિવ

<a name="antivirus-false-positives"></a>

### Avast/AVG `README.md` ને `MD:HttpRequest-inf[Susp]` તરીકે ક્વોરન્ટાઇન કરે છે

**આ ખોટો પોઝિટિવ છે. કંઈપણ સંક્રમિત નથી અને કોઈ કાર્યવાહી જરૂરી નથી.**

Avast અને AVG એવી હ્યુરિસ્ટિક ચલાવે છે જે ઘણા HTTP વિનંતી જેવા દેખાતા લિંક્સ ધરાવતી
પ્લેઇન-ટેક્સ્ટ/Markdown ફાઇલોને ફ્લૅગ કરે છે. OmniRoute નું `README.md` npm પૅકેજની અંદર આવે છે (તે
`package.json` → `files` માં સૂચિબદ્ધ છે), તેથી વૈશ્વિક ઇન્સ્ટોલેશન વખતે તે
`node_modules/omniroute/README.md` પર પહોંચે છે — અને તેમાં ~15 `http://localhost:20128/...`
ઉદાહરણો (MCP HTTP/SSE એન્ડપોઇન્ટ્સ, A2A `.well-known` URL અને `curl` સ્નિપેટ્સ) છે. લિંકની આટલી
ઘનતા હ્યુરિસ્ટિકને ટ્રિગર કરવા માટે પૂરતી છે.

જો આ સમસ્યા તાજેતરમાં જ શરૂ થઈ હોય: ફાઇલના પ્રકારમાં કોઈ ફેરફાર થયો નથી. README માં તેની
એન્ડપોઇન્ટ્સ ટેબલનો વિસ્તાર થયો (MCP HTTP + SSE + A2A ઉમેરવામાં આવ્યા) અને વધુ `curl`
ઉદાહરણો ઉમેરાયાં, જેના કારણે તે મર્યાદા વટાવી ગઈ.

આ ફાઇલ કોઈપણ એક્ઝિક્યુટેબલ સામગ્રી વિનાનું નિષ્ક્રિય દસ્તાવેજીકરણ છે. તમે તેને
ક્વોરન્ટાઇનમાંથી સુરક્ષિત રીતે પુનઃસ્થાપિત કરી શકો છો.

**શું કરવું:**

1. **સૂચનાઓ બંધ કરો** — તમારા એન્ટિવાયરસમાં ઇન્સ્ટોલેશન ડિરેક્ટરીને બાકાત રાખો
   (Avast: Settings → Exceptions), અને તેમાં તમારો વૈશ્વિક `node_modules` પાથ અને/અથવા
   OmniRoute ડેટા ડિર (`~/.omniroute/`) ઉમેરો.
2. **ખોટા પોઝિટિવની જાણ કરો** — <https://www.avast.com/false-positive-file-form.php>,
   અને ક્વોરન્ટાઇન કરેલું `README.md` જોડો. આ એવો ઉપાય છે જે દરેકને મદદ કરે છે, કારણ કે અહીં
   વેન્ડરની હ્યુરિસ્ટિક ટેક્સ્ટ ફાઇલ પર અતિશય પ્રતિક્રિયા આપી રહી છે.

**અમે અમારી તરફથી આને શા માટે "સુધારતા" નથી:** બધા ઉદાહરણો `http://localhost` છે અને
સ્વ-હસ્તાક્ષરિત પ્રમાણપત્રની અડચણ વિના localhost ને `https` બનાવી શકાતું નથી. એક વેન્ડરની
હ્યુરિસ્ટિકથી બચવા માટે દસ્તાવેજોને વિકૃત કરવાથી સ્કૅનરની ખામીને સંતોષવા માટે દરેક વાચકને
નુકસાન થશે.

### Kaspersky Desktop ઍપને `PDM:Trojan.Win32.Generic` તરીકે ફ્લૅગ કરે છે

**આ વર્તણૂક-આધારિત હ્યુરિસ્ટિકમાંથી આવતો ખોટો પોઝિટિવ છે. કંઈપણ સંક્રમિત નથી.** Kaspersky નો
`PDM:` પ્રીફિક્સ દર્શાવે છે કે નિર્ણય તેના Proactive Defense Module (System Watcher) માંથી
આવે છે, જે ઇન્સ્ટોલર જાણીતા માલવેર સાથે મેળ ખાય છે કે નહીં તેના બદલે તે શું _કરે છે_ તેનું
મૂલ્યાંકન કરે છે. જ્યારે તે ટ્રિગર થાય છે, ત્યારે Kaspersky સમગ્ર ઇન્સ્ટોલેશનને "રોલ બૅક"
કરે છે — તેણે અગાઉ લખેલી ફાઇલોને કાઢી નાખે છે — તેથી ઍપ અંતે ખરાબ થઈ જાય છે અથવા ગુમ થઈ જાય છે.

તે જે ફાઇલોને ફ્લૅગ કરે છે તે Desktop ઍપ સાથે બંડલ કરેલી જાહેર કરાયેલી, ઓપન-સોર્સ
ડિપેન્ડન્સીઝના પ્રમાણભૂત ભાગો છે, ઉદાહરણ તરીકે:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` અને
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ઍપમાં પ્રોવાઇડર લૉગિન અને
  બ્રાઉઝર-આધારિત ચૅટ માટે વપરાતી બ્રાઉઝર-ઑટોમેશન લાઇબ્રેરી.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — વેબ-કૂકી પ્રોવાઇડર્સ પર બ્રાઉઝર-ફિંગરપ્રિન્ટેડ HTTP માટે વપરાતું પિન કરેલું `wreq-js`
  નેટિવ બાઇન્ડિંગ (`<arch>` એ `x64` અથવા `arm64` છે).

**તે શા માટે ટ્રિગર થાય છે:** Windows ઇન્સ્ટોલર હજી સુધી **કોડ-સાઇન્ડ નથી**, તેથી અનસાઇન્ડ
NSIS ઇન્સ્ટોલરની કોઈ પ્રતિષ્ઠા હોતી નથી અને વર્તણૂક-આધારિત હ્યુરિસ્ટિક્સ મહત્તમ આક્રમકતા સાથે
ચાલે છે. બંડલ કરેલી નેટિવ DLL અને `%LOCALAPPDATA%\Programs\OmniRoute` હેઠળ લખાતી સેંકડો `.js`
ફાઇલો (Next.js સ્ટૅન્ડઅલોન બિલ્ડમાંથી હૅશ-સફિક્સ ધરાવતી પૅકેજ ડિરેક્ટરીઝ સહિત) સાથે મળીને,
આ હ્યુરિસ્ટિકને ટ્રિગર કરવા માટે પૂરતું છે. કોડ સાઇનિંગની યોજના છે; તે અમલમાં ન આવે ત્યાં સુધી,
નવી રિલીઝમાં આ ફરી થઈ શકે છે.

**શું કરવું:**

1. **પહેલાં તમારું ડાઉનલોડ ચકાસો** (આનાથી ચેડાં કરેલી ફાઇલની શક્યતા નકારી શકાય છે). દરેક રિલીઝ
   `latest.yml` પ્રકાશિત કરે છે, જેનું `sha512` ફીલ્ડ (base64) `OmniRoute.Setup.<version>.exe`
   ઇન્સ્ટોલરને આવરી લે છે. PowerShell માં, ઇન્સ્ટોલર ધરાવતા ફોલ્ડરમાંથી:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   આઉટપુટ `latest.yml` → `sha512` સાથે મેળ ખાતું હોવું જોઈએ. જો તેમ ન હોય, તો ફાઇલ કાઢી નાખો અને
   ફક્ત [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) પરથી ફરી ડાઉનલોડ કરો.
2. **પુનઃસ્થાપિત કરો + બાકાત રાખો** — રોલ બૅક કરેલી આઇટમ્સને ક્વોરન્ટાઇનમાંથી પુનઃસ્થાપિત કરો અને
   `%LOCALAPPDATA%\Programs\OmniRoute` માટે એક્સક્લૂઝન ઉમેરો (Kaspersky → Settings → Threats and Exclusions),
   પછી ફરીથી ઇન્સ્ટોલ કરો.
3. **ખોટા પોઝિટિવની જાણ કરો** — <https://opentip.kaspersky.com/>. વપરાશકર્તાઓ દ્વારા સબમિટ કરાયેલા FP
   રિપોર્ટ્સ ખરેખર અલાઉલિસ્ટિંગને ઝડપી બનાવે છે.

## Node.js સુસંગતતા

### લૉગિન પેજ ક્રૅશ થાય છે અથવા "Module self-registration" ભૂલ દર્શાવે છે

**કારણ:** તમે OmniRoute દ્વારા મંજૂર સુરક્ષિત રનટાઇમની લઘુતમ મર્યાદાની બહારનું Node.js વર્ઝન ચલાવી રહ્યા છો. સૌથી સામાન્ય કિસ્સો Node 22 અથવા 24નું એવું જૂનું પૅચ લેવલ ચલાવવાનો છે, જે OmniRoute માટે જરૂરી પૅચ કરેલી સુરક્ષા મર્યાદાથી નીચે હોય.

**લક્ષણો:**

- લૉગિન પેજ ખાલી સ્ક્રીન અથવા સર્વર ભૂલ દર્શાવે છે
- કન્સોલમાં `Error: Module did not self-register` અથવા તેના જેવી નેટિવ બાઇન્ડિંગ ભૂલો દેખાય છે
- જો રનટાઇમ સમર્થિત સુરક્ષા નીતિની બહાર હોય, તો લૉગિન પેજ તમારા Node વર્ઝન સાથે **નારંગી ચેતવણી બૅનર** દર્શાવે છે

**ઉકેલ:**

1. સમર્થિત Node.js LTS રિલીઝ ઇન્સ્ટૉલ કરો (ભલામણ કરેલ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. તમારું વર્ઝન ચકાસો: `node --version` એ 24.x LTS શ્રેણીમાં `v24.0.0` અથવા તેનાથી નવું વર્ઝન દર્શાવવું જોઈએ
3. OmniRoute ફરીથી ઇન્સ્ટૉલ કરો: `npm install -g omniroute`
4. ફરી શરૂ કરો: `omniroute`

> **સમર્થિત સુરક્ષિત વર્ઝન:** `>=22.22.2 <23` અથવા `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) અને Node.js 26 સંપૂર્ણપણે સમર્થિત છે.

### npm v11+: `better-sqlite3` ઇન્સ્ટૉલ થયેલું નથી (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**કારણ:** npm v11 (Node.js 24+ સાથે સમાવિષ્ટ) ડિફૉલ્ટ રૂપે વૈકલ્પિક
ડિપેન્ડન્સીઓ માટેની ઇન્સ્ટૉલ સ્ક્રિપ્ટ્સને અવરોધે છે. `better-sqlite3`ને `optionalDependencies`
માં સૂચિબદ્ધ કરવામાં આવ્યું છે અને તેને નેટિવ કમ્પાઇલેશન (`node-gyp rebuild`) જરૂરી હોવાથી, npm તેને કોઈ સૂચના આપ્યા વિના છોડી દે છે.

**લક્ષણો:**

- સર્વર શરૂ થતી વખતે `Cannot find module 'better-sqlite3'` સાથે ક્રૅશ થાય છે
- `ls node_modules/better-sqlite3` ચલાવવાથી "No such file or directory" દેખાય છે
- `npm ls better-sqlite3` ચલાવવાથી `(empty)` દેખાય છે

**ઉકેલ:**

1. ઇન્સ્ટૉલ સ્ક્રિપ્ટ્સને મંજૂરી આપો અને ફરીથી ઇન્સ્ટૉલ કરો:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. અથવા પૂર્વનિર્મિત પૅકેજને મૅન્યુઅલી ઇન્સ્ટૉલ કરો:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. તે કાર્ય કરે છે તેની ખાતરી કરો: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**કારણ:** વૈશ્વિક `npm install -g omniroute` પછી, પૅકેજની અંદરની `better-sqlite3` નેટિવ બાઇનરી સ્થાનિક રીતે ચાલી રહેલા આર્કિટેક્ચર અથવા Node.js ABI કરતાં અલગ આર્કિટેક્ચર અથવા ABI માટે કમ્પાઇલ થયેલી હોઈ શકે છે. જ્યારે પૂર્વનિર્મિત બાઇનરી તમારા પર્યાવરણ સાથે મેળ ખાતી નથી ત્યારે macOS પર (Apple Silicon અને Intel બંનેમાં) આવું સામાન્ય રીતે બને છે.

**લક્ષણો:**

- સર્વર શરૂ થતાની સાથે જ `dlopen` ભૂલ સાથે નિષ્ફળ જાય છે
- ભૂલમાં `slice is not valid mach-o file` હોય છે
- સંપૂર્ણ ઉદાહરણ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ઉકેલ — તમારા સ્થાનિક પર્યાવરણ માટે ફરીથી બિલ્ડ કરો (Node.js ડાઉનગ્રેડ કરવાની જરૂર નથી):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **નોંધ:** આ તમારા સ્થાનિક Node.js વર્ઝન અને CPU આર્કિટેક્ચર માટે નેટિવ બાઇન્ડિંગને ફરીથી કમ્પાઇલ કરે છે, જેનાથી બાઇનરીનો મેળ ન ખાવાની સમસ્યા ઉકેલાય છે. અધિકૃત રીતે સમર્થિત રનટાઇમ શ્રેણી **`>=22.22.2 <23` અથવા `>=24.0.0 <27`** છે (`src/shared/utils/nodeRuntimeSupport.ts`માં `SUPPORTED_NODE_RANGE`, જે `package.json`ના `engines` ફીલ્ડ સાથે સુસંગત છે). Node.js 24.x LTS (Krypton) અને Node.js 26, `better-sqlite3` v12.x સાથે સંપૂર્ણપણે સમર્થિત છે.

## પ્રોક્સી સમસ્યાઓ

<a name="proxy-issues"></a>

### પ્રોવાઇડર માન્યતા દરમિયાન "fetch failed" દેખાય છે

**કારણ:** API કી માન્યતા એન્ડપોઇન્ટ (`POST /api/providers/validate`) અગાઉ પ્રોક્સી કૉન્ફિગરેશનને બાયપાસ કરતું હતું, જેના કારણે પ્રોક્સી રૂટિંગ જરૂરી હોય તેવા પર્યાવરણોમાં નિષ્ફળતા થતી હતી.

**ઉકેલ (v3.5.5+):** હવે આ સમસ્યા સુધારવામાં આવી છે. પ્રોવાઇડર માન્યતા `runWithProxyContext` મારફતે રૂટ થાય છે અને પ્રોવાઇડર-સ્તરની તથા વૈશ્વિક પ્રોક્સી સેટિંગ્સને આપમેળે અનુસરે છે.

### ટોકન હેલ્થ ચેક "fetch failed" સાથે નિષ્ફળ જાય છે

**કારણ:** બૅકગ્રાઉન્ડ OAuth ટોકન રિફ્રેશ દરેક કનેક્શન માટે પ્રોક્સી કૉન્ફિગરેશન રિઝોલ્વ કરતું ન હતું.

**ઉકેલ (v3.5.5+):** ટોકન હેલ્થ ચેક શેડ્યૂલર હવે રિફ્રેશ કરવાનો પ્રયાસ કરતાં પહેલાં દરેક કનેક્શન માટે પ્રોક્સી કૉન્ફિગ રિઝોલ્વ કરે છે. v3.5.5+ પર અપડેટ કરો.

### SOCKS5 પ્રોક્સી "invalid onRequestStart method" પરત કરે છે

**કારણ:** Node.js 22 પર undici@8 ડિસ્પેચર, Node ના બિલ્ટ-ઇન `fetch()` અમલીકરણ સાથે અસંગત છે.

**ઉકેલ (v3.5.5+):** પ્રોક્સી ડિસ્પેચર સક્રિય હોય ત્યારે OmniRoute હવે undici ના પોતાના `fetch()` ફંક્શનનો ઉપયોગ કરે છે, જેથી સુસંગત વર્તન સુનિશ્ચિત થાય. v3.5.5+ પર અપડેટ કરો.

### WSL હેઠળ MITM પ્રોક્સી: Windows હોસ્ટ પરની ડેસ્કટોપ ઍપ્સ ઇન્ટરસેપ્ટ થતી નથી

**કારણ:** MITM પ્રોક્સી અને તેનું CA સર્ટિફિકેટ OmniRoute જે પર્યાવરણમાં ચાલે છે તેમાં ઇન્સ્ટોલ થાય છે. WSL હેઠળ તે પર્યાવરણ Linux ગેસ્ટ છે, જ્યારે AI ડેસ્કટોપ ઍપ્સ (Kiro, Trae, Copilot, Zed, …) Windows હોસ્ટ પર ચાલે છે. હોસ્ટ ઍપ્સ ગેસ્ટના સર્ટિફિકેટ સ્ટોર પર વિશ્વાસ કરતી નથી અને ગેસ્ટના સિસ્ટમ પ્રોક્સી મારફતે રૂટ થતી નથી, તેથી ડેસ્કટોપ ઇન્ટરસેપ્શન ત્યાં સક્રિય થતું નથી.

**ભલામણ:** તમે જે ડેસ્કટોપ ઍપ્સને ઇન્ટરસેપ્ટ કરવા માંગો છો, તે જ OS પર OmniRoute ને નેટિવ રીતે ચલાવો (Windows ઍપ્સ માટે Windows; તેવી જ રીતે macOS/Linux). હોસ્ટ ઍપ્સને લક્ષ્ય બનાવતી વખતે OmniRoute ને WSL ની અંદર રાખવા માટે Windows હોસ્ટ પર જનરેટ થયેલ CA સર્ટિફિકેટને મૅન્યુઅલી વિશ્વસનીય બનાવવું અને દરેક હોસ્ટ ઍપના નેટવર્ક/પ્રોક્સી સેટિંગ્સને WSL પ્રોક્સી એન્ડપોઇન્ટ તરફ નિર્દેશિત કરવું જરૂરી છે — આ અસપોર્ટેડ અને અસ્થિર સેટઅપ છે.

### રેટ લિમિટિંગ

**કારણ:** સબ્સ્ક્રિપ્શન ક્વોટા સમાપ્ત થઈ ગયો છે.

**ઉકેલ:**

OmniRoute ટોકન્સને આપમેળે રિફ્રેશ કરે છે. જો સમસ્યાઓ યથાવત્ રહે:

1. ડૅશબોર્ડ → પ્રોવાઇડર → ફરીથી કનેક્ટ કરો
2. પ્રોવાઇડર કનેક્શન ડિલીટ કરીને ફરીથી ઉમેરો

### Kiro મલ્ટિ-એકાઉન્ટ: બીજું એકાઉન્ટ પહેલા એકાઉન્ટને અમાન્ય કરે છે

**કારણ:** Kiro નું બૅકએન્ડ દરેક OIDC ક્લાયન્ટ રજિસ્ટ્રેશન દીઠ માત્ર એક સક્રિય સેશનની મંજૂરી આપે છે.
જ્યારે બે એકાઉન્ટ એક જ રજિસ્ટર્ડ ક્લાયન્ટ શેર કરે છે (v3.8.0 પહેલાં ઇમ્પોર્ટ કરાયેલા કનેક્શન્સ),
ત્યારે એક એકાઉન્ટનું ટોકન રિફ્રેશ કરવાથી બીજા એકાઉન્ટનું રિફ્રેશ ટોકન અમાન્ય થઈ જાય છે.

**ઉકેલ (v3.8.0+):** અસરગ્રસ્ત કનેક્શન્સને ફરીથી ઇમ્પોર્ટ કરો.
v3.8.0 થી શરૂ કરીને, **ટોકન ઇમ્પોર્ટ**, **Google/GitHub સોશિયલ લૉગિન**, અથવા **ઑટો-ઇમ્પોર્ટ** મારફતે બનાવવામાં આવતું દરેક નવું Kiro કનેક્શન આપમેળે પોતાનો
સમર્પિત OIDC ક્લાયન્ટ રજિસ્ટર કરે છે. તેથી કનેક્શન સંપૂર્ણપણે અલગ રહે છે અને એક
એકાઉન્ટને રિફ્રેશ કરવાથી અન્ય કોઈ એકાઉન્ટ પર અસર થતી નથી.

## ક્લાઉડ સમસ્યાઓ

### ક્લાઉડ સિંક ભૂલો

1. ખાતરી કરો કે `BASE_URL` તમારા ચાલી રહેલા ઇન્સ્ટન્સ તરફ નિર્દેશ કરે છે (દા.ત., `http://localhost:20128`)
2. ખાતરી કરો કે `CLOUD_URL` તમારા ક્લાઉડ એન્ડપોઇન્ટ તરફ નિર્દેશ કરે છે (દા.ત., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` મૂલ્યોને સર્વર-સાઇડ મૂલ્યો સાથે સુસંગત રાખો

### ક્લાઉડમાં `stream=false` 500 પરત કરે છે

**લક્ષણ:** નોન-સ્ટ્રીમિંગ કૉલ્સ માટે ક્લાઉડ એન્ડપોઇન્ટ પર `Unexpected token 'd'...`.

**કારણ:** ક્લાયંટ JSONની અપેક્ષા રાખે છે, જ્યારે અપસ્ટ્રીમ SSE પેલોડ પરત કરે છે.

**વૈકલ્પિક ઉપાય:** ક્લાઉડ પર સીધા કૉલ્સ માટે `stream=true` વાપરો. સ્થાનિક રનટાઇમમાં SSE→JSON ફૉલબૅક સામેલ છે.

### ક્લાઉડ કનેક્ટેડ બતાવે છે પરંતુ "અમાન્ય API કી" કહે છે

1. સ્થાનિક ડૅશબોર્ડ (`/api/keys`) પરથી નવી કી બનાવો
2. ક્લાઉડ સિંક ચલાવો: ક્લાઉડ સક્ષમ કરો → હમણાં સિંક કરો
3. જૂની/સિંક ન થયેલી કી હજુ પણ ક્લાઉડ પર `401` પરત કરી શકે છે

## Docker સમસ્યાઓ

### Docker IPv6 / કનેક્શન રીસેટ

<a name="docker-ipv6"></a>

**લક્ષણો:** `curl http://localhost:20128/v1/models` ચલાવવાથી `curl: (56) Recv failure: Connection reset by peer` પરત મળે છે. ડૅશબોર્ડ અને બિન-પ્રમાણિત એન્ડપોઇન્ટ કાર્ય કરે છે, પરંતુ પ્રમાણિત એન્ડપોઇન્ટ નિષ્ફળ જાય છે — આ પ્રમાણીકરણની સમસ્યા જેવું લાગે છે, પરંતુ એવું નથી.

**કારણ:** `docker run -p 20128:20128`, `0.0.0.0` (IPv4) અને `::` (IPv6) બંને પર પોર્ટ પ્રકાશિત કરે છે, પરંતુ કન્ટેનરની અંદરની પ્રોસેસ માત્ર IPv4 પર સાંભળે છે. જે હોસ્ટ પર `localhost` સૌપ્રથમ `::1` તરીકે રિઝોલ્વ થાય છે, ત્યાં કનેક્શન IPv6 પર પ્રકાશિત પોર્ટ સુધી પહોંચે છે, પરંતુ તેની પાછળ કોઈ લિસનર ન હોવાથી → કનેક્શન રીસેટ થાય છે.

**ઉકેલ:**

1. **ઝડપી નિદાન:** `curl -4 http://localhost:20128/v1/models` ચલાવો. જો તે `-4` સાથે કાર્ય કરે પરંતુ તેના વિના નિષ્ફળ જાય, તો તમારી પાસે IPv6 બાઇન્ડ અસંગતતા છે.
2. **કાયમી ઉકેલ:** તમારા `docker run` કમાન્ડમાં `-p 127.0.0.1:20128:20128` વાપરીને સ્પષ્ટપણે IPv4 સાથે બાઇન્ડ કરો:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   આ IPv4 બાઇન્ડને ફરજિયાત બનાવે છે અને પ્રૉક્સીને હોસ્ટનાં તમામ ઇન્ટરફેસ પર ખુલ્લું મૂકવાનું પણ ટાળે છે.

### CLI ટૂલ ઇન્સ્ટૉલ થયેલું નથી એમ બતાવે છે

1. રનટાઇમ ફીલ્ડ તપાસો: `curl http://localhost:20128/api/cli-tools/runtime/codex | jq`
2. પોર્ટેબલ મોડ માટે: ઇમેજ ટાર્ગેટ `runner-cli` (બંડલ કરેલા CLI) વાપરો
3. હોસ્ટ માઉન્ટ મોડ માટે: `CLI_EXTRA_PATHS` સેટ કરો અને હોસ્ટ bin ડિરેક્ટરીને ફક્ત વાંચવા માટે માઉન્ટ કરો
4. જો `installed=true` અને `runnable=false` હોય: બાઇનરી મળી હતી, પરંતુ હેલ્થચેક નિષ્ફળ ગયું

### ઝડપી રનટાઇમ માન્યતા તપાસ

```bash
curl -s http://localhost:20128/api/cli-tools/codex-settings | jq '{installed,runnable,commandPath,runtimeMode,reason}'
curl -s http://localhost:20128/api/cli-tools/claude-settings | jq '{installed,runnable,commandPath,runtimeMode,reason}'
curl -s http://localhost:20128/api/cli-tools/openclaw-settings | jq '{installed,runnable,commandPath,runtimeMode,reason}'
```

## ડિબગિંગ

### લૉગ ફાઇલો સક્ષમ કરો

તમારી `.env` ફાઇલમાં `APP_LOG_TO_FILE=true` સેટ કરો. એપ્લિકેશન લૉગ `logs/` હેઠળ લખાય છે.
જ્યારે સેટિંગ્સમાં કૉલ લૉગ પાઇપલાઇન સક્ષમ હોય, ત્યારે રિક્વેસ્ટ આર્ટિફૅક્ટ્સ `${DATA_DIR}/call_logs/` હેઠળ સંગ્રહિત થાય છે.
જ્યારે પાઇપલાઇન કૅપ્ચર સક્ષમ હોય, ત્યારે સ્ટ્રીમ ચંક પેલોડ્સને બાકાત રાખવા માટે `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` સેટ કરો, અથવા KBમાં આર્ટિફૅક્ટ મર્યાદા બદલવા માટે `CALL_LOG_PIPELINE_MAX_SIZE_KB` સમાયોજિત કરો.

### પ્રોવાઇડરની સ્થિતિ તપાસો

```bash
# હેલ્થ ડૅશબોર્ડ
http://localhost:20128/dashboard/health

# API હેલ્થ ચેક
curl http://localhost:20128/api/monitoring/health
```

### રનટાઇમ સ્ટોરેજ

- મુખ્ય સ્થિતિ: `${DATA_DIR}/storage.sqlite` (પ્રોવાઇડર્સ, કોમ્બોઝ, ઉપનામો, કીઓ, સેટિંગ્સ)
- વપરાશ: `storage.sqlite`માં SQLite ટેબલો (`usage_history`, `call_logs`, `proxy_logs`) + વૈકલ્પિક `${DATA_DIR}/call_logs/`
- એપ્લિકેશન લૉગ્સ: `<repo>/logs/...` (જ્યારે `APP_LOG_TO_FILE=true` હોય)
- કૉલ લૉગ આર્ટિફૅક્ટ્સ: કૉલ લૉગ પાઇપલાઇન સક્ષમ હોય ત્યારે `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

રિક્વેસ્ટ લૉગ્સ પેજની **ઇતિહાસ સાફ કરો** ક્રિયા `call_logs`, લેગસી
`request_detail_logs`, અને સ્થાનિક `${DATA_DIR}/call_logs/` આર્ટિફૅક્ટ ડિરેક્ટરી સાફ કરે છે.

## સર્કિટ બ્રેકર સમસ્યાઓ

### પ્રદાતા OPEN સ્થિતિમાં અટવાયેલો છે

જ્યારે પ્રદાતાનો સર્કિટ બ્રેકર OPEN હોય છે, ત્યારે કૂલડાઉન પૂર્ણ ન થાય ત્યાં સુધી વિનંતીઓ અવરોધિત રહે છે.

**ઉકેલ:**

1. **ડૅશબોર્ડ → સેટિંગ્સ → રેઝિલિયન્સ** પર જાઓ
2. અસરગ્રસ્ત પ્રદાતા માટેનું સર્કિટ બ્રેકર કાર્ડ તપાસો
3. બધા બ્રેકર્સ સાફ કરવા માટે **બધા રીસેટ કરો** પર ક્લિક કરો અથવા કૂલડાઉન પૂર્ણ થવાની રાહ જુઓ
4. રીસેટ કરતાં પહેલાં ખાતરી કરો કે પ્રદાતા ખરેખર ઉપલબ્ધ છે

### પ્રદાતા વારંવાર સર્કિટ બ્રેકરને ટ્રિપ કરે છે

જો કોઈ પ્રદાતા વારંવાર OPEN સ્થિતિમાં જાય:

1. નિષ્ફળતાની પેટર્ન માટે **ડૅશબોર્ડ → હેલ્થ → પ્રોવાઇડર હેલ્થ** તપાસો
2. **સેટિંગ્સ → રેઝિલિયન્સ → પ્રોવાઇડર પ્રોફાઇલ્સ** પર જઈને નિષ્ફળતાની મર્યાદા વધારો
3. તપાસો કે પ્રદાતાએ API મર્યાદાઓ બદલી છે કે ફરીથી પ્રમાણીકરણ જરૂરી છે
4. લેટન્સી ટેલિમેટ્રીની સમીક્ષા કરો — વધુ લેટન્સીને કારણે ટાઇમઆઉટ-આધારિત નિષ્ફળતાઓ થઈ શકે છે

## ઑડિયો ટ્રાન્સક્રિપ્શન સમસ્યાઓ

### "અસમર્થિત મોડેલ" ભૂલ

- એવા મોડેલ id નો ઉપયોગ કરો જેનો પ્રથમ સેગમેન્ટ એવા પ્રદાતાનો હોય જેના માટે તમારી પાસે ઓળખપત્રો છે (`openai/whisper-1`, `openrouter/deepgram/nova-3`). માત્ર `deepgram/nova-3` માટે મૂળ Deepgram કી જરૂરી છે.
- **ડૅશબોર્ડ → પ્રોવાઇડર્સ**માં પ્રદાતા જોડાયેલો છે તેની ખાતરી કરો

### ટ્રાન્સક્રિપ્શન ખાલી મળે છે અથવા નિષ્ફળ જાય છે

- સમર્થિત ઑડિયો ફૉર્મેટ તપાસો: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ખાતરી કરો કે ફાઇલનું કદ પ્રદાતાની મર્યાદામાં છે (સામાન્ય રીતે < 25MB)
- પ્રદાતા કાર્ડમાં પ્રદાતાની API કીની માન્યતા તપાસો

## ટ્રાન્સલેટર ડિબગિંગ

ફૉર્મેટ અનુવાદની સમસ્યાઓ ડિબગ કરવા માટે **ડૅશબોર્ડ → ટ્રાન્સલેટર**નો ઉપયોગ કરો:

| મોડ              | ક્યારે ઉપયોગ કરવો                                                                                              |
| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| **પ્લેગ્રાઉન્ડ** | ઇનપુટ/આઉટપુટ ફૉર્મેટની બાજુ-બાજુમાં સરખામણી કરો — અનુવાદ કેવી રીતે થાય છે તે જોવા માટે નિષ્ફળ વિનંતી પેસ્ટ કરો |
| **ચૅટ ટેસ્ટર**   | લાઇવ સંદેશા મોકલો અને હેડર્સ સહિત સંપૂર્ણ વિનંતી/પ્રતિસાદ પેલોડનું નિરીક્ષણ કરો                                |
| **ટેસ્ટ બેન્ચ**  | કયા અનુવાદો તૂટેલા છે તે શોધવા માટે ફૉર્મેટ સંયોજનોમાં બૅચ પરીક્ષણો ચલાવો                                      |
| **લાઇવ મોનિટર**  | વચ્ચે-વચ્ચે થતી અનુવાદ સમસ્યાઓ પકડવા માટે રિયલ-ટાઇમ વિનંતી પ્રવાહ જુઓ                                          |

### ફૉર્મેટ સંબંધિત સામાન્ય સમસ્યાઓ

- **થિંકિંગ ટૅગ્સ દેખાતા નથી** — લક્ષ્ય પ્રદાતા થિંકિંગને સમર્થન આપે છે કે નહીં અને થિંકિંગ બજેટ સેટિંગ તપાસો
- **ટૂલ કૉલ્સ ગાયબ થઈ રહ્યા છે** — કેટલાક ફૉર્મેટ અનુવાદો અસમર્થિત ફીલ્ડ્સને દૂર કરી શકે છે; પ્લેગ્રાઉન્ડ મોડમાં ચકાસો
- **સિસ્ટમ પ્રોમ્પ્ટ ગાયબ છે** — Claude અને Gemini સિસ્ટમ પ્રોમ્પ્ટ્સને અલગ રીતે હેન્ડલ કરે છે; અનુવાદનું આઉટપુટ તપાસો
- **SDK ઑબ્જેક્ટને બદલે રૉ સ્ટ્રિંગ પરત કરે છે** — v1.xમાં ઉકેલાયું; પ્રતિસાદ સેનિટાઇઝર બિન-પ્રમાણભૂત ફીલ્ડ્સ (`x_groq`, `usage_breakdown`, વગેરે) દૂર કરે છે, જે OpenAI SDK Pydantic વૅલિડેશન નિષ્ફળતાઓનું કારણ બને છે. જો તમને હજુ પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને સમસ્યા નોંધાવો.
- **GLM/ERNIE `system` ભૂમિકાને નકારે છે** — v1.xમાં ઉકેલાયું; અસંગત મોડેલ્સ માટે રોલ નોર્મલાઇઝર સિસ્ટમ સંદેશાઓને આપમેળે યુઝર સંદેશાઓમાં મર્જ કરે છે. જો તમને હજુ પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને સમસ્યા નોંધાવો.
- **`developer` ભૂમિકા ઓળખાતી નથી** — v1.xમાં ઉકેલાયું; non-OpenAI પ્રદાતાઓ માટે તેને આપમેળે `system`માં રૂપાંતરિત કરવામાં આવે છે. જો તમને હજુ પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને સમસ્યા નોંધાવો.
- **`json_schema` Gemini સાથે કામ કરતું નથી** — v1.xમાં ઉકેલાયું; હવે `response_format`ને Geminiના `responseMimeType` + `responseSchema`માં રૂપાંતરિત કરવામાં આવે છે. જો તમને હજુ પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને સમસ્યા નોંધાવો.

## સ્થિતિસ્થાપકતા સેટિંગ્સ

### સ્વચાલિત દર-મર્યાદા સક્રિય થતી નથી

- સ્વચાલિત દર-મર્યાદા ફક્ત API કી પ્રદાતાઓને લાગુ પડે છે (OAuth/સબ્સ્ક્રિપ્શનને નહીં)
- ખાતરી કરો કે **સેટિંગ્સ → સ્થિતિસ્થાપકતા → પ્રદાતા પ્રોફાઇલ્સ**માં સ્વચાલિત દર-મર્યાદા સક્ષમ છે
- પ્રદાતા `429` સ્થિતિ કોડ અથવા `Retry-After` હેડર્સ પરત કરે છે કે નહીં તે તપાસો

### ઘાતાંકીય બૅકઑફનું ટ્યુનિંગ

પ્રદાતા પ્રોફાઇલ્સ આ સેટિંગ્સને સમર્થન આપે છે:

- **મૂળ વિલંબ** — પ્રથમ નિષ્ફળતા પછીનો પ્રારંભિક પ્રતીક્ષા સમય (ડિફૉલ્ટ: 1s)
- **મહત્તમ વિલંબ** — પ્રતીક્ષા સમયની મહત્તમ મર્યાદા (ડિફૉલ્ટ: 30s)
- **ગુણક** — દરેક સળંગ નિષ્ફળતા દીઠ વિલંબ કેટલો વધારવો (ડિફૉલ્ટ: 2x)

### થન્ડરિંગ હર્ડ વિરોધી સુરક્ષા

જ્યારે અનેક સમકાલીન વિનંતીઓ દર-મર્યાદિત પ્રદાતા સુધી પહોંચે છે, ત્યારે OmniRoute વિનંતીઓને ક્રમબદ્ધ કરવા અને શ્રેણીબદ્ધ નિષ્ફળતાઓ અટકાવવા માટે મ્યુટેક્સ + સ્વચાલિત દર-મર્યાદાનો ઉપયોગ કરે છે. API કી પ્રદાતાઓ માટે આ સ્વચાલિત છે.

### ચેટ વિનંતીઓ 503 / chat_admission_busy સાથે નિષ્ફળ થાય છે

**લક્ષણો:**

- ચેટ કમ્પ્લીશન્સ એન્ડપોઇન્ટ ફરી પ્રયાસ કરી શકાય એવો `503` પ્રતિસાદ પરત કરે છે, જેનો ભૂલ કોડ
  `chat_admission_busy` છે.
- પ્રતિસાદમાં `Retry-After` સામેલ હોય છે. #12135 પછીથી તેનું મૂલ્ય નિરીક્ષિત
  વ્યસ્તતા પરથી મેળવવામાં આવે છે — વિનંતીએ પહેલેથી પ્રતીક્ષા કરેલી `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` વિન્ડો
  અને વર્તમાન હેવીવેઇટ લીઝ જેટલા સમયથી રાખવામાં આવી છે તેમાંથી મોટું મૂલ્ય — જેને પૂર્ણ
  સેકન્ડ સુધી ઉપરની તરફ રાઉન્ડ કરીને 60 પર મર્યાદિત કરવામાં આવે છે. નિષ્ક્રિય ગેટ પર તે ઐતિહાસિક લઘુત્તમ મર્યાદાઓ જાળવે છે:
  બાઇટ-આધારિત પાથ પર 2 સેકન્ડ અને સ્ટ્રક્ચર-આધારિત પાથ પર 1 સેકન્ડ (જેમાં
  `reason: "structure_limit"` પણ સામેલ છે).
- અન્ય હેવીવેઇટ ચેટ અથવા લાંબા સમયથી ચાલી રહેલો સ્ટ્રીમિંગ પ્રતિસાદ હજી
  પ્રક્રિયામાં હોય ત્યારે આવું બની શકે છે.

બાઇટ-આધારિત પ્રતિસાદ બોડી આ પ્રમાણે છે:

```json
{
  "error": {
    "message": "ચેટ પ્રવેશ ક્ષમતા અસ્થાયી રૂપે ઉપલબ્ધ નથી. ટૂંક સમયમાં ફરી પ્રયાસ કરો.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

સ્ટ્રક્ચર-આધારિત પ્રતિસાદ સમાન પ્રકાર અને કોડનો ઉપયોગ કરે છે, જેમાં સંદેશ
`આ સ્ટ્રક્ચરલ રીતે ભારે વિનંતી માટે સ્થાનિક ચેટ પ્રવેશ ક્ષમતા વ્યસ્ત છે; અપસ્ટ્રીમ પ્રદાતા રાઉટિંગનો પ્રયાસ કરવામાં આવ્યો નથી. ટૂંક સમયમાં ફરી પ્રયાસ કરો.`
અને `reason: "structure_limit"` હોય છે.
ડિફૉલ્ટ થ્રેશોલ્ડ પર, વિનંતીમાં ઓછામાં ઓછા `200` સંદેશા,
ઓછામાં ઓછા `64` ટૂલ્સ અથવા ઓછામાં ઓછા `32,000` અંદાજિત ટોકન્સ હોય, અથવા મર્યાદિત સ્ટ્રક્ચર અંદાજ
`10,000` મુલાકાત લેવાયેલા નોડ્સ અથવા `12` ઊંડાઈની મર્યાદા વટાવે, ત્યારે વિનંતી સ્ટ્રક્ચરલ રીતે ભારે ગણાય છે.

**કારણ:** આ OmniRouteની અંદર ઇરાદાપૂર્વકનું લોડ શેડિંગ છે, અપસ્ટ્રીમ-પ્રદાતાની નિષ્ફળતા નહીં.
દરેક પ્રોસેસ મોટા વિનંતી બોડીને જાળવી રાખવા અને પાર્સ કરતાં પહેલાં મર્યાદિત હેવીવેઇટ ક્ષમતા અનામત રાખવા માટે
પ્રોસેસ-લોકલ ગાર્ડનો ઉપયોગ કરે છે. SSE
પ્રતિસાદના સમગ્ર આયુષ્ય દરમિયાન હેવીવેઇટ લીઝ જાળવી રાખવામાં આવે છે.

**#503-ફૅનઆઉટ:** આ સુધારા પહેલાં, ગાર્ડ હોસ્ટ મેમરીને ધ્યાનમાં લીધા વગર સમકાલીનતાને નિશ્ચિત વિનંતી COUNT
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ડિફૉલ્ટ `1`) સુધી મર્યાદિત કરતો હતો, તેથી કોડિંગ-એજન્ટ
ફૅન-આઉટ (અનેક સબએજન્ટ્સ/CLIs, નિયમિત રીતે > 256 KB બોડીઝ) અસરકારક રીતે
~1 સમકાલીનતા સુધી ઘટી જતું અને સંપૂર્ણપણે સામાન્ય લોડ હેઠળ 503 આપતું હતું. હવે ગાર્ડ સ્વયં-ટ્યુન થાય છે: તે
પ્રોસેસની વાસ્તવિક મેમરી મર્યાદા પરથી માપ નક્કી કરાયેલા સ્વતઃ-પ્રાપ્ત ઇનજેસ્ટ BYTE બજેટ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) દ્વારા
નિયંત્રિત થાય છે, અને તે જીવંત સંસાધન-દબાણ સંકેત પણ તપાસે છે — તેથી તે
માત્ર ત્યારે જ લોડ ઘટાડે છે જ્યારે હોસ્ટ ખરેખર મેમરી દબાણ હેઠળ હોય, ફક્ત એકસાથે એકથી વધુ
ભારે વિનંતીઓ આવી હોવાને કારણે નહીં. જૂની કાઉન્ટ મર્યાદા (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)નું
હજી પણ પાલન થાય છે, પરંતુ ફક્ત ત્યારે જ્યારે તમે તેને સ્પષ્ટપણે સેટ કરો.

જ્યારે ક્ષમતા વ્યસ્ત હોય, ત્યારે હેવીવેઇટ વિનંતી ફરી પ્રયાસ કરી શકાય એવો `503` પ્રતિસાદ આપતાં પહેલાં
સ્લોટ ખાલી થવા માટે `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` સુધી (ડિફૉલ્ટ `RATE_LIMIT_MAX_WAIT_MS`; `0` પ્રતીક્ષા અક્ષમ કરે છે) પ્રતીક્ષા કરે છે.
આ મર્યાદિત પ્રતીક્ષા એટલા માટે છે કે ભારે ઉપ-વિનંતીઓને સમકાલીન રીતે ફૅન-આઉટ કરતા એજન્ટ-શૈલીના ક્લાયન્ટ્સ
(OpenCode, Claude Code, Cursor) તાત્કાલિક અસ્વીકારો પર તેમનું આખું પુનઃપ્રયાસ બજેટ વાપરીને કાર્યની વચ્ચે નિષ્ફળ થવાને બદલે
આકસ્મિક વધારાને ક્રમબદ્ધ કરે.
વર્તમાન હેવીવેઇટ લીઝ વ્યસ્તતા, નિર્ધારિત બાઇટ બજેટ અને જીવંત દબાણની ગંભીરતા
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) પર દર્શાવવામાં આવે છે — કોઈપણ env var બદલતાં પહેલાં આ તપાસો.
સેટિંગ્સ → સ્થિતિસ્થાપકતા → વિનંતી કતાર → સમકાલીન વિનંતીઓ આને નિયંત્રિત કરતું નથી; તે સેટિંગ
એક અલગ પ્રદાતા વિનંતી-કતાર વ્યવસ્થાને સંચાલિત કરે છે.

   ફરીથી મોકલવાને બદલે `Retry-After`નું પાલન કરવું અને બૅકઑફનો ઉપયોગ કરવો જોઈએ.
2. કંઈપણ ટ્યુન કરતાં પહેલાં `/api/monitoring/health` → `chatAdmission` તપાસો. `countCapEnabled:
false` અને ઉદાર `maxInflightBytes`નો અર્થ છે કે સ્વતઃ-પ્રાપ્ત બજેટ પહેલેથી જ યોગ્ય રીતે
   કાર્ય કરી રહ્યું છે; `high`/`critical`નું `pressureSeverity` દર્શાવે છે કે હોસ્ટમાં ખરેખર મેમરી ઓછી છે —
   તેને પ્રવેશ env var દ્વારા સુધારી શકાતું નથી; તેના માટે વધુ RAM અથવા ઓછો વર્કલોડ જરૂરી છે.
3. ફક્ત ત્યારે જ, જ્યારે `/api/monitoring/health` દર્શાવે કે સ્વતઃ-પ્રાપ્ત બજેટ તમારા હોસ્ટ માટે ખરેખર
   ખૂબ નાનું છે (દુર્લભ — તે કન્ટેનરથી બેર-મેટલ સુધી પહેલેથી જ સ્કેલ થાય છે), લેગસી વિનંતી-કાઉન્ટ મર્યાદા પર પાછા જવાને બદલે
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` વડે તેને સીધું ઓવરરાઇડ કરો.

અધિકૃત પ્રવેશ સેટિંગ્સ માટે [એન્વાયર્નમેન્ટ-વેરિએબલ સંદર્ભ](../reference/ENVIRONMENT.md#4-security--authentication)
જુઓ.

## વૈકલ્પિક RAG / LLM નિષ્ફળતા વર્ગીકરણ (16 સમસ્યાઓ)

કેટલાક OmniRoute વપરાશકર્તાઓ ગેટવેને RAG અથવા એજન્ટ સ્ટૅક્સની આગળ મૂકે છે. આવા સેટઅપ્સમાં એક વિચિત્ર પેટર્ન સામાન્ય રીતે જોવા મળે છે: OmniRoute સ્વસ્થ દેખાય છે (પ્રદાતાઓ કાર્યરત છે, રૂટિંગ પ્રોફાઇલ્સ યોગ્ય છે, કોઈ રેટ લિમિટ ચેતવણીઓ નથી), પરંતુ અંતિમ જવાબ તેમ છતાં ખોટો હોય છે.

વ્યવહારમાં, આ ઘટનાઓ સામાન્ય રીતે ગેટવેમાંથી નહીં, પરંતુ ડાઉનસ્ટ્રીમ RAG પાઇપલાઇનમાંથી ઉદ્ભવે છે.

જો તમે આવી નિષ્ફળતાઓનું વર્ણન કરવા માટે સહિયારી શબ્દાવલી ઇચ્છતા હો, તો તમે WFGY ProblemMap નો ઉપયોગ કરી શકો છો. તે MIT લાઇસન્સ હેઠળનું એક બાહ્ય ટેક્સ્ટ સંસાધન છે, જે વારંવાર જોવા મળતી સોળ RAG / LLM નિષ્ફળતા પેટર્ન્સને વ્યાખ્યાયિત કરે છે. ઉચ્ચ સ્તરે તે આ બાબતોને આવરી લે છે:

- રિટ્રીવલ ડ્રિફ્ટ અને તૂટેલી કોન્ટેક્સ્ટ સીમાઓ
- ખાલી અથવા જૂના ઇન્ડેક્સ અને વેક્ટર સ્ટોર્સ
- એમ્બેડિંગ અને સેમેન્ટિક અર્થ વચ્ચેની અસંગતતા
- પ્રોમ્પ્ટ એસેમ્બલી અને કોન્ટેક્સ્ટ વિન્ડોની સમસ્યાઓ
- તર્કનું પતન અને અતિશય આત્મવિશ્વાસભર્યા જવાબો
- લાંબી ચેઇન અને એજન્ટ સંકલનની નિષ્ફળતાઓ
- મલ્ટિ-એજન્ટ મેમરી અને ભૂમિકામાં ડ્રિફ્ટ
- ડિપ્લોયમેન્ટ અને બુટસ્ટ્રૅપ ક્રમની સમસ્યાઓ

વિચાર સરળ છે:

1. જ્યારે તમે ખરાબ પ્રતિસાદની તપાસ કરો, ત્યારે આ માહિતી કૅપ્ચર કરો:
   - વપરાશકર્તાનું કાર્ય અને વિનંતી
   - OmniRoute માં રૂટ અથવા પ્રદાતા કોમ્બો
   - ડાઉનસ્ટ્રીમમાં ઉપયોગમાં લેવાયેલ કોઈપણ RAG કોન્ટેક્સ્ટ (પ્રાપ્ત કરાયેલા દસ્તાવેજો, ટૂલ કૉલ્સ વગેરે)
2. ઘટનાને એક અથવા બે WFGY ProblemMap નંબરો (`No.1` … `No.16`) સાથે મેપ કરો.
3. OmniRoute લૉગ્સની બાજુમાં તમારા પોતાના ડૅશબોર્ડ, રનબુક અથવા ઇન્સિડન્ટ ટ્રૅકરમાં નંબર સંગ્રહિત કરો.
4. તમારે તમારા RAG સ્ટૅક, રિટ્રીવર અથવા રૂટિંગ વ્યૂહરચનામાં ફેરફાર કરવાની જરૂર છે કે નહીં તે નક્કી કરવા માટે સંબંધિત WFGY પેજનો ઉપયોગ કરો.

સંપૂર્ણ ટેક્સ્ટ અને ચોક્કસ રીતો અહીં ઉપલબ્ધ છે (MIT લાઇસન્સ, માત્ર ટેક્સ્ટ):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

જો તમે OmniRoute પાછળ RAG અથવા એજન્ટ પાઇપલાઇન્સ ચલાવતા ન હો, તો તમે આ વિભાગને અવગણી શકો છો.

## v3.8.0 ની જાણીતી સમસ્યાઓ

v3.8.0 રિલીઝને લગતી વિશિષ્ટ સમસ્યાઓ અને તેમના વર્તમાન ઉપાયો. જો પછીના કોઈ પૅચમાં સુધારો આવે, તો એન્ટ્રી અપડેટ કરવામાં આવશે અથવા દૂર કરવામાં આવશે.

### Devin CLI પ્રમાણીકરણ નિષ્ફળતાઓ

**લક્ષણો:**

- Devin-આધારિત ટૂલ્સ ચલાવતી વખતે "Devin CLI મળ્યું નથી" અથવા "પ્રમાણીકરણ નિષ્ફળ થયું"
- CLI રનટાઇમ તપાસ `installed=false` દર્શાવે છે

**કારણો:**

- `CLI_DEVIN_BIN` અસ્તિત્વમાં ન હોય તેવા પાથ તરફ નિર્દેશ કરે છે
- હોસ્ટ પર Devin CLI ઇન્સ્ટૉલ કરેલું નથી

**ઉકેલ:**

1. તમારા પ્લેટફોર્મ માટે Devin CLI ઇન્સ્ટૉલ કરો
2. `.env` માં `CLI_DEVIN_BIN=/usr/local/bin/devin` (અથવા વાસ્તવિક પાથ) સેટ કરો
3. OmniRoute પુનઃપ્રારંભ કરો અને **ડૅશબોર્ડ → CLI ટૂલ્સ** માંથી ફરી પરીક્ષણ કરો

### મોડલ કૂલડાઉન અટવાયેલું છે (મૅન્યુઅલ રીસેટ)

**લક્ષણો:**

- સમાપ્તિ સમય પસાર થઈ ગયા પછી પણ મોડલ કૂલડાઉનમાં સૂચિબદ્ધ રહે છે
- ટાઇમસ્ટૅમ્પ ભૂતકાળનો હોવા છતાં કોમ્બો રૂટિંગમાં વિનંતીઓ હજુ પણ મોડલને છોડી દે છે

**મૅન્યુઅલ રીસેટ:**

- **ડૅશબોર્ડ:** **સેટિંગ્સ → મોડલ કૂલડાઉન્સ** → અસરગ્રસ્ત કાર્ડ પર **ફરી સક્ષમ કરો** ક્લિક કરો
- **API:** મેનેજમેન્ટ પ્રમાણીકરણ હેડર્સ સાથે `DELETE /api/resilience/model-cooldowns`

### Command Code પ્રદાતા કનેક્શન 403 સાથે નિષ્ફળ જાય છે

**લક્ષણો:**

- Command Code પ્રદાતા કનેક્શનનું પરીક્ષણ કરતી વખતે 403
- નવું ઉમેર્યા પછી પ્રદાતા કાર્ડ "અધિકૃત નથી" દર્શાવે છે

**કારણ:** OAuth ફ્લો પૂર્ણ થયો નહોતો (કૉલબૅક પ્રાપ્ત થયો નહોતો અથવા ટોકન સાચવવામાં આવ્યું નહોતું).

**ઉકેલ:**

- OAuth ફ્લો ફરી શરૂ કરવા માટે CLI માંથી `omniroute providers` ચલાવો, અથવા
- **ડૅશબોર્ડ → પ્રદાતાઓ → Command Code → ફરી કનેક્ટ કરો** માંથી OAuth ફરી ચલાવો

### ModelScope અત્યંત આક્રમક 429 કૂલડાઉન્સ પરત કરે છે

**લક્ષણો:**

- વિનંતીઓના નાના બર્સ્ટ પછી ModelScope પર ખૂબ ટૂંકા અથવા તાત્કાલિક કૂલડાઉન્સ
- કોમ્બો રૂટિંગ અપેક્ષા કરતાં વહેલું ModelScope ને છોડી દે છે

**કારણ:** ModelScope પ્રદાતા-વિશિષ્ટ `Retry-After` હેડર્સ મોકલે છે. v3.8.0 માં આ હેડર્સ માટે સમર્પિત હૅન્ડલિંગ સામેલ છે, તેથી જૂના વર્ઝન્સ તેમને સામાન્ય રેટ-લિમિટ સંકેતો તરીકે ખોટી રીતે સમજે છે.

**ઉકેલ:**

- ખાતરી કરો કે તમે v3.8.0 અથવા પછીના વર્ઝન પર છો
- **સેટિંગ્સ → રેઝિલિયન્સ** હેઠળ `useUpstream429BreakerHints` ટૉગલ સક્ષમ છે તે ચકાસો

### પ્રોડક્શનમાં OMNIROUTE_WS_BRIDGE_SECRET ગાયબ છે

**લક્ષણો:**

- રિમોટ પ્રોડક્શન હોસ્ટ પર ચલાવતી વખતે દરેક Codex/Responses WebSocket બ્રિજ વિનંતી પર 401
- કનેક્ટ થયા પછી તરત જ WebSocket બ્રિજ હૅન્ડશેક બંધ થઈ જાય છે

**કારણ:** પ્રોડક્શન એન્વાયર્નમેન્ટમાંથી `OMNIROUTE_WS_BRIDGE_SECRET` એન્વાયરમેન્ટ વેરિએબલ ગાયબ છે.

**ઉકેલ:**

1. રૅન્ડમ સિક્રેટ જનરેટ કરો: `openssl rand -hex 32`
2. પ્રોડક્શન સર્વર એન્વાયર્નમેન્ટમાં (અને બ્રિજ સાથે સંચાર કરતા કોઈપણ ક્લાયન્ટમાં) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` સેટ કરો
3. OmniRoute પુનઃપ્રારંભ કરો

### Responses API: બૅકગ્રાઉન્ડ મોડને સિંક્રોનસમાં ડિગ્રેડ કરવામાં આવ્યો છે

**લક્ષણો:**

- લૉગ થયેલી ચેતવણી: `background mode degraded to synchronous`
- `background: true` વિનંતી બૅકગ્રાઉન્ડ જૉબ હૅન્ડલને બદલે સામાન્ય સિંક્રોનસ પ્રતિસાદ પરત કરે છે

**કારણ:** v3.8.0 માં Responses API પર `background: true` ને ઇરાદાપૂર્વક સિંક્રોનસ એક્ઝિક્યુશનમાં ડિગ્રેડ કરવામાં આવે છે અને સાથે ચેતવણી પણ આપવામાં આવે છે. સંપૂર્ણ અસિંક્રોનસ બૅકગ્રાઉન્ડ એક્ઝિક્યુશન ભવિષ્યમાં ઉપલબ્ધ કરાવવાનું છે.

**ઉકેલ:**

- `background` વિના કૉલ કરવા માટે ક્લાયન્ટને સમાયોજિત કરો, અથવા
- સંપૂર્ણ અસિંક્રોનસ બૅકગ્રાઉન્ડ મોડ ધરાવતી પછીની રિલીઝની રાહ જુઓ (ચેન્જલૉગ પર નજર રાખો)

આ સામાન્ય રીતે Windows (એન્ટિવાયરસ, ફાઇલસિસ્ટમ વોચર્સ) અથવા ભારે સ્ટાર્ટઅપ
વર્કલોડ ધરાવતા કન્ટેનર્સમાં થાય છે.

**ઉકેલ — બજેટ વધારો:**

```bash
# env var દ્વારા (સ્ટાર્ટ્સ વચ્ચે જળવાઈ રહે છે):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 મિનિટ
omniroute serve

# CLI ફ્લૅગ દ્વારા (માત્ર એક વખત):
omniroute serve --ready-timeout 180000
```

ડિફૉલ્ટ 60 000 ms (60 s) છે. ચેતવણી માત્ર માહિતી માટે છે; સર્વર
બૅકગ્રાઉન્ડમાં સ્ટાર્ટ થવાનું ચાલુ રાખે છે અને બૂટ પૂર્ણ થયા પછી ઍક્સેસ કરી શકાશે.

`OMNIROUTE_READY_TIMEOUT_MS` વિશેની સંપૂર્ણ વિગતો માટે
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) જુઓ.
