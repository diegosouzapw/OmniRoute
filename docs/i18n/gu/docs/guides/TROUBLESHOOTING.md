## ઝડપી સંદર્ભ

**OmniRoute માટે નવા છો?** અહીંથી શરૂ કરો — આ 90% સમસ્યાઓ ઉકેલે છે:

| મને આ દેખાય છે          | તેનો અર્થ શું છે                               | શું કરવું                                                                                                     |
| ----------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| "Can't connect"         | OmniRoute ચાલી રહ્યું નથી                      | `omniroute` ચલાવો અથવા `docker restart omniroute` ચલાવો                                                       |
| "Invalid API key"       | તમારી કી ખોટી છે અથવા તેની મુદત પૂરી થઈ ગઈ છે  | પ્રદાતાની વેબસાઇટ પરથી કી ફરીથી કૉપિ કરો                                                                      |
| "Rate limit exceeded"   | તમે ખૂબ વધારે વિનંતીઓ મોકલી રહ્યા છો           | 1 મિનિટ રાહ જુઓ અથવા આપમેળે ફૉલબૅક માટે `model: "auto"` વાપરો                                                 |
| "Quota exceeded"        | તમે તમારો મફત/ચૂકવેલ ક્વોટા પૂરો વાપરી લીધો છે | વધુ પ્રદાતાઓ જોડો અથવા મફત પ્રદાતાઓ (Kiro, Pollinations) વાપરો                                                |
| "Slow responses"        | પ્રદાતા વ્યસ્ત છે અથવા ખૂબ દૂર છે              | `model: "auto/fast"` વાપરો અથવા વધુ ઝડપી પ્રદાતા (Groq, Cerebras) જોડો                                        |
| "Wrong provider used"   | `auto` એ અલગ પ્રદાતા પસંદ કર્યો                | આ સામાન્ય છે! `auto` શ્રેષ્ઠ પ્રદાતા પસંદ કરે છે. `model: "openai/gpt-4o"` વડે કોઈ ચોક્કસ પ્રદાતા ફરજિયાત કરો |
| "502 Bad Gateway"       | પ્રદાતા બંધ છે                                 | રાહ જોઈને ફરી પ્રયાસ કરો અથવા પ્રદાતા બદલવા માટે `model: "auto"` વાપરો                                        |
| "401 Unauthorized"      | તમારા ઓળખપત્રો ખોટા છે                         | તમારી API કી તપાસો અથવા OAuth વડે ફરીથી પ્રમાણીકરણ કરો                                                        |
| "429 Too Many Requests" | દર મર્યાદા લાગુ થઈ છે                          | 1 મિનિટ રાહ જુઓ અથવા વધુ પ્રદાતાઓ જોડો                                                                        |

**હજુ પણ અટવાયા છો?** નીચે આપેલું [વિગતવાર સમસ્યાનિવારણ](#detailed-troubleshooting) જુઓ અથવા [Discord](https://discord.gg/U47eFqAXCn) પર પૂછો.

## વિગતવાર સમસ્યાનિવારણ

---

### મફત પ્રદાતાઓ પર દર મર્યાદા (429 / 400 / 401)

**લક્ષણ**: મફત/પ્રમાણીકરણ-વિહોણા પ્રદાતાઓ (opencode, auggie વગેરે) સાથે `model: "auto"` વાપરતી વખતે, તમને જવાબોના બદલે વચ્ચે-વચ્ચે `HTTP 429`, `400` અથવા `401` મળે છે. થોડી ક્ષણો પછી એ જ પ્રોમ્પ્ટ સાથે ફરી પ્રયાસ કરતાં વિનંતીઓ સફળ થાય છે, પરંતુ ઑટોમેશન (cron જોબ્સ, એજન્ટ્સ, સ્ક્રિપ્ટ્સ) પહેલી નિષ્ફળતાએ જ બંધ થઈ જાય છે.

**મૂળ કારણ**: ત્રણ સ્વતંત્ર નિષ્ફળતા સ્થિતિઓ એકસાથે ભેગી થાય છે:

1. **પ્રદાતાની દર મર્યાદા (`429`)**: મફત સ્તરો દરેક સમય-વિન્ડો માટે ક્વોટા લાગુ કરી શકે છે. સમાંતર કૉલ્સનો અચાનક ધસારો તેને પૂરો કરી નાખે છે, તેથી વિન્ડો રીસેટ થાય ત્યાં સુધી આગામી વિનંતી નકારવામાં આવે છે.
2. **પાસથ્રૂમાં ખામીયુક્ત મોડલ (`400`/`401`)**: `auto/*` પૂલ્સમાં `opencode`નાં એવા પાસથ્રૂ મોડલ્સ સામેલ હોઈ શકે છે, જે કેટલોગમાં નોંધાયેલા હોય પરંતુ તેમની પાસે સક્રિય ઓળખપત્રો ન હોય (દા.ત. `oc/north-mini-code-free` → `401`). ઑટો-રાઉટર કોઈ એક અજમાવે છે, નિષ્ફળ જાય છે અને ફૉલબૅક શરૂ થાય તે પહેલાં જ ભૂલ આગળ પ્રસારિત થઈ જાય છે.
3. **સમકાલીનતાને કારણે વધતી અસર (લોડ હેઠળ `429`)**: જ્યારે અનેક એજન્ટ/cron સેશન્સ એકસાથે `auto`ને હિટ કરે છે, ત્યારે કુલ વિનંતી દર મફત પ્રદાતાઓ સહન કરી શકે તેના કરતાં વધી જાય છે, તેથી માન્ય કૉલ્સને પણ દુરુપયોગી તરીકે ચિહ્નિત કરવામાં આવે છે.

**ચકાસાયેલો ઉકેલ (સમુદાય દ્વારા અહેવાલિત, 2026-08-10)**: ત્રણ પર્યાવરણ ચલોને એવી રીતે ગોઠવો કે રોટેશન, સમકાલીનતા અને ફૉલબૅક મફત સ્તરની અસ્થિરતાને કારણે બંધ થઈ જવાને બદલે તેને સંભાળી લે:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 પર અન્ય મોડલ/પ્રદાતા પર જાઓ (ખામીયુક્ત પાસથ્રૂ મોડલ્સને અવગણે છે)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ભારે વિનંતીઓ માટે સ્પષ્ટ પ્રવેશ મર્યાદા (મૂળભૂત રીતે સેટ નથી: વિનંતી-સંખ્યાની કોઈ મર્યાદા નથી, નીચેની નોંધ જુઓ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # તરત ફરી પ્રયાસ કરી શકાય તેવી 503 આપવાને બદલે ભારે ક્ષમતા માટે વધુ લાંબી, મર્યાદિત રાહ
```

આને OmniRoute પ્રોસેસના પર્યાવરણમાં સેટ કરો (ડિમન માટે, દા.ત. LaunchAgent plist અથવા `systemctl edit` દ્વારા), પછી OmniRoute ફરી શરૂ કરો. રોટેશન ફ્લૅગ એકમાત્ર સૌથી વધુ અસરકારક ઉપાય છે: તે કઠોર નિષ્ફળતાને પૂલમાં રહેલા સ્વસ્થ પ્રદાતા સામેના પારદર્શક પુનઃપ્રયાસમાં ફેરવે છે.

**નોંધ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` એકસાથે કેટલી ભારે — લાંબા-કૉન્ટેક્સ્ટવાળી — વિનંતીઓ ચાલે છે તે મર્યાદિત કરે છે; આ મર્યાદા પ્રવેશ દ્વાર છે, પ્રદાતાની દર મર્યાદા નથી. **#503-ફૅનઆઉટ અપડેટ:** આ ચલ હવે મૂળભૂત રીતે સેટ થતો નથી (હવે તે ઉપર બતાવ્યા મુજબ સ્પષ્ટ રીતે કૉન્ફિગર કરવામાં આવે ત્યારે જ લાગુ પડે છે) — તેના બદલે ભારે વિનંતીઓનો પ્રવેશ આપમેળે નિર્ધારિત બાઇટ બજેટ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) દ્વારા નિયંત્રિત થાય છે, જે હોસ્ટની વાસ્તવિક મેમરી મર્યાદા અનુસાર પોતે સ્કેલ થાય છે; તેથી નવા ડિપ્લોયમેન્ટમાં આ ચલ બિલકુલ સેટ કર્યા વિના પણ ઘણી ઓછી `503 chat_admission_busy` અસ્વીકૃતિઓ દેખાવી જોઈએ; તેને અહીં સ્પષ્ટ રીતે સેટ કરવું હજી પણ દસ્તાવેજીકરણમાં જણાવ્યા મુજબ જ કાર્ય કરે છે. સ્પષ્ટ બાઇટ-બજેટ ઓવરરાઇડ્સ 8 MiB–2 GiBની મર્યાદામાં બંધાય છે. `413 body_exceeds_budget` અસ્થાયી નથી: તે બાઇટ બજેટ વધારો, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ઘટાડો અથવા પ્રોસેસની મેમરી મર્યાદા વધારો. `inflight_bytes_budget` શેડ અસ્થાયી સંસાધન-સ્પર્ધા છે અને તેના માટે ફરી પ્રયાસ કરી શકાય છે. દરેક પ્રદાતા માટેની દર મર્યાદા (`open-sse/services/rateLimitManager.ts`) અલગથી `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` અને `RATE_LIMIT_AUTO_ENABLE` દ્વારા નિયંત્રિત થાય છે — `.env.example` જુઓ.

**તે કાર્યરત થયું છે કે નહીં તે કેવી રીતે ચકાસવું**: તમારા એજન્ટ/cronને ઝડપથી સતત બે વાર ચલાવો અને ખાતરી કરો કે બંને સફળ થાય છે. ઉકેલ પહેલાં, બીજી વાર ચલાવવાથી સામાન્ય રીતે `429`/`401` મળે છે. ઉકેલ પછી, નિષ્ફળતાઓ (જો કોઈ હોય તો) માટે પારદર્શક રીતે ફરી પ્રયાસ થાય છે અને કૉલ પૂર્ણ થાય છે. તમે `curl /monitoring/health` પણ ચલાવી શકો છો અને પ્રદાતા કનેક્શન્સ પરનું `rateLimitedUntil` ફીલ્ડ તથા અસરગ્રસ્ત પ્રદાતાઓ માટે `circuitBreakers.providerBreakers[].state` જોઈ શકો છો — સ્થિતિ `CLOSED`, `DEGRADED`, `OPEN` અથવા `HALF_OPEN`માંથી કોઈ એક હોય છે (`src/shared/utils/circuitBreaker.ts` જુઓ), અને વારંવાર નિષ્ફળ થતો પ્રદાતા રીસેટ વિન્ડો દ્વારા પ્રોબને પસાર થવા દેવામાં આવે તે પહેલાં `CLOSED → DEGRADED → OPEN`માં બદલાશે (`HALF_OPEN`).

**જો તમને હજી પણ 429 દેખાય**: તે પ્રદાતા માટેના સક્રિય ખાતાનો ખરેખર _quota_ સમાપ્ત થઈ ગયો છે (માત્ર દર-મર્યાદા નહીં). OmniRoute ડેશબોર્ડ → Providers → Accounts માં એ જ પ્રદાતા માટે બીજું ખાતું ઉમેરો અથવા અન્ય મફત પ્રદાતા (દા.ત. `routeway`, `auggie`) સામેલ કરો. રોટેશન માત્ર કામચલાઉ દર-મર્યાદા/400/401 માટે મદદ કરે છે; quota સંપૂર્ણપણે સમાપ્ત થઈ જાય ત્યારે બીજા ઓળખપત્ર અથવા અલગ પ્રદાતાની જરૂર પડે છે.

**જો તમને વિઝન મોડલ્સ (`auto/vision`, `bazaarlink/*`) પર 403 દેખાય**: કનેક્ટ કરેલા ખાતામાં વિઝનનો સમાવેશ કરતી પેઇડ યોજના નથી અથવા API કી પાસે પૂરતી પરવાનગીઓ નથી. પ્રદાતાના ડેશબોર્ડમાં ચકાસો કે કીનો સ્કોપ વિઝન/મલ્ટીમોડલનો સમાવેશ કરે છે અથવા પેઇડ ટિયર ખાતું કનેક્ટ કરીને તેને વિઝન લક્ષ્ય તરીકે રાખો.

## npm install ચેતવણીઓ (ERESOLVE / peer / deprecated)

જ્યારે તમે `npm install -g omniroute` ચલાવો છો, ત્યારે તમને `npm warn ERESOLVE`, peer-dependency સૂચનાઓ અને `deprecated` સંદેશાઓ જેવી ઘણી ચેતવણીઓ જોવા મળી શકે છે. **આ અપેક્ષિત અને હાનિરહિત છે.** જો આઉટપુટમાં `added <N> packages` દેખાય, તો તમારું ઇન્સ્ટોલેશન સફળ થયું છે.

આ ચેતવણીઓ એવા તૃતીય-પક્ષ પૅકેજોમાં જૂની peer-dependency શ્રેણીઓને કારણે આવે છે, જેના પર OmniRouteનું નિયંત્રણ નથી:

1. **`marked-terminal` ને `marked >=1 <16` જોઈએ છે, પરંતુ `marked@18` મળ્યું** — વ્યવહારમાં યોગ્ય રીતે કાર્ય કરે છે; upstream peer શ્રેણી માત્ર જૂની છે.
2. **`deprecated prebuild-install@7.1.3`** — આ એક transitive native-binary fetch helper છે. તેનો ઉપયોગ પિન કરેલ `wreq-js` transport binding ઇન્સ્ટોલ કરવા માટે થતો નથી અને તે web-cookie
   provider transport સેટઅપ નિષ્ફળ ગયું હોવાનું સૂચવતું નથી.

**કોઈ પગલાં લેવાની જરૂર નથી** — upstream પૅકેજોને fork કર્યા વિના આ ચેતવણીઓને સંપૂર્ણપણે બંધ કરી શકાતી નથી.

### Avast/AVG દ્વારા `README.md` ને `MD:HttpRequest-inf[Susp]` તરીકે ક્વોરન્ટાઇન કરવું

**આ એક ખોટો પોઝિટિવ છે. કંઈપણ સંક્રમિત નથી અને કોઈ કાર્યવાહી જરૂરી નથી.**

Avast અને AVG એવી હ્યુરિસ્ટિક ચલાવે છે જે ઘણા HTTP વિનંતી જેવા દેખાતા લિંક્સ ધરાવતી
સાદા-ટેક્સ્ટ/Markdown ફાઇલોને ફ્લેગ કરે છે. OmniRouteનું `README.md` npm પૅકેજની અંદર આવે છે (તે
`package.json` → `files`માં સૂચિબદ્ધ છે), તેથી વૈશ્વિક ઇન્સ્ટોલેશન વખતે તે
`node_modules/omniroute/README.md` પર આવે છે — અને તેમાં ~15 `http://localhost:20128/...`
ઉદાહરણો (MCP HTTP/SSE એન્ડપોઇન્ટ્સ, A2A `.well-known` URL અને `curl` સ્નિપેટ્સ) છે. લિંક્સની આ
ઘનતા હ્યુરિસ્ટિકને ટ્રિગર કરવા માટે પૂરતી છે.

જો આ હમણાં તાજેતરમાં જ શરૂ થયું હોય: ફાઇલના પ્રકારમાં કોઈ ફેરફાર થયો નથી. READMEમાં તેની
એન્ડપોઇન્ટ્સ ટેબલનો વિસ્તાર થયો (MCP HTTP + SSE + A2A ઉમેરવામાં આવ્યા) અને વધુ `curl`
ઉદાહરણો ઉમેરાયા, જેના કારણે તે થ્રેશોલ્ડથી આગળ નીકળી ગયું.

આ ફાઇલ શૂન્ય એક્ઝિક્યુટેબલ સામગ્રી ધરાવતો નિષ્ક્રિય દસ્તાવેજ છે. તમે તેને ક્વોરન્ટાઇનમાંથી
સુરક્ષિત રીતે પુનઃસ્થાપિત કરી શકો છો.

**શું કરવું:**

1. **સૂચનાઓ બંધ કરો** — તમારા એન્ટિવાયરસમાં ઇન્સ્ટોલેશન ડિરેક્ટરીને બાકાત રાખો
   (Avast: Settings → Exceptions), અને તમારો વૈશ્વિક `node_modules` પાથ અને/અથવા
   OmniRoute ડેટા ડિરેક્ટરી (`~/.omniroute/`) ઉમેરો.
2. **ખોટા પોઝિટિવની જાણ કરો** — <https://www.avast.com/false-positive-file-form.php>,
   અને ક્વોરન્ટાઇન કરેલું `README.md` જોડો. આ એવો ઉકેલ છે જે દરેકને મદદ કરે છે, કારણ કે અહીં
   વિક્રેતાની હ્યુરિસ્ટિક ટેક્સ્ટ ફાઇલ પર અતિશય પ્રતિક્રિયા આપી રહી છે.

**અમે અમારી બાજુએ આને શા માટે "ઠીક" કરતા નથી:** બધા ઉદાહરણો `http://localhost` છે અને
સ્વ-હસ્તાક્ષરિત પ્રમાણપત્રની અડચણ વિના localhostને `https` બનાવી શકાતું નથી. એક વિક્રેતાની
હ્યુરિસ્ટિકથી બચવા માટે દસ્તાવેજોને વિકૃત કરવાથી સ્કેનરની ખામીને સંતોષવા માટે દરેક વાચકને
નુકસાન થશે.

### Kaspersky દ્વારા Desktop ઍપને `PDM:Trojan.Win32.Generic` તરીકે ફ્લેગ કરવું

**આ વર્તણૂક-આધારિત હ્યુરિસ્ટિકથી આવેલો ખોટો પોઝિટિવ છે. કંઈપણ સંક્રમિત નથી.** Kasperskyનો
`PDM:` ઉપસર્ગ દર્શાવે છે કે આ નિર્ણય તેના Proactive Defense Module (System Watcher)માંથી
આવે છે, જે ઇન્સ્ટોલરનું જાણીતા માલવેર સાથે મેળાપ કરવાને બદલે તે _શું કરે છે_ તે નક્કી કરે છે.
જ્યારે તે ટ્રિગર થાય છે, ત્યારે Kaspersky સમગ્ર ઇન્સ્ટોલેશનને "રોલ બૅક" કરે છે — તેણે પહેલેથી
લખેલી ફાઇલો કાઢી નાખે છે — તેથી અંતે ઍપ બગડેલી હોય છે અથવા ગાયબ થઈ જાય છે.

તે જે ફાઇલોને ફ્લેગ કરે છે તે Desktop ઍપ સાથે બંડલ કરેલી જાહેર કરાયેલ ઓપન-સોર્સ ડિપેન્ડન્સીઓના
પ્રમાણભૂત ભાગો છે, ઉદાહરણ તરીકે:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` અને
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ઍપની અંદર પ્રોવાઇડર લૉગિન
  અને બ્રાઉઝર-આધારિત ચેટ માટે વપરાતી બ્રાઉઝર-ઑટોમેશન લાઇબ્રેરી.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — વેબ-કૂકી પ્રોવાઇડર્સ પર બ્રાઉઝર-ફિંગરપ્રિન્ટેડ HTTP માટે વપરાતું પિન કરેલું `wreq-js`
  નેટિવ બાઇન્ડિંગ (`<arch>` એ `x64` અથવા `arm64` છે).

**તે શા માટે ટ્રિગર થાય છે:** Windows ઇન્સ્ટોલર હજી **કોડ-સાઇન્ડ નથી**, તેથી સહી વિનાના NSIS
ઇન્સ્ટોલરની પ્રતિષ્ઠા શૂન્ય હોય છે અને વર્તણૂક-આધારિત હ્યુરિસ્ટિક્સ મહત્તમ આક્રમકતા સાથે ચાલે છે.
તેની સાથે બંડલ કરેલી નેટિવ DLL અને `%LOCALAPPDATA%\Programs\OmniRoute` હેઠળ લખાતી સેંકડો `.js`
ફાઇલો (Next.js સ્ટૅન્ડઅલોન બિલ્ડની હૅશ-પ્રત્યયવાળી પૅકેજ ડિરેક્ટરીઓ સહિત) મળીને હ્યુરિસ્ટિકને
ટ્રિગર કરવા માટે પૂરતી છે. કોડ સાઇનિંગનું આયોજન કરવામાં આવ્યું છે; તે અમલમાં આવે ત્યાં સુધી
નવી રિલીઝોમાં આનું પુનરાવર્તન થઈ શકે છે.

**શું કરવું:**

1. **પહેલા તમારા ડાઉનલોડની ચકાસણી કરો** (ફાઇલ સાથે ચેડાં થયાની શક્યતા નકારી કાઢે છે). દરેક
   રિલીઝ `latest.yml` પ્રકાશિત કરે છે, જેનું `sha512` ફીલ્ડ (base64)
   `OmniRoute.Setup.<version>.exe` ઇન્સ્ટોલરને આવરી લે છે. PowerShellમાં, ઇન્સ્ટોલર ધરાવતા
   ફોલ્ડરમાંથી:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   આઉટપુટ `latest.yml` → `sha512` સાથે મેળ ખાવું આવશ્યક છે. જો તે મેળ ન ખાય, તો ફાઇલ કાઢી
   નાખો અને માત્ર [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases)
   પરથી ફરી ડાઉનલોડ કરો.
2. **પુનઃસ્થાપિત કરો + બાકાત રાખો** — ક્વોરન્ટાઇનમાંથી રોલ બૅક કરેલી આઇટમ્સ પુનઃસ્થાપિત કરો
   અને `%LOCALAPPDATA%\Programs\OmniRoute` માટે એક બાકાત ઉમેરો (Kaspersky → Settings →
   Threats and Exclusions), પછી ફરીથી ઇન્સ્ટોલ કરો.
3. **ખોટા પોઝિટિવની જાણ કરો** — <https://opentip.kaspersky.com/>. વપરાશકર્તાઓ દ્વારા સબમિટ
   કરાયેલા FP અહેવાલો ખરેખર અલાઉલિસ્ટિંગને ઝડપી બનાવે છે.

## Node.js સુસંગતતા

<a name="nodejs-compatibility"></a>

### લૉગિન પેજ ક્રૅશ થાય છે અથવા "Module self-registration" ભૂલ બતાવે છે

**કારણ:** તમે OmniRoute દ્વારા મંજૂર સુરક્ષિત રનટાઇમની ન્યૂનતમ મર્યાદાની બહારની Node.js આવૃત્તિ ચલાવી રહ્યા છો. સૌથી સામાન્ય કિસ્સો Node 22 અથવા 24નું એવું જૂનું પૅચ સ્તર ચલાવવાનો છે, જે OmniRoute દ્વારા જરૂરી પૅચ કરેલી સુરક્ષા મર્યાદાથી નીચે હોય.

**લક્ષણો:**

- લૉગિન પેજ ખાલી સ્ક્રીન અથવા સર્વર ભૂલ બતાવે છે
- કન્સોલ `Error: Module did not self-register` અથવા તેના જેવી નેટિવ બાઇન્ડિંગ ભૂલો બતાવે છે
- જો રનટાઇમ સમર્થિત સુરક્ષા નીતિની બહાર હોય, તો લૉગિન પેજ તમારા Node સંસ્કરણ સાથે **નારંગી ચેતવણી બૅનર** બતાવે છે

**ઉકેલ:**

1. સમર્થિત Node.js LTS રિલીઝ ઇન્સ્ટૉલ કરો (ભલામણ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. તમારું સંસ્કરણ ચકાસો: `node --version` એ 24.x LTS શ્રેણીમાં `v24.0.0` અથવા તેનાથી નવું સંસ્કરણ બતાવવું જોઈએ
3. OmniRoute ફરીથી ઇન્સ્ટૉલ કરો: `npm install -g omniroute`
4. ફરી શરૂ કરો: `omniroute`

> **સમર્થિત સુરક્ષિત સંસ્કરણો:** `>=22.22.2 <23` અથવા `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) અને Node.js 26 સંપૂર્ણપણે સમર્થિત છે.

### npm v11+: `better-sqlite3` ઇન્સ્ટૉલ થયેલ નથી (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**કારણ:** npm v11 (Node.js 24+ સાથે ઉપલબ્ધ) મૂળભૂત રીતે વૈકલ્પિક
ડિપેન્ડન્સીઓ માટેની ઇન્સ્ટૉલ સ્ક્રિપ્ટ્સને અવરોધે છે. `better-sqlite3` ને `optionalDependencies`
માં સૂચિબદ્ધ કરાયેલ હોવાથી અને તેને નેટિવ કમ્પાઇલેશન (`node-gyp rebuild`) જરૂરી હોવાથી, npm તેને કોઈ સૂચના વિના છોડી દે છે.

**લક્ષણો:**

- સર્વર સ્ટાર્ટઅપ વખતે `Cannot find module 'better-sqlite3'` સાથે ક્રૅશ થાય છે
- `ls node_modules/better-sqlite3` ચલાવવાથી "No such file or directory" દેખાય છે
- `npm ls better-sqlite3` ચલાવવાથી `(empty)` દેખાય છે

**ઉકેલ:**

1. ઇન્સ્ટૉલ સ્ક્રિપ્ટ્સને મંજૂરી આપો અને ફરીથી ઇન્સ્ટૉલ કરો:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. અથવા પૂર્વ-બિલ્ટ પૅકેજને મૅન્યુઅલી ઇન્સ્ટૉલ કરો:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. તે કાર્ય કરે છે કે નહીં તે ચકાસો: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**કારણ:** વૈશ્વિક `npm install -g omniroute` પછી, પૅકેજની અંદરની `better-sqlite3` નેટિવ બાઇનરી સ્થાનિક રીતે ચાલી રહેલા આર્કિટેક્ચર અથવા Node.js ABI કરતાં અલગ માટે કમ્પાઇલ થયેલી હોઈ શકે છે. જ્યારે પૂર્વ-બિલ્ટ બાઇનરી તમારા પર્યાવરણ સાથે મેળ ન ખાતી હોય, ત્યારે macOS (Apple Silicon અને Intel બંને) પર આ સામાન્ય છે.

**લક્ષણો:**

- સર્વર સ્ટાર્ટઅપ વખતે તરત જ `dlopen` ભૂલ સાથે નિષ્ફળ જાય છે
- ભૂલમાં `slice is not valid mach-o file` હોય છે
- સંપૂર્ણ ઉદાહરણ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ઉકેલ — તમારા સ્થાનિક પર્યાવરણ માટે ફરીથી બિલ્ડ કરો (Node.js ડાઉનગ્રેડની જરૂર નથી):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **નોંધ:** આ તમારા સ્થાનિક Node.js સંસ્કરણ અને CPU આર્કિટેક્ચર માટે નેટિવ બાઇન્ડિંગને ફરીથી કમ્પાઇલ કરે છે, જેનાથી બાઇનરીની અસંગતતા ઉકેલાય છે. અધિકૃત રીતે સમર્થિત રનટાઇમ શ્રેણી **`>=22.22.2 <23` અથવા `>=24.0.0 <27`** છે (`src/shared/utils/nodeRuntimeSupport.ts` માં `SUPPORTED_NODE_RANGE`, જે `package.json` ના `engines` ફીલ્ડ સાથે સુસંગત છે). Node.js 24.x LTS (Krypton) અને Node.js 26, `better-sqlite3` v12.x સાથે સંપૂર્ણપણે સમર્થિત છે.

## પ્રોક્સી સમસ્યાઓ

### પ્રોવાઇડર માન્યતા દરમિયાન "fetch failed" દેખાય છે

**કારણ:** API કી માન્યતા એન્ડપોઇન્ટ (`POST /api/providers/validate`) અગાઉ પ્રોક્સી કન્ફિગરેશનને બાયપાસ કરતો હતો, જેના કારણે પ્રોક્સી રૂટિંગ જરૂરી હોય તેવા પર્યાવરણોમાં નિષ્ફળતા થતી હતી.

**ઉકેલ (v3.5.5+):** હવે આ સમસ્યા સુધારાઈ ગઈ છે. પ્રોવાઇડર માન્યતા હવે `runWithProxyContext` મારફતે રૂટ થાય છે અને પ્રોવાઇડર-સ્તર તથા વૈશ્વિક પ્રોક્સી સેટિંગ્સનું આપમેળે પાલન કરે છે.

### ટોકન હેલ્થ ચેક "fetch failed" સાથે નિષ્ફળ જાય છે

**કારણ:** બૅકગ્રાઉન્ડ OAuth ટોકન રિફ્રેશ દરેક કનેક્શન માટે પ્રોક્સી કન્ફિગરેશનનું નિરાકરણ કરતું નહોતું.

**ઉકેલ (v3.5.5+):** ટોકન હેલ્થ ચેક શેડ્યૂલર હવે રિફ્રેશ કરવાનો પ્રયાસ કરતા પહેલાં દરેક કનેક્શન માટે પ્રોક્સી કન્ફિગનું નિરાકરણ કરે છે. v3.5.5+ પર અપડેટ કરો.

### SOCKS5 પ્રોક્સી "invalid onRequestStart method" પરત કરે છે

**કારણ:** Node.js 22 પર undici@8 ડિસ્પેચર, Nodeના બિલ્ટ-ઇન `fetch()` અમલીકરણ સાથે અસંગત છે.

**ઉકેલ (v3.5.5+):** પ્રોક્સી ડિસ્પેચર સક્રિય હોય ત્યારે OmniRoute હવે undiciના પોતાના `fetch()` ફંક્શનનો ઉપયોગ કરે છે, જેથી સુસંગત વર્તન સુનિશ્ચિત થાય. v3.5.5+ પર અપડેટ કરો.

### WSL હેઠળ MITM પ્રોક્સી: Windows હોસ્ટ પરની ડેસ્કટૉપ ઍપ્સ ઇન્ટરસેપ્ટ થતી નથી

**કારણ:** MITM પ્રોક્સી અને તેનું CA સર્ટિફિકેટ OmniRoute જે પર્યાવરણમાં ચાલે છે તેમાં ઇન્સ્ટૉલ થાય છે. WSL હેઠળ તે પર્યાવરણ Linux ગેસ્ટ હોય છે, જ્યારે AI ડેસ્કટૉપ ઍપ્સ (Kiro, Trae, Copilot, Zed, …) Windows હોસ્ટ પર ચાલે છે. હોસ્ટ ઍપ્સ ગેસ્ટના સર્ટિફિકેટ સ્ટોર પર વિશ્વાસ કરતી નથી અને ગેસ્ટના સિસ્ટમ પ્રોક્સી મારફતે રૂટ થતી નથી, તેથી ત્યાં ડેસ્કટૉપ ઇન્ટરસેપ્શન સક્રિય થતું નથી.

**ભલામણ:** તમે જે ડેસ્કટૉપ ઍપ્સને ઇન્ટરસેપ્ટ કરવા માંગો છો તે જ OS પર OmniRouteને નેટિવ રીતે ચલાવો (Windows ઍપ્સ માટે Windows; macOS/Linux માટે પણ એ જ રીતે). હોસ્ટ ઍપ્સને લક્ષ્ય બનાવતી વખતે OmniRouteને WSLની અંદર જ રાખવા માટે, જનરેટ થયેલ CA સર્ટિફિકેટને Windows હોસ્ટ પર મેન્યુઅલી વિશ્વસનીય બનાવવું અને દરેક હોસ્ટ ઍપના નેટવર્ક/પ્રોક્સી સેટિંગ્સને WSL પ્રોક્સી એન્ડપોઇન્ટ તરફ નિર્દેશિત કરવાં જરૂરી છે — આ એક અસમર્થિત અને નાજુક સેટઅપ છે.

### "Language model did not provide messages"

**કારણ:** પ્રોવાઇડર ક્વોટા સમાપ્ત થઈ ગયો છે.

**ઉકેલ:**

1. ડેશબોર્ડ ક્વોટા ટ્રૅકર તપાસો
2. ફૉલબૅક ટિયર્સ ધરાવતા કૉમ્બોનો ઉપયોગ કરો
3. સસ્તા/મફત ટિયર પર સ્વિચ કરો

### રેટ લિમિટિંગ

**કારણ:** સબ્સ્ક્રિપ્શન ક્વોટા સમાપ્ત થઈ ગયો છે.

**ઉકેલ:**

- ફૉલબૅક ઉમેરો: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- સસ્તા બૅકઅપ તરીકે GLM/MiniMaxનો ઉપયોગ કરો

### OAuth ટોકન સમાપ્ત થઈ ગયું

OmniRoute ટોકન્સને આપમેળે રિફ્રેશ કરે છે. જો સમસ્યાઓ ચાલુ રહે:

1. ડેશબોર્ડ → પ્રોવાઇડર → ફરીથી કનેક્ટ કરો
2. પ્રોવાઇડર કનેક્શન કાઢી નાખો અને ફરીથી ઉમેરો

### Kiro મલ્ટિ-એકાઉન્ટ: બીજું એકાઉન્ટ પ્રથમને અમાન્ય બનાવે છે

**કારણ:** Kiroનું બૅકએન્ડ દરેક OIDC ક્લાયન્ટ રજિસ્ટ્રેશન માટે માત્ર એક સક્રિય સેશન લાગુ કરે છે.
જ્યારે બે એકાઉન્ટ એક જ રજિસ્ટર્ડ ક્લાયન્ટ શેર કરે છે (v3.8.0 પહેલાં ઇમ્પોર્ટ કરેલા કનેક્શન્સ),
ત્યારે એક એકાઉન્ટનું ટોકન રિફ્રેશ કરવાથી બીજા એકાઉન્ટનું રિફ્રેશ ટોકન અમાન્ય થઈ જાય છે.

**ઉકેલ (v3.8.0+):** અસરગ્રસ્ત કનેક્શન્સને ફરીથી ઇમ્પોર્ટ કરો.
v3.8.0થી શરૂ કરીને, **Import Token**,
**Google/GitHub સામાજિક લૉગિન**, અથવા **Auto-Import** મારફતે બનાવવામાં આવેલું દરેક નવું Kiro કનેક્શન આપમેળે પોતાનો
સમર્પિત OIDC ક્લાયન્ટ રજિસ્ટર કરે છે. તેથી કનેક્શન સંપૂર્ણપણે અલગ રહે છે અને એક
એકાઉન્ટને રિફ્રેશ કરવાથી અન્ય કોઈપણ એકાઉન્ટ પર કોઈ અસર થતી નથી.

v3.8.0 _પહેલાં_ ઇમ્પોર્ટ કરાયેલા કનેક્શન્સમાં દરેક કનેક્શન માટે અલગ ક્લાયન્ટ
રજિસ્ટ્રેશન હોતું નથી. તે કનેક્શન્સ શેર કરેલા સોશિયલ-ઑથ રિફ્રેશ એન્ડપોઇન્ટનો ઉપયોગ કરવાનું ચાલુ રાખે છે.
અલગીકરણ મેળવવા માટે, ડેશબોર્ડ → પ્રોવાઇડર્સમાંથી જૂનું કનેક્શન કાઢી નાખો અને તેને
ત્રણમાંથી કોઈપણ ઇમ્પોર્ટ ફ્લો મારફતે ફરીથી ઉમેરો.

બે Kiro એકાઉન્ટને એકસાથે ઉમેરવા માટેની સંપૂર્ણ વિગતો અને પગલું-દર-પગલું સૂચનાઓ માટે,
[`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md) જુઓ.

## ક્લાઉડ સંબંધિત સમસ્યાઓ

### ક્લાઉડ સિંક ભૂલો

1. ખાતરી કરો કે `BASE_URL` તમારા ચાલી રહેલા ઇન્સ્ટન્સ તરફ નિર્દેશ કરે છે (દા.ત., `http://localhost:20128`)
2. ખાતરી કરો કે `CLOUD_URL` તમારા ક્લાઉડ એન્ડપોઇન્ટ તરફ નિર્દેશ કરે છે (દા.ત., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` મૂલ્યોને સર્વર-સાઇડ મૂલ્યો સાથે સુસંગત રાખો

### ક્લાઉડમાં `stream=false` 500 પરત કરે છે

**લક્ષણ:** નોન-સ્ટ્રીમિંગ કૉલ્સ માટે ક્લાઉડ એન્ડપોઇન્ટ પર `Unexpected token 'd'...`.

**કારણ:** ક્લાયન્ટ JSONની અપેક્ષા રાખે છે, જ્યારે અપસ્ટ્રીમ SSE પેલોડ પરત કરે છે.

**વૈકલ્પિક ઉપાય:** ક્લાઉડ પરના ડાયરેક્ટ કૉલ્સ માટે `stream=true` વાપરો. લોકલ રનટાઇમમાં SSE→JSON ફૉલબૅક સામેલ છે.

### ક્લાઉડ કનેક્ટેડ બતાવે છે, પરંતુ "અમાન્ય API કી" કહે છે

1. લોકલ ડૅશબોર્ડ (`/api/keys`) પરથી નવી કી બનાવો
2. ક્લાઉડ સિંક ચલાવો: ક્લાઉડ સક્ષમ કરો → હમણાં સિંક કરો
3. જૂની/સિંક ન થયેલી કીઓ ક્લાઉડ પર હજી પણ `401` પરત કરી શકે છે

## Docker સંબંધિત સમસ્યાઓ

### Docker IPv6 / કનેક્શન રીસેટ

<a name="docker-ipv6"></a>

**લક્ષણો:** `curl http://localhost:20128/v1/models` ચલાવતાં `curl: (56) Recv failure: Connection reset by peer` પરત મળે છે. ડૅશબોર્ડ અને પ્રમાણીકરણ વિનાના એન્ડપોઇન્ટ્સ કાર્ય કરે છે, પરંતુ પ્રમાણીકૃત એન્ડપોઇન્ટ્સ નિષ્ફળ જાય છે — તે પ્રમાણીકરણની સમસ્યા જેવું લાગે છે, પરંતુ ખરેખર એવું નથી.

**કારણ:** `docker run -p 20128:20128`, `0.0.0.0` (IPv4) અને `::` (IPv6) બંને પર પોર્ટ પ્રકાશિત કરે છે, પરંતુ કન્ટેનરની અંદરની પ્રોસેસ માત્ર IPv4 પર સાંભળે છે. જે હોસ્ટ્સ પર `localhost` પહેલાં `::1` તરીકે રિઝોલ્વ થાય છે, ત્યાં કનેક્શન IPv6ના પ્રકાશિત પોર્ટ પર પહોંચે છે, જેની પાછળ કોઈ લિસનર હોતું નથી → કનેક્શન રીસેટ થાય છે.

**ઉકેલ:**

1. **ઝડપી નિદાન:** `curl -4 http://localhost:20128/v1/models` ચલાવો. જો તે `-4` સાથે કાર્ય કરે પરંતુ તેના વિના નિષ્ફળ જાય, તો તમારી પાસે IPv6 બાઇન્ડ મિસમૅચ છે.
2. **કાયમી ઉકેલ:** તમારા `docker run` કમાન્ડમાં `-p 127.0.0.1:20128:20128` વાપરીને સ્પષ્ટપણે IPv4 સાથે બાઇન્ડ કરો:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   આ IPv4 બાઇન્ડને ફરજિયાત બનાવે છે અને પ્રોક્સીને હોસ્ટનાં તમામ ઇન્ટરફેસ પર ખુલ્લું મૂકવાનું પણ ટાળે છે.

### CLI ટૂલ ઇન્સ્ટોલ થયેલું નથી એમ બતાવે છે

1. રનટાઇમ ફીલ્ડ્સ તપાસો: `curl http://localhost:20128/api/cli-tools/runtime/codex | jq`
2. પોર્ટેબલ મોડ માટે: ઇમેજ ટાર્ગેટ `runner-cli` વાપરો (સાથે સમાવિષ્ટ CLI)
3. હોસ્ટ માઉન્ટ મોડ માટે: `CLI_EXTRA_PATHS` સેટ કરો અને હોસ્ટની bin ડિરેક્ટરીને માત્ર-વાંચી શકાય તેવી રીતે માઉન્ટ કરો
4. જો `installed=true` અને `runnable=false` હોય: બાઇનરી મળી હતી પરંતુ હેલ્થચેક નિષ્ફળ થયું હતું

curl -s http://localhost:20128/api/cli-tools/codex-settings | jq '{installed,runnable,commandPath,runtimeMode,reason}'

## ડિબગિંગ

### લૉગ ફાઇલો સક્ષમ કરો

તમારી `.env` ફાઇલમાં `APP_LOG_TO_FILE=true` સેટ કરો. ઍપ્લિકેશન લૉગ્સ `logs/` હેઠળ લખવામાં આવે છે.
જ્યારે સેટિંગ્સમાં કૉલ લૉગ પાઇપલાઇન સક્ષમ હોય, ત્યારે રિક્વેસ્ટ આર્ટિફૅક્ટ્સ `${DATA_DIR}/call_logs/` હેઠળ સંગ્રહિત થાય છે.
જ્યારે પાઇપલાઇન કૅપ્ચર સક્ષમ હોય, ત્યારે સ્ટ્રીમ ચંક પેલોડ્સને બાકાત રાખવા માટે `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` સેટ કરો અથવા આર્ટિફૅક્ટની KB મર્યાદા બદલવા માટે `CALL_LOG_PIPELINE_MAX_SIZE_KB` સમાયોજિત કરો.

### પ્રોવાઇડરનું સ્વાસ્થ્ય તપાસો

```bash
# હેલ્થ ડૅશબોર્ડ
http://localhost:20128/dashboard/health

# API હેલ્થ ચેક
curl http://localhost:20128/api/monitoring/health
```

### રનટાઇમ સ્ટોરેજ

- મુખ્ય સ્ટેટ: `${DATA_DIR}/storage.sqlite` (પ્રોવાઇડર્સ, કોમ્બોઝ, ઉપનામો, કીઓ, સેટિંગ્સ)
- વપરાશ: `storage.sqlite`માં SQLite ટેબલ્સ (`usage_history`, `call_logs`, `proxy_logs`) + વૈકલ્પિક `${DATA_DIR}/call_logs/`
- ઍપ્લિકેશન લૉગ્સ: `<repo>/logs/...` (જ્યારે `APP_LOG_TO_FILE=true`)
- કૉલ લૉગ આર્ટિફૅક્ટ્સ: કૉલ લૉગ પાઇપલાઇન સક્ષમ હોય ત્યારે `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

રિક્વેસ્ટ લૉગ્સ પેજની **ઇતિહાસ સાફ કરો** ક્રિયા `call_logs`, જૂના
`request_detail_logs` અને લોકલ `${DATA_DIR}/call_logs/` આર્ટિફૅક્ટ ડિરેક્ટરીને સાફ કરે છે.

## સર્કિટ બ્રેકરની સમસ્યાઓ

### પ્રદાતા OPEN સ્થિતિમાં અટવાયેલો છે

જ્યારે કોઈ પ્રદાતાનું સર્કિટ બ્રેકર OPEN હોય, ત્યારે કૂલડાઉન સમાપ્ત થાય ત્યાં સુધી વિનંતીઓ અવરોધિત રહે છે.

**ઉકેલ:**

1. **ડૅશબોર્ડ → સેટિંગ્સ → રેઝિલિયન્સ** પર જાઓ
2. અસરગ્રસ્ત પ્રદાતા માટેનું સર્કિટ બ્રેકર કાર્ડ તપાસો
3. બધા બ્રેકર્સ સાફ કરવા માટે **બધા રીસેટ કરો** પર ક્લિક કરો અથવા કૂલડાઉન સમાપ્ત થવાની રાહ જુઓ
4. રીસેટ કરતાં પહેલાં ખાતરી કરો કે પ્રદાતા ખરેખર ઉપલબ્ધ છે

### પ્રદાતા વારંવાર સર્કિટ બ્રેકરને ટ્રિપ કરે છે

જો કોઈ પ્રદાતા વારંવાર OPEN સ્થિતિમાં જાય:

1. નિષ્ફળતાની પેટર્ન માટે **ડૅશબોર્ડ → હેલ્થ → પ્રોવાઇડર હેલ્થ** તપાસો
2. **સેટિંગ્સ → રેઝિલિયન્સ → પ્રોવાઇડર પ્રોફાઇલ્સ** પર જાઓ અને નિષ્ફળતાની થ્રેશોલ્ડ વધારો
3. તપાસો કે પ્રદાતાએ API મર્યાદાઓ બદલી છે કે ફરીથી પ્રમાણીકરણ જરૂરી છે
4. લેટન્સી ટેલિમેટ્રીની સમીક્ષા કરો — વધુ લેટન્સીથી ટાઇમઆઉટ-આધારિત નિષ્ફળતાઓ થઈ શકે છે

## ઑડિયો ટ્રાન્સક્રિપ્શનની સમસ્યાઓ

### "અસમર્થિત મોડલ" ભૂલ

- એવા મોડલ id નો ઉપયોગ કરો જેનો પ્રથમ સેગમેન્ટ એવો પ્રદાતા હોય જેના માટે તમારી પાસે ક્રેડેન્શિયલ્સ છે (`openai/whisper-1`, `openrouter/deepgram/nova-3`). માત્ર `deepgram/nova-3` નો ઉપયોગ કરવા માટે મૂળ Deepgram કી જરૂરી છે.
- ખાતરી કરો કે પ્રદાતા **ડૅશબોર્ડ → પ્રોવાઇડર્સ**માં કનેક્ટ થયેલો છે

### ટ્રાન્સક્રિપ્શન ખાલી મળે છે અથવા નિષ્ફળ જાય છે

- સમર્થિત ઑડિયો ફોર્મેટ તપાસો: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ખાતરી કરો કે ફાઇલનું કદ પ્રદાતાની મર્યાદામાં છે (સામાન્ય રીતે < 25MB)
- પ્રોવાઇડર કાર્ડમાં પ્રદાતાની API કીની માન્યતા તપાસો

## ટ્રાન્સલેટર ડિબગિંગ

ફોર્મેટ રૂપાંતરણની સમસ્યાઓ ડિબગ કરવા માટે **ડૅશબોર્ડ → ટ્રાન્સલેટર**નો ઉપયોગ કરો:

| મોડ              | ક્યારે ઉપયોગ કરવો                                                                                                |
| ---------------- | ---------------------------------------------------------------------------------------------------------------- |
| **પ્લેગ્રાઉન્ડ** | ઇનપુટ/આઉટપુટ ફોર્મેટની બાજુબાજુ સરખામણી કરો — રૂપાંતરણ કેવી રીતે થાય છે તે જોવા માટે નિષ્ફળ થતી વિનંતી પેસ્ટ કરો |
| **ચેટ ટેસ્ટર**   | લાઇવ સંદેશાઓ મોકલો અને હેડર્સ સહિત સંપૂર્ણ વિનંતી/પ્રતિસાદ પેલોડ તપાસો                                           |
| **ટેસ્ટ બેન્ચ**  | કયા રૂપાંતરણો ખામીયુક્ત છે તે શોધવા માટે ફોર્મેટ સંયોજનોમાં બૅચ ટેસ્ટ ચલાવો                                      |
| **લાઇવ મોનિટર**  | છૂટાછવાયા રૂપાંતરણની સમસ્યાઓ શોધવા માટે રીઅલ-ટાઇમ વિનંતી પ્રવાહ જુઓ                                              |

### ફોર્મેટની સામાન્ય સમસ્યાઓ

- **થિંકિંગ ટૅગ્સ દેખાતા નથી** — તપાસો કે લક્ષ્ય પ્રદાતા થિંકિંગને સમર્થન આપે છે કે નહીં અને થિંકિંગ બજેટ સેટિંગ ચકાસો
- **ટૂલ કૉલ્સ ગાયબ થઈ રહ્યા છે** — કેટલાક ફોર્મેટ રૂપાંતરણો અસમર્થિત ફીલ્ડ્સ દૂર કરી શકે છે; પ્લેગ્રાઉન્ડ મોડમાં ચકાસો
- **સિસ્ટમ પ્રોમ્પ્ટ ગાયબ છે** — Claude અને Gemini સિસ્ટમ પ્રોમ્પ્ટ્સને અલગ રીતે હેન્ડલ કરે છે; રૂપાંતરણ આઉટપુટ તપાસો
- **SDK ઑબ્જેક્ટને બદલે રૉ સ્ટ્રિંગ પરત કરે છે** — v1.x માં ઉકેલાયું; રિસ્પોન્સ સેનિટાઇઝર બિન-માનક ફીલ્ડ્સ (`x_groq`, `usage_breakdown`, વગેરે) દૂર કરે છે, જે OpenAI SDK Pydantic વૅલિડેશન નિષ્ફળતાઓનું કારણ બને છે. જો તમને હજી પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને ઇશ્યૂ ફાઇલ કરો.
- **GLM/ERNIE `system` રોલને નકારે છે** — v1.x માં ઉકેલાયું; અસંગત મોડલ્સ માટે રોલ નોર્મલાઇઝર સિસ્ટમ સંદેશાઓને આપમેળે યુઝર સંદેશાઓમાં મર્જ કરે છે. જો તમને હજી પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને ઇશ્યૂ ફાઇલ કરો.
- **`developer` રોલ ઓળખાતો નથી** — v1.x માં ઉકેલાયું; non-OpenAI પ્રદાતાઓ માટે આપમેળે `system`માં રૂપાંતરિત થાય છે. જો તમને હજી પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને ઇશ્યૂ ફાઇલ કરો.
- **`json_schema` Gemini સાથે કાર્ય કરતું નથી** — v1.x માં ઉકેલાયું; `response_format` હવે Geminiના `responseMimeType` + `responseSchema`માં રૂપાંતરિત થાય છે. જો તમને હજી પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને ઇશ્યૂ ફાઇલ કરો.

## સ્થિતિસ્થાપકતા સેટિંગ્સ

### સ્વચાલિત રેટ-લિમિટ ટ્રિગર થતી નથી

- સ્વચાલિત રેટ-લિમિટ ફક્ત API કી પ્રદાતાઓને લાગુ પડે છે (OAuth/સબ્સ્ક્રિપ્શનને નહીં)
- ખાતરી કરો કે **Settings → Resilience → Provider Profiles** માં સ્વચાલિત રેટ-લિમિટ સક્ષમ કરેલી છે
- પ્રદાતા `429` સ્ટેટસ કોડ અથવા `Retry-After` હેડર પરત કરે છે કે કેમ તે તપાસો

### એક્સ્પોનેન્શિયલ બૅકઑફને સમાયોજિત કરવું

પ્રદાતા પ્રોફાઇલ્સ આ સેટિંગ્સને સમર્થન આપે છે:

- **મૂળ વિલંબ** — પ્રથમ નિષ્ફળતા પછીનો પ્રારંભિક પ્રતીક્ષા સમય (ડિફૉલ્ટ: 1s)
- **મહત્તમ વિલંબ** — પ્રતીક્ષા સમયની મહત્તમ મર્યાદા (ડિફૉલ્ટ: 30s)
- **ગુણક** — દરેક સળંગ નિષ્ફળતા દીઠ વિલંબ કેટલો વધારવો (ડિફૉલ્ટ: 2x)

### થન્ડરિંગ હર્ડ નિવારણ

જ્યારે ઘણા સમકાલીન અનુરોધો રેટ-લિમિટ થયેલા પ્રદાતા સુધી પહોંચે છે, ત્યારે OmniRoute અનુરોધોને ક્રમબદ્ધ કરવા અને ક્રમિક નિષ્ફળતાઓ અટકાવવા માટે mutex + સ્વચાલિત રેટ-લિમિટિંગનો ઉપયોગ કરે છે. API કી પ્રદાતાઓ માટે આ આપમેળે થાય છે.

### ચૅટ અનુરોધો 503 / chat_admission_busy સાથે નિષ્ફળ જાય છે

**લક્ષણો:**

- ચૅટ કમ્પ્લીશન્સ એન્ડપોઇન્ટ ફરી પ્રયાસ કરી શકાય એવો `503` પ્રતિસાદ પરત કરે છે, જેનો ભૂલ કોડ
  `chat_admission_busy` છે.
- પ્રતિસાદમાં `Retry-After` સામેલ હોય છે. #12135 પછીથી તેનું મૂલ્ય અવલોકિત
  ઓક્યુપન્સી પરથી મેળવવામાં આવે છે — અનુરોધે અગાઉથી પ્રતીક્ષા કરેલી `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` વિન્ડો
  અને વર્તમાન હેવીવેઇટ લીઝ જેટલા સમયથી ધારણ કરવામાં આવી છે તેમાંથી જે વધુ હોય તે — પૂર્ણ
  સેકન્ડ સુધી ઉપર તરફ રાઉન્ડ કરીને અને વધુમાં વધુ 60 સુધી મર્યાદિત કરીને. નિષ્ક્રિય ગેટ પર તે ઐતિહાસિક ન્યૂનતમ મર્યાદાઓ જાળવે છે: બાઇટ-આધારિત
  પાથ પર 2 સેકન્ડ અને સ્ટ્રક્ચર-આધારિત પાથ પર 1 સેકન્ડ (જેમાં
  `reason: "structure_limit"` પણ સામેલ હોય છે).
- જ્યારે બીજી હેવીવેઇટ ચૅટ અથવા લાંબા સમયથી ચાલી રહેલો સ્ટ્રીમિંગ પ્રતિસાદ હજુ
  પ્રગતિમાં હોય ત્યારે આવું થઈ શકે છે.

બાઇટ-આધારિત પ્રતિસાદ બૉડી આ છે:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

સ્ટ્રક્ચર-આધારિત પ્રતિસાદ સમાન પ્રકાર અને કોડનો ઉપયોગ કરે છે, જેમાં સંદેશ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
અને `reason: "structure_limit"` હોય છે.
ડિફૉલ્ટ થ્રેશોલ્ડ પર, અનુરોધમાં ઓછામાં ઓછા `200` સંદેશાઓ,
ઓછામાં ઓછા `64` ટૂલ્સ અથવા ઓછામાં ઓછા `32,000` અંદાજિત ટોકન્સ હોય, અથવા મર્યાદિત સ્ટ્રક્ચર અંદાજ
`10,000` મુલાકાત લીધેલા નોડ્સ અથવા `12` ઊંડાઈની તેની મર્યાદા વટાવે, ત્યારે તે સ્ટ્રક્ચરની દૃષ્ટિએ ભારે ગણાય છે.

**કારણ:** આ OmniRouteની અંદર ઇરાદાપૂર્વકનું લોડ શેડિંગ છે, અપસ્ટ્રીમ પ્રદાતાની નિષ્ફળતા નહીં.
મોટી રિક્વેસ્ટ બૉડી જાળવી રાખવા અને પાર્સ કરવા પહેલાં મર્યાદિત હેવીવેઇટ ક્ષમતા આરક્ષિત કરવા માટે
દરેક પ્રોસેસ એક પ્રોસેસ-લોકલ ગાર્ડનો ઉપયોગ કરે છે. SSE પ્રતિસાદના સમગ્ર જીવનકાળ દરમિયાન
હેવીવેઇટ લીઝ ધારણ કરેલી રહે છે.

**#503-ફૅન-આઉટ:** આ સુધારા પહેલાં, હોસ્ટ મેમરીને ધ્યાનમાં લીધા વિના ગાર્ડ સમકાલીનતાને અનુરોધોની નિશ્ચિત સંખ્યા
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ડિફૉલ્ટ `1`) સુધી મર્યાદિત કરતો હતો, તેથી કોડિંગ-એજન્ટ
ફૅન-આઉટ (અનેક સબએજન્ટ્સ/CLIs, સામાન્ય રીતે > 256 KB બૉડી) આશરે ~1ની અસરકારક
સમકાલીનતા સુધી ઘટી જતો અને સંપૂર્ણપણે સામાન્ય લોડ હેઠળ 503 આપતો હતો. હવે ગાર્ડ સ્વયં સમાયોજિત થાય છે: તેને
પ્રોસેસની વાસ્તવિક મેમરી મર્યાદા પરથી માપ નક્કી કરાયેલા, આપમેળે પ્રાપ્ત થયેલા ઇન્જેસ્ટ BYTE બજેટ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) દ્વારા
નિયંત્રિત કરવામાં આવે છે અને તે જીવંત રિસોર્સ-પ્રેશર સિગ્નલ પણ તપાસે છે — તેથી તે
માત્ર ત્યારે જ લોડ ઘટાડે છે જ્યારે હોસ્ટ ખરેખર મેમરીના દબાણ હેઠળ હોય, માત્ર એકસાથે એક કરતાં વધુ
ભારે અનુરોધો આવ્યા હોવાને કારણે નહીં. જૂની ગણતરી મર્યાદા (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)નું
હજુ પણ પાલન થાય છે, પરંતુ ફક્ત ત્યારે જ્યારે તમે તેને સ્પષ્ટપણે સેટ કરો.

જ્યારે ક્ષમતા વ્યસ્ત હોય, ત્યારે ફરી પ્રયાસ કરી શકાય એવો `503` પ્રતિસાદ આપતા પહેલાં હેવીવેઇટ અનુરોધ
સ્લોટ ખાલી થવા માટે વધુમાં વધુ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ડિફૉલ્ટ `2000`, `0` પ્રતીક્ષા અક્ષમ કરે છે) સુધી
પ્રતીક્ષા કરે છે. આ મર્યાદિત પ્રતીક્ષા એટલા માટે છે કે એકસાથે ભારે ઉપ-અનુરોધોનું ફૅન-આઉટ કરતા એજન્ટ-શૈલીના ક્લાયન્ટ્સ
(OpenCode, Claude Code, Cursor) તાત્કાલિક અસ્વીકારો પર તેમનું આખું પુનઃપ્રયાસ બજેટ વાપરી નાખીને
કાર્યની વચ્ચે નિષ્ફળ જવાને બદલે બર્સ્ટને ક્રમબદ્ધ કરે.
વર્તમાન હેવીવેઇટ લીઝ ઓક્યુપન્સી, નિર્ધારિત બાઇટ બજેટ અને જીવંત દબાણની તીવ્રતા
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) પર દર્શાવવામાં આવે છે — કોઈપણ env var બદલતા પહેલાં આ તપાસો.
Settings → Resilience → Request Queue → Concurrent Requests આને નિયંત્રિત કરતું નથી; તે સેટિંગ
અલગ પ્રદાતા રિક્વેસ્ટ-ક્યૂ મિકેનિઝમનું સંચાલન કરે છે.

**ઉકેલ:**

1. પહેલાં ફરી પ્રયાસ કરો. ક્લાયન્ટ્સે અનુરોધને તરત જ
   પુનરાવર્તિત કરવાને બદલે `Retry-After`નું પાલન કરવું અને બૅકઑફનો ઉપયોગ કરવો જોઈએ.
2. કંઈપણ સમાયોજિત કરતાં પહેલાં `/api/monitoring/health` → `chatAdmission` તપાસો. `countCapEnabled:
false` અને પૂરતું મોટું `maxInflightBytes` દર્શાવે છે કે આપમેળે પ્રાપ્ત થયેલું બજેટ પહેલેથી જ યોગ્ય રીતે
   કાર્ય કરી રહ્યું છે; `high`/`critical`નું `pressureSeverity` દર્શાવે છે કે હોસ્ટમાં ખરેખર મેમરી ઓછી છે —
   તેને કોઈ ઍડમિશન env varથી સુધારી શકાતું નથી; તેના માટે વધુ RAM અથવા ઓછો વર્કલોડ જરૂરી છે.
3. ફક્ત ત્યારે જ, જ્યારે `/api/monitoring/health` દર્શાવે કે આપમેળે પ્રાપ્ત થયેલું બજેટ ખરેખર તમારા
   હોસ્ટ માટે ખૂબ નાનું છે (આવું ભાગ્યે જ બને છે — તે કન્ટેનરથી લઈને બેર-મેટલ સુધી પહેલેથી જ સ્કેલ થાય છે), લેગસી રિક્વેસ્ટ-કાઉન્ટ મર્યાદા પર પાછા જવાને બદલે
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` વડે તેને સીધું ઓવરરાઇડ કરો.

અધિકૃત ઍડમિશન સેટિંગ્સ માટે [પર્યાવરણ-ચલ સંદર્ભ](../reference/ENVIRONMENT.md#4-security--authentication)
જુઓ.

## વૈકલ્પિક RAG / LLM નિષ્ફળતા વર્ગીકરણ (16 સમસ્યાઓ)

કેટલાક OmniRoute વપરાશકર્તાઓ ગેટવેને RAG અથવા એજન્ટ સ્ટૅક્સની આગળ મૂકે છે. આવા સેટઅપમાં એક વિચિત્ર પેટર્ન જોવા મળવું સામાન્ય છે: OmniRoute સ્વસ્થ દેખાય છે (પ્રોવાઇડર્સ કાર્યરત છે, રાઉટિંગ પ્રોફાઇલ્સ યોગ્ય છે, કોઈ રેટ લિમિટ ચેતવણીઓ નથી), પરંતુ અંતિમ જવાબ હજુ પણ ખોટો હોય છે.

વ્યવહારમાં, આવી ઘટનાઓ સામાન્ય રીતે ડાઉનસ્ટ્રીમ RAG પાઇપલાઇનમાંથી ઉદ્ભવે છે, ગેટવેમાંથી નહીં.

જો તમે આવી નિષ્ફળતાઓનું વર્ણન કરવા માટે સહિયારી શબ્દાવલી ઇચ્છતા હો, તો તમે WFGY ProblemMap નો ઉપયોગ કરી શકો છો, જે બાહ્ય MIT લાઇસન્સ ધરાવતું ટેક્સ્ટ સંસાધન છે અને વારંવાર જોવા મળતી સોળ RAG / LLM નિષ્ફળતા પેટર્ન વ્યાખ્યાયિત કરે છે. ઉચ્ચ સ્તરે તે આ બાબતોને આવરી લે છે:

- રિટ્રીવલ ડ્રિફ્ટ અને તૂટેલી કોન્ટેક્સ્ટ સીમાઓ
- ખાલી અથવા જૂના ઇન્ડેક્સ અને વેક્ટર સ્ટોર્સ
- એમ્બેડિંગ અને સિમેન્ટિક વચ્ચેની અસંગતતા
- પ્રોમ્પ્ટ એસેમ્બલી અને કોન્ટેક્સ્ટ વિન્ડો સંબંધિત સમસ્યાઓ
- તર્કનું પતન અને અતિઆત્મવિશ્વાસપૂર્ણ જવાબો
- લાંબી ચેઇન અને એજન્ટ સંકલન નિષ્ફળતાઓ
- મલ્ટિ-એજન્ટ મેમરી અને ભૂમિકા ડ્રિફ્ટ
- ડિપ્લોયમેન્ટ અને બુટસ્ટ્રૅપ ક્રમ સંબંધિત સમસ્યાઓ

વિચાર સરળ છે:

1. જ્યારે તમે કોઈ ખરાબ પ્રતિસાદની તપાસ કરો, ત્યારે આ માહિતી નોંધો:
   - વપરાશકર્તાનું કાર્ય અને વિનંતી
   - OmniRoute માં રૂટ અથવા પ્રોવાઇડર કોમ્બો
   - ડાઉનસ્ટ્રીમમાં ઉપયોગમાં લેવાયેલ કોઈપણ RAG કોન્ટેક્સ્ટ (પ્રાપ્ત કરેલા દસ્તાવેજો, ટૂલ કૉલ્સ વગેરે)
2. ઘટનાને એક અથવા બે WFGY ProblemMap નંબરો (`No.1` … `No.16`) સાથે મેપ કરો.
3. OmniRoute લૉગ્સની બાજુમાં તમારા પોતાના ડૅશબોર્ડ, રનબુક અથવા ઇન્સિડન્ટ ટ્રૅકરમાં નંબર સંગ્રહિત કરો.
4. તમારે તમારો RAG સ્ટૅક, રિટ્રીવર અથવા રાઉટિંગ વ્યૂહરચના બદલવાની જરૂર છે કે નહીં તે નક્કી કરવા માટે સંબંધિત WFGY પેજનો ઉપયોગ કરો.

સંપૂર્ણ ટેક્સ્ટ અને ચોક્કસ રીતો અહીં ઉપલબ્ધ છે (MIT લાઇસન્સ, માત્ર ટેક્સ્ટ):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

જો તમે OmniRoute પાછળ RAG અથવા એજન્ટ પાઇપલાઇન્સ ચલાવતા ન હો, તો તમે આ વિભાગને અવગણી શકો છો.

**ઉકેલ:**

1. તમારા પ્લેટફોર્મ માટે Devin CLI ઇન્સ્ટૉલ કરો
2. `.env` માં `CLI_DEVIN_BIN=/usr/local/bin/devin` (અથવા વાસ્તવિક પાથ) સેટ કરો
3. OmniRoute રિસ્ટાર્ટ કરો અને **ડૅશબોર્ડ → CLI ટૂલ્સ** પરથી ફરી પરીક્ષણ કરો

### મોડલ કૂલડાઉન અટવાયેલું છે (મૅન્યુઅલ રીસેટ)

**લક્ષણો:**

- સમાપ્તિ સમય પસાર થઈ ગયા પછી પણ મોડલ કૂલડાઉનમાં સૂચિબદ્ધ રહે છે
- ટાઇમસ્ટૅમ્પ ભૂતકાળનો હોવા છતાં કોમ્બો રાઉટિંગમાં વિનંતીઓ હજુ પણ મોડલને છોડી દે છે

**મૅન્યુઅલ રીસેટ:**

- **ડૅશબોર્ડ:** **સેટિંગ્સ → મોડલ કૂલડાઉન્સ** → અસરગ્રસ્ત કાર્ડ પર **ફરી સક્ષમ કરો** ક્લિક કરો
- **API:** મેનેજમેન્ટ પ્રમાણીકરણ હેડર્સ સાથે `DELETE /api/resilience/model-cooldowns`

### Command Code પ્રોવાઇડર કનેક્શન 403 સાથે નિષ્ફળ થાય છે

**લક્ષણો:**

- Command Code પ્રોવાઇડર કનેક્શનનું પરીક્ષણ કરતી વખતે 403
- નવું ઉમેર્યા પછી પ્રોવાઇડર કાર્ડ "અનધિકૃત" દર્શાવે છે

**કારણ:** OAuth પ્રવાહ પૂર્ણ થયો નથી (કૉલબૅક મળ્યો નથી અથવા ટોકન સાચવવામાં આવ્યું નથી).

**ઉકેલ:**

- OAuth પ્રવાહ ફરી શરૂ કરવા માટે CLI માંથી `omniroute providers` ચલાવો, અથવા
- **ડૅશબોર્ડ → પ્રોવાઇડર્સ → Command Code → ફરી કનેક્ટ કરો** પરથી OAuth ફરી ચલાવો

### ModelScope આક્રમક 429 કૂલડાઉન્સ પરત કરે છે

**લક્ષણો:**

- વિનંતીઓના નાના બર્સ્ટ પછી ModelScope પર ખૂબ ટૂંકા અથવા તાત્કાલિક કૂલડાઉન્સ
- કોમ્બો રાઉટિંગ અપેક્ષા કરતાં વહેલું ModelScope ને છોડી દે છે

**કારણ:** ModelScope પ્રોવાઇડર-વિશિષ્ટ `Retry-After` હેડર્સ મોકલે છે. v3.8.0 માં આ હેડર્સ માટે સમર્પિત હૅન્ડલિંગ આપવામાં આવ્યું છે, તેથી જૂના વર્ઝન્સ તેમને સામાન્ય રેટ-લિમિટ સંકેતો તરીકે ખોટી રીતે વાંચે છે.

**ઉકેલ:**

- ખાતરી કરો કે તમે v3.8.0 અથવા પછીના વર્ઝન પર છો
- **સેટિંગ્સ → રિઝિલિયન્સ** હેઠળ `useUpstream429BreakerHints` ટૉગલ સક્ષમ છે તે ચકાસો

### પ્રોડક્શનમાં OMNIROUTE_WS_BRIDGE_SECRET ગેરહાજર છે

**લક્ષણો:**

- રિમોટ પ્રોડક્શન હોસ્ટ પર ચલાવતી વખતે દરેક Codex/Responses WebSocket બ્રિજ વિનંતી પર 401
- કનેક્ટ થયા પછી તરત જ WebSocket બ્રિજ હૅન્ડશેક બંધ થઈ જાય છે

**કારણ:** પ્રોડક્શન એન્વાયર્નમેન્ટમાંથી `OMNIROUTE_WS_BRIDGE_SECRET` એન્વાયરમેન્ટ વેરિએબલ ગેરહાજર છે.

**ઉકેલ:**

1. રૅન્ડમ સિક્રેટ જનરેટ કરો: `openssl rand -hex 32`
2. પ્રોડક્શન સર્વર એન્વાયર્નમેન્ટમાં (અને બ્રિજ સાથે સંચાર કરતા કોઈપણ ક્લાયન્ટમાં) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` સેટ કરો
3. OmniRoute રિસ્ટાર્ટ કરો

### Responses API: બૅકગ્રાઉન્ડ મોડ સિંક્રોનસમાં ડિગ્રેડ થયો

**લક્ષણો:**

- લૉગ થયેલી ચેતવણી: `background mode degraded to synchronous`
- `background: true` વિનંતી બૅકગ્રાઉન્ડ જૉબ હૅન્ડલના બદલે સામાન્ય સિંક્રોનસ પ્રતિસાદ પરત કરે છે

**કારણ:** v3.8.0 ઇરાદાપૂર્વક Responses API પર `background: true` ને ચેતવણી આપતી વખતે સિંક્રોનસ એક્ઝિક્યુશનમાં ડિગ્રેડ કરે છે. સંપૂર્ણ અસિંક્રોનસ બૅકગ્રાઉન્ડ એક્ઝિક્યુશન ભવિષ્યમાં ઉપલબ્ધ કરાવવામાં આવશે.

**ઉકેલ:**

- ક્લાયન્ટને `background` વિના કૉલ કરવા માટે સમાયોજિત કરો, અથવા
- સંપૂર્ણ અસિંક્રોનસ બૅકગ્રાઉન્ડ મોડ આપતી પછીની રિલીઝની રાહ જુઓ (ચેન્જલૉગ ટ્રૅક કરો)

## ધીમું સ્ટાર્ટઅપ / તૈયારી સમયસમાપ્તિ

જો CLI `⚠ Server did not respond within 60s` પ્રિન્ટ કરે, પરંતુ સર્વર
વાસ્તવમાં કાર્યરત હોય, તો તમારા પર્યાવરણ માટે તૈયારી પ્રોબનું સમય-બજેટ ખૂબ ઓછું છે.

આ સામાન્ય રીતે Windows પર (એન્ટિવાઇરસ, ફાઇલસિસ્ટમ વોચર્સ) અથવા ભારે સ્ટાર્ટઅપ
વર્કલોડ ધરાવતા કન્ટેનર્સમાં થાય છે.

**ઉકેલ — સમય-બજેટ વધારો:**

```bash
# એન્વાયરમેન્ટ વેરિએબલ દ્વારા (સ્ટાર્ટ્સ વચ્ચે યથાવત્ રહે છે):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 મિનિટ
omniroute serve

# CLI ફ્લૅગ દ્વારા (એક વખત માટે):
omniroute serve --ready-timeout 180000
```

ડિફૉલ્ટ 60 000 ms (60 s) છે. ચેતવણી માત્ર જાણકારી માટે છે; સર્વર
બૅકગ્રાઉન્ડમાં શરૂ થવાનું ચાલુ રાખે છે અને બૂટ પૂર્ણ થયા પછી ઍક્સેસ કરી શકાશે.

`OMNIROUTE_READY_TIMEOUT_MS` વિશેની સંપૂર્ણ વિગતો માટે
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) જુઓ.
