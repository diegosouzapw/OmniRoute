## ઝડપી સંદર્ભ

**OmniRoute માટે નવા છો?** અહીંથી શરૂઆત કરો — આ 90% સમસ્યાઓનું નિરાકરણ લાવે છે:

| મને આ દેખાય છે             | તેનો અર્થ શું છે                                    | શું કરવું                                                                                                              |
| -------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| "કનેક્ટ થઈ શકતું નથી"      | OmniRoute ચાલી રહ્યું નથી                           | `omniroute` ચલાવો અથવા `docker restart omniroute` ચલાવો                                                                |
| "અમાન્ય API કી"            | તમારી કી ખોટી છે અથવા તેની સમયમર્યાદા પૂરી થઈ ગઈ છે | પ્રદાતાની વેબસાઇટ પરથી કી ફરીથી કૉપિ કરો                                                                               |
| "દર મર્યાદા વટાવી દીધી"    | તમે ઘણા બધા અનુરોધો મોકલી રહ્યા છો                  | 1 મિનિટ રાહ જુઓ અથવા સ્વચાલિત ફૉલબૅક માટે `model: "auto"` વાપરો                                                        |
| "ક્વોટા વટાવી દીધો"        | તમે તમારો મફત/ચૂકવેલ ક્વોટા વાપરી લીધો છે           | વધુ પ્રદાતાઓ કનેક્ટ કરો અથવા મફત પ્રદાતાઓ (Kiro, Pollinations) વાપરો                                                   |
| "ધીમા પ્રતિભાવો"           | પ્રદાતા વ્યસ્ત છે અથવા ખૂબ દૂર છે                   | `model: "auto/fast"` વાપરો અથવા વધુ ઝડપી પ્રદાતા (Groq, Cerebras) કનેક્ટ કરો                                           |
| "ખોટા પ્રદાતાનો ઉપયોગ થયો" | `auto` એ અલગ પ્રદાતા પસંદ કર્યો                     | આ સામાન્ય છે! `auto` શ્રેષ્ઠ વિકલ્પ પસંદ કરે છે. `model: "openai/gpt-4o"` વડે કોઈ ચોક્કસ પ્રદાતાનો ઉપયોગ ફરજિયાત બનાવો |
| "502 ખરાબ ગેટવે"           | પ્રદાતા બંધ છે                                      | રાહ જોઈને ફરી પ્રયાસ કરો અથવા પ્રદાતાઓ બદલવા માટે `model: "auto"` વાપરો                                                |
| "401 અનધિકૃત"              | તમારા ઓળખપત્રો ખોટા છે                              | તમારી API કી તપાસો અથવા OAuth વડે ફરીથી પ્રમાણીકરણ કરો                                                                 |
| "omniroute ઓળખાયું નથી"    | Windows PATH માં વૈશ્વિક node મોડ્યુલો નથી          | તમારા npm વૈશ્વિક પ્રીફિક્સને Windows PATH માં ઉમેરો. તેને `npm config get prefix` વડે શોધો.                           |

### મફત પ્રદાતાઓ પર દર મર્યાદા (429 / 400 / 401)

**લક્ષણ**: મફત/પ્રમાણીકરણ-વિનાના પ્રદાતાઓ (opencode, auggie વગેરે) સાથે `model: "auto"` વાપરતી વખતે તમને જવાબોને બદલે ક્યારેક `HTTP 429`, `400` અથવા `401` મળે છે. થોડી ક્ષણો પછી એ જ પ્રોમ્પ્ટ સાથે ફરી પ્રયાસ કરવાથી અનુરોધો સફળ થાય છે, પરંતુ ઑટોમેશન (cron જૉબ્સ, એજન્ટ્સ, સ્ક્રિપ્ટ્સ) પ્રથમ નિષ્ફળતા પર જ અટકી જાય છે.

**મૂળ કારણ**: ત્રણ સ્વતંત્ર નિષ્ફળતા પ્રકારો એકસાથે ભેગા થાય છે:

1. **પ્રદાતા દર-મર્યાદા (`429`)**: મફત ટિઅર્સ દરેક સમય-વિન્ડો માટે ક્વોટા લાગુ કરી શકે છે. સમાંતર કૉલ્સનો અચાનક ધસારો તેને ખતમ કરી દે છે, તેથી વિન્ડો રીસેટ ન થાય ત્યાં સુધી આગામી અનુરોધ નકારવામાં આવે છે.
2. **પાસથ્રૂમાં ખામીયુક્ત મોડલ (`400`/`401`)**: `auto/*` પૂલ્સમાં `opencode` ના એવા પાસથ્રૂ મોડલ સામેલ હોઈ શકે છે, જે કૅટલૉગમાં નોંધાયેલા હોય પરંતુ તેમની પાસે સક્રિય ઓળખપત્રો ન હોય (દા.ત. `oc/north-mini-code-free` → `401`). ઑટો-રાઉટર તેમાંથી એકનો પ્રયાસ કરે છે, નિષ્ફળ જાય છે અને ફૉલબૅક સક્રિય થાય તે પહેલાં ભૂલ આગળ પ્રસારિત થઈ જાય છે.
3. **સમાનકાલીનતાનું પ્રવર્ધન (લોડ હેઠળ `429`)**: જ્યારે એકથી વધુ એજન્ટ/cron સેશન્સ એકસાથે `auto` નો ઉપયોગ કરે છે, ત્યારે કુલ અનુરોધ દર મફત પ્રદાતાઓની સહનશક્તિ કરતાં વધી જાય છે, જેથી વાજબી કૉલ્સ પણ દુરુપયોગ તરીકે ચિહ્નિત થાય છે.

**ચકાસાયેલ સુધારો (સમુદાય દ્વારા અહેવાલિત, 2026-08-10)**: ત્રણ એન્વાયરમેન્ટ વેરિએબલ્સને એવી રીતે સમાયોજિત કરો કે રોટેશન, સમાનકાલીનતા અને ફૉલબૅક મફત ટિઅરની અસ્થિરતાને કારણે બંધ થઈ જવાને બદલે તેને શોષી લે:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 પર બીજા મોડલ/પ્રદાતા પર જાઓ (ખામીયુક્ત પાસથ્રૂ મોડલ્સને છોડે છે)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ભારે અનુરોધોના પ્રવેશ માટે સ્પષ્ટ ઉચ્ચ મર્યાદા (મૂળભૂત રીતે સેટ નથી: અનુરોધોની સંખ્યા પર કોઈ મર્યાદા નથી, નીચેની નોંધ જુઓ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # તાત્કાલિક ફરી પ્રયાસ કરી શકાય તેવા 503 ને બદલે ભારે અનુરોધોની ક્ષમતા માટે વધુ લાંબી મર્યાદિત પ્રતીક્ષા
```

આને OmniRoute પ્રક્રિયાના એન્વાયરમેન્ટમાં સેટ કરો (ડિમન, દા.ત. LaunchAgent plist અથવા `systemctl edit` મારફતે), પછી OmniRoute ફરી શરૂ કરો. રોટેશન ફ્લૅગ એકમાત્ર સૌથી વધુ અસરકારક ઉપાય છે: તે ગંભીર નિષ્ફળતાને પૂલમાંના કાર્યરત પ્રદાતા સામેના પારદર્શક પુનઃપ્રયાસમાં ફેરવે છે.

**નોંધ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` એકસાથે ચાલી શકતા ભારે — લાંબા-સંદર્ભવાળા — અનુરોધોની સંખ્યાને મર્યાદિત કરે છે; આ મર્યાદા પ્રવેશ દ્વાર છે, પ્રદાતાની દર મર્યાદા નથી. **#503-fanout અપડેટ:** આ વેરિએબલ હવે મૂળભૂત રીતે સેટ કરવામાં આવતું નથી (હવે તે ઉપર દર્શાવ્યા મુજબ સ્પષ્ટ રીતે કૉન્ફિગર કરેલું હોય ત્યારે જ લાગુ પડે છે) — તેના બદલે ભારે અનુરોધોનો પ્રવેશ આપમેળે નક્કી થતા બાઇટ બજેટ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) દ્વારા નિયંત્રિત થાય છે, જે હોસ્ટની વાસ્તવિક મેમરી મર્યાદા અનુસાર પોતાને સ્કેલ કરે છે; તેથી નવી ડિપ્લૉયમેન્ટમાં આ વેરિએબલ સેટ કર્યા વિના પણ ઘણા ઓછા `503 chat_admission_busy` અસ્વીકાર જોવા મળવા જોઈએ. તેને અહીં સ્પષ્ટ રીતે સેટ કરવું હજુ પણ દસ્તાવેજીકરણમાં જણાવ્યા મુજબ જ કાર્ય કરે છે. સ્પષ્ટ બાઇટ-બજેટ ઓવરરાઇડ્સ 8 MiB–2 GiB ની મર્યાદામાં બંધાય છે. `413 body_exceeds_budget` અસ્થાયી નથી: તે બાઇટ બજેટ વધારો, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ઘટાડો અથવા પ્રક્રિયાની મેમરી મર્યાદા વધારો. `inflight_bytes_budget` શેડ અસ્થાયી સંસાધન-સ્પર્ધા છે અને ફરી પ્રયાસ કરી શકાય તેવું રહે છે. પ્રત્યેક પ્રદાતા માટેની દર મર્યાદા (`open-sse/services/rateLimitManager.ts`) અલગ રીતે `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` અને `RATE_LIMIT_AUTO_ENABLE` દ્વારા નિયંત્રિત થાય છે — `.env.example` જુઓ.

**તે કાર્યરત થયું છે કે નહીં તેની ચકાસણી કેવી રીતે કરવી**: તમારા agent/cron ને ટૂંકા અંતરે બે વાર ચલાવો અને ખાતરી કરો કે બંને વખત તે સફળ થાય છે. સુધારા પહેલાં, બીજી વખત ચલાવતાં સામાન્ય રીતે `429`/`401` ભૂલ આવે છે. સુધારા પછી, નિષ્ફળતાઓ (જો કોઈ હોય તો) માટે પારદર્શક રીતે ફરી પ્રયાસ કરવામાં આવે છે અને કૉલ પૂર્ણ થાય છે. તમે `curl /monitoring/health` પણ ચલાવી શકો છો અને provider connections પરના `rateLimitedUntil` field તથા અસરગ્રસ્ત providers માટે `circuitBreakers.providerBreakers[].state` પર નજર રાખી શકો છો — state એ `CLOSED`, `DEGRADED`, `OPEN`, અથવા `HALF_OPEN` પૈકી એક હોય છે (`src/shared/utils/circuitBreaker.ts` જુઓ), અને સતત નિષ્ફળ થતો provider, reset window દ્વારા probe પસાર થવા દે તે પહેલાં, `CLOSED → DEGRADED → OPEN` સ્થિતિમાં બદલાશે (`HALF_OPEN`).

**જો તમને હજી પણ 429 દેખાય**: તે provider માટેના સક્રિય account નો _quota_ ખરેખર પૂરો થઈ ગયો છે (માત્ર rate નહીં). OmniRoute dashboard → Providers → Accounts માં એ જ provider માટે બીજું account ઉમેરો અથવા અન્ય મફત provider (દા.ત. `routeway`, `auggie`) નો સમાવેશ કરો. Rotation માત્ર ક્ષણિક rate/400/401 માટે જ મદદરૂપ થાય છે; quota સંપૂર્ણપણે સમાપ્ત થઈ ગયો હોય તો બીજા credential અથવા અલગ provider ની જરૂર પડે છે.

**જો vision models (`auto/vision`, `bazaarlink/*`) પર 403 દેખાય**: જોડાયેલા account પાસે vision નો સમાવેશ કરતો paid plan નથી અથવા API key પાસે પૂરતી permissions નથી. provider dashboard માં ચકાસો કે key scope માં vision/multimodal નો સમાવેશ થાય છે અથવા paid tier account જોડો અને તેને vision target તરીકે રાખો.

## npm install ચેતવણીઓ (ERESOLVE / peer / deprecated)

જ્યારે તમે `npm install -g omniroute` ચલાવો છો, ત્યારે તમને `npm warn ERESOLVE`, peer-dependency સૂચનાઓ અને `deprecated` સંદેશાઓ જેવી ઘણી ચેતવણીઓ જોવા મળી શકે છે. **આ અપેક્ષિત અને હાનિરહિત છે.** જો આઉટપુટમાં `added <N> packages` દેખાય, તો તમારું ઇન્સ્ટોલેશન સફળ થયું છે.

peer-dependency રિઝોલ્યુશન ચેતવણીઓને દબાવવા માટે, OmniRouteના સમર્થિત ઇન્સ્ટોલેશન સ્વરૂપનો ઉપયોગ કરો:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` ફક્ત `ERESOLVE` અને peer-dependency સૂચનાઓને દબાવે છે. અવમૂલ્યન સૂચનાઓ દેખાતી રહે છે, કારણ કે તે પરોક્ષ તૃતીય-પક્ષ પેકેજોમાંથી આવે છે; તે ઇન્સ્ટોલેશન નિષ્ફળ થયું હોવાનું સૂચવતી નથી.

આ ચેતવણીઓ OmniRouteના નિયંત્રણ બહારના તૃતીય-પક્ષ પેકેજોમાં રહેલી જૂની peer-dependency રેન્જમાંથી આવે છે:

1. **`marked-terminal`ને `marked >=1 <16` જોઈએ છે, પરંતુ `marked@18` મળ્યું** — વ્યવહારમાં યોગ્ય રીતે કાર્ય કરે છે; upstream peer રેન્જ ફક્ત જૂની છે.
2. **`deprecated prebuild-install@7.1.3`** — એક પરોક્ષ native-binary fetch સહાયક. તેનો ઉપયોગ
   પિન કરેલ `wreq-js` ટ્રાન્સપોર્ટ બાઇન્ડિંગ ઇન્સ્ટોલ કરવા માટે થતો નથી અને તે web-cookie
   પ્રોવાઇડર ટ્રાન્સપોર્ટ સેટઅપ નિષ્ફળ થયું હોવાનું સૂચવતું નથી.

**કોઈ પગલું લેવાની જરૂર નથી** — upstream પેકેજોને fork કર્યા વિના ચેતવણીઓને સંપૂર્ણપણે નિષ્ક્રિય કરી શકાતી નથી.

## Gemini Web અને Playwright Chromium

જો Gemini Web રિક્વેસ્ટ `503` સાથે એવો સંદેશ પરત કરે કે Playwright Chromium
ઇન્સ્ટોલ થયેલું નથી, તો npm પેકેજ હાજર છે પરંતુ બ્રાઉઝર બાઇનરી ઉપલબ્ધ નથી.
Playwright ઇરાદાપૂર્વક બ્રાઉઝર ડાઉનલોડને npm પેકેજ
ઇન્સ્ટોલેશનથી અલગ રાખે છે, તેથી બ્રાઉઝર ઇન્સ્ટોલ ન થાય ત્યાં સુધી આ પ્રતિસાદ અપેક્ષિત છે.

વૈશ્વિક npm ઇન્સ્ટોલેશન માટે, OmniRoute પેકેજની
ડિરેક્ટરીમાંથી Chromium ઇન્સ્ટોલ કરો, જેથી બ્રાઉઝર કૅશ એ જ Playwright ઇન્સ્ટોલેશન સાથે સંકળાયેલું રહે:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ઇન્સ્ટોલેશન પછી OmniRoute પુનઃપ્રારંભ કરો અને ત્યારબાદ Gemini Web રિક્વેસ્ટ ફરીથી અજમાવો. જો તમે
Docker ઇમેજમાંથી OmniRoute ચલાવતા હો, તો `-web` ઇમેજ (અથવા `runner-web`
બિલ્ડ ટાર્ગેટ) વાપરો, જેમાં Chromium અને તેની dependencies સામેલ છે; બેઝ ઇમેજમાં
તે સામેલ નથી.

### Avast/AVG `README.md`ને `MD:HttpRequest-inf[Susp]` તરીકે ક્વોરન્ટાઇન કરે છે

**આ ખોટું પોઝિટિવ છે. કંઈપણ સંક્રમિત નથી અને કોઈ કાર્યવાહી કરવાની જરૂર નથી.**

Avast અને AVG એવી હ્યુરિસ્ટિક ચલાવે છે જે ઘણા HTTP વિનંતી જેવા દેખાતા
લિંક્સ ધરાવતી સાદા-ટેક્સ્ટ/Markdown ફાઇલોને ફ્લૅગ કરે છે. OmniRouteનું `README.md` npm પૅકેજમાં સામેલ હોય છે (તે
`package.json` → `files`માં સૂચિબદ્ધ છે), તેથી વૈશ્વિક ઇન્સ્ટોલેશન વખતે તે `node_modules/omniroute/README.md` પર
આવે છે — અને તેમાં ~15 `http://localhost:20128/...` ઉદાહરણો (MCP
HTTP/SSE એન્ડપોઇન્ટ્સ, A2A `.well-known` URL અને `curl` સ્નિપેટ્સ) છે. લિંક્સની આટલી ઘનતા
હ્યુરિસ્ટિકને ટ્રિગર કરવા માટે પૂરતી છે.

જો આ હમણાં જ શરૂ થયું હોય: ફાઇલના પ્રકારમાં કોઈ ફેરફાર થયો નથી. READMEમાં તેની
એન્ડપોઇન્ટ્સ કોષ્ટક (MCP HTTP + SSE + A2A ઉમેરવામાં આવ્યા હતા) અને વધુ `curl` ઉદાહરણો ઉમેરાયા,
જેના કારણે તે થ્રેશોલ્ડને પાર કરી ગયું.

આ ફાઇલ શૂન્ય એક્ઝિક્યુટેબલ સામગ્રી ધરાવતું નિષ્ક્રિય દસ્તાવેજીકરણ છે. તમે તેને ક્વોરન્ટાઇનમાંથી
સુરક્ષિત રીતે પુનઃસ્થાપિત કરી શકો છો.

**શું કરવું:**

1. **સૂચનાઓ બંધ કરો** — તમારા એન્ટિવાયરસમાં ઇન્સ્ટોલ ડિરેક્ટરીને બાકાત રાખો
   (Avast: Settings → Exceptions), તેમાં તમારો વૈશ્વિક `node_modules` પાથ અને/અથવા
   OmniRoute ડેટા ડિરેક્ટરી (`~/.omniroute/`) ઉમેરો.
2. **ખોટા પોઝિટિવની જાણ કરો** — <https://www.avast.com/false-positive-file-form.php>,
   અને ક્વોરન્ટાઇન કરેલું `README.md` જોડો. આ એવો સુધારો છે જે દરેકને મદદ કરે છે, કારણ કે આ
   ટેક્સ્ટ ફાઇલ પર વેન્ડરની હ્યુરિસ્ટિકની અતિપ્રતિક્રિયા છે.

**અમે અમારી બાજુએ આને શા માટે "સુધારતા" નથી:** બધા ઉદાહરણો `http://localhost` છે અને
સ્વ-હસ્તાક્ષરિત પ્રમાણપત્રની અડચણ વિના localhost `https` હોઈ શકતું નથી. એક વેન્ડરની હ્યુરિસ્ટિકને
ચકમો આપવા માટે દસ્તાવેજીકરણને વિકૃત કરવાથી સ્કેનરની ખામીને સંતોષવા માટે દરેક વાચકને નુકસાન થશે.

### Kaspersky Desktop ઍપને `PDM:Trojan.Win32.Generic` તરીકે ફ્લૅગ કરે છે

**આ વર્તણૂકલક્ષી હ્યુરિસ્ટિકનું ખોટું પોઝિટિવ છે. કંઈપણ સંક્રમિત નથી.** Kasperskyનો
`PDM:` ઉપસર્ગ સૂચવે છે કે નિર્ણય તેના Proactive Defense Module (System Watcher)માંથી આવે છે,
જે ઇન્સ્ટોલર જાણીતા માલવેર સાથે મેળ ખાય છે કે નહીં તેના બદલે તે શું _કરે છે_ તેનું મૂલ્યાંકન કરે છે. જ્યારે
તે ટ્રિગર થાય છે, ત્યારે Kaspersky આખા ઇન્સ્ટોલેશનને "રોલ બૅક" કરે છે — તેણે પહેલેથી
લખેલી ફાઇલોને કાઢી નાખે છે — તેથી ઍપ અંતે બગડેલી અથવા ગાયબ થઈ જાય છે.

તે જે ફાઇલોને ફ્લૅગ કરે છે તે Desktop ઍપ સાથે બંડલ કરેલી જાહેર કરાયેલી, ઓપન-સોર્સ ડિપેન્ડન્સીઝના
પ્રમાણભૂત ભાગો છે, ઉદાહરણ તરીકે:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` અને
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ઍપમાં પ્રોવાઇડર લૉગિન અને બ્રાઉઝર-સમર્થિત
  ચેટ માટે વપરાતી બ્રાઉઝર-ઑટોમેશન લાઇબ્રેરી.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — વેબ-કુકી પ્રોવાઇડર્સ પર બ્રાઉઝર-ફિંગરપ્રિન્ટેડ HTTP માટે વપરાતું પિન કરેલું `wreq-js` નેટિવ બાઇન્ડિંગ
  (`<arch>` એ `x64` અથવા `arm64` છે).

**તે શા માટે ટ્રિગર થાય છે:** Windows ઇન્સ્ટોલર હજી **કોડ-સાઇન્ડ નથી**, તેથી સાઇન ન કરેલા NSIS
ઇન્સ્ટોલરની પ્રતિષ્ઠા શૂન્ય હોય છે અને વર્તણૂકલક્ષી હ્યુરિસ્ટિક્સ મહત્તમ આક્રમકતા સાથે ચાલે છે. બંડલ કરેલી
નેટિવ DLL અને `%LOCALAPPDATA%\Programs\OmniRoute` હેઠળ લખવામાં આવેલી સેંકડો `.js` ફાઇલો
(Next.js સ્ટૅન્ડઅલોન બિલ્ડની હૅશ-પ્રત્યયવાળી પૅકેજ ડિરેક્ટરીઓ સહિત) સાથે મળીને,
આ હ્યુરિસ્ટિકને ટ્રિગર કરવા માટે પૂરતું છે. કોડ સાઇનિંગનું આયોજન છે;
તે લાગુ ન થાય ત્યાં સુધી નવી રિલીઝમાં આ ફરી થઈ શકે છે.

**શું કરવું:**

1. **પહેલા તમારું ડાઉનલોડ ચકાસો** (ફાઇલ સાથે ચેડાં થયાની શક્યતા નકારે છે). દરેક રિલીઝ
   `latest.yml` પ્રકાશિત કરે છે, જેનું `sha512` ફીલ્ડ (base64) `OmniRoute.Setup.<version>.exe`
   ઇન્સ્ટોલરને આવરે છે. PowerShellમાં, ઇન્સ્ટોલર ધરાવતા ફોલ્ડરમાંથી:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   આઉટપુટ `latest.yml` → `sha512` સાથે મેળ ખાવું આવશ્યક છે. જો તે મેળ ન ખાય, તો ફાઇલ કાઢી નાખો અને
   ફક્ત [GitHub રિલીઝ પેજ](https://github.com/diegosouzapw/OmniRoute/releases) પરથી ફરી ડાઉનલોડ કરો.
2. **પુનઃસ્થાપિત કરો + બાકાત રાખો** — રોલ બૅક કરેલી આઇટમ્સને ક્વોરન્ટાઇનમાંથી પુનઃસ્થાપિત કરો અને
   `%LOCALAPPDATA%\Programs\OmniRoute` માટે અપવાદ ઉમેરો (Kaspersky → Settings → Threats and Exclusions),
   પછી ફરી ઇન્સ્ટોલ કરો.
3. **ખોટા પોઝિટિવની જાણ કરો** — <https://opentip.kaspersky.com/>. વપરાશકર્તાઓ દ્વારા સબમિટ કરાયેલા FP
   અહેવાલો ખરેખર અલાઉલિસ્ટિંગને ઝડપી બનાવે છે.

## Node.js સુસંગતતા

<a name="nodejs-compatibility"></a>

### લૉગિન પેજ ક્રેશ થાય છે અથવા "Module self-registration" ભૂલ દર્શાવે છે

**કારણ:** તમે OmniRoute દ્વારા મંજૂર કરાયેલા સુરક્ષિત રનટાઇમના ન્યૂનતમ સ્તરની બહારનું Node.js વર્ઝન ચલાવી રહ્યા છો. સૌથી સામાન્ય કિસ્સો Node 22 અથવા 24નું એવું જૂનું પેચ સ્તર ચલાવવાનો છે, જે OmniRoute દ્વારા આવશ્યક પેચ કરાયેલા સુરક્ષા સ્તર કરતાં નીચું હોય.

**લક્ષણો:**

- લૉગિન પેજ ખાલી સ્ક્રીન અથવા સર્વર ભૂલ દર્શાવે છે
- કન્સોલમાં `Error: Module did not self-register` અથવા તેના જેવી નેટિવ બાઇન્ડિંગ ભૂલો દેખાય છે
- જો રનટાઇમ સમર્થિત સુરક્ષા નીતિની બહાર હોય, તો લૉગિન પેજ તમારા Node વર્ઝન સાથે **નારંગી ચેતવણી બેનર** દર્શાવે છે

**ઉકેલ:**

1. સમર્થિત Node.js LTS રિલીઝ ઇન્સ્ટૉલ કરો (ભલામણ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. તમારું વર્ઝન ચકાસો: `node --version` એ 24.x LTS શાખામાં `v24.0.0` અથવા તેનાથી નવું વર્ઝન દર્શાવવું જોઈએ
3. OmniRoute ફરીથી ઇન્સ્ટૉલ કરો: `npm install -g omniroute`
4. ફરી શરૂ કરો: `omniroute`

> **સમર્થિત સુરક્ષિત વર્ઝન:** `>=22.22.2 <23` અથવા `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) અને Node.js 26 સંપૂર્ણપણે સમર્થિત છે.

### npm v11+: `better-sqlite3` ઇન્સ્ટૉલ થયેલું નથી (મોડ્યુલ મળી શક્યું નથી)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**કારણ:** npm v11 (Node.js 24+ સાથે આવતું) ડિફૉલ્ટ રૂપે વૈકલ્પિક
ડિપેન્ડન્સી માટે ઇન્સ્ટૉલ સ્ક્રિપ્ટને અવરોધે છે. `better-sqlite3`ને `optionalDependencies`
માં સૂચિબદ્ધ કરેલું હોવાથી અને તેને નેટિવ કમ્પાઇલેશન (`node-gyp rebuild`) જરૂરી હોવાથી, npm કોઈ સૂચના વિના તેને છોડી દે છે.

**લક્ષણો:**

- સર્વર શરૂ થતી વખતે `Cannot find module 'better-sqlite3'` સાથે ક્રેશ થાય છે
- `ls node_modules/better-sqlite3` ચલાવતાં "No such file or directory" દેખાય છે
- `npm ls better-sqlite3` ચલાવતાં `(empty)` દેખાય છે

**ઉકેલ:**

1. ઇન્સ્ટૉલ સ્ક્રિપ્ટને મંજૂરી આપો અને ફરીથી ઇન્સ્ટૉલ કરો:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. અથવા અગાઉથી બિલ્ડ કરેલું પૅકેજ મેન્યુઅલી ઇન્સ્ટૉલ કરો:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. તે કાર્ય કરે છે કે નહીં તે ચકાસો: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**કારણ:** વૈશ્વિક `npm install -g omniroute` પછી, પૅકેજની અંદરની `better-sqlite3` નેટિવ બાઇનરી સ્થાનિક રીતે ચાલી રહેલા આર્કિટેક્ચર અથવા Node.js ABI કરતાં અલગ આર્કિટેક્ચર અથવા ABI માટે કમ્પાઇલ થયેલી હોઈ શકે છે. અગાઉથી બિલ્ડ કરેલી બાઇનરી તમારા પર્યાવરણ સાથે મેળ ન ખાતી હોય ત્યારે macOS (Apple Silicon અને Intel બંને) પર આ સામાન્ય છે.

**લક્ષણો:**

- સર્વર શરૂ થતાં જ `dlopen` ભૂલ સાથે નિષ્ફળ જાય છે
- ભૂલમાં `slice is not valid mach-o file` હોય છે
- સંપૂર્ણ ઉદાહરણ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ઉકેલ — તમારા સ્થાનિક પર્યાવરણ માટે ફરીથી બિલ્ડ કરો (Node.js ડાઉનગ્રેડ કરવાની જરૂર નથી):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **નોંધ:** આ તમારા સ્થાનિક Node.js વર્ઝન અને CPU આર્કિટેક્ચર માટે નેટિવ બાઇન્ડિંગને ફરીથી કમ્પાઇલ કરે છે, જેનાથી બાઇનરીનો મેળ ન ખાવાની સમસ્યા ઉકેલાય છે. અધિકૃત રીતે સમર્થિત રનટાઇમ શ્રેણી **`>=22.22.2 <23` અથવા `>=24.0.0 <27`** છે (`src/shared/utils/nodeRuntimeSupport.ts`માં `SUPPORTED_NODE_RANGE`, જે `package.json`ના `engines` ફીલ્ડ સાથે સુસંગત છે). Node.js 24.x LTS (Krypton) અને Node.js 26, `better-sqlite3` v12.x સાથે સંપૂર્ણપણે સમર્થિત છે.

## પ્રોક્સી સંબંધિત સમસ્યાઓ

<a name="proxy-issues"></a>

### પ્રોવાઇડર માન્યતામાં "fetch failed" દેખાય છે

**કારણ:** API કી માન્યતા એન્ડપોઇન્ટ (`POST /api/providers/validate`) અગાઉ પ્રોક્સી કૉન્ફિગરેશનને બાયપાસ કરતું હતું, જેના કારણે પ્રોક્સી રૂટિંગ જરૂરી હોય તેવા પર્યાવરણોમાં નિષ્ફળતા થતી હતી.

**ઉકેલ (v3.5.5+):** હવે આ સમસ્યા ઉકેલાઈ ગઈ છે. પ્રોવાઇડર માન્યતા હવે `runWithProxyContext` મારફતે રૂટ થાય છે અને પ્રોવાઇડર-સ્તર તેમજ વૈશ્વિક પ્રોક્સી સેટિંગ્સને આપમેળે અનુસરે છે.

### ટોકન હેલ્થ ચેક "fetch failed" સાથે નિષ્ફળ જાય છે

**કારણ:** બૅકગ્રાઉન્ડ OAuth ટોકન રિફ્રેશ દરેક કનેક્શન માટે પ્રોક્સી કૉન્ફિગરેશનનું નિરાકરણ કરતું નહોતું.

**ઉકેલ (v3.5.5+):** ટોકન હેલ્થ ચેક શેડ્યૂલર હવે રિફ્રેશ કરવાનો પ્રયાસ કરતાં પહેલાં દરેક કનેક્શન માટે પ્રોક્સી કૉન્ફિગનું નિરાકરણ કરે છે. v3.5.5+ પર અપડેટ કરો.

### SOCKS5 પ્રોક્સી "invalid onRequestStart method" પરત કરે છે

**કારણ:** Node.js 22 પર, undici@8 ડિસ્પૅચર Node ના બિલ્ટ-ઇન `fetch()` અમલીકરણ સાથે અસંગત છે.

**ઉકેલ (v3.5.5+):** પ્રોક્સી ડિસ્પૅચર સક્રિય હોય ત્યારે OmniRoute હવે undici ના પોતાના `fetch()` ફંક્શનનો ઉપયોગ કરે છે, જેથી સુસંગત વર્તન સુનિશ્ચિત થાય. v3.5.5+ પર અપડેટ કરો.

### WSL હેઠળ MITM પ્રોક્સી: Windows હોસ્ટ પરની ડેસ્કટૉપ ઍપ્સ ઇન્ટરસેપ્ટ થતી નથી

**કારણ:** MITM પ્રોક્સી અને તેનું CA સર્ટિફિકેટ એ જ પર્યાવરણમાં ઇન્સ્ટૉલ થાય છે જેમાં OmniRoute ચાલે છે. WSL હેઠળ આ પર્યાવરણ Linux ગેસ્ટ હોય છે, જ્યારે AI ડેસ્કટૉપ ઍપ્સ (Kiro, Trae, Copilot, Zed, …) Windows હોસ્ટ પર ચાલે છે. હોસ્ટ ઍપ્સ ગેસ્ટના સર્ટિફિકેટ સ્ટોર પર વિશ્વાસ કરતી નથી અને ગેસ્ટના સિસ્ટમ પ્રોક્સી મારફતે રૂટ થતી નથી, તેથી ત્યાં ડેસ્કટૉપ ઇન્ટરસેપ્શન સક્રિય થતું નથી.

**ભલામણ:** તમે જે ડેસ્કટૉપ ઍપ્સને ઇન્ટરસેપ્ટ કરવા માંગો છો તે જ OS પર OmniRoute ને નેટિવ રીતે ચલાવો (Windows ઍપ્સ માટે Windows; એ જ રીતે macOS/Linux માટે તે જ OS). હોસ્ટ ઍપ્સને લક્ષ્ય બનાવતી વખતે OmniRoute ને WSL ની અંદર રાખવા માટે Windows હોસ્ટ પર જનરેટ થયેલા CA સર્ટિફિકેટ પર મેન્યુઅલી વિશ્વાસ કરવો અને દરેક હોસ્ટ ઍપના નેટવર્ક/પ્રોક્સી સેટિંગ્સને WSL પ્રોક્સી એન્ડપોઇન્ટ તરફ નિર્દેશિત કરવાં જરૂરી છે — આ અસમર્થિત અને નાજુક સેટઅપ છે.

## ક્લાઉડ સંબંધિત સમસ્યાઓ

### ક્લાઉડ સિંક ભૂલો

1. ખાતરી કરો કે `BASE_URL` તમારા ચાલી રહેલા ઇન્સ્ટન્સ તરફ નિર્દેશ કરે છે (દા.ત., `http://localhost:20128`)
2. ખાતરી કરો કે `CLOUD_URL` તમારા ક્લાઉડ એન્ડપોઇન્ટ તરફ નિર્દેશ કરે છે (દા.ત., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` મૂલ્યોને સર્વર-સાઇડ મૂલ્યો સાથે સુસંગત રાખો

### ક્લાઉડ `stream=false` 500 પરત કરે છે

**લક્ષણ:** નોન-સ્ટ્રીમિંગ કૉલ્સ માટે ક્લાઉડ એન્ડપોઇન્ટ પર `Unexpected token 'd'...`.

**કારણ:** ક્લાયન્ટ JSONની અપેક્ષા રાખે છે, જ્યારે અપસ્ટ્રીમ SSE પેલોડ પરત કરે છે.

**વૈકલ્પિક ઉપાય:** ક્લાઉડ પર સીધા કૉલ્સ માટે `stream=true` વાપરો. લોકલ રનટાઇમમાં SSE→JSON ફૉલબૅક સામેલ છે.

### ક્લાઉડ કનેક્ટ થયેલું બતાવે છે પરંતુ "અમાન્ય API કી" કહે છે

1. લોકલ ડૅશબોર્ડમાંથી નવી કી બનાવો (`/api/keys`)
2. ક્લાઉડ સિંક ચલાવો: ક્લાઉડ સક્ષમ કરો → હમણાં સિંક કરો
3. જૂની/સિંક ન થયેલી કીઓ હજી પણ ક્લાઉડ પર `401` પરત કરી શકે છે

## Docker સંબંધિત સમસ્યાઓ

### Docker IPv6 / કનેક્શન રીસેટ

<a name="docker-ipv6"></a>

**લક્ષણો:** `curl http://localhost:20128/v1/models` ચલાવતાં `curl: (56) Recv failure: Connection reset by peer` પરત મળે છે. ડૅશબોર્ડ અને પ્રમાણીકરણ વિનાના એન્ડપોઇન્ટ્સ કાર્ય કરે છે, પરંતુ પ્રમાણિત એન્ડપોઇન્ટ્સ નિષ્ફળ જાય છે — આ પ્રમાણીકરણની સમસ્યા જેવી લાગે છે, પરંતુ વાસ્તવમાં એવી નથી.

**કારણ:** `docker run -p 20128:20128`, `0.0.0.0` (IPv4) અને `::` (IPv6) બંને પર પોર્ટ પ્રકાશિત કરે છે, પરંતુ કન્ટેનરની અંદરની પ્રોસેસ માત્ર IPv4 પર સાંભળે છે. જે હોસ્ટ્સ પર `localhost` પહેલાં `::1` તરીકે રિઝોલ્વ થાય છે, ત્યાં કનેક્શન IPv6 પર પ્રકાશિત પોર્ટ પર પહોંચે છે પરંતુ તેની પાછળ કોઈ લિસનર હોતું નથી → કનેક્શન રીસેટ.

**ઉકેલ:**

1. **ઝડપી નિદાન:** `curl -4 http://localhost:20128/v1/models` ચલાવો. જો તે `-4` સાથે કાર્ય કરે પરંતુ તેના વિના નિષ્ફળ જાય, તો તમારી પાસે IPv6 બાઇન્ડ અસંગતતા છે.
2. **કાયમી ઉકેલ:** તમારા `docker run` કમાન્ડમાં `-p 127.0.0.1:20128:20128` વાપરીને સ્પષ્ટ રીતે IPv4 સાથે બાઇન્ડ કરો:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   આ IPv4 બાઇન્ડને ફરજિયાત કરે છે અને પ્રોક્સીને હોસ્ટના તમામ ઇન્ટરફેસ પર ખુલ્લું મૂકવાનું પણ ટાળે છે.

4. જો `installed=true` અને `runnable=false` હોય: બાઇનરી મળી હતી પરંતુ હેલ્થચેક નિષ્ફળ ગયું

## ડિબગિંગ

### લૉગ ફાઇલો સક્ષમ કરો

તમારી `.env` ફાઇલમાં `APP_LOG_TO_FILE=true` સેટ કરો. એપ્લિકેશન લૉગ્સ `logs/` હેઠળ લખાય છે.
જ્યારે સેટિંગ્સમાં કૉલ લૉગ પાઇપલાઇન સક્ષમ હોય, ત્યારે રિક્વેસ્ટ આર્ટિફેક્ટ્સ `${DATA_DIR}/call_logs/` હેઠળ સંગ્રહિત થાય છે.
જ્યારે પાઇપલાઇન કૅપ્ચર સક્ષમ હોય, ત્યારે સ્ટ્રીમ ચંક પેલોડ્સને બાકાત રાખવા માટે `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` સેટ કરો અથવા આર્ટિફેક્ટની KB મર્યાદા બદલવા માટે `CALL_LOG_PIPELINE_MAX_SIZE_KB` સમાયોજિત કરો.

### પ્રોવાઇડરની હેલ્થ તપાસો

```bash
# હેલ્થ ડૅશબોર્ડ
http://localhost:20128/dashboard/health

# API હેલ્થ ચેક
curl http://localhost:20128/api/monitoring/health
```

### રનટાઇમ સ્ટોરેજ

- મુખ્ય સ્થિતિ: `${DATA_DIR}/storage.sqlite` (પ્રોવાઇડર્સ, કોમ્બોઝ, ઉપનામો, કીઓ, સેટિંગ્સ)
- વપરાશ: `storage.sqlite`માં SQLite ટેબલ્સ (`usage_history`, `call_logs`, `proxy_logs`) + વૈકલ્પિક `${DATA_DIR}/call_logs/`
- એપ્લિકેશન લૉગ્સ: `<repo>/logs/...` (જ્યારે `APP_LOG_TO_FILE=true` હોય)
- કૉલ લૉગ આર્ટિફેક્ટ્સ: કૉલ લૉગ પાઇપલાઇન સક્ષમ હોય ત્યારે `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

રિક્વેસ્ટ લૉગ્સ પેજની **ઇતિહાસ સાફ કરો** ક્રિયા `call_logs`, લેગસી
`request_detail_logs` અને લોકલ `${DATA_DIR}/call_logs/` આર્ટિફેક્ટ ડિરેક્ટરીને સાફ કરે છે.

## સર્કિટ બ્રેકર સમસ્યાઓ

### પ્રદાતા OPEN સ્થિતિમાં અટવાયેલો છે

જ્યારે કોઈ પ્રદાતાનું સર્કિટ બ્રેકર OPEN હોય, ત્યારે કૂલડાઉન પૂર્ણ ન થાય ત્યાં સુધી વિનંતીઓ અવરોધિત રહે છે.

**ઉકેલ:**

1. **Dashboard → Settings → Resilience** પર જાઓ
2. અસરગ્રસ્ત પ્રદાતા માટેનું સર્કિટ બ્રેકર કાર્ડ તપાસો
3. બધા બ્રેકર્સ સાફ કરવા માટે **Reset All** પર ક્લિક કરો અથવા કૂલડાઉન પૂર્ણ થાય ત્યાં સુધી રાહ જુઓ
4. રીસેટ કરતાં પહેલાં ખાતરી કરો કે પ્રદાતા ખરેખર ઉપલબ્ધ છે

### પ્રદાતા વારંવાર સર્કિટ બ્રેકરને ટ્રિપ કરે છે

જો કોઈ પ્રદાતા વારંવાર OPEN સ્થિતિમાં જાય:

1. નિષ્ફળતાની પેટર્ન માટે **Dashboard → Health → Provider Health** તપાસો
2. **Settings → Resilience → Provider Profiles** પર જાઓ અને નિષ્ફળતાની થ્રેશોલ્ડ વધારો
3. પ્રદાતાએ API મર્યાદાઓ બદલી છે કે ફરીથી પ્રમાણીકરણ જરૂરી છે તે તપાસો
4. લેટન્સી ટેલિમેટ્રીની સમીક્ષા કરો — ઊંચી લેટન્સી ટાઇમઆઉટ-આધારિત નિષ્ફળતાઓનું કારણ બની શકે છે

### સામાન્ય ફૉર્મેટ સમસ્યાઓ

- **થિંકિંગ ટૅગ્સ દેખાતા નથી** — લક્ષ્ય પ્રદાતા થિંકિંગને સમર્થન આપે છે કે નહીં અને થિંકિંગ બજેટ સેટિંગ તપાસો
- **ટૂલ કૉલ્સ ગાયબ થાય છે** — કેટલાક ફૉર્મેટ અનુવાદો અસમર્થિત ફીલ્ડ્સ દૂર કરી શકે છે; Playground મોડમાં ચકાસો
- **સિસ્ટમ પ્રૉમ્પ્ટ ગાયબ છે** — Claude અને Gemini સિસ્ટમ પ્રૉમ્પ્ટ્સને અલગ રીતે સંભાળે છે; અનુવાદ આઉટપુટ તપાસો
- **SDK ઑબ્જેક્ટને બદલે રૉ સ્ટ્રિંગ પરત કરે છે** — v1.xમાં ઉકેલાયું છે; પ્રતિસાદ સૅનિટાઇઝર OpenAI SDK Pydantic માન્યતા નિષ્ફળ થવાનું કારણ બનતા બિન-માનક ફીલ્ડ્સ (`x_groq`, `usage_breakdown`, વગેરે) દૂર કરે છે. જો તમને હજી પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને ઇશ્યૂ નોંધાવો.
- **GLM/ERNIE `system` ભૂમિકાને નકારે છે** — v1.xમાં ઉકેલાયું છે; અસંગત મૉડલ્સ માટે રોલ નૉર્મલાઇઝર સિસ્ટમ સંદેશાઓને આપમેળે વપરાશકર્તા સંદેશાઓમાં મર્જ કરે છે. જો તમને હજી પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને ઇશ્યૂ નોંધાવો.
- **`developer` ભૂમિકા ઓળખાતી નથી** — v1.xમાં ઉકેલાયું છે; બિન-OpenAI પ્રદાતાઓ માટે આપમેળે `system`માં રૂપાંતરિત થાય છે. જો તમને હજી પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને ઇશ્યૂ નોંધાવો.
- **`json_schema` Gemini સાથે કામ કરતું નથી** — v1.xમાં ઉકેલાયું છે; `response_format` હવે Geminiના `responseMimeType` + `responseSchema`માં રૂપાંતરિત થાય છે. જો તમને હજી પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને ઇશ્યૂ નોંધાવો.

## સ્થિતિસ્થાપકતા સેટિંગ્સ

### સ્વચાલિત દર-મર્યાદા ટ્રિગર થતી નથી

- સ્વચાલિત દર-મર્યાદા માત્ર API કી પ્રદાતાઓને લાગુ પડે છે (OAuth/સબ્સ્ક્રિપ્શનને નહીં)
- ચકાસો કે **Settings → Resilience → Provider Profiles** માં સ્વચાલિત દર-મર્યાદા સક્ષમ છે
- તપાસો કે પ્રદાતા `429` સ્થિતિ કોડ અથવા `Retry-After` હેડર્સ પરત કરે છે કે નહીં

### એક્સ્પોનેન્શિયલ બૅકઑફનું ટ્યુનિંગ

પ્રદાતા પ્રોફાઇલ્સ આ સેટિંગ્સને સપોર્ટ કરે છે:

- **મૂળભૂત વિલંબ** — પ્રથમ નિષ્ફળતા પછીનો પ્રારંભિક પ્રતીક્ષા સમય (ડિફૉલ્ટ: 1s)
- **મહત્તમ વિલંબ** — પ્રતીક્ષા સમયની મહત્તમ મર્યાદા (ડિફૉલ્ટ: 30s)
- **ગુણક** — દરેક સળંગ નિષ્ફળતા પર વિલંબ કેટલો વધારવો (ડિફૉલ્ટ: 2x)

### થન્ડરિંગ હર્ડ વિરોધી વ્યવસ્થા

જ્યારે ઘણા સમકાલીન અનુરોધો દર-મર્યાદિત પ્રદાતાને મોકલાય છે, ત્યારે OmniRoute અનુરોધોને ક્રમિક બનાવવા અને શ્રેણીબદ્ધ નિષ્ફળતાઓ અટકાવવા માટે mutex + સ્વચાલિત દર-મર્યાદાનો ઉપયોગ કરે છે. API કી પ્રદાતાઓ માટે આ આપમેળે થાય છે.

### ચેટ અનુરોધો 503 / chat_admission_busy સાથે નિષ્ફળ થાય છે

**લક્ષણો:**

- ચેટ કમ્પ્લીશન્સ એન્ડપોઇન્ટ ફરી પ્રયાસ કરી શકાય એવો `503` પ્રતિસાદ પરત કરે છે, જેનો ભૂલ કોડ
  `chat_admission_busy` છે.
- પ્રતિસાદમાં `Retry-After` સામેલ હોય છે. #12135 પછીથી તેનું મૂલ્ય અવલોકિત
  ઓક્યુપન્સી પરથી નક્કી થાય છે — અનુરોધે પહેલેથી રાહ જોયેલી `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` વિન્ડો
  અને વર્તમાન હેવીવેઇટ લીઝ જેટલા સમયથી ધારણ કરવામાં આવી છે તેમાંથી મોટી અવધિ — જેને પૂર્ણ
  સેકન્ડ સુધી ઉપરની તરફ રાઉન્ડ કરીને 60 સુધી મર્યાદિત કરવામાં આવે છે. નિષ્ક્રિય ગેટ પર તે ઐતિહાસિક ન્યૂનતમ મર્યાદાઓ જાળવે છે:
  બાઇટ-આધારિત પાથ પર 2 સેકન્ડ, સ્ટ્રક્ચર-આધારિત પાથ પર 1 સેકન્ડ (જેમાં
  `reason: "structure_limit"` પણ સામેલ છે).
- આવું ત્યારે થઈ શકે છે જ્યારે બીજી હેવીવેઇટ ચેટ અથવા લાંબા સમયથી ચાલી રહેલો સ્ટ્રીમિંગ પ્રતિસાદ હજુ પણ
  પ્રક્રિયામાં હોય.

બાઇટ-આધારિત પ્રતિસાદ બોડી આ છે:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

સ્ટ્રક્ચર-આધારિત પ્રતિસાદ સમાન પ્રકાર અને કોડનો ઉપયોગ કરે છે, જેમાં સંદેશ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
અને `reason: "structure_limit"` હોય છે.
ડિફૉલ્ટ થ્રેશોલ્ડ પર, અનુરોધમાં ઓછામાં ઓછા `200` સંદેશા,
ઓછામાં ઓછા `64` ટૂલ્સ અથવા ઓછામાં ઓછા `32,000` અંદાજિત ટોકન્સ હોય, અથવા મર્યાદિત સ્ટ્રક્ચર અંદાજ
`10,000` મુલાકાત લીધેલા નોડ્સ અથવા `12` ની ઊંડાઈની તેની મર્યાદાઓ વાપરી નાખે, ત્યારે અનુરોધ સ્ટ્રક્ચરની દૃષ્ટિએ હેવી ગણાય છે.

**કારણ:** આ OmniRouteની અંદર ઇરાદાપૂર્વકનું લોડ શેડિંગ છે, અપસ્ટ્રીમ પ્રદાતાની નિષ્ફળતા નહીં.
દરેક પ્રોસેસ મોટા અનુરોધની બોડી જાળવી રાખવા અને પાર્સ કરતા પહેલાં મર્યાદિત હેવીવેઇટ ક્ષમતા અનામત રાખવા માટે
પ્રોસેસ-સ્થાનિક ગાર્ડનો ઉપયોગ કરે છે. SSE પ્રતિસાદના સમગ્ર જીવનકાળ દરમિયાન હેવીવેઇટ લીઝ ધારણ કરવામાં
આવે છે.

**#503-ફેનઆઉટ:** આ સુધારા પહેલાં, ગાર્ડ હોસ્ટ મેમરીને ધ્યાનમાં લીધા વિના સમકાલીનતાને નિશ્ચિત અનુરોધ COUNT
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ડિફૉલ્ટ `1`) સુધી મર્યાદિત કરતો હતો, તેથી કોડિંગ-એજન્ટ
ફેન-આઉટ (બહુવિધ સબએજન્ટ્સ/CLIs, સામાન્ય રીતે 256 KB કરતાં મોટી બોડીઝ) આશરે 1ની અસરકારક
સમકાલીનતા સુધી ઘટી જતો હતો અને સંપૂર્ણપણે સામાન્ય લોડ હેઠળ 503 ભૂલો આપતો હતો. હવે ગાર્ડ સ્વયં-ટ્યુન થાય છે: તે પ્રોસેસની
વાસ્તવિક મેમરી મર્યાદાના આધારે માપવામાં આવેલા આપમેળે નિર્ધારિત ઇન્જેસ્ટ BYTE બજેટ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) દ્વારા
નિયંત્રિત થાય છે અને જીવંત રિસોર્સ-પ્રેશર સિગ્નલ પણ તપાસે છે — તેથી તે માત્ર ત્યારે જ
લોડ ઘટાડે છે જ્યારે હોસ્ટ ખરેખર મેમરી દબાણ હેઠળ હોય, માત્ર એકથી વધુ
હેવી અનુરોધો એકસાથે આવ્યા હોય ત્યારે નહીં. જૂની કાઉન્ટ મર્યાદા (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) હજુ પણ
માન્ય રાખવામાં આવે છે, પરંતુ માત્ર ત્યારે જ જ્યારે તમે તેને સ્પષ્ટપણે સેટ કરો.

જ્યારે ક્ષમતા વ્યસ્ત હોય, ત્યારે હેવીવેઇટ અનુરોધ ફરી પ્રયાસ કરી શકાય એવો `503` પ્રતિસાદ આપતા પહેલાં
સ્લોટ ખાલી થવા માટે `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ડિફૉલ્ટ `2000`, `0` પ્રતીક્ષાને અક્ષમ કરે છે) સુધી
રાહ જુએ છે. આ મર્યાદિત પ્રતીક્ષા એટલા માટે છે કે હેવી સબ-અનુરોધોનો સમકાલીન ફેન-આઉટ કરતા એજન્ટ-શૈલીના ક્લાયન્ટ્સ
(OpenCode, Claude Code, Cursor) તાત્કાલિક અસ્વીકારો પર તેમનું સમગ્ર ફરી-પ્રયાસ બજેટ વેડફીને કાર્યની વચ્ચે
બંધ થઈ જવાને બદલે બર્સ્ટને ક્રમિક રીતે પ્રક્રિયા કરે.
વર્તમાન હેવીવેઇટ લીઝ ઓક્યુપન્સી, નિર્ધારિત બાઇટ બજેટ અને જીવંત દબાણની તીવ્રતા
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) પર દર્શાવવામાં આવે છે — કોઈપણ env var બદલતા પહેલાં આ તપાસો.
Settings → Resilience → Request Queue → Concurrent Requests આને નિયંત્રિત કરતું નથી; તે સેટિંગ
અલગ પ્રદાતા અનુરોધ-કતાર વ્યવસ્થાને નિયંત્રિત કરે છે.

**ઉકેલ:**

1. પહેલાં ફરી પ્રયાસ કરો. ક્લાયન્ટ્સે અનુરોધને તરત જ પુનરાવર્તિત કરવાને બદલે `Retry-After`નું પાલન
   કરવું અને બૅકઑફનો ઉપયોગ કરવો જોઈએ.
2. કંઈપણ ટ્યુન કરતા પહેલાં `/api/monitoring/health` → `chatAdmission` તપાસો. `countCapEnabled:
false` અને ઉદાર `maxInflightBytes`નો અર્થ એ છે કે આપમેળે નિર્ધારિત બજેટ પહેલેથી જ તેનું
   કાર્ય કરી રહ્યું છે; `high`/`critical`નું `pressureSeverity` દર્શાવે છે કે હોસ્ટમાં ખરેખર મેમરી ઓછી છે —
   તેને એડમિશન env var વડે સુધારી શકાતું નથી; તેના માટે વધુ RAM અથવા ઓછો વર્કલોડ જરૂરી છે.
3. માત્ર ત્યારે જ જ્યારે `/api/monitoring/health` દર્શાવે કે આપમેળે નિર્ધારિત બજેટ ખરેખર તમારા હોસ્ટ માટે
   ખૂબ નાનું છે (આ દુર્લભ છે — તે પહેલેથી જ કન્ટેનરથી બેર-મેટલ સુધી સ્કેલ થાય છે), ત્યારે લેગસી અનુરોધ-કાઉન્ટ મર્યાદા પર પાછા જવાને બદલે
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` વડે તેને સીધું ઓવરરાઇડ કરો.

અધિકૃત એડમિશન સેટિંગ્સ માટે [પર્યાવરણ-ચલ સંદર્ભ](../reference/ENVIRONMENT.md#4-security--authentication)
જુઓ.

## વૈકલ્પિક RAG / LLM નિષ્ફળતા વર્ગીકરણ (16 સમસ્યાઓ)

કેટલાક OmniRoute વપરાશકર્તાઓ ગેટવેને RAG અથવા એજન્ટ સ્ટૅક્સની આગળ મૂકે છે. આવા સેટઅપમાં એક વિચિત્ર પેટર્ન જોવું સામાન્ય છે: OmniRoute સ્વસ્થ દેખાય છે (પ્રદાતાઓ કાર્યરત છે, રૂટિંગ પ્રોફાઇલ્સ બરાબર છે, કોઈ રેટ લિમિટ ચેતવણીઓ નથી), પરંતુ અંતિમ જવાબ હજુ પણ ખોટો હોય છે.

વ્યવહારમાં, આ ઘટનાઓ સામાન્ય રીતે ગેટવેના બદલે ડાઉનસ્ટ્રીમ RAG પાઇપલાઇનમાંથી ઉદ્ભવે છે.

જો તમે આ નિષ્ફળતાઓનું વર્ણન કરવા માટે સહિયારી શબ્દાવલી ઇચ્છતા હો, તો તમે WFGY ProblemMap નો ઉપયોગ કરી શકો છો. તે MIT લાઇસન્સ હેઠળનું એક બાહ્ય ટેક્સ્ટ સંસાધન છે, જે વારંવાર જોવા મળતી સોળ RAG / LLM નિષ્ફળતા પેટર્ન વ્યાખ્યાયિત કરે છે. ઉચ્ચ સ્તરે તેમાં આ બાબતો આવરી લેવાય છે:

- રિટ્રીવલ ડ્રિફ્ટ અને તૂટેલી સંદર્ભ સીમાઓ
- ખાલી અથવા જૂના ઇન્ડેક્સ અને વેક્ટર સ્ટોર્સ
- એમ્બેડિંગ અને અર્થવિષયક મેળ ન ખાવાની સમસ્યા
- પ્રોમ્પ્ટ એસેમ્બલી અને કોન્ટેક્સ્ટ વિન્ડોની સમસ્યાઓ
- તર્કનું પતન અને અતિશય આત્મવિશ્વાસભર્યા જવાબો
- લાંબી ચેઇન અને એજન્ટ સંકલનની નિષ્ફળતાઓ
- મલ્ટિ-એજન્ટ મેમરી અને ભૂમિકામાં ડ્રિફ્ટ
- ડિપ્લોયમેન્ટ અને બૂટસ્ટ્રૅપ ક્રમની સમસ્યાઓ

વિચાર સરળ છે:

1. જ્યારે તમે કોઈ ખરાબ પ્રતિસાદની તપાસ કરો, ત્યારે આ વિગતો નોંધો:
   - વપરાશકર્તાનું કાર્ય અને વિનંતી
   - OmniRoute માં રૂટ અથવા પ્રદાતા કોમ્બો
   - ડાઉનસ્ટ્રીમમાં ઉપયોગમાં લેવાયેલ કોઈપણ RAG સંદર્ભ (પુનઃપ્રાપ્ત કરેલા દસ્તાવેજો, ટૂલ કૉલ્સ વગેરે)
2. ઘટનાને એક અથવા બે WFGY ProblemMap નંબરો (`No.1` … `No.16`) સાથે મેપ કરો.
3. OmniRoute લૉગ્સની બાજુમાં તમારા પોતાના ડૅશબોર્ડ, રનબુક અથવા ઇન્સિડન્ટ ટ્રૅકરમાં નંબર સંગ્રહિત કરો.
4. તમારે તમારા RAG સ્ટૅક, રિટ્રીવર અથવા રૂટિંગ વ્યૂહરચનામાં ફેરફાર કરવાની જરૂર છે કે નહીં તે નક્કી કરવા માટે સંબંધિત WFGY પેજનો ઉપયોગ કરો.

સંપૂર્ણ ટેક્સ્ટ અને નક્કર રીતો અહીં ઉપલબ્ધ છે (MIT લાઇસન્સ, માત્ર ટેક્સ્ટ):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

જો તમે OmniRoute પાછળ RAG અથવા એજન્ટ પાઇપલાઇન્સ ચલાવતા ન હો, તો તમે આ વિભાગને અવગણી શકો છો.

### Devin CLI પ્રમાણીકરણ નિષ્ફળતાઓ

**લક્ષણો:**

- Devin-આધારિત ટૂલ્સ ચલાવતી વખતે "Devin CLI મળ્યું નથી" અથવા "પ્રમાણીકરણ નિષ્ફળ થયું"
- CLI રનટાઇમ તપાસ `installed=false` દર્શાવે છે

**કારણો:**

- `CLI_DEVIN_BIN` અસ્તિત્વમાં ન હોય તેવા પાથ તરફ નિર્દેશ કરે છે
- હોસ્ટ પર Devin CLI ઇન્સ્ટૉલ કરેલું નથી

**ઉકેલ:**

1. તમારા પ્લેટફોર્મ માટે Devin CLI ઇન્સ્ટૉલ કરો
2. `.env` માં `CLI_DEVIN_BIN=/usr/local/bin/devin` (અથવા વાસ્તવિક પાથ) સેટ કરો
3. OmniRoute ફરી શરૂ કરો અને **ડૅશબોર્ડ → CLI ટૂલ્સ** પરથી ફરી પરીક્ષણ કરો

### મોડલ કૂલડાઉન અટવાયેલું છે (મૅન્યુઅલ રીસેટ)

**લક્ષણો:**

- સમાપ્તિ સમય પસાર થઈ ગયા પછી પણ મોડલ કૂલડાઉનમાં સૂચિબદ્ધ રહે છે
- ટાઇમસ્ટૅમ્પ ભૂતકાળનો હોવા છતાં કોમ્બો રૂટિંગમાં વિનંતીઓ હજુ પણ મોડલને ટાળે છે

**મૅન્યુઅલ રીસેટ:**

- **ડૅશબોર્ડ:** **સેટિંગ્સ → મોડલ કૂલડાઉન્સ** → અસરગ્રસ્ત કાર્ડ પર **ફરી સક્રિય કરો** ક્લિક કરો
- **API:** મેનેજમેન્ટ પ્રમાણીકરણ હેડર્સ સાથે `DELETE /api/resilience/model-cooldowns`

### Command Code પ્રદાતા કનેક્શન 403 સાથે નિષ્ફળ થાય છે

**લક્ષણો:**

- Command Code પ્રદાતા કનેક્શનનું પરીક્ષણ કરતી વખતે 403
- નવું ઉમેર્યા પછી પ્રદાતા કાર્ડ "અનધિકૃત" દર્શાવે છે

**કારણ:** OAuth ફ્લો પૂર્ણ થયો નથી (કૉલબૅક પ્રાપ્ત થયો નથી અથવા ટોકન સંગ્રહિત થયું નથી).

**ઉકેલ:**

- OAuth ફ્લો ફરી શરૂ કરવા માટે CLI માંથી `omniroute providers` ચલાવો, અથવા
- **ડૅશબોર્ડ → પ્રદાતાઓ → Command Code → ફરી કનેક્ટ કરો** પરથી OAuth ફરી ચલાવો

### ModelScope અતિશય 429 કૂલડાઉન્સ પરત કરે છે

**લક્ષણો:**

- વિનંતીઓના નાના બર્સ્ટ પછી ModelScope પર ખૂબ ટૂંકા અથવા તાત્કાલિક કૂલડાઉન્સ
- કોમ્બો રૂટિંગ અપેક્ષા કરતાં વહેલું ModelScope ને ટાળે છે

**કારણ:** ModelScope પ્રદાતા-વિશિષ્ટ `Retry-After` હેડર્સ મોકલે છે. v3.8.0 માં આ હેડર્સ માટે વિશિષ્ટ હૅન્ડલિંગ સામેલ છે, તેથી જૂની આવૃત્તિઓ તેમને સામાન્ય રેટ-લિમિટ સંકેતો તરીકે ખોટી રીતે વાંચે છે.

**ઉકેલ:**

- ખાતરી કરો કે તમે v3.8.0 અથવા પછીની આવૃત્તિ પર છો
- **સેટિંગ્સ → રેઝિલિયન્સ** હેઠળ `useUpstream429BreakerHints` ટૉગલ સક્રિય છે તે ચકાસો

### પ્રોડક્શનમાં OMNIROUTE_WS_BRIDGE_SECRET ખૂટે છે

**લક્ષણો:**

- રિમોટ પ્રોડક્શન હોસ્ટ પર ચલાવતી વખતે દરેક Codex/Responses WebSocket બ્રિજ વિનંતી પર 401
- કનેક્ટ થયા પછી WebSocket બ્રિજ હૅન્ડશેક તરત જ બંધ થઈ જાય છે

**કારણ:** પ્રોડક્શન એન્વાયરમેન્ટમાં `OMNIROUTE_WS_BRIDGE_SECRET` એન્વાયરમેન્ટ વેરિએબલ ખૂટે છે.

**ઉકેલ:**

1. રૅન્ડમ સિક્રેટ જનરેટ કરો: `openssl rand -hex 32`
2. પ્રોડક્શન સર્વર એન્વાયરમેન્ટમાં (અને બ્રિજ સાથે સંચાર કરતા કોઈપણ ક્લાયન્ટમાં) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` સેટ કરો
3. OmniRoute ફરી શરૂ કરો

### Responses API: બૅકગ્રાઉન્ડ મોડ સિંક્રોનસમાં ડિગ્રેડ થયો

**લક્ષણો:**

- લૉગ થયેલી ચેતવણી: `background mode degraded to synchronous`
- `background: true` વિનંતી બૅકગ્રાઉન્ડ જૉબ હૅન્ડલના બદલે સામાન્ય સિંક્રોનસ પ્રતિસાદ પરત કરે છે

**કારણ:** v3.8.0 ઇરાદાપૂર્વક Responses API પર `background: true` ને સિંક્રોનસ એક્ઝિક્યુશનમાં ડિગ્રેડ કરે છે અને સાથે ચેતવણી પણ મોકલે છે. સંપૂર્ણ અસિંક્રોનસ બૅકગ્રાઉન્ડ એક્ઝિક્યુશન ભવિષ્યમાં ઉપલબ્ધ કરાવવાની બાબત છે.

**ઉકેલ:**

- ક્લાયન્ટને `background` વિના કૉલ કરવા માટે સમાયોજિત કરો, અથવા
- સંપૂર્ણ અસિંક્રોનસ બૅકગ્રાઉન્ડ મોડ ધરાવતી પછીની રિલીઝની રાહ જુઓ (ચેન્જલૉગ અનુસરો)

## ધીમું સ્ટાર્ટઅપ / તૈયારી સમયસમાપ્તિ

જો CLI `⚠ Server did not respond within 60s` પ્રિન્ટ કરે, પરંતુ સર્વર વાસ્તવમાં
કામ કરી રહ્યું હોય, તો તમારા પર્યાવરણ માટે તૈયારી તપાસનું સમય-બજેટ ખૂબ ઓછું છે.

આ સામાન્ય રીતે Windows પર (એન્ટીવાયરસ, ફાઇલસિસ્ટમ વૉચર્સ) અથવા ભારે સ્ટાર્ટઅપ
વર્કલોડ ધરાવતા કન્ટેનર્સમાં થાય છે.

**ઉકેલ — સમય-બજેટ વધારો:**

```bash
# env var દ્વારા (દરેક સ્ટાર્ટ દરમિયાન જળવાઈ રહે છે):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 મિનિટ
omniroute serve

# CLI ફ્લૅગ દ્વારા (માત્ર એક વખત):
omniroute serve --ready-timeout 180000
```

ડિફૉલ્ટ 60 000 ms (60 s) છે. આ ચેતવણી માત્ર માહિતી માટે છે; સર્વર
બૅકગ્રાઉન્ડમાં શરૂ થવાનું ચાલુ રાખે છે અને બૂટ પૂર્ણ થયા પછી ઍક્સેસ કરી શકાશે.

`OMNIROUTE_READY_TIMEOUT_MS` વિશે સંપૂર્ણ વિગતો માટે
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) જુઓ.
