## ઝડપી સંદર્ભ

**OmniRoute માટે નવા છો?** અહીંથી શરૂ કરો — આ 90% સમસ્યાઓ ઉકેલી આપે છે:

| મને આ દેખાય છે           | તેનો અર્થ શું છે                                | શું કરવું                                                                                                     |
| ------------------------ | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| "કનેક્ટ કરી શકાતું નથી"  | OmniRoute ચાલી રહ્યું નથી                       | `omniroute` ચલાવો અથવા `docker restart omniroute` ચલાવો                                                       |
| "અમાન્ય API કી"          | તમારી કી ખોટી છે અથવા તેની મુદત સમાપ્ત થઈ ગઈ છે | પ્રદાતાની વેબસાઇટ પરથી કી ફરી કૉપિ કરો                                                                        |
| "દર મર્યાદા વટાવી"       | તમે ખૂબ વધારે વિનંતીઓ મોકલી રહ્યા છો            | 1 મિનિટ રાહ જુઓ અથવા સ્વચાલિત ફૉલબૅક માટે `model: "auto"` વાપરો                                               |
| "ક્વોટા વટાવ્યો"         | તમે તમારો મફત/ચૂકવેલ ક્વોટા પૂરો વાપરી લીધો છે  | વધુ પ્રદાતાઓ કનેક્ટ કરો અથવા મફત પ્રદાતાઓ (Kiro, Pollinations) વાપરો                                          |
| "ધીમા પ્રતિસાદો"         | પ્રદાતા વ્યસ્ત છે અથવા ખૂબ દૂર છે               | `model: "auto/fast"` વાપરો અથવા વધુ ઝડપી પ્રદાતા (Groq, Cerebras) કનેક્ટ કરો                                  |
| "ખોટો પ્રદાતા વપરાયો"    | `auto`એ કોઈ અલગ પ્રદાતા પસંદ કર્યો              | આ સામાન્ય છે! `auto` શ્રેષ્ઠ પ્રદાતા પસંદ કરે છે. `model: "openai/gpt-4o"` વડે કોઈ ચોક્કસ પ્રદાતા ફરજિયાત કરો |
| "502 ખરાબ ગેટવે"         | પ્રદાતા બંધ છે                                  | રાહ જોઈને ફરી પ્રયાસ કરો અથવા પ્રદાતા બદલવા માટે `model: "auto"` વાપરો                                        |
| "401 અનધિકૃત"            | તમારા ઓળખપત્રો ખોટા છે                          | તમારી API કી તપાસો અથવા OAuth વડે ફરી પ્રમાણીકરણ કરો                                                          |
| "429 અત્યંત વધુ વિનંતીઓ" | દર મર્યાદિત છે                                  | 1 મિનિટ રાહ જુઓ અથવા વધુ પ્રદાતાઓ કનેક્ટ કરો                                                                  |

### મફત પ્રદાતાઓ પર દર મર્યાદા (429 / 400 / 401)

**લક્ષણ**: મફત/પ્રમાણીકરણ-વિનાના પ્રદાતાઓ (opencode, auggie વગેરે) સાથે `model: "auto"` વાપરતી વખતે, તમને ક્યારેક જવાબોને બદલે `HTTP 429`, `400` અથવા `401` મળે છે. થોડી ક્ષણો પછી એ જ પ્રોમ્પ્ટ સાથે ફરી પ્રયાસ કરતાં વિનંતીઓ સફળ થાય છે, પરંતુ ઑટોમેશન (cron jobs, agents, scripts) પ્રથમ નિષ્ફળતા પર તૂટી જાય છે.

**મૂળ કારણ**: ત્રણ સ્વતંત્ર નિષ્ફળતા-પ્રકારો એકસાથે થાય છે:

1. **પ્રદાતાની દર મર્યાદા (`429`)**: મફત સ્તરો સમયગાળા-દીઠ ક્વોટા લાગુ કરી શકે છે. સમાંતર કૉલનો અચાનક ધસારો તેને સમાપ્ત કરી દે છે, તેથી સમયગાળો રીસેટ થાય ત્યાં સુધી આગામી વિનંતી નકારવામાં આવે છે.
2. **પાસથ્રૂમાં ખામીયુક્ત મોડલ (`400`/`401`)**: `auto/*` પૂલમાં `opencode`નાં એવા પાસથ્રૂ મોડલ સામેલ હોઈ શકે છે જે કૅટલૉગમાં નોંધાયેલા છે, પરંતુ જીવંત ઓળખપત્રો ધરાવતા નથી (દા.ત. `oc/north-mini-code-free` → `401`). ઑટો-રાઉટર એક મોડલ અજમાવે છે, નિષ્ફળ જાય છે અને ફૉલબૅક સક્રિય થાય તે પહેલાં ભૂલ આગળ પ્રસારિત થઈ જાય છે.
3. **સમવર્તિતાનું પ્રવર્ધન (લોડ હેઠળ `429`)**: જ્યારે અનેક agent/cron સત્રો એકસાથે `auto`ને ઍક્સેસ કરે છે, ત્યારે કુલ વિનંતી દર મફત પ્રદાતાઓ સહન કરી શકે તેનાથી વધી જાય છે, તેથી માન્ય કૉલને અપમાનજનક ઉપયોગ તરીકે ચિહ્નિત કરવામાં આવે છે.

**ચકાસાયેલ ઉકેલ (સમુદાય દ્વારા અહેવાલિત, 2026-08-10)**: ત્રણ એન્વાયર્નમેન્ટ વેરિએબલને એવી રીતે ગોઠવો કે રોટેશન, સમવર્તિતા અને ફૉલબૅક મફત સ્તરની અસ્થિરતાને નિષ્ફળ થવાને બદલે શોષી લે:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 પર બીજા મોડલ/પ્રદાતા પર જાઓ (ખામીયુક્ત પાસથ્રૂ મોડલને અવગણે છે)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # હેવીવેઇટ પ્રવેશની સ્પષ્ટ મહત્તમ મર્યાદા (ડિફૉલ્ટ રૂપે સેટ નથી: વિનંતી-સંખ્યા પર કોઈ મર્યાદા નથી, નીચેની નોંધ જુઓ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # તાત્કાલિક ફરી પ્રયાસ કરી શકાય તેવી 503 ભૂલને બદલે હેવીવેઇટ ક્ષમતા માટે વધુ લાંબી મર્યાદિત રાહ
```

આને OmniRoute પ્રોસેસના એન્વાયર્નમેન્ટમાં સેટ કરો (ડિમન માટે, દા.ત. LaunchAgent plist અથવા `systemctl edit` મારફતે), પછી OmniRoute ફરી શરૂ કરો. રોટેશન ફ્લૅગ સૌથી વધુ અસરકારક એકમાત્ર સાધન છે: તે કઠોર નિષ્ફળતાને પૂલમાંના સ્વસ્થ પ્રદાતા સામેના પારદર્શક પુનઃપ્રયાસમાં ફેરવે છે.

**નોંધ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` એકસાથે ચાલી શકતી હેવીવેઇટ — લાંબા-સંદર્ભવાળી — વિનંતીઓની સંખ્યાને મર્યાદિત કરે છે; આ મર્યાદા પ્રવેશ-દ્વાર છે, પ્રદાતાની દર મર્યાદા નથી. **#503-fanout અપડેટ:** આ વેરિએબલ હવે ડિફૉલ્ટ રૂપે સેટ થતું નથી (હવે તે ઉપર બતાવ્યા પ્રમાણે સ્પષ્ટપણે કૉન્ફિગર કરવામાં આવે ત્યારે જ લાગુ પડે છે) — તેના બદલે હેવીવેઇટ પ્રવેશને આપમેળે નિર્ધારિત બાઇટ બજેટ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) દ્વારા નિયંત્રિત કરવામાં આવે છે, જે હોસ્ટની વાસ્તવિક મેમરી મર્યાદા અનુસાર પોતે સ્કેલ થાય છે. તેથી નવા ડિપ્લોયમેન્ટમાં આ વેરિએબલ બિલકુલ સેટ કર્યા વિના ઘણા ઓછા `503 chat_admission_busy` અસ્વીકાર જોવા મળવા જોઈએ; તેને અહીં સ્પષ્ટપણે સેટ કરવું હજી પણ દસ્તાવેજીકરણમાં જણાવ્યા મુજબ જ કાર્ય કરે છે. સ્પષ્ટ બાઇટ-બજેટ ઓવરરાઇડ 8 MiB–2 GiB સુધી મર્યાદિત થાય છે. `413 body_exceeds_budget` ક્ષણિક નથી: તે બાઇટ બજેટ વધારો, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ઘટાડો અથવા પ્રોસેસની મેમરી મર્યાદા વધારો. `inflight_bytes_budget` શેડ અસ્થાયી સ્પર્ધા છે અને તેના પર ફરી પ્રયાસ કરી શકાય છે. પ્રદાતા-દીઠ દર મર્યાદા (`open-sse/services/rateLimitManager.ts`) અલગથી `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` અને `RATE_LIMIT_AUTO_ENABLE` દ્વારા નિયંત્રિત થાય છે — `.env.example` જુઓ.

**તે કાર્યરત થયું છે કે નહીં તે કેવી રીતે ચકાસવું**: તમારા agent/cronને ઝડપી ક્રમમાં બે વખત ચલાવો અને ખાતરી કરો કે બંને સફળ થાય છે. ઉકેલ પહેલાં, બીજી વખત ચલાવવાથી સામાન્ય રીતે `429`/`401` મળે છે. ઉકેલ પછી, નિષ્ફળતાઓનો (જો કોઈ હોય તો) પારદર્શક રીતે ફરી પ્રયાસ કરવામાં આવે છે અને કૉલ પૂર્ણ થાય છે. તમે `curl /monitoring/health` પણ ચલાવી શકો છો અને પ્રદાતા કનેક્શનો પરના `rateLimitedUntil` ફીલ્ડ તથા અસરગ્રસ્ત પ્રદાતાઓ માટેના `circuitBreakers.providerBreakers[].state`નું નિરીક્ષણ કરી શકો છો — સ્થિતિ `CLOSED`, `DEGRADED`, `OPEN` અથવા `HALF_OPEN`માંથી એક હોય છે (`src/shared/utils/circuitBreaker.ts` જુઓ), અને સતત નિષ્ફળ થતો પ્રદાતા રીસેટ સમયગાળો ચકાસણીને પસાર થવા દે તે પહેલાં `CLOSED → DEGRADED → OPEN`માં બદલાશે (`HALF_OPEN`).

**જો તમને હજી પણ 429 દેખાય**: તે પ્રદાતા માટેના સક્રિય એકાઉન્ટનો _quota_ ખરેખર સમાપ્ત થઈ ગયો છે (માત્ર દર-મર્યાદા નહીં). OmniRoute ડૅશબોર્ડ → Providers → Accounts માં એ જ પ્રદાતા માટે બીજું એકાઉન્ટ ઉમેરો, અથવા અન્ય કોઈ મફત પ્રદાતા (દા.ત. `routeway`, `auggie`) પણ સામેલ કરો. રોટેશન ફક્ત કામચલાઉ દર-મર્યાદા/400/401 માટે જ મદદરૂપ થાય છે; સંપૂર્ણ quota સમાપ્તિ માટે બીજા credential અથવા અલગ પ્રદાતાની જરૂર પડે છે.

**જો તમને વિઝન મોડલ્સ (`auto/vision`, `bazaarlink/*`) પર 403 દેખાય**: કનેક્ટ કરેલા એકાઉન્ટમાં વિઝનનો સમાવેશ કરતો પેઇડ પ્લાન નથી, અથવા API key પાસે પૂરતી પરવાનગીઓ નથી. પ્રદાતાના ડૅશબોર્ડમાં ચકાસો કે key scope માં વિઝન/મલ્ટીમોડલનો સમાવેશ થાય છે કે નહીં, અથવા પેઇડ ટિયર એકાઉન્ટ કનેક્ટ કરીને તેને વિઝન ટાર્ગેટ તરીકે રાખો.

## npm install ચેતવણીઓ (ERESOLVE / peer / deprecated)

જ્યારે તમે `npm install -g omniroute` ચલાવો છો, ત્યારે તમને `npm warn ERESOLVE`, peer-dependency સૂચનાઓ અને `deprecated` સંદેશાઓ જેવી અનેક ચેતવણીઓ જોવા મળી શકે છે. **આ અપેક્ષિત અને હાનિરહિત છે.** જો આઉટપુટમાં `added <N> packages` દેખાય, તો તમારું ઇન્સ્ટોલેશન સફળ થયું છે.

peer-dependency રિઝોલ્યુશન ચેતવણીઓ દબાવવા માટે OmniRouteનું સમર્થિત ઇન્સ્ટોલેશન સ્વરૂપ વાપરો:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` ફક્ત `ERESOLVE` અને peer-dependency સૂચનાઓને દબાવે છે. ડિપ્રિકેશન સૂચનાઓ દેખાતી રહે છે, કારણ કે તે ટ્રાન્ઝિટિવ તૃતીય-પક્ષ પૅકેજોમાંથી આવે છે; તે ઇન્સ્ટોલેશન નિષ્ફળ ગયું હોવાનું દર્શાવતી નથી.

આ ચેતવણીઓ OmniRouteના નિયંત્રણ બહારનાં તૃતીય-પક્ષ પૅકેજોમાં જૂની peer-dependency રેન્જને કારણે આવે છે:

1. **`marked-terminal`ને `marked >=1 <16` જોઈએ છે, પરંતુ `marked@18` મળ્યું** — વ્યવહારમાં યોગ્ય રીતે કાર્ય કરે છે; upstream peer રેન્જ માત્ર જૂની છે.
2. **`deprecated prebuild-install@7.1.3`** — એક ટ્રાન્ઝિટિવ નેટિવ-બાઇનરી ફેચ સહાયક. તેનો ઉપયોગ
   પિન કરેલ `wreq-js` ટ્રાન્સપોર્ટ બાઇન્ડિંગ ઇન્સ્ટોલ કરવા માટે થતો નથી અને તે web-cookie
   પ્રોવાઇડર ટ્રાન્સપોર્ટ સેટઅપ નિષ્ફળ ગયું હોવાનું દર્શાવતું નથી.

**કોઈ પગલાં લેવાની જરૂર નથી** — upstream પૅકેજોને fork કર્યા વિના આ ચેતવણીઓને સંપૂર્ણપણે શાંત કરી શકાતી નથી.

## એન્ટિવાયરસના ખોટા પોઝિટિવ

<a name="antivirus-false-positives"></a>

### Avast/AVG દ્વારા `README.md` ને `MD:HttpRequest-inf[Susp]` તરીકે ક્વોરન્ટાઇન કરવામાં આવે છે

**આ ખોટું પોઝિટિવ છે. કંઈપણ સંક્રમિત નથી અને કોઈ પગલું લેવાની જરૂર નથી.**

Avast અને AVG એવી હ્યુરિસ્ટિક ચલાવે છે જે ઘણા HTTP વિનંતી જેવા દેખાતા લિંક્સ ધરાવતી
સાદા-ટેક્સ્ટ/Markdown ફાઇલોને ફ્લૅગ કરે છે. OmniRoute ની `README.md` npm package ની અંદર આવે છે (તે
`package.json` → `files` માં સૂચિબદ્ધ છે), તેથી વૈશ્વિક ઇન્સ્ટોલેશન વખતે તે
`node_modules/omniroute/README.md` પર મૂકાય છે — અને તેમાં આશરે 15 `http://localhost:20128/...`
ઉદાહરણો (MCP HTTP/SSE endpoints, A2A `.well-known` URL અને `curl` સ્નિપેટ્સ) છે. લિંક્સની આટલી ઘનતા
હ્યુરિસ્ટિકને ટ્રિગર કરવા માટે પૂરતી છે.

જો આ સમસ્યા તાજેતરમાં જ શરૂ થઈ હોય: ફાઇલના પ્રકારમાં કોઈ ફેરફાર થયો નથી. README માં
endpoints ટેબલ વિસ્તૃત થયું છે (MCP HTTP + SSE + A2A ઉમેરવામાં આવ્યા હતા) અને વધુ `curl`
ઉદાહરણો ઉમેરાયા છે, જેના કારણે તે મર્યાદા વટાવી ગયું છે.

આ ફાઇલ કોઈપણ એક્ઝિક્યુટેબલ સામગ્રી વિનાનું નિષ્ક્રિય દસ્તાવેજીકરણ છે. તમે તેને
ક્વોરન્ટાઇનમાંથી સુરક્ષિત રીતે પુનઃસ્થાપિત કરી શકો છો.

**શું કરવું:**

1. **સૂચનાઓ બંધ કરો** — તમારા એન્ટિવાયરસમાં ઇન્સ્ટોલેશન ડિરેક્ટરીને બાકાત રાખો
   (Avast: Settings → Exceptions), જેમાં તમારો વૈશ્વિક `node_modules` પાથ અને/અથવા
   OmniRoute ડેટા ડિરેક્ટરી (`~/.omniroute/`) ઉમેરો.
2. **ખોટા પોઝિટિવની જાણ કરો** — <https://www.avast.com/false-positive-file-form.php>,
   અને ક્વોરન્ટાઇન કરેલી `README.md` જોડો. આ ઉપાય દરેકને મદદ કરે છે, કારણ કે આ
   ટેક્સ્ટ ફાઇલ પ્રત્યે વિક્રેતાની હ્યુરિસ્ટિકની અતિશય પ્રતિક્રિયા છે.

**અમે અમારી તરફથી આને શા માટે "સુધારતા" નથી:** બધા ઉદાહરણો `http://localhost` છે અને
સેલ્ફ-સાઇન્ડ સર્ટિફિકેટની મુશ્કેલી વિના localhost `https` હોઈ શકતું નથી. એક વિક્રેતાની
હ્યુરિસ્ટિકથી બચવા માટે દસ્તાવેજોમાં વિકૃતિ કરવાથી સ્કેનરની બગને સંતોષવા માટે દરેક
વાચકને નુકસાન થશે.

### Kaspersky ડેસ્કટોપ ઍપને `PDM:Trojan.Win32.Generic` તરીકે ફ્લૅગ કરે છે

**આ વર્તણૂકીય હ્યુરિસ્ટિકથી આવેલું ખોટું પોઝિટિવ છે. કંઈપણ સંક્રમિત નથી.** Kaspersky નું
`PDM:` ઉપસર્ગ સૂચવે છે કે નિર્ણય તેના Proactive Defense Module (System Watcher) માંથી આવે છે,
જે ઇન્સ્ટોલર જાણીતા માલવેર સાથે મેળ ખાય છે કે નહીં તેના બદલે તે શું _કરે છે_ તેના આધારે
નિર્ણય કરે છે. જ્યારે તે ટ્રિગર થાય છે, ત્યારે Kaspersky આખા ઇન્સ્ટોલેશનને "રોલ બૅક" કરે છે —
તે પહેલેથી લખી ચૂકેલી ફાઇલોને કાઢી નાખે છે — તેથી ઍપ અંતે ખરાબ થઈ જાય છે અથવા ગાયબ થઈ જાય છે.

તે જે ફાઇલોને ફ્લૅગ કરે છે તે ડેસ્કટોપ ઍપ સાથે બંડલ કરેલી જાહેર કરાયેલી, ઓપન-સોર્સ
dependencies ના પ્રમાણભૂત ભાગો છે, ઉદાહરણ તરીકે:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` અને
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ઍપની અંદર provider login અને
  browser-backed chat માટે વપરાતી browser-automation library.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — web-cookie providers પર browser-fingerprinted HTTP માટે વપરાતું pinned `wreq-js` native binding
  (`<arch>` એ `x64` અથવા `arm64` છે).

**તે શા માટે ટ્રિગર થાય છે:** Windows installer પર **હજુ સુધી code-signing કરવામાં આવ્યું નથી**,
તેથી unsigned NSIS installer ની પ્રતિષ્ઠા શૂન્ય હોય છે અને વર્તણૂકીય હ્યુરિસ્ટિક્સ મહત્તમ
આક્રમકતાથી ચાલે છે. તેની સાથે બંડલ કરેલી native DLL અને
`%LOCALAPPDATA%\Programs\OmniRoute` હેઠળ લખાયેલી સેંકડો `.js` ફાઇલો (Next.js standalone build માંથી
hash-suffixed package directories સહિત) મળીને હ્યુરિસ્ટિકને ટ્રિગર કરવા માટે પૂરતી છે. Code signing
ની યોજના છે; તે અમલમાં ન આવે ત્યાં સુધી નવી releases માં આ ફરી થઈ શકે છે.

**શું કરવું:**

1. **પહેલા તમારા ડાઉનલોડની ચકાસણી કરો** (ફાઇલ સાથે ચેડાં થયાની શક્યતા નકારે છે). દરેક release
   `latest.yml` પ્રકાશિત કરે છે, જેનું `sha512` field (base64) `OmniRoute.Setup.<version>.exe`
   installer ને આવરી લે છે. PowerShell માં, installer ધરાવતા folder માંથી:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   આઉટપુટ `latest.yml` → `sha512` સાથે મેળ ખાતું હોવું જોઈએ. જો તે મેળ ન ખાય, તો ફાઇલ કાઢી નાખો અને
   ફક્ત [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) પરથી ફરી ડાઉનલોડ કરો.
2. **પુનઃસ્થાપિત કરો + બાકાત રાખો** — રોલ બૅક થયેલી વસ્તુઓને ક્વોરન્ટાઇનમાંથી પુનઃસ્થાપિત કરો અને
   `%LOCALAPPDATA%\Programs\OmniRoute` માટે exclusion ઉમેરો (Kaspersky → Settings → Threats and Exclusions),
   પછી ફરીથી ઇન્સ્ટોલ કરો.
3. **ખોટા પોઝિટિવની જાણ કરો** — <https://opentip.kaspersky.com/>. વપરાશકર્તાઓ દ્વારા સબમિટ કરાયેલા FP
   અહેવાલો ખરેખર allowlisting ને ઝડપી બનાવે છે.

## Node.js સુસંગતતા

<a name="nodejs-compatibility"></a>

### લૉગિન પેજ ક્રૅશ થાય છે અથવા "Module self-registration" ભૂલ બતાવે છે

**કારણ:** તમે OmniRoute દ્વારા મંજૂર કરાયેલ સુરક્ષિત રનટાઇમની ન્યૂનતમ મર્યાદાની બહારનું Node.js વર્ઝન ચલાવી રહ્યા છો. સૌથી સામાન્ય કિસ્સો Node 22 અથવા 24નું એવું જૂનું પૅચ સ્તર ચલાવવાનો છે, જે OmniRoute માટે જરૂરી પૅચ કરેલી સુરક્ષા મર્યાદાથી નીચે હોય.

**લક્ષણો:**

- લૉગિન પેજ ખાલી સ્ક્રીન અથવા સર્વર ભૂલ બતાવે છે
- કન્સોલ `Error: Module did not self-register` અથવા એવી જ મૂળ બાઇન્ડિંગ ભૂલો બતાવે છે
- જો રનટાઇમ સમર્થિત સુરક્ષા નીતિની બહાર હોય, તો લૉગિન પેજ તમારા Node વર્ઝન સાથે **નારંગી ચેતવણી બૅનર** બતાવે છે

**ઉકેલ:**

1. સમર્થિત Node.js LTS રિલીઝ ઇન્સ્ટૉલ કરો (ભલામણ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. તમારું વર્ઝન ચકાસો: `node --version` એ 24.x LTS શ્રેણીમાં `v24.0.0` અથવા તેનાથી નવું બતાવવું જોઈએ
3. OmniRoute ફરીથી ઇન્સ્ટૉલ કરો: `npm install -g omniroute`
4. ફરી શરૂ કરો: `omniroute`

> **સમર્થિત સુરક્ષિત વર્ઝન:** `>=22.22.2 <23` અથવા `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) અને Node.js 26 સંપૂર્ણ રીતે સમર્થિત છે.

### npm v11+: `better-sqlite3` ઇન્સ્ટૉલ થયેલ નથી (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**કારણ:** npm v11 (Node.js 24+ સાથે સમાવિષ્ટ) મૂળભૂત રીતે વૈકલ્પિક
ડિપેન્ડન્સીઓ માટેની ઇન્સ્ટૉલ સ્ક્રિપ્ટ્સને અવરોધે છે. `better-sqlite3` ને `optionalDependencies`
માં સૂચિબદ્ધ કરાયેલ હોવાથી અને તેને મૂળ કમ્પાઇલેશન (`node-gyp rebuild`) જરૂરી હોવાથી, npm તેને કોઈ સૂચના આપ્યા વિના છોડી દે છે.

**લક્ષણો:**

- સર્વર શરૂ થતાં જ `Cannot find module 'better-sqlite3'` સાથે ક્રૅશ થાય છે
- `ls node_modules/better-sqlite3` "No such file or directory" બતાવે છે
- `npm ls better-sqlite3` `(empty)` બતાવે છે

**ઉકેલ:**

1. ઇન્સ્ટૉલ સ્ક્રિપ્ટ્સને મંજૂરી આપો અને ફરીથી ઇન્સ્ટૉલ કરો:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. અથવા પહેલેથી બિલ્ડ કરેલું પૅકેજ મૅન્યુઅલી ઇન્સ્ટૉલ કરો:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. તે કાર્ય કરે છે કે નહીં તે ચકાસો: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**કારણ:** વૈશ્વિક `npm install -g omniroute` પછી, પૅકેજની અંદરની `better-sqlite3` મૂળ બાઇનરી સ્થાનિક રીતે ચાલી રહેલા આર્કિટેક્ચર અથવા Node.js ABI કરતાં અલગ માટે કમ્પાઇલ થયેલી હોઈ શકે છે. જ્યારે પહેલેથી બિલ્ડ કરેલી બાઇનરી તમારા પર્યાવરણ સાથે મેળ ખાતી ન હોય ત્યારે macOS (Apple Silicon અને Intel બંને) પર આ સામાન્ય છે.

**લક્ષણો:**

- સર્વર શરૂ થતાં જ `dlopen` ભૂલ સાથે નિષ્ફળ જાય છે
- ભૂલમાં `slice is not valid mach-o file` હોય છે
- સંપૂર્ણ ઉદાહરણ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ઉકેલ — તમારા સ્થાનિક પર્યાવરણ માટે ફરીથી બિલ્ડ કરો (Node.js ડાઉનગ્રેડ જરૂરી નથી):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **નોંધ:** આ તમારા સ્થાનિક Node.js વર્ઝન અને CPU આર્કિટેક્ચર સામે મૂળ બાઇન્ડિંગને ફરીથી કમ્પાઇલ કરે છે, જેનાથી બાઇનરીની અસંગતતા ઉકેલાય છે. અધિકૃત રીતે સમર્થિત રનટાઇમ શ્રેણી **`>=22.22.2 <23` અથવા `>=24.0.0 <27`** છે (`src/shared/utils/nodeRuntimeSupport.ts` માં `SUPPORTED_NODE_RANGE`, જે `package.json` ના `engines` ફીલ્ડ સાથે સુસંગત છે). Node.js 24.x LTS (Krypton) અને Node.js 26, `better-sqlite3` v12.x સાથે સંપૂર્ણ રીતે સમર્થિત છે.

## પ્રોક્સી સમસ્યાઓ

<a name="proxy-issues"></a>

### પ્રોવાઇડર માન્યતા દરમિયાન "fetch failed" દેખાય છે

**કારણ:** API કી માન્યતા એન્ડપોઇન્ટ (`POST /api/providers/validate`) અગાઉ પ્રોક્સી રૂપરેખાંકનને બાયપાસ કરતું હતું, જેના કારણે પ્રોક્સી રૂટિંગ જરૂરી હોય તેવા પર્યાવરણોમાં નિષ્ફળતા થતી હતી.

**ઉકેલ (v3.5.5+):** હવે આ સમસ્યા સુધારવામાં આવી છે. પ્રોવાઇડર માન્યતા `runWithProxyContext` મારફતે રૂટ થાય છે અને પ્રોવાઇડર-સ્તરના તથા વૈશ્વિક પ્રોક્સી સેટિંગ્સને આપમેળે અનુસરે છે.

### ટોકન હેલ્થ ચેક "fetch failed" સાથે નિષ્ફળ થાય છે

**કારણ:** બૅકગ્રાઉન્ડ OAuth ટોકન રિફ્રેશ દરેક કનેક્શન માટે પ્રોક્સી રૂપરેખાંકન રિઝોલ્વ કરતું નહોતું.

**ઉકેલ (v3.5.5+):** હવે ટોકન હેલ્થ ચેક શેડ્યૂલર રિફ્રેશ કરવાનો પ્રયાસ કરતા પહેલાં દરેક કનેક્શન માટે પ્રોક્સી રૂપરેખાંકન રિઝોલ્વ કરે છે. v3.5.5+ પર અપડેટ કરો.

### SOCKS5 પ્રોક્સી "invalid onRequestStart method" પરત કરે છે

**કારણ:** Node.js 22 પર, undici@8 ડિસ્પેચર Node ના બિલ્ટ-ઇન `fetch()` અમલીકરણ સાથે અસંગત છે.

**ઉકેલ (v3.5.5+):** જ્યારે પ્રોક્સી ડિસ્પેચર સક્રિય હોય ત્યારે OmniRoute હવે undici ના પોતાના `fetch()` ફંક્શનનો ઉપયોગ કરે છે, જે સુસંગત વર્તન સુનિશ્ચિત કરે છે. v3.5.5+ પર અપડેટ કરો.

### WSL હેઠળ MITM પ્રોક્સી: Windows હોસ્ટ પરની ડેસ્કટોપ એપ્સ ઇન્ટરસેપ્ટ થતી નથી

**કારણ:** MITM પ્રોક્સી અને તેનું CA પ્રમાણપત્ર OmniRoute જે પર્યાવરણમાં ચાલે છે તેમાં ઇન્સ્ટૉલ થાય છે. WSL હેઠળ તે પર્યાવરણ Linux ગેસ્ટ છે, જ્યારે AI ડેસ્કટોપ એપ્સ (Kiro, Trae, Copilot, Zed, …) Windows હોસ્ટ પર ચાલે છે. હોસ્ટ એપ્સ ગેસ્ટના પ્રમાણપત્ર સ્ટોર પર વિશ્વાસ કરતી નથી અને ગેસ્ટના સિસ્ટમ પ્રોક્સી મારફતે રૂટ થતી નથી, તેથી ત્યાં ડેસ્કટોપ ઇન્ટરસેપ્શન સક્રિય થતું નથી.

**ભલામણ:** તમે જે ડેસ્કટોપ એપ્સને ઇન્ટરસેપ્ટ કરવા માંગો છો, તે જ OS પર OmniRoute ને નેટિવ રીતે ચલાવો (Windows એપ્સ માટે Windows; એ જ રીતે macOS/Linux માટે તેમના સંબંધિત OS). હોસ્ટ એપ્સને લક્ષ્ય બનાવીને OmniRoute ને WSL ની અંદર રાખવા માટે, જનરેટ થયેલું CA પ્રમાણપત્ર Windows હોસ્ટ પર મેન્યુઅલી વિશ્વસનીય બનાવવું અને દરેક હોસ્ટ એપના નેટવર્ક/પ્રોક્સી સેટિંગ્સને WSL પ્રોક્સી એન્ડપોઇન્ટ તરફ નિર્દેશિત કરવું જરૂરી છે — આ એક અસમર્થિત અને નાજુક ગોઠવણ છે.

### રેટ લિમિટિંગ

**કારણ:** સબ્સ્ક્રિપ્શન ક્વોટા સમાપ્ત થઈ ગયો છે.

**ઉકેલ:**

OmniRoute ટોકન્સને આપમેળે રિફ્રેશ કરે છે. જો સમસ્યાઓ ચાલુ રહે:

1. ડૅશબોર્ડ → પ્રોવાઇડર → ફરીથી કનેક્ટ કરો
2. પ્રોવાઇડર કનેક્શન કાઢી નાખો અને ફરી ઉમેરો

### Kiro મલ્ટિ-એકાઉન્ટ: બીજું એકાઉન્ટ પ્રથમને અમાન્ય બનાવે છે

**કારણ:** Kiro નું બૅકએન્ડ દરેક OIDC ક્લાયન્ટ રજિસ્ટ્રેશન માટે માત્ર એક સક્રિય સત્ર લાગુ કરે છે.
જ્યારે બે એકાઉન્ટ એક જ રજિસ્ટર્ડ ક્લાયન્ટ શેર કરે છે (v3.8.0 પહેલાં ઇમ્પોર્ટ કરેલા કનેક્શન્સ),
ત્યારે એક એકાઉન્ટના ટોકનને રિફ્રેશ કરવાથી બીજા એકાઉન્ટનું રિફ્રેશ ટોકન અમાન્ય થઈ જાય છે.

**ઉકેલ (v3.8.0+):** અસરગ્રસ્ત કનેક્શન્સને ફરીથી ઇમ્પોર્ટ કરો.
v3.8.0 થી શરૂ કરીને, **Import Token**,
**Google/GitHub social login**, અથવા **Auto-Import** મારફતે બનાવવામાં આવેલું દરેક નવું Kiro કનેક્શન આપમેળે પોતાનું
સમર્પિત OIDC ક્લાયન્ટ રજિસ્ટર કરે છે. તેથી કનેક્શન સંપૂર્ણપણે અલગ રહે છે અને એક
એકાઉન્ટને રિફ્રેશ કરવાથી અન્ય કોઈ એકાઉન્ટ પર અસર થતી નથી.

v3.8.0 _પહેલાં_ ઇમ્પોર્ટ કરેલા કનેક્શન્સમાં દરેક કનેક્શન માટે અલગ ક્લાયન્ટ
રજિસ્ટ્રેશન હોતું નથી. તે કનેક્શન્સ શેર કરેલા social-auth રિફ્રેશ એન્ડપોઇન્ટનો ઉપયોગ કરવાનું ચાલુ રાખે છે.
અલગતા મેળવવા માટે, ડૅશબોર્ડ → પ્રોવાઇડર્સમાંથી જૂનું કનેક્શન કાઢી નાખો અને તેને
ત્રણમાંથી કોઈપણ ઇમ્પોર્ટ ફ્લો મારફતે ફરી ઉમેરો.

સંપૂર્ણ વિગતો અને બે Kiro એકાઉન્ટને સાથે-સાથે ઉમેરવા માટેની પગલું-દર-પગલું સૂચનાઓ માટે,
[`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md) જુઓ.

## ક્લાઉડ સમસ્યાઓ

### ક્લાઉડ સિંક ભૂલો

1. ખાતરી કરો કે `BASE_URL` તમારા ચાલી રહેલા ઇન્સ્ટન્સ તરફ નિર્દેશ કરે છે (દા.ત., `http://localhost:20128`)
2. ખાતરી કરો કે `CLOUD_URL` તમારા ક્લાઉડ એન્ડપોઇન્ટ તરફ નિર્દેશ કરે છે (દા.ત., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` મૂલ્યોને સર્વર-સાઇડ મૂલ્યો સાથે સુસંગત રાખો

### ક્લાઉડમાં `stream=false` 500 પરત કરે છે

**લક્ષણ:** નોન-સ્ટ્રીમિંગ કૉલ્સ માટે ક્લાઉડ એન્ડપોઇન્ટ પર `Unexpected token 'd'...`.

**કારણ:** ક્લાયન્ટ JSONની અપેક્ષા રાખે છે, જ્યારે અપસ્ટ્રીમ SSE પેલોડ પરત કરે છે.

**વૈકલ્પિક ઉપાય:** ક્લાઉડ પર સીધા કૉલ્સ માટે `stream=true` નો ઉપયોગ કરો. લોકલ રનટાઇમમાં SSE→JSON ફૉલબૅક સામેલ છે.

### ક્લાઉડ કનેક્ટેડ બતાવે છે પરંતુ "અમાન્ય API કી" કહે છે

1. લોકલ ડૅશબોર્ડ (`/api/keys`) પરથી નવી કી બનાવો
2. ક્લાઉડ સિંક ચલાવો: ક્લાઉડ સક્ષમ કરો → હમણાં સિંક કરો
3. જૂની/સિંક ન થયેલી કીઓ હજુ પણ ક્લાઉડ પર `401` પરત કરી શકે છે

## Docker સમસ્યાઓ

### Docker IPv6 / કનેક્શન રીસેટ

<a name="docker-ipv6"></a>

**લક્ષણો:** `curl http://localhost:20128/v1/models` ચલાવવાથી `curl: (56) Recv failure: Connection reset by peer` પરત મળે છે. ડૅશબોર્ડ અને પ્રમાણીકરણ વિનાના એન્ડપોઇન્ટ્સ કાર્ય કરે છે, પરંતુ પ્રમાણીકૃત એન્ડપોઇન્ટ્સ નિષ્ફળ જાય છે — આ પ્રમાણીકરણની સમસ્યા જેવી લાગે છે, પરંતુ હકીકતમાં એવી નથી.

**કારણ:** `docker run -p 20128:20128`, `0.0.0.0` (IPv4) અને `::` (IPv6) બંને પર પ્રકાશિત કરે છે, પરંતુ કન્ટેનરની અંદરની પ્રોસેસ માત્ર IPv4 પર સાંભળે છે. જે હોસ્ટ્સ પર `localhost` પહેલાં `::1` તરીકે રિઝોલ્વ થાય છે ત્યાં કનેક્શન IPv6 પર પ્રકાશિત પોર્ટ સુધી પહોંચે છે, પરંતુ તેની પાછળ કોઈ લિસનર હોતું નથી → કનેક્શન રીસેટ થાય છે.

**ઉકેલ:**

1. **ઝડપી નિદાન:** `curl -4 http://localhost:20128/v1/models` ચલાવો. જો તે `-4` સાથે કાર્ય કરે પરંતુ તેના વિના નિષ્ફળ જાય, તો IPv6 બાઇન્ડમાં અસંગતતા છે.
2. **કાયમી ઉકેલ:** તમારા `docker run` કમાન્ડમાં `-p 127.0.0.1:20128:20128` નો ઉપયોગ કરીને સ્પષ્ટપણે IPv4 સાથે બાઇન્ડ કરો:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   આ ફરજિયાત રીતે IPv4 બાઇન્ડનો ઉપયોગ કરાવે છે અને પ્રૉક્સીને હોસ્ટના તમામ ઇન્ટરફેસ પર ઉપલબ્ધ થતી અટકાવે છે.

## ડિબગિંગ

### લૉગ ફાઇલો સક્ષમ કરો

તમારી `.env` ફાઇલમાં `APP_LOG_TO_FILE=true` સેટ કરો. ઍપ્લિકેશન લૉગ્સ `logs/` હેઠળ લખવામાં આવે છે.
જ્યારે સેટિંગ્સમાં કૉલ લૉગ પાઇપલાઇન સક્ષમ હોય ત્યારે રિક્વેસ્ટ આર્ટિફેક્ટ્સ `${DATA_DIR}/call_logs/` હેઠળ સંગ્રહિત થાય છે.
જ્યારે પાઇપલાઇન કૅપ્ચર સક્ષમ હોય, ત્યારે સ્ટ્રીમ ચંક પેલોડ્સને બાકાત રાખવા માટે `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` સેટ કરો અથવા KBમાં આર્ટિફેક્ટ મર્યાદા બદલવા માટે `CALL_LOG_PIPELINE_MAX_SIZE_KB` સમાયોજિત કરો.

```bash
# હેલ્થ ડૅશબોર્ડ
http://localhost:20128/dashboard/health

# API હેલ્થ ચેક
curl http://localhost:20128/api/monitoring/health
```

### રનટાઇમ સ્ટોરેજ

- મુખ્ય સ્થિતિ: `${DATA_DIR}/storage.sqlite` (પ્રદાતાઓ, કૉમ્બો, ઉપનામો, કીઓ, સેટિંગ્સ)
- વપરાશ: `storage.sqlite` માં SQLite ટેબલ્સ (`usage_history`, `call_logs`, `proxy_logs`) + વૈકલ્પિક `${DATA_DIR}/call_logs/`
- ઍપ્લિકેશન લૉગ્સ: `<repo>/logs/...` (જ્યારે `APP_LOG_TO_FILE=true` હોય)
- કૉલ લૉગ આર્ટિફેક્ટ્સ: કૉલ લૉગ પાઇપલાઇન સક્ષમ હોય ત્યારે `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

રિક્વેસ્ટ લૉગ્સ પેજની **ઇતિહાસ સાફ કરો** ક્રિયા `call_logs`, જૂના
`request_detail_logs` અને લોકલ `${DATA_DIR}/call_logs/` આર્ટિફેક્ટ ડિરેક્ટરીને સાફ કરે છે.

## સર્કિટ બ્રેકર સંબંધિત સમસ્યાઓ

### પ્રદાતા OPEN સ્થિતિમાં અટવાયેલો છે

જ્યારે કોઈ પ્રદાતાનું સર્કિટ બ્રેકર OPEN હોય છે, ત્યારે કૂલડાઉન સમાપ્ત ન થાય ત્યાં સુધી વિનંતીઓ અવરોધિત રહે છે.

**ઉકેલ:**

1. **ડૅશબોર્ડ → સેટિંગ્સ → રેઝિલિયન્સ** પર જાઓ
2. અસરગ્રસ્ત પ્રદાતા માટેનું સર્કિટ બ્રેકર કાર્ડ તપાસો
3. બધા બ્રેકર સાફ કરવા માટે **બધા રીસેટ કરો** પર ક્લિક કરો અથવા કૂલડાઉન સમાપ્ત થાય ત્યાં સુધી રાહ જુઓ
4. રીસેટ કરતા પહેલાં ખાતરી કરો કે પ્રદાતા ખરેખર ઉપલબ્ધ છે

### પ્રદાતા વારંવાર સર્કિટ બ્રેકરને ટ્રિગર કરે છે

જો કોઈ પ્રદાતા વારંવાર OPEN સ્થિતિમાં જાય:

1. નિષ્ફળતાની પેટર્ન જોવા માટે **ડૅશબોર્ડ → હેલ્થ → પ્રદાતા હેલ્થ** તપાસો
2. **સેટિંગ્સ → રેઝિલિયન્સ → પ્રદાતા પ્રોફાઇલ્સ** પર જાઓ અને નિષ્ફળતાની થ્રેશોલ્ડ વધારો
3. તપાસો કે પ્રદાતાએ API મર્યાદાઓ બદલી છે કે ફરીથી પ્રમાણીકરણ જરૂરી છે
4. લેટન્સી ટેલિમેટ્રીની સમીક્ષા કરો — ઊંચી લેટન્સીને કારણે ટાઇમઆઉટ-આધારિત નિષ્ફળતાઓ થઈ શકે છે

## ઑડિયો ટ્રાન્સક્રિપ્શન સંબંધિત સમસ્યાઓ

### "અસમર્થિત મૉડલ" ભૂલ

- એવા મૉડલ IDનો ઉપયોગ કરો જેનો પ્રથમ સેગમેન્ટ એવો પ્રદાતા હોય જેના માટે તમારી પાસે ઓળખપત્રો છે (`openai/whisper-1`, `openrouter/deepgram/nova-3`). ફક્ત `deepgram/nova-3` માટે મૂળ Deepgram કી જરૂરી છે.
- ખાતરી કરો કે પ્રદાતા **ડૅશબોર્ડ → પ્રદાતાઓ**માં કનેક્ટ થયેલો છે

### ટ્રાન્સક્રિપ્શન ખાલી પરત કરે છે અથવા નિષ્ફળ જાય છે

- સમર્થિત ઑડિયો ફોર્મેટ તપાસો: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ખાતરી કરો કે ફાઇલનું કદ પ્રદાતાની મર્યાદામાં છે (સામાન્ય રીતે < 25MB)
- પ્રદાતા કાર્ડમાં પ્રદાતાની API કીની માન્યતા તપાસો

## ટ્રાન્સલેટર ડિબગિંગ

ફોર્મેટ ટ્રાન્સલેશન સંબંધિત સમસ્યાઓને ડિબગ કરવા માટે **ડૅશબોર્ડ → ટ્રાન્સલેટર**નો ઉપયોગ કરો:

| મોડ              | ક્યારે ઉપયોગ કરવો                                                                                               |
| ---------------- | --------------------------------------------------------------------------------------------------------------- |
| **પ્લેગ્રાઉન્ડ** | ઇનપુટ/આઉટપુટ ફોર્મેટની બાજુ-બાજુ સરખામણી કરો — ટ્રાન્સલેશન કેવી રીતે થાય છે તે જોવા નિષ્ફળ થતી વિનંતી પેસ્ટ કરો |
| **ચૅટ ટેસ્ટર**   | લાઇવ સંદેશાઓ મોકલો અને હેડર્સ સહિત સંપૂર્ણ વિનંતી/પ્રતિસાદ પેલોડ તપાસો                                          |
| **ટેસ્ટ બેન્ચ**  | કયા ટ્રાન્સલેશન બગડેલા છે તે શોધવા માટે વિવિધ ફોર્મેટ સંયોજનોમાં બૅચ ટેસ્ટ ચલાવો                                |
| **લાઇવ મોનિટર**  | વચ્ચે-વચ્ચે થતી ટ્રાન્સલેશન સમસ્યાઓ પકડવા માટે રિયલ-ટાઇમ વિનંતી પ્રવાહ જુઓ                                      |

### ફોર્મેટ સંબંધિત સામાન્ય સમસ્યાઓ

- **થિંકિંગ ટૅગ્સ દેખાતા નથી** — તપાસો કે લક્ષ્ય પ્રદાતા થિંકિંગને સમર્થન આપે છે કે નહીં અને થિંકિંગ બજેટ સેટિંગ પણ તપાસો
- **ટૂલ કૉલ્સ દૂર થઈ જાય છે** — કેટલાક ફોર્મેટ ટ્રાન્સલેશન અસમર્થિત ફીલ્ડ્સ દૂર કરી શકે છે; પ્લેગ્રાઉન્ડ મોડમાં ચકાસો
- **સિસ્ટમ પ્રૉમ્પ્ટ ગાયબ છે** — Claude અને Gemini સિસ્ટમ પ્રૉમ્પ્ટને અલગ રીતે સંભાળે છે; ટ્રાન્સલેશન આઉટપુટ તપાસો
- **SDK ઑબ્જેક્ટને બદલે રૉ સ્ટ્રિંગ પરત કરે છે** — v1.xમાં ઉકેલાયું છે; પ્રતિસાદ સૅનિટાઇઝર બિન-માનક ફીલ્ડ્સ (`x_groq`, `usage_breakdown`, વગેરે) દૂર કરે છે, જે OpenAI SDK Pydantic વૅલિડેશન નિષ્ફળતાઓનું કારણ બને છે. જો તમને હજુ પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને ઇશ્યૂ દાખલ કરો.
- **GLM/ERNIE `system` રોલને નકારે છે** — v1.xમાં ઉકેલાયું છે; રોલ નૉર્મલાઇઝર અસંગત મૉડલ્સ માટે સિસ્ટમ સંદેશાઓને આપમેળે વપરાશકર્તા સંદેશાઓમાં મર્જ કરે છે. જો તમને હજુ પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને ઇશ્યૂ દાખલ કરો.
- **`developer` રોલ ઓળખાતો નથી** — v1.xમાં ઉકેલાયું છે; બિન-OpenAI પ્રદાતાઓ માટે તેને આપમેળે `system`માં રૂપાંતરિત કરવામાં આવે છે. જો તમને હજુ પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને ઇશ્યૂ દાખલ કરો.
- **`json_schema` Gemini સાથે કામ કરતું નથી** — v1.xમાં ઉકેલાયું છે; હવે `response_format`ને Geminiના `responseMimeType` + `responseSchema`માં રૂપાંતરિત કરવામાં આવે છે. જો તમને હજુ પણ v3.x+ પર આ સમસ્યા દેખાય, તો કૃપા કરીને ઇશ્યૂ દાખલ કરો.

## સ્થિતિસ્થાપકતા સેટિંગ્સ

### સ્વચાલિત દર-મર્યાદા ટ્રિગર થતી નથી

- સ્વચાલિત દર-મર્યાદા ફક્ત API કી પ્રદાતાઓને લાગુ પડે છે (OAuth/સબ્સ્ક્રિપ્શનને નહીં)
- ખાતરી કરો કે **Settings → Resilience → Provider Profiles** માં સ્વચાલિત દર-મર્યાદા સક્ષમ છે
- પ્રદાતા `429` સ્થિતિ કોડ અથવા `Retry-After` હેડર પરત કરે છે કે નહીં તે તપાસો

### એક્સ્પોનેન્શિયલ બૅકઑફનું ટ્યુનિંગ

પ્રદાતા પ્રોફાઇલ્સ આ સેટિંગ્સને સપોર્ટ કરે છે:

- **મૂળ વિલંબ** — પ્રથમ નિષ્ફળતા પછીનો પ્રારંભિક પ્રતીક્ષા સમય (ડિફૉલ્ટ: 1s)
- **મહત્તમ વિલંબ** — મહત્તમ પ્રતીક્ષા સમયની મર્યાદા (ડિફૉલ્ટ: 30s)
- **ગુણક** — દરેક સળંગ નિષ્ફળતા દીઠ વિલંબ કેટલો વધારવો (ડિફૉલ્ટ: 2x)

### થન્ડરિંગ હર્ડ-વિરોધી સુરક્ષા

જ્યારે અનેક સમકાલીન વિનંતીઓ દર-મર્યાદિત પ્રદાતા સુધી પહોંચે છે, ત્યારે OmniRoute વિનંતીઓને ક્રમિક બનાવવા અને શ્રેણીબદ્ધ નિષ્ફળતાઓ અટકાવવા માટે મ્યુટેક્સ + સ્વચાલિત દર-મર્યાદાનો ઉપયોગ કરે છે. API કી પ્રદાતાઓ માટે આ સ્વચાલિત છે.

### ચેટ વિનંતીઓ 503 / chat_admission_busy સાથે નિષ્ફળ જાય છે

**લક્ષણો:**

- ચેટ કમ્પ્લીશન્સ એન્ડપોઇન્ટ ફરી પ્રયાસ કરી શકાય તેવો `503` પ્રતિસાદ પરત કરે છે, જેનો ભૂલ કોડ
  `chat_admission_busy` છે.
- પ્રતિસાદમાં `Retry-After` સામેલ હોય છે. #12135 પછીથી તેનું મૂલ્ય અવલોકિત
  ઑક્યુપન્સી પરથી મેળવવામાં આવે છે — વિનંતીએ પહેલેથી રાહ જોયેલી `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` વિન્ડો
  અને હાલની હેવીવેઇટ લીઝ જેટલા સમયથી ધારણ કરાયેલી છે તેમાંથી મોટું મૂલ્ય — પૂર્ણ
  સેકન્ડ સુધી ઉપર તરફ ગોળ કરીને અને 60 સુધી મર્યાદિત કરીને. નિષ્ક્રિય ગેટ પર તે ઐતિહાસિક ન્યૂનતમ જાળવે છે:
  બાઇટ-આધારિત પાથ પર 2 સેકન્ડ, સ્ટ્રક્ચર-આધારિત પાથ પર 1 સેકન્ડ (જેમાં
  `reason: "structure_limit"` પણ સામેલ છે).
- બીજી કોઈ હેવીવેઇટ ચેટ અથવા લાંબા સમયથી ચાલી રહેલો સ્ટ્રીમિંગ પ્રતિસાદ હજુ
  પ્રક્રિયામાં હોય ત્યારે આવું થઈ શકે છે.

બાઇટ-આધારિત પ્રતિસાદ બોડી આ છે:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

સ્ટ્રક્ચર-આધારિત પ્રતિસાદ સમાન પ્રકાર અને કોડનો ઉપયોગ કરે છે, જેમાં સંદેશ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
અને `reason: "structure_limit"` હોય છે.
ડિફૉલ્ટ થ્રેશોલ્ડ પર, વિનંતીમાં ઓછામાં ઓછા `200` સંદેશા,
ઓછામાં ઓછા `64` ટૂલ્સ અથવા ઓછામાં ઓછા `32,000` અંદાજિત ટોકન્સ હોય, અથવા મર્યાદિત સ્ટ્રક્ચર અંદાજન
`10,000` મુલાકાત લેવાયેલા નોડ્સ અથવા ઊંડાઈ `12` ની મર્યાદા વટાવે, ત્યારે વિનંતી સ્ટ્રક્ચરની દૃષ્ટિએ હેવી ગણાય છે.

**કારણ:** આ OmniRoute ની અંદર ઇરાદાપૂર્વકનું લોડ શેડિંગ છે, અપસ્ટ્રીમ-પ્રદાતાની નિષ્ફળતા નહીં.
દરેક પ્રોસેસ મોટા વિનંતી બોડીને જાળવી રાખવા અને પાર્સ કરવા પહેલાં મર્યાદિત હેવીવેઇટ ક્ષમતા આરક્ષિત
કરવા માટે પ્રોસેસ-સ્થાનિક ગાર્ડનો ઉપયોગ કરે છે. હેવીવેઇટ લીઝ SSE
પ્રતિસાદના સમગ્ર જીવનકાળ સુધી ધારણ કરાયેલી રહે છે.

**#503-ફેનઆઉટ:** આ સુધારા પહેલાં, ગાર્ડ હોસ્ટ મેમરીને ધ્યાનમાં લીધા વિના સમકાલીનતાને વિનંતીઓની નિશ્ચિત સંખ્યા
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ડિફૉલ્ટ `1`) સુધી મર્યાદિત કરતો હતો, તેથી કોડિંગ-એજન્ટ
ફેન-આઉટ (અનેક સબએજન્ટ્સ/CLIs, સામાન્ય રીતે > 256 KB બોડીઓ) અસરકારક રીતે
~1 ની સમકાલીનતા સુધી ઘટી જતું અને સંપૂર્ણપણે સામાન્ય લોડ હેઠળ 503 આપતું હતું. હવે ગાર્ડ સ્વયં-ટ્યુન થાય છે: તેને
પ્રોસેસની વાસ્તવિક મેમરી મર્યાદા પરથી કદ નક્કી કરાયેલા, આપમેળે મેળવેલા ઇન્જેસ્ટ બાઇટ બજેટ
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) દ્વારા નિયંત્રિત કરવામાં આવે છે, અને તે જીવંત રિસોર્સ-પ્રેશર સિગ્નલનો પણ
સંદર્ભ લે છે — તેથી તે માત્ર ત્યારે જ લોડ ઘટાડે છે જ્યારે હોસ્ટ ખરેખર મેમરી દબાણ હેઠળ હોય, માત્ર એકથી વધુ
હેવી વિનંતીઓ એકસાથે આવી હોવાને કારણે નહીં. જૂની ગણતરી મર્યાદા (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)નું
હજુ પણ પાલન થાય છે, પરંતુ ફક્ત ત્યારે જ્યારે તમે તેને સ્પષ્ટ રીતે સેટ કરો.

જ્યારે ક્ષમતા વ્યસ્ત હોય, ત્યારે હેવીવેઇટ વિનંતી ફરી પ્રયાસ કરી શકાય તેવો `503` પ્રતિસાદ
આપતાં પહેલાં સ્લોટ ખાલી થવા માટે પ્રથમ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ડિફૉલ્ટ `2000`, `0` પ્રતીક્ષા અક્ષમ કરે છે) સુધી રાહ જુએ છે.
આ મર્યાદિત પ્રતીક્ષા એટલા માટે છે કે એજન્ટ-શૈલીના ક્લાયન્ટ્સ
(OpenCode, Claude Code, Cursor), જે હેવી પેટા-વિનંતીઓને સમકાલીન રીતે ફેન-આઉટ કરે છે, તાત્કાલિક અસ્વીકારો પર
તેમનું આખું પુનઃપ્રયાસ બજેટ વાપરી નાખવા અને કાર્યની વચ્ચે નિષ્ફળ જવાને બદલે બર્સ્ટને ક્રમિક બનાવે.
વર્તમાન હેવીવેઇટ લીઝ ઑક્યુપન્સી, નિર્ધારિત બાઇટ બજેટ અને જીવંત દબાણની ગંભીરતા
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) પર દર્શાવવામાં આવે છે — કોઈપણ env var બદલતા પહેલાં આ તપાસો.
Settings → Resilience → Request Queue → Concurrent Requests આને નિયંત્રિત કરતું નથી; તે સેટિંગ
અલગ પ્રદાતા વિનંતી-કતાર મિકેનિઝમને નિયંત્રિત કરે છે.

**ઉકેલ:**

1. પહેલાં ફરી પ્રયાસ કરો. ક્લાયન્ટ્સે વિનંતીને તરત જ
   પુનરાવર્તિત કરવાને બદલે `Retry-After` નું પાલન કરવું અને બૅકઑફનો ઉપયોગ કરવો જોઈએ.
2. કંઈપણ ટ્યુન કરતાં પહેલાં `/api/monitoring/health` → `chatAdmission` તપાસો. `countCapEnabled:
false` અને ઉદાર `maxInflightBytes` નો અર્થ એ છે કે આપમેળે મેળવેલું બજેટ પહેલેથી જ તેનું
   કામ કરી રહ્યું છે; `high`/`critical` `pressureSeverity` નો અર્થ એ છે કે હોસ્ટ પાસે ખરેખર ઓછી મેમરી છે —
   તેને એડમિશન env var દ્વારા સુધારી શકાતું નથી, તેના માટે વધુ RAM અથવા નાનું વર્કલોડ જરૂરી છે.
3. ફક્ત ત્યારે જ જ્યારે `/api/monitoring/health` દર્શાવે કે આપમેળે મેળવેલું બજેટ તમારા હોસ્ટ માટે
   ખરેખર ખૂબ નાનું છે (દુર્લભ — તે પહેલેથી જ કન્ટેનરથી બેર-મેટલ સુધી સ્કેલ થાય છે), લેગસી વિનંતી-ગણતરી મર્યાદા પર પાછા જવાને બદલે
   તેને સીધું `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` વડે ઓવરરાઇડ કરો.

અધિકૃત એડમિશન સેટિંગ્સ માટે [એન્વાયરમેન્ટ-વેરિએબલ સંદર્ભ](../reference/ENVIRONMENT.md#4-security--authentication)
જુઓ.

## વૈકલ્પિક RAG / LLM નિષ્ફળતા વર્ગીકરણ (16 સમસ્યાઓ)

કેટલાક OmniRoute વપરાશકર્તાઓ ગેટવેને RAG અથવા એજન્ટ સ્ટૅક્સની આગળ મૂકે છે. આવા સેટઅપમાં એક વિચિત્ર પેટર્ન સામાન્ય રીતે જોવા મળે છે: OmniRoute સ્વસ્થ દેખાય છે (પ્રદાતાઓ કાર્યરત, રાઉટિંગ પ્રોફાઇલ્સ બરાબર, કોઈ રેટ લિમિટ ચેતવણીઓ નહીં), પરંતુ અંતિમ જવાબ હજી પણ ખોટો હોય છે.

વ્યવહારમાં, આવી ઘટનાઓ સામાન્ય રીતે ગેટવેમાંથી નહીં પરંતુ ડાઉનસ્ટ્રીમ RAG પાઇપલાઇનમાંથી ઉદ્ભવે છે.

જો તમે આવી નિષ્ફળતાઓનું વર્ણન કરવા માટે સહિયારી શબ્દાવલી ઇચ્છતા હો, તો તમે WFGY ProblemMapનો ઉપયોગ કરી શકો છો. આ એક બાહ્ય MIT લાઇસન્સ ધરાવતું ટેક્સ્ટ સંસાધન છે, જે વારંવાર જોવા મળતી સોળ RAG / LLM નિષ્ફળતા પેટર્ન વ્યાખ્યાયિત કરે છે. ઉચ્ચ સ્તરે તેમાં આ બાબતો આવરી લેવાય છે:

- રિટ્રીવલ ડ્રિફ્ટ અને તૂટેલી કન્ટેક્સ્ટ સીમાઓ
- ખાલી અથવા જૂના ઇન્ડેક્સ અને વેક્ટર સ્ટોર્સ
- એમ્બેડિંગ અને સિમેન્ટિક વચ્ચેની અસંગતતા
- પ્રોમ્પ્ટ એસેમ્બલી અને કન્ટેક્સ્ટ વિન્ડોની સમસ્યાઓ
- લોજિકનું પતન અને અતિ આત્મવિશ્વાસભર્યા જવાબો
- લાંબી ચેઇન અને એજન્ટ સંકલનની નિષ્ફળતાઓ
- મલ્ટિ-એજન્ટ મેમરી અને ભૂમિકામાં ડ્રિફ્ટ
- ડિપ્લોયમેન્ટ અને બૂટસ્ટ્રૅપ ક્રમની સમસ્યાઓ

વિચાર સરળ છે:

1. જ્યારે તમે કોઈ ખરાબ પ્રતિસાદની તપાસ કરો, ત્યારે આ માહિતી નોંધો:
   - વપરાશકર્તાનું કાર્ય અને વિનંતી
   - OmniRouteમાં રાઉટ અથવા પ્રદાતા કોમ્બો
   - ડાઉનસ્ટ્રીમમાં ઉપયોગમાં લેવાયેલ કોઈપણ RAG કન્ટેક્સ્ટ (પ્રાપ્ત કરેલા દસ્તાવેજો, ટૂલ કૉલ્સ વગેરે)
2. ઘટનાને એક અથવા બે WFGY ProblemMap નંબરો (`No.1` … `No.16`) સાથે મેપ કરો.
3. તે નંબરને OmniRoute લૉગ્સની બાજુમાં તમારા પોતાના ડૅશબોર્ડ, રનબુક અથવા ઇન્સિડન્ટ ટ્રૅકરમાં સંગ્રહો.
4. તમારે તમારા RAG સ્ટૅક, રિટ્રીવર અથવા રાઉટિંગ વ્યૂહરચનામાં ફેરફાર કરવાની જરૂર છે કે નહીં તે નક્કી કરવા માટે સંબંધિત WFGY પૃષ્ઠનો ઉપયોગ કરો.

સંપૂર્ણ લખાણ અને ચોક્કસ રીતો અહીં ઉપલબ્ધ છે (MIT લાઇસન્સ, માત્ર ટેક્સ્ટ):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

જો તમે OmniRouteની પાછળ RAG અથવા એજન્ટ પાઇપલાઇન્સ ચલાવતા ન હો, તો તમે આ વિભાગને અવગણી શકો છો.

## v3.8.0ની જાણીતી સમસ્યાઓ

v3.8.0 રિલીઝને લગતી વિશિષ્ટ સમસ્યાઓ અને તેમના વર્તમાન ઉપાયો. જો પછીના પૅચમાં સુધારો સામેલ થાય, તો એન્ટ્રી અપડેટ કરવામાં આવશે અથવા દૂર કરવામાં આવશે.

### Devin CLI પ્રમાણીકરણ નિષ્ફળતાઓ

**લક્ષણો:**

- Devin-આધારિત ટૂલ્સનો ઉપયોગ કરતી વખતે "Devin CLI મળ્યું નથી" અથવા "પ્રમાણીકરણ નિષ્ફળ થયું"
- CLI રનટાઇમ તપાસ `installed=false` દર્શાવે છે

**કારણો:**

- `CLI_DEVIN_BIN` એવા પાથ તરફ નિર્દેશ કરે છે જે અસ્તિત્વમાં નથી
- હોસ્ટ પર Devin CLI ઇન્સ્ટોલ કરેલું નથી

**ઉકેલ:**

1. તમારા પ્લેટફોર્મ માટે Devin CLI ઇન્સ્ટોલ કરો
2. `.env`માં `CLI_DEVIN_BIN=/usr/local/bin/devin` (અથવા વાસ્તવિક પાથ) સેટ કરો
3. OmniRouteને પુનઃપ્રારંભ કરો અને **ડૅશબોર્ડ → CLI ટૂલ્સ** પરથી ફરી પરીક્ષણ કરો

- **ડૅશબોર્ડ:** **સેટિંગ્સ → મોડલ કૂલડાઉન્સ** → અસરગ્રસ્ત કાર્ડ પર **ફરી સક્ષમ કરો** ક્લિક કરો
- **API:** મેનેજમેન્ટ પ્રમાણીકરણ હેડર્સ સાથે `DELETE /api/resilience/model-cooldowns`

### Command Code પ્રદાતાનું કનેક્શન 403 સાથે નિષ્ફળ થાય છે

**લક્ષણો:**

- Command Code પ્રદાતાના કનેક્શનનું પરીક્ષણ કરતી વખતે 403
- નવું ઉમેર્યા પછી પ્રદાતા કાર્ડ "અનધિકૃત" દર્શાવે છે

**કારણ:** OAuth પ્રવાહ પૂર્ણ થયો નહોતો (કૉલબૅક પ્રાપ્ત થયો નહોતો અથવા ટોકન સાચવવામાં આવ્યું નહોતું).

**ઉકેલ:**

- OAuth પ્રવાહ ફરી શરૂ કરવા માટે CLIમાંથી `omniroute providers` ચલાવો, અથવા
- **ડૅશબોર્ડ → પ્રદાતાઓ → Command Code → ફરી કનેક્ટ કરો** પરથી OAuth ફરી ચલાવો

### ModelScope આક્રમક 429 કૂલડાઉન્સ પરત કરે છે

**લક્ષણો:**

- વિનંતીઓના નાના બર્સ્ટ પછી ModelScope પર અત્યંત ટૂંકા અથવા તાત્કાલિક કૂલડાઉન્સ
- કોમ્બો રાઉટિંગ અપેક્ષા કરતાં વહેલું ModelScopeને અવગણે છે

**કારણ:** ModelScope પ્રદાતા-વિશિષ્ટ `Retry-After` હેડર્સ મોકલે છે. v3.8.0માં આ હેડર્સ માટે વિશિષ્ટ હૅન્ડલિંગ સામેલ છે, તેથી જૂના વર્ઝન્સ તેમને સામાન્ય રેટ-લિમિટ સંકેતો તરીકે ખોટી રીતે વાંચે છે.

**ઉકેલ:**

- ખાતરી કરો કે તમે v3.8.0 અથવા તે પછીના વર્ઝન પર છો
- **સેટિંગ્સ → રેઝિલિયન્સ** હેઠળ `useUpstream429BreakerHints` ટૉગલ સક્ષમ છે કે નહીં તે ચકાસો

### પ્રોડક્શનમાં OMNIROUTE_WS_BRIDGE_SECRET ગેરહાજર છે

**લક્ષણો:**

- રિમોટ પ્રોડક્શન હોસ્ટ પર ચલાવતી વખતે દરેક Codex/Responses WebSocket બ્રિજ વિનંતી પર 401
- કનેક્ટ થયા પછી તરત જ WebSocket બ્રિજ હૅન્ડશેક બંધ થઈ જાય છે

**કારણ:** પ્રોડક્શન એન્વાયર્નમેન્ટમાંથી `OMNIROUTE_WS_BRIDGE_SECRET` એન્વાયરમેન્ટ વેરિએબલ ગેરહાજર છે.

**ઉકેલ:**

1. રૅન્ડમ સિક્રેટ જનરેટ કરો: `openssl rand -hex 32`
2. પ્રોડક્શન સર્વર એન્વાયર્નમેન્ટમાં (અને બ્રિજ સાથે સંવાદ કરતા કોઈપણ ક્લાયન્ટમાં) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` સેટ કરો
3. OmniRouteને પુનઃપ્રારંભ કરો

### Responses API: બૅકગ્રાઉન્ડ મોડ સિંક્રોનસ મોડમાં ડિગ્રેડ થયો

**લક્ષણો:**

- લૉગ થયેલી ચેતવણી: `background mode degraded to synchronous`
- `background: true` વિનંતી બૅકગ્રાઉન્ડ જૉબ હૅન્ડલને બદલે સામાન્ય સિંક્રોનસ પ્રતિસાદ પરત કરે છે

**કારણ:** v3.8.0માં Responses API પર `background: true`ને ઇરાદાપૂર્વક સિંક્રોનસ એક્ઝિક્યુશનમાં ડિગ્રેડ કરવામાં આવે છે અને સાથે ચેતવણી પણ મોકલવામાં આવે છે. સંપૂર્ણ અસિંક્રોનસ બૅકગ્રાઉન્ડ એક્ઝિક્યુશન ભવિષ્યમાં ઉપલબ્ધ કરાવવાનું છે.

**ઉકેલ:**

- ક્લાયન્ટને `background` વિના કૉલ કરવા માટે સમાયોજિત કરો, અથવા
- સંપૂર્ણ અસિંક્રોનસ બૅકગ્રાઉન્ડ મોડ ધરાવતી પછીની રિલીઝની રાહ જુઓ (ચેન્જલૉગ અનુસરો)

## ધીમું સ્ટાર્ટઅપ / તૈયારી સમયસમાપ્તિ

જો CLI `⚠ Server did not respond within 60s` પ્રિન્ટ કરે, પરંતુ સર્વર
વાસ્તવમાં કાર્યરત હોય, તો તમારા પર્યાવરણ માટે તૈયારી પ્રોબનું સમય-બજેટ ખૂબ ઓછું છે.

આ સામાન્ય રીતે Windows પર (એન્ટિવાયરસ, ફાઇલસિસ્ટમ વૉચર્સ) અથવા ભારે સ્ટાર્ટઅપ
વર્કલોડ ધરાવતા કન્ટેનર્સમાં થાય છે.

**ઉકેલ — સમય-બજેટ વધારો:**

```bash
# એન્વાયરમેન્ટ વેરિએબલ દ્વારા (સ્ટાર્ટ્સ વચ્ચે જળવાઈ રહે છે):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 મિનિટ
omniroute serve

# CLI ફ્લૅગ દ્વારા (એક વખત માટે):
omniroute serve --ready-timeout 180000
```

ડિફૉલ્ટ 60 000 ms (60 s) છે. ચેતવણી માત્ર માહિતી માટે છે; સર્વર
બૅકગ્રાઉન્ડમાં શરૂ થવાનું ચાલુ રાખે છે અને બૂટ પૂર્ણ થયા પછી ઍક્સેસ કરી શકાશે.

`OMNIROUTE_READY_TIMEOUT_MS` વિશેની સંપૂર્ણ વિગતો માટે
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) જુઓ.
