આ માર્ગદર્શિકા OmniRouteમાં Kiro (AWS દ્વારા હોસ્ટ કરાયેલ AI કોડિંગ સહાયક) એકાઉન્ટ ઉમેરવાની પ્રક્રિયા આવરી લે છે,
જેમાં સેશન વચ્ચે કોઈ સંઘર્ષ વિના એકસાથે અનેક એકાઉન્ટ ચલાવવા પર વિશેષ ધ્યાન આપવામાં આવ્યું છે.

---

## પૃષ્ઠભૂમિ: Kiro એકાઉન્ટ વચ્ચે સંઘર્ષ કેમ થઈ શકે છે

Kiroનું બેકએન્ડ સક્રિય સેશનને ટ્રૅક કરવા માટે AWS SSO OIDC ક્લાયન્ટ રજિસ્ટ્રેશનનો ઉપયોગ કરે છે.
મહત્ત્વપૂર્ણ મર્યાદા: **દરેક OIDC ક્લાયન્ટ રજિસ્ટ્રેશન એક સમયે માત્ર એક સક્રિય
સેશનને સપોર્ટ કરે છે**. જ્યારે બીજું ડિવાઇસ અથવા વપરાશકર્તા એ જ રજિસ્ટર્ડ
ક્લાયન્ટનો ઉપયોગ કરીને પ્રમાણિત થાય છે, ત્યારે બેકએન્ડ પ્રથમ એકાઉન્ટના રિફ્રેશ ટોકનને અમાન્ય કરે છે.

આ એ જ પદ્ધતિ છે જે પહેલેથી અન્ય Kiro એકાઉન્ટમાં સાઇન ઇન કરેલ હોય તેવા
મશીન પર `kiro-cli login` ચલાવતી વખતે સમસ્યાઓ ઊભી કરે છે — નવું લૉગિન
પ્રથમ એકાઉન્ટના ટોકનને રદ કરે છે.

## OmniRoute આ સમસ્યા કેવી રીતે ઉકેલે છે (v3.8.0+)

v3.8.0થી શરૂ કરીને, OmniRoute દરેક Kiro કનેક્શન ઇમ્પોર્ટ દરમિયાન
`registerClient()` (AWS SSO OIDC)ને કૉલ કરે છે. આ દરેક OmniRoute કનેક્શનને તેનું પોતાનું સમર્પિત OIDC
ક્લાયન્ટ રજિસ્ટ્રેશન આપે છે. દરેક ક્લાયન્ટ રજિસ્ટ્રેશન સ્વતંત્ર હોવાથી, એક એકાઉન્ટને રિફ્રેશ કરવાથી અથવા
ફરીથી પ્રમાણિત કરવાથી અન્ય કોઈ એકાઉન્ટના રિફ્રેશ ટોકન પર અસર થતી નથી.

આ અલગીકરણ રિફ્રેશ-ટોકન ઇમ્પોર્ટ પદ્ધતિઓ પર લાગુ થાય છે, અને API-key પ્રમાણીકરણ
OIDC રિફ્રેશ સેશનને સંપૂર્ણપણે ટાળે છે:

| ઇમ્પોર્ટ પદ્ધતિ                                       | અલગીકરણની સ્થિતિ                                                                      |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------- |
| AWS Builder ID / IDC ડિવાઇસ-કોડ ફ્લો                  | ડિવાઇસ-કોડ ફ્લો રજૂ થયો ત્યારથી અલગ                                                   |
| **ટોકન ઇમ્પોર્ટ કરો** (રિફ્રેશ ટોકન જાતે પેસ્ટ કરવું) | v3.8.0થી અલગ                                                                          |
| **Google / GitHub સોશિયલ લૉગિન**                      | v3.8.0થી અલગ                                                                          |
| **ઑટો-ઇમ્પોર્ટ** (kiro-cli SQLite)                    | v3.8.0થી અલગ (SQLite પાથ પહેલેથી જ અલગ હતો; SSO-cache ફૉલબૅક પણ હવે અલગ છે)           |
| **API Key** (લાંબા સમય સુધી માન્ય CodeWhisperer કી)   | કોઈ રિફ્રેશ સેશન નથી; કી ચકાસવામાં આવે છે અને બેરર ક્રેડેન્શિયલ તરીકે સંગ્રહિત થાય છે |

## v3.8.0 પહેલાં બનાવેલ કનેક્શન માટે માઇગ્રેશન નોંધ

v3.8.0 પહેલાં ઇમ્પોર્ટ કરાયેલ કનેક્શનમાં `providerSpecificData`માં
સમર્પિત OIDC ક્લાયન્ટ રજિસ્ટ્રેશન સંગ્રહિત હોતું નથી. આ કનેક્શન કાર્ય કરવાનું ચાલુ રાખે છે, પરંતુ સહિયારા
સોશિયલ-ઑથ રિફ્રેશ એન્ડપોઇન્ટનો ઉપયોગ કરે છે, જેનો અર્થ એ છે કે આવા બે કનેક્શન હજી પણ એકબીજાને
અમાન્ય કરી શકે છે.

**અલગીકરણ મેળવવા માટે:** **ડૅશબોર્ડ → પ્રોવાઇડર્સ**માંથી જૂનું કનેક્શન કાઢી નાખો અને
સમર્થિત ઇમ્પોર્ટ ફ્લોમાંથી કોઈ એકનો ઉપયોગ કરીને તેને ફરીથી ઇમ્પોર્ટ કરો. નવા બનાવવામાં આવતા તમામ કનેક્શનને
આપમેળે તેમનું પોતાનું ક્લાયન્ટ રજિસ્ટ્રેશન મળશે.

## બે Kiro એકાઉન્ટને બાજુબાજુ ઉમેરવા

### પૂર્વજરૂરિયાતો

- OmniRoute v3.8.0 અથવા ત્યાર પછીનું વર્ઝન.
- કાર્યરત Kiro એકાઉન્ટ (ઇમેઇલ + પાસવર્ડ, Google અથવા GitHub લૉગિન).
- વૈકલ્પિક રીતે બીજું Kiro એકાઉન્ટ.

### પગલું 1: પ્રથમ એકાઉન્ટ ઇમ્પોર્ટ કરો

1. **ડૅશબોર્ડ → પ્રોવાઇડર્સ → પ્રોવાઇડર ઉમેરો → Kiro** ખોલો.
2. નીચેનામાંથી એક પસંદ કરો:
   - **ટોકન ઇમ્પોર્ટ કરો** — `aorAAAAAG`થી શરૂ થતું રિફ્રેશ ટોકન પેસ્ટ કરો.
   - **API Key** — લાંબા સમય સુધી માન્ય Kiro / CodeWhisperer API કી પેસ્ટ કરો.
   - **Google / GitHub લૉગિન** — બ્રાઉઝરમાં OAuth ફ્લો પૂર્ણ કરો.
   - **ઑટો-ઇમ્પોર્ટ** — બટન પર ક્લિક કરો; OmniRoute સ્થાનિક kiro-cli ડેટાબેઝ અથવા
     `~/.aws/sso/cache`માંથી ક્રેડેન્શિયલ વાંચે છે.
3. કનેક્શન સંગ્રહિત થાય છે. રિફ્રેશ-ટોકન ફ્લો આપમેળે સમર્પિત
   OIDC ક્લાયન્ટ રજિસ્ટર કરે છે. API-key ફ્લો AWS સાથે કીને માન્ય કરે છે અને રિફ્રેશ ટોકન સંગ્રહિત કરતા નથી.

### પગલું 2: બીજું એકાઉન્ટ ઇમ્પોર્ટ કરો

બીજા એકાઉન્ટ માટે પગલું 1નું પુનરાવર્તન કરો. દરેક ઇમ્પોર્ટ એક અલગ OIDC
ક્લાયન્ટ રજિસ્ટ્રેશન બનાવે છે, તેથી બંને કનેક્શન સંપૂર્ણપણે અલગ રહે છે.

### પગલું 3: બંને કનેક્શન સક્રિય છે તેની ચકાસણી કરો

1. **ડૅશબોર્ડ → પ્રોવાઇડર્સ** — બંને Kiro કનેક્શને **સક્રિય** સ્થિતિ દર્શાવવી જોઈએ.
2. **ડૅશબોર્ડ → હેલ્થ** — બંને કનેક્શને તેમની ટોકન હેલ્થ તપાસ પાસ કરવી જોઈએ.

### પગલું 4: એકાઉન્ટ વચ્ચે રૂટ કરવા માટે કૉમ્બોનો ઉપયોગ કરો

બંને કનેક્શનને ટાર્ગેટ તરીકે રાખીને તેમની વચ્ચે લોડ-બૅલેન્સ કરવા અથવા ફૉલબૅક માટે કૉમ્બો બનાવો:

```
kiro/kiro-dev → kiro/kiro-pro
```

કૉમ્બો કૉન્ફિગરેશન માટે [FEATURES.md](./FEATURES.md) અને રૂટિંગ દસ્તાવેજીકરણ જુઓ.

## એન્ટરપ્રાઇઝ / IDC વપરાશકર્તાઓ

AWS IAM Identity Center (IDC) એકાઉન્ટ્સ માટે, **Dashboard → Providers → Kiro → Device Code**માંથી **AWS Builder ID / IDC device-code** ફ્લોનો ઉપયોગ કરો. device-code ફ્લો હંમેશાં સંપૂર્ણપણે અલગ રાખવામાં આવ્યો છે. આ કનેક્શન્સ માટે ફરીથી ઇમ્પોર્ટ કરવાની જરૂર નથી.

જે એન્ટરપ્રાઇઝ વપરાશકર્તાઓ ડિફૉલ્ટ સિવાયના AWS રીજનમાં કાર્ય કરે છે, તેઓ Import Token API મારફતે ઇમ્પોર્ટ કરતી વખતે રીજન નિર્દિષ્ટ કરી શકે છે:

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

`region` ફીલ્ડ આપ્યું ન હોય ત્યારે તેનું ડિફૉલ્ટ મૂલ્ય `us-east-1` હોય છે.

## API-Key ઇમ્પોર્ટ ફ્લો

API-key પ્રમાણીકરણ લાંબા સમય સુધી માન્ય રહેતાં Kiro / AWS CodeWhisperer bearer ક્રેડેન્શિયલ્સ માટે છે. તે OAuth રિફ્રેશનો ઉપયોગ કરતું નથી, તેથી તે શેર કરેલા OIDC સેશનના અમાન્યીકરણને ટાળે છે.

### ડૅશબોર્ડ

1. **Dashboard -> Providers -> Kiro** ખોલો.
2. **API Key** પસંદ કરો.
3. API key અને વૈકલ્પિક AWS રીજન પેસ્ટ કરો (ડિફૉલ્ટ રૂપે `us-east-1`).
4. OmniRoute keyને માન્ય કરે છે અને કનેક્શન સાચવે છે.

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### આંતરિક કરાર

API રૂટ `KiroService.validateApiKey()`ને કૉલ કરીને keyને માન્ય કરે છે, જે રીજનને અનુરૂપ CodeWhisperer/Amazon Q એન્ડપોઇન્ટ સામે `ListAvailableProfiles`નો ઉપયોગ કરે છે અને `profileArn` નક્કી કરે છે.

સાચવેલું કનેક્શન આનો ઉપયોગ કરે છે:

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

રનટાઇમ દરમિયાન, `KiroExecutor.buildHeaders()` keyને `Authorization: Bearer <key>` તરીકે મોકલે છે અને `tokentype: API_KEY` ઉમેરે છે. ક્વોટા/પ્રોફાઇલ કૉલ્સ પણ એ જ માર્કરનો ઉપયોગ કરે છે, જેથી AWS bearerને OIDC અથવા સોશિયલ ઍક્સેસ ટોકનને બદલે લાંબા સમય સુધી માન્ય રહેતી API key તરીકે ગણે છે.

## OIDC ક્લાયન્ટની સમાપ્તિ

AWS SSO OIDC પબ્લિક ક્લાયન્ટ્સ સામાન્ય રીતે 90 દિવસ પછી સમાપ્ત થાય છે (`clientSecretExpiresAt`). અવલોકનક્ષમતા માટે OmniRoute આ ટાઇમસ્ટૅમ્પને `providerSpecificData`માં સંગ્રહિત કરે છે. જો કોઈ કનેક્શન ~90 દિવસ પછી રિફ્રેશ થવાનું બંધ કરે, તો નવું OIDC ક્લાયન્ટ રજિસ્ટ્રેશન મેળવવા માટે કનેક્શનને ફરીથી ઇમ્પોર્ટ કરો. સમાપ્તિ પછી આપમેળે ફરીથી રજિસ્ટ્રેશન કરવાનું ભાવિ સુધારા તરીકે ટ્રૅક કરવામાં આવે છે.

API-key કનેક્શન્સમાં OIDC ક્લાયન્ટ સમાપ્તિ હોતી નથી, કારણ કે તેઓ AWS SSO OIDC મારફતે રિફ્રેશ થતા નથી.

## સમસ્યા નિવારણ

### બીજું એકાઉન્ટ વારંવાર લૉગ આઉટ થઈ જાય છે

- **Dashboard → Providers**માં બંને કનેક્શન્સ તપાસો અને ખાતરી કરો કે દરેકના raw JSONમાં non-null `clientId` દેખાય છે (info icon મારફતે જોઈ શકાય છે). જો કોઈપણ કનેક્શનમાં `clientId` ન હોય, તો તે v3.8.0 પહેલાં ઇમ્પોર્ટ કરવામાં આવ્યું હતું — તેને ફરીથી ઇમ્પોર્ટ કરો.

### "Token validation failed" સાથે ઇમ્પોર્ટ નિષ્ફળ જાય છે

- ખાતરી કરો કે refresh token `aorAAAAAG`થી શરૂ થાય છે.
- ખાતરી કરો કે OmniRoute `https://oidc.us-east-1.amazonaws.com` (અથવા કૉન્ફિગર કરેલા રીજન) સુધી પહોંચી શકે છે. જો તમે કૉર્પોરેટ પ્રૉક્સીની પાછળ હો, તો **Dashboard → Settings → Proxies**માં provider-level પ્રૉક્સી સેટ કરો.

### API-key ઇમ્પોર્ટ નિષ્ફળ જાય છે

- ખાતરી કરો કે key Kiro / CodeWhisperer API key છે, refresh token નહીં.
- ખાતરી કરો કે AWS રીજન key/એકાઉન્ટ સાથે મેળ ખાય છે. `us-east-1` ડિફૉલ્ટ છે.
- key `ListAvailableProfiles`ને કૉલ કરી શકે તેવી હોવી જરૂરી છે; નહીં તો OmniRoute આવશ્યક `profileArn` નક્કી કરી શકશે નહીં.

અન્ય સમસ્યાઓ માટે, મુખ્ય [TROUBLESHOOTING.md](./TROUBLESHOOTING.md) જુઓ.
