## npm Trusted Publishing (v3.8.51થી ડિફૉલ્ટ) — વિનંતી પર staged, fallback તરીકે direct

`npm-publish.yml` ડિફૉલ્ટ રૂપે **npm Trusted Publishing (OIDC)** મારફતે publish કરે છે:
`stage-npm` job (github-hosted) તે run માટે GitHubના id-tokenને ટૂંકા સમય માટે માન્ય npm
credential સાથે exchange કરે છે — repository secretsમાં લાંબા સમય સુધી માન્ય npm token નહીં, કોઈ 2FA prompt નહીં અને provenance જોડાયેલું.
હવે જ્યારે 2FAને અવગણતા tokens નિવૃત્ત કરવામાં આવી રહ્યા છે, ત્યારે npm દ્વારા માન્ય આ bypass છે;
તે WS1.3ની ખાતરી જાળવી રાખીને પ્રોજેક્ટમાં v3.8.48 સુધી રહેલો સંપૂર્ણ automatic flow પુનઃસ્થાપિત કરે છે
(લીક થયેલો token એકલો publish કરી શકતો નથી — કારણ કે કોઈ token જ નથી).

**એક વખતનું setup (owner):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none). આ અસ્તિત્વમાં ન હોય ત્યાં સુધી automatic step `ENEEDAUTH` સાથે નિષ્ફળ જાય છે:
`publish_mode=staged` (નીચે) અથવા `direct` સાથે ફરી dispatch કરો.

### Staged publishing (વિનંતી પર — `publish_mode=staged`)

npm-publish workflow હવે સીધું publish કરતું નથી: તે packed tarballને boot કરે છે
(`check:pack-boot`) અને પછી `npm stage publish` ચલાવે છે — ચોક્કસ એ જ bytes registry પર રાખવામાં આવે છે,
પરંતુ owner મંજૂરી ન આપે ત્યાં સુધી તે **install કરી શકાતી નથી**. Human 2FA gate હવે proof પહેલાં નહીં,
પરંતુ તેના પછી આવે છે.

**Workflow green થયા પછી owner flow:**

1. `npm stage list omniroute` — stage id શોધો (તે workflow summaryમાં પણ print થાય છે).
2. Staged bytes ચકાસો (ભલામણ કરેલ): `npm stage download <id>`, ત્યારબાદ download કરેલી
   tarballને અસ્થાયી prefixમાં install કરીને તેને boot કરો (`npm run check:pack-boot` CIમાં
   એ જ pack→install→boot પરિણામને automate કરે છે).
3. `npm stage approve <id>` — 2FA prompt જ publish છે. `npm stage reject <id>` તેને કાઢી નાખે છે.
4. Publish પછીનું સુરક્ષા જાળું: post-publish verifier (v3.8.49 planનું WS1.4) clean containerમાં
   public registryમાંથી published version install કરીને તેને boot કરે છે.

**કટોકટી fallback:** `publish_mode=direct` સાથેનું `workflow_dispatch` legacy immediate
`npm publish` પુનઃસ્થાપિત કરે છે (ફક્ત stagingમાં જ ખામી સર્જાય તો તેનો ઉપયોગ કરો; કારણ નોંધો).

**એક વખતનું hardening (owner, npmjs.com):** `omniroute` માટે Trusted Publisherને
stage-only modeમાં configure કરો, જેથી લીક થયેલો લાંબા સમય સુધી માન્ય token ક્યાંયથી પણ સીધું `npm publish`
ન કરી શકે — CI માત્ર stage કરી શકે છે; માત્ર owner's 2FA જ release કરી શકે છે.

**ખામીયુક્ત artifact માટેની playbook (અપરિવર્તિત):** ડિફૉલ્ટ તાત્કાલિક પગલા તરીકે
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` વાપરો (થોડી મિનિટોમાં થઈ શકે, પાછું ફેરવી શકાય તેવું);
`npm unpublish` ફક્ત 72h/no-dependents windowની અંદર જ અને ક્યારેય પહેલા પગલા તરીકે નહીં.
Docker: version tag ક્યારેય ફરીથી ન લખો — rollback એટલે `latest`ને છેલ્લા યોગ્ય digest તરફ ફરી નિર્દેશિત કરવું.

**Docker Hub `latest` (દરેક stable SemVer publish માટે આવશ્યક):**
`docker-publish` workflowએ **બંને** `X.Y.Z`ને અને, જ્યારે
`should-promote-latest.sh` સંમત થાય કે આ સૌથી ઊંચું stable SemVer છે ત્યારે, `:latest`ને
**સમાન digest** સાથે tag કરવાં આવશ્યક છે. Job પછી: Hubનો `latest` digest નવા
SemVer digest જેટલો હોય અને `last_updated` આગળ વધેલું હોય. જ્યારે release notes એવા fixes વિશે જણાવતી હોય
જે ફક્ત git પર અસ્તિત્વમાં છે, ત્યારે `:latest`ને જૂના build પર રહેવા ન દો.
Compose quickstarts `:latest` વાપરે છે; GitOpsએ `X.Y.Z`ને pin કરવાનું ચાલુ રાખવું જોઈએ.
[Docker release channels](../guides/DOCKER_GUIDE.md#release-channels) અને #10317 જુઓ.

## હોટફિક્સ ફાસ્ટ-લેન (લેબલ `hotfix`)

`hotfix` લેબલ ધરાવતો PR ભારે CI મેટ્રિક્સ (9-shard E2E, coverage ratchet,
quality-gate, quality-extended)ને અવગણે છે અને ઝડપી, ઉચ્ચ-સંકેતવાળા ગેટ્સ જાળવી રાખે છે: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
અને tarball boot-smoke (`check:pack-boot`). લક્ષ્ય: ~33minને બદલે ≤15minમાં ગ્રીન.

**પ્રવેશ નીતિ — ચારેય આવશ્યક (Chromium/VS Code/Node ઇમરજન્સી લેન્સના આધારે):**

1. **ગંભીરતા**: પ્રોડક્શન તૂટી ગયું છે — પ્રકાશિત artifact બૂટ વખતે ક્રેશ થાય છે / કોઈ
   સુરક્ષા સુધારો / રિલીઝનો દરેક વપરાશકર્તા પ્રભાવિત થાય છે. "મહત્વપૂર્ણ" એટલે "તૂટેલું" નહીં.
2. **સત્તા**: માત્ર repository owner જ `hotfix` લેબલ લાગુ કરે છે. લેબલ જ
   મંજૂરી છે — campaign PR પર ક્યારેય સ્વયં તેનો ઉપયોગ કરશો નહીં.
3. **પુરાવો**: PR body અગાઉના સંપૂર્ણપણે-ગ્રીન ભારે run (જે suiteને
   અવગણાયેલા jobs ફરી માન્ય કરશે) ઉપરાંત fixના પોતાના પહેલા-નિષ્ફળ-પછી-સફળ testને લિંક કરે છે.
4. **વ્યાપ**: માત્ર cherry-pick — ન્યૂનતમ fix, કોઈ refactors નહીં, કોઈ બિનસંબંધિત ફેરફારો નહીં.

અવગણાયેલ coverage/ratchet સપાટી release branch પરના આગામી સંપૂર્ણ run દ્વારા
ફરી માન્ય કરવામાં આવે છે (સતત release-green) — lane માત્ર પ્રતીક્ષા અવગણે છે, validation ક્યારેય નહીં.
માત્ર tests ધરાવતા diffs (`tests/` હેઠળની બધી files, `tests/e2e/` હેઠળ કોઈ નહીં) કોઈપણ
લેબલ વિના E2E matrixને આપમેળે અવગણે છે.

### બિલ્ડ લેઆઉટ

રિપોઝિટરી ત્રણ અલગ આઉટપુટ ડિરેક્ટરીઓનો ઉપયોગ કરે છે — તેમને ક્યારેય ભેળવશો નહીં:

| ડિરેક્ટરી | હેતુ                                                     | ટ્રૅક કરાય છે?  |
| --------- | -------------------------------------------------------- | --------------- |
| `src/`    | એપ્લિકેશન સોર્સ (TypeScript / TSX)                       | હા              |
| `.build/` | બિલ્ડ મધ્યવર્તીઓ — `next build` આઉટપુટ (`distDir`)       | ના (gitignored) |
| `dist/`   | વિતરણયોગ્ય npm બંડલ — `assembleStandalone` દ્વારા બનેલું | ના (gitignored) |

> **ઑપરેટર નોંધ:** રિમોટ VPS ઇમેજ ડિરેક્ટરી `/usr/lib/node_modules/omniroute/app/` જ રહે છે.
> ફક્ત **રિપોઝિટરીની અંદરનું** બિલ્ડ આઉટપુટ ખસેડાયું (`app/` → `dist/`). ડિપ્લોય સ્કિલ્સ
> `dist/`ની સામગ્રીને રિમોટ `app/` ડિરેક્ટરીમાં rsync કરે છે — VPS પાથમાં કોઈ ફેરફાર જરૂરી નથી.

**એકલ-બિલ્ડ પ્રવાહ:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

ડિપ્લોય માટે `npm run build` ચલાવ્યા પછી અલગથી `npm run build:cli` ચલાવશો નહીં — તેના બદલે
`npm run build:release` વાપરો, જે એક જ કમાન્ડમાં ક્લીન રીબિલ્ડ + સેન્ટિનલ કરે છે.

ગ્રીન નહીં — Mergify `release` ક્યૂ કૉન્ફિગર થયેલી છે (G11: `queue_rules`, `checks_timeout`,
લેબલ `queue`), `release/*` રૂલસેટ હજી પણ ડિલીશન અને ફોર્સ-પુશને અવરોધે છે, અને
`stable/v3` તથા `develop` હજી અસ્તિત્વમાં નથી), બ્રાન્ચનાં બે પગલાં, કયા નિષ્ક્રિય-વર્કફ્લો
ટ્રિગર અને `if:` શરતો સાચી બને છે (અને કયા રિપોઝિટરી વેરિએબલ દ્વારા ગેટેડ રહે છે અથવા
કૅનોનિકલ રિપોઝિટરી પર પિન થયેલા રહે છે), અપેક્ષિત dist-tags (`latest` → 3.9.0, `next` અને
`nightly` ખાલી) અને રોલબૅક. એક્ઝિટ `0` = `RESULT: READY`, `1` = કોઈ અવરોધક પૂર્વશરત
નિષ્ફળ થઈ (`✗`), `2` = ઉપયોગની ભૂલ. `--advisory <id,...>` કોઈ ચેકને છુપાવ્યા વિના
તેને ચેતવણી (`!`)માં ડાઉનગ્રેડ કરે છે.

3.9.0 રિલીઝ ફ્રીઝ હજી ખુલ્લું હોય ત્યારે વાસ્તવિક કટનું ડ્રાય-રન ચલાવો — બ્રાન્ચો
ટૅગ પછી અને Phase 12c ફ્રીઝ હટાવે તે પહેલાં બનાવવામાં આવે છે.

### PR પ્રિવ્યૂ આર્ટિફૅક્ટ (એક વાર બિલ્ડ કરો, એ જ બાઇટ્સને પ્રમોટ કરો)

`.github/workflows/preview-artifact.yml` PR હેડમાંથી એક પ્રોડક્શન ટારબૉલ બનાવે છે અને
એ જ બિલ્ડને વૅલિડેટ કરે છે (#8084 slice (a)). ફક્ત એ જ રિપોઝિટરીના PRs; કંઈ પણ પબ્લિશ થતું નથી.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # અથવા `preview-artifact` લેબલ ઉમેરો
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # પ્રિવ્યૂ ઇન્સ્ટૉલ
```

રન `npm ci`, `npm run build:release`, `npm run check:pack-artifact` ચલાવે છે, ટારબૉલ
પૅક કરે છે, `npm run check:pack-boot` (નકલી સિક્રેટ્સ, અસ્થાયી ડેટા ડિરેક્ટરી) ચલાવે છે, ફરીથી પૅક કરે છે અને
જ્યાં સુધી ડાઇજેસ્ટ સમાન ન હોય ત્યાં સુધી નિષ્ફળ થાય છે, પછી `artifact-identity.json` (હેડ SHA, બેઝ
SHA, લૉકફાઇલ હૅશ, પ્લેટફોર્મ, આર્ક, node ABI, બંડલર, બિલ્ડ પૉલિસી —
`scripts/release/artifact-identity.mjs`) રેકોર્ડ કરે છે અને એક અલગ જૉબમાં ટારબૉલને અટેસ્ટ કરે છે. પ્રિવ્યૂને પ્રમોટ
કરવાનો અર્થ એ ટારબૉલ ઇન્સ્ટૉલ કરવો છે: સોર્સમાંથી ક્યારેય ફરીથી બિલ્ડ કરશો નહીં.

### કટ (3.9.0, GO પછી)

1. GO [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md)માં નોંધાયેલ છે.
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` `RESULT: READY` પ્રિન્ટ કરે છે.
3. ડ્રાય-રન દ્વારા પ્રિન્ટ કરેલા કમાન્ડ્સ વડે `origin` પર બ્રાન્ચો જાતે બનાવો —
   સ્ક્રિપ્ટ `origin` પર પુશ કરવાનો ઇનકાર કરે છે. સમીક્ષા કરેલી develop કમિટનો ફરી ઉપયોગ કરવા માટે, પહેલાં
   તમારા ફોર્ક સામે 3.9.0 ટિપ પર `--execute` પૂર્વાભ્યાસ ચલાવો; તે બંને SHA પ્રિન્ટ કરે છે, અને
   એ જ કમિટ્સ પુશ કરી શકાય છે:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. પ્રથમ PR મર્જ થાય તે પહેલાં `stable/v3` અને `develop` ને સુરક્ષિત કરો (rulesets + merge queue).
5. નિષ્ક્રિય workflows શાખાની હાજરીના આધારે સક્રિય થાય છે: `forward-port.yml` (`stable/v3` પર push),
   `validate-stable-pr.yml` (`stable/v3` માટેના PRs) અને `nightly-v4-build.yml`
   (`develop` ને build કરે છે). લાઇવ કરતાં પહેલાં, `secrets.FORWARD_PORT_TOKEN` repository secret સેટ કરો (જેથી
   forward-port PRs પર CI ચાલે); જ્યાં સુધી owner repository variable
   `vars.NIGHTLY_PUBLISH` ને `true` પર સેટ ન કરે અને npm Trusted Publishing
   `nightly-v4-build.yml` ને સ્વીકારે નહીં, ત્યાં સુધી nightly publishing બંધ રહે છે. Channel resolution
   `scripts/release/dist-tag.mjs` માં છે, જે `npm-publish.yml` દ્વારા ઉપયોગમાં લેવાતું એ જ
   resolver છે.
6. Channels ચકાસો: `npm view omniroute dist-tags --json` માં `latest` = 3.9.0 દેખાય અને
   v4 publish થાય ત્યાં સુધી `next` / `nightly` ન દેખાય.
7. જરૂર પડે તો rollback કરો: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   અને `npm dist-tag add omniroute@3.8.59 latest`.

જો રિલીઝમાં ગંભીર સમસ્યા હોય:

3. અથવા: `release/vX.Y.0` પર હોટફિક્સ → પૅચ રિલીઝ `vX.Y.(Z+1)`

## કડક નિયમો

- `main` પર ક્યારેય સીધું કમિટ ન કરો
- `main` અથવા `release/*` બ્રાન્ચ પર ક્યારેય `git push --force` નો ઉપયોગ ન કરો
- Husky હુક્સ (`--no-verify`) ક્યારેય છોડશો નહીં
- સિક્રેટ્સ, ઓળખપત્રો અથવા `.env` ફાઇલો ક્યારેય કમિટ ન કરો
- કવરેજ ≥60/60/60/60 (સ્ટેટમેન્ટ્સ/લાઇન્સ/ફંક્શન્સ/બ્રાન્ચિસ) જળવાઈ રહેવું આવશ્યક છે
- `src/`, `open-sse/`, `electron/` અથવા `bin/`માં પ્રોડક્શન કોડ બદલતી વખતે હંમેશાં ટેસ્ટ્સ ઉમેરો અથવા અપડેટ કરો
