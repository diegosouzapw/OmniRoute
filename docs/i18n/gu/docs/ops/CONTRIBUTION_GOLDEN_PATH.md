પુલ રિક્વેસ્ટ માટે સૌથી નાનો વિશ્વસનીય ડેવલપમેન્ટ લૂપ પસંદ કરવા આ માર્ગદર્શિકાનો ઉપયોગ કરો. આ નીચે લિંક કરેલા ક્ષેત્ર-વિશિષ્ટ આર્કિટેક્ચર અને સુરક્ષા દસ્તાવેજોનું
સ્થાન લેતું નથી; તે દરેક સામાન્ય ફેરફારના પ્રકારને તેના કોન્ટ્રાક્ટ્સ, કેન્દ્રિત ચકાસણીઓ અને CI કવરેજ સાથે જોડે છે.

## દરેક ફેરફાર જે માર્ગને અનુસરે છે

1. **સંપાદન કરતાં પહેલાં બેઝ પસંદ કરો.** સૌથી ઊંચી સક્રિય `release/v*` બ્રાન્ચ શોધો અને તેની
   ટિપ પરથી બ્રાન્ચ બનાવો. `main` ને નહીં, પરંતુ તે બ્રાન્ચને લક્ષ્ય બનાવો. જો રિલીઝ ફ્રીઝ સક્રિય હોય, તો ફ્રોઝન
   બ્રાન્ચને લક્ષ્ય ન બનાવો; તેના બદલે
   [Branching & Release Model](BRANCHING_MODEL.md) માં વર્ણવેલા આગામી સક્રિય ચક્રનો ઉપયોગ કરો.
2. **કોન્ટ્રાક્ટ્સનાં નામ આપો.** ફેરફાર જે દરેક કૅટલૉગ, સ્કીમા, જનરેટ થયેલી આર્ટિફેક્ટ, જાહેર API અથવા વપરાશકર્તા
   ઇન્ટરફેસને અસર કરે છે તે ઓળખો. નીચેનું કોષ્ટક ન્યૂનતમ પ્રારંભિક સમૂહ આપે છે.
3. **કેન્દ્રિત ટેસ્ટ લખો અથવા અપડેટ કરો.** `src/`, `open-sse/`, `electron/`, અથવા
   `bin/` માંના પ્રોડક્શન ફેરફારો માટે એ જ PR માં ઓટોમેટેડ ટેસ્ટ જરૂરી છે. વર્તન સાબિત કરતી સૌથી નાની ટેસ્ટ ફાઇલો
   ચલાવો, ત્યારબાદ સૂચિબદ્ધ કેન્દ્રિત ગેટ્સ ચલાવો.
4. **CI ને વિસ્તૃત મેટ્રિક્સ ચલાવવા દો.** સંપૂર્ણ યુનિટ શાર્ડ્સ, Vitest, કવરેજ રૅચેટ અને
   પ્રોડક્શન બિલ્ડ PR પર ચાલે છે. જ્યારે કોઈ કેન્દ્રિત નિષ્ફળતા વધુ વ્યાપક અસર તરફ નિર્દેશ કરે
   અથવા ફેરફાર અનેક સબસિસ્ટમમાં ફેલાયેલો હોય ત્યારે જ સ્થાનિક રીતે વિસ્તૃત સ્યુટ ચલાવો.
5. **સમીક્ષા પહેલાં સમાધાન કરો.** સક્રિય બેઝ ફેચ કરો, તેના નવા કમિટ્સ અને તેની સામેના તમારા ડિફનું નિરીક્ષણ
   કરો, પછી યોગદાનકર્તા વર્કફ્લો અનુસાર બેઝને રિબેઝ અથવા મર્જ કરો. જનરેટ થયેલી ફાઇલ
   અને કૅટલૉગના સંઘર્ષો તેમના સ્રોત પરથી ઉકેલો, તેમને ફરીથી જનરેટ કરો, કેન્દ્રિત લૂપ ફરીથી ચલાવો અને ખાતરી કરો કે
   PR હજી પણ સક્રિય રિલીઝ બ્રાન્ચને લક્ષ્ય બનાવે છે.
6. **પુરાવા નોંધો.** PR ટેમ્પલેટમાં ચલાવેલા કમાન્ડ્સ, ઉમેરેલી અથવા બદલેલી દરેક ટેસ્ટ ફાઇલ,
   માઇગ્રેશન્સ અથવા ફીચર ફ્લૅગ્સ અને હજી બાકી રહેલી કોઈપણ માત્ર-CI વૅલિડેશનની સૂચિ આપો.

## ફેરફારના પ્રકાર મુજબ ગોલ્ડન પાથ્સ

નીચેના કમાન્ડ્સ ન્યૂનતમ કેન્દ્રિત ચકાસણીઓ છે, તમે બદલેલા વર્તનને સીધું આવરી લેતા ટેસ્ટને છોડવાની
પરવાનગી નથી.

### પ્રોવાઇડર

**કોન્ટ્રાક્ટ્સ**

- `src/shared/constants/providers/` માં પ્રોવાઇડરની વ્યાખ્યા અને
  `src/shared/constants/providers.ts` માં તેનું કમ્પોઝિશન.
- `open-sse/config/providerRegistry.ts` અથવા તેની અલગ કરેલી રજિસ્ટ્રી ફાઇલોમાં મોડેલ્સ અને ક્ષમતાઓ.
- લાગુ પડતું હોય ત્યારે એક્ઝિક્યુટર/ટ્રાન્સલેટરની પસંદગી, OAuth અથવા API-key કન્ફિગરેશન, ડૅશબોર્ડ એસેટ્સ અને જનરેટ થયેલો
  પ્રોવાઇડર સંદર્ભ.
- જાહેર ક્રેડેન્શિયલ્સે `resolvePublicCred()` નો ઉપયોગ કરવો આવશ્યક છે; એરર રિસ્પોન્સે શેર કરેલા સેનિટાઇઝ્ડ
  એરર હેલ્પર્સનો ઉપયોગ કરવો આવશ્યક છે. `docs/security/PUBLIC_CREDS.md` (git; `/docs` માં કમ્પાઇલ થતું નથી) અને
  [Error Sanitization](../security/ERROR_SANITIZATION.md) જુઓ.

**કેન્દ્રિત લૂપ**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # જ્યારે કૅટલૉગ બદલાય; જનરેટ થયેલો ડિફ કમિટ કરો
npm run lint
```

અસરગ્રસ્ત દરેક રિક્વેસ્ટ ફેમિલીનું પણ પરીક્ષણ કરો: chat, Responses, images, embeddings, audio, અથવા video.
જનરેટ થયેલા કૅટલૉગ અને ગોલ્ડન ડિફ્સની કોન્ટ્રાક્ટ ફેરફારો તરીકે સમીક્ષા કરો; તેમને આંખ બંધ કરીને સ્વીકારશો નહીં.

### રાઉટિંગ

**કોન્ટ્રાક્ટ્સ**

- `src/shared/constants/routingStrategies.ts` માં જાહેર સ્ટ્રેટેજી વેલ્યુઝ અને UI મેટાડેટા.
- `open-sse/services/combo.ts` અને `open-sse/services/combo/` હેઠળ ડિસ્પૅચ અને ક્રમ.
- Combo સ્કીમા, પર્સિસ્ટન્સ, રિઝિલિયન્સ સ્ટેટ, મોડેલ ક્ષમતાઓ અને API/UI નિયંત્રણો.
- વર્તન બદલાય ત્યારે [Auto-Combo Engine](../routing/AUTO-COMBO.md) અને રિઝિલિયન્સ દસ્તાવેજીકરણ.

**કેન્દ્રિત લૂપ**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # સ્ટ્રેટેજી અથવા ડિસ્પૅચમાં ફેરફારો
npm run check:known-symbols      # સ્ટ્રેટેજી રજિસ્ટ્રેશનમાં ફેરફારો
npm run lint
```

સ્થાનિક રીતે નિર્ધારિત પરિણામ આપતા mocked-upstream ટેસ્ટ્સનો ઉપયોગ કરો. લાઇવ combo સ્મોક ટેસ્ટ્સ માટે ક્રેડેન્શિયલ્સ જરૂરી છે અને તે
મેન્યુઅલ છે, CI ના વિકલ્પ નથી.

### UI / UX

**કોન્ટ્રાક્ટ્સ**

- `src/app/` અને `src/shared/components/` હેઠળ Next.js રૂટ/પેજ અને શેર કરેલી કમ્પોનન્ટ સીમાઓ.
- API રિસ્પોન્સ આકારો, લોડિંગ/ખાલી/એરર સ્ટેટ્સ, કીબોર્ડ અને સ્ક્રીન-રીડર વર્તન,
  રિસ્પોન્સિવ લેઆઉટ, થીમિંગ અને લોકેલ વિસ્તરણ.
- `src/i18n/messages/en.json` માં અંગ્રેજી UI સ્રોત સ્ટ્રિંગ્સ; નવી વપરાશકર્તા-દૃશ્યમાન નકલ હાર્ડ-કોડ કરશો નહીં.

**કેન્દ્રિત લૂપ**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

ઇન્ટરૅક્શન અથવા દૃશ્યમાન ફેરફારો માટે એપ ચલાવો અને સાંકડા તથા પહોળા બંને વ્યૂપોર્ટ્સ તપાસો. CI
પ્રોડક્શન બિલ્ડ અને વધુ વિસ્તૃત સ્યુટ્સ ચલાવે છે; દૃશ્યમાન વર્તન માટે હજી પણ ફેરફારને અનુરૂપ કેન્દ્રિત કમ્પોનન્ટ, Playwright,
અથવા દસ્તાવેજીકૃત મેન્યુઅલ ચકાસણી જરૂરી છે.

### i18n

**કોન્ટ્રાક્ટ્સ**

- `src/i18n/messages/en.json` એ UI સ્રોત છે; `config/i18n.json` એ લોકેલ સ્રોત છે.
- CLI કૅટલૉગ્સ `bin/cli/locales/` હેઠળ અલગ રહે છે.
- ICU પ્લેસહોલ્ડર્સ અને ટૅગ્સને બરાબર એ જ રીતે જાળવો. પ્રોડક્ટ/પ્રોવાઇડર/મોડેલ નામો,
  પ્રોટોકૉલ અને હેડર નામો, કમાન્ડ્સ, કોડ/JSON આઇડેન્ટિફાયર્સ, URLs, એન્વાયર્નમેન્ટ વેરિએબલ્સ અથવા
  `OmniRoute`, `OAuth`, `MCP`, અને `A2A` જેવા સુરક્ષિત શબ્દોનું ભાષાંતર કરશો નહીં. વર્તમાન સ્રોત સૂચિ
  `scripts/i18n/glossary/protected-terms.json` છે.

**કેન્દ્રિત લૂપ**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # જ્યારે CLI સ્ટ્રિંગ્સ/કૅટલૉગ્સ બદલાય
npm run lint
```

આ હાલની સિસ્ટમ માટેનું માર્ગદર્શન છે, તેના ટૂલિંગ અથવા કી મોડેલને વિસ્તૃત કરવાનું આમંત્રણ નથી.
રિપ્લેસમેન્ટ સિસ્ટમ ડિઝાઇન થઈ રહી હોય ત્યારે i18n પૅચોને ચોક્કસ અને મર્યાદિત રાખો. એવા ટ્રાન્સલેશન
કમાન્ડ્સ ચલાવશો નહીં જે બાહ્ય સેવાઓને કૉલ કરે, સિવાય કે કાર્યમાં સ્પષ્ટપણે જનરેટ થયેલા અનુવાદોની જરૂર હોય અને
તમે પરિણામી ડિફની સમીક્ષા કરી હોય.

### CLI

**કોન્ટ્રાક્ટ્સ**

- `bin/cli/` માંના જાહેર commands અને flags, જનરેટ કરેલા API commands, exit codes, stdout/stderr અને
  JSON output shapes, config/environment વર્તણૂક અને પૅકેજ કરેલી files.
- CLIના user-facing stringsએ CLI i18n layerનો ઉપયોગ કરવો અને `en`/`pt-BR` catalogsને સુસંગત રાખવા.
- સમર્થિત runtime તરીકે Node અને પ્રકાશિત binary contractને જાળવો.

**કેન્દ્રિત લૂપ**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # જનરેટ કરેલા/બંડલ કરેલા CLI ફેરફારો
npm run check:pack-policy     # package-surface ફેરફારો
npm run lint
```

જ્યારે વર્તણૂક parsing, files અથવા exit status પર આધારિત હોય ત્યારે અસ્થાયી data directoryમાં ચોક્કસ commandનો ઉપયોગ કરો. CI વધુ વ્યાપક package artifact અને ecosystem checks કરે છે.

### Database

**Contracts**

- `src/lib/db/` હેઠળના domain modules; ચોક્કસ modulesને સીધા import કરો (જૂનું `localDb.ts` re-export layer દૂર કરવામાં આવ્યું હતું).
- `src/lib/db/migrations/` હેઠળ ક્રમાંકિત, idempotent SQL migrations, transaction safety, upgrade
  વર્તણૂક, indexes અને schemaથી પ્રભાવિત થતા દરેક caller.
- Routes અને handlers ક્યારેય સીધું raw SQL ચલાવતા નથી.

**કેન્દ્રિત લૂપ**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migration ઉમેરતી વખતે નવી database અને અગાઉના schemaમાંથી upgrade—બંનેનું પરીક્ષણ કરો. Database testsએ cleanup દરમિયાન handles બંધ કરવા અને `resetDbInstance()`ને call કરવું આવશ્યક છે. માત્ર best-effort Bun adapter path બદલાય ત્યારે જ `npm run test:bun:db` ચલાવો; Node અધિકૃત રહે છે.

### Build / deploy

**Contracts**

- Root અને workspace manifests/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/`
  package contents, Electron platform metadata, CI workflows અને deployment sentinels.
- સમર્થિત Node ranges અને `CLAUDE.md`માં allow-listed Bunનો ઉપયોગ અકબંધ રહેવો આવશ્યક છે.
- Build artifacts untracked રહે છે; dependency, license, workflow અને package policies લાગુ પડે છે.

**કેન્દ્રિત લૂપ**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency અથવા lockfile ફેરફારો
npm run check:pack-policy      # પ્રકાશિત package surface ફેરફારો
npm run lint
```

ફેરફાર compilation, standalone assembly, assets અથવા runtime bundlingને અસર કરતો હોય ત્યારે જ સ્થાનિક રીતે `npm run build`નો ઉપયોગ કરો. માત્ર release/deploy validation માટે `npm run build:release`નો ઉપયોગ કરો. CIનું build અંતિમ cross-platform signal છે; platform-specific Electron ફેરફારો માટે અનુરૂપ focused build અથવા smoke evidence જરૂરી છે.

## સ્થાનિક લૂપ વિરુદ્ધ CI

| દરેક પેચ માટે સ્થાનિક રીતે ચલાવો                                        | CI વ્યાપક સંકેત પૂરો પાડે છે                                          |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------- |
| ઉપર આપેલા સીધા વર્તન પરીક્ષણો અને શ્રેણી ગેટ્સ                          | શાર્ડ કરેલો સંપૂર્ણ યુનિટ સ્યુટ અને ક્રમિક પરીક્ષણો                   |
| `npm run lint`                                                          | Vitest સ્યુટ્સ અને કવરેજ/ગુણવત્તા રૅચેટ્સ                             |
| અસરગ્રસ્ત કોન્ટ્રાક્ટમાં જરૂરી હોય ત્યારે જ ટાઇપચેક અથવા બિલ્ડ          | પ્રોડક્શન બિલ્ડ, સુરક્ષા, દસ્તાવેજીકરણ, ડિપેન્ડન્સી અને PR-નીતિ ગેટ્સ |
| ઓટોમેશન વર્તન સાબિત ન કરી શકે ત્યારે જ મેન્યુઅલ ઇન્ટરેક્શન/લાઇવ ચકાસણીઓ | વર્કફ્લો દ્વારા ગોઠવેલી ક્રોસ-જોબ ઇન્ટિગ્રેશન અને પ્લેટફોર્મ ચકાસણીઓ  |

સફળ કેન્દ્રિત લૂપ બદલાયેલા કોન્ટ્રાક્ટ વિશેનો પુરાવો છે, પરંતુ તે અસંબંધિત CI ચકાસણીઓ
પાસ થશે તેનો પુરાવો નથી. તે જ રીતે, દરેક સ્થાનિક ફેરફારને સંપૂર્ણ રિપોઝિટરી મેટ્રિક્સ માટે રાહ જોવડાવશો નહીં.

## સુમેળ ચેકલિસ્ટ

સમીક્ષાની વિનંતી કરતાં પહેલાં:

- ખાતરી કરો કે PR બેઝ હજી પણ સર્વોચ્ચ સક્રિય `release/v*` બ્રાન્ચ છે.
- તે બેઝને ફેચ કરો અને તમે બ્રાન્ચ બનાવ્યા પછી સામેલ થયેલા કમિટ્સની સમીક્ષા કરો.
- આકસ્મિક અથવા જનરેટ થયેલા અનાવશ્યક ફેરફારો માટે `git diff <active-base>...HEAD` ની સમીક્ષા કરો.
- સ્રોતને અપડેટ કરીને અને આઉટપુટ ફરીથી જનરેટ કરીને કેટલોગ અને જનરેટ થયેલા દસ્તાવેજના સંઘર્ષો ઉકેલો.
- સુમેળ પછી PR વર્ણનમાં સૂચિબદ્ધ દરેક કેન્દ્રિત પરીક્ષણ/ગેટ ફરીથી ચલાવો.
- બદલાયેલા બેઝ સાથે મેળ બેસાડવા માટે માત્ર assertions ક્યારેય નબળાં ન પાડો અથવા જરૂરી પરીક્ષણો દૂર ન કરો.

રિલીઝ-ફ્રીઝ અને રિટાર્ગેટિંગ નિયમો માટે,
[બ્રાન્ચિંગ અને રિલીઝ મોડેલ](BRANCHING_MODEL.md) નો ઉપયોગ કરો. સંપૂર્ણ CI ઇન્વેન્ટરી માટે,
[ગુણવત્તા ગેટ્સ સંદર્ભ](../architecture/QUALITY_GATES.md) નો ઉપયોગ કરો.
