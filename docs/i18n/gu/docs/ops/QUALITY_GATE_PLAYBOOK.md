## ભાગ 1 — ચુકાદો અને પરિપક્વતાનું વર્ગીકરણ

**એકંદર ગ્રેડ: A− / "અદ્યતન". ટોચના ~5–10% પ્રોજેક્ટ્સમાં.** આ સિસ્ટમ ઉદ્યોગે
સ્પષ્ટપણે નામ આપેલી અનેક પેટર્ન્સને સ્વતંત્ર રીતે અમલમાં મૂકે છે — જે સંરેખણનો
સૌથી મજબૂત સંકેત છે (અમે કોઈ ચેકલિસ્ટની નકલ કરી નથી; અમે યોગ્ય પ્રથાઓ પર સ્વતંત્ર રીતે પહોંચ્યા છીએ).

## ભાગ 2 — ગંભીર મૂલ્યાંકન (મજબૂત પાસાં + પ્રામાણિક નબળાઈઓ)

### મજબૂત પાસાં (જે સરેરાશ કરતાં વધુ સારાં છે)

1. **મલ્ટિ-મેટ્રિક રૅચેટ એન્જિન.** સિસ્ટમનું હાર્દ. `quality-baseline.json`માં 24 મેટ્રિક્સ
   - 4 સમર્પિત બેઝલાઇન, દરેકમાં દિશા (`up`/`down`), સહનશીલતા (`eps`), છૂટ
     (`tightenSlack`) અને `dedicatedGate` ફ્લૅગ છે. જે બાબતો સુધારાઈ જાય છે તે **સુધારેલી જ રહે છે** — આ
     કોડબેઝ એન્ટ્રોપીનો પ્રતિકારક ઉપાય છે.
2. **સપ્લાય-ચેઇન માટે બહુસ્તરીય સુરક્ષા.** SAST (CodeQL/Sonar) + સિક્રેટ્સ (`useDefault` સાથે gitleaks)
   - SCA (osv/npm-audit/Trivy/Dependabot) + લાઇસન્સ + લૉકફાઇલ + SBOM + SLSA
     પ્રોવેનન્સ + Scorecard + વર્કફ્લો હાર્ડનિંગ (zizmor). બહુ ઓછા કોડબેઝ પાસે આટલો સંપૂર્ણ સ્ટૅક હોય છે.
3. **Goodhart's Law સામેના પ્રતિકારક ઉપાયો.** કવરેજને લક્ષ્ય બનાવવું એક જાણીતું ઍન્ટિ-પૅટર્ન છે
   ("જ્યારે માપદંડ જ લક્ષ્ય બની જાય, ત્યારે તે સારો માપદંડ રહેતો નથી"). આપણી પાસે
   સંતુલનકારી ઉપાયો છે: **મ્યુટેશન ટેસ્ટિંગ** (ટેસ્ટ માત્ર લાઇન ચલાવે છે કે ખરેખર બગ પકડે છે
   તે માપે છે), **`check-test-masking`** (પાસ થવા માટે assertions નબળા પાડવાનું અવરોધે છે),
   **પ્રતિ-મોડ્યુલ કવરેજ ફ્લોર** (માત્ર સરળ ભાગો નહીં, પણ HIGH-જોખમવાળા કોડનું પરીક્ષણ ફરજિયાત કરે છે) અને
   **`check-pr-evidence`** (કડક નિયમ #18).
4. **ઍન્ટિ-હેલ્યુસિનેશન / સુસંગતતા ગેટ્સ.** એક દુર્લભ અને મૂલ્યવાન શ્રેણી: `check-known-symbols`,
   `check-fetch-targets`, `check-openapi-routes`, `check-docs-symbols` ખાતરી કરે છે કે દસ્તાવેજો, સ્પેક્સ અને
   સ્ટ્રિંગ ડિસ્પૅચ જીવંત symbols તરફ નિર્દેશ કરે છે. lint/test ન પકડી શકે એવો "સડો" આ પકડે છે.
5. **સલાહકારી→અવરોધક જીવનચક્ર.** નવા ગેટ્સ સલાહકારી તરીકે દાખલ થાય છે (પરિપક્વ થઈ રહ્યા હોય ત્યારે
   મર્જને અવરોધતા નથી), પછી ચક્રના અંતે અવરોધક બને છે. ગુણવત્તાની મર્યાદા ગુમાવ્યા વિના ઘર્ષણ ઘટાડે છે.
6. **ઇન્ફ્રા ઉપલબ્ધ ન હોય ત્યારે સુવ્યવસ્થિત સ્કિપ.** જો binary/network નિષ્ફળ જાય તો સ્કૅનર્સ (`--ratchet`)
   `exit 0` સાથે બહાર નીકળે છે — ગેરહાજર ઇન્ફ્રા ક્યારેય યોગ્ય PRને અવરોધતું નથી. પરિપક્વ એન્જિનિયરિંગ.
7. **સંહિતાબદ્ધ સંસ્કૃતિ.** કડક નિયમો + `trust-but-verify` + stale-allowlist + evidence-gate
   શિસ્તને સ્વચાલિત ચકાસણીમાં ફેરવે છે.

### પ્રામાણિક નબળાઈઓ (વાસ્તવિક ખામીઓ)

1. **🔴 fast-gatesનું વિભાજન હજી પણ માળખાકીય ખામી છોડે છે.** `quality.yml` (PR→`release/**`)
   હવે typecheck, ઝડપી deterministic tests અને કોડ PR માટે સલાહકારી production build ચલાવે છે,
   પરંતુ તે હજી પણ `ci.yml`ની સંપૂર્ણ release-PR સપાટી (coverage ratchets,

## ભાગ 4 — કોઈપણ પ્રોજેક્ટ માટે પ્રતિકૃતિ યોજના

**તબક્કાઓમાં** બનાવો, જેમાં દરેક તબક્કો પોતાની રીતે મૂલ્ય પ્રદાન કરે. બધી 12 શ્રેણીઓ એકસાથે અજમાવશો નહીં —
તેનાથી બરાબર એ જ ગેટ થાક સર્જાય છે જેના વિશે ભાગ 2 ચેતવણી આપે છે. દરેક નવો ગેટ **સલાહકારી** તરીકે પ્રવેશે છે અને
સ્થિર થયા પછી **અવરોધક** બને છે.

### ફરી વાપરી શકાય તેવું કેન્દ્રબિંદુ: "રૅચેટ ગેટની રચના"

સમગ્ર સિસ્ટમ આ 3-ફાઇલની પેટર્નની આસપાસ ફરે છે. પહેલાં તેની નકલ કરો:

1. **`baseline.json`** — સ્થિર કરેલું મેટ્રિક મૂલ્ય + `direction` (`up`/`down`) + `eps` (અસ્થિરતા-વિરોધી) + `tightenSlack` + `dedicatedGate`.
2. **`collect-metrics.<ext>`** — સાધન ચલાવે છે, સંખ્યા કાઢે છે અને `metrics.json` લખે છે.
3. **`check-ratchet.<ext>`** — `metrics.json`ની `baseline.json` સાથે સરખામણી કરે છે; `eps` કરતાં વધુ પીછેહઠ થઈ હોય તો **માત્ર** `exit 1`; સાધન/ઇન્ફ્રા ઉપલબ્ધ ન હોય તો `exit 0` (સુગમ રીતે અવગણવું); `--require-tighten` સાથે, બેઝલાઇન અપડેટ કર્યા વિના તેમાં **સુધારો** થયો હોય તો `exit 1` (લાભને કાયમી કરે છે).

આ અમલમાં હોય ત્યારે, **દરેક** નવું મેટ્રિક (કવરેજ, જટિલતા, ચેતવણીઓ, SAST એલર્ટ, બંડલ કદ, મ્યુટેશન સ્કોર…) બેઝલાઇનમાં માત્ર એક પંક્તિ છે.

### તબક્કો 0 — પાયો (અઠવાડિયું 1)

CI હાજર છે; ફોર્મેટર + લિન્ટર + ટાઇપચેક + 1 ટેસ્ટ રનર + **ન્યૂનતમ નિશ્ચિત** કવરેજ મર્યાદા
(દા.ત., 60%). પ્રી-કમિટ ઝડપી, આપમેળે સુધારી શકાય તેવી ચકાસણીઓ ચલાવે છે. _પરિણામ: કોઈ PR મૂળભૂત બાબતોને તોડતું નથી._

### તબક્કો 1 — રૅચેટ એન્જિન (અઠવાડિયું 2) — **દરેક બાબતનો પાયો**

ઉપરોક્ત 3 ફાઇલો અમલમાં મૂકો. આ માટે બેઝલાઇન સ્થિર કરો: ચેતવણીઓ, કવરેજ, જટિલતા, નકલ,
નિષ્ક્રિય કોડ, ફાઇલનું કદ. _પરિણામ: અહીંથી કોડબેઝ માત્ર સુધરી શકે છે._

### તબક્કો 2 — સ્થિર વિશ્લેષણની ઊંડાઈ (અઠવાડિયું 3)

એલર્ટ રૅચેટ સાથે SAST (CodeQL/Sonar/semgrep); સિક્રેટ્સ સ્કેનર (**ડિફૉલ્ટ નિયમસમૂહ વારસામાં મેળવો**);
SCA (osv/Dependabot) + લાઇસન્સ મંજૂર-સૂચિ + lockfile-lint. _પરિણામ: જાણીતી નબળાઈઓ અને
લીક થયેલા સિક્રેટ્સ પસાર થતા નથી._

### તબક્કો 3 — બિલ્ડ પુરવઠા-શૃંખલા (અઠવાડિયું 4)

પ્રકાશન વખતે SBOM + સહી કરેલું મૂળપ્રમાણ (SLSA L2) + નિર્ધારિત સમયપત્રક મુજબ Scorecard + વર્કફ્લોનું સખ્તીકરણ
(zizmor: ન્યૂનતમ ટોકન્સ, કોઈ સંગ્રહિત ઓળખપત્રો નહીં, પિન કરેલી ઍક્શન્સ). _પરિણામ: શોધી શકાય તેવી અને
છેડછાડ-પ્રતિરોધક રિલીઝ._

### તબક્કો 4 — પરીક્ષણની તીવ્રતા (અઠવાડિયું 5–6)

ઉપયોગી હોય તો બીજો રનર; **મહત્ત્વપૂર્ણ મોડ્યુલો માટે મોડ્યુલ-દીઠ કવરેજ મર્યાદાઓ** (ગુડહાર્ટ-વિરોધી);
શુદ્ધ લોજિક માટે ગુણધર્મ-આધારિત પરીક્ષણ; **રાત્રે મ્યુટેશન પરીક્ષણ** → પહેલો સ્કોર આવે ત્યારે
`mutationScore`ને રૅચેટ બનાવો. _પરિણામ: કવરેજ દેખાડાનું મેટ્રિક રહેતું નથી; પરીક્ષણો સાબિત રીતે બગ્સ પકડે છે._

### તબક્કો 5 — કરાર અને ગતિશીલ પરીક્ષણ (અઠવાડિયું 7)

જો જાહેર API હોય: oasdiff (ભંગાણકારક ફેરફાર, **અવરોધક**) + schemathesis (રાત્રિ ફઝિંગ).
ડોમેન માટે યોગ્ય હોય તે મુજબ રાત્રે DAST/રેડ-ટીમ પરીક્ષણ. _પરિણામ: કરારો મૌન રીતે તૂટતા નથી._

### તબક્કો 6 — ભ્રમણા-વિરોધી અને ડોમેન (અઠવાડિયું 8)

પ્રોજેક્ટમાં દરેક "ડુપ્લિકેટ થયેલા સત્ય" માટે એક સુસંગતતા ગેટ. ડોમેન-વિશિષ્ટ નિષ્ફળતા-સ્થિતિ
ગેટ્સ (AI માટે: ઇન્જેક્શન રેડ-ટીમ). _પરિણામ: માળખાકીય સડો અને ડોમેન નિષ્ફળતાઓ માટે સુરક્ષા જાળ હોય છે._

### તબક્કો 7 — શાસન (સતત)

- દરેક નવા ગેટ માટે સલાહકારી→અવરોધક ચક્ર.
- `stale-allowlist`: દરેક દમન માટે વાજબી કારણ + ઇશ્યૂ હોય છે; અપ્રચલિત દમન પકડાય છે.
- `evidence-gate`: PRમાં સફળતાના દાવા માટે પુરાવા (ટેસ્ટ અથવા જીવંત ટેસ્ટ) જરૂરી છે.
- **દરેક ગેટ માટે ત્રિમાસિક ROI સમીક્ષા** (જે વળતર ન આપે તેને દૂર કરો/ભંડોળ બંધ કરો — થાક સામે લડે છે).
- તમારા પ્રોજેક્ટના કડક નિયમોને અમલક્ષમ ગેટ્સમાં રૂપાંતરિત કરો.

### સર્વવ્યાપી સિદ્ધાંતો (બાંધછોડ ન થઈ શકે તેવા)

- **રૅચેટ, નિશ્ચિત મર્યાદા નહીં.** કોઈ નિશ્ચિત સંખ્યાને નહીં, પરંતુ _પીછેહઠ ન થવાને_ ગેટ બનાવો (શૂન્ય-વિરોધી ન્યૂનતમ મર્યાદાઓ સિવાય).
- **નિશ્ચિત ન્યૂનતમ મર્યાદા + રૅચેટ સાથે.** મર્યાદા ધરાશાયી થવાનું અટકાવે છે; રૅચેટ ધીમા ધોવાણને અટકાવે છે.
- **ડિઝાઇન દ્વારા ગુડહાર્ટ-વિરોધી.** દરેક લક્ષિત મેટ્રિકને પ્રતિસંતુલન જોઈએ (કવરેજ ⇒ મ્યુટેશન + માસ્કિંગ-વિરોધી; મુશ્કેલ કોડનું પરીક્ષણ કરાવવા માટે મોડ્યુલ-દીઠ મર્યાદાઓ).
- **સુગમ રીતે અવગણવું.** ગેરહાજર ઇન્ફ્રા ક્યારેય અવરોધતું નથી; માત્ર વાસ્તવિક પીછેહઠ અવરોધે છે.
- **મોંઘા મેટ્રિક્સ માટે `dedicatedGate`.** જે મેટ્રિક્સને બાહ્ય બાઇનરીની જરૂર હોય તેમને સમકાલીન કેન્દ્રીય રૅચેટની બહાર પોતાની સ્ક્રિપ્ટ (અવગણવાની સુવિધા સાથે) મળે છે.
- **જ્યાં મર્જ થાય ત્યાં ગેટ મૂકો.** ઝડપી ગેટ અને વાસ્તવિક મર્જ વચ્ચે અંતર ન છોડો (fast-gates વિભાજનમાંથી મળેલો પાઠ).
- **થોડા, સારી રીતે પસંદ કરેલા અવરોધક ગેટ્સ.** Sonar/DORA: ઘણી બધી શરતો = થાક. અવરોધક ગેટ્સની દિવાલ કરતાં સલાહકારી + રૅચેટને પ્રાધાન્ય આપો.

## ભાગ 5 — ભલામણ કરેલા સુધારાઓ (પ્રાથમિકતા અનુસાર, સુસંગત)

**P0 — સર્વોચ્ચ ROI, લગભગ તૈયાર**

1. **Mutation score ratchet** (પ્રથમ nightly Stryker મૂલ્યો ઉત્પન્ન કરે ત્યાર પછી). coverage-Goodhart સામેનો મુખ્ય પ્રતિકાર; ~90% પૂર્ણ.
2. **બાકી રહેલી fast-gates ખામી બંધ કરો** — `quality.yml` production buildના
   advisory week પછી તેને પ્રમોટ કરો અને deterministic release-PR-only ચકાસણીઓને PR→release પાથમાં ખસેડવાનું ચાલુ રાખો.
3. **`main` પર branch-protection** (માલિકનું setting) — Scorecard વધારે છે, DSOMMની ખામી બંધ કરે છે.

**P1 — મૂલ્યવાન** 4. **osv/oasdiff → યોગ્ય scope સાથે blocking** — osv માત્ર CRITICAL+fixable (Trivyની જેમ બે-પગલાંમાં); oasdiff breaking-changesને અવરોધે. 5. **`require-tighten` → blocking** (ચક્રના અંતે) — metricમાં થયેલા સુધારાઓને સ્થિર કરે છે. 6. **`ci-summary`માં gate-દીઠ ROI/timing review** — ધીમા/ઓછા મૂલ્યવાળા gates શોધો અને દૂર કરો.

**P2 — ઘટતું વળતર** 7. **SLSA L3** — જો તમે L2થી ઉપર જવા માંગતા હોવ તો hermetic/reproducible builder (GitHub SLSA generator). 8. **Committed CodeQL config + versioned semgrep** — વધુ નિયંત્રણ/reproducibility. 9. **દરેક PR માટે DAST smoke** — સૌથી વધુ જોખમવાળા endpoints પર schemathesis/promptfooનો ઝડપી subset (માત્ર nightly નહીં). 10. **Flakiness dashboard + DORA metrics** — ખાતરી કરો કે gates ઝડપને નબળી નથી પાડી રહ્યા.

## ભાગ 6 — નક્કર releaseમાંથી મળેલા પાઠ (Phase 9માં ઉમેરવાના gates)

> આ વિભાગ release closure દરમિયાન બનેલી વાસ્તવિક ઘટનાઓ નોંધે છે, જ્યાં કોઈ gate **ગેરહાજર હતો**,
> અને તેના માટે નક્કર પુરાવા તથા સૂચિત gate આપે છે. દરેક મુદ્દો ભાગ 5 માટેનો ઉમેદવાર છે.

### પાઠ v3.8.27 (2026-06-17) — "fast-gates hole" deterministic regressionsને releaseના દિવસ સુધી પહોંચવા દે છે

**શું બન્યું.** v3.8.27 `/generate-release` દરમિયાન, release PR (`release/v3.8.27` → `main`)
એ સંકલિત ચક્રમાં સંપૂર્ણ `ci.yml` matrixનું **પ્રથમ** execution હતું. પરિણામ: એકસાથે 12 નિષ્ફળતાઓ
— **3 deterministic tests** + ~9 flakes/env. તેમાંથી કોઈ પણ live product regression નહોતું, પરંતુ
બધાં ધ્યાન બહાર રહ્યાં કારણ કે cycle PRs **Fast QG
(`quality.yml`)** મારફતે `release/**`માં પ્રવેશે છે, જે સંપૂર્ણ unit suite, `pr-test-policy` (test-masking),
સંપૂર્ણ integration suite અથવા schema parity checking ચલાવતું નથી. તે 3 deterministic નિષ્ફળતાઓ:

1. **UI ફેરફારથી test જૂનું થયું** — `permissions modal switch buttons declare button type`:
   #4034એ 4થું switch ઉમેર્યું (a11y `type="button"` જાળવ્યું); testની `=== 3` ગણતરી
   જૂની થઈ ગઈ. Static analysisએ આને #4034 PRમાં પકડી લેવું જોઈતું હતું.
2. **Packaging ફેરફારથી test જૂનું થયું** — `findMissingArtifactPaths ... root runtime files`:
   `dist/http-method-guard.cjs` કાયદેસર required-path બન્યું; testની expected list
   જૂની થઈ ગઈ.
3. **Lossy modularization divergence (સૌથી ગંભીર)** — `settings schemas accept ... unprefixed
toggle`: **modularized** `updateSettingsSchema` (`schemas/settings.ts`, #3988 દ્વારા બનાવાયેલું) canonical
   સંસ્કરણથી (`settingsSchemas.ts`) અલગ પડી ગયું: **45 fields સામે 85 — 40 છૂટી ગયાં + 6 અલગ (qdrant\*)**. તે
   **dead-code** હતું (runtime canonical સંસ્કરણ વાપરે છે), તેથી live અસર થઈ નહીં, પરંતુ માત્ર હાથેથી લખેલા parity
   testએ તેને પકડ્યું. #4030એ #3988/#3993માંથી થયેલાં 16 સમાન omissions પુનઃસ્થાપિત કર્યાં, પરંતુ આ રહી ગયું.

**સૂચિત gates (Phase 9):**

- **G1 — fast-gates ખામી ખરેખર બંધ કરો (P0 #2નું વિસ્તરણ).** `quality.yml`માં (PR→`release/**`),
  typecheck + impacted tests ઉપરાંત, **`pr-test-policy` (test-masking) + સંપૂર્ણ deterministic
  unit suite** ચલાવો (અથવા ઓછામાં ઓછું static/parity files, જે ઝડપી અને non-flaky છે).
  આ રીતે જૂના tests અને assert removalને તે રજૂ કરનાર PRમાં જ પકડવામાં આવે છે — releaseના
  દિવસે નહીં. integration/e2eને બહાર રાખો (ધીમા/flaky), પરંતુ deterministic layer માત્ર
  PR→mainમાં જ રહી શકે નહીં.
- **G2 — Modularization parity gate (નવું, હાલમાં આવરી લેવાયેલું નથી).** એવી ચકાસણી કે જે modularized barrel (`src/shared/validation/schemas/*`, `providerRegistry`
  modules વગેરે) દ્વારા ફરીથી export કરાયેલા દરેક symbol માટે canonical
  source સામે તેનું **shape** (`z.object` keys, registry entries) સરખાવે અને **divergence પર નિષ્ફળ થાય**
  (છૂટી ગયેલું/વધારાનું field). આ #3988થી થયેલા 40-field dropને એ જ PRમાં પકડી લેત. આ હાથેથી લખેલા parity testsને
  સામાન્ય સ્વરૂપ આપે છે (જે માત્ર ત્યાં જ અસ્તિત્વ ધરાવે છે જ્યાં કોઈએ તેને લખવાનું યાદ રાખ્યું હોય).
  સસ્તું: બંનેને import કરીને `Object.keys(shape)`નો diff કરે છે.
- **G3 — Deterministic flake triage (સહાયક).** LiveWS-startup અને integration-combo/breaker
  tests CIમાં server timeout/cascade (env)ને કારણે નિષ્ફળ થાય છે, logicને કારણે નહીં. તેમને
  `known-flaky` તરીકે ચિહ્નિત કરો (issue સાથે quarantined), જેથી release-PRમાં દેખાતો red **માત્ર વાસ્તવિક signals** હોય, વચ્ચેના deterministic regressionsને
  ઢાંકી દેતો noise નહીં.

**સિદ્ધાંત:** _gate ત્યાં ચાલવો જોઈએ જ્યાં merge થાય છે_ ("Cross-cutting principles"માં પહેલેથી જ છે).
v3.8.27ની ઘટના દર્શાવે છે કે આ બાબત માત્ર lint/typecheckને નહીં, પણ **deterministic test layer**ને પણ લાગુ પડે છે —
અન્યથા જૂના tests + lossy modularizationનું દેવું માત્ર PR→mainમાં, એકસાથે, સૌથી
ખરાબ સમયે દેખાય છે.
