## જેનિટર ઇન્સ્ટૉલ કરો (એક વખત, બૉક્સ પર)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): દર 30 મિનિટે, /var/log/runner-janitor.logમાં લૉગ કરો
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` જરૂરી છે: જેનિટર કોઈ પાથને દૂર કરતાં પહેલાં ખુલ્લી
ફાઇલોનો એક સ્નૅપશૉટ લઈને તે નિષ્ક્રિય છે તે સાબિત કરે છે, અને આ સાધન વિના તે કશું દૂર કરતું નથી તથા એવું જણાવે છે
(exit 1). કોઈપણ ફેરફાર પહેલાં `--dry-run` વડે અજમાવો — તે બરાબર શું કરશે તે બતાવે છે
અને કશાને સ્પર્શતું નથી.

દરેક રન વખતે તે શું કરે છે: **tmpfs પર 3 કલાક** અને ડિસ્કના
`_work/_temp`માં 24 કલાક પછી આપણા પોતાના અવશેષો (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) સાફ કરે છે; 75 મિનિટથી જૂના `next-build`ને બંધ કરે છે (કોઈ જૉબ આટલો લાંબો ચાલતો નથી —
2026-08-27ના રોજ GitHubએ તેનો જૉબ ગુમ થયેલો જાહેર કર્યા પછી એક જૉબ 70 મિનિટ સુધી ચાલ્યો હતો); જેમના યુનિટ **બંધ** છે
તેવા રનરના 48 કલાક જૂના ચેકઆઉટ દૂર કરે છે; ડિસ્ક ≥ 85 %, મેમરી PSI
`full/avg60` ≥ 10 %, અને `MAX_ACTIVE_RUNNERS` કરતાં વધુ લિસનર હોય ત્યારે ચેતવણી આપે છે (સાથે
omniroute/અન્યનું વિભાજન). Exit 1 = ધ્યાન આપવું જરૂરી છે; લૉગ વાંચો.

## રનર યુનિટ્સ: KillMode

રનરનું ડિફૉલ્ટ `KillMode=process`, યુનિટને બંધ અથવા રીસ્ટાર્ટ કરવામાં આવે ત્યારે `Runner.Worker → npm → next-build`ને ચાલુ રાખે છે — કોઈ જોબ જોડાયેલી ન હોવા છતાં અનાથ બિલ્ડ RAM અને CPU વાપરતું રહે છે. દરેક OmniRoute યુનિટમાં
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
ડ્રૉપ-ઇન છે, જેમાં `KillMode=mixed` છે: પહેલાં listenerને SIGTERM અને
`TimeoutStop` પર આખા cgroupને SIGKILL. તે યુનિટના આગામી રીસ્ટાર્ટ વખતે અમલમાં આવે છે — **એક સમયે માત્ર એક રનરને, અને તે નિષ્ક્રિય હોય ત્યારે જ રીસ્ટાર્ટ કરો**, તેમજ નિષ્ક્રિયતાની ચકાસણી અને રીસ્ટાર્ટ એક જ કમાન્ડમાં કરો.

## સંચાલનના નિયમો

- **હેવી-બિલ્ડ મર્યાદા: એક સમયે માત્ર એક — લેબલ દ્વારા અમલમાં (2026-08-29થી).** સંપૂર્ણ `next build` ચલાવતી દરેક જોબ `[self-hosted, omni-build]`ને લક્ષ્ય બનાવે છે, અને માત્ર **`omniroute-113-5`** પાસે જ તે લેબલ છે (રનર્સ API દ્વારા ઉમેરેલું — ફરીથી નોંધણી નહીં): `ci.yml`નું `Build`, `npm-publish.yml`નું `publish`, બંને `nightly-release-green` માન્યતાઓ અને `docker-publish.yml`નું **amd64** (હોસ્ટેડ 7 GB પર આ ટ્રી માટે ResourceExhausted થયું — #11976). arm64 Docker લેગ webpack સાથે `ubuntu-24.04-arm` પર જ રહે છે (કોઈ ARM બૉક્સ નથી). Docker amd64 પણ webpack વાપરે છે: આ ટ્રી પર Turbopack, BuildKitની અંદર પૅનિક થયું (`TurbopackInternalError:
there must be a path to a root`, રન 33253576569), 31 GB હોવા છતાં; એ જ ટ્રીનું arm64 webpack બિલ્ડ હોસ્ટેડ ARM પર સફળ થયું. `docker-publish` amd64, `ci.yml`ના `Build` સાથે `heavy-build-main` concurrency ગ્રુપ શેર કરે છે (`cancel-in-progress: false`), તેથી તે એકમાત્ર સ્લોટ માટે કતારમાં રહે છે. Docker Engine `omniroute-113-5` પર હોવું આવશ્યક છે (`docker info` એ publish જોબનું પ્રથમ પગલું છે). પહેલાં મર્યાદા બે હતી, પરંતુ 31 GB માટે તે ખોટી હતી: 2026-08-29 17:26 UTCએ એકસાથે ચાલી રહેલા બે `next-build`s (15.4 GB + 17.2 GB RSS)એ બૉક્સને 5 GB ખાલી મેમરી અને ઉપયોગમાં રહેલા 4 GB swap સુધી પહોંચાડ્યો, અને kernelએ OOM દ્વારા તેમાંથી એકને બંધ કર્યું — systemdએ આ killને _બીજા_ રનરના યુનિટ પર નોંધ્યું, `runsvc.sh`એ તે listenerને SIGKILL કર્યું, અને તેના પરની જોબ "The runner has received a shutdown signal" સાથે બંધ થઈ ગઈ (હોસ્ટેડ-રનર OOM જેવો જ ટેક્સ્ટ). `omniroute-113-6` માત્ર `omni-release` જ રાખે છે. `main` merges, PRs અને nightlyના હેવી બિલ્ડ્સ હવે એક જ સ્લોટ પર ક્રમબદ્ધ રીતે ચાલે છે; કતાર તેની કિંમત છે. Proxmox VMને વધુ RAM (48–64 GB) મળે તે દિવસે બીજો સ્લોટ પાછો આવશે:
  `gh api -X POST repos/<repo>/actions/runners/<id of omniroute-113-6>/labels -f 'labels[]=omni-build'`.
- **લાઇટ પૂલ: `omni-light` (2026-08-29, #11965).** `omniroute-113` અને `omniroute-113-2` પાસે એવી જોબ્સ માટે `omni-light` છે, જેને માત્ર backend `next build` (~5–6 GB) જોઈએ છે, સંપૂર્ણ બિલ્ડ નહીં: nightly Schemathesis, promptfoo, garak અને axe-a11y જોબ્સ. તે હોસ્ટેડ 7 GB રનર પર ચાલી હતી અને કોઈ દેખરેખ રાખતું ન હતું ત્યારે `release/v3.8.51` પર બંધ થઈ ગઈ હતી. બૉક્સ પર સૌથી ખરાબ સ્થિતિ 2 heavy + 2 light ≈ 30 + 12 GB છે — 31 GB RAM કરતાં વધુ, પણ 16 GB swapની અંદર; headroom માટેનો વાસ્તવિક ઉકેલ Proxmox VM (`tomni-proxmox-113`) પર વધુ RAM છે, જે લેબલ મર્યાદાઓને 3 heavy + 2 lightમાં ફેરવે છે.
- **ઇરાદાપૂર્વક ઓછા listeners.** 2026-08-29ના રોજ ચાર OmniRoute યુનિટ્સ અક્ષમ કરવામાં આવ્યા હતા — માત્ર `ci.yml`નું `Build` અને nightlies બૉક્સનો ઉપયોગ કરતા હોવાથી, 8 listeners નિષ્ક્રિય હતા અને દરેક વધારાનો listener સંભવિત 14 GB tenant છે. janitorની મર્યાદા 6 છે (cronમાં `MAX_ACTIVE_RUNNERS=6`): તે બૉક્સ પરના દરેક `Runner.Listener`ની ગણતરી કરે છે, અને OmniHeuris + OmniMind અમારા ચાર ઉપરાંત વધુ બે ઉમેરે છે.
- **કોઈ પણ રનર વ્યસ્ત હોય ત્યારે `/tmp` અથવા `_work`ને ક્યારેય હાથેથી સાફ કરશો નહીં.** ચકાસણી અને કાઢી નાખવા વચ્ચે વિરામ રાખીને કરાયેલી check-then-delete પ્રક્રિયાને કારણે 2026-08-27ના રોજ ચાલુ Build જોબે તેનું `_work` ગુમાવ્યું હતું. janitor ચકાસણી અને દૂર કરવાની ક્રિયા એક જ પગલામાં કરે છે; તેને જ કરવા દો.
- જોબની વચ્ચે રનરને રોકવાથી જોબ રદ થાય છે (લાઇવ નિરીક્ષણ મુજબ): `systemctl stop` માત્ર ત્યારે જ કરો જ્યારે તેના listener પાસે કોઈ `Runner.Worker` child ન હોય — અને તે એક જ કમાન્ડમાં કરો.
- Workflowsએ artefactsને `/tmp`માં રાખવા નહીં (તે RAM છે). `$RUNNER_TEMP`માં ડાઉનલોડ કરો (ડિસ્ક પર, દરેક રનર માટે અલગ) — 1.3 GB `next-build` artefactને tmpfs પર આવવામાં 27–32 મિનિટ લાગી હતી અને ડિસ્ક પરથી અપલોડ કરવામાં 2 મિનિટ લાગી હતી.
- `.15` VPS માત્ર homologation માટે છે — તેના પર ક્યારેય CI રનર્સ ચાલતા નથી.
