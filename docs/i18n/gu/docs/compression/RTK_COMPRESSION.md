RTK કમ્પ્રેશન એ ટર્મિનલ અને ટૂલ આઉટપુટ માટેનું OmniRouteનું કમાન્ડ-સજાગ કમ્પ્રેશન એન્જિન છે. તેને
કોડિંગ-એજન્ટ સત્રો માટે ડિઝાઇન કરવામાં આવ્યું છે, જેમાં સંદર્ભનો મોટાભાગનો વધારો ટેસ્ટ લૉગ્સ, બિલ્ડ આઉટપુટ,
પૅકેજ મેનેજરનો ઘોંઘાટ, શેલ ટ્રાન્સક્રિપ્ટ્સ, Docker આઉટપુટ, git આઉટપુટ અને સ્ટૅક ટ્રેસમાંથી થાય છે.

RTK સીધું `defaultMode: "rtk"` સાથે અથવા સ્ટૅક્ડ પાઇપલાઇનના પ્રથમ પગલા તરીકે ચાલી શકે છે, સામાન્ય રીતે:

```txt
rtk -> caveman
```

આ ક્રમ પહેલાં ઘોંઘાટભર્યા મશીન આઉટપુટને સંકુચિત કરે છે, ત્યારબાદ Cavemanને બાકી રહેલા ગદ્યને સંક્ષિપ્ત કરવા દે છે.

અપસ્ટ્રીમ RTK કમાન્ડ આઉટપુટમાં `60-90%` બચત દર્શાવે છે. તેના READMEના નમૂના સત્રમાં
`~118,000` પ્રમાણભૂત ટોકન્સ ઘટીને `~23,900` RTK ટોકન્સ થાય છે, એટલે `79.7%` બચત (`~80%`). OmniRoute,
Caveman ઇનપુટ કમ્પ્રેશન સાથે સ્ટૅક્ડ બચતની ગણતરી માટે તે અપસ્ટ્રીમ સરેરાશનો ઉપયોગ કરે છે:

```txt
RTK સરેરાશ:     80% બચત
Caveman ઇનપુટ:  46% બચત
સ્ટૅક્ડ:         1 - (1 - 0.80) * (1 - 0.46) = 89.2% બચત
શ્રેણી:         1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

## તે શું સંકુચિત કરે છે

બિલ્ટ-ઇન કૅટલૉગ હાલમાં આ શ્રેણીઓમાં 49 ફિલ્ટર્સ પ્રદાન કરે છે:

| શ્રેણી    | ઉદાહરણો                                                       |
| --------- | ------------------------------------------------------------- |
| `git`     | `git status`, `git branch`, `git diff`, `git log`             |
| `test`    | Vitest, Jest, Pytest, Playwright, Go ટેસ્ટ્સ, Cargo ટેસ્ટ્સ   |
| `build`   | TypeScript, ESLint, Biome, Prettier, Vite, Webpack, Turbo, Nx |
| `package` | `npm install`, `npm audit`, `pip`, `uv sync`, Poetry, Bundler |
| `shell`   | `ls`, `find`, `grep`, સામાન્ય શેલ લૉગ્સ                       |
| `docker`  | `docker ps`, Docker લૉગ્સ                                     |
| `infra`   | Terraform, OpenTofu, `systemctl status`                       |
| `generic` | JSON આઉટપુટ, સ્ટૅક ટ્રેસ, સામાન્ય આઉટપુટ ફૉલબૅક               |

`open-sse/services/compression/engines/rtk/commandDetector.ts`માં આવેલું ડિટેક્ટર ફિલ્ટર પસંદગી
પહેલાં આઉટપુટનું વર્ગીકરણ કરે છે. જ્યારે કમાન્ડ ક્લાસ પૂરતો ન હોય ત્યારે ફિલ્ટર્સ કમાન્ડ પેટર્ન અથવા આઉટપુટ રેગેક્સ દ્વારા પણ
મેળ ખાઈ શકે છે.

## ફિલ્ટર રિઝોલ્યુશન

RTK ફિલ્ટર્સને આ ક્રમમાં લોડ કરે છે:

1. `.rtk/filters.toml` અને `.rtk/filters.json`માંથી પ્રોજેક્ટ ફિલ્ટર્સ, માત્ર વિશ્વસનીય હોય ત્યારે.
2. `DATA_DIR/rtk/filters.toml` અને `DATA_DIR/rtk/filters.json`માંથી ગ્લોબલ ફિલ્ટર્સ.
3. `open-sse/services/compression/engines/rtk/filters/`માંથી બિલ્ટ-ઇન ફિલ્ટર્સ.

સમાન સ્કોપમાં, RTK TOML schema v1 ફિલ્ટર્સને OmniRoute JSON ફિલ્ટર્સ કરતાં અગ્રતા મળે છે. TOML
`match_command` એક્સપ્રેશન્સને કમાન્ડ-ટાઇપ મેચિંગ પહેલાં તપાસવામાં આવે છે, જેથી ઇમ્પોર્ટ કરેલું કમાન્ડ-વિશિષ્ટ
ફિલ્ટર તે સ્કોપમાં વધુ વ્યાપક ફિલ્ટરને ઓવરરાઇડ કરી શકે. ફાઇલ ફૉર્મેટ ગમે તે હોય, પ્રોજેક્ટ સ્કોપને હજી પણ ગ્લોબલ
સ્કોપ કરતાં અગ્રતા મળે છે.

પ્રોજેક્ટ ફિલ્ટર્સને ઇરાદાપૂર્વક ટ્રસ્ટ-ગેટ કરવામાં આવ્યા છે, કારણ કે રેગેક્સ ફિલ્ટર્સ ટૂલ આઉટપુટ એજન્ટોને
કેવી રીતે બતાવવામાં આવે છે તે બદલી શકે છે. નીચેમાંથી કોઈ એક બાબત સાચી હોય ત્યારે પ્રોજેક્ટ ફિલ્ટર ફાઇલ સ્વીકારવામાં આવે છે:

- `rtkConfig.trustProjectFilters`નું મૂલ્ય `true` છે.
- `OMNIROUTE_RTK_TRUST_PROJECT_FILTERS=1` સેટ કરેલું છે.
- `.rtk/trust.json`માં પ્રોજેક્ટ ફિલ્ટર ફાઇલ માટે મેળ ખાતો SHA-256 હૅશ છે.

ટ્રસ્ટ ફાઇલનું ઉદાહરણ:

```json
{
  "filtersSha256": "0123456789abcdef...",
  "filtersTomlSha256": "fedcba9876543210..."
}
```

હૅશ અલગ છે: `filtersSha256` `.rtk/filters.json` પર વિશ્વાસ કરે છે, જ્યારે `filtersTomlSha256`
`.rtk/filters.toml` પર વિશ્વાસ કરે છે. કોઈપણ ફાઇલને સંપાદિત કરવાથી માત્ર તેની પોતાની ટ્રસ્ટ એન્ટ્રી અમાન્ય થાય છે. ગ્લોબલ ફાઇલો
એડમિનિસ્ટ્રેટર દ્વારા ઇન્સ્ટૉલ કરવામાં આવે છે અને હાલની ગ્લોબલ-ફિલ્ટર ટ્રસ્ટ કાર્યપદ્ધતિનો ઉપયોગ કરે છે.

કસ્ટમ ફિલ્ટર્સ એક ફિલ્ટર ઑબ્જેક્ટ અથવા ફિલ્ટર ઑબ્જેક્ટ્સની ઍરે હોઈ શકે છે. અમાન્ય કસ્ટમ ફિલ્ટર્સને
છોડી દેવામાં આવે છે અને `/api/context/rtk/filters` ડાયગ્નોસ્ટિક્સ દ્વારા રિપોર્ટ કરવામાં આવે છે. અમાન્ય બિલ્ટ-ઇન ફિલ્ટર્સ તરત નિષ્ફળ જાય છે.

## RTK TOML schema v1 સુસંગતતા

OmniRoute, RTK TOML schema v1 નો ઉપયોગ કરતી ઘોષણાત્મક ફિલ્ટર ફાઇલોને પાર્સ, માન્ય, પરીક્ષણ અને ઇન્સ્ટોલ કરી શકે છે.
સપોર્ટેડ ફીલ્ડ્સ `description`, `match_command`, `strip_ansi`, `filter_stderr`,
`strip_lines_matching`, `keep_lines_matching`, `replace`, `match_output`, `truncate_lines_at`,
`head_lines`, `tail_lines`, `max_lines`, `on_empty`, અને `[[tests.<filter>]]` ઇનલાઇન પરીક્ષણો છે.
અજ્ઞાત ફીલ્ડ્સ, અમાન્ય અથવા અસુરક્ષિત રેગ્યુલર એક્સપ્રેશન્સ, એકસાથે ઉપયોગમાં લેવાતા strip/keep નિયમો, 1 MiB કરતાં મોટી ફાઇલો
અને અજ્ઞાત ફિલ્ટર્સના સંદર્ભો નકારવામાં આવે છે. જે ફાઇલનાં ઇનલાઇન પરીક્ષણો નિષ્ફળ જાય તેને
નિરીક્ષણ માટે માન્ય કરી શકાય છે, પરંતુ તેને ઇન્સ્ટોલ કે લોડ કરી શકાતી નથી. કસ્ટમ ફાઇલ લોડ કરવામાં થતી નિષ્ફળતાઓ
fail-open રહે છે: અમાન્ય ફાઇલને છોડી દેવામાં આવે છે અને બાકીના ફિલ્ટર્સ કાર્યરત રહે છે.

ક્લાયન્ટ દ્વારા ટૂલનું આઉટપુટ પહેલેથી જ કૅપ્ચર થઈ ગયા પછી OmniRoute તેને પ્રાપ્ત કરે છે, તેથી `filter_stderr = true`
પ્રોસેસ કૅપ્ચરને બદલી શકતું નથી. આ ફીલ્ડને કોઈ અસર ન કરતી ક્રિયા તરીકે સ્વીકારવામાં આવે છે અને માન્યતા પ્રક્રિયા ચેતવણી આપે છે.
આને ઇરાદાપૂર્વક **RTK TOML schema v1 સુસંગતતા** તરીકે વર્ણવવામાં આવ્યું છે, RTK એક્ઝિક્યુટેબલ,
શેલ હુક્સ, Rust કમાન્ડ અમલીકરણો અથવા તેના trust-store લેઆઉટ સાથેની સંપૂર્ણ સુસંગતતા તરીકે નહીં.

ડૅશબોર્ડનું અદ્યતન RTK દૃશ્ય પેસ્ટ કરેલું અથવા અપલોડ કરેલું TOML સ્વીકારે છે. માન્યતા પ્રક્રિયા માત્ર વાંચવા માટે છે.
ઇન્સ્ટોલેશન પ્રતિબંધિત પરવાનગીઓ સાથે `DATA_DIR/rtk/filters.toml` ને અખંડિત રીતે લખે છે અને
પુનઃપ્રારંભ કર્યા વિના લાઇવ ફિલ્ટર કૅટલૉગને રિફ્રેશ કરે છે. હાલની ફાઇલ બદલવા માટે સ્પષ્ટ `overwrite`
પુષ્ટિ જરૂરી છે અને પહેલાં `DATA_DIR/rtk/filters.toml.bak` બનાવવામાં આવે છે.

## ફિલ્ટર DSL

ફિલ્ટર્સ [Compression Rules Format](./COMPRESSION_RULES_FORMAT.md) માં વર્ણવેલી JSON સ્કીમાનો ઉપયોગ કરે છે.
રનટાઇમ આ તબક્કાઓને નીચેના ક્રમમાં લાગુ કરે છે:

```txt
stripAnsi -> filterStderr -> replace -> matchOutput -> drop/include lines
  -> truncateLineAt -> head/tail/maxLines -> onEmpty
```

મહત્વપૂર્ણ ફીલ્ડ્સ:

| ફીલ્ડ                        | હેતુ                                                                              |
| ---------------------------- | --------------------------------------------------------------------------------- |
| `rules.stripAnsi`            | મેળ બેસાડતાં પહેલાં ટર્મિનલના રંગ/નિયંત્રણ ક્રમો દૂર કરવા                         |
| `rules.filterStderr`         | મેળ બેસાડતાં/ફિલ્ટર કરતાં પહેલાં સામાન્ય stderr ઉપસર્ગોને સામાન્ય સ્વરૂપમાં લાવવા |
| `rules.replace`              | ક્રમબદ્ધ regex બદલીઓ લાગુ કરવા                                                    |
| `rules.matchOutput`          | આઉટપુટ કોઈ જાણીતી સ્થિતિ સાથે મેળ ખાય ત્યારે સંક્ષિપ્ત સારાંશ પરત કરવા            |
| `rules.matchOutput[].unless` | ભૂલ/નિષ્ફળતાની પેટર્ન હાજર હોય ત્યારે શૉર્ટકટ છોડવા                               |
| `rules.dropPatterns`         | બિનજરૂરી અવાજવાળી પંક્તિઓ દૂર કરવા                                                |
| `rules.includePatterns`      | કાર્યવાહી કરી શકાય તેવી પંક્તિઓને પ્રાથમિકતા આપવા                                 |
| `rules.collapsePatterns`     | વારંવાર આવતી મેળ ખાતી પંક્તિઓને સંકુચિત કરવા                                      |
| `rules.deduplicate`          | પ્રતિ-ફિલ્ટર વૈકલ્પિક પસંદગી: સળંગ પુનરાવર્તિત પંક્તિઓને સંકુચિત કરવા             |
| `rules.truncateLineAt`       | Unicode-સુરક્ષિત પ્રતિ-પંક્તિ સંક્ષેપ                                             |
| `rules.onEmpty`              | બધી પંક્તિઓ ફિલ્ટર થઈ જાય તો વૈકલ્પિક સંદેશ                                       |
| `tests[]`                    | ચકાસણી ગેટ દ્વારા ઉપયોગમાં લેવાતા ઇનલાઇન નમૂનાઓ                                   |

બિલ્ટ-ઇન ફિલ્ટર્સમાં ઇનલાઇન `tests[]` નમૂનાઓનો સમાવેશ અપેક્ષિત છે. કસ્ટમ ફિલ્ટર્સમાં પણ
તેમનો સમાવેશ કરવો જોઈએ, ખાસ કરીને જ્યારે તેઓ વિવિધ પ્રોજેક્ટ્સમાં શેર કરવામાં આવતા હોય.

## લાઇન ડિડુપ્લિકેશન (બે સ્તરો)

RTK બે સ્વતંત્ર સ્તરો પર ડુપ્લિકેટ લાઇનોને સંકુચિત કરે છે:

1. **ફિલ્ટર-દીઠ `deduplicate` (ઑપ્ટ-ઇન, ડિફૉલ્ટ `false`).** કોઈ ફિલ્ટર `rules.deduplicate: true`
   સેટ કરીને, કાપછાંટ પહેલાં, _તે ફિલ્ટરના મેળ ખાતા આઉટપુટની અંદર_ આવતી સળંગ ડુપ્લિકેટ લાઇનોને
   સંકુચિત કરી શકે છે. આ `lineFilter.ts` ની અંદર ચાલે છે. લેગસી ફિલ્ટર્સ માટે, જ્યારે ફિલ્ટર
   `collapsePatterns` વ્યાખ્યાયિત કરે છે ત્યારે તે આપમેળે સક્ષમ થાય છે. સ્કીમા:
   `open-sse/services/compression/engines/rtk/filterSchema.ts` માં
   `deduplicate: z.boolean().default(false)`.
2. **એન્જિન-વ્યાપી `deduplicateThreshold` (ડિફૉલ્ટ `3`).** બધા ફિલ્ટર્સ ચાલી ગયા પછી, એન્જિન
   સમગ્ર પરિણામમાં `>= deduplicateThreshold` જેટલી એકસરખી સળંગ લાઇનોના કોઈપણ ક્રમને સંકુચિત
   કરે છે (`deduplicateRepeatedLines`, જે `engines/rtk/index.ts` માં લાગુ થાય છે). નોર્મલાઇઝેશન
   દરમિયાન આ મૂલ્ય 2–100ની મર્યાદામાં રાખવામાં આવે છે.

ફિલ્ટર-દીઠ પાસ પહેલાં ચાલે છે (ફિલ્ટરની અંદર), જ્યારે એન્જિન-વ્યાપી પાસ છેલ્લે ચાલે છે (જોડાયેલા
આઉટપુટ પર), તેથી બંને બેવડી ગણતરી કર્યા વિના સંયોજિત થાય છે.

## લાઇન ગ્રુપિંગ (`enableGrouping`)

જ્યારે `rtkConfig.enableGrouping` `true` હોય છે (ડિફૉલ્ટ `false`), ત્યારે RTK ડિડુપ્લિકેશન પછીના
પરિણામ પર વધારાનો `groupSimilarLines` પાસ ચલાવે છે, જે _લગભગ સમકક્ષ_ (બાઇટ-દર-બાઇટ એકસરખી નહીં)
સળંગ લાઇનોના ક્રમને સંકુચિત કરે છે. `rtkConfig.groupingThreshold` (ડિફૉલ્ટ `3`) એ ગ્રુપિંગ શરૂ
કરવા માટે જરૂરી ન્યૂનતમ ક્રમ-લંબાઈ છે. આ `deduplicateThreshold` નો માળખાકીય સમકક્ષ છે:
ડિડુપ્લિકેશન ચોક્કસ પુનરાવર્તનોને સંભાળે છે, જ્યારે ગ્રુપિંગ "નાના તફાવતો સાથે સમાન આકાર" ધરાવતી
લાઇનોને સંભાળે છે. બંને ફ્લૅગ `key_value` ટેબલમાં સાચવવામાં આવતા `rtkConfig` JSON નો ભાગ છે
(ઉપરનું રૂપરેખાંકન જુઓ), તેથી સેટિંગ પુનઃપ્રારંભ પછી પણ જળવાઈ રહે છે.

## કોડ ટિપ્પણીઓ દૂર કરવી (`stripCodeComments` / `preserveDocstrings`)

જ્યારે `rtkConfig.applyToCodeBlocks` સક્ષમ હોય છે, ત્યારે RTK ફેન્સ કરેલા કોડ બ્લૉક્સમાંથી ટિપ્પણીઓ
પણ દૂર કરી શકે છે:

- `stripCodeComments` (ડિફૉલ્ટ `false`) — ઑપ્ટ-ઇન. જ્યારે `true` હોય, ત્યારે RTK JavaScript
  અને TypeScript ના ફેન્સ કરેલા બ્લૉક્સમાંથી ટિપ્પણીઓ દૂર કરે છે. ઐતિહાસિક રીતે આ ફ્લૅગ વાંચવામાં
  આવતો હતો પરંતુ ક્યારેય લાગુ કરાતો નહોતો, તેથી કોઈ અઘોષિત પ્રોડક્શન ફેરફાર ટાળવા માટે ડિફૉલ્ટ
  "જાળવી રાખો" રહે છે.
- `preserveDocstrings` (ડિફૉલ્ટ `true`) — ટિપ્પણીઓ દૂર કરતી વખતે, JSDoc/`/** … */` બ્લૉક
  ટિપ્પણીઓ જાળવી રાખવામાં આવે છે (તેમાં રહેલું API દસ્તાવેજીકરણ તેના માટે વપરાતા બાઇટ્સ કરતાં
  વધુ મૂલ્યવાન છે). તેને પણ દૂર કરવા માટે `false` સેટ કરો.

ટિપ્પણીઓ દૂર કરવાની પ્રક્રિયા `open-sse/services/compression/engines/rtk/codeStripper.ts` માં
અમલમાં મૂકવામાં આવી છે. તે **TypeScript parser** નો ઉપયોગ કરે છે (regex નો નહીં), જેથી string,
template અને regex literals ને ક્યારેય ભૂલથી ટિપ્પણીઓ માનવામાં ન આવે, અને JSX મળતાં જ તે પ્રક્રિયા
સંપૂર્ણપણે અટકાવી દે છે (જેથી JSX expression-container ટિપ્પણીઓ ક્યારેય બગડે નહીં). હાલમાં
ટિપ્પણીઓ દૂર કરવાની પ્રક્રિયા માત્ર **JavaScript અને TypeScript** પર લાગુ પડે છે — સ્ટ્રિપરના
`CodeLanguage` સમૂહની અન્ય ભાષાઓ (Python, Rust, Go, Ruby, Java) માટે ખાલી લાઇન અને વ્હાઇટસ્પેસનું
સંકોચન થાય છે, પરંતુ ટિપ્પણીઓ દૂર થતી નથી. સ્ટ્રિપ કરેલા બ્લૉકની પ્રક્રિયાને `rulesApplied` માં
`rtk:code-strip` ટૅગ આપવામાં આવે છે.

> **નોંધ — GCF / ટૅબ્યુલર એન્કોડિંગ એક અલગ એન્જિન છે.** RTK માં "GCF"
> (Graph Compact Format) ટૅબ્યુલર/કૉલમ્નર JSON એન્કોડર સમાવાયેલ નથી. એ એન્કોડર — જેણે જૂના
> `omni-tabular` એન્કોડરને બદલ્યું હતું — **headroom** એન્જિનમાં આવેલું છે
> (`open-sse/services/compression/engines/headroom/`, જેમાં vendored codec
> `headroom/gcf/` હેઠળ છે). અહીં દસ્તાવેજીકૃત RTK ફિલ્ટર પાઇપલાઇન સાથે તેનો કોઈ સંબંધ નથી.

## રૂપરેખાંકન

વૈશ્વિક સેટિંગ્સ `/api/settings/compression` મારફતે ઉપલબ્ધ છે. RTK-વિશિષ્ટ સેટિંગ્સ પણ
`/api/context/rtk/config` મારફતે ઉપલબ્ધ છે.

```json
{
  "defaultMode": "stacked",
  "autoTriggerMode": "stacked",
  "autoTriggerTokens": 32000,
  "stackedPipeline": [
    { "engine": "rtk", "intensity": "standard" },
    { "engine": "caveman", "intensity": "full" }
  ],
  "rtkConfig": {
    "enabled": true,
    "intensity": "standard",
    "applyToToolResults": true,
    "applyToCodeBlocks": false,
    "applyToAssistantMessages": false,
    "enabledFilters": [],
    "disabledFilters": [],
    "maxLinesPerResult": 120,
    "maxCharsPerResult": 12000,
    "deduplicateThreshold": 3,
    "customFiltersEnabled": true,
    "trustProjectFilters": false,
    "rawOutputRetention": "never",
    "rawOutputMaxBytes": 1048576,
    "enableGrouping": false,
    "groupingThreshold": 3,
    "stripCodeComments": false,
    "preserveDocstrings": true
  }
}
```

`enabledFilters` અને `disabledFilters` ફિલ્ટર ids નો ઉપયોગ કરે છે, ઉદાહરણ તરીકે `test-vitest` અથવા `git-diff`.

સંપૂર્ણ `rtkConfig` માળખું `open-sse/services/compression/types.ts` માં `RtkConfig` / `DEFAULT_RTK_CONFIG` દ્વારા વ્યાખ્યાયિત થયેલું છે. આખો ઑબ્જેક્ટ SQLite `key_value` કોષ્ટકમાં
`namespace = "compression"`, `key = "rtkConfig"` હેઠળ એક જ JSON મૂલ્ય તરીકે સંગ્રહિત થાય છે
(`/src/lib/db/compression.ts`), અને વાંચતી વખતે `normalizeRtkConfig` દ્વારા સામાન્યકૃત થાય છે. તેથી નીચેનું દરેક ફીલ્ડ
— જેમાં `enableGrouping`, `groupingThreshold`, `stripCodeComments`, અને `preserveDocstrings` સામેલ છે —
એ જ સ્ટોર મારફતે રાઉન્ડ-ટ્રિપ થાય છે અને પુનઃપ્રારંભ પછી પણ જળવાઈ રહે છે.

| કી                     | ડિફૉલ્ટ | હેતુ                                                                               |
| ---------------------- | ------- | ---------------------------------------------------------------------------------- |
| `deduplicateThreshold` | `3`     | સમગ્ર એન્જિન માટે: સંકોચવા માટે ન્યૂનતમ સળંગ સમાન લાઇનો (2–100 સુધી મર્યાદિત)      |
| `enableGrouping`       | `false` | વૈકલ્પિક: લગભગ સમકક્ષ સળંગ લાઇનોના ક્રમોને સંકોચો                                  |
| `groupingThreshold`    | `3`     | ગ્રુપિંગને ટ્રિગર કરતો સમાન લાઇનોનો ન્યૂનતમ સળંગ ક્રમ                              |
| `stripCodeComments`    | `false` | વૈકલ્પિક: ફેન્સ્ડ કોડ બ્લોક્સમાંથી ટિપ્પણીઓ દૂર કરો (`applyToCodeBlocks` જરૂરી છે) |
| `preserveDocstrings`   | `true`  | ટિપ્પણીઓ દૂર કરતી વખતે JSDoc/`/** … */` બ્લોક્સ જાળવી રાખો                         |

| `/api/context/rtk/raw-output/[id]` | GET    | જાળવી રાખેલું સંવેદનશીલ માહિતીથી સંપાદિત કાચું આઉટપુટ વાંચો |
| `/api/compression/preview`         | POST   | કોઈપણ કમ્પ્રેશન મોડનું પૂર્વાવલોકન કરો                      |

RTK પરીક્ષણ પેલોડ:

```json
{
  "command": "npm test",
  "text": "FAIL tests/example.test.ts\nAssertionError: expected true\nTest Files 1 failed",
  "config": {
    "intensity": "standard"
  }
}
```

કમ્પ્રેશન પૂર્વાવલોકન પેલોડ:

```json
{
  "mode": "stacked",
  "messages": [
    {
      "role": "tool",
      "content": "FAIL tests/example.test.ts\nAssertionError: expected true\nTest Files 1 failed"
    }
  ],
  "config": {
    "rtkConfig": {
      "rawOutputRetention": "failures"
    }
  }
}
```

મેનેજમેન્ટ રૂટ્સ માટે ડૅશબોર્ડ મેનેજમેન્ટ પ્રમાણીકરણ અથવા મેળ ખાતી API-key નીતિ જરૂરી છે.

RTK TOML માન્યતા પેલોડ:

```json
{
  "action": "validate",
  "content": "schema_version = 1\n\n[filters.my-tool]\nmatch_command = \"^my-tool\\\\b\"\nmax_lines = 20\n"
}
```

માન્ય કરેલી ફાઇલને વૈશ્વિક સ્તરે ઇન્સ્ટોલ કરવા માટે `"action": "install"` નો ઉપયોગ કરો. હાલની વૈશ્વિક ફાઇલને બદલવાની સમીક્ષા અને પુષ્ટિ કર્યા પછી જ `"overwrite": true` ઉમેરો.

## મૂળ આઉટપુટ પુનઃપ્રાપ્તિ

RTK સામાન્ય રીતે માત્ર સંકુચિત ટેક્સ્ટ પરત કરે છે. ડિબગિંગ માટે, `rawOutputRetention` રિડેક્ટ કરેલું
મૂળ આઉટપુટ જાળવી શકે છે:

| મૂલ્ય      | વર્તન                                          |
| ---------- | ---------------------------------------------- |
| `never`    | મૂળ આઉટપુટ જાળવશો નહીં                         |
| `failures` | ફક્ત સંભવિત નિષ્ફળતાનું આઉટપુટ જાળવો           |
| `always`   | રિડૅક્શન પછી દરેક સંકુચિત RTK મૂળ આઉટપુટ જાળવો |

જાળવેલી ફાઇલો આની અંદર લખવામાં આવે છે:

```txt
DATA_DIR/rtk/raw-output/
```

સ્થાયી સંગ્રહ પહેલાં સિક્રેટ્સ રિડેક્ટ કરવામાં આવે છે, જેમાં સામાન્ય bearer tokens, API keys, Slack tokens,
AWS access keys અને assignment-style `token=...`, `secret=...`, `password=...` મૂલ્યોનો સમાવેશ થાય છે. Analytics
માત્ર pointer id, કદ અને hash metadata સંગ્રહે છે.

## RTK નું વિસ્તરણ

1. filter JSON ફાઇલ ઉમેરો અથવા અપડેટ કરો.
2. મહત્વપૂર્ણ વર્તન સાબિત કરતું ઓછામાં ઓછું એક `tests[]` નમૂનો સામેલ કરો.
3. નવા command પરિવારો માટે `tests/unit/compression/fixtures/rtk/` હેઠળ fixture ઉમેરો.
4. નવો output class રજૂ કરતી વખતે command detection coverage ઉમેરો.
5. ચકાસણી અને વ્યાપક RTK ગેટ્સ ચલાવો.
6. જો filter પ્રોજેક્ટ-લોકલ હોય, તો `.rtk/filters.json` commit કરો અને સમીક્ષા પછી જ `.rtk/trust.json` refresh કરો.

## તીવ્રતાના સ્તરો (v3.8.16+)

RTK **3 તીવ્રતાના સ્તરો**ને સપોર્ટ કરે છે, જે **compression aggressiveness** અને **સલામતી** વચ્ચે સંતુલન સાધે છે. engine config માં `config.intensity` દ્વારા સ્તર સેટ થાય છે.

### 3 સ્તરો

| સ્તર                 | Truncation threshold | Token બચત | જોખમ     | આ માટે શ્રેષ્ઠ                      |
| -------------------- | -------------------- | --------- | -------- | ----------------------------------- |
| `minimal`            | વિભાગ દીઠ 24 લાઇન્સ  | ~20-40%   | ખૂબ ઓછું | નિર્ણાયક context ધરાવતું Production |
| `standard` (ડિફૉલ્ટ) | વિભાગ દીઠ 24 લાઇન્સ  | ~50-70%   | ઓછું     | દૈનિક coding sessions               |
| `aggressive`         | વિભાગ દીઠ 16 લાઇન્સ  | ~70-90%   | મધ્યમ    | લાંબા sessions, મહત્તમ બચત          |

### Truncation ક્યાં થાય છે

truncation threshold `lineFilter.ts`ને અસર કરે છે:

```ts
// open-sse/services/compression/engines/rtk/index.ts:329-330માંથી
config.intensity === "aggressive" ? 16 : 24,
config.intensity === "aggressive" ? 16 : 24,
```

દરેક વિભાગની **શરૂઆત** અને **અંત** બંને જાળવવામાં આવે છે; truncation અમલમાં આવે ત્યારે મધ્યવર્તી સામગ્રી દૂર કરવામાં આવે છે.

### શું જળવાય છે અને શું કાપવામાં આવે છે

| સામગ્રી                    | minimal       | standard      | aggressive    |
| -------------------------- | ------------- | ------------- | ------------- |
| Errors / stack traces      | ✅ જળવાય છે   | ✅ જળવાય છે   | ✅ જળવાય છે   |
| Test failures              | ✅ જળવાય છે   | ✅ જળવાય છે   | ✅ જળવાય છે   |
| Build errors               | ✅ જળવાય છે   | ✅ જળવાય છે   | ✅ જળવાય છે   |
| Test passes (verbose)      | ✅ જળવાય છે   | 🟡 સંકોચાય છે | 🟡 સંકોચાય છે |
| Routine output (info logs) | 🟡 સંકોચાય છે | 🟡 સંકોચાય છે | ❌ દૂર થાય છે |
| Progress bars              | 🟡 સંકોચાય છે | ❌ દૂર થાય છે | ❌ દૂર થાય છે |
| Banner / ASCII art         | 🟡 સંકોચાય છે | ❌ દૂર થાય છે | ❌ દૂર થાય છે |

### યોગ્ય તીવ્રતા પસંદ કરવી

```
                  શું context ગુમાવવું વિનાશક છે?
                  │
      ┌───────────┼───────────┐
      │           │           │
     હા          ના       ખાતરી નથી
      │           │           │
      ▼           │           │
   minimal        │           │
      │           │           │
      │           ▼           ▼
      │      throughput કેટલું  પહેલાં `standard` અજમાવો
      │      નિર્ણાયક છે?     (80% કિસ્સાઓ માટે
      │           │          કાર્ય કરે છે)
      │      ┌────┴────┐
      │      │         │
      │     ઓછું      વધુ
      │      │         │
      │      ▼         ▼

      │      │         │
      └──────┴─────────┘
```

### તીવ્રતા configure કરવી

**Per-combo** (combo config માં):

```json

  "routing": {/* ... */},
  "compression": {
    "engine": "rtk",
    "intensity": "aggressive"
  }

```

**પ્રોગ્રામેટિક રીતે**:

`rtkEngine` (`@omniroute/open-sse/services/compression/engines/rtk`) એક
`CompressionEngine` છે અને તેમાં `updateConfig` method નથી. તેના બદલે registry helper
દ્વારા engine નું config અપડેટ કરો:

```ts
import { updateEngineConfig } from "@omniroute/open-sse/services/compression/engines/registry";

updateEngineConfig("rtk", { intensity: "aggressive" });
```

### કસ્ટમ ફિલ્ટર લોડ કરવા

ફાઇલને માન્ય સ્થાન પર મૂકો:

```
~/.omniroute/rtk/filters/my-filter.json     # વપરાશકર્તા-સ્તર
<project>/.rtk/filters/my-filter.json      # પ્રોજેક્ટ-સ્તર
```

ફિલ્ટર સ્ટાર્ટઅપ વખતે `open-sse/services/compression/engines/rtk/filterLoader.ts`માંના `loadRtkFilters()` દ્વારા આપમેળે લોડ થાય છે. લોડર નીચેના સ્થાનોમાંથી ફિલ્ટર શોધે છે:

- બિલ્ટ-ઇન કૅટલૉગ: `open-sse/services/compression/engines/rtk/filters/`
- વપરાશકર્તા ડિરેક્ટરી: `~/.omniroute/rtk/filters/`
- પ્રોજેક્ટ ડિરેક્ટરી: `<project>/.rtk/filters/`

પ્રોગ્રામેટિક રીતે ફિલ્ટર લોડ કરવા માટે:

```ts
import { loadRtkFilters } from "@omniroute/open-sse/services/compression/engines/rtk/filterLoader";

// વિકલ્પો: customFiltersEnabled (વપરાશકર્તા/પ્રોજેક્ટ ફિલ્ટર લોડ કરો, ડિફૉલ્ટ રૂપે ચાલુ),
// trustProjectFilters, refresh.
const filters = loadRtkFilters({ customFiltersEnabled: true });
```

### માન્યતા

લોડ કરતી વખતે ફિલ્ટરને Zod સ્કીમા સામે માન્ય કરવામાં આવે છે. ખોટી સંરચનાવાળું ફિલ્ટર લોડ થવામાં નિષ્ફળ જશે અને ભૂલ લૉગ કરશે:

```
RTK_FILTER_LOADER: ફિલ્ટર "my-filter" માન્યતા તપાસમાં નિષ્ફળ ગયું:
  - rules.replace.0.pattern: અમાન્ય regex
  - match.commands: ખાલી ન હોવું જોઈએ
```

ઇન્સ્ટૉલ કરેલા બધા ફિલ્ટરની માન્યતા તપાસવા માટે, `open-sse/services/compression/engines/rtk/verify.ts`માંથી એક્સપોર્ટ કરાયેલ `runRtkFilterTests()` કૉલ કરો.

### શ્રેષ્ઠ પ્રથાઓ

1. **હંમેશા `tests[]` સામેલ કરો** — તે સાબિત કરે છે કે તમારું ફિલ્ટર કાર્ય કરે છે અને રિગ્રેશન અટકાવે છે
2. **શોર્ટ-સર્કિટ માટે `matchOutput` વાપરો** — જો એક જ લાઇન આખી વાત કહી દેતી હોય, તો આખા બ્લોકને બદલી દો
3. **`strip` કરતાં `keep` ને પ્રાધાન્ય આપો** — સ્પષ્ટ "હંમેશા જાળવી રાખો" નિયમો "હંમેશા દૂર કરો" કરતાં વધુ સુરક્ષિત છે
4. **તમામ 3 તીવ્રતા સ્તરો પર પરીક્ષણ કરો** — `minimal` એ કંઈ ફેરફાર ન કરવો જોઈએ, જ્યારે `aggressive` એ પણ ભૂલો જાળવી રાખવી જોઈએ
5. **`unless` ફીલ્ડનો ઉપયોગ કરો** — "જો X હાજર હોય તો ટ્રિગર ન કરો" વડે શોર્ટ-સર્કિટને સુરક્ષિત કરો

## મૂળ આઉટપુટ પુનઃપ્રાપ્તિ અને ચકાસણી ગેટ

જ્યારે RTK આઉટપુટને આક્રમક રીતે સંકુચિત કરે છે, ત્યારે તમે ડિબગિંગ, ઑડિટ અથવા રિપ્લે માટે **મૂળ ટેક્સ્ટ પુનઃપ્રાપ્ત** કરી શકો છો.

### મૂળ આઉટપુટ પુનઃપ્રાપ્તિ કેવી રીતે કાર્ય કરે છે

```
મૂળ આઉટપુટ (10K ટોકન)
        │
        ▼
RTK સંકોચન (rawOutput.enabled=true સાથે)
        │
        ├─▶ સંકુચિત આઉટપુટ (2K ટોકન)  ──▶ LLM તરફ
        │
        └─▶ મૂળ આઉટપુટ (10K ટોકન)      ──▶ DBમાં સંગ્રહિત
                                                  (request_id દ્વારા લિંક કરેલું)
```

### મૂળ આઉટપુટ સંગ્રહ સક્ષમ કરવો

**દરેક વિનંતી માટે** (combo configમાં):

```json
{
  "compression": {
    "engine": "rtk",
    "intensity": "aggressive",
    "rawOutput": {
      "enabled": true,
      "maxBytes": 1048576 // 1MB મર્યાદા
    }
  }
}
```

**ડિફૉલ્ટ**: `rawOutput.enabled: false` (સ્ટોરેજ બચાવે છે).

### સ્ટોરેજ ખર્ચ

| દરેક વિનંતી માટે        | 1MB મર્યાદા   | 10MB મર્યાદા   |
| ----------------------- | ------------- | -------------- |
| સરેરાશ સંકુચિત આઉટપુટ   | ~5KB          | ~5KB           |
| સંગ્રહિત મૂળ આઉટપુટ     | ~50-500KB     | ~500KB-5MB     |
| દરરોજ 1000 વિનંતીઓ સાથે | 50-500MB/દિવસ | 500MB-5GB/દિવસ |

> **ભલામણ**: મૂળ આઉટપુટ ફક્ત **ડિબગિંગ સત્રો** અથવા **નમૂનારૂપ ઑડિટિંગ** માટે સક્ષમ કરો, હંમેશાં સક્ષમ રાખવા માટે નહીં.

### મૂળ આઉટપુટ પુનઃપ્રાપ્ત કરવો

```ts
import { readRtkRawOutput } from "omniroute/compression/engines/rtk/rawOutput";

const raw = readRtkRawOutput(pointerId); // compression statsમાંથી pointerId
if (raw) {
  console.log("Original output:", raw);
}
```

સંકોચન પછી `pointerId`, `CompressionStats.rtkRawOutputPointers[]`માં પરત કરવામાં આવે છે.
ફંક્શન સિગ્નેચર માટે `open-sse/services/compression/engines/rtk/rawOutput.ts:102` જુઓ.

### ચકાસણી ગેટ

**RTK ફિલ્ટર ચકાસણી** (`open-sse/services/compression/engines/rtk/verify.ts`) તમામ ફિલ્ટર્સને તેમના `tests[]` સામે માન્ય કરે છે અને તમામ 3 તીવ્રતા સ્તરો પર વર્તન યોગ્ય છે તેની ખાતરી કરે છે.

ચકાસણી ચલાવવા માટે **`runRtkFilterTests()` કૉલ કરો**:

```ts
import { runRtkFilterTests } from "open-sse/services/compression/engines/rtk/verify";

const result = runRtkFilterTests();
console.log(`Passed: ${result.outcomes.filter((o) => o.passed).length}`);
console.log(`Failed: ${result.outcomes.filter((o) => !o.passed).length}`);
if (!result.passed) {
  console.error("Filters failed verification");
  result.outcomes
    .filter((o) => !o.passed)
    .forEach((o) => {
      console.error(
        `  - ${o.filterId} / ${o.testName}: expected "${o.expected}", got "${o.actual}"`
      );
    });
}
```

**તે શું માન્ય કરે છે**:

1. દરેક ફિલ્ટર લોડ થાય છે અને સ્કીમા માન્યતા પાસ કરે છે
2. દરેક `tests[]` એન્ટ્રી અપેક્ષિત આઉટપુટ ઉત્પન્ન કરે છે
3. `minimal` તીવ્રતા no-op છે (મૂળને જાળવે છે, ફક્ત માળખાકીય ફિલ્ટર્સ લાગુ કરે છે)
4. `aggressive` તીવ્રતા ભૂલો, પરીક્ષણ નિષ્ફળતાઓ અને સ્ટૅક ટ્રેસ જાળવે છે
5. સંકુચિત આઉટપુટ ક્યારેય મૂળ ઇનપુટ કરતાં મોટું હોતું નથી

- સ્રોત: `open-sse/services/compression/engines/rtk/` (63 ફાઇલો, ~70KB)

- **ફિલ્ટર ફેરફાર મર્જ કરતાં પહેલાં** — હંમેશાં ખાતરી કરો કે પરીક્ષણો પાસ થાય છે
- **RTK એન્જિન અપગ્રેડ કર્યા પછી** — સ્કીમા બદલાઈ હોઈ શકે છે
- **સમયાંતરે મોનિટરિંગમાં** — પરીક્ષણ ફિક્સ્ચર્સમાં થતા વિચલન સામે સુરક્ષા આપે છે
- **નવું ટૂલ/કમાન્ડ કુટુંબ ઉમેરતી વખતે** — નવું ફિલ્ટર કાર્ય કરે છે તે સાબિત કરે છે
