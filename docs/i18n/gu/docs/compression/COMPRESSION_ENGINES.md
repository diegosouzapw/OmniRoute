OmniRoute કમ્પ્રેશન એન્જિન કોન્ટ્રાક્ટ્સની આસપાસ રચાયેલું છે. કોઈ મોડ સીધું એક એન્જિન
(`caveman` અથવા `rtk`) ચલાવી શકે છે અથવા નિર્ધારિત સ્ટૅક્ડ પાઇપલાઇન ચલાવી શકે છે, જે ક્રમશઃ અનેક એન્જિનોને કાર્યાન્વિત કરે છે.

## મોડ્સ

| મોડ          | એન્જિન પાથ                         | ઉદ્દેશિત ઇનપુટ                               |
| ------------ | ---------------------------------- | -------------------------------------------- |
| `off`        | કોઈ નહીં                           | પ્રોમ્પ્ટનું ચોક્કસ સંરક્ષણ                  |
| `lite`       | Caveman lite હેલ્પર્સ              | ઓછા જોખમવાળું હંમેશાં-ચાલુ ક્લીનઅપ           |
| `standard`   | Caveman                            | કુદરતી-ભાષાના પ્રોમ્પ્ટનું સંક્ષેપણ          |
| `aggressive` | Caveman + હિસ્ટ્રી/ટૂલ સમરાઇઝર્સ   | લાંબા ચેટ સત્રો                              |
| `ultra`      | Caveman + પ્રૂનિંગ હેલ્પર્સ        | કોન્ટેક્સ્ટ-મર્યાદામાંથી પુનઃપ્રાપ્તિ        |
| `rtk`        | RTK                                | ટર્મિનલ, શેલ, બિલ્ડ, ટેસ્ટ અને git આઉટપુટ    |
| `omniglyph`  | OmniGlyph                          | મૂળ પ્રોવાઇડર વાયર પર ઇમેજ તરીકે કોન્ટેક્સ્ટ |
| `stacked`    | પાઇપલાઇન, ડિફૉલ્ટ `rtk -> caveman` | મિશ્ર ટૂલ લૉગ્સ અને ગદ્ય, મહત્તમ બચત         |

### OmniGlyph કમ્પ્રેશન પ્રોફાઇલ્સ

`omniglyph` એન્જિન (પૅકેજ `omniglyph`, 1.4.0+) નામિત સિમેન્ટિક પ્રોફાઇલ સ્વીકારે છે, જેને
કમ્પ્રેશન સેટિંગ્સમાં `omniglyph.profile` મારફતે વૈશ્વિક રીતે અથવા સ્ટૅક્ડ પાઇપલાઇનના
સ્ટેપ કૉન્ફિગ મારફતે દરેક સ્ટેપ માટે સેટ કરી શકાય છે:

| પ્રોફાઇલ      | સીમા                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------- |
| `aggressive`  | ડિફૉલ્ટ. પ્રકાશિત રસીદોમાં માપવામાં આવેલી નીતિ — સિસ્ટમ, ટૂલ ડૉક્સ અને ગાઢ હિસ્ટ્રીને ઇમેજમાં ફેરવે છે        |
| `balanced`    | લાઇવ સ્ટેટને મૂળ સ્વરૂપે રાખે છે, છેલ્લાં 8 ટર્ન્સને સુરક્ષિત કરે છે અને જૂની બંધ હિસ્ટ્રીને સંક્ષિપ્ત કરે છે |
| `coding-safe` | ઑથોરિટી, ટૂલ સ્કીમા અને લાઇવ ટૂલ આઉટપુટને મૂળ સ્વરૂપે રાખે છે તથા છેલ્લાં 12 ટર્ન્સને સુરક્ષિત કરે છે         |
| `passthrough` | રૂપાંતર કર્યા વિના રૂટ કરે છે; એન્જિનને છોડવામાં આવે છે                                                       |

પ્રોફાઇલ એક **મહત્તમ મર્યાદા છે, લઘુત્તમ નહીં**: પૅકેજમાં રહેલું `mergeCompressionProfileOptions`
કૉલર ઓવરરાઇડને પ્રોફાઇલ દ્વારા બંધ કરાયેલી લોસી લેન ફરીથી ખોલવા દેતું નથી, તેથી દરેક સ્ટેપ માટેનું
`preserveSystemPrompt: false`, `coding-safe` હેઠળ સિસ્ટમ કમ્પ્રેશનને ફરીથી સક્ષમ કરી શકતું નથી.

આ કોડબેઝ પરના માપન મુજબ: `coding-safe` અને `balanced`, `minCompressChars`ને તેના
મહત્તમ મૂલ્ય સુધી વધારે છે અને સિસ્ટમ, ટૂલ સ્કીમા તથા ટૂલ પરિણામોને મૂળ સ્વરૂપે રાખે છે, તેથી જે સત્રમાં
હજી સુધી હિસ્ટ્રી એકઠી થઈ નથી તે `below_min_chars` પર અટકી જાય છે અને એન્જિન કશું રૂપાંતરિત કરતું નથી.
તેથી સૌથી સુરક્ષિત પ્રોફાઇલને બદલે `aggressive` ડિફૉલ્ટ છે.

પૅકેજ તેના પર્યાવરણ કૉન્ફિગરેશનમાંથી પોતાનું મોડેલ સ્કોપ અને પ્રોફાઇલ નિર્ધારિત કરે છે.
OmniRoute ક્યારેય આ નિર્ણય સોંપતું નથી: ઍડૅપ્ટર મોડેલ ગેટને પૅકેજના સૌથી પ્રતિબંધાત્મક સ્કોપ પર
નિશ્ચિત કરે છે, તેથી હોસ્ટ પર્યાવરણ સેટિંગ્સ માત્ર અલાઉલિસ્ટને સંકુચિત કરી શકે છે, OmniRouteની
માપેલી રસીદોથી આગળ તેને ક્યારેય વિસ્તૃત કરી શકતી નથી.

## એન્જિન રજિસ્ટ્રી

રજિસ્ટ્રી `open-sse/services/compression/engines/registry.ts`માં સ્થિત છે. એન્જિનો એક સામાન્ય
કરાર પ્રદાન કરે છે:

- `id`: `caveman` અથવા `rtk` જેવું સ્થિર એન્જિન id
- `apply(text, config)`: સ્ટૅક્ડ પાઇપલાઇનો દ્વારા ઉપયોગમાં લેવાતો લેગસી એક્ઝિક્યુશન પાથ
- `compress(input, config)`: ટેક્સ્ટ + આંકડા પરત કરતો મુખ્ય એક્ઝિક્યુશન પાથ
- `getConfigSchema()`: માન્ય configનું JSON-Schema-જેવું માળખું પરત કરે છે
- `validateConfig(config)`: `{ valid, errors[] }` પરત કરે છે

નોંધણીમાં `registerCompressionEngine(engine)` (અથવા અદ્યતન કિસ્સાઓ માટે `registerEngine`)નો ઉપયોગ થાય છે,
જે સ્વીકારતા પહેલાં `assertValidEngine()` અને `validateConfig(defaultConfig)`ને કૉલ કરે છે.
રનટાઇમ દરમિયાન એન્જિન દૂર કરવા માટે `unregisterCompressionEngine(id)`નો ઉપયોગ કરો.

કમ્પ્રેશન ચાલે તે પહેલાં `strategySelector.ts` બિલ્ટ-ઇન એન્જિનોની નોંધણી કરે છે. આનાથી પ્રીવ્યૂ,
રનટાઇમ કમ્પ્રેશન, સ્ટૅક્ડ મોડ, પરીક્ષણો અને ભવિષ્યનાં એન્જિનો એક જ એક્ઝિક્યુશન પાથનો ઉપયોગ કરી શકે છે.

### MCP વર્ણન કમ્પ્રેશન (સંબંધિત)

એક અલગ રજિસ્ટ્રી, રજિસ્ટ્રી-સ્તરે MCP ટૂલ વર્ણન મેટાડેટાને સંકુચિત કરે છે — જુઓ
`open-sse/mcp-server/descriptionCompressor.ts` અને [MCP-SERVER.md](../frameworks/MCP-SERVER.md). તે Caveman
નિયમોનો પુનઃઉપયોગ કરે છે, પરંતુ રિક્વેસ્ટ પેલોડ્સને બદલે ટૂલ મેટાડેટા પર કાર્ય કરે છે.

### વધારાનાં બિલ્ટ-ઇન એન્જિનો

Caveman, RTK અને LLMLingua-2 ઉપરાંત, રજિસ્ટ્રીમાં કેટલાંક વિશિષ્ટ લૉસલેસ /
સ્ટ્રક્ચરલ એન્જિનો સામેલ છે (જેનો ઉપયોગ સ્ટૅક્ડ પાઇપલાઇનો, પ્લેગ્રાઉન્ડ અને પરીક્ષણો દ્વારા થાય છે):

| એન્જિન        | Id              | તે શું કરે છે                                                                                                                                                                |
| ------------- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CCR           | `ccr`           | Content-Compress-Retrieve (H4): મોટા સળંગ ટેક્સ્ટ બ્લૉક્સને કન્ટેન્ટ-એડ્રેસ્ડ રેફરન્સથી બદલે છે, જેથી પુનરાવર્તિત/મોટા બ્લૉક્સ એક વાર મોકલાય અને ત્યારબાદ તેમનો સંદર્ભ અપાય. |
| headroom      | `headroom`      | SmartCrusher (H3 + N5): સમાન પ્રકારના JSON-array પેલોડ્સનું કૉલમ આધારિત `[N rows]` સ્વરૂપમાં લૉસલેસ ટેબ્યુલર કોમ્પૅક્શન.                                                     |
| ionizer       | `ionizer`       | ખૂબ મોટા સમાન પ્રકારના બ્લૉક્સ માટે શરૂઆત/મધ્ય/અંતની પંક્તિઓનું સૅમ્પલિંગ કરે છે અને દૂર કરેલા મધ્યભાગને CCR કન્ટેન્ટ-એડ્રેસ્ડ રેફરન્સ તરીકે સંગ્રહે છે.                     |
| session-dedup | `session-dedup` | કન્ટેન્ટ-એડ્રેસ્ડ ક્રૉસ-ટર્ન ડિડુપ્લિકેશન (TokenMizerથી પ્રેરિત): એ જ સેશનના અગાઉના ટર્નમાં પહેલેથી જોવાયેલ ટેક્સ્ટને દૂર કરે છે.                                            |

**CCR રિટ્રીવ-પ્રોટોકૉલ સૂચના (#8033):** કોઈ રિક્વેસ્ટમાં CCR પહેલી વાર ≥1 બ્લૉક બદલે ત્યારે,
એન્જિન એકમાત્ર, આઇડેમ્પોટન્ટ `system` સંદેશ આગળ ઉમેરે છે (`[CCR protocol]`
સેન્ટિનેલથી શરૂ થતો), જે કૉલરને માર્કર → ટૂલ કરાર સમજાવે છે:
`[CCR retrieve hash=<24hex> chars=N]` માર્કરનો અર્થ શું છે, hashને યથાવત્ કૉપી કરવો આવશ્યક છે
(તમામ 24 hex અક્ષરો — ખોટી રીતે કૉપી કરેલા hash "block not found"
ચૂકોનું સંભવિત કારણ છે), અને `[dedup:ref sha=...]` માર્કરનો અર્થ "ઇતિહાસમાં પાછળ જુઓ" છે, "ટૂલને કૉલ કરો"
નહીં. નોંધ **માત્ર ત્યારે જ ઇન્જેક્ટ કરવામાં આવે છે જ્યારે કૉલરના જાહેર કરાયેલા `tools[]` સાબિત કરે કે તે
વાસ્તવમાં `omniroute_ccr_retrieve` સુધી પહોંચી શકે છે** (`callerSupportsCcrRetrieve()` અહીં:
`open-sse/services/compression/engines/ccr/protocolInstruction.ts`) — તે ટૂલ વિનાના સાદા
OpenAI-સુસંગત કૉલરને એવી કોઈ વસ્તુ કૉલ કરવાની સૂચના ક્યારેય મળતી નથી, જેના સુધી તે
પહોંચી શકતો નથી. ઇન્જેક્ટ કરતા પહેલાં સેન્ટિનેલ માટે સંદેશ ઇતિહાસને સ્કૅન કરીને
આઇડેમ્પોટન્સી સુનિશ્ચિત કરવામાં આવે છે, જેથી મલ્ટિ-ટર્ન રિક્વેસ્ટ્સ (જે અગાઉના સંદેશાઓ ફરી ચલાવે છે) દરેક
ટર્નમાં નોંધને ફરીથી ઉમેરતી નથી.

## Caveman

Caveman મોડ સામાન્ય ગદ્યના અર્થલક્ષી સંક્ષેપ પર ધ્યાન કેન્દ્રિત કરે છે:

- કોડ બ્લૉક્સ, URLs, JSON, પાથ્સ અને સંરચિત ડેટા જાળવી રાખે છે
- બિનજરૂરી શબ્દો, અનિશ્ચિતતા દર્શાવતી ભાષા, પુનરાવર્તિત સંદર્ભ અને વધુ પડતી જોડાણકારી શબ્દરચના દૂર કરે છે
- `open-sse/services/compression/rules/` માં ભાષા-અવગત ફાઇલ નિયમ પૅક્સને સપોર્ટ કરે છે
- લેગસી `standard`, `aggressive` અને `ultra` મોડ્સ દ્વારા ઉપલબ્ધ રહે છે

ડૅશબોર્ડમાં તેનું સ્થાન `Dashboard -> Context & Cache -> Caveman` છે.

Caveman અપસ્ટ્રીમ `~75%` ઓછા આઉટપુટ ટોકન્સ, બેન્ચમાર્ક્સમાં સરેરાશ `65%` આઉટપુટ બચત
અને `22-87%` ની રેન્જ તેમજ `~46%` ઇનપુટ-કમ્પ્રેશન ટૂલનો અહેવાલ આપે છે. સ્ટૅક્ડ પ્રોમ્પ્ટ/કૉન્ટેક્સ્ટ
બચતનું દસ્તાવેજીકરણ કરતી વખતે OmniRoute Cavemanના ઇનપુટ-સાઇડ આંકડાનો ઉપયોગ કરે છે; Caveman
આઉટપુટ મોડ એક અલગ પ્રતિસાદ-વર્તણૂક સુવિધા તરીકે રહે છે.

## RTK

RTK મોડ કમાન્ડ અને ટૂલ આઉટપુટ પર ધ્યાન કેન્દ્રિત કરે છે:

- `git status`, `git branch`, `git diff`, Vitest/Jest/Pytest, Cargo/Go ટેસ્ટ્સ,
  TypeScript/Vite/Webpack બિલ્ડ્સ, ESLint, npm audit/ઇન્સ્ટૉલ્સ, Docker લૉગ્સ,
  શેલ `find`/`grep`, સ્ટૅક ટ્રેસિસ અને સામાન્ય લૉગ્સ જેવા આઉટપુટ વર્ગો શોધે છે
- `open-sse/services/compression/engines/rtk/filters/` માંથી 49 JSON ફિલ્ટર્સ લાગુ કરે છે
- RTK-શૈલીની ઘોષણાત્મક પાઇપલાઇનને સપોર્ટ કરે છે: ANSI દૂર કરવું, રિપ્લેસ કરવું, match-output શૉર્ટ-સર્કિટ,
  લાઇન્સ દૂર કરવી/રાખવી, પ્રતિ-લાઇન ટ્રન્કેશન, head/tail/max-line ટ્રન્કેશન અને ખાલી હોય ત્યારે ફૉલબૅક
- `.rtk/filters.json` માં ટ્રસ્ટ-ગેટેડ પ્રોજેક્ટ ફિલ્ટર્સ અને
  `DATA_DIR/rtk/filters.json` માં ગ્લોબલ ફિલ્ટર્સને સપોર્ટ કરે છે
- ANSI સિક્વન્સિસ, પ્રોગ્રેસ નૉઇઝ, પુનરાવર્તિત લાઇન્સ અને બિનઉપયોગી બૉઇલરપ્લેટ દૂર કરે છે
- પગલાં લઈ શકાય તેવી નિષ્ફળતાઓ, ચેતવણીઓ, સારાંશો, બદલાયેલી ફાઇલો અને અંતિમ સંદર્ભ જાળવી રાખે છે
- પ્રમાણિત મેનેજમેન્ટ રૂટ્સ દ્વારા પુનઃપ્રાપ્તિ/ડિબગિંગ માટે વૈકલ્પિક રીતે સંપાદિત રૉ આઉટપુટ જાળવી શકે છે

ડૅશબોર્ડમાં તેનું સ્થાન `Dashboard -> Context & Cache -> RTK` છે.

કસ્ટમ ફિલ્ટર્સ, ટ્રસ્ટ, ચકાસણી અને રૉ-આઉટપુટ પુનઃપ્રાપ્તિ માટેની કાર્યકારી વિગતો
[`RTK_COMPRESSION.md`](./RTK_COMPRESSION.md) માં ઉપલબ્ધ છે.

RTK અપસ્ટ્રીમ કમાન્ડ-આઉટપુટ કમ્પ્રેશન માટે `60-90%` બચતનો અહેવાલ આપે છે. તેના README ઉદાહરણમાં
30-મિનિટનું Claude Code સત્ર `~118,000` ટોકન્સથી ઘટીને `~23,900` ટોકન્સ થાય છે, એટલે કે `79.7%` બચત થાય છે.

## LLMLingua-2 (અર્થલક્ષી છંટણી)

LLMLingua-2 મોડ નાના ONNX ટોકન ક્લાસિફાયરનો ઉપયોગ કરીને ગદ્ય પર **અર્થલક્ષી ટોકન છંટણી**
કરે છે અને નિયમ-આધારિત Caveman તથા RTK એન્જિન્સને પૂરક બને છે:

- ફક્ત નૉન-સિસ્ટમ સંદેશાઓમાં ગદ્યને કમ્પ્રેસ કરે છે; ફેન્સ્ડ કોડ બ્લૉક્સ અને અન્ય સંરક્ષિત
  રચનાઓમાં ક્યારેય ફેરફાર થતો નથી
- વર્કર થ્રેડમાં `@atjsh/llmlingua-2` બૅકએન્ડ (ONNX વાયા `@huggingface/transformers`)
  ચલાવે છે, જેથી મોડલ ઇન્ફરન્સ ક્યારેય રિક્વેસ્ટ ઇવેન્ટ લૂપને બ્લૉક કરતું નથી
- **સ્ટૅક કરી શકાય તેવું છે** (`stackPriority` 35): સ્ટૅક્ડ પાઇપલાઇનમાં તે સંરચનાત્મક
  એન્જિન્સ (CCR, session-dedup, headroom, Caveman) પછી, પરંતુ `ultra` પહેલાં ચાલે છે, કારણ કે
  અર્થલક્ષી છંટણી અગાઉથી સંરચનાત્મક રીતે કમ્પ્રેસ થયેલા ટેક્સ્ટ પર સૌથી અસરકારક છે — ઉદાહરણ તરીકે
  `rtk -> caveman -> llmlingua`
- **કોઈપણ ભૂલ આવે ત્યારે નિષ્ફળતાને ખુલ્લી રાખે છે** (ગેરહાજર વૈકલ્પિક ડિપેન્ડન્સીઝ, વર્કર સ્પૉન, મોડલ લોડ, ઇન્ફરન્સ
  અથવા ટાઇમઆઉટ) → મૂળ ટેક્સ્ટ કોઈ ફેરફાર વિના પાછું મળે છે, ભૂલ ક્યારેય પાછી મળતી નથી

એન્જિનનું સ્થાન: `open-sse/services/compression/engines/llmlingua/`. ડૅશબોર્ડમાં તેનું સ્થાન
`Dashboard -> Context & Cache -> LLMLingua` છે.

### મોડલ્સ

ડિફૉલ્ટ મોડલ **TinyBERT** (`atjsh/llmlingua-2-js-tinybert-meetingbank`, ~57 MB,
ઝડપી) છે. વધુ ચોકસાઈ ધરાવતું **BERT-base** મોડલ (`Arcoldd/llmlingua4j-bert-base-onnx`,
~710 MB) એન્જિન કૉન્ફિગના `model` ફીલ્ડ દ્વારા ઉપલબ્ધ છે. પ્રથમ કૉલ વખતે
`@huggingface/transformers` પસંદ કરેલું મોડલ HuggingFace Hub પરથી
`${DATA_DIR}/models/llmlingua` માં લેઝી રીતે ડાઉનલોડ કરે છે (`modelStore.ts`); તેના બદલે `modelPath` કૉન્ફિગ
ઓવરરાઇડ તેને સ્થાનિક નકલ તરફ નિર્દેશિત કરે છે (ઑફલાઇન / એર-ગૅપ્ડ ઇન્સ્ટૉલ્સ).

### વૈકલ્પિક ડિપેન્ડન્સીઝ અને માંગ મુજબ ઇન્સ્ટૉલેશન

છાંટી શકાય એવો LLMLingua રનટાઇમ પીઅર સ્ટૅક **વૈકલ્પિક** છે. બે પૅકેજ
`package.json` માં `optionalDependencies` તરીકે ઘોષિત છે અને પ્રોડક્શન બિલ્ડ દ્વારા **બાહ્ય**
રાખવામાં આવે છે (`scripts/build/prepublish.ts` તેમને બંડલ કરતું નથી):

| પૅકેજ                | વર્ઝન (પિન) | નોંધો                                           |
| -------------------- | ----------- | ----------------------------------------------- |
| `@atjsh/llmlingua-2` | `2.0.5`     | એન્ટ્રી પૅકેજ; અન્યને પીઅર્સ તરીકે ઘોષિત કરે છે |
| `js-tiktoken`        | `^1.0.20`   | ટોકનાઇઝર                                        |

`@huggingface/transformers` ને `^4.2.0` પર પિન કરવામાં આવ્યું છે (સ્થાનિક એમ્બેડિંગ્સ પાથ સાથે શેર કરેલું અને
સ્ટૅન્ડઅલોન બંડલમાં પણ ટ્રેસ કરેલું); `@atjsh/llmlingua-2@2.0.5` તેના પર
`"^3.5.2 || ^4.0.0"` સાથે પીઅર કરે છે, તેથી Transformers.js v3 અને v4 બંને સપોર્ટેડ છે. 2.0.4થી,
`@atjsh/llmlingua-2` ને હવે `@tensorflow/tfjs` ની જરૂર નથી, જેના કારણે SLM સ્ટૅકમાંથી સૌથી મોટો એકલ
યોગદાનકર્તા (TensorFlow.js) દૂર થયો છે. ફક્ત ઉપરનાં બે પૅકેજ જ છાંટી શકાય તેવા SLM
પીઅર્સ છે. માનક `npm install` (ડેવ) વૈકલ્પિક ડિપેન્ડન્સીઝને બાકાત ન રાખવામાં આવી હોય તો વૈકલ્પિક સ્ટૅક
આપમેળે ઇન્સ્ટૉલ કરે છે.

**માગ મુજબ શા માટે:** npm પર પ્રકાશિત પૅકેજ, સ્ટૅન્ડઅલોન બંડલ અને Docker ઇમેજને
નાનું રાખવા માટે આ ડિપેન્ડન્સીઝ **વિના** મોકલવામાં આવે છે. જ્યારે તે ગેરહાજર હોય, ત્યારે વર્કરનું ડિપેન્ડન્સી
ગેટ (`worker.ts` માં `@atjsh/llmlingua-2` રિઝૉલ પ્રોબ) નિષ્ફળ જાય છે અને એન્જિન
**નિઃશબ્દ રીતે નિષ્ફળતાને ખુલ્લી રાખે છે** — LLMLingua પસંદ કરવું no-op બની જાય છે (ટેક્સ્ટ કોઈ ફેરફાર વિના પાછું મળે છે અને કોઈ
ભૂલ લૉગ થતી નથી). છાંટેલા એન્વાયર્નમેન્ટમાં તેને સક્રિય કરવા માટે વૈકલ્પિક સ્ટૅક ઇન્સ્ટૉલ કરો:

```bash
# package.json optionalDependencies માં ઘોષિત વર્ઝન્સ પર પિન કરો
npm install @atjsh/llmlingua-2@2.0.5 js-tiktoken
```

`@tensorflow/tfjs` દૂર થવાથી (2.0.4+) અગાઉનું મુખ્ય ~800 MB
યોગદાન દૂર થાય છે — બાકી ફૂટપ્રિન્ટ transformers.js + onnxruntime-node રનટાઇમ્સનું છે,
સાથે પ્રથમ ઉપયોગ વખતે ડાઉનલોડ થતું TinyBERT મોડલ (~57 MB) છે (npm દ્વારા નહીં).

દરેક એન્વાયર્નમેન્ટ મુજબ:

- **Dev / `npm install`** — જો તમે `--omit=optional`
  (અથવા `--no-optional`) પાસ ન કર્યું હોય, તો આપમેળે ઇન્સ્ટોલ થાય છે. કોઈ કાર્યવાહી જરૂરી નથી.
- **Global npm (`npm i -g omniroute`) / standalone** — ઉપર આપેલો ઇન્સ્ટોલ કમાન્ડ
  ઇન્સ્ટોલ થયેલી package ડિરેક્ટરીમાં ચલાવો અથવા optional dependencies છોડ્યા વિના ફરીથી ઇન્સ્ટોલ કરો.
- **Docker** — derived image layerમાં ઇન્સ્ટોલ કમાન્ડ ઉમેરો; પ્રકાશિત imageને
  ઇરાદાપૂર્વક નાનું રાખવામાં આવ્યું છે.
- **VPS (PM2)** — એપના `node_modules`માં ઇન્સ્ટોલ કરો, પછી processને restart કરો જેથી
  worker gateને ફરીથી ચકાસે.
- **Raw Next standalone (`npm run build` → `.build/next/standalone/server.js`)** — standalone
  traceમાં worker કે optional dependencies, બંનેમાંથી કોઈ સામેલ નથી, તેથી engine કોઈ ભૂલ દર્શાવ્યા વિના
  fail-open થાય છે. `scripts/build/colocate-standalone.mjs` બંનેને ફરીથી લાગુ કરે છે (worker esbuild +
  standalone treeમાં optional-dep closure); દરેક build પછી તે
  `postbuild` npm hook દ્વારા આપમેળે ચાલે છે. આ idempotent છે અને dependencies ગેરહાજર હોય ત્યારે fail-soft થાય છે.

**તે સક્રિય છે તેની ચકાસણી કરો:** LLMLingua પસંદ કરેલું હોય ત્યારે વાસ્તવિક ગદ્ય ખરેખર સંકોચાય છે (engine
fail-open થવાનું બંધ કરે છે), અને પ્રથમ request modelને
`${DATA_DIR}/models/llmlingua`માં download કરે છે. gate ઇરાદાપૂર્વક માત્ર `@atjsh/llmlingua-2`ને જ ચકાસે છે —
અન્ય peers ફક્ત ESM છે અને હાજર હોય ત્યારે પણ તેમના પર `require.resolve` exception ફેંકે છે — તેથી
`import()` સમયે કોઈ peer ખરેખર ગેરહાજર હોય, તો worker હજુ પણ fail-open થાય છે.

## સ્ટૅક્ડ પાઇપલાઇન્સ

સ્ટૅક્ડ મોડ પાઇપલાઇનના પગલાં ક્રમમાં ચલાવે છે. ડિફૉલ્ટ આ છે:

```txt
rtk -> caveman
```

આનો ઉપયોગ એવા કોડિંગ-એજન્ટ સત્રો માટે કરો જ્યાં પ્રોમ્પ્ટમાં કમાન્ડ આઉટપુટની સાથે માનવ અથવા સહાયકનું ગદ્ય સંયોજિત હોય. RTK પહેલાં ઘોંઘાટભર્યા ટૂલ લૉગ્સ ઘટાડે છે, ત્યારબાદ Caveman બાકી રહેલી કુદરતી ભાષાને સંકુચિત કરે છે.

પાઇપલાઇનનાં પગલાં કમ્પ્રેશન સેટિંગ્સમાં `stackedPipeline` વડે અથવા કમ્પ્રેશન કોમ્બો દ્વારા કૉન્ફિગર કરવામાં આવે છે.

જ્યારે બંને એન્જિન સમાન પાત્ર પેલોડને ઘટાડે છે, ત્યારે બચત ચક્રવૃદ્ધિ પામે છે:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

## MCP ઍક્સેસિબિલિટી ટ્રી ફિલ્ટર

MCP ઍક્સેસિબિલિટી-ટ્રી સ્માર્ટ ફિલ્ટર એ અમલીકરણ પછીનું કમ્પ્રેશન સ્તર છે, જે પ્રોમ્પ્ટ્સ અથવા કૉન્ટેક્સ્ટ પર નહીં, પરંતુ MCP **ટૂલ પરિણામો** પર ચાલે છે. તે Playwright, computer-use અને browser-automation MCP સર્વર્સ જેવા ટૂલ્સ દ્વારા પરત કરાતા વિસ્તૃત ઍક્સેસિબિલિટી-ટ્રી અને બ્રાઉઝર સ્નૅપશૉટ પેલોડ્સને લક્ષ્ય બનાવે છે.

### તે શું કરે છે

1. **નૉઇઝ દૂર કરવું** — ખાલી generic/text એન્ટ્રીઓ (`- generic:`, `- text: ""`) દૂર કરે છે
2. **સિબ્લિંગ સંકોચન** — જ્યારે સતત ≥ `collapseThreshold` (ડિફૉલ્ટ 30) લાઇન્સ સંરચનાત્મક પુનરાવર્તનો હોય, ત્યારે તેમને પ્રથમ `collapseKeepHead` (ડિફૉલ્ટ 10) લાઇન્સ + સંખ્યાનો સારાંશ + છેલ્લી `collapseKeepTail` (ડિફૉલ્ટ 5) લાઇન્સમાં સંકોચે છે
3. **રેફ જાળવણી** — Playwright/computer-use માટે જરૂરી `[ref=eXX]` ઍન્કર્સને ક્યારેય બદલવામાં આવતા નથી
4. **હાર્ડ ટ્રન્કેશન** — જો સંકોચન પછીનું ટેક્સ્ટ હજુ પણ `maxTextChars` (ડિફૉલ્ટ 50,000) કરતાં વધુ હોય, તો તેને નેવિગેશન સંકેત સાથે ટ્રન્કેટ કરે છે, જેથી એજન્ટ કામ ચાલુ રાખી શકે

### એન્જિનનું સ્થાન

```txt
open-sse/services/compression/engines/mcpAccessibility/
  index.ts            ← smartFilterText() પ્રવેશ બિંદુ
  collapseRepeated.ts ← સિબ્લિંગ-સંકોચન અલ્ગોરિધમ
  constants.ts        ← DEFAULT_MCP_ACCESSIBILITY_CONFIG
```

### કૉન્ફિગરેશન

ગ્લોબલ સેટિંગ્સમાં `compression.mcpAccessibility` દ્વારા નિયંત્રિત થાય છે (માઇગ્રેશન 056). ડિફૉલ્ટ કૉન્ફિગ:

```json
{
  "enabled": true,
  "maxTextChars": 50000,
  "collapseThreshold": 30,
  "collapseKeepHead": 10,
  "collapseKeepTail": 5,
  "minLengthToProcess": 2000
}
```

આ ફિલ્ટર ફક્ત એવા ટૂલ-રિઝલ્ટ પેલોડ્સ પર લાગુ થાય છે, જેમનો `type` `"text"` હોય અને જેમની લંબાઈ `minLengthToProcess` કરતાં વધુ હોય. તે પ્રોમ્પ્ટ કમ્પ્રેશન અથવા રિક્વેસ્ટ પેલોડ્સને અસર કરતું નથી.

### અપેક્ષિત બચત

પેજની જટિલતાના આધારે, બ્રાઉઝર સ્નૅપશૉટ ટૂલ પરિણામો પર 60–80%. સંકોચન અલ્ગોરિધમ લાઇનની સંખ્યામાં O(n) છે અને નગણ્ય વિલંબ ઉમેરે છે.

### આ ફિલ્ટર અને ઉપરનાં કમ્પ્રેશન એન્જિનો વચ્ચેનો તફાવત

| પાસું       | Caveman / RTK / Stacked             | MCP ઍક્સેસિબિલિટી ફિલ્ટર               |
| ----------- | ----------------------------------- | -------------------------------------- |
| લક્ષ્ય      | રિક્વેસ્ટ પ્રોમ્પ્ટ્સ / કૉન્ટેક્સ્ટ | MCP ટૂલ પરિણામો                        |
| ટ્રિગર      | કમ્પ્રેશન મોડ સેટિંગ                | `compression.mcpAccessibility.enabled` |
| વ્યાપ       | બધા SSE સંદેશાઓ                     | ફક્ત ટૂલ પરિણામો                       |
| રેફ ઍન્કર્સ | લાગુ પડતું નથી                      | બિનશરતી રીતે જાળવવામાં આવે છે          |

## કમ્પ્રેશન કોમ્બોઝ

કમ્પ્રેશન કોમ્બોઝ એ નામ આપવામાં આવેલી કમ્પ્રેશન પ્રોફાઇલ્સ છે, જેને રાઉટિંગ કોમ્બોઝને સોંપી શકાય છે:

- `compression_combos`: મોડ, પાઇપલાઇન, RTK રૂપરેખાંકન, ભાષા રૂપરેખાંકન અને ડિફૉલ્ટ માર્કર સંગ્રહે છે
- `compression_combo_assignments`: કમ્પ્રેશન કોમ્બોને રાઉટિંગ કોમ્બો સાથે મેપ કરે છે
- રનટાઇમ ઇન્ટિગ્રેશન સામાન્ય કોમ્બો ઓવરરાઇડ્સ પહેલાં સોંપાયેલા કમ્પ્રેશન કોમ્બોને રિઝોલ્વ કરે છે
- એનાલિટિક્સમાં `compression_combo_id` અને `engine` સામેલ હોય છે

ડૅશબોર્ડ સ્થાન: `Dashboard -> Context & Cache -> Compression Combos`.

કમ્પ્રેશન એન્જિનને કૉલ કરતું નથી — વિનંતી/પ્રતિભાવ બોડીઝ કોઈ ફેરફાર વિના સીધી એક્ઝિક્યુટર સુધી
પહોંચે છે. હાલમાં આ માળખાકીય છે (એમ્બેડિંગ્સ અને ચૅટ કમ્પ્લીશન્સ અલગ હેન્ડલર્સ છે), કોઈ
રનટાઇમ ચકાસણી નથી, પરંતુ તેનો અર્થ એ છે કે #8034 માંની વેક્ટર-વિકૃતિની ચિંતાને
એમ્બેડિંગ્સ પાથમાં કોઈ એક્સપોઝર સપાટી નથી.

મોડેલ ids / `provider/model` લક્ષ્યોનાં નામ આપી શકે છે જેને ક્યારેય કમ્પ્રેસ કરવા ન જોઈએ — આ
એક ઉપયોગી સુરક્ષા-રેખા છે જો ભવિષ્યમાં કમ્પ્રેશનને એમ્બેડિંગ્સ-સંલગ્ન પાથની નજીક જોડવામાં
આવે, અને એવા કોઈપણ મોડેલ માટે સામાન્ય રીતે ઉપયોગી છે જેના માટે ચોક્કસ બાઇટ-દર-બાઇટ પ્રૉમ્પ્ટ
મહત્ત્વનો હોય (નિર્ધારિત ઇવૅલ્સ, કૅશ-સંવેદનશીલ પ્રિફિક્સ વગેરે).

- સેટિંગ્સ ફીલ્ડ: વૈશ્વિક કમ્પ્રેશન રૂપરેખાંકન પર `exclusions?: string[]`
  (`GET`/`PUT /api/settings/compression`), હાલના `key_value` કમ્પ્રેશન
  નેમસ્પેસ (`src/lib/db/compression.ts`) દ્વારા સંગ્રહિત — કોઈ નવું ટેબલ નહીં.
- ડૅશબોર્ડ ટૅબ: **Dashboard → Compression → Exclusions**
  (`/dashboard/compression/exclusions`).
- પેટર્ન સિન્ટૅક્સ: `*` એકમાત્ર વાઇલ્ડકાર્ડ છે. પેટર્નમાંના અન્ય દરેક regex મેટાકૅરેક્ટરને
  મેચિંગ પહેલાં એસ્કેપ કરવામાં આવે છે, તેથી `gpt-5.6` ફક્ત શાબ્દિક સ્ટ્રિંગ સાથે જ મેળ ખાય છે,
  `gpt-5x6` સાથે ક્યારેય નહીં (ReDoS-સુરક્ષિત, મર્યાદિત, કોઈ નેસ્ટેડ ક્વૉન્ટિફાયર્સ નહીં).
  પેટર્ન્સ બેર મોડેલ id અને `provider/model` કમ્પોઝિટ બંને સામે કેસ-ઇન્સેન્સિટિવ રીતે મેળ
  ખાય છે — `gpt-5-6`, `openai/gpt-5-6` અને `openai/*` બધાં કાર્ય કરે છે, અને માત્ર `*`
  દરેક મોડેલને બાકાત રાખે છે.
- મેચિંગ: `open-sse/services/compression/exclusions.ts` માં
  `isCompressionExcluded()` / `normalizeCompressionExclusions()`. `chatCore.ts` કમ્પ્રેશન
  સેટિંગ્સ રિઝોલ્વ કર્યા પછી તરત જ, **કોઈપણ એન્જિન ચાલે તે પહેલાં**, બાકાત રાખેલા લક્ષ્યને
  ચકાસે છે અને મેળને કમ્પ્રેશન વૈશ્વિક સ્તરે અક્ષમ હોય તે જ રીતે ગણે છે — વિનંતી બોડી
  સાબિતીપૂર્વક બાઇટ-સમાન રહે છે. એનાલિટિક્સમાં દૃશ્યતા માટે આ સ્કિપને
  `writeCompressionSkip(..., "excluded")` દ્વારા રેકોર્ડ કરવામાં આવે છે.
- ડિફૉલ્ટ (ખાલી/ગેરહાજર સૂચિ): #8034 પહેલાંના વર્તન જેવું જ — કંઈપણ બાકાત રાખવામાં આવતું નથી.

## જાણીતી મર્યાદાઓ

- **LLMLingua-2 (SLM) માટે વૈકલ્પિક નિર્ભરતાઓ એક જ સ્થાને હોવી જરૂરી છે.** પ્રોડક્શન બિલ્ડમાં વર્કર માત્ર ત્યારે જ ચાલે છે જ્યારે `@atjsh/llmlingua-2` + તેની પીઅર નિર્ભરતાઓને `dist/node_modules`માં એક જ સ્થાને મૂકવામાં આવી હોય (જુઓ `scripts/build/colocateOptionals.mjs`, #4286). તેમના વિના એન્જિન ફેઇલ-ઓપન થાય છે (મૂળ ટેક્સ્ટ પરત કરે છે). વર્કર રિઝોલ્યુશન હવે `import.meta.url` પર નિર્ભર નથી (તે સ્ટૅન્ડઅલોન બંડલમાં નિષ્ફળ જાય છે) — તે રનટાઇમ cwd / `argv[1]`ને આધાર બનાવે છે.
- **Caveman ભાષા પૅક્સ `de` / `fr` / `ja` આંશિક છે.** તેમાં `context` + `filler` + `structural` નિયમો સામેલ છે, પરંતુ `dedup` / `ultra` પૅક્સ નથી, તેથી આ ભાષાઓ માટે `ultra` તીવ્રતા `full` કરતાં વધુ શક્તિશાળી નથી (તેઓ ફક્ત પોતાના નિયમોનો જ ઉપયોગ કરે છે — અંગ્રેજી `dedup`/`ultra` નિયમો પર કોઈ મૌન ફૉલબૅક થતું નથી, કારણ કે તે વિદેશી ટેક્સ્ટને વિકૃત કરી શકે છે). `en` / `es` / `id` / `pt-BR` સંપૂર્ણ છે. આંશિક પૅક્સ માટે `dedup.json` + `ultra.json`નું યોગદાન આવકાર્ય છે.
- **સ્ટૅક્ડ ટેલિમેટ્રી ફક્ત કમ્પ્રેશન કરનારા એન્જિનોને જ સૂચિબદ્ધ કરે છે.** સ્ટૅક્ડ-પાઇપલાઇનનું એવું પગલું, જેમાં એન્જિન ચાલ્યું હતું પરંતુ 0 % બચત થઈ હતી, તે `stats:null` પરત કરે છે અને તેથી `engineBreakdown`માં દેખાતું નથી — પરિણામે તેને છોડવામાં આવેલા પગલાથી અલગ ઓળખી શકાતું નથી. "ચાલ્યું, 0 %" અને "છોડી દેવાયું" વચ્ચે ભેદ કરવા માટે બ્રેકડાઉન-મૉડલમાં ફેરફાર જરૂરી રહેશે અને તે હાલમાં મુલતવી રાખવામાં આવ્યો છે.
