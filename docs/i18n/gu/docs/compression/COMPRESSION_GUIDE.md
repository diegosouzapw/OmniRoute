## અવલોકન

OmniRoute એક મોડ્યુલર પ્રોમ્પ્ટ કમ્પ્રેશન પાઇપલાઇન અમલમાં મૂકે છે, જે વિનંતીઓ અપસ્ટ્રીમ પ્રદાતાઓ સુધી પહોંચે તે પહેલાં **સક્રિય રીતે** ચાલે છે. આનો અર્થ એ છે કે તમારી ટોકન બચત પારદર્શક રીતે થાય છે — તમારા વર્કફ્લોમાં કોઈ ફેરફાર કરવાની જરૂર નથી.

```
ક્લાયન્ટ વિનંતી
  → કમ્પ્રેશન વ્યૂહરચના પસંદગીકાર
    → કૉમ્બો ઓવરરાઇડ? → કૉમ્બો સેટિંગનો ઉપયોગ કરો
    → સ્વચાલિત-ટ્રિગર થ્રેશોલ્ડ? → સ્વચાલિત મોડનો ઉપયોગ કરો
    → ડિફૉલ્ટ મોડ? → વૈશ્વિક સેટિંગનો ઉપયોગ કરો
    → બંધ? → કમ્પ્રેશન છોડો
  → પસંદ કરેલો કમ્પ્રેશન મોડ
    → બંધ: કોઈ કમ્પ્રેશન નહીં
    → લાઇટ: સુરક્ષિત વ્હાઇટસ્પેસ/ફોર્મેટિંગ સફાઈ (~15%)
    → સ્ટાન્ડર્ડ: Caveman-શૈલીમાં વધારાના શબ્દો દૂર કરવા (~30%)
    → એગ્રેસિવ: ઇતિહાસ એજિંગ + સારાંશીકરણ (~50%)
    → અલ્ટ્રા: હ્યુરિસ્ટિક પ્રૂનિંગ + કોડ-બ્લૉક પાતળા કરવા (~75%)
    → RTK: કમાન્ડ-અવેર ટર્મિનલ/ટૂલ-આઉટપુટ ફિલ્ટરિંગ (60-90% અપસ્ટ્રીમ રેન્જ)
    → સ્ટૅક્ડ: ક્રમબદ્ધ મલ્ટિ-એન્જિન પાઇપલાઇન, સામાન્ય રીતે પહેલાં RTK અને પછી Caveman (78-95% પાત્ર રેન્જ)
  → કમ્પ્રેસ કરેલી વિનંતી → પ્રદાતા
```

## કમ્પ્રેશન મોડ્સ

### બંધ

કોઈ કમ્પ્રેશન લાગુ કરવામાં આવતું નથી. બધા સંદેશા કોઈ ફેરફાર વિના પસાર થાય છે.

### લાઇટ મોડ (~15% બચત, <1ms લેટન્સી)

સૌથી સુરક્ષિત મોડ — અર્થમાં શૂન્ય ફેરફાર, માત્ર ફોર્મેટિંગની સફાઈ:

| તકનીક                    | વર્ણન                                                   |
| ------------------------ | ------------------------------------------------------- |
| `collapseWhitespace`     | લગાતાર ખાલી લાઇનો અને લાઇનના અંતેની સ્પેસને મર્જ કરે છે |
| `dedupSystemPrompt`      | ડુપ્લિકેટ સિસ્ટમ સંદેશા દૂર કરે છે                      |
| `compressToolResults`    | વિસ્તૃત ટૂલ/ફંક્શન આઉટપુટને કમ્પ્રેસ કરે છે             |
| `removeRedundantContent` | પુનરાવર્તિત સૂચનાઓ દૂર કરે છે                           |
| `replaceImageUrls`       | base64 ઇમેજ ડેટા URIને ટૂંકા કરે છે                     |

**આ માટે શ્રેષ્ઠ:** હંમેશાં ચાલુ રાખીને ઉપયોગ કરવા અને સુરક્ષા-નિર્ણાયક વર્કફ્લો માટે.

### સ્ટાન્ડર્ડ મોડ (~30% બચત)

[Caveman](https://github.com/JuliusBrussee/caveman)થી પ્રેરિત — અર્થ જાળવી રાખીને વધારાના શબ્દો અને વિસ્તૃત શબ્દપ્રયોગ દૂર કરે છે:

- વધારાના શબ્દો દૂર કરે છે ("કૃપા કરીને", "મને લાગે છે", "મૂળભૂત રીતે", "ખરેખર")
- વિસ્તૃત શબ્દસમૂહોને સંક્ષિપ્ત કરે છે ("ના હેતુથી" → "માટે", "ના પરિણામે" → "કારણ કે")
- વિનમ્ર સંકોચભર્યા શબ્દપ્રયોગ દૂર કરે છે ("શું તમને વાંધો હશે...", "જો તમે કદાચ કરી શકો તો...")
- કોડિંગ પ્રોમ્પ્ટ માટે અનુકૂલિત 30+ regex નિયમો

**આ માટે શ્રેષ્ઠ:** દૈનિક કોડિંગ વર્કફ્લો અને ખર્ચ પ્રત્યે સચેત ટીમો માટે.

### એગ્રેસિવ મોડ (~50% બચત)

લાંબા સત્રો માટે સ્માર્ટ ઇતિહાસ વ્યવસ્થાપન:

- **સંદેશ એજિંગ** — જૂના સંદેશા ક્રમશઃ વધુ કમ્પ્રેસ થાય છે
- **ટૂલ પરિણામ કમ્પ્રેશન** — લાંબા ટૂલ આઉટપુટને કાપવામાં કે છોડી દેવામાં આવે છે (પ્રથમ/છેલ્લી લાઇનો,
  મેળ ખાતી લાઇનનું ફિલ્ટરિંગ, JSON કીનું સંકોચન)
- **માળખાકીય અખંડિતતા સુરક્ષાઓ** — ખાતરી કરે છે કે `tool_use` + `tool_result` જોડીઓ સુસંગત રહે
- **કોન્ટેક્સ્ટ વિન્ડો જાગૃતિ** — દરેક મોડલની ટોકન મર્યાદાનું પાલન કરે છે

**આ માટે શ્રેષ્ઠ:** વિસ્તૃત ડિબગિંગ સત્રો અને મોટા કોડબેઝ માટે.

### અલ્ટ્રા મોડ (~75% બચત)

ટોકન-નિર્ણાયક પરિસ્થિતિઓ માટે મહત્તમ કમ્પ્રેશન:

- **હ્યુરિસ્ટિક પ્રૂનિંગ** — ગદ્યનું સ્કોર-આધારિત ટોકન પ્રૂનિંગ
- **માળખું જાળવણી** — ફેન્સ્ડ કોડ બ્લૉક્સ, ઇનલાઇન કોડ, URLs અને આઇડેન્ટિફાયર્સને
  ટોમ્બસ્ટોન કરીને મૂળરૂપે ફરી જોડવામાં આવે છે, તેમને ક્યારેય પ્રૂન કરવામાં આવતા નથી
- **વૈકલ્પિક SLM સ્તર** — કૉન્ફિગર કરેલું હોય ત્યારે નાનું સ્થાનિક મોડલ પ્રૂનને વધુ ચોક્કસ બનાવી શકે છે
- એગ્રેસિવ મોડથી સ્વતંત્ર: તે સંદેશ એજિંગ, ટૂલ-પરિણામ કમ્પ્રેશન
  અથવા ફૉલબૅક સારાંશક ચલાવતું નથી (માત્ર SLM-સ્તરની નિષ્ફળતા જ ફૉલબૅક પાસને
  એગ્રેસિવ મારફતે રૂટ કરી શકે છે)

**આ માટે શ્રેષ્ઠ:** જ્યારે તમે વારંવાર કોન્ટેક્સ્ટ મર્યાદા સુધી પહોંચી રહ્યા હોવ.

### RTK મોડ (60-90% અપસ્ટ્રીમ રેન્જ)

RTK મોડ કોડિંગ-એજન્ટ સત્રોમાં દેખાતા વિસ્તૃત ટૂલ આઉટપુટ માટે ઑપ્ટિમાઇઝ કરેલો છે:

- `git status`, `git diff`, `git log`, ટેસ્ટ રનર્સ,
  TypeScript/Vite/Webpack બિલ્ડ્સ, ESLint/Biome/Prettier, npm ઑડિટ/ઇન્સ્ટોલ્સ, Docker લૉગ્સ, ઇન્ફ્રા
  આઉટપુટ અને સામાન્ય શેલ આઉટપુટ જેવા કમાન્ડ/આઉટપુટ વર્ગો શોધે છે
- `open-sse/services/compression/engines/rtk/filters/`માંથી JSON ફિલ્ટર પૅક્સ લાગુ કરે છે
- પ્રોજેક્ટ અથવા વૈશ્વિક `filters.toml` ફાઇલોમાંથી RTK TOML schema v1 ફિલ્ટર્સ ઇમ્પોર્ટ કરે છે, જેમાં ઇનલાઇન-ટેસ્ટ
  માન્યતા અને પ્રોજેક્ટ ફાઇલો માટે ટ્રસ્ટ-ગેટિંગ સામેલ છે
- ઇનલાઇન ચકાસણી નમૂનાઓ સાથે 55 બિલ્ટ-ઇન ફિલ્ટર્સ પૂરા પાડે છે
- ANSI નિયંત્રણ સિક્વન્સ, પ્રોગ્રેસ બાર, પુનરાવર્તિત લાઇનો અને કાર્યવાહી ન કરી શકાય તેવો ઘોંઘાટ દૂર કરે છે
- નિષ્ફળતાઓ, ભૂલો, ચેતવણીઓ, બદલાયેલી ફાઇલો, સારાંશો અને લાંબા આઉટપુટનો છેલ્લો ભાગ જાળવે છે
- ટ્રસ્ટ-ગેટેડ પ્રોજેક્ટ ફિલ્ટર્સ, વૈશ્વિક ફિલ્ટર્સ અને વૈકલ્પિક રીતે સંપાદિત કાચા આઉટપુટની પુનઃપ્રાપ્તિને સપોર્ટ કરે છે

**આ માટે શ્રેષ્ઠ:** શેલ, બિલ્ડ, ટેસ્ટ, git, grep અને ફાઇલ-આઉટપુટ ટ્રાન્સક્રિપ્ટ ધરાવતા એજન્ટ સત્રો માટે.

### સ્ટૅક્ડ મોડ (78-95% પાત્ર રેન્જ)

સ્ટૅક્ડ મોડ એક નિર્ધારિત ક્રમમાં અનેક કમ્પ્રેશન એન્જિન ચલાવે છે. ડિફૉલ્ટ પાઇપલાઇન આ છે:

```txt
RTK -> Caveman
```

આ ક્રમ પહેલાં ટર્મિનલ/ટૂલ આઉટપુટને સંક્ષિપ્ત રાખે છે, ત્યારબાદ બાકી રહેલા કુદરતી-ભાષાના પ્રોમ્પ્ટ પર Caveman અર્થલક્ષી સંક્ષેપ લાગુ કરે છે. સ્ટૅક્ડ પાઇપલાઇન્સને વૈશ્વિક રીતે અથવા રૂટિંગ કૉમ્બોને સોંપાયેલા કમ્પ્રેશન કૉમ્બો દ્વારા કૉન્ફિગર કરી શકાય છે.

**આ માટે શ્રેષ્ઠ:** મોટા ટૂલ લૉગ્સ ઉપરાંત માનવીય સૂચનાઓ અથવા સહાયક સારાંશો ધરાવતા મિશ્ર કોન્ટેક્સ્ટ માટે.

## અપસ્ટ્રીમ બચતનું ગણિત

OmniRoute બે સ્રોતોમાંથી કમ્પ્રેશનની બચતનું દસ્તાવેજીકરણ કરે છે: અપસ્ટ્રીમ પ્રોજેક્ટ બેન્ચમાર્ક્સ અને
OmniRouteનું પોતાનું એન્જિન સંયોજન.

| સ્રોત   | અહીં ઉપયોગમાં લેવાયેલ અપસ્ટ્રીમ READMEનો આંકડો                                                                    |
| ------- | ----------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` ઓછા આઉટપુટ ટોકન્સ, બેન્ચમાર્કમાં સરેરાશ `65%` આઉટપુટ બચત, `22-87%`ની શ્રેણી અને `~46%` ઇનપુટ કમ્પ્રેશન ટૂલ |
| RTK     | કમાન્ડ-આઉટપુટમાં `60-90%` બચત; નમૂના સત્રમાં `~118,000 -> ~23,900` ટોકન્સ, અથવા `79.7%` બચત (`~80%`)              |

ઓવરલેપ થતા ટૂલ/કોન્ટેક્સ્ટ પેલોડ્સ માટે, ડિફૉલ્ટ OmniRoute કોમ્બો એન્જિનોને આ ક્રમમાં સ્ટૅક કરે છે:

```txt
RTK -> Caveman
```

સંયુક્ત બચત ગુણાકાર આધારિત છે, સરવાળા આધારિત નહીં:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

આ `78-95%`નો આંકડો ત્યારે લાગુ પડે છે જ્યારે RTK અને Caveman બંને સમાન ઇનપુટ/કોન્ટેક્સ્ટ પેલોડને ઘટાડી શકે.
Cavemanનો રિસ્પોન્સ આઉટપુટ મોડ અલગ છે: જ્યારે તે સક્ષમ હોય, ત્યારે Cavemanની પોતાની આઉટપુટ બચતનો ઉપયોગ કરો (સરેરાશ `65%`,
મુખ્ય આંકડો `~75%`, શ્રેણી `22-87%`). કુલ બિલિંગ બચત તમારા પ્રોમ્પ્ટ/આઉટપુટના મિશ્રણ પર આધારિત છે.

### "પાત્ર"નો ખરેખર અર્થ શું છે

15-95%ની મુખ્ય શ્રેણી વાસ્તવિક છે, પરંતુ તે ફક્ત **પુનરાવર્તિત અથવા અતિવિસ્તૃત** સામગ્રી પર જ લાગુ પડે છે — વારંવાર આવતી
એરર લાઇનો, એક જ ચેતવણી વારંવાર બતાવતો બિલ્ડ લૉગ, અથવા જરૂર કરતાં મોટો `grep`/ફાઇલ-રીડ ડમ્પ. તેનો
અર્થ એ **નથી** કે દરેક રિક્વેસ્ટમાં એટલી બચત થાય છે.

પ્રાયોગિક રીતે ચકાસાયેલ (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300 સમાન
એરર લાઇનો ધરાવતા Anthropic-આકારના `tool_result` બ્લૉક સામે `stacked` (RTK + Caveman) રન કરવાથી
**95.93% ટોકન બચત / 96.26% અક્ષર બચત** મળી — જે જાહેર કરેલી
શ્રેણીમાં ચોક્કસપણે આવે છે. પરંતુ સામાન્ય, બિન-પુનરાવર્તિત ટૂલ આઉટપુટ (સ્વચ્છ `grep` મેચ સૂચિ,
ટૂંકું ફાઇલ રીડ, સામાન્ય વાર્તાલાપી ટેક્સ્ટ) સામે એ જ પાઇપલાઇન ચલાવવાથી યોગ્ય રીતે **લગભગ શૂન્ય બચત** થાય છે, કારણ કે
દૂર કરવા માટે કંઈપણ પુનરાવર્તિત નથી અને `validateCompression()` (`validation.ts`) એવા
પુનર્લેખનને મોકલવાનો ઇનકાર કરે છે જે કોડ બ્લૉક્સ, URLs, હેડિંગ્સ, વર્ઝન્સ અથવા ALL-CAPS કૉન્સ્ટન્ટ આઇડેન્ટિફાયર્સને કાઢી નાખે કે બદલે.

આ અપેક્ષિત અને સુરક્ષિત વર્તન છે, બગ નહીં: જે કોડિંગ સત્રમાં મોટાભાગે સ્વચ્છ ફાઇલો વાંચવામાં/grep કરવામાં આવે છે તેમાં
કમ્પ્રેશન સંપૂર્ણપણે સક્ષમ હોવા છતાં કુલ બચત મર્યાદિત જોવા મળશે, જ્યારે નિષ્ફળ થતી
લૂપ અથવા ખૂબ વધુ આઉટપુટ આપતા લિન્ટરનો સામનો કરતું સત્ર તે ટ્રાફિક પર સંપૂર્ણ 78-95% શ્રેણી જોશે. કોઈ એક સત્રની
નીચી એકંદર બચત ટકાવારીને કમ્પ્રેશન ખોટી રીતે કૉન્ફિગર થયું હોવાના પુરાવા તરીકે ઉપયોગ કરશો નહીં — પહેલાં તપાસો કે
અંતર્ગત ટૂલ આઉટપુટ ખરેખર પુનરાવર્તિત હતું કે નહીં.

## રૂપરેખાંકન

### ડેશબોર્ડ

`ડેશબોર્ડ → કોન્ટેક્સ્ટ અને કૅશ` પર જાઓ:

- **Caveman** — મોડની પસંદગી, ભાષા પૅક્સ, પૂર્વાવલોકન અને વૈશ્વિક ડિફૉલ્ટ્સ
- **RTK** — કમાન્ડ-ફિલ્ટર પૂર્વાવલોકન, RTK સુરક્ષા સેટિંગ્સ અને ફિલ્ટર કૅટલૉગ
- **કમ્પ્રેશન કોમ્બોઝ** — રૂટિંગ કોમ્બોઝને સોંપેલી નામવાળી એન્જિન પાઇપલાઇન્સ
- **ઑટો-ટ્રિગર થ્રેશોલ્ડ** — ટોકનની સંખ્યા થ્રેશોલ્ડ કરતાં વધી જાય ત્યારે કમ્પ્રેશન આપમેળે સક્રિય કરે છે

### પ્રતિ-કોમ્બો ઓવરરાઇડ

`ડેશબોર્ડ → કોન્ટેક્સ્ટ અને કૅશ → કમ્પ્રેશન કોમ્બોઝ`માં, રૂટિંગ કોમ્બોને કમ્પ્રેશન કોમ્બો સોંપો:

```txt
કોમ્બો: "free-tier-fallback"
  કમ્પ્રેશન કોમ્બો: "coding-agent-stack"
  પાઇપલાઇન: RTK -> Caveman
  લક્ષ્યો:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

આ તમને પેઇડ સબ્સ્ક્રિપ્શન્સ પર લાઇટ મોડ જાળવી રાખીને મફત/કોડિંગ પ્રદાતાઓ પર સ્ટૅક્ડ કમ્પ્રેશનનો ઉપયોગ કરવાની મંજૂરી આપે છે.

આ "પ્રતિ-કોમ્બો ઓવરરાઇડ" સોંપણી **રૂટિંગ-કોમ્બો કમ્પ્રેશન મોડ** ઓવરરાઇડ (ડિફૉલ્ટ/બંધ/લાઇટ/સ્ટાન્ડર્ડ/આક્રમક/અલ્ટ્રા/Codex Responses — આ ફીલ્ડનું સ્કીમા `rtk`, `stacked` અને `omniglyph` પણ સ્વીકારે છે) કરતાં અલગ નિયંત્રણ છે — તે ઓવરરાઇડ નામવાળી કમ્પ્રેશન-કોમ્બો પાઇપલાઇન પસંદ કરતું નથી; તે માત્ર `resolveCompressionPlan` દ્વારા ઉપયોગમાં લેવાતું `compressionMode` ફીલ્ડ સેટ કરે છે. તેને કોમ્બો કાર્ડ (`ડેશબોર્ડ → કોમ્બોઝ`) પર અથવા, #6760થી, ઉપર દસ્તાવેજીકૃત પાઇપલાઇન-સોંપણી ચેકબૉક્સની બાજુમાં `ડેશબોર્ડ → કોન્ટેક્સ્ટ અને કૅશ → કમ્પ્રેશન કોમ્બોઝ` પરની "રૂટિંગને સોંપો" સૂચિમાં પ્રતિ રૂટિંગ કોમ્બો સેટ કરી શકાય છે. બંને સપાટીઓ સમાન `PUT /api/combos/{id}` એન્ડપોઇન્ટ દ્વારા સંગ્રહિત થાય છે.

### પ્રતિ-વિનંતી ઓવરરાઇડ

એક વિનંતી માટે કમ્પ્રેશન પ્લાનને ઓવરરાઇડ કરવા `x-omniroute-compression` વિનંતી હેડર મોકલો. તેની પ્રાથમિકતા સૌથી ઊંચી છે — તે રૂટિંગ-કોમ્બો ઓવરરાઇડ, સક્રિય પ્રોફાઇલ, ઑટો-ટ્રિગર અને પેનલ ડિફૉલ્ટ કરતાં અગ્રતા ધરાવે છે. અજ્ઞાત મૂલ્યો અવગણવામાં આવે છે (વિનંતી ક્યારેય નકારવામાં આવતી નથી) અને વૈશ્વિક માસ્ટર સ્વિચ હજુ પણ બધું નિયંત્રિત કરે છે: જ્યારે કમ્પ્રેશન વૈશ્વિક સ્તરે બંધ હોય, ત્યારે હેડર તેને ચાલુ કરી શકતું નથી. મૂલ્યો:

| મૂલ્ય         | અસર                                                                                                |
| ------------- | -------------------------------------------------------------------------------------------------- |
| `off`         | આ વિનંતી માટે કોઈ કમ્પ્રેશન નહીં.                                                                  |
| `default`     | પેનલમાંથી મેળવેલી ડિફૉલ્ટ પ્રોફાઇલ (સક્રિય પ્રોફાઇલને અવગણે છે). લૉસી એન્જિનો બંધ રાખવામાં આવે છે. |
| `safe`        | હેડર ન આપ્યું હોય તેવું જ: ફક્ત ડિડુપ અને વ્હાઇટસ્પેસ ફોલ્ડિંગ.                                    |
| `allow-lossy` | સારાંશો, પ્રાસંગિકતા ફિલ્ટર્સ અને શૈલી પુનર્લેખન સહિત આ વિનંતીનો ઑપરેટર પ્લાન જાળવે છે.            |
| `engine:<id>` | સક્રિય હોય ત્યારે એક એન્જિન, દા.ત. `engine:rtk`. આ તે એન્જિન માટેનું પ્રતિ-વિનંતી ઑપ્ટ-ઇન છે.      |
| `<combo>`     | એક નામવાળો કોમ્બો, જે પહેલાં નામથી (કેસ-ઇન્સેન્સિટિવ રીતે) અને પછી id દ્વારા મેળ ખાય છે.           |

`allow-lossy`, `engine:<id>` અથવા કોઈ નામવાળા કોમ્બો વિના, લૉસી એન્જિનો લાગુ કરવામાં આવતા નથી. કમ્પ્રેશન ચાલુ હોય ત્યારે પણ વિનંતી પર સેશન ડિડુપ અને વ્હાઇટસ્પેસ ફોલ્ડિંગ લાગુ થાય છે.

લાગુ કરાયેલ પ્લાનને `X-OmniRoute-Compression: <mode>; source=<source>` પ્રતિસાદ હેડરમાં પાછો દર્શાવવામાં આવે છે, જ્યાં `<source>` એ `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` અથવા `off`માંથી એક હોય છે.

## આભારવિધિ

Standard મોડના કમ્પ્રેશન નિયમો **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ 51K+) દ્વારા બનાવાયેલા **[Caveman](https://github.com/JuliusBrussee/caveman)**થી પ્રેરિત છે — વાયરલ "જ્યારે થોડા ટોકનથી કામ થઈ જાય ત્યારે ઘણા ટોકન શા માટે વાપરવા" પ્રોજેક્ટ. Caveman `~75%` ઓછા આઉટપુટ ટોકન્સ, બેન્ચમાર્કમાં સરેરાશ `65%` આઉટપુટ બચત, `22-87%`ની આઉટપુટ રેન્જ અને `~46%`નું ઇનપુટ-કમ્પ્રેશન ટૂલ દર્શાવે છે.

RTK મોડ **[RTK AI](https://github.com/rtk-ai)** દ્વારા બનાવાયેલા **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)**થી પ્રેરિત છે — ટર્મિનલ, બિલ્ડ, ટેસ્ટ, git અને ટૂલ-આઉટપુટ ફિલ્ટરિંગ માટેનો ઉચ્ચ-પ્રદર્શન ધરાવતો કમાન્ડ-આઉટપુટ કમ્પ્રેશન પ્રોજેક્ટ. RTK `60-90%` બચત દર્શાવે છે, જ્યારે તેના READMEના નમૂના સેશનમાં `~80%` બચત બતાવવામાં આવી છે.

## અદ્યતન કમ્પ્રેશન સિસ્ટમ્સ

ઉપર વર્ણવેલા 7 મોડ્સ ઉપરાંત (સોર્સ `codex-responses` અને
`omniglyph` મોડ્સ પણ સ્વીકારે છે, જેને આ માર્ગદર્શિકા આવરી લેતી નથી), નીચેના વિભાગો એવા ફીચર્સને આવરી લે છે
જે આ મોડ્સની અંદર અથવા તેમની સાથે મળીને કાર્ય કરે છે: Tool Result Compression અને Progressive Aging
એ aggressive એન્જિનનાં પગલાં 1 અને 2 છે (Aggressive મોડ અને
stacked પાઇપલાઇનનું `aggressive` પગલું), Stacked Pipeline એ Stacked મોડને ચલાવવાની રીત છે, Cache-Aware Compression
કમ્પ્રેશન ચાલુ હોય ત્યારે કૅશિંગ પ્રોવાઇડર્સ માટે `aggressive` અને `ultra`ને `standard`માં ડાઉનગ્રેડ
કરે છે, અને Caveman Output Mode તથા Output Styles ઑપ્ટ-ઇન સિસ્ટમ-પ્રૉમ્પ્ટ સૂચનાઓ છે,
જે ડિફૉલ્ટ રૂપે બંધ હોય છે અને રિક્વેસ્ટને કમ્પ્રેસ કરવાને બદલે મૉડલના આઉટપુટને આકાર આપે છે.

### કૅશ-અવેર કમ્પ્રેશન

કેટલાક પ્રોવાઇડર્સ (જેમ કે પ્રૉમ્પ્ટ કૅશિંગ સાથે Anthropic) **પ્રૉમ્પ્ટ કૅશિંગ**ને સપોર્ટ કરે છે,
જે તેમને ખર્ચ અને લેટન્સી ઘટાડવા માટે પ્રૉમ્પ્ટના કેટલાક ભાગો કૅશ કરવાની સુવિધા આપે છે. જ્યારે
કૅશિંગ સક્ષમ હોય, ત્યારે aggressive કમ્પ્રેશન વાસ્તવમાં પ્રદર્શનને **નુકસાન** પહોંચાડી શકે છે
કારણ કે તે કૅશ કરેલા ટોકન્સને બદલે છે, જેથી કૅશ અમાન્ય થઈ જાય છે.

`cachingAware.ts` મૉડ્યૂલ **કૅશિંગ કોન્ટેક્સ્ટ શોધીને** અને
તે મુજબ **કમ્પ્રેશન વ્યૂહરચનાને સમાયોજિત કરીને** આ સમસ્યાનું નિરાકરણ લાવે છે.

#### તે કેવી રીતે કાર્ય કરે છે

1. **કૅશિંગ કોન્ટેક્સ્ટ શોધો** — `cache_control` માર્કર્સ માટે રિક્વેસ્ટ બૉડીને સ્કૅન કરે છે
2. **કૅશિંગ પ્રોવાઇડર્સ ઓળખો** — લક્ષ્ય પ્રોવાઇડર કૅશિંગને સપોર્ટ કરે છે કે નહીં તે તપાસે છે
3. **વ્યૂહરચના સમાયોજિત કરો** — કૅશિંગ પ્રોવાઇડર્સ માટે `aggressive`/`ultra`ને `standard`માં ડાઉનગ્રેડ કરે છે
4. **સિસ્ટમ પ્રૉમ્પ્ટ છોડો** — સિસ્ટમ પ્રૉમ્પ્ટ્સ સામાન્ય રીતે કૅશ થયેલા હોય છે, તેથી તેમને કમ્પ્રેસ કરશો નહીં

વ્યૂહરચના હેલ્પર `deterministicOnly` ફ્લૅગ પણ પરત કરે છે, પરંતુ પ્લાન બિલ્ડર
ફક્ત વ્યૂહરચનાનો ઉપયોગ કરે છે — હાલમાં ડાઉનસ્ટ્રીમમાં કંઈપણ આ ફ્લૅગને વાંચતું નથી.

#### કોડનું ઉદાહરણ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← કૅશ માર્કર
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ક્યારે ઉપયોગ કરવો

કૅશ-અવેર કમ્પ્રેશન **હંમેશાં ચાલુ** હોય છે — કોઈ કન્ફિગરેશનની જરૂર નથી. જ્યારે પણ
કમ્પ્રેશન ચાલુ હોય અને લક્ષ્ય પ્રોવાઇડર પ્રૉમ્પ્ટ કૅશિંગને સપોર્ટ કરતો હોય (Anthropic, OpenAI,
વગેરે), ત્યારે તે સક્રિય થાય છે; સ્પષ્ટ `cache_control` માર્કર્સ જરૂરી નથી — માત્ર કૅશિંગ પ્રોવાઇડર
જ ડાઉનગ્રેડને ટ્રિગર કરે છે, અને માત્ર માર્કર્સ ક્યારેય એવું કરતા નથી (માર્કર ડિટેક્શન કૅશ
ટેલિમેટ્રીને ઇનપુટ આપે છે, વ્યૂહરચના અંગેના નિર્ણયને નહીં).

### પ્રોગ્રેસિવ એજિંગ

લાંબી વાતચીતોમાં અનેક મેસેજ ટર્ન્સ એકઠા થાય છે, પરંતુ જૂના ટર્ન્સની
પ્રસ્તુતતા ઓછી થતી જાય છે. `progressiveAging.ts` મૉડ્યૂલ **ટર્નના અંતર અનુસાર મેસેજની ગુણવત્તા ઘટાડે છે**
(અંતર વાતચીતના અંતથી માપવામાં આવે છે). રિલીઝ કરેલા ડિફૉલ્ટ્સ સાથે
(`verbatim: 2, light: 2, moderate: 3`):

- **છેલ્લા 2 ટર્ન (અંતર ≤ 2)**: યથાવત્ રાખવામાં આવે છે
- **અંતર 3**: Caveman સંકોચન (બિનજરૂરી શબ્દો દૂર કરવા)
- **અંતર 4+**: Assistant સંદેશાઓનો સારાંશ બનાવવામાં આવે છે; user સંદેશાઓને તેમની પ્રથમ
  પંક્તિ સુધી ઘટાડવામાં આવે છે, વધુમાં વધુ 120 અક્ષરો સુધી; અન્ય ભૂમિકાઓને અસ્પર્શિત રાખવામાં આવે છે. System prompts, પહેલેથી જૂના કરાયેલા
  સંદેશાઓ અને નવીનતમ user સંદેશાને અંતર ગમે તે હોય, હંમેશાં યથાવત્ રાખવામાં આવે છે.
  કંઈપણ સંપૂર્ણપણે કાઢી નાખવામાં આવતું નથી, અને પ્રદાન કરેલા ડિફૉલ્ટ્સ સાથે `light`
  બેન્ડ અપ્રાપ્ય છે (`light`, `verbatim` જેટલું છે).

#### કોડ ઉદાહરણ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... વધુ 50 ટર્ન ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // છેલ્લા 3 ટર્ન: યથાવત્
  light: 8, // અંતર <= 8: હળવું સંકોચન
  moderate: 20, // અંતર <= 20: caveman સંકોચન
  fullSummary: 5, // type દ્વારા આવશ્યક, banding કોડ દ્વારા વાંચવામાં આવતું નથી
  // અંતર > 20: સારાંશ બનાવવામાં આવે છે (assistant) / પ્રથમ પંક્તિ રાખવામાં આવે છે (user)
});

// saved = બચાવેલા tokensની સંખ્યા
```

#### ક્યારે ઉપયોગ કરવો

`aggressive` મોડ માટે Progressive aging **હંમેશાં ચાલુ** હોય છે — તે
`compressAggressive()`નું પગલું 2 છે. Ultra મોડ તેને ચલાવતો નથી. તે ખાસ કરીને
આ માટે અસરકારક છે:

- લાંબા સમય સુધી ચાલતા કોડિંગ સત્રો
- અનેક દિવસોની વાતચીતો
- ઘણા tool calls ધરાવતા Agentic workflows

### Caveman Output Mode

Caveman output mode એવા **system prompt instructions** ઉમેરે છે જે મોડલને પોતે જ
સંક્ષિપ્ત output આપવા કહે છે — `lite` સ્તર પૂર્ણ વાક્યો જાળવીને સંક્ષિપ્ત જવાબો માંગે છે, `full`
તેને "સ્માર્ટ cavemanની જેમ સંક્ષિપ્ત જવાબ આપવા" કહે છે, અને `ultra` ટેલિગ્રાફિક output માંગે છે;
સૂચનાઓ માત્ર વિનંતી કરે છે, તેની ખાતરી આપી શકતી નથી. Requests તેને
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) મારફતે મેળવે છે:
`open-sse/handlers/chatCore.ts` પહેલાં back-compat shim વડે પસંદગી નક્કી કરે છે
(`open-sse/services/compression/outputStyles/backCompat.ts`માં
`resolveOutputStyleSelection()`), જે `outputStyles`
ખાલી હોય ત્યારે, સક્ષમ કરેલા `cavemanOutputMode`ને
`cavemanOutputMode.intensity` પરના `terse-prose` output style સાથે મેપ કરે છે
(નીચે Back-compat જુઓ); ખાલી ન હોય તેવી `outputStyles`
પસંદગી જેવી છે તેવી જ ઉપયોગમાં લેવાય છે, અને ત્યારબાદ `cavemanOutputMode.enabled` તથા `intensity`ની
કોઈ અસર થતી નથી, જ્યારે તેનું `autoClarity` toggle હજી પણ લાગુ પડે છે. `outputMode.ts`માં
સૂચનાના texts (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), content bypass અને
injection દ્વારા ઉપયોગમાં લેવાતો placement helper છે; તેના પોતાના `applyCavemanOutputMode()` injectorનો કોઈ
production caller નથી.

#### તે કેવી રીતે કાર્ય કરે છે

આ મોડ inputને સંકોચતો નથી. તે system promptમાં instruction block ઉમેરે છે
(નીચે How injection works જુઓ), અને request માટે પસંદ કરેલો કોઈપણ input compression mode
ત્યારબાદ પણ, હવે block ધરાવતા body પર ચાલે છે. દરેક સ્તર જેની સાથે સમાપ્ત થાય છે તે shared
boundaries clause પહેલાં, અંગ્રેજી `full` સ્તર આ રીતે લખાયેલું છે:

> "સ્માર્ટ cavemanની જેમ સંક્ષિપ્ત જવાબ આપો. articles (a/an/the), બિનજરૂરી શબ્દો (just/really/basically/actually/simply), ઔપચારિક સૌજન્ય, અને અનિશ્ચિતતા દર્શાવતા શબ્દો કાઢી નાખો. વાક્યખંડો માન્ય છે. ટૂંકા સમાનાર્થી શબ્દો વાપરો (extensive નહીં, big; implement નહીં, fix). તમામ તકનીકી સાર, code, errors, URLs અને identifiers ચોક્કસ રાખો."

આ ખાસ કરીને આ માટે સારી રીતે કાર્ય કરે છે:

- Code generation (વધુ સંક્ષિપ્ત output = ઓછા tokens)
- ઝડપી Q&A (વિસ્તૃત સમજૂતીઓની જરૂર નથી)
- Batch processing (throughput મહત્તમ કરવા)

#### ક્યારે ઉપયોગ કરવો

Caveman output mode **opt-in** છે. Compression ચાલુ હોય ત્યારે (`enabled: true`, Compression Settings પેજ પરનું master toggle
ચાલુ હોય), તેને `cavemanOutputMode.enabled` વડે ચાલુ કરો; `intensity`
`lite`, `full` અથવા `ultra` પસંદ કરે છે:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

Compression comboનું **Output Mode** toggle (`outputMode`, અને `outputModeIntensity`માં સ્તર)
તે combo લાગુ પડતી requests માટે એ જ switch સેટ કરે છે, અને
`omniroute_set_compression_engine` MCP tool તેના boolean `outputMode`
argument દ્વારા તેને લખે છે. ખાલી ન હોય તેવી `outputStyles` પસંદગી આ switch કરતાં પ્રાધાન્ય લે છે.
dashboardમાં, **Terse prose** output style સક્ષમ કરવાથી એ જ block inject થાય છે (નીચે Output
Styles જુઓ).

#### ઇન્જેક્શન કેવી રીતે કાર્ય કરે છે

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) પસંદગીને
કૅટલૉગ સામે નિર્ધારિત કરે છે (અજાણ્યા ids અને લોકેલ સાથે મેળ ન ખાતી શૈલીઓ
દૂર કરવામાં આવે છે, તેને ક્યારેય ભૂલ ગણાતી નથી; કોઈ શૈલીમાં નિર્ધારિત ન થતી પસંદગી bodyને
અપરિવર્તિત રાખે છે અને `no_styles` તરીકે છોડી દેવામાં આવે છે), પસંદ કરેલી સૂચનાઓને કૅટલૉગના
ક્રમમાં જોડે છે,
સીમાઓની કલમ **એક વાર** ઉમેરે છે (અને જ્યારે `less-code` અથવા `ponytail` પસંદ કરેલું હોય ત્યારે
સુરક્ષા કલમ, `SAFETY_BOUNDARIES` અથવા તેનો અનુવાદ પણ), અને બ્લૉકને એક
idempotency marker (`[OmniRoute Output Styles]`)થી શરૂ કરે છે, જેથી ફરી લાગુ કરવું no-op બને છે. જ્યારે
નિર્ધારિત ભાષા (નીચે Language selection જુઓ) માટે અનુવાદ ઉપલબ્ધ હોય, ત્યારે અંગ્રેજીને બદલે
સ્થાનિકીકૃત સૂચના દાખલ કરવામાં આવે છે.

ખાલી ન હોય તેવા `messages` arrayવાળા body પર, idempotency તપાસ
content bypass પહેલાં ચાલે છે: જ્યારે `[OmniRoute Output Styles]` marker પહેલેથી જ ટોપ-લેવલ
`system` fieldમાં (string અથવા content-block array) અથવા string
contentવાળા system messageમાં હોય, ત્યારે bodyને `already_applied` તરીકે અપરિવર્તિત રાખવામાં આવે છે અને કોઈ keyword તપાસ ચાલતી નથી.
અન્યથા content bypass (`open-sse/services/compression/outputMode.ts`માં
`shouldBypassCavemanOutputMode()`) છેલ્લાં ત્રણ
messagesની ભૂમિકા ગમે તે હોય, તેમનું લખાણ તપાસે છે અને જ્યારે તે લખાણ સુરક્ષા, અપરિવર્તનીય-ક્રિયા અથવા સ્પષ્ટીકરણ keywords સાથે મેળ ખાય, અથવા
ક્રમ-સંવેદનશીલ શ્રેણીમાં: `first`, `then`, `after that`, `before`, `rollback` અથવા
`backup` પછી 240 charactersની અંદર `delete`, `drop`, `migrate`, `deploy` અથવા
`release` આવે, ત્યારે સમગ્ર turn માટે શૈલીઓ છોડી દે છે. **Auto-Clarity Bypass** toggle
(`cavemanOutputMode.autoClarity`, ડિફૉલ્ટ રૂપે ચાલુ) ચાલુ હોય ત્યારે bypass ચાલે છે; toggle બંધ કરવાથી
keyword તપાસ છોડી દેવામાં આવે છે.

જ્યારે bypass turnને પસાર થવા દે છે, ત્યારે `placeSystemInstruction()` (એ જ file), જે
ક્યારેય નવું `messages[0]` બનાવતું નથી, તેને મળતી નીચેની પ્રથમ જગ્યાએ બ્લૉક મૂકે છે:

1. string contentવાળો શરૂઆતનો system message: બ્લૉક તેના લખાણ પછી ઉમેરવામાં આવે છે.
2. ટોપ-લેવલ `system` field: બ્લૉક stringના લખાણ પછી ઉમેરવામાં આવે છે અથવા
   content-block arrayમાં નવા text block તરીકે ઉમેરવામાં આવે છે.
3. string contentવાળો પછીનો પ્રથમ system message: બ્લૉક તેના
   લખાણ પછી ઉમેરવામાં આવે છે.
4. ઉપરોક્તમાંથી કંઈ નહીં: બ્લૉક `messages`ના અંતે નવા system messageમાં જાય છે.

`messages` array વિનાના (અથવા ખાલી arrayવાળા) body પર કોઈ content bypass ચાલતું નથી અને
ટોપ-લેવલ `system` field ધ્યાનમાં લેવાતું નથી. બ્લૉક string `instructions` fieldના લખાણ પછી ઉમેરવામાં આવે છે,
સિવાય કે તે fieldમાં પહેલેથી જ
`[OmniRoute Output Styles]` marker હોય; એ સ્થિતિમાં bodyને
`already_applied` તરીકે અપરિવર્તિત રાખવામાં આવે છે. જ્યારે bodyમાં string `instructions` field ન હોય પરંતુ `input`
(string અથવા array) હોય, ત્યારે બ્લૉક `instructions` બને છે અને તે fieldમાં રહેલી કોઈપણ non-string valueને
બદલે છે. string `instructions` field અથવા string કે array
`input`માંથી એકપણ ન ધરાવતો body અપરિવર્તિત રહે છે અને `no_messages` તરીકે છોડી દેવામાં આવે છે.

#### સક્ષમ કેવી રીતે કરવું

ડૅશબોર્ડમાં: **Compression Context → Compression Settings**
(`/dashboard/context/settings`), Output styles વિભાગ: દરેક સ્ટાઇલ માટે on/off
ટૉગલ અને લેવલ સિલેક્ટર ધરાવતી એક પંક્તિ. કમ્પ્રેશન પોતે ચાલુ હોય ત્યારે સ્ટાઇલ્સ ઇન્જેક્ટ થાય છે (પેજનું
માસ્ટર ટૉગલ, `enabled`). **Auto-Clarity Bypass** ટૉગલ **Caveman**
પેજ (`/dashboard/context/caveman`) પર, તેના **Output Mode** કાર્ડમાં છે. પ્રોગ્રામેટિક રીતે,
કમ્પ્રેશન કૉન્ફિગ પસંદગીને આ રીતે સાચવે છે:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

બૅકવર્ડ કમ્પેટિબિલિટી: `outputStyles` ખાલી હોય ત્યારે, લેગસી `cavemanOutputMode.enabled`
સેટિંગ `cavemanOutputMode.intensity` પર `terse-prose` સાથે મૅપ થાય છે. ત્યારબાદ બ્લૉક
`[OmniRoute Output Styles]` માર્કરથી શરૂ થાય છે, જ્યાં લેગસી `applyCavemanOutputMode()`
ઇન્જેક્ટરે `[OmniRoute Caveman Output Mode]` લખ્યું હતું. માર્કરની નીચેનું લખાણ
en, pt-BR, es, de, fr, it, ru, id અને viમાં લેગસી ઇન્જેક્શન સાથે મેળ ખાય છે; ja અને zhમાં
બાઉન્ડરીઝ ક્લૉઝ પહેલાં એક વધારાની સ્પેસ હોય છે. `terse-prose`નું pt-BR, es, de,
fr, it, ru, zh, ja, id અને viમાં અનુવાદ થાય છે, તેથી જે રિક્વેસ્ટની રિઝોલ્વ થયેલી ભાષા `hu` હોય તેને
અંગ્રેજી લખાણ મળે છે, જ્યારે લેગસી ઇન્જેક્ટર તેના હંગેરિયન લખાણનો ઉપયોગ કરતું હતું.

આઉટપુટ-સ્ટાઇલ ભાષા પસંદગી (`outputStyles/apply.ts`માં
`resolveOutputStyleLanguage()`): `languageConfig.enabled` ચાલુ હોય ત્યારે, `autoDetect`
રિક્વેસ્ટની `messages` ઍરેમાં લખાણ ધરાવતા સૌથી તાજેતરના યુઝર મેસેજને સૅમ્પલ કરે છે (સ્ટ્રિંગ કન્ટેન્ટ,
અથવા તેના કન્ટેન્ટ પાર્ટ્સનું `text`) અને તેના પર Caveman એન્જિનનું ડિટેક્ટર
(`detectCompressionLanguage()`) ચલાવે છે. લખાણમાં હાન અક્ષરો હોય અને કાના ન હોય તો ડિટેક્ટર
`zh` પરત કરે છે; અન્યથા, `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` અને `id`
માંથી જેને સૌથી વધુ હિન્ટ મૅચ મળે તે પરત કરે છે, અને કોઈ મૅચ ન હોય ત્યારે `en` પરત કરે છે —
જે લખાણનું તે વર્ગીકરણ ન કરી શકે તેને અંગ્રેજી મળે છે, `defaultLanguage` ક્યારેય નહીં, અને સ્ટાઇલ્સમાં
`vi` લખાણ સામેલ હોવા છતાં `vi` ક્યારેય ડિટેક્ટ થતું નથી. Responses API બોડી તેના ટર્ન્સ
`input`માં રાખે છે, જેને સૅમ્પલ કરવામાં આવતું નથી, તેથી તેને `defaultLanguage`, પછી અંગ્રેજી મળે છે.
જ્યારે `messages`માં કોઈ યુઝર મેસેજ પાસે લખાણ ન હોય, અથવા `autoDetect` બંધ હોય, ત્યારે
`defaultLanguage` લાગુ પડે છે, પછી અંગ્રેજી. `languageConfig.enabled` બંધ હોય ત્યારે, ભાષા
અંગ્રેજી હોય છે — સિવાય કે રિક્વેસ્ટ પર કોઈ કમ્પ્રેશન કોમ્બો લાગુ પડતો હોય (રિક્વેસ્ટના રાઉટિંગ
કોમ્બોને અસાઇન કરેલો કોમ્બો, અથવા બિલ્ટ-ઇન સ્ટૅક્ડ પાઇપલાઇન માટે chatCore જે ડિફૉલ્ટ કમ્પ્રેશન કોમ્બો
પર ફૉલબૅક કરે છે): કોઈ કોમ્બો લાગુ કરવાથી તે રિક્વેસ્ટ માટે `languageConfig.enabled` ચાલુ થાય છે અને
કોમ્બોના લેંગ્વેજ પૅક્સ પરથી `defaultLanguage` સેટ થાય છે (જો સેવ કરેલું મૂલ્ય કોમ્બોના પૅક્સમાંથી
એક હોય તો તે મૂલ્ય, અન્યથા કોમ્બોનો પ્રથમ પૅક, જે ડિફૉલ્ટ રૂપે `en` હોય છે), જ્યારે સેવ કરેલું
`autoDetect` (ડિફૉલ્ટ રૂપે ચાલુ) હજી પણ લાગુ પડે છે. Caveman ઇનપુટ એન્જિન તેની રૂલ-પૅક ભાષા
અલગ રીતે પસંદ કરે છે — દરેક ટેક્સ્ટ પાર્ટ દીઠ અને, ઑટો-ડિટેક્ટ બંધ હોય ત્યારે, `enabledPacks`
દ્વારા ગેટેડ.

સ્ટાઇલ × ભાષા મૅટ્રિક્સને
`tests/unit/compression/output-styles-i18n-matrix.test.ts` દ્વારા પિન કરવામાં આવે છે: દરેક કૅટલૉગ
સ્ટાઇલ માટે ટેસ્ટના `BASELINE_LANGUAGES`માં એન્ટ્રી હોવી આવશ્યક છે; જે સ્ટાઇલ લોકેલ-ગેટેડ નથી
તેમાં pt-BR અનુવાદ હોવો આવશ્યક છે (લોકેલ-ગેટેડ `terse-cjk`ને આ નિયમમાંથી મુક્તિ છે), સિવાય કે તે
`KNOWN_ENGLISH_ONLY`માં સૂચિબદ્ધ હોય, જેમાં માત્ર એવી સ્ટાઇલ્સ હોઈ શકે છે જેમના કોઈ અનુવાદ જ નથી —
સૂચિબદ્ધ સ્ટાઇલનો કોઈપણ અનુવાદ હોય તો ટેસ્ટ નિષ્ફળ જાય છે; અને જો કોઈ સ્ટાઇલ તેની
`BASELINE_LANGUAGES` એન્ટ્રીમાં સૂચિબદ્ધ ભાષા ગુમાવે તો તે ટેસ્ટમાં નિષ્ફળ જાય છે. સ્ટાઇલ ઉમેરવા માટે,
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) જુઓ.

### ટૂલ રિઝલ્ટ કમ્પ્રેશન

`open-sse/services/compression/toolResultCompressor.ts`માં `compressToolResult()`
ટૂલ-રિઝલ્ટ લખાણને **5 વ્યૂહરચનાઓ** વડે કમ્પ્રેસ કરે છે. તે તેમને આ ક્રમમાં અજમાવે છે, અને
જે પહેલી સક્ષમ વ્યૂહરચનાનો ચેક કન્ટેન્ટ સાથે મૅચ થાય છે તે પરિણામ નક્કી કરે છે:

1. **`fileContent`**: 3 અથવા વધુ લાઇનો ધરાવતી સામગ્રી, જેમાં ઓછામાં ઓછી એક લાઇન,
   શરૂઆતનું ઇન્ડેન્ટેશન અવગણીને, `import `, `export `, `function `, `class `,
   `const `, `let `, `var ` અથવા `return ` (કીવર્ડ અને તેની પછી સ્પેસ)થી શરૂ થાય છે,
   અથવા `if`, `for` અથવા `while` પછી `(` અથવા ` (` આવે છે, તે તેની પ્રથમ 20 અને છેલ્લી
   5 લાઇનો રાખે છે અને કાઢી નાખેલો મધ્ય ભાગ ચિહ્નિત કરે છે.
2. **`grepSearch`**: ઓછામાં ઓછી એક લાઇન `<path>:<digits>:` સ્વરૂપની હોય તેવી સામગ્રી,
   જેમાં પ્રથમ કોલન પહેલાંના ટેક્સ્ટમાં કોઈ વ્હાઇટસ્પેસ ન હોય, તે ફક્ત એવી લાઇનો રાખે છે,
   વધુમાં વધુ 30, અને ત્યારબાદ બાકીના મેળોની સંખ્યા તથા મેળ ખાતી ફાઇલોની સૂચિ આપે છે;
   બીજી બધી લાઇનો કાઢી નાખવામાં આવે છે. વ્યૂહરચના ટ્રિગર કરવા માટે આવી એક લાઇન પૂરતી છે,
   તેથી `12:30:45` જેવા ટાઇમસ્ટૅમ્પથી શરૂ થતી લૉગ લાઇન પણ ગણાય છે.
3. **`shellOutput`**: ANSI CSI ક્રમ (`ESC[` પછી અંકો અથવા સેમિકોલન અને પછી કોઈ અક્ષર,
   જેમ કે રંગ કોડમાં) ધરાવતું આઉટપુટ અથવા ટેક્સ્ટમાં ક્યાંય પણ વ્હાઇટસ્પેસ પછી આવતું `$`
   ધરાવતું આઉટપુટ તે ક્રમો ગુમાવે છે (અન્ય એસ્કેપ, જેમ કે `ESC[?25l` અથવા OSC
   વિન્ડો-શીર્ષક ક્રમ, જાળવી રાખવામાં આવે છે) અને તેની છેલ્લી 50 લાઇનો રાખે છે, જ્યારે
   સળંગ પુનરાવર્તિત લાઇનોને એકમાં સંકોચે છે. આ તપાસ `json` અને `errorMessage` પહેલાં
   ચાલતી હોવાથી, આવું `$` ધરાવતું JSON અથવા ભૂલ આઉટપુટ `shellOutput` ચાલુ હોય ત્યારે
   ક્યારેય તેમના સુધી પહોંચતું નથી.
4. **`json`**: 2,000 અક્ષરોથી મોટું JSON પેલોડ, જે વૈકલ્પિક વ્હાઇટસ્પેસ પછી `{` અથવા `[`
   થી શરૂ થાય છે અને સફળતાપૂર્વક પાર્સ થાય છે, તેનો સારાંશ બનાવવામાં આવે છે: 7 કરતાં વધુ
   આઇટમ ધરાવતો એરે તેની પ્રથમ 5 અને છેલ્લી 2 આઇટમ તથા તેની કુલ સંખ્યા રાખે છે, અને
   ઑબ્જેક્ટ તેની પ્રથમ 20 કી રાખે છે, જેમાં દરેક નેસ્ટેડ ઑબ્જેક્ટ અથવા એરે મૂલ્યને
   `{…N keys}` પ્લેસહોલ્ડરથી બદલવામાં આવે છે (એરે માટે, N તેની લંબાઈ છે) અને પ્રથમ 20
   પછી કાઢી નાખેલી કીની ગણતરી કરતું `_remaining_<N>_keys` માર્કર ઉમેરવામાં આવે છે.
   સ્કેલર મૂલ્યો આખેઆખા કૉપી થાય છે, તેથી નેસ્ટેડ મૂલ્યો વિનાનું 20 અથવા ઓછી કી ધરાવતું
   ઑબ્જેક્ટ માત્ર ફરી ઇન્ડેન્ટ થાય છે — મિનિફાઇડ ઑબ્જેક્ટમાં અક્ષરો વધે છે અને તે
   અપરિવર્તિત રહે છે.
5. **`errorMessage`**: ક્યાંય પણ અને કોઈપણ લેટર કેસમાં `error:`, `error ` (શબ્દ પછી
   સ્પેસ, જેમ કે `no error found`માં), `[error]`, `exception:`, `exception `,
   `[exception]` અથવા `traceback` ધરાવતું આઉટપુટ તેની પ્રથમ લાઇન, ત્યારપછીની 10 લાઇનો
   અને છેલ્લી 3 લાઇનો રાખે છે, અને તેમની વચ્ચેની લાઇનોના સ્થાને
   `… [N frames elided] …` માર્કર મૂકે છે. માર્કર ફક્ત ત્યારે દેખાય છે જ્યારે પ્રથમ
   લાઇન પછી 13 કરતાં વધુ લાઇનો હોય, તેથી 14 અથવા ઓછી લાઇનો ધરાવતું ભૂલ આઉટપુટ ટૂંકું
   થતું નથી (12 અથવા 13 લાઇનોમાં છેલ્લી 3 લાઇનો પહેલેથી જ રાખેલી લાઇનોનું પુનરાવર્તન
   કરે છે).

કોઈ વ્યૂહરચના મેળ ખાય પછી, ભલે તે કશું બચાવતી ન હોય, પછીની વ્યૂહરચનાઓ અજમાવવામાં
આવતી નથી. જ્યારે મેળ ખાતી વ્યૂહરચના કોઈ અંદાજિત ટોકન બચાવતી નથી (લંબાઈ ÷ 4, ઉપરની
પૂર્ણ સંખ્યા સુધી રાઉન્ડ કરેલું) — ઉદાહરણ તરીકે, 25 અથવા ઓછી લાઇનો ધરાવતી કોડ જેવી
ફાઇલ, અથવા 2,000 કરતાં વધુ અક્ષરો ધરાવતો પણ 7 અથવા ઓછી આઇટમ ધરાવતો JSON એરે —
ત્યારે એગ્રેસિવ એન્જિન મૂળ ટૂલ પરિણામ જાળવી રાખે છે: બંને કૉલર
(`compressAggressive()` અને `compressAnthropicToolResultBlock()`) જ્યારે `saved` 0
અથવા તેનાથી ઓછું હોય ત્યારે મૂળ પરિણામ રાખે છે, જ્યારે `compressToolResult()` પોતે
હજુ પણ તે વ્યૂહરચનાનું આઉટપુટ પરત કરે છે. ટૂલ-પરિણામનું પગલું અંતિમ નિર્ણય નથી:
એન્જિનનું ફૉલબૅક સારાંશકાર હજી પણ 8,192 અક્ષરોથી લાંબા `tool` અથવા `function`
સંદેશને ટૂંકો કરી શકે છે (`maxTokensPerMessage`, 2,048, ગુણ્યા 4).

#### ક્યારે ઉપયોગ કરવો

ટૂલ પરિણામનું સંકોચન એગ્રેસિવ એન્જિનનું પગલું 1 છે (`compressAggressive()` જે
`open-sse/services/compression/aggressive.ts`માં છે), તેથી તે Aggressive મોડમાં અને
સ્ટૅક્ડ પાઇપલાઇનના `aggressive` પગલામાં ચાલે છે. તે OpenAI-આકારના `tool` અને
`function` સંદેશાઓ તથા Anthropic `tool_result` બ્લૉક્સની અંદરના ટેક્સ્ટને સંકોચે છે.
દરેક વ્યૂહરચનાનો `aggressive.toolStrategies` હેઠળ પોતાનો સ્વિચ છે અને બધા ડિફૉલ્ટ રૂપે
ચાલુ હોય છે. ડૅશબોર્ડમાં, સંકોચન ચાલુ હોય અને ડિફૉલ્ટ મોડ Aggressive હોય ત્યારે
સ્વિચો Caveman પેજના **Advanced** દૃશ્યમાં હોય છે.

### સ્ટૅક્ડ પાઇપલાઇન

સ્ટૅક્ડ મોડ **અનેક એન્જિનને ક્રમમાં** ચલાવે છે — સામાન્ય રીતે પહેલાં RTK (ટૂલ
આઉટપુટમાં 60-90% બચત), ત્યારબાદ બાકી રહેલા ટેક્સ્ટ પર Caveman (~46% ઇનપુટ બચત).
સંયુક્ત રીતે, તે **78-95% પાત્ર શ્રેણી** છે (ઉપરનું Upstream Savings Math જુઓ):
`1 - (1 - 0.60..0.90) × (1 - 0.46)`ની સરેરાશ ≈89% થાય છે.

#### તે કેવી રીતે કાર્ય કરે છે

```
ઇનપુટ (1000 ટોકન)
  → RTK (કમાન્ડ-અવેર ફિલ્ટર) → 200 ટોકન
    → Caveman (અનાવશ્યક સામગ્રી દૂર કરવી) → 108 ટોકન
  → આઉટપુટ (108 ટોકન, ~89% બચત)
```

#### ક્યારે ઉપયોગ કરવો

સ્ટૅક્ડ મોડનો ઉપયોગ આ માટે કરો:

- ટૂલ-કેન્દ્રિત વર્કફ્લો (એજન્ટિક કોડિંગ, સંશોધન)
- ખર્ચ-સંવેદનશીલ બૅચ પ્રોસેસિંગ
- જ્યારે તમને મહત્તમ ટોકન બચતની જરૂર હોય

સ્ટૅક્ડ પાઇપલાઇનો વૈશ્વિક `stackedPipeline` સંકોચન સેટિંગ મારફતે અથવા રાઉટિંગ કોમ્બોને
સોંપાયેલા નામિત સંકોચન કોમ્બો મારફતે ગોઠવવામાં આવે છે (ઉપરનું Per-Combo Override
જુઓ) — auto-combo `modePack` મારફતે નહીં (એ ફીલ્ડ ફક્ત auto-combo મોડલ પસંદગીનાં
વજનો ફરી ગોઠવે છે અને `stacked` માન્ય પૅક નામ નથી).

## કોમ્પ્રેશન કોમ્બો ઓવરરાઇડ્સ

વિવિધ ઉપયોગના કિસ્સાઓ માટે વર્તનને વધુ ચોકસાઈથી ગોઠવવા તમે વૈશ્વિક કોમ્પ્રેશન મોડને **દરેક કોમ્બો માટે** ઓવરરાઇડ કરી શકો છો:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

આ નીચેના માટે ઉપયોગી છે:

- **કોડિંગ કોમ્બો**: લાંબા સત્રો માટે `aggressive` મોડનો ઉપયોગ કરો
- **ઝડપી પ્રશ્નોત્તરી કોમ્બો**: ઝડપી પ્રતિસાદો માટે `lite` મોડનો ઉપયોગ કરો
- **ટૂલ-હેવી કોમ્બો**: મહત્તમ બચત માટે `stacked` મોડનો ઉપયોગ કરો
- **પ્રોડક્શન કોમ્બો**: કૅશિંગ પ્રદાતાઓ માટે ઓવરરાઇડ બંધ રાખો — હંમેશાં સક્રિય
  કૅશ-અવેર સમાયોજન `aggressive`/`ultra`ને આપમેળે `standard`માં ડાઉનગ્રેડ કરે છે
  (પસંદ કરી શકાય એવો કોઈ `cache-aware` મોડ નથી)
