## વિહંગાવલોકન

OmniRoute એક મોડ્યુલર પ્રોમ્પ્ટ કોમ્પ્રેસન પાઇપલાઇન લાગુ કરે છે જે વિનંતીઓ અપસ્ટ્રીમ પ્રોવાઇડર્સ સુધી પહોંચે તે પહેલાં **પ્રોએક્ટિવલી (proactively)** ચાલે છે. આનો અર્થ એ છે કે તમારી ટોકન બચત પારદર્શક રીતે થાય છે — તમારા વર્કફ્લોમાં કોઈ ફેરફારની જરૂર નથી.

```
ક્લાયન્ટ વિનંતી
  → કોમ્પ્રેસન સ્ટ્રેટેજી સિલેક્ટર
    → કોમ્બો ઓવરરાઇડ? → કોમ્બો સેટિંગનો ઉપયોગ કરો
    → ઓટો-ટ્રિગર થ્રેશોલ્ડ? → ઓટો મોડનો ઉપયોગ કરો
    → ડિફોલ્ટ મોડ? → ગ્લોબલ સેટિંગનો ઉપયોગ કરો
    → બંધ? → કોમ્પ્રેસન છોડી દો
  → પસંદ કરેલ કોમ્પ્રેસન મોડ
    → Off: કોઈ કોમ્પ્રેસન નથી
    → Lite: સુરક્ષિત વ્હાઇટસ્પેસ/ફોર્મેટિંગ ક્લીનઅપ (~15%)
    → Standard: કેવમેન-સ્પીક (Caveman-speak) ફિલર રિમૂવલ (~30%)
    → Aggressive: હિસ્ટ્રી એજિંગ + સમરાઇઝેશન (~50%)
    → Ultra: હ્યુરિસ્ટિક પ્રુનિંગ + કોડ-બ્લોક થિનિંગ (~75%)
    → RTK: કમાન્ડ-અવેર ટર્મિનલ/ટૂલ-આઉટપુટ ફિલ્ટરિંગ (60-90% અપસ્ટ્રીમ રેન્જ)
    → Stacked: ઓર્ડર્ડ મલ્ટી-એન્જિન પાઇપલાઇન, સામાન્ય રીતે RTK પછી Caveman (78-95% પાત્ર રેન્જ)
  → કોમ્પ્રેસ્ડ વિનંતી → પ્રોવાઇડર
```

## કોમ્પ્રેસન મોડ્સ

### Off

કોઈ કોમ્પ્રેસન લાગુ કરવામાં આવતું નથી. બધા મેસેજ બદલાયા વગર પસાર થાય છે.

### Lite Mode (~15% બચત, <1ms લેટન્સી)

સૌથી સુરક્ષિત મોડ — શૂન્ય સેમેન્ટિક ફેરફાર, ફક્ત ફોર્મેટિંગ ક્લીનઅપ:

| ટેકનિક                   | વર્ણન                                       |
| ------------------------ | ------------------------------------------- |
| `collapseWhitespace`     | સતત ખાલી લાઇન અને ટ્રેલિંગ સ્પેસને મર્જ કરો |
| `dedupSystemPrompt`      | ડુપ્લિકેટ સિસ્ટમ મેસેજ દૂર કરો              |
| `compressToolResults`    | વર્બોઝ ટૂલ/ફંક્શન આઉટપુટને કોમ્પ્રેસ કરો    |
| `removeRedundantContent` | પુનરાવર્તિત સૂચનાઓ દૂર કરો                  |
| `replaceImageUrls`       | base64 ઇમેજ ડેટા URIs ટૂંકા કરો             |

**માટે શ્રેષ્ઠ:** હંમેશા ચાલુ વપરાશ, સેફ્ટી-ક્રિટિકલ વર્કફ્લો.

### Standard Mode (~30% બચત)

[Caveman](https://github.com/JuliusBrussee/caveman) દ્વારા પ્રેરિત — અર્થ જાળવી રાખીને ફિલર શબ્દો અને વર્બોઝ શબ્દસમૂહો દૂર કરે છે:

- ફિલર શબ્દો દૂર કરે છે ("please", "I think", "basically", "actually")
- વર્બોઝ શબ્દસમૂહોને ટૂંકાવે છે ("in order to" → "to", "as a result of" → "because")
- વિનમ્ર હેજિંગ (polite hedging) દૂર કરે છે ("Would you mind...", "If you could possibly...")
- કોડિંગ પ્રોમ્પ્ટ્સ માટે ટ્યુન કરેલા 30+ regex નિયમો

**માટે શ્રેષ્ઠ:** દૈનિક કોડિંગ વર્કફ્લો, ખર્ચ પ્રત્યે સભાન ટીમો.

### Aggressive Mode (~50% બચત)

લાંબા સત્રો માટે સ્માર્ટ હિસ્ટ્રી મેનેજમેન્ટ:

- **મેસેજ એજિંગ (Message Aging)** — જૂના મેસેજ ક્રમશઃ કોમ્પ્રેસ થાય છે
- **ટૂલ રિઝલ્ટ સમરાઇઝેશન (Tool Result Summarization)** — લાંબા ટૂલ આઉટપુટને સારાંશ સાથે બદલવામાં આવે છે
- **સ્ટ્રક્ચરલ ઇન્ટિગ્રિટી ગાર્ડ્સ (Structural Integrity Guards)** — ખાતરી કરે છે કે `tool_use` + `tool_result` જોડી સુસંગત રહે
- **કોન્ટેક્સ્ટ વિન્ડો અવેરનેસ (Context Window Awareness)** — મોડેલ દીઠ ટોકન મર્યાદાઓનું પાલન કરે છે

**માટે શ્રેષ્ઠ:** વિસ્તૃત ડીબગીંગ સત્રો, મોટા કોડબેઝ.

### Ultra Mode (~75% બચત)

ટોકન-ક્રિટિકલ પરિસ્થિતિઓ માટે મહત્તમ કોમ્પ્રેસન:

- **હ્યુરિસ્ટિક પ્રુનિંગ (Heuristic Pruning)** — સુસંગતતા થ્રેશોલ્ડથી નીચેના મેસેજ દૂર કરે છે
- **કોડ બ્લોક થિનિંગ (Code Block Thinning)** — પુનરાવર્તિત કોડ ઉદાહરણોને કોમ્પ્રેસ કરે છે
- **બાઈનરી સર્ચ ટ્રંકેશન (Binary Search Truncation)** — કોન્ટેક્સ્ટ વિન્ડો માટે શ્રેષ્ઠ કટ પોઈન્ટ શોધે છે
- બધા Aggressive મોડ ફીચર્સ શામેલ છે

**માટે શ્રેષ્ઠ:** જ્યારે તમે વારંવાર કોન્ટેક્સ્ટ મર્યાદા સુધી પહોંચતા હોવ.

### RTK Mode (60-90% અપસ્ટ્રીમ રેન્જ)

RTK મોડ કોડિંગ-એજન્ટ સત્રોમાં દેખાતા વર્બોઝ ટૂલ આઉટપુટ માટે ઓપ્ટિમાઇઝ કરેલ છે:

- `git status`, `git diff`, `git log`, ટેસ્ટ રનર્સ, TypeScript/Vite/Webpack બિલ્ડ્સ, ESLint/Biome/Prettier, npm audit/installs, Docker લોગ્સ, ઇન્ફ્રા આઉટપુટ અને જેનરિક શેલ આઉટપુટ જેવા કમાન્ડ/આઉટપુટ ક્લાસને શોધે છે
- `open-sse/services/compression/engines/rtk/filters/` માંથી JSON ફિલ્ટર પેક્સ લાગુ કરે છે
- પ્રોજેક્ટ અથવા ગ્લોબલ `filters.toml` ફાઇલોમાંથી RTK TOML schema v1 ફિલ્ટર્સ ઇમ્પોર્ટ કરે છે, જેમાં ઇનલાઇન-ટેસ્ટ વેલિડેશન અને પ્રોજેક્ટ ફાઇલો માટે ટ્રસ્ટ-ગેટિંગ (trust-gating) છે
- ઇનલાઇન વેરિફાય સેમ્પલ્સ સાથે 49 બિલ્ટ-ઇન ફિલ્ટર્સ મોકલે છે
- ANSI કંટ્રોલ સિક્વન્સ, પ્રોગ્રેસ બાર, પુનરાવર્તિત લાઇન અને બિન-કાર્યક્ષમ અવાજ (noise) દૂર કરે છે
- નિષ્ફળતાઓ, ભૂલો, ચેતવણીઓ, બદલાયેલી ફાઇલો, સારાંશ અને લાંબા આઉટપુટના અંતિમ ભાગને સાચવે છે
- ટ્રસ્ટ-ગેટ પ્રોજેક્ટ ફિલ્ટર્સ, ગ્લોબલ ફિલ્ટર્સ અને વૈકલ્પિક રિડેક્ટેડ રો-આઉટપુટ રિકવરીને સપોર્ટ કરે છે

**માટે શ્રેષ્ઠ:** શેલ, બિલ્ડ, ટેસ્ટ, git, grep અને ફાઇલ-આઉટપુટ ટ્રાન્સક્રિપ્ટ્સ સાથેના એજન્ટ સત્રો.

### Stacked Mode (78-95% પાત્ર રેન્જ)

Stacked મોડ નિર્ધારિત ક્રમમાં બહુવિધ કોમ્પ્રેસન એન્જિન ચલાવે છે. ડિફોલ્ટ પાઇપલાઇન છે:

```txt
RTK -> Caveman
```

તે ક્રમ પહેલા ટર્મિનલ/ટૂલ આઉટપુટને કોમ્પેક્ટ રાખે છે, પછી બાકીના નેચરલ-લેંગ્વેજ પ્રોમ્પ્ટ પર Caveman સેમેન્ટિક કન્ડેન્સેશન લાગુ કરે છે. Stacked પાઇપલાઇન્સને ગ્લોબલી અથવા રાઉટિંગ કોમ્બોઝને સોંપેલ કોમ્પ્રેસન કોમ્બોઝ દ્વારા કન્ફિગર કરી શકાય છે.

**માટે શ્રેષ્ઠ:** મોટા ટૂલ લોગ્સ વત્તા માનવ સૂચનાઓ અથવા આસિસ્ટન્ટ સારાંશ સાથેનો મિશ્ર કોન્ટેક્સ્ટ.

## અપસ્ટ્રીમ બચત ગણિત

ઓમ્નિરુટ બે સ્ત્રોતોમાંથી કમ્પ્રેશન બચતનું દસ્તાવેજીકરણ કરે છે: અપસ્ટ્રીમ પ્રોજેક્ટ બેન્ચમાર્ક્સ અને ઓમ્નિરુટની પોતાની એન્જિન કમ્પોઝિશન.

| સ્ત્રોત | અહીં ઉપયોગમાં લેવાયેલ અપસ્ટ્રીમ README નંબર                                                                   |
| ------- | ------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` ઓછા આઉટપુટ ટોકન્સ, `65%` બેન્ચમાર્ક સરેરાશ આઉટપુટ બચત, `22-87%` શ્રેણી, અને `~46%` ઇનપુટ કમ્પ્રેશન ટૂલ |
| RTK     | `60-90%` કમાન્ડ-આઉટપુટ બચત; નમૂના સત્ર `~118,000 -> ~23,900` ટોકન્સ, અથવા `79.7%` બચત (`~80%`)                |

ઓવરલેપિંગ ટૂલ/કોન્ટેક્સ્ટ પેલોડ્સ માટે, ડિફોલ્ટ ઓમ્નિરુટ કોમ્બો એન્જિનને સ્ટેક કરે છે:

```txt
RTK -> Caveman
```

સંયુક્ત બચત ગુણાકાર છે, સરવાળાત્મક નથી:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

તે `78-95%` નંબર ત્યારે લાગુ પડે છે જ્યારે RTK અને Caveman બંને સમાન ઇનપુટ/કોન્ટેક્સ્ટ પેલોડ ઘટાડી શકે. કેવમેન પ્રતિભાવ આઉટપુટ મોડ અલગ છે: જ્યારે સક્ષમ હોય, ત્યારે કેવમેનની પોતાની આઉટપુટ બચતનો ઉપયોગ કરો (`65%` સરેરાશ, `~75%` હેડલાઇન, `22-87%` શ્રેણી). કુલ બિલિંગ બચત તમારા પ્રોમ્પ્ટ/આઉટપુટ મિશ્રણ પર આધાર રાખે છે.

### "પાત્ર" નો ખરેખર શું અર્થ થાય છે

15-95% હેડલાઇન શ્રેણી વાસ્તવિક છે, પરંતુ તે ફક્ત **રીડન્ડન્ટ અથવા વર્બોઝ** કન્ટેન્ટને લાગુ પડે છે — પુનરાવર્તિત ભૂલ રેખાઓ, એક બિલ્ડ લોગ જે સમાન ચેતવણીને સ્પામ કરે છે, એક ઓવરસાઇઝ્ડ `grep`/ફાઇલ-રીડ ડમ્પ. તેનો અર્થ એ **નથી** કે દરેક વિનંતી એટલી બચત કરે છે.

પ્રાયોગિક રીતે ચકાસાયેલ (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300 સમાન ભૂલ રેખાઓ ધરાવતા એન્થ્રોપિક-આકારના `tool_result` બ્લોક સામે `stacked` (RTK + Caveman) રન દ્વારા **95.93% ટોકન બચત / 96.26% કેરેક્ટર બચત** ઉત્પન્ન થઈ — જે જાહેરાત કરેલી શ્રેણીમાં બરાબર છે. પરંતુ સામાન્ય, બિન-રીડન્ડન્ટ ટૂલ આઉટપુટ (એક સ્વચ્છ `grep` મેચ સૂચિ, એક ટૂંકી ફાઇલ રીડ, સામાન્ય વાતચીતનો ટેક્સ્ટ) સામે સમાન પાઇપલાઇન રન દ્વારા યોગ્ય રીતે **લગભગ શૂન્ય બચત** ઉત્પન્ન થાય છે, કારણ કે દૂર કરવા માટે કંઈ પુનરાવર્તિત નથી અને `validateCompression()` (`validation.ts`) એવા રીરાઇટને મોકલવાનો ઇનકાર કરે છે જે કોડ બ્લોક્સ, URL, હેડિંગ્સ, વર્ઝન અથવા ALL-CAPS કોન્સ્ટન્ટ આઇડેન્ટિફાયર્સને છોડી દેશે અથવા બદલશે.

આ અપેક્ષિત, સલામત વર્તન છે, બગ નથી: એક કોડિંગ સત્ર જે મોટે ભાગે સ્વચ્છ ફાઇલો વાંચે/ગ્રેપ કરે છે તે કમ્પ્રેશન સંપૂર્ણપણે સક્ષમ હોવા છતાં પણ સાધારણ કુલ બચત જોશે, જ્યારે એક સત્ર જે નિષ્ફળ લૂપ અથવા ચેટ્ટી લિન્ટરને હિટ કરે છે તે તે ટ્રાફિક પર સંપૂર્ણ 78-95% શ્રેણી જોશે. એક સત્રની ઓછી કુલ બચત ટકાવારીનો ઉપયોગ કમ્પ્રેશન ખોટી રીતે ગોઠવેલ છે તેના પુરાવા તરીકે કરશો નહીં — પહેલા તપાસો કે અંતર્ગત ટૂલ આઉટપુટ ખરેખર રીડન્ડન્ટ હતું કે નહીં.

## ગોઠવણી

### ડેશબોર્ડ

`Dashboard → Context & Cache` પર નેવિગેટ કરો:

- **Caveman** — મોડ પસંદગી, ભાષા પેક, પૂર્વાવલોકન અને વૈશ્વિક ડિફોલ્ટ્સ
- **RTK** — કમાન્ડ-ફિલ્ટર પૂર્વાવલોકન, RTK સલામતી સેટિંગ્સ અને ફિલ્ટર કેટલોગ
- **Compression Combos** — રૂટીંગ કોમ્બોઝને સોંપેલ નામવાળી એન્જિન પાઇપલાઇન્સ
- **Auto-Trigger Threshold** — જ્યારે ટોકન ગણતરી થ્રેશોલ્ડ કરતાં વધી જાય ત્યારે આપમેળે કમ્પ્રેશન લાગુ કરો

### પ્રતિ-કોમ્બો ઓવરરાઇડ

`Dashboard → Context & Cache → Compression Combos` માં, રૂટીંગ કોમ્બોને કમ્પ્રેશન કોમ્બો સોંપો:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

આ તમને મફત/કોડિંગ પ્રદાતાઓ પર સ્ટેક્ડ કમ્પ્રેશનનો ઉપયોગ કરવાની મંજૂરી આપે છે જ્યારે પેઇડ સબ્સ્ક્રિપ્શન્સ પર લાઇટ મોડ જાળવી રાખે છે.

આ "પ્રતિ-કોમ્બો ઓવરરાઇડ" સોંપણી **રૂટીંગ-કોમ્બો કમ્પ્રેશન મોડ** ઓવરરાઇડ (Default/Off/Lite/Standard/Aggressive/Ultra) થી અલગ નિયંત્રણ છે — તે ઓવરરાઇડ નામવાળી કમ્પ્રેશન-કોમ્બો પાઇપલાઇન પસંદ કરતું નથી; તે ફક્ત `resolveCompressionPlan` દ્વારા સલાહ લેવાયેલ `compressionMode` ફીલ્ડ સેટ કરે છે. તે કોમ્બો કાર્ડ (`Dashboard → Combos`) પર અથવા, #6760 થી, `Dashboard → Context & Cache → Compression Combos` પર "Assign to routing" સૂચિમાં પ્રતિ રૂટીંગ કોમ્બો, ઉપર દસ્તાવેજીકૃત પાઇપલાઇન-સોંપણી ચેકબોક્સની બરાબર બાજુમાં સેટ કરી શકાય છે. બંને સપાટીઓ સમાન `PUT /api/combos/{id}` એન્ડપોઇન્ટ દ્વારા જાળવી રાખવામાં આવે છે.

### પ્રતિ-વિનંતી ઓવરરાઇડ

એક જ વિનંતી માટે કમ્પ્રેશન પ્લાનને ઓવરરાઇડ કરવા માટે `x-omniroute-compression` વિનંતી હેડર મોકલો. તેની સર્વોચ્ચ અગ્રતા છે — તે રૂટીંગ-કોમ્બો ઓવરરાઇડ, સક્રિય પ્રોફાઇલ, ઓટો-ટ્રિગર અને પેનલ ડિફોલ્ટને હરાવે છે. અજાણ્યા મૂલ્યોને અવગણવામાં આવે છે (વિનંતી ક્યારેય નકારવામાં આવતી નથી) અને વૈશ્વિક માસ્ટર સ્વીચ હજુ પણ બધું નિયંત્રિત કરે છે: જ્યારે વૈશ્વિક સ્તરે કમ્પ્રેશન બંધ હોય, ત્યારે હેડર તેને ચાલુ કરી શકતું નથી. મૂલ્યો:

| મૂલ્ય         | અસર                                                                                             |
| ------------- | ----------------------------------------------------------------------------------------------- |
| `off`         | આ વિનંતી માટે કોઈ કમ્પ્રેશન નથી.                                                                |
| `default`     | પેનલ-વ્યુત્પન્ન ડિફોલ્ટ પ્રોફાઇલ (સક્રિય પ્રોફાઇલને અવગણે છે). લોસી એન્જિન બંધ રાખવામાં આવે છે. |
| `safe`        | હેડર છોડી દેવા જેવું જ: માત્ર ડુપ્લિકેશન દૂર કરવું અને વ્હાઇટસ્પેસ ફોલ્ડિંગ.                    |
| `allow-lossy` | આ વિનંતીનો ઓપરેટર પ્લાન રાખો, જેમાં સારાંશ, સુસંગતતા ફિલ્ટર્સ અને સ્ટાઇલ રીરાઇટ્સ શામેલ છે.     |
| `engine:<id>` | સક્ષમ હોય ત્યારે એક જ એન્જિન, દા.ત. `engine:rtk`. આ તે એન્જિન માટે પ્રતિ-વિનંતી ઓપ્ટ-ઇન છે.     |
| `<combo>`     | નામ દ્વારા (કેસ-સંવેદનશીલ નહીં) પ્રથમ, પછી ID દ્વારા મેળ ખાતો નામવાળો કોમ્બો.                   |

`allow-lossy`, `engine:<id>`, અથવા નામવાળા કોમ્બો વિના, લોસી એન્જિન લાગુ પડતા નથી. જ્યારે કમ્પ્રેશન ચાલુ હોય ત્યારે વિનંતીને સેશન ડુપ્લિકેશન દૂર કરવું અને વ્હાઇટસ્પેસ ફોલ્ડિંગ હજુ પણ મળે છે.

લાગુ કરાયેલ પ્લાન `X-OmniRoute-Compression: <mode>; source=<source>` રિસ્પોન્સ હેડરમાં પાછો ઇકો કરવામાં આવે છે, જ્યાં `<source>` એ `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, અથવા `off` માંથી એક છે.

### API

```bash
# કમ્પ્રેશન સેટિંગ્સ મેળવો
curl http://localhost:20128/api/settings/compression

# કમ્પ્રેશન સેટિંગ્સ અપડેટ કરો

  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# ચોક્કસ RTK/સ્ટેક્ડ પેલોડનું પૂર્વાવલોકન કરો

  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# RTK ફિલ્ટર પેક સૂચિબદ્ધ કરો
curl http://localhost:20128/api/context/rtk/filters

# વૈકલ્પિક કમાન્ડ મેટાડેટા સાથે RTKનું સીધું પરીક્ષણ કરો

  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

## શું સુરક્ષિત થાય છે

કમ્પ્રેશન એન્જિન **હંમેશા જાળવી રાખે છે:**

- ✅ કોડ બ્લોક્સ (ફેન્સ્ડ અને ઇનલાઇન)
- ✅ URLs અને ફાઇલ પાથ
- ✅ JSON સ્ટ્રક્ચર્સ અને સ્ટ્રક્ચર્ડ ડેટા
- ✅ ઓળખકર્તાઓ અને સુરક્ષિત તકનીકી ટોકન્સ
- ✅ ગાણિતિક અભિવ્યક્તિઓ
- ✅ ટૂલ/ફંક્શન કૉલ વ્યાખ્યાઓ
- ✅ સિસ્ટમ પ્રોમ્પ્ટ્સ (લાઇટ મોડમાં)

## સ્વીકૃતિઓ

સ્ટાન્ડર્ડ મોડ કમ્પ્રેશન નિયમો **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ 51K+) દ્વારા **[Caveman](https://github.com/JuliusBrussee/caveman)** દ્વારા પ્રેરિત છે — વાયરલ "શા માટે ઘણા ટોકનનો ઉપયોગ કરવો જ્યારે થોડા ટોકન યુક્તિ કરે" પ્રોજેક્ટ. કેવમેન `~75%` ઓછા આઉટપુટ ટોકન્સ, `65%` બેન્ચમાર્ક સરેરાશ આઉટપુટ બચત, `22-87%` આઉટપુટ રેન્જ અને `~46%` ઇનપુટ-કમ્પ્રેશન ટૂલની જાણ કરે છે.

RTK મોડ **[RTK AI](https://github.com/rtk-ai)** દ્વારા **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** દ્વારા પ્રેરિત છે — ટર્મિનલ, બિલ્ડ, ટેસ્ટ, ગિટ અને ટૂલ-આઉટપુટ ફિલ્ટરિંગ માટે ઉચ્ચ-પ્રદર્શન કમાન્ડ-આઉટપુટ કમ્પ્રેશન પ્રોજેક્ટ. RTK `60-90%` બચતની જાણ કરે છે, તેના README નમૂના સત્રમાં `~80%` બચત દર્શાવે છે.

## અદ્યતન કમ્પ્રેશન સિસ્ટમ્સ

7 સ્ટાન્ડર્ડ મોડ્સ ઉપરાંત, ઓમ્નીરૂટમાં ઘણી અદ્યતન કમ્પ્રેશન સિસ્ટમ્સ શામેલ છે જે સંદર્ભના આધારે આપમેળે કાર્ય કરે છે.

### કેશ-અવેર કમ્પ્રેશન

કેટલાક પ્રદાતાઓ (જેમ કે પ્રોમ્પ્ટ કેશીંગ સાથે એન્થ્રોપિક) **પ્રોમ્પ્ટ કેશીંગ** ને સપોર્ટ કરે છે, જે તેમને ખર્ચ અને લેટન્સી ઘટાડવા માટે પ્રોમ્પ્ટના ભાગોને કેશ કરવાની મંજૂરી આપે છે. જ્યારે કેશીંગ સક્ષમ હોય, ત્યારે આક્રમક કમ્પ્રેશન ખરેખર પ્રદર્શનને **નુકસાન** પહોંચાડી શકે છે કારણ કે તે કેશ કરેલા ટોકન્સને બદલે છે, કેશને અમાન્ય કરે છે.

`cachingAware.ts` મોડ્યુલ **કેશીંગ સંદર્ભને શોધીને** અને તે મુજબ **કમ્પ્રેશન વ્યૂહરચનાને સમાયોજિત કરીને** આ સમસ્યાનું નિરાકરણ લાવે છે.

#### તે કેવી રીતે કાર્ય કરે છે

1. **કેશીંગ સંદર્ભ શોધો** — `cache_control` માર્કર્સ માટે વિનંતી બોડીને સ્કેન કરે છે
2. **કેશીંગ પ્રદાતાઓને ઓળખો** — લક્ષ્ય પ્રદાતા કેશીંગને સપોર્ટ કરે છે કે કેમ તે તપાસે છે
3. **વ્યૂહરચના સમાયોજિત કરો** — કેશીંગ પ્રદાતાઓ માટે `aggressive`/`ultra` ને `standard` માં ડાઉનગ્રેડ કરે છે
4. **સિસ્ટમ પ્રોમ્પ્ટ છોડો** — સિસ્ટમ પ્રોમ્પ્ટ્સ સામાન્ય રીતે કેશ કરવામાં આવે છે, તેથી તેમને કમ્પ્રેસ કરશો નહીં
5. **નિર્ધારિત રૂપાંતરણોનો ઉપયોગ કરો** — ફક્ત સુસંગત આઉટપુટ ઉત્પન્ન કરતા રૂપાંતરણોનો ઉપયોગ કરો

#### કોડ ઉદાહરણ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← કેશ માર્કર
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ક્યારે ઉપયોગ કરવો

કેશ-અવેર કમ્પ્રેશન **હંમેશા ચાલુ** હોય છે — કોઈ ગોઠવણીની જરૂર નથી. તે ફક્ત ત્યારે જ શરૂ થાય છે જ્યારે:

- વિનંતીમાં `cache_control` માર્કર્સ હોય
- લક્ષ્ય પ્રદાતા પ્રોમ્પ્ટ કેશીંગને સપોર્ટ કરે છે (એન્થ્રોપિક, OpenAI, વગેરે)

### પ્રગતિશીલ વૃદ્ધત્વ

લાંબી વાર્તાલાપ ઘણા સંદેશાના વળાંક એકઠા કરે છે, પરંતુ જૂના વળાંક ઓછા સુસંગત બને છે. `progressiveAging.ts` મોડ્યુલ **વળાંકના અંતર દ્વારા સંદેશાઓને અધોગતિ કરે છે**:

- **તાજેતરના વળાંક (0-3)**: શબ્દશઃ રાખવામાં આવે છે (સંપૂર્ણ વિગત)
- **મધ્યમ વળાંક (4-8)**: લાઇટ કમ્પ્રેશન (વ્હાઇટસ્પેસ, ફોર્મેટિંગ ક્લીનઅપ)
- **જૂના વળાંક (9+)**: કેવમેન કમ્પ્રેશન (ફિલર દૂર કરવું, સારાંશ)
- **ખૂબ જૂના વળાંક (20+)**: ભારે સારાંશ અથવા છોડી દેવામાં આવે છે

#### કોડ ઉદાહરણ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 વધુ વળાંક ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // પ્રથમ 3 વળાંક: શબ્દશઃ
  light: 8, // વળાંક 4-8: લાઇટ કમ્પ્રેશન
  moderate: 20, // વળાંક 9-20: કેવમેન કમ્પ્રેશન
  // વળાંક 21+: ભારે સારાંશ
});

// saved = બચાવેલા ટોકન્સની સંખ્યા
```

#### ક્યારે ઉપયોગ કરવો

પ્રગતિશીલ વૃદ્ધત્વ `aggressive` અને `ultra` મોડ્સ માટે **હંમેશા ચાલુ** હોય છે. તે ખાસ કરીને આ માટે અસરકારક છે:

- લાંબા સમય સુધી ચાલતા કોડિંગ સત્રો
- બહુ-દિવસીય વાર્તાલાપ
- ઘણા ટૂલ કૉલ્સ સાથે એજન્ટિક વર્કફ્લો

### કેવમેન આઉટપુટ મોડ

`outputMode.ts` મોડ્યુલ મોડેલને સંકુચિત, સંક્ષિપ્ત આઉટપુટ ("કેવમેન" શૈલી) ઉત્પન્ન કરવા માટે **સિસ્ટમ પ્રોમ્પ્ટ સૂચનાઓ** દાખલ કરે છે.

#### તે કેવી રીતે કાર્ય કરે છે

ઇનપુટને સંકુચિત કરવાને બદલે, આ મોડ સિસ્ટમ પ્રોમ્પ્ટ ઉમેરે છે જેમ કે:

> "ઓછામાં ઓછા શબ્દોમાં જવાબ આપો. ઔપચારિકતાઓ છોડી દો. ટૂંકા વાક્યોનો ઉપયોગ કરો."

આ ખાસ કરીને આ માટે સારી રીતે કાર્ય કરે છે:

- કોડ જનરેશન (વધુ સંક્ષિપ્ત આઉટપુટ = ઓછા ટોકન્સ)
- ઝડપી પ્રશ્ન-જવાબ (વિગતવાર સમજૂતીની જરૂર નથી)
- બેચ પ્રોસેસિંગ (થ્રુપુટ મહત્તમ કરવા)

#### ક્યારે ઉપયોગ કરવો

કેવમેન આઉટપુટ મોડ **પસંદગીનો વિકલ્પ** છે — તેને કોમ્બો કન્ફિગ દ્વારા સેટ કરો:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "outputMode": "caveman"
    }
  }
}
```

| સંક્ષિપ્ત CJK (文言)       | `terse-cjk`   | શાસ્ત્રીય-ચાઇનીઝ અતિ-સંક્ષિપ્ત શૈલી.                                                                                                                                                                                 | zh (લોકેલ-ગેટ્ડ: જ્યારે રિઝોલ્વ્ડ ભાષા `zh` હોય ત્યારે જ ઓફર કરવામાં આવે છે) |

દરેક શૈલી ત્રણ તીવ્રતાના સ્તરો — `lite`, `full`, `ultra` — સાથે આવે છે અને દરેક સ્તર વહેંચાયેલ સીમાઓ કલમ સાથે સમાપ્ત થાય છે, જે કોડ બ્લોક્સ, ફાઇલ પાથ, કમાન્ડ્સ, ભૂલ સ્ટ્રિંગ્સ, URLs અને ઓળખકર્તાઓને શબ્દશઃ રાખે છે.

#### ઇન્જેક્શન કેવી રીતે કાર્ય કરે છે

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) કેટલોગ સામે પસંદગીનું નિરાકરણ કરે છે (અજાણી ID અને લોકેલ-અસંગત શૈલીઓ છોડી દેવામાં આવે છે, ક્યારેય ભૂલ નથી), પસંદ કરેલી સૂચનાઓને કેટલોગ ક્રમમાં જોડે છે, સીમાઓ કલમને **એકવાર** ઉમેરે છે, અને પરિણામને એક જ આઇડેમ્પોટેન્સી માર્કર (`[OmniRoute Output Styles]`) પાછળ સિસ્ટમ પ્રોમ્પ્ટમાં આગળ લોડ કરે છે — ફરીથી લાગુ કરવું એ નો-ઓપ છે. જ્યારે શોધાયેલ વિનંતી ભાષામાં અનુવાદ હોય, ત્યારે અંગ્રેજીને બદલે સ્થાનિક સૂચના દાખલ કરવામાં આવે છે.

#### કેવી રીતે સક્ષમ કરવું

ડેશબોર્ડમાં: **Context → Settings → Compression** — દરેક શૈલી માટે એક પંક્તિ જેમાં ચાલુ/બંધ ટૉગલ અને લેવલ સિલેક્ટર હોય છે. પ્રોગ્રામેટિકલી, કમ્પ્રેશન કન્ફિગ પસંદગીને આ રીતે જાળવી રાખે છે:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

પાછળની સુસંગતતા: જૂની `outputMode: "caveman"` કોમ્બો સેટિંગ હજુ પણ કાર્ય કરે છે અને `terse-prose` પર મેપ થાય છે, જે દરેક જૂની ભાષામાં જૂના ઇન્જેક્શન જેવું જ બાઇટ-આઇડેન્ટિકલ છે.

ભાષા પસંદગી: `languageConfig.enabled` ચાલુ હોય ત્યારે, `autoDetect` નવીનતમ વપરાશકર્તા સંદેશની ભાષા પસંદ કરે છે (ઇનપુટ એન્જિન જેવું જ ડિટેક્ટર); `autoDetect` બંધ કરવાથી `defaultLanguage` પિન થાય છે. બંધ → અંગ્રેજી.

શૈલી × ભાષા મેટ્રિક્સ `tests/unit/compression/output-styles-i18n-matrix.test.ts` દ્વારા પિન કરવામાં આવે છે: નવી શૈલી ઓછામાં ઓછા pt-BR અનુવાદ (અથવા સ્પષ્ટ ટ્રેક કરેલ અપવાદ) વિના શિપ કરી શકાતી નથી, અને હાલની શૈલી ચુપચાપ લોકેલ ગુમાવી શકતી નથી. શૈલી ઉમેરવા માટે, [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) જુઓ.

### ટૂલ પરિણામ કમ્પ્રેશન

`toolResultCompressor.ts` મોડ્યુલ ટૂલ પરિણામો (ફંક્શન કોલ્સ, એજન્ટ આઉટપુટ, શોધ પરિણામો, વગેરે) માટે **5 વિશિષ્ટ કમ્પ્રેશન વ્યૂહરચનાઓ** પ્રદાન કરે છે:

1.  **શોધ પરિણામ કમ્પ્રેશન** — બિનજરૂરી પરિણામો દૂર કરે છે, ટોચના-N રાખે છે
2.  **ફાઇલ રીડ કમ્પ્રેશન** — મોટી ફાઇલોને ટ્રંકેટ કરે છે, હેડર/ઇમ્પોર્ટ્સ જાળવી રાખે છે
3.  **કોડ એક્ઝેક્યુશન કમ્પ્રેશન** — માત્ર આવશ્યક stdout/stderr રાખે છે
4.  **ડેટાબેઝ ક્વેરી કમ્પ્રેશન** — પંક્તિઓ મર્યાદિત કરે છે, વર્બોઝ મેટાડેટા દૂર કરે છે
5.  **API રિસ્પોન્સ કમ્પ્રેશન** — નલ ફીલ્ડ્સ દૂર કરે છે, એરેને સંક્ષિપ્ત કરે છે

#### ક્યારે ઉપયોગ કરવો

જ્યારે ટૂલ કોલ્સ હાજર હોય ત્યારે ટૂલ પરિણામ કમ્પ્રેશન **હંમેશા ચાલુ** હોય છે. કોઈ ગોઠવણીની જરૂર નથી.

### સ્ટેક્ડ પાઇપલાઇન

સ્ટેક્ડ મોડ **ક્રમમાં બહુવિધ એન્જિન** ચલાવે છે — સામાન્ય રીતે પહેલા RTK (ટૂલ આઉટપુટ પર 60-90% બચત), પછી કેવમેન (બાકીના ટેક્સ્ટ પર 30% વધારાની બચત). આનાથી **78-95% કુલ બચત** થાય છે.

#### તે કેવી રીતે કાર્ય કરે છે

```
ઇનપુટ (1000 ટોકન્સ)
  → RTK (કમાન્ડ-અવેર ફિલ્ટર) → 200 ટોકન્સ
    → કેવમેન (ફિલર દૂર કરવું) → 140 ટોકન્સ
  → આઉટપુટ (140 ટોકન્સ, 86% બચત)
```

#### ક્યારે ઉપયોગ કરવો

આ માટે સ્ટેક્ડ મોડનો ઉપયોગ કરો:

- ટૂલ-હેવી વર્કફ્લો (એજન્ટિક કોડિંગ, સંશોધન)
- ખર્ચ-સંવેદનશીલ બેચ પ્રોસેસિંગ
- જ્યારે તમને મહત્તમ ટોકન બચતની જરૂર હોય

કોમ્બો દ્વારા ગોઠવો:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "modePack": "stacked"
    }
  }
}
```

## કોમ્પ્રેશન કોમ્બો ઓવરરાઇડ્સ

તમે વૈશ્વિક કોમ્પ્રેશન મોડને **પ્રતિ કોમ્બો** ઓવરરાઇડ કરી શકો છો જેથી વિવિધ ઉપયોગના કેસો માટે વર્તનને ફાઇન-ટ્યુન કરી શકાય:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "auto": {
      "weights": { "taskFit": 0.5 },
      "modePack": "quality-first"
    }
  },
  "compressionOverride": {
    "mode": "aggressive",
    "stackedPipelines": ["rtk", "caveman"],
    "preserveToolDefinitions": true
  }
}
```

આ આ માટે ઉપયોગી છે:

- **કોડિંગ કોમ્બોઝ**: લાંબા સત્રો માટે `aggressive` મોડનો ઉપયોગ કરો
- **ઝડપી પ્રશ્ન-જવાબ કોમ્બોઝ**: ઝડપી પ્રતિભાવો માટે `lite` મોડનો ઉપયોગ કરો
- **ટૂલ-હેવી કોમ્બોઝ**: મહત્તમ બચત માટે `stacked` મોડનો ઉપયોગ કરો
- **પ્રોડક્શન કોમ્બોઝ**: કેશિંગ પ્રદાતાઓ માટે `cache-aware` મોડનો ઉપયોગ કરો
