## ઝાંખી

OmniRoute એક મોડ્યુલર પ્રોમ્પ્ટ કમ્પ્રેશન પાઇપલાઇન અમલમાં મૂકે છે, જે વિનંતીઓ અપસ્ટ્રીમ પ્રદાતાઓ સુધી પહોંચે તે પહેલાં **સક્રિય રીતે** ચાલે છે. આનો અર્થ એ છે કે તમારી ટોકન બચત પારદર્શક રીતે થાય છે — તમારા કાર્યપ્રવાહમાં કોઈ ફેરફાર કરવાની જરૂર નથી.

```
ક્લાયન્ટ વિનંતી
  → કમ્પ્રેશન વ્યૂહરચના પસંદગીકાર
    → કૉમ્બો ઓવરરાઇડ? → કૉમ્બો સેટિંગનો ઉપયોગ કરો
    → સ્વચાલિત-ટ્રિગર થ્રેશોલ્ડ? → સ્વચાલિત મોડનો ઉપયોગ કરો
    → ડિફૉલ્ટ મોડ? → વૈશ્વિક સેટિંગનો ઉપયોગ કરો
    → બંધ? → કમ્પ્રેશન છોડો
  → પસંદ કરેલો કમ્પ્રેશન મોડ
    → બંધ: કોઈ કમ્પ્રેશન નહીં
    → લાઇટ: સુરક્ષિત વ્હાઇટસ્પેસ/ફોર્મેટિંગ સફાઈ (~15%)
    → સ્ટાન્ડર્ડ: કેવમેન-શૈલીમાં બિનજરૂરી શબ્દો દૂર કરવા (~30%)
    → એગ્રેસિવ: હિસ્ટ્રી એજિંગ + સારાંશીકરણ (~50%)
    → અલ્ટ્રા: હ્યુરિસ્ટિક પ્રૂનિંગ + કોડ-બ્લૉક થિનિંગ (~75%)
    → RTK: કમાન્ડ-અવેર ટર્મિનલ/ટૂલ-આઉટપુટ ફિલ્ટરિંગ (60-90% અપસ્ટ્રીમ શ્રેણી)
    → સ્ટૅક્ડ: ક્રમબદ્ધ મલ્ટિ-એન્જિન પાઇપલાઇન, સામાન્ય રીતે પહેલાં RTK પછી Caveman (78-95% યોગ્ય શ્રેણી)
  → કમ્પ્રેસ કરેલી વિનંતી → પ્રદાતા
```

## કમ્પ્રેશન મોડ્સ

### બંધ

કોઈ કમ્પ્રેશન લાગુ કરવામાં આવતું નથી. બધા સંદેશાઓ કોઈ ફેરફાર વિના પસાર થાય છે.

### લાઇટ મોડ (~15% બચત, <1ms લેટન્સી)

સૌથી સુરક્ષિત મોડ — અર્થમાં શૂન્ય ફેરફાર, માત્ર ફોર્મેટિંગની સફાઈ:

| તકનીક                    | વર્ણન                                         |
| ------------------------ | --------------------------------------------- |
| `collapseWhitespace`     | સળંગ ખાલી લાઇનો અને અંતિમ સ્પેસને મર્જ કરે છે |
| `dedupSystemPrompt`      | ડુપ્લિકેટ સિસ્ટમ સંદેશાઓ દૂર કરે છે           |
| `compressToolResults`    | વિસ્તૃત ટૂલ/ફંક્શન આઉટપુટને કમ્પ્રેસ કરે છે   |
| `removeRedundantContent` | પુનરાવર્તિત સૂચનાઓ દૂર કરે છે                 |
| `replaceImageUrls`       | base64 ઇમેજ ડેટા URI ટૂંકા કરે છે             |

**આ માટે શ્રેષ્ઠ:** હંમેશાં ચાલુ રાખવા માટેનો ઉપયોગ, સુરક્ષા-મહત્ત્વપૂર્ણ કાર્યપ્રવાહો.

### સ્ટાન્ડર્ડ મોડ (~30% બચત)

[Caveman](https://github.com/JuliusBrussee/caveman)થી પ્રેરિત — અર્થ જાળવી રાખીને બિનજરૂરી શબ્દો અને વધુ પડતી શબ્દાળુ અભિવ્યક્તિ દૂર કરે છે:

- બિનજરૂરી શબ્દો દૂર કરે છે ("કૃપા કરીને", "મને લાગે છે", "મૂળભૂત રીતે", "ખરેખર")
- શબ્દાળુ શબ્દસમૂહોને સંક્ષિપ્ત કરે છે ("કરવા માટે" → "માટે", "ના પરિણામે" → "કારણ કે")
- નમ્રતાપૂર્ણ અચોક્કસતા દૂર કરે છે ("શું તમને વાંધો આવશે...", "જો તમે શક્ય હોય તો...")
- કોડિંગ પ્રોમ્પ્ટ્સ માટે સુસંગત કરેલા 30+ regex નિયમો

**આ માટે શ્રેષ્ઠ:** દૈનિક કોડિંગ કાર્યપ્રવાહો, ખર્ચ પ્રત્યે સભાન ટીમો.

### એગ્રેસિવ મોડ (~50% બચત)

લાંબા સત્રો માટે સ્માર્ટ હિસ્ટ્રી મેનેજમેન્ટ:

- **મેસેજ એજિંગ** — જૂના સંદેશાઓને ક્રમશઃ વધુ કમ્પ્રેસ કરવામાં આવે છે
- **ટૂલ રિઝલ્ટ સારાંશીકરણ** — લાંબા ટૂલ આઉટપુટને સારાંશોથી બદલવામાં આવે છે
- **સ્ટ્રક્ચરલ ઇન્ટેગ્રિટી ગાર્ડ્સ** — `tool_use` + `tool_result` જોડી સુસંગત રહે તે સુનિશ્ચિત કરે છે
- **કન્ટેક્સ્ટ વિન્ડો અવેરનેસ** — દરેક મોડલની ટોકન મર્યાદાનો આદર કરે છે

**આ માટે શ્રેષ્ઠ:** લાંબા ડિબગિંગ સત્રો, મોટા કોડબેઝ.

### અલ્ટ્રા મોડ (~75% બચત)

ટોકન-મહત્ત્વપૂર્ણ પરિસ્થિતિઓ માટે મહત્તમ કમ્પ્રેશન:

- **હ્યુરિસ્ટિક પ્રૂનિંગ** — સંબંધિતતાના થ્રેશોલ્ડથી નીચેના સંદેશાઓ દૂર કરે છે
- **કોડ બ્લૉક થિનિંગ** — પુનરાવર્તિત કોડ ઉદાહરણોને કમ્પ્રેસ કરે છે
- **બાઇનરી સર્ચ ટ્રન્કેશન** — કન્ટેક્સ્ટ વિન્ડો માટે શ્રેષ્ઠ કટ પૉઇન્ટ શોધે છે
- એગ્રેસિવ મોડની બધી સુવિધાઓ સામેલ છે

**આ માટે શ્રેષ્ઠ:** જ્યારે તમે વારંવાર કન્ટેક્સ્ટ મર્યાદા સુધી પહોંચી રહ્યા હો.

### RTK મોડ (60-90% અપસ્ટ્રીમ શ્રેણી)

RTK મોડ કોડિંગ-એજન્ટ સત્રોમાં દેખાતા વિસ્તૃત ટૂલ આઉટપુટ માટે ઑપ્ટિમાઇઝ કરેલો છે:

- `git status`, `git diff`, `git log`, ટેસ્ટ રનર્સ,
  TypeScript/Vite/Webpack બિલ્ડ્સ, ESLint/Biome/Prettier, npm ઑડિટ/ઇન્સ્ટૉલ્સ, Docker લૉગ્સ, ઇન્ફ્રા
  આઉટપુટ અને સામાન્ય શેલ આઉટપુટ જેવા કમાન્ડ/આઉટપુટ વર્ગોને શોધે છે
- `open-sse/services/compression/engines/rtk/filters/`માંથી JSON ફિલ્ટર પૅક્સ લાગુ કરે છે
- પ્રોજેક્ટ અથવા વૈશ્વિક `filters.toml` ફાઇલોમાંથી RTK TOML schema v1 ફિલ્ટર્સ આયાત કરે છે, જેમાં પ્રોજેક્ટ ફાઇલો માટે ઇનલાઇન-ટેસ્ટ
  વેલિડેશન અને ટ્રસ્ટ-ગેટિંગ સામેલ છે
- ઇનલાઇન વેરિફાય નમૂનાઓ સાથે 49 બિલ્ટ-ઇન ફિલ્ટર્સ પૂરા પાડે છે
- ANSI કન્ટ્રોલ સિક્વન્સ, પ્રોગ્રેસ બાર, પુનરાવર્તિત લાઇનો અને બિન-કાર્યક્ષમ અવાજ દૂર કરે છે
- નિષ્ફળતાઓ, ભૂલો, ચેતવણીઓ, બદલાયેલી ફાઇલો, સારાંશો અને લાંબા આઉટપુટનો અંતિમ ભાગ જાળવે છે
- ટ્રસ્ટ-ગેટેડ પ્રોજેક્ટ ફિલ્ટર્સ, વૈશ્વિક ફિલ્ટર્સ અને વૈકલ્પિક રિડેક્ટ કરેલા રૉ-આઉટપુટ પુનઃપ્રાપ્તિને સપોર્ટ કરે છે

**આ માટે શ્રેષ્ઠ:** શેલ, બિલ્ડ, ટેસ્ટ, git, grep અને ફાઇલ-આઉટપુટ ટ્રાન્સક્રિપ્ટ્સ ધરાવતા એજન્ટ સત્રો.

### સ્ટૅક્ડ મોડ (78-95% યોગ્ય શ્રેણી)

સ્ટૅક્ડ મોડ નિર્ધારિત ક્રમમાં અનેક કમ્પ્રેશન એન્જિન્સ ચલાવે છે. ડિફૉલ્ટ પાઇપલાઇન આ છે:

```txt
RTK -> Caveman
```

આ ક્રમ પહેલાં ટર્મિનલ/ટૂલ આઉટપુટને સંક્ષિપ્ત રાખે છે, ત્યારબાદ
બાકીના કુદરતી-ભાષાના પ્રોમ્પ્ટ પર Caveman સિમેન્ટિક કન્ડેન્સેશન લાગુ કરે છે. સ્ટૅક્ડ પાઇપલાઇન્સને વૈશ્વિક રીતે અથવા
રાઉટિંગ કૉમ્બોઝને સોંપાયેલા કમ્પ્રેશન કૉમ્બોઝ દ્વારા કૉન્ફિગર કરી શકાય છે.

**આ માટે શ્રેષ્ઠ:** મોટા ટૂલ લૉગ્સ સાથે માનવીય સૂચનાઓ અથવા સહાયકના સારાંશો ધરાવતો મિશ્ર કન્ટેક્સ્ટ.

## અપસ્ટ્રીમ બચતનું ગણિત

OmniRoute બે સ્રોતોમાંથી થતી કમ્પ્રેશન બચતનું દસ્તાવેજીકરણ કરે છે: અપસ્ટ્રીમ પ્રોજેક્ટ બેન્ચમાર્ક્સ અને
OmniRouteનું પોતાનું એન્જિન સંયોજન.

| સ્રોત   | અહીં ઉપયોગમાં લેવાયેલ અપસ્ટ્રીમ READMEનો આંકડો                                                               |
| ------- | ------------------------------------------------------------------------------------------------------------ |
| Caveman | `~75%` ઓછા આઉટપુટ ટોકન્સ, `65%` બેન્ચમાર્ક સરેરાશ આઉટપુટ બચત, `22-87%` શ્રેણી અને `~46%` ઇનપુટ કમ્પ્રેશન ટૂલ |
| RTK     | `60-90%` કમાન્ડ-આઉટપુટ બચત; નમૂના સત્રમાં `~118,000 -> ~23,900` ટોકન્સ, અથવા `79.7%` બચત (`~80%`)            |

ઓવરલેપ થતા ટૂલ/કૉન્ટેક્સ્ટ પેલોડ્સ માટે, ડિફૉલ્ટ OmniRoute કોમ્બો એન્જિનોને આ ક્રમમાં સ્ટૅક કરે છે:

```txt
RTK -> Caveman
```

સંયુક્ત બચત સરવાળાકીય નહીં, પરંતુ ગુણાકારી છે:

```txt
combined = 1 - (1 - RTK બચત) * (1 - Caveman ઇનપુટ બચત)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

આ `78-95%` આંકડો ત્યારે લાગુ પડે છે જ્યારે RTK અને Caveman બંને સમાન ઇનપુટ/કૉન્ટેક્સ્ટ પેલોડ ઘટાડી શકે.
Cavemanનો રિસ્પૉન્સ આઉટપુટ મોડ અલગ છે: સક્ષમ હોય ત્યારે Cavemanની પોતાની આઉટપુટ બચતનો ઉપયોગ કરો (`65%`
સરેરાશ, `~75%` મુખ્ય આંકડો, `22-87%` શ્રેણી). કુલ બિલિંગ બચત તમારા પ્રૉમ્પ્ટ/આઉટપુટના મિશ્રણ પર આધાર રાખે છે.

### "પાત્ર"નો વાસ્તવિક અર્થ શું છે

15-95%ની મુખ્ય શ્રેણી વાસ્તવિક છે, પરંતુ તે માત્ર **પુનરાવર્તિત અથવા બિનજરૂરી રીતે વિસ્તૃત** સામગ્રીને લાગુ પડે છે — પુનરાવર્તિત
એરર લાઇન્સ, એક જ ચેતવણી વારંવાર બતાવતો બિલ્ડ લૉગ, અતિશય મોટો `grep`/ફાઇલ-રીડ ડમ્પ. તેનો
અર્થ એ **નથી** કે દરેક રિક્વેસ્ટમાં એટલી બચત થાય છે.

પ્રાયોગિક રીતે ચકાસેલું (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300 સમાન
એરર લાઇન્સ ધરાવતા Anthropic-આકારના `tool_result` બ્લૉક સામે `stacked` (RTK + Caveman) રનથી
**95.93% ટોકન બચત / 96.26% અક્ષર બચત** મળી — જે જાહેરાત કરેલી શ્રેણીમાં ચોક્કસપણે આવે છે.
પરંતુ સામાન્ય, પુનરાવર્તન વિનાના ટૂલ આઉટપુટ (સ્વચ્છ `grep` મેચ સૂચિ,
ટૂંકું ફાઇલ રીડ, સામાન્ય વાર્તાલાપનું લખાણ) સામે સમાન પાઇપલાઇન યોગ્ય રીતે **લગભગ શૂન્ય બચત** આપે છે, કારણ કે
દૂર કરવા માટે કંઈ પુનરાવર્તિત હોતું નથી અને `validateCompression()` (`validation.ts`) એવા
પુનર્લેખનને મોકલવાની મંજૂરી આપતું નથી જે કોડ બ્લૉક્સ, URLs, હેડિંગ્સ, વર્ઝન્સ અથવા ALL-CAPS કૉન્સ્ટન્ટ આઇડેન્ટિફાયર્સને કાઢી નાખે કે બદલી નાખે.

આ અપેક્ષિત, સુરક્ષિત વર્તન છે, બગ નથી: જે કોડિંગ સત્ર મોટાભાગે સ્વચ્છ ફાઇલો વાંચે/grep કરે છે તેમાં
કમ્પ્રેશન સંપૂર્ણપણે સક્ષમ હોવા છતાં કુલ બચત મર્યાદિત જોવા મળશે, જ્યારે નિષ્ફળ થતી
લૂપ અથવા વધુ પડતું આઉટપુટ આપતા લિન્ટરનો સામનો કરતા સત્રમાં તે ટ્રાફિક પર સંપૂર્ણ 78-95% શ્રેણીની બચત જોવા મળશે. કોઈ એક સત્રની
નીચી એકંદર બચત ટકાવારીને કમ્પ્રેશન ખોટી રીતે કૉન્ફિગર થયાનું પ્રમાણ ન માનો — પહેલાં તપાસો કે
મૂળ ટૂલ આઉટપુટ ખરેખર પુનરાવર્તિત હતું કે નહીં.

## ગોઠવણી

### ડૅશબોર્ડ

`Dashboard → Context & Cache` પર જાઓ:

- **Caveman** — મોડની પસંદગી, ભાષા પૅક્સ, પૂર્વાવલોકન અને વૈશ્વિક ડિફૉલ્ટ્સ
- **RTK** — કમાન્ડ-ફિલ્ટર પૂર્વાવલોકન, RTK સુરક્ષા સેટિંગ્સ અને ફિલ્ટર કૅટલૉગ
- **કમ્પ્રેશન કોમ્બોઝ** — રૂટિંગ કોમ્બોઝને સોંપવામાં આવેલી નામવાળી એન્જિન પાઇપલાઇન્સ
- **ઑટો-ટ્રિગર થ્રેશોલ્ડ** — ટોકનની સંખ્યા થ્રેશોલ્ડ કરતાં વધી જાય ત્યારે આપમેળે કમ્પ્રેશન સક્રિય કરે છે

### પ્રતિ-કોમ્બો ઓવરરાઇડ

`Dashboard → Context & Cache → Compression Combos` માં, રૂટિંગ કોમ્બોને કમ્પ્રેશન કોમ્બો સોંપો:

```txt
કોમ્બો: "free-tier-fallback"
  કમ્પ્રેશન કોમ્બો: "coding-agent-stack"
  પાઇપલાઇન: RTK -> Caveman
  લક્ષ્યો:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

આ તમને પેઇડ સબ્સ્ક્રિપ્શન્સ પર લાઇટ મોડ જાળવી રાખીને મફત/કોડિંગ પ્રદાતાઓ પર સ્ટૅક્ડ કમ્પ્રેશનનો ઉપયોગ કરવાની મંજૂરી આપે છે.

આ "પ્રતિ-કોમ્બો ઓવરરાઇડ" અસાઇનમેન્ટ **રૂટિંગ-કોમ્બો કમ્પ્રેશન મોડ** ઓવરરાઇડ (Default/Off/Lite/Standard/Aggressive/Ultra) કરતાં અલગ નિયંત્રણ છે — તે ઓવરરાઇડ નામવાળી કમ્પ્રેશન-કોમ્બો પાઇપલાઇન પસંદ કરતું નથી; તે ફક્ત `resolveCompressionPlan` દ્વારા તપાસવામાં આવતા `compressionMode` ફીલ્ડને સેટ કરે છે. તેને કોમ્બો કાર્ડ (`Dashboard → Combos`) પર અથવા, #6760થી, ઉપર દસ્તાવેજીકૃત પાઇપલાઇન-અસાઇનમેન્ટ ચેકબૉક્સની બરાબર બાજુએ `Dashboard → Context & Cache → Compression Combos` માં આવેલી "Assign to routing" સૂચિમાં પ્રતિ રૂટિંગ કોમ્બો સેટ કરી શકાય છે. બંને ઇન્ટરફેસ એક જ `PUT /api/combos/{id}` એન્ડપૉઇન્ટ દ્વારા સેટિંગ્સને કાયમી રાખે છે.

### પ્રતિ-વિનંતી ઓવરરાઇડ

એક જ વિનંતી માટે કમ્પ્રેશન પ્લાનને ઓવરરાઇડ કરવા `x-omniroute-compression` રિક્વેસ્ટ હેડર મોકલો. તેની પ્રાથમિકતા સર્વોચ્ચ છે — તે રૂટિંગ-કોમ્બો ઓવરરાઇડ, સક્રિય પ્રોફાઇલ, ઑટો-ટ્રિગર અને પેનલ ડિફૉલ્ટ કરતાં અગ્રતા ધરાવે છે. અજ્ઞાત મૂલ્યો અવગણવામાં આવે છે (વિનંતી ક્યારેય નકારવામાં આવતી નથી) અને વૈશ્વિક માસ્ટર સ્વિચ હજી પણ બધું નિયંત્રિત કરે છે: જ્યારે કમ્પ્રેશન વૈશ્વિક રીતે બંધ હોય, ત્યારે હેડર તેને ચાલુ કરી શકતું નથી. મૂલ્યો:

| મૂલ્ય         | અસર                                                                            |
| ------------- | ------------------------------------------------------------------------------ |
| `off`         | આ વિનંતી માટે કોઈ કમ્પ્રેશન નહીં.                                              |
| `default`     | પેનલમાંથી મેળવેલી ડિફૉલ્ટ પ્રોફાઇલ (સક્રિય પ્રોફાઇલને અવગણે છે).               |
| `engine:<id>` | સક્ષમ હોય ત્યારે એક એન્જિન, દા.ત. `engine:rtk`.                                |
| `<combo>`     | નામવાળો કોમ્બો, જે પહેલાં નામ (કેસ-ઇન્સેન્સિટિવ) અને પછી id દ્વારા મેળ ખાય છે. |

લાગુ કરાયેલ પ્લાન `X-OmniRoute-Compression: <mode>; source=<source>` રિસ્પૉન્સ હેડરમાં પાછો દર્શાવવામાં આવે છે, જ્યાં `<source>` એ `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` અથવા `off` માંથી એક હોય છે.


## શું સુરક્ષિત રાખવામાં આવે છે

કમ્પ્રેશન એન્જિન **હંમેશાં આને જાળવી રાખે છે:**

- ✅ કોડ બ્લૉક્સ (ફેન્સ્ડ અને ઇનલાઇન)
- ✅ URLs અને ફાઇલ પાથ્સ
- ✅ JSON સંરચનાઓ અને સંરચિત ડેટા
- ✅ આઇડેન્ટિફાયર્સ અને સુરક્ષિત ટેક્નિકલ ટોકન્સ
- ✅ ગાણિતિક અભિવ્યક્તિઓ
- ✅ ટૂલ/ફંક્શન કૉલ વ્યાખ્યાઓ
- ✅ સિસ્ટમ પ્રોમ્પ્ટ્સ (lite મોડમાં)

કંઈપણ સંગ્રહિત થાય તે પહેલાં RTK raw-output recovery સામાન્ય API કીઝ, bearer ટોકન્સ, Slack ટોકન્સ, AWS ઍક્સેસ કીઝ,
પાસવર્ડ્સ, ટોકન્સ અને સિક્રેટ્સને છુપાવે છે.

## આભાર સ્વીકાર

Standard મોડના કમ્પ્રેશન નિયમો **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ 51K+) દ્વારા બનાવવામાં આવેલા **[Caveman](https://github.com/JuliusBrussee/caveman)** પરથી પ્રેરિત છે — વાયરલ "જ્યારે થોડા ટોકનથી કામ થઈ શકે ત્યારે ઘણા ટોકન શા માટે વાપરવા" પ્રોજેક્ટ. Caveman `~75%` ઓછા આઉટપુટ ટોકન્સ, બેન્ચમાર્કમાં સરેરાશ `65%` આઉટપુટ બચત, `22-87%` આઉટપુટ રેન્જ અને `~46%` ઇનપુટ-કમ્પ્રેશન ટૂલ દર્શાવે છે.

RTK મોડ **[RTK AI](https://github.com/rtk-ai)** દ્વારા બનાવવામાં આવેલા **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** પરથી પ્રેરિત છે — ટર્મિનલ, બિલ્ડ, ટેસ્ટ, git અને ટૂલ-આઉટપુટ ફિલ્ટરિંગ માટેનો ઉચ્ચ-કાર્યક્ષમતા ધરાવતો કમાન્ડ-આઉટપુટ કમ્પ્રેશન પ્રોજેક્ટ. RTK `60-90%` બચત દર્શાવે છે, જ્યારે તેના READMEના નમૂનાના સેશનમાં `~80%` બચત બતાવવામાં આવી છે.

## અદ્યતન કમ્પ્રેશન સિસ્ટમ્સ

7 standard મોડ્સ ઉપરાંત, OmniRouteમાં કેટલીક અદ્યતન કમ્પ્રેશન
સિસ્ટમ્સ સામેલ છે, જે કૉન્ટેક્સ્ટના આધારે આપમેળે કાર્ય કરે છે.

### કૅશ-અવેર કમ્પ્રેશન

કેટલાક પ્રોવાઇડર્સ (જેમ કે prompt caching સાથે Anthropic) **prompt caching**ને સપોર્ટ કરે છે,
જે તેમને ખર્ચ અને વિલંબ ઘટાડવા માટે પ્રોમ્પ્ટના ભાગોને કૅશ કરવાની મંજૂરી આપે છે. જ્યારે
કૅશિંગ સક્ષમ હોય, ત્યારે aggressive કમ્પ્રેશન વાસ્તવમાં કાર્યક્ષમતાને **નુકસાન** પહોંચાડી શકે છે,
કારણ કે તે કૅશ કરેલા ટોકન્સને બદલે છે અને કૅશને અમાન્ય બનાવે છે.

`cachingAware.ts` મોડ્યુલ **કૅશિંગ કૉન્ટેક્સ્ટ શોધીને** અને
તે અનુસાર **કમ્પ્રેશન વ્યૂહરચનાને સમાયોજિત કરીને** આ સમસ્યા ઉકેલે છે.

#### તે કેવી રીતે કાર્ય કરે છે

1. **કૅશિંગ કૉન્ટેક્સ્ટ શોધે છે** — `cache_control` માર્કર્સ માટે રિક્વેસ્ટ બૉડી સ્કૅન કરે છે
2. **કૅશિંગ પ્રોવાઇડર્સ ઓળખે છે** — લક્ષ્ય પ્રોવાઇડર કૅશિંગને સપોર્ટ કરે છે કે નહીં તે તપાસે છે
3. **વ્યૂહરચના સમાયોજિત કરે છે** — કૅશિંગ પ્રોવાઇડર્સ માટે `aggressive`/`ultra`ને `standard`માં ડાઉનગ્રેડ કરે છે
4. **સિસ્ટમ પ્રોમ્પ્ટને અવગણે છે** — સિસ્ટમ પ્રોમ્પ્ટ્સ સામાન્ય રીતે કૅશ થયેલા હોય છે, તેથી તેમને કમ્પ્રેસ કરતું નથી
5. **નિર્ધારિત રૂપાંતરણો વાપરે છે** — માત્ર સુસંગત આઉટપુટ ઉત્પન્ન કરતા રૂપાંતરણોનો ઉપયોગ કરે છે

#### કોડનું ઉદાહરણ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← કૅશ માર્કર
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ક્યારે ઉપયોગ કરવો

કૅશ-અવેર કમ્પ્રેશન **હંમેશાં ચાલુ હોય છે** — કોઈ કૉન્ફિગરેશનની જરૂર નથી. તે માત્ર ત્યારે
સક્રિય થાય છે જ્યારે:

- વિનંતીમાં `cache_control` માર્કર્સ હોય
- લક્ષ્ય પ્રોવાઇડર prompt cachingને સપોર્ટ કરતો હોય (Anthropic, OpenAI વગેરે)

### પ્રોગ્રેસિવ એજિંગ

લાંબી વાતચીતમાં ઘણા મેસેજ ટર્ન્સ એકત્ર થાય છે, પરંતુ જૂના ટર્ન્સ ધીમે ધીમે ઓછા
પ્રાસંગિક બનતા જાય છે. `progressiveAging.ts` મોડ્યુલ **ટર્નના અંતરના આધારે મેસેજની વિગતો ઘટાડે છે**:

- **તાજેતરના ટર્ન્સ (0-3)**: શબ્દશઃ જાળવવામાં આવે છે (સંપૂર્ણ વિગતો)
- **મધ્યમ ટર્ન્સ (4-8)**: Lite કમ્પ્રેશન (વ્હાઇટસ્પેસ અને ફૉર્મેટિંગની સફાઈ)
- **જૂના ટર્ન્સ (9+)**: Caveman કમ્પ્રેશન (બિનજરૂરી સામગ્રી દૂર કરવી, સારાંશ બનાવવો)
- **ખૂબ જૂના ટર્ન્સ (20+)**: વ્યાપક રીતે સારાંશિત કરવામાં આવે છે અથવા દૂર કરવામાં આવે છે

#### કોડનું ઉદાહરણ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... વધુ 50 ટર્ન્સ ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // પ્રથમ 3 ટર્ન્સ: શબ્દશઃ
  light: 8, // ટર્ન્સ 4-8: lite કમ્પ્રેશન
  moderate: 20, // ટર્ન્સ 9-20: caveman કમ્પ્રેશન
  // ટર્ન્સ 21+: વ્યાપક સારાંશીકરણ
});

// saved = બચાવેલા ટોકન્સની સંખ્યા
```

#### ક્યારે ઉપયોગ કરવો

ક્રમશઃ એજિંગ `aggressive` અને `ultra` મોડ્સ માટે **હંમેશાં ચાલુ** હોય છે. તે ખાસ કરીને આ માટે અસરકારક છે:

- લાંબા સમય સુધી ચાલતા કોડિંગ સત્રો
- ઘણા દિવસો સુધી ચાલતી વાતચીતો
- ઘણા ટૂલ કૉલ્સ ધરાવતા એજન્ટિક વર્કફ્લો

### કેવમેન આઉટપુટ મોડ

`outputMode.ts` મોડ્યુલ, મોડલ પોતે જ સંકુચિત અને ટૂંકો આઉટપુટ ("કેવમેન" શૈલી) ઉત્પન્ન કરે તે માટે **સિસ્ટમ પ્રોમ્પ્ટ સૂચનાઓ** દાખલ કરે છે.

#### તે કેવી રીતે કાર્ય કરે છે

ઇનપુટને સંકુચિત કરવાને બદલે, આ મોડ નીચેના જેવો સિસ્ટમ પ્રોમ્પ્ટ ઉમેરે છે:

> "ન્યૂનતમ શબ્દોમાં જવાબ આપો. ઔપચારિક સૌજન્ય ટાળો. ટૂંકાં વાક્યો વાપરો."

આ ખાસ કરીને આ માટે સારી રીતે કાર્ય કરે છે:

- કોડ જનરેશન (વધુ ટૂંકો આઉટપુટ = ઓછા ટોકન્સ)
- ઝડપી પ્રશ્નોત્તરી (વિસ્તૃત સમજૂતીઓની જરૂર નથી)
- બૅચ પ્રોસેસિંગ (થ્રુપુટ મહત્તમ કરો)

#### ક્યારે ઉપયોગ કરવો

કેવમેન આઉટપુટ મોડ **વૈકલ્પિક** છે — તેને કોમ્બો કૉન્ફિગ દ્વારા સેટ કરો:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "outputMode": "caveman"
    }
  }
}
```

### આઉટપુટ શૈલીઓ (કૅટલૉગ)

ઉપરોક્ત કેવમેન આઉટપુટ મોડ **લેગસી સિંગલ-સ્ટાઇલ પાથ** છે. દરેક શૈલીમાં ત્રણ તીવ્રતા સ્તરો — `lite`, `full`, `ultra` — હોય છે અને દરેક સ્તર અંતે સહિયારી સીમાઓની કલમ ધરાવે છે, જે કોડ બ્લૉક્સ, ફાઇલ પાથ્સ, કમાન્ડ્સ, એરર સ્ટ્રિંગ્સ, URLs અને આઇડેન્ટિફાયર્સને યથાવત્ રાખે છે.

#### ઇન્જેક્શન કેવી રીતે કાર્ય કરે છે

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) પસંદગીને કૅટલૉગ સાથે ઉકેલે છે (અજ્ઞાત ids અને લોકેલ સાથે મેળ ન ખાતી શૈલીઓ કાઢી નાખવામાં આવે છે, તે ક્યારેય એરર નથી), પસંદ કરેલી સૂચનાઓને કૅટલૉગના ક્રમમાં જોડે છે, સીમાઓની કલમ **માત્ર એક વાર** ઉમેરે છે અને પરિણામને એક જ આઇડેમ્પોટન્સી માર્કર (`[OmniRoute Output Styles]`)ની પાછળ સિસ્ટમ પ્રોમ્પ્ટમાં આગળ મૂકે છે — ફરી લાગુ કરવાથી કંઈ થતું નથી. શોધાયેલી વિનંતીની ભાષા માટે અનુવાદ ઉપલબ્ધ હોય ત્યારે, અંગ્રેજીને બદલે સ્થાનિક ભાષાની સૂચના દાખલ કરવામાં આવે છે.

#### કેવી રીતે સક્ષમ કરવું

ડૅશબોર્ડમાં: **Context → Settings → Compression** — દરેક શૈલી માટે ચાલુ/બંધ ટૉગલ અને સ્તર પસંદગીકાર ધરાવતી એક પંક્તિ. પ્રોગ્રામેટિક રીતે, કમ્પ્રેશન કૉન્ફિગ પસંદગીને આ રીતે જાળવી રાખે છે:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

બૅકવર્ડ કમ્પેટિબિલિટી: લેગસી `outputMode: "caveman"` કોમ્બો સેટિંગ હજુ પણ કાર્ય કરે છે અને `terse-prose` સાથે મૅપ થાય છે, જે દરેક લેગસી ભાષામાં જૂના ઇન્જેક્શન સાથે બાઇટ-સમાન છે.

ભાષાની પસંદગી: `languageConfig.enabled` ચાલુ હોય ત્યારે, `autoDetect` તાજેતરના યુઝર મેસેજની ભાષા પસંદ કરે છે (ઇનપુટ એન્જિન્સ જેવો જ ડિટેક્ટર); `autoDetect` બંધ કરવાથી `defaultLanguage` નિશ્ચિત થાય છે. બંધ → અંગ્રેજી.

શૈલી × ભાષા મેટ્રિક્સને `tests/unit/compression/output-styles-i18n-matrix.test.ts` દ્વારા નિશ્ચિત કરવામાં આવ્યો છે: ઓછામાં ઓછા pt-BR અનુવાદ (અથવા સ્પષ્ટ રીતે ટ્રૅક કરાયેલ અપવાદ) વિના નવી શૈલી રિલીઝ કરી શકાતી નથી અને હાલની શૈલી મૌનપણે કોઈ લોકેલ ગુમાવી શકતી નથી. શૈલી ઉમેરવા માટે [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) જુઓ.

### ટૂલ પરિણામ કમ્પ્રેશન

`toolResultCompressor.ts` મોડ્યુલ ટૂલનાં પરિણામો (ફંક્શન કૉલ્સ, એજન્ટ આઉટપુટ્સ, શોધ પરિણામો વગેરે) માટે **5 વિશિષ્ટ કમ્પ્રેશન વ્યૂહરચનાઓ** પ્રદાન કરે છે:

1. **શોધ પરિણામ કમ્પ્રેશન** — પુનરાવર્તિત પરિણામો દૂર કરે છે, ટોચનાં-N રાખે છે
2. **ફાઇલ રીડ કમ્પ્રેશન** — મોટી ફાઇલોને કાપે છે, હેડર્સ/ઇમ્પોર્ટ્સ જાળવે છે
3. **કોડ એક્ઝિક્યુશન કમ્પ્રેશન** — ફક્ત આવશ્યક stdout/stderr રાખે છે
4. **ડેટાબેઝ ક્વેરી કમ્પ્રેશન** — પંક્તિઓ મર્યાદિત કરે છે, વધુ પડતું મેટાડેટા દૂર કરે છે
5. **API રિસ્પોન્સ કમ્પ્રેશન** — null ફીલ્ડ્સ દૂર કરે છે, ઍરેને સંક્ષિપ્ત કરે છે

#### ક્યારે ઉપયોગ કરવો

ટૂલ કૉલ્સ હાજર હોય ત્યારે ટૂલ પરિણામ કમ્પ્રેશન **હંમેશાં ચાલુ** હોય છે. કોઈ કૉન્ફિગરેશનની જરૂર નથી.

### સ્ટૅક્ડ પાઇપલાઇન

સ્ટૅક્ડ મોડ **એક પછી એક અનેક એન્જિન્સ** ચલાવે છે — સામાન્ય રીતે પહેલાં RTK (ટૂલ આઉટપુટમાં 60-90% બચત), પછી Caveman (બાકીના લખાણમાં વધારાની 30% બચત). તેનાથી **કુલ 78-95% બચત** પ્રાપ્ત થાય છે.

#### તે કેવી રીતે કાર્ય કરે છે

```
ઇનપુટ (1000 ટોકન્સ)
  → RTK (કમાન્ડ-અવેર ફિલ્ટર) → 200 ટોકન્સ
    → Caveman (વધારાના શબ્દો દૂર કરવા) → 140 ટોકન્સ
  → આઉટપુટ (140 ટોકન્સ, 86% બચત)
```

#### ક્યારે ઉપયોગ કરવો

આ માટે સ્ટૅક્ડ મોડનો ઉપયોગ કરો:

- ટૂલ-આધારિત વર્કફ્લો (એજન્ટિક કોડિંગ, સંશોધન)
- ખર્ચ-સંવેદનશીલ બૅચ પ્રોસેસિંગ
- જ્યારે તમને મહત્તમ ટોકન બચતની જરૂર હોય

કોમ્બો દ્વારા કૉન્ફિગર કરો:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "modePack": "stacked"
    }
  }
}
```

## કોમ્બિનેશન કમ્પ્રેશન ઓવરરાઇડ્સ

વિવિધ ઉપયોગના કિસ્સાઓ માટે વર્તનને વધુ ચોક્કસ બનાવવા તમે વૈશ્વિક કમ્પ્રેશન મોડને **દરેક કોમ્બિનેશન દીઠ** ઓવરરાઇડ કરી શકો છો:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "auto": {
      "weights": { "taskFit": 0.5 },
      "modePack": "quality-first"
    }
  },
  "compressionOverride": {
    "mode": "aggressive",
    "stackedPipelines": ["rtk", "caveman"],
    "preserveToolDefinitions": true
  }
}
```

આ નીચેના માટે ઉપયોગી છે:

- **કોડિંગ કોમ્બિનેશન્સ**: લાંબા સત્રો માટે `aggressive` મોડનો ઉપયોગ કરો
- **ઝડપી પ્રશ્નોત્તરી કોમ્બિનેશન્સ**: ઝડપી પ્રતિસાદો માટે `lite` મોડનો ઉપયોગ કરો
- **વધુ ટૂલ્સ ધરાવતા કોમ્બિનેશન્સ**: મહત્તમ બચત માટે `stacked` મોડનો ઉપયોગ કરો
- **પ્રોડક્શન કોમ્બિનેશન્સ**: કૅશિંગ પ્રદાતાઓ માટે `cache-aware` મોડનો ઉપયોગ કરો
