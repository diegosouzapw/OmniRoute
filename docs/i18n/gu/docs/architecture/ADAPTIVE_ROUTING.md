આ દસ્તાવેજ OmniRouteમાં ઉમેરાયેલા પ્રતિસાદ-સંચાલિત અનુકૂલનશીલ રૂટિંગના પાયાનું વર્ણન કરે છે. તેને ઇરાદાપૂર્વક નાનું રાખવામાં આવ્યું છે: તે ટાઇપ કરેલ રૂટિંગ-પરિણામ ચેનલ, હાલના auto-combo સ્કોરરને ઇનપુટ આપતો ઓનલાઇન ગુણવત્તા સંકેત, વૈકલ્પિક OpenTelemetry exporter અને સમજક્ષમતા endpoint રજૂ કરે છે. તે હાલના સ્થિતિસ્થાપકતા સ્ટેક (circuit breaker, connection cooldown, model lockout, health matrix, autopilot)ને **બદલતું નથી** — તે તેને પૂરક બને છે.

## 1. આર્કિટેક્ચરલ સંદર્ભ

OmniRoute એ **રિક્વેસ્ટ હોટ પાથ** અને **કંટ્રોલ/ઇન્ટેલિજન્સ પ્લેન** ધરાવતું ડેટા પ્લેન છે. હોટ પાથ ઝડપી, મેમરી-કાર્યક્ષમ, અસિંક્રોનસ, સ્થિતિસ્થાપક અને અનુમાનિત રહેવો આવશ્યક છે. મૂલ્યાંકન, ગુણવત્તા સ્કોરિંગ, પ્રયોગો અને ઐતિહાસિક વિશ્લેષણ કંટ્રોલ પ્લેનના ભાગ છે.

```
AI Agent / IDE
      │
      ▼
┌─────────────────────┐
│    OmniRoute        │   ડેટા પ્લેન (ઝડપી, સિંક, ઇન-મેમરી)
│  રૂટિંગ / ફેલઓવર   │
│  હેલ્થ / ગાર્ડરેલ   │
│  કૅશ / સ્ટ્રીમિંગ   │
└──────────┬──────────┘
           │ RoutingEvent (ફાયર-એન્ડ-ફૉર્ગેટ, ~0.2µs)
           ▼
┌─────────────────────┐
│  પ્રતિસાદ સિંક      │   કંટ્રોલ પ્લેન (અસિંક, બેસ્ટ-એફર્ટ)
│  ગુણવત્તા ટ્રૅકર   │
│  OTel exporter      │
│  એક્સપ્લેઇન સ્ટોર  │
└──────────┬──────────┘
           ▼  ગુણવત્તા સ્કોર
      auto-combo સ્કોરર
```

### જે પહેલેથી ઉપલબ્ધ હતું (ઑડિટ કરેલું, પુનરાવર્તિત નહીં)

| સંકલ્પના                                | હાલનું અમલીકરણ                                                                                       |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| ઉપલબ્ધતા (શું આપણે ટ્રાફિક મોકલી શકીએ?) | Circuit breaker (CLOSED/DEGRADED/OPEN/HALF_OPEN, DBમાં સંગ્રહિત), connection cooldown, model lockout |
| હેલ્થ રિપોર્ટિંગ                        | `providerHealthMatrix.ts`, `providerHealthAutopilot.ts`                                              |
| શેડો ટ્રાફિક                            | `open-sse/services/combo/shadowRouting.ts`                                                           |
| ગાર્ડરેલ્સ                              | `src/lib/guardrails/` (પ્રી/પોસ્ટ હુક્સ)                                                             |
| એક્ઝેક્ટ કૅશ                            | `src/lib/semanticCache.ts` (સિગ્નેચર-આધારિત)                                                         |
| મૂલ્યાંકનકારો / eval-સંચાલિત રૂટિંગ     | `src/lib/evals/`, `open-sse/services/evalRouting.ts`                                                 |
| Combo નિર્ણય સમજક્ષમતા                  | `open-sse/services/combo/decisionTrace.ts`                                                           |
| ડૅશબોર્ડ રિયલ-ટાઇમ ઇવેન્ટ્સ             | `src/lib/events/eventBus.ts` (UI નોટિફિકેશન ચેનલ, `unknown` પેલોડ્સ, 100-એન્ટ્રી હિસ્ટ્રી)           |

રૂટિંગ-ઇવેન્ટ લેયર એ `eventBus`નું પુનઃઅમલીકરણ **નથી**: તે બસ ડૅશબોર્ડની રિયલ-ટાઇમ નોટિફિકેશન ચેનલ છે (ટાઇપ કરેલા _ઇવેન્ટ નામો_, અપારદર્શક પેલોડ્સ, UI ઉપભોક્તાઓ). `RoutingEvent` એ ટાઇપ કરેલું _પરિણામ_ સ્ટ્રક્ટ છે (લેટન્સી/ટોકન્સ/ખર્ચ/પરિણામ/સમાપ્તિ-કારણ), જેનો ઉપયોગ કંટ્રોલ પ્લેનના પ્રતિસાદ સિંક (ગુણવત્તા ટ્રૅકર, OTel exporter, એક્સપ્લેઇન સ્ટોર) કરે છે.

### જે ગેરહાજર હતું (અહીં ઉમેર્યું છે)

1. **ટાઇપ કરેલ રૂટિંગ-પરિણામ ઇવેન્ટ + સિંક એબ્સ્ટ્રેક્શન** (`RoutingEvent` /
   `RoutingEventSink`). `decisionTrace` combo-સ્કોપ્ડ અને માત્ર ઇન-મેમરી છે;
   `comboMetrics` સંચિત કાઉન્ટર્સ છે; `call_logs` કાચું અસિંક પર્સિસ્ટન્સ છે.
   આમાંથી કોઈ પણ એવું ટાઇપ કરેલું, સિંક-આધારિત પરિણામ ચેનલ નથી કે જેને ગુણવત્તા ટ્રૅકર, OTel
   exporter અથવા Future-AGI-શૈલીનો મૂલ્યાંકનકાર સબ્સ્ક્રાઇબ કરી શકે.
2. આઉટપુટ ગુણવત્તા માટેનો **ઓનલાઇન ગુણવત્તા સંકેત** (EWMA) — અગાઉ સ્કોરર
   માત્ર સ્થિર ટાસ્ક ફિટનેસ અને opt-in eval પાસ-રેટ્સ મારફતે જ "ગુણવત્તા"નું પ્રોક્સી માપન કરતો હતો.
3. GenAI સિમેન્ટિક કન્વેન્શન્સનો ઉપયોગ કરતો **વૈકલ્પિક, ડિપેન્ડન્સી-મુક્ત OTel exporter**.
4. વાસ્તવિક રૂટિંગ નિર્ણયો + ગુણવત્તા સ્થિતિ પરત કરતો **સમજક્ષમતા endpoint**.

## 2. રાઉટિંગ ઇવેન્ટ્સ (ફીડબૅકનો પાયો)

ફાઇલો: `open-sse/services/routing/events.ts`, `.../index.ts`

એક `RoutingEvent` ફક્ત રાઉટિંગ મેટાડેટા વહન કરે છે:

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ...
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // અનુમતિસૂચિમાં સમાવાયેલ યુનિયન
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

`RoutingEventSink`, TypeScriptમાં `Send+Sync`-શૈલીનું ટ્રેઇટ છે:

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // O(1) હોવું આવશ્યક છે, કોઈ સિંક્રોનસ I/O નહીં
}
```

હોટ પાથ દરેક પૂર્ણ થયેલી વિનંતી દીઠ એકવાર `emitRoutingEvent(event)`ને કૉલ કરે છે
(સ્ટ્રીમિંગ-પૂર્ણતા કૉલબૅક, નૉન-સ્ટ્રીમિંગ સફળતા પાથ અને
`handleChatCore`માં malformed-200 નિષ્ફળતા પાથ). ડિસ્પૅચ એ નોંધાયેલા સિંકમાં
સિંક્રોનસ ફૅન-આઉટ છે, પરંતુ દરેક સિંક ફક્ત કતારમાં ઉમેરે છે/ઇન-મેમરી સ્ટેટ
અપડેટ કરે છે. **હોટ પાથ પર કોઈ સિંક્રોનસ ડેટાબેઝ રાઇટ નહીં, કોઈ નેટવર્ક I/O નહીં.**

ડિફૉલ્ટ સિંક:

- `MemoryRoutingEventStore` — મર્યાદિત (500) રિંગ બફર, સૌથી નવું પ્રથમ, explain
  એન્ડપૉઇન્ટ માટે.
- `QualityTracker` કન્ઝ્યુમર — EWMA ગુણવત્તા અંદાજને અપડેટ કરે છે.
- `OtlpHttpsEventSink` — વૈકલ્પિક, ફક્ત `OMNIROUTE_OTEL_ENDPOINT`
  (અથવા `OTEL_EXPORTER_OTLP_ENDPOINT`) સેટ હોય ત્યારે સક્ષમ થાય છે.

### માપેલો ઓવરહેડ (પ્રામાણિક સરખામણી)

આ વર્કસ્ટેશન પર `npm run bench:routing-events` (100k પુનરાવર્તનો; સબ-µs ઑપરેશનોને
એકંદર µs/op તરીકે માપવામાં આવ્યા છે, કારણ કે પ્રતિ-ઑપરેશન પર્સેન્ટાઇલ
`performance.now()` ટાઇમર રિઝોલ્યુશન કરતાં નીચે છે):

| પરિસ્થિતિ                       | µs/op  | ops/s  |
| ------------------------------- | ------ | ------ |
| બેઝલાઇન (ફક્ત સ્કોરિંગ)         | ~0.045 | ~22 M  |
| બેઝલાઇન + RoutingEvent (2 સિંક) | ~0.168 | ~5.9 M |
| બેઝલાઇન + ઇવેન્ટ + OTel એનક્યૂ  | ~0.163 | ~6.1 M |
| સહવર્તી (8 ઇન્ટરલીવ્ડ બર્સ્ટ)   | ~0.18  | —      |

બેઝલાઇન સ્કોરિંગની સરખામણીમાં ઇવેન્ટ-ડિસ્પૅચનો તફાવત ~0.12 µs/request છે; OTel સિંક
ફક્ત કતારમાં ઉમેરે છે (O(1) બફર પુશ), જેથી માપી શકાય તેટલો કોઈ ઉમેરો થતો નથી.
આ આંકડા મશીન-વિશિષ્ટ અને સાપેક્ષ છે — પ્રોડક્શન માટેની ગેરંટી નથી. v1નો "~0.2 µs"
આંકડો એકંદર અંદાજ હતો; આ પદ્ધતિ સ્કોરિંગ બેઝલાઇનને ઇવેન્ટ-ડિસ્પૅચ ખર્ચથી
અલગ પાડે છે.

## 3. ગુણવત્તા સિગ્નલ (ફીડબૅક-સંચાલિત પ્રોવાઇડર સ્ટેટ)

ફાઇલો: `open-sse/services/routing/quality.ts`

v2 **ઑપરેશનલ** ગુણવત્તાને **સિમેન્ટિક** ગુણવત્તાથી અલગ કરે છે:

- **ઑપરેશનલ** — રાઉટિંગ હોટ પાથમાંથી મેળવવામાં આવે છે (HTTP 4xx/5xx, કનેક્શન
  નિષ્ફળતાઓ, 429s, વિકૃત પ્રતિસાદો, સ્ટ્રીમ વિક્ષેપો, `finish_reason=length`,
  શૂન્ય-આઉટપુટ સફળતાઓ, લેટન્સી/TTFT EWMA). 200ને સિમેન્ટિક ગુણવત્તા તરીકે
  ગણવામાં આવતું નથી.
- **સિમેન્ટિક** — જનરેટ થયેલા આઉટપુટનું વાસ્તવિક મૂલ્ય. તે ફક્ત ઇવેલ્યુએટર દ્વારા
  `setSemanticQuality()` મારફતે જ ક્યારેય ઉત્પન્ન થાય છે. કોઈ ઇવેલ્યુએટર તે આપે
  ત્યાં સુધી તેનું મૂલ્ય `null` રહે છે અને તે ક્યારેય ઑપરેશનલ સ્કોરમાં પ્રવેશતું નથી.

પ્રતિ-(પ્રોવાઇડર, મૉડલ) સ્ટેટ (EWMA + મર્યાદિત કાઉન્ટર્સ):

- `successEwma` — પરિણામની સફળતાનો EWMA (α=0.2).
- `latencyEwma` / `ttftEwma` — લેટન્સીનો EWMA (α=0.1).
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`.
- `recencyMs` — મૉડલ છેલ્લે કેટલા સમય પહેલાં જોવામાં આવ્યું હતું.

### વિશ્વસનીયતા / સેમ્પલ જાગરૂકતા

`confidence = clamp01(samples / 50)`, અને સ્કોરરને પરત આપવામાં આવતો સ્કોર
તટસ્થ મધ્યબિંદુ તરફ મિશ્રિત કરવામાં આવે છે:

```
score = 0.5 + confidence * (operational - 0.5)
```

પરિણામો (ટેસ્ટ દ્વારા ચકાસાયેલા):

- કોલ્ડ પ્રોવાઇડર (0 સેમ્પલ)નો સ્કોર **0.5** છે — તેને અન્યાયપૂર્વક દંડિત કરવામાં
  આવતો નથી, પરંતુ તે હજારો મજબૂત અવલોકનો ધરાવતા પ્રોવાઇડર પર પ્રભુત્વ પણ મેળવી
  શકતો નથી.
- 7 નસીબદાર સફળતાઓ ધરાવતા પ્રોવાઇડરને 0.5 તરફ ખેંચવામાં આવે છે (તે આશાવાદી
  ઇનિશિયલાઇઝેશનના આધારે ક્યારેય પ્રભુત્વ મેળવતું નથી).
- 50+ સેમ્પલ ધરાવતો પ્રોવાઇડર તેના વાસ્તવિક ઑપરેશનલ સ્કોર તરફ કન્વર્જ થાય છે.
- અધોગતિ અને પુનઃપ્રાપ્તિ ક્રમશઃ થાય છે (EWMA), અને એક અલગ પડેલી નિષ્ફળતા
  સ્વસ્થ પ્રોવાઇડરને નષ્ટ કરતી નથી.

`ProviderQuality`, `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }` એક્સપોઝ કરે છે.

આ ઑટો-કૉમ્બો સ્કોરરને `quality` સ્કોરિંગ ફૅક્ટર તરીકે ઇનપુટ આપે છે:

- `open-sse/services/autoCombo/scoring.ts`માં `ScoringFactors.quality` /
  `ScoringWeights.quality`.
- `DEFAULT_WEIGHTS`: `health` 0.1905 → 0.1605, `quality` 0.03. સરવાળો 1.0 જ રહે છે.
- `buildAutoCandidates`, ટ્રૅકરમાંથી `candidate.quality` ભરે છે; ડેટા વિનાના
  કૅન્ડિડેટ માટે ડિફૉલ્ટ તટસ્થ **0.5** છે (કોલ્ડ કૅન્ડિડેટને ન તો બૂસ્ટ કરવામાં
  આવે છે કે ન તો દંડિત કરવામાં આવે છે).

બંધ લૂપ:

```
RoutingEvent → QualityTracker → getQualityScore → ઑટો-કૉમ્બો ગુણવત્તા ફૅક્ટર
      ↑                                                    │
      └────── વિનંતીનું પરિણામ (handleChatCore) ←──────────┘
```

### હાર્ડ બાકાતીકરણ વિરુદ્ધ સૉફ્ટ દંડ

ગુણવત્તા સિગ્નલ ફક્ત એક **સૉફ્ટ ઍડેપ્ટિવ પ્રેફરન્સ** છે. હાર્ડ બાકાતીકરણ
હાલના રેઝિલિયન્સ સ્ટૅક પાસે જ રહે છે: સર્કિટ બ્રેકર OPEN, ક્વોટા સમાપ્ત,
ઑથ નિષ્ફળતા, મૉડલ લૉકઆઉટ — આમાંથી કોઈપણ ગુણવત્તા સ્કોરથી પ્રભાવિત થતું નથી.
જે પ્રોવાઇડરનો ગુણવત્તા સ્કોર અસ્થાયી રીતે ઘટે છે, તેને ઓછી પ્રાથમિકતા આપવામાં
આવે છે, પરંતુ ક્યારેય હાર્ડ-ડિસેબલ કરવામાં આવતું નથી.

## 3b. કેનોનિકલ સ્ટ્રીમ ટાઇમિંગ (TTFT / ITL)

ફાઇલો: `open-sse/utils/streamTiming.ts`

`createStreamTiming()` એ સ્ટ્રીમિંગ પાથ માટેનું એકમાત્ર ઇન્સ્ટ્રુમેન્ટેશન સીમ છે,
જે `createSSEStream` (`open-sse/utils/stream.ts`) સાથે જોડાયેલું છે:

- `markByte()` — પ્રથમ અપસ્ટ્રીમ ચંક પ્રાપ્ત થયો.
- `markForward()` — ક્લાયન્ટને ફોરવર્ડ કરાયેલો પ્રથમ ચંક (TTFT માટે વપરાય છે).
- `markInterrupted()` — સ્વચ્છ રીતે પૂર્ણ થાય તે પહેલાં સ્ટ્રીમ ટાઇમઆઉટ/અબોર્ટ/ભૂલ.
- `ttft()` = પ્રથમ ફોરવર્ડ કરાયેલા SSE ચંકની લેટન્સી. **આ ટોકન-સ્તરનો TTFT નથી** —
  એક SSE ચંકમાં શૂન્ય/એક/ઘણા ટોકન હોઈ શકે છે. ચોક્કસ રીતે દસ્તાવેજીકૃત.
- `avgItlMs()` = ચંકો વચ્ચેના અંતરાલની સરેરાશ (ITL માટે ચંક-લેટન્સી પ્રોક્સી).

TTFT/ITL/interrupted `RoutingEvent` (`ttftMs`, `itlMs`)માં પ્રવાહિત થાય છે અને
OTel સિંક દ્વારા GenAI/OmniRoute સ્પાન ઍટ્રિબ્યુટ્સ તરીકે એક્સપોર્ટ થાય છે.

## 4. OpenTelemetry / GenAI અવલોકનક્ષમતા

ફાઇલો: `open-sse/services/routing/otel.ts`

- ડિપેન્ડન્સી-મુક્ત OTLP/HTTP JSON એક્સપોર્ટર (ગ્લોબલ `fetch` વાપરે છે,
  `@opentelemetry/*` SDK નહીં).
- સ્પાન્સ GenAI સિમેન્ટિક કન્વેન્શન્સ (`gen_ai.provider.name`,
  `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`,
  `gen_ai.completion.finish_reason`, `gen_ai.system`) તેમજ OmniRoute રાઉટિંગ
  ઍટ્રિબ્યુટ્સ (પરિણામ, સ્ટેટસ, ttft, પુનઃપ્રયાસો, ફૉલબૅક) અનુસરે છે.
- `record()` ફક્ત સીમિત બફરમાં એનક્યૂ કરે છે (O(1)); બૅકગ્રાઉન્ડ ટાઇમર
  અસિંક્રોનસ રીતે `POST {endpoint}/v1/traces` મારફતે ફ્લશ કરે છે. ઓવરલોડ હેઠળ
  સૌથી જૂની ઇવેન્ટ્સ ડ્રૉપ થાય છે (`dropped` કાઉન્ટર) — ડેટા પ્લેન પર ક્યારેય
  બૅકપ્રેશર લાદવામાં આવતું નથી.
- **કન્ફિગર ન થાય ત્યાં સુધી નિષ્ક્રિય.** `OMNIROUTE_OTEL_ENDPOINT` (અથવા
  `OTEL_EXPORTER_OTLP_ENDPOINT`) સેટ કરવું આવશ્યક છે; અન્યથા સિંક રજિસ્ટર થતું
  નથી અને કોઈ OTel કોડ ચાલતો નથી.

## 5. સમજૂતીક્ષમતા

- `GET /v1/explain/routing` તાજેતરના `RoutingEvent`s (વાસ્તવિક નિર્ણયો, સૌથી
  નવા પહેલા) અને પ્રતિ-પ્રોવાઇડર/મોડલ ગુણવત્તા સ્નૅપશૉટ પરત કરે છે.
- ઑથ `/v1/combos`ને અનુરૂપ છે (Bearer API કી અથવા ડૅશબોર્ડ સેશન;
  `REQUIRE_API_KEY=false` ધરાવતા સિંગલ-યૂઝર લોકલ ડિપ્લોયમેન્ટ્સ પર અનામી).
- કોમ્બો-સ્તરના પ્રતિ-ઇન્વોકેશન ટ્રેસ હાલના `decisionTrace.ts` દ્વારા ઉપલબ્ધ
  રહે છે (હેડર `X-OmniRoute-Combo-Trace`).
- સુરક્ષા: ઇવેન્ટ્સમાં ફક્ત રાઉટિંગ મેટાડેટા હોય છે, ક્યારેય
  પ્રોમ્પ્ટ્સ/બોડીઝ/ક્રેડેન્શિયલ્સ નહીં.

## 6. મૂલ્યાંકન-પ્લેન ઇન્ટિગ્રેશન (Future AGI તૈયારી)

OmniRoute, Future AGI (અથવા કોઈપણ મૂલ્યાંકનકાર)ને **સંભવિત
ઇન્ટેલિજન્સ/મૂલ્યાંકન બૅકએન્ડ તરીકે ગણે છે, ડિપેન્ડન્સી તરીકે નહીં**. ઇન્ટિગ્રેશન
સીમ્સ:

- `RoutingEventSink` ઇવેન્ટ્સને અસિંક્રોનસ રીતે મૂલ્યાંકનકારને ફોરવર્ડ કરી શકે છે.
- `MemoryRoutingEventStore` + ગુણવત્તા સ્નૅપશૉટ મૂલ્યાંકનકારને મૂળ નિર્ણય
  સ્ટ્રીમ આપે છે.
- ભાવિ `Evaluator` (ડિટર્મિનિસ્ટિક, લોકલ જજ, HTTP, WASM) ઇવેન્ટ્સ/ટ્રેસનો
  ઉપયોગ કરશે અને `QualityScore` પરત કરશે, જે એ જ
  `getQualityScore`/ગુણવત્તા-ફૅક્ટર પાથમાં ફીડ થાય છે.
- હાલનું મૂલ્યાંકન-સંચાલિત રાઉટિંગ (`open-sse/services/evalRouting.ts`) સક્ષમ
  હોય ત્યારે `eval_runs` પાસ-રેટ્સ મુજબ કોમ્બો ટાર્ગેટ્સને પહેલેથી જ ફરીથી
  ક્રમબદ્ધ કરે છે.

કોઈપણ મૂલ્યાંકન રિક્વેસ્ટ પાથ પર સિંક્રોનસ રીતે ચાલતું નથી અને મૂલ્યાંકનકાર
ગેરહાજર હોય ત્યારે પણ ગેટવે સંપૂર્ણ રીતે કાર્ય કરે છે.

## 7. અંતિમ આર્કિટેક્ચરલ સમીક્ષા

1. **સિંક્રોનસ હૉટ પાથ પર શું બાકી રહે છે?** રાઉટિંગ/સ્કોરિંગ, ગાર્ડરેલ
   પ્રી-ચેક્સ, કૅશ લુકઅપ અને ઇન-મેમરી સિંક્સ માટે એક `emitRoutingEvent` ફૅન-આઉટ
   (બેઝલાઇન સ્કોરિંગ કરતાં ~0.12 µs વધુ).
2. **અસિંક્રોનસ પ્રોસેસિંગમાં શું ખસેડાયું?** OTel એક્સપોર્ટ (ટાઇમર + fetch),
   `call_logs`/ઉપયોગ પર્સિસ્ટન્સ, સિમેન્ટિક-કૅશ રાઇટ્સ; ગુણવત્તા ઇન-મેમરી અને
   O(1) છે (અસિંક્રોનસની જરૂર નથી).
3. **રાઉટિંગ પરિણામ ફીડબૅક કેવી રીતે બને છે?** `handleChatCore` એક
   `RoutingEvent` એમિટ કરે છે → `QualityTracker` EWMA સ્ટેટ અપડેટ કરે છે →
   `getQualityScore` ઑટો-કોમ્બોના `quality` ફૅક્ટરને ફીડ કરે છે.
4. **ગુણવત્તા ભાવિ રાઉટિંગને કેવી રીતે પ્રભાવિત કરે છે?** નીચો ગુણવત્તા સ્કોર
   `scoreAutoTargets`માં તે પ્રોવાઇડર/મોડલનો વેઇટેડ સ્કોર ઘટાડે છે, તેથી
   અવમૂલ્યિત મોડલ્સની પસંદગી ધીમે ધીમે ઓછી થાય છે અને તેમનું EWMA સુધરતાં તેઓ
   પુનઃપ્રાપ્ત થાય છે.
5. **Future AGI ડિપેન્ડન્સી બન્યા વિના કેવી રીતે ઇન્ટિગ્રેટ થઈ શકે છે?**
   `RoutingEventSink` ઇન્ટરફેસ / ભાવિ `Evaluator` ઍડૅપ્ટર દ્વારા — કોઈ
   હાર્ડકોડેડ ડિપેન્ડન્સી નહીં.
6. **મૂલ્યાંકનકાર ઉપલબ્ધ ન હોય ત્યારે શું થાય છે?** રાઉટિંગ અપ્રભાવિત રહે છે;
   કોઈ અવલોકિત સિગ્નલ ન ધરાવતા મોડલ્સ માટે ગુણવત્તા ન્યુટ્રલ (1.0) પર ફૉલબૅક
   થાય છે.
7. **ટેલિમેટ્રી ઉપલબ્ધ ન હોય ત્યારે શું થાય છે?** OTel સિંક ફક્ત રજિસ્ટર થતું
   નથી; બાકીનું રાઉટિંગ લેયર કોઈ ફેરફાર વિના ચાલે છે.
8. **ઓવરલોડ હેઠળ શું થાય છે?** OTel બફર સૌથી જૂની ઇવેન્ટ્સને ડ્રૉપ કરે છે;
   ગુણવત્તા અને રિંગ બફર રચનાથી જ સીમિત છે; કોઈ બૅકપ્રેશર નથી.
9. **અવમૂલ્યન પછી પ્રોવાઇડર સ્ટેટ કેવી રીતે પુનઃપ્રાપ્ત થાય છે?** સફળતાઓ
   એકત્ર થતાં EWMA ફરી કન્વર્જ થાય છે; વૉર્મઅપ કોલ્ડ મોડલ્સને ન્યુટ્રલ રાખે છે;
   સર્કિટ બ્રેકર HALF_OPEN પ્રોબ્સ દ્વારા સ્વતંત્ર રીતે પુનઃપ્રાપ્ત થાય છે.
10. **કઈ પ્રસ્તાવિત સુવિધાઓ ઇરાદાપૂર્વક અમલમાં મૂકવામાં આવી નથી અને શા માટે?**
    - શૅડો ટ્રાફિક / પ્રયોગો — પહેલેથી અમલમાં છે
      (`combo/shadowRouting.ts`); ફરીથી બનાવ્યાં નથી.
    - ગાર્ડરેલ્સ — પહેલેથી અમલમાં છે (`src/lib/guardrails/`); ડુપ્લિકેટ કર્યાં
      નથી.
    - સિમેન્ટિક કૅશ — પહેલેથી અમલમાં છે (`src/lib/semanticCache.ts`); ડુપ્લિકેટ
      કર્યો નથી.
    - સંપૂર્ણ પ્રયોગ-વ્યવસ્થાપન પ્લૅટફોર્મ, ડેટાસેટ ટૂલિંગ, પ્રોમ્પ્ટ-ઑપ્ટિમાઇઝેશન
      પ્લૅટફોર્મ, વેક્ટર DB અથવા ફરજિયાત બાહ્ય OTel ઇન્ફ્રાસ્ટ્રક્ચર — લીન ડેટા
      પ્લેનના કાર્યક્ષેત્રની બહાર.
    - Rust `RoutingEvent` સ્ટ્રક્ટ — ડેટા પ્લેન TypeScriptમાં છે; TS ટાઇપ તેનું
      અનુકૂલિત સમકક્ષ છે.
