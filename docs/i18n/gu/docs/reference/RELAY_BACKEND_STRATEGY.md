## સારાંશ

OmniRoute હવે `/api/v1/relay/chat/completions` માટે ત્રણ રિલે મોડને સપોર્ટ કરે છે:

- `ts`: TypeScript રિલેનો પ્રક્રિયાની અંદર ઉપયોગ કરો.
- `bifrost`: Bifrost ગેટવેનો ફરજિયાત ઉપયોગ કરો.
- `auto`: ઉપલબ્ધ હોય ત્યારે Bifrostને પ્રાથમિકતા આપો અને નિષ્ફળતા આવે ત્યારે TypeScript પર પાછા ફરો.

જ્યારે તમે ઊંચા વિનંતી દરે (મોટી સંખ્યામાં ટોકન્સ/દિવસ, લગભગ સતત થ્રુપુટ) ચલાવી રહ્યા હો, ત્યારે ફૉલબૅક પાથને સ્પષ્ટ અને ઝડપી રાખવો એ શ્રેષ્ઠ વ્યૂહરચના છે, જેથી મુખ્ય પાથ ક્યારેય નિષ્ક્રિય સાઇડકારને કારણે અવરોધાય નહીં.

## મોડનું વર્તન

- `ts`
  - સૌથી ઓછી સંચાલકીય જટિલતા.
  - તમામ રાઉટિંગ અને માન્યતા Nodeમાં ચાલે છે.
  - ઉપલબ્ધતા માટે સાઇડકાર પર કોઈ નિર્ભરતા નથી.
- `bifrost`
  - તમામ વિનંતીઓને સાઇડકાર ગેટવે મારફતે ફરજિયાત મોકલે છે.
  - કોઈ સ્વચાલિત ફૉલબૅક નથી.
  - માત્ર ત્યારે ઉપયોગી છે જ્યારે સાઇડકારની કાર્યક્ષમતા અને વિલંબની ખાતરી હોય.
- `auto`
  - જ્યારે સાઇડકાર સુધી પહોંચી શકાય અને તે સક્ષમ હોય ત્યારે તેનો ઉપયોગ થાય છે.
  - નિષ્ફળ પ્રયાસો ફૉલબૅક હેડર્સને ટ્રિગર કરે છે અને ટ્રાફિકને TS પર પાછો મોકલે છે, જેથી વિનંતીની સફળતા મર્યાદિત સમયની અંદર જળવાઈ રહે.
  - જ્યારે માત્ર સાઇડકાર દ્વારા જ રાઉટિંગ કરવા કરતાં અપટાઇમ વધુ મહત્વપૂર્ણ હોય, ત્યારે ઉત્પાદન માટે આ મોડ સૌથી સુરક્ષિત પસંદગી છે.

## આજે 9router વિરુદ્ધ CLIPROXYAPI

9router અને CLIPROXYAPI બંને એવા એકીકરણો છે, જેઓ ઐતિહાસિક રીતે અપસ્ટ્રીમ પ્રદાતાઓ માટે સુસંગતતા પાથ ઉપલબ્ધ કરાવતા હતા.

- 9router એ અપસ્ટ્રીમ ઑર્કેસ્ટ્રેશન અને સુસંગતતા વર્તન માટેનો એમ્બેડેડ પાથ છે.
- CLIPROXYAPI એ CLI / SDK પ્રકારના ટ્રાફિક માટેનો પ્રૉક્સી API બ્રિજ છે.
- જ્યારે તમને સમર્પિત સાઇડકાર જેવો મધ્યવર્તી તબક્કો અને ઓછા વિલંબવાળું સ્થાનિક ડિસ્પેચ જોઈએ ત્યારે Bifrostને બાહ્યકૃત પાથ તરીકે સ્થિર કરવામાં આવી રહ્યું છે.

જો તમે હાલમાં 9router/CLIPROXYAPIની તુલના કરી રહ્યા હો:

- હેન્ડઑફ પહેલાં API રૂટમાં વિનંતી સહીકરણ, મંજૂર સૂચિની ચકાસણીઓ અને DB નીતિ નિયંત્રણો જાળવી રાખો.
- જો કોઈ વર્કફ્લોને કડક સાઇડકાર વર્તન અને વિનંતીદીઠ ઓછો ફેરફાર જોઈએ, તો `OMNIROUTE_RELAY_BACKEND=bifrost`નો ઉપયોગ કરો.
- જો તમને ઘટના દરમિયાન સુવ્યવસ્થિત ક્ષય સાથે સાઇડકારની સ્થિતિસ્થાપકતા જોઈએ, તો `OMNIROUTE_RELAY_BACKEND=auto`નો ઉપયોગ કરો.

## બૅકએન્ડ સીમાનો કરાર

સ્થિર ઉત્પાદન સીમા OmniRoute રિલે API છે, ડૅશબોર્ડનું અમલીકરણ નહીં. Next.js ડૅશબોર્ડ સ્થાનિક સેવાઓને ઇન્સ્ટૉલ, કૉન્ફિગર અને સુપરવાઇઝ કરી શકે છે, પરંતુ વિનંતી રાઉટિંગે રિલે API દ્વારા પ્રવેશવું જોઈએ અને તે સીમાની પાછળ હેન્ડઑફ કરવું જોઈએ.

લાંબા ગાળાની બૅકએન્ડ પસંદગીઓ:

- TypeScript રિલેને પ્રક્રિયાની અંદરના નીતિ અને ફૉલબૅક પાથ તરીકે રાખો. કોઈપણ બૅકએન્ડ હેન્ડઑફ પહેલાં પ્રમાણીકરણ, મંજૂર સૂચિઓ, વિનંતી સામાન્યીકરણ, હિસાબ અને સુરક્ષા ચકાસણીઓ અહીં જ રહે છે.
- જ્યારે ડિપ્લોયમેન્ટને ઓછો રાઉટિંગ ફેરફાર, કેન્દ્રિત પ્રદાતા પરિભ્રમણ અથવા બહુવિધ OmniRoute રેપ્લિકામાં સ્કેલ-આઉટની જરૂર હોય ત્યારે Bifrostનો પસંદગીના ઉચ્ચ-થ્રુપુટ Tier-1 સાઇડકાર તરીકે ઉપયોગ કરો.
- 9router અને CLIPROXYAPIને એમ્બેડેડ સુસંગતતા સેવાઓ તરીકે રાખો. તેઓ દેખરેખ હેઠળની સ્થાનિક પ્રક્રિયાઓ તરીકે ચાલે છે અને જ્યારે તેમનું પ્રદાતા/CLI વર્તન ઇચ્છિત ઍડૅપ્ટર હોય ત્યારે ઉપયોગી છે, પરંતુ તેમણે ડિફૉલ્ટ Tier-1 રાઉટિંગ એન્જિન બનવું જોઈએ નહીં.
- ડૅશબોર્ડને મુખ્ય પાથમાં મનસ્વી સેવા URLs મોકલવા ન દો. UI દ્વારા આપવામાં આવેલા URLs કૉન્ફિગરેશન ઇનપુટ્સ છે; રાઉટિંગ કોડે સર્વર-સાઇડ સેટિંગ્સ અને સુપરવાઇઝરની સ્થિતિમાંથી નોંધાયેલા તથા કાર્યક્ષમતા-ચકાસિત બૅકએન્ડ્સ ઉકેલવા જોઈએ.
- આજે દેખરેખ હેઠળની સેવાઓ માટે લૂપબૅક HTTPને પ્રાથમિકતા આપો, કારણ કે સંચાલિત પ્રક્રિયાઓ પહેલેથી HTTP-સુસંગત APIs પ્રદાન કરે છે, રૂટ ગાર્ડ સીમાનું ઑડિટ કરી શકે છે અને નિષ્ફળતા/ફૉલબૅક વર્તન વિનંતી લૉગ્સમાં દૃશ્યમાન હોય છે. ભાવિ SDK અથવા સૉકેટ ટ્રાન્સપોર્ટ ફક્ત ત્યારે જ ઉમેરવા યોગ્ય છે જ્યારે તે આઇસોલેશન અથવા ફૉલબૅકના અર્થને નબળા પાડ્યા વિના p99 રાઉટિંગ વિલંબને માપી શકાય એટલો ઘટાડે.

અત્યંત ઉચ્ચ-થ્રુપુટ ડિપ્લોયમેન્ટ માટે, ડિફૉલ્ટ જવાબ તેથી Bifrost સક્ષમ કરેલું `auto` છે: સફળતા દર જાળવવા માટે TypeScript ફૉલબૅક સાચવી રાખીને મુખ્ય પાથ પર Go સાઇડકારનો ઉપયોગ કરો. સુવ્યવસ્થિત ક્ષય કરતાં માત્ર સાઇડકાર દ્વારા જ કાર્ય કરવાનું કડક વર્તન વધુ મહત્વપૂર્ણ હોય ત્યારે જ `bifrost`નો ઉપયોગ કરો.

## ઉચ્ચ-થ્રુપુટ માર્ગદર્શન

સતત ઊંચા RPM/RPS અને કડક સફળતા SLO માટે:

1. વ્યવહારુ કૂલડાઉન અને નિષ્ફળતા ટેલિમેટ્રી સાથે `auto`નો ઉપયોગ કરો.
2. અપસ્ટ્રીમ માન્યતા અને API-કી ચકાસણીઓને TypeScript રૂટ સીમા પર રાખો.
3. સ્પષ્ટ હેડર્સ/કાઉન્ટર્સ સક્ષમ કરો, જેથી તમારી ચેતવણી પ્રણાલી ફૉલબૅકની આવર્તનતા અને કારણો જોઈ શકે.
4. અનંત સમય સુધી રાહ જોવાને બદલે ઝડપથી નિષ્ફળ થવા માટે સાઇડકાર ટાઇમઆઉટ્સને સમાયોજિત કરો.
5. સેવા સ્વચાલિત-પુનઃપ્રારંભ અને કાર્યક્ષમતા ટેલિમેટ્રી લૂપને સ્વસ્થ રાખો, જેથી ફૉલબૅક ખરેખર અપવાદરૂપ રહે.

## સૂચવેલ આધારરેખા

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- API કીઝ, મંજૂર સૂચિ, સૅનિટાઇઝર અને દર-મર્યાદાની ચકાસણીઓને રૂટ હેન્ડલર્સમાં સક્ષમ રાખો (તેઓ ડાઉનસ્ટ્રીમ ફૉર્વર્ડિંગ પહેલાં હંમેશાં ચાલે છે).
- તમારા રિવર્સ પ્રૉક્સી અને વિનંતી લૉગ્સમાંથી ફૉલબૅક મેટ્રિક્સ નિકાસ કરો, જેથી સાઇડકાર આઉટેજ એક મિનિટની અંદર દૃશ્યમાન થાય.

પાત્રતાના કરાર અને સ્થળાંતરના તબક્કાઓ માટે [પ્રદાતા પ્લગઇન મૅનિફેસ્ટ](./PROVIDER_PLUGIN_MANIFEST.md) જુઓ.
