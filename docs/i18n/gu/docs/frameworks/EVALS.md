> **સત્યનો અધિકૃત સ્રોત:** `src/lib/evals/`, `src/lib/db/evals.ts`, `src/app/api/evals/`
> **છેલ્લે અપડેટ કરેલું:** 2026-06-28 — v3.8.40

OmniRoute એક સામાન્ય મૂલ્યાંકન ફ્રેમવર્ક સાથે આવે છે, જેનો ઉપયોગ તમે રાઉટિંગ
કૉન્ફિગરેશન્સ, એકલ પ્રદાતાઓ/મૉડલ્સ અથવા સાથે સમાવિષ્ટ "golden set" સ્યુટ્સને બેન્ચમાર્ક કરવા માટે કરી શકો છો.
તેનો ઉપયોગ રાઉટિંગ ફેરફારોની ચકાસણી કરવા, નવા પ્રદાતાઓને માન્ય કરવા અને રિલીઝને
પ્રોડક્શન ટ્રાફિક માટે પ્રમોટ કરતાં પહેલાં નિયંત્રિત કરવા માટે કરો.

ફ્રેમવર્કનું અમલીકરણ આ રીતે થયેલું છે:

- એક શુદ્ધ રનર (`src/lib/evals/evalRunner.ts`), જે ઇન-મેમરી
  બિલ્ટ-ઇન સ્યુટ્સ રજિસ્ટર કરે છે, અપેક્ષિત માપદંડો સામે આઉટપુટ્સનું મૂલ્યાંકન કરે છે અને
  સ્કોરકાર્ડ્સને એકત્રિત કરે છે.
- કસ્ટમ (વપરાશકર્તા-નિર્ધારિત) સ્યુટ્સ
  અને SQLiteમાં ઐતિહાસિક રન્સ માટે પર્સિસ્ટન્સ લેયર (`src/lib/db/evals.ts`).
- એક ઑર્કેસ્ટ્રેશન લેયર (`src/lib/evals/runtime.ts`), જે `POST /v1/chat/completions` પર વાસ્તવિક કૉલ્સ મોકલીને
  દરેક કેસ એક્ઝિક્યુટ કરે છે, લેટન્સી
  અને આઉટપુટ્સ કૅપ્ચર કરે છે અને રનને સંગ્રહિત કરે છે.
- `/api/evals/*` હેઠળ REST એન્ડપૉઇન્ટ્સ (માત્ર મેનેજમેન્ટ-ઑથ).
- `Dashboard → Usage → Evals` પર ડૅશબોર્ડ ઇન્ટરફેસ (`EvalsTab.tsx`).

## સંકલ્પનાઓ

### સ્યુટ

સ્યુટ એ `description` અને એક અથવા
વધુ કેસ ધરાવતો ટેસ્ટ કેસોનો નામિત સંગ્રહ છે. સ્યુટ્સ બે સ્રોતોમાંથી આવે છે:

| સ્રોત      | ક્યાં નિર્ધારિત છે                              | રનટાઇમ દરમિયાન ફેરફારક્ષમ? |
| ---------- | ----------------------------------------------- | -------------------------- |
| `built-in` | બૂટ સમયે `registerSuite()` દ્વારા રજિસ્ટર થયેલ  | ના (કોડ-નિર્ધારિત)         |
| `custom`   | SQLite `eval_suites` + `eval_cases`માં સંગ્રહિત | હા (API/UI દ્વારા)         |

વર્તમાન બિલ્ટ-ઇન સ્યુટ્સ (`src/lib/evals/evalRunner.ts` જુઓ):

- `golden-set` — અભિવાદન/ગણિત/અનુવાદ/સલામતીમાં 10 બેઝલાઇન કેસ
- `coding-proficiency` — Python/JS/SQL/TS/બગ શોધ
- `reasoning-logic` — ન્યાયવાક્યો, શબ્દપ્રશ્નો, પેટર્ન ઓળખ
- `multilingual` — અનુવાદ અને ભાષાની ઓળખ
- `safety-guardrails` — PII, જેલબ્રેક, ઇનકાર, પૂર્વગ્રહ અંગે જાગૃતિ
- `instruction-following` — માત્ર JSON, ક્રમાંકિત યાદીઓ, ભાષાકીય મર્યાદાઓ
- `codex-comparison` — કમ્પેર મોડ માટે બનાવાયેલ સામ-સામેના કોડિંગ ટાસ્ક્સ

### કેસ

દરેક કેસમાં આ સામેલ હોય છે:

| ફીલ્ડ      | વર્ણન                                                            |
| ---------- | ---------------------------------------------------------------- |
| `id`       | સ્થિર ઓળખકર્તા (આઉટપુટ્સ અને મેટ્રિક્સની કી તરીકે વપરાય છે)      |
| `name`     | માનવ-વાંચનીય લેબલ                                                |
| `model`    | જ્યારે રન `suite-default` ટાર્ગેટિંગ વાપરે ત્યારે ડિફૉલ્ટ મૉડલ   |
| `input`    | `{ messages, max_tokens? }` — `/v1/chat/completions`ને મોકલાય છે |
| `expected` | `{ strategy, value }` — સ્કોરિંગ રૂબ્રિક (નીચે જુઓ)              |
| `tags`     | વૈકલ્પિક લેબલ્સ (દા.ત. `safety`, `pii`, `jailbreak`)             |

### ટાર્ગેટ

એક જ સ્યુટને અલગ-અલગ ટાર્ગેટ્સ સામે ચલાવી શકાય છે. ટાર્ગેટ સ્કીમા
`src/shared/validation/schemas.ts`માં `evalTargetSchema` છે:

| ટાર્ગેટનો પ્રકાર | `id`          | વર્તન                                                             |
| ---------------- | ------------- | ----------------------------------------------------------------- |
| `suite-default`  | `null`        | દરેક કેસ તેના બિલ્ટ-ઇન `model` ફીલ્ડનો ઉપયોગ કરે છે               |
| `model`          | મૉડલનું નામ   | દરેક કેસને એક સીધા મૉડલ મારફતે ફરજિયાત ચલાવો (દા.ત. `gpt-4o`)     |
| `combo`          | કૉમ્બોનું નામ | દરેક કેસને એક કૉમ્બો મારફતે ચલાવો (રાઉટિંગ એન્જિનની કસોટી કરે છે) |

`model` અને `combo` માટે `id` ફીલ્ડ આવશ્યક છે (Zod
`superRefine` દ્વારા અમલમાં મુકાયેલ). જ્યારે `compareTarget` આપવામાં આવે છે, ત્યારે બંને ટાર્ગેટ્સ અલગ હોવા જોઈએ —
રનર A/B તુલના માટે બંને રન્સને સમાન `runGroupId` હેઠળ સંગ્રહિત કરે છે.

## સ્કોરિંગ રૂબ્રિક્સ

`evaluateCase()` (evalRunner.ts) માં અમલમાં મૂકાયેલ:

| વ્યૂહરચના  | ત્યારે પાસ થાય જ્યારે…                                               |
| ---------- | -------------------------------------------------------------------- |
| `exact`    | `actualOutput === expected.value`                                    |
| `contains` | `actualOutput.toLowerCase().includes(expected.value.toLowerCase())`  |
| `regex`    | `new RegExp(expected.value).test(actualOutput)` truthy હોય           |
| `custom`   | `expected.fn(actualOutput, evalCase)` truthy પરત કરે (ફક્ત બિલ્ટ-ઇન) |

**નોંધ:** કસ્ટમ-ફંક્શન સ્કોરિંગ કોડ-વ્યાખ્યાયિત (બિલ્ટ-ઇન)
સ્યુટ્સ માટે આરક્ષિત છે, કારણ કે ફંક્શન્સને API દ્વારા સિરિયલાઇઝ કરી શકાતાં નથી.
વપરાશકર્તા દ્વારા બનાવેલા સ્યુટ્સ માટે `evalCaseBuilderSchema` ફક્ત
`contains | exact | regex` સ્વીકારે છે.

હાલમાં કોઈ LLM-એઝ-જજ અથવા એમ્બેડિંગ-આધારિત સમાનતા સ્કોરર નથી — તે
`evaluateCase()` માં એક સુઘડ એક્સ્ટેન્શન પોઇન્ટ બની શકે છે.

## ડેટાબેઝ સ્કીમા

ત્રણ ટેબલ્સ (માઇગ્રેશન્સ `030_create_eval_runs.sql` અને
`031_create_eval_suites.sql`):

| ટેબલ          | હેતુ                                                                                                                       |
| ------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `eval_suites` | કસ્ટમ સ્યુટ મેટાડેટા (`id`, `name`, `description`)                                                                         |
| `eval_cases`  | દરેક સ્યુટ માટેના કેસ — `input_json`, `expected_*`, `tags_json`                                                            |
| `eval_runs`   | ઐતિહાસિક રન્સ — `pass_rate`, `total`, `passed`, `failed`, `avg_latency_ms`, `summary_json`, `results_json`, `outputs_json` |

બિલ્ટ-ઇન સ્યુટ્સ DB માં સંગ્રહિત થતા **નથી**. તેઓ મેમરીમાં રહે છે અને
દર વખતે `evalRunner.ts` ઇમ્પોર્ટ થાય ત્યારે ફરીથી રજિસ્ટર થાય છે.

## REST API

તમામ એન્ડપોઇન્ટ્સ માટે મેનેજમેન્ટ ઑથ (`requireManagementAuth`) આવશ્યક છે — તેઓ
સાર્વજનિક પ્રોક્સી સપાટીનો ભાગ નથી.

| એન્ડપોઇન્ટ                    | મેથડ     | વર્ણન                                                         |
| ----------------------------- | -------- | ------------------------------------------------------------- |
| `/api/evals`                  | `GET`    | સ્યુટ્સ + તાજેતરના રન્સ + સ્કોરકાર્ડ + ટાર્ગેટ્સ + કીઝની યાદી |
| `/api/evals`                  | `POST`   | સ્યુટ ચલાવો (સિંગલ અથવા કમ્પેર) — સ્કીમા `evalRunSuiteSchema` |
| `/api/evals/{suiteId}`        | `GET`    | એક સ્યુટ મેળવો (બિલ્ટ-ઇન અથવા કસ્ટમ)                          |
| `/api/evals/suites`           | `POST`   | કસ્ટમ સ્યુટ બનાવો — સ્કીમા `evalSuiteSaveSchema`              |
| `/api/evals/suites/{suiteId}` | `GET`    | કસ્ટમ સ્યુટ મેળવો                                             |
| `/api/evals/suites/{suiteId}` | `PUT`    | કસ્ટમ સ્યુટ બદલો (કેસ ફરીથી ઇન્સર્ટ થાય છે)                   |
| `/api/evals/suites/{suiteId}` | `DELETE` | કસ્ટમ સ્યુટ અને તેના કેસ ડિલીટ કરો                            |

### સ્યુટ ચલાવવો

```bash
curl -X POST http://localhost:20128/api/evals \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "suiteId": "golden-set",
    "target": { "type": "combo", "id": "my-combo" },
    "apiKeyId": "optional-api-key-uuid"
  }'
```

વૈકલ્પિક ફીલ્ડ્સ:

- `outputs` — અગાઉથી ગણવામાં આવેલા આઉટપુટ્સનો `Record<caseId, string>`. જ્યારે
  આપવામાં આવે ત્યારે, રનર **ડિસ્પેચને છોડી દે છે** અને ફક્ત કૅશ કરેલા આઉટપુટ્સને સ્કોર કરે છે
  (ઑફલાઇન મૂલ્યાંકન માટે ઉપયોગી).
- `compareTarget` — સમાંતરમાં ચલાવવા માટેનો બીજો ટાર્ગેટ; સામસામે સરખામણી જોવા માટે
  બંને રન્સ જનરેટ કરેલ `runGroupId` શેર કરે છે.
- `apiKeyId` — ડિસ્પેચ કરેલા `/v1/chat/completions` કૉલ્સને ઑથેન્ટિકેટ કરવા માટે
  ઉપયોગમાં લેવાતી આંતરિક API કી. `REQUIRE_API_KEY` સક્ષમ હોય ત્યારે આવશ્યક છે.

### કસ્ટમ સ્યુટ બનાવવો

```bash
curl -X POST http://localhost:20128/api/evals/suites \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Production smoke",
    "description": "Quick sanity check before deploy",
    "cases": [
      {
        "name": "JSON shape",
        "model": "gpt-4o",
        "input": { "messages": [{ "role": "user", "content": "Reply with {\"ok\": true}" }] },
        "expected": { "strategy": "regex", "value": "\"ok\"\\s*:\\s*true" }
      }
    ]
  }'
```

## ડિસ્પેચ પાઇપલાઇન

`runEvalSuiteAgainstTarget()` (`src/lib/evals/runtime.ts`):

1. સ્યુટનું નિરાકરણ કરે છે (બિલ્ટ-ઇન અથવા કસ્ટમ).
2. દરેક કેસ માટે, કેસના `messages`, નિર્ધારિત `model`, `stream: false`, અને `max_tokens: 512` (અથવા કેસના ઓવરરાઇડ) સાથે `/v1/chat/completions` માટે `Request` બનાવે છે.
3. ચૅટ હૅન્ડલરને સીધું કૉલ કરે છે (ઇન-પ્રોસેસ — કોઈ વધારાનો HTTP હૉપ નહીં).
4. વિલંબતા કૅપ્ચર કરે છે અને `choices[0].message.content` અથવા Responses-APIના `output[]` પેલોડમાંથી ટેક્સ્ટ કાઢે છે.
5. `runSuite()` દ્વારા બધા આઉટપુટને સ્કોર કરે છે, પછી `saveEvalRun()` દ્વારા સાચવે છે.

કેસો **ક્રમિક રીતે** ચાલે છે. હાલમાં કોઈ કન્કરન્સી ફ્લૅગ નથી.

## ડૅશબોર્ડ

UI `Dashboard → Usage → Evals`
(`src/app/(dashboard)/dashboard/usage/components/EvalsTab.tsx`) પર ઉપલબ્ધ છે. ત્યાંથી તમે આ કરી શકો છો:

- કેસ-દર-કેસ પૂર્વાવલોકન સાથે બિલ્ટ-ઇન અને કસ્ટમ સ્યુટ્સ બ્રાઉઝ કરી શકો છો.
- કેસ બિલ્ડર વડે કસ્ટમ સ્યુટ્સ બનાવી/સંપાદિત/કાઢી શકો છો.
- ટાર્ગેટ (સ્યુટ ડિફૉલ્ટ્સ / મૉડલ / કૉમ્બો), વૈકલ્પિક રીતે બીજું `compareTarget`, વૈકલ્પિક રીતે API કી પસંદ કરીને, જરૂર મુજબ રન કરી શકો છો.
- રન ઇતિહાસ, દરેક કેસ માટે પાસ/ફેલ, વિલંબતા અને કૅપ્ચર કરેલા આઉટપુટ્સનું નિરીક્ષણ કરી શકો છો.
- દરેક `(suite, target)` સ્કોપ માટેના નવીનતમ રન પરથી એકત્રિત રોલિંગ સ્કોરકાર્ડ જોઈ શકો છો.

## Auto-Assessment RFC સાથેનો સંબંધ

એક અલગ, વધુ સંકુચિત અસેસમેન્ટ સબસિસ્ટમ `src/domain/assessment/`માં આવેલું છે
(લાઇવ સ્કોરિંગ એન્જિન માટે [AUTO-COMBO.md](../routing/AUTO-COMBO.md) પણ જુઓ).
આ સબસિસ્ટમ Auto Combo એન્જિનને લક્ષ્ય બનાવે છે — પ્રોવાઇડર્સ અને મૉડલ્સને આપમેળે સ્કોર કરે છે, જેથી અપસ્ટ્રીમ નિષ્ફળ જાય ત્યારે કૉમ્બોઝ પોતાની જાતે પુનઃસ્થાપિત થઈ શકે. તે પોતાના રનર, પોતાના વર્ગીકરણકાર અને પોતાના સ્કોરિંગ લૉજિકનો ઉપયોગ કરે છે.

અહીં દસ્તાવેજિત Evals ફ્રેમવર્ક એ **વધુ વ્યાપક, સામાન્ય હેતુ માટેની ટેસ્ટિંગ સપાટી** છે. મનસ્વી રિગ્રેશન સ્યુટ્સ, A/B સરખામણીઓ અને દરેક રિલીઝ માટેના સ્મોક ટેસ્ટ્સ માટે તેને પ્રાધાન્ય આપો. જ્યારે રાઉટિંગ નિર્ણયો પર અસર કરવા માટે રિયલ-ટાઇમ પ્રોવાઇડર હેલ્થની જરૂર હોય ત્યારે Auto-Assessment સબસિસ્ટમનો ઉપયોગ કરો.

## CI એકીકરણ

હાલમાં કોઈ સમર્પિત `eval:ci` npm સ્ક્રિપ્ટ નથી. જો તમે eval પરિણામોના આધારે રિલીઝને ગેટ કરવા માંગતા હો, તો બે માર્ગ છે:

- **HTTP માર્ગ**: સર્વર શરૂ કરો, જાણીતા `suiteId` + `target` સાથે `POST /api/evals`ને હિટ કરો અને પ્રતિસાદમાં `runs[].summary.passRate >= N` હોવાની ખાતરી કરો.
- **ઇન-પ્રોસેસ માર્ગ**: કોઈ સ્ક્રિપ્ટમાંથી `@/lib/evals/runtime` દ્વારા `runEvalSuiteAgainstTarget()` ઇમ્પોર્ટ કરો, ટેસ્ટ DB સામે ચલાવો અને પરત મળેલા `PersistedEvalRun.summary`ને તપાસો.

રૂટ અને ઇતિહાસને આવરી લેતા ટેસ્ટ્સ
`tests/unit/evals-route.test.ts` અને `tests/unit/evals-history.test.ts`માં છે.

## વિસ્તરણ બિંદુઓ

સામાન્ય ફેરફારો અને તે ક્યાં કરવા:

- **નવી સ્કોરિંગ વ્યૂહરચના** — `evaluateCase()` (`evalRunner.ts`)માંના `switch (evalCase.expected.strategy)` બ્લૉકને વિસ્તારો અને `src/lib/db/evals.ts`માં `EvalCaseStrategy` તથા `schemas.ts`માં `evalCaseBuilderSchema`ને વિસ્તૃત કરો.
- **નવું બિલ્ટ-ઇન સ્યુટ** — સ્યુટ ઑબ્જેક્ટ વ્યાખ્યાયિત કરો અને `evalRunner.ts`ના તળિયે `registerSuite()`ને કૉલ કરો. તે `listSuites()` દ્વારા આપમેળે શોધાઈ જશે.
- **કન્કરન્સી સાથે રન કરો** — `runEvalSuiteAgainstTarget()`માંના ક્રમિક `for` લૂપને મર્યાદિત `Promise.all`માં બદલો (હાલમાં કોઈ કન્કરન્સી નિયંત્રણ ઉપલબ્ધ નથી).
- **સ્ટ્રીમ/ટૂલ-કૉલ કેસો** — હાલમાં રનર ફરજિયાતપણે `stream: false` સેટ કરે છે. સ્ટ્રીમિંગ અથવા ટૂલ-અવેર મૂલ્યાંકન માટે `runtime.ts`માં ફેરફારો જરૂરી બનશે (સ્કોરિંગ પહેલાં SSE ચંક્સને કૅપ્ચર અને એકત્રિત કરવા).
