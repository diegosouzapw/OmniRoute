કૅટલૉગનું આવરણ મૂકે છે. તેનું અસ્તિત્વ એટલા માટે છે કે મફત-ટિયરનું પરિદૃશ્ય
રિલીઝની ગતિ કરતાં વધુ ઝડપથી બદલાય છે — પ્રદાતાઓ રિલીઝની વચ્ચે મફત ક્વોટા ઉમેરે છે, ઘટાડે છે અથવા
બંધ કરે છે, અને બેઝલાઇન કૅટલૉગને ફક્ત નવું વર્ઝન શિપ થાય ત્યારે જ તાજું કરી શકાય છે.

**આજે મફત હોય તેવી કોઈ પણ વસ્તુ રિમોટ ફીડને કારણે મફત રહેતી બંધ થતી નથી.** Radar ક્યારેય
બેઝલાઇન એન્ટ્રીને પેવૉલ પાછળ મૂકતું નથી; તે ફક્ત વાંચવાના સમયે મર્યાદા/સ્થિતિ ફીલ્ડને તાજાં કરે છે અને

મોડેલને સ્થાનિક રીતે છુપાવી શકે છે અને એ જ ડૅશબોર્ડમાંથી તેને પુનઃસ્થાપિત કરી શકે છે. બેઝલાઇન કૅટલૉગ પોતે
ડિસ્ક પર ક્યારેય બદલાતો નથી — નીચેના

## જાહેર જાહેરાત રીડર

સામાન્ય જાહેરાત રીડર Radar ફીચર ફ્લેગથી અલગ છે. ડૅશબોર્ડનું Home અને
Changelog વ્યૂઅર સાદા `GET` દ્વારા રિપોઝિટરીનું જાહેર `news.json`
`NEWS_JSON_URL` પરથી મેળવે છે (`src/shared/utils/releaseNotes.ts`). તેઓ કોઈ Radar સેટિંગ, પ્રોમ્પ્ટ, પ્રોવાઇડર
કન્ફિગરેશન, ઉપયોગ રેકોર્ડ અથવા સ્થાનિક ડિસમિસલ સ્થિતિ મોકલતા નથી.

`news.json`, `parseNewsPayload()` દ્વારા અમલમાં મૂકાયેલ બંધ v2 સ્કીમાનો ઉપયોગ કરે છે:

- `schemaVersion: 2` અને મર્યાદિત `items[]` સંગ્રહ;
- સ્થિર, અનન્ય જાહેરાત `id` મૂલ્યો;
- સ્પષ્ટ `active` અને ISO `publishedAt` ફીલ્ડ્સ;
- વૈકલ્પિક સ્થાનિકીકૃત નકલ સાથે આવશ્યક અંગ્રેજી નકલ;
- વૈકલ્પિક, ક્રેડેન્શિયલ-મુક્ત HTTPS લિંક્સ અને મંજૂર સૂચિમાંનું આઇકન;
- સૌથી નવા સક્રિયની પ્રથમ પસંદગી, લોકેલ ઉપલબ્ધ ન હોય તો અંગ્રેજીનો ઉપયોગ અને દરેક ID દીઠ સ્થાનિક ડિસમિસલ.

જૂના ફોર્ક્સ ખામીયુક્ત Changelog વ્યૂ વિના માઇગ્રેટ થઈ શકે તે માટે પાર્સર ભૂતપૂર્વ એકવચન
`{ active, title, message, ... }` સ્વરૂપને અસ્થાયી રૂપે સ્વીકારે છે. અમાન્ય ફીડ્સ નિષ્ક્રિય રહે છે. Radar લૉન્ચ
એન્ટ્રી `active: false` સાથે મોકલાય છે; તેને `true` માં બદલવું એ અલગ, મર્જ પછીની અને ડિપ્લોયમેન્ટ પછીની
રિલીઝ ક્રિયા છે અને તે `RADAR_ENABLED` અથવા સ્વતંત્ર ફીડ-સિંક ઑપ્ટ-ઇનને બદલતી નથી.

## ફ્લેગ: `RADAR_ENABLED` (ડિફૉલ્ટ રૂપે બંધ)

Radar, `RADAR_ENABLED` ફીચર ફ્લેગ દ્વારા છેડેથી છેડા સુધી નિયંત્રિત છે
(`src/shared/constants/featureFlagDefinitions.ts`, કેટેગરી `policies`,
`defaultValue: "false"`).

**જ્યારે ફ્લેગ બંધ હોય, ત્યારે આ સપાટી અસ્તિત્વમાં જ હોતી નથી:**

- સ્થાનિક મોડેલ-સ્થિતિ રીડ્સ અને રાઇટ્સ સહિતના બધા `/api/radar/*` એન્ડપોઇન્ટ્સ,
  કોઈપણ Radar મોડ્યુલને સ્પર્શતા પહેલાં `404` પરત કરે છે.
- ડૅશબોર્ડ સ્ક્રીન્સ (`/dashboard/radar`, `/dashboard/radar/setup`,
  `/dashboard/radar/combos`, `/dashboard/radar/offers`, `/dashboard/radar/intel`)
  `notFound()` રેન્ડર કરે છે.
- `getRadarCatalog()` (`src/lib/radar/index.ts`) અસ્પર્શિત બેઝલાઇન પરત કરે છે —
  સમાન એન્ટ્રી સંખ્યા, સમાન મૂલ્યો, દરેક એન્ટ્રી પર `origin: "baseline"` ટૅગ — અને ક્યારેય
  ફીડ કૅશ વાંચતું નથી.
- Radar માટે કોઈ નેટવર્ક કૉલ ક્યારેય થતો નથી; દરેક સિંક મોડ્યુલ `fetch`ને સ્પર્શતા પહેલાં
  `{ status: "disabled" }` પરત કરે છે.

આ એક કડક સુપરસેટ ગેટ છે: ફ્લેગ ચાલુ કરવાથી માત્ર _સ્ક્રીન્સ_ અનલૉક થાય છે,
તેના સિવાય કશું નહીં. તે ડેટા અપલોડ કરતું નથી, બૅકગ્રાઉન્ડ સિંક શરૂ કરતું નથી અને
રાઉટિંગ અથવા મોડેલ પસંદગી બદલતું નથી — નીચેનું અલગ ઑપ્ટ-ઇન જુઓ.

## ડેટા સિંક એક અલગ ઑપ્ટ-ઇન છે — ગોપનીયતાનું વચન

`RADAR_ENABLED` ચાલુ કરવાથી માત્ર UI અનલૉક થાય છે. ફીડ સિંક કરવા માટે
`radar_settings.opt_in`માં સંગ્રહિત બીજું, સ્વતંત્ર ઑપ્ટ-ઇન જરૂરી છે (`src/lib/db/radar.ts`,
માઇગ્રેશન `136_radar_cache_settings.sql`). કોઈપણ નેટવર્ક કૉલ કરતા પહેલાં `syncRadar()` ફ્લેગ _અને_
ઑપ્ટ-ઇન તપાસે છે:

```
ફ્લેગ બંધ       → { status: "disabled" }   — કોઈ નેટવર્ક કૉલ નહીં
ઑપ્ટ-ઇન ખોટું   → { status: "opt_out" }    — કોઈ નેટવર્ક કૉલ નહીં
```

જ્યારે બંને ચાલુ હોય, ત્યારે સિંક પાથ આ પ્રમાણે છે:

1. `x-omniroute-radar-schema: 2` અને વૈકલ્પિક
   `Authorization: Bearer <supporter key>` હેડર સાથે `GET <feed base URL>/v1/catalog/latest`
   (નીચે જુઓ). જ્યારે સ્કીમા હેડર ગેરહાજર હોય ત્યારે સર્વર્સ અલગથી
   સહી કરેલ v1 ટ્રાન્ઝિશન આર્ટિફેક્ટને ડિફૉલ્ટ બનાવે છે, જેથી જૂના ઇન્સ્ટૉલ કરેલા ક્લાયન્ટ્સને
   અપડેટ્સ મળતા રહે.
2. આ માત્ર ડાઉનલોડ માટેનો ઍપ્લિકેશન પ્રવાહ છે, પરંતુ તેમ છતાં તે HTTPS રિક્વેસ્ટ છે. હોસ્ટ કરાયેલ
   ઇન્ફ્રાસ્ટ્રક્ચરને સ્રોત IP જેવું સામાન્ય કનેક્શન મેટાડેટા મળે છે. જ્યારે સપોર્ટર
   કી કન્ફિગર કરેલી હોય, ત્યારે સિંક તે કીને Bearer હેડરમાં પણ મોકલે છે જેથી સર્વિસ
   એન્ટાઇટલમેન્ટ નિર્ધારિત કરી શકે. ઉપર દર્શાવેલી પુરાવાની સીમામાં ઓળખાયેલ ચોક્કસ પ્રાઇવેટ-સર્વર રિવિઝન પર,
   ફીડ-રિક્વેસ્ટ એકાઉન્ટિંગ મેન્યુઅલ દુરુપયોગ સમીક્ષા માટે કી હૅશ, એકંદર ઉપયોગ અને IPના
   દૈનિક રોટેટ થતા ટ્રન્કેટેડ HMACનો ઉપયોગ કરે છે; તે ટેબલ્સ કી કે IPને કાચા સ્વરૂપે સંગ્રહતી નથી.
   ઇન્ફ્રાસ્ટ્રક્ચર ઍક્સેસ લૉગ્સ અને એન્ક્રિપ્ટેડ ડિલિવરી આઉટબોક્સ અલગ ઑપરેશનલ
   સીમાઓ છે.
3. OmniRoute ક્યારેય પ્રોમ્પ્ટ્સ, પ્રતિસાદો, વાર્તાલાપો, પ્રોવાઇડર ક્રેડેન્શિયલ્સ, મોડેલ ટ્રાફિક,
   અપટાઇમ, લેટન્સી અથવા સ્થાનિક પ્રોવાઇડર કન્ફિગરેશન Radar સર્વિસને મોકલતું નથી.
4. પ્રતિસાદની ચકાસણી અને માન્યતા કરવામાં આવે છે અને તેને સ્થાનિક રીતે કૅશ કરવામાં આવે છે (
   [સુરક્ષા મોડેલ](#security-model) જુઓ). Radar પાસે સર્વર-સાઇડના બરાબર ચાર નેટવર્ક પાથ છે:
   કૅટલૉગ માટે `syncRadar()`, રેફરલ્સ માટે `syncRadarReferrals()`, અને
   માત્ર સપોર્ટર્સ માટેની ઑફર્સ અને Intel માટે `syncRadarOffers()` / `syncRadarIntel()`.

**સપોર્ટર કી** એક વૈકલ્પિક Bearer ટોકન (`radar_settings.supporter_key`) છે,
જે ફીડ સર્વિસને કયું ટિયર સર્વ કરવું તે નક્કી કરવા દે છે (
[ટિયર્સ](#tiers-community-and-live) જુઓ). તે:

- પ્રોવાઇડર ક્રેડેન્શિયલ્સ માટે ઉપયોગમાં લેવાતા સમાન AES-256-GCM `encrypt()`/`decrypt()`
  હેલ્પર્સ (`src/lib/db/encryption.ts`) વડે **એટ-રેસ્ટ એન્ક્રિપ્ટેડ** સ્વરૂપે સંગ્રહાય છે.
- `POST /api/radar/settings` (`{ supporterKey: "omr_" + 40 hex chars }`) દ્વારા સેટ થાય છે અને
  **ક્યારેય પાછી દર્શાવવામાં આવતી નથી** — પ્રતિસાદ માસ્ક કરેલું સ્વરૂપ (`omr_****abcd`) પરત કરે છે.
- તેને બદલવાથી અથવા સાફ કરવાથી કૅટલૉગ, રેફરલ્સ, ઑફર્સ અને Intel કૅશ પરમાણુ રીતે અમાન્ય થઈ જાય છે. આગામી
  સિંક/રીડ નવા એન્ટાઇટલમેન્ટને સર્વર-સાઇડ પર નિર્ધારિત કરે છે; કી સાચવવાથી પોતાની મેળે
  નેટવર્ક રિક્વેસ્ટ થતી નથી અથવા એકલ-ઉપયોગ ઍક્ટિવેશન કી વપરાતી નથી.
- સિંક GET પર ફીડ સર્વિસને Bearer ટોકન તરીકે મોકલાય છે — કી વિશેનું બીજું કંઈપણ
  ક્યારેય ક્લાયન્ટની બહાર જતું નથી.

PRની સંખ્યા ગમે તેટલી હોય, કોઈ contributor grant મળતું નથી. મર્યાદિત-અવધિની purchases, donations, contributor periods અને
manual grants વર્તમાન expirationથી સંચિત થાય છે; lifetime સર્વોપરી રહે છે. rankમાં ફેરફાર અગાઉથી
આપવામાં આવેલ સમયને ક્યારેય પૂર્વપ્રભાવથી રદ કરતો કે ટૂંકો કરતો નથી.

Hosted license વ્યક્તિગત છે અને વપરાશકર્તાને દર્શાવાતો નિયમ એક સમયે એક જ active installationનો છે. આ
release hardware lock હોવાનો **દાવો કરતી નથી**: OSS sync hardwareને fingerprint કરતું નથી અથવા
cryptographic device lease જાળવતું નથી. ઉપરના ચકાસાયેલા private-server revision પર અમલમાં મૂકાયેલ enforcement
entitlement validation સાથે manual-review signal છે, જે એક જ live key 24 કલાકમાં ચોથા
અલગ IP પરથી જોવામાં આવે ત્યારે સક્રિય થાય છે. તે signal ક્યારેય keyને આપમેળે block કે revoke કરતું નથી. Recovery
ખોવાયેલી keyને revoke કરીને બદલે છે અને હાલની expiration જાળવી રાખે છે; તે
ખરીદેલો અથવા મંજૂર કરેલો સમયગાળો ફરી શરૂ કરતું નથી.

Live offers હાથથી curate કરવામાં આવે છે અને બદલાઈ કે expire થઈ શકે છે. Opt-in screen ચોક્કસ
privacy boundary પણ જણાવે છે: signed catalog/referral metadata download થાય છે; valid key વધારામાં
signed offers અને Intelને unlock કરે છે; Bearer key અને સામાન્ય connection metadata hosted service સુધી પહોંચે છે;
prompts, responses, conversations, provider credentials, model traffic, uptime, latency અને સ્થાનિક
provider configuration પહોંચતાં નથી.

## સમર્થક કી મેળવવી

સક્રિયકરણ સ્ક્રીન (`/dashboard/radar`) સમર્થક કી **મેળવવા** માટેના બે પ્રવાહોની લિંક્સ આપે છે. OSS repo પોતે ક્યારેય કી જારી કરતું નથી, ચુકવણીનો કોડ ચલાવતું નથી અને **ક્યારેય કિંમત દર્શાવતું નથી** — કિંમત સંપૂર્ણપણે ગંતવ્ય પૃષ્ઠો પર નક્કી અને પ્રદર્શિત કરવામાં આવે છે, આ repoમાં નહીં (સ્પેસિફિકેશન નિર્ણય D14).

- **"હું યોગદાનકર્તા છું"** — `RADAR_CONTRIBUTOR_CLAIM_URL` (ડિફૉલ્ટ
  `https://radar.omniroute.online/auth/github`) ખોલે છે, જે ખાનગી Radar સર્વર પર હોસ્ટ કરાયેલો GitHub OAuth ક્લેમ પ્રવાહ છે. તે નવીનતમ પૂર્ણ સાપ્તાહિક રેન્કિંગ તપાસે છે: ટોચના 10ને 365 દિવસ મળે છે
  અને 11–100 સ્થાન ધરાવનારાઓને 90 દિવસ મળે છે. ટોચના 100ની બહાર, PRની સંખ્યા ક્યારેય ઍક્સેસ આપતી નથી; તેના બદલે પ્રવાહ અલગ star + follow એક-વખત-ઉપયોગ સ્તરની તપાસ કરે છે.
- **"પ્રોજેક્ટને સમર્થન આપો"** — `RADAR_SUPPORTER_PLANS_URL` (ડિફૉલ્ટ
  `https://radar.omniroute.online/planos`) ખોલે છે, જે એક-વખતના 6-મહિના, 1-વર્ષ અને
  આજીવન વિકલ્પો માટેનું હોસ્ટ કરાયેલું પૃષ્ઠ છે. OSS પૃષ્ઠ હજુ પણ કોઈ નાણાકીય મૂલ્ય દર્શાવતું નથી.

બંને URLs સર્વર-સાઇડ પર રિઝૉલ્વ થાય છે (`src/lib/radar/links.ts`, `RADAR_FEED_URL` જેવી જ env-override
પૅટર્ન) અને હાલના
`GET /api/radar/settings` પ્રતિસાદ (`contributorClaimUrl`, `supporterPlansUrl`) મારફતે ડૅશબોર્ડ સુધી પહોંચાડવામાં આવે છે — ક્લાયન્ટ કમ્પોનન્ટ પોતે ક્યારેય `process.env` વાંચતું નથી.

| ચલ                            | હેતુ                                                                                           |
| ----------------------------- | ---------------------------------------------------------------------------------------------- |
| `RADAR_CONTRIBUTOR_CLAIM_URL` | યોગદાનકર્તા-ક્લેમ URLને ઓવરરાઇડ કરે છે (ડિફૉલ્ટ `https://radar.omniroute.online/auth/github`). |
| `RADAR_SUPPORTER_PLANS_URL`   | સમર્થક-પ્લાન્સ URLને ઓવરરાઇડ કરે છે (ડિફૉલ્ટ `https://radar.omniroute.online/planos`).         |

### ખોવાયેલી સમર્થક કી પુનઃપ્રાપ્ત કરવી

હોસ્ટ કરેલી સેવાનો પુનઃપ્રાપ્તિ પ્રવેશ-બિંદુ `https://radar.omniroute.online/recover` છે; તેની લિંક પ્લાન્સ પૃષ્ઠ પરથી પણ આપવામાં આવી છે. પુનઃપ્રાપ્તિ સંપૂર્ણપણે OSS ક્લાયન્ટની બહાર રહે છે, કારણ કે સ્થાનિક ઇન્સ્ટોલેશન ક્યારેય ખરીદનાર/યોગદાનકર્તાનું ઈ-મેલ પ્રાપ્ત કરતું નથી અને તેની એન્ક્રિપ્ટ કરેલી સેટિંગ્સમાંથી મૂળ કી ફરી બનાવી શકતું નથી.

1. કી સાથે સંકળાયેલું ઈ-મેલ સબમિટ કરો. પુનઃપ્રાપ્ત કરી શકાય તેવું લાઇસન્સ અસ્તિત્વમાં હોય કે ન હોય, સેવા એક જ સ્વીકૃત પૃષ્ઠ પરત કરે છે, જેથી ફોર્મ એકાઉન્ટ્સની યાદી જાહેર કરતું નથી.
2. જો પાત્ર હોય, તો ડિલિવરી વર્કર ટૂંકા સમય માટે માન્ય, એક-વખત-ઉપયોગની લિંક મોકલે છે. તેને ખોલતાં જ
   ટોકનને અસ્થાયી એન્ક્રિપ્ટ કરેલી `HttpOnly`/`Secure` કૂકીમાં ખસેડવામાં આવે છે અને સ્વચ્છ
   `/recover` URL પર રીડાયરેક્ટ કરવામાં આવે છે; પૃષ્ઠમાં કોઈ ટોકન, ઈ-મેલ, જૂની કી કે બદલીની કી હોતી નથી.
3. રદ કરવાની પુષ્ટિ કરો. ખાનગી સેવા અગાઉની કી રદ કરે છે, સમાન પ્લાન/સમાપ્તિ સાથે બદલીની કી બનાવે છે અને એક જ ટ્રાન્ઝૅક્શનમાં તેને ઈ-મેલ માટે કતારમાં મૂકે છે. બદલીની કી ક્યારેય બ્રાઉઝરને પરત કરવામાં આવતી નથી.
4. બદલીની કી `/dashboard/radar`માં પેસ્ટ કરો. જૂની કી હવે `community`માં અવક્રમિત થવી જોઈએ; બદલીની કીએ ચકાસાયેલું `live` સિંક આપવું જોઈએ. એ જ પુનઃપ્રાપ્તિ લિંક ફરીથી ખોલવી સામાન્ય અમાન્ય/સમાપ્ત પ્રતિસાદ સાથે નિષ્ફળ જવી જોઈએ.

હોસ્ટ કરેલો પુનઃપ્રાપ્તિ રૂટ અને મેઇલ વર્કર કોડમાં હાજર હોઈ શકે છે, છતાં કોઈ ચોક્કસ ડિપ્લોયમેન્ટમાં ઉપલબ્ધ ન પણ હોય. સર્વર ડિપ્લોય ન થયું હોય, નિયંત્રિત પ્રાપ્તકર્તા સાથે ડિલિવરી પ્રદાતા કૉન્ફિગર ન થયો હોય અને સંપૂર્ણ એક-વખત-ઉપયોગ લિંકનું પરીક્ષણ ન થયું હોય ત્યાં સુધી આ પ્રવાહને પ્રોડક્શન માટે તૈયાર ન કહો.

એકવાર મુલાકાતી પાસે કી (`omr_` + 40 હેક્સ અક્ષરો) આવી જાય પછી, સક્રિયકરણ સ્ક્રીન
(`src/app/(dashboard)/dashboard/radar/page.tsx`) પર મુખ્ય માર્ગ તરીકે પેસ્ટ-કી ઇનપુટ હોય છે: કી પેસ્ટ કરીને સબમિટ કરવાથી એક જ કૉલમાં `POST /api/radar/settings`
(`{ optIn: true, supporterKey }`) મોકલાય છે — કી પેસ્ટ કરવાથી તે સેટ પણ થાય છે અને ઑપ્ટ-ઇન પણ થાય છે,
જેનાથી સ્ક્રીન અનલૉક થાય છે. ફૉર્મેટ (`omr_` + 40 હેક્સ અક્ષરો) પહેલાં ક્લાયન્ટ-સાઇડ પર
શેર્ડ `isValidSupporterKeyFormat()` હેલ્પર (`src/lib/radar/supporterKey.ts`) વડે UX સુવિધા તરીકે તપાસવામાં આવે છે; કોઈપણ સ્થિતિમાં સર્વરની Zod સ્કીમા અધિકૃત તપાસ છે. એકવાર
કી સેટ થઈ જાય પછી, સક્રિયકરણ સ્ક્રીન ખાલી ઇનપુટને બદલે માસ્ક કરેલું સ્વરૂપ (`GET /api/radar/settings`માંથી `supporterKeyMasked`) બતાવે છે, સાથે નવી કી પેસ્ટ કરવા માટે "કી બદલો" નિયંત્રણ હોય છે — મૂળ કી ફરી ક્યારેય પ્રદર્શિત થતી નથી. ઉપરનાં બે ક્લેમ/પ્લાન્સ બટનો શરૂઆતમાં કી _મેળવવાનો_ માર્ગ જ રહે છે; આ ઇનપુટ એ જગ્યા છે જ્યાં પહેલેથી કી ધરાવતો ઑપરેટર તેને સક્રિય કરે છે.

### શરૂઆતથી અંત સુધીનું સક્રિયકરણ અને માર્ગદર્શિત સેટઅપ

ખાનગી ફીડ સેવા અને આ OSS ક્લાયન્ટ વચ્ચે ઇરાદાપૂર્વક મર્યાદિત સીમા છે: સેવા સમર્થક કી જારી કરે છે અને તેની માન્યતા તપાસે છે, જ્યારે સ્થાનિક OmniRoute ઇન્સ્ટોલેશન કીને એન્ક્રિપ્ટ કરે છે,
સર્વર-સાઇડ પર સહી કરેલી આર્ટિફૅક્ટ્સ સિંક કરે છે અને પ્રદાતા સેટઅપમાં માર્ગદર્શન આપે છે. સહાયિત માન્યતા તપાસનો ક્રમ આ છે:

1. યોગદાનકર્તા ક્લેમ, plans/checkout, પુનઃપ્રાપ્તિ પ્રક્રિયા અથવા અધિકૃત ખાનગી સર્વર ઑપરેટર પાસેથી નવી જારી કરેલી અથવા પુનઃપ્રાપ્ત કરેલી કી મેળવો. મૂળ કીને લૉગ્સ,
   સ્ક્રીનશૉટ્સ, ઇશ્યૂ ટિપ્પણીઓ અથવા કમાન્ડ-લાઇન આર્ગ્યુમેન્ટ્સમાં પેસ્ટ કરશો નહીં.
2. સ્થાનિક OmniRoute ઇન્સ્ટોલેશન પર `RADAR_ENABLED` ફીચર ફ્લૅગ સક્રિય કરો. આ UIને ઉપલબ્ધ કરાવે છે,
   પરંતુ અલગ ઑપ્ટ-ઇન સાચવવામાં ન આવે ત્યાં સુધી નેટવર્ક પર કોઈ પ્રવૃત્તિ કરતું નથી.
3. `/dashboard/radar` ખોલો, કી પેસ્ટ કરો અને સક્રિય કરો. બ્રાઉઝર સ્થાનિક રીતે એક
   `POST /api/radar/settings` વિનંતી `{ optIn: true, supporterKey }` સાથે મોકલે છે; કી સ્થાનિક રીતે એન્ક્રિપ્ટ થાય છે અને
   પ્રતિસાદમાં માત્ર `omr_****<last4>` હોય છે.
4. સક્રિયકરણ સ્ક્રીનને તેનો કૅટલૉગ સિંક ચલાવવા દો અથવા **હમણાં સિંક કરો** પસંદ કરો. ખાતરી કરો કે પેજ
   `live`, ફીડ વર્ઝન અને ફેચ સમય દર્શાવે છે. પ્રમાણિત સ્થાનિક ડાયગ્નોસ્ટિક માટે,
   `GET /api/radar/status` કી પરત કર્યા વિના ઑપ્ટ-ઇન/કીની હાજરી અને ચાર કૅશ સ્થિતિઓ દર્શાવે છે.
   `POST /api/radar/sync-all` કૅટલૉગ, રેફરલ્સ, ઑફર્સ અને Intelને સ્પષ્ટપણે રિફ્રેશ કરી શકે છે.
5. `/dashboard/radar/setup?provider=<provider>` ખોલો. પ્રોવાઇડરની માલિકીના ક્રેડેન્શિયલ URLને અનુસરો,
   **API કી ઉમેરો** પસંદ કરો, પ્રોવાઇડરના વાસ્તવિક ફોર્મ દ્વારા સાચવો, માર્ગદર્શિકા પર પાછા ફરો અને
   **કનેક્શન ચકાસો** ચલાવો. માર્ગદર્શિકા સામાન્ય `/api/providers` અને
   `/api/providers/<connection-id>/test` રૂટ્સનો ઉપયોગ કરે છે; તે અલગ Radar ક્રેડેન્શિયલ બનાવતી નથી.
6. ઓછામાં ઓછાં બે સુસંગત પ્રોવાઇડર કનેક્શન્સ સક્રિય થયા પછી `/dashboard/radar/combos` ખોલો.
   સૂચવેલા ફૅમિલીની સમીક્ષા કરો અને હાલની કૉમ્બો API મારફતે કૉમ્બો બનાવો. ઑફર્સ અને
   Intel અલગ, માત્ર લાઇવ, સાઇન કરેલા કૅશ તરીકે જ રહે છે અને તેમને તેમના સમર્પિત Radar પેજ પર તપાસી શકાય છે.
7. `/dashboard/radar` અને સેટઅપ પેજ ફરી લોડ કરો. ઑપ્ટ-ઇન, માસ્ક કરેલી કીની સ્થિતિ, ચકાસાયેલ કૅશ, સાચવેલું
   પ્રોવાઇડર કનેક્શન અને ટેસ્ટ ક્રિયા ફરી લોડ કર્યા પછી પણ જળવાઈ રહેવી જોઈએ. મૂળ કી અને પ્રોવાઇડર ક્રેડેન્શિયલ
   હવે દેખાતા ન હોય ત્યાર બાદ જ પુરાવો કૅપ્ચર કરો.

કી સાચવવી એ પોતે લાઇવ હકદારીનો પુરાવો નથી. પુરાવો ખાનગી
સેવાના `GET /v1/license/check` પરિણામ, OSS કૅટલૉગ દ્વારા સર્વ કરાયેલા `live` ટિયર, ચકાસાયેલા સાઇન કરેલા
કૅશ અને વાસ્તવિક પ્રોવાઇડર કનેક્શન/ટેસ્ટ પ્રક્રિયાનું સંયોજન છે. અમાન્ય, સમાપ્ત થયેલી અથવા રદ કરેલી કી સુરક્ષિત રીતે
કૅટલૉગને `community` પર ડિગ્રેડ કરે છે; તેને સફળ લાઇવ-કી માન્યતા તરીકે રિપોર્ટ કરવી જોઈએ નહીં.

### ખાનગી ઍડમિન-પૅનલ લિંક

`RADAR_ADMIN_URL` વૈકલ્પિક રીતે Costs સાઇડબાર વિભાગમાં વપરાશકર્તા-લક્ષી
Radar આઇટમની તરત પછી **Radar Admin ↗** ઉમેરે છે. ઇરાદાપૂર્વક તેનું કોઈ ડિફૉલ્ટ નથી: જ્યારે વેરિએબલ
સેટ ન હોય અથવા અમાન્ય હોય, ત્યારે સ્ટેટિક સાઇડબાર, કમાન્ડ પૅલેટ અને સાઇડબાર-કસ્ટમાઇઝેશન સ્ક્રીનમાં કોઈ
ઍડમિન આઇટમ કે ખાનગી URL હોતું નથી.

મૂલ્ય સર્વર-સાઇડ પર રિઝૉલ્વ થાય છે અને મેનેજમેન્ટ-પ્રમાણિત
`GET /api/settings` પ્રતિસાદ મારફતે માત્ર પ્રમાણિત ડૅશબોર્ડ સેશનને અથવા સ્થાનિક નો-લૉગિન બૂટસ્ટ્રૅપ દરમિયાન વિશ્વસનીય
લૂપબૅક માલિકને મોકલવામાં આવે છે. CLI, આંતરિક-સેવા અને manage-scope API-કી
પ્રમાણીકરણને તે મળતું નથી. બાહ્ય લિંક બનાવતા પહેલાં બ્રાઉઝર પ્રતિસાદને ફરીથી માન્ય કરે છે,
અને લિંક `noopener noreferrer` સાથે ખૂલે છે.

ક્રેડેન્શિયલ-મુક્ત HTTPS ટનલ/tailnet URLનો ઉપયોગ કરો. સાદું HTTP માત્ર
`http://127.0.0.1:9351` જેવા લૂપબૅક SSH ફૉર્વર્ડ માટે સ્વીકાર્ય છે; અન્ય સ્કીમ્સ, એમ્બેડ કરેલા ક્રેડેન્શિયલ્સ, વિકૃત URLs અને
રિમોટ HTTP ગંતવ્યો નિષ્ફળ થવા પર સુરક્ષિત રીતે બંધ રહે છે અને નેવિગેશનને નિષ્ક્રિય રાખે છે.

## સુરક્ષા મોડેલ

### ચોક્કસ બાઇટ્સ પર Ed25519 હસ્તાક્ષર

ફીડ પેલોડ પર Ed25519 વડે હસ્તાક્ષર કરવામાં આવે છે. `verifyFeedBytes()`
(`src/lib/radar/verify.ts`) નેટવર્ક મારફતે પ્રાપ્ત થયેલા **પ્રતિસાદના ચોક્કસ બાઇટ્સ**
પર હસ્તાક્ષરની ચકાસણી કરે છે — ચકાસણી પહેલાં પેલોડને ક્યારેય ફરીથી સીરિયલાઇઝ
કરવામાં આવતો નથી, તેથી બાઇટ-દર-બાઇટ પુનઃએન્કોડિંગ હસ્તાક્ષર ચકાસણીને ચૂપચાપ
અમાન્ય બનાવી કે બાયપાસ કરી શકતું નથી. ચકાસણી નિષ્ફળ જાય (`invalid_signature`)
તો પેલોડને પાર્સ કે કૅશ કરવામાં આવે તે પહેલાં જ સિંક અટકી જાય છે.

### પિન કરેલી જાહેર કી + રોટેશન

ચકાસણી માટેની જાહેર કી `src/lib/radar/pinnedKeys.ts`
(`PINNED_FEED_PUBLIC_KEYS`) માં પિન કરેલી છે; તે એક ઍરે છે જેથી રોટેશન પહેલાં
નવી કી સૌથી આગળ ઉમેરી શકાય, જ્યારે અગાઉની કીથી હસ્તાક્ષર કરેલા જૂના કૅશ્ડ ફીડ
ફરીથી સિંક થાય ત્યાં સુધી માન્ય રહે.

### ફોર્ક-અનુકૂળ env ઓવરરાઇડ્સ

બે env vars ફોર્ક્સ અને સ્વ-હોસ્ટર્સને ડિફૉલ્ટ OmniRoute સેવાને બદલે ક્લાયન્ટને
તેમના પોતાના ફીડ તરફ દોરવાની મંજૂરી આપે છે — નીચે
[ફીડને સ્વ-હોસ્ટ કરવાની રીત](#how-to-self-host-a-feed) જુઓ:

| Var                 | હેતુ                                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| `RADAR_FEED_URL`    | ફીડનો બેઝ URL ઓવરરાઇડ કરે છે (ડિફૉલ્ટ `https://radar.omniroute.online`).                                |
| `RADAR_FEED_PUBKEY` | પિન કરેલી જાહેર કી (base64-DER SPKI અથવા PEM) ઓવરરાઇડ કરે છે અને બિલ્ટ-ઇન ઍરેને આ એકમાત્ર કીથી બદલે છે. |

### ન્યૂનતમ વર્ઝન

જો ડાઉનલોડ કરેલા ફીડનું `version` હાલમાં કૅશ કરેલા વર્ઝન કરતાં ચોક્કસપણે નવું ન
હોય, તો `syncRadar()` તેને નકારે છે (`compareVersions()`, ડૉટથી અલગ કરેલા
`YYYY.MM.DD.n` ની સરખામણી) — `{ status: "stale" }`. આ સમાધાનભંગ થયેલા અથવા
ખોટી રીતે કૉન્ફિગર કરેલા ફીડ એન્ડપોઇન્ટને ક્લાયન્ટને વધુ જૂના, અલગ રીતે
હસ્તાક્ષર કરેલા પેલોડ પર પાછો લઈ જતાં અટકાવે છે.

### બે તારીખો અને બંને શા માટે રાખવામાં આવે છે

કૅશ કરેલા ફીડમાં બે અલગ તારીખો હોય છે અને બંને રાખવાનો મુખ્ય હેતુ જ તેમની વચ્ચે
ગૂંચવણ થતી અટકાવવાનો છે:

| ફીલ્ડ         | ક્યાંથી આવે છે            | શેનો જવાબ આપે છે                          |
| ------------- | ------------------------- | ----------------------------------------- |
| `generatedAt` | હસ્તાક્ષરિત ફીડ બૉડીમાંથી | **ડેટા** કેટલો જૂનો છે                    |
| `fetchedAt`   | આ ઇન્સ્ટોલની ઘડિયાળમાંથી  | આ ઇન્સ્ટોલે તેને ક્યારે **ડાઉનલોડ** કર્યો |

થોડી મિનિટ પહેલાં મેળવેલા ફીડમાં કેટલાંક અઠવાડિયાં જૂના આંકડા હોઈ શકે છે, તેથી
માત્ર `fetchedAt` પરથી ઑપરેટર જાણી શકતો નથી કે ઓવરલે જે બેઝલાઇન પર સ્થિત છે તેના
કરતાં વધુ નવું છે કે નહીં. બંનેને `radar_feed_cache` માં કાયમી રીતે સાચવવામાં આવે
છે, `getRadarCatalog().meta` દ્વારા પરત કરવામાં આવે છે અને `GET /api/radar/status`
દ્વારા અલગથી રિપોર્ટ કરવામાં આવે છે. `generated_at` કૉલમ અસ્તિત્વમાં આવે તે પહેલાં
કૅશ કરેલી પંક્તિ (માઇગ્રેશન 163) પાછી વાંચવામાં આવે ત્યારે `null` આપે છે — અજ્ઞાત
મૂલ્ય ફેચ સમય ઉધાર લેવાને બદલે અજ્ઞાત જ રહે છે. `radar_referrals_cache` એ
માઇગ્રેશન 142 થી પોતાનું `generated_at` જાળવી રાખ્યું છે.

ઉપરોક્ત ન્યૂનતમ વર્ઝન બંને તારીખોમાંથી કોઈની નહીં, પરંતુ `version` ની સરખામણી કરે છે.

બે ખામીઓ બાકી છે અને બંને ઇરાદાપૂર્વક છે: ડૅશબોર્ડ હજી પણ માત્ર `Last fetched`
દર્શાવે છે, તેથી ત્યાં બિલ્ડ તારીખ વાંચવા માટે નવા લેબલની (અને તેની 41 લોકેલ
એન્ટ્રીઓની) જરૂર છે; અને offers તથા intel કૅશ કોઈ બિલ્ડ તારીખ જાળવતા નથી, ભલે
તેમની ફીડ સ્કીમામાં તે સમાવિષ્ટ હોય — તેથી `GET /api/radar/status` એ બંને માટે
`null` રિપોર્ટ કરવાને બદલે ફીલ્ડને છોડી દે છે, કારણ કે `null` નો અર્થ "અજ્ઞાત"
તરીકે સમજાશે.

### સ્કીમા માન્યતા

હસ્તાક્ષરની ચકાસણી **પછી** ડાઉનલોડ કરેલા બાઇટ્સને પાર્સ કરવામાં આવે છે અને
`RadarFeedSchema` (`src/lib/radar/feedSchema.ts`, એક Zod સ્કીમા) સામે માન્ય કરવામાં
આવે છે. સ્કીમા મેળ ન ખાય તો `{ status: "invalid_schema" }` પરત થાય છે અને કૅશને
સ્પર્શ કરવામાં આવતો નથી. દરેક વાંચન (`getRadarCatalog()`) વખતે કૅશ્ડ પેલોડને
સાવચેતીના પગલા તરીકે ફરીથી માન્ય કરવામાં આવે છે — દૂષિત અથવા હાથથી સંપાદિત કરેલી
કૅશ પંક્તિ સર્વ થવાને બદલે બેઝલાઇન પર પાછી જાય છે.

### પ્રતિસાદ કદની મર્યાદા (10 MB)

`syncRadar()` ફીડ પ્રતિસાદ બૉડી પર **10 MB ની કડક મર્યાદા** લાગુ કરે છે —
હસ્તાક્ષરિત ફીડ KB-સ્તરનો JSON દસ્તાવેજ છે, તેથી આ મર્યાદાથી મોટું કંઈપણ કાયદેસર
કૅટલોગ નહીં, પરંતુ ખોટી રીતે કૉન્ફિગર કરેલા અથવા દુર્ભાવનાપૂર્ણ
`RADAR_FEED_URL` (અથવા નકામો ડેટા સર્વ કરતા અપસ્ટ્રીમ) તરફ સંકેત કરે છે.
અમલીકરણ બે સ્તરે થાય છે:

1. જ્યારે હેડર પહેલેથી જ મર્યાદાથી વધુ મૂલ્ય જાહેર કરે ત્યારે `Content-Length`
   પ્રીફ્લાઇટ ચકાસણી બૉડીને સંપૂર્ણપણે વાંચવાનું ટાળી દે છે.
2. બૉડી વાંચતી વખતે ચાલતી કુલ-કદની ચકાસણી `Content-Length` ગેરહાજર હોય અથવા
   વાસ્તવિક કદ કરતાં ઓછું દર્શાવે ત્યારે પણ મર્યાદા લાગુ કરે છે — માત્ર હેડર પર
   ક્યારેય વિશ્વાસ કરવામાં આવતો નથી. સંચિત ચંક્સને જોડવાથી ત્યારબાદની Ed25519
   હસ્તાક્ષર ચકાસણી માટે જરૂરી ચોક્કસ બાઇટ્સ જળવાઈ રહે છે.

મર્યાદા ઓળંગવાથી `{ status: "too_large" }` પરત થાય છે અને કૅશને સ્પર્શ કરવામાં
આવતો નથી; આ દરેક અન્ય સિંક નિષ્ફળતા (`invalid_signature`, `invalid_schema`,
`stale`) જેવી જ બિન-વિનાશક પદ્ધતિને અનુસરે છે.

## સ્તરો: `community` અને `live`

ફીડ સ્કીમામાં `tier: "community" | "live"` ફીલ્ડ હોય છે, જે વિનંતીના આધારે ફીડ સેવા દ્વારા **સર્વર-સાઇડ**
નક્કી કરવામાં આવે છે (supporter keyની હાજરી અને માન્યતા)
— ક્લાયન્ટ ક્યારેય પોતાનો સ્તર નક્કી કરતું નથી.

- **`community`** — સૌથી તાજા ડેટાથી આશરે 30 દિવસ પાછળ રહેલી મફત કેટલોગ. અનધિકૃત અથવા અમાન્ય-key ધરાવતી વિનંતીને આ મળે છે.
- **`live`** — સૌથી તાજી કેટલોગ, જે માન્ય supporter key ધરાવતી વિનંતીઓને આપવામાં આવે છે.

**અમાન્ય અથવા સમયસમાપ્ત supporter keyનું સ્તર ઘટીને `community` થાય છે — તે ક્યારેય
ભૂલ નથી.** સિંક પાથ ફક્ત signature/schema/version નિષ્ફળતાઓ (તમામ
પુનઃપ્રાપ્ત કરી શકાય તેવી અને cached state માટે બિન-ઘાતક) અને સફળ `{ status:
"updated", version, tier }` વચ્ચે ભેદ કરે છે. ક્લાયન્ટે સંભાળવો પડે એવો કોઈ સ્તર-વિશિષ્ટ error path
નથી.

### સેવા અપાયેલ સ્તર signed bodyમાંથી નહીં, પરંતુ response headerમાંથી આવે છે

signed feed **body**નું `tier` ફીલ્ડ હંમેશાં `"live"` હોય છે — feed service દરેક version માટે
**બે signed artifacts** મોકલે છે: liveમાં વર્તમાન campaigns સામેલ હોય છે અને communityમાં
તે છોડવામાં આવે છે. દરેક artifact તેના પોતાના ચોક્કસ bytes પર signed હોય છે. તેમ છતાં body
entitlementના નિર્ણય તરીકે કામ કરતું નથી; વિનંતી માટે વાસ્તવમાં પસંદ કરાયેલ સ્તર
**`x-omniroute-feed-tier` response header**માં મોકલવામાં આવે છે, જે વિનંતીની
`Authorization` key પરથી server-side નક્કી થાય છે.

`syncRadar()` (`src/lib/radar/sync.ts::parseServedTierHeader()`) એ એકમાત્ર સ્થાન છે
જે ક્લાયન્ટે વિશ્વાસ કરવો જોઈએ તે સ્તર નક્કી કરે છે:

1. `x-omniroute-feed-tier`ને `RadarTierSchema` (Zod) વડે parse કરો — header ગેરહાજર હોય, અથવા
   તેનું value ચોક્કસપણે `"community"` કે `"live"` ન હોય, તો તેને **હાજર
   નથી** એમ ગણવામાં આવે છે (તેના મૂળ સ્વરૂપે cache/UIમાં ક્યારેય વિશ્વાસ કરવામાં આવતો નથી; આમાં એવા જૂના feed
   servers પણ આવરી લેવાય છે જે header પહેલાંના છે).
2. ફક્ત ત્યારે જ signed bodyના `tier` ફીલ્ડ (હંમેશાં `"live"`) પર fallback કરો, જ્યારે પગલું 1
   કોઈ પરિણામ ન આપે.
3. નક્કી થયેલું tier cacheમાં સંગ્રહાય છે અને `{ status: "updated",
version, tier }` તરીકે પરત કરવામાં આવે છે — dashboard આ જ value બતાવે છે, raw body
   field ક્યારેય નહીં.

## વાંચન-સમયના overlay mergeના નિયમો

`applyFeed()` (`src/lib/radar/applyFeed.ts`) cached feedને static baselineની **ઉપર**
**વાંચન સમયે**, `getRadarCatalog()`ની અંદર merge કરે છે. baseline array
(`FREE_MODEL_BUDGETS`) ક્યારેય બદલવામાં આવતું નથી — દરેક call પર નવું `MergedEntry[]` ગણવામાં
આવે છે.

અગ્રતાક્રમ પ્રમાણે ચાર નિયમો:

1. **Feed ક્યારેય local overrideને overwrite કરતું નથી.** દરેક field માટે: જો operatorએ
   entryનું કોઈ field customize કર્યું હોય (`localOverrides` map, જે `provider:modelId`થી keyed છે),
   તો તે ચોક્કસ field માટે feedનું value છોડી દેવામાં આવે છે — operatorનું value પ્રભાવી રહે છે.
2. **`enabled: false` provenance સાથે entryને disable કરે છે.** કોઈ entryને બંધ કરતી
   feed entry merged result પર `enabled: false` અને `disabledBy: "radar"` સેટ કરે છે,
   જેથી UI સમજાવી શકે કે entry ઉપલબ્ધમાંથી disabled _શા માટે_ થઈ.
3. **Feedમાં હાજર ન હોય તેવી user-added entry અસ્પર્શિત રહે છે.** જે entries
   ફક્ત baselineમાં અસ્તિત્વ ધરાવે છે (અથવા સ્થાનિક રીતે ઉમેરાઈ હતી) અને જેમની અનુરૂપ feed
   entry નથી, તે કોઈ ફેરફાર વિના પસાર થાય છે.
4. **Tombstoned entry ક્યારેય પુનઃસ્થાપિત થતી નથી.** જો operatorએ સ્પષ્ટપણે કોઈ
   entry delete કરી હોય (`tombstones` set), તો પછીની versionમાં feed દ્વારા તે
   `provider:modelId` ફરી ઉમેરવાથી તે પાછી આવતી નથી.

editable fields અને tombstones
`radar_local_model_state` (migration `153_radar_local_model_state.sql`)માં સંગ્રહિત રહે છે. public DB
adapter (`src/lib/db/radar.ts`) તે rowsને `applyFeed()` દ્વારા ઉપયોગમાં લેવાતા `localOverrides` map અને
`tombstones` setમાં રૂપાંતરિત કરે છે; production `getRadarCatalog()` flag, cache અને schema gates
પાસ થયા પછી તે state load કરે છે. ફક્ત `displayName` અને `enabled`
operator-editable છે. Provider/model identity, feed provenance, quota, capabilities, ToS,
અને setup data આ surface દ્વારા લખી શકાતા નથી.

dashboard ચાર local actions ઉપલબ્ધ કરાવે છે:

- **Edit** local display name અને enabled state બદલે છે.
- **Reset local changes** tombstone બદલ્યા વિના બંને editable fields સાફ કરે છે.
- **Hide** tombstone બનાવે છે, જેથી પછીના feed updates rowને ફરી બનાવી ન શકે.
- **Restore** tombstone દૂર કરે છે; અલગથી save કરાયેલ કોઈપણ override અમલમાં રહે છે.

Feedનું `enabled: false` safety exception તરીકે યથાવત રહે છે: તે stale local
`enabled: true` પર પ્રભાવી થાય છે, merged entryને disabled રાખે છે અને `disabledBy: "radar"` નોંધે છે.

Catalog publications `schemaVersion: 2` વાપરે છે. `contextWindow` અને `tools`, `vision`, તથા
`thinking`માંથી દરેક સ્વતંત્ર રીતે `number | null` / `boolean | null` હોય છે: `null`નો અર્થ અજ્ઞાત છે, જ્યારે
`false`નો અર્થ એ છે કે D16 દ્વારા પુષ્ટિ થયેલ અધિકૃત provider source સ્પષ્ટપણે જણાવે છે કે capability ગેરહાજર છે.
Internal OmniRoute registry/model-spec flagsને ક્યારેય સીધા feed facts તરીકે પ્રસ્તુત કરવામાં આવતા નથી. ક્લાયન્ટ
હજુ પણ v1 snapshots સ્વીકારે છે; જૂના builderએ ગેરહાજરીના placeholder તરીકે `false` વાપર્યું હોવાથી, v1 `false`ને
અજ્ઞાત તરીકે normalize કરવામાં આવે છે, જ્યારે v1 `true` હકીકત તરીકે યથાવત રહે છે. અજ્ઞાત schema versions fail closed થાય છે અને
છેલ્લું માન્ય cache ઉપલબ્ધ રહે છે. non-null context/capability ધરાવતા દરેક v2 model પાસે
credential-free HTTPS `metadataEvidenceUrls[]` હોવું આવશ્યક છે; અન્યથા schema validation નિષ્ફળ જાય છે અને cache
બદલવામાં આવતું નથી. catalog table ત્રણે statesને `✓`, `✕`, અને `?` તરીકે render કરે છે.

### Guided combos અને MCP access

પુષ્ટિ થયેલ `familyId` values read-time overlayમાંથી યથાવત પસાર થાય છે અને pure
`buildRadarComboSuggestions()` module (`src/lib/radar/comboSuggestions.ts`)ને ચલાવે છે. કોઈ familyનું suggestion
ફક્ત ત્યારે જ આપવામાં આવે છે જ્યારે ઓછામાં ઓછા બે અલગ providers પાસે active connections હોય અને તેઓ ચોક્કસ curated model
ID ઉપલબ્ધ કરાવતા હોય. Disabled models, inactive providers, ગેરહાજર model IDs, singleton families અને અસ્પષ્ટ
alias/prefix matches fail closed થાય છે. Suggestions હાલની `priority` strategy વાપરે છે અને
સૌથી મોટા પુનરાવર્તિત monthly budgetને પહેલાં ગોઠવે છે; UI તેમને ફક્ત `POST /api/combos` દ્વારા જ બનાવે છે.

માર્ગદર્શિત UI `/dashboard/radar/combos` પર ઉપલબ્ધ છે. તે ફક્ત સ્થાનિક
`GET /api/radar/catalog` અને `GET /api/combos/builder/options` endpoints વાંચે છે. તે ક્યારેય Radar sync ટ્રિગર કરતું નથી,
provider credentials વાંચતું નથી અથવા combo databaseમાં સીધું લખતું નથી.

MCP clients `omniroute_radar_catalog` (`read:radar`) વડે સમાન સ્થાનિક projection વાંચી શકે છે. વૈકલ્પિક
`provider`, `familyId`, અને `enabledOnly` filtersનું મૂલ્યાંકન એક સ્થાનિક
`GET /api/radar/catalog` read પછી કરવામાં આવે છે. તેના મર્યાદિત outputમાં catalog metadata ઉપરાંત provider/model,
display name, `familyId`, quota, capabilities, enabled state, origin, અને `disabledBy` સામેલ હોય છે; setup URLs,
steps, connections, e-mail addresses, keys, અને referral data ક્યારેય પરત કરવામાં આવતાં નથી. આ tool
ફક્ત વાંચવા માટે છે અને ક્યારેય `/api/radar/sync`ને invoke કરતું નથી.

### ઉદ્ભવ સૂચકો

દરેક merged entryમાં `origin` field હોય છે, જેને UI badge તરીકે render કરે છે:

- `"baseline"` — static release catalogમાંથી કોઈ ફેરફાર વિના લેવામાં આવેલ.
- `"radar"` — એક અથવા વધુ fields feed દ્વારા refresh કરવામાં આવ્યાં હતાં.
- `"local"` — operatorએ આ entry પર ઓછામાં ઓછો એક local override કર્યો છે (નિયમ 1 અનુસાર local
  overrides હંમેશાં feed કરતાં પ્રાથમિકતા મેળવે છે, પછી ભલે feedમાં કંઈપણ જણાવાયું હોય).

## સ્થાનિક સપાટીઓ — ક્યારેય feed proxy નહીં

નીચેના સ્થાનિક Radar route families `src/app/api/radar/` હેઠળના UIને આધાર આપે છે:

| Route                          | Method | હેતુ                                                                                                                    |
| ------------------------------ | ------ | ----------------------------------------------------------------------------------------------------------------------- |
| `/api/radar/catalog`           | GET    | સ્થાનિક cacheમાંથી મર્જ કરેલ catalog (`getRadarCatalog()`) પરત કરે છે.                                                  |
| `/api/radar/sync`              | POST   | server-side `syncRadar()` ટ્રિગર કરે છે; પરિણામરૂપ status પરત કરે છે.                                                   |
| `/api/radar/settings`          | GET    | `{ optIn, hasSupporterKey, supporterKeyMasked }` પરત કરે છે — ક્યારેય raw key નહીં.                                     |
| `/api/radar/settings`          | POST   | opt-in અને/અથવા (encrypted) supporter key સેટ કરે છે.                                                                   |
| `/api/radar/referrals`         | GET    | સ્થાનિક cacheમાંથી `{ fixed, campaigns, tier }` પરત કરે છે — નીચેની [Referral links](#referral-links-free-credits) જુઓ. |
| `/api/radar/offers`            | GET    | ચકાસાયેલ સ્થાનિક live cacheમાંથી સક્રિય offers પરત કરે છે; supporter key ક્યારેય પરત કરતું નથી.                         |
| `/api/radar/offers/sync`       | POST   | server-side, live-key-only `syncRadarOffers()` pipeline ટ્રિગર કરે છે.                                                  |
| `/api/radar/intel`             | GET    | ચકાસાયેલ સ્થાનિક live Intel તથા supporter-recognition boolean પરત કરે છે; ક્યારેય identity અથવા key નહીં.               |
| `/api/radar/intel/sync`        | POST   | server-side, live-key-only `syncRadarIntel()` pipeline ટ્રિગર કરે છે.                                                   |
| `/api/radar/status`            | GET    | secrets વિના catalog, referrals, offers અને Intel માટે read-only સ્થાનિક settings/cache status પરત કરે છે.              |
| `/api/radar/sync-all`          | POST   | ચારેય server-side sync modules ચલાવે છે અને દરેક feed માટે અલગ status પરત કરે છે.                                       |
| `/api/radar/local-model-state` | GET    | edit/restore controls માટે persisted overrides અને tombstonesની યાદી આપે છે.                                            |
| `/api/radar/local-model-state` | PATCH  | ચકાસાયેલ `displayName`/`enabled` override fields સેટ અથવા સાફ કરે છે.                                                   |
| `/api/radar/local-model-state` | PUT    | `{ provider, modelId, tombstoned }` સાથે tombstone બનાવે અથવા દૂર કરે છે.                                               |
| `/api/radar/local-model-state` | DELETE | કોઈપણ tombstone જાળવી રાખીને editable override fields સાફ કરે છે.                                                       |

**કડક નિયમ: આ routes ક્યારેય feed serviceને proxy કરતા નથી.** browser હંમેશાં માત્ર
સ્થાનિક OmniRoute server સાથે જ સંચાર કરે છે. Radar serviceને સ્પર્શતા ચાર modules
`src/lib/radar/sync.ts` (catalog), `src/lib/radar/referralsSync.ts` (referrals), અને
`src/lib/radar/offersSync.ts` (offers) ઉપરાંત `src/lib/radar/intelSync.ts` (Intel) છે; બધા
server-side ચાલે છે, ક્યારેય client-side નહીં. આ રીતે
feed URL અને કોઈપણ supporter key સંપૂર્ણપણે client-facing network trafficથી બહાર રહે છે.

જ્યારે `RADAR_ENABLED` બંધ હોય ત્યારે બધા Radar endpoints `404` પરત કરે છે (ઉપર
[Flag](#flag-radar_enabled-default-off) જુઓ), અને repo-wide error-sanitization નિયમ
(`docs/security/ERROR_SANITIZATION.md`) મુજબ route error responsesને
`buildErrorBody()`/`sanitizeErrorMessage()` મારફતે મોકલે છે.

### પ્રમાણીકરણ

બધા Radar endpointsને `isAuthenticated()`
(`src/shared/utils/apiAuth.ts`) મારફતે પ્રમાણીકરણ જરૂરી છે — dashboard session cookie અથવા management-scoped
API key, એ જ gate જે બાકીના `/api/settings/*`ને સુરક્ષિત કરે છે. flag-off
`404` તપાસ હંમેશાં auth તપાસની **પહેલાં** ચાલે છે, જેથી `RADAR_ENABLED`
બંધ હોય તેવું install byte-identical રહે (surface અસ્તિત્વમાં નથી એ જાણવા માટે auth prompt નહીં);
flag ચાલુ થયા પછી, કોઈપણ DB read અથવા
write પહેલાં unauthenticated requestને `401` મળે છે. auth state ગમે તે હોય,
`GET /api/radar/settings` raw supporter key ક્યારેય પરત કરતું નથી — માત્ર masked form અને `hasSupporterKey` boolean પરત કરે છે.

## સમર્થક ઑફરો

ઑફરો તેમના પોતાના હસ્તાક્ષરિત આર્ટિફેક્ટ, `GET /v1/offers/latest`, નો ઉપયોગ કરે છે અને ક્યારેય કેટલોગ અથવા
રેફરલ્સ કૅશ શેર કરતી નથી. સર્વર એન્ડપોઇન્ટને માન્ય લાઇવ સમર્થક Bearer કીની જરૂર પડે છે; કોઈ
કમ્યુનિટી ફૉલબૅક નથી. તેથી, જ્યારે ફીચર ફ્લૅગ બંધ હોય, ઑપરેટરે સંમતિ આપી ન હોય અથવા કોઈ સમર્થક કી કૉન્ફિગર કરેલી ન હોય ત્યારે
`syncRadarOffers()` નેટવર્ક સુધી પહોંચતા પહેલાં જ અટકી જાય છે.

સફળ GET પછી, ક્લાયન્ટ ચોક્કસ પ્રતિસાદ બાઇટ્સ પર Ed25519 હસ્તાક્ષર ચકાસે છે,
`RadarOffersFeedSchema` ને માન્ય કરે છે, હસ્તાક્ષરિત બૉડી અને
`x-omniroute-feed-tier` હેડર બંનેમાં `live` હોવું જરૂરી બનાવે છે, માત્ર બિંદુઓવાળા વધુ નવા વર્ઝનને સ્વીકારે છે અને તે પછી જ
`radar_offers_cache` ને ઍટોમિક રીતે બદલે છે (માઇગ્રેશન `144_radar_offers_cache.sql`). અન્ય ફીડ્સ દ્વારા ઉપયોગમાં લેવાતી સમાન 10 MB
હેડર-વત્તા-સ્ટ્રીમ મર્યાદા અહીં પણ લાગુ પડે છે. હસ્તાક્ષર, સ્કીમા, ટિયર, રીપ્લે, કદ, HTTP
અને નેટવર્ક નિષ્ફળતાઓમાં છેલ્લી ચકાસાયેલી કૅશ જળવાઈ રહે છે.

બંધ ઑફર સ્વરૂપ ત્રણ તુલનાત્મક લાભ પ્રકારોને સપોર્ટ કરે છે: બેસિસ પૉઇન્ટ્સમાં ટકાવારી, ચલણના નાના એકમોમાં
ક્રેડિટ અથવા ટ્રાયલ દિવસો. પાર્ટનર ઑફરમાં સમાન પ્રકારની જાહેર બેઝલાઇન સામેલ હોવી જરૂરી છે અને
તેનો લાભ ચુસ્તપણે વધુ હોવો આવશ્યક છે; સત્તાવાર ઑફરો માટે કોઈ પાર્ટનર બેઝલાઇન હોતી નથી. URLs
ઓળખપત્ર-રહિત HTTPS હોવા જોઈએ. `getRadarOffers()` રક્ષણાત્મક રીતે કૅશ કરેલા પેલોડને ફરીથી માન્ય કરે છે અને
દરેક સ્થાનિક રીડ વખતે સમયસમાપ્ત થયેલી એન્ટ્રીઓને ફિલ્ટર કરે છે; `/dashboard/radar/offers` રેન્ડર કરતાં પહેલાં ફરીથી સમયસમાપ્તિ ફિલ્ટર કરે છે,
ઉપલબ્ધ હોય ત્યારે પોર્ટુગીઝ લખાણ અને ન હોય ત્યારે અંગ્રેજી ફૉલબૅકનો ઉપયોગ કરે છે તથા પાર્ટનર ઑફરોને સ્પષ્ટ રીતે લેબલ કરે છે.

બ્રાઉઝર માત્ર સ્થાનિક રૂટ્સને કૉલ કરે છે: તે માસ્ક કરેલા સેટિંગ્સ સ્નૅપશૉટને વાંચે છે,
સર્વર-સાઇડ પર રિફ્રેશ કરવા માટે `POST /api/radar/offers/sync` ને વિનંતી કરે છે અને પછી `GET /api/radar/offers` વાંચે છે. કી વિના,
તે ફીડ વિનંતી કરવાનો પ્રયાસ કરવાને બદલે હાલની યોગદાનકર્તા/સપોર્ટ લિંક્સ બતાવે છે. બાહ્ય
ઑફર લિંક્સ `noopener noreferrer` સાથે નવા ટૅબમાં ખૂલે છે. આ રિલીઝમાં કોઈ `radar_offers` MCP ટૂલ ઉપલબ્ધ કરાવવામાં આવ્યું નથી.

## Radar Intel, સમર્થક બૅજ અને CLI

Intel એ `GET /v1/intel/latest` પર ઉપલબ્ધ હસ્તાક્ષરિત આર્ટિફેક્ટ છે. બંધ `RadarIntelFeedSchema`
માત્ર ખાનગી ક્યુરેટર દ્વારા પુષ્ટિ કરેલી તુલનાઓ પરથી મેળવેલા Radar-માલિકીના ELO રૅન્કિંગ્સ અને હસ્તાક્ષરિત
કેટલોગ સ્નૅપશૉટ્સ પરથી મેળવેલા તથ્યાત્મક કેટલોગ ઉંમર/સંખ્યા તફાવતોને સ્વીકારે છે. પદ્ધતિમાં પ્રારંભિક
રેટિંગ 1000 અને K=32 નિશ્ચિત છે. જ્યારે કોઈ તુલનાની પુષ્ટિ થઈ ન હોય ત્યારે ખાલી રૅન્કિંગ માન્ય છે; ક્લાયન્ટ
ક્યારેય કૃત્રિમ રીતે કોઈ રૅન્કિંગ બનાવતો નથી.

`syncRadarIntel()` ઑફરો જેવી જ સર્વર-સાઇડ Bearer, 30-સેકન્ડની સમયમર્યાદા, 10 MiB સ્ટ્રીમ કરેલી મર્યાદા,
ચોક્કસ-બાઇટ Ed25519 ચકાસણી, કડક સ્કીમા, `live` બૉડી/હેડર આવશ્યકતા, વર્ઝન ફ્લોર અને
છેલ્લી-સારી-કૅશ જાળવણી લાગુ કરે છે. ચકાસાયેલો લાઇવ સ્નૅપશૉટ સંગ્રહિત થયા પછી, ક્લાયન્ટ
`radar:<sha256(supporter key)>` બનાવે છે, માત્ર તે એકમાર્ગી ઓળખ સંગ્રહે છે અને સમર્પિત
`radar_supporter` માન્યતા ઇવેન્ટ ઉત્સર્જિત કરે છે. તેનો `radar-supporter` બૅજ ઇડેમ્પોટન્ટ છે અને શૂન્ય XP આપે છે;
તે ક્યારેય લીડરબોર્ડ્સ અપડેટ કરતો નથી અથવા `token_share` નો પુનઃઉપયોગ કરતો નથી. `/dashboard/radar/intel` બૅજને
માત્ર ચકાસાયેલા સ્થાનિક કૅશ મેટાડેટામાંથી રેન્ડર કરે છે.

CLI `omniroute radar status` અને `omniroute radar sync` ઉપલબ્ધ કરાવે છે. બંને ફક્ત
સ્થાનિક OmniRoute API સાથે સંચાર કરે છે. `status` ફક્ત વાંચવા માટેનો `GET /api/radar/status` કરે છે; `sync` એક
`POST /api/radar/sync-all` મોકલે છે અને દરેક ફીડ દીઠ પરિણામ પ્રિન્ટ કરે છે. કોઈ પણ કમાન્ડ સમર્થક કીને વાંચતી, સ્વીકારતી કે પ્રિન્ટ કરતી નથી
અને કોઈ પણ Radar સેવાનો સીધો સંપર્ક કરતી નથી.

## રેફરલ લિંક્સ (મફત ક્રેડિટ્સ)

રેફરલ લિંક્સ **સ્વતંત્ર, હંમેશાં અદ્યતન** ફીડમાંથી આપવામાં આવે છે —
`GET /v1/referrals/latest` — જે કેટલોગ ફીડથી અલગ છે. આ ઇરાદાપૂર્વક છે: કમ્યુનિટી ટિયર પરનું
કેટલોગ ફીડ એક સ્નેપશોટ છે જે 30 દિવસ જેટલું જૂનું હોઈ શકે છે, તેથી તેમાંથી મેળવેલી
રેફરલ લિંક સર્વરની વાસ્તવિક લિંક્સની સૂચિ કરતાં એટલા જ સમય સુધી પાછળ રહેતી હતી
(નવી ઉમેરાયેલી રેફરલ મફત/કમ્યુનિટી વપરાશકર્તા સુધી પહોંચવામાં એક મહિના જેટલો સમય લઈ શકતી હતી).
રેફરલ્સ ફીડ પોતાની અલગ અને ઘણી ટૂંકી આવર્તન-અવધિએ સિંક થઈને આ વિલંબ દૂર કરે છે.

```ts
// GET /v1/referrals/latest પ્રતિસાદ બોડી (Ed25519 દ્વારા સહી કરેલી, એ જ પિન કરેલી કી જે
// કેટલોગ ફીડમાં છે):
{
  feed: "omniroute-radar-referrals",
  schemaVersion: 1,
  generatedAt: string,           // ISO — નિર્ધારિત: તમામ રેફરલ લિંક્સમાં મહત્તમ(updatedAt),
                                  // જેથી બે સરખી વિનંતીઓ બરાબર એ જ સહી કરેલા
                                  // બાઇટ્સ/સિગ્નેચર ઉત્પન્ન કરે
  referrals: {
    fixed: RadarReferral[],      // no-auth/community સહિત દરેક ટિયરમાં હાજર
    campaigns: RadarReferral[],  // માત્ર માન્ય સક્રિય (supporter) Bearer કી માટે જ ભરાય છે;
                                  // no-auth/expired-key વિનંતીઓને []
  },
}
// RadarReferral = { provider, url, kind: "fixo" | "campanha", validUntil,
//                    requiredAction, isDefault }
```

કેટલોગ ફીડથી વિપરીત, આ બોડીમાં કોઈ `tier` ફીલ્ડ જ નથી — સર્વર
`Authorization` કીના આધારે દરેક વિનંતી માટે શું સમાવવું તે નક્કી કરે છે, તેથી
`x-omniroute-feed-tier` પ્રતિસાદ હેડર જ આપવામાં આવેલા ટિયરનો એકમાત્ર સ્રોત છે
(`referralsSync.ts::syncRadarReferrals`); ગેરહાજર/અજાણ્યું હેડર સૌથી ઓછા વિશેષાધિકારવાળી
ધારણા `"community"` પર ઉતરે છે. `RadarReferralsFeedSchema`
(`src/lib/radar/referralsFeedSchema.ts`) સમગ્ર બોડીને માન્ય કરે છે અને `feedSchema.ts`માંથી
નિકાસ કરાયેલા એ જ પ્રતિ-રેફરલ `RadarReferralSchema`નો ફરી ઉપયોગ કરે છે, જેથી બંને ફીડ
વ્યક્તિગત રેફરલ્સને એકસરખી રીતે માન્ય કરે. દરેક `RadarReferral.url` `https://` હોવું આવશ્યક છે —
`http://` url સ્કીમા માન્યતામાં નિષ્ફળ જાય છે.

`RadarFeedSchema` (`feedSchema.ts`) પરનું જૂનું કેટલોગમાં સમાવાયેલ `referrals` ફીલ્ડ
પહેલેથી કૅશ થયેલા કેટલોગ ફીડ્સ સાથે પશ્ચાદવર્તી સુસંગતતા માટે રાખવામાં આવ્યું છે, પરંતુ
`getRadarReferrals()` હવે તેને વાંચતું નથી — નીચે [ઍક્સેસર](#accessor) જુઓ.

### સિંક

`syncRadarReferrals()` (`src/lib/radar/referralsSync.ts`) રેફરલ્સ માટે નેટવર્કને
સ્પર્શતું એકમાત્ર મોડ્યુલ છે અને `syncRadar()`ના કરારનું બરાબર અનુસરણ કરે છે: ફ્લૅગ બંધ
→ `disabled`; opt-in false → `opt_out`; `${RADAR_FEED_URL}/v1/referrals/latest`
ડાઉનલોડ કરે છે (કેટલોગ જેવા જ `RADAR_FEED_URL`/`RADAR_FEED_PUBKEY` ફોર્ક ઓવરરાઇડ્સ),
ચોક્કસ પ્રતિસાદ બાઇટ્સ પર Ed25519 સિગ્નેચરને માન્ય કરે છે (`verifyFeedBytes`),
`RadarReferralsFeedSchema` સામે માન્યતા કરે છે અને `radar_referrals_cache` ટેબલમાં
કૅશ કરે છે (માઇગ્રેશન `142_radar_referrals_cache.sql`) — જે કેટલોગના
`radar_feed_cache`થી સંપૂર્ણપણે અલગ ટેબલ છે. 10 MB પ્રતિસાદ મર્યાદા અને `generatedAt`
ફ્લોર, કૅશ કરેલા ફીડ કરતાં જૂના આવતા ફીડને નકારે છે અને જૂની સહી કરેલી આર્ટિફેક્ટના
રીપ્લે સામે રક્ષણ આપે છે. સમાન ટાઇમસ્ટૅમ્પ સ્વીકારવામાં આવે છે: સર્વર ઇરાદાપૂર્વક
કમ્યુનિટી અને સક્રિય રેફરલ વેરિઅન્ટ્સને સમાન નિર્ધારિત `generatedAt` આપે છે, જેથી
આધારભૂત લિંક સેટ બદલાયા વિના supporter-key બદલાયા પછી સહી કરેલો પેલોડ અને આપવામાં
આવેલો ટિયર બદલાઈ શકે. ક્યારેય અપવાદ ફેંકતું નથી — હંમેશાં સ્ટેટસ ઑબ્જેક્ટ પરત કરે છે;
`reason`માં ભૂલો ક્યારેય સ્ટૅક ટ્રેસ ધરાવતી નથી.

બે ટ્રિગર રેફરલ્સ કૅશને તૈયાર રાખે છે અને બંને કેટલોગની પોતાની
24h આવર્તન-અવધિથી સ્વતંત્ર છે:

- **વાંચતી વખતે સિંક** — કૅશ ગેરહાજર હોય અથવા `REFERRALS_STALE_MS` (1h,
  `shouldSyncReferralsOnRead()`) કરતાં જૂનો હોય ત્યારે `GET /api/radar/referrals` પોતે
  પ્રતિસાદ આપતાં પહેલાં ઇનલાઇન `syncRadarReferrals()`ને કૉલ કરે છે. કોઈપણ
  બૅકગ્રાઉન્ડ ટાઇમરની રાહ જોયા વિના, આ જ બાબત આગલા ડૅશબોર્ડ લોડ માટે નિશ્ચિત
  લિંક્સને "હંમેશાં અદ્યતન" રાખે છે.
- **શેડ્યૂલર સાઇડ-સિંક** — `radarSchedulerTick()` (`scheduler.ts`) કેટલોગ માટે
  ઉપયોગમાં લેવાતા એ જ કલાકદીઠ ટિક પર રેફરલ્સ કેટલા જૂના છે તેનું સ્વતંત્રપણે
  મૂલ્યાંકન કરે છે અને સમય થયો હોય ત્યારે `syncRadarReferrals()`ને કૉલ કરે છે.
  તે ટિક પર કેટલોગ પોતે બાકી હતો કે નહીં તે ધ્યાનમાં લીધા વિના આ ચાલે છે અને
  `RadarTickResult`ના આકારને ક્યારેય અસર કરતું નથી (માત્ર શ્રેષ્ઠ-પ્રયાસવાળી આડઅસર,
  ભૂલ થાય ત્યારે અવગણવામાં આવે છે).

### ઍક્સેસર

`src/lib/radar/index.ts` બે ફક્ત-વાંચન ઍક્સેસર્સ નિકાસ કરે છે અને બંને ક્યારેય
અપવાદ ફેંકતા નથી (`getRadarCatalog()` જેવો જ રક્ષણાત્મક કરાર — ફ્લૅગ બંધ હોવો,
કૅશ ન હોવો અથવા કૅશ થયેલો પેલોડ દૂષિત હોવો, આ બધામાં ભૂલને બદલે ખાલી આકાર મળે છે):

- `getRadarReferrals()` → `{ fixed: RadarReferral[], campaigns: RadarReferral[] }`,
  `radar_referrals_cache`માંથી (`getRadarReferralsCache()` મારફતે) વાંચે છે અને
  `RadarReferralsFeedSchema` દ્વારા માન્યતા કરે છે — કેટલોગ કૅશ દ્વારા **નહીં**.
- `getDefaultReferralFor(provider)` → તે provider માટે `isDefault: true` ધરાવતી
  `fixed` રેફરલ અથવા `null`. માત્ર `fixed`ને જ જુએ છે — કોઈ campaignનો ઉપયોગ ક્યારેય
  providerની "ડિફૉલ્ટ" લિંક તરીકે થતો નથી.

"કઈ રેફરલ provider માટે ડિફૉલ્ટ છે" તેનો વાસ્તવિક નિયમ
`findDefaultReferral()` (`src/lib/radar/referrals.ts`)માં છે, જે **કોઈ DB import વિનાનું**
નાનું શુદ્ધ ફંક્શન છે — તેને `"use client"` કમ્પોનેન્ટમાં સુરક્ષિત રીતે import કરી શકાય છે.
`getRadarReferrals`/`getDefaultReferralFor` (`index.ts`માં) `@/lib/db/radar`ને સમાવે છે
અને તેથી માત્ર સર્વર પર જ રહે છે; બ્રાઉઝરમાં `better-sqlite3`ને બંડલ કરવાનું ટાળવા માટે
providers ડૅશબોર્ડ `index.ts`ને બદલે સીધું `referrals.ts` import કરે છે (નીચે જુઓ).

### `GET /api/radar/referrals`

દરેક અન્ય Radar રૂટ જેવો જ ચોક્કસ ગેટ ક્રમ અનુસરે છે: `RADAR_ENABLED` બંધ →
`404` (સૌપ્રથમ ચકાસવામાં આવે છે, બાઇટ-સમાન વર્તન); અપ્રમાણિત → `401`; અન્યથા,
જૂનું હોય ત્યારે sync-on-read (ઉપર જુઓ) ટ્રિગર કરે છે, ત્યારબાદ
`{ fixed, campaigns, tier }` સાથે `200` — `tier` સીધું (સંભવતઃ હમણાં જ રિફ્રેશ થયેલી)
કૅશ રોમાંથી આવે છે અને માત્ર માહિતીપ્રદ છે (નીચેની UIની નરમ અપસેલ કૉપીને સંચાલિત કરે છે).
ફીડ સર્વરને ક્યારેય સીધું પ્રૉક્સી કરતું નથી — રૂટના પોતાના સોર્સમાં કોઈ `fetch(` કૉલ નથી;
નેટવર્ક પ્રવૃત્તિ માત્ર `syncRadarReferrals()`ની અંદર જ થાય છે, એટલે
`/api/radar/catalog` જેવો જ માત્ર-સ્થાનિક-કૅશ સિદ્ધાંત.

### ડૅશબોર્ડ UI — `/dashboard/radar` પર "મફત ક્રેડિટ્સ" ટૅબ

હાલના Radar પેજ (`src/app/(dashboard)/dashboard/radar/page.tsx`)નો નવા રૂટને બદલે
બીજા ટૅબ તરીકે ફરી ઉપયોગ કરે છે — પેજ પહેલેથી જ મેળવતા ડેટાનું સ્વરૂપાંતર હોય તેવી
સુવિધા માટે ઓછું રૂટિંગ/i18n ક્ષેત્રફળ. ઑપ્ટ-ઇન કર્યા પછી, ટૅબ બારમાં
**કૅટલૉગ** (હાલનું ટેબલ) અને **મફત ક્રેડિટ્સ** ઉપલબ્ધ થાય છે:

- નિશ્ચિત લિંક્સને પ્રદાતા પ્રમાણે જૂથબદ્ધ કરવામાં આવે છે; દરેકમાં `requiredAction`
  (જ્યારે હાજર હોય) અને રેફરલ URL માટે `target="_blank" rel="noopener noreferrer"`
  બટન દેખાય છે.
- કૅમ્પેઇન્સમાં પણ એ જ દેખાય છે, ઉપરાંત હાજર હોય ત્યારે `validUntil` પણ દેખાય છે.
- જ્યારે `campaigns` ખાલી હોય **અને** સર્વ કરાયેલ ટિયર `community` હોય, ત્યારે UI
  એક ટૂંકી અપસેલ નોંધ ("મર્યાદિત-સમયના કૅમ્પેઇન્સ સમર્થકો માટેની વધારાની સુવિધા છે")
  બતાવે છે — આ નિશ્ચિત લિંક્સની સૂચિને **ક્યારેય** છુપાવતું કે ગેટ કરતું નથી,
  જે દરેક ટિયર માટે સંપૂર્ણ રીતે ભરેલી રહે છે. અપસેલ માત્ર નરમ સંદેશ છે,
  ક્યારેય અવરોધ નથી.

### પ્રદાતાના નામ પર રેફરલ લિંક (પ્રદાતા ડૅશબોર્ડ)

`ProviderPageHeader` (`src/app/(dashboard)/dashboard/providers/[id]/components/`)
પહેલેથી જ પ્રદાતાના નામને `providerInfo.website` હાજર હોય ત્યારે તેની સાથે લિંક કરતું હતું,
અને મોનેટાઇઝ્ડ લિંક માટે એક પૂર્વદૃષ્ટાંત હતો: Kimi (Moonshot AI) પાર્ટનર-લિંક નોંધ
(`providers.kimiPartnerLinkNote` i18n કી). D28 નવી કી રજૂ કરવાને બદલે Radarની
ડિફૉલ્ટ રેફરલ્સ માટે એ જ વિવેકપૂર્ણ નોંધની પેટર્નનો ફરી ઉપયોગ કરે છે.

ડિઝાઇન અનુસાર ઢીલું કપલિંગ:

- `resolveProviderHeaderLink()` (`src/app/(dashboard)/dashboard/providers/providerPageUtils.ts`)
  એક **શુદ્ધ** ફંક્શન છે — `(staticWebsite, referralUrl) => { website, isReferralLink }`
  — જેને `@/lib/radar` અથવા `@/lib/db/*` પર કોઈ નિર્ભરતા નથી. સમગ્ર
  `providerPageUtils.ts`માં પણ એ ઇમ્પોર્ટ્સ નથી (જેનું
  `tests/unit/provider-header-referral-link.test.ts` દ્વારા નિર્ધારણ કરાયું છે).
- `ProviderDetailPageClient.tsx` (એક `"use client"` કમ્પોનન્ટ) એકમાત્ર એવું સ્થાન છે
  જેને Radar ડેટા મેળવવાની મંજૂરી છે — `fetch("/api/radar/referrals")` દ્વારા, એટલે
  Radar ડૅશબોર્ડ પેજ પોતે જે સ્થાનિક-રૂટ પેટર્ન વાપરે છે એ જ — અને તે DB-મુક્ત
  `src/lib/radar/referrals.ts`માંથી `findDefaultReferral()` વડે ક્લાયન્ટ-સાઇડ પર
  ડિફૉલ્ટ રેફરલની ગણતરી કરે છે.
- `RADAR_ENABLED` બંધ હોય ત્યારે, fetchને 404 મળે છે, `referralUrl` `null` જ રહે છે,
  અને `resolveProviderHeaderLink()` સ્થિર કૅટલૉગ `website`ને કોઈ ફેરફાર વિના પરત કરે છે —
  પ્રદાતા પેજ આ સુવિધા અસ્તિત્વમાં આવી તે પહેલાં જેવું બાઇટ-સમાન રહે છે. હજી સુધી કોઈ
  કૅશ ન હોય અથવા તે ચોક્કસ પ્રદાતા માટે કોઈ ડિફૉલ્ટ રેફરલ ન હોય ત્યારે પણ એ જ પરિણામ મળે છે.
- જ્યારે ડિફૉલ્ટ રેફરલ લાગુ પડે છે, ત્યારે `ProviderPageHeader`ને `isReferralLink`
  મળે છે અને તે Kimi પાર્ટનર લિંક જેવી જ વિવેકપૂર્ણ નોંધ/ટૂલટિપ બતાવે છે
  (`providers.kimiPartnerLinkNote` કીનો ફરી ઉપયોગ કરીને) — ક્યારેય કોઈ નવી,
  અલગ વિઝ્યુઅલ ટ્રીટમેન્ટ નહીં.

## ફીડને સ્વયં કેવી રીતે હોસ્ટ કરવી

કૅટલૉગ પર સંપૂર્ણ નિયંત્રણ ઇચ્છતો ફોર્ક અથવા સ્વયં-હોસ્ટર ક્લાયન્ટ કોડને સ્પર્શ કર્યા વિના પોતાની ફીડ સેવા ચલાવી શકે છે:

1. `RadarFeedSchema` (`src/lib/radar/feedSchema.ts`) ને સંતોષતી JSON બૉડી પરત કરતું `GET /v1/catalog/latest` એન્ડપોઇન્ટ સર્વ કરો — ટોચના સ્તરે `feed:
"omniroute-radar"`, `schemaVersion: 2`, `version`, `tier`, `providers`, `models`,
   `quirks`, અને `totals`. `x-omniroute-radar-schema: 2` નું પાલન કરો; ટ્રાન્ઝિશન-સુસંગત સર્વરે તેના વિનાની વિનંતીઓ માટે અલગથી સહી કરેલ v1 આર્ટિફેક્ટ ડિફૉલ્ટ તરીકે આપવું જોઈએ.
2. ચોક્કસ પ્રતિસાદ બાઇટ્સ પર Ed25519 કી જોડી વડે સહી કરો અને base64 સહીને `x-omniroute-feed-signature` પ્રતિસાદ હેડરમાં પરત કરો.
3. `RADAR_FEED_URL` ને નવા બેઝ URL પર અને `RADAR_FEED_PUBKEY` ને મેળ ખાતી જાહેર કી (base64-DER SPKI અથવા PEM) પર સેટ કરો — [એન્વાયરમેન્ટ વેરિએબલ સંદર્ભ](../reference/ENVIRONMENT.md#27-radar-feed-self-hosting) જુઓ.
4. `RADAR_ENABLED` સક્ષમ કરો અને `POST /api/radar/settings`
   (`{ optIn: true }`) દ્વારા પસંદગીપૂર્વક જોડાઓ.

અન્ય કોઈ કોડ ફેરફાર જરૂરી નથી — `verifyFeedBytes()` ઓવરરાઇડને આપમેળે અપનાવે છે (`src/lib/radar/pinnedKeys.ts` માં `getFeedPublicKeys()`), અને વર્ઝનની સરખામણી, સ્કીમા માન્યતા તથા મર્જના નિયમો સ્વયં-હોસ્ટ કરેલી ફીડ પર સમાન રીતે લાગુ પડે છે.

રેફરલ લિંક્સ (ઉપર [રેફરલ લિંક્સ (મફત ક્રેડિટ્સ)](#referral-links-free-credits) જુઓ) એક અલગ, વૈકલ્પિક આર્ટિફેક્ટ છે: માત્ર `/v1/catalog/latest` સર્વ કરતો ફોર્ક પણ સંપૂર્ણપણે કાર્ય કરે છે — `/v1/referrals/latest` તરફથી `404` મળતાં `syncRadarReferrals()` ની સ્થિતિ `{ status: "error" }` થાય છે અને કૅશ ખાલી જ રહે છે, તેથી બાકીના પેજને નિષ્ફળ કરવાને બદલે `GET /api/radar/referrals` `{ fixed: [], campaigns: [], tier: null }` પરત કરવાનું ચાલુ રાખે છે. રેફરલ લિંક્સ પણ પ્રદાન કરવા માટે, `RadarReferralsFeedSchema` (`src/lib/radar/referralsFeedSchema.ts`) ને સંતોષતું `GET /v1/referrals/latest` સર્વ કરો અને કૅટલૉગ ફીડ માટે વપરાતી એ જ Ed25519 કી જોડી વડે તેના પર સહી કરો.

સમર્થક ઑફર્સ અન્ય એક વૈકલ્પિક આર્ટિફેક્ટ છે. તેમને સર્વ કરવા માટે, બંધ `RadarOffersFeedSchema` (`src/lib/radar/offersFeedSchema.ts`) સાથે `GET /v1/offers/latest` અમલમાં મૂકો, સક્રિય એન્ટાઇટલમેન્ટ આવશ્યક બનાવો, `x-omniroute-feed-tier: live` પરત કરો અને ચોક્કસ બાઇટ્સ પર એ જ કી વડે સહી કરો. આ એન્ડપોઇન્ટને છોડતો ફોર્ક કૅટલૉગ/રેફરલ્સનું વર્તન યથાવત્ રાખે છે; ઑફર રિફ્રેશ બિન-વિનાશક રીતે નિષ્ફળ જાય છે અને છેલ્લી ચકાસાયેલ સ્થાનિક ઑફર કૅશ ઉપલબ્ધ રહે છે.

Intel પણ એ જ રીતે વૈકલ્પિક છે. સ્વયં-હોસ્ટર `RadarIntelFeedSchema` (`src/lib/radar/intelFeedSchema.ts`) નો ઉપયોગ કરીને `GET /v1/intel/latest` સર્વ કરી શકે છે, સક્રિય એન્ટાઇટલમેન્ટ આવશ્યક બનાવી શકે છે, `x-omniroute-feed-tier: live` પરત કરી શકે છે અને ચોક્કસ બાઇટ્સ પર શેર કરેલી Ed25519 કી વડે સહી કરી શકે છે. એન્ડપોઇન્ટને છોડવાથી કૅટલૉગ, રેફરલ્સ અને ઑફર્સ યથાવત્ રહે છે; Intel રિફ્રેશ છેલ્લું ચકાસાયેલ સ્થાનિક સ્નૅપશૉટ જાળવી રાખે છે.
