Traffic Inspector એ OmniRouteનું બિલ્ટ-ઇન HTTPS ટ્રાફિક ડિબગર છે — Charles Proxy / mitmweb / HTTP Toolkit જેવું સાધન, જે **LLM-અવેર** અને **એજન્ટ-અવેર** છે. તે `/dashboard/tools/traffic-inspector` પર ઉપલબ્ધ છે અને એકસાથે વધુમાં વધુ 5 કેપ્ચર સ્રોતોમાંથી લાઇવ ટ્રાફિક મેળવે છે.

**ડૅશબોર્ડ સ્થાન:** `/dashboard/tools/traffic-inspector`
**સાઇડબાર જૂથ:** Tools (AgentBridge પછી)
**આ પણ જુઓ:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge એ કેપ્ચર મોડ 1 છે.

`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) એ શેર કરેલું ઇન-મેમરી રિંગ બફર છે (ડિફૉલ્ટ રૂપે 1000 એન્ટ્રીઓ, `INSPECTOR_BUFFER_SIZE` દ્વારા ગોઠવી શકાય છે). બધા કેપ્ચર સ્રોતો `push()` દ્વારા તેમાં લખે છે. બફર `kindDetector.ts`નો ઉપયોગ કરીને દરેક એન્ટ્રીનું વર્ગીકરણ કરે છે (તે LLM વિનંતી છે કે નહીં તે નક્કી કરે છે), `contextKey`ની ગણતરી કરે છે (સિસ્ટમ પ્રોમ્પ્ટની SHA-256 ફિંગરપ્રિન્ટ), અને `globalTrafficBuffer.subscribe()` દ્વારા બધા WebSocket સબ્સ્ક્રાઇબર્સને પ્રસારિત કરે છે. ડૅશબોર્ડ `GET /api/tools/traffic-inspector/ws` દ્વારા કનેક્ટ થાય છે અને કનેક્ટ થવા પર સ્નૅપશૉટ મેળવે છે, ત્યારબાદ `new`/`update`/`clear` ઇવેન્ટ્સ મેળવે છે.

## §2 કૅપ્ચર મોડ્સ

Traffic Inspector **5 સમકાલીન કૅપ્ચર સ્રોતો**ને સપોર્ટ કરે છે. દરેકને સ્વતંત્ર રીતે ચાલુ કે બંધ કરી શકાય છે. દરેક `InterceptedRequest` (`src/mitm/inspector/types.ts`) પરનું `source` ફીલ્ડ `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"`, અથવા `"tproxy"`માંથી એક હોય છે.

### મોડ 1 — AgentBridge (ડિફૉલ્ટ, હંમેશાં ચાલુ)

**સ્રોત:** AgentBridge હૅન્ડલર્સ (`src/mitm/handlers/base.ts`)
**કાર્યપદ્ધતિ:** `MitmHandlerBase`માંનો દરેક `intercept()` કૉલ ફૉર્વર્ડ કરતાં પહેલાં `hookBufferStart()` અને પૂર્ણ થયા પછી `hookBufferUpdate()` કૉલ કરે છે. કોઈ વધારાનું કન્ફિગરેશન જરૂરી નથી — AgentBridge ચાલુ થતાં જ કાર્ય કરે છે.
**વ્યાપ:** AgentBridgeમાં કન્ફિગર કરેલા 9 IDE એજન્ટ્સ
**નોંધ:** `InterceptedRequest`માં `source` ફીલ્ડ = `"agent-bridge"`

### મોડ 2 — કસ્ટમ હોસ્ટ્સ (DNS રીડાયરેક્ટ)

**સ્રોત:** વપરાશકર્તા દ્વારા નિર્ધારિત હોસ્ટ સૂચિ (`inspector_custom_hosts` ટેબલ)
**કાર્યપદ્ધતિ:** UI દ્વારા હોસ્ટ ઉમેરવાથી `/etc/hosts`માં `127.0.0.1 <host>` ઉમેરાય છે (sudo જરૂરી છે). હાલનું AgentBridge MITM સર્વર (પોર્ટ 443) નવા હોસ્ટ માટે ગતિશીલ રીતે SNI સર્ટિફિકેટ જનરેટ કરે છે.
**વ્યાપ:** ઉમેરેલા હોસ્ટનો ઉપયોગ કરતી કોઈપણ ઍપ્લિકેશન — ઍપના કન્ફિગરેશનમાં કોઈ ફેરફાર જરૂરી નથી
**નોંધ:** `source` = `"custom-host"`

ઉપયોગના ઉદાહરણો:

- Python સ્ક્રિપ્ટ્સમાંથી `api.openai.com`નું નિરીક્ષણ કરવું
- `my-internal-llm.company.com`ને ડિબગ કરવું
- સમાન નેટવર્ક પરનાં મોબાઇલ ઉપકરણોમાંથી ટ્રાફિક કૅપ્ચર કરવો (ARP સ્પૂફિંગ દ્વારા — અદ્યતન)

### મોડ 3 — HTTP_PROXY લિસનર (પોર્ટ 8080)

**સ્રોત:** `HTTP_PROXY`/`HTTPS_PROXY` એન્વાયર્નમેન્ટ વેરિએબલ્સનો ઉપયોગ કરતી ઍપ્લિકેશનો
**કાર્યપદ્ધતિ:** પોર્ટ 8080 પરનો સેકન્ડરી લિસનર (`src/mitm/inspector/httpProxyServer.ts`) પ્રમાણભૂત સ્પષ્ટ HTTP/HTTPS પ્રૉક્સી તરીકે કાર્ય કરે છે. `CONNECT` ટનલ્સ (HTTPS) અને સીધી HTTP રિક્વેસ્ટ્સ સ્વીકારે છે.
**વ્યાપ:** `HTTP_PROXY` envનું પાલન કરતી કોઈપણ ઍપ્લિકેશન — કોઈ DNS ફેરફાર નહીં, sudoની જરૂર નહીં
**નોંધ:** `source` = `"http-proxy"`

```bash
# એક કમાન્ડ માટે ઝડપી કૅપ્ચર:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# શેલ સેશનમાં સતત કૅપ્ચર:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**TLS મર્યાદા:** HTTPS `CONNECT` ટનલ્સ ફક્ત મેટાડેટા (હોસ્ટ, પોર્ટ, સમય) તરીકે કૅપ્ચર થાય છે — ડિફૉલ્ટ રૂપે TLS બૉડી ડિક્રિપ્ટ થતી નથી. સંપૂર્ણ બૉડી નિરીક્ષણ માટે "પ્રૉક્સી મોડમાં HTTPS ડિક્રિપ્ટ કરો" ટૉગલ ચાલુ કરો (વૈકલ્પિક, AgentBridge સર્ટિફિકેટ વિશ્વસનીય હોવું જરૂરી છે).

**પોર્ટ સંઘર્ષ:** જો પોર્ટ 8080 ઉપયોગમાં હોય, તો AgentBridge સંરચિત ભૂલ સાથે 409 પરત કરે છે. `INSPECTOR_HTTP_PROXY_PORT` env var દ્વારા પોર્ટ બદલો.

### મોડ 4 — સમગ્ર સિસ્ટમ માટેનો પ્રૉક્સી (અદ્યતન, વૈકલ્પિક)

**સ્રોત:** OS-સ્તરની પ્રૉક્સી સેટિંગ્સ (મશીન પરની બધી ઍપ્સને લાગુ પડે છે)
**કાર્યપદ્ધતિ:** તમામ HTTP/HTTPS ટ્રાફિકને HTTP_PROXY લિસનર દ્વારા રીડાયરેક્ટ કરવા માટે OS APIsનો ઉપયોગ કરે છે:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **વ્યાપ:** સિસ્ટમ પ્રૉક્સી સેટિંગ્સનું પાલન કરતી મશીન પરની દરેક ઍપ્લિકેશન
  **નોંધ:** `source` = `"system-proxy"`

**સુરક્ષા વ્યવસ્થાઓ:**

- આપમેળે બંધ થવાનું ટાઇમર (ડિફૉલ્ટ 30 મિનિટ, `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES` દ્વારા કન્ફિગર કરી શકાય છે)
- સિસ્ટમ પ્રૉક્સીની અગાઉની સ્થિતિ DBમાં સાચવવામાં આવે છે અને રિવર્ટ કરતી વખતે પુનઃસ્થાપિત થાય છે
- સક્રિય હોય ત્યારે વપરાશકર્તા અન્યત્ર નેવિગેટ કરે તો ડૅશબોર્ડ "સિસ્ટમ પ્રૉક્સી રિવર્ટ કરી રહ્યાં છીએ" પ્રૉમ્પ્ટ બતાવે છે
- UI `⚠ અદ્યતન` બૅજ + સ્પષ્ટ પુષ્ટિ માટેનું ચેકબૉક્સ બતાવે છે

### મોડ 5 — TPROXY પારદર્શક ડિક્રિપ્ટ (Linux, root, વૈકલ્પિક)

**સ્રોત:** કર્નલ TPROXY + પૉલિસી રૂટિંગ (`src/mitm/tproxy/`)
**કાર્યપદ્ધતિ:** `mangle OUTPUT`માં લક્ષ્ય પોર્ટ (ડિફૉલ્ટ `443`) તરફનાં નવાં સ્થાનિક આઉટબાઉન્ડ TCP કનેક્શન્સને ચિહ્નિત કરે છે, એક `ip rule` ચિહ્નિત પૅકેટ્સને સ્થાનિક ડિલિવરી તરફ ફરીથી રૂટ કરે છે અને `mangle PREROUTING`નું `TPROXY` લક્ષ્ય તેમને પારદર્શક (**IP_TRANSPARENT**) લિસનર (ડિફૉલ્ટ પોર્ટ `8443`)ને સોંપે છે. લિસનર ગતિશીલ CA દ્વારા **માગ પર દરેક SNI હોસ્ટનામ માટે** જારી કરાયેલા લીફ સર્ટિફિકેટથી TLS સમાપ્ત કરે છે, ડિક્રિપ્ટ થયેલા વિનિમયને કૅપ્ચર કરે છે અને રિક્વેસ્ટને ફરીથી એન્ક્રિપ્ટ કરીને મૂળ ગંતવ્ય પર ફૉર્વર્ડ કરે છે.
**વ્યાપ:** લક્ષ્ય પોર્ટ પરનાં **કોઈપણ** ગંતવ્ય હોસ્ટ્સ — કોઈ `/etc/hosts` સ્પૂફ નહીં, કોઈ `HTTP_PROXY` env નહીં અને સમગ્ર સિસ્ટમ માટેના પ્રૉક્સીમાં કોઈ ફેરફાર નહીં. ઇન્ટરસેપ્ટ કરાયેલી પ્રોસેસના કન્ફિગરેશનમાં કોઈ ફેરફાર જરૂરી નથી, પરંતુ તેણે ગતિશીલ CA પર વિશ્વાસ કરવો આવશ્યક છે.
**નોંધ:** `source` = `"tproxy"`

**આવશ્યકતાઓ:** માત્ર Linux (**IP_TRANSPARENT** ફક્ત Linux પર ઉપલબ્ધ છે), **CAP_NET_ADMIN** ક્ષમતા (root) અને C ટૂલચેઇન વડે બિલ્ડ કરવું આવશ્યક હોય તેવું નેટિવ N-API ઍડઑન (`npm run build:native:tproxy`). ઉપલબ્ધ ન હોય ત્યારે ડૅશબોર્ડ ટૉગલ "TPROXY ડિક્રિપ્ટ માટે Linux + root + નેટિવ ઍડઑન જરૂરી છે" ટૂલટિપ સાથે અક્ષમ રહે છે. ફાયરવૉલ નિયમો ટ્રાન્ઝૅક્શનના સ્વરૂપમાં લાગુ થાય છે/રિવર્ટ થાય છે (ક્રૅશ ક્યારેય કોઈ `mangle` નિયમ બાકી રાખતું નથી) અને રીબૂટ વખતે દૂર થાય છે. SO_MARK-આધારિત ઍન્ટિ-લૂપ પ્રૉક્સીના પોતાના ફરીથી એન્ક્રિપ્ટ કરેલા ફૉર્વર્ડને ફરી ઇન્ટરસેપ્ટ થવાથી અટકાવે છે.

આ એક વિશાળ સબસિસ્ટમ છે જેની પોતાની સમર્પિત ઑપરેટર માર્ગદર્શિકા છે — સંપૂર્ણ ફાયરવૉલ રેસિપી, દરેક SNI માટેનો ગતિશીલ CA + ટ્રસ્ટ-સ્ટોર ઇન્સ્ટૉલર, ફક્ત સ્થાનિક રૂટ, ઍન્ટિ-લૂપની વિગતો અને કન્ફિગરેશન સ્કીમા માટે `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs`માં કમ્પાઇલ કરેલું નથી) જુઓ. ટૉગલ `GET / POST / DELETE /api/tools/agent-bridge/tproxy` દ્વારા સંચાલિત થાય છે (નોંધ: રૂટ Traffic Inspector પ્રીફિક્સ હેઠળ નહીં, પરંતુ AgentBridge પ્રીફિક્સ હેઠળ છે).

### 4.1 પ્રકાર શોધક (`src/mitm/inspector/kindDetector.ts`)

4 સંકેતોનો ઉપયોગ કરીને દરેક વિનંતીને `"llm"`, `"app"`, અથવા `"unknown"` તરીકે વર્ગીકૃત કરે છે:

1. **હોસ્ટ રજિસ્ટ્રી** — ~18 જાણીતા LLM API હોસ્ટનામો (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot, વગેરે)
2. **પાથ પેટર્ન** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses`, વગેરે.
3. **બૉડીનું બંધારણ** — `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input` ફીલ્ડ શોધે છે
4. **યુઝર-એજન્ટ સંકેતો** — UA સ્ટ્રિંગમાં `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor`

Mode 2 દ્વારા ઉમેરવામાં આવેલા કસ્ટમ હોસ્ટ્સ ફોર્મ ઇનપુટમાંથી તેમનો `kind` વારસામાં મેળવે છે (ડિફૉલ્ટ `"custom"` છે).

### 4.2 SSE મર્જર (`src/mitm/inspector/sseMerger.ts`)

**સ્વતંત્ર ક્લીન-રૂમ અમલીકરણ.** ઇવેન્ટ પાર્સિંગ
[WHATWG server-sent events algorithm](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)
ને અનુસરે છે, જ્યારે પુનઃનિર્માણ જાહેર [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming), અને
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent)
સ્ટ્રીમિંગ સ્કીમાને અનુસરે છે.

કાચી SSE ડેલ્ટા ઇવેન્ટ્સમાંથી અંતિમ સહાયક સંદેશનું પુનઃનિર્માણ કરે છે:

- **Anthropic**: ઇન્ડેક્સ મુજબ `content_block_delta` સંચિત કરે છે; `text_delta`, `input_json_delta` (ટૂલ કૉલ્સ), `thinking_delta` સંભાળે છે
- **OpenAI**: Chat Completions પસંદગીઓ/ટૂલ કૉલ્સ અને Responses API આઉટપુટ આઇટમ્સને ઇન્ડેક્સ મુજબ સંચિત કરે છે
- **Gemini**: `candidates[i].content.parts` સંચિત કરે છે
- **અજ્ઞાત**: કાચી ઇવેન્ટ્સને જેમની તેમ પરત કરે છે

Response ટૅબ એક ટૉગલ બતાવે છે: **"કાચી ઇવેન્ટ્સ ↔ મર્જ કરેલ"**.

### 4.3 વાર્તાલાપ નોર્મલાઇઝર (`src/mitm/inspector/conversationNormalizer.ts`)

**સ્વતંત્ર ક્લીન-રૂમ અમલીકરણ.** નોર્મલાઇઝેશનને સ્થાનિક બ્લૅક-બૉક્સ
કોન્ટ્રાક્ટ્સ અને જાહેર OpenAI, Anthropic, અને Gemini સંદેશ સ્કીમા દ્વારા વ્યાખ્યાયિત કરવામાં આવ્યું છે; કોઈ અપસ્ટ્રીમ
અમલીકરણ સ્રોતનો ઉપયોગ કરાયો નથી.

રેન્ડરિંગ પહેલાં OpenAI, Anthropic, અને Gemini સંદેશ ફૉર્મેટ્સને એક `NormalizedConversation`માં રૂપાંતરિત કરે છે:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // વિનંતી બૉડીમાંથી messages / contents / prompt
  response: NormalizedTurn[]; // સહાયકનો પ્રતિસાદ (sseMerger મારફતે મર્જ કરેલો)
  contextKey: string | null; // SHA-256 સિસ્ટમ-પ્રૉમ્પ્ટ ફિંગરપ્રિન્ટ
}
```

બ્લૉકના પ્રકારો: `text`, `tool_use`, `tool_result`. પ્રદાતા ગમે તે હોય, Conversation ટૅબ આ બંધારણનો ઉપયોગ કરે છે.

### 4.4 કોન્ટેક્સ્ટ કી કલરાઇઝેશન (`src/mitm/inspector/contextKey.ts`)

- સિસ્ટમ પ્રૉમ્પ્ટનું `SHA-256` ગણે છે (પ્રથમ `role:system` સંદેશ, અથવા `system` ફીલ્ડ, અથવા Gemini `systemInstruction`)
- 12-અક્ષરનો હેક્સ પ્રિફિક્સ (`"a3f9c2..."`) પરત કરે છે
- ડાબી બૉર્ડર બાર માટે ફ્રન્ટએન્ડ કીને નિર્ધારિત HSL રંગ સાથે મેપ કરે છે
- **"સમાન કોન્ટેક્સ્ટ" ફિલ્ટર**: `ctx #a3f` ચિપ પર ક્લિક કરવાથી માત્ર સમાન ફિંગરપ્રિન્ટ ધરાવતી વિનંતીઓ બતાવવા માટે ફિલ્ટર ઉમેરાય છે

આનાથી સમાન એજન્ટ સેશનમાં ચાલતા અલગ-અલગ "પર્સોના" અથવા કાર્યોને દૃશ્યમાન રીતે અલગ પાડવાનું સરળ બને છે.

### 4.5 LLM મેટાડેટા નિષ્કર્ષણ

LLM વિનંતીઓ માટે, LLM Details ટૅબ આ માહિતી નિષ્કર્ષિત કરે છે:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // વિનંતી બૉડી અથવા પ્રતિસાદમાંથી
  messages: number; // ટર્નની સંખ્યા
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // SSE પ્રતિસાદ હોય તો true
  mappedTo: string | null; // x-omniroute-mapped હેડર
  costEstimateUsd: number | null; // OmniRoute ભાવનિર્ધારણ પર આધારિત અંદાજિત ખર્ચ
}
```

### 4.6 લાઇવ ચાલુ વિનંતી ફિલ્ટર

વિનંતીનું `status` ફીલ્ડ `number | "in-flight" | "error"` છે — વિનંતી શરૂ થાય તે જ ક્ષણે એન્ટ્રીને
`"in-flight"` તરીકે પુશ કરવામાં આવે છે અને પ્રતિસાદ (અથવા ભૂલ) આવે ત્યારે તેને **તે જ જગ્યાએ અપડેટ** કરવામાં આવે છે.
ટૂલબારનું **"લાઇવ"** ટૉગલ
(`liveOnly`, i18n કી `trafficInspector.liveOnly`) સૂચિને માત્ર એવી એન્ટ્રીઓ સુધી મર્યાદિત કરે છે
જેમનું `status === "in-flight"` હોય, જેથી તમે ખુલ્લા કનેક્શન્સને રિયલ ટાઇમમાં જોઈ શકો.

ફિલ્ટર
`src/lib/inspector/matchesTrafficFilter.ts`માં શુદ્ધ, ક્લાયન્ટ-સાઇડ પ્રેડિકેટ છે:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

ટૉગલની સ્થિતિ `useTrafficFilters` (ઇન્સ્પેક્ટર ડૅશબોર્ડ હુક્સ)માં રહે છે અને
અન્ય ફિલ્ટર્સ (પ્રોફાઇલ, હોસ્ટ, એજન્ટ, સ્રોત, સ્થિતિ, કોન્ટેક્સ્ટ) સાથે સંયોજાય છે.

### 4.7 પ્રોસેસ એટ્રિબ્યુશન (Linux)

Linux પર, દરેક ઇન્ટરસેપ્ટ કરેલી વિનંતીને **મૂળ સ્થાનિક
પ્રોસેસ** સાથે સાંકળી શકાય છે. `InterceptedRequest`માં બે વૈકલ્પિક ફીલ્ડ ઉમેરવામાં આવે છે:

```ts
pid?: number;          // મૂળ પ્રોસેસ id (માત્ર Linux)
processName?: string;  // મૂળ પ્રોસેસનું નામ (માત્ર Linux)
```

`src/mitm/inspector/processAttribution.ts` કનેક્શનના _ક્લાયન્ટ_
એફિમેરલ પોર્ટને PID + નામ સાથે આ રીતે મેપ કરે છે:

1. પોર્ટ માટે સૉકેટ inode શોધવા `/proc/net/tcp` અને `/proc/net/tcp6` વાંચે છે
   (`parseProcNetTcpForInode`, એક શુદ્ધ ફિક્સ્ચર-ટેસ્ટ કરી શકાય તેવું પાર્સર).
2. `socket:[<inode>]`ની સિમલિંક માટે `/proc/<pid>/fd/` સ્કૅન કરે છે.
3. `/proc/<pid>/comm`માંથી પ્રોસેસનું નામ વાંચે છે.

1-સેકન્ડની TTL કૅશ લોડ હેઠળ procfs સ્કૅનના ખર્ચને મર્યાદિત રાખે છે. એટ્રિબ્યુશન
**શ્રેષ્ઠ-પ્રયાસ આધારિત** છે — કોઈપણ નિષ્ફળતા `null`માં પરિણમે છે અને કૅપ્ચરને ક્યારેય અવરોધતી નથી.
macOS/Windows પર ફંક્શન `null` પરત કરે છે (સ્ટબ; `lsof`/`GetExtendedTcpTable`
સપોર્ટ અનુગામી કાર્ય છે).

## §5 સેશન્સ

### 5.1 સેશન રેકોર્ડ કરવું

1. ટૂલબારમાં **"● સેશન રેકોર્ડ કરો"** પર ક્લિક કરો → નામ દાખલ કરો (વૈકલ્પિક)
2. લાઇવ ટેઇલ સામાન્ય રીતે ચાલુ રહે છે; લાલ ધબકતું સૂચક `◉ REC · <name> · 00:42 · 23 વિનંતીઓ` દર્શાવે છે
3. **"⏹ રોકો"** પર ક્લિક કરો → સેશન સ્નૅપશૉટ `inspector_sessions` + `inspector_session_requests`માં સાચવવામાં આવે છે

### 5.2 રેકોર્ડ કરેલું સેશન જોવું

ટૂલબારમાંનું **સેશન્સ** ડ્રૉપડાઉન સાચવેલા સેશન્સની યાદી દર્શાવે છે. કોઈ એક પસંદ કરવાથી:

- સેશનનો સ્નૅપશૉટ લોડ થાય છે (સ્થિર સ્થિતિ)
- એક બૅનર દર્શાવે છે: `રેકોર્ડ કરેલું સેશન "<name>" જોવામાં આવી રહ્યું છે — [લાઇવ પર પાછા જાઓ]`
- Recharts એગ્રીગેટ્સ સાથે આંકડા ટૅબ ઉપલબ્ધ બને છે

### 5.3 નિકાસ ફૉર્મેટ્સ

દરેક સેશનને આ રીતે નિકાસ કરી શકાય છે:

| ફૉર્મેટ                    | ઉપયોગ                                                                         |
| -------------------------- | ----------------------------------------------------------------------------- |
| **HAR** (HTTP Archive 1.2) | Chrome DevTools, Charles, Fiddler સાથે સુસંગત — ઑફલાઇન વિશ્લેષણ માટે આયાત કરો |
| **JSONL**                  | દરેક લાઇન દીઠ એક `InterceptedRequest` — `llm-interceptor` ફૉર્મેટ સાથે સુસંગત |

`GET /api/tools/traffic-inspector/sessions/{id}/export.har` મારફતે અથવા સેશન્સ ડ્રૉપડાઉનમાંના ⬇ બટન દ્વારા નિકાસ કરો.

## §6 સુરક્ષા

ટ્રાફિક ઇન્સ્પેક્ટર ઑથોરાઇઝેશન હેડર્સ અને વિનંતીના બૉડીઝ સહિતનો **તમામ ઇન્ટરસેપ્ટ કરેલો HTTPS ટ્રાફિક** દર્શાવે છે. નીચેના નિયંત્રણો લાગુ છે:

| નિયંત્રણ                              | વિગતો                                                                                                                                                                         |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LOCAL_ONLY**                        | બધા રૂટ્સ અને WebSocket એન્ડપૉઇન્ટ ફક્ત લૂપબૅક માટે છે (ઑથ પહેલાં `routeGuard.ts`માં અમલમાં મૂકવામાં આવે છે)                                                                  |
| **ગુપ્ત માહિતીનું માસ્કિંગ**          | રેખીય `maskSecret()` સ્કૅનર `TrafficBuffer.push()` પહેલાં RFC 6750 Bearer ક્રેડેન્શિયલ્સ, પ્રોવાઇડર-પ્રિફિક્સ્ડ કીઝ અને લાંબા અપારદર્શક ટોકન્સને ઢાંકે છે                     |
| **બૉડીના કદની મર્યાદા**               | `INSPECTOR_MAX_BODY_KB`થી મોટા બૉડીઝ (ડિફૉલ્ટ 1024 KB)ને `"(કાર્યક્ષમતા માટે ટૂંકાવ્યું)"` સૂચના સાથે ટૂંકાવવામાં આવે છે                                                      |
| **હેડર સૅનિટાઇઝેશન**                  | નામો લોઅરકેસમાં ફેરવાય છે; ફ્રેમિંગ/હૉપ-બાય-હૉપ અને પ્રૉક્સી-ઑથ હેડર્સ કાઢી નાખવામાં આવે છે; કુકીઝ સંપૂર્ણપણે ઢંકાય છે; ક્રેડેન્શિયલ મૂલ્યો `maskSecret()`ને સોંપવામાં આવે છે |
| **CSP**                               | ઇન્જેક્ટ કરેલા પ્રતિસાદ બૉડીઝ મારફતે XSS અટકાવવા માટે ટ્રાફિક ઇન્સ્પેક્ટર પૃષ્ઠો પર કડક Content Security Policy                                                               |
| **ડિફૉલ્ટ રૂપે કોઈ પર્સિસ્ટન્સ નહીં** | `TrafficBuffer` ઇન-મેમરી છે અને સર્વર રીસ્ટાર્ટ થવા પર ગુમ થઈ જાય છે. સેશન્સ ફક્ત સ્પષ્ટપણે રેકોર્ડ કરવામાં આવે ત્યારે જ પર્સિસ્ટ થાય છે                                      |

### જાણીતી મર્યાદાઓ

- **સિસ્ટમ-વ્યાપી પ્રૉક્સી મોડ** VPN ક્લાયન્ટ્સ અને SSO સહિત મશીન પરની તમામ ઍપ્લિકેશન્સને અસર કરે છે. હંમેશાં ઑટો-ડિસેબલ ટાઇમર સાથે તેનો ઉપયોગ કરો. શેર કરેલા મશીનો પર તેનો ઉપયોગ કરશો નહીં.
- **CONNECT ટનલ HTTPS**: TLS ઇન્ટરસેપ્શન સક્ષમ ન હોય ત્યાં સુધી મોડ 3 (HTTP_PROXY) HTTPS ગંતવ્યો માટે ફક્ત ટનલ મેટાડેટા કૅપ્ચર કરે છે. આ ઇરાદાપૂર્વક છે — AgentBridge cert પર તે ઍપ્સ દ્વારા વિશ્વાસ ન હોય તો પારદર્શક કૅપ્ચર તેમના માટે TLS ચકાસણીને નિષ્ફળ બનાવશે.
- **કેટલાક કમ્પોનન્ટ્સમાં હાર્ડકોડ કરેલી સ્ટ્રિંગ્સ**: કેટલાક UI કમ્પોનન્ટ્સ (F7/F8)માં થોડી સંખ્યામાં હાર્ડકોડ કરેલી સ્ટ્રિંગ્સ છે, જે હજુ સુધી i18n કીઝ હેઠળ આવરી લેવામાં આવી નથી. i18n ગૅપ રિપોર્ટમાં આને જાણીતી મર્યાદા તરીકે દસ્તાવેજીકૃત કરવામાં આવી છે; અનુગામી તબક્કામાં તેમને માઇગ્રેટ કરવામાં આવશે. અસરગ્રસ્ત સ્ટ્રિંગ્સ UIના સુશોભનાત્મક લેબલ્સ છે, જેમના કાર્યાત્મક ઉપયોગ માટે અનુવાદ જરૂરી નથી.

## §7 સમસ્યા નિવારણ

### WebSocket ડિસ્કનેક્શન

જો લાઇવ ટેઇલ "ડિસ્કનેક્ટ થયું" બતાવે:

1. સર્વર હજી ચાલી રહ્યું છે કે નહીં તે તપાસો: `GET /api/tools/traffic-inspector/capture-modes`
2. પેજ ફરીથી લોડ કરો — WebSocket ફરીથી કનેક્ટ થાય છે અને નવો સ્નૅપશૉટ મેળવે છે
3. જો સર્વર ફરી શરૂ કરવામાં આવ્યું હોય, તો ઇન-મેમરી બફર સાફ થઈ ગયું હશે — સત્ર રેકોર્ડ કરવામાં આવ્યું ન હોય તો જૂની એન્ટ્રીઓ હવે ઉપલબ્ધ નહીં હોય

### પોર્ટ 8080નો સંઘર્ષ

જો HTTP_PROXY મોડ શરૂ થવામાં નિષ્ફળ જાય:

```bash
lsof -i :8080    # પ્રક્રિયા શોધો
```

પોર્ટ બદલો:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### સિસ્ટમ પ્રૉક્સી પાછું ફેરવાયું નથી

જો સિસ્ટમ-વ્યાપી પ્રૉક્સી મોડ સક્રિય હોય ત્યારે OmniRoute ક્રૅશ થાય:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

જો ડૅશબોર્ડ શોધે કે DB સ્થિતિ મુજબ પ્રૉક્સી સક્રિય હતું, તો તે આગલી વખત લોડ થવા પર "સિસ્ટમ પ્રૉક્સી પાછું ફેરવો" વિકલ્પ પણ આપશે.

### બફર ભરેલું છે

જ્યારે બફર `INSPECTOR_BUFFER_SIZE` (ડિફૉલ્ટ 1000) સુધી પહોંચે છે, ત્યારે નવી એન્ટ્રીઓ સૌથી જૂની એન્ટ્રીઓને બહાર કાઢે છે. જો મહત્વપૂર્ણ વિનંતીઓ ખોવાઈ રહી હોય:

- `INSPECTOR_BUFFER_SIZE` વધારો (દા.ત., 5000) — આ જાળવણી માટે વધુ મેમરી વાપરે છે
- સંબંધિત સમયગાળાને DBમાં કાયમી રાખવા માટે સત્ર રેકોર્ડ કરો
