રિઝનિંગ રાઉટિંગના નિયમો હાલના મોડેલ અને કોમ્બો રાઉટિંગને વિસ્તારે છે. જ્યારે કોઈ સક્રિય નિયમ મેળ ખાતો નથી,
ત્યારે હાલનું થિંકિંગ, સફિક્સ, કનેક્શન-ડિફૉલ્ટ અને પ્રોવાઇડર-ટ્રાન્સલેશન વર્તન
યથાવત્ રહે છે.

## સંચાલન

નિયમોનું સંચાલન **Settings → Global Routing** હેઠળ ઉપલબ્ધ છે. API-કી એડિટર પસંદ કરેલી કી માટે ફિલ્ટર કરેલું
એ જ સંચાલન UI પ્રદાન કરે છે.

સંચાલન API આ રૂટ્સ દ્વારા ઉપલબ્ધ છે:

- `/api/settings/reasoning-routing-rules` પર `GET` અને `POST`
- `/api/settings/reasoning-routing-rules/[id]` પર `GET`, `PATCH`, અને `DELETE`
- `/api/settings/reasoning-routing-rules/simulate` પર `POST`

બધા રૂટ્સ `requireManagementAuth`નો ઉપયોગ કરે છે. ઇનપુટ્સને
`src/shared/validation/schemas/reasoningRouting.ts`માં રહેલી સ્કીમા વડે માન્ય કરવામાં આવે છે. સિમ્યુલેટર ક્યારેય અપસ્ટ્રીમ કૉલ કરતું નથી.

## નિયમનું નિરાકરણ

પ્રારંભિક મૂલ્યાંકન ચોક્કસપણે એક નિયમ પસંદ કરે છે. સ્કોપ્સ આ ક્રમમાં તપાસવામાં આવે છે:

1. `apiKey`
2. `combo`
3. `model`
4. `global`

કોઈ સ્કોપની અંદર, પહેલાં વધુ ઉચ્ચ `priority` જીતે છે, ત્યારબાદ ગ્લોબ પેટર્નની સરખામણીએ ચોક્કસ મોડેલ મેચ,
અને પછી સ્થિર `createdAt` તથા `id` ક્રમ. `requestTags` ફક્ત `metadata.tags`માંથી વાંચવામાં આવે છે
અને `any` અથવા `all` મેચિંગને સપોર્ટ કરે છે.

`connection` નિયમનું મૂલ્યાંકન માત્ર ત્યારે થાય છે જ્યારે કોઈ પ્રારંભિક નિયમ જીત્યો ન હોય અને કોઈ ચોક્કસ પ્રોવાઇડર કનેક્શન
પહેલેથી પસંદ થઈ ચૂક્યું હોય. તે ફક્ત એફર્ટ અને બજેટ બદલી શકે છે.

## એફર્ટ અને બજેટ

`sourceEffort` `any`, `missing`, `none`, `low`, `medium`, `high`, `xhigh`, `max`, અને
`ultra` સ્વીકારે છે. `missing`નો અર્થ એ છે કે વિનંતીમાં ન તો અલગ એફર્ટ, ન થિંકિંગ ટૉગલ,
કે ન થિંકિંગ બજેટ હોય. તેથી ફક્ત બજેટ ધરાવતો સિગ્નલ માત્ર `any` સાથે જ મેળ ખાય છે.

`effortMode`ના ત્રણ પ્રકાર છે:

- `inherit` ક્લાયન્ટ એફર્ટ જાળવી રાખે છે અને તેમ છતાં મોડેલ અથવા કોમ્બોને બદલવાની મંજૂરી આપે છે.
- `default` માત્ર ત્યારે જ `targetEffort` સેટ કરે છે જ્યારે કોઈ સ્પષ્ટ રિઝનિંગ સિગ્નલ હાજર ન હોય.
- `force` અલગ એફર્ટને `targetEffort`થી બદલે છે.

સ્વતંત્ર રીતે, `budgetAction` `preserve`, `remove`, અથવા `set` હોઈ શકે છે. `none` સાથેનું `force`
બધા ઓળખાયેલા એફર્ટ અને બજેટ ફીલ્ડ્સ દૂર કરે છે. `set` સાથે `none` અમાન્ય છે.

જાણીતા અસંગત મોડેલ્સને લક્ષ્ય બનાવતી વિનંતીઓ અપસ્ટ્રીમ કૉલ પહેલાં નકારવામાં આવે છે. કોમ્બો
લક્ષ્યો માટે, અસંગત એન્ટ્રીઓ દૂર કરવામાં આવે છે; જો એક પણ બાકી ન રહે, તો વિનંતી `400` સ્ટેટસ પરત કરે છે.
અજ્ઞાત ક્ષમતા ડેટા ચેતવણી આપે છે અને નિયમને સક્રિય રાખે છે.

## સુરક્ષા અને ટ્રાન્સપોર્ટ્સ

સ્રોત અને લક્ષ્ય મોડેલ, અથવા સ્રોત અને લક્ષ્ય કોમ્બો, હાલની API-કી
નીતિને આધીન રહે છે. રિઝનિંગનો નિયમ ક્યારેય મોડેલ, કોમ્બો, અથવા ક્વોટાની પરવાનગીઓ વિસ્તારતો નથી.

એન્જિન Chat Completions, Responses, Anthropic Messages, અને આંતરિક
Codex WebSocket પાથમાં એકીકૃત છે. WebSocket પાથ માત્ર Codex લક્ષ્ય મોડેલ્સ સ્વીકારે છે; ત્યાં કોમ્બો લક્ષ્યો
ચલાવી શકાતા નથી. નિયમનો નિર્ણય હાલના રૂટ ટ્રેસમાં કોઈ પણ સિક્રેટ વિના સંગ્રહિત થાય છે.

## પર્સિસ્ટન્સ

માઇગ્રેશન `src/lib/db/migrations/126_reasoning_routing_rules.sql`
`reasoning_routing_rules` ટેબલ બનાવે છે. નિયમો સંગ્રહિત API કીઓ, કોમ્બોઝ, અને પ્રોવાઇડર કનેક્શન્સનો સંદર્ભ આપે છે.
ડિલીટ કરવાથી સંબંધિત નિયમો સાફ થાય છે. `src/lib/db/reasoningRoutingRules.ts`માં રહેલું ડેટાબેઝ ઍક્સેસ સ્તર
વિનંતી પાથ માટે અમાન્ય કરી શકાય તેવી કૅશ જાળવે છે.

નિયમો SQLite બૅકઅપ્સ, સંપૂર્ણ ડેટાબેઝ એક્સપોર્ટ, અને config-sync બંડલમાં સામેલ કરવામાં આવે છે.
`reconcileReasoningRulesForSync` ગુમ થયેલા સંદર્ભો ધરાવતા આયાત કરેલા નિયમોને નિષ્ક્રિય કરે છે અને તે
વિરોધોની જાણ કરે છે.
