> પસંદગીથી સક્ષમ કરવાનું, મૂળભૂત રીતે બંધ (`modelVisibilityAllowlist`/`modelVisibilityDenylist` બંને ખાલી હોય તો
> `/v1/models` કેટલોગ અને દરેક `auto/*` ઉમેદવાર પૂલ બાઇટ-દર-બાઇટ સમાન રહે છે). ખર્ચ સાથે
> કોઈ સંબંધ ન હોય તેવા કારણોસર ક્યુરેટ કરેલી મોડેલ સૂચિ ઇચ્છતા ઑપરેટરો માટે
> `hidePaidModels`/`hideAutoCombos` (`src/lib/db/settings.ts`)નું સમકક્ષ સેટિંગ.

## આ શા માટે અસ્તિત્વમાં છે

`hidePaidModels` "શું આ મોડેલ મફત છે?" તેનો જવાબ આપે છે અને `hideAutoCombos` "શું `auto/*`
વર્ચ્યુઅલ idsની જાહેરાત કરવી જોઈએ?" તેનો જવાબ આપે છે — પરંતુ કોઈ પણ ઑપરેટરને મોડેલોના મનસ્વી
સબસેટને ક્યુરેટ કરવાની મંજૂરી આપતું નથી (દા.ત. કિંમતથી સ્વતંત્ર રીતે, કોઈ ચોક્કસ Claude Code /
OpenCode ક્લાયન્ટે જોવાં જોઈએ તે જ મોડેલો રજૂ કરવા). #11481 આ સુવિધાને બે સ્વતંત્ર, પસંદગીથી
સક્ષમ કરવાની string-array સેટિંગ્સ તરીકે ઉમેરે છે.

## સેટિંગ્સ

| કી                         | પ્રકાર     | મૂળભૂત | અર્થ                                                                              |
| -------------------------- | ---------- | ------ | --------------------------------------------------------------------------------- |
| `modelVisibilityDenylist`  | `string[]` | `[]`   | ઉમેદવાર સાથે મેળ ખાતી એન્ટ્રીઓ તેને કેટલોગ/ઉમેદવાર પૂલમાંથી છુપાવે છે.            |
| `modelVisibilityAllowlist` | `string[]` | `[]`   | જ્યારે ખાલી ન હોય, ત્યારે માત્ર ઉમેદવાર સાથે મેળ ખાતી એન્ટ્રીઓ જ દૃશ્યમાન રહે છે. |

બંનેમાં દરેક વધુમાં વધુ 200 અક્ષરોની વધુમાં વધુ 500 એન્ટ્રીઓ સ્વીકારવામાં આવે છે
(`src/shared/validation/settingsSchemas.ts`માં Zod દ્વારા માન્ય કરાયેલ). એન્ટ્રી આમાંથી કોઈ એક હોય છે:

- ચોક્કસ કેટલોગ id — `"gpt-4o"` (માત્ર model id) અથવા `"openai/gpt-4o"` (provider-prefixed), અથવા
- `*`/`?`નો ઉપયોગ કરતી glob પેટર્ન — દા.ત. `"openai/gpt-4*"` અથવા `"anthropic/*"` — જેને એ જ
  વહેંચાયેલ `globToRegex()` મેળાપક (`src/shared/utils/globPattern.ts`) દ્વારા ઉકેલવામાં આવે છે, જેનો
  ઉપયોગ પહેલેથી `ModelRoutingSection`ના પ્રતિ-મોડેલ combo mappings અને `freeModels.ts::matchesOnlyPaidModels`માં થાય છે.

અગ્રતા: denylistને પ્રથમ તપાસવામાં આવે છે (નકારવામાં આવેલી એન્ટ્રી હંમેશાં છુપાયેલી રહે છે, ભલે તે
allowlist સાથે પણ મેળ ખાતી હોય); જ્યારે allowlist ખાલી ન હોય, ત્યારે માત્ર તેની સાથે મેળ ખાતી
એન્ટ્રીઓ જ બચે છે.

## એક નહીં, બે નિયંત્રણ-બિંદુઓ

#6512માંથી મળેલો બોધ (માત્ર `hidePaidModels` કેટલોગ ફિલ્ટર હોવા છતાં `auto/*`ને
paid model તરફ રૂટ કરવાની મંજૂરી મળતી હતી, કારણ કે combo ઉમેદવાર પૂલ સ્વતંત્ર રીતે બનાવવામાં આવતો હતો)
અહીં પણ એ જ રીતે લાગુ પડે છે. મેળાપ predicate `isModelExposureAllowed()`
(`src/shared/utils/modelExposureList.ts`)ને બંને જગ્યાએ કૉલ કરવામાં આવે છે:

- `src/app/api/v1/models/catalog.ts` — `/v1/models` સૂચિ પોતે, એ જ પ્રતિ-સ્રોત 5
  નિયંત્રણ-બિંદુઓ પર જેને `shouldHidePaid()` પહેલેથી નિયંત્રિત કરે છે (સ્થિર `PROVIDER_MODELS`, સમન્વયિત provider rows,
  custom rows, alias-backed rows, managed-fallback rows).
- `open-sse/services/autoCombo/modelExposureFilter.ts::filterModelExposureCandidates()` — જેને
  `virtualFactory.ts::buildPreparedPool`માંથી, સમકક્ષ `filterPaidOnlyCandidates()` કૉલ પછી તરત જ
  કૉલ કરવામાં આવે છે, જેથી નકારવામાં આવેલું મોડેલ ક્યારેય `auto/*` ઉમેદવાર પૂલમાં પસંદ થઈ ન શકે.

## શું ફિલ્ટર કરવામાં આવતું નથી

`hideAutoCombos`ની હાલની વર્તણૂકને અનુસરે છે: **સ્પષ્ટ રીતે** મોકલવામાં આવેલ model id (`auto/*` દ્વારા નહીં,
અને કેટલોગ સૂચિ દ્વારા શોધાયેલું નહીં) dispatch સમયે ક્યારેય અવરોધવામાં આવતું નથી — માત્ર
જાહેરાત/ઉમેદવાર-પૂલ સભ્યપદને ફિલ્ટર કરવામાં આવે છે. આ `hidePaidModels`થી સ્વતંત્ર છે;
ઑપરેટરને ખર્ચ સાથે કોઈ સંબંધ ન હોય તેવા કારણોસર ક્યુરેટ કરેલો સેટ જોઈતો હોઈ શકે છે, તેથી બંને
સેટિંગ્સ સ્વતંત્ર AND-ed ફિલ્ટર્સ તરીકે સંયોજિત થાય છે, બિલકુલ `catalog.ts`માં હાલના multi-flag
સંયોજનની જેમ.

સેટિંગ્સ export (`GET /api/settings/export-json`)માં અન્ય કોઈપણ settings fieldની જેમ બંને arrays
યથાવત્ સામેલ થાય છે — `hidePaidModels`ના combo-step export filterથી વિપરીત, અહીં re-hydrationનું
કોઈ જોખમ નથી: exported combo stepમાં સમાવાયેલ નકારવામાં આવેલ id એ ઑપરેટરની પોતાની સ્પષ્ટ routing
પસંદગી છે, જેને export boundaryએ દૂર કરવાની જરૂર નથી.
