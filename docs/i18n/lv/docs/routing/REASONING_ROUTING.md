Spriešanas maršrutēšanas kārtulas paplašina esošo modeļu un kombināciju maršrutēšanu. Ja neviena aktīva kārtula neatbilst,
esošā domāšanas, sufiksu, savienojuma noklusējumu un pakalpojumu sniedzēja tulkošanas darbība paliek
nemainīga.

## Pārvaldība

Kārtulu pārvaldība ir pieejama sadaļā **Iestatījumi → Globālā maršrutēšana**. API atslēgu redaktors nodrošina
to pašu pārvaldības saskarni, kas filtrēta pēc atlasītās atslēgas.

Pārvaldības API ir pieejama šajos maršrutos:

- `GET` un `POST` maršrutā `/api/settings/reasoning-routing-rules`
- `GET`, `PATCH` un `DELETE` maršrutā `/api/settings/reasoning-routing-rules/[id]`
- `POST` maršrutā `/api/settings/reasoning-routing-rules/simulate`

Visi maršruti izmanto `requireManagementAuth`. Ievaddati tiek validēti ar shēmām no
`src/shared/validation/schemas/reasoningRouting.ts`. Simulators nekad neveic augšupstraumes izsaukumu.

## Kārtulu atrisināšana

Agrīnā izvērtēšana atlasa tieši vienu kārtulu. Tvērumi tiek pārbaudīti šādā secībā:

1. `apiKey`
2. `combo`
3. `model`
4. `global`

Tvēruma ietvaros vispirms uzvar augstāka `priority` vērtība, pēc tam precīza modeļa atbilstība pār globu rakstu,
kam seko stabila kārtošana pēc `createdAt` un `id`. `requestTags` tiek nolasīti tikai no `metadata.tags`
un atbalsta `any` vai `all` atbilstību.

`connection` kārtula tiek izvērtēta tikai tad, ja neviena agrīnā kārtula nav uzvarējusi un jau ir atlasīts konkrēts pakalpojumu sniedzēja
savienojums. Tā drīkst mainīt tikai piepūles līmeni un budžetu.

## Piepūles līmenis un budžets

`sourceEffort` pieņem `any`, `missing`, `none`, `low`, `medium`, `high`, `xhigh`, `max` un
`ultra`. `missing` nozīmē, ka pieprasījums nesatur ne diskrētu piepūles līmeni, ne domāšanas slēdzi,
ne domāšanas budžetu. Tādēļ signālam, kurā norādīts tikai budžets, atbilst vienīgi `any`.

`effortMode` ir trīs varianti:

- `inherit` saglabā klienta piepūles līmeni, vienlaikus ļaujot mainīt modeli vai kombināciju.
- `default` iestata `targetEffort` tikai tad, ja nav norādīts neviens tiešs spriešanas signāls.
- `force` aizstāj diskrēto piepūles līmeni ar `targetEffort`.

Neatkarīgi no tā `budgetAction` var būt `preserve`, `remove` vai `set`. `force` kopā ar `none` noņem
visus atpazītos piepūles līmeņa un budžeta laukus. `none` kopā ar `set` nav derīga kombinācija.

Pieprasījumi, kuru mērķis ir zināmi nesaderīgi modeļi, tiek noraidīti pirms augšupstraumes izsaukuma. Kombināciju
mērķiem nesaderīgie ieraksti tiek noņemti; ja neviens nepaliek, pieprasījums atgriež statusu `400`.
Nezināmi spēju dati rada brīdinājumu, un kārtula paliek aktīva.

## Drošība un transporti

Avota un mērķa modelim vai avota un mērķa kombinācijai joprojām ir piemērojama esošā API atslēgas
politika. Spriešanas kārtula nekad nepaplašina modeļu, kombināciju vai kvotu atļaujas.

Dzinējs ir integrēts Chat Completions, Responses, Anthropic Messages un iekšējā
Codex WebSocket ceļā. WebSocket ceļš pieņem tikai Codex mērķa modeļus; kombināciju mērķus tajā nevar
izpildīt. Kārtulas lēmums tiek saglabāts esošajā maršruta trasē bez noslēpumiem.

## Pastāvīgā glabāšana

Migrācija `src/lib/db/migrations/126_reasoning_routing_rules.sql` izveido tabulu
`reasoning_routing_rules`. Kārtulas atsaucas uz saglabātām API atslēgām, kombinācijām un pakalpojumu sniedzēju savienojumiem.
Dzēšana iztīra saistītās kārtulas. Datubāzes piekļuves slānis
`src/lib/db/reasoningRoutingRules.ts` uztur pieprasījumu ceļam paredzētu invalidējamu kešatmiņu.

Kārtulas tiek iekļautas SQLite dublējumos, pilnā datubāzes eksportā un konfigurācijas sinhronizācijas pakotnē.
`reconcileReasoningRulesForSync` atspējo importētās kārtulas ar trūkstošām atsaucēm un ziņo par šiem
konfliktiem.
