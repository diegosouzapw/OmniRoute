`open-sse/config/providerPluginManifest.ts` definē JSON drošu pakalpojumu sniedzēja
spraudņa līgumu. `open-sse/config/providerPluginManifestRegistry.ts` sasaista šo
līgumu ar pašreizējo pakalpojumu sniedzēju reģistru blakusprocesiem, piemēram, Bifrost,
CLIProxyAPI vai nākotnes Go/Rust maršrutētājam. TypeScript reģistrs joprojām ir
patiesības avots, taču blakusprocesi var izmantot manifestu, neimportējot
izpildītāja kodu, OAuth noklusējuma vērtības, galvenes vai procesa vides stāvokli.

Tas pats manifests ir pieejams, izmantojot HTTP:
`GET /api/v1/provider-plugin-manifest` ārpus procesa palaistiem blakusprocesiem.

OmniRoute norāda šo URL Bifrost un CLIProxyAPI, izmantojot
`X-OmniRoute-Provider-Manifest-Url` pieprasījuma galveni. Iestatiet
`OMNIROUTE_PROVIDER_MANIFEST_URL`, ja blakusprocesam lokālā pieprasījuma izcelsmes
vietā ir nepieciešams publisks vai konteinera tīkla URL.

## Manifesta atsvaidzināšana

HTTP galapunkts atgriež `Cache-Control: public, max-age=60` un stipru
`ETag`. Blakusprocesam ir jāsaglabā pēdējais validētais manifests un atsvaidzināšanas
laikā jānosūta tā ETag laukā `If-None-Match`. Atbildei `304 Not Modified` nav satura;
blakusprocess turpina izmantot kešatmiņā saglabāto manifestu. Ja validēta kešatmiņā
saglabāta manifesta nav, blakusprocesam jāveic beznosacījuma pieprasījums, nevis
jāpieņem `304`.

## Mērķis

Virzīt pakalpojumu sniedzēju metadatus uz spraudņa līgumu, lai pieprasījumu aktīvo
ceļu ar laiku varētu pārvaldīt mazāka latentuma blakusprocess, kamēr OmniRoute
saglabā TypeScript maršrutu kā politiku piemērošanas vārteju un rezerves variantu.
Manifests ir papildinošs: pats par sevi tas nemaina pieprasījumu maršrutēšanu.

## Līgums

Manifests satur:

- pakalpojumu sniedzēja ID un aizstājvārdu
- augšupstraumes formātu un izpildītāja nosaukumu
- autentifikācijas tipu, autentifikācijas galveni un neobligātu autentifikācijas prefiksu
- statiskus galapunkta metadatus
- piemērotību blakusprocesam un skaidrus iemeslus, kad pakalpojumu sniedzējam jāpaliek TS ceļā
- JSON drošus modeļa metadatus, piemēram, konteksta garumu, attēlu apstrādes/spriešanas pazīmes un
  neatbalstītus parametrus
- iespēju tagus, tostarp `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` un `usage-supported`

Manifests apzināti neietver:

- OAuth klienta noslēpumus un noklusējuma slepenās vērtības
- izpildlaika vides vērtību noteikšanu
- pieprasījumu galvenes un publisko akreditācijas datu palīgfunkcijas
- dinamiskus URL veidotājus
- izpildītāja funkcijas
- sesiju pūla iekšējo struktūru

## Iespēju tagi

`capabilities` ir no reģistra ieraksta atvasināts sakārtots tagu masīvs. Integrētājiem
tas jāuzskata par mašīnlasāmu atbildi uz jautājumu „ko šis pakalpojumu sniedzējs spēj darīt”,
nevis atkārtoti jālasa TypeScript pirmkods.

| Tags                 | Nozīme                                                                              |
| -------------------- | ----------------------------------------------------------------------------------- |
| `apikey`             | Pieņem API atslēgu (`authType` ir `apikey` vai `optional`).                         |
| `oauth`              | Izmanto OAuth vai sesijas plūsmu.                                                   |
| `responses`          | Nodrošina OpenAI Responses API bāzes URL.                                           |
| `passthrough-models` | Apkalpo modeļus tieši no augšupstraumes, nevis statiska kataloga.                   |
| `custom-executor`    | Izmanto izpildītāju, kas nav noklusējuma izpildītājs, tādēļ paliek TypeScript ceļā. |
| `sidecar-candidate`  | Atspoguļo `sidecar.eligible` — var droši apsvērt importēšanai blakusprocesā.        |
| `usage-fetch`        | Ir piesaistīts lietojuma vai kvotas izgūšanas mehānisms (`getUsageForProvider`).    |
| `usage-supported`    | Lietojuma API pieņem šo pakalpojumu sniedzēju (`isSupportedUsageConnection`).       |

`usage-fetch` ir paredzēts tikai noteikšanai. Tas norāda, ka OmniRoute prot nolasīt
pakalpojumu sniedzēja lietojumu; tas neaktivizē izgūšanu, nemaina kvotu semantiku un
nenozīmē, ka informācijas paneļa kvotu logrīks šim pakalpojumu sniedzējam ir iespējots —
šī logrīka pieejamību atsevišķi kontrolē `USAGE_SUPPORTED_PROVIDERS`. Patiesības avots ir
`USAGE_FETCHER_PROVIDERS` failā
`open-sse/services/usage/fetcherProviders.ts`.

Šis saraksts ir indeksēts pēc virknēm, ko pieņem lietojuma dispečers, tādēļ tajā ir
sajaukti kanoniskie ID un aizstājvārdi un tas ir nedaudz garāks par tagoto pakalpojumu
sniedzēju skaitu: ierakstiem, kas manifesta reģistrā nav tērzēšanas pakalpojumu sniedzēji
(piemēram, `firecrawl` meklēšanas pakalpojumu sniedzējam un `amazon-q` ACP pakalpojumu
sniedzējam), nav manifesta ieraksta, ko tagot.

`usage-supported` norāda, vai servera un informācijas paneļa lietojuma maršruti pieņem
savienojumu ar attiecīgo pakalpojumu sniedzēju. Tas atspoguļo
`isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`) un
`supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), un abus kontrolē
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). Atšķirībā no
`usage-fetch` tas tiek pievienots tikai pakalpojumu sniedzēja ID — izpildlaika pārbaude veic
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` bez aizstājvārdu atrisināšanas, tādēļ manifests
saglabā to pašu noteikumu. Abiem tagiem ir atšķirīgas piemērošanas robežas: 3 pakalpojumu
sniedzējiem ir tikai `usage-fetch` (`opencode`, `opencode-zen`, `xai`), bet 1 pakalpojumu
sniedzējam ir tikai `usage-supported` (`xiaomi-mimo-token-plan`), tādēļ viens tags
nenozīmē otra esamību.

## Sidecar izmantošana

Sidecar komponentiem `sidecar.eligible` jāuztver kā konservatīvs kandidāta signāls, nevis kā beznosacījumu maršrutēšanas lēmums. Pirmajam importēšanas mērķim jābūt pakalpojumu sniedzējiem, kuri izmanto API atslēgu, statisku galapunktu un noklusējuma izpildītāju. Pakalpojumu sniedzēji ar pielāgotiem tīmekļa izpildītājiem, OAuth/sesiju plūsmām, dinamiskiem URL veidotājiem vai pūla konfigurāciju paliek TypeScript atkāpšanās ceļā, līdz sidecar ievieš līdzvērtīgu darbību un telemetrija apliecina paritāti.

Ieteicamie migrācijas posmi:

1. Ģenerēt un validēt pakalpojumu sniedzēju spraudņu manifestu no TS reģistra.
2. Iemācīt Bifrost vai CLIProxyAPI importēt manifestu pakalpojumu sniedzējiem ar API atslēgu un statisku galapunktu.
3. Maršrutēt piemērotos pakalpojumu sniedzējus caur sidecar aiz `OMNIROUTE_RELAY_BACKEND`, vienlaikus saglabājot iespējotu TS atkāpšanās mehānismu.
4. Pārcelt pakalpojumu sniedzējus tikai tad, kad veiksmīgo pieprasījumu īpatsvars, p99 latentums, straumēšanas darbība un neatbalstīto parametru apstrāde atbilst TS ceļam.
5. Pievienot sidecar paredzētus spraudņus pielāgotajiem izpildītājiem, vienlaikus apstrādājot vienu pakalpojumu sniedzēju saimi.

## Kāpēc pakalpojumu sniedzējus neiegult tieši Next

Next priekšgals nedrīkst pārvaldīt pakalpojumu sniedzēju izpildi. Tam jāizsauc API robeža. Pēc tam aizmugursistēma var izlemt, vai izmantot TypeScript izpildītāju, Bifrost, CLIProxyAPI vai nākotnē izstrādātu vietējo sidecar. Tādējādi pieprasījumu parakstīšana, atļauto vienumu saraksta pārbaudes, DB politika un atkāpšanās darbība tiek centralizēta pirms jebkādas nodošanas sidecar komponentam.
