> **ĪSUMĀ**: `open-sse/` ir galvenais straumēšanas dzinējs, kas apkalpo katru LLM pieprasījumu OmniRoute sistēmā. Tajā ir aptuveni 1 400 failu, kuros īstenota pieprasījumu apstrādes ķēde, izpildītāji, servisi, MCP serveris un tulkošanas slānis. Šajā ceļvedī izskaidrots, kā šīs daļas darbojas kopā.

**Avots:** `open-sse/` (darbvietas pakotne, aptuveni 1 440 ar testiem nesaistītu `.ts` failu)

## Kāpēc atsevišķa darbvietas pakotne?

`open-sse/` ir **patstāvīga darbvieta** OmniRoute monorepozitorijā vairāku iemeslu dēļ:

1. **Atkārtota izmantojamība** — `open-sse` tiek publicēts npm kā `@omniroute/open-sse`, tādēļ citi projekti to var izmantot neatkarīgi
2. **Skaidras robežas** — straumēšanas dzinējs ir nodalīts no OmniRoute specifiskā lietotāja saskarnes/DB slāņa
3. **Veiktspēja** — dzinējam nav Next.js atkarību, tādēļ CLI/serverless kontekstos tiek nodrošināta ātrāka aukstā palaišana
4. **Versiju pārvaldība** — `open-sse` var izlaist jaunās versijas pēc sava grafika

```json
// package.json
"workspaces": ["open-sse"]
```

## Pieprasījuma apstrādes ķēde

Katrs LLM pieprasījums iziet cauri **5 posmu apstrādes ķēdei**:

```
                              ┌──────────────┐
   HTTP pieprasījums           │  1. MARŠRUTĒT│   kombinācijas atrisināšana, modeļa atlase
   (Next.js maršruts)          └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. TULKOT   │   formāta pārveidošana (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. IZPILDĪT │   pakalpojumu sniedzēja izpildītājs, HTTP, atkārtošana, atslēdzējs
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STRAUMĒT │   SSE pārveidošana, pretspiediens
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. REĢISTRĒT│   lietojuma uzskaite, izsaukumu žurnāls, kļūdu klasificēšana
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP atbilde (SSE vai JSON)
```

### 1. posms: Maršrutēšana (services/combo.ts)

**Ieejas punkts**: `handleComboChat()` failā `services/combo.ts`

Pieprasījums tiek sasaistīts ar konkrētu `(provider, model, account, credentials)` kortežu:

- Atrast kombināciju pēc ID (vai izveidot virtuālu kombināciju `auto/*` modeļiem)
- Lietot maršrutēšanas stratēģiju (prioritāte, svērta atlase, cikliska atlase u.c.)
- Izfiltrēt neveselīgos pakalpojumu sniedzējus (ķēdes atslēdzējs)
- Izvēlēties nākamo derīgo mērķi

`auto/*` modeļiem šajā posmā arī:

- Tiek izpildīts **16 faktoru vērtēšanas** algoritms (`services/autoCombo/`)
- Tiek atlasīts `provider+model` pāris, ņemot vērā darbspēju, izmaksas, latentumu u.c.

### 2. posms: Tulkošana (translator/)

Ja avota formāts (piemēram, OpenAI) atšķiras no mērķa formāta (piemēram, Claude), pieprasījums tiek **tulkots**:

- Sistēmas uzvedne → sistēmas ziņojums
- Rīku definīcijas → pakalpojumu sniedzējam specifisks rīku formāts
- Spriešanas/domāšanas parametri → pakalpojumu sniedzējam specifiski ekvivalenti
- Ziņojumu lomu normalizēšana (`developer` → `system` pakalpojumu sniedzējiem, kas nav OpenAI)

`translator/index.ts` eksportē:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### 3. posms: Izpilde (executors/)

**Ieejas punkts**: `getExecutor(providerId).execute(request, options)`

Visi pakalpojumu sniedzēji izmanto `DefaultExecutor` (`executors/default.ts`), izmantojot `getExecutor()` fabrikas atkāpšanās mehānismu. Izpildītājs:

- Izveido augšupstraumes URL (`buildUrl()`)
- Pievieno pakalpojumu sniedzējam specifiskas galvenes (`buildHeaders()`)
- Pārveido pieprasījuma pamatdaļu (`transformRequest()`)
- Nosūta HTTP pieprasījumu, izmantojot atkārtošanu un eksponenciālu aizturi
- Vajadzības gadījumā apstrādā autentifikācijas atsvaidzināšanu (OAuth pakalpojumu sniedzējiem)

Visi izpildītāji paplašina `BaseExecutor` (`executors/base.ts`, 1170 koda rindas), kas nodrošina:

- Kopīgu atkārtošanas loģiku
- Starpniekservera integrāciju
- Ķēdes atslēdzēja integrāciju
- Lietojuma reģistrēšanas āķus

### 4. posms: Straumēšana (utils/stream.ts)

Straumēšanas atbildēm izpildītājs atgriež **ReadableStream**. Apstrādātājs:

- Novada datus caur SSE pārveidotāju (`createSSETransformStreamWithLogger`)
- Izmanto periodiskus kontrolsignālus, lai noteiktu pārtrauktus savienojumus
- Korekti apstrādā klienta atvienošanos (`pipeWithDisconnect`)
- Pārveido SSE → JSON klientiem, kuri neizmanto straumēšanu

Atbildēm bez straumēšanas izpildītājs atgriež parsētu JSON objektu, kas tiek nodots tālāk bez izmaiņām.

### 5. posms: Reģistrēšana (services/usage.ts)

Pēc atbildes (veiksmīgas vai neveiksmīgas) tiek reģistrēti lietojuma dati:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` no atbildes
- `cost_usd`, kas aprēķināts, izmantojot cenu datus
- `latency_ms`, `status`, `error_class`, ja pieprasījums neizdevās
- Saglabāti tabulā `usage_history`

Izsaukumu žurnālu artefakti (ja iespējoti) tiek ierakstīti `${DATA_DIR}/call_logs/`.

## Galveno failu padziļināta izpēte

### chatCore.ts (5977 rindas)

**Galvenais pieprasījumu apstrādātājs**. Neskatoties uz tā apjomu, tam ir skaidra struktūra:

```ts
// chatCore.ts pseidostruktūra
export async function handleChat(request: NextRequest) {
  // 1. Autentifikācija + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Pieprasījuma ķermeņa validācija
  const body = await parseRequestBody(request);

  // 3. Formāta noteikšana + tulkošana
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo maršrutēšana
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Turpināt ar nākamo mērķi
    }
  }

  // 5. Avārijas rezerves variants
  return await emergencyFallback(body);
}
```

Lai gan tā ir viena milzīga funkcija, tā ir organizēta **komentētās sadaļās**, kas atbilst 5 posmu konveijeram.

// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);

    try {
      return await handleSingleModel(target, body);

## Izpildītāji (150 moduļi)

Lielākoties viens fails uz katru nodrošinātāju. Visas izpildītāju klases manto no `BaseExecutor` un pārdefinē to, kas atšķiras; pārējie moduļi ir katra nodrošinātāja palīgmoduļi (rīku shēmas, fetch/TTS adapteri, īpatnību apstrādātāji).

### Tipiskie modeļi

Nodrošinātāji tiek atrisināti ar `getExecutor(providerId)`, kas atgriež konfigurēto izpildītāju. Ar OpenAI/Anthropic saderīgie nodrošinātāji izmanto `DefaultExecutor` (`executors/default.ts`). Nodrošinātājam raksturīgā uzvedība (bāzes URL, autentifikācijas galvenes, API versija) tiek konfigurēta `open-sse/config/providers/`, savukārt pieprasījuma ķermeņa transformācijas tiek apstrādātas `open-sse/translator/`.

**Pielāgoto URL** nosaka nodrošinātāja konfigurācijā:

```ts
// Nodrošinātāja konfigurācija open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Pielāgota autentifikācija** tiek nodrošināta caur nodrošinātāju reģistra autentifikācijas konfigurāciju (API atslēga, OAuth, galveņu profili).

**Pielāgotas pieprasījuma ķermeņa** transformācijas (piemēram, Anthropic atdala `system` no `messages`) tiek reģistrētas katram nodrošinātājam `open-sse/translator/`.

````

### Izpildītāju fabrika

`executors/index.ts` eksportē `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Atrisināšana notiek caur `ExecutorRegistry` (`executors/registry.ts`): katrs specializētais izpildītājs ir deklarēts `executors/index.ts` iebūvētajā tabulā un reģistrēts ar `registerExecutor(alias, instance)` moduļa ielādes laikā; `getExecutor()` vēršas pie reģistra un jebkuram nodrošinātājam bez specializēta ieraksta atkāpjas uz memoizētu `DefaultExecutor`. Pilno alias → izpildītājs kartējumu raksturo zelta tests `tests/unit/executor-map-golden.test.ts`.

## Tulkotāji

Tulko starp **3 formātiem**: OpenAI, Anthropic, Gemini, kā arī jauno Responses API.

### Kad notiek tulkošana

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Biežākie tulkojumi:

- `OpenAI → Anthropic`: atsevišķs `system` lauks, `x-api-key` galvene
- `OpenAI → Gemini`: `contents`, nevis `messages`, un `systemInstruction`
- `OpenAI → Responses API`: `input` masīvs, `previous_response_id` stāvoklis

### Apstrādātie robežgadījumi

- `developer` loma → `system` pakalpojumu sniedzējiem, kas nav OpenAI
- `system` loma → apvienota ar pirmo lietotāja ziņojumu GLM/ERNIE gadījumā
- `json_schema` → Gemini `responseMimeType` + `responseSchema`
- `tools` → pakalpojumu sniedzējam specifisks rīku formāts
- Domāšanas parametri (o1, Claude) → pakalpojumu sniedzējam specifiski ekvivalenti

## MCP serveris

`open-sse/mcp-server/` realizē **Model Context Protocol** serveri:

- **110 rīki** (pakalpojumu sniedzēju pārvaldība, kombinācijas, atmiņa, kešatmiņa, saspiešana, starpniekserveris, prasmes, spēliskošana, spraudņi, Notion, Obsidian, lokālais korpuss)
- **3 transporti**: stdio, SSE, Streamable HTTP
- **33 tvērumi** detalizētai autorizācijai

### Rīku reģistrēšana

Rīki ir reģistrēti kā atsevišķi faili mapē `open-sse/mcp-server/tools/`, un katrs no tiem eksportē nosaukumu, shēmu, apstrādātāju un tvērumu:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transporti

```ts
// stdio (CLI lietojums)
startMcpStdio(server);

// SSE (HTTP balstīta straumēšana)
startMcpSse(server, port);

// Streamable HTTP (modernais MCP)
startMcpStreamable(server, port);
```

### Autorizācija

Katrs rīka izsaukums tiek pakļauts tvēruma pārbaudēm (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Transformatori

`open-sse/transformer/` veic pārveidošanu starp **Chat Completions** un **Responses API** formātiem.

### Kāpēc nepieciešams atsevišķs transformators?

Responses API ir OpenAI jaunais formāts ar **sarunām, kas saglabā stāvokli** (`previous_response_id`). Kad klients nosūta Responses pieprasījumu, OmniRoute:

1. Iekšēji pārveido Responses → Chat Completions
2. Nosūta to pakalpojumu sniedzējam (jebkuram pakalpojumu sniedzējam, kas atbalsta Chat Completions)
3. Pārveido atbildi atpakaļ Responses formātā
4. Straumē pārveidoto atbildi klientam

Transformators (`transformer/responsesTransformer.ts`) nodrošina:

```ts
createResponsesApiTransformStream(): TransformStream
```

Tas apstrādā:

- `response.output_item.added` notikumus
- `response.output_text.delta` notikumus
- `response.completed` notikumu
- Rīku izsaukumu kartēšanu (`function_call` ↔ `tool_calls`)

## Jauna komponenta pievienošana

### Jauna pakalpojuma pievienošana

1. Izveidojiet `open-sse/services/[serviceName].ts` ar skaidri noteiktu atbildību
2. Eksportējiet galveno apstrādātāja funkciju un visas konstantes
3. Pievienojiet vienībtestus failā `tests/unit/services/[serviceName].test.mjs`
4. Integrējiet pieprasījumu konveijerā failā `handlers/chatCore.ts` (ja tas ir saistīts ar maršrutēšanu)
5. Atjauniniet maršrutēšanas loģiku failā `combo.ts`, ja pakalpojums ietekmē mērķa izvēli
6. Dokumentējiet šajā failā

### Jauna izpildītāja pievienošana

1. Izveidojiet `open-sse/executors/[provider].ts`, paplašinot `BaseExecutor`
2. Reģistrējiet failā `config/providerRegistry.ts`
3. Pievienojiet `executors/index.ts` fabrikai
4. Pievienojiet izpildītāja vienībtestus
5. Dokumentējiet failā `docs/architecture/ARCHITECTURE.md`

### Jauna MCP rīka pievienošana

1. Izveidojiet vai atjauniniet `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definējiet ievades Zod shēmu
3. Reģistrējiet rīku failā `mcp-server/index.ts`
4. Pievienojiet tvērumu matricai direktorijā `mcp-server/auth/`
5. Pievienojiet vienībtestus
