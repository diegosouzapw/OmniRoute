> **Kort fortalt**: `open-sse/` er den centrale streamingmotor, som driver alle LLM-anmodninger i OmniRoute. Den indeholder ~1.400 filer, der implementerer anmodningspipelinen, eksekveringskomponenter, tjenester, MCP-serveren og oversættelseslaget. Denne vejledning forklarer, hvordan delene hænger sammen.

**Kilde:** `open-sse/` (workspace-pakke, ~1.440 `.ts`-filer, som ikke er testfiler)

---

## Hvorfor en separat workspace-pakke?

`open-sse/` er et **selvstændigt workspace** i OmniRoute-monorepoet af flere årsager:

1. **Genbrugelighed** — `open-sse` udgives som `@omniroute/open-sse` på npm, så andre projekter kan bruge den uafhængigt
2. **Klare grænser** — streamingmotoren er afkoblet fra OmniRoute-specifikke UI-/DB-lag
3. **Ydeevne** — motoren har ingen Next.js-afhængigheder, hvilket muliggør hurtigere koldstarter i CLI-/serverless-sammenhænge
4. **Versionsstyring** — `open-sse` kan udgives efter sin egen tidsplan

```json
// package.json
"workspaces": ["open-sse"]
```

## Anmodningspipelinen

Alle LLM-anmodninger gennemløber en **pipeline med 5 faser**:

```
                              ┌──────────────┐
   HTTP-anmodning              │  1. ROUTE    │   combo-opløsning, modelvalg
   (Next.js-rute)              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. OVERSÆT  │   formatkonvertering (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. EKSEKVER │   udbydereksekvering, HTTP, genforsøg, afbryder
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAM   │   SSE-transformering, modtryk
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. REGISTRER│   brugsregistrering, kaldslog, fejlklassificering
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP-svar (SSE eller JSON)
```

### Fase 1: Routing (services/combo.ts)

**Indgangspunkt**: `handleComboChat()` i `services/combo.ts`

Opløser anmodningen til en konkret tuple af `(provider, model, account, credentials)`:

- Slå comboen op efter ID (eller opbyg en virtuel combo for `auto/*`-modeller)
- Anvend routingstrategien (prioritet, vægtet, round-robin osv.)
- Frasortér udbydere med driftsproblemer (circuit breaker)
- Vælg det næste brugbare mål

For `auto/*`-modeller gør denne fase også følgende:

- Kører algoritmen til **scoring ud fra 16 faktorer** (`services/autoCombo/`)
- Vælger et `provider+model`-par baseret på driftstilstand, omkostninger, latenstid osv.

### Fase 2: Oversættelse (translator/)

Hvis kildeformatet (f.eks. OpenAI) adskiller sig fra målformatet (f.eks. Claude), bliver anmodningen **oversat**:

- Systemprompt → systemmeddelelse
- Værktøjsdefinitioner → udbyderspecifikt værktøjsformat
- Parametre for ræsonnering/tænkning → udbyderspecifikke ækvivalenter
- Normalisering af meddelelsesroller (`developer` → `system` for andre end OpenAI)

`translator/index.ts` eksponerer:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Fase 3: Eksekvering (executors/)

**Indgangspunkt**: `getExecutor(providerId).execute(request, options)`

Alle udbydere bruger `DefaultExecutor` (`executors/default.ts`) via fallback-mekanismen i `getExecutor()`-factoryen. Eksekveringskomponenten:

- Opbygger upstream-URL'en (`buildUrl()`)
- Tilføjer udbyderspecifikke headere (`buildHeaders()`)
- Transformerer anmodningens body (`transformRequest()`)
- Sender HTTP-anmodningen med genforsøg + eksponentiel backoff
- Håndterer opdatering af godkendelse efter behov (OAuth-udbydere)

Alle eksekveringskomponenter udvider `BaseExecutor` (`executors/base.ts`, 1170 kodelinjer), som leverer:

- Fælles logik til genforsøg
- Proxyintegration
- Integration med circuit breaker
- Hooks til registrering af forbrug

### Fase 4: Streaming (utils/stream.ts)

Ved streamede svar returnerer eksekveringskomponenten en **ReadableStream**. Håndteringen:

- Sender data gennem en SSE-transformering (`createSSETransformStreamWithLogger`)
- Anvender heartbeat-pings til at registrere døde forbindelser
- Håndterer afbrydelse fra klienten på en kontrolleret måde (`pipeWithDisconnect`)
- Transformerer SSE → JSON for klienter uden streaming

Ved svar uden streaming returnerer eksekveringskomponenten et parset JSON-objekt, som videresendes uændret.

### Fase 5: Registrering (services/usage.ts)

Efter svaret (uanset om det lykkes eller mislykkes) registreres forbruget:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` fra svaret
- `cost_usd` beregnet ud fra prisdata
- `latency_ms`, `status`, `error_class`, hvis det mislykkes
- Gemmes i tabellen `usage_history`

Artefakter fra kaldeloggen (hvis aktiveret) skrives til `${DATA_DIR}/call_logs/`.

## Dybdegennemgang af nøglefiler

### chatCore.ts (5977 linjer)

Den **primære request-handler**. Trods dens størrelse har den en klar struktur:

```ts
// Pseudostruktur for chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Godkendelse + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Validering af body
  const body = await parseRequestBody(request);

  // 3. Formatregistrering + oversættelse
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo-routing
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Fortsæt til næste target
    }
  }

  // 5. Nødfallback
  return await emergencyFallback(body);
}
```

Selvom det er én stor funktion, er den organiseret i **sektioner med kommentarer**, der svarer til pipelinens 5 faser.

### combo.ts (4456 kodelinjer)

**Routingmotoren**, der omsætter en combo til en ordnet liste over targets.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

Understøtter **19 routingstrategier** (se `src/shared/constants/routingStrategies.ts`):

| Strategi            | Funktionsmåde                                                                   |
| ------------------- | ------------------------------------------------------------------------------- |
| `priority`          | Ordnet liste med første target som prioritet                                    |
| `weighted`          | Sandsynlighedsbaseret efter vægt pr. target                                     |
| `round-robin`       | Gennemløb targets i rækkefølge                                                  |
| `context-relay`     | Overdrag kontekst mellem targets                                                |
| `fill-first`        | Opfyld kvoten, før der skiftes til næste                                        |
| `p2c`               | Valg mellem to muligheder                                                       |
| `random`            | Ensartet tilfældig udvælgelse                                                   |
| `least-used`        | Vælg det target, der har været brugt færrest gange for nylig                    |
| `cost-optimized`    | Billigste velfungerende target først                                            |
| `reset-aware`       | Tager højde for udbydernes nulstillingsvinduer                                  |
| `reset-window`      | Routing baseret på nulstillingsvinduer                                          |
| `headroom`          | Størst resterende kvotemargen først                                             |
| `strict-random`     | Reelt ensartet (ingen kvalitetsvægtning)                                        |
| `auto`              | Brug scoring med 16 faktorer (`autoCombo/`)                                     |
| `lkgp`              | Senest kendte velfungerende udbyder først                                       |
| `context-optimized` | Bedst til requests med lang kontekst                                            |
| `fusion`            | Send parallelt til et panel, og syntetisér derefter via en dommer (`fusion.ts`) |

## Executors (75+ filer)

Én fil pr. udbyder. De udvider alle `BaseExecutor` og tilsidesætter det, der afviger.

### Fælles mønstre

Udbydere opløses via `getExecutor(providerId)`, som returnerer den konfigurerede executor. OpenAI/Anthropic-kompatible udbydere bruger `DefaultExecutor` (`executors/default.ts`). Udbyderspecifik adfærd (basis-URL, godkendelsesheaders, API-version) konfigureres i `open-sse/config/providers/`, mens transformationer af anmodningens body håndteres i `open-sse/translator/`.

**Brugerdefineret URL** angives via udbyderkonfigurationen:

```ts
// Udbyderkonfiguration i open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Brugerdefineret godkendelse** håndteres via udbyderregistreringens godkendelseskonfiguration (API-nøgle, OAuth, headerprofiler).

**Brugerdefinerede transformationer af anmodningens body** (f.eks. at Anthropic adskiller `system` fra `messages`) registreres pr. udbyder i `open-sse/translator/`.

````

### Executor-fabrikken

`executors/index.ts` eksporterer `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Opløsningen går gennem `ExecutorRegistry` (`executors/registry.ts`): Hver specialiseret executor deklareres i den indbyggede tabel i `executors/index.ts` og registreres via `registerExecutor(alias, instance)`, når modulet indlæses; `getExecutor()` slår op i registreringen og falder tilbage til en memoiseret `DefaultExecutor` for enhver udbyder uden en specialiseret post. Den komplette alias → executor-tilknytning er beskrevet af golden-testen `tests/unit/executor-map-golden.test.ts`.

## Oversættere

Oversæt mellem **3 formater**: OpenAI, Anthropic, Gemini samt det nye Responses API.

### Hvornår oversættelse finder sted

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Almindelige oversættelser:

- `OpenAI → Anthropic`: separat `system`-felt, `x-api-key`-header
- `OpenAI → Gemini`: `contents` i stedet for `messages`, `systemInstruction`
- `OpenAI → Responses API`: `input`-array, `previous_response_id`-tilstand

### Håndterede særtilfælde

- Rollen `developer` → `system` for andre end OpenAI
- Rollen `system` → flettes ind i den første brugermeddelelse for GLM/ERNIE
- `json_schema` → Geminis `responseMimeType` + `responseSchema`
- `tools` → udbyderspecifikt værktøjsformat
- Thinking-parametre (o1, Claude) → udbyderspecifikke ækvivalenter

## MCP-server

`open-sse/mcp-server/` implementerer **Model Context Protocol**-serveren:

- **110 værktøjer** (udbyderadministration, kombinationer, hukommelse, cache, komprimering, proxy, færdigheder, gamification, plugins, Notion, Obsidian, lokalt korpus)
- **3 transportmekanismer**: stdio, SSE, Streamable HTTP
- **33 scopes** til detaljeret godkendelse

### Registrering af værktøjer

Værktøjer registreres som separate filer i `open-sse/mcp-server/tools/`, hvor hver fil eksporterer et navn, et skema, en handler og et scope:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transportmekanismer

```ts
// stdio (CLI-brug)
startMcpStdio(server);

// SSE (HTTP-baseret streaming)
startMcpSse(server, port);

// Streamable HTTP (moderne MCP)
startMcpStreamable(server, port);
```

### Godkendelse

Hvert værktøjskald gennemgår scope-kontroller (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Transformere

`open-sse/transformer/` konverterer mellem formaterne **Chat Completions** og **Responses API**.

### Hvorfor en separat transformer?

Responses API er OpenAI's nye format med **tilstandsbevarende samtaler** (`previous_response_id`). Når en klient sender en Responses-anmodning, gør OmniRoute følgende:

1. Konverterer internt Responses → Chat Completions
2. Sender til udbyderen (enhver udbyder, der understøtter Chat Completions)
3. Konverterer svaret tilbage til Responses-formatet
4. Streamer det konverterede svar til klienten

Transformeren (`transformer/responsesTransformer.ts`) leverer:

```ts
createResponsesApiTransformStream(): TransformStream
```

Dette håndterer:

- `response.output_item.added`-hændelser
- `response.output_text.delta`-hændelser
- `response.completed`-hændelsen
- Mapping af værktøjskald (`function_call` ↔ `tool_calls`)

## Ydeevnekrav

Routingmotoren har strenge ydeevnebudgetter:

| Handling                                      | Mål   | Måling                      |
| --------------------------------------------- | ----- | --------------------------- |
| Kombinationsberegning                         | <10ms | For 50 mål                  |
| Ratebegrænsningskontrol                       | <1ms  | Token bucket i hukommelsen  |
| Fallback for modelfamilie                     | <5ms  | Cachede familiedefinitioner |
| Routing af anmodning                          | <2ms  | Kritisk sti                 |
| **Ingen blokerende I/O i kritisk routingsti** | —     | Alt er asynkront            |

## Antimønstre

❌ **Synkrone databasekald i `combo.ts`** — forudberegn og cache
❌ **Logik for gentagne forsøg i handlers** — brug `retry()` fra robusthedstjenesten
❌ **Direkte adgang til providerkonfiguration** — brug getters fra `providerRegistry`
❌ **Hardcodede fallback-kæder** — definer dem i `modelFamilyFallback.ts`
❌ **Tilstandsændringer på tværs af samtidige anmodninger** — brug kun kontekst afgrænset til anmodningen

## Tilføjelse af en ny komponent

### Tilføjelse af en ny tjeneste

1. Opret `open-sse/services/[serviceName].ts` med et fokuseret ansvarsområde
2. Eksportér den primære handlerfunktion og eventuelle konstanter
3. Tilføj enhedstests i `tests/unit/services/[serviceName].test.mjs`
4. Integrér den i anmodningspipelinen i `handlers/chatCore.ts` (hvis den er routingrelateret)
5. Opdatér routinglogikken i `combo.ts`, hvis tjenesten påvirker valg af mål
6. Dokumentér den i denne fil

### Tilføjelse af en ny executor

1. Opret `open-sse/executors/[provider].ts`, der udvider `BaseExecutor`
2. Registrér den i `config/providerRegistry.ts`
3. Føj den til factory-funktionen i `executors/index.ts`
4. Tilføj enhedstests for executoren
5. Dokumentér den i `docs/architecture/ARCHITECTURE.md`

### Tilføjelse af et nyt MCP-værktøj

1. Opret eller opdatér `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definér et Zod-skema for input
3. Registrér værktøjet i `mcp-server/index.ts`
4. Føj det til rettighedsmatricen i `mcp-server/auth/`
5. Tilføj enhedstests
