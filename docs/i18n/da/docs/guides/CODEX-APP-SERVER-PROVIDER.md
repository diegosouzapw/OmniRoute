---

OmniRoute tilbyder **to** måder at bruge OpenAI Codex på:

| Udbyder                | Sådan kommunikerer den med OpenAI                                                                                                                                               | Forbehold ved brug                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **`codex`**            | Genbruger din ChatGPT/OpenAI OAuth-token direkte mod Responses API                                                                                                              | **Ja** — den officielle session er ikke godkendt til brug med proxy/router |
| **`codex-app-server`** | Styrer **Codex CLI's egen `codex app-server`** via JSON-RPC/WebSocket; CLI'en ejer og fornyer selv sin OAuth (`~/.codex/auth.json`) nøjagtigt som en interaktiv `codex`-session | **Nej** — OmniRoute genbruger aldrig en token mod API'et                   |

Da `codex-app-server` aldrig genbruger en token, er den ikke omfattet af
forbeholdet vedrørende genbrug af sessioner. Den kræver dog en **Codex CLI, der
kan nås på den konfigurerede app-server-URL**, og denne CLI skal være **logget
ind**.

---

## 1. Arkitektur

```
┌─ OmniRoute-app ─────────────────┐        ┌─ codex-app-server-sidecar ──────────┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                   │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456         │
│  (+ kapabilitetstoken)           │  JSON  │  --ws-auth capability-token         │
│                                  │  RPC   │  administrerer selv OpenAI OAuth    │
└──────────────────────────────────┘        │  (~/.codex/auth.json, autofornyelse)│
        │ deles (compose-diskenheder)        └─────────────────────────────────────┘
        ▼
  codex-appserver-token   → WS-kapabilitetstokenen (begge monterer den)
  codex-appserver-home    → ~/.codex (auth.json skrives af kontrolpanelet og
                             læses af sidecarens codex app-server)
```

- Sidecaren lytter **kun** på det interne compose-netværk
  (`ws://codex-app-server:1456`) bag en kapabilitetstoken. Den eksponeres
  **aldrig** på værten eller internettet.
- Codex CLI er indbygget i `omniroute:base`, så det er ikke nødvendigt at
  installere codex på værten eller brugerens maskine, når sidecaren køres.

## 2. Start den

```bash
# Start stakken MED sidecar-profilen til codex app-server:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

Sidecaren opretter sin WS-kapabilitetstoken ved første opstart (i den delte
`codex-appserver-token`-diskenhed), og appen læser den samme token via
`OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`. Ingen manuel tokenkonfiguration er
nødvendig.

## 3. Opret forbindelse + log ind

1. Tilføj en forbindelse til **OpenAI Codex (App-Server)** i kontrolpanelet.
   Der kræves ingen API-nøgle eller token (det er en udbyder uden godkendelse —
   sidecaren håndterer godkendelsen).
2. Hvis sidecarens Codex CLI **endnu ikke er logget ind**, rapporterer
   forbindelsens helbredskontrol _"kører, men er ikke logget ind"_ (ikke en rød
   godkendelsesfejl). Brug **Log ind med ChatGPT**: Dette kører Codex'
   standardenheds-OAuth i din browser og skriver derefter
   `~/.codex/auth.json` til den delte diskenhed via **Anvend godkendelse** (det
   samme login bruges af både `codex`- og `codex-app-server`-udbyderne).
3. Når du er logget ind, bliver helbredskontrollen grøn (den kontrollerer både
   `/readyz` **og** `account/read` — dvs. både at tjenesten kører _og_ er
   godkendt), hvorefter den fungerer.

Kontrolpanelet overskriver aldrig en eksisterende velfungerende
`~/.codex/auth.json` — det skriver kun, når filen mangler, eller dens token er
forældet (der oprettes altid en sikkerhedskopi).

## 4. Implementeringsscenarier

- **Operatør med en allerede godkendt Codex CLI** — montér værtens
  `~/.codex` i sidecaren (`codex-appserver-home`), og spring logintrinnet over.
- **Offentlig bruger uden codex installeret lokalt** — irrelevant: Sidecaren
  indeholder CLI'en. Brugeren godkender sig kun via kontrolpanelet.
- **OmniRoute på fysisk server (ingen sidecar, codex på værten)** — peg
  `OMNIROUTE_CODEX_APPSERVER_WS` mod din egen `codex app-server`, og sørg for,
  at codex på værten er logget ind; tippet "codex er ikke installeret" vises,
  hvis den binære fil mangler.

## 5. Privat / UDP-udgående trafik (ekstra for operatøren, medfølger ikke)

Den generiske sidecar ovenfor sender udgående trafik via containerens normale
netværk. En operatør, der har brug for, at Codex-trafik sendes via en
**privat internetforbindelse** (f.eks. en TUN-tailscale-sidecar, der håndterer
TCP + UDP/QUIC), kører dette som en separat compose-tilsidesættelse; det er med
vilje **ikke** en del af den medfølgende `codex-app-server`-profil. Se den interne
driftsvejledning for denne opsætning.
