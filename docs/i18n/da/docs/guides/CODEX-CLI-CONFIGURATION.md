> **TOML er det eneste effektive format.** Moderne Codex læser udelukkende
> `~/.codex/config.toml` (bekræftet med codex-cli 0.147.0: `codex --help`
> dokumenterer, at `-c/--config`-tilsidesættelser "indlæses fra
> `~/.codex/config.toml`"). Den gamle `~/.codex/config.yaml` tilhørte den
> forældede npm-CLI og ignoreres uden nogen meddelelse. Dashboardgeneratoren
> (`/api/cli-tools/apply`, værktøjet `codex`) skriver TOML med en konservativ
> fletning — eksisterende nøgler og andre providerblokke bevares, API-nøglen
> forbliver i `OMNIROUTE_API_KEY` (aldrig i filen), og en tilbageværende ældre
> `config.yaml` rapporteres som en migreringsbemærkning uden at blive ændret.

## config.toml klar til at indsætte

Erstat `<YOUR_HOST>` og `<YOUR_KEY>` med dine værdier:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # grænse for historiklagring pr. værktøjskald

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc eller ~/.zshrc — den faktiske nøgleværdi, aldrig i config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex inkluderet i ChatGPT-appen

Hvis du installerede Codex via ChatGPT-skrivebordsappen, findes den binære
`codex`-fil muligvis kun i app-pakken og endnu ikke i din shells `PATH`. Føj
ressourcemappen til din shells opstartsfil:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Åbn en ny shell, og kontrollér derefter:

```bash
command -v codex
codex --version
```

### Lokal OmniRoute uden godkendelse: En pladsholdernøgle er tilstrækkelig

Codex kontrollerer, at den miljøvariabel, som er angivet af `env_key`, findes,
**før** den første anmodning forlader CLI'en. Hvis din **lokale**
OmniRoute-instans ikke kræver godkendelse, fungerer enhver ikke-tom pladsholder:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Brug i stedet en rigtig nøgle, når din OmniRoute-server er beskyttet eller ekstern.

> **Almindelige værtsindstillinger**
>
> | Adgang         | URL                           |
> | -------------- | ----------------------------- |
> | Lokalt netværk | `http://192.168.0.1:20128/v1` |
> | Tailscale      | `http://100.x.x.x:20128/v1`   |
> | Loopback       | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — derfor fungerer det for alle modeller

Codex CLI udfasede `wire_api = "chat"` (Chat Completions) i februar 2026 og
**kræver** nu `wire_api = "responses"` (OpenAI Responses API). Indstilling af
`wire_api = "chat"` medfører et øjeblikkeligt nedbrud ved opstart siden v0.138.

Mange providers, herunder GLM og Kimi, tilbyder stadig kun et Chat
Completions-endpoint. DeepSeek V4 tilbyder nu både en integreret Responses API
og et Anthropic-kompatibelt endpoint; OmniRoute bruger Responses som standard
og lader hver DeepSeek-forbindelse vælge Anthropic-kompatibilitet.

**OmniRoute løser dette på en gennemsigtig måde:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute vælger providerens integrerede protokol og oversætter efter behov
    → POST /responses (DeepSeek V4) eller /chat/completions (Mistral / GLM / Kimi / andre)
```

Du behøver aldrig en separat oversættelsesproxy, når du bruger OmniRoute.
**Alle modeller bruger `wire_api = "responses"`** — OmniRoute håndterer resten.

> **`wire_api` er standardindstillingen** — feltets standardværdi er
> `"responses"`, og det kan udelades helt fra `config.toml`. Angiv det kun
> eksplicit, hvis du dokumenterer hensigten.

## Kontekstvindue og komprimering

### Felter til tokenkonfiguration

| Felt                             | Beskrivelse                                                                                                                                                                                                                              |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Samlet tokenbudget for den aktive model. Indstil til modellens angivne grænse.                                                                                                                                                           |
| `model_auto_compact_token_limit` | Tærskel, der udløser automatisk komprimering af historikken. **Maksimum: 90 % af `model_context_window`** — værdier over 90 % ignoreres uden varsel.                                                                                     |
| `tool_output_token_limit`        | Grænse for antallet af tokens, der gemmes i historikken pr. output fra et værktøjskald. Forhindrer, at et enkelt stort værktøjssvar fylder vinduet. **Dette er ikke det maksimale output** — det er en grænse for lagring i historikken. |
| `compact_prompt`                 | Integreret tilsidesættelse af den systemprompt, der bruges under komprimering (v0.138+).                                                                                                                                                 |

> **Bemærkning om `model_max_output_tokens`**: Dette felt er **ikke en del af Codex CLI-konfigurationsskemaet** (det findes ikke i Codex-kodebasen i Rust). Det ignoreres uden varsel, hvis det angives. Stol ikke på det — brug `tool_output_token_limit` til at styre, hvor meget værktøjsoutput der gemmes i historikken.

## Ræsonneringsindsats

Styrer, hvor meget modellen "tænker", før den svarer.

| Værdi    | Bruges til                                           |
| -------- | ---------------------------------------------------- |
| `none`   | Ingen ræsonnering — direkte svar                     |
| `low`    | Trivielle opgaver (omdøbning, formatering)           |
| `medium` | **Serverstandard**, når det ikke er angivet          |
| `high`   | Opgaver på mellemniveau (refaktorering, fejlfinding) |
| `xhigh`  | Arkitektur, dybdegående analyse, komplekse problemer |

```bash
# Tilsidesættelse pr. kørsel
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

Angiv også et **resumé** af ræsonneringen, så Desktop kan gengive tanketekst (ikke kun krypterede datablokke):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # eller ultra, når det understøttes
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute-tænkebudget (serverindstilling)

På OmniRoute-værten skal **Settings → AI → Thinking Budget** være indstillet til **`passthrough`**, for at Codex-indsats/resumé kan nå den overordnede tjeneste. Tilstanden **`auto` fjerner** alle klientfelter af typen `reasoning` / `reasoning_effort` og vil tømme tænkningspanelerne, selv når Codex er konfigureret korrekt.

Komplet vejledning: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Komprimering og promptcache er uafhængige og fortsætter med at fungere under `passthrough`.

## Profiler — navngivne konfigurationer pr. model/arbejdsgang

Profiler gør det muligt at skifte model + kontekstvindue med et enkelt flag. Hver profil er en flad
`~/.codex/<name>.config.toml`, der lægges oven på den grundlæggende `config.toml`.

> **Navngivningsregel (Codex CLI v0.137+):** filen skal hedde `~/.codex/<name>.config.toml` — **uden præfikset `profile-`**.
> CLI'en fortolker `-p kimi-k27` som `~/.codex/kimi-k27.config.toml`. Hvis filen ikke findes, anvendes standardindstillingen uden varsel.

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # hurtig, billig
```

### Indsatsprofiler (samme model, forskellig indsats)

```bash
codex -p low      # cx/gpt-5.5, indsats=low
codex -p medium   # cx/gpt-5.5, indsats=medium
codex -p high     # cx/gpt-5.5, indsats=high
codex -p xhigh    # cx/gpt-5.5, indsats=xhigh (standard)
codex -p chat     # cx/gpt-5.5, ingen indsats angivet (serverstandard)
```

## Generering af profiler automatisk med `omniroute setup-codex`

Hvis du kører OmniRoute på en VPS, kan du automatisk generere profilfiler fra det aktive modelkatalog:

```bash
# Fra en VPS (bruger lokal OmniRoute på port 20128)
omniroute setup-codex

# Fra enhver maskine — peg på din VPS
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Forhåndsvis uden at skrive filer
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Generér kun GLM- og Kimi-profiler
omniroute setup-codex --only glm,kimi

# Skriv til en brugerdefineret mappe
omniroute setup-codex --codex-home /path/to/.codex
```

Kommandoen henter `/v1/models`, bruger finjusterede profiler til kendte modeller, falder tilbage til katalogmetadata for andre kompatible tekstmodeller og skriver `~/.codex/<name>.config.toml` for hver af dem. Idempotent — kan trygt køres igen.

OmniRoute kan også **automatisk synkronisere** de samme profilfiler, efter at en vellykket registrering/import af udbydermodeller ændrer det aktive katalog. Dette er **fravalgt og deaktiveret som standard**: Aktivér det fra **CLI Code-kontrolpanelet** ("Automatisk synkronisering af CLI-profiler" → Codex), eller angiv `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (det respekterer også `CLI_ALLOW_CONFIG_WRITES`, som er aktiveret som standard). Når funktionen er aktiveret, skriver den kun separate `~/.codex/*.config.toml`-profilfiler; den ændrer aldrig den aktive/standardmæssige `~/.codex/config.toml`, Codex-lb-indstillinger, godkendelse eller valg af udbyder.

## Start af Codex med `omniroute launch-codex`

Kontrollerer tilstanden for din OmniRoute-instans, før Codex startes:

```bash
# Start med lokal OmniRoute (standardport 20128)
omniroute launch-codex

# Start med en bestemt profil
omniroute launch-codex --profile kimi-k27

# Start med en ekstern VPS

# Send ekstra argumenter til codex
```

## Langvarige opgaver

To standardindstillinger i OmniRoute kan i det skjulte sabotere flere timer lange Codex CLI-sessioner. Ingen af dem er en Codex CLI-indstilling — begge findes på OmniRoute-siden. Brugere, der migrerer en konfiguration fra upstream-proxyer, som fastholder konti og deaktiverer timeout ved inaktivitet, rammer ofte begge problemer og konkluderer, at OmniRoute »ikke kan opretholde en lang session«.

| Symptom                                                                                        | Sandsynlig årsag                                                                      | Indstilling              |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------ |
| Sessionen bliver ved med at skifte konto / kontinuiteten i promptcachen går tabt mellem turene | TTL for sessionstilknytning er `0` (deaktiveret)                                      | `sessionAffinityTtlMs`   |
| Forbindelsen afbrydes midt i ræsonneringen uden en prompt, der er synlig for klienten          | Vagthunden for inaktiv stream blev udløst efter 10 minutter uden en upstream-datablok | `STREAM_IDLE_TIMEOUT_MS` |

Relaterede diskussioner: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (afbrydelser af lange opgaver), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (hvorfor tilknytning som standard er slået fra). Sporing: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Sessionstilknytning — fasthold én samtale til én konto

**Standard:** `sessionAffinityTtlMs = 0` (deaktiveret).

**Hvor den indstilles**

- Dashboard → **Indstillinger → Routing** → **Sessionstilknytning** → **Tilknytningens TTL (sekunder)** (`ComboDefaultsTab`)
- Eller brug PATCH på indstillingerne med `sessionAffinityTtlMs` i **millisekunder** (Zod-interval `0`–`86_400_000`, dvs. op til 24 timer)

> Omdøbt i #7274 fra den Codex-specifikke `codexSessionAffinityTtlMs`. Den ældre nøgle accepteres stadig som et skrivebeskyttet alias; nye konfigurationer bør bruge `sessionAffinityTtlMs`. Tilknytning gælder nu for **enhver** udbyder, når TTL er over `0`, ikke kun Codex — se [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Sessionstilknytning.

**Hvad der går i stykker, når den forbliver på 0**

Hver tur i en Codex-samtale med flere ture routes uafhængigt af den aktive kombinationsstrategi og kan ende på en **anden konto for hver tur**. Det bryder kontinuiteten for upstream-sessionen/-promptcachen. OmniRoute tager kun Codex-sessionsheadere (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) og body-felter såsom `prompt_cache_key` / `session_id` i betragtning, når TTL er større end `0` (`extractSessionAffinityKey` i `src/sse/services/auth.ts`).

**Anbefalet til en enkelt opgave, der varer flere timer**

Indstil TTL **højere end opgavens forventede faktiske varighed** (maksimum i brugergrænsefladen er **86400 sekunder** = 24 timer):

| Forventet opgavelængde | Tilknytningens TTL (brugergrænseflade, sekunder) | `sessionAffinityTtlMs` |
| ---------------------- | ------------------------------------------------ | ---------------------- |
| Nogle få timer         | `14400` (4 t.)                                   | `14400000`             |
| Natten over / ~12 t.   | `43200` (12 t.)                                  | `43200000`             |
| Et helt døgn           | `86400` (24 t., maksimum)                        | `86400000`             |

Aktivering er bevidst valgfri: Deaktivering af tilknytning prioriterer belastningsfordeling på tværs af konti; aktivering prioriterer kontinuitet for én lang agentsession. Denne vejledning ændrer **ikke** standardindstillingen — operatører, der kører lange Codex-opgaver, skal selv aktivere den.

### 2. Timeout for inaktiv stream — afbryd ikke stille ræsonneringsture

**Standard:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 minutter). Den nedarver fra `REQUEST_TIMEOUT_MS`, når den ikke er angivet; det fælles udgangspunkt er også 600000. Se [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Timeouts.

**Hvad der går i stykker med standardindstillingen**

En Codex-reasonnerings-/værktøjssekvens, der forbliver tavs i mere end 10 minutter uden **nogen reel upstream-chunk**, tvangslukkes af SSE-inaktivitetsvagthunden (`open-sse/utils/stream.ts`). Klienten oplever ofte blot, at forbindelsen afbrydes — hvilket stemmer overens med “stoppede automatisk uden nogen meddelelse.”

Kritisk detalje: OmniRoutes syntetiske SSE-**heartbeat nulstiller ikke** inaktivitetsuret. Kun en reel upstream-body-chunk opdaterer `lastChunkTime`. En stille model, der stadig “tænker”, ser fra vagthundens synspunkt identisk ud med en upstream-forbindelse, der er gået i stå.

Relateret Undici-body-inaktivitet: `FETCH_BODY_TIMEOUT_MS` (har også som standard den samme grundværdi på 10 minutter; `0` deaktiverer den). Ved streaming dækker `FETCH_TIMEOUT_MS` kun opsætning af forbindelsen/de første headers — når streamen er aktiv, styres afbrydelser ved stilstand af `STREAM_IDLE_TIMEOUT_MS` og `FETCH_BODY_TIMEOUT_MS`.

**Anbefalet til en enkelt opgave, der varer flere timer**

I OmniRoute-processens miljø (`.env` / compose / systemd):

```bash
# Deaktivér grænserne for stream-inaktivitet og body-inaktivitet ved lange ræsonneringssekvenser
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Eller hæv dem til mere end den længste stille periode, du forventer (værdierne er i millisekunder):

```bash
# Eksempel: Tillad op til 2 timers stilhed mellem upstream-chunks
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Genstart OmniRoute efter ændring af disse miljøvariabler.

### Konkret fremgangsmåde — Codex-opgave på flere timer

1. **Fastlås kontoen:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12 t.) eller `86400` (maks. 24 t.).
2. **Hæv/deaktivér inaktivitetsgrænserne** i OmniRoutes miljø:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Behold den sædvanlige Codex-`config.toml` (`wire_api = "responses"`, korrekt `base_url`, `OMNIROUTE_API_KEY`) — der findes ingen Codex-specifikke indstillinger for affinitet/inaktivitet for disse to funktioner.
4. Genstart OmniRoute, og start derefter den langvarige Codex-opgave.

### Beslutning om standardværdier (#7287)

| Indstilling              | Leveret standardværdi | Ændring i denne vejledning?                                                                                         |
| ------------------------ | --------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (fra)             | **Nej** — forbliver tilvalg (belastningsfordeling kontra kontinuitet; se Discussion #5718)                          |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 min.)    | **Nej** — forbliver 10 minutter for generel trafik; operatører med langvarig Codex-brug hæver eller deaktiverer den |

Hvis en af standardværdierne ændres globalt, ændres adfærden for alle klienter på en instans, ikke kun Codex. Dokumentér indstillingerne; lad standardværdierne være uændrede, indtil en udtrykkelig operatørbeslutning siger andet.

### Diagnosticering af inaktivitetsafbrydelser

Når inaktivitetsvagthunden udløses, logger OmniRoute en linje med denne form:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Søg med grep efter `Idle timeout: no data from` (eller koden `stream_idle_timeout` / fejlnavnet `StreamIdleTimeoutError`). Provider-segmentet er det, OmniRoute brugte til den pågældende anmodning (`codex`, et andet provider-id eller `provider`, hvis det er ukendt) — det er ikke altid den bogstavelige streng `codex`.

## Fejlfinding

**`Error: wire_api = "chat" understøttes ikke længere`**
Fjern `wire_api = "chat"` fra din konfiguration. Indstil `wire_api = "responses"`, eller udelad feltet (standardværdien har været `"responses"` siden v0.138).

**`Error: model not found`**
Kontrollér, at modellen findes i OmniRoute med det korrekte præfiks. Brug `omniroute models list`, eller åbn `/dashboard/providers/<provider>`.

**`Authentication error`**
Bekræft, at `OMNIROUTE_API_KEY` er eksporteret: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex kontrollerer, at miljøvariablen findes, før den første anmodning foretages. Eksportér
en rigtig nøgle til beskyttede servere eller en ikke-tom pladsholder såsom
`OMNIROUTE_API_KEY=local`, når din **lokale** OmniRoute-instans ikke
kræver godkendelse. Genstart shellen, hvis du har føjet den til `~/.bashrc` eller `~/.zshrc`.

**`Connection refused`**
Kontrollér, at OmniRoute kører, og at `base_url`-værten og -porten er korrekte for dit netværk (lokalt kontra Tailscale kontra VPS).

**Sessionen går ned tæt på kontekstgrænsen**
Indstil `model_context_window` og `model_auto_compact_token_limit` eksplicit. Se tabellen over kontekstvinduer ovenfor.

**Komprimering udløses for sent**
Sænk `model_auto_compact_token_limit` til 80–85 % af vinduet. Indstil den aldrig til over 90 %.

**Profilen indlæses ikke (`-p <name>` ignoreres uden fejlmeddelelse)**
Kontrollér, at filen findes på `~/.codex/<name>.config.toml` (intet `profile-`-præfiks). Kør `ls ~/.codex/*.config.toml`.

**Langvarig Codex-opgave afbrydes under kørslen/skifter konto mellem interaktioner**
Se [Langvarige opgaver](#long-running-tasks). Aktivér sessionstilknytning (TTL længere end opgavens varighed), og forhøj eller deaktiver `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`. Søg i OmniRoute-logfilerne med grep efter `Idle timeout: no data from`.
