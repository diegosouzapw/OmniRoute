Brug denne vejledning til at vælge den mindst omfattende, pålidelige udviklingscyklus til en pull request. Den erstatter ikke de områdespecifikke arkitektur- og sikkerhedsdokumenter, der er linket til nedenfor; den forbinder hver almindelig ændringstype med dens kontrakter, fokuserede kontroller og CI-dækning.

## Det forløb, som alle ændringer følger

1. **Vælg basisgrenen, før du redigerer.** Find den højeste aktive `release/v*`-gren, og opret din gren fra dens seneste commit. Brug denne gren som mål, ikke `main`. Hvis der er et aktivt release-freeze, må du ikke bruge den frosne gren som mål; brug den næste aktive cyklus, der er beskrevet i
   [Forgrenings- og releasemodel](BRANCHING_MODEL.md).
2. **Angiv kontrakterne.** Identificer alle kataloger, skemaer, genererede artefakter, offentlige API'er eller brugergrænseflader, som ændringen påvirker. Tabellen nedenfor angiver det minimale udgangspunkt.
3. **Skriv eller opdater fokuserede tests.** Produktionsændringer i `src/`, `open-sse/`, `electron/` eller
   `bin/` kræver en automatiseret test i samme PR. Kør de mindst omfattende testfiler, der dokumenterer adfærden, og derefter de angivne fokuserede kontroller.
4. **Lad CI køre den brede matrix.** De komplette enhedstest-shards, Vitest, dækningsratchet og
   produktionsbuild køres på PR'en. Kør kun en bred testsuite lokalt, når en fokuseret fejl peger på en bredere påvirkning, eller når ændringen berører flere undersystemer.
5. **Afstem før gennemgang.** Hent den aktive basisgren, gennemgå dens nye commits og din diff i forhold til den, og udfør derefter rebase eller merge af basisgrenen i overensstemmelse med bidragydernes arbejdsgang. Løs konflikter i genererede filer og kataloger ud fra deres kilde, generér dem igen, kør den fokuserede cyklus igen, og bekræft, at PR'en stadig er målrettet den aktive release-gren.
6. **Registrer dokumentation.** Angiv i PR-skabelonen de kørte kommandoer, alle tilføjede eller ændrede testfiler, migreringer eller feature flags samt eventuel validering, der kun udføres i CI og stadig afventer.

## Anbefalede forløb efter ændringstype

Kommandoerne nedenfor er de minimale fokuserede kontroller og giver ikke tilladelse til at springe en test over, som direkte dækker den adfærd, du har ændret.

### Udbyder

**Kontrakter**

- Udbyderdefinitionen i `src/shared/constants/providers/` og dens sammensætning i
  `src/shared/constants/providers.ts`.
- Modeller og egenskaber i `open-sse/config/providerRegistry.ts` eller de udskilte registerfiler.
- Valg af executor/translator, konfiguration af OAuth eller API-nøgle, dashboard-aktiver og den genererede udbyderreference, når det er relevant.
- Offentlige legitimationsoplysninger skal bruge `resolvePublicCred()`; fejlsvar skal bruge de delte hjælpefunktioner til rensning af fejl. Se `docs/security/PUBLIC_CREDS.md` (git; kompileres ikke ind i `/docs`) og
  [Rensning af fejl](../security/ERROR_SANITIZATION.md).

**Fokuseret cyklus**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # når kataloget ændres; commit den genererede diff
npm run lint
```

Test også alle berørte request-familier: chat, Responses, billeder, embeddings, lyd eller video.
Gennemgå genererede katalog- og golden-diffs som kontraktændringer; acceptér dem ikke ukritisk.

### Routing

**Kontrakter**

- Offentlige strategiværdier og UI-metadata i `src/shared/constants/routingStrategies.ts`.
- Dispatch og rækkefølge under `open-sse/services/combo.ts` og `open-sse/services/combo/`.
- Combo-skemaer, persistens, resiliensstatus, modelegenskaber og API-/UI-kontrolelementer.
- [Auto-Combo-motor](../routing/AUTO-COMBO.md) og dokumentation om resiliens, når adfærden ændres.

**Fokuseret cyklus**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ændringer af strategi eller dispatch
npm run check:known-symbols      # ændringer af strategiregistrering
npm run lint
```

Brug deterministiske tests med mockede upstreams lokalt. Live combo-smoketests kræver legitimationsoplysninger og er manuelle; de erstatter ikke CI.

### UI / UX

**Kontrakter**

- Next.js-rute/-side og grænser for delte komponenter under `src/app/` og
  `src/shared/components/`.
- API-svarstrukturer, indlæsnings-/tom-/fejltilstande, tastatur- og skærmlæseradfærd,
  responsivt layout, temaer og locale-udvidelse.
- Engelske UI-kildestrenge i `src/i18n/messages/en.json`; hardcod ikke ny brugervendt tekst.

**Fokuseret cyklus**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Kør appen ved interaktionsmæssige eller visuelle ændringer, og kontrollér både smalle og brede visningsområder. CI kører produktionsbuildet og bredere testsuiter; visuel adfærd kræver stadig en fokuseret komponenttest, Playwright-test eller dokumenteret manuel kontrol, der passer til ændringen.

### i18n

**Kontrakter**

- `src/i18n/messages/en.json` er UI-kilden; `config/i18n.json` er locale-kilden.
- CLI-kataloger findes separat under `bin/cli/locales/`.
- Bevar ICU-pladsholdere og tags nøjagtigt. Oversæt ikke produkt-/udbyder-/modelnavne,
  protokol- og headernavne, kommandoer, kode-/JSON-identifikatorer, URL'er, miljøvariabler eller
  beskyttede termer såsom `OmniRoute`, `OAuth`, `MCP` og `A2A`. Den aktuelle kildeliste er
  `scripts/i18n/glossary/protected-terms.json`.

**Fokuseret cyklus**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # når CLI-strenge/-kataloger ændres
npm run lint
```

Dette er vejledning til det eksisterende system, ikke en invitation til at udvide dets værktøjer eller nøglemodel.
Hold i18n-patches målrettede, mens erstatningssystemet designes. Kør ikke oversættelseskommandoer, der kalder eksterne tjenester, medmindre opgaven udtrykkeligt kræver genererede oversættelser, og du har gennemgået den resulterende diff.

### CLI

**Kontrakter**

- Offentlige kommandoer og flag i `bin/cli/`, genererede API-kommandoer, afslutningskoder, stdout/stderr og
  JSON-outputstrukturer, konfigurations-/miljøadfærd og pakkede filer.
- Brugerrettede CLI-strenge skal bruge CLI'ens i18n-lag og holde `en`/`pt-BR`-katalogerne synkroniserede.
- Bevar Node som den understøttede runtime og kontrakten for den udgivne binære fil.

**Fokuseret arbejdsgang**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # genererede/bundlede CLI-ændringer
npm run check:pack-policy     # ændringer af pakkens offentlige grænseflade
npm run lint
```

Brug den nøjagtige kommando i en midlertidig datamappe, når adfærden afhænger af parsing, filer eller
afslutningsstatus. CI udfører de bredere kontroller af pakkeartefakter og økosystemet.

### Database

**Kontrakter**

- Domænemoduler under `src/lib/db/`; importér specifikke moduler direkte (det gamle reeksportlag `localDb.ts` blev fjernet).
- Nummererede, idempotente SQL-migreringer under `src/lib/db/migrations/`, transaktionssikkerhed, opgraderingsadfærd,
  indekser og alle kaldere, der påvirkes af skemaet.
- Ruter og handlere udfører aldrig rå SQL direkte.

**Fokuseret arbejdsgang**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Test både en ny database og opgradering fra det foregående skema, når du tilføjer en migrering. Databasetest
skal lukke handles og kalde `resetDbInstance()` under oprydning. Kør kun `npm run test:bun:db`, når
adapterstien for Bun efter bedste evne ændres; Node er fortsat autoritativ.

### Build / udrulning

**Kontrakter**

- Rod- og workspace-manifester/låsefil, `scripts/build/`, selvstændig Next.js-samling, `dist/`-
  pakkeindhold, Electron-platformsmetadata, CI-workflows og udrulningsindikatorer.
- Understøttede Node-intervaller og den tilladelseslistede brug af Bun i `CLAUDE.md` skal forblive intakte.
- Build-artefakter forbliver usporede; politikker for afhængigheder, licenser, workflows og pakker er gældende.

**Fokuseret arbejdsgang**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # ændringer af afhængigheder eller låsefil
npm run check:pack-policy      # ændringer af den udgivne pakkes offentlige grænseflade
npm run lint
```

Brug kun `npm run build` lokalt, når ændringen påvirker kompilering, selvstændig samling, assets
eller runtime-bundling. Brug kun `npm run build:release` til validering af udgivelse/udrulning. CI's build er
det endelige signal på tværs af platforme; platformspecifikke Electron-ændringer kræver den tilsvarende fokuserede build
eller dokumentation fra en smoke-test.

## Lokal løkke kontra CI

| Kør lokalt for hver ændring                                                        | CI leverer det brede signal                                                           |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Direkte adfærdstests og kategorikontroller ovenfor                                 | Opdelt komplet enhedstestsuite og serielle tests                                      |
| `npm run lint`                                                                     | Vitest-suiter og skralder for dækning/kvalitet                                        |
| Typekontrol eller build kun, når den berørte kontrakt kræver det                   | Produktionsbuild, sikkerheds-, dokumentations-, afhængigheds- og PR-politikkontroller |
| Manuel interaktion/livekontroller kun, når automatisering ikke kan bevise adfærden | Integration på tværs af jobs og platformskontroller konfigureret af workflowet        |

En grøn fokuseret løkke er dokumentation for den ændrede kontrakt, ikke et bevis på, at ikke-relaterede CI-kontroller
vil lykkes. Omvendt bør hver lokal ændring ikke skulle vente på repositoryets fulde matrix.

## Tjekliste for afstemning

Før du anmoder om gennemgang:

- Bekræft, at PR'ens base stadig er den højest rangerende aktive `release/v*`-branch.
- Hent denne base, og gennemgå commits, der er landet, siden du oprettede din branch.
- Gennemgå `git diff <active-base>...HEAD` for utilsigtede eller genererede ændringer.
- Løs konflikter i kataloger og genererede dokumenter ved at opdatere kilden og regenerere outputtet.
- Kør alle fokuserede tests/kontroller, der er angivet i PR-beskrivelsen, igen efter afstemningen.
- Svæk aldrig assertions, og fjern ikke påkrævede tests blot for at matche en flyttet base.

Se
[Branching- og release-model](BRANCHING_MODEL.md) for regler om release-frysning og ændring af mål-branch. Se
[Reference til kvalitetskontroller](../architecture/QUALITY_GATES.md) for den komplette CI-oversigt.
