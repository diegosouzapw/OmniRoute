> **Omfattningsnotering:** `socket.yml` konfigurerar Socket.devs registerbaserade skanning efter publicering av npm-artefakten (sökvägar som ska ignoreras för innehåll som inte distribueras, exempelvis `tests/`, `docs/` och bygg­rapporter). Den kopplar inte in någon sammanslagningsspärr för CI/PR — inget arbetsflöde i `.github/workflows`, inget skript i `package.json` och inget mål i `Makefile` anropar Socket.dev.

Detta dokument är underhållarens intyg för de sex fynden
`AI-detected potential malware` som rapporterades för `omniroute@3.8.5` och
de riskreducerande åtgärder som tillämpades i `omniroute@3.8.6`. Det finns för att:

1. Operatörer av säkerhetspipelines ska ha en enda referens att hänvisa till när de behöver
   utvärdera fynden mot den faktiska källkoden.
2. Framtida AI-skannrar ska kunna uppfatta det underhållarsignerade påståendet att varje
   flaggad sökväg är avsiktlig, valfri och dokumenterad.
3. Vi ska ha en skriftlig redogörelse för _varför_ varje anropsställe är utformat som det är —
   så att en framtida omstrukturering inte av misstag återinför ett fingeravtryck som
   avsiktligt har tagits bort.

Om du använder en skanner som åter flaggar något av anropsställena nedan efter att
riskreduceringarna i v3.8.6 har publicerats, öppna ett ärende med skanningsspårningen så
utökar vi intyget här.

## §1 — Installation av MITM-rot-CA (`77484.js`)

**Källfiler**:

- `src/mitm/cert/install.ts` — publika `installCert()` / `uninstallCert()`,
  plattformsspecifika `installCertWindows/Mac/Linux`.
- `src/mitm/systemCommands.ts` — delade hjälpfunktioner för `execFile` / `spawn` / PowerShell
  som används av installationsvägarna.

**Utlösare**: användaren klickar på ”Aktivera MITM-proxy” i den lokala kontrollpanelen på
`/dashboard/cli-tools/mitm`. Rutten är endast tillgänglig via loopback — se strikt regel nr 17 i
`CLAUDE.md` och `src/server/authz/routeGuard.ts::isLocalOnlyPath()`. En läckt
JWT som exponeras via en tunnel **kan inte** utlösa denna kodväg.

**Privilegierade åtgärder som utförs (per plattform)**:

| OS                     | Kommando(n)                                                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | `certutil -addstore Root <cert>` via UAC                                                                          |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | uppdatering av NSS-databasen per profil via `certutil -d sql:<profile>`                                           |

Detta är samma kommandon som används av `mitmproxy`, Charles Proxy, Fiddler och
Caddy. Att de finns i OmniRoute är dokumenterat i
`docs/security/STEALTH_GUIDE.md`.

**Åtgärd i v3.8.6**:

- `runElevatedPowerShell()` använder inte längre `-EncodedCommand <base64utf16le>`.
  Den förhöjda nyttolasten skrivs till en temporär `.ps1`-fil per anrop (läge 0o600,
  i en privat `mkdtempSync`-katalog) och refereras via `-File`. Filen
  tas bort i `finally`. Detta avlägsnar det typiska fingeravtrycket för
  base64-baserad privilegiehöjning via PowerShell som flaggades av Socket.devs AI-
  klassificerare.
- `installCertWindows` innehåller ett infogat `SECURITY-AUDITOR-NOTE:`-block
  som hänvisar hit.

**Varför vi behåller det**: MITM-proxyn är en dokumenterad funktion som används av
`docs/security/STEALTH_GUIDE.md` och `docs/frameworks/MITM-PROXY.md`. Att ta bort
den skulle slå sönder funktionaliteten för agentbryggan.

## §2 — Import av Zed-autentiseringsuppgifter (`app/api/providers/zed/import/route.js`)

**Källfiler**:

- `src/app/api/providers/zed/discover/route.ts` _(ny i v3.8.6)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(ny i v3.8.6)_

**Utlösare**: användaren klickar på "Importera från Zed" på Providers-sidan i
den lokala instrumentpanelen. Ändpunkten skyddas av `requireManagementAuth`.
Zed-redigeraren skriver själv sina API-nycklar för leverantörer till
operativsystemets nyckelring under dokumenterade tjänstenamn — se
https://zed.dev/docs/ai/llm-providers.

**Beteende i v3.8.5 (det som Socket.dev flaggade)**:

`POST /import` hittade autentiseringsuppgifterna och sparade dem automatiskt i
det lokala SQLite-lagret under en enda rundresa. Ingen bekräftelse per konto,
inget fingeravtryck, bara "N token hittades, alla importerades."

**Åtgärd i v3.8.6 — bekräftelse i två steg**:

1. **`POST /api/providers/zed/discover`** returnerar
   `{ candidates: [{ provider, service, account, fingerprint }] }`. Råtoken
   överförs **aldrig**. Fingeravtrycket är
   `sha256(service|account|token).slice(0,16)`.
2. Instrumentpanelen visar kandidatlistan, operatören väljer vilka som ska
   importeras och skickar `{ confirmedAccounts: [{ service, account, fingerprint }] }`
   till **`POST /api/providers/zed/import`**.
3. Importändpunkten **läser nyckelringen på nytt på servern** och filtrerar
   efter `(service, account, fingerprint)`. Ett manipulerat eller återuppspelat
   identifieringssvar kan inte lura importändpunkten att spara en orelaterad
   token — om den aktuella token har ändrats sedan identifieringen matchar
   fingeravtrycket inte längre och autentiseringsuppgiften hoppas över.

Miljöflaggan `OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` bevarar beteendet från
v3.8.5 för operatörer som ännu inte har uppdaterat sin automatisering. Den
kommer att tas bort i v3.9.

**Varför vi behåller det**: Zed-import är den enklaste introduktionsvägen för
användare som redan använder Zed och vill spegla sina leverantörsnycklar till
OmniRoute utan att klistra in dem igen.

## §3 — `execFile` / `spawn` / PowerShell med förhöjda behörigheter (`21843.js`)

**Källfiler**: `src/mitm/systemCommands.ts`.

**Varför det flaggades**: kodsegmentet återexporterar `execFileWithPassword`,
`runElevatedPowerShell` och den delade hjälpfunktionen `quotePowerShell`.
Socket.devs AI-klassificerare tolkar dem som en allmän verktygslåda för
"körning på värdsystemet + behörighetshöjning". Inom OmniRoute används de
endast av installationsflödet för MITM-certifikat (§1) och av
`execFileWithPassword` för körning av `sudo`-kommandon.

**Åtgärd i v3.8.6**:

- Omstrukturering av `runElevatedPowerShell` (se §1).
- Ett infogat `SECURITY-AUDITOR-NOTE:`-block vid både
  `runElevatedPowerShell` och `execFileWithPassword` dokumenterar de
  tillåtna anroparna och den fasta listan över körbara filer.
- `spawn()`-anropet i `execFileWithPassword` har en `nosemgrep`-markör med
  listan över körbara filer som hjälpfunktionen får ta emot — det finns
  **ingen väg från användarindata till `finalCommand`/`finalArgs`**.

## §4 / §6 — 9router-tjänstövervakare (`api/services/9router/{start,restart}/route.js`)

**Källfiler**:

- `src/app/api/services/9router/_lib.ts` — fabrik för tjänstövervakaren.
- `src/app/api/services/9router/{start,stop,restart,status,install,update,auto-start}/route.ts`.
- `src/lib/services/ServiceSupervisor.ts` — allmän start av processer / hälsokontroll / loggbuffert.

**Utlösare**: användaren klickar på "Installera" / "Starta" på sidan för
inbäddade tjänster i den lokala instrumentpanelen.

**Redan implementerade skyddsåtgärder**:

- Alla `/api/services/*`-rutter är LOCAL_ONLY enligt
  `src/server/authz/routeGuard.ts` (fast regel nr 17). Begränsningen till
  loopback tillämpas före alla autentiseringskontroller — en läckt JWT kan
  inte nå dem.
- Databasraden för 9router skapas med
  `status='not_installed', auto_start=0` (se
  `src/lib/db/migrations/071_services.sql:19`). Tjänsten startar **inte** vid
  den första körningen.
- `spawn()` anropas med sökvägen till den binärfil som returneras av
  `resolveSpawnArgs(apiKey, PORT)` i `src/lib/services/installers/ninerouter.ts`,
  vilket är en fast lista över binärfiler som stöds.
- Stdout/stderr buffras i minnet (gräns på 5 MB, se `_lib.ts`) — ingen
  skrivning till disk sker om inte användaren aktiverar loggning från
  instrumentpanelen.

**Åtgärd i v3.8.6**: ingen funktionell ändring. Den minimala byggprofilen
(`OMNIROUTE_BUILD_PROFILE=minimal`) ersätter
`src/lib/services/installers/ninerouter.ts` med en stubbe för användare som
vill att kodvägarna med förhöjda behörigheter ska tas bort fysiskt från
paketet.

**Varför vi behåller det**: 9router är en valfri lokalt installerbar
kompanjontjänst (jämför med ett WordPress-tillägg) — strikt anmälan krävs.

## §5 — Återskrivning av autentiseringsuppgifter för OmniRoute Cloud Sync (`api/keys/[id]/route.js`)

**Källfiler**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`.
- `src/app/api/keys/[id]/route.ts` — anropar `syncKeysToCloudIfEnabled()`.

**Utlösare**: `isCloudEnabled()` returnerar `true` (anges från instrumentpanelen) **och**
`CLOUD_URL` är konfigurerad. När båda är avstängda görs inget utgående nätverksanrop till
Cloud-slutpunkten.

**Beteende i v3.8.5 (felet som Socket.dev upptäckte på rätt sätt)**:

`updateLocalTokens()` skrev över `accessToken`, `refreshToken` och
`providerSpecificData` från Cloud-svaret när
`cloudUpdatedAt > localUpdatedAt`. Ingen HMAC, ingen signatur, ingen kontrollsumma. En
felkonfigurerad eller fientlig `CLOUD_URL` (eller en MITM i kanalen) kunde obemärkt byta ut
leverantörens OAuth-token.

**Riskreducering i v3.8.6**:

1. **HMAC-verifiering**: `verifyCloudSignature(rawBody, sigHeader)` kontrollerar
   headern `X-Cloud-Sig` (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`) innan JSON-innehållet tolkas. Om hemligheten är angiven krävs
   signaturen. Om den inte är angiven (äldre kompatibilitetsläge) loggas en varning och svaret
   accepteras — hemligheten kommer att krävas i v3.9.
2. **Aktivt val för hemliga fält**: `accessToken` / `refreshToken` /
   `providerSpecificData` skrivs **endast** över när
   `OMNIROUTE_CLOUD_SYNC_SECRETS=true`. Standardläget synkroniserar endast
   metadata som inte är autentiseringsuppgifter (`expiresAt`, `status`, `lastError*`,
   `rateLimitedUntil`, `updatedAt`). Detta är en **bakåtinkompatibel ändring** för användare
   som förlitade sig på fjärrsynkronisering av token — de måste uttryckligen välja att aktivera den.

**Varför vi behåller det**: Cloud Sync är det enda sättet för en OmniRoute Cloud-klientorganisation
att centralisera teamets autentiseringsuppgifter. Korrigeringen gör hotmodellen tydlig:
"servern signerar, klienten verifierar, operatören väljer att aktivera funktionen."

## Byggprofil: `minimal`

För användare som behöver en Socket-kompatibel artefakt, bygg med:

```bash
OMNIROUTE_BUILD_PROFILE=minimal npm run build
```

Webpack-insticksprogrammet `NormalModuleReplacementPlugin` aliaserar fyra moduler till stubbar:

| Modul                                       | Stubb                                            |
| ------------------------------------------- | ------------------------------------------------ |
| `src/mitm/cert/install.ts`                  | `src/mitm/cert/install.stub.ts`                  |
| `src/lib/zed-oauth/keychain-reader.ts`      | `src/lib/zed-oauth/keychain-reader.stub.ts`      |
| `src/lib/cloudSync.ts`                      | `src/lib/cloudSync.stub.ts`                      |
| `src/lib/services/installers/ninerouter.ts` | `src/lib/services/installers/ninerouter.stub.ts` |

Varje stubb exporterar samma gränssnitt, men varje funktion utlöser
`featureDisabledError(name)` vid körning. Rutter som är beroende av den inaktiverade
modulen returnerar HTTP 503 med ett tydligt meddelande i stället för att aktivera den
känsliga kodvägen.

Det resulterande paketet är avsett att publiceras som `omniroute-secure`. Se
`docs/ops/PUBLISHING_SECURE.md` för publiceringsanvisningar.
