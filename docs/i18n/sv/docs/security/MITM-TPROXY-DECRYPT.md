TPROXY transparent dekryptering är OmniRoutes **femte insamlingsläge** för
MITM-stacken i [Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md).
Det fångar upp och **dekrypterar** lokal utgående HTTPS-trafik i Linux
med hjälp av TPROXY i kärnan samt policybaserad routning — **utan** att förfalska `/etc/hosts` och
**utan** att ändra operativsystemets globala systemproxyinställningar. Det är lämpligt för
huvudlösa miljöer (inga DNS-ändringar behöver återställas), och brandväggsreglerna rensas automatiskt vid omstart.

Till skillnad från de andra insamlingslägena kräver TPROXY ingen konfiguration per värd: det fångar
transparent upp **godtyckliga** destinationsvärdar på en målport, avslutar TLS med
ett lövcertifikat som utfärdas dynamiskt per SNI-värdnamn, samlar in det dekrypterade
utbytet och krypterar begäran på nytt till den ursprungliga destinationen.

> **Endast Linux, endast root, måste aktiveras uttryckligen.** Det här läget kräver Linux, ett systemspecifikt tillägg
> byggt med en C-verktygskedja och behörigheten **CAP_NET_ADMIN** (vanligtvis root). Det är endast
> tillgängligt via AgentBridge-API:t på loopback och är inaktiverat som standard. En betrodd
> MITM-CA som kan signera valfri värd är en kraftfull funktion — se [§6 Säkerhet](#6-security).

**Källkod:** `src/mitm/tproxy/`
**API-rutt:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**Växlingsknapp i kontrollpanelen:** Traffic Inspector → verktygsfältet för insamlingslägen → **"TPROXY-dekryptering"** ⚠
**Se även:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 Vad det är och när det ska användas

De fyra andra insamlingslägena har alla en begränsning:

| Läge                   | Hur trafiken styrs                                               | Begränsning                                               |
| ---------------------- | ---------------------------------------------------------------- | --------------------------------------------------------- |
| AgentBridge            | DNS-förfalskning via `/etc/hosts` för en fast uppsättning värdar | endast de registrerade IDE-agentvärdarna                  |
| Anpassade värdar       | DNS-förfalskning via `/etc/hosts` per värd                       | en post per värd; sudo krävs för att redigera hosts-filen |
| HTTP_PROXY             | Miljövariablerna `HTTP_PROXY`/`HTTPS_PROXY`                      | endast appar som respekterar miljövariabeln               |
| Systemomfattande proxy | Operativsystemets proxyinställningar                             | ändrar globalt tillstånd; måste återställas               |

TPROXY transparent dekryptering styr i stället trafiken på **kärnnivå**. Det
märker nya lokala utgående TCP-anslutningar till en målport (standardvärdet är `443`) i
kedjan `mangle OUTPUT`, en `ip rule` dirigerar om de märkta paketen till lokal leverans,
och vid återinträde överlämnar målet `TPROXY` i `mangle PREROUTING` dem till en
**IP_TRANSPARENT**-lyssnare — som sedan avslutar TLS och samlar in klartexten.

Använd det när du vill samla in och dekryptera trafik från en process som:

- kommunicerar med en värd som AgentBridge inte registrerar,
- inte respekterar `HTTP_PROXY`, och
- du inte vill störa genom en systemomfattande proxyändring.

Eftersom uppfångningen sker i kärnan behöver ursprungsprocessen **ingen
konfigurationsändring** — men processen måste lita på den dynamiska CA som OmniRoute
installerar (se [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 Krav

| Krav                | Detaljer                                                                                                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **OS**              | Endast Linux — **IP_TRANSPARENT** är ett socketalternativ som endast finns i Linux. Inläsaren returnerar "inte tillgänglig" på alla andra plattformar.                   |
| **Behörighet**      | Funktionen **CAP_NET_ADMIN** krävs för att skapa den transparenta socketen och tillämpa regler för `iptables`/`ip` — kör i praktiken som root.                           |
| **Internt tillägg** | Ett litet N-API-tillägg (`src/mitm/tproxy/native/transparent.c`) måste byggas eller levereras som en förkompilerad version. Se [§3](#3-the-native-ip_transparent-addon). |
| **Kärnmoduler**     | `iptables` med stöd för matchning via `TPROXY`, `mangle` och `mark` (validerat mot kärna 6.8.0).                                                                         |

**Kontrollerad degradering:** om något krav saknas (annat än Linux, ingen verktygskedja,
tillägget inte byggt) returnerar tilläggsinläsaren (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
`null` i stället för att kasta ett undantag. Statusen för infångningsläget rapporterar då
`available: false`, växlingsknappen på instrumentpanelen är **inaktiverad** med verktygstipset
"TPROXY-dekryptering kräver Linux + root + det interna tillägget", och resten av
OmniRoute fortsätter att fungera.

## §3 Det interna IP_TRANSPARENT-tillägget

Nodes `net`-modul kan inte anropa `setsockopt(IP_TRANSPARENT)` _före_ `bind()`, vilket
TPROXY kräver (annars släpper kärnan de omdirigerade paketen). Tillägget
(`src/mitm/tproxy/native/transparent.c`, byggt via `binding.gyp`) är en liten N-API-modul
som exponerar tre funktioner som används via `transparentSocket.ts`:

| Tilläggsfunktion                      | Socketåtgärd                                                                                 | Används för                                                                            |
| ------------------------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, returnerar rå fd | den transparenta infångningslyssnaren (Node tar över fd:n via `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | `setsockopt` **SO_MARK** på en befintlig fd                                                  | skydd mot loopar (markerar proxyns egna socketar)                                      |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **före** en icke-blockerande `connect()`, returnerar fd             | den återkrypterade vidarebefordringen uppströms (SYN-paketet bär markeringen)          |

Den ursprungliga destinationen läses från `socket.localAddress`/`localPort` — TPROXY
bevarar den, så ingen **SO_ORIGINAL_DST**-/NAT-uppslagning behövs.

### Bygga tillägget

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- Under `npm run build` kör `scripts/build/build-tproxy-native.mjs` `node-gyp
rebuild`. Det är **endast för Linux och inte fatalt** — om verktygskedjan saknas förblir
  infångningsläget helt enkelt otillgängligt.
- `assembleStandalone.mjs` kopierar `build/Release/transparent.node` till det
  fristående paketet; `transparentSocket.ts` hittar det både modulrelativt och
  cwd-relativt (`<cwd>/src/mitm/tproxy/native/...`).
- `build/` och `prebuilds/` ignoreras av git — binärfilen **byggs och checkas aldrig
  in**.

Inläsaren söker i följande prioritetsordning:
`native/build/Release/transparent.node`, därefter `native/prebuilds/transparent.node`
(båda modulrelativt och under `<cwd>/src/mitm/tproxy/`).

## §4 Den dynamiska CA:n per SNI och installationsprogrammet för betrodda certifikat

> **Uppdatering #6684:** AgentBridges statiska server (`src/mitm/server.cjs`) delar nu
> samma arkitekturmönster för CA/lövcertifikat i stället för att använda ett enda statiskt
> självsignerat lövcertifikat. Den använder en **separat** CA-instans
> (`src/mitm/cert/rootCa.ts`, beständigt lagrad i `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> och installeras på den befintliga platsen `omniroute-mitm.crt` i lagret för betrodda
> certifikat (och ersätter därmed det gamla enskilda lövcertifikatet där — ingen rensning
> av dubbla betrodda certifikat behövs), helt åtskild från TPROXY:s egen plats
> `omniroute-tproxy-ca.crt` nedan.
> Nya AgentBridge-installationer får CA-modellen automatiskt. En installation som
> redan litade på det gamla statiska lövcertifikatet fortsätter att använda det tills
> operatören aktivt väljer den nya modellen via `MITM_ROOT_CA_ENABLED=true` (se
> `src/mitm/cert/migration.ts`) — en betrodd MITM-CA som kan signera ett lövcertifikat
> för **vilken** värd som helst är betydligt kraftfullare än det gamla lövcertifikatet
> med fasta SAN-poster, så bytet sker aldrig omärkligt för en installation som redan
> har etablerat förtroende.

Historiskt fungerade AgentBridges statiska MITM-certifikat endast eftersom AgentBridge
DNS-förfalskar en **fast** uppsättning värdar (nu förenad med modellen nedan). TPROXY
avlyssnar **godtyckliga** värdar, så dess lyssnare måste presentera ett giltigt
lövcertifikat för det SNI som klienten begär — samma krav som AgentBridge nu har
för hela uppsättningen `MITM_TOOL_HOSTS` (9 verktygsposter) i stället för bara de 4
antigravity-värdarna.

### Dynamisk CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` kör en lokal CA (byggd på beroendet `selfsigned`) som:

- Genererar en långlivad CA via `generateMitmCa()` (CN `"OmniRoute MITM CA"`,
  10 års giltighet, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-bitars RSA/SHA-256).
- Utfärdar ett **lövcertifikat per SNI-värdnamn vid behov** via `issueLeafCert()` (1 års
  giltighet, `subjectAltName` = SNI-värden) och cachar en `tls.SecureContext`
  per värdnamn.
- Exponerar `createSNICallback()` för den TLS-terminerande servern (se [§5](#5-how-decrypt-and-capture-work)).
- Kan skapas med en `existingCa` för att hålla CA:n stabil mellan omstarter
  (så att lagret för betrodda certifikat inte behöver installeras om).

CA:ns privata nyckel **lämnar aldrig maskinen**.

### Installationsprogram för betrodda certifikat (`src/mitm/tproxy/caTrust.ts`)

Den avlyssnade klienten måste lita på den dynamiska CA:n, så när insamlingsläget
startas installeras CA-certifikatet i operativsystemets lager för betrodda certifikat
på en **dedikerad plats** — `omniroute-tproxy-ca.crt` (konstanten
`TPROXY_CA_CERT_NAME`) — som hålls åtskild från det statiska MITM-certifikatets plats
(`omniroute-mitm.crt`), så att de aldrig skriver över varandra.

`installTproxyCa(caPem, sudoPassword?)` identifierar distributionens katalog för
betrodda certifikat (i ordning: Debian-varianten först) och kör motsvarande
uppdateringskommando:

| Katalog för betrodda certifikat             | Uppdateringskommando     |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Installationen mellanlagrar PEM-filen i en temporär fil, kör sedan (med förhöjd
behörighet) `mkdir -p` för katalogen, använder `cp` för att kopiera den mellanlagrade
filen dit och kör uppdateringskommandot. `uninstallTproxyCa()` tar endast bort den
dedikerade platsen (och lämnar det statiska MITM-certifikatet orört) och uppdaterar
lagret — på andra system än Linux gör funktionen ingenting.

Alla kommandon som kräver förhöjd behörighet körs via `execFileWithPassword`
(`src/mitm/systemCommands.ts`) — `spawn` med **argumentvektorer, inget skal och ingen
stränginterpolering** (strikt regel nr 13). När processen körs som root (t.ex. på
VPS:en) körs målkommandot direkt och inget lösenord behövs. På en skrivbordsdator
där processen inte körs som root skickas `sudoPassword` via standardindata till
`sudo -S`.

> Skrivbordsdatorns `sudoPassword` anges i POST-anropets kropp för att auktorisera
> installationen i lagret för betrodda certifikat. Det ignoreras helt när processen
> körs som root.

## §5 Så fungerar dekryptering och insamling

Pipeline (allt under `src/mitm/tproxy/`):

```
lokal app  ──TCP/443──▶  mangle OUTPUT markerar anslutningen (fwmark)
                          ip rule → lokal routningstabell → lo
                          mangle PREROUTING TPROXY → IP_TRANSPARENT-lyssnare (port 8443)
                              │  captureMode.ts: läser ursprunglig destination från socket.localAddress
                              ▼
                          tlsCapture.ts:
                            1. TLS-terminera KLIENTEN med ett lövcertifikat per SNI (dynamicCert)
                            2. intern http.Server tolkar den dekrypterade klartexten
                            3. insamling → globalTrafficBuffer.push() med source: "tproxy"
                               (sanitizeHeaders + maskSecret tillämpas)
                            4. vidarebefordra ÅTERKRYPTERAT till den ursprungliga destinationen
                               via en socket med bypass-markering (connectMarked, anti-loop)
                              │
                              ▼
                          ursprunglig uppströmsserver (api.example.com)
```

- **TLS-terminering** (`createTlsCaptureServer`): omsluter den råa, avlyssnade
  socketen i en `tls.TLSSocket` på serversidan med den dynamiska CA:ns SNI-callback
  och överlämnar sedan den dekrypterade strömmen till en intern `http.Server`
  (standardtricket för MITM-terminering). Socketarnas livslängd begränsas av
  `MITM_IDLE_TIMEOUT_MS` så att en tunnel som har hängt sig inte kan uttömma
  filbeskrivare.
- **Insamling** (`handleDecryptedRequest`): lägger till en `InterceptedRequest` med
  `source: "tproxy"`, status som börjar med `"in-flight"`, headers som bearbetats
  med `sanitizeHeaders()` och bodies med `maskSecret()` innan de hamnar i
  bufferten. Posten uppdateras sedan med svaret, storlekarna och latensen.
- **Återkrypterad vidarebefordran** (`createForward` / `realForward`): krypterar
  åter till den ursprungliga destinationen. `rejectUnauthorized` är som standard
  **`true`** (säkert som standard) — uppströmscertifikatet verifieras mot det
  SNI/Host som klienten begärde, så proxyn avvisar exakt det som den ursprungliga
  klienten skulle ha avvisat.

### Anti-loop (SO_MARK)

Eftersom reglerna markerar nya lokala utgående anslutningar skulle proxyns **egen**
återkrypterade vidarebefordran normalt avlyssnas på nytt — en oändlig loop.
Vidarebefordringsvägen skyddar mot detta med en bypass-markering på socketen
(**SO_MARK**):

- `realForward` öppnar sin uppströmssocket via `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  — `DEFAULT_BYPASS_MARK = 0x539` — vilket ställer in **SO_MARK** **före** `connect()`,
  så att vidarebefordringens SYN bär bypass-markeringen.
- Regeln `mangle OUTPUT` undantar anslutningar som redan bär bypass-markeringen
  (`-m mark ! --mark <bypassMark>`), så proxyns vidarebefordran markeras **inte**
  på nytt och går inte in i TPROXY igen.

> Implementeringsanmärkning: socketen med bypass-markering måste installeras på
> agentens `createConnection` (`https.request({ createConnection })` ignoreras utan
> meddelande när en agent finns), annars skulle vidarebefordringen öppna en omarkerad
> socket och loopen återkomma. Detta var den e2e-validerade anti-loop-korrigeringen.

## §6 Säkerhet

| Kontroll                               | Detalj                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **API endast för loopback**            | `/api/tools/agent-bridge/tproxy` omfattas av prefixet `/api/tools/agent-bridge/` i `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`). Loopback-kontrollen körs **före** autentisering (hårda regler nr 15 och 17) — en läckt JWT över en tunnel kan inte starta TPROXY-insamling, som tillämpar `iptables`-regler och installerar en certifikatutfärdare i betroddhetsarkivet via underprocesser. |
| **Dedikerad CA-plats**                 | Den dynamiska certifikatutfärdaren installeras som `omniroute-tproxy-ca.crt` och skriver aldrig över det statiska MITM-certifikatet.                                                                                                                                                                                                                                                                         |
| **CA-nyckeln lämnar aldrig värden**    | `DynamicCertStore` lagrar CA-nyckeln i minnet; den exporteras inte.                                                                                                                                                                                                                                                                                                                                          |
| **Maskering av hemligheter**           | `maskSecret()` för begärande- och svarskroppar samt `sanitizeHeaders()` för huvuden körs **före** `globalTrafficBuffer.push()`.                                                                                                                                                                                                                                                                              |
| **Ingen skaltolkning**                 | Alla `iptables`-/`ip`-/betroddhetsarkivkommandon körs via `execFile`/`execFileWithPassword` med argumentmatriser (hård regel nr 13).                                                                                                                                                                                                                                                                         |
| **Verifiering av uppströmscertifikat** | Den återkrypterade vidarebefordringen verifierar uppströmscertifikatet som standard (`rejectUnauthorized: true`).                                                                                                                                                                                                                                                                                            |
| **Felsanering**                        | Ruttens felsvar bearbetas av `sanitizeErrorMessage()` (hård regel nr 12).                                                                                                                                                                                                                                                                                                                                    |

**MITM-certifikatutfärdaren är en kraftfull funktion.** En certifikatutfärdare som operativsystemet litar på och som kan signera valfri
värd innebär att allt som OmniRoute fångar upp kan dekrypteras. Funktionen skyddas bakom det
uttryckliga, lokala TPROXY-insamlingsläget, är inaktiverad som standard och posten i betroddhetsarkivet
tas bort när du stoppar läget.

## §7 Transaktionell tillämpning/återställning av brandvägg

En krasch får aldrig lämna kvar en `mangle`-regel eller en inaktuell rutt. Kommandobyggaren
(`src/mitm/tproxy/commands.ts`) och köraren (`src/mitm/tproxy/setup.ts`) garanterar att
**återställning är den exakta inversen av tillämpning, i omvänd ordning**.

`applyTproxy(cfg)` kör tillämpningskommandona i ordning. Vid **vilket som helst** fel kör den en
fullständig `revertTproxy(cfg)` efter bästa förmåga och kastar felet vidare — så brandväggen är antingen
fullständigt tillämpad eller fullständigt återställd, aldrig delvis tillämpad. `revertTproxy(cfg)` kör de
inversa kommandona i omvänd ordning och ignorerar fel (idempotent — säker att anropa
ovillkorligt, t.ex. från AgentBridge-rensningen `repairMitm()`).

`validateTproxyConfig(cfg)` körs före alla kommandon: portar måste vara `1–65535`,
`mark`/`routeTable`/`bypassMark` måste vara positiva heltal och `bypassMark` måste
skilja sig från `mark` (skydd mot loopar).

### Tillämpningskommandon (i ordning)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Återställningen tar bort dem i omvänd ordning: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> Lösningen är **OUTPUT-baserad** eftersom MITM-användningsfallet gäller _lokal_ utgående
> trafik (appar på samma värd), vilken TPROXY enbart i `PREROUTING` inte
> ser — `PREROUTING` ser endast vidarebefordrad trafik. Kedjan `OUTPUT` märker nya
> lokala anslutningar, `ip rule` omdirigerar dem till lokal leverans (`lo`) och
> `PREROUTING` tilldelar dem därefter till den transparenta lyssnaren.

## §8 Konfiguration

Startbegäran (`POST /api/tools/agent-bridge/tproxy`) accepterar följande
fält, validerade av `StartTproxyBodySchema` (`tproxy/route.ts`). Alla är valfria
och använder sina standardvärden om de utelämnas:

| Fält             | Typ                   | Standard | Anmärkningar                                                                                                                                       |
| ---------------- | --------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | heltal (1–65535)      | `443`    | TCP-destinationsport som ska avlyssnas transparent                                                                                                 |
| **mark**         | heltal (≥1)           | `0x2333` | Brandväggsmarkering som anges i `OUTPUT` och matchas av `ip rule` + `PREROUTING`                                                                   |
| **onPort**       | heltal (1–65535)      | `8443`   | Porten som den transparenta (**IP_TRANSPARENT**) lyssnaren binder till                                                                             |
| **routeTable**   | heltal (≥1)           | `233`    | ID för principroutningstabellen som innehåller rutten `local 0.0.0.0/0`                                                                            |
| **bypassMark**   | heltal (≥1, ≠ `mark`) | `0x539`  | Markeringen för förbikopplingssocketen (**SO_MARK**) som proxyn anger på sina egna uppströmsanslutningar; exkluderas i `OUTPUT` (skydd mot loopar) |
| **sudoPassword** | sträng                | —        | Endast för skrivbordsmiljöer utan root: auktoriserar installationen i betrodd lagring; ignoreras vid körning som root                              |

Det finns **inga miljövariabler** för TPROXY — all konfiguration sker via
POST-brödtexten eller standardvärdena ovan.

## §9 Aktivering från Traffic Inspector

1. Öppna **Traffic Inspector** (`/dashboard/tools/traffic-inspector`).
2. Leta reda på knappen **"TPROXY Decrypt"** ⚠ i verktygsfältet för insamlingslägen
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Om den är **inaktiverad** med verktygstipset "TPROXY-dekryptering kräver Linux + root +
     det inbyggda tillägget" är det inbyggda tillägget inte tillgängligt på den här värden (inte Linux,
     ingen verktygskedja eller tillägget har inte byggts). Se [§2](#2-requirements) och [§3](#3-the-native-ip_transparent-addon).
3. Klicka på knappen. Den anropar `POST /api/tools/agent-bridge/tproxy` via
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`), vilket
   skapar den dynamiska certifikatutfärdaren, öppnar den transparenta lyssnaren, tillämpar brandväggsreglerna
   och installerar certifikatutfärdaren i operativsystemets betrodda certifikatarkiv.
4. När läget körs blir växlingsknappen bärnstensfärgad och visar det aktuella antalet avlyssningar
   (`· <interceptCount>`). Avlyssnade förfrågningar visas i listan över förfrågningar med
   `source: "tproxy"`.
5. Klicka igen för att stoppa — `DELETE /api/tools/agent-bridge/tproxy` via
   `stopTproxyCaptureMode()` stänger lyssnaren, avinstallerar certifikatutfärdaren och återställer
   brandväggsreglerna.

Statusen för insamlingsläget (körs / tillgängligt / antal avlyssningar / lyssnarport) kommer
från `GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` i
`src/mitm/tproxy/captureManager.ts`). Endast **en** TPROXY-session körs åt gången —
ett försök att starta en andra avvisas med "TPROXY-insamlingsläget körs redan".

## §10 Felsökning

### Växlingsknappen är inaktiverad

Det inbyggda tillägget kan inte läsas in. Bekräfta att du använder Linux, har byggt tillägget
(`npm run build:native:tproxy`) och att processen kan läsa in `transparent.node`.
`isTransparentSocketAvailable()` styr växlingsknappen; `GET /api/tools/agent-bridge/tproxy`
returnerar `available: false` när tillägget saknas.

### Ingenting samlas in

- Bekräfta att den avlyssnade processen faktiskt ansluter till konfigurerad `dport`
  (standardvärde `443`).
- Bekräfta att processen litar på den dynamiska certifikatutfärdaren. Certifikatutfärdaren installeras som
  `omniroute-tproxy-ca.crt`; appar med egna betrodda certifikatarkiv (Firefox/Chrome NSS)
  kan behöva få certifikatet tillagt även där.
- Kör AgentBridges självtest **Diagnose** (se
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) för kontroller av betrott certifikat / serverns
  hälsa.

### Kvarvarande brandväggsregler efter en krasch

`revertTproxy()` är den exakta inversen till tillämpningen och är idempotent. När läget stoppas
återställs reglerna; om OmniRoute avslutades mitt under en session använder du AgentBridges
åtgärd **Repair** (`POST /api/tools/agent-bridge/repair`) för att återställa överblivet systemtillstånd
(DNS-förfalskning, rotcertifikatutfärdare, systemproxy). TPROXY-reglerna i `mangle` och rutten
rensas också automatiskt vid omstart.

### Oändlig loop / proxyn avlyssnar sin egen vidarebefordran

Det här är fallet som skyddet mot loopar hanterar. Bekräfta att `bypassMark` skiljer sig från `mark` (detta
säkerställs av valideringen) och att vidarebefordran använder `connectMarked` (vilket den gör i `realForward`).
Se [§5 Skydd mot loopar](#anti-loop-so_mark).
