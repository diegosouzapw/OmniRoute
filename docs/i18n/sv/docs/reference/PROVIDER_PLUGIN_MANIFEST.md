`open-sse/config/providerPluginManifest.ts` definierar det JSON-säkra kontraktet för
leverantörspluginer. `open-sse/config/providerPluginManifestRegistry.ts` kopplar detta
kontrakt till det aktuella leverantörsregistret för sidoprocesser som Bifrost,
CLIProxyAPI eller en framtida Go-/Rust-router. TypeScript-registret förblir
sanningskällan, men sidoprocesser kan använda manifestet utan att importera
exekveringskod, OAuth-standardvärden, headers eller processtillstånd från miljön.

Samma manifest är tillgängligt via HTTP på
`GET /api/v1/provider-plugin-manifest` för sidoprocesser som körs utanför processen.

OmniRoute annonserar denna URL till Bifrost och CLIProxyAPI via
request-headern `X-OmniRoute-Provider-Manifest-Url`. Ange
`OMNIROUTE_PROVIDER_MANIFEST_URL` när sidoprocessen behöver en publik URL eller
containernätverks-URL i stället för den lokala requestens ursprung.

## Uppdatera manifestet

HTTP-endpointen returnerar `Cache-Control: public, max-age=60` och en stark
`ETag`. En sidoprocess bör behålla det senast validerade manifestet och skicka dess ETag
i `If-None-Match` vid uppdatering. Ett `304 Not Modified`-svar har ingen body;
sidoprocessen behåller sitt cachade manifest. Om det inte finns något validerat cachat manifest
måste sidoprocessen skicka en ovillkorlig request i stället för att acceptera ett `304`.

## Mål

Flytta leverantörsmetadata mot ett pluginkontrakt så att den kritiska requestvägen
så småningom kan hanteras av en sidoprocess med lägre latens, samtidigt som OmniRoute behåller
TypeScript-routen som policygrind och reservlösning. Manifestet är additivt: det
ändrar inte requestdirigeringen i sig.

## Kontrakt

Manifestet innehåller:

- leverantörs-id och alias
- upstream-format och exekveringsnamn
- autentiseringstyp, autentiseringsheader och valfritt autentiseringsprefix
- statisk endpointmetadata
- lämplighet för sidoprocesser och uttryckliga skäl till att en leverantör bör stanna på TS
- JSON-säker modellmetadata såsom kontextlängd, stöd för vision/resonemang och
  parametrar som inte stöds
- kapacitetstaggar, inklusive `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` och `usage-supported`

Manifestet exkluderar avsiktligt:

- OAuth-klienthemligheter och förvalda hemliga värden
- uppslagning av exekveringsmiljö
- request-headers och publika hjälpfunktioner för inloggningsuppgifter
- dynamiska URL-byggare
- exekveringsfunktioner
- interna detaljer i sessionspoolen

## Kapacitetstaggar

`capabilities` är en sorterad array med taggar som härleds från registerposten. Integratörer
bör behandla den som det maskinläsbara svaret på ”vad kan den här leverantören göra”, i stället för
att läsa TypeScript-källorna på nytt.

| Tagg                 | Betydelse                                                                       |
| -------------------- | ------------------------------------------------------------------------------- |
| `apikey`             | Accepterar en API-nyckel (`authType` är `apikey` eller `optional`).             |
| `oauth`              | Använder ett OAuth- eller sessionsflöde.                                        |
| `responses`          | Exponerar en bas-URL för OpenAI Responses API.                                  |
| `passthrough-models` | Tillhandahåller modeller direkt från upstream i stället för en statisk katalog. |
| `custom-executor`    | Kör en exekverare som inte är standard, så den stannar på TypeScript-vägen.     |
| `sidecar-candidate`  | Speglar `sidecar.eligible` — säker att överväga för import till en sidoprocess. |
| `usage-fetch`        | Har en ansluten hämtare för användning eller kvot (`getUsageForProvider`).      |
| `usage-supported`    | Användnings-API:et accepterar denna leverantör (`isSupportedUsageConnection`).  |

`usage-fetch` är endast till för identifiering. Den anger att OmniRoute vet hur användning ska
läsas för leverantören; den aktiverar inte hämtning, ändrar inte kvotsemantiken och innebär inte att
Dashboard-widgeten för kvoter är aktiverad för leverantören — den widgeten styrs separat av
`USAGE_SUPPORTED_PROVIDERS`. Sanningskällan är `USAGE_FETCHER_PROVIDERS` i
`open-sse/services/usage/fetcherProviders.ts`.

Den listan använder strängarna som användningsdispatchern accepterar som nycklar, så den blandar kanoniska id:n
med alias och är något längre än antalet taggade leverantörer: poster som
inte är chattleverantörer i manifestregistret (exempelvis sökleverantören `firecrawl`
och ACP-leverantören `amazon-q`) har ingen manifestpost att tagga.

`usage-supported` anger huruvida serverns och Dashboardens användningsrutter accepterar en anslutning
för leverantören. Den speglar `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
och `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), som båda styrs av
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). Till skillnad från
`usage-fetch` genereras den enbart för leverantörens id — runtime-kontrollen kör
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` utan aliasuppslagning, så manifestet
behåller samma regel. De två taggarna har olika tillämpningsområden: 3 leverantörer har endast
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) och 1 har endast
`usage-supported` (`xiaomi-mimo-token-plan`), så den ena innebär inte den andra.

## Användning av sidecar

Sidecars bör behandla `sidecar.eligible` som en konservativ kandidatsignal, inte
som ett ovillkorligt dirigeringsbeslut. De första importmålen bör vara
leverantörer med API-nyckel och statisk slutpunkt som använder standardexekveraren. Leverantörer med
anpassade webbexekverare, OAuth-/sessionsflöden, dynamiska URL-byggare eller poolkonfiguration
ska fortsätta använda reservvägen i TypeScript tills en sidecar implementerar motsvarande
beteende och telemetrin visar likvärdighet.

Föreslagna migreringsfaser:

1. Generera och validera leverantörens pluginmanifest från TS-registret.
2. Lär Bifrost eller CLIProxyAPI att importera manifestet för leverantörer med
   API-nyckel och statisk slutpunkt.
3. Dirigera kvalificerade leverantörer genom sidecaren bakom `OMNIROUTE_RELAY_BACKEND`
   samtidigt som TS-reservvägen förblir aktiverad.
4. Flytta över leverantörer först när lyckandefrekvens, p99-latens, strömningsbeteende
   och hantering av parametrar som inte stöds motsvarar TS-vägen.
5. Lägg till sidecar-inbyggda pluginer för anpassade exekverare, en leverantörsfamilj
   i taget.

## Varför leverantörer inte bäddas in direkt i Next

Next-klientdelen bör inte ansvara för exekvering hos leverantörer. Den bör anropa API-
gränssnittet. Serverdelen kan sedan avgöra om TypeScript-exekveraren,
Bifrost, CLIProxyAPI eller en framtida inbyggd sidecar ska användas. Detta håller
begärandesignering, kontroller mot tillåtelselistor, DB-policy och reservbeteende centraliserade innan
någon överlämning till en sidecar sker.
