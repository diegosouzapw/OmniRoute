Reläer (Vercel, Deno, Cloudflare) avslutar uppströmsanslutningen i en
serverlös backend så att OmniRoute kan skicka utgående trafik från en stabil region samtidigt som
leverantörens API-nyckel hålls på serversidan. Det här dokumentet beskriver de två fellägen
som operatörer stöter på i produktion och de återställningsvägar som OmniRoute tillhandahåller för
vart och ett.

## Så lagras reläautentisering

När du distribuerar ett relä via **Inställningar → Proxypool → Distribuera relä**
lagrar distributionsflödet reläets autentiseringstoken i proxyobjektets JSON-fält `notes`:

- Om `STORAGE_ENCRYPTION_KEY` är inställd skrivs token som `relayAuthEnc`
  (AES-krypterad vid lagring).
- Annars skrivs den som `relayAuth` i klartext.

Vid en begäran returnerar `extractRelayAuth(notes)` den form som finns,
så att reläet fortsätter fungera efter omstarter.

## Felläge 1 — token kan inte dekrypteras efter nyckelrotation

**Symptom:** reläer som tidigare fungerade returnerar nu `401`-fel eller
autentiseringsfel från uppströmsleverantören efter att `STORAGE_ENCRYPTION_KEY`
har roterats i miljön eller hemlighetshanteraren. Den lagrade `relayAuthEnc`-blobben
kan inte längre dekrypteras, så `extractRelayAuth` returnerar en tom sträng och
reläet skickar ingen autentisering.

**Återställning — reparera på plats (ingen omdistribution):**

1. Öppna **Inställningar → Proxypool**.
2. Relärader som saknar autentisering visar en gul etikett med `autentisering saknas`
   och knappen **Reparera**.
3. Klicka på **Reparera**. OmniRoute anropar
   `POST /api/settings/proxies/[id]/repair-relay`, som:
   - dekrypterar `relayAuthEnc` med den **aktuella** nyckeln,
   - skriver tillbaka `relayAuth` i klartext till `notes`,
   - returnerar `{ repaired: true, mode: "recovered" }`.

Reläet börjar åter hantera trafik utan att du behöver ange några
distributionsautentiseringsuppgifter på nytt.

Detta fungerar endast om den aktuella `STORAGE_ENCRYPTION_KEY` fortfarande kan
dekryptera blobben. Om du roterade nyckeln **utan** en migrering kan blobben
inte återställas.

## Felläge 2 — token kan inte återställas (nyckeln har roterats bort)

**Symptom:** du klickade på **Reparera** och fick
`{ repaired: false, mode: "redeploy", status: 409 }`.

**Återställning — distribuera om:**

Den lagrade token kan inte återställas med den aktuella nyckeln. Distribuera om
reläet via samma dialogruta som du använde från början (menyn **Distribuera relä**
→ Vercel / Deno / Cloudflare). Distributionsflödet skriver en ny token
(krypterad med den aktuella nyckeln), och radens etikett `autentisering saknas`
försvinner.

I användargränssnittet öppnar knappen **Reparera** automatiskt dialogrutan för
omdistribution när token inte kan återställas, så du behöver aldrig leta efter
den manuellt.

## Felläge 3 — reläet är nåbart men fungerar inte korrekt

**Symptom:** proxytestet (knappen `speed`) visar att reläet är tillgängligt,
men begäranden misslyckas fortfarande emellanåt.

Kontrollera de relämedvetna huvuden som returneras av OmniRoutes automatiska
testsond (se **Inställningar → Proxypool** och räknarna `relayTested` /
`relayAlive`):

- `x-relay-url` — vilken reläbackend som svarade.
- `x-relay-mode` — `ts` | `bifrost` | `auto` för den begäran.
- `x-relay-attempts` — hur många relähopp som prövades innan begäran lyckades.
- `x-relay-fallback` — `true` när begäran föll tillbaka från den föredragna
  backend-tjänsten till TypeScript-reläet.

En hög frekvens för `x-relay-fallback` tillsammans med ett lågt `relayAlive`
innebär att sidecar-backend-tjänsten inte fungerar korrekt. Du bör då antingen
åtgärda den eller ändra reläets backend-strategi till `ts` (se
`RELAY_BACKEND_STRATEGY.md`).

## API-referens

| Metod  | Sökväg                                    | Brödtext                | Lyckat resultat                                                                                                                          | Fel                                                                                         |
| ------ | ----------------------------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }` när värdet härleds på nytt; `200 { repaired: false, mode: "noop" }` när klartext redan finns | `409 { mode: "redeploy" }` kan inte återställas; `400` inte en relätyp; `404` hittades inte |

Listrutten `GET /api/settings/proxies` lägger till ett hemlighetsfritt
`relayInfo: { isRelay, authMissing, repairMode }` för varje objekt så att
instrumentpanelen kan visa reparationsalternativet utan att någonsin exponera
token.
