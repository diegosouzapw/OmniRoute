> **Kort sagt**: `open-sse/` är den centrala strömningsmotorn som driver varje LLM-begäran i OmniRoute. Den innehåller cirka 1 400 filer som implementerar begärandepipelinen, exekverare, tjänster, MCP-servern och översättningslagret. Den här guiden förklarar hur delarna hänger ihop.

**Källa:** `open-sse/` (workspace-paket, cirka 1 440 `.ts`-filer som inte är testfiler)

---

## Varför ett separat workspace-paket?

`open-sse/` är ett **fristående workspace** i OmniRoutes monorepo av flera skäl:

1. **Återanvändbarhet** — `open-sse` publiceras som `@omniroute/open-sse` på npm, så att andra projekt kan använda det oberoende
2. **Tydliga gränser** — strömningsmotorn är frikopplad från OmniRoute-specifika gränssnitts- och databaslager
3. **Prestanda** — motorn har inga Next.js-beroenden, vilket möjliggör snabbare kallstarter i CLI- och serverless-sammanhang
4. **Versionshantering** — `open-sse` kan lansera utgåvor enligt sin egen tidsplan

```json
// package.json
"workspaces": ["open-sse"]
```

## Begärandepipelinen

Varje LLM-begäran flödar genom en **pipeline i 5 steg**:

```
                              ┌──────────────┐
   HTTP-begäran                │  1. ROUTNING │   combo-matchning, modellval
   (Next.js-route)             └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. ÖVERSÄTT │   formatkonvertering (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. EXEKVERA │   leverantörsexekverare, HTTP, återförsök, brytare
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STRÖMMA  │   SSE-transformering, mottryck
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. REGISTRERA│  användningsspårning, anropslogg, felklassificering
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP-svar (SSE eller JSON)
```

### Steg 1: Routning (services/combo.ts)

**Startpunkt**: `handleComboChat()` i `services/combo.ts`

Matchar begäran mot en konkret tupel av typen `(provider, model, account, credentials)`:

- Slå upp kombinationen efter ID (eller skapa en virtuell kombination för `auto/*`-modeller)
- Tillämpa routningsstrategin (prioritet, viktad, round-robin osv.)
- Filtrera bort leverantörer som inte fungerar korrekt (kretsbrytare)
- Välj nästa användbara mål

För `auto/*`-modeller gör det här steget även följande:

- Kör algoritmen för **poängsättning med 16 faktorer** (`services/autoCombo/`)
- Väljer ett `provider+model`-par baserat på hälsa, kostnad, latens osv.

### Steg 2: Översättning (translator/)

Om källformatet (t.ex. OpenAI) skiljer sig från målformatet (t.ex. Claude) **översätts** begäran:

- Systemprompt → systemmeddelande
- Verktygsdefinitioner → leverantörsspecifikt verktygsformat
- Parametrar för resonemang/tänkande → leverantörsspecifika motsvarigheter
- Normalisering av meddelanderoller (`developer` → `system` för andra än OpenAI)

`translator/index.ts` exponerar:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Steg 3: Exekvering (executors/)

**Startpunkt**: `getExecutor(providerId).execute(request, options)`

Alla leverantörer använder `DefaultExecutor` (`executors/default.ts`) via reservlösningen i `getExecutor()`-fabriken. Exekveraren:

- Skapar URL:en till den överordnade tjänsten (`buildUrl()`)
- Lägger till leverantörsspecifika headers (`buildHeaders()`)
- Transformerar begärandekroppen (`transformRequest()`)
- Skickar HTTP-begäran med återförsök och exponentiell väntetid
- Hanterar autentiseringsuppdatering vid behov (OAuth-leverantörer)

Alla exekverare utökar `BaseExecutor` (`executors/base.ts`, 1170 rader kod), som tillhandahåller:

- Gemensam logik för återförsök
- Proxyintegrering
- Integrering med kretsbrytare
- Hookar för registrering av användning

### Steg 4: Strömning (utils/stream.ts)

För strömmande svar returnerar exekveraren en **ReadableStream**. Hanteraren:

- Leder strömmen genom en SSE-transformering (`createSSETransformStreamWithLogger`)
- Använder regelbundna heartbeat-pingar för att identifiera döda anslutningar
- Hanterar klientfrånkopplingar korrekt (`pipeWithDisconnect`)
- Transformerar SSE → JSON för klienter som inte använder strömning

För icke-strömmande svar returnerar exekveraren ett tolkat JSON-objekt som vidarebefordras oförändrat.

### Steg 5: Registrering (services/usage.ts)

Efter svaret (oavsett om det lyckas eller misslyckas) registreras användningen:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` från svaret
- `cost_usd` beräknat från prisdata
- `latency_ms`, `status`, `error_class` om det misslyckas
- Sparas i tabellen `usage_history`

Anropsloggar (om aktiverade) skrivs till `${DATA_DIR}/call_logs/`.

## Djupdykning i nyckelfiler

### chatCore.ts (5977 rader)

Den **huvudsakliga hanteraren för förfrågningar**. Trots sin storlek har den en tydlig struktur:

```ts
// Pseudostruktur för chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Autentisering + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Validering av brödtext
  const body = await parseRequestBody(request);

  // 3. Formatidentifiering + översättning
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo-dirigering
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Fortsätt till nästa mål
    }
  }

  // 5. Reservlösning för nödsituationer
  return await emergencyFallback(body);
}
```

Trots att den består av en enda enorm funktion är den organiserad i **kommenterade avsnitt** som motsvarar pipeline-processens fem steg.

### combo.ts (4456 rader)

**Dirigeringsmotorn** som omvandlar en combo till en ordnad lista med mål.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

Stöder **19 dirigeringsstrategier** (se `src/shared/constants/routingStrategies.ts`):

| Strategi            | Beteende                                                                          |
| ------------------- | --------------------------------------------------------------------------------- |

| `weighted`          | Sannolikhetsbaserat enligt vikt per mål                                           |
| `round-robin`       | Växla mellan målen i tur och ordning                                              |
| `context-relay`     | Överlämna kontext mellan mål                                                      |
| `fill-first`        | Fyll kvoten innan nästa mål används                                               |
| `p2c`               | Val mellan två alternativ                                                         |
| `random`            | Likformigt slumpmässigt                                                           |

| `cost-optimized`    | Billigaste fungerande mål först                                                   |
| `reset-aware`       | Tar hänsyn till leverantörens återställningsfönster                               |

## Exekverare (75+ filer)

En fil per leverantör. De utökar alla `BaseExecutor` och åsidosätter det som skiljer sig.

### Gemensamma mönster

Leverantörer löses via `getExecutor(providerId)`, som returnerar den konfigurerade exekveraren. OpenAI-/Anthropic-kompatibla leverantörer använder `DefaultExecutor` (`executors/default.ts`). Leverantörsspecifikt beteende (bas-URL, autentiseringshuvuden, API-version) konfigureras i `open-sse/config/providers/`, medan transformeringar av förfrågningskroppen hanteras i `open-sse/translator/`.

**Anpassad URL** anges via leverantörskonfigurationen:

```ts
// Leverantörskonfiguration i open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Anpassad autentisering** hanteras genom leverantörsregistrets autentiseringskonfiguration (API-nyckel, OAuth, huvudprofiler).

Transformeringar av en **anpassad förfrågningskropp** (t.ex. när Anthropic separerar `system` från `messages`) registreras per leverantör i `open-sse/translator/`.

````

### Exekveringsfabriken

`executors/index.ts` exporterar `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Upplösningen sker via `ExecutorRegistry` (`executors/registry.ts`): varje specialiserad exekverare deklareras i den inbyggda tabellen i `executors/index.ts` och registreras via `registerExecutor(alias, instance)` när modulen läses in; `getExecutor()` konsulterar registret och återgår till en memoiserad `DefaultExecutor` för leverantörer som saknar en specialiserad post. Den fullständiga mappningen alias → exekverare beskrivs av det gyllene testet `tests/unit/executor-map-golden.test.ts`.

## Översättare

Översätt mellan **3 format**: OpenAI, Anthropic, Gemini samt det nya Responses API.

### När översättning sker

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Vanliga översättningar:

- `OpenAI → Anthropic`: separat `system`-fält, `x-api-key`-header
- `OpenAI → Gemini`: `contents` i stället för `messages`, `systemInstruction`
- `OpenAI → Responses API`: `input`-array, tillstånd via `previous_response_id`

### Hanterade specialfall

- Rollen `developer` → `system` för andra leverantörer än OpenAI
- Rollen `system` → sammanfogas med det första användarmeddelandet för GLM/ERNIE
- `json_schema` → Geminis `responseMimeType` + `responseSchema`
- `tools` → leverantörsspecifikt verktygsformat
- Parametrar för resonemang (o1, Claude) → leverantörsspecifika motsvarigheter

## MCP-server

`open-sse/mcp-server/` implementerar servern för **Model Context Protocol**:

- **110 verktyg** (leverantörshantering, kombinationer, minne, cache, komprimering, proxy, färdigheter, spelifiering, insticksprogram, Notion, Obsidian, lokal korpus)
- **3 transporter**: stdio, SSE, Streamable HTTP
- **33 behörighetsomfattningar** för finkornig auktorisering

### Verktygsregistrering

Verktyg registreras som fristående filer i `open-sse/mcp-server/tools/`, där varje fil exporterar ett namn, schema, en hanterare och en behörighetsomfattning:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Hämta en ögonblicksbild av systemets hälsa",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transporter

```ts
// stdio (CLI-användning)
startMcpStdio(server);

// SSE (HTTP-baserad strömning)
startMcpSse(server, port);

// Streamable HTTP (modern MCP)
startMcpStreamable(server, port);
```

### Auktorisering

Varje verktygsanrop genomgår kontroller av behörighetsomfattning (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Otillräcklig behörighetsomfattning");
}
```

## Transformatorer

`open-sse/transformer/` konverterar mellan formaten **Chat Completions** och **Responses API**.

### Varför en separat transformator?

Responses API är OpenAI:s nya format med **tillståndsbevarande konversationer** (`previous_response_id`). När en klient skickar en Responses-begäran gör OmniRoute följande:

1. Konverterar Responses → Chat Completions internt
2. Skickar till leverantören (valfri leverantör som stöder Chat Completions)
3. Konverterar tillbaka svaret till Responses-format
4. Strömmar det konverterade svaret till klienten

Transformatorn (`transformer/responsesTransformer.ts`) tillhandahåller:

```ts
createResponsesApiTransformStream(): TransformStream
```

Detta hanterar:

- `response.output_item.added`-händelser
- `response.output_text.delta`-händelser
- `response.completed`-händelsen
- Mappning av verktygsanrop (`function_call` ↔ `tool_calls`)

## Konfiguration

`open-sse/config/` innehåller konfigurationslagret:

| Fil                           | Syfte                                                        |
| ----------------------------- | ------------------------------------------------------------ |
| `providerRegistry.ts`         | Register över chattmodeller i katalogen med 352 leverantörer |
| `providerModels.ts`           | Modellalias och formatmappning                               |
| `constants.ts`                | Tidsgränser, begränsningar och statuskoder                   |
| `defaultThinkingSignature.ts` | Claudes standardsignatur för resonemang                      |
| `modelStrip.ts` (i services)  | Leverantörsspecifik borttagning av fält                      |

### Schema för leverantörsregistret

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Zod-validering vid modulinläsning säkerställer att alla leverantörskonfigurationer är giltiga.

## Antimönster

❌ **Synkrona databasanrop i `combo.ts`** — förberäkna och cacha
❌ **Logik för nya försök i hanterare** — använd `retry()` från resiliensservicen
❌ **Direkt åtkomst till leverantörskonfiguration** — använd getters från `providerRegistry`
❌ **Hårdkodade reservkedjor** — definiera i `modelFamilyFallback.ts`
❌ **Tillståndsmutationer mellan samtidiga begäranden** — använd endast kontext avgränsad till begäran

## Lägga till en ny komponent

### Lägga till en ny tjänst

1. Skapa `open-sse/services/[serviceName].ts` med ett avgränsat ansvarsområde
2. Exportera huvudhanteringsfunktionen och eventuella konstanter
3. Lägg till enhetstester i `tests/unit/services/[serviceName].test.mjs`
4. Integrera i begärandepipelinen i `handlers/chatCore.ts` (om routningsrelaterad)
5. Uppdatera routningslogiken i `combo.ts` om tjänsten påverkar val av mål
6. Dokumentera i den här filen

### Lägga till en ny exekverare

1. Skapa `open-sse/executors/[provider].ts` som utökar `BaseExecutor`
2. Registrera i `config/providerRegistry.ts`
3. Lägg till i fabriken i `executors/index.ts`
4. Lägg till enhetstester för exekveraren
5. Dokumentera i `docs/architecture/ARCHITECTURE.md`

### Lägga till ett nytt MCP-verktyg

1. Skapa eller uppdatera `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definiera Zod-schema för indata
3. Registrera verktyget i `mcp-server/index.ts`
4. Lägg till i behörighetsmatrisen i `mcp-server/auth/`
5. Lägg till enhetstester
