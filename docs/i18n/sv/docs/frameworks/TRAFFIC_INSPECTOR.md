Traffic Inspector är OmniRoutes inbyggda felsökningsverktyg för HTTPS-trafik — ett verktyg liknande Charles Proxy / mitmweb / HTTP Toolkit som är **LLM-medvetet** och **agentmedvetet**. Det finns på `/dashboard/tools/traffic-inspector` och tar emot trafik i realtid från upp till 5 samtidiga insamlingskällor.

**Plats i instrumentpanelen:** `/dashboard/tools/traffic-inspector`
**Grupp i sidofältet:** Verktyg (efter AgentBridge)
**Se även:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge är insamlingsläge 1.

### Arkitektur i ett stycke

`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) är en delad ringbuffert i minnet (som standard 1000 poster, konfigurerbar via `INSPECTOR_BUFFER_SIZE`). Alla insamlingskällor skriver till den via `push()`. Bufferten klassificerar varje post med hjälp av `kindDetector.ts` (avgör om det är en LLM-begäran), beräknar en `contextKey` (ett SHA-256-fingeravtryck av systemprompten) och sänder till alla WebSocket-prenumeranter via `globalTrafficBuffer.subscribe()`. Instrumentpanelen ansluter via `GET /api/tools/traffic-inspector/ws` och tar emot en ögonblicksbild vid anslutning, följd av händelserna `new`/`update`/`clear`.

## §2 Insamlingslägen

Traffic Inspector stöder **5 samtidiga insamlingskällor**. Var och en kan aktiveras och inaktiveras oberoende av de andra. Fältet `source` i varje `InterceptedRequest` (`src/mitm/inspector/types.ts`) är ett av `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"` eller `"tproxy"`.

### Läge 1 — AgentBridge (standard, alltid aktivt)

**Källa:** AgentBridge-hanterare (`src/mitm/handlers/base.ts`)
**Mekanism:** Varje anrop till `intercept()` i `MitmHandlerBase` anropar `hookBufferStart()` före vidarebefordran och `hookBufferUpdate()` när det är klart. Ingen extra konfiguration krävs — det fungerar så snart AgentBridge körs.
**Räckvidd:** De 9 IDE-agenter som konfigurerats i AgentBridge
**Obs:** Fältet `source` i `InterceptedRequest` = `"agent-bridge"`

### Läge 2 — Anpassade värdar (DNS-omdirigering)

**Källa:** Användardefinierad värdlista (tabellen `inspector_custom_hosts`)
**Mekanism:** När en värd läggs till via användargränssnittet läggs `127.0.0.1 <host>` till i `/etc/hosts` (kräver sudo). Den befintliga MITM-servern i AgentBridge (port 443) genererar dynamiskt ett SNI-certifikat för den nya värden.
**Räckvidd:** Alla applikationer som använder den tillagda värden — ingen ändring av applikationskonfigurationen krävs
**Obs:** `source` = `"custom-host"`

Exempel på användningsfall:

- Övervaka `api.openai.com` från Python-skript
- Felsöka `my-internal-llm.company.com`
- Samla in trafik från mobila enheter i samma nätverk (via ARP-spoofing — avancerat)

### Läge 3 — HTTP_PROXY-lyssnare (port 8080)

**Källa:** Applikationer som använder miljövariablerna `HTTP_PROXY`/`HTTPS_PROXY`
**Mekanism:** En sekundär lyssnare på port 8080 (`src/mitm/inspector/httpProxyServer.ts`) som fungerar som en vanlig explicit HTTP/HTTPS-proxy. Accepterar `CONNECT`-tunnlar (HTTPS) och direkta HTTP-förfrågningar.
**Räckvidd:** Alla applikationer som respekterar miljövariabeln `HTTP_PROXY` — ingen DNS-ändring, ingen sudo
**Obs:** `source` = `"http-proxy"`

```bash
# Snabb insamling för ett enskilt kommando:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# Beständig insamling under en skalsession:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**TLS-begränsning:** HTTPS-`CONNECT`-tunnlar samlas som standard endast in som metadata (värd, port, tidsuppgifter) — TLS-innehållet dekrypteras inte. Aktivera reglaget ”Dekryptera HTTPS i proxyläge” (valfritt, kräver att AgentBridge-certifikatet är betrott) för fullständig granskning av innehållet.

**Portkonflikt:** Om port 8080 används returnerar AgentBridge 409 med ett strukturerat fel. Ändra porten via miljövariabeln `INSPECTOR_HTTP_PROXY_PORT`.

### Läge 4 — Systemomfattande proxy (avancerat, valfritt)

**Källa:** Proxyinställningar på operativsystemnivå (gäller alla applikationer på datorn)
**Mekanism:** Använder operativsystemets API:er för att omdirigera all HTTP/HTTPS-trafik genom HTTP_PROXY-lyssnaren:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **Räckvidd:** Alla applikationer på datorn som respekterar systemets proxyinställningar
  **Obs:** `source` = `"system-proxy"`

**Säkerhetsmekanismer:**

- Timer för automatisk inaktivering (standardvärde 30 min, kan konfigureras via `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES`)
- Systemets tidigare proxytillstånd sparas i databasen och återställs vid återställning
- Kontrollpanelen visar uppmaningen ”Återställer systemproxy” om användaren navigerar bort medan funktionen är aktiv
- Användargränssnittet visar märket `⚠ Avancerat` + en explicit kryssruta för bekräftelse

### Läge 5 — Transparent TPROXY-dekryptering (Linux, root, valfritt)

**Källa:** Kärnans TPROXY + policybaserad routning (`src/mitm/tproxy/`)
**Mekanism:** Märker nya lokala utgående TCP-anslutningar till en målport (standardvärde `443`) i `mangle OUTPUT`, en `ip rule` dirigerar om de märkta paketen till lokal leverans och målet `TPROXY` i `mangle PREROUTING` överlämnar dem till en transparent (**IP_TRANSPARENT**) lyssnare (standardport `8443`). Lyssnaren avslutar TLS med ett lövcertifikat som utfärdas **på begäran för varje SNI-värdnamn** av en dynamisk CA, samlar in det dekrypterade utbytet och vidarebefordrar förfrågan återkrypterad till den ursprungliga destinationen.
**Räckvidd:** **Godtyckliga** destinationsvärdar på målporten — ingen förfalskning av `/etc/hosts`, ingen `HTTP_PROXY`-miljövariabel och ingen systemomfattande proxyändring. Den avlyssnade processen behöver ingen konfigurationsändring, men måste lita på den dynamiska CA:n.
**Obs:** `source` = `"tproxy"`

**Krav:** Endast Linux (**IP_TRANSPARENT** finns endast i Linux), behörigheten **CAP_NET_ADMIN** (root) och ett systemspecifikt N-API-tillägg som måste byggas med en C-verktygskedja (`npm run build:native:tproxy`). När detta inte är tillgängligt är reglaget på kontrollpanelen inaktiverat med verktygstipset ”TPROXY-dekryptering kräver Linux + root + det systemspecifika tillägget”. Brandväggsreglerna tillämpas och återställs transaktionellt (en krasch lämnar aldrig kvar en `mangle`-regel) och rensas vid omstart. En SO_MARK-baserad skyddsmekanism mot loopar förhindrar att proxyns egen återkrypterade vidarebefordran fångas upp igen.

Detta är ett omfattande delsystem med en egen operatörsguide — se `docs/security/MITM-TPROXY-DECRYPT.md` (git; kompileras inte till `/docs`) för det fullständiga brandväggsreceptet, den dynamiska CA:n per SNI + installationsprogrammet för betrodda certifikat, den lokala routen, information om skyddet mot loopar och konfigurationsschemat. Reglaget styrs av `GET / POST / DELETE /api/tools/agent-bridge/tproxy` (obs: routen finns under AgentBridge-prefixet, inte Traffic Inspector-prefixet).

## §4 LLM-medvetna funktioner

### 4.1 Typdetektor (`src/mitm/inspector/kindDetector.ts`)

Klassificerar varje begäran som `"llm"`, `"app"` eller `"unknown"` med hjälp av fyra signaler:

1. **Värdregister** — cirka 18 kända värdnamn för LLM-API:er (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot osv.)
2. **Sökvägsmönster** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses` osv.
3. **Brödtextstruktur** — identifierar fälten `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input`
4. **User-agent-indikationer** — `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor` i UA-strängen

Anpassade värdar som läggs till via läge 2 ärver sitt `kind` från formulärinmatningen (standardvärdet är `"custom"`).

### 4.2 SSE-sammanslagning (`src/mitm/inspector/sseMerger.ts`)

**Oberoende clean-room-implementation.** Händelsetolkningen följer
[WHATWG-algoritmen för server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream),
medan rekonstruktionen följer de offentliga strömningsschemana för [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) och
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent).

Rekonstruerar det slutliga assistentmeddelandet från råa SSE-deltahändelser:

- **Anthropic**: ackumulerar `content_block_delta` efter index; hanterar `text_delta`, `input_json_delta` (verktygsanrop), `thinking_delta`
- **OpenAI**: ackumulerar Chat Completions-val/verktygsanrop och Responses API-utdataobjekt
  efter index
- **Gemini**: ackumulerar `candidates[i].content.parts`
- **Okänd**: returnerar råa händelser oförändrade

Fliken Svar visar en växlingsknapp: **"Råa händelser ↔ Sammanslaget"**.

### 4.3 Konversationsnormaliserare (`src/mitm/inspector/conversationNormalizer.ts`)

**Oberoende clean-room-implementation.** Normaliseringen definieras av lokala black-box-kontrakt
och de offentliga meddelandeschemana för OpenAI, Anthropic och Gemini; ingen
implementationskälla från uppströmsprojekt används.

Konverterar meddelandeformaten för OpenAI, Anthropic och Gemini till en gemensam `NormalizedConversation` före rendering:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // meddelanden/innehåll/prompt från begärans brödtext
  response: NormalizedTurn[]; // assistentsvar (sammanslaget via sseMerger)
  contextKey: string | null; // SHA-256-fingeravtryck för systemprompten
}
```

Blocktyper: `text`, `tool_use`, `tool_result`. Fliken Konversation använder den här strukturen oavsett leverantör.

### 4.4 Färgsättning av kontextnyckel (`src/mitm/inspector/contextKey.ts`)

- Beräknar `SHA-256` för systemprompten (det första meddelandet med `role:system`, eller fältet `system`, eller Geminis `systemInstruction`)
- Returnerar ett hexadecimalt prefix med 12 tecken (`"a3f9c2..."`)
- Klientdelen mappar nyckeln till en deterministisk HSL-färg för vänsterkantens färgstapel
- **Filtret "samma kontext"**: när du klickar på etiketten `ctx #a3f` läggs ett filter till som endast visar begäranden med samma fingeravtryck

Det gör det enkelt att visuellt särskilja olika "personligheter" eller uppgifter som körs i samma agentsession.

### 4.5 Extrahering av LLM-metadata

För LLM-begäranden extraherar fliken LLM-detaljer:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // från begärans brödtext eller svar
  messages: number; // antal turer
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // true om SSE-svar
  mappedTo: string | null; // x-omniroute-mapped-header
  costEstimateUsd: number | null; // uppskattad kostnad baserat på OmniRoute-prissättning
}
```

### 4.6 Livefilter för pågående begäranden

Begärans `status`-fält är `number | "in-flight" | "error"` — en post
läggs till som `"in-flight"` i samma ögonblick som begäran startar och **uppdateras på plats**
när svaret (eller felet) anländer. Verktygsfältets växlingsknapp **"Live"**
(`liveOnly`, i18n-nyckeln `trafficInspector.liveOnly`) begränsar listan till poster
vars `status === "in-flight"`, så att du kan övervaka öppna anslutningar i realtid.

Filtret är ett rent predikat på klientsidan i
`src/lib/inspector/matchesTrafficFilter.ts`:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

Växlingsknappens tillstånd finns i `useTrafficFilters` (inspektörspanelens hooks) och
kombineras med de andra filtren (profil, värd, agent, källa, status, kontext).

### 4.7 Processattribution (Linux)

På Linux kan varje avlyssnad begäran attribueras till den **ursprungliga lokala
processen**. Två valfria fält läggs till i `InterceptedRequest`:

```ts
pid?: number;          // ursprungligt process-ID (endast Linux)
processName?: string;  // ursprungligt processnamn (endast Linux)
```

`src/mitm/inspector/processAttribution.ts` mappar anslutningens efemära
_klientport_ till PID + namn genom att:

1. Läsa `/proc/net/tcp` och `/proc/net/tcp6` för att hitta socket-inoden för
   porten (`parseProcNetTcpForInode`, en ren parser som kan testas med fixturer).
2. Söka igenom `/proc/<pid>/fd/` efter en symbolisk länk till `socket:[<inode>]`.
3. Läsa processnamnet från `/proc/<pid>/comm`.

En TTL-cache på 1 sekund begränsar kostnaden för procfs-genomsökningar under belastning. Attributionen sker
enligt **bästa förmåga** — varje fel returnerar `null` och blockerar aldrig insamlingen. På
macOS/Windows returnerar funktionen `null` (stub; stöd för `lsof`/`GetExtendedTcpTable`
är en framtida förbättring).

## §6 Säkerhet

Trafikinspektören visar **all avlyssnad HTTPS-trafik**, inklusive auktoriseringshuvuden och förfrågningskroppar. Följande kontroller finns på plats:

| Kontroll                                 | Detaljer                                                                                                                                                                               |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LOCAL_ONLY**                           | Alla rutter och WebSocket-slutpunkten är endast tillgängliga via loopback (framtvingas i `routeGuard.ts` före autentisering)                                                           |
| **Maskering av hemligheter**             | Den linjära `maskSecret()`-skannern maskerar Bearer-autentiseringsuppgifter enligt RFC 6750, leverantörsprefixerade nycklar och långa ogenomskinliga token före `TrafficBuffer.push()` |
| **Storleksgräns för kroppar**            | Kroppar > `INSPECTOR_MAX_BODY_KB` (standardvärde 1024 KB) trunkeras med meddelandet `"(trunkerat av prestandaskäl)"`                                                                   |
| **Sanering av huvuden**                  | Namn konverteras till gemener; ramnings-, hop-by-hop- och proxyautentiseringshuvuden tas bort; cookies maskeras helt; autentiseringsvärden delegeras till `maskSecret()`               |
| **CSP**                                  | Strikt Content Security Policy på Trafikinspektörens sidor för att förhindra XSS via injicerade svarskroppar                                                                           |
| **Ingen beständig lagring som standard** | `TrafficBuffer` lagras i minnet och går förlorad när servern startas om. Sessioner lagras beständigt endast när de uttryckligen spelas in                                              |

### Tillämpade hårda regler

| Regel                             | Tillämpning                                                                          |
| --------------------------------- | ------------------------------------------------------------------------------------ |
| **#12** `sanitizeErrorMessage`    | Alla HTTP-felsvar från Trafikinspektörens rutter saneras                             |
| **#15 + #17** `isLocalOnlyPath()` | `/api/tools/traffic-inspector/` är LOCAL_ONLY + SPAWN_CAPABLE (systemproxykommandon) |

### Kända begränsningar

- **Systemomfattande proxyläge** påverkar alla program på datorn, inklusive VPN-klienter och SSO. Använd alltid läget med timern för automatisk inaktivering. Använd det inte på delade datorer.
- **CONNECT-tunnel för HTTPS**: Läge 3 (HTTP_PROXY) registrerar endast tunnelmetadata för HTTPS-destinationer, såvida inte TLS-avlyssning är aktiverad. Detta är avsiktligt — transparent registrering utan att AgentBridge-certifikatet är betrott skulle bryta TLS-verifieringen för dessa appar.
- **Hårdkodade strängar i vissa komponenter**: Vissa användargränssnittskomponenter (F7/F8) har ett mindre antal hårdkodade strängar som ännu inte omfattas av i18n-nycklar. Dessa dokumenteras som en känd begränsning i rapporten över i18n-luckor; de kommer att migreras i en uppföljande omgång. De berörda strängarna är dekorativa etiketter i användargränssnittet som inte behöver översättas för funktionell användning.

## §7 Felsökning

### WebSocket-frånkoppling

Om liveflödet visar "Frånkopplad":

1. Kontrollera att servern fortfarande körs: `GET /api/tools/traffic-inspector/capture-modes`
2. Läs in sidan igen — WebSocket ansluter på nytt och tar emot en ny ögonblicksbild
3. Om servern startades om har minnesbufferten rensats — gamla poster är borta om inte en session spelades in

### Portkonflikt på 8080

Om HTTP_PROXY-läget inte kan startas:

```bash
lsof -i :8080    # hitta processen
```

Ändra porten:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### Systemproxyn återställdes inte

Om OmniRoute kraschar medan det systemomfattande proxyläget är aktivt:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

Instrumentpanelen erbjuder även "Återställ systemproxy" nästa gång den läses in om den upptäcker att databasens tillstånd indikerar att proxyn var aktiv.

### Full buffert

När bufferten når `INSPECTOR_BUFFER_SIZE` (standardvärde 1000) ersätter nya poster de äldsta. Om viktiga förfrågningar går förlorade:

- Öka `INSPECTOR_BUFFER_SIZE` (t.ex. 5000) — detta byter minne mot längre lagringstid
- Spela in en session för att spara det relevanta tidsintervallet i databasen
