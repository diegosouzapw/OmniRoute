Använd den här guiden för att välja den minsta tillförlitliga utvecklingsloopen för en pull request. Den
ersätter inte de områdesspecifika arkitektur- och säkerhetsdokument som länkas nedan; den kopplar varje vanlig
ändringstyp till dess kontrakt, fokuserade kontroller och CI-täckning.

## Vägen som varje ändring följer

1. **Välj basen innan du börjar redigera.** Hitta den högsta aktiva `release/v*`-grenen och skapa en gren från
   dess senaste commit. Rikta ändringen mot den grenen, inte `main`. Om en releasefrysning pågår ska du inte rikta ändringen mot den frysta
   grenen; använd nästa aktiva cykel som beskrivs i
   [Modell för grenar och releaser](BRANCHING_MODEL.md).
2. **Namnge kontrakten.** Identifiera varje katalog, schema, genererad artefakt, offentligt API eller
   användargränssnitt som ändringen påverkar. Tabellen nedan anger den minsta uppsättningen att utgå från.
3. **Skriv eller uppdatera fokuserade tester.** Produktionsändringar i `src/`, `open-sse/`, `electron/` eller
   `bin/` kräver ett automatiserat test i samma PR. Kör de minsta testfilerna som verifierar
   beteendet och därefter de angivna fokuserade kontrollerna.
4. **Låt CI köra den breda matrisen.** De fullständiga enhetstestdelarna, Vitest, tröskeln för kodtäckning och
   produktionsbygget körs för PR:en. Kör endast en bred testsvit lokalt när ett fokuserat fel tyder på
   större påverkan eller när ändringen omfattar flera delsystem.
5. **Stäm av före granskning.** Hämta den aktiva basen, granska dess nya commits och din diff mot
   den och utför sedan rebase eller merge av basen enligt arbetsflödet för bidragsgivare. Lös konflikter i genererade filer
   och kataloger utifrån deras källa, generera om dem, kör den fokuserade loopen igen och bekräfta att
   PR:en fortfarande riktas mot den aktiva releasegrenen.
6. **Dokumentera underlag.** Ange i PR-mallen vilka kommandon som körts, varje testfil som lagts till eller ändrats,
   migreringar eller funktionsflaggor samt all validering som endast kan göras i CI och fortfarande väntar.

## Rekommenderade flöden per ändringstyp

Kommandona nedan är de minsta fokuserade kontrollerna, inte ett tillstånd att hoppa över ett test som direkt täcker
beteendet du ändrade.

### Leverantör

**Kontrakt**

- Leverantörsdefinitionen i `src/shared/constants/providers/` och dess sammansättning i
  `src/shared/constants/providers.ts`.
- Modeller och funktioner i `open-sse/config/providerRegistry.ts` eller dess extraherade registerfiler.
- Val av exekverare/översättare, konfiguration av OAuth eller API-nycklar, resurser för kontrollpanelen och genererad
  leverantörsreferens när det är tillämpligt.
- Offentliga autentiseringsuppgifter måste använda `resolvePublicCred()`; felsvar måste använda de delade sanerade
  felhjälparna. Se `docs/security/PUBLIC_CREDS.md` (git; kompileras inte till `/docs`) och
  [Felsanering](../security/ERROR_SANITIZATION.md).

**Fokuserad loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # när katalogen ändras; checka in den genererade diffen
npm run lint
```

Testa även varje påverkad typ av begäran: chatt, Responses, bilder, inbäddningar, ljud eller video.
Granska genererade katalog- och referensdiffar som kontraktsändringar; godkänn dem inte blint.

### Routning

**Kontrakt**

- Offentliga strategivärden och UI-metadata i `src/shared/constants/routingStrategies.ts`.
- Distribution och ordning under `open-sse/services/combo.ts` och `open-sse/services/combo/`.
- Combo-scheman, persistens, resilienstillstånd, modellfunktioner och API/UI-kontroller.
- [Auto-Combo-motor](../routing/AUTO-COMBO.md) och dokumentation om resiliens när beteendet ändras.

**Fokuserad loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ändringar av strategi eller distribution
npm run check:known-symbols      # ändringar av strategiregistrering
npm run lint
```

Använd deterministiska tester med simulerade uppströmstjänster lokalt. Aktiva combo-röktester kräver autentiseringsuppgifter och är
manuella, inte ersättningar för CI.

### UI / UX

**Kontrakt**

- Next.js-rutter/-sidor och gränser för delade komponenter under `src/app/` och
  `src/shared/components/`.
- Former för API-svar, tillstånd för inläsning/tomt/fel, tangentbords- och skärmläsarbeteende,
  responsiv layout, teman och utökning av språkversioner.
- Engelska UI-källsträngar i `src/i18n/messages/en.json`; hårdkoda inte ny användartext.

**Fokuserad loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Kör appen för interaktions- eller visuella ändringar och kontrollera både smala och breda visningsytor. CI kör
produktionsbygget och bredare testsviter; visuellt beteende behöver fortfarande en fokuserad komponent, Playwright
eller en dokumenterad manuell kontroll som är lämplig för ändringen.

### i18n

**Kontrakt**

- `src/i18n/messages/en.json` är UI-källan; `config/i18n.json` är källan för språkversioner.
- CLI-kataloger finns separat under `bin/cli/locales/`.
- Bevara ICU-platshållare och taggar exakt. Översätt inte produkt-/leverantörs-/modellnamn,
  protokoll- och rubriknamn, kommandon, kod-/JSON-identifierare, URL:er, miljövariabler eller
  skyddade termer som `OmniRoute`, `OAuth`, `MCP` och `A2A`. Den aktuella källistan finns i
  `scripts/i18n/glossary/protected-terms.json`.

**Fokuserad loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # när CLI-strängar/-kataloger ändras
npm run lint
```

Detta är vägledning för det befintliga systemet, inte en uppmaning att utöka dess verktyg eller nyckelmodell.
Håll i18n-patchar strikt avgränsade medan ersättningssystemet utformas. Kör inte översättningskommandon
som anropar externa tjänster om inte uppgiften uttryckligen kräver genererade översättningar och
du har granskat den resulterande diffen.

### CLI

**Kontrakt**

- Publika kommandon och flaggor i `bin/cli/`, genererade API-kommandon, slutkoder, stdout/stderr och
  strukturer för JSON-utdata, konfigurations-/miljöbeteende samt paketerade filer.
- Användarvänliga CLI-strängar måste använda CLI:ns i18n-lager och hålla katalogerna `en`/`pt-BR` synkroniserade.
- Bevara Node som den runtime som stöds och kontraktet för den publicerade binärfilen.

**Fokuserad loop**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # genererade/paketerade CLI-ändringar
npm run check:pack-policy     # ändringar av paketets exponerade yta
npm run lint
```

Använd det exakta kommandot i en tillfällig datakatalog när beteendet beror på parsning, filer eller
slutstatus. CI utför de bredare kontrollerna av paketartefakter och ekosystemet.

### Databas

**Kontrakt**

- Domänmoduler under `src/lib/db/`; importera specifika moduler direkt (det gamla återexporteringslagret `localDb.ts` har tagits bort).
- Numrerade, idempotenta SQL-migreringar under `src/lib/db/migrations/`, transaktionssäkerhet, uppgraderingsbeteende,
  index och varje anropare som påverkas av schemat.
- Rutter och hanterare kör aldrig rå SQL direkt.

**Fokuserad loop**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Testa både en ny databas och uppgradering från det föregående schemat när du lägger till en migrering. Databastester
måste stänga handtag och anropa `resetDbInstance()` under rensningen. Kör `npm run test:bun:db` endast när
sökvägen för Bun-adaptern enligt bästa förmåga ändras; Node förblir normgivande.

### Bygge/distribution

**Kontrakt**

- Rot- och workspace-manifest/låsfil, `scripts/build/`, fristående Next.js-sammansättning, paketinnehåll i `dist/`,
  Electron-plattformsmetadata, CI-arbetsflöden och distributionsmarkörer.
- Node-intervallen som stöds och den tillåtelselistebaserade användningen av Bun i `CLAUDE.md` måste förbli intakta.
- Byggartefakter förblir ospårade; policyer för beroenden, licenser, arbetsflöden och paket gäller.

**Fokuserad loop**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # ändringar av beroenden eller låsfil
npm run check:pack-policy      # ändringar av det publicerade paketets exponerade yta
npm run lint
```

Använd `npm run build` lokalt endast när ändringen påverkar kompilering, fristående sammansättning, resurser
eller runtime-paketering. Använd `npm run build:release` endast för validering av releaser/distributioner. CI:s bygge är
den slutliga plattformsöverskridande signalen; plattformsspecifika Electron-ändringar kräver motsvarande fokuserade bygge
eller belägg från ett röktest.

## Lokal loop kontra CI

| Kör lokalt för varje ändring                                                                 | CI ger den breda signalen                                                            |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Direkta beteendetester och kategorikontroller ovan                                           | Uppdelad fullständig enhetstestsvit och seriella tester                              |
| `npm run lint`                                                                               | Vitest-sviter och stegvisa trösklar för täckning/kvalitet                            |
| Typkontroll eller bygge endast när det berörda kontraktet kräver det                         | Produktionsbygge samt kontroller av säkerhet, dokumentation, beroenden och PR-policy |
| Manuella interaktions-/livekontroller endast när automatisering inte kan verifiera beteendet | Integrations- och plattformskontroller mellan jobb, konfigurerade av arbetsflödet    |

En godkänd fokuserad loop är belägg för det ändrade kontraktet, inte ett bevis på att orelaterade CI-kontroller
kommer att godkännas. Omvänt ska inte varje lokal ändring behöva vänta på hela projektets testmatris.

## Checklista för avstämning

Innan du begär granskning:

- Bekräfta att PR:ens bas fortfarande är den högsta aktiva `release/v*`-grenen.
- Hämta basen och granska de commits som har lagts till sedan du skapade din gren.
- Granska `git diff <active-base>...HEAD` för oavsiktliga eller genererade ändringar.
- Lös konflikter i kataloger och genererade dokument genom att uppdatera källan och generera utdata på nytt.
- Kör om varje fokuserat test/kontroll som anges i PR-beskrivningen efter avstämningen.
- Försvaga aldrig verifieringar och ta inte bort obligatoriska tester enbart för att anpassa dig till en flyttad bas.

För regler om releasefrysning och omriktning, använd
[Förgrenings- och releasemodell](BRANCHING_MODEL.md). För den fullständiga CI-förteckningen, använd
[Referens för kvalitetskontroller](../architecture/QUALITY_GATES.md).
