Använd den här guiden för att välja den minsta tillförlitliga utvecklingsloopen för en pull request. Den
ersätter inte de områdesspecifika arkitektur- och säkerhetsdokument som länkas nedan, utan kopplar varje vanlig
ändringstyp till dess kontrakt, fokuserade kontroller och CI-täckning.

## Vägen som varje ändring följer

1. **Välj basen innan du börjar redigera.** Hitta den högsta aktiva `release/v*`-grenen och skapa en gren från
   dess senaste commit. Ange den grenen som mål, inte `main`. Om en releasefrysning pågår ska du inte ange den frysta
   grenen som mål; använd nästa aktiva cykel som beskrivs i
   [Modell för förgrening och releaser](BRANCHING_MODEL.md).
2. **Ange kontrakten.** Identifiera varje katalog, schema, genererad artefakt, publikt API eller
   användargränssnitt som ändringen påverkar. Tabellen nedan anger den minsta uppsättningen att utgå från.
3. **Skriv eller uppdatera fokuserade tester.** Produktionsändringar i `src/`, `open-sse/`, `electron/` eller
   `bin/` kräver ett automatiserat test i samma PR. Kör de minsta testfilerna som verifierar
   beteendet och därefter de angivna fokuserade kontrollerna.
4. **Låt CI köra den breda matrisen.** De fullständiga enhetstestsegmenten, Vitest, täckningströskeln och
   produktionsbygget körs för PR:en. Kör en bred testsvit lokalt endast när ett fokuserat fel pekar på
   en större påverkan eller när ändringen omfattar flera delsystem.
5. **Synkronisera före granskning.** Hämta den aktiva basen, granska dess nya commits och din diff mot
   den och utför sedan rebase eller merge av basen enligt arbetsflödet för bidragsgivare. Lös konflikter i genererade filer
   och kataloger från deras källa, generera om dem, kör den fokuserade loopen på nytt och bekräfta att
   PR:en fortfarande har den aktiva releasegrenen som mål.
6. **Dokumentera belägg.** Ange i PR-mallen vilka kommandon som körts, alla testfiler som lagts till eller ändrats,
   migreringar eller funktionsflaggor samt eventuell validering som endast sker i CI och fortfarande väntar.

## Standardflöden efter ändringstyp

Kommandona nedan är de minsta fokuserade kontrollerna, inte ett godkännande att hoppa över ett test som direkt täcker
beteendet du ändrade.

### Leverantör

**Kontrakt**

- Leverantörsdefinitionen i `src/shared/constants/providers/` och dess sammansättning i
  `src/shared/constants/providers.ts`.
- Modeller och funktioner i `open-sse/config/providerRegistry.ts` eller dess extraherade registerfiler.
- Val av exekverare/översättare, OAuth- eller API-nyckelkonfiguration, resurser för kontrollpanelen och den genererade
  leverantörsreferensen när det är tillämpligt.
- Publika autentiseringsuppgifter måste använda `resolvePublicCred()`; felsvar måste använda de delade sanerade
  felhjälparna. Se `docs/security/PUBLIC_CREDS.md` (git; kompileras inte till `/docs`) och
  [Felsanering](../security/ERROR_SANITIZATION.md).

**Fokuserad loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # när katalogen ändras; committa den genererade diffen
npm run lint
```

Testa även varje berörd typ av begäran: chatt, Responses, bilder, inbäddningar, ljud eller video.
Granska genererade katalog- och golden-diffar som kontraktsändringar; godkänn dem inte utan granskning.

### Routning

**Kontrakt**

- Publika strategivärden och metadata för användargränssnittet i `src/shared/constants/routingStrategies.ts`.
- Dispatch och ordning under `open-sse/services/combo.ts` och `open-sse/services/combo/`.
- Combo-scheman, beständighet, resiliensstatus, modellfunktioner samt API-/UI-kontroller.
- [Auto-Combo-motorn](../routing/AUTO-COMBO.md) och dokumentationen om resiliens när beteendet ändras.

**Fokuserad loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ändringar av strategi eller dispatch
npm run check:known-symbols      # ändringar av strategiregistrering
npm run lint
```

Använd deterministiska tester med mockade uppströmstjänster lokalt. Live-smoketester för combo kräver autentiseringsuppgifter och är
manuella, inte ersättningar för CI.

### UI / UX

**Kontrakt**

- Gränser för Next.js-rutter/-sidor och delade komponenter under `src/app/` och
  `src/shared/components/`.
- API-svarsformat, tillstånd för laddning/tomt/fel, beteende för tangentbord och skärmläsare,
  responsiv layout, teman och utökning av språkversioner.
- Engelska UI-källsträngar i `src/i18n/messages/en.json`; hårdkoda inte ny användarvänlig text.

**Fokuserad loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Kör appen vid interaktions- eller visuella ändringar och kontrollera både smala och breda visningsytor. CI kör
produktionsbygget och bredare testsviter; visuellt beteende behöver fortfarande en fokuserad komponentkontroll, Playwright-kontroll
eller dokumenterad manuell kontroll som är lämplig för ändringen.

### i18n

**Kontrakt**

- `src/i18n/messages/en.json` är UI-källan; `config/i18n.json` är källan för språkversioner.
- CLI-kataloger finns separat under `bin/cli/locales/`.
- Bevara ICU-platshållare och taggar exakt. Översätt inte produkt-/leverantörs-/modellnamn,
  protokoll- och rubriknamn, kommandon, kod-/JSON-identifierare, URL:er, miljövariabler eller
  skyddade termer som `OmniRoute`, `OAuth`, `MCP` och `A2A`. Den aktuella källistan är
  `scripts/i18n/glossary/protected-terms.json`.

**Fokuserad loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # när CLI-strängar/-kataloger ändras
npm run lint
```

Detta är vägledning för det befintliga systemet, inte en uppmaning att utöka dess verktyg eller nyckelmodell.
Håll i18n-patchar kirurgiskt avgränsade medan ersättningssystemet utformas. Kör inte översättningskommandon
som anropar externa tjänster om inte uppgiften uttryckligen kräver genererade översättningar och
du har granskat den resulterande diffen.

### CLI

**Kontrakt**

- Publika kommandon och flaggor i `bin/cli/`, genererade API-kommandon, slutkoder, stdout/stderr och
  strukturer för JSON-utdata, konfigurations-/miljöbeteende samt paketerade filer.
- Användarorienterade CLI-strängar måste använda CLI:ns i18n-lager och hålla katalogerna `en`/`pt-BR` synkroniserade.
- Bevara Node som den stödda exekveringsmiljön och kontraktet för den publicerade binärfilen.

**Fokuserad loop**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # ändringar i genererad/paketerad CLI
npm run check:pack-policy     # ändringar av paketets publika yta
npm run lint
```

Använd det exakta kommandot i en tillfällig datakatalog när beteendet beror på parsning, filer eller
slutstatus. CI utför de bredare kontrollerna av paketartefakter och ekosystemet.

### Databas

**Kontrakt**

- Domänmoduler under `src/lib/db/`; importera specifika moduler direkt (det gamla återexportlagret `localDb.ts` har tagits bort).
- Numrerade, idempotenta SQL-migreringar under `src/lib/db/migrations/`, transaktionssäkerhet, uppgraderingsbeteende,
  index och alla anropare som påverkas av schemat.
- Rutter och hanterare kör aldrig rå SQL direkt.

**Fokuserad loop**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Testa både en ny databas och uppgradering från föregående schema när du lägger till en migrering. Databastester
måste stänga resurser och anropa `resetDbInstance()` under upprensningen. Kör `npm run test:bun:db` endast när
sökvägen för Bun-adaptern, som stöds efter bästa förmåga, ändras; Node förblir normgivande.

### Bygge/distribution

**Kontrakt**

- Rot- och arbetsytemanifest/låsfil, `scripts/build/`, fristående Next.js-sammansättning, paketinnehåll i `dist/`,
  Electron-plattformsmetadata, CI-arbetsflöden och distributionsmarkörer.
- De Node-intervall som stöds och den tillåtelselista för användning av Bun som finns i `CLAUDE.md` måste förbli intakta.
- Byggartefakter förblir ospårade; policyer för beroenden, licenser, arbetsflöden och paket gäller.

**Fokuserad loop**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # ändringar av beroenden eller låsfil
npm run check:pack-policy      # ändringar av det publicerade paketets yta
npm run lint
```

Använd `npm run build` lokalt endast när ändringen påverkar kompilering, fristående sammansättning, resurser
eller paketering för exekveringsmiljön. Använd `npm run build:release` endast för verifiering av utgåva/distribution. CI:s bygge är
den slutliga plattformsöverskridande signalen; plattformsspecifika Electron-ändringar behöver motsvarande fokuserade bygge
eller belägg från ett röktest.

## Lokal kandidatloop

Källkodstester kan inte bevisa att den paketerade artefakten går att starta: paketeringslistor, borttagna beroenden
och plattformsspecifika binärfiler orsakar fel först när tar-arkivet har installerats och startats. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) är den lokala delen av flödet bygg en gång/validera/lansera från
RFC #8084: det bygger en kandidat, validerar exakt den artefakten, lanserar den genom namnbyten av
kataloger och återställer den när den lanserade platsen inte klarar sin hälsokontroll.

```bash
npm run dev:candidate -- run --dry-run --json  # skriv ut planen utan att ändra något
npm run dev:candidate -- run                   # bygg + validera + lansera, automatisk återställning
npm run dev:candidate -- build                 # npm pack + installera i _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # starta på en ledig port, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # växla current och previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # återanvänd ett tar-arkiv byggt någon annanstans (CI)
```

- **Bygg en gång.** `build` paketerar det aktuella trädet (det kräver `dist/server.js`, så kör
  `npm run build:release` först) eller kopierar `--from-tarball` och installerar sedan tar-arkivet i ett
  isolerat npm-prefix, eftersom tar-arkivet inte innehåller någon `node_modules`. ID:t är den korta `HEAD`-sha:n
  (`-dirty` när trädet har lokala ändringar) eller `tgz-<sha256>` för ett tar-arkiv. Ett rent ID som
  redan har byggts återanvänds i stället för att byggas om; ange `--force` för att bygga om det.
- **Validera paketet, inte källkoden.** `validate` startar det installerade CLI-verktyget
  (`serve --port <free port>`) med en ny `DATA_DIR=<candidate>/data`, falska hemligheter och operatörens
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` och `INITIAL_PASSWORD` borttagna från miljön,
  så att den nyinstallerade instansens nyckellösa loopback-konfiguration kontrolleras. Det väntar på att
  `GET /api/health` ska returnera 200, kräver att `GET /v1/models` returnerar 200, stoppar processgruppen
  och registrerar resultatet i `validation.json` tillsammans med tar-arkivets hash.
- **Lansera samma artefakt.** `promote` avvisar en kandidat som saknar en godkänd validering för dess
  aktuella tar-arkivshash. Den aktiva standardplatsen är `_artifacts/candidate/current`; `--target <dir>`
  väljer en annan katalog på samma filsystem, och dess föregående plats är `<dir>.previous`.
  Varje namnbyte är atomärt, och ett fel halvvägs återställer de namnbyten som redan har genomförts.
- **Återställ.** `run` validerar den lanserade platsen igen och växlar tillbaka `current` och `previous` när
  den kontrollen misslyckas. En kandidat som inte klarar den första valideringen lanseras aldrig.

Allt skrivs under den git-ignorerade `_artifacts/candidate/`; en befintlig OmniRoute-installation
och dess datakatalog påverkas aldrig. Det lanserade CLI-verktyget är
`_artifacts/candidate/current/prefix/bin/omniroute`; starta det med din egen `DATA_DIR` när du använder
det. Slutkoder: `0` lyckades, `1` misslyckad validering eller lansering, `2` användningsfel eller saknat bygge.

## Lokal loop kontra CI

| Kör lokalt för varje patch                                                                | CI ger den breda signalen                                                            |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Direkta beteendetester och kategorigrindar ovan                                           | Shardad fullständig enhetstestsvit och seriella tester                               |
| `npm run lint`                                                                            | Vitest-sviter och spärrhakar för täckning/kvalitet                                   |
| Typkontroll eller bygge endast när det berörda kontraktet kräver det                      | Produktionsbygge, säkerhets-, dokumentations-, beroende- och PR-policygrindar        |
| Manuell interaktion/livekontroller endast när automatisering inte kan verifiera beteendet | Integrations- och plattformskontroller mellan jobb som konfigurerats av arbetsflödet |

En grön fokuserad loop är belägg för det ändrade kontraktet, inte ett bevis på att orelaterade CI-kontroller
kommer att lyckas. Omvänt ska du inte låta varje lokal ändring vänta på hela arkivets matris.

## Checklista för avstämning

Innan du begär granskning:

- Bekräfta att PR:ens bas fortfarande är den högsta aktiva `release/v*`-grenen.
- Hämta den basen och granska de incheckningar som har lagts till sedan du skapade din gren.
- Granska `git diff <active-base>...HEAD` för oavsiktliga eller genererade ändringar.
- Lös konflikter i kataloger och genererade dokument genom att uppdatera källan och generera om utdata.
- Kör om varje fokuserat test/spärr som anges i PR-beskrivningen efter avstämningen.
- Försvaga aldrig kontroller eller ta bort obligatoriska tester enbart för att anpassa dig till en flyttad bas.

För regler om releasefrysning och omriktning, se
[Gren- och releasemodell](BRANCHING_MODEL.md). För den fullständiga CI-förteckningen, se
[Referens för kvalitetsgrindar](../architecture/QUALITY_GATES.md).
