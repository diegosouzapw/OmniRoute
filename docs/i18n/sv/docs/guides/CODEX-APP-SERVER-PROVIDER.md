OmniRoute erbjuder **två** sätt att använda OpenAI Codex:

| Leverantör             | Så kommunicerar den med OpenAI                                                                                                                                                         | Användningsförbehåll                                                                   |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **`codex`**            | Återanvänder din OAuth-token för ChatGPT/OpenAI direkt mot Responses API                                                                                                               | **Ja** — den officiella sessionen är inte auktoriserad för användning via proxy/router |
| **`codex-app-server`** | Styr **Codex CLI:s egen `codex app-server`** via JSON-RPC/WebSocket; CLI:t hanterar och förnyar automatiskt sin OAuth (`~/.codex/auth.json`), precis som en interaktiv `codex`-session | **Nej** — OmniRoute återanvänder aldrig en token mot API:t                             |

Eftersom `codex-app-server` aldrig återanvänder en token omfattas den inte av
användningsförbehållet för återanvändning av sessioner. Den kräver dock ett
**Codex CLI som kan nås via den konfigurerade app-server-URL:en**, och detta CLI
måste vara **inloggat**.

---

## 1. Arkitektur

```
┌─ OmniRoute-app ────────────────┐        ┌─ codex-app-server-sidovagn ─────────┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                   │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456         │
│  (+ behörighetstoken)            │  JSON  │  --ws-auth capability-token         │
│                                  │  RPC   │  hanterar själv OpenAI OAuth        │
└──────────────────────────────────┘        │  (~/.codex/auth.json, auto-refresh) │
        │ delar (compose-volymer)            └─────────────────────────────────────┘
        ▼
  codex-appserver-token   → WS-behörighetstoken (båda monterar den)
  codex-appserver-home    → ~/.codex (auth.json skrivs av instrumentpanelen,
                             läses av sidovagnens codex app-server)
```

- Sidovagnen lyssnar **endast** på det interna compose-nätverket
  (`ws://codex-app-server:1456`) bakom en behörighetstoken. Den publiceras
  **aldrig** till värden eller internet.
- Codex CLI är inbyggt i `omniroute:base`, så ingen installation av codex behövs
  på värden eller användarens dator när du kör sidovagnen.

## 2. Starta den

```bash
# Starta stacken MED sidovagnsprofilen för codex app-server:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

Sidovagnen skapar sin WS-behörighetstoken vid den första starten (i den delade
volymen `codex-appserver-token`), och appen läser samma token via
`OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`. Ingen manuell tokenkonfiguration
behövs.

## 3. Anslut + logga in

1. Lägg till en anslutning för **OpenAI Codex (App-Server)** på
   instrumentpanelen. Ingen API-nyckel eller token krävs (det är en leverantör
   utan autentisering — sidovagnen hanterar autentiseringen).
2. Om sidovagnens Codex CLI **ännu inte är inloggat** rapporterar
   anslutningens hälsokontroll _"körs men är inte inloggat"_ (inte ett rött
   autentiseringsfel). Använd **Logga in med ChatGPT**: detta kör Codex
   standardflöde för enhets-OAuth i din webbläsare och skriver sedan
   `~/.codex/auth.json` till den delade volymen via **Tillämpa autentisering**
   (samma inloggning används av både leverantören `codex` och
   `codex-app-server`).
3. När inloggningen är klar blir hälsokontrollen grön (den verifierar både
   `/readyz` **och** `account/read` — det vill säga att tjänsten är igång _och_
   autentiserad), varefter allt fungerar.

Instrumentpanelen skriver aldrig över en befintlig och fungerande
`~/.codex/auth.json` — den skriver endast när filen saknas eller dess token är
inaktuell (en säkerhetskopia skapas alltid).

## 4. Driftsättningsscenarier

- **Operatör med ett redan autentiserat Codex CLI** — montera värdens
  `~/.codex` i sidovagnen (`codex-appserver-home`) och hoppa över
  inloggningssteget.
- **Offentlig användare utan lokalt installerad codex** — irrelevant:
  sidovagnen innehåller CLI:t. Användaren autentiserar sig endast via
  instrumentpanelen.
- **OmniRoute på fysisk server (ingen sidovagn, codex på värden)** — låt
  `OMNIROUTE_CODEX_APPSERVER_WS` peka på din egen `codex app-server` och se till
  att codex på värden är inloggat; tipset "codex är inte installerat" visas om
  binärfilen saknas.

## 5. Utgående trafik via hemnätverk/UDP (operatörstillägg, medföljer inte)

Den generiska sidovagnen ovan skickar utgående trafik via containerns vanliga
nätverk. En operatör som behöver skicka Codex-trafik via en **utgång i ett
hemnätverk** (t.ex. en TUN-tailscale-sidovagn som transporterar TCP + UDP/QUIC)
kör den som en separat compose-åsidosättning; den ingår avsiktligt **inte** i
den medföljande profilen `codex-app-server`. Se den interna driftmanualen för
den konfigurationen.
