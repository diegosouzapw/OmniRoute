> **Kort sagt**: OmniRoute spårar tokenanvändningen för varje begäran, beräknar kostnaden, tillämpar kvoter per API-nyckel och visar analysdata i kontrollpanelen. Den här guiden förklarar hur allt fungerar.

**Källor:**

- `open-sse/services/usage.ts` (~70KB) — huvudsaklig spårning av användning
- `src/lib/usageAnalytics.ts` (~10KB) — aggregering för kontrollpanelen
- `src/lib/db/quotaSnapshots.ts` — historiska kvotdata
- `src/lib/db/usage*.ts` — flera användningsrelaterade databasmoduler

---

## Översikt

Varje begäran som passerar genom OmniRoute genererar en **användningspost** som registrerar:

- **Identitet**: vilken API-nyckel, leverantör, modell och kombination
- **Token**: prompttoken, slutförandetoken, cachelagrade token och totalt antal
- **Kostnad**: belopp i USD (beräknat från prisdata)
- **Tidsinformation**: latens samt start- och sluttidsstämplar
- **Status**: lyckad, fel, hastighetsbegränsad osv.

Dessa poster aggregeras till **analysdata**, sparas som **kvotögonblicksbilder** och används för att tillämpa **budgetgränser per nyckel**.

```
Begäran ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                     analys    kvot   fakturering
                  (kontrollpanel) (tillämpning) (export)
```

## Vad som registreras

Tjänsten `usage.ts` registrerar en **användningshändelse** för varje begäran:

| Fält               | Typ     | Källa                                                       |
| ------------------ | ------- | ----------------------------------------------------------- |
| `id`               | string  | UUID som genereras vid registreringen                       |
| `apiKeyId`         | string  | API-nyckeln som initierade begäran                          |
| `provider`         | string  | Leverantörs-ID (openai, anthropic osv.)                     |
| `model`            | string  | Modell-ID (gpt-5, claude-opus-4-6 osv.)                     |
| `comboId`          | string? | Kombinations-ID om begäran dirigerades via en kombination   |
| `promptTokens`     | number  | Från svaret från uppströmsleverantören                      |
| `completionTokens` | number  | Från svaret från uppströmsleverantören                      |
| `cachedTokens`     | number  | Token från cacheträffar (Anthropic-promptcachelagring osv.) |
| `totalTokens`      | number  | prompt + slutförande                                        |
| `costUsd`          | number  | Beräknat från prisdata                                      |
| `latencyMs`        | number  | Begärans totala varaktighet                                 |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`  |
| `errorClass`       | string? | Felklass om status != success                               |
| `timestamp`        | string  | ISO 8601 UTC                                                |
| `metadata`         | object  | Anpassade data som infogats av insticksprogram              |

### Varifrån token kommer

Token extraheras från uppströmsleverantörens svar i **svarshanteraren**:

```ts
// Från open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

För leverantörer som inte returnerar användningsdata (vissa leverantörer som använder webbkakor) **uppskattar** OmniRoute antalet token med hjälp av tumregeln `~4 tecken per token` (se `open-sse/services/autoCombo/pipelineRouter.ts`).

### Cachelagrade token

OmniRoute spårar `cached_tokens` separat från `prompt_tokens` eftersom:

- Anthropics promptcachelagring debiterar ett lägre pris för cachelagrade token (10 % av normalpriset)
- Vissa leverantörer returnerar `cache_read_input_tokens`, som bör prissättas annorlunda
- Analysdata kan visa **cacheträfffrekvensen** = `cached_tokens / prompt_tokens`

## Kostnadsberäkning

Kostnader beräknas från **prisdata** som synkroniserats från LiteLLM (`src/lib/pricingSync.ts`):

| Modell            | Indata $/1M | Utdata $/1M | Cachad $/1M |
| ----------------- | ----------- | ----------- | ----------- |
| gpt-5             | $2.50       | $10.00      | —           |
| claude-opus-4-6   | $15.00      | $75.00      | $1.50       |
| claude-sonnet-4-5 | $3.00       | $15.00      | $0.30       |
| gemini-2.5-pro    | $1.25       | $10.00      | —           |

Kostnadsformeln (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Varför subtraheras cachade token från prompten?** Den cachade delen prissätts separat; om indatapriset tillämpades på hela prompten skulle kostnaden räknas för högt.

### Prissynkronisering

Prisdata synkroniseras automatiskt från LiteLLM via slutpunkten `/api/pricing/sync` (utlöses av den inbyggda cron-uppgiften, inte av en användartillgänglig miljövariabel):

```bash
# Manuell utlösning
curl -X POST http://localhost:20128/api/pricing/sync
```

För modeller utan prisdata använder OmniRoute i stället en **uppskattad kostnad** baserad på interna genomsnittspriser (hämtade från LiteLLM:s prisdata).

## Aggregering efter datumintervall

Modulen `usageAnalytics.ts` beräknar instrumentpanelswidgetar från rå användningsdata. Den stöder 7 tidsintervall:

| Intervall | Tidsfönster                    | Användningsfall                           |
| --------- | ------------------------------ | ----------------------------------------- |
| `1d`      | De senaste 24 timmarna         | Identifiering av kostnadstoppar per timme |
| `7d`      | De senaste 7 dagarna           | Veckovis granskning                       |
| `30d`     | De senaste 30 dagarna          | Månadsfakturering                         |
| `90d`     | De senaste 90 dagarna          | Kvartalsanalys                            |
| `ytd`     | Sedan 1 januari innevarande år | Uppföljning av årsbudget                  |
| `all`     | Hela perioden                  | Samlad statistik för hela livstiden       |
| `custom`  | Användardefinierad start/slut  | Revisioner, ad hoc-frågor                 |

### Beräknade instrumentpanelswidgetar

För varje datumintervall beräknar analyslagret:

| Widget                    | Beskrivning                                                                     |
| ------------------------- | ------------------------------------------------------------------------------- |
| **Sammanfattningskort**   | Totalt antal förfrågningar, total kostnad, totalt antal token, lyckandefrekvens |
| **Dagligt trenddiagram**  | Kostnad + token per dag, staplade efter modell                                  |
| **Aktivitetsvärmekarta**  | Rutnät med timme på dagen × veckodag, färg = antal förfrågningar                |
| **Modellfördelning**      | Cirkeldiagram över kostnad per modell                                           |
| **Leverantörsfördelning** | Stapeldiagram över förfrågningar per leverantör                                 |
| **Främsta API-nycklar**   | Tabell över de 10 främsta nycklarna efter kostnad                               |
| **Felanalys**             | Felfrekvens över tid, vanligaste felklasser                                     |

### Programmatisk åtkomst

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // poster i användningshistoriken
  "7d",                 // tidsintervall: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // karta över leverantörsanslutningar (connectionId → kontonamn)
  {
    startDate: "2025-01-01",  // valfritt: för intervallet "custom"
    endDate: "2025-06-01",   // valfritt: för intervallet "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (cent)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Kvothantering

Kvoten per API-nyckel upprätthålls på två ställen:

1. **Mjuk gräns** (`quotaWarnAt`): varning på kontrollpanelen när användningen överskrider tröskelvärdet
2. **Hård gräns** (`quotaLimit`): begäran avvisas med HTTP 429 när gränsen överskrids

### Konfiguration

```ts
// Per API-nyckel
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — visa varning
  quotaLimit: 10_00,    // $10.00 — hårt stopp
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Hanteringsflöde

```
Begäran ──▶ quotaCheck()
              │
              ├── Inom gränsen?  ──▶ tillåt
              │
              └── Över gränsen?  ──▶ 429 För många begäranden
                                   med Retry-After-huvud
```

### Kvotögonblicksbilder

Tabellen `quotaSnapshots` lagrar **historisk kvotstatus** för trendanalys:

| Fält | Beskrivning |
| ----------- | ---------------------------------------- | ------ | ------- |
| `apiKeyId` | Nyckeln som spåras |
| `window` | "day" | "week" | "month" |
| `used` | Kostnad som använts i detta fönster (cent) |
| `limit` | Gränsen (cent) |
| `resetAt` | När fönstret återställs |
| `createdAt` | När ögonblicksbilden togs |

Ögonblicksbilder tas **vid varje begäran** vars kostnad är > 0 och används för att:

- Visa kvotens förloppsindikator på kontrollpanelen
- Visa diagram över kvottrenden för 30 dagar
- Utlösa aviseringar när användningen närmar sig gränsen

## Kvarhållning och rensning

Användningsdata växer med cirka 1–10 KB per begäran. I stor skala kan detta bli betydande.

### Inställningar för kvarhållning

Kvarhållningen av användningshistorik konfigureras via databasinställningarna i användargränssnittet eller via `/api/settings/database`.

Som standard sparas användningshistoriken i **90 dagar**.

### Rensning

Gamla poster rensas av `src/lib/db/cleanup.ts`:

- Utlöses av cron-processen i bakgrunden
- Tar bort poster från `usage_history` som är äldre än den konfigurerade kvarhållningsinställningen `usageHistory`

### Uppskattning av lagringsutrymme

| Begäranden per dag | Lagring i 30 dagar | Lagring i 90 dagar |
| ------------------ | ------------------ | ------------------ |
| 100                | ~3 MB              | ~9 MB              |
| 1 000              | ~30 MB             | ~90 MB             |
| 10 000             | ~300 MB            | ~900 MB            |
| 100 000            | ~3 GB              | ~9 GB              |

Vid mycket hög trafik bör du överväga att:

- Minska kvarhållningsperioden via databasinställningarna
- Använda `aggregated_metrics` i stället för rådata (endast för analys)

## Tips för kostnadsoptimering

### 1. Använd rätt modell

```bash
# Snabbt svar — använd en billig och snabb modell
curl -d '{"model":"auto/fast","messages":[...]}'

# Komplex uppgift — prioritera kvalitet
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Aktivera cachelagring

Anthropics promptcachelagring sparar **90 % vid upprepad kontext**:

```ts
// Cachelagringen sker automatiskt — inkludera bara samma stora systemprompt
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Cachelagras automatiskt
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Använd komprimering

RTK- och Caveman-komprimering sparar **15–95 % i sessioner med omfattande verktygsanvändning**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Ange kvoter per nyckel

Ange alltid `quotaLimit` för att förhindra skenande kostnader:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Tak på 10 USD/månad
```

### 5. Granska de största förbrukarna

Använd kontrollpanelen eller **`/api/usage/analytics`** för att gruppera efter API-nyckel och sortera efter kostnad:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Felsökning

### "Kostnaden är högre än förväntat"

1. Kontrollera **`/api/usage/analytics?groupBy=model`** — hitta den kostsamma modellen
2. Kontrollera **`/api/usage/analytics?groupBy=apiKey`** — hitta den stora förbrukaren
3. Kontrollera att prisuppgifterna är aktuella: `POST /api/pricing/sync`

### "Poster saknas"

- Kontrollera databasens kvarhållningsinställningar under Kontrollpanel → Databas → Rensning — gamla poster tas bort av den periodiska rensningsuppgiften (`src/lib/db/cleanup.ts`)
- Sök efter fel i `src/lib/db/usage*.ts` — skrivfel i databasen loggas men visas inte
- Kontrollera att begäran faktiskt nådde `chatCore` — kontrollera kombinationsroutningen

### "Kvoten tillämpas inte"

- Kontrollera nyckelns inställning `quotaLimit`
- Kontrollera att `quotaWindow` är korrekt inställd
- Leta efter `quotaSnapshots`-poster — de ska skapas vid varje begäran
