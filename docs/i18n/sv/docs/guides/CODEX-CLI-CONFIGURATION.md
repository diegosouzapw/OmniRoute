Komplett guide för att använda Codex CLI med OmniRoute som en OpenAI-kompatibel backend.

---

> **TOML är det enda formatet som fungerar.** Moderna Codex läser uteslutande
> `~/.codex/config.toml` (verifierat med codex-cli 0.147.0: `codex --help`
> dokumenterar att `-c/--config` åsidosätter inställningar som har ”lästs in från
> `~/.codex/config.toml`”). Den gamla `~/.codex/config.yaml` tillhörde den äldre
> npm-baserade CLI:n och ignoreras utan något meddelande. Kontrollpanelens generator
> (`/api/cli-tools/apply`, verktyget `codex`) skriver TOML med en försiktig
> sammanslagning — befintliga nycklar och andra providerblock bevaras, API-nyckeln
> ligger kvar i `OMNIROUTE_API_KEY` (aldrig i filen), och en kvarvarande äldre
> `config.yaml` rapporteras som en migreringsanmärkning utan att ändras.

## Färdig `config.toml` att klistra in

Ersätt `<YOUR_HOST>` och `<YOUR_KEY>` med dina värden:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # lagringsgräns i historiken per verktygsanrop

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc eller ~/.zshrc — det faktiska nyckelvärdet, aldrig i config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex som ingår i ChatGPT-appen

Om du installerade Codex via ChatGPT-skrivbordsappen kan den körbara filen
`codex` endast finnas i appaketet och ännu inte vara tillgänglig i skalets
`PATH`. Lägg till resurskatalogen i skalets startfil:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Öppna ett nytt skal och verifiera sedan:

```bash
command -v codex
codex --version
```

### Lokal OmniRoute utan autentisering: en platshållarnyckel räcker

Codex verifierar att miljövariabeln som anges av `env_key` finns
**innan** den första begäran lämnar CLI:n. Om din **lokala** OmniRoute-instans
inte kräver autentisering fungerar valfri icke-tom platshållare:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Använd i stället en riktig nyckel när OmniRoute-servern är skyddad eller fjärransluten.

> **Vanliga värdalternativ**
>
> | Åtkomst        | URL                           |
> | -------------- | ----------------------------- |
> | Lokalt nätverk | `http://192.168.0.1:20128/v1` |
> | Tailscale      | `http://100.x.x.x:20128/v1`   |
> | Loopback       | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — därför fungerar det för alla modeller

Codex CLI fasade ut `wire_api = "chat"` (Chat Completions) i februari 2026 och **kräver** nu `wire_api = "responses"` (OpenAI Responses API). Om `wire_api = "chat"` anges kraschar programmet omedelbart vid start sedan v0.138.

Många leverantörer, inklusive GLM och Kimi, erbjuder fortfarande endast en Chat Completions-slutpunkt. DeepSeek V4 erbjuder nu både ett inbyggt Responses API och en Anthropic-kompatibel slutpunkt. OmniRoute använder Responses som standard och låter varje DeepSeek-anslutning välja Anthropic-kompatibilitet.

**OmniRoute löser detta transparent:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute väljer leverantörens inbyggda protokoll och översätter vid behov
    → POST /responses (DeepSeek V4) eller /chat/completions (Mistral / GLM / Kimi / övriga)
```

Du behöver aldrig en separat översättningsproxy när du använder OmniRoute. **Alla modeller använder `wire_api = "responses"`** — OmniRoute hanterar resten.

> **`wire_api` är standardvärdet** — fältets standardvärde är `"responses"` och det kan utelämnas helt från `config.toml`. Ange det endast uttryckligen om du vill dokumentera avsikten.

## Kontextfönster och komprimering

### Fält för tokenkonfiguration

| Fält                             | Beskrivning                                                                                                                                                                                                                |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Total tokenbudget för den aktiva modellen. Ställ in den på modellens angivna gräns.                                                                                                                                        |
| `model_auto_compact_token_limit` | Tröskel som utlöser automatisk komprimering av historiken. **Maximalt: 90 % av `model_context_window`** — värden över 90 % ignoreras utan varning.                                                                         |
| `tool_output_token_limit`        | Begränsning av antalet token som lagras i historiken per utdata från verktygsanrop. Förhindrar att ett enda stort verktygssvar fyller fönstret. **Detta är inte maximal utdata** — det är en lagringsgräns för historiken. |
| `compact_prompt`                 | Infogad åsidosättning av systemprompten som används vid komprimering (v0.138+).                                                                                                                                            |

> **Anmärkning om `model_max_output_tokens`**: Det här fältet är **inte en del av konfigurationsschemat för Codex CLI** (det saknas i Codex Rust-kodbasen). Det ignoreras utan varning om det anges. Förlita dig inte på det — använd `tool_output_token_limit` för att styra hur mycket verktygsutdata som lagras i historiken.

## Modellprefix: `cx/`

Alla Codex-modeller i OmniRoute använder prefixet `cx/`:

| Codex CLI-namn          | OmniRoute-modell   |
| ----------------------- | ------------------ |
| `cx/gpt-5.5`            | GPT-5.5 standard   |
| `cx/gpt-5.4`            | GPT-5.4 standard   |
| `cx/gpt-5.4-mini`       | GPT-5.4 mini       |
| `cx/gpt-5.1-codex-mini` | GPT-5.1 Codex mini |

Andra leverantörer använder sina egna prefix (`kmc/`, `glm/`, `ds/`, `ollamacloud/`, `opencode-go/`, `mistral/`) — prefixet motsvarar leverantörens alias i OmniRoute.

## Resonemangsnivå

Styr hur mycket modellen ”tänker” innan den svarar.

| Värde    | Använd för                                       |
| -------- | ------------------------------------------------ |
| `none`   | Inget resonemang — direkt svar                   |
| `low`    | Enkla uppgifter (byt namn, formatera)            |
| `medium` | **Serverstandard** när inget anges               |
| `high`   | Medelsvåra uppgifter (refaktorering, felsökning) |
| `xhigh`  | Arkitektur, djupanalys, komplexa problem         |

```bash
# Åsidosätt per anrop
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

Ange även en **sammanfattning** av resonemanget så att Desktop kan visa tanketext (inte bara krypterade blobbar):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # eller ultra när det stöds
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute-resonemangsbudget (serverinställning)

På OmniRoute-värden måste **Settings → AI → Thinking Budget** vara inställt på **`passthrough`** för att Codex resonemangsnivå/sammanfattning ska nå uppströmsleverantören. Läget **`auto` tar bort** alla `reasoning`- och `reasoning_effort`-fält från klienten och gör resonemangspanelerna tomma även när Codex är korrekt konfigurerat.

Fullständig guide: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Komprimering och promptcache är oberoende och fortsätter att fungera med `passthrough`.

## Profiler — namngivna konfigurationer per modell/arbetsflöde

Med profiler kan du byta modell + kontextfönster med en enda flagga. Varje profil är en platt
`~/.codex/<name>.config.toml` som läggs ovanpå den grundläggande `config.toml`.

> **Namngivningsregel (Codex CLI v0.137+):** filen måste vara `~/.codex/<name>.config.toml` — **utan prefixet `profile-`**.
> CLI:n tolkar `-p kimi-k27` som `~/.codex/kimi-k27.config.toml`. Om filen inte hittas används standardinställningen utan något meddelande.

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # snabbt, billigt
```

### Resonemangsprofiler (samma modell, olika nivåer)

```bash
codex -p low      # cx/gpt-5.5, nivå=low
codex -p medium   # cx/gpt-5.5, nivå=medium
codex -p high     # cx/gpt-5.5, nivå=high
codex -p xhigh    # cx/gpt-5.5, nivå=xhigh (standard)
codex -p chat     # cx/gpt-5.5, ingen nivå angiven (serverstandard)
```

## Generera profiler automatiskt med `omniroute setup-codex`

Om du kör OmniRoute på en VPS kan du automatiskt generera profilfiler från den aktiva modellkatalogen:

```bash
# Från en VPS (använder lokal OmniRoute på port 20128)
omniroute setup-codex

# Från valfri dator – peka på din VPS
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Förhandsgranska utan att skriva filer
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Generera endast GLM- och Kimi-profiler
omniroute setup-codex --only glm,kimi

# Skriv till en anpassad katalog
omniroute setup-codex --codex-home /path/to/.codex
```

Kommandot hämtar `/v1/models`, använder finjusterade profiler för kända modeller, använder katalogens metadata som reserv för andra kompatibla textmodeller och skriver `~/.codex/<name>.config.toml` för varje modell. Det är idempotent och kan därför köras igen utan risk.

OmniRoute kan även **synkronisera automatiskt** samma profilfiler efter att en lyckad identifiering/import av leverantörsmodeller ändrar den aktiva katalogen. Detta är **valfritt och inaktiverat som standard**: aktivera det via **CLI Code-kontrollpanelen** ("CLI profile auto-sync" → Codex), eller ange `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (inställningen tar även hänsyn till `CLI_ALLOW_CONFIG_WRITES`, som är aktiverad som standard). När funktionen är aktiverad skriver den endast separata profilfiler i `~/.codex/*.config.toml`; den ändrar aldrig den aktiva/standardmässiga `~/.codex/config.toml`, Codex-lb-inställningar, autentisering eller val av leverantör.

## Starta Codex med `omniroute launch-codex`

Kontrollerar hälsostatusen för din OmniRoute-instans innan Codex startas:

```bash
# Starta mot lokal OmniRoute (standardport 20128)
omniroute launch-codex

# Starta med en specifik profil
omniroute launch-codex --profile kimi-k27

# Starta mot en fjärr-VPS
omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# Skicka extra argument till codex
omniroute launch-codex --profile glm52 -- --yolo "fix this bug"
```

Codex är också ett mål för de två generiska, manifeststyrda startpunkterna

## Långvariga uppgifter

Två standardinställningar i OmniRoute kan obemärkt sabotera Codex CLI-sessioner som pågår i flera timmar. Ingen av dem är en Codex CLI-inställning — båda finns på OmniRoute-sidan. Användare som migrerar en konfiguration från uppströmsproxyer som låser konton och inaktiverar tidsgränser för inaktivitet stöter ofta på båda och drar slutsatsen att OmniRoute ”inte kan upprätthålla en lång session”.

| Symtom                                                                                 | Trolig orsak                                                               | Inställning              |
| -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------ |
| Sessionen fortsätter att byta konto/promptcachekontinuiteten går förlorad mellan turer | TTL för sessionsaffinitet är `0` (inaktiverad)                             | `sessionAffinityTtlMs`   |
| Anslutningen bryts mitt under resonemanget utan något meddelande till klienten         | Övervakningen av inaktiv ström utlöstes efter 10 minuter utan uppströmsdel | `STREAM_IDLE_TIMEOUT_MS` |

Relaterade diskussioner: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (avbrott i långa uppgifter), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (varför affinitet är inaktiverad som standard). Spårning: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Sessionsaffinitet — lås en konversation till ett konto

**Standard:** `sessionAffinityTtlMs = 0` (inaktiverad).

**Var den ställs in**

- Kontrollpanel → **Inställningar → Routning** → **Sessionsaffinitet** → **Affinitets-TTL (sekunder)** (`ComboDefaultsTab`)
- Eller PATCH:a inställningarna med `sessionAffinityTtlMs` i **millisekunder** (Zod-intervall `0`–`86_400_000`, dvs. upp till 24 timmar)

> Bytte namn i #7274 från den Codex-specifika `codexSessionAffinityTtlMs`. Den äldre nyckeln accepteras fortfarande som ett skrivskyddat alias; nya konfigurationer bör använda `sessionAffinityTtlMs`. Affinitet gäller nu för **alla** leverantörer när TTL-värdet är högre än `0`, inte bara Codex — se [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Sessionsaffinitet.

**Vad som slutar fungera när värdet förblir 0**

Varje tur i en Codex-konversation med flera turer routas oberoende av den aktiva kombinationsstrategin och kan hamna på ett **annat konto för varje tur**. Det bryter kontinuiteten för uppströmssessionen/promptcachen. OmniRoute tar endast hänsyn till Codex-sessionshuvuden (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) och brödfält som `prompt_cache_key` / `session_id` när TTL-värdet är högre än `0` (`extractSessionAffinityKey` i `src/sse/services/auth.ts`).

**Rekommenderat för en enskild uppgift som pågår i flera timmar**

Ställ in TTL-värdet **högre än uppgiftens förväntade faktiska varaktighet** (gränssnittets maxvärde är **86400 sekunder** = 24 timmar):

| Förväntad uppgiftslängd | Affinitets-TTL (gränssnitt, sekunder) | `sessionAffinityTtlMs` |
| ----------------------- | ------------------------------------- | ---------------------- |
| Några timmar            | `14400` (4 tim)                       | `14400000`             |
| Över natten/~12 tim     | `43200` (12 tim)                      | `43200000`             |
| Ett helt dygn           | `86400` (24 tim, maximalt)            | `86400000`             |

Det är avsiktligt valfritt: inaktiverad affinitet gynnar lastbalansering mellan konton; aktiverad affinitet gynnar kontinuiteten för en lång agentsession. Den här guiden ändrar **inte** standardvärdet — operatörer som kör långa Codex-uppgifter måste själva aktivera funktionen.

### 2. Tidsgräns för inaktiv ström — avbryt inte tysta resonemangsturer

**Standard:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 minuter). Den ärver från `REQUEST_TIMEOUT_MS` när den inte är angiven; den gemensamma baslinjen är också 600000. Se [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Tidsgränser.

**Vad som slutar fungera med standardvärdet**

En Codex-resonemangs-/verktygstur som förblir tyst i mer än 10 minuter utan **någon riktig uppströmsdatabit** tvångsstängs av SSE-vakten för inaktivitet (`open-sse/utils/stream.ts`). Klienten ser ofta bara att anslutningen bryts — vilket stämmer överens med ”stoppades automatiskt utan någon avisering”.

Viktig detalj: OmniRoutes syntetiska SSE-**hjärtslag återställer inte** inaktivitetsklockan. Endast en riktig uppströmsdatabit uppdaterar `lastChunkTime`. En tyst modell som fortfarande ”tänker” ser ur vaktens perspektiv likadan ut som en uppströmsanslutning som har stannat.

Relaterad inaktivitet för Undici-svarskroppen: `FETCH_BODY_TIMEOUT_MS` (har också samma standardgräns på 10 minuter; `0` inaktiverar den). För strömning omfattar `FETCH_TIMEOUT_MS` endast upprättandet av anslutningen/de första headers — när strömmen väl är aktiv hanteras avbrott av `STREAM_IDLE_TIMEOUT_MS` och `FETCH_BODY_TIMEOUT_MS`.

**Rekommenderat för en enskild uppgift som tar flera timmar**

I OmniRoute-processens miljö (`.env` / compose / systemd):

```bash
# Inaktivera tidsgränser för ströminaktivitet och inaktiv svarskropp vid långa resonemangsturer
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Eller höj dem så att de överstiger den längsta tysta period du förväntar dig (värdena anges i millisekunder):

```bash
# Exempel: tillåt upp till 2 timmars tystnad mellan uppströmsdatabitar
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Starta om OmniRoute efter att du har ändrat dessa miljövariabler.

### Konkret recept — Codex-uppgift som tar flera timmar

1. **Lås kontot:** Kontrollpanelen → Inställningar → Routning → Sessionsaffinitet → Affinitets-TTL = `43200` (12 h) eller `86400` (max. 24 h).
2. **Höj/inaktivera tidsgränserna för inaktivitet** i OmniRoutes miljö:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Behåll den vanliga Codex-konfigurationen i `config.toml` (`wire_api = "responses"`, korrekt `base_url`, `OMNIROUTE_API_KEY`) — det finns inga Codex-inställningar för affinitet/inaktivitet som styr dessa två beteenden.
4. Starta om OmniRoute och starta sedan den långvariga Codex-uppgiften.

### Beslut om standardvärden (#7287)

| Inställning              | Levererat standardvärde | Ändra i den här guiden?                                                                                          |
| ------------------------ | ----------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (av)                | **Nej** — förblir valbart (lastbalansering kontra kontinuitet; se Diskussion #5718)                              |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 min)       | **Nej** — förblir 10 minuter för allmän trafik; operatörer med långa Codex-körningar höjer eller inaktiverar det |

Att ändra något av standardvärdena globalt skulle påverka beteendet för varje klient på en instans, inte bara Codex. Dokumentera inställningarna och lämna standardvärdena oförändrade tills ett uttryckligt operatörsbeslut anger något annat.

### Diagnostisera avbrott på grund av inaktivitet

När vakten för inaktivitet utlöses loggar OmniRoute en rad med följande form:

```text
[STREAM] Tidsgräns för inaktivitet: inga data från codex under 600000ms (modell: cx/gpt-5.5)
```

Sök med grep efter `Idle timeout: no data from` (eller koden `stream_idle_timeout`/felnamnet `StreamIdleTimeoutError`). Leverantörssegmentet är det som OmniRoute använde för den aktuella begäran (`codex`, ett annat leverantörs-id eller `provider` om det är okänt) — det är inte alltid den bokstavliga strängen `codex`.

## Felsökning

**`Error: wire_api = "chat" stöds inte längre`**
Ta bort `wire_api = "chat"` från din konfiguration. Ange `wire_api = "responses"` eller utelämna fältet (standardvärdet är `"responses"` sedan v0.138).

**`Error: modellen hittades inte`**
Kontrollera att modellen finns i OmniRoute med rätt prefix. Använd `omniroute models list` eller öppna `/dashboard/providers/<provider>`.

**`Autentiseringsfel`**
Bekräfta att `OMNIROUTE_API_KEY` har exporterats: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Miljövariabel saknas: OMNIROUTE_API_KEY`**
Codex verifierar att miljövariabeln finns innan den första begäran görs. Exportera
en riktig nyckel för skyddade servrar eller ett icke-tomt platshållarvärde, till exempel
`OMNIROUTE_API_KEY=local`, när din **lokala** OmniRoute-instans inte
kräver autentisering. Starta om skalet om du lade till den i `~/.bashrc` eller `~/.zshrc`.

**`Anslutningen nekades`**
Kontrollera att OmniRoute körs och att värden/porten i `base_url` är korrekt för ditt nätverk (lokalt kontra Tailscale kontra VPS).

**Sessionen kraschar nära kontextgränsen**
Ange `model_context_window` och `model_auto_compact_token_limit` uttryckligen. Se tabellen över kontextfönster ovan.

**Komprimeringen utlöses för sent**
Sänk `model_auto_compact_token_limit` till 80–85 % av fönstret. Ange aldrig ett värde över 90 %.

**Profilen läses inte in (`-p <name>` ignoreras utan meddelande)**
Bekräfta att filen finns på `~/.codex/<name>.config.toml` (utan prefixet `profile-`). Kör `ls ~/.codex/*.config.toml`.

**En långvarig Codex-uppgift avbryts mitt under körningen/konton växlas mellan turer**
Se [Långvariga uppgifter](#long-running-tasks). Aktivera sessionsaffinitet (TTL längre än uppgiftens varaktighet) och höj eller inaktivera `STREAM_IDLE_TIMEOUT_MS`/`FETCH_BODY_TIMEOUT_MS`. Sök i OmniRoute-loggarna med grep efter `Idle timeout: no data from`.
