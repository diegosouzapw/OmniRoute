### Hastighetsbegränsning hos kostnadsfria leverantörer (429 / 400 / 401)

**Symptom**: När du använder `model: "auto"` med kostnadsfria leverantörer eller leverantörer utan autentisering (opencode, auggie osv.) får du sporadiskt `HTTP 429`, `400` eller `401` i stället för svar. Förfrågningarna lyckas om samma prompt skickas igen en kort stund senare, men automatisering (cron-jobb, agenter, skript) avbryts vid det första felet.

**Grundorsak**: Tre oberoende fellägen samverkar:

1. **Leverantörens hastighetsgräns (`429`)**: Kostnadsfria nivåer kan tillämpa en kvot per tidsfönster. En skur av parallella anrop förbrukar den, så nästa förfrågan nekas tills tidsfönstret återställs.
2. **Trasig modell vid direktvidarebefordran (`400`/`401`)**: `auto/*`-pooler kan innehålla modeller för direktvidarebefordran från `opencode` som är registrerade i katalogen men saknar aktiva autentiseringsuppgifter (t.ex. `oc/north-mini-code-free` → `401`). Den automatiska routern provar en, misslyckas och vidarebefordrar felet innan reservväxlingen hinner aktiveras.
3. **Förstärkning genom samtidighet (`429` under belastning)**: När flera agent-/cron-sessioner anropar `auto` samtidigt överstiger den sammanlagda förfrågningsfrekvensen vad kostnadsfria leverantörer tolererar, vilket gör att legitima anrop flaggas som missbruk.

**Verifierad lösning (rapporterad av communityn, 2026-08-10)**: justera tre miljövariabler så att rotation, samtidighet och reservväxling hanterar instabiliteten i den kostnadsfria nivån i stället för att stoppas av den:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # växla till en annan modell/leverantör vid 400/401 (hoppar över trasiga modeller för direktvidarebefordran)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # explicit gräns för insläpp av tungviktare (ej angiven som standard: ingen gräns för antal förfrågningar, se anmärkningen nedan)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # längre begränsad väntan på tungviktskapacitet i stället för ett omedelbart 503-fel som kan försöka igen
```

Ange dessa i OmniRoute-processens miljö (demonen, t.ex. via LaunchAgent-plist-filen eller `systemctl edit`) och starta sedan om OmniRoute. Rotationsflaggan är den enskilda åtgärd som ger störst effekt: den omvandlar ett definitivt fel till ett transparent nytt försök mot en fungerande leverantör i poolen.

**Anmärkning**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` begränsar hur många tungviktsförfrågningar — förfrågningar med lång kontext — som körs samtidigt; gränsen är en insläppsport, inte en hastighetsbegränsare för leverantören. **Uppdatering om #503-fanout:** den här variabeln anges inte längre som standard (den gäller nu endast när den uttryckligen konfigureras, som ovan) — insläpp av tungviktare styrs i stället av en automatiskt härledd bytebudget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) som anpassar sig efter värddatorns faktiska minnesgräns. En ny distribution bör därför ge betydligt färre avvisningar med `503 chat_admission_busy` utan att variabeln behöver anges alls; om den anges uttryckligen här fungerar den fortfarande exakt som dokumenterat. Explicita åsidosättningar av bytebudgeten begränsas till 8 MiB–2 GiB. Ett `413 body_exceeds_budget` är inte tillfälligt: öka bytebudgeten, sänk `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` eller höj processens minnesgräns. En avlastning av typen `inflight_bytes_budget` orsakas av tillfällig resurskonkurrens och kan fortfarande försökas igen. Hastighetsbegränsningen per leverantör (`open-sse/services/rateLimitManager.ts`) styrs separat av `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` och `RATE_LIMIT_AUTO_ENABLE` — se `.env.example`.

**Så verifierar du att det fungerade**: kör din agent/ditt cron-jobb två gånger i snabb följd och bekräfta att båda körningarna lyckas. Före korrigeringen ger den andra körningen vanligtvis `429`/`401`. Efter korrigeringen görs nya försök transparent vid eventuella fel och anropet slutförs. Du kan även köra `curl /monitoring/health` och övervaka fältet `rateLimitedUntil` för leverantörsanslutningarna samt `circuitBreakers.providerBreakers[].state` för de berörda leverantörerna — tillståndet är ett av `CLOSED`, `DEGRADED`, `OPEN` eller `HALF_OPEN` (se `src/shared/utils/circuitBreaker.ts`), och en leverantör som fortsätter att misslyckas växlar från `CLOSED → DEGRADED → OPEN` innan återställningsfönstret släpper igenom ett testanrop (`HALF_OPEN`).

**Om du fortfarande ser 429**: det aktiva kontot för den leverantören har faktiskt förbrukat hela sin _kvot_ (inte bara nått hastighetsgränsen). Lägg till ett andra konto för samma leverantör i OmniRoute-instrumentpanelen → Providers → Accounts, eller lägg till en annan kostnadsfri leverantör (t.ex. `routeway`, `auggie`). Rotation hjälper endast vid tillfälliga hastighetsbegränsningar/400/401; en helt förbrukad kvot kräver en andra autentiseringsuppgift eller en annan leverantör.

**Om du ser 403 för visionsmodeller (`auto/vision`, `bazaarlink/*`)**: det anslutna kontot saknar ett betalabonnemang som inkluderar vision, eller så har API-nyckeln otillräckliga behörigheter. Kontrollera i leverantörens instrumentpanel att nyckelns omfång inkluderar vision/multimodal funktionalitet, eller anslut ett konto med betalnivå och behåll det som mål för vision.

## Varningar vid npm install (ERESOLVE / peer / deprecated)

När du kör `npm install -g omniroute` kan du få en mängd varningar, exempelvis `npm warn ERESOLVE`, meddelanden om peer-beroenden och `deprecated`-meddelanden. **Dessa är förväntade och ofarliga.** Installationen lyckades om du ser `added <N> packages` i utdata.

Varningarna kommer från inaktuella intervall för peer-beroenden i tredjepartspaket som OmniRoute inte styr över:

1. **`marked-terminal` kräver `marked >=1 <16`, men `marked@18` hittades** — fungerar bra i praktiken; intervallet för peer-beroendet uppströms är bara inaktuellt.
2. **`deprecated prebuild-install@7.1.3`** — ett transitivt hjälpprogram för hämtning av plattformsspecifika binärfiler. Det används inte
   för att installera den låsta transportbindningen `wreq-js` och innebär inte att konfigurationen av
   transporten för webbcookie-leverantören misslyckades.

**Ingen åtgärd krävs** — varningarna kan inte tystas helt utan att skapa egna avgreningar av uppströmspaketen.

## Falska positiva antivirusvarningar

<a name="antivirus-false-positives"></a>

### Avast/AVG placerar `README.md` i karantän med `MD:HttpRequest-inf[Susp]`

**Detta är en falsk positiv varning. Ingenting är infekterat och ingen åtgärd krävs.**

Avast och AVG använder en heuristisk analys som flaggar rena text-/Markdown-filer som innehåller många
länkar som ser ut som HTTP-förfrågningar. OmniRoutes `README.md` medföljer i npm-paketet (den
anges i `package.json` → `files`), så den hamnar i `node_modules/omniroute/README.md` vid
en global installation — och den innehåller cirka 15 exempel med `http://localhost:20128/...` (MCP:s
HTTP-/SSE-endpoints, A2A:s `.well-known`-URL och `curl`-utdrag). Den länktätheten är
tillräcklig för att utlösa heuristiken.

Om detta började först nyligen: filens karaktär har inte förändrats. README-filen fick en utökad
endpoint-tabell (MCP HTTP + SSE + A2A lades till) och fler `curl`-exempel, vilket gjorde
att den passerade tröskelvärdet.

Filen är inaktiv dokumentation helt utan körbart innehåll. Du kan utan risk återställa den
från karantänen.

**Gör så här:**

1. **Stoppa aviseringarna** — undanta installationskatalogen i ditt antivirusprogram
   (Avast: Inställningar → Undantag) genom att lägga till sökvägen till din globala `node_modules` och/eller
   OmniRoutes datakatalog (`~/.omniroute/`).
2. **Rapportera den falska positiva varningen** — <https://www.avast.com/false-positive-file-form.php>,
   och bifoga den karantänplacerade `README.md`. Det är den lösning som hjälper alla, eftersom det är
   leverantörens heuristik som överreagerar på en textfil.

**Varför vi inte ”åtgärdar” detta på vår sida:** alla exempel använder `http://localhost`, och
localhost kan inte använda `https` utan komplikationer med självsignerade certifikat. Att förvränga dokumentationen för att
kringgå en leverantörs heuristik skulle försämra den för alla läsare bara för att tillmötesgå ett fel i ett skanningsprogram.

### Kaspersky flaggar skrivbordsappen som `PDM:Trojan.Win32.Generic`

**Detta är en falsk positiv varning från en beteendeheuristik. Ingenting är infekterat.** Kasperskys
`PDM:`-prefix innebär att bedömningen kommer från dess Proactive Defense Module (System Watcher),
som bedömer vad installationsprogrammet _gör_ i stället för att jämföra det med känd skadlig kod. När
den utlöses ”återställer” Kaspersky hela installationen — och tar bort filer som redan
har skrivits — vilket gör att appen blir trasig eller saknas.

Filerna som flaggas är standarddelar av deklarerade beroenden med öppen källkod som paketeras med
skrivbordsappen, till exempel:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` och
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), biblioteket för webbläsarautomatisering
  som används för leverantörsinloggning i appen och webbläsarbaserad chatt.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — den fixerade inbyggda `wreq-js`-bindningen som används för webbläsarfingeravtryckad HTTP hos leverantörer
  som använder webbkakor (`<arch>` är `x64` eller `arm64`).

**Varför den utlöses:** Windows-installationsprogrammet är **ännu inte kodsignerat**, så ett osignerat NSIS-
installationsprogram har inget anseende och beteendeheuristiken körs med maximal aggressivitet. I kombination
med en medföljande inbyggd DLL och hundratals `.js`-filer som skrivs under
`%LOCALAPPDATA%\Programs\OmniRoute` (inklusive paketskataloger med hash-suffix från
Next.js fristående bygge) är det tillräckligt för att utlösa heuristiken. Kodsignering är planerad;
tills den är på plats kan detta upprepas för nya utgåvor.

**Gör så här:**

1. **Verifiera först din hämtade fil** (utesluter att filen har manipulerats). Varje utgåva publicerar
   `latest.yml`, vars `sha512`-fält (base64) omfattar installationsprogrammet
   `OmniRoute.Setup.<version>.exe`. I PowerShell, från mappen som innehåller installationsprogrammet:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Utdata måste matcha `latest.yml` → `sha512`. Om den inte gör det ska du radera filen och
   hämta den igen, endast från [GitHubs utgåvesida](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Återställ + undanta** — återställ objekten som togs bort från karantänen och lägg till ett undantag
   för `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Inställningar → Hot och undantag),
   och installera sedan om.
3. **Rapportera den falska positiva varningen** — <https://opentip.kaspersky.com/>. FP-rapporter
   som skickas in av användare påskyndar faktiskt tillåtelselistan.

## Node.js-kompatibilitet

<a name="nodejs-compatibility"></a>

### Inloggningssidan kraschar eller visar felet "Module self-registration"

**Orsak:** Du kör en Node.js-version som ligger utanför OmniRoutes godkända säkra körningsmiljö. Det vanligaste fallet är att du kör en äldre korrigeringsversion av Node 22 eller 24 som ligger under den säkerhetsnivå med korrigeringar som OmniRoute kräver.

**Symtom:**

- Inloggningssidan visar en tom skärm eller ett serverfel
- Konsolen visar `Error: Module did not self-register` eller liknande fel för systemspecifika bindningar
- Inloggningssidan visar en **orange varningsbanner** med din Node-version om körningsmiljön ligger utanför den säkra policy som stöds

**Åtgärd:**

1. Installera en LTS-version av Node.js som stöds (rekommenderas: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Kontrollera din version: `node --version` ska visa `v24.0.0` eller senare i LTS-serien 24.x
3. Installera om OmniRoute: `npm install -g omniroute`
4. Starta om: `omniroute`

> **Säkra versioner som stöds:** `>=22.22.2 <23` eller `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) och Node.js 26 stöds fullt ut.

### npm v11+: `better-sqlite3` är inte installerat (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Orsak:** npm v11 (som medföljer Node.js 24+) blockerar som standard installationsskript för valfria
beroenden. Eftersom `better-sqlite3` anges i `optionalDependencies`
och kräver systemspecifik kompilering (`node-gyp rebuild`) hoppar npm över det utan att meddela detta.

**Symtom:**

- Servern kraschar vid start med `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` visar "No such file or directory"
- `npm ls better-sqlite3` visar `(empty)`

**Åtgärd:**

1. Godkänn installationsskripten och installera om:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Eller installera den förkompilerade versionen manuellt:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Kontrollera att det fungerar: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Orsak:** Efter en global `npm install -g omniroute` kan den systemspecifika binärfilen för `better-sqlite3` i paketet ha kompilerats för en annan arkitektur eller Node.js-ABI än den som körs lokalt. Detta är vanligt på macOS (både Apple Silicon och Intel) när den förkompilerade binärfilen inte matchar din miljö.

**Symtom:**

- Servern slutar fungera omedelbart vid start med ett `dlopen`-fel
- Felet innehåller `slice is not valid mach-o file`
- Fullständigt exempel:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Åtgärd — kompilera om för din lokala miljö (ingen nedgradering av Node.js krävs):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Obs!** Detta kompilerar om den systemspecifika bindningen för din lokala Node.js-version och CPU-arkitektur, vilket löser binärinkompatibiliteten. Det officiellt stödda intervallet för körningsmiljön är **`>=22.22.2 <23` eller `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` i `src/shared/utils/nodeRuntimeSupport.ts`, i linje med fältet `engines` i `package.json`). Node.js 24.x LTS (Krypton) och Node.js 26 stöds fullt ut med `better-sqlite3` v12.x.

## Proxyproblem

<a name="proxy-issues"></a>

### Leverantörsvalideringen visar "fetch failed"

**Orsak:** Slutpunkten för validering av API-nyckeln (`POST /api/providers/validate`) kringgick tidigare proxykonfigurationen, vilket orsakade fel i miljöer som kräver proxytrafik.

**Lösning (v3.5.5+):** Detta är nu åtgärdat. Leverantörsvalideringen dirigeras genom `runWithProxyContext` och använder automatiskt både leverantörsspecifika och globala proxyinställningar.

### Hälsokontrollen för token misslyckas med "fetch failed"

**Orsak:** Bakgrundsuppdateringen av OAuth-token löste inte proxykonfigurationen separat för varje anslutning.

**Lösning (v3.5.5+):** Schemaläggaren för hälsokontroll av token löser nu proxykonfigurationen för varje anslutning innan den försöker uppdatera. Uppdatera till v3.5.5+.

### SOCKS5-proxyn returnerar "invalid onRequestStart method"

**Orsak:** I Node.js 22 är dispatchern i undici@8 inkompatibel med Node:s inbyggda `fetch()`-implementation.

**Lösning (v3.5.5+):** OmniRoute använder nu undicis egen `fetch()`-funktion när en proxydispatcher är aktiv, vilket säkerställer konsekvent beteende. Uppdatera till v3.5.5+.

### MITM-proxy under WSL: skrivbordsappar på Windows-värden fångas inte upp

**Orsak:** MITM-proxyn och dess CA-certifikat installeras i miljön där OmniRoute körs. Under WSL är den miljön Linux-gästen, medan AI-skrivbordsapparna (Kiro, Trae, Copilot, Zed, …) körs på Windows-värden. Värdapplikationerna litar inte på gästens certifikatarkiv och dirigerar inte trafiken genom gästens systemproxy, så skrivbordstrafiken fångas inte upp där.

**Rekommendation:** Kör OmniRoute direkt i samma operativsystem som skrivbordsapparna du vill fånga upp (Windows för Windows-appar och motsvarande för macOS/Linux). Om OmniRoute behålls inuti WSL samtidigt som värdapplikationer används måste du manuellt ange att det genererade CA-certifikatet ska vara betrott på Windows-värden och konfigurera varje värdapplikations nätverks-/proxyinställningar så att de pekar på WSL-proxyns slutpunkt — en konfiguration som inte stöds och är bräcklig.

## Leverantörsproblem

### "Language model did not provide messages"

**Orsak:** Leverantörskvoten är förbrukad.

**Lösning:**

1. Kontrollera kvotspåraren på instrumentpanelen
2. Använd en kombination med reservnivåer
3. Byt till en billigare eller kostnadsfri nivå

### Hastighetsbegränsning

**Orsak:** Prenumerationskvoten är förbrukad.

**Lösning:**

- Lägg till reservalternativ: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Använd GLM/MiniMax som ett billigt reservalternativ

### OAuth-token har upphört att gälla

OmniRoute uppdaterar token automatiskt. Om problemen kvarstår:

1. Instrumentpanel → Leverantör → Återanslut
2. Ta bort och lägg till leverantörsanslutningen igen

### Flera Kiro-konton: det andra kontot ogiltigförklarar det första

**Orsak:** Kiros serverdel tillåter endast en aktiv session per OIDC-klientregistrering.
När två konton delar samma registrerade klient (anslutningar som importerades före v3.8.0)
ogiltigförklaras det andra kontots uppdateringstoken när det ena kontots token uppdateras.

**Lösning (v3.8.0+):** Importera om berörda anslutningar.
Från och med v3.8.0 registrerar varje ny Kiro-anslutning som skapas via **Importera token**,
**social inloggning med Google/GitHub** eller **Automatisk import** automatiskt en egen
dedikerad OIDC-klient. Anslutningen är därför helt isolerad, och uppdatering av ett
konto påverkar inte något annat konto.

Anslutningar som importerades _före_ v3.8.0 har ingen klientregistrering per anslutning.
Dessa anslutningar fortsätter att använda den delade slutpunkten för uppdatering av social autentisering.
För att få isolering tar du bort den gamla anslutningen från Instrumentpanel → Leverantörer och lägger till den igen
via något av de tre importflödena.

Fullständig information och stegvisa instruktioner för att lägga till två Kiro-konton sida vid sida
finns i [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

1. Kontrollera att `BASE_URL` pekar på din aktiva instans (t.ex. `http://localhost:20128`)

2. Kör molnsynkronisering: Aktivera molnet → Synkronisera nu
3. Gamla/osynkroniserade nycklar kan fortfarande returnera `401` i molnet

## Docker-problem

### Docker IPv6/återställd anslutning

<a name="docker-ipv6"></a>

**Symptom:** `curl http://localhost:20128/v1/models` returnerar `curl: (56) Recv failure: Connection reset by peer`. Kontrollpanelen och oautentiserade slutpunkter fungerar, men autentiserade slutpunkter misslyckas – det ser ut som ett autentiseringsproblem, men är det inte.

**Orsak:** `docker run -p 20128:20128` publicerar både på `0.0.0.0` (IPv4) och `::` (IPv6), men processen inuti containern lyssnar endast på IPv4. På värdar där `localhost` först matchas mot `::1` hamnar anslutningen på den publicerade IPv6-porten utan någon lyssnare bakom den → anslutningen återställs.

**Lösning:**

1. **Snabbdiagnostik:** Kör `curl -4 http://localhost:20128/v1/models`. Om det fungerar med `-4` men misslyckas utan, har du en bindningskonflikt för IPv6.
2. **Permanent lösning:** Bind uttryckligen till IPv4 genom att använda `-p 127.0.0.1:20128:20128` i ditt `docker run`-kommando:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Detta framtvingar IPv4-bindning och förhindrar även att proxyn exponeras på värdens samtliga gränssnitt.

### Vanliga formatproblem

- **Tanketaggar visas inte** — Kontrollera om målleverantören stöder tänkande och inställningen för tankebudget
- **Verktygsanrop försvinner** — Vissa formatöversättningar kan ta bort fält som inte stöds; verifiera detta i läget Testmiljö
- **Systemprompt saknas** — Claude och Gemini hanterar systemprompter på olika sätt; kontrollera översättningsresultatet
- **SDK:n returnerar en rå sträng i stället för ett objekt** — Åtgärdat i v1.x; svarssaneraren tar bort icke-standardiserade fält (`x_groq`, `usage_breakdown` osv.) som orsakar valideringsfel i OpenAI SDK Pydantic. Om problemet fortfarande förekommer på v3.x+ bör du rapportera det.
- **GLM/ERNIE avvisar rollen `system`** — Åtgärdat i v1.x; rollnormaliseraren sammanfogar automatiskt systemmeddelanden med användarmeddelanden för inkompatibla modeller. Om problemet fortfarande förekommer på v3.x+ bör du rapportera det.
- **Rollen `developer` känns inte igen** — Åtgärdat i v1.x; konverteras automatiskt till `system` för leverantörer som inte är OpenAI. Om problemet fortfarande förekommer på v3.x+ bör du rapportera det.
- **`json_schema` fungerar inte med Gemini** — Åtgärdat i v1.x; `response_format` konverteras nu till Geminis `responseMimeType` + `responseSchema`. Om problemet fortfarande förekommer på v3.x+ bör du rapportera det.

## Inställningar för motståndskraft

### Automatisk hastighetsbegränsning utlöses inte

- Automatisk hastighetsbegränsning gäller endast leverantörer med API-nyckel (inte OAuth/prenumeration)
- Kontrollera att automatisk hastighetsbegränsning är aktiverad under **Inställningar → Motståndskraft → Leverantörsprofiler**
- Kontrollera om leverantören returnerar statuskoderna `429` eller `Retry-After`-huvuden

### Justera exponentiell backoff

Leverantörsprofiler stöder följande inställningar:

- **Grundfördröjning** — Inledande väntetid efter det första felet (standard: 1s)
- **Maximal fördröjning** — Övre gräns för väntetiden (standard: 30s)
- **Multiplikator** — Hur mycket fördröjningen ska ökas per fel i följd (standard: 2x)

### Skydd mot anstormning

När många samtidiga förfrågningar når en hastighetsbegränsad leverantör använder OmniRoute mutex + automatisk hastighetsbegränsning för att serialisera förfrågningar och förhindra kaskadfel. Detta sker automatiskt för leverantörer med API-nyckel.

### Chattförfrågningar misslyckas med 503 / chat_admission_busy

**Symptom:**

- Slutpunkten för chattkompletteringar returnerar ett återförsöksbart `503`-svar vars felkod är
  `chat_admission_busy`.
- Svaret innehåller `Retry-After`. Sedan #12135 härleds värdet från den observerade
  beläggningen — det högsta värdet av det `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`-fönster som förfrågan redan
  har väntat och den tid som de aktuella tungviktsreserveringarna har hållits — avrundat uppåt till hela
  sekunder och begränsat till högst 60. För en inaktiv spärr behålls de historiska miniminivåerna: 2 sekunder för den
  bytebaserade vägen, 1 sekund för den strukturbaserade vägen (som även inkluderar
  `reason: "structure_limit"`).
- Detta kan inträffa medan en annan tung chattförfrågan eller långvarig strömningsrespons fortfarande
  pågår.

Den bytebaserade svarskroppen är:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Det strukturbaserade svaret använder samma typ och kod, med meddelandet
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
och `reason: "structure_limit"`.
Med standardtröskelvärdena är en förfrågan strukturellt tung när den har minst `200` meddelanden,
minst `64` verktyg eller minst `32,000` uppskattade token, eller när den begränsade strukturuppskattningen
når sina gränser på `10,000` besökta noder eller djupet `12`.

**Orsak:** Detta är avsiktlig lastreducering inuti OmniRoute, inte ett fel hos en uppströmsleverantör.
Varje process använder ett processlokalt skydd för att reservera begränsad tungviktskapacitet innan en
stor förfrågningskropp behålls och parsas. En tungviktsreservering förblir aktiv under hela livslängden för ett SSE-
svar.

**#503-förgrening:** före den här korrigeringen begränsade skyddet samtidigheten till ett fast ANTAL förfrågningar
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, standard `1`) oavsett värddatorns minne, vilket gjorde att kodningsagenters
förgrening (flera underagenter/CLI:er, kroppar regelbundet > 256 KB) kollapsade till en effektiv
samtidighet på ~1 och gav 503-fel under helt normal belastning. Skyddet självjusteras nu: det styrs
av en automatiskt härledd BYTE-budget för inläsning (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) som dimensioneras utifrån
processens verkliga minnestak, och det tar även hänsyn till en aktuell signal för resursbelastning — så det
reducerar endast lasten när värddatorn verkligen är utsatt för minnesbelastning, inte bara för att fler än en
tung förfrågan anlände samtidigt. Den gamla antalsgränsen (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
respekteras fortfarande, men endast om du uttryckligen ställer in den.

När kapaciteten är upptagen väntar en tungviktsförfrågan först i upp till
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (standard `2000`, `0` inaktiverar väntan) på att en plats ska bli ledig
innan det återförsöksbara `503`-svaret skickas. Den begränsade väntan finns för att klienter av agenttyp
(OpenCode, Claude Code, Cursor) som förgrenar tunga underförfrågningar samtidigt ska serialisera anhopningen
i stället för att förbruka hela sin återförsöksbudget på omedelbara avvisningar och avbrytas mitt under uppgiften.
Aktuell beläggning för tungviktsreserveringar, den fastställda bytebudgeten och aktuell belastningsgrad
visas under `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — kontrollera dessa innan du ändrar någon miljövariabel.
Inställningar → Motståndskraft → Förfrågningskö → Samtidiga förfrågningar styr inte detta; den inställningen
styr en separat mekanism för leverantörens förfrågningskö.

**Åtgärd:**

1. Försök igen först. Klienter bör respektera `Retry-After` och använda backoff i stället för att omedelbart
   upprepa förfrågan.
2. Kontrollera `/api/monitoring/health` → `chatAdmission` innan du justerar något. `countCapEnabled:
false` och ett generöst `maxInflightBytes` innebär att den automatiskt härledda budgeten redan gör sitt
   jobb; en `pressureSeverity` på `high`/`critical` innebär att värddatorn verkligen har ont om minne —
   det kan inte åtgärdas med en miljövariabel för åtkomstkontroll, utan kräver mer RAM eller en mindre arbetsbelastning.
3. Endast om `/api/monitoring/health` visar att den automatiskt härledda budgeten verkligen är för liten för
   din värddator (sällsynt — den skalas redan från containrar till fysisk maskinvara) bör du åsidosätta den direkt med
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` i stället för att återgå till den äldre antalsgränsen för förfrågningar.

Se [referensen för miljövariabler](../reference/ENVIRONMENT.md#4-security--authentication)
för de auktoritativa inställningarna för åtkomstkontroll.

## Valfri feltaxonomi för RAG/LLM (16 problem)

Vissa OmniRoute-användare placerar gatewayen framför RAG- eller agentstackar. I sådana konfigurationer är det vanligt att se ett märkligt mönster: OmniRoute ser ut att fungera korrekt (leverantörerna är tillgängliga, routningsprofilerna är korrekta och inga hastighetsbegränsningsvarningar visas), men det slutliga svaret är ändå felaktigt.

I praktiken beror dessa incidenter vanligtvis på den efterföljande RAG-pipelinen, inte på själva gatewayen.

Om du vill ha en gemensam terminologi för att beskriva dessa fel kan du använda WFGY ProblemMap, en extern textresurs med MIT-licens som definierar sexton återkommande felmönster för RAG/LLM. På en övergripande nivå omfattar den:

- avvikelser i hämtning och trasiga kontextgränser
- tomma eller inaktuella index och vektorlager
- bristande överensstämmelse mellan inbäddningar och semantik
- problem med sammansättning av prompter och kontextfönster
- logiskt sammanbrott och överdrivet självsäkra svar
- fel i långa kedjor och agentsamordning
- minnes- och rollavvikelser i system med flera agenter
- problem med distributions- och initieringsordning

Idén är enkel:

1. När du undersöker ett felaktigt svar ska du registrera:
   - användarens uppgift och begäran
   - kombinationen av rutt och leverantör i OmniRoute
   - eventuell RAG-kontext som används i efterföljande led (hämtade dokument, verktygsanrop osv.)
2. Koppla incidenten till ett eller två WFGY ProblemMap-nummer (`No.1` … `No.16`).
3. Spara numret i din egen instrumentpanel, driftshandbok eller incidenthanterare tillsammans med OmniRoute-loggarna.
4. Använd motsvarande WFGY-sida för att avgöra om du behöver ändra din RAG-stack, hämtningskomponent eller routningsstrategi.

Den fullständiga texten och konkreta instruktioner finns här (MIT-licens, endast text):

[README för WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Du kan ignorera det här avsnittet om du inte kör RAG- eller agentpipelines bakom OmniRoute.

## Kända problem i v3.8.0

Problem som är specifika för version v3.8.0 och deras nuvarande lösningar. Om en korrigering inkluderas i en senare patch kommer posten att uppdateras eller tas bort.

### Autentiseringsfel för Devin CLI

**Symptom:**

- ”Devin CLI not found” eller ”auth failed” när Devin-baserade verktyg anropas
- CLI-körtidskontrollen rapporterar `installed=false`

**Orsaker:**

- `CLI_DEVIN_BIN` pekar på en sökväg som inte finns
- Devin CLI är inte installerat på värden

**Lösning:**

1. Installera Devin CLI för din plattform
2. Ange `CLI_DEVIN_BIN=/usr/local/bin/devin` (eller den faktiska sökvägen) i `.env`
3. Starta om OmniRoute och testa igen via **Instrumentpanel → CLI-verktyg**

### Modellens vänteperiod har fastnat (manuell återställning)

**Symptom:**

- En modell fortsätter att visas som satt i vänteperiod även efter att utgångstiden har passerat
- Begäranden fortsätter att hoppa över modellen vid kombinationsroutning trots att tidsstämpeln ligger bakåt i tiden

**Manuell återställning:**

- **Instrumentpanel:** **Inställningar → Modellernas vänteperioder** → klicka på **Återaktivera** på det berörda kortet
- **API:** `DELETE /api/resilience/model-cooldowns` med autentiseringshuvuden för administration

### Anslutningen till Command Code-leverantören misslyckas med 403

**Symptom:**

- 403 vid test av anslutningen till Command Code-leverantören
- Leverantörskortet visar ”unauthorized” efter att leverantören nyligen har lagts till

**Orsak:** OAuth-flödet slutfördes inte (återanropet togs inte emot eller token sparades inte).

**Lösning:**

- Kör `omniroute providers` från CLI för att starta OAuth-flödet på nytt, eller
- Kör OAuth igen via **Instrumentpanel → Leverantörer → Command Code → Återanslut**

### ModelScope returnerar aggressiva 429-vänteperioder

**Symptom:**

- Mycket korta eller omedelbara vänteperioder för ModelScope efter en mindre mängd begäranden
- Kombinationsroutningen hoppar över ModelScope tidigare än förväntat

**Orsak:** ModelScope skickar leverantörsspecifika `Retry-After`-huvuden. v3.8.0 innehåller särskild hantering för dessa huvuden, vilket innebär att äldre versioner feltolkar dem som allmänna indikationer på hastighetsbegränsning.

**Lösning:**

- Kontrollera att du använder v3.8.0 eller senare
- Kontrollera att reglaget `useUpstream429BreakerHints` är aktiverat under **Inställningar → Feltålighet**

### OMNIROUTE_WS_BRIDGE_SECRET saknas i produktion

**Symptom:**

- 401 för varje Codex/Responses-begäran via WebSocket-bryggan vid körning på en fjärransluten produktionsvärd
- WebSocket-bryggans handskakning stängs omedelbart efter anslutning

**Orsak:** Miljövariabeln `OMNIROUTE_WS_BRIDGE_SECRET` saknas i produktionsmiljön.

**Lösning:**

1. Generera en slumpmässig hemlighet: `openssl rand -hex 32`
2. Ange `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` i produktionsserverns miljö (och i alla klienter som kommunicerar med bryggan)
3. Starta om OmniRoute

### Responses API: bakgrundsläget nedgraderat till synkront

**Symptom:**

- Varning loggas: `background mode degraded to synchronous`
- En begäran med `background: true` returnerar ett normalt synkront svar i stället för ett handtag till ett bakgrundsjobb

**Orsak:** v3.8.0 nedgraderar avsiktligt `background: true` i Responses API till synkron körning och skickar samtidigt en varning. Fullständig asynkron bakgrundskörning är planerad för en framtida version.

**Lösning:**

- Anpassa klienten så att den anropar utan `background`, eller
- Vänta på en senare version som innehåller ett fullständigt asynkront bakgrundsläge (följ ändringsloggen)

## Långsam start/timeout för beredskap

Om CLI:t skriver ut `⚠ Server did not respond within 60s` men servern faktiskt
fungerar, är tidsbudgeten för beredskapskontrollen för kort för din miljö.

Detta inträffar ofta i Windows (antivirusprogram, filsystemsövervakare) eller i containrar
med hög arbetsbelastning vid start.

**Lösning – höj tidsbudgeten:**

```bash
# Via miljövariabel (kvarstår mellan starter):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuter
omniroute serve

# Via CLI-flagga (för ett enstaka tillfälle):
omniroute serve --ready-timeout 180000
```

Standardvärdet är 60 000 ms (60 s). Varningen är endast informativ. Servern
fortsätter att starta i bakgrunden och blir tillgänglig när starten har slutförts.

Fullständig information om `OMNIROUTE_READY_TIMEOUT_MS` finns i
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
