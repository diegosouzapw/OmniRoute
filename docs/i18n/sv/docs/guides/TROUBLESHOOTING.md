**Ny på OmniRoute?** Börja här — detta löser 90 % av problemen:

| Jag ser detta                 | Vad det betyder                                | Vad du ska göra                                                                                     |
| ----------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| "Can't connect"               | OmniRoute körs inte                            | Kör `omniroute` eller `docker restart omniroute`                                                    |
| "Invalid API key"             | Din nyckel är felaktig eller har gått ut       | Kopiera nyckeln på nytt från leverantörens webbplats                                                |
| "Rate limit exceeded"         | Du skickar för många förfrågningar             | Vänta 1 minut eller använd `model: "auto"` för automatisk reservlösning                             |

### Hastighetsbegränsning hos kostnadsfria leverantörer (429 / 400 / 401)

**Symptom**: När du använder `model: "auto"` med kostnadsfria leverantörer/leverantörer utan autentisering (opencode, auggie osv.) får du ibland `HTTP 429`, `400` eller `401` i stället för svar. Förfrågningarna lyckas om samma prompt skickas igen en kort stund senare, men automatisering (cron-jobb, agenter, skript) avbryts vid det första felet.

**Grundorsak**: Tre oberoende fellägen förstärker varandra:

1. **Leverantörens hastighetsbegränsning (`429`)**: Kostnadsfria nivåer kan tillämpa en kvot per tidsfönster. En skur av parallella anrop förbrukar den, så nästa förfrågan nekas tills tidsfönstret återställs.
2. **Trasig modell vid direktvidarebefordran (`400`/`401`)**: `auto/*`-pooler kan innehålla modeller för direktvidarebefordran från `opencode` som är registrerade i katalogen men saknar aktiva autentiseringsuppgifter (t.ex. `oc/north-mini-code-free` → `401`). Den automatiska routern provar en, misslyckas och felet sprids innan reservlösningen aktiveras.
3. **Förstärkning genom samtidighet (`429` under belastning)**: När flera agent-/cron-sessioner anropar `auto` samtidigt överstiger den sammanlagda förfrågningsfrekvensen vad kostnadsfria leverantörer tolererar, vilket gör att legitima anrop flaggas som missbruk.

**Verifierad lösning (rapporterad av communityn, 2026-08-10)**: justera tre miljövariabler så att rotation, samtidighet och reservlösningar absorberar svängningarna i den kostnadsfria nivån i stället för att krascha på grund av dem:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # hoppa till en annan modell/leverantör vid 400/401 (hoppar över trasiga modeller för direktvidarebefordran)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # explicit tak för samtidiga tungviktsförfrågningar (inte angivet som standard: inget tak för antal förfrågningar, se anmärkningen nedan)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # längre begränsad väntan på tungviktskapacitet i stället för ett omedelbart återförsökningsbart 503-fel
```

Ange dessa i OmniRoute-processens miljö (demonen, t.ex. via LaunchAgent plist eller `systemctl edit`) och starta sedan om OmniRoute. Rotationsflaggan är den enskilda åtgärd som ger störst effekt: den omvandlar ett definitivt fel till ett transparent nytt försök hos en fungerande leverantör i poolen.

**Anmärkning**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` begränsar hur många tungviktsförfrågningar — förfrågningar med lång kontext — som körs samtidigt; gränsen är en tillträdeskontroll, inte en hastighetsbegränsare för leverantören. **Uppdatering om #503-fanout:** denna variabel anges inte längre som standard (den tillämpas nu endast när den konfigureras explicit, som ovan) — tillträde för tungviktsförfrågningar styrs i stället av en automatiskt härledd bytebudget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) som anpassar sig efter värdens faktiska minnesgräns. En ny distribution bör därför få betydligt färre avvisningar med `503 chat_admission_busy` utan att denna variabel behöver anges alls; att uttryckligen ange den här fungerar fortfarande precis som dokumenterat. Explicita åsidosättningar av bytebudgeten begränsas till 8 MiB–2 GiB. Ett `413 body_exceeds_budget` är inte tillfälligt: öka bytebudgeten, sänk `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` eller höj processens minnesgräns. En bortkoppling på grund av `inflight_bytes_budget` beror på tillfällig resurskonkurrens och kan fortfarande försökas igen. Hastighetsbegränsningen per leverantör (`open-sse/services/rateLimitManager.ts`) styrs separat av `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` och `RATE_LIMIT_AUTO_ENABLE` — se `.env.example`.

**Så verifierar du att det fungerade**: kör din agent/cron två gånger i snabb följd och kontrollera att båda körningarna lyckas. Före korrigeringen kastar den andra körningen vanligtvis `429`/`401`. Efter korrigeringen görs nya försök transparent vid fel (om några uppstår), och anropet slutförs. Du kan också köra `curl /monitoring/health` och övervaka fältet `rateLimitedUntil` för leverantörsanslutningarna samt `circuitBreakers.providerBreakers[].state` för de berörda leverantörerna – tillståndet är något av `CLOSED`, `DEGRADED`, `OPEN` eller `HALF_OPEN` (se `src/shared/utils/circuitBreaker.ts`), och en leverantör som fortsätter att misslyckas växlar från `CLOSED → DEGRADED → OPEN` innan återställningsfönstret släpper igenom ett testanrop (`HALF_OPEN`).

**Om du fortfarande ser 429**: det aktiva kontot för den leverantören har faktiskt förbrukat hela sin _kvot_ (det handlar inte bara om frekvensbegränsning). Lägg till ett andra konto för samma leverantör i OmniRoute-instrumentpanelen → Providers → Accounts, eller använd även en annan kostnadsfri leverantör (t.ex. `routeway`, `auggie`). Rotation hjälper endast vid tillfälliga frekvensbegränsningsfel/400/401; en helt förbrukad kvot kräver en andra autentiseringsuppgift eller en annan leverantör.

**Om du ser 403 för visionsmodeller (`auto/vision`, `bazaarlink/*`)**: det anslutna kontot saknar en betalplan som omfattar vision, eller så har API-nyckeln otillräckliga behörigheter. Kontrollera i leverantörens instrumentpanel att nyckelns behörighetsomfång inkluderar vision/multimodal funktionalitet, eller anslut ett konto med en betalnivå och behåll det som mål för vision.

## npm install-varningar (ERESOLVE / peer / deprecated)

När du kör `npm install -g omniroute` kan du få mängder av varningar som `npm warn ERESOLVE`, meddelanden om peer-beroenden och `deprecated`-meddelanden. **Dessa är förväntade och ofarliga.** Installationen lyckades om du ser `added <N> packages` i utdata.

Använd OmniRoutes rekommenderade installationsform för att dölja varningarna om matchning av peer-beroenden:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` döljer endast `ERESOLVE` och meddelanden om peer-beroenden. Meddelanden om utfasning visas fortfarande eftersom de kommer från transitiva tredjepartspaket. De innebär inte att installationen misslyckades.

Varningarna orsakas av inaktuella intervall för peer-beroenden i tredjepartspaket som OmniRoute inte styr över:

1. **`marked-terminal` kräver `marked >=1 <16`, men `marked@18` hittades** — fungerar bra i praktiken; intervallet för peer-beroendet uppströms är bara inaktuellt.
2. **`deprecated prebuild-install@7.1.3`** — ett transitivt hjälppaket för hämtning av plattformsspecifika binärfiler. Det används inte
   för att installera den versionslåsta transportbindningen `wreq-js` och innebär inte att konfigurationen
   av webb-cookieleverantörens transport misslyckades.

**Ingen åtgärd behövs** — varningarna kan inte döljas helt utan att skapa egna förgreningar av uppströmspaketen.

## Gemini Web och Playwright Chromium

Om en Gemini Web-begäran returnerar `503` med ett meddelande om att Playwright Chromium
inte är installerat, finns npm-paketet men webbläsarbinären saknas.
Playwright håller avsiktligt webbläsarhämtningar åtskilda från installationen av
npm-paketet, så detta svar är förväntat tills webbläsaren har installerats.

För en global npm-installation installerar du Chromium från OmniRoute-paketets
katalog så att webbläsarcachen tillhör samma Playwright-installation:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Starta om OmniRoute efter installationen och försök sedan med Gemini Web-begäran igen. Om du
kör OmniRoute från en Docker-avbildning använder du `-web`-avbildningen (eller byggmålet `runner-web`),
som inkluderar Chromium och dess beroenden. Basavbildningen gör
inte det.

### Avast/AVG placerar `README.md` i karantän med `MD:HttpRequest-inf[Susp]`

**Detta är en falsk positiv varning. Ingenting är infekterat och ingen åtgärd krävs.**

Avast och AVG använder en heuristik som flaggar rena text-/Markdown-filer som innehåller många
länkar som ser ut som HTTP-förfrågningar. OmniRoutes `README.md` medföljer npm-paketet (den
listas i `package.json` → `files`), så vid en global installation hamnar den i
`node_modules/omniroute/README.md` — och den innehåller cirka 15 exempel med
`http://localhost:20128/...` (MCP:s HTTP-/SSE-slutpunkter, A2A:s `.well-known`-URL och
`curl`-utdrag). Denna länktäthet räcker för att utlösa heuristiken.

Om detta började först nyligen: filen har inte ändrat karaktär. README-filen utökades med
fler slutpunkter i tabellen (MCP HTTP + SSE + A2A lades till) och fler `curl`-exempel, vilket
gjorde att den passerade tröskelvärdet.

Filen är passiv dokumentation helt utan körbart innehåll. Du kan utan risk återställa den
från karantänen.

**Gör så här:**

1. **Stoppa aviseringarna** — undanta installationskatalogen i ditt antivirusprogram
   (Avast: Inställningar → Undantag) genom att lägga till sökvägen till din globala
   `node_modules`-katalog och/eller OmniRoutes datakatalog (`~/.omniroute/`).
2. **Rapportera den falska positiva varningen** — <https://www.avast.com/false-positive-file-form.php>
   och bifoga den karantänplacerade `README.md`. Detta är den lösning som hjälper alla,
   eftersom det är leverantörens heuristik som överreagerar på en textfil.

**Varför vi inte ”åtgärdar” detta från vår sida:** alla exempel använder `http://localhost`,
och localhost kan inte använda `https` utan besvär med självsignerade certifikat. Att
förvanska dokumentationen för att kringgå en leverantörs heuristik skulle försämra den för
alla läsare bara för att tillfredsställa en felaktig skanner.

### Kaspersky flaggar skrivbordsappen som `PDM:Trojan.Win32.Generic`

**Detta är en falsk positiv varning från en beteendebaserad heuristik. Ingenting är infekterat.**
Kasperskys prefix `PDM:` innebär att bedömningen kommer från dess Proactive Defense Module
(System Watcher), som bedömer vad installationsprogrammet _gör_ i stället för att jämföra
det med känd skadlig kod. När varningen utlöses ”återställer” Kaspersky hela installationen
— inklusive borttagning av filer som redan har skrivits — vilket gör att appen blir trasig
eller försvinner.

Filerna som flaggas är standardkomponenter i deklarerade beroenden med öppen källkod som
paketerats med skrivbordsappen, till exempel:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` och
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), biblioteket för
  webbläsarautomatisering som används för leverantörsinloggning i appen och
  webbläsarbaserad chatt.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — den versionslåsta inbyggda `wreq-js`-bindningen som används för webbläsarfingeravtryckad
  HTTP hos leverantörer som använder webbkakor (`<arch>` är `x64` eller `arm64`).

**Varför varningen utlöses:** installationsprogrammet för Windows är **ännu inte kodsignerat**,
så ett osignerat NSIS-installationsprogram har inget anseende och beteendebaserad heuristik
körs med maximal aggressivitet. I kombination med en paketerad inbyggd DLL-fil och hundratals
`.js`-filer som skrivs under `%LOCALAPPDATA%\Programs\OmniRoute` (inklusive paketkataloger
med hash-suffix från den fristående Next.js-versionen) räcker detta för att utlösa
heuristiken. Kodsignering är planerad; tills den är på plats kan detta återkomma i nya
versioner.

**Gör så här:**

1. **Verifiera först din hämtning** (detta utesluter att filen har manipulerats). Varje
   version publicerar `latest.yml`, vars `sha512`-fält (base64) omfattar
   installationsprogrammet `OmniRoute.Setup.<version>.exe`. Kör följande i PowerShell från
   mappen som innehåller installationsprogrammet:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Utdata måste stämma överens med `latest.yml` → `sha512`. Om de inte stämmer överens ska
   du ta bort filen och endast hämta den på nytt från
   [GitHubs versionssida](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Återställ + undanta** — återställ de återställda objekten från karantänen och lägg till
   ett undantag för `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Inställningar → Hot och
   undantag), och installera sedan om.
3. **Rapportera den falska positiva varningen** — <https://opentip.kaspersky.com/>.
   Rapporter om falska positiva varningar som skickas in av användare påskyndar faktiskt
   vitlistningen.

## Node.js-kompatibilitet

<a name="nodejs-compatibility"></a>

### Inloggningssidan kraschar eller visar felet "Module self-registration"

**Orsak:** Du kör en Node.js-version som ligger utanför OmniRoutes godkända lägstanivå för säker exekveringsmiljö. Det vanligaste fallet är att en äldre korrigeringsversion av Node 22 eller 24 används, som ligger under den säkerhetsnivå med korrigeringar som OmniRoute kräver.

**Symptom:**

- Inloggningssidan visar en tom skärm eller ett serverfel
- Konsolen visar `Error: Module did not self-register` eller liknande fel för systemnära bindningar
- Inloggningssidan visar en **orange varningsbanderoll** med din Node-version om exekveringsmiljön ligger utanför den säkra policy som stöds

**Åtgärd:**

1. Installera en Node.js LTS-version som stöds (rekommenderas: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Kontrollera din version: `node --version` ska visa `v24.0.0` eller senare i 24.x LTS-serien
3. Installera om OmniRoute: `npm install -g omniroute`
4. Starta om: `omniroute`

> **Säkra versioner som stöds:** `>=22.22.2 <23` eller `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) och Node.js 26 stöds fullt ut.

### npm v11+: `better-sqlite3` har inte installerats (modulen kan inte hittas)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Orsak:** npm v11 (som medföljer Node.js 24+) blockerar som standard installationsskript för valfria
beroenden. Eftersom `better-sqlite3` anges i `optionalDependencies`
och kräver systemnära kompilering (`node-gyp rebuild`) hoppar npm över det utan något meddelande.

**Symptom:**

- Servern kraschar vid start med `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` visar "No such file or directory"
- `npm ls better-sqlite3` visar `(empty)`

**Åtgärd:**

1. Godkänn installationsskripten och installera om:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Eller installera den förkompilerade versionen manuellt:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Kontrollera att den fungerar: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Orsak:** Efter en global `npm install -g omniroute` kan den systemnära binärfilen för `better-sqlite3` i paketet ha kompilerats för en annan arkitektur eller Node.js-ABI än den som körs lokalt. Detta är vanligt på macOS (både Apple Silicon och Intel) när den förkompilerade binärfilen inte matchar din miljö.

**Symptom:**

- Servern misslyckas omedelbart vid start med ett `dlopen`-fel
- Felet innehåller `slice is not valid mach-o file`
- Fullständigt exempel:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Åtgärd — kompilera om för din lokala miljö (ingen nedgradering av Node.js krävs):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Obs:** Detta kompilerar om den systemnära bindningen för din lokala Node.js-version och processorarkitektur, vilket löser binärinkompatibiliteten. Det officiellt stödda intervallet för exekveringsmiljön är **`>=22.22.2 <23` eller `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` i `src/shared/utils/nodeRuntimeSupport.ts`, i linje med fältet `engines` i `package.json`). Node.js 24.x LTS (Krypton) och Node.js 26 stöds fullt ut med `better-sqlite3` v12.x.

## Proxyproblem

<a name="proxy-issues"></a>

### Leverantörsvalideringen visar "fetch failed"

**Orsak:** Slutpunkten för validering av API-nycklar (`POST /api/providers/validate`) kringgick tidigare proxykonfigurationen, vilket orsakade fel i miljöer som kräver proxy-routing.

**Åtgärd (v3.5.5+):** Detta är nu åtgärdat. Leverantörsvalideringen dirigeras genom `runWithProxyContext` och tar automatiskt hänsyn till proxyinställningar på leverantörsnivå och global nivå.

### Hälsokontrollen av token misslyckas med "fetch failed"

**Orsak:** Bakgrundsuppdateringen av OAuth-token löste inte proxykonfigurationen för varje anslutning.

**Åtgärd (v3.5.5+):** Schemaläggaren för hälsokontroll av token löser nu proxykonfigurationen för varje anslutning innan ett uppdateringsförsök görs. Uppdatera till v3.5.5+.

### SOCKS5-proxyn returnerar "invalid onRequestStart method"

**Orsak:** I Node.js 22 är dispatchern i undici@8 inkompatibel med Nodes inbyggda `fetch()`-implementering.

**Åtgärd (v3.5.5+):** OmniRoute använder nu undicis egen `fetch()`-funktion när en proxydispatcher är aktiv, vilket säkerställer ett konsekvent beteende. Uppdatera till v3.5.5+.

### MITM-proxy under WSL: skrivbordsappar på Windows-värden fångas inte upp

**Orsak:** MITM-proxyn och dess CA-certifikat installeras i miljön där OmniRoute körs. Under WSL är den miljön Linux-gästen, medan AI-skrivbordsapparna (Kiro, Trae, Copilot, Zed, …) körs på Windows-värden. Värdapparna litar inte på gästens certifikatarkiv och dirigeras inte genom gästens systemproxy, så uppfångning av skrivbordsappar aktiveras inte där.

**Rekommendation:** Kör OmniRoute direkt i samma operativsystem som skrivbordsapparna du vill fånga upp (Windows för Windows-appar; motsvarande gäller för macOS/Linux). Att behålla OmniRoute i WSL samtidigt som värdappar används som mål kräver att det genererade CA-certifikatet manuellt görs betrott på Windows-värden och att nätverks-/proxyinställningarna för varje värdapp pekas mot WSL-proxyns slutpunkt – en bräcklig konfiguration som inte stöds.

## Leverantörsproblem

### "Language model did not provide messages"

**Orsak:** Leverantörens kvot är förbrukad.

**Åtgärd:**

1. Kontrollera kvotspåraren i kontrollpanelen
2. Använd en kombination med reservnivåer
3. Byt till en billigare kostnadsfri nivå

### Hastighetsbegränsning

**Orsak:** Prenumerationskvoten är förbrukad.

**Åtgärd:**

- Lägg till reservalternativ: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Använd GLM/MiniMax som ett billigt reservalternativ

### OAuth-token har löpt ut

OmniRoute uppdaterar token automatiskt. Om problemen kvarstår:

1. Kontrollpanelen → Leverantör → Anslut igen
2. Ta bort leverantörsanslutningen och lägg till den igen

### Flera Kiro-konton: det andra kontot ogiltigförklarar det första

**Orsak:** Kiros backend tillåter endast en aktiv session per OIDC-klientregistrering.
När två konton delar samma registrerade klient (anslutningar som importerades före v3.8.0)
ogiltigförklarar uppdateringen av token för det ena kontot det andra kontots uppdateringstoken.

**Åtgärd (v3.8.0+):** Importera de berörda anslutningarna igen.
Från och med v3.8.0 registrerar varje ny Kiro-anslutning som skapas via **Importera token**,
**social inloggning med Google/GitHub** eller **Automatisk import** automatiskt en egen
dedikerad OIDC-klient. Anslutningen är därför helt isolerad, och uppdatering av ett
konto påverkar inte något annat konto.

Anslutningar som importerades _före_ v3.8.0 har ingen klientregistrering per anslutning.
Dessa anslutningar fortsätter att använda den delade slutpunkten för uppdatering via social autentisering.
För att få isolering tar du bort den gamla anslutningen via Kontrollpanelen → Leverantörer och lägger till den igen
via något av de tre importflödena.

Fullständig information och stegvisa instruktioner för att lägga till två Kiro-konton sida vid sida
finns i [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Docker-problem

### Docker IPv6/återställning av anslutning

<a name="docker-ipv6"></a>

**Symptom:** `curl http://localhost:20128/v1/models` returnerar `curl: (56) Recv failure: Connection reset by peer`. Kontrollpanelen och oautentiserade slutpunkter fungerar, men autentiserade slutpunkter misslyckas — det ser ut som ett autentiseringsproblem men är det inte.

**Orsak:** `docker run -p 20128:20128` publicerar på både `0.0.0.0` (IPv4) och `::` (IPv6), men processen inuti containern lyssnar endast på IPv4. På värdar där `localhost` först matchas mot `::1` hamnar anslutningen på den publicerade IPv6-porten utan någon bakomliggande lyssnare → anslutningen återställs.

**Åtgärd:**

1. **Snabbdiagnostik:** Kör `curl -4 http://localhost:20128/v1/models`. Om det fungerar med `-4` men misslyckas utan flaggan har du en IPv6-bindningskonflikt.
2. **Permanent åtgärd:** Bind uttryckligen till IPv4 genom att använda `-p 127.0.0.1:20128:20128` i ditt `docker run`-kommando:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Detta framtvingar IPv4-bindningen och förhindrar dessutom att proxyn exponeras på värdens samtliga gränssnitt.

## Inställningar för motståndskraft

### Automatisk hastighetsbegränsning utlöses inte

- Automatisk hastighetsbegränsning gäller endast leverantörer med API-nyckel (inte OAuth/prenumeration)
- Kontrollera att **Inställningar → Motståndskraft → Leverantörsprofiler** har automatisk hastighetsbegränsning aktiverad
- Kontrollera om leverantören returnerar statuskoderna `429` eller rubrikerna `Retry-After`

### Justera exponentiell backoff

Leverantörsprofiler stöder följande inställningar:

- **Grundfördröjning** — Inledande väntetid efter det första felet (standard: 1s)
- **Maximal fördröjning** — Övre gräns för väntetiden (standard: 30s)
- **Multiplikator** — Hur mycket fördröjningen ska ökas per efterföljande fel (standard: 2x)

### Skydd mot thundering herd

När många samtidiga begäranden når en hastighetsbegränsad leverantör använder OmniRoute mutex + automatisk hastighetsbegränsning för att serialisera begäranden och förhindra kaskadfel. Detta sker automatiskt för leverantörer med API-nyckel.

### Chattbegäranden misslyckas med 503 / chat_admission_busy

**Symptom:**

- Slutpunkten för chattkompletteringar returnerar ett återförsökbart `503`-svar vars felkod är
  `chat_admission_busy`.
- Svaret innehåller `Retry-After`. Sedan #12135 härleds värdet från den observerade
  beläggningen — det större värdet av det `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`-fönster som begäran redan
  har väntat och den tid som de aktuella tungviktsleaserna har hållits — avrundat uppåt till hela
  sekunder och begränsat till 60. Vid en inaktiv spärr behålls de historiska miniminivåerna: 2 sekunder för den
  bytebaserade sökvägen och 1 sekund för den strukturbaserade sökvägen (som även innehåller
  `reason: "structure_limit"`).
- Detta kan inträffa medan en annan tungviktschatt eller långvarig strömmande respons fortfarande
  pågår.

Den bytebaserade svarstexten är:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Det strukturbaserade svaret använder samma typ och kod, med meddelandet
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
och `reason: "structure_limit"`.
Med standardtröskelvärdena betraktas en begäran som strukturellt tung när den har minst `200` meddelanden,
minst `64` verktyg eller minst `32,000` uppskattade token, eller när den begränsade strukturuppskattningen
uttömmer sina gränser på `10,000` besökta noder eller djupet `12`.

**Orsak:** Detta är avsiktlig lastreducering i OmniRoute, inte ett fel hos en uppströmsleverantör.
Varje process använder en processlokal spärr för att reservera begränsad tungviktskapacitet innan en stor
begärandetext behålls och parsas. En tungviktslease förblir reserverad under hela livslängden för ett SSE-
svar.

**#503-fan-out:** före den här korrigeringen begränsade spärren samtidigheten till ett fast ANTAL begäranden
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, standard `1`) oavsett värddatorns minne, vilket gjorde att
fan-out från kodningsagenter (flera underagenter/CLI:er, med texter som rutinmässigt är > 256 KB) kollapsade till en effektiv
samtidighet på ~1 och gav 503-fel under helt normal belastning. Spärren självjusteras nu: den styrs
av en automatiskt härledd BYTE-budget för inläsning (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) som dimensioneras utifrån
processens faktiska minnesgräns, och den tar även hänsyn till en aktuell signal för resurstryck — så den
reducerar endast lasten när värddatorn verkligen utsätts för minnestryck, inte enbart för att fler än en
tung begäran anlände samtidigt. Den gamla antalsgränsen (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
respekteras fortfarande, men endast om du uttryckligen anger den.

När kapaciteten är upptagen väntar en tungviktsbegäran först i upp till
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (standard `2000`, `0` inaktiverar väntan) på att en plats ska frigöras
innan det återförsökbara `503`-svaret returneras. Den begränsade väntetiden finns för att agentbaserade klienter
(OpenCode, Claude Code, Cursor), som sprider tunga underbegäranden samtidigt, ska serialisera belastningstoppen
i stället för att förbruka hela sin återförsöksbudget på omedelbara avvisningar och avbrytas mitt i uppgiften.
Aktuell beläggning för tungviktsleaser, den fastställda bytebudgeten och det aktuella resurstryckets allvarlighetsgrad
visas under `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — kontrollera dessa innan du ändrar någon miljövariabel.
Inställningar → Motståndskraft → Begärandekö → Samtidiga begäranden styr inte detta; den inställningen
styr en separat kömekanism för leverantörsbegäranden.

**Korrigering:**

1. Försök igen först. Klienter bör respektera `Retry-After` och använda backoff i stället för att omedelbart
   upprepa begäran.
2. Kontrollera `/api/monitoring/health` → `chatAdmission` innan du justerar något. `countCapEnabled:
false` och ett generöst `maxInflightBytes` innebär att den automatiskt härledda budgeten redan gör sitt
   jobb; en `pressureSeverity` på `high`/`critical` innebär att värddatorn faktiskt har ont om minne —
   det kan inte åtgärdas med en miljövariabel för insläpp, utan kräver mer RAM eller en mindre arbetsbelastning.
3. Endast om `/api/monitoring/health` visar att den automatiskt härledda budgeten verkligen är för liten för
   din värddator (sällsynt — den skalas redan från container till fysisk server) bör du åsidosätta den direkt med
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` i stället för att återgå till den äldre antalsgränsen för begäranden.

Se [referensen för miljövariabler](../reference/ENVIRONMENT.md#4-security--authentication)
för de auktoritativa insläppsinställningarna.

## Valfri felklassificering för RAG/LLM (16 problem)

Vissa OmniRoute-användare placerar gatewayen framför RAG- eller agentstackar. I sådana konfigurationer är det vanligt att se ett märkligt mönster: OmniRoute verkar fungera korrekt (leverantörerna är tillgängliga, routningsprofilerna är korrekta och inga varningar om hastighetsbegränsningar visas), men det slutliga svaret är ändå felaktigt.

I praktiken kommer dessa incidenter vanligtvis från den efterföljande RAG-pipelinen och inte från själva gatewayen.

Om du vill ha en gemensam vokabulär för att beskriva dessa fel kan du använda WFGY ProblemMap, en extern textresurs med MIT-licens som definierar sexton återkommande felmönster för RAG/LLM. På en övergripande nivå omfattar den:

- avvikelser i hämtning och brutna kontextgränser
- tomma eller inaktuella index och vektorlager
- bristande överensstämmelse mellan inbäddningar och semantik
- problem med promptsammansättning och kontextfönster
- logikkollaps och överdrivet självsäkra svar
- fel i långa kedjor och agentsamordning
- avvikelser i minne och roller för flera agenter
- problem med driftsättning och uppstartsordning

Idén är enkel:

1. När du undersöker ett felaktigt svar ska du registrera:
   - användarens uppgift och begäran
   - routen eller leverantörskombinationen i OmniRoute
   - eventuell RAG-kontext som används nedströms (hämtade dokument, verktygsanrop osv.)
2. Koppla incidenten till ett eller två WFGY ProblemMap-nummer (`No.1` … `No.16`).
3. Lagra numret i din egen instrumentpanel, driftshandbok eller incidenthanterare tillsammans med OmniRoute-loggarna.
4. Använd motsvarande WFGY-sida för att avgöra om du behöver ändra din RAG-stack, hämtningskomponent eller routningsstrategi.

Den fullständiga texten och konkreta anvisningar finns här (MIT-licens, endast text):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Du kan ignorera det här avsnittet om du inte kör RAG- eller agentpipelines bakom OmniRoute.

## Kända problem i v3.8.0

Problem som är specifika för version v3.8.0 och deras aktuella lösningar. Om en korrigering införs i en senare patch kommer posten att uppdateras eller tas bort.

### Autentiseringsfel i Devin CLI

**Symptom:**

- "Devin CLI not found" eller "auth failed" när Devin-baserade verktyg anropas
- CLI-kontrollen vid körning rapporterar `installed=false`

**Orsaker:**

- `CLI_DEVIN_BIN` pekar på en sökväg som inte finns
- Devin CLI är inte installerat på värden

**Åtgärd:**

1. Installera Devin CLI för din plattform
2. Ange `CLI_DEVIN_BIN=/usr/local/bin/devin` (eller den faktiska sökvägen) i `.env`
3. Starta om OmniRoute och testa igen från **Instrumentpanel → CLI-verktyg**

### Modellens nedkylningsperiod har fastnat (manuell återställning)

**Symptom:**

- En modell visas fortfarande som nedkyld även efter att utgångstiden har passerat
- Begäranden fortsätter att hoppa över modellen i kombinationsroutningen trots att tidsstämpeln ligger i det förflutna

**Manuell återställning:**

- **Instrumentpanel:** **Inställningar → Modellnedkylningar** → klicka på **Återaktivera** på det berörda kortet
- **API:** `DELETE /api/resilience/model-cooldowns` med autentiseringshuvuden för administration

### Anslutningen till Command Code-leverantören misslyckas med 403

**Symptom:**

- 403 vid test av anslutningen till Command Code-leverantören
- Leverantörskortet visar "unauthorized" efter att leverantören nyligen har lagts till

**Orsak:** OAuth-flödet slutfördes inte (återanropet mottogs inte eller token sparades inte).

**Åtgärd:**

- Kör `omniroute providers` från CLI för att starta OAuth-flödet igen, eller
- Kör OAuth igen från **Instrumentpanel → Leverantörer → Command Code → Återanslut**

### ModelScope returnerar aggressiva 429-nedkylningsperioder

**Symptom:**

- Mycket korta eller omedelbara nedkylningsperioder för ModelScope efter en mindre skur av begäranden
- Kombinationsroutningen hoppar över ModelScope tidigare än förväntat

**Orsak:** ModelScope skickar leverantörsspecifika `Retry-After`-huvuden. v3.8.0 innehåller särskild hantering för dessa huvuden, vilket innebär att äldre versioner feltolkar dem som allmänna indikationer om hastighetsbegränsning.

**Åtgärd:**

- Kontrollera att du använder v3.8.0 eller senare
- Kontrollera att reglaget `useUpstream429BreakerHints` är aktiverat under **Inställningar → Motståndskraft**

### OMNIROUTE_WS_BRIDGE_SECRET saknas i produktion

**Symptom:**

- 401 för varje Codex/Responses-begäran till WebSocket-bryggan vid körning på en fjärrvärd i produktionsmiljön
- WebSocket-bryggans handskakning stängs omedelbart efter anslutning

**Orsak:** Miljövariabeln `OMNIROUTE_WS_BRIDGE_SECRET` saknas i produktionsmiljön.

**Åtgärd:**

1. Generera en slumpmässig hemlighet: `openssl rand -hex 32`
2. Ange `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` i produktionsserverns miljö (och i alla klienter som kommunicerar med bryggan)
3. Starta om OmniRoute

### Responses API: bakgrundsläget har degraderats till synkront läge

**Symptom:**

- Varning loggas: `background mode degraded to synchronous`
- En begäran med `background: true` returnerar ett normalt synkront svar i stället för ett handtag till ett bakgrundsjobb

**Orsak:** v3.8.0 degraderar avsiktligt `background: true` i Responses API till synkron körning samtidigt som en varning genereras. Fullständig asynkron bakgrundskörning är planerad för en framtida version.

**Åtgärd:**

- Anpassa klienten så att anropet görs utan `background`, eller
- Vänta på en senare version med fullständigt asynkront bakgrundsläge (följ ändringsloggen)

## Långsam start/timeout för beredskap

Om CLI:t skriver ut `⚠ Server did not respond within 60s` men servern faktiskt
fungerar, är tidsbudgeten för beredskapskontrollen för kort för din miljö.

Detta händer ofta i Windows (antivirusprogram, filsystemsövervakare) eller i containrar
med hög arbetsbelastning vid start.

**Lösning – öka tidsbudgeten:**

```bash
# Via miljövariabel (kvarstår mellan starter):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuter
omniroute serve

# Via CLI-flagga (endast denna gång):
omniroute serve --ready-timeout 180000
```

Standardvärdet är 60 000 ms (60 s). Varningen är endast informativ; servern
fortsätter att starta i bakgrunden och blir tillgänglig när uppstarten är klar.

Se [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) för fullständig
information om `OMNIROUTE_READY_TIMEOUT_MS`.
