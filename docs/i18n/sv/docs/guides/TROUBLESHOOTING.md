### Hastighetsbegränsning hos kostnadsfria leverantörer (429 / 400 / 401)

**Symptom**: När du använder `model: "auto"` med kostnadsfria leverantörer/leverantörer utan autentisering (opencode, auggie osv.) får du periodvis `HTTP 429`, `400` eller `401` i stället för svar. Förfrågningarna lyckas när samma prompt skickas på nytt en kort stund senare, men automatisering (cron-jobb, agenter, skript) avbryts vid det första felet.

**Grundorsak**: Tre oberoende fellägen samverkar:

1. **Leverantörens hastighetsgräns (`429`)**: Kostnadsfria nivåer kan tillämpa en kvot per tidsfönster. En skur av parallella anrop förbrukar den, vilket gör att nästa förfrågan avvisas tills tidsfönstret återställs.
2. **Trasig modell vid direktvidarebefordran (`400`/`401`)**: `auto/*`-pooler kan innehålla modeller för direktvidarebefordran från `opencode` som är registrerade i katalogen men saknar giltiga autentiseringsuppgifter (t.ex. `oc/north-mini-code-free` → `401`). Den automatiska routern provar en, misslyckas och felet sprids innan reservlösningen hinner aktiveras.
3. **Förstärkning genom samtidighet (`429` under belastning)**: När flera agent-/cron-sessioner använder `auto` samtidigt överstiger den sammanlagda förfrågningsfrekvensen vad kostnadsfria leverantörer tolererar, vilket gör att legitima anrop flaggas som missbruk.

**Verifierad lösning (rapporterad av communityn, 2026-08-10)**: justera tre miljövariabler så att rotation, samtidighet och reservlösningar hanterar variationerna i den kostnadsfria nivån i stället för att avbrytas av dem:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # byt till en annan modell/leverantör vid 400/401 (hoppar över trasiga modeller för direktvidarebefordran)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # uttrycklig övre gräns för tunga förfrågningar (inte angiven som standard: ingen gräns för antalet förfrågningar, se anmärkningen nedan)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # höj den begränsade väntetiden över standardvärdet för RATE_LIMIT_MAX_WAIT_MS för långsamma uppströmsleverantörer
```

Ställ in dessa i OmniRoute-processens miljö (daemonen, t.ex. via LaunchAgent-plist-filen eller `systemctl edit`) och starta sedan om OmniRoute. Rotationsflaggan är den enskilt mest effektfulla inställningen: den omvandlar ett definitivt fel till ett transparent nytt försök hos en fungerande leverantör i poolen.

**Anmärkning**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` begränsar hur många tunga förfrågningar — med lång kontext — som körs samtidigt; gränsen är en insläppsport, inte en hastighetsbegränsare för leverantören. **Uppdatering om #503-fanout:** den här variabeln anges inte längre som standard (den gäller nu endast när den uttryckligen konfigureras, som ovan) — insläpp av tunga förfrågningar styrs i stället av en automatiskt beräknad bytebudget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) som anpassar sig efter värddatorns faktiska minnesgräns. En ny distribution bör därför få betydligt färre avvisningar med `503 chat_admission_busy` utan att variabeln behöver anges alls; om den anges uttryckligen här fungerar den fortfarande exakt enligt dokumentationen. Uttryckliga åsidosättningar av bytebudgeten begränsas till 8 MiB–2 GiB. Ett `413 body_exceeds_budget` är inte tillfälligt: öka bytebudgeten, sänk `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` eller höj processens minnesgräns. En avvisning av typen `inflight_bytes_budget` beror på tillfällig resurskonkurrens och kan fortfarande försökas igen. Hastighetsbegränsningen per leverantör (`open-sse/services/rateLimitManager.ts`) styrs separat av `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` och `RATE_LIMIT_AUTO_ENABLE` — se `.env.example`.

**Så verifierar du att det fungerade**: kör din agent/cron två gånger i snabb följd och bekräfta att båda körningarna lyckas. Före korrigeringen genererar den andra körningen vanligtvis `429`/`401`. Efter korrigeringen görs nya försök automatiskt vid eventuella fel och anropet slutförs. Du kan även köra `curl /monitoring/health` och övervaka fältet `rateLimitedUntil` för leverantörsanslutningarna samt `circuitBreakers.providerBreakers[].state` för de berörda leverantörerna – tillståndet är något av `CLOSED`, `DEGRADED`, `OPEN` eller `HALF_OPEN` (se `src/shared/utils/circuitBreaker.ts`), och en leverantör som fortsätter att misslyckas växlar från `CLOSED → DEGRADED → OPEN` innan återställningsintervallet släpper igenom ett testanrop (`HALF_OPEN`).

**Om du fortfarande får 429**: det aktiva kontot för den leverantören har faktiskt förbrukat hela sin _kvot_ (det handlar inte bara om anropsfrekvensen). Lägg till ett andra konto för samma leverantör i OmniRoute-kontrollpanelen → Leverantörer → Konton, eller lägg till en annan kostnadsfri leverantör (t.ex. `routeway`, `auggie`). Rotation hjälper endast vid tillfälliga frekvensbegränsningar/400/401; en helt förbrukad kvot kräver en andra autentiseringsuppgift eller en annan leverantör.

**Om du får 403 för visionsmodeller (`auto/vision`, `bazaarlink/*`)**: det anslutna kontot saknar ett betalabonnemang som inkluderar vision, eller så har API-nyckeln otillräckliga behörigheter. Kontrollera i leverantörens kontrollpanel att nyckelns behörighetsomfång inkluderar vision/multimodal funktionalitet, eller anslut ett konto med ett betalabonnemang och behåll det som mål för vision.

## Varningar vid npm install (ERESOLVE / peer / deprecated)

När du kör `npm install -g omniroute` kan du få en mängd varningar som `npm warn ERESOLVE`, meddelanden om peer-beroenden och `deprecated`. **Dessa är förväntade och ofarliga.** Installationen lyckades om du ser `added <N> packages` i utdata.

Använd OmniRoutes rekommenderade installationskommando för att undertrycka varningar om matchning av peer-beroenden:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` undertrycker endast `ERESOLVE` och meddelanden om peer-beroenden. Meddelanden om utfasning visas fortfarande eftersom de kommer från transitiva tredjepaket. De betyder inte att installationen misslyckades.

Varningarna kommer från inaktuella versionsintervall för peer-beroenden i tredjepaket som OmniRoute inte styr över:

1. **`marked-terminal` kräver `marked >=1 <16`, men `marked@18` hittades** — fungerar bra i praktiken; versionsintervallet för peer-beroendet uppströms är helt enkelt inaktuellt.
2. **`deprecated prebuild-install@7.1.3`** — ett transitivt hjälpverktyg för hämtning av plattformsspecifika binärfiler. Det används inte
   för att installera den låsta transportbindningen `wreq-js` och betyder inte att transportkonfigurationen
   för leverantören av webbkakor misslyckades.

**Ingen åtgärd krävs** — varningarna kan inte undertryckas helt utan att skapa egna varianter av uppströmspaketen.

## Varning om blockerade npm-installationsskript (global installation)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

När du kör `npm install -g omniroute` blockerar nyare npm-versioner (v11+ och v12+) paketens livscykelskript som standard och visar en varning om installationsskript:

```
npm warn install-scripts 7 paket hade installationsskript som blockerades eftersom de inte omfattas av allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Kan den här varningen ignoreras?

**Delvis, men det rekommenderas inte att köra utan skript.** OmniRoute innehåller robusta reservlösningar: om de plattformsspecifika bindningarna för `better-sqlite3` inte kan läsas in från det fristående paketet växlar programmet till alternativa drivrutiner som `node:sqlite` eller `sql.js` (se [Matchning av SQLite-körmiljö](../ops/SQLITE_RUNTIME.md)). Servern startar ändå, men användning av WASM-reservlösningar som `sql.js` inaktiverar SQLite-läget WAL (Write-Ahead Logging) och ökar minnesanvändningen samt belastningen från disksynkronisering.

### Vilka skript krävs egentligen?

Alla blockerade skript är inte nödvändiga för att köra OmniRoute:

- **Nödvändiga (`omniroute`, `better-sqlite3`):** OmniRoute körs från ett fristående Next.js-programpaket (`dist/`). Under installationen hämtar eller kompilerar npm den värdspecifika, plattformsspecifika SQLite-drivrutinen i `node_modules/better-sqlite3/` på toppnivå. OmniRoutes `postinstall`-skript (`scripts/build/postinstall.mjs`) verifierar och kopierar sedan dessa värdspecifika binärfiler till `dist/node_modules/` så att den fristående servern kan komma åt dem. Om OmniRoutes `postinstall`-skript blockeras hoppas det här kopieringssteget över.
- **Valfria/transitiva (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** Dessa är byggverktyg, bevakningsverktyg eller verktyg för systemets nyckelring. Om de tillåts förhindras byggvarningar, men de krävs inte för den grundläggande routningsfunktionen.
- **Undantaget (`onnxruntime-node`):** Ett valfritt beroende för lokala AI-inbäddningar som **inte** krävs för att köra OmniRoute. Dess `postinstall`-skript hämtar cirka 300 MB CUDA-resurser från NuGet. Ta inte med det i tillåtelselistan om du inte uttryckligen avser att använda lokal ONNX-acceleration på maskinvara som stöds.

### Rekommenderad lösning

För att tillåta de nödvändiga installationsskripten under en global installation och undertrycka varningarna anger du `--allow-scripts` för OmniRoute och dess plattformsspecifika beroenden:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

Alternativt kan du konfigurera detta permanent för alla globala installationer i ditt användarkonto:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### Verifiera installationen

Efter installationen kör du det inbyggda diagnostikverktyget för att kontrollera att de plattformsspecifika bindningarna och körmiljön fungerar korrekt:

```bash
omniroute doctor
```

## Falska antiviruslarm

<a name="antivirus-false-positives"></a>

### Avast/AVG placerar `README.md` i karantän med `MD:HttpRequest-inf[Susp]`

**Detta är ett falskt positivt resultat. Ingenting är infekterat och ingen åtgärd krävs.**

Avast och AVG använder en heuristisk analys som flaggar rena text-/Markdown-filer som innehåller många
länkar som liknar HTTP-förfrågningar. OmniRoutes `README.md` medföljer npm-paketet (den
anges i `package.json` → `files`), så vid en global installation hamnar den i
`node_modules/omniroute/README.md` — och den innehåller cirka 15 exempel med
`http://localhost:20128/...` (HTTP-/SSE-slutpunkterna för MCP, A2A-adressen under
`.well-known` och `curl`-exempel). Denna länktäthet är tillräcklig för att utlösa den
heuristiska analysen.

Om detta började inträffa först nyligen: filens karaktär har inte förändrats. README-filen fick
en utökad tabell med slutpunkter (MCP HTTP + SSE + A2A lades till) och fler `curl`-exempel,
vilket gjorde att den passerade tröskelvärdet.

Filen är passiv dokumentation helt utan körbart innehåll. Du kan utan risk återställa den
från karantänen.

**Så här gör du:**

1. **Stoppa aviseringarna** — undanta installationskatalogen i ditt antivirusprogram
   (Avast: Inställningar → Undantag) genom att lägga till sökvägen till din globala
   `node_modules`-katalog och/eller OmniRoutes datakatalog (`~/.omniroute/`).
2. **Rapportera det falska positiva resultatet** — <https://www.avast.com/false-positive-file-form.php>,
   och bifoga den karantänplacerade `README.md`. Detta är den lösning som hjälper alla,
   eftersom det är leverantörens heuristiska analys som överreagerar på en textfil.

**Varför vi inte ”åtgärdar” detta på vår sida:** alla exempel använder `http://localhost`,
och localhost kan inte använda `https` utan besvär med självsignerade certifikat. Att
förvanska dokumentationen för att kringgå en leverantörs heuristiska analys skulle försämra
den för alla läsare bara för att tillgodose ett fel i ett skanningsverktyg.

### Kaspersky flaggar skrivbordsappen som `PDM:Trojan.Win32.Generic`

**Detta är ett falskt positivt resultat från en beteendebaserad heuristisk analys. Ingenting är infekterat.**
Kasperskys prefix `PDM:` innebär att bedömningen kommer från dess Proactive Defense Module
(System Watcher), som bedömer vad installationsprogrammet _gör_ i stället för att jämföra
det mot känd skadlig kod. När analysen utlöses ”återställer” Kaspersky hela installationen
— och raderar filer som redan har skrivits — vilket gör att appen blir trasig eller
försvinner.

Filerna som flaggas är standardkomponenter från deklarerade beroenden med öppen källkod som
paketerats med skrivbordsappen, till exempel:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` och
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), biblioteket för
  webbläsarautomatisering som används för leverantörsinloggning i appen och
  webbläsarbaserad chatt.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — den versionslåsta inbyggda `wreq-js`-bindningen som används för webbläsarfingeravtryckad
  HTTP hos leverantörer som använder webbkakor (`<arch>` är `x64` eller `arm64`).

**Varför analysen utlöses:** Windows-installationsprogrammet är **ännu inte kodsignerat**,
så ett osignerat NSIS-installationsprogram har inget anseende och beteendebaserade
heuristiska analyser körs med maximal aggressivitet. I kombination med en paketerad inbyggd
DLL-fil och hundratals `.js`-filer som skrivs under
`%LOCALAPPDATA%\Programs\OmniRoute` (inklusive paketskataloger med hash-suffix från det
fristående Next.js-bygget) är detta tillräckligt för att utlösa den heuristiska analysen.
Kodsignering är planerad; tills den är på plats kan problemet återkomma i nya utgåvor.

**Så här gör du:**

1. **Verifiera först din nedladdning** (detta utesluter att filen har manipulerats). Varje
   utgåva publicerar `latest.yml`, vars `sha512`-fält (base64) omfattar installationsfilen
   `OmniRoute.Setup.<version>.exe`. Kör följande i PowerShell från mappen som innehåller
   installationsfilen:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Utdata måste matcha `latest.yml` → `sha512`. Om de inte matchar ska du radera filen och
   endast ladda ned den igen från [GitHubs utgivningssida](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Återställ + undanta** — återställ de borttagna objekten från karantänen och lägg till
   ett undantag för `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Inställningar → Hot och
   undantag) och installera sedan om.
3. **Rapportera det falska positiva resultatet** — <https://opentip.kaspersky.com/>.
   FP-rapporter från användare påskyndar verkligen vitlistningen.

## Node.js-kompatibilitet

<a name="nodejs-compatibility"></a>

### Inloggningssidan kraschar eller visar felet "Module self-registration"

**Orsak:** Du kör en Node.js-version som inte uppfyller OmniRoutes godkända säkra miniminivå för körmiljön. Det vanligaste fallet är att en äldre korrigeringsversion av Node 22 eller 24 används som ligger under den korrigerade säkerhetsnivå som OmniRoute kräver.

**Symtom:**

- Inloggningssidan visar en tom skärm eller ett serverfel
- Konsolen visar `Error: Module did not self-register` eller liknande fel för systemspecifika bindningar
- Inloggningssidan visar en **orange varningsbanderoll** med din Node-version om körmiljön inte uppfyller den säkra policy som stöds

**Lösning:**

1. Installera en Node.js LTS-version som stöds (rekommenderat: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Kontrollera din version: `node --version` ska visa `v24.0.0` eller senare i 24.x LTS-serien
3. Installera om OmniRoute: `npm install -g omniroute`
4. Starta om: `omniroute`

> **Säkra versioner som stöds:** `>=22.22.2 <23` eller `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) och Node.js 26 stöds fullt ut.

### npm v11+: `better-sqlite3` är inte installerat (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Orsak:** npm v11 (som medföljer Node.js 24+) blockerar som standard installationsskript för valfria
beroenden. Eftersom `better-sqlite3` anges i `optionalDependencies`
och kräver systemspecifik kompilering (`node-gyp rebuild`) hoppar npm över det utan något meddelande.

**Symtom:**

- Servern kraschar vid start med `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` visar "No such file or directory"
- `npm ls better-sqlite3` visar `(empty)`

**Lösning:**

1. Godkänn installationsskripten och installera om:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Eller installera det förkompilerade paketet manuellt:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Kontrollera att det fungerar: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Orsak:** Efter en global `npm install -g omniroute` kan den systemspecifika binärfilen för `better-sqlite3` inuti paketet ha kompilerats för en annan arkitektur eller Node.js ABI än den som körs lokalt. Detta är vanligt på macOS (både Apple Silicon och Intel) när den förkompilerade binärfilen inte matchar din miljö.

**Symtom:**

- Servern misslyckas omedelbart vid start med ett `dlopen`-fel
- Felet innehåller `slice is not valid mach-o file`
- Fullständigt exempel:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Lösning — kompilera om för din lokala miljö (ingen nedgradering av Node.js krävs):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Obs:** Detta kompilerar om den systemspecifika bindningen mot din lokala Node.js-version och CPU-arkitektur, vilket löser binärinkompatibiliteten. Det officiellt stödda intervallet för körmiljön är **`>=22.22.2 <23` eller `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` i `src/shared/utils/nodeRuntimeSupport.ts`, i linje med fältet `engines` i `package.json`). Node.js 24.x LTS (Krypton) och Node.js 26 stöds fullt ut med `better-sqlite3` v12.x.

## Proxyproblem

<a name="proxy-issues"></a>

### Leverantörsvalideringen visar "fetch failed"

**Orsak:** API-nyckelns valideringsslutpunkt (`POST /api/providers/validate`) kringgick tidigare proxykonfigurationen, vilket orsakade fel i miljöer som kräver proxyvägning.

**Åtgärd (v3.5.5+):** Detta är nu åtgärdat. Leverantörsvalideringen dirigeras genom `runWithProxyContext` och följer automatiskt proxyinställningar på leverantörsnivå och global nivå.

### Kontroll av tokenstatus misslyckas med "fetch failed"

**Orsak:** Bakgrundsuppdateringen av OAuth-token löste inte proxykonfigurationen separat för varje anslutning.

**Åtgärd (v3.5.5+):** Schemaläggaren för kontroll av tokenstatus löser nu proxykonfigurationen per anslutning innan den försöker uppdatera. Uppdatera till v3.5.5+.

### SOCKS5-proxyn returnerar "invalid onRequestStart method"

**Orsak:** I Node.js 22 är dispatchern i undici@8 inkompatibel med Node:s inbyggda `fetch()`-implementering.

**Åtgärd (v3.5.5+):** OmniRoute använder nu undicis egen `fetch()`-funktion när en proxydispatcher är aktiv, vilket säkerställer konsekvent beteende. Uppdatera till v3.5.5+.

### MITM-proxy under WSL: skrivbordsappar på Windows-värden fångas inte upp

**Orsak:** MITM-proxyn och dess CA-certifikat installeras i miljön där OmniRoute körs. Under WSL är den miljön Linux-gästen, medan AI-skrivbordsapparna (Kiro, Trae, Copilot, Zed, …) körs på Windows-värden. Värdapparna litar inte på gästens certifikatarkiv och dirigeras inte genom gästens systemproxy, så skrivbordstrafiken fångas inte upp där.

**Rekommendation:** Kör OmniRoute direkt på samma operativsystem som skrivbordsapparna du vill fånga upp (Windows för Windows-appar; motsvarande gäller för macOS/Linux). Om OmniRoute körs inuti WSL medan värdapparna är målet måste du manuellt godkänna det genererade CA-certifikatet på Windows-värden och konfigurera varje värdapps nätverks-/proxyinställningar till WSL-proxyns slutpunkt — en lösning som inte stöds och är bräcklig.

## Leverantörsproblem

### "Language model did not provide messages"

**Orsak:** Leverantörskvoten är förbrukad.

**Åtgärd:**

1. Kontrollera kvotspåraren på kontrollpanelen
2. Använd en kombination med reservnivåer
3. Byt till en billigare/kostnadsfri nivå

### Hastighetsbegränsning

**Orsak:** Prenumerationskvoten är förbrukad.

**Åtgärd:**

- Lägg till en reserv: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Använd GLM/MiniMax som en billig reserv

### OAuth-token har upphört att gälla

OmniRoute uppdaterar token automatiskt. Om problemen kvarstår:

1. Kontrollpanelen → Leverantör → Anslut igen
2. Ta bort och lägg till leverantörsanslutningen på nytt

### Flera Kiro-konton: det andra kontot ogiltigförklarar det första

**Orsak:** Kiros serverdel tillåter endast en aktiv session per OIDC-klientregistrering.
När två konton delar samma registrerade klient (anslutningar importerade före v3.8.0)
ogiltigförklaras det andra kontots uppdateringstoken när det ena kontots token uppdateras.

**Åtgärd (v3.8.0+):** Importera de berörda anslutningarna på nytt.
Från och med v3.8.0 registrerar varje ny Kiro-anslutning som skapas via **Importera token**,
**social inloggning med Google/GitHub** eller **Automatisk import** automatiskt en egen
dedikerad OIDC-klient. Anslutningen är därför helt isolerad, och uppdatering av ett
konto påverkar inte något annat konto.

Anslutningar som importerades _före_ v3.8.0 har ingen klientregistrering per anslutning.
Dessa anslutningar fortsätter att använda den delade slutpunkten för uppdatering via social autentisering.
För att få isolering tar du bort den gamla anslutningen från Kontrollpanelen → Leverantörer och lägger till den
på nytt via något av de tre importflödena.

Fullständig information och stegvisa instruktioner för att lägga till två Kiro-konton sida vid sida
finns i [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Docker-problem

### Docker IPv6/återställd anslutning

<a name="docker-ipv6"></a>

**Symptom:** `curl http://localhost:20128/v1/models` returnerar `curl: (56) Recv failure: Connection reset by peer`. Kontrollpanelen och oautentiserade slutpunkter fungerar, men autentiserade slutpunkter misslyckas – det ser ut som ett autentiseringsproblem, men är inte det.

**Orsak:** `docker run -p 20128:20128` publicerar på både `0.0.0.0` (IPv4) och `::` (IPv6), men processen i containern lyssnar endast på IPv4. På värdar där `localhost` först matchas mot `::1` hamnar anslutningen på den publicerade IPv6-porten utan någon bakomliggande lyssnare → anslutningen återställs.

**Åtgärd:**

1. **Snabbdiagnostik:** Kör `curl -4 http://localhost:20128/v1/models`. Om det fungerar med `-4` men misslyckas utan, har du en konflikt i IPv6-bindningen.
2. **Permanent åtgärd:** Bind uttryckligen till IPv4 genom att använda `-p 127.0.0.1:20128:20128` i ditt `docker run`-kommando:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Detta tvingar fram IPv4-bindning och förhindrar dessutom att proxyn exponeras på värdens alla nätverksgränssnitt.

- Artefakter för anropsloggar: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` när pipelinen för anropsloggar är aktiverad

Åtgärden **Rensa historik** på sidan Anropsloggar rensar `call_logs`, den äldre
`request_detail_logs` och den lokala artefaktkatalogen `${DATA_DIR}/call_logs/`.

## Inställningar för motståndskraft

### Automatisk hastighetsbegränsning utlöses inte

- Automatisk hastighetsbegränsning gäller endast leverantörer med API-nyckel (inte OAuth/prenumeration)
- Kontrollera att automatisk hastighetsbegränsning är aktiverad under **Inställningar → Motståndskraft → Leverantörsprofiler**
- Kontrollera om leverantören returnerar statuskoderna `429` eller huvuden av typen `Retry-After`

### Justera exponentiell backoff

Leverantörsprofiler stöder följande inställningar:

- **Basfördröjning** — Initial väntetid efter det första felet (standard: 1s)
- **Maximal fördröjning** — Övre gräns för väntetiden (standard: 30s)
- **Multiplikator** — Hur mycket fördröjningen ska ökas per efterföljande fel (standard: 2x)

### Skydd mot thundering herd-problemet

När många samtidiga förfrågningar når en hastighetsbegränsad leverantör använder OmniRoute mutex + automatisk hastighetsbegränsning för att serialisera förfrågningar och förhindra kaskadfel. Detta sker automatiskt för leverantörer med API-nyckel.

### Chattförfrågningar misslyckas med 503 / chat_admission_busy

**Symptom:**

- Slutpunkten för chattkompletteringar returnerar ett återförsökningsbart `503`-svar vars felkod är
  `chat_admission_busy`.
- Svaret innehåller `Retry-After`. Sedan #12135 härleds värdet från den observerade
  beläggningen — det största värdet av fönstret `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` som förfrågningen redan
  har väntat och den tid som de aktuella tungviktsreservationerna har innehafts — avrundat uppåt till hela
  sekunder och begränsat till 60. Vid en inaktiv spärr behålls de tidigare minimivärdena: 2 sekunder för den
  bytebaserade sökvägen och 1 sekund för den strukturbaserade sökvägen (som även inkluderar
  `reason: "structure_limit"`).
- Detta kan inträffa medan en annan tungviktschatt eller långvarig strömmande respons fortfarande
  pågår.

Den bytebaserade svarstexten är:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Det strukturbaserade svaret använder samma typ och kod, med meddelandet
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
och `reason: "structure_limit"`.
Med standardtrösklarna är en förfrågan strukturellt tung när den har minst `200` meddelanden,
minst `64` verktyg eller minst `32,000` uppskattade token, eller när den begränsade strukturuppskattningen
når sina gränser på `10,000` besökta noder eller djupet `12`.

**Orsak:** Detta är avsiktlig lastreducering i OmniRoute, inte ett fel hos en uppströmsleverantör.
Varje process använder ett processlokalt skydd för att reservera begränsad tungviktskapacitet innan en
stor förfrågningskropp behålls och parsas. En tungviktsreservation förblir innehavd under hela livslängden för ett SSE-
svar.

**#503-fan-out:** före den här korrigeringen begränsade skyddet samtidigheten till ett fast ANTAL förfrågningar
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, standard `1`) oavsett värdens minne, vilket gjorde att fan-out från
kodningsagenter (flera underagenter/CLI:er, kroppar rutinmässigt > 256 KB) kollapsade till en effektiv
samtidighet på ~1 och gav 503-fel under helt normal belastning. Skyddet självjusteras nu: det styrs
av en automatiskt härledd BYTE-budget för inläsning (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) som dimensioneras utifrån
processens faktiska minnesgräns, och det tar även hänsyn till en realtidssignal för resursbelastning — så att
det endast reducerar belastningen när värden verkligen är under minnestryck, inte enbart för att fler än en
tung förfrågan anlände samtidigt. Den gamla antalsgränsen (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
respekteras fortfarande, men endast om du uttryckligen anger den.

När kapaciteten är upptagen väntar en tungviktsförfrågan först i upp till
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (standard är `RATE_LIMIT_MAX_WAIT_MS`; `0` inaktiverar väntan) på att en plats ska bli ledig
innan det återförsökningsbara `503`-svaret skickas. Den begränsade väntan finns för att klienter av agenttyp
(OpenCode, Claude Code, Cursor) som skapar tunga underförfrågningar parallellt ska serialisera belastningstoppen
i stället för att förbruka hela sin återförsöksbudget på omedelbara avvisningar och avbrytas mitt i uppgiften.
Aktuell beläggning för tungviktsreservationer, den fastställda bytebudgeten och aktuell belastningsgrad
visas på `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — kontrollera dessa innan du ändrar någon miljövariabel.
Inställningar → Motståndskraft → Förfrågningskö → Samtidiga förfrågningar styr inte detta; den inställningen
reglerar en separat kömekanism för leverantörsförfrågningar.

**Åtgärd:**

1. Försök igen först. Klienter bör respektera `Retry-After` och använda backoff i stället för att omedelbart
   upprepa förfrågningen.
2. Kontrollera `/api/monitoring/health` → `chatAdmission` innan du justerar något. `countCapEnabled:
false` och ett generöst `maxInflightBytes` innebär att den automatiskt härledda budgeten redan fungerar som
   avsett; ett `pressureSeverity` på `high`/`critical` innebär att värden verkligen har ont om minne —
   det kan inte åtgärdas med en miljövariabel för åtkomstkontroll, utan kräver mer RAM eller en mindre arbetsbelastning.
3. Endast om `/api/monitoring/health` visar att den automatiskt härledda budgeten verkligen är för liten för
   din värd (ovanligt — den skalas redan från container till bare-metal) bör du åsidosätta den direkt med
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` i stället för att återgå till den äldre antalsgränsen för förfrågningar.

Se [referensen för miljövariabler](../reference/ENVIRONMENT.md#4-security--authentication)
för de auktoritativa inställningarna för åtkomstkontroll.

## Valfri feltaxonomi för RAG/LLM (16 problem)

Vissa OmniRoute-användare placerar gatewayen framför RAG- eller agentstackar. I sådana konfigurationer är det vanligt att se ett märkligt mönster: OmniRoute verkar fungera korrekt (leverantörerna är tillgängliga, routningsprofilerna är korrekta och det finns inga varningar om hastighetsbegränsningar), men det slutliga svaret är ändå felaktigt.

I praktiken kommer dessa incidenter vanligtvis från den efterföljande RAG-pipelinen, inte från själva gatewayen.

Om du vill ha en gemensam terminologi för att beskriva dessa fel kan du använda WFGY ProblemMap, en extern textresurs med MIT-licens som definierar sexton återkommande felmönster för RAG/LLM. På en övergripande nivå omfattar den:

- avvikande hämtning och brutna kontextgränser
- tomma eller inaktuella index och vektordatabaser
- bristande överensstämmelse mellan inbäddningar och semantik
- problem med promptsammansättning och kontextfönster
- logiska sammanbrott och överdrivet självsäkra svar
- fel i långa kedjor och agentsamordning
- minnes- och rollavvikelser i system med flera agenter
- problem med driftsättning och initieringsordning

Idén är enkel:

1. När du undersöker ett felaktigt svar ska du registrera:
   - användarens uppgift och begäran
   - routen eller leverantörskombinationen i OmniRoute
   - eventuell RAG-kontext som används nedströms (hämtade dokument, verktygsanrop osv.)
2. Koppla incidenten till ett eller två nummer i WFGY ProblemMap (`No.1` … `No.16`).
3. Lagra numret i din egen instrumentpanel, driftmanual eller incidenthanterare bredvid OmniRoute-loggarna.
4. Använd motsvarande WFGY-sida för att avgöra om du behöver ändra din RAG-stack, hämtare eller routningsstrategi.

Den fullständiga texten och konkreta anvisningar finns här (MIT-licens, endast text):

[README för WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Du kan ignorera det här avsnittet om du inte kör RAG- eller agentpipelines bakom OmniRoute.

## Kända problem i v3.8.0

Problem som är specifika för version v3.8.0 och deras aktuella tillfälliga lösningar. Om en korrigering införs i en senare patch kommer posten att uppdateras eller tas bort.

### Autentiseringsfel i Devin CLI

**Symptom:**

- ”Devin CLI not found” eller ”auth failed” vid anrop av Devin-baserade verktyg
- CLI-körtidskontrollen rapporterar `installed=false`

**Orsaker:**

- `CLI_DEVIN_BIN` pekar på en sökväg som inte finns
- Devin CLI är inte installerat på värden

**Lösning:**

1. Installera Devin CLI för din plattform
2. Ange `CLI_DEVIN_BIN=/usr/local/bin/devin` (eller den faktiska sökvägen) i `.env`
3. Starta om OmniRoute och testa igen från **Instrumentpanel → CLI-verktyg**

### Modellens nedkylningsperiod har fastnat (manuell återställning)

**Symptom:**

- En modell fortsätter att visas med en nedkylningsperiod även efter att utgångstiden har passerat
- Begäranden fortsätter att hoppa över modellen vid kombinationsroutning trots att tidsstämpeln ligger i det förflutna

**Manuell återställning:**

- **Instrumentpanel:** **Inställningar → Modellnedkylningar** → klicka på **Återaktivera** på det berörda kortet
- **API:** `DELETE /api/resilience/model-cooldowns` med autentiseringshuvuden för administration

### Anslutningen till Command Code-leverantören misslyckas med 403

**Symptom:**

- 403 vid test av anslutningen till Command Code-leverantören
- Leverantörskortet visar ”unauthorized” efter att leverantören nyligen lagts till

**Orsak:** OAuth-flödet slutfördes inte (återanropet togs inte emot eller token sparades inte).

**Lösning:**

- Kör `omniroute providers` från CLI för att utlösa OAuth-flödet igen, eller
- Kör OAuth igen från **Instrumentpanel → Leverantörer → Command Code → Återanslut**

### ModelScope returnerar aggressiva 429-nedkylningsperioder

**Symptom:**

- Mycket korta eller omedelbara nedkylningsperioder för ModelScope efter en mindre skur av begäranden
- Kombinationsroutningen hoppar över ModelScope tidigare än förväntat

**Orsak:** ModelScope skickar leverantörsspecifika `Retry-After`-huvuden. v3.8.0 innehåller särskild hantering för dessa huvuden, så äldre versioner misstolkar dem som generiska indikationer om hastighetsbegränsning.

**Lösning:**

- Kontrollera att du använder v3.8.0 eller senare
- Kontrollera att reglaget `useUpstream429BreakerHints` är aktiverat under **Inställningar → Motståndskraft**

### OMNIROUTE_WS_BRIDGE_SECRET saknas i produktionsmiljön

**Symptom:**

- 401 vid varje begäran till Codex/Responses WebSocket-bryggan när den körs på en fjärransluten produktionsvärd
- WebSocket-bryggans handskakning stängs omedelbart efter anslutningen

**Orsak:** Miljövariabeln `OMNIROUTE_WS_BRIDGE_SECRET` saknas i produktionsmiljön.

**Lösning:**

1. Generera en slumpmässig hemlighet: `openssl rand -hex 32`
2. Ange `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` i produktionsserverns miljö (och i alla klienter som kommunicerar med bryggan)
3. Starta om OmniRoute

### Responses API: bakgrundsläget har nedgraderats till synkront

**Symptom:**

- Varning loggas: `background mode degraded to synchronous`
- En begäran med `background: true` returnerar ett vanligt synkront svar i stället för ett handtag till ett bakgrundsjobb

**Orsak:** v3.8.0 nedgraderar avsiktligt `background: true` i Responses API till synkron körning samtidigt som en varning genereras. Fullständig asynkron bakgrundskörning är planerad för framtiden.

**Lösning:**

- Justera klienten så att den anropar utan `background`, eller
- Vänta på en senare version med fullständigt asynkront bakgrundsläge (följ ändringsloggen)

## Långsam start / timeout för beredskap

Om CLI:n skriver ut `⚠ Server did not respond within 60s` men servern faktiskt
fungerar, är beredskapskontrollens tidsbudget för kort för din miljö.

Detta inträffar ofta i Windows (antivirus, filsystemövervakare) eller i containrar
med hög arbetsbelastning vid start.

**Lösning — höj tidsbudgeten:**

```bash
# Via miljövariabel (kvarstår mellan starter):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuter
omniroute serve

# Via CLI-flagga (endast denna gång):
omniroute serve --ready-timeout 180000
```

Standardvärdet är 60 000 ms (60 s). Varningen är endast informativ; servern
fortsätter att starta i bakgrunden och blir tillgänglig när starten är slutförd.

Se [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) för fullständig
information om `OMNIROUTE_READY_TIMEOUT_MS`.
