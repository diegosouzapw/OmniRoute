TPROXY şəffaf deşifrləmə OmniRoute-un
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM steki üçün **5-ci tutma rejimidir**. O, nüvə TPROXY-si + siyasət əsaslı marşrutlaşdırmadan istifadə edərək Linux-da lokal çıxış HTTPS trafikini — `/etc/hosts` faylını saxtalaşdırmadan və ƏS miqyaslı sistem proksi parametrlərini dəyişdirmədən — ələ keçirir və **deşifrləyir**. O, başsız mühitlər üçün əlverişlidir
(təmizlənməli DNS dəyişiklikləri yoxdur) və təhlükəsizlik divarı qaydaları yenidən başladılma zamanı avtomatik təmizlənir.

Digər tutma rejimlərindən fərqli olaraq, TPROXY hər host üçün ayrıca quraşdırma tələb etmir: o, hədəf portundakı **istənilən** təyinat hostlarını şəffaf şəkildə ələ keçirir, hər SNI host adı üçün dinamik olaraq yaratdığı son qovşaq sertifikatı ilə TLS-i sonlandırır, deşifrlənmiş mübadiləni tutur və sorğunu ilkin təyinat nöqtəsinə yenidən şifrləyərək göndərir.

> **Yalnız Linux, yalnız root, könüllü aktivləşdirmə.** Bu rejim Linux, C alətlər zənciri ilə yığılmış yerli əlavə və **CAP_NET_ADMIN** imkanını (adətən root) tələb edir. O, yalnız loopback ilə məhdudlaşdırılmış AgentBridge API-si arxasında qorunur və standart olaraq deaktivdir. İstənilən host üçün imza yarada bilən etibarlı MITM CA güclü bir imkandır — [§6 Təhlükəsizlik](#6-security) bölməsinə baxın.

**Mənbə:** `src/mitm/tproxy/`
**API marşrutu:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**İdarəetmə paneli keçidi:** Traffic Inspector → tutma rejimləri alətlər paneli → **"TPROXY Decrypt"** ⚠
**Həmçinin baxın:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 Bu nədir və nə zaman istifadə edilməlidir

Digər dörd tutma rejiminin hər birinin bir məhdudiyyəti var:

| Rejim                  | Trafik necə yönləndirilir                              | Məhdudiyyət                                                   |
| ---------------------- | ------------------------------------------------------ | ------------------------------------------------------------- |
| AgentBridge            | Sabit host dəsti üçün `/etc/hosts` DNS saxtalaşdırması | yalnız qeydiyyatdan keçmiş IDE agent hostları                 |
| Xüsusi hostlar         | Hər host üçün `/etc/hosts` DNS saxtalaşdırması         | hər host üçün bir qeyd; hosts faylını redaktə etmək üçün sudo |
| HTTP_PROXY             | `HTTP_PROXY`/`HTTPS_PROXY` mühit dəyişəni              | yalnız mühit dəyişəninə əməl edən tətbiqlər                   |
| Sistem miqyaslı proksi | ƏS proksi parametrləri                                 | qlobal vəziyyəti dəyişdirir; geri qaytarma tələb edir         |

TPROXY şəffaf deşifrləmə isə trafiki **nüvə** səviyyəsində yönləndirir. O,
`mangle OUTPUT` zəncirində hədəf porta (standart olaraq `443`) yeni lokal çıxış TCP bağlantılarını işarələyir, `ip rule` işarələnmiş paketləri lokal çatdırılmaya yenidən yönləndirir və təkrar daxilolma zamanı `mangle PREROUTING` zəncirindəki `TPROXY` hədəfi onları **IP_TRANSPARENT** dinləyicisinə ötürür — dinləyici isə TLS-i sonlandırır və açıq mətni tutur.

Aşağıdakı xüsusiyyətlərə malik prosesdən gələn trafiki tutmaq və deşifrləmək istədikdə bu rejimdən istifadə edin:

- AgentBridge-in qeydiyyata almadığı hostla əlaqə qurur və
- `HTTP_PROXY` dəyişəninə əməl etmir və
- sistem miqyaslı proksi dəyişikliyi ilə ona müdaxilə etmək istəmirsiniz.

Ələ keçirmə nüvədə baş verdiyi üçün trafiki başladan prosesdə **heç bir
konfiqurasiya dəyişikliyi** tələb olunmur — lakin proses OmniRoute-un quraşdırdığı dinamik CA-ya etibar etməlidir ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) bölməsinə baxın).

## §2 Tələblər

| Tələb              | Təfərrüat                                                                                                                                                                        |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ƏS**             | Yalnız Linux — **IP_TRANSPARENT** yalnız Linux-da mövcud olan soket seçimidir. Yükləyici bütün digər platformalarda "əlçatan deyil" cavabını qaytarır.                           |
| **İmtiyaz**        | Şəffaf soketi yaratmaq və `iptables`/`ip` qaydalarını tətbiq etmək üçün **CAP_NET_ADMIN** imkanı — praktikada root olaraq işə salın.                                             |
| **Native addon**   | Kiçik bir N-API addonu (`src/mitm/tproxy/native/transparent.c`) yığılmalı və ya əvvəlcədən yığılmış formada təqdim edilməlidir. Baxın: [§3](#3-the-native-ip_transparent-addon). |
| **Nüvə modulları** | `TPROXY`, `mangle` və `mark` uyğunlaşdırma dəstəyinə malik `iptables` (kernel 6.8.0 ilə yoxlanılıb).                                                                             |

**Tədricən funksionallığın azalması:** hər hansı tələb ödənmirsə (Linux olmayan
sistem, alətlər zəncirinin olmaması, addon-un yığılmaması), addon yükləyicisi
(`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`) xəta atmaq əvəzinə
`null` qaytarır. Bundan sonra tutma rejiminin statusu `available: false` göstərir,
idarəetmə panelindəki keçid "TPROXY şifrəsinin açılması üçün Linux + root + native
addon tələb olunur" ipucu ilə **deaktiv edilir** və OmniRoute-un qalan hissəsi
işləməyə davam edir.

## §3 Native IP_TRANSPARENT addonu

Node-un `net` modulu TPROXY-nin tələb etdiyi kimi `bind()` çağırışından _əvvəl_
`setsockopt(IP_TRANSPARENT)` çağıra bilmir (əks halda nüvə yönləndirilmiş paketləri
atır). Addon (`binding.gyp` vasitəsilə yığılan
`src/mitm/tproxy/native/transparent.c`) `transparentSocket.ts` vasitəsilə istifadə
edilən üç funksiyanı təqdim edən kiçik N-API moduludur:

| Addon funksiyası                      | Soket əməliyyatı                                                                               | İstifadə məqsədi                                                                    |
| ------------------------------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, xam fd-ni qaytarır | şəffaf tutma dinləyicisi (Node fd-ni `server.listen({ fd })` vasitəsilə qəbul edir) |
| `setSocketMark(fd, mark)`             | Mövcud fd üzərində `setsockopt` **SO_MARK**                                                    | dövrənin qarşısının alınması (proksinin öz soketlərinin işarələnməsi)               |
| `connectMarked(ip, port, mark)`       | Bloklamayan `connect()` çağırışından **əvvəl** `socket()` + **SO_MARK**, fd-ni qaytarır        | yenidən şifrələnmiş yuxarı axın yönləndirməsi (SYN işarəni daşıyır)                 |

İlkin təyinat `socket.localAddress`/`localPort` vasitəsilə oxunur — TPROXY onu
qoruyub saxlayır, buna görə **SO_ORIGINAL_DST**/NAT axtarışına ehtiyac yoxdur.

### Addon-un yığılması

```bash
npm run build:native:tproxy      # src/mitm/tproxy/native qovluğuna keçin və node-gyp rebuild əmrini icra edin
                                 # -> native/build/Release/transparent.node
```

- `npm run build` zamanı `scripts/build/build-tproxy-native.mjs` faylı `node-gyp
rebuild` əmrini icra edir. Bu, **yalnız Linux üçündür və xəta kritik deyil** —
  alətlər zəncirinin olmaması sadəcə tutma rejimini əlçatmaz edir.
- `assembleStandalone.mjs`, `build/Release/transparent.node` faylını müstəqil
  paketə köçürür; `transparentSocket.ts` onu həm modula, həm də cwd-yə nəzərən
  (`<cwd>/src/mitm/tproxy/native/...`) tapır.
- `build/` və `prebuilds/` git tərəfindən nəzərə alınmır — binar fayl **yığılır,
  lakin heç vaxt repozitoriyaya daxil edilmir**.

Yükləyici aşağıdakıları prioritet sırası ilə yoxlayır:
`native/build/Release/transparent.node`, sonra `native/prebuilds/transparent.node`
(hər ikisi həm modula nəzərən, həm də `<cwd>/src/mitm/tproxy/` altında).

## §4 SNI üzrə dinamik CA və etibar anbarı quraşdırıcısı

> **#6684 yeniləməsi:** AgentBridge statik serveri (`src/mitm/server.cjs`) artıq
> tək statik, öz-özünə imzalanmış son sertifikat əvəzinə eyni CA/son sertifikat
> arxitekturası modelindən istifadə edir. O, **ayrıca** CA instansiyasından
> (`src/mitm/cert/rootCa.ts`, `<DATA_DIR>/mitm/ca.key`/`ca.crt` ünvanında saxlanılır)
> istifadə edir və əvvəlcədən mövcud olan `omniroute-mitm.crt` etibar anbarı yuvasına
> quraşdırılır (oradakı köhnə tək son sertifikatı əvəz edir — ikili etibar təmizləməsinə
> ehtiyac yoxdur); bu, aşağıdakı TPROXY-yə məxsus `omniroute-tproxy-ca.crt` yuvasından
> tamamilə ayrı saxlanılır.
> Yeni AgentBridge quraşdırmaları CA modelini avtomatik əldə edir; köhnə statik son
> sertifikata artıq etibar edən quraşdırma isə operator `MITM_ROOT_CA_ENABLED=true`
> vasitəsilə buna razılıq verənədək ondan istifadə etməyə davam edir
> (`src/mitm/cert/migration.ts` faylına baxın) — **istənilən** host üçün son sertifikat
> imzalaya bilən etibarlı MITM CA köhnə, sabit SAN-lı son sertifikatdan əhəmiyyətli
> dərəcədə daha güclüdür, buna görə də artıq etibar edilən quraşdırmada keçid heç vaxt
> səssiz həyata keçirilmir.

Tarixən statik AgentBridge MITM sertifikatı yalnız AgentBridge **sabit** host
dəsti üçün DNS saxtalaşdırması etdiyinə görə işləyirdi (bu dəst indi aşağıdakı
modellə birləşdirilib). TPROXY **ixtiyari** hostları ələ keçirir, buna görə onun
dinləyicisi müştərinin tələb etdiyi istənilən SNI üçün etibarlı son sertifikat
təqdim etməlidir — AgentBridge artıq yalnız 4 antigravity hostu əvəzinə tam
`MITM_TOOL_HOSTS` dəsti (9 alət qeydi) üçün eyni tələbə malikdir.

### Dinamik CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore`, `selfsigned` asılılığı əsasında qurulmuş lokal CA işlədir və:

- `generateMitmCa()` vasitəsilə uzunmüddətli CA yaradır (CN `"OmniRoute MITM CA"`,
  10 illik etibarlılıq, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048 bitlik RSA / SHA-256).
- `issueLeafCert()` vasitəsilə **hər SNI host adı üçün tələb əsasında son sertifikat**
  verir (1 illik etibarlılıq, `subjectAltName` = SNI hostu) və hər host adı üçün bir
  `tls.SecureContext` keşləyir.
- TLS-i sonlandıran server üçün `createSNICallback()` təqdim edir
  ([§5](#5-how-decrypt-and-capture-work) bölməsinə baxın).
- CA-nı yenidən başlatmalar arasında sabit saxlamaq üçün `existingCa` ilə yaradıla
  bilər (beləliklə, etibar anbarını yenidən quraşdırmağa ehtiyac qalmır).

CA məxfi açarı **heç vaxt maşını tərk etmir**.

### Etibar anbarı quraşdırıcısı (`src/mitm/tproxy/caTrust.ts`)

Ələ keçirilən müştəri dinamik CA-ya etibar etməlidir, buna görə tutma rejiminin
başladılması CA sertifikatını ƏS-in etibar anbarında **ayrılmış yuvaya** —
`omniroute-tproxy-ca.crt` (`TPROXY_CA_CERT_NAME` sabiti) — quraşdırır. Bu yuva
statik MITM sertifikatının yuvasından (`omniroute-mitm.crt`) ayrı saxlanılır ki,
onlar heç vaxt bir-birinin üzərinə yazılmasın.

`installTproxyCa(caPem, sudoPassword?)` distributivin anchor kataloqunu
(aşkarlama ardıcıllığında əvvəlcə Debian üslubu) müəyyən edir və uyğun yeniləmə
əmrini icra edir:

| Anchor kataloqu                             | Yeniləmə əmri            |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Quraşdırma PEM-i müvəqqəti fayla yerləşdirir, sonra (yüksək səlahiyyətlə)
anchor kataloqu üçün `mkdir -p` icra edir, mərhələlənmiş faylı `cp` ilə ora
köçürür və yeniləmə əmrini işlədir. `uninstallTproxyCa()` yalnız ayrılmış yuvanı
silir (statik MITM sertifikatına toxunmur) və yeniləmə aparır — Linux olmayan
sistemlərdə isə heç bir əməliyyat yerinə yetirmir.

Bütün yüksək səlahiyyətli əmrlər `execFileWithPassword`
(`src/mitm/systemCommands.ts`) vasitəsilə icra olunur — `spawn` **arqument
massivləri ilə, shell olmadan, sətir interpolyasiyası olmadan** (Sərt Qayda #13).
Proses root olduqda (məsələn, VPS-də) hədəf birbaşa icra olunur və parola ehtiyac
qalmır; root olmayan masaüstü sistemdə isə `sudoPassword`, stdin üzərindən
`sudo -S` əmrinə ötürülür.

> Masaüstü sistemin `sudoPassword` dəyəri etibar anbarı quraşdırmasına icazə
> vermək üçün POST gövdəsində təqdim edilir; proses root olduqda ona tamamilə
> məhəl qoyulmur.

## §5 Deşifrləmə və ələ keçirmə necə işləyir

Emal xətti (hamısı `src/mitm/tproxy/` altında):

```
yerli tətbiq  ──TCP/443──▶  mangle OUTPUT bağlantını işarələyir (fwmark)
                             ip rule → yerli marşrut cədvəli → lo
                             mangle PREROUTING TPROXY → IP_TRANSPARENT dinləyicisi (port 8443)
                                 │  captureMode.ts: ilkin təyinatı socket.localAddress-dən oxuyur
                                 ▼
                             tlsCapture.ts:
                               1. hər SNI üçün ayrıca sertifikatla (dynamicCert) CLIENT TLS bağlantısını sonlandırır
                               2. daxili http.Server deşifrlənmiş açıq mətni təhlil edir
                               3. ələ keçirmə → source: "tproxy" ilə globalTrafficBuffer.push()
                                  (sanitizeHeaders + maskSecret tətbiq edilir)
                               4. bypass işarəli soket üzərindən (connectMarked, dövrə əleyhinə)
                                  ilkin təyinata yenidən şifrələnmiş şəkildə yönləndirir
                                 │
                                 ▼
                             ilkin yuxarı axın (api.example.com)
```

- **TLS sonlandırılması** (`createTlsCaptureServer`): dinamik CA-nın SNI geri çağırışından istifadə edərək xam ələ keçirilmiş
  soketi server tərəfli `tls.TLSSocket` ilə əhatə edir,
  sonra deşifrlənmiş axını daxili `http.Server`-ə ötürür (standart MITM
  sonlandırma üsulu). Soketlərin işləmə müddəti `MITM_IDLE_TIMEOUT_MS` ilə məhdudlaşdırılır ki,
  ilişib qalmış tunel fayl deskriptorlarını tükəndirə bilməsin.
- **Ələ keçirmə** (`handleDecryptedRequest`): başlıqları
  `sanitizeHeaders()` funksiyasından, gövdələri isə buferə daxil olmazdan əvvəl `maskSecret()` funksiyasından keçirərək,
  `source: "tproxy"` və ilkin `"in-flight"` statusu ilə bir `InterceptedRequest`
  əlavə edir. Daha sonra qeyd cavab, ölçülər və gecikmə məlumatları ilə yenilənir.
- **Yenidən şifrələnmiş yönləndirmə** (`createForward` / `realForward`): məlumatı ilkin
  təyinata yenidən şifrələyir. `rejectUnauthorized` standart olaraq **`true`**-dur (standart olaraq
  təhlükəsizdir) — yuxarı axın sertifikatı müştərinin tələb etdiyi SNI/Host əsasında
  yoxlanılır, beləliklə proksi ilkin müştərinin rədd edəcəyi halları eynilə rədd edir.

### Dövrə əleyhinə qoruma (SO_MARK)

Qaydalar yeni yerli çıxış bağlantılarını işarələdiyi üçün proksinin **öz**
yenidən şifrələnmiş yönləndirməsi normalda yenidən ələ keçirilərdi — bu isə sonsuz dövrə yaradar.
Yönləndirmə yolu bypass soket işarəsi (**SO_MARK**) ilə bunun qarşısını alır:

- `realForward` yuxarı axın soketini `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  vasitəsilə açır — `DEFAULT_BYPASS_MARK = 0x539` — bu funksiya **SO_MARK** dəyərini `connect()` çağırışından **əvvəl** təyin edir,
  beləliklə yönləndirmənin SYN paketi bypass işarəsini daşıyır.
- `mangle OUTPUT` qaydası artıq bypass işarəsi daşıyan bağlantıları
  (`-m mark ! --mark <bypassMark>`) istisna edir, buna görə proksinin yönləndirməsi yenidən **işarələnmir**
  və TPROXY-yə təkrar daxil olmur.

> İcra qeydi: bypass işarəli soket agentin
> `createConnection` parametrində quraşdırılmalıdır (`https.request({ createConnection })` agent
> mövcud olduqda xəbərdarlıq edilmədən nəzərə alınmır), əks halda yönləndirmə işarələnməmiş soket açar və
> dövrə yenidən yaranardı. Bu, e2e ilə təsdiqlənmiş dövrə əleyhinə düzəlişdir.

## §7 Tranzaksiyalı firewall tətbiqi / geri qaytarılması

Nasazlıq heç vaxt geridə `mangle` qaydası və ya köhnəlmiş marşrut qoymamalıdır. Əmr qurucusu
(`src/mitm/tproxy/commands.ts`) və icraçı (`src/mitm/tproxy/setup.ts`)
**geri qaytarmanın tətbiqin tərs ardıcıllıqla yerinə yetirilən dəqiq əksi olmasına** zəmanət verir.

`applyTproxy(cfg)` tətbiq əmrlərini ardıcıllıqla icra edir; **istənilən** xəta baş verdikdə
mümkün olan ən yaxşı şəkildə tam `revertTproxy(cfg)` icra edir və xətanı yenidən atır — beləliklə,
firewall ya tam tətbiq edilir, ya da tam geri qaytarılır, heç vaxt qismən tətbiq edilmiş vəziyyətdə qalmır.
`revertTproxy(cfg)` əks əmrləri tərs ardıcıllıqla icra edir və xətaları nəzərə almır
(idempotentdir — şərtsiz çağırmaq təhlükəsizdir, məsələn, AgentBridge `repairMitm()` təmizləməsindən).

`validateTproxyConfig(cfg)` istənilən əmrdən əvvəl icra olunur: portlar `1–65535`
aralığında olmalı, `mark`/`routeTable`/`bypassMark` müsbət tam ədədlər olmalı və
`bypassMark`, `mark` dəyərindən fərqlənməlidir (dövrənin qarşısını almaq üçün).

### Tətbiq əmrləri (ardıcıllıqla)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Geri qaytarma onları tərs ardıcıllıqla silir: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> Bu resept **OUTPUT əsaslıdır**, çünki MITM istifadə ssenarisi _lokal_ çıxış
> trafikidir (eyni hostdakı tətbiqlər); yalnız `PREROUTING` daxilindəki TPROXY bu trafiki
> görmür — `PREROUTING` yalnız yönləndirilən trafiki görür. `OUTPUT` zənciri yeni
> lokal bağlantıları işarələyir, `ip rule` onları lokal çatdırılmaya (`lo`) yenidən yönləndirir və
> bundan sonra `PREROUTING` onları şəffaf dinləyiciyə təyin edir.

## §8 Konfiqurasiya

Başlatma sorğusu (`POST /api/tools/agent-bridge/tproxy`) `StartTproxyBodySchema`
(`tproxy/route.ts`) tərəfindən yoxlanılan aşağıdakı sahələri qəbul edir. Hamısı ixtiyaridir
və göstərilmədikdə standart dəyərlərindən istifadə edilir:

| Sahə             | Növ                | Standart | Qeydlər                                                                                                                                                    |
| ---------------- | ------------------ | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`    | Şəffaf şəkildə ələ keçiriləcək təyinat TCP portu                                                                                                           |
| **mark**         | int (≥1)           | `0x2333` | `OUTPUT` daxilində təyin edilən və `ip rule` + `PREROUTING` tərəfindən uyğunlaşdırılan firewall işarəsi                                                    |
| **onPort**       | int (1–65535)      | `8443`   | Şəffaf (**IP_TRANSPARENT**) dinləyicinin bağlandığı port                                                                                                   |
| **routeTable**   | int (≥1)           | `233`    | `local 0.0.0.0/0` marşrutunu saxlayan siyasət əsaslı marşrutlaşdırma cədvəlinin identifikatoru                                                             |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | Proksinin öz yuxarı axın bağlantılarına təyin etdiyi keçid soketi işarəsi (**SO_MARK**); `OUTPUT` daxilində istisna edilir (dövrənin qarşısını almaq üçün) |
| **sudoPassword** | string             | —        | Yalnız root olmayan masaüstü sistemlər üçün: etibar anbarının quraşdırılmasına icazə verir; root olduqda nəzərə alınmır                                    |

TPROXY üçün **heç bir mühit dəyişəni yoxdur** — bütün konfiqurasiya POST
gövdəsi və ya yuxarıdakı standart dəyərlər vasitəsilə təmin edilir.

## §9 Traffic Inspector vasitəsilə aktivləşdirmə

1. **Traffic Inspector**-u açın (`/dashboard/tools/traffic-inspector`).
2. Tutma rejimləri alətlər panelində **"TPROXY Decrypt"** ⚠ düyməsini tapın
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Əgər düymə "TPROXY decrypt requires Linux + root +
     the native addon" ipucu ilə **deaktivdirsə**, bu hostda native əlavə əlçatan deyil (Linux deyil,
     alətlər zənciri yoxdur və ya əlavə yığılmayıb). [§2](#2-requirements) və [§3](#3-the-native-ip_transparent-addon) bölmələrinə baxın.
3. Düyməyə klikləyin. Bu, `startTproxyCaptureMode()` vasitəsilə
   `POST /api/tools/agent-bridge/tproxy` sorğusunu göndərir
   (`src/lib/inspector/tproxyCaptureApi.ts`); həmin funksiya:
   dinamik CA yaradır, şəffaf dinləyicini açır, firewall
   qaydalarını tətbiq edir və CA-nı əməliyyat sisteminin etibar deposuna quraşdırır.
4. İşlədiyi zaman keçid kəhrəba rənginə çevrilir və canlı ələkeçirmə sayını
   (`· <interceptCount>`) göstərir. Ələ keçirilmiş sorğular sorğu siyahısında
   `source: "tproxy"` ilə görünür.
5. Dayandırmaq üçün yenidən klikləyin — `stopTproxyCaptureMode()` vasitəsilə
   `DELETE /api/tools/agent-bridge/tproxy` dinləyicini bağlayır, CA-nı silir və
   firewall qaydalarını geri qaytarır.

Tutma rejiminin statusu (işləyir / əlçatandır / ələkeçirmə sayı / dinləyici portu)
`GET /api/tools/agent-bridge/tproxy` sorğusundan (`src/mitm/tproxy/captureManager.ts`
faylındakı `getCaptureStatus()`) əldə edilir. Eyni anda yalnız **bir** TPROXY sessiyası
işləyir — ikinci sessiyanı başlatmaq cəhdi "TPROXY capture mode is already running"
xətası ilə rədd edilir.

## §10 Problemlərin aradan qaldırılması

### Keçid deaktivdir

Native əlavəni yükləmək mümkün deyil. Bunları yoxlayın: Linux istifadə edirsiniz,
əlavəni yığmısınız (`npm run build:native:tproxy`) və proses `transparent.node`
faylını yükləyə bilir. Keçidin əlçatanlığını `isTransparentSocketAvailable()`
idarə edir; əlavə olmadıqda `GET /api/tools/agent-bridge/tproxy`
`available: false` qaytarır.

### Heç nə tutulmur

- Ələ keçirilən prosesin həqiqətən konfiqurasiya edilmiş `dport`-a
  (standart olaraq `443`) qoşulduğunu yoxlayın.
- Prosesin dinamik CA-ya etibar etdiyini yoxlayın. CA
  `omniroute-tproxy-ca.crt` adı altında quraşdırılır; öz etibar deposu olan tətbiqlərdə
  (Firefox/Chrome NSS) sertifikatı ora da əlavə etmək lazım gələ bilər.
- Sertifikat etibarı / server sağlamlığı yoxlamaları üçün AgentBridge
  **Diagnose** özünü-sınağını işə salın (baxın:
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)).

### Qəzadan sonra qalan firewall qaydaları

`revertTproxy()` tətbiqetmə əməliyyatının tam əksidir və idempotentdir. Rejimin
dayandırılması qaydaları geri qaytarır; OmniRoute sessiyanın ortasında məcburi
dayandırılıbsa, sahibsiz sistem vəziyyətini (DNS saxtalaşdırması, kök CA, sistem
proksisi) geri qaytarmaq üçün AgentBridge **Repair** əməliyyatından
(`POST /api/tools/agent-bridge/repair`) istifadə edin. TPROXY `mangle` qaydaları
və marşrut da yenidən başladılma zamanı avtomatik təmizlənir.

### Sonsuz dövr / proksi öz yönləndirməsini ələ keçirir

Bu, dövrənin qarşısının alınması halıdır. `bypassMark` dəyərinin `mark` dəyərindən
fərqli olduğunu (validasiya bunu məcburi edir) və yönləndirmənin `connectMarked`
istifadə etdiyini (`realForward` daxilində edir) yoxlayın.
[§5 Dövrənin qarşısının alınması](#anti-loop-so_mark) bölməsinə baxın.
