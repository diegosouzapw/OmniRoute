Radar buraxılışın baza kataloqunun (`open-sse/config/freeModelCatalog.data.ts`
faylındakı `FREE_MODEL_BUDGETS`) üzərinə imzalanmış və yenicə kurasiya edilmiş pulsuz model
kataloqu yerləşdirən **istəyə bağlı əlavədir**. O, pulsuz səviyyə ekosistemi buraxılış
tezliyindən daha sürətlə dəyişdiyi üçün mövcuddur — provayderlər buraxılışlar arasında
pulsuz kvotalar əlavə edir, onları azaldır və ya dayandırır, baza kataloqu isə yalnız yeni
versiya yayımlandıqda yenilənə bilər.

**Bu gün pulsuz olan heç nə uzaq lentə görə pulsuz olmaqdan çıxmır.** Radar baza qeydini
heç vaxt ödənişli etmir; o, yalnız oxuma zamanı limit/status sahələrini yeniləyir və
buraxılışlar arasında yeni aşkarlanmış pulsuz modelləri əlavə edə bilər. Operator yenə də
modeli lokal olaraq gizlədə və eyni idarəetmə panelindən onu bərpa edə bilər. Baza kataloqunun
özü diskdə heç vaxt dəyişdirilmir — aşağıdakı
[Oxuma zamanı üst-üstə qat birləşdirmə qaydaları](#read-time-overlay-merge-rules) bölməsinə baxın.

## İctimai elan oxuyucusu

Ümumi elan oxuyucusu Radar funksiya bayrağından ayrıdır. İdarəetmə panelinin Əsas səhifəsi və
Dəyişiklik jurnalı görüntüləyicisi adi `GET` sorğusu vasitəsilə repozitoriyanın ictimai `news.json`
faylını `NEWS_JSON_URL` ünvanından əldə edir (`src/shared/utils/releaseNotes.ts`). Onlar heç bir Radar
parametri, sorğu mətni, provayder konfiqurasiyası, istifadə qeydi və ya lokal rəddetmə vəziyyəti göndərmir.

`news.json`, `parseNewsPayload()` tərəfindən reallaşdırılan qapalı v2 sxemindən istifadə edir:

- `schemaVersion: 2` və ölçüsü məhdudlaşdırılmış `items[]` kolleksiyası;
- sabit və unikal elan `id` dəyərləri;
- açıq şəkildə göstərilmiş `active` və ISO formatlı `publishedAt` sahələri;
- məcburi ingilis dilində mətn və istəyə bağlı lokallaşdırılmış mətn;
- istəyə bağlı, autentifikasiya məlumatı tələb etməyən HTTPS keçidləri və icazə siyahısındakı ikon;
- ən yenidən ən köhnəyə aktiv elan seçimi, lokal mövcud olmadıqda ingilis dilinə keçid və hər ID üzrə lokal rəddetmə.

Parser köhnə forkların Dəyişiklik jurnalı görünüşünü pozmadan miqrasiya edə bilməsi üçün əvvəlki
tək `{ active, title, message, ... }` formatını müvəqqəti olaraq qəbul edir. Etibarsız lentlər
qeyri-aktivdir. Radar-ın işə salınması qeydi `active: false` ilə təqdim olunur; onun `true` olaraq
dəyişdirilməsi birləşdirmədən və yerləşdirmədən sonra ayrıca buraxılış əməliyyatıdır və
`RADAR_ENABLED` dəyərini və ya lent sinxronizasiyası üçün müstəqil qoşulma seçimini dəyişdirmir.

## Bayraq: `RADAR_ENABLED` (standart olaraq söndürülüb)

Radar bütün axın boyunca `RADAR_ENABLED` funksiya bayrağı ilə məhdudlaşdırılır
(`src/shared/constants/featureFlagDefinitions.ts`, kateqoriya `policies`,
`defaultValue: "false"`).

**Bayraq söndürüldükdə bu səth mövcud olmur:**

- Lokal model vəziyyətinin oxunması və yazılması daxil olmaqla, bütün `/api/radar/*`
  son nöqtələri hər hansı Radar moduluna toxunmazdan əvvəl `404` qaytarır.
- İdarəetmə paneli ekranları (`/dashboard/radar`, `/dashboard/radar/setup`,
  `/dashboard/radar/combos`, `/dashboard/radar/offers`, `/dashboard/radar/intel`)
  `notFound()` render edir.
- `getRadarCatalog()` (`src/lib/radar/index.ts`) dəyişdirilməmiş baza vəziyyətini —
  eyni qeyd sayı, eyni dəyərlər və hər bir qeyd üçün `origin: "baseline"` etiketi ilə —
  qaytarır və lent keşini heç vaxt oxumur.
- Heç bir Radar şəbəkə çağırışı edilmir; hər sinxronizasiya modulu `fetch`-ə toxunmazdan
  əvvəl `{ status: "disabled" }` qaytarır.

Bu, ciddi üst çoxluq məhdudiyyətidir: bayrağın aktivləşdirilməsi yalnız _ekranların_
kilidini açır. Bu, məlumatları yükləmir, fon sinxronizasiyasını başlatmır və
marşrutlaşdırmanı və ya model seçimini dəyişdirmir — aşağıdakı ayrıca qoşulma seçiminə baxın.

## Məlumatların sinxronizasiyası AYRICA qoşulma seçimidir — məxfilik vədi

`RADAR_ENABLED` parametrinin aktivləşdirilməsi yalnız istifadəçi interfeysinin kilidini açır.
Lentin sinxronizasiyası üçün `radar_settings.opt_in` daxilində saxlanılan ikinci, müstəqil
qoşulma seçimi tələb olunur (`src/lib/db/radar.ts`, miqrasiya
`136_radar_cache_settings.sql`). `syncRadar()` hər hansı şəbəkə çağırışı etməzdən əvvəl
həm bayrağı, həm də qoşulma seçimini yoxlayır:

```
Bayraq söndürülüb    → { status: "disabled" }   — şəbəkə çağırışı yoxdur
Qoşulma seçimi false → { status: "opt_out" }    — şəbəkə çağırışı yoxdur
```

Hər ikisi aktiv olduqda sinxronizasiya yolu belədir:

1. `x-omniroute-radar-schema: 2` və istəyə bağlı `Authorization: Bearer <supporter key>`
   başlığı ilə `GET <feed base URL>/v1/catalog/latest` (aşağıya baxın). Sxem başlığı olmadıqda
   serverlər standart olaraq ayrıca imzalanmış v1 keçid artefaktından istifadə edir, beləliklə
   quraşdırılmış köhnə klientlər yeniləmələri almağa davam edir.
2. Bu, yalnız endirmə üçün nəzərdə tutulmuş tətbiq axınıdır, lakin yenə də HTTPS sorğusudur.
   Hostinq infrastrukturu mənbə IP kimi adi bağlantı metadatasını qəbul edir. Dəstəkçi açarı
   konfiqurasiya edildikdə sinxronizasiya həmin açarı Bearer başlığında da göndərir ki, xidmət
   hüququ müəyyən edə bilsin. Yuxarıdakı sübut sərhədində göstərilən özəl serverin dəqiq
   reviziyasında lent sorğularının uçotu əl ilə sui-istifadə yoxlaması üçün açar heşlərindən,
   ümumiləşdirilmiş istifadədən və IP-nin gündəlik rotasiya edilən qısaldılmış HMAC dəyərindən
   istifadə edir; həmin cədvəllər nə açarı, nə də IP-ni xam formada saxlayır.
   İnfrastruktur giriş jurnalları və şifrələnmiş çatdırılma çıxış qutusu ayrıca əməliyyat
   sərhədləridir.
3. OmniRoute heç vaxt Radar xidmətinə sorğu mətnlərini, cavabları, söhbətləri, provayder
   autentifikasiya məlumatlarını, model trafikini, işlək qalma müddətini, gecikməni və ya
   lokal provayder konfiqurasiyasını göndərmir.
4. Cavab yoxlanılır, doğrulanır və lokal olaraq keşlənir (bax:
   [Təhlükəsizlik modeli](#security-model)). Radar-ın server tərəfində dəqiq dörd şəbəkə yolu var:
   kataloq üçün `syncRadar()`, yönləndirmələr üçün `syncRadarReferrals()` və yalnız dəstəkçilər
   üçün olan təkliflər və Intel üçün `syncRadarOffers()` / `syncRadarIntel()`.

**Dəstəkçi açarı**, lent xidmətinə hansı səviyyənin təqdim ediləcəyinə qərar verməyə imkan
verən istəyə bağlı Bearer tokenidir (`radar_settings.supporter_key`) (bax:
[Səviyyələr](#tiers-community-and-live)). O:

- Provayder autentifikasiya məlumatları üçün istifadə edilən eyni AES-256-GCM
  `encrypt()`/`decrypt()` köməkçiləri (`src/lib/db/encryption.ts`) ilə **saxlanma zamanı
  şifrələnir**.
- `POST /api/radar/settings` (`{ supporterKey: "omr_" + 40 hex chars }`) vasitəsilə təyin
  edilir və **heç vaxt geri qaytarılmır** — cavab maskalanmış formanı (`omr_****abcd`) qaytarır.
- Onun dəyişdirilməsi və ya silinməsi kataloq, yönləndirmələr, təkliflər və Intel keşlərini
  atomar şəkildə etibarsız edir. Növbəti sinxronizasiya/oxuma yeni hüququ server tərəfində
  müəyyən edir; açarın saxlanılması öz-özlüyündə şəbəkə sorğusu yaratmır və birdəfəlik
  aktivləşdirmə açarını istifadə etmir.
- Sinxronizasiya GET sorğusunda lent xidmətinə Bearer tokeni kimi göndərilir — açar haqqında
  başqa heç nə klientdən kənara çıxmır.

Birləşdirilmiş PR-lər, commit-lər və dəyişdirilmiş sətirlər **yalnız reytinq göstəriciləridir**. İlk 100-lükdən kənarda olan girişə PR sayından asılı olmayaraq töhfəçi icazəsi verilmir. Hostinqdə yerləşdirilən lisenziya şəxsidir və istifadəçiyə göstərilən qayda eyni anda yalnız bir aktiv quraşdırmaya icazə verir. Bu buraxılış avadanlıq kilidinin mövcudluğunu **iddia etmir**: OSS sinxronlaşdırması avadanlığın rəqəmsal izini çıxarmır və ya kriptoqrafik cihaz icarəsini idarə etmir. Yuxarıda göstərilən təsdiqlənmiş şəxsi server reviziyasında tətbiq edilmiş nəzarət giriş hüququnun yoxlanılmasından və eyni canlı açar 24 saat ərzində dördüncü fərqli IP ünvanından göründükdə əl ilə yoxlama siqnalından ibarətdir. Bu siqnal heç vaxt açarı avtomatik bloklamır və ya ləğv etmir. Bərpa itirilmiş açarı ləğv edib əvəzləyir, mövcud bitmə tarixini isə qoruyur; alınmış və ya verilmiş müddəti yenidən başlatmır.

Canlı təkliflər əl ilə seçilir və dəyişə və ya müddəti bitə bilər. Qoşulma ekranı həmçinin dəqiq məxfilik sərhədini göstərir: imzalanmış kataloq/yönləndirmə metadatası endirilir; etibarlı açar əlavə olaraq imzalanmış təkliflərə və Intel-ə girişi açır; Bearer açarı və adi bağlantı metadatası hostinqdə yerləşdirilən xidmətə çatır; prompt-lar, cavablar, söhbətlər, provayder giriş məlumatları, model trafiki, işlək qalma müddəti, gecikmə və yerli provayder konfiqurasiyası isə çatmır.

## Dəstəkçi açarının əldə edilməsi

Aktivləşdirmə ekranında (`/dashboard/radar`) dəstəkçi açarını **əldə etmək** üçün iki keçid mövcuddur. OSS reposunun özü heç vaxt açar vermir, ödəniş kodunu icra etmir və **heç vaxt qiymət göstərmir** — qiymətlər bu repoda deyil, tamamilə keçid edilən səhifələrdə müəyyənləşdirilir və göstərilir (D14 spesifikasiya qərarı).

- **"Mən töhfəçiyəm"** — şəxsi Radar serverində yerləşdirilən GitHub OAuth vasitəsilə tələb prosesini, yəni `RADAR_CONTRIBUTOR_CLAIM_URL` ünvanını (standart olaraq `https://radar.omniroute.online/auth/github`) açır. Bu proses ən son tamamlanmış həftəlik reytinqi yoxlayır: ilk 10-luğa 365 gün, 11–100-cü yerlərə isə 90 gün verilir. İlk 100-lükdən kənarda PR sayı heç vaxt giriş hüququ vermir; bunun əvəzinə proses ayrıca ulduz + izləmə üçün birdəfəlik səviyyəni yoxlayır.
- **"Layihəni dəstəklə"** — birdəfəlik 6 aylıq, 1 illik və ömürlük seçimlər üçün hostinq edilən `RADAR_SUPPORTER_PLANS_URL` səhifəsini (standart olaraq `https://radar.omniroute.online/planos`) açır. OSS səhifəsi yenə də heç bir pul məbləği göstərmir.

Hər iki URL server tərəfində (`src/lib/radar/links.ts`, `RADAR_FEED_URL` ilə eyni mühit dəyişəni ilə əvəzləmə nümunəsi) müəyyənləşdirilir və mövcud `GET /api/radar/settings` cavabı (`contributorClaimUrl`, `supporterPlansUrl`) vasitəsilə idarəetmə panelinə ötürülür — klient komponenti heç vaxt `process.env` dəyişənini özü oxumur.

| Dəyişən                       | Məqsəd                                                                                          |
| ----------------------------- | ----------------------------------------------------------------------------------------------- |
| `RADAR_CONTRIBUTOR_CLAIM_URL` | Töhfəçi tələbi URL-ni əvəz edir (standart olaraq `https://radar.omniroute.online/auth/github`). |
| `RADAR_SUPPORTER_PLANS_URL`   | Dəstəkçi planları URL-ni əvəz edir (standart olaraq `https://radar.omniroute.online/planos`).   |

### İtirilmiş dəstəkçi açarının bərpası

Hostinq edilən xidmətin bərpa giriş nöqtəsi `https://radar.omniroute.online/recover` ünvanıdır; bu keçid planlar səhifəsində də mövcuddur. Bərpa prosesi tamamilə OSS klientindən kənarda qalır, çünki lokal quraşdırma heç vaxt alıcının/töhfəçinin e-poçt ünvanını qəbul etmir və şifrələnmiş parametrlərdən xam açarı yenidən yarada bilmir.

1. Açarla əlaqələndirilmiş e-poçt ünvanını təqdim edin. Bərpa edilə bilən lisenziyanın mövcud olub-olmamasından asılı olmayaraq, xidmət eyni qəbul səhifəsini qaytarır; beləliklə, forma hesabların mövcudluğunu açıqlamır.
2. Uyğun olduğu halda, çatdırılma işçisi qısamüddətli, birdəfəlik keçid göndərir. Keçidin açılması tokeni dərhal keçici, şifrələnmiş `HttpOnly`/`Secure` kukisinə köçürür və təmiz `/recover` URL-nə yönləndirir; səhifədə token, e-poçt ünvanı, köhnə açar və ya əvəzedici açar olmur.
3. Ləğvetməni təsdiqləyin. Şəxsi xidmət əvvəlki açarı ləğv edir, eyni plan/son istifadə tarixi ilə əvəzedici açar yaradır və bir tranzaksiya daxilində onu e-poçtla göndərilmək üçün növbəyə əlavə edir. Əvəzedici açar heç vaxt brauzerə qaytarılmır.
4. Əvəzedici açarı `/dashboard/radar` səhifəsinə yapışdırın. Köhnə açar artıq `community` səviyyəsinə enməlidir; əvəzedici açar isə təsdiqlənmiş `live` sinxronizasiyası yaratmalıdır. Eyni bərpa keçidinin yenidən açılması ümumi etibarsız/vaxtı bitmiş cavabı ilə uğursuz olmalıdır.

Hostinq edilən bərpa marşrutu və poçt işçisi kodda mövcud ola bilər, lakin müəyyən yerləşdirmədə əlçatmaz qala bilər. Server yerləşdirilməyənə, çatdırılma provayderi nəzarət edilən alıcı ilə konfiqurasiya olunmayana və tam birdəfəlik keçid sınaqdan keçirilməyənə qədər bu prosesi istehsala hazır hesab etməyin.

Ziyarətçi açar (`omr_` + 40 onaltılıq simvol) əldə etdikdən sonra aktivləşdirmə ekranında (`src/app/(dashboard)/dashboard/radar/page.tsx`) əsas üsul kimi açarı yapışdırmaq üçün daxiletmə sahəsi mövcuddur: açarın yapışdırılması və təqdim edilməsi bir çağırışla `POST /api/radar/settings` sorğusunu (`{ optIn: true, supporterKey }`) göndərir — açarın yapışdırılması həm onu təyin edir, həm də iştiraka razılıq verir və ekranı açır. Format (`omr_` + 40 onaltılıq simvol) UX rahatlığı üçün əvvəlcə klient tərəfində ortaq `isValidSupporterKeyFormat()` köməkçi funksiyası (`src/lib/radar/supporterKey.ts`) ilə yoxlanılır; istənilən halda serverin Zod sxemi səlahiyyətli yoxlamadır. Açar təyin edildikdən sonra aktivləşdirmə ekranı boş daxiletmə sahəsi əvəzinə maskalanmış formanı (`GET /api/radar/settings` cavabından `supporterKeyMasked`) və yeni açar yapışdırmaq üçün "açarı dəyiş" idarəetmə elementini göstərir — xam açar heç vaxt yenidən göstərilmir. Yuxarıdakı iki tələb/plan düyməsi əvvəlcə açarı _əldə etmək_ üçün istifadə olunan üsul olaraq qalır; artıq açarı olan operator onu məhz bu daxiletmə sahəsində aktivləşdirir.

### Başdan sona aktivləşdirmə və istiqamətləndirilən quraşdırma

Şəxsi lent xidməti ilə bu OSS klienti arasında məqsədli şəkildə dar sərhəd mövcuddur: xidmət dəstəkçi açarını verir və doğrulayır, lokal OmniRoute quraşdırması isə açarı şifrələyir, imzalanmış artefaktları server tərəfində sinxronlaşdırır və provayder quraşdırılmasını istiqamətləndirir. Dəstəklənən doğrulama ardıcıllığı belədir:

1. İştirakçı sorğusu, planlar/ödəniş, bərpa prosesi və ya səlahiyyətli özəl server operatorundan yeni verilmiş və ya bərpa edilmiş açarı əldə edin. Xam açarı jurnallara, ekran görüntülərinə, problem şərhlərinə və ya komanda sətri arqumentlərinə yapışdırmayın.
2. Lokal OmniRoute quraşdırmasında `RADAR_ENABLED` funksiya bayrağını aktivləşdirin. Bu, istifadəçi interfeysini əlçatan edir, lakin ayrıca qoşulma seçimi yadda saxlanılanadək şəbəkə fəaliyyəti baş vermir.
3. `/dashboard/radar` səhifəsini açın, açarı yapışdırın və aktivləşdirin. Brauzer lokal olaraq `{ optIn: true, supporterKey }` ilə bir dəfə `POST /api/radar/settings` sorğusu göndərir; açar lokal olaraq şifrələnir və cavab yalnız `omr_****<last4>` ehtiva edir.
4. Aktivləşdirmə ekranının kataloq sinxronizasiyasını tamamlamasına imkan verin və ya **İndi sinxronlaşdırın** seçin. Səhifədə `live` statusunun, lent versiyasının və əldəetmə vaxtının göstərildiyini təsdiqləyin. Autentifikasiya edilmiş lokal diaqnostika üçün `GET /api/radar/status` açarı qaytarmadan qoşulma seçiminin/açarın mövcudluğunu və dörd keşin vəziyyətini bildirir. `POST /api/radar/sync-all` kataloqu, yönləndirmələri, təklifləri və Intel-i açıq şəkildə yeniləyə bilər.
5. `/dashboard/radar/setup?provider=<provider>` səhifəsini açın. Provayderə məxsus giriş məlumatları URL-sinə keçin, **API açarı əlavə edin** seçin, real provayder forması vasitəsilə yadda saxlayın, bələdçiyə qayıdın və **Bağlantını sınaqdan keçirin** əməliyyatını başladın. Bələdçi standart `/api/providers` və `/api/providers/<connection-id>/test` marşrutlarından istifadə edir; ayrıca Radar giriş məlumatı yaratmır.
6. Ən azı iki uyğun provayder bağlantısı aktiv olduqdan sonra `/dashboard/radar/combos` səhifəsini açın. Təklif olunan ailəni nəzərdən keçirin və mövcud combo API-si vasitəsilə kombinasiyanı yaradın. Təkliflər və Intel ayrıca, yalnız canlı rejimdə işləyən imzalanmış keşlər olaraq qalır və onlar üçün ayrılmış Radar səhifələrində yoxlanıla bilər.
7. `/dashboard/radar` və quraşdırma səhifəsini yenidən yükləyin. Qoşulma seçimi, maskalanmış açar vəziyyəti, təsdiqlənmiş keş, yadda saxlanmış provayder bağlantısı və sınaq əməliyyatı yenidən yükləmədən sonra saxlanmalıdır. Sübutları yalnız xam açar və provayder giriş məlumatları artıq görünmədikdən sonra qeydə alın.

Açarın yadda saxlanması özlüyündə canlı istifadə hüququnun sübutu deyil. Sübut özəl xidmətin `GET /v1/license/check` nəticəsinin, OSS kataloqu tərəfindən təqdim edilən `live` səviyyəsinin, təsdiqlənmiş imzalanmış keşin və real provayder bağlantısı/sınaq prosesinin birləşməsidir. Etibarsız, vaxtı bitmiş və ya ləğv edilmiş açar kataloqu təhlükəsiz şəkildə `community` səviyyəsinə endirir; bu, canlı açarın uğurlu təsdiqlənməsi kimi bildirilməməlidir.

### Özəl admin paneli keçidi

`RADAR_ADMIN_URL` istəyə bağlı olaraq Xərclər yan paneli bölməsində istifadəçi üçün nəzərdə tutulmuş Radar elementindən dərhal sonra **Radar Admin ↗** əlavə edir. Onun qəsdən standart dəyəri yoxdur: dəyişən təyin edilmədikdə və ya etibarsız olduqda statik yan paneldə, əmrlər palitrasında və yan panelin fərdiləşdirilməsi ekranında heç bir admin elementi və özəl URL olmur.

Dəyər server tərəfində müəyyən edilir və idarəetmə autentifikasiyalı `GET /api/settings` cavabı vasitəsilə yalnız autentifikasiya edilmiş idarəetmə paneli sessiyasına və ya lokal girişsiz ilkin işəsalma zamanı etibarlı loopback sahibinə ötürülür. CLI, daxili xidmət və manage-scope API açarı autentifikasiyası onu almır. Brauzer `noopener noreferrer` ilə açılan xarici keçidi yaratmazdan əvvəl cavabı yenidən doğrulayır.

Giriş məlumatları olmayan HTTPS tunel/tailnet URL-sindən istifadə edin. Adi HTTP yalnız `http://127.0.0.1:9351` kimi loopback SSH yönləndirməsi üçün qəbul edilir; digər sxemlər, daxil edilmiş giriş məlumatları, düzgün qurulmamış URL-lər və uzaq HTTP ünvanları təhlükəsiz şəkildə rədd edilir və naviqasiya qeyri-aktiv qalır.

## Təhlükəsizlik modeli

### Dəqiq baytlar üzərində Ed25519 imzası

Lent yükü Ed25519 ilə imzalanır. `verifyFeedBytes()`
(`src/lib/radar/verify.ts`) şəbəkə üzərindən alınan **dəqiq cavab baytları**
üzərindəki imzanı yoxlayır — yük yoxlamadan əvvəl heç vaxt yenidən
serializasiya edilmir, buna görə də bayt-bayt yenidən kodlama imza yoxlamasını
gizli şəkildə etibarsız edə və ya keçə bilməz. Yoxlama uğursuz olduqda
(`invalid_signature`), yük təhlil edilməmiş və ya keşlənməmiş sinxronizasiya
dayandırılır.

### Bərkidilmiş açıq açar + rotasiya

Yoxlama üçün açıq açar `src/lib/radar/pinnedKeys.ts` faylında
(`PINNED_FEED_PUBLIC_KEYS`) bərkidilib. Bu, massivdir və bunun sayəsində rotasiyadan
əvvəl yeni açar əvvələ əlavə edilə bilər, əvvəlki açarla imzalanmış köhnə keşlənmiş
lentlər isə yenidən sinxronizasiya edilənədək etibarlı qalır.

### Fork-lar üçün əlverişli mühit dəyişəni əvəzləmələri

İki mühit dəyişəni fork-lara və sistemi öz serverində yerləşdirənlərə müştərini
standart OmniRoute xidməti əvəzinə öz lentlərinə yönəltməyə imkan verir — aşağıdakı
[Lenti öz serverinizdə necə yerləşdirməli](#how-to-self-host-a-feed) bölməsinə baxın:

| Dəyişən             | Məqsəd                                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------ |
| `RADAR_FEED_URL`    | Lentin baza URL-ni əvəzləyir (standart `https://radar.omniroute.online`).                              |
| `RADAR_FEED_PUBKEY` | Bərkidilmiş açıq açarı (base64-DER SPKI və ya PEM) əvəzləyərək daxili massivi bu tək açarla əvəz edir. |

### Minimum versiya həddi

`syncRadar()` endirilmiş lentin `version` dəyəri hazırda keşlənmiş versiyadan qəti
şəkildə daha yeni olmadıqda onu rədd edir (`compareVersions()`, nöqtələrlə ayrılmış
`YYYY.MM.DD.n` müqayisəsi) — `{ status: "stale" }`. Bu, təhlükəyə məruz qalmış və ya
yanlış konfiqurasiya edilmiş lent son nöqtəsinin müştərini daha köhnə, fərqli imzalanmış
yükə geri qaytarmasının qarşısını alır.

### İki tarix və hər ikisinin saxlanmasının səbəbi

Keşlənmiş lent iki fərqli tarix daşıyır və onların qarışdırılmasının qarşısını almaq
üçün hər ikisi saxlanılır:

| Sahə          | Mənbə                   | Cavab verdiyi sual                    |
| ------------- | ----------------------- | ------------------------------------- |
| `generatedAt` | imzalanmış lent gövdəsi | **verilənlərin** neçə yaşı var        |
| `fetchedAt`   | bu quraşdırmanın saatı  | bu quraşdırma onu nə vaxt **endirib** |

Bir neçə dəqiqə əvvəl əldə edilmiş lent həftələrlə köhnə göstəricilər daşıya bilər,
buna görə də təkcə `fetchedAt` operatora üst qatın əsaslandığı baza məlumatlarından
daha yeni olub-olmadığını deyə bilməz. Hər ikisi `radar_feed_cache` daxilində saxlanılır,
`getRadarCatalog().meta` tərəfindən qaytarılır və `GET /api/radar/status` vasitəsilə
ayrıca bildirilir. `generated_at` sütunu mövcud olmamışdan əvvəl keşlənmiş sətir
(miqrasiya 163) `null` kimi oxunur — naməlum dəyər əldəetmə vaxtını götürmək əvəzinə
naməlum olaraq qalır. `radar_referrals_cache` miqrasiya 142-dən etibarən öz
`generated_at` dəyərini saxlayır.

Yuxarıdakı minimum versiya həddi tarixlərdən hər hansı birini deyil, `version` dəyərini
müqayisə edir.

Hər ikisi məqsədli olmaqla iki boşluq qalır: idarə paneli hələ də yalnız `Last fetched`
göstərir, buna görə orada qurulma tarixini göstərmək üçün yeni etiket (və onun 41 lokal
tərcüməsi) tələb olunur; təkliflər və analitik məlumat keşləri isə, lent sxemlərində
belə bir tarix olsa da, qurulma tarixini ümumiyyətlə saxlamır — buna görə də `GET
/api/radar/status` həmin iki keş üçün "naməlum" kimi başa düşülə biləcək `null` dəyərini
bildirmək əvəzinə bu sahəni buraxır.

### Sxem yoxlaması

Endirilmiş baytlar imza yoxlamasından **sonra** təhlil edilir və `RadarFeedSchema`
(`src/lib/radar/feedSchema.ts`, Zod sxemi) ilə yoxlanılır. Sxem uyğunsuzluğu
`{ status: "invalid_schema" }` qaytarır və keşə toxunulmur. Keşlənmiş yük hər oxunuşda
(`getRadarCatalog()`) müdafiə məqsədilə yenidən yoxlanılır — zədələnmiş və ya əl ilə
redaktə edilmiş keş sətri təqdim edilmək əvəzinə baza məlumatlarına geri qayıdır.

### Cavab ölçüsü limiti (10 MB)

`syncRadar()` lent cavabının gövdəsinə **10 MB sərt limit** tətbiq edir — imzalanmış
lent KB miqyaslı JSON sənədidir, buna görə də bu həddi aşan hər şey qanuni kataloqdan
deyil, yanlış konfiqurasiya edilmiş və ya zərərli `RADAR_FEED_URL`-dən (yaxud yararsız
məlumat təqdim edən yuxarı axın mənbəyindən) xəbər verir. Tətbiq iki səviyyəlidir:

1. İlkin `Content-Length` yoxlaması başlıqda limitdən yüksək dəyər göstərildikdə
   gövdənin oxunmasını tamamilə atlayır.
2. Gövdə oxunarkən aparılan məcmu cəm yoxlaması `Content-Length` olmadıqda və ya real
   ölçünü olduğundan az göstərdikdə belə limiti tətbiq edir — təkcə başlığa heç vaxt
   etibar edilmir. Toplanmış hissələrin birləşdirilməsi sonrakı Ed25519 imza yoxlaması
   üçün tələb olunan dəqiq baytları qoruyur.

Limitin aşılması `{ status: "too_large" }` qaytarır və keşə toxunmur; bu, digər bütün
sinxronizasiya xətaları (`invalid_signature`, `invalid_schema`, `stale`) ilə eyni
dağıdıcı olmayan nümunəyə uyğundur.

## Səviyyələr: `community` və `live`

Lent sxemi sorğuya (dəstəkçi açarının mövcudluğuna və etibarlılığına) əsasən lent xidməti tərəfindən **server tərəfində** müəyyən edilən `tier: "community" | "live"` sahəsini daşıyır
— müştəri heç vaxt öz səviyyəsini özü müəyyən etmir.

- **`community`** — ən yeni məlumatlardan təxminən 30 gün geri qalan pulsuz kataloqdur.
  Autentifikasiya olunmamış və ya etibarsız açarla göndərilən sorğu bunu alır.
- **`live`** — etibarlı dəstəkçi açarı daşıyan sorğulara təqdim edilən ən yeni kataloqdur.

**Etibarsız və ya vaxtı bitmiş dəstəkçi açarı `community` səviyyəsinə endirilir — bu, heç vaxt
xəta sayılmır.** Sinxronizasiya yolu yalnız imza/sxem/versiya xətalarını (hamısı
bərpa oluna biləndir və keşlənmiş vəziyyət üçün ölümcül deyil) uğurlu `{ status:
"updated", version, tier }` nəticəsindən fərqləndirir. Müştərinin idarə etməli olduğu
səviyyəyə xas ayrıca xəta yolu yoxdur.

### Təqdim edilən səviyyə imzalanmış gövdədən deyil, cavab başlığından gəlir

İmzalanmış lent **gövdəsinin** `tier` sahəsi həmişə `"live"` olur — lent xidməti hər versiya üçün
**iki imzalanmış artefakt** təqdim edir: live cari kampaniyaları ehtiva edir, community isə
onları buraxır. Hər bir artefakt öz dəqiq baytları üzərindən imzalanır. Bununla belə, gövdə
istifadə hüququ ilə bağlı qərarın mənbəyi deyil; sorğu üçün faktiki seçilmiş səviyyə sorğunun
`Authorization` açarına əsasən server tərəfində müəyyən edilir və **`x-omniroute-feed-tier` cavab başlığında**
daşınır.

`syncRadar()` (`src/lib/radar/sync.ts::parseServedTierHeader()`) müştərinin etibar etməli olduğu
səviyyəni müəyyən edən yeganə yerdir:

1. `x-omniroute-feed-tier` dəyərini `RadarTierSchema` (Zod) ilə təhlil edin — başlıq yoxdursa və ya
   dəyər tam olaraq `"community"` yaxud `"live"` deyilsə, o, **mövcud
   deyilmiş kimi** qəbul edilir (heç vaxt olduğu kimi keşə/UI-a etibarlı dəyər kimi ötürülmür; bu,
   başlıqdan əvvəlki köhnə lent serverlərini də əhatə edir).
2. Yalnız 1-ci addım heç bir nəticə vermədikdə imzalanmış gövdənin `tier` sahəsinə (həmişə `"live"`)
   geri qayıdın.
3. Həll edilmiş səviyyə keşlənir və `{ status: "updated",
version, tier }` kimi qaytarılır — idarəetmə panelinin göstərdiyi dəyər budur, gövdənin xam
   sahəsi deyil.

## Oxuma zamanı örtük birləşdirmə qaydaları

`applyFeed()` (`src/lib/radar/applyFeed.ts`) keşlənmiş lenti statik baza üzərinə
**oxuma zamanı**, `getRadarCatalog()` daxilində birləşdirir. Baza massivi
(`FREE_MODEL_BUDGETS`) heç vaxt dəyişdirilmir — hər çağırışda yeni `MergedEntry[]` hesablanır.

Üstünlük sırasına görə dörd qayda:

1. **Lent heç vaxt lokal fərdiləşdirməni əvəz etmir.** Hər sahə üzrə: operator
   qeyddəki sahəni fərdiləşdiribsə (`provider:modelId` açarlı `localOverrides` xəritəsi),
   lentin həmin konkret sahə üçün dəyəri nəzərə alınmır — operatorun dəyəri üstün olur.
2. **`enabled: false` qeydi deaktiv edir və mənşəni göstərir.** Qeydi söndürən lent qeydi
   birləşdirilmiş nəticədə `enabled: false` və `disabledBy: "radar"` təyin edir,
   beləliklə UI qeydin niyə mövcud vəziyyətdən deaktiv vəziyyətə keçdiyini izah edə bilər.
3. **Lentdə olmayan, istifadəçi tərəfindən əlavə edilmiş qeyd toxunulmaz qalır.** Yalnız
   bazada mövcud olan (və ya lokal olaraq əlavə edilmiş) və uyğun lent qeydi olmayan qeydlər
   dəyişdirilmədən ötürülür.
4. **Silinmə nişanı qoyulmuş qeyd heç vaxt bərpa edilmir.** Operator qeydi açıq şəkildə silibsə
   (`tombstones` çoxluğu), lentin sonrakı versiyada həmin `provider:modelId` dəyərini yenidən
   əlavə etməsi onu geri qaytarmır.

Redaktə edilə bilən sahələr və silinmə nişanları
`radar_local_model_state` daxilində saxlanılır (miqrasiya `153_radar_local_model_state.sql`). İctimai DB
adapteri (`src/lib/db/radar.ts`) həmin sətirləri `applyFeed()` tərəfindən istifadə olunan
`localOverrides` xəritəsinə və `tombstones` çoxluğuna çevirir; istehsal mühitindəki
`getRadarCatalog()` bu vəziyyəti bayraq, keş və sxem yoxlamaları keçdikdən sonra yükləyir.
Operator yalnız `displayName` və `enabled` sahələrini redaktə edə bilər. Provayder/model identikliyi,
lent mənşəyi, kvota, imkanlar, ToS və quraşdırma məlumatları bu interfeys vasitəsilə yazıla bilməz.

İdarəetmə paneli dörd lokal əməliyyat təqdim edir:

- **Redaktə et** lokal ekran adını və aktivlik vəziyyətini dəyişir.
- **Lokal dəyişiklikləri sıfırla** silinmə nişanını dəyişdirmədən hər iki redaktə edilə bilən sahəni təmizləyir.
- **Gizlət** silinmə nişanı yaradır ki, sonrakı lent yeniləmələri sətri yenidən yarada bilməsin.
- **Bərpa et** silinmə nişanını götürür; ayrıca saxlanmış hər hansı fərdiləşdirmə qüvvədə qalır.

Lentdəki `enabled: false` təhlükəsizlik istisnası olaraq qalır: köhnəlmiş lokal
`enabled: true` dəyərindən üstün olur, birləşdirilmiş qeydi deaktiv saxlayır və
`disabledBy: "radar"` qeyd edir.

Kataloq nəşrləri `schemaVersion: 2` istifadə edir. `contextWindow` və `tools`, `vision` və
`thinking` sahələrinin hər biri müstəqil olaraq `number | null` / `boolean | null` tipindədir: `null`
naməlum deməkdir, `false` isə D16 ilə təsdiqlənmiş rəsmi provayder mənbəsinin imkanın mövcud olmadığını
açıq şəkildə bildirməsi deməkdir. Daxili OmniRoute reyestri/model spesifikasiyası bayraqları heç vaxt
birbaşa lent faktlarına çevrilmir. Müştəri hələ də v1 ani görüntülərini qəbul edir; köhnə qurucu
`false` dəyərini yoxluq əvəzedicisi kimi istifadə etdiyinə görə, v1-dəki `false` naməlum olaraq
normallaşdırılır, v1-dəki `true` isə fakt kimi qalır. Naməlum sxem versiyaları bağlı rejimdə uğursuz
olur və son etibarlı keş əlçatan qalır. Kontekst/imkan dəyəri null olmayan hər bir v2 modeli
giriş məlumatı tələb etməyən HTTPS `metadataEvidenceUrls[]` daşımalıdır; əks halda sxem yoxlaması
uğursuz olur və keş əvəz edilmir. Kataloq cədvəli hər üç vəziyyəti `✓`, `✕` və `?` kimi göstərir.

### İstiqamətləndirilən kombinasiyalar və MCP girişi

Təsdiqlənmiş `familyId` dəyərləri oxuma zamanı örtükdən sonra saxlanılır və saf
`buildRadarComboSuggestions()` modulunu (`src/lib/radar/comboSuggestions.ts`) idarə edir. Ailə yalnız
ən azı iki fərqli provayderin aktiv bağlantıları olduqda və dəqiq seçilmiş model ID-sini təqdim
etdikdə təklif olunur. Deaktiv modellər, qeyri-aktiv provayderlər, çatışmayan model ID-ləri, təküzvlü
ailələr və qeyri-müəyyən alias/prefiks uyğunluqları bağlı rejimdə rədd edilir. Təkliflər mövcud
`priority` strategiyasından istifadə edərək ən böyük təkrarlanan aylıq büdcəni birinci sıralayır;
UI onları yalnız `POST /api/combos` vasitəsilə yaradır.

İstiqamətləndirilən UI `/dashboard/radar/combos` ünvanında yerləşir. O, yalnız lokal
`GET /api/radar/catalog` və `GET /api/combos/builder/options` son nöqtələrini oxuyur. O, heç vaxt Radar sinxronizasiyasını işə salmır,
provayder giriş məlumatlarını oxumur və ya birbaşa combo verilənlər bazasına yazmır.

MCP müştəriləri eyni lokal proyeksiyanı `omniroute_radar_catalog` (`read:radar`) vasitəsilə oxuya bilər. İxtiyari
`provider`, `familyId` və `enabledOnly` filtrləri bir lokal
`GET /api/radar/catalog` sorğusundan sonra tətbiq edilir. Onun qapalı çıxışına kataloq metadatası, həmçinin provayder/model,
göstərilən ad, `familyId`, kvota, imkanlar, aktivlik vəziyyəti, mənşə və `disabledBy` daxildir; quraşdırma URL-ləri,
addımlar, bağlantılar, e-poçt ünvanları, açarlar və yönləndirmə məlumatları heç vaxt qaytarılmır. Bu alət
yalnız oxuma üçündür və heç vaxt `/api/radar/sync` çağırmır.

### Mənşə göstəriciləri

Birləşdirilmiş hər bir qeyddə UI-nin nişan kimi göstərdiyi `origin` sahəsi var:

- `"baseline"` — statik buraxılış kataloqundan dəyişdirilmədən götürülüb.
- `"radar"` — bir və ya daha çox sahə lent vasitəsilə yenilənib.
- `"local"` — operatorun bu qeyddə ən azı bir lokal əvəzləməsi var (lokal
  əvəzləmələr, lentin nə bildirməsindən asılı olmayaraq, 1-ci qaydaya əsasən həmişə üstün tutulur).

### Autentifikasiya

Bütün Radar son nöqtələri `isAuthenticated()`
(`src/shared/utils/apiAuth.ts`) vasitəsilə autentifikasiya tələb edir — idarə paneli
sessiya kukisi və ya idarəetmə əhatəli API açarı; bu, `/api/settings/*` hissəsinin
qalanını qoruyan eyni keçiddir. Bayrağın söndürülməsi ilə bağlı `404` yoxlaması həmişə
autentifikasiya yoxlamasından **əvvəl** icra olunur, buna görə `RADAR_ENABLED`
söndürülmüş quraşdırma bayt səviyyəsində eyni qalır (səthin mövcud olmadığını öyrənmək
üçün autentifikasiya sorğusu verilmir); bayraq aktiv edildikdən sonra autentifikasiya
olunmamış sorğu hər hansı DB oxuma və ya yazma əməliyyatından əvvəl `401` alır.
Autentifikasiya vəziyyətindən asılı olmayaraq `GET /api/radar/settings` xam dəstəkçi
açarını heç vaxt qaytarmır — yalnız maskalanmış formanı və `hasSupporterKey` məntiqi
dəyərini qaytarır.

## Dəstəkçi təklifləri

Təkliflər öz imzalanmış artefaktından, `GET /v1/offers/latest` istifadə edir və heç vaxt kataloq və ya
yönləndirmələr keşini paylaşmır. Server son nöqtəsi etibarlı və aktiv dəstəkçi Bearer açarı tələb edir;
icma üçün ehtiyat variant yoxdur. Buna görə də `syncRadarOffers()` funksiya bayrağı söndürüldükdə,
operator iştirak etməyə razılıq vermədikdə və ya heç bir dəstəkçi açarı konfiqurasiya edilmədikdə
şəbəkəyə müraciət etməzdən əvvəl dayanır.

Uğurlu GET sorğusundan sonra klient cavabın dəqiq baytları üzərindəki Ed25519 imzasını yoxlayır,
`RadarOffersFeedSchema` sxemini doğrulayır, həm imzalanmış gövdənin, həm də
`x-omniroute-feed-tier` başlığının `live` dəyərini göstərməsini tələb edir, yalnız ciddi şəkildə daha
yeni nöqtəli versiyanı qəbul edir və yalnız bundan sonra `radar_offers_cache` keşini atomar şəkildə
əvəz edir (`144_radar_offers_cache.sql` miqrasiyası). Digər lentlərdə istifadə olunan başlıq və axın
üçün eyni 10 MB həddi burada da tətbiq olunur. İmza, sxem, səviyyə, təkrar ötürmə, ölçü, HTTP və
şəbəkə xətalarının hamısı sonuncu doğrulanmış keşi qoruyub saxlayır.

Qapalı təklif strukturu müqayisə edilə bilən üç fayda növünü dəstəkləyir: baza bəndləri ilə faiz,
valyutanın kiçik vahidləri ilə kredit və ya sınaq günləri. Tərəfdaş təklifi eyni növdən olan açıq
baza göstəricisini ehtiva etməli və onun faydası ciddi şəkildə daha yüksək olmalıdır; rəsmi
təkliflərin tərəfdaş baza göstəricisi yoxdur. URL-lər giriş məlumatları ehtiva etməyən HTTPS
ünvanları olmalıdır. `getRadarOffers()` keşlənmiş faydalı yükü qoruyucu şəkildə yenidən doğrulayır
və hər lokal oxunuş zamanı müddəti bitmiş qeydləri filtrləyir; `/dashboard/radar/offers`
vizuallaşdırmadan əvvəl müddəti bitmiş qeydləri yenidən filtrləyir, mövcud olduqda portuqal dilində
mətndən, əks halda ingilis dilində ehtiyat mətndən istifadə edir və tərəfdaş təkliflərini açıq şəkildə
işarələyir.

Brauzer yalnız lokal marşrutlara müraciət edir: maskalanmış parametrlər şəklini oxuyur, server
tərəfində yeniləmə üçün `POST /api/radar/offers/sync` sorğusu göndərir, sonra isə
`GET /api/radar/offers` sorğusu ilə məlumatları oxuyur. Açar olmadıqda lent sorğusu göndərməyə cəhd
etmək əvəzinə mövcud töhfəçi/dəstək keçidlərini göstərir. Xarici təklif keçidləri `noopener noreferrer`
ilə yeni tabda açılır. Bu buraxılışda heç bir `radar_offers` MCP aləti təqdim edilmir.

## Radar Intel, dəstəkçi nişanı və CLI

Intel `GET /v1/intel/latest` ünvanındakı imzalanmış artefaktdır. Qapalı `RadarIntelFeedSchema`
yalnız şəxsi kuratorun təsdiqlənmiş müqayisələr əsasında əldə etdiyi Radar-a məxsus ELO reytinqlərini
və imzalanmış kataloq şəkillərindən əldə edilmiş kataloq yaşı/sayı üzrə faktiki fərqləri qəbul edir.
Metodologiyada ilkin reytinq 1000 və K=32 olaraq sabitləşdirilib. Heç bir müqayisə təsdiqlənmədikdə
boş reytinq etibarlıdır; klient heç vaxt süni reytinq yaratmır.

`syncRadarIntel()` təkliflərlə eyni server tərəfli Bearer autentifikasiyasını, 30 saniyəlik vaxt
limitini, 10 MiB axın həddini, dəqiq baytlar üzrə Ed25519 yoxlamasını, ciddi sxem yoxlamasını, gövdə
və başlıq üçün `live` tələbini, versiyanın minimum həddini və son etibarlı keşin qorunmasını tətbiq
edir. Doğrulanmış aktiv şəkil saxlanıldıqdan sonra klient `radar:<sha256(supporter key)>` dəyərini
yaradır, yalnız həmin birtərəfli identifikatoru saxlayır və xüsusi `radar_supporter` tanınma hadisəsini
yayır. Onun `radar-supporter` nişanı idempotentdir və sıfır XP verir; o, heç vaxt liderlik cədvəllərini
yeniləmir və ya `token_share` hadisəsindən təkrar istifadə etmir. `/dashboard/radar/intel` nişanı
yalnız doğrulanmış lokal keş metadatası əsasında göstərir.

CLI `omniroute radar status` və `omniroute radar sync` əmrlərini təqdim edir. Hər ikisi yalnız lokal
OmniRoute API ilə əlaqə saxlayır. `status` yalnız oxuma üçün `GET /api/radar/status` sorğusunu icra
edir; `sync` bir `POST /api/radar/sync-all` sorğusu göndərir və hər lent üçün nəticə çap edir. Heç bir
əmr dəstəkçi açarını oxumur, qəbul etmir və ya çap etmir və heç biri Radar xidməti ilə birbaşa əlaqə
saxlamır.

## Referal keçidləri (pulsuz kreditlər)

Referal keçidləri kataloq lentindən ayrı olan **müstəqil, həmişə aktual** lentdən təqdim edilir —
`GET /v1/referrals/latest`. Bu, məqsədli şəkildə belə edilib: icma səviyyəsindəki
kataloq lenti 30 günə qədər köhnə ola bilən ani görüntüdür, buna görə də ondan çıxarılan
referal keçidi serverin real keçid siyahısından eyni müddət qədər geri qalırdı
(yeni əlavə edilmiş referal pulsuz/icma istifadəçisinə bir aya qədər çatmaya bilərdi).
Referallar lenti özünün daha qısa intervalı ilə sinxronizasiya olunaraq bu gecikməni aradan qaldırır.

```ts
// GET /v1/referrals/latest cavab gövdəsi (Ed25519 ilə imzalanıb, kataloq lenti ilə
// eyni bərkidilmiş açardan istifadə edir):
{
  feed: "omniroute-radar-referrals",
  schemaVersion: 1,
  generatedAt: string,           // ISO — deterministikdir: referal keçidləri üzrə max(updatedAt),
                                  // buna görə iki eyni sorğu tamamilə eyni
                                  // imzalanmış baytları/imzanı yaradır
  referrals: {
    fixed: RadarReferral[],      // autentifikasiya olmayan/icma səviyyəsi də daxil olmaqla HƏR səviyyədə mövcuddur
    campaigns: RadarReferral[],  // yalnız etibarlı aktiv (dəstəkçi) Bearer açarı üçün doldurulur;
                                  // autentifikasiyasız/müddəti bitmiş açarlı sorğular [] alır
  },
}
// RadarReferral = { provider, url, kind: "fixo" | "campanha", validUntil,
//                    requiredAction, isDefault }
```

Kataloq lentindən fərqli olaraq, bu gövdədə ümumiyyətlə `tier` sahəsi yoxdur — server
`Authorization` açarına əsasən hər sorğu üçün nələrin daxil ediləcəyinə qərar verir, buna görə də
`x-omniroute-feed-tier` cavab başlığı təqdim edilən səviyyə üçün YEGANƏ mənbədir
(`referralsSync.ts::syncRadarReferrals`); mövcud olmayan/tanınmayan başlıq ən az imtiyazlı
fərziyyə olan `"community"` səviyyəsinə endirilir. `RadarReferralsFeedSchema`
(`src/lib/radar/referralsFeedSchema.ts`) bütün gövdəni yoxlayır və hər iki lentin
ayrı-ayrı referalları eyni qaydada yoxlaması üçün `feedSchema.ts` faylından ixrac edilən eyni
referal üzrə `RadarReferralSchema` sxemindən təkrar istifadə edir. Hər `RadarReferral.url`
`https://` ilə başlamalıdır — `http://` URL-i sxem yoxlamasından keçmir.

`RadarFeedSchema` (`feedSchema.ts`) üzərindəki kataloqa daxil edilmiş KÖHNƏ `referrals`
sahəsi artıq keşlənmiş kataloq lentləri ilə geriyə uyğunluq üçün saxlanılır, lakin
`getRadarReferrals()` artıq onu oxumur — aşağıdakı [Aksessora](#accessor) baxın.

### Sinxronizasiya

`syncRadarReferrals()` (`src/lib/radar/referralsSync.ts`) referallar üçün şəbəkəyə
müraciət edən YEGANƏ moduldur və `syncRadar()` müqaviləsini tam olaraq təkrarlayır:
bayraq söndürülüb → `disabled`; qoşulma seçimi false → `opt_out`;
`${RADAR_FEED_URL}/v1/referrals/latest` ünvanını endirir (kataloqla eyni
`RADAR_FEED_URL`/`RADAR_FEED_PUBKEY` fork əvəzləmələri), dəqiq cavab baytları üzərindəki
Ed25519 imzasını yoxlayır (`verifyFeedBytes`), `RadarReferralsFeedSchema` əsasında
validasiya edir və `radar_referrals_cache` cədvəlində keşləyir
(`142_radar_referrals_cache.sql` miqrasiyası) — bu cədvəl kataloqun
`radar_feed_cache` cədvəlindən tamamilə ayrıdır. 10 MB cavab həddi və `generatedAt`
üçün aşağı sərhəd daxil olan lent keşlənmiş lentdən köhnə olduqda onu rədd edir və
daha köhnə imzalanmış artefaktın təkrar oynadılmasından qoruyur. Eyni zaman damğası
qəbul edilir: server məqsədli şəkildə icma və aktiv referal variantlarına eyni deterministik
`generatedAt` dəyərini verir, beləliklə əsas keçid dəsti dəyişmədən dəstəkçi açarı
dəyişdikdən sonra imzalanmış faydalı yük və təqdim edilən səviyyə dəyişə bilər. Heç vaxt
istisna atmır — həmişə status obyekti qaytarır; xətaların `reason` sahəsində heç vaxt
stek izi olmur.

Hər ikisi kataloqun öz 24 saatlıq intervalından müstəqil olan iki trigger referallar
keşini aktual saxlayır:

- **Oxuma zamanı sinxronizasiya** — `GET /api/radar/referrals` özü cavabı təqdim etməzdən
  əvvəl keş mövcud olmadıqda və ya `REFERRALS_STALE_MS` müddətindən (1 saat,
  `shouldSyncReferralsOnRead()`) köhnə olduqda `syncRadarReferrals()` funksiyasını
  birbaşa çağırır. Məhz bu, hər hansı fon taymerini gözləmədən sabit keçidləri növbəti
  idarə paneli yüklənməsi üçün «həmişə aktual» edir.
- **Planlaşdırıcının yan sinxronizasiyası** — `radarSchedulerTick()` (`scheduler.ts`)
  kataloq üçün istifadə edilən eyni saatlıq tikdə referalların köhnəlməsini müstəqil
  şəkildə qiymətləndirir və vaxtı çatdıqda `syncRadarReferrals()` funksiyasını çağırır.
  Bu, həmin tikdə kataloqun özünün sinxronizasiya vaxtının çatıb-çatmamasından asılı
  olmayaraq işləyir və heç vaxt `RadarTickResult` strukturuna təsir etmir (yalnız ən yaxşı
  cəhd prinsipi ilə yan təsirdir, xəta baş verdikdə nəzərə alınmır).

### Aksessor

`src/lib/radar/index.ts` yalnız oxuma üçün iki aksessor ixrac edir və onların heç biri
istisna atmır (`getRadarCatalog()` ilə eyni müdafiə müqaviləsi — bayraq söndürüldükdə,
keş olmadıqda və ya keşlənmiş faydalı yük korlandıqda xəta əvəzinə boş struktur qaytarılır):

- `getRadarReferrals()` → `{ fixed: RadarReferral[], campaigns: RadarReferral[] }`,
  `radar_referrals_cache` cədvəlindən (`getRadarReferralsCache()` vasitəsilə) oxuyur və
  `RadarReferralsFeedSchema` ilə validasiya edir — kataloq keşindən **deyil**.
- `getDefaultReferralFor(provider)` → həmin provayder üçün `isDefault: true` olan `fixed`
  referalını və ya `null` qaytarır. Yalnız `fixed` daxilində axtarır — kampaniya heç vaxt
  provayderin «standart» keçidi kimi istifadə edilmir.

Faktiki «hansı referal provayder üçün standartdır» qaydası `findDefaultReferral()`
(`src/lib/radar/referrals.ts`) daxilində yerləşir; bu, **heç bir DB importu olmayan**
kiçik, saf funksiyadır — onu `"use client"` komponentinə import etmək təhlükəsizdir.
`getRadarReferrals`/`getDefaultReferralFor` (`index.ts` daxilində) `@/lib/db/radar`
modulunu daxil edir və buna görə də yalnız server üçün qalır; provayderlər idarə paneli
`better-sqlite3` paketinin brauzer paketinə daxil edilməsinin qarşısını almaq üçün
`index.ts` əvəzinə birbaşa `referrals.ts` faylını import edir (aşağıya baxın).

### `GET /api/radar/referrals`

Bütün digər Radar marşrutları ilə tam olaraq eyni yoxlama ardıcıllığına əməl edir: `RADAR_ENABLED` deaktivdir →
`404` (ilk olaraq yoxlanılır, bayt səviyyəsində eyni ətalət); autentifikasiya olunmayıb → `401`; əks halda
köhnəlibsə, oxuma zamanı sinxronizasiyanı işə salır (yuxarıya baxın), sonra
`{ fixed, campaigns, tier }` ilə `200` qaytarır — `tier` birbaşa (ola bilsin ki, indicə yenilənmiş)
keş sətrindən gəlir və yalnız məlumat xarakteri daşıyır (aşağıdakı UI-da yumşaq əlavə satış mətnini idarə edir). Heç vaxt
lent serverinə birbaşa proksi etmir — marşrutun öz mənbə kodunda `fetch(` çağırışı yoxdur;
şəbəkə sorğusu yalnız `syncRadarReferrals()` daxilində baş verir, bu da
`/api/radar/catalog` ilə eyni, yalnız lokal keşdən istifadə prinsipidir.

### İdarəetmə panelinin UI-ı — `/dashboard/radar` səhifəsində "Pulsuz kreditlər" vərəqi

Mövcud Radar səhifəsini (`src/app/(dashboard)/dashboard/radar/page.tsx`) yeni
marşrut əvəzinə ikinci vərəq kimi yenidən istifadə edir — səhifənin artıq əldə etdiyi
məlumatların variasiyası olan bir funksiya üçün daha az marşrutlaşdırma/i18n səthi yaradır. Qoşulduqdan sonra vərəq paneli
**Kataloq** (mövcud cədvəl) və **Pulsuz kreditlər** seçimlərini təqdim edir:

- Sabit keçidlər provayder üzrə qruplaşdırılır; hər birində `requiredAction` (mövcud olduqda)
  və referal URL-sinə aparan `target="_blank" rel="noopener noreferrer"` düyməsi göstərilir.
- Kampaniyalarda eyni məlumatlar, əlavə olaraq isə mövcud olduqda `validUntil` göstərilir.
- `campaigns` boş olduqda **və** təqdim edilən səviyyə `community` olduqda, UI
  qısa əlavə satış qeydi göstərir ("məhdudmüddətli kampaniyalar dəstəkçilər üçün əlavə imkandır") — bu, bütün səviyyələr üçün tam şəkildə göstərilməyə davam edən
  sabit keçidlər siyahısını **heç vaxt** gizlətmir və ya məhdudlaşdırmır. Bu əlavə satış qeydi
  yalnız yumşaq mesajdır, heç vaxt bloklama vasitəsi deyil.

### Provayder adındakı referal keçidi (provayderlərin idarəetmə paneli)

`ProviderPageHeader` (`src/app/(dashboard)/dashboard/providers/[id]/components/`)
əvvəldən mövcud olduqda provayder adını `providerInfo.website` ilə əlaqələndirirdi və
monetizasiya edilmiş keçid üçün bir presedent var idi: Kimi (Moonshot AI) tərəfdaş keçidi qeydi
(`providers.kimiPartnerLinkNote` i18n açarı). D28 yeni açar təqdim etmək əvəzinə
Radar-ın standart referalları üçün məhz həmin təmkinli qeyd nümunəsini yenidən istifadə edir.

Dizayna uyğun olaraq zəif əlaqələndirmə:

- `resolveProviderHeaderLink()` (`src/app/(dashboard)/dashboard/providers/providerPageUtils.ts`)
  `@/lib/radar` və ya `@/lib/db/*` asılılığı olmayan **təmiz** funksiyadır —
  `(staticWebsite, referralUrl) => { website, isReferralLink }`.
  `providerPageUtils.ts` bütövlükdə bu importlardan azad qalır (bu,
  `tests/unit/provider-header-referral-link.test.ts` tərəfindən təsdiqlənir).
- `"use client"` komponenti olan `ProviderDetailPageClient.tsx` Radar məlumatlarını əldə etməyə icazə verilən
  yeganə yerdir — Radar idarəetmə paneli səhifəsinin özündə istifadə olunan eyni lokal marşrut
  nümunəsi ilə `fetch("/api/radar/referrals")` vasitəsilə — və DB-dən asılı olmayan
  `src/lib/radar/referrals.ts` faylındakı `findDefaultReferral()` ilə standart referalı
  müştəri tərəfində hesablayır.
- `RADAR_ENABLED` deaktiv olduqda sorğu `404` qaytarır, `referralUrl` `null` olaraq qalır və
  `resolveProviderHeaderLink()` statik kataloqdakı `website` dəyərini dəyişmədən qaytarır — provayder
  səhifəsi bu funksiya mövcud olmamışdan əvvəlki vəziyyətlə bayt səviyyəsində eynidir. Hələ keş olmadıqda
  və ya konkret provayder üçün standart referal mövcud olmadıqda da nəticə eynidir.
- Standart referal tətbiq olunduqda `ProviderPageHeader` `isReferralLink` dəyərini qəbul edir
  və Kimi tərəfdaş keçidi ilə eyni təmkinli qeydi/ipucunu göstərir
  (`providers.kimiPartnerLinkNote` açarını yenidən istifadə etməklə) — heç vaxt yeni, ayrıca
  vizual təqdimat tətbiq etmir.

## Fidi özünüz necə host edə bilərsiniz

Kataloq üzərində tam nəzarət istəyən fork və ya öz-özünə host edən tərəf, müştəri koduna toxunmadan öz fid xidmətini işlədə bilər:

1. `RadarFeedSchema` (`src/lib/radar/feedSchema.ts`) tələblərinə cavab verən JSON gövdəsi qaytaran `GET /v1/catalog/latest` endpoint-i təqdim edin — üst səviyyədə `feed:
"omniroute-radar"`, `schemaVersion: 2`, `version`, `tier`, `providers`, `models`,
   `quirks` və `totals`. `x-omniroute-radar-schema: 2` başlığına riayət edin; keçidlə uyğun server bu başlıq olmayan sorğular üçün standart olaraq ayrıca imzalanmış v1 artefaktından istifadə etməlidir.
2. Cavabın dəqiq baytlarını Ed25519 açar cütü ilə imzalayın və base64 formatlı imzanı `x-omniroute-feed-signature` cavab başlığında qaytarın.
3. `RADAR_FEED_URL` dəyişənini yeni baza URL-inə, `RADAR_FEED_PUBKEY` dəyişənini isə uyğun açıq açara (base64-DER SPKI və ya PEM) təyin edin — [mühit dəyişənləri arayışına](../reference/ENVIRONMENT.md#27-radar-feed-self-hosting) baxın.
4. `RADAR_ENABLED` parametrini aktivləşdirin və `POST /api/radar/settings`
   (`{ optIn: true }`) vasitəsilə iştirak etməyi seçin.

Başqa heç bir kod dəyişikliyi tələb olunmur — `verifyFeedBytes()` əvəzləməni avtomatik olaraq götürür (`src/lib/radar/pinnedKeys.ts` daxilindəki `getFeedPublicKeys()`), versiyaların müqayisəsi, sxem yoxlaması və birləşdirmə qaydaları isə öz-özünə host edilən fidə eyni şəkildə tətbiq olunur.

Referal keçidləri (yuxarıdakı [Referal keçidləri (pulsuz kreditlər)](#referral-links-free-credits) bölməsinə baxın) ayrıca, ixtiyari artefaktdır: yalnız `/v1/catalog/latest` təqdim edən fork yenə də tam işləyir — `/v1/referrals/latest` ünvanından `404` cavabı gəldikdə `syncRadarReferrals()` funksiyası `{ status: "error" }` nəticəsinə keçir və keş sadəcə boş qalır; beləliklə, `GET /api/radar/referrals` səhifənin qalan hissəsinin işləməsini dayandırmaq əvəzinə `{ fixed: [], campaigns: [], tier: null }` qaytarmağa davam edir. Referal keçidləri də təqdim etmək üçün `RadarReferralsFeedSchema` (`src/lib/radar/referralsFeedSchema.ts`) tələblərinə cavab verən `GET /v1/referrals/latest` endpoint-i təqdim edin və onu kataloq fidi ilə eyni Ed25519 açar cütü vasitəsilə imzalayın.

Dəstəkçi təklifləri başqa bir ixtiyari artefaktdır. Onları təqdim etmək üçün qapalı `RadarOffersFeedSchema` (`src/lib/radar/offersFeedSchema.ts`) sxemi ilə `GET /v1/offers/latest` endpoint-ini reallaşdırın, aktiv hüquq tələb edin, `x-omniroute-feed-tier: live` qaytarın və dəqiq baytları eyni açarla imzalayın. Bu endpoint-i daxil etməyən fork-da kataloq/referal davranışı dəyişməz qalır; təkliflərin yenilənməsi məlumatları pozmadan uğursuz olur və son təsdiqlənmiş lokal təklif keşi əlçatan qalır.

Intel də eyni qaydada ixtiyaridir. Öz-özünə host edən tərəf `RadarIntelFeedSchema` (`src/lib/radar/intelFeedSchema.ts`) sxemindən istifadə edərək `GET /v1/intel/latest` təqdim edə, aktiv hüquq tələb edə, `x-omniroute-feed-tier: live` qaytara və dəqiq baytları ortaq Ed25519 açarı ilə imzalaya bilər. Endpoint-in buraxılması kataloqu, referalları və təklifləri dəyişməz saxlayır; Intel yenilənməsi son təsdiqlənmiş lokal snapshot-u qoruyur.
