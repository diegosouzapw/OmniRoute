> **Son yenilənmə:** 2026-09-09
> **Auditoriya:** Daxili xidmətləri (9Router, CLIProxyAPI, Mux, Bifrost, open-wa) əlavə edən, texniki baxışını həyata keçirən və ya sazlayan mühəndislər.

Daxili xidmətlər OmniRoute-un quraşdırdığı, nəzarət etdiyi və tamhüquqlu marşrutlaşdırma hədəfləri kimi təqdim etdiyi, lokal olaraq quraşdırılan köməkçi proses alətləridir. Xarici provayderlərdən (internet üzərindən API açarları vasitəsilə əlaqə qurulan) fərqli olaraq, daxili xidmətlər OmniRoute ilə eyni maşında işləyir və geri dövrə interfeysi üzərindən əlaqə saxlayır.

- OmniRoute onları alt proseslər kimi işə salır və izləyir
- OmniRoute alt prosesin mühitinə efemer API açarı daxil edir və onu dayanma olmadan rotasiya edir (tətbiq olunduğu hallarda)
- Bütün idarəetmə marşrutları (`/api/services/*`) **YALNIZ_LOKALDIR** — yalnız geri dönmə interfeysindən əlçatandır (sərt qayda #17)

## 3. Həyat dövrü vəziyyət maşını

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
              sağlamlıq yoxlaması uğurlu │      qəza / SIGTERM   │
                               ┌────▼─────┐  (5 san. ərzində çıxış)│
                               │ running  │──── qəza ───────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

Vəziyyətlər `version_manager` DB cədvəlində (`status` sütunu) saxlanılır və
`ServiceSupervisor`-un yaddaşdaxili vəziyyətində əks olunur. İşləyən proses üçün
yaddaşdaxili vəziyyət əsas mənbədir; DB vəziyyəti isə yüklənmə zamanı davamlı ehtiyat
mənbə rolunu oynayır.

### Vəziyyət keçidləri

| Başlanğıc       | Hadisə                                  | Nəticə                 |
| --------------- | --------------------------------------- | ---------------------- |
| `not_installed` | `install()` uğurla tamamlanır           | `stopped`              |
| `stopped`       | `start()` çağırılır                     | `starting`             |
| `starting`      | sağlamlıq yoxlaması 200 qaytarır        | `running`              |
| `starting`      | proses sağlam olmadan əvvəl dayanır     | `error`                |
| `running`       | `stop()` çağırılır                      | `stopping` → `stopped` |
| `running`       | proses gözlənilmədən dayanır (< 5 san.) | `error` (sürətli qəza) |
| `running`       | proses gözlənilmədən dayanır (> 5 san.) | `error`                |
| `error`         | `start()` çağırılır                     | `starting`             |
| istənilən       | `stopping` zamanı `stop()`              | əməliyyat yoxdur       |

### Əməliyyat kilidi

`ServiceSupervisor` həyat dövrü əməliyyatlarını asinxron əməliyyat kilidi
(`withLock()`) vasitəsilə ardıcıllaşdırır. Eyni supervisor üzərində paralel `start()`
çağırışları yalnız bir prosesin başladılması ilə nəticələnir; ikinci çağıran gözləyir
və mövcud vəziyyəti qaytarır. Bu, məsələn, avtomatik başlatma ilə UI düyməsinin eyni
anda işə düşdüyü hallarda yarış şəraitinin qarşısını alır.

## 4. API arayışı

`/api/services/` altındakı bütün marşrutlar **LOCAL_ONLY**-dir (yalnız geri döngü, sərt qayda #17).
Geri döngü olmayan sorğular autentifikasiya tokenindən asılı olmayaraq `403 LOCAL_ONLY` cavabı alır.

### 4.1 9Router son nöqtələri (11 marşrut)

#### `POST /api/services/9router/install`

9Router-i npm-dən quraşdırır. Öz `package.json` və `node_modules/` faylları ilə birlikdə
`DATA_DIR/services/9router/` yaradır. OmniRoute-un öz asılılıqları ilə ziddiyyət yaratmır.

**Sorğu gövdəsi** (hamısı istəyə bağlıdır):

```json
{ "version": "latest" }
```

| Sahə      | Növ      | Standart   | Təsvir                                       |
| --------- | -------- | ---------- | -------------------------------------------- |
| `version` | `string` | `"latest"` | Quraşdırılacaq npm versiya teqi və ya semver |

**Cavablar:**

| Status | Təsvir                                                                |
| ------ | --------------------------------------------------------------------- |
| `200`  | `{ ok: true, installedVersion: "x.y.z", path: "..." }`                |
| `400`  | Etibarsız sorğu gövdəsi (Zod doğrulama xətası)                        |
| `409`  | Quraşdırma artıq davam edir (kilid tutulub)                           |
| `500`  | npm quraşdırması uğursuz oldu — anlaşılan xəta üçün `message`-a baxın |

**Qeydlər:** `execFile('npm', [...])` istifadə edir — shell və interpolasiya yoxdur (sərt qayda #13).
EACCES xətaları anlaşılan mesajlar kimi təqdim olunur.

---

#### `POST /api/services/9router/start`

9Router-i başladır. Əgər supervayzer hələ qeydiyyatdan keçirilməyibsə, onu qeydiyyatdan keçirir,
sonra `supervisor.start()` çağırır. Artıq işlədiyi halda idempotentdir.

**Sorğu gövdəsi:** yoxdur

**Cavablar:**

| Status | Təsvir                                                      |
| ------ | ----------------------------------------------------------- |
| `200`  | `ServiceStatus` obyekti (aşağıdakı sxemə baxın)             |
| `409`  | 9Router quraşdırılmayıb (`status: "not_installed"`)         |

### 4.7 Əks proksi (9Router idarəetmə panelinin yerləşdirilməsi)

İdarəetmə paneli 9Router veb interfeysini iframe daxilində aşağıdakı ünvandakı daxili əks
proksi vasitəsilə yerləşdirir:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

Bu proksi:

- Sorğunu `http://127.0.0.1:{port}/{path}` ünvanına yönləndirir (yalnız geri döngə)
- Daxil olan `cookie` və `authorization` başlıqlarını silir (OmniRoute sessiyasının sızmasının qarşısını alır)
- 9Router autentifikasiyası üçün `Authorization: Bearer {apiKey}` daxil edir
- Cavabdan `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*` başlıqlarını silir
- `<base href>` daxil etmək və mütləq yolları normallaşdırmaq üçün HTML cavablarını yenidən yazır (`/foo` → `/dashboard/.../embed/foo`)

Yerləşdirilmiş idarəetmə paneli üçün WebSocket yeniləmələri xüsusi portdakı
köməkçi server tərəfindən idarə olunur (`src/lib/services/embedWsProxy.ts` faylına baxın).

**Təhlükəsizlik:** Yerləşdirmə proksisi marşrutları `LOCAL_ONLY_API_PREFIXES`
altında təsnif edilir və onlara yalnız geri döngədən daxil olmaq mümkündür. Cloudflare/Ngrok
tuneli vasitəsilə JWT əldə edən hücumçu yerləşdirilmiş xidmətlərə proksi vasitəsilə daxil ola bilməz.

## 5. Təhlükəsizlik

### LOCAL_ONLY tətbiqi (sərt qayda #17)

`/api/services/` və `/dashboard/providers/services/*/embed/` altındakı bütün marşrutlar
`src/server/authz/routeGuard.ts` faylında LOCAL_ONLY kimi təsnif edilir. Geriyə döngə yoxlaması
istənilən autentifikasiya şaxəsindən əvvəl qeyd-şərtsiz yerinə yetirilir:

```
sorğu daxil olur
  → isLocalOnlyPath(path)?
      → geriyə döngə deyil → 403 LOCAL_ONLY (həmişə, autentifikasiya yoxlamasından əvvəl)
      → geriyə döngədir    → normal autentifikasiyaya keç
```

Bu, sızdırılmış JWT-nin (məsələn, tunel vasitəsilə) `npm install` əməliyyatını və ya
prosesin işə salınmasını başladmasının qarşısını alır. Tam səviyyə matrisi üçün
`docs/security/ROUTE_GUARD_TIERS.md` sənədinə baxın.

### API açarının yeridilməsi

9Router və Mux öz HTTP son nöqtələri üçün API açarı/bearer token tələb edir.
OmniRoute:

1. Xidmətə xas prefikslə (`nr_` 9Router üçün, `mx_` Mux üçün)
   `crypto.randomBytes(32).toString("base64url")` vasitəsilə açar yaradır.
2. Onu AES-256-GCM istifadə edərək saxlanma zamanı şifrələyir (provayder giriş məlumatları üçün istifadə edilən eyni şifr).
3. Prosesi işə salarkən onun şifrəsini açır və mühit dəyişəni kimi yeridir —
   9Router üçün `NINEROUTER_API_KEY`, Mux üçün `MUX_SERVER_AUTH_TOKEN` (heç vaxt CLI
   bayrağı kimi deyil; beləliklə, token `ps`/proses siyahılarında görünmür).
4. Heç bir HTTP cavabında açıq mətn şəklində olan açarı qaytarmır.

CLIProxyAPI işə salınma zamanı yeridilən xüsusi məlumat müstəvisi açarı alır
(`needsApiKey: true` — adapterlə model sinxronizasiyası üçün istifadə edilir).

### SSRF müdafiəsi

Əks HTTP proksisi (`/dashboard/.../embed/[...path]`) yalnız
`http://127.0.0.1:{port}` ünvanına yönləndirmə üçün sərt şəkildə kodlaşdırılıb.
O, geriyə döngə olmayan təyinatlara yönləndirmələri heç vaxt izləmir.
`ssrf-req-filter` kitabxanası geriyə döngə diapazonundan kənar ünvana çevrilən
istənilən yuxarı axın URL-ni rədd etmək üçün istifadə olunur.

### Shell təhlükəsizliyi (sərt qayda #13)

`npm install`, `execFile('npm', ['install', pkg, '--prefix', dir])` vasitəsilə çağırılır —
şablon literalları, shell və xarici yolların əmr sətrinə interpolyasiyası yoxdur.
İcra vaxtı dəyərləri (portlar, API açarları) alt prosesin `env` obyekti vasitəsilə ötürülür.

### Xətaların təmizlənməsi (sərt qayda #12)

`/api/services/*` ünvanından gələn bütün xəta cavabları `buildErrorBody()` və ya
`sanitizeErrorMessage()` vasitəsilə emal olunur. Xam `err.stack` və `err.message`
çağırana heç vaxt olduğu kimi qaytarılmır.

#### Qoşula bilən provayder plaqini müqaviləsi (Mərhələ 1, #7333)

`src/lib/services/providerPlugins/`, eyni backend strukturunun əlaqəsiz iki faylda
ayrıca ifadə edilməsi əvəzinə backend-in `bootstrap.ts` faylındakı `ServiceEntry`
sahələrini və `serviceBackends.ts` manifest-şablon sahələrini bir obyektdə paketləyən
`ServiceProviderPlugin` müqaviləsini təqdim edir. Bu mətn yazılan vaxt **yalnız `9router`
miqrasiya edilib** — `bootstrap.ts`, `SERVICES[]` qeydini
`getServiceProviderPlugin("9router")` (`src/lib/services/providerPlugins/registry.ts`)
vasitəsilə əldə edir və plaqin nə vaxtsa mövcud olmazsa, başlanğıc xətası yaradır.
`cliproxy`, `mux` və `bifrost` dəyişdirilmədən əvvəlcədən mövcud olan daxili
`SERVICES[]` literallarında qalır.

`open-sse/config/providerPluginManifest.ts` həmçinin `SERVICE_BACKEND_MANIFEST_TEMPLATE`
qeydindən düzgün formalaşdırılmış `ProviderPluginManifestEntry` yaradan əlavə
`createServiceBackendManifestEntry(pluginId, template)` köməkçisini əldə edib — o,
hələ heç bir aktiv sorğu yoluna (nə `generateProviderPluginManifestFromRegistry()`,

## 7. Problemlərin aradan qaldırılması

### Xidmət işə düşmür

**Əlamətlər:** Başlatma düyməsi 503 qaytarır, vəziyyət `"error"` və ya `"starting"` olaraq qalır.

**Yoxlama siyahısı:**

1. `GET /api/services/{name}/logs` sorğusunu yoxlayın (və ya idarəetmə panelindəki Logs panelini). `Error: ENOENT`, `address already in use` və ya `Cannot find module` kimi sətirləri axtarın.
2. `npm`-in PATH-də olduğunu yoxlayın: OmniRoute-u işlədən eyni istifadəçi hesabından `which npm` əmrini icra edin.
3. Xidmətin quraşdırıldığını yoxlayın: `installedVersion` üçün `GET /api/services/{name}/status` sorğusunu yoxlayın. Əgər `null`-dırsa, əvvəlcə quraşdırmanı başladın.
4. `DATA_DIR/services/{name}/node_modules/` qovluğunun mövcud və boş olmadığını yoxlayın.
5. Təmizlənmiş çıxış səbəbi üçün status cavabındakı `lastError` sahəsini yoxlayın.

---

### Soyuq başlanğıc ləngdir (`running` vəziyyətinə çatmaq > 10 san.)

**Əlamətlər:** Vəziyyət `"running"` və ya `"error"` vəziyyətinə keçməzdən əvvəl uzun müddət `"starting"` olaraq qalır.

**İzah:** 9Router-in soyuq başlanğıcına böyük asılılıq ağaclarının (DNS, tunel, MITM modulları) import edilməsi daxildir. Standart sağlamlıq yoxlaması intervalı 2 san.-dir və nəzarətçi vaxt aşımı elan etməzdən əvvəl 3 cəhd edir (lakin sorğulamağa davam edir).

**Həll:** `healthIntervalMs` və `waitForHealthy` vaxt aşımı (`healthIntervalMs * 3`) `bootstrap.ts` daxilində konfiqurasiya edilə bilər. Başlanğıc müddəti daha uzun olan xidmətlər üçün `healthIntervalMs` dəyərini 5000-ə, `stopTimeoutMs` dəyərini isə 30 000-ə artırın.

---

### Port toqquşması (`EADDRINUSE`)

**Əlamətlər:** Jurnallarda `address already in use :::20130` göstərilir.

**Səbəblər:**

- Başqa bir proses artıq 20130 portundan istifadə edir.
- Əvvəlki 9Router prosesi tam dayandırılmayıb (zombi PID).

**Həll:**

1. `.env` daxilindəki `NINEROUTER_PORT` mühit dəyişəni vasitəsilə standart portu dəyişin.
2. Toqquşmaya səbəb olan prosesi tapıb dayandırın: `lsof -ti :20130 | xargs kill -9`.
3. Port hər xidmət üçün `bootstrap.ts` daxilindəki `port` sahəsi vasitəsilə konfiqurasiya edilə bilər.

**Qeyd:** OmniRoute-un standart 20128 portu ilə toqquşmanın qarşısını almaq üçün 9Router xüsusi olaraq standart 20130 portundan istifadə edir.

---

### Quraşdırma zamanı icazə rədd edilir (EACCES)

**Əlamətlər:** Quraşdırma 500 qaytarır, jurnallarda `EACCES` və ya `permission denied` göstərilir.

**Səbəblər:**

- `DATA_DIR` və ya onun üst qovluğu OmniRoute prosesi tərəfindən yazıla bilən deyil.
- Qoşulmuş disk bölməsinə yazma icazəsi olmadan köksüz Docker daxilində işlədilir.

**Həll:**

1. `DATA_DIR` qovluğunu yoxlayın (standart: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. OmniRoute prosesinin istifadəçisinin qovluğun sahibi olduğuna əmin olun: `chown -R $USER ~/.omniroute/`
3. Docker-də disk bölməsi qoşulmasının konteyner istifadəçisi üçün düzgün icazələrə malik olduğuna əmin olun.

---

### Yeniləmə uğursuz olur (`npm install` vaxt aşımı və ya şəbəkə xətası)

**Əlamətlər:** Yeniləmə `InstallError` ilə 500 qaytarır, jurnallarda şəbəkə vaxt aşımı göstərilir.

**Yoxlama siyahısı:**

1. npm reyestrinin əlçatan olduğunu təsdiqləyin: `npm ping`.
2. Korporativ proksini yoxlayın: `npm config get proxy`, `npm config get https-proxy`.
3. Quraşdırmanı əl ilə sınayın: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`.
4. İzolyasiya edilmiş şəbəkədəsinizsə, tarball faylını əvvəlcədən endirin və `npm install /path/to/tarball.tgz` əmrindən istifadə edin.

---

### Xidmət başladıqdan dərhal sonra `"error"` vəziyyətini göstərir (sürətli dayanma)

**Əlamətlər:** Vəziyyət 5 saniyədən az müddətdə `"starting"` vəziyyətindən `"error"` vəziyyətinə keçir. `lastError` sahəsində `"Fast crash (exited with code 1)"` göstərilir.

**Yoxlama siyahısı:**

1. Jurnalın son hissəsini tam oxuyun: `GET /api/services/{name}/logs?tail=500`.
2. Ümumi səbəb: xidmətin gözlədiyi mühit dəyişənlərinin olmaması.
3. 9Router üçün: proses başladılarkən ötürülən mühitdə `NINEROUTER_DISABLE_MITM=true` və `NINEROUTER_DISABLE_TUNNEL=true` dəyərlərinin olduğunu yoxlayın (`installers/ninerouter.ts` daxilindəki `resolveSpawnArgs` bölməsinə baxın).

## 8. Tez-tez verilən suallar

**S: Daxili xidmətlərin endpoint-lərini loopback olmayan müştərilər üçün əlçatan edə bilərəmmi?**

Xeyr. LOCAL_ONLY səviyyəsi məqsədli şəkildə tətbiq edilib (sərt qayda #17). `npm install` əməliyyatını icra edə və ya `node` prosesləri yarada bilən marşrutlar loopback olmayan trafikdən əlçatan olmamalıdır, çünki əks halda tunel (Cloudflare, Ngrok, Tailscale) vasitəsilə sızmış JWT ixtiyari proseslərin yaradılmasına imkan verərdi. `/api/services/` üçün bu qaydadan imtina etməyə imkan verən heç bir istisna yoxdur — `/api/mcp/`-dən fərqli olaraq, o, idarəetmə əhatə dairəsindən yan keçmə siyahısına daxil edilməyib. `docs/security/ROUTE_GUARD_TIERS.md` sənədinə baxın.

---

**S: 9Router və CLIProxyAPI istehsal/bulud yerləşdirmələrində əlçatan olacaqmı?**

Bəli. Hər iki xidmət OmniRoute-un özü ilə eyni, ilk növbədə lokal istifadə modelinə əməl edir. Onlar eyni maşında işləyir və loopback üzərindən əlaqə qurur. Burada «istehsal» uzaq bulud provayderini deyil, OmniRoute-un yerləşdirildiyi VPS-i və ya lokal serveri nəzərdə tutur.

---

**S: Supervisor-da sazlama işlərini necə apara bilərəm?**

1. SSE jurnal axınını izləyin: `curl -N http://localhost:20128/api/services/9router/logs`.
2. OmniRoute-un pino çıxışındakı strukturlaşdırılmış jurnalları `service:supervisor` ad sahəsinə görə filtrləyərək yoxlayın.
3. DB sətrini yoxlayın: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`.
4. Cari canlı vəziyyəti, PID-ni, sağlamlıq durumunu və `lastError` dəyərini bir sorğuda görmək üçün `GET /api/services/9router/status` istifadə edin.

---

**S: Supervisor `health: "degraded"` və ya `health: "unknown"` göstərir, lakin vəziyyət `"running"` olaraq qalır. Bu problemdirmi?**

`"degraded"` sağlamlıq yoxlamasının 200-dən fərqli cavab qaytardığını bildirir. `"unknown"` isə hələ heç bir yoxlamanın tamamlanmadığını bildirir (ilk sorğu ilə yarış vəziyyəti). Hər ikisi işə salınma zamanı keçici haldır. `"running"` vəziyyətindən sonra sağlamlıq durumu `healthIntervalMs * 3` ms-dən çox müddətdə `"degraded"` olaraq qalarsa, daxili xidmət işləyir, lakin onun HTTP API-si cavab vermir. Status cavabındakı portun düzgün olub-olmadığını və xidmətin həqiqətən həmin portu dinləyib-dinləmədiyini yoxlayın.

---

**S: Tam yenidən başlatma olmadan 9Router API açarını dəyişə bilərəmmi?**

Xeyr. API açarı proses yaradılarkən mühit dəyişəni vasitəsilə 9Router-ə ötürülür. İşləyən prosesdə mühit dəyişənlərini dəyişmək mümkün deyil. `POST .../rotate-key` yeni açarı tətbiq etmək üçün xidməti avtomatik dayandırır və yenidən başladır. Açarın rotasiyası xidmətin `stopTimeoutMs` müddəti (standart olaraq 15 s) və onun işə salınma vaxtı ərzində qüvvəyə minir.

---

**S: Halqavari buferin limiti nə qədərdir və dolduqda nə baş verir?**

Hər xidmətin ayrıca 5 MB-lıq halqavari buferi var. Bufer dolduqda yeni sətirlərə yer açmaq üçün ən köhnə jurnal sətirləri silinir. SSE `snapshot` hadisəsi `tail` limiti daxilində ən son sətirləri qaytarır. DB sətrində `logsBufferPath` təyin edilməyibsə, jurnallar diskdə saxlanılmır.
