Bu sənəd OmniRoute-un Fly.io platformasında faktiki yerləşdirmə prosesini iki ssenari üzrə təsvir edir:

- Cari layihənin ilk dəfə Fly.io platformasında yerləşdirilməsi
- Sonrakı kod yeniləmələrinin dərc edilməsi
- Eyni yerləşdirmə iş axınından istifadə edən yeni layihələr

Bu təlimat cari layihə üçün yoxlanılmış və işlək olduğu təsdiqlənmiş konfiqurasiyaya əsaslanır. Tətbiqin adı `omniroute`-dur.

---

## 1. Yerləşdirmə Məqsədləri

- Platforma: Fly.io
- Yerləşdirmə üsulu: Lokal `flyctl` vasitəsilə birbaşa dərc
- İcra mühiti: Repozitoridəki mövcud `Dockerfile` və `fly.toml` fayllarından istifadə
- Məlumatların davamlı saxlanması: `/data` qovluğuna qoşulmuş Fly Volume
- Giriş URL-i: `https://omniroute.fly.dev/`

---

## 2. Cari Layihənin Əsas Konfiqurasiyası

Cari repozitoridəki `fly.toml` faylında aşağıdakı əsas elementlərin olduğu təsdiqlənib:

```toml
app = 'omniroute'
primary_region = 'sin'

[[mounts]]
  source = 'data'
  destination = '/data'

[processes]
  app = 'node run-standalone.mjs'

[http_service]
  internal_port = 20128

[env]
  TZ = "Asia/Shanghai"
  HOST = "0.0.0.0"
  HOSTNAME = "0.0.0.0"
  BIND = "0.0.0.0"
```

Qeydlər:

- `app = 'omniroute'` yerləşdirmənin hansı Fly tətbiqini hədəflədiyini müəyyən edir
- `destination = '/data'` davamlı saxlama həcminin qoşulacağı qovluğu müəyyən edir
- Bu layihədə `DATA_DIR=/data` təyin edilməlidir, əks halda verilənlər bazası və açarlar konteynerin müvəqqəti qovluğuna yazılacaq

## 4. Cari Layihənin İlk Dəfə Yerləşdirilməsi

### 4.1 Kodu Klonlayın və Qovluğa Keçin

```powershell
git clone https://github.com/diegosouzapw/OmniRoute.git
cd OmniRoute
```

### 4.2 Tətbiqin Adını Təsdiqləyin

`fly.toml` faylını açın və aşağıdakı sətri yoxlayın:

```toml
app = 'omniroute'
```

Öz yeni tətbiqinizdə yerləşdirmə aparırsınızsa, bunu qlobal miqyasda unikal bir adla dəyişə bilərsiniz, məsələn:

```toml
app = 'omniroute-yourname'
```

Qeyd:

- Konsolda gördüyünüz tətbiqin `fly.toml` faylındakı `app` dəyəri ilə uyğun olduğuna əmin olun
- Əvvəllər `oroute` kimi fərqli addan istifadə etmisinizsə, onu `omniroute` ilə qarışdırmayın

### 4.3 Tətbiqi Yaradın

Tətbiq hələ mövcud deyilsə:

```powershell
flyctl apps create omniroute
```

Tətbiqin adını dəyişmisinizsə, `omniroute` əvəzinə seçdiyiniz addan istifadə edin.

### 4.4 İlk Yerləşdirmə

```powershell
flyctl deploy
```

## 5. Tələb Olunan Parametrlər

Bu layihə Fly.io platformasında ən azı aşağıdakı parametrlərin konfiqurasiya edilməsini tövsiyə edir.

### 5.1 Yoxlanılmış Parametrlər

Bu parametrlər cari `omniroute` tətbiqinin faktiki yerləşdirmələrində istifadə edilib:

- `API_KEY_SECRET`
- `DATA_DIR`
- `JWT_SECRET`
- `MACHINE_ID_SALT`
- `NEXT_PUBLIC_BASE_URL`
- `OMNIROUTE_WS_BRIDGE_SECRET` (istehsal mühitində tələb olunur — WebSocket körpüsünün autentifikasiyası üçün istifadə edilir)
- `STORAGE_ENCRYPTION_KEY`

### 5.2 `INITIAL_PASSWORD` Haqqında

Cari layihədə `INITIAL_PASSWORD` təyin edilməyib, çünki bu yerləşdirmə üçün tələb olunmur.

Təyin edilmədikdə:

- Başlanğıc jurnalında standart parolun `CHANGEME` olduğu göstəriləcək
- Yerləşdirmədən sonra sistem parametrlərində giriş parolunu mümkün qədər tez dəyişməlisiniz

Backend parolunu müdaxiləsiz ilkin olaraq təyin etmək istəyirsinizsə, bunu daha sonra əlavə edə bilərsiniz:

- `INITIAL_PASSWORD`

## 6. Tövsiyə olunan parametrlər

### 6.1 Məxfi məlumatların konfiqurasiyası

Fly Secrets üçün aşağıdakı dəyişənlər tövsiyə olunur:

| Dəyişən                        | Tövsiyə                    | Təsvir                                                           |
| ------------------------------ | -------------------------- | ---------------------------------------------------------------- |
| `API_KEY_SECRET`               | Məcburi                    | API açarlarının yaradılması və yoxlanılması üçün istifadə olunur |
| `JWT_SECRET`                   | Məcburi                    | Giriş sessiyaları və JWT imzalanması üçün istifadə olunur        |
| `OMNIROUTE_WS_BRIDGE_SECRET`   | İstehsal mühitində məcburi | WebSocket körpüsünün autentifikasiya sirri                       |
| `STORAGE_ENCRYPTION_KEY`       | Qətiyyətlə tövsiyə olunur  | Saxlanılan həssas bağlantı məlumatlarını şifrələyir              |
| `MACHINE_ID_SALT`              | Tövsiyə olunur             | Stabil maşın identifikatoru yaradır                              |
| `INITIAL_PASSWORD`             | İstəyə bağlı               | İlk yerləşdirmə zamanı ilkin backend parolunu təyin edir         |
| OAuth/API məxfi etimadnamələri | Ehtiyac olduqda            | Xarici platformanın autentifikasiya konfiqurasiyası              |

### 6.2 Cari layihə üçün tövsiyə olunan dəyərlər

| Dəyişən                | Tövsiyə olunan dəyər        |
| ---------------------- | --------------------------- |
| `DATA_DIR`             | `/data`                     |
| `NEXT_PUBLIC_BASE_URL` | `https://omniroute.fly.dev` |

Qeydlər:

- `DATA_DIR=/data` kritik əhəmiyyət daşıyır və Fly Volume qoşulma nöqtəsi ilə uyğun olmalıdır
- `NEXT_PUBLIC_BASE_URL` planlaşdırıcı, frontend geri çağırışları və oxşar ssenarilər tərəfindən istifadə olunur

### 6.3 OAuth geri çağırış URL-sinin konfiqurasiyası

Fly.io yerləşdirməsində OAuth əsaslı provayderləri (məsələn, Antigravity, Gemini, Cursor) aktivləşdirmək lazımdırsa, aşağıdakı iki məqama əmin olun:

1. **`NEXT_PUBLIC_BASE_URL` dəyişənini ictimai HTTPS domeninizə təyin edin**

   ```powershell
   flyctl secrets set NEXT_PUBLIC_BASE_URL=https://omniroute.fly.dev -a omniroute
   ```

   Fərdi domendən istifadə edirsinizsə, onu müvafiq domenlə əvəz edin (məsələn, `https://omniroute.yourdomain.com`).

2. **Provayder konsolunda geri çağırış URL-sini konfiqurasiya edin**

   Bütün OAuth provayderləri vahid `/callback` geri çağırış yolundan istifadə edir — hər provayder üçün ayrıca geri çağırış marşrutu YOXDUR:

   ```text
   <NEXT_PUBLIC_BASE_URL>/callback
   ```

   Məsələn, Gemini, Antigravity, Cursor və ya GitLab Duo olmasından asılı olmayaraq:
   - `https://omniroute.fly.dev/callback`

   `NEXT_PUBLIC_BASE_URL` provayderdə qeydiyyatdan keçirilmiş geri çağırış URL-si ilə uyğun gəlməzsə, OAuth prosesi brauzerin yönləndirmə mərhələsində uğursuz olacaq.

## 7. Məxfi məlumatların bir əmrlə qurulması

Aşağıdakı əmrlər təhlükəsiz təsadüfi dəyərlər yaradır və cari layihə üçün tələb olunan bütün parametrləri bir addımda Fly Secrets-ə yazır.

Qeydlər:

- `INITIAL_PASSWORD` daxil deyil
- Cari `omniroute` layihəsi üçün nəzərdə tutulub

```powershell
$apiKeySecret = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$jwtSecret = [Convert]::ToHexString((1..64 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$machineIdSalt = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$storageKey = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$wsBridgeSecret = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()

flyctl secrets set `
  API_KEY_SECRET=$apiKeySecret `
  JWT_SECRET=$jwtSecret `
  MACHINE_ID_SALT=$machineIdSalt `
  STORAGE_ENCRYPTION_KEY=$storageKey `
  OMNIROUTE_WS_BRIDGE_SECRET=$wsBridgeSecret `
  DATA_DIR=/data `
  NEXT_PUBLIC_BASE_URL=https://omniroute.fly.dev `
  -a omniroute
```

Linux / macOS sistemlərində `openssl rand -hex 32` əmrindən də istifadə edə bilərsiniz:

```bash
flyctl secrets set OMNIROUTE_WS_BRIDGE_SECRET=$(openssl rand -hex 32) -a omniroute
```

Qeydlər:

- `OMNIROUTE_WS_BRIDGE_SECRET` istehsal mühitində məcburidir; onun olmaması WebSocket körpüsünün əl sıxma prosesini pozacaq

İlkin parol da təyin etmək istəyirsinizsə:

```powershell
flyctl secrets set INITIAL_PASSWORD=your-strong-password -a omniroute
```

## 9. Sonrakı Yeniləmələr və Buraxılışlar

Kod yeniləmələrindən sonra buraxılış prosesi sadədir:

```powershell
git pull
flyctl deploy
```

Kodu dəyişdirmədən yalnız parametrləri yeniləmək lazımdırsa:

```powershell
flyctl secrets set KEY=value -a omniroute
```

Fly avtomatik olaraq maşınların mərhələli yenilənməsini həyata keçirəcək.

### 9.1 Forkunuzun `fly.toml` Faylını Qoruyaraq İlkin Repozitoriyanın Yeniləmələrini İzləmək

Cari repozitoriya forkdursa və `https://github.com/diegosouzapw/OmniRoute` ilkin repozitoriyasındakı yeniləmələri sinxronlaşdırmaq istəyirsinizsə, aşağıdakı iş axınını izləyin.

Əvvəlcə uzaq repozitoriyalarınızı yoxlayın:

```powershell
git remote -v
```

Ən azı aşağıdakıları görməlisiniz:

- Öz forkunuzu göstərən `origin`
- İlkin repozitoriyanı göstərən `upstream`

`upstream` konfiqurasiya edilməyibsə, onu əlavə edin:

```powershell
git remote add upstream https://github.com/diegosouzapw/OmniRoute.git
```

`upstream` ilə sinxronlaşdırmadan əvvəl ən son commitləri və teqləri əldə edin:

```powershell
git fetch upstream --tags
```

Cari versiyanı və `upstream` teqlərini yoxlayın:

```powershell
git describe --tags --always
git show --no-patch --oneline v3.4.7
```

> Qeyd: Layihənin cari versiyası `v3.8.0`-dır. Aşağıdakı `v3.4.7` istinadları yalnız tarixi nümunələr kimi saxlanılıb. Faktiki buraxılışlar üçün `:latest` və ya cari versiya teqindən (məsələn, `:v3.8.0`) istifadə edin.

Forkunuzun `fly.toml` faylını məcburi şəkildə qoruyaraq ən son `upstream` `main` qolunu birləşdirmək istəyirsinizsə, bu iş axınını izləyin:

```powershell
git merge upstream/main
git checkout HEAD~1 -- fly.toml
git add -- fly.toml
git commit -m "chore(deploy): keep fork fly.toml"
git push origin main
```

Qeydlər:

- `git merge upstream/main` ilkin repozitoriyadakı ən son kodu sinxronlaşdırır
- `git checkout HEAD~1 -- fly.toml` forkunuza məxsus `fly.toml` faylını birləşdirmədən əvvəlki vəziyyətinə qaytarır
- `upstream` `fly.toml` faylını dəyişməyibsə, bu addım heç bir fərq yaratmayacaq
- `upstream` `fly.toml` faylını dəyişibsə, bu addım Fly tətbiqinizin adının, disk qoşulmasının, regionun və forka xas digər yerləşdirmə konfiqurasiyalarının üzərinə yazılmamasını təmin edir

Konkret buraxılış teqi ilə (məsələn, `v3.4.7`) uyğunlaşmaq istəyirsinizsə, əvvəlcə həmin teqin artıq `upstream/main` qoluna daxil edildiyini yoxlayın:

```powershell
git merge-base --is-ancestor v3.4.7 upstream/main
```

Uğurlu nəticə `upstream/main` qolunun artıq həmin versiyanı ehtiva etdiyini bildirir; sadəcə `upstream/main` qolunu birləşdirə bilərsiniz.

### 9.2 `upstream` Sinxronlaşdırıldıqdan Sonra Standart Buraxılış Ardıcıllığı

İlkin repozitoriya ilə sinxronlaşdırdıqdan sonra bu tövsiyə olunan buraxılış ardıcıllığını izləyin:

1. `git fetch upstream --tags`
2. `git merge upstream/main`
3. Forkun `fly.toml` faylını bərpa edin
4. `git push origin main`
5. `flyctl deploy`
6. `flyctl status -a omniroute`
7. `flyctl logs --no-tail -a omniroute`

Bu, cari layihəni `v3.4.7` versiyasına yüksəldərkən istifadə edilmiş faktiki iş axınıdır (nümunə tarixi versiyaya aiddir; cari faktiki versiya `v3.8.0`-dır).

## 11. Uğurlu Yerləşdirmənin Göstəriciləri

Uğurlu yerləşdirmədən sonra jurnallarda aşağıdakına bənzər məzmun görünməlidir:

```text
[bootstrap] Secrets persisted to: /data/server.env
[DB] SQLite database ready: /data/storage.sqlite
```

Bu iki məqam vacibdir:

- `/data/server.env` icra mühiti məxfi məlumatlarının daimi disk bölməsinə yazıldığını təsdiqləyir
- `/data/storage.sqlite` verilənlər bazasının daimi disk bölməsinə yazıldığını təsdiqləyir

Əvəzində `/app/data/...` görürsünüzsə, `DATA_DIR` yanlış konfiqurasiya edilib və dərhal düzəldilməlidir.

## 12. Ümumi Problemlər

### 12.1 `Secrets` Səhifəsi Boşdur

Adətən bunun iki səbəbi olur:

- Siz hələ `flyctl secrets set` əmrini icra etməmisiniz
- Başqa tətbiqə baxırsınız (məsələn, `omniroute` əvəzinə `oroute`)

### 12.2 `flyctl deploy` `app not found` Xətası Verir

Əvvəlcə tətbiqi yaradın:

```powershell
flyctl apps create omniroute
```

### 12.3 `fly.toml` Faylının Təhlili Uğursuz Olur

Aşağıdakıları yoxlayın:

- Şərhlərdə pozulmuş simvolların olub-olmadığını
- TOML dırnaq işarələrinin və girintilərin düzgün olub-olmadığını

### 12.4 Verilənlər Daimi Saxlanmır

Aşağıdakıların hər ikisini yoxlayın:

- `fly.toml` faylında `destination = '/data'` var
- `DATA_DIR` `/data` olaraq təyin edilib

### 12.5 `INITIAL_PASSWORD` Olmadan İşləyə Bilərmi?

Bəli, işləyə bilər. Bu halda standart `CHANGEME` parolundan istifadə ediləcək. İstehsal mühitində backend parolunu mümkün qədər tez dəyişmək tövsiyə olunur.

## 13. Yeni Layihələr Üçün Təkrar İstifadə

Bu sənədə əsasən yeni layihə yerləşdirirsinizsə, yalnız aşağıdakıları dəyişdirməlisiniz:

1. `fly.toml` faylındakı `app` dəyərini dəyişdirin
2. `NEXT_PUBLIC_BASE_URL` dəyərini dəyişdirin
3. `DATA_DIR=/data` parametrini saxlayın
4. `API_KEY_SECRET`, `JWT_SECRET`, `MACHINE_ID_SALT` və `STORAGE_ENCRYPTION_KEY` dəyərlərini yenidən yaradın
5. İlk yerləşdirmədən sonra jurnalların `/data` qovluğuna yazıldığını yoxlayın

Əvvəlki layihənin açarlarını təkrar istifadə etməyin.

---

## 14. Cari Layihə üçün Minimal Buraxılış Yoxlama Siyahısı

Sonrakı buraxılışlar üçün ən çox istifadə olunan əmrlər bunlardır:

```powershell
flyctl auth whoami
flyctl status -a omniroute
flyctl secrets list -a omniroute
flyctl deploy
flyctl logs --no-tail -a omniroute
```

Adi buraxılış üçün əsas əmr sadəcə budur:

```powershell
flyctl deploy
```

Yeni mühitdə ilk yerləşdirmə üçün əsas addımlar bunlardır:

1. `flyctl auth login`
2. `flyctl apps create omniroute`
3. `flyctl secrets set ... -a omniroute`
4. `flyctl deploy`
5. `flyctl logs --no-tail -a omniroute`
