Codex CLI-ni OpenAI ilə uyğun backend kimi OmniRoute-a yönəldərək istifadə etmək üçün tam təlimat.

---

> **TOML yeganə effektiv formatdır.** Müasir Codex yalnız `~/.codex/config.toml`
> faylını oxuyur (codex-cli 0.147.0 ilə yoxlanılıb: `codex --help`
> sənədlərində `-c/--config` əvəzləmələrinin "`~/.codex/config.toml` faylından yükləndiyi" göstərilir). Köhnə
> `~/.codex/config.yaml` əvvəlki npm CLI-yə aid idi və xəbərdarlıq edilmədən nəzərə alınmır.
> İdarəetmə panelinin generatoru (`/api/cli-tools/apply`, alət `codex`) TOML-u
> ehtiyatlı birləşdirmə ilə yazır — mövcud açarlar və digər provayder blokları qorunur,
> API açarı `OMNIROUTE_API_KEY` daxilində qalır (heç vaxt fayla yazılmır) və qalan köhnə
> `config.yaml` faylına toxunulmadan onunla bağlı miqrasiya qeydi göstərilir.

## İstifadəyə hazır config.toml

`<YOUR_HOST>` və `<YOUR_KEY>` hissələrini öz dəyərlərinizlə əvəz edin:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # hər alət çağırışı üçün tarixçənin saxlama həddi

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc və ya ~/.zshrc — faktiki açar dəyəri, heç vaxt config.toml daxilində deyil
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT tətbiqinə daxil edilmiş Codex

Codex-i ChatGPT masaüstü tətbiqi vasitəsilə quraşdırmısınızsa, `codex` binar faylı
yalnız tətbiq paketinin daxilində mövcud ola və shell `PATH` dəyişəninizə hələ əlavə edilməmiş ola bilər. Resurslar
qovluğunu shell başlanğıc faylınıza əlavə edin:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Yeni shell açın, sonra yoxlayın:

```bash
command -v codex
codex --version
```

### Autentifikasiya tələb etməyən lokal OmniRoute: əvəzedici açar kifayətdir

Codex ilk sorğu CLI-dan çıxmazdan **əvvəl** `env_key` tərəfindən göstərilən
mühit dəyişəninin mövcudluğunu yoxlayır. **Lokal** OmniRoute
instansiyanız autentifikasiya tələb etmirsə, istənilən boş olmayan əvəzedici dəyər uyğundur:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

OmniRoute serveriniz qorunursa və ya uzaq serverdirsə, bunun əvəzinə həqiqi açardan istifadə edin.

> **Ümumi host seçimləri**
>
> | Giriş        | URL                           |
> | ------------ | ----------------------------- |
> | Lokal şəbəkə | `http://192.168.0.1:20128/v1` |
> | Tailscale    | `http://100.x.x.x:20128/v1`   |
> | Geri döngə   | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — niyə bütün modellər üçün işləyir

Codex CLI 2026-cı ilin fevralında `wire_api = "chat"` (Chat Completions) dəstəyini köhnəlmiş elan etdi və indi **`wire_api = "responses"` istifadəsini tələb edir** (OpenAI Responses API). `wire_api = "chat"` təyin edilməsi v0.138 versiyasından etibarən başlanğıc zamanı dərhal çökməyə səbəb olur.

GLM və Kimi daxil olmaqla bir çox provayder hələ də yalnız Chat Completions son nöqtəsi təqdim edir. DeepSeek V4 artıq Anthropic ilə uyğun son nöqtə ilə yanaşı, yerli Responses API də təqdim edir; OmniRoute standart olaraq Responses istifadə edir və hər DeepSeek bağlantısına Anthropic uyğunluğunu seçməyə imkan verir.

**OmniRoute bunu şəffaf şəkildə həll edir:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute provayderin yerli protokolunu seçir və lazım olduqda tərcümə edir
    → POST /responses (DeepSeek V4) və ya /chat/completions (Mistral / GLM / Kimi / digərləri)
```

OmniRoute istifadə edərkən ayrıca tərcümə proksisinə heç vaxt ehtiyacınız olmur. **Bütün modellər `wire_api = "responses"` istifadə edir** — qalan işi OmniRoute görür.

> **`wire_api` standart dəyərdir** — sahənin standart dəyəri `"responses"` olduğundan onu `config.toml` faylından tamamilə çıxarmaq olar. Yalnız məqsədi sənədləşdirirsinizsə, onu açıq şəkildə təyin edin.

## Kontekst pəncərəsi və sıxlaşdırma

### Token konfiqurasiyası sahələri

| Sahə                             | Təsvir                                                                                                                                                                                               |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Aktiv model üçün ümumi token büdcəsi. Modelin elan edilmiş limitinə təyin edin.                                                                                                                      |
| `model_auto_compact_token_limit` | Tarixçənin avtomatik sıxlaşdırılmasını başladan hədd. **Maksimum: `model_context_window` dəyərinin 90%-i** — 90%-dən yuxarı dəyərlər xəbərdarlıq edilmədən nəzərə alınmır.                           |
| `tool_output_token_limit`        | Hər alət çağırışının tarixçədə saxlanılan çıxışı üçün token limiti. Tək bir böyük alət cavabının pəncərəni doldurmasının qarşısını alır. **Bu, maksimum çıxış deyil** — tarixçədə saxlama limitidir. |
| `compact_prompt`                 | Sıxlaşdırma zamanı istifadə olunan sistem promptu üçün sətirdaxili əvəzetmə (v0.138+).                                                                                                               |

> **`model_max_output_tokens` haqqında qeyd**: Bu sahə **Codex CLI konfiqurasiya sxeminin bir hissəsi deyil** (Codex Rust kod bazasında mövcud deyil). Təyin edildikdə xəbərdarlıq edilmədən nəzərə alınmır. Ona etibar etməyin — tarixçədə nə qədər alət çıxışının saxlanıldığını idarə etmək üçün `tool_output_token_limit` istifadə edin.

## Düşünmə səyi

Modelin cavab verməzdən əvvəl nə qədər "düşündüyünü" idarə edir.

| Dəyər    | İstifadə sahəsi                                    |
| -------- | -------------------------------------------------- |
| `none`   | Düşünmə yoxdur — birbaşa cavab                     |
| `low`    | Sadə tapşırıqlar (adını dəyişmək, formatlaşdırmaq) |
| `medium` | Göstərilmədikdə **serverin standart dəyəri**       |
| `high`   | Orta səviyyəli tapşırıqlar (refaktorinq, sazlama)  |
| `xhigh`  | Arxitektura, dərin təhlil, mürəkkəb problemlər     |

```bash
# Hər çağırış üçün dəyəri əvəz edin
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

Həmçinin Desktop-un düşünmə mətnini (yalnız şifrələnmiş blob-ları deyil) göstərə bilməsi üçün düşünmə **xülasəsi** təyin edin:

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # və ya dəstəkləndikdə ultra
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute düşünmə büdcəsi (server ayarı)

OmniRoute hostunda Codex səyinin/xülasəsinin yuxarı axına çatması üçün **Settings → AI → Thinking Budget** dəyəri **`passthrough`** olmalıdır. **`auto` rejimi** bütün klient `reasoning` / `reasoning_effort` sahələrini silir və hətta Codex düzgün konfiqurasiya edildikdə belə düşünmə panellərini boş qoyur.

Tam təlimat: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Sıxılma və prompt keşi bir-birindən müstəqildir və `passthrough` altında işləməyə davam edir.

## Profillər — hər model/iş axını üçün adlandırılmış konfiqurasiyalar

Profillər tək bir bayraqla model + kontekst pəncərəsini dəyişməyə imkan verir. Hər profil əsas `config.toml` üzərinə tətbiq olunan sadə
`~/.codex/<name>.config.toml` faylıdır.

> **Adlandırma qaydası (Codex CLI v0.137+):** fayl `~/.codex/<name>.config.toml` olmalıdır — **`profile-` prefiksi olmamalıdır**.
> CLI `-p kimi-k27` → `~/.codex/kimi-k27.config.toml` kimi həll edir. Fayl tapılmasa, standart dəyər səssizcə tətbiq olunur.

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # sürətli, ucuz
```

### Səy profilləri (eyni model, fərqli səy)

```bash
codex -p low      # cx/gpt-5.5, səy=low
codex -p medium   # cx/gpt-5.5, səy=medium
codex -p high     # cx/gpt-5.5, səy=high
codex -p xhigh    # cx/gpt-5.5, səy=xhigh (standart)
codex -p chat     # cx/gpt-5.5, səy təyin edilməyib (server standartı)
```

## `omniroute setup-codex` ilə profillərin avtomatik yaradılması

OmniRoute-u VPS-də işlədirsinizsə, aktiv model kataloqundan profil fayllarını avtomatik yarada bilərsiniz:

```bash
# VPS-dən (20128 portundakı lokal OmniRoute-dan istifadə edir)
omniroute setup-codex

# İstənilən maşından — VPS ünvanınızı göstərin
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Faylları yazmadan önizləyin
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Yalnız GLM və Kimi profillərini yaradın
omniroute setup-codex --only glm,kimi

# Xüsusi qovluğa yazın
omniroute setup-codex --codex-home /path/to/.codex
```

Komanda `/v1/models` resursunu əldə edir, məlum modellər üçün optimallaşdırılmış profillərdən istifadə edir, digər uyğun mətn modelləri üçün kataloq metadatasına keçir və hər biri üçün `~/.codex/<name>.config.toml` faylını yazır. İdempotentdir — təkrar icra etmək təhlükəsizdir.

OmniRoute həmçinin uğurlu provayder model aşkarlaması/idxalı aktiv kataloqu dəyişdirdikdən sonra həmin profil fayllarını **avtomatik sinxronlaşdıra** bilər. Bu funksiya **seçimlidir və standart olaraq deaktivdir**: onu **CLI Code idarəetmə panelindən** ("CLI profilinin avtomatik sinxronlaşdırılması" → Codex) aktivləşdirin və ya `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` təyin edin (standart olaraq aktiv olan `CLI_ALLOW_CONFIG_WRITES` parametrini də nəzərə alır). Aktivləşdirildikdə yalnız ayrıca `~/.codex/*.config.toml` profil faylları yazılır; aktiv/standart `~/.codex/config.toml`, Codex-lb parametrləri, autentifikasiya və ya provayder seçimi heç vaxt dəyişdirilmir.

## Uzunmüddətli tapşırıqlar

OmniRoute-un iki standart ayarı çoxsaatlıq Codex CLI sessiyalarını nəzərə çarpmadan poza bilər. Onların heç biri Codex CLI ayarı deyil — hər ikisi OmniRoute tərəfində yerləşir. Hesabları sabitləyən və boşdayanma məhdudiyyətlərini deaktiv edən yuxarı axın proksilərindən konfiqurasiyanı köçürən istifadəçilər tez-tez hər iki problemlə qarşılaşır və OmniRoute-un “uzun sessiyanı davam etdirə bilmədiyi” qənaətinə gəlirlər.

| Əlamət                                                                                               | Ehtimal olunan səbəb                                                                                  | Tənzimləmə               |
| ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------ |
| Sessiya hesablar arasında keçid etməyə davam edir / sorğu keşinin ardıcıllığı gedişlər arasında itir | Sessiya yaxınlığının TTL dəyəri `0`-dır (deaktivdir)                                                  | `sessionAffinityTtlMs`   |
| Müştəriyə görünən heç bir sorğu olmadan əsaslandırmanın ortasında bağlantı kəsilir                   | Yuxarı axından 10 dəqiqə ərzində heç bir hissə gəlmədiyi üçün axının boşdayanma nəzarətçisi işə düşüb | `STREAM_IDLE_TIMEOUT_MS` |

Əlaqəli müzakirələr: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (uzun tapşırıqların kəsilməsi), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (yaxınlığın standart olaraq niyə deaktiv olması). İzləmə: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Sessiya yaxınlığı — bir söhbəti bir hesaba sabitləyin

**Standart:** `sessionAffinityTtlMs = 0` (deaktivdir).

**Harada təyin edilməlidir**

- İdarəetmə paneli → **Ayarlar → Marşrutlaşdırma** → **Sessiya yaxınlığı** → **Yaxınlıq TTL-i (saniyə)** (`ComboDefaultsTab`)
- Yaxud ayarları `sessionAffinityTtlMs` ilə **millisaniyə** vahidində PATCH edin (Zod diapazonu `0`–`86_400_000`, yəni 24 saata qədər)

> #7274-də yalnız Codex üçün nəzərdə tutulan `codexSessionAffinityTtlMs` adından dəyişdirilib. Köhnə açar hələ də yalnız oxuma üçün ləqəb kimi qəbul edilir; yeni konfiqurasiyalar `sessionAffinityTtlMs` istifadə etməlidir. TTL `0`-dan böyük olduqda yaxınlıq artıq yalnız Codex-ə deyil, **istənilən** provayderə tətbiq olunur — baxın: [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Sessiya yaxınlığı.

**Dəyər 0 olaraq qaldıqda nə pozulur**

Çoxgedişli Codex söhbətinin hər gedişi aktiv kombinasiya strategiyası ilə müstəqil şəkildə marşrutlaşdırılır və **hər gedişdə fərqli hesaba** yönləndirilə bilər. Bu, yuxarı axın sessiyasının / sorğu keşinin ardıcıllığını pozur. OmniRoute yalnız TTL `0`-dan böyük olduqda Codex sessiya başlıqlarını (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) və `prompt_cache_key` / `session_id` kimi gövdə sahələrini yoxlayır (`src/sse/services/auth.ts` daxilində `extractSessionAffinityKey`).

**Çoxsaatlıq vahid tapşırıq üçün tövsiyə**

TTL-i **tapşırığın gözlənilən faktiki müddətindən daha yüksək** təyin edin (UI maksimumu **86400 saniyə** = 24 saat):

| Gözlənilən tapşırıq müddəti | Yaxınlıq TTL-i (UI, saniyə) | `sessionAffinityTtlMs` |
| --------------------------- | --------------------------- | ---------------------- |
| Bir neçə saat               | `14400` (4 saat)            | `14400000`             |
| Gecə boyu / ~12 saat        | `43200` (12 saat)           | `43200000`             |
| Tam gün                     | `86400` (24 saat, maksimum) | `86400000`             |

Qoşulmanın seçimli olması məqsədyönlüdür: yaxınlığın deaktiv edilməsi hesablar arasında yük balanslaşdırmasına, aktiv edilməsi isə bir uzun agent sessiyası üçün ardıcıllığa üstünlük verir. Bu təlimat standart ayarı **dəyişmir** — uzun Codex tapşırıqlarını icra edən operatorlar bunu özləri aktivləşdirməlidirlər.

### 2. Axının boşdayanma taymautu — səssiz əsaslandırma gedişlərini dayandırmayın

**Standart:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 dəqiqə). Təyin edilmədikdə `REQUEST_TIMEOUT_MS` dəyərini miras alır; ortaq baza dəyəri də 600000-dir. Baxın: [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Taymautlar.

**Standart ayarda nə pozulur**

10 dəqiqədən çox müddətdə **heç bir real upstream hissəsi olmadan** səssiz qalan Codex reasoning / tool mərhələsi SSE boşdayanma nəzarətçisi (`open-sse/utils/stream.ts`) tərəfindən məcburi şəkildə bağlanır. Müştəri çox vaxt sadəcə bağlantının kəsildiyini görür — bu da “heç bir bildiriş olmadan avtomatik dayandı” halına uyğundur.

Kritik məqam: OmniRoute-un sintetik SSE **heartbeat-i boşdayanma taymerini sıfırlamır**. `lastChunkTime` yalnız real upstream body hissəsi gəldikdə yenilənir. Hələ də “düşünən” səssiz model nəzarətçinin nöqteyi-nəzərindən dayanmış upstream ilə eyni görünür.

Əlaqəli Undici body fəaliyyətsizliyi: `FETCH_BODY_TIMEOUT_MS` (standart olaraq eyni 10 dəqiqəlik baza dəyərinə malikdir; `0` onu deaktiv edir). Axın üçün `FETCH_TIMEOUT_MS` yalnız bağlantının qurulmasını / ilk header-ləri əhatə edir — axın aktivləşdikdən sonra dayanmalar `STREAM_IDLE_TIMEOUT_MS` və `FETCH_BODY_TIMEOUT_MS` tərəfindən idarə olunur.

**Bir neçə saat davam edən tək tapşırıq üçün tövsiyə**

OmniRoute proses mühitində (`.env` / compose / systemd):

```bash
# Uzun reasoning mərhələləri üçün axının boşdayanma və body fəaliyyətsizliyi limitlərini deaktiv edin
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Yaxud onları gözlədiyiniz ən uzun səssizlik müddətindən daha yüksək edin (dəyərlər millisaniyə ilədir):

```bash
# Nümunə: upstream hissələri arasında 2 saata qədər səssizliyə icazə verin
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Bu mühit dəyişənlərini dəyişdirdikdən sonra OmniRoute-u yenidən başladın.

### Konkret təlimat — bir neçə saatlıq Codex tapşırığı

1. **Hesabı sabitləyin:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12 saat) və ya `86400` (maksimum 24 saat).
2. OmniRoute mühitində **boşdayanma limitlərini artırın / deaktiv edin**:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Adi Codex `config.toml` konfiqurasiyasını (`wire_api = "responses"`, düzgün `base_url`, `OMNIROUTE_API_KEY`) saxlayın — bu iki davranış üçün Codex tərəfində affinity/boşdayanma parametrləri mövcud deyil.
4. OmniRoute-u yenidən başladın, sonra uzunmüddətli Codex tapşırığını başladın.

### Standart dəyərlərlə bağlı qərar (#7287)

| Parametr                 | Buraxılışdakı standart dəyər | Bu təlimatda dəyişdirilsin?                                                                                 |
| ------------------------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (söndürülüb)             | **Xeyr** — seçim əsasında qalır (yük balanslaşdırması və davamlılıq; bax: Discussion #5718)                 |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 dəq)            | **Xeyr** — ümumi trafik üçün 10 dəqiqə olaraq qalır; uzun Codex operatorları onu artırır və ya deaktiv edir |

Hər iki standart dəyərdən birini qlobal şəkildə dəyişmək yalnız Codex-in deyil, instansın bütün müştərilərinin davranışını dəyişər. Parametrləri sənədləşdirin; operator tərəfindən bunun əksini bildirən açıq qərar verilənədək standart dəyərləri dəyişməyin.

### Boşdayanma səbəbindən kəsilmələrin diaqnostikası

Boşdayanma nəzarətçisi işə düşdükdə OmniRoute aşağıdakı formaya uyğun bir sətir qeyd edir:

```text
[STREAM] Idle timeout: codex-dən 600000ms ərzində məlumat gəlmədi (model: cx/gpt-5.5)
```

`Idle timeout: no data from` ifadəsini (yaxud `stream_idle_timeout` kodunu / `StreamIdleTimeoutError` xəta adını) axtarın. Provayder seqmenti OmniRoute-un həmin sorğu üçün istifadə etdiyi dəyərdir (`codex`, başqa provayder id-si və ya bilinmirsə `provider`) — bu, həmişə hərfi olaraq `codex` sətri olmur.

## Problemlərin aradan qaldırılması

**`Error: wire_api = "chat" is no longer supported`**
Konfiqurasiyanızdan `wire_api = "chat"` sətrini silin. `wire_api = "responses"` təyin edin və ya sahəni buraxın (v0.138-dən etibarən standart dəyər `"responses"`-dır).

**`Error: model not found`**
Modelin düzgün prefikslə OmniRoute-da mövcud olduğunu yoxlayın. `omniroute models list` istifadə edin və ya `/dashboard/providers/<provider>` ünvanını açın.

**`Authentication error`**
`OMNIROUTE_API_KEY` dəyişəninin ixrac edildiyini təsdiqləyin: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex ilk sorğunu göndərməzdən əvvəl mühit dəyişəninin mövcudluğunu yoxlayır. Qorunan serverlər üçün
həqiqi açarı ixrac edin və ya **lokal** OmniRoute instansiyanız autentifikasiya tələb etmədikdə
`OMNIROUTE_API_KEY=local` kimi boş olmayan əvəzedici dəyərdən istifadə edin.
Dəyişəni `~/.bashrc` və ya `~/.zshrc` faylına əlavə etmisinizsə, shell-i yenidən başladın.

**`Connection refused`**
OmniRoute-un işlədiyini və `base_url` host/port dəyərinin şəbəkəniz üçün (lokal, Tailscale və ya VPS) düzgün olduğunu yoxlayın.

**Sessiya kontekst limitinə yaxın çökür**
`model_context_window` və `model_auto_compact_token_limit` dəyərlərini açıq şəkildə təyin edin. Yuxarıdakı kontekst pəncərəsi cədvəlinə baxın.

**Sıxlaşdırma çox gec işə düşür**
`model_auto_compact_token_limit` dəyərini pəncərənin 80–85%-nə endirin. Heç vaxt 90%-dən yuxarı təyin etməyin.

**Profil yüklənmir (`-p <name>` xəbərdarlıq etmədən nəzərə alınmır)**
Faylın `~/.codex/<name>.config.toml` ünvanında mövcud olduğunu təsdiqləyin (`profile-` prefiksi olmadan). `ls ~/.codex/*.config.toml` əmrini icra edin.

**Uzunmüddətli Codex tapşırığı icra zamanı yarımçıq dayanır / gedişlər arasında hesabları dəyişir**
[Uzunmüddətli tapşırıqlar](#long-running-tasks) bölməsinə baxın. Sessiya bağlılığını aktivləşdirin (TTL tapşırıq müddətindən uzun olmalıdır) və `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS` dəyərlərini artırın və ya deaktiv edin. OmniRoute jurnallarında `Idle timeout: no data from` mətnini grep ilə axtarın.
