## Qısa Məlumat

**OmniRoute ilə yeni tanışsınız?** Buradan başlayın — bunlar problemlərin 90%-ni həll edir:

| Bunu görürəm                       | Mənası                                    | Nə etməli                                                                                              |
| ---------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| "Qoşulmaq mümkün deyil"            | OmniRoute işləmir                         | `omniroute` əmrini icra edin və ya `docker restart omniroute` istifadə edin                            |
| "Yanlış API açarı"                 | Açarınız yanlışdır və ya vaxtı bitib      | Açarı provayderin veb-saytından yenidən kopyalayın                                                     |
| "Sürət limiti aşılıb"              | Həddindən çox sorğu göndərirsiniz         | 1 dəqiqə gözləyin və ya avtomatik ehtiyat keçidi üçün `model: "auto"` istifadə edin                    |
| "Kvota aşılıb"                     | Pulsuz/ödənişli kvotanızı bitirmisiniz    | Daha çox provayder qoşun və ya pulsuz provayderlərdən (Kiro, Pollinations) istifadə edin               |
| "Yavaş cavablar"                   | Provayder məşğuldur və ya uzaqda yerləşir | `model: "auto/fast"` istifadə edin və ya daha sürətli provayder (Groq, Cerebras) qoşun                 |
| "Yanlış provayder istifadə edilib" | `auto` başqa provayder seçib              | Bu normaldır! `auto` ən yaxşısını seçir. `model: "openai/gpt-4o"` ilə konkret provayderi məcburi seçin |
| "502 Bad Gateway"                  | Provayder işləmir                         | Gözləyib yenidən cəhd edin və ya provayderi dəyişmək üçün `model: "auto"` istifadə edin                |

| "429 Too Many Requests"            | Sürət limiti tətbiq edilib                | 1 dəqiqə gözləyin və ya daha çox provayder qoşun                                                       |

## Ətraflı Nasazlıq Aradan Qaldırma

---

### Pulsuz Provayderlərdə Sürət Məhdudiyyəti (429 / 400 / 401)

**Əlamət**: Pulsuz/autentifikasiyasız provayderlərlə (opencode, auggie və s.) `model: "auto"` istifadə edərkən cavabların əvəzinə fasilələrlə `HTTP 429`, `400` və ya `401` xətaları alırsınız. Eyni sorğunu bir neçə an sonra yenidən sınadıqda sorğular uğurla tamamlanır, lakin avtomatlaşdırma (cron tapşırıqları, agentlər, skriptlər) ilk xətada dayanır.

**Əsas səbəb**: Üç müstəqil xəta rejimi üst-üstə düşür:

1. **Provayderin sürət limiti (`429`)**: Pulsuz tariflər hər zaman intervalı üçün kvota tətbiq edə bilər. Paralel çağırışların ani artımı kvotanı tükəndirir, buna görə də interval sıfırlanana qədər növbəti sorğu rədd edilir.
2. **Birbaşa ötürmədə işləməyən model (`400`/`401`)**: `auto/*` hovuzlarına `opencode` provayderindən kataloqda qeydiyyatdan keçmiş, lakin aktiv giriş məlumatları olmayan birbaşa ötürmə modelləri daxil ola bilər (məsələn, `oc/north-mini-code-free` → `401`). Avtomatik marşrutlaşdırıcı onlardan birini sınayır, uğursuz olur və ehtiyat keçid işə düşməzdən əvvəl xəta ötürülür.
3. **Paralellik güclənməsi (yük altında `429`)**: Bir neçə agent/cron sessiyası eyni anda `auto` istifadə etdikdə ümumi sorğu sürəti pulsuz provayderlərin qəbul etdiyi həddi aşır və nəticədə etibarlı çağırışlar sui-istifadə kimi işarələnir.

**Təsdiqlənmiş həll (icma tərəfindən bildirilib, 2026-08-10)**: rotasiya, paralellik və ehtiyat keçidin pulsuz tarifdəki qeyri-sabitliyi xəta ilə dayanmaq əvəzinə kompensasiya etməsi üçün üç mühit dəyişənini tənzimləyin:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 baş verdikdə başqa modelə/provayderə keç (işləməyən birbaşa ötürmə modellərini buraxır)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ağır sorğular üçün açıq qəbul həddi (standart olaraq təyin edilməyib: sorğu sayı həddi yoxdur, aşağıdakı qeydə baxın)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # dərhal təkrar sınana bilən 503 əvəzinə ağır sorğu tutumu üçün daha uzun, məhdud gözləmə
```

Bunları OmniRoute prosesinin mühitində (demon prosesində, məsələn, LaunchAgent plist və ya `systemctl edit` vasitəsilə) təyin edin, sonra OmniRoute-u yenidən başladın. Rotasiya bayrağı ən güclü təsirə malik vasitədir: o, sərt xətanı hovuzdakı işlək provayderə qarşı şəffaf təkrar cəhdə çevirir.

**Qeyd**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` eyni anda neçə ağır — uzun kontekstli — sorğunun işləyə biləcəyini məhdudlaşdırır; bu hədd provayderin sürət məhdudlaşdırıcısı deyil, qəbul qapısıdır. **#503-fanout yeniləməsi:** bu dəyişən artıq standart olaraq təyin edilmir (indi yalnız yuxarıdakı kimi açıq şəkildə konfiqurasiya edildikdə tətbiq olunur) — bunun əvəzinə ağır sorğuların qəbulu hostun faktiki yaddaş həddinə əsasən özünü miqyaslandıran, avtomatik hesablanan bayt büdcəsi (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ilə idarə olunur. Buna görə də yeni quraşdırmada bu dəyişəni ümumiyyətlə təyin etmədən xeyli az `503 chat_admission_busy` rəddi müşahidə edilməlidir; onu burada açıq şəkildə təyin etmək isə sənədləşdirildiyi kimi işləməyə davam edir. Açıq bayt büdcəsi əvəzləmələri 8 MiB–2 GiB aralığı ilə məhdudlaşdırılır. `413 body_exceeds_budget` keçici deyil: həmin bayt büdcəsini artırın, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` dəyərini azaldın və ya prosesin yaddaş həddini artırın. `inflight_bytes_budget` səbəbilə yükün azaldılması müvəqqəti resurs rəqabətidir və təkrar sınana bilər. Hər provayder üzrə sürət məhdudiyyəti (`open-sse/services/rateLimitManager.ts`) ayrıca olaraq `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` və `RATE_LIMIT_AUTO_ENABLE` vasitəsilə idarə olunur — `.env.example` faylına baxın.

**İşlədiyini necə yoxlamaq olar**: agentinizi/cron tapşırığınızı qısa fasilə ilə iki dəfə işə salın və hər ikisinin uğurla tamamlandığını təsdiqləyin. Düzəlişdən əvvəl ikinci icra adətən `429`/`401` xətası verir. Düzəlişdən sonra xətalar (əgər baş verərsə) şəffaf şəkildə yenidən sınanır və çağırış tamamlanır. Həmçinin `curl /monitoring/health` icra edərək provayder bağlantılarındakı `rateLimitedUntil` sahəsini və təsirə məruz qalan provayderlər üçün `circuitBreakers.providerBreakers[].state` dəyərini izləyə bilərsiniz — vəziyyət `CLOSED`, `DEGRADED`, `OPEN` və ya `HALF_OPEN` dəyərlərindən biridir (`src/shared/utils/circuitBreaker.ts` faylına baxın) və davamlı olaraq uğursuz olan provayder sıfırlama intervalı sınaq sorğusunu buraxmazdan (`HALF_OPEN`) əvvəl `CLOSED → DEGRADED → OPEN` vəziyyətlərinə keçəcək.

**Hələ də 429 görürsünüzsə**: həmin provayder üçün aktiv hesabın həqiqətən _kvotası_ tükənib (yalnız sorğu tezliyi limiti deyil). OmniRoute idarəetmə panelində → Providers → Accounts bölməsinə eyni provayder üçün ikinci hesab əlavə edin və ya başqa pulsuz provayderdən (məsələn, `routeway`, `auggie`) də istifadə edin. Rotasiya yalnız müvəqqəti sorğu tezliyi limiti/400/401 xətalarında kömək edir; kvotanın tam tükənməsi ikinci giriş məlumatı və ya fərqli provayder tələb edir.

**Görüntü modellərində (`auto/vision`, `bazaarlink/*`) 403 görürsünüzsə**: qoşulmuş hesabda görüntü imkanlarını ehtiva edən ödənişli plan yoxdur və ya API açarının icazələri yetərli deyil. Provayderin idarəetmə panelində açarın əhatə dairəsinə görüntü/multimodal imkanlarının daxil olduğunu yoxlayın və ya ödənişli tarif hesabını qoşaraq onu görüntü hədəfi kimi saxlayın.

## npm install Xəbərdarlıqları (ERESOLVE / peer / deprecated)

`npm install -g omniroute` əmrini işlətdikdə `npm warn ERESOLVE`, peer-asılılıq bildirişləri və `deprecated` mesajlarından ibarət çoxlu sayda xəbərdarlıq görə bilərsiniz. **Bunlar gözləniləndir və zərərsizdir.** Çıxışda `added <N> packages` görürsünüzsə, quraşdırma uğurla tamamlanıb.

Xəbərdarlıqlar OmniRoute-un nəzarət etmədiyi üçüncü tərəf paketlərindəki köhnəlmiş peer-asılılıq diapazonlarından qaynaqlanır:

1. **`marked-terminal` paketi `marked >=1 <16` tələb edir, lakin `marked@18` tapılıb** — praktikada problemsiz işləyir; upstream peer diapazonu sadəcə köhnəlib.
2. **`deprecated prebuild-install@7.1.3`** — tranzitiv yerli binar fayl əldəetmə köməkçisidir. O, sabitlənmiş `wreq-js` nəqliyyat bağlantısını quraşdırmaq üçün
   istifadə edilmir və veb kuki provayderinin nəqliyyat konfiqurasiyasının uğursuz olduğunu
   göstərmir.

**Heç bir tədbir tələb olunmur** — upstream paketləri fork etmədən xəbərdarlıqları tamamilə susdurmaq mümkün deyil.

## Antivirusun yanlış müsbət nəticələri

<a name="antivirus-false-positives"></a>

### Avast/AVG `README.md` faylını `MD:HttpRequest-inf[Susp]` kimi karantinə alır

**Bu, yanlış müsbət nəticədir. Heç bir yoluxma yoxdur və heç bir tədbir tələb olunmur.**

Avast və AVG çoxlu sayda HTTP sorğusuna bənzəyən keçidlər ehtiva edən adi mətn/Markdown
fayllarını işarələyən evristik yoxlama tətbiq edir. OmniRoute-un `README.md` faylı npm paketinə daxildir (o,
`package.json` → `files` bölməsində göstərilib), buna görə qlobal quraşdırma zamanı
`node_modules/omniroute/README.md` ünvanına yerləşdirilir — və təxminən 15
`http://localhost:20128/...` nümunəsi (MCP HTTP/SSE son nöqtələri, A2A `.well-known` URL-i və
`curl` fraqmentləri) ehtiva edir. Keçidlərin bu sıxlığı evristik yoxlamanı işə salmaq üçün
kifayətdir.

Bu, yalnız yaxın zamanda başlayıbsa: faylın mahiyyəti dəyişməyib. README-dəki son nöqtələr
cədvəli genişləndirilib (MCP HTTP + SSE + A2A əlavə olunub) və daha çox `curl` nümunəsi
daxil edilib; nəticədə fayl həddi keçib.

Bu fayl heç bir icra edilə bilən məzmunu olmayan passiv sənəddir. Onu karantindən
təhlükəsiz şəkildə bərpa edə bilərsiniz.

**Nə etməli:**

1. **Bildirişləri dayandırın** — antivirusunuzda quraşdırma qovluğunu istisnalara əlavə edin
   (Avast: Settings → Exceptions); qlobal `node_modules` yolunuzu və/və ya
   OmniRoute məlumat qovluğunu (`~/.omniroute/`) əlavə edin.
2. **Yanlış müsbət nəticəni bildirin** — <https://www.avast.com/false-positive-file-form.php>,
   karantinə alınmış `README.md` faylını əlavə edin. Bu, hər kəsə kömək edən həlldir, çünki
   problem istehsalçının evristik yoxlamasının mətn faylına həddindən artıq reaksiya verməsidir.

**Niyə bunu öz tərəfimizdə “düzəltmirik”:** bütün nümunələr `http://localhost` istifadə edir və
localhost öz-özünə imzalanmış sertifikatlarla bağlı çətinliklər olmadan `https` istifadə edə bilməz. Bir
istehsalçının evristik yoxlamasından yayınmaq üçün sənədləri təhrif etmək, skanerdəki xətanı aradan qaldırmaq
naminə bütün oxuculara zərər verərdi.

### Kaspersky masaüstü tətbiqini `PDM:Trojan.Win32.Generic` kimi işarələyir

**Bu, davranış evristikasından qaynaqlanan yanlış müsbət nəticədir. Heç bir yoluxma yoxdur.** Kaspersky-nin
`PDM:` prefiksi qərarın Proactive Defense Module (System Watcher) tərəfindən verildiyini bildirir;
bu modul quraşdırıcını məlum zərərli proqramlarla müqayisə etmək əvəzinə onun _nə etdiyini_ qiymətləndirir. Bu
işə düşdükdə Kaspersky bütün quraşdırmanı “geri qaytarır” — artıq yazılmış faylları silir — və
nəticədə tətbiq ya zədələnir, ya da tamamilə yox olur.

İşarələnən fayllar masaüstü tətbiqi ilə birlikdə təqdim olunan, bəyan edilmiş açıq mənbəli asılılıqların
standart hissələridir, məsələn:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` və
  `workerProcessEntry.js` — tətbiqdaxili provayder girişi və brauzer dəstəkli çat üçün istifadə edilən
  brauzer avtomatlaşdırma kitabxanası [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — veb kuki provayderlərində brauzer barmaq izi ilə HTTP sorğuları üçün istifadə olunan sabitlənmiş
  `wreq-js` yerli bağlaması (`<arch>` `x64` və ya `arm64` olur).

**Niyə işə düşür:** Windows quraşdırıcısı **hələ rəqəmsal imza ilə imzalanmayıb**, buna görə imzasız NSIS
quraşdırıcısının reputasiyası sıfırdır və davranış evristikaları maksimum aqressivliklə işləyir. Buna
paketə daxil edilmiş yerli DLL və `%LOCALAPPDATA%\Programs\OmniRoute` daxilində yazılan yüzlərlə
`.js` faylı (Next.js müstəqil quruluşundan gələn heş şəkilçili paket qovluqları daxil olmaqla)
əlavə edildikdə, bu, evristik yoxlamanı işə salmaq üçün kifayətdir. Kodun imzalanması planlaşdırılır;
bu həyata keçirilənədək yeni buraxılışlarda problem təkrarlana bilər.

**Nə etməli:**

1. **Əvvəlcə endirdiyiniz faylı yoxlayın** (bu, faylın dəyişdirilməsi ehtimalını istisna edir). Hər buraxılışda
   `latest.yml` dərc olunur; onun `sha512` sahəsi (base64) `OmniRoute.Setup.<version>.exe`
   quraşdırıcısını əhatə edir. PowerShell-də quraşdırıcının olduğu qovluqdan:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Çıxış `latest.yml` → `sha512` ilə uyğun gəlməlidir. Uyğun gəlmirsə, faylı silin və
   yalnız [GitHub buraxılışları səhifəsindən](https://github.com/diegosouzapw/OmniRoute/releases) yenidən endirin.
2. **Bərpa edin + istisna əlavə edin** — geri qaytarılaraq silinmiş elementləri karantindən bərpa edin və
   `%LOCALAPPDATA%\Programs\OmniRoute` üçün istisna əlavə edin (Kaspersky → Settings → Threats and Exclusions),
   sonra yenidən quraşdırın.
3. **Yanlış müsbət nəticəni bildirin** — <https://opentip.kaspersky.com/>. İstifadəçilərin təqdim etdiyi yanlış
   müsbət nəticə hesabatları icazə siyahısına əlavə edilməni həqiqətən sürətləndirir.

## Node.js Uyğunluğu

<a name="nodejs-compatibility"></a>

### Giriş səhifəsi çökür və ya "Module self-registration" xətası göstərir

**Səbəb:** OmniRoute-un təsdiqlənmiş təhlükəsiz icra mühiti üzrə minimum tələblərindən kənar Node.js versiyasından istifadə edirsiniz. Ən çox rast gəlinən hal OmniRoute-un tələb etdiyi təhlükəsizlik yeniləmələri səviyyəsindən aşağı olan köhnə Node 22 və ya 24 yamaq versiyasından istifadə edilməsidir.

**Əlamətlər:**

- Giriş səhifəsi boş ekran və ya server xətası göstərir
- Konsolda `Error: Module did not self-register` və ya oxşar yerli bağlama xətaları görünür
- İcra mühiti dəstəklənən təhlükəsizlik siyasətinə uyğun olmadıqda giriş səhifəsində Node versiyanızın göstərildiyi **narıncı xəbərdarlıq banneri** görünür

**Həll:**

1. Dəstəklənən Node.js LTS buraxılışını quraşdırın (tövsiyə olunur: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Versiyanızı yoxlayın: `node --version` əmri 24.x LTS xəttində `v24.0.0` və ya daha yeni versiyanı göstərməlidir
3. OmniRoute-u yenidən quraşdırın: `npm install -g omniroute`
4. Yenidən başladın: `omniroute`

> **Dəstəklənən təhlükəsiz versiyalar:** `>=22.22.2 <23` və ya `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) və Node.js 26 tam dəstəklənir.

### npm v11+: `better-sqlite3` quraşdırılmayıb (Modul tapılmır)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Səbəb:** npm v11 (Node.js 24+ ilə birlikdə təqdim olunur) standart olaraq əlavə
asılılıqlar üçün quraşdırma skriptlərini bloklayır. `better-sqlite3` `optionalDependencies`
bölməsində göstərildiyinə və yerli kompilyasiya (`node-gyp rebuild`) tələb etdiyinə görə npm səssizcə onu ötürür.

**Əlamətlər:**

- Server işə salınarkən `Cannot find module 'better-sqlite3'` xətası ilə çökür
- `ls node_modules/better-sqlite3` əmri "No such file or directory" göstərir
- `npm ls better-sqlite3` əmri `(empty)` göstərir

**Həll:**

1. Quraşdırma skriptlərini təsdiqləyin və yenidən quraşdırın:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Yaxud əvvəlcədən hazırlanmış paketi əl ilə quraşdırın:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. İşlədiyini yoxlayın: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Səbəb:** Qlobal `npm install -g omniroute` quraşdırmasından sonra paketin daxilindəki `better-sqlite3` yerli binar faylı lokal olaraq işləyən mühitdən fərqli arxitektura və ya Node.js ABI üçün kompilyasiya edilmiş ola bilər. Əvvəlcədən hazırlanmış binar fayl mühitinizə uyğun gəlmədikdə bu problem macOS-da (həm Apple Silicon, həm də Intel platformalarında) tez-tez baş verir.

**Əlamətlər:**

- Server işə salınan kimi `dlopen` xətası ilə dayanır
- Xətada `slice is not valid mach-o file` mətni olur
- Tam nümunə:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Həll — lokal mühitiniz üçün yenidən qurun (Node.js versiyasını azaltmaq tələb olunmur):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Qeyd:** Bu əməliyyat yerli bağlamanı lokal Node.js versiyanıza və CPU arxitekturanıza uyğun olaraq yenidən kompilyasiya edir və binar uyğunsuzluğunu aradan qaldırır. Rəsmi olaraq dəstəklənən icra mühiti diapazonu **`>=22.22.2 <23` və ya `>=24.0.0 <27`**-dir (`src/shared/utils/nodeRuntimeSupport.ts` faylındakı `SUPPORTED_NODE_RANGE`, `package.json` faylındakı `engines` sahəsi ilə uyğunlaşdırılıb). Node.js 24.x LTS (Krypton) və Node.js 26 `better-sqlite3` v12.x ilə tam dəstəklənir.

## Proksi Problemləri

<a name="proxy-issues"></a>

### Təminatçı doğrulaması "fetch failed" xətası göstərir

**Səbəb:** API açarının doğrulama son nöqtəsi (`POST /api/providers/validate`) əvvəllər proksi konfiqurasiyasından yan keçirdi və bu, proksi marşrutlaşdırması tələb edən mühitlərdə xətalara səbəb olurdu.

**Həll (v3.5.5+):** Bu problem artıq aradan qaldırılıb. Təminatçı doğrulaması `runWithProxyContext` vasitəsilə marşrutlaşdırılır və təminatçı səviyyəsindəki və qlobal proksi parametrləri avtomatik nəzərə alınır.

### Tokenin vəziyyət yoxlaması "fetch failed" xətası ilə uğursuz olur

**Səbəb:** Arxa fonda OAuth tokeninin yenilənməsi hər bağlantı üçün proksi konfiqurasiyasını müəyyən etmirdi.

**Həll (v3.5.5+):** Token vəziyyətini yoxlayan planlaşdırıcı artıq yeniləməyə cəhd etməzdən əvvəl hər bağlantı üçün proksi konfiqurasiyasını müəyyən edir. v3.5.5+ versiyasına yeniləyin.

### SOCKS5 proksisi "invalid onRequestStart method" xətası qaytarır

**Səbəb:** Node.js 22-də undici@8 dispetçeri Node-un daxili `fetch()` reallaşdırması ilə uyğun deyil.

**Həll (v3.5.5+):** OmniRoute artıq proksi dispetçeri aktiv olduqda undici-nin öz `fetch()` funksiyasından istifadə edir və bununla da ardıcıl davranışı təmin edir. v3.5.5+ versiyasına yeniləyin.

### WSL daxilində MITM proksisi: Windows hostundakı masaüstü tətbiqləri ələ keçirilmir

**Səbəb:** MITM proksisi və onun CA sertifikatı OmniRoute-un işlədiyi mühitə quraşdırılır. WSL daxilində həmin mühit Linux qonaq sistemi olduğu halda, süni intellekt masaüstü tətbiqləri (Kiro, Trae, Copilot, Zed, …) Windows hostunda işləyir. Host tətbiqləri qonaq sisteminin sertifikat anbarına etibar etmir və qonaq sisteminin sistem proksisi vasitəsilə marşrutlaşdırılmır, buna görə də masaüstü trafikinin ələ keçirilməsi orada işə düşmür.

**Tövsiyə:** OmniRoute-u ələ keçirmək istədiyiniz masaüstü tətbiqləri ilə eyni əməliyyat sistemində yerli şəkildə işə salın (Windows tətbiqləri üçün Windows; macOS/Linux üçün də müvafiq olaraq). Host tətbiqlərini hədəfləyərkən OmniRoute-u WSL daxilində saxlamaq üçün yaradılmış CA sertifikatına Windows hostunda əl ilə etibar etmək və hər bir host tətbiqinin şəbəkə/proksi parametrlərini WSL proksi son nöqtəsinə yönəltmək lazımdır — bu, dəstəklənməyən və qeyri-sabit bir quraşdırmadır.

## Təminatçı Problemləri

### "Language model did not provide messages"

**Səbəb:** Təminatçı kvotası tükənib.

**Həll:**

1. İdarəetmə panelindəki kvota izləyicisini yoxlayın
2. Ehtiyat səviyyələri olan kombinasiyadan istifadə edin
3. Daha ucuz/pulsuz səviyyəyə keçin

### Sorğu Tezliyinin Məhdudlaşdırılması

**Səbəb:** Abunəlik kvotası tükənib.

**Həll:**

- Ehtiyat keçid əlavə edin: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Ucuz ehtiyat variant kimi GLM/MiniMax istifadə edin

### OAuth Tokeninin Müddəti Bitib

OmniRoute tokenləri avtomatik yeniləyir. Problemlər davam edərsə:

1. İdarəetmə paneli → Təminatçı → Yenidən qoşulun
2. Təminatçı bağlantısını silin və yenidən əlavə edin

### Kiro-da çoxsaylı hesablar: ikinci hesab birincini etibarsız edir

**Səbəb:** Kiro-nun arxa sistemi hər OIDC müştəri qeydiyyatı üçün yalnız bir aktiv sessiyaya icazə verir.
İki hesab eyni qeydiyyatdan keçmiş müştərini paylaşdıqda (v3.8.0-dan əvvəl idxal edilmiş bağlantılar),
bir hesabın tokeninin yenilənməsi digərinin yeniləmə tokenini etibarsız edir.

**Həll (v3.8.0+):** Təsirlənmiş bağlantıları yenidən idxal edin.
v3.8.0-dan başlayaraq **Tokeni İdxal Et**,
**Google/GitHub sosial girişi** və ya **Avtomatik İdxal** vasitəsilə yaradılan hər yeni Kiro bağlantısı avtomatik olaraq öz
ayrılmış OIDC müştərisini qeydiyyatdan keçirir. Beləliklə, bağlantı tam təcrid olunur və bir
hesabın yenilənməsi heç bir digər hesaba təsir etmir.

v3.8.0-dan _əvvəl_ idxal edilmiş bağlantılarda hər bağlantı üçün ayrıca müştəri
qeydiyyatı yoxdur. Bu bağlantılar ortaq sosial autentifikasiya yeniləmə son nöqtəsindən istifadə etməyə davam edir.
Təcridi təmin etmək üçün köhnə bağlantını İdarəetmə paneli → Təminatçılar bölməsindən silin və onu
üç idxal üsulundan hər hansı biri ilə yenidən əlavə edin.

Tam təfərrüatlar və iki Kiro hesabını yanaşı əlavə etmək üçün addım-addım təlimatlar üçün
[`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md) sənədinə baxın.

## Bulud Problemləri

## Docker Problemləri

### Docker IPv6 / Bağlantının Sıfırlanması

<a name="docker-ipv6"></a>

**Əlamətlər:** `curl http://localhost:20128/v1/models` əmri `curl: (56) Recv failure: Connection reset by peer` xətası qaytarır. İdarəetmə paneli və autentifikasiya tələb etməyən son nöqtələr işləyir, lakin autentifikasiya tələb edən son nöqtələr uğursuz olur — bu, autentifikasiya problemi kimi görünsə də, əslində belə deyil.

**Səbəb:** `docker run -p 20128:20128` portu həm `0.0.0.0` (IPv4), həm də `::` (IPv6) üzərində dərc edir, lakin konteyner daxilindəki proses yalnız IPv4 üzərində dinləyir. `localhost` ünvanının əvvəlcə `::1` kimi həll edildiyi hostlarda bağlantı arxasında dinləyici olmayan dərc edilmiş IPv6 portuna yönəlir → bağlantı sıfırlanır.

**Həll:**

1. **Sürətli diaqnostika:** `curl -4 http://localhost:20128/v1/models` əmrini işə salın. Əgər `-4` ilə işləyir, onsuz isə uğursuz olursa, IPv6 ünvan bağlama uyğunsuzluğu var.
2. **Daimi həll:** `docker run` əmrinizdə `-p 127.0.0.1:20128:20128` istifadə edərək portu açıq şəkildə IPv4 ünvanına bağlayın:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Bu, IPv4 ünvanına bağlanmanı məcburi edir və həmçinin proksinin hostun bütün interfeyslərində əlçatan olmasının qarşısını alır.

## Dayanıqlılıq Parametrləri

### Avtomatik sorğu tezliyi məhdudiyyəti işə düşmür

- Avtomatik sorğu tezliyi məhdudiyyəti yalnız API açarı provayderlərinə tətbiq olunur (OAuth/abunəlik üçün deyil)
- **Settings → Resilience → Provider Profiles** bölməsində avtomatik sorğu tezliyi məhdudiyyətinin aktiv olduğunu yoxlayın
- Provayderin `429` status kodları və ya `Retry-After` başlıqları qaytarıb-qaytarmadığını yoxlayın

### Eksponensial geriləmənin tənzimlənməsi

Provayder profilləri bu parametrləri dəstəkləyir:

- **Baza gecikməsi** — İlk uğursuzluqdan sonrakı ilkin gözləmə müddəti (standart: 1s)
- **Maksimum gecikmə** — Maksimum gözləmə müddəti həddi (standart: 30s)
- **Çarpan** — Hər ardıcıl uğursuzluqda gecikmənin nə qədər artırılacağı (standart: 2x)

### Kütləvi eyni-vaxtlı sorğuların qarşısının alınması

Çoxlu paralel sorğu tezliyi məhdudlaşdırılmış provayderə göndərildikdə, OmniRoute sorğuları ardıcıl icra etmək və zəncirvari xətaların qarşısını almaq üçün mutex + avtomatik sorğu tezliyi məhdudiyyətindən istifadə edir. Bu, API açarı provayderləri üçün avtomatikdir.

### Söhbət sorğuları 503 / chat_admission_busy xətası ilə uğursuz olur

**Əlamətlər:**

- Söhbət tamamlamaları son nöqtəsi xəta kodu
  `chat_admission_busy` olan, yenidən sınana bilən `503` cavabı qaytarır.
- Cavaba `Retry-After` daxildir. #12135-dən etibarən dəyər müşahidə olunan
  doluluq əsasında hesablanır — sorğunun artıq gözlədiyi `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  pəncərəsi ilə cari ağır yük icarələrinin saxlanma müddətindən daha böyük olanı götürülür —
  tam saniyələrə yuxarı yuvarlaqlaşdırılır və 60 ilə məhdudlaşdırılır. Boş keçiddə tarixi minimumlar
  qorunur: bayt əsaslı yolda 2 saniyə, struktur əsaslı yolda 1 saniyə (buraya həmçinin
  `reason: "structure_limit"` daxildir).
- Bu, başqa ağır yüklü söhbət və ya uzunmüddətli axın cavabı hələ də
  icra prosesində olarkən baş verə bilər.

Bayt əsaslı cavab gövdəsi belədir:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Struktur əsaslı cavab eyni növ və koddan, həmçinin
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
mesajından və `reason: "structure_limit"` dəyərindən istifadə edir.
Standart hədlərdə sorğu ən azı `200` mesaja, ən azı `64` alətə və ya ən azı
`32,000` təxmini tokenə malik olduqda, yaxud məhdudlaşdırılmış struktur qiymətləndirməsi
`10,000` ziyarət edilmiş qovşaq və ya `12` dərinlik hədlərini tükətdikdə struktur baxımından ağır sayılır.

**Səbəb:** Bu, yuxarı axın provayderinin nasazlığı deyil, OmniRoute daxilində qəsdən yükün azaldılmasıdır.
Hər proses böyük sorğu gövdəsini yaddaşda saxlamazdan və təhlil etməzdən əvvəl məhdud ağır yük
tutumunu rezerv etmək üçün prosesə lokal qoruyucudan istifadə edir. Ağır yük icarəsi SSE
cavabının bütün ömrü boyu saxlanılır.

**#503-fanout:** bu düzəlişdən əvvəl qoruyucu, host yaddaşından asılı olmayaraq paralelliyi sabit sorğu SAYI
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, standart `1`) ilə məhdudlaşdırırdı, buna görə kodlaşdırma agentlərinin
şaxələnməsi (çoxsaylı alt-agentlər/CLI-lər, adətən > 256 KB olan gövdələr) effektiv paralelliyi
təxminən 1-ə endirirdi və tamamilə normal yük altında 503 xətalarına səbəb olurdu. İndi qoruyucu özünü tənzimləyir:
o, prosesin real yaddaş həddinə əsasən ölçüləndirilən, avtomatik müəyyən edilmiş qəbul BAYT büdcəsi
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ilə idarə olunur və həmçinin canlı resurs təzyiqi siqnalını nəzərə alır —
beləliklə, birdən çox ağır sorğunun eyni anda gəlməsinə görə deyil, yalnız host həqiqətən yaddaş təzyiqi altında
olduqda yükü azaldır. Köhnə say həddinə (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) hələ də riayət olunur,
lakin yalnız onu açıq şəkildə təyin etdikdə.

Tutum məşğul olduqda ağır yüklü sorğu, yenidən sınana bilən `503` cavabını verməzdən əvvəl yerin boşalması üçün
əvvəlcə `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` müddətinədək (standart `2000`, `0` gözləməni deaktiv edir) gözləyir.
Məhdud gözləmə ona görə mövcuddur ki, ağır alt-sorğuları paralel şəkildə şaxələndirən agent tipli müştərilər
(OpenCode, Claude Code, Cursor) bütün yenidən sınama büdcələrini dərhal rədd cavablarına sərf edib tapşırığın
ortasında dayanmaq əvəzinə sorğu axınını ardıcıl icra etsinlər.
Ağır yük icarələrinin cari doluluğu, müəyyən edilmiş bayt büdcəsi və canlı təzyiqin ağırlıq dərəcəsi
`GET /api/monitoring/health` → `chatAdmission` ünvanında göstərilir (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — hər hansı mühit dəyişəninə toxunmazdan əvvəl bunları yoxlayın.
Settings → Resilience → Request Queue → Concurrent Requests bunu idarə etmir; həmin parametr
ayrıca provayder sorğu növbəsi mexanizmini idarə edir.

**Həll:**

1. Əvvəlcə yenidən sınayın. Müştərilər sorğunu dərhal təkrarlamaq əvəzinə `Retry-After` dəyərinə
   riayət etməli və geriləmədən istifadə etməlidirlər.
2. Hər hansı tənzimləmə etməzdən əvvəl `/api/monitoring/health` → `chatAdmission` bölməsini yoxlayın. `countCapEnabled:
false` və yüksək `maxInflightBytes` dəyəri avtomatik müəyyən edilmiş büdcənin artıq öz
   işini gördüyünü bildirir; `high`/`critical` olan `pressureSeverity` hostda həqiqətən yaddaş çatışmazlığı
   olduğunu göstərir — bunu qəbul mühit dəyişəni ilə düzəltmək mümkün deyil, daha çox RAM və ya daha kiçik iş yükü tələb olunur.
3. Yalnız `/api/monitoring/health` avtomatik müəyyən edilmiş büdcənin hostunuz üçün həqiqətən çox kiçik
   olduğunu göstərərsə (bu nadir haldır — büdcə artıq konteynerdən fiziki serverə qədər miqyaslanır), köhnə sorğu-sayı
   həddinə qayıtmaq əvəzinə onu birbaşa `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ilə əvəzləyin.

Rəsmi qəbul parametrləri üçün [mühit dəyişənləri arayışına](../reference/ENVIRONMENT.md#4-security--authentication)
baxın.

## İxtiyari RAG / LLM xəta taksonomiyası (16 problem)

Bəzi OmniRoute istifadəçiləri şlüzü RAG və ya agent steklərinin qarşısında yerləşdirirlər. Belə konfiqurasiyalarda qəribə bir mənzərə ilə tez-tez rastlaşmaq olur: OmniRoute normal işləyir (provayderlər aktivdir, yönləndirmə profilləri qaydasındadır, sürət məhdudiyyəti xəbərdarlıqları yoxdur), lakin yekun cavab yenə də yanlışdır.

Təcrübədə bu insidentlər adətən şlüzün özündən deyil, ondan sonrakı RAG konveyerindən qaynaqlanır.

Bu xətaları təsvir etmək üçün ortaq terminologiyadan istifadə etmək istəyirsinizsə, təkrarlanan on altı RAG / LLM xəta modelini müəyyən edən və MIT lisenziyalı xarici mətn resursu olan WFGY ProblemMap-dən istifadə edə bilərsiniz. Ümumi səviyyədə o, aşağıdakıları əhatə edir:

- axtarış sapması və pozulmuş kontekst sərhədləri
- boş və ya köhnəlmiş indekslər və vektor anbarları
- embedding və semantika uyğunsuzluğu
- prompt-un tərtibi və kontekst pəncərəsi problemləri
- məntiqin çökməsi və həddindən artıq əminliklə verilən cavablar
- uzun zəncir və agent koordinasiyası xətaları
- çoxagentli yaddaş və rol sapması
- yerləşdirmə və ilkin işəsalma ardıcıllığı problemləri

İdeya sadədir:

1. Səhv cavabı araşdırarkən aşağıdakıları qeydə alın:
   - istifadəçi tapşırığı və sorğusu
   - OmniRoute-dakı marşrut və ya provayder kombinasiyası
   - sonrakı mərhələdə istifadə olunan hər hansı RAG konteksti (əldə edilmiş sənədlər, alət çağırışları və s.)
2. İnsidenti bir və ya iki WFGY ProblemMap nömrəsi (`No.1` … `No.16`) ilə uyğunlaşdırın.
3. Nömrəni OmniRoute jurnallarının yanında öz idarəetmə panelinizdə, əməliyyat təlimatınızda və ya insident izləyicinizdə saxlayın.
4. RAG stekinizi, axtarış mexanizminizi və ya yönləndirmə strategiyanızı dəyişməli olub-olmadığınızı müəyyən etmək üçün müvafiq WFGY səhifəsindən istifadə edin.

Tam mətn və konkret reseptlər burada yerləşir (MIT lisenziyası, yalnız mətn):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute arxasında RAG və ya agent konveyerləri işlətmirsinizsə, bu bölməni nəzərə almaya bilərsiniz.

## v3.8.0 Məlum problemlər

v3.8.0 buraxılışına xas problemlər və onların cari müvəqqəti həlləri. Düzəliş sonrakı patçda təqdim olunarsa, müvafiq qeyd yenilənəcək və ya silinəcək.

### Devin CLI autentifikasiya xətaları

**Əlamətlər:**

- Devin əsaslı alətlər çağırılarkən "Devin CLI not found" və ya "auth failed" mesajı
- CLI icra mühiti yoxlaması `installed=false` nəticəsini göstərir

**Səbəblər:**

- `CLI_DEVIN_BIN` mövcud olmayan yola istinad edir
- Devin CLI hostda quraşdırılmayıb

**Həll:**

1. Platformanız üçün Devin CLI-ni quraşdırın
2. `.env` faylında `CLI_DEVIN_BIN=/usr/local/bin/devin` (və ya real yol) təyin edin
3. OmniRoute-u yenidən başladın və **İdarəetmə paneli → CLI Alətləri** bölməsindən təkrar sınaqdan keçirin

### Modelin gözləmə müddəti ilişib qalıb (əl ilə sıfırlama)

**Əlamətlər:**

- Gözləmə müddəti bitdikdən sonra belə model gözləmə rejimində göstərilməyə davam edir
- Vaxt nişanı keçmişdə olsa belə, kombinasiya yönləndirməsində sorğular hələ də modeli ötürür

**Əl ilə sıfırlama:**

- **İdarəetmə paneli:** **Parametrlər → Modelin Gözləmə Müddətləri** → təsirlənmiş kartda **Yenidən aktivləşdir** düyməsinə klikləyin
- **API:** idarəetmə autentifikasiyası başlıqları ilə `DELETE /api/resilience/model-cooldowns`

### Command Code provayderinə qoşulma 403 xətası ilə uğursuz olur

**Əlamətlər:**

- Command Code provayder bağlantısı sınaqdan keçirilərkən 403 xətası
- Provayder kartı yeni əlavə edildikdən sonra "unauthorized" göstərir

**Səbəb:** OAuth axını tamamlanmayıb (geri çağırış alınmayıb və ya token saxlanmayıb).

**Həll:**

- OAuth axınını yenidən işə salmaq üçün CLI-dən `omniroute providers` əmrini icra edin və ya
- OAuth-u **İdarəetmə paneli → Provayderlər → Command Code → Yenidən qoşul** bölməsindən təkrar başladın

### ModelScope aqressiv 429 gözləmə müddətləri qaytarır

**Əlamətlər:**

- Kiçik sorğu partlayışından sonra ModelScope-da çox qısa və ya dərhal başlayan gözləmə müddətləri
- Kombinasiya yönləndirməsi ModelScope-u gözləniləndən daha erkən ötürür

**Səbəb:** ModelScope provayderə xas `Retry-After` başlıqları göndərir. v3.8.0 bu başlıqlar üçün xüsusi emal mexanizmi ilə təqdim olunur, buna görə də köhnə versiyalar onları ümumi sürət məhdudiyyəti göstərişləri kimi səhv şərh edir.

**Həll:**

- v3.8.0 və ya daha yeni versiyadan istifadə etdiyinizə əmin olun
- **Parametrlər → Dayanıqlılıq** bölməsində `useUpstream429BreakerHints` keçidinin aktiv olduğunu yoxlayın

### OMNIROUTE_WS_BRIDGE_SECRET istehsal mühitində yoxdur

**Əlamətlər:**

- Uzaq istehsal hostunda işləyərkən hər Codex/Responses WebSocket körpü sorğusunda 401 xətası
- WebSocket körpüsünün ilkin əlaqəsi qoşulmadan dərhal sonra bağlanır

**Səbəb:** İstehsal mühitində `OMNIROUTE_WS_BRIDGE_SECRET` mühit dəyişəni yoxdur.

**Həll:**

1. Təsadüfi məxfi dəyər yaradın: `openssl rand -hex 32`
2. İstehsal serverinin mühitində (və körpü ilə əlaqə saxlayan istənilən klientdə) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` təyin edin
3. OmniRoute-u yenidən başladın

### Responses API: fon rejimi sinxron rejimə endirilib

**Əlamətlər:**

- Jurnala xəbərdarlıq yazılır: `background mode degraded to synchronous`
- `background: true` sorğusu fon tapşırığı identifikatoru əvəzinə adi sinxron cavab qaytarır

**Səbəb:** v3.8.0 Responses API-də `background: true` parametrini bilərəkdən sinxron icraya endirir və eyni zamanda xəbərdarlıq göndərir. Tam asinxron fon icrası gələcəkdə təqdim ediləcək funksiyadır.

**Həll:**

- Klienti `background` olmadan çağırış edəcək şəkildə tənzimləyin və ya
- Tam asinxron fon rejimini təqdim edən sonrakı buraxılışı gözləyin (dəyişiklik jurnalını izləyin)

## Yavaş Başlama / Hazırlıq Taym-autu

CLI `⚠ Server did not respond within 60s` mesajını göstərirsə, lakin server əslində işləyirsə, hazırlıq yoxlaması üçün ayrılmış vaxt mühitiniz üçün çox qısadır.

Bu, adətən Windows-da (antivirus, fayl sistemi izləyiciləri) və ya ağır başlanğıc iş yükü olan konteynerlərdə baş verir.

**Həll — ayrılmış vaxtı artırın:**

```bash
# Mühit dəyişəni vasitəsilə (başlatmalar arasında qüvvədə qalır):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 dəqiqə
omniroute serve

# CLI bayrağı vasitəsilə (birdəfəlik):
omniroute serve --ready-timeout 180000
```

Standart dəyər 60 000 ms-dir (60 s). Xəbərdarlıq yalnız məlumat xarakterlidir; server arxa planda başlamağa davam edir və yüklənmə tamamlandıqdan sonra əlçatan olacaq.

`OMNIROUTE_READY_TIMEOUT_MS` haqqında tam məlumat üçün [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) sənədinə baxın.
