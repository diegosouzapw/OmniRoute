## Qısa arayış

**OmniRoute-da yenisiniz?** Buradan başlayın — bunlar problemlərin 90%-ni həll edir:

| Bunu görürəm                       | Mənası                                       | Nə etməli                                                                                               |
| ---------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| "Qoşulmaq mümkün deyil"            | OmniRoute işləmir                            | `omniroute` və ya `docker restart omniroute` əmrini icra edin                                           |
| "Etibarsız API açarı"              | Açarınız yanlışdır və ya vaxtı bitib         | Açarı provayderin veb-saytından yenidən köçürün                                                         |
| "Sorğu limiti aşılıb"              | Həddindən artıq çox sorğu göndərirsiniz      | 1 dəqiqə gözləyin və ya avtomatik alternativə keçid üçün `model: "auto"` istifadə edin                  |
| "Kvota aşılıb"                     | Pulsuz/ödənişli kvotanızı bitirmisiniz       | Daha çox provayder qoşun və ya pulsuz provayderlərdən (Kiro, Pollinations) istifadə edin                |
| "Yavaş cavablar"                   | Provayder məşğuldur və ya uzaqdadır          | `model: "auto/fast"` istifadə edin və ya daha sürətli provayder (Groq, Cerebras) qoşun                  |
| "Yanlış provayder istifadə edildi" | `auto` fərqli provayder seçdi                | Bu, normaldır! `auto` ən yaxşısını seçir. `model: "openai/gpt-4o"` ilə konkret provayderi məcburi seçin |
| "502 Bad Gateway"                  | Provayder işləmir                            | Gözləyib yenidən cəhd edin və ya provayderləri dəyişmək üçün `model: "auto"` istifadə edin              |
| "401 Unauthorized"                 | Giriş məlumatlarınız yanlışdır               | API açarınızı yoxlayın və ya OAuth ilə yenidən autentifikasiyadan keçin                                 |
| "omniroute tanınmır"               | Windows PATH-də qlobal node modulları yoxdur | npm qlobal prefiksinizi Windows PATH-ə əlavə edin. Onu `npm config get prefix` ilə tapın.               |
| "429 Too Many Requests"            | Sorğu tezliyi məhdudlaşdırılıb               | 1 dəqiqə gözləyin və ya daha çox provayder qoşun                                                        |

## Ətraflı problemlərin aradan qaldırılması

---

### Pulsuz provayderlərdə sorğu tezliyinin məhdudlaşdırılması (429 / 400 / 401)

**Əlamət**: Pulsuz/autentifikasiya tələb etməyən provayderlərlə (opencode, auggie və s.) `model: "auto"` istifadə etdikdə cavablar əvəzinə arabir `HTTP 429`, `400` və ya `401` alırsınız. Eyni sorğu bir neçə an sonra yenidən göndərildikdə uğurlu olur, lakin avtomatlaşdırma (cron tapşırıqları, agentlər, skriptlər) ilk xətada dayanır.

**Əsas səbəb**: Üç müstəqil nasazlıq rejimi üst-üstə düşür:

1. **Provayderin sorğu tezliyi limiti (`429`)**: Pulsuz tariflər müəyyən zaman intervalı üçün kvota tətbiq edə bilər. Paralel çağırışların ani artımı bu kvotanı tükəndirir, buna görə də zaman intervalı sıfırlanana qədər növbəti sorğu rədd edilir.
2. **Birbaşa ötürmədə nasaz model (`400`/`401`)**: `auto/*` hovuzlarına `opencode` provayderindən kataloqda qeydiyyatdan keçmiş, lakin aktiv giriş məlumatları olmayan birbaşa ötürmə modelləri daxil ola bilər (məsələn, `oc/north-mini-code-free` → `401`). Avtomatik marşrutlaşdırıcı onlardan birini sınayır, uğursuz olur və alternativə keçid işə düşməzdən əvvəl xəta ötürülür.
3. **Paralelliyin gücləndirici təsiri (yük altında `429`)**: Bir neçə agent/cron sessiyası eyni anda `auto`-ya müraciət etdikdə ümumi sorğu tezliyi pulsuz provayderlərin dözə bildiyi həddi aşır və nəticədə etibarlı çağırışlar sui-istifadə kimi işarələnir.

**Təsdiqlənmiş həll (icma tərəfindən bildirilib, 2026-08-10)**: rotasiya, paralellik və alternativə keçid pulsuz tarifdəki qeyri-sabitliyi xəta ilə dayanmaq əvəzinə kompensasiya etsin deyə üç mühit dəyişənini tənzimləyin:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 zamanı başqa modelə/provayderə keçin (nasaz birbaşa ötürmə modellərini ötürür)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ağır sorğular üçün açıq qəbul həddi (standart olaraq təyin edilməyib: sorğu sayı limiti yoxdur, aşağıdakı qeydə baxın)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # yavaş yuxarı axınlar üçün məhdud gözləmə müddətini RATE_LIMIT_MAX_WAIT_MS standart dəyərindən yuxarı qaldırın
```

Bunları OmniRoute prosesinin mühitində (demonda, məsələn, LaunchAgent plist və ya `systemctl edit` vasitəsilə) təyin edin, sonra OmniRoute-u yenidən başladın. Rotasiya bayrağı ən güclü təsirə malik tənzimləmə vasitəsidir: o, ciddi xətanı hovuzdakı işlək provayder üzərindən şəffaf təkrar cəhdə çevirir.

**Qeyd**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` eyni vaxtda neçə ağır — uzun kontekstli — sorğunun işləyə biləcəyini məhdudlaşdırır; bu hədd provayderin sorğu tezliyi məhdudlaşdırıcısı deyil, qəbul qapısıdır. **#503-fanout yeniləməsi:** bu dəyişən artıq standart olaraq təyin edilmir (indi yalnız yuxarıdakı kimi açıq şəkildə konfiqurasiya edildikdə tətbiq olunur) — bunun əvəzinə ağır sorğuların qəbulu hostun real yaddaş həddinə uyğun olaraq özünü miqyaslandıran, avtomatik hesablanan bayt büdcəsi (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ilə idarə olunur. Buna görə yeni yerləşdirmədə bu dəyişən ümumiyyətlə təyin edilmədən xeyli daha az `503 chat_admission_busy` rəddi müşahidə edilməlidir; onu burada açıq şəkildə təyin etmək yenə də sənədləşdirildiyi kimi işləyir. Bayt büdcəsinin açıq şəkildə verilən dəyərləri 8 MiB–2 GiB aralığı ilə məhdudlaşdırılır. `413 body_exceeds_budget` müvəqqəti xəta deyil: həmin bayt büdcəsini artırın, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` dəyərini azaldın və ya prosesin yaddaş həddini artırın. `inflight_bytes_budget` səbəbilə yükün azaldılması müvəqqəti resurs rəqabətidir və təkrar cəhd edilə bilər. Hər provayder üzrə sorğu tezliyinin məhdudlaşdırılması (`open-sse/services/rateLimitManager.ts`) ayrıca olaraq `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` və `RATE_LIMIT_AUTO_ENABLE` tərəfindən idarə olunur — `.env.example` faylına baxın.

**İşlədiyini necə yoxlamaq olar**: agentinizi/cron tapşırığınızı qısa fasilə ilə iki dəfə işə salın və hər ikisinin uğurla tamamlandığını təsdiqləyin. Düzəlişdən əvvəl ikinci işə salınma adətən `429`/`401` xətası verir. Düzəlişdən sonra xətalar (əgər varsa) şəffaf şəkildə yenidən sınaqdan keçirilir və çağırış tamamlanır. Həmçinin `curl /monitoring/health` əmrini icra edib provayder bağlantılarındakı `rateLimitedUntil` sahəsini və təsirə məruz qalan provayderlər üçün `circuitBreakers.providerBreakers[].state` dəyərini izləyə bilərsiniz — vəziyyət `CLOSED`, `DEGRADED`, `OPEN` və ya `HALF_OPEN` dəyərlərindən biri olur (bax: `src/shared/utils/circuitBreaker.ts`) və davamlı xəta verən provayder, sıfırlama pəncərəsi sınaq sorğusunu buraxmazdan (`HALF_OPEN`) əvvəl `CLOSED → DEGRADED → OPEN` vəziyyətlərinə keçir.

**Hələ də 429 görürsünüzsə**: həmin provayder üçün aktiv hesabın _kvotası_ həqiqətən tükənib (sadəcə sorğu tezliyi limiti deyil). OmniRoute idarəetmə panelində Providers → Accounts bölməsinə keçərək eyni provayder üçün ikinci hesab əlavə edin və ya başqa pulsuz provayderdən (məsələn, `routeway`, `auggie`) də istifadə edin. Rotasiya yalnız müvəqqəti sorğu tezliyi/400/401 xətalarında kömək edir; kvotanın tam tükənməsi ikinci giriş məlumatı və ya fərqli provayder tələb edir.

**Görüntü modellərində (`auto/vision`, `bazaarlink/*`) 403 görürsünüzsə**: qoşulmuş hesabda görüntü imkanlarını əhatə edən ödənişli plan yoxdur və ya API açarının icazələri kifayət deyil. Provayderin idarəetmə panelində açarın əhatə dairəsinə görüntü/multimodal imkanlarının daxil olduğunu yoxlayın və ya ödənişli tarif hesabını qoşaraq onu görüntü üçün hədəf kimi saxlayın.

## npm install Xəbərdarlıqları (ERESOLVE / peer / deprecated)

`npm install -g omniroute` əmrini işlətdiyiniz zaman `npm warn ERESOLVE`, peer-asılılıq bildirişləri və `deprecated` mesajları kimi çoxlu sayda xəbərdarlıq görə bilərsiniz. **Bunlar gözləniləndir və zərərsizdir.** Çıxışda `added <N> packages` görürsünüzsə, quraşdırma uğurla tamamlanıb.

Peer-asılılıqların həlli ilə bağlı xəbərdarlıqları gizlətmək üçün OmniRoute tərəfindən dəstəklənən aşağıdakı quraşdırma formasından istifadə edin:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` yalnız `ERESOLVE` və peer-asılılıq bildirişlərini gizlədir. Köhnəlmə bildirişləri keçidli üçüncü tərəf paketlərindən gəldiyi üçün görünməyə davam edir; onlar quraşdırmanın uğursuz olduğunu göstərmir.

Xəbərdarlıqlar OmniRoute-un nəzarət etmədiyi üçüncü tərəf paketlərindəki köhnəlmiş peer-asılılıq diapazonlarından qaynaqlanır:

1. **`marked-terminal` paketi `marked >=1 <16` tələb edir, lakin `marked@18` tapılıb** — praktikada problemsiz işləyir; yuxarı axındakı peer diapazonu sadəcə köhnəlib.
2. **`deprecated prebuild-install@7.1.3`** — keçidli yerli ikili fayl əldəetmə köməkçisidir. O,
   sabitlənmiş `wreq-js` nəqliyyat bağlamasını quraşdırmaq üçün istifadə edilmir və veb-kuki
   provayderinin nəqliyyat sazlamasının uğursuz olduğunu göstərmir.

**Heç bir tədbir tələb olunmur** — yuxarı axın paketlərini fork etmədən xəbərdarlıqları tamamilə gizlətmək mümkün deyil.

## npm install-scripts Bloklanması Xəbərdarlığı (qlobal quraşdırma)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` işlədilərkən daha yeni npm versiyaları (v11+ və v12+) paketlərin həyat dövrü skriptlərini standart olaraq bloklayır və install-scripts xəbərdarlığı göstərir:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Bu xəbərdarlığa məhəl qoymamaq olarmı?

**Qismən, lakin skriptlər olmadan işlətmək tövsiyə edilmir.** OmniRoute problemsiz ehtiyat mexanizmləri ehtiva edir: yerli `better-sqlite3` bağlamalarını müstəqil paketdən yükləmək mümkün olmadıqda, tətbiq `node:sqlite` və ya `sql.js` kimi alternativ drayverlərə keçir (baxın: [SQLite İcra Mühitinin Müəyyənləşdirilməsi](../ops/SQLITE_RUNTIME.md)). Server yenə də işə düşəcək, lakin `sql.js` kimi WASM ehtiyat mexanizmləri üzərində işləmək SQLite WAL (Qabaqcadan Yazma Jurnalı) rejimini deaktiv edir, həmçinin yaddaş və disk sinxronizasiyası yükünü artırır.

### Hansı skriptlər həqiqətən tələb olunur?

Bloklanmış skriptlərin heç də hamısı OmniRoute-u işlətmək üçün vacib deyil:

- **Vacib (`omniroute`, `better-sqlite3`):** OmniRoute Next.js-in müstəqil tətbiq paketindən (`dist/`) işləyir. Quraşdırma zamanı npm hosta uyğun yerli SQLite drayverini üst səviyyədəki `node_modules/better-sqlite3/` daxilində endirir və ya kompilyasiya edir. Daha sonra OmniRoute-un `postinstall` skripti (`scripts/build/postinstall.mjs`) bu hosta uyğun ikili faylları yoxlayır və müstəqil serverin onlara çıxış əldə edə bilməsi üçün `dist/node_modules/` qovluğuna köçürür. `omniroute` paketinin postinstall skripti bloklanarsa, bu köçürmə addımı ötürülür.
- **İxtiyari/keçidli (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** Bunlar yığma köməkçiləri, izləmə alətləri və ya sistem açarlar zənciri utilitləridir. Onlara icazə vermək yığma xəbərdarlıqlarının qarşısını alır, lakin onlar əsas marşrutlaşdırma funksionallığı üçün tələb olunmur.
- **İstisna edilən (`onnxruntime-node`):** Lokal süni intellekt yerləşdirmələri üçün ixtiyari asılılıqdır və OmniRoute-un işləməsi üçün **tələb olunmur**. Onun postinstall skripti NuGet-dən təxminən 300MB həcmində CUDA resursu endirir; dəstəklənən avadanlıqda lokal ONNX sürətləndirməsindən istifadə etməyi açıq şəkildə planlaşdırmırsınızsa, onu icazə siyahısına daxil etməyin.

### Tövsiyə olunan həll

Qlobal quraşdırma zamanı tələb olunan quraşdırma skriptlərinə icazə vermək və xəbərdarlıqları gizlətmək üçün OmniRoute və onun yerli asılılıqları üçün `--allow-scripts` parametrini ötürün:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

Alternativ olaraq, bunu istifadəçi hesabınızdakı bütün qlobal quraşdırmalar üçün daimi şəkildə konfiqurasiya etmək məqsədilə:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### Quraşdırmanızı yoxlayın

Quraşdırmadan sonra yerli bağlamaların və icra mühitinin düzgün işlədiyinə əmin olmaq üçün daxili diaqnostika alətini işə salın:

```bash
omniroute doctor
```

## Antivirusun yanlış müsbət nəticələri

<a name="antivirus-false-positives"></a>

### Avast/AVG `README.md` faylını `MD:HttpRequest-inf[Susp]` kimi karantinə alır

**Bu, yanlış müsbət nəticədir. Heç nə yoluxmayıb və heç bir tədbir tələb olunmur.**

Avast və AVG çoxlu HTTP sorğusuna bənzəyən keçidlər ehtiva edən düz mətn/Markdown fayllarını işarələyən evristik yoxlama tətbiq edir. OmniRoute-un `README.md` faylı npm paketinə daxildir (`package.json` → `files` siyahısında göstərilib), buna görə də qlobal quraşdırma zamanı `node_modules/omniroute/README.md` ünvanına yerləşdirilir və təxminən 15 `http://localhost:20128/...` nümunəsi (MCP HTTP/SSE son nöqtələri, A2A `.well-known` URL-i və `curl` fraqmentləri) ehtiva edir. Keçidlərin bu sıxlığı evristik yoxlamanın işə düşməsi üçün kifayətdir.

Bu, yalnız yaxın zamanda baş verməyə başlayıbsa: faylın mahiyyəti dəyişməyib. README-dəki son nöqtələr cədvəli genişləndirilib (MCP HTTP + SSE + A2A əlavə olunub) və daha çox `curl` nümunəsi əlavə edilib; bu da faylın həddi keçməsinə səbəb olub.

Fayl heç bir icra edilə bilən məzmunu olmayan passiv sənədləşdirmədir. Onu təhlükəsiz şəkildə karantindən bərpa edə bilərsiniz.

**Nə etməli:**

1. **Bildirişləri dayandırın** — antivirusunuzda quraşdırma qovluğunu istisnalara əlavə edin (Avast: Settings → Exceptions); qlobal `node_modules` yolunuzu və/və ya OmniRoute məlumat qovluğunu (`~/.omniroute/`) əlavə edin.
2. **Yanlış müsbət nəticəni bildirin** — <https://www.avast.com/false-positive-file-form.php> ünvanına keçərək karantinə alınmış `README.md` faylını əlavə edin. Bu, hər kəsə kömək edən həll yoludur, çünki problem təchizatçının evristik yoxlamasının mətn faylına həddindən artıq reaksiya verməsidir.

**Niyə bunu öz tərəfimizdə «düzəltmirik»:** bütün nümunələr `http://localhost` istifadə edir və localhost öz-özünə imzalanmış sertifikatların yaratdığı çətinliklər olmadan `https` istifadə edə bilməz. Bir təchizatçının evristik yoxlamasından yayınmaq üçün sənədləri təhrif etmək, skaner xətasını aradan qaldırmaq naminə bütün oxuculara zərər verərdi.

### Kaspersky masaüstü tətbiqini `PDM:Trojan.Win32.Generic` kimi işarələyir

**Bu, davranış evristikasından qaynaqlanan yanlış müsbət nəticədir. Heç nə yoluxmayıb.** Kaspersky-nin `PDM:` prefiksi qərarın məlum zərərli proqramla uyğunluğu yoxlamaq əvəzinə quraşdırıcının nə _etdiyini_ qiymətləndirən Proactive Defense Module (System Watcher) tərəfindən verildiyini bildirir. Bu modul işə düşdükdə Kaspersky bütün quraşdırmanı «geri qaytarır» — artıq yazılmış faylları silir — nəticədə tətbiq işləməz vəziyyətə düşür və ya yox olur.

İşarələnən fayllar masaüstü tətbiqlə birlikdə paketlənmiş, bəyan edilmiş açıq mənbəli asılılıqların standart hissələridir, məsələn:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` və
  `workerProcessEntry.js` — tətbiqdaxili provayder girişində və brauzer əsaslı söhbətdə istifadə olunan brauzer avtomatlaşdırma kitabxanası [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — veb kuki provayderlərində brauzer barmaq izi ilə HTTP sorğuları üçün istifadə olunan sabitlənmiş `wreq-js` yerli bağlaması (`<arch>` `x64` və ya `arm64` olur).

**Niyə işə düşür:** Windows quraşdırıcısı **hələlik kod imzasına malik deyil**, buna görə imzasız NSIS quraşdırıcısının reputasiyası sıfırdır və davranış evristikası maksimum sərtliklə işləyir. Paketlənmiş yerli DLL və `%LOCALAPPDATA%\Programs\OmniRoute` daxilində yazılan yüzlərlə `.js` faylı (Next.js müstəqil yığmasından gələn, adlarına heş əlavə edilmiş paket qovluqları daxil olmaqla) ilə birlikdə bu, evristik yoxlamanın işə düşməsi üçün kifayətdir. Kod imzalanması planlaşdırılır; həyata keçirilənədək yeni buraxılışlarda bu hal təkrarlana bilər.

**Nə etməli:**

1. **Əvvəlcə endirdiyiniz faylı yoxlayın** (faylın dəyişdirilməsi ehtimalını aradan qaldırır). Hər buraxılış `latest.yml` faylını dərc edir və onun `sha512` sahəsi (base64) `OmniRoute.Setup.<version>.exe` quraşdırıcısını əhatə edir. PowerShell-də quraşdırıcının yerləşdiyi qovluqdan:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Çıxış `latest.yml` → `sha512` ilə uyğun olmalıdır. Uyğun deyilsə, faylı silin və yalnız [GitHub buraxılışları səhifəsindən](https://github.com/diegosouzapw/OmniRoute/releases) yenidən endirin.
2. **Bərpa edin + istisna əlavə edin** — geri qaytarılaraq silinmiş elementləri karantindən bərpa edin və `%LOCALAPPDATA%\Programs\OmniRoute` üçün istisna əlavə edin (Kaspersky → Settings → Threats and Exclusions), sonra yenidən quraşdırın.
3. **Yanlış müsbət nəticəni bildirin** — <https://opentip.kaspersky.com/>. İstifadəçilərin təqdim etdiyi yanlış müsbət nəticə hesabatları icazə verilənlər siyahısına əlavə olunma prosesini həqiqətən sürətləndirir.

## Node.js Uyğunluğu

<a name="nodejs-compatibility"></a>

### Giriş səhifəsi çökür və ya "Module self-registration" xətası göstərir

**Səbəb:** OmniRoute-un təsdiqlənmiş təhlükəsiz icra mühiti üçün minimum tələbindən kənar Node.js versiyasından istifadə edirsiniz. Ən çox rast gəlinən hal OmniRoute-un tələb etdiyi yenilənmiş təhlükəsizlik minimumundan aşağı olan köhnə Node 22 və ya 24 yamaq versiyasının istifadə edilməsidir.

**Əlamətlər:**

- Giriş səhifəsi boş ekran və ya server xətası göstərir
- Konsolda `Error: Module did not self-register` və ya buna bənzər yerli bağlama xətaları görünür
- İcra mühiti dəstəklənən təhlükəsizlik siyasətindən kənardadırsa, giriş səhifəsində Node versiyanızı göstərən **narıncı xəbərdarlıq banneri** görünür

**Həll:**

1. Dəstəklənən Node.js LTS buraxılışını quraşdırın (tövsiyə olunur: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Versiyanızı yoxlayın: `node --version` 24.x LTS xəttində `v24.0.0` və ya daha yeni versiyanı göstərməlidir
3. OmniRoute-u yenidən quraşdırın: `npm install -g omniroute`
4. Yenidən başladın: `omniroute`

> **Dəstəklənən təhlükəsiz versiyalar:** `>=22.22.2 <23` və ya `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) və Node.js 26 tam şəkildə dəstəklənir.

### npm v11+: `better-sqlite3` quraşdırılmayıb (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Səbəb:** npm v11 (Node.js 24+ ilə birlikdə təqdim olunur) standart olaraq istəyə bağlı
asılılıqların quraşdırma skriptlərini bloklayır. `better-sqlite3` `optionalDependencies`
bölməsində göstərildiyinə və yerli kompilyasiya (`node-gyp rebuild`) tələb etdiyinə görə npm onu heç bir bildiriş vermədən ötürür.

**Əlamətlər:**

- Server işə salınarkən `Cannot find module 'better-sqlite3'` xətası ilə çökür
- `ls node_modules/better-sqlite3` əmri "No such file or directory" göstərir
- `npm ls better-sqlite3` əmri `(empty)` göstərir

**Həll:**

1. Quraşdırma skriptlərini təsdiqləyin və yenidən quraşdırın:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Və ya əvvəlcədən yığılmış paketi əl ilə quraşdırın:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. İşlədiyini yoxlayın: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Səbəb:** Qlobal `npm install -g omniroute` quraşdırmasından sonra paketin daxilindəki `better-sqlite3` yerli binar faylı lokal olaraq işləyən mühitdən fərqli arxitektura və ya Node.js ABI üçün kompilyasiya edilmiş ola bilər. Əvvəlcədən yığılmış binar fayl mühitinizə uyğun gəlmədikdə bu hal macOS-da (həm Apple Silicon, həm də Intel sistemlərində) tez-tez baş verir.

**Əlamətlər:**

- Server işə salınarkən dərhal `dlopen` xətası ilə dayanır
- Xətada `slice is not valid mach-o file` ifadəsi yer alır
- Tam nümunə:


## Proksi problemləri

<a name="proxy-issues"></a>

### Provayder doğrulaması "fetch failed" xətasını göstərir

**Səbəb:** API açarının doğrulama son nöqtəsi (`POST /api/providers/validate`) əvvəllər proksi konfiqurasiyasından yan keçirdi və bu, proksi marşrutlaşdırması tələb edən mühitlərdə xətalara səbəb olurdu.

**Həll (v3.5.5+):** Bu problem artıq aradan qaldırılıb. Provayder doğrulaması `runWithProxyContext` vasitəsilə marşrutlaşdırılır və provayder səviyyəli, eləcə də qlobal proksi parametrləri avtomatik olaraq nəzərə alınır.

### Tokenin işləkliyinin yoxlanması "fetch failed" xətası ilə uğursuz olur

**Səbəb:** Arxa fonda OAuth tokeninin yenilənməsi hər bağlantı üçün proksi konfiqurasiyasını müəyyən etmirdi.

**Həll (v3.5.5+):** Tokenin işləkliyini yoxlayan planlaşdırıcı indi yeniləməyə cəhd etməzdən əvvəl hər bağlantı üçün proksi konfiqurasiyasını müəyyən edir. v3.5.5+ versiyasına yeniləyin.

### SOCKS5 proksisi "invalid onRequestStart method" xətasını qaytarır

**Səbəb:** Node.js 22-də undici@8 dispetçeri Node-un daxili `fetch()` implementasiyası ilə uyğun deyil.

**Həll (v3.5.5+):** OmniRoute indi proksi dispetçeri aktiv olduqda undici-nin öz `fetch()` funksiyasından istifadə edir və beləliklə ardıcıl davranışı təmin edir. v3.5.5+ versiyasına yeniləyin.

### WSL altında MITM proksisi: Windows hostundakı masaüstü tətbiqləri ələ keçirilmir

**Səbəb:** MITM proksisi və onun CA sertifikatı OmniRoute-un işlədiyi mühitə quraşdırılır. WSL altında həmin mühit Linux qonaq sistemidir, AI masaüstü tətbiqləri (Kiro, Trae, Copilot, Zed, …) isə Windows hostunda işləyir. Host tətbiqləri qonaq sisteminin sertifikat deposuna etibar etmir və qonaq sisteminin sistem proksisi vasitəsilə marşrutlaşdırılmır, buna görə də masaüstü trafikinin ələ keçirilməsi burada işə düşmür.

**Tövsiyə:** OmniRoute-u ələ keçirmək istədiyiniz masaüstü tətbiqləri ilə eyni əməliyyat sistemində yerli şəkildə işə salın (Windows tətbiqləri üçün Windows; macOS/Linux üçün də müvafiq olaraq). Host tətbiqlərini hədəfləyərkən OmniRoute-u WSL daxilində saxlamaq üçün yaradılmış CA sertifikatına Windows hostunda əl ilə etibar etmək və hər bir host tətbiqinin şəbəkə/proksi parametrlərini WSL proksi son nöqtəsinə yönəltmək tələb olunur — bu, dəstəklənməyən və etibarsız bir konfiqurasiyadır.

## Docker Problemləri

### Docker IPv6 / Bağlantının Sıfırlanması

<a name="docker-ipv6"></a>

**Əlamətlər:** `curl http://localhost:20128/v1/models` əmri `curl: (56) Recv failure: Connection reset by peer` qaytarır. İdarəetmə paneli və autentifikasiya tələb etməyən son nöqtələr işləyir, lakin autentifikasiya tələb edən son nöqtələr uğursuz olur — bu, autentifikasiya problemi kimi görünsə də, əslində belə deyil.

**Səbəb:** `docker run -p 20128:20128` portu həm `0.0.0.0` (IPv4), həm də `::` (IPv6) üzərində dərc edir, lakin konteyner daxilindəki proses yalnız IPv4 üzərindən dinləyir. `localhost` ünvanının əvvəlcə `::1` kimi həll edildiyi hostlarda bağlantı arxasında dinləyici olmayan dərc edilmiş IPv6 portuna yönəlir → bağlantı sıfırlanır.

**Həll:**

1. **Sürətli diaqnostika:** `curl -4 http://localhost:20128/v1/models` əmrini icra edin. `-4` ilə işləyib onsuz uğursuz olursa, IPv6 ünvanına bağlanma uyğunsuzluğu var.
2. **Daimi həll:** `docker run` əmrinizdə `-p 127.0.0.1:20128:20128` istifadə edərək açıq şəkildə IPv4 ünvanına bağlayın:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Bu, IPv4 ünvanına bağlanmanı məcburi edir və həmçinin proksinin hostun bütün interfeyslərində əlçatan olmasının qarşısını alır.

### Jurnal Fayllarını Aktivləşdirin

`.env` faylınızda `APP_LOG_TO_FILE=true` təyin edin. Tətbiq jurnalları `logs/` altında yazılır.
Çağırış jurnalı konveyeri parametrlərdə aktivləşdirildikdə sorğu artefaktları `${DATA_DIR}/call_logs/` altında saxlanılır.
Konveyer qeydəalması aktiv olduqda, axın hissələrinin faydalı yüklərini buraxmaq üçün `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` təyin edin və ya artefaktın KB ilə limitini dəyişmək üçün `CALL_LOG_PIPELINE_MAX_SIZE_KB` dəyərini tənzimləyin.

```bash
# Sağlamlıq idarəetmə paneli
http://localhost:20128/dashboard/health

# API sağlamlıq yoxlaması
curl http://localhost:20128/api/monitoring/health
```

### İcra Mühiti Yaddaşı

- Əsas vəziyyət: `${DATA_DIR}/storage.sqlite` (provayderlər, kombinasiyalar, aliaslar, açarlar, parametrlər)
- İstifadə: `storage.sqlite` daxilindəki SQLite cədvəlləri (`usage_history`, `call_logs`, `proxy_logs`) + istəyə bağlı `${DATA_DIR}/call_logs/`
- Tətbiq jurnalları: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` olduqda)
- Çağırış jurnalı artefaktları: çağırış jurnalı konveyeri aktiv olduqda `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Sorğu Jurnalları səhifəsindəki **Tarixçəni təmizlə** əməliyyatı `call_logs`, köhnə `request_detail_logs` və lokal `${DATA_DIR}/call_logs/` artefakt kataloqunu təmizləyir.

## Dayanıqlılıq Parametrləri

### Avtomatik sorğu tezliyi məhdudiyyətinin işə düşməməsi

- Avtomatik sorğu tezliyi məhdudiyyəti yalnız API açarı provayderlərinə tətbiq olunur (OAuth/abunəlik üçün deyil)
- **Settings → Resilience → Provider Profiles** bölməsində avtomatik sorğu tezliyi məhdudiyyətinin aktiv olduğunu yoxlayın
- Provayderin `429` status kodları və ya `Retry-After` başlıqları qaytarıb-qaytarmadığını yoxlayın

### Eksponensial gecikmənin tənzimlənməsi

Provayder profilləri bu parametrləri dəstəkləyir:

- **Baza gecikməsi** — İlk xətadan sonrakı ilkin gözləmə müddəti (standart: 1s)
- **Maksimum gecikmə** — Maksimum gözləmə müddəti həddi (standart: 30s)
- **Vuruq** — Hər ardıcıl xəta üçün gecikmənin nə qədər artırılacağı (standart: 2x)

### Kütləvi eyni vaxtlı sorğuların qarşısının alınması

Çoxsaylı paralel sorğular sorğu tezliyi məhdudlaşdırılmış provayderə göndərildikdə, OmniRoute sorğuları ardıcıl icra etmək və zəncirvari xətaların qarşısını almaq üçün mutex + avtomatik sorğu tezliyi məhdudiyyətindən istifadə edir. API açarı provayderləri üçün bu, avtomatik həyata keçirilir.

### Söhbət sorğuları 503 / chat_admission_busy xətası ilə uğursuz olur

**Əlamətlər:**

- Söhbət tamamlamaları son nöqtəsi xəta kodu
  `chat_admission_busy` olan, yenidən sınaqdan keçirilə bilən `503` cavabı qaytarır.
- Cavaba `Retry-After` daxildir. #12135 versiyasından etibarən dəyər müşahidə olunan
  doluluq əsasında hesablanır — sorğunun artıq gözlədiyi `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  pəncərəsi ilə cari ağır yük icarələrinin saxlanma müddətindən daha böyük olanı seçilir —
  tam saniyəyə yuxarı yuvarlaqlaşdırılır və 60 ilə məhdudlaşdırılır. Giriş mexanizmi boş olduqda
  tarixi minimumlar qorunur: bayt əsaslı yolda 2 saniyə, struktur əsaslı yolda isə 1 saniyə
  (bu yola həmçinin `reason: "structure_limit"` daxildir).
- Bu, başqa bir ağır yüklü söhbət və ya uzunmüddətli axın cavabı hələ icra olunarkən baş verə
  bilər.

Bayt əsaslı cavab gövdəsi:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Struktur əsaslı cavab eyni növ və koddan istifadə edir, lakin mesaj
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
və `reason: "structure_limit"` olur.
Standart hədlərdə sorğuda ən azı `200` mesaj, ən azı `64` alət və ya ən azı `32,000`
təxmini token olduqda, yaxud məhdudlaşdırılmış struktur qiymətləndirilməsi `10,000` ziyarət
edilmiş qovşaq və ya `12` dərinlik hədlərini tükətdikdə sorğu struktur baxımından ağır hesab olunur.

**Səbəb:** Bu, yuxarı axın provayderinin xətası deyil, OmniRoute daxilində məqsədli yükün
azaldılmasıdır. Hər proses böyük sorğu gövdəsini yaddaşda saxlamazdan və təhlil etməzdən əvvəl
məhdud ağır yük tutumunu rezerv etmək üçün prosesə lokal qoruyucudan istifadə edir. Ağır yük
icarəsi SSE cavabının bütün ömrü boyunca saxlanılır.

**#503-fanout:** bu düzəlişdən əvvəl qoruyucu, host yaddaşından asılı olmayaraq paralelliyi sabit
sorğu SAYI ilə (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, standart `1`) məhdudlaşdırırdı, buna görə
kodlaşdırma agentlərinin sorğuları şaxələndirməsi (çoxsaylı subagentlər/CLI-lər, adətən > 256 KB
olan gövdələr) faktiki paralelliyi təxminən 1-ə endirir və tamamilə normal yük altında 503 xətalarına
səbəb olurdu. Qoruyucu indi özünü avtomatik tənzimləyir: prosesin real yaddaş həddindən hesablanan
avtomatik müəyyənləşdirilmiş qəbul BAYT büdcəsi (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ilə idarə
olunur və həmçinin real vaxt resurs təzyiqi siqnalını nəzərə alır — beləliklə, sadəcə birdən çox
ağır sorğunun eyni vaxtda gəlməsinə görə deyil, yalnız host həqiqətən yaddaş təzyiqi altında
olduqda yükü azaldır. Köhnə say həddi (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) hələ də nəzərə
alınır, lakin yalnız onu açıq şəkildə təyin etdikdə.

Tutum dolu olduqda, ağır yük sorğusu yenidən sınaqdan keçirilə bilən `503` cavabını qaytarmazdan
əvvəl yerin boşalması üçün maksimum `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` müddəti qədər gözləyir
(standart dəyər `RATE_LIMIT_MAX_WAIT_MS`; `0` gözləməni deaktiv edir). Məhdud gözləmə ona görə
mövcuddur ki, ağır alt sorğuları paralel şəkildə şaxələndirən agent tipli müştərilər
(OpenCode, Claude Code, Cursor) dərhal rədd cavabları alaraq bütün təkrar sınaq büdcəsini
tükətmək və tapşırığın ortasında dayanmaq əvəzinə sorğu partlayışını ardıcıl icra etsinlər.
Cari ağır yük icarələrinin doluluğu, müəyyənləşdirilmiş bayt büdcəsi və real vaxt təzyiq
dərəcəsi `GET /api/monitoring/health` → `chatAdmission` bölməsində (`inflightBytes`,
`maxInflightBytes`, `budgetSource`, `pressureSeverity`, `countCapEnabled`) göstərilir — hər
hansı mühit dəyişənini dəyişməzdən əvvəl bunları yoxlayın.
Settings → Resilience → Request Queue → Concurrent Requests bunu idarə etmir; həmin parametr
ayrıca provayder sorğu növbəsi mexanizmini idarə edir.

**Həll:**

1. Əvvəlcə yenidən cəhd edin. Müştərilər sorğunu dərhal təkrarlamaq əvəzinə `Retry-After`
   başlığına əməl etməli və gecikmədən istifadə etməlidir.
2. Nəyisə tənzimləməzdən əvvəl `/api/monitoring/health` → `chatAdmission` bölməsini yoxlayın.
   `countCapEnabled: false` və böyük `maxInflightBytes` dəyəri avtomatik müəyyənləşdirilmiş
   büdcənin artıq düzgün işlədiyini göstərir; `high`/`critical` `pressureSeverity` dəyəri hostda
   həqiqətən yaddaş çatışmazlığı olduğunu göstərir — bunu qəbul mexanizminin mühit dəyişəni ilə
   düzəltmək mümkün deyil, daha çox RAM və ya daha kiçik iş yükü tələb olunur.
3. Yalnız `/api/monitoring/health` avtomatik müəyyənləşdirilmiş büdcənin hostunuz üçün həqiqətən
   çox kiçik olduğunu göstərirsə (bu nadir haldır — büdcə artıq konteynerdən fiziki serverə qədər
   miqyaslanır), köhnə sorğu sayı həddinə qayıtmaq əvəzinə onu birbaşa
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ilə əvəzləyin.

Rəsmi qəbul parametrləri üçün [mühit dəyişənləri arayışına](../reference/ENVIRONMENT.md#4-security--authentication)
baxın.

## İstəyə bağlı RAG / LLM xəta taksonomiyası (16 problem)

Bəzi OmniRoute istifadəçiləri şlüzü RAG və ya agent steklərinin önündə yerləşdirirlər. Belə konfiqurasiyalarda qəribə bir vəziyyətə tez-tez rast gəlinir: OmniRoute sağlam görünür (provayderlər işləyir, marşrutlaşdırma profilləri qaydasındadır, sürət məhdudiyyəti xəbərdarlıqları yoxdur), lakin yekun cavab yenə də səhv olur.

Təcrübədə bu insidentlər adətən şlüzün özündən deyil, sonrakı RAG konveyerindən qaynaqlanır.

Bu xətaları təsvir etmək üçün ortaq terminologiyadan istifadə etmək istəyirsinizsə, təkrarlanan on altı RAG / LLM xəta modelini müəyyənləşdirən, MIT lisenziyalı xarici mətn resursu olan WFGY ProblemMap-dən istifadə edə bilərsiniz. Ümumi səviyyədə bu resurs aşağıdakıları əhatə edir:

- axtarış sapması və pozulmuş kontekst sərhədləri
- boş və ya köhnəlmiş indekslər və vektor anbarları
- embeddinq və semantika uyğunsuzluğu
- promptun yığılması və kontekst pəncərəsi problemləri
- məntiqin çökməsi və həddindən artıq əminliklə verilən cavablar
- uzun zəncir və agent koordinasiyası xətaları
- çoxagentli yaddaş və rol sapması
- yerləşdirmə və ilkin işəsalma ardıcıllığı problemləri

İdeya sadədir:

1. Səhv cavabı araşdırarkən aşağıdakıları qeydə alın:
   - istifadəçi tapşırığı və sorğusu
   - OmniRoute daxilindəki marşrut və ya provayder kombinasiyası
   - sonrakı mərhələdə istifadə olunan hər hansı RAG konteksti (əldə edilmiş sənədlər, alət çağırışları və s.)
2. İnsidenti bir və ya iki WFGY ProblemMap nömrəsi (`No.1` … `No.16`) ilə uyğunlaşdırın.
3. Nömrəni öz idarə panelinizdə, əməliyyat təlimatınızda və ya insident izləmə sisteminizdə OmniRoute jurnallarının yanında saxlayın.
4. RAG stekinizi, axtarış komponentinizi və ya marşrutlaşdırma strategiyanızı dəyişdirməli olub-olmadığınızı müəyyənləşdirmək üçün müvafiq WFGY səhifəsindən istifadə edin.

Tam mətn və konkret reseptlər burada yerləşir (MIT lisenziyası, yalnız mətn):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute arxasında RAG və ya agent konveyerləri işlətmirsinizsə, bu bölməni nəzərə almaya bilərsiniz.

## v3.8.0 Məlum problemlər

v3.8.0 buraxılışına xas problemlər və onların cari müvəqqəti həlləri. Düzəliş sonrakı yamaq versiyasında təqdim olunarsa, müvafiq qeyd yenilənəcək və ya silinəcək.

### Devin CLI autentifikasiya xətaları

**Əlamətlər:**

- Devin əsaslı alətlər çağırılarkən "Devin CLI not found" və ya "auth failed" xətası
- CLI icra mühiti yoxlaması `installed=false` nəticəsini göstərir

**Səbəblər:**

- `CLI_DEVIN_BIN` mövcud olmayan yola işarə edir
- Devin CLI hostda quraşdırılmayıb

**Həll:**

1. Platformanız üçün Devin CLI-ni quraşdırın
2. `.env` faylında `CLI_DEVIN_BIN=/usr/local/bin/devin` (və ya faktiki yol) təyin edin
3. OmniRoute-u yenidən başladın və **Dashboard → CLI Tools** bölməsindən təkrar sınaqdan keçirin

### Modelin gözləmə müddəti ilişib qalır (əl ilə sıfırlama)

**Əlamətlər:**

- Bitmə vaxtı keçdikdən sonra belə model gözləmə rejimində göstərilməyə davam edir
- Vaxt möhürü keçmişdə olsa da, kombinasiya üzrə marşrutlaşdırma sorğuları modeli ötürməyə davam edir

**Əl ilə sıfırlama:**

- **İdarə paneli:** **Settings → Model Cooldowns** → təsirlənmiş kartda **Re-enable** düyməsinə klikləyin
- **API:** idarəetmə autentifikasiya başlıqları ilə `DELETE /api/resilience/model-cooldowns`

### Command Code provayderinə qoşulma 403 xətası ilə uğursuz olur

**Əlamətlər:**

- Command Code provayderi ilə əlaqə yoxlanılarkən 403 xətası
- Yeni əlavə edildikdən sonra provayder kartında "unauthorized" göstərilir

**Səbəb:** OAuth axını tamamlanmayıb (əks çağırış qəbul edilməyib və ya token saxlanılmayıb).

**Həll:**

- OAuth axınını yenidən başlatmaq üçün CLI-dan `omniroute providers` əmrini icra edin və ya
- OAuth prosesini **Dashboard → Providers → Command Code → Reconnect** bölməsindən yenidən başladın

### ModelScope aqressiv 429 gözləmə müddətləri qaytarır

**Əlamətlər:**

- Kiçik sorğu sıçrayışından sonra ModelScope-da çox qısa və ya dərhal başlayan gözləmə müddətləri
- Kombinasiya üzrə marşrutlaşdırma ModelScope-u gözləniləndən daha tez ötürür

**Səbəb:** ModelScope provayderə xas `Retry-After` başlıqları göndərir. v3.8.0 bu başlıqlar üçün xüsusi emal mexanizmi ilə təchiz olunur, buna görə də daha köhnə versiyalar onları ümumi sürət məhdudiyyəti göstərişləri kimi yanlış şərh edir.

**Həll:**

- v3.8.0 və ya daha yeni versiyadan istifadə etdiyinizə əmin olun
- **Settings → Resilience** bölməsində `useUpstream429BreakerHints` keçidinin aktiv olduğunu yoxlayın

### OMNIROUTE_WS_BRIDGE_SECRET istehsal mühitində yoxdur

**Əlamətlər:**

- Uzaq istehsal hostunda işləyərkən hər Codex/Responses WebSocket körpüsü sorğusunda 401 xətası
- WebSocket körpüsünün əl sıxışması bağlantı qurulduqdan dərhal sonra bağlanır

**Səbəb:** İstehsal mühitində `OMNIROUTE_WS_BRIDGE_SECRET` mühit dəyişəni yoxdur.

**Həll:**

1. Təsadüfi məxfi dəyər yaradın: `openssl rand -hex 32`
2. İstehsal serverinin mühitində (və körpü ilə əlaqə saxlayan bütün klientlərdə) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` təyin edin
3. OmniRoute-u yenidən başladın

### Responses API: fon rejimi sinxron rejimə endirilib

**Əlamətlər:**

- Jurnala xəbərdarlıq yazılır: `background mode degraded to synchronous`
- `background: true` sorğusu fon tapşırığı identifikatoru əvəzinə adi sinxron cavab qaytarır

**Səbəb:** v3.8.0 xəbərdarlıq göndərməklə yanaşı, Responses API-də `background: true` parametrini qəsdən sinxron icraya endirir. Tam asinxron fon icrası gələcəkdə təqdim ediləcək funksionallıqdır.

**Həll:**

- Klienti `background` parametri olmadan çağırış etməyə uyğunlaşdırın və ya
- Tam asinxron fon rejimini təqdim edən sonrakı buraxılışı gözləyin (dəyişiklik jurnalını izləyin)

## Yavaş Başlama / Hazırlıq Taym-autu

CLI `⚠ Server 60 saniyə ərzində cavab vermədi` mesajını göstərirsə, lakin server
əslində işləyirsə, hazırlıq yoxlaması üçün ayrılmış vaxt mühitiniz üçün çox qısadır.

Bu, adətən Windows-da (antivirus, fayl sistemi izləyiciləri) və ya işə salınma
zamanı ağır iş yükü olan konteynerlərdə baş verir.

**Həll — ayrılmış vaxtı artırın:**

```bash
# Mühit dəyişəni vasitəsilə (işə salmalar arasında qüvvədə qalır):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 dəqiqə
omniroute serve

# CLI bayrağı vasitəsilə (birdəfəlik):
omniroute serve --ready-timeout 180000
```

Standart dəyər 60 000 ms-dir (60 san). Xəbərdarlıq yalnız məlumat xarakterlidir; server
arxa planda işə düşməyə davam edir və yüklənmə tamamlandıqdan sonra əlçatan olacaq.

`OMNIROUTE_READY_TIMEOUT_MS` haqqında tam təfərrüatlar üçün
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) sənədinə baxın.
