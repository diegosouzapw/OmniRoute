`open-sse/config/providerPluginManifest.ts` JSON üçün təhlükəsiz provayder
plagini müqaviləsini müəyyən edir. `open-sse/config/providerPluginManifestRegistry.ts` həmin
müqaviləni Bifrost, CLIProxyAPI və ya gələcək Go/Rust marşrutlayıcısı kimi sidecar-lar üçün
cari provayder reyestri ilə əlaqələndirir. TypeScript reyestri əsas həqiqət mənbəyi olaraq
qalır, lakin sidecar-lar icraçı kodunu, OAuth standartlarını, başlıqları və ya proses mühiti
vəziyyətini idxal etmədən manifestdən istifadə edə bilər.

Eyni manifest prosesdən kənar işləyən sidecar-lar üçün HTTP üzərindən
`GET /api/v1/provider-plugin-manifest` ünvanında əlçatandır.

OmniRoute həmin URL-i `X-OmniRoute-Provider-Manifest-Url` sorğu başlığı vasitəsilə
Bifrost və CLIProxyAPI-yə bildirir. Sidecar yerli sorğu mənbəyi əvəzinə ictimai və ya
konteyner şəbəkəsi URL-inə ehtiyac duyduqda `OMNIROUTE_PROVIDER_MANIFEST_URL` təyin edin.

## Manifestin Yenilənməsi

HTTP son nöqtəsi `Cache-Control: public, max-age=60` və güclü bir
`ETag` qaytarır. Sidecar son təsdiqlənmiş manifesti saxlamalı və yeniləmə zamanı onun
ETag dəyərini `If-None-Match` daxilində göndərməlidir. `304 Not Modified` cavabının gövdəsi
olmur; sidecar keşlənmiş manifestini saxlayır. Təsdiqlənmiş keşlənmiş manifest mövcud
deyilsə, sidecar `304` cavabını qəbul etmək əvəzinə şərtsiz sorğu göndərməlidir.

## Məqsəd

Provayder metadatasını plagin müqaviləsinə doğru yönəltməkdir ki, nəticədə aşağı
gecikməli sidecar operativ sorğu yolunu idarə edə bilsin, OmniRoute isə TypeScript
marşrutunu siyasət qapısı və ehtiyat variant kimi saxlasın. Manifest əlavəlidir: o,
öz-özlüyündə sorğuların marşrutlaşdırılmasını dəyişmir.

## Müqavilə

Manifest aşağıdakıları ehtiva edir:

- provayder identifikatoru və ləqəbi
- yuxarı axın formatı və icraçı adı
- autentifikasiya növü, autentifikasiya başlığı və istəyə bağlı autentifikasiya prefiksi
- statik son nöqtə metadatası
- sidecar uyğunluğu və provayderin TS yolunda qalmalı olduğu hallarda bunun aydın səbəbləri
- kontekst uzunluğu, görüntü/düşünmə bayraqları və dəstəklənməyən parametrlər kimi JSON üçün təhlükəsiz model metadatası
- `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` və `usage-supported` daxil olmaqla imkan teqləri

Manifest aşağıdakıları məqsədli şəkildə istisna edir:

- OAuth müştəri məxfi məlumatları və standart məxfi dəyərlər
- icra zamanı mühitin müəyyənləşdirilməsi
- sorğu başlıqları və açıq etimadnamə köməkçiləri
- dinamik URL qurucuları
- icraçı funksiyaları
- sessiya hovuzunun daxili komponentləri

## İmkan Teqləri

`capabilities` reyestr qeydindən əldə edilən çeşidlənmiş teqlər massividir. İnteqratorlar
TypeScript mənbələrini yenidən oxumaq əvəzinə, bunu «bu provayder nə edə bilər» sualına
maşın tərəfindən oxuna bilən cavab kimi qəbul etməlidirlər.

| Teq                  | Mənası                                                                                          |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| `apikey`             | API açarını qəbul edir (`authType` dəyəri `apikey` və ya `optional` olur).                      |
| `oauth`              | OAuth və ya sessiya axınından istifadə edir.                                                    |
| `responses`          | OpenAI Responses-API baza URL-ini təqdim edir.                                                  |
| `passthrough-models` | Modelləri statik kataloq əvəzinə birbaşa yuxarı axından təqdim edir.                            |
| `custom-executor`    | Standart olmayan icraçını işlədir, buna görə TypeScript yolunda qalır.                          |
| `sidecar-candidate`  | `sidecar.eligible` dəyərini əks etdirir — sidecar-a idxal üçün nəzərdən keçirmək təhlükəsizdir. |
| `usage-fetch`        | Qoşulmuş istifadə və ya kvota əldəedicisinə (`getUsageForProvider`) malikdir.                   |
| `usage-supported`    | İstifadə API-si bu provayderi qəbul edir (`isSupportedUsageConnection`).                        |

`usage-fetch` yalnız aşkarlama üçündür. Bu, OmniRoute-un provayder üçün istifadə məlumatlarını
necə oxumağı bildiyini göstərir; məlumatların əldə edilməsini aktivləşdirmir, kvota semantikasını
dəyişmir və ya İdarəetmə panelindəki kvota vidcetinin provayder üçün aktiv olduğunu nəzərdə tutmur —
həmin vidcet ayrıca `USAGE_SUPPORTED_PROVIDERS` ilə idarə olunur. Əsas həqiqət mənbəyi
`open-sse/services/usage/fetcherProviders.ts` daxilindəki `USAGE_FETCHER_PROVIDERS`-dir.

Həmin siyahı istifadə dispetçerinin qəbul etdiyi sətirlərə əsasən açarlanır, buna görə də kanonik
identifikatorlarla ləqəbləri qarışdırır və teqlənmiş provayderlərin sayından bir qədər uzundur:
manifest reyestrində çat provayderi olmayan qeydlər (məsələn, `firecrawl` axtarış provayderi
və `amazon-q` ACP provayderi) teqlənəcək manifest qeydinə malik deyil.

`usage-supported` server və İdarəetmə panelinin istifadə marşrutlarının provayder üçün bağlantını
qəbul edib-etmədiyini göstərir. O, hər ikisi `USAGE_SUPPORTED_PROVIDERS`
(`open-sse/services/usage/supportedProviders.ts`) tərəfindən idarə olunan
`isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`) və
`supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`) funksiyalarını əks
etdirir. `usage-fetch`-dən fərqli olaraq, o, yalnız provayder identifikatorunda yaradılır — icra
zamanı qoruyucusu ləqəb həlli olmadan
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` çağırır, buna görə manifest də eyni qaydanı
saxlayır. İki teqin əhatə dairəsi fərqlidir: 3 provayder yalnız
`usage-fetch` (`opencode`, `opencode-zen`, `xai`), 1 provayder isə yalnız
`usage-supported` (`xiaomi-mimo-token-plan`) daşıyır, buna görə biri digərini nəzərdə tutmur.

## Sidecar İstifadəsi

Sidecar-lar `sidecar.eligible` göstəricisinə qeyd-şərtsiz marşrutlaşdırma qərarı kimi deyil,
konservativ namizəd siqnalı kimi yanaşmalıdır. İlk idxal hədəfi standart icra mexanizmindən
istifadə edən API açarlı, statik son nöqtəli provayderlər olmalıdır. Fərdi veb icra
mexanizmləri, OAuth/sessiya axınları, dinamik URL qurucuları və ya hovuz konfiqurasiyası
olan provayderlər sidecar ekvivalent davranışı həyata keçirənədək və telemetriya uyğunluğu
təsdiqləyənədək TypeScript ehtiyat yolunda qalmalıdır.

Tövsiyə olunan miqrasiya mərhələləri:

1. TS reyestrindən provayder plagin manifestini yaradın və doğrulayın.
2. Bifrost və ya CLIProxyAPI-yə API açarlı/statik provayderlər üçün manifesti idxal etməyi
   öyrədin.
3. TS ehtiyat yolunu aktiv saxlayaraq uyğun provayderləri `OMNIROUTE_RELAY_BACKEND`
   arxasındakı sidecar vasitəsilə marşrutlaşdırın.
4. Provayderləri yalnız uğur faizi, p99 gecikməsi, axın davranışı və dəstəklənməyən
   parametrlərin emalı TS yolu ilə uyğun gəldikdə irəli çəkin.
5. Fərdi icra mexanizmləri üçün sidecar-a məxsus plaginləri hər dəfə bir provayder ailəsi
   üzrə əlavə edin.

## Niyə Provayderləri Birbaşa Next-ə Yerləşdirməməli

Next ön tərəfi provayder icrasına cavabdeh olmamalıdır. O, API sərhədini çağırmalıdır.
Bundan sonra backend TypeScript icra mexanizmindən, Bifrost-dan, CLIProxyAPI-dən və ya
gələcək yerli sidecar-dan istifadə edib-etməməyə qərar verə bilər. Bu yanaşma sorğuların
imzalanmasını, icazə siyahısı yoxlamalarını, DB siyasətini və ehtiyat davranışını hər hansı
sidecar-a ötürmədən əvvəl mərkəzləşdirilmiş şəkildə saxlayır.
