> **Nota de âmbito:** `socket.yml` configura a análise pós-publicação, no lado do registo, efetuada pelo Socket.dev ao artefacto npm (caminhos ignorados para conteúdo não distribuído, como `tests/`, `docs/` e relatórios de compilação). Não configura qualquer bloqueio de integração de CI/PR — nenhum fluxo de trabalho em `.github/workflows`, nenhum script de `package.json` e nenhum alvo de `Makefile` invoca o Socket.dev.

Este documento constitui a declaração, redigida pelos responsáveis pela manutenção, relativa às seis
deteções de `potencial malware detetado por IA` assinaladas em `omniroute@3.8.5` e
às medidas de mitigação aplicadas em `omniroute@3.8.6`. Existe para que:

1. Os operadores do pipeline de segurança tenham uma referência única que possam citar quando precisarem
   de avaliar as deteções face ao código-fonte efetivo.
2. Os futuros analisadores de IA possam identificar a declaração assinada pelos responsáveis pela manutenção de que cada
   caminho assinalado é intencional, opcional e está documentado.
3. Tenhamos um registo escrito do _motivo_ pelo qual cada local de chamada está estruturado dessa forma —
   para que uma futura refatoração não volte a introduzir acidentalmente uma assinatura que
   foi deliberadamente removida.

Se utiliza um analisador que volte a assinalar qualquer um dos locais de chamada abaixo após a
disponibilização das medidas de mitigação da v3.8.6, abra um problema com o rastreio da análise e
alargaremos esta declaração aqui.

## §1 — Instalação da AC raiz para MITM (`77484.js`)

**Ficheiros de código-fonte**:

- `src/mitm/cert/install.ts` — funções públicas `installCert()` / `uninstallCert()`,
  e `installCertWindows/Mac/Linux` específicas de cada plataforma.
- `src/mitm/systemCommands.ts` — funções auxiliares partilhadas de `execFile` / `spawn` / PowerShell,
  utilizadas pelos caminhos de instalação.

**Acionamento**: o utilizador clica em "Ativar proxy MITM" no painel local em
`/dashboard/cli-tools/mitm`. A rota está limitada à interface de loopback — consulte a regra rígida n.º 17 em
`CLAUDE.md` e `src/server/authz/routeGuard.ts::isLocalOnlyPath()`. Um JWT exposto
através de um túnel **não pode** acionar este caminho de código.

**Operações privilegiadas executadas (por plataforma)**:

| SO                     | Comando(s)                                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | `certutil -addstore Root <cert>` através do UAC                                                                   |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | atualização da base de dados NSS de cada perfil através de `certutil -d sql:<profile>`                            |

Estes são os mesmos comandos utilizados pelo `mitmproxy`, Charles Proxy, Fiddler e
Caddy. A sua existência no OmniRoute está documentada em
`docs/security/STEALTH_GUIDE.md`.

**Mitigação na v3.8.6**:

- `runElevatedPowerShell()` deixou de utilizar `-EncodedCommand <base64utf16le>`.
  O payload elevado é escrito num ficheiro `.ps1` temporário por chamada (modo 0o600,
  dentro de um diretório `mkdtempSync` privado) e referenciado através de `-File`. O
  ficheiro é removido em `finally`. Isto elimina a assinatura clássica de
  elevação através de PowerShell com base64 assinalada pelo classificador de IA do
  Socket.dev.
- `installCertWindows` inclui um bloco `SECURITY-AUDITOR-NOTE:` inline
  que remete para este documento.

**Motivo para o mantermos**: o proxy MITM é uma funcionalidade documentada, utilizada por
`docs/security/STEALTH_GUIDE.md` e `docs/frameworks/MITM-PROXY.md`. A sua remoção
quebraria o conjunto de funcionalidades da ponte de agentes.

## §2 — Importação de credenciais do Zed (`app/api/providers/zed/import/route.js`)

**Ficheiros de origem**:

- `src/app/api/providers/zed/discover/route.ts` _(novo na v3.8.6)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(novo na v3.8.6)_

**Acionador**: o utilizador clica em "Importar do Zed" na página de Fornecedores
do painel de controlo local. O acesso ao endpoint é controlado por
`requireManagementAuth`. O próprio editor Zed guarda as chaves de API dos
fornecedores no porta-chaves do sistema operativo, sob nomes de serviço
documentados — consulte https://zed.dev/docs/ai/llm-providers.

**Comportamento da v3.8.5 (o que foi sinalizado pelo Socket.dev)**:

`POST /import` descobria as credenciais e guardava-as automaticamente no
armazenamento SQLite local numa única operação. Sem confirmação por conta,
sem impressão digital, apenas "foram encontrados N tokens, todos importados".

**Mitigação da v3.8.6 — confirmação em 2 passos**:

1. **`POST /api/providers/zed/discover`** devolve
   `{ candidates: [{ provider, service, account, fingerprint }] }`. O token em
   bruto **nunca** é transmitido. A impressão digital é
   `sha256(service|account|token).slice(0,16)`.
2. O painel de controlo apresenta a lista de candidatos, o operador seleciona
   quais pretende importar e envia
   `{ confirmedAccounts: [{ service, account, fingerprint }] }`
   para **`POST /api/providers/zed/import`**.
3. O endpoint de importação **volta a ler o porta-chaves no servidor** e filtra
   por `(service, account, fingerprint)`. Uma resposta de descoberta adulterada
   ou reutilizada não consegue levar o endpoint de importação a guardar um token
   não relacionado — se o token ativo tiver sido alterado desde a descoberta, a
   impressão digital deixa de corresponder e a credencial é ignorada.

Uma variável de ambiente `OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` preserva o
comportamento da v3.8.5 para os operadores que ainda não atualizaram a sua
automatização. Será removida na v3.9.

**Porque o mantemos**: a importação do Zed é o método de integração inicial mais
simples para os utilizadores que já utilizam o Zed e pretendem replicar as suas
chaves de fornecedor no OmniRoute sem terem de as colar novamente.

## §3 — `execFile` / `spawn` / PowerShell elevado (`21843.js`)

**Ficheiros de origem**: `src/mitm/systemCommands.ts`.

**Porque foi sinalizado**: o chunk volta a exportar `execFileWithPassword`,
`runElevatedPowerShell` e o auxiliar partilhado `quotePowerShell`. O
classificador de IA do Socket.dev interpreta-os como um "conjunto de
ferramentas genérico para execução no anfitrião + elevação de privilégios".
No OmniRoute, são utilizados apenas pelo fluxo de instalação do certificado
MITM (§1) e por `execFileWithPassword` para a execução de comandos `sudo`.

**Mitigação da v3.8.6**:

- Refatoração de `runElevatedPowerShell` (consulte §1).
- Um bloco `SECURITY-AUDITOR-NOTE:` inline em `runElevatedPowerShell` e
  `execFileWithPassword` documenta os chamadores permitidos e a lista fixa
  de executáveis.
- A chamada `spawn()` de `execFileWithPassword` inclui um marcador `nosemgrep`
  com a lista de executáveis que o auxiliar pode receber — **não existe
  qualquer caminho entre a entrada do utilizador e `finalCommand`/`finalArgs`**.

## §4 / §6 — Supervisor do serviço 9router (`api/services/9router/{start,restart}/route.js`)

**Ficheiros de origem**:

- `src/app/api/services/9router/_lib.ts` — fábrica do supervisor.
- `src/app/api/services/9router/{start,stop,restart,status,install,update,auto-start}/route.ts`.
- `src/lib/services/ServiceSupervisor.ts` — mecanismo genérico de criação de processos / consulta periódica do estado de funcionamento / memória intermédia de registos.

**Acionador**: o utilizador clica em "Instalar" / "Iniciar" na página de serviços
incorporada no painel de controlo local.

**Proteções já existentes**:

- Todas as rotas `/api/services/*` são LOCAL_ONLY, de acordo com
  `src/server/authz/routeGuard.ts` (regra rígida n.º 17). A restrição ao
  endereço de loopback ocorre antes de qualquer verificação de autenticação —
  um JWT comprometido não consegue aceder-lhes.
- A linha do 9router na base de dados é criada com
  `status='not_installed', auto_start=0` (consulte
  `src/lib/db/migrations/071_services.sql:19`). O serviço **não** é iniciado
  na primeira execução.
- `spawn()` é chamado com o caminho do binário devolvido por
  `resolveSpawnArgs(apiKey, PORT)` em `src/lib/services/installers/ninerouter.ts`,
  que utiliza uma lista fixa de binários suportados.
- stdout/stderr é mantido numa memória intermédia (limite de 5 MB, consulte
  `_lib.ts`) — não existe qualquer escrita no disco, a menos que o utilizador
  ative os registos no painel de controlo.

**Mitigação da v3.8.6**: nenhuma alteração funcional. O perfil de compilação
mínimo (`OMNIROUTE_BUILD_PROFILE=minimal`) substitui
`src/lib/services/installers/ninerouter.ts` por um stub para os utilizadores
que pretendam remover fisicamente do bundle os caminhos privilegiados.

**Porque o mantemos**: o 9router é um serviço complementar opcional, instalável
localmente (semelhante a um plugin do WordPress) — adesão estritamente
voluntária.

## §5 — Reescrita de credenciais do OmniRoute Cloud Sync (`api/keys/[id]/route.js`)

**Ficheiros de origem**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`.
- `src/app/api/keys/[id]/route.ts` — invoca `syncKeysToCloudIfEnabled()`.

**Acionador**: `isCloudEnabled()` devolve `true` (definido a partir do painel) **e**
`CLOUD_URL` está configurado. Com ambos desativados, não é efetuada nenhuma
chamada de rede externa para o endpoint da Cloud.

**Comportamento da v3.8.5 (o erro que o Socket.dev detetou corretamente)**:

`updateLocalTokens()` substituía `accessToken`, `refreshToken` e
`providerSpecificData` pelos valores da resposta da Cloud quando
`cloudUpdatedAt > localUpdatedAt`. Sem HMAC, sem assinatura, sem soma de verificação.
Um `CLOUD_URL` mal configurado ou hostil (ou um ataque MITM no canal) podia
trocar silenciosamente os tokens OAuth do fornecedor.

**Mitigação na v3.8.6**:

1. **Verificação HMAC**: `verifyCloudSignature(rawBody, sigHeader)` verifica
   o cabeçalho `X-Cloud-Sig` (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`) antes de analisar o JSON. Se o segredo estiver definido, a
   assinatura é obrigatória. Caso contrário (modo legado), é registado um
   aviso e a resposta é aceite — o segredo será obrigatório na v3.9.
2. **Adesão explícita para campos secretos**: `accessToken` / `refreshToken` /
   `providerSpecificData` são substituídos **apenas** quando
   `OMNIROUTE_CLOUD_SYNC_SECRETS=true`. O modo predefinido sincroniza apenas
   metadados que não sejam credenciais (`expiresAt`, `status`, `lastError*`,
   `rateLimitedUntil`, `updatedAt`). Esta é uma **alteração incompatível** para os
   utilizadores que dependiam da sincronização remota de tokens — têm de aderir
   explicitamente.

**Por que motivo o mantemos**: o Cloud Sync é a única forma de um inquilino do
OmniRoute Cloud centralizar as credenciais da equipa. A correção torna o modelo
de ameaças explícito: "o servidor assina, o cliente verifica e o operador adere."

## Perfil de compilação: `minimal`

Para os utilizadores que necessitem de um artefacto compatível com o Socket,
compile com:

```bash
OMNIROUTE_BUILD_PROFILE=minimal npm run build
```

O `NormalModuleReplacementPlugin` do webpack associa quatro módulos a stubs:

| Módulo                                      | Stub                                             |
| ------------------------------------------- | ------------------------------------------------ |
| `src/mitm/cert/install.ts`                  | `src/mitm/cert/install.stub.ts`                  |
| `src/lib/zed-oauth/keychain-reader.ts`      | `src/lib/zed-oauth/keychain-reader.stub.ts`      |
| `src/lib/cloudSync.ts`                      | `src/lib/cloudSync.stub.ts`                      |
| `src/lib/services/installers/ninerouter.ts` | `src/lib/services/installers/ninerouter.stub.ts` |

Cada stub exporta a mesma interface, mas todas as funções lançam um
`featureDisabledError(name)` em tempo de execução. As rotas que dependem do
módulo desativado devolvem HTTP 503 com uma mensagem clara, em vez de ativarem
o caminho de código sensível.

O bundle resultante destina-se a ser publicado como `omniroute-secure`. Consulte
`docs/ops/PUBLISHING_SECURE.md` para obter as instruções de publicação.
