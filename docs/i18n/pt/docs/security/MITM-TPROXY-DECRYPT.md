A desencriptação transparente TPROXY é o **5.º modo de captura** do OmniRoute para a pilha MITM do
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md).
Interceta e **desencripta** tráfego HTTPS local de saída no Linux
utilizando TPROXY do kernel + encaminhamento baseado em políticas — **sem** falsificar `/etc/hosts` e
**sem** alterar as definições de proxy de todo o sistema operativo. É adequado para ambientes sem interface gráfica
(não existem alterações de DNS para reverter) e as regras da firewall são automaticamente eliminadas ao reiniciar.

Ao contrário dos outros modos de captura, o TPROXY não necessita de configuração por anfitrião: interceta de forma transparente
**quaisquer** anfitriões de destino numa porta-alvo, termina o TLS com
um certificado final emitido dinamicamente para cada nome de anfitrião SNI, captura a troca
desencriptada e volta a encriptar o pedido para o destino original.

> **Apenas Linux, apenas root, ativação explícita.** Este modo requer Linux, um addon nativo
> compilado com uma cadeia de ferramentas C e a capacidade **CAP_NET_ADMIN** (normalmente root). Está protegido
> pela API AgentBridge limitada ao loopback e desativado por predefinição. Uma AC MITM fidedigna
> capaz de assinar qualquer anfitrião é uma funcionalidade poderosa — consulte [§6 Segurança](#6-security).

**Origem:** `src/mitm/tproxy/`
**Rota da API:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**Comutador do painel:** Traffic Inspector → barra de ferramentas dos modos de captura → **"Desencriptação TPROXY"** ⚠
**Consulte também:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 O que é e quando utilizá-lo

Cada um dos outros quatro modos de captura tem uma limitação:

| Modo                      | Como o tráfego é encaminhado                                            | Limitação                                                 |
| ------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------- |
| AgentBridge               | Falsificação de DNS em `/etc/hosts` para um conjunto fixo de anfitriões | apenas os anfitriões de agentes de IDE registados         |
| Anfitriões personalizados | Falsificação de DNS em `/etc/hosts` por anfitrião                       | uma entrada por anfitrião; sudo para editar os anfitriões |
| HTTP_PROXY                | Variáveis de ambiente `HTTP_PROXY`/`HTTPS_PROXY`                        | apenas aplicações que respeitem a variável de ambiente    |
| Proxy de todo o sistema   | Definições de proxy do SO                                               | altera o estado global; requer reversão                   |

Em alternativa, a desencriptação transparente TPROXY encaminha o tráfego ao nível do **kernel**.
Marca novas ligações TCP locais de saída para uma porta-alvo (por predefinição, `443`) na
cadeia `mangle OUTPUT`; uma `ip rule` reencaminha os pacotes marcados para entrega local
e, ao reentrarem, o destino `TPROXY` de `mangle PREROUTING` entrega-os a um
listener **IP_TRANSPARENT** — que termina o TLS e captura o texto simples.

Utilize-o quando pretender capturar e desencriptar tráfego de um processo que:

- comunica com um anfitrião que o AgentBridge não regista, e
- não respeita `HTTP_PROXY`, e
- não pretende perturbar através de uma alteração ao proxy de todo o sistema.

Como a interceção ocorre no kernel, o processo de origem **não necessita de qualquer
alteração de configuração** — mas tem de confiar na AC dinâmica que o OmniRoute
instala (consulte [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 Requisitos

| Requisito             | Detalhe                                                                                                                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **SO**                | Apenas Linux — **IP_TRANSPARENT** é uma opção de socket exclusiva do Linux. O carregador devolve "indisponível" em todas as outras plataformas.                                 |
| **Privilégio**        | A capacidade **CAP_NET_ADMIN** para criar o socket transparente e aplicar regras `iptables`/`ip` — na prática, executar como root.                                              |
| **Addon nativo**      | É necessário compilar um pequeno addon N-API (`src/mitm/tproxy/native/transparent.c`) ou fornecê-lo como uma pré-compilação. Consulte [§3](#3-the-native-ip_transparent-addon). |
| **Módulos do kernel** | `iptables` com suporte para correspondência `TPROXY`, `mangle` e `mark` (validado com o kernel 6.8.0).                                                                          |

**Degradação elegante:** se algum requisito estiver em falta (sistema que não seja
Linux, ausência da cadeia de ferramentas, addon não compilado), o carregador do
addon (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`) devolve
`null` em vez de lançar uma exceção. O estado do modo de captura indica então
`available: false`, o seletor no painel fica **desativado** com a descrição
"TPROXY decrypt requer Linux + root + o addon nativo", e o restante do
OmniRoute continua a funcionar.

## §3 O addon nativo IP_TRANSPARENT

O módulo `net` do Node não consegue executar `setsockopt(IP_TRANSPARENT)` _antes_
de `bind()`, o que é exigido pelo TPROXY (caso contrário, o kernel descarta os
pacotes redirecionados). O addon (`src/mitm/tproxy/native/transparent.c`,
compilado através de `binding.gyp`) é um pequeno módulo N-API que expõe três
funções, utilizadas através de `transparentSocket.ts`:

| Função do addon                       | Operações no socket                                                                            | Utilização                                                                                |
| ------------------------------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, devolve o fd bruto | o listener de captura transparente (o Node adota o fd através de `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | `setsockopt` **SO_MARK** num fd existente                                                      | prevenção de ciclos (marca os sockets do próprio proxy)                                   |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **antes** de um `connect()` não bloqueante, devolve o fd              | o reencaminhamento re-encriptado para o servidor upstream (o SYN transporta a marca)      |

O destino original é lido a partir de `socket.localAddress`/`localPort` — o TPROXY
preserva-o, pelo que não é necessária qualquer consulta **SO_ORIGINAL_DST**/NAT.

### Compilar o addon

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- Durante `npm run build`, `scripts/build/build-tproxy-native.mjs` executa
  `node-gyp rebuild`. É **exclusivo do Linux e não fatal** — a ausência da cadeia
  de ferramentas apenas deixa o modo de captura indisponível.
- `assembleStandalone.mjs` copia `build/Release/transparent.node` para o pacote
  autónomo; `transparentSocket.ts` resolve-o tanto relativamente ao módulo como
  relativamente ao cwd (`<cwd>/src/mitm/tproxy/native/...`).
- `build/` e `prebuilds/` são ignorados pelo git — o binário é **compilado, nunca
  submetido ao repositório**.

O carregador verifica, por ordem de prioridade:
`native/build/Release/transparent.node` e, em seguida,
`native/prebuilds/transparent.node` (ambos relativamente ao módulo e em
`<cwd>/src/mitm/tproxy/`).

## §4 A CA dinâmica por SNI e o instalador do repositório de confiança

> **Atualização #6684:** o servidor estático do AgentBridge (`src/mitm/server.cjs`) passa agora
> a partilhar este mesmo padrão de arquitetura de CA/certificado de entidade final, em vez de um único certificado
> de entidade final autoassinado estático. Utiliza uma instância de CA **distinta**
> (`src/mitm/cert/rootCa.ts`, persistida em `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> e instala-a na entrada preexistente `omniroute-mitm.crt` do repositório de confiança
> (substituindo aí o antigo certificado de entidade final único — não é necessária qualquer limpeza de confiança dupla),
> mantendo-a totalmente separada da entrada `omniroute-tproxy-ca.crt` do próprio TPROXY, abaixo.
> As novas instalações do AgentBridge obtêm automaticamente o modelo de CA; uma instalação que
> já confiava no antigo certificado de entidade final estático continua a utilizá-lo até que o operador adira
> através de `MITM_ROOT_CA_ENABLED=true` (consulte `src/mitm/cert/migration.ts`) — uma
> CA MITM de confiança que pode assinar um certificado de entidade final para **qualquer** anfitrião é substancialmente mais
> poderosa do que o antigo certificado de entidade final com SAN fixo, pelo que a mudança nunca ocorre silenciosamente numa
> instalação que já confia nesse certificado.

Historicamente, o certificado MITM estático do AgentBridge só funcionava porque o AgentBridge
falsifica o DNS de um conjunto **fixo** de anfitriões (agora unificado com o modelo abaixo). O TPROXY
interceta anfitriões **arbitrários**, pelo que o respetivo listener tem de apresentar um certificado de entidade final válido para
qualquer SNI pedido pelo cliente — o mesmo requisito que o AgentBridge tem agora
para o conjunto completo `MITM_TOOL_HOSTS` (9 entradas de ferramentas), em vez de apenas os 4
anfitriões antigravity.

### CA dinâmica (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` executa uma CA local (baseada na dependência `selfsigned`) que:

- Gera uma CA de longa duração através de `generateMitmCa()` (CN `"OmniRoute MITM CA"`,
  validade de 10 anos, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  RSA de 2048 bits/SHA-256).
- Emite, **a pedido, um certificado de entidade final por nome de anfitrião SNI** através de `issueLeafCert()` (validade de 1 ano,
  `subjectAltName` = o anfitrião SNI) e mantém em cache um `tls.SecureContext`
  por nome de anfitrião.
- Expõe `createSNICallback()` para o servidor que termina a ligação TLS (consulte [§5](#5-how-decrypt-and-capture-work)).
- Pode ser construído com uma `existingCa` para manter a CA estável entre reinícios
  (para que não seja necessário reinstalar o repositório de confiança).

A chave privada da CA **nunca sai da máquina**.

### Instalador do repositório de confiança (`src/mitm/tproxy/caTrust.ts`)

O cliente intercetado tem de confiar na CA dinâmica, pelo que iniciar o modo de captura
instala o certificado da CA no repositório de confiança do SO, numa **entrada dedicada** —
`omniroute-tproxy-ca.crt` (constante `TPROXY_CA_CERT_NAME`) — mantida separada da
entrada do certificado MITM estático (`omniroute-mitm.crt`), para que nunca se substituam
mutuamente.

`installTproxyCa(caPem, sudoPassword?)` deteta o diretório de âncoras da distribuição
(por ordem: primeiro, o estilo Debian) e executa o comando de atualização correspondente:

| Diretório de âncoras                        | Comando de atualização   |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

A instalação coloca temporariamente o PEM num ficheiro temporário e, em seguida, executa (com privilégios) `mkdir -p` no
diretório de âncoras, usa `cp` para copiar o ficheiro temporário para esse diretório e executa o comando de atualização. `uninstallTproxyCa()`
remove apenas a entrada dedicada (deixando intacto o certificado MITM estático) e
atualiza o repositório — em sistemas que não sejam Linux, não efetua qualquer operação.

Todos os comandos privilegiados são executados através de `execFileWithPassword` (`src/mitm/systemCommands.ts`)
— `spawn` com **matrizes de argumentos, sem shell e sem interpolação de strings** (Regra Rígida #13).
Quando o processo é executado como root (por exemplo, no VPS), o comando de destino é executado diretamente e não é necessária
qualquer palavra-passe; num ambiente de trabalho sem root, a `sudoPassword` é transmitida através de `sudo -S` pela entrada padrão.

> A `sudoPassword` do ambiente de trabalho é fornecida no corpo do pedido POST para autorizar a
> instalação no repositório de confiança; é totalmente ignorada quando o processo é executado como root.

## §5 Como funcionam a desencriptação e a captura

O pipeline (tudo em `src/mitm/tproxy/`):

```
aplicação local  ──TCP/443──▶  mangle OUTPUT marca a ligação (fwmark)
                                ip rule → tabela de encaminhamento local → lo
                                mangle PREROUTING TPROXY → listener IP_TRANSPARENT (porta 8443)
                                    │  captureMode.ts: lê o destino original de socket.localAddress
                                    ▼
                                tlsCapture.ts:
                                  1. termina o TLS do CLIENTE com um certificado final por SNI (dynamicCert)
                                  2. o http.Server interno analisa o texto simples desencriptado
                                  3. captura → globalTrafficBuffer.push() com source: "tproxy"
                                     (sanitizeHeaders + maskSecret aplicados)
                                  4. reencaminha, novamente encriptado, para o destino original
                                     através de um socket com marca de bypass (connectMarked, antirrecursão)
                                    │
                                    ▼
                                upstream original (api.example.com)
```

- **Terminação TLS** (`createTlsCaptureServer`): envolve o socket bruto intercetado
  num `tls.TLSSocket` do lado do servidor, utilizando o callback SNI da CA dinâmica,
  e depois entrega o fluxo desencriptado a um `http.Server` interno (a técnica
  padrão de terminação MITM). Os tempos de vida dos sockets são limitados por
  `MITM_IDLE_TIMEOUT_MS`, para que um túnel bloqueado não possa esgotar os
  descritores de ficheiros.
- **Captura** (`handleDecryptedRequest`): adiciona um `InterceptedRequest` com
  `source: "tproxy"`, estado inicial `"in-flight"`, cabeçalhos processados por
  `sanitizeHeaders()` e corpos processados por `maskSecret()` antes de entrarem
  no buffer. A entrada é depois atualizada com a resposta, os tamanhos e a
  latência.
- **Reencaminhamento novamente encriptado** (`createForward` / `realForward`):
  volta a encriptar os dados para o destino original. `rejectUnauthorized` tem
  **`true`** como valor predefinido (seguro por predefinição) — o certificado
  upstream é verificado em relação ao SNI/Host pedido pelo cliente, pelo que o
  proxy rejeita exatamente aquilo que o cliente original rejeitaria.

### Antirrecursão (SO_MARK)

Como as regras marcam novas ligações locais de saída, o reencaminhamento
novamente encriptado do **próprio** proxy seria normalmente intercetado de novo
— criando um ciclo infinito. O caminho de reencaminhamento protege-se contra
isto com uma marca de bypass no socket (**SO_MARK**):

- `realForward` abre o seu socket upstream através de
  `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` — `DEFAULT_BYPASS_MARK = 0x539`
  — que define **SO_MARK** **antes** de `connect()`, para que o SYN do
  reencaminhamento transporte a marca de bypass.
- A regra `mangle OUTPUT` exclui ligações que já transportem a marca de bypass
  (`-m mark ! --mark <bypassMark>`), pelo que o reencaminhamento do proxy **não**
  volta a ser marcado e não reentra no TPROXY.

> Nota de implementação: o socket com a marca de bypass tem de ser instalado no
> `createConnection` do agente (`https.request({ createConnection })` é
> silenciosamente ignorado quando existe um agente), caso contrário o
> reencaminhamento abriria um socket sem marca e o ciclo regressaria. Esta foi a
> correção antirrecursão validada de ponta a ponta.

## §6 Segurança

| Controlo                                  | Detalhe                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API apenas de loopback**                | `/api/tools/agent-bridge/tproxy` está abrangido pelo prefixo `/api/tools/agent-bridge/` em `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`). A restrição a loopback é aplicada **antes** da autenticação (Regras Rígidas n.º 15 + n.º 17) — um JWT divulgado através de um túnel não pode iniciar a captura TPROXY, que aplica regras `iptables` e instala uma AC no repositório de confiança através de processos-filho. |
| **Espaço dedicado para a AC**             | A AC dinâmica é instalada em `omniroute-tproxy-ca.crt`, sem nunca substituir o certificado MITM estático.                                                                                                                                                                                                                                                                                                                             |
| **A chave da AC nunca sai do anfitrião**  | `DynamicCertStore` mantém a chave da AC em memória; esta não é exportada.                                                                                                                                                                                                                                                                                                                                                             |
| **Ocultação de segredos**                 | `maskSecret()` nos corpos dos pedidos/respostas e `sanitizeHeaders()` nos cabeçalhos são executados **antes** de `globalTrafficBuffer.push()`.                                                                                                                                                                                                                                                                                        |
| **Sem interpolação na shell**             | Todos os comandos `iptables`/`ip`/do repositório de confiança são executados através de `execFile`/`execFileWithPassword` com matrizes de argumentos (Regra Rígida n.º 13).                                                                                                                                                                                                                                                           |
| **Verificação do certificado a montante** | O reencaminhamento novamente encriptado verifica, por predefinição, o certificado a montante (`rejectUnauthorized: true`).                                                                                                                                                                                                                                                                                                            |
| **Saneamento de erros**                   | As respostas de erro da rota passam por `sanitizeErrorMessage()` (Regra Rígida n.º 12).                                                                                                                                                                                                                                                                                                                                               |

**A AC MITM é uma capacidade poderosa.** Uma AC considerada fidedigna pelo sistema operativo e capaz de assinar para qualquer
anfitrião significa que tudo o que o OmniRoute intercetar pode ser desencriptado. Esta capacidade está protegida pelo
modo explícito de captura TPROXY apenas local, desativado por predefinição, e a entrada
no repositório de confiança é removida quando o modo é interrompido.

## §7 Aplicação / reversão transacional da firewall

Uma falha nunca deve deixar para trás uma regra `mangle` ou uma rota obsoleta. O construtor de comandos
(`src/mitm/tproxy/commands.ts`) e o executor (`src/mitm/tproxy/setup.ts`) garantem que
**a reversão é exatamente o inverso da aplicação, pela ordem inversa**.

`applyTproxy(cfg)` executa os comandos de aplicação por ordem; perante **qualquer** falha, executa uma
reversão completa, segundo o princípio de melhor esforço, através de `revertTproxy(cfg)` e volta a lançar o erro — assim, a firewall fica
totalmente configurada ou totalmente revertida, nunca parcialmente configurada. `revertTproxy(cfg)` executa os
comandos inversos pela ordem inversa e ignora as falhas (é idempotente — pode ser chamada
incondicionalmente, por exemplo, a partir da limpeza `repairMitm()` do AgentBridge).

`validateTproxyConfig(cfg)` é executada antes de qualquer comando: as portas devem estar entre `1–65535`,
`mark`/`routeTable`/`bypassMark` devem ser números inteiros positivos e `bypassMark` deve
ser diferente de `mark` (antibucle).

### Comandos de aplicação (por ordem)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

A reversão elimina-os pela ordem inversa: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> A configuração baseia-se em **OUTPUT**, porque o caso de utilização MITM é tráfego de saída
> _local_ (aplicações no mesmo anfitrião), que o TPROXY apenas em `PREROUTING` não
> vê — `PREROUTING` apenas vê tráfego reencaminhado. A cadeia `OUTPUT` marca novas
> ligações locais, a `ip rule` reencaminha-as para entrega local (`lo`) e
> `PREROUTING` atribui-as então ao listener transparente.

## §8 Configuração

O pedido de inicialização (`POST /api/tools/agent-bridge/tproxy`) aceita os seguintes
campos, validados por `StartTproxyBodySchema` (`tproxy/route.ts`). Todos são opcionais
e, quando omitidos, são usados os respetivos valores predefinidos:

| Campo            | Tipo               | Predefinição | Notas                                                                                                                            |
| ---------------- | ------------------ | ------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`        | Porta TCP de destino a intercetar de forma transparente                                                                          |
| **mark**         | int (≥1)           | `0x2333`     | Marca da firewall definida em `OUTPUT`, correspondida pela `ip rule` + `PREROUTING`                                              |
| **onPort**       | int (1–65535)      | `8443`       | Porta à qual o listener transparente (**IP_TRANSPARENT**) se associa                                                             |
| **routeTable**   | int (≥1)           | `233`        | ID da tabela de encaminhamento baseado em políticas que contém a rota `local 0.0.0.0/0`                                          |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`      | Marca de socket de desvio (**SO_MARK**) que o proxy define nas suas próprias ligações upstream; excluída em `OUTPUT` (antibucle) |
| **sudoPassword** | string             | —            | Apenas para ambientes de trabalho sem root: autoriza a instalação no arquivo de confiança; ignorada quando executado como root   |

**Não existem variáveis de ambiente** para TPROXY — toda a configuração é efetuada através do
corpo do pedido POST ou dos valores predefinidos acima.

## §9 Ativação a partir do Inspetor de Tráfego

1. Abra o **Inspetor de Tráfego** (`/dashboard/tools/traffic-inspector`).
2. Na barra de ferramentas dos modos de captura, localize o botão **"Desencriptação TPROXY"** ⚠
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Se estiver **desativado** com a descrição "A desencriptação TPROXY requer Linux + root +
     o addon nativo", o addon nativo não está disponível neste anfitrião (não é Linux,
     não tem uma cadeia de ferramentas ou o addon não foi compilado). Consulte [§2](#2-requirements) e [§3](#3-the-native-ip_transparent-addon).
3. Clique no botão. Este chama `POST /api/tools/agent-bridge/tproxy` através de
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`), que:
   cria a CA dinâmica, abre o listener transparente, aplica as regras de firewall
   e instala a CA no repositório de confiança do SO.
4. Durante a execução, o botão fica âmbar e apresenta a contagem de interceções em tempo real
   (`· <interceptCount>`). Os pedidos intercetados aparecem na lista de pedidos com
   `source: "tproxy"`.
5. Clique novamente para parar — `DELETE /api/tools/agent-bridge/tproxy` através de
   `stopTproxyCaptureMode()` fecha o listener, desinstala a CA e reverte
   as regras de firewall.

O estado do modo de captura (em execução / disponível / contagem de interceções / porta do listener) é obtido
a partir de `GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` em
`src/mitm/tproxy/captureManager.ts`). Apenas **uma** sessão TPROXY é executada de cada vez —
a tentativa de iniciar uma segunda sessão é rejeitada com "O modo de captura TPROXY já está em execução".

## §10 Resolução de problemas

### O botão está desativado

Não é possível carregar o addon nativo. Confirme que: está a utilizar Linux, compilou o addon
(`npm run build:native:tproxy`) e o processo consegue carregar `transparent.node`.
`isTransparentSocketAvailable()` controla o botão; `GET /api/tools/agent-bridge/tproxy`
devolve `available: false` quando o addon está em falta.

### Nada é capturado

- Confirme que o processo intercetado estabelece efetivamente ligação à `dport`
  configurada (predefinição: `443`).
- Confirme que o processo confia na CA dinâmica. A CA é instalada como
  `omniroute-tproxy-ca.crt`; as aplicações com o seu próprio repositório de confiança (NSS do Firefox/Chrome)
  também podem necessitar que o certificado seja aí adicionado.
- Execute o autoteste **Diagnose** do AgentBridge (consulte
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) para verificar a confiança no certificado /
  o estado de funcionamento do servidor.

### Regras de firewall obsoletas após uma falha

`revertTproxy()` é o inverso exato da aplicação e é idempotente. Parar o
modo reverte as regras; se o OmniRoute tiver sido terminado a meio da sessão, utilize a ação
**Repair** do AgentBridge (`POST /api/tools/agent-bridge/repair`) para reverter o estado de sistema
órfão (falsificação de DNS, CA raiz, proxy do sistema). As regras `mangle` do TPROXY e a rota também
são automaticamente removidas ao reiniciar.

### Ciclo infinito / o proxy interceta o seu próprio reencaminhamento

Este é o caso de prevenção de ciclos. Confirme que `bypassMark` é diferente de `mark` (a validação
impõe esta condição) e que o reencaminhamento utiliza `connectMarked` (como acontece em `realForward`).
Consulte [§5 Prevenção de ciclos](#anti-loop-so_mark).
