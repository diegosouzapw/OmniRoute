## Visão geral

Todas as rotas da API de gestão do OmniRoute estão classificadas num de três níveis de proteção. A classificação é estática, está definida em `src/server/authz/routeGuard.ts` e é avaliada antes da execução de qualquer outro ramo de autenticação.

## Níveis

### Nível 1 — LOCAL_ONLY

**Imposto por:** `isLocalOnlyPath(path)` → verificação do anfitrião de loopback  
**Contorno:** Nenhum por predefinição. Exceção restrita para caminhos em `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` quando o pedido contém uma chave de API válida com o âmbito `manage` (consulte [Exceção para o âmbito manage](#manage-scope-carve-out)).

Estas rotas iniciam processos-filho ou executam código em tempo de execução. Expô-las a tráfego que não seja de loopback permitiria que um atacante que tivesse obtido um JWT válido (por exemplo, através de um túnel Cloudflared/Ngrok) desencadeasse a criação de processos — uma classe de CVE conhecida ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**O que é o GHSA-fhh6-4qxv-rpqj (a classe de ataque):** um servidor de gestão/agente expõe um endpoint que inicia um subprocesso (`npm install`, `node`, um navegador, um proxy, `git`, `tar`, …). Se esse endpoint estiver acessível a partir de fora do anfitrião — porque o operador colocou o OmniRoute atrás de um túnel nginx/Cloudflare/Tailscale e ocorreu uma fuga de um JWT, ou porque a autenticação foi configurada incorretamente — o atacante transforma «chamar uma API» em «executar um comando no anfitrião» (execução remota de código). O OmniRoute impede isto ao aplicar **incondicionalmente uma verificação do anfitrião de loopback, antes de qualquer verificação de autenticação**, em todas as rotas com capacidade para iniciar processos: um token exposto através de um túnel continua sem conseguir aceder à funcionalidade de criação de processos.

**O conjunto LOCAL_ONLY completo.** A fonte oficial é `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` em `src/server/authz/routeGuard.ts`; a tabela abaixo reflete o estado atual. A verificação `check-route-guard-membership` enumera todos os ficheiros `route.ts` nos prefixos com capacidade para iniciar processos e faz com que a CI falhe se algum não estiver classificado como exclusivamente local.

#### Exceção para o âmbito de gestão

Um subconjunto dos caminhos LOCAL_ONLY TAMBÉM PODE ser acedido a partir de endereços que não sejam de loopback se, e
apenas se, o pedido incluir um `Authorization: Bearer <api-key>` cujos
metadados incluam o âmbito `manage` (ou `admin`). A exceção é controlada
explicitamente por caminho através de `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, para que a
predefinição para qualquer novo caminho LOCAL_ONLY continue a exigir estritamente loopback. Os pedidos sem autenticação
e os pedidos com chaves sem âmbito de gestão continuam a ser rejeitados com
`403 LOCAL_ONLY`.

Atualmente, o único prefixo que permite esta exceção é `/api/mcp/`. `/api/cli-tools/runtime/` e
`/api/services/` são intencionalmente excluídos porque podem iniciar
subprocessos arbitrários (`npm install`, `node`), que constituem precisamente a classe de CVE que o
nível LOCAL_ONLY existe para impedir.

**#7895 — âmbito restrito `mcp:connect`:** a exceção de `/api/mcp/` TAMBÉM aceita
uma chave Bearer que tenha o âmbito restrito `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), verificado através de
`hasMcpConnectOrManageScope()` em `src/server/authz/policies/management.ts`.
Isto está limitado APENAS a `/api/mcp/` — `mcp:connect` não concede qualquer acesso a nenhuma outra
rota de gestão (incluindo qualquer outro prefixo de exceção LOCAL_ONLY, caso algum
venha a ser adicionado), e é deliberadamente excluído de
`MANAGEMENT_API_KEY_SCOPES`. Uma chave com `manage`/`admin` continua a beneficiar da
exceção exatamente como antes; `mcp:connect` é uma alternativa com privilégios inferiores
para clientes remotos exclusivamente MCP que não devem necessitar de acesso de gestão abrangente.

| Pedido                                          | Caminho                    | Resultado                       |
| ----------------------------------------------- | -------------------------- | ------------------------------- |
| Sem loopback, sem Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY                  |
| Sem loopback, Bearer com âmbito `manage`        | `/api/mcp/*`               | Permitido                       |
| Sem loopback, Bearer com âmbito `mcp:connect`   | `/api/mcp/*`               | Permitido                       |
| Sem loopback, Bearer sem `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                  |
| Sem loopback, Bearer com âmbito `mcp:connect`   | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                  |
| Sem loopback, Bearer com âmbito `manage`        | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                  |
| Loopback, com qualquer/sem Bearer               | qualquer LOCAL_ONLY        | Permitido (passa pelo controlo) |

#### Orientações para operadores e auditoria

Se executar o OmniRoute atrás de um proxy inverso ou túnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), a verificação de loopback continua a proteger as rotas acima
capazes de iniciar processos — um pedido cujo endereço de cliente não seja de loopback é rejeitado com
`403 LOCAL_ONLY` **antes da execução da autenticação**, pelo que um JWT exposto não consegue iniciar um processo. Permanecem
duas responsabilidades para o operador:

- **Não «corrija» um erro 403 falsificando o IP do cliente como loopback.** Definir
  `X-Forwarded-For: 127.0.0.1`, ou usar um proxy que reescreva o endereço de origem como
  loopback, reabre exatamente a classe de RCE que este nível elimina. Exponha o
  painel/API através do proxy — nunca as rotas capazes de iniciar processos.
- **Mantenha mínima a exceção para o âmbito de gestão.** Apenas `/api/mcp/` permite a exceção, e
  apenas com uma chave de API com o âmbito `manage`. Os `SPAWN_CAPABLE_PREFIXES` nunca podem ser
  adicionados à lista de exceções — o esquema zod rejeita-os e
  `isLocalOnlyBypassableByManageScope` recusa-os em tempo de execução (defesa em profundidade),
  que é aquilo a que o painel se refere com «não pode permitir uma exceção». As rotas
  com segmentos dinâmicos e caminhos estáticos capazes de iniciar processos em `/api/providers/` (por exemplo, `/login`,
  `/refresh-cursor`) são abrangidas pelo mecanismo complementar baseado em expressões regulares `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` em
  `src/shared/constants/spawnCapablePrefixes.ts`, e não pelo array simples
  `SPAWN_CAPABLE_PREFIXES` — o array simples teria de abranger todo o
  prefixo `/api/providers/` para as incluir, alargando excessivamente uma árvore de rotas
  que os painéis remotos utilizam legitimamente para operações CRUD de fornecedores.

**Auditoria de acesso** — para verificar que nada externo ao anfitrião está a aceder a estas rotas:

- Abra o **Inventário de Autorizações** em `/dashboard/settings/security`: apresenta a
  lista ativa de prefixos LOCAL_ONLY, os prefixos que permitem bypass e o conjunto
  com capacidade de iniciar processos definido em tempo de compilação ("não pode permitir bypass").
- Use grep nos registos do proxy inverso/de acesso para procurar os prefixos acima associados a um
  endereço de cliente que não seja loopback. Qualquer ocorrência que tenha devolvido `200` em vez de
  `403 LOCAL_ONLY` significa que o proxy está a ocultar o IP real do cliente — corrija o proxy.
- Um `403 LOCAL_ONLY` nos registos do OmniRoute para um destes caminhos significa que a proteção
  está a funcionar conforme previsto, não sendo um erro a suprimir.

### Nível 2 — ALWAYS_PROTECTED

**Imposto por:** `isAlwaysProtectedPath(path)` → ignora o bypass `requireLogin=false`
**Bypass:** Nenhum quando `requireLogin=false`; JWT sempre obrigatório

Estas rotas são destrutivas ou irreversíveis. Permiti-las numa instalação "sem palavra-passe"
significaria que qualquer pessoa na mesma LAN poderia apagar a base de dados ou terminar o
processo do servidor.

| Caminho                                   | Motivo                                                             |
| ----------------------------------------- | ------------------------------------------------------------------ |
| `/api/shutdown`                           | Termina o processo do servidor                                     |
| `/api/settings/database`                  | Exportação, importação e eliminação da base de dados               |
| `/api/db-backups`                         | Acesso ao arquivo completo de cópia de segurança da base de dados  |
| `/api/settings/export-json`               | Exporta o bloco completo de definições (incl. segredos)            |
| `/api/settings/import-json`               | Substitui o bloco completo de definições                           |
| `/api/providers/health-autopilot/actions` | Executa ações de remediação do piloto automático                   |
| `/api/settings/obsidian`                  | Emite credenciais WebDAV reutilizáveis para qualquer raiz de cofre |

**Resposta em caso de violação:** `401 Authentication required`

`/api/settings/obsidian` abrange o seu caminho subordinado `/webdav`: `POST` direciona o serviço de ficheiros WebDAV —
servido pela camada Node personalizada antes do Next.js, fora deste pipeline — para uma raiz escolhida
pelo chamador e devolve credenciais Basic recém-emitidas, `DELETE` efetua a rotação das mesmas e o `POST`
principal armazena o token da REST API do Obsidian. O GHSA-62vw apenas ocultou a revelação da palavra-passe
por `GET`; a emissão continuava no nível permissivo em caso de falha (GHSA-7pq4-8pvv-rx7r).
`enableObsidianVaultSync()` também recusa um cofre que seja o diretório de dados, esteja dentro do mesmo
ou o contenha.

### O bootstrap de uma instalação nova está limitado a loopback — pelo par real, não por `Host`

Sem uma palavra-passe de gestão configurada (e sem `INITIAL_PASSWORD`), `isAuthRequired()` em
`src/shared/utils/apiAuth.ts` mantém o bootstrap anónimo aberto **apenas para pares loopback**.
O loopback é determinado a partir dos sinais de pares fidedignos, por esta ordem: o par TCP real
marcado com token (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, aquilo que a política vê), o veredicto
`AUTHZ_HEADER_PEER_LOCALITY` do próprio pipeline (aquilo que os processadores de rotas veem, considerado
fidedigno apenas enquanto `OMNIROUTE_PEER_STAMP_TOKEN` estiver definido) ou um par de socket real para
chamadores diretos. `Host` / `nextUrl.hostname` nunca são consultados, e a primeira gravação da
palavra-passe (`POST /api/settings/require-login`) está sujeita à mesma restrição, em vez de estar aberta
a todos os pares da rede (GHSA-7pq4-8pvv-rx7r). `managementPolicy` transmite explicitamente o seu próprio
veredicto `peerContext`, pelo que os cabeçalhos do pedido ORIGINAL (antes da remoção) nunca o determinam.

### Nível 3 — MANAGEMENT (predefinição)

Todas as restantes rotas de gestão. É necessária autenticação, exceto se
`requireLogin=false` estiver configurado. Os tokens da CLI podem autenticar estas rotas
(loopback + HMAC válido).

## Ordem de avaliação

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → continuar
     → não-loopback, Bearer com âmbito manage
        E isLocalOnlyBypassableByManageScope     → permitir (management_key)
     → caso contrário                            → rejeitar 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → permitir (system)
  3. hasValidCliToken(headers)?
     → permitir (cli) [loopback + verificação HMAC com timingSafeEqual]
  4. isAlwaysProtectedPath(path) ou requireLogin=true?
     → isDashboardSessionAuthenticated?
        → permitir (dashboard_session)
     → Bearer com âmbito manage num caminho não contornável?
        → permitir (management_key)
     → rejeitar 401/403
  5. requireLogin=false?
     → permitir (anonymous)
```

A ramificação de âmbito manage do passo 1 é o único caminho autenticado que pode satisfazer uma rota
LOCAL_ONLY; o modo de falha do backend de autenticação devolve 503 (não 403), para que uma
BD expirada não seja silenciosamente rebaixada para "negar".

## Adicionar uma nova rota capaz de iniciar processos

1. Adicione o prefixo do caminho a `LOCAL_ONLY_API_PREFIXES` em
   `src/server/authz/routeGuard.ts`
2. Adicione um teste em `tests/unit/authz/routeGuard.test.ts` que confirme que
   `isLocalOnlyPath()` devolve true para o novo prefixo
3. **Nunca ignore este passo** — consulte a Regra Rígida n.º 15 em `CLAUDE.md`
4. Decida: esta rota também deve pertencer a `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   A resposta predefinida é **não**. Opte por incluí-la apenas quando for seguro expor a rota a um
   detentor do âmbito manage (ou seja, quando NÃO iniciar código arbitrário controlado pelo utilizador).

## Adicionar um caminho contornável pelo âmbito manage

1. Confirme que a rota não executa código ou comandos fornecidos pelo utilizador. Se
   o fizer, pare — esta exceção não é a ferramenta adequada.
2. Adicione o prefixo a `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` em
   `src/server/authz/routeGuard.ts`
3. Adicione cobertura em `tests/unit/authz/management-policy.test.ts` para os quatro
   formatos de pedido: sem Bearer (403), Bearer manage (permitir), Bearer não-manage
   (403) e a regressão por prefixo que garante que `/api/cli-tools/runtime/*` permanece
   estritamente limitado a loopback, mesmo com um Bearer manage.

## Documentar níveis de segurança no OpenAPI

Ao adicionar uma nova rota a `docs/openapi.yaml`, aplique a extensão de
fornecedor correspondente caso a rota seja classificada por `routeGuard.ts`:

| Classificação de routeGuard.ts          | Anotação YAML                        | Aplicação                                               |
| --------------------------------------- | ------------------------------------ | ------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`               | `x-loopback-only: true`              | Bloqueada incondicionalmente fora de loopback           |
| `ALWAYS_PROTECTED_API_PATHS`            | `x-always-protected: true`           | Autenticação obrigatória mesmo com `requireLogin=false` |
| Rota interna de admin/debug             | `x-internal: true`                   | Oculta de /dashboard/api-endpoints por predefinição     |
| Nenhuma (pública / autenticação padrão) | (não é necessária qualquer anotação) | Acesso padrão controlado por `requireLogin`             |

### Validação

Dois scripts garantem a consistência entre as anotações YAML e `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — falha se a cobertura for < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — falha se as anotações `x-loopback-only` ou
  `x-always-protected` divergirem das constantes em tempo de compilação

Ambos os scripts são executados no hook de pre-commit e na CI.

### Regra de falsos positivos

Se `x-always-protected` ou `x-loopback-only` estiver anotado numa rota que NÃO consta da
constante de `routeGuard.ts`, o script de cobertura falha. A correção consiste sempre em alinhar o
YAML com aquilo que `routeGuard.ts` realmente impõe — e não em adicionar rotas a `routeGuard.ts`
sem implementar também a lógica de aplicação.
