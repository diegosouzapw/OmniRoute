Este documento descreve o processo efetivo de implementação do OmniRoute no Fly.io, abrangendo dois cenários:

- Implementar o projeto atual no Fly.io pela primeira vez
- Publicar atualizações de código subsequentes
- Novos projetos que sigam o mesmo fluxo de implementação

Este guia baseia-se numa configuração funcional verificada para o projeto atual. O nome da aplicação é `omniroute`.

---

## 1. Objetivos da implementação

- Plataforma: Fly.io
- Método de implementação: publicação direta local com o `flyctl`
- Ambiente de execução: utilização dos ficheiros `Dockerfile` e `fly.toml` existentes no repositório
- Persistência de dados: Fly Volume montado em `/data`
- URL de acesso: `https://omniroute.fly.dev/`

---

## 2. Configuração principal do projeto atual

Foi confirmado que o ficheiro `fly.toml` no repositório atual contém os seguintes elementos principais:

```toml
app = 'omniroute'
primary_region = 'sin'

[[mounts]]
  source = 'data'
  destination = '/data'

[processes]
  app = 'node run-standalone.mjs'

[http_service]
  internal_port = 20128

[env]
  TZ = "Asia/Shanghai"
  HOST = "0.0.0.0"
  HOSTNAME = "0.0.0.0"
  BIND = "0.0.0.0"
```

Notas:

- `app = 'omniroute'` determina a aplicação Fly de destino da implementação
- `destination = '/data'` determina o diretório de montagem do volume persistente
- Este projeto tem de definir `DATA_DIR=/data`; caso contrário, a base de dados e as chaves serão escritas no diretório temporário do contentor

## 3. Pré-requisitos

### 3.1 Instalar a CLI do Fly

Windows PowerShell:

```powershell
pwsh -Command "iwr https://fly.io/install.ps1 -useb | iex"
```

Se o script de instalação falhar no seu ambiente, também pode transferir manualmente o binário `flyctl` e adicioná-lo ao seu `PATH`.

### 3.2 Iniciar sessão na sua conta Fly

```powershell
flyctl auth login
```

### 3.3 Verificar o estado da sessão

```powershell
flyctl auth whoami
flyctl version
```

## 4. Primeira implementação do projeto atual

### 4.1 Clonar o código e entrar no diretório

```powershell
git clone https://github.com/diegosouzapw/OmniRoute.git
cd OmniRoute
```

### 4.2 Confirmar o nome da aplicação

Abra o ficheiro `fly.toml` e verifique a seguinte linha:

```toml
app = 'omniroute'
```

Se estiver a implementar numa nova aplicação sua, pode alterá-lo para um nome globalmente exclusivo, por exemplo:

```toml
app = 'omniroute-yourname'
```

Nota:

- Certifique-se de que a aplicação apresentada na consola corresponde ao valor de `app` no ficheiro `fly.toml`
- Se tiver utilizado anteriormente um nome diferente, como `oroute`, não o confunda com `omniroute`

### 4.3 Criar a aplicação

Se a aplicação ainda não existir:

```powershell
flyctl apps create omniroute
```

Se tiver alterado o nome da aplicação, substitua `omniroute` pelo nome escolhido.

### 4.4 Primeira implementação

```powershell
flyctl deploy
```

## 5. Parâmetros obrigatórios

Para este projeto, recomenda-se a configuração de, pelo menos, os seguintes parâmetros no Fly.io.

### 5.1 Parâmetros verificados

Estes parâmetros foram utilizados em implementações reais na aplicação `omniroute` atual:

- `API_KEY_SECRET`
- `DATA_DIR`
- `JWT_SECRET`
- `MACHINE_ID_SALT`
- `NEXT_PUBLIC_BASE_URL`
- `OMNIROUTE_WS_BRIDGE_SECRET` (obrigatório em produção — utilizado para autenticação da ponte WebSocket)
- `STORAGE_ENCRYPTION_KEY`

### 5.2 Acerca de `INITIAL_PASSWORD`

O projeto atual não define `INITIAL_PASSWORD`, uma vez que esta implementação não o exige.

Se não estiver definido:

- O registo de arranque indicará que a palavra-passe predefinida é `CHANGEME`
- Deve alterar a palavra-passe de início de sessão nas definições do sistema assim que possível após a implementação

Se pretender inicializar a palavra-passe do backend de forma não assistida, pode adicioná-la posteriormente:

- `INITIAL_PASSWORD`

## 6. Parâmetros recomendados

### 6.1 Configuração de segredos

As seguintes variáveis são recomendadas para os Fly Secrets:

| Variável                       | Recomendação            | Descrição                                                           |
| ------------------------------ | ----------------------- | ------------------------------------------------------------------- |
| `API_KEY_SECRET`               | Obrigatória             | Utilizada para gerar e validar chaves de API                        |
| `JWT_SECRET`                   | Obrigatória             | Utilizada para sessões de início de sessão e assinatura de JWT      |
| `OMNIROUTE_WS_BRIDGE_SECRET`   | Obrigatória em produção | Segredo de autenticação da ponte WebSocket                          |
| `STORAGE_ENCRYPTION_KEY`       | Fortemente recomendada  | Encripta em repouso informações de ligação confidenciais            |
| `MACHINE_ID_SALT`              | Recomendada             | Gera um identificador de máquina estável                            |
| `INITIAL_PASSWORD`             | Opcional                | Define a palavra-passe inicial do backend na primeira implementação |
| Credenciais privadas OAuth/API | Conforme necessário     | Configuração de autenticação de plataformas externas                |

### 6.2 Valores recomendados para o projeto atual

| Variável               | Valor recomendado           |
| ---------------------- | --------------------------- |
| `DATA_DIR`             | `/data`                     |
| `NEXT_PUBLIC_BASE_URL` | `https://omniroute.fly.dev` |

Notas:

- `DATA_DIR=/data` é essencial e tem de corresponder ao ponto de montagem do Fly Volume
- `NEXT_PUBLIC_BASE_URL` é utilizada pelo agendador, pelas chamadas de retorno do frontend e em cenários semelhantes

### 6.3 Configuração do URL de chamada de retorno OAuth

Se precisar de ativar fornecedores baseados em OAuth (por exemplo, Antigravity, Gemini, Cursor) na implementação do Fly.io, certifique-se dos dois pontos seguintes:

1. **Defina `NEXT_PUBLIC_BASE_URL` como o seu domínio HTTPS público**

   ```powershell
   flyctl secrets set NEXT_PUBLIC_BASE_URL=https://omniroute.fly.dev -a omniroute
   ```

   Se estiver a utilizar um domínio personalizado, substitua-o pelo domínio correspondente (por exemplo, `https://omniroute.yourdomain.com`).

2. **Configure o URL de chamada de retorno na consola do fornecedor**

   Todos os fornecedores OAuth partilham o único caminho de chamada de retorno `/callback` — NÃO existe uma rota de chamada de retorno por fornecedor:

   ```text
   <NEXT_PUBLIC_BASE_URL>/callback
   ```

   Por exemplo, independentemente de ser Gemini, Antigravity, Cursor ou GitLab Duo:
   - `https://omniroute.fly.dev/callback`

   Se `NEXT_PUBLIC_BASE_URL` não corresponder ao URL de chamada de retorno registado junto do fornecedor, o fluxo OAuth irá falhar na etapa de redirecionamento do browser.

## 7. Configuração de segredos com um único comando

Os comandos seguintes geram valores aleatórios seguros e gravam, num único passo, todos os parâmetros necessários para o projeto atual nos Fly Secrets.

Notas:

- Não inclui `INITIAL_PASSWORD`
- Destina-se ao projeto atual `omniroute`

```powershell
$apiKeySecret = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$jwtSecret = [Convert]::ToHexString((1..64 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$machineIdSalt = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$storageKey = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$wsBridgeSecret = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()

flyctl secrets set `
  API_KEY_SECRET=$apiKeySecret `
  JWT_SECRET=$jwtSecret `
  MACHINE_ID_SALT=$machineIdSalt `
  STORAGE_ENCRYPTION_KEY=$storageKey `
  OMNIROUTE_WS_BRIDGE_SECRET=$wsBridgeSecret `
  DATA_DIR=/data `
  NEXT_PUBLIC_BASE_URL=https://omniroute.fly.dev `
  -a omniroute
```

No Linux/macOS, também pode utilizar `openssl rand -hex 32`:

```bash
flyctl secrets set OMNIROUTE_WS_BRIDGE_SECRET=$(openssl rand -hex 32) -a omniroute
```

Notas:

- `OMNIROUTE_WS_BRIDGE_SECRET` é obrigatória em produção; a sua ausência irá impedir o handshake da ponte WebSocket

Se também pretender definir uma palavra-passe inicial:

```powershell
flyctl secrets set INITIAL_PASSWORD=your-strong-password -a omniroute
```

## 9. Atualizações e Lançamentos Posteriores

Após atualizar o código, o processo de lançamento é simples:

```powershell
git pull
flyctl deploy
```

Se apenas precisar de atualizar os parâmetros sem alterar o código:

```powershell
flyctl secrets set KEY=value -a omniroute
```

O Fly efetuará automaticamente uma atualização gradual das máquinas.

### 9.1 Acompanhar as Atualizações do Repositório Upstream Preservando o `fly.toml` do Seu Fork

Se o repositório atual for um fork e pretender sincronizar as atualizações do upstream `https://github.com/diegosouzapw/OmniRoute`, siga o fluxo de trabalho abaixo.

Primeiro, verifique os seus repositórios remotos:

```powershell
git remote -v
```

Deverá ver, pelo menos:

- `origin` a apontar para o seu próprio fork
- `upstream` a apontar para o repositório original

Se `upstream` não estiver configurado, adicione-o:

```powershell
git remote add upstream https://github.com/diegosouzapw/OmniRoute.git
```

Antes de sincronizar com o upstream, obtenha os commits e as tags mais recentes:

```powershell
git fetch upstream --tags
```

Verifique a versão atual e as tags do upstream:

```powershell
git describe --tags --always
git show --no-patch --oneline v3.4.7
```

> Nota: A versão atual do projeto é `v3.8.0`. As referências a `v3.4.7` abaixo são mantidas apenas como exemplos históricos. Para lançamentos reais, utilize `:latest` ou a tag da versão atual (por exemplo, `:v3.8.0`).

Se pretender integrar a versão mais recente de `main` do upstream, mantendo à força o `fly.toml` do seu fork, siga este fluxo de trabalho:

```powershell
git merge upstream/main
git checkout HEAD~1 -- fly.toml
git add -- fly.toml
git commit -m "chore(deploy): keep fork fly.toml"
git push origin main
```

Notas:

- `git merge upstream/main` sincroniza o código mais recente do repositório original
- `git checkout HEAD~1 -- fly.toml` restaura o `fly.toml` do seu fork a partir do estado anterior à integração
- Se o upstream não tiver modificado o `fly.toml`, este passo não introduzirá quaisquer diferenças
- Se o upstream tiver modificado o `fly.toml`, este passo garante que o nome da sua aplicação Fly, a montagem do volume, a região e outras configurações de implementação específicas do fork não são substituídos

Se pretender alinhar com uma tag de lançamento específica (por exemplo, `v3.4.7`), verifique primeiro se a tag já está incluída em `upstream/main`:

```powershell
git merge-base --is-ancestor v3.4.7 upstream/main
```

Um resultado bem-sucedido significa que `upstream/main` já contém essa versão; pode simplesmente integrar `upstream/main`.

### 9.2 Sequência de Lançamento Padrão Após a Sincronização com o Upstream

Após sincronizar com o repositório original, siga esta ordem de lançamento recomendada:

1. `git fetch upstream --tags`
2. `git merge upstream/main`
3. Restaurar o `fly.toml` do fork
4. `git push origin main`
5. `flyctl deploy`
6. `flyctl status -a omniroute`
7. `flyctl logs --no-tail -a omniroute`

Este é o fluxo de trabalho efetivamente utilizado ao atualizar o projeto atual para `v3.4.7` (o exemplo refere-se a uma versão histórica; a versão atual é `v3.8.0`).

try {

  if ($_.Exception.Response) {
    $_.Exception.Response.StatusCode.value__

## 11. Indicadores de Sucesso

Após uma implementação bem-sucedida, os registos deverão apresentar conteúdo semelhante a:

```text
[bootstrap] Secrets persisted to: /data/server.env
[DB] SQLite database ready: /data/storage.sqlite
```

Estes dois pontos são essenciais:

- `/data/server.env` confirma que os segredos de tempo de execução são guardados no volume persistente
- `/data/storage.sqlite` confirma que a base de dados é guardada no volume persistente

Se vir `/app/data/...`, significa que `DATA_DIR` está configurado incorretamente e deve ser corrigido de imediato.

## 12. Problemas Comuns

### 12.1 A Página `Secrets` Está Vazia

Normalmente, existem dois motivos:

- Ainda não executou `flyctl secrets set`
- Está a consultar uma aplicação diferente (por exemplo, `oroute` em vez de `omniroute`)

### 12.2 `flyctl deploy` Apresenta `app not found`

Crie primeiro a aplicação:

```powershell
flyctl apps create omniroute
```

### 12.3 Falha ao Analisar `fly.toml`

Verifique o seguinte:

- Se existem caracteres corrompidos nos comentários
- Se as aspas e a indentação TOML estão corretas

### 12.4 Os Dados Não São Persistidos

Verifique ambos os pontos seguintes:

- `fly.toml` contém `destination = '/data'`
- `DATA_DIR` está definido como `/data`

### 12.5 É Possível Executar sem `INITIAL_PASSWORD`?

Sim, é possível. Será utilizada a palavra-passe predefinida `CHANGEME`. Recomenda-se que altere a palavra-passe do backend assim que possível em produção.

---

## 13. Reutilização em Novos Projetos

Se estiver a implementar um novo projeto com base neste documento, apenas precisa de alterar estes itens:

1. Altere o valor de `app` em `fly.toml`
2. Altere `NEXT_PUBLIC_BASE_URL`
3. Mantenha `DATA_DIR=/data`
4. Gere novamente `API_KEY_SECRET`, `JWT_SECRET`, `MACHINE_ID_SALT` e `STORAGE_ENCRYPTION_KEY`
5. Após a primeira implementação, verifique se os registos são guardados em `/data`

Não reutilize chaves de um projeto anterior.
