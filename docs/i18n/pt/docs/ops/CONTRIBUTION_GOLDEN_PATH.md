Utilize este guia para escolher o ciclo de desenvolvimento fiável mais pequeno para um pull request. Este não
substitui os documentos de arquitetura e segurança específicos de cada área ligados abaixo; associa cada tipo
comum de alteração aos respetivos contratos, verificações específicas e cobertura de CI.

## O percurso seguido por todas as alterações

1. **Escolha a base antes de editar.** Encontre o branch `release/v*` ativo mais recente e crie o seu branch a partir
   da respetiva ponta. Defina esse branch como destino, não o `main`. Se estiver em vigor um congelamento de versão, não utilize o branch
   congelado como destino; utilize o próximo ciclo ativo descrito em
   [Modelo de Branches e Lançamentos](BRANCHING_MODEL.md).
2. **Identifique os contratos.** Identifique todos os catálogos, esquemas, artefactos gerados, APIs públicas ou interfaces
   de utilizador afetados pela alteração. A tabela abaixo apresenta o conjunto inicial mínimo.
3. **Escreva ou atualize testes específicos.** As alterações de produção em `src/`, `open-sse/`, `electron/` ou
   `bin/` exigem um teste automatizado no mesmo PR. Execute os ficheiros de teste mínimos que comprovem o
   comportamento e, em seguida, as verificações específicas indicadas.
4. **Deixe o CI executar a matriz abrangente.** As partições completas de testes unitários, o Vitest, o mecanismo incremental de cobertura e
   a compilação de produção são executados no PR. Execute localmente um conjunto abrangente apenas quando uma falha específica indicar
   um impacto mais alargado ou quando a alteração abranger vários subsistemas.
5. **Faça a reconciliação antes da revisão.** Obtenha a base ativa, inspecione os respetivos commits novos e as suas diferenças em relação
   a ela e, em seguida, efetue o rebase ou o merge da base de acordo com o fluxo de trabalho dos contribuidores. Resolva os conflitos em ficheiros
   gerados e catálogos a partir da respetiva origem, volte a gerá-los, execute novamente o ciclo específico e confirme que o
   PR continua a ter como destino o branch de versão ativo.
6. **Registe as evidências.** No modelo de PR, indique os comandos executados, todos os ficheiros de teste adicionados ou alterados,
   as migrações ou feature flags e qualquer validação exclusiva de CI ainda pendente.

## Percursos recomendados por tipo de alteração

Os comandos abaixo são verificações específicas mínimas, não uma autorização para omitir um teste que cubra diretamente o
comportamento alterado.

### Fornecedor

**Contratos**

- Definição do fornecedor em `src/shared/constants/providers/` e respetiva composição em
  `src/shared/constants/providers.ts`.
- Modelos e capacidades em `open-sse/config/providerRegistry.ts` ou nos respetivos ficheiros de registo extraídos.
- Seleção do executor/tradutor, configuração de OAuth ou chave de API, recursos do painel e referência
  gerada do fornecedor, quando aplicável.
- As credenciais públicas têm de utilizar `resolvePublicCred()`; as respostas de erro têm de utilizar as funções auxiliares partilhadas de
  sanitização de erros. Consulte `docs/security/PUBLIC_CREDS.md` (git; não compilado em `/docs`) e
  [Sanitização de Erros](../security/ERROR_SANITIZATION.md).

**Ciclo específico**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # quando o catálogo for alterado; inclua as diferenças geradas no commit
npm run lint
```

Teste também todas as famílias de pedidos afetadas: chat, Responses, imagens, embeddings, áudio ou vídeo.
Reveja as diferenças do catálogo gerado e dos testes de referência como alterações de contrato; não as aceite sem análise.

### Encaminhamento

**Contratos**

- Valores públicos das estratégias e metadados da IU em `src/shared/constants/routingStrategies.ts`.
- Distribuição e ordenação em `open-sse/services/combo.ts` e `open-sse/services/combo/`.
- Esquemas de combinações, persistência, estado de resiliência, capacidades dos modelos e controlos da API/IU.
- [Motor de Combinações Automáticas](../routing/AUTO-COMBO.md) e documentação de resiliência quando o comportamento for alterado.

**Ciclo específico**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # alterações de estratégia ou distribuição
npm run check:known-symbols      # alterações ao registo de estratégias
npm run lint
```

Utilize localmente testes determinísticos com serviços a montante simulados. Os testes rápidos de combinações em sistemas reais exigem credenciais e são
manuais, não substitutos do CI.

### IU / UX

**Contratos**

- Limites das rotas/páginas Next.js e dos componentes partilhados em `src/app/` e
  `src/shared/components/`.
- Formatos das respostas da API, estados de carregamento/vazio/erro, comportamento do teclado e dos leitores de ecrã,
  disposição responsiva, temas e expansão de idiomas.
- Strings de origem da IU em inglês em `src/i18n/messages/en.json`; não introduza diretamente novo texto apresentado ao utilizador.

**Ciclo específico**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Execute a aplicação para alterações visuais ou de interação e verifique vistas estreitas e largas. O CI executa a
compilação de produção e conjuntos de testes mais abrangentes; o comportamento visual continua a exigir uma verificação específica adequada à alteração,
seja através de um componente, do Playwright ou de uma verificação manual documentada.

### i18n

**Contratos**

- `src/i18n/messages/en.json` é a origem da IU; `config/i18n.json` é a origem dos idiomas.
- Os catálogos da CLI encontram-se separadamente em `bin/cli/locales/`.
- Preserve exatamente os marcadores de posição e as etiquetas ICU. Não traduza nomes de produtos/fornecedores/modelos,
  nomes de protocolos e cabeçalhos, comandos, identificadores de código/JSON, URLs, variáveis de ambiente ou
  termos protegidos, como `OmniRoute`, `OAuth`, `MCP` e `A2A`. A lista de origem atual é
  `scripts/i18n/glossary/protected-terms.json`.

**Ciclo específico**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # quando as strings/os catálogos da CLI forem alterados
npm run lint
```

Estas são orientações para o sistema existente, não um convite para expandir as respetivas ferramentas ou o modelo de chaves.
Mantenha as alterações de i18n cirúrgicas enquanto o sistema de substituição está a ser concebido. Não execute comandos de tradução
que chamem serviços externos, a menos que a tarefa exija explicitamente traduções geradas e tenha
revisto as diferenças resultantes.

### CLI

**Contratos**

- Comandos e flags públicos em `bin/cli/`, comandos de API gerados, códigos de saída, stdout/stderr e
  formatos da saída JSON, comportamento da configuração/do ambiente e ficheiros incluídos no pacote.
- As strings da CLI apresentadas ao utilizador devem utilizar a camada de i18n da CLI e manter os catálogos `en`/`pt-BR` alinhados.
- Preserve o Node como runtime suportado e o contrato do binário publicado.

**Ciclo focado**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # alterações à CLI gerada/agrupada
npm run check:pack-policy     # alterações à superfície do pacote
npm run lint
```

Utilize o comando exato num diretório de dados temporário quando o comportamento depender da análise sintática, de ficheiros ou do estado
de saída. A CI executa as verificações mais abrangentes dos artefactos do pacote e do ecossistema.

### Base de dados

**Contratos**

- Módulos de domínio em `src/lib/db/`; importe diretamente os módulos específicos (a antiga camada de reexportação `localDb.ts` foi removida).
- Migrações SQL numeradas e idempotentes em `src/lib/db/migrations/`, segurança das transações, comportamento das atualizações,
  índices e todos os chamadores afetados pelo esquema.
- As rotas e os processadores nunca executam SQL em bruto diretamente.

**Ciclo focado**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Ao adicionar uma migração, teste tanto uma base de dados nova como a atualização a partir do esquema anterior. Os testes da base de dados
devem fechar os identificadores e chamar `resetDbInstance()` durante a limpeza. Execute `npm run test:bun:db` apenas quando
o caminho do adaptador Bun de melhor esforço for alterado; o Node continua a ser a referência.

### Compilação / implementação

**Contratos**

- Manifestos/ficheiro de bloqueio da raiz e do espaço de trabalho, `scripts/build/`, montagem autónoma do Next.js, conteúdo do pacote `dist/`,
  metadados de plataforma do Electron, fluxos de trabalho de CI e sentinelas de implementação.
- Os intervalos de versões do Node suportados e a utilização permitida do Bun em `CLAUDE.md` devem permanecer intactos.
- Os artefactos de compilação não devem ser rastreados; aplicam-se as políticas de dependências, licenças, fluxos de trabalho e pacotes.

**Ciclo focado**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # alterações a dependências ou ao ficheiro de bloqueio
npm run check:pack-policy      # alterações à superfície do pacote publicado
npm run lint
```

Utilize `npm run build` localmente apenas quando a alteração afetar a compilação, a montagem autónoma, os recursos
ou o agrupamento em runtime. Utilize `npm run build:release` apenas para validação de versões/implementação. A compilação da CI é
o sinal multiplataforma final; as alterações específicas de plataforma do Electron necessitam da compilação focada correspondente
ou de evidências de testes rápidos.

## Ciclo local de candidatos

Os testes do código-fonte não conseguem provar que o artefacto empacotado arranca: listas de empacotamento, dependências removidas e binários nativos só falham quando o tarball é instalado e iniciado. `npm run dev:candidate` (`scripts/dev/candidate.mjs`) é o lado local do fluxo compilar uma vez / validar / promover da RFC #8084: compila um candidato, valida esse artefacto exato, promove-o através da renomeação de diretórios e reverte-o quando o slot promovido falha a verificação de estado.

```bash
npm run dev:candidate -- run --dry-run --json  # apresentar o plano sem alterar nada
npm run dev:candidate -- run                   # compilar + validar + promover, reversão automática
npm run dev:candidate -- build                 # npm pack + instalar em _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # arrancar numa porta livre, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # trocar current e previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # reutilizar um tarball compilado noutro local (CI)
```

- **Compile uma vez.** `build` empacota a árvore atual (necessita de `dist/server.js`, pelo que deve executar primeiro `npm run build:release`) ou copia `--from-tarball` e, em seguida, instala o tarball num prefixo npm isolado, porque o tarball não contém `node_modules`. O id é o sha abreviado de `HEAD` (`-dirty` quando a árvore contém alterações locais) ou `tgz-<sha256>` para um tarball. Um id limpo que já tenha sido compilado é reutilizado em vez de ser novamente compilado; especifique `--force` para o recompilar.
- **Valide o pacote, não o código-fonte.** `validate` inicia a CLI instalada (`serve --port <free port>`) com um novo `DATA_DIR=<candidate>/data`, segredos fictícios e as variáveis `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` e `INITIAL_PASSWORD` do operador removidas do ambiente, para verificar a configuração sem chaves da interface de loopback de uma instalação nova. Aguarda que `GET /api/health` devolva 200, exige que `GET /v1/models` devolva 200, termina o grupo de processos e regista o veredicto em `validation.json`, juntamente com o hash do tarball.
- **Promova o mesmo artefacto.** `promote` rejeita um candidato que não tenha uma validação bem-sucedida para o hash do tarball atual. O slot ativo predefinido é `_artifacts/candidate/current`; `--target <dir>` seleciona outro diretório no mesmo sistema de ficheiros e o respetivo slot anterior é `<dir>.previous`. Cada renomeação é atómica e uma falha durante o processo reverte as renomeações já efetuadas.
- **Reverta.** `run` volta a validar o slot promovido e troca novamente `current` e `previous` quando essa verificação falha. Um candidato que falhe a primeira validação nunca é promovido.

Tudo é escrito em `_artifacts/candidate/`, que é ignorado pelo git; uma instalação existente do OmniRoute e o respetivo diretório de dados nunca são alterados. A CLI promovida encontra-se em `_artifacts/candidate/current/prefix/bin/omniroute`; inicie-a com o seu próprio `DATA_DIR` quando a utilizar. Códigos de saída: `0` sucesso, `1` falha na validação ou promoção, `2` erro de utilização ou compilação em falta.

## Ciclo local versus CI

| Executar localmente para cada alteração                                                                           | A CI fornece o sinal abrangente                                                                 |
| ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Testes diretos de comportamento e verificações de categoria acima                                                 | Conjunto completo de testes unitários particionados e testes em série                           |
| `npm run lint`                                                                                                    | Conjuntos de testes Vitest e mecanismos progressivos de cobertura/qualidade                     |
| Verificação de tipos ou compilação apenas quando o contrato afetado o exigir                                      | Compilação de produção, segurança, documentação, dependências e verificações de políticas de PR |
| Interação manual/verificações em tempo real apenas quando a automatização não conseguir comprovar o comportamento | Verificações de integração entre jobs e de plataformas configuradas pelo workflow               |

Um ciclo focado bem-sucedido constitui evidência sobre o contrato alterado, não uma prova de que as verificações de CI não relacionadas
serão aprovadas. Inversamente, não faça com que cada edição local tenha de aguardar pela matriz completa do repositório.

## Lista de verificação de reconciliação

Antes de solicitar uma revisão:

- Confirme que a base do PR continua a ser o branch `release/v*` ativo mais elevado.
- Obtenha essa base e reveja os commits integrados desde que criou o seu branch.
- Reveja `git diff <active-base>...HEAD` para detetar alterações acidentais ou geradas.
- Resolva conflitos de catálogos e documentos gerados atualizando a fonte e regenerando o resultado.
- Execute novamente todos os testes/verificações focados indicados na descrição do PR após a reconciliação.
- Nunca enfraqueça as asserções nem remova testes obrigatórios apenas para se adaptar a uma base que foi alterada.

Para as regras de congelamento de versões e redirecionamento, consulte
[Modelo de Branching e de Versões](BRANCHING_MODEL.md). Para obter o inventário completo da CI, consulte
[Referência das Verificações de Qualidade](../architecture/QUALITY_GATES.md).
