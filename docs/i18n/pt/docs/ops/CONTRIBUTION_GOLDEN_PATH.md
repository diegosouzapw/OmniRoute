Utilize este guia para escolher o ciclo de desenvolvimento fiável mais reduzido para um pull request. Este não
substitui os documentos de arquitetura e segurança específicos de cada área indicados abaixo; associa cada tipo
comum de alteração aos respetivos contratos, verificações específicas e cobertura de CI.

## O percurso seguido por todas as alterações

1. **Escolha a base antes de editar.** Encontre o branch `release/v*` ativo mais recente e crie o seu branch a partir
   da respetiva ponta. Defina esse branch como destino, não `main`. Se estiver ativo um congelamento de versão, não
   utilize o branch congelado como destino; utilize o ciclo ativo seguinte descrito em
   [Modelo de branching e versões](BRANCHING_MODEL.md).
2. **Identifique os contratos.** Identifique todos os catálogos, esquemas, artefactos gerados, APIs públicas ou
   interfaces de utilizador afetados pela alteração. A tabela abaixo apresenta o conjunto inicial mínimo.
3. **Crie ou atualize testes específicos.** As alterações de produção em `src/`, `open-sse/`, `electron/` ou
   `bin/` requerem um teste automatizado no mesmo PR. Execute os ficheiros de teste mínimos que comprovem o
   comportamento e, em seguida, as verificações específicas indicadas.
4. **Deixe o CI executar a matriz abrangente.** Os segmentos completos de testes unitários, o Vitest, o controlo
   incremental da cobertura e a compilação de produção são executados no PR. Execute localmente um conjunto
   abrangente apenas quando uma falha específica indicar um impacto mais amplo ou quando a alteração abranger
   vários subsistemas.
5. **Faça a reconciliação antes da revisão.** Obtenha a base ativa, inspecione os respetivos commits novos e o seu diff
   relativamente a esta e, em seguida, faça rebase ou merge da base de acordo com o fluxo de trabalho dos
   contribuidores. Resolva os conflitos em ficheiros gerados e catálogos a partir da respetiva origem, volte a
   gerá-los, execute novamente o ciclo específico e confirme que o PR continua a ter como destino o branch de
   versão ativo.
6. **Registe as evidências.** No modelo do PR, indique os comandos executados, todos os ficheiros de teste adicionados
   ou alterados, as migrações ou feature flags e qualquer validação exclusiva do CI que ainda esteja pendente.

## Percursos recomendados por tipo de alteração

Os comandos abaixo são as verificações específicas mínimas, não uma autorização para ignorar um teste que cubra
diretamente o comportamento que alterou.

### Fornecedor

**Contratos**

- Definição do fornecedor em `src/shared/constants/providers/` e respetiva composição em
  `src/shared/constants/providers.ts`.
- Modelos e capacidades em `open-sse/config/providerRegistry.ts` ou nos respetivos ficheiros de registo extraídos.
- Seleção do executor/tradutor, configuração de OAuth ou de chave de API, recursos do dashboard e referência
  gerada do fornecedor, quando aplicável.
- As credenciais públicas têm de utilizar `resolvePublicCred()`; as respostas de erro têm de utilizar os auxiliares
  partilhados de sanitização de erros. Consulte `docs/security/PUBLIC_CREDS.md` (git; não compilado em `/docs`) e
  [Sanitização de erros](../security/ERROR_SANITIZATION.md).

**Ciclo específico**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # quando o catálogo for alterado; faça commit do diff gerado
npm run lint
```

Teste também todas as famílias de pedidos afetadas: chat, Responses, imagens, embeddings, áudio ou vídeo.
Analise os diffs gerados do catálogo e dos testes golden como alterações contratuais; não os aceite sem os verificar.

### Encaminhamento

**Contratos**

- Valores públicos das estratégias e metadados da IU em `src/shared/constants/routingStrategies.ts`.
- Distribuição e ordenação em `open-sse/services/combo.ts` e `open-sse/services/combo/`.
- Esquemas combo, persistência, estado de resiliência, capacidades dos modelos e controlos da API/IU.
- [Motor Auto-Combo](../routing/AUTO-COMBO.md) e documentação de resiliência quando o comportamento for alterado.

**Ciclo específico**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # alterações de estratégia ou distribuição
npm run check:known-symbols      # alterações ao registo de estratégias
npm run lint
```

Utilize localmente testes determinísticos com upstream simulado. Os testes rápidos de combo em sistemas reais
requerem credenciais e são manuais, não substitutos do CI.

### IU / UX

**Contratos**

- Limites de rotas/páginas do Next.js e componentes partilhados em `src/app/` e
  `src/shared/components/`.
- Formatos das respostas da API, estados de carregamento/vazio/erro, comportamento do teclado e dos leitores de ecrã,
  layout responsivo, temas e expansão de idiomas.
- Strings de origem em inglês da IU em `src/i18n/messages/en.json`; não introduza diretamente no código novo texto
  destinado aos utilizadores.

**Ciclo específico**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Execute a aplicação para alterações visuais ou de interação e verifique viewports estreitos e largos. O CI executa
a compilação de produção e conjuntos de testes mais abrangentes; o comportamento visual continua a exigir um
componente específico, Playwright ou uma verificação manual documentada adequada à alteração.

### i18n

**Contratos**

- `src/i18n/messages/en.json` é a origem da IU; `config/i18n.json` é a origem dos idiomas.
- Os catálogos da CLI encontram-se separadamente em `bin/cli/locales/`.
- Preserve exatamente os marcadores de posição e as tags ICU. Não traduza nomes de produtos/fornecedores/modelos,
  nomes de protocolos e cabeçalhos, comandos, identificadores de código/JSON, URLs, variáveis de ambiente ou
  termos protegidos, como `OmniRoute`, `OAuth`, `MCP` e `A2A`. A lista de origem atual é
  `scripts/i18n/glossary/protected-terms.json`.

**Ciclo específico**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # quando as strings/os catálogos da CLI forem alterados
npm run lint
```

Estas são orientações para o sistema existente, não um convite para expandir as respetivas ferramentas ou o modelo
de chaves. Mantenha as alterações de i18n cirúrgicas enquanto o sistema de substituição está a ser concebido. Não
execute comandos de tradução que chamem serviços externos, exceto se a tarefa exigir explicitamente traduções
geradas e tiver analisado o diff resultante.

### CLI

**Contratos**

- Comandos públicos e opções em `bin/cli/`, comandos de API gerados, códigos de saída, stdout/stderr e
  formatos de saída JSON, comportamento da configuração/do ambiente e ficheiros incluídos no pacote.
- As cadeias de texto da CLI apresentadas ao utilizador têm de utilizar a camada de i18n da CLI e manter os catálogos `en`/`pt-BR` alinhados.
- Preserve o Node como ambiente de execução suportado e o contrato do binário publicado.

**Ciclo focado**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # alterações à CLI gerada/empacotada
npm run check:pack-policy     # alterações à superfície do pacote
npm run lint
```

Utilize o comando exato num diretório temporário de dados quando o comportamento depender da análise, de ficheiros ou do código
de saída. A CI executa as verificações mais abrangentes dos artefactos do pacote e do ecossistema.

### Base de dados

**Contratos**

- Módulos de domínio em `src/lib/db/`; importe diretamente módulos específicos (a antiga camada de reexportação `localDb.ts` foi removida).
- Migrações SQL numeradas e idempotentes em `src/lib/db/migrations/`, segurança das transações, comportamento
  das atualizações, índices e todos os chamadores afetados pelo esquema.
- As rotas e os handlers nunca executam SQL em bruto diretamente.

**Ciclo focado**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Ao adicionar uma migração, teste tanto uma base de dados nova como a atualização a partir do esquema anterior. Os testes da base de dados
têm de fechar os handles e chamar `resetDbInstance()` durante a limpeza. Execute `npm run test:bun:db` apenas quando
o percurso do adaptador Bun de melhor esforço for alterado; o Node continua a ser a referência.

### Compilação / implementação

**Contratos**

- Manifestos/lockfile da raiz e dos workspaces, `scripts/build/`, montagem standalone do Next.js, conteúdo
  do pacote `dist/`, metadados de plataforma do Electron, workflows de CI e sentinelas de implementação.
- Os intervalos de versões do Node suportados e a utilização autorizada do Bun em `CLAUDE.md` têm de permanecer intactos.
- Os artefactos de compilação permanecem não monitorizados; aplicam-se as políticas de dependências, licenças, workflows e pacotes.

**Ciclo focado**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # alterações às dependências ou ao lockfile
npm run check:pack-policy      # alterações à superfície do pacote publicado
npm run lint
```

Utilize `npm run build` localmente apenas quando a alteração afetar a compilação, a montagem standalone, os recursos
ou o empacotamento em tempo de execução. Utilize `npm run build:release` apenas para validação de lançamento/implementação. A compilação da CI é
o sinal final multiplataforma; as alterações específicas de uma plataforma do Electron necessitam da compilação focada correspondente
ou de evidências de um teste de fumo.

## Ciclo local versus CI

| Executar localmente para cada alteração                                                                         | O CI fornece o sinal abrangente                                                               |
| --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Testes diretos de comportamento e os critérios de categoria acima                                               | Conjunto completo de testes unitários em partições e testes sequenciais                       |
| `npm run lint`                                                                                                  | Conjuntos de testes Vitest e critérios progressivos de cobertura/qualidade                    |
| Verificação de tipos ou compilação apenas quando o contrato afetado o exigir                                    | Compilação de produção, segurança, documentação, dependências e critérios de política de PR   |
| Interação manual/verificações em execução apenas quando a automatização não conseguir comprovar o comportamento | Verificações de integração entre tarefas e de plataformas configuradas pelo fluxo de trabalho |

Um ciclo focado bem-sucedido constitui evidência sobre o contrato alterado, não uma prova de que verificações de CI não relacionadas
serão bem-sucedidas. Inversamente, não faça com que cada edição local tenha de aguardar pela matriz completa do repositório.

## Lista de verificação de reconciliação

Antes de solicitar uma revisão:

- Confirme que a base do PR continua a ser o ramo `release/v*` ativo mais recente.
- Obtenha essa base e reveja os commits integrados desde que criou o seu ramo.
- Reveja `git diff <active-base>...HEAD` para detetar alterações acidentais ou geradas.
- Resolva conflitos de catálogo e de documentos gerados atualizando a fonte e gerando novamente o resultado.
- Execute novamente todos os testes/critérios focados indicados na descrição do PR após a reconciliação.
- Nunca enfraqueça as asserções nem remova testes obrigatórios apenas para corresponder a uma base alterada.

Para consultar as regras de congelamento de versões e de alteração da base de destino, utilize
[Modelo de Ramificação e Lançamento](BRANCHING_MODEL.md). Para consultar o inventário completo do CI, utilize
[Referência dos Critérios de Qualidade](../architecture/QUALITY_GATES.md).
