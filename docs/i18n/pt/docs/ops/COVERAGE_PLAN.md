## Referência

Existem vários valores de cobertura, dependendo da forma como o relatório é calculado. Para efeitos de planeamento, apenas um deles é útil.

| Métrica                | Âmbito                                                       | Instruções / Linhas | Ramificações | Funções | Notas                                                        |
| ---------------------- | ------------------------------------------------------------ | ------------------: | -----------: | ------: | ------------------------------------------------------------ |
| Legada                 | Antigo `npm run test:coverage`                               |              79,42% |       75,15% |  67,94% | Inflacionada: conta ficheiros de teste e exclui `open-sse`   |
| Diagnóstico            | Apenas código-fonte, excluindo testes e excluindo `open-sse` |              68,16% |       63,55% |  64,06% | Útil apenas para isolar `src/**`                             |
| Referência recomendada | Apenas código-fonte, excluindo testes e incluindo `open-sse` |              82,58% |       75,22% |  84,23% | Esta é a referência global do projeto que deve ser melhorada |

A referência recomendada é o valor a otimizar.

## Regras

- Os objetivos de cobertura aplicam-se aos ficheiros de código-fonte, não a `tests/**`.
- `open-sse/**` faz parte do produto e tem de permanecer no âmbito.
- O novo código não deve reduzir a cobertura nas áreas alteradas.
- Deve dar-se preferência a testar o comportamento e os resultados das ramificações, em vez dos detalhes de implementação.
- Para `src/lib/db/**`, devem preferir-se bases de dados SQLite temporárias e pequenas fixtures a mocks abrangentes.

## Conjunto atual de comandos

- `npm run test:coverage`
  - Principal mecanismo de controlo da cobertura do código-fonte para o conjunto de testes unitários
  - Gera `text-summary`, `html`, `json-summary` e `lcov`
- `npm run coverage:report`
  - Relatório detalhado, ficheiro a ficheiro, da execução mais recente
- `npm run test:coverage:legacy`
  - Apenas para comparação histórica

## Política de ratchet

Atualize os limiares de `npm run test:coverage` apenas depois de o projeto ultrapassar efetivamente o marco seguinte com uma margem confortável.

**Limite atual:** `npm run test:coverage` impõe **60 instruções / 60 linhas / 60 funções / 60 ramificações** (a métrica foi recalibrada na Fase 6A.1 das Quality-Gates — o valor de referência anterior de 82,58% estava inflacionado porque contabilizava os ficheiros de teste e excluía `open-sse`). O comando `test:coverage:legacy` preserva a antiga métrica 50/50/50 para comparação histórica.

Para verificações pontuais dos limiares com base no relatório mais recente, utilize:

```bash
node scripts/check/test-report-summary.mjs --threshold 75
```

Sequência de ratchet recomendada (a ordem é `instruções-linhas / ramificações / funções`):

1. 55/60/55
2. 60/62/58
3. 65/64/62
4. 70/66/66
5. 75/70/72 <-- limite atual (75/70/75)
6. 80/75/78
7. 85/80/84
8. 90/85/88

O próximo objetivo do ratchet é `80/75/78`, assim que a cobertura de ramificações se mantiver acima de 78% em duas execuções consecutivas.

## Lacuna conhecida

O comando de cobertura atual mede o conjunto principal de testes unitários do Node e inclui o código-fonte alcançado a partir do mesmo, incluindo `open-sse`. Ainda não combina a cobertura do Vitest num único relatório unificado. Vale a pena efetuar essa combinação mais tarde, mas não constitui um impedimento para iniciar a progressão de 60% -> 80%.
