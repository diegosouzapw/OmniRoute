`open-sse/config/providerPluginManifest.ts` define o contrato JSON-safe do plugin de
fornecedor. `open-sse/config/providerPluginManifestRegistry.ts` associa esse
contrato ao registo atual de fornecedores para sidecars como Bifrost,
CLIProxyAPI ou um futuro router em Go/Rust. O registo TypeScript continua a ser a
fonte de verdade, mas os sidecars podem consumir o manifesto sem importar
código de executores, predefinições OAuth, cabeçalhos ou o estado do ambiente do processo.

O mesmo manifesto está disponível através de HTTP em
`GET /api/v1/provider-plugin-manifest` para sidecars executados fora do processo.

O OmniRoute anuncia esse URL ao Bifrost e ao CLIProxyAPI através do cabeçalho
de pedido `X-OmniRoute-Provider-Manifest-Url`. Defina
`OMNIROUTE_PROVIDER_MANIFEST_URL` quando o sidecar necessitar de um URL público ou
da rede de contentores em vez da origem do pedido local.

## Atualizar o Manifesto

O endpoint HTTP devolve `Cache-Control: public, max-age=60` e um
`ETag` forte. Um sidecar deve conservar o último manifesto validado e enviar o respetivo ETag
em `If-None-Match` ao atualizar. Uma resposta `304 Not Modified` não tem corpo;
o sidecar mantém o manifesto em cache. Se não existir um manifesto validado em cache,
o sidecar deve emitir um pedido incondicional em vez de aceitar um `304`.

## Objetivo

Fazer evoluir os metadados dos fornecedores para um contrato de plugin, para que o caminho
de pedidos crítico possa, eventualmente, ficar a cargo de um sidecar com menor latência,
enquanto o OmniRoute mantém a rota TypeScript como ponto de aplicação de políticas e mecanismo
de contingência. O manifesto é aditivo: por si só, não altera o encaminhamento de pedidos.

## Contrato

O manifesto contém:

- id e alias do fornecedor
- formato do upstream e nome do executor
- tipo de autenticação, cabeçalho de autenticação e prefixo de autenticação opcional
- metadados estáticos do endpoint
- elegibilidade para sidecar e motivos explícitos para um fornecedor permanecer no TS
- metadados de modelos compatíveis com JSON, como o comprimento do contexto, indicadores de visão/raciocínio e
  parâmetros não suportados
- etiquetas de capacidades, incluindo `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` e `usage-supported`

O manifesto exclui intencionalmente:

- segredos de clientes OAuth e valores secretos predefinidos
- resolução do ambiente em tempo de execução
- cabeçalhos de pedidos e funções auxiliares de credenciais públicas
- construtores dinâmicos de URLs
- funções de executores
- detalhes internos do pool de sessões

## Etiquetas de Capacidades

`capabilities` é um array ordenado de etiquetas derivadas da entrada do registo. Os integradores
devem tratá-lo como a resposta legível por máquinas à pergunta «o que pode este fornecedor fazer?»,
em vez de voltarem a consultar os ficheiros de origem TypeScript.

| Etiqueta             | Significado                                                                                   |
| -------------------- | --------------------------------------------------------------------------------------------- |
| `apikey`             | Aceita uma chave de API (`authType` é `apikey` ou `optional`).                                |
| `oauth`              | Utiliza um fluxo OAuth ou de sessão.                                                          |
| `responses`          | Expõe um URL base da API Responses da OpenAI.                                                 |
| `passthrough-models` | Disponibiliza modelos diretamente do upstream em vez de um catálogo estático.                 |
| `custom-executor`    | Executa um executor não predefinido, pelo que permanece no caminho TypeScript.                |
| `sidecar-candidate`  | Reflete `sidecar.eligible` — pode ser considerado com segurança para importação pelo sidecar. |
| `usage-fetch`        | Tem um recuperador de utilização ou quota configurado (`getUsageForProvider`).                |
| `usage-supported`    | A API de utilização aceita este fornecedor (`isSupportedUsageConnection`).                    |

`usage-fetch` destina-se apenas à descoberta. Indica que o OmniRoute sabe como obter a utilização do
fornecedor; não ativa a obtenção, não altera a semântica das quotas nem implica que o
widget de quotas do Dashboard esteja ativado para o fornecedor — esse widget é controlado separadamente por
`USAGE_SUPPORTED_PROVIDERS`. A fonte de verdade é `USAGE_FETCHER_PROVIDERS` em
`open-sse/services/usage/fetcherProviders.ts`.

Essa lista é indexada pelas cadeias de caracteres aceites pelo dispatcher de utilização, pelo que combina ids
canónicos com aliases e é ligeiramente mais extensa do que o número de fornecedores etiquetados: as entradas que
não são fornecedores de chat no registo do manifesto (por exemplo, o fornecedor de pesquisa `firecrawl`
e o fornecedor ACP `amazon-q`) não têm nenhuma entrada no manifesto à qual aplicar a etiqueta.

`usage-supported` indica se as rotas de utilização do servidor e do Dashboard aceitam uma ligação
para o fornecedor. Reflete `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
e `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), ambos controlados por
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). Ao contrário de
`usage-fetch`, é emitido apenas com base no id do fornecedor — a verificação em tempo de execução executa
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` sem resolução de aliases, pelo que o manifesto
mantém a mesma regra. As duas etiquetas têm âmbitos diferentes: 3 fornecedores têm apenas
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) e 1 tem apenas
`usage-supported` (`xiaomi-mimo-token-plan`), pelo que uma não implica a outra.

## Utilização de Sidecars

Os sidecars devem tratar `sidecar.eligible` como um sinal conservador de possível seleção, e não
como uma decisão de encaminhamento incondicional. O primeiro alvo de importação deve ser
os fornecedores que utilizam chaves de API e endpoints estáticos, através do executor predefinido. Os fornecedores com
executores Web personalizados, fluxos de OAuth/sessão, construtores de URL dinâmicos ou configuração de pools
permanecem no mecanismo de contingência em TypeScript até que um sidecar implemente um comportamento
equivalente e a telemetria comprove a paridade.

Fases de migração sugeridas:

1. Gerar e validar o manifesto de plugins de fornecedores a partir do registo TS.
2. Preparar o Bifrost ou o CLIProxyAPI para importar o manifesto de fornecedores com chaves de API/endpoints
   estáticos.
3. Encaminhar os fornecedores elegíveis através do sidecar, controlado por `OMNIROUTE_RELAY_BACKEND`,
   mantendo ativo o mecanismo de contingência em TS.
4. Promover os fornecedores apenas quando a taxa de sucesso, a latência p99, o comportamento de streaming
   e o tratamento de parâmetros não suportados forem equivalentes aos do fluxo TS.
5. Adicionar plugins nativos do sidecar para executores personalizados, uma família de fornecedores de
   cada vez.

## Por Que Não Integrar os Fornecedores Diretamente no Next

O frontend Next não deve ser responsável pela execução dos fornecedores. Deve chamar o limite da API.
O backend pode então decidir se utiliza o executor TypeScript,
o Bifrost, o CLIProxyAPI ou um futuro sidecar nativo. Isto mantém a assinatura de pedidos,
as verificações de listas de permissões, as políticas da base de dados e o comportamento de contingência centralizados antes de qualquer
transferência para o sidecar.
