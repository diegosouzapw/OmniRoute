## Resumo

O OmniRoute suporta agora três modos de encaminhamento para `/api/v1/relay/chat/completions`:

- `ts`: utiliza o encaminhamento TypeScript no processo.
- `bifrost`: força a utilização do gateway Bifrost.
- `auto`: dá preferência ao Bifrost quando este está disponível e, em caso de falha, recorre ao TypeScript.

Quando opera com uma taxa de pedidos elevada (grande número de tokens/dia, débito quase constante), a melhor estratégia consiste em manter o caminho alternativo explícito e rápido, para que o caminho crítico nunca fique bloqueado por um sidecar inativo.

## Comportamento dos modos

- `ts`
  - Menor complexidade operacional.
  - Todo o encaminhamento e validação são executados no Node.
  - A disponibilidade não depende de qualquer sidecar.
- `bifrost`
  - Força o encaminhamento de todos os pedidos através do gateway sidecar.
  - Sem recurso automático a uma alternativa.
  - Útil apenas quando a integridade e a latência do sidecar estão garantidas.
- `auto`
  - O sidecar é utilizado quando está ativado e acessível.
  - As tentativas falhadas acionam cabeçalhos de recurso a alternativa e devolvem o tráfego ao TS, para que o sucesso dos pedidos se mantenha dentro de limites previsíveis.
  - Este modo é a opção mais segura para produção quando o tempo de atividade é mais importante do que um encaminhamento estritamente exclusivo pelo sidecar.

## 9router vs CLIPROXYAPI atualmente

O 9router e a CLIPROXYAPI são integrações que, historicamente, disponibilizam caminhos de compatibilidade para fornecedores a montante.

- O 9router é um caminho incorporado para orquestração a montante e comportamento de compatibilidade.
- A CLIPROXYAPI é uma ponte de API proxy para tráfego ao estilo de CLI / SDK.
- O Bifrost está a ser estabilizado como o caminho externalizado para situações em que é necessário um salto dedicado semelhante a um sidecar e encaminhamento local de baixa latência.

Se está atualmente a comparar o 9router e a CLIPROXYAPI:

- Mantenha a assinatura de pedidos, as verificações da lista de permissões e os controlos de políticas da BD na rota da API antes da transferência.
- Se um fluxo de trabalho necessitar de um comportamento estrito do sidecar e de menor variação por pedido, utilize `OMNIROUTE_RELAY_BACKEND=bifrost`.
- Se necessitar de resiliência do sidecar com degradação controlada durante incidentes, utilize `OMNIROUTE_RELAY_BACKEND=auto`.

## Contrato de fronteira do backend

A fronteira estável do produto é a API de encaminhamento do OmniRoute, não a implementação do dashboard. O dashboard Next.js pode instalar, configurar e supervisionar serviços locais, mas o encaminhamento de pedidos deve entrar através da API de encaminhamento e ser transferido para outro componente atrás dessa fronteira.

Opções de backend a longo prazo:

- Mantenha o encaminhamento TypeScript como caminho de políticas e alternativa no processo. A autenticação, as listas de permissões, a normalização de pedidos, a contabilização e as verificações de segurança permanecem aqui antes de qualquer transferência para o backend.
- Utilize o Bifrost como o sidecar Tier-1 preferencial para elevado débito quando a implementação necessitar de menor variação no encaminhamento, rotação centralizada de fornecedores ou expansão horizontal por várias réplicas do OmniRoute.
- Mantenha o 9router e a CLIPROXYAPI como serviços de compatibilidade incorporados. São executados como processos locais supervisionados e são úteis quando o respetivo comportamento de fornecedor/CLI é o adaptador pretendido, mas não devem tornar-se o motor de encaminhamento Tier-1 predefinido.
- Não permita que o dashboard introduza URLs de serviços arbitrários no caminho crítico. Os URLs fornecidos pela IU são dados de configuração; o código de encaminhamento deve resolver backends registados e sujeitos a verificações de integridade a partir das definições do servidor e do estado do supervisor.
- Atualmente, dê preferência a HTTP por loopback para serviços supervisionados, porque os processos geridos já expõem APIs compatíveis com HTTP, a proteção da rota pode auditar a fronteira e o comportamento de falha/recurso a alternativa é visível nos registos de pedidos. Só vale a pena adicionar futuramente um transporte por SDK ou socket se este reduzir de forma mensurável a latência de encaminhamento p99 sem enfraquecer o isolamento nem a semântica de recurso a alternativa.

Por conseguinte, para uma implementação de débito muito elevado, a resposta predefinida é `auto` com o Bifrost ativado: utilize o sidecar em Go no caminho crítico, preservando simultaneamente o TypeScript como alternativa para manter a taxa de sucesso. Utilize `bifrost` apenas quando um comportamento estritamente exclusivo pelo sidecar for mais importante do que a degradação controlada.

## Orientações para elevado débito

Para RPM/RPS elevados e sustentados, bem como para um SLO de sucesso rigoroso:

1. Utilize `auto` com um período de espera prático e telemetria de falhas.
2. Mantenha a validação a montante e as verificações de chaves de API na fronteira da rota TypeScript.
3. Ative cabeçalhos/contadores explícitos para que os seus alertas detetem a frequência e os motivos do recurso a alternativas.
4. Ajuste os tempos limite do sidecar para falhar rapidamente, em vez de esperar indefinidamente.
5. Mantenha operacionais o reinício automático dos serviços e o ciclo de telemetria de integridade, para que o recurso à alternativa seja verdadeiramente excecional.

## Configuração de referência sugerida

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- Mantenha ativadas nos processadores de rotas as verificações de chaves de API, listas de permissões, sanitização e limites de taxa (estas são sempre executadas antes do reencaminhamento a jusante).
- Exporte métricas de recurso a alternativas a partir do seu proxy inverso e dos registos de pedidos, para que as indisponibilidades do sidecar sejam visíveis no prazo de um minuto.

## Contrato de plugins de fornecedores

Os sidecars devem importar os metadados dos fornecedores através do manifesto de plugins de fornecedores compatível com JSON, em vez de dependerem dos componentes internos do executor TypeScript. Consulte o [Manifesto de Plugins de Fornecedores](./PROVIDER_PLUGIN_MANIFEST.md) para conhecer o contrato de elegibilidade dos sidecars e as fases de migração.
