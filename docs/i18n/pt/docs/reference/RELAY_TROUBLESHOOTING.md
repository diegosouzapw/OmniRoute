Os relays (Vercel, Deno, Cloudflare) terminam a ligação a montante num backend
serverless, para que o OmniRoute possa encaminhar o tráfego de saída a partir
de uma região estável, mantendo a chave da API do fornecedor no servidor. Este
documento aborda os dois modos de falha encontrados pelos operadores em
produção e os procedimentos de recuperação disponibilizados pelo OmniRoute
para cada um.

## Como é armazenada a autenticação do relay

Quando implementa um relay a partir de **Definições → Conjunto de proxies → Implementar relay**, o
processo de implementação armazena o token de autenticação do relay no campo
JSON `notes` do proxy:

- Se `STORAGE_ENCRYPTION_KEY` estiver definida, o token é guardado como
  `relayAuthEnc` (encriptado em repouso com AES).
- Caso contrário, é guardado como texto simples em `relayAuth`.

No momento do pedido, `extractRelayAuth(notes)` devolve a forma que estiver
presente, pelo que o relay continua a funcionar após reinícios.

## Modo de falha 1 — token impossível de desencriptar após a rotação da chave

**Sintoma:** os relays que anteriormente funcionavam passam a devolver erros
`401`/de autenticação a montante após uma rotação de
`STORAGE_ENCRYPTION_KEY` no ambiente ou no gestor de segredos. O blob
`relayAuthEnc` armazenado deixa de poder ser desencriptado, pelo que
`extractRelayAuth` devolve uma cadeia vazia e o relay não envia qualquer
autenticação.

**Recuperação — reparar no local (sem nova implementação):**

1. Abra **Definições → Conjunto de proxies**.
2. As linhas de relays cuja autenticação está em falta apresentam um distintivo
   amarelo `auth missing` e um botão **Reparar**.
3. Clique em **Reparar**. O OmniRoute chama
   `POST /api/settings/proxies/[id]/repair-relay`, que:
   - desencripta `relayAuthEnc` com a chave **atual**,
   - volta a escrever o texto simples `relayAuth` em `notes`,
   - devolve `{ repaired: true, mode: "recovered" }`.

O relay retoma o serviço sem ser necessário voltar a introduzir quaisquer
credenciais de implementação.

Isto só funciona se a `STORAGE_ENCRYPTION_KEY` atual ainda conseguir
desencriptar o blob. Se tiver rodado a chave **sem** uma migração, não é
possível recuperar o blob.

## Modo de falha 2 — token irrecuperável (a chave anterior deixou de estar disponível)

**Sintoma:** clicou em **Reparar** e recebeu
`{ repaired: false, mode: "redeploy", status: 409 }`.

**Recuperação — voltar a implementar:**

Não é possível recuperar o token armazenado com a chave atual. Volte a
implementar o relay a partir da mesma janela modal utilizada originalmente
(menu **Implementar relay** → Vercel / Deno / Cloudflare). O processo de
implementação grava um novo token (encriptado com a chave atual) e o
distintivo `auth missing` da linha desaparece.

Na interface, o próprio botão **Reparar** abre a janela modal de nova
implementação quando o token é irrecuperável, pelo que nunca terá de a procurar
manualmente.

## Modo de falha 3 — relay acessível, mas com problemas de funcionamento

**Sintoma:** o teste do proxy (botão `speed`) indica que o relay está
operacional, mas os pedidos continuam a falhar de forma intermitente.

Verifique os cabeçalhos de reconhecimento do relay devolvidos pela sonda de
teste automático do OmniRoute (consulte **Definições → Conjunto de proxies** e
os contadores `relayTested` / `relayAlive`):

- `x-relay-url` — indica qual backend do relay respondeu.
- `x-relay-mode` — `ts` | `bifrost` | `auto` para esse pedido.
- `x-relay-attempts` — indica quantos saltos de relay foram tentados antes do
  sucesso.
- `x-relay-fallback` — `true` quando o pedido recorreu ao relay TypeScript
  depois de o backend preferencial ter falhado.

Uma taxa elevada de `x-relay-fallback` com um valor baixo de `relayAlive`
significa que o backend sidecar tem problemas de funcionamento e que deve
corrigi-lo ou alterar a estratégia de backend do relay para `ts` (consulte
`RELAY_BACKEND_STRATEGY.md`).

## Referência da API

| Método | Caminho                                   | Corpo                   | Sucesso                                                                                                                                       | Falha                                                                                        |
| ------ | ----------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }` quando derivado novamente; `200 { repaired: false, mode: "noop" }` quando já existe texto simples | `409 { mode: "redeploy" }` irrecuperável; `400` não é um tipo de relay; `404` não encontrado |

A rota de listagem `GET /api/settings/proxies` adiciona a cada item um
`relayInfo: { isRelay, authMissing, repairMode }` sem segredos, para que o
painel possa apresentar a opção de reparação sem nunca expor o token.
