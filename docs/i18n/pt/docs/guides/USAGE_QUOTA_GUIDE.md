> **TL;DR**: O OmniRoute monitoriza a utilização de tokens de cada pedido, calcula o custo, aplica a quota por chave de API e apresenta análises no painel. Este guia explica como tudo funciona.

**Fontes:**

- `open-sse/services/usage.ts` (~70KB) — monitorização principal da utilização
- `src/lib/usageAnalytics.ts` (~10KB) — agregação para o painel
- `src/lib/db/quotaSnapshots.ts` — dados históricos de quotas
- `src/lib/db/usage*.ts` — vários módulos de BD relacionados com a utilização

---

## Visão geral

Cada pedido que passa pelo OmniRoute gera um **registo de utilização** que inclui:

- **Identidade**: qual a chave de API, fornecedor, modelo e combinação
- **Tokens**: tokens de prompt, tokens de conclusão, tokens em cache e total
- **Custo**: montante em USD (calculado a partir dos dados de preços)
- **Temporização**: latência, carimbos de data/hora de início e fim
- **Estado**: sucesso, erro, limitação de taxa, etc.

Estes registos são agregados em **análises**, mantidos como **instantâneos de quota** e utilizados para aplicar **limites de orçamento por chave**.

```
Pedido ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                      análises  quota  faturação
                       (painel) (aplicar) (exportar)
```

## O que é registado

O serviço `usage.ts` captura um **evento de utilização** para cada pedido:

| Campo              | Tipo    | Origem                                                            |
| ------------------ | ------- | ----------------------------------------------------------------- |
| `id`               | string  | UUID gerado durante o registo                                     |
| `apiKeyId`         | string  | A chave de API que iniciou o pedido                               |
| `provider`         | string  | ID do fornecedor (openai, anthropic, etc.)                        |
| `model`            | string  | ID do modelo (gpt-5, claude-opus-4-6, etc.)                       |
| `comboId`          | string? | ID da combinação, caso o encaminhamento use uma combinação        |
| `promptTokens`     | number  | Provenientes da resposta do serviço a montante                    |
| `completionTokens` | number  | Provenientes da resposta do serviço a montante                    |
| `cachedTokens`     | number  | Tokens encontrados em cache (cache de prompts da Anthropic, etc.) |
| `totalTokens`      | number  | prompt + conclusão                                                |
| `costUsd`          | number  | Calculado a partir dos dados de preços                            |
| `latencyMs`        | number  | Duração integral do pedido                                        |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`        |
| `errorClass`       | string? | Classe do erro se o estado != success                             |
| `timestamp`        | string  | ISO 8601 UTC                                                      |
| `metadata`         | object  | Dados personalizados injetados por plugins                        |

### De onde vêm os tokens

Os tokens são extraídos da resposta do fornecedor a montante no **processador de respostas**:

```ts
// De open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

Para fornecedores que não devolvem dados de utilização (alguns fornecedores baseados em cookies Web), o OmniRoute **estima** os tokens utilizando uma heurística de `~4 caracteres por token` (consulte `open-sse/services/autoCombo/pipelineRouter.ts`).

### Tokens em cache

O OmniRoute monitoriza `cached_tokens` separadamente de `prompt_tokens` porque:

- O cache de prompts da Anthropic cobra uma taxa reduzida pelos tokens em cache (10% da taxa normal)
- Alguns fornecedores devolvem `cache_read_input_tokens`, que devem ter um preço diferente
- As análises podem mostrar a **taxa de acertos da cache** = `cached_tokens / prompt_tokens`

## Cálculo de custos

Os custos são calculados a partir dos **dados de preços** sincronizados com o LiteLLM (`src/lib/pricingSync.ts`):

| Modelo            | Entrada $/1M | Saída $/1M | Em cache $/1M |
| ----------------- | ------------ | ---------- | ------------- |
| gpt-5             | $2.50        | $10.00     | —             |
| claude-opus-4-6   | $15.00       | $75.00     | $1.50         |
| claude-sonnet-4-5 | $3.00        | $15.00     | $0.30         |
| gemini-2.5-pro    | $1.25        | $10.00     | —             |

A fórmula de cálculo do custo (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Porquê subtrair os tokens em cache do prompt?** A parte em cache tem um preço separado; aplicar o preço de entrada ao prompt completo resultaria numa contagem excessiva.

### Sincronização de preços

Os dados de preços são sincronizados automaticamente com o LiteLLM através do endpoint `/api/pricing/sync` (acionado pela tarefa cron integrada, e não por uma variável de ambiente acessível ao utilizador):

```bash
# Acionamento manual
curl -X POST http://localhost:20128/api/pricing/sync
```

Para modelos sem dados de preços, o OmniRoute recorre à **estimativa do custo** utilizando tarifas médias internas (obtidas a partir dos dados de preços do LiteLLM).

## Agregação por intervalo de datas

O módulo `usageAnalytics.ts` calcula os widgets do painel a partir dos dados de utilização em bruto. Suporta 7 intervalos de tempo:

| Intervalo | Período                              | Caso de utilização                           |
| --------- | ------------------------------------ | -------------------------------------------- |
| `1d`      | Últimas 24 horas                     | Deteção de picos de custos por hora          |
| `7d`      | Últimos 7 dias                       | Revisão semanal                              |
| `30d`     | Últimos 30 dias                      | Faturação mensal                             |
| `90d`     | Últimos 90 dias                      | Análise trimestral                           |
| `ytd`     | Desde 1 de janeiro do ano atual      | Acompanhamento do orçamento anual            |
| `all`     | Todo o período                       | Estatísticas de todo o período de utilização |
| `custom`  | Início/fim definidos pelo utilizador | Auditorias, consultas ad hoc                 |

### Widgets calculados para o painel

Para qualquer intervalo de datas, a camada de análise calcula:

| Widget                            | Descrição                                                       |
| --------------------------------- | --------------------------------------------------------------- |
| **Cartões de resumo**             | Total de pedidos, custo total, total de tokens, taxa de sucesso |
| **Gráfico de tendências diárias** | Custo + tokens por dia, agrupados por modelo                    |
| **Mapa de calor da atividade**    | Grelha hora do dia × dia da semana, cor = número de pedidos     |
| **Distribuição por modelo**       | Gráfico circular do custo por modelo                            |
| **Distribuição por fornecedor**   | Gráfico de barras dos pedidos por fornecedor                    |
| **Principais chaves de API**      | Tabela das 10 principais chaves por custo                       |
| **Análise de erros**              | Taxa de erros ao longo do tempo, principais classes de erros    |

### Acesso programático

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // registos do histórico de utilização
  "7d",                 // intervalo de tempo: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // mapa de ligações a fornecedores (connectionId → nome da conta)
  {
    startDate: "2025-01-01",  // opcional: para o intervalo "custom"
    endDate: "2025-06-01",   // opcional: para o intervalo "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (cêntimos)
console.log(analytics.byModel[0]);           // { modelo, custo, pedidos, tokens do prompt, tokens da conclusão }

## Aplicação de Quotas

A quota por chave de API é aplicada em dois locais:

1. **Limite flexível** (`quotaWarnAt`): aviso no painel quando a utilização excede o limiar
2. **Limite rígido** (`quotaLimit`): pedido rejeitado com HTTP 429 quando o limite é excedido

### Configuração

```ts
// Por chave de API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — apresentar aviso
  quotaLimit: 10_00,    // $10.00 — bloqueio rígido
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Fluxo de Aplicação

```
Pedido ──▶ quotaCheck()
             │
             ├── Dentro do limite?  ──▶ permitir
             │
             └── Acima do limite?  ──▶ 429 Demasiados Pedidos
                                      com o cabeçalho Retry-After
```

### Instantâneos de Quota

A tabela `quotaSnapshots` armazena o **estado histórico das quotas** para análise de tendências:

| Campo | Descrição |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | A chave que está a ser monitorizada |
| `window` | "day" | "week" | "month" |
| `used` | Custo utilizado nesta janela (cêntimos) |
| `limit` | O limite (cêntimos) |
| `resetAt` | Quando a janela é reposta |
| `createdAt` | Quando o instantâneo foi obtido |

São obtidos instantâneos **em cada pedido** que utilize um custo > 0, sendo estes utilizados para:

- Apresentar a barra de progresso da quota no painel
- Apresentar gráficos de tendências de quota dos últimos 30 dias
- Acionar alertas quando a utilização se aproxima do limite

## Retenção e Limpeza

Os dados de utilização aumentam cerca de 1–10 KB por pedido. Em grande escala, este volume pode ser significativo.

### Definições de Retenção

A retenção do histórico de utilização é configurada através das Definições da Base de Dados na interface ou através de `/api/settings/database`.

Por predefinição, o histórico de utilização é mantido durante **90 dias**.

### Limpeza

Os registos antigos são limpos por `src/lib/db/cleanup.ts`:

- Acionado pelo processo cron em segundo plano
- Elimina os registos de `usage_history` mais antigos do que o período definido na configuração de retenção `usageHistory`

### Estimativa de Armazenamento

| Taxa de pedidos     | Armazenamento por 30 dias | Armazenamento por 90 dias |
| ------------------- | ------------------------- | ------------------------- |
| 100 pedidos/dia     | ~3 MB                     | ~9 MB                     |
| 1 000 pedidos/dia   | ~30 MB                    | ~90 MB                    |
| 10 000 pedidos/dia  | ~300 MB                   | ~900 MB                   |
| 100 000 pedidos/dia | ~3 GB                     | ~9 GB                     |

Para tráfego muito elevado, considere:

- Reduzir o período de retenção através das Definições da Base de Dados
- Utilizar `aggregated_metrics` em vez de registos em bruto (apenas para análise)

## Sugestões de Otimização de Custos

### 1. Utilize o Modelo Adequado

```bash
# Resposta rápida — utilizar um modelo económico e rápido
curl -d '{"model":"auto/fast","messages":[...]}'

# Tarefa complexa — utilizar um modelo de qualidade
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Ative a Colocação em Cache

A colocação em cache de prompts da Anthropic permite poupar **90% em contexto repetido**:

```ts
// A colocação em cache é automática — basta incluir o mesmo prompt de sistema extenso
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Será colocado em cache automaticamente
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Utilize Compressão

A compressão RTK + Caveman permite poupar **15–95% em sessões com utilização intensiva de ferramentas**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Defina Quotas por Chave

Defina sempre `quotaLimit` para evitar custos descontrolados:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Limite de 10 $/mês
```

### 5. Audite os Maiores Consumidores

Utilize o painel ou **`/api/usage/analytics`** para agrupar por chave de API e ordenar por custo:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Resolução de Problemas

### "O custo é superior ao esperado"

1. Consulte **`/api/usage/analytics?groupBy=model`** — identifique o modelo dispendioso
2. Consulte **`/api/usage/analytics?groupBy=apiKey`** — identifique o maior consumidor
3. Confirme se os dados de preços estão atualizados: `POST /api/pricing/sync`

### "Registos em falta"

- Verifique as definições de retenção da BD em Painel → Base de Dados → Limpeza — os registos antigos são eliminados pela tarefa de limpeza periódica (`src/lib/db/cleanup.ts`)
- Verifique se existem erros em `src/lib/db/usage*.ts` — as falhas de escrita na BD são registadas, mas não são apresentadas
- Confirme se o pedido chegou efetivamente a `chatCore` — verifique o encaminhamento combinado

### "A quota não está a ser aplicada"

- Verifique a definição `quotaLimit` da chave
- Confirme se `quotaWindow` está definido corretamente
- Procure registos `quotaSnapshots` — estes devem ser criados em cada pedido
