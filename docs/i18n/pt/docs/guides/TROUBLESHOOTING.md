## Referência rápida

**É a primeira vez que utiliza o OmniRoute?** Comece aqui — estas soluções resolvem 90% dos problemas:

| Vejo isto                     | O que significa                                      | O que fazer                                                                                    |
| ----------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| "Can't connect"               | O OmniRoute não está em execução                     | Execute `omniroute` ou `docker restart omniroute`                                              |
| "Invalid API key"             | A sua chave está errada ou expirou                   | Copie novamente a chave a partir do site do fornecedor                                         |
| "Rate limit exceeded"         | Está a enviar demasiados pedidos                     | Aguarde 1 minuto ou utilize `model: "auto"` para uma alternativa automática                    |
| "Quota exceeded"              | Esgotou a sua quota gratuita/paga                    | Ligue mais fornecedores ou utilize fornecedores gratuitos (Kiro, Pollinations)                 |
| "Slow responses"              | O fornecedor está ocupado ou longe                   | Utilize `model: "auto/fast"` ou ligue um fornecedor mais rápido (Groq, Cerebras)               |
| "Wrong provider used"         | `auto` escolheu um fornecedor diferente              | É normal! `auto` escolhe o melhor. Force um fornecedor específico com `model: "openai/gpt-4o"` |
| "502 Bad Gateway"             | O fornecedor está indisponível                       | Aguarde e tente novamente ou utilize `model: "auto"` para mudar de fornecedor                  |
| "401 Unauthorized"            | As suas credenciais estão erradas                    | Verifique a sua chave de API ou autentique-se novamente com OAuth                              |
| "omniroute is not recognized" | Faltam os módulos globais do node no PATH do Windows | Adicione o prefixo global do npm ao PATH do Windows. Encontre-o com `npm config get prefix`.   |
| "429 Too Many Requests"       | O limite de pedidos foi atingido                     | Aguarde 1 minuto ou ligue mais fornecedores                                                    |

## Resolução de problemas detalhada

---

### Limitação de pedidos em fornecedores gratuitos (429 / 400 / 401)

**Sintoma**: Ao utilizar `model: "auto"` com fornecedores gratuitos/sem autenticação (opencode, auggie, etc.), recebe ocasionalmente `HTTP 429`, `400` ou `401` em vez de respostas. Os pedidos são bem-sucedidos quando volta a tentar o mesmo pedido momentos depois, mas a automatização (tarefas cron, agentes, scripts) falha logo no primeiro erro.

**Causa principal**: Três modos de falha independentes acumulam-se:

1. **Limite de pedidos do fornecedor (`429`)**: Os níveis gratuitos podem impor uma quota por intervalo. Uma sequência de chamadas paralelas esgota-a, pelo que o pedido seguinte é recusado até o intervalo ser reposto.
2. **Modelo avariado no passthrough (`400`/`401`)**: Os grupos `auto/*` podem incluir modelos passthrough do `opencode` que estão registados no catálogo, mas não têm credenciais ativas (por exemplo, `oc/north-mini-code-free` → `401`). O encaminhador automático tenta um, falha e o erro é propagado antes de a alternativa ser acionada.
3. **Amplificação da simultaneidade (`429` sob carga)**: Quando várias sessões de agente/cron acedem a `auto` ao mesmo tempo, a taxa agregada de pedidos excede o que os fornecedores gratuitos toleram, pelo que chamadas legítimas são assinaladas como abusivas.

**Correção verificada (comunicada pela comunidade, 2026-08-10)**: ajuste três variáveis de ambiente para que a rotação, a simultaneidade e as alternativas absorvam a instabilidade do nível gratuito, em vez de falharem devido a ela:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # muda para outro modelo/fornecedor após 400/401 (ignora modelos passthrough avariados)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # limite explícito de admissão de pedidos pesados (por predefinição, não definido: sem limite de contagem de pedidos; consulte a nota abaixo)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # espera limitada mais longa por capacidade para pedidos pesados, em vez de um 503 imediato que permite nova tentativa
```

Defina estas variáveis no ambiente do processo do OmniRoute (o daemon, por exemplo, através do plist do LaunchAgent ou de `systemctl edit`) e, em seguida, reinicie o OmniRoute. A opção de rotação é, por si só, a medida com maior impacto: converte uma falha definitiva numa nova tentativa transparente através de um fornecedor operacional do grupo.

**Nota**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` limita o número de pedidos pesados — de contexto longo — executados em simultâneo; o limite é uma barreira de admissão, não um limitador de pedidos do fornecedor. **Atualização sobre a propagação de erros 503:** esta variável já não é definida por predefinição (agora só é aplicada quando configurada explicitamente, como acima) — em vez disso, a admissão de pedidos pesados é controlada por um orçamento de bytes calculado automaticamente (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), que se ajusta com base no limite real de memória do anfitrião. Assim, uma implementação nova deverá ter muito menos rejeições `503 chat_admission_busy` sem que seja necessário definir esta variável; defini-la explicitamente aqui continua a funcionar exatamente como documentado. As substituições explícitas do orçamento de bytes são limitadas ao intervalo entre 8 MiB e 2 GiB. Um erro `413 body_exceeds_budget` não é transitório: aumente esse orçamento de bytes, reduza `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ou aumente o limite de memória do processo. Uma rejeição `inflight_bytes_budget` resulta de contenção temporária e permite uma nova tentativa. A limitação de pedidos por fornecedor (`open-sse/services/rateLimitManager.ts`) é gerida separadamente por `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` e `RATE_LIMIT_AUTO_ENABLE` — consulte `.env.example`.

**Como verificar se funcionou**: execute o seu agente/cron duas vezes em rápida sucessão e confirme que ambas as execuções são bem-sucedidas. Antes da correção, a segunda execução normalmente devolve `429`/`401`. Após a correção, as falhas (caso existam) são repetidas de forma transparente e a chamada é concluída. Também pode executar `curl /monitoring/health` e observar o campo `rateLimitedUntil` nas ligações aos fornecedores e o campo `circuitBreakers.providerBreakers[].state` dos fornecedores afetados — o estado é um de `CLOSED`, `DEGRADED`, `OPEN` ou `HALF_OPEN` (consulte `src/shared/utils/circuitBreaker.ts`), e um fornecedor que continue a falhar passará por `CLOSED → DEGRADED → OPEN` antes de a janela de reposição permitir uma tentativa de diagnóstico (`HALF_OPEN`).

**Se continuar a ver 429**: a conta ativa desse fornecedor esgotou efetivamente a sua _quota_ (não apenas o limite de pedidos). Adicione uma segunda conta para o mesmo fornecedor no painel do OmniRoute → Fornecedores → Contas, ou combine-a com outro fornecedor gratuito (por exemplo, `routeway`, `auggie`). A rotação só ajuda com erros transitórios de limite de pedidos/400/401; o esgotamento total da quota requer uma segunda credencial ou um fornecedor diferente.

**Se vir 403 em modelos de visão (`auto/vision`, `bazaarlink/*`)**: a conta associada não tem um plano pago que inclua visão ou a chave de API não possui permissões suficientes. Verifique no painel do fornecedor se o âmbito da chave inclui visão/multimodal ou associe uma conta de um nível pago e mantenha-a como destino para visão.

## Avisos do npm install (ERESOLVE / peer / deprecated)

Ao executar `npm install -g omniroute`, poderá ver uma série de avisos, como `npm warn ERESOLVE`, notificações de dependências peer e mensagens `deprecated`. **Estes avisos são esperados e inofensivos.** A instalação foi bem-sucedida se vir `added <N> packages` no resultado.

Para suprimir os avisos de resolução de dependências peer, utilize a forma de instalação suportada pelo OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` suprime apenas os avisos `ERESOLVE` e as notificações de dependências peer. As notificações de descontinuação continuam visíveis porque têm origem em pacotes transitivos de terceiros; não indicam que a instalação falhou.

Os avisos resultam de intervalos de dependências peer desatualizados em pacotes de terceiros que o OmniRoute não controla:

1. **`marked-terminal` requer `marked >=1 <16`, mas foi encontrado `marked@18`** — na prática, funciona sem problemas; o intervalo peer do projeto upstream está simplesmente desatualizado.
2. **`deprecated prebuild-install@7.1.3`** — um auxiliar transitivo para obtenção de binários nativos. Não é
   utilizado para instalar a associação de transporte `wreq-js` fixada e não indica que a configuração
   de transporte do fornecedor de cookies Web tenha falhado.

**Não é necessária qualquer ação** — os avisos não podem ser totalmente silenciados sem criar forks dos pacotes upstream.

## Gemini Web e Playwright Chromium

Se um pedido do Gemini Web devolver `503` com uma mensagem a indicar que o Playwright Chromium
não está instalado, o pacote npm está presente, mas falta o binário do browser.
O Playwright mantém deliberadamente as transferências de browsers separadas da instalação
do pacote npm, pelo que esta resposta é esperada até o browser ser instalado.

Para uma instalação global do npm, instale o Chromium a partir do diretório do pacote
OmniRoute, para que a cache do browser pertença à mesma instalação do Playwright:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Reinicie o OmniRoute após a instalação e, em seguida, tente novamente o pedido do Gemini Web. Se
executar o OmniRoute a partir de uma imagem Docker, utilize a imagem `-web` (ou o destino de compilação
`runner-web`), que inclui o Chromium e as respetivas dependências; a imagem base
não os inclui.

| Problema                                                    | Solução                                                                                                                                                                             |

| A estratégia de encaminhamento não é guardada               | Atualize para a versão v3.x mais recente (a correção do esquema Zod para a persistência das definições foi disponibilizada em versões anteriores)                                   |
| Falha no início de sessão / página em branco                | Verifique a versão do Node.js — consulte [Compatibilidade com o Node.js](#nodejs-compatibility) abaixo                                                                              |

| "fetch failed" do proxy                                     | Certifique-se de que a configuração do proxy está definida no nível correto — consulte [Problemas de proxy](#proxy-issues) abaixo                                                   |

## Falsos positivos do antivírus

<a name="antivirus-false-positives"></a>

### O Avast/AVG coloca o `README.md` em quarentena com `MD:HttpRequest-inf[Susp]`

**Trata-se de um falso positivo. Nada está infetado e não é necessária qualquer ação.**

O Avast e o AVG executam uma heurística que sinaliza ficheiros de texto simples/Markdown que contêm muitas
ligações semelhantes a pedidos HTTP. O `README.md` do OmniRoute é incluído no pacote npm (está
indicado em `package.json` → `files`), pelo que, numa instalação global, é colocado em
`node_modules/omniroute/README.md` — e contém cerca de 15 exemplos `http://localhost:20128/...` (os
endpoints HTTP/SSE do MCP, o URL `.well-known` do A2A e excertos de `curl`). Esta densidade de ligações é
suficiente para acionar a heurística.

Se isto começou apenas recentemente: a natureza do ficheiro não mudou. A tabela de endpoints
do README aumentou (foram adicionados MCP HTTP + SSE + A2A), assim como o número de exemplos de `curl`, o que
fez com que ultrapassasse o limiar.

O ficheiro é documentação inerte, sem qualquer conteúdo executável. Pode restaurá-lo da
quarentena em segurança.

**O que fazer:**

1. **Parar as notificações** — exclua o diretório de instalação no seu antivírus
   (Avast: Definições → Exceções), adicionando o caminho global de `node_modules` e/ou o
   diretório de dados do OmniRoute (`~/.omniroute/`).
2. **Comunicar o falso positivo** — <https://www.avast.com/false-positive-file-form.php>,
   anexando o `README.md` colocado em quarentena. Esta é a correção que ajuda toda a gente, uma vez que é
   a heurística do fornecedor que está a reagir excessivamente a um ficheiro de texto.

**Porque não “corrigimos” isto do nosso lado:** todos os exemplos utilizam `http://localhost`, e
localhost não pode utilizar `https` sem os inconvenientes dos certificados autoassinados. Adulterar a documentação para
contornar a heurística de um fornecedor prejudicaria todos os leitores para satisfazer um erro do analisador.

### O Kaspersky sinaliza a aplicação para computador como `PDM:Trojan.Win32.Generic`

**Trata-se de um falso positivo de uma heurística comportamental. Nada está infetado.** O prefixo
`PDM:` do Kaspersky significa que o veredito provém do seu Proactive Defense Module (System Watcher),
que avalia o que o instalador _faz_, em vez de o comparar com software malicioso conhecido. Quando
é acionado, o Kaspersky “reverte” toda a instalação — eliminando ficheiros que já tinha
gravado — pelo que a aplicação fica danificada ou desaparece.

Os ficheiros sinalizados são componentes padrão de dependências declaradas e de código aberto incluídas com a
aplicação para computador, por exemplo:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` e
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), a biblioteca de automatização
  do navegador utilizada para iniciar sessão nos fornecedores dentro da aplicação e para conversas suportadas pelo navegador.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — o binding nativo fixado do `wreq-js`, utilizado para HTTP com impressão digital do navegador em fornecedores
  que utilizam cookies da Web (`<arch>` é `x64` ou `arm64`).

**Porque é acionado:** o instalador do Windows **ainda não está assinado digitalmente**, pelo que um instalador NSIS
não assinado não tem qualquer reputação e as heurísticas comportamentais são executadas com agressividade máxima. Em conjunto
com uma DLL nativa incluída e centenas de ficheiros `.js` gravados em
`%LOCALAPPDATA%\Programs\OmniRoute` (incluindo diretórios de pacotes com hashes como sufixos, provenientes da
compilação autónoma do Next.js), isto é suficiente para acionar a heurística. A assinatura de código está planeada;
até ser implementada, isto pode repetir-se em novas versões.

**O que fazer:**

1. **Verifique primeiro a sua transferência** (para excluir a possibilidade de um ficheiro adulterado). Cada versão publica
   `latest.yml`, cujo campo `sha512` (base64) abrange o instalador
   `OmniRoute.Setup.<version>.exe`. No PowerShell, a partir da pasta que contém o instalador:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   O resultado tem de corresponder a `latest.yml` → `sha512`. Se não corresponder, elimine o ficheiro e
   volte a transferi-lo apenas a partir da [página de versões do GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Restaurar + excluir** — restaure da quarentena os itens removidos durante a reversão e adicione uma exclusão
   para `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Definições → Ameaças e Exclusões);
   depois, reinstale.
3. **Comunicar o falso positivo** — <https://opentip.kaspersky.com/>. Os relatórios de falsos
   positivos enviados pelos utilizadores aceleram efetivamente a inclusão na lista de permissões.

## Compatibilidade com Node.js

<a name="nodejs-compatibility"></a>

### A página de início de sessão falha ou apresenta o erro "Module self-registration"

**Causa:** Está a executar uma versão do Node.js fora do nível mínimo de execução segura aprovado pelo OmniRoute. O caso mais comum é a utilização de uma versão de correção mais antiga do Node 22 ou 24, inferior ao nível mínimo de segurança corrigido exigido pelo OmniRoute.

**Sintomas:**

- A página de início de sessão apresenta um ecrã em branco ou um erro do servidor
- A consola apresenta `Error: Module did not self-register` ou erros semelhantes de associações nativas
- A página de início de sessão apresenta uma **faixa de aviso laranja** com a sua versão do Node, caso o ambiente de execução não cumpra a política de segurança suportada

**Correção:**

1. Instale uma versão LTS suportada do Node.js (recomendado: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Verifique a sua versão: `node --version` deve apresentar `v24.0.0` ou uma versão posterior da linha LTS 24.x
3. Reinstale o OmniRoute: `npm install -g omniroute`
4. Reinicie: `omniroute`

> **Versões seguras suportadas:** `>=22.22.2 <23` ou `>=24.0.0 <27`. O Node.js 24.x LTS (Krypton) e o Node.js 26 são totalmente suportados.

### npm v11+: `better-sqlite3` não instalado (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Causa:** O npm v11 (incluído no Node.js 24+) bloqueia, por predefinição, os scripts de instalação de dependências
opcionais. Como o `better-sqlite3` está listado em `optionalDependencies`
e requer compilação nativa (`node-gyp rebuild`), o npm ignora-o silenciosamente.

**Sintomas:**

- O servidor falha ao arrancar com `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` apresenta "No such file or directory"
- `npm ls better-sqlite3` apresenta `(empty)`

**Correção:**

1. Aprove os scripts de instalação e reinstale:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Em alternativa, instale manualmente o binário pré-compilado:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Verifique se funciona: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Causa:** Após uma instalação global com `npm install -g omniroute`, o binário nativo do `better-sqlite3` dentro do pacote pode ter sido compilado para uma arquitetura ou ABI do Node.js diferente da que está a ser executada localmente. Isto é comum no macOS (tanto em Apple Silicon como em Intel) quando o binário pré-compilado não corresponde ao seu ambiente.

**Sintomas:**

- O servidor falha imediatamente ao arrancar com um erro `dlopen`
- O erro contém `slice is not valid mach-o file`
- Exemplo completo:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Correção — volte a compilar para o seu ambiente local (não é necessário reverter para uma versão anterior do Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Nota:** Isto recompila a associação nativa para a sua versão local do Node.js e arquitetura de CPU, resolvendo a incompatibilidade binária. O intervalo de versões do ambiente de execução oficialmente suportado é **`>=22.22.2 <23` ou `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` em `src/shared/utils/nodeRuntimeSupport.ts`, alinhado com o campo `engines` do `package.json`). O Node.js 24.x LTS (Krypton) e o Node.js 26 são totalmente suportados com o `better-sqlite3` v12.x.

## Problemas de proxy

<a name="proxy-issues"></a>

### A validação do fornecedor apresenta "fetch failed"

**Causa:** Anteriormente, o endpoint de validação da chave da API (`POST /api/providers/validate`) ignorava a configuração do proxy, causando falhas em ambientes que exigem encaminhamento através de proxy.

**Correção (v3.5.5+):** Este problema está agora corrigido. As validações dos fornecedores são encaminhadas através de `runWithProxyContext`, respeitando automaticamente as definições de proxy ao nível do fornecedor e as definições globais.

### A verificação do estado do token falha com "fetch failed"

**Causa:** A atualização de tokens OAuth em segundo plano não estava a resolver a configuração do proxy para cada ligação.

**Correção (v3.5.5+):** O agendador da verificação do estado dos tokens resolve agora a configuração do proxy para cada ligação antes de tentar a atualização. Atualize para a v3.5.5+.

### O proxy SOCKS5 devolve "invalid onRequestStart method"

**Causa:** No Node.js 22, o dispatcher do undici@8 é incompatível com a implementação incorporada de `fetch()` do Node.

**Correção (v3.5.5+):** O OmniRoute utiliza agora a função `fetch()` do próprio undici quando está ativo um dispatcher de proxy, garantindo um comportamento consistente. Atualize para a v3.5.5+.

### Proxy MITM em WSL: as aplicações de ambiente de trabalho no anfitrião Windows não são intercetadas

**Causa:** O proxy MITM e o respetivo certificado de AC são instalados no ambiente onde o OmniRoute é executado. Em WSL, esse ambiente é o sistema convidado Linux, enquanto as aplicações de IA para ambiente de trabalho (Kiro, Trae, Copilot, Zed, …) são executadas no anfitrião Windows. As aplicações do anfitrião não confiam no repositório de certificados do sistema convidado e não encaminham o tráfego através do proxy do sistema convidado, pelo que a interceção das aplicações de ambiente de trabalho não é efetuada.

**Recomendação:** Execute o OmniRoute nativamente no mesmo SO das aplicações de ambiente de trabalho que pretende intercetar (Windows para aplicações Windows; de igual modo para macOS/Linux). Manter o OmniRoute no WSL enquanto se visa as aplicações do anfitrião exige confiar manualmente no certificado de AC gerado no anfitrião Windows e configurar as definições de rede/proxy de cada aplicação do anfitrião para utilizarem o endpoint de proxy do WSL — uma configuração frágil e não suportada.

## Problemas dos fornecedores

### "Language model did not provide messages"

**Causa:** A quota do fornecedor esgotou-se.

**Correção:**

1. Verifique o monitorizador de quota no painel
2. Utilize uma combinação com níveis de contingência
3. Mude para um nível mais barato/gratuito

### Limitação da taxa

**Causa:** A quota da subscrição esgotou-se.

**Correção:**

- Adicione uma contingência: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Utilize GLM/MiniMax como alternativa económica

### Token OAuth expirado

O OmniRoute atualiza os tokens automaticamente. Se os problemas persistirem:

1. Painel → Fornecedor → Voltar a ligar
2. Elimine e volte a adicionar a ligação do fornecedor

### Várias contas Kiro: a segunda conta invalida a primeira

**Causa:** O backend do Kiro impõe uma única sessão ativa por registo de cliente OIDC.
Quando duas contas partilham o mesmo cliente registado (ligações importadas antes da v3.8.0),
a atualização do token de uma conta invalida o token de atualização da outra.

**Correção (v3.8.0+):** Volte a importar as ligações afetadas.
A partir da v3.8.0, cada nova ligação Kiro criada através de **Importar token**,
**início de sessão social com Google/GitHub** ou **Importação automática** regista automaticamente
o seu próprio cliente OIDC dedicado. Assim, a ligação fica totalmente isolada e a atualização de uma
conta não afeta qualquer outra conta.

As ligações que foram importadas _antes_ da v3.8.0 não incluem um registo de cliente
por ligação. Essas ligações continuam a utilizar o endpoint de atualização de autenticação social partilhado.
Para obter isolamento, elimine a ligação antiga em Painel → Fornecedores e volte a adicioná-la
através de qualquer um dos três fluxos de importação.

Para obter todos os detalhes e instruções passo a passo para adicionar duas contas Kiro lado a lado,
consulte [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Problemas da Cloud

### Erros de Sincronização com a Cloud

1. Verifique se `BASE_URL` aponta para a instância em execução (por exemplo, `http://localhost:20128`)
2. Verifique se `CLOUD_URL` aponta para o endpoint da cloud (por exemplo, `https://omniroute.dev`)
3. Mantenha os valores `NEXT_PUBLIC_*` alinhados com os valores do lado do servidor

### `stream=false` na Cloud Devolve 500

**Sintoma:** `Unexpected token 'd'...` no endpoint da cloud para chamadas sem streaming.

**Causa:** O serviço a montante devolve uma carga SSE enquanto o cliente espera JSON.

**Solução alternativa:** Utilize `stream=true` para chamadas diretas à cloud. O runtime local inclui uma alternativa de SSE→JSON.

### A Cloud Indica que Está Ligada, mas Apresenta "Invalid API key"

1. Crie uma nova chave no painel local (`/api/keys`)
2. Execute a sincronização com a cloud: Ativar Cloud → Sincronizar Agora
3. As chaves antigas/não sincronizadas podem continuar a devolver `401` na cloud

## Problemas do Docker

### IPv6 / Reposição da Ligação no Docker

<a name="docker-ipv6"></a>

**Sintomas:** `curl http://localhost:20128/v1/models` devolve `curl: (56) Recv failure: Connection reset by peer`. O painel e os endpoints não autenticados funcionam, mas os endpoints autenticados falham — parece um problema de autenticação, mas não é.

**Causa:** `docker run -p 20128:20128` publica tanto em `0.0.0.0` (IPv4) como em `::` (IPv6), mas o processo dentro do contentor escuta apenas em IPv4. Em anfitriões onde `localhost` é resolvido primeiro como `::1`, a ligação chega à porta IPv6 publicada sem nenhum processo à escuta por trás → reposição da ligação.

**Correção:**

1. **Diagnóstico rápido:** Execute `curl -4 http://localhost:20128/v1/models`. Se funcionar com `-4`, mas falhar sem esta opção, existe uma incompatibilidade de associação IPv6.
2. **Correção permanente:** Associe explicitamente ao IPv4 utilizando `-p 127.0.0.1:20128:20128` no comando `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Isto força a associação IPv4 e também evita expor o proxy em todas as interfaces do anfitrião.

## Depuração

### Ativar Ficheiros de Registo

Defina `APP_LOG_TO_FILE=true` no ficheiro `.env`. Os registos da aplicação são escritos em `logs/`.
Os artefactos dos pedidos são armazenados em `${DATA_DIR}/call_logs/` quando o pipeline de registos de chamadas está
ativado nas definições.
Quando a captura do pipeline está ativada, defina `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` para omitir
as cargas dos fragmentos de streaming ou ajuste `CALL_LOG_PIPELINE_MAX_SIZE_KB` para alterar o limite dos artefactos em KB.

### Verificar o Estado dos Fornecedores

```bash
# Painel de estado
http://localhost:20128/dashboard/health

# Verificação do estado da API
curl http://localhost:20128/api/monitoring/health
```

### Armazenamento do Runtime

- Estado principal: `${DATA_DIR}/storage.sqlite` (fornecedores, combinações, aliases, chaves, definições)
- Utilização: tabelas SQLite em `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + `${DATA_DIR}/call_logs/` opcional
- Registos da aplicação: `<repo>/logs/...` (quando `APP_LOG_TO_FILE=true`)
- Artefactos dos registos de chamadas: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` quando o pipeline de registos de chamadas está ativado

A ação **Limpar histórico** da página Registos de Pedidos limpa `call_logs`, o
`request_detail_logs` legado e o diretório local de artefactos `${DATA_DIR}/call_logs/`.

## Problemas do Circuit Breaker

### Fornecedor bloqueado no estado OPEN

Quando o circuit breaker de um fornecedor está no estado OPEN, os pedidos são bloqueados até o período de espera terminar.

**Correção:**

1. Aceda a **Painel → Definições → Resiliência**
2. Verifique o cartão do circuit breaker do fornecedor afetado
3. Clique em **Repor Tudo** para limpar todos os circuit breakers ou aguarde até o período de espera terminar
4. Antes de efetuar a reposição, confirme se o fornecedor está realmente disponível

### O fornecedor continua a acionar o circuit breaker

Se um fornecedor entrar repetidamente no estado OPEN:

1. Consulte **Painel → Estado → Estado dos Fornecedores** para verificar o padrão de falhas
2. Aceda a **Definições → Resiliência → Perfis de Fornecedor** e aumente o limiar de falhas
3. Verifique se o fornecedor alterou os limites da API ou exige uma nova autenticação
4. Analise a telemetria da latência — uma latência elevada pode causar falhas por tempo limite

## Depuração do Tradutor

Utilize **Painel → Tradutor** para depurar problemas de tradução de formatos:

| Modo                   | Quando utilizar                                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------- |
| **Ambiente de Testes** | Compare os formatos de entrada/saída lado a lado — cole um pedido com falha para ver como é traduzido |
| **Testador de Chat**   | Envie mensagens em direto e inspecione o payload completo do pedido/resposta, incluindo os cabeçalhos |
| **Banco de Testes**    | Execute testes em lote em várias combinações de formatos para identificar as traduções com problemas  |
| **Monitor em Direto**  | Observe o fluxo de pedidos em tempo real para detetar problemas de tradução intermitentes             |

### Problemas comuns de formato

- **As etiquetas de raciocínio não aparecem** — Verifique se o fornecedor de destino suporta raciocínio e confirme a definição do orçamento de raciocínio
- **As chamadas de ferramentas desaparecem** — Algumas traduções de formatos podem remover campos não suportados; verifique no modo Ambiente de Testes
- **O prompt do sistema está em falta** — O Claude e o Gemini processam os prompts do sistema de formas diferentes; verifique o resultado da tradução
- **O SDK devolve uma cadeia de caracteres simples em vez de um objeto** — Resolvido na v1.x; o sanitizador de respostas remove campos não padronizados (`x_groq`, `usage_breakdown`, etc.) que causam falhas de validação Pydantic no SDK da OpenAI. Se continuar a observar este problema na v3.x+, comunique-o.
- **GLM/ERNIE rejeita a função `system`** — Resolvido na v1.x; o normalizador de funções combina automaticamente as mensagens do sistema com as mensagens do utilizador para modelos incompatíveis. Se continuar a observar este problema na v3.x+, comunique-o.
- **A função `developer` não é reconhecida** — Resolvido na v1.x; é convertida automaticamente em `system` para fornecedores que não sejam a OpenAI. Se continuar a observar este problema na v3.x+, comunique-o.
- **`json_schema` não funciona com o Gemini** — Resolvido na v1.x; `response_format` é agora convertido em `responseMimeType` + `responseSchema` do Gemini. Se continuar a observar este problema na v3.x+, comunique-o.

## Definições de resiliência

### A limitação automática de taxa não é acionada

- A limitação automática de taxa aplica-se apenas a fornecedores com chave de API (não a OAuth/subscrição)
- Verifique se a limitação automática de taxa está ativada em **Definições → Resiliência → Perfis de fornecedores**
- Verifique se o fornecedor devolve códigos de estado `429` ou cabeçalhos `Retry-After`

### Ajustar o recuo exponencial

Os perfis de fornecedores suportam estas definições:

- **Atraso base** — Tempo de espera inicial após a primeira falha (predefinição: 1s)
- **Atraso máximo** — Limite máximo do tempo de espera (predefinição: 30s)
- **Multiplicador** — Quanto aumentar o atraso por cada falha consecutiva (predefinição: 2x)

### Prevenção do efeito de manada

Quando muitos pedidos simultâneos atingem um fornecedor com limitação de taxa, o OmniRoute utiliza mutex + limitação automática de taxa para serializar os pedidos e evitar falhas em cascata. Isto é automático para fornecedores com chave de API.

### Os pedidos de chat falham com 503 / chat_admission_busy

**Sintomas:**

- O endpoint de conclusões de chat devolve uma resposta `503` repetível, cujo código de erro é
  `chat_admission_busy`.
- A resposta inclui `Retry-After`. Desde a #12135, o valor deriva da ocupação observada — o maior valor entre a janela `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` durante a qual o pedido já
  esperou e o tempo durante o qual as concessões pesadas atuais estiveram retidas — arredondado para cima para
  segundos inteiros e limitado a 60. Num mecanismo de admissão inativo, mantém os limites mínimos históricos: 2 segundos no
  caminho baseado em bytes e 1 segundo no caminho baseado na estrutura (que também inclui
  `reason: "structure_limit"`).
- Isto pode acontecer enquanto outro chat pesado ou uma resposta de transmissão de longa duração ainda está
  em curso.

O corpo da resposta baseada em bytes é:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

A resposta baseada na estrutura utiliza o mesmo tipo e código, com a mensagem
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
e `reason: "structure_limit"`.
Com os limiares predefinidos, um pedido é estruturalmente pesado quando tem pelo menos `200` mensagens,
pelo menos `64` ferramentas ou pelo menos `32,000` tokens estimados, ou quando a estimativa estrutural limitada
esgota os respetivos limites de `10,000` nós visitados ou de profundidade `12`.

**Causa:** Esta é uma rejeição deliberada de carga dentro do OmniRoute, não uma falha de um fornecedor a montante.
Cada processo utiliza uma proteção local ao processo para reservar capacidade pesada limitada antes de reter
e analisar o corpo de um pedido grande. Uma concessão pesada permanece retida durante todo o ciclo de vida de uma resposta
SSE.

**Propagação de #503:** antes desta correção, a proteção limitava a simultaneidade a uma CONTAGEM fixa de pedidos
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, predefinição `1`), independentemente da memória do anfitrião, pelo que a
distribuição em leque dos agentes de programação (vários subagentes/CLIs, corpos habitualmente > 256 KB) reduzia a simultaneidade
efetiva para ~1 e devolvia erros 503 sob uma carga perfeitamente normal. Agora, a proteção ajusta-se automaticamente: é controlada
por um orçamento de BYTES de ingestão derivado automaticamente (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), dimensionado a partir do
limite real de memória do processo, e também consulta um sinal de pressão sobre os recursos em tempo real — pelo que
apenas rejeita carga quando o anfitrião está realmente sob pressão de memória, e não simplesmente porque chegou mais do que um
pedido pesado em simultâneo. O antigo limite de contagem (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) continua
a ser respeitado, mas apenas se o definir explicitamente.

Quando a capacidade está ocupada, um pedido pesado aguarda primeiro até
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (predefinição `2000`; `0` desativa a espera) pela libertação de uma vaga
antes de responder com o erro `503` repetível. A espera limitada existe para que os clientes orientados para agentes
(OpenCode, Claude Code, Cursor) que distribuem subpedidos pesados em simultâneo serializem a rajada,
em vez de consumirem todo o orçamento de novas tentativas em rejeições imediatas e falharem a meio da tarefa.
A ocupação atual das concessões pesadas, o orçamento de bytes determinado e a gravidade da pressão em tempo real são
apresentados em `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — verifique-os antes de alterar qualquer variável de ambiente.
Definições → Resiliência → Fila de pedidos → Pedidos simultâneos não controla isto; essa definição
controla um mecanismo separado de fila de pedidos do fornecedor.

**Correção:**

1. Tente novamente primeiro. Os clientes devem respeitar `Retry-After` e utilizar recuo, em vez de repetirem
   imediatamente o pedido.
2. Verifique `/api/monitoring/health` → `chatAdmission` antes de ajustar qualquer definição. `countCapEnabled:
false` e um `maxInflightBytes` generoso significam que o orçamento derivado automaticamente já está a cumprir a sua
   função; uma `pressureSeverity` de `high`/`critical` significa que o anfitrião tem realmente pouca memória —
   isso não pode ser corrigido por uma variável de ambiente de admissão; requer mais RAM ou uma carga de trabalho menor.
3. Apenas se `/api/monitoring/health` mostrar que o orçamento derivado automaticamente é realmente demasiado pequeno para
   o seu anfitrião (raro — já é dimensionado desde contentores até sistemas bare-metal), substitua-o diretamente através de
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, em vez de recorrer ao antigo limite de contagem de pedidos.

Consulte a [referência de variáveis de ambiente](../reference/ENVIRONMENT.md#4-security--authentication)
para conhecer as definições de admissão oficiais.

## Taxonomia opcional de falhas de RAG / LLM (16 problemas)

Alguns utilizadores do OmniRoute colocam o gateway à frente de stacks de RAG ou de agentes. Nessas configurações, é comum observar um padrão estranho: o OmniRoute parece estar operacional (fornecedores disponíveis, perfis de encaminhamento corretos, sem alertas de limite de taxa), mas a resposta final continua errada.

Na prática, estes incidentes têm normalmente origem no pipeline de RAG a jusante, e não no próprio gateway.

Se pretender um vocabulário comum para descrever essas falhas, pode utilizar o WFGY ProblemMap, um recurso de texto externo com licença MIT que define dezasseis padrões recorrentes de falhas de RAG / LLM. De forma geral, abrange:

- desvio da recuperação e limites de contexto incorretos
- índices e repositórios vetoriais vazios ou desatualizados
- incompatibilidade entre embeddings e semântica
- problemas na composição de prompts e na janela de contexto
- colapso lógico e respostas excessivamente confiantes
- falhas em cadeias longas e na coordenação de agentes
- desvios de memória e de função em sistemas multiagente
- problemas de implementação e de ordem de inicialização

A ideia é simples:

1. Ao investigar uma resposta incorreta, registe:
   - tarefa e pedido do utilizador
   - combinação de rota ou fornecedor no OmniRoute
   - qualquer contexto de RAG utilizado a jusante (documentos recuperados, chamadas de ferramentas, etc.)
2. Associe o incidente a um ou dois números do WFGY ProblemMap (`No.1` … `No.16`).
3. Guarde o número no seu próprio painel, manual de operações ou sistema de acompanhamento de incidentes, junto aos registos do OmniRoute.
4. Utilize a página correspondente do WFGY para decidir se é necessário alterar a sua stack de RAG, o recuperador ou a estratégia de encaminhamento.

O texto integral e as instruções concretas estão disponíveis aqui (licença MIT, apenas texto):

[README do WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Pode ignorar esta secção se não executar pipelines de RAG ou de agentes atrás do OmniRoute.

## Problemas conhecidos da v3.8.0

Problemas específicos da versão v3.8.0 e as respetivas soluções temporárias atuais. Se for disponibilizada uma correção num patch posterior, a entrada será atualizada ou removida.

### Falhas de autenticação da Devin CLI

**Sintomas:**

- "Devin CLI não encontrada" ou "falha na autenticação" ao invocar ferramentas suportadas pelo Devin
- A verificação da CLI em tempo de execução indica `installed=false`

**Causas:**

- `CLI_DEVIN_BIN` aponta para um caminho que não existe
- A Devin CLI não está instalada no anfitrião

**Correção:**

1. Instale a Devin CLI para a sua plataforma
2. Defina `CLI_DEVIN_BIN=/usr/local/bin/devin` (ou o caminho real) em `.env`
3. Reinicie o OmniRoute e volte a testar em **Painel → Ferramentas de CLI**

### Período de suspensão do modelo bloqueado (reposição manual)

**Sintomas:**

- Um modelo permanece listado como estando em período de suspensão mesmo depois de o prazo de validade ter expirado
- Os pedidos continuam a ignorar o modelo no encaminhamento combinado, apesar de a indicação de data e hora estar no passado

**Reposição manual:**

- **Painel:** **Definições → Períodos de suspensão dos modelos** → clique em **Reativar** no cartão afetado
- **API:** `DELETE /api/resilience/model-cooldowns` com cabeçalhos de autenticação de gestão

### A ligação ao fornecedor Command Code falha com 403

**Sintomas:**

- Erro 403 ao testar a ligação ao fornecedor Command Code
- O cartão do fornecedor apresenta "não autorizado" após uma nova adição

**Causa:** O fluxo OAuth não foi concluído (a chamada de retorno não foi recebida ou o token não foi guardado).

**Correção:**

- Execute `omniroute providers` a partir da CLI para acionar novamente o fluxo OAuth, ou
- Volte a executar o OAuth em **Painel → Fornecedores → Command Code → Voltar a ligar**

### O ModelScope devolve períodos de suspensão 429 agressivos

**Sintomas:**

- Períodos de suspensão muito curtos ou imediatos no ModelScope após uma pequena sequência de pedidos
- O encaminhamento combinado ignora o ModelScope mais cedo do que o esperado

**Causa:** O ModelScope emite cabeçalhos `Retry-After` específicos do fornecedor. A v3.8.0 inclui tratamento dedicado para esses cabeçalhos, pelo que as versões anteriores os interpretam incorretamente como indicações genéricas de limite de taxa.

**Correção:**

- Certifique-se de que está a utilizar a v3.8.0 ou posterior
- Verifique se a opção `useUpstream429BreakerHints` está ativada em **Definições → Resiliência**

### OMNIROUTE_WS_BRIDGE_SECRET em falta em produção

**Sintomas:**

- Erro 401 em todos os pedidos da ponte WebSocket de Codex/Responses ao executar num anfitrião remoto de produção
- O handshake da ponte WebSocket é encerrado imediatamente após a ligação

**Causa:** A variável de ambiente `OMNIROUTE_WS_BRIDGE_SECRET` está em falta no ambiente de produção.

**Correção:**

1. Gere um segredo aleatório: `openssl rand -hex 32`
2. Defina `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` no ambiente do servidor de produção (e em qualquer cliente que comunique com a ponte)
3. Reinicie o OmniRoute

### Responses API: modo em segundo plano degradado para síncrono

**Sintomas:**

- Aviso registado: `background mode degraded to synchronous`
- Um pedido com `background: true` devolve uma resposta síncrona normal em vez de um identificador de tarefa em segundo plano

**Causa:** A v3.8.0 degrada intencionalmente `background: true` na Responses API para execução síncrona, emitindo simultaneamente um aviso. A execução assíncrona completa em segundo plano será disponibilizada no futuro.

**Correção:**

- Ajuste o cliente para efetuar a chamada sem `background`, ou
- Aguarde por uma versão posterior que inclua o modo assíncrono completo em segundo plano (acompanhe o registo de alterações)

## Arranque Lento / Tempo Limite de Disponibilidade

Se a CLI apresentar `⚠ Server did not respond within 60s`, mas o servidor estiver
efetivamente a funcionar, o tempo disponível para a verificação de disponibilidade é demasiado curto para o seu ambiente.

Isto acontece frequentemente no Windows (antivírus, monitores do sistema de ficheiros) ou em contentores
com cargas de trabalho pesadas durante o arranque.

**Solução — aumente o tempo disponível:**

```bash
# Através de uma variável de ambiente (mantém-se entre arranques):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minutos
omniroute serve

# Através de uma opção da CLI (utilização única):
omniroute serve --ready-timeout 180000
```

O valor predefinido é 60 000 ms (60 s). O aviso é meramente informativo; o servidor
continua a iniciar em segundo plano e ficará acessível assim que o arranque estiver concluído.

Consulte [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) para obter todos os
detalhes sobre `OMNIROUTE_READY_TIMEOUT_MS`.
