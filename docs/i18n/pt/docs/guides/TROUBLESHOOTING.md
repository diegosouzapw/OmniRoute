## Referência Rápida

**É a primeira vez que utiliza o OmniRoute?** Comece aqui — estas soluções resolvem 90% dos problemas:

| Vejo isto                           | O que significa                                | O que fazer                                                                                    |
| ----------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| "Não é possível ligar"              | O OmniRoute não está em execução               | Execute `omniroute` ou `docker restart omniroute`                                              |
| "Chave de API inválida"             | A sua chave está errada ou expirou             | Volte a copiar a chave a partir do site do fornecedor                                          |
| "Limite de pedidos excedido"        | Está a enviar demasiados pedidos               | Aguarde 1 minuto ou utilize `model: "auto"` para recorrer automaticamente a uma alternativa    |
| "Quota excedida"                    | Esgotou a sua quota gratuita/paga              | Ligue mais fornecedores ou utilize fornecedores gratuitos (Kiro, Pollinations)                 |
| "Respostas lentas"                  | O fornecedor está ocupado ou encontra-se longe | Utilize `model: "auto/fast"` ou ligue um fornecedor mais rápido (Groq, Cerebras)               |
| "Foi utilizado o fornecedor errado" | `auto` escolheu um fornecedor diferente        | É normal! `auto` escolhe o melhor. Force um fornecedor específico com `model: "openai/gpt-4o"` |
| "502 Bad Gateway"                   | O fornecedor está indisponível                 | Aguarde e tente novamente ou utilize `model: "auto"` para mudar de fornecedor                  |
| "401 Unauthorized"                  | As suas credenciais estão erradas              | Verifique a sua chave de API ou volte a autenticar-se com OAuth                                |
| "429 Too Many Requests"             | Limite de pedidos atingido                     | Aguarde 1 minuto ou ligue mais fornecedores                                                    |

## Resolução de Problemas Detalhada

---

### Limitação de Pedidos em Fornecedores Gratuitos (429 / 400 / 401)

**Sintoma**: Ao utilizar `model: "auto"` com fornecedores gratuitos/sem autenticação (opencode, auggie, etc.), recebe de forma intermitente `HTTP 429`, `400` ou `401` em vez de respostas. Os pedidos são bem-sucedidos quando volta a tentar o mesmo pedido instantes depois, mas a automatização (tarefas cron, agentes, scripts) falha logo no primeiro erro.

**Causa principal**: Três modos de falha independentes acumulam-se:

1. **Limite de pedidos do fornecedor (`429`)**: Os níveis gratuitos podem impor uma quota por intervalo. Uma sequência de chamadas paralelas esgota-a, pelo que o pedido seguinte é recusado até o intervalo ser reposto.
2. **Modelo com problemas em passthrough (`400`/`401`)**: Os conjuntos `auto/*` podem incluir modelos passthrough do `opencode` que estão registados no catálogo, mas não têm credenciais ativas (por exemplo, `oc/north-mini-code-free` → `401`). O encaminhador automático tenta um deles, falha e o erro é propagado antes de o recurso a uma alternativa ser acionado.
3. **Amplificação da simultaneidade (`429` sob carga)**: Quando várias sessões de agentes/cron acedem a `auto` em simultâneo, a taxa agregada de pedidos excede o que os fornecedores gratuitos toleram, fazendo com que chamadas legítimas sejam assinaladas como abusivas.

**Correção verificada (comunicada pela comunidade, 2026-08-10)**: ajuste três variáveis de ambiente para que a rotação, a simultaneidade e o recurso a alternativas absorvam a instabilidade do nível gratuito em vez de falharem devido a ela:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # muda para outro modelo/fornecedor em caso de 400/401 (ignora modelos passthrough com problemas)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # limite explícito de admissão de pedidos pesados (por predefinição, não está definido: sem limite de número de pedidos; consulte a nota abaixo)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # espera limitada mais longa por capacidade para pedidos pesados, em vez de um 503 imediato que permite nova tentativa
```

Defina estas variáveis no ambiente do processo do OmniRoute (o daemon, por exemplo, através do plist do LaunchAgent ou de `systemctl edit`) e, em seguida, reinicie o OmniRoute. O sinalizador de rotação é a medida individual com maior impacto: transforma uma falha definitiva numa nova tentativa transparente através de um fornecedor operacional do conjunto.

**Nota**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` limita quantos pedidos pesados — com contexto longo — são executados em simultâneo; o limite é um controlo de admissão, não um limitador de pedidos do fornecedor. **Atualização sobre a propagação de erros #503:** esta variável já não é definida por predefinição (agora só estabelece um limite quando é explicitamente configurada, como acima) — em vez disso, a admissão de pedidos pesados é controlada por um orçamento de bytes calculado automaticamente (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), que se ajusta com base no limite real de memória do anfitrião. Assim, uma implementação nova deverá apresentar muito menos rejeições `503 chat_admission_busy` sem que seja necessário definir esta variável; defini-la explicitamente aqui continua a funcionar exatamente como documentado. As substituições explícitas do orçamento de bytes são limitadas ao intervalo entre 8 MiB e 2 GiB. Um erro `413 body_exceeds_budget` não é temporário: aumente esse orçamento de bytes, reduza `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ou aumente o limite de memória do processo. Uma rejeição `inflight_bytes_budget` é uma contenção temporária e continua a permitir uma nova tentativa. A limitação de pedidos por fornecedor (`open-sse/services/rateLimitManager.ts`) é gerida separadamente por `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` e `RATE_LIMIT_AUTO_ENABLE` — consulte `.env.example`.

**Como verificar se funcionou**: execute o seu agente/cron duas vezes em rápida sucessão e confirme que ambas as execuções são bem-sucedidas. Antes da correção, a segunda execução apresenta normalmente um erro `429`/`401`. Depois da correção, as falhas (caso existam) são repetidas de forma transparente e a chamada é concluída. Também pode executar `curl /monitoring/health` e observar o campo `rateLimitedUntil` nas ligações dos fornecedores, bem como `circuitBreakers.providerBreakers[].state` para os fornecedores afetados — o estado é um de `CLOSED`, `DEGRADED`, `OPEN` ou `HALF_OPEN` (consulte `src/shared/utils/circuitBreaker.ts`), e um fornecedor que continue a falhar passará de `CLOSED → DEGRADED → OPEN` antes de a janela de reposição permitir a passagem de uma verificação (`HALF_OPEN`).

**Se ainda vir 429**: a conta ativa desse fornecedor esgotou efetivamente a respetiva _quota_ (não apenas o limite de pedidos). Adicione uma segunda conta para o mesmo fornecedor no painel do OmniRoute → Providers → Accounts, ou combine com outro fornecedor gratuito (por exemplo, `routeway`, `auggie`). A rotação apenas ajuda com erros transitórios de limite de pedidos/400/401; o esgotamento total da quota requer uma segunda credencial ou um fornecedor diferente.

**Se vir 403 em modelos de visão (`auto/vision`, `bazaarlink/*`)**: a conta associada não dispõe de um plano pago que inclua visão, ou a chave de API não tem permissões suficientes. Verifique no painel do fornecedor se o âmbito da chave inclui visão/multimodalidade, ou associe uma conta de um nível pago e mantenha-a como destino para visão.

## Avisos do npm install (ERESOLVE / peer / deprecated)

Ao executar `npm install -g omniroute`, poderá ver uma série de avisos como `npm warn ERESOLVE`, notificações sobre dependências peer e mensagens `deprecated`. **Estes avisos são esperados e inofensivos.** A instalação foi bem-sucedida se vir `added <N> packages` no resultado.

Os avisos são causados por intervalos desatualizados de dependências peer em pacotes de terceiros que a OmniRoute não controla:

1. **`marked-terminal` requer `marked >=1 <16`, mas foi encontrado `marked@18`** — na prática, funciona sem problemas; o intervalo peer do projeto upstream está apenas desatualizado.
2. **`deprecated prebuild-install@7.1.3`** — um utilitário transitivo para obter binários nativos. Não é
   utilizado para instalar a ligação de transporte `wreq-js` fixada e não indica que a configuração
   do transporte do fornecedor de cookies Web tenha falhado.

**Não é necessária qualquer ação** — os avisos não podem ser totalmente ocultados sem criar forks dos pacotes upstream.

## Falsos Positivos de Antivírus

<a name="antivirus-false-positives"></a>

### O Avast/AVG coloca o `README.md` em quarentena com `MD:HttpRequest-inf[Susp]`

**Este é um falso positivo. Nada está infetado e não é necessária qualquer ação.**

O Avast e o AVG executam uma heurística que sinaliza ficheiros de texto simples/Markdown que contêm muitas
ligações semelhantes a pedidos HTTP. O `README.md` do OmniRoute é incluído no pacote npm (está
indicado em `package.json` → `files`), pelo que é colocado em `node_modules/omniroute/README.md` numa
instalação global — e contém cerca de 15 exemplos `http://localhost:20128/...` (os endpoints
HTTP/SSE do MCP, o URL `.well-known` do A2A e excertos de `curl`). Essa densidade de ligações é
suficiente para acionar a heurística.

Se isto só começou recentemente: o tipo de ficheiro não mudou. O README expandiu a sua
tabela de endpoints (foram adicionados MCP HTTP + SSE + A2A) e passou a incluir mais exemplos de `curl`, o que fez
com que ultrapassasse o limiar.

O ficheiro é documentação inerte, sem qualquer conteúdo executável. Pode restaurá-lo
da quarentena em segurança.

**O que fazer:**

1. **Parar as notificações** — exclua o diretório de instalação no seu antivírus
   (Avast: Definições → Exceções), adicionando o caminho global de `node_modules` e/ou o
   diretório de dados do OmniRoute (`~/.omniroute/`).
2. **Comunicar o falso positivo** — <https://www.avast.com/false-positive-file-form.php>,
   anexando o `README.md` colocado em quarentena. Esta é a correção que ajuda todos, uma vez que é
   a heurística do fornecedor que está a reagir excessivamente a um ficheiro de texto.

**Porque não «corrigimos» isto do nosso lado:** todos os exemplos utilizam `http://localhost`, e
o localhost não pode utilizar `https` sem o inconveniente de certificados autoassinados. Adulterar a documentação para
contornar a heurística de um fornecedor prejudicaria todos os leitores para satisfazer um erro do scanner.

### O Kaspersky sinaliza a aplicação para computador como `PDM:Trojan.Win32.Generic`

**Este é um falso positivo de uma heurística comportamental. Nada está infetado.** O prefixo
`PDM:` do Kaspersky significa que o veredito provém do respetivo Módulo de Defesa Proativa (System Watcher),
que avalia o que o instalador _faz_ em vez de o comparar com software malicioso conhecido. Quando
é acionado, o Kaspersky «reverte» toda a instalação — eliminando ficheiros que já tinha
escrito — pelo que a aplicação acaba danificada ou em falta.

Os ficheiros que sinaliza são componentes padrão de dependências de código aberto declaradas, incluídas com a
aplicação para computador, por exemplo:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` e
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), a biblioteca de automatização de browsers
  utilizada para o início de sessão nos fornecedores dentro da aplicação e para conversas suportadas pelo browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — a vinculação nativa `wreq-js` com versão fixa, utilizada para HTTP com impressão digital do browser em fornecedores
  baseados em cookies da Web (`<arch>` é `x64` ou `arm64`).

**Porque é acionado:** o instalador do Windows **ainda não está assinado digitalmente**, pelo que um instalador NSIS
não assinado não tem qualquer reputação e as heurísticas comportamentais são executadas com a máxima agressividade. Em conjunto
com uma DLL nativa incluída e centenas de ficheiros `.js` escritos em
`%LOCALAPPDATA%\Programs\OmniRoute` (incluindo diretórios de pacotes com sufixos de hash da
compilação autónoma do Next.js), isto é suficiente para acionar a heurística. A assinatura de código está planeada;
até ser implementada, isto pode repetir-se em novas versões.

**O que fazer:**

1. **Verifique primeiro a sua transferência** (permite excluir a possibilidade de um ficheiro adulterado). Cada versão publica
   `latest.yml`, cujo campo `sha512` (base64) abrange o instalador `OmniRoute.Setup.<version>.exe`.
   No PowerShell, a partir da pasta que contém o instalador:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   O resultado tem de corresponder a `latest.yml` → `sha512`. Se não corresponder, elimine o ficheiro e
   volte a transferi-lo apenas a partir da [página de versões do GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Restaurar + excluir** — restaure os itens revertidos a partir da quarentena e adicione uma exclusão
   para `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Definições → Ameaças e Exclusões);
   depois, reinstale.
3. **Comunicar o falso positivo** — <https://opentip.kaspersky.com/>. Os relatórios de falsos positivos
   enviados pelos utilizadores aceleram realmente a inclusão na lista de permissões.

## Compatibilidade com Node.js

<a name="nodejs-compatibility"></a>

### A página de início de sessão bloqueia ou apresenta o erro "Module self-registration"

**Causa:** Está a executar uma versão do Node.js fora do limite mínimo de execução segura aprovado pelo OmniRoute. O caso mais comum é a utilização de uma versão de correção mais antiga do Node 22 ou 24, abaixo do limite de segurança corrigido exigido pelo OmniRoute.

**Sintomas:**

- A página de início de sessão apresenta um ecrã em branco ou um erro do servidor
- A consola apresenta `Error: Module did not self-register` ou erros semelhantes de vinculação nativa
- A página de início de sessão apresenta uma **faixa de aviso laranja** com a sua versão do Node se o ambiente de execução estiver fora da política segura suportada

**Correção:**

1. Instale uma versão LTS suportada do Node.js (recomendado: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Verifique a sua versão: `node --version` deverá apresentar `v24.0.0` ou uma versão mais recente da linha LTS 24.x
3. Reinstale o OmniRoute: `npm install -g omniroute`
4. Reinicie: `omniroute`

> **Versões seguras suportadas:** `>=22.22.2 <23` ou `>=24.0.0 <27`. O Node.js 24.x LTS (Krypton) e o Node.js 26 são totalmente suportados.

### npm v11+: `better-sqlite3` não instalado (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Causa:** O npm v11 (incluído com o Node.js 24+) bloqueia, por predefinição, os scripts de instalação de dependências
opcionais. Uma vez que `better-sqlite3` está listado em `optionalDependencies`
e requer compilação nativa (`node-gyp rebuild`), o npm ignora-o silenciosamente.

**Sintomas:**

- O servidor bloqueia durante o arranque com `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` apresenta "No such file or directory"
- `npm ls better-sqlite3` apresenta `(empty)`

**Correção:**

1. Aprove os scripts de instalação e reinstale:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Em alternativa, instale manualmente o binário pré-compilado:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Verifique se funciona: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Causa:** Após um `npm install -g omniroute` global, o binário nativo de `better-sqlite3` incluído no pacote poderá ter sido compilado para uma arquitetura ou ABI do Node.js diferente da que está a ser executada localmente. Isto é comum no macOS (tanto em Apple Silicon como em Intel) quando o binário pré-compilado não corresponde ao seu ambiente.

**Sintomas:**

- O servidor falha imediatamente durante o arranque com um erro `dlopen`
- O erro contém `slice is not valid mach-o file`
- Exemplo completo:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Correção — recompile para o seu ambiente local (não é necessário mudar para uma versão anterior do Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Nota:** Isto recompila a vinculação nativa para a sua versão local do Node.js e arquitetura de CPU, resolvendo a incompatibilidade do binário. O intervalo de ambientes de execução oficialmente suportado é **`>=22.22.2 <23` ou `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` em `src/shared/utils/nodeRuntimeSupport.ts`, alinhado com o campo `engines` de `package.json`). O Node.js 24.x LTS (Krypton) e o Node.js 26 são totalmente suportados com o `better-sqlite3` v12.x.

## Problemas de Proxy

<a name="proxy-issues"></a>

### A validação do fornecedor apresenta "fetch failed"

**Causa:** O endpoint de validação da chave da API (`POST /api/providers/validate`) ignorava anteriormente a configuração do proxy, causando falhas em ambientes que exigem encaminhamento através de proxy.

**Correção (v3.5.5+):** Este problema já foi corrigido. A validação do fornecedor é encaminhada através de `runWithProxyContext`, respeitando automaticamente as definições de proxy globais e ao nível do fornecedor.

### A verificação do estado do token falha com "fetch failed"

**Causa:** A atualização de tokens OAuth em segundo plano não resolvia a configuração do proxy para cada ligação.

**Correção (v3.5.5+):** O agendador de verificação do estado dos tokens passa agora a resolver a configuração do proxy para cada ligação antes de tentar a atualização. Atualize para a v3.5.5+.

### O proxy SOCKS5 devolve "invalid onRequestStart method"

**Causa:** No Node.js 22, o dispatcher do undici@8 é incompatível com a implementação integrada de `fetch()` do Node.

**Correção (v3.5.5+):** O OmniRoute utiliza agora a função `fetch()` do próprio undici quando está ativo um dispatcher de proxy, garantindo um comportamento consistente. Atualize para a v3.5.5+.

### Proxy MITM no WSL: as aplicações de ambiente de trabalho no anfitrião Windows não são intercetadas

**Causa:** O proxy MITM e o respetivo certificado de CA são instalados no ambiente onde o OmniRoute é executado. No WSL, esse ambiente é o sistema Linux convidado, enquanto as aplicações de IA para ambiente de trabalho (Kiro, Trae, Copilot, Zed, …) são executadas no anfitrião Windows. As aplicações do anfitrião não confiam no repositório de certificados do sistema convidado nem encaminham o tráfego através do proxy de sistema do convidado, pelo que a interceção das aplicações de ambiente de trabalho não é ativada.

**Recomendação:** Execute o OmniRoute nativamente no mesmo sistema operativo das aplicações de ambiente de trabalho que pretende intercetar (Windows para aplicações Windows; o mesmo se aplica ao macOS/Linux). Manter o OmniRoute no WSL enquanto se pretende intercetar aplicações do anfitrião exige confiar manualmente no certificado de CA gerado no anfitrião Windows e apontar as definições de rede/proxy de cada aplicação do anfitrião para o endpoint de proxy do WSL — uma configuração frágil e não suportada.

## Problemas de Fornecedores

### "Language model did not provide messages"

**Causa:** A quota do fornecedor esgotou-se.

**Correção:**

1. Verifique o monitor de quotas no painel
2. Utilize uma combinação com níveis de recurso
3. Mude para um nível mais económico/gratuito

### Limitação de Taxa

**Causa:** A quota da subscrição esgotou-se.

**Correção:**

- Adicione uma alternativa: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Utilize o GLM/MiniMax como alternativa económica

### Token OAuth Expirado

O OmniRoute atualiza automaticamente os tokens. Se os problemas persistirem:

1. Painel → Fornecedor → Voltar a ligar
2. Elimine e volte a adicionar a ligação ao fornecedor

### Várias contas Kiro: a segunda conta invalida a primeira

**Causa:** O backend do Kiro impõe uma única sessão ativa por registo de cliente OIDC.
Quando duas contas partilham o mesmo cliente registado (ligações importadas antes da v3.8.0),
a atualização do token de uma conta invalida o token de atualização da outra.

**Correção (v3.8.0+):** Volte a importar as ligações afetadas.
A partir da v3.8.0, cada nova ligação Kiro criada através de **Importar Token**,
**início de sessão social com Google/GitHub** ou **Importação Automática** regista automaticamente
o seu próprio cliente OIDC dedicado. Assim, a ligação fica totalmente isolada e a atualização
de uma conta não afeta qualquer outra conta.

As ligações importadas _antes_ da v3.8.0 não incluem um registo de cliente
por ligação. Essas ligações continuam a utilizar o endpoint partilhado de atualização da autenticação social.
Para obter isolamento, elimine a ligação antiga em Painel → Fornecedores e volte a adicioná-la
através de qualquer um dos três fluxos de importação.

Para obter todos os detalhes e instruções passo a passo para adicionar duas contas Kiro lado a lado,
consulte [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Problemas do Docker

### IPv6 do Docker / Reposição da ligação

<a name="docker-ipv6"></a>

**Sintomas:** `curl http://localhost:20128/v1/models` devolve `curl: (56) Recv failure: Connection reset by peer`. O dashboard e os endpoints não autenticados funcionam, mas os endpoints autenticados falham — parece um problema de autenticação, mas não é.

**Causa:** `docker run -p 20128:20128` publica tanto em `0.0.0.0` (IPv4) como em `::` (IPv6), mas o processo no interior do contentor escuta apenas em IPv4. Em hosts onde `localhost` é resolvido primeiro como `::1`, a ligação é encaminhada para a porta IPv6 publicada sem qualquer serviço a escutar por trás → reposição da ligação.

**Correção:**

1. **Diagnóstico rápido:** Execute `curl -4 http://localhost:20128/v1/models`. Se funcionar com `-4`, mas falhar sem essa opção, existe uma incompatibilidade de associação IPv6.
2. **Correção permanente:** Associe explicitamente ao IPv4 utilizando `-p 127.0.0.1:20128:20128` no comando `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Isto força a associação IPv4 e também evita expor o proxy em todas as interfaces do host.

4. Analise a telemetria de latência — uma latência elevada pode causar falhas por tempo limite

## Definições de resiliência

### A limitação automática de taxa não é acionada

- A limitação automática de taxa aplica-se apenas a fornecedores com chave de API (não a OAuth/subscrições)
- Verifique se **Definições → Resiliência → Perfis de fornecedores** tem a limitação automática de taxa ativada
- Verifique se o fornecedor devolve códigos de estado `429` ou cabeçalhos `Retry-After`

### Ajustar o recuo exponencial

Os perfis de fornecedores suportam estas definições:

- **Atraso base** — Tempo de espera inicial após a primeira falha (predefinição: 1s)
- **Atraso máximo** — Limite máximo do tempo de espera (predefinição: 30s)
- **Multiplicador** — Quanto aumentar o atraso por cada falha consecutiva (predefinição: 2x)

### Prevenção do efeito de manada

Quando muitos pedidos simultâneos atingem um fornecedor sujeito a limitação de taxa, o OmniRoute utiliza mutex + limitação automática de taxa para serializar os pedidos e evitar falhas em cascata. Isto é automático para fornecedores com chave de API.

### Os pedidos de chat falham com 503 / chat_admission_busy

**Sintomas:**

- O endpoint de conclusões de chat devolve uma resposta `503` que pode ser repetida e cujo código de erro é
  `chat_admission_busy`.
- A resposta inclui `Retry-After`. Desde a #12135, o valor deriva da ocupação observada
  — o maior entre a janela `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` que o pedido já
  aguardou e o tempo durante o qual as atuais concessões de grande consumo estiveram retidas — arredondado para cima para segundos
  inteiros e limitado a 60. Num mecanismo de admissão inativo, mantém os mínimos históricos: 2 segundos no
  fluxo baseado em bytes e 1 segundo no fluxo baseado em estrutura (que também inclui
  `reason: "structure_limit"`).
- Isto pode ocorrer enquanto outro chat de grande consumo ou uma resposta de streaming de longa duração ainda
  está em curso.

O corpo da resposta baseada em bytes é:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

A resposta baseada em estrutura utiliza o mesmo tipo e código, com a mensagem
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
e `reason: "structure_limit"`.
Com os limiares predefinidos, um pedido é estruturalmente pesado quando tem pelo menos `200` mensagens,
pelo menos `64` ferramentas ou pelo menos `32,000` tokens estimados, ou quando a estimativa limitada da estrutura
esgota os seus limites de `10,000` nós visitados ou de profundidade `12`.

**Causa:** Trata-se de uma redução deliberada de carga no OmniRoute, e não de uma falha do fornecedor a montante.
Cada processo utiliza uma proteção local ao processo para reservar uma capacidade limitada para pedidos de grande consumo antes de reter
e analisar o corpo de um pedido grande. Uma concessão de grande consumo permanece retida durante toda a duração de uma resposta
SSE.

**#503-fanout:** antes desta correção, a proteção limitava a simultaneidade a uma CONTAGEM fixa de pedidos
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, predefinição `1`), independentemente da memória do anfitrião, pelo que a
distribuição de agentes de programação (vários subagentes/CLIs, com corpos habitualmente > 256 KB) reduzia-se a uma
simultaneidade efetiva de ~1 e devolvia erros 503 sob uma carga perfeitamente normal. Agora, a proteção ajusta-se
automaticamente: é controlada por um orçamento de ingestão em BYTES derivado automaticamente (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), dimensionado a partir do
limite real de memória do processo, e também consulta um sinal em tempo real de pressão sobre os recursos — pelo que
só reduz a carga quando o anfitrião está efetivamente sob pressão de memória, e não apenas porque chegou mais do que um
pedido pesado em simultâneo. O antigo limite de contagem (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) continua a ser
respeitado, mas apenas se o definir explicitamente.

Quando a capacidade está ocupada, um pedido de grande consumo aguarda primeiro até
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (predefinição `2000`; `0` desativa a espera) que fique disponível um lugar
antes de responder com o erro `503`, que pode ser repetido. A espera limitada existe para que os clientes do tipo agente
(OpenCode, Claude Code, Cursor) que distribuem simultaneamente subpedidos pesados serializem o pico
em vez de esgotarem todo o respetivo orçamento de novas tentativas em rejeições imediatas e falharem a meio da tarefa.
A ocupação atual das concessões de grande consumo, o orçamento de bytes determinado e a gravidade da pressão em tempo real são
disponibilizados em `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — verifique estes valores antes de alterar qualquer variável de ambiente.
Definições → Resiliência → Fila de pedidos → Pedidos simultâneos não controla este comportamento; essa definição
controla um mecanismo separado de fila de pedidos do fornecedor.

**Correção:**

1. Tente novamente primeiro. Os clientes devem respeitar `Retry-After` e utilizar recuo, em vez de repetirem
   imediatamente o pedido.
2. Verifique `/api/monitoring/health` → `chatAdmission` antes de ajustar qualquer parâmetro. `countCapEnabled:
false` e um `maxInflightBytes` generoso significam que o orçamento derivado automaticamente já está a cumprir a sua
   função; um `pressureSeverity` de `high`/`critical` significa que o anfitrião tem efetivamente pouca memória —
   isso não pode ser corrigido através de uma variável de ambiente de admissão; requer mais RAM ou uma carga de trabalho menor.
3. Apenas se `/api/monitoring/health` mostrar que o orçamento derivado automaticamente é efetivamente demasiado pequeno para
   o seu anfitrião (raro — já se ajusta desde contentores até sistemas físicos), substitua-o diretamente com
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, em vez de recorrer ao antigo limite de contagem de pedidos.

Consulte a [referência de variáveis de ambiente](../reference/ENVIRONMENT.md#4-security--authentication)
para obter as definições de admissão oficiais.

## Taxonomia opcional de falhas de RAG / LLM (16 problemas)

Alguns utilizadores do OmniRoute colocam o gateway à frente de sistemas de RAG ou de agentes. Nessas configurações, é comum observar um padrão estranho: o OmniRoute parece estar saudável (fornecedores operacionais, perfis de encaminhamento corretos, sem alertas de limite de pedidos), mas a resposta final continua a estar errada.

Na prática, estes incidentes têm geralmente origem no pipeline de RAG a jusante, e não no próprio gateway.

Se pretender um vocabulário comum para descrever essas falhas, pode utilizar o WFGY ProblemMap, um recurso de texto externo com licença MIT que define dezasseis padrões recorrentes de falhas de RAG / LLM. Em termos gerais, abrange:

- desvio da recuperação e limites de contexto incorretos
- índices e armazéns vetoriais vazios ou desatualizados
- incompatibilidade entre embeddings e semântica
- problemas na composição de prompts e na janela de contexto
- colapso lógico e respostas excessivamente confiantes
- falhas em cadeias longas e na coordenação de agentes
- desvio de memória e de funções em sistemas multiagente
- problemas de implementação e da ordem de inicialização

A ideia é simples:

1. Ao investigar uma resposta incorreta, registe:
   - a tarefa e o pedido do utilizador
   - a rota ou combinação de fornecedores no OmniRoute
   - qualquer contexto de RAG utilizado a jusante (documentos recuperados, chamadas de ferramentas, etc.)
2. Associe o incidente a um ou dois números do WFGY ProblemMap (`No.1` … `No.16`).
3. Guarde o número no seu próprio dashboard, guia operacional ou sistema de acompanhamento de incidentes, junto dos registos do OmniRoute.
4. Utilize a página WFGY correspondente para decidir se precisa de alterar o seu sistema de RAG, o recuperador ou a estratégia de encaminhamento.

O texto completo e as instruções concretas estão disponíveis aqui (licença MIT, apenas texto):

[README do WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Pode ignorar esta secção se não executar pipelines de RAG ou de agentes por trás do OmniRoute.

## Problemas conhecidos da v3.8.0

Problemas específicos da versão v3.8.0 e respetivas soluções temporárias atuais. Se uma correção for disponibilizada numa atualização posterior, a entrada será atualizada ou removida.

### Falhas de autenticação da Devin CLI

**Sintomas:**

- "Devin CLI não encontrada" ou "falha na autenticação" ao invocar ferramentas suportadas pelo Devin
- A verificação da CLI em tempo de execução apresenta `installed=false`

**Causas:**

- `CLI_DEVIN_BIN` aponta para um caminho que não existe
- A Devin CLI não está instalada no anfitrião

**Correção:**

1. Instale a Devin CLI para a sua plataforma
2. Defina `CLI_DEVIN_BIN=/usr/local/bin/devin` (ou o caminho real) em `.env`
3. Reinicie o OmniRoute e volte a testar em **Dashboard → Ferramentas CLI**

### Período de suspensão do modelo bloqueado (reposição manual)

**Sintomas:**

- Um modelo continua listado como estando em período de suspensão, mesmo depois de o tempo de expiração ter terminado
- Os pedidos continuam a ignorar o modelo no encaminhamento combinado, apesar de o carimbo de data/hora estar no passado

**Reposição manual:**

- **Dashboard:** **Definições → Períodos de suspensão dos modelos** → clique em **Reativar** no cartão afetado
- **API:** `DELETE /api/resilience/model-cooldowns` com cabeçalhos de autenticação de gestão

### A ligação ao fornecedor Command Code falha com o erro 403

**Sintomas:**

- Erro 403 ao testar a ligação ao fornecedor Command Code
- O cartão do fornecedor apresenta "não autorizado" depois de uma nova adição

**Causa:** O fluxo OAuth não foi concluído (a chamada de retorno não foi recebida ou o token não foi guardado).

**Correção:**

- Execute `omniroute providers` na CLI para voltar a acionar o fluxo OAuth, ou
- Execute novamente o OAuth em **Dashboard → Fornecedores → Command Code → Voltar a ligar**

### O ModelScope devolve períodos de suspensão 429 agressivos

**Sintomas:**

- Períodos de suspensão muito curtos ou imediatos no ModelScope após uma pequena sequência de pedidos
- O encaminhamento combinado ignora o ModelScope mais cedo do que o esperado

**Causa:** O ModelScope emite cabeçalhos `Retry-After` específicos do fornecedor. A v3.8.0 inclui um tratamento dedicado para esses cabeçalhos, pelo que as versões anteriores os interpretam incorretamente como indicações genéricas de limite de pedidos.

**Correção:**

- Certifique-se de que está a utilizar a v3.8.0 ou posterior
- Verifique se a opção `useUpstream429BreakerHints` está ativada em **Definições → Resiliência**

### OMNIROUTE_WS_BRIDGE_SECRET em falta em produção

**Sintomas:**

- Erro 401 em todos os pedidos à ponte WebSocket do Codex/Responses ao executar num anfitrião de produção remoto
- O handshake da ponte WebSocket é terminado imediatamente após a ligação

**Causa:** A variável de ambiente `OMNIROUTE_WS_BRIDGE_SECRET` está em falta no ambiente de produção.

**Correção:**

1. Gere um segredo aleatório: `openssl rand -hex 32`
2. Defina `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` no ambiente do servidor de produção (e em qualquer cliente que comunique com a ponte)
3. Reinicie o OmniRoute

### API Responses: modo em segundo plano degradado para síncrono

**Sintomas:**

- Aviso registado: `background mode degraded to synchronous`
- Um pedido com `background: true` devolve uma resposta síncrona normal em vez de um identificador de tarefa em segundo plano

**Causa:** A v3.8.0 degrada intencionalmente `background: true` na API Responses para execução síncrona, emitindo simultaneamente um aviso. A execução assíncrona completa em segundo plano será disponibilizada futuramente.

**Correção:**

- Ajuste o cliente para efetuar a chamada sem `background`, ou
- Aguarde uma versão posterior que inclua o modo assíncrono completo em segundo plano (acompanhe o registo de alterações)

## Arranque Lento / Tempo Limite de Disponibilidade

Se a CLI apresentar `⚠ Server did not respond within 60s`, mas o servidor estiver
efetivamente a funcionar, o tempo limite da verificação de disponibilidade é demasiado curto para o seu ambiente.

Isto acontece frequentemente no Windows (antivírus, monitores do sistema de ficheiros) ou em contentores
com cargas de trabalho pesadas durante o arranque.

**Solução — aumente o tempo limite:**

```bash
# Através de uma variável de ambiente (mantém-se entre arranques):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minutos
omniroute serve

# Através de uma opção da CLI (utilização única):
omniroute serve --ready-timeout 180000
```

A predefinição é 60 000 ms (60 s). O aviso é apenas informativo; o servidor
continua a iniciar em segundo plano e ficará acessível assim que o arranque estiver concluído.

Consulte [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) para obter todos os
detalhes sobre `OMNIROUTE_READY_TIMEOUT_MS`.
