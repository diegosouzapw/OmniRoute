Guia completo para utilizar a CLI do Codex com o OmniRoute como backend compatível com a OpenAI.

---

> **TOML é o único formato eficaz.** As versões modernas do Codex leem exclusivamente
> `~/.codex/config.toml` (verificado com codex-cli 0.147.0: `codex --help` documenta
> que as substituições de `-c/--config` são «carregadas a partir de `~/.codex/config.toml`»). O antigo
> `~/.codex/config.yaml` pertencia à CLI npm legada e é silenciosamente ignorado.
> O gerador do painel (`/api/cli-tools/apply`, ferramenta `codex`) escreve TOML com uma
> integração conservadora — as chaves existentes e os blocos de outros fornecedores são preservados, a
> chave da API permanece em `OMNIROUTE_API_KEY` (nunca no ficheiro) e qualquer
> `config.yaml` legado remanescente é indicado numa nota de migração sem ser alterado.

## config.toml pronto a colar

Substitua `<YOUR_HOST>` e `<YOUR_KEY>` pelos seus valores:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # limite de armazenamento no histórico por chamada de ferramenta

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc ou ~/.zshrc — valor real da chave, nunca em config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex incluído na aplicação ChatGPT

Se instalou o Codex através da aplicação ChatGPT para computador, o binário `codex` poderá
existir apenas no pacote da aplicação e ainda não estar no `PATH` da sua shell. Adicione o
diretório de recursos ao ficheiro de inicialização da sua shell:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Abra uma nova shell e, em seguida, confirme:

```bash
command -v codex
codex --version
```

### OmniRoute local sem autenticação: uma chave de marcador é suficiente

O Codex valida se a variável de ambiente indicada por `env_key` existe
**antes** de o primeiro pedido sair da CLI. Se a sua instância **local** do OmniRoute
não exigir autenticação, qualquer marcador não vazio funciona:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Utilize uma chave real se o seu servidor OmniRoute estiver protegido ou for remoto.

> **Opções de anfitrião comuns**
>
> | Acesso     | URL                           |
> | ---------- | ----------------------------- |
> | Rede local | `http://192.168.0.1:20128/v1` |
> | Tailscale  | `http://100.x.x.x:20128/v1`   |
> | Loopback   | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — por que motivo funciona com todos os modelos

A CLI do Codex descontinuou `wire_api = "chat"` (Chat Completions) em fevereiro de 2026 e agora **exige** `wire_api = "responses"` (API Responses da OpenAI). Definir `wire_api = "chat"` provoca uma falha imediata no arranque desde a v0.138.

Muitos fornecedores, incluindo GLM e Kimi, continuam a disponibilizar apenas um endpoint de Chat Completions. O DeepSeek V4 disponibiliza agora uma API Responses nativa, bem como um endpoint compatível com a Anthropic; o OmniRoute utiliza Responses por predefinição e permite que cada ligação ao DeepSeek selecione a compatibilidade com a Anthropic.

**O OmniRoute resolve esta questão de forma transparente:**

```
CLI do Codex
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → O OmniRoute seleciona o protocolo nativo do fornecedor e traduz quando necessário
    → POST /responses (DeepSeek V4) ou /chat/completions (Mistral / GLM / Kimi / outros)
```

Nunca precisa de um proxy de tradução separado ao utilizar o OmniRoute. **Todos os modelos utilizam `wire_api = "responses"`** — o OmniRoute trata do resto.

> **`wire_api` é a predefinição** — o campo utiliza `"responses"` por predefinição e pode ser completamente omitido de `config.toml`. Defina-o explicitamente apenas se estiver a documentar a intenção.

## Janela de contexto e compactação

### Campos de configuração de tokens

| Campo                            | Descrição                                                                                                                                                                                                                                    |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Orçamento total de tokens para o modelo ativo. Defina-o com o limite anunciado do modelo.                                                                                                                                                    |
| `model_auto_compact_token_limit` | Limiar que aciona a compactação automática do histórico. **Máximo: 90% de `model_context_window`** — os valores acima de 90% são silenciosamente ignorados.                                                                                  |
| `tool_output_token_limit`        | Limite de tokens armazenados no histórico por resultado de chamada de ferramenta. Impede que uma única resposta extensa de uma ferramenta preencha a janela. **Não é o limite máximo de saída** — é um limite de armazenamento no histórico. |
| `compact_prompt`                 | Substituição inline do prompt de sistema utilizado durante a compactação (v0.138+).                                                                                                                                                          |

> **Nota sobre `model_max_output_tokens`**: Este campo **não faz parte do esquema de configuração da Codex CLI** (está ausente da base de código Rust do Codex). Se for definido, é silenciosamente ignorado. Não dependa dele — utilize `tool_output_token_limit` para controlar a quantidade de resultados de ferramentas armazenada no histórico.

## Esforço de raciocínio

Controla quanto o modelo «pensa» antes de responder.

| Valor    | Utilizar para                                         |
| -------- | ----------------------------------------------------- |
| `none`   | Sem raciocínio — resposta direta                      |
| `low`    | Tarefas triviais (mudar nomes, formatar)              |
| `medium` | **Predefinição do servidor** quando não indicado      |
| `high`   | Tarefas intermédias (refatoração, depuração)          |
| `xhigh`  | Arquitetura, análise aprofundada, problemas complexos |

```bash
# Substituição por invocação
codex -c model_reasoning_effort=low "mudar o nome da variável x para count"
codex -c model_reasoning_effort=xhigh "conceber o módulo de autenticação"
```

Defina também um **resumo** do raciocínio para que o Desktop possa apresentar o texto do pensamento (e não apenas blocos encriptados):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # ou ultra, quando suportado
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### Orçamento de pensamento do OmniRoute (definição do servidor)

No anfitrião do OmniRoute, **Settings → AI → Thinking Budget** tem de estar definido como **`passthrough`** para que o esforço/resumo do Codex chegue ao fornecedor a montante. O modo **`auto` remove** todos os campos `reasoning` / `reasoning_effort` do cliente e deixa os painéis de pensamento vazios, mesmo quando o Codex está configurado corretamente.

Guia completo: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

A compressão e a cache de pedidos são independentes e continuam a funcionar com `passthrough`.

## Perfis — configurações com nome por modelo/fluxo de trabalho

Os perfis permitem alternar entre modelo + janela de contexto com uma única opção. Cada perfil é um ficheiro simples
`~/.codex/<name>.config.toml` que se sobrepõe ao `config.toml` base.

> **Regra de nomenclatura (Codex CLI v0.137+):** o ficheiro tem de ser `~/.codex/<name>.config.toml` — **sem o prefixo `profile-`**.
> A CLI resolve `-p kimi-k27` como `~/.codex/kimi-k27.config.toml`. Se o ficheiro não for encontrado, a predefinição é aplicada silenciosamente.

```bash
codex --profile kimi-k27 "analisar 10 mil linhas desta base de código"
codex -p glm52 "revisão da arquitetura"
codex --profile deepseek-flash "mudar o nome da variável"   # rápido, económico
```

### Perfis de esforço (o mesmo modelo, diferentes níveis de esforço)

```bash
codex -p low      # cx/gpt-5.5, esforço=low
codex -p medium   # cx/gpt-5.5, esforço=medium
codex -p high     # cx/gpt-5.5, esforço=high
codex -p xhigh    # cx/gpt-5.5, esforço=xhigh (predefinição)
codex -p chat     # cx/gpt-5.5, sem esforço definido (predefinição do servidor)
```

## Gerar perfis automaticamente com `omniroute setup-codex`

Se executar o OmniRoute num VPS, pode gerar automaticamente ficheiros de perfil a partir do catálogo de modelos ativo:

```bash
# A partir de um VPS (utiliza o OmniRoute local na porta 20128)
omniroute setup-codex

# A partir de qualquer máquina — aponte para o seu VPS
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Pré-visualizar sem escrever ficheiros
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Gerar apenas perfis GLM e Kimi
omniroute setup-codex --only glm,kimi

# Escrever num diretório personalizado
omniroute setup-codex --codex-home /path/to/.codex
```

O comando obtém `/v1/models`, utiliza perfis otimizados para modelos conhecidos, recorre aos metadados do catálogo para outros modelos de texto compatíveis e escreve `~/.codex/<name>.config.toml` para cada um. É idempotente — pode ser executado novamente em segurança.

O OmniRoute também pode **sincronizar automaticamente** estes mesmos ficheiros de perfil depois de uma deteção/importação bem-sucedida dos modelos do fornecedor alterar o catálogo ativo. Esta opção é **facultativa e está desativada por predefinição**: ative-a no **painel CLI Code** ("Sincronização automática de perfis CLI" → Codex) ou defina `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (também respeita `CLI_ALLOW_CONFIG_WRITES`, que está ativado por predefinição). Quando ativada, apenas escreve ficheiros de perfil `~/.codex/*.config.toml` separados; nunca altera o ficheiro ativo/predefinido `~/.codex/config.toml`, as definições do Codex-lb, a autenticação ou a seleção do fornecedor.

## Iniciar o Codex com `omniroute launch-codex`

Verifica o estado da sua instância do OmniRoute antes de iniciar o Codex:

```bash
# Iniciar com o OmniRoute local (porta predefinida 20128)
omniroute launch-codex

# Iniciar com um perfil específico
omniroute launch-codex --profile kimi-k27

# Iniciar com um VPS remoto
omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# Passar argumentos adicionais ao codex
```

## Tarefas de longa duração

Duas predefinições do OmniRoute podem comprometer silenciosamente sessões do Codex CLI com várias horas de duração. Nenhuma delas é uma definição do Codex CLI — ambas pertencem ao OmniRoute. Os utilizadores que migram uma configuração de proxies a montante que fixam contas e desativam os limites de inatividade deparam-se frequentemente com ambas e concluem que o OmniRoute «não consegue manter uma sessão longa».

| Sintoma                                                                                            | Causa provável                                                                                  | Parâmetro                |
| -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------ |
| A sessão continua a trocar de conta / a continuidade da cache de prompts perde-se entre interações | O TTL da afinidade de sessão é `0` (desativado)                                                 | `sessionAffinityTtlMs`   |
| A ligação termina durante o raciocínio sem qualquer aviso apresentado ao cliente                   | O supervisor de inatividade do fluxo foi acionado após 10 minutos sem qualquer bloco a montante | `STREAM_IDLE_TIMEOUT_MS` |

Discussões relacionadas: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (interrupções de tarefas longas), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (motivo pelo qual a afinidade está desativada por predefinição). Acompanhamento: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Afinidade de sessão — fixar uma conversa a uma conta

**Predefinição:** `sessionAffinityTtlMs = 0` (desativado).

**Onde configurar**

- Painel → **Definições → Encaminhamento** → **Afinidade de sessão** → **TTL da afinidade (segundos)** (`ComboDefaultsTab`)
- Ou aplique PATCH às definições com `sessionAffinityTtlMs` em **milissegundos** (intervalo Zod de `0`–`86_400_000`, ou seja, até 24 horas)

> Renomeado em #7274 a partir do `codexSessionAffinityTtlMs`, exclusivo do Codex. A chave legada continua a ser aceite como um alias só de leitura; as novas configurações devem utilizar `sessionAffinityTtlMs`. A afinidade aplica-se agora a **qualquer** fornecedor quando o TTL é superior a `0`, e não apenas ao Codex — consulte [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Afinidade de sessão.

**O que deixa de funcionar quando permanece em 0**

Cada interação de uma conversa com várias interações no Codex é encaminhada de forma independente pela estratégia de combinação ativa e pode acabar numa **conta diferente em cada interação**. Isso interrompe a continuidade da sessão/cache de prompts a montante. O OmniRoute apenas consulta os cabeçalhos de sessão do Codex (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) e campos do corpo, como `prompt_cache_key` / `session_id`, quando o TTL é superior a `0` (`extractSessionAffinityKey` em `src/sse/services/auth.ts`).

**Recomendação para uma única tarefa com várias horas de duração**

Defina o TTL para um valor **superior à duração real prevista da tarefa** (o máximo da IU é **86400 segundos** = 24 horas):

| Duração prevista da tarefa | TTL da afinidade (IU, segundos) | `sessionAffinityTtlMs` |
| -------------------------- | ------------------------------- | ---------------------- |
| Algumas horas              | `14400` (4 h)                   | `14400000`             |
| Durante a noite / ~12 h    | `43200` (12 h)                  | `43200000`             |
| Dia inteiro                | `86400` (24 h, máximo)          | `86400000`             |

A adesão é deliberada: desativar a afinidade favorece o balanceamento de carga entre contas; ativá-la favorece a continuidade de uma sessão longa de um agente. Este guia **não** altera a predefinição — os operadores que executam tarefas longas do Codex têm de aderir explicitamente.

### 2. Tempo limite de inatividade do fluxo — não interromper interações de raciocínio silenciosas

**Predefinição:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 minutos). Quando não está definido, herda de `REQUEST_TIMEOUT_MS`; o valor base partilhado também é 600000. Consulte [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Tempos limite.

**O que deixa de funcionar com a predefinição**

Um turno de raciocínio / utilização de ferramenta do Codex que permaneça silencioso durante mais de 10 minutos **sem qualquer bloco real a montante** é encerrado à força pelo mecanismo de vigilância de inatividade SSE (`open-sse/utils/stream.ts`). Frequentemente, o cliente vê apenas uma interrupção abrupta da ligação — o que corresponde a «parou automaticamente sem qualquer notificação».

Detalhe crítico: o **heartbeat** SSE sintético do OmniRoute não reinicia o temporizador de inatividade. Apenas um bloco real do corpo da resposta a montante atualiza `lastChunkTime`. Para o mecanismo de vigilância, um modelo silencioso que ainda está «a pensar» parece exatamente igual a uma ligação a montante bloqueada.

Inatividade relacionada do corpo no Undici: `FETCH_BODY_TIMEOUT_MS` (também assume, por predefinição, o mesmo valor de referência de 10 minutos; `0` desativa-o). Para streaming, `FETCH_TIMEOUT_MS` abrange apenas o estabelecimento da ligação / os primeiros cabeçalhos — assim que o stream fica ativo, os bloqueios são controlados por `STREAM_IDLE_TIMEOUT_MS` e `FETCH_BODY_TIMEOUT_MS`.

**Recomendação para uma única tarefa com várias horas de duração**

No ambiente do processo do OmniRoute (`.env` / compose / systemd):

```bash
# Desativar os limites de inatividade do stream e do corpo para turnos de raciocínio prolongados
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Em alternativa, aumente-os para valores superiores ao maior intervalo de silêncio previsto (os valores são em milissegundos):

```bash
# Exemplo: permitir até 2 horas de silêncio entre blocos a montante
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Reinicie o OmniRoute depois de alterar estas variáveis de ambiente.

### Procedimento concreto — tarefa do Codex com várias horas de duração

1. **Fixe a conta:** Painel → Definições → Encaminhamento → Afinidade de sessão → TTL da afinidade = `43200` (12 h) ou `86400` (máximo de 24 h).
2. **Aumente / desative os limites de inatividade** no ambiente do OmniRoute:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Mantenha o `config.toml` habitual do Codex (`wire_api = "responses"`, `base_url` correto, `OMNIROUTE_API_KEY`) — não existem opções de afinidade/inatividade no lado do Codex para estes dois comportamentos.
4. Reinicie o OmniRoute e, em seguida, inicie a tarefa prolongada do Codex.

### Decisão sobre os valores predefinidos (#7287)

| Opção                    | Valor predefinido | Alterar neste guia?                                                                                                             |
| ------------------------ | ----------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (desativado)  | **Não** — continua a ser opcional (balanceamento de carga vs. continuidade; consulte a Discussão #5718)                         |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 min) | **Não** — mantém-se em 10 minutos para tráfego geral; os operadores de tarefas prolongadas do Codex aumentam-no ou desativam-no |

Alterar globalmente qualquer um dos valores predefinidos mudaria o comportamento para todos os clientes de uma instância, não apenas para o Codex. Documente as opções; mantenha os valores predefinidos inalterados até que uma decisão explícita do operador determine o contrário.

### Diagnosticar interrupções por inatividade

Quando o mecanismo de vigilância de inatividade é acionado, o OmniRoute regista uma linha com este formato:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Procure por `Idle timeout: no data from` com grep (ou pelo código `stream_idle_timeout` / nome do erro `StreamIdleTimeoutError`). O segmento do fornecedor corresponde ao que o OmniRoute utilizou nesse pedido (`codex`, outro ID de fornecedor ou `provider` caso seja desconhecido) — nem sempre é a cadeia literal `codex`.

## Resolução de problemas

**`Error: wire_api = "chat" is no longer supported`**
Remova `wire_api = "chat"` da sua configuração. Defina `wire_api = "responses"` ou omita o campo (a predefinição é `"responses"` desde a v0.138).

**`Error: model not found`**
Verifique se o modelo existe no OmniRoute com o prefixo correto. Utilize `omniroute models list` ou abra `/dashboard/providers/<provider>`.

**`Authentication error`**
Confirme que `OMNIROUTE_API_KEY` foi exportada: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
O Codex valida se a variável de ambiente existe antes de efetuar o primeiro pedido. Exporte
uma chave real para servidores protegidos ou um marcador de posição não vazio, como
`OMNIROUTE_API_KEY=local`, quando a sua instância **local** do OmniRoute não
exigir autenticação. Reinicie a shell se a tiver adicionado a `~/.bashrc` ou `~/.zshrc`.

**`Connection refused`**
Verifique se o OmniRoute está em execução e se o anfitrião/porta de `base_url` está correto para a sua rede (local, Tailscale ou VPS).

**A sessão termina inesperadamente perto do limite de contexto**
Defina explicitamente `model_context_window` e `model_auto_compact_token_limit`. Consulte a tabela da janela de contexto acima.

**A compactação é acionada demasiado tarde**
Reduza `model_auto_compact_token_limit` para 80–85% da janela. Nunca o defina acima de 90%.

**O perfil não é carregado (`-p <name>` é silenciosamente ignorado)**
Confirme que o ficheiro existe em `~/.codex/<name>.config.toml` (sem o prefixo `profile-`). Execute `ls ~/.codex/*.config.toml`.

**Uma tarefa prolongada do Codex é interrompida a meio da execução/muda de conta entre interações**
Consulte [Tarefas de longa duração](#long-running-tasks). Ative a afinidade de sessão (TTL superior à duração da tarefa) e aumente ou desative `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`. Pesquise `Idle timeout: no data from` nos registos do OmniRoute.
