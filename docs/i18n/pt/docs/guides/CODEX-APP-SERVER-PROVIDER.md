---

O OmniRoute disponibiliza **duas** formas de utilizar o OpenAI Codex:

| Fornecedor             | Como comunica com a OpenAI                                                                                                                                                                                          | Ressalva de utilização                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **`codex`**            | Reenvia o seu token OAuth do ChatGPT/OpenAI diretamente para a Responses API                                                                                                                                        | **Sim** — a sessão oficial não está autorizada para utilização através de proxies/routers |
| **`codex-app-server`** | Controla o **`codex app-server` da própria Codex CLI** através de JSON-RPC/WebSocket; a CLI detém e renova automaticamente o respetivo OAuth (`~/.codex/auth.json`), exatamente como numa sessão `codex` interativa | **Não** — o OmniRoute nunca reenvia um token para a API                                   |

Como o `codex-app-server` nunca reenvia um token, não está sujeito à ressalva de
utilização relacionada com o reenvio de sessões. Requer, no entanto, uma
**Codex CLI acessível no URL configurado do app-server**, e essa CLI tem de ter
uma **sessão iniciada**.

---

## 1. Arquitetura

```
┌─ aplicação OmniRoute ────────────┐        ┌─ sidecar codex-app-server ──────────┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                   │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456         │
│  (+ token de capacidade)         │  JSON  │  --ws-auth capability-token         │
│                                  │  RPC   │  gere autonomamente o OAuth OpenAI  │
└──────────────────────────────────┘        │  (~/.codex/auth.json, renovação auto.)│
        │ partilha (volumes do compose)      └─────────────────────────────────────┘
        ▼
  codex-appserver-token   → o token de capacidade WS (ambos o montam)
  codex-appserver-home    → ~/.codex (auth.json escrito pelo dashboard,
                             lido pelo codex app-server do sidecar)
```

- O sidecar escuta **apenas** na rede interna do compose
  (`ws://codex-app-server:1456`), protegido por um token de capacidade. **Nunca**
  é publicado no anfitrião nem na Internet.
- A Codex CLI está incluída em `omniroute:base`, pelo que não é necessário
  instalar o codex no anfitrião nem na máquina do utilizador ao executar o
  sidecar.

## 2. Iniciar o serviço

```bash
# Iniciar a stack COM o perfil do sidecar codex app-server:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

No primeiro arranque, o sidecar gera o respetivo token de capacidade WS (no
volume partilhado `codex-appserver-token`) e a aplicação lê o mesmo token através
de `OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`. Não é necessária qualquer
configuração manual do token.

## 3. Ligar + iniciar sessão

1. No dashboard, adicione uma ligação para **OpenAI Codex (App-Server)**. Não é
   necessária qualquer chave de API ou token (é um fornecedor sem autenticação —
   o sidecar é responsável pela autenticação).
2. Se a Codex CLI do sidecar **ainda não tiver uma sessão iniciada**, a
   verificação de estado da ligação indica _"em execução, mas sem sessão
   iniciada"_ (e não um erro de autenticação a vermelho). Utilize **Iniciar
   sessão com o ChatGPT**: isto executa o OAuth de dispositivo padrão do Codex no
   seu browser e, em seguida, escreve `~/.codex/auth.json` no volume partilhado
   através de **Aplicar autenticação** (o mesmo início de sessão serve os
   fornecedores `codex` e `codex-app-server`).
3. Após iniciar sessão, a verificação de estado fica verde (verifica tanto
   `/readyz` **como** `account/read` — ou seja, que está operacional _e_
   autenticado) e começa a processar pedidos.

O dashboard nunca substitui um ficheiro `~/.codex/auth.json` existente e válido —
apenas escreve quando o ficheiro não existe ou quando o respetivo token está
obsoleto (é sempre criada uma cópia de segurança).

## 4. Cenários de implementação

- **Operador com uma Codex CLI já autenticada** — monte o diretório
  `~/.codex` do anfitrião no sidecar (`codex-appserver-home`) e ignore o passo de
  início de sessão.
- **Utilizador público, sem o codex instalado localmente** — irrelevante: o
  sidecar contém a CLI. O utilizador autentica-se apenas através do dashboard.
- **OmniRoute em bare metal (sem sidecar, codex no anfitrião)** — aponte
  `OMNIROUTE_CODEX_APPSERVER_WS` para o seu próprio `codex app-server` e
  certifique-se de que o codex no anfitrião tem uma sessão iniciada; a indicação
  "codex não instalado" é apresentada caso o binário esteja em falta.

## 5. Saída residencial/UDP (extra para operadores, não incluído)

O sidecar genérico acima encaminha o tráfego de saída através da rede normal do
contentor. Um operador que necessite de encaminhar o tráfego do Codex através de
uma **saída residencial** (por exemplo, um sidecar Tailscale com TUN que
transporte TCP + UDP/QUIC) deve executá-lo como uma substituição separada do
compose; esta configuração **não** faz intencionalmente parte do perfil
`codex-app-server` incluído. Consulte o manual interno de operações para obter
informações sobre essa configuração.
