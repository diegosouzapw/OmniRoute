O Traffic Inspector é o depurador de tráfego HTTPS integrado do OmniRoute — uma ferramenta semelhante ao Charles Proxy / mitmweb / HTTP Toolkit que está **preparada para LLMs** e **preparada para agentes**. Está disponível em `/dashboard/tools/traffic-inspector` e recebe tráfego em tempo real de até 5 fontes de captura simultâneas.

**Localização no dashboard:** `/dashboard/tools/traffic-inspector`
**Grupo na barra lateral:** Ferramentas (depois do AgentBridge)
**Ver também:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — o AgentBridge é o modo de captura 1.

### Arquitetura num parágrafo

O `TrafficBuffer` (`src/mitm/inspector/buffer.ts`) é um buffer circular partilhado em memória (1000 entradas por predefinição, configurável através de `INSPECTOR_BUFFER_SIZE`). Todas as fontes de captura escrevem nele através de `push()`. O buffer classifica cada entrada utilizando `kindDetector.ts` (determina se se trata de um pedido de LLM), calcula uma `contextKey` (impressão digital SHA-256 do prompt de sistema) e transmite para todos os subscritores WebSocket através de `globalTrafficBuffer.subscribe()`. O dashboard estabelece ligação através de `GET /api/tools/traffic-inspector/ws` e recebe um snapshot ao ligar-se, seguido de eventos `new`/`update`/`clear`.

## §2 Modos de captura

O Traffic Inspector suporta **5 fontes de captura simultâneas**. Cada uma pode ser ativada ou desativada de forma independente. O campo `source` de cada `InterceptedRequest` (`src/mitm/inspector/types.ts`) tem um dos valores `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"` ou `"tproxy"`.

### Modo 1 — AgentBridge (predefinido, sempre ativo)

**Origem:** Processadores do AgentBridge (`src/mitm/handlers/base.ts`)
**Mecanismo:** Cada chamada a `intercept()` em `MitmHandlerBase` chama `hookBufferStart()` antes de reencaminhar e `hookBufferUpdate()` após a conclusão. Não requer configuração adicional — funciona assim que o AgentBridge estiver em execução.
**Abrangência:** Os 9 agentes de IDE configurados no AgentBridge
**Nota:** Campo `source` em `InterceptedRequest` = `"agent-bridge"`

### Modo 2 — Hosts personalizados (redirecionamento de DNS)

**Origem:** Lista de hosts definida pelo utilizador (tabela `inspector_custom_hosts`)
**Mecanismo:** Adicionar um host através da IU adiciona `127.0.0.1 <host>` a `/etc/hosts` (requer sudo). O servidor MITM existente do AgentBridge (porta 443) gera dinamicamente um certificado SNI para o novo host.
**Abrangência:** Qualquer aplicação que utilize o host adicionado — não é necessário alterar a configuração da aplicação
**Nota:** `source` = `"custom-host"`

Exemplos de utilização:

- Monitorizar `api.openai.com` a partir de scripts Python
- Depurar `my-internal-llm.company.com`
- Capturar tráfego de dispositivos móveis na mesma rede (através de falsificação ARP — avançado)

### Modo 3 — Serviço de escuta HTTP_PROXY (porta 8080)

**Origem:** Aplicações que utilizam as variáveis de ambiente `HTTP_PROXY`/`HTTPS_PROXY`
**Mecanismo:** Serviço de escuta secundário na porta 8080 (`src/mitm/inspector/httpProxyServer.ts`) que funciona como um proxy HTTP/HTTPS explícito padrão. Aceita túneis `CONNECT` (HTTPS) e pedidos HTTP diretos.
**Abrangência:** Qualquer aplicação que respeite a variável de ambiente `HTTP_PROXY` — sem alterações de DNS, sem sudo
**Nota:** `source` = `"http-proxy"`

```bash
# Captura rápida para um único comando:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# Captura persistente numa sessão de shell:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**Limitação de TLS:** Os túneis HTTPS `CONNECT` são capturados apenas como metadados (host, porta, tempos) — o corpo TLS não é desencriptado por predefinição. Ative a opção "Desencriptar HTTPS no modo proxy" (adesão opcional, requer que o certificado do AgentBridge seja considerado fidedigno) para inspecionar o corpo completo.

**Conflito de porta:** Se a porta 8080 estiver a ser utilizada, o AgentBridge devolve um erro 409 estruturado. Altere a porta através da variável de ambiente `INSPECTOR_HTTP_PROXY_PORT`.

### Modo 4 — Proxy para todo o sistema (avançado, opcional)

**Origem:** Definições de proxy ao nível do SO (aplicam-se a todas as aplicações na máquina)
**Mecanismo:** Utiliza as APIs do SO para redirecionar todo o tráfego HTTP/HTTPS através do serviço de escuta HTTP_PROXY:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **Abrangência:** Todas as aplicações na máquina que respeitem as definições de proxy do sistema
  **Nota:** `source` = `"system-proxy"`

**Mecanismos de segurança:**

- Temporizador de desativação automática (30 min por predefinição, configurável através de `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES`)
- O estado anterior do proxy do sistema é guardado na BD e restaurado ao reverter
- O painel apresenta a mensagem "A reverter o proxy do sistema" se o utilizador sair da página enquanto estiver ativo
- A IU apresenta o distintivo `⚠ Avançado` + uma caixa de confirmação explícita

### Modo 5 — Desencriptação transparente TPROXY (Linux, root, opcional)

**Origem:** TPROXY do kernel + encaminhamento baseado em políticas (`src/mitm/tproxy/`)
**Mecanismo:** Marca novas ligações TCP locais de saída para uma porta de destino (por predefinição, `443`) em `mangle OUTPUT`; uma `ip rule` reencaminha os pacotes marcados para entrega local; e o destino `TPROXY` de `mangle PREROUTING` entrega-os a um serviço de escuta transparente (**IP_TRANSPARENT**) (porta predefinida `8443`). O serviço de escuta termina o TLS com um certificado de folha emitido **a pedido para cada nome de host SNI** por uma AC dinâmica, captura a comunicação desencriptada e reencaminha o pedido, novamente encriptado, para o destino original.
**Abrangência:** Hosts de destino **arbitrários** na porta de destino — sem falsificação de `/etc/hosts`, sem variável de ambiente `HTTP_PROXY`, sem alteração do proxy de todo o sistema. O processo intercetado não requer qualquer alteração de configuração, mas tem de confiar na AC dinâmica.
**Nota:** `source` = `"tproxy"`

**Requisitos:** Apenas Linux (**IP_TRANSPARENT** só está disponível no Linux), a capacidade **CAP_NET_ADMIN** (root) e um addon N-API nativo que tem de ser compilado com uma cadeia de ferramentas C (`npm run build:native:tproxy`). Quando não está disponível, a opção no painel fica desativada com a descrição "A desencriptação TPROXY requer Linux + root + o addon nativo". As regras de firewall são aplicadas/revertidas de forma transacional (uma falha nunca deixa uma regra `mangle` para trás) e são removidas no reinício. Um mecanismo antirrecursão baseado em SO_MARK impede que o reencaminhamento novamente encriptado do próprio proxy seja intercetado de novo.

Este é um subsistema substancial, com o seu próprio guia dedicado para operadores — consulte `docs/security/MITM-TPROXY-DECRYPT.md` (git; não compilado em `/docs`) para obter a configuração completa da firewall, a AC dinâmica por SNI + o instalador do arquivo de confiança, a rota apenas local, os detalhes do mecanismo antirrecursão e o esquema de configuração. A opção é controlada por `GET / POST / DELETE /api/tools/agent-bridge/tproxy` (nota: a rota encontra-se sob o prefixo do AgentBridge, não sob o prefixo do Traffic Inspector).

## §4 Funcionalidades cientes de LLM

### 4.1 Detetor de tipo (`src/mitm/inspector/kindDetector.ts`)

Classifica cada pedido como `"llm"`, `"app"` ou `"unknown"` utilizando 4 sinais:

1. **Registo de hosts** — cerca de 18 nomes de host conhecidos de APIs de LLM (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot, etc.)
2. **Padrões de caminhos** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses`, etc.
3. **Estrutura do corpo** — deteta os campos `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input`
4. **Indícios no agente do utilizador** — `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor` na cadeia UA

Os hosts personalizados adicionados através do Modo 2 herdam o respetivo `kind` do campo do formulário (a predefinição é `"custom"`).

### 4.2 Agregador de SSE (`src/mitm/inspector/sseMerger.ts`)

**Implementação independente de sala limpa.** A análise de eventos segue o
[algoritmo de eventos enviados pelo servidor do WHATWG](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream),
enquanto a reconstrução segue os esquemas públicos de transmissão em fluxo da [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) e
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent).

Reconstrói a mensagem final do assistente a partir de eventos delta SSE em bruto:

- **Anthropic**: acumula `content_block_delta` por índice; processa `text_delta`, `input_json_delta` (chamadas de ferramentas), `thinking_delta`
- **OpenAI**: acumula opções/chamadas de ferramentas de Chat Completions e itens de saída da Responses API
  por índice
- **Gemini**: acumula `candidates[i].content.parts`
- **Desconhecido**: devolve os eventos em bruto sem alterações

O separador Response apresenta um seletor: **"Eventos em bruto ↔ Agregados"**.

### 4.3 Normalizador de conversas (`src/mitm/inspector/conversationNormalizer.ts`)

**Implementação independente de sala limpa.** A normalização é definida por contratos
locais de caixa negra e pelos esquemas públicos de mensagens da OpenAI, Anthropic e Gemini; não é utilizado
qualquer código-fonte de implementação a montante.

Converte os formatos de mensagens da OpenAI, Anthropic e Gemini num único `NormalizedConversation` antes da apresentação:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // mensagens / conteúdos / pedido do corpo do pedido
  response: NormalizedTurn[]; // resposta do assistente (agregada através de sseMerger)
  contextKey: string | null; // impressão digital SHA-256 do prompt de sistema
}
```

Tipos de blocos: `text`, `tool_use`, `tool_result`. O separador Conversation utiliza esta estrutura independentemente do fornecedor.

### 4.4 Colorização da chave de contexto (`src/mitm/inspector/contextKey.ts`)

- Calcula o `SHA-256` do prompt de sistema (primeira mensagem com `role:system`, ou o campo `system`, ou `systemInstruction` do Gemini)
- Devolve um prefixo hexadecimal de 12 caracteres (`"a3f9c2..."`)
- O frontend associa a chave a uma cor HSL determinística para a barra da margem esquerda
- **Filtro "mesmo contexto"**: clicar no chip `ctx #a3f` adiciona um filtro para apresentar apenas pedidos com a mesma impressão digital

Isto facilita a distinção visual entre diferentes "personas" ou tarefas em execução na mesma sessão do agente.

### 4.5 Extração de metadados de LLM

Para pedidos de LLM, o separador LLM Details extrai:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // proveniente do corpo do pedido ou da resposta
  messages: number; // número de turnos
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // verdadeiro se for uma resposta SSE
  mappedTo: string | null; // cabeçalho x-omniroute-mapped
  costEstimateUsd: number | null; // custo estimado com base nos preços do OmniRoute
}
```

### 4.6 Filtro em tempo real de pedidos em curso

O campo `status` do pedido é `number | "in-flight" | "error"` — é adicionada uma entrada
como `"in-flight"` no momento em que o pedido é iniciado e **atualizada no mesmo local**
quando chega a resposta (ou o erro). O seletor **"Em direto"** da barra de ferramentas
(`liveOnly`, chave i18n `trafficInspector.liveOnly`) restringe a lista às entradas
cujo `status === "in-flight"`, permitindo acompanhar ligações abertas em tempo real.

O filtro é um predicado puro do lado do cliente em
`src/lib/inspector/matchesTrafficFilter.ts`:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

O estado do seletor reside em `useTrafficFilters` (os hooks do painel do inspetor) e
combina-se com os restantes filtros (perfil, host, agente, origem, estado, contexto).

### 4.7 Atribuição de processos (Linux)

No Linux, cada pedido intercetado pode ser atribuído ao **processo local de
origem**. São adicionados dois campos opcionais a `InterceptedRequest`:

```ts
pid?: number;          // ID do processo de origem (apenas Linux)
processName?: string;  // nome do processo de origem (apenas Linux)
```

`src/mitm/inspector/processAttribution.ts` associa a porta efémera do _cliente_
da ligação a um PID + nome através dos seguintes passos:

1. Lê `/proc/net/tcp` e `/proc/net/tcp6` para encontrar o inode do socket correspondente à
   porta (`parseProcNetTcpForInode`, um analisador puro testável através de fixtures).
2. Percorre `/proc/<pid>/fd/` à procura de uma ligação simbólica para `socket:[<inode>]`.
3. Lê o nome do processo a partir de `/proc/<pid>/comm`.

Uma cache com TTL de 1 segundo limita o custo da análise de procfs sob carga. A atribuição é
feita com base no **melhor esforço** — qualquer falha é resolvida como `null` e nunca bloqueia a captura. No
macOS/Windows, a função devolve `null` (stub; o suporte de `lsof`/`GetExtendedTcpTable`
será adicionado posteriormente).

## §6 Segurança

O Traffic Inspector mostra **todo o tráfego HTTPS intercetado**, incluindo cabeçalhos de autorização e corpos dos pedidos. Estão implementados os seguintes controlos:

| Controlo                              | Detalhes                                                                                                                                                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **LOCAL_ONLY**                        | Todas as rotas e o endpoint WebSocket estão limitados ao endereço de loopback (imposto em `routeGuard.ts` antes da autenticação)                                                                                               |
| **Ocultação de segredos**             | O analisador linear `maskSecret()` oculta credenciais Bearer da RFC 6750, chaves com prefixos de fornecedores e tokens opacos longos antes de `TrafficBuffer.push()`                                                           |
| **Limite do tamanho do corpo**        | Os corpos > `INSPECTOR_MAX_BODY_KB` (predefinição: 1024 KB) são truncados com o aviso `"(truncado por motivos de desempenho)"`                                                                                                 |
| **Saneamento de cabeçalhos**          | Os nomes são convertidos para minúsculas; os cabeçalhos de enquadramento/salto a salto e de autenticação do proxy são removidos; os cookies são totalmente ocultados; os valores de credenciais são delegados a `maskSecret()` |
| **CSP**                               | Política de Segurança de Conteúdos rigorosa nas páginas do Traffic Inspector para impedir XSS através de corpos de resposta injetados                                                                                          |
| **Sem persistência por predefinição** | O `TrafficBuffer` é mantido em memória e perde-se ao reiniciar o servidor. As sessões apenas são persistidas quando gravadas explicitamente                                                                                    |

### Regras rígidas aplicadas

| Regra                             | Aplicação                                                                                   |
| --------------------------------- | ------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | Todas as respostas de erro HTTP das rotas do Traffic Inspector são saneadas                 |
| **#15 + #17** `isLocalOnlyPath()` | `/api/tools/traffic-inspector/` é LOCAL_ONLY + SPAWN_CAPABLE (comandos do proxy do sistema) |

### Limitações conhecidas

- O **modo de proxy para todo o sistema** afeta todas as aplicações na máquina, incluindo clientes VPN e SSO. Utilize-o sempre com o temporizador de desativação automática. Não o utilize em máquinas partilhadas.
- **HTTPS em túnel CONNECT**: o Modo 3 (HTTP_PROXY) captura apenas metadados do túnel para destinos HTTPS, a menos que a interceção TLS esteja ativada. Isto é intencional — a captura transparente sem que o certificado AgentBridge seja considerado fidedigno interromperia a verificação TLS dessas aplicações.
- **Cadeias de caracteres codificadas diretamente em alguns componentes**: alguns componentes da IU (F7/F8) têm um pequeno número de cadeias de caracteres codificadas diretamente que ainda não estão abrangidas por chaves de i18n. Estas estão documentadas como uma Limitação Conhecida no relatório de lacunas de i18n; serão migradas numa fase posterior. As cadeias de caracteres afetadas são etiquetas decorativas da IU que não necessitam de tradução para uma utilização funcional.

## §7 Resolução de problemas

### Desconexão do WebSocket

Se o acompanhamento em direto apresentar "Desligado":

1. Verifique se o servidor ainda está em execução: `GET /api/tools/traffic-inspector/capture-modes`
2. Recarregue a página — o WebSocket volta a ligar-se e recebe um novo instantâneo
3. Se o servidor tiver sido reiniciado, o buffer em memória foi limpo — as entradas antigas perderam-se, a menos que tenha sido gravada uma sessão

### Conflito na porta 8080

Se o modo HTTP_PROXY não iniciar:

```bash
lsof -i :8080    # localizar o processo
```

Altere a porta:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### Proxy do sistema não revertido

Se o OmniRoute falhar enquanto o modo de proxy para todo o sistema estiver ativo:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

O painel também apresentará a opção "Reverter proxy do sistema" no carregamento seguinte se detetar que o estado da BD indica que o proxy estava ativo.

### Buffer cheio

Quando o buffer atinge `INSPECTOR_BUFFER_SIZE` (predefinição: 1000), as novas entradas substituem as mais antigas. Se estiverem a perder-se pedidos importantes:

- Aumente `INSPECTOR_BUFFER_SIZE` (por exemplo, 5000) — utiliza mais memória em troca de uma maior retenção
- Grave uma sessão para guardar a janela relevante na BD
