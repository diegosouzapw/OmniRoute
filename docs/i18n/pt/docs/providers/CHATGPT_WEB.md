`chatgpt-web-codex` (alias `cgpt-codex`) encaminha interações de Responses do Codex através de uma
sessão autenticada do ChatGPT no browser. É independente do fornecedor comum descontinuado
`chatgpt-web` e utiliza a implementação com aviso MIT em
`open-sse/vendor/codex-chatgpt-web/`, atualizada até ao commit upstream v4.0.7
`b59d7dc51b84fb1f465ff1d00f5207f3b2b4a494`.

## Descontinuação do fornecedor comum

Os antigos IDs do fornecedor comum `chatgpt-web` e `cgpt-web` já não são disponibilizados porque não
foi possível esclarecer a proveniência da respetiva implementação de pré-chave/prova de trabalho. Os pedidos
explícitos para qualquer um desses IDs, incluindo IDs de modelos com prefixo de barra e aliases persistidos, falham
de forma segura com HTTP `410` e o código **PROVIDER_RETIRED** antes de qualquer pedido upstream.

A migração `168_retire_chatgpt_web.sql` marca como eliminadas as ligações de fornecedor correspondentes e
invalida os respetivos leases de sessão ativos. Preserva o histórico de ligações e as listas de permissões
de chaves de API; não adiciona acesso de substituição a nenhuma lista de permissões. O fornecedor Codex e
as respetivas ligações não são abrangidos por esta descontinuação.

## Pré-requisitos

- um cabeçalho Cookie completo de uma sessão autenticada no ChatGPT;
- Chrome ou Chromium, juntamente com uma sessão gráfica ou um ecrã Xvfb para instalações com npm, systemd e PM2;
- com o perfil `web` do Docker, o serviço Chromium interno de
  `docker-compose.yml`;
- o `tunnel-client` v0.0.13 da OpenAI e um conector personalizado do ChatGPT para ferramentas Codex locais.

O túnel apenas é necessário para interações com ferramentas. Todas as rotas indicadas, incluindo `pro`, podem utilizar a
mesma capacidade de ferramenta local associada à interação quando o túnel e o conector estão configurados.

## Configuração no painel

1. Abra o fornecedor **ChatGPT Web (Codex)** e adicione uma ligação.
2. Cole o cabeçalho Cookie completo do ChatGPT, o ID do túnel, a chave de runtime e o nome do conector
   personalizado. As novas configurações com capacidade para ferramentas têm de utilizar um conector recém-criado com o nome exato
   `OmniRoute Codex v2`, com Authentication definido como None e Permissions definido como Allow all
   actions.
3. Execute a verificação da ligação. O OmniRoute abre um Temporary Chat baseado no browser e deteta
   se Sol e Pro estão disponíveis para a conta.
4. Guarde a ligação. O OmniRoute substitui o cookie colado pelo estado de armazenamento
   verificado do Playwright e armazena-o com a chave de runtime através da abstração de credenciais
   encriptadas.

O cookie original não é retido após ser guardado com êxito. Quando a sessão expirar, abra
a ligação, cole um novo cabeçalho Cookie completo e execute novamente a verificação. O estado de diagnóstico
na caixa de diálogo de edição comunica separadamente o estado do browser, do estado de armazenamento, da autenticação, do Temporary Chat, do túnel,
do conector e do ciclo completo da ferramenta.

> Nunca submeta para o repositório um cookie real, uma chave de runtime, um estado de armazenamento ou um token de capacidade. Os valores de teste e
> de documentação têm de ser sempre marcadores de posição.

## Modelos e combos

As rotas fixas de modelos são:

- `chatgpt-web-codex/luna` — GPT-5.6 Luna, esforço baixo
- `chatgpt-web-codex/think` — GPT-5.6 Luna, esforço médio
- `chatgpt-web-codex/instant`
- `chatgpt-web-codex/medium`
- `chatgpt-web-codex/high`
- `chatgpt-web-codex/extra-high`
- `chatgpt-web-codex/pro`

Adicione uma delas a um combo como faria com qualquer outro modelo. A aplicação Codex envia o nome do combo como
`model` para o endpoint normal de Responses, `/v1/responses`; não existe um endpoint Codex
separado nem um seletor de modo.

As contas Free/Go disponibilizam as rotas Luna. As contas com acesso ao Sol disponibilizam desde Instant até
High, e as contas com acesso ao Pro disponibilizam adicionalmente Extra High e Pro. Cada rota tem um
modelo de backend e um nível de esforço de raciocínio fixos; um esforço explícito de Responses que entre em conflito faz o pedido falhar
de forma segura, em vez de alterar silenciosamente o modo selecionado no browser.

Não altere o nome nem reutilize um conector `Codex Native` ou `OmniRoute Codex` antigo. O ChatGPT
coloca em cache o contrato MCP público com base na identidade do conector, enquanto a ponte atualizada utiliza um
novo contrato direto de tokens por interação. O runtime rejeita essas identidades legadas e exige
um novo conector `OmniRoute Codex v2`.

## Modelo de segurança

- O caminho nativo requer um pedido Responses, um cliente Codex reconhecido e identidades de
  thread e de turno correspondentes.
- O espaço de trabalho, a sandbox, a política de aprovação e o catálogo de ferramentas provêm da shell nativa do Codex;
  o texto livre do prompt não constitui autoridade para os mesmos.
- O ChatGPT recebe apenas uma capacidade de curta duração por turno. O broker MCP aceita apenas
  as ferramentas que o Codex disponibilizou nesse turno específico.
- A confirmação automática de **Permitir uma vez** apenas devolve o pedido da ferramenta ao Codex. Apenas o Codex
  decide sobre a aprovação e a execução.
- Antes do primeiro resultado, uma combinação pode recorrer a outro alvo compatível. Depois de
  o resultado começar, o fornecedor, o modelo, a ligação e o turno do browser permanecem fixos até o
  turno ser concluído.
- Os cookies, as chaves de runtime, o estado de armazenamento e os tokens de capacidade não aparecem nas respostas
  do fornecedor nem nos registos de pedidos.

## VPS sem ecrã e Docker

Para instalações com npm, systemd e PM2, o OmniRoute deteta caminhos comuns do Chrome e do Chromium.
Em alternativa, defina `CHATGPT_WEB_CODEX_CHROME_PATH`. Os turnos de runtime utilizam deliberadamente o
Chrome com interface gráfica, porque o ChatGPT rejeita a configuração de um browser verdadeiramente headless. Por conseguinte, um anfitrião sem ecrã tem de
executar o OmniRoute com um ecrã Xvfb privado; definir apenas o caminho do Chrome não disponibiliza um.

O perfil `web` do Docker inicia `chatgpt-web-codex-browser` na rede interna do
Compose. O sidecar executa o Chrome com interface gráfica dentro do Xvfb, pelo que não é necessário um ecrã físico. A respetiva porta
CDP não é publicada no anfitrião. O volume protegido do perfil do browser é separado do
volume de dados do OmniRoute, e o browser recebe memória partilhada suficiente. O proxy CDP interno
escuta apenas na porta `9223` dentro da rede do Compose; o Chrome permanece associado ao loopback no
sidecar.

Um lease de supervisor em `DATA_DIR` impede que vários processos do OmniRoute controlem
o mesmo estado do túnel e do broker. Um conflito é reportado pelo doctor.

## Recuperação interativa

O processo automatizado do Docker não tem uma janela visível no anfitrião, mas o próprio Chrome é executado com interface gráfica no
ecrã Xvfb privado. Quando o ChatGPT exige um início de sessão ou desafio interativo, a infraestrutura VNC
existente do browser pode ser utilizada para recuperação. A interface do browser e o CDP têm de permanecer acessíveis apenas
através de loopback, de uma ligação de gestão autenticada ou de um túnel SSH; o noVNC permanece desativado
durante o funcionamento normal.

## Fallback de WebSocket

Quando uma combinação contém o ChatGPT Web (Codex), a ponte WebSocket de Responses solicita o
fallback HTTP/SSE antes de estabelecer a ligação upstream. A transferência é então efetuada através de
`/v1/responses`.
