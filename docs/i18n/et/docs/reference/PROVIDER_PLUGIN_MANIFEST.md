`open-sse/config/providerPluginManifest.ts` määratleb JSON-ohutu teenusepakkuja
plugina lepingu. `open-sse/config/providerPluginManifestRegistry.ts` seob selle
lepingu praeguse teenusepakkujate registriga külgprotsesside, nagu Bifrost,
CLIProxyAPI või tulevane Go/Rust ruuter, jaoks. TypeScripti register jääb
tõeallikaks, kuid külgprotsessid saavad manifesti kasutada ilma täituri koodi,
OAuthi vaikeväärtusi, päiseid või protsessi keskkonnaolekut importimata.

Sama manifest on HTTP kaudu saadaval aadressil
`GET /api/v1/provider-plugin-manifest` protsessiväliselt töötavate külgprotsesside jaoks.

OmniRoute edastab selle URL-i Bifrostile ja CLIProxyAPI-le
päringupäise `X-OmniRoute-Provider-Manifest-Url` kaudu. Määrake
`OMNIROUTE_PROVIDER_MANIFEST_URL`, kui külgprotsess vajab kohaliku päringu päritolu
asemel avalikku või konteinerivõrgu URL-i.

## Manifesti värskendamine

HTTP lõpp-punkt tagastab `Cache-Control: public, max-age=60` ja tugeva
`ETag`-i. Külgprotsess peaks säilitama viimati valideeritud manifesti ja saatma
värskendamisel selle ETag-i päises `If-None-Match`. Vastusel `304 Not Modified`
puudub keha; külgprotsess säilitab vahemällu salvestatud manifesti. Kui valideeritud
vahemällu salvestatud manifesti pole, peab külgprotsess `304` aktsepteerimise asemel
tegema tingimusteta päringu.

## Eesmärk

Liigutada teenusepakkuja metaandmed pluginalepingu suunas, et madalama
latentsusega külgprotsess saaks lõpuks kuuma päringutee üle võtta, samal ajal kui
OmniRoute säilitab TypeScripti marsruudi reeglite jõustamise kihina ja
varuvariandina. Manifest on lisanduv: see ei muuda iseseisvalt päringute
marsruutimist.

## Leping

Manifest sisaldab järgmist:

- teenusepakkuja ID ja alias
- ülesvoolu vorming ja täituri nimi
- autentimise tüüp, autentimispäis ja valikuline autentimise prefiks
- staatilised lõpp-punkti metaandmed
- sobivus külgprotsessile ja selgesõnalised põhjused, miks teenusepakkuja peaks jääma TS-i
- JSON-ohutud mudeli metaandmed, nagu konteksti pikkus, pildi- ja arutlusvõime lipud ning
  toetamata parameetrid
- võimekussildid, sealhulgas `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` ja `usage-supported`

Manifest jätab tahtlikult välja:

- OAuthi kliendisaladused ja saladuste vaikeväärtused
- käitusaegse keskkonna lahendamise
- päringupäised ja avalike mandaatide abifunktsioonid
- dünaamilised URL-i koostajad
- täiturifunktsioonid
- seansikogumi sisemised üksikasjad

## Võimekussildid

`capabilities` on registrikirjest tuletatud sorteeritud siltide massiiv. Integreerijad
peaksid käsitlema seda masinloetava vastusena küsimusele „mida see teenusepakkuja suudab“,
selle asemel et TypeScripti lähtekoodi uuesti läbi lugeda.

| Silt                 | Tähendus                                                                          |
| -------------------- | --------------------------------------------------------------------------------- |
| `apikey`             | Aktsepteerib API-võtit (`authType` on `apikey` või `optional`).                   |
| `oauth`              | Kasutab OAuthi või seansivoogu.                                                   |
| `responses`          | Avaldab OpenAI Responses API baas-URL-i.                                          |
| `passthrough-models` | Pakub mudeleid staatilise kataloogi asemel otse ülesvoolust.                      |
| `custom-executor`    | Käitab mittevaikimisi täiturit, mistõttu jääb TypeScripti päringuteele.           |
| `sidecar-candidate`  | Peegeldab välja `sidecar.eligible` — külgprotsessi importimiseks ohutu kandidaat. |
| `usage-fetch`        | Kasutuse või kvoodi hankija (`getUsageForProvider`) on ühendatud.                 |
| `usage-supported`    | Kasutus-API aktsepteerib seda teenusepakkujat (`isSupportedUsageConnection`).     |

`usage-fetch` on mõeldud ainult tuvastamiseks. See näitab, et OmniRoute oskab
teenusepakkuja kasutusandmeid lugeda; see ei aktiveeri andmete hankimist, ei muuda
kvoodisemantikat ega tähenda, et juhtpaneeli kvoodividin on teenusepakkuja jaoks
lubatud — seda vidinat juhib eraldi `USAGE_SUPPORTED_PROVIDERS`. Tõeallikas on
`USAGE_FETCHER_PROVIDERS` failis `open-sse/services/usage/fetcherProviders.ts`.

See loend kasutab võtmetena kasutuse dispetšeri aktsepteeritavaid sõnesid, mistõttu
sisaldab see nii kanoonilisi ID-sid kui ka aliaseid ja on veidi pikem kui sildistatud
teenusepakkujate arv: kirjetel, mis pole manifestiregistris vestlusteenuse pakkujad
(näiteks otsinguteenuse pakkuja `firecrawl` ja ACP teenusepakkuja `amazon-q`), puudub
sildistatav manifestikirje.

`usage-supported` näitab, kas serveri ja juhtpaneeli kasutusmarsruudid aktsepteerivad
teenusepakkuja ühendust. See peegeldab funktsioone `isSupportedUsageConnection()`
(`src/lib/usage/providerLimits.ts`) ja `supportsProviderQuota()`
(`src/shared/utils/providerQuotaVisibility.ts`), mida mõlemat juhib
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). Erinevalt
sildist `usage-fetch` väljastatakse see ainult teenusepakkuja ID alusel — käitusaegne
kontroll teeb `USAGE_SUPPORTED_PROVIDERS.includes(providerId)` ilma aliaste
lahendamiseta, seega säilitab manifest sama reegli. Kahel sildil on erinevad
kohaldamispiirid: kolm teenusepakkujat kannavad ainult silti `usage-fetch`
(`opencode`, `opencode-zen`, `xai`) ja üks ainult silti `usage-supported`
(`xiaomi-mimo-token-plan`), seega ei tulene üks teisest.

## Sidecar'i kasutamine

Sidecar'id peaksid käsitlema `sidecar.eligible` konservatiivse kandidaadisignaalina, mitte tingimusteta marsruutimisotsusena. Esimeseks importimise sihtmärgiks peaksid olema API-võtit ja staatilist lõpp-punkti kasutavad teenusepakkujad, mis kasutavad vaikimisi täiturit. Kohandatud veebitäiturite, OAuth-/seansivoogude, dünaamiliste URL-i koostajate või puuli konfiguratsiooniga teenusepakkujad jäävad TypeScripti varuteele seni, kuni sidecar rakendab samaväärse käitumise ja telemeetria tõendab pariteeti.

Soovitatud migratsioonietapid:

1. Genereerige ja valideerige teenusepakkuja pistikprogrammi manifest TS-i registri põhjal.
2. Õpetage Bifrost või CLIProxyAPI importima API-võtit/staatilist lõpp-punkti kasutavate teenusepakkujate manifesti.
3. Marsruutige sobivad teenusepakkujad sidecar'i kaudu `OMNIROUTE_RELAY_BACKEND` taga, hoides TS-i varutee lubatuna.
4. Viige teenusepakkujad üle ainult siis, kui edukuse määr, p99 latentsus, voogedastuse käitumine ja toetamata parameetrite käsitlemine vastavad TS-i teele.
5. Lisage kohandatud täiturite jaoks sidecar'i omapistikprogramme ühe teenusepakkujate perekonna kaupa.

## Miks mitte manustada teenusepakkujaid otse Nexti

Nexti kasutajaliides ei tohiks teenusepakkujate käitamist hallata. See peaks kutsuma API piiri. Seejärel saab tagasüsteem otsustada, kas kasutada TypeScripti täiturit, Bifrosti, CLIProxyAPI-t või tulevast natiivset sidecar'i. Nii jäävad päringute allkirjastamine, lubatud loendi kontrollid, andmebaasipoliitika ja varukäitumine tsentraliseerituks enne mis tahes sidecar'ile üleandmist.
