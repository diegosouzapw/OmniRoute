> **Lühidalt**: `open-sse/` on keskne voogedastusmootor, mis käitab OmniRoute'is iga LLM-päringut. See sisaldab ligikaudu 1400 faili, mis teostavad päringukonveieri, täiturid, teenused, MCP-serveri ja tõlkekihi. See juhend selgitab, kuidas osad omavahel kokku sobituvad.

**Lähtekood:** `open-sse/` (tööruumipakett, ligikaudu 1440 testivälist `.ts`-faili)

## Miks eraldi tööruumipakett?

`open-sse/` on OmniRoute'i monorepos **iseseisev tööruum** mitmel põhjusel:

1. **Taaskasutatavus** — `open-sse` avaldatakse npm-is paketina `@omniroute/open-sse`, seega saavad teised projektid seda iseseisvalt kasutada
2. **Selged piirid** — voogedastusmootor on OmniRoute'i-spetsiifilisest kasutajaliidese/andmebaasi kihist lahutatud
3. **Jõudlus** — mootoril puuduvad Next.js-i sõltuvused, mis võimaldab CLI- ja serverivabades keskkondades kiiremat külmkäivitust
4. **Versioonihaldus** — `open-sse` saab versioone avaldada oma ajakava järgi

```json
// package.json
"workspaces": ["open-sse"]
```

## Päringukonveier

Iga LLM-päring läbib **5-etapilise konveieri**:

```
                              ┌──────────────┐
   HTTP-päring                 │  1. MARSRUUT │   kombinatsiooni lahendamine, mudeli valimine
   (Next.js-i marsruut)        └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. TÕLGI    │   vormingu teisendamine (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. KÄIVITA  │   pakkuja täitur, HTTP, korduskatsed, kaitselüliti
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. VOOG     │   SSE teisendamine, vastusurve
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. SALVESTA │   kasutuse jälgimine, kõnelogi, vigade liigitamine
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP-vastus (SSE või JSON)
```

### 1. etapp: marsruutimine (services/combo.ts)

**Sisenemispunkt**: `handleComboChat()` failis `services/combo.ts`

Lahendab päringu konkreetseks `(provider, model, account, credentials)` ennikuks:

- Otsib kombinatsiooni ID järgi (või koostab `auto/*`-mudelite jaoks virtuaalse kombinatsiooni)
- Rakendab marsruutimisstrateegiat (prioriteet, kaalutud, tsükliline jne)
- Filtreerib välja mittetöötavad pakkujad (kaitselüliti)
- Valib järgmise sobiva sihtmärgi

`auto/*`-mudelite puhul teeb see etapp ka järgmist:

- Käitab **16 teguriga hindamisalgoritmi** (`services/autoCombo/`)
- Valib tervise, maksumuse, latentsuse jne põhjal `provider+model` paari

### 2. etapp: tõlkimine (translator/)

Kui lähtevorming (nt OpenAI) erineb sihtvormingust (nt Claude), siis päring **tõlgitakse**:

- Süsteemiviip → süsteemisõnum
- Tööriistade definitsioonid → pakkujapõhine tööriistavorming
- Arutlus-/mõtlemisparameetrid → pakkujapõhised vasted
- Sõnumirollide normaliseerimine (`developer` → `system` muude kui OpenAI pakkujate puhul)

`translator/index.ts` ekspordib:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### 3. etapp: käivitamine (executors/)

**Sisenemispunkt**: `getExecutor(providerId).execute(request, options)`

Kõik pakkujad kasutavad `getExecutor()` tehase varumehhanismi kaudu `DefaultExecutor`-it (`executors/default.ts`). Täitur:

- Koostab ülesvoolu URL-i (`buildUrl()`)
- Lisab pakkujapõhised päised (`buildHeaders()`)
- Teisendab päringu keha (`transformRequest()`)
- Saadab HTTP-päringu koos korduskatsete ja eksponentsiaalse ooteaja pikendamisega
- Vajaduse korral värskendab autentimist (OAuthi pakkujad)

Kõik täiturid laiendavad `BaseExecutor`-it (`executors/base.ts`, 1170 koodirida), mis pakub järgmist:

- Ühine korduskatsete loogika
- Puhverserveri integratsioon
- Kaitselüliti integratsioon
- Kasutuse salvestamise konksud

### 4. etapp: voogedastus (utils/stream.ts)

Voogedastusega vastuste korral tagastab täitur **ReadableStream**-i. Töötleja:

- Suunab voo läbi SSE-teisenduse (`createSSETransformStreamWithLogger`)
- Rakendab südamelöögipäringuid katkenud ühenduste tuvastamiseks
- Käsitleb kliendi ühenduse katkemist sujuvalt (`pipeWithDisconnect`)
- Teisendab SSE → JSON klientide jaoks, mis voogedastust ei kasuta

Voogedastuseta vastuste korral tagastab täitur parsitud JSON-objekti, mis edastatakse muudatusteta.

### 5. etapp: salvestamine (services/usage.ts)

Pärast vastust (õnnestunud või nurjunud) salvestatakse kasutusandmed:

- vastusest pärinevad `prompt_tokens`, `completion_tokens`, `cached_tokens`
- hinnateabe põhjal arvutatud `cost_usd`
- `latency_ms`, `status`, nurjumise korral `error_class`
- salvestatakse tabelisse `usage_history`

Kõnelogi artefaktid (kui need on lubatud) kirjutatakse asukohta `${DATA_DIR}/call_logs/`.

## Võtmefailide põhjalik ülevaade

### chatCore.ts (5977 rida)

**Põhiline päringute töötleja**. Vaatamata oma mahukusele on sellel selge struktuur:

```ts
// chatCore.ts pseudo-struktuur
export async function handleChat(request: NextRequest) {
  // 1. Autentimine + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Päringu keha valideerimine
  const body = await parseRequestBody(request);

  // 3. Formaadi tuvastamine + tõlkimine
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Kombosuunamine
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Jätka järgmise sihtmärgiga
    }
  }

  // 5. Avariiline varumehhanism
  return await emergencyFallback(body);
}
```

Kuigi tegemist on ühe hiiglasliku funktsiooniga, on see jaotatud **kommenteeritud sektsioonideks**, mis vastavad 5-astmelise pipeline'i etappidele.

// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);

      log.warn("target failed, trying next", { target, err });

## Executorid (150 moodulit)

Enamasti üks fail pakkuja kohta. Kõik executori klassid laiendavad `BaseExecutor`-it ja alistavad vaid selle, mis erineb; ülejäänud moodulid on pakkujapõhised abimoodulid (tööriistade skeemid, fetch/TTS-adapterid, eripärade käsitlejad).

### Levinud mustrid

Pakkuja tuvastamine toimub funktsiooni `getExecutor(providerId)` kaudu, mis tagastab seadistatud executori. OpenAI/Anthropic-ga ühilduvad pakkujad kasutavad `DefaultExecutor`-it (`executors/default.ts`). Pakkujaspetsiifiline käitumine (baas-URL, autentimispäised, API versioon) seadistatakse kataloogis `open-sse/config/providers/`, päringu keha teisendusi käsitletakse aga kataloogis `open-sse/translator/`.

**Kohandatud URL** määratakse pakkuja konfiguratsiooni kaudu:

```ts
// Pakkuja konfiguratsioon kataloogis open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Kohandatud autentimine** toimub pakkujate registri autentimiskonfiguratsiooni kaudu (API võti, OAuth, päisteprofiilid).

**Kohandatud päringu keha** teisendused (nt Anthropic eraldab `system` parameetri `messages` parameetrist) registreeritakse iga pakkuja kohta kataloogis `open-sse/translator/`.

````

### Executorite tehas

`executors/index.ts` ekspordib `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Lahendus käib läbi `ExecutorRegistry` (`executors/registry.ts`): iga spetsialiseeritud executor on deklareeritud faili `executors/index.ts` sisseehitatud tabelis ja registreeritakse funktsiooniga `registerExecutor(alias, instance)` mooduli laadimise ajal; `getExecutor()` pöördub registri poole ja kasutab tagavarana memoizeeritud `DefaultExecutor`-it iga pakkuja jaoks, kellel pole spetsialiseeritud kirjet. Täielikku aliase → executori vastavust iseloomustab kuldtest `tests/unit/executor-map-golden.test.ts`.

## Tõlkijad

Tõlkige **3 vormingu** vahel: OpenAI, Anthropic, Gemini ning uus Responses API.

### Millal tõlkimine toimub

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Levinud teisendused:

- `OpenAI → Anthropic`: eraldi `system` väli, `x-api-key` päis
- `OpenAI → Gemini`: `messages` asemel `contents`, `systemInstruction`
- `OpenAI → Responses API`: `input` massiiv, `previous_response_id` olek

### Käsitletavad erijuhud

- `developer` roll → `system` mitte-OpenAI vormingute jaoks
- `system` roll → GLM-i/ERNIE puhul liidetakse esimese kasutaja sõnumiga
- `json_schema` → Gemini `responseMimeType` + `responseSchema`
- `tools` → teenusepakkujapõhine tööriistavorming
- Mõtlemisparameetrid (o1, Claude) → teenusepakkujapõhised vasted

## MCP-server

`open-sse/mcp-server/` teostab **Model Context Protocoli** serveri:

- **110 tööriista** (teenusepakkujate haldus, kombinatsioonid, mälu, vahemälu, tihendamine, puhverserver, oskused, mängustamine, pistikprogrammid, Notion, Obsidian, kohalik korpus)
- **3 transpordiviisi**: stdio, SSE, voogedastatav HTTP
- **33 ulatust** detailseks autoriseerimiseks

### Tööriistade registreerimine

Tööriistad registreeritakse eraldiseisvate failidena kataloogis `open-sse/mcp-server/tools/`, millest igaüks ekspordib nime, skeemi, töötleja ja ulatuse:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Süsteemi seisundi hetktõmmise hankimine",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transpordiviisid

```ts
// stdio (CLI-s kasutamine)
startMcpStdio(server);

// SSE (HTTP-põhine voogedastus)
startMcpSse(server, port);

// Voogedastatav HTTP (tänapäevane MCP)
startMcpStreamable(server, port);
```

### Autoriseerimine

Iga tööriistakutse läbib ulatusekontrolli (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Ebapiisav ulatus");
}
```

## Teisendajad

`open-sse/transformer/` teisendab **Chat Completionsi** ja **Responses API** vormingute vahel.

### Miks eraldi teisendaja?

Responses API on OpenAI uus vorming, mis toetab **olekuga vestlusi** (`previous_response_id`). Kui klient saadab Responses-päringu, teeb OmniRoute järgmist:

1. Teisendab Responses-vormingu sisemiselt Chat Completionsi vorminguks
2. Saadab selle teenusepakkujale (mis tahes teenusepakkujale, kes toetab Chat Completionsi)
3. Teisendab vastuse tagasi Responses-vormingusse
4. Voogedastab teisendatud vastuse kliendile

Teisendaja (`transformer/responsesTransformer.ts`) pakub järgmist:

```ts
createResponsesApiTransformStream(): TransformStream
```

See käsitleb järgmist:

- `response.output_item.added` sündmused
- `response.output_text.delta` sündmused
- `response.completed` sündmus
- Tööriistakutsete vastendamine (`function_call` ↔ `tool_calls`)

## Konfiguratsioon

`open-sse/config/` sisaldab konfiguratsioonikihti:

| Fail                          | Otstarve                                               |
| ----------------------------- | ------------------------------------------------------ |
| `providerRegistry.ts`         | Vestlusmudelite register 375 pakkujaga kataloogi kohal |
| `providerModels.ts`           | Mudelite aliased, formaadi vastendamine                |
| `constants.ts`                | Ajalõpud, piirangud, olekukoodid                       |

| `modelStrip.ts` (teenustes)   | Väljade eemaldamine pakkujapõhiselt                    |

### Pakkujate registri skeem

```ts
interface ProviderConfig {
  id: string;

  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

## Uue komponendi lisamine

### Uue teenuse lisamine

1. Looge selgelt piiritletud vastutusalaga fail `open-sse/services/[serviceName].ts`
2. Eksportige peamine töötleja funktsioon ja kõik konstandid
3. Lisage üksustestid faili `tests/unit/services/[serviceName].test.mjs`
4. Integreerige teenus päringukonveierisse failis `handlers/chatCore.ts` (kui see on seotud marsruutimisega)
5. Kui teenus mõjutab sihtmärgi valimist, värskendage marsruutimisloogikat failis `combo.ts`
6. Dokumenteerige selles failis

### Uue täituri lisamine

1. Looge klassi `BaseExecutor` laiendav fail `open-sse/executors/[provider].ts`
2. Registreerige see failis `config/providerRegistry.ts`
3. Lisage see faili `executors/index.ts` tehasesse
4. Lisage täituri üksustestid
5. Dokumenteerige failis `docs/architecture/ARCHITECTURE.md`

### Uue MCP-tööriista lisamine

1. Looge või värskendage faili `open-sse/mcp-server/tools/[category]Tools.ts`
2. Määratlege sisendite Zod-skeem
3. Registreerige tööriist failis `mcp-server/index.ts`
4. Lisage see kataloogis `mcp-server/auth/` asuvasse õiguste maatriksisse
5. Lisage üksustestid
