Kasutage seda juhendit, et valida pull request'i jaoks väikseim töökindel arendustsükkel. See ei
asenda allpool lingitud valdkonnapõhiseid arhitektuuri- ja turbedokumente, vaid seob iga levinud
muudatuse tüübi selle lepingute, sihitud kontrollide ja CI-katvusega.

## Iga muudatuse teekond

1. **Valige enne muutmist alusharu.** Leidke kõrgeima versiooniga aktiivne `release/v*` haru ja looge
   uus haru selle tipust. Määrake sihiks see haru, mitte `main`. Kui väljalaske külmutamine on aktiivne,
   ärge määrake sihiks külmutatud haru, vaid kasutage järgmist aktiivset tsüklit, mida kirjeldab
   [harundamis- ja väljalaskemudel](BRANCHING_MODEL.md).
2. **Nimetage lepingud.** Tuvastage kõik kataloogid, skeemid, genereeritud artefaktid, avalikud API-d
   või kasutajaliidesed, mida muudatus mõjutab. Allolev tabel esitab minimaalse lähtekomplekti.
3. **Kirjutage või uuendage sihitud teste.** Tootmiskoodi muudatused kataloogides `src/`, `open-sse/`,
   `electron/` või `bin/` nõuavad samas PR-is automatiseeritud testi. Käivitage esmalt väikseimad
   testifailid, mis käitumist tõendavad, ja seejärel loetletud sihitud kontrollid.
4. **Laske CI-l käivitada lai maatriks.** PR-is käivitatakse kõik ühiktestide killud, Vitest,
   katvuse lävendikontroll ja tootmisversiooni ehitamine. Käivitage lai testikomplekt lokaalselt ainult
   siis, kui sihitud tõrge viitab laiemale mõjule või kui muudatus hõlmab mitut alamsüsteemi.
5. **Ühtlustage enne ülevaatust.** Tõmmake aktiivse alusharu värske seis, vaadake üle selle uued
   commit'id ja oma muudatuste erinevus sellest ning tehke seejärel vastavalt panustaja töövoole rebase
   või merge alusharuga. Lahendage genereeritud failide ja kataloogide konfliktid nende lähteallikas,
   genereerige need uuesti, käivitage sihitud tsükkel uuesti ning veenduge, et PR-i siht on endiselt
   aktiivne väljalaskeharu.
6. **Jäädvustage tõendid.** Loetlege PR-i mallis käivitatud käsud, kõik lisatud või muudetud
   testifailid, migratsioonid või funktsioonilipud ning kõik veel ootel olevad ainult CI-s tehtavad
   valideerimised.

## Soovituslikud teekonnad muudatuse tüübi järgi

Allolevad käsud on minimaalsed sihitud kontrollid, mitte luba jätta käivitamata test, mis katab
otseselt teie muudetud käitumist.

### Teenusepakkuja

**Lepingud**

- Teenusepakkuja definitsioon kataloogis `src/shared/constants/providers/` ja selle koondamine failis
  `src/shared/constants/providers.ts`.
- Mudelid ja võimekused failis `open-sse/config/providerRegistry.ts` või sellest eraldatud registrifailides.
- Täituri/tõlkija valik, OAuthi või API-võtme konfiguratsioon, töölaua ressursid ja genereeritud
  teenusepakkuja viited, kui need on asjakohased.
- Avalikud identimisteabe andmed peavad kasutama funktsiooni `resolvePublicCred()`; veavastused peavad
  kasutama ühiseid puhastatud vea abifunktsioone. Vaadake `docs/security/PUBLIC_CREDS.md` (git'is;
  ei kompileerita kataloogi `/docs`) ja
  [vigade puhastamist](../security/ERROR_SANITIZATION.md).

**Sihitud tsükkel**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # kui kataloog muutub; commit'ige genereeritud erinevus
npm run lint
```

Testige ka iga mõjutatud päringuperet: vestlus, Responses, pildid, manused, heli või video.
Käsitlege genereeritud kataloogi ja etalonide erinevusi lepingumuudatustena; ärge aktsepteerige neid
pimesi.

### Marsruutimine

**Lepingud**

- Avalikud strateegiaväärtused ja kasutajaliidese metaandmed failis
  `src/shared/constants/routingStrategies.ts`.
- Suunamine ja järjestamine failis `open-sse/services/combo.ts` ning kataloogis
  `open-sse/services/combo/`.
- Kombinatsioonide skeemid, püsivus, vastupidavuse olek, mudelite võimekused ning API/kasutajaliidese
  juhtelemendid.
- [Automaatse kombineerimise mootor](../routing/AUTO-COMBO.md) ja vastupidavuse dokumentatsioon, kui
  käitumine muutub.

**Sihitud tsükkel**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strateegia või suunamise muudatused
npm run check:known-symbols      # strateegia registreerimise muudatused
npm run lint
```

Kasutage lokaalselt deterministlikke teste, milles ülesvoolu teenused on matkitud. Reaalajas
kombinatsioonide suitsutestid nõuavad identimisteavet ja on käsitsi käivitatavad, mitte CI asendajad.

### UI / UX

**Lepingud**

- Next.js-i marsruudi/lehe ja jagatud komponentide piirid kataloogides `src/app/` ja
  `src/shared/components/`.
- API vastuste kujud, laadimis-, tühjad ja veaolekud, klaviatuuri ja ekraanilugeri käitumine,
  kohanduv paigutus, kujundus ning lokaatide laiendamine.
- Ingliskeelsed kasutajaliidese lähtestringid failis `src/i18n/messages/en.json`; ärge kirjutage uut
  kasutajale nähtavat teksti otse koodi.

**Sihitud tsükkel**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Käivitage rakendus interaktsiooni- või visuaalsete muudatuste korral ning kontrollige nii kitsaid kui
ka laiu vaatealasid. CI käivitab tootmisversiooni ehitamise ja laiemad testikomplektid; visuaalne
käitumine vajab siiski sihitud komponenditesti, Playwrighti testi või muudatusele sobivat
dokumenteeritud käsitsi kontrolli.

### i18n

**Lepingud**

- `src/i18n/messages/en.json` on kasutajaliidese lähtefail; `config/i18n.json` on lokaatide lähtefail.
- CLI-kataloogid asuvad eraldi kataloogis `bin/cli/locales/`.
- Säilitage ICU kohatäited ja sildid täpselt. Ärge tõlkige toote-, teenusepakkuja- ega mudelinimesid,
  protokolli- ja päisenimesid, käske, koodi/JSON-i identifikaatoreid, URL-e, keskkonnamuutujaid ega
  kaitstud termineid, nagu `OmniRoute`, `OAuth`, `MCP` ja `A2A`. Praegune lähteloend on
  `scripts/i18n/glossary/protected-terms.json`.

**Sihitud tsükkel**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # kui CLI stringid/kataloogid muutuvad
npm run lint
```

See on olemasoleva süsteemi juhis, mitte kutse laiendada selle tööriistu või võtmemudelit.
Hoidke i18n-i parandused täpselt piiritletuna, kuni asendussüsteemi kavandatakse. Ärge käivitage
väliste teenuste poole pöörduvaid tõlkekäske, välja arvatud juhul, kui ülesanne nõuab sõnaselgelt
genereeritud tõlkeid ja olete tekkiva erinevuse üle vaadanud.

### CLI

**Lepingud**

- Avalikud käsud ja lipud kataloogis `bin/cli/`, genereeritud API käsud, väljumiskoodid, stdout/stderr ja
  JSON-väljundi struktuurid, konfiguratsiooni-/keskkonnakäitumine ning pakendatud failid.
- CLI kasutajale kuvatavad tekstid peavad kasutama CLI i18n-kihti ning `en`/`pt-BR` kataloogid peavad olema kooskõlas.
- Säilita Node toetatud käituskeskkonnana ja avaldatud kahendfaili leping.

**Fookustatud tsükkel**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # genereeritud/pakendatud CLI muudatused
npm run check:pack-policy     # paketi avaliku pinna muudatused
npm run lint
```

Kui käitumine sõltub parsimisest, failidest või väljumisolekust, kasuta täpset käsku ajutises andmekataloogis.
CI teeb laiemad paketi artefakti- ja ökosüsteemikontrollid.

### Andmebaas

**Lepingud**

- Domeenimoodulid asuvad kataloogis `src/lib/db/`; impordi konkreetsed moodulid otse (vana `localDb.ts` reeksportimise kiht on eemaldatud).
- Nummerdatud ja idempotentsed SQL-migratsioonid kataloogis `src/lib/db/migrations/`, tehinguohutus, uuendamise
  käitumine, indeksid ning kõik skeemist mõjutatud väljakutsujad.
- Marsruudid ja töötlejad ei väljasta kunagi otse töötlemata SQL-i.

**Fookustatud tsükkel**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migratsiooni lisamisel testi nii värsket andmebaasi kui ka eelmiselt skeemilt uuendamist. Andmebaasitestid
peavad puhastamise käigus sulgema pidemed ja kutsuma välja `resetDbInstance()`. Käivita `npm run test:bun:db` ainult siis,
kui muutub Bun-adapteri parima võimaliku toe tee; Node jääb autoriteetseks.

### Koostamine / juurutamine

**Lepingud**

- Juur- ja tööruumi manifestid/lukufail, `scripts/build/`, Next.js-i autonoomne komplekteerimine, `dist/`
  paketi sisu, Electroni platvormi metaandmed, CI töövood ja juurutuse kontrollmarkerid.
- Toetatud Node versioonivahemikud ja failis `CLAUDE.md` lubatud Bun-kasutus peavad säilima.
- Koosteartefakte ei lisata versioonihaldusse; kehtivad sõltuvuste, litsentside, töövoogude ja pakettide reeglid.

**Fookustatud tsükkel**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # sõltuvuste või lukufaili muudatused
npm run check:pack-policy      # avaldatud paketi pinna muudatused
npm run lint
```

Kasuta käsku `npm run build` lokaalselt ainult siis, kui muudatus mõjutab kompileerimist, autonoomset komplekteerimist, varasid
või käitusaegset pakendamist. Kasuta käsku `npm run build:release` ainult väljalaske/juurutuse valideerimiseks. CI koosteprotsess on
lõplik platvormideülene indikaator; platvormipõhised Electroni muudatused vajavad vastava fookustatud kooste
või suitsutesti tõendeid.

## Kohalik kandidaaditsükkel

Lähtekoodi testid ei saa tõestada, et pakendatud artefakt käivitub: pakendamisloendite, eemaldatud sõltuvuste
ja platvormipõhiste kahendfailidega seotud vead ilmnevad alles siis, kui tarball on installitud ja käivitatud. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) on RFC #8084 ühekordse koostamise / valideerimise / edutamise voo kohalik
osa: see koostab ühe kandidaadi, valideerib täpselt selle artefakti, edutab selle kataloogide
ümbernimetamise abil ja pöörab edutamise tagasi, kui edutatud pesa seisundikontroll nurjub.

```bash
npm run dev:candidate -- run --dry-run --json  # kuva plaan ilma midagi muutmata
npm run dev:candidate -- run                   # koosta + valideeri + eduta, automaatne tagasipööramine
npm run dev:candidate -- build                 # npm pack + installimine asukohta _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # käivita vabal pordil, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # vaheta current ja previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # kasuta mujal (CI-s) koostatud tarballi
```

- **Koosta üks kord.** `build` pakendab aktiivse lähtekoodipuu (see vajab faili `dist/server.js`, seega käivita
  esmalt `npm run build:release`) või kopeerib `--from-tarball` abil, seejärel installib tarballi
  isoleeritud npm-i prefiksisse, sest tarball ei sisalda kataloogi `node_modules`. ID on lühike `HEAD`-i
  sha (`-dirty`, kui lähtekoodipuus on kohalikke muudatusi) või tarballi puhul `tgz-<sha256>`. Juba
  koostatud puhta ID-ga kandidaati kasutatakse uuesti; selle uuesti koostamiseks edasta `--force`.
- **Valideeri paketti, mitte lähtekoodi.** `validate` käivitab installitud CLI
  (`serve --port <free port>`) värske `DATA_DIR=<candidate>/data`, fiktiivsete saladustega ning eemaldab
  operaatori `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` ja `INITIAL_PASSWORD` keskkonnast, et
  kontrollida värske installi võtmeta loopback-režiimi. See ootab, kuni `GET /api/health` tagastab 200,
  nõuab, et `GET /v1/models` tagastaks 200, peatab protsessirühma ja salvestab tulemuse faili
  `validation.json` koos tarballi räsiga.
- **Eduta sama artefakt.** `promote` keeldub kandidaadi edutamisest, kui selle praeguse tarballi räsi
  valideerimine ei ole edukalt läbitud. Vaikimisi aktiivne pesa on `_artifacts/candidate/current`;
  `--target <dir>` valib samas failisüsteemis teise kataloogi ja selle eelmine pesa on
  `<dir>.previous`. Iga ümbernimetamine on atomaarne ning vahepealse tõrke korral pööratakse juba
  tehtud ümbernimetamised tagasi.
- **Pööra tagasi.** `run` valideerib edutatud pesa uuesti ning vahetab `current` ja `previous` tagasi,
  kui see kontroll nurjub. Esimesel valideerimisel nurjunud kandidaati ei edutata kunagi.

Kõik kirjutatakse giti ignoreeritavasse kataloogi `_artifacts/candidate/`; olemasolevat OmniRoute'i
installatsiooni ega selle andmekataloogi ei muudeta kunagi. Edutatud CLI asub teel
`_artifacts/candidate/current/prefix/bin/omniroute`; kasutamisel käivita see oma `DATA_DIR`-iga.
Väljumiskoodid: `0` õnnestumine, `1` nurjunud valideerimine või edutamine, `2` kasutusviga või puuduv koosteversioon.

## Kohalik tsükkel võrreldes CI-ga

| Käivita iga paiga puhul kohalikult                                                                        | CI annab laiaulatusliku signaali                                                       |
| --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Ülaltoodud otsesed käitumistestid ja kategooriaväravad                                                    | Osadeks jaotatud täielik ühiktestide komplekt ja järjestikused testid                  |
| `npm run lint`                                                                                            | Vitesti testikomplektid ning katvuse/kvaliteedi järkjärgulised lävendid                |
| Tüübikontroll või ehitamine ainult siis, kui mõjutatud leping seda nõuab                                  | Tootmisversiooni ehitamise, turbe, dokumentatsiooni, sõltuvuste ja PR-reeglite väravad |
| Käsitsi interaktsiooni-/reaalajakontrollid ainult siis, kui automatiseerimine ei suuda käitumist tõendada | Töödevahelised integratsiooni- ja platvormikontrollid, mis on töövoos seadistatud      |

Roheliselt läbitud sihitud tsükkel on tõend muudetud lepingu kohta, mitte kinnitus, et sõltumatud CI kontrollid
läbivad edukalt. Samas ära lase igal kohalikul muudatusel oodata kogu hoidla maatriksi läbimist.

## Ühitamise kontrollnimekiri

Enne ülevaatuse taotlemist:

- Veendu, et PR-i alus on endiselt kõrgeim aktiivne `release/v*` haru.
- Tõmba see alus alla ja vaata üle pärast oma haru loomist lisandunud sissekanded.
- Vaata käsuga `git diff <active-base>...HEAD` üle juhuslikud või genereeritud muudatused.
- Lahenda kataloogi ja genereeritud dokumentide konfliktid, uuendades lähteallikat ning genereerides väljundi uuesti.
- Pärast ühitamist käivita uuesti kõik PR-i kirjelduses loetletud sihitud testid/väravad.
- Ära kunagi nõrgenda kontrolle ega eemalda nõutavaid teste üksnes muutunud alusega sobitumiseks.

Väljalaske külmutamise ja sihtharu muutmise reegleid vaata dokumendist
[Harundamise ja väljalasete mudel](BRANCHING_MODEL.md). CI täieliku loendi leiad dokumendist
[Kvaliteediväravate viide](../architecture/QUALITY_GATES.md).
