## Kiirjuhend

**Kas OmniRoute on sulle uus?** Alusta siit — need lahendavad 90% probleemidest:

| Näen seda                     | Mida see tähendab                                    | Mida teha                                                                                                |
| ----------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| "Can't connect"               | OmniRoute ei tööta                                   | Käivita `omniroute` või `docker restart omniroute`                                                       |
| "Invalid API key"             | Sinu võti on vale või aegunud                        | Kopeeri võti teenusepakkuja veebisaidilt uuesti                                                          |
| "Rate limit exceeded"         | Sa saadad liiga palju päringuid                      | Oota 1 minut või kasuta automaatseks varuvariandile lülitumiseks `model: "auto"`                         |
| "Quota exceeded"              | Oled oma tasuta või tasulise kvoodi ära kasutanud    | Ühenda rohkem teenusepakkujaid või kasuta tasuta teenusepakkujaid (Kiro, Pollinations)                   |
| "Slow responses"              | Teenusepakkuja on hõivatud või asub kaugel           | Kasuta `model: "auto/fast"` või ühenda kiirem teenusepakkuja (Groq, Cerebras)                            |
| "Wrong provider used"         | `auto` valis teise teenusepakkuja                    | See on normaalne! `auto` valib parima. Kindla teenusepakkuja kasutamiseks määra `model: "openai/gpt-4o"` |
| "502 Bad Gateway"             | Teenusepakkuja ei tööta                              | Oota ja proovi uuesti või kasuta teenusepakkuja vahetamiseks `model: "auto"`                             |
| "401 Unauthorized"            | Sinu identimisteave on vale                          | Kontrolli oma API-võtit või autendi end OAuthiga uuesti                                                  |
| "omniroute is not recognized" | Windows PATH ei sisalda globaalseid node'i mooduleid | Lisa oma npm-i globaalne prefiks Windows PATH-i. Leia see käsuga `npm config get prefix`.                |
| "429 Too Many Requests"       | Rakendatud on päringusageduse piirang                | Oota 1 minut või ühenda rohkem teenusepakkujaid                                                          |

**Kas probleem püsib?** Vaata allpool olevat [üksikasjalikku tõrkeotsingut](#detailed-troubleshooting) või küsi abi [Discordis](https://discord.gg/U47eFqAXCn).

### Tasuta teenusepakkujate päringusageduse piirangud (429 / 400 / 401)

**Sümptom**: Kui kasutad `model: "auto"` koos tasuta või autentimist mittenõudvate teenusepakkujatega (opencode, auggie jne), saad vastuste asemel aeg-ajalt veateate `HTTP 429`, `400` või `401`. Kui proovid mõni hetk hiljem sama päringut uuesti, õnnestub see, kuid automatiseerimine (cron-tööd, agendid, skriptid) katkeb esimese tõrke korral.

**Algpõhjus**: Korraga kuhjuvad kolm sõltumatut tõrkerežiimi:

1. **Teenusepakkuja päringusageduse piirang (`429`)**: Tasuta paketid võivad rakendada ajavahemikupõhist kvooti. Paralleelpäringute puhang ammendab selle, mistõttu keeldutakse järgmisest päringust kuni ajavahemiku lähtestamiseni.
2. **Katkine mudel otseedastuses (`400`/`401`)**: `auto/*` kogumid võivad sisaldada `opencode`-i otseedastusmudeleid, mis on kataloogis registreeritud, kuid millel puuduvad kehtivad identimisteabe andmed (nt `oc/north-mini-code-free` → `401`). Automaatne marsruuter proovib üht neist, ebaõnnestub ja viga levib enne, kui varuvariandile lülitumine jõuab rakenduda.
3. **Samaaegsuse võimendus (koormuse all `429`)**: Kui mitu agendi- või cron-seanssi kasutavad korraga valikut `auto`, ületab päringute kogusagedus tasuta teenusepakkujate taluvuspiiri, mistõttu märgitakse ka õiguspärased päringud kuritarvitusena.

**Kontrollitud lahendus (kogukonna teatatud, 2026-08-10)**: kohanda kolme keskkonnamuutujat, et roteerimine, samaaegsuse juhtimine ja varuvariandile lülitumine leevendaksid tasuta paketi ebastabiilsust, mitte ei põhjustaks selle tõttu töö katkemist:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # liigu tõrke 400/401 korral järgmise mudeli või teenusepakkuja juurde (jätab katkised otseedastusmudelid vahele)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # raskekaaluliste päringute vastuvõtu selgesõnaline ülempiir (vaikimisi määramata: päringute arvu piirang puudub, vt allolevat märkust)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # pikem piiratud ooteaeg raskekaaluliste päringute läbilaskevõime vabanemiseks, mitte kohene uuesti proovitav tõrge 503
```

Määra need OmniRoute'i protsessi keskkonnas (deemonis, näiteks LaunchAgenti plist-faili või käsu `systemctl edit` kaudu) ja taaskäivita seejärel OmniRoute. Roteerimislipp on kõige mõjusam hoob: see muudab lõpliku tõrke läbipaistvaks korduskatseks kogumi töötava teenusepakkuja kaudu.

**Märkus**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` piirab korraga töötavate raskekaaluliste ehk pika kontekstiga päringute arvu; see piir on vastuvõtulüüs, mitte teenusepakkuja päringusageduse piiraja. **#503-fanout värskendus:** seda muutujat ei määrata enam vaikimisi (nüüd rakendub see ainult siis, kui see on selgesõnaliselt seadistatud, nagu ülal) — raskekaaluliste päringute vastuvõttu piirab selle asemel automaatselt tuletatud baidieelarve (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), mis kohandub hosti tegeliku mälupiiranguga. Seetõttu peaks värskes juurutuses esinema palju vähem tõrkega `503 chat_admission_busy` tagasilükatud päringuid, ilma et seda muutujat üldse määrataks; selle selgesõnaline määramine siin toimib endiselt täpselt dokumenteeritud viisil. Selgesõnaliselt määratud baidieelarve alampiir on 8 MiB ja ülempiir 2 GiB. Tõrge `413 body_exceeds_budget` ei ole ajutine: suurenda baidieelarvet, vähenda väärtust `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` või suurenda protsessi mälupiirangut. Koormuse vähendamine põhjusega `inflight_bytes_budget` tuleneb ajutisest ressursikonkurentsist ja päringut saab uuesti proovida. Teenusepakkujapõhiseid päringusageduse piiranguid (`open-sse/services/rateLimitManager.ts`) juhivad eraldi `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` ja `RATE_LIMIT_AUTO_ENABLE` — vaata faili `.env.example`.

**Kuidas kontrollida, et see töötas**: käivita oma agent/cron kaks korda kiiresti järjest ja veendu, et mõlemad käivitused õnnestuvad. Enne parandust annab teine käivitus tavaliselt vea `429`/`401`. Pärast parandust proovitakse ebaõnnestunud päringuid (kui neid esineb) läbipaistvalt uuesti ja kutse viiakse lõpule. Samuti võid käivitada `curl /monitoring/health` ning jälgida teenusepakkuja ühenduste välja `rateLimitedUntil` ja mõjutatud teenusepakkujate välja `circuitBreakers.providerBreakers[].state` — olek on üks järgmistest: `CLOSED`, `DEGRADED`, `OPEN` või `HALF_OPEN` (vt `src/shared/utils/circuitBreaker.ts`) ning pidevalt ebaõnnestuva teenusepakkuja olek muutub `CLOSED → DEGRADED → OPEN`, enne kui lähtestusaken lubab proovipäringu läbi (`HALF_OPEN`).

**Kui näed endiselt viga 429**: selle teenusepakkuja aktiivse konto _kvoot_ (mitte ainult päringusageduse piirang) on tegelikult ammendunud. Lisa OmniRoute’i juhtpaneelil sama teenusepakkuja jaoks teine konto: Providers → Accounts, või lisa mõni teine tasuta teenusepakkuja (nt `routeway`, `auggie`). Vahetamine aitab ainult ajutiste sageduspiirangu ning vigade 400/401 korral; kvoodi täielik ammendumine nõuab teisi identimisteavet või teist teenusepakkujat.

**Kui näed nägemismudelites (`auto/vision`, `bazaarlink/*`) viga 403**: ühendatud kontol puudub nägemisfunktsiooni sisaldav tasuline pakett või API-võtmel pole piisavaid õigusi. Veendu teenusepakkuja juhtpaneelil, et võtme õiguste ulatus hõlmab nägemis-/multimodaalseid funktsioone, või ühenda tasulise paketiga konto ja kasuta seda jätkuvalt nägemismudelite sihtkontona.

## npm installi hoiatused (ERESOLVE / partnersõltuvus / aegunud)

Kui käivitate käsu `npm install -g omniroute`, võite näha hulgaliselt hoiatusi, nagu `npm warn ERESOLVE`, partnersõltuvuste teated ja `deprecated`-sõnumid. **Need on ootuspärased ja ohutud.** Installimine õnnestus, kui väljundis kuvatakse `added <N> packages`.

Partnersõltuvuste lahendamise hoiatuste peitmiseks kasutage OmniRoute'i toetatud installimiskäsku:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` peidab ainult `ERESOLVE`- ja partnersõltuvuste teated. Aegunuks märkimise teated jäävad nähtavaks, sest need pärinevad kaudsetest kolmanda poole pakettidest; need ei tähenda, et installimine ebaõnnestus.

Hoiatused tulenevad kolmanda poole pakettide aegunud partnersõltuvuste versioonivahemikest, mida OmniRoute ei halda:

1. **`marked-terminal` nõuab versiooni `marked >=1 <16`, kuid leiti `marked@18`** — praktikas töötab see probleemideta; ülesvoolu partnersõltuvuse versioonivahemik on lihtsalt aegunud.
2. **`deprecated prebuild-install@7.1.3`** — kaudne abivahend natiivse kahendfaili hankimiseks. Seda ei
   kasutata fikseeritud versiooniga `wreq-js` transpordisideme installimiseks ning see ei tähenda, et veebiküpsiste
   pakkuja transpordi seadistamine ebaõnnestus.

**Midagi pole vaja teha** — hoiatusi ei saa täielikult vaigistada ilma ülesvoolu pakette hargnemata.

## Gemini Web ja Playwright Chromium

Kui Gemini Webi päring tagastab vastuse `503` teatega, et Playwright Chromium
pole installitud, on npm-pakett olemas, kuid brauseri kahendfail puudub.
Playwright hoiab brauseri allalaadimised teadlikult npm-paketi
installimisest eraldi, seega on selline vastus ootuspärane seni, kuni brauser installitakse.

Globaalse npm-installi korral installige Chromium OmniRoute'i paketi
kataloogist, et brauseri vahemälu kuuluks samale Playwrighti installile:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Taaskäivitage OmniRoute pärast installimist ja proovige seejärel Gemini Webi päringut uuesti. Kui
käitate OmniRoute'i Dockeri tõmmisest, kasutage `-web` tõmmist (või `runner-web`
koostesihtmärki), mis sisaldab Chromiumi ja selle sõltuvusi; põhitõmmis neid
ei sisalda.

## Viirusetõrje valepositiivsed tuvastused

<a name="antivirus-false-positives"></a>

### Avast/AVG paigutab faili `README.md` karantiini tuvastusega `MD:HttpRequest-inf[Susp]`

**See on valepositiivne tuvastus. Miski pole nakatunud ja midagi pole vaja teha.**

Avast ja AVG kasutavad heuristikat, mis märgistab lihtteksti-/Markdown-faile, mis sisaldavad palju
HTTP-päringutena näivaid linke. OmniRoute'i `README.md` sisaldub npm-paketis (see on
loetletud failis `package.json` → `files`), mistõttu paigutatakse see globaalse installimise korral
asukohta `node_modules/omniroute/README.md` — ja see sisaldab umbes 15 näidet kujul
`http://localhost:20128/...` (MCP HTTP/SSE otspunktid, A2A `.well-known` URL ja `curl`-i
näited). Sellisest linkide tihedusest piisab heuristika käivitamiseks.

Kui see algas alles hiljuti, siis faili olemus ei ole muutunud. README otspunktide tabel
laienes (lisati MCP HTTP + SSE + A2A) ja lisandus rohkem `curl`-i näiteid, mistõttu ületati
läviväärtus.

Fail on passiivne dokumentatsioon ega sisalda käivitatavat sisu. Selle võib turvaliselt
karantiinist taastada.

**Mida teha:**

1. **Peatage teavitused** — lisage installikataloog viirusetõrje välistuste hulka
   (Avast: Settings → Exceptions), lisades globaalse `node_modules`-i tee ja/või
   OmniRoute'i andmekataloogi (`~/.omniroute/`).
2. **Teatage valepositiivsest tuvastusest** — <https://www.avast.com/false-positive-file-form.php>,
   lisades karantiini paigutatud faili `README.md`. See lahendus aitab kõiki, sest probleem
   tuleneb teenusepakkuja heuristika ülereageerimisest tekstifailile.

**Miks me seda omalt poolt ei „paranda“:** kõik näited kasutavad aadressi `http://localhost`
ja localhost ei saa kasutada `https`-i ilma isesigneeritud sertifikaatidega seotud ebamugavusteta.
Dokumentatsiooni moonutamine ühe teenusepakkuja heuristikast möödahiilimiseks kahjustaks kõigi
lugejate kasutuskogemust üksnes skanneri vea rahuldamiseks.

### Kaspersky märgistab töölauarakenduse tuvastusega `PDM:Trojan.Win32.Generic`

**See on käitumusliku heuristika valepositiivne tuvastus. Miski pole nakatunud.** Kaspersky
prefiks `PDM:` tähendab, et otsus pärineb selle proaktiivse kaitse moodulilt Proactive Defense
Module (System Watcher), mis hindab installeri _tegevust_, mitte ei võrdle seda teadaoleva
pahavaraga. Tuvastuse käivitumisel „võtab Kaspersky tagasi“ kogu installimise — kustutades juba
kirjutatud failid — mistõttu rakendus jääb katki või kaob.

Märgistatud failid on töölauarakendusega kaasas olevate deklareeritud avatud lähtekoodiga
sõltuvuste tavapärased osad, näiteks:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ja
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), brauseri automatiseerimise
  teek, mida kasutatakse rakendusesiseseks teenusepakkuja kontole sisselogimiseks ja brauseripõhiseks vestluseks.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — fikseeritud versiooniga `wreq-js`-i omakompileeritud sidend, mida kasutatakse brauseri
  sõrmejäljega HTTP jaoks veebiküpsiseid kasutavate teenusepakkujate puhul (`<arch>` on `x64` või `arm64`).

**Miks see käivitub:** Windowsi installer **ei ole veel koodisigneeritud**, mistõttu
signatuurita NSIS-installeril puudub maine ja käitumuslikud heuristikad töötavad maksimaalse
agressiivsusega. Koos komplekti kuuluva omakompileeritud DLL-i ja sadade `.js`-failidega,
mis kirjutatakse kataloogi `%LOCALAPPDATA%\Programs\OmniRoute` (sealhulgas Next.js-i autonoomse
järgu räsiliitega paketikaustad), piisab sellest heuristika käivitamiseks. Koodi signeerimine
on plaanis; kuni see on tehtud, võib probleem uute väljalasetega korduda.

**Mida teha:**

1. **Esmalt kontrollige allalaaditud faili** (see välistab faili muutmise). Iga väljalase
   avaldab faili `latest.yml`, mille väli `sha512` (base64) katab installeri
   `OmniRoute.Setup.<version>.exe`. Käivitage PowerShellis installerit sisaldavas kaustas:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Väljund peab vastama väärtusele `latest.yml` → `sha512`. Kui see ei vasta, kustutage fail
   ja laadige see uuesti alla ainult [GitHubi väljalasete lehelt](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Taastage + välistage** — taastage tagasivõtmise käigus eemaldatud üksused karantiinist ja lisage
   kataloog `%LOCALAPPDATA%\Programs\OmniRoute` välistuste hulka (Kaspersky → Settings → Threats and Exclusions),
   seejärel installige rakendus uuesti.
3. **Teatage valepositiivsest tuvastusest** — <https://opentip.kaspersky.com/>. Kasutajate esitatud
   valepositiivsete tuvastuste teated kiirendavad tõepoolest lubatud loendisse lisamist.

## Node.js-i ühilduvus

<a name="nodejs-compatibility"></a>

### Sisselogimisleht jookseb kokku või kuvab vea „Module self-registration“

**Põhjus:** Kasutate Node.js-i versiooni, mis jääb väljapoole OmniRoute'i heakskiidetud turvalise käituskeskkonna versioonivahemikku. Kõige sagedamini kasutatakse Node 22 või 24 vanemat paigaversiooni, mis jääb alla OmniRoute'i nõutava parandatud turbetaseme.

**Sümptomid:**

- Sisselogimislehel kuvatakse tühi ekraan või serveritõrge
- Konsoolis kuvatakse `Error: Module did not self-register` või sarnased omamooduli sidumise vead
- Kui käituskeskkond ei vasta toetatud turbepoliitikale, kuvatakse sisselogimislehel teie Node'i versiooniga **oranž hoiatusriba**

**Lahendus:**

1. Installige toetatud Node.js-i LTS-väljalase (soovitatav: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Kontrollige versiooni: `node --version` peaks 24.x LTS-i harus kuvama `v24.0.0` või uuema versiooni
3. Installige OmniRoute uuesti: `npm install -g omniroute`
4. Taaskäivitage: `omniroute`

> **Toetatud turvalised versioonid:** `>=22.22.2 <23` või `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) ja Node.js 26 on täielikult toetatud.

### npm v11+: `better-sqlite3` pole installitud (moodulit ei leitud)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Põhjus:** npm v11 (kaasas Node.js 24+-ga) blokeerib vaikimisi valikuliste
sõltuvuste installiskriptid. Kuna `better-sqlite3` on loetletud väljal `optionalDependencies`
ja nõuab omakompileerimist (`node-gyp rebuild`), jätab npm selle vaikides vahele.

**Sümptomid:**

- Server jookseb käivitamisel kokku veaga `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` kuvab „No such file or directory“
- `npm ls better-sqlite3` kuvab `(empty)`

**Lahendus:**

1. Kinnitage installiskriptid ja installige uuesti:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Või installige eelkompileeritud pakett käsitsi:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Kontrollige, kas see töötab: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file“

<a name="macos-native-module-rebuild"></a>

**Põhjus:** Pärast globaalset käsku `npm install -g omniroute` võib paketis sisalduv `better-sqlite3` omabinaarfail olla kompileeritud kohaliku käituskeskkonna omast erineva arhitektuuri või Node.js-i ABI jaoks. See on macOS-is (nii Apple Siliconi kui ka Inteli puhul) tavaline, kui eelkompileeritud binaarfail ei vasta teie keskkonnale.

**Sümptomid:**

- Serveri käivitamine nurjub kohe veaga `dlopen`
- Veateade sisaldab teksti `slice is not valid mach-o file`
- Täielik näide:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Lahendus — kompileerige oma kohaliku keskkonna jaoks uuesti (Node.js-i versiooni pole vaja alandada):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Märkus:** See kompileerib omamooduli sidumise uuesti teie kohaliku Node.js-i versiooni ja protsessoriarhitektuuri jaoks, lahendades binaarfailide ühildumatuse. Ametlikult toetatud käituskeskkonna versioonivahemik on **`>=22.22.2 <23` või `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` failis `src/shared/utils/nodeRuntimeSupport.ts`, kooskõlas faili `package.json` väljaga `engines`). Node.js 24.x LTS (Krypton) ja Node.js 26 on versiooniga `better-sqlite3` v12.x täielikult toetatud.

## Puhverserveri probleemid

<a name="proxy-issues"></a>

### Teenusepakkuja valideerimisel kuvatakse „fetch failed”

**Põhjus:** API-võtme valideerimise lõpp-punkt (`POST /api/providers/validate`) eiras varem puhverserveri konfiguratsiooni, põhjustades tõrkeid keskkondades, mis nõuavad liikluse suunamist puhverserveri kaudu.

**Parandus (v3.5.5+):** See on nüüd parandatud. Teenusepakkuja valideerimine toimub `runWithProxyContext` kaudu ning teenusepakkuja tasemel ja globaalseid puhverserveri sätteid järgitakse automaatselt.

### Loa seisundi kontroll nurjub veateatega „fetch failed”

**Põhjus:** OAuthi loa taustal värskendamisel ei tuvastatud puhverserveri konfiguratsiooni iga ühenduse jaoks eraldi.

**Parandus (v3.5.5+):** Loa seisundi kontrollimise ajastaja tuvastab nüüd enne värskendamiskatset iga ühenduse puhverserveri konfiguratsiooni. Värskendage versioonile v3.5.5+.

### SOCKS5-puhverserver tagastab veateate „invalid onRequestStart method”

**Põhjus:** Node.js 22 korral ei ühildu undici@8 dispetšer Node'i sisseehitatud `fetch()`-i teostusega.

**Parandus (v3.5.5+):** OmniRoute kasutab nüüd puhverserveri dispetšeri aktiveerimisel undici enda funktsiooni `fetch()`, tagades ühtse käitumise. Värskendage versioonile v3.5.5+.

### MITM-puhverserver WSL-is: Windowsi hostis olevaid töölauarakendusi ei püüta kinni

**Põhjus:** MITM-puhverserver ja selle CA-sertifikaat installitakse keskkonda, kus OmniRoute töötab. WSL-i korral on selleks keskkonnaks Linuxi külalissüsteem, samas kui AI-töölauarakendused (Kiro, Trae, Copilot, Zed, …) töötavad Windowsi hostis. Hostirakendused ei usalda külalissüsteemi serdihoidlat ega suuna liiklust külalissüsteemi süsteemse puhverserveri kaudu, mistõttu töölauarakenduste liiklust seal kinni ei püüta.

**Soovitus:** Käitage OmniRoute'i otse samas operatsioonisüsteemis, kus töötavad töölauarakendused, mille liiklust soovite kinni püüda (Windowsi rakenduste jaoks Windowsis; macOS-i/Linuxi puhul vastavalt nendes süsteemides). OmniRoute'i hoidmine WSL-is ja samal ajal hostirakenduste sihtimine nõuab loodud CA-sertifikaadi käsitsi usaldamist Windowsi hostis ning iga hostirakenduse võrgu-/puhverserveri sätete suunamist WSL-i puhverserveri lõpp-punktile — see on mittetoetatud ja ebakindel lahendus.

## Dockeri probleemid

### Dockeri IPv6 / ühenduse lähtestamine

<a name="docker-ipv6"></a>

**Sümptomid:** `curl http://localhost:20128/v1/models` tagastab `curl: (56) Recv failure: Connection reset by peer`. Juhtpaneel ja autentimata lõpp-punktid töötavad, kuid autenditud lõpp-punktid nurjuvad — see näib autentimisprobleemina, kuid tegelikult ei ole seda.

**Põhjus:** `docker run -p 20128:20128` avaldab pordi nii aadressil `0.0.0.0` (IPv4) kui ka `::` (IPv6), kuid konteineris olev protsess kuulab ainult IPv4 kaudu. Hostides, kus `localhost` lahendatakse esmalt aadressiks `::1`, jõuab ühendus avaldatud IPv6-porti, mille taga pole kuulajat → ühendus lähtestatakse.

**Parandus:**

1. **Kiirdiagnoos:** Käivitage `curl -4 http://localhost:20128/v1/models`. Kui see töötab võtmega `-4`, kuid ilma selleta nurjub, on teil IPv6 sidumise mittevastavus.
2. **Püsiv parandus:** Siduge port selgesõnaliselt IPv4-ga, kasutades käsus `docker run` parameetrit `-p 127.0.0.1:20128:20128`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   See sunnib kasutama IPv4 sidumist ja väldib ühtlasi puhverserveri avaldamist hosti kõigil võrguliidestel.

### Levinud vorminguprobleemid

- **Mõtlemissilte ei kuvata** — kontrollige, kas sihtpakkuja toetab mõtlemist, ja vaadake üle mõtlemise eelarve säte
- **Tööriistakutsed kaovad** — mõned vorminguteisendused võivad eemaldada toetamata välju; kontrollige seda mänguväljaku režiimis
- **Süsteemiviip puudub** — Claude ja Gemini käsitlevad süsteemiviipe erinevalt; kontrollige teisenduse väljundit
- **SDK tagastab objekti asemel töötlemata sõne** — lahendatud versioonis v1.x; vastuse puhastaja eemaldab ebastandardsed väljad (`x_groq`, `usage_breakdown` jne), mis põhjustavad OpenAI SDK Pydanticu valideerimistõrkeid. Kui näete seda endiselt versioonis v3.x+, esitage probleemiaruanne.
- **GLM/ERNIE lükkab rolli `system` tagasi** — lahendatud versioonis v1.x; rollide normaliseerija liidab süsteemisõnumid ühildumatute mudelite puhul automaatselt kasutajasõnumitega. Kui näete seda endiselt versioonis v3.x+, esitage probleemiaruanne.
- **Rolli `developer` ei tuvastata** — lahendatud versioonis v1.x; muude kui OpenAI pakkujate puhul teisendatakse see automaatselt rolliks `system`. Kui näete seda endiselt versioonis v3.x+, esitage probleemiaruanne.
- **`json_schema` ei tööta Geminiga** — lahendatud versioonis v1.x; `response_format` teisendatakse nüüd Gemini väljadeks `responseMimeType` + `responseSchema`. Kui näete seda endiselt versioonis v3.x+, esitage probleemiaruanne.

## Töökindluse sätted

### Automaatne kiiruspiirang ei käivitu

- Automaatne kiiruspiirang kehtib ainult API-võtme pakkujatele (mitte OAuthi/tellimuse korral)
- Veenduge, et jaotises **Sätted → Töökindlus → Pakkuja profiilid** oleks automaatne kiiruspiirang lubatud
- Kontrollige, kas pakkuja tagastab olekukoode `429` või päiseid `Retry-After`

### Eksponentsiaalse viivituse häälestamine

Pakkuja profiilid toetavad järgmisi sätteid:

- **Baasviivitus** — Esialgne ooteaeg pärast esimest tõrget (vaikimisi: 1s)
- **Maksimaalne viivitus** — Ooteaja ülempiir (vaikimisi: 30s)
- **Kordaja** — Kui palju suurendada viivitust iga järjestikuse tõrke korral (vaikimisi: 2x)

### Päringutulva vältimine

Kui palju samaaegseid päringuid jõuab kiiruspiiranguga pakkujani, kasutab OmniRoute päringute järjestamiseks ja aheltõrgete vältimiseks muteksit koos automaatse kiiruspiiranguga. API-võtme pakkujate puhul toimub see automaatselt.

### Vestluspäringud nurjuvad veaga 503 / chat_admission_busy

**Sümptomid:**

- Vestluse lõpetamiste lõpp-punkt tagastab uuesti proovitava `503` vastuse, mille veakood on
  `chat_admission_busy`.
- Vastus sisaldab päist `Retry-After`. Alates muudatusest #12135 tuletatakse väärtus vaadeldud
  hõivatusest — valitakse suurem väärtus ajast, mille päring on juba aknas `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  oodanud, ja ajast, mille jooksul praeguseid suure koormusega päringute lube on hoitud — ümardatakse üles
  täissekunditeni ning piiratakse 60 sekundiga. Jõudeolekus oleva pääsu korral säilivad varasemad
  miinimumid: baidipõhisel teel 2 sekundit, struktuuripõhisel teel 1 sekund (viimane sisaldab ka
  `reason: "structure_limit"`).
- See võib juhtuda ajal, mil mõni teine suure koormusega vestlus või kaua kestev voogvastus on endiselt
  pooleli.

Baidipõhise vastuse keha on:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Struktuuripõhine vastus kasutab sama tüüpi ja koodi ning sisaldab teadet
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ja väärtust `reason: "structure_limit"`.
Vaikimisi lävendite korral on päring struktuuriliselt mahukas, kui selles on vähemalt `200` sõnumit,
vähemalt `64` tööriista või vähemalt `32,000` hinnangulist luba või kui piiratud struktuurihinnang
ammendab oma piirid: `10,000` külastatud sõlme või sügavus `12`.

**Põhjus:** See on OmniRoute'i tahtlik koormuse vähendamine, mitte ülesvoolu pakkuja tõrge.
Iga protsess kasutab protsessisisest kaitsemehhanismi, et reserveerida piiratud mahukate päringute
töötlemisvõimsus enne suure päringukeha mälus hoidmist ja parsimist. Mahuka päringu luba jääb kehtima
kogu SSE-vastuse eluea jooksul.

**#503-hargnemine:** enne seda parandust piiras kaitsemehhanism samaaegsust fikseeritud päringute ARVU alusel
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, vaikimisi `1`), sõltumata hosti mälumahust, mistõttu programmeerimisagentide
hargnemine (mitu alamagenti/CLI-d, päringukehad tavaliselt > 256 KB) langetas tegeliku samaaegsuse
ligikaudu ühele ja põhjustas täiesti tavapärase koormuse korral 503-tõrkeid. Nüüd häälestub kaitsemehhanism
automaatselt: seda juhib automaatselt tuletatud sisendi BAIDIEELARVE (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`),
mille suurus põhineb protsessi tegelikul mälupiirangul, ning see arvestab ka reaalajas ressursisurve
signaali — seega vähendab see koormust ainult siis, kui host on tõepoolest mälusurve all, mitte pelgalt
seetõttu, et korraga saabus rohkem kui üks mahukas päring. Vana arvuline piirang
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) kehtib endiselt, kuid ainult siis, kui määrate selle sõnaselgelt.

Kui töötlemisvõimsus on hõivatud, ootab mahukas päring enne uuesti proovitava `503` vastuse tagastamist
kuni `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (vaikimisi `2000`, väärtus `0` keelab ootamise), et koht vabaneks.
Piiratud ooteaeg võimaldab agentidel põhinevatel klientidel
(OpenCode, Claude Code, Cursor), mis hargnevad samaaegselt mahukateks alampäringuteks, päringutulva
järjestada, selle asemel et kulutada kogu uuesti proovimise limiit kohe saadud tagasilükkamistele ja
katkestada ülesande täitmine. Mahukate päringute lubade praegune hõivatus, määratud baidieelarve ja
reaalajas surve tugevus kuvatakse lõpp-punktis `GET /api/monitoring/health` → `chatAdmission`
(`inflightBytes`, `maxInflightBytes`, `budgetSource`, `pressureSeverity`, `countCapEnabled`) — kontrollige
neid enne mis tahes keskkonnamuutuja muutmist.
Sätted → Töökindlus → Päringujärjekord → Samaaegsed päringud ei juhi seda; see säte
haldab eraldi pakkuja päringujärjekorra mehhanismi.

**Parandus:**

1. Proovige esmalt uuesti. Kliendid peaksid järgima päist `Retry-After` ja kasutama viivitusega
   korduskatseid, selle asemel et päringut kohe korrata.
2. Enne millegi häälestamist kontrollige `/api/monitoring/health` → `chatAdmission`. `countCapEnabled:
false` ja piisavalt suur `maxInflightBytes` tähendavad, et automaatselt tuletatud eelarve juba
   toimib; `pressureSeverity` väärtusega `high`/`critical` tähendab, et hostil on tõepoolest vähe mälu —
   seda ei saa parandada vastuvõttu juhtiva keskkonnamuutujaga, vaid vaja on rohkem RAM-i või väiksemat töökoormust.
3. Ainult juhul, kui `/api/monitoring/health` näitab, et automaatselt tuletatud eelarve on teie
   hosti jaoks tõepoolest liiga väike (harv olukord — see skaleerub juba konteinerist füüsilise serverini),
   alistage see otse muutujaga `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, selle asemel et naasta päringute arvul
   põhineva pärandpiirangu juurde.

Ametlikud vastuvõtusätted leiate [keskkonnamuutujate teatmikust](../reference/ENVIRONMENT.md#4-security--authentication).

## Valikuline RAG / LLM-i tõrgete taksonoomia (16 probleemi)

Mõned OmniRoute'i kasutajad paigutavad lüüsi RAG- või agendisüsteemide ette. Sellistes seadistustes esineb sageli kummaline muster: OmniRoute näib olevat korras (pakkujad töötavad, marsruutimisprofiilid on korras, kiiruspiirangu hoiatusi pole), kuid lõplik vastus on ikkagi vale.

Praktikas tulenevad need intsidendid tavaliselt järgnevast RAG-konveierist, mitte lüüsist endast.

Kui soovite nende tõrgete kirjeldamiseks ühist sõnavara, võite kasutada WFGY ProblemMapi – välist MIT-litsentsiga tekstipõhist ressurssi, mis määratleb kuusteist korduvat RAG / LLM-i tõrkemustrit. Üldjoontes hõlmab see järgmist:

- otsingu triiv ja katkised kontekstipiirid
- tühjad või aegunud indeksid ja vektorandmebaasid
- manuste ja semantika mittevastavus
- viiba koostamise ja kontekstiakna probleemid
- loogika kokkuvarisemine ja liiga enesekindlad vastused
- pikkade ahelate ja agentide koordineerimise tõrked
- mitme agendi mälu ja rollide triiv
- juurutamise ja algkäivituse järjekorra probleemid

Põhimõte on lihtne:

1. Vigase vastuse uurimisel jäädvustage:
   - kasutaja ülesanne ja päring
   - OmniRoute'i marsruudi või pakkujate kombinatsioon
   - kogu järgnevates etappides kasutatud RAG-kontekst (hangitud dokumendid, tööriistakutsed jne)
2. Seostage intsident ühe või kahe WFGY ProblemMapi numbriga (`No.1` … `No.16`).
3. Salvestage number oma juhtpaneelile, tegevusjuhendisse või intsidendihaldussüsteemi OmniRoute'i logide kõrvale.
4. Kasutage vastavat WFGY lehte, et otsustada, kas peate muutma oma RAG-süsteemi, otsingukomponenti või marsruutimisstrateegiat.

Täistekst ja konkreetsed juhised asuvad siin (MIT-litsents, ainult tekst):

[WFGY ProblemMapi README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Kui te ei käita OmniRoute'i taga RAG- või agendikonveiereid, võite seda jaotist eirata.

## v3.8.0 teadaolevad probleemid

Versioonile v3.8.0 omased probleemid ja nende praegused ajutised lahendused. Kui parandus lisatakse hilisemasse paika, värskendatakse või eemaldatakse vastav kirje.

### Devin CLI autentimistõrked

**Sümptomid:**

- „Devin CLI-d ei leitud” või „autentimine ebaõnnestus” Devinil põhinevate tööriistade käivitamisel
- CLI käituskeskkonna kontroll kuvab `installed=false`

**Põhjused:**

- `CLI_DEVIN_BIN` osutab teele, mida pole olemas
- Devin CLI pole hosti installitud

**Parandus:**

1. Installige oma platvormile Devin CLI
2. Määrake `.env`-failis `CLI_DEVIN_BIN=/usr/local/bin/devin` (või tegelik tee)
3. Taaskäivitage OmniRoute ja testige uuesti jaotises **Juhtpaneel → CLI tööriistad**

### Mudeli ooteaeg on takerdunud (käsitsi lähtestamine)

**Sümptomid:**

- Mudel on jätkuvalt märgitud ooteajal olevaks ka pärast aegumisaja möödumist
- Päringud jätavad mudeli kombineeritud marsruutimisel endiselt vahele, kuigi ajatempel on minevikus

**Käsitsi lähtestamine:**

- **Juhtpaneel:** **Seaded → Mudelite ooteajad** → klõpsake mõjutatud kaardil nuppu **Luba uuesti**
- **API:** `DELETE /api/resilience/model-cooldowns` koos halduse autentimispäistega

### Ühendus Command Code'i pakkujaga nurjub veakoodiga 403

**Sümptomid:**

- Command Code'i pakkuja ühenduse testimisel tagastatakse 403
- Pärast värsket lisamist kuvatakse pakkuja kaardil „volitamata”

**Põhjus:** OAuthi voog ei jõudnud lõpule (tagasikutset ei saadud või luba ei salvestatud).

**Parandus:**

- Käivitage CLI-s `omniroute providers`, et OAuthi voog uuesti käivitada, või
- Käivitage OAuth uuesti jaotises **Juhtpaneel → Pakkujad → Command Code → Ühenda uuesti**

### ModelScope tagastab agressiivseid 429 ooteaegu

**Sümptomid:**

- ModelScope rakendab pärast väikest päringute tulva väga lühikesi või koheseid ooteaegu
- Kombineeritud marsruutimine jätab ModelScope'i oodatust varem vahele

**Põhjus:** ModelScope väljastab pakkujapõhiseid `Retry-After`-päiseid. v3.8.0 sisaldab nende päiste jaoks spetsiaalset töötlust, mistõttu vanemad versioonid tõlgendavad neid valesti üldiste kiiruspiirangu vihjetena.

**Parandus:**

- Veenduge, et kasutate versiooni v3.8.0 või uuemat
- Kontrollige, et lüliti `useUpstream429BreakerHints` oleks jaotises **Seaded → Töökindlus** lubatud

### OMNIROUTE_WS_BRIDGE_SECRET puudub tootmiskeskkonnas

**Sümptomid:**

- Kõik Codexi/Responsesi WebSocketi silla päringud tagastavad kaugtootmishostis käitamisel 401
- WebSocketi silla käepigistus sulgub kohe pärast ühenduse loomist

**Põhjus:** Keskkonnamuutuja `OMNIROUTE_WS_BRIDGE_SECRET` puudub tootmiskeskkonnast.

**Parandus:**

1. Looge juhuslik saladus: `openssl rand -hex 32`
2. Määrake tootmisserveri keskkonnas `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` (ja igas kliendis, mis sillaga suhtleb)
3. Taaskäivitage OmniRoute

### Responses API: taustarežiim taandatud sünkroonseks

**Sümptomid:**

- Logisse kirjutatakse hoiatus: `background mode degraded to synchronous`
- Päring `background: true` tagastab taustatöö pideme asemel tavalise sünkroonse vastuse

**Põhjus:** v3.8.0 taandab Responses API puhul `background: true` kasutamise teadlikult sünkroonseks täitmiseks ja väljastab samal ajal hoiatuse. Täielik asünkroonne taustal täitmine lisatakse tulevikus.

**Parandus:**

- Kohandage klienti nii, et kutse tehtaks ilma parameetrita `background`, või
- Oodake hilisemat väljalaset, mis sisaldab täielikku asünkroonset taustarežiimi (jälgige muudatuste logi)

## Aeglane käivitumine / valmisoleku ajalõpp

Kui CLI kuvab teate `⚠ Server did not respond within 60s`, kuid server tegelikult töötab, on valmisolekukontrolli ajavaru teie keskkonna jaoks liiga lühike.

Seda juhtub sageli Windowsis (viirusetõrje, failisüsteemi jälgijad) või suure käivituskoormusega konteinerites.

**Lahendus — suurendage ajavaru:**

```bash
# Keskkonnamuutuja kaudu (säilib käivituste vahel):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minutit
omniroute serve

# CLI lipu kaudu (ühekordne):
omniroute serve --ready-timeout 180000
```

Vaikeväärtus on 60 000 ms (60 s). Hoiatus on ainult informatiivne; server jätkab taustal käivitumist ja muutub kättesaadavaks pärast käivitamise lõppemist.

Täieliku teabe `OMNIROUTE_READY_TIMEOUT_MS` kohta leiate dokumendist [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
