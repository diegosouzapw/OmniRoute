La línea base recomendada es la cifra que se debe optimizar.

## Reglas

- Los objetivos de cobertura se aplican a los archivos de código fuente, no a `tests/**`.
- `open-sse/**` forma parte del producto y debe permanecer dentro del alcance.
- El código nuevo no debe reducir la cobertura en las áreas modificadas.
- Es preferible probar el comportamiento y los resultados de las ramas en lugar de los detalles de implementación.
- Para `src/lib/db/**`, es preferible usar bases de datos SQLite temporales y fixtures pequeños en lugar de mocks amplios.

## Conjunto actual de comandos

- `npm run test:coverage`
  - Puerta principal de cobertura del código fuente para el conjunto de pruebas unitarias
  - Genera `text-summary`, `html`, `json-summary` y `lcov`
- `npm run coverage:report`
  - Informe detallado archivo por archivo de la ejecución más reciente
- `npm run test:coverage:legacy`
  - Solo para comparación histórica

## Política de incremento progresivo

Actualiza los umbrales de `npm run test:coverage` solo después de que el proyecto supere realmente el siguiente hito con un margen cómodo.

**Umbral actual:** `npm run test:coverage` exige **60 sentencias / 60 líneas / 60 funciones / 60 ramas** (la métrica se recalculó en Quality-Gates Fase 6A.1; la referencia anterior del 82.58% estaba inflada porque contabilizaba los archivos de prueba y excluía `open-sse`). El comando `test:coverage:legacy` conserva la métrica anterior de 50/50/50 para fines de comparación histórica.

Para realizar comprobaciones puntuales de umbrales con el informe más reciente, usa:

```bash
node scripts/check/test-report-summary.mjs --threshold 75
```

## Brecha conocida

El comando de cobertura actual mide la suite principal de pruebas unitarias de Node e incluye el código fuente alcanzado desde ella, incluido `open-sse`. Todavía no combina la cobertura de Vitest en un único informe consolidado. Merece la pena realizar esa integración más adelante, pero no es un impedimento para comenzar el avance del 60% al 80%.
