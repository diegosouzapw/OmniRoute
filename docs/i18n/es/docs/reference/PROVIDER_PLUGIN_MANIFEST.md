`open-sse/config/providerPluginManifest.ts` define el contrato de plugins de proveedor compatible con JSON. `open-sse/config/providerPluginManifestRegistry.ts` vincula ese contrato con el registro actual de proveedores para sidecars como Bifrost, CLIProxyAPI o un futuro router en Go/Rust. El registro de TypeScript sigue siendo la fuente de verdad, pero los sidecars pueden consumir el manifiesto sin importar código de ejecutores, valores predeterminados de OAuth, encabezados ni el estado del entorno del proceso.

El mismo manifiesto está disponible mediante HTTP en
`GET /api/v1/provider-plugin-manifest` para sidecars que se ejecutan fuera del proceso.

OmniRoute anuncia esa URL a Bifrost y CLIProxyAPI mediante el encabezado de solicitud
`X-OmniRoute-Provider-Manifest-Url`. Configure
`OMNIROUTE_PROVIDER_MANIFEST_URL` cuando el sidecar necesite una URL pública o de la red del contenedor en lugar del origen de la solicitud local.

## Actualización del manifiesto

El endpoint HTTP devuelve `Cache-Control: public, max-age=60` y un
`ETag` fuerte. Un sidecar debe conservar el último manifiesto validado y enviar su ETag
en `If-None-Match` al actualizarlo. Una respuesta `304 Not Modified` no tiene cuerpo;
el sidecar conserva su manifiesto almacenado en caché. Si no existe ningún manifiesto validado en caché,
el sidecar debe realizar una solicitud incondicional en lugar de aceptar un `304`.

## Objetivo

Orientar los metadatos de los proveedores hacia un contrato de plugins para que la ruta crítica de solicitudes pueda
acabar siendo gestionada por un sidecar de menor latencia, mientras OmniRoute mantiene la
ruta de TypeScript como punto de aplicación de políticas y mecanismo de respaldo. El manifiesto es aditivo:
no modifica por sí mismo el enrutamiento de solicitudes.

## Contrato

El manifiesto contiene:

- id y alias del proveedor
- formato de origen y nombre del ejecutor
- tipo de autenticación, encabezado de autenticación y prefijo de autenticación opcional
- metadatos estáticos del endpoint
- elegibilidad para sidecar y motivos explícitos cuando un proveedor deba permanecer en TS
- metadatos de modelos compatibles con JSON, como longitud de contexto, indicadores de visión/razonamiento y
  parámetros no admitidos
- etiquetas de capacidades, incluidas `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` y `usage-supported`

El manifiesto excluye intencionadamente:

- secretos de cliente OAuth y valores secretos predeterminados
- resolución del entorno en tiempo de ejecución
- encabezados de solicitud y auxiliares de credenciales públicas
- generadores dinámicos de URL
- funciones de ejecutores
- detalles internos del pool de sesiones

## Etiquetas de capacidades

`capabilities` es un array ordenado de etiquetas derivadas de la entrada del registro. Los integradores
deben tratarlo como la respuesta legible por máquinas a «qué puede hacer este proveedor», en lugar de
volver a consultar el código fuente de TypeScript.

| Etiqueta             | Significado                                                                           |
| -------------------- | ------------------------------------------------------------------------------------- |
| `apikey`             | Acepta una clave de API (`authType` es `apikey` u `optional`).                        |
| `oauth`              | Utiliza un flujo de OAuth o de sesión.                                                |
| `responses`          | Expone una URL base de la API Responses de OpenAI.                                    |
| `passthrough-models` | Sirve modelos directamente desde el origen en lugar de un catálogo estático.          |
| `custom-executor`    | Ejecuta un ejecutor no predeterminado, por lo que permanece en la ruta de TypeScript. |
| `sidecar-candidate`  | Refleja `sidecar.eligible`: es seguro considerarlo para importarlo en un sidecar.     |
| `usage-fetch`        | Tiene configurado un recuperador de uso o cuota (`getUsageForProvider`).              |
| `usage-supported`    | La API de uso acepta este proveedor (`isSupportedUsageConnection`).                   |

`usage-fetch` solo sirve para detección. Indica que OmniRoute sabe cómo consultar el uso del
proveedor; no activa la recuperación, no cambia la semántica de las cuotas ni implica que
el widget de cuotas del Dashboard esté habilitado para el proveedor; ese widget se controla por separado mediante
`USAGE_SUPPORTED_PROVIDERS`. La fuente de verdad es `USAGE_FETCHER_PROVIDERS` en
`open-sse/services/usage/fetcherProviders.ts`.

Esa lista utiliza como claves las cadenas que acepta el despachador de uso, por lo que mezcla ids canónicos
con alias y es ligeramente más larga que el número de proveedores etiquetados: las entradas que
no son proveedores de chat en el registro del manifiesto (por ejemplo, el proveedor de búsqueda `firecrawl`
y el proveedor ACP `amazon-q`) no tienen ninguna entrada de manifiesto que etiquetar.

`usage-supported` indica si las rutas de uso del servidor y del Dashboard aceptan una conexión
para el proveedor. Refleja `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
y `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), ambas controladas por
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). A diferencia de
`usage-fetch`, se emite únicamente para el id del proveedor: la comprobación en tiempo de ejecución realiza
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` sin resolución de alias, por lo que el manifiesto
mantiene la misma regla. Las dos etiquetas tienen ámbitos diferentes: 3 proveedores solo incluyen
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) y 1 solo incluye
`usage-supported` (`xiaomi-mimo-token-plan`), por lo que una no implica la otra.

## Uso de sidecars

Los sidecars deben tratar `sidecar.eligible` como una señal conservadora de posible elegibilidad, no como una decisión de enrutamiento incondicional. El primer objetivo de importación deben ser los proveedores con clave de API y endpoint estático que utilicen el ejecutor predeterminado. Los proveedores con ejecutores web personalizados, flujos de OAuth/sesión, generadores dinámicos de URL o configuración de pools deben permanecer en la ruta de respaldo de TypeScript hasta que un sidecar implemente un comportamiento equivalente y la telemetría demuestre la paridad.

Fases de migración sugeridas:

1. Generar y validar el manifiesto de plugins de proveedores a partir del registro de TS.
2. Enseñar a Bifrost o CLIProxyAPI a importar el manifiesto para proveedores con clave de API y endpoint estático.
3. Enrutar los proveedores elegibles a través del sidecar mediante `OMNIROUTE_RELAY_BACKEND`, manteniendo habilitada la ruta de respaldo de TS.
4. Promover proveedores únicamente cuando la tasa de éxito, la latencia p99, el comportamiento de streaming y la gestión de parámetros no compatibles coincidan con la ruta de TS.
5. Añadir plugins nativos del sidecar para ejecutores personalizados, una familia de proveedores cada vez.

## Por qué no integrar proveedores directamente en Next

El frontend de Next no debe encargarse de la ejecución de proveedores. Debe llamar al límite de la API. El backend puede decidir entonces si utilizar el ejecutor de TypeScript, Bifrost, CLIProxyAPI o un futuro sidecar nativo. Esto mantiene centralizados la firma de solicitudes, las comprobaciones de listas de permitidos, las políticas de la base de datos y el comportamiento de respaldo antes de cualquier transferencia a un sidecar.
