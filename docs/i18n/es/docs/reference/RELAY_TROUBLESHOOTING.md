Los relés (Vercel, Deno, Cloudflare) finalizan la conexión ascendente en un
backend sin servidor para que OmniRoute pueda enrutar el tráfico saliente desde
una región estable mientras mantiene la clave de API del proveedor en el
servidor. Este documento describe los dos modos de fallo que los operadores
encuentran en producción y las vías de recuperación que OmniRoute proporciona
para cada uno.

## Cómo se almacena la autenticación del relé

Cuando despliega un relé desde **Configuración → Grupo de proxies → Desplegar relé**,
el flujo de despliegue almacena el token de autenticación del relé en el campo
JSON `notes` del proxy:

- Si `STORAGE_ENCRYPTION_KEY` está configurada, el token se guarda como
  `relayAuthEnc` (cifrado con AES en reposo).
- De lo contrario, se guarda como texto sin formato en `relayAuth`.

En el momento de la solicitud, `extractRelayAuth(notes)` devuelve la forma que
esté presente, por lo que el relé continúa funcionando tras los reinicios.

## Modo de fallo 1 — token indescifrable tras la rotación de la clave

**Síntoma:** los relés que funcionaban anteriormente ahora devuelven errores
`401`/de autenticación del servicio ascendente después de una rotación de
`STORAGE_ENCRYPTION_KEY` en el entorno o en el gestor de secretos. El objeto
binario `relayAuthEnc` almacenado ya no puede descifrarse, por lo que
`extractRelayAuth` devuelve una cadena vacía y el relé no envía datos de
autenticación.

**Recuperación — reparación en el lugar (sin volver a desplegar):**

1. Abra **Configuración → Grupo de proxies**.
2. Las filas de relés cuya autenticación no está disponible muestran una
   insignia amarilla `autenticación ausente` y un botón **Reparar**.
3. Haga clic en **Reparar**. OmniRoute llama a
   `POST /api/settings/proxies/[id]/repair-relay`, que:
   - descifra `relayAuthEnc` con la clave **actual**,
   - vuelve a escribir el valor de texto sin formato `relayAuth` en `notes`,
   - devuelve `{ repaired: true, mode: "recovered" }`.

El relé reanuda el servicio sin necesidad de volver a introducir credenciales
de despliegue.

Esto solo funciona si la `STORAGE_ENCRYPTION_KEY` actual todavía puede
descifrar el objeto binario. Si rotó la clave **sin** realizar una migración,
el objeto binario no se puede recuperar.

## Modo de fallo 2 — token irrecuperable (la clave anterior ya no está disponible)

**Síntoma:** hizo clic en **Reparar** y obtuvo
`{ repaired: false, mode: "redeploy", status: 409 }`.

**Recuperación — volver a desplegar:**

El token almacenado no puede recuperarse con la clave actual. Vuelva a
desplegar el relé desde el mismo cuadro modal que utilizó originalmente
(menú **Desplegar relé** → Vercel / Deno / Cloudflare). El flujo de despliegue
guarda un token nuevo (cifrado con la clave actual) y desaparece la insignia
`autenticación ausente` de la fila.

En la interfaz de usuario, el propio botón **Reparar** abre el cuadro modal de
redespliegue cuando el token es irrecuperable, por lo que nunca tendrá que
buscarlo manualmente.

## Modo de fallo 3 — relé accesible pero en mal estado

**Síntoma:** la prueba del proxy (botón `speed`) muestra que el relé está
activo, pero las solicitudes siguen fallando de forma intermitente.

Compruebe los encabezados de información del relé devueltos por el sondeo de
prueba automática de OmniRoute (consulte **Configuración → Grupo de proxies**
y los contadores `relayTested` / `relayAlive`):

- `x-relay-url` — qué backend de relé respondió.
- `x-relay-mode` — `ts` | `bifrost` | `auto` para esa solicitud.
- `x-relay-attempts` — cuántos saltos de relé se intentaron antes de obtener
  una respuesta correcta.
- `x-relay-fallback` — `true` cuando la solicitud pasó del backend preferido
  al relé de TypeScript como alternativa.

Una tasa alta de `x-relay-fallback` junto con un valor bajo de `relayAlive`
significa que el backend complementario no está en buen estado y debería
corregirlo o cambiar la estrategia del backend de relé a `ts` (consulte
`RELAY_BACKEND_STRATEGY.md`).

## Referencia de la API

| Método | Ruta                                      | Cuerpo                  | Éxito                                                                                                                                     | Fallo                                                                                      |
| ------ | ----------------------------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }` al volver a derivarlo; `200 { repaired: false, mode: "noop" }` si ya existe texto sin formato | `409 { mode: "redeploy" }` irrecuperable; `400` no es un tipo de relé; `404` no encontrado |

La ruta de listado `GET /api/settings/proxies` adjunta a cada elemento un
`relayInfo: { isRelay, authMissing, repairMode }` sin secretos, para que el
panel pueda mostrar la opción de reparación sin exponer nunca el token.
