## Resumen

OmniRoute ahora admite tres modos de retransmisión para `/api/v1/relay/chat/completions`:

- `ts`: usa la retransmisión de TypeScript dentro del proceso.
- `bifrost`: fuerza el uso de la puerta de enlace Bifrost.
- `auto`: prioriza Bifrost cuando está disponible y recurre a TypeScript en caso de fallo.

Cuando se opera con una tasa de solicitudes elevada (gran cantidad de tokens/día y rendimiento casi constante), la mejor estrategia es mantener la ruta de respaldo explícita y rápida para que la ruta crítica nunca quede bloqueada por un sidecar inactivo.

## Comportamiento de los modos

- `ts`
  - Menor complejidad operativa.
  - Todo el enrutamiento y la validación se ejecutan en Node.
  - La disponibilidad no depende de un sidecar.
- `bifrost`
  - Fuerza el paso de todas las solicitudes por la puerta de enlace del sidecar.
  - Sin conmutación por error automática.
  - Solo resulta útil cuando se garantizan el estado y la latencia del sidecar.
- `auto`
  - El sidecar se utiliza cuando está habilitado y se puede acceder a él.
  - Los intentos fallidos activan cabeceras de conmutación por error y devuelven el tráfico a TS, de modo que se mantenga acotado el tiempo necesario para completar correctamente la solicitud.
  - Este modo es la opción más segura para producción cuando el tiempo de actividad importa más que un enrutamiento estricto exclusivamente mediante el sidecar.

## Situación actual de 9router frente a CLIPROXYAPI

9router y CLIPROXYAPI son integraciones que históricamente han expuesto rutas de compatibilidad para proveedores ascendentes.

- 9router es una ruta integrada para la orquestación ascendente y el comportamiento de compatibilidad.
- CLIPROXYAPI es un puente de API proxy para tráfico de tipo CLI / SDK.
- Bifrost se está estabilizando como la ruta externalizada para los casos en los que se necesita un salto dedicado similar a un sidecar y un despacho local de baja latencia.

Si actualmente está comparando 9router/CLIPROXYAPI:

- Mantenga la firma de solicitudes, las comprobaciones de listas de permitidos y las puertas de políticas de la base de datos en la ruta de la API antes de la transferencia.
- Si un flujo de trabajo necesita un comportamiento estricto del sidecar y una menor variación por solicitud, use `OMNIROUTE_RELAY_BACKEND=bifrost`.
- Si necesita resiliencia del sidecar con una degradación gradual durante incidentes, use `OMNIROUTE_RELAY_BACKEND=auto`.

## Contrato del límite del backend

El límite estable del producto es la API de retransmisión de OmniRoute, no la implementación del panel de control. El panel de control de Next.js puede instalar, configurar y supervisar servicios locales, pero el enrutamiento de solicitudes debe entrar a través de la API de retransmisión y transferirse detrás de ese límite.

Opciones de backend a largo plazo:

- Mantenga la retransmisión de TypeScript como la ruta de políticas y respaldo dentro del proceso. La autenticación, las listas de permitidos, la normalización de solicitudes, la contabilidad y las comprobaciones de seguridad permanecen aquí antes de cualquier transferencia al backend.
- Use Bifrost como el sidecar Tier-1 preferido para un alto rendimiento cuando el despliegue necesite una menor variación del enrutamiento, una rotación centralizada de proveedores o escalado horizontal entre varias réplicas de OmniRoute.
- Mantenga 9router y CLIPROXYAPI como servicios de compatibilidad integrados. Se ejecutan como procesos locales supervisados y resultan útiles cuando su comportamiento de proveedor/CLI es el adaptador deseado, pero no deben convertirse en el motor de enrutamiento Tier-1 predeterminado.
- No permita que el panel de control introduzca URLs de servicios arbitrarias en la ruta crítica. Las URLs proporcionadas por la interfaz de usuario son entradas de configuración; el código de enrutamiento debe resolver backends registrados y sometidos a comprobaciones de estado a partir de la configuración del servidor y del estado del supervisor.
- Actualmente, dé preferencia a HTTP mediante loopback para los servicios supervisados, ya que los procesos administrados ya exponen APIs compatibles con HTTP, la protección de rutas puede auditar el límite y el comportamiento de fallo/conmutación por error es visible en los registros de solicitudes. Solo merece la pena añadir en el futuro un transporte mediante SDK o sockets si reduce de forma medible la latencia de enrutamiento p99 sin debilitar el aislamiento ni la semántica de conmutación por error.

Por lo tanto, para un despliegue de muy alto rendimiento, la opción predeterminada es `auto` con Bifrost habilitado: use el sidecar de Go en la ruta crítica y conserve el respaldo de TypeScript para mantener la tasa de éxito. Use `bifrost` únicamente cuando un comportamiento estricto y exclusivo del sidecar sea más importante que una degradación gradual.

## Recomendaciones para un alto rendimiento

Para valores elevados y sostenidos de RPM/RPS y un SLO de éxito estricto:

1. Use `auto` con un período de espera práctico y telemetría de fallos.
2. Mantenga la validación ascendente y las comprobaciones de claves de API en el límite de la ruta de TypeScript.
3. Habilite cabeceras/contadores explícitos para que su sistema de alertas detecte la frecuencia y los motivos de las conmutaciones por error.
4. Ajuste los tiempos de espera del sidecar para que falle rápidamente, en lugar de esperar indefinidamente.
5. Mantenga en buen estado el reinicio automático de servicios y el bucle de telemetría de estado para que la conmutación por error sea realmente excepcional.

## Configuración inicial sugerida

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- Mantenga habilitadas las comprobaciones de claves de API, listas de permitidos, saneamiento y límites de tasa en los controladores de rutas (siempre se ejecutan antes del reenvío descendente).
- Exporte las métricas de conmutación por error desde su proxy inverso y los registros de solicitudes para que las interrupciones del sidecar sean visibles en menos de un minuto.

## Contrato de plugins de proveedores

Los sidecars deben importar los metadatos de los proveedores mediante el manifiesto JSON seguro de plugins de proveedores, en lugar de depender de los componentes internos del ejecutor de TypeScript. Consulte
[Manifiesto de plugins de proveedores](./PROVIDER_PLUGIN_MANIFEST.md) para conocer el contrato de idoneidad de los sidecars y las fases de migración.
