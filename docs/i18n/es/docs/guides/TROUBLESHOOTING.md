## Solución de problemas detallada

---

### Limitación de solicitudes en proveedores gratuitos (429 / 400 / 401)

**Síntoma**: Al usar `model: "auto"` con proveedores gratuitos o sin autenticación (opencode, auggie, etc.), recibe de forma intermitente `HTTP 429`, `400` o `401` en lugar de respuestas. Las solicitudes se completan correctamente al volver a intentar la misma instrucción unos instantes después, pero la automatización (tareas cron, agentes y scripts) falla en el primer error.

**Causa raíz**: Se acumulan tres modos de fallo independientes:

1. **Límite de solicitudes del proveedor (`429`)**: Los niveles gratuitos pueden imponer una cuota por intervalo. Una ráfaga de llamadas paralelas la agota, por lo que la siguiente solicitud se rechaza hasta que se restablece el intervalo.
2. **Modelo defectuoso en el acceso directo (`400`/`401`)**: Los grupos `auto/*` pueden incluir modelos de acceso directo de `opencode` que están registrados en el catálogo, pero no disponen de credenciales activas (p. ej., `oc/north-mini-code-free` → `401`). El enrutador automático prueba uno, falla y el error se propaga antes de que se active la conmutación por error.
3. **Amplificación por concurrencia (`429` bajo carga)**: Cuando varias sesiones de agentes o tareas cron acceden a `auto` al mismo tiempo, la tasa agregada de solicitudes supera lo que toleran los proveedores gratuitos, por lo que las llamadas legítimas se marcan como abusivas.

**Solución verificada (comunicada por la comunidad, 2026-08-10)**: ajuste tres variables de entorno para que la rotación, la concurrencia y la conmutación por error absorban la inestabilidad del nivel gratuito en lugar de fallar por ella:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # cambia a otro modelo/proveedor ante un 400/401 (omite los modelos de acceso directo defectuosos)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # límite explícito de admisión de solicitudes pesadas (sin establecer de forma predeterminada: no hay límite por número de solicitudes; consulte la nota siguiente)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # espera limitada más larga para obtener capacidad para solicitudes pesadas, en lugar de devolver inmediatamente un 503 reintentable
```

Establezca estas variables en el entorno del proceso de OmniRoute (el demonio, por ejemplo, mediante el plist de LaunchAgent o `systemctl edit`) y, a continuación, reinicie OmniRoute. La opción de rotación es, con diferencia, la medida de mayor impacto: convierte un fallo irrecuperable en un reintento transparente con un proveedor operativo del grupo.

**Nota**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` limita cuántas solicitudes pesadas —de contexto largo— se ejecutan simultáneamente; este límite es una puerta de admisión, no un limitador de solicitudes del proveedor. **Actualización sobre la propagación de errores #503:** esta variable ya no se establece de forma predeterminada (ahora solo aplica un límite cuando se configura explícitamente, como se muestra arriba); en su lugar, la admisión de solicitudes pesadas está controlada por un presupuesto de bytes calculado automáticamente (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), que se ajusta según el límite real de memoria del host. Por tanto, una implementación nueva debería generar muchos menos rechazos `503 chat_admission_busy` sin necesidad de establecer esta variable; establecerla explícitamente aquí sigue funcionando exactamente como se documenta. Las sustituciones explícitas del presupuesto de bytes se restringen al intervalo de 8 MiB a 2 GiB. Un error `413 body_exceeds_budget` no es transitorio: aumente ese presupuesto de bytes, reduzca `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` o aumente el límite de memoria del proceso. Un descarte `inflight_bytes_budget` se debe a una contención temporal y se puede volver a intentar. La limitación de solicitudes por proveedor (`open-sse/services/rateLimitManager.ts`) se controla por separado mediante `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` y `RATE_LIMIT_AUTO_ENABLE`; consulte `.env.example`.

**Cómo verificar que funcionó**: ejecute dos veces seguidas y con poca diferencia de tiempo su agente o tarea cron, y confirme que ambas ejecuciones se completan correctamente. Antes de aplicar la solución, la segunda ejecución suele devolver `429`/`401`. Después de aplicar la solución, los fallos, si los hay, se reintentan de forma transparente y la llamada se completa. También puede ejecutar `curl /monitoring/health` y observar el campo `rateLimitedUntil` de las conexiones de los proveedores y `circuitBreakers.providerBreakers[].state` para los proveedores afectados; el estado será `CLOSED`, `DEGRADED`, `OPEN` o `HALF_OPEN` (consulte `src/shared/utils/circuitBreaker.ts`), y un proveedor que continúe fallando pasará de `CLOSED → DEGRADED → OPEN` antes de que el intervalo de restablecimiento permita una solicitud de prueba (`HALF_OPEN`).

**Si sigues viendo 429**: la cuenta activa de ese proveedor ha agotado realmente su _cuota_ (no solo el límite de solicitudes). Añade una segunda cuenta para el mismo proveedor en el panel de OmniRoute → Proveedores → Cuentas, o incorpora otro proveedor gratuito (p. ej., `routeway`, `auggie`). La rotación solo ayuda con errores transitorios de límite de solicitudes/400/401; el agotamiento total de la cuota requiere una segunda credencial o un proveedor diferente.

**Si ves 403 en modelos de visión (`auto/vision`, `bazaarlink/*`)**: la cuenta conectada no dispone de un plan de pago que incluya visión, o la clave de API no tiene permisos suficientes. Comprueba en el panel del proveedor que el ámbito de la clave incluya visión/multimodalidad, o conecta una cuenta de un nivel de pago y mantenla como destino para visión.

## Advertencias de npm install (ERESOLVE / dependencias peer / paquetes obsoletos)

Cuando ejecutas `npm install -g omniroute`, es posible que veas una gran cantidad de advertencias como `npm warn ERESOLVE`, avisos sobre dependencias peer y mensajes de paquetes `deprecated`. **Estas advertencias son esperadas e inofensivas.** La instalación se realizó correctamente si ves `added <N> packages` en la salida.

Para suprimir las advertencias de resolución de dependencias peer, utiliza la forma de instalación compatible con OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` solo suprime los avisos de `ERESOLVE` y de dependencias peer. Los avisos de obsolescencia siguen siendo visibles porque provienen de paquetes transitivos de terceros; no indican que la instalación haya fallado.

Las advertencias proceden de rangos de dependencias peer desactualizados en paquetes de terceros que OmniRoute no controla:

1. **`marked-terminal` requiere `marked >=1 <16`, pero se encontró `marked@18`** — en la práctica funciona correctamente; el rango peer del proyecto original simplemente está desactualizado.
2. **`deprecated prebuild-install@7.1.3`** — una utilidad transitiva para obtener binarios nativos. No se
   utiliza para instalar el binding de transporte fijado de `wreq-js` y no indica que haya fallado la
   configuración del transporte del proveedor de cookies web.

**No es necesario realizar ninguna acción** — las advertencias no pueden silenciarse por completo sin crear bifurcaciones de los paquetes originales.

## Falsos positivos del antivirus

<a name="antivirus-false-positives"></a>

### Avast/AVG pone en cuarentena `README.md` con `MD:HttpRequest-inf[Susp]`

**Esto es un falso positivo. Nada está infectado y no se requiere ninguna acción.**

Avast y AVG ejecutan una heurística que marca archivos de texto plano/Markdown que contienen muchos
enlaces con apariencia de solicitudes HTTP. El archivo `README.md` de OmniRoute se incluye dentro del paquete npm (está
incluido en `package.json` → `files`), por lo que, en una instalación global, se guarda en `node_modules/omniroute/README.md`
y contiene unos 15 ejemplos de `http://localhost:20128/...` (los endpoints HTTP/SSE de MCP, la URL
`.well-known` de A2A y fragmentos de `curl`). Esa densidad de enlaces es suficiente para activar
la heurística.

Si esto comenzó hace poco: el tipo de archivo no ha cambiado. El README amplió su
tabla de endpoints (se añadieron HTTP de MCP + SSE + A2A) y agregó más ejemplos de `curl`, lo que hizo
que superara el umbral.

El archivo es documentación inerte sin ningún contenido ejecutable. Puede restaurarlo de forma segura
desde la cuarentena.

**Qué hacer:**

1. **Detenga las notificaciones** — excluya el directorio de instalación en su antivirus
   (Avast: Configuración → Excepciones), añadiendo la ruta global de `node_modules` o el
   directorio de datos de OmniRoute (`~/.omniroute/`), o ambos.
2. **Informe del falso positivo** — <https://www.avast.com/false-positive-file-form.php>,
   adjuntando el archivo `README.md` puesto en cuarentena. Esta es la solución que ayuda a todos, ya que es
   la heurística del proveedor la que está reaccionando de forma exagerada ante un archivo de texto.

**Por qué no «solucionamos» esto de nuestro lado:** todos los ejemplos usan `http://localhost`, y
localhost no puede usar `https` sin las complicaciones de los certificados autofirmados. Alterar la documentación para
eludir la heurística de un proveedor perjudicaría a todos los lectores para satisfacer un error del escáner.

### Kaspersky marca la aplicación de escritorio como `PDM:Trojan.Win32.Generic`

**Esto es un falso positivo de una heurística de comportamiento. Nada está infectado.** El
prefijo `PDM:` de Kaspersky significa que el veredicto procede de su Módulo de Defensa Proactiva (System Watcher),
que evalúa lo que el instalador _hace_ en lugar de compararlo con malware conocido. Cuando
se activa, Kaspersky «revierte» toda la instalación —eliminando archivos que ya había
escrito—, por lo que la aplicación termina dañada o desaparece.

Los archivos que marca son componentes estándar de dependencias de código abierto declaradas e incluidas con la
aplicación de escritorio, por ejemplo:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` y
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), la biblioteca de automatización
  de navegadores utilizada para iniciar sesión en proveedores desde la aplicación y para el chat respaldado por el navegador.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — el binding nativo fijado de `wreq-js`, utilizado para HTTP con huella digital de navegador en proveedores
  basados en cookies web (`<arch>` es `x64` o `arm64`).

**Por qué se activa:** el instalador de Windows **aún no está firmado con código**, por lo que un instalador NSIS
sin firmar no tiene ninguna reputación y las heurísticas de comportamiento funcionan con la máxima agresividad. Esto,
combinado con una DLL nativa incluida y cientos de archivos `.js` escritos en
`%LOCALAPPDATA%\Programs\OmniRoute` (incluidos directorios de paquetes con sufijos hash de la
compilación independiente de Next.js), es suficiente para activar la heurística. Está previsto implementar la firma de código;
hasta que se haga, esto puede repetirse con las nuevas versiones.

**Qué hacer:**

1. **Verifique primero la descarga** (esto descarta que el archivo haya sido manipulado). Cada versión publica
   `latest.yml`, cuyo campo `sha512` (base64) corresponde al instalador `OmniRoute.Setup.<version>.exe`.
   En PowerShell, desde la carpeta que contiene el instalador:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   La salida debe coincidir con `latest.yml` → `sha512`. Si no coincide, elimine el archivo y
   vuelva a descargarlo únicamente desde la [página de versiones de GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Restaure y excluya** — restaure desde la cuarentena los elementos eliminados durante la reversión y añada una exclusión
   para `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Configuración → Amenazas y exclusiones);
   después, vuelva a realizar la instalación.
3. **Informe del falso positivo** — <https://opentip.kaspersky.com/>. Los informes de falsos positivos
   enviados por usuarios realmente aceleran la inclusión en la lista de permitidos.

## Compatibilidad con Node.js

<a name="nodejs-compatibility"></a>

### La página de inicio de sesión se bloquea o muestra el error "Module self-registration"

**Causa:** Está ejecutando una versión de Node.js que no cumple con la versión mínima de ejecución segura aprobada por OmniRoute. El caso más habitual es ejecutar un nivel de parche antiguo de Node 22 o 24 que no alcanza el mínimo de seguridad con parches que exige OmniRoute.

**Síntomas:**

- La página de inicio de sesión muestra una pantalla en blanco o un error del servidor
- La consola muestra `Error: Module did not self-register` o errores similares de enlaces nativos
- La página de inicio de sesión muestra un **banner de advertencia naranja** con su versión de Node si el entorno de ejecución no cumple con la política segura admitida

**Solución:**

1. Instale una versión LTS compatible de Node.js (recomendado: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Compruebe su versión: `node --version` debe mostrar `v24.0.0` o una versión posterior de la línea LTS 24.x
3. Vuelva a instalar OmniRoute: `npm install -g omniroute`
4. Reinicie: `omniroute`

> **Versiones seguras compatibles:** `>=22.22.2 <23` o `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) y Node.js 26 son totalmente compatibles.

### npm v11+: `better-sqlite3` no está instalado (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Causa:** npm v11 (incluido con Node.js 24+) bloquea de forma predeterminada los scripts de instalación de las dependencias
opcionales. Dado que `better-sqlite3` aparece en `optionalDependencies`
y requiere compilación nativa (`node-gyp rebuild`), npm lo omite silenciosamente.

**Síntomas:**

- El servidor se bloquea al iniciarse con `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` muestra "No such file or directory"
- `npm ls better-sqlite3` muestra `(empty)`

**Solución:**

1. Apruebe los scripts de instalación y vuelva a instalar:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. O instale manualmente el paquete precompilado:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Compruebe que funciona: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Causa:** Después de ejecutar un `npm install -g omniroute` global, es posible que el binario nativo de `better-sqlite3` incluido en el paquete se haya compilado para una arquitectura o ABI de Node.js distinta de la que se ejecuta localmente. Esto es habitual en macOS (tanto en Apple Silicon como en Intel) cuando el binario precompilado no coincide con su entorno.

**Síntomas:**

- El servidor falla inmediatamente al iniciarse con un error de `dlopen`
- El error contiene `slice is not valid mach-o file`
- Ejemplo completo:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Solución — vuelva a compilar para su entorno local (no es necesario cambiar a una versión anterior de Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Nota:** Esto vuelve a compilar el enlace nativo para su versión local de Node.js y la arquitectura de su CPU, lo que resuelve la incompatibilidad del binario. El intervalo de entornos de ejecución oficialmente compatible es **`>=22.22.2 <23` o `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` en `src/shared/utils/nodeRuntimeSupport.ts`, alineado con el campo `engines` de `package.json`). Node.js 24.x LTS (Krypton) y Node.js 26 son totalmente compatibles con `better-sqlite3` v12.x.

## Problemas con el proxy

<a name="proxy-issues"></a>

### La validación del proveedor muestra "fetch failed"

**Causa:** El endpoint de validación de la clave de API (`POST /api/providers/validate`) omitía anteriormente la configuración del proxy, lo que provocaba fallos en entornos que requieren enrutamiento mediante proxy.

**Solución (v3.5.5+):** Esto ya está solucionado. La validación del proveedor se enruta mediante `runWithProxyContext`, respetando automáticamente la configuración de proxy tanto del proveedor como global.

### La comprobación del estado del token falla con "fetch failed"

**Causa:** La actualización en segundo plano del token OAuth no resolvía la configuración del proxy para cada conexión.

**Solución (v3.5.5+):** El programador de comprobaciones del estado del token ahora resuelve la configuración del proxy para cada conexión antes de intentar la actualización. Actualiza a v3.5.5+.

### El proxy SOCKS5 devuelve "invalid onRequestStart method"

**Causa:** En Node.js 22, el dispatcher de undici@8 es incompatible con la implementación integrada de `fetch()` de Node.

**Solución (v3.5.5+):** OmniRoute ahora utiliza la propia función `fetch()` de undici cuando hay un dispatcher de proxy activo, lo que garantiza un comportamiento coherente. Actualiza a v3.5.5+.

### Proxy MITM en WSL: las aplicaciones de escritorio del host Windows no son interceptadas

**Causa:** El proxy MITM y su certificado de CA se instalan en el entorno donde se ejecuta OmniRoute. En WSL, ese entorno es el sistema Linux invitado, mientras que las aplicaciones de escritorio de IA (Kiro, Trae, Copilot, Zed, …) se ejecutan en el host Windows. Las aplicaciones del host no confían en el almacén de certificados del sistema invitado ni enrutan el tráfico a través del proxy del sistema invitado, por lo que la interceptación de las aplicaciones de escritorio no funciona allí.

**Recomendación:** Ejecuta OmniRoute de forma nativa en el mismo SO que las aplicaciones de escritorio que deseas interceptar (Windows para aplicaciones de Windows; lo mismo para macOS/Linux). Mantener OmniRoute dentro de WSL mientras se dirige a aplicaciones del host requiere confiar manualmente en el certificado de CA generado en el host Windows y configurar los ajustes de red/proxy de cada aplicación del host para que apunten al endpoint del proxy de WSL; se trata de una configuración no compatible y frágil.

## Problemas con proveedores

### "Language model did not provide messages"

**Causa:** Se ha agotado la cuota del proveedor.

**Solución:**

1. Comprueba el rastreador de cuota del panel
2. Usa una combinación con niveles de respaldo
3. Cambia a un nivel más barato/gratuito

### Limitación de solicitudes

**Causa:** Se ha agotado la cuota de la suscripción.

**Solución:**

- Añade una alternativa: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Usa GLM/MiniMax como alternativa económica

### Token OAuth caducado

OmniRoute actualiza los tokens automáticamente. Si los problemas persisten:

1. Panel → Proveedor → Volver a conectar
2. Elimina y vuelve a añadir la conexión del proveedor

### Varias cuentas de Kiro: la segunda cuenta invalida la primera

**Causa:** El backend de Kiro impone una única sesión activa por cada registro de cliente OIDC.
Cuando dos cuentas comparten el mismo cliente registrado (conexiones importadas antes de v3.8.0),
actualizar el token de una cuenta invalida el token de actualización de la otra.

**Solución (v3.8.0+):** Vuelve a importar las conexiones afectadas.
A partir de v3.8.0, cada nueva conexión de Kiro creada mediante **Importar token**,
**inicio de sesión social con Google/GitHub** o **Importación automática** registra automáticamente su propio
cliente OIDC dedicado. Por lo tanto, la conexión queda completamente aislada y actualizar una
cuenta no afecta a ninguna otra.

Las conexiones que se importaron _antes_ de v3.8.0 no incluyen un registro de cliente
por conexión. Esas conexiones siguen utilizando el endpoint compartido de actualización de autenticación social.
Para obtener aislamiento, elimina la conexión antigua desde Panel → Proveedores y vuelve a añadirla
mediante cualquiera de los tres flujos de importación.

Para obtener todos los detalles e instrucciones paso a paso sobre cómo añadir dos cuentas de Kiro en paralelo,
consulta [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Problemas de Docker

### IPv6 de Docker / Restablecimiento de la conexión

<a name="docker-ipv6"></a>

**Síntomas:** `curl http://localhost:20128/v1/models` devuelve `curl: (56) Recv failure: Connection reset by peer`. El panel y los endpoints sin autenticación funcionan, pero los endpoints autenticados fallan; parece un problema de autenticación, pero no lo es.

**Causa:** `docker run -p 20128:20128` publica tanto en `0.0.0.0` (IPv4) como en `::` (IPv6), pero el proceso dentro del contenedor solo escucha en IPv4. En hosts donde `localhost` se resuelve primero como `::1`, la conexión llega al puerto publicado mediante IPv6 sin que haya ningún proceso escuchando detrás → se restablece la conexión.

**Solución:**

1. **Diagnóstico rápido:** Ejecuta `curl -4 http://localhost:20128/v1/models`. Si funciona con `-4` pero falla sin esa opción, tienes una discrepancia en la vinculación de IPv6.
2. **Solución permanente:** Vincula explícitamente a IPv4 usando `-p 127.0.0.1:20128:20128` en tu comando `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Esto fuerza la vinculación a IPv4 y también evita exponer el proxy en todas las interfaces del host.

## Configuración de resiliencia

### El límite de tasa automático no se activa

- El límite de tasa automático solo se aplica a proveedores con clave de API (no a OAuth/suscripción)
- Verifique que **Configuración → Resiliencia → Perfiles de proveedor** tenga habilitado el límite de tasa automático
- Compruebe si el proveedor devuelve códigos de estado `429` o encabezados `Retry-After`

### Ajuste del retroceso exponencial

Los perfiles de proveedor admiten esta configuración:

- **Retraso base** — Tiempo de espera inicial tras el primer fallo (valor predeterminado: 1s)
- **Retraso máximo** — Límite máximo del tiempo de espera (valor predeterminado: 30s)
- **Multiplicador** — Cuánto aumentar el retraso por cada fallo consecutivo (valor predeterminado: 2x)

### Prevención de avalanchas de solicitudes

Cuando muchas solicitudes simultáneas llegan a un proveedor con límite de tasa, OmniRoute utiliza un mutex y el límite de tasa automático para serializar las solicitudes y evitar fallos en cascada. Esto es automático para los proveedores con clave de API.

### Las solicitudes de chat fallan con 503 / chat_admission_busy

**Síntomas:**

- El endpoint de finalizaciones de chat devuelve una respuesta reintentable `503` cuyo código de error es
  `chat_admission_busy`.
- La respuesta incluye `Retry-After`. Desde #12135, el valor se deriva de la ocupación observada:
  el mayor valor entre la ventana `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` que la solicitud ya ha
  esperado y el tiempo durante el cual se han mantenido las concesiones pesadas actuales, redondeado
  hacia arriba a segundos enteros y limitado a 60. Cuando la puerta está inactiva, conserva los mínimos
  históricos: 2 segundos en la ruta basada en bytes y 1 segundo en la ruta basada en estructura
  (que también incluye `reason: "structure_limit"`).
- Esto puede ocurrir mientras otro chat pesado o una respuesta de streaming de larga duración sigue
  en curso.

El cuerpo de la respuesta basada en bytes es:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

La respuesta basada en estructura utiliza el mismo tipo y código, con el mensaje
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
y `reason: "structure_limit"`.
Con los umbrales predeterminados, una solicitud se considera estructuralmente pesada cuando tiene al menos `200` mensajes,
al menos `64` herramientas o al menos `32,000` tokens estimados, o cuando la estimación acotada de la estructura
agota sus límites de `10,000` nodos visitados o una profundidad de `12`.

**Causa:** Se trata de una reducción de carga deliberada dentro de OmniRoute, no de un fallo del proveedor ascendente.
Cada proceso utiliza una protección local del proceso para reservar una capacidad pesada limitada antes de retener
y analizar el cuerpo de una solicitud grande. Una concesión pesada permanece retenida durante toda la vida útil de una respuesta
SSE.

**#503-fanout:** antes de esta corrección, la protección limitaba la simultaneidad a un NÚMERO fijo de solicitudes
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, valor predeterminado `1`) independientemente de la memoria del host, por lo que la
ramificación de agentes de programación (varios subagentes/CLI, con cuerpos habitualmente > 256 KB) se reducía a una
simultaneidad efectiva de ~1 y generaba respuestas 503 bajo una carga completamente normal. Ahora la protección se autoajusta:
está controlada por un presupuesto de BYTES de ingesta derivado automáticamente (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`),
dimensionado a partir del límite real de memoria del proceso, y también consulta una señal activa de presión de recursos,
por lo que solo reduce la carga cuando el host se encuentra realmente bajo presión de memoria, no simplemente porque haya
llegado más de una solicitud pesada a la vez. El antiguo límite de cantidad (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) se
sigue respetando, pero solo si se establece explícitamente.

Cuando la capacidad está ocupada, una solicitud pesada espera primero hasta
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (valor predeterminado `2000`; `0` deshabilita la espera) a que se libere un espacio
antes de responder con el `503` reintentable. La espera acotada existe para que los clientes de tipo agente
(OpenCode, Claude Code, Cursor) que ramifican simultáneamente solicitudes secundarias pesadas serialicen la ráfaga
en lugar de agotar todo su presupuesto de reintentos con rechazos inmediatos y detenerse en mitad de la tarea.
La ocupación actual de las concesiones pesadas, el presupuesto de bytes resuelto y la gravedad de la presión activa se
muestran en `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`); compruebe estos valores antes de modificar cualquier variable de entorno.
Configuración → Resiliencia → Cola de solicitudes → Solicitudes simultáneas no controla esto; esa configuración
rige un mecanismo independiente de cola de solicitudes del proveedor.

**Solución:**

1. Reintente primero. Los clientes deben respetar `Retry-After` y utilizar retroceso en lugar de
   repetir inmediatamente la solicitud.
2. Compruebe `/api/monitoring/health` → `chatAdmission` antes de ajustar nada. `countCapEnabled:
false` y un `maxInflightBytes` generoso significan que el presupuesto derivado automáticamente ya está haciendo su
   trabajo; un valor de `pressureSeverity` de `high`/`critical` significa que el host realmente tiene poca memoria.
   Esto no se puede solucionar mediante una variable de entorno de admisión; requiere más RAM o una carga de trabajo menor.
3. Solo si `/api/monitoring/health` muestra que el presupuesto derivado automáticamente es realmente demasiado pequeño para
   su host (algo poco frecuente, ya que se escala desde contenedores hasta servidores físicos), anúlelo directamente con
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` en lugar de recurrir al antiguo límite de cantidad de solicitudes.

Consulte la [referencia de variables de entorno](../reference/ENVIRONMENT.md#4-security--authentication)
para conocer la configuración de admisión oficial.

## Taxonomía opcional de fallos de RAG / LLM (16 problemas)

Algunos usuarios de OmniRoute colocan el gateway delante de pilas de RAG o agentes. En esas configuraciones es habitual observar un patrón extraño: OmniRoute parece funcionar correctamente (proveedores activos, perfiles de enrutamiento correctos, sin alertas de límites de solicitudes), pero la respuesta final sigue siendo incorrecta.

En la práctica, estos incidentes suelen originarse en el pipeline de RAG posterior, no en el propio gateway.

Si desea disponer de un vocabulario común para describir esos fallos, puede utilizar WFGY ProblemMap, un recurso de texto externo con licencia MIT que define dieciséis patrones recurrentes de fallos de RAG / LLM. A grandes rasgos, abarca:

- desviación de la recuperación y límites de contexto defectuosos
- índices y almacenes vectoriales vacíos u obsoletos
- discrepancia entre embeddings y semántica
- problemas con la composición de prompts y la ventana de contexto
- colapso lógico y respuestas excesivamente seguras
- fallos en cadenas largas y en la coordinación de agentes
- desviación de la memoria y los roles en sistemas multiagente
- problemas de orden de despliegue e inicialización

La idea es sencilla:

1. Cuando investigue una respuesta incorrecta, recopile:
   - la tarea y la solicitud del usuario
   - la ruta o combinación de proveedores en OmniRoute
   - cualquier contexto de RAG utilizado posteriormente (documentos recuperados, llamadas a herramientas, etc.)
2. Asocie el incidente a uno o dos números de WFGY ProblemMap (`No.1` … `No.16`).
3. Guarde el número en su propio panel, guía operativa o sistema de seguimiento de incidentes junto a los registros de OmniRoute.
4. Utilice la página correspondiente de WFGY para decidir si necesita modificar su pila de RAG, recuperador o estrategia de enrutamiento.

El texto completo y las recetas concretas están disponibles aquí (licencia MIT, solo texto):

[README de WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Puede ignorar esta sección si no ejecuta pipelines de RAG o de agentes detrás de OmniRoute.

## Problemas conocidos de v3.8.0

Problemas específicos de la versión v3.8.0 y sus soluciones alternativas actuales. Si se incorpora una corrección en un parche posterior, la entrada se actualizará o eliminará.

### Fallos de autenticación de Devin CLI

**Síntomas:**

- "Devin CLI no encontrado" o "fallo de autenticación" al invocar herramientas respaldadas por Devin
- La comprobación del entorno de ejecución de la CLI informa de `installed=false`

**Causas:**

- `CLI_DEVIN_BIN` apunta a una ruta que no existe
- Devin CLI no está instalado en el host

**Solución:**

1. Instale Devin CLI para su plataforma
2. Establezca `CLI_DEVIN_BIN=/usr/local/bin/devin` (o la ruta real) en `.env`
3. Reinicie OmniRoute y vuelva a realizar la prueba desde **Panel → Herramientas de CLI**

### Bloqueo persistente del tiempo de espera de un modelo (restablecimiento manual)

**Síntomas:**

- Un modelo sigue apareciendo en tiempo de espera incluso después de que haya pasado la hora de expiración
- Las solicitudes siguen omitiendo el modelo en el enrutamiento combinado pese a que la marca de tiempo está en el pasado

**Restablecimiento manual:**

- **Panel:** **Configuración → Tiempos de espera de modelos** → haga clic en **Volver a habilitar** en la tarjeta afectada
- **API:** `DELETE /api/resilience/model-cooldowns` con encabezados de autenticación de administración

### La conexión con el proveedor Command Code falla con un error 403

**Síntomas:**

- Error 403 al probar la conexión con el proveedor Command Code
- La tarjeta del proveedor muestra "no autorizado" después de añadirlo de nuevo

**Causa:** El flujo de OAuth no se completó (no se recibió la devolución de llamada o no se guardó el token).

**Solución:**

- Ejecute `omniroute providers` desde la CLI para volver a activar el flujo de OAuth, o
- Vuelva a ejecutar OAuth desde **Panel → Proveedores → Command Code → Volver a conectar**

### ModelScope devuelve tiempos de espera 429 agresivos

**Síntomas:**

- Tiempos de espera muy breves o inmediatos en ModelScope tras una pequeña ráfaga de solicitudes
- El enrutamiento combinado omite ModelScope antes de lo esperado

**Causa:** ModelScope emite encabezados `Retry-After` específicos del proveedor. v3.8.0 incluye un tratamiento específico para esos encabezados, por lo que las versiones anteriores los interpretan erróneamente como indicaciones genéricas de límites de solicitudes.

**Solución:**

- Asegúrese de utilizar v3.8.0 o una versión posterior
- Compruebe que la opción `useUpstream429BreakerHints` esté habilitada en **Configuración → Resiliencia**

### Falta OMNIROUTE_WS_BRIDGE_SECRET en producción

**Síntomas:**

- Error 401 en todas las solicitudes al puente WebSocket de Codex/Responses cuando se ejecuta en un host de producción remoto
- El protocolo de enlace del puente WebSocket se cierra inmediatamente después de conectarse

**Causa:** Falta la variable de entorno `OMNIROUTE_WS_BRIDGE_SECRET` en el entorno de producción.

**Solución:**

1. Genere un secreto aleatorio: `openssl rand -hex 32`
2. Establezca `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` en el entorno del servidor de producción (y en cualquier cliente que se comunique con el puente)
3. Reinicie OmniRoute

### API Responses: el modo en segundo plano se degrada a síncrono

**Síntomas:**

- Advertencia registrada: `background mode degraded to synchronous`
- Una solicitud con `background: true` devuelve una respuesta síncrona normal en lugar de un identificador de trabajo en segundo plano

**Causa:** v3.8.0 degrada intencionadamente `background: true` en la API Responses a una ejecución síncrona y emite una advertencia. La ejecución asíncrona completa en segundo plano se ofrecerá en el futuro.

**Solución:**

- Ajuste el cliente para realizar la llamada sin `background`, o
- Espere a una versión posterior que incluya el modo asíncrono completo en segundo plano (consulte el registro de cambios)

## Inicio lento / Tiempo de espera de disponibilidad

Si la CLI muestra `⚠ El servidor no respondió en 60 s`, pero el servidor está
funcionando, el tiempo asignado a la sonda de disponibilidad es demasiado corto para su entorno.

Esto suele ocurrir en Windows (antivirus, observadores del sistema de archivos) o en contenedores
con cargas de trabajo intensivas durante el inicio.

**Solución — aumente el tiempo asignado:**

```bash
# Mediante una variable de entorno (se mantiene entre inicios):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minutos
omniroute serve

# Mediante una opción de la CLI (solo para esta ejecución):
omniroute serve --ready-timeout 180000
```

El valor predeterminado es 60 000 ms (60 s). La advertencia es meramente informativa; el servidor
continúa iniciándose en segundo plano y estará accesible una vez que finalice el arranque.

Consulte [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) para obtener información
completa sobre `OMNIROUTE_READY_TIMEOUT_MS`.
