- **ട്രാക്കിംഗ് ഇഷ്യൂ:** [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075)
- **വ്യാപ്തി:** പെർസിസ്റ്റൻസ് ആർക്കിടെക്ചർ മാത്രം; ഈ തീരുമാനം ഒരു ബാഹ്യ ഡാറ്റാബേസ് ചേർക്കുകയോ തിരഞ്ഞെടുക്കുകയോ ചെയ്യുന്നില്ല

## പശ്ചാത്തലം

OmniRoute നിലവിൽ `src/lib/db/`-ൽ നിന്ന് ഡൊമെയ്ൻ-അധിഷ്ഠിത പെർസിസ്റ്റൻസ് ഫംഗ്ഷനുകൾ ലഭ്യമാക്കുന്നു, അതേസമയം
`src/lib/db/core.ts` തിരികെ നൽകുന്ന പങ്കിട്ട കണക്ഷൻ `src/lib/db/adapters/types.ts`-ലെ സിൻക്രണസ് `SqliteAdapter`
കരാർ നടപ്പിലാക്കുന്നു. ആ അഡാപ്റ്റർ നിരവധി SQLite റൺടൈമുകളെ പിന്തുണയ്ക്കുന്നുവെങ്കിലും, അതിന്റെ
ഇന്റർഫേസ് SQLite-രൂപത്തിലുള്ളതായിത്തന്നെ തുടരുന്നു: സിൻക്രണസ് പ്രിപെയേർഡ് സ്റ്റേറ്റ്മെന്റുകൾ, `pragma`, ഡിഫേർഡ്, ഇമീഡിയറ്റ്
ട്രാൻസാക്ഷനുകൾ, നേറ്റീവ്/ഫയൽ-കോപ്പി ബാക്കപ്പ്, ചെക്ക്പോയിന്റ്, ഒരു ലോക്കൽ ഡാറ്റാബേസ് ഹാൻഡിൽ എന്നിവ.

നിലവിലെ സ്റ്റാർട്ടപ്പ്, റിക്കവറി പാതകൾ SQLite ഫയൽ ലൈഫ്സൈക്കിളും കൈകാര്യം ചെയ്യുന്നു. `src/lib/db/core.ts`
`storage.sqlite` പരിഹരിക്കുന്നു, പ്രോസസ്-ഗ്ലോബൽ അഡാപ്റ്റർ ഒന്ന് നിലനിർത്തുന്നു, WAL ചെക്ക്പോയിന്റ് ചെയ്യുന്നു, റിക്കവറി സമയത്ത് തിരഞ്ഞെടുത്ത
ടേബിളുകൾ സംരക്ഷിക്കുന്നു, കൂടാതെ ഡാറ്റാബേസ് പുനർനിർമ്മിക്കുമ്പോൾ SQLite കമ്പാനിയൻ ഫയലുകൾ നീക്കം ചെയ്യുന്നു. `src/lib/db/adapters/driverFactory.ts`-ലെ
ഡ്രൈവർ തിരഞ്ഞെടുപ്പ് പിന്തുണയ്ക്കുന്ന SQLite റൺടൈമുകളിൽ നിന്ന് ഒന്ന് തിരഞ്ഞെടുക്കുന്നു; അത്
ഒരു ബാഹ്യ ബാക്കെൻഡ് അബ്സ്ട്രാക്ഷൻ അല്ല.

സ്കീമയുടെ പരിണാമവും സമാനമായി പരസ്പരബന്ധിതമാണ്. `src/lib/db/migrationRunner.ts` നമ്പർ നൽകിയ SQL ഫയലുകൾ പ്രയോഗിക്കുന്നു,
`sqlite_master`, `PRAGMA table_info` എന്നിവ പരിശോധിക്കുന്നു, ഓപ്ഷണൽ FTS5 പിന്തുണ കണ്ടെത്തുന്നു, കൂടാതെ മൈഗ്രേഷൻ
പ്രവർത്തനങ്ങൾ SQLite ട്രാൻസാക്ഷനുകളിൽ നടത്തുന്നു. `src/lib/db/backup.ts`,
`src/lib/db/optimizationSettings.ts` പോലുള്ള പ്രവർത്തന മൊഡ്യൂളുകൾ ബാക്കപ്പ്, `PRAGMA`, WAL, പേജ്-സൈസ്, ഓട്ടോ-വാക്വം, `VACUUM`
സെമാന്റിക്സ് എന്നിവ നേരിട്ട് ഉപയോഗിക്കുന്നു.

ഇവ എംബെഡഡ് SQLite ഡിപ്ലോയ്മെന്റിന്റെ സാധുവായ സവിശേഷതകളാണ്. PostgreSQL അല്ലെങ്കിൽ MySQL എന്നിവയെ ഒരു SQLite API അനുകരിക്കാൻ
നിർബന്ധിക്കാതെ തന്നെ ഇവ ലഭ്യമായി തുടരണം.

## തീരുമാനം

പോർട്ടബിൾ ഡ്യൂറബിൾ സ്റ്റേറ്റിനായി രണ്ട്-തല പെർസിസ്റ്റൻസ് ബൗണ്ടറി സ്വീകരിക്കുക:

1. **ഡൊമെയ്ൻ റിപ്പോസിറ്ററി കരാറുകൾ** ബിസിനസ്, റൂട്ടിംഗ്
   കോഡുകൾക്ക് ആവശ്യമായ പെർസിസ്റ്റൻസ് പ്രവർത്തനങ്ങൾ നിർവചിക്കുന്നു. കോളറുകൾ SQL ടെക്സ്റ്റ്, പ്രിപെയേർഡ് സ്റ്റേറ്റ്മെന്റുകൾ,
   ഡാറ്റാബേസ് ഫയലുകൾ, അല്ലെങ്കിൽ ഡയലക്റ്റ് ഒബ്ജക്റ്റുകൾ എന്നിവയെയല്ല, ഡൊമെയ്ൻ പെരുമാറ്റത്തെയും ഡൊമെയ്ൻ ഡാറ്റയെയുമാണ് ആശ്രയിക്കുന്നത്.
2. **ഒരു ഇന്റേണൽ അസിങ്ക്രണസ് ബാക്കെൻഡ് കരാർ** ട്രാൻസാക്ഷൻ കോൺടെക്സ്റ്റുകൾ, ആരോഗ്യം/സന്നദ്ധത, മൈഗ്രേഷൻ ഏകോപനം, ബാക്കെൻഡ് ശേഷികൾ,
   വർഗ്ഗീകരിച്ച പിശകുകൾ എന്നിവ ഉപയോഗിച്ച് റിപ്പോസിറ്ററി ഇംപ്ലിമെന്റേഷനുകളെ പിന്തുണയ്ക്കുന്നു. കൃത്യമായ TypeScript ഇന്റർഫേസ് ആദ്യ ഇംപ്ലിമെന്റേഷൻ
   PR-നൊപ്പം നിർദ്ദേശിക്കുകയും കൺഫോർമൻസ് ടെസ്റ്റുകളിലൂടെ തെളിയിക്കുകയും ചെയ്യും; ഈ ADR ഒരു അനുമാനാധിഷ്ഠിത API മനഃപൂർവം സ്ഥിരപ്പെടുത്തുന്നില്ല.

SQLite ഡിഫോൾട്ട് ഇംപ്ലിമെന്റേഷനായി തുടരുന്നു. നിലവിലുള്ള SQLite ഡ്രൈവർ കാസ്കേഡും സിൻക്രണസ്
`SqliteAdapter`-ഉം ഡൊമെയ്നുകൾ ചെറിയ വെർട്ടിക്കൽ സ്ലൈസുകളായി മൈഗ്രേറ്റ് ചെയ്യപ്പെടുമ്പോൾ SQLite റിപ്പോസിറ്ററി ഇംപ്ലിമെന്റേഷന്റെ പിന്നിൽ തുടരുന്നു.
ഒരു ബാഹ്യ സർവീസ് കോൺഫിഗർ ചെയ്യാൻ ഒരു ഉപയോക്താവും നിർബന്ധിതനല്ല.

SQLite-ന് എതിരായി റിപ്പോസിറ്ററി ബൗണ്ടറി തെളിയിച്ചതിനുശേഷമുള്ള ആദ്യ നിർദ്ദേശിത ബാഹ്യ ഇംപ്ലിമെന്റേഷനാണ് PostgreSQL.
രണ്ടാമത്തെ ബിസിനസ്-ലോജിക് ഫോർക്ക് എന്ന നിലയ്ക്കല്ല, അതേ കൺഫോർമൻസ് സ്യൂട്ടിനെതിരെയുള്ള സമാന-നിലയിലുള്ള ഇംപ്ലിമെന്റേഷനായാണ് MySQL തുടർന്ന് വരുന്നത്.

## ബൗണ്ടറി നിയമങ്ങൾ

### പോർട്ടബിൾ റിപ്പോസിറ്ററി ഇന്റർഫേസ്

ഒരു പോർട്ടബിൾ റിപ്പോസിറ്ററിക്ക് ഇനിപ്പറയുന്നവ ലഭ്യമാക്കാം:

- ഡൊമെയ്ൻ റീഡുകളും റൈറ്റുകളും;
- വ്യക്തമായ അറ്റോമിക് പ്രവർത്തനങ്ങളും ട്രാൻസാക്ഷൻ-സ്കോപ്പിലുള്ള റിപ്പോസിറ്ററി ആക്സസും;
- കൺകറൻസി സെമാന്റിക്സ് ഡൊമെയ്നിന്റെ ഭാഗമായിരിക്കുന്നിടത്ത് കംപെയർ/അപ്ഡേറ്റ് അല്ലെങ്കിൽ ലീസ് പ്രവർത്തനങ്ങൾ;
- ബാക്കെൻഡ്-ന്യൂട്രൽ പേജിനേഷൻ, ഓർഡറിംഗ്, കൺസ്ട്രെയിന്റ് പിശകുകൾ.

ബാക്കെൻഡ് ആരോഗ്യം, സന്നദ്ധത, മൈഗ്രേഷൻ ഏകോപനം എന്നിവ വ്യക്തിഗത ഡൊമെയ്ൻ റിപ്പോസിറ്ററികളിലല്ല,
ഇന്റേണൽ ബാക്കെൻഡ്/ഓപ്പറേഷണൽ കരാറിലാണ് ഉൾപ്പെടുന്നത്.

ഒരു പോർട്ടബിൾ റിപ്പോസിറ്ററി ഇനിപ്പറയുന്നവ ലഭ്യമാക്കരുത്:

- `prepare`, `get`, `all`, `run`, അല്ലെങ്കിൽ റോ ഡ്രൈവർ ഹാൻഡിലുകൾ;
- `PRAGMA`, WAL ചെക്ക്പോയിന്റ് മോഡുകൾ, `VACUUM`, അല്ലെങ്കിൽ പേജ്/കാഷ് ട്യൂണിംഗ്;
- SQLite ഫയൽ പാത്തുകൾ, കമ്പാനിയൻ ഫയലുകൾ, അല്ലെങ്കിൽ ഫയൽ-കോപ്പി ബാക്കപ്പ്;
- ക്രോസ്-ബാക്കെൻഡ് ഡൊമെയ്ൻ കരാറായി `lastInsertRowid`;
- FTS5 അല്ലെങ്കിൽ `sqlite-vec` സിന്റാക്സ്;
- സാധാരണ ബിസിനസ് കോഡ് ഉപയോഗിക്കുന്ന ഒരു ജനറിക് ഡയലക്റ്റ് എസ്കേപ്പ് ഹാച്ച്.

### ബാക്കെൻഡ് ശേഷികളുടെ ഇന്റർഫേസ്

ബാക്കെൻഡ്-നിർദ്ദിഷ്ട പെരുമാറ്റം വ്യക്തവും കണ്ടെത്താവുന്നതുമായി തുടരുന്നു. ഇനിപ്പറയുന്നവ ഉൾപ്പെടെയുള്ള
SQLite-മാത്രം മെയിന്റനൻസ്, അതിന്റെ സ്വന്തം ഇംപ്ലിമെന്റേഷനും ഓപ്പറേഷണൽ ഇന്റർഫേസിനും പിന്നിൽ തുടരുന്നു:

- റൺടൈം ഡ്രൈവർ തിരഞ്ഞെടുപ്പ്;
- WAL ചെക്ക്പോയിന്റും SQLite ഷട്ട്ഡൗൺ പെരുമാറ്റവും;
- പേജ്-സൈസ്, കാഷ്-സൈസ്, ഓട്ടോ-വാക്വം ക്രമീകരണങ്ങൾ;
- ഡാറ്റാബേസ്-ഫയൽ ബാക്കപ്പ്, റിസ്റ്റോർ, റിക്കവറി;
- SQLite സ്കീമ ഇൻട്രോസ്പെക്ഷൻ;
- FTS5, `sqlite-vec` ഇന്റഗ്രേഷൻ.

ഒരു ബാഹ്യ ബാക്കെൻഡ് ആ സവിശേഷതകൾ അനുകരിക്കേണ്ടതില്ല. റിപ്പോസിറ്ററികൾ ഒന്നുകിൽ ഒരു
പോർട്ടബിൾ ശേഷി ഉപയോഗിക്കണം, രേഖപ്പെടുത്തിയ പെരുമാറ്റത്തോടുകൂടിയ ബാക്കെൻഡ്-നിർദ്ദിഷ്ട ഇംപ്ലിമെന്റേഷൻ നൽകണം, അല്ലെങ്കിൽ
ഒരു ശേഷി ലഭ്യമല്ലെന്ന് റിപ്പോർട്ട് ചെയ്യണം.

## ട്രാൻസാക്ഷൻ, മൈഗ്രേഷൻ മാതൃക

റിപ്പോസിറ്ററി API-കൾ അറ്റോമിക് ബിസിനസ് പ്രവർത്തനത്തെ നിർവചിക്കുന്നു; കോളർമാർ ഒരു SQL ട്രാൻസാക്ഷൻ മോഡ് തിരഞ്ഞെടുക്കുന്നില്ല.
ഓരോ പ്രവർത്തനവും നിരീക്ഷിക്കാവുന്ന അതിന്റെ കൺകറൻസി ഉറപ്പുകൾ നിർവചിക്കണം: സംരക്ഷിക്കപ്പെടുന്ന ഇൻവേറിയന്റുകൾ, കോൺഫ്ലിക്റ്റ്
കണ്ടെത്തൽ, റീട്രൈ വർഗ്ഗീകരണം, ഐഡംപൊട്ടൻസി പ്രതീക്ഷകൾ, ട്രാൻസാക്ഷൻ-കോൺടെക്സ്റ്റ് പ്രൊപ്പഗേഷൻ എന്നിവ.
നിരീക്ഷിക്കാവുന്ന ആ ഉറപ്പുകൾ തുല്യമായി തുടരുന്ന സാഹചര്യത്തിൽ മാത്രമേ ഇംപ്ലിമെന്റേഷനുകൾക്ക് വ്യത്യസ്ത ട്രാൻസാക്ഷൻ,
ഐസൊലേഷൻ സംവിധാനങ്ങൾ ഉപയോഗിക്കാനാകൂ. പ്രവർത്തനത്തിന്റെ കരാർ പാലിക്കപ്പെടുന്നിടത്ത് SQLite-ന് നിലവിലുള്ള deferred
അല്ലെങ്കിൽ immediate ട്രാൻസാക്ഷൻ സ്വഭാവം ആന്തരികമായി തുടർന്നും ഉപയോഗിക്കാം.

ഒരേ സ്കീമ മാറ്റത്തിനായി ഒന്നിലധികം ആപ്ലിക്കേഷൻ റെപ്ലിക്കകൾ മത്സരിക്കുന്നത് തടയാൻ, ബാഹ്യ ബാക്കെൻഡുകൾക്ക് വ്യക്തമായ
മൈഗ്രേഷൻ ഉടമസ്ഥാവകാശം ആവശ്യമാണ്. ബാക്കെൻഡ് മൈഗ്രേഷൻ ചരിത്രങ്ങൾക്ക് യുക്തിപരമായ നാഴികക്കല്ലുകൾ പങ്കിടാമെങ്കിലും,
SQLite SQL ഫയലുകൾ മറ്റൊരു ഡയലക്റ്റിലേക്ക് പോർട്ടബിൾ ആണെന്നോ പുനരുപയോഗിക്കാമെന്നോ അനുമാനിക്കുന്നില്ല.

## ക്രോസ്-ബാക്കെൻഡ് അനുരൂപതാ സെമാന്റിക്സ്

അനുരൂപതാ ടെസ്റ്റുകൾ റിപ്പോസിറ്ററി മെത്തഡ് സിഗ്നേച്ചറുകൾ മാത്രമല്ല, സ്വഭാവവും ഉൾക്കൊള്ളണം. മൈഗ്രേറ്റ് ചെയ്യുന്ന ഓരോ ഡൊമെയ്നും
ഇനിപ്പറയുന്നവ നിർവചിക്കുകയും സ്ഥിരീകരിക്കുകയും വേണം:

- ടൈംസ്റ്റാമ്പിന്റെ സമയമേഖല, പ്രിസിഷൻ, സീരിയലൈസേഷൻ;
- `NULL` ഓർഡറിംഗ്, കൊളേഷൻ, കേസ്-സെൻസിറ്റിവിറ്റി പ്രതീക്ഷകൾ;
- JSON റെപ്രസന്റേഷനും താരതമ്യ സ്വഭാവവും;
- ഇന്റിജർ, ഡെസിമൽ, മോണിറ്ററി പ്രിസിഷൻ;
- പാജിനേഷനായി സ്ഥിരതയുള്ള ഓർഡറിംഗും നിർണായകമായ ടൈ-ബ്രേക്കറുകളും;
- SQLite row ID-കളെ ആശ്രയിക്കാതെയുള്ള ID ജനറേഷൻ;
- യുണീക്നസ്, ഫോറിൻ-കീ ലംഘനങ്ങളുടെ വർഗ്ഗീകരണം;
- no-op, compare/update, delete പ്രവർത്തനങ്ങൾക്കായുള്ള ബാധിക്കപ്പെട്ട-വരികളുടെ സ്വഭാവം;
- സമകാലിക റൈറ്റ് ഫലങ്ങൾ, വീണ്ടും ശ്രമിക്കാവുന്ന കോൺഫ്ലിക്റ്റുകൾ, ഐഡംപൊട്ടന്റ് റീട്രൈകൾ.

ഒരു ഡൊമെയ്നിന് തുല്യമായ നിരീക്ഷിക്കാവുന്ന സെമാന്റിക്സ് വ്യക്തമാക്കാൻ കഴിയുന്നില്ലെങ്കിൽ, അത് ഇതുവരെ പോർട്ടബിൾ അല്ല;
ആ കരാർ രൂപകൽപ്പന ചെയ്യുന്നതുവരെ അത് ബാക്കെൻഡ്-നിർദ്ദിഷ്ടമായി തുടരേണ്ടതാണ്.

## അനുയോജ്യതാ ആവശ്യകതകൾ

ഈ ADR പിന്തുടരുന്ന ഏതൊരു ഇംപ്ലിമെന്റേഷനും ഇനിപ്പറയുന്ന സവിശേഷതകൾ നിലനിർത്തണം:

- SQLite സീറോ-കോൺഫിഗറേഷൻ ഡിഫോൾട്ടായി തുടരണം.
- നിലവിലുള്ള SQLite ഫയലുകളും മൈഗ്രേഷൻ ചരിത്രവും തുടർന്നും വായിക്കാനാകണം.
- npm, Electron, Docker, നിയന്ത്രിത-റൺടൈം SQLite ഫാൾബാക്കുകൾ എന്നിവ നിലവിലുള്ള സ്റ്റാർട്ടപ്പ് പാത നിലനിർത്തണം.
- സംഭരിച്ച പ്രൊവൈഡർ ക്രെഡൻഷ്യലുകൾ നിലവിലുള്ള ആപ്ലിക്കേഷൻ എൻക്രിപ്ഷൻ സ്വഭാവം തുടർന്നും ഉപയോഗിക്കണം.
- ഒരു റിപ്പോസിറ്ററി മൈഗ്രേഷൻ റൂട്ടിംഗ്, ക്വോട്ട, API-key, അല്ലെങ്കിൽ ഓഡിറ്റ് സെമാന്റിക്സ് നിശ്ശബ്ദമായി മാറ്റരുത്.
- ബാക്കപ്പിന്റെയും റിക്കവറിയുടെയും സ്വഭാവം സാർവത്രികമായി അവതരിപ്പിക്കുന്നതിനുപകരം ഓരോ ബാക്കെൻഡിനും പ്രത്യേകം രേഖപ്പെടുത്തണം.
- ശുദ്ധമായ SQLite-മാത്രമുള്ള ഇൻസ്റ്റലേഷൻ ഒരു ബാഹ്യ ഡാറ്റാബേസ് ഡ്രൈവർ ലോഡ് ചെയ്യുകയോ ആവശ്യപ്പെടുകയോ ചെയ്യരുത്.

## ഡെലിവറി ക്രമം

1. പുനരുത്പാദിപ്പിക്കാവുന്ന ഒരു SQLite കപ്ലിംഗ് ഇൻവെന്ററി പ്രത്യേക റിവ്യൂ ആർട്ടിഫാക്റ്റായി പ്രസിദ്ധീകരിക്കുക.
2. ആദ്യ ഡൊമെയ്ൻ റിപ്പോസിറ്ററി കരാറുകളും അനുരൂപതാ ടെസ്റ്റുകളും അവതരിപ്പിക്കുക.
3. ഡിഫോൾട്ടുകൾ മാറ്റാതെ, നിലവിലുള്ള SQLite ഇംപ്ലിമെന്റേഷനെ ആ കരാറുകൾക്ക് പിന്നിൽ അഡാപ്റ്റ് ചെയ്യുക.
4. മെയിന്റെയ്നറുടെ അംഗീകാരത്തിന് വിധേയമായി, ഒരു പരിധിനിർണ്ണയിച്ച കൺട്രോൾ-പ്ലെയിൻ സ്ലൈസിനായി PostgreSQL-നെ ആദ്യ
   ബാഹ്യ ഇംപ്ലിമെന്റേഷനായി ചേർക്കുക.
5. സമകാലിക റൈറ്റ്, മൈഗ്രേഷൻ-ഉടമസ്ഥാവകാശ ടെസ്റ്റുകൾ നിലവിൽ വന്നതിനുശേഷം മാത്രം പങ്കിട്ട സ്റ്റേറ്റ് വിപുലീകരിക്കുക.
6. ഡാറ്റാബേസ് സ്വിച്ചിംഗ് പരസ്യപ്പെടുത്തുന്നതിനുമുമ്പ്, ഓഫ്ലൈൻ ആയതും സാധൂകരിച്ചതുമായ SQLite-ൽനിന്ന്-ബാഹ്യ-ഡാറ്റാബേസിലേക്കുള്ള മൈഗ്രേഷൻ പാത ചേർക്കുക.
7. തെളിയിക്കപ്പെട്ട റിപ്പോസിറ്ററി, ബാക്കെൻഡ് കരാറുകൾക്ക് അനുസൃതമായി MySQL ചേർക്കുക.

ഓരോ റൺടൈം ഘട്ടവും പ്രത്യേകം റിവ്യൂ ചെയ്യാവുന്ന PR ആയിരിക്കണം. മുമ്പത്തെ ഘട്ടത്തിലെ തെളിയിക്കപ്പെടാത്ത ഒരു അബ്സ്ട്രാക്ഷൻ
ലയിപ്പിക്കുന്നതിനെ ന്യായീകരിക്കാൻ പിന്നീടുള്ള ഒരു ഘട്ടം ഉപയോഗിക്കരുത്.

## ആദ്യ ഇംപ്ലിമെന്റേഷൻ സ്ലൈസ്

കപ്ലിംഗ് ഇൻവെന്ററി അവലോകനം ചെയ്തതിന് ശേഷമാണ് ആദ്യ റൺടൈം സ്ലൈസ് തിരഞ്ഞെടുക്കേണ്ടത്. പ്രൊവൈഡർ
കണക്ഷനുകൾ, API കീകൾ, കോമ്പോകൾ, റൂട്ടിംഗ് കോൺഫിഗറേഷൻ എന്നിവയുടെ അടിസ്ഥാന ടേബിളുകൾ
`src/lib/db/core.ts`-ൽ ദൃശ്യമാകുന്നതിനാൽ അവ പരിഗണിക്കാവുന്നവയാണ്. എന്നാൽ ഈ ADR ഒരു ടേബിൾ ലിസ്റ്റിനോ മൈഗ്രേഷൻ PR-നോ
അംഗീകാരം നൽകുന്നില്ല. സ്ലൈസിൽ ഇനിപ്പറയുന്നവ ഉൾപ്പെടണം:

- SQLite സ്വഭാവം സംരക്ഷിക്കുന്നതിനുള്ള ടെസ്റ്റുകൾ;
- റിപ്പോസിറ്ററി അനുരൂപതാ ടെസ്റ്റുകൾ;
- വ്യക്തമായ ട്രാൻസാക്ഷൻ അതിരുകൾ;
- സംഭരിച്ച ക്രെഡൻഷ്യലുകൾക്കായുള്ള എൻക്രിപ്ഷൻ, റിഡാക്ഷൻ പരിശോധന;
- ഡിഫോൾട്ട് സ്റ്റാർട്ടപ്പ് കോൺഫിഗറേഷനിൽ മാറ്റമില്ലായ്മ.

## പരിഗണിച്ച ബദലുകൾ

### `SqliteAdapter`-ന് കീഴിൽ PostgreSQL ചേർക്കുക

നിരസിച്ചു. `SqliteAdapter` എന്നത് SQLite റൺടൈമുകൾക്കായുള്ള ഒരു കോംപാറ്റിബിലിറ്റി ലെയറാണ്, കൂടാതെ SQLite-നിർദ്ദിഷ്ട
ഓപ്പറേഷനുകൾ അത് ലഭ്യമാക്കുന്നു. ആ ഉപരിതലം അനുകരിക്കുന്നത് സിൻക്രണസ്, ഡയലക്റ്റ്-നിർദ്ദിഷ്ട അനുമാനങ്ങൾ ഒരു
പുതിയ ബാക്കെൻഡിലേക്ക് ചോരാൻ ഇടയാക്കും.

### എല്ലാ ഡൊമെയിനുകൾക്കും ഒരു ജനറിക് ക്വറി/എക്സിക്യൂട്ട് API ലഭ്യമാക്കുക

പ്രാഥമിക അതിരായി നിരസിച്ചു. അത് കണക്ഷൻ കൈകാര്യം ചെയ്യൽ കേന്ദ്രീകരിക്കുമെങ്കിലും SQL ഡയലക്റ്റ്,
ട്രാൻസാക്ഷൻ, ടേബിൾ കപ്ലിംഗ് എന്നിവ ബിസിനസ് മൊഡ്യൂളുകളിൽ തന്നെ ശേഷിക്കും. ഒരു ലോ-ലെവൽ ബാക്കെൻഡ് പ്രിമിറ്റീവ്
റിപ്പോസിറ്ററി ഇംപ്ലിമെന്റേഷനുകൾക്കുള്ളിൽ ഉണ്ടായേക്കാം, ആപ്ലിക്കേഷൻ അഭിമുഖീകരിക്കുന്ന പെർസിസ്റ്റൻസ് API ആയി അല്ല.

### ഒരു സ്ലൈസ് സാധൂകരിക്കുന്നതിന് മുമ്പ് മുഴുവൻ പെർസിസ്റ്റൻസും പുനരെഴുതുക

നിരസിച്ചു. നിലവിലെ പെർസിസ്റ്റൻസ് ഉപരിതലം വിശാലമാണ്; അതിൽ ഫയൽ ലൈഫ്സൈക്കിൾ, റിക്കവറി, സെർച്ച്,
ഓപ്പറേഷണൽ സെറ്റിംഗുകൾ എന്നിവ ഉൾപ്പെടുന്നു. വെർട്ടിക്കൽ സ്ലൈസുകൾ അവലോകനം ചെയ്യാവുന്ന സ്വഭാവവും റോൾബാക്ക് അതിരുകളും നൽകുന്നു.

### SQLite-നെ ഡിഫോൾട്ടായി ഉപയോഗിക്കുന്നത് മാറ്റിസ്ഥാപിക്കുക

നിരസിച്ചു. എംബെഡഡ്, ഡെസ്ക്ടോപ്പ് ഡിപ്ലോയ്മെന്റുകൾ നിലവിലുള്ള സീറോ-സർവീസ് സ്റ്റാർട്ടപ്പ് മോഡലിനെ ആശ്രയിക്കുന്നു. ഒരു
എക്സ്റ്റേണൽ ബാക്കെൻഡ് ഓപ്റ്റ്-ഇൻ ആണ്.

### Redis-നെ ഡ്യൂറബിൾ അതോറിറ്റിയായി ഉപയോഗിക്കുക

നിരസിച്ചു. വ്യക്തമായി എഫെമറൽ ആയ കോർഡിനേഷൻ, കാഷ്, അല്ലെങ്കിൽ കൗണ്ടറുകൾ എന്നിവയെ Redis പിന്തുണച്ചേക്കാം, എന്നാൽ ഇവിടെ
വിവരിച്ചിരിക്കുന്ന ഡ്യൂറബിൾ റിപ്പോസിറ്ററി കോൺട്രാക്റ്റിന് അത് പകരമാകുന്നില്ല.

## അനന്തരഫലങ്ങൾ

### ഗുണപരമായവ

- ഡാറ്റാബേസ് ഡയലക്റ്റിൽ നിന്ന് സ്വതന്ത്രമായ, സ്ഥിരതയുള്ള ഒരു പെർസിസ്റ്റൻസ് സീം ബിസിനസ് കോഡിന് ലഭിക്കുന്നു.
- ഒരു എക്സ്റ്റേണൽ ബാക്കെൻഡ് അബ്സ്ട്രാക്ഷൻ നിർവചിക്കുന്നതിന് മുമ്പ് SQLite സ്വഭാവം പരിശോധിക്കപ്പെടുന്നു.
- ഡൊമെയ്ൻ ലോജിക് തനിപ്പകർപ്പാക്കുന്നതിന് പകരം PostgreSQL-ഉം MySQL-ഉം കോൺട്രാക്റ്റുകളും ടെസ്റ്റുകളും പങ്കിടുന്നു.
- SQLite-ന് മാത്രമുള്ള ശേഷികൾ ചോർച്ചയുള്ള കോംപാറ്റിബിലിറ്റി ഷിമുകളായി മാറാതെ ഫസ്റ്റ്-ക്ലാസ് ആയി തുടരുന്നു.
- മൾട്ടി-റെപ്ലിക്ക മൈഗ്രേഷനും ട്രാൻസാക്ഷൻ സ്വഭാവവും വ്യക്തമായ ഡിസൈൻ പരിഗണനകളാകുന്നു.

### ചെലവുകളും അപകടസാധ്യതകളും

- റിപ്പോസിറ്ററി എക്സ്ട്രാക്ഷന് ക്രമാനുഗതമായ കോൾ-സൈറ്റ് മൈഗ്രേഷൻ ആവശ്യമാണ്.
- നിലവിൽ സിൻക്രണസ് ആയ സർവീസ് കോഡിലുടനീളം അസിങ്ക് അതിരുകൾ വ്യാപിച്ചേക്കാം.
- ക്രോസ്-ബാക്കെൻഡ് സെമാന്റിക്സിന് SQL സിന്റാക്സ് കോംപാറ്റിബിലിറ്റിക്ക് അപ്പുറമുള്ള അനുരൂപതാ ടെസ്റ്റുകൾ ആവശ്യമാണ്.
- ബാക്കപ്പ്, സെർച്ച്, വെക്റ്റർ സ്റ്റോറേജ്, മെയിന്റനൻസ് എന്നിവ ശേഷി-നിർദ്ദിഷ്ടമായി തുടരുന്നു.
- ഒന്നിലധികം പെർസിസ്റ്റൻസ് ഇംപ്ലിമെന്റേഷനുകൾ പ്രവർത്തിപ്പിക്കുന്നത് CI, ഓപ്പറേഷണൽ സപ്പോർട്ട് ചെലവുകൾ വർധിപ്പിക്കുന്നു.

## ലക്ഷ്യങ്ങളിൽ ഉൾപ്പെടാത്തവ

ഈ ADR ഇനിപ്പറയുന്നവ ചെയ്യുന്നില്ല:

- ഡാറ്റാബേസ് ഡിപെൻഡൻസി, എൻവയോൺമെന്റ് വേരിയബിൾ, സ്കീമ, അല്ലെങ്കിൽ മൈഗ്രേഷൻ ചേർക്കുന്നില്ല;
- ലൈവ് SQLite സിംഗിൾട്ടണിലോ ഡ്രൈവർ കാസ്കേഡിലോ മാറ്റം വരുത്തുന്നില്ല;
- ഒരു നിർദ്ദിഷ്ട റിലീസിൽ PostgreSQL അല്ലെങ്കിൽ MySQL പിന്തുണ വാഗ്ദാനം ചെയ്യുന്നില്ല;
- FTS5, `sqlite-vec`, ബാക്കപ്പ് ഫയലുകൾ, അല്ലെങ്കിൽ SQLite മെയിന്റനൻസ് എന്നിവ പോർട്ടബിൾ ആക്കുന്നില്ല;
- ഷെയർഡ്-സ്റ്റേറ്റ്, കോർഡിനേഷൻ ടെസ്റ്റുകൾ നിലവിൽ വരുന്നതിന് മുമ്പ് ആക്റ്റീവ്-ആക്റ്റീവ് സന്നദ്ധത നിർവചിക്കുന്നില്ല;
- `src/lib/db/`-ന്റെ ഒറ്റയടിക്കുള്ള പുനരെഴുത്തിന് അംഗീകാരം നൽകുന്നില്ല.

## പരിപാലകന്റെ അംഗീകാരത്തിനായുള്ള തുറന്ന ചോദ്യങ്ങൾ

1. റിപ്പോസിറ്ററിയും ആന്തരിക async ബാക്ക്എൻഡ് അതിർത്തിയും ഉൾപ്പെടുന്ന സമീപനമാണോ അഭികാമ്യം, അതോ
   ബാഹ്യ പെർസിസ്റ്റൻസ് ഒരു പ്രത്യേക കൺട്രോൾ-പ്ലെയിൻ സേവനത്തിന് പിന്നിലായിരിക്കണമോ?
2. SQLite അനുരൂപതയ്ക്കുശേഷമുള്ള ആദ്യ ബാഹ്യ ഇംപ്ലിമെന്റേഷനായി PostgreSQL സ്വീകാര്യമാണോ?
3. ആദ്യത്തെ പരിധിനിർണ്ണയിച്ച റിപ്പോസിറ്ററി സ്ലൈസായി ഏത് ഡൊമെയ്ൻ വേണം?
4. ആദ്യ മൾട്ടി-റെപ്ലിക്ക നാഴികക്കല്ലിനായി ഏത് സ്റ്റേറ്റാണ് പങ്കിടേണ്ടത്, ഏതാണ് നോഡ്-ലോക്കലായി തുടരേണ്ടത്?
5. തടസ്സപ്പെട്ടതോ റോൾ-ബാക്ക് ചെയ്തതോ ആയ റിപ്പോസിറ്ററി മൈഗ്രേഷനായി ഏത് അനുയോജ്യതാ കാലയളവാണ് ആവശ്യമായത്?

ഈ ചോദ്യങ്ങൾ പരിഹരിക്കപ്പെടുന്നതുവരെ, ഈ പ്രമാണം ഒരു നിർദ്ദേശമാണ്; റൺടൈം റീഫാക്ടർ ഇതിലൂടെ സൂചിപ്പിക്കുന്നില്ല.
