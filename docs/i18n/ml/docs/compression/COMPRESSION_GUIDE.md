> യോഗ്യമായ കോൺടെക്സ്റ്റിൽ സ്വയമേവ 15-95% ലാഭിക്കൂ. പെട്ടെന്നുള്ള ഒരു അവലോകനത്തിനായി, [README കംപ്രഷൻ വിഭാഗം](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) കാണുക.

## അവലോകനം

അപ്സ്ട്രീം പ്രൊവൈഡറുകളിലേക്ക് അഭ്യർത്ഥനകൾ എത്തുന്നതിന് മുമ്പ് **മുൻകൂട്ടി** പ്രവർത്തിക്കുന്ന ഒരു മോഡുലാർ പ്രോംപ്റ്റ് കംപ്രഷൻ പൈപ്പ്ലൈൻ OmniRoute നടപ്പിലാക്കുന്നു. അതായത്, നിങ്ങളുടെ ടോക്കൺ ലാഭം സുതാര്യമായി സംഭവിക്കുന്നു — നിങ്ങളുടെ വർക്ക്ഫ്ലോയിൽ മാറ്റങ്ങളൊന്നും ആവശ്യമില്ല.

```
ക്ലയന്റ് അഭ്യർത്ഥന
  → കംപ്രഷൻ സ്ട്രാറ്റജി സെലക്ടർ
    → കോംബോ ഓവർറൈഡ് ഉണ്ടോ? → കോംബോ ക്രമീകരണം ഉപയോഗിക്കുക
    → ഓട്ടോ-ട്രിഗർ ത്രെഷോൾഡ് എത്തിയോ? → ഓട്ടോ മോഡ് ഉപയോഗിക്കുക
    → ഡിഫോൾട്ട് മോഡ് ഉണ്ടോ? → ഗ്ലോബൽ ക്രമീകരണം ഉപയോഗിക്കുക
    → ഓഫാണോ? → കംപ്രഷൻ ഒഴിവാക്കുക
  → തിരഞ്ഞെടുത്ത കംപ്രഷൻ മോഡ്
    → ഓഫ്: കംപ്രഷൻ ഇല്ല
    → ലൈറ്റ്: സുരക്ഷിതമായ വൈറ്റ്സ്പേസ്/ഫോർമാറ്റിംഗ് വൃത്തിയാക്കൽ (~15%)
    → സ്റ്റാൻഡേർഡ്: ഗുഹാമനുഷ്യ ശൈലിയിലുള്ള അനാവശ്യ വാക്കുകൾ നീക്കംചെയ്യൽ (~30%)
    → അഗ്രസീവ്: ഹിസ്റ്ററി ഏജിംഗ് + സംഗ്രഹിക്കൽ (~50%)
    → അൾട്രാ: ഹ്യൂറിസ്റ്റിക് പ്രൂണിംഗ് + കോഡ്-ബ്ലോക്ക് ചുരുക്കൽ (~75%)
    → RTK: കമാൻഡ്-അവബോധമുള്ള ടെർമിനൽ/ടൂൾ-ഔട്ട്പുട്ട് ഫിൽട്ടറിംഗ് (60-90% അപ്സ്ട്രീം പരിധി)
    → സ്റ്റാക്ക്ഡ്: ക്രമപ്പെടുത്തിയ മൾട്ടി-എഞ്ചിൻ പൈപ്പ്ലൈൻ, സാധാരണയായി ആദ്യം RTK, തുടർന്ന് Caveman (78-95% യോഗ്യമായ പരിധി)
  → കംപ്രസ് ചെയ്ത അഭ്യർത്ഥന → പ്രൊവൈഡർ
```

## കംപ്രഷൻ മോഡുകൾ

### ഓഫ്

കംപ്രഷൻ പ്രയോഗിക്കില്ല. എല്ലാ സന്ദേശങ്ങളും മാറ്റമില്ലാതെ കടന്നുപോകുന്നു.

### ലൈറ്റ് മോഡ് (~15% ലാഭം, <1ms ലേറ്റൻസി)

ഏറ്റവും സുരക്ഷിതമായ മോഡ് — അർത്ഥപരമായ മാറ്റങ്ങളൊന്നുമില്ല, ഫോർമാറ്റിംഗ് വൃത്തിയാക്കൽ മാത്രം:

| സാങ്കേതികത               | വിവരണം                                                                     |
| ------------------------ | -------------------------------------------------------------------------- |
| `collapseWhitespace`     | തുടർച്ചയായ ശൂന്യവരികളും വരികളുടെ അവസാനത്തിലുള്ള സ്പേസുകളും ലയിപ്പിക്കുന്നു |
| `dedupSystemPrompt`      | ഡ്യൂപ്ലിക്കേറ്റ് സിസ്റ്റം സന്ദേശങ്ങൾ നീക്കംചെയ്യുന്നു                      |
| `compressToolResults`    | വിശദമായ ടൂൾ/ഫങ്ഷൻ ഔട്ട്പുട്ടുകൾ കംപ്രസ് ചെയ്യുന്നു                         |
| `removeRedundantContent` | ആവർത്തിച്ച നിർദ്ദേശങ്ങൾ നീക്കംചെയ്യുന്നു                                   |
| `replaceImageUrls`       | base64 ഇമേജ് ഡാറ്റ URI-കൾ ചുരുക്കുന്നു                                     |

**ഏറ്റവും അനുയോജ്യം:** എപ്പോഴും ഓണായുള്ള ഉപയോഗം, സുരക്ഷ നിർണായകമായ വർക്ക്ഫ്ലോകൾ.

### സ്റ്റാൻഡേർഡ് മോഡ് (~30% ലാഭം)

[Caveman](https://github.com/JuliusBrussee/caveman)-ൽ നിന്ന് പ്രചോദനം ഉൾക്കൊണ്ടത് — അർത്ഥം നിലനിർത്തിക്കൊണ്ട് അനാവശ്യ വാക്കുകളും അതിവിശദമായ പ്രയോഗങ്ങളും നീക്കംചെയ്യുന്നു:

- അനാവശ്യ വാക്കുകൾ നീക്കംചെയ്യുന്നു ("please", "I think", "basically", "actually")
- അതിവിശദമായ പ്രയോഗങ്ങൾ ചുരുക്കുന്നു ("in order to" → "to", "as a result of" → "because")
- വിനയപൂർവമായ മയപ്പെടുത്തലുകൾ നീക്കംചെയ്യുന്നു ("Would you mind...", "If you could possibly...")
- കോഡിംഗ് പ്രോംപ്റ്റുകൾക്കായി ക്രമീകരിച്ച 30+ regex നിയമങ്ങൾ

**ഏറ്റവും അനുയോജ്യം:** ദൈനംദിന കോഡിംഗ് വർക്ക്ഫ്ലോകൾ, ചെലവ് പരിഗണിക്കുന്ന ടീമുകൾ.

### അഗ്രസീവ് മോഡ് (~50% ലാഭം)

ദൈർഘ്യമേറിയ സെഷനുകൾക്കായുള്ള സ്മാർട്ട് ഹിസ്റ്ററി മാനേജ്മെന്റ്:

- **മെസേജ് ഏജിംഗ്** — പഴയ സന്ദേശങ്ങൾ ക്രമേണ കൂടുതൽ കംപ്രസ് ചെയ്യപ്പെടുന്നു
- **ടൂൾ റിസൾട്ട് സംഗ്രഹിക്കൽ** — ദൈർഘ്യമേറിയ ടൂൾ ഔട്ട്പുട്ടുകൾക്ക് പകരം സംഗ്രഹങ്ങൾ നൽകുന്നു
- **ഘടനാപരമായ സമഗ്രതാ ഗാർഡുകൾ** — `tool_use` + `tool_result` ജോടികൾ സ്ഥിരതയോടെ തുടരുന്നുവെന്ന് ഉറപ്പാക്കുന്നു
- **കോൺടെക്സ്റ്റ് വിൻഡോ അവബോധം** — ഓരോ മോഡലിന്റെയും ടോക്കൺ പരിധികൾ പാലിക്കുന്നു

**ഏറ്റവും അനുയോജ്യം:** ദൈർഘ്യമേറിയ ഡീബഗ്ഗിംഗ് സെഷനുകൾ, വലിയ കോഡ്ബേസുകൾ.

### അൾട്രാ മോഡ് (~75% ലാഭം)

ടോക്കൺ നിർണായകമായ സാഹചര്യങ്ങൾക്കുള്ള പരമാവധി കംപ്രഷൻ:

- **ഹ്യൂറിസ്റ്റിക് പ്രൂണിംഗ്** — പ്രസക്തി ത്രെഷോൾഡിന് താഴെയുള്ള സന്ദേശങ്ങൾ നീക്കംചെയ്യുന്നു
- **കോഡ് ബ്ലോക്ക് ചുരുക്കൽ** — ആവർത്തനമുള്ള കോഡ് ഉദാഹരണങ്ങൾ കംപ്രസ് ചെയ്യുന്നു
- **ബൈനറി സെർച്ച് ട്രങ്കേഷൻ** — കോൺടെക്സ്റ്റ് വിൻഡോയ്ക്കുള്ള ഏറ്റവും അനുയോജ്യമായ കട്ട് പോയിന്റ് കണ്ടെത്തുന്നു
- അഗ്രസീവ് മോഡിലെ എല്ലാ സവിശേഷതകളും ഉൾപ്പെടുത്തിയിരിക്കുന്നു

**ഏറ്റവും അനുയോജ്യം:** നിങ്ങൾ തുടർച്ചയായി കോൺടെക്സ്റ്റ് പരിധികളിൽ എത്തുമ്പോൾ.

### RTK മോഡ് (60-90% അപ്സ്ട്രീം പരിധി)

കോഡിംഗ്-ഏജന്റ് സെഷനുകളിൽ പ്രത്യക്ഷപ്പെടുന്ന വിശദമായ ടൂൾ ഔട്ട്പുട്ടുകൾക്കായി RTK മോഡ് ഒപ്റ്റിമൈസ് ചെയ്തിരിക്കുന്നു:

- `git status`, `git diff`, `git log`, ടെസ്റ്റ് റണ്ണറുകൾ,
  TypeScript/Vite/Webpack ബിൽഡുകൾ, ESLint/Biome/Prettier, npm ഓഡിറ്റ്/ഇൻസ്റ്റാളുകൾ, Docker ലോഗുകൾ, ഇൻഫ്രാ
  ഔട്ട്പുട്ട്, പൊതുവായ ഷെൽ ഔട്ട്പുട്ട് എന്നിവ പോലുള്ള കമാൻഡ്/ഔട്ട്പുട്ട് ക്ലാസുകൾ കണ്ടെത്തുന്നു
- `open-sse/services/compression/engines/rtk/filters/`-ൽ നിന്നുള്ള JSON ഫിൽട്ടർ പാക്കുകൾ പ്രയോഗിക്കുന്നു
- പ്രോജക്റ്റിലെയോ ഗ്ലോബൽ `filters.toml` ഫയലുകളിലെയോ RTK TOML സ്കീമ v1 ഫിൽട്ടറുകൾ, ഇൻലൈൻ-ടെസ്റ്റ്
  സാധൂകരണത്തോടും പ്രോജക്റ്റ് ഫയലുകൾക്കായുള്ള ട്രസ്റ്റ്-ഗേറ്റിംഗോടും കൂടി ഇമ്പോർട്ട് ചെയ്യുന്നു
- ഇൻലൈൻ പരിശോധനാ സാമ്പിളുകളുള്ള 49 ബിൽറ്റ്-ഇൻ ഫിൽട്ടറുകൾ ഉൾപ്പെടുന്നു
- ANSI കൺട്രോൾ സീക്വൻസുകൾ, പ്രോഗ്രസ് ബാറുകൾ, ആവർത്തിച്ച വരികൾ, നടപടിയെടുക്കാനാകാത്ത അനാവശ്യ വിവരങ്ങൾ എന്നിവ നീക്കംചെയ്യുന്നു
- പരാജയങ്ങൾ, പിശകുകൾ, മുന്നറിയിപ്പുകൾ, മാറ്റം വരുത്തിയ ഫയലുകൾ, സംഗ്രഹങ്ങൾ, ദൈർഘ്യമേറിയ ഔട്ട്പുട്ടിന്റെ അവസാനഭാഗം എന്നിവ നിലനിർത്തുന്നു
- ട്രസ്റ്റ്-ഗേറ്റഡ് പ്രോജക്റ്റ് ഫിൽട്ടറുകൾ, ഗ്ലോബൽ ഫിൽട്ടറുകൾ, ഐച്ഛികമായി റീഡാക്റ്റ് ചെയ്ത റോ-ഔട്ട്പുട്ട് വീണ്ടെടുക്കൽ എന്നിവ പിന്തുണയ്ക്കുന്നു

**ഏറ്റവും അനുയോജ്യം:** ഷെൽ, ബിൽഡ്, ടെസ്റ്റ്, git, grep, ഫയൽ-ഔട്ട്പുട്ട് ട്രാൻസ്ക്രിപ്റ്റുകൾ എന്നിവയുള്ള ഏജന്റ് സെഷനുകൾ.

### സ്റ്റാക്ക്ഡ് മോഡ് (78-95% യോഗ്യമായ പരിധി)

സ്റ്റാക്ക്ഡ് മോഡ് ഒന്നിലധികം കംപ്രഷൻ എഞ്ചിനുകൾ നിർണായകമായ ഒരു ക്രമത്തിൽ പ്രവർത്തിപ്പിക്കുന്നു. ഡിഫോൾട്ട് പൈപ്പ്ലൈൻ ഇതാണ്:

```txt
RTK -> Caveman
```

ഈ ക്രമത്തിൽ ആദ്യം ടെർമിനൽ/ടൂൾ ഔട്ട്പുട്ട് ചുരുക്കുന്നു, തുടർന്ന് ശേഷിക്കുന്ന സ്വാഭാവിക-ഭാഷാ പ്രോംപ്റ്റിൽ
Caveman അർത്ഥപരമായ ചുരുക്കൽ പ്രയോഗിക്കുന്നു. സ്റ്റാക്ക്ഡ് പൈപ്പ്ലൈനുകൾ ഗ്ലോബലായോ റൂട്ടിംഗ് കോംബോകൾക്ക്
അസൈൻ ചെയ്ത കംപ്രഷൻ കോംബോകൾ വഴിയോ കോൺഫിഗർ ചെയ്യാം.

**ഏറ്റവും അനുയോജ്യം:** വലിയ ടൂൾ ലോഗുകൾക്കൊപ്പം മനുഷ്യ നിർദ്ദേശങ്ങളോ അസിസ്റ്റന്റ് സംഗ്രഹങ്ങളോ ഉള്ള മിശ്രിത കോൺടെക്സ്റ്റ്.

## അപ്സ്ട്രീം ലാഭത്തിന്റെ കണക്ക്

രണ്ട് ഉറവിടങ്ങളിൽ നിന്നുള്ള കംപ്രഷൻ ലാഭം OmniRoute രേഖപ്പെടുത്തുന്നു: അപ്സ്ട്രീം പ്രോജക്റ്റ് ബെഞ്ച്മാർക്കുകളും
OmniRoute-ന്റെ സ്വന്തം എൻജിൻ സംയോജനവും.

| ഉറവിടം  | ഇവിടെ ഉപയോഗിച്ച അപ്സ്ട്രീം README കണക്ക്                                                                                            |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` കുറവ് ഔട്ട്പുട്ട് ടോക്കണുകൾ, `65%` ബെഞ്ച്മാർക്ക് ശരാശരി ഔട്ട്പുട്ട് ലാഭം, `22-87%` പരിധി, കൂടാതെ `~46%` ഇൻപുട്ട് കംപ്രഷൻ ടൂൾ |
| RTK     | `60-90%` കമാൻഡ്-ഔട്ട്പുട്ട് ലാഭം; മാതൃകാ സെഷനിൽ `~118,000 -> ~23,900` ടോക്കണുകൾ, അഥവാ `79.7%` ലാഭം (`~80%`)                         |

ഓവർലാപ്പ് ചെയ്യുന്ന ടൂൾ/കോൺടെക്സ്റ്റ് പേലോഡുകൾക്കായി, ഡിഫോൾട്ട് OmniRoute കോംബോ എൻജിനുകളെ ഇങ്ങനെ സ്റ്റാക്ക് ചെയ്യുന്നു:

```txt
RTK -> Caveman
```

സംയോജിത ലാഭം സങ്കലിതമല്ല, ഗുണനാത്മകമാണ്:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

RTK-ക്കും Caveman-നും ഒരേ ഇൻപുട്ട്/കോൺടെക്സ്റ്റ് പേലോഡ് കുറയ്ക്കാൻ കഴിയുമ്പോഴാണ് ആ `78-95%` കണക്ക് ബാധകമാകുന്നത്.
Caveman റെസ്പോൺസ് ഔട്ട്പുട്ട് മോഡ് വേറിട്ടതാണ്: അത് പ്രവർത്തനക്ഷമമാക്കുമ്പോൾ, Caveman-ന്റെ സ്വന്തം ഔട്ട്പുട്ട് ലാഭം (`65%`
ശരാശരി, `~75%` പ്രധാന കണക്ക്, `22-87%` പരിധി) ഉപയോഗിക്കുക. മൊത്തം ബില്ലിംഗ് ലാഭം നിങ്ങളുടെ പ്രോംപ്റ്റ്/ഔട്ട്പുട്ട് അനുപാതത്തെ ആശ്രയിച്ചിരിക്കുന്നു.

### "യോഗ്യമായത്" എന്നതുകൊണ്ട് യഥാർഥത്തിൽ അർത്ഥമാക്കുന്നത്

15-95% എന്ന പ്രധാന പരിധി യഥാർഥമാണ്, എന്നാൽ അത് **ആവർത്തനമുള്ളതോ അനാവശ്യമായി ദൈർഘ്യമേറിയതോ ആയ** ഉള്ളടക്കത്തിന് മാത്രമാണ് ബാധകമാകുന്നത് — ആവർത്തിച്ചുള്ള
പിശക് വരികൾ, ഒരേ മുന്നറിയിപ്പ് തുടർച്ചയായി പുറപ്പെടുവിക്കുന്ന ഒരു ബിൽഡ് ലോഗ്, അമിതവലുപ്പമുള്ള `grep`/ഫയൽ-റീഡ് ഡംപ് എന്നിവയ്ക്ക്.
**എല്ലാ** അഭ്യർത്ഥനയിലും ഇത്രയും ലാഭമുണ്ടാകുമെന്ന് ഇതിനർത്ഥമില്ല.

അനുഭവപരമായി സ്ഥിരീകരിച്ചത് (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): ഒരേപോലുള്ള 300
പിശക് വരികൾ അടങ്ങിയ Anthropic-രൂപത്തിലുള്ള `tool_result` ബ്ലോക്കിനെതിരെ നടത്തിയ ഒരു `stacked` (RTK + Caveman)
റൺ **95.93% ടോക്കൺ ലാഭം / 96.26% ക്യാരക്ടർ ലാഭം** നൽകി — പരസ്യപ്പെടുത്തിയ പരിധിക്കുള്ളിൽ തന്നെ.
എന്നാൽ, സാധാരണ ആവർത്തനമില്ലാത്ത ടൂൾ ഔട്ട്പുട്ടിനെതിരെ (വൃത്തിയുള്ള ഒരു `grep` മാച്ച് ലിസ്റ്റ്,
ഒരു ചെറിയ ഫയൽ റീഡ്, സാധാരണ സംഭാഷണ ടെക്സ്റ്റ്) ഇതേ പൈപ്പ്ലൈൻ പ്രവർത്തിപ്പിക്കുമ്പോൾ ശരിയായിത്തന്നെ **ഏതാണ്ട് പൂജ്യം ലാഭമാണ്** ലഭിക്കുന്നത്, കാരണം
നീക്കം ചെയ്യാൻ ആവർത്തനമുള്ളതായി ഒന്നുമില്ല; കൂടാതെ കോഡ് ബ്ലോക്കുകൾ, URLs, ഹെഡിങ്ങുകൾ, പതിപ്പുകൾ, അല്ലെങ്കിൽ ALL-CAPS കോൺസ്റ്റന്റ് ഐഡന്റിഫയറുകൾ
ഒഴിവാക്കുകയോ മാറ്റുകയോ ചെയ്യുന്ന ഒരു പുനരെഴുത്ത് അയയ്ക്കാൻ `validateCompression()` (`validation.ts`) അനുവദിക്കില്ല.

ഇത് പ്രതീക്ഷിക്കുന്ന സുരക്ഷിതമായ പെരുമാറ്റമാണ്, ബഗ് അല്ല: പ്രധാനമായും വൃത്തിയുള്ള ഫയലുകൾ റീഡ്/grep ചെയ്യുന്ന ഒരു കോഡിംഗ് സെഷനിൽ,
കംപ്രഷൻ പൂർണ്ണമായി പ്രവർത്തനക്ഷമമാക്കിയിട്ടുണ്ടെങ്കിലും മൊത്തം ലാഭം മിതമായിരിക്കും; അതേസമയം പരാജയപ്പെടുന്ന ഒരു
ലൂപ്പോ അമിതമായി ഔട്ട്പുട്ട് നൽകുന്ന ഒരു ലിന്ററോ നേരിടുന്ന സെഷനിൽ ആ ട്രാഫിക്കിന് പൂർണ്ണമായ 78-95% പരിധി ലഭിക്കും. ഒരൊറ്റ സെഷന്റെ
കുറഞ്ഞ മൊത്തം ലാഭശതമാനം, കംപ്രഷൻ തെറ്റായി കോൺഫിഗർ ചെയ്തതിനുള്ള തെളിവായി ഉപയോഗിക്കരുത് — ആദ്യം
അടിസ്ഥാന ടൂൾ ഔട്ട്പുട്ടിൽ യഥാർഥത്തിൽ ആവർത്തനം ഉണ്ടായിരുന്നോ എന്ന് പരിശോധിക്കുക.

## കോൺഫിഗറേഷൻ

### ഡാഷ്ബോർഡ്

`Dashboard → Context & Cache` എന്നതിലേക്ക് പോകുക:

- **കേവ്മാൻ** — മോഡ് തിരഞ്ഞെടുക്കൽ, ഭാഷാ പാക്കുകൾ, പ്രിവ്യൂ, ആഗോള ഡിഫോൾട്ടുകൾ
- **RTK** — കമാൻഡ്-ഫിൽട്ടർ പ്രിവ്യൂ, RTK സുരക്ഷാ ക്രമീകരണങ്ങൾ, ഫിൽട്ടർ കാറ്റലോഗ്
- **കംപ്രഷൻ കോമ്പോസ്** — റൂട്ടിംഗ് കോമ്പോകളിലേക്ക് അസൈൻ ചെയ്ത പേരുള്ള എഞ്ചിൻ പൈപ്പ്ലൈനുകൾ
- **ഓട്ടോ-ട്രിഗർ ത്രെഷോൾഡ്** — ടോക്കൺ എണ്ണം ത്രെഷോൾഡ് കവിയുമ്പോൾ കംപ്രഷൻ സ്വയമേവ പ്രവർത്തിപ്പിക്കുക

### ഓരോ കോംബോ ഓവർറൈഡും

`Dashboard → Context & Cache → Compression Combos` എന്നതിൽ, ഒരു റൂട്ടിംഗ് കോംബോയിലേക്ക് ഒരു കംപ്രഷൻ കോംബോ അസൈൻ ചെയ്യുക:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

ഇത് സൗജന്യ/കോഡിംഗ് പ്രൊവൈഡർമാരിൽ സ്റ്റാക്ക്ഡ് കംപ്രഷൻ ഉപയോഗിക്കാനും പണമടച്ചുള്ള സബ്സ്ക്രിപ്ഷനുകളിൽ ലൈറ്റ് മോഡ് നിലനിർത്താനും നിങ്ങളെ അനുവദിക്കുന്നു.

ഈ "പെർ-കോംബോ ഓവർറൈഡ്" അസൈൻമെന്റ് **റൂട്ടിംഗ്-കോംബോ കംപ്രഷൻ മോഡ്** ഓവർറൈഡിൽ (Default/Off/Lite/Standard/Aggressive/Ultra) നിന്ന് വ്യത്യസ്തമായ ഒരു നിയന്ത്രണമാണ് — ആ ഓവർറൈഡ് ഒരു പേരുള്ള കംപ്രഷൻ-കോംബോ പൈപ്പ്ലൈൻ തിരഞ്ഞെടുക്കുന്നില്ല; ഇത് `resolveCompressionPlan` ഉപയോഗിക്കുന്ന `compressionMode` ഫീൽഡ് സജ്ജമാക്കുന്നു. ഇത് കോംബോ കാർഡിൽ (`Dashboard → Combos`) അല്ലെങ്കിൽ, #6760 മുതൽ, `Dashboard → Context & Cache → Compression Combos` എന്നതിലെ "Assign to routing" ലിസ്റ്റിൽ ഓരോ റൂട്ടിംഗ് കോംബോയ്ക്കും, മുകളിൽ രേഖപ്പെടുത്തിയ പൈപ്പ്ലൈൻ-അസൈൻമെന്റ് ചെക്ക്ബോക്സിന് അടുത്തായി സജ്ജീകരിക്കാൻ കഴിയും. രണ്ട് ഉപരിതലങ്ങളും ഒരേ `PUT /api/combos/{id}` എൻഡ്പോയിന്റ് വഴി നിലനിൽക്കുന്നു.

### ഓരോ അഭ്യർത്ഥന ഓവർറൈഡും

ഒരൊറ്റ അഭ്യർത്ഥനയ്ക്കുള്ള കംപ്രഷൻ പ്ലാൻ ഓവർറൈഡ് ചെയ്യാൻ `x-omniroute-compression` അഭ്യർത്ഥന ഹെഡർ അയയ്ക്കുക. ഇതിന് ഏറ്റവും ഉയർന്ന മുൻഗണനയുണ്ട് — ഇത് റൂട്ടിംഗ്-കോംബോ ഓവർറൈഡ്, സജീവ പ്രൊഫൈൽ, ഓട്ടോ-ട്രിഗർ, പാനൽ ഡിഫോൾട്ട് എന്നിവയെ മറികടക്കുന്നു. അജ്ഞാത മൂല്യങ്ങൾ അവഗണിക്കപ്പെടുന്നു (അഭ്യർത്ഥന ഒരിക്കലും നിരസിക്കപ്പെടുന്നില്ല) കൂടാതെ ആഗോള മാസ്റ്റർ സ്വിച്ച് ഇപ്പോഴും എല്ലാം നിയന്ത്രിക്കുന്നു: കംപ്രഷൻ ആഗോളമായി ഓഫായിരിക്കുമ്പോൾ, ഹെഡറിന് അത് ഓണാക്കാൻ കഴിയില്ല. മൂല്യങ്ങൾ:

| മൂല്യം        | പ്രഭാവം                                                                                                             |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| `off`         | ഈ അഭ്യർത്ഥനയ്ക്ക് കംപ്രഷൻ ഇല്ല.                                                                                     |
| `default`     | പാനലിൽ നിന്ന് ലഭിച്ച ഡിഫോൾട്ട് പ്രൊഫൈൽ (സജീവ പ്രൊഫൈൽ അവഗണിക്കുന്നു). ലോസി എഞ്ചിനുകൾ ഓഫാക്കിയിരിക്കുന്നു.            |
| `safe`        | ഹെഡർ ഒഴിവാക്കുന്നതിന് തുല്യം: ഡെഡ്യൂപ്പും വൈറ്റ്സ്പേസ് ഫോൾഡിംഗും മാത്രം.                                            |
| `allow-lossy` | ഈ അഭ്യർത്ഥനയുടെ ഓപ്പറേറ്റർ പ്ലാൻ നിലനിർത്തുക, സംഗ്രഹങ്ങൾ, പ്രസക്തി ഫിൽട്ടറുകൾ, സ്റ്റൈൽ റീറൈറ്റുകൾ എന്നിവ ഉൾപ്പെടെ.  |
| `engine:<id>` | പ്രവർത്തനക്ഷമമാക്കുമ്പോൾ ഒരൊറ്റ എഞ്ചിൻ, ഉദാഹരണത്തിന് `engine:rtk`. ഇത് ആ എഞ്ചിനായുള്ള ഓരോ അഭ്യർത്ഥന ഓപ്റ്റ്-ഇൻ ആണ്. |
| `<combo>`     | പേര് (കേസ്-ഇൻസെൻസിറ്റീവ്) അനുസരിച്ച് ആദ്യം, പിന്നീട് ഐഡി അനുസരിച്ച് പൊരുത്തപ്പെടുന്ന ഒരു പേരുള്ള കോംബോ.             |

`allow-lossy`, `engine:<id>`, അല്ലെങ്കിൽ ഒരു പേരുള്ള കോംബോ ഇല്ലാതെ, ലോസി എഞ്ചിനുകൾ പ്രയോഗിക്കില്ല. കംപ്രഷൻ ഓണായിരിക്കുമ്പോൾ അഭ്യർത്ഥനയ്ക്ക് ഇപ്പോഴും സെഷൻ ഡെഡ്യൂപ്പും വൈറ്റ്സ്പേസ് ഫോൾഡിംഗും ലഭിക്കും.

പ്രയോഗിച്ച പ്ലാൻ `X-OmniRoute-Compression: <mode>; source=<source>` റെസ്പോൺസ് ഹെഡറിൽ പ്രതിധ്വനിക്കുന്നു, ഇവിടെ `<source>` എന്നത് `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, അല്ലെങ്കിൽ `off` എന്നിവയിൽ ഒന്നാണ്.

### API

```bash
# കംപ്രഷൻ ക്രമീകരണങ്ങൾ നേടുക
curl http://localhost:20128/api/settings/compression

# കംപ്രഷൻ ക്രമീകരണങ്ങൾ അപ്ഡേറ്റ് ചെയ്യുക
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# ഒരു പ്രത്യേക RTK/സ്റ്റാക്ക്ഡ് പേലോഡ് പ്രിവ്യൂ ചെയ്യുക
```

## വിപുലമായ കംപ്രഷൻ സിസ്റ്റങ്ങൾ

7 സ്റ്റാൻഡേർഡ് മോഡുകൾക്ക് പുറമെ, സന്ദർഭത്തിനനുസരിച്ച് സ്വയമേവ പ്രവർത്തിക്കുന്ന നിരവധി വിപുലമായ കംപ്രഷൻ സിസ്റ്റങ്ങൾ OmniRoute-ൽ ഉൾപ്പെടുന്നു.

### കാഷെ-അവബോധമുള്ള കംപ്രഷൻ

ചില ദാതാക്കൾ (പ്രോംപ്റ്റ് കാഷിംഗ് ഉള്ള ആന്ത്രോപിക് പോലുള്ളവ) **പ്രോംപ്റ്റ് കാഷിംഗ്** പിന്തുണയ്ക്കുന്നു, ഇത് ചെലവുകളും ലേറ്റൻസിയും കുറയ്ക്കുന്നതിന് പ്രോംപ്റ്റിന്റെ ഭാഗങ്ങൾ കാഷെ ചെയ്യാൻ അവരെ അനുവദിക്കുന്നു. കാഷിംഗ് പ്രവർത്തനക്ഷമമാക്കുമ്പോൾ, അമിതമായ കംപ്രഷൻ യഥാർത്ഥത്തിൽ പ്രകടനത്തെ **ദോഷകരമായി** ബാധിക്കും, കാരണം ഇത് കാഷെ ചെയ്ത ടോക്കണുകൾ മാറ്റുകയും കാഷെ അസാധുവാക്കുകയും ചെയ്യുന്നു.

`cachingAware.ts` മൊഡ്യൂൾ **കാഷിംഗ് സന്ദർഭം കണ്ടെത്തുകയും** അതിനനുസരിച്ച് **കംപ്രഷൻ തന്ത്രം ക്രമീകരിക്കുകയും** ചെയ്തുകൊണ്ട് ഇത് പരിഹരിക്കുന്നു.

#### ഇത് എങ്ങനെ പ്രവർത്തിക്കുന്നു

1. **കാഷിംഗ് സന്ദർഭം കണ്ടെത്തുക** — `cache_control` മാർക്കറുകൾക്കായി അഭ്യർത്ഥന ബോഡി സ്കാൻ ചെയ്യുന്നു
2. **കാഷിംഗ് ദാതാക്കളെ തിരിച്ചറിയുക** — ടാർഗെറ്റ് ദാതാവ് കാഷിംഗ് പിന്തുണയ്ക്കുന്നുണ്ടോയെന്ന് പരിശോധിക്കുന്നു
3. **തന്ത്രം ക്രമീകരിക്കുക** — കാഷിംഗ് ദാതാക്കൾക്കായി `aggressive`/`ultra` എന്നിവയെ `standard` ആയി തരംതാഴ്ത്തുന്നു
4. **സിസ്റ്റം പ്രോംപ്റ്റ് ഒഴിവാക്കുക** — സിസ്റ്റം പ്രോംപ്റ്റുകൾ സാധാരണയായി കാഷെ ചെയ്യപ്പെടുന്നു, അതിനാൽ അവയെ കംപ്രസ് ചെയ്യരുത്
5. **നിർണ്ണായക പരിവർത്തനങ്ങൾ ഉപയോഗിക്കുക** — സ്ഥിരമായ ഔട്ട്പുട്ട് ഉത്പാദിപ്പിക്കുന്ന പരിവർത്തനങ്ങൾ മാത്രം ഉപയോഗിക്കുക

#### കോഡ് ഉദാഹരണം

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← കാഷെ മാർക്കർ
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### എപ്പോൾ ഉപയോഗിക്കണം

കാഷെ-അവബോധമുള്ള കംപ്രഷൻ **എപ്പോഴും ഓൺ** ആണ് — കോൺഫിഗറേഷൻ ആവശ്യമില്ല. ഇത് ഈ സാഹചര്യങ്ങളിൽ മാത്രമേ പ്രവർത്തിക്കൂ:

- അഭ്യർത്ഥനയിൽ `cache_control` മാർക്കറുകൾ ഉണ്ട്
- ടാർഗെറ്റ് ദാതാവ് പ്രോംപ്റ്റ് കാഷിംഗ് പിന്തുണയ്ക്കുന്നു (ആന്ത്രോപിക്, OpenAI മുതലായവ)

### പ്രോഗ്രസ്സീവ് ഏജിംഗ്

നീണ്ട സംഭാഷണങ്ങൾ നിരവധി സന്ദേശങ്ങൾ ശേഖരിക്കുന്നു, എന്നാൽ പഴയ സന്ദേശങ്ങൾ അപ്രസക്തമാകുന്നു. `progressiveAging.ts` മൊഡ്യൂൾ **ടേൺ ദൂരത്തിനനുസരിച്ച് സന്ദേശങ്ങളെ തരംതാഴ്ത്തുന്നു**:

- **സമീപകാല ടേണുകൾ (0-3)**: അതേപടി നിലനിർത്തുന്നു (പൂർണ്ണ വിവരങ്ങൾ)
- **ഇടത്തരം ടേണുകൾ (4-8)**: ലൈറ്റ് കംപ്രഷൻ (വൈറ്റ്സ്പേസ്, ഫോർമാറ്റിംഗ് ക്ലീനപ്പ്)
- **പഴയ ടേണുകൾ (9+)**: കേവ്മാൻ കംപ്രഷൻ (ഫില്ലർ നീക്കംചെയ്യൽ, സംഗ്രഹം)
- **വളരെ പഴയ ടേണുകൾ (20+)**: വളരെയധികം സംഗ്രഹിക്കുകയോ ഒഴിവാക്കുകയോ ചെയ്യുന്നു

#### കോഡ് ഉദാഹരണം

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "നിങ്ങൾ ഒരു സഹായകരമായ അസിസ്റ്റന്റാണ്" },
  { role: "user", content: "2+2 എത്രയാണ്?" },
  { role: "assistant", content: "4" },
  // ... 50 കൂടുതൽ ടേണുകൾ ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // ആദ്യത്തെ 3 ടേണുകൾ: അതേപടി
  light: 8, // ടേണുകൾ 4-8: ലൈറ്റ് കംപ്രഷൻ
  moderate: 20, // ടേണുകൾ 9-20: കേവ്മാൻ കംപ്രഷൻ
  // ടേണുകൾ 21+: കനത്ത സംഗ്രഹം
});

// saved = സംരക്ഷിച്ച ടോക്കണുകളുടെ എണ്ണം
```

#### എപ്പോൾ ഉപയോഗിക്കണം

`aggressive`, `ultra` മോഡുകൾക്ക് പ്രോഗ്രസ്സീവ് ഏജിംഗ് **എപ്പോഴും ഓൺ** ആണ്. ഇത് പ്രത്യേകിച്ചും ഫലപ്രദമാണ്:

- ദീർഘകാല കോഡിംഗ് സെഷനുകൾക്ക്
- പല ദിവസങ്ങളിലായി നടക്കുന്ന സംഭാഷണങ്ങൾക്ക്
- നിരവധി ടൂൾ കോളുകളുള്ള ഏജന്റിക് വർക്ക്ഫ്ലോകൾക്ക്

### കേവ്മാൻ ഔട്ട്പുട്ട് മോഡ്

`outputMode.ts` മൊഡ്യൂൾ **സിസ്റ്റം പ്രോംപ്റ്റ് നിർദ്ദേശങ്ങൾ** നൽകി മോഡലിനെ കംപ്രസ് ചെയ്തതും സംക്ഷിപ്തവുമായ ഔട്ട്പുട്ട് (ഒരു "കേവ്മാൻ" ശൈലി) ഉത്പാദിപ്പിക്കാൻ പ്രേരിപ്പിക്കുന്നു.

#### ഇത് എങ്ങനെ പ്രവർത്തിക്കുന്നു

ഇൻപുട്ട് കംപ്രസ് ചെയ്യുന്നതിനുപകരം, ഈ മോഡ് ഒരു സിസ്റ്റം പ്രോംപ്റ്റ് ചേർക്കുന്നു:

> "കുറഞ്ഞ വാക്കുകളിൽ മറുപടി നൽകുക. മര്യാദകൾ ഒഴിവാക്കുക. ചെറിയ വാക്യങ്ങൾ ഉപയോഗിക്കുക."

ഇത് പ്രത്യേകിച്ചും നന്നായി പ്രവർത്തിക്കുന്നു:

- കോഡ് ജനറേഷന് (കൂടുതൽ സംക്ഷിപ്തമായ ഔട്ട്പുട്ട് = കുറഞ്ഞ ടോക്കണുകൾ)
- പെട്ടെന്നുള്ള ചോദ്യോത്തരങ്ങൾക്ക് (വിശദമായ വിശദീകരണങ്ങൾ ആവശ്യമില്ല)
- ബാച്ച് പ്രോസസ്സിംഗിന് (ത്രൂപുട്ട് പരമാവധിയാക്കാൻ)

#### എപ്പോൾ ഉപയോഗിക്കണം

കേവ്മാൻ ഔട്ട്പുട്ട് മോഡ് **ഓപ്റ്റ്-ഇൻ** ആണ് — കോംബോ കോൺഫിഗറേഷൻ വഴി ഇത് സജ്ജമാക്കുക:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "outputMode": "caveman"
    }
  }
}
```

### ഔട്ട്പുട്ട് സ്റ്റൈലുകൾ (കാറ്റലോഗ്)

മുകളിലുള്ള കേവ്മാൻ ഔട്ട്പുട്ട് മോഡ് **പഴയ സിംഗിൾ-സ്റ്റൈൽ പാത്ത്** ആണ്. ഘട്ടം 4 ഇത് കമ്പോസിബിൾ ഔട്ട്പുട്ട് സ്റ്റൈലുകളുടെ ഒരു കാറ്റലോഗായി സാമാന്യവൽക്കരിച്ചു: `open-sse/services/compression/outputStyles/catalog.ts` എന്നതിലെ `OUTPUT_STYLE_CATALOG`. ഓരോ ശൈലിയും മോഡലിനെ വിലകുറഞ്ഞ ഔട്ട്പുട്ട് ഉത്പാദിപ്പിക്കാൻ പ്രേരിപ്പിക്കുന്ന ഒരു സിസ്റ്റം-പ്രോംപ്റ്റ് നിർദ്ദേശമാണ്; ശൈലികൾ ഒരുമിച്ച് പ്രവർത്തനക്ഷമമാക്കാനും കാറ്റലോഗ് ക്രമത്തിൽ ഉൾപ്പെടുത്താനും കഴിയും.

#### ഇൻജക്ഷൻ എങ്ങനെ പ്രവർത്തിക്കുന്നു

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`)
തിരഞ്ഞെടുപ്പിനെ കാറ്റലോഗിനെതിരെ പരിഹരിക്കുന്നു (അജ്ഞാത ഐഡികളും ലൊക്കേൽ-പൊരുത്തപ്പെടാത്ത ശൈലികളും
ഒഴിവാക്കപ്പെടുന്നു, ഒരിക്കലും ഒരു പിശകല്ല), തിരഞ്ഞെടുത്ത നിർദ്ദേശങ്ങൾ കാറ്റലോഗ് ക്രമത്തിൽ സംയോജിപ്പിക്കുന്നു,
അതിർത്തി ക്ലോസ് **ഒരിക്കൽ** ചേർക്കുന്നു, കൂടാതെ ഒരു ഐഡംപൊട്ടൻസി മാർക്കറിന് (`[OmniRoute Output Styles]`) പിന്നിൽ സിസ്റ്റം പ്രോംപ്റ്റിലേക്ക് ഫലത്തെ മുൻകൂട്ടി ലോഡ് ചെയ്യുന്നു — വീണ്ടും പ്രയോഗിക്കുന്നത് ഒരു നോ-ഓപ്പ് ആണ്. കണ്ടെത്തിയ അഭ്യർത്ഥന ഭാഷയ്ക്ക് ഒരു വിവർത്തനം ഉണ്ടെങ്കിൽ, ഇംഗ്ലീഷിന് പകരം പ്രാദേശികവൽക്കരിച്ച നിർദ്ദേശം ഇൻജക്ട് ചെയ്യപ്പെടുന്നു.

#### എങ്ങനെ പ്രവർത്തനക്ഷമമാക്കാം

ഡാഷ്ബോർഡിൽ: **Context → Settings → Compression** — ഓരോ ശൈലിക്കും ഒരു ഓൺ/ഓഫ് ടോഗിളും ഒരു ലെവൽ സെലക്ടറും ഉള്ള ഒരു നിര. പ്രോഗ്രാമാറ്റിക്കായി, കംപ്രഷൻ കോൺഫിഗറേഷൻ തിരഞ്ഞെടുപ്പിനെ ഇങ്ങനെ നിലനിർത്തുന്നു:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

ബാക്ക്-കോംപാറ്റ്: ലെഗസി `outputMode: "caveman"` കോംബോ ക്രമീകരണം ഇപ്പോഴും പ്രവർത്തിക്കുന്നു, കൂടാതെ `terse-prose` ലേക്ക് മാപ്പ് ചെയ്യുന്നു, എല്ലാ ലെഗസി ഭാഷകളിലെയും പഴയ ഇൻജക്ഷന് സമാനമായ ബൈറ്റ്-ഐഡന്റിക്കൽ ആണ്.

ഭാഷാ തിരഞ്ഞെടുപ്പ്: `languageConfig.enabled` ഓൺ ആയിരിക്കുമ്പോൾ, `autoDetect` ഏറ്റവും പുതിയ ഉപയോക്തൃ സന്ദേശത്തിന്റെ ഭാഷ തിരഞ്ഞെടുക്കുന്നു (ഇൻപുട്ട് എഞ്ചിനുകൾക്ക് സമാനമായ ഡിറ്റക്ടർ); `autoDetect` ഓഫ് ചെയ്യുന്നത് `defaultLanguage` പിൻ ചെയ്യുന്നു. ഓഫ് → ഇംഗ്ലീഷ്.

`tests/unit/compression/output-styles-i18n-matrix.test.ts` വഴി ശൈലി × ഭാഷാ മാട്രിക്സ് പിൻ ചെയ്തിരിക്കുന്നു: ഒരു പുതിയ ശൈലിക്ക് കുറഞ്ഞത് ഒരു pt-BR വിവർത്തനമെങ്കിലും ഇല്ലാതെ (അല്ലെങ്കിൽ വ്യക്തമായ ട്രാക്ക് ചെയ്ത ഒഴിവാക്കൽ) ഷിപ്പ് ചെയ്യാൻ കഴിയില്ല, കൂടാതെ നിലവിലുള്ള ഒരു ശൈലിക്ക് ഒരു ലൊക്കേൽ നിശബ്ദമായി നഷ്ടപ്പെടാനും കഴിയില്ല. ഒരു ശൈലി ചേർക്കാൻ, [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) കാണുക.

### ടൂൾ ഫലം കംപ്രഷൻ

`toolResultCompressor.ts` മൊഡ്യൂൾ ടൂൾ ഫലങ്ങൾക്കായി (ഫംഗ്ഷൻ കോളുകൾ, ഏജന്റ് ഔട്ട്പുട്ടുകൾ, തിരയൽ ഫലങ്ങൾ മുതലായവ) **5 പ്രത്യേക കംപ്രഷൻ തന്ത്രങ്ങൾ** നൽകുന്നു:

1. **തിരയൽ ഫല കംപ്രഷൻ** — അനാവശ്യ ഫലങ്ങൾ നീക്കംചെയ്യുന്നു, ടോപ്പ്-N നിലനിർത്തുന്നു
2. **ഫയൽ റീഡ് കംപ്രഷൻ** — വലിയ ഫയലുകൾ ട്രങ്കേറ്റ് ചെയ്യുന്നു, ഹെഡറുകൾ/ഇംപോർട്ടുകൾ സംരക്ഷിക്കുന്നു
3. **കോഡ് എക്സിക്യൂഷൻ കംപ്രഷൻ** — അവശ്യമായ stdout/stderr മാത്രം നിലനിർത്തുന്നു
4. **ഡാറ്റാബേസ് ക്വറി കംപ്രഷൻ** — വരികൾ പരിമിതപ്പെടുത്തുന്നു, വെർബോസ് മെറ്റാഡാറ്റ നീക്കംചെയ്യുന്നു
5. **API പ്രതികരണ കംപ്രഷൻ** — നൾ ഫീൽഡുകൾ നീക്കംചെയ്യുന്നു, അറേകൾ സംയോജിപ്പിക്കുന്നു

#### എപ്പോൾ ഉപയോഗിക്കണം

ടൂൾ കോളുകൾ ഉള്ളപ്പോൾ ടൂൾ ഫല കംപ്രഷൻ **എപ്പോഴും ഓൺ** ആണ്. കോൺഫിഗറേഷൻ ആവശ്യമില്ല.

### സ്റ്റാക്ക്ഡ് പൈപ്പ്ലൈൻ

സ്റ്റാക്ക്ഡ് മോഡ് **ഒന്നിലധികം എഞ്ചിനുകൾ തുടർച്ചയായി** പ്രവർത്തിപ്പിക്കുന്നു — സാധാരണയായി RTK ആദ്യം (ടൂൾ ഔട്ട്പുട്ടിൽ 60-90% ലാഭം), തുടർന്ന് കേവ്മാൻ (ശേഷിക്കുന്ന ടെക്സ്റ്റിൽ 30% അധിക ലാഭം). ഇത് **മൊത്തം 78-95% ലാഭം** നേടുന്നു.

#### ഇത് എങ്ങനെ പ്രവർത്തിക്കുന്നു

```
ഇൻപുട്ട് (1000 ടോക്കണുകൾ)
  → RTK (കമാൻഡ്-അവബോധമുള്ള ഫിൽട്ടർ) → 200 ടോക്കണുകൾ
    → കേവ്മാൻ (ഫില്ലർ നീക്കംചെയ്യൽ) → 140 ടോക്കണുകൾ
  → ഔട്ട്പുട്ട് (140 ടോക്കണുകൾ, 86% ലാഭം)
```

#### എപ്പോൾ ഉപയോഗിക്കണം

ഇതിനായി സ്റ്റാക്ക്ഡ് മോഡ് ഉപയോഗിക്കുക:

- ടൂൾ-ഹെവി വർക്ക്ഫ്ലോകൾ (ഏജന്റിക് കോഡിംഗ്, ഗവേഷണം)
- ചെലവ്-സെൻസിറ്റീവ് ബാച്ച് പ്രോസസ്സിംഗ്
- നിങ്ങൾക്ക് പരമാവധി ടോക്കൺ ലാഭം ആവശ്യമുള്ളപ്പോൾ

കോംബോ വഴി കോൺഫിഗർ ചെയ്യുക:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "modePack": "stacked"
    }
  }
}
```

## കോംപ്രഷൻ കോംബോ ഓവർറൈഡുകൾ

വ്യത്യസ്ത ഉപയോഗസാഹചര്യങ്ങൾക്കായി പെരുമാറ്റം സൂക്ഷ്മമായി ക്രമീകരിക്കുന്നതിന്, ഗ്ലോബൽ കോംപ്രഷൻ മോഡ് **ഓരോ കോംബോയ്ക്കും** ഓവർറൈഡ് ചെയ്യാം:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "auto": {
      "weights": { "taskFit": 0.5 },
      "modePack": "quality-first"
    }
  },
  "compressionOverride": {
    "mode": "aggressive",
    "stackedPipelines": ["rtk", "caveman"],
    "preserveToolDefinitions": true
  }
}
```

ഇത് ഇനിപ്പറയുന്നവയ്ക്ക് ഉപകാരപ്രദമാണ്:

- **കോഡിംഗ് കോംബോകൾ**: ദീർഘമായ സെഷനുകൾക്കായി `aggressive` മോഡ് ഉപയോഗിക്കുക
- **ദ്രുത ചോദ്യോത്തര കോംബോകൾ**: വേഗത്തിലുള്ള പ്രതികരണങ്ങൾക്കായി `lite` മോഡ് ഉപയോഗിക്കുക
- **ടൂളുകൾ കൂടുതലായി ഉപയോഗിക്കുന്ന കോംബോകൾ**: പരമാവധി ലാഭത്തിനായി `stacked` മോഡ് ഉപയോഗിക്കുക
- **പ്രൊഡക്ഷൻ കോംബോകൾ**: കാഷിംഗ് പ്രൊവൈഡറുകൾക്കായി `cache-aware` മോഡ് ഉപയോഗിക്കുക
