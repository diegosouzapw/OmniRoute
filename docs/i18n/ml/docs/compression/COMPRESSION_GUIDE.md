> അനുയോജ്യമായ കോൺടെക്സ്റ്റിൽ സ്വയമേവ 15-95% ലാഭിക്കുക. പെട്ടെന്നുള്ള ഒരു അവലോകനത്തിനായി, [README കംപ്രഷൻ വിഭാഗം](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) കാണുക.

## അവലോകനം

അപ്സ്ട്രീം പ്രൊവൈഡർമാരിലേക്ക് അഭ്യർത്ഥനകൾ എത്തുന്നതിന് **മുൻകൂട്ടി** പ്രവർത്തിക്കുന്ന ഒരു മോഡുലാർ പ്രോംപ്റ്റ് കംപ്രഷൻ പൈപ്പ്ലൈൻ OmniRoute നടപ്പിലാക്കുന്നു. അതായത്, നിങ്ങളുടെ ടോക്കൺ ലാഭം സുതാര്യമായി സംഭവിക്കുന്നു — നിങ്ങളുടെ വർക്ക്ഫ്ലോയിൽ മാറ്റങ്ങളൊന്നും ആവശ്യമില്ല.

```
ക്ലയന്റ് അഭ്യർത്ഥന
  → കംപ്രഷൻ സ്ട്രാറ്റജി സെലക്ടർ
    → കോംബോ ഓവർറൈഡ്? → കോംബോ ക്രമീകരണം ഉപയോഗിക്കുക
    → ഓട്ടോ-ട്രിഗർ പരിധി? → ഓട്ടോ മോഡ് ഉപയോഗിക്കുക
    → ഡിഫോൾട്ട് മോഡ്? → ഗ്ലോബൽ ക്രമീകരണം ഉപയോഗിക്കുക
    → ഓഫ്? → കംപ്രഷൻ ഒഴിവാക്കുക
  → തിരഞ്ഞെടുത്ത കംപ്രഷൻ മോഡ്
    → ഓഫ്: കംപ്രഷൻ ഇല്ല
    → ലൈറ്റ്: സുരക്ഷിതമായ വൈറ്റ്സ്പേസ്/ഫോർമാറ്റിംഗ് വൃത്തിയാക്കൽ (~15%)
    → സ്റ്റാൻഡേർഡ്: ഗുഹാമനുഷ്യ ശൈലിയിൽ അനാവശ്യ പദങ്ങൾ നീക്കംചെയ്യൽ (~30%)
    → അഗ്രസീവ്: ഹിസ്റ്ററി ഏജിംഗ് + സംഗ്രഹിക്കൽ (~50%)
    → അൾട്രാ: ഹ്യൂറിസ്റ്റിക് പ്രൂണിംഗ് + കോഡ്-ബ്ലോക്ക് ലഘൂകരിക്കൽ (~75%)
    → RTK: കമാൻഡ്-അവബോധമുള്ള ടെർമിനൽ/ടൂൾ-ഔട്ട്പുട്ട് ഫിൽട്ടറിംഗ് (അപ്സ്ട്രീം പരിധി 60-90%)
    → സ്റ്റാക്ക്ഡ്: ക്രമീകരിച്ച മൾട്ടി-എഞ്ചിൻ പൈപ്പ്ലൈൻ, സാധാരണയായി RTK, തുടർന്ന് Caveman (അനുയോജ്യമായ പരിധി 78-95%)
  → കംപ്രസ് ചെയ്ത അഭ്യർത്ഥന → പ്രൊവൈഡർ
```

## കംപ്രഷൻ മോഡുകൾ

### ഓഫ്

കംപ്രഷൻ പ്രയോഗിക്കുന്നില്ല. എല്ലാ സന്ദേശങ്ങളും മാറ്റമില്ലാതെ കടന്നുപോകുന്നു.

### ലൈറ്റ് മോഡ് (~15% ലാഭം, <1ms ലേറ്റൻസി)

ഏറ്റവും സുരക്ഷിതമായ മോഡ് — അർത്ഥപരമായ മാറ്റമൊന്നുമില്ല, ഫോർമാറ്റിംഗ് വൃത്തിയാക്കൽ മാത്രം:

| സാങ്കേതികവിദ്യ           | വിവരണം                                                                     |
| ------------------------ | -------------------------------------------------------------------------- |
| `collapseWhitespace`     | തുടർച്ചയായ ശൂന്യവരികളും വരികളുടെ അവസാനത്തിലുള്ള സ്പേസുകളും ലയിപ്പിക്കുന്നു |
| `dedupSystemPrompt`      | ഡ്യൂപ്ലിക്കേറ്റ് സിസ്റ്റം സന്ദേശങ്ങൾ നീക്കംചെയ്യുന്നു                      |
| `compressToolResults`    | ദീർഘമായ ടൂൾ/ഫങ്ഷൻ ഔട്ട്പുട്ടുകൾ കംപ്രസ് ചെയ്യുന്നു                         |
| `removeRedundantContent` | ആവർത്തിച്ച നിർദ്ദേശങ്ങൾ നീക്കംചെയ്യുന്നു                                   |
| `replaceImageUrls`       | base64 ഇമേജ് ഡാറ്റ URI-കൾ ചുരുക്കുന്നു                                     |

**ഏറ്റവും അനുയോജ്യം:** എല്ലായ്പ്പോഴും പ്രവർത്തിക്കുന്ന ഉപയോഗം, സുരക്ഷാ-നിർണായക വർക്ക്ഫ്ലോകൾ.

### സ്റ്റാൻഡേർഡ് മോഡ് (~30% ലാഭം)

[Caveman](https://github.com/JuliusBrussee/caveman)-ൽ നിന്ന് പ്രചോദനം ഉൾക്കൊണ്ടത് — അർത്ഥം നിലനിർത്തിക്കൊണ്ട് അനാവശ്യ പദങ്ങളും ദീർഘമായ പ്രയോഗങ്ങളും നീക്കംചെയ്യുന്നു:

- അനാവശ്യ പദങ്ങൾ നീക്കംചെയ്യുന്നു ("please", "I think", "basically", "actually")
- ദീർഘമായ പ്രയോഗങ്ങൾ ചുരുക്കുന്നു ("in order to" → "to", "as a result of" → "because")
- വിനയപൂർവമായ മയപ്പെടുത്തൽ പ്രയോഗങ്ങൾ നീക്കംചെയ്യുന്നു ("Would you mind...", "If you could possibly...")
- കോഡിംഗ് പ്രോംപ്റ്റുകൾക്കായി ക്രമീകരിച്ച 30+ regex നിയമങ്ങൾ

**ഏറ്റവും അനുയോജ്യം:** ദൈനംദിന കോഡിംഗ് വർക്ക്ഫ്ലോകൾ, ചെലവ് പരിഗണിക്കുന്ന ടീമുകൾ.

### അഗ്രസീവ് മോഡ് (~50% ലാഭം)

ദൈർഘ്യമേറിയ സെഷനുകൾക്കായുള്ള സ്മാർട്ട് ഹിസ്റ്ററി മാനേജ്മെന്റ്:

- **സന്ദേശ ഏജിംഗ്** — പഴയ സന്ദേശങ്ങൾ ക്രമാനുഗതമായി കൂടുതൽ കംപ്രസ് ചെയ്യപ്പെടുന്നു
- **ടൂൾ റിസൾട്ട് കംപ്രഷൻ** — ദൈർഘ്യമേറിയ ടൂൾ ഔട്ട്പുട്ടുകൾ വെട്ടിച്ചുരുക്കുകയോ ഒഴിവാക്കുകയോ ചെയ്യുന്നു (ആദ്യ/അവസാന വരികൾ,
  പൊരുത്തപ്പെടുന്ന വരികളുടെ ഫിൽട്ടറിംഗ്, JSON കീ കംപാക്ഷൻ)
- **ഘടനാപരമായ സമഗ്രതാ സംരക്ഷണങ്ങൾ** — `tool_use` + `tool_result` ജോടികൾ സ്ഥിരതയോടെ തുടരുന്നുവെന്ന് ഉറപ്പാക്കുന്നു
- **കോൺടെക്സ്റ്റ് വിൻഡോ അവബോധം** — ഓരോ മോഡലിന്റെയും ടോക്കൺ പരിധികൾ മാനിക്കുന്നു

**ഏറ്റവും അനുയോജ്യം:** ദീർഘമായ ഡീബഗ്ഗിംഗ് സെഷനുകൾ, വലിയ കോഡ്ബേസുകൾ.

### അൾട്രാ മോഡ് (~75% ലാഭം)

ടോക്കൺ നിർണായകമായ സാഹചര്യങ്ങൾക്കുള്ള പരമാവധി കംപ്രഷൻ:

- **ഹ്യൂറിസ്റ്റിക് പ്രൂണിംഗ്** — ഗദ്യത്തിന്റെ സ്കോർ അടിസ്ഥാനത്തിലുള്ള ടോക്കൺ പ്രൂണിംഗ്
- **ഘടനാ സംരക്ഷണം** — ഫെൻസ് ചെയ്ത കോഡ് ബ്ലോക്കുകൾ, ഇൻലൈൻ കോഡ്, URL-കൾ, ഐഡന്റിഫയറുകൾ എന്നിവ
  ടൂംബ്സ്റ്റോൺ ചെയ്ത് അതേപടി വീണ്ടും ചേർക്കുന്നു; ഒരിക്കലും പ്രൂൺ ചെയ്യില്ല
- **ഓപ്ഷണൽ SLM ടയർ** — കോൺഫിഗർ ചെയ്തിട്ടുണ്ടെങ്കിൽ, ഒരു ചെറിയ ലോക്കൽ മോഡലിന് പ്രൂണിംഗ് കൂടുതൽ മെച്ചപ്പെടുത്താനാകും
- അഗ്രസീവ് മോഡിൽ നിന്ന് സ്വതന്ത്രമാണ്: ഇത് സന്ദേശ ഏജിംഗ്, ടൂൾ-റിസൾട്ട് കംപ്രഷൻ,
  അല്ലെങ്കിൽ ഫാൾബാക്ക് സംഗ്രഹിക്കൽ എന്നിവ പ്രവർത്തിപ്പിക്കില്ല (SLM-ടയർ പരാജയം മാത്രമേ
  അഗ്രസീവിലൂടെ ഒരു ഫാൾബാക്ക് പാസ് റൂട്ട് ചെയ്യുകയുള്ളൂ)

**ഏറ്റവും അനുയോജ്യം:** നിങ്ങൾ ആവർത്തിച്ച് കോൺടെക്സ്റ്റ് പരിധികളിൽ എത്തുമ്പോൾ.

### RTK മോഡ് (അപ്സ്ട്രീം പരിധി 60-90%)

കോഡിംഗ്-ഏജന്റ് സെഷനുകളിൽ പ്രത്യക്ഷപ്പെടുന്ന ദീർഘമായ ടൂൾ ഔട്ട്പുട്ടുകൾക്കായി RTK മോഡ് ഒപ്റ്റിമൈസ് ചെയ്തിരിക്കുന്നു:

- `git status`, `git diff`, `git log`, ടെസ്റ്റ് റണ്ണറുകൾ,
  TypeScript/Vite/Webpack ബിൽഡുകൾ, ESLint/Biome/Prettier, npm ഓഡിറ്റ്/ഇൻസ്റ്റാളുകൾ, Docker ലോഗുകൾ, ഇൻഫ്രാ
  ഔട്ട്പുട്ട്, പൊതുവായ ഷെൽ ഔട്ട്പുട്ട് തുടങ്ങിയ കമാൻഡ്/ഔട്ട്പുട്ട് ക്ലാസുകൾ കണ്ടെത്തുന്നു
- `open-sse/services/compression/engines/rtk/filters/`-ൽ നിന്നുള്ള JSON ഫിൽട്ടർ പാക്കുകൾ പ്രയോഗിക്കുന്നു
- പ്രോജക്റ്റിലെയോ ഗ്ലോബൽ `filters.toml` ഫയലുകളിലെയോ RTK TOML സ്കീമ v1 ഫിൽട്ടറുകൾ ഇംപോർട്ട് ചെയ്യുന്നു; ഇൻലൈൻ-ടെസ്റ്റ്
  വാലിഡേഷനും പ്രോജക്റ്റ് ഫയലുകൾക്കായുള്ള ട്രസ്റ്റ്-ഗേറ്റിംഗും ഉൾപ്പെടെ
- ഇൻലൈൻ വെരിഫൈ സാമ്പിളുകളുള്ള 55 ബിൽറ്റ്-ഇൻ ഫിൽട്ടറുകൾ ഉൾക്കൊള്ളുന്നു
- ANSI കൺട്രോൾ സീക്വൻസുകൾ, പ്രോഗ്രസ് ബാറുകൾ, ആവർത്തിച്ച വരികൾ, നടപടിയെടുക്കാനാകാത്ത അനാവശ്യ ഉള്ളടക്കം എന്നിവ നീക്കംചെയ്യുന്നു
- പരാജയങ്ങൾ, പിശകുകൾ, മുന്നറിയിപ്പുകൾ, മാറിയ ഫയലുകൾ, സംഗ്രഹങ്ങൾ, ദൈർഘ്യമേറിയ ഔട്ട്പുട്ടിന്റെ അവസാനഭാഗം എന്നിവ സംരക്ഷിക്കുന്നു
- ട്രസ്റ്റ്-ഗേറ്റഡ് പ്രോജക്റ്റ് ഫിൽട്ടറുകൾ, ഗ്ലോബൽ ഫിൽട്ടറുകൾ, ഓപ്ഷണൽ റിഡാക്റ്റഡ് റോ-ഔട്ട്പുട്ട് വീണ്ടെടുക്കൽ എന്നിവ പിന്തുണയ്ക്കുന്നു

**ഏറ്റവും അനുയോജ്യം:** ഷെൽ, ബിൽഡ്, ടെസ്റ്റ്, git, grep, ഫയൽ-ഔട്ട്പുട്ട് ട്രാൻസ്ക്രിപ്റ്റുകൾ എന്നിവയുള്ള ഏജന്റ് സെഷനുകൾ.

### സ്റ്റാക്ക്ഡ് മോഡ് (അനുയോജ്യമായ പരിധി 78-95%)

സ്റ്റാക്ക്ഡ് മോഡ് ഒന്നിലധികം കംപ്രഷൻ എഞ്ചിനുകൾ നിർണായകമായ ഒരു ക്രമത്തിൽ പ്രവർത്തിപ്പിക്കുന്നു. ഡിഫോൾട്ട് പൈപ്പ്ലൈൻ:

```txt
RTK -> Caveman
```

ആ ക്രമം ആദ്യം ടെർമിനൽ/ടൂൾ ഔട്ട്പുട്ട് ചുരുക്കുന്നു, തുടർന്ന് ശേഷിക്കുന്ന സ്വാഭാവിക-ഭാഷാ പ്രോംപ്റ്റിൽ Caveman അർത്ഥപരമായ സംക്ഷിപ്തീകരണം പ്രയോഗിക്കുന്നു. സ്റ്റാക്ക്ഡ് പൈപ്പ്ലൈനുകൾ ഗ്ലോബലായോ റൂട്ടിംഗ് കോംബോകൾക്ക് നൽകിയിരിക്കുന്ന കംപ്രഷൻ കോംബോകൾ വഴിയോ കോൺഫിഗർ ചെയ്യാം.

**ഏറ്റവും അനുയോജ്യം:** വലിയ ടൂൾ ലോഗുകളും മനുഷ്യ നിർദ്ദേശങ്ങളോ അസിസ്റ്റന്റ് സംഗ്രഹങ്ങളോ ഉൾപ്പെടുന്ന സമ്മിശ്ര കോൺടെക്സ്റ്റ്.

## അപ്സ്ട്രീം ലാഭത്തിന്റെ കണക്ക്

OmniRoute രണ്ട് ഉറവിടങ്ങളിൽ നിന്നുള്ള കംപ്രഷൻ ലാഭം രേഖപ്പെടുത്തുന്നു: അപ്സ്ട്രീം പ്രോജക്റ്റ് ബെഞ്ച്മാർക്കുകളും
OmniRoute-ന്റെ സ്വന്തം എഞ്ചിൻ സംയോജനവും.

| ഉറവിടം  | ഇവിടെ ഉപയോഗിച്ചിരിക്കുന്ന അപ്സ്ട്രീം README സംഖ്യ                                                                                   |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` കുറവ് ഔട്ട്പുട്ട് ടോക്കണുകൾ, `65%` ബെഞ്ച്മാർക്ക് ശരാശരി ഔട്ട്പുട്ട് ലാഭം, `22-87%` പരിധി, കൂടാതെ `~46%` ഇൻപുട്ട് കംപ്രഷൻ ടൂൾ |
| RTK     | കമാൻഡ്-ഔട്ട്പുട്ടിൽ `60-90%` ലാഭം; സാമ്പിൾ സെഷനിൽ `~118,000 -> ~23,900` ടോക്കണുകൾ, അഥവാ `79.7%` ലാഭം (`~80%`)                       |

ഓവർലാപ്പ് ചെയ്യുന്ന ടൂൾ/കോൺടെക്സ്റ്റ് പേലോഡുകൾക്കായി, ഡിഫോൾട്ട് OmniRoute കോംബോ എഞ്ചിനുകളെ ഒന്നിനുപുറകെ ഒന്നായി പ്രയോഗിക്കുന്നു:

```txt
RTK -> Caveman
```

സംയോജിത ലാഭം അഡിറ്റീവ് അല്ല, മൾട്ടിപ്ലിക്കേറ്റീവ് ആണ്:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

RTK-യ്ക്കും Caveman-നും ഒരേ ഇൻപുട്ട്/കോൺടെക്സ്റ്റ് പേലോഡ് കുറയ്ക്കാൻ കഴിയുമ്പോഴാണ് ആ `78-95%` സംഖ്യ ബാധകമാകുന്നത്.
Caveman റെസ്പോൺസ് ഔട്ട്പുട്ട് മോഡ് വേറിട്ടതാണ്: അത് പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ, Caveman-ന്റെ സ്വന്തം ഔട്ട്പുട്ട് ലാഭം (`65%`
ശരാശരി, `~75%` പ്രധാന കണക്ക്, `22-87%` പരിധി) ഉപയോഗിക്കുക. മൊത്തം ബില്ലിംഗ് ലാഭം നിങ്ങളുടെ പ്രോംപ്റ്റ്/ഔട്ട്പുട്ട് അനുപാതത്തെ ആശ്രയിച്ചിരിക്കുന്നു.

### "യോഗ്യമായത്" യഥാർത്ഥത്തിൽ എന്താണ് അർത്ഥമാക്കുന്നത്

15-95% എന്ന പ്രധാന പരിധി യഥാർത്ഥമാണ്, പക്ഷേ അത് **ആവർത്തനമുള്ളതോ അനാവശ്യമായി ദൈർഘ്യമേറിയതോ ആയ** ഉള്ളടക്കത്തിന് മാത്രമാണ് ബാധകമാകുന്നത് — ആവർത്തിക്കുന്ന
പിശക് വരികൾ, ഒരേ മുന്നറിയിപ്പ് നിരന്തരം പ്രദർശിപ്പിക്കുന്ന ബിൽഡ് ലോഗ്, അമിതമായി വലുതായ `grep`/ഫയൽ-റീഡ് ഡമ്പ് എന്നിവയ്ക്ക്.
**എല്ലാ** അഭ്യർത്ഥനകളിലും ഇത്രയും ലാഭമുണ്ടാകുമെന്ന് ഇതിനർത്ഥമില്ല.

പ്രായോഗികമായി സ്ഥിരീകരിച്ചത് (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): സമാനമായ 300
പിശക് വരികൾ അടങ്ങിയ Anthropic-രൂപത്തിലുള്ള `tool_result` ബ്ലോക്കിൽ നടത്തിയ ഒരു `stacked` (RTK + Caveman) റൺ
**95.93% ടോക്കൺ ലാഭം / 96.26% ക്യാരക്ടർ ലാഭം** നൽകി — പരസ്യപ്പെടുത്തിയ പരിധിക്കുള്ളിൽത്തന്നെ.
എന്നാൽ സാധാരണവും ആവർത്തനമില്ലാത്തതുമായ ടൂൾ ഔട്ട്പുട്ടിൽ (വൃത്തിയുള്ള ഒരു `grep` മാച്ച് ലിസ്റ്റ്,
ഹ്രസ്വമായ ഫയൽ റീഡ്, സാധാരണ സംഭാഷണ ടെക്സ്റ്റ്) അതേ പൈപ്പ്ലൈൻ പ്രവർത്തിപ്പിക്കുമ്പോൾ, ശരിയായി **പൂജ്യത്തോട് അടുത്ത ലാഭം** മാത്രമാണ് ലഭിക്കുന്നത്, കാരണം
നീക്കം ചെയ്യാൻ ആവർത്തനമുള്ള ഒന്നുമില്ല; കൂടാതെ കോഡ് ബ്ലോക്കുകൾ, URL-കൾ, തലക്കെട്ടുകൾ, പതിപ്പുകൾ, അല്ലെങ്കിൽ ALL-CAPS കോൺസ്റ്റന്റ് ഐഡന്റിഫയറുകൾ
ഒഴിവാക്കുകയോ മാറ്റുകയോ ചെയ്യുന്ന ഒരു റീറൈറ്റ് അയയ്ക്കാൻ `validateCompression()` (`validation.ts`) അനുവദിക്കില്ല.

ഇത് പ്രതീക്ഷിക്കാവുന്ന സുരക്ഷിതമായ പെരുമാറ്റമാണ്, ബഗ് അല്ല: കംപ്രഷൻ പൂർണ്ണമായി പ്രവർത്തനക്ഷമമാക്കിയിട്ടും, പ്രധാനമായും വൃത്തിയുള്ള ഫയലുകൾ
വായിക്കുകയോ grep ചെയ്യുകയോ ചെയ്യുന്ന ഒരു കോഡിംഗ് സെഷനിൽ മൊത്തത്തിലുള്ള ലാഭം മിതമായിരിക്കും; അതേസമയം, പരാജയപ്പെടുന്ന ഒരു
ലൂപ്പോ അമിതമായി ഔട്ട്പുട്ട് നൽകുന്ന ലിന്ററോ നേരിടുന്ന സെഷനിൽ, ആ ട്രാഫിക്കിൽ പൂർണ്ണമായ 78-95% പരിധിയിലുള്ള ലാഭം ലഭിക്കും. കംപ്രഷൻ തെറ്റായി കോൺഫിഗർ ചെയ്തിരിക്കുന്നു എന്നതിന് തെളിവായി ഒരൊറ്റ സെഷനിലെ
കുറഞ്ഞ മൊത്തം ലാഭശതമാനം ഉപയോഗിക്കരുത് — ആദ്യം അടിസ്ഥാന ടൂൾ ഔട്ട്പുട്ട് യഥാർത്ഥത്തിൽ ആവർത്തനമുള്ളതായിരുന്നോ എന്ന് പരിശോധിക്കുക.

## കോൺഫിഗറേഷൻ

### ഡാഷ്ബോർഡ്

`Dashboard → Context & Cache` എന്നതിലേക്ക് പോകുക:

- **Caveman** — മോഡ് തിരഞ്ഞെടുക്കൽ, ഭാഷാ പാക്കുകൾ, പ്രിവ്യൂ, ആഗോള ഡിഫോൾട്ടുകൾ
- **RTK** — കമാൻഡ്-ഫിൽട്ടർ പ്രിവ്യൂ, RTK സുരക്ഷാ ക്രമീകരണങ്ങൾ, ഫിൽട്ടർ കാറ്റലോഗ്
- **Compression Combos** — റൂട്ടിംഗ് കോംബോകൾക്ക് നിയോഗിച്ചിരിക്കുന്ന പേരിട്ട എൻജിൻ പൈപ്പ്ലൈനുകൾ
- **Auto-Trigger Threshold** — ടോക്കൺ എണ്ണം പരിധി കവിയുമ്പോൾ കംപ്രഷൻ സ്വയമേവ സജീവമാക്കുന്നു

### ഓരോ കോംബോയ്ക്കുമുള്ള ഓവർറൈഡ്

`Dashboard → Context & Cache → Compression Combos` എന്നതിൽ, ഒരു റൂട്ടിംഗ് കോംബോയ്ക്ക് ഒരു കംപ്രഷൻ കോംബോ നിയോഗിക്കുക:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

പണമടച്ചുള്ള സബ്സ്ക്രിപ്ഷനുകളിൽ ലൈറ്റ് മോഡ് നിലനിർത്തിക്കൊണ്ട്, സൗജന്യ/കോഡിംഗ് പ്രൊവൈഡറുകളിൽ സ്റ്റാക്ക് ചെയ്ത കംപ്രഷൻ ഉപയോഗിക്കാൻ ഇത് നിങ്ങളെ അനുവദിക്കുന്നു.

ഈ "Per-Combo Override" നിയോഗം **routing-combo compression mode** ഓവർറൈഡിൽനിന്ന് വ്യത്യസ്തമായ ഒരു നിയന്ത്രണമാണ് (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — ഈ ഫീൽഡിന്റെ സ്കീമ `rtk`, `stacked`, `omniglyph` എന്നിവയും സ്വീകരിക്കുന്നു) — ആ ഓവർറൈഡ് പേരിട്ട കംപ്രഷൻ-കോംബോ പൈപ്പ്ലൈൻ തിരഞ്ഞെടുക്കുന്നില്ല; `resolveCompressionPlan` പരിശോധിക്കുന്ന `compressionMode` ഫീൽഡ് മാത്രമാണ് അത് സജ്ജമാക്കുന്നത്. ഇത് കോംബോ കാർഡിൽ (`Dashboard → Combos`) സജ്ജമാക്കാം, അല്ലെങ്കിൽ #6760 മുതൽ, മുകളിൽ രേഖപ്പെടുത്തിയ പൈപ്പ്ലൈൻ-അസൈൻമെന്റ് ചെക്ക്ബോക്സിന് തൊട്ടടുത്തുള്ള `Dashboard → Context & Cache → Compression Combos` എന്നതിലെ "Assign to routing" പട്ടികയിൽ ഓരോ റൂട്ടിംഗ് കോംബോയ്ക്കും പ്രത്യേകം സജ്ജമാക്കാം. രണ്ട് ഇന്റർഫേസുകളിലെയും മാറ്റങ്ങൾ ഒരേ `PUT /api/combos/{id}` എൻഡ്പോയിന്റിലൂടെയാണ് നിലനിർത്തുന്നത്.

### ഓരോ അഭ്യർത്ഥനയ്ക്കുമുള്ള ഓവർറൈഡ്

ഒരൊറ്റ അഭ്യർത്ഥനയ്ക്കുള്ള കംപ്രഷൻ പ്ലാൻ ഓവർറൈഡ് ചെയ്യാൻ `x-omniroute-compression` അഭ്യർത്ഥന ഹെഡർ അയയ്ക്കുക. ഇതിന് ഏറ്റവും ഉയർന്ന മുൻഗണനയുണ്ട് — റൂട്ടിംഗ്-കോംബോ ഓവർറൈഡ്, സജീവ പ്രൊഫൈൽ, ഓട്ടോ-ട്രിഗർ, പാനലിലെ Default എന്നിവയെ ഇത് മറികടക്കും. തിരിച്ചറിയാത്ത മൂല്യങ്ങൾ അവഗണിക്കപ്പെടും (അഭ്യർത്ഥന ഒരിക്കലും നിരസിക്കപ്പെടില്ല), കൂടാതെ ആഗോള മാസ്റ്റർ സ്വിച്ച് ഇപ്പോഴും എല്ലാം നിയന്ത്രിക്കുന്നു: ആഗോളതലത്തിൽ കംപ്രഷൻ ഓഫായിരിക്കുമ്പോൾ, ഹെഡറിന് അത് ഓൺ ചെയ്യാനാകില്ല. മൂല്യങ്ങൾ:

| മൂല്യം        | ഫലം                                                                                                                  |
| ------------- | -------------------------------------------------------------------------------------------------------------------- |
| `off`         | ഈ അഭ്യർത്ഥനയ്ക്ക് കംപ്രഷൻ ഇല്ല.                                                                                      |
| `default`     | പാനലിൽനിന്ന് ലഭിക്കുന്ന Default പ്രൊഫൈൽ (സജീവ പ്രൊഫൈൽ അവഗണിക്കുന്നു). നഷ്ടമുണ്ടാക്കുന്ന എൻജിനുകൾ ഓഫായി തുടരും.       |
| `safe`        | ഹെഡർ ഒഴിവാക്കുന്നതിന് തുല്യം: ഡീഡ്യൂപ്ലിക്കേഷനും വൈറ്റ്സ്പേസ് ഫോൾഡിംഗും മാത്രം.                                      |
| `allow-lossy` | സംഗ്രഹങ്ങൾ, പ്രസക്തി ഫിൽട്ടറുകൾ, ശൈലി പുനരെഴുത്തുകൾ എന്നിവ ഉൾപ്പെടെ ഈ അഭ്യർത്ഥനയുടെ ഓപ്പറേറ്റർ പ്ലാൻ നിലനിർത്തുക.    |
| `engine:<id>` | പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ ഒരൊറ്റ എൻജിൻ, ഉദാ. `engine:rtk`. ആ എൻജിനുള്ള ഓരോ അഭ്യർത്ഥനയുടെയും ഓപ്റ്റ്-ഇൻ ഇതാണ്. |
| `<combo>`     | പേരിട്ട കോംബോ; ആദ്യം പേര് ഉപയോഗിച്ച് (കേസ് പരിഗണിക്കാതെ), തുടർന്ന് id ഉപയോഗിച്ച് പൊരുത്തപ്പെടുത്തുന്നു.              |

`allow-lossy`, `engine:<id>`, അല്ലെങ്കിൽ പേരിട്ട കോംബോ എന്നിവ ഇല്ലെങ്കിൽ, നഷ്ടമുണ്ടാക്കുന്ന എൻജിനുകൾ പ്രയോഗിക്കില്ല. കംപ്രഷൻ ഓണായിരിക്കുമ്പോൾ അഭ്യർത്ഥനയ്ക്ക് സെഷൻ ഡീഡ്യൂപ്ലിക്കേഷനും വൈറ്റ്സ്പേസ് ഫോൾഡിംഗും തുടർന്നും ലഭിക്കും.

പ്രയോഗിച്ച പ്ലാൻ `X-OmniRoute-Compression: <mode>; source=<source>` പ്രതികരണ ഹെഡറിൽ തിരികെ നൽകുന്നു; ഇവിടെ `<source>` എന്നത് `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, അല്ലെങ്കിൽ `off` എന്നിവയിൽ ഒന്നായിരിക്കും.

### API

```bash
# കംപ്രഷൻ ക്രമീകരണങ്ങൾ നേടുക
curl http://localhost:20128/api/settings/compression

# കംപ്രഷൻ ക്രമീകരണങ്ങൾ അപ്ഡേറ്റ് ചെയ്യുക
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# ഒരു നിർദ്ദിഷ്ട RTK/stacked പേലോഡ് പ്രിവ്യൂ ചെയ്യുക
curl -X POST http://localhost:20128/api/compression/preview \
  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# RTK ഫിൽട്ടർ പാക്കുകൾ പട്ടികപ്പെടുത്തുക
curl http://localhost:20128/api/context/rtk/filters

# ഐച്ഛിക കമാൻഡ് മെറ്റാഡാറ്റയോടെ RTK നേരിട്ട് പരിശോധിക്കുക
curl -X POST http://localhost:20128/api/context/rtk/test \
  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

## അംഗീകാരങ്ങൾ

Standard മോഡ് കംപ്രഷൻ നിയമങ്ങൾ **[JuliusBrussee](https://github.com/JuliusBrussee)**-യുടെ **[Caveman](https://github.com/JuliusBrussee/caveman)** (⭐ 51K+)-ൽ നിന്ന് പ്രചോദനം ഉൾക്കൊണ്ടവയാണ് — വൈറലായ "കുറച്ച് ടോക്കണുകൾകൊണ്ട് കാര്യം നടക്കുമ്പോൾ എന്തിന് കൂടുതൽ ടോക്കണുകൾ ഉപയോഗിക്കണം" എന്ന പ്രോജക്റ്റ്. `~75%` കുറവ് ഔട്ട്പുട്ട് ടോക്കണുകളും, ബെഞ്ച്മാർക്കുകളിൽ ശരാശരി `65%` ഔട്ട്പുട്ട് ലാഭവും, `22-87%` ഔട്ട്പുട്ട് പരിധിയും, `~46%` ഇൻപുട്ട്-കംപ്രഷൻ ടൂളും Caveman റിപ്പോർട്ട് ചെയ്യുന്നു.

RTK മോഡ് **[RTK AI](https://github.com/rtk-ai)**-യുടെ **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)**-ൽ നിന്ന് പ്രചോദനം ഉൾക്കൊണ്ടതാണ് — ടെർമിനൽ, ബിൽഡ്, ടെസ്റ്റ്, git, ടൂൾ-ഔട്ട്പുട്ട് ഫിൽട്ടറിംഗ് എന്നിവയ്ക്കായുള്ള ഉയർന്ന പ്രകടനമുള്ള കമാൻഡ്-ഔട്ട്പുട്ട് കംപ്രഷൻ പ്രോജക്റ്റ്. RTK `60-90%` ലാഭം റിപ്പോർട്ട് ചെയ്യുന്നു; അതിന്റെ README സാമ്പിൾ സെഷനിൽ `~80%` ലാഭിച്ചതായി കാണിക്കുന്നു.

## വിപുലമായ കംപ്രഷൻ സിസ്റ്റങ്ങൾ

മുകളിൽ വിവരിച്ച 7 മോഡുകൾക്ക് പുറമെ (സോഴ്സ് `codex-responses`, `omniglyph`
മോഡുകളും സ്വീകരിക്കുന്നു; ഈ ഗൈഡിൽ അവ ഉൾപ്പെടുത്തിയിട്ടില്ല), ആ മോഡുകൾക്കുള്ളിലോ അവയ്ക്കൊപ്പമോ
പ്രവർത്തിക്കുന്ന ഫീച്ചറുകളാണ് താഴെയുള്ള വിഭാഗങ്ങളിൽ വിശദീകരിക്കുന്നത്: Tool Result Compression, Progressive Aging
എന്നിവ അഗ്രസീവ് എഞ്ചിന്റെ 1, 2 ഘട്ടങ്ങളാണ് (Aggressive മോഡും സ്റ്റാക്ക്ഡ് പൈപ്പ്ലൈനിലെ `aggressive` ഘട്ടവും);
Stacked മോഡ് എങ്ങനെ പ്രവർത്തിക്കുന്നു എന്നതാണ് Stacked Pipeline; കംപ്രഷൻ ഓണായിരിക്കുമ്പോൾ
കാഷിംഗ് പ്രൊവൈഡറുകൾക്കായി Cache-Aware Compression, `aggressive`, `ultra` എന്നിവയെ `standard`-ലേക്ക്
താഴ്ത്തുന്നു; കൂടാതെ Caveman Output Mode, Output Styles എന്നിവ ഡിഫോൾട്ടായി ഓഫായിരിക്കുന്ന, ഓപ്റ്റ്-ഇൻ സിസ്റ്റം-പ്രോംപ്റ്റ് നിർദ്ദേശങ്ങളാണ്;
അവ റിക്വസ്റ്റ് കംപ്രസ് ചെയ്യുന്നതിനുപകരം മോഡലിന്റെ ഔട്ട്പുട്ടിന് രൂപം നൽകുന്നു.

### കാഷ്-അവബോധമുള്ള കംപ്രഷൻ

ചില പ്രൊവൈഡറുകൾ (പ്രോംപ്റ്റ് കാഷിംഗ് ഉള്ള Anthropic പോലുള്ളവ) **പ്രോംപ്റ്റ് കാഷിംഗ്**
പിന്തുണയ്ക്കുന്നു; ചെലവും ലേറ്റൻസിയും കുറയ്ക്കാൻ പ്രോംപ്റ്റിന്റെ ഭാഗങ്ങൾ കാഷ് ചെയ്യാൻ
ഇത് അവരെ അനുവദിക്കുന്നു. കാഷിംഗ് പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ, അഗ്രസീവ് കംപ്രഷൻ
കാഷ് ചെയ്ത ടോക്കണുകളെ മാറ്റി കാഷ് അസാധുവാക്കുന്നതിനാൽ യഥാർത്ഥത്തിൽ പ്രകടനത്തെ **ദോഷകരമായി ബാധിക്കാം**.

`cachingAware.ts` മൊഡ്യൂൾ **കാഷിംഗ് കോൺടെക്സ്റ്റ് കണ്ടെത്തുകയും**
അതിനനുസരിച്ച് **കംപ്രഷൻ സ്ട്രാറ്റജി ക്രമീകരിക്കുകയും** ചെയ്തുകൊണ്ട് ഇത് പരിഹരിക്കുന്നു.

#### ഇത് പ്രവർത്തിക്കുന്ന വിധം

1. **കാഷിംഗ് കോൺടെക്സ്റ്റ് കണ്ടെത്തുക** — `cache_control` മാർക്കറുകൾക്കായി റിക്വസ്റ്റ് ബോഡി സ്കാൻ ചെയ്യുന്നു
2. **കാഷിംഗ് പ്രൊവൈഡറുകളെ തിരിച്ചറിയുക** — ലക്ഷ്യ പ്രൊവൈഡർ കാഷിംഗ് പിന്തുണയ്ക്കുന്നുണ്ടോയെന്ന് പരിശോധിക്കുന്നു
3. **സ്ട്രാറ്റജി ക്രമീകരിക്കുക** — കാഷിംഗ് പ്രൊവൈഡറുകൾക്കായി `aggressive`/`ultra` എന്നിവയെ `standard`-ലേക്ക് താഴ്ത്തുന്നു
4. **സിസ്റ്റം പ്രോംപ്റ്റ് ഒഴിവാക്കുക** — സിസ്റ്റം പ്രോംപ്റ്റുകൾ സാധാരണയായി കാഷ് ചെയ്യപ്പെടുന്നതിനാൽ അവ കംപ്രസ് ചെയ്യരുത്

സ്ട്രാറ്റജി ഹെൽപ്പർ ഒരു `deterministicOnly` ഫ്ലാഗും മടക്കി നൽകുന്നു; എന്നാൽ പ്ലാൻ ബിൽഡർ
സ്ട്രാറ്റജി മാത്രമാണ് ഉപയോഗിക്കുന്നത് — നിലവിൽ ഡൗൺസ്ട്രീമിൽ ഒന്നും ആ ഫ്ലാഗ് വായിക്കുന്നില്ല.

#### കോഡ് ഉദാഹരണം

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← കാഷ് മാർക്കർ
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### എപ്പോൾ ഉപയോഗിക്കണം

കാഷ്-അവബോധമുള്ള കംപ്രഷൻ **എല്ലായ്പ്പോഴും ഓണാണ്** — കോൺഫിഗറേഷൻ ആവശ്യമില്ല. കംപ്രഷൻ
ഓണായിരിക്കുകയും ലക്ഷ്യ പ്രൊവൈഡർ പ്രോംപ്റ്റ് കാഷിംഗ് പിന്തുണയ്ക്കുകയും ചെയ്യുമ്പോഴെല്ലാം (Anthropic, OpenAI,
തുടങ്ങിയവ) ഇത് പ്രവർത്തനമാരംഭിക്കുന്നു; വ്യക്തമായ `cache_control` മാർക്കറുകൾ ആവശ്യമില്ല — ഒരു കാഷിംഗ് പ്രൊവൈഡർ
മാത്രം മതി ഡൗൺഗ്രേഡ് ട്രിഗർ ചെയ്യാൻ; മാർക്കറുകൾ മാത്രം ഒരിക്കലും അത് ചെയ്യില്ല (മാർക്കർ ഡിറ്റക്ഷൻ കാഷ്
ടെലിമെട്രിക്കാണ് വിവരങ്ങൾ നൽകുന്നത്, സ്ട്രാറ്റജി തീരുമാനത്തിനല്ല).

### പ്രോഗ്രസീവ് ഏജിംഗ്

ദൈർഘ്യമേറിയ സംഭാഷണങ്ങളിൽ നിരവധി സന്ദേശ ടേണുകൾ അടിഞ്ഞുകൂടുന്നു; എന്നാൽ പഴയ ടേണുകളുടെ
പ്രസക്തി കുറയുന്നു. `progressiveAging.ts` മൊഡ്യൂൾ **ടേൺ ദൂരം അനുസരിച്ച് സന്ദേശങ്ങളുടെ വിശദാംശനില കുറയ്ക്കുന്നു**
(സംഭാഷണത്തിന്റെ അവസാനം മുതൽ ദൂരം അളക്കുന്നു). പുറത്തിറക്കിയിട്ടുള്ള ഡിഫോൾട്ടുകൾ പ്രകാരം
(`verbatim: 2, light: 2, moderate: 3`):

- **അവസാന 2 ടേണുകൾ (ദൂരം ≤ 2)**: അതേപടി നിലനിർത്തുന്നു
- **ദൂരം 3**: കേവ്മാൻ കംപ്രഷൻ (അനാവശ്യ പദങ്ങൾ നീക്കംചെയ്യൽ)
- **ദൂരം 4+**: അസിസ്റ്റന്റ് സന്ദേശങ്ങൾ സംഗ്രഹിക്കുന്നു; ഉപയോക്തൃ സന്ദേശങ്ങൾ അവയുടെ ആദ്യ
  വരിയിലേക്ക് ചുരുക്കുകയും പരമാവധി 120 പ്രതീകങ്ങളായി പരിമിതപ്പെടുത്തുകയും ചെയ്യുന്നു; മറ്റ് റോളുകൾ മാറ്റമില്ലാതെ നിലനിർത്തുന്നു. ദൂരം പരിഗണിക്കാതെ സിസ്റ്റം പ്രോംപ്റ്റുകൾ, ഇതിനകം കാലപ്പഴക്കം വരുത്തിയ
  സന്ദേശങ്ങൾ, ഏറ്റവും പുതിയ ഉപയോക്തൃ സന്ദേശം എന്നിവ എല്ലായ്പ്പോഴും അതേപടി നിലനിർത്തുന്നു.
  ഒന്നും പൂർണ്ണമായി ഒഴിവാക്കുന്നില്ല, കൂടാതെ നൽകിയിരിക്കുന്ന ഡിഫോൾട്ടുകളിൽ `light`
  ബാൻഡിലേക്ക് എത്താനാവില്ല (`light`, `verbatim`-ന് തുല്യമാണ്).

#### കോഡ് ഉദാഹരണം

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 ടേണുകൾ കൂടി ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // അവസാന 3 ടേണുകൾ: അതേപടി
  light: 8, // ദൂരം <= 8: ലഘു കംപ്രഷൻ
  moderate: 20, // ദൂരം <= 20: കേവ്മാൻ കംപ്രഷൻ
  fullSummary: 5, // ടൈപ്പിന് ആവശ്യമാണ്, ബാൻഡിങ് കോഡ് ഇത് വായിക്കുന്നില്ല
  // ദൂരം > 20: സംഗ്രഹിക്കുന്നു (അസിസ്റ്റന്റ്) / ആദ്യ വരി നിലനിർത്തുന്നു (ഉപയോക്താവ്)
});

// saved = ലാഭിച്ച ടോക്കണുകളുടെ എണ്ണം
```

#### എപ്പോൾ ഉപയോഗിക്കണം

`aggressive` മോഡിൽ പ്രോഗ്രസീവ് ഏജിങ് **എല്ലായ്പ്പോഴും പ്രവർത്തനക്ഷമമാണ്** — ഇത്
`compressAggressive()`-ന്റെ ഘട്ടം 2 ആണ്. Ultra മോഡ് ഇത് പ്രവർത്തിപ്പിക്കുന്നില്ല. ഇത്
പ്രത്യേകിച്ച് ഫലപ്രദമാകുന്ന സാഹചര്യങ്ങൾ:

- ദീർഘകാലം തുടരുന്ന കോഡിങ് സെഷനുകൾ
- നിരവധി ദിവസങ്ങൾ നീളുന്ന സംഭാഷണങ്ങൾ
- അനവധി ടൂൾ കോളുകളുള്ള ഏജന്റിക് വർക്ക്ഫ്ലോകൾ

### കേവ്മാൻ ഔട്ട്പുട്ട് മോഡ്

കേവ്മാൻ ഔട്ട്പുട്ട് മോഡ്, സംക്ഷിപ്തമായ ഔട്ട്പുട്ട് നൽകാൻ മോഡലിനോട് തന്നെ ആവശ്യപ്പെടുന്ന **സിസ്റ്റം പ്രോംപ്റ്റ് നിർദ്ദേശങ്ങൾ** ചേർക്കുന്നു — `lite` ലെവൽ പൂർണ്ണ വാക്യങ്ങൾ നിലനിർത്തുന്ന സംക്ഷിപ്ത ഉത്തരങ്ങൾ ആവശ്യപ്പെടുന്നു, `full`
"ബുദ്ധിമാനായ ഗുഹാമനുഷ്യനെപ്പോലെ സംക്ഷിപ്തമായി പ്രതികരിക്കാൻ" ആവശ്യപ്പെടുന്നു, `ultra` ടെലഗ്രാഫിക് ഔട്ട്പുട്ട് ആവശ്യപ്പെടുന്നു;
നിർദ്ദേശങ്ങൾ ആവശ്യപ്പെടുക മാത്രമേ ചെയ്യൂ, അവയ്ക്ക് അത് ഉറപ്പുനൽകാനാവില്ല. അഭ്യർത്ഥനകൾക്ക് ഇവ ലഭിക്കുന്നത്
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) വഴിയാണ്:
`open-sse/handlers/chatCore.ts` ആദ്യം ബാക്ക്-കംപാറ്റ് ഷിം ഉപയോഗിച്ച് തിരഞ്ഞെടുപ്പ് പരിഹരിക്കുന്നു
(`resolveOutputStyleSelection()` എന്നത്
`open-sse/services/compression/outputStyles/backCompat.ts`-ൽ), ഇത് `outputStyles`
ശൂന്യമായിരിക്കുമ്പോൾ, പ്രവർത്തനക്ഷമമാക്കിയ `cavemanOutputMode`-നെ
`cavemanOutputMode.intensity`-ലെ `terse-prose` ഔട്ട്പുട്ട് സ്റ്റൈലിലേക്ക് മാപ്പ് ചെയ്യുന്നു
(ചുവടെയുള്ള ബാക്ക്-കംപാറ്റ് കാണുക); ശൂന്യമല്ലാത്ത `outputStyles`
തിരഞ്ഞെടുപ്പ് അതേപടി ഉപയോഗിക്കുന്നു, തുടർന്ന് `cavemanOutputMode.enabled`, `intensity` എന്നിവയ്ക്ക്
പ്രഭാവമുണ്ടാകില്ല, എന്നാൽ അതിന്റെ `autoClarity` ടോഗിൾ തുടർന്നും ബാധകമാണ്. `outputMode.ts`-ൽ
നിർദ്ദേശ ടെക്സ്റ്റുകളും (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), ഉള്ളടക്ക ബൈപാസും,
ഇൻജക്ഷൻ ഉപയോഗിക്കുന്ന പ്ലേസ്മെന്റ് ഹെൽപ്പറും അടങ്ങിയിരിക്കുന്നു; അതിന്റെ സ്വന്തം `applyCavemanOutputMode()` ഇൻജക്ടറിന്
പ്രൊഡക്ഷൻ കോളർ ഇല്ല.

#### ഇത് എങ്ങനെ പ്രവർത്തിക്കുന്നു

ഈ മോഡ് ഇൻപുട്ട് കംപ്രസ് ചെയ്യുന്നില്ല. ഇത് സിസ്റ്റം പ്രോംപ്റ്റിലേക്ക് ഒരു നിർദ്ദേശ ബ്ലോക്ക് ചേർക്കുന്നു
(ചുവടെയുള്ള ഇൻജക്ഷൻ എങ്ങനെ പ്രവർത്തിക്കുന്നു എന്ന ഭാഗം കാണുക), തുടർന്ന് അഭ്യർത്ഥനയ്ക്കായി തിരഞ്ഞെടുത്ത ഏതൊരു ഇൻപുട്ട് കംപ്രഷൻ മോഡും
ഇപ്പോൾ ആ ബ്ലോക്ക് ഉൾക്കൊള്ളുന്ന ബോഡിയിൽ പ്രവർത്തിക്കുന്നു. എല്ലാ ലെവലുകളും അവസാനിക്കുന്ന പൊതുവായ
പരിധികളുടെ ക്ലോസിന് മുമ്പ്, ഇംഗ്ലീഷിലെ `full` ലെവലിൽ ഇങ്ങനെ പറയുന്നു:

> "ബുദ്ധിമാനായ ഗുഹാമനുഷ്യനെപ്പോലെ സംക്ഷിപ്തമായി പ്രതികരിക്കുക. ആർട്ടിക്കിളുകൾ (a/an/the), അനാവശ്യ പദങ്ങൾ (just/really/basically/actually/simply), ഔപചാരിക സൗഹൃദപ്രകടനങ്ങൾ, സന്ദിഗ്ധഭാഷ എന്നിവ ഒഴിവാക്കുക. വാക്യശകലങ്ങൾ അനുവദനീയമാണ്. ഹ്രസ്വ പര്യായങ്ങൾ ഉപയോഗിക്കുക (extensive എന്നതിന് പകരം big, implement എന്നതിന് പകരം fix). എല്ലാ സാങ്കേതിക ഉള്ളടക്കവും, കോഡും, പിശകുകളും, URL-കളും, ഐഡന്റിഫയറുകളും കൃത്യമായി നിലനിർത്തുക."

ഇത് പ്രത്യേകിച്ച് നന്നായി പ്രവർത്തിക്കുന്ന സാഹചര്യങ്ങൾ:

- കോഡ് ജനറേഷൻ (കൂടുതൽ സംക്ഷിപ്തമായ ഔട്ട്പുട്ട് = കുറച്ച് ടോക്കണുകൾ)
- ദ്രുത ചോദ്യോത്തരങ്ങൾ (വിശദമായ വിശദീകരണങ്ങൾ ആവശ്യമില്ല)
- ബാച്ച് പ്രോസസ്സിങ് (ത്രൂപ്പുട്ട് പരമാവധിയാക്കുക)

#### എപ്പോൾ ഉപയോഗിക്കണം

കേവ്മാൻ ഔട്ട്പുട്ട് മോഡ് **ഓപ്റ്റ്-ഇൻ** ആണ്. കംപ്രഷൻ ഓണായിരിക്കുമ്പോൾ (`enabled: true`, Compression Settings പേജിലെ മാസ്റ്റർ ടോഗിൾ
ഓണായിരിക്കണം), `cavemanOutputMode.enabled` ഉപയോഗിച്ച് ഇത് ഓണാക്കുക; `intensity`
`lite`, `full`, അല്ലെങ്കിൽ `ultra` തിരഞ്ഞെടുക്കുന്നു:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

ഒരു കംപ്രഷൻ കോംബോയുടെ **ഔട്ട്പുട്ട് മോഡ്** ടോഗിൾ (`outputMode`, ലെവൽ `outputModeIntensity`-ൽ)
ആ കോംബോ ബാധകമായ അഭ്യർത്ഥനകൾക്കായി അതേ സ്വിച്ച് സജ്ജമാക്കുന്നു, കൂടാതെ
`omniroute_set_compression_engine` MCP ടൂൾ അതിന്റെ ബൂളിയൻ `outputMode`
ആർഗ്യുമെന്റ് വഴി അത് എഴുതുന്നു. ശൂന്യമല്ലാത്ത `outputStyles` തിരഞ്ഞെടുപ്പിന് ഈ സ്വിച്ചിനേക്കാൾ മുൻഗണനയുണ്ട്. ഡാഷ്ബോർഡിൽ,
**സംക്ഷിപ്ത ഗദ്യം** ഔട്ട്പുട്ട് സ്റ്റൈൽ പ്രവർത്തനക്ഷമമാക്കുന്നത് അതേ ബ്ലോക്ക് ഇൻജക്റ്റ് ചെയ്യുന്നു (ചുവടെയുള്ള ഔട്ട്പുട്ട് സ്റ്റൈലുകൾ കാണുക).

### ഔട്ട്പുട്ട് സ്റ്റൈലുകൾ (കാറ്റലോഗ്)

മുകളിലുള്ള കേവ്മാൻ ഔട്ട്പുട്ട് മോഡ് **ലെഗസി സിംഗിൾ-സ്റ്റൈൽ പാത** ആണ്. Phase 4 അതിനെ
സംയോജിപ്പിക്കാവുന്ന ഔട്ട്പുട്ട് സ്റ്റൈലുകളുടെ ഒരു കാറ്റലോഗായി സാമാന്യവൽക്കരിച്ചു: `OUTPUT_STYLE_CATALOG` എന്നത്

#### ഉൾപ്പെടുത്തൽ പ്രവർത്തിക്കുന്ന വിധം

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) തിരഞ്ഞെടുപ്പിനെ
catalog-നോട് പൊരുത്തപ്പെടുത്തി നിർണ്ണയിക്കുന്നു (അജ്ഞാത ids-ഉം ലൊക്കേലുമായി പൊരുത്തപ്പെടാത്ത ശൈലികളും
ഒഴിവാക്കപ്പെടും, ഒരിക്കലും പിശകാകില്ല; ഒരു ശൈലിയിലേക്കും നിർണ്ണയിക്കപ്പെടാത്ത തിരഞ്ഞെടുപ്പ് body
മാറ്റമില്ലാതെ വിടുകയും `no_styles` ആയി ഒഴിവാക്കുകയും ചെയ്യും), തിരഞ്ഞെടുത്ത നിർദ്ദേശങ്ങൾ catalog
ക്രമത്തിൽ സംയോജിപ്പിക്കുന്നു,
boundaries clause **ഒരിക്കൽ** ചേർക്കുന്നു (`less-code` അല്ലെങ്കിൽ `ponytail` തിരഞ്ഞെടുത്തിട്ടുണ്ടെങ്കിൽ
safety clause, `SAFETY_BOUNDARIES` അല്ലെങ്കിൽ അതിന്റെ പരിഭാഷയും ചേർക്കുന്നു), കൂടാതെ ഒരൊറ്റ
idempotency marker (`[OmniRoute Output Styles]`) ഉപയോഗിച്ച് block ആരംഭിക്കുന്നു; അതിനാൽ വീണ്ടും
പ്രയോഗിക്കുന്നത് ഒന്നും ചെയ്യില്ല. നിർണ്ണയിച്ച ഭാഷയ്ക്ക് (താഴെയുള്ള ഭാഷാ തിരഞ്ഞെടുപ്പ് കാണുക)
പരിഭാഷയുണ്ടെങ്കിൽ, English-ന് പകരം പ്രാദേശികവത്കരിച്ച നിർദ്ദേശം ഉൾപ്പെടുത്തുന്നു.

ശൂന്യമല്ലാത്ത `messages` array ഉള്ള body-യിൽ, content bypass-ന് മുമ്പ് idempotency പരിശോധന
നടക്കുന്നു: top-level `system` field-ലോ (string അല്ലെങ്കിൽ content-block array) string content ഉള്ള
system message-ലോ `[OmniRoute Output Styles]` marker ഇതിനകം ഉണ്ടെങ്കിൽ, body `already_applied`
ആയി മാറ്റമില്ലാതെ വിടുന്നു; keyword പരിശോധന നടത്തില്ല.
അല്ലെങ്കിൽ content bypass (`open-sse/services/compression/outputMode.ts`-ലെ
`shouldBypassCavemanOutputMode()`) അവസാനത്തെ മൂന്ന് messages-ന്റെ text, അവയുടെ role ഏതായാലും,
പരിശോധിക്കുന്നു. ആ text അതിന്റെ security, irreversible-action അല്ലെങ്കിൽ clarification
keywords-നോട് പൊരുത്തപ്പെടുമ്പോഴോ, ക്രമം പ്രസക്തമായ ഒരു sequence—`first`, `then`, `after that`,
`before`, `rollback` അല്ലെങ്കിൽ `backup`, തുടർന്ന് 240 characters-നുള്ളിൽ `delete`, `drop`,
`migrate`, `deploy` അല്ലെങ്കിൽ `release`—ഉണ്ടാകുമ്പോഴോ, മുഴുവൻ turn-ലെയും styles ഒഴിവാക്കുന്നു.
**Auto-Clarity Bypass** toggle
(`cavemanOutputMode.autoClarity`, സ്ഥിരസ്ഥിതിയിൽ on) on ആയിരിക്കുമ്പോഴാണ് bypass പ്രവർത്തിക്കുന്നത്;

3. **`shellOutput`**: ടെക്സ്റ്റിൽ എവിടെയെങ്കിലും ഒരു ANSI CSI സീക്വൻസ് (`ESC[`-ന് ശേഷം അക്കങ്ങളോ
   സെമിക്കോളണുകളോ, തുടർന്ന് ഒരു അക്ഷരമോ വരുന്നത്, കളർ കോഡുകളിലെന്നപോലെ) അല്ലെങ്കിൽ ഒരു `$`-ന്
   ശേഷം വൈറ്റ്സ്പേസ് അടങ്ങിയ ഔട്ട്പുട്ടിൽ നിന്ന് ആ സീക്വൻസുകൾ നീക്കംചെയ്യുകയും (മറ്റ് എസ്കേപ്പുകൾ,
   ഉദാഹരണത്തിന് `ESC[?25l` അല്ലെങ്കിൽ ഒരു OSC വിൻഡോ-ടൈറ്റിൽ സീക്വൻസ്, നിലനിർത്തുന്നു) തുടർച്ചയായി
   ആവർത്തിക്കുന്ന വരികൾ ഒറ്റ വരിയായി ചുരുക്കിക്കൊണ്ട് അവസാനത്തെ 50 വരികൾ നിലനിർത്തുകയും ചെയ്യുന്നു.
   ഈ പരിശോധന `json`, `errorMessage` എന്നിവയ്ക്കുമുമ്പ് നടക്കുന്നതിനാൽ, അത്തരമൊരു `$` അടങ്ങിയ JSON
   അല്ലെങ്കിൽ പിശക് ഔട്ട്പുട്ട് `shellOutput` ഓണായിരിക്കുമ്പോൾ അവയിലേക്ക് ഒരിക്കലും എത്തില്ല.
4. **`json`**: 2,000-ത്തിലധികം പ്രതീകങ്ങളുള്ളതും (ഓപ്ഷണൽ വൈറ്റ്സ്പേസിന് ശേഷം) `{` അല്ലെങ്കിൽ `[`
   കൊണ്ട് ആരംഭിക്കുന്നതും വിജയകരമായി പാർസ് ചെയ്യപ്പെടുന്നതുമായ JSON പേലോഡ് സംഗ്രഹിക്കപ്പെടുന്നു:
   7-ൽ കൂടുതൽ ഇനങ്ങളുള്ള ഒരു അറേ അതിന്റെ ആദ്യത്തെ 5, അവസാനത്തെ 2 ഇനങ്ങളും മൊത്തം എണ്ണവും
   നിലനിർത്തുന്നു; ഒരു ഒബ്ജക്റ്റ് അതിന്റെ ആദ്യത്തെ 20 കീകൾ നിലനിർത്തുന്നു, കൂടാതെ നെസ്റ്റഡ് ഒബ്ജക്റ്റ്
   അല്ലെങ്കിൽ അറേ മൂല്യങ്ങൾ ഓരോന്നും ഒരു `{…N keys}` പ്ലേസ്ഹോൾഡർ ഉപയോഗിച്ച് മാറ്റിസ്ഥാപിക്കുന്നു
   (ഒരു അറേയ്ക്ക്, N അതിന്റെ നീളമാണ്), ആദ്യത്തെ 20-ന് ശേഷം ഒഴിവാക്കിയ കീകളുടെ എണ്ണം സൂചിപ്പിക്കുന്ന
   ഒരു `_remaining_<N>_keys` മാർക്കറും ചേർക്കുന്നു. സ്കെയ്ലർ മൂല്യങ്ങൾ പൂർണ്ണമായി പകർത്തപ്പെടുന്നതിനാൽ,
   നെസ്റ്റഡ് മൂല്യങ്ങളില്ലാത്ത 20 കീകളോ അതിൽ കുറവോ ഉള്ള ഒരു ഒബ്ജക്റ്റ് വീണ്ടും ഇൻഡെന്റ് ചെയ്യുക മാത്രമേ
   ചെയ്യൂ — മിനിഫൈ ചെയ്ത ഒന്നിന് കൂടുതൽ പ്രതീകങ്ങൾ ലഭിക്കുകയും അത് മാറ്റമില്ലാതെ തുടരുകയും ചെയ്യും.
5. **`errorMessage`**: എവിടെയെങ്കിലും, അക്ഷരങ്ങളുടെ കേസ് പരിഗണിക്കാതെ, `error:`,
   `error ` (`no error found` എന്നതിലെപ്പോലെ, വാക്കിന് ശേഷം ഒരു സ്പേസ്), `[error]`,
   `exception:`, `exception `, `[exception]` അല്ലെങ്കിൽ `traceback` അടങ്ങിയ ഔട്ട്പുട്ട് അതിന്റെ
   ആദ്യ വരിയും അടുത്ത 10 വരികളും അവസാനത്തെ 3 വരികളും നിലനിർത്തുന്നു; അവയ്ക്കിടയിലെ വരികൾക്ക് പകരം
   ഒരു `… [N frames elided] …` മാർക്കർ ഉപയോഗിക്കുന്നു. ആദ്യ വരിക്ക് ശേഷം 13-ൽ കൂടുതൽ വരികൾ
   ഉള്ളപ്പോൾ മാത്രമേ മാർക്കർ പ്രത്യക്ഷപ്പെടൂ; അതിനാൽ 14 വരികളോ അതിൽ കുറവോ ഉള്ള പിശക് ഔട്ട്പുട്ട്
   ചുരുക്കപ്പെടില്ല (12 അല്ലെങ്കിൽ 13 വരികളിൽ അവസാനത്തെ 3 വരികൾ ഇതിനകം നിലനിർത്തിയ വരികളെ
   ആവർത്തിക്കുന്നു).

ഒരു സ്ട്രാറ്റജി പൊരുത്തപ്പെട്ടാൽ, അത് ഒന്നും ലാഭിക്കാത്തതാണെങ്കിലും, പിന്നീടുള്ള സ്ട്രാറ്റജികൾ
പരീക്ഷിക്കില്ല. പൊരുത്തപ്പെടുന്ന സ്ട്രാറ്റജി കണക്കാക്കിയ ടോക്കണുകളൊന്നും ലാഭിക്കാത്തപ്പോൾ (നീളം ÷ 4,
മുകളിലേക്കു റൗണ്ട് ചെയ്തത്) — ഉദാഹരണത്തിന്, 25 വരികളോ അതിൽ കുറവോ ഉള്ള കോഡ് പോലെയുള്ള ഒരു
ഫയൽ, അല്ലെങ്കിൽ 2,000-ത്തിലധികം പ്രതീകങ്ങളുള്ളതും 7 ഇനങ്ങളോ അതിൽ കുറവോ ഉള്ളതുമായ ഒരു JSON
അറേ — അഗ്രസീവ് എൻജിൻ യഥാർത്ഥ ടൂൾ ഫലം നിലനിർത്തുന്നു: `saved` 0 അല്ലെങ്കിൽ അതിൽ കുറവായിരിക്കുമ്പോൾ
രണ്ട് കോളറുകളും (`compressAggressive()`-ഉം `compressAnthropicToolResultBlock()`-ഉം) യഥാർത്ഥത്
നിലനിർത്തുന്നു, അതേസമയം `compressToolResult()` തന്നെ ഇപ്പോഴും ആ സ്ട്രാറ്റജിയുടെ ഔട്ട്പുട്ട്
തിരികെ നൽകുന്നു. ടൂൾ-റിസൾട്ട് ഘട്ടം അന്തിമ തീരുമാനമല്ല: എൻജിന്റെ ഫാൾബാക്ക് സമ്മറൈസറിന് ഇപ്പോഴും
8,192 പ്രതീകങ്ങളിൽ കൂടുതൽ നീളമുള്ള ഒരു `tool` അല്ലെങ്കിൽ `function` സന്ദേശം
(`maxTokensPerMessage`, 2,048, ഗുണം 4) ചുരുക്കാനാകും.

#### എപ്പോൾ ഉപയോഗിക്കണം

ടൂൾ ഫല കംപ്രഷൻ അഗ്രസീവ് എൻജിന്റെ ഘട്ടം 1 ആണ് (`open-sse/services/compression/aggressive.ts`-ലെ
`compressAggressive()`), അതിനാൽ ഇത് Aggressive മോഡിലും സ്റ്റാക്ക്ഡ് പൈപ്പ്ലൈനിലെ ഒരു
`aggressive` ഘട്ടത്തിലും പ്രവർത്തിക്കുന്നു. ഇത് OpenAI-രൂപത്തിലുള്ള `tool`, `function`
സന്ദേശങ്ങളെയും Anthropic `tool_result` ബ്ലോക്കുകൾക്കുള്ളിലെ ടെക്സ്റ്റിനെയും കംപ്രസ് ചെയ്യുന്നു.
ഓരോ സ്ട്രാറ്റജിക്കും `aggressive.toolStrategies`-ന് കീഴിൽ അതിന്റേതായ സ്വിച്ച് ഉണ്ട്; എല്ലാം
ഡിഫോൾട്ടായി ഓണാണ്. ഡാഷ്ബോർഡിൽ, കംപ്രഷൻ ഓണായിരിക്കുകയും ഡിഫോൾട്ട് മോഡ് Aggressive
ആയിരിക്കുകയും ചെയ്യുമ്പോൾ Caveman പേജിന്റെ **Advanced** കാഴ്ചയിലാണ് സ്വിച്ചുകൾ.

### സ്റ്റാക്ക്ഡ് പൈപ്പ്ലൈൻ

സ്റ്റാക്ക്ഡ് മോഡ് **ഒന്നിലധികം എൻജിനുകൾ ക്രമത്തിൽ** പ്രവർത്തിപ്പിക്കുന്നു — സാധാരണയായി ആദ്യം RTK
(ടൂൾ ഔട്ട്പുട്ടിൽ 60-90% ലാഭം), തുടർന്ന് ശേഷിക്കുന്ന ടെക്സ്റ്റിൽ Caveman (~46% ഇൻപുട്ട്
ലാഭം). സംയോജിപ്പിക്കുമ്പോൾ, അത് **78-95% യോഗ്യമായ പരിധിയാണ്** (മുകളിലെ Upstream Savings Math
കാണുക): `1 - (1 - 0.60..0.90) × (1 - 0.46)`-ന്റെ ശരാശരി ≈89%.

#### ഇത് എങ്ങനെ പ്രവർത്തിക്കുന്നു

```
ഇൻപുട്ട് (1000 ടോക്കണുകൾ)
  → RTK (കമാൻഡ്-അവബോധമുള്ള ഫിൽട്ടർ) → 200 ടോക്കണുകൾ
    → Caveman (അനാവശ്യ ഉള്ളടക്കം നീക്കംചെയ്യൽ) → 108 ടോക്കണുകൾ
  → ഔട്ട്പുട്ട് (108 ടോക്കണുകൾ, ~89% ലാഭം)
```

#### എപ്പോൾ ഉപയോഗിക്കണം

ഇവയ്ക്കായി സ്റ്റാക്ക്ഡ് മോഡ് ഉപയോഗിക്കുക:

- ടൂൾ-കേന്ദ്രീകൃത വർക്ക്ഫ്ലോകൾ (ഏജന്റിക് കോഡിംഗ്, ഗവേഷണം)
- ചെലവ് പരിഗണിക്കുന്ന ബാച്ച് പ്രോസസ്സിംഗ്
- പരമാവധി ടോക്കൺ ലാഭം ആവശ്യമായപ്പോൾ

സ്റ്റാക്ക്ഡ് പൈപ്പ്ലൈനുകൾ ഗ്ലോബൽ `stackedPipeline` കംപ്രഷൻ ക്രമീകരണത്തിലൂടെയോ, അല്ലെങ്കിൽ ഒരു
റൂട്ടിംഗ് കോംബോയ്ക്ക് നൽകിയിട്ടുള്ള പേരുള്ള കംപ്രഷൻ കോംബോയിലൂടെയോ കോൺഫിഗർ ചെയ്യുന്നു (മുകളിലെ
Per-Combo Override കാണുക) — ഒരു ഓട്ടോ-കോംബോ `modePack` വഴിയല്ല (ആ ഫീൽഡ് ഓട്ടോ-കോംബോ മോഡൽ
തിരഞ്ഞെടുപ്പിന്റെ വെയ്റ്റുകൾ പുനഃക്രമീകരിക്കുക മാത്രമാണ് ചെയ്യുന്നത്, കൂടാതെ `stacked` സാധുവായ
ഒരു പാക്ക് പേരല്ല).

## കോംപ്രഷൻ കോംബോ ഓവർറൈഡുകൾ

വ്യത്യസ്ത ഉപയോഗ സാഹചര്യങ്ങൾക്കായി പ്രവർത്തനം സൂക്ഷ്മമായി ക്രമീകരിക്കുന്നതിന് ഗ്ലോബൽ കോംപ്രഷൻ മോഡ് **ഓരോ കോംബോയ്ക്കും** ഓവർറൈഡ് ചെയ്യാം:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

ഇത് ഇനിപ്പറയുന്നവയ്ക്ക് ഉപകാരപ്രദമാണ്:

- **കോഡിംഗ് കോംബോകൾ**: ദൈർഘ്യമേറിയ സെഷനുകൾക്കായി `aggressive` മോഡ് ഉപയോഗിക്കുക
- **ദ്രുത ചോദ്യോത്തര കോംബോകൾ**: വേഗത്തിലുള്ള പ്രതികരണങ്ങൾക്കായി `lite` മോഡ് ഉപയോഗിക്കുക
- **ടൂൾ-അധിഷ്ഠിത കോംബോകൾ**: പരമാവധി ലാഭത്തിനായി `stacked` മോഡ് ഉപയോഗിക്കുക
- **പ്രൊഡക്ഷൻ കോംബോകൾ**: കാഷിംഗ് പ്രൊവൈഡറുകൾക്കായി ഓവർറൈഡ് ഓഫാക്കി വെക്കുക — എല്ലായ്പ്പോഴും സജീവമായ
  കാഷ്-അവെയർ ക്രമീകരണം `aggressive`/`ultra` മോഡുകളെ സ്വയമേവ `standard` ആയി ഡൗൺഗ്രേഡ് ചെയ്യുന്നു
  (തിരഞ്ഞെടുക്കാവുന്ന `cache-aware` മോഡ് നിലവിലില്ല)
