## അവലോകനം

എല്ലാ OmniRoute മാനേജ്മെന്റ് API റൂട്ടുകളും മൂന്ന് സംരക്ഷണ
തലങ്ങളിൽ ഒന്നായി വർഗ്ഗീകരിച്ചിരിക്കുന്നു. ഈ വർഗ്ഗീകരണം സ്ഥിരമാണ്,
`src/server/authz/routeGuard.ts`-ൽ നിർവചിച്ചിരിക്കുന്നു, കൂടാതെ മറ്റേതെങ്കിലും ഓത്ത് ശാഖ
പ്രവർത്തിക്കുന്നതിന് മുമ്പ് വിലയിരുത്തപ്പെടുന്നു.

## തലങ്ങൾ

### തലം 1 — LOCAL_ONLY

**നടപ്പിലാക്കുന്നത്:** `isLocalOnlyPath(path)` → ലൂപ്പ്ബാക്ക് ഹോസ്റ്റ് പരിശോധന
**ബൈപാസ്:** ഡിഫോൾട്ടായി ഒന്നുമില്ല. അഭ്യർത്ഥനയിൽ `manage` സ്കോപ്പുള്ള സാധുവായ
API കീ ഉൾപ്പെട്ടിരിക്കുമ്പോൾ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലെ പാതകൾക്ക്
മാത്രം പരിമിതമായ ഇളവുണ്ട് ([മാനേജ്-സ്കോപ്പ് ഇളവ്](#manage-scope-carve-out) കാണുക).

ഈ റൂട്ടുകൾ ചൈൽഡ് പ്രോസസ്സുകൾ ആരംഭിക്കുകയോ റൺടൈം കോഡ് എക്സിക്യൂട്ട് ചെയ്യുകയോ ചെയ്യുന്നു.
ഇവയെ ലൂപ്പ്ബാക്ക് അല്ലാത്ത ട്രാഫിക്കിന് ലഭ്യമാക്കുന്നത് സാധുവായ JWT നേടിയ ഒരു ആക്രമണകാരിക്ക്
(ഉദാ., Cloudflared/Ngrok ടണലിലൂടെ) പ്രോസസുകൾ ആരംഭിക്കാൻ വഴിയൊരുക്കും — ഇത് അറിയപ്പെടുന്ന
ഒരു CVE വിഭാഗമാണ്
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj എന്താണ് (ആക്രമണ വിഭാഗം):** ഒരു മാനേജ്മെന്റ്/ഏജന്റ് സെർവർ
ഒരു സബ്പ്രോസസ് (`npm install`, `node`, ഒരു ബ്രൗസർ,
ഒരു പ്രോക്സി, `git`, `tar`, …) ആരംഭിക്കുന്ന എൻഡ്പോയിന്റ് ലഭ്യമാക്കുന്നു. ആ എൻഡ്പോയിന്റ് ഹോസ്റ്റിന് പുറത്തുനിന്ന്
ആക്സസ് ചെയ്യാനാകുന്നുവെങ്കിൽ — ഓപ്പറേറ്റർ OmniRoute-നെ ഒരു nginx/Cloudflare/Tailscale ടണലിന് പിന്നിൽ
വെക്കുകയും ഒരു JWT ചോർന്നുപോകുകയും ചെയ്തതിനാലോ, അല്ലെങ്കിൽ ഓത്ത് തെറ്റായി കോൺഫിഗർ ചെയ്തതിനാലോ —
ആക്രമണകാരി "ഒരു API വിളിക്കുക" എന്നതിനെ "ഹോസ്റ്റിൽ ഒരു കമാൻഡ് പ്രവർത്തിപ്പിക്കുക"
(റിമോട്ട് കോഡ് എക്സിക്യൂഷൻ) എന്നാക്കി മാറ്റുന്നു. സ്പോൺ ചെയ്യാൻ കഴിയുന്ന എല്ലാ റൂട്ടുകളിലും
**യാതൊരു നിബന്ധനയുമില്ലാതെ, ഏതൊരു ഓത്ത് പരിശോധനയ്ക്കും മുമ്പ് ലൂപ്പ്ബാക്ക് ഹോസ്റ്റ് പരിശോധന**
നടപ്പിലാക്കിക്കൊണ്ട് OmniRoute ഇത് തടയുന്നു: ഒരു ടണലിലൂടെ ചോർന്ന ടോക്കണിനും സ്പോൺ പ്രവർത്തനത്തിലേക്ക്
എത്തിച്ചേരാനാകില്ല.

**പൂർണ്ണമായ LOCAL_ONLY ഗണം.** ആധികാരിക ഉറവിടം
`src/server/authz/routeGuard.ts`-ലെ
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ആണ്; താഴെയുള്ള പട്ടിക നിലവിലെ അവസ്ഥയെ
പ്രതിഫലിപ്പിക്കുന്നു. സ്പോൺ ചെയ്യാൻ കഴിയുന്ന പ്രിഫിക്സുകൾക്ക് കീഴിലുള്ള ഓരോ `route.ts`-ഉം
`check-route-guard-membership` ഗേറ്റ് പട്ടികപ്പെടുത്തുകയും അവയിൽ ഏതെങ്കിലും ലോക്കൽ-ഒൺലി ആയി
വർഗ്ഗീകരിച്ചിട്ടില്ലെങ്കിൽ CI പരാജയപ്പെടുത്തുകയും ചെയ്യുന്നു.

#### മാനേജ്-സ്കോപ്പ് ഒഴിവാക്കൽ

അഭ്യർത്ഥനയിൽ `manage` സ്കോപ്പ് (അല്ലെങ്കിൽ `admin`) ഉൾപ്പെടുന്ന മെറ്റാഡാറ്റയോടുകൂടിയ
`Authorization: Bearer <api-key>` ഉണ്ടെങ്കിൽ മാത്രം, LOCAL_ONLY പാതകളുടെ ഒരു ഉപഗണം
നോൺ-ലൂപ്പ്ബാക്കിൽ നിന്നും ആക്സസ് ചെയ്യാൻ കഴിയും. ഈ ഒഴിവാക്കൽ ഓരോ പാതയ്ക്കുമായി
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` വഴി വ്യക്തമായി നിയന്ത്രിക്കപ്പെടുന്നതിനാൽ,
ഏതൊരു പുതിയ LOCAL_ONLY പാതയ്ക്കുമുള്ള ഡിഫോൾട്ട് കർശനമായ ലൂപ്പ്ബാക്കായി തുടരും.
ഓതന്റിക്കേറ്റ് ചെയ്യാത്ത അഭ്യർത്ഥനകളും മാനേജ് സ്കോപ്പ് ഇല്ലാത്ത കീകളോടുകൂടിയ
അഭ്യർത്ഥനകളും ഇപ്പോഴും `403 LOCAL_ONLY` ഉപയോഗിച്ച് നിരസിക്കപ്പെടും.

നിലവിൽ ബൈപാസ് ചെയ്യാവുന്ന ഏക പ്രിഫിക്സ് `/api/mcp/` ആണ്. `/api/cli-tools/runtime/`-ഉം
`/api/services/`-ഉം മനഃപൂർവം ഒഴിവാക്കിയിരിക്കുന്നു, കാരണം അവയ്ക്ക് ഇഷ്ടാനുസൃത
സബ്പ്രോസസ്സുകൾ (`npm install`, `node`) ആരംഭിക്കാനാകും; LOCAL_ONLY ടയർ
തടയുന്നതിനായി നിലനിൽക്കുന്ന അതേ CVE വിഭാഗമാണിത്.

**#7895 — `mcp:connect` പരിമിതമായ സ്കോപ്പ്:** `/api/mcp/` ഒഴിവാക്കൽ,
പരിമിതമായ `mcp:connect` സ്കോപ്പ് കൈവശമുള്ള ഒരു Bearer കീയും സ്വീകരിക്കുന്നു
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), ഇത്
`src/server/authz/policies/management.ts`-ലെ `hasMcpConnectOrManageScope()`
വഴി പരിശോധിക്കുന്നു. ഇത് `/api/mcp/`-നു മാത്രമായി പരിമിതപ്പെടുത്തിയിരിക്കുന്നു —
മറ്റേതൊരു മാനേജ്മെന്റ് റൂട്ടിലും (ഭാവിയിൽ മറ്റേതെങ്കിലും LOCAL_ONLY ബൈപാസ്
പ്രിഫിക്സ് ചേർത്താലും അതുൾപ്പെടെ) `mcp:connect` യാതൊരു അനുമതിയും നൽകുന്നില്ല,
കൂടാതെ ഇത് `MANAGEMENT_API_KEY_SCOPES`-ൽ നിന്ന് മനഃപൂർവം ഒഴിവാക്കിയിരിക്കുന്നു.
`manage`/`admin` കൈവശമുള്ള ഒരു കീ മുമ്പത്തെപ്പോലെതന്നെ ഒഴിവാക്കൽ കടന്നുപോകും;
വിശാലമായ മാനേജ്മെന്റ് ആക്സസ് ആവശ്യമില്ലാത്ത റിമോട്ട് MCP-മാത്രം കോളർമാർക്കുള്ള
കുറഞ്ഞ-പ്രിവിലേജുള്ള ഒരു ബദലാണ് `mcp:connect`.

#### ഓപ്പറേറ്റർ മാർഗ്ഗനിർദ്ദേശവും ഓഡിറ്റിംഗും

നിങ്ങൾ OmniRoute ഒരു റിവേഴ്സ് പ്രോക്സിയുടെയോ ടണലിന്റെയോ (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) പിന്നിൽ പ്രവർത്തിപ്പിക്കുകയാണെങ്കിൽ, മുകളിലുള്ള
സ്പോൺ ചെയ്യാൻ ശേഷിയുള്ള റൂട്ടുകളെ ലൂപ്പ്ബാക്ക് പരിശോധന തുടർന്നും സംരക്ഷിക്കും —
ക്ലയന്റ് വിലാസം നോൺ-ലൂപ്പ്ബാക്കായ ഒരു അഭ്യർത്ഥന **ഓത്ത് പ്രവർത്തിക്കുന്നതിന് മുമ്പ്**
`403 LOCAL_ONLY` ഉപയോഗിച്ച് നിരസിക്കപ്പെടുന്നതിനാൽ, ചോർന്ന JWT-ക്ക് ഒരു സ്പോണിലേക്ക്
എത്താൻ കഴിയില്ല. രണ്ട് ഓപ്പറേറ്റർ ഉത്തരവാദിത്തങ്ങൾ അവശേഷിക്കുന്നു:

- **ക്ലയന്റ് IP ലൂപ്പ്ബാക്കായി വ്യാജമാക്കി 403 "പരിഹരിക്കരുത്".**
  `X-Forwarded-For: 127.0.0.1` സജ്ജീകരിക്കുന്നതോ, ഉറവിട വിലാസം ലൂപ്പ്ബാക്കായി
  മാറ്റിയെഴുതുന്ന ഒരു പ്രോക്സിയോ, ഈ ടയർ അടച്ചുപൂട്ടുന്ന അതേ RCE വിഭാഗം വീണ്ടും
  തുറക്കുന്നു. പ്രോക്സിയിലൂടെ ഡാഷ്ബോർഡ്/API ലഭ്യമാക്കുക — സ്പോൺ ചെയ്യാൻ ശേഷിയുള്ള
  റൂട്ടുകൾ ഒരിക്കലും ലഭ്യമാക്കരുത്.
- **മാനേജ്-സ്കോപ്പ് ബൈപാസ് പരമാവധി പരിമിതമായി നിലനിർത്തുക.** `/api/mcp/` മാത്രമാണ്
  ബൈപാസ് ചെയ്യാവുന്നത്, അതും `manage`-സ്കോപ്പുള്ള API കീ ഉപയോഗിച്ച് മാത്രം.
  `SPAWN_CAPABLE_PREFIXES` ഒരിക്കലും ബൈപാസ് പട്ടികയിൽ ചേർക്കാൻ കഴിയില്ല — zod
  സ്കീമ അവയെ നിരസിക്കുകയും റൺടൈമിൽ `isLocalOnlyBypassableByManageScope`
  അവയെ നിഷേധിക്കുകയും ചെയ്യുന്നു (ആഴത്തിലുള്ള പ്രതിരോധം); ഡാഷ്ബോർഡിലെ
  "ബൈപാസ് ചെയ്യാവുന്നതാക്കാൻ കഴിയില്ല" എന്നതിന്റെ അർത്ഥം ഇതാണ്.
  `/api/providers/`-ന് കീഴിലുള്ള ഡൈനാമിക്-സെഗ്മെന്റ്, സ്റ്റാറ്റിക്-പാത്ത്,
  സ്പോൺ ചെയ്യാൻ ശേഷിയുള്ള റൂട്ടുകൾ (ഉദാ. `/login`, `/refresh-cursor`) ഫ്ലാറ്റായ
  `SPAWN_CAPABLE_PREFIXES` അറേയ്ക്കു പകരം
  `src/shared/constants/spawnCapablePrefixes.ts`-ലെ regex-അധിഷ്ഠിത
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` അനുബന്ധമാണ്
  ഉൾക്കൊള്ളുന്നത് — അവയെ പിടികൂടാൻ ഫ്ലാറ്റ് അറേയ്ക്ക് മുഴുവൻ
  `/api/providers/` പ്രിഫിക്സും ഉൾക്കൊള്ളേണ്ടിവരും; ഇത് പ്രൊവൈഡർ CRUD-നായി
  റിമോട്ട് ഡാഷ്ബോർഡുകൾ നിയമാനുസൃതമായി ഉപയോഗിക്കുന്ന റൂട്ട് ട്രീയെ അമിതമായി
  വിപുലീകരിക്കും.

**ആക്സസ് ഓഡിറ്റ് ചെയ്യൽ** — ഹോസ്റ്റിന് പുറത്തുനിന്ന് ഒന്നും ഈ റൂട്ടുകളിൽ എത്തുന്നില്ലെന്ന് സ്ഥിരീകരിക്കാൻ:

- `/dashboard/settings/security`-ൽ **Authorization Inventory** തുറക്കുക: തത്സമയ
  LOCAL_ONLY പ്രിഫിക്സ് പട്ടിക, ബൈപാസ് ചെയ്യാവുന്ന പ്രിഫിക്സുകൾ, കംപൈൽ സമയത്തെ
  spawn-ശേഷിയുള്ള ("ബൈപാസ് ചെയ്യാവുന്നതാക്കാൻ കഴിയാത്ത") സെറ്റ് എന്നിവ അത് പ്രദർശിപ്പിക്കുന്നു.
- മുകളിലുള്ള പ്രിഫിക്സുകളും loopback അല്ലാത്ത ക്ലയന്റ് വിലാസവും ഒരുമിച്ച് വരുന്നുണ്ടോയെന്ന് കണ്ടെത്താൻ നിങ്ങളുടെ
  reverse-proxy / access ലോഗുകളിൽ Grep ചെയ്യുക. `403 LOCAL_ONLY` എന്നതിന് പകരം `200`
  നൽകിയ അത്തരം ഏതൊരു ഹിറ്റും യഥാർത്ഥ ക്ലയന്റ് IP-യെ proxy മറയ്ക്കുന്നു എന്നാണ് അർത്ഥമാക്കുന്നത് — proxy ശരിയാക്കുക.
- ഈ പാതകളിലൊന്നിനായി OmniRoute-ന്റെ ലോഗുകളിൽ വരുന്ന `403 LOCAL_ONLY`, guard
  ഉദ്ദേശിച്ച രീതിയിൽ പ്രവർത്തിക്കുന്നതിന്റെ സൂചനയാണ്; മറച്ചുവെക്കേണ്ട പിശകല്ല.

### ടയർ 2 — ALWAYS_PROTECTED

**നടപ്പിലാക്കുന്നത്:** `isAlwaysProtectedPath(path)` → `requireLogin=false` ബൈപാസ് ഒഴിവാക്കുന്നു
**ബൈപാസ്:** `requireLogin=false` ആയിരിക്കുമ്പോൾ ഒന്നുമില്ല; JWT എപ്പോഴും ആവശ്യമാണ്

ഈ റൂട്ടുകൾ നാശകരമോ തിരിച്ചെടുക്കാനാകാത്തതോ ആണ്. "പാസ്വേഡ് ഇല്ലാത്ത"
ഇൻസ്റ്റാളേഷനിൽ ഇവ അനുവദിച്ചാൽ, അതേ LAN-ലുള്ള ആർക്കും ഡാറ്റാബേസ് മായ്ക്കാനോ
സെർവർ പ്രോസസ് അവസാനിപ്പിക്കാനോ കഴിയും.

**ലംഘനമുണ്ടായാലുള്ള പ്രതികരണം:** `401 Authentication required`

`/api/settings/obsidian` അതിന്റെ `/webdav` ചൈൽഡിനെയും ഉൾക്കൊള്ളുന്നു: `POST`, Next.js-ന് മുമ്പ്
ഈ pipeline-ന് പുറത്തായി ഇഷ്ടാനുസൃത Node ലെയർ നൽകുന്ന WebDAV ഫയൽ സർവീസിനെ, കോൾ ചെയ്യുന്നയാൾ
തിരഞ്ഞെടുക്കുന്ന root-ലേക്ക് ചൂണ്ടുകയും പുതുതായി സൃഷ്ടിച്ച Basic ക്രെഡൻഷ്യലുകൾ തിരികെ നൽകുകയും ചെയ്യുന്നു;

GHSA-62vw `GET` വഴിയുള്ള പാസ്വേഡ് വെളിപ്പെടുത്തൽ മാത്രമാണ് മറച്ചത്; ക്രെഡൻഷ്യൽ നൽകൽ ഇപ്പോഴും

ഡാറ്റാ ഡയറക്ടറി തന്നെയായതോ അതിനുള്ളിൽ സ്ഥിതിചെയ്യുന്നതോ അതിനെ ഉൾക്കൊള്ളുന്നതോ ആയ vault നിരസിക്കുന്നു.

### പുതിയ ഇൻസ്റ്റാളേഷന്റെ bootstrap loopback-ൽ മാത്രം — `Host` അടിസ്ഥാനമാക്കിയല്ല, യഥാർത്ഥ peer അടിസ്ഥാനമാക്കി

management password ക്രമീകരിച്ചിട്ടില്ലെങ്കിൽ (`INITIAL_PASSWORD`-ഉം ഇല്ലെങ്കിൽ),
`src/shared/utils/apiAuth.ts`-ലെ `isAuthRequired()` അജ്ഞാത bootstrap **loopback peer-കൾക്ക് മാത്രം**
തുറന്നിടുന്നു. ഇനിപ്പറയുന്ന വിശ്വസനീയ peer സിഗ്നലുകളിൽ നിന്ന്, ഈ ക്രമത്തിൽ, loopback നിർണ്ണയിക്കുന്നു:
token-stamped ചെയ്ത യഥാർത്ഥ TCP peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, policy കാണുന്നത്),
pipeline-ന്റെ സ്വന്തം `AUTHZ_HEADER_PEER_LOCALITY` വിധി (route handler-കൾ കാണുന്നത്,
`OMNIROUTE_PEER_STAMP_TOKEN` സജ്ജീകരിച്ചിരിക്കുമ്പോൾ മാത്രം വിശ്വസനീയം), അല്ലെങ്കിൽ നേരിട്ട്
വിളിക്കുന്നവർക്കുള്ള യഥാർത്ഥ socket peer. `Host` / `nextUrl.hostname` ഒരിക്കലും പരിഗണിക്കില്ല;
ആദ്യ പാസ്വേഡ് എഴുതുന്നതും (`POST /api/settings/require-login`) എല്ലാ network peer-കൾക്കും
തുറന്നിടുന്നതിന് പകരം ഇതേ നിയന്ത്രണത്തിന് കീഴിലാണ് (GHSA-7pq4-8pvv-rx7r).
`managementPolicy` സ്വന്തം `peerContext` വിധി വ്യക്തമായി താഴേക്ക് കൈമാറുന്നതിനാൽ,
ORIGINAL (strip ചെയ്യുന്നതിന് മുമ്പുള്ള) request-ന്റെ header-കൾ ഒരിക്കലും അത് നിർണ്ണയിക്കില്ല.

### ടയർ 3 — MANAGEMENT (ഡിഫോൾട്ട്)

മറ്റെല്ലാ management റൂട്ടുകളും. `requireLogin=false` ക്രമീകരിച്ചിട്ടില്ലെങ്കിൽ
authentication ആവശ്യമാണ്. CLI token-കൾക്ക് ഈ റൂട്ടുകളിൽ authenticate ചെയ്യാൻ കഴിയും
(loopback + സാധുവായ HMAC).

## മൂല്യനിർണ്ണയ ക്രമം

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ലൂപ്പ്ബാക്ക്                                  → അടുത്ത ഘട്ടത്തിലേക്ക്
     → ലൂപ്പ്ബാക്ക് അല്ലാത്തത്, manage-scope Bearer
        കൂടാതെ isLocalOnlyBypassableByManageScope   → അനുവദിക്കുക (management_key)
     → അല്ലെങ്കിൽ                                   → നിരസിക്കുക 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → അനുവദിക്കുക (system)
  3. hasValidCliToken(headers)?
     → അനുവദിക്കുക (cli) [ലൂപ്പ്ബാക്ക് + timingSafeEqual HMAC പരിശോധന]
  4. isAlwaysProtectedPath(path) അല്ലെങ്കിൽ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → അനുവദിക്കുക (dashboard_session)
     → മറികടക്കാനാകാത്ത പാതയിൽ manage-scope Bearer ഉണ്ടോ?
        → അനുവദിക്കുക (management_key)
     → നിരസിക്കുക 401/403
  5. requireLogin=false?
     → അനുവദിക്കുക (anonymous)
```

ഘട്ടം 1-ലെ manage-scope ശാഖ മാത്രമാണ് ഒരു LOCAL_ONLY റൂട്ടിന്റെ ആവശ്യകത നിറവേറ്റാൻ കഴിയുന്ന പ്രാമാണീകരിച്ച പാത; കാലഹരണപ്പെട്ട DB നിശ്ശബ്ദമായി "നിരസിക്കുക" എന്നതിലേക്ക് തരംതാഴാതിരിക്കാൻ auth-backend പരാജയ മോഡ് 403-ന് പകരം 503 നൽകുന്നു.

## പ്രോസസുകൾ സൃഷ്ടിക്കാൻ കഴിയുന്ന പുതിയ റൂട്ട് ചേർക്കൽ

1. `src/server/authz/routeGuard.ts`-ലെ `LOCAL_ONLY_API_PREFIXES`-ലേക്ക് പാതാ പ്രിഫിക്സ് ചേർക്കുക
2. പുതിയ പ്രിഫിക്സിന് `isLocalOnlyPath()` true നൽകുന്നുവെന്ന് ഉറപ്പാക്കുന്ന ഒരു ടെസ്റ്റ് `tests/unit/authz/routeGuard.test.ts`-ൽ ചേർക്കുക
3. **ഈ ഘട്ടം ഒരിക്കലും ഒഴിവാക്കരുത്** — `CLAUDE.md`-ലെ കർശന നിയമം #15 കാണുക
4. തീരുമാനിക്കുക: ഈ റൂട്ട് `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലും ഉൾപ്പെടണമോ?
   സ്വതവേയുള്ള ഉത്തരം **ഇല്ല** എന്നാണ്. manage-scope ഉടമയ്ക്ക് തുറന്നുകൊടുക്കാൻ റൂട്ട് സുരക്ഷിതമാണെങ്കിൽ മാത്രം ഇത് തിരഞ്ഞെടുക്കുക (അതായത്, ഉപയോക്താവ് നിയന്ത്രിക്കുന്ന ഏതെങ്കിലും കോഡ് അത് പ്രോസസായി സൃഷ്ടിക്കരുത്).

## manage-scope വഴി മറികടക്കാവുന്ന പാത ചേർക്കൽ

1. ഉപയോക്താവ് നൽകുന്ന കോഡോ കമാൻഡുകളോ റൂട്ട് പ്രവർത്തിപ്പിക്കുന്നില്ലെന്ന് സ്ഥിരീകരിക്കുക. പ്രവർത്തിപ്പിക്കുന്നുണ്ടെങ്കിൽ നിർത്തുക — ഈ പ്രത്യേക ഇളവ് അതിന് അനുയോജ്യമായ ഉപകരണമല്ല.
2. `src/server/authz/routeGuard.ts`-ലെ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലേക്ക് പ്രിഫിക്സ് ചേർക്കുക
3. നാല് അഭ്യർത്ഥനാ രൂപങ്ങൾക്കും `tests/unit/authz/management-policy.test.ts`-ൽ കവറേജ് ചേർക്കുക: Bearer ഇല്ല (403), manage Bearer (അനുവദിക്കുക), non-manage Bearer (403), കൂടാതെ manage Bearer ഉണ്ടായാലും `/api/cli-tools/runtime/*` കർശനമായ ലൂപ്പ്ബാക്ക് മാത്രമായി തുടരുന്നുവെന്ന് ഉറപ്പാക്കുന്ന ഓരോ പ്രിഫിക്സിനുമായുള്ള റിഗ്രഷൻ.

- `scripts/check/check-openapi-coverage.mjs` — കവറേജ് < 99% ആണെങ്കിൽ പരാജയപ്പെടുന്നു
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` അല്ലെങ്കിൽ
  `x-always-protected` അനോട്ടേഷനുകൾ കംപൈൽ സമയ സ്ഥിരാങ്കങ്ങളിൽ നിന്ന് വ്യതിചലിച്ചാൽ പരാജയപ്പെടുന്നു

രണ്ട് സ്ക്രിപ്റ്റുകളും pre-commit hook-ലും CI-ലും പ്രവർത്തിക്കുന്നു.

### തെറ്റായ പോസിറ്റീവ് നിയമം

`routeGuard.ts` സ്ഥിരാങ്കത്തിൽ ഉൾപ്പെടാത്ത ഒരു റൂട്ടിൽ `x-always-protected` അല്ലെങ്കിൽ `x-loopback-only` അനോട്ടേറ്റ് ചെയ്താൽ, കവറേജ് സ്ക്രിപ്റ്റ് പരാജയപ്പെടുന്നു. `routeGuard.ts` യഥാർത്ഥത്തിൽ നിർബന്ധമാക്കുന്ന കാര്യവുമായി YAML-നെ പൊരുത്തപ്പെടുത്തുക എന്നതാണ് എല്ലായ്പ്പോഴും പരിഹാരം — നിർബന്ധിത നിയന്ത്രണ ലോജിക് നടപ്പാക്കാതെ `routeGuard.ts`-ലേക്ക് റൂട്ടുകൾ ചേർക്കുകയല്ല.
