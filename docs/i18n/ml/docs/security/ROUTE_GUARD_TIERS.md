## അവലോകനം

എല്ലാ OmniRoute മാനേജ്മെന്റ് API റൂട്ടുകളും മൂന്ന് സംരക്ഷണ
തലങ്ങളിൽ ഒന്നായി വർഗ്ഗീകരിച്ചിരിക്കുന്നു. ഈ വർഗ്ഗീകരണം സ്ഥിരമാണ്,
`src/server/authz/routeGuard.ts`-ൽ നിർവചിച്ചിരിക്കുന്നു, കൂടാതെ മറ്റേതെങ്കിലും ഓത്ത് ശാഖ
പ്രവർത്തിക്കുന്നതിന് മുമ്പ് വിലയിരുത്തപ്പെടുന്നു.

## ടിയറുകൾ

### ടിയർ 1 — LOCAL_ONLY

**നടപ്പിലാക്കുന്നത്:** `isLocalOnlyPath(path)` → ലൂപ്പ്ബാക്ക് ഹോസ്റ്റ് പരിശോധന  
**ബൈപാസ്:** ഡിഫോൾട്ടായി ഒന്നുമില്ല. അഭ്യർത്ഥനയിൽ `manage` സ്കോപ്പുള്ള സാധുവായ API കീ ഉണ്ടായിരിക്കുമ്പോൾ, `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലുള്ള പാതകൾക്ക് മാത്രമായി പരിമിതപ്പെടുത്തിയ ഇളവ് (കാണുക [Manage-സ്കോപ്പ് ഇളവ്](#manage-scope-carve-out)).

ഈ റൂട്ടുകൾ ചൈൽഡ് പ്രോസസ്സുകൾ സൃഷ്ടിക്കുകയോ റൺടൈം കോഡ് പ്രവർത്തിപ്പിക്കുകയോ ചെയ്യുന്നു. ഇവയെ ലൂപ്പ്ബാക്ക് ഇതര ട്രാഫിക്കിന് ലഭ്യമാക്കുന്നത്, സാധുവായ JWT നേടിയ ഒരു ആക്രമണകാരിക്ക് (ഉദാ., Cloudflared/Ngrok ടണൽ വഴി) പ്രോസസുകൾ സൃഷ്ടിക്കാൻ ഇടയാക്കും — ഇത് അറിയപ്പെടുന്ന ഒരു CVE വിഭാഗമാണ് ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj എന്താണ് (ആക്രമണ വിഭാഗം):** ഒരു മാനേജ്മെന്റ്/ഏജന്റ് സെർവർ ഒരു സബ്പ്രോസസ് (`npm install`, `node`, ഒരു ബ്രൗസർ, ഒരു പ്രോക്സി, `git`, `tar`, …) സമാരംഭിക്കുന്ന എൻഡ്പോയിന്റ് ലഭ്യമാക്കുന്നു. ആ എൻഡ്പോയിന്റ് ഹോസ്റ്റിന് പുറത്തുനിന്ന് ആക്സസ് ചെയ്യാനാകുന്നുവെങ്കിൽ — ഓപ്പറേറ്റർ OmniRoute-നെ nginx/Cloudflare/Tailscale ടണലിന് പിന്നിൽ സ്ഥാപിക്കുകയും ഒരു JWT ചോർന്നുപോകുകയും ചെയ്തതിനാലോ, അല്ലെങ്കിൽ ഓത്ത് തെറ്റായി കോൺഫിഗർ ചെയ്തതിനാലോ — ആക്രമണകാരി "ഒരു API വിളിക്കുക" എന്നതിനെ "ഹോസ്റ്റിൽ ഒരു കമാൻഡ് പ്രവർത്തിപ്പിക്കുക" എന്നതാക്കി മാറ്റുന്നു (റിമോട്ട് കോഡ് എക്സിക്യൂഷൻ). സ്പോൺ ചെയ്യാൻ ശേഷിയുള്ള എല്ലാ റൂട്ടുകളിലും **ഏതൊരു ഓത്ത് പരിശോധനയ്ക്കും മുമ്പ്, നിബന്ധനകളില്ലാതെ ലൂപ്പ്ബാക്ക് ഹോസ്റ്റ് പരിശോധന** നിർബന്ധമാക്കുന്നതിലൂടെ OmniRoute ഇത് തടയുന്നു: ടണലിലൂടെ ചോർന്ന ടോക്കണിന് പോലും സ്പോൺ പ്രവർത്തനത്തിലേക്ക് എത്താൻ കഴിയില്ല.

**പൂർണ്ണമായ LOCAL_ONLY ഗണം.** ആധികാരിക ഉറവിടം `src/server/authz/routeGuard.ts`-ലുള്ള `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ആണ്; താഴെയുള്ള പട്ടിക നിലവിലെ സ്ഥിതി പ്രതിഫലിപ്പിക്കുന്നു. `check-route-guard-membership` ഗേറ്റ് സ്പോൺ ചെയ്യാൻ ശേഷിയുള്ള പ്രിഫിക്സുകൾക്ക് കീഴിലുള്ള എല്ലാ `route.ts` ഫയലുകളും പട്ടികപ്പെടുത്തുകയും അവയിൽ ഏതെങ്കിലും ലോക്കൽ-ഒൺലി ആയി വർഗ്ഗീകരിച്ചിട്ടില്ലെങ്കിൽ CI പരാജയപ്പെടുത്തുകയും ചെയ്യുന്നു.

#### മാനേജ്-സ്കോപ്പ് ഒഴിവാക്കൽ

LOCAL_ONLY പാതകളുടെ ഒരു ഉപഗണം, അഭ്യർത്ഥനയിൽ `manage` സ്കോപ്പ് (അല്ലെങ്കിൽ
`admin`) ഉൾപ്പെടുന്ന മെറ്റാഡാറ്റയുള്ള `Authorization: Bearer <api-key>`
ഉണ്ടെങ്കിൽ മാത്രം, നോൺ-ലൂപ്പ്ബാക്കിൽ നിന്നും ആക്സസ് ചെയ്യാവുന്നതാണ്. ഈ ഒഴിവാക്കൽ
ഓരോ പാതയ്ക്കും `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` വഴി വ്യക്തമായി
നിയന്ത്രിച്ചിരിക്കുന്നതിനാൽ, ഏതൊരു പുതിയ LOCAL_ONLY പാതയ്ക്കും കർശനമായ ലൂപ്പ്ബാക്ക്
മാത്രം എന്നതുതന്നെ ഡിഫോൾട്ടായി തുടരും. പ്രാമാണീകരിക്കാത്ത അഭ്യർത്ഥനകളും മാനേജ്
അനുമതിയില്ലാത്ത കീകളുള്ള അഭ്യർത്ഥനകളും ഇപ്പോഴും `403 LOCAL_ONLY` ഉപയോഗിച്ച്
നിരസിക്കപ്പെടും.

നിലവിൽ ഒഴിവാക്കാവുന്ന ഏക പ്രിഫിക്സ് `/api/mcp/` ആണ്. `/api/cli-tools/runtime/`,
`/api/services/` എന്നിവ മനഃപൂർവം ഒഴിവാക്കിയിരിക്കുന്നു, കാരണം അവയ്ക്ക് ഏതെങ്കിലും
സബ്പ്രോസസുകൾ (`npm install`, `node`) ആരംഭിക്കാൻ കഴിയും; LOCAL_ONLY തലം
തടയുന്നതിനായി നിലവിലുള്ള അതേ CVE വിഭാഗമാണിത്.

**#7895 — `mcp:connect` പരിമിതമായ സ്കോപ്പ്:** `/api/mcp/` ഒഴിവാക്കൽ,
പരിമിതമായ `mcp:connect` സ്കോപ്പ് കൈവശമുള്ള ഒരു Bearer കീയും സ്വീകരിക്കുന്നു
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`); ഇത്
`src/server/authz/policies/management.ts`-ലെ `hasMcpConnectOrManageScope()`
വഴി പരിശോധിക്കുന്നു. ഇത് `/api/mcp/`-നു മാത്രമായി പരിമിതപ്പെടുത്തിയിരിക്കുന്നു —
മറ്റേതെങ്കിലും മാനേജ്മെന്റ് റൂട്ടിൽ (ഭാവിയിൽ ചേർക്കാനിടയുള്ള മറ്റെല്ലാ LOCAL_ONLY
ബൈപാസ് പ്രിഫിക്സുകളും ഉൾപ്പെടെ) `mcp:connect` യാതൊരു അനുമതിയും നൽകുന്നില്ല;
കൂടാതെ ഇത് `MANAGEMENT_API_KEY_SCOPES`-ൽ നിന്ന് മനഃപൂർവം ഒഴിവാക്കിയിരിക്കുന്നു.
`manage`/`admin` കൈവശമുള്ള ഒരു കീ മുമ്പത്തെപ്പോലെ തന്നെ ഒഴിവാക്കൽ കടന്നുപോകും;
വിപുലമായ മാനേജ്മെന്റ് ആക്സസ് ആവശ്യമില്ലാത്ത, വിദൂര MCP-മാത്രം കോളർമാർക്കുള്ള
കുറഞ്ഞ-അധികാരമുള്ള ഒരു ബദലാണ് `mcp:connect`.

#### ഓപ്പറേറ്റർക്കുള്ള മാർഗനിർദേശവും ഓഡിറ്റിങ്ങും

നിങ്ങൾ OmniRoute ഒരു റിവേഴ്സ് പ്രോക്സിയുടെയോ ടണലിന്റെയോ (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) പിന്നിൽ പ്രവർത്തിപ്പിക്കുകയാണെങ്കിൽ, മുകളിലുള്ള പ്രോസസ്
ആരംഭിക്കാൻ ശേഷിയുള്ള റൂട്ടുകളെ ലൂപ്പ്ബാക്ക് പരിശോധന തുടർന്നും സംരക്ഷിക്കും —
ക്ലയന്റ് വിലാസം നോൺ-ലൂപ്പ്ബാക്ക് ആയ ഒരു അഭ്യർത്ഥന, **പ്രാമാണീകരണം നടക്കുന്നതിന്
മുമ്പുതന്നെ** `403 LOCAL_ONLY` ഉപയോഗിച്ച് നിരസിക്കപ്പെടും; അതിനാൽ ചോർന്ന JWT-ക്ക്
ഒരു പ്രോസസ് ആരംഭിക്കാൻ കഴിയില്ല. ഓപ്പറേറ്റർക്ക് രണ്ട് ഉത്തരവാദിത്തങ്ങൾ ശേഷിക്കുന്നു:

- **ക്ലയന്റ് IP ലൂപ്പ്ബാക്കായി വ്യാജമാക്കി 403 "പരിഹരിക്കരുത്".**
  `X-Forwarded-For: 127.0.0.1` സജ്ജീകരിക്കുന്നതോ സോഴ്സ് വിലാസം ലൂപ്പ്ബാക്കായി
  മാറ്റിയെഴുതുന്ന പ്രോക്സി ഉപയോഗിക്കുന്നതോ ഈ തലം അടയ്ക്കുന്ന അതേ RCE വിഭാഗം
  വീണ്ടും തുറക്കും. പ്രോക്സി വഴി ഡാഷ്ബോർഡ്/API ലഭ്യമാക്കുക — പ്രോസസ് ആരംഭിക്കാൻ
  ശേഷിയുള്ള റൂട്ടുകൾ ഒരിക്കലും ലഭ്യമാക്കരുത്.
- **മാനേജ്-സ്കോപ്പ് ബൈപാസ് ഏറ്റവും കുറഞ്ഞ നിലയിൽ നിലനിർത്തുക.** `/api/mcp/`
  മാത്രമാണ് ബൈപാസ് ചെയ്യാവുന്നത്, അതും `manage` സ്കോപ്പുള്ള API കീ ഉപയോഗിച്ച്
  മാത്രം. `SPAWN_CAPABLE_PREFIXES` ഒരിക്കലും ബൈപാസ് പട്ടികയിലേക്ക് ചേർക്കാനാവില്ല —
  zod സ്കീമ അവ നിരസിക്കുകയും റൺടൈമിൽ `isLocalOnlyBypassableByManageScope`
  അവ നിഷേധിക്കുകയും ചെയ്യുന്നു (ബഹുതല പ്രതിരോധം); ഡാഷ്ബോർഡിലെ "ബൈപാസ്
  ചെയ്യാവുന്നതാക്കാൻ കഴിയില്ല" എന്നതിന്റെ അർത്ഥം ഇതാണ്. `/api/providers/`-ന്
  കീഴിലുള്ള ഡൈനാമിക്-സെഗ്മെന്റ്, സ്റ്റാറ്റിക്-പാത പ്രോസസ്-ആരംഭ ശേഷിയുള്ള റൂട്ടുകൾ
  (ഉദാ. `/login`, `/refresh-cursor`) ഫ്ലാറ്റ് `SPAWN_CAPABLE_PREFIXES` അറേയ്ക്ക്
  പകരം `src/shared/constants/spawnCapablePrefixes.ts`-ലെ regex-അധിഷ്ഠിത
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` സഹചാരി വഴി
  ഉൾക്കൊള്ളുന്നു — അവയെ കണ്ടെത്താൻ ഫ്ലാറ്റ് അറേ മുഴുവൻ `/api/providers/`
  പ്രിഫിക്സും ഉൾക്കൊള്ളേണ്ടിവരും; അങ്ങനെ ചെയ്താൽ പ്രൊവൈഡർ CRUD-നായി വിദൂര
  ഡാഷ്ബോർഡുകൾ നിയമാനുസൃതമായി ഉപയോഗിക്കുന്ന ഒരു റൂട്ട് ട്രീ അനാവശ്യമായി
  അതിവിപുലീകരിക്കപ്പെടും.

**ആക്സസ് ഓഡിറ്റ് ചെയ്യൽ** — ഹോസ്റ്റിന് പുറത്തുനിന്ന് ഒന്നും ഈ റൂട്ടുകളിൽ എത്തുന്നില്ലെന്ന് സ്ഥിരീകരിക്കാൻ:

- `/dashboard/settings/security` എന്നതിലെ **Authorization Inventory** തുറക്കുക: ഇത് തത്സമയ LOCAL_ONLY പ്രിഫിക്സ് പട്ടികയും, ബൈപാസ് ചെയ്യാവുന്ന പ്രിഫിക്സുകളും, കംപൈൽ സമയത്തെ spawn-സാധ്യതയുള്ള ("ബൈപാസ് ചെയ്യാവുന്നതാക്കാൻ കഴിയാത്ത") ഗണവും പ്രദർശിപ്പിക്കുന്നു.
- മുകളിലുള്ള പ്രിഫിക്സുകൾ loopback അല്ലാത്ത ക്ലയന്റ് വിലാസവുമായി ജോടിയാകുന്നുണ്ടോ എന്ന് കണ്ടെത്താൻ നിങ്ങളുടെ reverse-proxy / access ലോഗുകളിൽ grep ചെയ്യുക. അത്തരത്തിലുള്ള ഏതെങ്കിലും ഹിറ്റിന് `403 LOCAL_ONLY` എന്നതിനുപകരം `200` ലഭിച്ചിട്ടുണ്ടെങ്കിൽ, പ്രോക്സി യഥാർഥ ക്ലയന്റ് IP മറയ്ക്കുകയാണ് — പ്രോക്സി ശരിയാക്കുക.
- ഈ പാതകളിലൊന്നിനായി OmniRoute-ന്റെ ലോഗുകളിൽ കാണുന്ന `403 LOCAL_ONLY`, ഗാർഡ് ഉദ്ദേശിച്ച പ്രകാരം പ്രവർത്തിക്കുന്നതിന്റെ സൂചനയാണ്; അടിച്ചമർത്തേണ്ട ഒരു പിശകല്ല.

### ടയർ 2 — ALWAYS_PROTECTED

**നടപ്പിലാക്കുന്നത്:** `isAlwaysProtectedPath(path)` → `requireLogin=false` ബൈപാസ് ഒഴിവാക്കുന്നു
**ബൈപാസ്:** `requireLogin=false` ആയിരിക്കുമ്പോൾ ഒന്നുമില്ല; JWT എപ്പോഴും ആവശ്യമാണ്

ഈ റൂട്ടുകൾ നാശകരമോ പഴയപടിയാക്കാനാകാത്തതോ ആണ്. "പാസ്വേഡ് ഇല്ലാത്ത"
ഇൻസ്റ്റാളേഷനിൽ ഇവ അനുവദിച്ചാൽ, അതേ LAN-ലുള്ള ആർക്കും ഡാറ്റാബേസ് മായ്ക്കാനോ
സെർവർ പ്രോസസ് അവസാനിപ്പിക്കാനോ കഴിയും.

| ----------------------------------------- | ------------------------------------------------------------------------ |

| `/api/db-backups`                         | സമ്പൂർണ ഡാറ്റാബേസ് ബാക്കപ്പ് ആർക്കൈവിലേക്കുള്ള ആക്സസ്                    |
| `/api/settings/export-json`               | സമ്പൂർണ settings blob എക്സ്പോർട്ട് ചെയ്യുന്നു (രഹസ്യങ്ങൾ ഉൾപ്പെടെ)       |

**ലംഘനത്തിനുള്ള പ്രതികരണം:** `401 Authentication required`

`/api/settings/obsidian` അതിന്റെ `/webdav` ചൈൽഡിനെയും ഉൾക്കൊള്ളുന്നു: `POST`, ഈ pipeline-ന് പുറത്തായി Next.js-ന് മുമ്പ് കസ്റ്റം Node layer നൽകുന്ന WebDAV ഫയൽ സർവീസിനെ, കോളർ തിരഞ്ഞെടുക്കുന്ന root-ലേക്ക് ചൂണ്ടുകയും പുതുതായി സൃഷ്ടിച്ച Basic credentials തിരികെ നൽകുകയും ചെയ്യുന്നു; `DELETE` അവ rotate ചെയ്യുന്നു; parent `POST` Obsidian REST API token സംഭരിക്കുന്നു. GHSA-62vw, `GET` വഴിയുള്ള പാസ്വേഡ് വെളിപ്പെടുത്തൽ മാത്രമാണ് മറച്ചത്; credentials നൽകുന്ന സംവിധാനം അപ്പോഴും fail-open ടയറിലായിരുന്നു (GHSA-7pq4-8pvv-rx7r). കൂടാതെ `enableObsidianVaultSync()`, data directory തന്നെയായതോ അതിനുള്ളിലുള്ളതോ അതിനെ ഉൾക്കൊള്ളുന്നതോ ആയ vault നിരസിക്കുന്നു.

### പുതിയ ഇൻസ്റ്റാളേഷന്റെ bootstrap loopback-ൽ മാത്രം — `Host` അടിസ്ഥാനമാക്കിയല്ല, യഥാർഥ peer അടിസ്ഥാനമാക്കി

management password കോൺഫിഗർ ചെയ്തിട്ടില്ലാത്തപ്പോൾ (`INITIAL_PASSWORD` ഇല്ലാതെയും), `src/shared/utils/apiAuth.ts`-ലെ `isAuthRequired()` അജ്ഞാത bootstrap **loopback peers-ന് മാത്രം** തുറന്നുവെക്കുന്നു. വിശ്വസനീയമായ peer signals-ൽനിന്ന് ഇനിപ്പറയുന്ന ക്രമത്തിലാണ് loopback നിർണയിക്കുന്നത്: token-stamp ചെയ്ത യഥാർഥ TCP peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, policy കാണുന്നത്), pipeline-ന്റെ സ്വന്തം `AUTHZ_HEADER_PEER_LOCALITY` വിധി (route handlers കാണുന്നത്; `OMNIROUTE_PEER_STAMP_TOKEN` സജ്ജീകരിച്ചിരിക്കുമ്പോൾ മാത്രം വിശ്വസനീയം), അല്ലെങ്കിൽ നേരിട്ടുള്ള callers-ന്റെ യഥാർഥ socket peer. `Host` / `nextUrl.hostname` ഒരിക്കലും പരിശോധിക്കപ്പെടുന്നില്ല; ആദ്യത്തെ password write (`POST /api/settings/require-login`) എല്ലാ network peer-കൾക്കും തുറന്നുകൊടുക്കുന്നതിന് പകരം ഇതേ നിയന്ത്രണത്തിന് കീഴിലാണ് (GHSA-7pq4-8pvv-rx7r). `managementPolicy` സ്വന്തം `peerContext` വിധി വ്യക്തമായി താഴേക്ക് കൈമാറുന്നതിനാൽ, ORIGINAL (strip ചെയ്യുന്നതിന് മുമ്പുള്ള) request-ന്റെ headers ഒരിക്കലും അത് നിർണയിക്കുന്നില്ല.

### ടയർ 3 — MANAGEMENT (സ്ഥിരസ്ഥിതി)

മറ്റെല്ലാ management റൂട്ടുകളും. `requireLogin=false` കോൺഫിഗർ ചെയ്തിട്ടില്ലെങ്കിൽ authentication ആവശ്യമാണ്. CLI tokens-ന് ഈ റൂട്ടുകളിൽ authentication നടത്താം (loopback + സാധുവായ HMAC).

## മൂല്യനിർണ്ണയ ക്രമം

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ലൂപ്പ്ബാക്ക്                                  → അടുത്ത ഘട്ടത്തിലേക്ക്
     → ലൂപ്പ്ബാക്ക് അല്ലാത്തത്, manage-scope Bearer
        കൂടാതെ isLocalOnlyBypassableByManageScope   → അനുവദിക്കുക (management_key)
     → അല്ലെങ്കിൽ                                   → നിരസിക്കുക 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → അനുവദിക്കുക (system)
  3. hasValidCliToken(headers)?
     → അനുവദിക്കുക (cli) [ലൂപ്പ്ബാക്ക് + timingSafeEqual HMAC പരിശോധന]
  4. isAlwaysProtectedPath(path) അല്ലെങ്കിൽ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → അനുവദിക്കുക (dashboard_session)
     → മറികടക്കാനാകാത്ത പാതയിൽ manage-scope Bearer ഉണ്ടോ?
        → അനുവദിക്കുക (management_key)
     → നിരസിക്കുക 401/403
  5. requireLogin=false?
     → അനുവദിക്കുക (anonymous)
```

ഘട്ടം 1-ലെ manage-scope ശാഖ മാത്രമാണ് ഒരു LOCAL_ONLY റൂട്ടിന്റെ ആവശ്യകത നിറവേറ്റാൻ കഴിയുന്ന പ്രാമാണീകരിച്ച പാത; കാലഹരണപ്പെട്ട DB നിശ്ശബ്ദമായി "നിരസിക്കുക" എന്നതിലേക്ക് തരംതാഴാതിരിക്കാൻ auth-backend പരാജയ മോഡ് 403-ന് പകരം 503 നൽകുന്നു.

## പ്രോസസുകൾ സൃഷ്ടിക്കാൻ കഴിയുന്ന പുതിയ റൂട്ട് ചേർക്കൽ

1. `src/server/authz/routeGuard.ts`-ലെ `LOCAL_ONLY_API_PREFIXES`-ലേക്ക് പാതാ പ്രിഫിക്സ് ചേർക്കുക
2. പുതിയ പ്രിഫിക്സിന് `isLocalOnlyPath()` true നൽകുന്നുവെന്ന് ഉറപ്പാക്കുന്ന ഒരു ടെസ്റ്റ് `tests/unit/authz/routeGuard.test.ts`-ൽ ചേർക്കുക
3. **ഈ ഘട്ടം ഒരിക്കലും ഒഴിവാക്കരുത്** — `CLAUDE.md`-ലെ കർശന നിയമം #15 കാണുക
4. തീരുമാനിക്കുക: ഈ റൂട്ട് `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലും ഉൾപ്പെടണമോ?
   സ്വതവേയുള്ള ഉത്തരം **ഇല്ല** എന്നാണ്. manage-scope ഉടമയ്ക്ക് തുറന്നുകൊടുക്കാൻ റൂട്ട് സുരക്ഷിതമാണെങ്കിൽ മാത്രം ഇത് തിരഞ്ഞെടുക്കുക (അതായത്, ഉപയോക്താവ് നിയന്ത്രിക്കുന്ന ഏതെങ്കിലും കോഡ് അത് പ്രോസസായി സൃഷ്ടിക്കരുത്).

## manage-scope വഴി മറികടക്കാവുന്ന പാത ചേർക്കൽ

1. ഉപയോക്താവ് നൽകുന്ന കോഡോ കമാൻഡുകളോ റൂട്ട് പ്രവർത്തിപ്പിക്കുന്നില്ലെന്ന് സ്ഥിരീകരിക്കുക. പ്രവർത്തിപ്പിക്കുന്നുണ്ടെങ്കിൽ നിർത്തുക — ഈ പ്രത്യേക ഇളവ് അതിന് അനുയോജ്യമായ ഉപകരണമല്ല.
2. `src/server/authz/routeGuard.ts`-ലെ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ലേക്ക് പ്രിഫിക്സ് ചേർക്കുക
3. നാല് അഭ്യർത്ഥനാ രൂപങ്ങൾക്കും `tests/unit/authz/management-policy.test.ts`-ൽ കവറേജ് ചേർക്കുക: Bearer ഇല്ല (403), manage Bearer (അനുവദിക്കുക), non-manage Bearer (403), കൂടാതെ manage Bearer ഉണ്ടായാലും `/api/cli-tools/runtime/*` കർശനമായ ലൂപ്പ്ബാക്ക് മാത്രമായി തുടരുന്നുവെന്ന് ഉറപ്പാക്കുന്ന ഓരോ പ്രിഫിക്സിനുമായുള്ള റിഗ്രഷൻ.

## OpenAPI-യിൽ സുരക്ഷാ ടയറുകൾ രേഖപ്പെടുത്തൽ

`docs/openapi.yaml`-ലേക്ക് പുതിയ റൂട്ട് ചേർക്കുമ്പോൾ, റൂട്ട് `routeGuard.ts` പ്രകാരം വർഗ്ഗീകരിച്ചിട്ടുണ്ടെങ്കിൽ അനുബന്ധ vendor extension പ്രയോഗിക്കുക:

### സാധൂകരണം

YAML അനോട്ടേഷനുകളും `routeGuard.ts`-ഉം തമ്മിലുള്ള സ്ഥിരത രണ്ട് സ്ക്രിപ്റ്റുകൾ നിർബന്ധമാക്കുന്നു:

- `scripts/check/check-openapi-coverage.mjs` — കവറേജ് < 99% ആണെങ്കിൽ പരാജയപ്പെടുന്നു
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` അല്ലെങ്കിൽ
  `x-always-protected` അനോട്ടേഷനുകൾ കംപൈൽ സമയ സ്ഥിരാങ്കങ്ങളിൽ നിന്ന് വ്യതിചലിച്ചാൽ പരാജയപ്പെടുന്നു

രണ്ട് സ്ക്രിപ്റ്റുകളും pre-commit hook-ലും CI-ലും പ്രവർത്തിക്കുന്നു.

### തെറ്റായ പോസിറ്റീവ് നിയമം

`routeGuard.ts` സ്ഥിരാങ്കത്തിൽ ഉൾപ്പെടാത്ത ഒരു റൂട്ടിൽ `x-always-protected` അല്ലെങ്കിൽ `x-loopback-only` അനോട്ടേറ്റ് ചെയ്താൽ, കവറേജ് സ്ക്രിപ്റ്റ് പരാജയപ്പെടുന്നു. `routeGuard.ts` യഥാർത്ഥത്തിൽ നിർബന്ധമാക്കുന്ന കാര്യവുമായി YAML-നെ പൊരുത്തപ്പെടുത്തുക എന്നതാണ് എല്ലായ്പ്പോഴും പരിഹാരം — നിർബന്ധിത നിയന്ത്രണ ലോജിക് നടപ്പാക്കാതെ `routeGuard.ts`-ലേക്ക് റൂട്ടുകൾ ചേർക്കുകയല്ല.
