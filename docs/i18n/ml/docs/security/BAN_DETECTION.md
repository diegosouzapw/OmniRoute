OmniRoute, ഒരു ദാതാവിന്റെ **അക്കൗണ്ട് ശാശ്വതമായി പ്രവർത്തനരഹിതമായതായി** (സസ്പെൻഡ് ചെയ്തത് / നിർജ്ജീവമാക്കിയത് / സേവന നിബന്ധനകൾ ലംഘിച്ചതിനാൽ നിരോധിച്ചത്) സൂചിപ്പിക്കുന്ന അടയാളങ്ങൾക്കായി അപ്സ്ട്രീം പിശക് പ്രതികരണങ്ങൾ പരിശോധിക്കുന്നു. പൊരുത്തം കണ്ടെത്തുമ്പോൾ, ആ കണക്ഷനെ **അന്തിമ `banned` അവസ്ഥയിലേക്ക്** മാറ്റുന്നതിനാൽ അഭ്യർത്ഥനകൾക്കായി പിന്നീട് അത് തിരഞ്ഞെടുക്കപ്പെടില്ല. **Security → Banned Keywords** ക്രമീകരണ കാർഡ് കോൺഫിഗർ ചെയ്യുന്നത് ഇതാണ് ("ശാശ്വത അക്കൗണ്ട് നിരോധനം കണ്ടെത്തുന്നതിന് കാരണമാകുന്ന അധിക കീവേഡുകൾ. അന്തർനിർമ്മിത കീവേഡുകൾ എല്ലായ്പ്പോഴും ബാധകമാണ്.").

ഈ പേജ് അന്തർനിർമ്മിത പട്ടിക, കണ്ടെത്തൽ പ്രവാഹം, അതിന്റെ പരിധി, ഇഷ്ടാനുസൃത കീവേഡുകൾ സുരക്ഷിതമായി ചേർക്കുന്ന വിധം, ഫ്ലാഗ് ചെയ്ത കണക്ഷൻ വീണ്ടെടുക്കുന്ന വിധം എന്നിവ രേഖപ്പെടുത്തുന്നു. അന്തിമ അവസ്ഥ തന്നെ പ്രതിരോധക്ഷമതാ മാതൃകയുടെ ഭാഗമാണ് — [RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) ("അന്തിമ അവസ്ഥകൾ") കാണുക.

**ആധികാരിക ഉറവിടം:** `open-sse/services/accountFallback.ts`
(`ACCOUNT_DEACTIVATED_SIGNALS`, `getMergedBannedSignals()`, `isAccountDeactivated()`),
കൂടാതെ അന്തിമമല്ലാത്ത സ്ഥിരീകരണ ക്ലാസിനായി
(`ACCOUNT_VERIFICATION_REQUIRED_SIGNALS` / `isAccountVerificationRequired()`) എന്നതും അത് ഉപയോഗിക്കുന്ന 403 ശാഖയ്ക്കുമായി
`open-sse/services/errorClassifier.ts`.

## അന്തർനിർമ്മിത കീവേഡുകൾ

ഇഷ്ടാനുസൃത ലിസ്റ്റ് ഏതായാലും, ഈ 7 സബ്സ്ട്രിങ്ങുകൾ എല്ലായ്പ്പോഴും ബാധകമാണ് (അക്ഷരവലുപ്പം പരിഗണിക്കാതെ):

```
account_deactivated
account has been deactivated
account has been disabled
your account has been suspended
this account is deactivated
this service has been disabled in this account for violation    (Antigravity)
this service has been disabled in this account                  (Antigravity)
```

> ദാതാക്കൾ അവരുടെ നിരോധന സന്ദേശങ്ങളുടെ പദപ്രയോഗം മാറ്റുന്നതിനനുസരിച്ച് ഈ ലിസ്റ്റും പരിണമിക്കുന്നു. ആധികാരികമായ
> പകർപ്പ് `open-sse/services/accountFallback.ts`-ലെ `ACCOUNT_DEACTIVATED_SIGNALS` ആണ്;
> മുകളിലെ ബ്ലോക്കിനെ ഒരു സ്നാപ്പ്ഷോട്ടായി കണക്കാക്കുക.

### നിരോധനമല്ല: ഓപ്പറേറ്റർക്ക് നടപടിയെടുക്കാവുന്ന സ്ഥിരീകരണ നിർദ്ദേശങ്ങൾ

`verify your account to continue` **മുമ്പ്** മുകളിലെ ലിസ്റ്റിൽ ഉണ്ടായിരുന്നു. അത് ഒരു നിരോധന
സിഗ്നൽ അല്ല; ഇപ്പോൾ അത് `ACCOUNT_VERIFICATION_REQUIRED_SIGNALS`-ലാണ് ഉള്ളത്, ഇത് കണക്ഷൻ
അവസാനിപ്പിക്കുന്നതിന് പകരം വീണ്ടെടുക്കാവുന്ന `PROJECT_ROUTE_ERROR` ആയി വർഗ്ഗീകരിക്കുന്നു.

Google Cloud Code / Antigravity ഇത് `403 VALIDATION_REQUIRED` ആയി നൽകുന്നു. ഇത്
**താൽക്കാലികമാണ്, ക്വോട്ട പൂർണ്ണമായും ലഭ്യമായ ആരോഗ്യകരമായ അക്കൗണ്ടുകളിലും സംഭവിക്കുന്നു** — ഒരു ലൈവ്
ഡിപ്ലോയ്മെന്റിൽ അളന്നത് (2026-09-25, `proxy_logs`): ഒരു Antigravity കണക്ഷൻ 10 മിനിറ്റിനുള്ളിൽ
ഇത്തരം 403 പ്രതികരണങ്ങളിൽ 33 എണ്ണം നൽകി, എന്നിട്ടും `active` ആയി തുടർന്നു; അതേസമയം, എല്ലാ 17 വിൻഡോകളിലും
അതിന്റെ ക്വോട്ടയുടെ 100 % കൈവശമുണ്ടായിരുന്ന മറ്റൊരു കണക്ഷൻ **ഒരൊറ്റ** ഇത്തരത്തിലുള്ള പ്രതികരണത്താൽ ശാശ്വതമായി നിരോധിക്കപ്പെട്ടു. ഏത്
ശ്രമത്തിനാണ് പ്രതികരണം ലഭിച്ചത് എന്നത് മാത്രമായിരുന്നു വ്യത്യാസം.

ഈ വ്യത്യാസം പ്രധാനമാണ്, കാരണം ഒരു ടെർമിനൽ പൊരുത്തം `permanent: true` ആണ് (1 വർഷത്തെ കൂൾഡൗൺ,
ഒരിക്കലും സ്വയമേവ വീണ്ടെടുക്കില്ല), അതേസമയം ഓപ്പറേറ്റർക്ക് ബ്രൗസറിൽ ഒരു സ്ഥിരീകരണ നിർദ്ദേശം പരിഹരിക്കാനാകും.
ഈ വാചകം നിരോധന ലിസ്റ്റിൽ നിലനിർത്തിയത്, `classifyProviderError`-ലെ വീണ്ടെടുക്കാവുന്ന cloud-code 403 ശാഖയെ
ഈ പദപ്രയോഗത്തിന് എത്തിച്ചേരാനാകാത്തതുമാക്കി, കാരണം `accountDeactivated` ആണ്
ആദ്യം വിലയിരുത്തപ്പെടുന്നത് — അതിനാൽ Gemini Code Assist-നായി
[#868](https://github.com/diegosouzapw/OmniRoute/pull/868),
[#6452](https://github.com/diegosouzapw/OmniRoute/pull/6452) എന്നിവയിൽ ചേർത്ത project-route വീണ്ടെടുക്കൽ ഒരിക്കലും പ്രവർത്തിക്കുമായിരുന്നില്ല.

അടുത്തടുത്തുള്ള മൂന്ന് **വേറിട്ട** സിഗ്നൽ പട്ടികകൾ നിരോധിത-കീവേഡ് കണ്ടെത്തലിന്റെ ഭാഗമല്ല:

- `CREDITS_EXHAUSTED_SIGNALS` — ബില്ലിംഗ്/ക്വോട്ട തീർന്നു (`insufficient_quota`,
  `credit_balance_too_low`, `payment required`, …) → ടെർമിനൽ `credits_exhausted`.
- `OAUTH_INVALID_TOKEN_SIGNALS` — **ടെർമിനൽ അല്ല**; ഒരു ടോക്കൺ പുതുക്കലിലൂടെ വീണ്ടെടുക്കാനാകും.
- `ACCOUNT_VERIFICATION_REQUIRED_SIGNALS` — **ടെർമിനൽ അല്ല**; ഓപ്പറേറ്റർ
  അപ്സ്ട്രീമിൽ അക്കൗണ്ട് വീണ്ടും സ്ഥിരീകരിക്കണം. ഇത് `open-sse/services/errorClassifier.ts`-ലാണ്
  ഉള്ളത് (മറ്റ് രണ്ടെണ്ണം `accountFallback.ts`-ലാണ്). മുകളിലെ വിഭാഗം കാണുക.

കുറിപ്പ്: **`rate limit`** / `429` പോലുള്ള സാധാരണ താൽക്കാലിക വാചകങ്ങൾ
rate-limit / connection-cooldown പാതയാണ് കൈകാര്യം ചെയ്യുന്നത്; അവ നിരോധന സിഗ്നലുകൾ **അല്ല**.

## കണ്ടെത്തൽ പ്രവാഹം

```
അപ്സ്ട്രീം പിശക് പ്രതികരണം
  → ബോഡി സ്ട്രിങ്ങാക്കി + ചെറിയക്ഷരത്തിലാക്കുന്നു
  → isAccountDeactivated(body): getMergedBannedSignals().some(sig => body.includes(sig))   [ഉപസ്ട്രിങ് പൊരുത്തം]
  → പൊരുത്തമുണ്ടോ?
      → കണക്ഷൻ testStatus = "banned"      (സ്ഥിരം — 1-വർഷ കൂൾഡൗൺ, ഒരിക്കലും സ്വയമേവ വീണ്ടെടുക്കില്ല)
      → `autoDisableBannedAccounts` ക്രമീകരണം ഓൺ ആണെങ്കിൽ, കൂടാതെ `autoDisableBannedScope`
        ഈ കണക്ഷനെ ഉൾക്കൊള്ളുന്നുവെങ്കിൽ (`all`, അല്ലെങ്കിൽ OAuth/cookie/session-നായി `subscription`)
        → isActive = false എന്നതും സജ്ജമാക്കുന്നു. സ്കോപ്പ്
        `subscription` ആയിരിക്കുമ്പോൾ പ്രീപെയ്ഡ് API കീകൾ സജീവമായി തുടരും.
      → അക്കൗണ്ട് തിരഞ്ഞെടുക്കുമ്പോൾ കണക്ഷൻ ഒഴിവാക്കപ്പെടുന്നു (സംയോജിത QUOTA_BLOCKING അവസ്ഥകൾ)
```

- പ്രതികരണ **ബോഡി**യിൽ നടത്തുന്ന **അക്ഷരവലുപ്പ വ്യത്യാസം പരിഗണിക്കാത്ത ഉപസ്ട്രിങ്** തിരയലാണ് പൊരുത്തനിർണ്ണയം
  (`isAccountDeactivated`, `accountFallback.ts`).
- നിരോധന-സിഗ്നൽ അടങ്ങിയ ബോഡി ലഭിച്ചാൽ, **ഏത്
  HTTP സ്റ്റാറ്റസിലും** സ്ഥിരമായ `banned` അന്തിമവൽക്കരണം സംഭവിക്കുന്നു (`markAccountUnavailable` → `checkFallbackError` വഴി). കൂടുതൽ
  പരിമിതമായ **`deactivated`** ലേബൽ (കണക്ഷനിൽ അധിക
  API കീകൾ ഇല്ലാത്തപ്പോൾ `isActive=false`) ഇൻലൈൻ `chatCore.ts` പാത **HTTP 401 / 403**-ൽ എഴുതുന്നു
  (`classifyProviderError` → `ACCOUNT_DEACTIVATED` വഴി വർഗ്ഗീകരിച്ചത്). അതേ
  `ACCOUNT_DEACTIVATED` സിഗ്നലിന് `markAccountUnavailable()` പാത
  `resolveTerminalConnectionStatus` വഴി ഒരു _വ്യത്യസ്ത_ അന്തിമ സ്റ്റാറ്റസ് —
  **`expired`** — എഴുതുന്നു എന്നത് ശ്രദ്ധിക്കുക. അതിനാൽ ഏത് പാതയാണ് പ്രതികരണം കൈകാര്യം ചെയ്തതെന്നതിനെ ആശ്രയിച്ച്, ഒരേ നിരോധനം
  `deactivated` അല്ലെങ്കിൽ `expired` ആയി പ്രത്യക്ഷപ്പെടാം. (പഴയ കോഡ് കമന്റിൽ "ഒരു 401 ബോഡിയിൽ ഈ സ്ട്രിങ്ങുകൾ അടങ്ങിയിരിക്കുമ്പോൾ" എന്ന് പറയുന്നു — അത്
  നിലവിലെ പെരുമാറ്റത്തെ പൂർണ്ണമായി പ്രതിഫലിപ്പിക്കുന്നില്ല.)
- അന്തിമ സ്റ്റാറ്റസുകൾ ഫിൽട്ടർ ചെയ്യുന്ന എല്ലായിടത്തും ഒരു `banned` കണക്ഷൻ തിരഞ്ഞെടുപ്പിൽ നിന്ന് ഒഴിവാക്കപ്പെടുന്നു
  (`isTerminalConnectionStatus`, സംയോജിത `QUOTA_BLOCKING_CONNECTION_STATUSES`).

## പരിധി — ഏതെല്ലാം പ്രൊവൈഡറുകളാണ് സ്കാൻ ചെയ്യുന്നത്

**എല്ലാ പ്രൊവൈഡറുകളും.** പരാജയപ്പെട്ട ഓരോ upstream അഭ്യർത്ഥനയും കടന്നുപോകുന്ന പൊതുവായ പിശക്-കൈകാര്യം ചെയ്യൽ പൈപ്പ്ലൈനിലാണ് ഈ പരിശോധന പ്രവർത്തിക്കുന്നത് — ഇത് OAuth/subscription scrapers-ൽ മാത്രം പരിമിതപ്പെടുത്തിയിട്ടില്ല. ഫലമായുണ്ടാകുന്ന അന്തിമാവസ്ഥ ഓരോ **connection**-നും പ്രത്യേകം ബാധകമാണ്, ഓരോ provider-നും അല്ല.

എന്നിരുന്നാലും, യഥാർത്ഥ ban സാധ്യതയുള്ള subscription/OAuth പ്രൊവൈഡറുകളെ (ChatGPT Web Codex, Claude Web, Codex, Muse Spark, Antigravity) മുൻനിർത്തിയാണ് ഉൾപ്പെടുത്തിയിട്ടുള്ള _സ്ട്രിങ്ങുകൾ_ തയ്യാറാക്കിയിരിക്കുന്നത്. ഒരു API-key പ്രൊവൈഡറിന്റെ പിശക് ബോഡിയിൽ ഏതെങ്കിലും substring അക്ഷരാർത്ഥത്തിൽ ഉൾപ്പെട്ടിട്ടുണ്ടെങ്കിൽ മാത്രമേ detector പ്രവർത്തിക്കൂ.

`autoDisableBannedScope` (`all` | `subscription`, സ്ഥിരസ്ഥിതി `all`) ഒരു പൊരുത്തം കണ്ടെത്തുമ്പോൾ `isActive=false` ആക്കണമോ എന്നത് നിയന്ത്രിക്കുന്നു. `subscription` എന്നത് login-style seats-നെ സൂചിപ്പിക്കുന്നു (പണമടച്ച subscriptions-ഉം സൗജന്യ അക്കൗണ്ടുകളും, web-cookie sessions ഉൾപ്പെടെ). prepaid API keys-ന് അത് ഇപ്പോഴും `testStatus=banned` രേഖപ്പെടുത്തും, പക്ഷേ അവയെ routing pool-ൽ നിലനിർത്തും. ഓരോ provider-നും ഓരോ account-നും പ്രത്യേകം override നൽകുന്നതാണ് ദീർഘകാല രൂപകൽപ്പന; global enum അതിന്റെ ആദ്യ പതിപ്പാണ്.

## ഇഷ്ടാനുസൃത banned keywords

**Security → Banned Keywords** എന്നതിൽ keywords ചേർക്കുകയോ നീക്കം ചെയ്യുകയോ ചെയ്യുക (`PATCH /api/settings` വഴി global `customBannedSignals` setting ആയി നിലനിൽക്കുന്നവ). അവ ഉൾപ്പെടുത്തിയിട്ടുള്ള ലിസ്റ്റിലേക്ക് **ചേർക്കപ്പെടുന്നതാണ്** — ഒരിക്കലും പകരംവയ്ക്കുന്നതല്ല — കൂടാതെ save ചെയ്യുമ്പോഴും startup സമയത്തും `setCustomBannedSignals()` വഴി hot-reload ചെയ്യപ്പെടും. ഓരോ keyword-നും പരമാവധി 200 അക്ഷരങ്ങളാണ്; array length-ന് പരിധിയില്ല.

**⚠ തെറ്റായ positive ഫലത്തിന്റെ സാധ്യത — കൃത്യമായ phrases തിരഞ്ഞെടുക്കുക.** മുഴുവൻ response body-യിലും raw substring match ഉപയോഗിച്ചാണ് കണ്ടെത്തൽ നടത്തുന്നത്; ഒരു match **സ്ഥിരമാണ്** (1 വർഷത്തെ cooldown, സ്വമേധയാ recovery). വളരെ പൊതുവായ keyword പൂർണ്ണമായും ആരോഗ്യകരമായ ഒരു connection-നെ ban ചെയ്തേക്കാം:

- **മോശം:** `quota`, `limit`, `error`, `denied` — പല താൽക്കാലിക പിശകുകളിലും ഇവ പ്രത്യക്ഷപ്പെടും.
- **നല്ലത്:** പൂർണ്ണമായ ban വാക്യങ്ങൾ, ഉദാ. `your account has been suspended for`,
  `account permanently banned`, `violation of our terms`.

യഥാർത്ഥ ban സമയത്ത് provider നൽകുന്ന ഏറ്റവും ദൈർഘ്യമേറിയതും അവ്യക്തതയില്ലാത്തതുമായ phrase തിരഞ്ഞെടുക്കുക. സംശയമുണ്ടെങ്കിൽ, ആദ്യം connection-ന്റെ `lastError` നിരീക്ഷിക്കുക, തുടർന്ന് അതേ കൃത്യമായ വാചകം ചേർക്കുക.

## Flag ചെയ്ത connection വീണ്ടെടുക്കൽ

അന്തിമ `banned` / `deactivated` അവസ്ഥകൾ **ഒരിക്കലും സ്വയമേവ വീണ്ടെടുക്കപ്പെടില്ല** (അവ proactive-recovery tick-ൽ നിന്ന് ഒഴിവാക്കിയിരിക്കുന്നു — `unavailable` cooldowns മാത്രമാണ് സ്വയം വീണ്ടെടുക്കുന്നത്). ഒരു operator അവ വ്യക്തമായി നീക്കം ചെയ്യണം:

1. **Connection വീണ്ടും പരിശോധിക്കുക** — dashboard-ലെ **Test** നടപടി
   (`POST /api/providers/{id}/test`); വിജയകരമായ probe `testStatus`-നെ
   `active` ആയി reset ചെയ്യുകയും പിശക് fields മായ്ക്കുകയും ചെയ്യും.
2. **വീണ്ടും authenticate ചെയ്യുക / credentials തിരുത്തുക** — OAuth പ്രൊവൈഡറുകൾക്കായി login
   / refresh flow വീണ്ടും പ്രവർത്തിപ്പിക്കുക; provider create/import routes `isActive = true` ആയി സജ്ജീകരിക്കും.
3. **Connection വീണ്ടും enable ചെയ്യുക** — auto-disable `isActive = false` ആയി സജ്ജീകരിച്ചിട്ടുണ്ടെങ്കിൽ
   (`all` scope, അല്ലെങ്കിൽ OAuth/cookie/session connection-ന് `subscription`),
   account ശരിയാക്കിയ ശേഷം അത് വീണ്ടും on ചെയ്യുക.

പ്രത്യേകമായ "clear ban flag" button ഇല്ല — recovery എന്നത് re-test, re-auth, അല്ലെങ്കിൽ re-enable ആണ്; ഇത് [RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md)-ലെ പൊതുവായ terminal-state നിയമവുമായി പൊരുത്തപ്പെടുന്നു.

## Probe വേർതിരിക്കൽ (model test-all)

ഒരു **probe-origin failure** (`runAsProbe`-നുള്ളിൽ പ്രവർത്തിപ്പിക്കുന്ന model test-all / health-check dispatches) pool-ൽ നിന്ന് ഒരു connection-നെയും ഒരിക്കലും നീക്കം ചെയ്യില്ല (#9817): അത് **ദൃശ്യപരതയ്ക്കായി രേഖപ്പെടുത്തപ്പെടും** (`last_error`, `last_error_type`, `error_code`,
`last_error_at`), എന്നാൽ **എല്ലാ** routing mutation-കളും ഒഴിവാക്കും — cooldowns, terminal
status (`banned` / `deactivated` / `credits_exhausted`), ഓരോ model-ന്റെയും lockouts,
provider circuit breaker, 5-minute quota cache, OAuth token refresh,
auto-disable എന്നിവ ഉൾപ്പെടെ. യഥാർത്ഥ request-path failure മാത്രമാണ് deactivate ചെയ്യുന്നത്. രേഖപ്പെടുത്തിയ
പിശക് dashboard-ൽ flag ചെയ്ത account ദൃശ്യമാക്കുന്നു; അതേസമയം അത്
traffic serve ചെയ്യുന്നത് തുടരും.

ഒരേയൊരു decision point `shouldIsolateProbeFailures()`
(`src/shared/utils/probeOrigin.ts`) ആണ്; probe-origin failure മൂലം
routing state മാറ്റാൻ കഴിയുന്ന **എല്ലാ** ഇടങ്ങളും ഇത് പരിശോധിക്കുന്നു:

- `markAccountUnavailable` (`auth.ts`) — record-only (`lastError` raw text,
  `lastErrorType`, `errorCode`, `lastErrorAt`; selection-time auto-decay trigger ചെയ്ത്
  record മായ്ച്ചുകളയാൻ സാധ്യതയുള്ള `backoffLevel` മനഃപൂർവം ഉൾപ്പെടുത്തിയിട്ടില്ല)
- `maybeAutoDisableBannedAccount` — auto-disable ഇല്ല
- `chatCore` — FORBIDDEN, ACCOUNT_DEACTIVATED, QUOTA_EXHAUSTED (record-only,
  terminal `credits_exhausted` ഇല്ല), GEO_BLOCKED (24h exclusion ഇല്ല),
  MODEL_NOT_FOUND (`lockModel` ഇല്ല), codex 429 account-rotation failover
  (`markCodexScopeRateLimited` ഇല്ല, നിലനിൽക്കുന്ന `rate_limited_until` ഇല്ല,
  session-affinity clear ഇല്ല), `persistCodexQuotaState` (quota-state write ഇല്ല,
  cache invalidation ഇല്ല), `recordKeyHealthStatus` (key-health rotator
  മാറ്റമില്ലാതെ തുടരുന്നു)
- OAuth refresh — executor base-ലെ proactive refresh
  (`base.ts` `execute()`, refresh-token rotation ഉപയോഗിക്കപ്പെടില്ല), കൂടാതെ
  `chatCore`-ലെ reactive 401/403 path (`expired` deactivation ഇല്ല)
- `chat.ts` — provider circuit breaker-ഉം 5-minute quota cache-ഉം
  (`markAccountExhaustedFrom429`) ഒരിക്കലും degrade ചെയ്യപ്പെടില്ല

രേഖപ്പെടുത്തിയ പിശക് dashboard-ൽ flag ചെയ്ത account ദൃശ്യമാക്കുന്നു;
അതേസമയം അത് traffic serve ചെയ്യുന്നത് തുടരും. ശ്രദ്ധിക്കുക: യഥാർത്ഥ path-ലെ `slice(0,100)` truncation-ൽ നിന്ന് വ്യത്യസ്തമായി, probe record **raw**
(മുറിച്ചിട്ടില്ലാത്ത) error text സൂക്ഷിക്കുന്നു.

test-all ഒരു maintenance tool ആയി ഉപയോഗിക്കുന്ന operators-ന് താഴെപ്പറയുന്ന ഏതെങ്കിലും മാർഗത്തിലൂടെ പഴയ behavior (probe ഒരു യഥാർത്ഥ generation ആയി കണക്കാക്കുന്നത്) പുനഃസ്ഥാപിക്കാം:

- `probeCanDisable` setting (`POST /api/settings`-ലേക്ക്
  `{"probeCanDisable": true}` നൽകി, അല്ലെങ്കിൽ നേരിട്ടുള്ള `key_value` DB edit), അല്ലെങ്കിൽ
- feature flag **`PROBE_CAN_DISABLE=true`** (env അല്ലെങ്കിൽ DB override; setting-നെക്കാൾ മുൻഗണന ലഭിക്കും).

Fail-safe: flag അല്ലെങ്കിൽ settings lookup പിശക് സൃഷ്ടിച്ചാൽ, isolation ON ആയി തുടരും.
