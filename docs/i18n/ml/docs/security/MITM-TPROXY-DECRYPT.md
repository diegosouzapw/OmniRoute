TPROXY സുതാര്യ ഡീക്രിപ്റ്റ് എന്നത് [Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) /
[AgentBridge](../frameworks/AGENTBRIDGE.md) MITM സ്റ്റാക്കിനായുള്ള OmniRoute-ന്റെ
**അഞ്ചാമത്തെ ക്യാപ്ചർ മോഡ്** ആണ്. കേർണൽ TPROXY + പോളിസി റൂട്ടിംഗ് ഉപയോഗിച്ച് Linux-ലെ
ലോക്കൽ ഔട്ട്ബൗണ്ട് HTTPS ട്രാഫിക് ഇത് തടഞ്ഞുപിടിക്കുകയും **ഡീക്രിപ്റ്റ്** ചെയ്യുകയും ചെയ്യുന്നു —
`/etc/hosts` സ്പൂഫ് ചെയ്യാതെയും OS-വ്യാപകമായ സിസ്റ്റം-പ്രോക്സി ക്രമീകരണങ്ങളിൽ
**മാറ്റം വരുത്താതെയും**. ഇത് ഹെഡ്ലെസ് പരിതസ്ഥിതികൾക്ക് അനുയോജ്യമാണ്
(വൃത്തിയാക്കേണ്ട DNS തിരുത്തലുകളില്ല), കൂടാതെ റീബൂട്ട് ചെയ്യുമ്പോൾ ഫയർവാൾ നിയമങ്ങൾ സ്വയമേവ നീക്കം ചെയ്യപ്പെടും.

മറ്റ് ക്യാപ്ചർ മോഡുകളിൽനിന്ന് വ്യത്യസ്തമായി, TPROXY-ക്ക് ഓരോ ഹോസ്റ്റിനും പ്രത്യേകം സജ്ജീകരണം ആവശ്യമില്ല:
ടാർഗറ്റ് പോർട്ടിലേക്കുള്ള **ഏത്** ഡെസ്റ്റിനേഷൻ ഹോസ്റ്റിനെയും ഇത് സുതാര്യമായി തടഞ്ഞുപിടിക്കുന്നു,
ഓരോ SNI ഹോസ്റ്റ്നെയിമിനുമായി തത്സമയം നൽകുന്ന ലീഫ് സർട്ടിഫിക്കറ്റ് ഉപയോഗിച്ച് TLS അവസാനിപ്പിക്കുന്നു,
ഡീക്രിപ്റ്റ് ചെയ്ത കൈമാറ്റം ക്യാപ്ചർ ചെയ്യുന്നു, തുടർന്ന് യഥാർത്ഥ ഡെസ്റ്റിനേഷനിലേക്കുള്ള അഭ്യർത്ഥന
വീണ്ടും എൻക്രിപ്റ്റ് ചെയ്യുന്നു.

> **Linux-ൽ മാത്രം, root-ന് മാത്രം, സമ്മതപ്രകാരം മാത്രം.** ഈ മോഡിന് Linux, C ടൂൾചെയിൻ
> ഉപയോഗിച്ച് ബിൽഡ് ചെയ്ത ഒരു നേറ്റീവ് ആഡോൺ, കൂടാതെ **CAP_NET_ADMIN** ശേഷി (സാധാരണയായി root) എന്നിവ ആവശ്യമാണ്. ഇത്
> ലൂപ്പ്ബാക്ക്-മാത്രമുള്ള AgentBridge API-യുടെ പിന്നിൽ നിയന്ത്രിക്കപ്പെടുകയും ഡിഫോൾട്ടായി പ്രവർത്തനരഹിതമാക്കുകയും ചെയ്തിരിക്കുന്നു. ഏത്
> ഹോസ്റ്റിനും ഒപ്പിടാൻ കഴിയുന്ന വിശ്വസനീയ MITM CA ശക്തമായൊരു ശേഷിയാണ് — [§6 സുരക്ഷ](#6-security) കാണുക.

**സോഴ്സ്:** `src/mitm/tproxy/`

## §1 ഇത് എന്താണ്, എപ്പോൾ ഉപയോഗിക്കണം

മറ്റ് നാല് ക്യാപ്ചർ മോഡുകൾക്കും ഓരോ പരിമിതിയുണ്ട്:

| മോഡ്                     | ട്രാഫിക് എങ്ങനെ വഴിതിരിച്ചുവിടുന്നു                    | പരിമിതി                                            |
| ------------------------ | ------------------------------------------------------ | -------------------------------------------------- |
| AgentBridge              | നിശ്ചിത ഹോസ്റ്റ് സെറ്റിന്റെ `/etc/hosts` DNS സ്പൂഫിംഗ് | രജിസ്റ്റർ ചെയ്ത IDE-ഏജന്റ് ഹോസ്റ്റുകൾ മാത്രം       |
| കസ്റ്റം ഹോസ്റ്റുകൾ       | ഓരോ ഹോസ്റ്റിനുമുള്ള `/etc/hosts` DNS സ്പൂഫിംഗ്         | ഓരോ ഹോസ്റ്റിനും ഒരു എൻട്രി; hosts തിരുത്താൻ sudo   |
| HTTP_PROXY               | `HTTP_PROXY`/`HTTPS_PROXY` env                         | env var മാനിക്കുന്ന ആപ്പുകൾ മാത്രം                 |
| സിസ്റ്റം-വ്യാപക പ്രോക്സി | OS പ്രോക്സി ക്രമീകരണങ്ങൾ                               | ആഗോള സ്റ്റേറ്റിൽ മാറ്റം വരുത്തുന്നു; പഴയപടിയാക്കണം |

പകരം TPROXY സുതാര്യ ഡീക്രിപ്റ്റ് **കേർണൽ** തലത്തിൽ ട്രാഫിക് വഴിതിരിച്ചുവിടുന്നു.
`mangle OUTPUT` ചെയിനിൽ ഒരു ടാർഗറ്റ് പോർട്ടിലേക്കുള്ള (ഡിഫോൾട്ട് `443`) പുതിയ ലോക്കൽ ഔട്ട്ബൗണ്ട് TCP കണക്ഷനുകൾക്ക്
ഇത് മാർക്ക് നൽകുന്നു, ഒരു `ip rule` മാർക്ക് ചെയ്ത പാക്കറ്റുകളെ ലോക്കൽ ഡെലിവറിയിലേക്ക് വീണ്ടും റൂട്ട് ചെയ്യുന്നു,
വീണ്ടും പ്രവേശിക്കുമ്പോൾ `mangle PREROUTING`-ലെ `TPROXY` ടാർഗറ്റ് അവയെ ഒരു
**IP_TRANSPARENT** ലിസണറിന് കൈമാറുന്നു — തുടർന്ന് അത് TLS അവസാനിപ്പിക്കുകയും പ്ലെയിൻടെക്സ്റ്റ് ക്യാപ്ചർ ചെയ്യുകയും ചെയ്യുന്നു.

ഇനിപ്പറയുന്ന സവിശേഷതകളുള്ള ഒരു പ്രോസസിൽനിന്നുള്ള ട്രാഫിക് ക്യാപ്ചർ ചെയ്ത് ഡീക്രിപ്റ്റ് ചെയ്യേണ്ടപ്പോൾ ഇത് ഉപയോഗിക്കുക:

- AgentBridge രജിസ്റ്റർ ചെയ്യാത്ത ഒരു ഹോസ്റ്റുമായി ആശയവിനിമയം നടത്തുന്നു, കൂടാതെ
- `HTTP_PROXY` മാനിക്കുന്നില്ല, കൂടാതെ
- സിസ്റ്റം-വ്യാപക പ്രോക്സി മാറ്റം വരുത്തി അതിനെ ബാധിക്കാൻ നിങ്ങൾ ആഗ്രഹിക്കുന്നില്ല.

തടഞ്ഞുപിടിക്കൽ കേർണലിൽ നടക്കുന്നതിനാൽ, ഉത്ഭവ പ്രോസസിന് **കോൺഫിഗറേഷൻ മാറ്റമൊന്നും
ആവശ്യമില്ല** — എന്നാൽ OmniRoute ഇൻസ്റ്റാൾ ചെയ്യുന്ന ഡൈനാമിക് CA-യെ പ്രോസസ് വിശ്വസിക്കണം
([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) കാണുക).

## §2 ആവശ്യകതകൾ

| ആവശ്യകത            | വിശദാംശം                                                                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **OS**             | Linux മാത്രം — **IP_TRANSPARENT** എന്നത് Linux-ൽ മാത്രം ലഭ്യമായ socket option ആണ്. മറ്റെല്ലാ പ്ലാറ്റ്ഫോമുകളിലും loader "unavailable" എന്ന് മടക്കിനൽകുന്നു.         |
| **Privilege**      | transparent socket സൃഷ്ടിക്കാനും `iptables`/`ip` നിയമങ്ങൾ പ്രയോഗിക്കാനും **CAP_NET_ADMIN** capability ആവശ്യമാണ് — പ്രായോഗികമായി, root ആയി പ്രവർത്തിപ്പിക്കുക.      |
| **Native addon**   | ഒരു ചെറിയ N-API addon (`src/mitm/tproxy/native/transparent.c`) build ചെയ്യുകയോ prebuild ആയി വിതരണം ചെയ്യുകയോ വേണം. [§3](#3-the-native-ip_transparent-addon) കാണുക. |
| **Kernel modules** | `TPROXY`, `mangle`, `mark` match പിന്തുണയുള്ള `iptables` (kernel 6.8.0-ൽ സാധൂകരിച്ചത്).                                                                            |

**സുഗമമായ നിലവാരത്തകർച്ച:** ഏതെങ്കിലും ആവശ്യകത ലഭ്യമല്ലെങ്കിൽ (Linux അല്ലാത്തത്, toolchain ഇല്ലാത്തത്,
addon build ചെയ്തിട്ടില്ലാത്തത്), addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
exception എറിയുന്നതിന് പകരം `null` മടക്കിനൽകുന്നു. തുടർന്ന് capture-mode status
`available: false` എന്ന് റിപ്പോർട്ട് ചെയ്യുന്നു, dashboard toggle
"TPROXY decrypt requires Linux + root + the native addon" എന്ന tooltip സഹിതം **പ്രവർത്തനരഹിതമാക്കപ്പെടുന്നു**,
അതേസമയം OmniRoute-ന്റെ ശേഷിക്കുന്ന ഭാഗങ്ങൾ തുടർന്നും പ്രവർത്തിക്കുന്നു.

## §3 Native IP_TRANSPARENT addon

Node-ന്റെ `net` module-ന് `bind()`-ന് _മുമ്പ്_ `setsockopt(IP_TRANSPARENT)` ചെയ്യാൻ കഴിയില്ല;
TPROXY-യ്ക്ക് ഇത് ആവശ്യമാണ് (അല്ലെങ്കിൽ kernel തിരിച്ചുവിട്ട packet-ുകൾ ഉപേക്ഷിക്കും). ഈ addon
(`src/mitm/tproxy/native/transparent.c`, `binding.gyp` വഴി build ചെയ്യുന്നത്) മൂന്ന് function-ുകൾ
ലഭ്യമാക്കുന്ന ഒരു ചെറിയ N-API module ആണ്; ഇവ `transparentSocket.ts` വഴി ഉപയോഗിക്കുന്നു:

| Addon function                        | Socket പ്രവർത്തനം                                                                                 | ഉപയോഗിക്കുന്നത്                                                                          |
| ------------------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`; raw fd മടക്കിനൽകുന്നു | transparent capture listener-നായി (Node, `server.listen({ fd })` വഴി fd ഏറ്റെടുക്കുന്നു) |
| `setSocketMark(fd, mark)`             | നിലവിലുള്ള fd-യിൽ `setsockopt` **SO_MARK** പ്രയോഗിക്കുന്നു                                        | anti-loop-നായി (proxy-യുടെ സ്വന്തം socket-ുകളിൽ mark ഇടുന്നു)                            |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()`-ന് **മുമ്പ്** `socket()` + **SO_MARK**; fd മടക്കിനൽകുന്നു                | വീണ്ടും encrypt ചെയ്ത upstream forward-നായി (SYN mark വഹിക്കുന്നു)                       |

യഥാർത്ഥ destination `socket.localAddress`/`localPort`-ൽ നിന്ന് വായിക്കുന്നു — TPROXY
അത് നിലനിർത്തുന്നതിനാൽ **SO_ORIGINAL_DST**/NAT lookup ആവശ്യമില്ല.

### Addon build ചെയ്യുന്നത്

```bash
npm run build:native:tproxy      # src/mitm/tproxy/native-ലേക്ക് cd ചെയ്ത് node-gyp rebuild പ്രവർത്തിപ്പിക്കുന്നു
                                 # -> native/build/Release/transparent.node
```

- `npm run build` നടക്കുമ്പോൾ, `scripts/build/build-tproxy-native.mjs` `node-gyp
rebuild` പ്രവർത്തിപ്പിക്കുന്നു. ഇത് **Linux-ൽ മാത്രമുള്ളതും പരാജയം മൊത്തം build-നെ ബാധിക്കാത്തതുമാണ്** — toolchain ഇല്ലെങ്കിൽ
  capture mode ലഭ്യമാകാതെ മാത്രമേ ഇരിക്കൂ.
- `assembleStandalone.mjs`, `build/Release/transparent.node`-നെ
  standalone bundle-ലേക്ക് പകർത്തുന്നു; `transparentSocket.ts` അതിനെ module-relative ആയും
  cwd-relative ആയും (`<cwd>/src/mitm/tproxy/native/...`) കണ്ടെത്തുന്നു.
- `build/`, `prebuilds/` എന്നിവ git-ignored ആണ് — binary **build ചെയ്യപ്പെടുന്നു, ഒരിക്കലും
  commit ചെയ്യപ്പെടുന്നില്ല**.

Loader മുൻഗണനാക്രമത്തിൽ താഴെപ്പറയുന്നവ പരിശോധിക്കുന്നു:
`native/build/Release/transparent.node`, തുടർന്ന് `native/prebuilds/transparent.node`
(module-relative ആയും `<cwd>/src/mitm/tproxy/`-ന് കീഴിലും).

## §4 ഓരോ-SNI-യ്ക്കുമുള്ള ഡൈനാമിക് CA-യും ട്രസ്റ്റ്-സ്റ്റോർ ഇൻസ്റ്റാളറും

> **#6684 അപ്ഡേറ്റ്:** AgentBridge സ്റ്റാറ്റിക് സെർവർ (`src/mitm/server.cjs`) ഇപ്പോൾ
> ഒരൊറ്റ സ്റ്റാറ്റിക് സ്വയം-സൈൻ ചെയ്ത ലീഫിന് പകരം ഇതേ CA/ലീഫ് ആർക്കിടെക്ചർ മാതൃക
> പങ്കിടുന്നു. ഇത് ഒരു **വ്യത്യസ്ത** CA ഇൻസ്റ്റൻസ്
> (`src/mitm/cert/rootCa.ts`, `<DATA_DIR>/mitm/ca.key`/`ca.crt`-ൽ സ്ഥിരമായി സംഭരിക്കുന്നത്)
> ഉപയോഗിക്കുകയും, മുമ്പേ നിലവിലുള്ള `omniroute-mitm.crt` ട്രസ്റ്റ്-സ്റ്റോർ സ്ലോട്ടിൽ
> ഇൻസ്റ്റാൾ ചെയ്യുകയും ചെയ്യുന്നു (അവിടെയുള്ള പഴയ ഒരൊറ്റ ലീഫിനെ ഇത് മാറ്റിസ്ഥാപിക്കുന്നു —
> ഇരട്ട-ട്രസ്റ്റ് ക്ലീനപ്പ് ആവശ്യമില്ല); താഴെയുള്ള TPROXY-യുടെ സ്വന്തം
> `omniroute-tproxy-ca.crt` സ്ലോട്ടിൽനിന്ന് ഇത് പൂർണ്ണമായും വേർതിരിച്ചിരിക്കുന്നു.
> പുതിയ AgentBridge ഇൻസ്റ്റാളുകൾക്ക് CA മോഡൽ സ്വയമേവ ലഭിക്കും; പഴയ സ്റ്റാറ്റിക്
> ലീഫിനെ ഇതിനകം വിശ്വസിച്ചിരുന്ന ഒരു ഇൻസ്റ്റാൾ, ഓപ്പറേറ്റർ
> `MITM_ROOT_CA_ENABLED=true` വഴി അത് തിരഞ്ഞെടുക്കുന്നതുവരെ അതുതന്നെ ഉപയോഗിക്കുന്നത്
> തുടരും (`src/mitm/cert/migration.ts` കാണുക) — **ഏത്** ഹോസ്റ്റിനായും ഒരു ലീഫ്
> സൈൻ ചെയ്യാൻ കഴിയുന്ന വിശ്വസനീയമായ MITM CA, പഴയ സ്ഥിരമായ-SAN ലീഫിനെക്കാൾ
> ഗണ്യമായി ശക്തമാണ്; അതിനാൽ ഇതിനകം വിശ്വസനീയമായ ഒരു ഇൻസ്റ്റാളിൽ ഈ മാറ്റം
> ഒരിക്കലും നിശ്ശബ്ദമായി നടക്കില്ല.

ചരിത്രപരമായി, സ്റ്റാറ്റിക് AgentBridge MITM സർട്ടിഫിക്കറ്റ് പ്രവർത്തിച്ചിരുന്നത്
AgentBridge ഒരു **സ്ഥിരമായ** ഹോസ്റ്റ് സെറ്റിന്റെ DNS സ്പൂഫ് ചെയ്യുന്നതിനാൽ മാത്രമാണ്
(ഇപ്പോൾ അത് താഴെയുള്ള മോഡലുമായി ഏകീകരിച്ചിരിക്കുന്നു). TPROXY **ഏത്** ഹോസ്റ്റുകളെയും
തടഞ്ഞുപിടിക്കുന്നു; അതിനാൽ ക്ലയന്റ് അഭ്യർത്ഥിക്കുന്ന ഏത് SNI-യ്ക്കും അതിന്റെ ലിസണർ
സാധുവായ ഒരു ലീഫ് അവതരിപ്പിക്കണം — വെറും 4 antigravity ഹോസ്റ്റുകൾക്ക് പകരം
പൂർണ്ണമായ `MITM_TOOL_HOSTS` സെറ്റിനും (9 ടൂൾ എൻട്രികൾ) ഇപ്പോൾ AgentBridge-ന്
ഇതേ ആവശ്യകതയുണ്ട്.

### ഡൈനാമിക് CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore`, `selfsigned` ഡിപ്പൻഡൻസിയെ അടിസ്ഥാനമാക്കി നിർമ്മിച്ച ഒരു ലോക്കൽ
CA പ്രവർത്തിപ്പിക്കുന്നു, അത്:

- `generateMitmCa()` വഴി ദീർഘകാല സാധുതയുള്ള ഒരു CA സൃഷ്ടിക്കുന്നു (CN
  `"OmniRoute MITM CA"`, 10 വർഷത്തെ സാധുത, `basicConstraints CA=true` +
  `keyUsage keyCertSign,cRLSign`, 2048-ബിറ്റ് RSA / SHA-256).
- `issueLeafCert()` വഴി **ഓരോ SNI ഹോസ്റ്റ്നെയിമിനും ആവശ്യാനുസരണം ഒരു ലീഫ്**
  നൽകുന്നു (1 വർഷത്തെ സാധുത, `subjectAltName` = SNI ഹോസ്റ്റ്), കൂടാതെ ഓരോ
  ഹോസ്റ്റ്നെയിമിനും ഒരു `tls.SecureContext` കാഷ് ചെയ്യുന്നു.
- TLS അവസാനിപ്പിക്കുന്ന സെർവറിനായി `createSNICallback()` ലഭ്യമാക്കുന്നു
  ([§5](#5-how-decrypt-and-capture-work) കാണുക).
- റീസ്റ്റാർട്ടുകൾക്കിടയിലും CA സ്ഥിരമായി നിലനിർത്താൻ ഒരു `existingCa` ഉപയോഗിച്ച്
  നിർമ്മിക്കാനാകും (അതുവഴി ട്രസ്റ്റ് സ്റ്റോർ വീണ്ടും ഇൻസ്റ്റാൾ ചെയ്യേണ്ടതില്ല).

CA സ്വകാര്യ കീ **ഒരിക്കലും മെഷീനിന് പുറത്തേക്ക് പോകുന്നില്ല**.

### ട്രസ്റ്റ്-സ്റ്റോർ ഇൻസ്റ്റാളർ (`src/mitm/tproxy/caTrust.ts`)

തടഞ്ഞുപിടിക്കപ്പെട്ട ക്ലയന്റ് ഡൈനാമിക് CA-യെ വിശ്വസിക്കണം; അതിനാൽ ക്യാപ്ചർ മോഡ്
ആരംഭിക്കുമ്പോൾ CA സർട്ടിഫിക്കറ്റ് OS ട്രസ്റ്റ് സ്റ്റോറിലെ ഒരു **സമർപ്പിത സ്ലോട്ടിൽ** —
`omniroute-tproxy-ca.crt` (`TPROXY_CA_CERT_NAME` കോൺസ്റ്റന്റ്) — ഇൻസ്റ്റാൾ ചെയ്യുന്നു.
ഇത് സ്റ്റാറ്റിക് MITM സർട്ടിഫിക്കറ്റിന്റെ സ്ലോട്ടിൽനിന്ന് (`omniroute-mitm.crt`)
വേർതിരിച്ച് സൂക്ഷിക്കുന്നതിനാൽ അവ രണ്ടും ഒരിക്കലും പരസ്പരം തിരുത്തിയെഴുതില്ല.

`installTproxyCa(caPem, sudoPassword?)` ഡിസ്ട്രിബ്യൂഷന്റെ ആങ്കർ ഡയറക്ടറി
കണ്ടെത്തുകയും (ക്രമത്തിൽ: Debian ശൈലി ആദ്യം), അതിന് അനുയോജ്യമായ റിഫ്രഷ് കമാൻഡ്
പ്രവർത്തിപ്പിക്കുകയും ചെയ്യുന്നു:

| ആങ്കർ ഡയറക്ടറി                              | റിഫ്രഷ് കമാൻഡ്           |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

ഇൻസ്റ്റാളേഷൻ ആദ്യം PEM-നെ ഒരു താൽക്കാലിക ഫയലിലേക്ക് സ്റ്റേജ് ചെയ്യുന്നു; തുടർന്ന്
(പ്രിവിലേജ്ഡ് ആയി) ആങ്കർ ഡയറക്ടറിയിൽ `mkdir -p` പ്രവർത്തിപ്പിക്കുകയും, സ്റ്റേജ്
ചെയ്ത ഫയൽ അതിലേക്ക് `cp` ചെയ്യുകയും, റിഫ്രഷ് കമാൻഡ് പ്രവർത്തിപ്പിക്കുകയും ചെയ്യുന്നു.
`uninstallTproxyCa()` സമർപ്പിത സ്ലോട്ട് മാത്രം നീക്കംചെയ്യുന്നു (സ്റ്റാറ്റിക് MITM
സർട്ടിഫിക്കറ്റിനെ മാറ്റമില്ലാതെ നിലനിർത്തുന്നു), തുടർന്ന് റിഫ്രഷ് ചെയ്യുന്നു —
Linux അല്ലാത്ത സിസ്റ്റങ്ങളിൽ ഇത് ഒന്നും ചെയ്യില്ല.

എല്ലാ പ്രിവിലേജ്ഡ് കമാൻഡുകളും `execFileWithPassword`
(`src/mitm/systemCommands.ts`) വഴിയാണ് പ്രവർത്തിക്കുന്നത് — **ആർഗ് അറേകളോടുകൂടിയ,
ഷെൽ ഇല്ലാത്ത, സ്ട്രിംഗ് ഇന്റർപൊളേഷൻ ഇല്ലാത്ത** `spawn` (കർശന നിയമം #13).
പ്രോസസ് root ആയി പ്രവർത്തിക്കുമ്പോൾ (ഉദാ. VPS), ടാർഗറ്റ് നേരിട്ട് പ്രവർത്തിക്കും,
പാസ്വേഡ് ആവശ്യമില്ല; root അല്ലാത്ത ഡെസ്ക്ടോപ്പിൽ `sudoPassword`, stdin-ൽ
`sudo -S` വഴി നൽകപ്പെടുന്നു.

> ട്രസ്റ്റ്-സ്റ്റോർ ഇൻസ്റ്റാളിന് അനുമതി നൽകാനായി ഡെസ്ക്ടോപ്പിന്റെ `sudoPassword`
> POST ബോഡിയിൽ നൽകുന്നു; പ്രോസസ് root ആയി പ്രവർത്തിക്കുമ്പോൾ അത് പൂർണ്ണമായും
> അവഗണിക്കപ്പെടുന്നു.

## §5 ഡീക്രിപ്ഷനും ക്യാപ്ചറും എങ്ങനെ പ്രവർത്തിക്കുന്നു

പൈപ്പ്ലൈൻ (എല്ലാം `src/mitm/tproxy/`-ന് കീഴിൽ):

```
ലോക്കൽ ആപ്പ്  ──TCP/443──▶  mangle OUTPUT കണക്ഷനെ അടയാളപ്പെടുത്തുന്നു (fwmark)
                            ip rule → ലോക്കൽ റൂട്ട് പട്ടിക → lo
                            mangle PREROUTING TPROXY → IP_TRANSPARENT ലിസണർ (പോർട്ട് 8443)
                                │  captureMode.ts: socket.localAddress-ൽനിന്ന് യഥാർത്ഥ ലക്ഷ്യസ്ഥാനം വായിക്കുന്നു
                                ▼
                            tlsCapture.ts:
                              1. ഓരോ SNI-ക്കും പ്രത്യേകമായ ലീഫ് ഉപയോഗിച്ച് CLIENT-ന്റെ TLS അവസാനിപ്പിക്കുന്നു (dynamicCert)
                              2. ആന്തരിക http.Server ഡീക്രിപ്റ്റ് ചെയ്ത പ്ലെയിൻടെക്സ്റ്റ് പാർസ് ചെയ്യുന്നു
                              3. ക്യാപ്ചർ → source: "tproxy" ഉപയോഗിച്ച് globalTrafficBuffer.push()
                                 (sanitizeHeaders + maskSecret പ്രയോഗിക്കുന്നു)
                              4. ബൈപാസ്-മാർക്ക് ചെയ്ത സോക്കറ്റിലൂടെ യഥാർത്ഥ ലക്ഷ്യസ്ഥാനത്തേക്ക്
                                 വീണ്ടും എൻക്രിപ്റ്റ് ചെയ്ത് ഫോർവേഡ് ചെയ്യുന്നു (connectMarked, ആന്റി-ലൂപ്പ്)
                                │
                                ▼
                            യഥാർത്ഥ അപ്സ്ട്രീം (api.example.com)
```

- **TLS അവസാനിപ്പിക്കൽ** (`createTlsCaptureServer`): ഡൈനാമിക് CA-യുടെ SNI കോൾബാക്ക് ഉപയോഗിച്ച് അസംസ്കൃതമായി ഇന്റർസെപ്റ്റ് ചെയ്ത
  സോക്കറ്റിനെ സർവർ-സൈഡ് `tls.TLSSocket`-ൽ റാപ്പ് ചെയ്യുകയും തുടർന്ന് ഡീക്രിപ്റ്റ് ചെയ്ത സ്ട്രീം ഒരു ആന്തരിക
  `http.Server`-ന് കൈമാറുകയും ചെയ്യുന്നു (സാധാരണ MITM അവസാനിപ്പിക്കൽ രീതി). ഹാംഗ് ആയ ഒരു ടണൽ
  ഫയൽ ഡിസ്ക്രിപ്റ്ററുകൾ തീർക്കാതിരിക്കാൻ സോക്കറ്റുകളുടെ ആയുസ്സ് `MITM_IDLE_TIMEOUT_MS` ഉപയോഗിച്ച് പരിമിതപ്പെടുത്തിയിരിക്കുന്നു.
- **ക്യാപ്ചർ** (`handleDecryptedRequest`): `source: "tproxy"` ഉപയോഗിച്ച് ഒരു `InterceptedRequest`
  പുഷ് ചെയ്യുന്നു; സ്റ്റാറ്റസ് `"in-flight"` ആയി ആരംഭിക്കുന്നു, കൂടാതെ ബഫറിലേക്ക് പ്രവേശിക്കുന്നതിന് മുമ്പ്
  ഹെഡറുകളിൽ `sanitizeHeaders()`-ഉം ബോഡികളിൽ `maskSecret()`-ഉം പ്രയോഗിക്കുന്നു.
  തുടർന്ന് റെസ്പോൺസ്, വലുപ്പങ്ങൾ, ലേറ്റൻസി എന്നിവ ഉപയോഗിച്ച് എൻട്രി അപ്ഡേറ്റ് ചെയ്യുന്നു.
- **വീണ്ടും എൻക്രിപ്റ്റ് ചെയ്ത ഫോർവേഡ്** (`createForward` / `realForward`): യഥാർത്ഥ ലക്ഷ്യസ്ഥാനത്തേക്ക്
  വീണ്ടും എൻക്രിപ്റ്റ് ചെയ്യുന്നു. `rejectUnauthorized`-ന്റെ ഡിഫോൾട്ട് **`true`** ആണ് (ഡിഫോൾട്ടായി
  സുരക്ഷിതം) — ക്ലയന്റ് അഭ്യർത്ഥിച്ച SNI/Host-ന് എതിരായി അപ്സ്ട്രീം സർട്ടിഫിക്കറ്റ് പരിശോധിക്കുന്നതിനാൽ,
  യഥാർത്ഥ ക്ലയന്റ് നിരസിക്കുമായിരുന്നവ തന്നെയാണ് പ്രോക്സിയും നിരസിക്കുന്നത്.

### ആന്റി-ലൂപ്പ് (SO_MARK)

നിയമങ്ങൾ പുതിയ ലോക്കൽ ഔട്ട്ബൗണ്ട് കണക്ഷനുകളെ അടയാളപ്പെടുത്തുന്നതിനാൽ, പ്രോക്സിയുടെ **സ്വന്തം**
വീണ്ടും എൻക്രിപ്റ്റ് ചെയ്ത ഫോർവേഡ് സാധാരണയായി വീണ്ടും ഇന്റർസെപ്റ്റ് ചെയ്യപ്പെടും — അതൊരു അനന്തമായ ലൂപ്പാണ്.
ബൈപാസ് സോക്കറ്റ് മാർക്ക് (**SO_MARK**) ഉപയോഗിച്ച് ഫോർവേഡ് പാത്ത് ഇതിനെ പ്രതിരോധിക്കുന്നു:

- `realForward` അതിന്റെ അപ്സ്ട്രീം സോക്കറ്റ് `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  വഴി തുറക്കുന്നു — `DEFAULT_BYPASS_MARK = 0x539` — ഇത് `connect()`-ന് **മുമ്പ്** **SO_MARK**
  സജ്ജീകരിക്കുന്നതിനാൽ, ഫോർവേഡിന്റെ SYN ബൈപാസ് മാർക്ക് വഹിക്കുന്നു.
- ഇതിനകം ബൈപാസ് മാർക്ക് വഹിക്കുന്ന കണക്ഷനുകളെ `mangle OUTPUT` നിയമം ഒഴിവാക്കുന്നു
  (`-m mark ! --mark <bypassMark>`), അതിനാൽ പ്രോക്സിയുടെ ഫോർവേഡ് വീണ്ടും മാർക്ക് ചെയ്യപ്പെടുകയോ
  TPROXY-യിലേക്ക് വീണ്ടും പ്രവേശിക്കുകയോ ചെയ്യുന്നില്ല.

> നടപ്പാക്കൽ കുറിപ്പ്: ബൈപാസ്-മാർക്ക് ചെയ്ത സോക്കറ്റ് ഏജന്റിന്റെ `createConnection`-ൽ
> ഇൻസ്റ്റാൾ ചെയ്യണം (ഒരു ഏജന്റ് നിലവിലുണ്ടെങ്കിൽ `https.request({ createConnection })` നിശ്ശബ്ദമായി
> അവഗണിക്കപ്പെടുന്നു); അല്ലാത്തപക്ഷം ഫോർവേഡ് മാർക്ക് ചെയ്യാത്ത ഒരു സോക്കറ്റ് തുറക്കുകയും ലൂപ്പ്
> വീണ്ടും വരികയും ചെയ്യും. ഇത് e2e ഉപയോഗിച്ച് സാധൂകരിച്ച ആന്റി-ലൂപ്പ് പരിഹാരമായിരുന്നു.

## §7 ട്രാൻസാക്ഷണൽ ഫയർവാൾ പ്രയോഗം / പഴയപടിയാക്കൽ

ഒരു ക്രാഷും ഒരിക്കലും ഒരു `mangle` നിയമമോ കാലഹരണപ്പെട്ട റൂട്ടോ അവശേഷിപ്പിക്കരുത്. കമാൻഡ് ബിൽഡറും
(`src/mitm/tproxy/commands.ts`) റണ്ണറും (`src/mitm/tproxy/setup.ts`)
**പഴയപടിയാക്കൽ എന്നത് പ്രയോഗത്തിന്റെ കൃത്യമായ വിപരീതം, വിപരീത ക്രമത്തിൽ** ആണെന്ന് ഉറപ്പുനൽകുന്നു.

`applyTproxy(cfg)` പ്രയോഗ കമാൻഡുകൾ ക്രമത്തിൽ പ്രവർത്തിപ്പിക്കുന്നു; **ഏതെങ്കിലും** പരാജയം ഉണ്ടായാൽ,
സാധ്യമായത്ര മികച്ച രീതിയിൽ പൂർണ്ണമായ `revertTproxy(cfg)` പ്രവർത്തിപ്പിച്ചശേഷം പിശക് വീണ്ടും ഉയർത്തുന്നു — അതിനാൽ ഫയർവാൾ
ഒന്നുകിൽ പൂർണ്ണമായി പ്രയോഗിക്കപ്പെടും, അല്ലെങ്കിൽ പൂർണ്ണമായി പഴയപടിയാക്കപ്പെടും; ഒരിക്കലും ഭാഗികമായി പ്രയോഗിച്ച നിലയിലാകില്ല. `revertTproxy(cfg)`
വിപരീത കമാൻഡുകൾ വിപരീത ക്രമത്തിൽ പ്രവർത്തിപ്പിക്കുകയും പരാജയങ്ങൾ അവഗണിക്കുകയും ചെയ്യുന്നു (ഐഡംപൊട്ടന്റ് — നിബന്ധനകളില്ലാതെ
വിളിക്കുന്നത് സുരക്ഷിതമാണ്, ഉദാ. AgentBridge `repairMitm()` ക്ലീനപ്പിൽ നിന്ന്).

ഏതെങ്കിലും കമാൻഡിന് മുമ്പ് `validateTproxyConfig(cfg)` പ്രവർത്തിക്കുന്നു: പോർട്ടുകൾ `1–65535`
ആയിരിക്കണം, `mark`/`routeTable`/`bypassMark` പോസിറ്റീവ് പൂർണ്ണസംഖ്യകളായിരിക്കണം, കൂടാതെ `bypassMark`
`mark`-ൽ നിന്ന് വ്യത്യസ്തമായിരിക്കണം (ആന്റി-ലൂപ്പ്).

### പ്രയോഗ കമാൻഡുകൾ (ക്രമത്തിൽ)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

പഴയപടിയാക്കൽ അവയെ വിപരീത ക്രമത്തിൽ ഇല്ലാതാക്കുന്നു: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> ഈ നടപടിക്രമം **OUTPUT-അടിസ്ഥാനമാക്കിയുള്ളതാണ്**, കാരണം MITM ഉപയോഗസാഹചര്യം _ലോക്കൽ_ ഔട്ട്ബൗണ്ട്
> ട്രാഫിക്കാണ് (അതേ ഹോസ്റ്റിലെ ആപ്പുകൾ); `PREROUTING`-ലെ TPROXY മാത്രം അതിനെ
> കാണുന്നില്ല — `PREROUTING` ഫോർവേഡ് ചെയ്ത ട്രാഫിക് മാത്രമേ കാണൂ. `OUTPUT` ചെയിൻ പുതിയ
> ലോക്കൽ കണക്ഷനുകൾ അടയാളപ്പെടുത്തുന്നു, `ip rule` അവയെ ലോക്കൽ ഡെലിവറിയിലേക്ക് (`lo`) പുനഃറൂട്ട് ചെയ്യുന്നു, തുടർന്ന്
> `PREROUTING` അവയെ ട്രാൻസ്പാരന്റ് ലിസണറിലേക്ക് നിയോഗിക്കുന്നു.

## §8 കോൺഫിഗറേഷൻ

ആരംഭ അഭ്യർത്ഥന (`POST /api/tools/agent-bridge/tproxy`) താഴെപ്പറയുന്ന
ഫീൽഡുകൾ സ്വീകരിക്കുന്നു; ഇവ `StartTproxyBodySchema` (`tproxy/route.ts`) സാധൂകരിക്കുന്നു. എല്ലാം ഐച്ഛികമാണ്,
നൽകാത്തവ അവയുടെ ഡിഫോൾട്ട് മൂല്യങ്ങളിലേക്ക് മടങ്ങും:

| ഫീൽഡ്            | തരം                | ഡിഫോൾട്ട് | കുറിപ്പുകൾ                                                                                                                                          |
| ---------------- | ------------------ | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`     | ട്രാൻസ്പാരന്റ് ആയി ഇന്റർസെപ്റ്റ് ചെയ്യേണ്ട ഡെസ്റ്റിനേഷൻ TCP പോർട്ട്                                                                                 |
| **mark**         | int (≥1)           | `0x2333`  | `OUTPUT`-ൽ സജ്ജീകരിക്കുകയും `ip rule` + `PREROUTING` പൊരുത്തപ്പെടുത്തുകയും ചെയ്യുന്ന ഫയർവാൾ മാർക്ക്                                                 |
| **onPort**       | int (1–65535)      | `8443`    | ട്രാൻസ്പാരന്റ് (**IP_TRANSPARENT**) ലിസണർ ബൈൻഡ് ചെയ്യുന്ന പോർട്ട്                                                                                   |
| **routeTable**   | int (≥1)           | `233`     | `local 0.0.0.0/0` റൂട്ട് ഉൾക്കൊള്ളുന്ന പോളിസി-റൂട്ടിംഗ് പട്ടികയുടെ id                                                                               |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`   | പ്രോക്സി സ്വന്തം അപ്സ്ട്രീം കണക്ഷനുകളിൽ സജ്ജീകരിക്കുന്ന ബൈപാസ് സോക്കറ്റ് മാർക്ക് (**SO_MARK**); `OUTPUT`-ൽ നിന്ന് ഒഴിവാക്കപ്പെടുന്നു (ആന്റി-ലൂപ്പ്) |
| **sudoPassword** | string             | —         | റൂട്ട് അല്ലാത്ത ഡെസ്ക്ടോപ്പുകൾക്ക് മാത്രം: ട്രസ്റ്റ്-സ്റ്റോർ ഇൻസ്റ്റാളേഷന് അംഗീകാരം നൽകുന്നു; റൂട്ട് ആയിരിക്കുമ്പോൾ അവഗണിക്കുന്നു                   |

TPROXY-ക്കായി **പരിസ്ഥിതി വേരിയബിളുകളൊന്നുമില്ല** — എല്ലാ കോൺഫിഗറേഷനും
POST ബോഡി വഴിയോ മുകളിലുള്ള ഡിഫോൾട്ടുകൾ വഴിയോ ആണ്.

## §9 Traffic Inspector-ൽ നിന്ന് പ്രവർത്തനക്ഷമമാക്കൽ

1. **Traffic Inspector** (`/dashboard/tools/traffic-inspector`) തുറക്കുക.
2. ക്യാപ്ചർ-മോഡുകളുടെ ടൂൾബാറിൽ **"TPROXY Decrypt"** ⚠ ബട്ടൺ കണ്ടെത്തുക
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - "TPROXY decrypt requires Linux + root +
     the native addon" എന്ന ടൂൾടിപ്പോടെ ഇത് **പ്രവർത്തനരഹിതമാണെങ്കിൽ**, ഈ ഹോസ്റ്റിൽ നേറ്റീവ് ആഡോൺ ലഭ്യമല്ല (Linux അല്ല,
     ടൂൾചെയിൻ ഇല്ല, അല്ലെങ്കിൽ ആഡോൺ ബിൽഡ് ചെയ്തിട്ടില്ല). [§2](#2-requirements), [§3](#3-the-native-ip_transparent-addon) എന്നിവ കാണുക.
3. ബട്ടൺ ക്ലിക്ക് ചെയ്യുക. ഇത്
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`) വഴി `POST /api/tools/agent-bridge/tproxy` വിളിക്കുന്നു. ഇത്:
   ഡൈനാമിക് CA ബിൽഡ് ചെയ്യുകയും, ട്രാൻസ്പാരന്റ് ലിസണർ തുറക്കുകയും, ഫയർവാൾ
   നിയമങ്ങൾ പ്രയോഗിക്കുകയും, OS ട്രസ്റ്റ് സ്റ്റോറിൽ CA ഇൻസ്റ്റാൾ ചെയ്യുകയും ചെയ്യുന്നു.
4. പ്രവർത്തിക്കുമ്പോൾ, ടോഗിൾ ആംബർ നിറത്തിലാകുകയും തത്സമയ ഇന്റർസെപ്റ്റ് എണ്ണം
   (`· <interceptCount>`) കാണിക്കുകയും ചെയ്യുന്നു. ഇന്റർസെപ്റ്റ് ചെയ്ത അഭ്യർത്ഥനകൾ
   `source: "tproxy"` സഹിതം അഭ്യർത്ഥനാ ലിസ്റ്റിൽ ദൃശ്യമാകും.
5. നിർത്താൻ വീണ്ടും ക്ലിക്ക് ചെയ്യുക — `stopTproxyCaptureMode()` വഴി
   `DELETE /api/tools/agent-bridge/tproxy` ലിസണർ അടയ്ക്കുകയും, CA അൺഇൻസ്റ്റാൾ ചെയ്യുകയും,
   ഫയർവാൾ നിയമങ്ങൾ പഴയപടിയാക്കുകയും ചെയ്യുന്നു.

ക്യാപ്ചർ-മോഡ് നില (പ്രവർത്തിക്കുന്നു / ലഭ്യമാണ് / ഇന്റർസെപ്റ്റ് എണ്ണം / ലിസണർ പോർട്ട്)
`GET /api/tools/agent-bridge/tproxy`-ൽ നിന്നാണ് ലഭിക്കുന്നത് (`src/mitm/tproxy/captureManager.ts`-ലെ
`getCaptureStatus()`). ഒരേ സമയം **ഒരു** TPROXY സെഷൻ മാത്രമേ പ്രവർത്തിക്കൂ —
രണ്ടാമത്തേത് ആരംഭിക്കാൻ ശ്രമിച്ചാൽ "TPROXY capture mode is already running" എന്ന സന്ദേശത്തോടെ നിരസിക്കും.

## §10 പ്രശ്നപരിഹാരം

### ടോഗിൾ പ്രവർത്തനരഹിതമാണ്

നേറ്റീവ് ആഡോൺ ലോഡ് ചെയ്യാനാകുന്നില്ല. ഇനിപ്പറയുന്നവ സ്ഥിരീകരിക്കുക: നിങ്ങൾ Linux-ലാണ്,
ആഡോൺ ബിൽഡ് ചെയ്തിട്ടുണ്ട് (`npm run build:native:tproxy`), കൂടാതെ പ്രോസസിന്
`transparent.node` ലോഡ് ചെയ്യാനാകും. `isTransparentSocketAvailable()` ആണ് ടോഗിൾ നിയന്ത്രിക്കുന്നത്;
ആഡോൺ ഇല്ലാത്തപ്പോൾ `GET /api/tools/agent-bridge/tproxy` എന്നത് `available: false` മടക്കിനൽകുന്നു.

### ഒന്നും ക്യാപ്ചർ ചെയ്യപ്പെടുന്നില്ല

- ഇന്റർസെപ്റ്റ് ചെയ്യുന്ന പ്രോസസ് കോൺഫിഗർ ചെയ്ത `dport`-ലേക്ക്
  (സ്ഥിരസ്ഥിതി `443`) യഥാർത്ഥത്തിൽ കണക്റ്റ് ചെയ്യുന്നുണ്ടെന്ന് സ്ഥിരീകരിക്കുക.
- പ്രോസസ് ഡൈനാമിക് CA-യെ വിശ്വസിക്കുന്നുവെന്ന് സ്ഥിരീകരിക്കുക. CA
  `omniroute-tproxy-ca.crt` എന്ന പേരിലാണ് ഇൻസ്റ്റാൾ ചെയ്യുന്നത്; സ്വന്തം ട്രസ്റ്റ് സ്റ്റോറുള്ള ആപ്പുകളിൽ (Firefox/Chrome NSS)
  സർട്ടിഫിക്കറ്റ് അവിടെയും ചേർക്കേണ്ടിവന്നേക്കാം.
- സർട്ടിഫിക്കറ്റ് വിശ്വസനീയം / സെർവർ ആരോഗ്യം എന്നിവ പരിശോധിക്കാൻ AgentBridge **Diagnose**
  സ്വയം-പരിശോധന പ്രവർത്തിപ്പിക്കുക ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md) കാണുക).

### ക്രാഷിന് ശേഷം ശേഷിക്കുന്ന പഴയ ഫയർവാൾ നിയമങ്ങൾ

`revertTproxy()` എന്നത് പ്രയോഗത്തിന്റെ കൃത്യമായ വിപരീതവും ഐഡംപൊട്ടന്റുമാണ്. മോഡ്
നിർത്തുന്നത് നിയമങ്ങൾ പഴയപടിയാക്കുന്നു; സെഷന്റെ മധ്യേ OmniRoute നിർത്തപ്പെട്ടാൽ, അനാഥമായി ശേഷിച്ച സിസ്റ്റം
നില (DNS സ്പൂഫ്, റൂട്ട് CA, സിസ്റ്റം പ്രോക്സി) പഴയപടിയാക്കാൻ AgentBridge
**Repair** പ്രവർത്തനം (`POST /api/tools/agent-bridge/repair`) ഉപയോഗിക്കുക. TPROXY `mangle`
നിയമങ്ങളും റൂട്ടും റീബൂട്ട് ചെയ്യുമ്പോൾ സ്വയമേവ നീക്കം ചെയ്യപ്പെടും.

### അനന്തമായ ലൂപ്പ് / പ്രോക്സി സ്വന്തം ഫോർവേഡ് ഇന്റർസെപ്റ്റ് ചെയ്യുന്നു

ഇത് ആന്റി-ലൂപ്പ് സാഹചര്യമാണ്. `bypassMark`, `mark`-ൽ നിന്ന് വ്യത്യസ്തമാണെന്ന് സ്ഥിരീകരിക്കുക
(വാലിഡേഷൻ ഇത് ഉറപ്പാക്കുന്നു), കൂടാതെ ഫോർവേഡ് `connectMarked` ഉപയോഗിക്കുന്നുണ്ടെന്നും സ്ഥിരീകരിക്കുക
(`realForward`-ൽ ഇത് ഉപയോഗിക്കുന്നുണ്ട്).
[§5 ആന്റി-ലൂപ്പ്](#anti-loop-so_mark) കാണുക.
