> **ആധികാരിക ഉറവിടം:** `src/lib/guardrails/`
> **അവസാനം പുതുക്കിയത്:** 2026-08-29 — v3.8.51 (Video Bridge ട്രാൻസ്ക്രിപ്റ്റിന്റെ ഉറവിടം കോളർ പ്രഖ്യാപിക്കുന്നതാണ്,
> ഇതുവരെ സെർവർ പരിശോധിച്ചുറപ്പിച്ചതല്ല — #11661 പ്രകാരം വ്യക്തമാക്കിയത്)

OmniRoute-നും അപ്സ്ട്രീം പ്രൊവൈഡർമാർക്കും ഇടയിലുള്ള അതിർത്തിയിൽ സുരക്ഷ, നയം, ഉള്ളടക്ക പരിവർത്തനങ്ങൾ എന്നിവ Guardrails നടപ്പിലാക്കുന്നു. ഓരോ guardrail-നും അഭ്യർത്ഥനാ പേലോഡുകൾ (`preCall`), അപ്സ്ട്രീം പ്രതികരണങ്ങൾ (`postCall`) എന്നിവ പരിശോധിക്കാനും (ആവശ്യമെങ്കിൽ നിരസിക്കാനും, പരിവർത്തനം ചെയ്യാനും, വ്യാഖ്യാനക്കുറിപ്പുകൾ ചേർക്കാനും) കഴിയും.

ഈ സിസ്റ്റം **fail-open** രീതിയിലാണ് പ്രവർത്തിക്കുന്നത്: ഒരു guardrail പ്രവർത്തിക്കുമ്പോൾ exception എറിഞ്ഞാൽ, അഭ്യർത്ഥന പരാജയപ്പെടുത്തുന്നതിന് പകരം registry പിശക് രേഖപ്പെടുത്തി അടുത്ത guardrail-ലേക്ക് തുടരുന്നു. തടയൽ എന്നത് വ്യക്തമായ ഒരു തീരുമാനമാണ് (`block: true`), ഒരിക്കലും അബദ്ധത്തിൽ സംഭവിക്കുന്നതല്ല.

## അന്തർനിർമ്മിത Guardrails

ഇംപോർട്ട് ചെയ്യുമ്പോൾ മുൻഗണനാക്രമത്തിൽ ആറ് guardrails registry സ്വയമേവ ലോഡ് ചെയ്യുന്നു
(`registry.ts` → `registerDefaultGuardrails()` കാണുക):

| മുൻഗണന | പേര്                | ഘട്ടം(ങ്ങൾ)    | ഫയൽ                   |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

കുറഞ്ഞ മുൻഗണനാ സംഖ്യകളുള്ളവ **ആദ്യം** പ്രവർത്തിക്കുന്നു.

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

**വിഷൻ പിന്തുണയില്ലാത്ത മോഡലുകളെ** ലക്ഷ്യമിട്ടുള്ള, ചിത്രങ്ങൾ ഉൾക്കൊള്ളുന്ന അഭ്യർത്ഥനകളെ തടഞ്ഞെടുത്ത്, മുഴുവൻ അഭ്യർത്ഥനയും വിഷൻ പിന്തുണയുള്ള ഒരു മോഡലിലേക്ക് തിരിച്ചുവിടുകയോ അപ്സ്ട്രീം കോളിന് മുമ്പ് കോൺഫിഗർ ചെയ്യാവുന്ന ഒരു വിഷൻ മോഡൽ സൃഷ്ടിച്ച ടെക്സ്റ്റ് വിവരണങ്ങൾകൊണ്ട് ചിത്രഭാഗങ്ങൾ മാറ്റിസ്ഥാപിക്കുകയോ ചെയ്യുന്നു. ഇതിലൂടെ ടെക്സ്റ്റ് മാത്രം പിന്തുണയ്ക്കുന്ന പ്രൊവൈഡർമാർക്ക് മൾട്ടിമോഡൽ പേലോഡുകൾ സുതാര്യമായി കൈകാര്യം ചെയ്യാനാകും.

പ്രവാഹം:

1. ലക്ഷ്യമിട്ട മോഡൽ ഇതിനകം വിഷൻ പിന്തുണയ്ക്കുന്നുവെങ്കിൽ ഒഴിവാക്കുക (അത് നിർബന്ധിത-ബ്രിഡ്ജ് ലിസ്റ്റായ `isVisionBridgeForcedModel`-ൽ ഉൾപ്പെട്ടിട്ടില്ലെങ്കിൽ).
2. `extractImageParts(messages)` വഴി ചിത്രഭാഗങ്ങൾ എക്സ്ട്രാക്റ്റ് ചെയ്യുക
   (`visionBridgeHelpers.ts`). ഇത് `open-sse/utils/mediaParts.ts`-ലെ **ഏകീകൃത മീഡിയ
   ഡിറ്റക്ടറായ** `detectMediaParts()`-ലേക്ക് ചുമതല കൈമാറുന്നു — combo compatibility filter-മായി പങ്കിടുന്ന ഏക ആധികാരിക ഉറവിടമാണിത്.
   `replaceImageParts`-ന് തിരികെ ചേർക്കാൻ കഴിയുന്ന രൂപങ്ങളിലുള്ള top-level ഭാഗങ്ങൾ മാത്രമാണ് എക്സ്ട്രാക്ഷനായി അനുവദിച്ചിരിക്കുന്നത് (extract↔replace കരാർ): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, Responses API `input_image` എന്നിവ. നെസ്റ്റഡ് പൊരുത്തങ്ങളും
   സൂചന മാത്രമുള്ള രൂപങ്ങളും combo-filter-നുള്ളവയാണ്; അവ ഒരിക്കലും എക്സ്ട്രാക്റ്റ് ചെയ്യില്ല.
   ഒന്നും കണ്ടെത്തിയില്ലെങ്കിൽ ഒഴിവാക്കുക.
3. `resolveVisionBridgeRuntimeSettings()` വഴി runtime config നിർണ്ണയിക്കുക
   (`src/shared/constants/modalityBridgeDefaults.ts`): പുതിയ `modalityBridge*`
   settings കീകൾക്കാണ് മുൻഗണന; പഴയ `visionBridge*` കീകൾ **ഒരു സൈക്കിളിലേക്കുള്ള
   fallback** ആയി (rollback window) തുടരും. ബ്രിഡ്ജ് പ്രവർത്തനരഹിതമാണെങ്കിൽ ഏതെങ്കിലും മീഡിയ ട്രാവേഴ്സലിന് മുമ്പുതന്നെ ഒഴിവാക്കുക.
4. മോഡ് സെലക്ടർ (`modalityBridgeVisionMode`, താഴെയുള്ള പട്ടിക കാണുക) reroute ആണോ describe ആണോ എന്ന് തീരുമാനിക്കുന്നു. Reroute, `model` മാത്രം മാറ്റിയ `modifiedPayload`-ഉം meta `{ rerouted, fromModel, toModel, imagesKept }`-യും തിരികെ നൽകുന്നു.
5. Describe പാത: ചിത്രങ്ങളുടെ എണ്ണം `maxImages` ആയി പരിമിതപ്പെടുത്തുക, ടാസ്ക് പരിഗണിക്കുന്ന prompt തയ്യാറാക്കുക,
   describe cache പരിശോധിക്കുക, വിഷൻ മോഡലിനെ **സമാന്തരമായി**
   (`Promise.allSettled`) വിളിക്കുക, തുടർന്ന് ചിത്രങ്ങളുടെ സ്ഥാനത്ത് `[Image N]: <description>` എന്ന ടെക്സ്റ്റ് ഭാഗങ്ങൾ ചേർക്കുക.
   പരാജയപ്പെട്ട describe `null` നൽകുകയും യഥാർത്ഥ ചിത്രഭാഗം
   **നിലനിർത്തുകയും** ചെയ്യും (#4012) — എന്നാൽ combo describe പാതയിൽ എല്ലാ
   describe ശ്രമങ്ങളും പരാജയപ്പെടുകയും അപ്സ്ട്രീം വിഷൻ പിന്തുണയ്ക്കുന്നില്ലെന്ന് സ്ഥിരീകരിക്കപ്പെടുകയും ചെയ്താൽ, പകരം
   `(unavailable — no vision-capable provider connected)` എന്ന stub നൽകും (#8430).
6. `modifiedPayload` + meta (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) തിരികെ നൽകുക.

#### മോഡ് സെലക്ടർ (`modalityBridgeVisionMode`)

| മോഡ്       | ഡിഫോൾട്ട് | പ്രവർത്തനം                                                                                                                                                                                                                                                                                                       |
| ---------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔         | മാറ്റമില്ലാത്ത പഴയ heuristic (#6640/#7204): യഥാർത്ഥ മോഡലിന് ഇതിനകം ഉപയോഗയോഗ്യമായ credentials ഇല്ലെങ്കിൽ, non-combo/`auto/` മോഡലുകൾ മികച്ച വിഷൻ മോഡലിലേക്ക് reroute ചെയ്യപ്പെടും (credentials ഉണ്ടെങ്കിൽ describe ചെയ്യും); combo ലക്ഷ്യങ്ങൾ എല്ലായ്പ്പോഴും describe ചെയ്യും.                                     |
| `describe` |           | എല്ലായ്പ്പോഴും describe ചെയ്യുക — reroute block പൂർണ്ണമായും ഒഴിവാക്കപ്പെടും; ഉപയോക്താവ് തിരഞ്ഞെടുത്ത മോഡൽ തന്നെയാണ് എല്ലായ്പ്പോഴും ഉത്തരം നൽകുന്നത്.                                                                                                                                                             |
| `reroute`  |           | നിർബന്ധിത reroute: credential ഉള്ള മോഡൽ നിലനിർത്തുന്ന guard മറികടക്കപ്പെടും. Reroute-**target** credential guard അപ്പോഴും ബാധകമാണ് — ഉപയോഗയോഗ്യമായ വിഷൻ ലക്ഷ്യമൊന്നും ഇല്ലെങ്കിൽ, അസംസ്കൃത ചിത്രങ്ങൾ ടെക്സ്റ്റ്-മാത്രമുള്ള backend-ലേക്ക് ഒരിക്കലും എത്താതിരിക്കാനായി അഭ്യർത്ഥന describe-ലേക്ക് നീങ്ങും (#8430). |

നിർബന്ധിത മോഡുകൾ auto heuristic പ്രവർത്തിക്കുന്നതിന് **മുമ്പ്** short-circuit ചെയ്യുന്നു; `auto`-യുടെ പ്രവർത്തനം PR-1-ന് മുമ്പുള്ള guardrail-ുമായി ബൈറ്റ്-തലത്തിൽ സമാനമാണ്.

#### ടാസ്ക് പരിഗണിക്കുന്ന describe prompt (`modalityBridgeVisionTaskAware`)

ഡിഫോൾട്ട് **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) അടിസ്ഥാന
describe prompt-നോട് **അവസാനത്തെ ഉപയോക്തൃ സന്ദേശത്തിലെ** ടെക്സ്റ്റ് (500 അക്ഷരങ്ങളായി ചുരുക്കിയത്) ചേർക്കുന്നു. ഇതിലൂടെ ഉപയോക്താവ് യഥാർത്ഥത്തിൽ ചോദിച്ചതിനെ അടിസ്ഥാനമാക്കി വിവരണം നയിക്കുകയും (codex-vision-proxy pattern), ദൃശ്യമാകുന്ന ടെക്സ്റ്റ് ട്രാൻസ്ക്രൈബ് ചെയ്യാൻ വിഷൻ മോഡലിനോട് ആവശ്യപ്പെടുകയും ചെയ്യുന്നു. ഫ്ലാഗ് ഓഫായിരിക്കുമ്പോൾ — അല്ലെങ്കിൽ ഉപയോക്തൃ ടെക്സ്റ്റ് ഇല്ലെങ്കിൽ — അടിസ്ഥാന prompt മാറ്റമില്ലാതെ ഉപയോഗിക്കുന്നു.

describe സെൽഫ്-ലൂപ്പിന്റെ സ്വന്തം OpenAI-അനുയോജ്യമായ അഭ്യർത്ഥന (`callVisionModelSingle()`
`visionBridgeHelpers.ts`-ൽ) എല്ലായ്പ്പോഴും `image_url.detail: "high"` അഭ്യർത്ഥിക്കുന്നു —
ഒരു നിബന്ധനയുമില്ലാതെ, എല്ലാ കോളർമാർക്കും/പ്രൊവൈഡർമാർക്കും, ഏതെങ്കിലും ക്ലയന്റ് സിഗ്നലിന്റെ
അടിസ്ഥാനത്തിൽ നിയന്ത്രിക്കപ്പെടാതെ. ഈ പ്രോംപ്റ്റ് ആവശ്യപ്പെടുന്ന ടെക്സ്റ്റ്-ട്രാൻസ്ക്രിപ്ഷൻ
ടാസ്കിൽ ലോ-ഡീറ്റെയിൽ സാംപ്ലിംഗ് OCR കൃത്യത കുറയ്ക്കുന്നതിനാൽ, യഥാർത്ഥ ഇൻബൗണ്ട് അഭ്യർത്ഥന
ഏത് ഡീറ്റെയിൽ ലെവൽ ഉപയോഗിച്ചാലും describe കോൾ തന്നെ എല്ലായ്പ്പോഴും ഉയർന്ന ഡീറ്റെയിൽ
ആവശ്യപ്പെടുന്നു. ഇത് ആന്തരിക describe അഭ്യർത്ഥനയുടെ ബോഡിയെ മാത്രമേ ബാധിക്കൂ; പ്രാഥമിക
അഭ്യർത്ഥനയിൽ കോളറുടെ സ്വന്തം `image_url.detail` OmniRoute എങ്ങനെ ഫോർവേഡ് ചെയ്യുന്നു
എന്നത് ഇത് മാറ്റുന്നില്ല — ആ ഡിഫോൾട്ട് പ്രത്യേകം പ്രയോഗിക്കപ്പെടുന്നതും, കണ്ടെത്തിയ
OpenCode ക്ലയന്റുകൾക്ക് മാത്രമായി, `defaultImageDetail()`
(`open-sse/handlers/chatCore/upstreamBody.ts`)-ലുമാണ്. describe സെൽഫ്-ലൂപ്പിന്റെ
Anthropic വയർ-ഫോർമാറ്റ് ബ്രാഞ്ചിന് `detail` ഫീൽഡ് ഇല്ലാത്തതിനാൽ, ഈ രണ്ട്
ഡിഫോൾട്ടുകളിലൊന്നും അതിനെ ബാധിക്കില്ല.

#### Describe ഔട്ട്പുട്ട് പരിധി (`modalityBridgeVisionMaxChars`)

| കീ                             | ഡിഫോൾട്ട് | പരിധി                    |
| ------------------------------ | --------- | ------------------------ |
| `modalityBridgeVisionMaxChars` | `0`       | `0` അല്ലെങ്കിൽ 100–50000 |

`0` (ഡിഫോൾട്ട്) എന്നത് **പരിധിയില്ല** എന്നാണ് അർത്ഥമാക്കുന്നത് —
`callVisionModel()` മടക്കിനൽകുന്ന വിവരണം മാറ്റമില്ലാതെ കൈമാറപ്പെടുകയും, നിലവിലുള്ള
പെരുമാറ്റം നിലനിർത്തുകയും ചെയ്യുന്നു. 100–50000 പരിധിയിലുള്ള ഏതൊരു മൂല്യവും വിവരണത്തെ
`…` സഫിക്സ് ചേർത്ത് ചുരുക്കുന്നു; അതിനുശേഷം അത് `[Image N]: <description>` ആയി
തിരികെ ചേർക്കപ്പെടും (`src/lib/guardrails/visionBridge.ts`-ലെ
`VisionBridgeGuardrail.preCall()`). ഡൗൺസ്ട്രീം മോഡലിന് പൂർണ്ണ ട്രാൻസ്ക്രിപ്ഷൻ
ആവശ്യമായ, ധാരാളം വിശദാംശങ്ങളുള്ള OCR ടാസ്കുകൾക്ക് ഈ മൂല്യം ഉയർത്തുക; അധികമായി
സംസാരിക്കുന്ന വിഷൻ മോഡലുകളുടെ ടോക്കൺ ഉപയോഗം പരിമിതപ്പെടുത്താൻ ഇത് കുറയ്ക്കുക.
ഡാഷ്ബോർഡ് ഫീൽഡ് Vision ടാബിലെ Advanced പാനലിലാണ്
(`ModalityBridgeVisionTab.tsx`-ലെ `modality-bridge-max-chars`); വ്യക്തമായി നൽകിയ
`0` മാറ്റമില്ലാതെ നിലനിർത്തിക്കൊണ്ട്, 1-നും 99-നും ഇടയിലുള്ള ഏതൊരു മൂല്യവും അത്
കുറഞ്ഞ പരിധിയായ 100 വരെ ഉയർത്തുന്നു — `0` എന്നത് കേവലം "സജ്ജീകരിക്കാത്തത്"
എന്ന ഡിഫോൾട്ട് മാത്രമല്ല, സ്വന്തമായി സാധുതയുള്ള ഒരു Zod മൂല്യമാണ്
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`).

#### Describe കാഷ് (`modalityBridge/bridgeCache.ts`)

ഉത്തരം നൽകിയ മോഡലല്ല, **കോൺഫിഗർ ചെയ്ത** ബ്രിഡ്ജ് മോഡലാണ് —

#### റിമോട്ട് ഇമേജ് നോർമലൈസേഷൻ (സെൽഫ്-ലൂപ്പ് describe/base64 ഫെച്ച്)

ബ്രിഡ്ജ് സ്വയം ഒരു **റിമോട്ട്** ഇമേജ് ഫെച്ച് ചെയ്യുമ്പോൾ — Anthropic describe
സെൽഫ്-കോളും claude-wire-format base64 പരിവർത്തനവും
(`ensureBase64ImagesForClaudeWire`), രണ്ടും `visionBridgeHelpers.ts`-ലെ
`fetchRemoteImageAsDataUri()` വഴിയാണ് — ലഭിക്കുന്ന ഡാറ്റ URI, വിഷൻ-മോഡൽ
അഭ്യർത്ഥനയിൽ എംബെഡ് ചെയ്യുന്നതിന് മുമ്പ് `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) വഴി കടത്തിവിടുന്നു. അതിപ്രമാണമുള്ള ഇമേജുകൾ
**2048px നീളമുള്ള വശം** എന്ന പരിധിയിലേക്ക് ഡൗൺസ്കെയിൽ ചെയ്യപ്പെടുന്നു
(OpenAI/Anthropic ഇതിനകം സെർവർ-സൈഡിൽ പ്രയോഗിക്കുന്ന റീസൈസ് പരിധിയുമായി
പൊരുത്തപ്പെടുന്നത്); വിഷൻ മോഡൽ കാണുന്നതിൽ മാറ്റം വരുത്താതെ ഇത് അപ്ലോഡ്
ബൈറ്റുകളും/ലേറ്റൻസിയും കുറയ്ക്കുന്നു. റീസൈസിങ്ങിന് ഡൈനാമിക് ഇംപോർട്ട് വഴി ലോഡ്
ചെയ്യുന്ന `sharp` ഉപയോഗിക്കുന്നു: അതിന്റെ നേറ്റീവ് ബൈനറി ലോഡ് ചെയ്യുന്നതിൽ പരാജയപ്പെടുന്ന
പ്ലാറ്റ്ഫോമിൽ `normalizeDataUri()` **ഒരിക്കലും എറർ ത്രോ ചെയ്യില്ല** — അത് യഥാർത്ഥ
ബൈറ്റുകൾ മാറ്റമില്ലാതെ കടത്തിവിടുന്നതിലേക്ക് ഫാൾബാക്ക് ചെയ്യുന്നതിനാൽ,
describe/base64-പരിവർത്തന പാത എല്ലായ്പ്പോഴും പ്രവർത്തിച്ചുകൊണ്ടിരിക്കും.
ഇമേജ് അല്ലാത്ത ബൈറ്റുകളും (ഡീകോഡ് ചെയ്യാവുന്ന ഇമേജ് മടക്കിനൽകാത്ത ഒരു ഫെച്ച്)
മാറ്റമില്ലാതെ കടത്തിവിടുന്നു. ബ്രിഡ്ജ് സ്വന്തം സെൽഫ്-കോളിനായി ഫെച്ച് ചെയ്യുന്ന
ഇമേജുകൾക്ക് മാത്രമാണ് ഈ നോർമലൈസേഷൻ ബാധകമാകുന്നത് — കോളറുടെ റോ പാസ്ത്രൂ
പേലോഡിൽ ഇത് ഒരിക്കലും പ്രയോഗിക്കില്ല; ഇത് ഓപ്റ്റ്-ഇൻ ചെയ്താൽ മാത്രം മാറ്റം വരുത്തുക
എന്ന തത്ത്വവുമായി (Hard Rule #20) പൊരുത്തപ്പെടുന്നു.

`averageLatencyMs` അതിന്റെ ഡിനോമിനേറ്ററായി എല്ലാ ശ്രമങ്ങളെയും ഉപയോഗിക്കുന്നതിന് പകരം
`latencySamples` ഉപയോഗിക്കുന്നു; ടൈമിങ് ഇല്ലാത്ത ഒരു ഓപ്പറേഷൻ കൃത്രിമമായി
പൂജ്യം-മില്ലിസെക്കൻഡ് സാമ്പിൾ സൃഷ്ടിക്കില്ല. വിജയകരമായ പരിവർത്തനങ്ങൾക്കുള്ള
ബാക്ക്വേഡ്-കംപാറ്റിബിൾ അപരനാമമായി `bridged` തുടരും; പരാജയപ്പെട്ട ശ്രമങ്ങൾ അതിന്റെ
മൂല്യം വർധിപ്പിക്കില്ല.
രൂപകൽപ്പനപ്രകാരം പ്രോസസ് പുനരാരംഭിക്കുമ്പോൾ കൗണ്ടറുകൾ റീസെറ്റ് ചെയ്യും
(ടെലിമെട്രിയാണ്, അക്കൗണ്ടിങ് അല്ല).

#### ഡാഷ്ബോർഡ് കോൺഫിഗറേഷൻ

സമർപ്പിത ഡാഷ്ബോർഡ് പേജ്
`/dashboard/settings/modality-bridge` ആണ്. ഇതിലെ URL മുഖേന നേരിട്ട് ആക്സസ് ചെയ്യാവുന്ന `Vision`, `Audio`,
`Video` ടാബുകൾ, `tab` മൂല്യം മാറ്റുമ്പോഴും ക്വറി പാരാമീറ്ററുകൾ നിലനിർത്തുന്നു.
Vision ടാബ് സജ്ജമാക്കൽ, മോഡ്, മോഡൽ തിരഞ്ഞെടുക്കൽ (സ്വയമേവയുള്ള
ഡിഫോൾട്ട് ഉൾപ്പെടെ), ടാസ്ക്-അവബോധമുള്ള പ്രോംപ്റ്റിംഗ്, വിപുലമായ ടൈംഔട്ട്/ഇമേജ്/വിവരണ-ദൈർഘ്യം/കാഷ്
പരിധികൾ, റൺടൈം
കൗണ്ടറുകൾ, സുരക്ഷിതമായി നിയന്ത്രിച്ച ഒരു സാമ്പിൾ അഭ്യർത്ഥന എന്നിവ ലഭ്യമാക്കുന്നു. Audio ടാബും പ്രവർത്തനക്ഷമമാണ്: ഇത്
സജ്ജമാക്കൽ, Auto ഉൾപ്പെടെയുള്ള STT-മാത്രം മോഡൽ പിക്കർ, ടൈംഔട്ട്/പരമാവധി-ക്ലിപ്പ് പരിധികൾ, ഓഡിയോ
കൗണ്ടറുകൾ, ഒരു `input_audio` സാമ്പിൾ ടെസ്റ്റ് എന്നിവ ലഭ്യമാക്കുന്നു. Video ടാബ് പൂർണ്ണമായും പ്രവർത്തനക്ഷമമാണ്: ഇത്
FFmpeg/ffprobe റൺടൈം നില റിപ്പോർട്ട് ചെയ്യുന്നു — വ്യക്തമായി നിർവചിച്ച നാല് UI നിലകളിൽ ഒന്ന് (`unknown` എന്നത്
പ്രോബ് പുരോഗമിക്കുമ്പോഴോ പൂർത്തിയാക്കാൻ കഴിയാതിരിക്കുമ്പോഴോ, `restricted` എന്നത് ലൂപ്പ്ബാക്ക് അല്ലാത്ത
ഡാഷ്ബോർഡ് ഹോസ്റ്റിൽ പ്രോബ് ക്ലയന്റ്-സൈഡിൽ ഒഴിവാക്കപ്പെടുമ്പോൾ, `unavailable` എന്നത് പ്രോബ് ചെയ്തശേഷം
ലഭ്യമല്ലെന്ന് സ്ഥിരീകരിക്കുമ്പോൾ, അല്ലെങ്കിൽ FFmpeg/ffprobe പതിപ്പുകളോടുകൂടിയ `available`) — സജ്ജമാക്കൽ/മോഡൽ/ഫ്രെയിം/വീഡിയോ/ടൈംഔട്ട്
പരിധികൾ സ്ഥിരമായി സൂക്ഷിക്കുന്നു, വിഷൻ പിന്തുണയുള്ള
മോഡലുകൾ മാത്രമായി മോഡൽ പിക്കർ ഫിൽട്ടർ ചെയ്യുന്നു, കൂടാതെ വീഡിയോ കൗണ്ടറുകൾ ലഭ്യമാക്കുന്നു.

AI ക്രമീകരണങ്ങൾക്ക് കീഴിലുണ്ടായിരുന്ന പഴയ Vision Bridge കാർഡ് ഇപ്പോൾ പുതിയ
പേജിലേക്കുള്ള ഒരു അനുയോജ്യതാ ലിങ്കാണ്; ഫോമിന്റെ രണ്ടാമത്തെ പകർപ്പ് ഇനി അതിൽ ഇല്ല. നിലവിലുള്ള Speech-to-Text പ്ലേഗ്രൗണ്ട് നീക്കം ചെയ്യാതെ,
Media Providers, Image-to-Text, Speech-to-Text വർക്ക്ഫ്ലോകളെ അവയ്ക്ക് അനുയോജ്യമായ Modality
Bridge ടാബുകളുമായി ലിങ്ക് ചെയ്യുകയും ചെയ്യുന്നു.

**സ്വയം-ലൂപ്പ് അഡ്മിഷൻ ബൈപാസ്:** describe കോൾ OmniRoute-ന്റെ
സ്വന്തം `/v1` സ്വയം-ലൂപ്പിലൂടെ (സ്റ്റാൻഡേർഡ് അല്ലാത്ത പ്രൊവൈഡർ മോഡൽ) റൂട്ട് ചെയ്യുമ്പോൾ, ഉപ-അഭ്യർത്ഥന
`x-omniroute-admission-bypass: internal` അയയ്ക്കുകയും പരിഹരിച്ച
സ്വയം-ലൂപ്പ് ക്രെഡൻഷ്യൽ ഉപയോഗിച്ച് പ്രാമാണീകരിക്കുകയും ചെയ്യുന്നു — ലോക്കൽ മോഡിൽ ലോക്കൽ `sk_omniroute` സെന്റിനൽ, അല്ലെങ്കിൽ
ഓപ്പറേറ്റർ ക്രമീകരിച്ച `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env കീ (#1350). അതിനാൽ
`REQUIRE_API_KEY=true` ഡിപ്ലോയ്മെന്റുകൾക്കും describe കോൾ പ്രവർത്തിപ്പിക്കാൻ കഴിയും. കൃത്യമായി ഈ ക്രെഡൻഷ്യലുകൾക്കു മാത്രമേ
ബൈപാസ് അനുവദിക്കൂ; അതിനാൽ പുറത്തുനിന്നുള്ള ക്ലയന്റുകൾക്ക് അഡ്മിഷൻ ഒഴിവാക്കാൻ ഈ
ഹെഡർ ഉപയോഗിക്കാനാവില്ല.

ലെഗസി ഡിഫോൾട്ടുകൾ `src/shared/constants/visionBridgeDefaults.ts`-ൽ ഉണ്ട്;
പുതിയ മോഡ്/ടാസ്ക്-അവബോധമുള്ള/കാഷ് ഡിഫോൾട്ടുകളും ക്രമീകരണ റിസോൾവറും
`src/shared/constants/modalityBridgeDefaults.ts`-ൽ ഉണ്ട്. ടെസ്റ്റുകൾക്ക് വ്യാജ `getSettings`, `callVisionModel`
ഇംപ്ലിമെന്റേഷനുകൾ ഇൻജക്റ്റ് ചെയ്യാൻ കഴിയുന്നതിനായി ഗാർഡ്റെയിൽ ഒരു
`deps` കൺസ്ട്രക്റ്റർ ഓപ്ഷൻ ലഭ്യമാക്കുന്നു.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ഓഡിയോ ഇൻപുട്ട് സ്വീകരിക്കുന്നതായി അറിയപ്പെടാത്ത ഒരു ലക്ഷ്യത്തിലേക്ക് ഓഡിയോ അടങ്ങിയ ചാറ്റ് അഭ്യർത്ഥനകൾ
എത്തുന്നതിന് മുമ്പ് അവയെ ഇന്റർസെപ്റ്റ് ചെയ്യുന്നു. ഇത് ചാറ്റ് അഭ്യർത്ഥനയെ ഒരിക്കലും മറ്റൊരു റൂട്ടിലേക്ക് മാറ്റുന്നില്ല: നിലവിലുള്ള
OpenAI-അനുയോജ്യമായ multipart എൻഡ്പോയിന്റ് വഴി ഓഡിയോ ഭാഗങ്ങൾ ട്രാൻസ്ക്രൈബ് ചെയ്യപ്പെടുകയും,
തിരഞ്ഞെടുത്ത ചാറ്റ് മോഡൽ ടെക്സ്റ്റ് ട്രാൻസ്ക്രിപ്റ്റുകളുമായി തുടരുകയും ചെയ്യുന്നു.

പ്രവാഹം:

1. `getResolvedModelCapabilities()` വഴി `supportsAudio` പരിഹരിക്കുക. വ്യക്തമായി നൽകിയ
   പ്രൊവൈഡർ-രജിസ്ട്രി മെറ്റാഡാറ്റയ്ക്കാണ് മുൻഗണന; തുടർന്ന് സ്റ്റാറ്റിക് മോഡൽ മെറ്റാഡാറ്റയ്ക്കും പിന്നെ സമന്വയിപ്പിച്ച
   `modalities_input`-നും. `audio` ഇല്ലാത്ത പ്രഖ്യാപിത ഇൻപുട്ട് ലിസ്റ്റിന്റെ മൂല്യം `false` ആണ്; ശേഷി സംബന്ധിച്ച
   തെളിവുകളൊന്നുമില്ലെങ്കിൽ മൂല്യം `null` ആയി തുടരുന്നു. `false`, `null` എന്നിവ രണ്ടും
   യാഥാസ്ഥിതിക ബ്രിഡ്ജ് സജീവമാക്കുമ്പോൾ, `true` അതിനെ ബൈപാസ് ചെയ്യുന്നു.
2. `modalityBridgeAudio*` ക്രമീകരണങ്ങൾ പരിഹരിച്ച് പങ്കിട്ട `detectMediaParts()`
   ഡിറ്റക്ടർ ഉപയോഗിച്ച് ഓരോ സന്ദേശത്തിൽനിന്നും സ്പ്ലൈസ് ചെയ്യാവുന്ന ടോപ്പ്-ലെവൽ
   ഓഡിയോ ഭാഗങ്ങൾ എക്സ്ട്രാക്റ്റ് ചെയ്യുക. പിന്തുണയ്ക്കുന്ന വയർ രൂപങ്ങൾ OpenAI `input_audio`, `audio_url`,
   `source.media_type: "audio/*"` എന്നിവയാണ്. റൂട്ടിംഗിനായി നെസ്റ്റഡ് ഓഡിയോ കണ്ടെത്തുമെങ്കിലും
   സ്പ്ലൈസ് പാത അത് നീക്കം ചെയ്യില്ല. പ്രവർത്തനം `modalityBridgeAudioMaxClips` അനുസരിച്ച് പരിമിതപ്പെടുത്തിയിരിക്കുന്നു;
   തുടർന്നുള്ള ഭാഗങ്ങൾ മാറ്റമില്ലാതെ തുടരും.
3. ക്രമീകരിച്ച `provider/model` മാനിക്കുക, അല്ലെങ്കിൽ `selectAudioBridgeModel()`-നെ
   സ്ഥിരതയുള്ള കാറ്റലോഗ് ക്രമത്തിൽ `AUDIO_TRANSCRIPTION_PROVIDERS` പരിശോധിക്കാനും ഉപയോഗിക്കാവുന്ന സജീവ പ്രൊവൈഡർ
   ക്രെഡൻഷ്യൽ ഉള്ള ആദ്യ മോഡൽ തിരഞ്ഞെടുക്കാനും അനുവദിക്കുക.
4. `callAudioTranscription()` base64/data-URI ഓഡിയോയെ multipart
   `file` ആക്കി മാറ്റുന്നു, അല്ലെങ്കിൽ DNS പിന്നിംഗും 25 MB പരിധിയുമുള്ള public-only ഔട്ട്ബൗണ്ട്
   ഗാർഡ് വഴി റിമോട്ട് `audio_url` ഡൗൺലോഡ് ചെയ്യുന്നു. തുടർന്ന് അത് ഫയലും തിരഞ്ഞെടുത്ത
   മോഡലും ലോക്കൽ `/v1/audio/transcriptions` സ്വയം-ലൂപ്പിലേക്ക് POST ചെയ്യുന്നു; പ്രാമാണീകരണത്തിന്
   `resolveSelfLoopBearer()` ഉപയോഗിക്കുന്നു. നിലവിലുള്ള ട്രാൻസ്ക്രിപ്ഷൻ റൂട്ട് സാധാരണ
   ക്രെഡൻഷ്യൽ ലുക്കപ്പ്, കൂൾഡൗൺ/റേറ്റ്-ലിമിറ്റ് കൈകാര്യം ചെയ്യൽ, പ്രൊവൈഡർ ഡിസ്പാച്ച് എന്നിവ നിർവഹിക്കുന്നു.
5. വിജയകരമായ കോളുകൾ അവയുടെ ഭാഗങ്ങളെ `[Audio N]: <transcript>` ഉപയോഗിച്ച് മാറ്റിസ്ഥാപിക്കുന്നു. കോളുകൾ
   `Promise.allSettled` ഉപയോഗിച്ചാണ് പ്രവർത്തിക്കുന്നത്: ഒറ്റപ്പെട്ട പരാജയം ആ യഥാർത്ഥ
   ഓഡിയോ ഭാഗം നിലനിർത്തുന്നു (#4012 കരാർ). എല്ലാ കോളുകളും പരാജയപ്പെടുകയും ലക്ഷ്യം
   `supportsAudio === false` ആണെന്ന് തെളിയിക്കപ്പെടുകയും ചെയ്താൽ, ഭാഗങ്ങൾ
   `[Audio N]: (ലഭ്യമല്ല — ഒരു STT പ്രൊവൈഡറും കണക്റ്റ് ചെയ്തിട്ടില്ല)` ആയി മാറുന്നു (#8430 കരാർ). ഒരു
   അജ്ഞാത ലക്ഷ്യത്തിന് (`null`), എല്ലാ കോളുകളും പരാജയപ്പെട്ടാലും ഉള്ളടക്കം മാറ്റമില്ലാതെ തുടരും. ഉപയോഗിക്കാവുന്ന STT
   ക്രെഡൻഷ്യൽ ഇല്ലാത്ത, ടെക്സ്റ്റ്-മാത്രം പിന്തുണയ്ക്കുന്നതായി തെളിയിച്ച ലക്ഷ്യത്തിന് നെറ്റ്വർക്ക് കോൾ നടത്താതെ അതേ വ്യക്തമായ
   സ്റ്റബ് ലഭിക്കും.

വിജയകരമായ ട്രാൻസ്ക്രിപ്റ്റുകൾ പ്രോസസ്-വ്യാപകമായ Modality Bridge LRU/TTL കാഷ് ഉപയോഗിക്കുന്നു.
കീയിൽ ഓഡിയോ റഫറൻസ്, സ്ഥിരമായ `audio-transcription` ഓപ്പറേഷൻ
ലേബൽ, തിരഞ്ഞെടുത്ത STT മോഡൽ എന്നിവ സംയോജിപ്പിച്ചിരിക്കുന്നു; പരാജയങ്ങൾ ഒരിക്കലും കാഷ് ചെയ്യില്ല. ഓഡിയോ ശ്രമങ്ങൾ
പങ്കിട്ട `bridged`, `cacheHits`, `failures`, `lastUsedAt` കൗണ്ടറുകൾ അപ്ഡേറ്റ് ചെയ്യുന്നു.
രൂപാന്തരപ്പെടുത്തിയ പ്രതികരണങ്ങളിൽ
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ഉൾപ്പെടുന്നു; മാറ്റമില്ലാത്ത
അഭ്യർത്ഥനകൾക്ക് Audio Bridge സെഗ്മെന്റ് ലഭിക്കില്ല.

റൺടൈം ക്രമീകരണങ്ങൾ DB-യിൽ സൂക്ഷിക്കുന്നതും Zod ഉപയോഗിച്ച് സാധൂകരിക്കുന്നതുമാണ്:

| കീ                            | ഡിഫോൾട്ട് | പരിധി                  |
| ----------------------------- | --------- | ---------------------- |
| `modalityBridgeAudioEnabled`  | `true`    | —                      |
| `modalityBridgeAudioModel`    | `""`      | Auto അല്ലെങ്കിൽ STT ID |
| `modalityBridgeAudioTimeout`  | `60000`   | 1000–300000            |
| `modalityBridgeAudioMaxClips` | `3`       | 1–10                   |

പങ്കിട്ട കാഷ് ഇപ്പോഴും `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, `modalityBridgeCacheMaxEntries` എന്നിവയാൽ നിയന്ത്രിക്കപ്പെടുന്നു.

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

അറിയപ്പെടുന്ന നേറ്റീവ് വീഡിയോ പിന്തുണയില്ലാത്ത ഒരു ടാർഗെറ്റ് വിളിക്കപ്പെടുന്നതിന് മുമ്പ്, Chat Completions `messages`-ലെയും Responses API `input`-ലെയും ടോപ്പ്-ലെവൽ വീഡിയോ ഭാഗങ്ങളെ ഇന്റർസെപ്റ്റ് ചെയ്യുന്നു. പിന്തുണയ്ക്കുന്ന രൂപങ്ങൾ `input_video`, `video_url`, `video_source`, HTTPS URL-കൾ, `data:video/*;base64,...` ഡാറ്റ URI-കൾ എന്നിവയാണ്. ടെക്സ്റ്റിലെ സാധാരണ ഫയൽനാമങ്ങളെ വീഡിയോയായി പരിഗണിക്കില്ല.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) അഭ്യർത്ഥന ട്രാവേഴ്സൽ, ശേഷി/നയ പരിശോധന, ഓരോ അഭ്യർത്ഥനയുടെയും അഗ്രിഗേഷൻ, പ്രതികരണ പേലോഡ് എന്നിവ കൈകാര്യം ചെയ്യുന്നു. ഓരോ വീഡിയോയ്ക്കുമുള്ള പ്രവർത്തനം — വീഡിയോ ലഭ്യമാക്കൽ, പൂർണ്ണ-ഫല കാഷ്, ഫ്രെയിം സീക്വൻസിന്റെ വിവരണം തയ്യാറാക്കൽ (കോളർ പ്രഖ്യാപിച്ച ഏതെങ്കിലും ഓഡിയോ ട്രാൻസ്ക്രിപ്റ്റ് ഇതിൽ സംയോജിപ്പിക്കുന്നു), ഓരോ ശ്രമത്തിന്റെയും മെട്രിക്കുകൾ/അബോർട്ട്/ക്ലീനപ്പ് — `videoBridgePipeline.ts`-ലെ `processVideoPart`-ന് പിന്നിൽ മറച്ചിരിക്കുന്നു; `preCall`-ന്റെ ലൂപ്പിനുള്ളിൽ ഓരോ വീഡിയോ ഭാഗത്തിനും ഇത് ഒരിക്കൽ വീതം വിളിക്കപ്പെടുന്നു. വ്യക്തമായ പോർട്ട് അതിരുകളായ `VideoMediaBrokerPort` (ബൈറ്റുകൾ ലഭ്യമാക്കുകയും സാമ്പിൾ ചെയ്ത ഫ്രെയിമുകൾ എക്സ്ട്രാക്റ്റ് ചെയ്യുകയും ചെയ്യുന്നത്), `VideoAudioTranscriptionPort` (കോളർ പ്രഖ്യാപിച്ച ഓഡിയോ ട്രാൻസ്ക്രിപ്റ്റിനെ സാമ്പിൾ ചെയ്ത ക്യാപ്ഷനുകളുമായി സംയോജിപ്പിക്കുന്നത്), `VideoDrilldownPort` (ഫ്രെയിം ഡ്രിൽ-ഡൗൺ പെർസിസ്റ്റൻസ് അതിര്; ഇത് ഇതുവരെ `processVideoPart`-ലേക്ക് വയർ ചെയ്തിട്ടില്ല — നിലവിൽ പ്രത്യേകം `/api/modality-bridge/video/drilldown` റൂട്ട് മാത്രമാണ് ഡ്രിൽ-ഡൗൺ എൻട്രികൾ എഴുതുന്നത്) എന്നിവയും ആ മൊഡ്യൂൾ നിർവചിക്കുന്നു.

പൊതു `/v1` അഭ്യർത്ഥന പാത ഒരിക്കലും ഒരു സബ്പ്രോസസ് ഇംപോർട്ട് ചെയ്യുകയോ പ്രവർത്തിപ്പിക്കുകയോ ചെയ്യുന്നില്ല. റിമോട്ട് വീഡിയോകൾ 50 MiB പരിധിക്കുള്ളിൽ ഡൗൺലോഡ് ചെയ്യുന്നു; മോഡൽ/സന്ദേശങ്ങൾ/ഫ്രെയ്മിംഗ് എൻവലപ്പ് 50 MiB എന്ന പൊതു JSON അഭ്യർത്ഥന അഡ്മിഷൻ പരിധിക്കുള്ളിൽ നിലനിർത്താൻ, ഇൻലൈൻ base64 വീഡിയോകൾക്ക് ഓരോ വീഡിയോയ്ക്കും ഡീകോഡ് ചെയ്ത വലുപ്പത്തിൽ പരമാവധി 36 MiB എന്ന സൂക്ഷ്മമായ പരിധിയുണ്ട്. അലോക്കേഷനുമുമ്പ് ഇൻലൈൻ നീളവും ഡീകോഡ് ചെയ്ത വലുപ്പത്തിന്റെ കണക്കുകളും പരിശോധിക്കുന്നു. നിലവിലുള്ള, DNS പിന്നിംഗ് ഉള്ള പബ്ലിക്-ഒൺലി ഔട്ട്ബൗണ്ട് ഗാർഡ് ഉപയോഗിച്ച്, പ്രാരംഭ റിമോട്ട് URL-ലും ഓരോ റീഡയറക്ടിലും HTTPS നിർബന്ധമാണ്. തുടർന്ന് ബൈറ്റുകൾ കൃത്യമായ ആന്തരിക `POST /api/modality-bridge/video/extract` ബ്രോക്കർ അതിര് കടക്കുന്നു. ആ റൂട്ട് `LOCAL_ONLY`-യും `SPAWN_CAPABLE`-യും ആണ്; ഓരോ പ്രോസസിനും പ്രത്യേകം ഓതന്റിക്കേറ്റ് ചെയ്ത, വിശ്വസനീയമായ ലൂപ്പ്ബാക്ക് അഭ്യർത്ഥനകൾ മാത്രമേ അത് സ്വീകരിക്കൂ; URL, ഫയൽസിസ്റ്റം പാത, എക്സിക്യൂട്ടബിൾ, അല്ലെങ്കിൽ ആർഗ്യുമെന്റ് ലിസ്റ്റ് എന്നിവ അത് ഒരിക്കലും സ്വീകരിക്കില്ല. API ബോഡി-സൈസ് പൈപ്പ്ലൈനും ഹാൻഡ്ലറിന്റെ ഇൻക്രിമെന്റൽ ബോഡി റീഡറും സ്വതന്ത്രമായി 50 MiB ബ്രോക്കർ ഇൻപുട്ട് പരിധി നടപ്പാക്കുന്നു. അതിന്റെ പരിധിയുള്ള ക്യൂ ഒരേസമയം ഒരു എക്സ്ട്രാക്ഷൻ മാത്രം പ്രവർത്തിപ്പിക്കുന്നു, നാല് പെൻഡിംഗ് ജോലുകൾ അനുവദിക്കുന്നു, കൂടാതെ പെൻഡിംഗ് ഇൻപുട്ട് 100 MiB ആയി പരിമിതപ്പെടുത്തുന്നു.

ബ്രോക്കറിനുള്ളിൽ, `ffprobe` ഒരു സ്വകാര്യ ലോക്കൽ ഫയൽ വായിക്കുന്നു; സ്ഥിരമായ ഫോർമാറ്റ് അലൗലിസ്റ്റിൽ പ്ലേലിസ്റ്റ്, മാനിഫെസ്റ്റ് ഫോർമാറ്റുകൾ ഉൾപ്പെടുന്നില്ല. അനുവദിച്ച MOV-ഫാമിലി കണ്ടെയ്നറുകളിൽ, ബാഹ്യ MOV ഡാറ്റ റഫറൻസുകൾ ഡിഫോൾട്ടായി പ്രവർത്തനരഹിതമായി തുടരുന്നു; സ്ഥിരമായ കമാൻഡ് അവ പ്രവർത്തനക്ഷമമാക്കുന്നില്ല. `ffprobe`, `ffmpeg` എന്നിവ രണ്ടും `file`-മാത്രമുള്ള പ്രോട്ടോക്കോൾ വൈറ്റ്ലിസ്റ്റ്, ഒരു ത്രെഡ്, സ്ഥിരമായ ആർഗ്യുമെന്റ് അറേകൾ, ഷെൽ ഇല്ലാത്ത നിർവഹണം, `PATH`-ൽ നിന്ന് റിസോൾവ് ചെയ്യുന്ന എക്സിക്യൂട്ടബിളുകൾ എന്നിവ ഉപയോഗിക്കുന്നു. അറ്റാച്ച് ചെയ്ത ചിത്ര-കവർ സ്ട്രീമുകൾ പ്ലേ ചെയ്യാവുന്ന കാൻഡിഡേറ്റുകളല്ല. പ്ലേ ചെയ്യാവുന്ന എല്ലാ സ്ട്രീമുകളും പരിധികൾ പാലിക്കണം; ഡിറ്റർമിനിസ്റ്റിക് ആയ ഏറ്റവും കുറഞ്ഞ ഇൻഡക്സ് ഫാൾബാക്കിന് മുമ്പ് വ്യക്തമായി നിർവചിച്ച ഡിഫോൾട്ട് സ്ട്രീമിന് മുൻഗണന നൽകുന്നു. വീഡിയോകൾക്ക് പരമാവധി 600 സെക്കൻഡ് ദൈർഘ്യം, ഓരോ അളവിലും 8,192 പിക്സൽ, 33,554,432 സോഴ്സ് പിക്സലുകൾ എന്നീ പരിധികളുണ്ട്. FFmpeg മധ്യബിന്ദുവിലുള്ള 1–16 JPEG ഫ്രെയിമുകൾ സാമ്പിൾ ചെയ്യുന്നു, ചെറിയ ഇൻപുട്ടുകൾ അപ്സ്കെയിൽ ചെയ്യാതെ നീളമുള്ള വശം പരമാവധി 1,024 പിക്സലായി ഡൗൺസ്കെയിൽ ചെയ്യുന്നു, കൂടാതെ അതിന് ഒരിക്കലും URL ലഭിക്കില്ല. ഡിഫോൾട്ടായി സാമ്പ്ലിംഗ് `uniform` ആണ്. ഐച്ഛികമായ `scene_aware`, പരീക്ഷണാത്മകമായ `segment_aware` നയങ്ങൾ ഇതിനകം വാലിഡേറ്റ് ചെയ്ത ലോക്കൽ സ്ട്രീമിൽ ഒരു അധിക സ്ഥിരമായ FFmpeg പാസ് നടത്തുകയും, പരിധിയുള്ള `showinfo` സീൻ ടൈംസ്റ്റാമ്പുകൾ തിരഞ്ഞെടുക്കുകയും, ഡിറ്റക്ടർ പരാജയം, ടൈംഔട്ട്, തെറ്റായ രൂപത്തിലുള്ള ഔട്ട്പുട്ട്, അല്ലെങ്കിൽ ശൂന്യമായ കാൻഡിഡേറ്റ് സെറ്റ് എന്നിവ ഉണ്ടായാൽ അതേ യൂണിഫോം മധ്യബിന്ദുക്കളിലേക്ക് ഡിറ്റർമിനിസ്റ്റിക് ആയി ഫാൾബാക്ക് ചെയ്യുകയും ചെയ്യുന്നു. വാലിഡേറ്റ് ചെയ്ത സീൻ ഇടവേളകൾക്ക് ആനുപാതികമായി മധ്യബിന്ദു സാമ്പിളുകൾ `segment_aware` മോഡ് അനുവദിക്കുന്നു; സെഗ്മെന്റ്-അവെയർ എവിഡൻസും ഫാൾബാക്ക് പെരുമാറ്റവും താഴെ വിശദീകരിച്ചിരിക്കുന്നു. ഓരോ നയത്തിലും തിരഞ്ഞെടുപ്പിന് ശേഷം 16-ഫ്രെയിം എന്ന കർശന പരിധി പ്രയോഗിക്കുന്നു. ഒരു സീൻ-അവെയർ അഭ്യർത്ഥനയ്ക്ക് ഒരു ഫ്രെയിം മാത്രം അനുവദിക്കുന്ന ബജറ്റ് ഉള്ളപ്പോൾ, സജീവമായ പൂർണ്ണ-വീഡിയോ അല്ലെങ്കിൽ ഫോക്കസ് വിൻഡോയുടെ യൂണിഫോം മധ്യബിന്ദു ഉപയോഗിക്കുകയും `policyEffective: uniform` എന്ന് റിപ്പോർട്ട് ചെയ്യുകയും ചെയ്യുന്നു: തിരഞ്ഞെടുത്ത ഒരൊറ്റ സീൻ ഫ്രെയിമിന് സമയപരമായ രണ്ട് അറ്റങ്ങളും സംരക്ഷിക്കാനാവില്ല. കോളർക്ക് വേണമെങ്കിൽ പരിധിയുള്ള ഒരു ഫോക്കസ് വിൻഡോ (`start`/`end` സെക്കൻഡുകൾ) നൽകാം; അതിരുകൾ മീഡിയ ദൈർഘ്യത്തിലേക്ക് ക്ലാമ്പ് ചെയ്യുന്നു, വിപരീതമായതോ പരിധിയില്ലാത്തതോ ആയ വിൻഡോകൾ നിരസിക്കുന്നു, എല്ലാ സാമ്പ്ലിംഗ് നയങ്ങളും നോർമലൈസ് ചെയ്ത ഇടവേളയ്ക്കുള്ളിൽ മാത്രമാണ് നടപ്പാക്കുന്നത്. ഫലമായുണ്ടാകുന്ന വിൻഡോ സാമ്പ്ലിംഗ് മെറ്റാഡാറ്റയിലും വിശ്വസനീയമല്ലാത്ത വിവരണ പ്രിഫിക്സിലും ഉൾപ്പെടുത്തുന്നു; ഇതുവഴി ഡൗൺസ്ട്രീം മോഡലുകൾക്ക് ഫോക്കസ് ചെയ്ത ഒരു ഭാഗത്തെ പൂർണ്ണ ടൈംലൈനിൽ നിന്ന് വേർതിരിച്ചറിയാൻ കഴിയും.

സെമാന്റിക് ക്യാപ്ഷൻ ഫോക്കസ് വേറിട്ടതും വ്യക്തവുമായ ഒരു ക്രമീകരണമാണ്. ഡിഫോൾട്ട് `full` വിശകലന മോഡ് നിലവിലുള്ള ഫ്രെയിം പ്രോംപ്റ്റ് നിലനിർത്തുകയും അഭ്യർത്ഥനയിലെ ടെക്സ്റ്റ് ക്യാപ്ഷൻ മോഡലിലേക്ക് ഒരിക്കലും ഫോർവേഡ് ചെയ്യാതിരിക്കുകയും ചെയ്യുന്നു. `focused` മോഡിൽ, അതേ Chat അല്ലെങ്കിൽ Responses കണ്ടെയ്നറിൽ നിന്ന് ഉപയോക്താവ് രചിച്ച ഏറ്റവും പുതിയ ശൂന്യമല്ലാത്ത `text`/`input_text` മാത്രം ബ്രിഡ്ജ് വായിക്കുന്നു, അത് NFC-യിലേക്ക് നോർമലൈസ് ചെയ്യുന്നു, കൺട്രോൾ പ്രതീകങ്ങളും വൈറ്റ്സ്പേസും ഏകീകരിക്കുന്നു, കൂടാതെ 500 Unicode കോഡ് പോയിന്റുകളായി പരിമിതപ്പെടുത്തുന്നു. ശൂന്യമായ ഫലം ലഭിച്ചാൽ കൃത്യമായ `full` പ്രോംപ്റ്റിലേക്ക് ഫാൾബാക്ക് ചെയ്യുന്നു. ഉപയോഗയോഗ്യമായ ഒരു സൂചന പ്രത്യേകം വിശ്വസനീയമല്ലാത്ത-ഉപയോക്തൃ-സന്ദർഭ ബ്ലോക്കിൽ JSON ആയി സീരിയലൈസ് ചെയ്യുന്നു; നിരീക്ഷിക്കാവുന്ന വിശദാംശങ്ങൾക്ക് മുൻഗണന നൽകാൻ മാത്രമേ അതിന് കഴിയൂ. മീഡിയയിൽ ദൃശ്യമായോ കേൾക്കാവുന്നതായോ ഉള്ള നിർദ്ദേശങ്ങൾ പാലിക്കരുതെന്ന പ്രത്യേകം മുന്നറിയിപ്പിനെ അതിന് മറികടക്കാനാവില്ല. ടെക്സ്റ്റ് അടിസ്ഥാനത്തിലുള്ള ഫോക്കസ് ഒരിക്കലും `start`/`end` അനുമാനിക്കുകയോ ടെംപറൽ സാമ്പ്ലർ മാറ്റുകയോ ചെയ്യുന്നില്ല.

#### FU-07 ഘടനാപരമായ സെഗ്മെന്റ് തെളിവ്

ഇതിനകം വാലിഡേറ്റ് ചെയ്ത ലോക്കൽ വീഡിയോ സ്ട്രീമിൽ പരിധിയുള്ള ഒരു പ്രീ-അനാലിസിസ് പാസ് `segment_aware` ഉപയോഗിക്കുന്നു. സ്ഥിരമായ ഫിൽട്ടർ ചെയിൻ ആദ്യം വീതി പരമാവധി 320 പിക്സലായി സ്കെയിൽ ചെയ്യുന്നു, സീൻ മാറ്റങ്ങളും ഫ്രീസ് ചെയ്ത ഇടവേളകളും കണ്ടെത്തുന്നു, തുടർന്ന് ബ്ലർ, ശരാശരി ലൂമ, സ്പേഷ്യൽ/ടെംപറൽ വിവരങ്ങൾ എന്നിവയ്ക്കായി സെക്കൻഡിൽ 1 ഫ്രെയിം എന്ന നിരക്കിൽ സാമ്പിൾ ചെയ്യുന്നു. ഈ പാസ് 600 ഘടനാപരമായ സാമ്പിളുകൾ, ഒരു FFmpeg/ഫിൽട്ടർ ത്രെഡ്, അതേ `file`-മാത്രമുള്ള പ്രോട്ടോക്കോൾ, കണ്ടെയ്നർ അലൗലിസ്റ്റുകൾ, 1 MiB പ്രോസസ്-ഔട്ട്പുട്ട് പരിധി, ബ്രോക്കറിന്റെ പങ്കിട്ട അബോർട്ട്/ഡെഡ്ലൈനിനുള്ളിൽ പരമാവധി 30 സെക്കൻഡ് എന്നിവയായി പരിമിതപ്പെടുത്തിയിരിക്കുന്നു. അഭ്യർത്ഥനയിൽ നിന്ന് ഒരു കമാൻഡ്, ഫിൽട്ടർ, പാത, അല്ലെങ്കിൽ URL എന്നിവ അത് ഒരിക്കലും സ്വീകരിക്കില്ല.

`audioFusionFailureCodes`), ഫല-കാഷ് മെറ്റാഡാറ്റയിലും, ബ്രിഡ്ജ് ഫ്യൂഷൻ കൗണ്ടറുകളിലും സംരക്ഷിക്കപ്പെടുന്നു. ഡിഫോൾട്ട് Video Bridge പാത speech-to-text പ്രവർത്തിപ്പിക്കുകയോ മീഡിയയുടെ രണ്ടാമത്തെ പകർപ്പ് ഡൗൺലോഡ് ചെയ്യുകയോ ചെയ്യുന്നില്ല; ആ വ്യക്തമായ ട്രാക്ക് ഇല്ലെങ്കിൽ, അത് വീഡിയോ-മാത്രം എന്ന നിലയിൽ തുടരുന്നു.

**ട്രാൻസ്ക്രിപ്റ്റ് നിലനിർത്തൽ (#12150 P1).** Video Bridge (അത് തന്നെ opt-in ആണ്) ഒരു ട്രാൻസ്ക്രിപ്റ്റ് ക്യൂ റെൻഡർ ചെയ്യുമ്പോഴെല്ലാം ഇത് സ്വയമേവ ബാധകമാകും — പ്രത്യേക നിലനിർത്തൽ ഫ്ലാഗ് ഇല്ല. ഒരു അഭ്യർത്ഥന ഏതെങ്കിലും ട്രാൻസ്ക്രിപ്റ്റ് ക്യൂ (കോളർ പ്രഖ്യാപിച്ച `transcript` അല്ലെങ്കിൽ ഫ്യൂസ് ചെയ്ത `audioTranscript`) റെൻഡർ ചെയ്യുമ്പോൾ, ഗാർഡ്റെയിൽ അതിനെ `videoBridgeObserved` എന്ന് അടയാളപ്പെടുത്തുകയും വീഡിയോ വിവരണത്തിന്റെ തിരുത്തിമറച്ച ഒരു ഷാഡോ സൃഷ്ടിക്കുകയും ചെയ്യുന്നു — ഓരോ ക്യൂവിന്റെയും സ്വതന്ത്ര-ടെക്സ്റ്റ് ബോഡി `[redacted-video-transcript]` ഉപയോഗിച്ച് മാറ്റിസ്ഥാപിച്ച, സമാനമായ ഒരു റെൻഡറിങ്; സ്ട്രിങ് അസംബിൾ ചെയ്യുന്നതിന് മുമ്പ് ഘടനാബദ്ധമായ ക്യൂ ഫീൽഡ് പകരംവച്ചാണ് ഇത് നിർമിക്കുന്നത് (ഫ്ലാറ്റ് ചെയ്ത ടെക്സ്റ്റ് പാഴ്സ് ചെയ്തുകൊണ്ടല്ല; അതിനാൽ `]` അടങ്ങിയ `[inaudible]`/`[music]` പോലുള്ള ബോഡികൾ ഉൾപ്പെടെ, ദോഷകരമോ സാധാരണമോ ആയ ഒരു ക്യൂ ഉള്ളടക്കവും നിലനിൽക്കാൻ കഴിയില്ല). സ്ഥിരമായി സൂക്ഷിക്കുന്ന കോൾ-ലോഗ് അഭ്യർത്ഥനാ ബോഡി, ഉള്ളടക്ക സമത്വം ഉപയോഗിച്ച് പൊരുത്തപ്പെടുത്തി, വീഡിയോയിൽനിന്ന് ഉത്ഭവിച്ച ഓരോ ടെക്സ്റ്റ് ഭാഗവും ആ തിരുത്തിമറച്ച ഷാഡോ ഉപയോഗിച്ച് മാറ്റുന്നു; പൂർത്തിയായ പ്രീ-കോൾ ഗാർഡ്റെയിൽ പേലോഡിൽനിന്ന് `fullText` ആങ്കർ വീണ്ടും വായിക്കുന്നതിനാൽ, പിന്നീടുള്ള ചെയിൻ ഗാർഡ്റെയിലുകൾ (PII, ക്രെഡൻഷ്യൽ മാസ്കറുകൾ, മുൻഗണനകൾ 10/95) വിവരണ ടെക്സ്റ്റ് അതേ സ്ഥാനത്ത് മാറ്റിയെഴുതിയതിനുശേഷവും, സിസ്റ്റം-പ്രോംപ്റ്റ്/ഹാൻഡ്ഓഫ്/മെമ്മറി ഇൻജക്ഷൻ സന്ദേശ അറേയുടെ ആകൃതി മാറ്റിയതിനുശേഷവും പൊരുത്തപ്പെടുത്തൽ വിജയിക്കുന്നു. മോഡലിലേക്ക് അപ്സ്ട്രീം അയയ്ക്കുന്ന ബോഡിയിൽ മാറ്റമില്ല. നിരീക്ഷിക്കപ്പെട്ട ഒരു അഭ്യർത്ഥന സ്ഥിരമായ Memory-യെയും പൂരിപ്പിക്കുന്നില്ല (അഭ്യർത്ഥനയിൽനിന്നും പ്രതികരണത്തിൽനിന്നുമുള്ള എക്സ്ട്രാക്ഷൻ ഒഴിവാക്കപ്പെടുന്നു); അതിനാൽ മോഡലിന്റെ സ്വന്തം മറുപടിക്ക് ട്രാൻസ്ക്രിപ്റ്റ് ടെക്സ്റ്റ് Memory-യിലേക്ക് പ്രതിധ്വനിപ്പിക്കാൻ കഴിയില്ല.

ഓരോ പ്രിൻസിപ്പലിനും 16 എൻട്രികളും 64 MiB കാനോണിക്കൽ JPEG ഡാറ്റയും എന്ന പരിധിയുണ്ട്. ആ പരിധികൾ ആഗോളമായ 64-എൻട്രി/256 MiB പരിധിയിൽനിന്ന് സ്വതന്ത്രമാണ്: പ്രിൻസിപ്പൽ ക്വോട്ടയിലെ സമ്മർദം, ആഗോള LRU ഒഴിപ്പിക്കൽ പരിഗണിക്കുന്നതിന് മുമ്പ്, ആ പ്രിൻസിപ്പലിന്റെ ഏറ്റവും കുറച്ച് അടുത്തിടെ ഉപയോഗിച്ച എൻട്രികൾ മാത്രം ഒഴിപ്പിക്കുന്നു. കാഷ് പ്രവർത്തനത്തിനിടെ കാലഹരണപ്പെട്ട എൻട്രികൾ പ്രിൻസിപ്പൽ അക്കൗണ്ടിങ്ങിൽനിന്നും ആഗോള അക്കൗണ്ടിങ്ങിൽനിന്നും നീക്കംചെയ്യപ്പെടുന്നു; അതേസമയം റദ്ദാക്കലും സാധൂകരണ പരാജയവും ഭാഗികമായ ഒരു പകരംവയ്ക്കൽ commit ചെയ്യുന്നില്ല.

text marker-കളായി മാറുന്നു; അതിനാൽ അസംസ്കൃത വീഡിയോ ഒന്നും ശേഷിക്കില്ല. Capability അജ്ഞാതമാണെങ്കിൽ, ആ ഭാഗങ്ങൾ
മാറ്റമില്ലാതെ തുടരുന്നു. `supportsVideo === true` ഉള്ള target-ുകൾ bridge ഒഴിവാക്കുന്നു.
Client request abort signal, download, broker queue, subprocess-ുകൾ, caption call-ുകൾ എന്നിവയിലൂടെ പ്രചരിക്കുന്നു;
abort-ുകൾ വീഡിയോകൾക്കിടയിൽ പ്രോസസ്സിംഗ് നിർത്തുകയും അസംസ്കൃത മീഡിയയിലേക്ക് ഒരിക്കലും fail open ചെയ്യാതിരിക്കുകയും ചെയ്യുന്നു.

Runtime ക്രമീകരണങ്ങൾ DB-backed ഉം Zod-validated ഉം ആണ്:

| കീ                                  | ഡിഫോൾട്ട്   | പരിധി / പെരുമാറ്റം                                                                                                               |
| ----------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | ഐച്ഛിക runtime, opt-in                                                                                                           |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` പൊതുവായ അടിക്കുറിപ്പുകൾ നിലനിർത്തുന്നു; `focused` പരിധിയിട്ട, വിശ്വസനീയമല്ലാത്ത ഏറ്റവും പുതിയ user context ഉപയോഗിക്കുന്നു |
| `modalityBridgeVideoModel`          | `""`        | Vision Bridge മോഡൽ പാരമ്പര്യമായി സ്വീകരിക്കുക                                                                                    |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                                             |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, അല്ലെങ്കിൽ ആനുപാതികമായ `segment_aware`; detector പരാജയം `uniform`-ലേക്ക് fallback ചെയ്യുന്നു           |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                                              |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                                                   |

120 സെക്കൻഡിന് മുകളിലുള്ള പഴയ persisted Video timeout മൂല്യങ്ങൾ
broker deadline-ലേക്ക് clamp ചെയ്യപ്പെടുന്നു; ആ പരിധിക്ക് മുകളിലുള്ള പുതിയ settings write-ുകൾ നിരസിക്കപ്പെടുന്നു.
`GET /api/modality-bridge/video/runtime`, authentication അല്ലെങ്കിൽ runtime probing-ന് മുമ്പ് വിശ്വസനീയമായി stamp ചെയ്ത loopback
locality ആവശ്യപ്പെടുന്നു; തുടർന്ന് management auth ആവശ്യപ്പെടുന്നു. ഇത് `available`, ശുദ്ധീകരിച്ച FFmpeg/ffprobe version-ുകൾ,
runtime ലഭ്യമല്ലാത്തപ്പോൾ സ്ഥിരമായ ഒരു reason എന്നിവ മാത്രം തിരികെ നൽകുന്നു. Internal extraction endpoint ഒരു
പൊതു upload API അല്ല: queue saturation `503`-ഉം `Retry-After`-ഉം തിരികെ നൽകുന്നു, caller
disconnect `499` തിരികെ നൽകുന്നു, സ്ഥിരമായ broker deadline `504` തിരികെ നൽകുന്നു. പരിവർത്തനം ചെയ്ത response-ുകൾ,
Vision അല്ലെങ്കിൽ Audio segment-ുകൾ നീക്കം ചെയ്യാതെ, കേന്ദ്ര
`x-omniroute-modality-bridge` header-ലേക്ക്
`video->text;model=<visionModel>;parts=<videos>` ചേർക്കുന്നു.

### PII Masker (`piiMasker.ts`)

**രണ്ട്** ഘട്ടങ്ങളിലും പ്രവർത്തിക്കുന്നു.

- **`preCall`** payload clone ചെയ്യുന്നു; `system`, `messages`, `input`,
  `prompt` എന്നിവയിലൂടെ (plain string item-ുകൾ ഉൾപ്പെടെ) സഞ്ചരിച്ച് string
  `content`/`text` field-ുകളിൽ `processPII()` (`@/shared/utils/inputSanitizer`-ൽ നിന്ന്)
  പ്രയോഗിക്കുന്നു. `PII_REDACTION_ENABLED=true` ആയിരിക്കുമ്പോൾ, കണ്ടെത്തിയ PII outbound
  payload-ൽ redact ചെയ്യപ്പെടുന്നു. ഇത് `INPUT_SANITIZER_MODE`-ൽ നിന്ന് സ്വതന്ത്രമാണ് (അത്
  prompt-injection policy മാത്രം നിയന്ത്രിക്കുന്നു). Redaction ഓഫായിരിക്കുമ്പോൾ, content
  തിരുത്താതെ call detection count-ുകൾ രേഖപ്പെടുത്തുന്നു.
- **`postCall`** response deep-clone ചെയ്യുന്നു, `sanitizePIIResponse()`-ഉം
  Responses-API-shape masker-ഉം (`maskResponsesOutput` — `output_text`,
  `output[].content[].text` എന്നിവ ഉൾക്കൊള്ളുന്നു) പ്രവർത്തിപ്പിക്കുന്നു. ഏതെങ്കിലും redaction സംഭവിച്ചാൽ,
  പരിഷ്കരിച്ച response യഥാർത്ഥത്തിനെ മാറ്റിസ്ഥാപിക്കുന്നു.

Guardrail ഒരിക്കലും block ചെയ്യുന്നില്ല; അത് annotate (`meta.detections`,
`meta.redacted`) ചെയ്യുകയോ rewrite ചെയ്യുകയോ മാത്രം ചെയ്യുന്നു.

### Prompt Injection (`promptInjection.ts`)

User നൽകിയ content-ലെ adversarial structure-ുകൾ കണ്ടെത്തുകയും ക്രമീകരിച്ച
policy നടപ്പിലാക്കുകയും ചെയ്യുന്നു. പെരുമാറ്റം environment variable-ുകളും constructor
option-ുകളും നിയന്ത്രിക്കുന്നു:

| ക്രമീകരണം              | Env var                                                                                                | ഡിഫോൾട്ട് | പ്രഭാവം                                                                                                                                                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| പ്രവർത്തനക്ഷമമാക്കിയത് | `INPUT_SANITIZER_ENABLED`                                                                              | `true`    | `false` ആയിരിക്കുമ്പോൾ, guardrail ഷോർട്ട്-സർക്യൂട്ട് ചെയ്യുന്നു.                                                                                                                                                                           |
| മോഡ്                   | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                        | `warn`    | Injection നയം: `block`, `warn`, അല്ലെങ്കിൽ `log`. (പിന്നോട്ടുള്ള അനുയോജ്യതയ്ക്കായി `redact` സ്വീകരിക്കുമെങ്കിലും അത് injection ടെക്സ്റ്റ് നീക്കം ചെയ്യില്ല; അഭ്യർത്ഥനയിലെ PII പുനരെഴുത്ത് `PII_REDACTION_ENABLED` ആണ് നിയന്ത്രിക്കുന്നത്.) |
| ബ്ലോക്ക് പരിധി         | `blockThreshold` ഓപ്ഷൻ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (അപരനാമം `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`    | ബ്ലോക്ക് ചെയ്യാൻ ആവശ്യമായ ഏറ്റവും കുറഞ്ഞ തീവ്രത. ഡിഫോൾട്ടിൽ Medium നിരീക്ഷണത്തിന് മാത്രമുള്ളതാണ്.                                                                                                                                          |

**മോഡ് മുൻഗണന** (`getMode`): കോളറിന്റെ `options.mode` →
`INJECTION_GUARD_MODE` **DB feature-flag override** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. അതിനാൽ, dashboard override-ന് env vars-നെക്കാൾ മുൻഗണനയുണ്ട്; അതുകൊണ്ട് Feature
Flags UI പ്രവർത്തിച്ചുകൊണ്ടിരിക്കുന്ന guard-നെ തത്സമയം നിയന്ത്രിക്കുന്നു (പുനരാരംഭം ആവശ്യമില്ല). DB വായന fail-safe ആണ്:
അതിൽ പിശക് സംഭവിച്ചാൽ, guard env അടിസ്ഥാനമാക്കിയുള്ള പ്രവർത്തനരീതിയിലേക്ക് മടങ്ങും; കൂടാതെ
override സജ്ജമാക്കിയിട്ടില്ലെങ്കിൽ, പ്രവർത്തനം env-only resolution-നോട് സമാനമായിരിക്കും.

കണ്ടെത്തൽ ഉറവിടങ്ങൾ:

1. `@/shared/utils/inputSanitizer`-ൽ നിന്നുള്ള `sanitizeRequest()` (pipeline-ന്റെ
   മറ്റു ഭാഗങ്ങളിലും ഉപയോഗിക്കുന്ന പങ്കിട്ട detector set).
2. ബിൽറ്റ്-ഇൻ `DEFAULT_GUARD_PATTERNS` (നിലവിൽ `system_override_inline`,
   `markdown_system_block` എന്നിവ; രണ്ടിനും `high` തീവ്രത).
3. constructor options വഴി നൽകുന്ന ഐച്ഛിക `customPatterns` (strings, regex,
   അല്ലെങ്കിൽ `{ name, pattern, severity }` records).

`mode === "block"` ആയിരിക്കുകയും **കൂടാതെ** കുറഞ്ഞത് ഒരു detection എങ്കിലും severity
threshold പാലിക്കുകയും ചെയ്യുമ്പോൾ, `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` മടക്കിനൽകുന്നു. `warn`/`log` മോഡുകളിൽ guardrail ലോഗ് ചെയ്യുമെങ്കിലും
കോൾ അനുവദിക്കും. registry വഴി കടന്നുപോകാതെ prompts വിലയിരുത്തേണ്ട
കോളർമാർക്കായി പങ്കിട്ട helper ആയ `evaluatePromptInjection()`-ഉം export ചെയ്തിട്ടുണ്ട്.

**സ്കാൻ പരിധി (v3.8.20):** ചേർത്ത prompt ടെക്സ്റ്റിന്റെ **ആദ്യത്തെ 16 KB** മാത്രമാണ്
detector പരിശോധിക്കുന്നത് — `src/shared/utils/inputSanitizer.ts`-ൽ
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes). pattern loop പ്രവർത്തിപ്പിക്കുന്നതിന് മുമ്പ്
`detectInjection()`-ഉം `evaluatePromptInjection()`-ഉം `slice(0, MAX_INJECTION_SCAN_BYTES)`
ഉപയോഗിക്കുന്നു. Injection directives സാധാരണയായി input-ന്റെ മുകൾഭാഗത്താണ് വരുന്നത്; അതിനാൽ ഇത്
കണ്ടെത്തൽ ദുർബലമാക്കാതെ നൂറുകണക്കിന് KB വലുപ്പമുള്ള payloads-ൽ regex CPU/GC പരിമിതപ്പെടുത്തുന്നു (cf.
#3932, #4041).

### Credential Masker (`credentialMasker.ts`)

**രണ്ട്** stages-ലും പ്രവർത്തിക്കുകയും ഡിഫോൾട്ട് chain-ൽ അവസാനത്തേതായി വരികയും ചെയ്യുന്നു (priority `95`).
ഔട്ട്ബൗണ്ട് payload-ൽ (message content, tool-call arguments, tool results) **കൂടാതെ**
provider response-ലുമുള്ള സുപരിചിതമായ API-key / secret-token patterns മറയ്ക്കുന്നു; അതിനാൽ
prompt-ലേക്ക് paste ചെയ്ത credential (അല്ലെങ്കിൽ tool result തിരികെ echo ചെയ്ത ഒന്ന്) upstream
provider-ലേക്കോ client-ലേക്ക് തിരികെയോ ചോർന്നുപോകില്ല.

- **Opt-in മാത്രം**, PII redaction-ന്റെ അതേ രീതി (Hard Rule #20-നോട് ചേർന്നത്):
  `settings.credentialRedactionEnabled === true` **അല്ലെങ്കിൽ**
  `CREDENTIAL_REDACTION_ENABLED=true` അല്ലാത്തിടത്തോളം പ്രവർത്തനരഹിതമാണ്. ഇത് ഓഫായിരിക്കുമ്പോൾ, guardrail ഒരു no-op ആണ് —
  ഇത് ഒരിക്കലും ബ്ലോക്ക് ചെയ്യുകയോ പുനരെഴുതുകയോ ഇല്ല.
- `redactCredentials()` മുഴുവൻ payload/response tree-യിലൂടെയും സഞ്ചരിക്കുകയും (`walkValue()`,
  prototype-pollution-safe, `WeakSet` വഴി cycle-safe) പൊരുത്തങ്ങൾ
  `[REDACTED:<type>]` placeholder ഉപയോഗിച്ച് മാറ്റിസ്ഥാപിക്കുകയും ചെയ്യുന്നു; യഥാർത്ഥത്തിൽ
  മാറിയ branches മാത്രം clone ചെയ്യുന്നു.
- `CREDENTIAL_PATTERNS` LLM provider keys (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS tokens (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), payment keys (Stripe, Square), cloud
  keys (AWS access key, Twilio, SendGrid, Mailgun), private keys / JWTs,
  credentials അടങ്ങിയ connection strings (`mongodb://user:pass@...`, മുതലായവ), കൂടാതെ
  പൊതുവായ `Authorization`/`x-api-key`/`api-key`/`apikey` header-value
  pattern എന്നിവ ഉൾക്കൊള്ളുന്നു. Header രൂപത്തിലുള്ള keys (`authorization`, `x-api-key`, `api-key`,
  `apikey`) പൊതുവായ text regex വഴിയല്ലാതെ ഘടനാപരമായി (value മാത്രം, `Bearer `/`Basic `
  പോലുള്ള scheme prefix നിലനിർത്തിക്കൊണ്ട്) മറയ്ക്കുന്നു.
- guardrail ഒരിക്കലും ബ്ലോക്ക് ചെയ്യുന്നില്ല; അത് പുനരെഴുതുകയും (`modifiedPayload` /
  `modifiedResponse`) annotation ചേർക്കുകയും (`meta.credentialsRedacted`, `meta.count`) മാത്രമാണ് ചെയ്യുന്നത്.

Regression guard: `tests/unit/credential-masker-guardrail.test.ts`.

## അടിസ്ഥാന കോൺട്രാക്ട് (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ചെയിൻ ഉടനടി അവസാനിപ്പിക്കുന്നു
  message?: string; // ബ്ലോക്ക് ചെയ്യുമ്പോൾ പ്രദർശിപ്പിക്കുന്നു
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // അഭ്യർത്ഥന മാറ്റിയെഴുതുന്നതിനായി preCall മടക്കിനൽകുന്നത്
  modifiedResponse?: TValue; // പ്രതികരണം മാറ്റിയെഴുതുന്നതിനായി postCall മടക്കിനൽകുന്നത്
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

`void`, `{}`, അല്ലെങ്കിൽ `{ block: false }` എന്നിവയിൽ ഏതെങ്കിലും മടക്കിനൽകിക്കൊണ്ട് ഒരു ഗാർഡ്റെയിൽ "മാറ്റമില്ല" എന്ന് സൂചിപ്പിക്കുന്നു. `modifiedPayload`/`modifiedResponse` മടക്കിനൽകുന്നത്, തുടർന്നുള്ള ഗാർഡ്റെയിലുകൾക്കായി ചെയിനിലൂടെ കടന്നുപോകുന്ന മൂല്യത്തെ മാറ്റിസ്ഥാപിക്കുന്നു.
`signal?: AbortSignal` കോളറുടെ ലൈഫ്സൈക്കിളിനെ ഗാർഡ്റെയിലുകളിലേക്ക് കൈമാറുന്നു. ഒരു അഭ്യർത്ഥന അബോർട്ട് ചെയ്യുന്നത് ബോധപൂർവമായ fail-open അപവാദമാണ്: റോ മീഡിയ പിന്തുണയ്ക്കില്ലെന്ന് അറിയാവുന്ന ഒരു ലക്ഷ്യത്തിലേക്ക് അത് പുനഃസ്ഥാപിക്കാതെ, മീഡിയ ബ്രിഡ്ജുകൾ പ്രവർത്തനം നിർത്തുകയും ക്ലീനപ്പ് നടത്തുകയും ചെയ്യുന്നു.

## രജിസ്ട്രി (`registry.ts`)

സിംഗിൾടൺ `guardrailRegistry` ലഭ്യമാക്കുന്നവ:

- `register(guardrail)` — ഒരു ഗാർഡ്റെയിൽ ചേർക്കുന്നു (അല്ലെങ്കിൽ നോർമലൈസ് ചെയ്ത പേരനുസരിച്ച് മാറ്റിസ്ഥാപിക്കുന്നു), തുടർന്ന് ആരോഹണ `priority` ക്രമത്തിൽ വീണ്ടും സോർട്ട് ചെയ്യുന്നു.
- `clear()` / `list()` — അഡ്മിനിസ്ട്രേറ്റീവ് സഹായികൾ.
- `runPreCallHooks(payload, context)` — സജീവ ഗാർഡ്റെയിലുകളിലൂടെ ആവർത്തിക്കുന്നു, `modifiedPayload` വഴി പേലോഡ് കൈമാറുന്നു, ആദ്യത്തെ `block: true` ലഭിക്കുമ്പോൾ നിർത്തുന്നു.
- `runPostCallHooks(response, context)` — പ്രതികരണ ഭാഗത്തും ഇതേ പ്രവാഹം.
- `resetGuardrailsForTests({ registerDefaults })` — ശുദ്ധമായ ടെസ്റ്റ് ഐസൊലേഷനായി സ്റ്റേറ്റ് മായ്ക്കുകയും, ആവശ്യമെങ്കിൽ ഡിഫോൾട്ടുകൾ വീണ്ടും രജിസ്റ്റർ ചെയ്യുകയും ചെയ്യുന്നു.

രണ്ട് റണ്ണറുകളും `{ blocked, payload|response, results, guardrail?, message? }` മടക്കിനൽകുന്നു; ഇവിടെ `results` എന്നത് ഓരോ ഗാർഡ്റെയിലിനുമുള്ള `blocked`, `skipped`, `modified`, `error`, `meta` ഫീൽഡുകൾ ഉൾക്കൊള്ളുന്ന `GuardrailExecutionResult` റെക്കോർഡുകളുടെ ഒരു അറേയാണ്, ഇത് ട്രേസിംഗിന് പ്രയോജനപ്പെടുന്നു.

### ഓരോ അഭ്യർത്ഥനയ്ക്കും ഗാർഡ്റെയിലുകൾ പ്രവർത്തനരഹിതമാക്കൽ

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` നിലവിലെ അഭ്യർത്ഥനയ്ക്കായി ഒഴിവാക്കേണ്ട ഗാർഡ്റെയിൽ പേരുകളുടെ ഡ്യൂപ്ലിക്കേറ്റുകൾ നീക്കംചെയ്ത ഒരു ലിസ്റ്റ് സമാഹരിക്കുന്നു. ഉറവിടങ്ങൾ (എല്ലാം ഐച്ഛികം, എല്ലാം ലയിപ്പിക്കുന്നു):

- `apiKeyInfo.disabledGuardrails`
- അഭ്യർത്ഥന ബോഡിയിലെ `disabledGuardrails` (ടോപ്പ്-ലെവൽ)
- അഭ്യർത്ഥന ബോഡിയിലെ `metadata.disabledGuardrails`
- ഹെഡർ `x-omniroute-disabled-guardrails` (അല്ലെങ്കിൽ പഴയ
  `x-disabled-guardrails`)

മൂല്യങ്ങൾ സ്ട്രിങ്ങുകളുടെ അറേകളോ കോമ ഉപയോഗിച്ച് വേർതിരിച്ച സ്ട്രിങ്ങോ ആകാം; പേരുകൾ ലോവർകേസ് kebab-case-ലേക്ക് നോർമലൈസ് ചെയ്യപ്പെടുന്നു (`pii_masker` → `pii-masker`). ഫലം `context.disabledGuardrails` വഴി രജിസ്ട്രിയിലേക്ക് കൈമാറുന്നു; പൊരുത്തപ്പെടുന്ന ഗാർഡ്റെയിലുകൾ രജിസ്ട്രി ഒഴിവാക്കുന്നു (`results`-ൽ `skipped: true`).

## നിർവഹണ ക്രമം

`src/sse/handlers/chat.ts`, `open-sse/handlers/chatCore.ts` എന്നിവയിലൂടെ കടന്നുപോകുന്ന ഓരോ അഭ്യർത്ഥനയ്ക്കും:

1. API കീ, ബോഡി, ഹെഡറുകൾ എന്നിവയിൽനിന്ന് `resolveDisabledGuardrails(...)` ഒഴിവാക്കേണ്ടവയുടെ പട്ടിക നിർമ്മിക്കുന്നു.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` മുൻഗണനയുടെ ആരോഹണക്രമത്തിൽ ഗാർഡ്റെയിലുകൾ പ്രവർത്തിപ്പിക്കുന്നു:
   - പ്രവർത്തനരഹിതമാക്കിയ ഗാർഡ്റെയിലുകൾ `skipped` ആയി രേഖപ്പെടുത്തുന്നു.
   - ഓരോ ഗാർഡ്റെയിലിന്റെയും `preCall`-ന് `modifiedPayload` വഴി പേലോഡ് തിരുത്താനാകും.
   - ആദ്യത്തെ `block: true` ചെയിൻ ഉടൻ അവസാനിപ്പിക്കുകയും ഹാൻഡ്ലർ ഒരു ഗാർഡ്റെയിൽ നിരസിക്കൽ പ്രതികരണം മടക്കുകയും ചെയ്യുന്നു.
3. തിരുത്തപ്പെട്ടിരിക്കാനിടയുള്ള പേലോഡ് കോംബോ റൂട്ടിങ്ങിലേക്കും അപ്സ്ട്രീം ഡിസ്പാച്ചിലേക്കും കടക്കുന്നു.
4. പ്രതികരണം തയ്യാറാക്കിയശേഷം, പ്രതികരണത്തിൽ അതേ ചെയിൻ `guardrailRegistry.runPostCallHooks(...)` പ്രവർത്തിപ്പിക്കുന്നു. ഇവിടെയുള്ള `block: true` അപ്സ്ട്രീം പ്രതികരണം ഉപേക്ഷിക്കുന്നു.

എറർ ത്രോ ചെയ്യുന്ന ഗാർഡ്റെയിലുകൾ `error: <message>` എന്ന രീതിയിൽ രേഖപ്പെടുത്തുകയും
`logger.warn` വഴി ലോഗ് ചെയ്യുകയും ചെയ്യുന്നു, എന്നാൽ ചെയിൻ തുടരുന്നു — രൂപകൽപ്പനപ്രകാരം ഫെയിൽ-ഓപ്പൺ ആണ്.

## കോൺഫിഗറേഷൻ

ബിൽറ്റ്-ഇൻ ഗാർഡ്റെയിലുകൾ വായിക്കുന്ന എൻവയോൺമെന്റ് വേരിയബിളുകൾ:

| വേരിയബിൾ                              | ഉപയോഗിക്കുന്നത്           | ഫലം                                                                                                         |
| ------------------------------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | കണ്ടെത്തൽ പൂർണ്ണമായി പ്രവർത്തനരഹിതമാക്കാൻ `false` ആയി സജ്ജീകരിക്കുക.                                        |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | ഇൻജക്ഷൻ നയം: `warn`, `block`, അല്ലെങ്കിൽ `log`. ലെഗസി മൂല്യമായ `redact` ഇൻജക്ഷൻ ടെക്സ്റ്റ് തിരുത്തുന്നില്ല. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | ഇൻജക്ഷൻ ഗാർഡിനുള്ള മോഡ്; എൻവ് വേരിയബിളുകളെ **മറികടക്കുന്ന** ഒരു DB ഫീച്ചർ ഫ്ലാഗ് കൂടിയാണിത് (DB > ENV).     |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | `MODE=block` നിരസിക്കുന്ന ഏറ്റവും കുറഞ്ഞ തീവ്രത: `high` (ഡിഫോൾട്ട്), `medium`, അല്ലെങ്കിൽ `low`.            |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | `INPUT_SANITIZER_BLOCK_THRESHOLD`-ന്റെ ലെഗസി അപരനാമം.                                                       |

| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ഡൗൺസ്ട്രീം) | പ്രതികരണ ഭാഗത്തെ മാസ്കറിന്റെ പെരുമാറ്റം നിയന്ത്രിക്കുന്നു.                                                  |

`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, കൂടാതെ
`modalityBridgeCacheMaxEntries` എന്നിവയാണ്. ലെഗസി

Audio, `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout`, `modalityBridgeAudioMaxClips` എന്നിവയ്ക്കൊപ്പം പങ്കിട്ട

`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, കൂടാതെ

FFmpeg/ffprobe ഐച്ഛിക പ്രവർത്തന ഡിപെൻഡൻസികളായതിനാലും ഫ്രെയിം ക്യാപ്ഷനിങ് ലേറ്റൻസിയും മോഡൽ ചെലവും വർധിപ്പിക്കുന്നതിനാലും ഇത് ഡിഫോൾട്ടായി പ്രവർത്തനരഹിതമാണ്.

## ഇഷ്ടാനുസൃത ഗാർഡ്റെയിലുകൾ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ഘട്ടങ്ങൾ:

1. `BaseGuardrail` വിപുലീകരിക്കുന്ന `src/lib/guardrails/myGuardrail.ts` സൃഷ്ടിക്കുക.
2. `preCall` കൂടാതെ/അല്ലെങ്കിൽ `postCall` നടപ്പിലാക്കുക.
3. ഒന്നുകിൽ ഇംപോർട്ട് ചെയ്യുന്ന സമയത്ത് രജിസ്റ്റർ ചെയ്യുക (`registerDefaultGuardrails`-ൽനിന്ന് പുഷ് ചെയ്യുക), അല്ലെങ്കിൽ
   റൺടൈമിൽ `guardrailRegistry.register(...)` വിളിക്കുക — ഒരേ നോർമലൈസ് ചെയ്ത പേരുള്ള
   മുൻ ഗാർഡ്റെയിലിനെ രജിസ്ട്രി മാറ്റിസ്ഥാപിക്കും.
4. `tests/unit/`-ന് കീഴിൽ ടെസ്റ്റുകൾ ചേർക്കുക (നിലവിലുള്ള ഉദാഹരണങ്ങൾ:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## ടെസ്റ്റിംഗ്

അറിയാവുന്ന ഒരു അവസ്ഥയിൽനിന്ന് ആരംഭിക്കാൻ ടെസ്റ്റുകൾക്കിടയിൽ `resetGuardrailsForTests()` ഉപയോഗിക്കുക.
ശൂന്യമായ രജിസ്ട്രിയിൽ ആരംഭിക്കുന്നതിനും ടെസ്റ്റിലുള്ള ഗാർഡ്റെയിലുകൾ മാത്രം
രജിസ്റ്റർ ചെയ്യുന്നതിനും `{ registerDefaults: false }` നൽകുക. Vision Bridge ഡിപ്പെൻഡൻസി
ഇൻജക്ഷൻ (`deps.getSettings`, `deps.callVisionModel`) സ്വീകരിക്കുന്നു; ക്രമീകരണങ്ങൾ, ശേഷികൾ,
STT മോഡൽ തിരഞ്ഞെടുക്കൽ, ക്രെഡൻഷ്യൽ പരിശോധനകൾ, ട്രാൻസ്ക്രിപ്ഷൻ എന്നിവയ്ക്കായി Audio Bridge
തത്തുല്യമായ സീമുകൾ ലഭ്യമാക്കുന്നു. അതിനാൽ, DB അല്ലെങ്കിൽ നെറ്റ്വർക്ക് ആക്സസ് ഇല്ലാതെ തന്നെ
ടെസ്റ്റുകൾക്ക് രണ്ട് ഫ്ലോകളും പരിശോധിക്കാനാകും.

## ഇൻജക്ഷൻ-ഗാർഡ് റൂട്ട് കവറേജും റെഡ്-ടീമും (Phase 8 · Block D)

ഉപയോക്തൃ പ്രോംപ്റ്റുകൾ സ്വീകരിക്കുന്ന എല്ലാ റൂട്ടുകളും ഇൻജക്ഷൻ-ഗാർഡ് (`createInjectionGuard` / `withInjectionGuard`) ഉൾക്കൊള്ളുന്നു.
ഇത് `INJECTION_GUARD_MODE` മാനിക്കുന്നു (ഡിഫോൾട്ട് `warn` = ലോഗ് മാത്രം;
`block` = HTTP 400 `SECURITY_001` മടക്കിനൽകുന്നു).

| തരം                       | റൂട്ടുകൾ                                                                                                                                             | ഡിഫോൾട്ട് മോഡ് |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| ടെക്സ്റ്റ് (നിലവിലുള്ളത്) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn           |
| ജനറേറ്റീവ്                | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn           |
| ഡാറ്റ                     | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn           |

ടെക്സ്റ്റ് എക്സ്ട്രാക്ഷൻ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` എന്നിവ ഉൾക്കൊള്ളുന്നു.

**റെഡ്-ടീം (രാത്രിതോറും, `nightly-llm-security.yml`):** `INJECTION_GUARD_MODE=block` ആയിരിക്കുമ്പോൾ
ഓരോ റൂട്ടും OWASP-LLM കോർപ്പസ് തടയുന്നുവെന്ന് promptfoo സാധൂകരിക്കുന്നു; garak പ്രോബുകൾ പ്രവർത്തിപ്പിക്കുന്നു
(സീക്രട്ട് ഇല്ലെങ്കിൽ ഒഴിവാക്കുന്നു). സ്ഥിരതയ്ക്കായി `moderations` ഉൾപ്പെടുത്തിയിട്ടുണ്ട് — ബ്ലോക്ക് മോഡിലുള്ള
ഓപ്പറേറ്റർമാർക്ക് `resolveDisabledGuardrails` വഴി അത് ഒഴിവാക്കാനാകും.

രാത്രിതോറുമുള്ള വർക്ക്ഫ്ലോയ്ക്ക് (`.github/workflows/nightly-llm-security.yml`, cron + മാനുവൽ
ഡിസ്പാച്ച്) രണ്ട് ജോബുകളുണ്ട്:

- **`promptfoo-guard` (ബ്ലോക്കിംഗ്)** — `INJECTION_GUARD_MODE=block` ഉപയോഗിച്ച്
  `promptfoo eval -c promptfooconfig.yaml` പ്രവർത്തിപ്പിക്കുന്നു. ഓരോ പ്രതികൂല കേസും
  (ഉദാ. "മുമ്പത്തെ എല്ലാ നിർദ്ദേശങ്ങളും അവഗണിക്കുക…", DAN-ശൈലിയിലുള്ള ജെയിൽബ്രേക്കുകൾ)
  റെസ്പോൺസിൽ `error.code === "SECURITY_001"` ഉണ്ടെന്ന് ഉറപ്പാക്കുന്നു; അതായത്,
  ഗാർഡ് അഭ്യർത്ഥന യഥാർത്ഥത്തിൽ നിരസിച്ചു.
- **`garak` (ഉപദേശാത്മകം)** — ഒരു ലോക്കൽ OmniRoute ഇൻസ്റ്റൻസിനെതിരെ
  (`http://localhost:20128/v1`) garak `--probes promptinject,dan,leakreplay` പ്രവർത്തിപ്പിക്കുന്നു.
  ഒരു പ്രൊവൈഡർ സീക്രട്ട് (`PROMPTFOO_PROVIDER_KEY`) അടിസ്ഥാനമാക്കി ഗേറ്റ് ചെയ്തിരിക്കുന്നു;
  അത് ഇല്ലെങ്കിൽ പ്രശ്നമില്ലാതെ ഒഴിവാക്കുകയും `|| true` സഫിക്സ് ചെയ്യുകയും ചെയ്യുന്നതിനാൽ,
  CI പരാജയപ്പെടുത്താതെ ഇത് റിപ്പോർട്ട് ചെയ്യുന്നു.

ഗാർഡ് ഹെൽപ്പറിന്റെ (`createInjectionGuard` / `withInjectionGuard`) കവറേജ് പ്രോംപ്റ്റ് ഉൾക്കൊള്ളുന്ന
ഓരോ `/v1` റൂട്ടിലേക്കും വ്യാപിക്കുന്നു; `src/shared/utils/inputSanitizer.ts`-ലെ
`extractMessageContents()` മുഖേന `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`
എന്നിവയിൽനിന്ന് പ്രോംപ്റ്റ് ടെക്സ്റ്റ് എടുക്കുന്നു.
