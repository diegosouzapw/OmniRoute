ഒരു pull request-നായി ഏറ്റവും ചെറുതും വിശ്വസനീയവുമായ development loop തിരഞ്ഞെടുക്കാൻ ഈ മാർഗ്ഗനിർദ്ദേശം ഉപയോഗിക്കുക. താഴെ ലിങ്ക് ചെയ്തിരിക്കുന്ന മേഖലാ-നിർദ്ദിഷ്ട architecture, security രേഖകൾക്ക് ഇത്
പകരമല്ല; സാധാരണയായ ഓരോ മാറ്റത്തിന്റെ തരത്തെയും അതിന്റെ contracts, കേന്ദ്രീകൃത checks, CI coverage എന്നിവയുമായി ഇത് ബന്ധിപ്പിക്കുന്നു.

## ഓരോ മാറ്റവും പിന്തുടരുന്ന പാത

1. **തിരുത്തുന്നതിന് മുമ്പ് base തിരഞ്ഞെടുക്കുക.** സജീവമായ ഏറ്റവും ഉയർന്ന `release/v*` branch കണ്ടെത്തി അതിന്റെ
   tip-ൽ നിന്ന് branch സൃഷ്ടിക്കുക. `main` അല്ല, ആ branch ആണ് target ചെയ്യേണ്ടത്. ഒരു release freeze നിലവിലുണ്ടെങ്കിൽ, freeze ചെയ്ത
   branch target ചെയ്യരുത്; പകരം
   [Branching & Release Model](BRANCHING_MODEL.md)-ൽ വിവരിച്ചിരിക്കുന്ന അടുത്ത സജീവ cycle ഉപയോഗിക്കുക.
2. **Contracts വ്യക്തമാക്കുക.** മാറ്റം ബാധിക്കുന്ന ഓരോ catalog, schema, generated artifact, public API, അല്ലെങ്കിൽ user
   interface എന്നിവയും തിരിച്ചറിയുക. താഴെയുള്ള table ഏറ്റവും കുറഞ്ഞ ആരംഭസെറ്റ് നൽകുന്നു.
3. **കേന്ദ്രീകൃത tests എഴുതുകയോ പുതുക്കുകയോ ചെയ്യുക.** `src/`, `open-sse/`, `electron/`, അല്ലെങ്കിൽ
   `bin/` എന്നിവയിലെ production മാറ്റങ്ങൾക്ക് അതേ PR-ൽ ഒരു automated test ആവശ്യമാണ്. behavior തെളിയിക്കുന്ന ഏറ്റവും ചെറിയ test files പ്രവർത്തിപ്പിക്കുക,
   തുടർന്ന് പട്ടികപ്പെടുത്തിയിരിക്കുന്ന focused gates പ്രവർത്തിപ്പിക്കുക.
4. **വിശാലമായ matrix പ്രവർത്തിപ്പിക്കാൻ CI-യെ അനുവദിക്കുക.** സമ്പൂർണ്ണ unit shards, Vitest, coverage ratchet, കൂടാതെ
   production build എന്നിവ PR-ൽ പ്രവർത്തിക്കും. ഒരു focused failure കൂടുതൽ വ്യാപകമായ സ്വാധീനം സൂചിപ്പിക്കുമ്പോഴോ
   മാറ്റം നിരവധി subsystems-ൽ വ്യാപിക്കുമ്പോഴോ മാത്രം വിശാലമായ suite പ്രാദേശികമായി പ്രവർത്തിപ്പിക്കുക.
5. **Review-ന് മുമ്പ് പൊരുത്തപ്പെടുത്തുക.** സജീവമായ base fetch ചെയ്ത്, അതിലെ പുതിയ commits-ഉം അതിനെതിരായ നിങ്ങളുടെ diff-ഉം പരിശോധിക്കുക,
   തുടർന്ന് contributor workflow അനുസരിച്ച് base rebase ചെയ്യുകയോ merge ചെയ്യുകയോ ചെയ്യുക. Generated-file,
   catalog conflicts എന്നിവ അവയുടെ source-ൽ നിന്ന് പരിഹരിച്ച്, അവ വീണ്ടും generate ചെയ്യുക, focused loop വീണ്ടും പ്രവർത്തിപ്പിക്കുക, കൂടാതെ
   PR ഇപ്പോഴും സജീവമായ release branch-നെ target ചെയ്യുന്നുവെന്ന് സ്ഥിരീകരിക്കുക.
6. **തെളിവുകൾ രേഖപ്പെടുത്തുക.** PR template-ൽ പ്രവർത്തിപ്പിച്ച commands, ചേർത്തതോ മാറ്റിയതോ ആയ എല്ലാ test files,
   migrations അല്ലെങ്കിൽ feature flags, കൂടാതെ ഇപ്പോഴും ശേഷിക്കുന്ന CI-only validation എന്നിവ പട്ടികപ്പെടുത്തുക.

## മാറ്റത്തിന്റെ തരം അനുസരിച്ചുള്ള Golden paths

താഴെയുള്ള commands ആവശ്യമായ ഏറ്റവും കുറഞ്ഞ focused checks ആണ്; നിങ്ങൾ മാറ്റിയ behavior നേരിട്ട് പരിശോധിക്കുന്ന ഒരു test
ഒഴിവാക്കാനുള്ള അനുമതിയല്ല അവ.

### Provider

**Contracts**

- `src/shared/constants/providers/`-ലെ Provider definition-ഉം
  `src/shared/constants/providers.ts`-ലെ അതിന്റെ composition-ഉം.
- `open-sse/config/providerRegistry.ts`-ലോ അതിൽ നിന്ന് വേർതിരിച്ചെടുത്ത registry files-ലോ ഉള്ള models, capabilities.
- ബാധകമാകുമ്പോൾ executor/translator selection, OAuth അല്ലെങ്കിൽ API-key configuration, dashboard assets, കൂടാതെ generated
  provider reference.
- Public credentials `resolvePublicCred()` ഉപയോഗിക്കണം; error responses പങ്കിട്ട sanitized
  error helpers ഉപയോഗിക്കണം. `docs/security/PUBLIC_CREDS.md` (git-ൽ; `/docs`-ലേക്ക് compile ചെയ്യില്ല), കൂടാതെ
  [Error Sanitization](../security/ERROR_SANITIZATION.md) കാണുക.

**Focused loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog മാറുമ്പോൾ; generated diff commit ചെയ്യുക
npm run lint
```

ബാധിക്കുന്ന ഓരോ request family-യും പരിശോധിക്കുക: chat, Responses, images, embeddings, audio, അല്ലെങ്കിൽ video.
Generated catalog, golden diffs എന്നിവ contract changes ആയി review ചെയ്യുക; അവ പരിശോധിക്കാതെ സ്വീകരിക്കരുത്.

### Routing

**Contracts**

- `src/shared/constants/routingStrategies.ts`-ലെ public strategy values, UI metadata.
- `open-sse/services/combo.ts`, `open-sse/services/combo/` എന്നിവയ്ക്ക് കീഴിലെ dispatch, ordering.
- Combo schemas, persistence, resilience state, model capabilities, കൂടാതെ API/UI controls.
- Behavior മാറുമ്പോൾ [Auto-Combo Engine](../routing/AUTO-COMBO.md), resilience documentation എന്നിവ.

**Focused loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy അല്ലെങ്കിൽ dispatch മാറ്റങ്ങൾ
npm run check:known-symbols      # strategy registration മാറ്റങ്ങൾ
npm run lint
```

പ്രാദേശികമായി deterministic mocked-upstream tests ഉപയോഗിക്കുക. Live combo smokes-ന് credentials ആവശ്യമാണ്; അവ
manual ആണ്, CI-യ്ക്ക് പകരമല്ല.

### UI / UX

**Contracts**

- `src/app/`, `src/shared/components/` എന്നിവയ്ക്ക് കീഴിലുള്ള Next.js route/page, shared component boundaries.
- API response shapes, loading/empty/error states, keyboard, screen-reader behavior,
  responsive layout, theming, locale expansion.
- `src/i18n/messages/en.json`-ലെ English UI source strings; ഉപയോക്താക്കൾക്ക് ദൃശ്യമാകുന്ന പുതിയ copy hard-code ചെയ്യരുത്.

**Focused loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction അല്ലെങ്കിൽ visual മാറ്റങ്ങൾക്കായി app പ്രവർത്തിപ്പിച്ച് narrow, wide viewports രണ്ടും പരിശോധിക്കുക. CI
production build-ഉം കൂടുതൽ വിശാലമായ suites-ഉം പ്രവർത്തിപ്പിക്കും; visual behavior-ന് മാറ്റത്തിന് അനുയോജ്യമായ focused component, Playwright,
അല്ലെങ്കിൽ രേഖപ്പെടുത്തിയ manual check ഇപ്പോഴും ആവശ്യമാണ്.

### i18n

**Contracts**

- `src/i18n/messages/en.json` ആണ് UI source; `config/i18n.json` ആണ് locale source.
- CLI catalogs `bin/cli/locales/`-ന് കീഴിൽ വേർതിരിച്ചാണ് നിലനിൽക്കുന്നത്.
- ICU placeholders, tags എന്നിവ കൃത്യമായി അതേപടി നിലനിർത്തുക. Product/provider/model names,
  protocol, header names, commands, code/JSON identifiers, URLs, environment variables, അല്ലെങ്കിൽ
  `OmniRoute`, `OAuth`, `MCP`, `A2A` പോലുള്ള protected terms എന്നിവ വിവർത്തനം ചെയ്യരുത്. നിലവിലുള്ള source list
  `scripts/i18n/glossary/protected-terms.json` ആണ്.

**Focused loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI strings/catalogs മാറുമ്പോൾ
npm run lint
```

ഇത് നിലവിലുള്ള system-നുള്ള മാർഗ്ഗനിർദ്ദേശമാണ്; അതിന്റെ tooling അല്ലെങ്കിൽ key model വികസിപ്പിക്കാനുള്ള ക്ഷണമല്ല.
പകരംവയ്ക്കുന്ന system രൂപകൽപ്പന ചെയ്തുകൊണ്ടിരിക്കുമ്പോൾ i18n patches പരിമിതവും കൃത്യവുമായിരിക്കണം. Task-ൽ generated translations വ്യക്തമായി ആവശ്യപ്പെടുകയും
ലഭിക്കുന്ന diff നിങ്ങൾ review ചെയ്തിരിക്കുകയും ചെയ്യുന്നില്ലെങ്കിൽ, external services-നെ വിളിക്കുന്ന translation
commands പ്രവർത്തിപ്പിക്കരുത്.

### CLI

**Contracts**

- `bin/cli/`-യിലെ പൊതുവായ commands-ഉം flags-ഉം, സൃഷ്ടിക്കപ്പെട്ട API commands, exit codes, stdout/stderr, കൂടാതെ
  JSON output രൂപങ്ങൾ, config/environment പെരുമാറ്റം, package ചെയ്ത files.
- CLI-യിലെ ഉപയോക്താവിന് ദൃശ്യമാകുന്ന strings, CLI i18n layer ഉപയോഗിക്കുകയും `en`/`pt-BR` catalogs സമന്വയത്തിൽ നിലനിർത്തുകയും വേണം.
- പിന്തുണയ്ക്കുന്ന runtime ആയി Node-നെയും പ്രസിദ്ധീകരിച്ച binary contract-നെയും നിലനിർത്തുക.

**കേന്ദ്രീകൃത ലൂപ്പ്**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # സൃഷ്ടിച്ച/bundle ചെയ്ത CLI മാറ്റങ്ങൾ
npm run check:pack-policy     # package surface-ലെ മാറ്റങ്ങൾ
npm run lint
```

പെരുമാറ്റം parsing, files, അല്ലെങ്കിൽ exit status എന്നിവയെ ആശ്രയിക്കുമ്പോൾ, ഒരു താൽക്കാലിക data directory-യിൽ കൃത്യമായ command ഉപയോഗിക്കുക. CI കൂടുതൽ വിപുലമായ package artifact, ecosystem പരിശോധനകൾ നടത്തുന്നു.

### Database

**Contracts**

- `src/lib/db/`-ന് കീഴിലുള്ള domain modules; നിർദ്ദിഷ്ട modules നേരിട്ട് import ചെയ്യുക (പഴയ `localDb.ts` re-export layer നീക്കം ചെയ്തിട്ടുണ്ട്).
- `src/lib/db/migrations/`-ന് കീഴിലുള്ള ക്രമനമ്പറുള്ള, idempotent SQL migrations, transaction സുരക്ഷ, upgrade
  പെരുമാറ്റം, indexes, schema ബാധിക്കുന്ന എല്ലാ callers-ഉം.
- Routes-ഉം handlers-ഉം ഒരിക്കലും നേരിട്ട് raw SQL പുറപ്പെടുവിക്കരുത്.

**കേന്ദ്രീകൃത ലൂപ്പ്**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

ഒരു migration ചേർക്കുമ്പോൾ പുതിയ database-ഉം മുമ്പത്തെ schema-യിൽ നിന്നുള്ള upgrade-ഉം പരിശോധിക്കുക. Database tests
handles അടയ്ക്കുകയും cleanup സമയത്ത് `resetDbInstance()` വിളിക്കുകയും വേണം. best-effort Bun adapter path മാറുമ്പോൾ മാത്രം
`npm run test:bun:db` പ്രവർത്തിപ്പിക്കുക; Node തന്നെയാണ് ആധികാരികം.

### Build / deploy

**Contracts**

- Root, workspace manifests/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/`
  package ഉള്ളടക്കം, Electron platform metadata, CI workflows, deployment sentinels.
- പിന്തുണയ്ക്കുന്ന Node ranges-ഉം `CLAUDE.md`-ൽ allow-list ചെയ്ത Bun ഉപയോഗവും മാറ്റമില്ലാതെ നിലനിർത്തണം.
- Build artifacts track ചെയ്യാതെ നിലനിർത്തുക; dependency, license, workflow, package policies ബാധകമാണ്.

**കേന്ദ്രീകൃത ലൂപ്പ്**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency അല്ലെങ്കിൽ lockfile മാറ്റങ്ങൾ
npm run check:pack-policy      # പ്രസിദ്ധീകരിച്ച package surface-ലെ മാറ്റങ്ങൾ
npm run lint
```

മാറ്റം compilation, standalone assembly, assets, അല്ലെങ്കിൽ runtime bundling എന്നിവയെ ബാധിക്കുമ്പോൾ മാത്രം പ്രാദേശികമായി `npm run build` ഉപയോഗിക്കുക. Release/deploy validation-നായി മാത്രം `npm run build:release` ഉപയോഗിക്കുക. CI-യുടെ build ആണ് അന്തിമ cross-platform signal; platform-specific Electron മാറ്റങ്ങൾക്ക് അനുയോജ്യമായ കേന്ദ്രീകൃത build അല്ലെങ്കിൽ smoke തെളിവ് ആവശ്യമാണ്.

## ലോക്കൽ കാൻഡിഡേറ്റ് ലൂപ്പ്

പാക്കേജ് ചെയ്ത ആർട്ടിഫാക്റ്റ് ബൂട്ട് ചെയ്യുമെന്ന് സോഴ്സ് ടെസ്റ്റുകൾക്ക് തെളിയിക്കാനാവില്ല: പാക്കേജിംഗ് ലിസ്റ്റുകൾ, ഒഴിവാക്കിയ ഡിപെൻഡൻസികൾ,
നേറ്റീവ് ബൈനറികൾ എന്നിവയിലെ പരാജയങ്ങൾ ടാർബോൾ ഇൻസ്റ്റാൾ ചെയ്ത് ആരംഭിച്ചതിനുശേഷം മാത്രമേ സംഭവിക്കൂ. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) എന്നത് RFC #8084-ലെ ഒരിക്കൽ ബിൽഡ് ചെയ്യുക / സാധൂകരിക്കുക / പ്രൊമോട്ട് ചെയ്യുക എന്ന ഫ്ലോയുടെ
ലോക്കൽ ഭാഗമാണ്: ഇത് ഒരു കാൻഡിഡേറ്റ് ബിൽഡ് ചെയ്യുന്നു, അതേ ആർട്ടിഫാക്റ്റ് സാധൂകരിക്കുന്നു, ഡയറക്ടറി
പുനർനാമകരണങ്ങളിലൂടെ അത് പ്രൊമോട്ട് ചെയ്യുന്നു, പ്രൊമോട്ട് ചെയ്ത സ്ലോട്ടിന്റെ ഹെൽത്ത് ചെക്ക് പരാജയപ്പെടുമ്പോൾ അത് റോൾ ബാക്ക് ചെയ്യുന്നു.

```bash
npm run dev:candidate -- run --dry-run --json  # പ്ലാൻ പ്രിന്റ് ചെയ്യുക, ഒന്നും മാറ്റരുത്
npm run dev:candidate -- run                   # ബിൽഡ് + സാധൂകരണം + പ്രൊമോഷൻ, സ്വയമേവ റോൾ ബാക്ക്
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/-ലേക്ക് ഇൻസ്റ്റാൾ ചെയ്യുക
npm run dev:candidate -- validate --id <id>    # ലഭ്യമായ ഒരു പോർട്ടിൽ ബൂട്ട് ചെയ്യുക, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current-ഉം previous-ഉം പരസ്പരം മാറ്റുക
npm run dev:candidate -- run --from-tarball <file.tgz>  # മറ്റൊരിടത്ത് (CI) ബിൽഡ് ചെയ്ത ടാർബോൾ വീണ്ടും ഉപയോഗിക്കുക
```

- **ഒരിക്കൽ ബിൽഡ് ചെയ്യുക.** `build` നിലവിലെ ട്രീയെ പാക്ക് ചെയ്യുന്നു (ഇതിന് `dist/server.js` ആവശ്യമാണ്, അതിനാൽ ആദ്യം
  `npm run build:release` പ്രവർത്തിപ്പിക്കുക) അല്ലെങ്കിൽ `--from-tarball` പകർത്തുന്നു; തുടർന്ന് ടാർബോളിൽ
  `node_modules` ഇല്ലാത്തതിനാൽ, ഒറ്റപ്പെടുത്തിയ ഒരു npm പ്രിഫിക്സിലേക്ക് ടാർബോൾ ഇൻസ്റ്റാൾ ചെയ്യുന്നു. ഐഡി ഹ്രസ്വമായ `HEAD`
  sha ആണ് (ട്രീയിൽ ലോക്കൽ മാറ്റങ്ങളുണ്ടെങ്കിൽ `-dirty`) അല്ലെങ്കിൽ ഒരു ടാർബോളിന് `tgz-<sha256>` ആണ്. ഇതിനകം
  ബിൽഡ് ചെയ്തിട്ടുള്ള ക്ലീൻ ഐഡി വീണ്ടും ബിൽഡ് ചെയ്യുന്നതിനുപകരം പുനരുപയോഗിക്കും; വീണ്ടും ബിൽഡ് ചെയ്യാൻ `--force` നൽകുക.
- **സോഴ്സിനെയല്ല, പാക്കേജിനെയാണ് സാധൂകരിക്കേണ്ടത്.** `validate`, പുതുതായുള്ള `DATA_DIR=<candidate>/data`,
  വ്യാജ സീക്രട്ടുകൾ എന്നിവയോടെയും ഓപ്പറേറ്ററുടെ `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY`, `INITIAL_PASSWORD`
  എന്നിവ എൻവയൺമെന്റിൽ നിന്ന് നീക്കിയശേഷവും ഇൻസ്റ്റാൾ ചെയ്ത CLI (`serve --port <free port>`) ആരംഭിക്കുന്നു; അതുവഴി
  പുതിയ ഇൻസ്റ്റാളേഷന്റെ കീയില്ലാത്ത ലൂപ്പ്ബാക്ക് നിലപാട് പരിശോധിക്കുന്നു. `GET /api/health` 200 തിരികെ നൽകുന്നതുവരെ
  ഇത് കാത്തിരിക്കുന്നു, `GET /v1/models` 200 തിരികെ നൽകണമെന്ന് നിർബന്ധമാക്കുന്നു, പ്രോസസ് ഗ്രൂപ്പ് നിർത്തുന്നു,
  കൂടാതെ ടാർബോൾ ഹാഷിനൊപ്പം വിധി `validation.json`-ൽ രേഖപ്പെടുത്തുന്നു.
- **അതേ ആർട്ടിഫാക്റ്റ് പ്രൊമോട്ട് ചെയ്യുക.** നിലവിലെ ടാർബോൾ ഹാഷിനായി വിജയകരമായ സാധൂകരണം ഇല്ലാത്ത
  കാൻഡിഡേറ്റിനെ `promote` നിരസിക്കുന്നു. ഡിഫോൾട്ട് ആക്റ്റീവ് സ്ലോട്ട് `_artifacts/candidate/current` ആണ്;
  അതേ ഫയൽസിസ്റ്റത്തിലെ മറ്റൊരു ഡയറക്ടറി `--target <dir>` തിരഞ്ഞെടുക്കുന്നു, അതിന്റെ മുൻ സ്ലോട്ട്
  `<dir>.previous` ആയിരിക്കും. ഓരോ പുനർനാമകരണവും ആറ്റോമിക് ആണ്; ഇടയ്ക്ക് പരാജയമുണ്ടായാൽ, ഇതിനകം നടന്ന
  പുനർനാമകരണങ്ങൾ വിപരീതമാക്കുന്നു.
- **റോൾ ബാക്ക് ചെയ്യുക.** `run` പ്രൊമോട്ട് ചെയ്ത സ്ലോട്ട് വീണ്ടും സാധൂകരിക്കുകയും ആ പരിശോധന പരാജയപ്പെടുമ്പോൾ
  `current`, `previous` എന്നിവ തിരികെ പരസ്പരം മാറ്റുകയും ചെയ്യുന്നു. ആദ്യ സാധൂകരണം പരാജയപ്പെടുന്ന
  കാൻഡിഡേറ്റ് ഒരിക്കലും പ്രൊമോട്ട് ചെയ്യപ്പെടില്ല.

എല്ലാം gitignore ചെയ്ത `_artifacts/candidate/`-ന് കീഴിലാണ് എഴുതുന്നത്; നിലവിലുള്ള OmniRoute
ഇൻസ്റ്റാളേഷനെയോ അതിന്റെ ഡാറ്റ ഡയറക്ടറിയെയോ ഒരിക്കലും സ്പർശിക്കില്ല. പ്രൊമോട്ട് ചെയ്ത CLI
`_artifacts/candidate/current/prefix/bin/omniroute` ആണ്; അത് ഉപയോഗിക്കുമ്പോൾ നിങ്ങളുടെ സ്വന്തം `DATA_DIR`
ഉപയോഗിച്ച് ആരംഭിക്കുക. എക്സിറ്റ് കോഡുകൾ: `0` വിജയം, `1` സാധൂകരണമോ പ്രൊമോഷനോ പരാജയപ്പെട്ടു, `2` ഉപയോഗത്തിലെ
പിശക് അല്ലെങ്കിൽ ബിൽഡ് ലഭ്യമല്ല.

വിജയിക്കുമെന്നതിനുള്ള തെളിവല്ല. അതേസമയം, ഓരോ പ്രാദേശിക എഡിറ്റും സമ്പൂർണ്ണ റിപ്പോസിറ്ററി മാട്രിക്സിനായി കാത്തിരിക്കേണ്ടതില്ല.

## സമന്വയ ചെക്ക്ലിസ്റ്റ്

അവലോകനം അഭ്യർത്ഥിക്കുന്നതിന് മുമ്പ്:

- PR ബേസ് ഇപ്പോഴും ഏറ്റവും ഉയർന്ന സജീവ `release/v*` ബ്രാഞ്ചാണെന്ന് സ്ഥിരീകരിക്കുക.
- ആ ബേസ് ഫെച്ച് ചെയ്ത്, നിങ്ങൾ ബ്രാഞ്ച് സൃഷ്ടിച്ചതിനുശേഷം ചേർത്ത കമ്മിറ്റുകൾ അവലോകനം ചെയ്യുക.
- അബദ്ധത്തിൽ വന്നതോ ജനറേറ്റ് ചെയ്തതോ ആയ അനാവശ്യ മാറ്റങ്ങൾക്കായി `git diff <active-base>...HEAD` അവലോകനം ചെയ്യുക.
- സോഴ്സ് അപ്ഡേറ്റ് ചെയ്ത് ഔട്ട്പുട്ട് വീണ്ടും ജനറേറ്റ് ചെയ്തുകൊണ്ട് കാറ്റലോഗിലെയും ജനറേറ്റ് ചെയ്ത ഡോക്യുമെന്റുകളിലെയും കോൺഫ്ലിക്റ്റുകൾ പരിഹരിക്കുക.
- സമന്വയത്തിനുശേഷം PR വിവരണത്തിൽ നൽകിയിരിക്കുന്ന എല്ലാ കേന്ദ്രീകൃത ടെസ്റ്റുകളും ഗേറ്റുകളും വീണ്ടും പ്രവർത്തിപ്പിക്കുക.
- മാറിയ ബേസുമായി പൊരുത്തപ്പെടുത്താൻ വേണ്ടി മാത്രം അസർഷനുകൾ ദുർബലമാക്കുകയോ ആവശ്യമായ ടെസ്റ്റുകൾ ഒഴിവാക്കുകയോ ഒരിക്കലും ചെയ്യരുത്.
