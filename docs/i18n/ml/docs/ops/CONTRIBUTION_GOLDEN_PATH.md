ഒരു pull request-നായി ഏറ്റവും ചെറിയ, വിശ്വസനീയമായ development loop തിരഞ്ഞെടുക്കാൻ ഈ ഗൈഡ് ഉപയോഗിക്കുക. താഴെ ലിങ്ക് ചെയ്തിരിക്കുന്ന മേഖലാ-നിർദ്ദിഷ്ട architecture, security രേഖകൾക്ക് ഇത് പകരമല്ല; സാധാരണയായി വരുന്ന ഓരോ change type-നെയും അതിന്റെ contracts, focused checks, CI coverage എന്നിവയുമായി ഇത് ബന്ധിപ്പിക്കുന്നു.

## ഓരോ മാറ്റവും പിന്തുടരുന്ന പാത

1. **എഡിറ്റ് ചെയ്യുന്നതിന് മുമ്പ് base തിരഞ്ഞെടുക്കുക.** സജീവമായതിൽ ഏറ്റവും ഉയർന്ന `release/v*` branch കണ്ടെത്തി അതിന്റെ tip-ൽ നിന്ന് branch സൃഷ്ടിക്കുക. `main` അല്ല, ആ branch ആണ് target ചെയ്യേണ്ടത്. ഒരു release freeze സജീവമാണെങ്കിൽ, freeze ചെയ്ത branch target ചെയ്യരുത്; [Branching & Release Model](BRANCHING_MODEL.md)-ൽ വിവരിച്ചിരിക്കുന്ന അടുത്ത സജീവ cycle ഉപയോഗിക്കുക.
2. **Contracts വ്യക്തമാക്കുക.** മാറ്റം ബാധിക്കുന്ന എല്ലാ catalog, schema, generated artifact, public API, അല്ലെങ്കിൽ user interface-ഉം തിരിച്ചറിയുക. താഴെയുള്ള പട്ടിക ഏറ്റവും കുറഞ്ഞ ആരംഭസെറ്റ് നൽകുന്നു.
3. **Focused tests എഴുതുകയോ പുതുക്കുകയോ ചെയ്യുക.** `src/`, `open-sse/`, `electron/`, അല്ലെങ്കിൽ `bin/` എന്നിവയിലെ production മാറ്റങ്ങൾക്ക് അതേ PR-ൽ ഒരു automated test ആവശ്യമാണ്. behavior തെളിയിക്കുന്ന ഏറ്റവും ചെറിയ test files ആദ്യം പ്രവർത്തിപ്പിക്കുക, തുടർന്ന് പട്ടികപ്പെടുത്തിയിരിക്കുന്ന focused gates പ്രവർത്തിപ്പിക്കുക.
4. **വിശാലമായ matrix CI പ്രവർത്തിപ്പിക്കട്ടെ.** സമ്പൂർണ്ണ unit shards, Vitest, coverage ratchet, production build എന്നിവ PR-ൽ പ്രവർത്തിക്കും. ഒരു focused failure കൂടുതൽ വ്യാപകമായ impact സൂചിപ്പിക്കുമ്പോഴോ മാറ്റം പല subsystems-ലായി വ്യാപിക്കുമ്പോഴോ മാത്രം വിശാലമായ suite പ്രാദേശികമായി പ്രവർത്തിപ്പിക്കുക.
5. **Review-ന് മുമ്പ് പൊരുത്തപ്പെടുത്തുക.** സജീവ base fetch ചെയ്യുക, അതിലെ പുതിയ commits-ഉം അതിനെതിരായ നിങ്ങളുടെ diff-ഉം പരിശോധിക്കുക, തുടർന്ന് contributor workflow അനുസരിച്ച് base rebase ചെയ്യുകയോ merge ചെയ്യുകയോ ചെയ്യുക. Generated-file, catalog conflicts എന്നിവ അവയുടെ source-ൽ നിന്ന് പരിഹരിക്കുക, അവ വീണ്ടും generate ചെയ്യുക, focused loop വീണ്ടും പ്രവർത്തിപ്പിക്കുക, PR ഇപ്പോഴും സജീവ release branch-നെയാണ് target ചെയ്യുന്നതെന്ന് സ്ഥിരീകരിക്കുക.
6. **തെളിവുകൾ രേഖപ്പെടുത്തുക.** PR template-ൽ പ്രവർത്തിപ്പിച്ച commands, ചേർത്തതോ മാറ്റിയതോ ആയ എല്ലാ test files, migrations അല്ലെങ്കിൽ feature flags, ഇനിയും ബാക്കിയുള്ള CI-only validation എന്നിവ പട്ടികപ്പെടുത്തുക.

## Change type അനുസരിച്ചുള്ള Golden paths

താഴെയുള്ള commands ഏറ്റവും കുറഞ്ഞ focused checks ആണ്; നിങ്ങൾ മാറ്റിയ behavior നേരിട്ട് cover ചെയ്യുന്ന test ഒഴിവാക്കാനുള്ള അനുമതിയല്ല.

### Provider

**Contracts**

- `src/shared/constants/providers/`-ലെ provider definition-ഉം `src/shared/constants/providers.ts`-ലെ അതിന്റെ composition-ഉം.
- `open-sse/config/providerRegistry.ts`-ലോ അതിൽ നിന്ന് വേർതിരിച്ചെടുത്ത registry files-ലോ ഉള്ള models, capabilities.
- ബാധകമായിടത്ത് executor/translator selection, OAuth അല്ലെങ്കിൽ API-key configuration, dashboard assets, generated provider reference.
- Public credentials `resolvePublicCred()` ഉപയോഗിക്കണം; error responses പങ്കിട്ട sanitized error helpers ഉപയോഗിക്കണം. `docs/security/PUBLIC_CREDS.md` (git; `/docs`-ലേക്ക് compile ചെയ്യുന്നതല്ല), [Error Sanitization](../security/ERROR_SANITIZATION.md) എന്നിവ കാണുക.

**Focused loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog മാറുമ്പോൾ; generated diff commit ചെയ്യുക
npm run lint
```

ബാധിക്കപ്പെട്ട എല്ലാ request family-കളും test ചെയ്യുക: chat, Responses, images, embeddings, audio, അല്ലെങ്കിൽ video. Generated catalog, golden diffs എന്നിവ contract changes ആയി review ചെയ്യുക; അവ പരിശോധിക്കാതെ അംഗീകരിക്കരുത്.

### Routing

**Contracts**

- `src/shared/constants/routingStrategies.ts`-ലെ public strategy values, UI metadata.
- `open-sse/services/combo.ts`, `open-sse/services/combo/` എന്നിവയ്ക്ക് കീഴിലുള്ള dispatch, ordering.
- Combo schemas, persistence, resilience state, model capabilities, API/UI controls.
- Behavior മാറുമ്പോൾ [Auto-Combo Engine](../routing/AUTO-COMBO.md), resilience documentation എന്നിവ.

**Focused loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy അല്ലെങ്കിൽ dispatch മാറ്റങ്ങൾ
npm run check:known-symbols      # strategy registration മാറ്റങ്ങൾ
npm run lint
```

പ്രാദേശികമായി deterministic mocked-upstream tests ഉപയോഗിക്കുക. Live combo smokes-ന് credentials ആവശ്യമാണ്; അവ manual ആണ്, CI-യ്ക്ക് പകരമല്ല.

### UI / UX

**Contracts**

- `src/app/`, `src/shared/components/` എന്നിവയ്ക്ക് കീഴിലുള്ള Next.js route/page, shared component boundaries.
- API response shapes, loading/empty/error states, keyboard, screen-reader behavior, responsive layout, theming, locale expansion.
- `src/i18n/messages/en.json`-ലെ English UI source strings; ഉപയോക്താക്കൾക്ക് ദൃശ്യമാകുന്ന പുതിയ copy hard-code ചെയ്യരുത്.

**Focused loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction അല്ലെങ്കിൽ visual മാറ്റങ്ങൾക്കായി app പ്രവർത്തിപ്പിച്ച് narrow, wide viewports രണ്ടും പരിശോധിക്കുക. Production build-ഉം കൂടുതൽ വിശാലമായ suites-ഉം CI പ്രവർത്തിപ്പിക്കും; visual behavior-ന് ഇപ്പോഴും മാറ്റത്തിന് അനുയോജ്യമായ focused component, Playwright, അല്ലെങ്കിൽ രേഖപ്പെടുത്തിയ manual check ആവശ്യമാണ്.

### i18n

**Contracts**

- `src/i18n/messages/en.json` ആണ് UI source; `config/i18n.json` ആണ് locale source.
- CLI catalogs `bin/cli/locales/`-ന് കീഴിൽ വേറെയായി സ്ഥിതിചെയ്യുന്നു.
- ICU placeholders, tags എന്നിവ അതേപടി സംരക്ഷിക്കുക. Product/provider/model names, protocol, header names, commands, code/JSON identifiers, URLs, environment variables, അല്ലെങ്കിൽ `OmniRoute`, `OAuth`, `MCP`, `A2A` പോലുള്ള protected terms വിവർത്തനം ചെയ്യരുത്. നിലവിലെ source list `scripts/i18n/glossary/protected-terms.json` ആണ്.

**Focused loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI strings/catalogs മാറുമ്പോൾ
npm run lint
```

ഇത് നിലവിലുള്ള system-നുള്ള മാർഗനിർദേശമാണ്; അതിന്റെ tooling അല്ലെങ്കിൽ key model വിപുലീകരിക്കാനുള്ള ക്ഷണമല്ല. പകരംവയ്ക്കുന്ന system രൂപകൽപ്പന ചെയ്തുകൊണ്ടിരിക്കുമ്പോൾ i18n patches ആവശ്യമായ പരിധിയിൽ മാത്രം നിലനിർത്തുക. Task വ്യക്തമായി generated translations ആവശ്യപ്പെടുകയും ലഭിക്കുന്ന diff നിങ്ങൾ review ചെയ്തിരിക്കുകയും ചെയ്യുന്നില്ലെങ്കിൽ external services വിളിക്കുന്ന translation commands പ്രവർത്തിപ്പിക്കരുത്.

### CLI

**Contracts**

- `bin/cli/`-യിലെ പൊതു കമാൻഡുകളും ഫ്ലാഗുകളും, ജനറേറ്റ് ചെയ്ത API കമാൻഡുകൾ, എക്സിറ്റ് കോഡുകൾ, stdout/stderr, JSON ഔട്ട്പുട്ട് ഘടനകൾ, കോൺഫിഗറേഷൻ/എൻവയൺമെന്റ് പ്രവർത്തനം, പാക്കേജ് ചെയ്ത ഫയലുകൾ എന്നിവ.
- CLI ഉപയോക്താക്കൾക്ക് ദൃശ്യമാകുന്ന സ്ട്രിങ്ങുകൾ CLI i18n ലെയർ ഉപയോഗിക്കുകയും `en`/`pt-BR` കാറ്റലോഗുകൾ സമന്വയത്തിൽ നിലനിർത്തുകയും വേണം.
- പിന്തുണയ്ക്കുന്ന റൺടൈമായി Node-നെയും പ്രസിദ്ധീകരിച്ച ബൈനറി കരാറിനെയും നിലനിർത്തുക.

**കേന്ദ്രീകൃത ലൂപ്പ്**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # ജനറേറ്റ് ചെയ്ത/ബണ്ടിൽ ചെയ്ത CLI മാറ്റങ്ങൾ
npm run check:pack-policy     # പാക്കേജ് ഉപരിതലത്തിലെ മാറ്റങ്ങൾ
npm run lint
```

പ്രവർത്തനം പാർസിങ്, ഫയലുകൾ, അല്ലെങ്കിൽ എക്സിറ്റ് നില എന്നിവയെ ആശ്രയിക്കുമ്പോൾ, ഒരു താൽക്കാലിക ഡാറ്റ ഡയറക്ടറിയിൽ കൃത്യമായ കമാൻഡ് ഉപയോഗിക്കുക. വിശാലമായ പാക്കേജ് ആർട്ടിഫാക്റ്റ്, ഇക്കോസിസ്റ്റം പരിശോധനകൾ CI നിർവഹിക്കുന്നു.

### ഡാറ്റാബേസ്

**കരാറുകൾ**

- `src/lib/db/`-ന് കീഴിലുള്ള ഡൊമെയ്ൻ മൊഡ്യൂളുകൾ; നിർദ്ദിഷ്ട മൊഡ്യൂളുകൾ നേരിട്ട് ഇംപോർട്ട് ചെയ്യുക (പഴയ `localDb.ts` റീ-എക്സ്പോർട്ട് ലെയർ നീക്കം ചെയ്തിട്ടുണ്ട്).
- `src/lib/db/migrations/`-ന് കീഴിലുള്ള നമ്പർ നൽകിയ, ഐഡംപൊട്ടന്റ് SQL മൈഗ്രേഷനുകൾ, ട്രാൻസാക്ഷൻ സുരക്ഷ, അപ്ഗ്രേഡ് പ്രവർത്തനം, ഇൻഡക്സുകൾ, സ്കീമ ബാധിക്കുന്ന എല്ലാ കോളറുകളും.
- റൂട്ടുകളും ഹാൻഡ്ലറുകളും ഒരിക്കലും അസംസ്കൃത SQL നേരിട്ട് പ്രവർത്തിപ്പിക്കരുത്.

**കേന്ദ്രീകൃത ലൂപ്പ്**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

ഒരു മൈഗ്രേഷൻ ചേർക്കുമ്പോൾ പുതിയ ഡാറ്റാബേസും മുൻ സ്കീമയിൽ നിന്നുള്ള അപ്ഗ്രേഡും പരിശോധിക്കുക. ഡാറ്റാബേസ് ടെസ്റ്റുകൾ ഹാൻഡിലുകൾ അടയ്ക്കുകയും ക്ലീനപ്പ് സമയത്ത് `resetDbInstance()` വിളിക്കുകയും വേണം. പരമാവധി ശ്രമ അടിസ്ഥാനത്തിലുള്ള Bun അഡാപ്റ്റർ പാത മാറുമ്പോൾ മാത്രം `npm run test:bun:db` പ്രവർത്തിപ്പിക്കുക; Node തന്നെയാണ് ആധികാരികമായി തുടരുന്നത്.

### ബിൽഡ് / വിന്യാസം

**കരാറുകൾ**

- റൂട്ട്, വർക്ക്സ്പേസ് മാനിഫെസ്റ്റുകൾ/ലോക്ക്ഫയൽ, `scripts/build/`, Next.js സ്റ്റാൻഡ്എലോൺ അസംബ്ലി, `dist/` പാക്കേജ് ഉള്ളടക്കങ്ങൾ, Electron പ്ലാറ്റ്ഫോം മെറ്റാഡാറ്റ, CI വർക്ക്ഫ്ലോകൾ, വിന്യാസ സെന്റിനലുകൾ എന്നിവ.
- പിന്തുണയ്ക്കുന്ന Node ശ്രേണികളും `CLAUDE.md`-ൽ അനുവദനീയമായി പട്ടികപ്പെടുത്തിയ Bun ഉപയോഗവും മാറ്റമില്ലാതെ നിലനിർത്തണം.
- ബിൽഡ് ആർട്ടിഫാക്റ്റുകൾ ട്രാക്ക് ചെയ്യാതിരിക്കുക; ഡിപ്പൻഡൻസി, ലൈസൻസ്, വർക്ക്ഫ്ലോ, പാക്കേജ് നയങ്ങൾ ബാധകമാണ്.

**കേന്ദ്രീകൃത ലൂപ്പ്**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # ഡിപ്പൻഡൻസി അല്ലെങ്കിൽ ലോക്ക്ഫയൽ മാറ്റങ്ങൾ
npm run check:pack-policy      # പ്രസിദ്ധീകരിച്ച പാക്കേജ് ഉപരിതലത്തിലെ മാറ്റങ്ങൾ
npm run lint
```

മാറ്റം കംപൈലേഷൻ, സ്റ്റാൻഡ്എലോൺ അസംബ്ലി, അസറ്റുകൾ, അല്ലെങ്കിൽ റൺടൈം ബണ്ടിലിങ് എന്നിവയെ ബാധിക്കുമ്പോൾ മാത്രം പ്രാദേശികമായി `npm run build` ഉപയോഗിക്കുക. റിലീസ്/വിന്യാസ സാധൂകരണത്തിനായി മാത്രം `npm run build:release` ഉപയോഗിക്കുക. CI-യുടെ ബിൽഡാണ് അന്തിമ ക്രോസ്-പ്ലാറ്റ്ഫോം സൂചന; പ്ലാറ്റ്ഫോം-നിർദ്ദിഷ്ട Electron മാറ്റങ്ങൾക്ക് അതിനനുസരിച്ചുള്ള കേന്ദ്രീകൃത ബിൽഡ് അല്ലെങ്കിൽ സ്മോക്ക് പരിശോധനാ തെളിവ് ആവശ്യമാണ്.

## ലോക്കൽ ലൂപ്പും CI-യും തമ്മിലുള്ള താരതമ്യം

| ഓരോ പാച്ചിനും ലോക്കലായി പ്രവർത്തിപ്പിക്കേണ്ടവ                                        | CI നൽകുന്ന വിപുലമായ സൂചന                                               |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| മുകളിലുള്ള നേരിട്ടുള്ള പെരുമാറ്റ പരിശോധനകളും വിഭാഗ ഗേറ്റുകളും                        | ഷാർഡ് ചെയ്ത പൂർണ്ണ യൂണിറ്റ് സ്യൂട്ടും സീരിയൽ പരിശോധനകളും               |
| `npm run lint`                                                                       | Vitest സ്യൂട്ടുകളും കവറേജ്/ഗുണനിലവാര റാച്ചറ്റുകളും                     |
| ബാധിക്കപ്പെട്ട കോൺട്രാക്റ്റ് ആവശ്യപ്പെടുമ്പോൾ മാത്രം ടൈപ്പ്ചെക്ക് അല്ലെങ്കിൽ ബിൽഡ്   | പ്രൊഡക്ഷൻ ബിൽഡ്, സുരക്ഷ, ഡോക്സ്, ഡിപ്പൻഡൻസി, PR-നയ ഗേറ്റുകൾ            |
| ഓട്ടോമേഷന് പെരുമാറ്റം തെളിയിക്കാനാകാത്തപ്പോൾ മാത്രം മാനുവൽ ഇന്ററാക്ഷൻ/ലൈവ് പരിശോധനകൾ | വർക്ക്ഫ്ലോ കോൺഫിഗർ ചെയ്ത ക്രോസ്-ജോബ് ഇന്റഗ്രേഷൻ, പ്ലാറ്റ്ഫോം പരിശോധനകൾ |

ഗ്രീൻ ആയ ഫോക്കസ്ഡ് ലൂപ്പ്, മാറ്റിയ കോൺട്രാക്റ്റിനെക്കുറിച്ചുള്ള തെളിവാണ്; ബന്ധമില്ലാത്ത CI പരിശോധനകൾ
വിജയിക്കുമെന്നതിനുള്ള തെളിവല്ല. അതുപോലെ, ഓരോ ലോക്കൽ എഡിറ്റും പൂർണ്ണ റിപ്പോസിറ്ററി മാട്രിക്സിനായി കാത്തിരിക്കേണ്ടതില്ല.

## അനുരഞ്ജന ചെക്ക്ലിസ്റ്റ്

റിവ്യൂ അഭ്യർത്ഥിക്കുന്നതിന് മുമ്പ്:

- PR ബേസ് ഇപ്പോഴും ഏറ്റവും ഉയർന്ന സജീവ `release/v*` ബ്രാഞ്ചാണെന്ന് സ്ഥിരീകരിക്കുക.
- ആ ബേസ് ഫെച്ച് ചെയ്ത്, നിങ്ങൾ ബ്രാഞ്ച് സൃഷ്ടിച്ചതിനുശേഷം ലാൻഡ് ചെയ്ത കമ്മിറ്റുകൾ റിവ്യൂ ചെയ്യുക.
- ആകസ്മികമായതോ ജനറേറ്റ് ചെയ്തതോ ആയ അനാവശ്യ മാറ്റങ്ങൾ കണ്ടെത്താൻ `git diff <active-base>...HEAD` റിവ്യൂ ചെയ്യുക.
- സോഴ്സ് അപ്ഡേറ്റ് ചെയ്ത് ഔട്ട്പുട്ട് വീണ്ടും ജനറേറ്റ് ചെയ്തുകൊണ്ട് കാറ്റലോഗിലെയും ജനറേറ്റ് ചെയ്ത ഡോക്യുമെന്റുകളിലെയും കോൺഫ്ലിക്റ്റുകൾ പരിഹരിക്കുക.
- അനുരഞ്ജനത്തിനുശേഷം PR വിവരണത്തിൽ ലിസ്റ്റ് ചെയ്തിട്ടുള്ള എല്ലാ ഫോക്കസ്ഡ് ടെസ്റ്റുകളും ഗേറ്റുകളും വീണ്ടും പ്രവർത്തിപ്പിക്കുക.
- മാറിയ ബേസുമായി പൊരുത്തപ്പെടുത്താൻ വേണ്ടി മാത്രം അസർഷനുകൾ ഒരിക്കലും ദുർബലമാക്കുകയോ ആവശ്യമായ ടെസ്റ്റുകൾ ഒഴിവാക്കുകയോ ചെയ്യരുത്.

റിലീസ്-ഫ്രീസ്, റീടാർഗറ്റിംഗ് നിയമങ്ങൾക്കായി
[ബ്രാഞ്ചിംഗ് & റിലീസ് മോഡൽ](BRANCHING_MODEL.md) ഉപയോഗിക്കുക. പൂർണ്ണമായ CI ഇൻവെന്ററിക്കായി
[ക്വാളിറ്റി ഗേറ്റ്സ് റഫറൻസ്](../architecture/QUALITY_GATES.md) ഉപയോഗിക്കുക.
