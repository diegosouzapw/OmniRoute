> **ചുരുക്കത്തിൽ**: ബിൽറ്റ്-ഇൻ ആരോഗ്യ നിരീക്ഷണം, പ്രൊവൈഡർ ഓട്ടോപൈലറ്റ്, ക്വാട്ട ട്രാക്കിംഗ്, ഒബ്സർവബിലിറ്റി ഹുക്കുകൾ എന്നിവയോടെയാണ് OmniRoute ലഭ്യമാകുന്നത്. ഡാഷ്ബോർഡ്, അലേർട്ടുകൾ, ട്രബിൾഷൂട്ടിംഗ് എന്നിവ ഈ ഗൈഡിൽ ഉൾപ്പെടുത്തിയിരിക്കുന്നു.

**സ്രോതസ്സുകൾ:**

- `src/lib/monitoring/observability.ts` — ഒബ്സർവബിലിറ്റി സ്നാപ്പ്ഷോട്ട്
- `src/lib/monitoring/comboHealthAutopilot.ts` — കോംബോ ഹെൽത്ത് ഓട്ടോപൈലറ്റ്
- `src/lib/monitoring/providerHealthAutopilot.ts` — പ്രൊവൈഡർ ഓട്ടോപൈലറ്റ്
- `src/lib/monitoring/providerHealthMatrix.ts` — പ്രൊവൈഡർ ഹെൽത്ത് മാട്രിക്സ്
- `src/lib/localHealthCheck.ts` — ലോക്കൽ ഹെൽത്ത് പരിശോധന
- `src/lib/tokenHealthCheck.ts` — ടോക്കൺ പുതുക്കലിന്റെ ആരോഗ്യം
- `src/lib/proxyHealth.ts` — പ്രോക്സി ഹെൽത്ത് കാഷ് (PROXY_GUIDE.md-ൽ ഉൾപ്പെടുത്തിയിരിക്കുന്നു)

## അവലോകനം

OmniRoute-ന് **നിരീക്ഷണത്തിന്റെ 3 ലെയറുകൾ** ഉണ്ട്:

```
┌──────────────────────────────────────────────────────────────┐
│  ലെയർ 1: സിസ്റ്റം ഹെൽത്ത് (സെർവർ തലം)                        │
│  ├─ localHealthCheck.ts — DB, പോർട്ടുകൾ, നേറ്റീവ് ഡിപെൻഡൻസികൾ │
│  ├─ db/healthCheck.ts — സമഗ്രത, FK, അനാഥ ആർട്ടിഫാക്റ്റുകൾ     │
│  └─ ഡാഷ്ബോർഡ്: /dashboard/health                            │
├──────────────────────────────────────────────────────────────┤
│  ലെയർ 2: പ്രൊവൈഡർ ഹെൽത്ത് (ഓരോ പ്രൊവൈഡറിനുമുള്ള പ്രതിരോധശേഷി) │
│  ├─ providerHealthAutopilot.ts — സർക്യൂട്ട് ബ്രേക്കർ, കൂൾഡൗണുകൾ │
│  ├─ providerHealthMatrix.ts — പ്രൊവൈഡർ/മോഡൽ അനുസരിച്ചുള്ള ഹെൽത്ത് സ്കോറുകൾ │
│  └─ ഡാഷ്ബോർഡ്: /dashboard/providers                         │
├──────────────────────────────────────────────────────────────┤
│  ലെയർ 3: ലൈവ് ഒബ്സർവബിലിറ്റി (റൺടൈം സ്നാപ്പ്ഷോട്ടുകൾ)          │
│  ├─ observability.ts — സർക്യൂട്ട് ബ്രേക്കറുകൾ, സെഷനുകൾ, ക്വാട്ട │
│  ├─ tokenHealthCheck.ts — OAuth ടോക്കൺ പുതുക്കലിന്റെ ആരോഗ്യം  │
│  └─ MCP ടൂളുകൾ: omniroute_get_health, omniroute_get_session_snapshot │
└──────────────────────────────────────────────────────────────┘
```

## ഡാഷ്ബോർഡ് പേജുകൾ

### `/dashboard/health` (സിസ്റ്റം ഹെൽത്ത്)

ഉയർന്ന തലത്തിലുള്ള ഹെൽത്ത് ഡാഷ്ബോർഡ് ഇനിപ്പറയുന്നവ കാണിക്കുന്നു:

| വിഭാഗം                  | കാണിക്കുന്നത്                                                   |
| ----------------------- | --------------------------------------------------------------- |
| **സെർവർ നില**           | പ്രവർത്തനസമയം, പതിപ്പ്, പോർട്ട്, സജീവ കണക്ഷനുകൾ                 |
| **ഡാറ്റാബേസ്**          | കണക്ഷൻ, സമഗ്രത, WAL വലുപ്പം, സമീപകാല മൈഗ്രേഷനുകൾ                |
| **പ്രൊവൈഡർ സംഗ്രഹം**    | സജീവ എണ്ണം, ആരോഗ്യകരമായവയുടെ എണ്ണം, തുറന്ന ബ്രേക്കറുകളുടെ എണ്ണം |
| **ക്വാട്ട മോണിറ്ററുകൾ** | സജീവ സെഷനുകൾ, അലേർട്ടിംഗ്, തീർന്നവ                              |
| **സമീപകാല പിശകുകൾ**     | സ്റ്റാക്ക് ട്രേസുകളോടുകൂടിയ അവസാന 10 പിശകുകൾ                    |
| **റിസോഴ്സ് ഉപയോഗം**     | മെമ്മറി, CPU, ഹീപ്പ് പ്രഷർ ഇൻഡിക്കേറ്റർ                         |

### `/dashboard/providers` (പ്രൊവൈഡർ ഹെൽത്ത്)

ഓരോ പ്രൊവൈഡറിനുമുള്ള ഡാഷ്ബോർഡ്:

| കോളം       | വിവരണം                                                      |
| ---------- | ----------------------------------------------------------- |
| പ്രൊവൈഡർ   | പ്രൊവൈഡർ ID + പ്രദർശന നാമം                                  |
| ആരോഗ്യം    | പച്ച/മഞ്ഞ/ചുവപ്പ് നില                                       |
| സർക്യൂട്ട് | തുറന്ന/അടച്ച/പകുതി തുറന്ന അവസ്ഥ                             |
| കണക്ഷനുകൾ  | കണക്ഷനുകളുടെ എണ്ണം, അവസാന പുതുക്കൽ                          |
| മോഡലുകൾ    | ലഭ്യമായ മോഡലുകൾ, ഓരോ മോഡലിന്റെയും ആരോഗ്യം                   |
| ചെലവ്      | ഇന്നത്തെ ചെലവ്, 7 ദിവസത്തെ പ്രവണത                           |
| പിശകുകൾ    | കഴിഞ്ഞ 24 മണിക്കൂറിലെ പിശകുകളുടെ എണ്ണം, പ്രധാന പിശക് ക്ലാസ് |

കൂടുതൽ വിവരങ്ങൾ കാണാൻ ഒരു പ്രൊവൈഡറിൽ ക്ലിക്ക് ചെയ്യുക:

- ലേറ്റൻസി വിഭജനത്തോടുകൂടിയ സമീപകാല അഭ്യർത്ഥനകൾ
- ഓരോ കണക്ഷനുമുള്ള ഹെൽത്ത് സ്കോറുകൾ
- ഓരോ മോഡലിനുമുള്ള ലോക്കൗട്ടുകൾ
- ഓട്ടോപൈലറ്റ് ശുപാർശകൾ

### `/dashboard/quota` (ക്വാട്ട ട്രാക്കിംഗ്)

ഓരോ API കീക്കും:

## ആരോഗ്യ പരിശോധന API

OmniRoute **രണ്ട്** HTTP ആരോഗ്യ എൻഡ്പോയിന്റുകൾ ലഭ്യമാക്കുന്നു. ഓർക്കസ്ട്രേറ്ററുകൾക്കായി ഇവ പരസ്പരം മാറ്റി ഉപയോഗിക്കാനാവില്ല.

| പാത്ത്                       | ഉദ്ദേശ്യം                                                                                   | ഭാരം                                                | ഇതിനായി ഉപയോഗിക്കുക                                                                      |
| ---------------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `GET /healthz`               | ലൈഫ്സൈക്കിൾ ലൈവ്നസ്/റെഡിനസ് (`ok` / `starting` / `stopping`)                                | വളരെ ലഘു (ഘട്ട ഫ്ലാഗ് മാത്രം)                       | Kubernetes **readiness**; HTTP ഉപയോഗിക്കേണ്ടത് നിർബന്ധമാണെങ്കിൽ ലഘുവായ **liveness**      |
| `GET /api/monitoring/health` | സിസ്റ്റത്തിന്റെയും പ്രൊവൈഡറിന്റെയും ആഴത്തിലുള്ള സംഗ്രഹം (DB, ഹീപ്പ്, കാറ്റലോഗ് എണ്ണങ്ങൾ, …) | ഭാരമേറിയത് (സിങ്ക്രണസ് DB / മോണിറ്ററിങ് പ്രവർത്തനം) | ഡാഷ്ബോർഡുകൾ, ബ്ലാക്ക്ബോക്സ് ആഴത്തിലുള്ള പരിശോധനകൾ, Docker-ന്റെ ബിൽറ്റ്-ഇൻ ഹെൽത്ത് ചെക്ക് |

> **കുറിപ്പ്:** പ്രൊവൈഡർ ആരോഗ്യ മാട്രിക്സുകൾ, ഓട്ടോപൈലറ്റ് പ്രശ്നങ്ങൾ, ക്വോട്ട മോണിറ്ററുകൾ, ടോക്കൺ ആരോഗ്യം, `/api/monitoring/health`-ന് അപ്പുറമുള്ള ലേറ്റൻസി വിശദാംശങ്ങൾ എന്നിവ **MCP ടൂൾ** `observability_snapshot` വഴിയോ **ഡാഷ്ബോർഡ്** പേജുകൾ വഴിയോ ലഭ്യമാണ് — അവയ്ക്കായി പ്രത്യേകം REST റൂട്ടുകളില്ല.

അഭ്യർത്ഥനകൾ കൈകാര്യം ചെയ്യുന്ന **അതേ Node ഇവന്റ് ലൂപ്പിലാണ്** രണ്ട് റൂട്ടുകളും പ്രവർത്തിക്കുന്നത്. CPU-ബന്ധിതമായ ഒരു പാത്തിന് (വലിയ `GET /v1/models` കാറ്റലോഗ് പ്രവർത്തനം, ദൈർഘ്യമേറിയ കോൺടെക്സ്റ്റ് കംപ്രഷൻ / ടോക്കൺ എണ്ണൽ) `/healthz` ഉൾപ്പെടെയുള്ള **എല്ലാ** HTTP ഹാൻഡ്ലറുകളെയും വൈകിപ്പിക്കാനാകും. ഇവന്റ് ലൂപ്പ് തിരക്കിലാണ് ≠ പ്രോസസ് പ്രവർത്തനരഹിതമാണ്. വിഭവങ്ങൾ അമിതമായി ഉപയോഗിക്കുന്ന പ്രവർത്തനം പരിഹരിക്കുന്നതിന് മുൻഗണന നൽകുക; പ്രോബ് ട്യൂണിങ് തെറ്റായ കില്ലുകൾ കുറയ്ക്കുക മാത്രമേ ചെയ്യൂ.

#### `credentialHealth`: പ്രോബ് കാഷും SQLite `test_status`-ഉം

`GET /api/monitoring/health` → `credentialHealth` എന്നത് **ഇൻ-മെമ്മറി പ്രോബ്-കാഷ്
ഗേജ്** ആണ്, `provider_connections.test_status`-ന്റെ തത്സമയ ഡംപ് അല്ല. #12532-ന് ശേഷം
അഭ്യർത്ഥനാ പാത്ത് `getCachedCredentialHealthSummary()` മാത്രം വായിക്കുന്നു; പശ്ചാത്തല പ്രോബുകൾ
ഇവന്റ് ലൂപ്പിന് പുറത്തുവെച്ച് കാഷ് പുതുക്കുന്നു.

| ലെയർ                            | എവിടെ                                                                 | അതിന്റെ അർത്ഥം                                                                                                                                                                                                                                                  |
| ------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| പ്രോബ്-കാഷ് ഗേജ്                | `credentialHealth.total` / `healthy` / `failed` / `unknown` / `stale` | പ്രോസസ് മെമ്മറിയിൽ ഇപ്പോഴും നിലനിൽക്കുന്ന ഏറ്റവും പുതിയ ക്രെഡൻഷ്യൽ-ആരോഗ്യ പ്രോബ് ഫലങ്ങൾ. `source` എല്ലായ്പ്പോഴും `probe-cache` ആണ്.                                                                                                                             |
| പരാജയപ്പെട്ട കണക്ഷന്റെ വിശദാംശം | `credentialHealth.failedConnections`                                  | **`failed > 0` ആയിരിക്കുമ്പോൾ മാത്രം** ഉണ്ടായിരിക്കും. `status=error` ഉള്ള കാഷ് വരികളുടെ പരിമിതപ്പെടുത്തിയ പട്ടിക (`connectionId`, `status`, ശുദ്ധീകരിച്ച `lastError` / `lastErrorType`). പട്ടിക പരിമിതപ്പെടുത്തിയിട്ടുണ്ടെങ്കിൽ `failedOmitted` സജ്ജീകരിക്കും. |
| SQLite സ്റ്റിക്കി സ്റ്റാറ്റസ്   | `credentialHealth.staleDbNonOkCount`                                  | നിലനിൽപ്പോടെ സൂക്ഷിച്ചിട്ടുള്ള `test_status`, അറിയപ്പെടുന്ന non-ok മൂല്യമായ (`error`, `expired`, `credits_exhausted`, `banned`, `deactivated`, `unavailable`) **സജീവമായ** (`is_active=1`) കണക്ഷൻ വരികളുടെ എണ്ണം.                                                |

രണ്ട് ലെയറുകളും ഉദ്ദേശ്യപൂർവം വ്യത്യസ്ത ഫലങ്ങൾ നൽകാം:

- ഗേജിൽ `failed=0` ആയിരിക്കുമ്പോൾ `staleDbNonOkCount>0` — ഏറ്റവും പുതിയ
  പ്രോബ്-കാഷ് സ്നാപ്പ്ഷോട്ട് `status=error` ആയി കണക്കാക്കാത്ത ഒരു സ്റ്റിക്കി
  `test_status` (ഉദാഹരണത്തിന് `expired` അല്ലെങ്കിൽ `credits_exhausted`) SQLite-ൽ ഇപ്പോഴും നിലനിൽക്കുന്നു.
- ഗേജിൽ `failed>0` ആയിരിക്കുമ്പോൾ SQLite ആരോഗ്യകരമായി കാണപ്പെടുന്നു — അടുത്തിടെ ഒരു പ്രോബ് പരാജയപ്പെടുകയും അത്
  കാഷ് ചെയ്യപ്പെടുകയും ചെയ്തു; DB വരി പുതുക്കിയിട്ടില്ല, അല്ലെങ്കിൽ പിന്നീട് മായ്ച്ചിരിക്കുന്നു.

ഈ എൻഡ്പോയിന്റ് സ്ക്രേപ്പ് ചെയ്യുമ്പോൾ `provider_connections.test_status` മാത്രം അടിസ്ഥാനമാക്കി
അലേർട്ട് ചെയ്യരുത്. തത്സമയ പ്രോബ് പരാജയങ്ങൾക്ക് `failed` + `failedConnections` ഉപയോഗിക്കുക,
നിലനിൽപ്പോടെ സൂക്ഷിച്ച സ്റ്റിക്കി-സ്റ്റാറ്റസ് എണ്ണം ആവശ്യമായിരിക്കുമ്പോൾ `staleDbNonOkCount` ഉപയോഗിക്കുക.

### Kubernetes പ്രോബ് ശുപാർശകൾ

OmniRoute ഒരു **ഒറ്റ Node പ്രോസസ്** ആണ് (ഒരു ഇവന്റ് ലൂപ്പ്). സാധാരണ Docker `HEALTHCHECK` ലഘുവായ `/healthz`-നെയാണ് ലക്ഷ്യമിടുന്നത്. kubelet ലൈവ്നസ് ഇടവേളകൾക്ക് `/api/monitoring/health` **അമിതമായി ഭാരമേറിയതാണ്**.

| പരിശോധന                       | ശുപാർശ ചെയ്യുന്ന ലക്ഷ്യം                                                                  | കുറിപ്പുകൾ                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ----------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ആരംഭം**                     | ദൈർഘ്യമേറിയ `failureThreshold` (അല്ലെങ്കിൽ വലിയ `startPeriod`) ഉള്ള HTTP `GET /healthz`   | കോൾഡ് സ്റ്റാർട്ട് + SQLite മൈഗ്രേഷന് ഏതാനും സെക്കൻഡിലധികം എടുത്തേക്കാം                                                                                                                                                                                                                                                                                                                                                                                |
| **സജ്ജത**                     | HTTP `GET /healthz`                                                                       | ലൈഫ്സൈക്കിൾ `ok` / `starting` / `stopping` (200 vs 503). ലൂപ്പ് CPU-ബ്ലോക്ക് ചെയ്യപ്പെട്ടാൽ ഇപ്പോഴും നില മാറിക്കൊണ്ടിരിക്കും. **നിരവധി സെക്കൻഡുകൾക്കുശേഷം ലഭിക്കുന്ന 200 ആരോഗ്യകരമല്ല** (#10303) — 3-ബൈറ്റ് ഹാൻഡ്ലർ പ്രവർത്തിക്കുന്നതിന് മുമ്പ് ഇവന്റ് ലൂപ്പിന് പ്രവർത്തനസമയം ലഭിച്ചില്ലെന്നാണ് അതിനർത്ഥം                                                                                                                                             |
| **സജീവത**                     | HTTP `GET /livez`, **അല്ലെങ്കിൽ പ്രധാന സർവീസ് പോർട്ടിലെ TCP** (`PORT`, ഡിഫോൾട്ട് `20128`) | `/livez` പ്രോസസ് പ്രവർത്തിക്കുന്നുണ്ടോ എന്ന് മാത്രമാണ് പരിശോധിക്കുന്നത് (ഹാൻഡ്ലർ പ്രവർത്തിച്ചാൽ എപ്പോഴും 200). അതും ഇവന്റ് ലൂപ്പ് പങ്കിടുന്നു — തിരക്കിലായത് ≠ പ്രവർത്തനരഹിതമായത്, കൂടാതെ TCP-യെക്കാൾ മെച്ചമായി ഇവന്റ്-ലൂപ്പ് സ്റ്റാർവേഷൻ (#10303) കണ്ടെത്താനും അതിന് കഴിയില്ല. കാറ്റലോഗ്/കംപ്രഷൻ ലോഡിൽ HTTP പരിശോധനകൾ ടൈംഔട്ട് ആകുന്നെങ്കിൽ **TCP** തിരഞ്ഞെടുക്കുക; ഏത് രീതിയിലായാലും ചെറിയ ഇവന്റ്-ലൂപ്പ് സ്തംഭനങ്ങളുടെ പേരിൽ പോഡ് അവസാനിപ്പിക്കരുത് |
| **ആഴത്തിലുള്ള ആരോഗ്യപരിശോധന** | ഒരു ബാഹ്യ ചെക്കറിൽ നിന്ന് `GET /api/monitoring/health`                                    | kubelet `livenessProbe` / കർശനമായ `readinessProbe` എന്നിവയ്ക്കുള്ളതല്ല                                                                                                                                                                                                                                                                                                                                                                                |

ഉദാഹരണ ഘടന (നിങ്ങളുടെ കോൾഡ്-സ്റ്റാർട്ട്, കംപ്രഷൻ ലോഡ് എന്നിവയ്ക്ക് അനുസരിച്ച് ത്രെഷോൾഡുകൾ ക്രമീകരിക്കുക):

```yaml
ports:
  - name: http
    containerPort: 20128
startupProbe:
  httpGet:
    path: /healthz
    port: http
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /healthz
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 6
livenessProbe:
  httpGet:
    path: /livez
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 6
  # ഇവന്റ്-ലൂപ്പ് സ്തംഭനസമയത്ത് HTTP /livez-നും ടൈംഔട്ട് സംഭവിക്കാം. TCP ആണ്
  # കൂടുതൽ സുരക്ഷിതമായ ബദൽ:
  # tcpSocket:
  #   port: http
```

kubelet **liveness** പരിശോധനയെ `/api/monitoring/health`-ലേക്ക് ചൂണ്ടിക്കാണിക്കരുത്. ആ പാത്ത് യഥാർഥ DB/മോണിറ്ററിങ് പ്രവർത്തനങ്ങൾ നടത്തുന്നതിനാൽ ലോഡുള്ളപ്പോൾ തെറ്റായ പോസിറ്റീവ് ഫലം നൽകും.

ബന്ധപ്പെട്ടവ: [#10052](https://github.com/diegosouzapw/OmniRoute/issues/10052) (ഇവന്റ് ലൂപ്പ് തിരക്കിലായിരിക്കുമ്പോഴുള്ള പരിശോധനകൾ), [#9685](https://github.com/diegosouzapw/OmniRoute/issues/9685) / [#10055](https://github.com/diegosouzapw/OmniRoute/pull/10055) (കാറ്റലോഗ് പ്രൈസിങ് അമിതമായി വിഭവങ്ങൾ ഉപയോഗിക്കുന്നത്), [#10117](https://github.com/diegosouzapw/OmniRoute/issues/10117) (കംപ്രഷൻ ടോക്കൺ-എണ്ണൽ അമിതമായി വിഭവങ്ങൾ ഉപയോഗിക്കുന്നത്).

### systemd വാച്ച്ഡോഗ് (സ്തംഭിച്ച ഇവന്റ് ലൂപ്പ്)

ഒരു systemd ഹോസ്റ്റിൽ, OmniRoute സജ്ജമാകുമ്പോൾ അത് സർവീസ് മാനേജറെ അറിയിക്കുകയും തുടർച്ചയായി പിങ്ങുകൾ അയയ്ക്കുകയും ചെയ്യുന്നു. അതിനാൽ ഇവന്റ് ലൂപ്പ് സ്തംഭിച്ച ഒരു സെർവർ പ്രവർത്തിക്കുന്നതുപോലെ തുടരുകയും നിശ്ശബ്ദമായിരിക്കുകയും ചെയ്യുന്നതിന് പകരം അവസാനിപ്പിച്ച് പുനരാരംഭിക്കപ്പെടും. സെർവറിന്റെ സ്വന്തം ഇവന്റ് ലൂപ്പിൽ നിന്നാണ് പിങ്ങുകൾ വരുന്നത്: അത് ബ്ലോക്ക് ചെയ്യുമ്പോൾ പിങ്ങുകൾ നിലയ്ക്കും, തുടർന്ന് ഒരു പിങ്ങും ലഭിക്കാതെ `WatchdogSec` കാലയളവ് കഴിഞ്ഞാൽ systemd സർവീസ് പുനരാരംഭിക്കും.

[`omniroute autostart enable`](../../bin/cli/tray/autostart.mjs) ഇത് ഉൾക്കൊള്ളുന്ന ഒരു യൂസർ യൂണിറ്റ് ഇതിനകം എഴുതുന്നു. നിങ്ങൾ സ്വയം എഴുതുന്ന ഒരു യൂണിറ്റിന് (ഡിഫോൾട്ട് `Type=simple`) വാച്ച്ഡോഗ് ലഭിക്കില്ല, അതിനാൽ അതിന്റെ `[Service]` വിഭാഗത്തിൽ ഈ വരികൾ ചേർക്കുക:

```ini
[Service]
Type=notify
NotifyAccess=all
WatchdogSec=180
TimeoutStartSec=300
```

ജനറേറ്റ് ചെയ്ത യൂണിറ്റ് `Restart=on-failure` സജ്ജീകരിക്കുന്നു, അതിനാൽ ആ വരിയും ചേർക്കുക — അതില്ലെങ്കിൽ വാച്ച്ഡോഗ് സ്തംഭിച്ച സർവീസ് പുനരാരംഭിക്കുന്നതിന് പകരം അവസാനിപ്പിക്കുക മാത്രമേ ചെയ്യൂ.

- `Type=notify`: പ്രോസസ് ഫോർക്ക് ചെയ്യുമ്പോഴല്ല, സെർവർ `READY=1` അയയ്ക്കുമ്പോഴാണ് സർവീസ് "ആരംഭിച്ചതായി" കണക്കാക്കുന്നത്. മന്ദഗതിയിലുള്ള ആരംഭത്തിന് `TimeoutStartSec` പരിധി നിശ്ചയിക്കുന്നു.
- `NotifyAccess=all`: `omniroute serve` സൂപ്പർവൈസറിന്റെ ചൈൽഡ് ആയ സെർവർ പ്രോസസാണ് പിങ്ങുകൾ അയയ്ക്കുന്നത്.
- `WatchdogSec`: ഓരോ 60 സെക്കൻഡിലും പിങ്ങുകൾ അയയ്ക്കുന്നതിനാൽ **120 അല്ലെങ്കിൽ അതിൽ കൂടുതൽ** ഉപയോഗിക്കുക. അതിലും ചെറിയ മൂല്യങ്ങൾ ആരോഗ്യകരമായ സെർവറിനെ പുനരാരംഭിക്കും.
- `omniroute serve` ഫോർഗ്രൗണ്ടിൽ പ്രവർത്തിപ്പിക്കുക. `--daemon` സെർവറിനെ യൂണിറ്റിന്റെ cgroup-ൽ നിന്ന് വേർപെടുത്തുന്നതിനാൽ അറിയിക്കൽ ഹാൻഡ്ഷേക്ക് ഒരിക്കലും പൂർത്തിയാകില്ല.

പുനരാരംഭിച്ചതിനുശേഷം ഇത് സജീവമാണെന്ന് പരിശോധിക്കുക:

```bash
systemctl --user show omniroute -p WatchdogUSec -p WatchdogTimestamp
```

`WatchdogUSec` കോൺഫിഗർ ചെയ്ത കാലതാമസം കാണിക്കുകയും `WatchdogTimestamp` ഓരോ മിനിറ്റിലും മുന്നോട്ട് നീങ്ങുകയും ചെയ്യും. വാച്ച്ഡോഗ് കാരണമുള്ള പുനരാരംഭം `Result=watchdog` ആയി രേഖപ്പെടുത്തും. യൂണിറ്റ് അതേപടി നിലനിർത്തിക്കൊണ്ട് പിങ്ങുകൾ ഓഫാക്കാൻ `OMNIROUTE_DISABLE_SD_NOTIFY=1` സജ്ജീകരിക്കുക; `NOTIFY_SOCKET` ഇല്ലെങ്കിൽ (ടെർമിനൽ, Docker, Electron, Windows) ഒന്നും അയയ്ക്കില്ല.

ഇവന്റ് ലൂപ്പ് തുടർന്നും പ്രവർത്തിക്കുന്നുണ്ടോ എന്ന് മാത്രമാണ് വാച്ച്ഡോഗ് പരിശോധിക്കുന്നത്. വേഗത കുറഞ്ഞതാണെങ്കിലും തുടർന്നും പ്രവർത്തിക്കുന്ന സെർവർ പുനരാരംഭിക്കപ്പെടില്ല.

### ഐച്ഛിക റിക്വസ്റ്റ്-പാത്ത് പ്രവർത്തനം (മെമ്മറി, സ്കില്ലുകൾ, ടോക്കൺ പുതുക്കൽ)

മെമ്മറി എക്സ്ട്രാക്ഷൻ, സ്കിൽസ് ഇൻജക്ഷൻ, OAuth ടോക്കൺ റിഫ്രെഷ് എന്നിവ `/healthz`-നൊപ്പം **പ്രധാന Node ഇവന്റ് ലൂപ്പ്** പങ്കിടുന്നു. അവ ഡാഷ്ബോർഡ്-ടോഗിൾ സവിശേഷതകളാണ് (`memoryEnabled`, `skillsEnabled`), വർക്കർ പൂൾ അല്ല. [പരിസ്ഥിതി — ഇവന്റ്-ലൂപ്പ് ചെലവ്](../reference/ENVIRONMENT.md#event-loop-cost-of-memory-skills-and-token-refresh-10349) കാണുക.

## പ്രൊവൈഡർ ഹെൽത്ത് ഓട്ടോപൈലറ്റ്

`providerHealthAutopilot.ts` മൊഡ്യൂൾ ഇനിപ്പറയുന്ന കാര്യങ്ങൾ ചെയ്യുന്ന ഒരു **സ്വയം സുഖപ്പെടുന്ന സിസ്റ്റമാണ്**:

1. പ്രൊവൈഡറിലെ പ്രശ്നങ്ങൾ കണ്ടെത്തുന്നു (സർക്യൂട്ട് തുറന്നിരിക്കുക, കൂൾഡൗണുകൾ, ലോക്കൗട്ടുകൾ, ക്വോട്ട മുന്നറിയിപ്പുകൾ)
2. അവ പരിഹരിക്കുന്നതിനുള്ള **ശുപാർശചെയ്ത നടപടികൾ** സൃഷ്ടിക്കുന്നു
3. കുറഞ്ഞ അപകടസാധ്യതയുള്ള നടപടികൾ വേണമെങ്കിൽ **സ്വയമേവ നടപ്പിലാക്കുന്നു**

### API

> **REST എൻഡ്പോയിന്റ് ഇല്ല.** ഓട്ടോപൈലറ്റ് പ്രശ്നങ്ങൾ MCP ടൂൾ `observability_snapshot` വഴിയോ ഡാഷ്ബോർഡിലൂടെയോ ലഭ്യമാണ്. ഓട്ടോപൈലറ്റ് ആന്തരികമായി പ്രവർത്തിക്കുന്നു; അതിന്റെ പെരുമാറ്റം പരിസ്ഥിതി വേരിയബിളുകൾ വഴിയല്ല, ക്രമീകരണ DB-യിലെ (ഓരോ കണക്ഷനിലുമുള്ള `autopilotMode` ഫീൽഡ്) ക്രമീകരണങ്ങളിലൂടെയാണ് നിർണ്ണയിക്കുന്നത് — ഓട്ടോപൈലറ്റ്-മോഡ് env var-നായി `grep -rn` പ്രവർത്തിപ്പിച്ചാൽ ഫലങ്ങളൊന്നും ലഭിക്കില്ല.

### ഓട്ടോപൈലറ്റ് മോഡ്

ഓട്ടോപൈലറ്റ് സ്ഥിരസ്ഥിതിയായി **മാനുവൽ മോഡിലാണ്** പ്രവർത്തിക്കുന്നത് — ഇത് പ്രശ്നങ്ങൾ കണ്ടെത്തുകയും ശുപാർശചെയ്ത നടപടികൾ സൃഷ്ടിക്കുകയും ചെയ്യുന്നു, എന്നാൽ അവ സ്വയമേവ പ്രയോഗിക്കുന്നില്ല. ഡാഷ്ബോർഡ് വഴി നടപടികൾ പ്രയോഗിക്കാം.

## ക്വോട്ട മോണിറ്ററുകൾ

സബ്സ്ക്രിപ്ഷൻ പ്രൊവൈഡറുകൾക്കായി (Claude Code, Codex, GitHub Copilot) `observability.ts` **ഓരോ സെഷനുമുള്ള ക്വോട്ട മോണിറ്ററുകൾ** ലഭ്യമാക്കുന്നു:

```ts
interface QuotaMonitorSnapshot {
  sessionId: string;
  provider: string;
  accountId: string;
  status: "starting" | "idle" | "healthy" | "warning" | "exhausted" | "error";
  lastQuotaPercent: number | null; // 0-100
  lastQuotaUsed: number | null;
  lastQuotaTotal: number | null;
  lastResetAt: string | null;
  nextPollAt: string | null;
  totalPolls: number;
  totalAlerts: number;
  consecutiveFailures: number;
}
```

### സ്റ്റാറ്റസുകളുടെ അർത്ഥം

| സ്റ്റാറ്റസ് | എപ്പോൾ                          | UI നടപടി                                               |
| ----------- | ------------------------------- | ------------------------------------------------------ |
| `starting`  | പ്രാരംഭ പോളിംഗ് പുരോഗമിക്കുന്നു | സ്പിന്നർ                                               |
| `idle`      | സമീപകാല പ്രവർത്തനമൊന്നുമില്ല    | ഡാഷ്ബോർഡിൽനിന്ന് മറയ്ക്കുന്നു                          |
| `healthy`   | ക്വോട്ടയിൽ > 50% ശേഷിക്കുന്നു   | പച്ച ബിന്ദു                                            |
| `warning`   | ക്വോട്ടയിൽ < 50% ശേഷിക്കുന്നു   | മഞ്ഞ മുന്നറിയിപ്പ്                                     |
| `exhausted` | ക്വോട്ട = 0%                    | ചുവന്ന ബ്ലോക്ക്, അടുത്ത പ്രൊവൈഡറിലേക്ക് റൂട്ട് ചെയ്യുക |
| `error`     | പോളിംഗ് പരാജയപ്പെട്ടു           | ചുവന്ന ബിന്ദു, ഉടൻ വീണ്ടും ശ്രമിക്കുക                  |

### API

## ടോക്കൺ ആരോഗ്യ പരിശോധന

OAuth പ്രൊവൈഡറുകൾക്ക് (Claude Code, GitHub Copilot, Cursor) **ആനുകാലിക ടോക്കൺ പുതുക്കൽ** ആവശ്യമാണ്. `src/lib/tokenHealthCheck.ts` ഒരു പശ്ചാത്തല ഷെഡ്യൂളർ പ്രവർത്തിപ്പിക്കുന്നു:

- **സ്വീപ്പ് ടിക്ക്**: ഓരോ 60 സെക്കൻഡിലും (`src/lib/tokenHealthCheck.ts:30`-ലെ `TICK_MS = 60 * 1000` സ്വീപ്പ്)
- **ഓരോ കണക്ഷനുമുള്ള ആരോഗ്യ പരിശോധനാ ഇടവേള**: ഡിഫോൾട്ടായി 60 മിനിറ്റ് (`DEFAULT_HEALTH_CHECK_INTERVAL_MIN = 60`); ക്രമീകരണ DB വഴി കോൺഫിഗർ ചെയ്യാം
- **401 ലഭിക്കുമ്പോഴുള്ള മുൻകരുതൽ പുതുക്കൽ**: ഓരോ കണക്ഷനുമുള്ള ഇന്റർസെപ്റ്റർ കൈകാര്യം ചെയ്യുന്നു

### ടോക്കൺ ആരോഗ്യനില

```ts
interface TokenHealth {
  connectionId: string;
  provider: string;
  status: "valid" | "expiring_soon" | "expired" | "refresh_failed";
  expiresAt: string;
  lastRefresh: string;
  nextRefresh: string;
  consecutiveFailures: number;
}
```

### കോൺഫിഗറേഷൻ

ടോക്കൺ ആരോഗ്യ പരിശോധനാ കോൺഫിഗറേഷൻ `tokenHealthCheck.ts` ആന്തരികമായി കൈകാര്യം ചെയ്യുന്നു.

### ടോക്കൺ ആരോഗ്യം

> **REST എൻഡ്പോയിന്റ് ഇല്ല.** ടോക്കൺ ആരോഗ്യ ഡാറ്റ ഡാഷ്ബോർഡ് വഴിയോ MCP ടൂൾ `observability_snapshot` വഴിയോ ലഭ്യമാണ്.

## പ്രശ്നപരിഹാരം

### "പ്രൊവൈഡർ ആരോഗ്യകരമാണെന്ന് പറയുന്നു, പക്ഷേ അഭ്യർത്ഥനകൾ പരാജയപ്പെടുന്നു"

1. **autopilot പ്രശ്നങ്ങൾ** പരിശോധിക്കുക — ഒരു മോഡൽ ലോക്ക് ഔട്ട് ആയിരിക്കാം
2. നിർദ്ദിഷ്ട പിശക് ക്ലാസിനായി **സമീപകാല പിശകുകൾ** നോക്കുക
3. പ്രൊവൈഡർ കാർഡിലെ **കണക്ഷൻ ടെസ്റ്റ്** പരീക്ഷിക്കുക
4. പ്രൊവൈഡർ **അപ്സ്ട്രീമിൽ റേറ്റ്-ലിമിറ്റ് ചെയ്യപ്പെട്ടിട്ടുണ്ടോ** എന്ന് പരിശോധിക്കുക (ലോക്കലായി ദൃശ്യമല്ല)

### "ക്വോട്ട ആരോഗ്യകരമാണെന്ന് പറയുന്നു, പക്ഷേ എനിക്ക് 429-കൾ കാണുന്നു"

- 429 എന്നത് നിങ്ങൾ ക്വോട്ട ഉപയോഗിച്ചുതീർത്തതായി പ്രൊവൈഡർ പറയുന്നു എന്നാണ് അർത്ഥം
- OmniRoute-ന്റെ ക്വോട്ട ട്രാക്കിംഗ് **കാലഹരണപ്പെട്ടത്** ആയിരിക്കാം — പ്രൊവൈഡറുടെ അപ്സ്ട്രീം വിവരമാണ് ആധികാരികം
- ആന്തരിക ക്വോട്ട മോണിറ്റർ വഴി ക്വോട്ട ഡാറ്റ സ്വയമേവ പുതുക്കപ്പെടുന്നു

### "എല്ലാ ടാർഗറ്റുകളും ആരോഗ്യകരമായി കാണപ്പെടുന്നുണ്ടെങ്കിലും Combo പരാജയപ്പെടുന്നു"

- ടാർഗറ്റ് ക്രമീകരണ പ്രശ്നങ്ങൾക്കായി **combo health** ഡാഷ്ബോർഡ് പരിശോധിക്കുക
- **fallback ഇവന്റുകൾ** നോക്കുക — combo വളരെ വേഗത്തിൽ എല്ലാ ഓപ്ഷനുകളും ഉപയോഗിച്ചുതീർക്കുന്നുണ്ടാകാം
- **strategy** നിങ്ങളുടെ ഉപയോഗ സാഹചര്യവുമായി പൊരുത്തപ്പെടുന്നുവെന്ന് ഉറപ്പാക്കുക (priority vs round-robin vs auto)

### "ഡാറ്റാബേസ് ഹെൽത്ത് ചെക്ക് പരാജയപ്പെടുന്നു"

- `sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"` പ്രവർത്തിപ്പിക്കുക
- "ok" ആണെങ്കിൽ — തെറ്റായ മുന്നറിയിപ്പാണ്; ഹെൽത്ത് ചെക്ക് ആവശ്യത്തിലധികം കർശനമാണ്
- മറ്റെന്തെങ്കിലും ആണെങ്കിൽ — **OmniRoute നിർത്തുക**, തുടർന്ന് [ദുരന്ത വീണ്ടെടുക്കൽ ഗൈഡ്](./DATABASE_GUIDE.md#disaster-recovery) പിന്തുടരുക

### "മെമ്മറി ഹീപ്പ് സമ്മർദ്ദം ഗുരുതരമാണ്"

