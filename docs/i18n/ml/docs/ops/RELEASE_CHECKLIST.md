## npm Trusted Publishing (v3.8.51 മുതൽ ഡിഫോൾട്ട്) — അഭ്യർത്ഥനപ്രകാരം സ്റ്റേജ്ഡ്, ഫാൾബാക്കായി ഡയറക്ട്

`npm-publish.yml`, ഡിഫോൾട്ടായി **npm Trusted Publishing (OIDC)** വഴിയാണ് പ്രസിദ്ധീകരിക്കുന്നത്:
`stage-npm` ജോബ് (github-hosted), ആ റണ്ണിനായി GitHub-ന്റെ id-token ഒരു ഹ്രസ്വകാല npm
ക്രെഡൻഷ്യലുമായി കൈമാറ്റം ചെയ്യുന്നു — റെപ്പോസിറ്ററി സീക്രട്ടുകളിൽ ദീർഘകാല npm ടോക്കൺ ഇല്ല, 2FA പ്രോംപ്റ്റ് ഇല്ല, provenance ഉൾപ്പെടുത്തിയിരിക്കുന്നു.
2FA ഒഴിവാക്കുന്ന ടോക്കണുകൾ പിൻവലിക്കുന്ന സാഹചര്യത്തിൽ npm ഇപ്പോൾ അനുവദിക്കുന്ന ബൈപാസ് ഇതാണ്;
WS1.3 ഉറപ്പ് നിലനിർത്തിക്കൊണ്ട്, v3.8.48 വരെ പ്രോജക്റ്റിനുണ്ടായിരുന്ന പൂർണ്ണമായും ഓട്ടോമാറ്റിക് പ്രവാഹം
ഇത് പുനഃസ്ഥാപിക്കുന്നു (ചോർന്ന ടോക്കണിന് ഒറ്റയ്ക്ക് പ്രസിദ്ധീകരിക്കാനാകില്ല — ടോക്കൺ തന്നെയില്ല).

**ഒറ്റത്തവണ സജ്ജീകരണം (ഉടമ):** npmjs.com → പാക്കേജ് `omniroute` → Settings → _Trusted
Publisher_ → GitHub: ഉടമ `diegosouzapw`, റിപ്പോ `OmniRoute`, വർക്ക്ഫ്ലോ `npm-publish.yml`
(എൻവയൺമെന്റ്: ഒന്നുമില്ല). ഇത് നിലവിൽ വരുന്നതുവരെ, ഓട്ടോമാറ്റിക് ഘട്ടം `ENEEDAUTH` ഉപയോഗിച്ച് പരാജയപ്പെടും:
`publish_mode=staged` (താഴെ) അല്ലെങ്കിൽ `direct` ഉപയോഗിച്ച് വീണ്ടും ഡിസ്പാച്ച് ചെയ്യുക.

### സ്റ്റേജ്ഡ് പബ്ലിഷിംഗ് (അഭ്യർത്ഥനപ്രകാരം — `publish_mode=staged`)

npm-publish വർക്ക്ഫ്ലോ ഇനി നേരിട്ട് പ്രസിദ്ധീകരിക്കില്ല: പാക്ക് ചെയ്ത tarball അത്
ബൂട്ട് ചെയ്യുകയും (`check:pack-boot`), തുടർന്ന് `npm stage publish` പ്രവർത്തിപ്പിക്കുകയും ചെയ്യുന്നു — കൃത്യമായ ബൈറ്റുകൾ
റെജിസ്ട്രിയിൽ പാർക്ക് ചെയ്യപ്പെടും, ഉടമ അംഗീകരിക്കുന്നതുവരെ അവ **ഇൻസ്റ്റാൾ ചെയ്യാനാകില്ല**.
മനുഷ്യ 2FA ഗേറ്റ് തെളിവിന് മുമ്പല്ല, അതിന് ശേഷമാണ് ഇപ്പോൾ വരുന്നത്.

**വർക്ക്ഫ്ലോ ഗ്രീൻ ആയതിനുശേഷമുള്ള ഉടമയുടെ പ്രവാഹം:**

1. `npm stage list omniroute` — സ്റ്റേജ് id കണ്ടെത്തുക (വർക്ക്ഫ്ലോ സംഗ്രഹത്തിലും ഇത് പ്രിന്റ് ചെയ്യപ്പെടും).
2. സ്റ്റേജ് ചെയ്ത ബൈറ്റുകൾ പരിശോധിക്കുക (ശുപാർശ ചെയ്യുന്നു): `npm stage download <id>`, തുടർന്ന് ഡൗൺലോഡ് ചെയ്ത
   tarball ഒരു താൽക്കാലിക prefix-ൽ ഇൻസ്റ്റാൾ ചെയ്ത് ബൂട്ട് ചെയ്യുക (`npm run check:pack-boot`, CI-യിൽ
   ഇതേ pack→install→boot പരിശോധന ഓട്ടോമേറ്റ് ചെയ്യുന്നു).
3. `npm stage approve <id>` — 2FA പ്രോംപ്റ്റ് തന്നെയാണ് പബ്ലിഷ്. `npm stage reject <id>` അത് ഉപേക്ഷിക്കുന്നു.
4. പബ്ലിഷിന് ശേഷമുള്ള സുരക്ഷാവലയം: പബ്ലിഷിന് ശേഷമുള്ള വെരിഫയർ (v3.8.49 പ്ലാനിലെ WS1.4)
   പ്രസിദ്ധീകരിച്ച പതിപ്പ് പബ്ലിക് റെജിസ്ട്രിയിൽനിന്ന് വൃത്തിയുള്ള ഒരു കണ്ടെയ്നറിൽ ഇൻസ്റ്റാൾ ചെയ്ത് ബൂട്ട് ചെയ്യുന്നു.

**അടിയന്തര ഫാൾബാക്ക്:** `publish_mode=direct` ഉപയോഗിച്ചുള്ള `workflow_dispatch`, പഴയ രീതിയിലുള്ള
ഉടനടിയുള്ള `npm publish` പുനഃസ്ഥാപിക്കുന്നു (സ്റ്റേജിംഗ് തന്നെ തകരാറിലാകുമ്പോൾ മാത്രം ഉപയോഗിക്കുക; കാരണം രേഖപ്പെടുത്തുക).

**ഒറ്റത്തവണ ഹാർഡനിംഗ് (ഉടമ, npmjs.com):** ചോർന്ന ദീർഘകാല ടോക്കണിന് എവിടെനിന്നും നേരിട്ട്
`npm publish` ചെയ്യാനാകാത്തവിധം, `omniroute`-നുള്ള Trusted Publisher സ്റ്റേജ്-ഒൺലി മോഡിൽ
കോൺഫിഗർ ചെയ്യുക — CI-യ്ക്ക് സ്റ്റേജ് ചെയ്യാൻ മാത്രമേ കഴിയൂ; ഉടമയുടെ 2FA-യ്ക്ക് മാത്രമേ റിലീസ് ചെയ്യാനാകൂ.

**തകരാറിലായ ആർട്ടിഫാക്റ്റിനുള്ള പ്ലേബുക്ക് (മാറ്റമില്ല):** ഡിഫോൾട്ട് ഉടനടി നടപടിയായി
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` ഉപയോഗിക്കുക (മിനിറ്റുകൾക്കുള്ളിൽ, പഴയപടിയാക്കാവുന്നത്);
72h/ഡിപ്പെൻഡന്റുകളില്ലാത്ത ജാലകത്തിനുള്ളിൽ മാത്രം `npm unpublish` ഉപയോഗിക്കുക, ഒരിക്കലും ആദ്യ നടപടിയായി ഉപയോഗിക്കരുത്.
Docker: ഒരു വേർഷൻ ടാഗും ഒരിക്കലും തിരുത്തിയെഴുതരുത് — `latest` അവസാനത്തെ മികച്ച digest-ലേക്ക് വീണ്ടും പോയിന്റ് ചെയ്യുന്നതാണ് റോൾബാക്ക്.

**Docker Hub `latest` (ഓരോ സ്ഥിരതയുള്ള SemVer പബ്ലിഷിലും നിർബന്ധം):**
`docker-publish` വർക്ക്ഫ്ലോ **രണ്ടും** ടാഗ് ചെയ്യണം: `X.Y.Z`, കൂടാതെ
ഇതാണ് ഏറ്റവും ഉയർന്ന സ്ഥിരതയുള്ള SemVer എന്ന് `should-promote-latest.sh` സമ്മതിക്കുമ്പോൾ `:latest`;
രണ്ടിനും **ഒരേ digest** ആയിരിക്കണം. ജോബിനുശേഷം: Hub `latest` digest പുതിയ
SemVer digest-ന് തുല്യമായിരിക്കണം, കൂടാതെ `last_updated` മുന്നോട്ടു നീങ്ങിയിരിക്കണം. റിലീസ് നോട്ടുകൾ git-ൽ മാത്രം
നിലവിലുള്ള പരിഹാരങ്ങളെക്കുറിച്ച് പറയുമ്പോൾ, `:latest` ഒരു പഴയ ബിൽഡിൽ തുടരാൻ അനുവദിക്കരുത്.
Compose ക്വിക്ക്സ്റ്റാർട്ടുകൾ `:latest` ഉപയോഗിക്കുന്നു; GitOps, `X.Y.Z` പിൻ ചെയ്യുന്നത് തുടരേണ്ടതാണ്.
[Docker റിലീസ് ചാനലുകൾ](../guides/DOCKER_GUIDE.md#release-channels), #10317 എന്നിവ കാണുക.

## ഹോട്ട്ഫിക്സ് ഫാസ്റ്റ്-ലെയിൻ (`hotfix` ലേബൽ)

`hotfix` ലേബൽ നൽകിയ PR, ഭാരമേറിയ CI മാട്രിക്സ് (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) ഒഴിവാക്കി വേഗമേറിയതും ശക്തമായ സൂചന നൽകുന്നതുമായ ഗേറ്റുകൾ നിലനിർത്തുന്നു: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`,
കൂടാതെ tarball boot-smoke (`check:pack-boot`). ലക്ഷ്യം: ~33min-ന് പകരം ≤15min-ൽ green.

**പ്രവേശന നയം — നാലും നിർബന്ധം (Chromium/VS Code/Node എമർജൻസി ലെയിനുകളെ മാതൃകയാക്കി):**

1. **ഗൗരവനില**: production പ്രവർത്തനരഹിതമാണ് — പ്രസിദ്ധീകരിച്ച artifact boot സമയത്ത് crash ചെയ്യുന്നു / ഒരു
   security fix / release-ന്റെ എല്ലാ ഉപയോക്താക്കളെയും ബാധിക്കുന്നു. "പ്രധാനപ്പെട്ടത്" എന്നത് "പ്രവർത്തനരഹിതം" എന്നല്ല.
2. **അധികാരം**: repository owner മാത്രമാണ് `hotfix` ലേബൽ പ്രയോഗിക്കുന്നത്. ലേബൽ തന്നെയാണ്
   അംഗീകാരം — campaign PR-ൽ ഒരിക്കലും സ്വയം ഉപയോഗിക്കരുത്.
3. **തെളിവ്**: ഒഴിവാക്കിയ jobs വീണ്ടും സാധൂകരിക്കുമായിരുന്ന suite-ന്റെ മുമ്പത്തെ പൂർണ്ണമായി-green ആയ heavy run-ലേക്കുള്ള link-ഉം,
   fix-ന്റെ സ്വന്തം ആദ്യം പരാജയപ്പെടുകയും പിന്നീട് വിജയിക്കുകയും ചെയ്യുന്ന test-ഉം PR body-യിൽ ഉൾപ്പെടുത്തണം.
4. **പരിധി**: cherry-pick-only — ഏറ്റവും കുറഞ്ഞ fix മാത്രം; refactors ഇല്ല, അനുബന്ധ മാറ്റങ്ങൾ ഇല്ല.

ഒഴിവാക്കിയ coverage/ratchet ഉപരിതലം release branch-ലെ അടുത്ത full run വഴി വീണ്ടും സാധൂകരിക്കുന്നു
(തുടർച്ചയായ release-green) — lane ഒഴിവാക്കുന്നത് കാത്തിരിപ്പാണ്, validation ഒരിക്കലുമല്ല.
Tests-only diffs (`tests/`-നു കീഴിലുള്ള എല്ലാ files-ഉം, `tests/e2e/`-നു കീഴിൽ ഒന്നുമില്ലാത്തത്) യാതൊരു label-ഉം കൂടാതെ
E2E matrix സ്വയമേവ ഒഴിവാക്കും.

### Build Layout

repository മൂന്ന് വ്യത്യസ്ത output directories ഉപയോഗിക്കുന്നു — അവ ഒരിക്കലും തമ്മിൽ കലർത്തരുത്:

| Directory | ഉദ്ദേശ്യം                                                          | Track ചെയ്തിട്ടുണ്ടോ? |
| --------- | ------------------------------------------------------------------ | --------------------- |
| `src/`    | Application source (TypeScript / TSX)                              | ഉണ്ട്                 |
| `.build/` | Build intermediates — `next build` output (`distDir`)              | ഇല്ല (gitignored)     |
| `dist/`   | വിതരണം ചെയ്യാവുന്ന npm bundle — `assembleStandalone` സജ്ജീകരിച്ചത് | ഇല്ല (gitignored)     |

> **Operator കുറിപ്പ്:** remote VPS image directory `/usr/lib/node_modules/omniroute/app/` ആയി തുടരുന്നു.
> **repository-ക്കുള്ളിലെ** build output മാത്രമാണ് മാറിയത് (`app/` → `dist/`). deploy skills,
> `dist/`-ലെ ഉള്ളടക്കം remote `app/` dir-ലേക്ക് rsync ചെയ്യുന്നു — VPS path മാറ്റങ്ങളൊന്നും ആവശ്യമില്ല.

**Single-build flow:**

```
npm run build:release
  └─ rm -rf .build dist          (വൃത്തിയാക്കുന്നു)
  └─ next build → .build/next/   (ഇടക്കാല files)
  └─ assembleStandalone          (standalone + static + public + natives → dist/ എന്നതിലേക്ക് പകർത്തുന്നു)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

deploy ചെയ്യുന്നതിനായി `npm run build` പ്രവർത്തിപ്പിച്ചതിന് ശേഷം വേറിട്ട് `npm run build:cli` പ്രവർത്തിപ്പിക്കരുത് —
ഒറ്റ command-ൽ clean rebuild + sentinel ചെയ്യുന്ന `npm run build:release` ഉപയോഗിക്കുക.

റിലീസിൽ ഗുരുതരമായ പ്രശ്നമുണ്ടെങ്കിൽ:

1. `gh release edit vX.Y.Z --prerelease` (ഏറ്റവും പുതിയതല്ലെന്ന് അടയാളപ്പെടുത്തുന്നു)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (ഉപയോക്താക്കൾ ഇതുവരെ സ്വീകരിച്ചിട്ടില്ലെങ്കിൽ മാത്രം)
3. അല്ലെങ്കിൽ: `release/vX.Y.0`-ൽ ഹോട്ട്ഫിക്സ് → പാച്ച് റിലീസ് `vX.Y.(Z+1)`
4. GitHub Discussions-ലും Discord-ലും ഉടൻ അറിയിക്കുക

## കർശന നിയമങ്ങൾ

- `main`-ലേക്ക് ഒരിക്കലും നേരിട്ട് കമ്മിറ്റ് ചെയ്യരുത്
- `main` അല്ലെങ്കിൽ `release/*` ബ്രാഞ്ചുകളിലേക്ക് ഒരിക്കലും `git push --force` ഉപയോഗിക്കരുത്
- Husky ഹുക്കുകൾ (`--no-verify`) ഒരിക്കലും ഒഴിവാക്കരുത്
- രഹസ്യങ്ങൾ, ക്രെഡൻഷ്യലുകൾ, അല്ലെങ്കിൽ `.env` ഫയലുകൾ ഒരിക്കലും കമ്മിറ്റ് ചെയ്യരുത്
- കവറേജ് ≥60/60/60/60 (സ്റ്റേറ്റ്മെന്റുകൾ/ലൈനുകൾ/ഫങ്ഷനുകൾ/ബ്രാഞ്ചുകൾ) ആയി നിലനിർത്തണം
- `src/`, `open-sse/`, `electron/`, അല്ലെങ്കിൽ `bin/` എന്നിവയിലെ പ്രൊഡക്ഷൻ കോഡ് മാറ്റുമ്പോൾ എല്ലായ്പ്പോഴും ടെസ്റ്റുകൾ ഉൾപ്പെടുത്തുകയോ അപ്ഡേറ്റ് ചെയ്യുകയോ വേണം
