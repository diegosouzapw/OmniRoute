## npm Trusted Publishing (v3.8.51 മുതൽ ഡിഫോൾട്ട്) — അഭ്യർത്ഥനപ്രകാരം staged, പകരമായി direct

ഡിഫോൾട്ടായി `npm-publish.yml` **npm Trusted Publishing (OIDC)** വഴിയാണ് പ്രസിദ്ധീകരിക്കുന്നത്:
`stage-npm` job (github-hosted) GitHub-ന്റെ id-token ആ റണ്ണിനായുള്ള ഹ്രസ്വകാല npm
credential ആയി കൈമാറ്റം ചെയ്യുന്നു — repository secrets-ൽ ദീർഘകാല npm token ഇല്ല, 2FA prompt ഇല്ല, provenance ചേർത്തിരിക്കുന്നു.
2FA ഒഴിവാക്കുന്ന tokens പിൻവലിക്കപ്പെടുന്നതിനാൽ npm ഇപ്പോൾ അംഗീകരിക്കുന്ന bypass ഇതാണ്;
WS1.3 ഉറപ്പ് നിലനിർത്തിക്കൊണ്ട്, v3.8.48 വരെ പ്രോജക്റ്റിലുണ്ടായിരുന്ന പൂർണ്ണമായും സ്വയമേവയുള്ള
പ്രവാഹം ഇത് പുനഃസ്ഥാപിക്കുന്നു (ചോർന്ന token-ന് ഒറ്റയ്ക്ക് പ്രസിദ്ധീകരിക്കാൻ കഴിയില്ല — token തന്നെയില്ല).

**ഒറ്റത്തവണ സജ്ജീകരണം (ഉടമ):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none). ഇത് നിലവിൽ വരുന്നതുവരെ, സ്വയമേവയുള്ള ഘട്ടം `ENEEDAUTH` സഹിതം പരാജയപ്പെടും:
`publish_mode=staged` (താഴെ) അല്ലെങ്കിൽ `direct` ഉപയോഗിച്ച് വീണ്ടും dispatch ചെയ്യുക.

### ഘട്ടംഘട്ടമായ പ്രസിദ്ധീകരണം (അഭ്യർത്ഥനപ്രകാരം — `publish_mode=staged`)

npm-publish workflow ഇനി നേരിട്ട് പ്രസിദ്ധീകരിക്കുന്നില്ല: അത് പാക്ക് ചെയ്ത tarball
ബൂട്ട് ചെയ്യുകയും (`check:pack-boot`) തുടർന്ന് `npm stage publish` പ്രവർത്തിപ്പിക്കുകയും ചെയ്യുന്നു — കൃത്യമായ അതേ bytes
registry-യിൽ സൂക്ഷിക്കപ്പെടുന്നു, ഉടമ അംഗീകരിക്കുന്നതുവരെ അവ **ഇൻസ്റ്റാൾ ചെയ്യാനാവില്ല**.
മനുഷ്യ ഇടപെടലോടെയുള്ള 2FA gate, തെളിവിന് മുമ്പല്ല, അതിന് ശേഷത്തേക്കാണ് മാറ്റിയത്.

**workflow ഗ്രീൻ ആയതിന് ശേഷമുള്ള ഉടമയുടെ പ്രവാഹം:**

1. `npm stage list omniroute` — stage id കണ്ടെത്തുക (workflow summary-യിലും ഇത് പ്രിന്റ് ചെയ്യപ്പെടും).
2. staged bytes പരിശോധിക്കുക (ശുപാർശ ചെയ്യുന്നു): `npm stage download <id>`, തുടർന്ന് ഡൗൺലോഡ് ചെയ്ത
   tarball ഒരു താൽക്കാലിക prefix-ൽ ഇൻസ്റ്റാൾ ചെയ്ത് അത് ബൂട്ട് ചെയ്യുക (`npm run check:pack-boot`, CI-യിൽ
   ഇതേ pack→install→boot വിധി ഓട്ടോമേറ്റ് ചെയ്യുന്നു).
3. `npm stage approve <id>` — 2FA prompt തന്നെയാണ് പ്രസിദ്ധീകരണം. `npm stage reject <id>` അത് ഉപേക്ഷിക്കുന്നു.
4. പ്രസിദ്ധീകരണാനന്തര സുരക്ഷാവലയം: post-publish verifier (v3.8.49 പ്ലാനിലെ WS1.4), പ്രസിദ്ധീകരിച്ച
   പതിപ്പ് public registry-യിൽ നിന്ന് ഒരു ശുദ്ധമായ container-ൽ ഇൻസ്റ്റാൾ ചെയ്ത് ബൂട്ട് ചെയ്യുന്നു.

**അടിയന്തര പകരംമാർഗം:** `publish_mode=direct` ഉപയോഗിച്ചുള്ള `workflow_dispatch`, പഴയ
ഉടനടിയുള്ള `npm publish` പുനഃസ്ഥാപിക്കുന്നു (staging തന്നെ തെറ്റായി പ്രവർത്തിച്ചാൽ മാത്രം ഉപയോഗിക്കുക; കാരണം രേഖപ്പെടുത്തുക).

**ഒറ്റത്തവണ ശക്തിപ്പെടുത്തൽ (ഉടമ, npmjs.com):** `omniroute`-നുള്ള Trusted Publisher
stage-only മോഡിൽ ക്രമീകരിക്കുക; അങ്ങനെ ചോർന്ന ദീർഘകാല token-ന് എവിടെനിന്നും നേരിട്ട് `npm publish`
ചെയ്യാൻ കഴിയില്ല — CI-ക്ക് stage ചെയ്യാൻ മാത്രമേ കഴിയൂ; ഉടമയുടെ 2FA മാത്രമാണ് റിലീസ് ചെയ്യുന്നത്.

**തകരാറുള്ള artifact-നുള്ള നടപടിക്രമം (മാറ്റമില്ല):** ഡിഫോൾട്ട് പ്രതികരണമായി
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` ഉപയോഗിക്കുക (മിനിറ്റുകൾക്കുള്ളിൽ, തിരിച്ചെടുക്കാവുന്നത്);
72h/no-dependents പരിധിക്കുള്ളിൽ മാത്രം `npm unpublish` ഉപയോഗിക്കുക, ഒരിക്കലും ആദ്യ നടപടിയായി ഉപയോഗിക്കരുത്.
Docker: ഒരു version tag ഒരിക്കലും തിരുത്തിയെഴുതരുത് — rollback എന്നത് `latest`-നെ അവസാനം ശരിയായി
പ്രവർത്തിച്ച digest-ലേക്ക് വീണ്ടും ചൂണ്ടുന്നതാണ്.

**Docker Hub `latest` (ഓരോ സ്ഥിരതയുള്ള SemVer പ്രസിദ്ധീകരണത്തിലും നിർബന്ധം):**
`docker-publish` workflow **രണ്ടും** tag ചെയ്യണം: `X.Y.Z`; കൂടാതെ,
ഇതാണ് ഏറ്റവും ഉയർന്ന സ്ഥിരതയുള്ള SemVer എന്ന് `should-promote-latest.sh` അംഗീകരിക്കുമ്പോൾ,
അതേ **digest** ഉപയോഗിച്ച് `:latest`-ഉം. job-ന് ശേഷം: Hub `latest` digest പുതിയ
SemVer digest-ന് തുല്യമായിരിക്കണം, കൂടാതെ `last_updated` മാറിയിരിക്കണം. git-ൽ മാത്രം
നിലവിലുള്ള പരിഹാരങ്ങളെക്കുറിച്ച് release notes പറയുമ്പോൾ, `:latest`-നെ പഴയ
build-ൽ നിലനിർത്തരുത്. Compose quickstarts `:latest` ഉപയോഗിക്കുന്നു; GitOps തുടർന്ന്
`X.Y.Z` pin ചെയ്യണം. [Docker റിലീസ് ചാനലുകൾ](../guides/DOCKER_GUIDE.md#release-channels), #10317 എന്നിവ കാണുക.

## ഹോട്ട്ഫിക്സ് ഫാസ്റ്റ്-ലെയ്ൻ (ലേബൽ `hotfix`)

`hotfix` ലേബൽ നൽകിയ ഒരു PR, ഭാരമേറിയ CI മാട്രിക്സ് (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) ഒഴിവാക്കുകയും വേഗമേറിയതും ഉയർന്ന സിഗ്നൽ നൽകുന്നതുമായ ഗേറ്റുകൾ നിലനിർത്തുകയും ചെയ്യുന്നു: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`,
കൂടാതെ tarball boot-smoke (`check:pack-boot`). ലക്ഷ്യം: ~33min-ന് പകരം ≤15min-ൽ വിജയകരമാകുക.

**പ്രവേശന നയം — നാലും നിർബന്ധം (Chromium/VS Code/Node എമർജൻസി ലെയ്നുകളെ മാതൃകയാക്കിയത്):**

1. **തീവ്രത**: പ്രൊഡക്ഷൻ തകരാറിലാണ് — പ്രസിദ്ധീകരിച്ച ആർട്ടിഫാക്റ്റ് ബൂട്ട് ചെയ്യുമ്പോൾ ക്രാഷാകുന്നു / ഒരു
   സുരക്ഷാ പരിഹാരം / റിലീസിന്റെ എല്ലാ ഉപയോക്താക്കളെയും ബാധിക്കുന്നു. "പ്രധാനപ്പെട്ടത്" എന്നത് "തകരാറിലായത്" എന്നല്ല.
2. **അധികാരം**: repository ഉടമ മാത്രമേ `hotfix` ലേബൽ പ്രയോഗിക്കാവൂ. ലേബൽ തന്നെയാണ്
   അംഗീകാരം — campaign PR-ൽ ഒരിക്കലും സ്വയം പ്രയോഗിക്കരുത്.
3. **തെളിവ്**: PR ബോഡിയിൽ മുമ്പത്തെ പൂർണ്ണമായി വിജയിച്ച heavy run-ലേക്കുള്ള ലിങ്കും (ഒഴിവാക്കിയ jobs
   വീണ്ടും സാധൂകരിക്കുമായിരുന്ന suite), പരിഹാരത്തിന്റെ സ്വന്തം ആദ്യം പരാജയപ്പെടുകയും പിന്നീട് വിജയിക്കുകയും ചെയ്ത test-ഉം ഉണ്ടായിരിക്കണം.
4. **വ്യാപ്തി**: cherry-pick-only — ഏറ്റവും ചുരുങ്ങിയ പരിഹാരം മാത്രം; refactor-കളോ അനുബന്ധ മാറ്റങ്ങളോ പാടില്ല.

ഒഴിവാക്കിയ coverage/ratchet ഉപരിതലം release branch-ലെ അടുത്ത full run വഴി
വീണ്ടും സാധൂകരിക്കപ്പെടുന്നു (തുടർച്ചയായ release-green) — lane ഒഴിവാക്കുന്നത് കാത്തിരിപ്പാണ്, സാധൂകരണമല്ല.
Tests-only diff-കൾ (`tests/`-ന് കീഴിലുള്ള എല്ലാ files-ഉം, `tests/e2e/`-ന് കീഴിൽ ഒന്നുമില്ലാത്തതും) യാതൊരു label-ഉം കൂടാതെ
E2E matrix സ്വയമേവ ഒഴിവാക്കും.

### Hooks (Husky സാധൂകരിച്ചത്)

Husky hooks `.husky/`-ൽ സ്ഥിതിചെയ്യുന്നു; git operations നടക്കുമ്പോൾ അവ സ്വയമേവ പ്രവർത്തിക്കും.

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** വേഗമേറിയ നിർണിത gates — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (2026-06-13-ന് സജീവമാക്കി). `test:unit` മനഃപൂർവം ഒഴിവാക്കിയിരിക്കുന്നു (വേഗം കുറവാണ്; CI `test-unit` job ഇത് ഉൾക്കൊള്ളുന്നു).
  - release branches push ചെയ്യുന്നതിന് മുമ്പ് `npm run test:unit` മാനുവലായി പ്രവർത്തിപ്പിക്കുക.

ഒരു hook പരാജയപ്പെട്ടാൽ: അടിസ്ഥാന പ്രശ്നം പരിഹരിക്കുക; `--no-verify` ഉപയോഗിച്ച് മറികടക്കരുത്.

### Build ലേഔട്ട്

റിപ്പോസിറ്ററി മൂന്ന് വ്യത്യസ്ത output directory-കൾ ഉപയോഗിക്കുന്നു — അവ ഒരിക്കലും പരസ്പരം കലർത്തരുത്:

| Directory | ഉദ്ദേശ്യം                                                                        | ട്രാക്ക് ചെയ്യുന്നുണ്ടോ? |
| --------- | -------------------------------------------------------------------------------- | ------------------------ |
| `src/`    | ആപ്ലിക്കേഷൻ ഉറവിടം (TypeScript / TSX)                                            | ഉണ്ട്                    |
| `.build/` | Build intermediate-കൾ — `next build` output (`distDir`)                          | ഇല്ല (gitignored)        |
| `dist/`   | വിതരണം ചെയ്യാവുന്ന npm bundle — `assembleStandalone` ഉപയോഗിച്ച് കൂട്ടിച്ചേർത്തത് | ഇല്ല (gitignored)        |

> **ഓപ്പറേറ്റർ കുറിപ്പ്:** റിമോട്ട് VPS image directory `/usr/lib/node_modules/omniroute/app/` ആയി തുടരുന്നു.
> **റിപ്പോസിറ്ററിക്കുള്ളിലെ** build output മാത്രമാണ് മാറിയത് (`app/` → `dist/`). Deploy skill-കൾ
> `dist/`-ലെ ഉള്ളടക്കം റിമോട്ട് `app/` dir-ലേക്ക് rsync ചെയ്യുന്നു — VPS path-ൽ മാറ്റങ്ങളൊന്നും ആവശ്യമില്ല.

**ഒറ്റ-build പ്രവാഹം:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Deploy ചെയ്യുന്നതിനായി `npm run build` പ്രവർത്തിപ്പിച്ചതിനുശേഷം വേറിട്ട് `npm run build:cli` പ്രവർത്തിപ്പിക്കരുത് — ഒറ്റ command-ൽ clean rebuild + sentinel ചെയ്യുന്ന
`npm run build:release` ഉപയോഗിക്കുക.

develop ബമ്പ് കമ്മിറ്റ് git പ്ലംബിംഗ് ഉപയോഗിച്ചാണ് നിർമ്മിക്കുന്നത് (വർക്കിംഗ് ട്രീയിൽ മാറ്റമൊന്നും വരുത്തുന്നില്ല), കൂടാതെ
ഒരു സൈക്കിൾ-ഓപ്പൺ കമ്മിറ്റിലെ അതേ അഞ്ച് ഫയലുകൾ ബമ്പ് ചെയ്യുന്നു: `package.json`, `open-sse/package.json`,
`electron/package.json`, `package-lock.json`, `docs/openapi.yaml` എന്നിവ. `[4.0.0]`
CHANGELOG വിഭാഗവും അതിന്റെ i18n മിററുകളും `develop`-ൽ അതിന്റെ ആദ്യ PR-ന് മുമ്പായി പിന്നീട് തുറക്കുന്നു.
സ്ക്രിപ്റ്റ് ഒരിക്കലും npm dist-tags മാറ്റുന്നില്ല — അവ ഒരു സ്ക്രാച്ച് പാക്കേജിൽ റിഹേഴ്സൽ ചെയ്യുക.

### PR പ്രിവ്യൂ ആർട്ടിഫാക്റ്റ് (ഒരിക്കൽ ബിൽഡ് ചെയ്യുക, അതേ ബൈറ്റുകൾ പ്രമോട്ട് ചെയ്യുക)

`.github/workflows/preview-artifact.yml` ഒരു PR ഹെഡിൽ നിന്ന് ഒരു പ്രൊഡക്ഷൻ ടാർബോൾ നിർമ്മിക്കുകയും
അതേ ബിൽഡ് സാധൂകരിക്കുകയും ചെയ്യുന്നു (#8084 സ്ലൈസ് (a)). അതേ റിപ്പോസിറ്ററിയിലുള്ള PR-കൾക്ക് മാത്രം;
ഒന്നും പബ്ലിഷ് ചെയ്യില്ല.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # അല്ലെങ്കിൽ `preview-artifact` ലേബൽ ചേർക്കുക
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # പ്രിവ്യൂ ഇൻസ്റ്റാൾ
```

ഈ റൺ `npm ci`, `npm run build:release`, `npm run check:pack-artifact` എന്നിവ നിർവഹിച്ച്
ടാർബോൾ പാക്ക് ചെയ്യുന്നു, `npm run check:pack-boot` പ്രവർത്തിപ്പിക്കുന്നു (വ്യാജ സീക്രട്ടുകൾ, താൽക്കാലിക ഡാറ്റ ഡയറക്ടറി),
വീണ്ടും പാക്ക് ചെയ്യുന്നു, ഡൈജസ്റ്റ് സമാനമല്ലെങ്കിൽ പരാജയപ്പെടുന്നു; തുടർന്ന് `artifact-identity.json` രേഖപ്പെടുത്തുന്നു
(ഹെഡ് SHA, ബേസ് SHA, ലോക്ക്ഫയൽ ഹാഷ്, പ്ലാറ്റ്ഫോം, ആർക്കിടെക്ചർ, node ABI, ബണ്ട്ലർ, ബിൽഡ് പോളിസി —
`scripts/release/artifact-identity.mjs`) കൂടാതെ വേറൊരു ജോബിൽ ടാർബോളിന് അറ്റസ്റ്റേഷൻ നൽകുന്നു. ഒരു പ്രിവ്യൂ
പ്രമോട്ട് ചെയ്യുക എന്നത് ആ ടാർബോൾ ഇൻസ്റ്റാൾ ചെയ്യുക എന്നതാണ്: സോഴ്സിൽ നിന്ന് ഒരിക്കലും വീണ്ടും ബിൽഡ് ചെയ്യരുത്.

### കട്ട് (3.9.0, GO-യ്ക്ക് ശേഷം)

1. GO [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md)-ൽ രേഖപ്പെടുത്തിയിരിക്കുന്നു.
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` എന്നത് `RESULT: READY` പ്രിന്റ് ചെയ്യുന്നു.
3. ഡ്രൈ-റൺ പ്രിന്റ് ചെയ്യുന്ന കമാൻഡുകൾ ഉപയോഗിച്ച് `origin`-ൽ ബ്രാഞ്ചുകൾ മാനുവലായി സൃഷ്ടിക്കുക —
   `origin`-ലേക്ക് പുഷ് ചെയ്യാൻ സ്ക്രിപ്റ്റ് വിസമ്മതിക്കും. റിവ്യൂ ചെയ്ത develop കമ്മിറ്റ് വീണ്ടും ഉപയോഗിക്കാൻ,
   ആദ്യം നിങ്ങളുടെ ഫോർക്കിനെതിരെ 3.9.0 ടിപ്പിൽ `--execute` റിഹേഴ്സൽ പ്രവർത്തിപ്പിക്കുക; അത് രണ്ട് SHA-കളും
   പ്രിന്റ് ചെയ്യും, അതേ കമ്മിറ്റുകൾ പുഷ് ചെയ്യാം:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. ആദ്യ PR ലാൻഡ് ചെയ്യുന്നതിന് മുമ്പ് `stable/v3`, `develop` എന്നിവ പരിരക്ഷിക്കുക (റൂൾസെറ്റുകൾ + മെർജ് ക്യൂ).
5. ബ്രാഞ്ചുകളുടെ നിലനിൽപ്പ് അനുസരിച്ച് പ്രവർത്തനരഹിതമായ വർക്ക്ഫ്ലോകൾ ഓൺ ആകുന്നു: `forward-port.yml`
   (`stable/v3`-ലേക്കുള്ള പുഷ്), `validate-stable-pr.yml` (`stable/v3`-ലേക്കുള്ള PR-കൾ), `nightly-v4-build.yml`
   (`develop` ബിൽഡ് ചെയ്യുന്നു). ഗോ-ലൈവിന് മുമ്പ് `secrets.FORWARD_PORT_TOKEN` റിപ്പോസിറ്ററി സീക്രട്ട് സജ്ജമാക്കുക
   (ഫോർവേഡ്-പോർട്ട് PR-കളിൽ CI പ്രവർത്തിക്കാൻ); ഉടമ `vars.NIGHTLY_PUBLISH` റിപ്പോസിറ്ററി വേരിയബിൾ `true`
   ആയി സജ്ജമാക്കുകയും npm Trusted Publishing `nightly-v4-build.yml` അംഗീകരിക്കുകയും ചെയ്യുന്നതുവരെ
   nightly പബ്ലിഷിംഗ് ഓഫ് ആയിരിക്കും. ചാനൽ റിസല്യൂഷൻ `scripts/release/dist-tag.mjs` ആണ്,
   `npm-publish.yml` ഉപയോഗിക്കുന്ന അതേ റിസോൾവർ.
6. ചാനലുകൾ പരിശോധിക്കുക: `npm view omniroute dist-tags --json` എന്നത് `latest` = 3.9.0 എന്നും
   v4 പബ്ലിഷ് ചെയ്യുന്നതുവരെ `next` / `nightly` ഇല്ലെന്നും കാണിക്കുന്നു.
7. ആവശ്യമെങ്കിൽ റോൾബാക്ക് ചെയ്യുക: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   കൂടാതെ `npm dist-tag add omniroute@3.8.59 latest`.

## കർശന നിയമങ്ങൾ

- ഒരിക്കലും നേരിട്ട് `main`-ലേക്ക് കമ്മിറ്റ് ചെയ്യരുത്
- `main` അല്ലെങ്കിൽ `release/*` ബ്രാഞ്ചുകളിലേക്ക് ഒരിക്കലും `git push --force` ഉപയോഗിക്കരുത്
- Husky ഹുക്കുകൾ (`--no-verify`) ഒരിക്കലും ഒഴിവാക്കരുത്
- രഹസ്യങ്ങൾ, ക്രെഡൻഷ്യലുകൾ, അല്ലെങ്കിൽ `.env` ഫയലുകൾ ഒരിക്കലും കമ്മിറ്റ് ചെയ്യരുത്
- കവറേജ് ≥60/60/60/60 (സ്റ്റേറ്റ്മെന്റുകൾ/ലൈനുകൾ/ഫങ്ഷനുകൾ/ബ്രാഞ്ചുകൾ) ആയി നിലനിർത്തണം
- `src/`, `open-sse/`, `electron/`, അല്ലെങ്കിൽ `bin/` എന്നിവയിലെ പ്രൊഡക്ഷൻ കോഡ് മാറ്റുമ്പോൾ എല്ലായ്പ്പോഴും ടെസ്റ്റുകൾ ഉൾപ്പെടുത്തുകയോ അപ്ഡേറ്റ് ചെയ്യുകയോ വേണം
