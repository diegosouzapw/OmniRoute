## ഭാഗം 1 — വിധിയും പക്വതാ വർഗ്ഗീകരണവും

**മൊത്തത്തിലുള്ള ഗ്രേഡ്: A− / "Advanced". പ്രോജക്റ്റുകളുടെ ഏറ്റവും മികച്ച ~5–10%-ത്തിൽ.** വ്യവസായം വ്യക്തമായി പേരിട്ടിട്ടുള്ള നിരവധി pattern-ുകൾ ഈ സിസ്റ്റം സ്വതന്ത്രമായി നടപ്പിലാക്കുന്നു — അതാണ് പൊരുത്തപ്പെടലിന്റെ ഏറ്റവും ശക്തമായ സൂചന (ഞങ്ങൾ ഒരു checklist പകർത്തിയതല്ല; ശരിയായ സമ്പ്രദായങ്ങളിലേക്ക് സ്വതന്ത്രമായി എത്തിച്ചേർന്നതാണ്).

## ഭാഗം 2 — നിർണായക വിലയിരുത്തൽ (ശക്തികൾ + സത്യസന്ധമായ ദൗർബല്യങ്ങൾ)

### ശക്തികൾ (ശരാശരിയേക്കാൾ മികച്ചവ)

1. **മൾട്ടി-മെട്രിക് റാച്ചറ്റ് എഞ്ചിൻ.** സിസ്റ്റത്തിന്റെ ഹൃദയം. `quality-baseline.json`-ൽ 24 മെട്രിക്കുകൾ
   - 4 സമർപ്പിത ബേസ്ലൈനുകൾ; ഓരോന്നിനും ദിശ (`up`/`down`), ടോളറൻസ് (`eps`), സ്ലാക്ക്
     (`tightenSlack`), `dedicatedGate` ഫ്ലാഗ് എന്നിവയുണ്ട്. ഒരിക്കൽ പരിഹരിച്ച കാര്യങ്ങൾ **പരിഹരിക്കപ്പെട്ട നിലയിൽ**
     തുടരുന്നു — കോഡ്ബേസ് എൻട്രോപ്പിക്കുള്ള മറുമരുന്നാണിത്.
2. **സപ്ലൈ-ചെയിനിനായുള്ള ഡിഫൻസ്-ഇൻ-ഡെപ്ത്.** SAST (CodeQL/Sonar) + സീക്രറ്റുകൾ (`useDefault`
   സഹിതമുള്ള gitleaks) + SCA (osv/npm-audit/Trivy/Dependabot) + ലൈസൻസുകൾ + ലോക്ക്ഫയൽ + SBOM + SLSA
   പ്രൊവനൻസ് + Scorecard + വർക്ക്ഫ്ലോ ഹാർഡനിംഗ് (zizmor). ഇത്രയും സമ്പൂർണ്ണമായ സ്റ്റാക്ക് വളരെ കുറച്ച് കോഡ്ബേസുകൾക്കേ ഉള്ളൂ.
3. **Goodhart's Law-നെതിരായ മറുമരുന്നുകൾ.** കവറേജിനെ ലക്ഷ്യമാക്കുന്നത് ഒരു ക്ലാസിക് ആന്റി-പാറ്റേണാണ്
   ("ഒരു അളവുകോൽ തന്നെ ലക്ഷ്യമായി മാറുമ്പോൾ, അത് ഒരു നല്ല അളവുകോൽ അല്ലാതാകുന്നു"). അതിനെ സന്തുലിതമാക്കാൻ നമുക്കുള്ളത്:
   **മ്യൂട്ടേഷൻ ടെസ്റ്റിംഗ്** (ടെസ്റ്റ് ഒരു വരി എക്സിക്യൂട്ട് ചെയ്യുന്നുണ്ടോ എന്നതിനു പകരം ബഗ് കണ്ടെത്തുന്നുണ്ടോ എന്ന് അളക്കുന്നു),
   **`check-test-masking`** (പാസ് ആക്കുന്നതിനായി അസേർട്ടുകൾ ദുർബലമാക്കുന്നത് തടയുന്നു),
   **ഓരോ മൊഡ്യൂളിനുമുള്ള കവറേജ് ഫ്ലോറുകൾ** (എളുപ്പമുള്ള ഭാഗങ്ങൾ മാത്രമല്ല, ഉയർന്ന അപകടസാധ്യതയുള്ള കോഡും ടെസ്റ്റ് ചെയ്യാൻ നിർബന്ധിക്കുന്നു), കൂടാതെ
   **`check-pr-evidence`** (കർശന നിയമം #18).
4. **ഹാലൂസിനേഷൻ-വിരുദ്ധ / സ്ഥിരതാ ഗേറ്റുകൾ.** അപൂർവവും വിലപ്പെട്ടതുമായ വിഭാഗം: `check-known-symbols`,
   `check-fetch-targets`, `check-openapi-routes`, `check-docs-symbols` എന്നിവ ഡോക്യുമെന്റുകളും സ്പെക്കുകളും
   സ്ട്രിംഗ് ഡിസ്പാച്ചുകളും നിലവിലുള്ള സിംബലുകളിലേക്കാണ് വിരൽചൂണ്ടുന്നതെന്ന് ഉറപ്പാക്കുന്നു. ലിന്റ്/ടെസ്റ്റ് കണ്ടെത്താത്ത "ജീർണത" ഇത് കണ്ടെത്തുന്നു.
5. **അഡ്വൈസറി→ബ്ലോക്കിംഗ് ലൈഫ്സൈക്കിൾ.** പുതിയ ഗേറ്റുകൾ അഡ്വൈസറിയായി പ്രവേശിക്കുന്നു (പക്വത കൈവരിക്കുന്നതിനിടെ
   മെർജുകൾ തടയില്ല), തുടർന്ന് സൈക്കിൾ അവസാനിക്കുമ്പോൾ ബ്ലോക്കിംഗായി മാറുന്നു. ഗുണനിലവാരപരിധി നഷ്ടപ്പെടുത്താതെ ഘർഷണം കുറയ്ക്കുന്നു.
6. **ഇൻഫ്രാസ്ട്രക്ചർ ലഭ്യമല്ലെങ്കിൽ തടസ്സമില്ലാത്ത സ്കിപ്പ്.** ബൈനറി/നെറ്റ്വർക്ക് പരാജയപ്പെട്ടാൽ സ്കാനറുകൾ (`--ratchet`)
   `exit 0` ഉപയോഗിച്ച് അവസാനിക്കുന്നു — ലഭ്യമല്ലാത്ത ഇൻഫ്രാസ്ട്രക്ചർ സാധുവായ PR-നെ ഒരിക്കലും തടയില്ല. പക്വതയാർന്ന എൻജിനീയറിംഗ്.
7. **ചട്ടബദ്ധമാക്കിയ സംസ്കാരം.** കർശന നിയമങ്ങൾ + `trust-but-verify` + സ്റ്റെയിൽ-അലൗലിസ്റ്റ് + എവിഡൻസ്-ഗേറ്റ്
   എന്നിവ അച്ചടക്കത്തെ സ്വയമേവയുള്ള പരിശോധനയാക്കി മാറ്റുന്നു.

### സത്യസന്ധമായ ദൗർബല്യങ്ങൾ (യഥാർത്ഥ വിടവുകൾ)

1. **🔴 ഫാസ്റ്റ്-ഗേറ്റ്സ് വിഭജനം ഇപ്പോഴും ഘടനാപരമായൊരു വിടവ് അവശേഷിപ്പിക്കുന്നു.** `quality.yml` (PR→`release/**`)
   ഇപ്പോൾ കോഡ് PR-കൾക്കായി ടൈപ്പ്ചെക്ക്, വേഗത്തിലുള്ള ഡിറ്റർമിനിസ്റ്റിക് ടെസ്റ്റുകൾ, ഒരു അഡ്വൈസറി പ്രൊഡക്ഷൻ ബിൽഡ് എന്നിവ പ്രവർത്തിപ്പിക്കുന്നു;
   എന്നാൽ `ci.yml`-ലെ പൂർണ്ണമായ റിലീസ്-PR പരിധി (കവറേജ് റാച്ചറ്റുകൾ,
   പാക്കേജ് ആർട്ടിഫാക്റ്റ്, ഇന്റഗ്രേഷൻ, E2E, SonarQube) ഇപ്പോഴും പ്രവർത്തിപ്പിക്കുന്നില്ല. പ്രചോദനം (വേഗത) സാധുവാണ്, പക്ഷേ മെർജ് നടക്കുന്നിടത്താണ് ഗേറ്റ്
   ഉണ്ടായിരിക്കേണ്ടത് (ഷിഫ്റ്റ്-ലെഫ്റ്റ്). **പരിഹരിക്കാനുള്ളതിൽ ഏറ്റവും വലിയ ഘടനാപരമായ പ്രശ്നം.**
2. **🟠 ഗേറ്റുകളുടെ അമിതവ്യാപനം/ക്ഷീണ സാധ്യത.** ~46 ഗേറ്റുകൾ + 25 ജോലികൾ എന്നത് വളരെ കൂടുതലാണ്. Sonar തന്നെ മുന്നറിയിപ്പ് നൽകുന്നു:
   അത്യധികം നിബന്ധനകൾ "ഗേറ്റ് ഫറ്റീഗ്"-നും മുൻഗണനാ തർക്കങ്ങൾക്കും കാരണമാകുന്നു; അതിലൂടെ ഒരു ഗേറ്റ്
   അവഗണിക്കപ്പെടാനുള്ള അപകടമുണ്ട്. ഭാരമേറിയ ഗേറ്റുകൾ ലീഡ്-ടൈം വർധിപ്പിക്കുന്നുവെന്ന് DORA മുന്നറിയിപ്പ് നൽകുന്നു. അഡ്വൈസറി ടയറുകളും
   കേവലമല്ലാത്ത റാച്ചറ്റുകളും ഉപയോഗിച്ച് നാം ഇത് ലഘൂകരിക്കുന്നു, പക്ഷേ **ഓരോ ഗേറ്റിനുമുള്ള ആനുകാലിക ROI അവലോകനം** നിലവിലില്ല (ഡോക്-സിങ്കിനായുള്ള ചില
   മൈക്രോ-ഗേറ്റുകൾ ഏകീകരിക്കാവുന്നതാണ്).
3. **🟠 മ്യൂട്ടേഷൻ സ്കോർ ഇതുവരെ ഒരു റാച്ചറ്റല്ല.** കവറേജ്-ഗെയിമിംഗിനെതിരായ ഏറ്റവും ശക്തമായ മറുമരുന്ന്
   **അഡ്വൈസറി** മാത്രമാണ്. തീർപ്പാക്കാനുള്ളതിൽ ഏറ്റവും ഉയർന്ന മൂല്യമുള്ള ഇനമാണിത് (ഇതിനകം 90% പൂർത്തിയായിട്ടുണ്ട്).
4. **🟡 ബ്ലോക്ക് ചെയ്യേണ്ട അഡ്വൈസറികൾ (ശരിയായ പരിധിയോടെ).** ഫ്രീസ് ചെയ്ത ബേസ്ലൈനുകൾ ഉണ്ടായിട്ടും `osv` (vulnCount), `oasdiff` എന്നിവ
   അഡ്വൈസറിയാണ്. osv-അഡ്വൈസറി എന്നത് യുക്തിസഹമാണ് (ഒരു പഴയ ഡിപ്പെൻഡൻസിയിലെ പുതിയ CVE,
   ബന്ധമില്ലാത്ത ഒരു PR-നെ തടയും) — എന്നാൽ ഒരു മധ്യപാതയുണ്ട് (Trivy-യിൽ ചെയ്തതുപോലെ CRITICAL+fixable മാത്രം ബ്ലോക്ക് ചെയ്യുക).
   oasdiff അഡ്വൈസറിയായതിനാൽ കരാർ ലംഘിക്കുന്ന ഒരു മാറ്റത്തിന് കടന്നുപോകാനാകും.
5. **🟡 റൺടൈം സുരക്ഷ രാത്രികാല പരിശോധനയിൽ മാത്രം.** schemathesis/garak/promptfoo/chaos/k6 രാത്രിയിൽ പ്രവർത്തിക്കുന്നു.

   അടുത്ത രാത്രി മാത്രമേ കണ്ടെത്തപ്പെടൂ.
6. **🟡 `main`-ലെ ബ്രാഞ്ച്-പ്രൊട്ടക്ഷൻ ഓഫാണ്.** `BRANCH_LOCK_TOKEN` _release_ ബ്രാഞ്ചുകൾ ലോക്ക് ചെയ്യുന്നു, പക്ഷേ

## ഭാഗം 3 — ഗുണനിലവാര പരിശോധനാ ഘട്ടങ്ങളുടെ സമ്പൂർണ്ണ കാറ്റലോഗ് (പോർട്ടബിൾ)

താഴെയുള്ള 12 വിഭാഗങ്ങൾ പുനരുപയോഗിക്കാവുന്ന രൂപത്തിലുള്ള "ഗുണനിലവാര സംവിധാനമാണ്". ഓരോന്നിലും
**ലക്ഷ്യം** (എന്താണ് സംരക്ഷിക്കേണ്ടത്), **ഞങ്ങൾ ഉപയോഗിക്കുന്ന ഉപകരണങ്ങൾ**, ഏത് സ്റ്റാക്കിലും അത് പുനഃസൃഷ്ടിക്കാനുള്ള
**ഉപകരണ-സ്വതന്ത്രമായ തത്തുല്യരീതി** എന്നിവ പട്ടികപ്പെടുത്തിയിരിക്കുന്നു.

### 1. ശൈലിയും ഫോർമാറ്റിംഗും (നിർണിതം, വേഗമേറിയത്)

- **OmniRoute:** lint-staged വഴി Prettier + ESLint (pre-commit), 2-spaces/double-quotes/100col.
- **പൊതുവായത്:** സ്വയമേവ പരിഹരിക്കാവുന്ന ഒരു ഫോർമാറ്റർ + ഒരു ലിന്റർ; staged ഫയലുകളിൽ pre-commit സമയത്ത് പ്രവർത്തിക്കുന്നത്.

### 2. ടൈപ്പുകൾ

- **OmniRoute:** `typecheck:core` (തടയുന്നത്) + `typecheck:noimplicit:core` (ഉപദേശാത്മകം) + `type-coverage` റാച്ചറ്റ് 92.17% + ഓരോ ഫയലിനുമുള്ള any-budget.
- **പൊതുവായത്:** CI-യിൽ കർശനമായ typecheck + റാച്ചറ്റ് ചെയ്ത type-coverage മെട്രിക് + ഓരോ ഫയലിനുമുള്ള `any`/escape-hatch ബജറ്റ്.

### 3. ടെസ്റ്റുകൾ (തീവ്രത)

- **OmniRoute:** പരസ്പരം ഓവർലാപ്പ് ചെയ്യാത്ത 2 റണ്ണറുകൾ (Node native + vitest), 8 shards, ആഗോള കവറേജ് 60/60/60/60 + റാച്ചറ്റ് ~76% + **നിർണായക മൊഡ്യൂളുകൾക്കായി ഓരോ മൊഡ്യൂളിനുമുള്ള 8 കുറഞ്ഞ പരിധികൾ** + രാത്രികാല property tests + രാത്രികാല **mutation testing**.
- **പൊതുവായത്:** ടെസ്റ്റ് റണ്ണർ(കൾ) + **സമ്പൂർണ്ണമായ** കവറേജ് കുറഞ്ഞ പരിധി (പൂജ്യമാകുന്നത് തടയാൻ) + കവറേജ് **റാച്ചറ്റ്** (പിന്നോട്ടുപോകൽ തടയാൻ) + **ഉയർന്ന അപകടസാധ്യതയുള്ള കോഡിനായി ഓരോ മൊഡ്യൂളിനുമുള്ള കുറഞ്ഞ പരിധികൾ** (Goodhart പ്രതിഭാസം തടയാൻ) + ശുദ്ധമായ ലോജിക്കിനായി property-based പരിശോധന + ടെസ്റ്റ് ഗുണനിലവാരത്തിന്റെ യഥാർഥ അളവായി രാത്രികാല **mutation testing**.

### 4. ടെസ്റ്റ് നയം (കൃത്രിമമായി മറികടക്കുന്നത് തടയാൻ)

- **OmniRoute:** `pr-test-policy` (പ്രൊഡക്ഷൻ കോഡിന് ടെസ്റ്റ് നിർബന്ധം), `check-test-masking` (ദുർബലമാക്കിയ asserts തടയുന്നു), `pr-evidence` (വിജയവാദത്തിന് തെളിവ് ബ്ലോക്ക് ആവശ്യമാണ്), `test-discovery` (ഓരോ ടെസ്റ്റും ഒരു റണ്ണർ ശേഖരിക്കുന്നു).
- **പൊതുവായത്:** "പുതിയ കോഡ് ⇒ പുതിയ ടെസ്റ്റ്" ഗേറ്റ് + നീക്കംചെയ്ത assert/tautology കണ്ടെത്തൽ + തെളിവ് ആവശ്യകത (TDD അല്ലെങ്കിൽ നിലവിലുള്ള ടെസ്റ്റ്) + glob-കൾക്ക് പുറത്തായി ഒരു ടെസ്റ്റും അനാഥമാകുന്നില്ലെന്ന ഉറപ്പ്.

### 5. സങ്കീർണ്ണതയും കോഡ് ആരോഗ്യവും (റാച്ചറ്റുകൾ)

- **OmniRoute:** ESLint-warnings (3769↓), jscpd duplication (5.72%↓), cyclomatic+max-lines complexity (1800↓), cognitive complexity sonarjs (753↓), dead-code/unused-exports knip (339↓), ഓരോ ഫയലിനുമുള്ള file-size (സ്ഥിരീകരിച്ചത്, കുറയ്ക്കാൻ മാത്രം), circular-deps (ഇഷ്ടാനുസൃത Tarjan, തടയുന്നത്).
- **പൊതുവായത്:** എല്ലാ ആരോഗ്യ മെട്രിക്കുകളും റാച്ചറ്റ് ചെയ്യുക (മുന്നറിയിപ്പുകൾ, ഡ്യൂപ്ലിക്കേഷൻ, cyclomatic **കൂടാതെ** cognitive complexity, dead code, file size, import cycles). ദിശ എല്ലായ്പ്പോഴും "പിന്നോട്ടുപോകരുത്" എന്നതാണ്.

### 6. സ്റ്റാറ്റിക് സുരക്ഷ (SAST + രഹസ്യങ്ങൾ)

- **OmniRoute:** CodeQL (അലേർട്ട് റാച്ചറ്റ് = 0), gitleaks (`[extend] useDefault=true` — നിർണായകം!), SonarQube, ഇഷ്ടാനുസൃത സുരക്ഷാ നിയമങ്ങൾ (public-creds, error-helper, route-guard-membership, route-validation).
- **പൊതുവായത്:** അലേർട്ട് റാച്ചറ്റോടുകൂടിയ SAST (CodeQL/Sonar/semgrep) + **പാരമ്പര്യമായി ലഭിച്ച ഡിഫോൾട്ട് നിയമസമുച്ചയം** ഉപയോഗിക്കുന്ന secrets scanner (ഡിഫോൾട്ടിനെ അസാധുവാക്കുന്ന ഇഷ്ടാനുസൃത കോൺഫിഗറേഷൻ = അന്ധത) + പ്രോജക്റ്റ്-നിർദ്ദിഷ്ട Hard Rule സുരക്ഷാ ഗേറ്റുകൾ.

### 7. വിതരണ ശൃംഖല (ഡിപെൻഡൻസികൾ)

- **OmniRoute:** osv-scanner + npm-audit + Trivy + Dependabot (SCA), license-checker (SPDX allowlist), lockfile-lint (HTTPS+sha512+registry), `check-deps` anti-slopsquatting (allowlist + പ്രായം ≥72h).
- **പൊതുവായത്:** ഒന്നിലധികം സ്രോതസ്സുകളുള്ള SCA + ലൈസൻസ് allowlist + lockfile സമഗ്രതാ പരിശോധന + പ്രായം/typosquatting പരിശോധനയോടുകൂടിയ ഡിപെൻഡൻസി allowlist + ഗ്രൂപ്പ് ചെയ്ത അപ്ഡേറ്റ് ബോട്ട്.

### 8. വിതരണ ശൃംഖല (ബിൽഡും റിലീസും)

- **OmniRoute:** SBOM (CycloneDX + syft), SLSA provenance (`--provenance`), OpenSSF Scorecard (പ്രതിവാരം), workflow hardening (zizmor: artipacked→`persist-credentials:false`, cache-poisoning, token-permissions).
- **പൊതുവായത്:** പ്രസിദ്ധീകരിക്കുമ്പോൾ SBOM സൃഷ്ടിക്കുക + ഒപ്പിട്ട provenance (SLSA L2+) + ഷെഡ്യൂൾ ചെയ്ത Scorecard + എല്ലാ workflows-ഉം സുരക്ഷിതമാക്കുക (കുറഞ്ഞ പ്രിവിലേജുള്ള ടോക്കണുകൾ, പുഷ് ചെയ്യാത്ത checkout-ൽ credentials നിലനിർത്തരുത്, actions SHA ഉപയോഗിച്ച് പിൻ ചെയ്യുക).

### 9. കരാറുകളും API-യും

- **OmniRoute:** oasdiff (ബ്രേക്കിംഗ്-ചേഞ്ച് OpenAPI), schemathesis (രാത്രികാല contract fuzz), openapi-coverage (% രേഖപ്പെടുത്തിയ routes, റാച്ചറ്റ് 38.3%), openapi-security-tiers (spec-നും route-guard-നും ഇടയിൽ).
- **പൊതുവായത്:** ബ്രേക്കിംഗ്-ചേഞ്ച് contract diff (oasdiff/buf) + spec-നെ അടിസ്ഥാനമാക്കിയുള്ള property-based fuzz (schemathesis) + റാച്ചറ്റ് ചെയ്ത ഡോക്യുമെന്റേഷൻ കവറേജ് + spec↔code സ്ഥിരത.

### 10. ഡോക്സും i18n-ഉം (കാലഹരണപ്പെടൽ തടയാൻ)

- **OmniRoute:** docs-sync (പ്രതിഫലിപ്പിച്ച പതിപ്പുകൾ), docs-counts-sync (ഡോക്സിലെ സംഖ്യകളും കോഡിലെ സംഖ്യകളും), env-doc-sync, doc-links, fabricated-docs, cli-i18n, i18n-ui-coverage (`--threshold=65` + റാച്ചറ്റ് 80.1%).
- **പൊതുവായത്:** ഡോക്സിനും കോഡിനുമിടയിൽ versions/counts/env-vars സമന്വയിപ്പിക്കുക (വിശ്വാസമല്ല, ഗേറ്റ്) + ആന്തരിക ലിങ്കുകൾ സാധൂകരിക്കുക + റാച്ചറ്റ് ചെയ്ത i18n കവറേജ്.

### 11. ഭ്രമാത്മക സൃഷ്ടികൾ തടയൽ / സ്ഥിരത (അപൂർവ വിഭാഗം)

- **OmniRoute:** known-symbols (string dispatch ⇒ നിലവിലുള്ള symbol), provider-consistency, fetch-targets (client fetch ⇒ യഥാർഥ route), docs-symbols, db-rules (Hard Rules #2/#5), migration-numbering.
- **പൊതുവായത്:** ഓരോ "ഡ്യൂപ്ലിക്കേറ്റ് ചെയ്ത ഏക സത്യസ്രോതസ്സിനും" (registry, string dispatch, cross-layer references), ഇരുവശവും പൊരുത്തപ്പെടുന്നുവെന്ന് തെളിയിക്കുന്ന ഒരു ഗേറ്റ്. typecheck/test കണ്ടെത്താത്ത കാലഹരണപ്പെടൽ ഇത് കണ്ടെത്തുന്നു.

### 12. പ്രതിരോധശേഷിയും ഡൊമെയ്നും (ഉൽപ്പന്ന-നിർദ്ദിഷ്ടം)

- **OmniRoute:** chaos (fault-injection), heap-growth (leak), k6 (soak), promptfoo+garak (LLM red-team OWASP LLM Top 10), 3 resilience നിയമങ്ങൾ (circuit-breaker/cooldown/lockout).
- **പൊതുവായത്:** **നിങ്ങളുടെ** ഡൊമെയ്നിന്റെ പരാജയ സാഹചര്യങ്ങൾ തിരിച്ചറിയുകയും ഓരോന്നിനും ഒരു ഗേറ്റ് ഉണ്ടായിരിക്കുകയും ചെയ്യുക (അത് രാത്രികാലമാണെങ്കിലും). AI ആപ്പുകൾക്ക്: injection red-team. വിതരണ സംവിധാനങ്ങൾക്ക്: chaos + leak + soak.

## ഭാഗം 4 — ഏത് പ്രോജക്റ്റിനുമുള്ള പുനരാവർത്തന പദ്ധതി

ഓരോന്നും സ്വതന്ത്രമായി മൂല്യം നൽകുന്ന വിധത്തിൽ **ഘട്ടങ്ങളായി** നിർമ്മിക്കുക. 12 വിഭാഗങ്ങളും ഒരേസമയം പരീക്ഷിക്കരുത് —
അത് ഭാഗം 2 മുന്നറിയിപ്പ് നൽകുന്ന ഗേറ്റ് ക്ഷീണം തന്നെയാണ് സൃഷ്ടിക്കുന്നത്. ഓരോ പുതിയ ഗേറ്റും ആദ്യം **നിർദേശാത്മകമായി** പ്രവേശിക്കുകയും
സ്ഥിരത കൈവരിക്കുമ്പോൾ **തടയുന്നതായി** മാറുകയും വേണം.

### പുനരുപയോഗിക്കാവുന്ന കേന്ദ്രഘടകം: "ഒരു റാച്ചറ്റ് ഗേറ്റിന്റെ ഘടന"

മുഴുവൻ സിസ്റ്റവും ഈ 3-ഫയൽ മാതൃകയെ ചുറ്റിപ്പറ്റിയാണ് പ്രവർത്തിക്കുന്നത്. ആദ്യം ഇത് പകർത്തുക:

1. **`baseline.json`** — നിശ്ചലമാക്കിയ മെട്രിക് മൂല്യം + `direction` (`up`/`down`) + `eps` (അസ്ഥിരത തടയാൻ) + `tightenSlack` + `dedicatedGate`.
2. **`collect-metrics.<ext>`** — ടൂൾ പ്രവർത്തിപ്പിക്കുകയും സംഖ്യ വേർതിരിച്ചെടുക്കുകയും `metrics.json` എഴുതുകയും ചെയ്യുന്നു.
3. **`check-ratchet.<ext>`** — `metrics.json`-നെ `baseline.json`-മായി താരതമ്യം ചെയ്യുന്നു; `eps`-നപ്പുറം പിന്നോട്ടുപോയാൽ **മാത്രം** `exit 1`; ടൂൾ/ഇൻഫ്രാസ്ട്രക്ചർ ലഭ്യമല്ലെങ്കിൽ `exit 0` (തടസ്സമില്ലാതെ ഒഴിവാക്കൽ); `--require-tighten` ഉപയോഗിക്കുമ്പോൾ, ബേസ്ലൈൻ പുതുക്കാതെ അത് **മെച്ചപ്പെട്ടാൽ** `exit 1` (നേട്ടം സ്ഥിരപ്പെടുത്തുന്നു).

ഇത് സജ്ജമായാൽ, **ഓരോ** പുതിയ മെട്രിക്കും (കവറേജ്, സങ്കീർണ്ണത, മുന്നറിയിപ്പുകൾ, SAST അലേർട്ടുകൾ, ബണ്ടിൽ വലുപ്പം, മ്യൂട്ടേഷൻ സ്കോർ…) ബേസ്ലൈനിലെ ഒരു വരി മാത്രമാണ്.

### ഘട്ടം 0 — അടിത്തറ (ആഴ്ച 1)

CI നിലവിലുണ്ട്; ഫോർമാറ്റർ + ലിന്റർ + ടൈപ്പ് ചെക്ക് + 1 ടെസ്റ്റ് റണ്ണർ + **കേവല** കവറേജ് പരിധി
(ഉദാ., 60%). പ്രീ-കമ്മിറ്റ് വേഗത്തിൽ പ്രവർത്തിക്കുന്ന, സ്വയമേവ പരിഹരിക്കാവുന്ന പരിശോധനകൾ നടത്തുന്നു. _ഫലം: ഒരു PR-ഉം അടിസ്ഥാന കാര്യങ്ങൾ തകർക്കില്ല._

### ഘട്ടം 1 — റാച്ചറ്റ് എൻജിൻ (ആഴ്ച 2) — **എല്ലാറ്റിന്റെയും അടിത്തറ**

മുകളിലെ 3 ഫയലുകൾ നടപ്പിലാക്കുക. ഇവയ്ക്കുള്ള ബേസ്ലൈനുകൾ നിശ്ചലമാക്കുക: മുന്നറിയിപ്പുകൾ, കവറേജ്, സങ്കീർണ്ണത, ആവർത്തനം,
നിർജ്ജീവ കോഡ്, ഫയൽ വലുപ്പം. _ഫലം: ഇനി മുതൽ കോഡ്ബേസിന് മെച്ചപ്പെടാൻ മാത്രമേ കഴിയൂ._

### ഘട്ടം 2 — സ്റ്റാറ്റിക് ആഴം (ആഴ്ച 3)

അലേർട്ട് റാച്ചറ്റോടെയുള്ള SAST (CodeQL/Sonar/semgrep); സീക്രെറ്റ്സ് സ്കാനർ (**ഡിഫോൾട്ട് റൂൾസെറ്റ് പാരമ്പര്യമായി സ്വീകരിക്കുക**);
SCA (osv/Dependabot) + ലൈസൻസ് അനുവദനീയ പട്ടിക + lockfile-lint. _ഫലം: അറിയപ്പെടുന്ന ദുർബലതകളും
ചോർന്ന സീക്രെറ്റുകളും കടന്നുപോകില്ല._

### ഘട്ടം 3 — ബിൽഡ് സപ്ലൈ ചെയിൻ (ആഴ്ച 4)

പ്രസിദ്ധീകരിക്കുമ്പോൾ SBOM + ഒപ്പിട്ട ഉറവിടസാക്ഷ്യം (SLSA L2) + ഷെഡ്യൂൾ ചെയ്ത Scorecard + വർക്ക്ഫ്ലോ ശക്തിപ്പെടുത്തൽ
(zizmor: ഏറ്റവും കുറഞ്ഞ ടോക്കണുകൾ, സ്ഥിരമായി സൂക്ഷിക്കുന്ന ക്രെഡൻഷ്യലുകൾ ഇല്ല, പിൻ ചെയ്ത ആക്ഷനുകൾ). _ഫലം: പിന്തുടരാവുന്നതും
കൃത്രിമമായി മാറ്റാനാകാത്തതുമായ റിലീസുകൾ._

### ഘട്ടം 4 — ടെസ്റ്റ് തീവ്രത (ആഴ്ച 5–6)

പ്രയോജനകരമാണെങ്കിൽ രണ്ടാമത്തെ റണ്ണർ; **നിർണായക മൊഡ്യൂളുകൾക്കായി ഓരോ മൊഡ്യൂളിനും പ്രത്യേകം കവറേജ് പരിധികൾ** (ആന്റി-Goodhart);
ശുദ്ധ ലോജിക്കിനായി പ്രോപ്പർട്ടി അധിഷ്ഠിത ടെസ്റ്റിംഗ്; **രാത്രിതോറും മ്യൂട്ടേഷൻ ടെസ്റ്റിംഗ്** → ആദ്യ സ്കോർ ലഭിക്കുമ്പോൾ,
`mutationScore`-നെ ഒരു റാച്ചറ്റാക്കുക. _ഫലം: കവറേജ് ഒരു പ്രദർശന മെട്രിക് മാത്രമല്ലാതാകുന്നു; ടെസ്റ്റുകൾ യഥാർത്ഥത്തിൽ ബഗുകൾ കണ്ടെത്തുന്നുവെന്ന് തെളിയുന്നു._

### ഘട്ടം 5 — കരാറും ഡൈനാമിക് പരിശോധനയും (ആഴ്ച 7)

പൊതു API ഉണ്ടെങ്കിൽ: oasdiff (ബ്രേക്കിംഗ്-ചേഞ്ച്, **തടയുന്നത്**) + schemathesis (രാത്രിതോറുമുള്ള ഫസിംഗ്).
ഡൊമെയ്നിന് അനുയോജ്യമായി രാത്രിതോറും DAST/റെഡ്-ടീം പരിശോധന. _ഫലം: കരാറുകൾ നിശ്ശബ്ദമായി തകരില്ല._

### ഘട്ടം 6 — ആന്റി-ഹാലുസിനേഷനും ഡൊമെയ്നും (ആഴ്ച 8)

പ്രോജക്റ്റിലെ ഓരോ "ആവർത്തിച്ച സത്യത്തിനും" ഒരു സ്ഥിരതാ ഗേറ്റ്. ഡൊമെയ്ൻ-നിർദ്ദിഷ്ട പരാജയ-രീതി
ഗേറ്റുകൾ (AI-യ്ക്കായി: ഇൻജക്ഷൻ റെഡ്-ടീം). _ഫലം: ഘടനാപരമായ ജീർണ്ണതയ്ക്കും ഡൊമെയ്ൻ പരാജയങ്ങൾക്കും ഒരു സുരക്ഷാവലയമുണ്ടാകും._

### ഘട്ടം 7 — ഭരണനിർവഹണം (തുടർച്ചയായി)

- ഓരോ പുതിയ ഗേറ്റിനും നിർദേശാത്മകം→തടയുന്നത് എന്ന ചക്രം.
- `stale-allowlist`: ഓരോ ഒഴിവാക്കലിനും ഒരു ന്യായീകരണം + ഇഷ്യൂ ഉണ്ടായിരിക്കണം; കാലഹരണപ്പെട്ട ഒഴിവാക്കൽ കണ്ടെത്തപ്പെടുന്നു.
- `evidence-gate`: ഒരു PR-ലെ വിജയവാദത്തിന് തെളിവ് ആവശ്യമാണ് (ടെസ്റ്റ് അല്ലെങ്കിൽ നിരന്തരം പരിപാലിക്കുന്ന ടെസ്റ്റ്).
- **ഓരോ ഗേറ്റിനും ത്രൈമാസ ROI അവലോകനം** (മൂല്യം തിരികെ നൽകാത്തവ ഒഴിവാക്കുക/ധനസഹായം നിർത്തുക — ഇത് ക്ഷീണം ചെറുക്കുന്നു).
- നിങ്ങളുടെ പ്രോജക്റ്റിന്റെ കർശന നിയമങ്ങളെ എക്സിക്യൂട്ടബിൾ ഗേറ്റുകളായി ഉയർത്തുക.

### എല്ലായിടത്തും ബാധകമായ തത്വങ്ങൾ (വിട്ടുവീഴ്ചയില്ലാത്തവ)

- **കേവല പരിധിയല്ല, റാച്ചറ്റ്.** ഒരു നിശ്ചിത സംഖ്യയല്ല, _പിന്നോട്ടുപോകാതിരിക്കലാണ്_ ഗേറ്റ് ചെയ്യേണ്ടത് (പൂജ്യം തടയുന്ന പരിധികൾ ഒഴികെ).
- **കേവല പരിധിയും റാച്ചറ്റും ഒരുമിച്ച്.** പരിധി തകർച്ച തടയുന്നു; റാച്ചറ്റ് ക്രമാനുഗതമായ ശോഷണം തടയുന്നു.
- **രൂപകൽപ്പനയിൽ തന്നെ ആന്റി-Goodhart.** ഓരോ ലക്ഷ്യ മെട്രിക്കിനും ഒരു പ്രതിതുലനം ആവശ്യമാണ് (കവറേജ് ⇒ മ്യൂട്ടേഷൻ + മറച്ചുവെക്കൽ തടയൽ; പ്രയാസമുള്ള കോഡ് നിർബന്ധമായി ടെസ്റ്റ് ചെയ്യിക്കാൻ ഓരോ മൊഡ്യൂളിനും പ്രത്യേക പരിധികൾ).
- **തടസ്സമില്ലാതെ ഒഴിവാക്കൽ.** ലഭ്യമല്ലാത്ത ഇൻഫ്രാസ്ട്രക്ചർ ഒരിക്കലും തടയില്ല; യഥാർത്ഥ പിന്നോട്ടുപോക്ക് മാത്രമേ തടയൂ.
- **ചെലവേറിയ മെട്രിക്കുകൾക്ക് `dedicatedGate`.** ഒരു ബാഹ്യ ബൈനറി ആവശ്യമായ മെട്രിക്കുകൾക്ക്, സമകാലിക കേന്ദ്ര റാച്ചറ്റിന് പുറത്തായി, ഒഴിവാക്കൽ പിന്തുണയുള്ള സ്വന്തം സ്ക്രിപ്റ്റ് നൽകുക.
- **ലയനം നടക്കുന്നിടത്ത് ഗേറ്റ് ചെയ്യുക.** വേഗത്തിലുള്ള ഗേറ്റിനും യഥാർത്ഥ ലയനത്തിനും ഇടയിൽ വിടവ് അവശേഷിപ്പിക്കരുത് (ഫാസ്റ്റ്-ഗേറ്റ്സ് വിഭജനത്തിൽനിന്നുള്ള പാഠം).
- **നന്നായി തിരഞ്ഞെടുത്ത കുറച്ച് തടയുന്ന ഗേറ്റുകൾ.** Sonar/DORA: അമിതമായ വ്യവസ്ഥകൾ = ക്ഷീണം. തടയുന്ന ഗേറ്റുകളുടെ മതിലിനേക്കാൾ നിർദേശാത്മക ഗേറ്റുകളും റാച്ചറ്റും മുൻഗണിക്കുക.

## ഭാഗം 5 — ശുപാർശ ചെയ്യുന്ന മെച്ചപ്പെടുത്തലുകൾ (മുൻഗണനാക്രമത്തിൽ, അനുയോജ്യമായവ)

**P0 — ഏറ്റവും ഉയർന്ന ROI, ഏതാണ്ട് തയ്യാറാണ്**

1. **മ്യൂട്ടേഷൻ സ്കോർ റാച്ചറ്റ്** (ആദ്യ nightly Stryker മൂല്യങ്ങൾ സൃഷ്ടിച്ചതിന് ശേഷം). coverage-Goodhart-നെതിരായ പ്രധാന പ്രതിവിധി; ~90% പൂർത്തിയായി.
2. **ശേഷിക്കുന്ന fast-gates വിടവ് അടയ്ക്കുക** — `quality.yml`-ലെ production build-ന്റെ
   advisory week കഴിഞ്ഞാൽ അതിനെ നിർബന്ധിതമാക്കുകയും, നിർണായകമായ release-PR-only പരിശോധനകൾ PR→release പാതയിലേക്ക് മാറ്റുന്നത് തുടരുകയും ചെയ്യുക.
3. **`main`-ൽ branch-protection** (ഉടമയുടെ ക്രമീകരണം) — Scorecard ഉയർത്തുകയും DSOMM വിടവ് അടയ്ക്കുകയും ചെയ്യുന്നു.

**P1 — മൂല്യമുള്ളത്** 4. **osv/oasdiff → ശരിയായ scope-ോടെ blocking** — osv-യിൽ CRITICAL+fixable മാത്രം (Trivy പോലെ രണ്ട് ഘട്ടമായി); breaking-changes ഉണ്ടെങ്കിൽ oasdiff തടയും. 5. **`require-tighten` → blocking** (സൈക്കിളിന്റെ അവസാനം) — മെട്രിക് നേട്ടങ്ങൾ സ്ഥിരപ്പെടുത്തുന്നു. 6. **`ci-summary`-യിൽ ഓരോ gate-നും ROI/timing അവലോകനം** — വേഗം കുറഞ്ഞതോ കുറഞ്ഞ മൂല്യമുള്ളതോ ആയ gates കണ്ടെത്തി ഒഴിവാക്കുക.

**P2 — ക്രമേണ കുറയുന്ന നേട്ടങ്ങൾ** 7. **SLSA L3** — L2-ൽ നിന്ന് മുന്നേറാൻ ആഗ്രഹിക്കുന്നുവെങ്കിൽ hermetic/reproducible builder (GitHub SLSA generator). 8. **Committed CodeQL config + versioned semgrep** — കൂടുതൽ നിയന്ത്രണവും പുനരുത്പാദനക്ഷമതയും. 9. **ഓരോ PR-നും DAST smoke** — ഏറ്റവും ഉയർന്ന അപകടസാധ്യതയുള്ള endpoints-ൽ schemathesis/promptfoo-യുടെ വേഗത്തിലുള്ള subset (nightly-ൽ മാത്രം അല്ല). 10. **Flakiness dashboard + DORA metrics** — gates വേഗത കുറയ്ക്കുന്നില്ലെന്ന് ഉറപ്പാക്കുക.

## ഭാഗം 6 — വ്യക്തമായ release പാഠങ്ങൾ (Phase 9-ൽ ചേർക്കേണ്ട gates)

> release closure-ുകളിൽ ഒരു gate **ഇല്ലാതിരുന്ന** യഥാർത്ഥ സംഭവങ്ങൾ,
> വ്യക്തമായ തെളിവുകളും നിർദേശിച്ച gate-ഉം സഹിതം ഈ വിഭാഗം രേഖപ്പെടുത്തുന്നു. ഓരോ ഇനവും ഭാഗം 5-ലേക്കുള്ള സ്ഥാനാർഥിയാണ്.

### പാഠം v3.8.27 (2026-06-17) — "fast-gates വിടവ്" നിർണായക regressions release ദിവസത്തിലെത്താൻ അനുവദിക്കുന്നു

**എന്താണ് സംഭവിച്ചത്.** v3.8.27 `/generate-release` സമയത്ത്, സംയോജിത സൈക്കിളിലെ സമ്പൂർണ്ണ `ci.yml` matrix-ന്റെ
**ആദ്യ** നിർവഹണം release PR (`release/v3.8.27` → `main`) ആയിരുന്നു. ഫലം: ഒരേസമയം 12 failures
— **3 നിർണായക tests** + ~9 flakes/env. ഇവയൊന്നും സജീവ product regressions ആയിരുന്നില്ല, എന്നാൽ
cycle PR-കൾ **Fast QG
(`quality.yml`)** വഴി `release/**`-ലേക്ക് പ്രവേശിക്കുന്നതിനാൽ അവയെല്ലാം ശ്രദ്ധിക്കപ്പെടാതെ പോയി. ഇത് സമ്പൂർണ്ണ unit suite-ഓ `pr-test-policy`-യോ (test-masking), സമ്പൂർണ്ണ integration suite-ഓ, schema parity checking-ഓ പ്രവർത്തിപ്പിക്കുന്നില്ല. നിർണായകമായ 3 എണ്ണം:

1. **UI മാറ്റം മൂലം കാലഹരണപ്പെട്ട test** — `permissions modal switch buttons declare button type`:
   #4034 നാലാമത്തെ switch ചേർത്തു (a11y `type="button"` നിലനിർത്തി); test-ലെ `=== 3` എണ്ണം
   കാലഹരണപ്പെട്ടു. #4034 PR-ൽ static analysis ഇത് കണ്ടെത്തേണ്ടതായിരുന്നു.
2. **Packaging മാറ്റം മൂലം കാലഹരണപ്പെട്ട test** — `findMissingArtifactPaths ... root runtime files`:
   `dist/http-method-guard.cjs` നിയമാനുസൃതമായ ഒരു required-path ആയി; test-ന്റെ expected list
   കാലഹരണപ്പെട്ടു.
3. **നഷ്ടകരമായ modularization divergence (ഏറ്റവും ഗുരുതരം)** — `settings schemas accept ... unprefixed
toggle`: **modularized** `updateSettingsSchema` (`schemas/settings.ts`, #3988 സൃഷ്ടിച്ചത്) canonical പതിപ്പിൽ നിന്ന് (`settingsSchemas.ts`) വ്യതിചലിച്ചു: **45 fields vs 85 — 40 ഒഴിവാക്കി + 6 വ്യത്യസ്തമായി (qdrant\*)**. അത്
   **dead-code** ആയിരുന്നു (runtime canonical പതിപ്പാണ് ഉപയോഗിക്കുന്നത്), അതിനാൽ സജീവമായ ആഘാതമൊന്നുമുണ്ടായില്ല; എന്നാൽ കൈകൊണ്ട് എഴുതിയ parity
   test മാത്രമാണ് ഇത് കണ്ടെത്തിയത്. #3988/#3993-ൽ ഉണ്ടായ സമാനമായ 16 ഒഴിവാക്കലുകൾ #4030 പുനഃസ്ഥാപിച്ചെങ്കിലും ഇത് ശ്രദ്ധയിൽപ്പെടാതെ പോയി.

**നിർദേശിച്ച gates (Phase 9):**

- **G1 — fast-gates വിടവ് യഥാർത്ഥത്തിൽ അടയ്ക്കുക (P0 #2 വിപുലീകരിക്കുന്നു).** `quality.yml`-ൽ (PR→`release/**`),
  typecheck + impacted tests എന്നിവയ്ക്കു പുറമേ, **`pr-test-policy` (test-masking) + സമ്പൂർണ്ണ deterministic
  unit suite** പ്രവർത്തിപ്പിക്കുക (അല്ലെങ്കിൽ കുറഞ്ഞത് വേഗമുള്ളതും flakiness ഇല്ലാത്തതുമായ static/parity files എങ്കിലും).
  ഈ രീതിയിൽ, കാലഹരണപ്പെട്ട tests-ഉം assert നീക്കംചെയ്യലും അവ അവതരിപ്പിക്കുന്ന PR-ൽത്തന്നെ കണ്ടെത്തപ്പെടും — release
  ദിവസം അല്ല. integration/e2e ഉൾപ്പെടുത്താതിരിക്കുക (വേഗം കുറഞ്ഞത്/flaky), എന്നാൽ deterministic layer PR→main-ൽ
  മാത്രം തുടരാൻ പാടില്ല.
- **G2 — Modularization parity gate (പുതിയത്, നിലവിൽ ഉൾപ്പെടുത്തിയിട്ടില്ല).** modularized barrel (`src/shared/validation/schemas/*`, `providerRegistry`
  modules മുതലായവ) വീണ്ടും export ചെയ്യുന്ന ഓരോ symbol-ന്റെയും **shape** (`z.object` keys, registry entries) canonical
  source-മായി താരതമ്യം ചെയ്യുകയും **divergence ഉണ്ടായാൽ പരാജയപ്പെടുകയും** ചെയ്യുന്ന ഒരു പരിശോധന (ഒഴിവാക്കിയ/അധിക field). #3988-ലെ
  40-field ഒഴിവാക്കൽ അതേ PR-ൽത്തന്നെ ഇത് കണ്ടെത്തുമായിരുന്നു. കൈകൊണ്ട് എഴുതിയ parity tests-നെ ഇത് പൊതുവൽക്കരിക്കുന്നു (അവ എഴുതാൻ ആരെങ്കിലും
  ഓർത്തിടങ്ങളിൽ മാത്രമാണ് ഇപ്പോൾ അവയുള്ളത്). ചെലവ് കുറവാണ്: രണ്ടും import ചെയ്ത് `Object.keys(shape)` diff ചെയ്യുന്നു.
- **G3 — Deterministic flake triage (പിന്തുണ).** CI-യിൽ (env) server timeout/cascade കാരണം LiveWS-startup-ഉം integration-combo/breaker
  tests-ഉം പരാജയപ്പെടുന്നു; logic കാരണമല്ല. ഇവയെ `known-flaky` ആയി അടയാളപ്പെടുത്തുക (issue സഹിതം quarantine ചെയ്യുക), അങ്ങനെ release-PR-ലെ ചുവപ്പ്
  **യഥാർത്ഥ signals മാത്രം** ആയിരിക്കും; ഇടയിൽ deterministic regressions മറച്ചുവയ്ക്കുന്ന noise ആയിരിക്കില്ല.

**തത്ത്വം:** _merge നടക്കുന്നിടത്ത് gate പ്രവർത്തിക്കണം_ ("Cross-cutting principles"-ൽ ഇതിനകം ഉൾപ്പെടുത്തിയിട്ടുണ്ട്). ഇത് lint/typecheck-ന് മാത്രമല്ല,
**deterministic test layer**-നും ബാധകമാണെന്ന് v3.8.27 സംഭവം കാണിക്കുന്നു —
അല്ലാത്തപക്ഷം കാലഹരണപ്പെട്ട tests + നഷ്ടകരമായ modularization എന്നിവയുടെ debt, ഏറ്റവും മോശമായ സമയത്ത്,
PR→main-ൽ കൂട്ടമായിട്ടാണ് പ്രത്യക്ഷപ്പെടുക.
