**സ്രോതസ്സുകൾ:**

- `src/lib/db/usage*.ts` — ഉപയോഗവുമായി ബന്ധപ്പെട്ട ഒന്നിലധികം DB മൊഡ്യൂളുകൾ

## അവലോകനം

OmniRoute-ലൂടെ കടന്നുപോകുന്ന ഓരോ അഭ്യർത്ഥനയും ഇനിപ്പറയുന്ന വിവരങ്ങൾ രേഖപ്പെടുത്തുന്ന ഒരു **ഉപയോഗ റെക്കോർഡ്** സൃഷ്ടിക്കുന്നു:

- **ഐഡന്റിറ്റി**: ഏത് API കീ, പ്രൊവൈഡർ, മോഡൽ, കോംബോ
- **ടോക്കണുകൾ**: പ്രോംപ്റ്റ് ടോക്കണുകൾ, കംപ്ലീഷൻ ടോക്കണുകൾ, കാഷ് ചെയ്ത ടോക്കണുകൾ, ആകെ
- **ചെലവ്**: USD തുക (വിലനിർണ്ണയ ഡാറ്റയിൽ നിന്ന് കണക്കാക്കിയത്)
- **സമയവിവരങ്ങൾ**: ലേറ്റൻസി, ആരംഭ/അവസാന ടൈംസ്റ്റാമ്പുകൾ
- **സ്റ്റാറ്റസ്**: വിജയം, പിശക്, നിരക്ക്-പരിമിതപ്പെടുത്തിയത് തുടങ്ങിയവ

ഈ റെക്കോർഡുകൾ **അനലിറ്റിക്സ്** ആയി സമാഹരിക്കുകയും, **ക്വാട്ട സ്നാപ്പ്ഷോട്ടുകൾ** ആയി സ്ഥിരമായി സംഭരിക്കുകയും, **ഓരോ കീയുടെയും ബജറ്റ് പരിധികൾ** നടപ്പിലാക്കാൻ ഉപയോഗിക്കുകയും ചെയ്യുന്നു.

```
അഭ്യർത്ഥന ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    അനലിറ്റിക്സ്  ക്വാട്ട  ബില്ലിംഗ്
                    (ഡാഷ്ബോർഡ്) (നടപ്പാക്കൽ) (എക്സ്പോർട്ട്)
```

## രേഖപ്പെടുത്തുന്ന വിവരങ്ങൾ

ഓരോ അഭ്യർത്ഥനയ്ക്കും `usage.ts` സേവനം ഒരു **ഉപയോഗ ഇവന്റ്** രേഖപ്പെടുത്തുന്നു:

| ഫീൽഡ്              | തരം     | ഉറവിടം                                                          |
| ------------------ | ------- | --------------------------------------------------------------- |
| `id`               | string  | രേഖപ്പെടുത്തുമ്പോൾ സൃഷ്ടിക്കുന്ന UUID                           |
| `apiKeyId`         | string  | അഭ്യർത്ഥന ആരംഭിച്ച API കീ                                       |
| `provider`         | string  | പ്രൊവൈഡർ ID (openai, anthropic തുടങ്ങിയവ)                       |
| `model`            | string  | മോഡൽ ID (gpt-5, claude-opus-4-6 തുടങ്ങിയവ)                      |
| `comboId`          | string? | കോംബോയിലൂടെ റൂട്ട് ചെയ്തിട്ടുണ്ടെങ്കിൽ കോംബോ ID                 |
| `promptTokens`     | number  | അപ്സ്ട്രീം റെസ്പോൺസിൽ നിന്ന്                                    |
| `completionTokens` | number  | അപ്സ്ട്രീം റെസ്പോൺസിൽ നിന്ന്                                    |
| `cachedTokens`     | number  | കാഷ് ഹിറ്റ് ടോക്കണുകൾ (Anthropic പ്രോംപ്റ്റ് കാഷിംഗ് തുടങ്ങിയവ) |
| `totalTokens`      | number  | പ്രോംപ്റ്റ് + കംപ്ലീഷൻ                                          |
| `costUsd`          | number  | വിലനിർണ്ണയ ഡാറ്റയിൽ നിന്ന് കണക്കാക്കിയത്                        |
| `latencyMs`        | number  | അഭ്യർത്ഥനയുടെ തുടക്കം മുതൽ അവസാനം വരെയുള്ള ദൈർഘ്യം              |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`      |
| `errorClass`       | string? | സ്റ്റാറ്റസ് `success` അല്ലെങ്കിൽ പിശകിന്റെ ക്ലാസ്               |
| `timestamp`        | string  | ISO 8601 UTC                                                    |
| `metadata`         | object  | പ്ലഗിൻ ഉൾപ്പെടുത്തിയ ഇഷ്ടാനുസൃത ഡാറ്റ                           |

### ടോക്കണുകൾ എവിടെനിന്ന് ലഭിക്കുന്നു

**റെസ്പോൺസ് ഹാൻഡ്ലറിൽ**, അപ്സ്ട്രീം പ്രൊവൈഡറുടെ റെസ്പോൺസിൽ നിന്നാണ് ടോക്കണുകൾ വേർതിരിച്ചെടുക്കുന്നത്:

```ts
// open-sse/handlers/chatCore.ts-ൽ നിന്ന്
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

ഉപയോഗവിവരങ്ങൾ തിരികെ നൽകാത്ത പ്രൊവൈഡറുകൾക്കായി (ചില വെബ്-കുക്കി പ്രൊവൈഡറുകൾ), OmniRoute `ഒരു ടോക്കണിന് ~4 പ്രതീകങ്ങൾ` എന്ന ഏകദേശ കണക്കാക്കൽ രീതി ഉപയോഗിച്ച് ടോക്കണുകൾ **കണക്കാക്കുന്നു** (`open-sse/services/autoCombo/pipelineRouter.ts` കാണുക).

### കാഷ് ചെയ്ത ടോക്കണുകൾ

OmniRoute `cached_tokens`-നെ `prompt_tokens`-ൽ നിന്ന് വേർതിരിച്ച് ട്രാക്ക് ചെയ്യുന്നു, കാരണം:

- കാഷ് ചെയ്ത ടോക്കണുകൾക്ക് Anthropic പ്രോംപ്റ്റ് കാഷിംഗ് കുറഞ്ഞ നിരക്ക് ഈടാക്കുന്നു (സാധാരണ നിരക്കിന്റെ 10%)
- ചില പ്രൊവൈഡറുകൾ വ്യത്യസ്തമായി വില നിശ്ചയിക്കേണ്ട `cache_read_input_tokens` തിരികെ നൽകുന്നു
- അനലിറ്റിക്സിന് **കാഷ് ഹിറ്റ് നിരക്ക്** = `cached_tokens / prompt_tokens` കാണിക്കാനാകും

## ചെലവ് കണക്കാക്കൽ

LiteLLM-ൽ നിന്ന് സമന്വയിപ്പിച്ച **വിലനിർണ്ണയ ഡാറ്റ** (`src/lib/pricingSync.ts`) ഉപയോഗിച്ചാണ് ചെലവുകൾ കണക്കാക്കുന്നത്:

| മോഡൽ              | ഇൻപുട്ട് $/1M | ഔട്ട്പുട്ട് $/1M | കാഷ് ചെയ്തത് $/1M |
| ----------------- | ------------- | ---------------- | ----------------- |
| gpt-5             | $2.50         | $10.00           | —                 |
| claude-opus-4-6   | $15.00        | $75.00           | $1.50             |
| claude-sonnet-4-5 | $3.00         | $15.00           | $0.30             |
| gemini-2.5-pro    | $1.25         | $10.00           | —                 |

ചെലവ് കണക്കാക്കുന്നതിനുള്ള സൂത്രവാക്യം (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **പ്രോംപ്റ്റിൽ നിന്ന് കാഷ് ചെയ്ത ഭാഗം കുറയ്ക്കുന്നത് എന്തുകൊണ്ട്?** കാഷ് ചെയ്ത ഭാഗത്തിന് പ്രത്യേകം വില നിശ്ചയിച്ചിരിക്കുന്നതിനാൽ, മുഴുവൻ പ്രോംപ്റ്റിനും ഇൻപുട്ട് വില ഈടാക്കുന്നത് ചെലവ് അധികമായി കണക്കാക്കാൻ ഇടയാക്കും.

### വിലനിർണ്ണയ സമന്വയം

ബിൽറ്റ്-ഇൻ cron ടാസ്ക് പ്രവർത്തനക്ഷമമാക്കുന്ന `/api/pricing/sync` എൻഡ്പോയിന്റ് വഴി LiteLLM-ൽ നിന്ന് വിലനിർണ്ണയ ഡാറ്റ സ്വയമേവ സമന്വയിപ്പിക്കുന്നു (ഉപയോക്താവിന് ലഭ്യമായ env var വഴിയല്ല):

```bash
# മാനുവൽ ട്രിഗർ
curl -X POST http://localhost:20128/api/pricing/sync
```

വിലനിർണ്ണയ ഡാറ്റയില്ലാത്ത മോഡലുകൾക്കായി, ആന്തരിക ശരാശരി നിരക്കുകൾ ഉപയോഗിച്ച് (LiteLLM-ന്റെ വിലനിർണ്ണയ ഡാറ്റയിൽ നിന്ന് ലഭിച്ചത്) OmniRoute **ചെലവ് കണക്കാക്കുന്നു**.

## തീയതി പരിധി അഗ്രിഗേഷൻ

അസംസ്കൃത ഉപയോഗ ഡാറ്റയിൽ നിന്ന് ഡാഷ്ബോർഡ് വിജറ്റുകൾ `usageAnalytics.ts` മൊഡ്യൂൾ കണക്കാക്കുന്നു. ഇത് 7 സമയപരിധികളെ പിന്തുണയ്ക്കുന്നു:

| പരിധി    | സമയജാലകം                          | ഉപയോഗസാഹചര്യം                                   |
| -------- | --------------------------------- | ----------------------------------------------- |
| `1d`     | കഴിഞ്ഞ 24 മണിക്കൂർ                | മണിക്കൂർ അടിസ്ഥാനത്തിലുള്ള ചെലവ് വർധന കണ്ടെത്തൽ |
| `7d`     | കഴിഞ്ഞ 7 ദിവസം                    | പ്രതിവാര അവലോകനം                                |
| `30d`    | കഴിഞ്ഞ 30 ദിവസം                   | പ്രതിമാസ ബില്ലിംഗ്                              |
| `90d`    | കഴിഞ്ഞ 90 ദിവസം                   | ത്രൈമാസ വിശകലനം                                 |
| `ytd`    | നിലവിലെ വർഷത്തിലെ Jan 1 മുതൽ      | വാർഷിക ബജറ്റ് നിരീക്ഷണം                         |
| `all`    | എല്ലാ കാലയളവും                    | ആജീവനാന്ത സ്ഥിതിവിവരക്കണക്കുകൾ                  |
| `custom` | ഉപയോക്താവ് നിർവചിച്ച ആരംഭം/അവസാനം | ഓഡിറ്റുകൾ, തത്സമയ ആവശ്യത്തിനുള്ള അന്വേഷണങ്ങൾ    |

### കണക്കാക്കുന്ന ഡാഷ്ബോർഡ് വിജറ്റുകൾ

ഏത് തീയതി പരിധിക്കും അനലിറ്റിക്സ് ലെയർ ഇനിപ്പറയുന്നവ കണക്കാക്കുന്നു:

| വിജറ്റ്                      | വിവരണം                                                                   |
| ---------------------------- | ------------------------------------------------------------------------ |
| **സംഗ്രഹ കാർഡുകൾ**           | ആകെ അഭ്യർത്ഥനകൾ, ആകെ ചെലവ്, ആകെ ടോക്കണുകൾ, വിജയനിരക്ക്                   |
| **പ്രതിദിന ട്രെൻഡ് ചാർട്ട്** | മോഡൽ അനുസരിച്ച് സ്റ്റാക്ക് ചെയ്ത പ്രതിദിന ചെലവും ടോക്കണുകളും             |
| **പ്രവർത്തന ഹീറ്റ്മാപ്പ്**   | ദിവസത്തിലെ മണിക്കൂർ × ആഴ്ചയിലെ ദിവസം ഗ്രിഡ്, നിറം = അഭ്യർത്ഥനകളുടെ എണ്ണം |
| **മോഡൽ വിഭജനം**              | മോഡൽ അനുസരിച്ചുള്ള ചെലവിന്റെ പൈ ചാർട്ട്                                  |
| **പ്രൊവൈഡർ വിഭജനം**          | പ്രൊവൈഡർ അനുസരിച്ചുള്ള അഭ്യർത്ഥനകളുടെ ബാർ ചാർട്ട്                        |
| **മുൻനിര API കീകൾ**          | ചെലവ് അനുസരിച്ചുള്ള മുൻനിര 10 കീകളുടെ പട്ടിക                             |
| **പിശക് വിശകലനം**            | കാലക്രമത്തിലുള്ള പിശക് നിരക്ക്, മുൻനിര പിശക് ക്ലാസുകൾ                    |

### പ്രോഗ്രാമാറ്റിക് ആക്സസ്

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // ഉപയോഗ ചരിത്ര റെക്കോർഡുകൾ

    endDate: "2025-06-01",   // ഐച്ഛികം: "custom" പരിധിക്കായി
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (സെന്റുകൾ)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## ക്വോട്ട നടപ്പാക്കൽ

ഓരോ API കീയുടെയും ക്വോട്ട രണ്ട് സ്ഥലങ്ങളിൽ നടപ്പാക്കുന്നു:

1. **സോഫ്റ്റ് പരിധി** (`quotaWarnAt`): ഉപയോഗം പരിധി കവിയുമ്പോൾ ഡാഷ്ബോർഡ് മുന്നറിയിപ്പ്
2. **ഹാർഡ് പരിധി** (`quotaLimit`): പരിധി കവിയുമ്പോൾ അഭ്യർത്ഥന HTTP 429 ഉപയോഗിച്ച് നിരസിക്കുന്നു

### കോൺഫിഗറേഷൻ

```ts
// ഓരോ API കീയ്ക്കും
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — മുന്നറിയിപ്പ് കാണിക്കുക
  quotaLimit: 10_00,    // $10.00 — പൂർണ്ണമായി നിർത്തുക
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### നടപ്പാക്കൽ പ്രവാഹം

```
അഭ്യർത്ഥന ──▶ quotaCheck()
                 │
                 ├── പരിധിക്കുള്ളിലാണോ?  ──▶ അനുവദിക്കുക
                 │
                 └── പരിധി കവിഞ്ഞോ?  ──▶ 429 വളരെയധികം അഭ്യർത്ഥനകൾ
                                          Retry-After ഹെഡറിനൊപ്പം
```

### ക്വോട്ട സ്നാപ്പ്ഷോട്ടുകൾ

ട്രെൻഡ് വിശകലനത്തിനായി `quotaSnapshots` പട്ടിക **ചരിത്രപരമായ ക്വോട്ട നില** സംഭരിക്കുന്നു:

| ഫീൽഡ് | വിവരണം |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | ട്രാക്ക് ചെയ്യുന്ന കീ |
| `window` | "day" | "week" | "month" |
| `used` | ഈ വിൻഡോയിൽ ഉപയോഗിച്ച ചെലവ് (സെന്റിൽ) |
| `limit` | പരിധി (സെന്റിൽ) |
| `resetAt` | വിൻഡോ പുനഃസജ്ജമാകുന്ന സമയം |
| `createdAt` | സ്നാപ്പ്ഷോട്ട് എടുത്ത സമയം |

> 0 ചെലവ് ഉപയോഗിക്കുന്ന **ഓരോ അഭ്യർത്ഥനയിലും** സ്നാപ്പ്ഷോട്ടുകൾ എടുക്കുന്നു; അവ ഇനിപ്പറയുന്നവയ്ക്കായി ഉപയോഗിക്കുന്നു:

- ഡാഷ്ബോർഡിൽ ക്വോട്ട പുരോഗതി ബാർ റെൻഡർ ചെയ്യാൻ
- 30 ദിവസത്തെ ക്വോട്ട ട്രെൻഡ് ചാർട്ടുകൾ കാണിക്കാൻ
- ഉപയോഗം പരിധിയോട് അടുക്കുമ്പോൾ അലേർട്ടുകൾ ട്രിഗർ ചെയ്യാൻ

## നിലനിർത്തലും ശുചീകരണവും

ഓരോ അഭ്യർത്ഥനയ്ക്കും ഉപയോഗ ഡാറ്റ ~1-10KB വീതം വർധിക്കുന്നു. വലിയ തോതിൽ ഇത് ഗണ്യമായേക്കാം.

### നിലനിർത്തൽ ക്രമീകരണങ്ങൾ

UI-യിലെ Database Settings വഴിയോ `/api/settings/database` വഴിയോ ഉപയോഗ ചരിത്രത്തിന്റെ നിലനിർത്തൽ ക്രമീകരിക്കാം.

സ്ഥിരസ്ഥിതിയായി, ഉപയോഗ ചരിത്രം **90 ദിവസം** നിലനിർത്തുന്നു.

### ശുചീകരണം

പഴയ രേഖകൾ `src/lib/db/cleanup.ts` ഉപയോഗിച്ച് ശുചീകരിക്കുന്നു:

- പശ്ചാത്തല cron പ്രോസസ് പ്രവർത്തിപ്പിക്കുന്നു
- ക്രമീകരിച്ച `usageHistory` നിലനിർത്തൽ കാലയളവിനേക്കാൾ പഴയ `usage_history` രേഖകൾ ഇല്ലാതാക്കുന്നു

### സംഭരണ കണക്ക്

| അഭ്യർത്ഥന നിരക്ക്         | 30 ദിവസത്തെ സംഭരണം | 90 ദിവസത്തെ സംഭരണം |
| ------------------------- | ------------------ | ------------------ |
| 100 അഭ്യർത്ഥനകൾ/ദിവസം     | ~3MB               | ~9MB               |
| 1,000 അഭ്യർത്ഥനകൾ/ദിവസം   | ~30MB              | ~90MB              |
| 10,000 അഭ്യർത്ഥനകൾ/ദിവസം  | ~300MB             | ~900MB             |
| 100,000 അഭ്യർത്ഥനകൾ/ദിവസം | ~3GB               | ~9GB               |

വളരെ ഉയർന്ന ട്രാഫിക്കിന്, ഇനിപ്പറയുന്നവ പരിഗണിക്കുക:

- Database Settings വഴി നിലനിർത്തൽ കാലയളവ് കുറയ്ക്കുക


### 5. ഏറ്റവും കൂടുതൽ ഉപയോഗിക്കുന്നവരെ ഓഡിറ്റ് ചെയ്യുക

API കീ പ്രകാരം ഗ്രൂപ്പ് ചെയ്യാനും ചെലവ് അനുസരിച്ച് ക്രമീകരിക്കാനും ഡാഷ്ബോർഡോ **`/api/usage/analytics`**-ഓ ഉപയോഗിക്കുക:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## പ്രശ്നപരിഹാരം

### "ചെലവ് പ്രതീക്ഷിച്ചതിനേക്കാൾ കൂടുതലാണ്"

1. **`/api/usage/analytics?groupBy=model`** പരിശോധിക്കുക — ചെലവേറിയ മോഡൽ കണ്ടെത്തുക
2. **`/api/usage/analytics?groupBy=apiKey`** പരിശോധിക്കുക — ഏറ്റവും കൂടുതൽ ഉപയോഗിക്കുന്ന ഉപയോക്താവിനെ കണ്ടെത്തുക
3. വിലനിർണ്ണയ ഡാറ്റ കാലികമാണെന്ന് സ്ഥിരീകരിക്കുക: `POST /api/pricing/sync`

### "രേഖകൾ കാണുന്നില്ല"

- Dashboard → Database → Cleanup എന്നതിന് കീഴിലുള്ള DB നിലനിർത്തൽ ക്രമീകരണങ്ങൾ പരിശോധിക്കുക — നിശ്ചിത ഇടവേളയിലുള്ള ശുചീകരണ ടാസ്ക് (`src/lib/db/cleanup.ts`) പഴയ രേഖകൾ ഇല്ലാതാക്കുന്നു
- `src/lib/db/usage*.ts`-ലെ പിശകുകൾ പരിശോധിക്കുക — DB റൈറ്റ് പരാജയങ്ങൾ ലോഗ് ചെയ്യപ്പെടുന്നുണ്ടെങ്കിലും പുറത്തേക്ക് കാണിക്കപ്പെടുന്നില്ല
- അഭ്യർത്ഥന യഥാർത്ഥത്തിൽ `chatCore`-ൽ എത്തിയെന്ന് സ്ഥിരീകരിക്കുക — കോംബോ റൂട്ടിംഗ് പരിശോധിക്കുക

### "ക്വാട്ട നടപ്പാക്കപ്പെടുന്നില്ല"

- കീയുടെ `quotaLimit` ക്രമീകരണം പരിശോധിക്കുക
- `quotaWindow` ശരിയായി സജ്ജമാക്കിയിട്ടുണ്ടെന്ന് സ്ഥിരീകരിക്കുക
- `quotaSnapshots` രേഖകൾ പരിശോധിക്കുക — ഓരോ അഭ്യർത്ഥനയിലും അവ സൃഷ്ടിക്കപ്പെടണം
