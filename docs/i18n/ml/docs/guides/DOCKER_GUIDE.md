## വേഗത്തിൽ പ്രവർത്തിപ്പിക്കൽ

> **ഒരൊറ്റ കമാൻഡ് ഉപയോഗിച്ച് സ്വയം ഹോസ്റ്റ് ചെയ്യണോ?**
> [സ്വയം ഹോസ്റ്റ് ചെയ്യുന്നതിനുള്ള ഗൈഡ്](../getting-started/SELF_HOST_GUIDE.md) കാണുക —
> `docker compose -f docker-compose.selfhost.yml up -d` (പ്രസിദ്ധീകരിച്ച ഇമേജ് +
> Redis, ലൂപ്പ്ബാക്കിൽ മാത്രം, പ്രൊഫൈൽ തിരഞ്ഞെടുക്കേണ്ടതില്ല). താഴെയുള്ള വേഗത്തിലുള്ള പ്രവർത്തനരീതി,
> ഇതിനകം മറ്റെവിടെയെങ്കിലും Redis പ്രവർത്തിപ്പിക്കുന്ന ഉപയോക്താക്കൾക്കുള്ള
> ഒറ്റ കണ്ടെയ്നർ രീതിയാണ്.

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## എൻവയൺമെന്റ് ഫയലിനൊപ്പം

```bash
# ആദ്യം .env പകർത്തി എഡിറ്റ് ചെയ്യുക
cp .env.example .env

docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  --env-file .env \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## Docker Compose

```bash
# അടിസ്ഥാന പ്രൊഫൈൽ (CLI ടൂളുകളില്ല)
docker compose --profile base up -d

# CLI പ്രൊഫൈൽ (Claude Code, Codex, OpenClaw എന്നിവ ഉൾപ്പെടുത്തിയിരിക്കുന്നു)
docker compose --profile cli up -d

# ഹോസ്റ്റ് പ്രൊഫൈൽ (പ്രധാനമായും Linux-നായി; ഹോസ്റ്റിലെ CLI ബൈനറികൾ റീഡ്-ഒൺലി ആയി മൗണ്ട് ചെയ്യുന്നു)
docker compose --profile host up -d

# വെബ് പ്രൊഫൈൽ (വെബ്-സെഷൻ പ്രൊവൈഡറുകൾക്കായി Chromium/Playwright)
docker compose --profile web up -d

# CLI + CLIProxyAPI സൈഡ്കാർ സംയോജിപ്പിക്കുക
docker compose --profile cli --profile cliproxyapi up -d
```

## ലഭ്യമായ പ്രൊഫൈലുകൾ

പ്രധാന വിന്യാസരീതികൾക്കായി OmniRoute-ൽ Compose പ്രൊഫൈലുകൾ ലഭ്യമാണ്. നിങ്ങളുടെ എൻവയൺമെന്റിന് അനുയോജ്യമായത് തിരഞ്ഞെടുക്കുക.

| പ്രൊഫൈൽ            | സർവീസ്           | എപ്പോൾ ഉപയോഗിക്കണം                                                                                                                                             | കമാൻഡ്                                       |
| ------------------ | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `base` (ഡിഫോൾട്ട്) | `omniroute-base` | ഹെഡ്ലെസ് സെർവർ / ഏറ്റവും കുറഞ്ഞ റൺടൈം; പ്രൊവൈഡർ CLI-കൾ ഉൾപ്പെടുത്തിയിട്ടില്ല                                                                                   | `docker compose --profile base up -d`        |
| `cli`              | `omniroute-cli`  | `omniroute providers/setup/doctor`, ഉൾപ്പെടുത്തിയ CLI-കൾ (Codex, Claude Code, Droid, OpenClaw) എന്നിവ വിളിക്കുന്ന ഏജന്റിക് വർക്ക്ഫ്ലോകൾ                        | `docker compose --profile cli up -d`         |
| `host`             | `omniroute-host` | `~/.local/bin`, `~/.codex`, `~/.claude` തുടങ്ങിയവ റീഡ്-ഒൺലി ആയി മൗണ്ട് ചെയ്ത് ഹോസ്റ്റ് CLI-കളിലേക്ക് `network_mode` പോലുള്ള ആക്സസ് ആവശ്യമുള്ള Linux ഹോസ്റ്റുകൾ | `docker compose --profile host up -d`        |
| `cliproxyapi`      | `cliproxyapi`    | അപ്സ്ട്രീം CLI പ്രോക്സിയിങ്ങിനായി `8317` പോർട്ടിൽ [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) സൈഡ്കാർ പ്രവർത്തിപ്പിക്കുക                       | `docker compose --profile cliproxyapi up -d` |
| `web`              | `omniroute-web`  | ബ്രൗസർ ആവശ്യമുള്ള വെബ്-സെഷൻ പ്രൊവൈഡറുകൾ: `gemini-web`, `claude-web`, `claude-turnstile` (`runner-web` ബിൽഡ് ചെയ്യുന്നു, Chromium ഉൾപ്പെടുത്തിയിരിക്കുന്നു)     | `docker compose --profile web up -d`         |

> ഒന്നിലധികം പ്രൊഫൈലുകൾ സംയോജിപ്പിക്കാം: `docker compose --profile cli --profile cliproxyapi up -d`.

## OmniRoute Docker-ൽ പ്രവർത്തിക്കുമ്പോൾ ഹോസ്റ്റ് CLI ടൂളുകൾ കോൺഫിഗർ ചെയ്യൽ

`omniroute setup-codex`, `setup-claude`, `config set <tool>` എന്നിവയും ഡാഷ്ബോർഡിലെ
**കോൺഫിഗ് സംരക്ഷിക്കുക** ബട്ടണും `~/.codex/*.config.toml` പോലുള്ള ഫയലുകളാണ് എഴുതുന്നത്. CLI യഥാർത്ഥത്തിൽ
പ്രവർത്തിക്കുന്ന മെഷീനിൽ മാത്രമാണ് ആ പാതകൾക്ക് അർത്ഥമുള്ളത്. അവ കണ്ടെയ്നറിനുള്ളിൽ
പ്രവർത്തിപ്പിച്ചാൽ, എഴുത്ത് കണ്ടെയ്നറിന്റെ സ്വന്തം ഹോമിലാണ് (`/home/node` —
ഇമേജ് `USER node` ആയാണ് പ്രവർത്തിക്കുന്നത്) സംഭവിക്കുക; ഒരു ഹോസ്റ്റ് CLI-യും അത് വായിക്കുകയില്ല,
കണ്ടെയ്നർ പുനഃസൃഷ്ടിക്കുന്ന നിമിഷം അത് ഉപേക്ഷിക്കപ്പെടുകയും ചെയ്യും.

OmniRoute ഇത് കണ്ടെത്തുകയും നിങ്ങൾക്ക് ഉപയോഗിക്കാൻ കഴിയാത്ത വിജയസന്ദേശം
റിപ്പോർട്ട് ചെയ്യുന്നതിനുപകരം നിർദ്ദേശങ്ങളോടെ എഴുത്ത് നിരസിക്കുകയും ചെയ്യുന്നു: CLI `2` എന്ന കോഡിൽ പുറത്തുകടക്കും,
API `containerEphemeralTarget: true` സഹിതം `422` എന്ന് മറുപടി നൽകും.

### ശുപാർശ ചെയ്യുന്നത്: CLI ഹോസ്റ്റിലും OmniRoute Docker-ലും പ്രവർത്തിപ്പിക്കുക

കണ്ടെയ്നർ API നൽകുന്നു; CLI നിങ്ങളുടെ ഹോസ്റ്റ് ടൂളുകൾ കോൺഫിഗർ ചെയ്യുന്നു.

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # CLI-യെ കണ്ടെയ്നറിലേക്ക് ചൂണ്ടുക
omniroute setup-codex                      # നിങ്ങളുടെ ഹോസ്റ്റിലെ യഥാർത്ഥ ~/.codex എഴുതുന്നു
```

Codex, Claude Code, Cursor അല്ലെങ്കിൽ സമാനമായവ നിങ്ങളുടെ
ലാപ്ടോപ്പിൽ പ്രവർത്തിക്കുമ്പോൾ ഇതാണ് ശരിയായ തിരഞ്ഞെടുപ്പ് — സാധാരണ സജ്ജീകരണവും ഇതുതന്നെയാണ്.

### മറ്റൊരു മാർഗം: ഹോസ്റ്റ് കോൺഫിഗ് ഡയറക്ടറികൾ bind-mount ചെയ്യുക (`host` പ്രൊഫൈൽ)

കണ്ടെയ്നർ തന്നെ നിങ്ങളുടെ ഹോസ്റ്റ് കോൺഫിഗ് എഴുതണമെന്ന് നിങ്ങൾ ആഗ്രഹിക്കുന്നുവെങ്കിൽ,
ഡയറക്ടറികൾ mount ചെയ്യുകയും `CLI_CONFIG_HOME` mount root-ലേക്ക് ചൂണ്ടുകയും ചെയ്യുക. `host` പ്രൊഫൈൽ
ഇത് ഇതിനകം ചെയ്യുന്നു:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

ഒരു bind mount ആണ് പാതയെ വിശ്വസനീയമാക്കുന്നത്: OmniRoute
`/proc/self/mountinfo` വായിക്കുകയും mounted പാതകളിലേക്കുള്ള എഴുത്തുകൾ അനുവദിക്കുകയും ചെയ്യുന്നു (കൂടാതെ,
child ഡയറക്ടറികൾ mount ചെയ്തിട്ടുള്ള ഡയറക്ടറികളിലേക്കും; മുകളിലെ `/host-home` ഘടന കൃത്യമായി അത്തരത്തിലുള്ളതാണ്),
അതേസമയം mount ചെയ്യാത്തവയിലേക്കുള്ള എഴുത്തുകൾ ഇപ്പോഴും നിരസിക്കുന്നു.

### ഒഴിവുവഴി: കണ്ടെയ്നറിന്റെ സ്വന്തം CLI-കൾ കോൺഫിഗർ ചെയ്യുക (പരിമിതമായി മാത്രം ഉപയോഗിക്കുക)

CLI-കൾ യഥാർത്ഥത്തിൽ കണ്ടെയ്നറിനുള്ളിൽ തന്നെയാണെങ്കിൽ (`cli` പ്രൊഫൈൽ), എഴുത്ത്
മനഃപൂർവമാണ്. ഏതെങ്കിലും `setup-*` കമാൻഡിന് `--allow-container-write` നൽകുക, അല്ലെങ്കിൽ
സെർവറിനായി `OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` സജ്ജമാക്കുക. ഈ എഴുത്ത്
കണ്ടെയ്നറിനെ അതിജീവിക്കില്ലെന്ന മുന്നറിയിപ്പോടെ തുടരും.

> **സുരക്ഷാ മുന്നറിയിപ്പ് — `cli` പ്രൊഫൈൽ + `docker.sock` mount.**
> കണ്ടെയ്നറിനുള്ളിലെ auto-updater-ന് ഹോസ്റ്റ് daemon ഉപയോഗിച്ച് stack പുനഃസൃഷ്ടിക്കാൻ കഴിയുന്നതിനായി
> `cli` പ്രൊഫൈൽ `/var/run/docker.sock` bind-mount ചെയ്യുന്നു
> (`src/lib/system/autoUpdate.ts` ആ socket ഉണ്ടോയെന്ന് പരിശോധിക്കുകയും അത്
> ഇല്ലെങ്കിൽ Docker പാത ഒഴിവാക്കുകയും ചെയ്യുന്നു). ആ socket **ഹോസ്റ്റിന്റെ root അധികാരത്തിലേക്കുള്ള
> വിശ്വാസ അതിർത്തിയാണ്**: അതിലേക്ക് പ്രവേശിക്കാൻ കഴിയുന്ന എന്തിനും ഹോസ്റ്റ് Docker daemon-നെ
> root ആയി നിയന്ത്രിക്കാനാകും — ഹോസ്റ്റിലെ ഏത് കണ്ടെയ്നറും സൃഷ്ടിക്കാനും പരിശോധിക്കാനും നിർത്താനും നീക്കം ചെയ്യാനും അതിന് കഴിയും.
> ഇതിന്റെ പ്രത്യാഘാതങ്ങൾ:
>
> 1. **`cli` പ്രൊഫൈലിന്റെ port ഒരിക്കലും നെറ്റ്വർക്കിലേക്ക് തുറന്നുകാട്ടരുത്.** അത്
>    `127.0.0.1`-ൽ പ്രസിദ്ധീകരിക്കുക (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LAN വഴി എത്തിച്ചേരാവുന്ന ഒരു `cli` പ്രൊഫൈൽ dashboard-level RCE-യെ
>    പൂർണ്ണമായ ഹോസ്റ്റ് കൈയേറ്റമാക്കി മാറ്റുന്നു.
> 2. **`cli` പ്രൊഫൈലിലേക്ക് അധിക ഹോസ്റ്റ് ഡയറക്ടറികളൊന്നും bind ചെയ്യരുത്.**
>    Docker socket-നോടൊപ്പം മറ്റേതെങ്കിലും mount കൂടിയുണ്ടെങ്കിൽ, അത് കണ്ടെയ്നറിന് നിങ്ങളുടെ
>    filesystem-ലേക്കും ഹോസ്റ്റ് കോൺഫിഗിലേക്കും പൂർണ്ണമായ read/write പ്രവേശനം നൽകുന്നു. ഒരു ടൂളിന്
>    ഒരു project കാണേണ്ടതുണ്ടെങ്കിൽ, CLI binary ഉപയോഗിച്ച് അത് ലോക്കലായി പ്രവർത്തിപ്പിക്കുക — അത്
>    `cli` കണ്ടെയ്നറിലേക്ക് mount ചെയ്യരുത്.
>
> കണ്ടെയ്നറിനുള്ളിലെ auto-update ആവശ്യമില്ലെങ്കിൽ, `cli` പ്രൊഫൈൽ പ്രവർത്തനരഹിതമാക്കി വയ്ക്കുക
> (`COMPOSE_PROFILES=core,redis` അല്ലെങ്കിൽ അതിലും ചുരുങ്ങിയത്). മറ്റ് പ്രൊഫൈലുകൾ
> Docker socket mount ചെയ്യുന്നില്ല.
>
> MITM-നെ ചുറ്റിപ്പറ്റിയുള്ള അനുബന്ധ threat model-നായി `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs`-ലേക്ക് compile ചെയ്തിട്ടില്ല) കാണുക;
> `codex`/`claude-code`/`droid`/`openclaw` binary provenance chain-നായി
> `docs/security/SUPPLY_CHAIN.md` കാണുക.

## Redis സൈഡ്കാർ

വിതരണാധിഷ്ഠിത റേറ്റ് ലിമിറ്ററിനും പങ്കിട്ട കാഷിനും പിന്തുണ നൽകാൻ OmniRoute Redis-നെ ആശ്രയിക്കുന്നു. `docker-compose.yml`-ൽ `redis` സേവനം **എല്ലായ്പ്പോഴും നിർവചിച്ചിരിക്കുന്നു** (ഇതിന് പ്രൊഫൈൽ ഗേറ്റ് ഇല്ല), കൂടാതെ മറ്റേതൊരു പ്രൊഫൈലിനൊപ്പവും ഇത് ആരംഭിക്കുന്നു.

| വിശദാംശം                   | മൂല്യം                                    |
| -------------------------- | ----------------------------------------- |
| ഇമേജ്                      | `redis:7-alpine`                          |
| കണ്ടെയ്നറിന്റെ പേര്        | `omniroute-redis`                         |
| ആന്തരിക പോർട്ട്            | `6379`                                    |
| ഹോസ്റ്റ് പോർട്ട് (ഓവർറൈഡ്) | `REDIS_PORT` (ഡിഫോൾട്ട് `6379`)           |
| ഹോസ്റ്റ് ബൈൻഡ് (ഓവർറൈഡ്)   | `REDIS_BIND_HOST` (ഡിഫോൾട്ട് `127.0.0.1`) |
| വോള്യം                     | `omniroute-redis-data` → `/data`          |
| ഹെൽത്ത് ചെക്ക്             | `redis-cli ping` (10s ഇടവേള)              |

ബന്ധപ്പെട്ട എൻവയോൺമെന്റ് വേരിയബിളുകൾ:

- `REDIS_URL` — ആപ്പിലേക്ക് ഇൻജക്റ്റ് ചെയ്യുന്ന കണക്ഷൻ സ്ട്രിംഗ് (ഡിഫോൾട്ടായി `redis://redis:6379`).
- `REDIS_PORT` — Redis കണ്ടെയ്നറിനുള്ള ഹോസ്റ്റ്-സൈഡ് പോർട്ട് മാപ്പിംഗ്.
- `REDIS_BIND_HOST` — പോർട്ട് പ്രസിദ്ധീകരിക്കുന്ന ഹോസ്റ്റ് ഇന്റർഫേസ്. ഡിഫോൾട്ട് `127.0.0.1`.

> **ഡിഫോൾട്ടായി ലൂപ്പ്ബാക്ക് ഉപയോഗിക്കുന്നത് എന്തുകൊണ്ട്:** സൈഡ്കാർ `requirepass` ഇല്ലാതെയാണ് പ്രവർത്തിക്കുന്നത്, കൂടാതെ ആപ്പ്
> കണ്ടെയ്നറുകൾ compose നെറ്റ്വർക്കിലൂടെ (`redis:6379`) അതിലേക്ക് എത്തുന്നു — പ്രസിദ്ധീകരിച്ച പോർട്ട്
> ഹോസ്റ്റ്-സൈഡ് ടൂളുകൾക്കായി (`redis-cli`, ഒരു ലോക്കൽ `npm run dev`) മാത്രമുള്ളതാണ്. `0.0.0.0`-ൽ
> പ്രസിദ്ധീകരിക്കുന്നത് ഓതന്റിക്കേഷൻ ഇല്ലാത്ത Redis-നെ നിങ്ങളുടെ LAN-ലെ എല്ലാ ഹോസ്റ്റുകൾക്കും ലഭ്യമാക്കും. നിങ്ങൾ
> `REDIS_BIND_HOST=0.0.0.0` സജ്ജമാക്കുകയാണെങ്കിൽ, സേവനത്തിന്റെ `command:`-ലും `--requirepass` ചേർക്കുക.

**Redis പ്രവർത്തനരഹിതമാക്കുന്നത്** ശുപാർശ ചെയ്യുന്നില്ല (റേറ്റ് ലിമിറ്റർ ഇൻ-മെമ്മറി ഫാൾബാക്കിലേക്ക് താഴും). നിർബന്ധമാണെങ്കിൽ, `docker-compose.yml`-ലെ `redis:` സേവന ബ്ലോക്ക് നീക്കംചെയ്യുക/കമന്റ് ചെയ്യുക, അല്ലെങ്കിൽ അതിനെ പൂജ്യത്തിലേക്ക് സ്കെയിൽ ചെയ്യുക:

```bash
docker compose up -d --scale redis=0
```

## പ്രൊഡക്ഷൻ Compose

ഡെവിനൊപ്പം പ്രവർത്തിക്കുന്ന ഒരു ഒറ്റപ്പെട്ട പ്രൊഡക്ഷൻ സ്നാപ്പ്ഷോട്ടിനായി `docker-compose.prod.yml` ഉപയോഗിക്കുക.

| വിശദാംശം                    | മൂല്യം                                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| ഫയൽ                         | `docker-compose.prod.yml`                                                                                          |
| ഡിഫോൾട്ട് ഡാഷ്ബോർഡ് പോർട്ട് | `PROD_DASHBOARD_PORT=20130` (ആന്തരിക `${DASHBOARD_PORT:-20128}`-ലേക്ക് മാപ്പ് ചെയ്തിരിക്കുന്നു)                    |
| ഡിഫോൾട്ട് API പോർട്ട്       | `PROD_API_PORT=20131`                                                                                              |
| ഇമേജ്                       | `omniroute:prod` (`runner-cli` ടാർഗറ്റിൽ നിന്ന് ബിൽഡ് ചെയ്തത്)                                                     |
| Redis കണ്ടെയ്നർ             | `omniroute-redis-prod` (`redis:8.6.2`, സമർപ്പിത `redis-prod-data` വോള്യം)                                          |
| ഡാറ്റ വോള്യം                | `omniroute-prod-data` (പേരിട്ടത്, റീബിൽഡുകൾക്കിടയിലും നിലനിർത്തുന്നത്)                                             |
| ഹെൽത്ത് ചെക്കുകൾ            | `node healthcheck.mjs` + `redis-cli ping`, Redis-ന്റെ ആരോഗ്യസ്ഥിതിയെ അടിസ്ഥാനമാക്കിയുള്ള `depends_on` ഗേറ്റോടുകൂടി |

ഉപയോഗിക്കേണ്ട വിധം:

```bash
# പ്രൊഡക്ഷൻ സ്റ്റാക്ക് ബിൽഡ് ചെയ്ത് ആരംഭിക്കുക
docker compose -f docker-compose.prod.yml up -d --build

# ലോഗുകൾ തത്സമയം കാണുക
docker compose -f docker-compose.prod.yml logs -f

# പ്രവർത്തനം അവസാനിപ്പിക്കുക (വോള്യങ്ങൾ നിലനിർത്തുക)
docker compose -f docker-compose.prod.yml down
```

പ്രൊഡക്ഷൻ സ്റ്റാക്ക് ഡെവ് compose-നൊപ്പം സമാന്തരമായി പ്രവർത്തിക്കുന്നു (വ്യത്യസ്ത കണ്ടെയ്നർ പേരുകൾ, പോർട്ടുകൾ, വോള്യങ്ങൾ), അതിനാൽ പ്രൊഡക്ഷൻ പ്രവർത്തനക്ഷമമായി തുടരുമ്പോൾ നിങ്ങൾക്ക് ലോക്കലായി ആവർത്തിച്ച് വികസിപ്പിക്കുന്നത് തുടരാം.

## Dockerfile ഘട്ടങ്ങൾ

ഈ റിപ്പോസിറ്ററിയിൽ ഒരു മൾട്ടി-സ്റ്റേജ് Dockerfile (`Dockerfile`) ഉൾപ്പെടുത്തിയിരിക്കുന്നു. നാല് ഘട്ടങ്ങൾ ലഭ്യമാണ്; നിങ്ങളുടെ ഉപയോഗസാഹചര്യത്തിന് അനുയോജ്യമായ `target` തിരഞ്ഞെടുക്കുക.

| ഘട്ടം         | അടിസ്ഥാന ഇമേജ്        | ഉദ്ദേശ്യം                                                                                                                                                                                                                                                                                                                    |
| ------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `builder`     | `node:26-trixie-slim` | ഡിപെൻഡൻസികൾ ഇൻസ്റ്റാൾ ചെയ്യുന്നു (`npm ci --legacy-peer-deps`), തുടർന്ന് `npm run build` പ്രവർത്തിപ്പിക്കുന്നു (ഡിഫോൾട്ടായി Turbopack — താഴെയുള്ള ബിൽഡ്-സമയ റിസോഴ്സുകൾ കാണുക)                                                                                                                                                |
| `runner-base` | `node:26-trixie-slim` | Next.js-ന്റെ സ്റ്റാൻഡ്എലോൺ ഔട്ട്പുട്ടോടുകൂടിയ പ്രൊഡക്ഷൻ റൺടൈം. **പ്രൊവൈഡർ CLI-കൾ ഉൾപ്പെടുത്തിയിട്ടില്ല.**                                                                                                                                                                                                                    |
| `runner-cli`  | `runner-base`         | `git`, `docker.io`, `docker-compose` എന്നിവയും ഗ്ലോബൽ CLI-കളായ `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw` എന്നിവയും ചേർക്കുന്നു. **ഏജന്റിക് വർക്ക്ഫ്ലോകൾക്കായി ഇത് തിരഞ്ഞെടുക്കുക.**                                                                                                                  |
| `runner-web`  | `runner-base`         | വെബ്-സെഷൻ പ്രൊവൈഡർമാരായ `gemini-web`, `claude-web`, `claude-turnstile` എന്നിവയ്ക്കായി Playwright-ഉം Chromium ബ്രൗസറും (`--with-deps`) ചേർക്കുന്നു. **ആ പ്രൊവൈഡറുകൾ ഉപയോഗിക്കുമ്പോൾ ഇത് തിരഞ്ഞെടുക്കുക** — ഇത് ഇല്ലെങ്കിൽ സാധാരണ ഇമേജ് റിക്വസ്റ്റ് സമയത്ത് പരാജയപ്പെടും (റിലീസ് ചാനലുകൾക്ക് കീഴിലുള്ള `-web` കുറിപ്പ് കാണുക). |

ഒരു നിർദ്ദിഷ്ട ടാർഗറ്റ് മാനുവലായി ബിൽഡ് ചെയ്യുക:

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### ബിൽഡ്-സമയ റിസോഴ്സുകൾ

`builder` ഘട്ടത്തിന്റെ റിസോഴ്സ് ഉപയോഗം മൂന്ന് ബിൽഡ് ആർഗുകൾ നിയന്ത്രിക്കുന്നു. അവ ബിൽഡ് സമയത്ത് മാത്രമുള്ളവയാണ് —
`OMNIROUTE_MEMORY_MB` (താഴെ) റൺടൈമിനായുള്ള വേറൊരു ക്രമീകരണമാണ്.

| ബിൽഡ് ആർഗ്                  | ഡിഫോൾട്ട് | പ്രഭാവം                                                                                                       |
| --------------------------- | --------- | ------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `0`       | `0` webpack ഉപയോഗിച്ച് ബിൽഡ് ചെയ്യുന്നു: കുറഞ്ഞ പീക്ക് മെമ്മറി, കുറഞ്ഞ വേഗത. `1` Turbopack തിരഞ്ഞെടുക്കുന്നു. |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144`    | ആരംഭിക്കുന്ന `next build`-നുള്ള V8 ഹീപ്പ് പരിധി (`--max-old-space-size`).                                     |
| `OMNIROUTE_BUILD_WORKERS`   | `2`       | `CIRCLE_NODE_TOTAL`-ന് മൂല്യം നൽകുന്നു; പേജ്-ഡാറ്റ ശേഖരണത്തിനായി Next `workers = N - 1` കണക്കാക്കുന്നു.       |

വലിയ ബിൽഡറിൽ വർധിപ്പിക്കേണ്ടതും, പരിമിതമായ റിസോഴ്സുകളുള്ള ബിൽഡ്
`✓ Compiled successfully` എന്നതിന് **ശേഷം** നിലച്ചാൽ സംശയിക്കേണ്ടതുമായ ക്രമീകരണം
`OMNIROUTE_BUILD_WORKERS` ആണ്. ഓരോ പേജ്-ഡാറ്റ വർക്കറും പ്രത്യേകം പ്രോസസ്സാണ്;
പാരന്റ് `next build`-ഉം അങ്ങനെ തന്നെയാണ്. ഒരു തത്സമയ VPS പുനരാവിഷ്കരണത്തിൽ
(issue #7518), `NODE_OPTIONS` ഹീപ്പ് ഫ്ലാഗിനെ ആശ്രയിക്കാതെ ഓരോ പ്രോസസ്സിന്റെയും
പീക്ക് RSS ~4.5 GB ആണെന്ന് അളന്നു (Turbopack, V8 ഹീപ്പിന് പുറത്തുള്ള നേറ്റീവ്/Rust
മെമ്മറിയിലാണ് കംപൈൽ ചെയ്യുന്നത്). പബ്ലിഷ് പൈപ്പ്ലൈൻ ഉപയോഗിക്കുന്ന 16 GB / 4 vCPU
GitHub-ഹോസ്റ്റഡ് റണ്ണറുകൾക്ക് അനുസൃതമായാണ് ഡിഫോൾട്ട് `2` (→ 1 വർക്കർ, ആകെ 2
പ്രോസസ്സുകൾ) സജ്ജീകരിച്ചിരിക്കുന്നത്. `8` (→ 7 വർക്കറുകൾ) ആയപ്പോൾ ആ റണ്ണറിന്റെ
മെമ്മറി തീർന്നു; `ResourceExhausted: ... cannot allocate memory` എന്ന പിശകോടെ
buildkit ആ ഘട്ടം പരാജയപ്പെടുത്തി. ഓരോ പ്രോസസ്സിന്റെയും RSS അനുമാനിക്കുന്നതിന്
പകരം നേരിട്ട് അളന്നപ്പോൾ `3` (→ 2 വർക്കറുകൾ) പോലും ഉൾക്കൊള്ളാനായില്ല.
`tests/unit/docker-build-memory-budget.test.ts` അളന്ന കണക്കിനെ അടിസ്ഥാനമാക്കി
ഗണിതം നിർവഹിക്കുകയും ഏതെങ്കിലും ക്രമീകരണം റണ്ണറിന്റെ പരിധി കവിഞ്ഞാൽ
പരാജയപ്പെടുകയും ചെയ്യുന്നു.

Turbopack, V8 ഹീപ്പിന് **പുറത്തുള്ള** നേറ്റീവ് Rust മെമ്മറിയിലാണ് കംപൈൽ ചെയ്യുന്നത്;
അതിനാൽ `OMNIROUTE_BUILD_MEMORY_MB` അതിനെ പരിമിതപ്പെടുത്തുന്നില്ല. മെമ്മറി പരിധിയുള്ള
ഹോസ്റ്റിൽ, യാതൊരു പിശക് സന്ദേശവുമില്ലാതെ OOM കില്ലർ ബിൽഡിനെ SIGKILL ചെയ്യുന്നു —
`Creating an optimized production build`-ന്റെ മധ്യത്തിൽ അത് വെറുതെ നിലയ്ക്കുന്നു;
അതിനാൽ മെമ്മറി തീർന്നതായി തോന്നുന്നതിന് പകരം ഹാങ്ങായതായി തോന്നും. അതുകൊണ്ടാണ്
`npm run dev` / `npm run build` എന്നിവയിൽ കോഡ് ഡിഫോൾട്ട് Turbopack ആണെങ്കിലും,
`Dockerfile` webpack (`OMNIROUTE_USE_TURBOPACK=0`) ഡിഫോൾട്ടാക്കുന്നത്:
ബിൽഡ് ആർഗുകളൊന്നുമില്ലാത്ത ഒരു സാധാരണ `docker build .` (Railway-യും മറ്റ്
ഒറ്റ-ക്ലിക്ക് ഹോസ്റ്റുകളും പ്രവർത്തിപ്പിക്കുന്നത്) മെമ്മറി പരിധിയുള്ള ബിൽഡറിൽ
നിശ്ശബ്ദമായി നിലച്ചുപോകരുത്. പ്രസിദ്ധീകരിച്ച ഇമേജുകൾ ഇതിനകം തന്നെ
`docker-publish.yml`-ൽ `OMNIROUTE_USE_TURBOPACK=0` വ്യക്തമായി നൽകുന്നു.
ധാരാളം RAM ഉള്ള ബിൽഡറിൽ വേഗത്തിലുള്ള ബിൽഡിനായി Turbopack തിരഞ്ഞെടുക്കുക:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

`webpackBuildWorker` പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുന്നതിനാൽ `next build` ഒരു പാരന്റ്
പ്രോസസ്സും **കൂടാതെ** ഒരു വർക്കർ പ്രോസസ്സും പ്രവർത്തിപ്പിക്കുന്നു; ഓരോന്നും
`OMNIROUTE_BUILD_MEMORY_MB` പ്രത്യേകം പാലിക്കുന്നു. കണ്ടെയ്നർ പരിധി ആ മൂല്യത്തിന്റെ
ഒരിരട്ടിക്കല്ല, ഏകദേശം രണ്ടിരട്ടിയിലധികമായി സജ്ജീകരിക്കുക.

ഈ ട്രീയിൽ അളന്നത് (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| ബണ്ട്ലർ   | കണ്ടെയ്നർ പരിധി | ഫലം                                             |
| --------- | --------------- | ----------------------------------------------- |
| Turbopack | 8 GiB / 16 GiB  | രണ്ടിലും യാതൊരു സന്ദേശവുമില്ലാതെ OOM-killed ആയി |
| webpack   | 8 GiB           | ബിൽഡ് വർക്കർ SIGKILLed ആയി                      |
| webpack   | 12 GiB          | വിജയിച്ചു; പീക്ക് ഉപയോഗം 11.1 GiB               |

### റൺടൈം ഡിഫോൾട്ടുകൾ

`runner-base` എക്സ്പോർട്ട് ചെയ്യുന്ന ഡിഫോൾട്ടുകൾ: `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`.

Docker-ലെ മെമ്മറി പെരുമാറ്റം:

- ഇമേജ് `OMNIROUTE_MEMORY_MB=1024` സജ്ജീകരിക്കുകയും അതിൽ നിന്ന് `NODE_OPTIONS=--max-old-space-size=1024` നിർണ്ണയിക്കുകയും ചെയ്യുന്നു.
- യഥാർഥ സെർവർ പ്രോസസ് standalone launcher ആണ് ആരംഭിക്കുന്നത്; അത് `OMNIROUTE_MEMORY_MB` വായിച്ച് `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` ചേർക്കുന്നു.
- ആവർത്തിച്ചുള്ള `--max-old-space-size` മൂല്യങ്ങളിൽ അവസാനത്തേതാണ് Node ഉപയോഗിക്കുന്നത്; അതിനാൽ `OMNIROUTE_MEMORY_MB` സജ്ജീകരിക്കുന്നത് പ്രാബല്യത്തിലുള്ള Docker heap പരിധിയെ നിയന്ത്രിക്കുന്നു.
- ഇമേജ് ഇത് എല്ലായ്പ്പോഴും സജ്ജീകരിക്കുന്നതിനാൽ, launcher's സ്വന്തം RAM-അടിസ്ഥാനത്തിലുള്ള fallback Docker-ൽ ഒരിക്കലും പ്രയോഗിക്കപ്പെടുന്നില്ല. workload-നായി ഇത് വ്യക്തമായി ഉയർത്തുക (ചുവടെയുള്ള പട്ടിക). coding-agent `/v1/responses`-ന് `2048` ഇപ്പോഴും വളരെ കുറവാണ്.

### coding agent-കൾക്കുള്ള runtime RAM

1 GiB Docker default ഒരു dashboard/light-chat-നുള്ള ഏറ്റവും കുറഞ്ഞ പരിധിയാണ്, production വലുപ്പമല്ല. ദൈർഘ്യമേറിയ `POST /v1/responses` body-കൾ (നൂറുകണക്കിന് messages, പതിനക്കണക്കിന് tools) compression നടക്കുമ്പോൾ ഒന്നിലധികം in-memory graph-കൾ നിലനിർത്തുന്നു. ഒരേസമയം വന്ന ~3 MiB / ~750k-token വീതമുള്ള രണ്ട് request-ുകൾ **12 GiB** old-space-ൽ V8-നെ abort ചെയ്യിച്ചിട്ടുണ്ട് (`FATAL ERROR: Reached heap limit`), കൂടാതെ 16 GiB cgroup OOM-ലും എത്തിയിട്ടുണ്ട്. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) കാണുക.

**cgroup `--memory` heap-നെക്കാൾ കൂടുതലായി** വലുപ്പം നിശ്ചയിക്കുക — native buffer-കൾ, SQLite, compression intermediate-കൾ എന്നിവ V8-ന് പുറത്താണ് സ്ഥിതി ചെയ്യുന്നത്.

| Workload                                            | `OMNIROUTE_MEMORY_MB`              | Container / cgroup             | കുറിപ്പുകൾ                                                                                                          |
| --------------------------------------------------- | ---------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| Dashboard, ഒരു light chat                           | `1024` (image default)             | ≥2 GiB                         |                                                                                                                     |
| ഒരു coding agent (Claude/Codex/Grok)                | `8192`                             | ≥10 GiB                        | സാധാരണ single-session `/v1/responses`                                                                               |
| ഒരേസമയം രണ്ട് ദൈർഘ്യമേറിയ `/v1/responses`           | `10240`–`12288`                    | ≥12–16 GiB                     | ~12 GiB heap-ൽ V8 abort രേഖപ്പെടുത്തി                                                                               |
| ഒരേസമയം മൂന്ന് അല്ലെങ്കിൽ അതിലധികം long context-ുകൾ | ഒരു process-ൽ പ്രവർത്തിപ്പിക്കരുത് | serialize ചെയ്യുക / കൂടുതൽ RAM | default heavyweight admission-ൽ 1 in-flight മാത്രമാണ്; RAM വർധിപ്പിക്കാതെ അത് ഉയർത്തുന്നത് abort വീണ്ടും ഉണ്ടാക്കും |

bare metal-ൽ `OMNIROUTE_MEMORY_MB` **സജ്ജീകരിച്ചിട്ടില്ലെങ്കിൽ**, `omniroute serve` RAM-ന്റെ ~35% ആയി calibrate ചെയ്യുന്നു (`[512, 4096]` പരിധിക്കുള്ളിൽ). Docker എല്ലായ്പ്പോഴും `1024` സജ്ജീകരിക്കുന്നതിനാൽ, official image-ൽ ആ calibration ഒരിക്കലും പ്രവർത്തിക്കില്ല.

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

## ഉപപാതത്തിലെ റിവേഴ്സ് പ്രോക്സി (Traefik / nginx)

Next.js `basePath` സ്റ്റാൻഡ്അലോൺ ബണ്ടിലിലേക്ക് കംപൈൽ ചെയ്യപ്പെടുന്നു. OmniRoute, ആപ്പിന്റെ റൂട്ടിലുള്ള ഒരു സെന്റിനൽ ഫയലിൽ ബിൽഡ് സമയത്ത് ഉൾപ്പെടുത്തിയ മൂല്യം രേഖപ്പെടുത്തുന്നു (`npm run build` സമയത്ത് എഴുതുന്നു; `scripts/docker/ensure-docker-base-path.mjs` വായിക്കുന്നു), തുടർന്ന് കണ്ടെയ്നർ ആരംഭിക്കുമ്പോൾ അതിനെ `OMNIROUTE_BASE_PATH`-മായി താരതമ്യം ചെയ്യുന്നു. അവ വ്യത്യസ്തമായിരിക്കുകയും ഇമേജ് ഡൊമെയ്ൻ റൂട്ടിനായി ബിൽഡ് ചെയ്തതായിരിക്കുകയും ചെയ്യുമ്പോൾ, `node dev/run-standalone.mjs` പ്രവർത്തിക്കുന്നതിന് മുമ്പ് എൻട്രിപോയിന്റ് സ്റ്റാൻഡ്അലോൺ മാനിഫെസ്റ്റുകൾ, ഉൾച്ചേർത്ത `basePath`/`assetPrefix` ലിറ്ററലുകൾ (Next 16, SSR അസറ്റ് URL-കൾ `assetPrefix`-ൽ നിന്ന് മാത്രം റെൻഡർ ചെയ്യുന്നു — പാച്ചർ ഉപപാതം അതിലേക്കും പകർത്തുന്നു), ബിൽഡ് സമയത്ത് ഉൾപ്പെടുത്തിയ `/_next/static` അസറ്റ് URL-കൾ (ക്ലയന്റ്-റഫറൻസ് മാനിഫെസ്റ്റുകൾ, മീഡിയ ഇംപോർട്ടുകൾ, മുൻകൂട്ടി റെൻഡർ ചെയ്ത പിശക് പേജുകൾ), കൂടാതെ ക്ലയന്റ് `process.env` ഷിം എന്നിവ തിരുത്തിയെഴുതുന്നു.

### Compose ബിൽഡ് (ശുപാർശ ചെയ്യുന്നത്)

ഇമേജും റൺടൈമും ഒരേ ക്രമീകരണം ഉപയോഗിക്കുന്നതിന് `.env`-ൽ രണ്ട് വേരിയബിളുകളും സജ്ജമാക്കിയ ശേഷം വീണ്ടും ബിൽഡ് ചെയ്യുക:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml`, `OMNIROUTE_BASE_PATH`-നെ Docker ബിൽഡ് ആർഗ്യുമെന്റായും റൺടൈം എൻവയോൺമെന്റ് വേരിയബിളായും കൈമാറുന്നു.

### മുൻകൂട്ടി ബിൽഡ് ചെയ്ത റൂട്ട് ഇമേജ് + റൺടൈം ഉപപാതം

പ്രസിദ്ധീകരിച്ച `diegosouzapw/omniroute:*` ഇമേജുകൾ ഡൊമെയ്ൻ റൂട്ടിനായി ബിൽഡ് ചെയ്തവയാണ്. എന്നിരുന്നാലും റൺടൈമിൽ `OMNIROUTE_BASE_PATH` സജ്ജമാക്കാം; സ്റ്റാർട്ടപ്പിൽ കണ്ടെയ്നർ ബണ്ടിൽ ഒരിക്കൽ പാച്ച് ചെയ്യും. അതിനോട് പൊരുത്തപ്പെടുന്ന പബ്ലിക് ഒറിജിൻ കൂടി സജ്ജമാക്കുക:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

**പൂർണ്ണമായ** ബാഹ്യ പാത ഫോർവേഡ് ചെയ്യാൻ റിവേഴ്സ് പ്രോക്സി ക്രമീകരിക്കുക (പ്രിഫിക്സ് നീക്കം ചെയ്യരുത്). Traefik, `StripPrefix` ഇല്ലാതെ `PathPrefix(`/omniroute`)` കണ്ടെയ്നറിലേക്ക് റൂട്ട് ചെയ്യണം; അങ്ങനെ Next.js-ന് `/omniroute/...` ലഭിക്കുകയും `/omniroute/_next/...`-ൽ നിന്ന് അസറ്റുകൾ നൽകുകയും ചെയ്യും.

Docker ഹെൽത്ത്ചെക്ക്, സജീവമായ `OMNIROUTE_BASE_PATH` പ്രിഫിക്സ് ചേർത്ത ഭാരം കുറഞ്ഞ `/healthz` ലൈഫ്സൈക്കിൾ എൻഡ്പോയിന്റ് പരിശോധിക്കുന്നു. മനുഷ്യർ/ഡാഷ്ബോർഡുകൾ ഉപയോഗിക്കുന്ന ഡയഗ്നോസ്റ്റിക്സിനായി `/api/monitoring/health` തുടർന്നും ലഭ്യമാണ്; കണ്ടെയ്നറിന്റെ HEALTHCHECK വീണ്ടും അതിലേക്ക് ചൂണ്ടാൻ (ഉദാഹരണത്തിന്, ആഴത്തിലുള്ള ആരോഗ്യനില നിർബന്ധിതമാക്കാൻ), `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health` സജ്ജമാക്കുക. ആ പാത ഒരു **ആഴത്തിലുള്ള** പരിശോധനയാണ് (DB + മോണിറ്ററിംഗ് സംഗ്രഹം) — നിങ്ങൾ വീണ്ടും അത് തിരഞ്ഞെടുക്കുന്നുവെങ്കിൽ Docker-ന്റെ ഇടയ്ക്കിടെ മാത്രം പ്രവർത്തിക്കുന്ന `HEALTHCHECK`-ന് അനുയോജ്യം, എന്നാൽ Kubernetes `livenessProbe` ഇടവേളകൾക്ക് **അനുയോജ്യമല്ല**.

ഓർക്കസ്ട്രേറ്ററുകൾക്കായി (Kubernetes, Nomad മുതലായവ):

| പ്രോബ്                       | മുൻഗണന നൽകുക                                                                   | ഒഴിവാക്കുക                                                                      |
| ---------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| ലൈവ്നസ്                      | HTTP `GET /livez`, അല്ലെങ്കിൽ പ്രധാന പോർട്ടിലെ TCP (`PORT`, ഡിഫോൾട്ട് `20128`) | ലൈവ്നസായി `/api/monitoring/health`                                              |
| റെഡിനസ്                      | HTTP `GET /healthz`                                                            | ഇവന്റ് ലൂപ്പ് തിരക്കിലായതിനെ പ്രവർത്തനരഹിതമായി കണക്കാക്കുന്ന കർശനമായ ടൈംഔട്ടുകൾ |
| ആഴത്തിലുള്ള / ബ്ലാക്ക്ബോക്സ് | `/api/monitoring/health`                                                       | —                                                                               |

`/healthz`, പ്രോസസിന്റെ ലൈഫ്സൈക്കിൾ റിപ്പോർട്ട് ചെയ്യുന്നു (`ok` / `starting` / `stopping`). `/livez`, പ്രോസസ് സജീവമാണോ എന്ന് മാത്രം പരിശോധിക്കുന്നു (ഹാൻഡ്ലർ പ്രവർത്തിക്കാൻ കഴിയുമ്പോഴെല്ലാം 200 നൽകുന്നു; റെഡിനസിനായി കാത്തിരിക്കില്ല). അഭ്യർത്ഥനകൾ കൈകാര്യം ചെയ്യുന്ന അതേ Node ഇവന്റ് ലൂപ്പിലാണ് രണ്ടും പ്രവർത്തിക്കുന്നത്; അതിനാൽ CPU-അധിഷ്ഠിത കാറ്റലോഗ് അല്ലെങ്കിൽ കംപ്രഷൻ ജോലികൾ അവയെ വൈകിപ്പിക്കാം — തിരക്ക് ≠ പ്രവർത്തനരഹിതം. HTTP പ്രോബുകൾ ടൈംഔട്ട് ആകുന്നുവെങ്കിൽ TCP ലൈവ്നസിന് മുൻഗണന നൽകുക. പൂർണ്ണമായ പ്രോബ് മാർഗനിർദേശം:
[മോണിറ്ററിംഗ് ഗൈഡ് — Kubernetes പ്രോബ് ശുപാർശകൾ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations).

## Caddy ഉപയോഗിച്ചുള്ള Docker Compose (HTTPS Auto-TLS)

Caddy-യുടെ സ്വയമേവയുള്ള SSL പ്രൊവിഷനിംഗ് ഉപയോഗിച്ച് OmniRoute സുരക്ഷിതമായി ലഭ്യമാക്കാം. നിങ്ങളുടെ ഡൊമെയ്നിന്റെ DNS A റെക്കോർഡ് നിങ്ങളുടെ സെർവറിന്റെ IP-യിലേക്ക് ചൂണ്ടുന്നുണ്ടെന്ന് ഉറപ്പാക്കുക.

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # OAuth കോൾബാക്കുകൾ, ഡാഷ്ബോർഡ് ലിങ്കുകൾ, സൃഷ്ടിക്കപ്പെടുന്ന പൊതു URL-കൾ എന്നിവയ്ക്കുള്ള ബ്രൗസർ അഭിമുഖമായ ഒറിജിൻ.
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # ഷെഡ്യൂൾ ചെയ്ത ജോലികൾ / സ്വയം-ഫെച്ചുകൾ എന്നിവയ്ക്കുള്ള ആന്തരിക സെർവർ-ടു-സെർവർ URL.
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

അപ്സ്ട്രീം കണ്ടെയ്നറിനായുള്ള സ്റ്റാൻഡേർഡ് ഫോർവേഡിംഗ് ഹെഡറുകൾ Caddy സജ്ജമാക്കുന്നു. OAuth കോൾബാക്കുകൾക്കും സൃഷ്ടിക്കപ്പെടുന്ന പൊതു
ലിങ്കുകൾക്കുമുള്ള കാനോനിക്കൽ പബ്ലിക് ഒറിജിനായി OmniRoute
`NEXT_PUBLIC_BASE_URL` ഉപയോഗിക്കുന്നു; പ്രാമാണീകരിച്ച ഡാഷ്ബോർഡ് റൈറ്റ് അഭ്യർത്ഥനകൾ ഒരേ ഒറിജിനിൽ നിന്നുള്ള അഭ്യർത്ഥനകളും സെഷനുമായി ബന്ധിപ്പിച്ച CSRF
സംരക്ഷണവും ഉപയോഗിക്കുന്നു. വ്യക്തമായ കോൺഫിഗറേഷനു പകരം വിശ്വസനീയമായ ഫോർവേഡ് ചെയ്ത ഹെഡറുകളിൽനിന്ന് OmniRoute പബ്ലിക് ഒറിജിൻ നിർണ്ണയിക്കണമെന്ന് നിങ്ങൾ മനഃപൂർവം
ആഗ്രഹിക്കുന്ന വിപുലമായ ഡിപ്ലോയ്മെന്റുകൾക്കായി മാത്രം `OMNIROUTE_TRUST_PROXY` പ്രവർത്തനക്ഷമമാക്കുക.

## Cloudflare Quick Tunnel

Docker ഡിപ്ലോയ്മെന്റുകൾക്കുള്ള ഡാഷ്ബോർഡ് പിന്തുണയിൽ `Dashboard → Endpoints` എന്നതിൽ ഒറ്റ ക്ലിക്കിലൂടെ പ്രവർത്തനക്ഷമമാക്കാവുന്ന **Cloudflare Quick Tunnel** ഉൾപ്പെടുന്നു. ആദ്യമായി പ്രവർത്തനക്ഷമമാക്കുമ്പോൾ ആവശ്യമുള്ളപ്പോൾ മാത്രം `cloudflared` ഡൗൺലോഡ് ചെയ്യുകയും, നിങ്ങളുടെ നിലവിലെ `/v1` എൻഡ്പോയിന്റിലേക്ക് ഒരു താൽക്കാലിക ടണൽ ആരംഭിക്കുകയും, സൃഷ്ടിച്ച `https://*.trycloudflare.com/v1` URL നിങ്ങളുടെ സാധാരണ പബ്ലിക് URL-ന് നേരിട്ട് താഴെ കാണിക്കുകയും ചെയ്യും.

സജീവ ടണലിന്റെ അവസ്ഥ മാറ്റാതെ `Settings → Appearance` എന്നതിൽനിന്ന് എൻഡ്പോയിന്റ് ടണൽ പാനലുകൾ (Cloudflare, Tailscale, ngrok) കാണിക്കുകയോ മറയ്ക്കുകയോ ചെയ്യാം.

### ടണൽ കുറിപ്പുകൾ

- Quick Tunnel URL-കൾ താൽക്കാലികമാണ്, ഓരോ പുനരാരംഭത്തിനും ശേഷം അവ മാറും.
- OmniRoute അല്ലെങ്കിൽ കണ്ടെയ്നർ പുനരാരംഭിച്ചതിനുശേഷം Quick Tunnels സ്വയമേവ പുനഃസ്ഥാപിക്കപ്പെടില്ല. ആവശ്യമുള്ളപ്പോൾ ഡാഷ്ബോർഡിൽനിന്ന് അവ വീണ്ടും പ്രവർത്തനക്ഷമമാക്കുക.
- നിയന്ത്രിത ഇൻസ്റ്റാളേഷൻ നിലവിൽ `x64` / `arm64` ആർക്കിടെക്ചറുകളിലുള്ള Linux, macOS, Windows എന്നിവയെ പിന്തുണയ്ക്കുന്നു.
- നിയന്ത്രിത Quick Tunnels-ൽ, നിയന്ത്രിത കണ്ടെയ്നർ പരിതസ്ഥിതികളിലെ ശബ്ദമേറിയ QUIC UDP ബഫർ മുന്നറിയിപ്പുകൾ ഒഴിവാക്കുന്നതിനായി HTTP/2 ട്രാൻസ്പോർട്ടാണ് ഡിഫോൾട്ട്. മറ്റൊരു ട്രാൻസ്പോർട്ട് വേണമെങ്കിൽ `CLOUDFLARED_PROTOCOL=quic` അല്ലെങ്കിൽ `auto` സജ്ജമാക്കുക.
- Docker ഇമേജുകളിൽ സിസ്റ്റം CA റൂട്ടുകൾ ഉൾപ്പെടുത്തിയിട്ടുണ്ട്; അവ നിയന്ത്രിത `cloudflared`-ലേക്ക് കൈമാറുന്നതിനാൽ, കണ്ടെയ്നറിനുള്ളിൽ ടണൽ ബൂട്ട്സ്ട്രാപ്പ് ചെയ്യുമ്പോൾ TLS വിശ്വാസ്യതാ പരാജയങ്ങൾ ഒഴിവാക്കാം.
- പുതിയൊരു ബൈനറി ഡൗൺലോഡ് ചെയ്യുന്നതിനുപകരം നിലവിലുള്ള ഒന്ന് OmniRoute ഉപയോഗിക്കണമെങ്കിൽ `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` സജ്ജമാക്കുക.

#### വെബ്-സെഷൻ പ്രൊവൈഡറുകൾ: `-web` ഇമേജുകൾ

മുകളിലുള്ള ഓരോ ചാനലിനും `-web` ടാഗ് (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`) ലഭ്യമാണ്. ഇത് `runner-web` സ്റ്റേജിൽനിന്നാണ് ബിൽഡ് ചെയ്യുന്നത് — അതേ ഇമേജിനൊപ്പം Playwright-ഉം Chromium ബ്രൗസറും ഉൾപ്പെടുന്നു. സാധാരണ ഇമേജ് Chromium **ഇല്ലാതെയാണ്** വിതരണം ചെയ്യുന്നത്; `gemini-web`, `claude-web`, `claude-turnstile` എന്നിവയ്ക്ക് അത് ആവശ്യമാണ്.

പരാജയം സ്റ്റാർട്ടപ്പ് സമയത്തല്ല, പിന്നീടാണ് സംഭവിക്കുന്നത്: ആ പ്രൊവൈഡറുകൾ അവരുടെ മോഡലുകൾ ലിസ്റ്റ് ചെയ്യുകയും ഡാഷ്ബോർഡിൽ കണക്റ്റുചെയ്തതായി കാണിക്കുകയും ചെയ്യും; ആദ്യ അഭ്യർത്ഥന മാത്രമാണ് ഇനിപ്പറയുന്ന പിശകോടെ പരാജയപ്പെടുന്നത്

```
[500]: Failed to load external module playwright: Error: Cannot find module
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

ആ പ്രൊവൈഡറുകൾ ഉപയോഗിക്കുന്നുവെങ്കിൽ, നിങ്ങൾ നിലവിൽ ഉപയോഗിക്കുന്ന ചാനലിന്റെ `-web` ടാഗ് പുൾ ചെയ്യുക — മറ്റൊന്നും മാറില്ല. npm/CLI ഇൻസ്റ്റാളേഷനിൽ (Docker ഇമേജ് ഇല്ലാതെ), സമാനമായി നഷ്ടമായിരിക്കുന്നത് ബ്രൗസർ ബൈനറിയാണ്: ഹോസ്റ്റിൽ `npx playwright install chromium` പ്രവർത്തിപ്പിക്കുക.

#### പ്രീ-റിലീസ് ചാനൽ ഉപയോഗിക്കൽ

നിലവിലെ ഡിഫോൾട്ട് `release/v*` ബ്രാഞ്ചിലേക്കുള്ള ഓരോ push-ലും `next` ചാനൽ വീണ്ടും build ചെയ്യപ്പെടുകയും AMD64, ARM64 എന്നിവയ്ക്കായി പ്രസിദ്ധീകരിക്കപ്പെടുകയും ചെയ്യുന്നു. പഴയ maintenance ബ്രാഞ്ചുകൾക്ക് ഇത് overwrite ചെയ്യാൻ കഴിയില്ല. അടുത്ത stable tag സൃഷ്ടിക്കുന്നതിന് മുമ്പ് സജീവ release ബ്രാഞ്ചിലേക്ക് merge ചെയ്ത fixes ഉൾപ്പെട്ട, pull ചെയ്യാവുന്ന ഒരു image ഈ ചാനൽ നൽകുന്നു.

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Docker Compose-നായി, തിരഞ്ഞെടുത്ത profile ഉപയോഗിക്കുന്ന image tag override ചെയ്തശേഷം service pull ചെയ്ത് വീണ്ടും സൃഷ്ടിക്കുക:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### സുരക്ഷയും rollback-ഉം

`next` ഒരു floating pre-release ചാനലാണ്. സജീവ release ബ്രാഞ്ചിലേക്കുള്ള ഏത് push-ലും ഇത് മാറാം, കൂടാതെ ഇത് **production ഉപയോഗത്തിനായി പിന്തുണയ്ക്കപ്പെടുന്നില്ല**. ഒരു നിർദ്ദിഷ്ട build വിലയിരുത്തുമ്പോൾ image digest pin ചെയ്യുക:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

പരിശോധിക്കുന്നതിന് മുമ്പ്, OmniRoute data volume അല്ലെങ്കിൽ bind-mounted data directory backup ചെയ്യുക. Rollback ചെയ്യാൻ, മുമ്പ് ഉപയോഗിച്ചിരുന്ന stable version അല്ലെങ്കിൽ digest പുനഃസ്ഥാപിച്ച് container വീണ്ടും സൃഷ്ടിക്കുക:

```bash
docker pull diegosouzapw/omniroute:<stable-version>
docker compose up -d
```

ഒരു release-branch build-ന് ഒരിക്കലും `latest` നീക്കാനാകില്ല; യോഗ്യതയുള്ള ഒരു stable semantic version-ന് മാത്രമേ stable pointer promote ചെയ്യാനാകൂ. `next` images, release image inspection-ഉം തടയൽ സ്വഭാവമുള്ള CRITICAL-vulnerability gate-ഉം നിലനിർത്തുന്നു.

**`latest` എന്നത് git-ന്റെ പുതുമയ്ക്കുള്ള ഉറപ്പല്ല.** `main`-ലോ സജീവ `release/v*` ബ്രാഞ്ചിലോ merge ചെയ്ത fixes, ഒരു stable SemVer image പ്രസിദ്ധീകരിക്കുകയും publish job `:latest`-നെ promote ചെയ്യുകയും ചെയ്യുന്നതുവരെ `:latest`-ൽ ഉണ്ടായിരിക്കില്ല (ആ SemVer-ന്റെ അതേ digest). GitHub-ൽ fix ഇതിനകം കാണുന്നുണ്ടെങ്കിലും `latest` മാറ്റമില്ലാതെ തുടരുന്നതായി തോന്നുന്നുവെങ്കിൽ, release ബ്രാഞ്ച് പരിശോധിക്കാൻ `:next` pull ചെയ്യുക അല്ലെങ്കിൽ SemVer tag വരുന്നതുവരെ കാത്തിരിക്കുക.

| നിങ്ങൾ ആഗ്രഹിക്കുന്നത്                                                                   | ഉപയോഗിക്കുക                                    |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------- |
| വ്യതിയാനം സംഭവിക്കാൻ പാടില്ലാത്ത GitOps / production                                     | `:X.Y.Z` pin ചെയ്യുക (അല്ലെങ്കിൽ image digest) |
| പ്രസിദ്ധീകരിച്ച stables പിന്തുടരുകയും ഓരോ release-ലും recreation അംഗീകരിക്കുകയും ചെയ്യുക | `:latest`                                      |
| പുറത്തിറക്കാത്ത `release/v*` commits പരിശോധിക്കുക                                        | `:next` (production-നല്ല)                      |
| `main` പരിശോധിക്കുക                                                                      | `:main` (production-നല്ല)                      |

## ലഭ്യത: ഡിഫോൾട്ട് SQLite ഒറ്റ replica മാത്രമാണ്

Stock Docker / Kubernetes OmniRoute എന്നത് **ഒരു Node process + ഒരു SQLite writer** ആണ്. ഈ topology-യിൽ high availability **പിന്തുണയ്ക്കുന്നില്ല**.

| നിയന്ത്രണം                                        | അനന്തരഫലം                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ഒറ്റ writer                                       | ഒരേ SQLite file ഉപയോഗിച്ച് ഒന്നിലധികം replicas പ്രവർത്തിപ്പിക്കരുത്. അത് DB കേടാക്കും.                                                                                                                                                                                                                                                                                                               |
| പുനഃസൃഷ്ടിക്കൽ / പുനരാരംഭിക്കൽ / HEALTHCHECK kill | പുരോഗമിച്ചുകൊണ്ടിരിക്കുന്ന SSE, dashboard sessions, in-memory state എന്നിവയ്ക്ക് **പൂർണ്ണമായ സേവനതടസ്സം** ഉണ്ടാകും. ബന്ധിപ്പിച്ചിരിക്കുന്ന എല്ലാ clients-ഉം വിച്ഛേദിക്കപ്പെടും. endpoint ലഭ്യമല്ലാത്ത ഇടവേളയിലെ പുതിയ requests-ന് OmniRoute JSON-ന് പകരം reverse-proxy **`502 Bad Gateway: Unknown error`** ലഭിക്കും — clients-ന് ഇതിനെ provider failure-ൽ നിന്ന് വേർതിരിച്ചറിയാൻ കഴിയില്ല (#11015). |
| `/healthz`-ന്റെ അതേ event loop                    | തിരക്കേറിയ catalog അല്ലെങ്കിൽ compression tick probes വൈകിപ്പിക്കാം; തുടർന്ന് ചെറിയ timeout **ഒരേയൊരു** replica പുനരാരംഭിക്കും.                                                                                                                                                                                                                                                                      |

**Probe matrix** ([Kubernetes probe recommendations](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations) കൂടി കാണുക):

| Probe         | ലക്ഷ്യം                                                            | ഉപയോഗിക്കരുതാത്തത്                                                   |
| ------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------- |
| Liveness      | `PORT`-ലെ TCP (ഡിഫോൾട്ട് `20128`), അല്ലെങ്കിൽ soft HTTP `/healthz` | `/api/monitoring/health`                                             |
| Readiness     | HTTP `GET /healthz`                                                | event-loop തിരക്കിനെ പ്രവർത്തനരഹിതമായി കണക്കാക്കുന്ന കുറഞ്ഞ timeouts |
| Deep / humans | `/api/monitoring/health`                                           | ഓട്ടോമേറ്റഡ് kubelet liveness                                        |

**Upgrades:** എല്ലാ sessions-ഉം വിച്ഛേദിക്കപ്പെടുമെന്ന് പ്രതീക്ഷിക്കുക. കഴിയുമെങ്കിൽ clients drain ചെയ്യുക; ഡിഫോൾട്ട് SQLite-ൽ rolling update ഇല്ല. Compose `restart: unless-stopped`-ഉം Docker `HEALTHCHECK`-ഉം container Unhealthy ആകുമ്പോൾ ഒരേയൊരു process-നെ മാറ്റിസ്ഥാപിക്കും — ഇതിന് അതേ blast radius തന്നെയായിരിക്കും.

**ഒറ്റ replica**-യ്ക്കുള്ള Kubernetes snippet (Recreate നിർബന്ധമാണ്; ഒരൊറ്റ SQLite file ഉപയോഗിക്കുമ്പോൾ `replicas` വർധിപ്പിക്കരുത്):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` sleep കാരണം SIGTERM-ന് മുമ്പ് kube Service endpoints നീക്കംചെയ്യുന്നു; അതിനാൽ **പുതിയ** traffic അവസാനിക്കാനിരിക്കുന്ന process-ൽ എത്തുന്നത് നിൽക്കും. പുരോഗമിച്ചുകൊണ്ടിരിക്കുന്ന `/v1/responses` SSE, heavyweight admission leases (#11015) വഴി `SHUTDOWN_TIMEOUT_MS` (ഡിഫോൾട്ട് 30s) വരെ drain ചെയ്യപ്പെടും. എന്നിട്ടും process-ൽ എത്തുന്ന പുതിയ requests-ന് `503` + `Retry-After: 5` ലഭിക്കും. പകരംവരുന്ന instance Ready ആകുന്നതുവരെ നിലനിൽക്കുന്ന Recreate empty-endpoint gap പൂർണ്ണമായ സേവനതടസ്സമായി തുടരും — അത് SQLite topology കാരണമാണ്, probe misconfig കാരണമല്ല.

External Postgres / multi-writer HA എന്നത് രേഖപ്പെടുത്തിയിട്ടുള്ള stock path **അല്ല**. നിങ്ങൾക്ക് HA ആവശ്യമാണെങ്കിൽ, ഒറ്റ replica നിലനിർത്തുക അല്ലെങ്കിൽ project പ്രത്യേകം പരീക്ഷിച്ച് രേഖപ്പെടുത്തിയിട്ടുള്ള topology പ്രവർത്തിപ്പിക്കുക. Postgres/MySQL പ്രവർത്തനം [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075)-ൽ പുരോഗമിക്കുന്നു. അത് പുറത്തിറങ്ങുന്നതുവരെ, **വലിയ** `/v1/responses` capacity വർധിപ്പിക്കുന്നതിനുള്ള പിന്തുണയുള്ള ഏക മാർഗം N സ്വതന്ത്ര processes (അടുത്ത വിഭാഗം) ആണ്; ഒരൊറ്റ volume-ൽ `replicas > 1` അല്ല.

## സ്കെയിൽ-ഔട്ട്: N സ്വതന്ത്ര പ്രോസസുകൾ

ഒരു Node പ്രോസസ് എന്നത് **ഒരു V8 heap** ആണ്. പരസ്പരം ഓവർലാപ്പ് ചെയ്യുന്ന ~3 MiB / ~750k-token coding-agent `POST /v1/responses` അഭ്യർത്ഥനകൾ രണ്ടെണ്ണം (RTK + Caveman), ~12 Gi-ൽ ആ heap-നെ അബോർട്ട് ചെയ്യുകയും (`FATAL ERROR: Reached heap limit`) 16 Gi cgroup-ൽ OOM ഉണ്ടാക്കുകയും ചെയ്യാം. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) കാണുക. ആ അളവ് ഒരു **മെമ്മറി-ബജറ്റ്** മുന്നറിയിപ്പാണ്; ഒരേസമയം പ്രവർത്തിക്കുന്ന ദൈർഘ്യമേറിയ `/v1/responses` അഭ്യർത്ഥനകൾക്ക് ഉൽപ്പന്നം ഏർപ്പെടുത്തിയ പരമാവധി പരിധി രണ്ട് എന്നല്ല. അതേ V8/cgroup പരിധിയിൽനിന്ന് വലുപ്പം സ്വയം നിർണ്ണയിക്കപ്പെടുന്ന ingest byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) ഉപയോഗിച്ചാണ് heavyweight chat admission നിയന്ത്രിക്കുന്നത് — ഇതിനകം വലുപ്പം ക്രമീകരിച്ച പ്രോസസിൽ അത് ഉയർന്ന മൂല്യത്തിലേക്ക് override ചെയ്യുന്നത് (അല്ലെങ്കിൽ പഴയ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` request-count cap സജ്ജമാക്കുന്നത്) അബോർട്ട് വീണ്ടും ഉണ്ടാകാൻ ഇടയാക്കും. ചെറിയ chats, `/healthz`, `/v1/models`, MCP എന്നിവ **ആ പരിധിയിൽ ഉൾപ്പെടുന്നില്ല**.

### ഒറ്റ പ്രോസസ്: രണ്ടിലധികം ദൈർഘ്യമേറിയ `/v1/responses`

പ്രോസസ്-വ്യാപകമായ inflight-byte budget-ൽ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) ഇനിയും ഇടമുണ്ടെങ്കിൽ, **ആരോഗ്യകരമായ** ഒരു പ്രോസസിന് (heap `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO`-നേക്കാൾ താഴെ, ഡിഫോൾട്ട് `0.75`) ഒരേസമയം രണ്ടിലധികം ദൈർഘ്യമേറിയ `POST /v1/responses` പ്രവർത്തിപ്പിക്കാൻ **കഴിഞ്ഞേക്കാം**. `OMNIROUTE_CHAT_LARGE_BODY_BYTES`-നു തുല്യമോ അതിലധികമോ വലുപ്പമുള്ള bodies (ഡിഫോൾട്ട് 256 KiB) structure-heavy അഭ്യർത്ഥനകളുടെ അതേ heavyweight lease എടുക്കുകയും അതേ [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` escape (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ഉപയോഗിക്കുകയും ചെയ്യുന്നു. ഒരേസമയം പ്രവർത്തിക്കുന്ന പതിനുകണക്കിന് ദൈർഘ്യമേറിയ SSE clients (ഓപ്പറേറ്റർമാർക്ക് പലപ്പോഴും 40–50 എണ്ണം ആവശ്യമാണ്) എന്നത് ഒരു **മെമ്മറി-ബജറ്റ്** ചോദ്യമാണ് — heap + primary/headroom slots + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` എന്നിവയ്ക്ക് അനുസൃതമായി വലുപ്പം നിശ്ചയിക്കുക — അല്ലാതെ ഉൽപ്പന്നത്തിന്റെ “പരമാവധി 2” എന്ന കർശന പരിധിയല്ല. സമ്മർദ്ദത്തിലായ heap ഇപ്പോഴും വീണ്ടും ശ്രമിക്കാവുന്ന `503` നൽകി ലോഡ് ഒഴിവാക്കുന്നതിനാൽ #7849 വീണ്ടും സംഭവിക്കില്ല.

**heaps ഗുണിക്കുന്നതിന്** (സ്വതന്ത്ര V8 old-spaces) **ഇപ്പോൾ**:

| ചെയ്യുക                                                                                                                                                                               | ചെയ്യരുത്                                                           |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| ഓരോന്നിനും **സ്വന്തം** `DATA_DIR` / volume ഉള്ള **N containers/pods** പ്രവർത്തിപ്പിക്കുക                                                                                              | ഒരൊറ്റ SQLite file-നെതിരെ `replicas > 1` സജ്ജമാക്കുക                |
| heap / inflight-byte budget അടിസ്ഥാനമാക്കി heavy in-flight + healthy-headroom വലുപ്പം നിശ്ചയിക്കുക; 1–2 എന്നത് യാഥാസ്ഥിതികമായ #7849 ഡിഫോൾട്ടാണ്, ഉൽപ്പന്നത്തിന്റെ കർശനമായ പരമാവധിയല്ല | ഒരു പ്രോസസിന് 8× RAM-ഉം പരിധിയില്ലാത്ത count cap-ഉം നൽകുക           |
| ഐച്ഛികം: **പങ്കിട്ട quota counters**-നായി `QUOTA_STORE_DRIVER=redis` + `QUOTA_STORE_REDIS_URL`                                                                                        | Redis-നെ പങ്കിട്ട SQLite ആയി കണക്കാക്കരുത് — അത് അങ്ങനെയല്ല         |
| ഓരോ instance-ലേക്കും provider secrets പകർത്തുക (അല്ലെങ്കിൽ വിഭജിക്കപ്പെട്ട dashboards അംഗീകരിക്കുക)                                                                                   | instances-ലുടനീളം ഒരൊറ്റ dashboard / ഒരൊറ്റ call-log പ്രതീക്ഷിക്കുക |
| ഏതെങ്കിലും load balancer മുന്നിൽ സ്ഥാപിക്കുക; API key അല്ലെങ്കിൽ session അടിസ്ഥാനമാക്കിയ sticky routing മതിയാകും                                                                      | vendor-specific size-aware middleware നിർബന്ധമാക്കുക                |

ഹാർഡ്വെയർ: ഓരോ instance-ലും ഒരേസമയം പ്രവർത്തിക്കുന്ന ദൈർഘ്യമേറിയ `/v1/responses`-ന്റെ എണ്ണം ഒരു **മെമ്മറി-ബജറ്റ്** ചോദ്യമാണ് (heap + inflight-byte / #10110). സ്വതന്ത്രമായ `N` `DATA_DIR`-കൾ ഇപ്പോഴും heaps ഗുണിക്കുന്നു: host RAM, `N × cgroup` ഉൾക്കൊള്ളാൻ പര്യാപ്തമായിരിക്കണം; “N=8 ഉള്ള ഒരൊറ്റ 16 Gi pod” എന്നല്ല. ഒരൊറ്റ SQLite file-ൽ ഒരിക്കലും `replicas > 1` ഉപയോഗിക്കരുത്.

Compose മാതൃക (രണ്ട് heaps, രണ്ട് volumes — `deploy.replicas: 2` അല്ല):

```yaml
services:
  omniroute-a:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

In-process density (HTTP isolate-ന് പുറത്തുള്ള compression) [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023)-ലുണ്ട്. പങ്കിട്ട durable state-ലുള്ള ഒരൊറ്റ logical cluster [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075)-ലുണ്ട്.

## Docker-നുള്ളിലെ Gemini പ്രാദേശിക പിശകുകൾ

Google AI Studio / Gemini API, FAILED_PRECONDITION സഹിതം HTTP 400-ഉം
`User location is not supported for the API use.` എന്ന സന്ദേശവും തിരികെ നൽകിയേക്കാം. ഹോസ്റ്റിലെ വിജയകരമായ ഒരു അഭ്യർത്ഥന,
കണ്ടെയ്നറും അതേ ഔട്ട്ബൗണ്ട് റൂട്ട് ഉപയോഗിക്കുന്നുവെന്ന് തെളിയിക്കുന്നില്ല. DNS ക്രമീകരണം,
IPv4/IPv6 കണക്റ്റിവിറ്റി, VPN റൂട്ടിംഗ്, കോൺഫിഗർ ചെയ്ത പ്രോക്സികൾ എന്നിവ വ്യത്യാസപ്പെട്ടേക്കാം.
[Google പിന്തുണയ്ക്കുന്ന പ്രദേശങ്ങൾ](https://ai.google.dev/gemini-api/docs/available-regions)
എന്നതോടൊപ്പം യഥാർത്ഥ കണക്ഷൻ റൂട്ടും പരിശോധിക്കുക; ഈ പിശക് മാത്രം ഒരു മോശം API കീ ആണെന്ന് സൂചിപ്പിക്കുന്നില്ല.

### ഓരോ കണക്ഷനുമുള്ള പ്രോക്സിക്ക് മുൻഗണന നൽകുക

ബാധിക്കപ്പെട്ട Gemini കണക്ഷനായി OmniRoute-ന്റെ [ഓരോ കണക്ഷനുമുള്ള പ്രോക്സി കോൺഫിഗറേഷൻ](../ops/PROXY_GUIDE.md#4-level-proxy-system)
ഉപയോഗിക്കുക, തുടർന്ന് അതേ മോഡൽ ഉപയോഗിച്ച് **Test Connection**-ഉം ഒരു ചെറിയ അഭ്യർത്ഥനയും
വീണ്ടും നടത്തുക. ഇത് റൂട്ടിംഗ് മാറ്റത്തെ ആ കണക്ഷനിൽ മാത്രം പരിമിതപ്പെടുത്തുന്നു. കണ്ടെയ്നറിൽ നിന്ന്
പ്രോക്സി ആക്സസ് ചെയ്യാനാകുന്നുണ്ടെന്നും കണക്ഷൻ യഥാർത്ഥത്തിൽ അത് തിരഞ്ഞെടുക്കുന്നുണ്ടെന്നും സ്ഥിരീകരിക്കുക.
റൂട്ട് മാറ്റുന്നത് അപ്സ്ട്രീം പ്രാദേശിക യോഗ്യത ഉറപ്പാക്കുന്നില്ല.

### ഹോസ്റ്റിലെയും കണ്ടെയ്നറിലെയും നെറ്റ്വർക്കിംഗ് താരതമ്യം ചെയ്യുക

ഓതന്റിക്കേറ്റ് ചെയ്ത ഫലങ്ങൾ താരതമ്യം ചെയ്യുമ്പോൾ കീയും മോഡലും അഭ്യർത്ഥനയും ഒരേപോലെ നിലനിർത്തുക; ക്രെഡൻഷ്യലുകൾ,
പ്രോക്സി പാസ്വേഡുകൾ, അല്ലെങ്കിൽ പൂർണ്ണമായ ഓതറൈസേഷൻ ഹെഡറുകൾ ഒരിക്കലും ഒരു ഇഷ്യൂവിൽ
പേസ്റ്റ് ചെയ്യരുത്. ആദ്യം, ഹോസ്റ്റിലും കണ്ടെയ്നറിനുള്ളിലും ഒരേ കമാൻഡ്
ഉപയോഗിച്ച് OS റിസോൾവർ ഏതെല്ലാം അഡ്രസ് ഫാമിലികളാണ് നൽകുന്നതെന്ന് പരിശോധിക്കുക:

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

`omniroute`-ന് പകരം നിങ്ങൾ പ്രവർത്തിപ്പിക്കുന്ന സർവീസ് നൽകുക (ഉദാഹരണത്തിന്, `omniroute-web`). ഈ
കമാൻഡുകൾ ക്രെഡൻഷ്യലുകളോ IP വിലാസങ്ങളോ ഇല്ലാതെ അഡ്രസ് ഫാമിലികൾ പ്രിന്റ് ചെയ്യുന്നു. തിരികെ ലഭിക്കുന്ന `6`
ഒരു IPv6 DNS ഫലം മാത്രമാണ് കാണിക്കുന്നത്: ഉപയോഗിക്കാവുന്ന IPv6 റൂട്ടോ API ആക്സസോ ഉണ്ടെന്ന് അത്
തെളിയിക്കുന്നില്ല. `curl` ഇൻസ്റ്റാൾ ചെയ്തിട്ടുള്ളിടത്ത്, രണ്ട് എൻവയോൺമെന്റുകളിലും
`curl -4 -I https://generativelanguage.googleapis.com` എന്നതും
`curl -6 -I https://generativelanguage.googleapis.com` എന്നതും താരതമ്യം ചെയ്യുക.
ഓതന്റിക്കേറ്റ് ചെയ്യാത്ത പിശകാണെങ്കിലും, ഒരു HTTP പ്രതികരണം ആ പ്രോബിനുള്ള കണക്റ്റിവിറ്റി തെളിയിക്കുന്നു;
ഓതന്റിക്കേറ്റ് ചെയ്ത മോഡൽ അഭ്യർത്ഥന മാത്രമാണ് Gemini യോഗ്യത പരിശോധിക്കുന്നത്.

### ഹോസ്റ്റ്-തലത്തിലുള്ള ബദൽ: പ്രവർത്തിക്കുന്ന IPv6-ഉം റിസോൾവർ നയവും

[#12762](https://github.com/diegosouzapw/OmniRoute/issues/12762)-ന്റെ റിപ്പോർട്ടർ, കണ്ടെയ്നർ IPv6 പ്രവർത്തനക്ഷമമാക്കിയും glibc അഡ്രസ്
തിരഞ്ഞെടുക്കൽ മാറ്റിയും അവരുടെ എൻവയോൺമെന്റിൽ ആക്സസ് പുനഃസ്ഥാപിച്ചു.
ഇത് എൻവയോൺമെന്റ്-നിർദ്ദിഷ്ടമായ ഒരു ബദലായി പരിഗണിക്കുക. റിസോൾവർ മുൻഗണനകൾ ക്രമീകരിക്കുന്നതിന് മുമ്പ്
പ്രവർത്തിക്കുന്ന ഹോസ്റ്റ് IPv6, കണ്ടെയ്നർ എഗ്രസ്/റൂട്ടിംഗ്, ഫയർവാൾ നിയമങ്ങൾ എന്നിവ സ്ഥിരീകരിക്കുക.
ഒരു സ്വകാര്യ ULA വിലാസം മാത്രം പൊതു IPv6 കണക്റ്റിവിറ്റി സ്ഥാപിക്കുന്നില്ല.

Compose-ന്റെ ഡിഫോൾട്ട് നെറ്റ്വർക്കുമായി ഇതിനകം അറ്റാച്ച് ചെയ്തിട്ടുള്ള സർവീസുകൾക്ക്, ഈ ഫ്രാഗ്മെന്റ്
ആ നെറ്റ്വർക്കിൽ IPv6 പ്രവർത്തനക്ഷമമാക്കുന്നു; നിങ്ങളുടെ സർവീസിന്റെ ബാക്കിയുള്ള ഭാഗം, പോർട്ടുകൾ, വോള്യങ്ങൾ, കോൺഫിഗറേഷൻ എന്നിവ നിലനിർത്തുക:

```yaml
networks:
  default:
    enable_ipv6: true
```

പേരിട്ട ഒരു നെറ്റ്വർക്കിന്, സർവീസ് യഥാർത്ഥത്തിൽ ചേരുന്ന നെറ്റ്വർക്കിൽ അത് പ്രവർത്തനക്ഷമമാക്കുക. Docker-ന്
ഒരു ULA സബ്നെറ്റ് അലോക്കേറ്റ് ചെയ്യാനാകും; നിങ്ങളുടെ നെറ്റ്വർക്കിന് അത് ആവശ്യമായിരിക്കുമ്പോൾ മാത്രം വ്യക്തമായതും
ഓവർലാപ്പ് ചെയ്യാത്തതുമായ ഒരു സബ്നെറ്റ് തിരഞ്ഞെടുക്കുക. [Docker IPv6 നെറ്റ്വർക്കിംഗ്](https://docs.docker.com/engine/daemon/ipv6/)
എന്നതും [Compose നെറ്റ്വർക്ക് ഓപ്ഷനുകൾ](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6) എന്നതും കാണുക.

ഒരു **glibc അടിസ്ഥാനമാക്കിയുള്ള ഇമേജിൽ**, `/etc/gai.conf`-ന് അഡ്രസ് തിരഞ്ഞെടുക്കൽ മാറ്റാനാകും. നിലവിലെ
റിപ്പോസിറ്ററി Dockerfile Debian ഉപയോഗിക്കുന്നു; ഇഷ്ടാനുസൃത musl അടിസ്ഥാനമാക്കിയുള്ള ഇമേജുകൾ ഈ സംവിധാനം
പങ്കിടുന്നില്ല. റിപ്പോർട്ട് ചെയ്ത ക്രമീകരണം ULA ലേബലിനെ `label fc00::/7 6` എന്നതിൽ നിന്ന്
`label fc00::/7 1` എന്നതിലേക്ക് മാറ്റുന്നു. ഇമേജിന്റെ പൂർണ്ണമായ പോളിസി ടേബിളിൽ നിന്ന് ആരംഭിച്ച് അതിലെ മറ്റ്
എൻട്രികൾ നിലനിർത്തുക: ഒരു `label` അല്ലെങ്കിൽ `precedence` എൻട്രി ചേർക്കുന്നത് ആ ഡിഫോൾട്ട് ടേബിളിനെ
മാറ്റിസ്ഥാപിക്കുന്നു, അതിനാൽ മാറ്റിയ വരി മാത്രം അടങ്ങിയ ഫയൽ മതിയാകില്ല.
[glibc കോൺഫിഗറേഷൻ റഫറൻസ്](https://github.com/bminor/glibc/blob/master/posix/gai.conf)
ആ സെമാന്റിക്സ് രേഖപ്പെടുത്തുന്നു. അവലോകനം ചെയ്ത ഫയൽ `/etc/gai.conf`-ൽ റീഡ്-ഒൺലിയായി ബൈൻഡ്-മൗണ്ട്
ചെയ്യുകയും അത് പ്രയോഗിക്കാൻ സർവീസ് പുനഃസൃഷ്ടിക്കുകയും ചെയ്യുക.

ഇത് **ആ കണ്ടെയ്നറിലെ എല്ലാ ഔട്ട്ബൗണ്ട് ട്രാഫിക്കിനുമുള്ള** OS അഡ്രസ് തിരഞ്ഞെടുക്കൽ മാറ്റുന്നു.
എല്ലാ ആപ്ലിക്കേഷനുകളും IPv6 തിരഞ്ഞെടുക്കണമെന്ന് ഇത് നിർബന്ധിക്കുന്നില്ല: Node-ന്റെ DNS ക്രമവും കണക്ഷൻ
തിരഞ്ഞെടുക്കലും പ്രധാനമാണ്. പ്രത്യേകിച്ച്, `--dns-result-order=ipv4first` IPv4-ന് മുൻഗണന നൽകുന്നു,
അതിനാൽ IPv4-മാത്രമുള്ള പരാജയത്തിനുള്ള പരിഹാരമല്ല ഇത്. [Node DNS ക്രമീകരണം](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder) കാണുക.

ഹോസ്റ്റ്-തലത്തിലുള്ള ഏതൊരു മാറ്റത്തിനും ശേഷം Gemini-യെയും നിങ്ങളുടെ മറ്റ് പ്രൊവൈഡർമാരെയും വീണ്ടും പരിശോധിക്കുക.
പഴയ നിലയിലേക്ക് മടങ്ങാൻ, ഇഷ്ടാനുസൃത `gai.conf` മൗണ്ട് നീക്കം ചെയ്യുക, മുമ്പത്തെ നെറ്റ്വർക്ക് കോൺഫിഗറേഷൻ
പുനഃസ്ഥാപിക്കുക, മെയിന്റനൻസ് വിൻഡോയിൽ ബാധിക്കപ്പെട്ട സർവീസ്/നെറ്റ്വർക്ക് പുനഃസൃഷ്ടിക്കുക. ഒരു നെറ്റ്വർക്ക്
പുനഃസൃഷ്ടിക്കുന്നത് അതുമായി അറ്റാച്ച് ചെയ്തിട്ടുള്ള മറ്റ് കണ്ടെയ്നറുകൾക്ക് തടസ്സമുണ്ടാക്കാം; സ്ഥിരമായ ഡാറ്റ വോള്യം ഇല്ലാതാക്കരുത്.

## പ്രധാന കുറിപ്പുകൾ

- **SQLite WAL മോഡ്:** ഏറ്റവും പുതിയ മാറ്റങ്ങൾ `storage.sqlite`-ലേക്ക് checkpoint ചെയ്യാൻ OmniRoute-ന് കഴിയുന്ന തരത്തിൽ `docker stop` പൂർത്തിയാകാൻ അനുവദിക്കണം. ഉൾപ്പെടുത്തിയിരിക്കുന്ന Compose ഫയലുകളിൽ ഇതിനകം 40s stop grace period സജ്ജീകരിച്ചിട്ടുണ്ട്. നിങ്ങൾ image നേരിട്ട് പ്രവർത്തിപ്പിക്കുകയാണെങ്കിൽ, `--stop-timeout 40` നിലനിർത്തുക.
- **`DISABLE_SQLITE_AUTO_BACKUP`:** പതിവ്/pre-write backup-കൾ ബാഹ്യമായി കൈകാര്യം ചെയ്യുന്നുവെങ്കിൽ `true` ആയി സജ്ജീകരിക്കുക. നിലവിലുള്ള database migration-കൾക്ക് അവയ്ക്കായുള്ള സ്ഥിരതയുള്ള safety snapshot-ഉം mass-migration guard-ഉം തുടർന്നും ആവശ്യമാണ്.
- **ഡാറ്റ നിലനിർത്തൽ:** container restart-കൾക്കിടയിലും നിങ്ങളുടെ database, key-കൾ, configuration-കൾ എന്നിവ നിലനിർത്താൻ `/app/data`-യിലേക്ക് എല്ലായ്പ്പോഴും ഒരു volume mount ചെയ്യുക.
- **Port configuration:** default `20128` port മാറ്റാൻ `PORT` environment variable override ചെയ്യുക.
