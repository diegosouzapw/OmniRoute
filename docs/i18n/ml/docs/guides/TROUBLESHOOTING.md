## ദ്രുത റഫറൻസ്

**OmniRoute ആദ്യമായാണോ ഉപയോഗിക്കുന്നത്?** ഇവിടെ തുടങ്ങുക — 90% പ്രശ്നങ്ങൾക്കും ഇവ പരിഹാരമാകും:

| നിങ്ങൾ കാണുന്നത്                    | അതിന്റെ അർത്ഥം                                          | ചെയ്യേണ്ടത്                                                                                                                           |
| ----------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| "കണക്റ്റ് ചെയ്യാനാകുന്നില്ല"        | OmniRoute പ്രവർത്തിക്കുന്നില്ല                          | `omniroute` അല്ലെങ്കിൽ `docker restart omniroute` പ്രവർത്തിപ്പിക്കുക                                                                  |
| "അസാധുവായ API കീ"                   | നിങ്ങളുടെ കീ തെറ്റാണ് അല്ലെങ്കിൽ കാലഹരണപ്പെട്ടു         | പ്രൊവൈഡറുടെ വെബ്സൈറ്റിൽ നിന്ന് കീ വീണ്ടും പകർത്തുക                                                                                    |
| "നിരക്ക് പരിധി കവിഞ്ഞു"             | നിങ്ങൾ വളരെയധികം അഭ്യർത്ഥനകൾ അയയ്ക്കുന്നു               | 1 മിനിറ്റ് കാത്തിരിക്കുക, അല്ലെങ്കിൽ സ്വയമേവ ഫാൾബാക്ക് ചെയ്യാൻ `model: "auto"` ഉപയോഗിക്കുക                                            |
| "ക്വോട്ട കവിഞ്ഞു"                   | നിങ്ങളുടെ സൗജന്യ/പണമടച്ച ക്വോട്ട പൂർണ്ണമായി ഉപയോഗിച്ചു  | കൂടുതൽ പ്രൊവൈഡർമാരെ കണക്റ്റ് ചെയ്യുക, അല്ലെങ്കിൽ സൗജന്യ പ്രൊവൈഡർമാരെ (Kiro, Pollinations) ഉപയോഗിക്കുക                                 |
| "പ്രതികരണങ്ങൾ മന്ദഗതിയിലാണ്"        | പ്രൊവൈഡർ തിരക്കിലാണ് അല്ലെങ്കിൽ വളരെ അകലെയാണ്           | `model: "auto/fast"` ഉപയോഗിക്കുക അല്ലെങ്കിൽ കൂടുതൽ വേഗതയുള്ള പ്രൊവൈഡറെ (Groq, Cerebras) കണക്റ്റ് ചെയ്യുക                              |
| "തെറ്റായ പ്രൊവൈഡർ ഉപയോഗിച്ചു"       | `auto` മറ്റൊരു പ്രൊവൈഡറെ തിരഞ്ഞെടുത്തു                  | ഇത് സാധാരണമാണ്! `auto` ഏറ്റവും മികച്ചത് തിരഞ്ഞെടുക്കും. `model: "openai/gpt-4o"` ഉപയോഗിച്ച് ഒരു നിർദ്ദിഷ്ട പ്രൊവൈഡറെ നിർബന്ധിതമാക്കുക |
| "502 മോശം ഗേറ്റ്വേ"                 | പ്രൊവൈഡർ പ്രവർത്തനരഹിതമാണ്                              | കാത്തിരുന്ന് വീണ്ടും ശ്രമിക്കുക, അല്ലെങ്കിൽ പ്രൊവൈഡർമാരെ മാറ്റാൻ `model: "auto"` ഉപയോഗിക്കുക                                          |

| "omniroute തിരിച്ചറിയപ്പെടുന്നില്ല" | Windows PATH-ൽ ഗ്ലോബൽ node മൊഡ്യൂളുകൾ ഉൾപ്പെട്ടിട്ടില്ല | നിങ്ങളുടെ npm ഗ്ലോബൽ പ്രിഫിക്സ് Windows PATH-ലേക്ക് ചേർക്കുക. `npm config get prefix` ഉപയോഗിച്ച് അത് കണ്ടെത്തുക.                      |
| "429 വളരെയധികം അഭ്യർത്ഥനകൾ"         | നിരക്ക് പരിമിതപ്പെടുത്തിയിരിക്കുന്നു                    | 1 മിനിറ്റ് കാത്തിരിക്കുക, അല്ലെങ്കിൽ കൂടുതൽ പ്രൊവൈഡർമാരെ കണക്റ്റ് ചെയ്യുക                                                             |

### സൗജന്യ പ്രൊവൈഡർമാരിലെ നിരക്ക് പരിമിതപ്പെടുത്തൽ (429 / 400 / 401)

**ലക്ഷണം**: സൗജന്യ/പ്രാമാണീകരണം ആവശ്യമില്ലാത്ത പ്രൊവൈഡർമാരുമായി (opencode, auggie മുതലായവ) `model: "auto"` ഉപയോഗിക്കുമ്പോൾ, ഉത്തരങ്ങൾക്ക് പകരം ഇടയ്ക്കിടെ `HTTP 429`, `400`, അല്ലെങ്കിൽ `401` ലഭിക്കുന്നു. ഏതാനും നിമിഷങ്ങൾക്കുശേഷം അതേ പ്രോംപ്റ്റ് വീണ്ടും ശ്രമിക്കുമ്പോൾ അഭ്യർത്ഥനകൾ വിജയിക്കുന്നു, എന്നാൽ ഓട്ടോമേഷൻ (cron ജോലികൾ, ഏജന്റുകൾ, സ്ക്രിപ്റ്റുകൾ) ആദ്യ പരാജയത്തിൽ തന്നെ തകരുന്നു.

**മൂലകാരണം**: സ്വതന്ത്രമായ മൂന്ന് പരാജയ രീതികൾ ഒരുമിച്ച് സംഭവിക്കുന്നു:

1. **പ്രൊവൈഡർ നിരക്ക് പരിധി (`429`)**: സൗജന്യ ടയറുകളിൽ ഓരോ സമയജാലകത്തിനും ഒരു ക്വോട്ട നടപ്പിലാക്കിയേക്കാം. ഒരേസമയം വരുന്ന നിരവധി സമാന്തര കോളുകൾ അത് തീർത്തുകളയുന്നതിനാൽ, സമയജാലകം പുനഃസജ്ജമാകുന്നതുവരെ അടുത്ത അഭ്യർത്ഥന നിരസിക്കപ്പെടും.
2. **പാസ്ത്രൂവിലെ തകരാറുള്ള മോഡൽ (`400`/`401`)**: കാറ്റലോഗിൽ രജിസ്റ്റർ ചെയ്തിട്ടുണ്ടെങ്കിലും സജീവ ക്രെഡൻഷ്യലുകൾ ഇല്ലാത്ത `opencode`-ൽ നിന്നുള്ള പാസ്ത്രൂ മോഡലുകൾ `auto/*` പൂളുകളിൽ ഉൾപ്പെട്ടേക്കാം (ഉദാ. `oc/north-mini-code-free` → `401`). ഓട്ടോ-റൂട്ടർ ഒന്ന് പരീക്ഷിക്കുന്നു, പരാജയപ്പെടുന്നു, ഫാൾബാക്ക് ആരംഭിക്കുന്നതിന് മുമ്പുതന്നെ പിശക് പുറത്തേക്ക് കൈമാറപ്പെടുന്നു.
3. **കൺകറൻസി വർധന (`429` ലോഡിന് കീഴിൽ)**: ഒന്നിലധികം ഏജന്റ്/cron സെഷനുകൾ ഒരേസമയം `auto` ഉപയോഗിക്കുമ്പോൾ, മൊത്തം അഭ്യർത്ഥന നിരക്ക് സൗജന്യ പ്രൊവൈഡർമാർക്ക് കൈകാര്യം ചെയ്യാനാകുന്നതിനെ കവിയുന്നു; അതിനാൽ സാധുവായ കോളുകളും ദുരുപയോഗമായി അടയാളപ്പെടുത്തപ്പെടുന്നു.

**സ്ഥിരീകരിച്ച പരിഹാരം (കമ്മ്യൂണിറ്റി റിപ്പോർട്ട് ചെയ്തത്, 2026-08-10)**: റൊട്ടേഷൻ, കൺകറൻസി, ഫാൾബാക്ക് എന്നിവ സൗജന്യ ടയറിലെ അസ്ഥിരതയെ പരാജയപ്പെടാതെ ഉൾക്കൊള്ളുന്ന തരത്തിൽ മൂന്ന് എൻവയൺമെന്റ് വേരിയബിളുകൾ ക്രമീകരിക്കുക:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ലഭിക്കുമ്പോൾ മറ്റൊരു മോഡൽ/പ്രൊവൈഡറിലേക്ക് മാറുക (തകരാറുള്ള പാസ്ത്രൂ മോഡലുകൾ ഒഴിവാക്കുന്നു)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ഹെവിവെയ്റ്റ് പ്രവേശനത്തിനുള്ള പരിധി വ്യക്തമായി സജ്ജമാക്കുന്നു (ഡിഫോൾട്ടായി സജ്ജമല്ല: അഭ്യർത്ഥനകളുടെ എണ്ണത്തിന് പരിധിയില്ല, താഴെയുള്ള കുറിപ്പ് കാണുക)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # മന്ദഗതിയിലുള്ള അപ്സ്ട്രീമുകൾക്കായി പരിമിതമായ കാത്തിരിപ്പ് RATE_LIMIT_MAX_WAIT_MS-ന്റെ ഡിഫോൾട്ടിനപ്പുറം ഉയർത്തുക
```

ഇവ OmniRoute പ്രോസസിന്റെ എൻവയൺമെന്റിൽ സജ്ജമാക്കുക (ഡീമൺ, ഉദാ. LaunchAgent plist അല്ലെങ്കിൽ `systemctl edit` വഴി), തുടർന്ന് OmniRoute പുനരാരംഭിക്കുക. റൊട്ടേഷൻ ഫ്ലാഗാണ് ഏറ്റവും കൂടുതൽ പ്രയോജനം നൽകുന്ന ഏക ക്രമീകരണം: ഇത് ഒരു പൂർണ്ണ പരാജയത്തെ പൂളിലുള്ള ആരോഗ്യകരമായ മറ്റൊരു പ്രൊവൈഡറിലേക്കുള്ള സുതാര്യമായ പുനഃശ്രമമാക്കി മാറ്റുന്നു.

**കുറിപ്പ്**: ഒരേസമയം പ്രവർത്തിക്കുന്ന ഹെവിവെയ്റ്റ് — ദീർഘ-കോൺടെക്സ്റ്റ് — അഭ്യർത്ഥനകളുടെ എണ്ണം `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` പരിമിതപ്പെടുത്തുന്നു; ഈ പരിധി ഒരു പ്രവേശന ഗേറ്റാണ്, പ്രൊവൈഡറുടെ നിരക്ക് പരിമിതപ്പെടുത്തൽ സംവിധാനമല്ല. **#503-fanout അപ്ഡേറ്റ്:** ഈ വേരിയബിൾ ഇനി ഡിഫോൾട്ടായി സജ്ജമാക്കപ്പെടുന്നില്ല (മുകളിൽ കാണിച്ചതുപോലെ വ്യക്തമായി കോൺഫിഗർ ചെയ്യുമ്പോൾ മാത്രമാണ് ഇപ്പോൾ ഇത് ബാധകമാകുന്നത്) — പകരം, ഹോസ്റ്റിന്റെ യഥാർത്ഥ മെമ്മറി പരിധിക്ക് അനുസരിച്ച് സ്വയം സ്കെയിൽ ചെയ്യുന്ന, സ്വയമേവ നിർണ്ണയിക്കപ്പെടുന്ന ബൈറ്റ് ബജറ്റ് (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ഉപയോഗിച്ചാണ് ഹെവിവെയ്റ്റ് പ്രവേശനം നിയന്ത്രിക്കുന്നത്. അതിനാൽ പുതുതായി ഡിപ്ലോയ് ചെയ്യുമ്പോൾ ഈ വേരിയബിൾ സജ്ജമാക്കാതെത്തന്നെ വളരെ കുറച്ച് `503 chat_admission_busy` നിരസിക്കലുകൾ മാത്രമേ കാണാൻ പാടുള്ളൂ; ഇവിടെ ഇത് വ്യക്തമായി സജ്ജമാക്കുന്നതും രേഖപ്പെടുത്തിയിരിക്കുന്നതുപോലെ തന്നെ പ്രവർത്തിക്കും. വ്യക്തമായി നൽകിയ ബൈറ്റ്-ബജറ്റ് ഓവർറൈഡുകൾ 8 MiB–2 GiB പരിധിയിലേക്ക് നിയന്ത്രിക്കപ്പെടുന്നു. ഒരു `413 body_exceeds_budget` താൽക്കാലികമല്ല: ആ ബൈറ്റ് ബജറ്റ് വർധിപ്പിക്കുക, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` കുറയ്ക്കുക, അല്ലെങ്കിൽ പ്രോസസിന്റെ മെമ്മറി പരിധി വർധിപ്പിക്കുക. `inflight_bytes_budget` മൂലമുള്ള ഒഴിവാക്കൽ താൽക്കാലികമായ വിഭവമത്സരമാണ്, അതിനാൽ വീണ്ടും ശ്രമിക്കാവുന്നതാണ്. ഓരോ പ്രൊവൈഡർക്കുമുള്ള നിരക്ക് പരിമിതപ്പെടുത്തൽ (`open-sse/services/rateLimitManager.ts`) `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, `RATE_LIMIT_AUTO_ENABLE` എന്നിവയാൽ പ്രത്യേകം നിയന്ത്രിക്കപ്പെടുന്നു — `.env.example` കാണുക.

**ഇത് പ്രവർത്തിച്ചുവെന്ന് എങ്ങനെ സ്ഥിരീകരിക്കാം**: നിങ്ങളുടെ agent/cron തുടർച്ചയായി രണ്ടുതവണ വേഗത്തിൽ പ്രവർത്തിപ്പിച്ച് രണ്ടും വിജയിക്കുന്നുവെന്ന് സ്ഥിരീകരിക്കുക. പരിഹാരത്തിന് മുമ്പ്, രണ്ടാമത്തെ പ്രവർത്തനം സാധാരണയായി `429`/`401` പിശക് നൽകും. പരിഹാരത്തിന് ശേഷം, പരാജയങ്ങൾ (ഉണ്ടെങ്കിൽ) ഉപയോക്താവിന് അറിയാതെ വീണ്ടും ശ്രമിക്കുകയും കോൾ പൂർത്തിയാകുകയും ചെയ്യും. നിങ്ങൾക്ക് `curl /monitoring/health` പ്രവർത്തിപ്പിച്ച് provider കണക്ഷനുകളിലെ `rateLimitedUntil` ഫീൽഡും ബാധിക്കപ്പെട്ട provider-കൾക്കായുള്ള `circuitBreakers.providerBreakers[].state`-ഉം നിരീക്ഷിക്കാം — state എന്നത് `CLOSED`, `DEGRADED`, `OPEN`, അല്ലെങ്കിൽ `HALF_OPEN` എന്നിവയിൽ ഒന്നായിരിക്കും (`src/shared/utils/circuitBreaker.ts` കാണുക). തുടർച്ചയായി പരാജയപ്പെടുന്ന ഒരു provider, reset window ഒരു probe കടത്തിവിടുന്നതിന് (`HALF_OPEN`) മുമ്പ് `CLOSED → DEGRADED → OPEN` എന്നിങ്ങനെ മാറും.

**നിങ്ങൾ ഇപ്പോഴും 429 കാണുന്നുവെങ്കിൽ**: ആ provider-ന്റെ സജീവ account അതിന്റെ _quota_ യഥാർഥത്തിൽ പൂർണ്ണമായി ഉപയോഗിച്ചുകഴിഞ്ഞിരിക്കുന്നു (rate മാത്രമല്ല). OmniRoute dashboard → Providers → Accounts എന്നതിൽ അതേ provider-നായി രണ്ടാമത്തെ account ചേർക്കുക, അല്ലെങ്കിൽ മറ്റൊരു സൗജന്യ provider (ഉദാ. `routeway`, `auggie`) കൂടി ഉൾപ്പെടുത്തുക. താൽക്കാലികമായ rate/400/401 പ്രശ്നങ്ങളിൽ മാത്രമേ rotation സഹായിക്കൂ; quota പൂർണ്ണമായി തീർന്ന സാഹചര്യത്തിൽ രണ്ടാമത്തെ credential അല്ലെങ്കിൽ മറ്റൊരു provider ആവശ്യമാണ്.

**vision model-കളിൽ (`auto/vision`, `bazaarlink/*`) 403 കാണുന്നുവെങ്കിൽ**: കണക്റ്റ് ചെയ്ത account-ന് vision ഉൾപ്പെടുന്ന paid plan ഇല്ല, അല്ലെങ്കിൽ API key-ക്ക് മതിയായ permissions ഇല്ല. key scope-ൽ vision/multimodal ഉൾപ്പെടുന്നുവെന്ന് provider dashboard-ൽ സ്ഥിരീകരിക്കുക, അല്ലെങ്കിൽ paid tier account കണക്റ്റ് ചെയ്ത് അതിനെ vision target ആയി നിലനിർത്തുക.

## npm install മുന്നറിയിപ്പുകൾ (ERESOLVE / peer / deprecated)

നിങ്ങൾ `npm install -g omniroute` പ്രവർത്തിപ്പിക്കുമ്പോൾ, `npm warn ERESOLVE`, peer-dependency അറിയിപ്പുകൾ, `deprecated` സന്ദേശങ്ങൾ എന്നിവ പോലുള്ള നിരവധി മുന്നറിയിപ്പുകൾ കണ്ടേക്കാം. **ഇവ പ്രതീക്ഷിക്കാവുന്നതും ദോഷകരമല്ലാത്തതുമാണ്.** ഔട്ട്പുട്ടിൽ `added <N> packages` കാണുന്നുവെങ്കിൽ ഇൻസ്റ്റാളേഷൻ വിജയിച്ചു.

peer-dependency പരിഹാര മുന്നറിയിപ്പുകൾ ഒഴിവാക്കാൻ, OmniRoute പിന്തുണയ്ക്കുന്ന ഇൻസ്റ്റാളേഷൻ രീതി ഉപയോഗിക്കുക:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps`, `ERESOLVE`, peer-dependency അറിയിപ്പുകൾ എന്നിവ മാത്രം ഒഴിവാക്കുന്നു. ഡിപ്രിക്കേഷൻ അറിയിപ്പുകൾ ട്രാൻസിറ്റീവ് മൂന്നാംകക്ഷി പാക്കേജുകളിൽ നിന്നുള്ളതിനാൽ അവ തുടർന്നും ദൃശ്യമാകും; ഇൻസ്റ്റാളേഷൻ പരാജയപ്പെട്ടുവെന്ന് അവ സൂചിപ്പിക്കുന്നില്ല.

OmniRoute-ന് നിയന്ത്രണമില്ലാത്ത മൂന്നാംകക്ഷി പാക്കേജുകളിലെ കാലഹരണപ്പെട്ട peer-dependency റേഞ്ചുകളാണ് ഈ മുന്നറിയിപ്പുകൾക്ക് കാരണം:

1. **`marked-terminal`-ന് `marked >=1 <16` വേണം, എന്നാൽ കണ്ടെത്തിയത് `marked@18` ആണ്** — പ്രായോഗികമായി ഇത് പ്രശ്നമില്ലാതെ പ്രവർത്തിക്കുന്നു; അപ്സ്ട്രീം peer റേഞ്ച് കാലഹരണപ്പെട്ടതാണ്.
2. **`deprecated prebuild-install@7.1.3`** — ഒരു ട്രാൻസിറ്റീവ് നേറ്റീവ്-ബൈനറി ഫെച്ച് ഹെൽപ്പർ. പിൻ ചെയ്ത `wreq-js` ട്രാൻസ്പോർട്ട് ബൈൻഡിങ് ഇൻസ്റ്റാൾ ചെയ്യാൻ ഇത്
   ഉപയോഗിക്കുന്നില്ല; web-cookie പ്രൊവൈഡർ ട്രാൻസ്പോർട്ട് സജ്ജീകരണം പരാജയപ്പെട്ടുവെന്നും ഇത് സൂചിപ്പിക്കുന്നില്ല.

**നടപടിയൊന്നും ആവശ്യമില്ല** — അപ്സ്ട്രീം പാക്കേജുകൾ ഫോർക്ക് ചെയ്യാതെ ഈ മുന്നറിയിപ്പുകൾ പൂർണ്ണമായും നിശ്ശബ്ദമാക്കാനാകില്ല.

## npm install-scripts തടഞ്ഞതിനെക്കുറിച്ചുള്ള മുന്നറിയിപ്പ് (ഗ്ലോബൽ ഇൻസ്റ്റാൾ)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` പ്രവർത്തിപ്പിക്കുമ്പോൾ, പുതിയ npm പതിപ്പുകൾ (v11+ ഉം v12+ ഉം) ഡിഫോൾട്ടായി പാക്കേജ് ലൈഫ്സൈക്കിൾ സ്ക്രിപ്റ്റുകൾ തടയുകയും install-scripts മുന്നറിയിപ്പ് പ്രദർശിപ്പിക്കുകയും ചെയ്യുന്നു:

```
npm warn install-scripts 7 പാക്കേജുകളുടെ ഇൻസ്റ്റാൾ സ്ക്രിപ്റ്റുകൾ allowScripts-ൽ ഉൾപ്പെടാത്തതിനാൽ തടഞ്ഞു:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### ഈ മുന്നറിയിപ്പ് അവഗണിക്കാമോ?

**ഭാഗികമായി അവഗണിക്കാം, എന്നാൽ സ്ക്രിപ്റ്റുകളില്ലാതെ പ്രവർത്തിപ്പിക്കുന്നത് ശുപാർശ ചെയ്യുന്നില്ല.** OmniRoute-ൽ പരാജയം മാന്യമായി കൈകാര്യം ചെയ്യുന്ന ഫാൾബാക്കുകൾ ഉൾപ്പെടുന്നു: സ്റ്റാൻഡ്എലോൺ ബണ്ടിലിൽ നിന്ന് നേറ്റീവ് `better-sqlite3` ബൈൻഡിങ്ങുകൾ ലോഡ് ചെയ്യാൻ കഴിയുന്നില്ലെങ്കിൽ, ആപ്ലിക്കേഷൻ `node:sqlite` അല്ലെങ്കിൽ `sql.js` പോലുള്ള ഇതര ഡ്രൈവറുകളിലേക്ക് ഫാൾബാക്ക് ചെയ്യും ([SQLite റൺടൈം റെസല്യൂഷൻ](../ops/SQLITE_RUNTIME.md) കാണുക). സെർവർ തുടർന്നും ആരംഭിക്കും, എന്നാൽ `sql.js` പോലുള്ള WASM ഫാൾബാക്കുകളിൽ പ്രവർത്തിപ്പിക്കുന്നത് SQLite WAL (Write-Ahead Logging) മോഡ് പ്രവർത്തനരഹിതമാക്കുകയും മെമ്മറി, ഡിസ്ക്-സിങ്ക് ഓവർഹെഡ് വർധിപ്പിക്കുകയും ചെയ്യും.

### യഥാർത്ഥത്തിൽ ആവശ്യമായ സ്ക്രിപ്റ്റുകൾ ഏതെല്ലാമാണ്?

തടഞ്ഞ എല്ലാ സ്ക്രിപ്റ്റുകളും OmniRoute പ്രവർത്തിപ്പിക്കുന്നതിന് അനിവാര്യമല്ല:

- **അനിവാര്യം (`omniroute`, `better-sqlite3`):** OmniRoute ഒരു Next.js സ്റ്റാൻഡ്എലോൺ ആപ്ലിക്കേഷൻ ബണ്ടിലിൽ (`dist/`) നിന്നാണ് പ്രവർത്തിക്കുന്നത്. ഇൻസ്റ്റാളേഷൻ സമയത്ത്, npm ടോപ്പ്-ലെവൽ `node_modules/better-sqlite3/`-ലേക്ക് ഹോസ്റ്റിന് അനുയോജ്യമായ നേറ്റീവ് SQLite ഡ്രൈവർ ഡൗൺലോഡ് ചെയ്യുകയോ കംപൈൽ ചെയ്യുകയോ ചെയ്യുന്നു. തുടർന്ന് OmniRoute-ന്റെ `postinstall` സ്ക്രിപ്റ്റ് (`scripts/build/postinstall.mjs`) ഈ ഹോസ്റ്റിന് അനുയോജ്യമായ ബൈനറികൾ പരിശോധിച്ച് `dist/node_modules/`-ലേക്ക് പകർത്തുന്നു, അതുവഴി സ്റ്റാൻഡ്എലോൺ സെർവറിന് അവ ആക്സസ് ചെയ്യാനാകും. `omniroute`-ന്റെ postinstall സ്ക്രിപ്റ്റ് തടഞ്ഞാൽ, ഈ പകർത്തൽ ഘട്ടം ഒഴിവാക്കപ്പെടും.
- **ഐച്ഛികം/ട്രാൻസിറ്റീവ് (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** ഇവ ബിൽഡ് ഹെൽപ്പറുകൾ, വാച്ചർ ടൂളുകൾ, അല്ലെങ്കിൽ സിസ്റ്റം കീചെയിൻ യൂട്ടിലിറ്റികൾ എന്നിവയാണ്. ഇവ അനുവദിക്കുന്നത് ബിൽഡ് മുന്നറിയിപ്പുകൾ ഒഴിവാക്കുന്നു, എന്നാൽ കോർ റൂട്ടിങ് പ്രവർത്തനത്തിന് ഇവ ആവശ്യമില്ല.
- **ഒഴിവാക്കിയത് (`onnxruntime-node`):** ലോക്കൽ AI എംബെഡ്ഡിങ്ങുകൾക്കുള്ള ഒരു ഐച്ഛിക dependency ആണിത്; OmniRoute പ്രവർത്തിക്കാൻ ഇത് **ആവശ്യമില്ല**. ഇതിന്റെ postinstall സ്ക്രിപ്റ്റ് NuGet-ൽ നിന്ന് ഏകദേശം 300MB CUDA അസറ്റുകൾ ഡൗൺലോഡ് ചെയ്യുന്നു; പിന്തുണയ്ക്കുന്ന ഹാർഡ്വെയറിൽ ലോക്കൽ ONNX ആക്സിലറേഷൻ ഉപയോഗിക്കാൻ നിങ്ങൾ വ്യക്തമായി ഉദ്ദേശിക്കുന്നില്ലെങ്കിൽ ഇതിനെ allow-list-ൽ ഉൾപ്പെടുത്തരുത്.

### ശുപാർശ ചെയ്യുന്ന പരിഹാരം

ഗ്ലോബൽ ഇൻസ്റ്റാളേഷൻ സമയത്ത് ആവശ്യമായ ഇൻസ്റ്റാൾ സ്ക്രിപ്റ്റുകൾ അനുവദിക്കാനും മുന്നറിയിപ്പുകൾ ഒഴിവാക്കാനും, OmniRoute-നും അതിന്റെ നേറ്റീവ് dependency-കൾക്കുമായി `--allow-scripts` നൽകുക:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

പകരമായി, നിങ്ങളുടെ ഉപയോക്തൃ അക്കൗണ്ടിലെ എല്ലാ ഗ്ലോബൽ ഇൻസ്റ്റാളേഷനുകൾക്കുമായി ഇത് സ്ഥിരമായി കോൺഫിഗർ ചെയ്യാൻ:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### നിങ്ങളുടെ ഇൻസ്റ്റാളേഷൻ പരിശോധിക്കുക

ഇൻസ്റ്റാളേഷനുശേഷം, നേറ്റീവ് ബൈൻഡിങ്ങുകളും റൺടൈം എൻവയോൺമെന്റും ശരിയായ നിലയിലാണെന്ന് ഉറപ്പാക്കാൻ ബിൽറ്റ്-ഇൻ ഡയഗ്നോസ്റ്റിക് ടൂൾ പ്രവർത്തിപ്പിക്കുക:

```bash
omniroute doctor
```

## Gemini Web-ഉം Playwright Chromium-ഉം

ഒരു Gemini Web അഭ്യർത്ഥനയിൽ Playwright Chromium ഇൻസ്റ്റാൾ ചെയ്തിട്ടില്ലെന്ന സന്ദേശത്തോടൊപ്പം `503` ലഭിക്കുകയാണെങ്കിൽ, npm പാക്കേജ് നിലവിലുണ്ടെങ്കിലും ബ്രൗസർ ബൈനറി ലഭ്യമല്ലെന്നാണ് അർത്ഥം.
Playwright മനഃപൂർവം ബ്രൗസർ ഡൗൺലോഡുകളെ npm പാക്കേജ് ഇൻസ്റ്റാളേഷനിൽനിന്ന് വേർതിരിച്ചാണ് സൂക്ഷിക്കുന്നത്, അതിനാൽ ബ്രൗസർ ഇൻസ്റ്റാൾ ചെയ്യുന്നതുവരെ ഈ പ്രതികരണം പ്രതീക്ഷിക്കാവുന്നതാണ്.

ആഗോള npm ഇൻസ്റ്റാളേഷനായി, ബ്രൗസർ കാഷ് അതേ Playwright ഇൻസ്റ്റാളേഷന്റെ ഭാഗമാകുന്നതിനായി OmniRoute പാക്കേജിന്റെ ഡയറക്ടറിയിൽനിന്ന് Chromium ഇൻസ്റ്റാൾ ചെയ്യുക:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ഇൻസ്റ്റാളേഷനുശേഷം OmniRoute പുനരാരംഭിച്ച് Gemini Web അഭ്യർത്ഥന വീണ്ടും ശ്രമിക്കുക. നിങ്ങൾ ഒരു Docker ഇമേജിൽനിന്നാണ് OmniRoute പ്രവർത്തിപ്പിക്കുന്നതെങ്കിൽ, Chromium-ഉം അതിന്റെ ഡിപെൻഡൻസികളും ഉൾക്കൊള്ളുന്ന `-web` ഇമേജ് (അല്ലെങ്കിൽ `runner-web` ബിൽഡ് ടാർഗറ്റ്) ഉപയോഗിക്കുക; അടിസ്ഥാന ഇമേജിൽ അവ ഉൾപ്പെട്ടിട്ടില്ല.

## ആന്റിവൈറസിലെ തെറ്റായ തിരിച്ചറിയലുകൾ

<a name="antivirus-false-positives"></a>

### Avast/AVG, `README.md`-നെ `MD:HttpRequest-inf[Susp]` ആയി ക്വാറന്റൈൻ ചെയ്യുന്നു

**ഇത് തെറ്റായ തിരിച്ചറിയലാണ്. ഒന്നിലും അണുബാധയില്ല, യാതൊരു നടപടിയും ആവശ്യമില്ല.**

നിരവധി HTTP അഭ്യർത്ഥനകളെപ്പോലെ തോന്നിക്കുന്ന ലിങ്കുകൾ അടങ്ങിയ പ്ലെയിൻ-ടെക്സ്റ്റ്/Markdown ഫയലുകളെ ഫ്ലാഗ് ചെയ്യുന്ന ഒരു ഹ്യൂറിസ്റ്റിക് Avast-ഉം AVG-യും പ്രവർത്തിപ്പിക്കുന്നു. OmniRoute-ന്റെ `README.md`, npm പാക്കേജിനുള്ളിൽ ഉൾപ്പെടുത്തിയിട്ടുള്ളതാണ് (അത് `package.json` → `files` എന്നതിൽ പട്ടികപ്പെടുത്തിയിരിക്കുന്നു); അതിനാൽ ഒരു ഗ്ലോബൽ ഇൻസ്റ്റാളിൽ അത് `node_modules/omniroute/README.md` എന്നിടത്ത് എത്തുന്നു — കൂടാതെ അതിൽ ഏകദേശം 15 `http://localhost:20128/...` ഉദാഹരണങ്ങളുണ്ട് (MCP HTTP/SSE എൻഡ്പോയിന്റുകൾ, A2A `.well-known` URL, `curl` സ്നിപ്പറ്റുകൾ എന്നിവ). ലിങ്കുകളുടെ ഈ സാന്ദ്രത ഹ്യൂറിസ്റ്റിക് പ്രവർത്തനക്ഷമമാകാൻ മതിയാകും.

ഇത് അടുത്തിടെയാണ് ആരംഭിച്ചതെങ്കിൽ: ഫയലിന്റെ സ്വഭാവത്തിൽ മാറ്റമൊന്നും വന്നിട്ടില്ല. README-യിലെ എൻഡ്പോയിന്റ് പട്ടിക വികസിക്കുകയും (MCP HTTP + SSE + A2A ചേർത്തു) കൂടുതൽ `curl` ഉദാഹരണങ്ങൾ ഉൾപ്പെടുത്തുകയും ചെയ്തതിനാൽ അത് പരിധി കടന്നു.

ഈ ഫയൽ പ്രവർത്തിപ്പിക്കാനാകുന്ന ഉള്ളടക്കമൊന്നുമില്ലാത്ത നിഷ്ക്രിയ ഡോക്യുമെന്റേഷനാണ്. ക്വാറന്റൈനിൽ നിന്ന് ഇത് സുരക്ഷിതമായി പുനഃസ്ഥാപിക്കാം.

**ചെയ്യേണ്ടത്:**

1. **അറിയിപ്പുകൾ നിർത്തുക** — നിങ്ങളുടെ ആന്റിവൈറസിൽ ഇൻസ്റ്റാൾ ഡയറക്ടറി ഒഴിവാക്കുക
   (Avast: Settings → Exceptions); നിങ്ങളുടെ ഗ്ലോബൽ `node_modules` പാതയും കൂടാതെ/അല്ലെങ്കിൽ
   OmniRoute ഡാറ്റാ ഡയറക്ടറിയും (`~/.omniroute/`) ചേർക്കുക.
2. **തെറ്റായ തിരിച്ചറിയൽ റിപ്പോർട്ട് ചെയ്യുക** — <https://www.avast.com/false-positive-file-form.php>,
   ക്വാറന്റൈൻ ചെയ്ത `README.md` അറ്റാച്ച് ചെയ്യുക. ഒരു ടെക്സ്റ്റ് ഫയലിനോട് വെണ്ടർ ഹ്യൂറിസ്റ്റിക്
   അമിതമായി പ്രതികരിക്കുന്നതാണ് പ്രശ്നമെന്നതിനാൽ, എല്ലാവർക്കും സഹായകരമാകുന്ന പരിഹാരം ഇതാണ്.

**ഞങ്ങളുടെ ഭാഗത്ത് ഇത് "പരിഹരിക്കാത്തത്" എന്തുകൊണ്ട്:** എല്ലാ ഉദാഹരണങ്ങളും `http://localhost` ആണ്;
സ്വയം ഒപ്പിട്ട സർട്ടിഫിക്കറ്റുകൾ മൂലമുള്ള ബുദ്ധിമുട്ടുകളില്ലാതെ localhost-ന് `https` ഉപയോഗിക്കാനാവില്ല.
ഒരു വെണ്ടറുടെ ഹ്യൂറിസ്റ്റിക്കിൽ നിന്ന് ഒഴിഞ്ഞുമാറാൻ ഡോക്യുമെന്റേഷൻ വികലമാക്കുന്നത് ഒരു സ്കാനർ ബഗിനെ
തൃപ്തിപ്പെടുത്താനായി എല്ലാ വായനക്കാർക്കും ബുദ്ധിമുട്ടുണ്ടാക്കും.

### Kaspersky, Desktop ആപ്പിനെ `PDM:Trojan.Win32.Generic` ആയി ഫ്ലാഗ് ചെയ്യുന്നു

**ഇത് പെരുമാറ്റാധിഷ്ഠിത ഹ്യൂറിസ്റ്റിക് മൂലമുള്ള തെറ്റായ തിരിച്ചറിയലാണ്. ഒന്നിലും അണുബാധയില്ല.**
Kaspersky-യുടെ `PDM:` പ്രിഫിക്സ് അർത്ഥമാക്കുന്നത്, അറിയപ്പെടുന്ന മാൽവെയറുമായി പൊരുത്തപ്പെടുത്തുന്നതിനു
പകരം ഇൻസ്റ്റാളർ _ചെയ്യുന്ന കാര്യങ്ങൾ_ വിലയിരുത്തുന്ന അതിന്റെ Proactive Defense Module (System Watcher)-ൽ
നിന്നാണ് ഈ വിധി വരുന്നത് എന്നാണ്. ഇത് പ്രവർത്തനക്ഷമമാകുമ്പോൾ, Kaspersky മുഴുവൻ ഇൻസ്റ്റാളേഷനും
"റോൾ ബാക്ക്" ചെയ്യുന്നു — ഇതിനകം എഴുതിയ ഫയലുകൾ ഇല്ലാതാക്കുന്നു — അതിനാൽ ആപ്പ് തകരാറിലാവുകയോ
അപ്രത്യക്ഷമാവുകയോ ചെയ്യും.

അത് ഫ്ലാഗ് ചെയ്യുന്ന ഫയലുകൾ Desktop ആപ്പിനൊപ്പം ബണ്ടിൽ ചെയ്തിട്ടുള്ള, പ്രഖ്യാപിത ഓപ്പൺ സോഴ്സ്
ഡിപെൻഡൻസികളുടെ സാധാരണ ഘടകങ്ങളാണ്, ഉദാഹരണത്തിന്:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js`,
  `workerProcessEntry.js` എന്നിവ — ആപ്പിനുള്ളിലെ പ്രൊവൈഡർ ലോഗിനിനും ബ്രൗസർ അധിഷ്ഠിത ചാറ്റിനും
  ഉപയോഗിക്കുന്ന ബ്രൗസർ ഓട്ടോമേഷൻ ലൈബ്രറിയായ [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — വെബ്-കുക്കി പ്രൊവൈഡറുകളിൽ ബ്രൗസർ-ഫിംഗർപ്രിന്റ് ചെയ്ത HTTP-ക്കായി ഉപയോഗിക്കുന്ന പിൻ ചെയ്ത
  `wreq-js` നേറ്റീവ് ബൈൻഡിങ് (`<arch>` എന്നത് `x64` അല്ലെങ്കിൽ `arm64` ആണ്).

**ഇത് പ്രവർത്തനക്ഷമമാകുന്നത് എന്തുകൊണ്ട്:** Windows ഇൻസ്റ്റാളർ **ഇതുവരെ കോഡ്-സൈൻ ചെയ്തിട്ടില്ല**;
അതിനാൽ ഒപ്പിടാത്ത NSIS ഇൻസ്റ്റാളറിന് യാതൊരു വിശ്വാസ്യതാ ചരിത്രവുമില്ല, കൂടാതെ പെരുമാറ്റാധിഷ്ഠിത
ഹ്യൂറിസ്റ്റിക്കുകൾ പരമാവധി കടുപ്പത്തിൽ പ്രവർത്തിക്കുന്നു. ബണ്ടിൽ ചെയ്ത ഒരു നേറ്റീവ് DLL-ഉം
`%LOCALAPPDATA%\Programs\OmniRoute`-ന് കീഴിൽ എഴുതപ്പെടുന്ന നൂറുകണക്കിന് `.js` ഫയലുകളും
(Next.js സ്റ്റാൻഡ്അലോൺ ബിൽഡിൽ നിന്നുള്ള ഹാഷ്-സഫിക്സുള്ള പാക്കേജ് ഡയറക്ടറികൾ ഉൾപ്പെടെ)
കൂടിച്ചേരുമ്പോൾ, ഹ്യൂറിസ്റ്റിക് പ്രവർത്തനക്ഷമമാകാൻ അത് മതിയാകും. കോഡ് സൈനിങ് ആസൂത്രണം ചെയ്തിട്ടുണ്ട്;
അത് നടപ്പിലാകുന്നതുവരെ പുതിയ റിലീസുകളിലും ഇത് ആവർത്തിക്കാം.

**ചെയ്യേണ്ടത്:**

1. **ആദ്യം നിങ്ങളുടെ ഡൗൺലോഡ് പരിശോധിക്കുക** (ഫയലിൽ കൃത്രിമം നടന്നിട്ടില്ലെന്ന് ഉറപ്പാക്കാൻ).
   ഓരോ റിലീസും `latest.yml` പ്രസിദ്ധീകരിക്കുന്നു; അതിലെ `sha512` ഫീൽഡ് (base64)
   `OmniRoute.Setup.<version>.exe` ഇൻസ്റ്റാളറിനെ ഉൾക്കൊള്ളുന്നു. PowerShell-ൽ, ഇൻസ്റ്റാളർ അടങ്ങിയ
   ഫോൾഡറിൽ നിന്ന്:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ഔട്ട്പുട്ട് `latest.yml` → `sha512` എന്നതുമായി പൊരുത്തപ്പെടണം. പൊരുത്തപ്പെടുന്നില്ലെങ്കിൽ ഫയൽ
   ഇല്ലാതാക്കി [GitHub റിലീസ് പേജിൽ](https://github.com/diegosouzapw/OmniRoute/releases) നിന്ന്
   മാത്രം വീണ്ടും ഡൗൺലോഡ് ചെയ്യുക.
2. **പുനഃസ്ഥാപിക്കുക + ഒഴിവാക്കുക** — റോൾ ബാക്ക് ചെയ്ത ഇനങ്ങൾ ക്വാറന്റൈനിൽ നിന്ന് പുനഃസ്ഥാപിച്ച്
   `%LOCALAPPDATA%\Programs\OmniRoute`-ന് ഒരു ഒഴിവാക്കൽ ചേർക്കുക (Kaspersky → Settings → Threats and Exclusions),
   തുടർന്ന് വീണ്ടും ഇൻസ്റ്റാൾ ചെയ്യുക.
3. **തെറ്റായ തിരിച്ചറിയൽ റിപ്പോർട്ട് ചെയ്യുക** — <https://opentip.kaspersky.com/>. ഉപയോക്താക്കൾ
   സമർപ്പിക്കുന്ന തെറ്റായ തിരിച്ചറിയൽ റിപ്പോർട്ടുകൾ allowlisting യഥാർഥത്തിൽ വേഗത്തിലാക്കുന്നു.

**കാരണം:** OmniRoute അംഗീകരിച്ച സുരക്ഷിത റൺടൈം പരിധിക്ക് പുറത്തുള്ള ഒരു Node.js പതിപ്പാണ് നിങ്ങൾ പ്രവർത്തിപ്പിക്കുന്നത്. OmniRoute ആവശ്യപ്പെടുന്ന സുരക്ഷാ പാച്ച് പരിധിയേക്കാൾ താഴെയുള്ള പഴയ Node 22 അല്ലെങ്കിൽ 24 പാച്ച് ലെവൽ പ്രവർത്തിപ്പിക്കുന്നതാണ് ഏറ്റവും സാധാരണമായ സാഹചര്യം.

**ലക്ഷണങ്ങൾ:**

- ലോഗിൻ പേജിൽ ശൂന്യമായ സ്ക്രീനോ സെർവർ പിശകോ കാണിക്കുന്നു
- കൺസോളിൽ `Error: Module did not self-register` അല്ലെങ്കിൽ സമാനമായ നേറ്റീവ് ബൈൻഡിംഗ് പിശകുകൾ കാണിക്കുന്നു
- റൺടൈം പിന്തുണയ്ക്കുന്ന സുരക്ഷാ നയത്തിന് പുറത്താണെങ്കിൽ, ലോഗിൻ പേജിൽ നിങ്ങളുടെ Node പതിപ്പിനൊപ്പം ഒരു **ഓറഞ്ച് മുന്നറിയിപ്പ് ബാനർ** കാണിക്കുന്നു

**പരിഹാരം:**

1. പിന്തുണയ്ക്കുന്ന ഒരു Node.js LTS റിലീസ് ഇൻസ്റ്റാൾ ചെയ്യുക (ശുപാർശ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. നിങ്ങളുടെ പതിപ്പ് പരിശോധിക്കുക: `node --version`, 24.x LTS ശ്രേണിയിൽ `v24.0.0` അല്ലെങ്കിൽ അതിലും പുതിയ പതിപ്പ് കാണിക്കണം
3. OmniRoute വീണ്ടും ഇൻസ്റ്റാൾ ചെയ്യുക: `npm install -g omniroute`
4. പുനരാരംഭിക്കുക: `omniroute`

> **പിന്തുണയ്ക്കുന്ന സുരക്ഷിത പതിപ്പുകൾ:** `>=22.22.2 <23` അല്ലെങ്കിൽ `>=24.0.0 <27`. Node.js 24.x LTS (Krypton), Node.js 26 എന്നിവയ്ക്ക് പൂർണ്ണ പിന്തുണയുണ്ട്.

### npm v11+: `better-sqlite3` ഇൻസ്റ്റാൾ ചെയ്തിട്ടില്ല (മൊഡ്യൂൾ കണ്ടെത്താനാകുന്നില്ല)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**കാരണം:** Node.js 24+-നൊപ്പം ലഭിക്കുന്ന npm v11, ഐച്ഛിക
ഡിപെൻഡൻസികൾക്കായുള്ള ഇൻസ്റ്റാൾ സ്ക്രിപ്റ്റുകൾ ഡിഫോൾട്ടായി തടയുന്നു. `better-sqlite3`, `optionalDependencies`-ൽ
ലിസ്റ്റ് ചെയ്തിരിക്കുന്നതിനാലും നേറ്റീവ് കംപൈലേഷൻ (`node-gyp rebuild`) ആവശ്യമായതിനാലും npm അറിയിപ്പൊന്നും നൽകാതെ അത് ഒഴിവാക്കുന്നു.

**ലക്ഷണങ്ങൾ:**

- ആരംഭിക്കുമ്പോൾ `Cannot find module 'better-sqlite3'` എന്ന പിശകോടെ സെർവർ ക്രാഷാകുന്നു
- `ls node_modules/better-sqlite3`, "No such file or directory" എന്ന് കാണിക്കുന്നു
- `npm ls better-sqlite3`, `(empty)` എന്ന് കാണിക്കുന്നു

**പരിഹാരം:**

1. ഇൻസ്റ്റാൾ സ്ക്രിപ്റ്റുകൾ അംഗീകരിച്ച് വീണ്ടും ഇൻസ്റ്റാൾ ചെയ്യുക:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. അല്ലെങ്കിൽ മുൻകൂട്ടി ബിൽഡ് ചെയ്ത പാക്കേജ് നേരിട്ട് ഇൻസ്റ്റാൾ ചെയ്യുക:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ഇത് പ്രവർത്തിക്കുന്നുണ്ടെന്ന് പരിശോധിക്കുക: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**കാരണം:** ആഗോളതലത്തിലുള്ള `npm install -g omniroute` ഇൻസ്റ്റാളേഷനുശേഷം, പാക്കേജിനുള്ളിലെ `better-sqlite3` നേറ്റീവ് ബൈനറി പ്രാദേശികമായി പ്രവർത്തിക്കുന്നതിൽനിന്ന് വ്യത്യസ്തമായ ഒരു ആർക്കിടെക്ചറിനോ Node.js ABI-ക്കോ വേണ്ടി കംപൈൽ ചെയ്തതായിരിക്കാം. മുൻകൂട്ടി ബിൽഡ് ചെയ്ത ബൈനറി നിങ്ങളുടെ പരിതസ്ഥിതിയുമായി പൊരുത്തപ്പെടാത്തപ്പോൾ, macOS-ൽ (Apple Silicon, Intel എന്നിവയിൽ) ഇത് സാധാരണമാണ്.

**ലക്ഷണങ്ങൾ:**

- ആരംഭിക്കുമ്പോൾ തന്നെ `dlopen` പിശകോടെ സെർവർ പരാജയപ്പെടുന്നു
- പിശകിൽ `slice is not valid mach-o file` ഉൾപ്പെടുന്നു
- പൂർണ്ണ ഉദാഹരണം:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**പരിഹാരം — നിങ്ങളുടെ പ്രാദേശിക പരിതസ്ഥിതിക്കായി വീണ്ടും ബിൽഡ് ചെയ്യുക (Node.js ഡൗൺഗ്രേഡ് ആവശ്യമില്ല):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **കുറിപ്പ്:** ഇത് നിങ്ങളുടെ പ്രാദേശിക Node.js പതിപ്പിനും CPU ആർക്കിടെക്ചറിനും അനുസൃതമായി നേറ്റീവ് ബൈൻഡിംഗ് വീണ്ടും കംപൈൽ ചെയ്ത് ബൈനറി പൊരുത്തക്കേട് പരിഹരിക്കുന്നു. ഔദ്യോഗികമായി പിന്തുണയ്ക്കുന്ന റൺടൈം പരിധി **`>=22.22.2 <23` അല്ലെങ്കിൽ `>=24.0.0 <27`** ആണ് (`src/shared/utils/nodeRuntimeSupport.ts`-ലെ `SUPPORTED_NODE_RANGE`, `package.json`-ലെ `engines` ഫീൽഡുമായി വിന്യസിച്ചിരിക്കുന്നു). `better-sqlite3` v12.x ഉപയോഗിച്ച് Node.js 24.x LTS (Krypton), Node.js 26 എന്നിവയ്ക്ക് പൂർണ്ണ പിന്തുണയുണ്ട്.

## പ്രോക്സി പ്രശ്നങ്ങൾ

### പ്രൊവൈഡർ സാധൂകരണത്തിൽ "fetch failed" കാണിക്കുന്നു

**കാരണം:** API കീ സാധൂകരണ എൻഡ്പോയിന്റ് (`POST /api/providers/validate`) മുമ്പ് പ്രോക്സി കോൺഫിഗറേഷൻ മറികടന്നിരുന്നതിനാൽ, പ്രോക്സി റൂട്ടിംഗ് ആവശ്യമായ എൻവയോൺമെന്റുകളിൽ പരാജയങ്ങൾ സംഭവിച്ചിരുന്നു.

**പരിഹാരം (v3.5.5+):** ഇത് ഇപ്പോൾ പരിഹരിച്ചിട്ടുണ്ട്. പ്രൊവൈഡർ തലത്തിലെയും ഗ്ലോബൽ തലത്തിലെയും പ്രോക്സി ക്രമീകരണങ്ങൾ സ്വയമേവ പാലിച്ചുകൊണ്ട്, പ്രൊവൈഡർ സാധൂകരണ അഭ്യർത്ഥനകൾ ഇപ്പോൾ `runWithProxyContext` വഴി റൂട്ട് ചെയ്യുന്നു.

### ടോക്കൺ ഹെൽത്ത് ചെക്ക് "fetch failed" എന്ന പിശകോടെ പരാജയപ്പെടുന്നു

**കാരണം:** പശ്ചാത്തല OAuth ടോക്കൺ പുതുക്കൽ ഓരോ കണക്ഷനുമുള്ള പ്രോക്സി കോൺഫിഗറേഷൻ പ്രത്യേകം റിസോൾവ് ചെയ്തിരുന്നില്ല.

**പരിഹാരം (v3.5.5+):** പുതുക്കാൻ ശ്രമിക്കുന്നതിനുമുമ്പ് ടോക്കൺ ഹെൽത്ത് ചെക്ക് ഷെഡ്യൂളർ ഇപ്പോൾ ഓരോ കണക്ഷനുമുള്ള പ്രോക്സി കോൺഫിഗറേഷൻ റിസോൾവ് ചെയ്യുന്നു. v3.5.5+ ലേക്ക് അപ്ഡേറ്റ് ചെയ്യുക.

### SOCKS5 പ്രോക്സി "invalid onRequestStart method" എന്ന് നൽകുന്നു

**കാരണം:** Node.js 22-ൽ, undici@8 ഡിസ്പാച്ചർ Node-ന്റെ ബിൽറ്റ്-ഇൻ `fetch()` ഇംപ്ലിമെന്റേഷനുമായി പൊരുത്തപ്പെടുന്നില്ല.

**പരിഹാരം (v3.5.5+):** ഒരു പ്രോക്സി ഡിസ്പാച്ചർ സജീവമായിരിക്കുമ്പോൾ OmniRoute ഇപ്പോൾ undici-യുടെ സ്വന്തം `fetch()` ഫങ്ഷൻ ഉപയോഗിക്കുന്നു; ഇത് സ്ഥിരതയുള്ള പ്രവർത്തനം ഉറപ്പാക്കുന്നു. v3.5.5+ ലേക്ക് അപ്ഡേറ്റ് ചെയ്യുക.

### WSL-ന് കീഴിലുള്ള MITM പ്രോക്സി: Windows ഹോസ്റ്റിലെ ഡെസ്ക്ടോപ്പ് ആപ്പുകൾ ഇന്റർസെപ്റ്റ് ചെയ്യപ്പെടുന്നില്ല

**കാരണം:** MITM പ്രോക്സിയും അതിന്റെ CA സർട്ടിഫിക്കറ്റും OmniRoute പ്രവർത്തിക്കുന്ന എൻവയോൺമെന്റിലാണ് ഇൻസ്റ്റാൾ ചെയ്യപ്പെടുന്നത്. WSL-ന് കീഴിൽ ആ എൻവയോൺമെന്റ് Linux ഗസ്റ്റ് ആണ്, അതേസമയം AI ഡെസ്ക്ടോപ്പ് ആപ്പുകൾ (Kiro, Trae, Copilot, Zed, …) Windows ഹോസ്റ്റിലാണ് പ്രവർത്തിക്കുന്നത്. ഹോസ്റ്റ് ആപ്പുകൾ ഗസ്റ്റിന്റെ സർട്ടിഫിക്കറ്റ് സ്റ്റോറിനെ വിശ്വസിക്കുന്നില്ല, കൂടാതെ ഗസ്റ്റിന്റെ സിസ്റ്റം പ്രോക്സിയിലൂടെ റൂട്ട് ചെയ്യുകയുമില്ല; അതിനാൽ അവിടെ ഡെസ്ക്ടോപ്പ് ഇന്റർസെപ്ഷൻ പ്രവർത്തിക്കില്ല.

**ശുപാർശ:** നിങ്ങൾ ഇന്റർസെപ്റ്റ് ചെയ്യാൻ ആഗ്രഹിക്കുന്ന ഡെസ്ക്ടോപ്പ് ആപ്പുകൾ പ്രവർത്തിക്കുന്ന അതേ OS-ൽ OmniRoute നേറ്റീവായി പ്രവർത്തിപ്പിക്കുക (Windows ആപ്പുകൾക്ക് Windows; macOS/Linux-നും അതുപോലെ). ഹോസ്റ്റ് ആപ്പുകളെ ലക്ഷ്യമിടുമ്പോൾ OmniRoute-നെ WSL-നുള്ളിൽ നിലനിർത്തുന്നതിന്, ജനറേറ്റ് ചെയ്ത CA സർട്ടിഫിക്കറ്റ് Windows ഹോസ്റ്റിൽ മാനുവലായി വിശ്വസനീയമാക്കുകയും ഓരോ ഹോസ്റ്റ് ആപ്പിന്റെയും നെറ്റ്വർക്ക്/പ്രോക്സി ക്രമീകരണങ്ങൾ WSL പ്രോക്സി എൻഡ്പോയിന്റിലേക്ക് ചൂണ്ടുകയും വേണം — ഇത് പിന്തുണയ്ക്കാത്തതും എളുപ്പത്തിൽ തകരാവുന്നതുമായ ഒരു സജ്ജീകരണമാണ്.

### നിരക്ക് പരിമിതപ്പെടുത്തൽ

**കാരണം:** സബ്സ്ക്രിപ്ഷൻ ക്വോട്ട തീർന്നിരിക്കുന്നു.

**പരിഹാരം:**

രണ്ട് അക്കൗണ്ടുകൾ ഒരേ രജിസ്റ്റർ ചെയ്ത ക്ലയന്റ് പങ്കിടുമ്പോൾ (v3.8.0-ന് മുമ്പ് ഇംപോർട്ട് ചെയ്ത കണക്ഷനുകൾ),
ഒരു അക്കൗണ്ടിന്റെ ടോക്കൺ പുതുക്കുന്നത് മറ്റേതിന്റെ റിഫ്രഷ് ടോക്കൺ അസാധുവാക്കുന്നു.

## ക്ലൗഡ് പ്രശ്നങ്ങൾ

### ക്ലൗഡ് സിങ്ക് പിശകുകൾ

1. `BASE_URL` പ്രവർത്തിച്ചുകൊണ്ടിരിക്കുന്ന നിങ്ങളുടെ ഇൻസ്റ്റൻസിലേക്കാണ് വിരൽചൂണ്ടുന്നതെന്ന് ഉറപ്പാക്കുക (ഉദാ., `http://localhost:20128`)
2. `CLOUD_URL` നിങ്ങളുടെ ക്ലൗഡ് എൻഡ്പോയിന്റിലേക്കാണ് വിരൽചൂണ്ടുന്നതെന്ന് ഉറപ്പാക്കുക (ഉദാ., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` മൂല്യങ്ങൾ സെർവർ-സൈഡ് മൂല്യങ്ങളുമായി ഒത്തുപോകുന്നുവെന്ന് ഉറപ്പാക്കുക

### ക്ലൗഡിൽ `stream=false` ഉപയോഗിക്കുമ്പോൾ 500 ലഭിക്കുന്നു

**ലക്ഷണം:** നോൺ-സ്ട്രീമിംഗ് കോളുകൾക്കായി ക്ലൗഡ് എൻഡ്പോയിന്റിൽ `Unexpected token 'd'...` ലഭിക്കുന്നു.

**കാരണം:** ക്ലയന്റ് JSON പ്രതീക്ഷിക്കുമ്പോൾ അപ്സ്ട്രീം SSE പേലോഡ് നൽകുന്നു.

**താൽക്കാലിക പരിഹാരം:** ക്ലൗഡിലേക്കുള്ള നേരിട്ടുള്ള കോളുകൾക്കായി `stream=true` ഉപയോഗിക്കുക. ലോക്കൽ റൺടൈമിൽ SSE→JSON ഫാൾബാക്ക് ഉൾപ്പെടുത്തിയിട്ടുണ്ട്.

### ക്ലൗഡ് കണക്റ്റ് ചെയ്തതായി കാണിക്കുന്നുവെങ്കിലും "Invalid API key" എന്ന് പറയുന്നു

1. ലോക്കൽ ഡാഷ്ബോർഡിൽ നിന്ന് പുതിയൊരു കീ സൃഷ്ടിക്കുക (`/api/keys`)
2. ക്ലൗഡ് സിങ്ക് പ്രവർത്തിപ്പിക്കുക: Enable Cloud → Sync Now
3. പഴയതോ സിങ്ക് ചെയ്യാത്തതോ ആയ കീകൾ ക്ലൗഡിൽ ഇപ്പോഴും `401` നൽകാം

## Docker പ്രശ്നങ്ങൾ

### Docker IPv6 / കണക്ഷൻ റീസെറ്റ്

<a name="docker-ipv6"></a>

**ലക്ഷണങ്ങൾ:** `curl http://localhost:20128/v1/models` പ്രവർത്തിപ്പിക്കുമ്പോൾ `curl: (56) Recv failure: Connection reset by peer` ലഭിക്കുന്നു. ഡാഷ്ബോർഡും പ്രാമാണീകരണം ആവശ്യമില്ലാത്ത എൻഡ്പോയിന്റുകളും പ്രവർത്തിക്കുന്നുവെങ്കിലും പ്രാമാണീകരിച്ച എൻഡ്പോയിന്റുകൾ പരാജയപ്പെടുന്നു — ഇത് ഒരു പ്രാമാണീകരണ പ്രശ്നമായി തോന്നുമെങ്കിലും യഥാർത്ഥത്തിൽ അങ്ങനെയല്ല.

**കാരണം:** `docker run -p 20128:20128` എന്നത് `0.0.0.0` (IPv4), `::` (IPv6) എന്നിവ രണ്ടിലും പബ്ലിഷ് ചെയ്യുന്നു, എന്നാൽ കണ്ടെയ്നറിനുള്ളിലെ പ്രോസസ്സ് IPv4-ൽ മാത്രമാണ് ലിസൻ ചെയ്യുന്നത്. `localhost` ആദ്യം `::1` ആയി റിസോൾവ് ചെയ്യുന്ന ഹോസ്റ്റുകളിൽ, കണക്ഷൻ പിന്നിൽ ലിസണർ ഇല്ലാത്ത IPv6 പബ്ലിഷ് ചെയ്ത പോർട്ടിൽ എത്തുന്നു → കണക്ഷൻ റീസെറ്റ്.

**പരിഹാരം:**

1. **ദ്രുത പരിശോധന:** `curl -4 http://localhost:20128/v1/models` പ്രവർത്തിപ്പിക്കുക. `-4` ഉപയോഗിക്കുമ്പോൾ ഇത് പ്രവർത്തിക്കുകയും അതില്ലാതെ പരാജയപ്പെടുകയും ചെയ്യുന്നുവെങ്കിൽ, നിങ്ങൾക്ക് IPv6 ബൈൻഡ് പൊരുത്തക്കേടുണ്ട്.
2. **സ്ഥിരമായ പരിഹാരം:** നിങ്ങളുടെ `docker run` കമാൻഡിൽ `-p 127.0.0.1:20128:20128` ഉപയോഗിച്ച് IPv4-ലേക്ക് വ്യക്തമായി ബൈൻഡ് ചെയ്യുക:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ഇത് IPv4 ബൈൻഡ് നിർബന്ധമാക്കുകയും എല്ലാ ഹോസ്റ്റ് ഇന്റർഫേസുകളിലും പ്രോക്സി തുറന്നുകാട്ടുന്നത് ഒഴിവാക്കുകയും ചെയ്യുന്നു.

## ഡീബഗ്ഗിംഗ്

### ലോഗ് ഫയലുകൾ പ്രവർത്തനക്ഷമമാക്കുക

നിങ്ങളുടെ `.env` ഫയലിൽ `APP_LOG_TO_FILE=true` സജ്ജമാക്കുക. ആപ്ലിക്കേഷൻ ലോഗുകൾ `logs/` എന്നതിന് കീഴിൽ എഴുതപ്പെടുന്നു.
ക്രമീകരണങ്ങളിൽ കോൾ ലോഗ് പൈപ്പ്ലൈൻ പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ റിക്വസ്റ്റ് ആർട്ടിഫാക്റ്റുകൾ `${DATA_DIR}/call_logs/` എന്നതിന് കീഴിൽ സംഭരിക്കുന്നു.
പൈപ്പ്ലൈൻ ക്യാപ്ചർ പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ, സ്ട്രീം ചങ്ക് പേലോഡുകൾ ഒഴിവാക്കാൻ `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` സജ്ജമാക്കുക, അല്ലെങ്കിൽ KB-യിലെ ആർട്ടിഫാക്റ്റ് പരിധി മാറ്റാൻ `CALL_LOG_PIPELINE_MAX_SIZE_KB` ക്രമീകരിക്കുക.

### പ്രൊവൈഡറിന്റെ ആരോഗ്യനില പരിശോധിക്കുക

```bash

http://localhost:20128/dashboard/health

# API ആരോഗ്യനില പരിശോധന
```

### റൺടൈം സ്റ്റോറേജ്

- പ്രധാന നില: `${DATA_DIR}/storage.sqlite` (പ്രൊവൈഡറുകൾ, കോംബോകൾ, അപരനാമങ്ങൾ, കീകൾ, ക്രമീകരണങ്ങൾ)
- ഉപയോഗം: `storage.sqlite`-ലെ SQLite പട്ടികകൾ (`usage_history`, `call_logs`, `proxy_logs`) + ഐച്ഛികമായ `${DATA_DIR}/call_logs/`
- ആപ്ലിക്കേഷൻ ലോഗുകൾ: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ആയിരിക്കുമ്പോൾ)
- കോൾ ലോഗ് ആർട്ടിഫാക്റ്റുകൾ: കോൾ ലോഗ് പൈപ്പ്ലൈൻ പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs പേജിലെ **Clean history** പ്രവർത്തനം `call_logs`, പഴയ
`request_detail_logs`, ലോക്കൽ `${DATA_DIR}/call_logs/` ആർട്ടിഫാക്റ്റ് ഡയറക്ടറി എന്നിവ മായ്ക്കുന്നു.

## സർക്യൂട്ട് ബ്രേക്കർ പ്രശ്നങ്ങൾ

### പ്രൊവൈഡർ OPEN നിലയിൽ കുടുങ്ങിക്കിടക്കുന്നു

ഒരു പ്രൊവൈഡറിന്റെ സർക്യൂട്ട് ബ്രേക്കർ OPEN ആയിരിക്കുമ്പോൾ, കൂൾഡൗൺ കാലയളവ് അവസാനിക്കുന്നതുവരെ അഭ്യർത്ഥനകൾ തടയപ്പെടും.

**പരിഹാരം:**

1. **ഡാഷ്ബോർഡ് → ക്രമീകരണങ്ങൾ → പ്രതിരോധശേഷി** എന്നതിലേക്ക് പോകുക
2. ബാധിക്കപ്പെട്ട പ്രൊവൈഡറിന്റെ സർക്യൂട്ട് ബ്രേക്കർ കാർഡ് പരിശോധിക്കുക
3. എല്ലാ ബ്രേക്കറുകളും മായ്ക്കാൻ **എല്ലാം റീസെറ്റ് ചെയ്യുക** ക്ലിക്ക് ചെയ്യുക, അല്ലെങ്കിൽ കൂൾഡൗൺ കാലയളവ് അവസാനിക്കുന്നതുവരെ കാത്തിരിക്കുക
4. റീസെറ്റ് ചെയ്യുന്നതിന് മുമ്പ് പ്രൊവൈഡർ യഥാർത്ഥത്തിൽ ലഭ്യമാണെന്ന് സ്ഥിരീകരിക്കുക

### പ്രൊവൈഡർ സർക്യൂട്ട് ബ്രേക്കർ ആവർത്തിച്ച് ട്രിപ്പ് ചെയ്യുന്നു

ഒരു പ്രൊവൈഡർ ആവർത്തിച്ച് OPEN നിലയിലേക്ക് പ്രവേശിക്കുന്നുവെങ്കിൽ:

1. പരാജയങ്ങളുടെ പാറ്റേൺ കണ്ടെത്താൻ **ഡാഷ്ബോർഡ് → ആരോഗ്യം → പ്രൊവൈഡർ ആരോഗ്യം** പരിശോധിക്കുക
2. **ക്രമീകരണങ്ങൾ → പ്രതിരോധശേഷി → പ്രൊവൈഡർ പ്രൊഫൈലുകൾ** എന്നതിലേക്ക് പോയി പരാജയ പരിധി വർധിപ്പിക്കുക
3. പ്രൊവൈഡർ API പരിധികൾ മാറ്റിയിട്ടുണ്ടോ അല്ലെങ്കിൽ വീണ്ടും പ്രാമാണീകരിക്കേണ്ടതുണ്ടോ എന്ന് പരിശോധിക്കുക
4. ലേറ്റൻസി ടെലിമെട്രി അവലോകനം ചെയ്യുക — ഉയർന്ന ലേറ്റൻസി ടൈംഔട്ട് അടിസ്ഥാനമാക്കിയുള്ള പരാജയങ്ങൾക്ക് കാരണമായേക്കാം

## ഓഡിയോ ട്രാൻസ്ക്രിപ്ഷൻ പ്രശ്നങ്ങൾ

### "പിന്തുണയ്ക്കാത്ത മോഡൽ" പിശക്

- ആദ്യ സെഗ്മെന്റ് നിങ്ങളുടെ പക്കൽ ക്രെഡൻഷ്യലുകളുള്ള ഒരു പ്രൊവൈഡറായ മോഡൽ id ഉപയോഗിക്കുക (`openai/whisper-1`, `openrouter/deepgram/nova-3`). `deepgram/nova-3` നേരിട്ട് ഉപയോഗിക്കുന്നതിന് ഒരു നേറ്റീവ് Deepgram കീ ആവശ്യമാണ്.
- **ഡാഷ്ബോർഡ് → പ്രൊവൈഡർമാർ** എന്നതിൽ പ്രൊവൈഡർ കണക്റ്റ് ചെയ്തിട്ടുണ്ടെന്ന് സ്ഥിരീകരിക്കുക

### ട്രാൻസ്ക്രിപ്ഷൻ ശൂന്യമായി ലഭിക്കുന്നു അല്ലെങ്കിൽ പരാജയപ്പെടുന്നു

- പിന്തുണയ്ക്കുന്ന ഓഡിയോ ഫോർമാറ്റുകൾ പരിശോധിക്കുക: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ഫയൽ വലുപ്പം പ്രൊവൈഡറുടെ പരിധിക്കുള്ളിലാണെന്ന് സ്ഥിരീകരിക്കുക (സാധാരണയായി < 25MB)
- പ്രൊവൈഡർ കാർഡിൽ പ്രൊവൈഡറുടെ API കീ സാധുവാണോ എന്ന് പരിശോധിക്കുക

## ട്രാൻസ്ലേറ്റർ ഡീബഗ്ഗിംഗ്

ഫോർമാറ്റ് വിവർത്തന പ്രശ്നങ്ങൾ ഡീബഗ് ചെയ്യാൻ **ഡാഷ്ബോർഡ് → ട്രാൻസ്ലേറ്റർ** ഉപയോഗിക്കുക:

| മോഡ്                | എപ്പോൾ ഉപയോഗിക്കണം                                                                                                                                       |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **പ്ലേഗ്രൗണ്ട്**    | ഇൻപുട്ട്/ഔട്ട്പുട്ട് ഫോർമാറ്റുകൾ അടുത്തടുത്തായി താരതമ്യം ചെയ്യുക — വിവർത്തനം എങ്ങനെ നടക്കുന്നു എന്ന് കാണാൻ പരാജയപ്പെടുന്ന ഒരു അഭ്യർത്ഥന പേസ്റ്റ് ചെയ്യുക |
| **ചാറ്റ് ടെസ്റ്റർ** | തത്സമയ സന്ദേശങ്ങൾ അയച്ച് ഹെഡറുകൾ ഉൾപ്പെടെയുള്ള പൂർണ്ണ അഭ്യർത്ഥന/പ്രതികരണ പേലോഡ് പരിശോധിക്കുക                                                             |
| **ടെസ്റ്റ് ബെഞ്ച്** | ഏതൊക്കെ വിവർത്തനങ്ങളാണ് തകരാറിലായതെന്ന് കണ്ടെത്താൻ ഫോർമാറ്റ് കോമ്പിനേഷനുകളിലുടനീളം ബാച്ച് ടെസ്റ്റുകൾ പ്രവർത്തിപ്പിക്കുക                                  |
| **ലൈവ് മോണിറ്റർ**   | ഇടയ്ക്കിടെ സംഭവിക്കുന്ന വിവർത്തന പ്രശ്നങ്ങൾ കണ്ടെത്താൻ തത്സമയ അഭ്യർത്ഥനാ പ്രവാഹം നിരീക്ഷിക്കുക                                                           |

### സാധാരണ ഫോർമാറ്റ് പ്രശ്നങ്ങൾ

- **തിങ്കിംഗ് ടാഗുകൾ ദൃശ്യമാകുന്നില്ല** — ലക്ഷ്യ പ്രൊവൈഡർ തിങ്കിംഗ് പിന്തുണയ്ക്കുന്നുണ്ടോ എന്നും തിങ്കിംഗ് ബജറ്റ് ക്രമീകരണവും പരിശോധിക്കുക
- **ടൂൾ കോളുകൾ നഷ്ടപ്പെടുന്നു** — ചില ഫോർമാറ്റ് വിവർത്തനങ്ങൾ പിന്തുണയ്ക്കാത്ത ഫീൽഡുകൾ നീക്കംചെയ്തേക്കാം; പ്ലേഗ്രൗണ്ട് മോഡിൽ സ്ഥിരീകരിക്കുക
- **സിസ്റ്റം പ്രോംപ്റ്റ് കാണുന്നില്ല** — Claude, Gemini എന്നിവ സിസ്റ്റം പ്രോംപ്റ്റുകൾ വ്യത്യസ്തമായി കൈകാര്യം ചെയ്യുന്നു; വിവർത്തന ഔട്ട്പുട്ട് പരിശോധിക്കുക
- **SDK ഒബ്ജക്റ്റിന് പകരം റോ സ്ട്രിംഗ് നൽകുന്നു** — v1.x-ൽ പരിഹരിച്ചിട്ടുണ്ട്; OpenAI SDK Pydantic വാലിഡേഷൻ പരാജയങ്ങൾക്ക് കാരണമാകുന്ന നിലവാരേതര ഫീൽഡുകൾ (`x_groq`, `usage_breakdown` തുടങ്ങിയവ) റെസ്പോൺസ് സാനിറ്റൈസർ നീക്കംചെയ്യുന്നു. v3.x+-ൽ ഇപ്പോഴും ഇത് കാണുന്നുവെങ്കിൽ, ദയവായി ഒരു ഇഷ്യൂ ഫയൽ ചെയ്യുക.
- **GLM/ERNIE `system` റോൾ നിരസിക്കുന്നു** — v1.x-ൽ പരിഹരിച്ചിട്ടുണ്ട്; പൊരുത്തപ്പെടാത്ത മോഡലുകൾക്കായി റോൾ നോർമലൈസർ സിസ്റ്റം സന്ദേശങ്ങളെ സ്വയമേവ ഉപയോക്തൃ സന്ദേശങ്ങളുമായി ലയിപ്പിക്കുന്നു. v3.x+-ൽ ഇപ്പോഴും ഇത് കാണുന്നുവെങ്കിൽ, ദയവായി ഒരു ഇഷ്യൂ ഫയൽ ചെയ്യുക.
- **`developer` റോൾ തിരിച്ചറിയുന്നില്ല** — v1.x-ൽ പരിഹരിച്ചിട്ടുണ്ട്; OpenAI ഇതര പ്രൊവൈഡർമാർക്കായി ഇത് സ്വയമേവ `system` ആയി പരിവർത്തനം ചെയ്യപ്പെടുന്നു. v3.x+-ൽ ഇപ്പോഴും ഇത് കാണുന്നുവെങ്കിൽ, ദയവായി ഒരു ഇഷ്യൂ ഫയൽ ചെയ്യുക.
- **Gemini-യിൽ `json_schema` പ്രവർത്തിക്കുന്നില്ല** — v1.x-ൽ പരിഹരിച്ചിട്ടുണ്ട്; `response_format` ഇപ്പോൾ Gemini-യുടെ `responseMimeType` + `responseSchema` ആയി പരിവർത്തനം ചെയ്യപ്പെടുന്നു. v3.x+-ൽ ഇപ്പോഴും ഇത് കാണുന്നുവെങ്കിൽ, ദയവായി ഒരു ഇഷ്യൂ ഫയൽ ചെയ്യുക.

## പ്രതിരോധക്ഷമതാ ക്രമീകരണങ്ങൾ

### സ്വയമേവയുള്ള നിരക്ക്-പരിധി പ്രവർത്തനക്ഷമമാകുന്നില്ല

- സ്വയമേവയുള്ള നിരക്ക്-പരിധി API കീ ദാതാക്കൾക്ക് മാത്രമാണ് ബാധകം (OAuth/സബ്സ്ക്രിപ്ഷന് ബാധകമല്ല)
- **Settings → Resilience → Provider Profiles** എന്നതിൽ സ്വയമേവയുള്ള നിരക്ക്-പരിധി പ്രവർത്തനക്ഷമമാക്കിയിട്ടുണ്ടെന്ന് ഉറപ്പാക്കുക
- ദാതാവ് `429` സ്റ്റാറ്റസ് കോഡുകളോ `Retry-After` ഹെഡറുകളോ മടക്കിനൽകുന്നുണ്ടോയെന്ന് പരിശോധിക്കുക

### എക്സ്പോണൻഷ്യൽ ബാക്ക്ഓഫ് ക്രമീകരിക്കൽ

ദാതൃ പ്രൊഫൈലുകൾ ഈ ക്രമീകരണങ്ങളെ പിന്തുണയ്ക്കുന്നു:

- **അടിസ്ഥാന കാലതാമസം** — ആദ്യ പരാജയത്തിന് ശേഷമുള്ള പ്രാരംഭ കാത്തിരിപ്പ് സമയം (സ്ഥിരസ്ഥിതി: 1s)
- **പരമാവധി കാലതാമസം** — കാത്തിരിപ്പ് സമയത്തിന്റെ പരമാവധി പരിധി (സ്ഥിരസ്ഥിതി: 30s)
- **ഗുണകം** — തുടർച്ചയായ ഓരോ പരാജയത്തിലും കാലതാമസം എത്രത്തോളം വർധിപ്പിക്കണം (സ്ഥിരസ്ഥിതി: 2x)

### തണ്ടറിങ് ഹെർഡ് തടയൽ

നിരവധി സമകാലിക അഭ്യർത്ഥനകൾ നിരക്ക്-പരിധിയുള്ള ഒരു ദാതാവിൽ എത്തുമ്പോൾ, അഭ്യർത്ഥനകൾ ക്രമമായി നടപ്പിലാക്കാനും തുടർപരാജയങ്ങൾ തടയാനും OmniRoute മ്യൂട്ടെക്സ് + സ്വയമേവയുള്ള നിരക്ക്-പരിധി ഉപയോഗിക്കുന്നു. API കീ ദാതാക്കൾക്ക് ഇത് സ്വയമേവയാണ്.

### ചാറ്റ് അഭ്യർത്ഥനകൾ 503 / chat_admission_busy ഉപയോഗിച്ച് പരാജയപ്പെടുന്നു

**ലക്ഷണങ്ങൾ:**

- ചാറ്റ് പൂർത്തീകരണ എൻഡ്പോയിന്റ് വീണ്ടും ശ്രമിക്കാവുന്ന ഒരു `503` പ്രതികരണം മടക്കിനൽകുന്നു; അതിന്റെ പിശക് കോഡ്
  `chat_admission_busy` ആണ്.
- പ്രതികരണത്തിൽ `Retry-After` ഉൾപ്പെടുന്നു. #12135 മുതൽ, നിരീക്ഷിച്ച
  ഒക്ക്യുപ്പൻസിയിൽ നിന്നാണ് മൂല്യം നിർണ്ണയിക്കുന്നത് — അഭ്യർത്ഥന ഇതിനകം കാത്തിരുന്ന `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  ജാലകവും നിലവിലെ ഹെവിവെയ്റ്റ് ലീസുകൾ കൈവശം വെച്ചിരിക്കുന്ന സമയവും തമ്മിലുള്ള വലിയ മൂല്യം — പൂർണ്ണ
  സെക്കൻഡുകളിലേക്ക് മുകളിലേക്ക് റൗണ്ട് ചെയ്ത് പരമാവധി 60 ആയി പരിമിതപ്പെടുത്തുന്നു. നിഷ്ക്രിയമായ ഒരു ഗേറ്റിൽ ഇത് ചരിത്രപരമായ കുറഞ്ഞ പരിധികൾ നിലനിർത്തുന്നു:
  ബൈറ്റ് അധിഷ്ഠിത പാതയിൽ 2 സെക്കൻഡും ഘടന അധിഷ്ഠിത പാതയിൽ 1 സെക്കൻഡും (ഇതിൽ
  `reason: "structure_limit"` എന്നതും ഉൾപ്പെടുന്നു).
- മറ്റൊരു ഹെവിവെയ്റ്റ് ചാറ്റോ ദീർഘനേരം പ്രവർത്തിക്കുന്ന സ്ട്രീമിങ് പ്രതികരണമോ ഇപ്പോഴും
  പുരോഗമിച്ചുകൊണ്ടിരിക്കുമ്പോൾ ഇത് സംഭവിക്കാം.

ബൈറ്റ് അധിഷ്ഠിത പ്രതികരണ ബോഡി ഇതാണ്:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ഘടന അധിഷ്ഠിത പ്രതികരണം അതേ തരവും കോഡും ഉപയോഗിക്കുന്നു; സന്ദേശം
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
എന്നതും `reason: "structure_limit"` എന്നതുമാണ്.
സ്ഥിരസ്ഥിതി പരിധികളിൽ, ഒരു അഭ്യർത്ഥനയിൽ കുറഞ്ഞത് `200` സന്ദേശങ്ങളോ,
കുറഞ്ഞത് `64` ടൂളുകളോ, കുറഞ്ഞത് `32,000` കണക്കാക്കിയ ടോക്കണുകളോ ഉണ്ടെങ്കിൽ, അല്ലെങ്കിൽ പരിധിയിട്ട ഘടനാ കണക്കുകൂട്ടൽ
സന്ദർശിച്ച `10,000` നോഡുകളുടെ പരിധിയോ `12` ആഴമോ തീർത്താൽ, അത് ഘടനാപരമായി ഹെവിവെയ്റ്റ് ആയിരിക്കും.

**കാരണം:** ഇത് OmniRoute-നുള്ളിലെ മനഃപൂർവമായ ലോഡ് ഷെഡ്ഡിങ് ആണ്, അപ്സ്ട്രീം ദാതാവിന്റെ പരാജയമല്ല.
ഒരു വലിയ അഭ്യർത്ഥനാ ബോഡി നിലനിർത്തി പാഴ്സ് ചെയ്യുന്നതിന് മുമ്പ് പരിമിതമായ ഹെവിവെയ്റ്റ് ശേഷി റിസർവ് ചെയ്യാൻ
ഓരോ പ്രോസസും പ്രോസസ്-ലോക്കൽ ഗാർഡ് ഉപയോഗിക്കുന്നു. ഒരു SSE പ്രതികരണത്തിന്റെ മുഴുവൻ ആയുഷ്കാലത്തും ഒരു ഹെവിവെയ്റ്റ്
ലീസ് കൈവശം തുടരും.

**#503-ഫാൻഔട്ട്:** ഈ പരിഹാരത്തിന് മുമ്പ്, ഹോസ്റ്റ് മെമ്മറി പരിഗണിക്കാതെ ഗാർഡ് സമകാലികതയെ ഒരു നിശ്ചിത അഭ്യർത്ഥനാ എണ്ണത്തിൽ
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, സ്ഥിരസ്ഥിതി `1`) പരിമിതപ്പെടുത്തിയിരുന്നു; അതിനാൽ കോഡിങ്-ഏജന്റ്
ഫാൻഔട്ട് (ഒന്നിലധികം സബ്ഏജന്റുകൾ/CLI-കൾ, പതിവായി > 256 KB വലുപ്പമുള്ള ബോഡികൾ) പ്രായോഗികമായി
~1 സമകാലികതയിലേക്ക് ചുരുങ്ങുകയും പൂർണ്ണമായും സാധാരണ ലോഡിൽ 503 പിശകുകൾ സൃഷ്ടിക്കുകയും ചെയ്തു. ഇപ്പോൾ ഗാർഡ് സ്വയം ക്രമീകരിക്കുന്നു: പ്രോസസിന്റെ
യഥാർത്ഥ മെമ്മറി പരിധിയിൽ നിന്ന് വലുപ്പം നിർണ്ണയിക്കുന്ന, സ്വയമേവ ഉരുത്തിരിയുന്ന ഇൻജെസ്റ്റ് BYTE ബജറ്റ്
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ഉപയോഗിച്ചാണ് ഇത് നിയന്ത്രിക്കുന്നത്; കൂടാതെ ഇത് ഒരു തത്സമയ റിസോഴ്സ്-പ്രഷർ സിഗ്നലും പരിശോധിക്കുന്നു — അതിനാൽ
ഒന്നിലധികം ഹെവി അഭ്യർത്ഥനകൾ ഒരേസമയം എത്തി എന്ന കാരണത്താൽ മാത്രമല്ല, ഹോസ്റ്റ് യഥാർത്ഥത്തിൽ മെമ്മറി സമ്മർദ്ദത്തിലായിരിക്കുമ്പോൾ
മാത്രമാണ് ഇത് ലോഡ് ഒഴിവാക്കുന്നത്. പഴയ എണ്ണം-പരിധി (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ഇപ്പോഴും
മാനിക്കപ്പെടുന്നു, പക്ഷേ നിങ്ങൾ അത് വ്യക്തമായി സജ്ജീകരിച്ചാൽ മാത്രം.

ശേഷി തിരക്കിലായിരിക്കുമ്പോൾ, വീണ്ടും ശ്രമിക്കാവുന്ന `503` ഉപയോഗിച്ച് മറുപടി നൽകുന്നതിന് മുമ്പ് ഒരു സ്ലോട്ട് ഒഴിവാകാനായി ഹെവിവെയ്റ്റ് അഭ്യർത്ഥന ആദ്യം
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` വരെ കാത്തിരിക്കും (സ്ഥിരസ്ഥിതി `RATE_LIMIT_MAX_WAIT_MS`; `0` കാത്തിരിപ്പ് പ്രവർത്തനരഹിതമാക്കുന്നു).
സമകാലികമായി ഹെവി ഉപ-അഭ്യർത്ഥനകൾ ഫാൻഔട്ട് ചെയ്യുന്ന ഏജന്റ്-ശൈലിയിലുള്ള ക്ലയന്റുകൾക്ക്
(OpenCode, Claude Code, Cursor), ഉടനടിയുള്ള നിരസിക്കലുകളിൽ അവരുടെ മുഴുവൻ പുനഃശ്രമ ബജറ്റും ചെലവാക്കി ജോലിക്കിടെ പരാജയപ്പെടുന്നതിനുപകരം,
ഈ ബർസ്റ്റ് ക്രമമായി നടപ്പിലാക്കാനാണ് ഈ പരിധിയിട്ട കാത്തിരിപ്പ് നിലവിലുള്ളത്.
നിലവിലെ ഹെവിവെയ്റ്റ് ലീസ് ഒക്ക്യുപ്പൻസി, നിർണ്ണയിച്ച ബൈറ്റ് ബജറ്റ്, തത്സമയ സമ്മർദ്ദ തീവ്രത എന്നിവ
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) എന്നതിൽ പ്രദർശിപ്പിക്കുന്നു — ഏതെങ്കിലും env var മാറ്റുന്നതിന് മുമ്പ് ഇവ പരിശോധിക്കുക.
Settings → Resilience → Request Queue → Concurrent Requests ഇത് നിയന്ത്രിക്കുന്നില്ല; ആ ക്രമീകരണം
വേറൊരു ദാതൃ അഭ്യർത്ഥനാ-ക്യൂ സംവിധാനത്തെയാണ് നിയന്ത്രിക്കുന്നത്.

**പരിഹാരം:**

1. ആദ്യം വീണ്ടും ശ്രമിക്കുക. അഭ്യർത്ഥന ഉടൻ
   ആവർത്തിക്കുന്നതിനുപകരം ക്ലയന്റുകൾ `Retry-After` മാനിക്കുകയും ബാക്ക്ഓഫ് ഉപയോഗിക്കുകയും വേണം.
2. എന്തെങ്കിലും ക്രമീകരിക്കുന്നതിന് മുമ്പ് `/api/monitoring/health` → `chatAdmission` പരിശോധിക്കുക. `countCapEnabled:
false` എന്നതും മതിയായ `maxInflightBytes` എന്നതും, സ്വയമേവ ഉരുത്തിരിഞ്ഞ ബജറ്റ് ഇതിനകം അതിന്റെ
   ജോലി നിർവഹിക്കുന്നുവെന്ന് സൂചിപ്പിക്കുന്നു; `high`/`critical` ആയ `pressureSeverity`, ഹോസ്റ്റിൽ യഥാർത്ഥത്തിൽ മെമ്മറി കുറവാണെന്ന് സൂചിപ്പിക്കുന്നു —
   ഒരു അഡ്മിഷൻ env var ഉപയോഗിച്ച് അത് പരിഹരിക്കാനാവില്ല; അതിന് കൂടുതൽ RAM അല്ലെങ്കിൽ ചെറിയ വർക്ക്ലോഡ് ആവശ്യമാണ്.
3. നിങ്ങളുടെ ഹോസ്റ്റിനായി സ്വയമേവ ഉരുത്തിരിഞ്ഞ ബജറ്റ് യഥാർത്ഥത്തിൽ വളരെ ചെറുതാണെന്ന്
   `/api/monitoring/health` കാണിക്കുന്നുവെങ്കിൽ മാത്രം (അപൂർവം — കണ്ടെയ്നർ മുതൽ ബെയർ-മെറ്റൽ വരെ ഇത് ഇതിനകം സ്കെയിൽ ചെയ്യുന്നു), പഴയ അഭ്യർത്ഥനാ-എണ്ണ പരിധിയിലേക്ക് മടങ്ങുന്നതിനുപകരം
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ഉപയോഗിച്ച് അതിനെ നേരിട്ട് ഓവർറൈഡ് ചെയ്യുക.

ആധികാരിക അഡ്മിഷൻ ക്രമീകരണങ്ങൾക്കായി [പരിസ്ഥിതി-വേരിയബിൾ റഫറൻസ്](../reference/ENVIRONMENT.md#4-security--authentication)
കാണുക.

## ഐച്ഛിക RAG / LLM പരാജയ വർഗ്ഗീകരണം (16 പ്രശ്നങ്ങൾ)

ചില OmniRoute ഉപയോക്താക്കൾ RAG അല്ലെങ്കിൽ ഏജന്റ് സ്റ്റാക്കുകൾക്ക് മുന്നിൽ ഗേറ്റ്വേ സ്ഥാപിക്കുന്നു. അത്തരം സജ്ജീകരണങ്ങളിൽ വിചിത്രമായ ഒരു രീതി സാധാരണയായി കാണാം: OmniRoute ആരോഗ്യകരമായി തോന്നുന്നു (ദാതാക്കൾ പ്രവർത്തനക്ഷമമാണ്, റൂട്ടിംഗ് പ്രൊഫൈലുകൾ ശരിയാണ്, നിരക്ക് പരിധി അലേർട്ടുകളില്ല), എന്നാൽ അന്തിമ ഉത്തരം അപ്പോഴും തെറ്റായിരിക്കും.

പ്രായോഗികമായി, ഈ സംഭവങ്ങൾ സാധാരണയായി ഉണ്ടാകുന്നത് ഡൗൺസ്ട്രീം RAG പൈപ്പ്ലൈനിൽ നിന്നാണ്, ഗേറ്റ്വേയിൽ നിന്നല്ല.

ആ പരാജയങ്ങൾ വിവരിക്കാൻ പൊതുവായ ഒരു പദാവലി വേണമെങ്കിൽ, ആവർത്തിച്ചുണ്ടാകുന്ന പതിനാറ് RAG / LLM പരാജയ രീതികൾ നിർവചിക്കുന്ന, MIT ലൈസൻസിലുള്ള ഒരു ബാഹ്യ ടെക്സ്റ്റ് റിസോഴ്സായ WFGY ProblemMap ഉപയോഗിക്കാം. ഉയർന്ന തലത്തിൽ ഇത് ഉൾക്കൊള്ളുന്നത്:

- റിട്രീവൽ ഡ്രിഫ്റ്റും തകർന്ന കോൺടെക്സ്റ്റ് അതിരുകളും
- ശൂന്യമായതോ കാലഹരണപ്പെട്ടതോ ആയ ഇൻഡെക്സുകളും വെക്റ്റർ സ്റ്റോറുകളും
- എംബെഡ്ഡിംഗും സെമാന്റിക്സും തമ്മിലുള്ള പൊരുത്തക്കേട്
- പ്രോംപ്റ്റ് അസംബ്ലി, കോൺടെക്സ്റ്റ് വിൻഡോ പ്രശ്നങ്ങൾ
- ലോജിക് തകർച്ചയും അമിത ആത്മവിശ്വാസമുള്ള ഉത്തരങ്ങളും
- ദീർഘമായ ചെയിൻ, ഏജന്റ് ഏകോപന പരാജയങ്ങൾ
- മൾട്ടി-ഏജന്റ് മെമ്മറിയും റോൾ ഡ്രിഫ്റ്റും
- ഡിപ്ലോയ്മെന്റ്, ബൂട്ട്സ്ട്രാപ്പ് ക്രമീകരണ പ്രശ്നങ്ങൾ

ആശയം ലളിതമാണ്:

1. ഒരു മോശം പ്രതികരണം അന്വേഷിക്കുമ്പോൾ, ഇനിപ്പറയുന്നവ രേഖപ്പെടുത്തുക:
   - ഉപയോക്തൃ ടാസ്കും അഭ്യർത്ഥനയും
   - OmniRoute-ലെ റൂട്ട് അല്ലെങ്കിൽ ദാതാക്കളുടെ കോമ്പിനേഷൻ
   - ഡൗൺസ്ട്രീമിൽ ഉപയോഗിച്ച ഏതെങ്കിലും RAG കോൺടെക്സ്റ്റ് (റിട്രീവ് ചെയ്ത ഡോക്യുമെന്റുകൾ, ടൂൾ കോളുകൾ തുടങ്ങിയവ)
2. സംഭവത്തെ ഒന്നോ രണ്ടോ WFGY ProblemMap നമ്പറുകളുമായി (`No.1` … `No.16`) മാപ്പ് ചെയ്യുക.
3. OmniRoute ലോഗുകൾക്കൊപ്പം നിങ്ങളുടെ സ്വന്തം ഡാഷ്ബോർഡിലോ റൺബുക്കിലോ ഇൻസിഡന്റ് ട്രാക്കറിലോ ആ നമ്പർ സംഭരിക്കുക.
4. നിങ്ങളുടെ RAG സ്റ്റാക്ക്, റിട്രീവർ, അല്ലെങ്കിൽ റൂട്ടിംഗ് തന്ത്രം മാറ്റേണ്ടതുണ്ടോ എന്ന് തീരുമാനിക്കാൻ അനുബന്ധ WFGY പേജ് ഉപയോഗിക്കുക.

പൂർണ്ണമായ ടെക്സ്റ്റും പ്രായോഗിക റെസിപ്പികളും ഇവിടെ ലഭ്യമാണ് (MIT ലൈസൻസ്, ടെക്സ്റ്റ് മാത്രം):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute-ന് പിന്നിൽ നിങ്ങൾ RAG അല്ലെങ്കിൽ ഏജന്റ് പൈപ്പ്ലൈനുകൾ പ്രവർത്തിപ്പിക്കുന്നില്ലെങ്കിൽ ഈ വിഭാഗം അവഗണിക്കാം.

## v3.8.0-ലെ അറിയപ്പെടുന്ന പ്രശ്നങ്ങൾ

v3.8.0 റിലീസിന് മാത്രമുള്ള പ്രശ്നങ്ങളും അവയുടെ നിലവിലെ പരിഹാര മാർഗങ്ങളും. പിന്നീടുള്ള ഒരു പാച്ചിൽ പരിഹാരം ഉൾപ്പെടുത്തിയാൽ, ഈ എൻട്രി അപ്ഡേറ്റ് ചെയ്യുകയോ നീക്കം ചെയ്യുകയോ ചെയ്യും.

### Devin CLI ഓതന്റിക്കേഷൻ പരാജയങ്ങൾ

**ലക്ഷണങ്ങൾ:**

- Devin പിന്തുണയുള്ള ടൂളുകൾ വിളിക്കുമ്പോൾ "Devin CLI not found" അല്ലെങ്കിൽ "auth failed"
- CLI റൺടൈം പരിശോധന `installed=false` എന്ന് റിപ്പോർട്ട് ചെയ്യുന്നു

**കാരണങ്ങൾ:**

- `CLI_DEVIN_BIN` നിലവിലില്ലാത്ത ഒരു പാതയിലേക്കാണ് വിരൽചൂണ്ടുന്നത്
- ഹോസ്റ്റിൽ Devin CLI ഇൻസ്റ്റാൾ ചെയ്തിട്ടില്ല

**പരിഹാരം:**

1. നിങ്ങളുടെ പ്ലാറ്റ്ഫോമിനായുള്ള Devin CLI ഇൻസ്റ്റാൾ ചെയ്യുക
2. `.env`-ൽ `CLI_DEVIN_BIN=/usr/local/bin/devin` (അല്ലെങ്കിൽ യഥാർത്ഥ പാത) സജ്ജമാക്കുക
3. OmniRoute പുനരാരംഭിച്ച് **Dashboard → CLI Tools**-ൽ നിന്ന് വീണ്ടും പരിശോധിക്കുക

### മോഡൽ കൂൾഡൗൺ മാറാതെ തുടരുന്നു (മാനുവൽ റീസെറ്റ്)

**ലക്ഷണങ്ങൾ:**

- കാലഹരണ സമയം കഴിഞ്ഞിട്ടും ഒരു മോഡൽ കൂൾഡൗണിലുള്ളതായി പട്ടികയിൽ തുടരുന്നു
- ടൈംസ്റ്റാമ്പ് കഴിഞ്ഞ സമയത്തേതായിരുന്നിട്ടും കോമ്പോ റൂട്ടിംഗിൽ അഭ്യർത്ഥനകൾ ആ മോഡലിനെ ഒഴിവാക്കുന്നു

**മാനുവൽ റീസെറ്റ്:**

- **Dashboard:** **Settings → Model Cooldowns** → ബാധിച്ച കാർഡിലെ **Re-enable** ക്ലിക്ക് ചെയ്യുക
- **API:** മാനേജ്മെന്റ് ഓതന്റിക്കേഷൻ ഹെഡറുകളോടൊപ്പം `DELETE /api/resilience/model-cooldowns`

### Command Code ദാതാവിലേക്കുള്ള കണക്ഷൻ 403 കാരണം പരാജയപ്പെടുന്നു

**ലക്ഷണങ്ങൾ:**

- Command Code ദാതാവിലേക്കുള്ള കണക്ഷൻ പരിശോധിക്കുമ്പോൾ 403
- പുതുതായി ചേർത്തതിന് ശേഷം ദാതാവിന്റെ കാർഡ് "unauthorized" എന്ന് കാണിക്കുന്നു

**കാരണം:** OAuth ഫ്ലോ പൂർത്തിയായില്ല (കോൾബാക്ക് ലഭിച്ചില്ല അല്ലെങ്കിൽ ടോക്കൺ നിലനിർത്തിയില്ല).

**പരിഹാരം:**

- OAuth ഫ്ലോ വീണ്ടും ട്രിഗർ ചെയ്യാൻ CLI-യിൽ നിന്ന് `omniroute providers` പ്രവർത്തിപ്പിക്കുക, അല്ലെങ്കിൽ
- **Dashboard → Providers → Command Code → Reconnect** എന്നതിൽ നിന്ന് OAuth വീണ്ടും പ്രവർത്തിപ്പിക്കുക

### ModelScope അമിതമായ 429 കൂൾഡൗണുകൾ നൽകുന്നു

**ലക്ഷണങ്ങൾ:**

- ചെറിയൊരു അഭ്യർത്ഥനാ ബർസ്റ്റിന് ശേഷം ModelScope-ൽ വളരെ ഹ്രസ്വമായതോ ഉടനടിയുള്ളതോ ആയ കൂൾഡൗണുകൾ
- പ്രതീക്ഷിച്ചതിലും നേരത്തേ കോമ്പോ റൂട്ടിംഗ് ModelScope-നെ ഒഴിവാക്കുന്നു

**കാരണം:** ModelScope ദാതാവിന് പ്രത്യേകമായ `Retry-After` ഹെഡറുകൾ നൽകുന്നു. ആ ഹെഡറുകൾക്കായുള്ള പ്രത്യേക കൈകാര്യം v3.8.0-ൽ ഉൾപ്പെടുത്തിയിട്ടുണ്ട്, അതിനാൽ പഴയ പതിപ്പുകൾ അവയെ പൊതുവായ നിരക്ക്-പരിധി സൂചനകളായി തെറ്റായി വായിക്കുന്നു.

**പരിഹാരം:**

- നിങ്ങൾ v3.8.0 അല്ലെങ്കിൽ അതിന് ശേഷമുള്ള പതിപ്പിലാണ് എന്ന് ഉറപ്പാക്കുക
- **Settings → Resilience** എന്നതിന് കീഴിൽ `useUpstream429BreakerHints` ടോഗിൾ പ്രവർത്തനക്ഷമമാണെന്ന് പരിശോധിക്കുക

### പ്രൊഡക്ഷനിൽ OMNIROUTE_WS_BRIDGE_SECRET ലഭ്യമല്ല

**ലക്ഷണങ്ങൾ:**

- റിമോട്ട് പ്രൊഡക്ഷൻ ഹോസ്റ്റിൽ പ്രവർത്തിപ്പിക്കുമ്പോൾ എല്ലാ Codex/Responses WebSocket ബ്രിഡ്ജ് അഭ്യർത്ഥനകളിലും 401
- കണക്ട് ചെയ്ത ഉടൻ WebSocket ബ്രിഡ്ജ് ഹാൻഡ്ഷേക്ക് അവസാനിക്കുന്നു

**കാരണം:** പ്രൊഡക്ഷൻ എൻവയോൺമെന്റിൽ `OMNIROUTE_WS_BRIDGE_SECRET` എൻവയോൺമെന്റ് വേരിയബിൾ ലഭ്യമല്ല.

**പരിഹാരം:**

1. ക്രമരഹിതമായ ഒരു സീക്രട്ട് സൃഷ്ടിക്കുക: `openssl rand -hex 32`
2. പ്രൊഡക്ഷൻ സെർവർ എൻവയോൺമെന്റിൽ (കൂടാതെ ബ്രിഡ്ജുമായി ആശയവിനിമയം നടത്തുന്ന ഏതൊരു ക്ലയന്റിലും) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` സജ്ജമാക്കുക
3. OmniRoute പുനരാരംഭിക്കുക

### Responses API: ബാക്ക്ഗ്രൗണ്ട് മോഡ് സിൻക്രണസ് രീതിയിലേക്ക് താഴ്ത്തി

**ലക്ഷണങ്ങൾ:**

- മുന്നറിയിപ്പ് ലോഗ് ചെയ്യുന്നു: `background mode degraded to synchronous`
- ഒരു `background: true` അഭ്യർത്ഥന ബാക്ക്ഗ്രൗണ്ട് ജോബ് ഹാൻഡിലിന് പകരം സാധാരണ സിൻക്രണസ് പ്രതികരണം നൽകുന്നു

**കാരണം:** ഒരു മുന്നറിയിപ്പ് നൽകിക്കൊണ്ട്, Responses API-യിലെ `background: true` എന്നത് v3.8.0 മനഃപൂർവം സിൻക്രണസ് എക്സിക്യൂഷനിലേക്ക് താഴ്ത്തുന്നു. പൂർണ്ണമായ അസിൻക്രണസ് ബാക്ക്ഗ്രൗണ്ട് എക്സിക്യൂഷൻ ഭാവിയിൽ ലഭ്യമാക്കാനിരിക്കുന്ന ഒരു സവിശേഷതയാണ്.

**പരിഹാരം:**

- `background` ഇല്ലാതെ കോൾ ചെയ്യാൻ ക്ലയന്റ് ക്രമീകരിക്കുക, അല്ലെങ്കിൽ
- പൂർണ്ണമായ അസിൻക്രണസ് ബാക്ക്ഗ്രൗണ്ട് മോഡ് ഉൾപ്പെടുന്ന പിന്നീടുള്ള ഒരു റിലീസിനായി കാത്തിരിക്കുക (ചേഞ്ച്ലോഗ് പിന്തുടരുക)

## മന്ദഗതിയിലുള്ള ആരംഭം / സന്നദ്ധതാ സമയപരിധി

CLI `⚠ Server did not respond within 60s` എന്ന് പ്രദർശിപ്പിക്കുന്നുവെങ്കിലും സെർവർ
യഥാർത്ഥത്തിൽ പ്രവർത്തിക്കുന്നുണ്ടെങ്കിൽ, നിങ്ങളുടെ പരിതസ്ഥിതിക്കായി സന്നദ്ധതാ പരിശോധനയുടെ സമയപരിധി വളരെ കുറവാണ്.

Windows-ലോ (ആന്റിവൈറസ്, ഫയൽസിസ്റ്റം വാച്ചറുകൾ) അല്ലെങ്കിൽ ആരംഭസമയത്ത് കനത്ത ജോലിഭാരമുള്ള
കണ്ടെയ്നറുകളിലോ ഇത് സാധാരണയായി സംഭവിക്കുന്നു.

**പരിഹാരം — സമയപരിധി വർധിപ്പിക്കുക:**

```bash
# പരിതസ്ഥിതി വേരിയബിൾ വഴി (ആരംഭങ്ങൾക്കിടയിലും നിലനിൽക്കും):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 മിനിറ്റ്
omniroute serve

# CLI ഫ്ലാഗ് വഴി (ഒറ്റത്തവണ):
omniroute serve --ready-timeout 180000
```

സ്ഥിരസ്ഥിതി 60 000 ms (60 s) ആണ്. മുന്നറിയിപ്പ് വിവരദായകം മാത്രമാണ്; സെർവർ
പശ്ചാത്തലത്തിൽ ആരംഭിക്കുന്നത് തുടരുകയും ബൂട്ട് പൂർത്തിയായാൽ ലഭ്യമാകുകയും ചെയ്യും.

`OMNIROUTE_READY_TIMEOUT_MS`-നെക്കുറിച്ചുള്ള പൂർണ്ണ വിവരങ്ങൾക്ക്
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) കാണുക.
