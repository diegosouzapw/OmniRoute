## വിശദമായ പ്രശ്നപരിഹാരം

---

### സൗജന്യ ദാതാക്കളിലെ നിരക്ക് പരിമിതപ്പെടുത്തൽ (429 / 400 / 401)

**ലക്ഷണം**: സൗജന്യ/പ്രാമാണീകരണം ആവശ്യമില്ലാത്ത ദാതാക്കളുമായി (opencode, auggie മുതലായവ) `model: "auto"` ഉപയോഗിക്കുമ്പോൾ, ഉത്തരങ്ങൾക്ക് പകരം ഇടയ്ക്കിടെ `HTTP 429`, `400`, അല്ലെങ്കിൽ `401` ലഭിക്കുന്നു. ഏതാനും നിമിഷങ്ങൾക്കുശേഷം അതേ പ്രോംപ്റ്റ് വീണ്ടും ശ്രമിക്കുമ്പോൾ അഭ്യർത്ഥനകൾ വിജയിക്കുന്നു, എന്നാൽ ഓട്ടോമേഷൻ (cron ജോലികൾ, ഏജന്റുകൾ, സ്ക്രിപ്റ്റുകൾ) ആദ്യ പരാജയത്തിൽ തന്നെ തകരുന്നു.

**മൂലകാരണം**: സ്വതന്ത്രമായ മൂന്ന് പരാജയരീതികൾ ഒരുമിച്ച് സംഭവിക്കുന്നു:

1. **ദാതാവിന്റെ നിരക്ക് പരിധി (`429`)**: സൗജന്യ ടയറുകൾക്ക് ഓരോ സമയജാലകത്തിനും ഒരു ക്വോട്ട നടപ്പാക്കാനാകും. സമാന്തര കോളുകളുടെ ഒരു കുത്തൊഴുക്ക് അത് തീർത്തുകളയുന്നതിനാൽ, സമയജാലകം റീസെറ്റ് ചെയ്യുന്നതുവരെ അടുത്ത അഭ്യർത്ഥന നിരസിക്കപ്പെടും.
2. **പാസ്ത്രൂവിലെ തകരാറുള്ള മോഡൽ (`400`/`401`)**: `auto/*` പൂളുകളിൽ കാറ്റലോഗിൽ രജിസ്റ്റർ ചെയ്തിട്ടുണ്ടെങ്കിലും സജീവ ക്രെഡൻഷ്യലുകളില്ലാത്ത `opencode`-ൽ നിന്നുള്ള പാസ്ത്രൂ മോഡലുകൾ ഉൾപ്പെടാം (ഉദാ. `oc/north-mini-code-free` → `401`). ഓട്ടോ-റൂട്ടർ ഒരെണ്ണം പരീക്ഷിക്കുകയും പരാജയപ്പെടുകയും ചെയ്യുന്നു; ഫാൾബാക്ക് പ്രവർത്തിക്കുന്നതിന് മുമ്പ് പിശക് പുറത്തേക്ക് പ്രചരിക്കുന്നു.
3. **കൺകറൻസി വർധനം (ലോഡിലുള്ള `429`)**: ഒന്നിലധികം ഏജന്റ്/cron സെഷനുകൾ ഒരേസമയം `auto` ഉപയോഗിക്കുമ്പോൾ, മൊത്തം അഭ്യർത്ഥന നിരക്ക് സൗജന്യ ദാതാക്കൾക്ക് കൈകാര്യം ചെയ്യാനാകുന്നതിലും കൂടുതലാകുന്നു; അതിനാൽ സാധുവായ കോളുകൾ പോലും ദുരുപയോഗമായി അടയാളപ്പെടുത്തപ്പെടുന്നു.

**സ്ഥിരീകരിച്ച പരിഹാരം (കമ്മ്യൂണിറ്റി റിപ്പോർട്ട് ചെയ്തത്, 2026-08-10)**: റൊട്ടേഷൻ, കൺകറൻസി, ഫാൾബാക്ക് എന്നിവ സൗജന്യ ടയറിലെ അസ്ഥിരത കാരണം പരാജയപ്പെടുന്നതിനുപകരം അതിനെ ഉൾക്കൊള്ളുന്ന വിധത്തിൽ മൂന്ന് എൻവയോൺമെന്റ് വേരിയബിളുകൾ ക്രമീകരിക്കുക:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ലഭിക്കുമ്പോൾ മറ്റൊരു മോഡലിലേക്കോ ദാതാവിലേക്കോ മാറുക (തകരാറുള്ള പാസ്ത്രൂ മോഡലുകൾ ഒഴിവാക്കുന്നു)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ഹെവിവെയിറ്റ് അഡ്മിഷന്റെ വ്യക്തമായ പരമാവധി (ഡിഫോൾട്ടായി സജ്ജീകരിച്ചിട്ടില്ല: അഭ്യർത്ഥനകളുടെ എണ്ണത്തിന് പരിധിയില്ല, താഴെയുള്ള കുറിപ്പ് കാണുക)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ഉടനടി വീണ്ടും ശ്രമിക്കാവുന്ന 503 നൽകുന്നതിനുപകരം ഹെവിവെയിറ്റ് ശേഷിക്കായി കൂടുതൽ ദൈർഘ്യമുള്ള, പരിധിയുള്ള കാത്തിരിപ്പ്
```

OmniRoute പ്രോസസ് എൻവയോൺമെന്റിൽ ഇവ സജ്ജീകരിക്കുക (ഡീമൺ, ഉദാ. LaunchAgent plist അല്ലെങ്കിൽ `systemctl edit` വഴി), തുടർന്ന് OmniRoute പുനരാരംഭിക്കുക. റൊട്ടേഷൻ ഫ്ലാഗാണ് ഏറ്റവും കൂടുതൽ പ്രയോജനം നൽകുന്ന ഒറ്റ ക്രമീകരണം: ഇത് പൂളിലെ പ്രവർത്തനക്ഷമമായ ഒരു ദാതാവിനെതിരെ സുതാര്യമായി വീണ്ടും ശ്രമിക്കുന്നതിലൂടെ പൂർണ്ണമായ പരാജയത്തെ ഒഴിവാക്കുന്നു.

**കുറിപ്പ്**: ഒരേസമയം എത്ര ഹെവിവെയിറ്റ് — ദീർഘ-കോൺടെക്സ്റ്റ് — അഭ്യർത്ഥനകൾ പ്രവർത്തിക്കാമെന്ന് `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` പരിമിതപ്പെടുത്തുന്നു; ഈ പരിധി ഒരു അഡ്മിഷൻ ഗേറ്റാണ്, ദാതാവിന്റെ നിരക്ക് പരിമിതപ്പെടുത്തൽ സംവിധാനമല്ല. **#503-fanout അപ്ഡേറ്റ്:** ഈ വേരിയബിൾ ഇനി ഡിഫോൾട്ടായി സജ്ജീകരിക്കുന്നില്ല (മുകളിൽ കാണിച്ചിരിക്കുന്നതുപോലെ വ്യക്തമായി കോൺഫിഗർ ചെയ്യുമ്പോൾ മാത്രമാണ് ഇപ്പോൾ ഇത് ബാധകമാകുന്നത്) — പകരം, ഹോസ്റ്റിന്റെ യഥാർത്ഥ മെമ്മറി പരിധിയെ അടിസ്ഥാനമാക്കി സ്വയം സ്കെയിൽ ചെയ്യുന്ന, സ്വയമേവ നിർണ്ണയിക്കപ്പെടുന്ന ബൈറ്റ് ബജറ്റ് (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ആണ് ഇപ്പോൾ ഹെവിവെയിറ്റ് അഡ്മിഷൻ നിയന്ത്രിക്കുന്നത്. അതിനാൽ, ഈ വേരിയബിൾ സജ്ജീകരിക്കാതെയും പുതിയൊരു ഡിപ്ലോയ്മെന്റിൽ വളരെ കുറച്ച് `503 chat_admission_busy` നിരസിക്കലുകൾ മാത്രമേ ഉണ്ടാകാവൂ; ഇവിടെ ഇത് വ്യക്തമായി സജ്ജീകരിക്കുന്നത് ഡോക്യുമെന്റ് ചെയ്തിരിക്കുന്നതുപോലെ തന്നെ തുടർന്നും പ്രവർത്തിക്കും. വ്യക്തമായ ബൈറ്റ്-ബജറ്റ് ഓവർറൈഡുകൾ 8 MiB–2 GiB പരിധിക്കുള്ളിൽ നിയന്ത്രിക്കപ്പെടുന്നു. `413 body_exceeds_budget` താൽക്കാലികമല്ല: ആ ബൈറ്റ് ബജറ്റ് വർധിപ്പിക്കുക, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` കുറയ്ക്കുക, അല്ലെങ്കിൽ പ്രോസസിന്റെ മെമ്മറി പരിധി വർധിപ്പിക്കുക. `inflight_bytes_budget` ഷെഡ് താൽക്കാലികമായ വിഭവമത്സരമാണ്, അതിനാൽ വീണ്ടും ശ്രമിക്കാവുന്നതായി തുടരും. ഓരോ ദാതാവിനുമുള്ള നിരക്ക് പരിമിതപ്പെടുത്തൽ (`open-sse/services/rateLimitManager.ts`) `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, `RATE_LIMIT_AUTO_ENABLE` എന്നിവയാൽ പ്രത്യേകം നിയന്ത്രിക്കപ്പെടുന്നു — `.env.example` കാണുക.

**ഇത് പ്രവർത്തിച്ചുവെന്ന് എങ്ങനെ സ്ഥിരീകരിക്കാം**: നിങ്ങളുടെ agent/cron വേഗത്തിൽ തുടർച്ചയായി രണ്ടുതവണ പ്രവർത്തിപ്പിച്ച് രണ്ടും വിജയിക്കുന്നുവെന്ന് സ്ഥിരീകരിക്കുക. പരിഹാരത്തിന് മുമ്പ്, രണ്ടാമത്തെ പ്രവർത്തനം സാധാരണയായി `429`/`401` പിശക് സൃഷ്ടിക്കും. പരിഹാരത്തിന് ശേഷം, പരാജയങ്ങൾ (ഉണ്ടെങ്കിൽ) സുതാര്യമായി വീണ്ടും ശ്രമിക്കപ്പെടുകയും കോൾ പൂർത്തിയാകുകയും ചെയ്യും. നിങ്ങൾക്ക് `curl /monitoring/health` പ്രവർത്തിപ്പിച്ച് provider കണക്ഷനുകളിലെ `rateLimitedUntil` ഫീൽഡും ബാധിച്ച provider-കൾക്കായുള്ള `circuitBreakers.providerBreakers[].state`-ഉം നിരീക്ഷിക്കാം — state എന്നത് `CLOSED`, `DEGRADED`, `OPEN`, അല്ലെങ്കിൽ `HALF_OPEN` എന്നിവയിൽ ഒന്നായിരിക്കും (`src/shared/utils/circuitBreaker.ts` കാണുക); തുടർച്ചയായി പരാജയപ്പെടുന്ന ഒരു provider, reset window ഒരു probe കടത്തിവിടുന്നതിന് (`HALF_OPEN`) മുമ്പ് `CLOSED → DEGRADED → OPEN` എന്ന ക്രമത്തിലേക്ക് മാറും.

**നിങ്ങൾക്ക് ഇപ്പോഴും 429 കാണുന്നുവെങ്കിൽ**: ആ provider-ന്റെ സജീവ account അതിന്റെ _quota_ യഥാർത്ഥത്തിൽ പൂർണ്ണമായി ഉപയോഗിച്ചുകഴിഞ്ഞിരിക്കുന്നു (rate മാത്രമല്ല). OmniRoute dashboard → Providers → Accounts എന്നതിൽ അതേ provider-നായി രണ്ടാമത്തെ account ചേർക്കുക, അല്ലെങ്കിൽ മറ്റൊരു സൗജന്യ provider (ഉദാ. `routeway`, `auggie`) കൂടി ഉൾപ്പെടുത്തുക. താൽക്കാലിക rate/400/401 പ്രശ്നങ്ങളിൽ മാത്രമേ rotation സഹായിക്കൂ; quota പൂർണ്ണമായി തീർന്നാൽ രണ്ടാമത്തെ credential അല്ലെങ്കിൽ മറ്റൊരു provider ആവശ്യമാണ്.

**vision models-ൽ (`auto/vision`, `bazaarlink/*`) 403 കാണുന്നുവെങ്കിൽ**: കണക്റ്റുചെയ്ത account-ന് vision ഉൾപ്പെടുന്ന പണമടച്ച plan ഇല്ല, അല്ലെങ്കിൽ API key-ക്ക് ആവശ്യമായ permissions ഇല്ല. key scope-ൽ vision/multimodal ഉൾപ്പെടുന്നുവെന്ന് provider dashboard-ൽ സ്ഥിരീകരിക്കുക, അല്ലെങ്കിൽ പണമടച്ച tier account കണക്റ്റുചെയ്ത് അതിനെ vision target ആയി നിലനിർത്തുക.

## npm install മുന്നറിയിപ്പുകൾ (ERESOLVE / peer / deprecated)

നിങ്ങൾ `npm install -g omniroute` പ്രവർത്തിപ്പിക്കുമ്പോൾ, `npm warn ERESOLVE`, peer-dependency അറിയിപ്പുകൾ, `deprecated` സന്ദേശങ്ങൾ എന്നിവ പോലുള്ള നിരവധി മുന്നറിയിപ്പുകൾ കണ്ടേക്കാം. **ഇവ പ്രതീക്ഷിക്കാവുന്നതും ദോഷകരമല്ലാത്തതുമാണ്.** ഔട്ട്പുട്ടിൽ `added <N> packages` എന്ന് കാണുന്നുവെങ്കിൽ ഇൻസ്റ്റാളേഷൻ വിജയിച്ചു.

peer-dependency പരിഹാര മുന്നറിയിപ്പുകൾ ഒഴിവാക്കാൻ, OmniRoute പിന്തുണയ്ക്കുന്ന ഇൻസ്റ്റാളേഷൻ രീതി ഉപയോഗിക്കുക:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps`, `ERESOLVE`, peer-dependency അറിയിപ്പുകൾ എന്നിവ മാത്രമേ ഒഴിവാക്കൂ. ഡിപ്രിക്കേഷൻ അറിയിപ്പുകൾ തുടർന്നും ദൃശ്യമാകും, കാരണം അവ പരോക്ഷമായ മൂന്നാം കക്ഷി പാക്കേജുകളിൽ നിന്നാണ് വരുന്നത്; ഇൻസ്റ്റാളേഷൻ പരാജയപ്പെട്ടുവെന്ന് അവ സൂചിപ്പിക്കുന്നില്ല.

OmniRoute-ന്റെ നിയന്ത്രണത്തിലല്ലാത്ത മൂന്നാം കക്ഷി പാക്കേജുകളിലെ കാലഹരണപ്പെട്ട peer-dependency പരിധികളിൽ നിന്നാണ് മുന്നറിയിപ്പുകൾ വരുന്നത്:

1. **`marked-terminal`-ന് `marked >=1 <16` വേണം, എന്നാൽ `marked@18` കണ്ടെത്തി** — പ്രായോഗികമായി ഇത് പ്രശ്നമില്ലാതെ പ്രവർത്തിക്കുന്നു; upstream peer പരിധി കാലഹരണപ്പെട്ടതാണ്.
2. **`deprecated prebuild-install@7.1.3`** — പരോക്ഷമായ ഒരു native-binary fetch സഹായി. പിൻ ചെയ്ത `wreq-js` transport binding ഇൻസ്റ്റാൾ ചെയ്യാൻ ഇത്
   ഉപയോഗിക്കുന്നില്ല, കൂടാതെ web-cookie provider transport സജ്ജീകരണം പരാജയപ്പെട്ടുവെന്നും ഇത് സൂചിപ്പിക്കുന്നില്ല.

**നടപടിയൊന്നും ആവശ്യമില്ല** — upstream പാക്കേജുകൾ fork ചെയ്യാതെ മുന്നറിയിപ്പുകൾ പൂർണ്ണമായി നിശ്ശബ്ദമാക്കാനാവില്ല.

## Gemini Web-ഉം Playwright Chromium-ഉം

Playwright Chromium ഇൻസ്റ്റാൾ ചെയ്തിട്ടില്ലെന്ന സന്ദേശത്തോടെ ഒരു Gemini Web അഭ്യർത്ഥന `503` നൽകുന്നുവെങ്കിൽ,
npm പാക്കേജ് നിലവിലുണ്ട്, എന്നാൽ ബ്രൗസർ ബൈനറി ലഭ്യമല്ല.
Playwright മനഃപൂർവം ബ്രൗസർ ഡൗൺലോഡുകളെ npm പാക്കേജ്
ഇൻസ്റ്റാളേഷനിൽ നിന്ന് വേർതിരിച്ച് സൂക്ഷിക്കുന്നു, അതിനാൽ ബ്രൗസർ ഇൻസ്റ്റാൾ ചെയ്യുന്നതുവരെ ഈ പ്രതികരണം പ്രതീക്ഷിക്കാവുന്നതാണ്.

ഒരു global npm ഇൻസ്റ്റാളേഷനായി, OmniRoute പാക്കേജിന്റെ
ഡയറക്ടറിയിൽ നിന്ന് Chromium ഇൻസ്റ്റാൾ ചെയ്യുക, അങ്ങനെ ബ്രൗസർ കാഷ് അതേ Playwright ഇൻസ്റ്റാളേഷന്റെ ഭാഗമായിരിക്കും:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ഇൻസ്റ്റാളേഷനുശേഷം OmniRoute പുനരാരംഭിക്കുക, തുടർന്ന് Gemini Web അഭ്യർത്ഥന വീണ്ടും ശ്രമിക്കുക. നിങ്ങൾ
ഒരു Docker image-ൽ നിന്ന് OmniRoute പ്രവർത്തിപ്പിക്കുന്നുവെങ്കിൽ, Chromium-ഉം അതിന്റെ dependencies-ഉം ഉൾപ്പെടുത്തിയിരിക്കുന്ന `-web` image (അല്ലെങ്കിൽ `runner-web`
build target) ഉപയോഗിക്കുക; base image-ൽ അവ
ഉൾപ്പെടുന്നില്ല.

## ആന്റിവൈറസ് തെറ്റായ പോസിറ്റീവുകൾ

<a name="antivirus-false-positives"></a>

### Avast/AVG `README.md`-നെ `MD:HttpRequest-inf[Susp]` ആയി ക്വാറന്റൈൻ ചെയ്യുന്നു

**ഇത് ഒരു തെറ്റായ പോസിറ്റീവാണ്. ഒന്നും ബാധിക്കപ്പെട്ടിട്ടില്ല, യാതൊരു നടപടിയും ആവശ്യമില്ല.**

HTTP അഭ്യർത്ഥനകളുടേതെന്ന് തോന്നിക്കുന്ന നിരവധി ലിങ്കുകൾ അടങ്ങിയ പ്ലെയിൻ-ടെക്സ്റ്റ്/Markdown ഫയലുകളെ ഫ്ലാഗ് ചെയ്യുന്ന ഒരു ഹ്യൂറിസ്റ്റിക് Avast-ഉം AVG-യും പ്രവർത്തിപ്പിക്കുന്നു. OmniRoute-ന്റെ `README.md` npm പാക്കേജിനുള്ളിലാണ് ലഭ്യമാക്കുന്നത് (അത് `package.json` → `files` എന്നതിൽ പട്ടികപ്പെടുത്തിയിരിക്കുന്നു), അതിനാൽ ഗ്ലോബൽ ഇൻസ്റ്റാൾ ചെയ്യുമ്പോൾ അത് `node_modules/omniroute/README.md` എന്നതിൽ എത്തുന്നു — കൂടാതെ അതിൽ ഏകദേശം 15 `http://localhost:20128/...` ഉദാഹരണങ്ങളുണ്ട് (MCP HTTP/SSE എൻഡ്പോയിന്റുകൾ, A2A `.well-known` URL, `curl` സ്നിപ്പറ്റുകൾ). ആ ലിങ്കുകളുടെ സാന്ദ്രത ഹ്യൂറിസ്റ്റിക് പ്രവർത്തനക്ഷമമാക്കാൻ മതിയാകുന്നു.

ഇത് അടുത്തിടെയാണ് ആരംഭിച്ചതെങ്കിൽ: ഫയലിന്റെ സ്വഭാവത്തിൽ മാറ്റമൊന്നും വന്നിട്ടില്ല. README-യിലെ എൻഡ്പോയിന്റ് പട്ടിക വികസിച്ചു (MCP HTTP + SSE + A2A ചേർത്തു), കൂടുതൽ `curl` ഉദാഹരണങ്ങളും ഉൾപ്പെടുത്തി; ഇതാണ് അതിനെ പരിധിക്കപ്പുറം എത്തിച്ചത്.

ഈ ഫയൽ പ്രവർത്തനരഹിതമായ ഡോക്യുമെന്റേഷൻ മാത്രമാണ്; ഇതിൽ എക്സിക്യൂട്ട് ചെയ്യാവുന്ന ഉള്ളടക്കമൊന്നുമില്ല. നിങ്ങൾക്ക് ഇത് ക്വാറന്റൈനിൽനിന്ന് സുരക്ഷിതമായി പുനഃസ്ഥാപിക്കാം.

**എന്ത് ചെയ്യണം:**

1. **അറിയിപ്പുകൾ നിർത്തുക** — നിങ്ങളുടെ ആന്റിവൈറസിൽ ഇൻസ്റ്റാൾ ഡയറക്ടറി ഒഴിവാക്കുക
   (Avast: Settings → Exceptions); അതിൽ നിങ്ങളുടെ ഗ്ലോബൽ `node_modules` പാത്ത് കൂടാതെ/അല്ലെങ്കിൽ
   OmniRoute ഡാറ്റ ഡയറക്ടറി (`~/.omniroute/`) ചേർക്കുക.
2. **തെറ്റായ പോസിറ്റീവ് റിപ്പോർട്ട് ചെയ്യുക** — <https://www.avast.com/false-positive-file-form.php>,
   ക്വാറന്റൈൻ ചെയ്ത `README.md` അറ്റാച്ച് ചെയ്യുക. ഒരു ടെക്സ്റ്റ് ഫയലിനോട് വെൻഡറുടെ ഹ്യൂറിസ്റ്റിക് അമിതമായി പ്രതികരിക്കുന്നതാണ് കാരണം എന്നതിനാൽ, എല്ലാവർക്കും സഹായകരമാകുന്ന പരിഹാരം ഇതാണ്.

**ഞങ്ങളുടെ ഭാഗത്ത് ഇത് "പരിഹരിക്കാത്തത്" എന്തുകൊണ്ട്:** എല്ലാ ഉദാഹരണങ്ങളും `http://localhost` ആണ്; സ്വയം ഒപ്പിട്ട സർട്ടിഫിക്കറ്റുകളുടെ ബുദ്ധിമുട്ടില്ലാതെ localhost-ൽ `https` ഉപയോഗിക്കാൻ കഴിയില്ല. ഒരു വെൻഡറുടെ ഹ്യൂറിസ്റ്റിക്കിനെ മറികടക്കാനായി ഡോക്യുമെന്റേഷൻ വികൃതമാക്കുന്നത് ഒരു സ്കാനർ ബഗിനെ തൃപ്തിപ്പെടുത്താൻ എല്ലാ വായനക്കാർക്കും ദോഷകരമാകും.

### Kaspersky ഡെസ്ക്ടോപ്പ് ആപ്പിനെ `PDM:Trojan.Win32.Generic` ആയി ഫ്ലാഗ് ചെയ്യുന്നു

**ഇത് പെരുമാറ്റാധിഷ്ഠിത ഹ്യൂറിസ്റ്റിക്കിൽനിന്നുള്ള ഒരു തെറ്റായ പോസിറ്റീവാണ്. ഒന്നും ബാധിക്കപ്പെട്ടിട്ടില്ല.** Kaspersky-യുടെ `PDM:` പ്രിഫിക്സ് സൂചിപ്പിക്കുന്നത്, അറിയപ്പെടുന്ന മാൽവെയറുമായി പൊരുത്തപ്പെടുത്തുന്നതിനുപകരം ഇൻസ്റ്റാളർ _എന്ത് ചെയ്യുന്നു_ എന്ന് വിലയിരുത്തുന്ന അതിന്റെ Proactive Defense Module-ൽനിന്നാണ് (System Watcher) ഈ വിധി വരുന്നത് എന്നാണ്. ഇത് പ്രവർത്തനക്ഷമമാകുമ്പോൾ, Kaspersky മുഴുവൻ ഇൻസ്റ്റാളേഷനും "റോൾ ബാക്ക്" ചെയ്യുന്നു — ഇതിനകം എഴുതിയ ഫയലുകൾ ഇല്ലാതാക്കുന്നു — അതിനാൽ ആപ്പ് തകരാറിലാകുകയോ അപ്രത്യക്ഷമാകുകയോ ചെയ്യുന്നു.

ഇത് ഫ്ലാഗ് ചെയ്യുന്ന ഫയലുകൾ ഡെസ്ക്ടോപ്പ് ആപ്പിനൊപ്പം ബണ്ടിൽ ചെയ്തിട്ടുള്ള, പ്രഖ്യാപിതവും ഓപ്പൺ സോഴ്സുമായ ഡിപ്പൻഡൻസികളുടെ സാധാരണ ഭാഗങ്ങളാണ്, ഉദാഹരണത്തിന്:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js`, `workerProcessEntry.js` എന്നിവ — ആപ്പിനുള്ളിലെ പ്രൊവൈഡർ ലോഗിനും ബ്രൗസർ പിന്തുണയുള്ള ചാറ്റിനുമായി ഉപയോഗിക്കുന്ന ബ്രൗസർ ഓട്ടോമേഷൻ ലൈബ്രറിയായ [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — വെബ്-കുക്കി പ്രൊവൈഡറുകളിൽ ബ്രൗസർ ഫിംഗർപ്രിന്റ് ചെയ്ത HTTP-യ്ക്കായി ഉപയോഗിക്കുന്ന പിൻ ചെയ്ത `wreq-js` നേറ്റീവ് ബൈൻഡിങ് (`<arch>` എന്നത് `x64` അല്ലെങ്കിൽ `arm64` ആണ്).

**ഇത് പ്രവർത്തനക്ഷമമാകുന്നത് എന്തുകൊണ്ട്:** Windows ഇൻസ്റ്റാളർ **ഇതുവരെ കോഡ്-സൈൻ ചെയ്തിട്ടില്ല**, അതിനാൽ ഒപ്പിടാത്ത NSIS ഇൻസ്റ്റാളറിന് യാതൊരു റെപ്യൂട്ടേഷനും ഇല്ലാത്തതിനാൽ പെരുമാറ്റാധിഷ്ഠിത ഹ്യൂറിസ്റ്റിക്കുകൾ പരമാവധി ആക്രമണാത്മകതയോടെ പ്രവർത്തിക്കുന്നു. ബണ്ടിൽ ചെയ്ത നേറ്റീവ് DLL-ഉം `%LOCALAPPDATA%\Programs\OmniRoute` എന്നതിന് കീഴിൽ എഴുതുന്ന നൂറുകണക്കിന് `.js` ഫയലുകളും (Next.js സ്റ്റാൻഡ്എലോൺ ബിൽഡിൽനിന്നുള്ള ഹാഷ്-സഫിക്സ് ചേർത്ത പാക്കേജ് ഡയറക്ടറികൾ ഉൾപ്പെടെ) കൂടിച്ചേരുമ്പോൾ, ഹ്യൂറിസ്റ്റിക് പ്രവർത്തനക്ഷമമാകാൻ അത് മതിയാകുന്നു. കോഡ് സൈനിങ് ആസൂത്രണം ചെയ്തിട്ടുണ്ട്; അത് നടപ്പിലാകുന്നതുവരെ പുതിയ റിലീസുകളിലും ഇത് ആവർത്തിക്കാം.

**എന്ത് ചെയ്യണം:**

1. **ആദ്യം നിങ്ങളുടെ ഡൗൺലോഡ് പരിശോധിക്കുക** (ഫയലിൽ കൃത്രിമം നടന്നിട്ടില്ലെന്ന് ഇത് ഉറപ്പാക്കുന്നു). ഓരോ റിലീസിലും
   `latest.yml` പ്രസിദ്ധീകരിക്കുന്നു; അതിലെ `sha512` ഫീൽഡ് (base64) `OmniRoute.Setup.<version>.exe`
   ഇൻസ്റ്റാളറിനെ ഉൾക്കൊള്ളുന്നു. PowerShell-ൽ, ഇൻസ്റ്റാളർ അടങ്ങിയ ഫോൾഡറിൽനിന്ന്:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ഔട്ട്പുട്ട് `latest.yml` → `sha512` എന്നതുമായി പൊരുത്തപ്പെടണം. പൊരുത്തപ്പെടുന്നില്ലെങ്കിൽ, ഫയൽ ഇല്ലാതാക്കി
   [GitHub റിലീസ് പേജിൽനിന്ന്](https://github.com/diegosouzapw/OmniRoute/releases) മാത്രം വീണ്ടും ഡൗൺലോഡ് ചെയ്യുക.
2. **പുനഃസ്ഥാപിക്കുക + ഒഴിവാക്കുക** — റോൾ ബാക്ക് ചെയ്ത ഇനങ്ങൾ ക്വാറന്റൈനിൽനിന്ന് പുനഃസ്ഥാപിച്ച്
   `%LOCALAPPDATA%\Programs\OmniRoute`-നായി ഒരു ഒഴിവാക്കൽ ചേർക്കുക (Kaspersky → Settings → Threats and Exclusions),
   തുടർന്ന് വീണ്ടും ഇൻസ്റ്റാൾ ചെയ്യുക.
3. **തെറ്റായ പോസിറ്റീവ് റിപ്പോർട്ട് ചെയ്യുക** — <https://opentip.kaspersky.com/>. ഉപയോക്താക്കൾ സമർപ്പിക്കുന്ന FP റിപ്പോർട്ടുകൾ അലൗലിസ്റ്റിങ് വേഗത്തിലാക്കാൻ യഥാർത്ഥത്തിൽ സഹായിക്കുന്നു.

## Node.js അനുയോജ്യത

<a name="nodejs-compatibility"></a>

### ലോഗിൻ പേജ് ക്രാഷാകുന്നു അല്ലെങ്കിൽ "Module self-registration" പിശക് കാണിക്കുന്നു

**കാരണം:** OmniRoute അംഗീകരിച്ച സുരക്ഷിത റൺടൈമിന്റെ ഏറ്റവും കുറഞ്ഞ പതിപ്പിന് പുറത്തുള്ള ഒരു Node.js പതിപ്പാണ് നിങ്ങൾ പ്രവർത്തിപ്പിക്കുന്നത്. OmniRoute ആവശ്യപ്പെടുന്ന സുരക്ഷാ പാച്ചുകളുള്ള ഏറ്റവും കുറഞ്ഞ പതിപ്പിനെക്കാൾ പഴയ Node 22 അല്ലെങ്കിൽ 24 പാച്ച് ലെവൽ ഉപയോഗിക്കുന്നതാണ് ഏറ്റവും സാധാരണമായ സാഹചര്യം.

**ലക്ഷണങ്ങൾ:**

- ലോഗിൻ പേജ് ശൂന്യമായ സ്ക്രീനോ സെർവർ പിശകോ കാണിക്കുന്നു
- കൺസോളിൽ `Error: Module did not self-register` അല്ലെങ്കിൽ സമാനമായ നേറ്റീവ് ബൈൻഡിങ് പിശകുകൾ കാണിക്കുന്നു
- റൺടൈം പിന്തുണയ്ക്കുന്ന സുരക്ഷാ നയത്തിന് പുറത്താണെങ്കിൽ, നിങ്ങളുടെ Node പതിപ്പ് ഉൾപ്പെടുന്ന ഒരു **ഓറഞ്ച് മുന്നറിയിപ്പ് ബാനർ** ലോഗിൻ പേജിൽ കാണിക്കുന്നു

**പരിഹാരം:**

1. പിന്തുണയ്ക്കുന്ന ഒരു Node.js LTS റിലീസ് ഇൻസ്റ്റാൾ ചെയ്യുക (ശുപാർശ ചെയ്യുന്നത്: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. നിങ്ങളുടെ പതിപ്പ് പരിശോധിക്കുക: 24.x LTS ശ്രേണിയിൽ `node --version` എന്നത് `v24.0.0` അല്ലെങ്കിൽ അതിലും പുതിയ പതിപ്പ് കാണിക്കണം
3. OmniRoute വീണ്ടും ഇൻസ്റ്റാൾ ചെയ്യുക: `npm install -g omniroute`
4. പുനരാരംഭിക്കുക: `omniroute`

> **പിന്തുണയ്ക്കുന്ന സുരക്ഷിത പതിപ്പുകൾ:** `>=22.22.2 <23` അല്ലെങ്കിൽ `>=24.0.0 <27`. Node.js 24.x LTS (Krypton), Node.js 26 എന്നിവ പൂർണ്ണമായി പിന്തുണയ്ക്കുന്നു.

### npm v11+: `better-sqlite3` ഇൻസ്റ്റാൾ ചെയ്തിട്ടില്ല (മൊഡ്യൂൾ കണ്ടെത്താനാകുന്നില്ല)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**കാരണം:** Node.js 24+ നൊപ്പം ലഭിക്കുന്ന npm v11, ഐച്ഛിക ഡിപെൻഡൻസികൾക്കായുള്ള ഇൻസ്റ്റാൾ സ്ക്രിപ്റ്റുകൾ ഡിഫോൾട്ടായി തടയുന്നു. `better-sqlite3` എന്നത് `optionalDependencies`-ൽ ഉൾപ്പെടുത്തിയിട്ടുള്ളതിനാലും നേറ്റീവ് കംപൈലേഷൻ (`node-gyp rebuild`) ആവശ്യമായതിനാലും npm യാതൊരു അറിയിപ്പുമില്ലാതെ അത് ഒഴിവാക്കുന്നു.

**ലക്ഷണങ്ങൾ:**

- ആരംഭിക്കുമ്പോൾ `Cannot find module 'better-sqlite3'` എന്ന പിശകോടെ സെർവർ ക്രാഷാകുന്നു
- `ls node_modules/better-sqlite3` എന്നത് "No such file or directory" എന്ന് കാണിക്കുന്നു
- `npm ls better-sqlite3` എന്നത് `(empty)` എന്ന് കാണിക്കുന്നു

**പരിഹാരം:**

1. ഇൻസ്റ്റാൾ സ്ക്രിപ്റ്റുകൾ അംഗീകരിച്ച് വീണ്ടും ഇൻസ്റ്റാൾ ചെയ്യുക:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. അല്ലെങ്കിൽ മുൻകൂട്ടി ബിൽഡ് ചെയ്ത പാക്കേജ് നേരിട്ട് ഇൻസ്റ്റാൾ ചെയ്യുക:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ഇത് പ്രവർത്തിക്കുന്നുണ്ടെന്ന് പരിശോധിക്കുക: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**കാരണം:** ആഗോളതലത്തിൽ `npm install -g omniroute` പ്രവർത്തിപ്പിച്ചതിന് ശേഷം, പാക്കേജിനുള്ളിലെ `better-sqlite3` നേറ്റീവ് ബൈനറി, പ്രാദേശികമായി പ്രവർത്തിക്കുന്നതിൽനിന്ന് വ്യത്യസ്തമായ ആർക്കിടെക്ചറിനോ Node.js ABI-ക്കോ വേണ്ടി കംപൈൽ ചെയ്തതായിരിക്കാം. മുൻകൂട്ടി ബിൽഡ് ചെയ്ത ബൈനറി നിങ്ങളുടെ പരിതസ്ഥിതിയുമായി പൊരുത്തപ്പെടാത്തപ്പോൾ, macOS-ൽ (Apple Silicon, Intel എന്നിവ രണ്ടിലും) ഇത് സാധാരണമാണ്.

**ലക്ഷണങ്ങൾ:**

- ആരംഭിച്ച ഉടൻതന്നെ `dlopen` പിശകോടെ സെർവർ പരാജയപ്പെടുന്നു
- പിശകിൽ `slice is not valid mach-o file` ഉൾപ്പെട്ടിരിക്കുന്നു
- പൂർണ്ണമായ ഉദാഹരണം:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**പരിഹാരം — നിങ്ങളുടെ പ്രാദേശിക പരിതസ്ഥിതിക്കായി വീണ്ടും ബിൽഡ് ചെയ്യുക (Node.js ഡൗൺഗ്രേഡ് ആവശ്യമില്ല):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **കുറിപ്പ്:** ഇത് നിങ്ങളുടെ പ്രാദേശിക Node.js പതിപ്പിനും CPU ആർക്കിടെക്ചറിനും അനുയോജ്യമായി നേറ്റീവ് ബൈൻഡിങ് വീണ്ടും കംപൈൽ ചെയ്ത് ബൈനറി പൊരുത്തക്കേട് പരിഹരിക്കുന്നു. ഔദ്യോഗികമായി പിന്തുണയ്ക്കുന്ന റൺടൈം പരിധി **`>=22.22.2 <23` അല്ലെങ്കിൽ `>=24.0.0 <27`** ആണ് (`src/shared/utils/nodeRuntimeSupport.ts`-ലെ `SUPPORTED_NODE_RANGE`, `package.json`-ലെ `engines` ഫീൽഡുമായി വിന്യസിച്ചിരിക്കുന്നു). Node.js 24.x LTS (Krypton), Node.js 26 എന്നിവ `better-sqlite3` v12.x-നൊപ്പം പൂർണ്ണമായി പിന്തുണയ്ക്കുന്നു.

## പ്രോക്സി പ്രശ്നങ്ങൾ

<a name="proxy-issues"></a>

### പ്രൊവൈഡർ സാധൂകരണത്തിൽ "fetch failed" എന്ന് കാണിക്കുന്നു

**കാരണം:** API കീ സാധൂകരണ എൻഡ്പോയിന്റ് (`POST /api/providers/validate`) മുമ്പ് പ്രോക്സി കോൺഫിഗറേഷൻ ഒഴിവാക്കിയിരുന്നതിനാൽ, പ്രോക്സി റൂട്ടിംഗ് ആവശ്യമായ പരിതസ്ഥിതികളിൽ പരാജയങ്ങൾ സംഭവിച്ചിരുന്നു.

**പരിഹാരം (v3.5.5+):** ഇത് ഇപ്പോൾ പരിഹരിച്ചിട്ടുണ്ട്. പ്രൊവൈഡർ സാധൂകരണം `runWithProxyContext` വഴി റൂട്ട് ചെയ്യപ്പെടുകയും, പ്രൊവൈഡർ-തലത്തിലെയും ആഗോളതലത്തിലെയും പ്രോക്സി ക്രമീകരണങ്ങൾ സ്വയമേവ പാലിക്കുകയും ചെയ്യുന്നു.

### ടോക്കൺ ഹെൽത്ത് ചെക്ക് "fetch failed" എന്ന പിശകോടെ പരാജയപ്പെടുന്നു

**കാരണം:** പശ്ചാത്തല OAuth ടോക്കൺ പുതുക്കൽ ഓരോ കണക്ഷനുമുള്ള പ്രോക്സി കോൺഫിഗറേഷൻ പരിഹരിച്ചിരുന്നില്ല.

**പരിഹാരം (v3.5.5+):** പുതുക്കാൻ ശ്രമിക്കുന്നതിന് മുമ്പ് ടോക്കൺ ഹെൽത്ത് ചെക്ക് ഷെഡ്യൂളർ ഇപ്പോൾ ഓരോ കണക്ഷനുമുള്ള പ്രോക്സി കോൺഫിഗറേഷൻ പരിഹരിക്കുന്നു. v3.5.5+ ലേക്ക് അപ്ഡേറ്റ് ചെയ്യുക.

### SOCKS5 പ്രോക്സി "invalid onRequestStart method" എന്ന് നൽകുന്നു

**കാരണം:** Node.js 22-ൽ, undici@8 ഡിസ്പാച്ചർ Node-ന്റെ ബിൽറ്റ്-ഇൻ `fetch()` നടപ്പാക്കലുമായി പൊരുത്തപ്പെടുന്നില്ല.

**പരിഹാരം (v3.5.5+):** ഒരു പ്രോക്സി ഡിസ്പാച്ചർ സജീവമായിരിക്കുമ്പോൾ OmniRoute ഇപ്പോൾ undici-യുടെ സ്വന്തം `fetch()` ഫങ്ഷൻ ഉപയോഗിക്കുന്നു, അതുവഴി സ്ഥിരതയുള്ള പെരുമാറ്റം ഉറപ്പാക്കുന്നു. v3.5.5+ ലേക്ക് അപ്ഡേറ്റ് ചെയ്യുക.

### WSL-ന് കീഴിലുള്ള MITM പ്രോക്സി: Windows ഹോസ്റ്റിലെ ഡെസ്ക്ടോപ്പ് ആപ്പുകൾ ഇന്റർസെപ്റ്റ് ചെയ്യപ്പെടുന്നില്ല

**കാരണം:** MITM പ്രോക്സിയും അതിന്റെ CA സർട്ടിഫിക്കറ്റും OmniRoute പ്രവർത്തിക്കുന്ന പരിതസ്ഥിതിയിലാണ് ഇൻസ്റ്റാൾ ചെയ്യപ്പെടുന്നത്. WSL-ന് കീഴിൽ ആ പരിതസ്ഥിതി Linux ഗസ്റ്റാണ്, അതേസമയം AI ഡെസ്ക്ടോപ്പ് ആപ്പുകൾ (Kiro, Trae, Copilot, Zed, …) Windows ഹോസ്റ്റിലാണ് പ്രവർത്തിക്കുന്നത്. ഹോസ്റ്റ് ആപ്പുകൾ ഗസ്റ്റിന്റെ സർട്ടിഫിക്കറ്റ് സ്റ്റോറിനെ വിശ്വസിക്കുകയോ ഗസ്റ്റിന്റെ സിസ്റ്റം പ്രോക്സിയിലൂടെ റൂട്ട് ചെയ്യുകയോ ചെയ്യുന്നില്ല, അതിനാൽ അവിടെ ഡെസ്ക്ടോപ്പ് ഇന്റർസെപ്ഷൻ പ്രവർത്തിക്കില്ല.

**ശുപാർശ:** നിങ്ങൾ ഇന്റർസെപ്റ്റ് ചെയ്യാൻ ആഗ്രഹിക്കുന്ന ഡെസ്ക്ടോപ്പ് ആപ്പുകൾ പ്രവർത്തിക്കുന്ന അതേ OS-ൽ OmniRoute നേറ്റീവായി പ്രവർത്തിപ്പിക്കുക (Windows ആപ്പുകൾക്ക് Windows; macOS/Linux-നും അതുപോലെ). ഹോസ്റ്റ് ആപ്പുകളെ ലക്ഷ്യമിട്ടുകൊണ്ട് OmniRoute WSL-നുള്ളിൽ നിലനിർത്തണമെങ്കിൽ, ജനറേറ്റ് ചെയ്ത CA സർട്ടിഫിക്കറ്റിനെ Windows ഹോസ്റ്റിൽ മാനുവലായി വിശ്വസനീയമാക്കുകയും ഓരോ ഹോസ്റ്റ് ആപ്പിന്റെയും നെറ്റ്വർക്ക്/പ്രോക്സി ക്രമീകരണങ്ങൾ WSL പ്രോക്സി എൻഡ്പോയിന്റിലേക്ക് ചൂണ്ടുകയും വേണം — ഇത് പിന്തുണയ്ക്കാത്തതും എളുപ്പത്തിൽ തകരാവുന്നതുമായ സജ്ജീകരണമാണ്.

രണ്ട് അക്കൗണ്ടുകൾ ഒരേ രജിസ്റ്റർ ചെയ്ത ക്ലയന്റ് പങ്കിടുമ്പോൾ (v3.8.0-ന് മുമ്പ് ഇംപോർട്ട് ചെയ്ത കണക്ഷനുകൾ),
ഒരു അക്കൗണ്ടിന്റെ ടോക്കൺ പുതുക്കുന്നത് മറ്റേ അക്കൗണ്ടിന്റെ റിഫ്രഷ് ടോക്കൺ അസാധുവാക്കുന്നു.

**പരിഹാരം (v3.8.0+):** ബാധിച്ച കണക്ഷനുകൾ വീണ്ടും ഇംപോർട്ട് ചെയ്യുക.

## ക്ലൗഡ് പ്രശ്നങ്ങൾ

### ക്ലൗഡ് സിങ്ക് പിശകുകൾ

1. `BASE_URL` പ്രവർത്തിച്ചുകൊണ്ടിരിക്കുന്ന നിങ്ങളുടെ ഇൻസ്റ്റൻസിലേക്കാണ് വിരൽചൂണ്ടുന്നതെന്ന് ഉറപ്പാക്കുക (ഉദാ., `http://localhost:20128`)
2. `CLOUD_URL` നിങ്ങളുടെ ക്ലൗഡ് എൻഡ്പോയിന്റിലേക്കാണ് വിരൽചൂണ്ടുന്നതെന്ന് ഉറപ്പാക്കുക (ഉദാ., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` മൂല്യങ്ങൾ സെർവർ-സൈഡ് മൂല്യങ്ങളുമായി പൊരുത്തപ്പെടുത്തി നിലനിർത്തുക

### ക്ലൗഡിൽ `stream=false` 500 നൽകുന്നു

**ലക്ഷണം:** നോൺ-സ്ട്രീമിംഗ് കോളുകൾക്കായുള്ള ക്ലൗഡ് എൻഡ്പോയിന്റിൽ `Unexpected token 'd'...`.

**കാരണം:** ക്ലയന്റ് JSON പ്രതീക്ഷിക്കുമ്പോൾ അപ്സ്ട്രീം SSE പേലോഡ് നൽകുന്നു.

**താൽക്കാലിക പരിഹാരം:** ക്ലൗഡിലേക്കുള്ള നേരിട്ടുള്ള കോളുകൾക്ക് `stream=true` ഉപയോഗിക്കുക. ലോക്കൽ റൺടൈമിൽ SSE→JSON ഫാൾബാക്ക് ഉൾപ്പെടുത്തിയിട്ടുണ്ട്.

### ക്ലൗഡ് കണക്റ്റഡ് എന്ന് കാണിക്കുന്നുവെങ്കിലും "Invalid API key"

1. ലോക്കൽ ഡാഷ്ബോർഡിൽനിന്ന് (`/api/keys`) ഒരു പുതിയ കീ സൃഷ്ടിക്കുക
2. ക്ലൗഡ് സിങ്ക് പ്രവർത്തിപ്പിക്കുക: Enable Cloud → Sync Now
3. പഴയതോ സിങ്ക് ചെയ്യാത്തതോ ആയ കീകൾക്ക് ക്ലൗഡിൽ തുടർന്നും `401` ലഭിക്കാം

## Docker പ്രശ്നങ്ങൾ

### Docker IPv6 / കണക്ഷൻ റീസെറ്റ്

<a name="docker-ipv6"></a>

**ലക്ഷണങ്ങൾ:** `curl http://localhost:20128/v1/models` പ്രവർത്തിപ്പിക്കുമ്പോൾ `curl: (56) Recv failure: Connection reset by peer` ലഭിക്കുന്നു. ഡാഷ്ബോർഡും ഓതന്റിക്കേഷൻ ആവശ്യമില്ലാത്ത എൻഡ്പോയിന്റുകളും പ്രവർത്തിക്കുന്നു, എന്നാൽ ഓതന്റിക്കേഷൻ ആവശ്യമായ എൻഡ്പോയിന്റുകൾ പരാജയപ്പെടുന്നു — ഇത് ഒരു ഓതന്റിക്കേഷൻ പ്രശ്നമായി തോന്നുമെങ്കിലും യഥാർഥത്തിൽ അങ്ങനെയല്ല.

**കാരണം:** `docker run -p 20128:20128` എന്നത് `0.0.0.0` (IPv4), `::` (IPv6) എന്നിവ രണ്ടിലും പ്രസിദ്ധീകരിക്കുന്നു, എന്നാൽ കണ്ടെയ്നറിനുള്ളിലെ പ്രോസസ് IPv4-ൽ മാത്രമാണ് ലിസൻ ചെയ്യുന്നത്. `localhost` ആദ്യം `::1` ആയി റിസോൾവ് ചെയ്യുന്ന ഹോസ്റ്റുകളിൽ, കണക്ഷൻ പിന്നിൽ ലിസണർ ഇല്ലാത്ത IPv6 പ്രസിദ്ധീകരിച്ച പോർട്ടിലെത്തുന്നു → കണക്ഷൻ റീസെറ്റ് ചെയ്യപ്പെടുന്നു.

**പരിഹാരം:**

1. **ദ്രുത ഡയഗ്നോസ്റ്റിക്:** `curl -4 http://localhost:20128/v1/models` പ്രവർത്തിപ്പിക്കുക. `-4` ഉപയോഗിക്കുമ്പോൾ പ്രവർത്തിക്കുകയും അതില്ലാതെ പരാജയപ്പെടുകയും ചെയ്യുന്നുവെങ്കിൽ, നിങ്ങൾക്ക് IPv6 ബൈൻഡ് പൊരുത്തക്കേടുണ്ട്.
2. **സ്ഥിരമായ പരിഹാരം:** നിങ്ങളുടെ `docker run` കമാൻഡിൽ `-p 127.0.0.1:20128:20128` ഉപയോഗിച്ച് IPv4-ലേക്ക് വ്യക്തമായി ബൈൻഡ് ചെയ്യുക:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ഇത് IPv4 ബൈൻഡ് നിർബന്ധമാക്കുകയും എല്ലാ ഹോസ്റ്റ് ഇന്റർഫേസുകളിലും പ്രോക്സി ലഭ്യമാകുന്നത് ഒഴിവാക്കുകയും ചെയ്യുന്നു.

## ഡീബഗ്ഗിംഗ്

### ലോഗ് ഫയലുകൾ പ്രവർത്തനക്ഷമമാക്കുക

നിങ്ങളുടെ `.env` ഫയലിൽ `APP_LOG_TO_FILE=true` സജ്ജമാക്കുക. ആപ്ലിക്കേഷൻ ലോഗുകൾ `logs/`-ന് കീഴിൽ എഴുതപ്പെടുന്നു.
ക്രമീകരണങ്ങളിൽ കോൾ ലോഗ് പൈപ്പ്ലൈൻ പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ, റിക്വസ്റ്റ് ആർട്ടിഫാക്റ്റുകൾ `${DATA_DIR}/call_logs/`-ന് കീഴിൽ സംഭരിക്കപ്പെടുന്നു.
പൈപ്പ്ലൈൻ ക്യാപ്ചർ പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ, സ്ട്രീം ചങ്ക് പേലോഡുകൾ ഒഴിവാക്കാൻ `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` സജ്ജമാക്കുക, അല്ലെങ്കിൽ ആർട്ടിഫാക്റ്റിന്റെ KB പരിധി മാറ്റാൻ `CALL_LOG_PIPELINE_MAX_SIZE_KB` ക്രമീകരിക്കുക.

### പ്രൊവൈഡറിന്റെ ആരോഗ്യനില പരിശോധിക്കുക

```bash
# ഹെൽത്ത് ഡാഷ്ബോർഡ്
http://localhost:20128/dashboard/health

# API ഹെൽത്ത് പരിശോധന
curl http://localhost:20128/api/monitoring/health
```

### റൺടൈം സ്റ്റോറേജ്

- പ്രധാന സ്റ്റേറ്റ്: `${DATA_DIR}/storage.sqlite` (പ്രൊവൈഡറുകൾ, കോംബോകൾ, അപരനാമങ്ങൾ, കീകൾ, ക്രമീകരണങ്ങൾ)
- ഉപയോഗം: `storage.sqlite`-ലെ SQLite പട്ടികകൾ (`usage_history`, `call_logs`, `proxy_logs`) + ഓപ്ഷണലായി `${DATA_DIR}/call_logs/`
- ആപ്ലിക്കേഷൻ ലോഗുകൾ: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ആയിരിക്കുമ്പോൾ)
- കോൾ ലോഗ് ആർട്ടിഫാക്റ്റുകൾ: കോൾ ലോഗ് പൈപ്പ്ലൈൻ പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs പേജിലെ **Clean history** നടപടി `call_logs`, ലെഗസി
`request_detail_logs`, ലോക്കൽ `${DATA_DIR}/call_logs/` ആർട്ടിഫാക്റ്റ് ഡയറക്ടറി എന്നിവ മായ്ക്കുന്നു.

## സർക്യൂട്ട് ബ്രേക്കർ പ്രശ്നങ്ങൾ

### പ്രൊവൈഡർ OPEN അവസ്ഥയിൽ കുടുങ്ങിയിരിക്കുന്നു

ഒരു പ്രൊവൈഡറുടെ സർക്യൂട്ട് ബ്രേക്കർ OPEN ആയിരിക്കുമ്പോൾ, കൂൾഡൗൺ കാലാവധി അവസാനിക്കുന്നതുവരെ അഭ്യർത്ഥനകൾ തടയപ്പെടും.

**പരിഹാരം:**

1. **Dashboard → Settings → Resilience** എന്നതിലേക്ക് പോകുക
2. ബാധിച്ച പ്രൊവൈഡറുടെ സർക്യൂട്ട് ബ്രേക്കർ കാർഡ് പരിശോധിക്കുക
3. എല്ലാ ബ്രേക്കറുകളും മായ്ക്കാൻ **Reset All** ക്ലിക്ക് ചെയ്യുക, അല്ലെങ്കിൽ കൂൾഡൗൺ കാലാവധി അവസാനിക്കുന്നതുവരെ കാത്തിരിക്കുക
4. റീസെറ്റ് ചെയ്യുന്നതിന് മുമ്പ് പ്രൊവൈഡർ യഥാർത്ഥത്തിൽ ലഭ്യമാണെന്ന് സ്ഥിരീകരിക്കുക

### പ്രൊവൈഡർ സർക്യൂട്ട് ബ്രേക്കർ ആവർത്തിച്ച് ട്രിപ്പ് ചെയ്യുന്നു

ഒരു പ്രൊവൈഡർ ആവർത്തിച്ച് OPEN അവസ്ഥയിലേക്ക് പ്രവേശിക്കുകയാണെങ്കിൽ:

1. പരാജയ പാറ്റേൺ കണ്ടെത്താൻ **Dashboard → Health → Provider Health** പരിശോധിക്കുക
2. **Settings → Resilience → Provider Profiles** എന്നതിലേക്ക് പോയി പരാജയ പരിധി വർധിപ്പിക്കുക
3. പ്രൊവൈഡർ API പരിധികൾ മാറ്റിയിട്ടുണ്ടോ അല്ലെങ്കിൽ വീണ്ടും പ്രാമാണീകരണം ആവശ്യമാണോ എന്ന് പരിശോധിക്കുക
4. ലേറ്റൻസി ടെലിമെട്രി അവലോകനം ചെയ്യുക — ഉയർന്ന ലേറ്റൻസി ടൈംഔട്ട് അടിസ്ഥാനമാക്കിയുള്ള പരാജയങ്ങൾക്ക് കാരണമായേക്കാം

- പിന്തുണയ്ക്കുന്ന ഓഡിയോ ഫോർമാറ്റുകൾ പരിശോധിക്കുക: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ഫയൽ വലുപ്പം പ്രൊവൈഡറുടെ പരിധിക്കുള്ളിലാണെന്ന് സ്ഥിരീകരിക്കുക (സാധാരണയായി < 25MB)
- പ്രൊവൈഡർ കാർഡിൽ പ്രൊവൈഡറുടെ API കീ സാധുവാണോയെന്ന് പരിശോധിക്കുക

### സാധാരണ ഫോർമാറ്റ് പ്രശ്നങ്ങൾ

- **തിങ്കിംഗ് ടാഗുകൾ ദൃശ്യമാകുന്നില്ല** — ലക്ഷ്യ പ്രൊവൈഡർ തിങ്കിംഗിനെയും തിങ്കിംഗ് ബജറ്റ് ക്രമീകരണത്തെയും പിന്തുണയ്ക്കുന്നുണ്ടോ എന്ന് പരിശോധിക്കുക
- **ടൂൾ കോളുകൾ നഷ്ടപ്പെടുന്നു** — ചില ഫോർമാറ്റ് വിവർത്തനങ്ങൾ പിന്തുണയ്ക്കാത്ത ഫീൽഡുകൾ നീക്കം ചെയ്തേക്കാം; Playground മോഡിൽ പരിശോധിച്ചുറപ്പിക്കുക
- **സിസ്റ്റം പ്രോംപ്റ്റ് കാണുന്നില്ല** — Claude-ഉം Gemini-യും സിസ്റ്റം പ്രോംപ്റ്റുകൾ വ്യത്യസ്തമായാണ് കൈകാര്യം ചെയ്യുന്നത്; വിവർത്തന ഔട്ട്പുട്ട് പരിശോധിക്കുക
- **SDK ഒബ്ജക്റ്റിന് പകരം റോ സ്ട്രിംഗ് നൽകുന്നു** — v1.x-ൽ പരിഹരിച്ചു; OpenAI SDK Pydantic വാലിഡേഷൻ പരാജയങ്ങൾക്ക് കാരണമാകുന്ന നിലവാരമില്ലാത്ത ഫീൽഡുകൾ (`x_groq`, `usage_breakdown` തുടങ്ങിയവ) റെസ്പോൺസ് സാനിറ്റൈസർ നീക്കം ചെയ്യുന്നു. v3.x+-ലും ഇത് കാണുന്നുണ്ടെങ്കിൽ, ദയവായി ഒരു ഇഷ്യൂ ഫയൽ ചെയ്യുക.
- **GLM/ERNIE `system` റോൾ നിരസിക്കുന്നു** — v1.x-ൽ പരിഹരിച്ചു; പൊരുത്തമില്ലാത്ത മോഡലുകൾക്കായി റോൾ നോർമലൈസർ സിസ്റ്റം സന്ദേശങ്ങളെ സ്വയമേവ ഉപയോക്തൃ സന്ദേശങ്ങളിലേക്ക് ലയിപ്പിക്കുന്നു. v3.x+-ലും ഇത് കാണുന്നുണ്ടെങ്കിൽ, ദയവായി ഒരു ഇഷ്യൂ ഫയൽ ചെയ്യുക.
- **`developer` റോൾ തിരിച്ചറിയുന്നില്ല** — v1.x-ൽ പരിഹരിച്ചു; OpenAI ഇതര പ്രൊവൈഡറുകൾക്കായി സ്വയമേവ `system` എന്നതിലേക്ക് പരിവർത്തനം ചെയ്യുന്നു. v3.x+-ലും ഇത് കാണുന്നുണ്ടെങ്കിൽ, ദയവായി ഒരു ഇഷ്യൂ ഫയൽ ചെയ്യുക.
- **Gemini-യിൽ `json_schema` പ്രവർത്തിക്കുന്നില്ല** — v1.x-ൽ പരിഹരിച്ചു; `response_format` ഇപ്പോൾ Gemini-യുടെ `responseMimeType` + `responseSchema` എന്നതിലേക്ക് പരിവർത്തനം ചെയ്യപ്പെടുന്നു. v3.x+-ലും ഇത് കാണുന്നുണ്ടെങ്കിൽ, ദയവായി ഒരു ഇഷ്യൂ ഫയൽ ചെയ്യുക.

## പ്രതിരോധശേഷി ക്രമീകരണങ്ങൾ

### സ്വയമേവയുള്ള നിരക്ക്-പരിധി പ്രവർത്തനക്ഷമമാകുന്നില്ല

- സ്വയമേവയുള്ള നിരക്ക്-പരിധി API കീ ദാതാക്കൾക്ക് മാത്രമാണ് ബാധകം (OAuth/സബ്സ്ക്രിപ്ഷന് അല്ല)
- **Settings → Resilience → Provider Profiles** എന്നതിൽ സ്വയമേവയുള്ള നിരക്ക്-പരിധി പ്രവർത്തനക്ഷമമാക്കിയിട്ടുണ്ടെന്ന് ഉറപ്പാക്കുക
- ദാതാവ് `429` സ്റ്റാറ്റസ് കോഡുകളോ `Retry-After` ഹെഡറുകളോ തിരികെ നൽകുന്നുണ്ടോയെന്ന് പരിശോധിക്കുക

### എക്സ്പോണൻഷ്യൽ ബാക്ക്ഓഫ് ക്രമീകരിക്കൽ

ദാതൃ പ്രൊഫൈലുകൾ ഈ ക്രമീകരണങ്ങളെ പിന്തുണയ്ക്കുന്നു:

- **അടിസ്ഥാന കാലതാമസം** — ആദ്യ പരാജയത്തിനുശേഷമുള്ള പ്രാരംഭ കാത്തിരിപ്പ് സമയം (സ്ഥിരസ്ഥിതി: 1s)
- **പരമാവധി കാലതാമസം** — കാത്തിരിപ്പ് സമയത്തിന്റെ പരമാവധി പരിധി (സ്ഥിരസ്ഥിതി: 30s)
- **ഗുണകം** — തുടർച്ചയായ ഓരോ പരാജയത്തിലും കാലതാമസം എത്രത്തോളം വർധിപ്പിക്കണം (സ്ഥിരസ്ഥിതി: 2x)

### തണ്ടറിങ് ഹെർഡ് പ്രതിരോധം

നിരക്ക്-പരിമിതപ്പെടുത്തിയ ഒരു ദാതാവിലേക്ക് ഒരേസമയം നിരവധി അഭ്യർത്ഥനകൾ എത്തുമ്പോൾ, അഭ്യർത്ഥനകൾ ക്രമാനുഗതമായി പ്രോസസ്സ് ചെയ്യാനും തുടർപരാജയങ്ങൾ തടയാനും OmniRoute mutex + സ്വയമേവയുള്ള നിരക്ക്-പരിമിതപ്പെടുത്തൽ ഉപയോഗിക്കുന്നു. API കീ ദാതാക്കൾക്ക് ഇത് സ്വയമേവയാണ്.

### ചാറ്റ് അഭ്യർത്ഥനകൾ 503 / chat_admission_busy ഉപയോഗിച്ച് പരാജയപ്പെടുന്നു

**ലക്ഷണങ്ങൾ:**

- ചാറ്റ് കംപ്ലീഷൻസ് എൻഡ്പോയിന്റ് വീണ്ടും ശ്രമിക്കാവുന്ന `503` പ്രതികരണം തിരികെ നൽകുന്നു; അതിന്റെ പിശക് കോഡ്
  `chat_admission_busy` ആണ്.
- പ്രതികരണത്തിൽ `Retry-After` ഉൾപ്പെടുന്നു. #12135 മുതൽ, നിരീക്ഷിച്ച
  ഒക്ക്യുപ്പൻസിയിൽ നിന്നാണ് മൂല്യം നിർണ്ണയിക്കുന്നത് — അഭ്യർത്ഥന ഇതിനകം കാത്തിരുന്ന `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  വിൻഡോയുടെയും നിലവിലെ ഹെവിവെയ്റ്റ് ലീസുകൾ നിലനിർത്തിയിരിക്കുന്ന സമയത്തിന്റെയും വലിയ മൂല്യം — പൂർണ്ണ
  സെക്കൻഡുകളിലേക്ക് മുകളിലേക്ക് റൗണ്ട് ചെയ്ത് 60 ആയി പരിമിതപ്പെടുത്തുന്നു. നിഷ്ക്രിയമായ ഒരു ഗേറ്റിൽ ഇത് ചരിത്രപരമായ കുറഞ്ഞ പരിധികൾ നിലനിർത്തുന്നു: ബൈറ്റ് അധിഷ്ഠിത
  പാതയിൽ 2 സെക്കൻഡ്, ഘടനാധിഷ്ഠിത പാതയിൽ 1 സെക്കൻഡ് (ഇതിൽ
  `reason: "structure_limit"` എന്നതും ഉൾപ്പെടുന്നു).
- മറ്റൊരു ഹെവിവെയ്റ്റ് ചാറ്റോ ദീർഘനേരം പ്രവർത്തിക്കുന്ന സ്ട്രീമിങ് പ്രതികരണമോ ഇപ്പോഴും
  പുരോഗതിയിലായിരിക്കുമ്പോൾ ഇത് സംഭവിക്കാം.

ബൈറ്റ് അധിഷ്ഠിത പ്രതികരണ ബോഡി ഇതാണ്:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ഘടനാധിഷ്ഠിത പ്രതികരണം ഇതേ തരവും കോഡും ഉപയോഗിക്കുന്നു; സന്ദേശം
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
എന്നതും `reason: "structure_limit"` എന്നതുമാണ്.
സ്ഥിരസ്ഥിതി പരിധികളിൽ, ഒരു അഭ്യർത്ഥനയിൽ കുറഞ്ഞത് `200` സന്ദേശങ്ങളോ,
കുറഞ്ഞത് `64` ടൂളുകളോ, കുറഞ്ഞത് `32,000` കണക്കാക്കിയ ടോക്കണുകളോ ഉണ്ടെങ്കിൽ, അല്ലെങ്കിൽ പരിധിയുള്ള ഘടനാ നിർണ്ണയം
സന്ദർശിച്ച `10,000` നോഡുകൾ എന്ന പരിധിയോ `12` ആഴമോ തീർത്താൽ, അത് ഘടനാപരമായി ഹെവിവെയ്റ്റ് ആണ്.

**കാരണം:** ഇത് OmniRoute-നുള്ളിലെ മനഃപൂർവമായ ലോഡ് ഷെഡ്ഡിങ്ങാണ്, അപ്സ്ട്രീം ദാതാവിന്റെ പരാജയമല്ല.
വലിയൊരു അഭ്യർത്ഥനാ ബോഡി നിലനിർത്തുന്നതിനും പാഴ്സ് ചെയ്യുന്നതിനും മുമ്പ് പരിമിതമായ ഹെവിവെയ്റ്റ് ശേഷി റിസർവ് ചെയ്യാൻ
ഓരോ പ്രോസസ്സും പ്രോസസ്സ്-ലോക്കൽ ഗാർഡ് ഉപയോഗിക്കുന്നു. ഒരു SSE
പ്രതികരണത്തിന്റെ മുഴുവൻ ആയുസ്സിലും ഹെവിവെയ്റ്റ് ലീസ് നിലനിർത്തപ്പെടുന്നു.

**#503-ഫാൻ-ഔട്ട്:** ഈ പരിഹാരത്തിന് മുമ്പ്, ഹോസ്റ്റ് മെമ്മറി പരിഗണിക്കാതെ ഗാർഡ് ഒരേസമയം അനുവദിക്കുന്ന അഭ്യർത്ഥനകളെ ഒരു നിശ്ചിത COUNT-ൽ
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, സ്ഥിരസ്ഥിതി `1`) പരിമിതപ്പെടുത്തിയിരുന്നു; അതിനാൽ കോഡിങ്-ഏജന്റ്
ഫാൻ-ഔട്ട് (ഒന്നിലധികം സബ്ഏജന്റുകൾ/CLI-കൾ, സാധാരണയായി > 256 KB വലുപ്പമുള്ള ബോഡികൾ) ഫലപ്രദമായ
ഒരേസമയം പ്രവർത്തനശേഷിയെ ~1 ആയി ചുരുക്കുകയും പൂർണ്ണമായും സാധാരണ ലോഡിൽ 503 ഉണ്ടാക്കുകയും ചെയ്തു. ഇപ്പോൾ ഗാർഡ് സ്വയം ക്രമീകരിക്കുന്നു: പ്രോസസ്സിന്റെ യഥാർത്ഥ മെമ്മറി പരിധിയിൽനിന്ന് വലുപ്പം നിർണ്ണയിക്കുന്ന,
സ്വയമേവ നിർണ്ണയിച്ച ഇൻജസ്റ്റ് BYTE ബജറ്റ് (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) അതിനെ നിയന്ത്രിക്കുന്നു;
കൂടാതെ തത്സമയ റിസോഴ്സ്-പ്രഷർ സിഗ്നലും അത് പരിശോധിക്കുന്നു — അതിനാൽ ഒന്നിലധികം
ഹെവി അഭ്യർത്ഥനകൾ ഒരേസമയം എത്തിയെന്ന കാരണത്താൽ മാത്രമല്ല, ഹോസ്റ്റ് യഥാർത്ഥത്തിൽ മെമ്മറി സമ്മർദ്ദത്തിലായിരിക്കുമ്പോൾ മാത്രമാണ്
അത് ലോഡ് കുറയ്ക്കുന്നത്. പഴയ എണ്ണം പരിധി (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ഇപ്പോഴും
പാലിക്കപ്പെടുന്നു, എന്നാൽ നിങ്ങൾ അത് വ്യക്തമായി സജ്ജമാക്കിയാൽ മാത്രം.

ശേഷി തിരക്കിലായിരിക്കുമ്പോൾ, വീണ്ടും ശ്രമിക്കാവുന്ന `503` ഉപയോഗിച്ച് പ്രതികരിക്കുന്നതിന് മുമ്പ് ഒരു ഹെവിവെയ്റ്റ് അഭ്യർത്ഥന ആദ്യം ഒരു സ്ലോട്ട് ഒഴിവാകുന്നതിനായി
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` വരെ (സ്ഥിരസ്ഥിതി `2000`, `0` കാത്തിരിപ്പ് പ്രവർത്തനരഹിതമാക്കുന്നു) കാത്തിരിക്കും.
ഒരേസമയം ഹെവി ഉപ-അഭ്യർത്ഥനകൾ ഫാൻ-ഔട്ട് ചെയ്യുന്ന ഏജന്റ്-ശൈലി ക്ലയന്റുകൾ
(OpenCode, Claude Code, Cursor), ഉടനടിയുള്ള നിരസിക്കലുകളിൽ അവരുടെ മുഴുവൻ പുനഃശ്രമ ബജറ്റും ചെലവഴിച്ച് ടാസ്ക്കിന്റെ മധ്യത്തിൽ
പരാജയപ്പെടുന്നതിനുപകരം ബർസ്റ്റിനെ ക്രമാനുഗതമാക്കുന്നതിനാണ് ഈ പരിധിയുള്ള കാത്തിരിപ്പ് നിലവിലുള്ളത്.
നിലവിലെ ഹെവിവെയ്റ്റ് ലീസ് ഒക്ക്യുപ്പൻസി, നിർണ്ണയിച്ച ബൈറ്റ് ബജറ്റ്, തത്സമയ സമ്മർദ്ദ തീവ്രത എന്നിവ
`GET /api/monitoring/health` → `chatAdmission` എന്നതിൽ (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) പ്രദർശിപ്പിക്കുന്നു — ഏതെങ്കിലും env var മാറ്റുന്നതിന് മുമ്പ് ഇവ പരിശോധിക്കുക.
Settings → Resilience → Request Queue → Concurrent Requests ഇത് നിയന്ത്രിക്കുന്നില്ല; ആ ക്രമീകരണം
വേറിട്ടൊരു ദാതൃ അഭ്യർത്ഥന-ക്യൂ സംവിധാനം നിയന്ത്രിക്കുന്നു.

**പരിഹാരം:**

1. ആദ്യം വീണ്ടും ശ്രമിക്കുക. അഭ്യർത്ഥന ഉടൻതന്നെ
   ആവർത്തിക്കുന്നതിനുപകരം ക്ലയന്റുകൾ `Retry-After` മാനിക്കുകയും ബാക്ക്ഓഫ് ഉപയോഗിക്കുകയും വേണം.
2. എന്തെങ്കിലും ക്രമീകരിക്കുന്നതിന് മുമ്പ് `/api/monitoring/health` → `chatAdmission` പരിശോധിക്കുക. `countCapEnabled:
false` എന്നതും ഉദാരമായ `maxInflightBytes` എന്നതും സ്വയമേവ നിർണ്ണയിച്ച ബജറ്റ് ഇതിനകം അതിന്റെ
   ജോലി ചെയ്യുന്നുവെന്ന് അർത്ഥമാക്കുന്നു; `high`/`critical` എന്ന `pressureSeverity` ഹോസ്റ്റിൽ യഥാർത്ഥത്തിൽ മെമ്മറി കുറവാണെന്ന് അർത്ഥമാക്കുന്നു —
   അഡ്മിഷൻ env var ഉപയോഗിച്ച് അത് പരിഹരിക്കാനാവില്ല; അതിന് കൂടുതൽ RAM അല്ലെങ്കിൽ ചെറിയ വർക്ക്ലോഡ് ആവശ്യമാണ്.
3. `/api/monitoring/health` സ്വയമേവ നിർണ്ണയിച്ച ബജറ്റ് നിങ്ങളുടെ
   ഹോസ്റ്റിന് യഥാർത്ഥത്തിൽ വളരെ ചെറുതാണെന്ന് കാണിച്ചാൽ മാത്രം (അപൂർവം — ഇത് ഇതിനകം കണ്ടെയ്നർ മുതൽ ബെയർ-മെറ്റൽ വരെ സ്കെയിൽ ചെയ്യുന്നു), പഴയ അഭ്യർത്ഥന-എണ്ണ പരിധിയിലേക്ക് മടങ്ങുന്നതിനുപകരം
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ഉപയോഗിച്ച് അത് നേരിട്ട് ഓവർറൈഡ് ചെയ്യുക.

ആധികാരിക അഡ്മിഷൻ ക്രമീകരണങ്ങൾക്കായി [പരിസ്ഥിതി-വേരിയബിൾ റഫറൻസ്](../reference/ENVIRONMENT.md#4-security--authentication)
കാണുക.

## ഐച്ഛിക RAG / LLM പരാജയ വർഗ്ഗീകരണം (16 പ്രശ്നങ്ങൾ)

ചില OmniRoute ഉപയോക്താക്കൾ RAG അല്ലെങ്കിൽ ഏജന്റ് സ്റ്റാക്കുകൾക്ക് മുന്നിൽ ഗേറ്റ്വേ സ്ഥാപിക്കുന്നു. അത്തരം സജ്ജീകരണങ്ങളിൽ അസാധാരണമായ ഒരു രീതി കാണുന്നത് സാധാരണമാണ്: OmniRoute ആരോഗ്യകരമായി കാണപ്പെടുന്നു (പ്രൊവൈഡറുകൾ പ്രവർത്തിക്കുന്നു, റൂട്ടിംഗ് പ്രൊഫൈലുകൾ ശരിയാണ്, നിരക്ക്-പരിധി മുന്നറിയിപ്പുകളില്ല), എന്നാൽ അന്തിമ ഉത്തരം ഇപ്പോഴും തെറ്റായിരിക്കും.

പ്രായോഗികമായി, ഈ സംഭവങ്ങൾ സാധാരണയായി ഗേറ്റ്വേയിൽ നിന്നല്ല, തുടർന്നുള്ള RAG പൈപ്പ്ലൈനിൽ നിന്നാണ് ഉണ്ടാകുന്നത്.

ആ പരാജയങ്ങളെ വിവരിക്കാൻ പങ്കിട്ട ഒരു പദാവലി വേണമെങ്കിൽ, ആവർത്തിച്ച് സംഭവിക്കുന്ന പതിനാറ് RAG / LLM പരാജയ രീതികൾ നിർവചിക്കുന്ന ബാഹ്യ MIT ലൈസൻസുള്ള ടെക്സ്റ്റ് റിസോഴ്സായ WFGY ProblemMap ഉപയോഗിക്കാം. ഉന്നത തലത്തിൽ ഇത് ഉൾക്കൊള്ളുന്നത്:

- റിട്രീവൽ വ്യതിചലനവും തകർന്ന കോൺടെക്സ്റ്റ് അതിരുകളും
- ശൂന്യമായതോ കാലഹരണപ്പെട്ടതോ ആയ ഇൻഡക്സുകളും വെക്റ്റർ സ്റ്റോറുകളും
- എംബെഡിംഗും സെമാന്റിക്സും തമ്മിലുള്ള പൊരുത്തക്കേട്
- പ്രോംപ്റ്റ് അസംബ്ലിയിലെയും കോൺടെക്സ്റ്റ് വിൻഡോയിലെയും പ്രശ്നങ്ങൾ
- ലോജിക് തകർച്ചയും അമിത ആത്മവിശ്വാസമുള്ള ഉത്തരങ്ങളും
- ദൈർഘ്യമേറിയ ചെയിനുകളിലെയും ഏജന്റ് ഏകോപനത്തിലെയും പരാജയങ്ങൾ
- മൾട്ടി-ഏജന്റ് മെമ്മറിയിലെയും റോളുകളിലെയും വ്യതിചലനം
- ഡിപ്ലോയ്മെന്റ്, ബൂട്ട്സ്ട്രാപ്പ് ക്രമീകരണ പ്രശ്നങ്ങൾ

ആശയം ലളിതമാണ്:

1. ഒരു മോശം പ്രതികരണം അന്വേഷിക്കുമ്പോൾ, ഇനിപ്പറയുന്നവ രേഖപ്പെടുത്തുക:
   - ഉപയോക്തൃ ടാസ്കും അഭ്യർത്ഥനയും
   - OmniRoute-ലെ റൂട്ട് അല്ലെങ്കിൽ പ്രൊവൈഡർ കോമ്പിനേഷൻ
   - തുടർന്ന് ഉപയോഗിച്ച ഏതെങ്കിലും RAG കോൺടെക്സ്റ്റ് (റിട്രീവ് ചെയ്ത ഡോക്യുമെന്റുകൾ, ടൂൾ കോളുകൾ തുടങ്ങിയവ)
2. സംഭവത്തെ ഒന്നോ രണ്ടോ WFGY ProblemMap നമ്പറുകളുമായി (`No.1` … `No.16`) മാപ്പ് ചെയ്യുക.
3. OmniRoute ലോഗുകൾക്ക് സമീപം, നിങ്ങളുടെ സ്വന്തം ഡാഷ്ബോർഡിലോ റൺബുക്കിലോ ഇൻസിഡന്റ് ട്രാക്കറിലോ ആ നമ്പർ സംഭരിക്കുക.
4. നിങ്ങളുടെ RAG സ്റ്റാക്ക്, റിട്രീവർ, അല്ലെങ്കിൽ റൂട്ടിംഗ് തന്ത്രം മാറ്റേണ്ടതുണ്ടോ എന്ന് തീരുമാനിക്കാൻ അനുബന്ധ WFGY പേജ് ഉപയോഗിക്കുക.

പൂർണ്ണ ടെക്സ്റ്റും പ്രായോഗിക റെസിപ്പികളും ഇവിടെ ലഭ്യമാണ് (MIT ലൈസൻസ്, ടെക്സ്റ്റ് മാത്രം):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute-ന്റെ പിന്നിൽ നിങ്ങൾ RAG അല്ലെങ്കിൽ ഏജന്റ് പൈപ്പ്ലൈനുകൾ പ്രവർത്തിപ്പിക്കുന്നില്ലെങ്കിൽ, ഈ വിഭാഗം അവഗണിക്കാം.

## v3.8.0-ലെ അറിയപ്പെടുന്ന പ്രശ്നങ്ങൾ

v3.8.0 റിലീസിന് മാത്രമുള്ള പ്രശ്നങ്ങളും അവയ്ക്കുള്ള നിലവിലെ പരിഹാര മാർഗങ്ങളും. പിന്നീടുള്ള ഒരു പാച്ചിൽ പരിഹാരം ഉൾപ്പെടുത്തിയാൽ, ഈ എൻട്രി അപ്ഡേറ്റ് ചെയ്യുകയോ നീക്കം ചെയ്യുകയോ ചെയ്യും.

### Devin CLI ഓതന്റിക്കേഷൻ പരാജയങ്ങൾ

**ലക്ഷണങ്ങൾ:**

- Devin അടിസ്ഥാനമാക്കിയുള്ള ടൂളുകൾ അഭ്യർത്ഥിക്കുമ്പോൾ "Devin CLI not found" അല്ലെങ്കിൽ "auth failed"
- CLI റൺടൈം പരിശോധന `installed=false` എന്ന് റിപ്പോർട്ട് ചെയ്യുന്നു

**കാരണങ്ങൾ:**

- `CLI_DEVIN_BIN` നിലവിലില്ലാത്ത ഒരു പാത്തിലേക്ക് ചൂണ്ടുന്നു
- ഹോസ്റ്റിൽ Devin CLI ഇൻസ്റ്റാൾ ചെയ്തിട്ടില്ല

**പരിഹാരം:**

1. നിങ്ങളുടെ പ്ലാറ്റ്ഫോമിനായുള്ള Devin CLI ഇൻസ്റ്റാൾ ചെയ്യുക
2. `.env`-ൽ `CLI_DEVIN_BIN=/usr/local/bin/devin` (അല്ലെങ്കിൽ യഥാർഥ പാത്ത്) സജ്ജമാക്കുക
3. OmniRoute പുനരാരംഭിച്ച് **Dashboard → CLI Tools** എന്നതിൽ നിന്ന് വീണ്ടും പരിശോധിക്കുക

### മോഡൽ കൂൾഡൗൺ നീങ്ങാതെ തുടരുന്നു (മാനുവൽ റീസെറ്റ്)

**ലക്ഷണങ്ങൾ:**

- കാലാവധി കഴിഞ്ഞിട്ടും ഒരു മോഡൽ കൂൾഡൗൺ പട്ടികയിൽ തുടരുന്നു
- ടൈംസ്റ്റാമ്പ് കഴിഞ്ഞ സമയത്തേതായിരുന്നിട്ടും, കോമ്പോ റൂട്ടിംഗിൽ അഭ്യർത്ഥനകൾ ഇപ്പോഴും ആ മോഡലിനെ ഒഴിവാക്കുന്നു

**മാനുവൽ റീസെറ്റ്:**

- **ഡാഷ്ബോർഡ്:** **Settings → Model Cooldowns** → ബാധിച്ച കാർഡിലെ **Re-enable** ക്ലിക്ക് ചെയ്യുക
- **API:** മാനേജ്മെന്റ് ഓതന്റിക്കേഷൻ ഹെഡറുകളോടൊപ്പം `DELETE /api/resilience/model-cooldowns`

### Command Code പ്രൊവൈഡർ കണക്ഷൻ 403 മൂലം പരാജയപ്പെടുന്നു

**ലക്ഷണങ്ങൾ:**

- Command Code പ്രൊവൈഡർ കണക്ഷൻ പരിശോധിക്കുമ്പോൾ 403
- പുതുതായി ചേർത്തതിന് ശേഷം പ്രൊവൈഡർ കാർഡ് "unauthorized" എന്ന് കാണിക്കുന്നു

**കാരണം:** OAuth ഫ്ലോ പൂർത്തിയായില്ല (കോൾബാക്ക് ലഭിച്ചില്ല അല്ലെങ്കിൽ ടോക്കൺ നിലനിർത്തിയില്ല).

**പരിഹാരം:**

- OAuth ഫ്ലോ വീണ്ടും ആരംഭിക്കാൻ CLI-യിൽ നിന്ന് `omniroute providers` പ്രവർത്തിപ്പിക്കുക, അല്ലെങ്കിൽ
- **Dashboard → Providers → Command Code → Reconnect** എന്നതിൽ നിന്ന് OAuth വീണ്ടും പ്രവർത്തിപ്പിക്കുക

### ModelScope അമിതമായ 429 കൂൾഡൗണുകൾ നൽകുന്നു

**ലക്ഷണങ്ങൾ:**

- അഭ്യർത്ഥനകളുടെ ചെറിയൊരു ബർസ്റ്റിന് ശേഷം ModelScope-ൽ വളരെ ഹ്രസ്വമായതോ ഉടനടിയുള്ളതോ ആയ കൂൾഡൗണുകൾ
- പ്രതീക്ഷിച്ചതിനേക്കാൾ നേരത്തെ കോമ്പോ റൂട്ടിംഗ് ModelScope-നെ ഒഴിവാക്കുന്നു

**കാരണം:** ModelScope പ്രൊവൈഡറിന് മാത്രമുള്ള `Retry-After` ഹെഡറുകൾ പുറപ്പെടുവിക്കുന്നു. ആ ഹെഡറുകൾക്കായുള്ള പ്രത്യേക കൈകാര്യം v3.8.0-ൽ ഉൾപ്പെടുത്തിയിട്ടുണ്ട്; അതിനാൽ പഴയ പതിപ്പുകൾ അവയെ പൊതുവായ നിരക്ക്-പരിധി സൂചനകളായി തെറ്റായി വ്യാഖ്യാനിക്കുന്നു.

**പരിഹാരം:**

- നിങ്ങൾ v3.8.0 അല്ലെങ്കിൽ അതിനുശേഷമുള്ള പതിപ്പിലാണെന്ന് ഉറപ്പാക്കുക
- **Settings → Resilience** എന്നതിന് കീഴിൽ `useUpstream429BreakerHints` ടോഗിൾ പ്രവർത്തനക്ഷമമാണെന്ന് സ്ഥിരീകരിക്കുക

### പ്രൊഡക്ഷനിൽ OMNIROUTE_WS_BRIDGE_SECRET ലഭ്യമല്ല

**ലക്ഷണങ്ങൾ:**

- റിമോട്ട് പ്രൊഡക്ഷൻ ഹോസ്റ്റിൽ പ്രവർത്തിക്കുമ്പോൾ ഓരോ Codex/Responses WebSocket ബ്രിഡ്ജ് അഭ്യർത്ഥനയിലും 401
- കണക്ട് ചെയ്ത ഉടൻ WebSocket ബ്രിഡ്ജ് ഹാൻഡ്ഷേക്ക് അവസാനിക്കുന്നു

**കാരണം:** പ്രൊഡക്ഷൻ എൻവയൺമെന്റിൽ `OMNIROUTE_WS_BRIDGE_SECRET` എൻവയൺമെന്റ് വേരിയബിൾ ലഭ്യമല്ല.

**പരിഹാരം:**

1. ക്രമരഹിതമായ ഒരു സീക്രട്ട് സൃഷ്ടിക്കുക: `openssl rand -hex 32`
2. പ്രൊഡക്ഷൻ സെർവർ എൻവയൺമെന്റിൽ (ബ്രിഡ്ജുമായി ആശയവിനിമയം നടത്തുന്ന ഏത് ക്ലയന്റിലും) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` സജ്ജമാക്കുക
3. OmniRoute പുനരാരംഭിക്കുക

### Responses API: പശ്ചാത്തല മോഡ് സിൻക്രണസ് പ്രവർത്തനത്തിലേക്ക് താഴ്ത്തിയിരിക്കുന്നു

**ലക്ഷണങ്ങൾ:**

- ലോഗ് ചെയ്ത മുന്നറിയിപ്പ്: `background mode degraded to synchronous`
- ഒരു `background: true` അഭ്യർത്ഥന പശ്ചാത്തല ജോബ് ഹാൻഡിലിന് പകരം സാധാരണ സിൻക്രണസ് പ്രതികരണം നൽകുന്നു

**കാരണം:** മുന്നറിയിപ്പ് പുറപ്പെടുവിച്ചുകൊണ്ട് Responses API-യിലെ `background: true`-നെ v3.8.0 മനഃപൂർവം സിൻക്രണസ് എക്സിക്യൂഷനിലേക്ക് താഴ്ത്തുന്നു. പൂർണ്ണ അസിങ്ക്രണസ് പശ്ചാത്തല എക്സിക്യൂഷൻ ഭാവിയിൽ ലഭ്യമാക്കുന്ന സവിശേഷതയാണ്.

**പരിഹാരം:**

- `background` ഇല്ലാതെ കോൾ ചെയ്യാൻ ക്ലയന്റിനെ ക്രമീകരിക്കുക, അല്ലെങ്കിൽ
- പൂർണ്ണ അസിങ്ക്രണസ് പശ്ചാത്തല മോഡ് ഉൾപ്പെടുന്ന പിന്നീടുള്ള ഒരു റിലീസിനായി കാത്തിരിക്കുക (ചേഞ്ച്ലോഗ് നിരീക്ഷിക്കുക)

## മന്ദഗതിയിലുള്ള സ്റ്റാർട്ടപ്പ് / സന്നദ്ധതാ സമയപരിധി

CLI `⚠ Server did not respond within 60s` എന്ന് പ്രിന്റ് ചെയ്യുന്നുവെങ്കിലും സെർവർ യഥാർത്ഥത്തിൽ പ്രവർത്തിക്കുന്നുണ്ടെങ്കിൽ, നിങ്ങളുടെ പരിതസ്ഥിതിക്ക് സന്നദ്ധതാ പരിശോധനയ്ക്കുള്ള സമയപരിധി വളരെ കുറവാണ്.

Windows-ലോ (ആന്റിവൈറസ്, ഫയൽസിസ്റ്റം വാച്ചറുകൾ) വലിയ സ്റ്റാർട്ടപ്പ് വർക്ക്ലോഡുകളുള്ള കണ്ടെയ്നറുകളിലോ ഇത് സാധാരണയായി സംഭവിക്കാറുണ്ട്.

**പരിഹാരം — സമയപരിധി വർധിപ്പിക്കുക:**

```bash
# പരിതസ്ഥിതി വേരിയബിൾ വഴി (സ്റ്റാർട്ടുകൾക്കിടയിലും നിലനിൽക്കും):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 മിനിറ്റ്
omniroute serve

# CLI ഫ്ലാഗ് വഴി (ഒറ്റത്തവണ):
omniroute serve --ready-timeout 180000
```

ഡിഫോൾട്ട് 60 000 ms (60 s) ആണ്. മുന്നറിയിപ്പ് വിവരദായകം മാത്രമാണ്; സെർവർ പശ്ചാത്തലത്തിൽ സ്റ്റാർട്ട് ചെയ്യുന്നത് തുടരുകയും ബൂട്ട് പൂർത്തിയായിക്കഴിഞ്ഞാൽ ലഭ്യമാകുകയും ചെയ്യും.

`OMNIROUTE_READY_TIMEOUT_MS`-നെക്കുറിച്ചുള്ള പൂർണ്ണ വിവരങ്ങൾക്ക് [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) കാണുക.
