**ഇന്ന് സൗജന്യമായ ഒന്നും റിമോട്ട് ഫീഡ് കാരണം സൗജന്യമല്ലാതാകുന്നില്ല.** Radar ഒരിക്കലും

## പൊതു അറിയിപ്പ് റീഡർ

പൊതുവായ അറിയിപ്പ് റീഡർ Radar ഫീച്ചർ ഫ്ലാഗിൽ നിന്ന് വേറിട്ടതാണ്. ഡാഷ്ബോർഡ് Home, Changelog വ്യൂവർ എന്നിവ സാധാരണ `GET` ഉപയോഗിച്ച് `NEWS_JSON_URL`-ൽ നിന്ന് (`src/shared/utils/releaseNotes.ts`) റിപ്പോസിറ്ററിയുടെ പൊതുവായ `news.json` ലഭ്യമാക്കുന്നു. അവ Radar ക്രമീകരണം, പ്രോംപ്റ്റ്, പ്രൊവൈഡർ കോൺഫിഗറേഷൻ, ഉപയോഗ റെക്കോർഡ്, അല്ലെങ്കിൽ ലോക്കൽ ഡിസ്മിസൽ നില എന്നിവയൊന്നും അയയ്ക്കുന്നില്ല.

`news.json`, `parseNewsPayload()` നടപ്പിലാക്കിയ ക്ലോസ്ഡ് v2 സ്കീമ ഉപയോഗിക്കുന്നു:

- `schemaVersion: 2`, പരിധിയുള്ള `items[]` ശേഖരം;
- സ്ഥിരതയുള്ള, തനതായ അറിയിപ്പ് `id` മൂല്യങ്ങൾ;
- വ്യക്തമായ `active`, ISO `publishedAt` ഫീൽഡുകൾ;
- നിർബന്ധിത ഇംഗ്ലീഷ് പകർപ്പും ഓപ്ഷണലായ പ്രാദേശികവൽക്കരിച്ച പകർപ്പും;
- ക്രെഡൻഷ്യലുകൾ ആവശ്യമില്ലാത്ത ഓപ്ഷണൽ HTTPS ലിങ്കുകളും അനുവദനീയ പട്ടികയിലുള്ള ഒരു ഐക്കണും;
- ഏറ്റവും പുതിയ സജീവ അറിയിപ്പ് ആദ്യം തിരഞ്ഞെടുക്കൽ, ഇംഗ്ലീഷിലേക്കുള്ള ലോക്കേൽ ഫാൾബാക്ക്, ഓരോ ID-യ്ക്കുമുള്ള ലോക്കൽ ഡിസ്മിസൽ.

പഴയ ഫോർക്കുകൾക്ക് Changelog കാഴ്ച തകരാതെ മൈഗ്രേറ്റ് ചെയ്യാൻ കഴിയുന്നതിനായി, മുമ്പുണ്ടായിരുന്ന ഏകവചന `{ active, title, message, ... }` രൂപം പാർസർ താൽക്കാലികമായി സ്വീകരിക്കുന്നു. അസാധുവായ ഫീഡുകൾ പ്രവർത്തനരഹിതമാണ്. Radar ലോഞ്ച് എൻട്രി `active: false` എന്ന നിലയിലാണ് വിതരണം ചെയ്യുന്നത്; അത് `true` ആക്കുന്നത് മെർജിനും ഡിപ്ലോയ്മെന്റിനും ശേഷമുള്ള വേറിട്ട റിലീസ് നടപടിയാണ്, കൂടാതെ അത് `RADAR_ENABLED`-നെയോ സ്വതന്ത്രമായ ഫീഡ്-സിങ്ക് ഓപ്റ്റ്-ഇന്നിനെയോ മാറ്റുന്നില്ല.

## ഫ്ലാഗ്: `RADAR_ENABLED` (ഡിഫോൾട്ടായി ഓഫ്)

Radar പൂർണ്ണമായും `RADAR_ENABLED` ഫീച്ചർ ഫ്ലാഗ് മുഖേന നിയന്ത്രിക്കപ്പെടുന്നു
(`src/shared/constants/featureFlagDefinitions.ts`, വിഭാഗം `policies`,
`defaultValue: "false"`).

**ഫ്ലാഗ് ഓഫ് ആയിരിക്കുമ്പോൾ, ഈ സർഫേസ് നിലവിലില്ല:**

- ലോക്കൽ മോഡൽ-സ്റ്റേറ്റ് റീഡുകളും റൈറ്റുകളും ഉൾപ്പെടെ എല്ലാ `/api/radar/*` എൻഡ്പോയിന്റുകളും, ഏതെങ്കിലും Radar മൊഡ്യൂളിനെ സ്പർശിക്കുന്നതിന് മുമ്പ് `404` മടക്കിനൽകുന്നു.
- ഡാഷ്ബോർഡ് സ്ക്രീനുകൾ (`/dashboard/radar`, `/dashboard/radar/setup`,
  `/dashboard/radar/combos`, `/dashboard/radar/offers`, `/dashboard/radar/intel`)
  `notFound()` റെൻഡർ ചെയ്യുന്നു.
- `getRadarCatalog()` (`src/lib/radar/index.ts`) മാറ്റം വരുത്താത്ത ബേസ്ലൈൻ മടക്കിനൽകുന്നു —
  അതേ എൻട്രി എണ്ണം, അതേ മൂല്യങ്ങൾ, ഓരോ എൻട്രിയിലും `origin: "baseline"` എന്ന ടാഗ് — കൂടാതെ ഫീഡ് കാഷ് ഒരിക്കലും വായിക്കുകയുമില്ല.
- Radar നെറ്റ്വർക്ക് കോൾ ഒന്നും ഒരിക്കലും നടത്തപ്പെടുന്നില്ല; `fetch` സ്പർശിക്കുന്നതിന് മുമ്പ് ഓരോ സിങ്ക് മൊഡ്യൂളും `{ status: "disabled" }` മടക്കിനൽകുന്നു.

ഇത് കർശനമായ ഒരു സൂപ്പർസെറ്റ് ഗേറ്റാണ്: ഫ്ലാഗ് ഓൺ ആക്കുന്നത് _സ്ക്രീനുകൾ_ മാത്രമാണ് അൺലോക്ക് ചെയ്യുന്നത്. അത് ഡാറ്റ അപ്ലോഡ് ചെയ്യുകയോ, പശ്ചാത്തല സിങ്ക് ആരംഭിക്കുകയോ, റൂട്ടിങ് അല്ലെങ്കിൽ മോഡൽ തിരഞ്ഞെടുപ്പ് മാറ്റുകയോ ചെയ്യുന്നില്ല — താഴെയുള്ള വേറിട്ട ഓപ്റ്റ്-ഇൻ കാണുക.

## ഡാറ്റാ സിങ്ക് ഒരു വേറിട്ട ഓപ്റ്റ്-ഇൻ ആണ് — സ്വകാര്യതാ വാഗ്ദാനം

`RADAR_ENABLED` ഓൺ ആക്കുന്നത് UI മാത്രമാണ് അൺലോക്ക് ചെയ്യുന്നത്. ഫീഡ് സിങ്ക് ചെയ്യുന്നതിന് `radar_settings.opt_in`-ൽ സൂക്ഷിച്ചിരിക്കുന്ന രണ്ടാമത്തെ, സ്വതന്ത്രമായ ഓപ്റ്റ്-ഇൻ ആവശ്യമാണ് (`src/lib/db/radar.ts`,
മൈഗ്രേഷൻ `136_radar_cache_settings.sql`). ഏതെങ്കിലും നെറ്റ്വർക്ക് കോൾ നടത്തുന്നതിന് മുമ്പ് `syncRadar()` ഫ്ലാഗും ഓപ്റ്റ്-ഇന്നും പരിശോധിക്കുന്നു:

```
ഫ്ലാഗ് ഓഫ്      → { status: "disabled" }   — നെറ്റ്വർക്ക് കോൾ ഇല്ല
ഓപ്റ്റ്-ഇൻ false  → { status: "opt_out" }    — നെറ്റ്വർക്ക് കോൾ ഇല്ല
```

രണ്ടും ഓൺ ആയിരിക്കുമ്പോൾ, സിങ്ക് പാത ഇപ്രകാരമാണ്:

1. `x-omniroute-radar-schema: 2`, കൂടാതെ ഓപ്ഷണലായി `Authorization: Bearer <supporter key>` ഹെഡർ (താഴെ കാണുക) സഹിതം `GET <feed base URL>/v1/catalog/latest`. സ്കീമ ഹെഡർ ഇല്ലാത്തപ്പോൾ സർവറുകൾ വേറിട്ട് ഒപ്പിട്ട v1 ട്രാൻസിഷൻ ആർട്ടിഫാക്റ്റിലേക്ക് ഡിഫോൾട്ട് ചെയ്യുന്നു; അതിനാൽ മുമ്പ് ഇൻസ്റ്റാൾ ചെയ്ത പഴയ ക്ലയന്റുകൾക്കും അപ്ഡേറ്റുകൾ തുടർന്നും ലഭിക്കും.
2. ഇത് ഡൗൺലോഡ് മാത്രമുള്ള ഒരു ആപ്ലിക്കേഷൻ ഫ്ലോയാണ്, എങ്കിലും ഇത് ഒരു HTTPS അഭ്യർത്ഥന തന്നെയാണ്. ഹോസ്റ്റ് ചെയ്ത ഇൻഫ്രാസ്ട്രക്ചറിന് സോഴ്സ് IP പോലുള്ള സാധാരണ കണക്ഷൻ മെറ്റാഡാറ്റ ലഭിക്കുന്നു. ഒരു സപ്പോർട്ടർ കീ കോൺഫിഗർ ചെയ്തിട്ടുണ്ടെങ്കിൽ, അവകാശം നിർണ്ണയിക്കാൻ സേവനത്തിന് കഴിയുന്ന വിധം സിങ്ക് ആ കീയും Bearer ഹെഡറിൽ അയയ്ക്കുന്നു. മുകളിൽ പറഞ്ഞ എവിഡൻസ് ബൗണ്ടറിയിൽ തിരിച്ചറിഞ്ഞ കൃത്യമായ സ്വകാര്യ-സർവർ റിവിഷനിൽ, ഫീഡ്-റിക്വസ്റ്റ് അക്കൗണ്ടിങ് മാനുവൽ ദുരുപയോഗ പരിശോധനയ്ക്കായി കീ ഹാഷുകൾ, സമാഹൃത ഉപയോഗം, IP-യുടെ ദിവസേന റൊട്ടേറ്റ് ചെയ്യുന്ന ട്രങ്കേറ്റഡ് HMAC എന്നിവ ഉപയോഗിക്കുന്നു; ആ പട്ടികകൾ കീയോ IP-യോ അസംസ്കൃത രൂപത്തിൽ നിലനിർത്തുന്നില്ല. ഇൻഫ്രാസ്ട്രക്ചർ ആക്സസ് ലോഗുകളും എൻക്രിപ്റ്റ് ചെയ്ത ഡെലിവറി ഔട്ട്ബോക്സും വേറിട്ട പ്രവർത്തന ബൗണ്ടറികളാണ്.
3. OmniRoute ഒരിക്കലും പ്രോംപ്റ്റുകൾ, പ്രതികരണങ്ങൾ, സംഭാഷണങ്ങൾ, പ്രൊവൈഡർ ക്രെഡൻഷ്യലുകൾ, മോഡൽ ട്രാഫിക്, അപ്ടൈം, ലേറ്റൻസി, അല്ലെങ്കിൽ ലോക്കൽ പ്രൊവൈഡർ കോൺഫിഗറേഷൻ എന്നിവ Radar സേവനത്തിലേക്ക് അയയ്ക്കുന്നില്ല.
4. പ്രതികരണം പരിശോധിക്കുകയും സാധുത ഉറപ്പാക്കുകയും ലോക്കലായി കാഷ് ചെയ്യുകയും ചെയ്യുന്നു ([സുരക്ഷാ മോഡൽ](#security-model) കാണുക). Radar-ന് കൃത്യമായി നാല് സർവർ-സൈഡ് നെറ്റ്വർക്ക് പാതകളുണ്ട്: കാറ്റലോഗിനായി `syncRadar()`, റഫറലുകൾക്കായി `syncRadarReferrals()`, കൂടാതെ സപ്പോർട്ടർമാർക്ക് മാത്രമുള്ള ഓഫറുകൾക്കും Intel-നും വേണ്ടി `syncRadarOffers()` / `syncRadarIntel()`.

**സപ്പോർട്ടർ കീ** എന്നത് ഏത് ടിയർ നൽകണമെന്ന് ഫീഡ് സേവനത്തിന് തീരുമാനിക്കാൻ സഹായിക്കുന്ന ഒരു ഓപ്ഷണൽ Bearer ടോക്കണാണ് (`radar_settings.supporter_key`) ([ടിയറുകൾ](#tiers-community-and-live) കാണുക). ഇത്:

- പ്രൊവൈഡർ ക്രെഡൻഷ്യലുകൾക്കായി ഉപയോഗിക്കുന്ന അതേ AES-256-GCM `encrypt()`/`decrypt()` ഹെൽപ്പറുകൾ (`src/lib/db/encryption.ts`) ഉപയോഗിച്ച് **സംഭരണത്തിൽ എൻക്രിപ്റ്റ് ചെയ്ത്** സൂക്ഷിക്കുന്നു.
- `POST /api/radar/settings` (`{ supporterKey: "omr_" + 40 hex chars }`) വഴി സജ്ജമാക്കുന്നു, കൂടാതെ **ഒരിക്കലും തിരികെ കാണിക്കുന്നില്ല** — പ്രതികരണം മറച്ചുവെച്ച രൂപം (`omr_****abcd`) മടക്കിനൽകുന്നു.
- ഇത് മാറ്റുകയോ മായ്ക്കുകയോ ചെയ്യുന്നത് കാറ്റലോഗ്, റഫറലുകൾ, ഓഫറുകൾ, Intel കാഷുകൾ എന്നിവയെ ആറ്റോമിക്കായി അസാധുവാക്കുന്നു. അടുത്ത സിങ്ക്/റീഡ് പുതിയ അവകാശം സർവർ-സൈഡിൽ നിർണ്ണയിക്കുന്നു; ഒരു കീ സേവ് ചെയ്യുന്നത് സ്വയം നെറ്റ്വർക്ക് അഭ്യർത്ഥന നടത്തുകയോ ഒറ്റത്തവണ ഉപയോഗിക്കാവുന്ന ആക്ടിവേഷൻ കീ വിനിയോഗിക്കുകയോ ചെയ്യുന്നില്ല.
- സിങ്ക് GET-ൽ Bearer ടോക്കണായി ഫീഡ് സേവനത്തിലേക്ക് അയയ്ക്കുന്നു — കീ സംബന്ധിച്ച മറ്റൊന്നും ക്ലയന്റിൽ നിന്ന് പുറത്തേക്ക് പോകുന്നില്ല.

## ഒരു supporter key നേടൽ

ആക്റ്റിവേഷൻ സ്ക്രീൻ (`/dashboard/radar`) ഒരു supporter key **നേടുന്നതിനുള്ള** രണ്ട് പ്രക്രിയകളിലേക്കുള്ള ലിങ്കുകൾ നൽകുന്നു. OSS repo സ്വയം ഒരിക്കലും key നൽകുകയോ, പേയ്മെന്റ് കോഡ് പ്രവർത്തിപ്പിക്കുകയോ, **വില വ്യക്തമാക്കുകയോ ചെയ്യുന്നില്ല** — വിലനിർണ്ണയം തീരുമാനിക്കുന്നതും പ്രദർശിപ്പിക്കുന്നതും പൂർണ്ണമായും ലക്ഷ്യസ്ഥാന പേജുകളിലാണ്, ഈ repo-യിൽ അല്ല (സ്പെസിഫിക്കേഷൻ തീരുമാനം D14).

- **"ഞാൻ ഒരു contributor ആണ്"** — സ്വകാര്യ Radar server-ൽ ഹോസ്റ്റ് ചെയ്യുന്ന GitHub OAuth claim പ്രക്രിയയായ `RADAR_CONTRIBUTOR_CLAIM_URL` (ഡിഫോൾട്ട്
  `https://radar.omniroute.online/auth/github`) തുറക്കുന്നു. ഇത് ഏറ്റവും പുതിയ, പൂർണ്ണമായ പ്രതിവാര റാങ്കിങ് പരിശോധിക്കുന്നു: Top 10-ന് 365 ദിവസവും
  11–100 സ്ഥാനങ്ങളിലുള്ളവർക്ക് 90 ദിവസവും ലഭിക്കും. Top 100-ന് പുറത്താണെങ്കിൽ, PR എണ്ണം ഒരിക്കലും ആക്സസ് നൽകില്ല; പകരം, ഈ പ്രക്രിയ പ്രത്യേകമായ ഒരുതവണ ഉപയോഗിക്കാവുന്ന star + follow ലെവൽ പരിശോധിക്കുന്നു.
- **"പ്രോജക്റ്റിനെ പിന്തുണയ്ക്കുക"** — ഒരുതവണ പണമടയ്ക്കേണ്ട 6-മാസ, 1-വർഷ, lifetime ഓപ്ഷനുകൾക്കായുള്ള ഹോസ്റ്റ് ചെയ്ത പേജായ `RADAR_SUPPORTER_PLANS_URL` (ഡിഫോൾട്ട്
  `https://radar.omniroute.online/planos`) തുറക്കുന്നു. OSS പേജ് തുടർന്നും പണമൂല്യം ഒന്നും പ്രദർശിപ്പിക്കുന്നില്ല.

രണ്ട് URL-കളും server-side-ൽ പരിഹരിക്കപ്പെടുകയും (`src/lib/radar/links.ts`, `RADAR_FEED_URL`-ലേതിന് സമാനമായ env-override
രീതി) നിലവിലുള്ള `GET /api/radar/settings` പ്രതികരണത്തിലൂടെ (`contributorClaimUrl`, `supporterPlansUrl`) dashboard-ലേക്ക് കൈമാറുകയും ചെയ്യുന്നു — client component ഒരിക്കലും `process.env` നേരിട്ട് വായിക്കുന്നില്ല.

### നഷ്ടപ്പെട്ട supporter key വീണ്ടെടുക്കൽ

ഹോസ്റ്റ് ചെയ്ത സേവനത്തിന്റെ recovery entry point `https://radar.omniroute.online/recover` ആണ്; plans പേജിൽ നിന്നും ഇതിലേക്കുള്ള ലിങ്കും നൽകിയിട്ടുണ്ട്. Recovery പൂർണ്ണമായും OSS client-ന് പുറത്തുതന്നെയാണ് നിലനിൽക്കുന്നത്, കാരണം ലോക്കൽ installation ഒരിക്കലും വാങ്ങുന്നയാളുടെ/contributor-ന്റെ e-mail സ്വീകരിക്കുന്നില്ല, കൂടാതെ അതിന്റെ എൻക്രിപ്റ്റ് ചെയ്ത settings-ൽ നിന്ന് ഒരു raw key പുനർനിർമ്മിക്കാനും കഴിയില്ല.

1. key-യുമായി ബന്ധപ്പെട്ട e-mail സമർപ്പിക്കുക. വീണ്ടെടുക്കാവുന്ന license നിലവിലുണ്ടെങ്കിലും ഇല്ലെങ്കിലും സേവനം ഒരേ accepted പേജാണ് നൽകുന്നത്, അതിനാൽ form അക്കൗണ്ടുകൾ വെളിപ്പെടുത്തുന്നില്ല.
2. അർഹതയുണ്ടെങ്കിൽ, delivery worker കുറഞ്ഞ കാലാവധിയുള്ള, ഒരുതവണ മാത്രം ഉപയോഗിക്കാവുന്ന link അയയ്ക്കുന്നു. അത് തുറക്കുമ്പോൾ ഉടൻതന്നെ token താൽക്കാലികമായി എൻക്രിപ്റ്റ് ചെയ്ത `HttpOnly`/`Secure` cookie-യിലേക്ക് മാറ്റുകയും ശുദ്ധമായ
   `/recover` URL-ലേക്ക് redirect ചെയ്യുകയും ചെയ്യും; പേജിൽ token, e-mail, പഴയ key, അല്ലെങ്കിൽ replacement key എന്നിവയൊന്നും ഉണ്ടായിരിക്കില്ല.
3. revocation സ്ഥിരീകരിക്കുക. സ്വകാര്യ സേവനം മുമ്പത്തെ key revoke ചെയ്യുകയും, അതേ plan/expiration സഹിതം replacement സൃഷ്ടിക്കുകയും, ഒരൊറ്റ transaction-ൽ അത് e-mail വഴി അയയ്ക്കുന്നതിനായി queue ചെയ്യുകയും ചെയ്യുന്നു. replacement ഒരിക്കലും browser-ലേക്ക് മടക്കി നൽകുന്നില്ല.
4. replacement `/dashboard/radar`-ൽ paste ചെയ്യുക. പഴയ key ഇപ്പോൾ `community` നിലയിലേക്ക് താഴേണ്ടതാണ്; replacement സ്ഥിരീകരിച്ച `live` sync സൃഷ്ടിക്കണം. അതേ recovery link വീണ്ടും തുറക്കുന്നത് ഒരു പൊതുവായ invalid/expired പ്രതികരണത്തോടെ പരാജയപ്പെടണം.

ഹോസ്റ്റ് ചെയ്ത recovery route-ഉം mail worker-ഉം code-ൽ ഉണ്ടായിരിക്കാമെങ്കിലും, ഒരു പ്രത്യേക deployment-ൽ അവ ലഭ്യമല്ലായിരിക്കാം. server deploy ചെയ്യുകയും, നിയന്ത്രിത recipient ഉപയോഗിച്ച് delivery provider configure ചെയ്യുകയും, ഒരുതവണ ഉപയോഗിക്കാവുന്ന മുഴുവൻ link പരീക്ഷിക്കുകയും ചെയ്യുന്നതുവരെ ഈ പ്രക്രിയ production-ready ആണെന്ന് പറയരുത്.

ഒരു സന്ദർശകന് key (`omr_` + 40 hex chars) ലഭിച്ചുകഴിഞ്ഞാൽ, ആക്റ്റിവേഷൻ സ്ക്രീനിൽ
(`src/app/(dashboard)/dashboard/radar/page.tsx`) പ്രധാന മാർഗമായി ഒരു paste-key input ഉണ്ട്: key paste ചെയ്ത് submit ചെയ്യുമ്പോൾ, ഒരൊറ്റ call-ൽ `POST /api/radar/settings`
(`{ optIn: true, supporterKey }`) അയയ്ക്കുന്നു — key paste ചെയ്യുന്നത് അതിനെ സജ്ജീകരിക്കുകയും opt in ചെയ്യുകയും ചെയ്ത് സ്ക്രീൻ unlock ചെയ്യുന്നു. മെച്ചപ്പെട്ട UX-നായി shared `isValidSupporterKeyFormat()` helper (`src/lib/radar/supporterKey.ts`) ഉപയോഗിച്ച് ഫോർമാറ്റ് (`omr_` + 40 hex chars) ആദ്യം client-side-ൽ പരിശോധിക്കുന്നു; ഏത് സാഹചര്യത്തിലും server-ന്റെ Zod schema ആണ് ആധികാരിക പരിശോധന. ഒരു key സജ്ജീകരിച്ചുകഴിഞ്ഞാൽ, ശൂന്യമായ input-ന് പകരം ആക്റ്റിവേഷൻ സ്ക്രീൻ masked രൂപം (`GET /api/radar/settings`-ൽ നിന്നുള്ള `supporterKeyMasked`) കാണിക്കുന്നു, കൂടാതെ പുതിയത് paste ചെയ്യാനുള്ള "key മാറ്റുക" control-ഉം നൽകുന്നു — raw key ഒരിക്കലും വീണ്ടും പ്രദർശിപ്പിക്കില്ല. മുകളിലുള്ള രണ്ട് claim/plans button-കൾ തന്നെയാണ് ആദ്യം ഒരു key _നേടാനുള്ള_ മാർഗം; ഇതിനകം key ഉള്ള ഒരു operator അത് ആക്റ്റിവേറ്റ് ചെയ്യേണ്ടത് ഈ input-ലാണ്.

### End-to-end ആക്റ്റിവേഷനും മാർഗനിർദ്ദേശത്തോടെയുള്ള സജ്ജീകരണവും

സ്വകാര്യ feed service-നും ഈ OSS client-നും ഇടയിൽ മനപ്പൂർവം പരിമിതമായ ഒരു അതിർത്തിയാണുള്ളത്: service supporter key നൽകുകയും സാധൂകരിക്കുകയും ചെയ്യുമ്പോൾ, ലോക്കൽ OmniRoute installation key എൻക്രിപ്റ്റ് ചെയ്യുകയും, ഒപ്പിട്ട artifacts server-side-ൽ sync ചെയ്യുകയും, provider setup-ൽ മാർഗനിർദ്ദേശം നൽകുകയും ചെയ്യുന്നു. സഹായത്തോടെയുള്ള validation ക്രമം ഇപ്രകാരമാണ്:

1. കോൺട്രിബ്യൂട്ടർ ക്ലെയിം, plans/checkout, recovery യാത്ര, അല്ലെങ്കിൽ അംഗീകൃത സ്വകാര്യ സർവർ ഓപ്പറേറ്റർ എന്നിവയിൽ നിന്ന് പുതുതായി നൽകിയതോ വീണ്ടെടുത്തതോ ആയ ഒരു കീ നേടുക. അസംസ്കൃത കീ ലോഗുകളിലോ,
   സ്ക്രീൻഷോട്ടുകളിലോ, issue കമന്റുകളിലോ, command-line ആർഗ്യുമെന്റുകളിലോ പേസ്റ്റ് ചെയ്യരുത്.
2. പ്രാദേശിക OmniRoute ഇൻസ്റ്റാളേഷനിൽ `RADAR_ENABLED` ഫീച്ചർ ഫ്ലാഗ് പ്രവർത്തനക്ഷമമാക്കുക. ഇത് UI ലഭ്യമാക്കുന്നു,
   എന്നാൽ പ്രത്യേകമായ opt-in സേവ് ചെയ്യുന്നതുവരെ നെറ്റ്വർക്ക് പ്രവർത്തനരഹിതമായി തുടരും.
3. `/dashboard/radar` തുറന്ന് കീ പേസ്റ്റ് ചെയ്ത് സജീവമാക്കുക. ബ്രൗസർ പ്രാദേശികമായി ഒരൊറ്റ
   `POST /api/radar/settings` അഭ്യർത്ഥന `{ optIn: true, supporterKey }` സഹിതം അയയ്ക്കുന്നു; കീ പ്രാദേശികമായി എൻക്രിപ്റ്റ് ചെയ്യപ്പെടുകയും
   പ്രതികരണത്തിൽ `omr_****<last4>` മാത്രം ഉൾപ്പെടുകയും ചെയ്യും.
4. ആക്ടിവേഷൻ സ്ക്രീനിലെ കാറ്റലോഗ് സിങ്ക് പൂർത്തിയാകാൻ അനുവദിക്കുക, അല്ലെങ്കിൽ **ഇപ്പോൾ സിങ്ക് ചെയ്യുക** തിരഞ്ഞെടുക്കുക. പേജ്
   `live`, ഒരു ഫീഡ് പതിപ്പ്, ഒരു ഫെച്ച് സമയം എന്നിവ റിപ്പോർട്ട് ചെയ്യുന്നുണ്ടെന്ന് സ്ഥിരീകരിക്കുക. പ്രാമാണീകരിച്ച പ്രാദേശിക ഡയഗ്നോസ്റ്റിക്കിനായി,
   `GET /api/radar/status` കീ തിരികെ നൽകാതെ opt-in/കീ സാന്നിധ്യവും നാല് കാഷ് നിലകളും റിപ്പോർട്ട് ചെയ്യുന്നു.
   `POST /api/radar/sync-all` ഉപയോഗിച്ച് കാറ്റലോഗ്, റഫറലുകൾ, ഓഫറുകൾ, Intel എന്നിവ വ്യക്തമായി പുതുക്കാനാകും.
5. `/dashboard/radar/setup?provider=<provider>` തുറക്കുക. പ്രൊവൈഡറിന്റെ ക്രെഡൻഷ്യൽ URL പിന്തുടരുക,
   **API കീ ചേർക്കുക** തിരഞ്ഞെടുക്കുക, യഥാർഥ പ്രൊവൈഡർ ഫോം വഴി സേവ് ചെയ്യുക, ഗൈഡിലേക്ക് മടങ്ങി
   **കണക്ഷൻ പരിശോധിക്കുക** പ്രവർത്തിപ്പിക്കുക. ഗൈഡ് സാധാരണ `/api/providers`,
   `/api/providers/<connection-id>/test` റൂട്ടുകൾ ഉപയോഗിക്കുന്നു; ഇത് സമാന്തരമായ Radar ക്രെഡൻഷ്യൽ സൃഷ്ടിക്കുന്നില്ല.
6. കുറഞ്ഞത് രണ്ട് അനുയോജ്യമായ പ്രൊവൈഡർ കണക്ഷനുകൾ സജീവമായ ശേഷം `/dashboard/radar/combos` തുറക്കുക.
   നിർദ്ദേശിച്ച ഫാമിലി അവലോകനം ചെയ്ത് നിലവിലുള്ള combo API വഴി കോംബോ സൃഷ്ടിക്കുക. ഓഫറുകളും
   Intel-ഉം വേറിട്ട, ലൈവിൽ മാത്രം ലഭ്യമായ signed cache-കളായി തുടരും; അവയുടെ സമർപ്പിത Radar പേജുകളിൽ അവ പരിശോധിക്കാം.
7. `/dashboard/radar`-ഉം സജ്ജീകരണ പേജും റീലോഡ് ചെയ്യുക. opt-in, മാസ്ക് ചെയ്ത കീ നില, പരിശോധിച്ചുറപ്പിച്ച കാഷ്, സേവ് ചെയ്ത
   പ്രൊവൈഡർ കണക്ഷൻ, ടെസ്റ്റ് പ്രവർത്തനം എന്നിവ റീലോഡിന് ശേഷവും നിലനിൽക്കണം. അസംസ്കൃത കീയും പ്രൊവൈഡർ ക്രെഡൻഷ്യലും
   ഇനി ദൃശ്യമല്ലാതായതിന് ശേഷം മാത്രം തെളിവ് പകർത്തുക.

ഒരു കീ സേവ് ചെയ്യുന്നത് മാത്രം live entitlement-ന്റെ തെളിവല്ല. സ്വകാര്യ
സേവനത്തിന്റെ `GET /v1/license/check` ഫലം, OSS കാറ്റലോഗ് നൽകുന്ന `live` ടയർ, പരിശോധിച്ചുറപ്പിച്ച signed
cache, യഥാർഥ പ്രൊവൈഡർ കണക്ഷൻ/ടെസ്റ്റ് പ്രവാഹം എന്നിവയുടെ സംയോജനമാണ് തെളിവ്. അസാധുവായതോ കാലഹരണപ്പെട്ടതോ പിൻവലിച്ചതോ ആയ കീ
കാറ്റലോഗിനെ സുരക്ഷിതമായി `community`-യിലേക്ക് താഴ്ത്തുന്നു; അതിനെ വിജയകരമായ live-key സാധൂകരണമായി റിപ്പോർട്ട് ചെയ്യരുത്.

### സ്വകാര്യ അഡ്മിൻ-പാനൽ ലിങ്ക്

Costs സൈഡ്ബാർ വിഭാഗത്തിലെ ഉപയോക്തൃ-അഭിമുഖമായ Radar ഇനത്തിന് തൊട്ടുപിന്നാലെ `RADAR_ADMIN_URL` ഐച്ഛികമായി **Radar Admin ↗** ചേർക്കുന്നു.
ഇതിന് മനഃപൂർവം ഡിഫോൾട്ട് നൽകിയിട്ടില്ല: വേരിയബിൾ സജ്ജമാക്കാതിരിക്കുകയോ അസാധുവായിരിക്കുകയോ ചെയ്യുമ്പോൾ, സ്റ്റാറ്റിക് സൈഡ്ബാർ, കമാൻഡ് പാലറ്റ്,
സൈഡ്ബാർ-കസ്റ്റമൈസേഷൻ സ്ക്രീൻ എന്നിവയിൽ അഡ്മിൻ ഇനമോ സ്വകാര്യ URL-ഓ ഉണ്ടാകില്ല.

മൂല്യം സർവർ-സൈഡിൽ പരിഹരിക്കുകയും മാനേജ്മെന്റ്-പ്രാമാണീകരിച്ച
`GET /api/settings` പ്രതികരണത്തിലൂടെ പ്രാമാണീകരിച്ച ഡാഷ്ബോർഡ് സെഷന് മാത്രം, അല്ലെങ്കിൽ പ്രാദേശിക no-login ബൂട്ട്സ്ട്രാപ്പ് സമയത്ത് വിശ്വസനീയമായ
loopback ഉടമയ്ക്ക് മാത്രം കൈമാറുകയും ചെയ്യുന്നു. CLI, internal-service, manage-scope API-key
പ്രാമാണീകരണങ്ങൾക്ക് ഇത് ലഭിക്കില്ല. `noopener noreferrer` ഉപയോഗിച്ച് തുറക്കുന്ന ബാഹ്യ ലിങ്ക് സൃഷ്ടിക്കുന്നതിന് മുമ്പ്
ബ്രൗസർ പ്രതികരണം വീണ്ടും സാധൂകരിക്കുന്നു.

ക്രെഡൻഷ്യലുകളില്ലാത്ത HTTPS tunnel/tailnet URL ഉപയോഗിക്കുക. `http://127.0.0.1:9351` പോലുള്ള loopback SSH
ഫോർവേഡിന് മാത്രമാണ് പ്ലെയിൻ HTTP അനുവദിക്കുന്നത്; മറ്റ് സ്കീമുകൾ, ഉൾച്ചേർത്ത ക്രെഡൻഷ്യലുകൾ, വികലമായ URL-കൾ,
റിമോട്ട് HTTP ലക്ഷ്യസ്ഥാനങ്ങൾ എന്നിവ സുരക്ഷിതമായി നിരസിക്കപ്പെടുകയും നാവിഗേഷൻ പ്രവർത്തനരഹിതമായി തുടരുകയും ചെയ്യും.

## സുരക്ഷാ മാതൃക

### കൃത്യമായ ബൈറ്റുകളിലെ Ed25519 ഒപ്പ്

ഫീഡ് പേലോഡ് Ed25519 ഉപയോഗിച്ച് ഒപ്പിട്ടിരിക്കുന്നു. `verifyFeedBytes()`
(`src/lib/radar/verify.ts`) നെറ്റ്വർക്കിലൂടെ ലഭിച്ച **കൃത്യമായ പ്രതികരണ ബൈറ്റുകളിലെ**
ഒപ്പ് പരിശോധിക്കുന്നു — പരിശോധനയ്ക്ക് മുമ്പ് പേലോഡ് ഒരിക്കലും വീണ്ടും സീരിയലൈസ് ചെയ്യപ്പെടുന്നില്ല; അതിനാൽ
ബൈറ്റ്-ബൈ-ബൈറ്റ് പുനഃ-എൻകോഡിങ്ങിന് ഒപ്പ് പരിശോധനയെ നിശ്ശബ്ദമായി അസാധുവാക്കാനോ മറികടക്കാനോ കഴിയില്ല.
പരിശോധന പരാജയം (`invalid_signature`) പേലോഡ് പാർസ് ചെയ്യപ്പെടുകയോ കാഷ് ചെയ്യപ്പെടുകയോ
ചെയ്യുന്നതിന് മുമ്പുതന്നെ സിങ്ക് നിർത്തുന്നു.

### പിൻ ചെയ്ത പബ്ലിക് കീ + റൊട്ടേഷൻ

പരിശോധനയ്ക്കുള്ള പബ്ലിക് കീ `src/lib/radar/pinnedKeys.ts`-ൽ
(`PINNED_FEED_PUBLIC_KEYS`) പിൻ ചെയ്തിരിക്കുന്നു. ഇത് ഒരു അറേയാണ്; അതിനാൽ റൊട്ടേഷന്
മുന്നോടിയായി പുതിയൊരു കീ ആദ്യം ചേർക്കാം, അതേസമയം മുൻ കീയുപയോഗിച്ച് ഒപ്പിട്ട പഴയ കാഷ് ചെയ്ത
ഫീഡുകൾ വീണ്ടും സിങ്ക് ചെയ്യുന്നതുവരെ സാധുവായി തുടരും.

### ഫോർക്കുകൾക്ക് അനുയോജ്യമായ env ഓവർറൈഡുകൾ

ഡിഫോൾട്ട് OmniRoute സേവനത്തിന് പകരം സ്വന്തം ഫീഡ് ഉപയോഗിക്കാൻ ഫോർക്കുകൾക്കും സ്വയം ഹോസ്റ്റ്
ചെയ്യുന്നവർക്കും രണ്ട് env വേരിയബിളുകൾ സഹായിക്കുന്നു — താഴെയുള്ള
[ഒരു ഫീഡ് സ്വയം ഹോസ്റ്റ് ചെയ്യുന്നതെങ്ങനെ](#how-to-self-host-a-feed) കാണുക:

| വേരിയബിൾ            | ഉദ്ദേശ്യം                                                                                                                     |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `RADAR_FEED_URL`    | ഫീഡിന്റെ ബേസ് URL ഓവർറൈഡ് ചെയ്യുന്നു (ഡിഫോൾട്ട് `https://radar.omniroute.online`).                                            |
| `RADAR_FEED_PUBKEY` | പിൻ ചെയ്ത പബ്ലിക് കീ ഓവർറൈഡ് ചെയ്യുന്നു (base64-DER SPKI അല്ലെങ്കിൽ PEM); ബിൽറ്റ്-ഇൻ അറേയ്ക്ക് പകരം ഈ ഒറ്റ കീ ഉപയോഗിക്കുന്നു. |

### ഏറ്റവും കുറഞ്ഞ പതിപ്പ്

നിലവിൽ കാഷ് ചെയ്ത പതിപ്പിനേക്കാൾ കർശനമായി പുതിയത് അല്ലാത്ത ഡൗൺലോഡ് ചെയ്ത ഫീഡിന്റെ
`version`, `syncRadar()` നിരസിക്കുന്നു (`compareVersions()`, ഡോട്ടുകളാൽ വേർതിരിച്ച
`YYYY.MM.DD.n` താരതമ്യം) — `{ status: "stale" }`. അപകടത്തിലായതോ തെറ്റായി
കോൺഫിഗർ ചെയ്തതോ ആയ ഒരു ഫീഡ് എൻഡ്പോയിന്റ്, ക്ലയന്റിനെ പഴയതും വ്യത്യസ്തമായി ഒപ്പിട്ടതുമായ
പേലോഡിലേക്ക് പിൻവലിക്കുന്നത് ഇത് തടയുന്നു.

### രണ്ട് തീയതികൾ, രണ്ടും നിലനിർത്തുന്നതിന്റെ കാരണം

കാഷ് ചെയ്ത ഒരു ഫീഡിൽ വ്യത്യസ്തമായ രണ്ട് തീയതികളുണ്ട്; അവ തമ്മിൽ ആശയക്കുഴപ്പമുണ്ടാകാതിരിക്കാനാണ്
രണ്ടും നിലനിർത്തുന്നത്:

| ഫീൽഡ്         | ലഭിക്കുന്നത്               | വ്യക്തമാക്കുന്നത്                             |
| ------------- | -------------------------- | --------------------------------------------- |
| `generatedAt` | ഒപ്പിട്ട ഫീഡ് ബോഡി         | **ഡാറ്റ** എത്ര പഴക്കമുള്ളതാണ്                 |
| `fetchedAt`   | ഈ ഇൻസ്റ്റാളേഷന്റെ ക്ലോക്ക് | ഈ ഇൻസ്റ്റാളേഷൻ അത് **ഡൗൺലോഡ്** ചെയ്തത് എപ്പോൾ |

മിനിറ്റുകൾക്ക് മുമ്പ് ലഭ്യമാക്കിയ ഒരു ഫീഡിൽ ആഴ്ചകൾ പഴക്കമുള്ള കണക്കുകൾ ഉണ്ടായേക്കാം; അതിനാൽ
`fetchedAt` മാത്രം ഉപയോഗിച്ച് ഒരു ഓപ്പറേറ്റർക്ക് ഓവർലേ, അതിന്റെ അടിസ്ഥാനമായ ബേസ്ലൈനിനേക്കാൾ
പുതിയതാണോ എന്ന് മനസ്സിലാക്കാനാകില്ല. രണ്ടും `radar_feed_cache`-ൽ നിലനിർത്തുകയും,
`getRadarCatalog().meta` വഴി തിരികെ നൽകുകയും, `GET /api/radar/status` വഴി വെവ്വേറെ
റിപ്പോർട്ട് ചെയ്യുകയും ചെയ്യുന്നു. `generated_at` കോളം നിലവിൽ വരുന്നതിന് മുമ്പ്
(മൈഗ്രേഷൻ 163) കാഷ് ചെയ്ത ഒരു റോ `null` ആയി വായിക്കപ്പെടുന്നു — ലഭ്യമാക്കൽ സമയം
കടമെടുക്കുന്നതിന് പകരം, അജ്ഞാതമായത് അജ്ഞാതമായി തന്നെ തുടരുന്നു.
മൈഗ്രേഷൻ 142 മുതൽ `radar_referrals_cache` സ്വന്തം `generated_at` നിലനിർത്തുന്നുണ്ട്.

മുകളിലുള്ള ഏറ്റവും കുറഞ്ഞ പതിപ്പ് പരിശോധന `version` ആണ് താരതമ്യം ചെയ്യുന്നത്, തീയതികളിലൊന്നുമല്ല.

ബോധപൂർവം അവശേഷിപ്പിച്ചിരിക്കുന്ന രണ്ട് വിടവുകളുണ്ട്: ഡാഷ്ബോർഡ് ഇപ്പോഴും `Last fetched`
മാത്രമാണ് കാണിക്കുന്നത്; അതിനാൽ അവിടെ ബിൽഡ് തീയതി കാണിക്കുന്നതിന് ഒരു പുതിയ ലേബലും
(അതിന്റെ 41 ലോക്കേൽ എൻട്രികളും) ആവശ്യമാണ്. കൂടാതെ, ഓഫറുകളുടെയും ഇന്റൽ കാഷുകളുടെയും ഫീഡ്
സ്കീമകളിൽ ബിൽഡ് തീയതി ഉൾപ്പെട്ടിട്ടുണ്ടെങ്കിലും അവ അത് സൂക്ഷിക്കുന്നില്ല — അതിനാൽ "അജ്ഞാതം"
എന്ന് വായിക്കപ്പെടാവുന്ന ഒരു `null` റിപ്പോർട്ട് ചെയ്യുന്നതിന് പകരം, ആ രണ്ടിനും `GET
/api/radar/status` ആ ഫീൽഡ് ഒഴിവാക്കുന്നു.

### സ്കീമ പരിശോധന

ഡൗൺലോഡ് ചെയ്ത ബൈറ്റുകൾ ഒപ്പ് പരിശോധിച്ചതിന് **ശേഷം** `RadarFeedSchema`
(`src/lib/radar/feedSchema.ts`, ഒരു Zod സ്കീമ) ഉപയോഗിച്ച് പാർസ് ചെയ്ത് പരിശോധിക്കുന്നു.
സ്കീമ പൊരുത്തക്കേട് `{ status: "invalid_schema" }` തിരികെ നൽകുകയും കാഷിനെ
മാറ്റമില്ലാതെ നിലനിർത്തുകയും ചെയ്യുന്നു. ഓരോ തവണ വായിക്കുമ്പോഴും (`getRadarCatalog()`)
കാഷ് ചെയ്ത പേലോഡ് മുൻകരുതലായി വീണ്ടും പരിശോധിക്കുന്നു — കേടായതോ കൈകൊണ്ട് തിരുത്തിയതോ
ആയ ഒരു കാഷ് റോ നൽകുന്നതിന് പകരം ബേസ്ലൈനിലേക്ക് മടങ്ങുന്നു.

### പ്രതികരണ വലുപ്പ പരിധി (10 MB)

ഫീഡ് പ്രതികരണ ബോഡിക്ക് `syncRadar()` ഒരു **10 MB കർശന പരിധി** ഏർപ്പെടുത്തുന്നു —
ഒപ്പിട്ട ഫീഡ് KB തോതിലുള്ള ഒരു JSON ഡോക്യുമെന്റാണ്; അതിനാൽ ഈ പരിധി കവിയുന്ന എന്തും
നിയമാനുസൃതമായ ഒരു കാറ്റലോഗല്ല, മറിച്ച് തെറ്റായി കോൺഫിഗർ ചെയ്തതോ ദോഷകരമായതോ ആയ
`RADAR_FEED_URL`-ലേക്കാണ് (അല്ലെങ്കിൽ അസംബന്ധ ഡാറ്റ നൽകുന്ന ഒരു അപ്സ്ട്രീമിലേക്കാണ്)
വിരൽ ചൂണ്ടുന്നത്. രണ്ട് തലങ്ങളിലായാണ് ഇത് നടപ്പാക്കുന്നത്:

1. ഹെഡർ ഇതിനകം പരിധിക്ക് മുകളിലുള്ള ഒരു മൂല്യം പ്രഖ്യാപിക്കുന്നുവെങ്കിൽ,
   `Content-Length` പ്രീഫ്ലൈറ്റ് പരിശോധന ബോഡി വായിക്കുന്നത് പൂർണ്ണമായി ഒഴിവാക്കുന്നു.
2. ബോഡി വായിക്കുമ്പോഴുള്ള റണ്ണിങ്-ടോട്ടൽ പരിശോധന, `Content-Length` ഇല്ലാതിരിക്കുമ്പോഴും
   യഥാർഥ വലുപ്പം കുറച്ചുകാണിക്കുമ്പോഴും പരിധി നടപ്പാക്കുന്നു — ഹെഡറിനെ മാത്രം ഒരിക്കലും
   വിശ്വസിക്കുന്നില്ല. ശേഖരിച്ച ചങ്കുകൾ കൂട്ടിച്ചേർക്കുന്നത് തുടർന്നുള്ള Ed25519 ഒപ്പ്
   പരിശോധനയ്ക്ക് ആവശ്യമായ കൃത്യമായ ബൈറ്റുകൾ സംരക്ഷിക്കുന്നു.

പരിധി കവിഞ്ഞാൽ `{ status: "too_large" }` തിരികെ നൽകുകയും കാഷിനെ മാറ്റമില്ലാതെ
നിലനിർത്തുകയും ചെയ്യുന്നു. മറ്റെല്ലാ സിങ്ക് പരാജയങ്ങളുടെയും അതേ നാശമുണ്ടാക്കാത്ത മാതൃകയാണ്
ഇത് പിന്തുടരുന്നത് (`invalid_signature`, `invalid_schema`, `stale`).

## ടയറുകൾ: `community`, `live`

ഫീഡ് സ്കീമയിൽ `tier: "community" | "live"` ഫീൽഡ് ഉൾപ്പെടുന്നു. അഭ്യർത്ഥനയെ
(സപ്പോർട്ടർ കീയുടെ സാന്നിധ്യവും സാധുതയും) അടിസ്ഥാനമാക്കി ഫീഡ് സേവനമാണ് ഇത്
**സെർവർ ഭാഗത്ത്** തീരുമാനിക്കുന്നത് — ക്ലയന്റ് ഒരിക്കലും സ്വന്തം ടയർ തീരുമാനിക്കില്ല.

- **`community`** — ഏറ്റവും പുതിയ ഡാറ്റയെക്കാൾ ഏകദേശം 30 ദിവസം വൈകിയുള്ള സൗജന്യ
  കാറ്റലോഗ്. പ്രാമാണീകരിക്കാത്തതോ അസാധുവായ കീ ഉള്ളതോ ആയ അഭ്യർത്ഥനയ്ക്ക് ലഭിക്കുന്നത് ഇതാണ്.
- **`live`** — സാധുവായ സപ്പോർട്ടർ കീ ഉൾക്കൊള്ളുന്ന അഭ്യർത്ഥനകൾക്ക് നൽകുന്ന ഏറ്റവും പുതിയ
  കാറ്റലോഗ്.

**അസാധുവായതോ കാലഹരണപ്പെട്ടതോ ആയ സപ്പോർട്ടർ കീ `community`-യിലേക്ക് താഴ്ത്തപ്പെടുന്നു —
അത് ഒരിക്കലും ഒരു പിശകല്ല.** സിങ്ക് പാത ഒപ്പ്/സ്കീമ/പതിപ്പ് പരാജയങ്ങളെയും (എല്ലാം
വീണ്ടെടുക്കാവുന്നവയും കാഷ് ചെയ്ത നിലയ്ക്ക് മാരകമല്ലാത്തവയും) വിജയകരമായ `{ status:
"updated", version, tier }`-നെയും മാത്രമാണ് വേർതിരിക്കുന്നത്. ക്ലയന്റ് കൈകാര്യം
ചെയ്യേണ്ട ടയർ-നിർദ്ദിഷ്ട പിശക് പാതയൊന്നുമില്ല.

### നൽകപ്പെടുന്ന ടയർ വരുന്നത് പ്രതികരണ ഹെഡറിൽ നിന്നാണ്, ഒപ്പിട്ട ബോഡിയിൽ നിന്നല്ല

ഒപ്പിട്ട ഫീഡ് **ബോഡി**യിലെ `tier` ഫീൽഡ് എല്ലായ്പ്പോഴും `"live"` ആണ് — ഫീഡ് സേവനം
**ഓരോ പതിപ്പിനും ഒപ്പിട്ട രണ്ട് ആർട്ടിഫാക്ടുകൾ** നൽകുന്നു: live-ൽ നിലവിലെ ക്യാംപെയ്നുകൾ
ഉൾപ്പെടുന്നു, community അവ ഒഴിവാക്കുന്നു. ഓരോ ആർട്ടിഫാക്ടിനും അതിന്റേതായ കൃത്യമായ ബൈറ്റുകൾ
അടിസ്ഥാനമാക്കിയാണ് ഒപ്പിടുന്നത്. എന്നിരുന്നാലും, അർഹതാ തീരുമാനം എടുക്കുന്നതിനുള്ള ഉറവിടമായി
ബോഡി പ്രവർത്തിക്കുന്നില്ല; ഒരു അഭ്യർത്ഥനയ്ക്കായി യഥാർഥത്തിൽ തിരഞ്ഞെടുത്ത ടയർ
**`x-omniroute-feed-tier` പ്രതികരണ ഹെഡറിൽ** ഉൾപ്പെടുത്തുന്നു. അഭ്യർത്ഥനയിലെ
`Authorization` കീയെ അടിസ്ഥാനമാക്കി സെർവർ ഭാഗത്താണ് അത് തീരുമാനിക്കുന്നത്.

ക്ലയന്റ് വിശ്വസിക്കേണ്ട ടയർ നിർണ്ണയിക്കുന്ന ഏക സ്ഥലം
`syncRadar()` (`src/lib/radar/sync.ts::parseServedTierHeader()`) ആണ്:

1. `RadarTierSchema` (Zod) ഉപയോഗിച്ച് `x-omniroute-feed-tier` പാഴ്സ് ചെയ്യുക — ഹെഡർ
   ഇല്ലെങ്കിലോ മൂല്യം കൃത്യമായി `"community"` അല്ലെങ്കിൽ `"live"` അല്ലെങ്കിലോ, അത്
   **നിലവിലില്ലാത്തതായി** കണക്കാക്കുന്നു (ഉള്ളതുപോലെ ഒരിക്കലും കാഷിലേക്കോ UI-യിലേക്കോ
   വിശ്വസിച്ച് ചേർക്കില്ല; ഹെഡർ നിലവിൽ വരുന്നതിന് മുമ്പുള്ള പഴയ ഫീഡ് സെർവറുകളെയും
   ഇത് ഉൾക്കൊള്ളുന്നു).
2. ഘട്ടം 1 ഒന്നും നൽകാത്തപ്പോൾ മാത്രം ഒപ്പിട്ട ബോഡിയിലെ `tier` ഫീൽഡിലേക്ക്
   (എല്ലായ്പ്പോഴും `"live"`) മടങ്ങുക.
3. നിർണ്ണയിച്ച ടയർ തന്നെയാണ് കാഷ് ചെയ്യപ്പെടുന്നതും `{ status: "updated",
version, tier }` ആയി തിരികെ നൽകപ്പെടുന്നതും — ഡാഷ്ബോർഡ് കാണിക്കുന്ന മൂല്യം ഇതാണ്,
   അസംസ്കൃത ബോഡി ഫീൽഡല്ല.

## വായനാ-സമയ ഓവർലേ ലയന നിയമങ്ങൾ

`applyFeed()` (`src/lib/radar/applyFeed.ts`), `getRadarCatalog()`-ന്റെ ഉള്ളിൽ
**വായനാ സമയത്ത്**, സ്റ്റാറ്റിക് ബേസ്ലൈനിന് **മുകളിൽ** കാഷ് ചെയ്ത ഫീഡ് ലയിപ്പിക്കുന്നു.
ബേസ്ലൈൻ അറേ (`FREE_MODEL_BUDGETS`) ഒരിക്കലും മാറ്റപ്പെടുന്നില്ല — ഓരോ കോളിലും പുതിയൊരു
`MergedEntry[]` കണക്കാക്കുന്നു.

മുൻഗണനാക്രമത്തിലുള്ള നാല് നിയമങ്ങൾ:

1. **ഫീഡ് ഒരിക്കലും ലോക്കൽ ഓവർറൈഡിനെ മാറ്റിയെഴുതില്ല.** ഓരോ ഫീൽഡിനും: ഓപ്പറേറ്റർ
   ഒരു എൻട്രിയിലെ ഫീൽഡ് ഇഷ്ടാനുസൃതമാക്കിയിട്ടുണ്ടെങ്കിൽ (`provider:modelId` കീ ആക്കിയ
   `localOverrides` മാപ്പ്), ആ നിർദ്ദിഷ്ട ഫീൽഡിനുള്ള ഫീഡിന്റെ മൂല്യം ഒഴിവാക്കപ്പെടുന്നു —
   ഓപ്പറേറ്ററുടെ മൂല്യത്തിനാണ് മുൻഗണന.
2. **`enabled: false` എൻട്രി പ്രവർത്തനരഹിതമാക്കുകയും അതിന്റെ ഉറവിടം രേഖപ്പെടുത്തുകയും
   ചെയ്യുന്നു.** ഒരു എൻട്രി ഓഫാക്കുന്ന ഫീഡ് എൻട്രി, ലയിപ്പിച്ച ഫലത്തിൽ `enabled: false`,
   `disabledBy: "radar"` എന്നിവ സജ്ജീകരിക്കുന്നു. അതുവഴി, ലഭ്യമായിരുന്ന ഒരു എൻട്രി
   പ്രവർത്തനരഹിതമായത് _എന്തുകൊണ്ടാണെന്ന്_ UI-ക്ക് വിശദീകരിക്കാൻ കഴിയും.
3. **ഫീഡിൽ ഇല്ലാത്ത ഉപയോക്താവ് ചേർത്ത എൻട്രി മാറ്റമില്ലാതെ നിലനിൽക്കും.** ബേസ്ലൈനിൽ
   മാത്രം നിലവിലുള്ളതോ ലോക്കലായി ചേർത്തതോ, അതിനൊത്ത ഫീഡ് എൻട്രി ഇല്ലാത്തതോ ആയ
   എൻട്രികൾ മാറ്റമില്ലാതെ കടന്നുപോകുന്നു.
4. **ടോംബ്സ്റ്റോൺ ചെയ്ത എൻട്രി ഒരിക്കലും പുനഃസ്ഥാപിക്കപ്പെടില്ല.** ഓപ്പറേറ്റർ ഒരു
   എൻട്രി വ്യക്തമായി ഇല്ലാതാക്കിയിട്ടുണ്ടെങ്കിൽ (`tombstones` സെറ്റ്), പിന്നീടുള്ള
   പതിപ്പിൽ ഫീഡ് ആ `provider:modelId` വീണ്ടും ചേർത്താലും അത് തിരികെ വരില്ല.

എഡിറ്റ് ചെയ്യാവുന്ന ഫീൽഡുകളും ടോംബ്സ്റ്റോണുകളും
`radar_local_model_state`-ൽ (മൈഗ്രേഷൻ `153_radar_local_model_state.sql`) സ്ഥിരമായി
സൂക്ഷിക്കുന്നു. പൊതു DB അഡാപ്റ്റർ (`src/lib/db/radar.ts`) ആ വരികളെ `applyFeed()`
ഉപയോഗിക്കുന്ന `localOverrides` മാപ്പിലേക്കും `tombstones` സെറ്റിലേക്കും മാറ്റുന്നു;
പ്രൊഡക്ഷനിലെ `getRadarCatalog()`, ഫ്ലാഗ്, കാഷ്, സ്കീമ ഗേറ്റുകൾ കടന്നതിന് ശേഷം ആ നില
ലോഡ് ചെയ്യുന്നു. `displayName`, `enabled` എന്നിവ മാത്രമാണ് ഓപ്പറേറ്റർക്ക് എഡിറ്റ്
ചെയ്യാനാകുന്നത്. പ്രൊവൈഡർ/മോഡൽ ഐഡന്റിറ്റി, ഫീഡ് ഉറവിടം, ക്വാട്ട, ശേഷികൾ, ToS,
സജ്ജീകരണ ഡാറ്റ എന്നിവ ഈ ഉപരിതലത്തിലൂടെ എഴുതാനാവില്ല.

ഡാഷ്ബോർഡ് നാല് ലോക്കൽ പ്രവർത്തനങ്ങൾ നൽകുന്നു:

- **എഡിറ്റ്** ലോക്കൽ പ്രദർശന നാമവും പ്രവർത്തനക്ഷമമായ നിലയും മാറ്റുന്നു.
- **ലോക്കൽ മാറ്റങ്ങൾ റീസെറ്റ് ചെയ്യുക** ടോംബ്സ്റ്റോൺ മാറ്റാതെ എഡിറ്റ് ചെയ്യാവുന്ന രണ്ട്
  ഫീൽഡുകളും മായ്ക്കുന്നു.
- **മറയ്ക്കുക** ഒരു ടോംബ്സ്റ്റോൺ സൃഷ്ടിക്കുന്നു; അതിനാൽ പിന്നീടുള്ള ഫീഡ് അപ്ഡേറ്റുകൾക്ക്
  ആ വരി വീണ്ടും സൃഷ്ടിക്കാനാവില്ല.
- **പുനഃസ്ഥാപിക്കുക** ടോംബ്സ്റ്റോൺ നീക്കം ചെയ്യുന്നു; പ്രത്യേകം സേവ് ചെയ്തിട്ടുള്ള
  ഏതൊരു ഓവർറൈഡും തുടർന്നും പ്രാബല്യത്തിലുണ്ടാകും.

ഫീഡിലെ `enabled: false` സുരക്ഷാ അപവാദമായി തുടരുന്നു: കാലഹരണപ്പെട്ട ലോക്കൽ
`enabled: true`-നെക്കാൾ അതിന് മുൻഗണന ലഭിക്കുകയും, ലയിപ്പിച്ച എൻട്രിയെ
പ്രവർത്തനരഹിതമായി നിലനിർത്തുകയും, `disabledBy: "radar"` രേഖപ്പെടുത്തുകയും ചെയ്യുന്നു.

കാറ്റലോഗ് പ്രസിദ്ധീകരണങ്ങൾ `schemaVersion: 2` ഉപയോഗിക്കുന്നു. `contextWindow`-വും
`tools`, `vision`, `thinking` എന്നിവ ഓരോന്നും സ്വതന്ത്രമായി `number | null` /
`boolean | null` ആണ്: `null` എന്നാൽ അജ്ഞാതം എന്നാണ്; `false` എന്നാൽ ആ ശേഷി ഇല്ലെന്ന്
D16 സ്ഥിരീകരിച്ച ഔദ്യോഗിക പ്രൊവൈഡർ ഉറവിടം വ്യക്തമായി പറയുന്നു എന്നാണ്. ആന്തരിക
OmniRoute രജിസ്ട്രി/മോഡൽ-സ്പെക് ഫ്ലാഗുകൾ ഒരിക്കലും നേരിട്ട് ഫീഡ് വസ്തുതകളാക്കി
ഉയർത്തപ്പെടുന്നില്ല. ക്ലയന്റ് ഇപ്പോഴും v1 സ്നാപ്പ്ഷോട്ടുകൾ സ്വീകരിക്കുന്നു; പഴയ ബിൽഡർ
അഭാവം സൂചിപ്പിക്കുന്ന പ്ലേസ്ഹോൾഡറായി `false` ഉപയോഗിച്ചിരുന്നതിനാൽ, v1 `false`
അജ്ഞാതമായി നോർമലൈസ് ചെയ്യപ്പെടുന്നു, എന്നാൽ v1 `true` വസ്തുതയായി തുടരുന്നു. അജ്ഞാതമായ
സ്കീമ പതിപ്പുകൾ സുരക്ഷിതമായി നിരസിക്കപ്പെടുകയും അവസാനം സാധുതയുണ്ടായിരുന്ന കാഷ് തുടർന്നും
ലഭ്യമായിരിക്കുകയും ചെയ്യും. null അല്ലാത്ത context/capability ഉള്ള ഓരോ v2 മോഡലിലും
ക്രെഡൻഷ്യൽ ആവശ്യമില്ലാത്ത HTTPS `metadataEvidenceUrls[]` ഉണ്ടായിരിക്കണം; അല്ലെങ്കിൽ
സ്കീമ സാധൂകരണം പരാജയപ്പെടുകയും കാഷ് മാറ്റിസ്ഥാപിക്കപ്പെടാതിരിക്കുകയും ചെയ്യും.
കാറ്റലോഗ് പട്ടിക മൂന്ന് നിലകളും `✓`, `✕`, `?` എന്നിങ്ങനെ റെൻഡർ ചെയ്യുന്നു.

### മാർഗനിർദ്ദേശമുള്ള കോംബോകളും MCP ആക്സസും

സ്ഥിരീകരിച്ച `familyId` മൂല്യങ്ങൾ വായനാ-സമയ ഓവർലേയ്ക്ക് ശേഷവും നിലനിൽക്കുകയും ശുദ്ധമായ
`buildRadarComboSuggestions()` മൊഡ്യൂളിനെ (`src/lib/radar/comboSuggestions.ts`)
നിയന്ത്രിക്കുകയും ചെയ്യുന്നു. കുറഞ്ഞത് രണ്ട് വ്യത്യസ്ത പ്രൊവൈഡർമാർക്ക് സജീവ കണക്ഷനുകൾ
ഉണ്ടാകുകയും അവർ കൃത്യമായ ക്യൂറേറ്റ് ചെയ്ത മോഡൽ ID ലഭ്യമാക്കുകയും ചെയ്യുമ്പോൾ മാത്രമാണ്
ഒരു ഫാമിലി നിർദ്ദേശിക്കപ്പെടുന്നത്. പ്രവർത്തനരഹിതമായ മോഡലുകൾ, നിഷ്ക്രിയ പ്രൊവൈഡർമാർ,
നഷ്ടമായ മോഡൽ ID-കൾ, ഒറ്റ അംഗമുള്ള ഫാമിലികൾ, അവ്യക്തമായ അലിയാസ്/പ്രിഫിക്സ് പൊരുത്തങ്ങൾ
എന്നിവ സുരക്ഷിതമായി നിരസിക്കപ്പെടുന്നു. നിർദ്ദേശങ്ങൾ നിലവിലുള്ള `priority` തന്ത്രം
ഉപയോഗിക്കുകയും, ആവർത്തിച്ചുള്ള ഏറ്റവും വലിയ പ്രതിമാസ ബജറ്റിന് ആദ്യം സ്ഥാനം നൽകുകയും
ചെയ്യുന്നു; UI അവ സൃഷ്ടിക്കുന്നത് `POST /api/combos` വഴി മാത്രമാണ്.

ഗൈഡഡ് UI `/dashboard/radar/combos`-ലാണ് സ്ഥിതിചെയ്യുന്നത്. ഇത് ലോക്കൽ
`GET /api/radar/catalog`, `GET /api/combos/builder/options` എൻഡ്പോയിന്റുകൾ മാത്രമാണ് വായിക്കുന്നത്. ഇത് ഒരിക്കലും Radar സമന്വയം പ്രവർത്തനക്ഷമമാക്കുകയോ,
പ്രൊവൈഡർ ക്രെഡൻഷ്യലുകൾ വായിക്കുകയോ, കോംബോ ഡാറ്റാബേസിലേക്ക് നേരിട്ട് എഴുതുകയോ ചെയ്യുന്നില്ല.

MCP ക്ലയന്റുകൾക്ക് `omniroute_radar_catalog` (`read:radar`) ഉപയോഗിച്ച് ഇതേ ലോക്കൽ പ്രൊജക്ഷൻ വായിക്കാനാകും. ഐച്ഛികമായ
`provider`, `familyId`, `enabledOnly` ഫിൽട്ടറുകൾ ഒരൊറ്റ ലോക്കൽ
`GET /api/radar/catalog` റീഡിന് ശേഷം മൂല്യനിർണ്ണയം ചെയ്യപ്പെടുന്നു. ഇതിന്റെ നിയന്ത്രിത ഔട്ട്പുട്ടിൽ കാറ്റലോഗ് മെറ്റാഡാറ്റയ്ക്കൊപ്പം പ്രൊവൈഡർ/മോഡൽ,
ഡിസ്പ്ലേ നാമം, `familyId`, ക്വോട്ട, ശേഷികൾ, പ്രവർത്തനക്ഷമമാക്കിയ നില, ഉറവിടം, `disabledBy` എന്നിവ ഉൾപ്പെടുന്നു; സജ്ജീകരണ URL-കൾ,
ഘട്ടങ്ങൾ, കണക്ഷനുകൾ, ഇ-മെയിൽ വിലാസങ്ങൾ, കീകൾ, റഫറൽ ഡാറ്റ എന്നിവ ഒരിക്കലും തിരികെ നൽകില്ല. ഈ ടൂൾ
വായിക്കാൻ മാത്രമുള്ളതാണ്, കൂടാതെ `/api/radar/sync` ഒരിക്കലും പ്രവർത്തിപ്പിക്കില്ല.

### ഉറവിട സൂചകങ്ങൾ

ലയിപ്പിച്ച ഓരോ എൻട്രിയിലും UI ഒരു ബാഡ്ജായി റെൻഡർ ചെയ്യുന്ന `origin` ഫീൽഡ് ഉണ്ടായിരിക്കും:

- `"baseline"` — സ്റ്റാറ്റിക് റിലീസ് കാറ്റലോഗിൽ നിന്ന് മാറ്റമില്ലാത്തത്.
- `"radar"` — ഒന്നോ അതിലധികമോ ഫീൽഡുകൾ ഫീഡ് വഴി പുതുക്കിയവ.
- `"local"` — ഓപ്പറേറ്റർ ഈ എൻട്രിയിൽ കുറഞ്ഞത് ഒരു ലോക്കൽ ഓവർറൈഡെങ്കിലും നൽകിയിട്ടുണ്ട് (ഫീഡ് എന്ത് പറയുന്നുവെന്നത് പരിഗണിക്കാതെ,
  നിയമം 1 അനുസരിച്ച് ലോക്കൽ ഓവർറൈഡുകൾക്കാണ് എല്ലായ്പ്പോഴും മുൻഗണന).

ലോക്കൽ OmniRoute സെർവറുമായി മാത്രമാണ് ആശയവിനിമയം നടത്തുന്നത്. Radar സേവനവുമായി ബന്ധപ്പെടുന്ന നാല് മൊഡ്യൂളുകൾ
`src/lib/radar/sync.ts` (കാറ്റലോഗ്), `src/lib/radar/referralsSync.ts` (റഫറലുകൾ), കൂടാതെ
`src/lib/radar/offersSync.ts` (ഓഫറുകൾ), അതോടൊപ്പം `src/lib/radar/intelSync.ts` (Intel) എന്നിവയാണ്; എല്ലാം
സെർവർ ഭാഗത്താണ് പ്രവർത്തിക്കുന്നത്, ക്ലയന്റ് ഭാഗത്ത് ഒരിക്കലുമല്ല. ഇതുവഴി
ഫീഡ് URL-ഉം ഏതൊരു സപ്പോർട്ടർ കീയും ക്ലയന്റിന് ദൃശ്യമാകുന്ന നെറ്റ്വർക്ക് ട്രാഫിക്കിൽ നിന്ന് പൂർണമായും ഒഴിവാക്കുന്നു.

`RADAR_ENABLED` ഓഫായിരിക്കുമ്പോൾ എല്ലാ Radar എൻഡ്പോയിന്റുകളും `404` തിരികെ നൽകുന്നു (മുകളിലുള്ള
[ഫ്ലാഗ്](#flag-radar_enabled-default-off) കാണുക), കൂടാതെ റിപ്പോ മുഴുവനുമുള്ള പിശക്-ശുചീകരണ നിയമം
(`docs/security/ERROR_SANITIZATION.md`) അനുസരിച്ച് റൂട്ട് പിശക് പ്രതികരണങ്ങൾ
`buildErrorBody()`/`sanitizeErrorMessage()` വഴി കൈകാര്യം ചെയ്യുന്നു.

### പ്രാമാണീകരണം

എല്ലാ Radar എൻഡ്പോയിന്റുകൾക്കും `isAuthenticated()`
(`src/shared/utils/apiAuth.ts`) വഴിയുള്ള പ്രാമാണീകരണം ആവശ്യമാണ് — ഒരു ഡാഷ്ബോർഡ് സെഷൻ കുക്കി അല്ലെങ്കിൽ മാനേജ്മെന്റ്-സ്കോപ്പിലുള്ള
API കീ; `/api/settings/*`-ന്റെ ബാക്കി ഭാഗങ്ങളെ സംരക്ഷിക്കുന്ന അതേ ഗേറ്റാണിത്. ഫ്ലാഗ്-ഓഫ്
`404` പരിശോധന എപ്പോഴും പ്രാമാണീകരണ പരിശോധനയ്ക്ക് **മുമ്പ്** പ്രവർത്തിക്കുന്നു, അതിനാൽ `RADAR_ENABLED`
ഓഫായിരിക്കുന്ന ഒരു ഇൻസ്റ്റാളേഷൻ ബൈറ്റ്-തലത്തിൽ അതേപടി തുടരുന്നു (ഈ സർഫേസ് നിലവിലില്ലെന്ന് അറിയാൻ മാത്രം പ്രാമാണീകരണ പ്രോംപ്റ്റ് ഉണ്ടാകില്ല);
ഫ്ലാഗ് ഓണാക്കിയശേഷം, പ്രാമാണീകരിക്കാത്ത ഒരു അഭ്യർത്ഥനയ്ക്ക് ഏതൊരു DB വായനയ്ക്കോ
എഴുത്തിനോ മുമ്പ് `401` ലഭിക്കും. പ്രാമാണീകരണ നില എന്തായാലും `GET /api/radar/settings` അസംസ്കൃത സപ്പോർട്ടർ കീ ഒരിക്കലും തിരികെ നൽകില്ല
— മാസ്ക് ചെയ്ത രൂപവും ഒരു `hasSupporterKey` ബൂളിയനും മാത്രമാണ് നൽകുന്നത്.

## സപ്പോർട്ടർ ഓഫറുകൾ

ഓഫറുകൾ അവയ്ക്കായി പ്രത്യേകം സൈൻ ചെയ്ത ആർട്ടിഫാക്റ്റായ `GET /v1/offers/latest` ഉപയോഗിക്കുന്നു; കാറ്റലോഗ് അല്ലെങ്കിൽ
റഫറൽ കാഷെ അവ ഒരിക്കലും പങ്കിടുന്നില്ല. സെർവർ എൻഡ്പോയിന്റിന് സാധുവും സജീവവുമായ സപ്പോർട്ടർ Bearer കീ ആവശ്യമാണ്;
കമ്മ്യൂണിറ്റി ഫാൾബാക്ക് ഇല്ല. അതിനാൽ, ഫീച്ചർ ഫ്ലാഗ് ഓഫായിരിക്കുമ്പോഴോ, ഓപ്പറേറ്റർ സമ്മതം
നൽകിയിട്ടില്ലെങ്കിലോ, സപ്പോർട്ടർ കീ കോൺഫിഗർ ചെയ്തിട്ടില്ലെങ്കിലോ `syncRadarOffers()` നെറ്റ്വർക്ക് ആക്സസിന് മുമ്പ് നിർത്തുന്നു.

വിജയകരമായ GET-ന് ശേഷം, കൃത്യമായ റെസ്പോൺസ് ബൈറ്റുകളുടെ Ed25519 സിഗ്നേച്ചർ ക്ലയന്റ് പരിശോധിക്കുകയും,
`RadarOffersFeedSchema` സാധൂകരിക്കുകയും, സൈൻ ചെയ്ത ബോഡിയിലും
`x-omniroute-feed-tier` ഹെഡറിലും `live` എന്ന് ഉണ്ടായിരിക്കണമെന്ന് നിർബന്ധിക്കുകയും, കൃത്യമായി കൂടുതൽ പുതിയ ഡോട്ടഡ് പതിപ്പ്
നിർബന്ധമാക്കുകയും ചെയ്യുന്നു; അതിനുശേഷം മാത്രമാണ് `radar_offers_cache` (മൈഗ്രേഷൻ `144_radar_offers_cache.sql`)
അറ്റോമിക്കായി മാറ്റിസ്ഥാപിക്കുന്നത്. മറ്റ് ഫീഡുകൾ ഉപയോഗിക്കുന്ന അതേ 10 MB
ഹെഡർ-പ്ലസ്-സ്ട്രീം പരിധി ഇവിടെയും ബാധകമാണ്. സിഗ്നേച്ചർ, സ്കീമ, ടിയർ, റീപ്ലേ, വലുപ്പം, HTTP,
നെറ്റ്വർക്ക് പരാജയങ്ങൾ എല്ലാം അവസാനം പരിശോധിച്ചുറപ്പിച്ച കാഷെ നിലനിർത്തുന്നു.

ക്ലോസ്ഡ് ഓഫർ ഘടന താരതമ്യം ചെയ്യാവുന്ന മൂന്ന് ആനുകൂല്യ തരങ്ങളെ പിന്തുണയ്ക്കുന്നു: ബേസിസ് പോയിന്റുകളിലെ ശതമാനം, ചെറിയ
കറൻസി യൂണിറ്റുകളിലെ ക്രെഡിറ്റ്, അല്ലെങ്കിൽ ട്രയൽ ദിവസങ്ങൾ. ഒരു പാർട്ണർ ഓഫറിൽ അതേ തരത്തിലുള്ള പൊതു ബേസ്ലൈൻ ഉൾപ്പെടുത്തണം;
അതിന്റെ ആനുകൂല്യം നിർബന്ധമായും അതിലും കൂടുതലായിരിക്കണം. ഔദ്യോഗിക ഓഫറുകൾക്ക് പാർട്ണർ ബേസ്ലൈൻ ഇല്ല. URL-കൾ
ക്രെഡൻഷ്യലുകളില്ലാത്ത HTTPS ആയിരിക്കണം. ഓരോ ലോക്കൽ റീഡിലും കാഷ് ചെയ്ത പേലോഡ് `getRadarOffers()` പ്രതിരോധാത്മകമായി
വീണ്ടും സാധൂകരിക്കുകയും കാലഹരണപ്പെട്ട എൻട്രികൾ ഫിൽട്ടർ ചെയ്യുകയും ചെയ്യുന്നു; `/dashboard/radar/offers` റെൻഡർ ചെയ്യുന്നതിന് മുമ്പ്
കാലഹരണ തീയതി വീണ്ടും ഫിൽട്ടർ ചെയ്യുന്നു, ലഭ്യമാകുമ്പോൾ പോർച്ചുഗീസ് ടെക്സ്റ്റും അല്ലാത്തപ്പോൾ ഇംഗ്ലീഷ് ഫാൾബാക്കും ഉപയോഗിക്കുന്നു,
കൂടാതെ പാർട്ണർ ഓഫറുകൾ വ്യക്തമായി ലേബൽ ചെയ്യുന്നു.

ബ്രൗസർ ലോക്കൽ റൂട്ടുകൾ മാത്രമാണ് വിളിക്കുന്നത്: മാസ്ക് ചെയ്ത സെറ്റിങ്സ് സ്നാപ്പ്ഷോട്ട് വായിക്കുകയും, സെർവർ-സൈഡിൽ
റിഫ്രഷ് ചെയ്യാൻ `POST /api/radar/offers/sync`-നോട് ആവശ്യപ്പെടുകയും, തുടർന്ന് `GET /api/radar/offers` വായിക്കുകയും ചെയ്യുന്നു.
കീ ഇല്ലെങ്കിൽ, ഫീഡ് അഭ്യർത്ഥന നടത്താൻ ശ്രമിക്കുന്നതിന് പകരം നിലവിലുള്ള കോൺട്രിബ്യൂട്ടർ/പിന്തുണാ ലിങ്കുകൾ കാണിക്കുന്നു. ബാഹ്യ
ഓഫർ ലിങ്കുകൾ `noopener noreferrer` ഉപയോഗിച്ച് പുതിയ ടാബിൽ തുറക്കുന്നു. ഈ റിലീസിൽ `radar_offers` MCP ടൂൾ ലഭ്യമാക്കിയിട്ടില്ല.

## Radar Intel, സപ്പോർട്ടർ ബാഡ്ജ്, CLI

Intel എന്നത് `GET /v1/intel/latest`-ൽ ലഭിക്കുന്ന സൈൻ ചെയ്ത ആർട്ടിഫാക്റ്റാണ്. സ്ഥിരീകരിച്ച താരതമ്യങ്ങളിൽ നിന്ന് സ്വകാര്യ
ക്യൂറേറ്റർ നിർണ്ണയിച്ച Radar-ന്റെ സ്വന്തം ELO റാങ്കിങ്ങുകളും, സൈൻ ചെയ്ത കാറ്റലോഗ് സ്നാപ്പ്ഷോട്ടുകളിൽ നിന്ന് നിർണ്ണയിച്ച വസ്തുതാപരമായ
കാറ്റലോഗ് പ്രായ/എണ്ണ വ്യത്യാസങ്ങളും മാത്രമാണ് ക്ലോസ്ഡ് `RadarIntelFeedSchema` സ്വീകരിക്കുന്നത്. പ്രാരംഭ
റേറ്റിങ് 1000, K=32 എന്നിങ്ങനെ രീതിശാസ്ത്രം നിശ്ചിതമാണ്. ഒരു താരതമ്യവും സ്ഥിരീകരിച്ചിട്ടില്ലാത്തപ്പോൾ ശൂന്യമായ റാങ്കിങ് സാധുവാണ്;
ക്ലയന്റ് ഒരിക്കലും ഒരെണ്ണം കൃത്രിമമായി സൃഷ്ടിക്കുന്നില്ല.

ഓഫറുകൾക്ക് ബാധകമായ അതേ സെർവർ-സൈഡ് Bearer, 30 സെക്കൻഡ് ടൈംഔട്ട്, 10 MiB സ്ട്രീംഡ് പരിധി,
കൃത്യമായ ബൈറ്റുകളുടെ Ed25519 പരിശോധന, കർശനമായ സ്കീമ, ബോഡി/ഹെഡറിൽ `live` ഉണ്ടായിരിക്കണമെന്ന നിബന്ധന, പതിപ്പ് ഫ്ലോർ,
അവസാനം സാധൂകരിച്ച കാഷ് സംരക്ഷണം എന്നിവ `syncRadarIntel()` പ്രയോഗിക്കുന്നു. പരിശോധിച്ചുറപ്പിച്ച ഒരു ലൈവ് സ്നാപ്പ്ഷോട്ട്
സംഭരിച്ച ശേഷം, ക്ലയന്റ് `radar:<sha256(supporter key)>` ഡെറൈവ് ചെയ്യുകയും ആ ഏകദിശ ഐഡന്റിറ്റി മാത്രം സംഭരിക്കുകയും
പ്രത്യേക `radar_supporter` അംഗീകാര ഇവന്റ് പുറപ്പെടുവിക്കുകയും ചെയ്യുന്നു. അതിന്റെ `radar-supporter` ബാഡ്ജ് ഐഡംപൊട്ടന്റാണ്,
കൂടാതെ പൂജ്യം XP നൽകുന്നു; അത് ഒരിക്കലും ലീഡർബോർഡുകൾ അപ്ഡേറ്റ് ചെയ്യുകയോ `token_share` വീണ്ടും ഉപയോഗിക്കുകയോ ചെയ്യുന്നില്ല.
പരിശോധിച്ചുറപ്പിച്ച ലോക്കൽ കാഷ് മെറ്റാഡാറ്റയിൽ നിന്ന് മാത്രമാണ് `/dashboard/radar/intel` ബാഡ്ജ് റെൻഡർ ചെയ്യുന്നത്.

CLI-യിൽ `omniroute radar status`, `omniroute radar sync` എന്നിവ ലഭ്യമാണ്. രണ്ടും ലോക്കൽ OmniRoute API-യുമായി
മാത്രമാണ് ആശയവിനിമയം നടത്തുന്നത്. `status` റീഡ്-ഒൺലി `GET /api/radar/status` നടത്തുന്നു; `sync` ഒരൊറ്റ
`POST /api/radar/sync-all` അയയ്ക്കുകയും ഓരോ ഫീഡിന്റെയും ഫലം പ്രിന്റ് ചെയ്യുകയും ചെയ്യുന്നു. രണ്ട് കമാൻഡുകളും
സപ്പോർട്ടർ കീ വായിക്കുകയോ സ്വീകരിക്കുകയോ പ്രിന്റ് ചെയ്യുകയോ ചെയ്യുന്നില്ല; Radar സേവനവുമായി നേരിട്ട് ബന്ധപ്പെടുന്നുമില്ല.

## റഫറൽ ലിങ്കുകൾ (സൗജന്യ ക്രെഡിറ്റുകൾ)

റഫറൽ ലിങ്കുകൾ കാറ്റലോഗ് ഫീഡിൽനിന്ന് വേറിട്ടുള്ള, **സ്വതന്ത്രവും എല്ലായ്പ്പോഴും കാലികവുമായ** ഒരു ഫീഡിൽനിന്നാണ് ലഭ്യമാക്കുന്നത് —
`GET /v1/referrals/latest`. ഇത് മനഃപൂർവമാണ്: കമ്മ്യൂണിറ്റി ടയറിലെ
കാറ്റലോഗ് ഫീഡ് 30 ദിവസംവരെ പഴക്കമുള്ള ഒരു സ്നാപ്പ്ഷോട്ടാണ്, അതിനാൽ അതിൽനിന്ന്
എടുത്തിരുന്ന ഒരു റഫറൽ ലിങ്ക്, സെർവറിന്റെ യഥാർത്ഥ ലിങ്ക് പട്ടികയേക്കാൾ അതേ
കാലയളവോളം പിന്നിലാകുമായിരുന്നു (പുതുതായി ചേർത്ത റഫറൽ ഒരു സൗജന്യ/കമ്മ്യൂണിറ്റി
ഉപയോക്താവിലേക്ക് എത്താൻ ഒരു മാസംവരെ എടുത്തേക്കാം). റഫറൽ ഫീഡ് അതിന്റേതായ,
വളരെ കുറഞ്ഞ ഇടവേളയിൽ സമന്വയിപ്പിക്കുന്നതിലൂടെ ആ കാലതാമസം ഒഴിവാക്കുന്നു.

```ts
// GET /v1/referrals/latest പ്രതികരണ ബോഡി (Ed25519 ഉപയോഗിച്ച് ഒപ്പിട്ടത്, കാറ്റലോഗ്
// ഫീഡിന്റെ അതേ പിൻ ചെയ്ത കീ):
{
  feed: "omniroute-radar-referrals",
  schemaVersion: 1,
  generatedAt: string,           // ISO — നിർണായകം: റഫറൽ ലിങ്കുകളിലുടനീളമുള്ള max(updatedAt),
                                  // അതിനാൽ ഒരേപോലുള്ള രണ്ട് അഭ്യർത്ഥനകൾ കൃത്യമായി ഒരേ
                                  // ഒപ്പിട്ട ബൈറ്റുകൾ/ഒപ്പ് സൃഷ്ടിക്കുന്നു
  referrals: {
    fixed: RadarReferral[],      // ഓതന്റിക്കേഷൻ ഇല്ലാത്ത/കമ്മ്യൂണിറ്റി ഉൾപ്പെടെ എല്ലാ ടയറിലും ഉണ്ടായിരിക്കും
    campaigns: RadarReferral[],  // സാധുവായ സജീവ (പിന്തുണക്കാരൻ) Bearer കീക്ക് മാത്രം
                                  // ഡാറ്റ ഉണ്ടായിരിക്കും; ഓതന്റിക്കേഷൻ ഇല്ലാത്ത/കാലഹരണപ്പെട്ട കീ അഭ്യർത്ഥനകൾക്ക് []
  },

```

കാറ്റലോഗ് ഫീഡിൽനിന്ന് വ്യത്യസ്തമായി, ഈ ബോഡിയിൽ `tier` ഫീൽഡ് ഒട്ടും ഇല്ല —
`Authorization` കീയെ അടിസ്ഥാനമാക്കി ഓരോ അഭ്യർത്ഥനയിലും എന്തൊക്കെ ഉൾപ്പെടുത്തണമെന്ന്
സെർവർ തീരുമാനിക്കുന്നു. അതിനാൽ ലഭ്യമാക്കിയ ടയർ നിർണ്ണയിക്കുന്നതിനുള്ള **ഏക**
സ്രോതസ്സ് `x-omniroute-feed-tier` പ്രതികരണ ഹെഡറാണ്
(`referralsSync.ts::syncRadarReferrals`); ഹെഡർ ഇല്ലെങ്കിലോ തിരിച്ചറിയാൻ കഴിയാത്തതാണെങ്കിലോ,
ഏറ്റവും കുറഞ്ഞ പ്രത്യേകാവകാശമുള്ള അനുമാനമായ `"community"`-ലേക്ക് താഴ്ത്തപ്പെടും.
`RadarReferralsFeedSchema` (`src/lib/radar/referralsFeedSchema.ts`) മുഴുവൻ ബോഡിയും
സാധൂകരിക്കുന്നു. രണ്ട് ഫീഡുകളും ഓരോ റഫറലിനെയും ഒരേ രീതിയിൽ സാധൂകരിക്കുന്നതിനായി
`feedSchema.ts`-ൽനിന്ന് എക്സ്പോർട്ട് ചെയ്യുന്ന അതേ ഓരോ-റഫറലിനുമുള്ള
`RadarReferralSchema` ഇത് പുനരുപയോഗിക്കുന്നു. ഓരോ `RadarReferral.url`-ഉം
`https://` ആയിരിക്കണം — ഒരു `http://` url സ്കീമ സാധൂകരണത്തിൽ പരാജയപ്പെടും.

`RadarFeedSchema`-യിലെ (`feedSchema.ts`) പഴയ, കാറ്റലോഗിനുള്ളിൽ ഉൾച്ചേർത്ത
`referrals` ഫീൽഡ് ഇതിനകം കാഷ് ചെയ്ത കാറ്റലോഗ് ഫീഡുകളുമായുള്ള പിന്നോട്ടുള്ള
പൊരുത്തത്തിനായി നിലനിർത്തിയിട്ടുണ്ട്. എന്നാൽ `getRadarReferrals()` ഇനി അത്
വായിക്കുന്നില്ല — താഴെയുള്ള [ആക്സസർ](#accessor) കാണുക.

### സമന്വയം

`syncRadarReferrals()` (`src/lib/radar/referralsSync.ts`) മാത്രമാണ് റഫറലുകൾക്കായി
നെറ്റ്വർക്ക് ആക്സസ് ചെയ്യുന്ന **ഏക** മൊഡ്യൂൾ. ഇത് `syncRadar()`-ന്റെ കരാർ കൃത്യമായി
പ്രതിഫലിപ്പിക്കുന്നു: ഫ്ലാഗ് ഓഫാണെങ്കിൽ → `disabled`; ഓപ്റ്റ്-ഇൻ false ആണെങ്കിൽ →
`opt_out`; `${RADAR_FEED_URL}/v1/referrals/latest` ഡൗൺലോഡ് ചെയ്യുന്നു
(കാറ്റലോഗിലെ അതേ `RADAR_FEED_URL`/`RADAR_FEED_PUBKEY` ഫോർക്ക് ഓവർറൈഡുകളോടെ);
കൃത്യമായ പ്രതികരണ ബൈറ്റുകളിലെ Ed25519 ഒപ്പ് (`verifyFeedBytes`) പരിശോധിക്കുന്നു;
`RadarReferralsFeedSchema` ഉപയോഗിച്ച് സാധൂകരിക്കുന്നു; തുടർന്ന്
`radar_referrals_cache` പട്ടികയിലേക്ക് (മൈഗ്രേഷൻ
`142_radar_referrals_cache.sql`) കാഷ് ചെയ്യുന്നു — ഇത് കാറ്റലോഗിന്റെ
`radar_feed_cache`-ൽനിന്ന് പൂർണ്ണമായും വേറിട്ട പട്ടികയാണ്. 10 MB പ്രതികരണ പരിധിയും
`generatedAt`-ന്റെ ഏറ്റവും കുറഞ്ഞ പരിധിയും, കാഷ് ചെയ്തതിനേക്കാൾ പഴയതായി ലഭിക്കുന്ന
ഫീഡിനെ നിരസിക്കുന്നു; ഇതിലൂടെ പഴയ ഒപ്പിട്ട ആർട്ടിഫാക്റ്റിന്റെ റീപ്ലേയിൽനിന്ന്
സംരക്ഷിക്കുന്നു. തുല്യമായ ടൈംസ്റ്റാമ്പ് സ്വീകരിക്കും: കമ്മ്യൂണിറ്റി, ലൈവ് റഫറൽ
വേരിയന്റുകൾക്ക് സെർവർ മനഃപൂർവം ഒരേ നിർണായക `generatedAt` നൽകുന്നു. അതിനാൽ
അടിസ്ഥാന ലിങ്ക് സെറ്റ് മാറാതെതന്നെ, പിന്തുണക്കാരന്റെ കീ മാറിയതിന് ശേഷം ഒപ്പിട്ട
പേയ്ലോഡും ലഭ്യമാക്കുന്ന ടയറും മാറാം. ഇത് ഒരിക്കലും എക്സെപ്ഷൻ എറിയില്ല — എല്ലായ്പ്പോഴും
ഒരു സ്റ്റാറ്റസ് ഒബ്ജക്റ്റ് തിരികെ നൽകും; `reason`-ലെ പിശകുകളിൽ ഒരിക്കലും സ്റ്റാക്ക്
ട്രേസ് ഉണ്ടായിരിക്കില്ല.

രണ്ട് ട്രിഗറുകൾ റഫറൽ കാഷ് സജ്ജമായി നിലനിർത്തുന്നു. രണ്ടും കാറ്റലോഗിന്റെ സ്വന്തം
24h ഇടവേളയിൽനിന്ന് സ്വതന്ത്രമാണ്:

- **വായനയ്ക്കൊപ്പം സമന്വയം** — കാഷ് ഇല്ലാതിരിക്കുമ്പോഴോ
  `REFERRALS_STALE_MS`-നേക്കാൾ പഴക്കമുള്ളപ്പോഴോ (1h,
  `shouldSyncReferralsOnRead()`), പ്രതികരണം നൽകുന്നതിനുമുമ്പ്
  `GET /api/radar/referrals` തന്നെ ഇൻലൈനായി `syncRadarReferrals()` വിളിക്കുന്നു.
  പശ്ചാത്തല ടൈമറിനായി കാത്തിരിക്കാതെ, അടുത്ത ഡാഷ്ബോർഡ് ലോഡിൽ തന്നെ സ്ഥിര ലിങ്കുകൾ
  "എല്ലായ്പ്പോഴും കാലികമായി" ലഭ്യമാക്കുന്നത് ഇതാണ്.
- **ഷെഡ്യൂളറിലെ അനുബന്ധ സമന്വയം** — കാറ്റലോഗിന് ഉപയോഗിക്കുന്ന അതേ മണിക്കൂർ
  ടിക്കിൽ `radarSchedulerTick()` (`scheduler.ts`) റഫറലുകളുടെ പഴക്കം സ്വതന്ത്രമായി
  വിലയിരുത്തുകയും, ആവശ്യമുള്ളപ്പോൾ `syncRadarReferrals()` വിളിക്കുകയും ചെയ്യുന്നു.
  ആ ടിക്കിൽ കാറ്റലോഗ് സമന്വയിക്കേണ്ടതുണ്ടായിരുന്നോ എന്നതിനെ ആശ്രയിക്കാതെയാണ് ഇത്
  പ്രവർത്തിക്കുന്നത്. ഇത് ഒരിക്കലും `RadarTickResult`-ന്റെ ഘടനയെ ബാധിക്കില്ല
  (സാധ്യമാകുന്നത്ര മികച്ച രീതിയിലുള്ള അനുബന്ധ പ്രഭാവം മാത്രം; പിശകുണ്ടായാൽ അത്
  അവഗണിക്കും).

### ആക്സസർ

`src/lib/radar/index.ts` വായനയ്ക്ക് മാത്രമുള്ള രണ്ട് ആക്സസറുകൾ എക്സ്പോർട്ട് ചെയ്യുന്നു.
രണ്ടും ഒരിക്കലും എക്സെപ്ഷൻ എറിയില്ല (`getRadarCatalog()`-ന്റെ അതേ പ്രതിരോധാത്മക
കരാർ — ഫ്ലാഗ് ഓഫ്, കാഷ് ഇല്ലായ്മ, അല്ലെങ്കിൽ കേടായ കാഷ് ചെയ്ത പേയ്ലോഡ് എന്നിവയെല്ലാം
പിശകിന് പകരം ശൂന്യമായ ഘടനയിലേക്ക് പരിഹരിക്കപ്പെടും):

- `getRadarReferrals()` → `{ fixed: RadarReferral[], campaigns: RadarReferral[] }`,
  `radar_referrals_cache`-ൽനിന്ന് (`getRadarReferralsCache()` വഴി) വായിക്കുകയും
  `RadarReferralsFeedSchema` ഉപയോഗിച്ച് സാധൂകരിക്കുകയും ചെയ്യുന്നു — കാറ്റലോഗ്
  കാഷിൽനിന്നല്ല.
- `getDefaultReferralFor(provider)` → ആ ദാതാവിനുള്ള `isDefault: true` ആയ `fixed`
  റഫറൽ, അല്ലെങ്കിൽ `null`. ഇത് `fixed` മാത്രം പരിശോധിക്കുന്നു — ഒരു ക്യാമ്പെയ്ൻ
  ഒരിക്കലും ദാതാവിന്റെ "ഡിഫോൾട്ട്" ലിങ്കായി ഉപയോഗിക്കില്ല.

"ഒരു ദാതാവിന് ഏത് റഫറലാണ് ഡിഫോൾട്ട്" എന്ന യഥാർത്ഥ നിയമം
`findDefaultReferral()`-ലാണ് (`src/lib/radar/referrals.ts`) ഉള്ളത്. ഇത് **DB
ഇംപോർട്ട് ഇല്ലാത്ത** ഒരു ചെറിയ പ്യൂർ ഫങ്ഷനാണ് — ഒരു `"use client"` ഘടകത്തിലേക്ക്
ഇത് സുരക്ഷിതമായി ഇംപോർട്ട് ചെയ്യാം. `getRadarReferrals`/
`getDefaultReferralFor` (`index.ts`-ൽ) `@/lib/db/radar` ഉൾപ്പെടുത്തുന്നതിനാൽ
സെർവറിൽ മാത്രം നിലനിൽക്കും; ബ്രൗസർ ബണ്ടിലിൽ `better-sqlite3` ഉൾപ്പെടുന്നത്
ഒഴിവാക്കാൻ പ്രൊവൈഡർമാരുടെ ഡാഷ്ബോർഡ് `index.ts`-ന് പകരം `referrals.ts` നേരിട്ട്
ഇംപോർട്ട് ചെയ്യുന്നു (താഴെ കാണുക).

### `GET /api/radar/referrals`

മറ്റെല്ലാ Radar റൂട്ടുകളിലുമുള്ള അതേ ഗേറ്റ് ക്രമം കൃത്യമായി പിന്തുടരുന്നു: `RADAR_ENABLED` ഓഫ് →
`404` (ആദ്യം പരിശോധിക്കുന്നു, ബൈറ്റ്-സമാനമായ നിഷ്ക്രിയത്വം); പ്രാമാണീകരിക്കാത്തത് → `401`; അല്ലാത്തപക്ഷം
കാലഹരണപ്പെട്ടിരിക്കുമ്പോൾ sync-on-read ട്രിഗർ ചെയ്യുന്നു (മുകളിൽ കാണുക), തുടർന്ന്
`{ fixed, campaigns, tier }` സഹിതം `200` — `tier` നേരിട്ട് (ഒരുപക്ഷേ ഇപ്പോൾ മാത്രം പുതുക്കിയ)
കാഷ് റോയിൽനിന്ന് വരുന്നതും പൂർണ്ണമായും വിവരദായകവുമാണ് (താഴെയുള്ള UI-യുടെ മൃദുവായ അപ്സെൽ
സന്ദേശത്തെ നിയന്ത്രിക്കുന്നു). ഫീഡ് സെർവറിനെ ഒരിക്കലും നേരിട്ട് പ്രോക്സി ചെയ്യുന്നില്ല — റൂട്ടിന്റെ
സ്വന്തം സോഴ്സിൽ `fetch(` കോൾ ഇല്ല; നെറ്റ്വർക്ക് ഉപയോഗം എല്ലായ്പ്പോഴും
`syncRadarReferrals()`-ന്റെ ഉള്ളിൽ മാത്രമാണ് സംഭവിക്കുന്നത്, `/api/radar/catalog`-ലേതുപോലെ
പ്രാദേശിക-കാഷ്-മാത്രം എന്ന അതേ തത്ത്വം.

പുതിയ റൂട്ടിന് പകരം നിലവിലുള്ള Radar പേജ്
(`src/app/(dashboard)/dashboard/radar/page.tsx`) രണ്ടാമത്തെ ടാബായി വീണ്ടും ഉപയോഗിക്കുന്നു —
പേജ് ഇതിനകം ലഭ്യമാക്കുന്ന ഡാറ്റയുടെ ഒരു വകഭേദം മാത്രമായ ഫീച്ചറിന് കുറഞ്ഞ routing/i18n
ഉപരിതലം. ഓപ്റ്റ് ഇൻ ചെയ്തുകഴിഞ്ഞാൽ, ടാബ് ബാർ **കാറ്റലോഗ്** (നിലവിലുള്ള പട്ടിക), **സൗജന്യ
ക്രെഡിറ്റുകൾ** എന്നിവ നൽകുന്നു:

- സ്ഥിരം ലിങ്കുകൾ പ്രൊവൈഡർ അനുസരിച്ച് ഗ്രൂപ്പ് ചെയ്യുന്നു; ഓരോന്നിലും `requiredAction`
  (ഉണ്ടെങ്കിൽ), കൂടാതെ റെഫറൽ URL-ലേക്ക് നയിക്കുന്ന
  `target="_blank" rel="noopener noreferrer"` ബട്ടണും കാണിക്കുന്നു.
- ക്യാമ്പെയ്നുകളിൽ ഇവയ്ക്കൊപ്പം `validUntil` ഉണ്ടെങ്കിൽ അതും കാണിക്കുന്നു.
- `campaigns` ശൂന്യവും നൽകിയ ടയർ `community`-യുമാകുമ്പോൾ, UI ഒരു ചെറിയ അപ്സെൽ
  കുറിപ്പ് ("പരിമിതകാല ക്യാമ്പെയ്നുകൾ സപ്പോർട്ടർമാർക്കുള്ള അധിക ആനുകൂല്യമാണ്") കാണിക്കുന്നു —
  ഇത് സ്ഥിരം ലിങ്കുകളുടെ പട്ടികയെ **ഒരിക്കലും** മറയ്ക്കുകയോ നിയന്ത്രിക്കുകയോ ചെയ്യുന്നില്ല;
  എല്ലാ ടയറുകളിലും അത് പൂർണ്ണമായി ലഭ്യമാണ്. അപ്സെൽ ഒരു മൃദുവായ സന്ദേശം മാത്രമാണ്,
  ഒരിക്കലും ഒരു തടസ്സമല്ല.

### പ്രൊവൈഡർ പേരിലെ റെഫറൽ ലിങ്ക് (പ്രൊവൈഡർ ഡാഷ്ബോർഡ്)

`ProviderPageHeader` (`src/app/(dashboard)/dashboard/providers/[id]/components/`)
ഇതിനകം തന്നെ പ്രൊവൈഡറുടെ പേര് `providerInfo.website` ലഭ്യമാകുമ്പോൾ അതിലേക്ക് ലിങ്ക്
ചെയ്തിരുന്നു; ധനസമ്പാദന ലിങ്കിന് ഒരു മുൻമാതൃകയുമുണ്ട്: Kimi (Moonshot AI) പങ്കാളി-ലിങ്ക്
കുറിപ്പ് (`providers.kimiPartnerLinkNote` i18n കീ). പുതിയൊരു കീ അവതരിപ്പിക്കുന്നതിന്
പകരം Radar-ന്റെ ഡിഫോൾട്ട് റെഫറലുകൾക്കായി D28 അതേ സൂക്ഷ്മമായ കുറിപ്പ് പാറ്റേൺ തന്നെ
വീണ്ടും ഉപയോഗിക്കുന്നു.

രൂപകൽപ്പനാപരമായി ശിഥിലമായ കപ്പ്ലിംഗ്:

- `resolveProviderHeaderLink()` (`src/app/(dashboard)/dashboard/providers/providerPageUtils.ts`)
  ഒരു **പ്യൂർ** ഫങ്ഷനാണ് — `(staticWebsite, referralUrl) => { website, isReferralLink }`
  — ഇതിന് `@/lib/radar`-ലോ `@/lib/db/*`-ലോ യാതൊരു ആശ്രിതത്വവുമില്ല.
  `providerPageUtils.ts` മുഴുവനായും ആ ഇംപോർട്ടുകളിൽനിന്ന് സ്വതന്ത്രമായി തുടരുന്നു
  (`tests/unit/provider-header-referral-link.test.ts` ഇത് ഉറപ്പാക്കുന്നു).
- `ProviderDetailPageClient.tsx` (ഒരു `"use client"` കംപോണന്റ്) മാത്രമാണ് Radar ഡാറ്റ
  ഫെച്ച് ചെയ്യാൻ അനുവദിച്ചിരിക്കുന്ന സ്ഥലം — Radar ഡാഷ്ബോർഡ് പേജ് തന്നെ ഉപയോഗിക്കുന്ന അതേ
  ലോക്കൽ-റൂട്ട് പാറ്റേണായ `fetch("/api/radar/referrals")` വഴി — കൂടാതെ DB-യിൽനിന്ന്
  സ്വതന്ത്രമായ `src/lib/radar/referrals.ts`-ലെ `findDefaultReferral()` ഉപയോഗിച്ച്
  ക്ലയന്റ് ഭാഗത്ത് ഡിഫോൾട്ട് റെഫറൽ കണക്കാക്കുന്നു.
- `RADAR_ENABLED` ഓഫ് ആയിരിക്കുമ്പോൾ, ഫെച്ച് `404` നൽകുന്നു, `referralUrl` `null` ആയി
  തുടരുന്നു, കൂടാതെ `resolveProviderHeaderLink()` സ്റ്റാറ്റിക് കാറ്റലോഗ് `website`
  മാറ്റമില്ലാതെ മടക്കുന്നു — ഈ ഫീച്ചർ നിലവിൽ വരുന്നതിന് മുമ്പുള്ള പ്രൊവൈഡർ പേജുമായി അത്
  ബൈറ്റ്-സമാനമായിരിക്കും. ഇതുവരെ കാഷ് ഇല്ലാത്തപ്പോഴും ആ പ്രത്യേക പ്രൊവൈഡറിന് ഡിഫോൾട്ട്
  റെഫറൽ ഇല്ലാത്തപ്പോഴും ഇതേ ഫലമാണ്.
- ഒരു ഡിഫോൾട്ട് റെഫറൽ ബാധകമാകുമ്പോൾ, `ProviderPageHeader`-ന് `isReferralLink`
  ലഭിക്കുകയും Kimi പങ്കാളി ലിങ്കിലേതുപോലെ അതേ സൂക്ഷ്മമായ കുറിപ്പ്/ടൂൾടിപ്പ് കാണിക്കുകയും
  ചെയ്യുന്നു (`providers.kimiPartnerLinkNote` കീ വീണ്ടും ഉപയോഗിക്കുന്നു) — ഒരിക്കലും
  പുതിയതും വേറിട്ടതുമായ ദൃശ്യ അവതരണം ഉപയോഗിക്കുന്നില്ല.

## ഒരു ഫീഡ് സ്വയം ഹോസ്റ്റ് ചെയ്യുന്നതെങ്ങനെ

കാറ്റലോഗിന്മേൽ പൂർണ്ണ നിയന്ത്രണം ആഗ്രഹിക്കുന്ന ഒരു fork-നോ self-hoster-നോ client code-ൽ മാറ്റം വരുത്താതെ സ്വന്തം feed
service പ്രവർത്തിപ്പിക്കാം:

1. `RadarFeedSchema` (`src/lib/radar/feedSchema.ts`) പാലിക്കുന്ന JSON body തിരികെ നൽകുന്ന ഒരു
   `GET /v1/catalog/latest` endpoint ലഭ്യമാക്കുക — top-level `feed:
"omniroute-radar"`, `schemaVersion: 2`, `version`, `tier`, `providers`, `models`,
   `quirks`, `totals` എന്നിവ ഉൾപ്പെടണം. `x-omniroute-radar-schema: 2` മാനിക്കുക; transition-compatible ആയ ഒരു server,
   അതില്ലാത്ത requests-നെ പ്രത്യേകം sign ചെയ്ത v1 artifact-ലേക്ക് default ചെയ്യണം.
2. കൃത്യമായ response bytes ഒരു Ed25519 key pair ഉപയോഗിച്ച് sign ചെയ്ത്, base64
   signature `x-omniroute-feed-signature` response header-ൽ തിരികെ നൽകുക.
3. `RADAR_FEED_URL` പുതിയ base URL ആയും `RADAR_FEED_PUBKEY` അതിനോട് പൊരുത്തപ്പെടുന്ന
   public key (base64-DER SPKI അല്ലെങ്കിൽ PEM) ആയും സജ്ജീകരിക്കുക —
   [env var reference](../reference/ENVIRONMENT.md#27-radar-feed-self-hosting) കാണുക.
4. `RADAR_ENABLED` പ്രവർത്തനക്ഷമമാക്കി `POST /api/radar/settings`
   (`{ optIn: true }`) വഴി opt in ചെയ്യുക.

മറ്റ് code മാറ്റങ്ങളൊന്നും ആവശ്യമില്ല — `verifyFeedBytes()` override സ്വയമേവ
ഉപയോഗിക്കും (`src/lib/radar/pinnedKeys.ts`-ലെ `getFeedPublicKeys()`), കൂടാതെ version
താരതമ്യം, schema validation, merge rules എന്നിവ self-hosted
feed-നും ഒരേപോലെ ബാധകമാണ്.

Referral links (മുകളിലുള്ള [Referral links (free credits)](#referral-links-free-credits)
കാണുക) വേറിട്ടതും ഐച്ഛികവുമായ ഒരു artifact ആണ്: `/v1/catalog/latest` മാത്രം നൽകുന്ന ഒരു fork-ഉം
പൂർണ്ണമായി പ്രവർത്തിക്കും — `/v1/referrals/latest`-ൽ നിന്നുള്ള `404` ലഭിക്കുമ്പോൾ `syncRadarReferrals()`
`{ status: "error" }` എന്ന നിലയിലേക്ക് താഴുകയും cache ശൂന്യമായി തുടരുകയും ചെയ്യും, അതിനാൽ
page-ന്റെ ബാക്കി ഭാഗം പരാജയപ്പെടുത്തുന്നതിനുപകരം `GET /api/radar/referrals`
`{ fixed: [], campaigns: [], tier: null }` തുടർന്നും തിരികെ നൽകും. Referral links കൂടി നൽകാൻ,
`RadarReferralsFeedSchema` (`src/lib/radar/referralsFeedSchema.ts`) പാലിക്കുന്ന
`GET /v1/referrals/latest` ലഭ്യമാക്കി, catalog feed-ിന് ഉപയോഗിച്ച അതേ Ed25519 key pair ഉപയോഗിച്ച്
അത് sign ചെയ്യുക.

Supporter offers മറ്റൊരു ഐച്ഛിക artifact ആണ്. അവ നൽകാൻ, closed
`RadarOffersFeedSchema` (`src/lib/radar/offersFeedSchema.ts`) ഉപയോഗിച്ച്
`GET /v1/offers/latest` നടപ്പിലാക്കുക, live entitlement നിർബന്ധമാക്കുക,
`x-omniroute-feed-tier: live` തിരികെ നൽകുക, കൂടാതെ കൃത്യമായ bytes അതേ key ഉപയോഗിച്ച് sign ചെയ്യുക. ഈ
endpoint ഒഴിവാക്കുന്ന ഒരു fork-ൽ catalog/referrals പെരുമാറ്റം മാറ്റമില്ലാതെ തുടരും; offer refresh വിനാശകരമല്ലാത്ത വിധത്തിൽ പരാജയപ്പെടുകയും
അവസാനം verify ചെയ്ത local offer cache തുടർന്നും ലഭ്യമായിരിക്കുകയും ചെയ്യും.

Intel-ഉം ഇതേ രീതിയിൽ ഐച്ഛികമാണ്. ഒരു self-hoster-ന്
`RadarIntelFeedSchema` (`src/lib/radar/intelFeedSchema.ts`) ഉപയോഗിച്ച് `GET /v1/intel/latest` ലഭ്യമാക്കാം,
live entitlement നിർബന്ധമാക്കാം, `x-omniroute-feed-tier: live` തിരികെ നൽകാം, കൂടാതെ കൃത്യമായ bytes പങ്കിട്ട Ed25519 key ഉപയോഗിച്ച് sign ചെയ്യാം.
ഈ endpoint ഒഴിവാക്കുന്നത് catalog, referrals, offers എന്നിവയിൽ മാറ്റമുണ്ടാക്കില്ല; Intel refresh അവസാനം verify ചെയ്ത ഏതെങ്കിലും
local snapshot സംരക്ഷിക്കും.
