> **ആധികാരിക ഉറവിടം:** `src/lib/evals/`, `src/lib/db/evals.ts`, `src/app/api/evals/`
> **അവസാനം പുതുക്കിയത്:** 2026-06-28 — v3.8.40

റൂട്ടിംഗ് കോൺഫിഗറേഷനുകൾ, ഒറ്റപ്പെട്ട പ്രൊവൈഡർമാർ/മോഡലുകൾ, അല്ലെങ്കിൽ ഉൾപ്പെടുത്തിയിരിക്കുന്ന "ഗോൾഡൻ സെറ്റ്" സ്യൂട്ടുകൾ എന്നിവ ബെഞ്ച്മാർക്ക് ചെയ്യാൻ ഉപയോഗിക്കാവുന്ന ഒരു പൊതുവായ മൂല്യനിർണ്ണയ ഫ്രെയിംവർക്ക് OmniRoute-ൽ ഉൾപ്പെടുന്നു.
റൂട്ടിംഗ് മാറ്റങ്ങൾ പരിശോധിക്കാനും പുതിയ പ്രൊവൈഡർമാരെ സാധൂകരിക്കാനും പ്രൊഡക്ഷൻ ട്രാഫിക്കിലേക്ക് അവയെ പ്രമോട്ട് ചെയ്യുന്നതിന് മുമ്പ് റിലീസുകൾക്ക് നിയന്ത്രണങ്ങൾ ഏർപ്പെടുത്താനും ഇത് ഉപയോഗിക്കുക.

ഫ്രെയിംവർക്ക് ഇനിപ്പറയുന്ന രീതിയിലാണ് നടപ്പിലാക്കിയിരിക്കുന്നത്:

- ഇൻ-മെമ്മറി ബിൽറ്റ്-ഇൻ സ്യൂട്ടുകൾ രജിസ്റ്റർ ചെയ്യുകയും പ്രതീക്ഷിക്കുന്ന മാനദണ്ഡങ്ങളുമായി ഔട്ട്പുട്ടുകൾ താരതമ്യം ചെയ്ത് മൂല്യനിർണ്ണയം നടത്തുകയും സ്കോർകാർഡുകൾ ഏകീകരിക്കുകയും ചെയ്യുന്ന ഒരു പ്യൂർ റണ്ണർ (`src/lib/evals/evalRunner.ts`).
- ഇഷ്ടാനുസൃതമായ (ഉപയോക്താവ് നിർവചിച്ച) സ്യൂട്ടുകൾക്കും മുമ്പത്തെ റണ്ണുകൾക്കും വേണ്ടി SQLite ഉപയോഗിക്കുന്ന ഒരു പെർസിസ്റ്റൻസ് ലെയർ (`src/lib/db/evals.ts`).
- `POST /v1/chat/completions` എന്നതിലേക്ക് യഥാർഥ കോളുകൾ അയച്ച് ഓരോ കേസും എക്സിക്യൂട്ട് ചെയ്യുകയും ലേറ്റൻസിയും ഔട്ട്പുട്ടുകളും ക്യാപ്ചർ ചെയ്യുകയും റൺ പെർസിസ്റ്റ് ചെയ്യുകയും ചെയ്യുന്ന ഒരു ഓർക്കസ്ട്രേഷൻ ലെയർ (`src/lib/evals/runtime.ts`).
- `/api/evals/*`-ന് കീഴിലുള്ള REST എൻഡ്പോയിന്റുകൾ (മാനേജ്മെന്റ് ഓതന്റിക്കേഷൻ ഉള്ളവർക്ക് മാത്രം).
- `Dashboard → Usage → Evals`-ൽ ലഭ്യമായ ഒരു ഡാഷ്ബോർഡ് ഇന്റർഫേസ് (`EvalsTab.tsx`).

## ആശയങ്ങൾ

### സ്യൂട്ട്

ഒരു `description`-ഉം ഒന്നോ അതിലധികമോ കേസുകളും ഉൾക്കൊള്ളുന്ന, പേരുനൽകിയ ടെസ്റ്റ് കേസുകളുടെ ശേഖരമാണ് സ്യൂട്ട്. സ്യൂട്ടുകൾ രണ്ട് ഉറവിടങ്ങളിൽനിന്നാണ് ലഭിക്കുന്നത്:

| ഉറവിടം     | നിർവചിച്ചിരിക്കുന്ന സ്ഥലം                                   | റൺടൈമിൽ മാറ്റാനാകുമോ?    |
| ---------- | ----------------------------------------------------------- | ------------------------ |
| `built-in` | ബൂട്ട് സമയത്ത് `registerSuite()` വഴി രജിസ്റ്റർ ചെയ്തത്      | ഇല്ല (കോഡിൽ നിർവചിച്ചത്) |
| `custom`   | SQLite-ലെ `eval_suites` + `eval_cases` എന്നിവയിൽ സംഭരിച്ചത് | ഉണ്ട് (API/UI വഴി)       |

നിലവിലെ ബിൽറ്റ്-ഇൻ സ്യൂട്ടുകൾ (`src/lib/evals/evalRunner.ts` കാണുക):

- `golden-set` — അഭിവാദ്യം/ഗണിതം/വിവർത്തനം/സുരക്ഷ എന്നിവയിലായി 10 അടിസ്ഥാന കേസുകൾ
- `coding-proficiency` — Python/JS/SQL/TS/ബഗ് കണ്ടെത്തൽ
- `reasoning-logic` — ന്യായവാക്യങ്ങൾ, വാചിക പ്രശ്നങ്ങൾ, പാറ്റേൺ തിരിച്ചറിയൽ
- `multilingual` — വിവർത്തനവും ഭാഷ തിരിച്ചറിയലും
- `safety-guardrails` — PII, ജയിൽബ്രേക്ക്, നിരസിക്കൽ, പക്ഷപാതത്തെക്കുറിച്ചുള്ള അവബോധം
- `instruction-following` — JSON മാത്രം, അക്കമിട്ട ലിസ്റ്റുകൾ, ഭാഷാ നിയന്ത്രണങ്ങൾ
- `codex-comparison` — താരതമ്യ മോഡിനായി ഉദ്ദേശിച്ചിട്ടുള്ള നേരിട്ടുള്ള കോഡിംഗ് ടാസ്കുകൾ

### കേസ്

ഓരോ കേസിലും ഇനിപ്പറയുന്നവ ഉൾപ്പെടുന്നു:

| ഫീൽഡ്      | വിവരണം                                                                          |
| ---------- | ------------------------------------------------------------------------------- |
| `id`       | സ്ഥിരമായ ഐഡന്റിഫയർ (ഔട്ട്പുട്ടുകൾക്കും മെട്രിക്കുകൾക്കും കീ ആയി ഉപയോഗിക്കുന്നു) |
| `name`     | മനുഷ്യർക്ക് വായിച്ചറിയാവുന്ന ലേബൽ                                               |
| `model`    | റൺ `suite-default` ടാർഗറ്റിങ് ഉപയോഗിക്കുമ്പോഴുള്ള ഡിഫോൾട്ട് മോഡൽ                |
| `input`    | `{ messages, max_tokens? }` — `/v1/chat/completions`-ലേക്ക് അയയ്ക്കുന്നു        |
| `expected` | `{ strategy, value }` — സ്കോറിങ് മാനദണ്ഡം (താഴെ കാണുക)                          |
| `tags`     | ഓപ്ഷണൽ ലേബലുകൾ (ഉദാ. `safety`, `pii`, `jailbreak`)                              |

### ടാർഗറ്റ്

ഒരേ സ്യൂട്ട് വ്യത്യസ്ത ടാർഗറ്റുകൾക്കെതിരെ പ്രവർത്തിപ്പിക്കാം. ടാർഗറ്റ് സ്കീമ എന്നത്
`src/shared/validation/schemas.ts`-ലെ `evalTargetSchema` ആണ്:

| ടാർഗറ്റ് തരം    | `id`           | പ്രവർത്തനം                                                                        |
| --------------- | -------------- | --------------------------------------------------------------------------------- |
| `suite-default` | `null`         | ഓരോ കേസും അതിന്റെ ബിൽറ്റ്-ഇൻ `model` ഫീൽഡ് ഉപയോഗിക്കുന്നു                         |
| `model`         | മോഡലിന്റെ പേര് | ഓരോ കേസും ഒരു ഡയറക്ട് മോഡലിലൂടെ നിർബന്ധമായി പ്രവർത്തിപ്പിക്കുന്നു (ഉദാ. `gpt-4o`) |
| `combo`         | കോംബോയുടെ പേര് | ഓരോ കേസും ഒരു കോംബോയിലൂടെ പ്രവർത്തിപ്പിക്കുന്നു (റൂട്ടിംഗ് എൻജിൻ പരീക്ഷിക്കുന്നു) |

`model`, `combo` എന്നിവയ്ക്ക് `id` ഫീൽഡ് നിർബന്ധമാണ് (`superRefine` ഉപയോഗിച്ച് Zod ഇത് ഉറപ്പാക്കുന്നു). `compareTarget` നൽകിയിരിക്കുമ്പോൾ, രണ്ട് ടാർഗറ്റുകളും വ്യത്യസ്തമായിരിക്കണം —
A/B താരതമ്യത്തിനായി റണ്ണർ രണ്ട് റണ്ണുകളും ഒരേ `runGroupId`-ന് കീഴിൽ പെർസിസ്റ്റ് ചെയ്യുന്നു.

## സ്കോറിംഗ് മാനദണ്ഡങ്ങൾ

`evaluateCase()`-ൽ (evalRunner.ts) നടപ്പിലാക്കിയിരിക്കുന്നത്:

| സ്ട്രാറ്റജി | വിജയിക്കുന്ന സാഹചര്യം…                                                       |
| ----------- | ---------------------------------------------------------------------------- |
| `exact`     | `actualOutput === expected.value`                                            |
| `contains`  | `actualOutput.toLowerCase().includes(expected.value.toLowerCase())`          |
| `regex`     | `new RegExp(expected.value).test(actualOutput)` truthy ആകുമ്പോൾ              |
| `custom`    | `expected.fn(actualOutput, evalCase)` truthy മടക്കുമ്പോൾ (ബിൽറ്റ്-ഇൻ മാത്രം) |

**കുറിപ്പ്:** ഫങ്ഷനുകൾ API വഴി സീരിയലൈസ് ചെയ്യാൻ കഴിയാത്തതിനാൽ, കസ്റ്റം-ഫങ്ഷൻ
സ്കോറിംഗ് കോഡിൽ നിർവചിച്ച (ബിൽറ്റ്-ഇൻ) സ്യൂട്ടുകൾക്കായി മാത്രമായി നീക്കിവെച്ചിരിക്കുന്നു.
ഉപയോക്താവ് സൃഷ്ടിക്കുന്ന സ്യൂട്ടുകൾക്കായി `evalCaseBuilderSchema`
`contains | exact | regex` മാത്രമേ സ്വീകരിക്കൂ.

നിലവിൽ LLM-as-judge അല്ലെങ്കിൽ എംബെഡ്ഡിംഗ് അധിഷ്ഠിതമായ സാമ്യതാ സ്കോറർ ഇല്ല —
`evaluateCase()`-ലെ വ്യക്തമായ ഒരു വിപുലീകരണ ബിന്ദുവായിരിക്കും അത്.

## ഡാറ്റാബേസ് സ്കീമ

മൂന്ന് പട്ടികകൾ (`030_create_eval_runs.sql`,
`031_create_eval_suites.sql` എന്നീ മൈഗ്രേഷനുകൾ):

| പട്ടിക        | ഉദ്ദേശ്യം                                                                                                                        |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `eval_suites` | കസ്റ്റം സ്യൂട്ട് മെറ്റാഡാറ്റ (`id`, `name`, `description`)                                                                       |
| `eval_cases`  | ഓരോ സ്യൂട്ടിലെയും കേസുകൾ — `input_json`, `expected_*`, `tags_json`                                                               |
| `eval_runs`   | ചരിത്രപരമായ റണ്ണുകൾ — `pass_rate`, `total`, `passed`, `failed`, `avg_latency_ms`, `summary_json`, `results_json`, `outputs_json` |

ബിൽറ്റ്-ഇൻ സ്യൂട്ടുകൾ DB-യിൽ സംഭരിക്കപ്പെടുന്നില്ല. അവ മെമ്മറിയിലാണ് നിലനിൽക്കുന്നത്,
`evalRunner.ts` ഇംപോർട്ട് ചെയ്യുമ്പോഴെല്ലാം വീണ്ടും രജിസ്റ്റർ ചെയ്യപ്പെടുകയും ചെയ്യുന്നു.

## REST API

എല്ലാ എൻഡ്പോയിന്റുകൾക്കും മാനേജ്മെന്റ് ഓത്ത് (`requireManagementAuth`) ആവശ്യമാണ് —
അവ പൊതു പ്രോക്സി സർഫേസിന്റെ ഭാഗമല്ല.

| എൻഡ്പോയിന്റ്                  | രീതി     | വിവരണം                                                                                    |
| ----------------------------- | -------- | ----------------------------------------------------------------------------------------- |
| `/api/evals`                  | `GET`    | സ്യൂട്ടുകൾ + സമീപകാല റണ്ണുകൾ + സ്കോർകാർഡ് + ടാർഗെറ്റുകൾ + കീകൾ എന്നിവ ലിസ്റ്റ് ചെയ്യുക    |
| `/api/evals`                  | `POST`   | ഒരു സ്യൂട്ട് പ്രവർത്തിപ്പിക്കുക (ഒറ്റയ്ക്കോ താരതമ്യത്തിനായോ) — സ്കീമ `evalRunSuiteSchema` |
| `/api/evals/{suiteId}`        | `GET`    | ഒരു സ്യൂട്ട് ലഭ്യമാക്കുക (ബിൽറ്റ്-ഇൻ അല്ലെങ്കിൽ കസ്റ്റം)                                  |
| `/api/evals/suites`           | `POST`   | ഒരു കസ്റ്റം സ്യൂട്ട് സൃഷ്ടിക്കുക — സ്കീമ `evalSuiteSaveSchema`                            |
| `/api/evals/suites/{suiteId}` | `GET`    | ഒരു കസ്റ്റം സ്യൂട്ട് ലഭ്യമാക്കുക                                                          |
| `/api/evals/suites/{suiteId}` | `PUT`    | ഒരു കസ്റ്റം സ്യൂട്ട് മാറ്റിസ്ഥാപിക്കുക (കേസുകൾ വീണ്ടും ഇൻസേർട്ട് ചെയ്യപ്പെടും)            |
| `/api/evals/suites/{suiteId}` | `DELETE` | ഒരു കസ്റ്റം സ്യൂട്ടും അതിലെ കേസുകളും ഇല്ലാതാക്കുക                                         |

### ഒരു സ്യൂട്ട് പ്രവർത്തിപ്പിക്കൽ

```bash
curl -X POST http://localhost:20128/api/evals \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "suiteId": "golden-set",
    "target": { "type": "combo", "id": "my-combo" },
    "apiKeyId": "optional-api-key-uuid"
  }'
```

ഐച്ഛിക ഫീൽഡുകൾ:

- `outputs` — മുൻകൂട്ടി കണക്കാക്കിയ ഔട്ട്പുട്ടുകളുടെ `Record<caseId, string>`.
  ഇത് നൽകിയാൽ, റണ്ണർ **ഡിസ്പാച്ച് ഒഴിവാക്കുകയും** കാഷ് ചെയ്ത ഔട്ട്പുട്ടുകൾ മാത്രം
  സ്കോർ ചെയ്യുകയും ചെയ്യും (ഓഫ്ലൈൻ മൂല്യനിർണ്ണയത്തിന് ഉപയോഗപ്രദം).
- `compareTarget` — സമാന്തരമായി പ്രവർത്തിപ്പിക്കേണ്ട രണ്ടാമത്തെ ടാർഗെറ്റ്; നേർക്കുനേർ
  കാണുന്നതിനായി രണ്ട് റണ്ണുകളും ജനറേറ്റ് ചെയ്ത ഒരു `runGroupId` പങ്കിടുന്നു.
- `apiKeyId` — ഡിസ്പാച്ച് ചെയ്യുന്ന `/v1/chat/completions` കോളുകൾ
  ഓതന്റിക്കേറ്റ് ചെയ്യാൻ ഉപയോഗിക്കുന്ന ആന്തരിക API കീ. `REQUIRE_API_KEY`
  പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ ഇത് ആവശ്യമാണ്.

### ഒരു കസ്റ്റം സ്യൂട്ട് സൃഷ്ടിക്കൽ

```bash
curl -X POST http://localhost:20128/api/evals/suites \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Production smoke",
    "description": "Quick sanity check before deploy",
    "cases": [
      {
        "name": "JSON shape",
        "model": "gpt-4o",
        "input": { "messages": [{ "role": "user", "content": "Reply with {\"ok\": true}" }] },
        "expected": { "strategy": "regex", "value": "\"ok\"\\s*:\\s*true" }
      }
    ]
  }'
```

## ഡിസ്പാച്ച് പൈപ്പ്ലൈൻ

`runEvalSuiteAgainstTarget()` (`src/lib/evals/runtime.ts`):

1. സ്യൂട്ട് പരിഹരിക്കുന്നു (ബിൽറ്റ്-ഇൻ അല്ലെങ്കിൽ കസ്റ്റം).
2. ഓരോ കേസിനും, കേസിന്റെ `messages`, പരിഹരിച്ച `model`, `stream: false`, `max_tokens: 512` എന്നിവ ഉപയോഗിച്ച് `/v1/chat/completions`-ലേക്കുള്ള ഒരു `Request` നിർമ്മിക്കുന്നു (അല്ലെങ്കിൽ കേസിലെ ഓവർറൈഡ് ഉപയോഗിക്കുന്നു).
3. ചാറ്റ് ഹാൻഡ്ലറെ നേരിട്ട് വിളിക്കുന്നു (ഇൻ-പ്രോസസ് — അധിക HTTP ഹോപ്പ് ഇല്ല).
4. ലേറ്റൻസി രേഖപ്പെടുത്തുകയും `choices[0].message.content`-ൽ നിന്നോ Responses-API `output[]` പേലോഡിൽ നിന്നോ ടെക്സ്റ്റ് എക്സ്ട്രാക്റ്റ് ചെയ്യുകയും ചെയ്യുന്നു.
5. `runSuite()` വഴി എല്ലാ ഔട്ട്പുട്ടുകൾക്കും സ്കോർ നൽകുന്നു, തുടർന്ന് `saveEvalRun()` വഴി അവ നിലനിർത്തുന്നു.

കേസുകൾ **ക്രമാനുഗതമായി** പ്രവർത്തിക്കുന്നു. നിലവിൽ കൺകറൻസി ഫ്ലാഗ് ഇല്ല.

## ഡാഷ്ബോർഡ്

UI സ്ഥിതിചെയ്യുന്നത് `Dashboard → Usage → Evals`
(`src/app/(dashboard)/dashboard/usage/components/EvalsTab.tsx`)-ലാണ്. അവിടെ നിന്ന് നിങ്ങൾക്ക്:

- ഓരോ കേസിന്റെയും പ്രിവ്യൂ സഹിതം ബിൽറ്റ്-ഇൻ, കസ്റ്റം സ്യൂട്ടുകൾ ബ്രൗസ് ചെയ്യാം.
- കേസ് ബിൽഡർ ഉപയോഗിച്ച് കസ്റ്റം സ്യൂട്ടുകൾ സൃഷ്ടിക്കാനും എഡിറ്റ് ചെയ്യാനും ഇല്ലാതാക്കാനും കഴിയും.
- ഒരു ടാർഗറ്റ് (സ്യൂട്ട് ഡിഫോൾട്ടുകൾ / മോഡൽ / കോമ്പോ), ഐച്ഛികമായി രണ്ടാമത്തെ `compareTarget`, ഐച്ഛികമായി ഒരു API കീ എന്നിവ തിരഞ്ഞെടുത്ത് ആവശ്യാനുസരണം പ്രവർത്തിപ്പിക്കാം.
- റൺ ചരിത്രം, ഓരോ കേസിന്റെയും പാസ്/ഫെയിൽ നില, ലേറ്റൻസി, രേഖപ്പെടുത്തിയ ഔട്ട്പുട്ടുകൾ എന്നിവ പരിശോധിക്കാം.
- ഓരോ `(suite, target)` സ്കോപ്പിലെയും ഏറ്റവും പുതിയ റണ്ണുകളിലുടനീളം സമാഹരിച്ച റോളിംഗ് സ്കോർകാർഡ് കാണാം.

## ഓട്ടോ-അസസ്മെന്റ് RFC-യുമായുള്ള ബന്ധം

വേറിട്ടതും കൂടുതൽ പരിമിതവുമായ ഒരു അസസ്മെന്റ് സബ്സിസ്റ്റം `src/domain/assessment/`-ൽ സ്ഥിതിചെയ്യുന്നു
(തത്സമയ സ്കോറിംഗ് എഞ്ചിനായി [AUTO-COMBO.md](../routing/AUTO-COMBO.md)-യും കാണുക).
ആ സബ്സിസ്റ്റം Auto Combo എഞ്ചിനെയാണ് ലക്ഷ്യമിടുന്നത് — അപ്സ്ട്രീമുകൾ പരാജയപ്പെടുമ്പോൾ കോമ്പോകൾക്ക് സ്വയം പുനഃസ്ഥാപിക്കാനാകുന്ന വിധത്തിൽ പ്രൊവൈഡർമാർക്കും മോഡലുകൾക്കും സ്വയമേവ സ്കോർ നൽകുന്നു. അത് സ്വന്തം റണ്ണർ, സ്വന്തം കാറ്റഗറൈസർ, സ്വന്തം സ്കോറിംഗ് ലോജിക് എന്നിവ ഉപയോഗിക്കുന്നു.

ഇവിടെ രേഖപ്പെടുത്തിയിരിക്കുന്ന Evals ഫ്രെയിംവർക്ക് **കൂടുതൽ വിശാലവും പൊതുവായ ആവശ്യങ്ങൾക്കുള്ളതുമായ ടെസ്റ്റിംഗ് ഉപരിതലമാണ്**. ഏത് തരത്തിലുള്ള റിഗ്രഷൻ സ്യൂട്ടുകൾക്കും, A/B താരതമ്യങ്ങൾക്കും, ഓരോ റിലീസിലെയും സ്മോക്ക് ടെസ്റ്റുകൾക്കും ഇതിന് മുൻഗണന നൽകുക. റൂട്ടിംഗ് തീരുമാനങ്ങളെ സ്വാധീനിക്കാൻ തത്സമയ പ്രൊവൈഡർ ആരോഗ്യനില ആവശ്യമായി വരുമ്പോൾ Auto-Assessment സബ്സിസ്റ്റം ഉപയോഗിക്കുക.

## CI ഇന്റഗ്രേഷൻ

നിലവിൽ പ്രത്യേക `eval:ci` npm സ്ക്രിപ്റ്റ് ഇല്ല. ഇവാൽ ഫലങ്ങളെ അടിസ്ഥാനമാക്കി റിലീസുകൾ ഗേറ്റ് ചെയ്യണമെങ്കിൽ രണ്ട് മാർഗങ്ങളുണ്ട്:

- **HTTP മാർഗം**: സെർവർ പ്രവർത്തിപ്പിക്കുക, അറിയാവുന്ന `suiteId` + `target` ഉപയോഗിച്ച് `POST /api/evals` അഭ്യർത്ഥന നടത്തുക, തുടർന്ന് പ്രതികരണത്തിൽ `runs[].summary.passRate >= N` ആണെന്ന് അസേർട്ട് ചെയ്യുക.
- **ഇൻ-പ്രോസസ് മാർഗം**: ഒരു സ്ക്രിപ്റ്റിൽ നിന്ന് `@/lib/evals/runtime`-ലുള്ള `runEvalSuiteAgainstTarget()` ഇംപോർട്ട് ചെയ്യുക, ഒരു ടെസ്റ്റ് DB-ക്കെതിരെ പ്രവർത്തിപ്പിക്കുക, തുടർന്ന് ലഭിക്കുന്ന `PersistedEvalRun.summary` പരിശോധിക്കുക.

റൂട്ടും ചരിത്രവും ഉൾക്കൊള്ളുന്ന ടെസ്റ്റുകൾ
`tests/unit/evals-route.test.ts`, `tests/unit/evals-history.test.ts` എന്നിവിടങ്ങളിലാണ്.

## വിപുലീകരണ പോയിന്റുകൾ

സാധാരണ മാറ്റങ്ങളും അവ വരുത്തേണ്ട സ്ഥലങ്ങളും:

- **പുതിയ സ്കോറിംഗ് സ്ട്രാറ്റജി** — `evaluateCase()` (`evalRunner.ts`)-ലെ `switch (evalCase.expected.strategy)` ബ്ലോക്ക് വിപുലീകരിക്കുകയും `src/lib/db/evals.ts`-ലെ `EvalCaseStrategy`, `schemas.ts`-ലെ `evalCaseBuilderSchema` എന്നിവ വിശാലമാക്കുകയും ചെയ്യുക.
- **പുതിയ ബിൽറ്റ്-ഇൻ സ്യൂട്ട്** — ഒരു സ്യൂട്ട് ഒബ്ജക്റ്റ് നിർവചിച്ച് `evalRunner.ts`-ന്റെ താഴെ `registerSuite()` വിളിക്കുക. `listSuites()` അത് സ്വയമേവ കണ്ടെത്തും.
- **കൺകറൻസിയോടെ പ്രവർത്തിപ്പിക്കൽ** — `runEvalSuiteAgainstTarget()`-ലെ ക്രമാനുഗതമായ `for` ലൂപ്പിനെ പരിധിയുള്ള `Promise.all` ആയി മാറ്റുക (നിലവിൽ കൺകറൻസി നിയന്ത്രണം നിലവിലില്ല).
- **സ്ട്രീം/ടൂൾ-കോൾ കേസുകൾ** — നിലവിൽ റണ്ണർ `stream: false` നിർബന്ധിതമാക്കുന്നു. സ്ട്രീമിംഗ് അല്ലെങ്കിൽ ടൂൾ-അവെയർ ഇവാലുവേഷനായി `runtime.ts`-ൽ മാറ്റങ്ങൾ ആവശ്യമാണ് (സ്കോറിംഗ് നടത്തുന്നതിന് മുമ്പ് SSE ചങ്കുകൾ രേഖപ്പെടുത്തി സമാഹരിക്കുക).
