> **ചുരുക്കത്തിൽ**: OmniRoute-ലെ ഓരോ LLM അഭ്യർത്ഥനയ്ക്കും ശക്തി പകരുന്ന മുഖ്യ സ്ട്രീമിംഗ് എഞ്ചിനാണ് `open-sse/`. അഭ്യർത്ഥന പൈപ്പ്ലൈൻ, എക്സിക്യൂട്ടറുകൾ, സേവനങ്ങൾ, MCP സെർവർ, വിവർത്തന പാളി എന്നിവ നടപ്പാക്കുന്ന ~1,400 ഫയലുകൾ ഇതിൽ അടങ്ങിയിരിക്കുന്നു. ഈ ഘടകങ്ങൾ എങ്ങനെ ഒരുമിച്ച് പ്രവർത്തിക്കുന്നുവെന്ന് ഈ മാർഗ്ഗദർശി വിശദീകരിക്കുന്നു.

**ഉറവിടം:** `open-sse/` (വർക്ക്സ്പേസ് പാക്കേജ്, ടെസ്റ്റ് ഇതര `.ts` ഫയലുകൾ ~1,440)

## പ്രത്യേക വർക്ക്സ്പേസ് പാക്കേജ് എന്തുകൊണ്ട്?

പല കാരണങ്ങളാൽ OmniRoute മോണോറെപ്പോയിലെ ഒരു **സ്വതന്ത്ര വർക്ക്സ്പേസ്** ആണ് `open-sse/`:

1. **പുനരുപയോഗക്ഷമത** — npm-ൽ `@omniroute/open-sse` എന്ന പേരിൽ `open-sse` പ്രസിദ്ധീകരിക്കുന്നതിനാൽ, മറ്റ് പ്രോജക്റ്റുകൾക്ക് അത് സ്വതന്ത്രമായി ഉപയോഗിക്കാം
2. **വ്യക്തമായ അതിരുകൾ** — OmniRoute-നിർദ്ദിഷ്ട UI/DB പാളിയിൽനിന്ന് സ്ട്രീമിംഗ് എഞ്ചിൻ വേർതിരിച്ചിരിക്കുന്നു
3. **പ്രകടനം** — എഞ്ചിന് Next.js ഡിപെൻഡൻസികൾ ഇല്ലാത്തതിനാൽ, CLI/serverless സാഹചര്യങ്ങളിൽ വേഗത്തിലുള്ള കോൾഡ് സ്റ്റാർട്ടുകൾ സാധ്യമാകുന്നു
4. **പതിപ്പ് നിയന്ത്രണം** — `open-sse`-ന് സ്വന്തം സമയക്രമത്തിൽ റിലീസ് ചെയ്യാനാകും

```json
// package.json
"workspaces": ["open-sse"]
```

                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. വിവർത്തനം│   ഫോർമാറ്റ് പരിവർത്തനം (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. നിർവഹണം │   പ്രൊവൈഡർ എക്സിക്യൂട്ടർ, HTTP, പുനഃശ്രമം, ബ്രേക്കർ

### ഘട്ടം 1: റൂട്ട് (services/combo.ts)

**എൻട്രി പോയിന്റ്**: `services/combo.ts`-ലെ `handleComboChat()`

അഭ്യർത്ഥനയെ ഒരു നിർദ്ദിഷ്ട `(provider, model, account, credentials)` ട്യൂപ്പിളിലേക്ക് പരിഹരിക്കുന്നു:

- ID ഉപയോഗിച്ച് കോംബോ കണ്ടെത്തുക (അല്ലെങ്കിൽ `auto/*` മോഡലുകൾക്കായി ഒരു വെർച്വൽ കോംബോ നിർമ്മിക്കുക)
- റൂട്ടിംഗ് തന്ത്രം പ്രയോഗിക്കുക (മുൻഗണന, വെയ്റ്റഡ്, റൗണ്ട്-റോബിൻ മുതലായവ)
- ആരോഗ്യകരമല്ലാത്ത പ്രൊവൈഡറുകളെ ഒഴിവാക്കുക (സർക്യൂട്ട് ബ്രേക്കർ)
- അടുത്ത പ്രായോഗിക ടാർഗറ്റ് തിരഞ്ഞെടുക്കുക

`auto/*` മോഡലുകൾക്കായി, ഈ ഘട്ടം ഇനിപ്പറയുന്നവയും ചെയ്യുന്നു:

- **16-ഘടക സ്കോറിംഗ്** അൽഗോരിതം പ്രവർത്തിപ്പിക്കുന്നു (`services/autoCombo/`)
- ആരോഗ്യം, ചെലവ്, ലേറ്റൻസി മുതലായവയെ അടിസ്ഥാനമാക്കി ഒരു `provider+model` ജോടി തിരഞ്ഞെടുക്കുന്നു

### ഘട്ടം 2: വിവർത്തനം (translator/)

ഉറവിട ഫോർമാറ്റ് (ഉദാ., OpenAI) ലക്ഷ്യ ഫോർമാറ്റിൽനിന്ന് (ഉദാ., Claude) വ്യത്യസ്തമാണെങ്കിൽ, അഭ്യർത്ഥന **വിവർത്തനം ചെയ്യപ്പെടുന്നു**:

- സിസ്റ്റം പ്രോംപ്റ്റ് → സിസ്റ്റം സന്ദേശം
- ടൂൾ നിർവചനങ്ങൾ → പ്രൊവൈഡർ-നിർദ്ദിഷ്ട ടൂൾ ഫോർമാറ്റ്
- റീസണിംഗ്/തിങ്കിംഗ് പാരാമീറ്ററുകൾ → പ്രൊവൈഡർ-നിർദ്ദിഷ്ട തത്തുല്യങ്ങൾ
- സന്ദേശ റോളുകളുടെ നോർമലൈസേഷൻ (OpenAI അല്ലാത്തവയ്ക്കായി `developer` → `system`)

`translator/index.ts` ഇനിപ്പറയുന്നവ ലഭ്യമാക്കുന്നു:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### ഘട്ടം 3: നിർവഹണം (executors/)

**എൻട്രി പോയിന്റ്**: `getExecutor(providerId).execute(request, options)`

എല്ലാ പ്രൊവൈഡറുകളും `getExecutor()` ഫാക്ടറി ഫാൾബാക്കിലൂടെ `DefaultExecutor` (`executors/default.ts`) ഉപയോഗിക്കുന്നു. എക്സിക്യൂട്ടർ:

- അപ്സ്ട്രീം URL നിർമ്മിക്കുന്നു (`buildUrl()`)
- പ്രൊവൈഡർ-നിർദ്ദിഷ്ട ഹെഡറുകൾ ചേർക്കുന്നു (`buildHeaders()`)
- അഭ്യർത്ഥന ബോഡി പരിവർത്തനം ചെയ്യുന്നു (`transformRequest()`)
- പുനഃശ്രമവും എക്സ്പോണൻഷ്യൽ ബാക്ക്ഓഫും സഹിതം HTTP അഭ്യർത്ഥന അയയ്ക്കുന്നു
- ആവശ്യമെങ്കിൽ ഓത്ത് പുതുക്കൽ കൈകാര്യം ചെയ്യുന്നു (OAuth പ്രൊവൈഡറുകൾ)

എല്ലാ എക്സിക്യൂട്ടറുകളും `BaseExecutor` (`executors/base.ts`, 1170 LOC) വിപുലീകരിക്കുന്നു; ഇത് ഇനിപ്പറയുന്നവ നൽകുന്നു:

- പൊതുവായ പുനഃശ്രമ ലോജിക്
- പ്രോക്സി സംയോജനം
- സർക്യൂട്ട് ബ്രേക്കർ സംയോജനം
- ഉപയോഗം രേഖപ്പെടുത്തുന്നതിനുള്ള ഹുക്കുകൾ

### ഘട്ടം 4: സ്ട്രീം (utils/stream.ts)

സ്ട്രീമിംഗ് പ്രതികരണങ്ങൾക്കായി, എക്സിക്യൂട്ടർ ഒരു **ReadableStream** തിരികെ നൽകുന്നു. ഹാൻഡ്ലർ:

- ഒരു SSE ട്രാൻസ്ഫോമിലൂടെ പൈപ്പ് ചെയ്യുന്നു (`createSSETransformStreamWithLogger`)
- പ്രവർത്തനരഹിതമായ കണക്ഷനുകൾ കണ്ടെത്താൻ ഹാർട്ട്ബീറ്റ് പിങ്ങുകൾ പ്രയോഗിക്കുന്നു
- ക്ലയന്റ് വിച്ഛേദനം സുഗമമായി കൈകാര്യം ചെയ്യുന്നു (`pipeWithDisconnect`)
- സ്ട്രീമിംഗ് അല്ലാത്ത ക്ലയന്റുകൾക്കായി SSE → JSON പരിവർത്തനം ചെയ്യുന്നു

സ്ട്രീമിംഗ് അല്ലാത്ത പ്രതികരണങ്ങൾക്കായി, മാറ്റമൊന്നും വരുത്താതെ കൈമാറുന്ന ഒരു പാർസ് ചെയ്ത JSON ഒബ്ജക്റ്റ് എക്സിക്യൂട്ടർ തിരികെ നൽകുന്നു.

### ഘട്ടം 5: രേഖപ്പെടുത്തൽ (services/usage.ts)

പ്രതികരണത്തിന് ശേഷം (വിജയമോ പരാജയമോ ആയാലും), ഉപയോഗം രേഖപ്പെടുത്തുന്നു:

- പ്രതികരണത്തിൽ നിന്നുള്ള `prompt_tokens`, `completion_tokens`, `cached_tokens`
- വിലനിർണ്ണയ ഡാറ്റയിൽ നിന്ന് കണക്കാക്കുന്ന `cost_usd`

### chatCore.ts (5977 വരികൾ)

**പ്രധാന അഭ്യർത്ഥന കൈകാര്യം ചെയ്യുന്ന ഘടകം**. വലുപ്പം കൂടുതലാണെങ്കിലും, ഇതിന് വ്യക്തമായ ഘടനയുണ്ട്:

```ts
// chatCore.ts-ന്റെ സ്യൂഡോ-ഘടന
export async function handleChat(request: NextRequest) {
  // 1. പ്രാമാണീകരണം + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. ബോഡി സാധൂകരണം
  const body = await parseRequestBody(request);

  // 3. ഫോർമാറ്റ് കണ്ടെത്തൽ + പരിവർത്തനം
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. കോംബോ റൂട്ടിംഗ്
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // അടുത്ത ടാർഗറ്റിലേക്ക് തുടരുക
    }
  }

  // 5. അടിയന്തര ഫാൾബാക്ക്
  return await emergencyFallback(body);
}
```

ഒരൊറ്റ വലിയ ഫങ്ഷൻ ആണെങ്കിലും, 5-ഘട്ട പൈപ്പ്ലൈനുമായി പൊരുത്തപ്പെടുന്ന **അഭിപ്രായങ്ങളോടുകൂടിയ വിഭാഗങ്ങളായി** ഇത് ക്രമീകരിച്ചിരിക്കുന്നു.

### combo.ts (4456 LOC)

// services/combo.ts

## എക്സിക്യൂട്ടറുകൾ (75+ ഫയലുകൾ)

ഓരോ പ്രൊവൈഡറിനും ഓരോ ഫയൽ. അവയെല്ലാം `BaseExecutor` വിപുലീകരിക്കുകയും വ്യത്യാസമുള്ള ഭാഗങ്ങൾ ഓവർറൈഡ് ചെയ്യുകയും ചെയ്യുന്നു.

### പൊതുവായ പാറ്റേണുകൾ

പ്രൊവൈഡറുകളെ `getExecutor(providerId)` വഴി റിസോൾവ് ചെയ്യുന്നു; ഇത് കോൺഫിഗർ ചെയ്ത എക്സിക്യൂട്ടർ നൽകുന്നു. OpenAI/Anthropic-അനുയോജ്യമായ പ്രൊവൈഡറുകൾ `DefaultExecutor` (`executors/default.ts`) ഉപയോഗിക്കുന്നു. പ്രൊവൈഡർ-നിർദ്ദിഷ്ട സ്വഭാവം (അടിസ്ഥാന URL, ഓതന്റിക്കേഷൻ ഹെഡറുകൾ, API പതിപ്പ്) `open-sse/config/providers/`-ൽ കോൺഫിഗർ ചെയ്യുന്നു; അതേസമയം അഭ്യർത്ഥനാ ബോഡി പരിവർത്തനങ്ങൾ `open-sse/translator/`-ൽ കൈകാര്യം ചെയ്യുന്നു.

**കസ്റ്റം URL** പ്രൊവൈഡർ കോൺഫിഗറേഷൻ വഴി സജ്ജീകരിക്കുന്നു:

```ts
// open-sse/config/providers/-ലെ പ്രൊവൈഡർ കോൺഫിഗ്
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**കസ്റ്റം ഓതന്റിക്കേഷൻ** പ്രൊവൈഡർ രജിസ്ട്രിയുടെ ഓതന്റിക്കേഷൻ കോൺഫിഗറേഷൻ (API കീ, OAuth, ഹെഡർ പ്രൊഫൈലുകൾ) വഴി കൈകാര്യം ചെയ്യുന്നു.

**കസ്റ്റം അഭ്യർത്ഥനാ ബോഡി** പരിവർത്തനങ്ങൾ (ഉദാഹരണത്തിന്, Anthropic `system`-ത്തെ `messages`-ൽനിന്ന് വേർതിരിക്കുന്നത്) ഓരോ പ്രൊവൈഡറിനും പ്രത്യേകം `open-sse/translator/`-ൽ രജിസ്റ്റർ ചെയ്യുന്നു.

````

### എക്സിക്യൂട്ടർ ഫാക്ടറി

`executors/index.ts`, `getExecutor(providerId)` എക്സ്പോർട്ട് ചെയ്യുന്നു:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

റിസല്യൂഷൻ `ExecutorRegistry` (`executors/registry.ts`) വഴിയാണ് നടക്കുന്നത്: ഓരോ പ്രത്യേക എക്സിക്യൂട്ടറും `executors/index.ts`-ന്റെ ബിൽറ്റ്-ഇൻ പട്ടികയിൽ പ്രഖ്യാപിക്കുകയും മൊഡ്യൂൾ ലോഡ് ചെയ്യുമ്പോൾ `registerExecutor(alias, instance)` വഴി രജിസ്റ്റർ ചെയ്യുകയും ചെയ്യുന്നു; `getExecutor()` രജിസ്ട്രി പരിശോധിക്കുകയും പ്രത്യേക എൻട്രിയില്ലാത്ത ഏത് പ്രൊവൈഡറിനും മെമോയിസ് ചെയ്ത `DefaultExecutor`-ലേക്ക് ഫാൾബാക്ക് ചെയ്യുകയും ചെയ്യുന്നു. സമ്പൂർണ്ണ alias → executor മാപ്പിംഗ്, ഗോൾഡൻ ടെസ്റ്റായ `tests/unit/executor-map-golden.test.ts` മുഖേന നിർവചിച്ചിരിക്കുന്നു.

## വിവർത്തകർ

**3 ഫോർമാറ്റുകൾക്കിടയിൽ** വിവർത്തനം ചെയ്യുക: OpenAI, Anthropic, Gemini, കൂടാതെ പുതിയ Responses API.

### വിവർത്തനം നടക്കുന്നത് എപ്പോൾ

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

സാധാരണ വിവർത്തനങ്ങൾ:

- `OpenAI → Anthropic`: വേർതിരിച്ച `system` ഫീൽഡ്, `x-api-key` ഹെഡർ
- `OpenAI → Gemini`: `messages`-ന് പകരം `contents`, `systemInstruction`
- `OpenAI → Responses API`: `input` അറേ, `previous_response_id` സ്റ്റേറ്റ്

### കൈകാര്യം ചെയ്യുന്ന എഡ്ജ് കേസുകൾ

- `developer` റോൾ → OpenAI അല്ലാത്തവയ്ക്ക് `system`
- `system` റോൾ → GLM/ERNIE-ക്കായി ആദ്യ യൂസർ സന്ദേശത്തിലേക്ക് ലയിപ്പിക്കുന്നു
- `json_schema` → Gemini-യുടെ `responseMimeType` + `responseSchema`
- `tools` → പ്രൊവൈഡർ-നിർദ്ദിഷ്ട ടൂൾ ഫോർമാറ്റ്
- തിങ്കിങ് പാരാമീറ്ററുകൾ (o1, Claude) → പ്രൊവൈഡർ-നിർദ്ദിഷ്ട തുല്യരൂപങ്ങൾ

## MCP സെർവർ

`open-sse/mcp-server/` **Model Context Protocol** സെർവർ നടപ്പിലാക്കുന്നു:

- **110 ടൂളുകൾ** (പ്രൊവൈഡർ മാനേജ്മെന്റ്, കോംബോകൾ, മെമ്മറി, കാഷ്, കംപ്രഷൻ, പ്രോക്സി, സ്കില്ലുകൾ, ഗെയിമിഫിക്കേഷൻ, പ്ലഗിനുകൾ, Notion, Obsidian, ലോക്കൽ കോർപ്പസ്)
- **3 ട്രാൻസ്പോർട്ടുകൾ**: stdio, SSE, Streamable HTTP
- സൂക്ഷ്മതലത്തിലുള്ള ഓതറൈസേഷനായി **33 സ്കോപ്പുകൾ**

### ടൂൾ രജിസ്ട്രേഷൻ

ടൂളുകൾ `open-sse/mcp-server/tools/`-ൽ സ്വതന്ത്ര ഫയലുകളായി രജിസ്റ്റർ ചെയ്യപ്പെടുന്നു; ഓരോന്നും ഒരു പേര്, സ്കീമ, ഹാൻഡ്ലർ, സ്കോപ്പ് എന്നിവ എക്സ്പോർട്ട് ചെയ്യുന്നു:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### ട്രാൻസ്പോർട്ടുകൾ

```ts
// stdio (CLI ഉപയോഗം)
startMcpStdio(server);

// SSE (HTTP അടിസ്ഥാനമാക്കിയുള്ള സ്ട്രീമിങ്)
startMcpSse(server, port);

// Streamable HTTP (ആധുനിക MCP)
startMcpStreamable(server, port);
```

### ഓതറൈസേഷൻ

ഓരോ ടൂൾ കോളും സ്കോപ്പ് പരിശോധനകളിലൂടെ കടന്നുപോകുന്നു (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## ട്രാൻസ്ഫോർമറുകൾ

`open-sse/transformer/` **Chat Completions**, **Responses API** ഫോർമാറ്റുകൾക്കിടയിൽ പരിവർത്തനം ചെയ്യുന്നു.

### എന്തുകൊണ്ട് ഒരു പ്രത്യേക ട്രാൻസ്ഫോർമർ?

Responses API എന്നത് **സ്റ്റേറ്റ്ഫുൾ സംഭാഷണങ്ങൾ** (`previous_response_id`) ഉള്ള OpenAI-യുടെ പുതിയ ഫോർമാറ്റാണ്. ഒരു ക്ലയന്റ് Responses അഭ്യർത്ഥന അയയ്ക്കുമ്പോൾ, OmniRoute:

1. ആന്തരികമായി Responses → Chat Completions ആയി പരിവർത്തനം ചെയ്യുന്നു
2. പ്രൊവൈഡറിലേക്ക് അയയ്ക്കുന്നു (Chat Completions പിന്തുണയ്ക്കുന്ന ഏതൊരു പ്രൊവൈഡറിലേക്കും)
3. പ്രതികരണം വീണ്ടും Responses ഫോർമാറ്റിലേക്ക് പരിവർത്തനം ചെയ്യുന്നു
4. പരിവർത്തനം ചെയ്ത പ്രതികരണം ക്ലയന്റിലേക്ക് സ്ട്രീം ചെയ്യുന്നു

ട്രാൻസ്ഫോർമർ (`transformer/responsesTransformer.ts`) നൽകുന്നത്:

```ts
createResponsesApiTransformStream(): TransformStream
```

ഇത് കൈകാര്യം ചെയ്യുന്നത്:

- `response.output_item.added` ഇവന്റുകൾ
- `response.output_text.delta` ഇവന്റുകൾ
- `response.completed` ഇവന്റ്
- ടൂൾ കോൾ മാപ്പിങ് (`function_call` ↔ `tool_calls`)

## കോൺഫിഗറേഷൻ

`open-sse/config/` കോൺഫിഗറേഷൻ ലെയർ ഉൾക്കൊള്ളുന്നു:

| ഫയൽ                           | ഉദ്ദേശ്യം                                                 |
| ----------------------------- | --------------------------------------------------------- |
| `providerRegistry.ts`         | 352-പ്രൊവൈഡർ കാറ്റലോഗിന് മുകളിലുള്ള ചാറ്റ്-മോഡൽ രജിസ്ട്രി |
| `providerModels.ts`           | മോഡൽ അപരനാമങ്ങൾ, ഫോർമാറ്റ് മാപ്പിങ്                       |
| `constants.ts`                | ടൈംഔട്ടുകൾ, പരിധികൾ, സ്റ്റാറ്റസ് കോഡുകൾ                   |
| `defaultThinkingSignature.ts` | ഡിഫോൾട്ട് Claude തിങ്കിങ് സിഗ്നേച്ചർ                      |
| `modelStrip.ts` (സർവീസുകളിൽ)  | ഓരോ പ്രൊവൈഡറിനും പ്രത്യേകമായ ഫീൽഡ് നീക്കംചെയ്യൽ           |

### പ്രൊവൈഡർ രജിസ്ട്രി സ്കീമ

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

മൊഡ്യൂൾ ലോഡ് ചെയ്യുന്ന സമയത്തെ Zod വാലിഡേഷൻ എല്ലാ പ്രൊവൈഡർ കോൺഫിഗറേഷനുകളും സാധുവാണെന്ന് ഉറപ്പാക്കുന്നു.

## ഒരു പുതിയ ഘടകം ചേർക്കൽ

### ഒരു പുതിയ സർവീസ് ചേർക്കൽ

1. കേന്ദ്രീകൃത ഉത്തരവാദിത്തത്തോടെ `open-sse/services/[serviceName].ts` സൃഷ്ടിക്കുക
2. പ്രധാന ഹാൻഡ്ലർ ഫങ്ഷനും ആവശ്യമായ കോൺസ്റ്റന്റുകളും എക്സ്പോർട്ട് ചെയ്യുക
3. `tests/unit/services/[serviceName].test.mjs`-ൽ യൂണിറ്റ് ടെസ്റ്റുകൾ ചേർക്കുക
4. റൂട്ടിംഗുമായി ബന്ധപ്പെട്ടതാണെങ്കിൽ `handlers/chatCore.ts`-ലെ അഭ്യർത്ഥന പൈപ്പ്ലൈനിലേക്ക് സംയോജിപ്പിക്കുക
5. സർവീസ് ലക്ഷ്യ തിരഞ്ഞെടുപ്പിനെ ബാധിക്കുന്നുണ്ടെങ്കിൽ `combo.ts`-ലെ റൂട്ടിംഗ് ലോജിക് അപ്ഡേറ്റ് ചെയ്യുക
6. ഈ ഫയലിൽ ഡോക്യുമെന്റ് ചെയ്യുക

### ഒരു പുതിയ എക്സിക്യൂട്ടർ ചേർക്കൽ

1. `BaseExecutor` വിപുലീകരിക്കുന്ന `open-sse/executors/[provider].ts` സൃഷ്ടിക്കുക
2. `config/providerRegistry.ts`-ൽ രജിസ്റ്റർ ചെയ്യുക
3. `executors/index.ts` ഫാക്ടറിയിലേക്ക് ചേർക്കുക
4. എക്സിക്യൂട്ടറിനായി യൂണിറ്റ് ടെസ്റ്റുകൾ ചേർക്കുക
5. `docs/architecture/ARCHITECTURE.md`-ൽ ഡോക്യുമെന്റ് ചെയ്യുക

### ഒരു പുതിയ MCP ടൂൾ ചേർക്കൽ

1. `open-sse/mcp-server/tools/[category]Tools.ts` സൃഷ്ടിക്കുകയോ അപ്ഡേറ്റ് ചെയ്യുകയോ ചെയ്യുക
2. ഇൻപുട്ടുകൾക്കായി Zod സ്കീമ നിർവചിക്കുക
3. `mcp-server/index.ts`-ൽ ടൂൾ രജിസ്റ്റർ ചെയ്യുക
4. `mcp-server/auth/`-ലെ സ്കോപ്പ് മാട്രിക്സിലേക്ക് ചേർക്കുക
5. യൂണിറ്റ് ടെസ്റ്റുകൾ ചേർക്കുക
