## സീറോ-കോൺഫിഗ് ഓട്ടോ-റൂട്ടിംഗ് (`auto/` പ്രിഫിക്സ്)

> **പുതിയത്:** കോംബോ സൃഷ്ടിക്കേണ്ടതില്ല. ഏത് ക്ലയന്റിലും നേരിട്ട് `auto/` പ്രിഫിക്സ് ഉപയോഗിക്കുക.

### ദ്രുത ഉദാഹരണങ്ങൾ

| മോഡൽ ID        | വേരിയന്റ് | പ്രവർത്തനം                                                                             |
| -------------- | --------- | -------------------------------------------------------------------------------------- |
| `auto`         | default   | കണക്റ്റുചെയ്ത എല്ലാ പ്രൊവൈഡർമാരും, LKGP സ്ട്രാറ്റജി, സന്തുലിത വെയിറ്റുകൾ               |
| `auto/coding`  | coding    | ഗുണനിലവാരത്തിന് മുൻഗണന നൽകുന്ന വെയിറ്റുകൾ, കോഡ് ജനറേഷനു അനുയോജ്യം                      |
| `auto/fast`    | fast      | കുറഞ്ഞ ലേറ്റൻസിക്ക് വെയിറ്റ് നൽകിയ തിരഞ്ഞെടുപ്പ്                                       |
| `auto/cheap`   | cheap     | ചെലവ് ഒപ്റ്റിമൈസ് ചെയ്ത റൂട്ടിംഗ് (ഏറ്റവും കുറഞ്ഞ ചെലവിന് ആദ്യം)                       |
| `auto/offline` | offline   | ഏറ്റവും കൂടുതൽ ക്വോട്ട ലഭ്യതയുള്ള പ്രൊവൈഡർമാർക്ക് മുൻഗണന നൽകുന്നു                      |
| `auto/smart`   | smart     | മികച്ച മോഡൽ കണ്ടെത്തലിനായി ഗുണനിലവാരത്തിന് മുൻഗണന + ഉയർന്ന എക്സ്പ്ലോറേഷൻ നിരക്ക് (10%) |
| `auto/lkgp`    | lkgp      | വ്യക്തമായ LKGP (ഡിഫോൾട്ട് `auto` പോലെത്തന്നെ)                                          |
| `auto/chaos`   | chaos     | പ്രതിരോധശേഷി പരിശോധനയ്ക്കുള്ള ഫോൾട്ട്-ഇൻജക്ഷൻ വെയിറ്റുകൾ (കേയോസ് എൻജിനീയറിംഗ്)         |

### കാറ്റഗറി × ടിയർ ഘടന (`auto/<category>:<tier>`)

OpenRouter-ശൈലിയിലുള്ള സഫിക്സുകൾ **ഏത് തരത്തിലുള്ള റൂട്ട്** (കാറ്റഗറി) എന്നതിനെ **അത് എങ്ങനെ ഒപ്റ്റിമൈസ് ചെയ്യണം** (ടിയർ) എന്നതിൽനിന്ന് വേർതിരിക്കുന്നു, അതിനാൽ നിങ്ങൾക്ക് അവ സ്വതന്ത്രമായി സംയോജിപ്പിക്കാം (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **കാറ്റഗറികൾ** (ശേഷിയനുസരിച്ച് കാൻഡിഡേറ്റ് പൂൾ ഫിൽട്ടർ ചെയ്യുന്നു): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` വിഷൻ ശേഷിയുള്ള മോഡലുകളെ നിലനിർത്തുന്നു; `reasoning` റീസണിംഗ്/തിങ്കിംഗ് മോഡലുകളെ നിലനിർത്തുന്നു.
- **ടിയറുകൾ** (സ്കോറിംഗ് വെയിറ്റുകൾ / പൂൾ ഫിൽട്ടർ തിരഞ്ഞെടുക്കുന്നു): `fast` (വേഗത്തിൽ പുറത്തിറക്കൽ) · `cheap` (`floor` എന്ന അപരനാമം, ചെലവ് ലാഭിക്കൽ) · `reliable` (സർക്യൂട്ട്-ബ്രേക്കർ ആരോഗ്യം + ലേറ്റൻസി സ്ഥിരത) · `free` / `pro` (`classifyTier` വഴി മോഡൽ ടിയർ അനുസരിച്ച് പൂൾ ഫിൽട്ടർ ചെയ്യുന്നു — സൗജന്യ ടിയർ vs. പ്രീമിയം).

| ഉദാഹരണം                | പരിഹരിക്കപ്പെടുന്നത്                                                      |
| ---------------------- | ------------------------------------------------------------------------- |
| `auto/coding:fast`     | കോഡിംഗ് പൂൾ, കുറഞ്ഞ ലേറ്റൻസി വെയിറ്റുകൾ                                   |
| `auto/coding:cheap`    | കോഡിംഗ് പൂൾ, ചെലവ് ഒപ്റ്റിമൈസ് ചെയ്തത് (`auto/coding:floor` എന്ന അപരനാമം) |
| `auto/reasoning:pro`   | റീസണിംഗ്/തിങ്കിംഗ് മോഡലുകൾ മാത്രം, പ്രീമിയം ടിയർ                          |
| `auto/vision`          | വിഷൻ ശേഷിയുള്ള മോഡലുകൾ (ടിയർ ഇല്ല → സന്തുലിത വെയിറ്റുകൾ)                  |
| `auto/multimodal:free` | മൾട്ടിമോഡൽ ശേഷിയുള്ള മോഡലുകൾ, സൗജന്യ ടിയർ മാത്രം                          |

സാധുവായ ഏത് `auto/<category>[:<tier>]`-ഉം ആവശ്യപ്പെടുമ്പോൾ പരിഹരിക്കപ്പെടുന്നു; തിരഞ്ഞെടുത്ത ഒരു ഉപഗണം `/v1/models`-ലും ഡാഷ്ബോർഡിലും പരസ്യപ്പെടുത്തുന്നു (`open-sse/services/autoCombo/builtinCatalog.ts`-ലെ `AUTO_SUFFIX_VARIANTS`). ഫിൽട്ടറിംഗ് **fail-open** ആണ് — ഒരു നിയന്ത്രണത്തിനും കണക്റ്റുചെയ്ത മോഡലുകൾ പൊരുത്തപ്പെടുന്നില്ലെങ്കിൽ, റൂട്ടിംഗ് ഒരിക്കലും തടസ്സപ്പെടാതിരിക്കാൻ മുഴുവൻ പൂൾ ഉപയോഗിക്കും. കോർ സ്കോറർ (`combo.ts`) മാറ്റമില്ലാതെ തുടരുന്നു; കാറ്റഗറി/ടിയർ ഫിൽട്ടർ `buildAutoCandidates`-ൽ പ്രയോഗിക്കുന്നു.

> **തത്സമയ മോഡൽ ഇന്റലിജൻസ്:** `ARENA_ELO_SYNC_ENABLED` ഫ്ലാഗ് ഓണായിരിക്കുമ്പോൾ തത്സമയ **Arena ELO** റാങ്കിംഗുകളും **models.dev** ടിയർ ഡാറ്റയും ഓട്ടോ-റൂട്ടിംഗ് ഫിറ്റ്നസിനെ സ്വാധീനിക്കുന്നു (അല്ലാത്തപ്പോൾ സ്റ്റാറ്റിക് ഫിറ്റ്നസ് മാപ്പിലേക്ക് ഫാൾബാക്ക് ചെയ്യുന്നു).

**ഉപയോഗിക്കേണ്ട വിധം:**

```bash
# OpenAI ഫോർമാറ്റ് പിന്തുണയ്ക്കുന്ന ഏതെങ്കിലും IDE അല്ലെങ്കിൽ CLI ടൂൾ
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# നിങ്ങളുടെ കോഡ്/കോൺഫിഗിൽ, മോഡൽ ഇങ്ങനെ സജ്ജീകരിക്കുക:
model: "auto"                 # സന്തുലിത ഡിഫോൾട്ട്
model: "auto/coding"          # കോഡിംഗ് ടാസ്കുകൾക്ക് ഏറ്റവും മികച്ചത്
model: "auto/fast"            # ലഭ്യമായതിൽ ഏറ്റവും വേഗമേറിയത്
model: "auto/cheap"           # ഓരോ ടോക്കണിനും ഏറ്റവും ചെലവ് കുറഞ്ഞത്
```

**എന്താണ് സംഭവിക്കുന്നത്:**

1. `src/sse/handlers/chat.ts`-ൽ OmniRoute `auto/` പ്രിഫിക്സ് കണ്ടെത്തുന്നു
2. ഡാറ്റാബേസിൽനിന്ന് എല്ലാ **സജീവ പ്രൊവൈഡർ കണക്ഷനുകളും** അന്വേഷിക്കുന്നു
3. സാധുവായ ക്രെഡൻഷ്യലുകളുള്ളവയിലേക്ക് ഫിൽട്ടർ ചെയ്യുന്നു (API കീ അല്ലെങ്കിൽ OAuth ടോക്കൺ)
4. ഓരോ കണക്ഷനുമുള്ള മോഡൽ നിർണ്ണയിക്കുന്നു (`connection.defaultModel` അല്ലെങ്കിൽ പ്രൊവൈഡറുടെ ആദ്യ മോഡൽ)
5. മെമ്മറിയിൽ ഒരു **വെർച്വൽ കോംബോ** നിർമ്മിക്കുന്നു (DB-യിൽ സംഭരിക്കില്ല)
6. തിരഞ്ഞെടുത്ത വേരിയന്റിന്റെ വെയിറ്റ് പ്രൊഫൈൽ + LKGP സ്ട്രാറ്റജി ഉപയോഗിച്ച് റൂട്ട് ചെയ്യുന്നു

**പ്രധാന സവിശേഷതകൾ:**

- ✅ **എപ്പോഴും പ്രവർത്തനം:** ടോഗിൾ, കോംബോ സൃഷ്ടിക്കൽ, കോൺഫിഗറേഷൻ എന്നിവയൊന്നും ആവശ്യമില്ല
- ✅ **ഡൈനാമിക്:** നിലവിൽ കണക്റ്റുചെയ്ത പ്രൊവൈഡർമാരെ സ്വയമേവ പ്രതിഫലിപ്പിക്കുന്നു
- ✅ **സെഷൻ സ്റ്റിക്കിനസ്:** അവസാനം വിജയിച്ച പ്രൊവൈഡർക്ക് മുൻഗണന നൽകുന്നത് LKGP ഉറപ്പാക്കുന്നു
- ✅ **ഒന്നിലധികം അക്കൗണ്ടുകൾ പരിഗണിക്കുന്നു:** ഓരോ പ്രൊവൈഡർ കണക്ഷനും പ്രത്യേക കാൻഡിഡേറ്റായി മാറുന്നു
- ✅ **DB റൈറ്റുകളില്ല:** വെർച്വൽ കോംബോ റിക്വസ്റ്റിന് വേണ്ടി മാത്രം നിലനിൽക്കുന്നു, പെർസിസ്റ്റൻസ് ഓവർഹെഡ് പൂജ്യം

### ഓരോ കീയ്ക്കുമുള്ള കാൻഡിഡേറ്റ് നിയന്ത്രണം (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/`-ന് ശേഷമുള്ള സഫിക്സ്, അല്ലെങ്കിൽ
അടിസ്ഥാന ചാനലിനുള്ള ലിറ്ററൽ `auto`) എന്നത് നിലവിലുള്ള പ്രതിരോധശേഷി റീഡുകൾ വീണ്ടും ഉപയോഗിച്ച്,
തത്സമയ റീച്ചബിലിറ്റി വിവരങ്ങൾ ചേർത്ത ഒരു `auto/*` ചാനലിന്റെ നിലവിലെ കാൻഡിഡേറ്റ് പൂൾ ലിസ്റ്റ് ചെയ്യുന്ന
**വായനയ്ക്ക് മാത്രമുള്ള** എൻഡ്പോയിന്റാണ് (ബ്രേക്കറിന്റെ അസംസ്കൃത `state` ഒരിക്കലും ഉപയോഗിക്കില്ല):

- പ്രൊവൈഡർ സർക്യൂട്ട് ബ്രേക്കർ — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- കണക്ഷൻ കൂൾഡൗൺ — പരിഹരിച്ച `provider_connections` റൗവിലെ `rateLimitedUntil` / `testStatus`
- മോഡൽ ലോക്കൗട്ട് — `isModelLocked(provider, connectionId, model)`

ഓരോ കാൻഡിഡേറ്റിലും ഈ API കീയുടെ `excluded` ഫ്ലാഗും ഉൾപ്പെടുന്നു. ഒഴിവാക്കലുകൾ
ഓരോ API കീയ്ക്കുമായി സംഭരിക്കുന്നു (`auto_candidate_overrides` പട്ടിക, മൈഗ്രേഷൻ `128`) — OmniRoute
`users` പട്ടികയില്ലാത്ത സിംഗിൾ-ടെനന്റ് സംവിധാനമായതിനാൽ, യഥാർത്ഥ ഓരോ കോളറിനുമുള്ള ഐഡന്റിറ്റിയോട്
ഏറ്റവും അടുത്തത് `apiKeyId` ആണ് — കൂടാതെ പൂർണ്ണമായും യൂണിറ്റ്-ടെസ്റ്റ് ചെയ്ത
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) വഴി
`open-sse/services/autoCombo/virtualFactory.ts`-ലെ കാൻഡിഡേറ്റ്-പൂൾ ചോക്ക്പോയിന്റിൽ ഇത് നടപ്പാക്കുന്നു.
ഫിൽട്ടർ **fail-open** ആണ്: സജ്ജീകരിക്കാത്ത apiKeyId/channel അല്ലെങ്കിൽ DB ലുക്കപ്പ് പരാജയം എന്നിവ രണ്ടും
പൂൾ ഫിൽട്ടർ ചെയ്യാതെ നിലനിർത്തുന്നു, അതിനാൽ ഓവർറൈഡുകളൊന്നും കോൺഫിഗർ ചെയ്തിട്ടില്ലാത്ത ഒരു ഓപ്പറേറ്റർക്ക്
ഈ ഫീച്ചറിന് മുമ്പുണ്ടായിരുന്നതിന് ബൈറ്റ്-സമാനമായ റൂട്ടിംഗ് ലഭിക്കുന്നു.

**ഒരു തുടർ ഇഷ്യൂവിലേക്ക് മാറ്റിവെച്ചത്:** ഓരോ കാൻഡിഡേറ്റിനുമുള്ള വെയിറ്റുകൾ + വ്യക്തമായ ക്രമീകരണം (Level 3
— നിലവിലുള്ള വെയിറ്റഡ്/പ്രയോറിറ്റി സ്ട്രാറ്റജി പാതകളിലേക്ക് നൽകുന്നു), കൂടാതെ ഓരോ `auto/*` ചാനലിനുമായി
ഒരു നിർദ്ദിഷ്ട `combo.ts` സ്ട്രാറ്റജി പിൻ ചെയ്യൽ (Level 4). സിംഗിൾ-ടെനന്റ് മോഡൽ പരിഗണിക്കുമ്പോൾ
ഓവർറൈഡുകൾ ഓരോ API കീയ്ക്കുമായി തുടരണമോ അതോ ഗ്ലോബൽ ആക്കണമോ എന്ന തുറന്ന ചോദ്യത്തിന് #7819 പ്ലാൻ കാണുക.

**പശ്ചാത്തലത്തിൽ:**

```txt
റിക്വസ്റ്റ്: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts പ്രിഫിക്സ് കണ്ടെത്തുന്നു
   ↓
createVirtualAutoCombo('coding') → സജീവ കണക്ഷനുകളിൽനിന്നുള്ള candidatePool
   ↓
handleComboChat (പെർസിസ്റ്റ് ചെയ്ത കോംബോകൾ ഉപയോഗിക്കുന്ന അതേ എഞ്ചിൻ)
   ↓
ഓരോ റിക്വസ്റ്റിനും ഏറ്റവും മികച്ച പ്രൊവൈഡർ/മോഡൽ ഓട്ടോ-സ്കോറിംഗ് തിരഞ്ഞെടുക്കുന്നു
```

## യഥാർത്ഥ മോഡൽ ഐഡിയുമായി പൊരുത്തപ്പെടുന്ന കോംബോ പേരുകൾ

പ്രിഫിക്സില്ലാത്ത ഒരു മോഡൽ ഐഡിക്ക് സമാനമായ `name` ഉള്ള കോംബോ (ഉദാ. `gpt-5.5`
എന്ന് പേരുള്ള കോംബോ) ഒരു ബഗ് അല്ല; മറിച്ച് അത് **മനഃപൂർവമുള്ളതും പിന്തുണയ്ക്കുന്നതുമായ പാറ്റേൺ** ആണ്:
ഓരോ മോഡൽ ഐഡിനുമുള്ള പ്രൊവൈഡർ ഫാൾബാക്കിനായി
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940)-ൽ രേഖപ്പെടുത്തിയിരിക്കുന്ന
സംവിധാനമാണിത്. പ്രിഫിക്സില്ലാത്ത മോഡൽ ഐഡി റെസല്യൂഷനു മുമ്പായി കോംബോ
റെസല്യൂഷൻ പരിശോധിക്കുന്നതിനാൽ
(`src/sse/services/model.ts`-ലെ `getComboForModel()`), പ്രിഫിക്സില്ലാത്ത
`gpt-5.5` ഐഡിക്കായുള്ള ഒരു അഭ്യർത്ഥന ഒരൊറ്റ പ്രൊവൈഡറിലേക്ക് നേരിട്ട്
അയയ്ക്കുന്നതിനുപകരം കോംബോയുടെ ടാർഗെറ്റുകളിലൂടെ (ഉദാ.
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) റൂട്ട് ചെയ്യപ്പെടുന്നു —
ഇത് [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227)-നായി
നിർമ്മിച്ച കോംബോ-ബിഫോർ-റീറൈറ്റ് മുൻഗണന വീണ്ടും ഉപയോഗിക്കുന്നു; കൂടാതെ
`tests/unit/responses-combo-resolution-3227.test.ts`,
`tests/unit/combo-name-codex-responses-rewrite.test.ts` എന്നിവയിലൂടെ
റിഗ്രഷൻ പരിശോധനയും നടത്തുന്നു.

ഒരു യഥാർത്ഥ മോഡൽ ഐഡിയെ ഷാഡോ ചെയ്യുന്ന പേരിൽ കോംബോ സൃഷ്ടിക്കുകയോ അതിലേക്ക്
പുനർനാമകരണം ചെയ്യുകയോ ചെയ്യുന്നത് **ഒരിക്കലും നിരസിക്കപ്പെടില്ല** — അങ്ങനെ
ചെയ്യുന്നത് രേഖപ്പെടുത്തിയിരിക്കുന്ന ഈ വർക്ക്ഫ്ലോയെ തകർക്കും. പകരം
(#8530), (പുതിയ) പേര് ഒരു യഥാർത്ഥ മോഡൽ ഐഡിയുമായി കൂട്ടിയിടിക്കുമ്പോൾ
`POST /api/combos`, `PUT /api/combos/[id]` എന്നിവ റെസ്പോൺസിൽ തടസ്സമുണ്ടാക്കാത്ത
ഒരു `warning` ഫീൽഡ് ചേർക്കുന്നു:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

ബൂട്ട് സമയത്ത്, `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) ഒരു മോഡൽ ഐഡിയെ ഷാഡോ ചെയ്യുന്ന നിലവിലുള്ള
ഓരോ കോംബോയും പട്ടികപ്പെടുത്തുന്ന ഒറ്റവരി `[STARTUP]` മുന്നറിയിപ്പും ലോഗ്
ചെയ്യുന്നു. അതിനാൽ #6940 പ്രകാരം മനഃപൂർവം ചെയ്യുന്നതിനുപകരം അബദ്ധത്തിൽ
ഇത് സംഭവിച്ച ഓപ്പറേറ്റർമാർക്ക് ഒരു സൂചന ലഭിക്കും. കണ്ടെത്തൽ ഹെൽപ്പർ
`src/lib/combos/modelNameCollision.ts`-ലാണ്.

## ഒരു ക്ലയന്റിൽ നിന്ന് കസ്റ്റം കോംബോ വിളിക്കുന്നത്

ക്ലയന്റ് `model` ഫീൽഡിൽ കോംബോയുടെ **കൃത്യമായ പേര്** അയയ്ക്കുമ്പോൾ മാത്രമാണ്
നിലനിർത്തിയ കോംബോകൾ (ക്രമീകരണങ്ങൾ → കോംബോകൾ) ഉപയോഗിക്കുന്നത് — കോംബോയുടെ
പേരിന് ഫസി അല്ലെങ്കിൽ ഭാഗിക പൊരുത്തപ്പെടുത്തൽ ഇല്ല; `auto/` പ്രിഫിക്സും
ഉൾപ്പെട്ടിട്ടില്ല. റെസല്യൂഷൻ ക്രമം (`src/sse/services/model.ts`-ലെ
`getComboForModel()`):

1. കോംബോയുടെ കൃത്യമായ പേരുമായുള്ള പൊരുത്തം (`model: "my-combo"`),
2. `combo/<name>` പ്രിഫിക്സ് (`model: "combo/my-combo"`),
3. മോഡൽ→കോംബോ ഗ്ലോബ് മാപ്പിങ്ങുകൾ (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

സാധാരണയായി സംഭവിക്കുന്ന രണ്ട് പിഴവുകൾ:

- **`auto` നിങ്ങളുടെ കോംബോകൾ ഉപയോഗിക്കുന്നില്ല.** `auto`/`auto/*` സ്വന്തമായി ഒരു സീറോ-കോൺഫിഗ് കാൻഡിഡേറ്റ് പൂൾ നിർമ്മിക്കുന്നു; കൂടാതെ ഒരു കോംബോയുടെ പേര് അക്ഷരാർഥത്തിൽ `auto` ആണെങ്കിൽ മാത്രമേ നിലനിർത്തിയ കോംബോകൾ പരിശോധിക്കൂ (ശുപാർശ ചെയ്യുന്നില്ല). ഒരു കോംബോയിലൂടെ റൂട്ട് ചെയ്യാൻ അതിന്റെ കൃത്യമായ പേര് അയയ്ക്കുക — `auto` അല്ല.
- **`openrouter/auto` എന്നത് പണം നൽകേണ്ട യഥാർത്ഥ OpenRouter ഉൽപ്പന്നമാണ്** ("Auto Best Available"), OmniRoute അപരനാമമല്ല. OpenRouter രജിസ്ട്രിയിലെ (`open-sse/config/providers/registry/openrouter/index.ts`) ഒരേയൊരു സ്റ്റാറ്റിക് മോഡൽ എൻട്രിയാണിത്; ഇതിന് പ്രത്യേകം ബിൽ ഈടാക്കുകയും ചെയ്യും. `auto` പൂളുകളിൽ നിന്ന് ഇതിനെ ഒഴിവാക്കാൻ ക്രമീകരണങ്ങൾ → റൂട്ടിംഗ് → പണം നൽകേണ്ട മോഡലുകൾ മറയ്ക്കുക ഉപയോഗിക്കുക.

ഇവിടെ രേഖപ്പെടുത്തിയിരിക്കുന്ന യഥാർത്ഥ ആശയക്കുഴപ്പത്തെക്കുറിച്ച് അറിയാൻ [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992), [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) എന്നിവ കാണുക.

## ഇത് എങ്ങനെ പ്രവർത്തിക്കുന്നു (സ്ഥിരമായി സംഭരിക്കുന്ന ഓട്ടോ-കോംബോകൾ)

ഓരോ അഭ്യർത്ഥനയ്ക്കും ഏറ്റവും അനുയോജ്യമായ പ്രൊവൈഡർ/മോഡൽ തിരഞ്ഞെടുക്കാൻ Auto-Combo Engine ഒരു **16-ഘടക സ്കോറിംഗ് ഫംഗ്ഷൻ** (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` എന്നതിൽ നിർവചിച്ചിരിക്കുന്നത്) ഡൈനാമിക്കായി ഉപയോഗിക്കുന്നു. ഡിഫോൾട്ട് ഭാരങ്ങളുടെ ആകെത്തുക `1.0` ആണ്; ഇഷ്ടാനുസൃത ഭാരങ്ങൾ `normalizeScoringWeights()` ഉപയോഗിച്ച് വീണ്ടും നോർമലൈസ് ചെയ്യുന്നു. പതിനാറ് ഘടകങ്ങളിൽ രണ്ടെണ്ണമായ `cacheAffinity`, `resetWindowAffinity` എന്നിവയുടെ ഡിഫോൾട്ട് ഭാരം `0` ആണ്; `reliability`-ന് `DEFAULT_WEIGHTS`-ൽ `0` ആണെങ്കിലും പൊതുവായ പാക്കുകളിൽ `0.03` ഉം `reliability-first`-ൽ `0.04` ഉം ആണ്, കൂടാതെ `quality`-ന് പാക്കുകളിൽ `0.02` (`quality-first`-ൽ `0.03`) ആണ്: എന്നിരുന്നാലും ഓരോ കാൻഡിഡേറ്റിനും ഇവ കണക്കാക്കപ്പെടുന്നു, കൂടാതെ സ്കോറിന് പുറത്ത് പ്രോംപ്റ്റ്-കാഷ് ഡീഡ്യൂപ്ലിക്കേഷൻ `cacheAffinity` നിയന്ത്രിക്കുന്നു. അതിനാൽ, ഡിഫോൾട്ട് ഭാരം പൂജ്യമായ ഘടകങ്ങൾ ഡിഫോൾട്ടായി സ്കോറിൽ സംഭാവന ചെയ്യില്ലെങ്കിലും പാക്കുകളിൽ അവ സംഭാവന ചെയ്യും.

## മോഡ് പാക്കുകൾ

`open-sse/services/autoCombo/modePacks.ts`-ൽ മുൻകൂട്ടി നിർവചിച്ച 6 വെയിറ്റ് പ്രൊഫൈലുകളുണ്ട്. തിരഞ്ഞെടുപ്പ് ഒരു ലക്ഷ്യത്തിലേക്ക് ചായ്ക്കുന്നതിനായി ഓരോ പാക്കും ഡിഫോൾട്ട് വെയിറ്റുകളെ പൂർണ്ണമായും മാറ്റിസ്ഥാപിക്കുന്നു. ഓരോ പാക്കിന്റെയും ആകെത്തുക ഇതിനകംതന്നെ `1.0` ആണ് (നാല് ദശാംശ സ്ഥാനങ്ങളിൽ പ്രിന്റ് ചെയ്യുമ്പോൾ `0.9999`), അതിനാൽ ഒരു പാക്ക് സജീവമായിരിക്കുമ്പോൾ `normalizeScoringWeights()`-ന് അർത്ഥവത്തായി തിരുത്താൻ ഒന്നുമില്ല — റൗണ്ടിങ് പരിഗണിച്ചാൽ, സ്കോറർ പ്രയോഗിക്കുന്ന മൂല്യങ്ങൾ താഴെ നൽകിയിരിക്കുന്നവ തന്നെയാണ്.

- ഓരോ പാക്കിന്റെയും ഊന്നൽ ഒറ്റനോട്ടത്തിൽ:
  - **ship-fast** → latencyInv 0.3048 + health 0.2667 (കുറഞ്ഞ ലേറ്റൻസിയുള്ള, ആരോഗ്യകരമായ കണക്ഷനുകൾ)
  - **cost-saver** → costInv 0.3324 (ഏറ്റവും വിലകുറഞ്ഞ ടോക്കണുകൾ വിജയിക്കുന്നു)
  - **quality-first** → taskFit 0.3524 + stability 0.1429 + quality 0.03, എല്ലാ പാക്കുകളിലും ഏറ്റവും ഉയർന്നത് (ടാസ്കിന് ഏറ്റവും അനുയോജ്യവും സ്ഥിരതയുള്ളതുമായ മോഡൽ)
  - **offline-friendly** → quota 0.3324 + health 0.2667 (വേഗത/ചെലവ് പരിഗണിക്കാതെ പരമാവധി ഹെഡ്റൂം)
  - **reliability-first** → health 0.3524 + stability 0.1905 + reliability 0.04, എല്ലാ പാക്കുകളിലും ഏറ്റവും ഉയർന്നത് (ഏറ്റവും കുറവ് അപ്രതീക്ഷിത സംഭവങ്ങൾ)
  - **chaos-mode** → health 0.4000 + taskFit 0.1905 (ഫോൾട്ട്-ഇൻജക്ഷൻ പ്രൊഫൈൽ)

### ഓരോ അഭ്യർത്ഥനയ്ക്കുമുള്ള നിയന്ത്രണങ്ങൾ (ഹെഡറുകൾ) — #6023 / #6024 / #6025 / #3470

സംഭരിച്ചിരിക്കുന്ന കോംബോ കോൺഫിഗിൽ മാറ്റം വരുത്താതെ, മൂന്ന് ഹെഡറുകൾ വഴി ഓരോ അഭ്യർത്ഥനയ്ക്കും പ്രത്യേകം ഒരു `auto` കോംബോ നിയന്ത്രിക്കാനാകും. ഇവ `auto` സ്ട്രാറ്റജിക്ക് മാത്രവും അവ ഉൾക്കൊള്ളുന്ന അഭ്യർത്ഥനയ്ക്ക് മാത്രവും ബാധകമാണ്; ഹെഡർ ഇല്ലാത്തപ്പോൾ കോംബോയിൽ സേവ് ചെയ്തിരിക്കുന്ന `modePack`/`budgetCap`/`budgetFallback` ഉപയോഗിക്കുന്നു.

## എല്ലാ റൂട്ടിംഗ് തന്ത്രങ്ങളും

OmniRoute-ന്റെ കോംബോ എഞ്ചിൻ **19 റൂട്ടിംഗ് തന്ത്രങ്ങളെ** പിന്തുണയ്ക്കുന്നു (`src/shared/constants/routingStrategies.ts` → `ROUTING_STRATEGY_VALUES` എന്നതിൽ പ്രഖ്യാപിച്ചിരിക്കുന്നു). Auto Combo എഞ്ചിൻ തന്നെ `auto` തന്ത്രത്തിന് കീഴിൽ ലഭ്യമാണ്; മറ്റുള്ളവ സേവ് ചെയ്ത കോംബോകൾക്കായി ലഭ്യമാണ്.

| `cost-optimized`    | കാറ്റലോഗ് വിലനിർണ്ണയത്തിന്റെ അടിസ്ഥാനത്തിൽ ഓരോ അഭ്യർത്ഥനയുടെയും ചെലവ് $ പരമാവധി കുറയ്ക്കുക                                                                                                                                                        |
| `reset-aware` ⭐    | ക്വോട്ട റീസെറ്റ് സമയമനുസരിച്ച് മുൻഗണന നൽകുക — ചെറിയ റീസെറ്റ് വിൻഡോകൾക്ക് ഉയർന്ന റാങ്ക് നൽകുന്നു                                                                                                                                                   |
| `reset-window`      | ക്വോട്ട വിൻഡോ ഏറ്റവും വേഗം റീസെറ്റ് ചെയ്യുന്ന ടാർഗറ്റുകൾക്ക് മുൻഗണന നൽകുക                                                                                                                                                                         |
| `headroom`          | ശേഷിക്കുന്ന ക്വോട്ട ഹെഡ്റൂം ഏറ്റവും കൂടുതലുള്ള ടാർഗറ്റ് തിരഞ്ഞെടുക്കുക                                                                                                                                                                            |
| `strict-random`     | ആവർത്തനങ്ങൾ ഒഴിവാക്കാതെയുള്ള റാൻഡം തിരഞ്ഞെടുപ്പ്                                                                                                                                                                                                  |
| `auto`              | Auto Combo സ്കോറിംഗ് (16 ഘടകങ്ങൾ) ഉപയോഗിക്കുക — **ശുപാർശ ചെയ്യുന്നത്**                                                                                                                                                                            |
| `lkgp`              | Last-Known-Good Path (അവസാനം വിജയിച്ച പ്രൊവൈഡറിലേക്ക് പിന് ചെയ്യുകയും തുടർന്ന് നിയമങ്ങളിലേക്ക് ഫാൾബാക്ക് ചെയ്യുകയും ചെയ്യുന്നു)                                                                                                                   |
| `context-optimized` | നിലവിലെ കോൺടെക്സ്റ്റ് വലുപ്പത്തിന് ഏറ്റവും അനുയോജ്യമായ ടാർഗറ്റ് തിരഞ്ഞെടുക്കുക                                                                                                                                                                    |
| `cache-optimized`   | പ്രോംപ്റ്റ്-കാഷ് അഫിനിറ്റി അനുസരിച്ച് ടാർഗറ്റുകൾ പുനഃക്രമീകരിക്കുക — ഈ അഭ്യർത്ഥനയുടെ കാഷ് ചെയ്ത പ്രിഫിക്സ് ഇതിനകം കൈവശം ഉണ്ടായിരിക്കാൻ ഏറ്റവും സാധ്യതയുള്ള കണക്ഷൻ ആദ്യം പരീക്ഷിക്കുന്നു (`open-sse/services/combo/promptCacheAffinity.ts`, #8008) |
| `fusion` 🧬         | മോഡലുകളുടെ ഒരു പാനലിലേക്ക് സമാന്തരമായി അഭ്യർത്ഥനകൾ അയയ്ക്കുകയും തുടർന്ന് ഒരു ജഡ്ജ് വഴി ഒരൊറ്റ ഉത്തരം സംശ്ലേഷിപ്പിക്കുകയും ചെയ്യുക (താഴെ കാണുക)                                                                                                    |
| `pipeline`          | ഓരോ ഘട്ടത്തിന്റെയും ഔട്ട്പുട്ട് അടുത്ത ഘട്ടത്തിന്റെ ഇൻപുട്ടിലേക്ക് കൈമാറിക്കൊണ്ട് ടാർഗറ്റുകൾ ക്രമാനുഗതമായി പ്രവർത്തിപ്പിക്കുക; അന്തിമ ഉത്തരം മാത്രം തിരികെ നൽകുന്നു (#6396)                                                                       |

### `weighted`-ന്റെ പ്രവർത്തനരീതി

`weighted` എന്നത് **ഓരോ അഭ്യർത്ഥനയ്ക്കുമുള്ള ആനുപാതിക റാൻഡം തിരഞ്ഞെടുപ്പാണ്**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), ഒരു സമീകരണ സംവിധാനമല്ല:

- ഓരോ അഭ്യർത്ഥനയും `weight / totalWeight` സാധ്യതയോടെ **ഒരു** ഘട്ടം തിരഞ്ഞെടുക്കുന്നു; ശേഷിക്കുന്ന ഘട്ടങ്ങൾ
  ആ അഭ്യർത്ഥനയ്ക്കുള്ള ഫാൾബാക്ക് ശൃംഖലയായി വെയ്റ്റിന്റെ അവരോഹണക്രമത്തിൽ ക്രമീകരിക്കുന്നു.
- വെയ്റ്റ് `0` ആയ (അല്ലെങ്കിൽ വെയ്റ്റ് ഇല്ലാത്ത) ഒരു ഘട്ടം, മറ്റേതെങ്കിലും ഘട്ടത്തിന്
  വെയ്റ്റ് > 0 ഉള്ളിടത്തോളം **ഒരിക്കലും തിരഞ്ഞെടുക്കപ്പെടില്ല** — തിരഞ്ഞെടുത്ത ഘട്ടം പരാജയപ്പെട്ടതിന് ശേഷം മാത്രമേ അതിന് ഫാൾബാക്കായി പ്രവർത്തിക്കാനാകൂ. **എല്ലാ**
  വെയ്റ്റുകളും 0 ആയിരിക്കുമ്പോൾ മാത്രമാണ് തിരഞ്ഞെടുപ്പ് ഏകസമമാകുന്നത്.
- എല്ലാ ടാർഗറ്റുകളും ലഭ്യമല്ലാത്ത ഘട്ടങ്ങൾ — പ്രൊവൈഡർ സർക്യൂട്ട് ബ്രേക്കർ `OPEN`, കണക്ഷൻ
  കൂൾഡൗൺ, മോഡൽ ലോക്കൗട്ട് — തിരഞ്ഞെടുപ്പ് നടക്കുന്നതിന് മുമ്പ് അതിൽനിന്ന് നീക്കം ചെയ്യപ്പെടുന്നു
  (`open-sse/services/combo/targetResolution.ts`), അതിനാൽ ആരോഗ്യകരമായ ഒരൊറ്റ ഘട്ടത്തിന് താൽക്കാലികമായി
  എല്ലാ അഭ്യർത്ഥനകളും ലഭിക്കാം.
- `stickyWeightedLimit` (കോംബോ കോൺഫിഗ്, ഡിഫോൾട്ട് `1` = പ്രവർത്തനരഹിതം) വീണ്ടും തിരഞ്ഞെടുക്കുന്നതിന് മുമ്പ്, തിരഞ്ഞെടുത്ത ഘട്ടത്തെ അത്രയും
  തുടർച്ചയായ വിജയങ്ങൾക്കായി പിന് ചെയ്യുന്നു.

കർശനമായ റൊട്ടേഷനായി `round-robin` ഉപയോഗിക്കുക; `weighted`-ലെ തുല്യ വെയ്റ്റുകൾ നൽകുന്നത് സ്ഥിതിവിവരശാസ്ത്രപരമായ ബാലൻസാണ് —
കർശനമായ ബാലൻസല്ല.

## ഫ്യൂഷൻ തന്ത്രം

ഒരൊറ്റ ലക്ഷ്യം തിരഞ്ഞെടുക്കാത്ത ഏക തന്ത്രമാണ് `fusion`. ഇത് പ്രോംപ്റ്റ്
**എല്ലാ പാനൽ മോഡലുകളിലേക്കും സമാന്തരമായി** അയയ്ക്കുന്നു, തുടർന്ന് ക്രമീകരിക്കാവുന്ന ഒരു **വിധികർത്തൃ മോഡൽ**
എല്ലാ പാനൽ പ്രതികരണങ്ങളിൽനിന്നും ഒരൊറ്റ അന്തിമ ഉത്തരം സംശ്ലേഷിപ്പിക്കുന്നു. അപ്സ്ട്രീം `decolua/9router`-ൽ
നിന്ന് പോർട്ട് ചെയ്തതാണ് (OpenRouter-ന്റെ Fusion രൂപകൽപ്പന); ഇംപ്ലിമെന്റേഷൻ `open-sse/services/fusion.ts`-ൽ.

ഇത് പ്രവർത്തിക്കുന്ന വിധം:

0. **ടൂളുകൾ ഉൾപ്പെട്ട അഭ്യർത്ഥനകളുടെ ബൈപാസ്** — ശൂന്യമല്ലാത്ത `tools` അറേയും
   വ്യക്തമായി `"none"` ആയി സജ്ജീകരിക്കാത്ത `tool_choice`-ഉം ഉള്ള അഭ്യർത്ഥന പാനൽ പൂർണ്ണമായും ഒഴിവാക്കുന്നു:
   മാറ്റമൊന്നും വരുത്താതെ `tools`/`tool_choice` കൈമാറിക്കൊണ്ട് അത് നേരിട്ട്
   ഒരൊറ്റ മോഡലിലേക്കാണ് (ക്രമീകരിച്ച വിധികർത്താവ്, അല്ലെങ്കിൽ `panel[0]`) റൂട്ട് ചെയ്യുന്നത്.
   പാനൽ അംഗങ്ങൾക്ക് ടൂൾ ആക്സസ് ഇല്ല; വിധികർത്താവിന്റെ സംശ്ലേഷണ നിർദ്ദേശം
   ടൂൾ-കോൾ പുറപ്പെടുവിക്കുന്നത് നിരുത്സാഹപ്പെടുത്തുകയും ചെയ്യുന്നു. അതിനാൽ ഏജന്റിക്/ടൂൾ-കോളിംഗ് ക്ലയന്റുകൾക്ക്
   സംശ്ലേഷിപ്പിച്ച ഗദ്യത്തിനുപകരം യഥാർഥ ടൂൾ-കോൾ തീരുമാനം ലഭിക്കുന്നു (#6771).
1. **ഫാൻ-ഔട്ട്** (ടൂളുകൾ ഉൾപ്പെടാത്ത അഭ്യർത്ഥനകൾക്ക് മാത്രം) — പ്രോംപ്റ്റ് എല്ലാ പാനൽ
   മോഡലുകളിലേക്കും ഒരേസമയം അയയ്ക്കുന്നു; ടൂളുകൾ നീക്കംചെയ്ത് നോൺ-സ്ട്രീമിംഗ് നിർബന്ധിതമാക്കുന്നു (സംശ്ലേഷണത്തിനായി
   വിധികർത്താവിന് പൂർണ്ണമായ ഗദ്യം ആവശ്യമാണ്).
2. **ക്വാറം-ഗ്രേസ് ശേഖരണം** — `minPanel` ഉത്തരങ്ങൾ ലഭിച്ച ഉടൻ, വൈകിയെത്തുന്നവയ്ക്കായി ഒരു ചെറിയ ഗ്രേസ്
   ടൈമർ ആരംഭിക്കുന്നു; തുടർന്ന് ശേഖരിച്ചതെല്ലാം ഉപയോഗിച്ച് ഫ്യൂഷൻ തുടരുന്നു.
   ഒരു ഹാർഡ് ടൈമൗട്ടിനുള്ളിൽ, ഏറ്റവും വേഗം കുറഞ്ഞ മോഡൽ ആകെ സമയത്തിൽ വരുത്തുന്ന കാലതാമസം ഇത് പരിമിതപ്പെടുത്തുന്നു.
3. **വിധികർത്തൃ സംശ്ലേഷണം** — പാനൽ ഉത്തരങ്ങൾ അജ്ഞാതമാക്കുന്നു (`Source 1`, `Source 2`, … — അതിനാൽ
   വിധികർത്താവ് മോഡൽ ബ്രാൻഡിനല്ല, ഉള്ളടക്കത്തിനാണ് പ്രാധാന്യം നൽകുന്നത്), തുടർന്ന് അവ വിധികർത്താവിന് കൈമാറുന്നു.
   വിധികർത്താവ് സമവായം / വൈരുധ്യങ്ങൾ / ഭാഗികമായ വിഷയാവരണം / സവിശേഷ ഉൾക്കാഴ്ചകൾ / ശ്രദ്ധയിൽപ്പെടാത്ത വശങ്ങൾ എന്നിവ
   വിശകലനംചെയ്ത് **ഒരൊറ്റ** ആധികാരിക ഉത്തരം എഴുതുന്നു. വിധികർത്തൃ കോൾ ക്ലയന്റിന്റെ യഥാർഥ
   `stream` ഫ്ലാഗും ടൂളുകളും നിലനിർത്തുന്നതിനാൽ, സ്ട്രീമിംഗും തുടർന്നുള്ള ടൂൾ ഉപയോഗവും പ്രവർത്തിച്ചുകൊണ്ടിരിക്കും.
4. **സുഗമമായ ഡീഗ്രഡേഷൻ** — 0 പാനൽ ഉത്തരങ്ങൾ → `503`; കൃത്യമായി 1 ഉത്തരം മാത്രം ലഭിച്ചാൽ → ആ ഉത്തരം
   നേരിട്ട് നൽകുന്നു (ഫ്യൂസ് ചെയ്യാൻ ഒന്നുമില്ല); ഒറ്റ മോഡലുള്ള പാനൽ നേരിട്ട് ഉത്തരം നൽകുന്നു.

ഒരു പാനൽ അംഗത്തിന് മറ്റൊരു കോംബോയെ റഫർ ചെയ്യുന്ന ഒരു `combo-ref` ഘട്ടവുമാകാം
(`{kind: "combo-ref", comboName: "..."}`). ഇത് **ഒരൊറ്റ ബ്ലാക്ക്-ബോക്സ് പാനൽ ശബ്ദമായി** പരിഹരിക്കപ്പെടുന്നു
(ആ കോംബോയുടെ സ്വന്തം ലക്ഷ്യങ്ങളിലേക്കുള്ള ഫാൻ-ഔട്ട് അല്ല, മറിച്ച് റഫർ ചെയ്ത കോംബോയിലേക്കുള്ള സമ്പൂർണ്ണ റിക്കഴ്സീവ് ഡിസ്പാച്ച്);
മറ്റെല്ലാ combo-ref ഉപയോഗിക്കുന്ന തന്ത്രങ്ങളും ഇതിനകം ഉപയോഗിക്കുന്ന അതേ ഡെപ്ത്/സൈക്കിൾ പരിരക്ഷയോടെയാണിത് (#6764).

### ക്രമീകരണം

കോംബോയുടെ `config` ബ്ലോബിലാണ് ക്രമീകരിക്കുന്നത് (സ്കീമ മൈഗ്രേഷൻ ആവശ്യമില്ല — നിലവിലുള്ള
`combos` പട്ടിക വീണ്ടും ഉപയോഗിക്കുന്നു):

| ഫീൽഡ്                                    | തരം      | ഡിഫോൾട്ട്      | ഉദ്ദേശ്യം                                                                                                             |
| :--------------------------------------- | :------- | :------------- | :-------------------------------------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | ആദ്യ പാനൽ മോഡൽ | അന്തിമ ഉത്തരം സംശ്ലേഷിപ്പിക്കുന്ന മോഡൽ                                                                                |
| `config.fusionTuning.minPanel`           | `number` | `2`            | ഗ്രേസ് ടൈമർ ആരംഭിക്കുന്നതിനുമുമ്പ് ആവശ്യമായ വിജയകരമായ ഉത്തരങ്ങൾ (`[2, panelSize]` പരിധിയിലേക്ക് പരിമിതപ്പെടുത്തുന്നു) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`         | ക്വാറം ലഭിച്ചശേഷം വൈകിയെത്തുന്നവയ്ക്കായി കാത്തിരിക്കേണ്ട സമയം                                                         |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`        | പ്രതികരിക്കാതെ നിൽക്കുന്ന ഒരു മോഡൽ അഭ്യർത്ഥന തടഞ്ഞുവയ്ക്കാതിരിക്കാനുള്ള പരമാവധി സമയപരിധി                              |

ഡിഫോൾട്ടുകൾ `FUSION_DEFAULTS`-ൽ (`open-sse/services/fusion.ts`) ലഭ്യമാണ്.

## വെർച്വൽ ഓട്ടോ-കോംബോ ഫാക്ടറി

Auto Combo എഞ്ചിന് മുൻകൂട്ടി നിർവചിച്ച കോംബോകൾ ആവശ്യമില്ല. പകരം, `open-sse/services/autoCombo/virtualFactory.ts` ആവശ്യാനുസരണം സ്ഥാനാർഥികളെ നിർമ്മിക്കുന്നു:

1. `getProviderConnections({ isActive: true })` ലഭ്യമാക്കുന്നു (പ്രവർത്തനക്ഷമമാക്കിയ എല്ലാ കണക്ഷനുകളും)
2. സാധുവായ ക്രെഡൻഷ്യലുകളുള്ളവ മാത്രം ഫിൽട്ടർ ചെയ്യുന്നു (API കീ അല്ലെങ്കിൽ `hasUsableOAuthToken()` വഴിയുള്ള കാലാവധി കഴിയാത്ത OAuth ടോക്കൺ)
3. മോഡൽ ലഭ്യതയും വിലനിർണ്ണയവും കണ്ടെത്താൻ `getProviderRegistry()`-യുമായി ക്രോസ്-റഫറൻസ് ചെയ്യുന്നു
4. ഓരോ `(provider, model, connection)` ട്യൂപ്പിളിനും ഒരു `VirtualAutoComboCandidate` നിർമ്മിക്കുന്നു
5. ഡിസ്പാച്ച് ലക്ഷ്യമായി `connection.defaultModel` (അല്ലെങ്കിൽ രജിസ്ട്രിയിലെ ആദ്യ മോഡൽ) തിരഞ്ഞെടുക്കുന്നു
6. 16 ഘടകങ്ങളുള്ള `scorePool()`-ഉം വേരിയന്റിന്റെ വെയ്റ്റ് പാക്കും ഉപയോഗിച്ച് ഓരോ സ്ഥാനാർഥിക്കും സ്കോർ നൽകുന്നു
7. `handleComboChat()`-നായി ലഭിക്കുന്ന ഇൻ-മെമ്മറി `AutoComboConfig` തിരികെ നൽകുന്നു — ഇത് ഒരിക്കലും DB-യിൽ സ്ഥിരമായി സംഭരിക്കപ്പെടുന്നില്ല

ഇതിനർത്ഥം **`auto/*` പ്രവർത്തനക്ഷമമാക്കിയ ഒരു പുതിയ പ്രൊവൈഡറെ ചേർക്കുന്നത് സ്ഥാനാർഥി പൂളിനെ സ്വയമേവ വിപുലീകരിക്കുന്നു** എന്നാണ് — കോംബോ സ്വമേധയാ എഡിറ്റ് ചെയ്യേണ്ടതില്ല. ഓരോ അഭ്യർത്ഥനയ്ക്കും വെർച്വൽ കോംബോ പുനർനിർമ്മിക്കുന്നതിനാൽ, പുതുതായി ചേർത്തതോ പുതുതായി ആരോഗ്യകരമായതോ ആയ കണക്ഷനുകൾ ഉടൻ തിരഞ്ഞെടുക്കപ്പെടും.

## സ്വയം പരിഹരിക്കൽ

- **താൽക്കാലിക ഒഴിവാക്കൽ**: സ്കോർ < 0.2 → 5 മിനിറ്റേക്ക് ഒഴിവാക്കുന്നു (ക്രമാനുഗത ബാക്ക്ഓഫ്, പരമാവധി 30 മിനിറ്റ്)
- **സർക്യൂട്ട് ബ്രേക്കർ അവബോധം**: OPEN → സ്വയമേവ ഒഴിവാക്കുന്നു; HALF_OPEN → പ്രോബ് അഭ്യർത്ഥനകൾ
- **ഇൻസിഡന്റ് മോഡ്**: >50% OPEN → പര്യവേക്ഷണം പ്രവർത്തനരഹിതമാക്കി സ്ഥിരത പരമാവധിയാക്കുന്നു
- **കൂൾഡൗൺ വീണ്ടെടുക്കൽ**: ഒഴിവാക്കലിനുശേഷമുള്ള ആദ്യ അഭ്യർത്ഥന കുറഞ്ഞ ടൈംഔട്ടുള്ള ഒരു "പ്രോബ്" ആയിരിക്കും

## ബാൻഡിറ്റ് പര്യവേക്ഷണം

അഭ്യർത്ഥനകളിൽ 5% (ക്രമീകരിക്കാവുന്നത്) പര്യവേക്ഷണത്തിനായി ക്രമരഹിത പ്രൊവൈഡറുകളിലേക്ക് റൂട്ട് ചെയ്യപ്പെടുന്നു. ഇൻസിഡന്റ് മോഡിൽ ഇത് പ്രവർത്തനരഹിതമാണ്.

## API

**പ്രത്യേകമായ `POST /api/combos/auto` എൻഡ്പോയിന്റ് ഇല്ല** — Auto-Combo രണ്ട് രീതികളിലാണ് ഉപയോഗിക്കുന്നത്:

1. **സീറോ-കോൺഫിഗ് (ശുപാർശ ചെയ്യുന്നത്):** `model: "auto"` അല്ലെങ്കിൽ `model: "auto/<variant>"` ഉപയോഗിച്ച് ഏതെങ്കിലും ചാറ്റ് കംപ്ലീഷൻ അഭ്യർത്ഥന അയയ്ക്കുക. ഓരോ അഭ്യർത്ഥനയ്ക്കും വെർച്വൽ ഫാക്ടറി കോംബോ നിർമ്മിക്കുന്നു — സ്ഥിരസംഭരണമോ API കോളുകളോ ആവശ്യമില്ല.

2. **`strategy: "auto"` ഉപയോഗിച്ചുള്ള സ്ഥിരമായി സംഭരിച്ച കോംബോ:** `POST /api/combos` വഴി ഒരു സാധാരണ കോംബോ സൃഷ്ടിച്ച്, `strategy: "auto"` എന്നതിനൊപ്പം `config.auto.weights` / `config.auto.candidatePool` സജ്ജമാക്കുക. അതേ സ്കോറിംഗ് എഞ്ചിനാണ് ഉപയോഗിക്കുന്നത്; കോംബോ `combos`-ൽ സംഭരിക്കപ്പെടുകയും ID ഉപയോഗിച്ച് വീണ്ടും ഉപയോഗിക്കാനാവുകയും ചെയ്യും.

കണ്ടെത്തലിനായി, `GET /api/combos/auto` ഓരോ വേരിയന്റിനെയും അതിന്റെ പരിഹരിച്ച സ്ഥാനാർഥി പൂളിനൊപ്പം `context_length` / `max_output_tokens` എന്നിവയും ചേർത്ത് പട്ടികപ്പെടുത്തുന്നു — ഇവ സ്ഥാനാർഥി പൂളിലെ വിൻഡോകളിലെ MAX മൂല്യങ്ങളാണ്. ക്ലയന്റുകൾ (ഉദാ. opencode പ്ലഗിൻ) `0`-ന് പകരം ഈ മൂല്യങ്ങൾ പ്രസിദ്ധീകരിക്കണം: സീറോ കോൺടെക്സ്റ്റ് opencode-ന്റെ ഓട്ടോ-കോംപാക്ഷൻ പൂർണ്ണമായി പ്രവർത്തനരഹിതമാക്കുന്നു; അതിനാൽ ഗേറ്റ്വേയുടെ ഹിസ്റ്ററി പർജ് കോൺടെക്സ്റ്റ് നശിപ്പിക്കുന്നതുവരെ സെഷനുകൾ വളരും. MAX പ്രസിദ്ധീകരിക്കുന്നത് സുരക്ഷിതമാണ്, കാരണം auto-combo കോൺടെക്സ്റ്റ് പ്രീ-ഫിൽട്ടർ അമിത വലുപ്പമുള്ള അഭ്യർത്ഥനകളെ വലിയ വിൻഡോയുള്ള സ്ഥാനാർഥികളിലേക്ക് റൂട്ട് ചെയ്യുന്നു.

```bash
# സീറോ-കോൺഫിഗ് ഉപയോഗം (കോംബോ സൃഷ്ടിക്കേണ്ടതില്ല)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# സാധാരണ combos എൻഡ്പോയിന്റ് വഴിയുള്ള സ്ഥിരമായി സംഭരിച്ച auto combo
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### ഓട്ടോ റൂട്ടർ തന്ത്രങ്ങൾ

സ്ഥിരമായി സംഭരിച്ച `strategy: "auto"` കോംബോകൾക്ക് `config.routerStrategy` (അല്ലെങ്കിൽ പഴയ
`config.auto.routerStrategy`) ഇനിപ്പറയുന്നവയിൽ ഒന്നായി സജ്ജമാക്കാം:

- `rules` — ഡിഫോൾട്ട് വെയ്റ്റഡ് സ്കോറിംഗ്
- `score` — ക്രമീകരിച്ചിട്ടുള്ള ഏറ്റവും ഉയർന്ന വെയ്റ്റഡ് സ്കോർ തിരഞ്ഞെടുക്കുന്നു. കൃത്യമായ ടൈ സംഭവിച്ചാൽ ക്രമീകരിച്ചിട്ടുള്ള
  സ്ഥാനാർഥി ക്രമം നിലനിർത്തും; നിലവിലുള്ള `explorationRate` പൂർണ്ണ റാങ്ക് ചെയ്ത പൂളിൽനിന്ന് സാമ്പിൾ ചെയ്യുന്നു.
- `cost` / `eco` — ഏറ്റവും ചെലവ് കുറഞ്ഞ ആരോഗ്യകരമായ പ്രൊവൈഡർ
- `latency` / `fast` — വിശ്വാസ്യതാ പിഴയോടുകൂടിയ ഏറ്റവും കുറഞ്ഞ p95 ലേറ്റൻസി
- `sla-aware` / `sla` — p95 ലേറ്റൻസി, പിശക് നിരക്ക്, ഐച്ഛിക
  ചെലവ് SLO-കൾ എന്നിവ പാലിക്കുന്ന സ്ഥാനാർഥികൾക്ക് മുൻഗണന നൽകുന്നു
- `lkgp` — അവസാനം നല്ല നിലയിൽ അറിയപ്പെട്ട പ്രൊവൈഡർ ആദ്യം

### റൂട്ടർ തന്ത്രങ്ങൾ വിശദമായി

Auto-combo എഞ്ചിൻ പ്ലഗ് ചെയ്യാവുന്ന 6 **RouterStrategy** ഇംപ്ലിമെന്റേഷനുകൾ നൽകുന്നു; അവ
`config.routerStrategy` (അല്ലെങ്കിൽ പഴയ `config.auto.routerStrategy`) വഴി മാറ്റിവയ്ക്കാം.
ഒരു `RoutingContext` (ടാസ്ക് തരം, ടൂൾ/വിഷൻ സൂചനകൾ, ടോക്കൺ എസ്റ്റിമേറ്റ്, ഐച്ഛിക SLA പോളിസി, ഐച്ഛികമായി
അവസാനം നല്ല നിലയിൽ അറിയപ്പെട്ട പ്രൊവൈഡർ) നൽകിയാൽ, ഓരോ തന്ത്രവും സ്ഥാനാർഥി പൂളിൽനിന്ന് ഒരു പ്രൊവൈഡറെ തിരഞ്ഞെടുക്കുന്നു.

#### 1. `rules` (ഡിഫോൾട്ട്) — 16 ഘടകങ്ങളുള്ള വെയ്റ്റഡ് സ്കോറിംഗ്

നിലവിലുള്ള സ്കോറിംഗ് എഞ്ചിനെ റാപ് ചെയ്യുന്നു. `OPEN` സർക്യൂട്ട് ബ്രേക്കർ
സ്ഥാനാർഥികളെ ഫിൽട്ടർ ചെയ്തശേഷം, നിലവിലെ ടാസ്ക് തരവും `getTaskFitness()`-ഉം ഉപയോഗിച്ച് `scorePool()`
പ്രവർത്തിപ്പിച്ച് ഏറ്റവും ഉയർന്ന സ്കോറുള്ള പ്രൊവൈഡറെ തിരഞ്ഞെടുക്കുന്നു.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**എപ്പോൾ ഉപയോഗിക്കണം**: ഡിഫോൾട്ടായി. എല്ലാ സിഗ്നലുകളും പരിഗണിച്ചുള്ള സന്തുലിതമായ വിട്ടുവീഴ്ച ആവശ്യമുള്ളപ്പോൾ ഉപയോഗിക്കുക.

**അപരനാമം**: `rules` (അപരനാമമില്ല)

---

#### 2. `cost` / `eco` — ഏറ്റവും ചെലവ് കുറഞ്ഞ ആരോഗ്യകരമായ പ്രൊവൈഡർ

സ്ഥാനാർഥി പൂളിനെ `costPer1MTokens` അനുസരിച്ച് (ആരോഹണക്രമത്തിൽ) ക്രമീകരിച്ച് ഏറ്റവും ചെലവ് കുറഞ്ഞത് തിരഞ്ഞെടുക്കുന്നു.
ആദ്യം `OPEN` സ്ഥാനാർഥികളെ ഫിൽട്ടർ ചെയ്യുന്നു.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**എപ്പോൾ ഉപയോഗിക്കണം**: ചെലവ്-സെൻസിറ്റീവായ വർക്ക്ലോഡുകൾ, ബാച്ച് പ്രോസസ്സിംഗ്, അല്ലെങ്കിൽ പശ്ചാത്തല ജോലികൾ.

**അപരനാമങ്ങൾ**: `cost`, `eco`

---

#### 3. `latency` / `fast` — വിശ്വാസ്യതാ പിഴയോടുകൂടിയ ഏറ്റവും കുറഞ്ഞ p95 ലേറ്റൻസി

`p95LatencyMs + (errorRate * 1000)` അനുസരിച്ച് ക്രമീകരിക്കുന്നു. നാമമാത്ര ലേറ്റൻസി കുറവാണെങ്കിലും
വിശ്വാസ്യത കുറഞ്ഞ പ്രൊവൈഡറുകൾ താഴ്ന്ന റാങ്കിലാകുമെന്ന് പിശക്-നിരക്ക് പിഴ ഉറപ്പാക്കുന്നു.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**എപ്പോൾ ഉപയോഗിക്കണം**: തത്സമയ ചാറ്റ്, ഓട്ടോകംപ്ലീറ്റ്, അല്ലെങ്കിൽ
ഇന്ററാക്ടീവ് കോഡിംഗ് അസിസ്റ്റന്റുകൾ പോലുള്ള ലേറ്റൻസി-സെൻസിറ്റീവായ വർക്ക്ലോഡുകൾ.

**അപരനാമങ്ങൾ**: `latency`, `fast`

#### 4. `sla-aware` / `sla` — ലേറ്റൻസി/പിശക്/ചെലവ് SLO പാലനം

ക്രമീകരിച്ചിട്ടുള്ള SLO പോളിസി എത്ര നന്നായി പാലിക്കുന്നു എന്നതിന്റെ അടിസ്ഥാനത്തിൽ ഓരോ സ്ഥാനാർഥിക്കും സ്കോർ നൽകുന്നു:

| ഘടകം           | ഭാരം | ഫോർമുല                                                   |
| -------------- | ---- | -------------------------------------------------------- |
| ലേറ്റൻസി സ്കോർ | 35%  | `threshold / max(value, ε)`                              |
| പിശക് സ്കോർ    | 35%  | `threshold / max(value, ε)`                              |
| ആരോഗ്യ സ്കോർ   | 15%  | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)        |
| ചെലവ് സ്കോർ    | 10%  | `threshold / max(value, ε)` അല്ലെങ്കിൽ വിപരീത നോർമലൈസ്ഡ് |
| സ്ഥിരതാ സ്കോർ  | 5%   | വിപരീത നോർമലൈസ്ഡ് ലേറ്റൻസി സ്റ്റാൻഡേർഡ് ഡീവിയേഷൻ         |

`hardConstraints: true` ആയിരിക്കുമ്പോൾ, സ്ഥാനാർഥികളെ പ്രധാനമായും **ലംഘന സ്കോർ**
(അവർ ഏതെങ്കിലും SLO എത്രത്തോളം മറികടക്കുന്നു എന്നത്), തുടർന്ന് കോമ്പോസിറ്റ് സ്കോർ എന്നിവ അനുസരിച്ച് ക്രമീകരിക്കുന്നു. അല്ലാത്തപക്ഷം,
കോമ്പോസിറ്റ് സ്കോർ മാത്രം ഉപയോഗിക്കുന്നു.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // പോളിസിക്കെതിരെ ഓരോ സ്ഥാനാർഥിക്കും സ്കോർ നൽകുന്നു: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA ഫീൽഡുകൾ** (കോംബോ കോൺഫിഗിൽ സജ്ജമാക്കുക):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**എപ്പോൾ ഉപയോഗിക്കണം**: കർശനമായ ലേറ്റൻസി, പിശക്-നിരക്ക്, അല്ലെങ്കിൽ ചെലവ് ബജറ്റുകളുള്ള പ്രൊഡക്ഷൻ വർക്ക്ലോഡുകൾ.

**അപരനാമങ്ങൾ**: `sla-aware`, `sla`

#### 5. `lkgp` — അവസാനം നല്ല നിലയിൽ അറിയപ്പെട്ട പ്രൊവൈഡർ ആദ്യം

**അവസാനം നല്ല നിലയിൽ അറിയപ്പെട്ട പ്രൊവൈഡർ** സജ്ജമാക്കിയിട്ടുണ്ടെങ്കിൽ ആദ്യം അതിനെ പരീക്ഷിക്കുന്നു, തുടർന്ന്
`rules` തന്ത്രത്തിലേക്ക് ഫാൾബാക്ക് ചെയ്യുന്നു. സെഷൻ സ്റ്റിക്കിനസിന് ഇത് ഉപകാരപ്രദമാണ് — ഒരു സംഭാഷണത്തിലെ
തുടർ അഭ്യർത്ഥനകൾ അതേ പ്രൊവൈഡർ കൈകാര്യം ചെയ്യും.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // rules തന്ത്രത്തിലേക്ക് ഫാൾബാക്ക് ചെയ്യുന്നു
    return getStrategy("rules").select(pool, context);
  }
}
```

**എപ്പോൾ ഉപയോഗിക്കണം**: തുടർ അഭ്യർത്ഥനകൾ അതേ പ്രൊവൈഡർ കൈകാര്യം ചെയ്യണമെന്ന് ആഗ്രഹിക്കുന്ന
മൾട്ടി-ടേൺ സംഭാഷണങ്ങൾ (ഉദാ., കാഷിംഗ്, കോൺടെക്സ്റ്റ് തുടർച്ച, അല്ലെങ്കിൽ വിലനിർണ്ണയ സ്ഥിരതയ്ക്കായി).

**അപരനാമം**: `lkgp` (അപരനാമമില്ല)

### കസ്റ്റം റൂട്ടർ തന്ത്രങ്ങൾ

പബ്ലിക് API വഴി നിങ്ങളുടെ സ്വന്തം `RouterStrategy` ഇംപ്ലിമെന്റേഷൻ രജിസ്റ്റർ ചെയ്യാം:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // നിങ്ങളുടെ റൂട്ടിംഗ് ലോജിക് ഇവിടെ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

തുടർന്ന് അത് ഉപയോഗിക്കുക:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

| ഉപയോഗ സാഹചര്യം         | തന്ത്രം     | കാരണം                                                        |

| ചെലവ് കുറയ്ക്കുക       | `cost`      | എല്ലായ്പ്പോഴും ഏറ്റവും ചെലവ് കുറഞ്ഞത് തിരഞ്ഞെടുക്കുന്നു      |
| ലേറ്റൻസി കുറയ്ക്കുക    | `latency`   | ഏറ്റവും വേഗമേറിയ വിശ്വാസയോഗ്യമായ പ്രൊവൈഡറെ തിരഞ്ഞെടുക്കുന്നു |
| കർശനമായ SLO-കൾ         | `sla-aware` | p95/പിശക്/ചെലവ് ത്രെഷോൾഡുകൾ അനുസരിച്ച് ഫിൽട്ടർ ചെയ്യുന്നു    |
| മൾട്ടി-ടേൺ ചാറ്റ്      | `lkgp`      | സെഷൻ സ്റ്റിക്കിനസ്                                           |

## ടാസ്ക് അനുയോജ്യത

6 ടാസ്ക് തരങ്ങളിലായി (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) 30-ലധികം മോഡലുകൾക്ക് സ്കോർ നൽകിയിരിക്കുന്നു. വൈൽഡ്കാർഡ് പാറ്റേണുകൾ പിന്തുണയ്ക്കുന്നു (ഉദാ., `*-coder` → ഉയർന്ന കോഡിംഗ് സ്കോർ).

## Auto വേരിയന്റുകളുടെ സംഗ്രഹം

അടിസ്ഥാന `auto` (ഡിഫോൾട്ട്) കൂടാതെ `autoPrefix.ts`-ൽ പ്രഖ്യാപിച്ചിരിക്കുന്ന 6 `AutoVariant` മൂല്യങ്ങളും ഉൾപ്പെടെ, **പ്രവർത്തിപ്പിക്കാവുന്ന 7 മോഡൽ ID-കൾ** ഉണ്ട്:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` തന്നെ 6 മൂല്യങ്ങളാണ് ഉൾക്കൊള്ളുന്നത്; ഏഴാമത്തെ ഓപ്ഷൻ "വേരിയന്റ് ഇല്ല" എന്നതാണ് — അടിസ്ഥാന `auto` — ഇത് `parseAutoPrefix()` വഴി `variant: undefined` ആയി കൈകാര്യം ചെയ്യപ്പെടുന്നു.)

## ടയറുകൾ Auto-Combo-യിൽ എങ്ങനെ ഉൾപ്പെടുന്നു

16-ഘടക സ്കോറിംഗ് ഫങ്ഷൻ (`open-sse/services/autoCombo/scoring.ts`) ടയർ
അംഗത്വത്തെ രണ്ട് സിഗ്നലുകളായി കണക്കാക്കുന്നു: `tierPriority` (0.0476), `tierAffinity` (0.0476). പൂർണ്ണമായ
`DEFAULT_WEIGHTS` സെറ്റിനായി മുകളിലുള്ള പ്രാമാണിക [സ്കോറിംഗ് ഘടക പട്ടിക](#how-it-works-persisted-auto-combos) കാണുക —
ഓരോ പാക്കിനുമുള്ള ഓവർറൈഡുകൾ (ship-fast/cost-saver/quality-first/
offline-friendly) "ഓരോ പാക്കിനുമുള്ള വെയ്റ്റ് പ്രൊഫൈലുകൾ" പട്ടികയിൽ നൽകിയിരിക്കുന്നു.

ടയർ മാത്രം **Tier 1-നെ ആദ്യം തിരഞ്ഞെടുക്കാൻ നിർബന്ധിക്കില്ല** — Tier 1-ന്റെ ലേറ്റൻസി മോശമാണെങ്കിലോ
ചെലവ്-ഗുണനിലവാര അനുപാതം അനുയോജ്യമല്ലെങ്കിലോ, Tier 2 വിജയിക്കും. ടയർ ക്രമം നിർബന്ധമാക്കാൻ, കോംബോ
സ്ട്രാറ്റജി `priority` ഉപയോഗിച്ച് ദാതാക്കളെ ടയർ അനുസരിച്ച് ക്രമീകരിക്കുക.

Tier 1-ന് (സബ്സ്ക്രിപ്ഷൻ) ശക്തമായ മുൻഗണന നൽകാൻ, `tierPriority` വെയ്റ്റ് വർധിപ്പിക്കുക:

```json
{
  "strategy": "auto",
```

## ടെസ്റ്റിംഗും കവറേജും

### നിർണായക റൂട്ടിംഗ്-ഡിസിഷൻ മാട്രിക്സ് (`npm run test:combo:matrix`)

മോക്ക് ചെയ്ത അപ്സ്ട്രീം ഉപയോഗിച്ച് യഥാർഥ കോംബോ പൈപ്പ്ലൈനിലൂടെ എല്ലാ 19 പൊതു
സ്ട്രാറ്റജികളുടെയും റൂട്ടിംഗ് **തീരുമാനം** എൻഡ്-ടു-എൻഡ് രീതിയിൽ `tests/integration/combo-matrix/*.test.ts` തെളിയിക്കുന്നു.
കവറേജിൽ ഉൾപ്പെടുന്നവ:

- എല്ലാ 19 `ROUTING_STRATEGY_VALUES` സ്ട്രാറ്റജികളും (ordered, weighted, cost, context, fusion, …).
- `quota-share` (ആന്തരികം) എൻഡ്-ടു-എൻഡ്: യഥാർഥ `selectQuotaShareTarget` സീം (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`) വഴിയുള്ള DRR നീതിപൂർണതയും സാച്ചുറേഷൻ ഡീപ്രയോറിറ്റൈസേഷനും.
- എല്ലാ ടാർഗറ്റ് എണ്ണങ്ങളിലുമുള്ള `context-relay` യൂണിവേഴ്സൽ-ഹാൻഡോഫ് കവറേജ്.

ഈ സ്യൂട്ട് CI-യിൽ (`test:integration` ജോബ്) `--test-concurrency=1`, `--test-force-exit`
എന്നിവയോടെ പ്രവർത്തിക്കുന്നതിനാൽ ഇത് നിർണായകമാണ്; ലൈവ് ക്രെഡൻഷ്യലുകൾ ആവശ്യമില്ല.

### നിയന്ത്രിത ലൈവ് സ്മോക്ക് (CI-യിൽ ഇല്ല — യഥാർഥ ദാതാക്കൾ)

| കമാൻഡ്                                 | ഇത് ചെയ്യുന്നത്                                                                                                  |
| :------------------------------------- | :--------------------------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` ഉപയോഗിച്ചുള്ള ഇൻ-പ്രോസസ് യഥാർഥ റൂട്ടിംഗ്; ഒരു ലൈവ് OmniRoute DB-യുടെ സ്നാപ്ഷോട്ട് എടുക്കുന്നു |
| `npm run test:combo:live:vps`          | ഒരു ലൈവ് OmniRoute സെർവറിലേക്കുള്ള HTTP കോളുകൾ (`COMBO_LIVE_BASE_URL` സജ്ജമാക്കുക)                               |
| `npm run test:combo:live:vps:failover` | അതേ രീതി, എന്നാൽ മനഃപൂർവമായ ഫെയിൽഓവർ സാഹചര്യങ്ങളോടെ                                                              |

ഈ സ്മോക്ക് ടെസ്റ്റുകൾ യഥാർഥ വയർ പാത്ത് (കോംബോ → ദാതാവ് → കംപ്ലീഷൻ) പരിശോധിക്കുന്നു. ലൈവ്
ക്രെഡൻഷ്യലുകളും VPS ആക്സസും ആവശ്യമുള്ളതിനാൽ ഇവ മനഃപൂർവം CI-യിൽ നിന്ന് ഒഴിവാക്കിയിരിക്കുന്നു.
