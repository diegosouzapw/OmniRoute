> ഓപ്റ്റ്-ഇൻ, ഡിഫോൾട്ടായി ഓഫാണ് (`settings.freeAccessPolicy !== "strict"` എല്ലാ `auto/*`
> candidate pool-ഉം byte-identical ആയി നിലനിർത്തുന്നു). ക്രമാനുഗതമായ ഏതെങ്കിലും സാമ്പത്തിക ചെലവിനെതിരെ
> കർശനമായ ഉറപ്പ് ആവശ്യമായ ഓപ്പറേറ്റർമാർക്കായി `hidePaidModels`-ന്റെ കൂടുതൽ കർശനമായ സഹോദര സംവിധാനം
> (`open-sse/services/autoCombo/paidModelFilter.ts`, #6512); കേവലം "സൗജന്യമാണെന്ന് രേഖപ്പെടുത്തിയിരിക്കുന്നു"
> എന്നതിനെ ആശ്രയിക്കുന്നതല്ല.

## ഇത് എന്തിനാണ് നിലവിലുള്ളത്, `hidePaidModels` മാത്രം മതിയാകാത്തത് എന്തുകൊണ്ട്

`hidePaidModels` ഉത്തരം നൽകുന്നത് "ഇപ്പോൾ ഈ മോഡൽ `FREE_MODEL_BUDGETS`-ൽ സൗജന്യമായി
വർഗ്ഗീകരിച്ചിട്ടുണ്ടോ?" എന്ന ചോദ്യത്തിനാണ് — ഒരു നിർദ്ദിഷ്ട സമയത്തെ catalog വസ്തുത,
`isFreeModel()`/`providerHasFreeModels()` വഴി പരിശോധിക്കുന്നു
(`src/shared/utils/freeModels.ts`). എന്നാൽ യഥാർത്ഥത്തിലുള്ള രണ്ട് അപകടസാധ്യതകളെക്കുറിച്ച് ഇത്
ഒന്നും പറയുന്നില്ല:

1. ഒരു `recurring-*`/`one-time-initial` സൗജന്യ ടിയറിന്റെ allowance **തീർന്നുപോകാം** — catalog
   അപ്പോഴും മോഡലിനെ സൗജന്യമായി പട്ടികപ്പെടുത്തും, എന്നാൽ അതിന് പിന്നിലുള്ള അക്കൗണ്ടിൽ ശേഷിക്കുന്ന
   ശേഷി ഉണ്ടാകില്ല.
2. സൗജന്യ ടിയർ പരിധി കവിയുന്നത് എല്ലായ്പ്പോഴും നിർബന്ധിതമായി സേവനം നിർത്തുന്നതിലേക്ക് നയിക്കില്ല.
   ചില providers ഒരിക്കലും payment method ബന്ധിപ്പിക്കാൻ കഴിയില്ലെന്ന് വ്യക്തമായി രേഖപ്പെടുത്തുന്നു
   ("credit card ആവശ്യമില്ല"); മറ്റുള്ളവർ അങ്ങനെ പറയുന്നില്ല, കൂടാതെ ചിലർ സൗജന്യ allowance
   കഴിഞ്ഞാൽ സ്വയമേവ ബിൽ ഈടാക്കുന്നു.

`hidePaidModels`-ന് ഇവ തമ്മിൽ വേർതിരിച്ചറിയാനാവില്ല — അതിനായി അത് ഒരിക്കലും ഉദ്ദേശിച്ചിരുന്നില്ല.
STRICT_ZERO_COST കൃത്യമായി ഈ രണ്ട് പരിശോധനകൾ കൂടി ചേർക്കുന്നു; ഓരോ candidate-നുമായി,
category/tier ranking-ന് **മുമ്പും** dispatch-ന് **മുമ്പും** അവ വിലയിരുത്തുന്നു — ഒരു request
ഇതിനകം അയച്ചുകഴിഞ്ഞതിന് ശേഷം ഒരിക്കലുമല്ല.

## Candidate വർഗ്ഗീകരണം

Pool-ലുള്ള ഓരോ candidate-നും
(`open-sse/services/autoCombo/virtualFactory.ts::buildPreparedPool`,
`filterPaidOnlyCandidates`-ന് തൊട്ടുപിന്നാലെ):

1. **`FREE_MODEL_BUDGETS`-ൽ ഒട്ടും ഇല്ല** → ഒഴിവാക്കപ്പെടുന്നു. യഥാർത്ഥത്തിൽ പണം നൽകേണ്ട മോഡലുകളും
   OmniRoute ഇതുവരെ വർഗ്ഗീകരിച്ചിട്ടില്ലാത്ത ഏതൊരു provider/model-ഉം ഇതിൽ ഉൾപ്പെടുന്നു — പുതിയ
   candidates ഉൾപ്പെടുത്തപ്പെട്ടല്ല, ഒഴിവാക്കപ്പെട്ട നിലയിലാണ് ആരംഭിക്കുന്നത്.
2. **`freeType: "keyless"`** → ഉടൻ കടന്നുപോകുന്നു, **എന്നാൽ യഥാർത്ഥത്തിൽ no-auth path വഴി
   എത്തിയ candidate-ന് മാത്രം** (`connectionId === SYNTHETIC_NOAUTH_CONNECTION_ID`,
   `open-sse/services/autoCombo/resilienceCandidateFilter.ts`). ആ candidate-ന് credential
   നിലവിലില്ലാത്തതിനാൽ, അതിനെതിരെയുള്ള ഒരു request-നും ഒരിക്കലും ബിൽ ഈടാക്കാനാവില്ല — runtime
   പരിശോധന ആവശ്യമില്ല, സാധ്യവുമല്ല. ഒരു **യഥാർത്ഥ** DB connection വഴി എത്തിച്ചേർന്ന, catalog-ൽ
   ഉൾപ്പെട്ട അതേ `keyless` provider/model-ന് (`connectionId` ഒരു യഥാർത്ഥ connection id ആണ്,
   അല്ലെങ്കിൽ candidate-ൽ `allowedConnectionIds` ഉണ്ട്) ഈ shortcut ലഭിക്കില്ല — `keyless`
   metadata പ്രത്യേകം no-auth path-നെയാണ് വിവരിക്കുന്നത്, പൊതുവായി provider-നെയല്ല; കൂടാതെ അത്
   ഒരിക്കലും യഥാർത്ഥ credential ഉള്ള അക്കൗണ്ടിന് അനുമതി നൽകുന്നില്ല. അത്തരമൊരു candidate
   മറ്റേതൊരു candidate-നെയും പോലെ പരിശോധന 3-ലേക്ക് കടക്കും; അവിടെ catalog entry-യിൽ പ്രത്യേകം
   `hardStopGuaranteed: true` ഇല്ലെങ്കിൽ അത് ഒഴിവാക്കപ്പെടും (യഥാർത്ഥ `keyless` entries-ൽ ഇത്
   ഒരിക്കലും ഉണ്ടാകില്ല — shortcut മാത്രമായിരുന്നു അവയുടെ സുരക്ഷിതമായ ഏക മാർഗം).
3. **മറ്റേതെങ്കിലും `freeType`** (`recurring-daily`, `recurring-monthly`, `recurring-credit`,
   `recurring-uncapped`, `one-time-initial`, കൂടാതെ ഈ module പ്രത്യേകമായി കൈകാര്യം ചെയ്യാത്ത
   ഭാവിയിലെ ഏതൊരു type-ഉം) → താഴെപ്പറയുന്നവ **എല്ലാം** ശരിയായാൽ മാത്രം കടന്നുപോകുന്നു:
   - Catalog entry-യിൽ `hardStopGuaranteed: true` സജ്ജീകരിച്ചിരിക്കണം
     (`FreeModelBudget.hardStopGuaranteed`, `open-sse/config/freeModelCatalog.ts`) — ഇത്
     provider-ന്റെ തന്നെ പ്രസിദ്ധീകരിച്ച നിബന്ധനകളെക്കുറിച്ചുള്ള **ശ്രദ്ധാപൂർവം പരിശോധിച്ച്,
     കൈകൊണ്ട് സജ്ജീകരിച്ച വസ്തുതയാണ്** (ഉദാ. വ്യക്തമായ "credit card ആവശ്യമില്ല" എന്ന അവകാശവാദം);
     `freeType`-ൽ നിന്നോ live API response-ൽ നിന്നോ ഇത് ഒരിക്കലും കണ്ടെത്തുന്നതല്ല. സജ്ജീകരിക്കാത്തത്
     (`undefined`) കൂടാതെ `false` എന്നിവ രണ്ടും "ഉറപ്പില്ല" എന്നായാണ് കണക്കാക്കുന്നത്.
   - `USAGE_FETCHER_PROVIDERS`-ൽ provider-നായി ഒരു usage adapter നിലവിലുണ്ടായിരിക്കണം
     (`open-sse/services/usage.ts`) — quota dashboard-നും `getUsageForProvider()`-നും ഇതിനകം
     പിന്തുണ നൽകുന്ന അതേ registry. Adapter ഇല്ല → ഒന്ന് ചേർക്കുന്നതുവരെ ശാശ്വതമായി ഒഴിവാക്കപ്പെടും.
   - **യഥാർത്ഥത്തിൽ വിലയിരുത്തപ്പെടുന്ന നിർദ്ദിഷ്ട connection-ന്റെ** live, cached
     `FreeAccessState` എന്നതിന്റെ `status: "SAFE"` ആയിരിക്കണം; അത്
     `settings.autoRefreshProviderQuotaInterval`-നുള്ളിൽ പരിശോധിച്ചതായിരിക്കണം (ഡിഫോൾട്ട് 180s —
     നിലവിലുള്ള setting തന്നെയാണ്, പുതിയൊരു സംഖ്യയല്ല); കൂടാതെ ഒരു ചെറിയ safety margin-നേക്കാൾ
     കൂടുതലായി `remainingFreeAllowance` റിപ്പോർട്ട് ചെയ്യണം.
4. **`freeType: "discontinued"`** → എല്ലായ്പ്പോഴും ഒഴിവാക്കപ്പെടുന്നു.

## കണക്ഷൻ സുരക്ഷ (ഓരോ കണക്ഷനും പ്രത്യേകം പരിശോധിക്കൽ, ഒരിക്കലും ഓരോ കാൻഡിഡേറ്റിനുമല്ല)

auto-combo പൂളിലെ ഒരു കാൻഡിഡേറ്റ് എല്ലായ്പ്പോഴും ഒരൊറ്റ കണക്ഷനുമായി ബന്ധിപ്പിക്കപ്പെട്ടിരിക്കണമെന്നില്ല. ഒരു "ലോജിക്കൽ" കാൻഡിഡേറ്റ്
(`connectionId: null`) ഒരു `allowedConnectionIds` അനുവദനീയ പട്ടിക വഹിക്കുന്നു — അഭ്യർത്ഥന കൈകാര്യം ചെയ്യാൻ കഴിയുന്ന ഒന്നോ അതിലധികമോ യഥാർത്ഥ
പ്രൊവൈഡർ കണക്ഷനുകൾ/അക്കൗണ്ടുകൾ — ഇവയിൽ യഥാർത്ഥത്തിൽ ഉപയോഗിക്കേണ്ട അക്കൗണ്ട് പിന്നീട് dispatch സമയത്ത്
`open-sse/services/combo/autoStrategy.ts` ആണ് തീരുമാനിക്കുന്നത്
(`allowedConnectionIds`-നെ അതിന്റെ സ്വന്തം കണക്ഷൻ-തിരഞ്ഞെടുക്കൽ ലോജിക്കുമായി intersect ചെയ്യുന്നു, ഏകദേശം 315-331 വരികൾ).

STRICT_ZERO_COST ആ അനുവദനീയ പട്ടികയിലെ **ഓരോ കണക്ഷന്റെയും സൗജന്യ-ആക്സസ് നില പ്രത്യേകം**
പരിശോധിക്കുകയും (`strictZeroCostFilter.ts`-ലെ `evaluateCandidateConnections()`) `allowedConnectionIds`-നെ
`SAFE` ആയി തിരിച്ചുവന്ന കൃത്യമായ ഉപസമുച്ചയത്തിലേക്ക് ചുരുക്കി മാറ്റിയെഴുതുകയും ചെയ്യുന്നു — ഒരിക്കലും പൂർണ്ണമായ
യഥാർത്ഥ പട്ടികയിലേക്കോ, ഏകപക്ഷീയമായി തിരഞ്ഞെടുത്ത ഒരൊറ്റ അംഗത്തിലേക്കോ അല്ല. വ്യക്തമായി പറഞ്ഞാൽ:

- അക്കൗണ്ട് A `SAFE`, അക്കൗണ്ട് B `UNKNOWN`/പരിധി തീർന്നത്/നിരക്ക് ഈടാക്കാവുന്നത് → A മാത്രം തിരഞ്ഞെടുക്കാവുന്നതായി ശേഷിക്കും.
- എല്ലാ അക്കൗണ്ടുകളും `UNKNOWN` → കാൻഡിഡേറ്റ് പൂർണ്ണമായും ഒഴിവാക്കപ്പെടും (ശൂന്യമായ സുരക്ഷിത സെറ്റ്).
- പരാജയപ്പെടുന്ന ഒറ്റ-കണക്ഷൻ കാൻഡിഡേറ്റ് (`connectionId` നേരിട്ട് സജ്ജീകരിച്ചിരിക്കുന്നു, അനുവദനീയ പട്ടികയില്ല)
  പൂർണ്ണമായും ഒഴിവാക്കപ്പെടും; ശൂന്യമായ `allowedConnectionIds` സഹിതം ഒരിക്കലും തിരികെ നൽകില്ല.

dispatch ചെയ്യാനുള്ള കണക്ഷൻ തിരഞ്ഞെടുക്കുന്നതിന് മുമ്പ് `autoStrategy.ts` ഇതിനകം തന്നെ
`allowedConnectionIds`-നെ നിർബന്ധിത അനുവദനീയ പട്ടികയായി പ്രയോഗിക്കുന്നതിനാൽ, പരിശോധിച്ച് `SAFE` ആണെന്ന് ഉറപ്പാക്കിയ
ഉപസമുച്ചയത്തിലേക്ക് അതിനെ മാറ്റിയെഴുതുന്നത്, dispatch സമയത്ത് യഥാർത്ഥത്തിൽ ഉപയോഗിക്കുന്ന കണക്ഷൻ ഈ ഫിൽട്ടർ തന്നെ
പരിശോധിച്ച ഒന്നാണെന്ന് ഉറപ്പാക്കാൻ മതിയാകും — അതേ കാൻഡിഡേറ്റിലുള്ള മറ്റൊരു, പരിശോധിക്കാത്ത അക്കൗണ്ട് ഒരിക്കലും ഉപയോഗിക്കില്ല. റിഗ്രഷൻ തെളിവിനായി
`tests/unit/autoCombo/strict-zero-cost-connection-safety.test.ts` കാണുക
(keyless-bypass കേസുകൾ A/B/C, multi-account കേസുകൾ 1-5).

`discovered automatically`: ശരിയായ മെറ്റാഡാറ്റയോടെ നാളെ പുറത്തിറങ്ങുന്ന ഒരു പ്രൊവൈഡർ/മോഡൽ (catalog-ൽ,
ഒരു usage adapter സഹിതം, `hardStopGuaranteed: true`) OmniRoute അതിനെക്കുറിച്ച് അറിയുന്ന നിമിഷം മുതൽ
ഉപയോഗിക്കാനാകും — കോഡ് മാറ്റമോ whitelist എൻട്രിയോ ഈ മൊഡ്യൂളിൽ തിരുത്തേണ്ട ഒന്നുമോ ഇല്ല. catalog-ൽ നിന്ന്
നീക്കം ചെയ്യപ്പെടുന്ന ഒന്ന് അതേ രീതിയിൽ അപ്രത്യക്ഷമാകും. റിഗ്രഷൻ തെളിവിനായി
`tests/unit/autoCombo/strict-zero-cost-autodiscovery.test.ts` കാണുക (യഥാർത്ഥ catalog മാറ്റാതെ,
inject ചെയ്യാവുന്ന fixtures വഴിയായി).

## ക്വോട്ട കാഷിംഗ് (`open-sse/services/autoCombo/freeAccessQuota.ts`)

`getUsageForProvider()` വീണ്ടും ഉപയോഗിക്കുന്നു — രണ്ടാമതൊരു ക്വോട്ട സിസ്റ്റമില്ല. ഹ്രസ്വകാലത്തേക്കുള്ള, in-memory,
പ്രോസസിന്റെ ആയുസ്സോളം നിലനിൽക്കുന്ന ഒരു കാഷ് അതിന്റെ മുന്നിലുണ്ട് (TTL, ഡിഫോൾട്ട്
`autoRefreshProviderQuotaInterval`-ന് തുല്യം); അതിനാൽ Telegram-തോതിലുള്ള അഭ്യർത്ഥന നിരക്ക് ഓരോ അഭ്യർത്ഥനയിലെയും
ഓരോ കാൻഡിഡേറ്റിനുമായി ഒരു തത്സമയ billing-API കോൾ ഒരിക്കലും സൃഷ്ടിക്കില്ല. റീഡുകൾ synchronous ആണ്: ഒരു cache miss
`undefined` തിരികെ നൽകുകയും (→ ഒഴിവാക്കപ്പെടുന്നു, fail-closed) _അടുത്ത_ റീഡിനായി പശ്ചാത്തല refresh ആരംഭിക്കുകയും
ചെയ്യുന്നു — candidate-pool നിർമ്മാണ പാതയിലെ ഒന്നും ഒരിക്കലും ഒരു network call-നായി കാത്തിരിക്കില്ല.

ഏതെങ്കിലും കാരണത്താൽ ഒരു കണക്ഷൻ പരാജയപ്പെടുന്ന നിമിഷം
`src/sse/services/auth.ts::markAccountUnavailable()`-ൽ നിന്ന്
`invalidateFreeAccessState(provider, connectionId)` വിളിക്കപ്പെടുന്നു; അതിനാൽ തൊട്ടടുത്ത pool build പഴകിയ
`SAFE` എൻട്രിക്ക് പകരം ശുദ്ധമായ cache miss വായിക്കും — 402/403/quota-exhausted പ്രതികരണത്തിന് ശേഷം TTL
കാലാവധി കഴിയുന്നതുവരെ കാത്തിരിക്കേണ്ടതില്ല.

## ToS ഗാർഡ് (സാമ്പത്തിക സുരക്ഷയിൽനിന്ന് സ്വതന്ത്രം)

`excludeTosAvoid` (സ്ഥിരസ്ഥിതി `false`) ക്യൂറേറ്റ് ചെയ്ത `tos` വിധി
(`FreeModelBudget.tos`) `"avoid"` ആയ എല്ലാ കാൻഡിഡേറ്റുകളെയും ഒഴിവാക്കുന്നു — `hidePaidModels`-ന്റെ അനുബന്ധ ഡോക്യുമെന്റുകൾ
(`docs/reference/FREE_TIERS.md`) ഇതിനകം പൂരിപ്പിക്കുന്ന അതേ ഫീൽഡാണ് ഇത് വീണ്ടും ഉപയോഗിക്കുന്നത്. ഇത് മനഃപൂർവം
`freeAccessPolicy`-യിൽനിന്ന് വേർതിരിച്ചിരിക്കുന്നു: ഒരു കാൻഡിഡേറ്റ് സാമ്പത്തികമായി `SAFE` ആയിരിക്കാം, എന്നിരുന്നാലും കരാർപരമായ
കാരണങ്ങളാൽ ഇവിടെ ഒഴിവാക്കപ്പെടാം; അല്ലെങ്കിൽ `freeAccessPolicy: "strict"` ഓണായിരിക്കുമ്പോൾപ്പോലും ഈ ഗാർഡ് ഓഫാണെങ്കിൽ ഉൾപ്പെടുത്തപ്പെട്ടേക്കാം.

## ഗാർഡ് ഒഴിവാക്കുന്നത് എന്തൊക്കെയാണെന്ന് കാണൽ

`GET /v1/auto-combo/{channel}/candidates` ഈ ഗാർഡ് ഡിസ്പാച്ചിൽനിന്ന്
ഒഴിവാക്കുന്നവ ഉൾപ്പെടെ എല്ലാ കാൻഡിഡേറ്റുകളെയും പട്ടികപ്പെടുത്തുന്നു; ഓരോന്നിലും `freeAccessExclusion` ഉണ്ടായിരിക്കും — ഗാർഡിന്റെ
നിബന്ധനകൾ പാലിക്കപ്പെടുമ്പോൾ `null`, അല്ലാത്തപ്പോൾ അതിന്റെ കാരണം. ഈ പട്ടിക റിപ്പോർട്ട് ചെയ്യുക മാത്രമാണ് ചെയ്യുന്നത്; ഒരിക്കലും നിർബന്ധിതമായി നടപ്പാക്കുന്നില്ല. പോളിസി ഓഫാക്കുന്നത്

| `no-connection`        | പരിശോധിക്കാൻ കാൻഡിഡേറ്റിനൊപ്പം ഒരു അക്കൗണ്ടും ഇല്ല.                                                                                              | ഇത് ക്വോട്ട പ്രശ്നമല്ല: കണക്ഷൻ ഇല്ലാതെയാണ് കാൻഡിഡേറ്റ് നിർമ്മിച്ചത്, അതിനാൽ ഒന്നും പരിശോധിച്ചിട്ടില്ല. പൂൾ എങ്ങനെ അസംബിൾ ചെയ്തുവെന്ന് പരിശോധിക്കുക.  |

അവസാനത്തെ രണ്ടും വേർതിരിച്ചറിയേണ്ട ജോടിയാണ്. തീർന്നുപോയ അനുവദനീയ പരിധി സ്വയം റീസെറ്റ് ചെയ്യും; എന്നാൽ ഒരിക്കലും ലഭിക്കാത്ത ഒരു റീഡിംഗ്
എന്നാൽ ലുക്കപ്പ് തന്നെ തകരാറിലാണെന്നാണ് അർത്ഥം. ഇതുവരെ ഇവ രണ്ടും പുറത്തുനിന്ന് ഒരുപോലെയാണ് തോന്നിയിരുന്നത് —
കാൻഡിഡേറ്റ് അപ്രത്യക്ഷമാകുകയായിരുന്നു.

**ഒരു വിടവ് ശേഷിക്കുന്നു, അത് മനഃപൂർവമാണ്.** പട്ടിക നിർമ്മിക്കുന്നതിന് മുമ്പുതന്നെ `excludeTosAvoid` കാൻഡിഡേറ്റുകളെ ഇപ്പോഴും നീക്കംചെയ്യുന്നതിനാൽ,
`tos: "avoid"` ആയി ക്യൂറേറ്റ് ചെയ്ത ഒരു മോഡൽ യാതൊരു കാരണവും നൽകാതെ പട്ടികയിൽനിന്ന് അപ്രത്യക്ഷമാകും — zero-cost ഗാർഡിനായി ഈ വിഭാഗം ഇപ്പോൾ പരിഹരിച്ച
അതേ അദൃശ്യാവസ്ഥയാണിത്. ഇതും പരിഹരിക്കാൻ, ഒരു ToS ഒഴിവാക്കൽ എന്താണ് റിപ്പോർട്ട് ചെയ്യേണ്ടതെന്ന് തീരുമാനിക്കേണ്ടതുണ്ട്;
അത് സാമ്പത്തിക സുരക്ഷയിൽനിന്ന് വേറിട്ടൊരു ചോദ്യമാണ്. വിടവ് നിലവിലില്ലെന്ന് നടിക്കുന്നതിനുപകരം ഈ പേജ് അതിനെ വ്യക്തമായി പരാമർശിക്കുന്നു.

ഓഫ്ലൈൻ before/after പരിശോധനയ്ക്കായി, `npx tsx scripts/ad-hoc/dry-run-strict-zero-cost.ts` ഒരു ലൈവ് ഇൻസ്റ്റൻസിന്റെ
കാൻഡിഡേറ്റ് ഔട്ട്പുട്ടിനെതിരെ ഇപ്പോഴും പ്രവർത്തിക്കും; ഇത് ഓരോ കാൻഡിഡേറ്റിന്റെയും യഥാർത്ഥ `connectionId` വായിക്കുന്നതിനാൽ,
കണക്ഷൻ-സുരക്ഷാ പാതയും പരിശോധിക്കുന്നു. Keyless കാൻഡിഡേറ്റുകൾ യഥാർത്ഥ കണക്ഷനുമായല്ല, സിന്തറ്റിക്
no-auth `connectionId`-യോടെയാണ് എത്തേണ്ടത്. നിലവിലെ ബിൽറ്റ്-ഇൻ keyless auto പാത OpenCode Free ആണ്; കൃത്യമായ കാൻഡിഡേറ്റ് എണ്ണങ്ങൾ
ലൈവ് മോഡൽ കണ്ടെത്തലിനെ ആശ്രയിച്ചിരിക്കുന്നതിനാൽ, പഴയൊരു റണ്ണിൽനിന്ന് പകർത്തുന്നതിനുപകരം ലക്ഷ്യ ഡിപ്ലോയ്മെന്റിൽ അളക്കണം.
രജിസ്റ്റർ ചെയ്ത usage adapter-ഉം `hardStopGuaranteed: true`-ഉം ഒരുമിച്ച് ഉണ്ടെങ്കിൽ മാത്രമേ ഒരു `recurring-*` കാൻഡിഡേറ്റ് പാസാകൂ;
അപൂർണ്ണമായ മെറ്റാഡാറ്റ fail-closed ആയി തുടരും.

`excludeTosAvoid: true` ആയിരിക്കുമ്പോൾ, `tos: "avoid"` ആയി ക്യൂറേറ്റ് ചെയ്ത എല്ലാ കാൻഡിഡേറ്റുകളും നീക്കംചെയ്യപ്പെടും. OpenCode Free-ന്
നിലവിൽ ആ വിധിയാണുള്ളത്; അതിനാൽ ഗാർഡ് സജ്ജമാക്കുന്നത് ഒരു ഡിപ്ലോയ്മെന്റിൽ ശേഷിക്കുന്ന keyless
പൂൾ ശൂന്യമാക്കിയേക്കാം. ഇത് ToS ഗാർഡ് ഓണാക്കുന്നതിന്റെ പ്രതീക്ഷിതമായ ഒരു വിട്ടുവീഴ്ചയാണ്, ബഗ് അല്ല: കൃത്യമായി ഈ കാരണത്താലാണ് ഗാർഡ് സ്ഥിരസ്ഥിതിയായി `false`
ആയിരിക്കുന്നത് (മുകളിലെ "ToS ഗാർഡ്" കാണുക).

## പ്രവർത്തനക്ഷമമാക്കൽ

```json
PUT /api/settings
{ "freeAccessPolicy": "strict", "excludeTosAvoid": false }
```

രണ്ട് പുതിയ ക്രമീകരണങ്ങളും അവയുടെ ഫീച്ചറിന് മുമ്പുള്ള മൂല്യങ്ങളിലേക്ക് (`"off"` / `false`) ഡിഫോൾട്ട് ചെയ്യുന്നു — ഇവയിലൊന്നും പ്രവർത്തനക്ഷമമാക്കാതിരിക്കുന്നത് നിലവിലുള്ള ഒരു `auto/*` റൂട്ടിങ് സ്വഭാവത്തിലും മാറ്റം വരുത്തില്ല.
