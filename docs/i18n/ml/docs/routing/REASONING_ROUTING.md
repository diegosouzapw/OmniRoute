നിലവിലുള്ള മോഡൽ, കോംബോ റൂട്ടിംഗുകളെ റീസണിംഗ് റൂട്ടിംഗ് നിയമങ്ങൾ വിപുലീകരിക്കുന്നു. സജീവമായ ഒരു നിയമവും പൊരുത്തപ്പെടാത്തപ്പോൾ, നിലവിലുള്ള തിങ്കിംഗ്, സഫിക്സ്, കണക്ഷൻ-ഡിഫോൾട്ട്, പ്രൊവൈഡർ-ട്രാൻസ്ലേഷൻ പ്രവർത്തനരീതികൾ മാറ്റമില്ലാതെ തുടരും.

## മാനേജ്മെന്റ്

നിയമങ്ങളുടെ മാനേജ്മെന്റ് **Settings → Global Routing** എന്നതിന് കീഴിൽ ലഭ്യമാണ്. തിരഞ്ഞെടുത്ത കീയിലേക്ക് ഫിൽട്ടർ ചെയ്ത അതേ മാനേജ്മെന്റ് UI, API-key എഡിറ്ററും നൽകുന്നു.

മാനേജ്മെന്റ് API ഇനിപ്പറയുന്ന റൂട്ടുകളിലൂടെ ലഭ്യമാക്കുന്നു:

- `/api/settings/reasoning-routing-rules` എന്നതിൽ `GET`, `POST`
- `/api/settings/reasoning-routing-rules/[id]` എന്നതിൽ `GET`, `PATCH`, `DELETE`
- `/api/settings/reasoning-routing-rules/simulate` എന്നതിൽ `POST`

എല്ലാ റൂട്ടുകളും `requireManagementAuth` ഉപയോഗിക്കുന്നു. `src/shared/validation/schemas/reasoningRouting.ts` എന്നതിലെ സ്കീമകൾ ഉപയോഗിച്ചാണ് ഇൻപുട്ടുകൾ സാധൂകരിക്കുന്നത്. സിമുലേറ്റർ ഒരിക്കലും അപ്സ്ട്രീം കോൾ നടത്തില്ല.

## നിയമ നിർണയം

പ്രാരംഭ മൂല്യനിർണ്ണയം കൃത്യമായി ഒരു നിയമം തിരഞ്ഞെടുക്കുന്നു. സ്കോപ്പുകൾ ഈ ക്രമത്തിലാണ് പരിശോധിക്കുന്നത്:

1. `apiKey`
2. `combo`
3. `model`
4. `global`

ഒരു സ്കോപ്പിനുള്ളിൽ, ആദ്യം ഉയർന്ന `priority` വിജയിക്കും; തുടർന്ന് ഗ്ലോബ് പാറ്റേണിനെക്കാൾ കൃത്യമായ മോഡൽ പൊരുത്തത്തിനും, അതിനുശേഷം സ്ഥിരതയുള്ള `createdAt`, `id` ക്രമത്തിനും മുൻഗണന ലഭിക്കും. `requestTags`, `metadata.tags` എന്നതിൽ നിന്ന് മാത്രമാണ് വായിക്കുന്നത്; അവ `any` അല്ലെങ്കിൽ `all` പൊരുത്തപ്പെടുത്തലിനെ പിന്തുണയ്ക്കുന്നു.

ഒരു പ്രാരംഭ നിയമവും വിജയിക്കാതിരിക്കുകയും, വ്യക്തമായ ഒരു പ്രൊവൈഡർ കണക്ഷൻ ഇതിനകം തിരഞ്ഞെടുക്കപ്പെട്ടിരിക്കുകയും ചെയ്യുമ്പോൾ മാത്രമാണ് `connection` നിയമം മൂല്യനിർണ്ണയം ചെയ്യുന്നത്. അതിന് എഫർട്ടും ബജറ്റും മാത്രമേ മാറ്റാനാകൂ.

## എഫർട്ടും ബജറ്റും

`sourceEffort`, `any`, `missing`, `none`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra` എന്നിവ സ്വീകരിക്കുന്നു. അഭ്യർത്ഥനയിൽ വ്യതിരിക്തമായ എഫർട്ടോ തിങ്കിംഗ് ടോഗിളോ തിങ്കിംഗ് ബജറ്റോ ഇല്ലെന്നാണ് `missing` അർത്ഥമാക്കുന്നത്. അതിനാൽ ബജറ്റ് മാത്രമുള്ള ഒരു സിഗ്നൽ `any` മുഖേന മാത്രമേ പൊരുത്തപ്പെടുത്തപ്പെടൂ.

`effortMode`-ന് മൂന്ന് വകഭേദങ്ങളുണ്ട്:

- മോഡലോ കോംബോയോ മാറ്റാൻ അനുവദിച്ചുകൊണ്ടുതന്നെ `inherit`, ക്ലയന്റിന്റെ എഫർട്ട് നിലനിർത്തുന്നു.
- വ്യക്തമായ റീസണിംഗ് സിഗ്നൽ ഇല്ലാത്തപ്പോൾ മാത്രമാണ് `default`, `targetEffort` സജ്ജമാക്കുന്നത്.
- `force`, വ്യതിരിക്തമായ എഫർട്ടിനെ `targetEffort` കൊണ്ട് മാറ്റിസ്ഥാപിക്കുന്നു.

ഇതിൽ നിന്ന് സ്വതന്ത്രമായി, `budgetAction` എന്നത് `preserve`, `remove`, അല്ലെങ്കിൽ `set` ആകാം. `none` സഹിതമുള്ള `force`, തിരിച്ചറിയപ്പെട്ട എല്ലാ എഫർട്ട്, ബജറ്റ് ഫീൽഡുകളും നീക്കംചെയ്യുന്നു. `set`-നോടൊപ്പമുള്ള `none` അസാധുവാണ്.

പൊരുത്തമില്ലെന്ന് അറിയപ്പെടുന്ന മോഡലുകളെ ലക്ഷ്യമിടുന്ന അഭ്യർത്ഥനകൾ അപ്സ്ട്രീം കോളിന് മുമ്പ് നിരസിക്കുന്നു. കോംബോ ടാർഗെറ്റുകളിൽ നിന്ന് പൊരുത്തമില്ലാത്ത എൻട്രികൾ നീക്കംചെയ്യുന്നു; ഒന്നും ശേഷിക്കുന്നില്ലെങ്കിൽ, അഭ്യർത്ഥന `400` സ്റ്റാറ്റസ് നൽകുന്നു. അറിയാത്ത ശേഷി ഡാറ്റ ഒരു മുന്നറിയിപ്പ് സൃഷ്ടിക്കുകയും നിയമത്തെ സജീവമായി നിലനിർത്തുകയും ചെയ്യുന്നു.

## സുരക്ഷയും ട്രാൻസ്പോർട്ടുകളും

സോഴ്സ്, ടാർഗെറ്റ് മോഡലുകൾ അല്ലെങ്കിൽ സോഴ്സ്, ടാർഗെറ്റ് കോംബോകൾ നിലവിലുള്ള API-key നയത്തിന് തുടർന്നും വിധേയമാണ്. ഒരു റീസണിംഗ് നിയമം ഒരിക്കലും മോഡൽ, കോംബോ, അല്ലെങ്കിൽ ക്വോട്ട അനുമതികൾ വിപുലീകരിക്കില്ല.

എഞ്ചിൻ Chat Completions, Responses, Anthropic Messages, ആന്തരിക Codex WebSocket പാത എന്നിവയുമായി സംയോജിപ്പിച്ചിരിക്കുന്നു. WebSocket പാത Codex ടാർഗെറ്റ് മോഡലുകൾ മാത്രമേ സ്വീകരിക്കൂ; കോംബോ ടാർഗെറ്റുകൾ അവിടെ എക്സിക്യൂട്ട് ചെയ്യാനാവില്ല. നിയമ തീരുമാനം രഹസ്യങ്ങളില്ലാതെ നിലവിലുള്ള റൂട്ട് ട്രേസിൽ സംഭരിക്കുന്നു.

## പെർസിസ്റ്റൻസ്

`src/lib/db/migrations/126_reasoning_routing_rules.sql` മൈഗ്രേഷൻ `reasoning_routing_rules` പട്ടിക സൃഷ്ടിക്കുന്നു. നിയമങ്ങൾ സംഭരിച്ച API കീകൾ, കോംബോകൾ, പ്രൊവൈഡർ കണക്ഷനുകൾ എന്നിവയെ റഫറൻസ് ചെയ്യുന്നു. ഡിലീറ്റുകൾ ബന്ധപ്പെട്ട നിയമങ്ങൾ വൃത്തിയാക്കുന്നു. `src/lib/db/reasoningRoutingRules.ts` എന്നതിലെ ഡാറ്റാബേസ് ആക്സസ് ലെയർ, അഭ്യർത്ഥനാ പാതയ്ക്കായി അസാധുവാക്കാനാകുന്ന ഒരു കാഷ് പരിപാലിക്കുന്നു.

SQLite ബാക്കപ്പുകൾ, സമ്പൂർണ്ണ ഡാറ്റാബേസ് എക്സ്പോർട്ട്, config-sync ബണ്ടിൽ എന്നിവയിൽ നിയമങ്ങൾ ഉൾപ്പെടുത്തിയിട്ടുണ്ട്. `reconcileReasoningRulesForSync`, റഫറൻസുകൾ നഷ്ടപ്പെട്ട ഇറക്കുമതി ചെയ്ത നിയമങ്ങൾ പ്രവർത്തനരഹിതമാക്കുകയും ആ വൈരുധ്യങ്ങൾ റിപ്പോർട്ട് ചെയ്യുകയും ചെയ്യുന്നു.
