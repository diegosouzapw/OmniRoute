## സംഗ്രഹം

`/api/v1/relay/chat/completions`-നായി OmniRoute ഇപ്പോൾ മൂന്ന് റിലേ മോഡുകൾ പിന്തുണയ്ക്കുന്നു:

- `ts`: പ്രോസസിനുള്ളിൽ TypeScript റിലേ ഉപയോഗിക്കുന്നു.
- `bifrost`: Bifrost ഗേറ്റ്വേ നിർബന്ധിതമായി ഉപയോഗിക്കുന്നു.
- `auto`: ലഭ്യമാകുമ്പോൾ Bifrost-ന് മുൻഗണന നൽകുകയും പരാജയപ്പെട്ടാൽ TypeScript-ലേക്ക് മടങ്ങുകയും ചെയ്യുന്നു.

ഉയർന്ന അഭ്യർത്ഥനാ നിരക്കിൽ (പ്രതിദിനം വലിയ തോതിലുള്ള ടോക്കണുകൾ, ഏതാണ്ട് സ്ഥിരമായ ത്രൂപുട്ട്) പ്രവർത്തിക്കുമ്പോൾ, ഫാൾബാക്ക് പാത വ്യക്തവും വേഗമുള്ളതുമായി നിലനിർത്തുന്നതാണ് ഏറ്റവും മികച്ച തന്ത്രം. ഇതിലൂടെ പ്രധാന പ്രവർത്തനപാത പ്രവർത്തനരഹിതമായ ഒരു സൈഡ്കാറിനായി കാത്തുനിൽക്കില്ല.

## മോഡുകളുടെ പ്രവർത്തനം

- `ts`
  - ഏറ്റവും കുറഞ്ഞ പ്രവർത്തന സങ്കീർണ്ണത.
  - എല്ലാ റൂട്ടിംഗും സാധൂകരണവും Node-ൽ പ്രവർത്തിക്കുന്നു.
  - ലഭ്യതയ്ക്കായി സൈഡ്കാർ ആശ്രിതത്വമില്ല.
- `bifrost`
  - എല്ലാ അഭ്യർത്ഥനകളും സൈഡ്കാർ ഗേറ്റ്വേയിലൂടെ നിർബന്ധിതമായി അയയ്ക്കുന്നു.
  - സ്വയമേവയുള്ള ഫാൾബാക്ക് ഇല്ല.
  - സൈഡ്കാറിന്റെ ആരോഗ്യനിലയും ലേറ്റൻസിയും ഉറപ്പുള്ളപ്പോൾ മാത്രം പ്രയോജനപ്രദം.
- `auto`
  - സൈഡ്കാറിൽ എത്തിച്ചേരാനാകുകയും അത് പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുകയും ചെയ്യുമ്പോൾ അത് ഉപയോഗിക്കുന്നു.
  - പരാജയപ്പെട്ട ശ്രമങ്ങൾ ഫാൾബാക്ക് ഹെഡറുകൾ ട്രിഗർ ചെയ്യുകയും ട്രാഫിക് TS-ലേക്ക് തിരികെ അയയ്ക്കുകയും ചെയ്യുന്നു; അതിനാൽ അഭ്യർത്ഥനയുടെ വിജയസാധ്യത നിയന്ത്രിതമായി നിലനിൽക്കും.
  - കർശനമായ സൈഡ്കാർ-മാത്രം റൂട്ടിംഗിനേക്കാൾ അപ്ടൈമിന് പ്രാധാന്യമുള്ള പ്രൊഡക്ഷൻ സാഹചര്യങ്ങളിൽ ഈ മോഡാണ് ഏറ്റവും സുരക്ഷിതമായ തിരഞ്ഞെടുപ്പ്.

## നിലവിൽ 9router-ഉം CLIPROXYAPI-യും തമ്മിലുള്ള താരതമ്യം

9router-ഉം CLIPROXYAPI-യും ചരിത്രപരമായി അപ്സ്ട്രീം പ്രൊവൈഡർമാർക്കായി അനുയോജ്യതാ പാതകൾ ലഭ്യമാക്കിയിരുന്ന ഇന്റഗ്രേഷനുകളാണ്.

- അപ്സ്ട്രീം ഓർക്കസ്ട്രേഷനും അനുയോജ്യതാ പ്രവർത്തനരീതിക്കുമായി ഉൾച്ചേർത്ത പാതയാണ് 9router.
- CLI / SDK ശൈലിയിലുള്ള ട്രാഫിക്കിനായുള്ള ഒരു പ്രോക്സി API ബ്രിഡ്ജാണ് CLIPROXYAPI.
- സമർപ്പിതമായ സൈഡ്കാർ പോലുള്ള ഒരു അധിക ഹോപ്പും കുറഞ്ഞ ലേറ്റൻസിയുള്ള ലോക്കൽ ഡിസ്പാച്ചും ആവശ്യമുള്ള സാഹചര്യങ്ങളിൽ ബാഹ്യവൽക്കരിച്ച പാതയായി Bifrost സ്ഥിരത കൈവരിച്ചുകൊണ്ടിരിക്കുന്നു.

നിങ്ങൾ നിലവിൽ 9router/CLIPROXYAPI താരതമ്യം ചെയ്യുകയാണെങ്കിൽ:

- കൈമാറ്റത്തിന് മുമ്പ് API റൂട്ടിൽ അഭ്യർത്ഥന സൈനിംഗ്, അലൗലിസ്റ്റ് പരിശോധനകൾ, DB നയ ഗേറ്റുകൾ എന്നിവ നിലനിർത്തുക.
- ഒരു വർക്ക്ഫ്ലോയ്ക്ക് കർശനമായ സൈഡ്കാർ പ്രവർത്തനവും ഓരോ അഭ്യർത്ഥനയിലുമുള്ള കുറഞ്ഞ വ്യതിയാനവും ആവശ്യമാണെങ്കിൽ, `OMNIROUTE_RELAY_BACKEND=bifrost` ഉപയോഗിക്കുക.
- തകരാർ സംഭവിക്കുന്ന സാഹചര്യങ്ങളിൽ ക്രമാനുഗതമായ സേവനത്തകർച്ചയോടൊപ്പം സൈഡ്കാർ പ്രതിരോധശേഷിയും ആവശ്യമാണെങ്കിൽ, `OMNIROUTE_RELAY_BACKEND=auto` ഉപയോഗിക്കുക.

## ബാക്കെൻഡ് അതിർത്തി കരാർ

സ്ഥിരമായ ഉൽപ്പന്ന അതിർത്തി OmniRoute റിലേ API ആണ്, ഡാഷ്ബോർഡ് നടപ്പാക്കലല്ല. Next.js ഡാഷ്ബോർഡിന് ലോക്കൽ സേവനങ്ങൾ ഇൻസ്റ്റാൾ ചെയ്യാനും കോൺഫിഗർ ചെയ്യാനും മേൽനോട്ടം വഹിക്കാനും കഴിയും. എന്നാൽ അഭ്യർത്ഥനാ റൂട്ടിംഗ് റിലേ API-യിലൂടെ പ്രവേശിക്കുകയും ആ അതിർത്തിക്കു പിന്നിൽ കൈമാറ്റം ചെയ്യപ്പെടുകയും വേണം.

ദീർഘകാല ബാക്കെൻഡ് തിരഞ്ഞെടുപ്പുകൾ:

- പ്രോസസിനുള്ളിലെ നയ, ഫാൾബാക്ക് പാതയായി TypeScript റിലേ നിലനിർത്തുക. ഏതെങ്കിലും ബാക്കെൻഡ് കൈമാറ്റത്തിന് മുമ്പ് ഓത്ത്, അലൗലിസ്റ്റുകൾ, അഭ്യർത്ഥനാ നോർമലൈസേഷൻ, അക്കൗണ്ടിംഗ്, സുരക്ഷാ പരിശോധനകൾ എന്നിവ ഇവിടെത്തന്നെ നിലനിർത്തണം.
- കുറഞ്ഞ റൂട്ടിംഗ് വ്യതിയാനം, കേന്ദ്രീകൃത പ്രൊവൈഡർ റൊട്ടേഷൻ, അല്ലെങ്കിൽ ഒന്നിലധികം OmniRoute റെപ്ലിക്കകളിലേക്കുള്ള സ്കെയിൽ-ഔട്ട് എന്നിവ വിന്യാസത്തിന് ആവശ്യമായപ്പോൾ, Bifrost-നെ മുൻഗണനയുള്ള ഉയർന്ന ത്രൂപുട്ടുള്ള Tier-1 സൈഡ്കാറായി ഉപയോഗിക്കുക.
- 9router-നെയും CLIPROXYAPI-യെയും ഉൾച്ചേർത്ത അനുയോജ്യതാ സേവനങ്ങളായി നിലനിർത്തുക. അവ മേൽനോട്ടത്തിലുള്ള ലോക്കൽ പ്രോസസുകളായി പ്രവർത്തിക്കുന്നു. അവയുടെ പ്രൊവൈഡർ/CLI പ്രവർത്തനരീതിയാണ് ആവശ്യമായ അഡാപ്റ്റർ എങ്കിൽ അവ പ്രയോജനപ്രദമാണ്; എന്നാൽ അവയെ ഡിഫോൾട്ട് Tier-1 റൂട്ടിംഗ് എൻജിനാക്കരുത്.
- പ്രധാന പ്രവർത്തനപാതയിലേക്ക് ഡാഷ്ബോർഡ് അനിയന്ത്രിതമായ സേവന URL-കൾ കൈമാറാൻ അനുവദിക്കരുത്. UI നൽകുന്ന URL-കൾ കോൺഫിഗറേഷൻ ഇൻപുട്ടുകളാണ്; റൂട്ടിംഗ് കോഡ് സെർവർ-സൈഡ് ക്രമീകരണങ്ങളിൽനിന്നും സൂപ്പർവൈസർ നിലയിൽനിന്നും രജിസ്റ്റർ ചെയ്തതും ആരോഗ്യപരിശോധന നടത്തിയതുമായ ബാക്കെൻഡുകൾ കണ്ടെത്തണം.
- നിയന്ത്രിത പ്രോസസുകൾ ഇതിനകം HTTP-അനുയോജ്യമായ API-കൾ ലഭ്യമാക്കുന്നതിനാലും റൂട്ട് ഗാർഡിന് അതിർത്തി ഓഡിറ്റ് ചെയ്യാനാകുന്നതിനാലും പരാജയ/ഫാൾബാക്ക് പ്രവർത്തനം അഭ്യർത്ഥനാ ലോഗുകളിൽ ദൃശ്യമാകുന്നതിനാലും നിലവിൽ മേൽനോട്ടത്തിലുള്ള സേവനങ്ങൾക്കായി ലൂപ്പ്ബാക്ക് HTTP-യ്ക്ക് മുൻഗണന നൽകുക. ഐസൊലേഷനോ ഫാൾബാക്ക് സെമാന്റിക്സോ ദുർബലമാക്കാതെ p99 റൂട്ടിംഗ് ലേറ്റൻസി ഗണ്യമായി കുറയ്ക്കുന്നുവെങ്കിൽ മാത്രം ഭാവിയിൽ ഒരു SDK അല്ലെങ്കിൽ സോക്കറ്റ് ട്രാൻസ്പോർട്ട് ചേർക്കുന്നത് മൂല്യവത്തായിരിക്കും.

വളരെ ഉയർന്ന ത്രൂപുട്ടുള്ള വിന്യാസത്തിന്, Bifrost പ്രവർത്തനക്ഷമമാക്കിയ `auto` ആണ് ഡിഫോൾട്ട് ഉത്തരം: വിജയനിരക്ക് നിലനിർത്താൻ TypeScript ഫാൾബാക്ക് സംരക്ഷിച്ചുകൊണ്ട് പ്രധാന പ്രവർത്തനപാതയിൽ Go സൈഡ്കാർ ഉപയോഗിക്കുക. ക്രമാനുഗതമായ സേവനത്തകർച്ചയെക്കാൾ കർശനമായ സൈഡ്കാർ-മാത്രം പ്രവർത്തനത്തിന് പ്രാധാന്യമുള്ളപ്പോൾ മാത്രം `bifrost` ഉപയോഗിക്കുക.

## ഉയർന്ന ത്രൂപുട്ടിനുള്ള മാർഗ്ഗനിർദ്ദേശം

തുടർച്ചയായ ഉയർന്ന RPM/RPS-നും കർശനമായ വിജയ SLO-യ്ക്കുമായി:

1. പ്രായോഗികമായ ഒരു കൂൾഡൗണും പരാജയ ടെലിമെട്രിയും സഹിതം `auto` ഉപയോഗിക്കുക.
2. അപ്സ്ട്രീം സാധൂകരണവും API-കീ പരിശോധനകളും TypeScript റൂട്ട് അതിർത്തിയിൽ നിലനിർത്തുക.
3. ഫാൾബാക്കിന്റെ ആവൃത്തിയും കാരണങ്ങളും നിങ്ങളുടെ അലേർട്ടിംഗ് സംവിധാനത്തിന് കണ്ടെത്താനായി വ്യക്തമായ ഹെഡറുകൾ/കൗണ്ടറുകൾ പ്രവർത്തനക്ഷമമാക്കുക.
4. അനന്തമായി കാത്തുനിൽക്കുന്നതിനുപകരം വേഗത്തിൽ പരാജയപ്പെടുന്ന രീതിയിൽ സൈഡ്കാർ ടൈംഔട്ടുകൾ ക്രമീകരിക്കുക.
5. ഫാൾബാക്ക് യഥാർഥത്തിൽ അസാധാരണമായ ഒരു സാഹചര്യം മാത്രമായി നിലനിർത്താൻ സേവനത്തിന്റെ സ്വയമേവയുള്ള പുനരാരംഭവും ആരോഗ്യ ടെലിമെട്രി ലൂപ്പും ആരോഗ്യകരമായി നിലനിർത്തുക.

## നിർദ്ദേശിക്കുന്ന അടിസ്ഥാന ക്രമീകരണം

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- API കീകൾ, അലൗലിസ്റ്റ്, സാനിറ്റൈസർ, റേറ്റ്-ലിമിറ്റ് പരിശോധനകൾ എന്നിവ റൂട്ട് ഹാൻഡ്ലറുകളിൽ പ്രവർത്തനക്ഷമമായി നിലനിർത്തുക (ഡൗൺസ്ട്രീം ഫോർവേഡിംഗിന് മുമ്പ് അവ എല്ലായ്പ്പോഴും പ്രവർത്തിക്കും).
- സൈഡ്കാർ പ്രവർത്തനത്തകരാറുകൾ ഒരു മിനിറ്റിനുള്ളിൽ ദൃശ്യമാകുന്നതിനായി നിങ്ങളുടെ റിവേഴ്സ് പ്രോക്സിയിൽനിന്നും അഭ്യർത്ഥനാ ലോഗുകളിൽനിന്നും ഫാൾബാക്ക് മെട്രിക്കുകൾ എക്സ്പോർട്ട് ചെയ്യുക.

## പ്രൊവൈഡർ പ്ലഗിൻ കരാർ

TypeScript എക്സിക്യൂട്ടറിന്റെ ആന്തരിക ഘടകങ്ങളെ ആശ്രയിക്കുന്നതിനുപകരം, JSON-സുരക്ഷിതമായ പ്രൊവൈഡർ പ്ലഗിൻ
മാനിഫെസ്റ്റിലൂടെ സൈഡ്കാറുകൾ പ്രൊവൈഡർ മെറ്റാഡാറ്റ ഇംപോർട്ട് ചെയ്യണം. സൈഡ്കാർ
യോഗ്യതാ കരാറിനും മൈഗ്രേഷൻ ഘട്ടങ്ങൾക്കുമായി [Provider Plugin Manifest](./PROVIDER_PLUGIN_MANIFEST.md) കാണുക.
