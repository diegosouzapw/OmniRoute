റിലേകൾ (Vercel, Deno, Cloudflare) ഒരു serverless backend-ൽ upstream കണക്ഷൻ അവസാനിപ്പിക്കുന്നു. ഇതുവഴി provider API key server-side-ൽ തന്നെ സൂക്ഷിച്ചുകൊണ്ട് സ്ഥിരതയുള്ള ഒരു region-ൽ നിന്ന് OmniRoute-ന് egress ചെയ്യാൻ കഴിയും. production-ൽ operators നേരിടുന്ന രണ്ട് failure mode-കളും ഓരോന്നിനുമായി OmniRoute നൽകുന്ന recovery path-കളും ഈ രേഖ വിശദീകരിക്കുന്നു.

## Relay auth എങ്ങനെ സംഭരിക്കുന്നു

**Settings → Proxy Pool → Deploy Relay** എന്നതിൽ നിന്ന് നിങ്ങൾ ഒരു relay deploy ചെയ്യുമ്പോൾ,
deploy flow relay-യുടെ auth token proxy-യുടെ `notes` JSON field-ൽ സംഭരിക്കുന്നു:

- `STORAGE_ENCRYPTION_KEY` സജ്ജീകരിച്ചിട്ടുണ്ടെങ്കിൽ, token `relayAuthEnc` ആയി
  എഴുതപ്പെടുന്നു (സംഭരിച്ചിരിക്കുമ്പോൾ AES ഉപയോഗിച്ച് encrypt ചെയ്ത നിലയിൽ).
- അല്ലെങ്കിൽ അത് plaintext `relayAuth` ആയി എഴുതപ്പെടുന്നു.

Request സമയത്ത് `extractRelayAuth(notes)` ലഭ്യമായ രൂപം ഏതാണോ അത് തിരികെ നൽകുന്നു,
അതിനാൽ restart-കൾക്കുശേഷവും relay പ്രവർത്തിക്കുന്നത് തുടരുന്നു.

## Failure mode 1 — key rotation-നുശേഷം decrypt ചെയ്യാനാകാത്ത token

**ലക്ഷണം:** മുമ്പ് പ്രവർത്തിച്ചിരുന്ന relay-കൾ ഇപ്പോൾ
`STORAGE_ENCRYPTION_KEY`-യുടെ environment അല്ലെങ്കിൽ secret-manager rotation-നുശേഷം upstream `401`/auth
error-കൾ തിരികെ നൽകുന്നു. സംഭരിച്ചിരിക്കുന്ന `relayAuthEnc` blob ഇനി
decrypt ചെയ്യാൻ കഴിയില്ല, അതിനാൽ `extractRelayAuth` ശൂന്യമായ string തിരികെ നൽകുകയും relay
auth ഒന്നും അയയ്ക്കാതിരിക്കുകയും ചെയ്യുന്നു.

**വീണ്ടെടുക്കൽ — നിലവിലുള്ളിടത്തുതന്നെ repair ചെയ്യുക (redeploy ആവശ്യമില്ല):**

1. **Settings → Proxy Pool** തുറക്കുക.
2. auth നഷ്ടമായ relay row-കളിൽ മഞ്ഞ നിറത്തിലുള്ള `auth missing` badge-ഉം
   **Repair** button-ഉം കാണിക്കും.
3. **Repair** ക്ലിക്ക് ചെയ്യുക. OmniRoute
   `POST /api/settings/proxies/[id]/repair-relay` call ചെയ്യുന്നു, അത്:
   - **നിലവിലെ** key ഉപയോഗിച്ച് `relayAuthEnc` decrypt ചെയ്യുന്നു,
   - plaintext `relayAuth` വീണ്ടും `notes`-ലേക്ക് എഴുതുന്നു,
   - `{ repaired: true, mode: "recovered" }` തിരികെ നൽകുന്നു.

Deploy credential-കളൊന്നും വീണ്ടും നൽകാതെ relay സേവനം പുനരാരംഭിക്കുന്നു.

നിലവിലെ `STORAGE_ENCRYPTION_KEY`-ന് ഇപ്പോഴും blob decrypt ചെയ്യാൻ കഴിയുമെങ്കിൽ മാത്രമേ
ഇത് പ്രവർത്തിക്കൂ. migration ഇല്ലാതെ നിങ്ങൾ key rotate ചെയ്തിട്ടുണ്ടെങ്കിൽ, blob
വീണ്ടെടുക്കാനാകില്ല.

## Failure mode 2 — വീണ്ടെടുക്കാനാകാത്ത token (പഴയ key ലഭ്യമല്ല)

**ലക്ഷണം:** നിങ്ങൾ **Repair** ക്ലിക്ക് ചെയ്തപ്പോൾ
`{ repaired: false, mode: "redeploy", status: 409 }` ലഭിച്ചു.

**വീണ്ടെടുക്കൽ — redeploy ചെയ്യുക:**

നിലവിലെ key ഉപയോഗിച്ച് സംഭരിച്ച token വീണ്ടെടുക്കാനാകില്ല. ആദ്യം ഉപയോഗിച്ച അതേ modal-ൽ നിന്ന് relay
വീണ്ടും deploy ചെയ്യുക (**Deploy Relay** menu → Vercel / Deno
/ Cloudflare). deploy flow ഒരു പുതിയ token എഴുതുന്നു (നിലവിലെ
key ഉപയോഗിച്ച് encrypt ചെയ്തത്), തുടർന്ന് row-യിലെ `auth missing` badge അപ്രത്യക്ഷമാകും.

Token വീണ്ടെടുക്കാനാകാത്തപ്പോൾ UI-യിൽ **Repair** button തന്നെയാണ് redeploy modal തുറക്കുന്നത്,
അതിനാൽ അത് നിങ്ങൾക്ക് സ്വയം തിരഞ്ഞുപിടിക്കേണ്ടതില്ല.

## Failure mode 3 — relay ലഭ്യമാണെങ്കിലും ആരോഗ്യകരമല്ല

**ലക്ഷണം:** proxy test (`speed` button) relay പ്രവർത്തനക്ഷമമാണെന്ന് കാണിക്കുന്നു, എന്നാൽ request-ുകൾ
ഇപ്പോഴും ഇടയ്ക്കിടെ പരാജയപ്പെടുന്നു.

OmniRoute-ന്റെ auto-test probe തിരികെ നൽകുന്ന relay awareness header-കൾ പരിശോധിക്കുക
(**Settings → Proxy Pool**-ഉം `relayTested` / `relayAlive` counter-ുകളും കാണുക):

- `x-relay-url` — ഏത് relay backend ആണ് മറുപടി നൽകിയത്.
- `x-relay-mode` — ആ request-നുള്ള `ts` | `bifrost` | `auto`.
- `x-relay-attempts` — വിജയിക്കുന്നതിന് മുമ്പ് എത്ര relay hop-ുകൾ ശ്രമിച്ചു.
- `x-relay-fallback` — request തിരഞ്ഞെടുത്ത backend-ൽ നിന്ന് TypeScript relay-യിലേക്ക്
  fallback ചെയ്തപ്പോൾ `true`.

കുറഞ്ഞ `relayAlive`-നൊപ്പം ഉയർന്ന `x-relay-fallback` നിരക്ക് ഉണ്ടായാൽ sidecar
backend ആരോഗ്യകരമല്ലെന്നാണ് അർത്ഥം. നിങ്ങൾ അത് പരിഹരിക്കുകയോ relay backend
strategy `ts`-ലേക്ക് മാറ്റുകയോ വേണം (`RELAY_BACKEND_STRATEGY.md` കാണുക).

## API റഫറൻസ്

| Method | Path                                      | Body                    | Success                                                                                                                                    | Failure                                                                                                      |
| ------ | ----------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | വീണ്ടും derive ചെയ്യുമ്പോൾ `200 { repaired: true, mode: "recovered" }`; plaintext ഇതിനകം ഉള്ളപ്പോൾ `200 { repaired: false, mode: "noop" }` | വീണ്ടെടുക്കാനാകാത്തപ്പോൾ `409 { mode: "redeploy" }`; relay type അല്ലെങ്കിൽ `400`; കണ്ടെത്തിയില്ലെങ്കിൽ `404` |

List route ആയ `GET /api/settings/proxies`, ഓരോ item-ലേക്കും secret ഉൾപ്പെടാത്ത
`relayInfo: { isRelay, authMissing, repairMode }` ചേർക്കുന്നു. ഇതുവഴി token ഒരിക്കലും വെളിപ്പെടുത്താതെ തന്നെ dashboard-ന്
repair സൗകര്യം render ചെയ്യാൻ കഴിയും.
