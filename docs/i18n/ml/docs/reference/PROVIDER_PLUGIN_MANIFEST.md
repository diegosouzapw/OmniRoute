`open-sse/config/providerPluginManifest.ts` JSON-സുരക്ഷിതമായ പ്രൊവൈഡർ
പ്ലഗിൻ കരാർ നിർവചിക്കുന്നു. `open-sse/config/providerPluginManifestRegistry.ts` ആ
കരാറിനെ Bifrost, CLIProxyAPI, അല്ലെങ്കിൽ ഭാവിയിലെ ഒരു Go/Rust റൗട്ടർ പോലുള്ള
സൈഡ്കാറുകൾക്കായി നിലവിലെ പ്രൊവൈഡർ രജിസ്ട്രിയുമായി ബന്ധിപ്പിക്കുന്നു. TypeScript രജിസ്ട്രി
തുടർന്നും ആധികാരിക ഉറവിടമായി നിലകൊള്ളുന്നു, എന്നാൽ എക്സിക്യൂട്ടർ കോഡ്, OAuth ഡിഫോൾട്ടുകൾ,
ഹെഡറുകൾ, അല്ലെങ്കിൽ പ്രോസസ് എൻവയോൺമെന്റ് സ്റ്റേറ്റ് എന്നിവ ഇംപോർട്ട് ചെയ്യാതെ സൈഡ്കാറുകൾക്ക്
മാനിഫെസ്റ്റ് ഉപയോഗിക്കാം.

പ്രോസസിന് പുറത്തു പ്രവർത്തിക്കുന്ന സൈഡ്കാറുകൾക്കായി ഇതേ മാനിഫെസ്റ്റ് HTTP വഴിയും
`GET /api/v1/provider-plugin-manifest` എന്നതിൽ ലഭ്യമാണ്.

OmniRoute, Bifrost-നും CLIProxyAPI-ക്കും ആ URL
`X-OmniRoute-Provider-Manifest-Url` റിക്വസ്റ്റ് ഹെഡർ വഴി അറിയിക്കുന്നു. സൈഡ്കാറിന്
ലോക്കൽ റിക്വസ്റ്റ് ഒറിജിന് പകരം ഒരു പബ്ലിക് അല്ലെങ്കിൽ കണ്ടെയ്നർ നെറ്റ്വർക്ക് URL
ആവശ്യമുള്ളപ്പോൾ `OMNIROUTE_PROVIDER_MANIFEST_URL` സജ്ജമാക്കുക.

## മാനിഫെസ്റ്റ് പുതുക്കൽ

HTTP എൻഡ്പോയിന്റ് `Cache-Control: public, max-age=60` എന്നതും ശക്തമായ ഒരു
`ETag`-ഉം തിരികെ നൽകുന്നു. ഒരു സൈഡ്കാർ അവസാനം സാധൂകരിച്ച മാനിഫെസ്റ്റ് നിലനിർത്തുകയും
പുതുക്കുമ്പോൾ അതിന്റെ ETag `If-None-Match`-ൽ അയയ്ക്കുകയും വേണം. `304 Not Modified`
റെസ്പോൺസിന് ബോഡി ഉണ്ടായിരിക്കില്ല; സൈഡ്കാർ അതിന്റെ കാഷ് ചെയ്ത മാനിഫെസ്റ്റ് നിലനിർത്തും.
സാധൂകരിച്ച കാഷ് ചെയ്ത മാനിഫെസ്റ്റ് നിലവിലില്ലെങ്കിൽ, `304` സ്വീകരിക്കുന്നതിന് പകരം സൈഡ്കാർ
ഉപാധികളില്ലാത്ത ഒരു റിക്വസ്റ്റ് അയയ്ക്കണം.

## ലക്ഷ്യം

പ്രൊവൈഡർ മെറ്റാഡാറ്റയെ ഒരു പ്ലഗിൻ കരാറിലേക്കു നീക്കുക, അതുവഴി ഹോട്ട് റിക്വസ്റ്റ് പാത്തിന്റെ
ഉടമസ്ഥത ഭാവിയിൽ കുറഞ്ഞ ലേറ്റൻസിയുള്ള ഒരു സൈഡ്കാറിന് ഏറ്റെടുക്കാനാകും; അതേസമയം OmniRoute
TypeScript റൂട്ടിനെ പോളിസി ഗേറ്റായും ഫാൾബാക്കായും നിലനിർത്തും. മാനിഫെസ്റ്റ് കൂട്ടിച്ചേർക്കുന്നതാണ്:
അത് സ്വയം റിക്വസ്റ്റ് റൂട്ടിങ്ങിൽ മാറ്റം വരുത്തുന്നില്ല.

## കരാർ

മാനിഫെസ്റ്റിൽ ഉൾപ്പെടുന്നവ:

- പ്രൊവൈഡർ ഐഡിയും അപരനാമവും
- അപ്സ്ട്രീം ഫോർമാറ്റും എക്സിക്യൂട്ടർ പേരും
- ഓത്ത് തരം, ഓത്ത് ഹെഡർ, ഐച്ഛികമായ ഓത്ത് പ്രിഫിക്സ്
- സ്റ്റാറ്റിക് എൻഡ്പോയിന്റ് മെറ്റാഡാറ്റ
- സൈഡ്കാർ യോഗ്യതയും ഒരു പ്രൊവൈഡർ TS-ൽ തന്നെ തുടരേണ്ട സാഹചര്യത്തിലെ വ്യക്തമായ കാരണങ്ങളും
- കോൺടെക്സ്റ്റ് ദൈർഘ്യം, വിഷൻ/റീസണിങ് ഫ്ലാഗുകൾ, പിന്തുണയ്ക്കാത്ത പാരാമീറ്ററുകൾ തുടങ്ങിയ
  JSON-സുരക്ഷിത മോഡൽ മെറ്റാഡാറ്റ
- `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch`, `usage-supported` എന്നിവ ഉൾപ്പെടുന്ന ശേഷി ടാഗുകൾ

മാനിഫെസ്റ്റ് ഉദ്ദേശ്യപൂർവം ഒഴിവാക്കുന്നവ:

- OAuth ക്ലയന്റ് സീക്രട്ടുകളും ഡിഫോൾട്ട് സീക്രട്ട് മൂല്യങ്ങളും
- റൺടൈം എൻവയോൺമെന്റ് റെസല്യൂഷൻ
- റിക്വസ്റ്റ് ഹെഡറുകളും പബ്ലിക് ക്രെഡൻഷ്യൽ ഹെൽപ്പറുകളും
- ഡൈനാമിക് URL ബിൽഡറുകൾ
- എക്സിക്യൂട്ടർ ഫങ്ഷനുകൾ
- സെഷൻ പൂൾ ഇന്റേണലുകൾ

## ശേഷി ടാഗുകൾ

`capabilities` എന്നത് രജിസ്ട്രി എൻട്രിയിൽ നിന്ന് നിർണയിച്ച, ക്രമീകരിച്ച ടാഗുകളുടെ ഒരു അറേയാണ്. ഇന്റഗ്രേറ്റർമാർ
TypeScript സോഴ്സുകൾ വീണ്ടും വായിക്കുന്നതിന് പകരം, "ഈ പ്രൊവൈഡറിന് എന്തെല്ലാം ചെയ്യാനാകും" എന്നതിനുള്ള
മെഷീൻ-റീഡബിൾ ഉത്തരമായി ഇതിനെ കണക്കാക്കണം.

| ടാഗ്                 | അർത്ഥം                                                                                         |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| `apikey`             | ഒരു API കീ സ്വീകരിക്കുന്നു (`authType` എന്നത് `apikey` അല്ലെങ്കിൽ `optional` ആണ്).             |
| `oauth`              | ഒരു OAuth അല്ലെങ്കിൽ സെഷൻ ഫ്ലോ ഉപയോഗിക്കുന്നു.                                                 |
| `responses`          | ഒരു OpenAI Responses-API ബേസ് URL ലഭ്യമാക്കുന്നു.                                              |
| `passthrough-models` | ഒരു സ്റ്റാറ്റിക് കാറ്റലോഗിന് പകരം അപ്സ്ട്രീമിൽ നിന്ന് നേരിട്ട് മോഡലുകൾ നൽകുന്നു.               |
| `custom-executor`    | ഡിഫോൾട്ടല്ലാത്ത ഒരു എക്സിക്യൂട്ടർ പ്രവർത്തിപ്പിക്കുന്നതിനാൽ, ഇത് TypeScript പാത്തിൽ തുടരുന്നു. |
| `sidecar-candidate`  | `sidecar.eligible` പ്രതിഫലിപ്പിക്കുന്നു — സൈഡ്കാർ ഇംപോർട്ടിനായി പരിഗണിക്കുന്നത് സുരക്ഷിതമാണ്.  |
| `usage-fetch`        | കണക്റ്റ് ചെയ്ത ഒരു ഉപയോഗ അല്ലെങ്കിൽ ക്വോട്ട ഫെച്ചർ (`getUsageForProvider`) ഉണ്ട്.              |
| `usage-supported`    | ഉപയോഗ API ഈ പ്രൊവൈഡറെ സ്വീകരിക്കുന്നു (`isSupportedUsageConnection`).                          |

`usage-fetch` കണ്ടെത്തലിനായി മാത്രമുള്ളതാണ്. പ്രൊവൈഡറുടെ ഉപയോഗം എങ്ങനെ വായിക്കാമെന്ന് OmniRoute-ന്
അറിയാമെന്ന് ഇത് റിപ്പോർട്ട് ചെയ്യുന്നു; ഇത് ഫെച്ചിങ് സജീവമാക്കുകയോ, ക്വോട്ടയുടെ അർത്ഥശാസ്ത്രം മാറ്റുകയോ,
Dashboard ക്വോട്ട വിജറ്റ് പ്രൊവൈഡറിനായി പ്രവർത്തനക്ഷമമാണെന്ന് സൂചിപ്പിക്കുകയോ ചെയ്യുന്നില്ല — ആ വിജറ്റ്
`USAGE_SUPPORTED_PROVIDERS` വഴി വേറിട്ട് നിയന്ത്രിക്കപ്പെടുന്നു. `open-sse/services/usage/fetcherProviders.ts`-ലെ
`USAGE_FETCHER_PROVIDERS` ആണ് ആധികാരിക ഉറവിടം.

ഉപയോഗ ഡിസ്പാച്ചർ സ്വീകരിക്കുന്ന സ്ട്രിങ്ങുകളെ അടിസ്ഥാനമാക്കിയാണ് ആ ലിസ്റ്റിന്റെ കീകൾ നിശ്ചയിച്ചിരിക്കുന്നത്,
അതിനാൽ അതിൽ കാനോണിക്കൽ ഐഡികളും അപരനാമങ്ങളും കലർന്നിരിക്കുന്നു; ടാഗ് ചെയ്ത പ്രൊവൈഡർമാരുടെ എണ്ണത്തേക്കാൾ

## സൈഡ്കാർ ഉപയോഗം

സൈഡ്കാറുകൾ `sidecar.eligible`-നെ നിരുപാധികമായ ഒരു റൂട്ടിംഗ് തീരുമാനമായല്ല, മറിച്ച് കരുതലോടെയുള്ള ഒരു സ്ഥാനാർഥി സിഗ്നലായി പരിഗണിക്കണം. ഡിഫോൾട്ട് എക്സിക്യൂട്ടർ ഉപയോഗിക്കുന്ന API-key, static-endpoint പ്രൊവൈഡർമാരായിരിക്കണം ആദ്യ ഇംപോർട്ട് ലക്ഷ്യം. തുല്യമായ പെരുമാറ്റം ഒരു സൈഡ്കാർ നടപ്പാക്കുകയും ടെലിമെട്രി സമാനത തെളിയിക്കുകയും ചെയ്യുന്നതുവരെ, custom web executors, OAuth/session ഫ്ലോകൾ, dynamic URL builders, അല്ലെങ്കിൽ pool config ഉള്ള പ്രൊവൈഡർമാർ TypeScript fallback പാതയിൽ തുടരണം.

നിർദ്ദേശിക്കുന്ന മൈഗ്രേഷൻ ഘട്ടങ്ങൾ:

1. TS registry-യിൽ നിന്ന് provider plugin manifest സൃഷ്ടിച്ച് സാധൂകരിക്കുക.
2. API-key/static പ്രൊവൈഡർമാർക്കായി manifest ഇംപോർട്ട് ചെയ്യാൻ Bifrost അല്ലെങ്കിൽ CLIProxyAPI-യെ പ്രാപ്തമാക്കുക.
3. TS fallback പ്രവർത്തനക്ഷമമായി നിലനിർത്തിക്കൊണ്ട്, `OMNIROUTE_RELAY_BACKEND`-ന് പിന്നിലുള്ള സൈഡ്കാറിലൂടെ യോഗ്യരായ പ്രൊവൈഡർമാരെ റൂട്ട് ചെയ്യുക.
4. വിജയനിരക്ക്, p99 latency, streaming പെരുമാറ്റം, unsupported-param കൈകാര്യംചെയ്യൽ എന്നിവ TS പാതയുമായി പൊരുത്തപ്പെടുമ്പോൾ മാത്രം പ്രൊവൈഡർമാരെ പ്രൊമോട്ട് ചെയ്യുക.
5. custom executors-നായി ഓരോ provider family വീതം sidecar-native plugins ചേർക്കുക.

## പ്രൊവൈഡർമാരെ നേരിട്ട് Next-ൽ ഉൾച്ചേർക്കാത്തത് എന്തുകൊണ്ട്

Next frontend പ്രൊവൈഡർ എക്സിക്യൂഷന്റെ ചുമതല വഹിക്കരുത്. അത് API boundary-യെ വിളിക്കണം. തുടർന്ന് TypeScript executor, Bifrost, CLIProxyAPI, അല്ലെങ്കിൽ ഭാവിയിലെ native sidecar എന്നിവയിൽ ഏതാണ് ഉപയോഗിക്കേണ്ടതെന്ന് backend-ന് തീരുമാനിക്കാം. ഏതൊരു sidecar handoff-നും മുമ്പ് request signing, allowlist checks, DB policy, fallback പെരുമാറ്റം എന്നിവ കേന്ദ്രീകൃതമായി നിലനിർത്താൻ ഇത് സഹായിക്കുന്നു.
