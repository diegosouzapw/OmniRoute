Välityspalvelut (Vercel, Deno, Cloudflare) päättävät ylävirran yhteyden
palvelimettomassa taustajärjestelmässä, jotta OmniRoute voi ohjata lähtevän liikenteen
vakaalta alueelta ja pitää samalla palveluntarjoajan API-avaimen palvelinpuolella.
Tässä asiakirjassa käsitellään kahta tuotantoympäristössä esiintyvää vikatilaa
sekä OmniRouten tarjoamia palautusmenetelmiä kummallekin.

## Välityspalvelimen todennuksen tallennustapa

Kun otat välityspalvelimen käyttöön kohdasta **Asetukset → Välityspalvelinvaranto → Ota välityspalvelin käyttöön**,
käyttöönottoprosessi tallentaa välityspalvelimen todennustunnuksen välityspalvelimen
`notes`-JSON-kenttään:

- Jos `STORAGE_ENCRYPTION_KEY` on asetettu, tunnus tallennetaan nimellä `relayAuthEnc`
  (AES-salattuna levossa).
- Muussa tapauksessa se tallennetaan selväkielisenä nimellä `relayAuth`.

Pyyntöä käsiteltäessä `extractRelayAuth(notes)` palauttaa käytettävissä olevan
muodon, joten välityspalvelin jatkaa toimintaansa uudelleenkäynnistysten jälkeen.

## Vikatila 1 — tunnusta ei voida purkaa avaimen kierrättämisen jälkeen

**Oire:** aiemmin toimineet välityspalvelimet palauttavat nyt ylävirran `401`- tai
todennusvirheitä sen jälkeen, kun `STORAGE_ENCRYPTION_KEY` on kierrätetty
ympäristössä tai salaisuuksien hallintajärjestelmässä. Tallennettua `relayAuthEnc`-blobia
ei voi enää purkaa, joten `extractRelayAuth` palauttaa tyhjän merkkijonon eikä
välityspalvelin lähetä todennustietoja.

**Palautus — korjaa paikallaan (ei uutta käyttöönottoa):**

1. Avaa **Asetukset → Välityspalvelinvaranto**.
2. Välityspalvelinriveillä, joilta todennus puuttuu, näkyy keltainen `auth missing` -merkki ja
   **Korjaa**-painike.
3. Napsauta **Korjaa**. OmniRoute kutsuu
   `POST /api/settings/proxies/[id]/repair-relay` -päätepistettä, joka:
   - purkaa `relayAuthEnc`-arvon salauksen **nykyisellä** avaimella,
   - kirjoittaa selväkielisen `relayAuth`-arvon takaisin `notes`-kenttään,
   - palauttaa `{ repaired: true, mode: "recovered" }`.

Välityspalvelin jatkaa pyyntöjen käsittelyä ilman käyttöönottotunnusten
syöttämistä uudelleen.

Tämä toimii vain, jos nykyinen `STORAGE_ENCRYPTION_KEY` pystyy edelleen purkamaan
blobin salauksen. Jos kierrätit avaimen **ilman** migraatiota, blobia
ei voida palauttaa.

## Vikatila 2 — tunnusta ei voida palauttaa (avain on poistunut käytöstä kierrättämisen yhteydessä)

**Oire:** napsautit **Korjaa** ja sait vastauksen
`{ repaired: false, mode: "redeploy", status: 409 }`.

**Palautus — ota uudelleen käyttöön:**

Tallennettua tunnusta ei voida palauttaa nykyisellä avaimella. Ota välityspalvelin
uudelleen käyttöön samasta valintaikkunasta, jota käytit alun perin
(**Ota välityspalvelin käyttöön** -valikko → Vercel / Deno / Cloudflare).
Käyttöönottoprosessi kirjoittaa uuden tunnuksen (salattuna nykyisellä avaimella),
ja rivin `auth missing` -merkki poistuu.

Käyttöliittymässä **Korjaa**-painike avaa automaattisesti uudelleenkäyttöönoton
valintaikkunan, jos tunnusta ei voida palauttaa, joten sinun ei tarvitse etsiä
sitä manuaalisesti.

## Vikatila 3 — välityspalvelin on tavoitettavissa mutta epäkunnossa

**Oire:** välityspalvelintesti (`speed`-painike) näyttää välityspalvelimen olevan
toiminnassa, mutta pyynnöt epäonnistuvat edelleen ajoittain.

Tarkista OmniRouten automaattisen testikyselyn palauttamat välityspalvelimen
tilatieto-otsakkeet (katso **Asetukset → Välityspalvelinvaranto** sekä
`relayTested`- ja `relayAlive`-laskurit):

- `x-relay-url` — mikä välityspalvelimen taustajärjestelmä vastasi.
- `x-relay-mode` — kyseisen pyynnön tila: `ts` | `bifrost` | `auto`.
- `x-relay-attempts` — kuinka monta välityspalvelinhyppyä kokeiltiin ennen onnistumista.
- `x-relay-fallback` — `true`, kun pyyntö siirtyi ensisijaisesta
  taustajärjestelmästä TypeScript-välityspalvelimeen.

Suuri `x-relay-fallback`-osuus yhdessä pienen `relayAlive`-arvon kanssa
tarkoittaa, että sidecar-taustajärjestelmä on epäkunnossa. Se on joko korjattava
tai välityspalvelimen taustajärjestelmästrategiaksi on vaihdettava `ts`
(katso `RELAY_BACKEND_STRATEGY.md`).

## API-viite

| Menetelmä | Polku                                     | Runko                   | Onnistuminen                                                                                                                                              | Epäonnistuminen                                                                                                         |
| --------- | ----------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `POST`    | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }`, kun arvo johdetaan uudelleen; `200 { repaired: false, mode: "noop" }`, kun selväkielinen arvo on jo olemassa | `409 { mode: "redeploy" }`, jos palautus ei onnistu; `400`, jos tyyppi ei ole välityspalvelin; `404`, jos sitä ei löydy |

Luetteloreitti `GET /api/settings/proxies` liittää jokaiseen kohteeseen
salaisuuksia sisältämättömän `relayInfo: { isRelay, authMissing, repairMode }` -arvon,
jotta hallintapaneeli voi näyttää korjaustoiminnon paljastamatta tunnusta missään
vaiheessa.
