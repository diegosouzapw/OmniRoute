Tämän oppaan avulla voit valita pienimmän luotettavan kehityssyklin pull requestille. Se ei
korvaa alla linkitettyjä aluekohtaisia arkkitehtuuri- ja tietoturva-asiakirjoja, vaan yhdistää
yleiset muutostyypit niiden sopimuksiin, kohdennettuihin tarkistuksiin ja CI-kattavuuteen.

## Jokaisen muutoksen kulkema polku

1. **Valitse pohjahaara ennen muokkaamista.** Etsi korkein aktiivinen `release/v*`-haara ja luo uusi
   haara sen kärjestä. Kohdista PR kyseiseen haaraan, älä `main`-haaraan. Jos julkaisujäädytys on
   voimassa, älä kohdista PR:ää jäädytettyyn haaraan, vaan käytä seuraavaa aktiivista sykliä, joka on
   kuvattu dokumentissa [Haarautumis- ja julkaisumalli](BRANCHING_MODEL.md).
2. **Nimeä sopimukset.** Tunnista kaikki katalogit, skeemat, generoidut artefaktit, julkiset
   rajapinnat tai käyttöliittymät, joihin muutos vaikuttaa. Alla oleva taulukko sisältää
   vähimmäislähtökohdat.
3. **Kirjoita tai päivitä kohdennetut testit.** Tuotantokoodin muutokset hakemistoissa `src/`,
   `open-sse/`, `electron/` tai `bin/` edellyttävät automatisoitua testiä samassa PR:ssä. Suorita
   ensin pienin joukko testitiedostoja, joka todentaa toiminnan, ja sitten luetellut kohdennetut
   tarkistukset.
4. **Anna CI:n suorittaa laaja matriisi.** Täydelliset yksikkötestiosiot, Vitest, kattavuuden
   vähimmäistason tarkistus ja tuotantokäännös suoritetaan PR:lle. Suorita laaja testikokonaisuus
   paikallisesti vain, jos kohdennettu virhe viittaa laajempaan vaikutukseen tai jos muutos kattaa
   useita alijärjestelmiä.
5. **Yhteensovita muutokset ennen katselmointia.** Nouda aktiivinen pohjahaara, tarkista sen uudet
   commitit ja oma diffisi sitä vasten ja tee sitten rebase tai merge pohjahaarasta
   osallistujatyönkulun mukaisesti. Ratkaise generoitujen tiedostojen ja katalogien ristiriidat
   niiden lähteessä, generoi ne uudelleen, suorita kohdennettu sykli uudelleen ja varmista, että PR
   on edelleen kohdistettu aktiiviseen julkaisuhaaraan.
6. **Kirjaa todisteet.** Luettele PR-mallipohjassa suoritetut komennot, kaikki lisätyt tai muutetut
   testitiedostot, migraatiot tai ominaisuusliput sekä mahdolliset vain CI:ssä tehtävät tarkistukset,
   jotka ovat vielä kesken.

## Vakiopolut muutostyypeittäin

Alla olevat komennot ovat kohdennettujen tarkistusten vähimmäisvaatimukset, eivät lupa ohittaa testiä,
joka kattaa suoraan muuttamasi toiminnan.

### Palveluntarjoaja

**Sopimukset**

- Palveluntarjoajan määritys hakemistossa `src/shared/constants/providers/` ja sen koostaminen
  tiedostossa `src/shared/constants/providers.ts`.
- Mallit ja ominaisuudet tiedostossa `open-sse/config/providerRegistry.ts` tai siitä erotetuissa
  rekisteritiedostoissa.
- Suorittimen/kääntäjän valinta, OAuth- tai API-avainmääritys, hallintapaneelin resurssit ja
  generoitu palveluntarjoajaviite soveltuvin osin.
- Julkisissa tunnistetiedoissa on käytettävä `resolvePublicCred()`-funktiota; virhevastauksissa on
  käytettävä yhteisiä sanitointiapufunktioita. Katso `docs/security/PUBLIC_CREDS.md` (gitissä; ei
  käännetä hakemistoon `/docs`) ja
  [Virheiden sanitointi](../security/ERROR_SANITIZATION.md).

**Kohdennettu sykli**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # kun katalogi muuttuu; sisällytä generoitu diff commitiin
npm run lint
```

Testaa myös jokainen muuttunut pyyntöperhe: chat, Responses, kuvat, upotukset, ääni tai video.
Käsittele generoitujen katalogien ja golden-tiedostojen diffejä sopimusmuutoksina; älä hyväksy niitä
kritiikittä.

### Reititys

**Sopimukset**

- Julkiset strategiavaihtoehdot ja käyttöliittymän metatiedot tiedostossa
  `src/shared/constants/routingStrategies.ts`.
- Pyyntöjen välitys ja järjestys tiedostossa `open-sse/services/combo.ts` ja hakemistossa
  `open-sse/services/combo/`.
- Combo-skeemat, pysyvyys, vikasietoisuuden tila, mallien ominaisuudet sekä API:n ja käyttöliittymän
  hallintatoiminnot.
- [Automaattinen Combo-moottori](../routing/AUTO-COMBO.md) ja vikasietoisuusdokumentaatio, kun
  toiminta muuttuu.

**Kohdennettu sykli**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategian tai pyyntöjen välityksen muutokset
npm run check:known-symbols      # strategian rekisteröinnin muutokset
npm run lint
```

Käytä paikallisesti deterministisiä testejä, joissa ylävirran palvelu on mockattu. Reaaliaikaiset
Combo-savutestit edellyttävät tunnistetietoja ja ovat manuaalisia, eivät CI-testien korvikkeita.

### Käyttöliittymä / käyttökokemus

**Sopimukset**

- Next.js-reitti/-sivu ja jaettujen komponenttien rajat hakemistoissa `src/app/` ja
  `src/shared/components/`.
- API-vastausten muodot, lataus-, tyhjä- ja virhetilat, näppäimistön ja ruudunlukijan toiminta,
  responsiivinen asettelu, teemat ja kielialueiden laajennus.
- Englanninkieliset käyttöliittymän lähdemerkkijonot tiedostossa `src/i18n/messages/en.json`; älä
  kovakoodaa uutta käyttäjälle näkyvää tekstiä.

**Kohdennettu sykli**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Suorita sovellus vuorovaikutus- tai visuaalisia muutoksia varten ja tarkista sekä kapeat että leveät
näkymät. CI suorittaa tuotantokäännöksen ja laajemmat testikokonaisuudet; visuaalinen toiminta
edellyttää silti muutokseen soveltuvaa kohdennettua komponenttitestiä, Playwright-testiä tai
dokumentoituja manuaalisia tarkistuksia.

### i18n

**Sopimukset**

- `src/i18n/messages/en.json` on käyttöliittymän lähde; `config/i18n.json` on kielialueiden lähde.
- CLI-katalogit sijaitsevat erikseen hakemistossa `bin/cli/locales/`.
- Säilytä ICU-paikkamerkit ja tunnisteet täsmälleen ennallaan. Älä käännä tuotteiden,
  palveluntarjoajien tai mallien nimiä, protokollien tai otsakkeiden nimiä, komentoja, koodi- tai
  JSON-tunnisteita, URL-osoitteita, ympäristömuuttujia tai suojattuja termejä, kuten `OmniRoute`,
  `OAuth`, `MCP` ja `A2A`. Nykyinen lähdeluettelo on
  `scripts/i18n/glossary/protected-terms.json`.

**Kohdennettu sykli**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # kun CLI-merkkijonot tai -katalogit muuttuvat
npm run lint
```

Tämä on ohjeistus nykyistä järjestelmää varten, ei kehotus laajentaa sen työkaluja tai avainmallia.
Pidä i18n-muutokset tarkasti rajattuina korvaavan järjestelmän suunnittelun aikana. Älä suorita
ulkoisia palveluita käyttäviä käännöskomentoja, ellei tehtävä nimenomaisesti edellytä generoituja
käännöksiä ja ellet ole tarkistanut syntynyttä diffiä.

### CLI

**Sopimukset**

- Julkiset komennot ja valitsimet hakemistossa `bin/cli/`, generoidut API-komennot, lopetuskoodit, stdout/stderr ja
  JSON-tulosteiden rakenteet, määritysten ja ympäristön toiminta sekä pakettiin sisällytettävät tiedostot.
- CLI:n käyttäjälle näkyvien merkkijonojen on käytettävä CLI:n i18n-kerrosta, ja `en`/`pt-BR`-luettelot on pidettävä yhdenmukaisina.
- Säilytä Node tuettuna suoritusympäristönä ja julkaistun binääritiedoston sopimus.

**Kohdennettu kierros**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # generoidun/paketoidun CLI:n muutokset
npm run check:pack-policy     # paketin julkisen pinnan muutokset
npm run lint
```

Käytä täsmällistä komentoa väliaikaisessa datahakemistossa, kun toiminta riippuu jäsentämisestä, tiedostoista tai
lopetustilasta. CI suorittaa laajemmat pakettiartefakti- ja ekosysteemitarkistukset.

### Tietokanta

**Sopimukset**

- Toimialuemoduulit sijaitsevat hakemistossa `src/lib/db/`; tuo tietyt moduulit suoraan (vanha `localDb.ts`-uudelleenvientikerros on poistettu).
- Numeroidut ja idempotentit SQL-migraatiot hakemistossa `src/lib/db/migrations/`, transaktioturvallisuus, päivitysten
  toiminta, indeksit sekä kaikki skeeman vaikutuspiirissä olevat kutsujat.
- Reitit ja käsittelijät eivät koskaan suorita raakaa SQL:ää suoraan.

**Kohdennettu kierros**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Kun lisäät migraation, testaa sekä uusi tietokanta että päivitys aiemmasta skeemasta. Tietokantatestien
on suljettava kahvat ja kutsuttava `resetDbInstance()`-funktiota siivouksen aikana. Suorita `npm run test:bun:db` vain, kun
parhaan yrityksen Bun-sovitinpolku muuttuu; Node säilyy määräävänä.

### Koonti / käyttöönotto

**Sopimukset**

- Juuren ja työtilojen manifestit/lukkotiedosto, `scripts/build/`, Next.js:n itsenäinen kokoonpano, `dist/`-paketin
  sisältö, Electronin alustakohtaiset metatiedot, CI-työnkulut sekä käyttöönoton tarkistuspisteet.
- Tuetut Node-versioalueet ja `CLAUDE.md`-tiedostossa sallittujen Bun-käyttötapojen luettelo on säilytettävä ennallaan.
- Koontiartefakteja ei seurata versionhallinnassa; riippuvuus-, lisenssi-, työnkulku- ja pakettikäytännöt ovat voimassa.

**Kohdennettu kierros**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # riippuvuuden tai lukkotiedoston muutokset
npm run check:pack-policy      # julkaistun paketin pinnan muutokset
npm run lint
```

Käytä komentoa `npm run build` paikallisesti vain, kun muutos vaikuttaa kääntämiseen, itsenäiseen kokoonpanoon, resursseihin
tai suorituksenaikaiseen niputtamiseen. Käytä komentoa `npm run build:release` vain julkaisun tai käyttöönoton validointiin. CI:n koonti on
lopullinen alustariippumaton signaali; alustakohtaiset Electron-muutokset edellyttävät vastaavaa kohdennettua koontia
tai smoke-testin tuloksia.

## Paikallinen ehdokassilmukka

Lähdekooditestit eivät voi todistaa, että paketoitu artefakti käynnistyy: paketointiluetteloiden, karsittujen riippuvuuksien
ja natiivien binääritiedostojen ongelmat ilmenevät vasta, kun tar-paketti asennetaan ja käynnistetään. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) on RFC #8084:ssä kuvatun kerran koonti / validointi / julkaisu -prosessin
paikallinen osa: se kokoaa yhden ehdokkaan, validoi täsmälleen kyseisen artefaktin, julkaisee sen nimeämällä
hakemistoja uudelleen ja palauttaa sen takaisin, jos julkaistun paikan kuntotarkistus epäonnistuu.

```bash
npm run dev:candidate -- run --dry-run --json  # tulosta suunnitelma muuttamatta mitään
npm run dev:candidate -- run                   # kokoa + validoi + julkaise, automaattinen palautus
npm run dev:candidate -- build                 # npm pack + asenna hakemistoon _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # käynnistä vapaassa portissa, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # vaihda current ja previous keskenään
npm run dev:candidate -- run --from-tarball <file.tgz>  # käytä muualla (CI:ssä) koottua tar-pakettia
```

- **Kokoa kerran.** `build` paketoi nykyisen puun (se tarvitsee tiedoston `dist/server.js`, joten suorita
  ensin `npm run build:release`) tai kopioi parametrilla `--from-tarball` annetun tiedoston ja asentaa sitten tar-paketin
  eristettyyn npm-etuliitteeseen, koska tar-paketti ei sisällä `node_modules`-hakemistoa. Tunniste on lyhyt `HEAD`-sha
  (`-dirty`, kun puussa on paikallisia muutoksia) tai tar-paketille `tgz-<sha256>`. Puhdas tunniste, joka
  on jo koottu, käytetään uudelleen uuden koonnin sijaan; kokoa se uudelleen antamalla `--force`.
- **Validoi paketti, älä lähdekoodia.** `validate` käynnistää asennetun CLI:n
  (`serve --port <free port>`) käyttäen tuoretta `DATA_DIR=<candidate>/data`-hakemistoa ja valetunnuksia sekä poistamalla
  operaattorin `OMNIROUTE_API_KEY`-, `STORAGE_ENCRYPTION_KEY`- ja `INITIAL_PASSWORD`-arvot
  ympäristöstä, jotta se tarkistaa uuden asennuksen avaimettoman loopback-toimintatavan. Se odottaa, että
  `GET /api/health` palauttaa arvon 200, edellyttää, että `GET /v1/models` palauttaa arvon 200, pysäyttää prosessiryhmän
  ja tallentaa tuloksen tiedostoon `validation.json` yhdessä tar-paketin tiivisteen kanssa.
- **Julkaise sama artefakti.** `promote` hylkää ehdokkaan, jolla ei ole hyväksyttyä validointia sen
  nykyiselle tar-paketin tiivisteelle. Aktiivinen oletuspaikka on `_artifacts/candidate/current`; `--target <dir>`
  valitsee toisen hakemiston samasta tiedostojärjestelmästä, ja sen edellinen paikka on `<dir>.previous`.
  Jokainen uudelleennimeäminen on atominen, ja kesken prosessin tapahtuva virhe kumoaa jo tehdyt uudelleennimeämiset.
- **Palauta takaisin.** `run` validoi julkaistun paikan uudelleen ja vaihtaa `current`- ja `previous`-paikat takaisin keskenään, jos
  tarkistus epäonnistuu. Ensimmäisessä validoinnissa epäonnistunutta ehdokasta ei koskaan julkaista.

Kaikki kirjoitetaan Gitin ohittamaan `_artifacts/candidate/`-hakemistoon; olemassa olevaan OmniRoute-
asennukseen ja sen datahakemistoon ei koskaan kosketa. Julkaistu CLI sijaitsee polussa
`_artifacts/candidate/current/prefix/bin/omniroute`; käynnistä se omalla `DATA_DIR`-arvollasi, kun käytät
sitä. Poistumiskoodit: `0` onnistuminen, `1` epäonnistunut validointi tai julkaisu, `2` käyttövirhe tai puuttuva koonti.

## Paikallinen silmukka verrattuna CI:hin

| Suorita paikallisesti jokaiselle korjaukselle                                                  | CI tarjoaa laaja-alaisen signaalin                                                |
| ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Yllä mainitut suorat toimintatestit ja kategoriaportit                                         | Ositettu täydellinen yksikkötestisarja ja sarjamuotoiset testit                   |
| `npm run lint`                                                                                 | Vitest-testisarjat sekä kattavuus- ja laatukynnykset                              |
| Tyyppitarkistus tai koonti vain, kun muutoksen kohteena oleva sopimus sitä edellyttää          | Tuotantokoonti sekä tietoturva-, dokumentaatio-, riippuvuus- ja PR-käytäntöportit |
| Manuaaliset vuorovaikutus- ja live-tarkistukset vain, kun automaatio ei voi todentaa toimintaa | Työnkulussa määritetyt töiden väliset integraatio- ja alustatarkistukset          |

Vihreä kohdennettu silmukka on näyttöä muutetusta sopimuksesta, ei todiste siitä, että asiaan liittymättömät CI-tarkistukset
läpäistään. Älä myöskään anna jokaisen paikallisen muokkauksen odottaa koko repositoriomatriisin suorittamista.

## Täsmäytyksen tarkistuslista

Ennen tarkistuspyynnön lähettämistä:

- Varmista, että PR:n pohjana on edelleen korkein aktiivinen `release/v*`-haara.
- Nouda kyseinen pohjahaara ja tarkista haarautumisesi jälkeen siihen lisätyt commitit.
- Tarkista komennolla `git diff <active-base>...HEAD`, ettei mukana ole tahattomia tai generoituja muutoksia.
- Ratkaise luetteloiden ja generoitujen dokumenttien ristiriidat päivittämällä lähde ja generoimalla tuloste uudelleen.
- Suorita täsmäytyksen jälkeen uudelleen kaikki PR-kuvauksessa luetellut kohdennetut testit ja portit.
- Älä koskaan heikennä ehtolausekkeita tai poista vaadittuja testejä vain mukautuaksesi muuttuneeseen pohjahaaraan.

Julkaisujäädytystä ja uudelleenkohdistamista koskevat säännöt ovat dokumentissa
[Haarautumis- ja julkaisumalli](BRANCHING_MODEL.md). Täydellinen CI-luettelo on dokumentissa
[Laatuporttien viite](../architecture/QUALITY_GATES.md).
