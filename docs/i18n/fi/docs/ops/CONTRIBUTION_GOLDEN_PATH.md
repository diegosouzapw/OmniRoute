Tämän oppaan avulla voit valita pienimmän luotettavan kehityssilmukan pull requestille. Se ei
korvaa alla linkitettyjä aluekohtaisia arkkitehtuuri- ja tietoturva-asiakirjoja, vaan yhdistää kunkin
yleisen muutostyypin sen sopimuksiin, kohdennettuihin tarkistuksiin ja CI-kattavuuteen.

## Jokaisen muutoksen etenemispolku

1. **Valitse kantahaara ennen muokkaamista.** Etsi korkein aktiivinen `release/v*`-haara ja luo haara
   sen kärjestä. Kohdista kyseiseen haaraan, älä `main`-haaraan. Jos julkaisujäädytys on voimassa, älä
   kohdista jäädytettyyn haaraan, vaan käytä seuraavaa aktiivista sykliä, joka on kuvattu asiakirjassa
   [Haarautumis- ja julkaisumalli](BRANCHING_MODEL.md).
2. **Nimeä sopimukset.** Tunnista kaikki katalogit, skeemat, generoidut artefaktit, julkiset API:t ja
   käyttöliittymät, joihin muutos vaikuttaa. Alla olevassa taulukossa annetaan vähimmäislähtöjoukko.
3. **Kirjoita tai päivitä kohdennetut testit.** Tuotantokoodin muutokset hakemistoissa `src/`,
   `open-sse/`, `electron/` tai `bin/` edellyttävät automatisoitua testiä samassa PR:ssä. Suorita
   pienimmät testitiedostot, jotka todentavat toiminnan, ja sen jälkeen luetellut kohdennetut portit.
4. **Anna CI:n suorittaa laaja matriisi.** Täydelliset yksikkötestien osiot, Vitest,
   kattavuuskynnyksen tarkistus ja tuotantokoonti suoritetaan PR:lle. Suorita laaja testikokonaisuus
   paikallisesti vain, jos kohdennettu virhe viittaa laajempiin vaikutuksiin tai jos muutos kattaa
   useita alijärjestelmiä.
5. **Yhteensovita ennen katselmointia.** Nouda aktiivinen kantahaara, tarkista sen uudet commitit ja
   oma diffisi siihen nähden ja tee sitten rebase tai yhdistä kantahaara avustajien työnkulun
   mukaisesti. Ratkaise generoitujen tiedostojen ja katalogien ristiriidat niiden lähteessä, generoi
   ne uudelleen, suorita kohdennettu silmukka uudelleen ja varmista, että PR kohdistuu edelleen
   aktiiviseen julkaisuhaaraan.
6. **Kirjaa todisteet.** Luettele PR-mallissa suoritetut komennot, kaikki lisätyt tai muutetut
   testitiedostot, migraatiot tai ominaisuusliput sekä kaikki vielä odottavat vain CI:ssä tehtävät
   validoinnit.

## Suositellut polut muutostyypeittäin

Alla olevat komennot ovat kohdennettujen tarkistusten vähimmäisvaatimuksia, eivät lupa ohittaa testiä,
joka kattaa muuttamasi toiminnan suoraan.

### Palveluntarjoaja

**Sopimukset**

- Palveluntarjoajan määritys hakemistossa `src/shared/constants/providers/` ja sen koostaminen
  tiedostossa `src/shared/constants/providers.ts`.
- Mallit ja ominaisuudet tiedostossa `open-sse/config/providerRegistry.ts` tai siitä erotetuissa
  rekisteritiedostoissa.
- Suorittimen/kääntäjän valinta, OAuth- tai API-avainmääritys, hallintapaneelin resurssit ja
  generoitu palveluntarjoajaviite soveltuvin osin.
- Julkisten tunnistetietojen on käytettävä `resolvePublicCred()`-funktiota, ja virhevastausten on
  käytettävä jaettuja puhdistettuja virheaputoimintoja. Katso `docs/security/PUBLIC_CREDS.md`
  (gitissä; sitä ei koota hakemistoon `/docs`) ja
  [Virheiden puhdistaminen](../security/ERROR_SANITIZATION.md).

**Kohdennettu silmukka**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # kun katalogi muuttuu; commitoi generoitu diff
npm run lint
```

Testaa myös jokainen muuttunut pyyntöperhe: chat, Responses, kuvat, upotukset, ääni tai video.
Käsittele generoituja katalogi- ja golden-diffejä sopimusmuutoksina; älä hyväksy niitä sokeasti.

### Reititys

**Sopimukset**

- Julkiset strategiavaihtoehdot ja käyttöliittymän metatiedot tiedostossa
  `src/shared/constants/routingStrategies.ts`.
- Välitys ja järjestys tiedostossa `open-sse/services/combo.ts` ja hakemistossa
  `open-sse/services/combo/`.
- Combo-skeemat, pysyvyys, vikasietoisuustila, mallien ominaisuudet sekä API- ja
  käyttöliittymäohjaimet.
- [Auto-Combo-moottori](../routing/AUTO-COMBO.md) ja vikasietoisuusdokumentaatio, kun toiminta
  muuttuu.

**Kohdennettu silmukka**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategian tai välityksen muutokset
npm run check:known-symbols      # strategian rekisteröinnin muutokset
npm run lint
```

Käytä paikallisesti deterministisiä testejä, joissa upstream-palvelut on mockattu. Reaaliaikaiset
combo-savutestit vaativat tunnistetiedot ja ovat manuaalisia, eivät CI:n korvikkeita.

### Käyttöliittymä / käyttökokemus

**Sopimukset**

- Next.js-reitin/-sivun ja jaettujen komponenttien rajat hakemistoissa `src/app/` ja
  `src/shared/components/`.
- API-vastausten rakenteet, lataus-/tyhjä-/virhetilat, näppäimistö- ja ruudunlukijakäyttö,
  responsiivinen asettelu, teemat ja locale-laajennukset.
- Englanninkieliset käyttöliittymän lähdemerkkijonot tiedostossa `src/i18n/messages/en.json`; älä
  kovakoodaa uutta käyttäjälle näkyvää tekstiä.

**Kohdennettu silmukka**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Käynnistä sovellus vuorovaikutus- tai visuaalisia muutoksia varten ja tarkista sekä kapeat että leveät
näkymät. CI suorittaa tuotantokoontiversion ja laajemmat testikokonaisuudet; visuaalinen toiminta
tarvitsee silti muutokseen soveltuvan kohdennetun komponentti- tai Playwright-testin tai dokumentoidun
manuaalisen tarkistuksen.

### i18n

**Sopimukset**

- `src/i18n/messages/en.json` on käyttöliittymän lähde; `config/i18n.json` on locale-lähde.
- CLI-katalogit sijaitsevat erikseen hakemistossa `bin/cli/locales/`.
- Säilytä ICU-paikkamerkit ja tagit täsmälleen ennallaan. Älä käännä tuote-, palveluntarjoaja- tai
  mallinimiä, protokollien ja otsakkeiden nimiä, komentoja, koodi-/JSON-tunnisteita, URL-osoitteita,
  ympäristömuuttujia tai suojattuja termejä, kuten `OmniRoute`, `OAuth`, `MCP` ja `A2A`. Nykyinen
  lähdeluettelo on `scripts/i18n/glossary/protected-terms.json`.

**Kohdennettu silmukka**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # kun CLI-merkkijonot tai -katalogit muuttuvat
npm run lint
```

Tämä on nykyistä järjestelmää koskevaa ohjeistusta, ei kehotus laajentaa sen työkaluja tai
avainmallia. Pidä i18n-muutokset tarkasti rajattuina, kun korvaavaa järjestelmää suunnitellaan. Älä
suorita ulkoisia palveluita kutsuvia käännöskomentoja, ellei tehtävä nimenomaisesti edellytä
generoituja käännöksiä ja ellet ole tarkistanut tuloksena syntyvää diffiä.

### CLI

**Sopimukset**

- Julkiset komennot ja valitsimet hakemistossa `bin/cli/`, generoidut API-komennot, poistumiskoodit, stdout/stderr ja
  JSON-tulosteiden rakenteet, määritysten ja ympäristön toiminta sekä pakettiin sisällytettävät tiedostot.
- Käyttäjälle näkyvien CLI-merkkijonojen on käytettävä CLI:n i18n-kerrosta, ja `en`/`pt-BR`-luettelot on pidettävä yhdenmukaisina.
- Säilytä Node tuettuna ajoympäristönä ja julkaistun binääritiedoston sopimus ennallaan.

**Kohdennettu sykli**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # generoidun/paketoidun CLI:n muutokset
npm run check:pack-policy     # paketin julkisen pinnan muutokset
npm run lint
```

Käytä täsmällistä komentoa tilapäisessä datahakemistossa, kun toiminta riippuu jäsentämisestä, tiedostoista tai
poistumistilasta. CI suorittaa laajemmat pakettiartefaktien ja ekosysteemin tarkistukset.

### Tietokanta

**Sopimukset**

- Toimialuemoduulit sijaitsevat hakemistossa `src/lib/db/`; tuo tietyt moduulit suoraan (vanha `localDb.ts`-jälleenvientikerros on poistettu).
- Numeroituja ja idempotentteja SQL-migraatioita hakemistossa `src/lib/db/migrations/`, transaktioturvallisuus, päivitysten
  toiminta, indeksit sekä jokainen skeeman muuttamisen vaikutuspiirissä oleva kutsuja.
- Reitit ja käsittelijät eivät koskaan suorita raakaa SQL:ää suoraan.

**Kohdennettu sykli**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Kun lisäät migraation, testaa sekä puhdas tietokanta että päivitys aiemmasta skeemasta. Tietokantatestien
on suljettava kahvat ja kutsuttava `resetDbInstance()`-funktiota siivouksen aikana. Suorita `npm run test:bun:db` vain silloin,
kun parhaansa yrittävän Bun-sovitinpolun toiminta muuttuu; Node säilyy ensisijaisena.

### Koonti / käyttöönotto

**Sopimukset**

- Juuren ja työtilojen manifestit/lukitustiedosto, `scripts/build/`, Next.js:n itsenäinen kokoonpano, `dist/`-hakemiston
  pakettisisältö, Electronin alustakohtaiset metatiedot, CI-työnkulut ja käyttöönoton varmistimet.
- Tuetut Node-versioalueet ja tiedostossa `CLAUDE.md` sallittu Bunin käyttö on säilytettävä ennallaan.
- Koontiartefakteja ei lisätä versionhallintaan; riippuvuus-, lisenssi-, työnkulku- ja pakettikäytännöt ovat voimassa.

**Kohdennettu sykli**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # riippuvuuden tai lukitustiedoston muutokset
npm run check:pack-policy      # julkaistun paketin julkisen pinnan muutokset
npm run lint
```

Käytä komentoa `npm run build` paikallisesti vain silloin, kun muutos vaikuttaa kääntämiseen, itsenäiseen kokoonpanoon, resursseihin
tai ajonaikaiseen paketointiin. Käytä komentoa `npm run build:release` vain julkaisu- tai käyttöönottovalidointiin. CI:n koonti on
lopullinen alustariippumaton signaali; alustakohtaiset Electron-muutokset edellyttävät vastaavaa kohdennettua koontia
tai savutestinäyttöä.

## Paikallinen silmukka verrattuna CI:hin

| Suorita paikallisesti jokaiselle muutokselle                                                                   | CI tarjoaa laaja-alaisen signaalin                                                |
| -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Yllä kuvatut suorat toimintatestit ja kategoriaportit                                                          | Ositettu täysi yksikkötestikokonaisuus ja sarjalliset testit                      |
| `npm run lint`                                                                                                 | Vitest-testikokonaisuudet sekä kattavuus- ja laatukynnykset                       |
| Tyyppitarkistus tai koonti vain, kun muutoksen kohteena oleva sopimus sitä vaatii                              | Tuotantokoonti sekä tietoturva-, dokumentaatio-, riippuvuus- ja PR-käytäntöportit |
| Manuaalinen vuorovaikutus tai tarkistukset aidossa ympäristössä vain, kun automaatio ei voi todentaa toimintaa | Työnkulun määrittämät töiden väliset integraatio- ja alustatarkistukset           |

Vihreä kohdennettu silmukka on näyttöä muutetusta sopimuksesta, ei todiste siitä, että muut asiaan liittymättömät CI-tarkistukset
läpäistään. Älä myöskään pakota jokaista paikallista muutosta odottamaan koko repositorion testimatriisia.

## Täsmäytyksen tarkistuslista

Ennen katselmoinnin pyytämistä:

- Varmista, että PR:n kohdehaara on edelleen aktiivisista `release/v*`-haaroista uusin.
- Nouda kyseinen kohdehaara ja tarkista haarasi luomisen jälkeen siihen lisätyt commitit.
- Tarkista komennolla `git diff <active-base>...HEAD`, ettei mukana ole tahattomia tai generoituja muutoksia.
- Ratkaise luetteloiden ja generoitujen dokumenttien ristiriidat päivittämällä lähde ja generoimalla tuloste uudelleen.
- Suorita täsmäytyksen jälkeen uudelleen kaikki PR-kuvauksessa mainitut kohdennetut testit ja portit.
- Älä koskaan heikennä tarkistuksia tai poista vaadittuja testejä vain mukautuaksesi muuttuneeseen kohdehaaraan.

Julkaisujäädytystä ja uudelleenkohdistamista koskevat säännöt ovat dokumentissa
[Haarautumis- ja julkaisumalli](BRANCHING_MODEL.md). Täydellinen CI-luettelo on dokumentissa
[Laatuporttien viite](../architecture/QUALITY_GATES.md).
