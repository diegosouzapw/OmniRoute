## npm Trusted Publishing (oletuksena versiosta v3.8.51 alkaen) — pyynnöstä vaiheistettu, varavaihtoehtona suora julkaisu

`npm-publish.yml` julkaisee oletusarvoisesti **npm Trusted Publishing (OIDC)** -toiminnon kautta:
`stage-npm`-työ (GitHubin ylläpitämässä ympäristössä) vaihtaa GitHubin id-tokenin kyseisen
ajon lyhytikäiseen npm-tunnistetietoon — repositorion salaisuuksissa ei ole pitkäikäistä
npm-tokenia, 2FA-kehotetta ei näytetä ja alkuperätiedot liitetään mukaan.
Tämä on npm:n nyt hyväksymä ohitusmenetelmä, kun 2FA:n ohittavat tokenit poistuvat käytöstä;
se palauttaa projektin versioon v3.8.48 asti käyttämän täysin automaattisen prosessin säilyttäen
samalla WS1.3-takuun (vuotanut token ei voi julkaista yksin — tokenia ei ole).

**Kertaluonteinen määritys (omistaja):** npmjs.com → paketti `omniroute` → Settings → _Trusted
Publisher_ → GitHub: omistaja `diegosouzapw`, repositorio `OmniRoute`, työnkulku `npm-publish.yml`
(ympäristö: ei mitään). Kunnes tämä on määritetty, automaattinen vaihe epäonnistuu virheeseen `ENEEDAUTH`:
käynnistä ajo uudelleen arvolla `publish_mode=staged` (alla) tai `direct`.

### Vaiheistettu julkaiseminen (pyynnöstä — `publish_mode=staged`)

npm-publish-työnkulku ei enää julkaise suoraan: se käynnistää pakatun tarball-paketin
(`check:pack-boot`) ja suorittaa sitten komennon `npm stage publish` — täsmälleen samat tavut
pysäköidään rekisteriin, eivätkä ne ole **asennettavissa**, ennen kuin omistaja hyväksyy ne.
Ihmisen suorittama 2FA-portti siirrettiin todentamisen JÄLKEEN, ei sitä edeltäväksi.

**Omistajan prosessi työnkulun muuttumisen jälkeen vihreäksi:**

1. `npm stage list omniroute` — etsi vaiheen tunnus (se tulostetaan myös työnkulun yhteenvetoon).
2. Tarkista vaiheistetut tavut (suositeltavaa): `npm stage download <id>`, asenna sitten
   ladattu tarball-paketti väliaikaiseen etuliitteeseen ja käynnistä se (`npm run check:pack-boot` automatisoi
   saman pakkaus→asennus→käynnistys-tarkistuksen CI:ssä).
3. `npm stage approve <id>` — 2FA-kehote ON julkaisu. `npm stage reject <id>` hylkää sen.
4. Julkaisun jälkeinen turvaverkko: julkaisun jälkeinen tarkistin (v3.8.49-suunnitelman WS1.4) asentaa
   julkaistun version julkisesta rekisteristä puhtaaseen konttiin ja käynnistää sen.

**Varavaihtoehto hätätilanteessa:** `workflow_dispatch` arvolla `publish_mode=direct` palauttaa
vanhan välittömän `npm publish` -toiminnon (käytä vain, jos itse vaiheistus ei toimi oikein; kirjaa syy).

**Kertaluonteinen suojaus (omistaja, npmjs.com):** määritä Trusted Publisher paketille
`omniroute` vain vaiheistuksen sallivaan tilaan, jotta vuotanut pitkäikäinen token ei voi suorittaa
komentoa `npm publish` suoraan mistään — CI voi vain vaiheistaa; julkaisu edellyttää omistajan 2FA:ta.

**Rikkinäisen artefaktin toimintaohje (ennallaan):** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"`
on oletusarvoinen ensireaktio (kestää minuutteja ja on peruttavissa); käytä komentoa `npm unpublish` vain
72 tunnin / ei riippuvaisia -aikaikkunan sisällä, äläkä koskaan ensimmäisenä toimenpiteenä. Dockerissa
versiotunnistetta ei saa koskaan kirjoittaa uudelleen — palautus tehdään kohdistamalla `latest` uudelleen
viimeiseen toimivaan tiivisteeseen.

**Docker Hubin `latest` (pakollinen jokaisessa vakaan SemVer-version julkaisussa):**
`docker-publish`-työnkulun on lisättävä tunnisteeksi **sekä** `X.Y.Z` että, kun
`should-promote-latest.sh` toteaa sen olevan korkein vakaa SemVer-versio, `:latest`
**samalla tiivisteellä**. Työn jälkeen Hubin `latest`-tiivisteen on vastattava uutta
SemVer-tiivistettä ja `last_updated`-arvon on päivityttävä. Älä jätä `:latest`-tunnistetta
vanhempaan koontiversioon, jos julkaisutiedoissa kerrotaan korjauksista, jotka ovat olemassa
vain gitissä. Composen pika-aloitukset käyttävät `:latest`-tunnistetta; GitOpsissa on edelleen
kiinnitettävä versioon `X.Y.Z`. Katso [Dockerin julkaisukanavat](../guides/DOCKER_GUIDE.md#release-channels) ja #10317.

## Hotfix-pikakaista (tunniste `hotfix`)

Tunnisteella `hotfix` merkitty PR ohittaa raskaan CI-matriisin (9 osaan jaettu E2E, kattavuusraja,
quality-gate, quality-extended) ja säilyttää nopeat, olennaiset tarkistukset: koonti,
yksikkötestien osiot, integraatiotestit, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
sekä tar-paketin käynnistyksen smoke-testin (`check:pack-boot`). Tavoite: vihreä tulos ≤15 minuutissa noin 33 minuutin sijaan.

**Käyttöehdot — kaikkien neljän on täytyttävä (Chromiumin, VS Coden ja Noden hätäkaistojen mallin mukaisesti):**

1. **Vakavuus**: tuotanto on rikki — julkaistu artefakti kaatuu käynnistyksessä /
   kyseessä on tietoturvakorjaus / ongelma vaikuttaa julkaisun jokaiseen käyttäjään. ”Tärkeä” ei tarkoita ”rikki”.
2. **Valtuutus**: vain repositorion omistaja lisää `hotfix`-tunnisteen. Tunniste ON
   hyväksyntä — sitä ei koskaan lisätä itse kampanja-PR:ään.
3. **Todisteet**: PR:n kuvaus linkittää edelliseen täysin vihreään raskaaseen ajoon (testikokonaisuuteen,
   jonka ohitetut työt validoisivat uudelleen) sekä korjauksen omaan testiin, joka ensin epäonnistuu ja sitten läpäisee.
4. **Laajuus**: vain cherry-pick — mahdollisimman pieni korjaus, ei refaktorointeja eikä sivumuutoksia.

Ohitettu kattavuus-/ratchet-pinta validoidaan uudelleen seuraavassa täydellisessä ajossa
julkaisuhaarassa (jatkuvasti vihreä julkaisu) — kaista ohittaa vain ODOTUKSEN, ei koskaan validointia.
Pelkästään testejä koskevat muutokset (kaikki tiedostot hakemistossa `tests/`, ei yhtään hakemistossa `tests/e2e/`) ohittavat E2E-matriisin
automaattisesti ilman tunnistetta.

### Hookit (Huskyn validoimat)

Husky-hookit sijaitsevat hakemistossa `.husky/` ja suoritetaan automaattisesti git-toimintojen yhteydessä.

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** nopeat deterministiset tarkistukset — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (otettu käyttöön 2026-06-13). Jättää tarkoituksella komennon `test:unit` pois (hidas; CI:n `test-unit`-työ kattaa sen).
  - Suorita `npm run test:unit` manuaalisesti ennen julkaisuhaarojen push-toimintoa.

Jos hook epäonnistuu: korjaa taustalla oleva ongelma, älä ohita sitä valitsimella `--no-verify`.

### Conventional Commits

Kaikkien julkaisuun sisällytettävien commitien on noudatettava muotoa `type(scope): subject`.

**Sallitut tyypit:** `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `style`, `ci`

**Sallitut kohdealueet:** `db`, `sse`, `oauth`, `dashboard`, `api`, `cli`, `docker`, `ci`, `mcp`, `a2a`, `memory`, `skills`, `cloud-agent`, `guardrails`, `compression`, `auto-combo`, `resilience`, `providers`, `executors`, `translator`, `domain`, `authz`

| `dist/`   | Toimitettava npm-paketti — `assembleStandalone` kokoaa sen      | Ei (gitignored) |

> **Ylläpitäjän huomautus:** VPS-etäkuvan hakemisto on edelleen `/usr/lib/node_modules/omniroute/app/`.
> Vain tietovaraston **sisäinen** koontituloste siirtyi (`app/` → `dist/`). Käyttöönottotaidot synkronoivat rsyncillä
> hakemiston `dist/` sisällön etäpalvelimen `app/`-hakemistoon — VPS-polkuja ei tarvitse muuttaa.

**Yhden koonnin työnkulku:**

```
npm run build:release
  └─ rm -rf .build dist          (puhdistus)
  └─ next build → .build/next/   (välitiedostot)
  └─ assembleStandalone          (kopioi standalone-tiedostot + staattiset tiedostot + julkiset tiedostot + natiivikomponentit → dist/)
  └─ kirjoittaa dist/BUILD_SHA   (HEAD-tarkiste)
```

ÄLÄ suorita käyttöönottoa varten ensin komentoa `npm run build` ja sitten erikseen komentoa `npm run build:cli` — käytä
komentoa `npm run build:release`, joka tekee puhtaan uudelleenkoonnin ja luo tarkisteen yhdellä komennolla.

## Palautus aiempaan versioon

Jos julkaisussa on kriittinen ongelma:

1. `gh release edit vX.Y.Z --prerelease` (merkitsee julkaisun muuksi kuin uusimmaksi)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (vain jos käyttäjät eivät ole vielä ottaneet sitä käyttöön)
3. Tai: pikakorjaus haarassa `release/vX.Y.0` → korjausjulkaisu `vX.Y.(Z+1)`
4. Tiedota asiasta välittömästi GitHub Discussionsissa ja Discordissa

## Ehdottomat säännöt

- Älä koskaan tee committia suoraan `main`-haaraan
- Älä koskaan käytä komentoa `git push --force` `main`- tai `release/*`-haaroihin
- Älä koskaan ohita Husky-koukkuja (`--no-verify`)
- Älä koskaan sisällytä committiin salaisuuksia, tunnistetietoja tai `.env`-tiedostoja
- Testikattavuuden on pysyttävä tasolla ≥60/60/60/60 (lauseet/rivit/funktiot/haarat)
- Sisällytä tai päivitä aina testit, kun muutat tuotantokoodia hakemistoissa `src/`, `open-sse/`, `electron/` tai `bin/`
