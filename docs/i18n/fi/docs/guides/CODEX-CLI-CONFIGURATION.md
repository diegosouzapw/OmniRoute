Täydellinen opas Codex CLI:n käyttämiseen siten, että se osoittaa OmniRouteen OpenAI-yhteensopivana taustajärjestelmänä.

---

> **TOML on ainoa toimiva muoto.** Moderni Codex lukee yksinomaan tiedostoa
> `~/.codex/config.toml` (vahvistettu codex-cli 0.147.0:lla: `codex --help`
> dokumentoi, että `-c/--config`-ohitukset ”ladataan tiedostosta
> `~/.codex/config.toml`”). Vanha `~/.codex/config.yaml` kuului aiempaan npm
> CLI:hin, ja se ohitetaan ilman ilmoitusta. Hallintapaneelin generaattori
> (`/api/cli-tools/apply`, työkalu `codex`) kirjoittaa TOML-muotoa käyttäen
> varovaista yhdistämistä — olemassa olevat avaimet ja muut palveluntarjoajalohkot
> säilytetään, API-avain pysyy muuttujassa `OMNIROUTE_API_KEY` (ei koskaan
> tiedostossa), ja jäljelle jääneestä vanhasta `config.yaml`-tiedostosta
> ilmoitetaan siirtohuomautuksella koskematta tiedostoon.

## Valmis config.toml kopioitavaksi

Korvaa `<YOUR_HOST>` ja `<YOUR_KEY>` omilla arvoillasi:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # historiatallennuksen raja työkalukutsua kohden

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc tai ~/.zshrc — avaimen varsinainen arvo, ei koskaan tiedostossa config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT-sovellukseen sisällytetty Codex

Jos asensit Codexin ChatGPT-työpöytäsovelluksen kautta, `codex`-binääritiedosto
saattaa sijaita vain sovelluspaketin sisällä eikä vielä komentotulkkisi
`PATH`-muuttujassa. Lisää resurssihakemisto komentotulkin käynnistystiedostoon:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Avaa uusi komentotulkki ja varmista sitten toimivuus:

```bash
command -v codex
codex --version
```

### Paikallinen OmniRoute ilman todennusta: paikkamerkkiavain riittää

Codex tarkistaa, että `env_key`-arvolla nimetty ympäristömuuttuja on olemassa
**ennen kuin** ensimmäinen pyyntö lähtee CLI:stä. Jos **paikallinen**
OmniRoute-instanssisi ei vaadi todennusta, mikä tahansa ei-tyhjä paikkamerkki
toimii:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Käytä sen sijaan oikeaa avainta, kun OmniRoute-palvelimesi on suojattu tai
etäpalvelin.

> **Yleiset palvelinvaihtoehdot**
>
> | Yhteystapa       | URL                           |
> | ---------------- | ----------------------------- |
> | Paikallisverkko  | `http://192.168.0.1:20128/v1` |
> | Tailscale        | `http://100.x.x.x:20128/v1`   |
> | Takaisinkytkentä | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — miksi se toimii kaikilla malleilla

Codex CLI poisti `wire_api = "chat"`-asetuksen (Chat Completions) käytöstä helmikuussa 2026 ja **vaatii** nyt asetuksen `wire_api = "responses"` (OpenAI Responses API). Asetus `wire_api = "chat"` aiheuttaa välittömän kaatumisen käynnistyksen yhteydessä versiosta v0.138 alkaen.

Monet palveluntarjoajat, kuten GLM ja Kimi, tarjoavat edelleen vain Chat Completions -päätepisteen. DeepSeek V4 tarjoaa nyt natiivin Responses API:n sekä Anthropic-yhteensopivan päätepisteen; OmniRoute käyttää oletusarvoisesti Responses-rajapintaa ja sallii jokaisen DeepSeek-yhteyden valita Anthropic-yhteensopivuuden.

**OmniRoute ratkaisee tämän läpinäkyvästi:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute valitsee palveluntarjoajan natiivin protokollan ja muuntaa tarvittaessa
    → POST /responses (DeepSeek V4) tai /chat/completions (Mistral / GLM / Kimi / muut)
```

Et koskaan tarvitse erillistä muunnosvälityspalvelinta käyttäessäsi OmniRoutea. **Kaikki mallit käyttävät asetusta `wire_api = "responses"`** — OmniRoute hoitaa loput.

> **`wire_api` on oletusarvo** — kentän oletusarvo on `"responses"`, joten sen voi jättää kokonaan pois tiedostosta `config.toml`. Aseta se erikseen vain, jos haluat dokumentoida tarkoituksen.

## Konteksti-ikkuna ja tiivistäminen

### Tokenien määrityskentät

| Kenttä                           | Kuvaus                                                                                                                                                                                                                           |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Aktiivisen mallin tokenien kokonaisbudjetti. Aseta mallille ilmoitettuun enimmäismäärään.                                                                                                                                        |
| `model_auto_compact_token_limit` | Kynnysarvo, joka käynnistää historian automaattisen tiivistämisen. **Enintään 90 % arvosta `model_context_window`** — yli 90 %:n arvot ohitetaan ilman ilmoitusta.                                                               |
| `tool_output_token_limit`        | Historiaan tallennettavien tokenien enimmäismäärä työkalukutsun tulostetta kohden. Estää yksittäistä suurta työkaluvastausta täyttämästä ikkunaa. **Tämä ei ole tulosteen enimmäismäärä** — kyseessä on historian tallennusraja. |
| `compact_prompt`                 | Tiivistämisen aikana käytettävän järjestelmäkehotteen sisäinen ohitus (v0.138+).                                                                                                                                                 |

> **Huomautus kentästä `model_max_output_tokens`**: Tämä kenttä **ei kuulu Codex CLI:n määritysskeemaan** (se puuttuu Codexin Rust-koodikannasta). Jos se asetetaan, se ohitetaan ilman ilmoitusta. Älä luota siihen — käytä kenttää `tool_output_token_limit` hallitaksesi, kuinka paljon työkalun tulostetta tallennetaan historiaan.

## Päättelyn vaativuustaso

Määrittää, kuinka paljon malli "ajattelee" ennen vastaamista.

| Arvo     | Käyttötarkoitus                                     |
| -------- | --------------------------------------------------- |
| `none`   | Ei päättelyä — suora vastaus                        |
| `low`    | Yksinkertaiset tehtävät (nimeäminen, muotoilu)      |
| `medium` | **Palvelimen oletus**, jos arvoa ei määritetä       |
| `high`   | Keskitason tehtävät (refaktorointi, virheenkorjaus) |
| `xhigh`  | Arkkitehtuuri, syväanalyysi, monimutkaiset ongelmat |

```bash
# Ohita asetus yksittäisessä suorituksessa
codex -c model_reasoning_effort=low "nimeä muuttuja x uudelleen nimelle count"
codex -c model_reasoning_effort=xhigh "suunnittele todennusmoduuli"
```

Määritä myös päättelyn **yhteenveto**, jotta Desktop voi näyttää ajattelutekstin (eikä ainoastaan salattuja tietolohkoja):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # tai ultra, kun sitä tuetaan
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRouten ajattelubudjetti (palvelinasetus)

OmniRoute-isännällä kohdan **Settings → AI → Thinking Budget** arvoksi on asetettava **`passthrough`**, jotta Codexin vaativuustaso ja yhteenveto välittyvät ylävirran palveluun. Tila **`auto` poistaa** kaikki asiakkaan `reasoning`- ja `reasoning_effort`-kentät ja jättää ajattelupaneelit tyhjiksi, vaikka Codex olisi määritetty oikein.

Täydellinen opas: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Pakkaus ja kehotteiden välimuisti ovat toisistaan riippumattomia ja toimivat edelleen `passthrough`-tilassa.

## Profiilit — nimetyt määritykset malleittain ja työnkuluittain

Profiilien avulla voit vaihtaa mallin ja konteksti-ikkunan yhdellä valitsimella. Kukin profiili on yksitasoinen
`~/.codex/<name>.config.toml`-tiedosto, jonka asetukset korvaavat perusmuotoisen `config.toml`-tiedoston vastaavat asetukset.

> **Nimeämissääntö (Codex CLI v0.137+):** tiedoston on oltava `~/.codex/<name>.config.toml` — **ei `profile-`-etuliitettä**.
> CLI tulkitsee valinnan `-p kimi-k27` → `~/.codex/kimi-k27.config.toml`. Jos tiedostoa ei löydy, oletusasetuksia käytetään ilman ilmoitusta.

```bash
codex --profile kimi-k27 "analysoi tämän koodikannan 10 000 riviä"
codex -p glm52 "arkkitehtuurin katselmointi"
codex --profile deepseek-flash "nimeä muuttuja uudelleen"   # nopea ja edullinen
```

### Vaativuustasoprofiilit (sama malli, eri vaativuustaso)

```bash
codex -p low      # cx/gpt-5.5, vaativuustaso=low
codex -p medium   # cx/gpt-5.5, vaativuustaso=medium
codex -p high     # cx/gpt-5.5, vaativuustaso=high
codex -p xhigh    # cx/gpt-5.5, vaativuustaso=xhigh (oletus)
codex -p chat     # cx/gpt-5.5, vaativuustasoa ei asetettu (palvelimen oletus)
```

## Profiilien automaattinen luominen komennolla `omniroute setup-codex`

Jos käytät OmniRoutea VPS-palvelimella, voit luoda profiilitiedostot automaattisesti reaaliaikaisesta malliluettelosta:

```bash
# VPS-palvelimelta (käyttää paikallista OmniRoutea portissa 20128)
omniroute setup-codex

# Miltä tahansa koneelta — osoita komento VPS-palvelimeesi
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Esikatsele kirjoittamatta tiedostoja
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Luo vain GLM- ja Kimi-profiilit
omniroute setup-codex --only glm,kimi

# Kirjoita mukautettuun hakemistoon
omniroute setup-codex --codex-home /path/to/.codex
```

Komento noutaa `/v1/models`-luettelon, käyttää tunnetuille malleille optimoituja profiileja, käyttää muiden yhteensopivien tekstimallien osalta varavaihtoehtona luettelon metatietoja ja kirjoittaa kullekin tiedoston `~/.codex/<name>.config.toml`. Komento on idempotentti, joten sen suorittaminen uudelleen on turvallista.

OmniRoute voi myös **synkronoida automaattisesti** samat profiilitiedostot sen jälkeen, kun onnistunut palveluntarjoajan mallien haku tai tuonti muuttaa reaaliaikaista luetteloa. Tämä on **valinnainen toiminto ja oletusarvoisesti poissa käytöstä**: ota se käyttöön **CLI Code -hallintapaneelista** ("CLI-profiilien automaattinen synkronointi" → Codex) tai aseta `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (se huomioi myös asetuksen `CLI_ALLOW_CONFIG_WRITES`, joka on oletusarvoisesti käytössä). Kun toiminto on käytössä, se kirjoittaa vain erillisiä `~/.codex/*.config.toml`-profiilitiedostoja. Se ei koskaan muuta aktiivista/oletusarvoista `~/.codex/config.toml`-tiedostoa, Codex-lb-asetuksia, todennusta tai palveluntarjoajan valintaa.

## Pitkäkestoiset tehtävät

Kaksi OmniRouten oletusasetusta voi huomaamatta sabotoida useita tunteja kestäviä Codex CLI -istuntoja. Kumpikaan ei ole Codex CLI -asetus — molemmat sijaitsevat OmniRoute-puolella. Käyttäjät, jotka siirtävät määrityksen aiemmista välityspalvelimista, joissa tilit kiinnitetään ja joutokäynnin aikakatkaisut poistetaan käytöstä, törmäävät usein molempiin ja päättelevät, ettei OmniRoute ”pysty ylläpitämään pitkää istuntoa”.

| Oire                                                                                   | Todennäköinen syy                                                                 | Säädin                   |
| -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------ |
| Istunto vaihtaa jatkuvasti tiliä / kehotevälimuistin jatkuvuus katoaa vuorojen välillä | Istunnon affiniteetin TTL on `0` (poistettu käytöstä)                             | `sessionAffinityTtlMs`   |
| Yhteys katkeaa kesken päättelyn ilman asiakkaalle näkyvää kehotetta                    | Virran joutokäynnin valvonta laukesi, kun ylävirrasta ei saatu osaa 10 minuuttiin | `STREAM_IDLE_TIMEOUT_MS` |

Aiheeseen liittyviä keskusteluja: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (pitkän tehtävän katkeamiset), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (miksi affiniteetti on oletusarvoisesti poissa käytöstä). Seuranta: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Istunnon affiniteetti — kiinnitä yksi keskustelu yhteen tiliin

**Oletus:** `sessionAffinityTtlMs = 0` (poistettu käytöstä).

**Missä se asetetaan**

- Hallintapaneeli → **Asetukset → Reititys** → **Istunnon affiniteetti** → **Affiniteetin TTL (sekunteina)** (`ComboDefaultsTab`)
- Tai tee asetuksiin PATCH-pyyntö käyttäen `sessionAffinityTtlMs`-arvoa **millisekunteina** (Zod-alue `0`–`86_400_000`, eli enintään 24 tuntia)

> Nimi vaihdettiin muutoksessa #7274 vain Codexia koskeneesta `codexSessionAffinityTtlMs`-nimestä. Vanha avain hyväksytään edelleen vain luku -aliaksena; uusissa määrityksissä tulee käyttää `sessionAffinityTtlMs`-avainta. Affiniteetti koskee nyt **kaikkia** palveluntarjoajia, kun TTL on suurempi kuin `0`, ei vain Codexia — katso [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Istunnon affiniteetti.

**Mikä rikkoutuu, kun arvoksi jää 0**

Monivuoroisen Codex-keskustelun jokainen vuoro reititetään erikseen aktiivisen yhdistelmästrategian mukaisesti, joten jokainen vuoro voi päätyä **eri tilille**. Tämä rikkoo ylävirran istunnon ja kehotevälimuistin jatkuvuuden. OmniRoute tarkistaa Codex-istunto-otsakkeet (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) ja rungon kentät, kuten `prompt_cache_key` / `session_id`, vain silloin, kun TTL on suurempi kuin `0` (`extractSessionAffinityKey` tiedostossa `src/sse/services/auth.ts`).

**Suositus useita tunteja kestävään yksittäiseen tehtävään**

Aseta TTL **tehtävän odotettua kokonaiskestoa pidemmäksi** (käyttöliittymän enimmäisarvo on **86400 sekuntia** = 24 tuntia):

| Tehtävän odotettu kesto | Affiniteetin TTL (käyttöliittymässä, sekunteina) | `sessionAffinityTtlMs` |
| ----------------------- | ------------------------------------------------ | ---------------------- |
| Muutama tunti           | `14400` (4 h)                                    | `14400000`             |
| Yön yli / ~12 h         | `43200` (12 h)                                   | `43200000`             |
| Koko päivä              | `86400` (24 h, enimmäisarvo)                     | `86400000`             |

Valinnaisuus on tarkoituksellista: affiniteetin poistaminen käytöstä suosii kuormantasausta tilien välillä, kun taas sen käyttöönotto suosii yhden pitkän agentti-istunnon jatkuvuutta. Tämä opas **ei** muuta oletusasetusta — pitkiä Codex-tehtäviä suorittavien ylläpitäjien on otettava asetus erikseen käyttöön.

### 2. Virran joutokäynnin aikakatkaisu — älä katkaise hiljaisia päättelyvuoroja

**Oletus:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 minuuttia). Jos sitä ei ole asetettu, se periytyy `REQUEST_TIMEOUT_MS`-muuttujasta; myös yhteinen perustaso on 600000. Katso [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Aikakatkaisut.

**Mikä rikkoutuu oletusasetuksella**

Codexin päättely-/työkaluvuoro, joka pysyy hiljaisena yli 10 minuuttia ilman **yhtäkään todellista ylävirran datapalaa**, suljetaan pakotetusti SSE:n toimettomuusvalvojan (`open-sse/utils/stream.ts`) toimesta. Asiakas havaitsee usein vain yhteyden katkeamisen ilman lisätietoja — mikä vastaa kuvausta ”pysähtyi automaattisesti ilman ilmoitusta”.

Kriittinen yksityiskohta: OmniRouten synteettinen SSE-**syke ei nollaa** toimettomuusajastinta. Vain todellinen ylävirran rungon datapala päivittää `lastChunkTime`-arvon. Hiljainen malli, joka edelleen ”ajattelee”, näyttää valvojan näkökulmasta samalta kuin jumittunut ylävirta.

Tähän liittyy Undicin rungon toimettomuusraja: `FETCH_BODY_TIMEOUT_MS` (myös sen oletusarvona on sama 10 minuutin perustaso; `0` poistaa sen käytöstä). Suoratoistossa `FETCH_TIMEOUT_MS` kattaa vain yhteyden muodostamisen / ensimmäisten otsakkeiden vastaanottamisen — kun suoratoisto on aktiivinen, jumittumista hallitsevat `STREAM_IDLE_TIMEOUT_MS` ja `FETCH_BODY_TIMEOUT_MS`.

**Suositus useita tunteja kestävään yksittäiseen tehtävään**

OmniRoute-prosessin ympäristössä (`.env` / compose / systemd):

```bash
# Poista suoratoiston toimettomuus- ja rungon toimettomuuskatkaisut käytöstä pitkiä päättelyvuoroja varten
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Tai nosta ne pisintä odottamaasi hiljaista jaksoa suuremmiksi (arvot ovat millisekunteina):

```bash
# Esimerkki: salli enintään 2 tunnin hiljaisuus ylävirran datapalasien välillä
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Käynnistä OmniRoute uudelleen näiden ympäristömuuttujien muuttamisen jälkeen.

### Konkreettinen ohje — useita tunteja kestävä Codex-tehtävä

1. **Kiinnitä tili:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12 h) tai `86400` (enintään 24 h).
2. **Nosta toimettomuusrajoja tai poista ne käytöstä** OmniRouten ympäristössä:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Säilytä tavallinen Codexin `config.toml` (`wire_api = "responses"`, oikea `base_url`, `OMNIROUTE_API_KEY`) — Codex-puolella ei ole affiniteetti- tai toimettomuusasetuksia näitä kahta toimintoa varten.
4. Käynnistä OmniRoute uudelleen ja aloita sitten pitkä Codex-tehtävä.

### Oletusarvoja koskeva päätös (#7287)

| Asetus                   | Toimitettava oletusarvo | Muutetaanko tässä oppaassa?                                                                                                         |
| ------------------------ | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (pois käytöstä)     | **Ei** — säilyy valinnaisena (kuormantasaus vs. jatkuvuus; katso Discussion #5718)                                                  |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 min)       | **Ei** — säilyy 10 minuutissa yleiselle liikenteelle; pitkien Codex-tehtävien ylläpitäjät nostavat rajaa tai poistavat sen käytöstä |

Kumman tahansa oletusarvon muuttaminen maailmanlaajuisesti muuttaisi toimintaa instanssin jokaisen asiakkaan osalta, ei vain Codexin. Dokumentoi asetukset; jätä oletusarvot ennalleen, kunnes nimenomaisella ylläpitäjän päätöksellä määrätään toisin.

### Toimettomuudesta johtuvien katkaisujen diagnosointi

Kun toimettomuusvalvoja aktivoituu, OmniRoute kirjaa seuraavanmuotoisen rivin:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Etsi komennolla grep merkkijonoa `Idle timeout: no data from` (tai koodia `stream_idle_timeout` / virheen nimeä `StreamIdleTimeoutError`). Palveluntarjoajaosa on se, jota OmniRoute käytti kyseisessä pyynnössä (`codex`, jonkin muun palveluntarjoajan tunniste tai `provider`, jos palveluntarjoaja ei ole tiedossa) — se ei aina ole kirjaimellisesti `codex`.

## Vianmääritys

**`Error: wire_api = "chat" is no longer supported`**
Poista `wire_api = "chat"` määrityksistäsi. Aseta `wire_api = "responses"` tai jätä kenttä pois (oletusarvo on ollut `"responses"` versiosta v0.138 lähtien).

**`Error: model not found`**
Varmista, että malli on olemassa OmniRoutessa oikealla etuliitteellä. Käytä komentoa `omniroute models list` tai avaa `/dashboard/providers/<provider>`.

**`Authentication error`**
Varmista, että `OMNIROUTE_API_KEY` on viety ympäristöön: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex tarkistaa ennen ensimmäistä pyyntöä, että ympäristömuuttuja on olemassa. Vie
oikea avain ympäristöön suojattuja palvelimia varten tai käytä tyhjästä poikkeavaa paikkamerkkiä, kuten
`OMNIROUTE_API_KEY=local`, kun **paikallinen** OmniRoute-instanssisi ei
vaadi todennusta. Käynnistä komentotulkki uudelleen, jos lisäsit sen tiedostoon `~/.bashrc` tai `~/.zshrc`.

**`Connection refused`**
Varmista, että OmniRoute on käynnissä ja että `base_url`-arvon isäntä/portti on oikein verkossasi (paikallinen vs. Tailscale vs. VPS).

**Istunto kaatuu lähellä konteksti-ikkunan rajaa**
Aseta `model_context_window` ja `model_auto_compact_token_limit` erikseen. Katso yllä olevaa konteksti-ikkunataulukkoa.

**Tiivistys käynnistyy liian myöhään**
Laske `model_auto_compact_token_limit` arvoon 80–85 % ikkunasta. Älä koskaan aseta sitä yli 90 %:iin.

**Profiili ei lataudu (`-p <name>` ohitetaan ilman ilmoitusta)**
Varmista, että tiedosto on olemassa polussa `~/.codex/<name>.config.toml` (ei `profile-`-etuliitettä). Suorita `ls ~/.codex/*.config.toml`.

**Pitkä Codex-tehtävä katkeaa kesken suorituksen / vaihtaa tiliä vuorojen välillä**
Katso [Pitkäkestoiset tehtävät](#long-running-tasks). Ota käyttöön istunnon sidonnaisuus (TTL pidempi kuin tehtävän kesto) ja suurenna `STREAM_IDLE_TIMEOUT_MS`- ja `FETCH_BODY_TIMEOUT_MS`-arvoja tai poista niiden aikakatkaisut käytöstä. Etsi OmniRoute-lokeista komennolla grep merkkijonoa `Idle timeout: no data from`.
