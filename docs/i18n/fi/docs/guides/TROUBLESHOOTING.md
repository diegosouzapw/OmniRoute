## Pikaopas

**Oletko uusi OmniRouten käyttäjä?** Aloita tästä — nämä ratkaisevat 90 % ongelmista:

| Näen tämän                    | Mitä se tarkoittaa                                        | Mitä tehdä                                                                                                    |
| ----------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| "Can't connect"               | OmniRoute ei ole käynnissä                                | Suorita `omniroute` tai `docker restart omniroute`                                                            |
| "Invalid API key"             | Avaimesi on virheellinen tai vanhentunut                  | Kopioi avain uudelleen palveluntarjoajan verkkosivustolta                                                     |
| "Rate limit exceeded"         | Lähetät liian monta pyyntöä                               | Odota 1 minuutti tai käytä automaattista varajärjestelyä asetuksella `model: "auto"`                          |
| "Quota exceeded"              | Olet käyttänyt ilmaisen tai maksullisen kiintiösi loppuun | Yhdistä lisää palveluntarjoajia tai käytä ilmaisia palveluntarjoajia (Kiro, Pollinations)                     |
| "Slow responses"              | Palveluntarjoaja on ruuhkainen tai kaukana                | Käytä asetusta `model: "auto/fast"` tai yhdistä nopeampi palveluntarjoaja (Groq, Cerebras)                    |
| "Wrong provider used"         | `auto` valitsi toisen palveluntarjoajan                   | Se on normaalia! `auto` valitsee parhaan. Pakota tietty palveluntarjoaja asetuksella `model: "openai/gpt-4o"` |
| "502 Bad Gateway"             | Palveluntarjoaja ei ole käytettävissä                     | Odota ja yritä uudelleen tai vaihda palveluntarjoajaa asetuksella `model: "auto"`                             |
| "401 Unauthorized"            | Tunnistetietosi ovat virheelliset                         | Tarkista API-avaimesi tai tunnistaudu uudelleen OAuthilla                                                     |
| "omniroute is not recognized" | Windows PATH -muuttujasta puuttuvat yleiset node-moduulit | Lisää npm:n yleinen etuliite Windows PATH -muuttujaan. Selvitä se komennolla `npm config get prefix`.         |
| "429 Too Many Requests"       | Pyyntömäärää on rajoitettu                                | Odota 1 minuutti tai yhdistä lisää palveluntarjoajia                                                          |

**Eikö ongelma vieläkään ratkennut?** Katso alta [yksityiskohtainen vianmääritys](#detailed-troubleshooting) tai kysy [Discordissa](https://discord.gg/U47eFqAXCn).

## Yksityiskohtainen vianmääritys

---

### Ilmaisten palveluntarjoajien pyyntömäärän rajoitukset (429 / 400 / 401)

**Oire**: Kun käytät asetusta `model: "auto"` ilmaisten tai tunnistautumista vaatimattomien palveluntarjoajien (opencode, auggie jne.) kanssa, saat ajoittain vastausten sijaan virheen `HTTP 429`, `400` tai `401`. Pyynnöt onnistuvat, kun sama kehote lähetetään uudelleen hetkeä myöhemmin, mutta automaatio (cron-tehtävät, agentit, komentosarjat) keskeytyy ensimmäiseen virheeseen.

**Perimmäinen syy**: Kolme toisistaan riippumatonta virhetilannetta kasaantuu:

1. **Palveluntarjoajan pyyntömäärärajoitus (`429`)**: Ilmaistasot voivat käyttää aikajaksoittaista kiintiötä. Rinnakkaisten kutsujen purske kuluttaa sen loppuun, joten seuraava pyyntö hylätään, kunnes aikajakso nollautuu.
2. **Rikkinäinen malli passthrough-tilassa (`400`/`401`)**: `auto/*`-poolit voivat sisältää `opencode`-palvelun passthrough-malleja, jotka on rekisteröity luetteloon mutta joilla ei ole toimivia tunnistetietoja (esim. `oc/north-mini-code-free` → `401`). Automaattinen reititin kokeilee sellaista, epäonnistuu ja välittää virheen eteenpäin ennen kuin varajärjestely ehtii käynnistyä.
3. **Rinnakkaisuuden voimistava vaikutus (`429` kuormituksessa)**: Kun useat agentti- tai cron-istunnot käyttävät `auto`-asetusta samanaikaisesti, pyyntöjen kokonaismäärä ylittää ilmaisten palveluntarjoajien sietokyvyn, jolloin hyväksyttävätkin kutsut merkitään väärinkäytöksiksi.

**Vahvistettu korjaus (yhteisön raportoima, 2026-08-10)**: säädä kolmea ympäristömuuttujaa niin, että kierrätys, rinnakkaisuus ja varajärjestely vaimentavat ilmaistason epävakauden sen sijaan, että prosessi keskeytyisi siihen:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # siirry toiseen malliin tai palveluntarjoajaan virheessä 400/401 (ohittaa rikkinäiset passthrough-mallit)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # raskaiden pyyntöjen eksplisiittinen enimmäismäärä (oletusarvoisesti määrittämätön: ei pyyntömäärärajaa, katso huomautus alta)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # pidennä rajattu odotusaika hitaiden ylävirran palvelujen RATE_LIMIT_MAX_WAIT_MS-oletusarvoa pidemmäksi
```

Aseta nämä OmniRoute-prosessin ympäristöön (demoniin, esimerkiksi LaunchAgent plist -tiedoston tai `systemctl edit` -komennon kautta) ja käynnistä sitten OmniRoute uudelleen. Kierrätyslippu on yksittäisistä asetuksista vaikutukseltaan merkittävin: se muuntaa vakavan virheen läpinäkyväksi uudelleenyritykseksi poolin toimivalla palveluntarjoajalla.

**Huomautus**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` rajoittaa samanaikaisesti suoritettavien raskaiden eli pitkän kontekstin pyyntöjen määrää. Raja on sisäänpääsyportti, ei palveluntarjoajan pyyntömäärärajoitin. **#503-fanout-päivitys:** tätä muuttujaa ei enää aseteta oletusarvoisesti (se vaikuttaa nyt vain, kun se määritetään eksplisiittisesti yllä esitetyllä tavalla). Raskaiden pyyntöjen sisäänpääsyä hallitsee sen sijaan automaattisesti johdettu tavubudjetti (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), joka skaalautuu isäntäkoneen todellisen muistirajan perusteella. Siksi uudessa käyttöönotossa pitäisi ilmetä huomattavasti vähemmän `503 chat_admission_busy` -hylkäyksiä ilman tämän muuttujan asettamista; sen eksplisiittinen asettaminen tässä toimii edelleen täsmälleen dokumentoidulla tavalla. Tavubudjetin eksplisiittiset ohitukset rajataan välille 8 MiB–2 GiB. `413 body_exceeds_budget` ei ole tilapäinen virhe: kasvata tavubudjettia, pienennä `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`-arvoa tai kasvata prosessin muistirajaa. `inflight_bytes_budget`-kuormanpudotus johtuu tilapäisestä resurssikilpailusta, ja pyyntö voidaan edelleen yrittää uudelleen. Palveluntarjoajakohtaista pyyntömäärän rajoitusta (`open-sse/services/rateLimitManager.ts`) hallitaan erikseen muuttujilla `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` ja `RATE_LIMIT_AUTO_ENABLE` — katso `.env.example`.

**Näin varmistat, että korjaus toimii**: suorita agenttisi/cron-tehtäväsi kahdesti nopeasti peräkkäin ja varmista, että molemmat suoritukset onnistuvat. Ennen korjausta toinen suoritus aiheuttaa yleensä virheen `429`/`401`. Korjauksen jälkeen virheitä (jos niitä ilmenee) yritetään automaattisesti uudelleen, ja kutsu suoritetaan loppuun. Voit myös suorittaa komennon `curl /monitoring/health` ja tarkkailla palveluntarjoajayhteyksien `rateLimitedUntil`-kenttää sekä ongelmallisten palveluntarjoajien `circuitBreakers.providerBreakers[].state`-kenttää — tila on jokin seuraavista: `CLOSED`, `DEGRADED`, `OPEN` tai `HALF_OPEN` (katso `src/shared/utils/circuitBreaker.ts`). Jatkuvasti epäonnistuvan palveluntarjoajan tila vaihtuu `CLOSED → DEGRADED → OPEN`, ennen kuin nollausikkuna päästää testipyynnön läpi (`HALF_OPEN`).

**Jos virhe 429 näkyy edelleen**: kyseisen palveluntarjoajan aktiivinen tili on aidosti käyttänyt _kiintiönsä_ loppuun (kyse ei ole pelkästä pyyntötiheysrajoituksesta). Lisää samalle palveluntarjoajalle toinen tili OmniRoute-hallintapaneelissa kohdassa Providers → Accounts tai ota mukaan toinen maksuton palveluntarjoaja (esim. `routeway` tai `auggie`). Kierrätys auttaa vain tilapäisiin pyyntötiheysrajoituksiin sekä 400- ja 401-virheisiin. Kiintiön loppuminen edellyttää toista tunnistetietoa tai eri palveluntarjoajaa.

**Jos konenäkömalleissa (`auto/vision`, `bazaarlink/*`) näkyy virhe 403**: yhdistettyyn tiliin ei kuulu maksullista sopimusta, joka sisältää konenäköominaisuudet, tai API-avaimella ei ole riittäviä käyttöoikeuksia. Varmista palveluntarjoajan hallintapaneelista, että avaimen käyttöoikeusalue sisältää konenäön/monimodaalisuuden, tai yhdistä maksullisen tason tili ja pidä se konenäön kohteena.

## npm install -varoitukset (ERESOLVE / vertaisriippuvuudet / vanhentuneet paketit)

Kun suoritat komennon `npm install -g omniroute`, saatat nähdä suuren määrän varoituksia, kuten `npm warn ERESOLVE`, vertaisriippuvuuksia koskevia ilmoituksia ja `deprecated`-viestejä. **Nämä ovat odotettuja ja vaarattomia.** Asennus onnistui, jos tulosteessa näkyy `added <N> packages`.

Voit piilottaa vertaisriippuvuuksien ratkaisemista koskevat varoitukset käyttämällä OmniRouten tukemaa asennustapaa:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` piilottaa vain `ERESOLVE`-varoitukset ja vertaisriippuvuuksia koskevat ilmoitukset. Vanhentumisilmoitukset jäävät näkyviin, koska ne ovat peräisin epäsuorista kolmannen osapuolen paketeista. Ne eivät tarkoita, että asennus olisi epäonnistunut.

Varoitukset johtuvat vanhentuneista vertaisriippuvuuksien versioalueista kolmannen osapuolen paketeissa, joita OmniRoute ei hallitse:

1. **`marked-terminal` vaatii version `marked >=1 <16`, mutta löytyi `marked@18`** — toimii käytännössä ongelmitta; upstream-paketin vertaisriippuvuuden versioalue on vain vanhentunut.
2. **`deprecated prebuild-install@7.1.3`** — epäsuora apuohjelma natiivibinäärien hakemiseen. Sitä ei
   käytetä kiinnitetyn `wreq-js`-siirtosidoksen asentamiseen, eikä se tarkoita, että verkkoevästeiden
   tarjoajan siirtoyhteyden määritys olisi epäonnistunut.

**Toimia ei tarvita** — varoituksia ei voi täysin piilottaa ilman upstream-pakettien haarauttamista.

## Estettyjen npm install-scripts -komentosarjojen varoitus (globaali asennus)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

Kun suoritat komennon `npm install -g omniroute`, uudemmat npm-versiot (v11+ ja v12+) estävät oletusarvoisesti pakettien elinkaarikomentosarjat ja näyttävät install-scripts-varoituksen:

```
npm warn install-scripts 7 paketin asennuskomentosarjat estettiin, koska allowScripts ei kata niitä:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Voiko tämän varoituksen jättää huomiotta?

**Osittain, mutta suorittamista ilman komentosarjoja ei suositella.** OmniRoute sisältää hallitut vararatkaisut: jos natiiveja `better-sqlite3`-sidoksia ei voida ladata itsenäisestä sovelluspaketista, sovellus siirtyy käyttämään vaihtoehtoisia ajureita, kuten `node:sqlite` tai `sql.js` (katso [SQLite-ajonaikainen ratkaisu](../ops/SQLITE_RUNTIME.md)). Palvelin käynnistyy silti, mutta WASM-vararatkaisujen, kuten `sql.js`, käyttäminen poistaa SQLite WAL (Write-Ahead Logging) -tilan käytöstä ja lisää muistin käyttöä sekä levysynkronoinnin kuormitusta.

### Mitkä komentosarjat ovat oikeasti pakollisia?

Kaikki estetyt komentosarjat eivät ole välttämättömiä OmniRouten suorittamiseksi:

- **Välttämättömät (`omniroute`, `better-sqlite3`):** OmniRoute suoritetaan itsenäisestä Next.js-sovelluspaketista (`dist/`). Asennuksen aikana npm lataa tai kääntää isäntäkohtaisen natiivin SQLite-ajurin ylätason hakemistoon `node_modules/better-sqlite3/`. OmniRouten `postinstall`-komentosarja (`scripts/build/postinstall.mjs`) tarkistaa ja kopioi sitten nämä isäntäkohtaiset binäärit hakemistoon `dist/node_modules/`, jotta itsenäinen palvelin voi käyttää niitä. Jos `omniroute`-paketin postinstall-komentosarja estetään, tämä kopiointivaihe ohitetaan.
- **Valinnaiset/epäsuorat (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** Nämä ovat kääntämisen apuohjelmia, tiedostomuutosten seurantatyökaluja tai järjestelmän avainnipun apuohjelmia. Niiden salliminen estää käännösvaroitukset, mutta niitä ei tarvita reitityksen ydintoimintoihin.
- **Pois jätettävä (`onnxruntime-node`):** Valinnainen riippuvuus paikallisia tekoälyupotuksia varten, eikä sitä **tarvita** OmniRouten suorittamiseen. Sen postinstall-komentosarja lataa NuGetistä noin 300 Mt CUDA-resursseja. Älä lisää sitä sallittujen luetteloon, ellet nimenomaisesti aio käyttää paikallista ONNX-kiihdytystä tuetulla laitteistolla.

### Suositeltu korjaus

Voit sallia vaaditut asennuskomentosarjat globaalin asennuksen aikana ja piilottaa varoitukset antamalla `--allow-scripts`-valitsimelle OmniRouten ja sen natiivien riippuvuuksien nimet:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

Vaihtoehtoisesti voit määrittää tämän pysyvästi kaikille käyttäjätilisi globaaleille asennuksille:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### Tarkista asennus

Suorita asennuksen jälkeen sisäänrakennettu diagnostiikkatyökalu varmistaaksesi, että natiivisidokset ja ajoympäristö toimivat oikein:

```bash
omniroute doctor
```

## Gemini Web ja Playwright Chromium

Jos Gemini Web -pyyntö palauttaa tilakoodin `503` ja ilmoittaa, ettei Playwright Chromiumia
ole asennettu, npm-paketti on olemassa, mutta selaimen binääritiedosto puuttuu.
Playwright pitää selaimen lataukset tarkoituksella erillään npm-paketin
asennuksesta, joten tämä vastaus on odotettavissa, kunnes selain on asennettu.

Jos npm on asennettu globaalisti, asenna Chromium OmniRoute-paketin
hakemistosta, jotta selainvälimuisti kuuluu samaan Playwright-asennukseen:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Käynnistä OmniRoute uudelleen asennuksen jälkeen ja yritä sitten Gemini Web -pyyntöä uudelleen. Jos
suoritat OmniRoutea Docker-levykuvasta, käytä `-web`-levykuvaa (tai `runner-web`-
koontikohdetta), joka sisältää Chromiumin ja sen riippuvuudet; peruslevykuva ei
sisällä niitä.

## Virustorjunnan väärät positiiviset havainnot

<a name="antivirus-false-positives"></a>

### Avast/AVG asettaa `README.md`-tiedoston karanteeniin tunnisteella `MD:HttpRequest-inf[Susp]`

**Kyseessä on väärä positiivinen havainto. Mikään ei ole saastunut, eikä toimenpiteitä tarvita.**

Avast ja AVG käyttävät heuristiikkaa, joka merkitsee paljon HTTP-pyynnöiltä näyttäviä
linkkejä sisältävät teksti-/Markdown-tiedostot epäilyttäviksi. OmniRouten `README.md`
toimitetaan npm-paketin mukana (se on lueteltu kohdassa `package.json` → `files`), joten
globaalissa asennuksessa se päätyy polkuun `node_modules/omniroute/README.md` — ja sisältää
noin 15 `http://localhost:20128/...`-esimerkkiä (MCP:n HTTP/SSE-päätepisteet, A2A:n
`.well-known`-URL-osoitteen ja `curl`-katkelmia). Tämä linkkitiheys riittää laukaisemaan
heuristiikan.

Jos tämä alkoi vasta äskettäin: tiedoston luonne ei ole muuttunut. README-tiedoston
päätepistetaulukko kasvoi (MCP HTTP + SSE + A2A lisättiin), ja siihen lisättiin enemmän
`curl`-esimerkkejä, minkä vuoksi se ylitti raja-arvon.

Tiedosto on passiivinen dokumentaatio, jossa ei ole lainkaan suoritettavaa sisältöä. Voit
palauttaa sen turvallisesti karanteenista.

**Toimi näin:**

1. **Lopeta ilmoitukset** — lisää asennushakemisto virustorjunnan poikkeuksiin
   (Avast: Settings → Exceptions) lisäämällä globaali `node_modules`-polkusi ja/tai
   OmniRouten datahakemisto (`~/.omniroute/`).
2. **Ilmoita väärästä positiivisesta havainnosta** — <https://www.avast.com/false-positive-file-form.php>,
   ja liitä mukaan karanteeniin asetettu `README.md`. Tämä korjaustapa auttaa kaikkia,
   sillä ongelma johtuu valmistajan heuristiikan ylireagoinnista tekstitiedostoon.

**Miksi emme ”korjaa” tätä omalta puoleltamme:** kaikki esimerkit käyttävät osoitetta
`http://localhost`, eikä localhost voi käyttää `https`-yhteyttä ilman itse allekirjoitettujen
varmenteiden aiheuttamaa vaivaa. Dokumentaation vääristely yhden valmistajan heuristiikan
kiertämiseksi haittaisi kaikkia lukijoita vain skannerivirheen vuoksi.

### Kaspersky merkitsee työpöytäsovelluksen tunnisteella `PDM:Trojan.Win32.Generic`

**Kyseessä on käyttäytymisheuristiikan aiheuttama väärä positiivinen havainto. Mikään ei ole saastunut.**
Kasperskyn `PDM:`-etuliite tarkoittaa, että arvio on peräisin sen Proactive Defense Module
(System Watcher) -moduulista, joka arvioi asennusohjelman _toimintaa_ sen sijaan, että
vertailisi sitä tunnettuihin haittaohjelmiin. Kun tunnistus laukeaa, Kaspersky ”peruuttaa”
koko asennuksen — poistaen jo kirjoittamansa tiedostot — jolloin sovellus jää rikkinäiseksi
tai katoaa kokonaan.

Sen merkitsemät tiedostot ovat työpöytäsovellukseen sisällytettyjen ilmoitettujen avoimen
lähdekoodin riippuvuuksien tavallisia osia, esimerkiksi:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ja
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), selaimen automatisointiin
  tarkoitettu kirjasto, jota käytetään sovelluksen sisäiseen palveluntarjoajiin kirjautumiseen
  ja selainpohjaiseen keskusteluun.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — lukittu natiivi `wreq-js`-sidonta, jota käytetään selaimen sormenjälkeä jäljitteleviin
  HTTP-pyyntöihin verkkoevästeitä käyttävillä palveluntarjoajilla (`<arch>` on `x64` tai
  `arm64`).

**Miksi tunnistus laukeaa:** Windows-asennusohjelmaa **ei ole vielä allekirjoitettu
koodivarmenteella**, joten allekirjoittamattomalla NSIS-asennusohjelmalla ei ole lainkaan
mainetta ja käyttäytymisheuristiikat toimivat mahdollisimman aggressiivisesti. Kun tähän
yhdistetään mukana toimitettava natiivi DLL-tiedosto ja sadat hakemistoon
`%LOCALAPPDATA%\Programs\OmniRoute` kirjoitettavat `.js`-tiedostot (mukaan lukien Next.js:n
itsenäisen koontiversion tiivistepäätteiset pakettihakemistot), heuristiikka laukeaa helposti.
Koodin allekirjoitus on suunnitteilla; siihen asti ongelma voi toistua uusissa julkaisuissa.

**Toimi näin:**

1. **Tarkista ensin lataamasi tiedosto** (tämä sulkee pois peukaloidun tiedoston
   mahdollisuuden). Jokaisessa julkaisussa julkaistaan `latest.yml`, jonka `sha512`-kenttä
   (base64) kattaa `OmniRoute.Setup.<version>.exe`-asennusohjelman. Suorita PowerShellissä
   asennusohjelman sisältävässä kansiossa:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Tulosteen on vastattava arvoa `latest.yml` → `sha512`. Jos se ei vastaa, poista tiedosto
   ja lataa se uudelleen ainoastaan [GitHubin julkaisusivulta](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Palauta + lisää poikkeus** — palauta peruutetut kohteet karanteenista ja lisää
   `%LOCALAPPDATA%\Programs\OmniRoute` poikkeukseksi (Kaspersky → Settings → Threats and Exclusions)
   ja asenna sitten uudelleen.
3. **Ilmoita väärästä positiivisesta havainnosta** — <https://opentip.kaspersky.com/>.
   Käyttäjien lähettämät väärien positiivisten havaintojen ilmoitukset nopeuttavat aidosti
   sallittujen luetteloon lisäämistä.

## Node.js-yhteensopivuus

<a name="nodejs-compatibility"></a>

### Kirjautumissivu kaatuu tai näyttää "Module self-registration" -virheen

**Syy:** Käytössäsi on Node.js-versio, joka ei täytä OmniRouten hyväksyttyä turvallisen suoritusympäristön vähimmäisvaatimusta. Yleisin tapaus on vanhempi Node 22- tai 24-korjausversio, joka alittaa OmniRouten vaatiman korjatun turvallisuustason.

**Oireet:**

- Kirjautumissivu näyttää tyhjän näytön tai palvelinvirheen
- Konsolissa näkyy `Error: Module did not self-register` tai vastaavia natiivisidontavirheitä
- Kirjautumissivulla näkyy **oranssi varoituspalkki**, jossa ilmoitetaan Node-versiosi, jos suoritusympäristö ei täytä tuettua turvallisuuskäytäntöä

**Korjaus:**

1. Asenna tuettu Node.js LTS -julkaisu (suositus: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Tarkista versiosi: komennon `node --version` pitäisi näyttää `v24.0.0` tai uudempi 24.x LTS -sarjan versio
3. Asenna OmniRoute uudelleen: `npm install -g omniroute`
4. Käynnistä uudelleen: `omniroute`

> **Tuetut turvalliset versiot:** `>=22.22.2 <23` tai `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) ja Node.js 26 ovat täysin tuettuja.

### npm v11+: `better-sqlite3` ei ole asennettu (moduulia ei löydy)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Syy:** npm v11 (toimitetaan Node.js 24+:n mukana) estää oletusarvoisesti valinnaisten
riippuvuuksien asennuskomentosarjat. Koska `better-sqlite3` on lueteltu kohdassa `optionalDependencies`
ja vaatii natiivin kääntämisen (`node-gyp rebuild`), npm ohittaa sen ilmoittamatta.

**Oireet:**

- Palvelin kaatuu käynnistyksen yhteydessä virheeseen `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` näyttää ilmoituksen "No such file or directory"
- `npm ls better-sqlite3` näyttää `(empty)`

**Korjaus:**

1. Hyväksy asennuskomentosarjat ja asenna uudelleen:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Tai asenna esikäännetty versio manuaalisesti:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Tarkista, että se toimii: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Syy:** Globaalin `npm install -g omniroute` -asennuksen jälkeen paketin sisällä oleva natiivi `better-sqlite3`-binääritiedosto on saatettu kääntää eri arkkitehtuurille tai Node.js ABI:lle kuin paikallisesti käytössä oleva ympäristö. Tämä on yleistä macOS:ssä (sekä Apple Silicon- että Intel-järjestelmissä), kun esikäännetty binääritiedosto ei vastaa ympäristöäsi.

**Oireet:**

- Palvelin epäonnistuu heti käynnistyksen yhteydessä `dlopen`-virheeseen
- Virhe sisältää tekstin `slice is not valid mach-o file`
- Täydellinen esimerkki:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Korjaus — käännä uudelleen paikallista ympäristöäsi varten (Node.js-version alentamista ei tarvita):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Huomautus:** Tämä kääntää natiivisidonnan uudelleen paikallista Node.js-versiotasi ja suoritinarkkitehtuuriasi varten, mikä ratkaisee binäärien yhteensopimattomuuden. Virallisesti tuettu suoritusympäristön versioalue on **`>=22.22.2 <23` tai `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` tiedostossa `src/shared/utils/nodeRuntimeSupport.ts`, yhdenmukainen `package.json`-tiedoston `engines`-kentän kanssa). Node.js 24.x LTS (Krypton) ja Node.js 26 ovat täysin tuettuja `better-sqlite3` v12.x:n kanssa.

## Välityspalvelinongelmat

<a name="proxy-issues"></a>

### Palveluntarjoajan vahvistus näyttää virheen "fetch failed"

**Syy:** API-avaimen vahvistuspäätepiste (`POST /api/providers/validate`) ohitti aiemmin välityspalvelinasetukset, mikä aiheutti virheitä ympäristöissä, joissa liikenne on reititettävä välityspalvelimen kautta.

**Korjaus (v3.5.5+):** Tämä on nyt korjattu. Palveluntarjoajan vahvistus reititetään `runWithProxyContext`-toiminnon kautta, jolloin palveluntarjoajakohtaisia ja yleisiä välityspalvelinasetuksia noudatetaan automaattisesti.

### Tunnuksen kuntotarkistus epäonnistuu virheellä "fetch failed"

**Syy:** OAuth-tunnusten päivittäminen taustalla ei selvittänyt välityspalvelinasetuksia yhteyskohtaisesti.

**Korjaus (v3.5.5+):** Tunnusten kuntotarkistuksen ajastin selvittää nyt välityspalvelinasetukset yhteyskohtaisesti ennen päivitysyritystä. Päivitä versioon v3.5.5 tai uudempaan.

### SOCKS5-välityspalvelin palauttaa virheen "invalid onRequestStart method"

**Syy:** Node.js 22:ssa undici@8:n dispatcher ei ole yhteensopiva Noden sisäänrakennetun `fetch()`-toteutuksen kanssa.

**Korjaus (v3.5.5+):** OmniRoute käyttää nyt undicin omaa `fetch()`-funktiota, kun välityspalvelimen dispatcher on aktiivinen, mikä varmistaa yhdenmukaisen toiminnan. Päivitä versioon v3.5.5 tai uudempaan.

### MITM-välityspalvelin WSL:ssä: Windows-isäntäjärjestelmän työpöytäsovellusten liikennettä ei siepata

**Syy:** MITM-välityspalvelin ja sen CA-varmenne asennetaan ympäristöön, jossa OmniRoute suoritetaan. WSL:ssä tämä ympäristö on Linux-vierasjärjestelmä, kun taas tekoälytyöpöytäsovellukset (Kiro, Trae, Copilot, Zed, …) suoritetaan Windows-isäntäjärjestelmässä. Isäntäjärjestelmän sovellukset eivät luota vierasjärjestelmän varmennevarastoon eivätkä reititä liikennettä vierasjärjestelmän järjestelmävälityspalvelimen kautta, joten työpöytäsovellusten liikenteen sieppaus ei toimi siellä.

**Suositus:** Suorita OmniRoute natiivisti samassa käyttöjärjestelmässä kuin työpöytäsovellukset, joiden liikenteen haluat siepata (Windows Windows-sovelluksille; vastaavasti macOS/Linux). Jos OmniRoute pidetään WSL:n sisällä ja kohteena ovat isäntäjärjestelmän sovellukset, luotu CA-varmenne on lisättävä manuaalisesti luotetuksi Windows-isäntäjärjestelmässä ja jokaisen isäntäjärjestelmän sovelluksen verkko-/välityspalvelinasetukset on määritettävä käyttämään WSL:n välityspalvelinpäätepistettä — tätä kokoonpanoa ei tueta, ja se on altis häiriöille.

## Palveluntarjoajaongelmat

### "Language model did not provide messages"

**Syy:** Palveluntarjoajan kiintiö on käytetty loppuun.

**Korjaus:**

1. Tarkista kiintiöseuranta hallintapaneelista
2. Käytä yhdistelmää, jossa on varatasoja
3. Vaihda edullisempaan tai maksuttomaan tasoon

### Nopeusrajoitus

**Syy:** Tilauksen kiintiö on käytetty loppuun.

**Korjaus:**

- Lisää varavaihtoehdot: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Käytä GLM:ää/MiniMaxia edullisena varavaihtoehtona

### OAuth-tunnus on vanhentunut

OmniRoute päivittää tunnukset automaattisesti. Jos ongelmat jatkuvat:

1. Hallintapaneeli → Palveluntarjoaja → Yhdistä uudelleen
2. Poista palveluntarjoajayhteys ja lisää se uudelleen

### Useita Kiro-tilejä: toinen tili mitätöi ensimmäisen

**Syy:** Kiron taustajärjestelmä sallii vain yhden aktiivisen istunnon kutakin OIDC-asiakasrekisteröintiä kohden.
Kun kaksi tiliä käyttää samaa rekisteröityä asiakasta (ennen versiota v3.8.0 tuodut yhteydet),
yhden tilin tunnuksen päivittäminen mitätöi toisen tilin päivitystunnuksen.

**Korjaus (v3.8.0+):** Tuo ongelmalliset yhteydet uudelleen.
Versiosta v3.8.0 alkaen jokainen uusi Kiro-yhteys, joka luodaan toiminnolla **Tuo tunnus**,
**Google/GitHub-kirjautumisella** tai **Automaattisella tuonnilla**, rekisteröi automaattisesti oman

## Pilviongelmat

### Pilvisynkronoinnin virheet

1. Varmista, että `BASE_URL` osoittaa käynnissä olevaan instanssiisi (esim. `http://localhost:20128`)
2. Varmista, että `CLOUD_URL` osoittaa pilvipäätepisteeseesi (esim. `https://omniroute.dev`)

### Pilven `stream=false` palauttaa virheen 500

**Oire:** `Unexpected token 'd'...` pilvipäätepisteessä suoratoistoa käyttämättömillä kutsuilla.

**Syy:** Ylävirran palvelu palauttaa SSE-hyötykuorman, vaikka asiakas odottaa JSON-muotoa.

**Kiertotapa:** Käytä `stream=true` pilveen suoraan tehtävissä kutsuissa. Paikallinen suoritusympäristö sisältää SSE→JSON-varamekanismin.

### Pilvi ilmoittaa yhteyden olevan muodostettu, mutta näyttää virheen "Invalid API key"

1. Luo uusi avain paikallisessa hallintapaneelissa (`/api/keys`)
2. Suorita pilvisynkronointi: Ota pilvi käyttöön → Synkronoi nyt
3. Vanhat tai synkronoimattomat avaimet voivat edelleen palauttaa pilvessä virheen `401`

## Docker-ongelmat

### Dockerin IPv6 / yhteyden nollautuminen

<a name="docker-ipv6"></a>

**Oireet:** `curl http://localhost:20128/v1/models` palauttaa virheen `curl: (56) Recv failure: Connection reset by peer`. Hallintapaneeli ja todentamattomat päätepisteet toimivat, mutta todennetut päätepisteet eivät — tämä vaikuttaa todennusongelmalta, mutta ei ole sellainen.

**Syy:** `docker run -p 20128:20128` julkaisee portin sekä osoitteessa `0.0.0.0` (IPv4) että `::` (IPv6), mutta säilön sisällä oleva prosessi kuuntelee vain IPv4-yhteyksiä. Isännissä, joissa `localhost` selvitetään ensin osoitteeksi `::1`, yhteys päätyy julkaistuun IPv6-porttiin, jonka takana ei ole kuuntelijaa → yhteys nollautuu.

**Korjaus:**

1. **Nopea vianmääritys:** Suorita `curl -4 http://localhost:20128/v1/models`. Jos se toimii valitsimella `-4` mutta ei ilman sitä, IPv6-sidonta ei vastaa kuunteluasetusta.
2. **Pysyvä korjaus:** Sido nimenomaisesti IPv4-osoitteeseen käyttämällä `docker run` -komennossa asetusta `-p 127.0.0.1:20128:20128`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Tämä pakottaa IPv4-sidonnan ja estää samalla välityspalvelimen paljastamisen kaikissa isännän verkkoliitännöissä.

## Vikasietoisuusasetukset

### Automaattinen nopeusrajoitus ei aktivoidu

- Automaattinen nopeusrajoitus koskee vain API-avainpalveluntarjoajia (ei OAuth-/tilauspalveluntarjoajia)
- Varmista, että kohdassa **Asetukset → Vikasietoisuus → Palveluntarjoajaprofiilit** automaattinen nopeusrajoitus on käytössä
- Tarkista, palauttaako palveluntarjoaja `429`-tilakoodeja tai `Retry-After`-otsakkeita

### Eksponentiaalisen viiveen säätäminen

Palveluntarjoajaprofiilit tukevat seuraavia asetuksia:

- **Perusviive** — Odotusaika ensimmäisen virheen jälkeen (oletus: 1s)
- **Enimmäisviive** — Odotusajan enimmäisraja (oletus: 30s)
- **Kerroin** — Kuinka paljon viivettä kasvatetaan kutakin peräkkäistä virhettä kohden (oletus: 2x)

### Samanaikaisten uudelleenyritysten estäminen

Kun useat samanaikaiset pyynnöt kohdistuvat nopeusrajoitettuun palveluntarjoajaan, OmniRoute käyttää mutexia ja automaattista nopeusrajoitusta pyyntöjen sarjallistamiseen ja ketjureaktiona syntyvien virheiden estämiseen. Tämä tapahtuu automaattisesti API-avainpalveluntarjoajille.

### Keskustelupyynnöt epäonnistuvat virheellä 503 / chat_admission_busy

**Oireet:**

- Keskustelun täydennyspäätepiste palauttaa uudelleenyrityksen sallivan `503`-vastauksen, jonka virhekoodi on
  `chat_admission_busy`.
- Vastaus sisältää `Retry-After`-otsakkeen. Muutoksesta #12135 alkaen arvo johdetaan havaitusta
  käyttöasteesta — suurempi joko `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`-ikkunasta, jonka ajan pyyntö on jo
  odottanut, tai ajasta, jonka nykyiset raskaat varaukset ovat olleet voimassa — pyöristettynä ylöspäin täysiin
  sekunteihin ja rajattuna enintään 60 sekuntiin. Kun pääsynhallinta on vapaana, käytetään aiempia vähimmäisarvoja: 2 sekuntia
  tavumäärään perustuvalla polulla ja 1 sekunti rakenteeseen perustuvalla polulla (joka sisältää myös arvon
  `reason: "structure_limit"`).
- Näin voi tapahtua, kun toinen raskas keskustelu tai pitkään jatkuva suoratoistovastaus on edelleen
  käsiteltävänä.

Tavumäärään perustuvan vastauksen runko on:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Rakenteeseen perustuva vastaus käyttää samaa tyyppiä ja koodia sekä viestiä
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ja arvoa `reason: "structure_limit"`.
Oletuskynnysarvoilla pyyntö on rakenteellisesti raskas, jos siinä on vähintään `200` viestiä,
vähintään `64` työkalua tai vähintään `32,000` arvioitua tokenia tai jos rajattu rakenteen arviointi
saavuttaa rajansa eli `10,000` vierailtua solmua tai syvyyden `12`.

**Syy:** Kyse on tarkoituksellisesta kuormanpudotuksesta OmniRouten sisällä, ei ylävirran palveluntarjoajan virheestä.
Kukin prosessi käyttää prosessikohtaista suojausta varatakseen rajallista kapasiteettia raskaille pyynnöille ennen suuren
pyyntörungon säilyttämistä ja jäsentämistä. Raskaan pyynnön varaus pysyy voimassa SSE-vastauksen
koko elinkaaren ajan.

**#503-fanout:** ennen tätä korjausta suojaus rajoitti samanaikaisuuden kiinteään pyyntöMÄÄRÄÄN
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, oletus `1`) isännän muistista riippumatta, joten koodausagenttien
hajautus (useita aliagentteja/CLI-työkaluja, pyyntörungot tavallisesti > 256 kt) pudotti käytännön
samanaikaisuuden noin yhteen ja aiheutti 503-virheitä täysin normaalilla kuormalla. Suojaus säätyy nyt
automaattisesti: sitä ohjaa automaattisesti johdettu vastaanoton TAVUBUDJETTI (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), jonka koko perustuu
prosessin todelliseen muistirajaan, ja se hyödyntää myös reaaliaikaista resurssipaineen signaalia — joten se
pudottaa kuormaa vain, kun isäntä kärsii aidosti muistipaineesta, eikä vain siksi, että useampi kuin yksi
raskas pyyntö saapui samanaikaisesti. Vanhaa määrärajaa (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
noudatetaan edelleen, mutta vain jos asetat sen erikseen.

Kun kapasiteetti on varattu, raskas pyyntö odottaa ensin enintään
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (oletuksena `RATE_LIMIT_MAX_WAIT_MS`; `0` poistaa odotuksen käytöstä), että paikka vapautuu,
ennen kuin se vastaa uudelleenyrityksen sallivalla `503`-vastauksella. Rajattu odotus on olemassa, jotta agenttityyliset asiakkaat
(OpenCode, Claude Code, Cursor), jotka hajauttavat raskaita alipyyntöjä samanaikaisesti, sarjallistavat pyynnöt
sen sijaan, että kuluttaisivat koko uudelleenyritysbudjettinsa välittömiin hylkäyksiin ja keskeytyisivät kesken tehtävän.
Raskaiden varausten nykyinen käyttöaste, ratkaistu tavubudjetti ja reaaliaikaisen paineen vakavuus
näytetään kohdassa `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — tarkista nämä ennen minkään ympäristömuuttujan muuttamista.
Asetukset → Vikasietoisuus → Pyyntöjono → Samanaikaiset pyynnöt ei hallitse tätä; kyseinen asetus
ohjaa erillistä palveluntarjoajan pyyntöjonomekanismia.

**Korjaus:**

1. Yritä ensin uudelleen. Asiakkaiden tulee noudattaa `Retry-After`-otsaketta ja käyttää viivettä sen sijaan, että ne
   toistaisivat pyynnön välittömästi.
2. Tarkista `/api/monitoring/health` → `chatAdmission` ennen minkään säätämistä. `countCapEnabled:
false` ja riittävän suuri `maxInflightBytes` tarkoittavat, että automaattisesti johdettu budjetti toimii jo
   oikein; `pressureSeverity`-arvo `high`/`critical` tarkoittaa, että isännän muisti on aidosti vähissä —
   tätä ei voi korjata pääsynhallinnan ympäristömuuttujalla, vaan tarvitaan enemmän RAM-muistia tai pienempi työkuorma.
3. Vain jos `/api/monitoring/health` osoittaa, että automaattisesti johdettu budjetti on aidosti liian pieni
   isännällesi (harvinaista — se skaalautuu jo konteista fyysisiin palvelimiin), ohita se suoraan muuttujalla
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` sen sijaan, että palaisit vanhaan pyyntömäärään perustuvaan rajaan.

Viralliset pääsynhallinta-asetukset löytyvät [ympäristömuuttujien viitteestä](../reference/ENVIRONMENT.md#4-security--authentication).

## Valinnainen RAG-/LLM-virheluokitus (16 ongelmaa)

Jotkut OmniRoute-käyttäjät sijoittavat yhdyskäytävän RAG- tai agenttipinojen eteen. Tällaisissa kokoonpanoissa esiintyy usein outo tilanne: OmniRoute vaikuttaa toimivan oikein (palveluntarjoajat ovat käytettävissä, reititysprofiilit ovat kunnossa eikä nopeusrajoitushälytyksiä ole), mutta lopullinen vastaus on silti väärä.

Käytännössä nämä häiriöt johtuvat yleensä jatkokäsittelyssä olevasta RAG-putkesta, eivät itse yhdyskäytävästä.

Jos haluat yhteisen sanaston näiden virheiden kuvaamiseen, voit käyttää WFGY ProblemMapia. Se on ulkoinen MIT-lisensoitu tekstiresurssi, joka määrittelee kuusitoista toistuvaa RAG-/LLM-virhemallia. Yleisellä tasolla se kattaa seuraavat:

- haun ajautuminen ja rikkoutuneet kontekstirajat
- tyhjät tai vanhentuneet indeksit ja vektoritietokannat
- upotusten ja semantiikan vastaamattomuus
- kehotteen kokoamiseen ja konteksti-ikkunaan liittyvät ongelmat
- logiikan romahtaminen ja yliluottavaiset vastaukset
- pitkien ketjujen ja agenttien koordinoinnin häiriöt
- useiden agenttien muistin ja roolien ajautuminen
- käyttöönoton ja alustuksen järjestysongelmat

Ajatus on yksinkertainen:

1. Kun tutkit virheellistä vastausta, tallenna:
   - käyttäjän tehtävä ja pyyntö
   - OmniRouten reitti tai palveluntarjoajayhdistelmä
   - jatkokäsittelyssä käytetty RAG-konteksti (haetut asiakirjat, työkalukutsut jne.)
2. Yhdistä häiriö yhteen tai kahteen WFGY ProblemMap -numeroon (`No.1` … `No.16`).
3. Tallenna numero omaan hallintapaneeliisi, toimintaohjeeseesi tai häiriöseurantaasi OmniRoute-lokien yhteyteen.
4. Päätä vastaavan WFGY-sivun avulla, onko RAG-pinoa, hakukomponenttia tai reititysstrategiaa muutettava.

Täydellinen teksti ja käytännön ohjeet ovat täällä (MIT-lisenssi, vain tekstiä):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Voit ohittaa tämän osion, jos et käytä RAG- tai agenttiputkia OmniRouten takana.

**Oireet:**

- ModelScope asettaa erittäin lyhyitä tai välittömiä jäähdytyksiä pienen pyyntöpurskeen jälkeen
- Yhdistelmäreititys ohittaa ModelScopen odotettua aiemmin

**Syy:** ModelScope lähettää palveluntarjoajakohtaisia `Retry-After`-otsakkeita. v3.8.0 sisältää näille otsakkeille erillisen käsittelyn, joten vanhemmat versiot tulkitsevat ne virheellisesti yleisiksi nopeusrajoitusvihjeiksi.

**Korjaus:**

- Varmista, että käytössäsi on v3.8.0 tai uudempi
- Varmista, että `useUpstream429BreakerHints`-valitsin on käytössä kohdassa **Asetukset → Vikasietoisuus**

### OMNIROUTE_WS_BRIDGE_SECRET puuttuu tuotannosta

**Oireet:**

- Virhe 401 jokaisessa Codex/Responses-WebSocket-siltapyynnössä etätuotantopalvelimella
- WebSocket-sillan kättely sulkeutuu välittömästi yhteyden muodostamisen jälkeen

**Syy:** Ympäristömuuttuja `OMNIROUTE_WS_BRIDGE_SECRET` puuttuu tuotantoympäristöstä.

**Korjaus:**

1. Luo satunnainen salaisuus: `openssl rand -hex 32`
2. Aseta `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` tuotantopalvelimen ympäristöön (sekä kaikkiin siltaan yhteydessä oleviin asiakasohjelmiin)
3. Käynnistä OmniRoute uudelleen

### Responses API: taustatila heikennetty synkroniseksi

**Oireet:**

- Lokiin kirjataan varoitus: `background mode degraded to synchronous`
- `background: true`-pyyntö palauttaa tavallisen synkronisen vastauksen taustatyön käsittelijän sijaan

**Syy:** v3.8.0 heikentää tarkoituksellisesti Responses API:n `background: true`-pyynnöt synkroniseksi suoritukseksi ja antaa samalla varoituksen. Täysi asynkroninen taustasuoritus toteutetaan tulevaisuudessa.

**Korjaus:**

- Muuta asiakasohjelmaa tekemään kutsu ilman `background`-asetusta, tai
- Odota myöhempää julkaisua, joka sisältää täyden asynkronisen taustatilan (seuraa muutoslokia)

## Hidas käynnistys / valmiustarkistuksen aikakatkaisu

Jos CLI tulostaa ilmoituksen `⚠ Server did not respond within 60s`, mutta palvelin
todellisuudessa toimii, valmiustarkistukselle varattu aika on liian lyhyt ympäristöllesi.

Tätä tapahtuu yleisesti Windowsissa (virustorjunta, tiedostojärjestelmän tarkkailijat) tai säilöissä,
joiden käynnistyskuorma on suuri.

**Korjaus — pidennä varattua aikaa:**

```bash
# Ympäristömuuttujan kautta (säilyy käynnistysten välillä):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuuttia
omniroute serve

# CLI-valitsimen kautta (vain tämän kerran):
omniroute serve --ready-timeout 180000
```

Oletusarvo on 60 000 ms (60 s). Varoitus on vain tiedoksi; palvelimen
käynnistyminen jatkuu taustalla, ja palvelin on tavoitettavissa käynnistyksen valmistuttua.

Katso täydelliset tiedot muuttujasta `OMNIROUTE_READY_TIMEOUT_MS` tiedostosta
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
