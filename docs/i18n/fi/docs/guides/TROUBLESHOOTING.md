## Pikaopas

**Oletko uusi OmniRouten käyttäjä?** Aloita tästä — nämä ratkaisevat 90 % ongelmista:

| Näet tämän                    | Mitä se tarkoittaa                                           | Mitä tehdä                                                                                                                |
| ----------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| "Can't connect"               | OmniRoute ei ole käynnissä                                   | Suorita `omniroute` tai `docker restart omniroute`                                                                        |
| "Invalid API key"             | Avaimesi on virheellinen tai vanhentunut                     | Kopioi avain uudelleen palveluntarjoajan verkkosivustolta                                                                 |
| "Rate limit exceeded"         | Lähetät liian monta pyyntöä                                  | Odota 1 minuutti tai käytä automaattista varajärjestelmää asetuksella `model: "auto"`                                     |
| "Quota exceeded"              | Olet käyttänyt maksuttoman/maksullisen kiintiösi loppuun     | Yhdistä lisää palveluntarjoajia tai käytä maksuttomia palveluntarjoajia (Kiro, Pollinations)                              |
| "Slow responses"              | Palveluntarjoaja on ruuhkautunut tai kaukana                 | Käytä `model: "auto/fast"` tai yhdistä nopeampi palveluntarjoaja (Groq, Cerebras)                                         |
| "Wrong provider used"         | `auto` valitsi toisen palveluntarjoajan                      | Se on normaalia! `auto` valitsee parhaan vaihtoehdon. Pakota tietty palveluntarjoaja asetuksella `model: "openai/gpt-4o"` |
| "502 Bad Gateway"             | Palveluntarjoaja ei ole käytettävissä                        | Odota ja yritä uudelleen tai vaihda palveluntarjoajaa asetuksella `model: "auto"`                                         |
| "401 Unauthorized"            | Tunnistetietosi ovat virheelliset                            | Tarkista API-avaimesi tai tunnistaudu uudelleen OAuthilla                                                                 |
| "omniroute is not recognized" | Windowsin PATH-muuttujasta puuttuvat globaalit node-moduulit | Lisää npm:n globaali etuliite Windowsin PATH-muuttujaan. Selvitä se komennolla `npm config get prefix`.                   |
| "429 Too Many Requests"       | Pyyntötiheyttä on rajoitettu                                 | Odota 1 minuutti tai yhdistä lisää palveluntarjoajia                                                                      |

**Eikö ongelma vieläkään ratkennut?** Katso alta [yksityiskohtainen vianmääritys](#detailed-troubleshooting) tai kysy [Discordissa](https://discord.gg/U47eFqAXCn).

### Maksuttomien palveluntarjoajien pyyntötiheyden rajoitus (429 / 400 / 401)

**Oire**: Kun käytät asetusta `model: "auto"` maksuttomien tai tunnistautumista vaatimattomien palveluntarjoajien (opencode, auggie jne.) kanssa, saat ajoittain vastauksen sijaan virheen `HTTP 429`, `400` tai `401`. Pyynnöt onnistuvat, kun sama kehote lähetetään uudelleen hetkeä myöhemmin, mutta automaatio (cron-työt, agentit, komentosarjat) keskeytyy ensimmäiseen virheeseen.

**Perussyy**: Kolme toisistaan riippumatonta virhetilannetta kasaantuu:

1. **Palveluntarjoajan pyyntötiheyden rajoitus (`429`)**: Maksuttomissa tasoissa voidaan käyttää aikajaksoihin perustuvaa kiintiötä. Rinnakkaisten kutsujen ryöppy kuluttaa sen loppuun, joten seuraava pyyntö hylätään, kunnes aikajakso nollautuu.
2. **Rikkinäinen malli suoravälityksessä (`400`/`401`)**: `auto/*`-poolit voivat sisältää `opencode`-palvelun suoravälitysmalleja, jotka on rekisteröity luetteloon mutta joilla ei ole toimivia tunnistetietoja (esim. `oc/north-mini-code-free` → `401`). Automaattinen reititin kokeilee yhtä niistä, epäonnistuu ja välittää virheen eteenpäin ennen kuin varajärjestelmä ehtii aktivoitua.
3. **Samanaikaisuuden vahvistava vaikutus (`429` kuormituksen aikana)**: Kun useat agentti- tai cron-istunnot käyttävät `auto`-asetusta samanaikaisesti, pyyntöjen kokonaismäärä ylittää maksuttomien palveluntarjoajien sietokyvyn, jolloin kelvolliset kutsut tulkitaan väärinkäytöksiksi.

**Vahvistettu korjaus (yhteisön ilmoittama, 2026-08-10)**: säädä kolmea ympäristömuuttujaa siten, että kierrätys, samanaikaisuuden hallinta ja varajärjestelmä käsittelevät maksuttoman tason vaihtelun sen sijaan, että prosessi keskeytyisi siihen:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # siirry toiseen malliin/palveluntarjoajaan virheen 400/401 yhteydessä (ohittaa rikkinäiset suoravälitysmallit)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # eksplisiittinen raja raskaiden pyyntöjen hyväksymiselle (oletuksena asettamatta: pyyntömäärälle ei ole ylärajaa, katso huomautus alta)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # pidempi rajattu odotus raskaille pyynnöille varatun kapasiteetin vapautumista varten välittömän, uudelleenyrityksen sallivan 503-virheen sijaan
```

Aseta nämä OmniRoute-prosessin ympäristöön (taustaprosessiin, esimerkiksi LaunchAgent plist -tiedoston tai komennon `systemctl edit` kautta) ja käynnistä sitten OmniRoute uudelleen. Kierrätysasetus on yksittäisistä asetuksista vaikutuksiltaan merkittävin: se muuntaa lopullisen virheen läpinäkyväksi uudelleenyritykseksi poolissa olevan toimivan palveluntarjoajan kautta.

**Huomautus**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` rajoittaa samanaikaisesti suoritettavien raskaiden eli pitkän kontekstin pyyntöjen määrää; raja toimii hyväksyntäporttina, ei palveluntarjoajan pyyntötiheyden rajoittimena. **#503-fanout-päivitys:** tätä muuttujaa ei enää aseteta oletuksena (se vaikuttaa nyt vain, kun se on määritetty eksplisiittisesti yllä esitetyllä tavalla) — sen sijaan raskaiden pyyntöjen hyväksyntää rajoittaa automaattisesti johdettu tavubudjetti (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), joka skaalautuu isäntäkoneen todellisen muistirajan mukaan. Siksi uuden käyttöönoton pitäisi tuottaa huomattavasti vähemmän `503 chat_admission_busy` -hylkäyksiä ilman, että tätä muuttujaa asetetaan lainkaan; sen eksplisiittinen asettaminen tässä toimii edelleen täsmälleen dokumentoidulla tavalla. Eksplisiittiset tavubudjetin ohitukset rajataan välille 8 MiB–2 GiB. `413 body_exceeds_budget` ei ole tilapäinen virhe: kasvata tavubudjettia, pienennä arvoa `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` tai kasvata prosessin muistirajaa. `inflight_bytes_budget`-rajoitus johtuu tilapäisestä resurssikilpailusta, ja pyyntö voidaan yrittää uudelleen. Palveluntarjoajakohtaista pyyntötiheyden rajoitusta (`open-sse/services/rateLimitManager.ts`) hallitaan erikseen muuttujilla `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` ja `RATE_LIMIT_AUTO_ENABLE` — katso `.env.example`.

**Näin varmistat, että korjaus toimii**: suorita agentti/cron kahdesti nopeasti peräkkäin ja varmista, että molemmat suoritukset onnistuvat. Ennen korjausta toinen suoritus aiheuttaa yleensä `429`/`401`-virheen. Korjauksen jälkeen virheitä (jos niitä ilmenee) yritetään automaattisesti uudelleen ja kutsu suoritetaan loppuun. Voit myös suorittaa komennon `curl /monitoring/health` ja seurata palveluntarjoajayhteyksien `rateLimitedUntil`-kenttää sekä kyseisten palveluntarjoajien `circuitBreakers.providerBreakers[].state`-kenttää — tila on jokin seuraavista: `CLOSED`, `DEGRADED`, `OPEN` tai `HALF_OPEN` (katso `src/shared/utils/circuitBreaker.ts`). Jatkuvasti epäonnistuvan palveluntarjoajan tila vaihtuu `CLOSED → DEGRADED → OPEN`, kunnes palautusikkuna sallii koekutsun (`HALF_OPEN`).

**Jos näet edelleen 429-virheen**: kyseisen palveluntarjoajan aktiivisen tilin _kiintiö_ on todella käytetty loppuun (kyse ei siis ole vain kutsunopeuden rajoituksesta). Lisää toinen saman palveluntarjoajan tili OmniRoute-hallintapaneelissa kohdassa Providers → Accounts tai ota käyttöön jokin toinen maksuton palveluntarjoaja (esim. `routeway`, `auggie`). Kierrätys auttaa vain tilapäisiin kutsunopeusrajoituksiin sekä 400- ja 401-virheisiin; kiintiön täydellinen loppuminen edellyttää toisia tunnistetietoja tai toista palveluntarjoajaa.

**Jos näet 403-virheen konenäkömalleissa (`auto/vision`, `bazaarlink/*`)**: yhdistettyyn tiliin ei kuulu maksullista sopimusta, joka sisältää konenäön, tai API-avaimen käyttöoikeudet eivät riitä. Varmista palveluntarjoajan hallintapaneelista, että avaimen käyttöoikeusalue sisältää konenäön tai multimodaalisuuden, tai yhdistä maksullisen tason tili ja pidä se konenäön kohteena.

## npm install -varoitukset (ERESOLVE / vertaisriippuvuudet / vanhentuneet paketit)

Kun suoritat komennon `npm install -g omniroute`, saatat nähdä suuren määrän varoituksia, kuten `npm warn ERESOLVE`, vertaisriippuvuuksia koskevia ilmoituksia ja `deprecated`-viestejä. **Nämä ovat odotettuja ja harmittomia.** Asennus onnistui, jos tulosteessa näkyy `added <N> packages`.

Voit estää vertaisriippuvuuksien ratkaisemista koskevat varoitukset käyttämällä OmniRouten tukemaa asennustapaa:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` estää vain `ERESOLVE`-varoitukset ja vertaisriippuvuuksia koskevat ilmoitukset. Vanhentumisilmoitukset jäävät näkyviin, koska ne ovat peräisin transitiivisista kolmannen osapuolen paketeista. Ne eivät tarkoita, että asennus epäonnistui.

Varoitukset johtuvat sellaisten kolmannen osapuolen pakettien vanhentuneista vertaisriippuvuuksien versioalueista, joihin OmniRoute ei voi vaikuttaa:

1. **`marked-terminal` edellyttää versiota `marked >=1 <16`, mutta löytyi `marked@18`** — toimii käytännössä ongelmitta; upstream-projektin vertaisriippuvuuden versioalue on vain vanhentunut.
2. **`deprecated prebuild-install@7.1.3`** — transitiivinen apuohjelma natiivien binaaritiedostojen noutamiseen. Sitä ei
   käytetä kiinnitetyn `wreq-js`-siirtosidoksen asentamiseen, eikä se tarkoita, että verkkoevästeiden
   tarjoajan siirtoasetusten määritys epäonnistui.

**Toimia ei tarvita** — varoituksia ei voi poistaa kokonaan näkyvistä haarauttamatta upstream-paketteja.

## Gemini Web ja Playwright Chromium

Jos Gemini Web -pyyntö palauttaa tilakoodin `503` ja ilmoittaa, ettei Playwright Chromiumia
ole asennettu, npm-paketti on asennettu mutta selaimen binaaritiedosto puuttuu.
Playwright pitää selainlataukset tarkoituksellisesti erillään npm-paketin
asennuksesta, joten tämä vastaus on odotettavissa, kunnes selain on asennettu.

Jos npm on asennettu globaalisti, asenna Chromium OmniRoute-paketin
hakemistosta, jotta selainvälimuisti kuuluu samalle Playwright-asennukselle:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Käynnistä OmniRoute uudelleen asennuksen jälkeen ja yritä sitten Gemini Web -pyyntöä uudelleen. Jos
suoritat OmniRoutea Docker-kuvasta, käytä `-web`-kuvaa (tai `runner-web`-
koontikohdetta), joka sisältää Chromiumin ja sen riippuvuudet; peruskuva ei
sisällä niitä.

## Virustorjunnan väärät positiiviset havainnot

<a name="antivirus-false-positives"></a>

### Avast/AVG asettaa `README.md`-tiedoston karanteeniin tunnisteella `MD:HttpRequest-inf[Susp]`

**Tämä on väärä positiivinen havainto. Mikään ei ole saastunut, eikä toimenpiteitä tarvita.**

Avast ja AVG käyttävät heuristiikkaa, joka merkitsee tavalliset teksti-/Markdown-tiedostot, jos ne sisältävät paljon
HTTP-pyyntöjä muistuttavia linkkejä. OmniRouten `README.md` toimitetaan npm-paketin mukana (se on
lueteltu kohdassa `package.json` → `files`), joten globaalissa asennuksessa se päätyy polkuun `node_modules/omniroute/README.md` — ja se sisältää noin 15 `http://localhost:20128/...`-esimerkkiä (MCP:n
HTTP/SSE-päätepisteet, A2A:n `.well-known`-URL-osoitteen sekä `curl`-katkelmia). Tämä linkkitiheys
riittää laukaisemaan heuristiikan.

Jos tämä alkoi vasta äskettäin: tiedoston luonne ei ole muuttunut. README-tiedoston
päätepistetaulukkoa laajennettiin (MCP HTTP + SSE + A2A lisättiin) ja siihen lisättiin enemmän `curl`-esimerkkejä, mikä nosti
sen kynnysarvon yli.

Tiedosto on passiivinen dokumentaatiotiedosto, jossa ei ole lainkaan suoritettavaa sisältöä. Voit turvallisesti palauttaa sen
karanteenista.

**Toimi näin:**

1. **Lopeta ilmoitukset** — lisää asennushakemisto virustorjuntasi poikkeuksiin
   (Avast: Asetukset → Poikkeukset) lisäämällä globaalin `node_modules`-polkusi ja/tai
   OmniRouten datahakemiston (`~/.omniroute/`).
2. **Ilmoita väärästä positiivisesta havainnosta** — <https://www.avast.com/false-positive-file-form.php>,
   ja liitä mukaan karanteeniin asetettu `README.md`. Tämä korjaustapa auttaa kaikkia, sillä kyse on
   valmistajan heuristiikasta, joka ylireagoi tekstitiedostoon.

**Miksi emme ”korjaa” tätä omalta puoleltamme:** kaikki esimerkit käyttävät osoitetta `http://localhost`, eikä
localhost voi käyttää `https`-protokollaa ilman itse allekirjoitettujen varmenteiden aiheuttamaa hankaluutta. Dokumentaation vääristäminen
yhden valmistajan heuristiikan kiertämiseksi haittaisi jokaista lukijaa vain siksi, että skannerissa on virhe.

### Kaspersky merkitsee työpöytäsovelluksen tunnisteella `PDM:Trojan.Win32.Generic`

**Tämä on käyttäytymiseen perustuvan heuristiikan aiheuttama väärä positiivinen havainto. Mikään ei ole saastunut.** Kasperskyn
`PDM:`-etuliite tarkoittaa, että tulos tulee sen Proactive Defense Module (System Watcher) -moduulista,
joka arvioi, mitä asennusohjelma _tekee_, sen sijaan että vertaisi sitä tunnettuun haittaohjelmaan. Kun
se laukeaa, Kaspersky ”peruu” koko asennuksen — poistaen jo kirjoittamansa tiedostot — jolloin
sovellus jää rikkinäiseksi tai katoaa kokonaan.

Sen merkitsemät tiedostot ovat työpöytäsovellukseen pakattujen ilmoitettujen avoimen lähdekoodin riippuvuuksien
vakiokomponentteja, esimerkiksi:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ja
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), selaimen automatisointiin tarkoitettu
  kirjasto, jota käytetään sovelluksen sisäiseen palveluntarjoajaan kirjautumiseen ja selainpohjaiseen keskusteluun.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — kiinnitetty natiivi `wreq-js`-sidonta, jota käytetään selaimen sormenjälkeä jäljittelevään HTTP-liikenteeseen verkkosivustoevästeitä käyttävillä
  palveluntarjoajilla (`<arch>` on `x64` tai `arm64`).

**Miksi se laukeaa:** Windows-asennusohjelmaa **ei ole vielä allekirjoitettu digitaalisesti**, joten allekirjoittamattomalla NSIS-asennusohjelmalla
ei ole lainkaan mainetta, ja käyttäytymisheuristiikka toimii mahdollisimman aggressiivisesti. Kun tähän yhdistetään
mukana toimitettu natiivi DLL-tiedosto ja sadat hakemistoon
`%LOCALAPPDATA%\Programs\OmniRoute` kirjoitetut `.js`-tiedostot (mukaan lukien Next.js:n itsenäisen koontiversion
tiivistepäätteiset pakettihakemistot), tämä riittää laukaisemaan heuristiikan. Digitaalinen allekirjoittaminen on suunnitteilla;
siihen asti tämä voi toistua uusien versioiden yhteydessä.

**Toimi näin:**

1. **Tarkista ensin latauksesi** (tämä sulkee pois tiedoston peukaloinnin). Jokaisessa julkaisussa julkaistaan
   `latest.yml`, jonka `sha512`-kenttä (base64) kattaa `OmniRoute.Setup.<version>.exe`-asennusohjelman.
   Suorita PowerShellissä seuraava komento asennusohjelman sisältävässä kansiossa:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Tuloksen on vastattava arvoa `latest.yml` → `sha512`. Jos se ei vastaa, poista tiedosto ja
   lataa se uudelleen vain [GitHubin julkaisusivulta](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Palauta + lisää poikkeus** — palauta peruutetut kohteet karanteenista ja lisää poikkeus
   polulle `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Asetukset → Uhat ja poikkeukset),
   ja asenna sitten uudelleen.
3. **Ilmoita väärästä positiivisesta havainnosta** — <https://opentip.kaspersky.com/>. Käyttäjien lähettämät ilmoitukset vääristä positiivisista havainnoista
   todella nopeuttavat sallittujen luetteloon lisäämistä.

## Node.js-yhteensopivuus

<a name="nodejs-compatibility"></a>

### Kirjautumissivu kaatuu tai näyttää "Module self-registration" -virheen

**Syy:** Käytössäsi on Node.js-versio, joka ei täytä OmniRouten hyväksymää turvallisen suoritusympäristön vähimmäisvaatimusta. Yleisin tapaus on vanhempi Node 22- tai 24-korjausversio, joka alittaa OmniRouten edellyttämän korjatun tietoturvatason.

**Oireet:**

- Kirjautumissivu näyttää tyhjän näytön tai palvelinvirheen
- Konsolissa näkyy `Error: Module did not self-register` tai vastaavia natiivisidosten virheitä
- Kirjautumissivulla näkyy **oranssi varoituspalkki**, joka sisältää Node-versiosi, jos suoritusympäristö ei ole tuetun tietoturvakäytännön mukainen

**Korjaus:**

1. Asenna tuettu Node.js LTS -julkaisu (suositus: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Tarkista versiosi: komennon `node --version` tulisi näyttää `v24.0.0` tai uudempi 24.x LTS -sarjan versio
3. Asenna OmniRoute uudelleen: `npm install -g omniroute`
4. Käynnistä uudelleen: `omniroute`

> **Tuetut turvalliset versiot:** `>=22.22.2 <23` tai `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) ja Node.js 26 ovat täysin tuettuja.

### npm v11+: `better-sqlite3` ei ole asennettu (moduulia ei löydy)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Syy:** npm v11 (toimitetaan Node.js 24+:n mukana) estää valinnaisten
riippuvuuksien asennusskriptit oletusarvoisesti. Koska `better-sqlite3` on lueteltu kohdassa `optionalDependencies`
ja edellyttää natiivikäännöstä (`node-gyp rebuild`), npm ohittaa sen ilmoittamatta.

**Oireet:**

- Palvelin kaatuu käynnistyessään ja näyttää virheen `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` näyttää ilmoituksen "No such file or directory"
- `npm ls better-sqlite3` näyttää `(empty)`

**Korjaus:**

1. Hyväksy asennusskriptit ja asenna uudelleen:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Tai asenna esikäännetty versio manuaalisesti:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Varmista, että se toimii: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Syy:** Globaalin `npm install -g omniroute` -asennuksen jälkeen paketin sisällä oleva natiivi `better-sqlite3`-binääritiedosto on saatettu kääntää eri arkkitehtuurille tai Node.js ABI:lle kuin paikallisesti käytössä oleva ympäristö. Tämä on yleistä macOS:ssä (sekä Apple Silicon- että Intel-järjestelmissä), kun esikäännetty binääritiedosto ei vastaa ympäristöäsi.

**Oireet:**

- Palvelin epäonnistuu heti käynnistyessään ja näyttää `dlopen`-virheen
- Virhe sisältää tekstin `slice is not valid mach-o file`
- Täydellinen esimerkki:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Korjaus — käännä uudelleen paikallista ympäristöäsi varten (Node.js-version alentamista ei tarvita):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Huomautus:** Tämä kääntää natiivisidoksen uudelleen paikallista Node.js-versiotasi ja suoritinarkkitehtuuriasi vasten, mikä korjaa binääritiedostojen yhteensopimattomuuden. Virallisesti tuettu suoritusympäristöalue on **`>=22.22.2 <23` tai `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` tiedostossa `src/shared/utils/nodeRuntimeSupport.ts`, yhdenmukainen `package.json`-tiedoston `engines`-kentän kanssa). Node.js 24.x LTS (Krypton) ja Node.js 26 ovat täysin tuettuja `better-sqlite3` v12.x:n kanssa.

## Välityspalvelinongelmat

<a name="proxy-issues"></a>

### Palveluntarjoajan validointi näyttää virheen "fetch failed"

**Syy:** API-avaimen validointipäätepiste (`POST /api/providers/validate`) ohitti aiemmin välityspalvelinasetukset, mikä aiheutti virheitä ympäristöissä, joissa liikenne on reititettävä välityspalvelimen kautta.

**Korjaus (v3.5.5+):** Ongelma on nyt korjattu. Palveluntarjoajan validointi reititetään `runWithProxyContext`-toiminnon kautta, jolloin palveluntarjoajakohtaiset ja yleiset välityspalvelinasetukset huomioidaan automaattisesti.

### Tunnuksen kuntotarkistus epäonnistuu virheellä "fetch failed"

**Syy:** OAuth-tunnuksen päivitys taustalla ei selvittänyt välityspalvelinasetuksia yhteyskohtaisesti.

**Korjaus (v3.5.5+):** Tunnuksen kuntotarkistuksen ajastin selvittää nyt välityspalvelinasetukset yhteyskohtaisesti ennen päivitysyritystä. Päivitä versioon v3.5.5+.

### SOCKS5-välityspalvelin palauttaa virheen "invalid onRequestStart method"

**Syy:** Node.js 22:ssa undici@8-välittäjä ei ole yhteensopiva Noden sisäänrakennetun `fetch()`-toteutuksen kanssa.

**Korjaus (v3.5.5+):** OmniRoute käyttää nyt undicin omaa `fetch()`-funktiota välityspalvelinvälittäjän ollessa aktiivinen, mikä varmistaa yhdenmukaisen toiminnan. Päivitä versioon v3.5.5+.

### MITM-välityspalvelin WSL:ssä: Windows-isäntäjärjestelmän työpöytäsovellusten liikennettä ei siepata

**Syy:** MITM-välityspalvelin ja sen CA-varmenne asennetaan ympäristöön, jossa OmniRoute suoritetaan. WSL:ssä tämä ympäristö on Linux-vierasjärjestelmä, kun taas tekoälytyöpöytäsovellukset (Kiro, Trae, Copilot, Zed, …) suoritetaan Windows-isäntäjärjestelmässä. Isäntäjärjestelmän sovellukset eivät luota vierasjärjestelmän varmennevarastoon eivätkä reititä liikennettä vierasjärjestelmän järjestelmävälityspalvelimen kautta, joten työpöytäsovellusten liikennettä ei siepata.

**Suositus:** Suorita OmniRoute natiivisti samassa käyttöjärjestelmässä kuin työpöytäsovellukset, joiden liikennettä haluat siepata (Windows Windows-sovelluksille ja vastaavasti macOS/Linux). Jos OmniRoute pidetään WSL:n sisällä ja kohteena ovat isäntäjärjestelmän sovellukset, luotu CA-varmenne on lisättävä manuaalisesti luotetuksi Windows-isäntäjärjestelmässä ja jokaisen isäntäsovelluksen verkko-/välityspalvelinasetukset on määritettävä käyttämään WSL:n välityspalvelinpäätepistettä — tätä määritystä ei tueta, ja se on altis häiriöille.

## Pilviongelmat

### Pilvisynkronoinnin virheet

1. Varmista, että `BASE_URL` osoittaa käynnissä olevaan instanssiisi (esim. `http://localhost:20128`)
2. Varmista, että `CLOUD_URL` osoittaa pilvipäätepisteeseesi (esim. `https://omniroute.dev`)
3. Pidä `NEXT_PUBLIC_*`-arvot yhdenmukaisina palvelinpuolen arvojen kanssa

### Pilven `stream=false` palauttaa 500-virheen

**Oire:** `Unexpected token 'd'...` pilvipäätepisteessä suoratoistamattomissa kutsuissa.

**Syy:** Ylävirran palvelu palauttaa SSE-hyötykuorman, vaikka asiakas odottaa JSON-muotoa.

**Kiertotapa:** Käytä `stream=true` pilveen suoraan tehtävissä kutsuissa. Paikallinen suoritusympäristö sisältää SSE→JSON-varamekanismin.

### Pilvi ilmoittaa yhteyden olevan muodostettu, mutta näyttää virheen "Invalid API key"

1. Luo uusi avain paikallisessa hallintapaneelissa (`/api/keys`)
2. Suorita pilvisynkronointi: Ota pilvi käyttöön → Synkronoi nyt
3. Vanhat tai synkronoimattomat avaimet voivat edelleen palauttaa pilvessä virheen `401`

## Docker-ongelmat

### Dockerin IPv6 / yhteyden katkeaminen

<a name="docker-ipv6"></a>

**Oireet:** `curl http://localhost:20128/v1/models` palauttaa virheen `curl: (56) Recv failure: Connection reset by peer`. Hallintapaneeli ja todentamattomat päätepisteet toimivat, mutta todennetut päätepisteet eivät — ongelma näyttää todennusongelmalta, mutta ei ole sitä.

**Syy:** `docker run -p 20128:20128` julkaisee portin sekä osoitteessa `0.0.0.0` (IPv4) että `::` (IPv6), mutta säilön sisällä oleva prosessi kuuntelee vain IPv4-osoitetta. Isännissä, joissa `localhost` selvitetään ensin osoitteeksi `::1`, yhteys päätyy julkaistuun IPv6-porttiin, jonka takana ei ole kuuntelijaa → yhteys katkaistaan.

**Korjaus:**

1. **Nopea diagnostiikka:** Suorita `curl -4 http://localhost:20128/v1/models`. Jos se toimii valitsimella `-4`, mutta epäonnistuu ilman sitä, IPv6-sidonnassa on ristiriita.
2. **Pysyvä korjaus:** Sido nimenomaisesti IPv4-osoitteeseen käyttämällä `docker run` -komennossa määritystä `-p 127.0.0.1:20128:20128`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Tämä pakottaa IPv4-sidonnan ja estää samalla välityspalvelimen julkaisemisen isännän kaikissa verkkoliitännöissä.

```bash
# API:n kuntotarkistus
curl http://localhost:20128/api/monitoring/health
```

### Suoritusympäristön tallennustila

- Päätila: `${DATA_DIR}/storage.sqlite` (palveluntarjoajat, yhdistelmät, aliakset, avaimet, asetukset)
- Käyttö: SQLite-taulut tiedostossa `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + valinnainen `${DATA_DIR}/call_logs/`
- Sovelluslokit: `<repo>/logs/...` (kun `APP_LOG_TO_FILE=true`)
- Kutsulokien artefaktit: `${DATA_DIR}/call_logs/YYYY-MM-DD/...`, kun kutsulokiputki on käytössä

Pyyntölokit-sivun **Tyhjennä historia** -toiminto tyhjentää kohteet `call_logs`, vanhat
`request_detail_logs`-lokit sekä paikallisen `${DATA_DIR}/call_logs/`-artefaktihakemiston.

## Vikasietoisuusasetukset

### Automaattinen nopeusrajoitus ei aktivoidu

- Automaattinen nopeusrajoitus koskee vain API-avainpalveluntarjoajia (ei OAuth-/tilauspohjaisia palveluntarjoajia)
- Varmista, että kohdassa **Asetukset → Vikasietoisuus → Palveluntarjoajaprofiilit** automaattinen nopeusrajoitus on käytössä
- Tarkista, palauttaako palveluntarjoaja `429`-tilakoodeja tai `Retry-After`-otsakkeita

### Eksponentiaalisen viiveen säätäminen

Palveluntarjoajaprofiilit tukevat seuraavia asetuksia:

- **Perusviive** — Ensimmäisen virheen jälkeinen alkuodotusaika (oletus: 1s)
- **Enimmäisviive** — Odotusajan enimmäisraja (oletus: 30s)
- **Kerroin** — Kuinka paljon viivettä kasvatetaan kutakin peräkkäistä virhettä kohden (oletus: 2x)

### Pyyntöryntäyksen esto

Kun useat samanaikaiset pyynnöt kohdistuvat nopeusrajoitettuun palveluntarjoajaan, OmniRoute käyttää mutex-lukitusta ja automaattista nopeusrajoitusta pyyntöjen sarjoittamiseen ja ketjureaktioina syntyvien virheiden estämiseen. Tämä tapahtuu automaattisesti API-avainpalveluntarjoajilla.

### Keskustelupyynnöt epäonnistuvat virheellä 503 / chat_admission_busy

**Oireet:**

- Keskustelutäydennysten päätepiste palauttaa uudelleenyrityksen sallivan `503`-vastauksen, jonka virhekoodi on
  `chat_admission_busy`.
- Vastaus sisältää `Retry-After`-otsakkeen. Muutoksesta #12135 lähtien arvo johdetaan havaitusta
  kuormituksesta — arvoksi valitaan suurempi ajasta, jonka pyyntö on jo odottanut
  `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`-ikkunassa, ja ajasta, jonka nykyiset raskaat varaukset ovat olleet voimassa —
  pyöristettynä ylöspäin kokonaisiin sekunteihin ja rajoitettuna enintään 60 sekuntiin. Kun portti on
  käyttämättömänä, käytetään aiempia vähimmäisarvoja: 2 sekuntia tavumäärään perustuvalla polulla ja
  1 sekunti rakenteeseen perustuvalla polulla (joka sisältää myös arvon
  `reason: "structure_limit"`).
- Näin voi tapahtua, kun toinen raskas keskustelu tai pitkäkestoinen suoratoistovastaus on yhä
  käsiteltävänä.

Tavumäärään perustuvan vastauksen runko on:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Rakenteeseen perustuva vastaus käyttää samaa tyyppiä ja koodia sekä viestiä
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ja arvoa `reason: "structure_limit"`.
Oletuskynnysarvoilla pyyntö on rakenteellisesti raskas, jos siinä on vähintään `200` viestiä,
vähintään `64` työkalua tai vähintään `32,000` arvioitua tokenia tai jos rajattu rakenteen arviointi
saavuttaa rajansa, jotka ovat `10,000` vierailtua solmua tai syvyys `12`.

**Syy:** Tämä on OmniRouten sisäistä tarkoituksellista kuormanpudotusta, ei palveluntarjoajan virhe.
Jokainen prosessi käyttää prosessikohtaista suojausta rajallisen raskaan käsittelykapasiteetin varaamiseen ennen
suuren pyyntörungon säilyttämistä ja jäsentämistä. Raskas varaus pysyy voimassa SSE-vastauksen
koko elinkaaren ajan.

**#503-fanout:** ennen tätä korjausta suojaus rajoitti samanaikaisuuden kiinteään pyyntöMÄÄRÄÄN
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, oletus `1`) palvelimen muistimäärästä riippumatta, joten koodausagenttien
rinnakkaishajautus (useita aliagentteja/CLI-asiakasohjelmia, pyyntörungot säännöllisesti > 256 KB) romahdutti
tehollisen samanaikaisuuden noin yhteen ja aiheutti 503-virheitä täysin normaalillakin kuormalla. Suojaus
mukautuu nyt automaattisesti: sitä ohjaa automaattisesti johdettu vastaanoton TAVUbudjetti
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), joka mitoitetaan prosessin todellisen muistirajan perusteella, ja se
hyödyntää myös reaaliaikaista resurssipainesignaalia — joten se pudottaa kuormaa vain, kun palvelimeen
kohdistuu todellista muistipainetta, eikä vain siksi, että useampi kuin yksi raskas pyyntö saapui
samanaikaisesti. Vanhaa määrärajaa (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) noudatetaan
edelleen, mutta vain, jos asetat sen erikseen.

Kun kapasiteetti on varattu, raskas pyyntö odottaa ensin enintään
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`-ajan (oletus `2000`, arvo `0` poistaa odotuksen käytöstä), että paikka vapautuu,
ennen kuin se palauttaa uudelleenyrityksen sallivan `503`-vastauksen. Rajattu odotus on käytössä, jotta
agenttityyliset asiakasohjelmat (OpenCode, Claude Code, Cursor), jotka hajauttavat raskaita alipyyntöjä
samanaikaisesti, sarjoittavat pyyntöryntäyksen sen sijaan, että käyttäisivät koko uudelleenyritysbudjettinsa
välittömiin hylkäyksiin ja keskeytyisivät kesken tehtävän.
Raskaiden varausten nykyinen käyttöaste, määritetty tavubudjetti ja reaaliaikaisen paineen vakavuus
näytetään kohdassa `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — tarkista nämä ennen minkään ympäristömuuttujan muuttamista.
Asetukset → Vikasietoisuus → Pyyntöjono → Samanaikaiset pyynnöt ei hallitse tätä; kyseinen asetus
hallitsee erillistä palveluntarjoajapyyntöjen jonotusmekanismia.

**Korjaus:**

1. Yritä ensin uudelleen. Asiakasohjelmien tulee noudattaa `Retry-After`-otsaketta ja käyttää viivettä sen sijaan, että
   pyyntö toistettaisiin välittömästi.
2. Tarkista `/api/monitoring/health` → `chatAdmission` ennen minkään säätämistä. `countCapEnabled:
false` ja riittävän suuri `maxInflightBytes` tarkoittavat, että automaattisesti johdettu budjetti toimii jo
   oikein; `pressureSeverity`-arvo `high`/`critical` tarkoittaa, että palvelimen muisti on aidosti vähissä —
   tätä ei voi korjata käsittelyynpääsyn ympäristömuuttujalla, vaan tarvitaan lisää RAM-muistia tai pienempi työkuorma.
3. Vain jos `/api/monitoring/health` osoittaa, että automaattisesti johdettu budjetti on aidosti liian pieni
   palvelimellesi (harvinaista — se skaalautuu jo konteista fyysisiin palvelimiin), ohita se suoraan muuttujalla
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` sen sijaan, että palaisit vanhaan pyyntömäärään perustuvaan rajaan.

Katso viralliset käsittelyynpääsyn asetukset [ympäristömuuttujien viitteestä](../reference/ENVIRONMENT.md#4-security--authentication).

## Valinnainen RAG-/LLM-virheiden luokittelu (16 ongelmaa)

Jotkut OmniRoute-käyttäjät sijoittavat yhdyskäytävän RAG- tai agenttipinojen eteen. Tällaisissa kokoonpanoissa esiintyy usein outo tilanne: OmniRoute näyttää toimivan oikein (palveluntarjoajat ovat käytettävissä, reititysprofiilit ovat kunnossa eikä nopeusrajoitushälytyksiä ole), mutta lopullinen vastaus on silti väärä.

Käytännössä nämä häiriöt johtuvat yleensä myöhemmästä RAG-putkesta eivätkä itse yhdyskäytävästä.

Jos haluat käyttää yhteistä sanastoa näiden virheiden kuvaamiseen, voit käyttää WFGY ProblemMapia. Se on ulkoinen MIT-lisensoitu tekstiresurssi, joka määrittelee kuusitoista toistuvaa RAG-/LLM-virhemallia. Yleisellä tasolla se kattaa seuraavat aiheet:

- haun ajautuminen ja rikkoutuneet kontekstirajat
- tyhjät tai vanhentuneet indeksit ja vektorivarastot
- upotusten ja semantiikan yhteensopimattomuus
- kehotteen kokoamiseen ja konteksti-ikkunaan liittyvät ongelmat
- päättelyn romahtaminen ja liian itsevarmat vastaukset
- pitkien ketjujen ja agenttien koordinoinnin häiriöt
- moniagenttimuistin ja roolien ajautuminen
- käyttöönoton ja alustuksen järjestysongelmat

Ajatus on yksinkertainen:

1. Kun tutkit virheellistä vastausta, tallenna:
   - käyttäjän tehtävä ja pyyntö
   - OmniRoutessa käytetty reitti tai palveluntarjoajayhdistelmä
   - kaikki myöhemmässä käsittelyssä käytetty RAG-konteksti (haetut asiakirjat, työkalukutsut jne.)
2. Yhdistä häiriö yhteen tai kahteen WFGY ProblemMap -numeroon (`No.1` … `No.16`).
3. Tallenna numero omaan hallintapaneeliisi, toimintaohjeeseesi tai häiriöseurantaasi OmniRoute-lokien yhteyteen.
4. Päätä vastaavan WFGY-sivun avulla, pitääkö sinun muuttaa RAG-pinoasi, hakukomponenttiasi tai reititysstrategiaasi.

Koko teksti ja konkreettiset ohjeet löytyvät täältä (MIT-lisenssi, vain tekstiä):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Voit ohittaa tämän osion, jos OmniRouten takana ei käytetä RAG- tai agenttiputkia.

## v3.8.0:n tunnetut ongelmat

v3.8.0-julkaisuun liittyvät ongelmat ja niiden nykyiset kiertotavat. Jos korjaus sisällytetään myöhempään korjausjulkaisuun, merkintä päivitetään tai poistetaan.

### Devin CLI -todennusvirheet

**Oireet:**

- "Devin CLI:tä ei löydy" tai "todennus epäonnistui" kutsuttaessa Deviniin perustuvia työkaluja
- CLI:n suorituksenaikainen tarkistus ilmoittaa `installed=false`

**Syyt:**

- `CLI_DEVIN_BIN` osoittaa polkuun, jota ei ole olemassa
- Devin CLI:tä ei ole asennettu isäntäkoneeseen

**Korjaus:**

1. Asenna Devin CLI käyttöympäristöllesi
2. Aseta `.env`-tiedostossa `CLI_DEVIN_BIN=/usr/local/bin/devin` (tai todellinen polku)
3. Käynnistä OmniRoute uudelleen ja testaa uudelleen kohdasta **Hallintapaneeli → CLI-työkalut**

### Mallin jäähdytys jää jumiin (manuaalinen nollaus)

**Oireet:**

- Malli näkyy edelleen jäähdytystilassa, vaikka vanhenemisaika on jo kulunut
- Pyynnöt ohittavat mallin edelleen yhdistelmäreitityksessä, vaikka aikaleima on menneisyydessä

**Manuaalinen nollaus:**

- **Hallintapaneeli:** **Asetukset → Mallien jäähdytykset** → napsauta kyseisen kortin **Ota uudelleen käyttöön** -painiketta
- **API:** `DELETE /api/resilience/model-cooldowns` hallintatodennuksen otsakkeilla

### Yhteys Command Code -palveluntarjoajaan epäonnistuu 403-virheellä

**Oireet:**

- 403-virhe testattaessa yhteyttä Command Code -palveluntarjoajaan
- Palveluntarjoajan kortissa näkyy "ei valtuutettu" uuden lisäyksen jälkeen

**Syy:** OAuth-työnkulku ei valmistunut (takaisinkutsua ei vastaanotettu tai tunnusta ei tallennettu pysyvästi).

**Korjaus:**

- Käynnistä OAuth-työnkulku uudelleen suorittamalla CLI:ssä `omniroute providers`, tai
- Suorita OAuth uudelleen kohdasta **Hallintapaneeli → Palveluntarjoajat → Command Code → Yhdistä uudelleen**

### ModelScope palauttaa aggressiivisia 429-jäähdytyksiä

**Oireet:**

- ModelScopen jäähdytysajat ovat erittäin lyhyitä tai alkavat välittömästi jo pienen pyyntöryöpyn jälkeen
- Yhdistelmäreititys ohittaa ModelScopen odotettua aikaisemmin

**Syy:** ModelScope lähettää palveluntarjoajakohtaisia `Retry-After`-otsakkeita. v3.8.0 sisältää näiden otsakkeiden erillisen käsittelyn, joten vanhemmat versiot tulkitsevat ne virheellisesti yleisiksi nopeusrajoitusvihjeiksi.

**Korjaus:**

- Varmista, että käytössäsi on v3.8.0 tai uudempi
- Varmista kohdassa **Asetukset → Vikasietoisuus**, että `useUpstream429BreakerHints`-valitsin on käytössä

### OMNIROUTE_WS_BRIDGE_SECRET puuttuu tuotannosta

**Oireet:**

- Jokainen Codex/Responses WebSocket -siltapyyntö palauttaa 401-virheen etätuotantoisännässä suoritettaessa
- WebSocket-sillan kättely sulkeutuu välittömästi yhteyden muodostamisen jälkeen

**Syy:** Ympäristömuuttuja `OMNIROUTE_WS_BRIDGE_SECRET` puuttuu tuotantoympäristöstä.

**Korjaus:**

1. Luo satunnainen salaisuus: `openssl rand -hex 32`
2. Aseta tuotantopalvelimen ympäristössä `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` (ja kaikissa siltaan yhteyttä ottavissa asiakkaissa)
3. Käynnistä OmniRoute uudelleen

### Responses API: taustatila heikennetty synkroniseksi

**Oireet:**

- Lokiin kirjataan varoitus: `background mode degraded to synchronous`
- `background: true` -pyyntö palauttaa taustatyön tunnisteen sijaan tavallisen synkronisen vastauksen

**Syy:** v3.8.0 heikentää tarkoituksellisesti Responses API:n `background: true` -pyynnöt synkroniseksi suoritukseksi ja lähettää samalla varoituksen. Täysi asynkroninen taustasuoritus toteutetaan tulevaisuudessa.

**Korjaus:**

- Muuta asiakasta kutsumaan ilman `background`-asetusta, tai
- Odota myöhempää julkaisua, joka sisältää täyden asynkronisen taustatilan (seuraa muutoslokia)

## Hidas käynnistys / valmiuden aikakatkaisu

Jos CLI tulostaa ilmoituksen `⚠ Server did not respond within 60s`, mutta palvelin
todellisuudessa toimii, valmiustarkistuksen aikaraja on ympäristöllesi liian lyhyt.

Tätä tapahtuu yleisesti Windowsissa (virustorjunta, tiedostojärjestelmän valvontaprosessit) tai säilöissä,
joissa käynnistyksen työkuorma on suuri.

**Korjaus — pidennä aikarajaa:**

```bash
# Ympäristömuuttujan kautta (säilyy käynnistysten välillä):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuuttia
omniroute serve

# CLI-valitsimen kautta (vain tällä suorituskerralla):
omniroute serve --ready-timeout 180000
```

Oletusarvo on 60 000 ms (60 s). Varoitus on vain tiedoksi; palvelin
jatkaa käynnistymistä taustalla ja on tavoitettavissa, kun käynnistys on valmis.

Lisätietoja muuttujasta `OMNIROUTE_READY_TIMEOUT_MS` on tiedostossa
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
