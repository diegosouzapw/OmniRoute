## Pikaopas

**Oletko uusi OmniRoute-käyttäjä?** Aloita tästä — nämä ratkaisevat 90 % ongelmista:

| Näet tämän              | Mitä se tarkoittaa                                    | Mitä tehdä                                                                                                      |
| ----------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| "Can't connect"         | OmniRoute ei ole käynnissä                            | Suorita `omniroute` tai `docker restart omniroute`                                                              |
| "Invalid API key"       | Avaimesi on virheellinen tai vanhentunut              | Kopioi avain uudelleen palveluntarjoajan verkkosivustolta                                                       |
| "Rate limit exceeded"   | Lähetät liian monta pyyntöä                           | Odota 1 minuutti tai käytä automaattista varapalvelua asetuksella `model: "auto"`                               |
| "Quota exceeded"        | Olet käyttänyt ilmaisen/maksullisen kiintiösi loppuun | Yhdistä lisää palveluntarjoajia tai käytä ilmaisia palveluntarjoajia (Kiro, Pollinations)                       |
| "Slow responses"        | Palveluntarjoaja on ruuhkautunut tai kaukana          | Käytä `model: "auto/fast"` tai yhdistä nopeampi palveluntarjoaja (Groq, Cerebras)                               |
| "Wrong provider used"   | `auto` valitsi eri palveluntarjoajan                  | Tämä on normaalia! `auto` valitsee parhaan. Pakota tietty palveluntarjoaja asetuksella `model: "openai/gpt-4o"` |
| "502 Bad Gateway"       | Palveluntarjoaja ei ole käytettävissä                 | Odota ja yritä uudelleen tai vaihda palveluntarjoajaa asetuksella `model: "auto"`                               |
| "401 Unauthorized"      | Kirjautumistietosi ovat virheelliset                  | Tarkista API-avaimesi tai tunnistaudu uudelleen OAuthilla                                                       |
| "429 Too Many Requests" | Pyyntötiheyttä on rajoitettu                          | Odota 1 minuutti tai yhdistä lisää palveluntarjoajia                                                            |

**Eikö ongelma vieläkään ratkennut?** Katso alta [yksityiskohtainen vianmääritys](#detailed-troubleshooting) tai kysy [Discordissa](https://discord.gg/U47eFqAXCn).

## Yksityiskohtainen vianmääritys

---

### Ilmaisten palveluntarjoajien pyyntötiheyden rajoitukset (429 / 400 / 401)

**Oire**: Kun käytät asetusta `model: "auto"` ilmaisten tai tunnistautumista vaatimattomien palveluntarjoajien (opencode, auggie jne.) kanssa, saat vastausten sijaan ajoittain virheen `HTTP 429`, `400` tai `401`. Pyynnöt onnistuvat, kun sama kehote lähetetään uudelleen hetkeä myöhemmin, mutta automaatio (cron-työt, agentit, komentosarjat) keskeytyy ensimmäiseen virheeseen.

**Perussyy**: Kolme toisistaan riippumatonta vikatilaa kasautuu:

1. **Palveluntarjoajan pyyntötiheysrajoitus (`429`)**: Ilmaistasot voivat käyttää aikajaksoihin perustuvaa kiintiötä. Rinnakkaisten kutsujen pyrähdys kuluttaa sen loppuun, minkä jälkeen seuraava pyyntö hylätään, kunnes aikajakso nollautuu.
2. **Rikkinäinen malli läpivälityksessä (`400`/`401`)**: `auto/*`-poolit voivat sisältää `opencode`-palvelun läpivälitysmalleja, jotka on rekisteröity luetteloon mutta joilla ei ole toimivia kirjautumistietoja (esim. `oc/north-mini-code-free` → `401`). Automaattinen reititin kokeilee tällaista mallia, epäonnistuu, ja virhe välitetään eteenpäin ennen kuin varapalveluun siirtyminen ehtii käynnistyä.
3. **Samanaikaisuuden voimistava vaikutus (`429` kuormituksessa)**: Kun useat agentti- tai cron-istunnot käyttävät `auto`-asetusta yhtä aikaa, pyyntöjen kokonaismäärä ylittää ilmaisten palveluntarjoajien sietokyvyn, jolloin asianmukaisetkin kutsut merkitään väärinkäytöksiksi.

**Vahvistettu korjaus (yhteisön ilmoittama, 2026-08-10)**: säädä kolmea ympäristömuuttujaa siten, että kierrätys, samanaikaisuuden hallinta ja varapalveluun siirtyminen vaimentavat ilmaistason vaihtelua sen sijaan, että prosessi keskeytyisi siihen:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # siirry toiseen malliin/palveluntarjoajaan virhetilanteessa 400/401 (ohittaa rikkinäiset läpivälitysmallit)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # raskaiden pyyntöjen samanaikaisuuden nimenomainen yläraja (oletusarvoisesti asettamatta: pyyntömäärälle ei ole rajaa, katso huomautus alta)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # pidempi rajattu odotus raskaan kapasiteetin vapautumiselle välittömän, uudelleenyrityksen sallivan 503-virheen sijaan
```

Aseta nämä OmniRoute-prosessin ympäristöön (taustapalveluun, esimerkiksi LaunchAgent-plist-tiedoston tai komennon `systemctl edit` kautta) ja käynnistä sitten OmniRoute uudelleen. Kierrätysasetus on yksittäisistä keinoista vaikutukseltaan suurin: se muuttaa lopullisen virheen läpinäkyväksi uudelleenyritykseksi poolin toimintakuntoista palveluntarjoajaa käyttäen.

**Huomautus**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` rajoittaa samanaikaisesti suoritettavien raskaiden eli pitkän kontekstin pyyntöjen määrää; raja on sisäänpääsyportti, ei palveluntarjoajan pyyntötiheyden rajoitin. **#503-fanout-päivitys:** tätä muuttujaa ei enää aseteta oletusarvoisesti (se rajoittaa nyt vain silloin, kun se on määritetty erikseen yllä kuvatulla tavalla) — raskaiden pyyntöjen sisäänpääsyä rajoittaa sen sijaan automaattisesti johdettu tavubudjetti (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), joka skaalautuu isäntäkoneen todellisen muistirajan perusteella. Näin ollen tuoreessa käyttöönotossa pitäisi ilmetä huomattavasti vähemmän `503 chat_admission_busy` -hylkäyksiä ilman, että tätä muuttujaa tarvitsee asettaa lainkaan; sen nimenomainen asettaminen tässä toimii edelleen täsmälleen dokumentoidulla tavalla. Nimenomaiset tavubudjetin ohitukset rajataan välille 8 MiB–2 GiB. `413 body_exceeds_budget` ei ole tilapäinen virhe: kasvata tavubudjettia, pienennä arvoa `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` tai kasvata prosessin muistirajaa. `inflight_bytes_budget`-pudotus johtuu tilapäisestä resurssikilpailusta, ja pyyntö voidaan yrittää uudelleen. Palveluntarjoajakohtaista pyyntötiheyden rajoitusta (`open-sse/services/rateLimitManager.ts`) hallitaan erikseen muuttujilla `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` ja `RATE_LIMIT_AUTO_ENABLE` — katso `.env.example`.

**Korjauksen toimivuuden varmistaminen**: suorita agenttisi tai cron-työsi kahdesti nopeasti peräkkäin ja varmista, että molemmat suoritukset onnistuvat. Ennen korjausta toinen suoritus aiheuttaa tavallisesti virheen `429`/`401`. Korjauksen jälkeen virheet (jos niitä ilmenee) yritetään automaattisesti uudelleen ja kutsu suoritetaan loppuun. Voit myös suorittaa komennon `curl /monitoring/health` ja tarkkailla palveluntarjoajayhteyksien `rateLimitedUntil`-kenttää sekä kyseisten palveluntarjoajien `circuitBreakers.providerBreakers[].state`-tilaa — tila on jokin seuraavista: `CLOSED`, `DEGRADED`, `OPEN` tai `HALF_OPEN` (katso `src/shared/utils/circuitBreaker.ts`). Jatkuvasti epäonnistuva palveluntarjoaja siirtyy tilasta `CLOSED → DEGRADED → OPEN`, ennen kuin nollausikkuna sallii koepyynnön (`HALF_OPEN`).

**Jos näet edelleen 429-virheen**: kyseisen palveluntarjoajan aktiivisen tilin _kiintiö_ on todella käytetty loppuun (kyse ei ole pelkästä pyyntörajasta). Lisää toinen saman palveluntarjoajan tili OmniRoute-hallintapaneelissa kohdassa Providers → Accounts tai ota käyttöön toinen maksuton palveluntarjoaja (esim. `routeway`, `auggie`). Kierrätys auttaa vain tilapäisiin pyyntörajoitus-/400-/401-virheisiin; kokonaan loppuun käytetty kiintiö edellyttää toisia tunnistetietoja tai eri palveluntarjoajaa.

**Jos näet 403-virheen konenäkömalleissa (`auto/vision`, `bazaarlink/*`)**: yhdistetyltä tililtä puuttuu konenäön sisältävä maksullinen tilaus, tai API-avaimella ei ole riittäviä käyttöoikeuksia. Tarkista palveluntarjoajan hallintapaneelista, että avaimen käyttöoikeusalue sisältää konenäön/monimodaalisuuden, tai yhdistä maksullisen tason tili ja pidä se konenäön kohteena.

## npm install -varoitukset (ERESOLVE / vertaisriippuvuudet / vanhentuneet paketit)

Kun suoritat komennon `npm install -g omniroute`, saatat nähdä suuren määrän varoituksia, kuten `npm warn ERESOLVE`, ilmoituksia vertaisriippuvuuksista ja `deprecated`-viestejä. **Nämä ovat odotettuja ja harmittomia.** Asennus onnistui, jos tulosteessa näkyy `added <N> packages`.

Varoitukset johtuvat sellaisten kolmannen osapuolen pakettien vanhentuneista vertaisriippuvuuksien versioalueista, joita OmniRoute ei hallitse:

1. **`marked-terminal` vaatii version `marked >=1 <16`, mutta löytyi `marked@18`** — toimii käytännössä hyvin; upstream-paketin vertaisriippuvuuden versioalue on vain vanhentunut.
2. **`deprecated prebuild-install@7.1.3`** — transitiivinen apuohjelma natiivibinäärien noutamiseen. Sitä ei
   käytetä lukitun `wreq-js`-siirtosidoksen asentamiseen, eikä se tarkoita, että verkkoevästeiden
   tarjoajan siirtoasetusten määritys olisi epäonnistunut.

**Toimenpiteitä ei tarvita** — varoituksia ei voi poistaa kokonaan käytöstä ilman upstream-pakettien haarauttamista.

## Virustorjunnan väärät positiiviset havainnot

<a name="antivirus-false-positives"></a>

### Avast/AVG asettaa `README.md`-tiedoston karanteeniin tunnisteella `MD:HttpRequest-inf[Susp]`

**Tämä on väärä positiivinen havainto. Mikään ei ole saastunut, eikä toimenpiteitä tarvita.**

Avast ja AVG käyttävät heuristiikkaa, joka merkitsee tekstitiedostoja ja Markdown-tiedostoja,
jos ne sisältävät paljon HTTP-pyynnöiltä näyttäviä linkkejä. OmniRouten `README.md` toimitetaan
npm-paketin mukana (se on lueteltu kohdassa `package.json` → `files`), joten globaalissa
asennuksessa se sijoitetaan polkuun `node_modules/omniroute/README.md` — ja se sisältää noin
15 `http://localhost:20128/...`-esimerkkiä (MCP:n HTTP/SSE-päätepisteet, A2A:n `.well-known`-URL
ja `curl`-katkelmia). Tämä linkkitiheys riittää laukaisemaan heuristiikan.

Jos tämä alkoi vasta äskettäin: tiedoston luonne ei ole muuttunut. README-tiedoston
päätepistetaulukkoa laajennettiin (MCP HTTP + SSE + A2A lisättiin), ja siihen lisättiin
enemmän `curl`-esimerkkejä, mikä nosti sen heuristiikan kynnysarvon yli.

Tiedosto on passiivista dokumentaatiota, jossa ei ole lainkaan suoritettavaa sisältöä.
Voit palauttaa sen turvallisesti karanteenista.

**Toimi näin:**

1. **Lopeta ilmoitukset** — lisää asennushakemisto virustorjuntasi poikkeuksiin
   (Avast: Asetukset → Poikkeukset) lisäämällä globaalin `node_modules`-polkusi ja/tai
   OmniRouten datahakemiston (`~/.omniroute/`).
2. **Ilmoita väärästä positiivisesta havainnosta** — <https://www.avast.com/false-positive-file-form.php>,
   ja liitä mukaan karanteeniin asetettu `README.md`. Tämä korjaus auttaa kaikkia, sillä
   kyse on valmistajan heuristiikan ylireagoinnista tekstitiedostoon.

**Miksi emme ”korjaa” tätä omalta puoleltamme:** kaikki esimerkit käyttävät osoitetta
`http://localhost`, eikä localhost voi käyttää `https`-yhteyttä ilman itse allekirjoitettujen
varmenteiden aiheuttamaa vaivaa. Dokumentaation vääristäminen yhden valmistajan heuristiikan
kiertämiseksi haittaisi jokaista lukijaa vain skannerivirheen vuoksi.

### Kaspersky merkitsee työpöytäsovelluksen tunnisteella `PDM:Trojan.Win32.Generic`

**Tämä on käyttäytymiseen perustuvan heuristiikan aiheuttama väärä positiivinen havainto.
Mikään ei ole saastunut.** Kasperskyn `PDM:`-etuliite tarkoittaa, että arvio on peräisin sen
Proactive Defense Module (System Watcher) -moduulista, joka arvioi, mitä asennusohjelma
_tekee_, sen sijaan että vertaisi sitä tunnettuihin haittaohjelmiin. Kun tunnistus laukeaa,
Kaspersky ”peruuttaa” koko asennuksen — poistaen jo kirjoittamansa tiedostot — joten sovellus
jää rikkinäiseksi tai puuttuu kokonaan.

Sen merkitsemät tiedostot ovat työpöytäsovellukseen sisällytettyjen ilmoitettujen avoimen
lähdekoodin riippuvuuksien vakiokomponentteja, esimerkiksi:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ja
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), selaimen automatisointikirjasto,
  jota käytetään sovelluksen sisäiseen palveluntarjoajaan kirjautumiseen ja selainpohjaiseen
  keskusteluun.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — kiinnitetty natiivi `wreq-js`-sidonta, jota käytetään selaimen sormenjälkeä jäljittelevään
  HTTP-liikenteeseen verkkosivustojen evästeitä käyttävillä palveluntarjoajilla (`<arch>` on
  `x64` tai `arm64`).

**Miksi tunnistus laukeaa:** Windows-asennusohjelmaa **ei ole vielä allekirjoitettu
koodivarmenteella**, joten allekirjoittamattomalla NSIS-asennusohjelmalla ei ole minkäänlaista
mainetta ja käyttäytymisheuristiikat toimivat mahdollisimman aggressiivisesti. Kun tähän
yhdistyvät mukana toimitettu natiivi DLL-tiedosto ja sadat hakemistoon
`%LOCALAPPDATA%\Programs\OmniRoute` kirjoitettavat `.js`-tiedostot (mukaan lukien Next.js:n
itsenäisen koontiversion hajautusarvopäätteiset pakettihakemistot), se riittää laukaisemaan
heuristiikan. Koodin allekirjoitus on suunnitteilla; ennen sen toteutumista tämä voi toistua
uusissa julkaisuissa.

**Toimi näin:**

1. **Tarkista ensin latauksesi** (tämä sulkee pois tiedoston peukaloinnin). Jokaisessa
   julkaisussa julkaistaan `latest.yml`, jonka `sha512`-kenttä (base64) kattaa
   `OmniRoute.Setup.<version>.exe`-asennusohjelman. Suorita PowerShellissä seuraava komento
   asennusohjelman sisältävästä kansiosta:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Tulosteen on vastattava kohtaa `latest.yml` → `sha512`. Jos se ei vastaa, poista tiedosto
   ja lataa se uudelleen ainoastaan [GitHubin julkaisusivulta](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Palauta + lisää poikkeus** — palauta peruutetut kohteet karanteenista ja lisää
   `%LOCALAPPDATA%\Programs\OmniRoute` poikkeuksiin (Kaspersky → Asetukset → Uhat ja
   poikkeukset), ja asenna sitten uudelleen.
3. **Ilmoita väärästä positiivisesta havainnosta** — <https://opentip.kaspersky.com/>.
   Käyttäjien lähettämät väärien positiivisten havaintojen ilmoitukset nopeuttavat
   aidosti sallittujen luetteloon lisäämistä.

## Node.js-yhteensopivuus

<a name="nodejs-compatibility"></a>

### Kirjautumissivu kaatuu tai näyttää "Module self-registration" -virheen

**Syy:** Käytössäsi on Node.js-versio, joka ei täytä OmniRouten hyväksymää turvallisen suoritusympäristön vähimmäisvaatimusta. Yleisin tapaus on vanhempi Node 22- tai 24-korjausversio, joka alittaa OmniRouten edellyttämän korjatun tietoturvatason.

**Oireet:**

- Kirjautumissivu näyttää tyhjän näytön tai palvelinvirheen
- Konsolissa näkyy `Error: Module did not self-register` tai vastaavia natiivisidontavirheitä
- Kirjautumissivulla näkyy **oranssi varoituspalkki**, jossa ilmoitetaan Node-versiosi, jos suoritusympäristö ei vastaa tuettua tietoturvakäytäntöä

**Korjaus:**

1. Asenna tuettu Node.js LTS -julkaisu (suositus: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Tarkista versiosi: komennon `node --version` pitäisi näyttää `v24.0.0` tai uudempi 24.x LTS -sarjan versio
3. Asenna OmniRoute uudelleen: `npm install -g omniroute`
4. Käynnistä uudelleen: `omniroute`

> **Tuetut turvalliset versiot:** `>=22.22.2 <23` tai `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) ja Node.js 26 ovat täysin tuettuja.

### npm v11+: `better-sqlite3` ei ole asennettu (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Syy:** npm v11 (toimitetaan Node.js 24+:n mukana) estää oletusarvoisesti valinnaisten
riippuvuuksien asennusskriptit. Koska `better-sqlite3` on lueteltu kohdassa `optionalDependencies`
ja vaatii natiivin käännöksen (`node-gyp rebuild`), npm ohittaa sen ilmoittamatta.

**Oireet:**

- Palvelin kaatuu käynnistyksen yhteydessä virheeseen `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` näyttää ilmoituksen "No such file or directory"
- `npm ls better-sqlite3` näyttää `(empty)`

**Korjaus:**

1. Hyväksy asennusskriptit ja asenna uudelleen:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Tai asenna esikäännetty versio manuaalisesti:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Varmista, että se toimii: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Syy:** Yleisen `npm install -g omniroute` -asennuksen jälkeen paketin sisältämä natiivi `better-sqlite3`-binääritiedosto on voitu kääntää eri arkkitehtuurille tai Node.js ABI:lle kuin paikallisesti käytössä oleva ympäristö. Tämä on yleistä macOS:ssä (sekä Apple Silicon- että Intel-järjestelmissä), kun esikäännetty binääritiedosto ei vastaa ympäristöäsi.

**Oireet:**

- Palvelin epäonnistuu välittömästi käynnistyksen yhteydessä `dlopen`-virheeseen
- Virhe sisältää tekstin `slice is not valid mach-o file`
- Täydellinen esimerkki:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Korjaus — käännä uudelleen paikallista ympäristöäsi varten (Node.js-version alentamista ei tarvita):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Huomautus:** Tämä kääntää natiivisidonnan uudelleen paikallista Node.js-versiotasi ja suoritinarkkitehtuuriasi varten ja korjaa siten binääritiedostojen yhteensopimattomuuden. Virallisesti tuettu suoritusympäristön versioalue on **`>=22.22.2 <23` tai `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` tiedostossa `src/shared/utils/nodeRuntimeSupport.ts`, yhdenmukainen `package.json`-tiedoston `engines`-kentän kanssa). Node.js 24.x LTS (Krypton) ja Node.js 26 ovat täysin tuettuja `better-sqlite3` v12.x:n kanssa.

## Välityspalvelinongelmat

<a name="proxy-issues"></a>

### Palveluntarjoajan vahvistuksessa näkyy virhe "fetch failed"

**Syy:** API-avaimen vahvistuspäätepiste (`POST /api/providers/validate`) ohitti aiemmin välityspalvelinmääritykset, mikä aiheutti virheitä ympäristöissä, joissa liikenne on reititettävä välityspalvelimen kautta.

**Korjaus (v3.5.5+):** Tämä on nyt korjattu. Palveluntarjoajan vahvistus reititetään `runWithProxyContext`-toiminnon kautta, jolloin palveluntarjoajakohtaiset ja yleiset välityspalvelinasetukset huomioidaan automaattisesti.

### Tokenin kuntotarkistus epäonnistuu virheellä "fetch failed"

**Syy:** OAuth-tokenien päivitys taustalla ei selvittänyt välityspalvelinmäärityksiä yhteyskohtaisesti.

**Korjaus (v3.5.5+):** Tokenien kuntotarkistuksen ajoittaja selvittää nyt välityspalvelinmääritykset yhteyskohtaisesti ennen päivitysyritystä. Päivitä versioon v3.5.5+.

### SOCKS5-välityspalvelin palauttaa virheen "invalid onRequestStart method"

**Syy:** Node.js 22:ssa undici@8-välittäjä ei ole yhteensopiva Noden sisäänrakennetun `fetch()`-toteutuksen kanssa.

**Korjaus (v3.5.5+):** OmniRoute käyttää nyt undicin omaa `fetch()`-funktiota, kun välityspalvelinvälittäjä on aktiivinen, mikä varmistaa yhdenmukaisen toiminnan. Päivitä versioon v3.5.5+.

### MITM-välityspalvelin WSL:ssä: Windows-isännän työpöytäsovellusten liikennettä ei siepata

**Syy:** MITM-välityspalvelin ja sen CA-varmenne asennetaan ympäristöön, jossa OmniRoute suoritetaan. WSL:ssä tämä ympäristö on Linux-vierasjärjestelmä, kun taas tekoälytyöpöytäsovellukset (Kiro, Trae, Copilot, Zed, …) toimivat Windows-isännässä. Isännän sovellukset eivät luota vierasjärjestelmän varmennevarastoon eivätkä reititä liikennettä vierasjärjestelmän järjestelmävälityspalvelimen kautta, joten työpöytäsovellusten liikennettä ei tällöin siepata.

**Suositus:** Suorita OmniRoute natiivisti samassa käyttöjärjestelmässä kuin työpöytäsovellukset, joiden liikennettä haluat siepata (Windows Windows-sovelluksille ja vastaavasti macOS/Linux). Jos OmniRoute pidetään WSL:ssä ja kohteena ovat isäntäjärjestelmän sovellukset, luotu CA-varmenne on lisättävä manuaalisesti luotetuksi Windows-isännässä ja kunkin isäntäsovelluksen verkko-/välityspalvelinasetukset on määritettävä käyttämään WSL-välityspalvelimen päätepistettä — tämä on ei-tuettu ja hauras kokoonpano.

## Pilviongelmat

### Pilvisynkronoinnin virheet

1. Varmista, että `BASE_URL` osoittaa käynnissä olevaan instanssiisi (esim. `http://localhost:20128`)
2. Varmista, että `CLOUD_URL` osoittaa pilvipäätepisteeseesi (esim. `https://omniroute.dev`)

**Oire:** `Unexpected token 'd'...` pilvipäätepisteessä suoratoistamattomissa kutsuissa.

**Syy:** Ylävirta palauttaa SSE-hyötykuorman, vaikka asiakas odottaa JSON-muotoa.

**Kiertotapa:** Käytä `stream=true`-asetusta suorissa pilvikutsuissa. Paikallinen suoritusympäristö sisältää SSE→JSON-varatoiminnon.

### Pilvi ilmoittaa yhteyden olevan muodostettu, mutta näyttää virheen "Virheellinen API-avain"

1. Luo uusi avain paikallisessa hallintapaneelissa (`/api/keys`)
2. Suorita pilvisynkronointi: Ota pilvi käyttöön → Synkronoi nyt
3. Vanhat tai synkronoimattomat avaimet voivat edelleen palauttaa pilvessä `401`-virheen

## Docker-ongelmat

### Dockerin IPv6 / yhteyden nollautuminen

<a name="docker-ipv6"></a>

**Oireet:** `curl http://localhost:20128/v1/models` palauttaa virheen `curl: (56) Recv failure: Connection reset by peer`. Hallintapaneeli ja todentamattomat päätepisteet toimivat, mutta todennetut päätepisteet epäonnistuvat — ongelma vaikuttaa todentamisongelmalta, vaikka se ei sitä ole.

**Syy:** `docker run -p 20128:20128` julkaisee portin sekä osoitteessa `0.0.0.0` (IPv4) että `::` (IPv6), mutta säilön sisällä oleva prosessi kuuntelee vain IPv4-osoitetta. Isännissä, joissa `localhost` ratkaistaan ensin osoitteeksi `::1`, yhteys päätyy julkaistuun IPv6-porttiin, jonka takana ei ole kuuntelijaa → yhteys nollautuu.

**Korjaus:**

1. **Nopea diagnostiikka:** Suorita `curl -4 http://localhost:20128/v1/models`. Jos se toimii `-4`-valitsimella mutta epäonnistuu ilman sitä, IPv6-sidonnassa on ristiriita.
2. **Pysyvä korjaus:** Sido nimenomaisesti IPv4-osoitteeseen käyttämällä `docker run` -komennossa asetusta `-p 127.0.0.1:20128:20128`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Tämä pakottaa IPv4-sidonnan ja estää samalla välityspalvelimen paljastamisen kaikissa isännän verkkoliitännöissä.

## Virheenkorjaus

Kun putken tallennus on käytössä, aseta `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false`, jos haluat jättää
suoratoiston osien hyötykuormat pois, tai säädä `CALL_LOG_PIPELINE_MAX_SIZE_KB`-arvoa muuttaaksesi artefaktien enimmäiskokoa kilotavuina.

### Palveluntarjoajan kunnon tarkistaminen

```bash
# Kunnon hallintapaneeli
http://localhost:20128/dashboard/health

# API:n kuntotarkistus
curl http://localhost:20128/api/monitoring/health
```

### Suoritusympäristön tallennustila

- Päätila: `${DATA_DIR}/storage.sqlite` (palveluntarjoajat, yhdistelmät, aliakset, avaimet, asetukset)
- Käyttö: SQLite-taulut tiedostossa `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + valinnainen `${DATA_DIR}/call_logs/`
- Sovelluslokit: `<repo>/logs/...` (kun `APP_LOG_TO_FILE=true`)
- Kutsulokien artefaktit: `${DATA_DIR}/call_logs/YYYY-MM-DD/...`, kun kutsulokiputki on käytössä

Pyyntölokit-sivun **Tyhjennä historia** -toiminto tyhjentää `call_logs`-taulun, vanhan
`request_detail_logs`-taulun ja paikallisen `${DATA_DIR}/call_logs/`-artefaktihakemiston.

## Circuit Breaker -ongelmat

### Palveluntarjoaja on juuttunut OPEN-tilaan

Kun palveluntarjoajan Circuit Breaker on OPEN-tilassa, pyynnöt estetään, kunnes jäähdytysjakso päättyy.

**Korjaus:**

1. Siirry kohtaan **Dashboard → Settings → Resilience**
2. Tarkista kyseisen palveluntarjoajan Circuit Breaker -kortti
3. Tyhjennä kaikki Circuit Breakerit napsauttamalla **Reset All** tai odota jäähdytysjakson päättymistä
4. Varmista ennen nollaamista, että palveluntarjoaja on todella käytettävissä

1. Tarkista virheiden toistumismalli kohdasta **Dashboard → Health → Provider Health**
2. Siirry kohtaan **Settings → Resilience → Provider Profiles** ja nosta virhekynnystä
3. Tarkista, onko palveluntarjoaja muuttanut API-rajoituksiaan tai vaatiiko se uudelleentodennusta
4. Tarkista latenssitelemetria — suuri latenssi voi aiheuttaa aikakatkaisuun perustuvia virheitä

## Vikasietoisuusasetukset

### Automaattinen nopeusrajoitus ei aktivoidu

- Automaattinen nopeusrajoitus koskee vain API-avainta käyttäviä palveluntarjoajia (ei OAuth-/tilaustodennusta)
- Varmista, että automaattinen nopeusrajoitus on käytössä kohdassa **Settings → Resilience → Provider Profiles**
- Tarkista, palauttaako palveluntarjoaja `429`-tilakoodeja tai `Retry-After`-otsakkeita

### Eksponentiaalisen viiveen säätäminen

Palveluntarjoajaprofiilit tukevat seuraavia asetuksia:

- **Perusviive** — Ensimmäisen virheen jälkeinen alkuodotusaika (oletus: 1s)
- **Enimmäisviive** — Odotusajan enimmäisraja (oletus: 30s)
- **Kerroin** — Kuinka paljon viivettä kasvatetaan kutakin peräkkäistä virhettä kohden (oletus: 2x)

### Samanaikaisten uudelleenyritysten estäminen

Kun useat samanaikaiset pyynnöt kohdistuvat nopeusrajoitettuun palveluntarjoajaan, OmniRoute käyttää mutexia ja automaattista nopeusrajoitusta pyyntöjen sarjoittamiseen ja ketjureaktiona syntyvien virheiden estämiseen. Tämä tapahtuu automaattisesti API-avainta käyttävillä palveluntarjoajilla.

### Keskustelupyynnöt epäonnistuvat virheellä 503 / chat_admission_busy

**Oireet:**

- Keskustelun täydennyspäätepiste palauttaa uudelleenyrityksen sallivan `503`-vastauksen, jonka virhekoodi on
  `chat_admission_busy`.
- Vastaus sisältää `Retry-After`-otsakkeen. Muutoksesta #12135 lähtien arvo johdetaan havaitusta
  käyttöasteesta — suuremmasta seuraavien välillä: `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`-aikaikkuna, jonka pyyntö on jo
  odottanut, ja aika, jonka nykyiset raskaat varaukset ovat olleet voimassa — pyöristettynä ylöspäin täysiin
  sekunteihin ja rajattuna 60 sekuntiin. Kun pääsynhallinta on käyttämättömänä, historialliset vähimmäisarvot säilyvät: 2 sekuntia
  tavupohjaisella polulla ja 1 sekunti rakennepohjaisella polulla (joka sisältää myös arvon
  `reason: "structure_limit"`).
- Näin voi tapahtua, kun toinen raskas keskustelu tai pitkäkestoinen suoratoistovastaus on edelleen
  käsiteltävänä.

Tavupohjaisen vastauksen runko on:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Rakennepohjainen vastaus käyttää samaa tyyppiä ja koodia sekä viestiä
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ja arvoa `reason: "structure_limit"`.
Oletuskynnysarvoilla pyyntö on rakenteellisesti raskas, kun siinä on vähintään `200` viestiä,
vähintään `64` työkalua tai vähintään `32,000` arvioitua tokenia tai kun rajattu rakennearviointi
saavuttaa rajansa: `10,000` käsiteltyä solmua tai syvyys `12`.

**Syy:** Kyse on tarkoituksellisesta kuormituksen keventämisestä OmniRouten sisällä, ei ylävirran palveluntarjoajan virheestä.
Kukin prosessi käyttää prosessikohtaista suojausta rajallisen raskaan kapasiteetin varaamiseen ennen suuren
pyyntörungon säilyttämistä ja jäsentämistä. Raskas varaus pysyy voimassa SSE-vastauksen
koko elinkaaren ajan.

**#503-fanout:** ennen tätä korjausta suojaus rajoitti samanaikaisuuden kiinteään pyyntömäärään
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, oletus `1`) isäntäkoneen muistista riippumatta, joten koodausagenttien
hajautus (useita aliagentteja/CLI-työkaluja, rungot tavallisesti > 256 KB) supisti tosiasiallisen
samanaikaisuuden noin yhteen ja aiheutti 503-virheitä täysin normaalissa kuormituksessa. Suojaus säätyy nyt
automaattisesti: sitä ohjaa automaattisesti johdettu vastaanoton TAVUbudjetti (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), joka mitoitetaan
prosessin todellisen muistirajan perusteella, ja se huomioi myös reaaliaikaisen resurssipainesignaalin — joten se
keventää kuormitusta vain, kun isäntäkoneella on todellista muistipainetta, eikä pelkästään siksi, että useampi kuin yksi
raskas pyyntö saapui samanaikaisesti. Vanhaa määrärajaa (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
noudatetaan edelleen, mutta vain, jos asetat sen nimenomaisesti.

Kun kapasiteetti on varattu, raskas pyyntö odottaa ensin enintään
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`-ajan (oletus `2000`, arvo `0` poistaa odotuksen käytöstä), että paikka vapautuu,
ennen kuin se palauttaa uudelleenyrityksen sallivan `503`-vastauksen. Rajattu odotus on käytössä, jotta agenttityyliset asiakkaat
(OpenCode, Claude Code, Cursor), jotka hajauttavat raskaita alipyyntöjä samanaikaisesti, sarjoittavat purskeen
sen sijaan, että kuluttaisivat koko uudelleenyritysbudjettinsa välittömiin hylkäyksiin ja keskeytyisivät kesken tehtävän.
Nykyisten raskaiden varausten käyttöaste, määritetty tavubudjetti ja reaaliaikaisen paineen vakavuus
näytetään kohdassa `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — tarkista nämä ennen ympäristömuuttujien muuttamista.
Settings → Resilience → Request Queue → Concurrent Requests ei ohjaa tätä; kyseinen asetus
ohjaa erillistä palveluntarjoajapyyntöjen jonotusmekanismia.

**Korjaus:**

1. Yritä ensin uudelleen. Asiakkaiden tulee noudattaa `Retry-After`-arvoa ja käyttää viivettä sen sijaan, että ne
   toistaisivat pyynnön välittömästi.
2. Tarkista `/api/monitoring/health` → `chatAdmission` ennen minkään säätämistä. `countCapEnabled:
false` ja suuri `maxInflightBytes` tarkoittavat, että automaattisesti johdettu budjetti toimii jo
   oikein; `pressureSeverity`-arvo `high`/`critical` tarkoittaa, että isäntäkoneen muisti on aidosti vähissä —
   tätä ei voi korjata pääsynhallinnan ympäristömuuttujalla, vaan tarvitaan enemmän RAM-muistia tai pienempi työkuorma.
3. Vain jos `/api/monitoring/health` osoittaa, että automaattisesti johdettu budjetti on aidosti liian pieni
   isäntäkoneellesi (harvinaista — se skaalautuu jo säilöistä fyysisiin palvelimiin), ohita se suoraan muuttujalla
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` sen sijaan, että palaisit vanhaan pyyntömäärään perustuvaan rajoitukseen.

Viralliset pääsynhallinta-asetukset ovat [ympäristömuuttujien viitteessä](../reference/ENVIRONMENT.md#4-security--authentication).

## Valinnainen RAG-/LLM-virheluokitus (16 ongelmaa)

Jotkut OmniRoute-käyttäjät sijoittavat yhdyskäytävän RAG- tai agenttipinojen eteen. Tällaisissa kokoonpanoissa esiintyy usein erikoinen tilanne: OmniRoute näyttää toimivan normaalisti (palveluntarjoajat ovat käytettävissä, reititysprofiilit ovat kunnossa eikä nopeusrajoitushälytyksiä ole), mutta lopullinen vastaus on silti väärä.

Käytännössä nämä ongelmat johtuvat yleensä yhdyskäytävän jälkeisestä RAG-putkesta, eivät itse yhdyskäytävästä.

Jos haluat yhteisen sanaston näiden virheiden kuvaamiseen, voit käyttää WFGY ProblemMapia. Se on ulkoinen MIT-lisensoitu tekstiresurssi, joka määrittelee kuusitoista toistuvaa RAG-/LLM-virhemallia. Yleisellä tasolla se käsittelee seuraavia aiheita:

- haun ajautuminen ja rikkoutuneet kontekstirajat
- tyhjät tai vanhentuneet indeksit ja vektoritietokannat
- upotusten ja semantiikan yhteensopimattomuus
- kehotteen koostamiseen ja konteksti-ikkunaan liittyvät ongelmat
- logiikan romahtaminen ja liian itsevarmat vastaukset
- pitkien ketjujen ja agenttien koordinointivirheet
- moniagenttimuistin ja roolien ajautuminen
- käyttöönottoon ja alustuksen järjestykseen liittyvät ongelmat

Ajatus on yksinkertainen:

1. Kun tutkit virheellistä vastausta, tallenna:
   - käyttäjän tehtävä ja pyyntö
   - OmniRouten reitti tai palveluntarjoajayhdistelmä
   - kaikki myöhemmässä käsittelyssä käytetyt RAG-kontekstit (haetut asiakirjat, työkalukutsut jne.)
2. Yhdistä tapaus yhteen tai kahteen WFGY ProblemMap -numeroon (`No.1` … `No.16`).
3. Tallenna numero omaan koontinäyttöösi, toimintaohjeeseesi tai poikkeamien seurantajärjestelmääsi OmniRoute-lokien viereen.
4. Päätä vastaavan WFGY-sivun avulla, pitääkö RAG-pinoa, hakukomponenttia tai reititysstrategiaa muuttaa.

Koko teksti ja konkreettiset toimintaohjeet ovat täällä (MIT-lisenssi, vain tekstiä):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Voit ohittaa tämän osion, jos et käytä RAG- tai agenttiputkia OmniRouten takana.

## v3.8.0:n tunnetut ongelmat

v3.8.0-julkaisuun liittyvät ongelmat ja niiden nykyiset kiertotavat. Jos korjaus julkaistaan myöhemmässä korjausversiossa, merkintä päivitetään tai poistetaan.

### Devin CLI:n todennusvirheet

**Oireet:**

- "Devin CLI:tä ei löytynyt" tai "todennus epäonnistui" kutsuttaessa Deviniä käyttäviä työkaluja
- CLI:n suorituksenaikainen tarkistus ilmoittaa `installed=false`

**Syyt:**

- `CLI_DEVIN_BIN` osoittaa polkuun, jota ei ole olemassa
- Devin CLI:tä ei ole asennettu isäntäkoneeseen

**Korjaus:**

1. Asenna Devin CLI käyttöympäristöllesi
2. Aseta `.env`-tiedostossa `CLI_DEVIN_BIN=/usr/local/bin/devin` (tai todellinen polku)
3. Käynnistä OmniRoute uudelleen ja testaa uudelleen kohdasta **Koontinäyttö → CLI-työkalut**

### Mallin jäähdytys jää jumiin (manuaalinen nollaus)

**Oireet:**

- Malli näkyy edelleen jäähdytystilassa, vaikka päättymisaika on jo ohitettu
- Pyynnöt ohittavat mallin edelleen yhdistelmäreitityksessä, vaikka aikaleima on menneisyydessä

**Manuaalinen nollaus:**

- **Koontinäyttö:** **Asetukset → Mallien jäähdytykset** → napsauta kyseisessä kortissa **Ota uudelleen käyttöön**
- **API:** `DELETE /api/resilience/model-cooldowns` hallinnan todennusotsakkeilla

### Yhteys Command Code -palveluntarjoajaan epäonnistuu virheellä 403

**Oireet:**

- 403-virhe testattaessa yhteyttä Command Code -palveluntarjoajaan
- Palveluntarjoajan kortissa näkyy uuden lisäyksen jälkeen "ei valtuutettu"

**Syy:** OAuth-prosessia ei suoritettu loppuun (takaisinkutsua ei vastaanotettu tai tunnistetta ei tallennettu pysyvästi).

**Korjaus:**

- Käynnistä OAuth-prosessi uudelleen suorittamalla CLI:ssä `omniroute providers`, tai
- Suorita OAuth uudelleen kohdasta **Koontinäyttö → Palveluntarjoajat → Command Code → Yhdistä uudelleen**

### ModelScope palauttaa aggressiivisia 429-jäähdytyksiä

**Oireet:**

- ModelScopessa ilmenee hyvin lyhyitä tai välittömiä jäähdytyksiä pienen pyyntöryöpyn jälkeen
- Yhdistelmäreititys ohittaa ModelScopen odotettua aikaisemmin

**Syy:** ModelScope lähettää palveluntarjoajakohtaisia `Retry-After`-otsakkeita. v3.8.0 sisältää näille otsakkeille erillisen käsittelyn, joten vanhemmat versiot tulkitsevat ne virheellisesti yleisiksi nopeusrajoitusvihjeiksi.

**Korjaus:**

- Varmista, että käytössäsi on v3.8.0 tai uudempi
- Varmista kohdasta **Asetukset → Vikasietoisuus**, että `useUpstream429BreakerHints`-valitsin on käytössä

### OMNIROUTE_WS_BRIDGE_SECRET puuttuu tuotannosta

**Oireet:**

- 401-virhe jokaisessa Codex/Responses-WebSocket-siltapyynnössä, kun järjestelmää käytetään etätuotantopalvelimella
- WebSocket-sillan kättely sulkeutuu heti yhteyden muodostamisen jälkeen

**Syy:** Ympäristömuuttuja `OMNIROUTE_WS_BRIDGE_SECRET` puuttuu tuotantoympäristöstä.

**Korjaus:**

1. Luo satunnainen salaisuus: `openssl rand -hex 32`
2. Aseta tuotantopalvelimen ympäristössä `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` (sekä jokaisessa siltaan yhteyttä ottavassa asiakasohjelmassa)
3. Käynnistä OmniRoute uudelleen

### Responses API: taustatila heikennetty synkroniseksi

**Oireet:**

- Lokiin kirjataan varoitus: `background mode degraded to synchronous`
- `background: true` -pyyntö palauttaa taustatyön käsittelijän sijaan tavallisen synkronisen vastauksen

**Syy:** v3.8.0 heikentää tarkoituksella Responses API:n `background: true` -pyynnöt synkroniseksi suoritukseksi ja antaa samalla varoituksen. Täysi asynkroninen taustasuoritus toteutetaan tulevaisuudessa.

**Korjaus:**

- Muuta asiakasohjelmaa tekemään kutsu ilman `background`-asetusta, tai
- Odota myöhempää julkaisua, joka sisältää täyden asynkronisen taustatilan (seuraa muutoslokia)

## Hidas käynnistys / valmiuden aikakatkaisu

Jos CLI tulostaa ilmoituksen `⚠ Server did not respond within 60s`, vaikka palvelin
todellisuudessa toimii, valmiustarkistuksen aikaraja on liian lyhyt ympäristöllesi.

Näin tapahtuu yleisesti Windowsissa (virustorjunta, tiedostojärjestelmän valvonta) tai säilöissä,
joissa on raskaita käynnistystyökuormia.

**Korjaus — pidennä aikarajaa:**

```bash
# Ympäristömuuttujan kautta (säilyy käynnistysten välillä):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuuttia
omniroute serve

# CLI-valitsimen kautta (vain tämän kerran):
omniroute serve --ready-timeout 180000
```

Oletusarvo on 60 000 ms (60 s). Varoitus on vain tiedoksi; palvelin
jatkaa käynnistymistä taustalla ja on tavoitettavissa, kun käynnistys on valmis.

Katso täydelliset tiedot muuttujasta `OMNIROUTE_READY_TIMEOUT_MS` tiedostosta
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
