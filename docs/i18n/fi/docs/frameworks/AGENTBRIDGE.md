AgentBridge on OmniRouten MITM (Man-in-the-Middle) -välityspalvelin, joka sieppaa IDE-tekoälyagenttien HTTPS-liikenteen ja reitittää sen uudelleen OmniRouten yhtenäisen reititysmoottorin kautta. Se tukee **10:tä IDE-agenttia** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code ja Trae (tutkittavana) — minkä ansiosta OmniRoute on markkinoiden kattavimmin tekoälyavusteisia koodausagentteja tukeva MITM-välityspalvelin.

**Hallintapaneelin sijainti:** `/dashboard/tools/agent-bridge`
**Sivupalkin ryhmä:** Työkalut (Cloud Agents -ryhmän jälkeen)
**Katso myös:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — seuraa kaikkea siepattua liikennettä reaaliajassa; `docs/security/MITM-TPROXY-DECRYPT.md` (gitissä; ei käännetä osaksi `/docs`-hakemistoa) — Linuxin TPROXY-pohjainen läpinäkyvän salauksenpurun kaappaustila, jota ohjataan `/api/tools/agent-bridge/tproxy`-reitillä.

## §1 Yleiskatsaus

### Mikä AgentBridge on?

Kun IDE-agentti (esim. GitHub Copilot, Cursor tai Claude Code) tekee API-kutsun, se muodostaa yhteyden suoraan ylävirran tekoälypalveluntarjoajaan (OpenAI, Anthropic jne.). AgentBridge sieppaa tämän yhteyden läpinäkyvästi TLS-tasolla — ilman muutoksia agentin määrityksiin — ja ohjaa pyynnön uudelleen OmniRouten kautta.

Tämän ansiosta voit:

- **Reitittää minkä tahansa agentin mille tahansa palveluntarjoajalle**: Keskusteleeko Copilot OpenAI:n kanssa? Ohjaa se Anthropic Claudelle, Geminille tai mille tahansa OmniRouten 352 palveluntarjoajasta.
- **Käyttää mallimäärityksiä**: `gemini-3-flash` → `claude-sonnet-4.7` läpinäkyvästi käsittelijätasolla.
- **Tarkkailla kaikkea agenttiliikennettä**: jokainen siepattu pyyntö julkaistaan [Traffic Inspectorissa](./TRAFFIC_INSPECTOR.md).
- **Hyödyntää OmniRouten vikasietoisuutta**: yhdistelmäreititys, katkaisijat, varareitit ja kustannusseuranta toimivat myös IDE-agenttien liikenteelle.

## §2 Arkkitehtuuri

### 2.1 Komponenttien yleiskatsaus

```
IDE-agentti (VS Code / Cursor / jne.)
    │  HTTPS (portti 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← DNS-uudelleenohjaus
    │
    ▼
src/mitm/server.cjs  (portti 443, CJS-aliprosessi)
    │  ratkaisee kohteen Host-otsakkeen SNI:n perusteella
    │  luo SNI-kohtaisen TLS-varmenteen, jonka AgentBridge CA on allekirjoittanut
    ├── Ohitusluettelo täsmää? → TCP-läpivienti (ei salauksen purkua)
    ├── Kohde täsmää? → fetch → OmniRoute-reititin (portti 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() pyynnön rungolle/otsakkeille
    │               ├── TrafficBuffer.push() — julkaisee Traffic Inspectoriin
    │               └── fetchRouter() → /v1/chat/completions
    └── Ei täsmäystä? → TCP-läpivienti (ei salauksen purkua)
```

### 2.2 MITM-palvelin (`src/mitm/server.cjs`)

MITM-ydinpalvelin toimii Node.jsin CJS-aliprosessina (jotta olemassa olevaa CJS-koodikantaa ei tarvitse kirjoittaa uudelleen). Se:

- Kuuntelee porttia 443 (vaatii käyttöoikeuden tai `authbind`/`setcap`-määrityksen)
- Vastaanottaa CONNECT-tunneleita käyttöjärjestelmältä (`/etc/hosts`-tiedoston DNS-uudelleenohjauksen kautta)
- Luo SNI-kohtaisia TLS-varmenteita, jotka AgentBridge CA (`DATA_DIR/mitm/ca.crt`) on allekirjoittanut
- Ratkaisee kohdeagentin Host-otsakkeen perusteella `targets/index.ts`-rekisterin kautta
- Välittää pyynnöt TypeScript-käsittelijäkerrokselle HTTP:n kautta osoitteeseen `http://127.0.0.1:20128`

`TARGET_HOSTS` ladataan tiedostosta `DATA_DIR/mitm/targets.json` (jonka `targets/index.ts` kirjoittaa käynnistyksen yhteydessä), mikä mahdollistaa dynaamiset päivitykset ilman CJS-palvelimen uudelleenkäynnistystä.

> **Juurivarmenteen CA-malli (#6684).** Edellä kuvattu SNI-kohtaisen, CA:n allekirjoittaman varmenteen
> malli on muutoksessa #6684 lisätty pysyvä juurivarmenteen CA-malli (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, joka käyttää uudelleen TPROXYa varten jo
> toimivaksi osoitettua CA-/lehtivarmennekryptografiaa tiedostosta `src/mitm/tproxy/dynamicCert.ts`) — se korvaa
> vanhemman yksittäisen staattisen itseallekirjoitetun lehtivarmenteen (`src/mitm/cert/generate.ts`, joka on edelleen
> rajattu vain antigravity-isäntiin), johon pelkkä levyllä oleva `server.crt`/`server.key`-pari
> viittaa. **Siirtymistoiminta**: uusi asennus (ei aiempaa
> `server.crt`-tiedostoa) saa juurivarmenteen CA-mallin automaattisesti; asennus, joka jo
> luottaa vanhaan staattiseen lehtivarmenteeseen, jatkaa sen käyttöä, kunnes ylläpitäjä asettaa
> `MITM_ROOT_CA_ENABLED=true` ja käynnistää sillan uudelleen (`src/mitm/cert/migration.ts`
> on puhdas päätösfunktio — luotettu MITM CA, joka voi allekirjoittaa lehtivarmenteen
> **mille tahansa** isännälle, on olennaisesti tehokkaampi kuin vanha kiinteän SAN-joukon lehtivarmenne, joten
> vaihtoa ei koskaan tehdä huomaamatta asennuksessa, jossa vanhaan varmenteeseen jo luotetaan). CA-varmenne asennetaan
> samaan luottamussäilön `omniroute-mitm.crt`-paikkaan, jota vanha lehtivarmenne käytti
> (`cert/install.ts::installCaCert`) — kahden luottamuksen puhdistusta ei tarvita.

### 2.3 Käsittelijän perusluokka (`src/mitm/handlers/base.ts`)

Kaikki agenttien käsittelijät laajentavat `MitmHandlerBase`-luokkaa:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // Suojatut apumetodit: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

Kukin käsittelijä kutsuu `hookBufferStart()`-metodia ennen välitystä ja `hookBufferUpdate()`-metodia valmistuttuaan. Nämä lisäävät `InterceptedRequest`-merkintöjä `globalTrafficBuffer`-puskuriin (katso [Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4).

### 2.4 Kohderekisteri (`src/mitm/targets/`)

Jokaisella agentilla on deklaratiivinen kohdetiedosto:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

Rekisteri (`targets/index.ts`) vie `ALL_TARGETS`-muuttujan ja tuottaa tiedoston `DATA_DIR/mitm/targets.json` käynnistyksen yhteydessä.

### 2.5 Läpivienti ja ohitusluettelo (`src/mitm/passthrough.ts`)

**Ohitusluettelo** (tarkistetaan ensin, ja sillä on etusija kohdetäsmäykseen nähden):

- Oletusmallit: pankkipalvelujen isännät, `.gov.`, OAuth-/SSO-palveluntarjoajat (Okta, Auth0) jne.
- Käyttäjän määrittämät mallit: tallennetaan tietokantatauluun `agent_bridge_bypass`
- Ohitetut isännät saavat läpinäkyvän TCP-tunnelin — TLS-salausta **ei koskaan pureta**

**Oletusarvoinen läpivienti** (ei kohdetäsmäystä eikä isäntä ole ohitusluettelossa):

- Saa myös TCP-tunnelin — yhteyksiä ei koskaan katkaista
- Estää AgentBridgeä häiritsemästä järjestelmän yleistä HTTPS-liikennettä

Reitityksen etusijajärjestys:

```
ohitusluettelo → kohdetäsmäys → läpivienti
```

### 2.6 Ylävirran CA-varmenne (`src/mitm/upstreamTrust.ts`)

Mukautettua CA:ta käyttävissä yritysverkkoympäristöissä:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

Kun muuttuja on asetettu, se määrittää `undici`-paketin yleisen välittäjän käyttämään ylimääräistä CA-varmennetta, minkä ansiosta AgentBridge voi tavoittaa ylävirran palveluntarjoajat yrityksen TLS-päätösvälityspalvelinten kautta.

### 2.7 Salaisuuksien peittäminen (`src/mitm/maskSecrets.ts`)

Riippumatonta puhtaalta pöydältä toteutettua tarkistinta sovelletaan pyyntöjen runkoihin ja tunnistetietoja sisältäviin otsakkeisiin
**ennen** niiden siirtymistä Traffic Inspector -puskuriin tai mihinkään lokiin. Se suorittaa yhden lineaarisen läpikäynnin:

- Etuliitteillä `sk-` / `ak-` / `pk-` alkavat tunnukset (OpenAI-/Anthropic-tyyliset)
- RFC 6750:n mukaiset `Authorization: Bearer <token>` -tunnistetiedot, joissa koko tunnuksen täsmäys on etusijalla
- Yleiset pitkät läpinäkymättömät tunnukset (≥40 merkkiä), mukaan lukien pisteelliset ja täytetyt muodot

`sanitizeHeaders()` muuntaa säilytetyt nimet pieniksi kirjaimiksi, yhdistää taulukkoarvot deterministisesti, poistaa
jaetun hyppykohtaisia otsakkeita ja kehystystä koskevan estoluettelon mukaiset otsakkeet (mukaan lukien välityspalvelimen todennuksen), peittää `cookie`- ja
`set-cookie`-otsakkeet kokonaan sekä delegoi tunnistetietoarvot tarkistimelle.

## §3 Määritys

### 3.1 MITM-palvelimen käynnistäminen/pysäyttäminen

Käytä AgentBridge-palvelinkorttia osoitteessa `/dashboard/tools/agent-bridge`:

| Toiminto               | Kuvaus                                                                            |
| ---------------------- | --------------------------------------------------------------------------------- |
| Käynnistä palvelin     | Käynnistää tiedoston `src/mitm/server.cjs` portissa 443                           |
| Pysäytä palvelin       | Sammuttaa aliprosessin hallitusti                                                 |
| Käynnistä uudelleen    | Pysäyttää ja käynnistää (ottaa kohdemuutokset käyttöön)                           |
| Luota varmenteeseen    | Asentaa tiedoston `DATA_DIR/mitm/ca.crt` käyttöjärjestelmän luottamussäilöön      |
| Lataa varmenne         | Lataa tiedoston `ca.crt` manuaalista asennusta varten                             |
| Luo varmenne uudelleen | Luo uuden CA-avainparin (kaikki nykyiset agenttikohtaiset varmenteet mitätöidään) |

### 3.2 Varmenteeseen luottaminen

Käyttöjärjestelmän on luotettava AgentBridge-CA-varmenteeseen, ennen kuin IDEt hyväksyvät MITM-yhteyden.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Avainnippu):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

Voit myös käyttää hallintapaneelin "Luota varmenteeseen" -painiketta (suorittaa käyttöjärjestelmällesi sopivan komennon ja näyttää tarvittaessa sudo-kehotteen).

#### Electron-pohjaiset IDEt ohittavat käyttöjärjestelmän luottamussäilön (`NODE_EXTRA_CA_CERTS`)

Jotkin IDEt — erityisesti **Antigravity IDE** sekä muut Electron- tai VS Code -pohjaiset sovellukset — sisältävät oman Node.js-ajoympäristönsä, joka **ei käytä käyttöjärjestelmän luottamussäilöä** lähteville `fetch`-/HTTPS-yhteyksille. CA:han luottaminen käyttöjärjestelmä-/NSS-tasolla riittää IDE:n natiiville **taustajärjestelmälle** (esimerkiksi Go-kielipalvelimelle, joka käyttää käyttöjärjestelmän CA-varmennepakettia), mutta **Electron-käyttöliittymän** TLS-yhteys epäonnistuu silti — tämä näkyy sovelluksessa _uloskirjautuneena_ tilana tai _"yhteysvirheenä"_, vaikka MITM-loki osoittaisi taustajärjestelmän käynnistyskutsujen palauttavan tilakoodin `200`. Tarvitaan kaksi vaihetta, ja molemmat ovat tärkeitä:

1. Osoita CA-varmenne ajoympäristölle eksplisiittisesti:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **Käynnistä IDE kyseisestä komentotulkista.** Käynnistäminen työpöydän kuvakkeesta / Dockista / Käynnistä-valikosta
   **ei** peri komentotulkin vientimuuttujia, ja `~/.config/environment.d/*.conf` tulee voimaan vasta
   uuden graafisen kirjautumisen jälkeen. Sulje IDE ensin kokonaan — Electronin yhden ilmentymän lukitus tarkoittaa, että toinen
   käynnistys vain kohdistaa olemassa olevaan prosessiin ja uusi ympäristö ohitetaan.

Edellä kuvattu käyttöjärjestelmätason luottamus- ja NSS-vaihe on edelleen tarpeen (joidenkin todennusprosessien käyttämä Chromium-verkkopino lukee käyttäjäkohtaisen NSS-säilön, ja sillä on omat staattiset varmenneneulonnat kohteelle `*.googleapis.com`, jotka paikallisesti luotettu CA ohittaa). `NODE_EXTRA_CA_CERTS` kattaa lisäksi Node-ympäristön `fetch`-polun.

### 3.3 DNS-reititys

Jokaisen siepattavan agentin API-isäntänimien on ratkettava osoitteeseen `127.0.0.1`. AgentBridge hallitsee `/etc/hosts`-merkintöjä automaattisesti, kun otat agentin DNS:n käyttöön tai poistat sen käytöstä ohjatussa määrityksessä.

Esimerkkejä GitHub Copilotin `/etc/hosts`-merkinnöistä:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 Mallimääritykset

Määritä lähde → kohde -määritykset kunkin agenttikortin mallimääritystaulukossa:

| Lähdemalli (agentin natiivi) | Kohdemalli (OmniRoute) |
| ---------------------------- | ---------------------- |
| `gpt-4o`                     | `claude-sonnet-4.7`    |
| `*` (jokerimerkki)           | `claude-haiku-4.7`     |

Jokerimerkki `*` määrittää minkä tahansa tunnistamattoman mallin annetulle kohteelle. Määritykset tallennetaan `agent_bridge_mappings`-tauluun.

> **Vinkki — selvitä agentin todelliset mallitunnukset.** IDE saattaa lähettää mallinimiä, jotka poikkeavat
> sen käyttöliittymän nimikkeistä ja muuttuvat pääversioiden välillä. Esimerkiksi **Antigravity 2** lähettää
> verkon kautta arvot `gemini-3.1-pro-low`, `gemini-pro-agent` ja `gemini-3.1-flash-lite` — ei
> vanhemmissa ohjeissa näkyvää arvoa `gemini-2.5-pro`. Lähetä yksi keskustelu ilman vastaavaa määritystä: MITM
> kirjaa lokiin tarkan saapuvan `model:`-arvon ja välittää pyynnön sellaisenaan. Määritä kyseinen kirjaimellinen arvo, jolloin
> seuraava pyyntö siepataan ja reititetään kohteeseesi.

### 3.5 Riski-ilmoitus

AgentBridge sieppaa tunnistetietoja (OAuth-tunnuksia ja API-avaimia), joita IDE käyttää todentautuakseen ylävirran palveluntarjoajille. Ne **peitetään ennen lokiin kirjaamista** (katso §2.7), mutta näkyvät OmniRouten MITM-kerrokselle. Kunkin agentin ensimmäisen aktivoinnin yhteydessä näytetään suljettava riski-ilmoitusikkuna.

### 3.6 Ylläpito ja diagnostiikka

Hallintapaneelissa on **Ylläpito ja diagnostiikka** -kortti (`AgentBridgeMaintenanceCard`, hakemistossa `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`), joka tuo näkyviin toiminnalliset MITM-reitit, joille ei aiemmin ollut käyttöliittymää. Sen alaotsikko on: _"Testaa sieppausputki, kumoa jäljelle jäänyt järjestelmätila ja siirrä määrityksesi koneesta toiseen."_ Kortin asiakaspuolen apufunktiot sijaitsevat tiedostossa `src/lib/inspector/agentBridgeMaintenanceApi.ts`.

| Painike             | Reitti                                 | Mitä se tekee                                                                                                                                                                                                                                  |
| ------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Diagnosoi**       | `GET /api/tools/agent-bridge/diagnose` | Suorittaa kaappaustoimintoketjun itsetestin ja näyttää tarkistuskohtaisen raportin (✓/✗ + korjausehdotus).                                                                                                                                     |
| **Korjaa**          | `POST /api/tools/agent-bridge/repair`  | Kumoaa kaatumisen tai SIGKILL-signaalin jäljiltä jääneen irrallisen MITM-järjestelmätilan (DNS-väärennösmerkinnät, juurivarmentaja, järjestelmän välityspalvelin). Idempotentti — ilmoittaa "Ei korjattavaa", kun tila on puhdas.              |
| **Poista CA**       | `DELETE /api/tools/agent-bridge/cert`  | Poistaa MITM-juurivarmentajan luottamuksen ja poistaa sen käyttöjärjestelmän luottamussäilöstä (eksplisiittinen, idempotentti). Näytetään vain, kun varmentajaan luotetaan parhaillaan; vaatii rivinsisäisen "Poistetaanko CA?" -vahvistuksen. |
| **Vie määritykset** | `GET /api/tools/agent-bridge/config`   | Lataa siirrettävän JSON-määrityksen (katso §3.7).                                                                                                                                                                                              |
| **Tuo määritykset** | `POST /api/tools/agent-bridge/config`  | Lähettää aiemmin viedyn JSON-määrityksen (katso §3.7).                                                                                                                                                                                         |

**Diagnostiikkatarkistukset** (`summarizeDiagnostics()` tiedostossa `src/mitm/inspector/diagnostics.ts`). Reitti suorittaa kutakin tarkistusta varten sivuvaikutteisen kokeen ja syöttää totuusarvot puhtaalle yhteenvetofunktiolle; palautuksena saadaan yksi `healthy`-arvio sekä tarkistuskohtainen korjausehdotus:

| Tarkistuksen nimi  | Mitä se varmistaa                                            | Vihje epäonnistumisen yhteydessä                                                                                                                                                  |
| ------------------ | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | MITM-palvelinprosessi on aktiivinen                          | "MITM-palvelin ei ole käynnissä. Käynnistä se AgentBridge-välilehdeltä."                                                                                                          |
| `server-reachable` | MITM-palvelin hyväksyy yhteyksiä portissaan (TCP-koe)        | "MITM-palvelin ei hyväksy yhteyksiä portissaan. Tarkista, että portti on vapaa ja että sinulla on oikeudet sitoa se."                                                             |
| `cert-exists`      | MITM-varmenne on luotu levylle                               | "MITM-varmennetta ei ole vielä luotu. Luo se AgentBridge-välilehdeltä."                                                                                                           |
| `cert-trusted`     | MITM-juurivarmentaja on käyttöjärjestelmän luottamussäilössä | "Käyttöjärjestelmän luottamussäilö ei luota MITM-juurivarmentajaan, joten TLS-sieppaus epäonnistuu. Luota varmenteeseen AgentBridge-välilehdellä."                                |
| `dns-configured`   | Kohdeisäntänimet väärennetään tiedostossa `/etc/hosts`       | "Kohdeisäntänimiä ei ole väärennetty tiedostossa /etc/hosts, joten liikenne ei koskaan saavuta välityspalvelinta. Ota DNS käyttöön agenteille, joiden liikenteen haluat kaapata." |

**Irrallisen tilan ilmoituspalkki:** kun sivu havaitsee kaatumisen jäljiltä jääneen tilan (DNS-väärennös / CA / järjestelmän välityspalvelin), kortissa näytetään kullanruskea ilmoituspalkki — _"Edellinen istunto jätti jälkeensä järjestelmätilaa (DNS-väärennös, CA tai järjestelmän välityspalvelin). Siivoa se suorittamalla Korjaa."_ — ja **Korjaa**-painike korostetaan. `Repair` on sovelluskerroksen vastine ProxyBridgen `--cleanup`-valitsimelle (se delegoi toiminnon tiedoston `src/mitm/manager.ts` funktiolle `repairMitm()`).

> MITM-juurivarmentaja pidetään asennettuna pysäytys- ja käynnistyskertojen välillä toistuvien sudo-
> kehotteiden välttämiseksi (sama toimintatapa kuin mitmproxyssa/Charlesissa), joten sen poistaminen on eksplisiittinen
> **Poista CA** -toiminto eikä jotain, joka tapahtuisi automaattisesti pysäytyksen yhteydessä.

### 3.7 Siirrettävien määritysten tuonti/vienti

AgentBridge voi sarjallistaa **operaattorin säädettävissä olevan** tilan versioiduksi JSON-objektiksi, jotta asetelma voidaan toisintaa eri koneille. Sarjallistaja on `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`), ja `AgentBridgeConfigSchema` validoi sen.

Vienti sisältää täsmälleen kolme osaa (sisäisiä oletusarvoja **EI** tarkoituksellisesti viedä, joten tuonti ei koskaan monista niitä tai aiheuta ristiriitoja niiden kanssa):

| Kenttä           | Lähde                                                             | Huomautukset                                                                     |
| ---------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `bypassPatterns` | käyttäjän määrittämät ohitusmallit (`agent_bridge_bypass`)        | pankkien, viranomaisten ja Oktan oletusmallit jätetään pois                      |
| `customHosts`    | Traffic Inspectorin mukautetut isännät (`inspector_custom_hosts`) | kukin: `{ host, kind: "llm"\|"app"\|"custom", label? }`                          |
| `agentMappings`  | agenttikohtaiset mallimääritykset (`agent_bridge_mappings`)       | `{ [agentId]: [{ source, target }] }` jokaiselle agentille, jolla on määrityksiä |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**Tuonnin toiminta** (`POST /api/tools/agent-bridge/config`): ohitusmallit ja agenttikohtaiset määritykset **korvataan kokonaan**; mukautetut isännät lisätään **idempotentisti** (`INSERT OR IGNORE`). Vastaus ilmoittaa, kuinka monta kutakin otettiin käyttöön:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

Mitä määrityksiin **EI** sisälly: palvelimen käynnissäolotila, varmennepolut, agenttikohtainen DNS-tila, ylävirran CA-polku ja TPROXY-asetukset — ne ovat isäntä-/ajonaikaista tilaa, eivät siirrettäviä asetuksia.

### Ohitusluettelo arkaluonteisille isännille

Ohitusluettelo varmistaa, että rahoituslaitosten, OAuth-/SSO-palveluntarjoajien ja muiden arkaluonteisten isäntien liikennettä **ei koskaan pureta**. Niiden TLS-liikenne kulkee läpinäkyvän TCP-tunnelin kautta — OmniRoute ei koskaan näe salaamatonta sisältöä.

Oletusarvoiset ohitusmallit sisältävät:

- `*.bank.*`, `*.gov.*` (rahoitussektori/julkishallinto)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/identiteetti)
- `*.apple.com`, `*.icloud.com` (Applen järjestelmäpalvelut)

Käyttäjän lisäämät ohitusmallit tallennetaan `agent_bridge_bypass`-tauluun, ja ne ovat etusijalla kaikkeen muuhun nähden.

### Salaisuuksien peittäminen

Tiedoston `src/mitm/maskSecrets.ts` funktiota `maskSecrets()` käytetään:

- Jokaisen pyyntörungon kohdalla ennen `TrafficBuffer.push()`-kutsua
- Jokaisen otsakkeen kohdalla ennen lokiin kirjaamista tai lähettämistä vastaanottajille

Mallit: etuliitteillä `sk-`/`ak-`/`pk-` varustetut tunnukset, `Bearer`-tunnukset ja yleiset vähintään 40 merkkiä pitkät tunnukset.

### Ylävirran CA-varmenne

Kun `AGENTBRIDGE_UPSTREAM_CA_CERT` on asetettu, tiedosto luetaan käynnistyksen yhteydessä. Jos polku on olemassa, mutta tiedostoa ei voida lukea, AgentBridge kirjaa selkeän virheen lokiin ja kieltäytyy käynnistymästä (tämä estää huomaamattomat TLS-virheet yritysympäristöissä).

### Tunnetut rajoitukset

- **Portti 443 vaatii erityisoikeuksia**: Linuxissa AgentBridge tarvitsee Node-binäärille asetuksen `setcap 'cap_net_bind_service=+ep'`, tai se on suoritettava `authbind`-ohjelmalla. Ohjattu määritys näyttää käyttöjärjestelmäkohtaiset ohjeet.
- **IDE on käynnistettävä uudelleen**: DNS-uudelleenohjauksen jälkeen IDE on käynnistettävä uudelleen, jotta uusi isäntänimen selvitys tulee voimaan.
- **Kiinteästi määritetyt OAuth-tunnukset**: Jotkin agentit (Kiro, Antigravity) tallentavat OAuth-päivitystunnukset paikallisesti. Ne ovat AgentBridgelle läpinäkyviä — se näkee kunkin pyynnön Bearer-tunnuksen, joka peitetään ennen lokiin kirjaamista.
- **Electron-käyttöliittymät tarvitsevat `NODE_EXTRA_CA_CERTS`-muuttujan**: IDE:t, joiden käyttöliittymä toimii mukana toimitettavassa Node-/Electron-ajoympäristössä, ohittavat käyttöjärjestelmän/NSS:n luottamussäilön, ja ne on käynnistettävä komentotulkista siten, että `NODE_EXTRA_CA_CERTS` on asetettu (katso §3.2). Puuttuvan asetuksen oire: IDE:n taustajärjestelmä todentautuu (MITM näyttää `200`-vastauksia), mutta käyttöliittymä pysyy uloskirjautuneena.
- **Saman IDE:n useat asennukset ovat toisistaan riippumattomia**: järjestelmäasennus (esim. `/usr/share/antigravity/antigravity`) ja käyttäjäkohtainen paikallinen ”Full”-asennus (esim. `~/AntigravityIDE_Full/antigravity-ide`) ovat erillisiä prosesseja, joilla on omat ajoympäristönsä — jokainen niistä on käynnistettävä uudelleen CA-varmenne lisättynä. Selvitä ennen uudelleenkäynnistystä binääripolun perusteella, mikä niistä on käynnissä.
- **Identiteetti määräytyy agentin järjestelmäkehotteen, ei reititetyn mallin perusteella**: kun agentin malli määritetään käyttämään toista palveluntarjoajaa, vastaus väittää silti edustavansa agentin alkuperäistä identiteettiä (esim. Antigravity vastaa ”Gemini antaa minulle tehon”), koska IDE lisää tämän järjestelmäkehotteeseen. Varmista todellinen taustajärjestelmä tauluista `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`) äläkä kysymällä mallilta, mikä se on.

## §6 Vianmääritys

### Portin 443 ristiriita

Jos jokin toinen prosessi kuuntelee jo porttia 443 (verkkopalvelin, VPN jne.):

```bash
lsof -i :443          # etsi prosessi
sudo fuser -k 443/tcp  # pakota lopetus (käytä varoen)
```

Vaihtoehtoisesti voit määrittää AgentBridgen asetuksissa ei-etuoikeutetun portin ja ottaa käyttöön `iptables`- / `pf`-uudelleenohjaussäännöt.

### Varmenne ei ole luotettu

Jos IDE näyttää TLS-virheitä AgentBridgen käynnistämisen jälkeen:

1. Varmista, että varmenne on asennettu: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) tai `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. Jotkin sovellukset ylläpitävät omaa luottamusvarastoaan (Firefox, Chrome Linuxissa). Suorita "Luota varmenteeseen" uudelleen ja tarkista NSS-/Firefox-kohtainen varmennevarasto.
3. Käynnistä IDE uudelleen varmenteeseen luottamisen jälkeen — käynnissä olevat TLS-istunnot käyttävät vanhaa luottamustilaa.

### IDE on kirjautunut ulos / "yhteysvirhe" luotetusta CA:sta huolimatta

Oire: DNS:n uudelleenohjauksen ja CA:han luottamisen jälkeen Electron-pohjainen IDE (esim. Antigravity)
avautuu **uloskirjautuneena** tai näyttää todennus-/yhteysvirheen, vaikka MITM-loki osoittaa
käynnistyskutsujen (`loadCodeAssist`, `fetchAvailableModels`, …) palauttavan tilakoodin `200`.

Syy: IDE:n **mukana toimitettu Node/Electron-ajoaikaympäristö ohittaa käyttöjärjestelmän luottamusvaraston**. Natiivi
taustajärjestelmä (Go-kielipalvelin) luottaa käyttöjärjestelmän CA:han ja todentuu, mutta Electron-käyttöliittymä
ei luota — joten käyttöliittymä tulkitsee olevansa offline-tilassa.

Korjaus (molemmat vaiheet): vie `NODE_EXTRA_CA_CERTS=<ca.crt>` **ja käynnistä IDE uudelleen kyseisestä
komentotulkista**, älä työpöydän kuvakkeesta. Sulje IDE ensin kokonaan — Electronin yhden instanssin lukitus tarkoittaa,
että toinen käynnistys vain siirtää kohdistuksen olemassa olevaan prosessiin ja uusi ympäristö ohitetaan. Katso §3.2.
Tämä vastaa avointa upstream-raporttia, jossa itsenäinen agentti toimii MITM:n kautta, mutta IDE-versio
epäonnistuu samoilla asetuksilla.

### DNS-muutokset eivät ole levinneet

Tarkista, että `/etc/hosts` on päivitetty:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

Tyhjennä DNS-välimuisti:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE:tä ei havaittu

Automaattinen tunnistus käyttää yleisiä asennuspolkuja. Jos tunnistus epäonnistuu, vaikka IDE on asennettu:

- Tarkista, sijaitseeko IDE:n binaaritiedosto poikkeavassa sijainnissa
- Ohjattu asennustoiminto toimii silti — tunnistuksen epäonnistuminen tarkoittaa vain sitä, ettei tunniste näytä asennuspolkua

### Käsittelijän virheet (upstream-haku epäonnistuu)

Jos AgentBridge sieppaa pyynnöt, mutta kaikki pyynnöt epäonnistuvat:

1. Varmista, että vähintään yksi palveluntarjoaja on yhdistetty osoitteessa `/dashboard/providers`
2. Tarkista OmniRoute-palvelimen lokit: `APP_LOG_LEVEL=debug` tiedostossa `.env`
3. Varmista, että `OMNIROUTE_BASE_URL` osoittaa oikeaan reitittimen päätepisteeseen (oletus: `http://127.0.0.1:20128`)

## §8 Kehityssuunnitelma

### Trae-selvitys

Trae on suhteellisen uusi tekoälyavusteinen ohjelmointiassistentti. Ennen käsittelijän toteuttamista:

1. Tunnista binääri/laajennus VS Code- tai JetBrains-markkinapaikoista tai erillissovelluksena
2. Tallenna liikenne mitmproxylla API-isäntien ja päätepisteiden rakenteiden selvittämiseksi
3. Selvitä todennusmekanismi
4. Arvioi käyttöehtojen ja API:n löydettävyyden perusteella, jatketaanko toteutusta vai ei

Kunnes selvitys valmistuu, hallintapaneelin Trae-kortissa näkyy "Selvitetään"-tunniste ja "Raportoi toteuttamiskelpoisuus" -linkki. Käsittelijän runko tiedostossa `src/mitm/handlers/trae.ts` antaa rakenteisen `Ei vielä toteutettu` -virheen.

### Työjonossa olevat agentit (MITM vaaditaan — ei mukautetun perus-URL-osoitteen tukea)

Seuraavat työkalut eivät nykyisissä versioissaan tue mukautettuja perus-URL-osoitteita, joten MITM on ainoa tapa siepata liikennettä. Toteuttamiskelpoisuuden arviointi on kesken:
