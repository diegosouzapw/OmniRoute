> **Lyhyesti**: `open-sse/` on keskeinen suoratoistomoottori, joka käsittelee kaikki OmniRouten LLM-pyynnöt. Se sisältää noin 1 400 tiedostoa, joissa toteutetaan pyyntöputki, suorittimet, palvelut, MCP-palvelin ja käännöskerros. Tässä oppaassa selitetään, miten osat toimivat yhdessä.

**Lähde:** `open-sse/` (työtilapaketti, noin 1 440 muuta kuin testaukseen tarkoitettua `.ts`-tiedostoa)

---

## Miksi erillinen työtilapaketti?

`open-sse/` on **itsenäinen työtila** OmniRoute-monorepositoriossa useista syistä:

1. **Uudelleenkäytettävyys** — `open-sse` julkaistaan npm:ssä nimellä `@omniroute/open-sse`, joten muut projektit voivat käyttää sitä itsenäisesti
2. **Selkeät rajat** — suoratoistomoottori on irrotettu OmniRoute-kohtaisesta käyttöliittymä- ja tietokantakerroksesta
3. **Suorituskyky** — moottorilla ei ole Next.js-riippuvuuksia, mikä mahdollistaa nopeammat kylmäkäynnistykset komentorivi- ja palvelimettomissa ympäristöissä
4. **Versiointi** — `open-sse` voidaan julkaista omassa tahdissaan

```json
// package.json
"workspaces": ["open-sse"]
```

## Pyyntöputki

Jokainen LLM-pyyntö kulkee **viisivaiheisen putken** läpi:

```
                              ┌──────────────┐
   HTTP-pyyntö                 │  1. REITITÄ  │   yhdistelmän ratkaisu, mallin valinta
   (Next.js-reitti)            └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. KÄÄNNÄ   │   muodon muuntaminen (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. SUORITA  │   palveluntarjoajan suoritin, HTTP, uudelleenyritys, katkaisija
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. SUORATOISTA│ SSE-muunnos, vastapaine
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. KIRJAA   │   käytön seuranta, kutsuloki, virheiden luokittelu
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP-vastaus (SSE tai JSON)
```

### Vaihe 1: Reititys (services/combo.ts)

**Aloituspiste**: `handleComboChat()` tiedostossa `services/combo.ts`

Ratkaisee pyynnön konkreettiseksi `(provider, model, account, credentials)`-monikoksi:

- Hae yhdistelmä tunnuksella (tai muodosta virtuaalinen yhdistelmä `auto/*`-malleille)
- Käytä reititysstrategiaa (prioriteetti, painotettu, vuorottelu jne.)
- Suodata pois epäkuntoiset palveluntarjoajat (katkaisija)
- Valitse seuraava käyttökelpoinen kohde

`auto/*`-mallien tapauksessa tämä vaihe myös:

- Suorittaa **16 tekijän pisteytysalgoritmin** (`services/autoCombo/`)
- Valitsee `provider+model`-parin toimintakunnon, kustannusten, viiveen ja muiden tekijöiden perusteella

### Vaihe 2: Käännös (translator/)

Jos lähdemuoto (esimerkiksi OpenAI) poikkeaa kohdemuodosta (esimerkiksi Claude), pyyntö **käännetään**:

- Järjestelmäkehote → järjestelmäviesti
- Työkalumääritykset → palveluntarjoajakohtainen työkalumuoto
- Päättely-/ajatteluparametrit → palveluntarjoajakohtaiset vastineet
- Viestiroolien normalisointi (`developer` → `system` muille kuin OpenAI-palveluntarjoajille)

`translator/index.ts` tarjoaa seuraavat:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Vaihe 3: Suoritus (executors/)

**Aloituspiste**: `getExecutor(providerId).execute(request, options)`

Kaikki palveluntarjoajat käyttävät `DefaultExecutor`-suoritinta (`executors/default.ts`) `getExecutor()`-tehtaan vararatkaisun kautta. Suoritin:

- Muodostaa ylävirran URL-osoitteen (`buildUrl()`)
- Lisää palveluntarjoajakohtaiset otsakkeet (`buildHeaders()`)
- Muuntaa pyynnön rungon (`transformRequest()`)
- Lähettää HTTP-pyynnön käyttäen uudelleenyrityksiä ja eksponentiaalista viivettä
- Käsittelee tarvittaessa todennuksen päivittämisen (OAuth-palveluntarjoajat)

Kaikki suorittimet laajentavat `BaseExecutor`-luokkaa (`executors/base.ts`, 1170 koodiriviä), joka tarjoaa:

- Yhteisen uudelleenyrityslogiikan
- Välityspalvelinintegraation
- Katkaisijaintegraation
- Käytön kirjaamiskoukut

### Vaihe 4: Suoratoisto (utils/stream.ts)

Suoratoistettavia vastauksia varten suoritin palauttaa **ReadableStream**-virran. Käsittelijä:

- Ohjaa virran SSE-muunnoksen läpi (`createSSETransformStreamWithLogger`)
- Käyttää sykeviestejä kuolleiden yhteyksien havaitsemiseen
- Käsittelee asiakkaan yhteyden katkeamisen hallitusti (`pipeWithDisconnect`)
- Muuntaa SSE:n JSON-muotoon asiakkaille, jotka eivät käytä suoratoistoa

Muiden kuin suoratoistettavien vastausten tapauksessa suoritin palauttaa jäsennetyn JSON-objektin, joka välitetään muuttamattomana.

### Vaihe 5: Kirjaaminen (services/usage.ts)

Vastauksen jälkeen (onnistui tai epäonnistui) käyttötiedot tallennetaan:

- Vastauksesta saadut `prompt_tokens`-, `completion_tokens`- ja `cached_tokens`-arvot
- Hinnoittelutiedoista laskettu `cost_usd`
- `latency_ms`, `status` ja epäonnistumisen yhteydessä `error_class`
- Tallennetaan `usage_history`-tauluun

Kutsulokien artefaktit (jos käytössä) kirjoitetaan hakemistoon `${DATA_DIR}/call_logs/`.

## Keskeisten tiedostojen syväsukellus

### chatCore.ts (5977 riviä)

**Pääpyyntökäsittelijä**. Koostaan huolimatta siinä on selkeä rakenne:

```ts
// chatCore.ts:n pseudorakenne
export async function handleChat(request: NextRequest) {
  // 1. Todennus + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Pyynnön rungon validointi
  const body = await parseRequestBody(request);

  // 3. Muodon tunnistus + käännös
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo-reititys
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Jatka seuraavaan kohteeseen
    }
  }

  // 5. Hätävara (fallback)
  return await emergencyFallback(body);
}
```

Vaikka kyseessä on yksi valtava funktio, se on järjestetty **kommentoituihin osioihin**, jotka vastaavat 5-vaiheista käsittelyputkea.

// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });

### base.ts (1170 riviä)

**Abstrakti executor**, josta kaikki executor-luokat periytyvät (joko suoraan tai `DefaultExecutor`-luokan ja muiden aliluokkien kautta). Se sisältää:

- `buildUrl()` — URL:n oletusmuodostus (aliluokat korvaavat sen tarvittaessa mukautetulla toteutuksella)
- `buildHeaders()` — oletusotsakkeet (todennus, content-type)
- `transformRequest()` — oletuksena suora läpivienti
- `execute()` — tärkein HTTP-silmukka, jossa uudelleenyritys/backoff/breaker

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Käsittelee kaikki OpenAI/Anthropic-yhteensopivat palveluntarjoajat
  // Palveluntarjoajat rekisteröivät konfiguraationsa (URL, todennus, otsakkeet), mutta jakavat saman executor-logiikan
}
```

Palveluntarjoajakohtainen käyttäytyminen (todennusotsakkeet, perus-URL, versio-otsakkeet) määritetään palveluntarjoajarekisterin kautta, ei erillisillä executor-luokilla.

````

## Executorit (150 moduulia)

Enimmäkseen yksi tiedosto palveluntarjoajaa kohden. Executor-luokat perivät kaikki `BaseExecutor`-luokan ja korvaavat vain poikkeavat osat; muut moduulit ovat palveluntarjoajakohtaisia apumoduuleja (työkaluskeemat, fetch/TTS-adapterit, erikoisuuksien käsittelijät).

### Yleiset mallit

Palveluntarjoajat ratkaistaan funktiolla `getExecutor(providerId)`, joka palauttaa määritetyn executorin. OpenAI/Anthropic-yhteensopivat palveluntarjoajat käyttävät `DefaultExecutor`-luokkaa (`executors/default.ts`). Palveluntarjoajakohtainen toiminta (perus-URL-osoite, todennusotsakkeet, API-versio) määritetään hakemistossa `open-sse/config/providers/`, kun taas pyyntörunkojen muunnokset käsitellään hakemistossa `open-sse/translator/`.

**Mukautettu URL-osoite** asetetaan palveluntarjoajan määrityksessä:

```ts
// Palveluntarjoajan määritys hakemistossa open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Mukautettu todennus** hoidetaan palveluntarjoajarekisterin todennusmäärityksen kautta (API-avain, OAuth, otsakeprofiilit).

**Mukautetun pyyntörungon** muunnokset (esim. Anthropic erottaa `system`-kentän `messages`-kentästä) rekisteröidään palveluntarjoajakohtaisesti hakemistossa `open-sse/translator/`.

````

### Executor-tehdas

`executors/index.ts` eksportoi funktion `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Ratkaisu kulkee `ExecutorRegistry`-rekisterin kautta (`executors/registry.ts`): jokainen erikoistunut executor määritellään `executors/index.ts`-tiedoston sisäänrakennetussa taulukossa ja rekisteröidään funktiolla `registerExecutor(alias, instance)` moduulin latautuessa; `getExecutor()` tutkii rekisterin ja käyttää varana memoisoitua `DefaultExecutor`-instanssia kaikille palveluntarjoajille, joilla ei ole erikoistunutta merkintää. Koko alias → executor -kuvauksen määrittelee golden-testi `tests/unit/executor-map-golden.test.ts`.

## Kääntäjät

Muuntaa **3 muodon** välillä: OpenAI, Anthropic, Gemini sekä uusi Responses API.

### Milloin muunnos tehdään

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Yleisiä muunnoksia:

- `OpenAI → Anthropic`: erillinen `system`-kenttä, `x-api-key`-otsake
- `OpenAI → Gemini`: `contents` kentän `messages` sijaan, `systemInstruction`
- `OpenAI → Responses API`: `input`-taulukko, `previous_response_id`-tila

### Käsitellyt reunatapaukset

- `developer`-rooli → `system` muille kuin OpenAI:lle
- `system`-rooli → yhdistetään ensimmäiseen käyttäjäviestiin GLM:ää/ERNIEä varten
- `json_schema` → Geminin `responseMimeType` + `responseSchema`
- `tools` → palveluntarjoajakohtainen työkalumuoto
- Päättelyparametrit (o1, Claude) → palveluntarjoajakohtaiset vastineet

## MCP-palvelin

`open-sse/mcp-server/` toteuttaa **Model Context Protocol** -palvelimen:

- **110 työkalua** (palveluntarjoajien hallinta, yhdistelmät, muisti, välimuisti, pakkaus, välityspalvelin, taidot, pelillistäminen, liitännäiset, Notion, Obsidian, paikallinen aineisto)
- **3 siirtotapaa**: stdio, SSE, Streamable HTTP
- **33 käyttöoikeusaluetta** tarkkarajaiseen valtuutukseen

### Työkalujen rekisteröinti

Työkalut rekisteröidään erillisinä tiedostoina hakemistossa `open-sse/mcp-server/tools/`. Kukin niistä vie nimen, skeeman, käsittelijän ja käyttöoikeusalueen:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Siirtotavat

```ts
// stdio (CLI-käyttö)
startMcpStdio(server);

// SSE (HTTP-pohjainen suoratoisto)
startMcpSse(server, port);

// Streamable HTTP (nykyaikainen MCP)
startMcpStreamable(server, port);
```

### Valtuutus

Jokainen työkalukutsu käy läpi käyttöoikeusalueiden tarkistukset (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Muuntimet

`open-sse/transformer/` muuntaa **Chat Completions**- ja **Responses API** -muotojen välillä.

### Miksi erillinen muunnin?

Responses API on OpenAI:n uusi muoto, joka tukee **tilallisia keskusteluja** (`previous_response_id`). Kun asiakas lähettää Responses-pyynnön, OmniRoute:

1. Muuntaa Responses-muodon sisäisesti Chat Completions -muotoon
2. Lähettää pyynnön palveluntarjoajalle (mille tahansa Chat Completions -muotoa tukevalle palveluntarjoajalle)
3. Muuntaa vastauksen takaisin Responses-muotoon
4. Suoratoistaa muunnetun vastauksen asiakkaalle

Muunnin (`transformer/responsesTransformer.ts`) tarjoaa seuraavan:

```ts
createResponsesApiTransformStream(): TransformStream
```

Se käsittelee seuraavat:

- `response.output_item.added`-tapahtumat
- `response.output_text.delta`-tapahtumat
- `response.completed`-tapahtuma
- Työkalukutsujen vastaavuus (`function_call` ↔ `tool_calls`)

## Konfiguraatio

`open-sse/config/` sisältää konfiguraatiokerroksen:

| Tiedosto                       | Tarkoitus                                                |
| ------------------------------ | -------------------------------------------------------- |
| `providerRegistry.ts`          | Chat-mallien rekisteri 375 palveluntarjoajan luettelolle |
| `providerModels.ts`            | Mallialiasukset, formaattikartoitus                      |
| `constants.ts`                 | Aikakatkaisut, rajat, tilakoodit                         |
| `defaultThinkingSignature.ts`  | Clauden oletusarvoinen thinking-allekirjoitus            |
| `modelStrip.ts` (servicesissä) | Kenttien poisto palveluntarjoajakohtaisesti              |

### Palveluntarjoajarekisterin skeema

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Zod-validointi moduulin latauksen yhteydessä varmistaa, että kaikki palveluntarjoajien konfiguraatiot ovat kelvollisia.

## Suorituskykyrajoitteet

Reititysmoottorilla on tiukat suorituskykyrajat:

| Toiminto                                                       | Tavoite | Mittaus                          |
| -------------------------------------------------------------- | ------- | -------------------------------- |
| Yhdistelmän ratkaisu                                           | <10ms   | 50 kohteelle                     |
| Nopeusrajoituksen tarkistus                                    | <1ms    | Muistissa oleva token bucket     |
| Malliperheen varajärjestely                                    | <5ms    | Välimuistissa olevat määritykset |
| Reitityspyynnön välitys                                        | <2ms    | Kriittinen suorituspolku         |
| **Ei estävää I/O:ta reitityksen kriittisellä suorituspolulla** | —       | Kaikki asynkronista              |

## Vältettävät toimintamallit

❌ **Synkroniset tietokantakutsut tiedostossa `combo.ts`** — esilaske ja tallenna välimuistiin
❌ **Uudelleenyrityslogiikka käsittelijöissä** — käytä vikasietoisuuspalvelun `retry()`-toimintoa
❌ **Suora pääsy palveluntarjoajan määrityksiin** — käytä `providerRegistry`-gettereitä
❌ **Kovakoodatut varaketjut** — määritä ne tiedostossa `modelFamilyFallback.ts`
❌ **Tilan muutokset samanaikaisten pyyntöjen välillä** — käytä vain pyyntökohtaista kontekstia

## Uuden komponentin lisääminen

### Uuden palvelun lisääminen

1. Luo `open-sse/services/[serviceName].ts`, jolla on tarkasti rajattu vastuu
2. Vie pääkäsittelijäfunktio ja mahdolliset vakiot
3. Lisää yksikkötestit tiedostoon `tests/unit/services/[serviceName].test.mjs`
4. Integroi palvelu pyyntöputkeen tiedostossa `handlers/chatCore.ts` (jos se liittyy reititykseen)
5. Päivitä reitityslogiikka tiedostossa `combo.ts`, jos palvelu vaikuttaa kohteen valintaan
6. Dokumentoi tässä tiedostossa

### Uuden suorittimen lisääminen

1. Luo `open-sse/executors/[provider].ts`, joka laajentaa `BaseExecutor`-luokkaa
2. Rekisteröi tiedostossa `config/providerRegistry.ts`
3. Lisää tiedoston `executors/index.ts` tehtaaseen
4. Lisää suorittimelle yksikkötestit
5. Dokumentoi tiedostossa `docs/architecture/ARCHITECTURE.md`

### Uuden MCP-työkalun lisääminen

1. Luo tai päivitä `open-sse/mcp-server/tools/[category]Tools.ts`
2. Määritä syötteille Zod-skeema
3. Rekisteröi työkalu tiedostossa `mcp-server/index.ts`
4. Lisää käyttöoikeusmatriisiin hakemistossa `mcp-server/auth/`
5. Lisää yksikkötestit
