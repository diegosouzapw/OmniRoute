Web Cookie-providers stellen OmniRoute in staat om via je bestaande browsersessie een AI-service te gebruiken in plaats van een API-sleutel. Ze zijn handig wanneer je via de website van een service al toegang hebt en je wilt dat OmniRoute dezelfde geauthenticeerde sessie gebruikt.

In tegenstelling tot providers met een API-sleutel gebruiken Web Cookie-providers voor authenticatie de inloggegevens die je browser naar de website stuurt.

---

# Voordat je begint

> **Belangrijk:** Kopieer inloggegevens altijd uit een **live netwerkverzoek**, **niet** uit de cookieopslag van je browser.

Veel authenticatieproblemen worden veroorzaakt doordat cookies vanaf de verkeerde plek worden gekopieerd.

## Kopieer NIET uit de cookieopslag

De meeste browsers tonen opgeslagen cookies via:

```
DevTools
→ Application (of Storage)
→ Cookies
```

Hoewel deze cookies er correct uitzien, kunnen ze:

- verouderd zijn
- onvolledig zijn
- cookies missen die alleen bij geauthenticeerde verzoeken worden verzonden

Het gebruik van deze waarden kan authenticatiefouten veroorzaken, zelfs als ze geldig lijken.

## Kopieer uit een live verzoek

Gebruik in plaats daarvan de cookies van een geslaagd verzoek:

```
DevTools
→ Network
→ Vernieuw de pagina
→ Open een chat- of gespreksverzoek
→ Request Headers
→ Cookie
```

De `Cookie`-requestheader bevat precies de authenticatiegegevens die je browser met succes heeft gebruikt.

Voor de meeste Web Cookie-providers is dit de waarde die je in OmniRoute moet plakken.

# Algemene configuratie

Het configuratieproces is voor de meeste Web Cookie-providers hetzelfde.

1. Meld je aan op de website van de provider.
2. Open de ontwikkelaarstools van de browser.
3. Open het tabblad **Network**.
4. Vernieuw de pagina.
5. Open een geauthenticeerd chat- of gespreksverzoek.
6. Kopieer de vereiste authenticatiegegevens.
7. Open OmniRoute.
8. Ga naar **Providers → Add Provider**.
9. Selecteer je Web Cookie-provider.
10. Plak de inloggegevens.
11. Klik op **Test Connection**.
12. Sla de provider op.

Welke inloggegevens precies vereist zijn, hangt af van de provider.

## NoTrack (notrack-web)

NoTrack ([notrack.ai](https://notrack.ai)) is een gratis chatplatform voor consumenten waarvoor geen registratie vereist is — de sessie wordt bij het eerste bezoek anoniem aangemaakt en blijft behouden via drie cookies: `uid`, `si_usr_id` en `si_ses_id`. OmniRoute stuurt hetzelfde `/api/dispatch`-eindpunt door via één model-id (`notrack-c`, alias `ntw`).

### Stappen om verbinding te maken

1. Open [notrack.ai](https://notrack.ai) in uw browser en laat de anonieme sessiecookie instellen.
2. Open **DevTools → Network**, vernieuw de pagina en klik op een willekeurig `/api`-verzoek.
3. Kopieer bij **Request Headers** de volledige waarde van de `Cookie`-header.
4. Ga in OmniRoute naar **Providers → Add Provider → NoTrack Web (Free)**.
5. Plak de cookietekenreeks in het veld `apiKey` en klik op **Save**.

OmniRoute extraheert `uid`, `si_usr_id` en `si_ses_id` uit de geplakte tekenreeks en bouwt een schone `Cookie`-header op met uitsluitend die paren — plus `nt_session` (het `ntk_…`-token dat wordt ingesteld voor ingelogde accounts), indien aanwezig. Als een van de drie ontbreekt, wordt de ongewijzigde geplakte tekenreeks doorgestuurd, zodat beheerders met alternatieve indelingen kunnen experimenteren.

### Model-id's

| Model-id    | Weergavenaam | Opmerkingen                                          |
| ----------- | ------------ | ---------------------------------------------------- |
| `notrack-c` | NoTrack C    | Standaard — het upstream-dispatchmodel `C`.          |
| `C`         | NoTrack C    | Alias voor `notrack-c` (ruwe upstream-dispatchcode). |
| `notrack`   | NoTrack C    | Alias voor `notrack-c`.                              |
| `ntw`       | NoTrack C    | Korte alias voor `notrack-c`.                        |

Alle vier model-id's verwijzen naar hetzelfde upstream-dispatchmodel (`C`).

### Verzoekopties

De executor accepteert deze optionele velden in de verzoekbody:

| Bodyveld              | Standaard | Doel                                                                                      |
| --------------------- | --------- | ----------------------------------------------------------------------------------------- |
| `notrack_mode`        | `usual`   | Dispatchmodus (vrije tekenreeks; upstream accepteert `usual`, …)                          |
| `notrack_max_turns`   | `6`       | Aantal interne beurten dat upstream mag uitvoeren voordat het antwoordt.                  |
| `notrack_chat_id`     | `null`    | Hervat een bestaande upstream-chat (laat weg voor een nieuwe chat).                       |
| `notrack_attachments` | `[]`      | Doorgeefarray met upstream-bijlagebeschrijvingen.                                         |
| `notrack_regenerate`  | `false`   | Stel in op `true` om een opnieuw gegenereerd antwoord voor de vorige beurt aan te vragen. |

### Mogelijkheden

- **Streaming en niet-streaming** chatvoltooiingen.
- **Toolaanroepen** — stel `tools: [...]` in voor het verzoek; de executor serialiseert deze naar een envelope-contract voor toolaanroepen en parseert de antwoorden van het model terug naar OpenAI-`tool_calls`.
- **`response_format`** — `json_object` en `json_schema` worden ondersteund. De executor extraheert het eerste JSON-object uit het antwoord van het model en zet het om in een tekenreeks voordat het wordt geretourneerd.
- **Redeneringshint** — de executor verzendt een `reasoning`-delta wanneer upstream een `thinking`-gebeurtenis verzendt.

### Beperkingen

- Upstream hanteert gebruikslimieten voor anonieme gebruikers — wanneer die worden overschreden, geeft de executor een 429-status met een gebruiksvriendelijke melding.
- Alle model-id's verwijzen naar hetzelfde upstream-dispatchmodel; er is geen afzonderlijke omschakeling per model.
- De executor roept het `/api/chats`-eindpunt van upstream niet aan, waardoor chatgeschiedenis en sessies niet automatisch worden beheerd. Gebruik `notrack_chat_id` om een bestaande upstream-chat te hervatten.

# Wat webcookieproviders wel en niet kunnen

Webcookieproviders hergebruiken de chatinterface van een website. Ze bieden **niet** dezelfde mogelijkheden als officiële API's.

## Ondersteund

- Authenticeren met uw bestaande browsersessie
- Toegang tot modellen die via uw account beschikbaar zijn
- Chatreacties streamen
- Geen API-sleutel vereist

## Niet ondersteund

- Functies aanroepen
- Tools aanroepen
- Automatische bestandsbewerking
- Agentische IDE-workflows
- Functies die alleen via de API beschikbaar zijn

Dit is verwacht gedrag en **geen** bug.

Als u tools moet uitvoeren, bestanden automatisch wilt bewerken of andere agentworkflows nodig hebt, gebruik dan een **provider met API-sleutel** in plaats van een Web Cookie-provider.

# Kanttekening bij validatie

Een geslaagde **Test Connection** of cookievalidatie controleert alleen of de opgegeven aanmeldgegevens de verwachte indeling lijken te hebben.

Totdat Issue #7857 is opgelost, **garandeert een geslaagde validatie niet** dat de provider zich met succes kan authenticeren.

Als de authenticatie nog steeds mislukt, controleer dan of u de aanmeldgegevens uit een live netwerkverzoek hebt gekopieerd en niet uit de cookieopslag van de browser.

---

# Problemen oplossen

## Authenticatie mislukt

Controleer of de aanmeldgegevens zijn gekopieerd uit:

```
Network
→ Request Headers
→ Cookie
```

en **niet** uit:

```
Application
→ Cookies
```

---

## Cookie werkt in de browser, maar niet in OmniRoute

Sommige providers gebruiken cookies die alleen tijdens geauthenticeerde verzoeken worden verzonden.

Kopieer de aanmeldgegevens opnieuw uit een nieuw netwerkverzoek nadat u een gesprek met succes hebt geopend.

---

## Sessie verlopen

Web Cookie-providers gebruiken uw bestaande browsersessie.

Als uw browsersessie verloopt of u zich afmeldt, moet u een nieuwe set aanmeldgegevens kopiëren. Raadpleeg de bijbehorende tool [Browser Session Sync Extension](../guides/SESSION-SYNC-EXTENSION.md) om het vernieuwen van cookies voor ondersteunde webproviders te automatiseren.

---

## Test Connection slaagt, maar verzoeken mislukken

Totdat Issue #7857 is opgelost, garandeert een geslaagde validatie niet dat het authenticatieverzoek zal slagen.

Kopieer uw aanmeldgegevens opnieuw uit een nieuw geauthenticeerd verzoek voordat u verdergaat met het oplossen van problemen.

# Aanbevolen werkwijzen

- Kopieer aanmeldgegevens uit een nieuw geauthenticeerd verzoek.
- Gebruik geen oude cookies opnieuw.
- Houd uw browsersessie actief terwijl u Web Cookie-providers gebruikt.
- Behandel gekopieerde cookies als gevoelige aanmeldgegevens.
- Gebruik providers met een API-sleutel wanneer u functies wilt aanroepen of agentworkflows nodig hebt.
