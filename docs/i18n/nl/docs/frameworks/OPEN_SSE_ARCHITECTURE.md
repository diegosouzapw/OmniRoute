> **TL;DR**: `open-sse/` is de kernstreamingengine die elk LLM-verzoek in OmniRoute aandrijft. Het bevat ongeveer 1.400 bestanden die de verzoekpijplijn, executors, services, MCP-server en vertaallaag implementeren. Deze handleiding legt uit hoe de onderdelen samenhangen.

**Bron:** `open-sse/` (workspacepakket, ongeveer 1.440 `.ts`-bestanden die geen tests zijn)

---

## Waarom een afzonderlijk workspacepakket?

`open-sse/` is om verschillende redenen een **zelfstandige workspace** in de OmniRoute-monorepo:

1. **Herbruikbaarheid** — `open-sse` wordt als `@omniroute/open-sse` op npm gepubliceerd, zodat andere projecten het onafhankelijk kunnen gebruiken
2. **Duidelijke grenzen** — de streamingengine is losgekoppeld van de OmniRoute-specifieke UI-/databaselaag
3. **Prestaties** — de engine heeft geen Next.js-afhankelijkheden, wat snellere koude starts in CLI- en serverless-omgevingen mogelijk maakt
4. **Versiebeheer** — `open-sse` kan volgens zijn eigen planning releases uitbrengen

```json
// package.json
"workspaces": ["open-sse"]
```

## De verzoekpijplijn

Elk LLM-verzoek doorloopt een **pijplijn met 5 fasen**:

```
                              ┌──────────────┐
   HTTP-verzoek                │  1. ROUTEREN │   combo-resolutie, modelselectie
   (Next.js-route)             └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. VERTALEN │   formaatconversie (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. UITVOEREN│   providerexecutor, HTTP, opnieuw proberen, stroomonderbreker
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAMEN │   SSE-transformatie, tegendruk
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. REGISTREREN│ gebruiksregistratie, aanroeplogboek, foutclassificatie
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP-respons (SSE of JSON)
```

### Fase 1: Routeren (services/combo.ts)

**Toegangspunt**: `handleComboChat()` in `services/combo.ts`

Leidt het verzoek naar een concrete tuple `(provider, model, account, credentials)`:

- Zoek de combo op aan de hand van de ID (of bouw een virtuele combo voor `auto/*`-modellen)
- Pas de routeringsstrategie toe (prioriteit, gewogen, round-robin, enz.)
- Filter providers uit die niet goed functioneren (stroomonderbreker)
- Kies het volgende bruikbare doel

Voor `auto/*`-modellen doet deze fase ook het volgende:

- Voert het algoritme voor **scoring op basis van 16 factoren** uit (`services/autoCombo/`)
- Selecteert een `provider+model`-paar op basis van status, kosten, latentie, enz.

### Fase 2: Vertalen (translator/)

Als het bronformaat (bijvoorbeeld OpenAI) afwijkt van het doelformaat (bijvoorbeeld Claude), wordt het verzoek **vertaald**:

- Systeemprompt → systeembericht
- Tooldefinities → providerspecifiek toolformaat
- Parameters voor redeneren/denken → providerspecifieke equivalenten
- Normalisatie van berichtrollen (`developer` → `system` voor andere providers dan OpenAI)

`translator/index.ts` stelt het volgende beschikbaar:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Fase 3: Uitvoeren (executors/)

**Toegangspunt**: `getExecutor(providerId).execute(request, options)`

Alle providers gebruiken `DefaultExecutor` (`executors/default.ts`) via de fallback van de `getExecutor()`-factory. De executor:

- Bouwt de upstream-URL (`buildUrl()`)
- Voegt providerspecifieke headers toe (`buildHeaders()`)
- Transformeert de verzoekbody (`transformRequest()`)
- Verstuurt het HTTP-verzoek met nieuwe pogingen en exponentiële back-off
- Handelt indien nodig de vernieuwing van authenticatie af (OAuth-providers)

Alle executors breiden `BaseExecutor` (`executors/base.ts`, 1170 regels code) uit, dat het volgende biedt:

- Algemene logica voor nieuwe pogingen
- Proxy-integratie
- Integratie met de stroomonderbreker
- Hooks voor gebruiksregistratie

### Fase 4: Streamen (utils/stream.ts)

Voor streamingresponsen retourneert de executor een **ReadableStream**. De handler:

- Leidt de stream door een SSE-transformatie (`createSSETransformStreamWithLogger`)
- Past heartbeat-pings toe om verbroken verbindingen te detecteren
- Handelt het verbreken van de verbinding door de client correct af (`pipeWithDisconnect`)
- Transformeert SSE → JSON voor clients die geen streaming gebruiken

Voor niet-streamingresponsen retourneert de executor een geparseerd JSON-object dat ongewijzigd wordt doorgegeven.

### Fase 5: Registreren (services/usage.ts)

Na de respons (geslaagd of mislukt) wordt het gebruik geregistreerd:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` uit de respons
- `cost_usd` berekend op basis van prijsgegevens
- `latency_ms`, `status`, `error_class` bij mislukking
- Opgeslagen in de tabel `usage_history`

Aanroeplogbestanden (indien ingeschakeld) worden weggeschreven naar `${DATA_DIR}/call_logs/`.

## Diepgaande analyse van belangrijke bestanden

### chatCore.ts (5977 regels)

De **hoofdhandler voor verzoeken**. Ondanks de omvang heeft deze een duidelijke structuur:

```ts
// Pseudostructuur van chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Authenticatie + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Validatie van de body
  const body = await parseRequestBody(request);

  // 3. Formaatdetectie + vertaling
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Comboroutering
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Doorgaan naar het volgende doel
    }
  }

  // 5. Noodfallback
  return await emergencyFallback(body);
}
```

Hoewel het één gigantische functie is, is deze ingedeeld in **secties met commentaar** die overeenkomen met de pijplijn van 5 fasen.

### combo.ts (4456 regels code)

De **routeringsengine** die een combo omzet in geordende doelen.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("doel mislukt, volgende wordt geprobeerd", { target, err });
    }
  }
  throw new ComboExhaustedError("Alle doelen zijn mislukt");
}
```

Ondersteunt **19 routeringsstrategieën** (zie `src/shared/constants/routingStrategies.ts`):

| Strategie           | Gedrag                                                                                               |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| `priority`          | Geordende lijst met het eerste doel voorop                                                           |
| `weighted`          | Probabilistisch op basis van het gewicht per doel                                                    |
| `round-robin`       | Doorloop de doelen op volgorde                                                                       |
| `context-relay`     | Geef context door tussen doelen                                                                      |
| `fill-first`        | Vul het quotum voordat naar het volgende doel wordt gegaan                                           |
| `p2c`               | Power of two choices                                                                                 |
| `random`            | Uniform willekeurig                                                                                  |
| `least-used`        | Kies het doel met het laagste recente gebruik                                                        |
| `cost-optimized`    | Goedkoopste gezonde doel eerst                                                                       |
| `reset-aware`       | Houdt rekening met resetvensters van providers                                                       |
| `reset-window`      | Routering op basis van resetvensters                                                                 |
| `headroom`          | Doel met de meeste resterende quotumruimte eerst                                                     |
| `strict-random`     | Werkelijk uniform (geen kwaliteitsweging)                                                            |
| `auto`              | Gebruik scoring met 16 factoren (`autoCombo/`)                                                       |
| `lkgp`              | Laatst bekende goed werkende provider eerst                                                          |
| `context-optimized` | Meest geschikt voor verzoeken met een lange context                                                  |
| `fusion`            | Stuur parallel naar een panel en laat daarna een beoordelaar het resultaat samenvoegen (`fusion.ts`) |

### base.ts (1170 regels code)

De **abstracte executor** die door alle 107 executors wordt uitgebreid. Deze bevat:

- `buildUrl()` — standaardconstructie van URL's (subklassen overschrijven dit voor aangepaste constructie)
- `buildHeaders()` — standaardheaders (authenticatie, content-type)
- `transformRequest()` — standaard ongewijzigde doorgifte
- `execute()` — de belangrijkste HTTP-lus met nieuwe pogingen, back-off en circuitbreaker

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Verwerkt alle OpenAI-/Anthropic-compatibele providers
  // Providers registreren configuraties (URL, authenticatie, headers), maar delen de executorlogica
}
```

Providerspecifiek gedrag (authenticatieheaders, basis-URL, versieheaders) wordt geconfigureerd via het providerregister, niet via afzonderlijke executorklassen.

````
## Executors (75+ bestanden)

Eén bestand per provider. Ze breiden allemaal `BaseExecutor` uit en overschrijven alleen wat afwijkt.

### Algemene patronen

Providers worden opgezocht via `getExecutor(providerId)`, dat de geconfigureerde executor retourneert. OpenAI/Anthropic-compatibele providers gebruiken `DefaultExecutor` (`executors/default.ts`). Providerspecifiek gedrag (basis-URL, authenticatieheaders, API-versie) wordt geconfigureerd in `open-sse/config/providers/`, terwijl transformaties van requestbodies worden afgehandeld in `open-sse/translator/`.

**Aangepaste URL** wordt ingesteld via de providerconfiguratie:

```ts
// Providerconfiguratie in open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Aangepaste authenticatie** wordt afgehandeld via de authenticatieconfiguratie van het providerregister (API-sleutel, OAuth, headerprofielen).

Transformaties van **aangepaste requestbodies** (bijvoorbeeld wanneer Anthropic `system` van `messages` scheidt) worden per provider geregistreerd in `open-sse/translator/`.

````

### De executorfactory

`executors/index.ts` exporteert `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

De resolutie verloopt via `ExecutorRegistry` (`executors/registry.ts`): elke gespecialiseerde executor wordt gedeclareerd in de ingebouwde tabel van `executors/index.ts` en bij het laden van de module geregistreerd via `registerExecutor(alias, instance)`; `getExecutor()` raadpleegt het register en valt terug op een gememoiseerde `DefaultExecutor` voor elke provider zonder gespecialiseerde invoer. De volledige koppeling van alias → executor wordt vastgelegd door de golden test `tests/unit/executor-map-golden.test.ts`.

## Vertalers

Vertaal tussen **3 indelingen**: OpenAI, Anthropic, Gemini, plus de nieuwe Responses API.

### Wanneer vertaling plaatsvindt

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Veelvoorkomende vertalingen:

- `OpenAI → Anthropic`: afzonderlijk `system`-veld, `x-api-key`-header
- `OpenAI → Gemini`: `contents` in plaats van `messages`, `systemInstruction`
- `OpenAI → Responses API`: `input`-array, status via `previous_response_id`

### Afgehandelde randgevallen

- Rol `developer` → `system` voor niet-OpenAI-providers
- Rol `system` → samengevoegd met het eerste gebruikersbericht voor GLM/ERNIE
- `json_schema` → Gemini's `responseMimeType` + `responseSchema`
- `tools` → providerspecifieke toolindeling
- Denkparameters (o1, Claude) → providerspecifieke equivalenten

## MCP-server

`open-sse/mcp-server/` implementeert de **Model Context Protocol**-server:

- **110 tools** (providerbeheer, combinaties, geheugen, cache, compressie, proxy, vaardigheden, gamificatie, plug-ins, Notion, Obsidian, lokaal corpus)
- **3 transportmethoden**: stdio, SSE, Streamable HTTP
- **33 scopes** voor fijnmazige autorisatie

### Toolregistratie

Tools worden geregistreerd als zelfstandige bestanden in `open-sse/mcp-server/tools/`, waarbij elk bestand een naam, schema, handler en scope exporteert:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Momentopname van de systeemstatus ophalen",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transportmethoden

```ts
// stdio (CLI-gebruik)
startMcpStdio(server);

// SSE (HTTP-gebaseerde streaming)
startMcpSse(server, port);

// Streamable HTTP (moderne MCP)
startMcpStreamable(server, port);
```

### Autorisatie

Elke toolaanroep wordt onderworpen aan scopecontroles (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Onvoldoende scope");
}
```

## Transformers

`open-sse/transformer/` converteert tussen de indelingen **Chat Completions** en **Responses API**.

### Waarom een afzonderlijke transformer?

De Responses API is de nieuwe indeling van OpenAI met **stateful gesprekken** (`previous_response_id`). Wanneer een client een Responses-verzoek verzendt, voert OmniRoute de volgende stappen uit:

1. Converteert Responses intern naar Chat Completions
2. Verzendt het naar de provider (elke provider die Chat Completions ondersteunt)
3. Converteert het antwoord terug naar de Responses-indeling
4. Streamt het geconverteerde antwoord naar de client

De transformer (`transformer/responsesTransformer.ts`) biedt:

```ts
createResponsesApiTransformStream(): TransformStream
```

Deze verwerkt:

- `response.output_item.added`-gebeurtenissen
- `response.output_text.delta`-gebeurtenissen
- `response.completed`-gebeurtenis
- Toewijzing van toolaanroepen (`function_call` ↔ `tool_calls`)

## Configuratie

`open-sse/config/` bevat de configuratielaag:

| Bestand                       | Doel                                                          |
| ----------------------------- | ------------------------------------------------------------- |
| `providerRegistry.ts`         | Register voor chatmodellen uit de catalogus met 352 providers |
| `providerModels.ts`           | Modelaliassen, indelingstoewijzing                            |
| `constants.ts`                | Time-outs, limieten, statuscodes                              |
| `defaultThinkingSignature.ts` | Standaarddenksignatuur van Claude                             |
| `modelStrip.ts` (in services) | Veldverwijdering per provider                                 |

### Schema van het providerregister

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Zod-validatie tijdens het laden van de module waarborgt dat alle providerconfiguraties geldig zijn.

## Prestatiebeperkingen

De routeringsengine heeft strikte prestatiebudgetten:

| Bewerking                                         | Doel  | Meting                      |
| ------------------------------------------------- | ----- | --------------------------- |
| Combinatieresolutie                               | <10ms | Voor 50 doelen              |
| Controle van snelheidslimiet                      | <1ms  | Tokenbucket in het geheugen |
| Terugval voor modelfamilie                        | <5ms  | Gecachte familiedefinities  |
| Routeringsdispatch van aanvragen                  | <2ms  | Kritiek pad                 |
| **Geen blokkerende I/O in kritiek routeringspad** | —     | Alles asynchroon            |

## Antipatronen

❌ **Synchrone databaseaanroepen in `combo.ts`** — vooraf berekenen en cachen
❌ **Logica voor nieuwe pogingen in handlers** — gebruik `retry()` van de weerbaarheidsservice
❌ **Directe toegang tot providerconfiguratie** — gebruik getters van `providerRegistry`
❌ **Hardgecodeerde terugvalketens** — definieer deze in `modelFamilyFallback.ts`
❌ **Statusmutaties tussen gelijktijdige aanvragen** — gebruik uitsluitend een context per aanvraag

## Een nieuwe component toevoegen

### Een nieuwe service toevoegen

1. Maak `open-sse/services/[serviceName].ts` met een duidelijk afgebakende verantwoordelijkheid
2. Exporteer de hoofdhandlerfunctie en eventuele constanten
3. Voeg unittests toe in `tests/unit/services/[serviceName].test.mjs`
4. Integreer deze in de aanvraagpipeline in `handlers/chatCore.ts` (indien routeringsgerelateerd)
5. Werk de routeringslogica in `combo.ts` bij als de service invloed heeft op de doelselectie
6. Documenteer dit in dit bestand

### Een nieuwe executor toevoegen

1. Maak `open-sse/executors/[provider].ts` dat `BaseExecutor` uitbreidt
2. Registreer deze in `config/providerRegistry.ts`
3. Voeg deze toe aan de factory in `executors/index.ts`
4. Voeg unittests voor de executor toe
5. Documenteer dit in `docs/architecture/ARCHITECTURE.md`

### Een nieuwe MCP-tool toevoegen

1. Maak of wijzig `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definieer een Zod-schema voor de invoer
3. Registreer de tool in `mcp-server/index.ts`
4. Voeg deze toe aan de scopematrix in `mcp-server/auth/`
5. Voeg unittests toe
