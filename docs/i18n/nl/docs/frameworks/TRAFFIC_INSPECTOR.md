Traffic Inspector is de ingebouwde debugger voor HTTPS-verkeer van OmniRoute — een tool vergelijkbaar met Charles Proxy / mitmweb / HTTP Toolkit die **LLM-bewust** en **agent-bewust** is. De tool bevindt zich op `/dashboard/tools/traffic-inspector` en ontvangt live verkeer van maximaal 5 gelijktijdige opnamebronnen.

**Dashboardlocatie:** `/dashboard/tools/traffic-inspector`
**Zijbalkgroep:** Tools (na AgentBridge)
**Zie ook:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge is opnamemodus 1.

### Architectuur in één alinea

De `TrafficBuffer` (`src/mitm/inspector/buffer.ts`) is een gedeelde ringbuffer in het geheugen (standaard 1000 vermeldingen, configureerbaar via `INSPECTOR_BUFFER_SIZE`). Alle opnamebronnen schrijven ernaar via `push()`. De buffer classificeert elke vermelding met behulp van `kindDetector.ts` (bepaalt of het een LLM-verzoek is), berekent een `contextKey` (SHA-256-vingerafdruk van de systeemprompt) en zendt deze via `globalTrafficBuffer.subscribe()` naar alle WebSocket-abonnees. Het dashboard maakt verbinding via `GET /api/tools/traffic-inspector/ws` en ontvangt bij het verbinden een momentopname, gevolgd door `new`/`update`/`clear`-events.

## §2 Vastleggingsmodi

Traffic Inspector ondersteunt **5 gelijktijdige vastleggingsbronnen**. Elke bron kan onafhankelijk worden in- en uitgeschakeld. Het veld `source` van elke `InterceptedRequest` (`src/mitm/inspector/types.ts`) is `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"` of `"tproxy"`.

### Modus 1 — AgentBridge (standaard, altijd ingeschakeld)

**Bron:** AgentBridge-handlers (`src/mitm/handlers/base.ts`)
**Mechanisme:** Elke aanroep van `intercept()` in `MitmHandlerBase` roept vóór het doorsturen `hookBufferStart()` aan en na voltooiing `hookBufferUpdate()`. Geen extra configuratie — werkt zodra AgentBridge actief is.
**Bereik:** De 9 IDE-agents die in AgentBridge zijn geconfigureerd
**Opmerking:** Het veld `source` in `InterceptedRequest` = `"agent-bridge"`

### Modus 2 — Aangepaste hosts (DNS-omleiding)

**Bron:** Door de gebruiker gedefinieerde lijst met hosts (tabel `inspector_custom_hosts`)
**Mechanisme:** Wanneer een host via de gebruikersinterface wordt toegevoegd, wordt `127.0.0.1 <host>` aan `/etc/hosts` toegevoegd (vereist sudo). De bestaande MITM-server van AgentBridge (poort 443) genereert dynamisch een SNI-certificaat voor de nieuwe host.
**Bereik:** Elke toepassing die de toegevoegde host gebruikt — geen configuratiewijziging in de toepassing nodig
**Opmerking:** `source` = `"custom-host"`

Voorbeelden van gebruiksscenario's:

- `api.openai.com` monitoren vanuit Python-scripts
- Problemen met `my-internal-llm.company.com` opsporen
- Verkeer vastleggen van mobiele apparaten in hetzelfde netwerk (via ARP-spoofing — geavanceerd)

### Modus 3 — HTTP_PROXY-listener (poort 8080)

**Bron:** Toepassingen die de omgevingsvariabelen `HTTP_PROXY`/`HTTPS_PROXY` gebruiken
**Mechanisme:** Secundaire listener op poort 8080 (`src/mitm/inspector/httpProxyServer.ts`) die als een standaard expliciete HTTP/HTTPS-proxy fungeert. Accepteert `CONNECT`-tunnels (HTTPS) en directe HTTP-verzoeken.
**Bereik:** Elke toepassing die de omgevingsvariabele `HTTP_PROXY` respecteert — geen DNS-wijziging, geen sudo
**Opmerking:** `source` = `"http-proxy"`

```bash
# Snel verkeer voor één opdracht vastleggen:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# Verkeer permanent vastleggen in een shellsessie:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**TLS-beperking:** HTTPS-`CONNECT`-tunnels worden alleen als metadata vastgelegd (host, poort, timing) — de TLS-inhoud wordt standaard niet ontsleuteld. Schakel de optie "HTTPS ontsleutelen in proxymodus" in (opt-in, vereist dat het AgentBridge-certificaat wordt vertrouwd) om de volledige inhoud te inspecteren.

**Poortconflict:** Als poort 8080 in gebruik is, retourneert AgentBridge een 409 met een gestructureerde foutmelding. Wijzig de poort via de omgevingsvariabele `INSPECTOR_HTTP_PROXY_PORT`.

### Modus 4 — Systeembrede proxy (geavanceerd, opt-in)

**Bron:** Proxy-instellingen op besturingssysteemniveau (van toepassing op alle toepassingen op de machine)
**Mechanisme:** Gebruikt API's van het besturingssysteem om al het HTTP/HTTPS-verkeer via de HTTP_PROXY-listener om te leiden:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **Bereik:** Elke toepassing op de machine die de systeemproxy-instellingen respecteert
  **Opmerking:** `source` = `"system-proxy"`

**Veiligheidsmechanismen:**

- Timer voor automatisch uitschakelen (standaard 30 min., configureerbaar via `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES`)
- De vorige status van de systeemproxy wordt in de database opgeslagen en bij het terugdraaien hersteld
- Het dashboard toont de melding "Systeemproxy terugdraaien" als de gebruiker weg navigeert terwijl deze actief is
- De gebruikersinterface toont de badge `⚠ Geavanceerd` en een expliciet bevestigingsselectievakje

### Modus 5 — Transparante TPROXY-ontsleuteling (Linux, root, opt-in)

**Bron:** Kernel-TPROXY + beleidsroutering (`src/mitm/tproxy/`)
**Mechanisme:** Markeert nieuwe lokale uitgaande TCP-verbindingen naar een doelpoort (standaard `443`) in `mangle OUTPUT`, waarna een `ip rule` de gemarkeerde pakketten omleidt voor lokale aflevering en het `TPROXY`-doel van `mangle PREROUTING` ze overdraagt aan een transparante (**IP_TRANSPARENT**) listener (standaardpoort `8443`). De listener beëindigt TLS met een leaf-certificaat dat **op aanvraag per SNI-hostnaam** door een dynamische CA wordt uitgegeven, legt de ontsleutelde uitwisseling vast en stuurt het verzoek opnieuw versleuteld door naar de oorspronkelijke bestemming.
**Bereik:** **Willekeurige** doelhosts op de doelpoort — geen spoofing via `/etc/hosts`, geen omgevingsvariabele `HTTP_PROXY`, geen systeembrede wijziging van de proxy. Het onderschepte proces hoeft niet anders te worden geconfigureerd, maar moet de dynamische CA wel vertrouwen.
**Opmerking:** `source` = `"tproxy"`

**Vereisten:** Alleen Linux (**IP_TRANSPARENT** is uitsluitend beschikbaar op Linux), de capability **CAP_NET_ADMIN** (root) en een native N-API-addon dat met een C-toolchain moet worden gebouwd (`npm run build:native:tproxy`). Wanneer dit niet beschikbaar is, wordt de schakelaar op het dashboard uitgeschakeld met de tooltip "TPROXY-ontsleuteling vereist Linux + root + het native addon". De firewallregels worden transactioneel toegepast/teruggedraaid (een crash laat nooit een `mangle`-regel achter) en worden bij het opnieuw opstarten gewist. Een op SO_MARK gebaseerde anti-loop voorkomt dat de opnieuw versleutelde doorstuurverbinding van de proxy zelf opnieuw wordt onderschept.

Dit is een omvangrijk subsysteem met een eigen, specifieke beheerdershandleiding — zie `docs/security/MITM-TPROXY-DECRYPT.md` (git; niet gecompileerd in `/docs`) voor het volledige firewallrecept, de dynamische CA per SNI + het installatieprogramma voor de trust store, de uitsluitend lokale route, details over anti-loop en het configuratieschema. De schakelaar wordt aangestuurd via `GET / POST / DELETE /api/tools/agent-bridge/tproxy` (opmerking: de route bevindt zich onder het AgentBridge-voorvoegsel, niet onder het Traffic Inspector-voorvoegsel).

## §4 LLM-bewuste functies

### 4.1 Soortdetector (`src/mitm/inspector/kindDetector.ts`)

Classificeert elk verzoek als `"llm"`, `"app"` of `"unknown"` aan de hand van 4 signalen:

1. **Hostregister** — circa 18 bekende hostnamen van LLM-API's (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot, enz.)
2. **Padpatronen** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses`, enz.
3. **Bodystructuur** — detecteert de velden `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input`
4. **User-agent-aanwijzingen** — `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor` in de UA-tekenreeks

Aangepaste hosts die via Modus 2 worden toegevoegd, nemen hun `kind` over van de formulierinvoer (standaard `"custom"`).

### 4.2 SSE-samenvoeger (`src/mitm/inspector/sseMerger.ts`)

**Onafhankelijke cleanroom-implementatie.** Het parseren van gebeurtenissen volgt het
[WHATWG-algoritme voor server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream),
terwijl de reconstructie de openbare streamingschema's van
[OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) en
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent)
volgt.

Reconstrueert het uiteindelijke assistentbericht uit ruwe SSE-deltagebeurtenissen:

- **Anthropic**: verzamelt `content_block_delta` per index; verwerkt `text_delta`, `input_json_delta` (toolaanroepen), `thinking_delta`
- **OpenAI**: verzamelt keuzes/toolaanroepen van Chat Completions en uitvoeritems van de Responses API
  per index
- **Gemini**: verzamelt `candidates[i].content.parts`
- **Onbekend**: retourneert ruwe gebeurtenissen ongewijzigd

Het tabblad Response toont een schakelaar: **"Ruwe gebeurtenissen ↔ Samengevoegd"**.

### 4.3 Gespreksnormalisator (`src/mitm/inspector/conversationNormalizer.ts`)

**Onafhankelijke cleanroom-implementatie.** Normalisatie wordt gedefinieerd door lokale black-boxcontracten
en de openbare berichtschema's van OpenAI, Anthropic en Gemini; er wordt geen upstream
implementatiebron gebruikt.

Converteert de berichtindelingen van OpenAI, Anthropic en Gemini vóór het renderen naar één `NormalizedConversation`:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // messages / contents / prompt uit de request-body
  response: NormalizedTurn[]; // assistentrespons (samengevoegd via sseMerger)
  contextKey: string | null; // SHA-256-vingerafdruk van de systeemprompt
}
```

Bloktypen: `text`, `tool_use`, `tool_result`. Het tabblad Conversation gebruikt deze structuur, ongeacht de provider.

### 4.4 Contextsleutelkleuring (`src/mitm/inspector/contextKey.ts`)

- Berekent `SHA-256` van de systeemprompt (eerste bericht met `role:system`, of het veld `system`, of Gemini `systemInstruction`)
- Retourneert een hexadecimaal voorvoegsel van 12 tekens (`"a3f9c2..."`)
- De frontend koppelt de sleutel aan een deterministische HSL-kleur voor de linkerrandbalk
- **Filter "dezelfde context"**: klikken op de chip `ctx #a3f` voegt een filter toe waarmee alleen verzoeken met dezelfde vingerafdruk worden weergegeven

Dit maakt het eenvoudig om verschillende "persona's" of taken die binnen dezelfde agentsessie worden uitgevoerd, visueel van elkaar te onderscheiden.

### 4.5 Extractie van LLM-metadata

Voor LLM-verzoeken extraheert het tabblad LLM Details:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // uit de request-body of respons
  messages: number; // aantal beurten
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // true bij een SSE-respons
  mappedTo: string | null; // x-omniroute-mapped-header
  costEstimateUsd: number | null; // geschatte kosten op basis van OmniRoute-prijzen
}
```

### 4.6 Live filter voor lopende verzoeken

Het veld `status` van het verzoek is `number | "in-flight" | "error"` — een item wordt
als `"in-flight"` toegevoegd zodra het verzoek begint en **ter plaatse bijgewerkt**
wanneer de respons (of fout) binnenkomt. De schakelaar **"Live"** in de werkbalk
(`liveOnly`, i18n-sleutel `trafficInspector.liveOnly`) beperkt de lijst tot items
waarvan `status === "in-flight"`, zodat je open verbindingen in realtime kunt volgen.

Het filter is een zuiver client-side predicaat in
`src/lib/inspector/matchesTrafficFilter.ts`:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

De status van de schakelaar bevindt zich in `useTrafficFilters` (de hooks van het inspectordashboard) en
wordt gecombineerd met de andere filters (profiel, host, agent, bron, status, context).

### 4.7 Procestoewijzing (Linux)

Op Linux kan elk onderschept verzoek worden toegeschreven aan het **lokale proces
waarvan het afkomstig is**. Er worden twee optionele velden toegevoegd aan `InterceptedRequest`:

```ts
pid?: number;          // id van het proces van oorsprong (alleen Linux)
processName?: string;  // naam van het proces van oorsprong (alleen Linux)
```

`src/mitm/inspector/processAttribution.ts` koppelt de tijdelijke _clientpoort_
van de verbinding als volgt aan een PID + naam:

1. `/proc/net/tcp` en `/proc/net/tcp6` lezen om de socket-inode voor de
   poort te vinden (`parseProcNetTcpForInode`, een zuivere parser die met fixtures kan worden getest).
2. `/proc/<pid>/fd/` doorzoeken naar een symbolische koppeling naar `socket:[<inode>]`.
3. De procesnaam lezen uit `/proc/<pid>/comm`.

Een TTL-cache van 1 seconde begrenst de kosten van de procfs-scan onder belasting. Toewijzing gebeurt
volgens het **best-effortprincipe** — elke fout wordt omgezet in `null` en blokkeert de vastlegging nooit. Op
macOS/Windows retourneert de functie `null` (stub; ondersteuning voor `lsof`/`GetExtendedTcpTable`
volgt later).

## §6 Beveiliging

Traffic Inspector toont **al het onderschepte HTTPS-verkeer**, inclusief autorisatieheaders en aanvraagbody's. De volgende beveiligingsmaatregelen zijn van kracht:

| Maatregel                       | Details                                                                                                                                                                                                                 |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LOCAL_ONLY**                  | Alle routes en het WebSocket-eindpunt zijn uitsluitend toegankelijk via loopback (afgedwongen in `routeGuard.ts` vóór authenticatie)                                                                                    |
| **Maskering van geheimen**      | De lineaire scanner `maskSecret()` anonimiseert RFC 6750 Bearer-aanmeldgegevens, providerspecifieke sleutels en lange ondoorzichtige tokens vóór `TrafficBuffer.push()`                                                 |
| **Limiet voor bodygrootte**     | Body's > `INSPECTOR_MAX_BODY_KB` (standaard 1024 KB) worden afgekapt met de melding `"(afgekapt voor betere prestaties)"`                                                                                               |
| **Opschoning van headers**      | Namen worden omgezet naar kleine letters; framing-, hop-by-hop- en proxyauthenticatieheaders worden verwijderd; cookies worden volledig geanonimiseerd; waarden van aanmeldgegevens worden verwerkt door `maskSecret()` |
| **CSP**                         | Strikt Content Security Policy op Traffic Inspector-pagina's om XSS via geïnjecteerde antwoordbody's te voorkomen                                                                                                       |
| **Standaard geen persistentie** | De `TrafficBuffer` bevindt zich in het geheugen en gaat verloren wanneer de server opnieuw wordt gestart. Sessies worden alleen opgeslagen wanneer ze expliciet worden opgenomen                                        |

### Toegepaste harde regels

| Regel                             | Toepassing                                                                             |
| --------------------------------- | -------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | Alle HTTP-foutreacties van Traffic Inspector-routes worden opgeschoond                 |
| **#15 + #17** `isLocalOnlyPath()` | `/api/tools/traffic-inspector/` is LOCAL_ONLY + SPAWN_CAPABLE (systeemproxyopdrachten) |

### Bekende beperkingen

- **Systeembrede proxymodus** beïnvloedt alle toepassingen op de machine, waaronder VPN-clients en SSO. Gebruik deze modus altijd met de timer voor automatisch uitschakelen. Gebruik deze modus niet op gedeelde machines.
- **HTTPS via CONNECT-tunnel**: Modus 3 (HTTP_PROXY) legt voor HTTPS-bestemmingen alleen tunnelmetadata vast, tenzij TLS-onderschepping is ingeschakeld. Dit is zo ontworpen — transparante vastlegging zonder dat het AgentBridge-certificaat wordt vertrouwd, zou de TLS-verificatie voor die apps verbreken.
- **Hardgecodeerde tekenreeksen in sommige componenten**: Sommige UI-componenten (F7/F8) bevatten een klein aantal hardgecodeerde tekenreeksen waarvoor nog geen i18n-sleutels beschikbaar zijn. Deze zijn als bekende beperking gedocumenteerd in het i18n-hiatenrapport; ze worden in een volgende aanpassingsronde gemigreerd. De betreffende tekenreeksen zijn decoratieve UI-labels waarvoor geen vertaling nodig is voor functioneel gebruik.

## §7 Probleemoplossing

### WebSocket-verbinding verbroken

Als de liveweergave "Verbinding verbroken" toont:

1. Controleer of de server nog actief is: `GET /api/tools/traffic-inspector/capture-modes`
2. Herlaad de pagina — de WebSocket maakt opnieuw verbinding en ontvangt een nieuwe momentopname
3. Als de server opnieuw is gestart, is de buffer in het geheugen gewist — oude vermeldingen zijn verdwenen, tenzij er een sessie is opgenomen

### Conflict met poort 8080

Als de HTTP_PROXY-modus niet kan worden gestart:

```bash
lsof -i :8080    # zoek het proces
```

Wijzig de poort:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### Systeemproxy niet teruggezet

Als OmniRoute crasht terwijl de systeembrede proxymodus actief is:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

Het dashboard biedt bij de volgende keer laden ook de optie "Systeemproxy terugzetten" als het detecteert dat de databasestatus aangeeft dat de proxy actief was.

### Buffer vol

Wanneer de buffer `INSPECTOR_BUFFER_SIZE` bereikt (standaard 1000), verdringen nieuwe vermeldingen de oudste. Als belangrijke aanvragen verloren gaan:

- Verhoog `INSPECTOR_BUFFER_SIZE` (bijv. 5000) — hierdoor wordt meer geheugen gebruikt voor een langere bewaartijd
- Neem een sessie op om het relevante tijdvenster in de database op te slaan
