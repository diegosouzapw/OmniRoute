Gebruik deze handleiding om de kleinste betrouwbare ontwikkelcyclus voor een pull request te kiezen. Deze
vervangt niet de hieronder gekoppelde architectuur- en beveiligingsdocumenten voor specifieke gebieden; de handleiding koppelt elk veelvoorkomend
wijzigingstype aan de bijbehorende contracten, gerichte controles en CI-dekking.

## Het pad dat elke wijziging volgt

1. **Kies de basis voordat je wijzigingen aanbrengt.** Zoek de hoogste actieve `release/v*`-branch en maak een branch vanaf
   de tip daarvan. Richt de PR op die branch, niet op `main`. Als er een releasefreeze actief is, richt de PR dan niet op de bevroren
   branch; gebruik de volgende actieve cyclus die wordt beschreven in
   [Branching- en releasemodel](BRANCHING_MODEL.md).
2. **Benoem de contracten.** Identificeer elke catalogus, elk schema, elk gegenereerd artefact, elke openbare API of gebruikersinterface
   waarop de wijziging van invloed is. De onderstaande tabel bevat de minimale uitgangsset.
3. **Schrijf gerichte tests of werk ze bij.** Productiewijzigingen in `src/`, `open-sse/`, `electron/` of
   `bin/` vereisen een geautomatiseerde test in dezelfde PR. Voer de kleinst mogelijke testbestanden uit die het
   gedrag aantonen en voer daarna de vermelde gerichte controles uit.
4. **Laat CI de brede matrix uitvoeren.** De volledige unitshards, Vitest, de dekkingratel en
   de productiebuild worden op de PR uitgevoerd. Voer lokaal alleen een brede suite uit wanneer een gerichte fout op
   een bredere impact wijst of wanneer de wijziging meerdere subsystemen omvat.
5. **Stem alles af vóór de review.** Haal de actieve basis op, bekijk de nieuwe commits daarvan en je diff ten opzichte
   ervan en rebase of merge de basis vervolgens volgens de workflow voor bijdragers. Los conflicten in gegenereerde bestanden
   en catalogi op vanuit hun bron, genereer ze opnieuw, voer de gerichte cyclus opnieuw uit en bevestig dat de
   PR nog steeds op de actieve releasebranch is gericht.
6. **Leg bewijs vast.** Vermeld in het PR-sjabloon de uitgevoerde commando's, elk toegevoegd of gewijzigd testbestand,
   migraties of featureflags en eventuele validatie die alleen in CI plaatsvindt en nog in behandeling is.

## Gouden paden per wijzigingstype

De onderstaande commando's zijn minimale gerichte controles, geen toestemming om een test over te slaan die het
door jou gewijzigde gedrag rechtstreeks dekt.

### Provider

**Contracten**

- Providerdefinitie in `src/shared/constants/providers/` en de samenstelling ervan in
  `src/shared/constants/providers.ts`.
- Modellen en mogelijkheden in `open-sse/config/providerRegistry.ts` of de daaruit geëxtraheerde registerbestanden.
- Selectie van executor/translator, OAuth- of API-sleutelconfiguratie, dashboardassets en de gegenereerde
  providerreferentie, indien van toepassing.
- Openbare inloggegevens moeten `resolvePublicCred()` gebruiken; foutreacties moeten de gedeelde opgeschoonde
  fouthulpfuncties gebruiken. Zie `docs/security/PUBLIC_CREDS.md` (git; niet gecompileerd naar `/docs`) en
  [Opschoning van fouten](../security/ERROR_SANITIZATION.md).

**Gerichte cyclus**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # wanneer de catalogus verandert; commit de gegenereerde diff
npm run lint
```

Test ook elke betrokken aanvraagfamilie: chat, Responses, afbeeldingen, embeddings, audio of video.
Beoordeel gegenereerde catalogus- en golden-diffs als contractwijzigingen; accepteer ze niet klakkeloos.

### Routering

**Contracten**

- Openbare strategiewaarden en UI-metadata in `src/shared/constants/routingStrategies.ts`.
- Dispatch en volgorde onder `open-sse/services/combo.ts` en `open-sse/services/combo/`.
- Combo-schema's, persistentie, resiliencestatus, modelmogelijkheden en API-/UI-besturingselementen.
- [Auto-Combo-engine](../routing/AUTO-COMBO.md) en resiliencedocumentatie wanneer het gedrag verandert.

**Gerichte cyclus**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # wijzigingen in strategie of dispatch
npm run check:known-symbols      # wijzigingen in strategieregistratie
npm run lint
```

Gebruik lokaal deterministische tests met gemockte upstreams. Live combo-rooktests vereisen inloggegevens en zijn
handmatig; ze zijn geen vervanging voor CI.

### UI / UX

**Contracten**

- Next.js-route/-pagina en grenzen van gedeelde componenten onder `src/app/` en
  `src/shared/components/`.
- API-responsstructuren, laad-/lege-/foutstatussen, gedrag voor toetsenbord en schermlezer,
  responsieve lay-out, thematisering en uitbreiding van locales.
- Engelse UI-bronteksten in `src/i18n/messages/en.json`; codeer geen nieuwe gebruikersgerichte tekst hard.

**Gerichte cyclus**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Voer de app uit voor interactie- of visuele wijzigingen en controleer zowel smalle als brede viewports. CI voert de
productiebuild en bredere suites uit; visueel gedrag vereist nog steeds een gerichte componenttest, Playwright-test
of gedocumenteerde handmatige controle die bij de wijziging past.

### i18n

**Contracten**

- `src/i18n/messages/en.json` is de UI-bron; `config/i18n.json` is de localebron.
- CLI-catalogi staan afzonderlijk onder `bin/cli/locales/`.
- Behoud ICU-placeholders en -tags exact. Vertaal geen product-/provider-/modelnamen,
  protocol- en headernamen, commando's, code-/JSON-identificatoren, URL's, omgevingsvariabelen of
  beschermde termen zoals `OmniRoute`, `OAuth`, `MCP` en `A2A`. De huidige bronlijst is
  `scripts/i18n/glossary/protected-terms.json`.

**Gerichte cyclus**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # wanneer CLI-teksten/-catalogi veranderen
npm run lint
```

Dit is een richtlijn voor het bestaande systeem, geen uitnodiging om de tooling of het sleutelmodel ervan uit te breiden.
Houd i18n-patches doelgericht terwijl het vervangende systeem wordt ontworpen. Voer geen vertaalcommando's
uit die externe services aanroepen, tenzij de taak expliciet gegenereerde vertalingen vereist en
je de resulterende diff hebt beoordeeld.

### CLI

**Contracten**

- Openbare opdrachten en vlaggen in `bin/cli/`, gegenereerde API-opdrachten, afsluitcodes, stdout/stderr en
  JSON-uitvoerstructuren, configuratie-/omgevingsgedrag en verpakte bestanden.
- Voor de gebruiker zichtbare CLI-teksten moeten de i18n-laag van de CLI gebruiken en de catalogi `en`/`pt-BR` op elkaar afgestemd houden.
- Behoud Node als de ondersteunde runtime en handhaaf het contract van het gepubliceerde binaire bestand.

**Gerichte cyclus**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # wijzigingen in de gegenereerde/gebundelde CLI
npm run check:pack-policy     # wijzigingen in het pakketoppervlak
npm run lint
```

Gebruik de exacte opdracht in een tijdelijke gegevensmap wanneer het gedrag afhankelijk is van parsering, bestanden of de
afsluitstatus. CI voert de bredere controles van pakketartefacten en het ecosysteem uit.

### Database

**Contracten**

- Domeinmodules onder `src/lib/db/`; importeer specifieke modules rechtstreeks (de oude herexportlaag `localDb.ts` is verwijderd).
- Genummerde, idempotente SQL-migraties onder `src/lib/db/migrations/`, transactieveiligheid, upgradegedrag,
  indexen en elke aanroeper die door het schema wordt beïnvloed.
- Routes en handlers voeren nooit rechtstreeks ruwe SQL uit.

**Gerichte cyclus**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Test bij het toevoegen van een migratie zowel een nieuwe database als een upgrade vanaf het vorige schema. Databasetests
moeten handles sluiten en tijdens het opschonen `resetDbInstance()` aanroepen. Voer `npm run test:bun:db` alleen uit wanneer
het best-effort-adapterpad voor Bun verandert; Node blijft leidend.

### Build / implementatie

**Contracten**

- Root- en workspace-manifesten/lockfile, `scripts/build/`, zelfstandige Next.js-assemblage, inhoud van het
  `dist/`-pakket, Electron-platformmetadata, CI-workflows en implementatiesentinels.
- Ondersteunde Node-bereiken en het toegestane gebruik van Bun in `CLAUDE.md` moeten intact blijven.
- Buildartefacten blijven niet-gevolgd; beleid voor afhankelijkheden, licenties, workflows en pakketten is van toepassing.

**Gerichte cyclus**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # wijzigingen in afhankelijkheden of het lockfile
npm run check:pack-policy      # wijzigingen in het oppervlak van het gepubliceerde pakket
npm run lint
```

Gebruik `npm run build` lokaal alleen wanneer de wijziging invloed heeft op compilatie, zelfstandige assemblage, assets
of runtimebundeling. Gebruik `npm run build:release` alleen voor release-/implementatievalidatie. De build van CI is
het definitieve platformoverschrijdende signaal; platformspecifieke Electron-wijzigingen vereisen de bijbehorende gerichte build
of bewijs uit een rooktest.

## Lokale kandidaatcyclus

Brontests kunnen niet aantonen dat het verpakte artefact opstart: fouten in verpakkingslijsten, opgeschoonde afhankelijkheden en native binaries worden pas zichtbaar wanneer de tarball wordt geïnstalleerd en gestart. `npm run dev:candidate` (`scripts/dev/candidate.mjs`) is de lokale kant van de eenmalig bouwen / valideren / promoveren-stroom uit RFC #8084: het bouwt één kandidaat, valideert exact dat artefact, promoveert het door mappen te hernoemen en draait de promotie terug wanneer de gepromoveerde sleuf niet door de statuscontrole komt.

```bash
npm run dev:candidate -- run --dry-run --json  # toon het plan, wijzig niets
npm run dev:candidate -- run                   # bouw + valideer + promoveer, automatisch terugdraaien
npm run dev:candidate -- build                 # npm pack + installeren in _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # opstarten op een vrije poort, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current en previous omwisselen
npm run dev:candidate -- run --from-tarball <file.tgz>  # een elders gebouwde tarball hergebruiken (CI)
```

- **Bouw één keer.** `build` verpakt de huidige bronstructuur (hiervoor is `dist/server.js` nodig, dus voer eerst `npm run build:release` uit) of kopieert `--from-tarball`, en installeert de tarball vervolgens in een geïsoleerd npm-prefix, omdat de tarball geen `node_modules` bevat. De id is de korte `HEAD`-sha (`-dirty` wanneer de bronstructuur lokale wijzigingen bevat) of `tgz-<sha256>` voor een tarball. Een ongewijzigde id die al is gebouwd, wordt hergebruikt in plaats van opnieuw gebouwd; geef `--force` door om deze opnieuw te bouwen.
- **Valideer het pakket, niet de broncode.** `validate` start de geïnstalleerde CLI (`serve --port <free port>`) met een nieuwe `DATA_DIR=<candidate>/data`, nepgeheimen en de `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` en `INITIAL_PASSWORD` van de beheerder verwijderd uit de omgeving, zodat de sleutelloze loopback-configuratie van een nieuwe installatie wordt gecontroleerd. Het wacht totdat `GET /api/health` 200 retourneert, vereist dat `GET /v1/models` 200 retourneert, stopt de procesgroep en legt het oordeel samen met de hash van de tarball vast in `validation.json`.
- **Promoveer hetzelfde artefact.** `promote` weigert een kandidaat zonder geslaagde validatie voor de huidige hash van de tarball. De standaard actieve sleuf is `_artifacts/candidate/current`; met `--target <dir>` selecteert u een andere map op hetzelfde bestandssysteem en de vorige sleuf daarvan is `<dir>.previous`. Elke hernoeming is atomair en bij een fout halverwege worden de reeds uitgevoerde hernoemingen teruggedraaid.
- **Draai terug.** `run` valideert de gepromoveerde sleuf opnieuw en verwisselt `current` en `previous` wanneer die controle mislukt. Een kandidaat die niet door de eerste validatie komt, wordt nooit gepromoveerd.

Alles wordt geschreven onder de door git genegeerde map `_artifacts/candidate/`; een bestaande OmniRoute-installatie en de bijbehorende gegevensmap worden nooit gewijzigd. De gepromoveerde CLI is `_artifacts/candidate/current/prefix/bin/omniroute`; start deze met uw eigen `DATA_DIR` wanneer u deze gebruikt. Afsluitcodes: `0` geslaagd, `1` mislukte validatie of promotie, `2` gebruiksfout of ontbrekende build.

## Lokale cyclus versus CI

| Lokaal uitvoeren voor elke patch                                                                | CI biedt het brede signaal                                                                  |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Directe gedragstests en bovenstaande categoriecontroles                                         | Opgesplitste volledige unit-testsuite en seriële tests                                      |
| `npm run lint`                                                                                  | Vitest-suites en stapsgewijs aangescherpte dekkings-/kwaliteitsdrempels                     |
| Typecheck of build alleen wanneer het betreffende contract dit vereist                          | Productiebuild, beveiligings-, documentatie-, afhankelijkheids- en PR-beleidscontroles      |
| Handmatige interactie-/livecontroles alleen wanneer automatisering het gedrag niet kan bewijzen | Taakoverstijgende integratie- en platformcontroles die door de workflow zijn geconfigureerd |

Een geslaagde gerichte cyclus levert bewijs voor het gewijzigde contract, maar bewijst niet dat niet-gerelateerde CI-controles
zullen slagen. Laat omgekeerd niet elke lokale wijziging wachten op de volledige repositorymatrix.

## Reconciliatiechecklist

Voordat je om een review vraagt:

- Bevestig dat de basisbranch van de PR nog steeds de hoogste actieve `release/v*`-branch is.
- Haal die basisbranch op en bekijk de commits die zijn toegevoegd sinds je je branch hebt gemaakt.
- Controleer `git diff <active-base>...HEAD` op onbedoelde of gegenereerde wijzigingen.
- Los conflicten in catalogi en gegenereerde documenten op door de bron bij te werken en de uitvoer opnieuw te genereren.
- Voer na de reconciliatie elke gerichte test/controle uit die in de PR-beschrijving staat vermeld.
- Verzwak nooit assertions en verwijder geen vereiste tests alleen om aan te sluiten op een gewijzigde basisbranch.
