---

OmniRoute biedt **twee** manieren om OpenAI Codex te gebruiken:

| Provider               | Hoe deze met OpenAI communiceert                                                                                                                                                                          | Gebruiksbeperking                                                                    |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **`codex`**            | Stuurt je ChatGPT/OpenAI OAuth-token rechtstreeks door naar de Responses API                                                                                                                              | **Ja** — de officiële sessie is niet geautoriseerd voor gebruik met een proxy/router |
| **`codex-app-server`** | Stuurt de **eigen `codex app-server` van de Codex CLI** aan via JSON-RPC/WebSocket; de CLI beheert en vernieuwt zijn OAuth (`~/.codex/auth.json`) zelf, precies zoals bij een interactieve `codex`-sessie | **Nee** — OmniRoute stuurt nooit een token door naar de API                          |

Omdat `codex-app-server` nooit een token doorstuurt, geldt de
gebruiksbeperking voor het doorsturen van sessies niet. Hiervoor moet wel een
**Codex CLI bereikbaar zijn via de geconfigureerde app-server-URL**, en die CLI
moet **aangemeld zijn**.

---

## 1. Architectuur

```
┌─ OmniRoute-app ─────────────────┐        ┌─ codex-app-server-sidecar ──────────┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                   │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456         │
│  (+ capaciteitstoken)            │  JSON  │  --ws-auth capability-token         │
│                                  │  RPC   │  beheert OpenAI OAuth zelf          │
└──────────────────────────────────┘        │  (~/.codex/auth.json, autovernieuwing)│
        │ gedeeld (compose-volumes)          └─────────────────────────────────────┘
        ▼
  codex-appserver-token   → het WS-capaciteitstoken (beide koppelen dit)
  codex-appserver-home    → ~/.codex (auth.json wordt door het dashboard geschreven
                             en door de codex app-server van de sidecar gelezen)
```

- De sidecar luistert **alleen** op het interne compose-netwerk
  (`ws://codex-app-server:1456`), beveiligd met een capaciteitstoken. Deze wordt
  **nooit** op de host of het internet gepubliceerd.
- De Codex CLI is ingebouwd in `omniroute:base`, zodat Codex niet op de host of
  de machine van de gebruiker hoeft te worden geïnstalleerd wanneer je de
  sidecar uitvoert.

## 2. Opstarten

```bash
# Start de stack MET het sidecarprofiel voor de Codex-app-server:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

De sidecar maakt bij de eerste start zijn WS-capaciteitstoken aan (in het
gedeelde volume `codex-appserver-token`) en de app leest hetzelfde token via
`OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`. Handmatige configuratie van het token
is niet nodig.

## 3. Verbinden en aanmelden

1. Voeg in het dashboard een verbinding toe voor **OpenAI Codex (App-Server)**.
   Er is geen API-sleutel of token vereist (dit is een provider zonder
   authenticatie — de sidecar beheert de authenticatie).
2. Als de Codex CLI van de sidecar **nog niet is aangemeld**, meldt de
   statuscontrole van de verbinding _"actief, maar niet aangemeld"_ (geen rode
   authenticatiefout). Gebruik **Aanmelden met ChatGPT**: hiermee wordt de
   standaard Codex-device-OAuth in je browser uitgevoerd, waarna
   `~/.codex/auth.json` via **Authenticatie toepassen** naar het gedeelde volume
   wordt geschreven (dezelfde aanmelding bedient zowel de provider `codex` als
   `codex-app-server`).
3. Na het aanmelden wordt de statuscontrole groen (deze controleert zowel
   `/readyz` **als** `account/read` — dus actief _en_ geauthenticeerd) en begint
   alles te werken.

Het dashboard overschrijft nooit een gezond bestaand `~/.codex/auth.json` — het
schrijft alleen wanneer het bestand ontbreekt of het token verouderd is (er wordt
altijd een back-up gemaakt).

## 4. Implementatiescenario's

- **Beheerder met een reeds geauthenticeerde Codex CLI** — koppel je
  `~/.codex` op de host aan de sidecar (`codex-appserver-home`) en sla de
  aanmeldingsstap over.
- **Publieke gebruiker zonder lokaal geïnstalleerde Codex** — niet relevant: de
  sidecar bevat de CLI. De gebruiker authenticeert zich alleen via het
  dashboard.
- **Bare-metal OmniRoute (geen sidecar, Codex op de host)** — laat
  `OMNIROUTE_CODEX_APPSERVER_WS` verwijzen naar je eigen `codex app-server` en
  zorg ervoor dat Codex op de host is aangemeld; de melding "Codex is niet
  geïnstalleerd" verschijnt als het binaire bestand ontbreekt.

## 5. Residentiële/UDP-uitgaande verbindingen (extra voor beheerders, niet meegeleverd)

De generieke sidecar hierboven gebruikt voor uitgaand verkeer het normale
netwerk van de container. Een beheerder die Codex-verkeer via een
**residentieel uitgangspunt** moet leiden (bijvoorbeeld een TUN-tailscale-sidecar
die TCP + UDP/QUIC transporteert), voert dit uit als een afzonderlijke
compose-override; dit maakt bewust **geen** deel uit van het meegeleverde profiel
`codex-app-server`. Raadpleeg het interne operationele draaiboek voor deze
configuratie.
