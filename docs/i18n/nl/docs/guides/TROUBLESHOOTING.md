## Snel overzicht

**Nieuw bij OmniRoute?** Begin hier — hiermee los je 90% van de problemen op:

| Ik zie dit                     | Wat het betekent                            | Wat je moet doen                                                                                     |
| ------------------------------ | ------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| "Kan geen verbinding maken"    | OmniRoute wordt niet uitgevoerd             | Voer `omniroute` of `docker restart omniroute` uit                                                   |
| "Ongeldige API-sleutel"        | Je sleutel is onjuist of verlopen           | Kopieer de sleutel opnieuw vanaf de website van de provider                                          |
| "Snelheidslimiet overschreden" | Je verstuurt te veel verzoeken              | Wacht 1 minuut of gebruik `model: "auto"` voor automatische terugval                                 |
| "Quota overschreden"           | Je hebt je gratis/betaalde quota opgebruikt | Verbind meer providers of gebruik gratis providers (Kiro, Pollinations)                              |
| "Trage reacties"               | De provider is bezet of ver weg             | Gebruik `model: "auto/fast"` of verbind een snellere provider (Groq, Cerebras)                       |
| "Verkeerde provider gebruikt"  | `auto` heeft een andere provider gekozen    | Dat is normaal! `auto` kiest de beste. Dwing een specifieke provider af met `model: "openai/gpt-4o"` |
| "502 Bad Gateway"              | De provider is offline                      | Wacht en probeer het opnieuw, of gebruik `model: "auto"` om van provider te wisselen                 |
| "401 Unauthorized"             | Je aanmeldgegevens zijn onjuist             | Controleer je API-sleutel of verifieer je opnieuw via OAuth                                          |
| "429 Too Many Requests"        | De snelheidslimiet is bereikt               | Wacht 1 minuut of verbind meer providers                                                             |

## Gedetailleerde probleemoplossing

---

### Snelheidsbeperking bij gratis providers (429 / 400 / 401)

**Symptoom**: Wanneer je `model: "auto"` gebruikt met gratis providers/providers zonder authenticatie (opencode, auggie enzovoort), krijg je met tussenpozen `HTTP 429`, `400` of `401` in plaats van antwoorden. De verzoeken slagen wanneer je dezelfde prompt even later opnieuw probeert, maar automatisering (cronjobs, agents, scripts) stopt bij de eerste fout.

**Hoofdoorzaak**: Drie onafhankelijke foutmodi stapelen zich op:

1. **Snelheidslimiet van de provider (`429`)**: Gratis abonnementen kunnen een quota per tijdsvenster afdwingen. Een piek van parallelle aanroepen put dit uit, waardoor het volgende verzoek wordt geweigerd totdat het venster opnieuw wordt ingesteld.
2. **Defect model bij passthrough (`400`/`401`)**: `auto/*`-pools kunnen passthrough-modellen van `opencode` bevatten die in de catalogus zijn geregistreerd, maar geen werkende aanmeldgegevens hebben (bijvoorbeeld `oc/north-mini-code-free` → `401`). De automatische router probeert er een, dit mislukt en de fout wordt doorgegeven voordat de terugval wordt geactiveerd.
3. **Versterking door gelijktijdigheid (`429` onder belasting)**: Wanneer meerdere agent-/cronsessies tegelijk `auto` gebruiken, overschrijdt de totale aanvraagsnelheid wat gratis providers tolereren, waardoor legitieme aanroepen als misbruik worden aangemerkt.

**Geverifieerde oplossing (gerapporteerd door de community, 2026-08-10)**: stel drie omgevingsvariabelen zo af dat rotatie, gelijktijdigheid en terugval de wisselvalligheid van gratis abonnementen opvangen, in plaats van erop vast te lopen:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # ga bij 400/401 naar een ander model/een andere provider (slaat defecte passthrough-modellen over)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # expliciete toelatingslimiet voor zware verzoeken (standaard niet ingesteld: geen limiet voor het aantal verzoeken, zie opmerking hieronder)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # langere begrensde wachttijd voor capaciteit voor zware verzoeken, in plaats van een onmiddellijke, opnieuw te proberen 503
```

Stel deze in de procesomgeving van OmniRoute in (de daemon, bijvoorbeeld via de LaunchAgent-plist of `systemctl edit`) en start OmniRoute vervolgens opnieuw. De rotatievlag heeft verreweg de grootste impact: deze zet een definitieve fout om in een transparante nieuwe poging bij een gezonde provider in de pool.

**Opmerking**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` begrenst hoeveel zware verzoeken — verzoeken met een lange context — tegelijk worden uitgevoerd; de limiet is een toelatingspoort, geen snelheidsbeperking van een provider. **Update over #503-fanout:** deze variabele wordt niet langer standaard ingesteld (de limiet geldt nu alleen wanneer deze expliciet wordt geconfigureerd, zoals hierboven) — de toelating van zware verzoeken wordt in plaats daarvan beperkt door een automatisch afgeleid bytebudget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) dat zichzelf schaalt op basis van de werkelijke geheugenlimiet van de host. Daardoor zou een nieuwe implementatie veel minder afwijzingen met `503 chat_admission_busy` moeten opleveren zonder dat je deze variabele hoeft in te stellen; expliciet instellen zoals hier beschreven werkt nog steeds precies zoals gedocumenteerd. Expliciete overschrijvingen van het bytebudget worden begrensd op 8 MiB–2 GiB. Een `413 body_exceeds_budget` is niet tijdelijk: verhoog dat bytebudget, verlaag `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` of verhoog de geheugenlimiet van het proces. Een afwijzing wegens `inflight_bytes_budget` is tijdelijke capaciteitsconcurrentie en kan opnieuw worden geprobeerd. De snelheidsbeperking per provider (`open-sse/services/rateLimitManager.ts`) wordt afzonderlijk geregeld door `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` en `RATE_LIMIT_AUTO_ENABLE` — zie `.env.example`.

**Controleren of het heeft gewerkt**: voer je agent/cron tweemaal kort na elkaar uit en controleer of beide uitvoeringen slagen. Vóór de oplossing geeft de tweede uitvoering doorgaans `429`/`401`. Na de oplossing worden fouten (indien aanwezig) transparant opnieuw geprobeerd en wordt de aanroep voltooid. Je kunt ook `curl /monitoring/health` uitvoeren en het veld `rateLimitedUntil` bij de providerverbindingen en `circuitBreakers.providerBreakers[].state` voor de getroffen providers in de gaten houden — de status is `CLOSED`, `DEGRADED`, `OPEN` of `HALF_OPEN` (zie `src/shared/utils/circuitBreaker.ts`), en een provider die blijft mislukken, schakelt van `CLOSED → DEGRADED → OPEN` voordat na het resetvenster een testverzoek wordt doorgelaten (`HALF_OPEN`).

**Als je nog steeds 429 ziet**: het actieve account voor die provider heeft daadwerkelijk zijn _quotum_ opgebruikt (niet alleen de snelheidslimiet). Voeg een tweede account voor dezelfde provider toe in het OmniRoute-dashboard → Providers → Accounts, of voeg een andere gratis provider toe (bijv. `routeway`, `auggie`). Rotatie helpt alleen bij tijdelijke snelheidslimieten/400/401; wanneer een quotum volledig is opgebruikt, is een tweede aanmeldingsgegeven of een andere provider vereist.

**Als je 403 ziet bij vision-modellen (`auto/vision`, `bazaarlink/*`)**: het gekoppelde account heeft geen betaald abonnement dat vision omvat, of de API-sleutel heeft onvoldoende machtigingen. Controleer in het providerdashboard of het bereik van de sleutel vision/multimodaal omvat, of koppel een account met een betaald abonnement en behoud dit als vision-doel.

## Waarschuwingen bij npm install (ERESOLVE / peer / deprecated)

Wanneer u `npm install -g omniroute` uitvoert, ziet u mogelijk een hele reeks waarschuwingen, zoals `npm warn ERESOLVE`, meldingen over peer-dependencies en `deprecated`-berichten. **Deze zijn te verwachten en onschadelijk.** De installatie is geslaagd als u `added <N> packages` in de uitvoer ziet.

De waarschuwingen zijn afkomstig van verouderde peer-dependency-versiebereiken in pakketten van derden waarover OmniRoute geen controle heeft:

1. **`marked-terminal` vereist `marked >=1 <16`, maar `marked@18` is gevonden** — werkt in de praktijk prima; het upstream peer-versiebereik is gewoon verouderd.
2. **`deprecated prebuild-install@7.1.3`** — een transitieve helper voor het ophalen van native binaries. Deze wordt niet
   gebruikt om de vastgezette `wreq-js`-transportbinding te installeren en betekent niet dat het instellen van het transport voor de web-cookieprovider
   is mislukt.

**Geen actie nodig** — de waarschuwingen kunnen niet volledig worden onderdrukt zonder upstream pakketten te forken.

## Valse positieven van antivirussoftware

<a name="antivirus-false-positives"></a>

### Avast/AVG plaatst `README.md` in quarantaine met `MD:HttpRequest-inf[Susp]`

**Dit is een vals positief resultaat. Niets is geïnfecteerd en er is geen actie vereist.**

Avast en AVG gebruiken een heuristiek die plattetekst-/Markdown-bestanden markeert die veel
links bevatten die op HTTP-verzoeken lijken. OmniRoute's `README.md` wordt meegeleverd in het npm-pakket (het staat
vermeld in `package.json` → `files`), waardoor het bij een globale installatie terechtkomt in
`node_modules/omniroute/README.md` — en het bevat ongeveer 15 voorbeelden met
`http://localhost:20128/...` (de MCP HTTP/SSE-eindpunten, de A2A-URL `.well-known` en
`curl`-fragmenten). Die linkdichtheid is voldoende om de heuristiek te activeren.

Als dit pas onlangs is begonnen: het soort bestand is niet veranderd. De README is uitgebreid met
een tabel van eindpunten (MCP HTTP + SSE + A2A zijn toegevoegd) en meer `curl`-voorbeelden, waardoor
de drempel werd overschreden.

Het bestand is inerte documentatie zonder enige uitvoerbare inhoud. U kunt het veilig herstellen
vanuit quarantaine.

**Wat u kunt doen:**

1. **Stop de meldingen** — sluit de installatiemap uit in uw antivirussoftware
   (Avast: Instellingen → Uitzonderingen) door het pad naar uw globale `node_modules` en/of de
   OmniRoute-gegevensmap (`~/.omniroute/`) toe te voegen.
2. **Meld het valse positieve resultaat** — <https://www.avast.com/false-positive-file-form.php>,
   en voeg het in quarantaine geplaatste `README.md` toe. Dit is de oplossing waar iedereen baat bij heeft, omdat
   de heuristiek van de leverancier overdreven reageert op een tekstbestand.

**Waarom we dit niet aan onze kant 'oplossen':** alle voorbeelden gebruiken `http://localhost`, en
localhost kan niet met `https` worden gebruikt zonder gedoe met zelfondertekende certificaten. De documentatie
verminken om de heuristiek van één leverancier te omzeilen, zou iedere lezer benadelen om een scannerbug
tegemoet te komen.

### Kaspersky markeert de desktop-app als `PDM:Trojan.Win32.Generic`

**Dit is een vals positief resultaat van een gedragsheuristiek. Niets is geïnfecteerd.** Het
voorvoegsel `PDM:` van Kaspersky betekent dat het oordeel afkomstig is van de Proactive Defense Module (System Watcher),
die beoordeelt wat het installatieprogramma _doet_ in plaats van het te vergelijken met bekende malware. Wanneer
de detectie wordt geactiveerd, draait Kaspersky de hele installatie 'terug' — waarbij reeds
geschreven bestanden worden verwijderd — zodat de app uiteindelijk defect is of ontbreekt.

De gemarkeerde bestanden zijn standaardonderdelen van gedeclareerde opensourcedependency's die met de
desktop-app worden meegeleverd, bijvoorbeeld:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` en
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), de bibliotheek voor browserautomatisering
  die wordt gebruikt voor het aanmelden bij providers vanuit de app en voor browsergebaseerde chats.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — de vastgezette native binding `wreq-js` die wordt gebruikt voor HTTP met een browservingerafdruk bij providers
  die webcookies gebruiken (`<arch>` is `x64` of `arm64`).

**Waarom dit wordt geactiveerd:** het Windows-installatieprogramma is **nog niet digitaal ondertekend**, waardoor een niet-ondertekend NSIS-
installatieprogramma geen reputatie heeft en gedragsheuristieken met maximale agressiviteit worden uitgevoerd. In combinatie
met een meegeleverde native DLL en honderden `.js`-bestanden die worden geschreven onder
`%LOCALAPPDATA%\Programs\OmniRoute` (inclusief pakketmappen met hashachtervoegsels uit de zelfstandige
Next.js-build), is dat voldoende om de heuristiek te activeren. Codeondertekening staat gepland;
totdat deze is ingevoerd, kan dit bij nieuwe releases opnieuw gebeuren.

**Wat u kunt doen:**

1. **Verifieer eerst uw download** (dit sluit een gemanipuleerd bestand uit). Elke release publiceert
   `latest.yml`, waarvan het veld `sha512` (base64) betrekking heeft op het installatieprogramma
   `OmniRoute.Setup.<version>.exe`. Voer in PowerShell vanuit de map met het installatieprogramma het volgende uit:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   De uitvoer moet overeenkomen met `latest.yml` → `sha512`. Als dat niet het geval is, verwijdert u het bestand en
   downloadt u het opnieuw, uitsluitend vanaf de [GitHub-releasepagina](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Herstel + sluit uit** — herstel de teruggedraaide items vanuit quarantaine en voeg een uitsluiting
   toe voor `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Instellingen → Bedreigingen en uitsluitingen),
   en voer daarna de installatie opnieuw uit.
3. **Meld het valse positieve resultaat** — <https://opentip.kaspersky.com/>. Door gebruikers ingediende meldingen
   van valse positieven versnellen het toevoegen aan de toelatingslijst daadwerkelijk.

## Node.js-compatibiliteit

<a name="nodejs-compatibility"></a>

### Inlogpagina crasht of toont de foutmelding "Module self-registration"

**Oorzaak:** U gebruikt een Node.js-versie die buiten de goedgekeurde, veilige runtimeversies van OmniRoute valt. Meestal gaat het om een oudere patchversie van Node 22 of 24 die niet voldoet aan de minimale beveiligde versie die OmniRoute vereist.

**Symptomen:**

- De inlogpagina toont een leeg scherm of een serverfout
- De console toont `Error: Module did not self-register` of vergelijkbare fouten met native bindings
- De inlogpagina toont een **oranje waarschuwingsbanner** met uw Node-versie als de runtime buiten het ondersteunde beveiligingsbeleid valt

**Oplossing:**

1. Installeer een ondersteunde Node.js LTS-release (aanbevolen: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Controleer uw versie: `node --version` moet `v24.0.0` of nieuwer binnen de 24.x LTS-reeks tonen
3. Installeer OmniRoute opnieuw: `npm install -g omniroute`
4. Start opnieuw: `omniroute`

> **Ondersteunde veilige versies:** `>=22.22.2 <23` of `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) en Node.js 26 worden volledig ondersteund.

### npm v11+: `better-sqlite3` niet geïnstalleerd (module niet gevonden)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Oorzaak:** npm v11 (meegeleverd met Node.js 24+) blokkeert standaard installatiescripts voor optionele
afhankelijkheden. Omdat `better-sqlite3` in `optionalDependencies` staat
en native compilatie (`node-gyp rebuild`) vereist, slaat npm dit zonder melding over.

**Symptomen:**

- De server crasht bij het opstarten met `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` toont "No such file or directory"
- `npm ls better-sqlite3` toont `(empty)`

**Oplossing:**

1. Keur de installatiescripts goed en installeer opnieuw:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Of installeer de vooraf gecompileerde versie handmatig:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Controleer of het werkt: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Oorzaak:** Na een globale `npm install -g omniroute` kan het zijn dat het native binaire bestand van `better-sqlite3` in het pakket is gecompileerd voor een andere architectuur of Node.js-ABI dan lokaal wordt gebruikt. Dit komt vaak voor op macOS (zowel Apple Silicon als Intel) wanneer het vooraf gecompileerde binaire bestand niet overeenkomt met uw omgeving.

**Symptomen:**

- De server stopt direct tijdens het opstarten met een `dlopen`-fout
- De fout bevat `slice is not valid mach-o file`
- Volledig voorbeeld:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Oplossing — compileer opnieuw voor uw lokale omgeving (downgraden van Node.js is niet nodig):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Opmerking:** Hiermee wordt de native binding opnieuw gecompileerd voor uw lokale Node.js-versie en CPU-architectuur, waardoor de incompatibiliteit van het binaire bestand wordt opgelost. Het officieel ondersteunde runtimebereik is **`>=22.22.2 <23` of `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` in `src/shared/utils/nodeRuntimeSupport.ts`, afgestemd op het veld `engines` in `package.json`). Node.js 24.x LTS (Krypton) en Node.js 26 worden volledig ondersteund met `better-sqlite3` v12.x.

## Proxyproblemen

<a name="proxy-issues"></a>

### Providervalidatie toont "fetch failed"

**Oorzaak:** Het API-eindpunt voor sleutelvalidatie (`POST /api/providers/validate`) omzeilde voorheen de proxyconfiguratie, wat storingen veroorzaakte in omgevingen waarin proxyroutering vereist is.

**Oplossing (v3.5.5+):** Dit is nu opgelost. Providervalidatie wordt via `runWithProxyContext` gerouteerd, waarbij automatisch rekening wordt gehouden met proxyinstellingen op provider- en globaal niveau.

### Tokenstatuscontrole mislukt met "fetch failed"

**Oorzaak:** Bij het op de achtergrond vernieuwen van OAuth-tokens werd de proxyconfiguratie niet per verbinding bepaald.

**Oplossing (v3.5.5+):** De planner voor tokenstatuscontroles bepaalt nu per verbinding de proxyconfiguratie voordat een vernieuwing wordt geprobeerd. Werk bij naar v3.5.5+.

### SOCKS5-proxy retourneert "invalid onRequestStart method"

**Oorzaak:** In Node.js 22 is de dispatcher van undici@8 niet compatibel met de ingebouwde `fetch()`-implementatie van Node.

**Oplossing (v3.5.5+):** OmniRoute gebruikt nu de eigen `fetch()`-functie van undici wanneer een proxydispatcher actief is, zodat consistent gedrag wordt gegarandeerd. Werk bij naar v3.5.5+.

### MITM-proxy onder WSL: desktopapps op de Windows-host worden niet onderschept

**Oorzaak:** De MITM-proxy en het bijbehorende CA-certificaat worden geïnstalleerd in de omgeving waarin OmniRoute wordt uitgevoerd. Onder WSL is die omgeving de Linux-gast, terwijl de AI-desktopapps (Kiro, Trae, Copilot, Zed, …) op de Windows-host worden uitgevoerd. De hostapps vertrouwen het certificaatarchief van de gast niet en routeren niet via de systeemproxy van de gast, waardoor onderschepping van desktopverkeer daar niet wordt geactiveerd.

**Aanbeveling:** Voer OmniRoute rechtstreeks uit op hetzelfde besturingssysteem als de desktopapps die u wilt onderscheppen (Windows voor Windows-apps; hetzelfde geldt voor macOS/Linux). Als u OmniRoute binnen WSL laat draaien terwijl u zich op hostapps richt, moet u het gegenereerde CA-certificaat handmatig vertrouwen op de Windows-host en de netwerk-/proxyinstellingen van elke hostapp naar het WSL-proxyeindpunt laten verwijzen — een niet-ondersteunde, kwetsbare configuratie.

**Oplossing:**

2. Gebruik een combinatie met fallbackniveaus

### Meerdere Kiro-accounts: het tweede account maakt het eerste ongeldig

**Oorzaak:** De backend van Kiro staat slechts één actieve sessie per OIDC-clientregistratie toe.
Wanneer twee accounts dezelfde geregistreerde client delen (verbindingen die vóór v3.8.0 zijn geïmporteerd),
maakt het vernieuwen van het token van het ene account het vernieuwingstoken van het andere ongeldig.

**Oplossing (v3.8.0+):** Importeer de betreffende verbindingen opnieuw.

**inloggen via Google/GitHub** of **Automatisch importeren** wordt aangemaakt, automatisch een eigen
speciale OIDC-client. De verbinding is daardoor volledig geïsoleerd en het vernieuwen van het ene
account heeft geen gevolgen voor andere accounts.

Verbindingen die _vóór_ v3.8.0 zijn geïmporteerd, hebben geen clientregistratie per verbinding.
Die verbindingen blijven het gedeelde vernieuwingseindpunt voor sociale authenticatie gebruiken.
Om isolatie te verkrijgen, verwijdert u de oude verbinding via Dashboard → Providers en voegt u deze
opnieuw toe via een van de drie importmethoden.

Zie voor volledige details en stapsgewijze instructies voor het naast elkaar toevoegen van twee Kiro-accounts
[`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Docker-problemen

### Docker IPv6 / Verbinding opnieuw ingesteld

<a name="docker-ipv6"></a>

**Symptomen:** `curl http://localhost:20128/v1/models` retourneert `curl: (56) Recv failure: Connection reset by peer`. Het dashboard en niet-geverifieerde eindpunten werken, maar geverifieerde eindpunten mislukken — het lijkt een authenticatieprobleem, maar dat is het niet.

**Oorzaak:** `docker run -p 20128:20128` publiceert op zowel `0.0.0.0` (IPv4) als `::` (IPv6), maar het proces in de container luistert alleen op IPv4. Op hosts waar `localhost` eerst naar `::1` wordt omgezet, komt de verbinding terecht op de gepubliceerde IPv6-poort zonder achterliggende listener → de verbinding wordt opnieuw ingesteld.

**Oplossing:**

1. **Snelle diagnose:** Voer `curl -4 http://localhost:20128/v1/models` uit. Als dit met `-4` werkt, maar zonder niet, is er sprake van een niet-overeenkomende IPv6-binding.
2. **Permanente oplossing:** Bind expliciet aan IPv4 door `-p 127.0.0.1:20128:20128` te gebruiken in uw `docker run`-opdracht:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Dit dwingt de IPv4-binding af en voorkomt ook dat de proxy op alle hostinterfaces beschikbaar wordt gesteld.

## Instellingen voor veerkracht

### Automatische snelheidsbeperking wordt niet geactiveerd

- Automatische snelheidsbeperking is alleen van toepassing op providers met API-sleutels (niet op OAuth/abonnementen)
- Controleer of automatische snelheidsbeperking is ingeschakeld onder **Instellingen → Veerkracht → Providerprofielen**
- Controleer of de provider `429`-statuscodes of `Retry-After`-headers retourneert

### Exponentiële back-off afstemmen

Providerprofielen ondersteunen deze instellingen:

- **Basisvertraging** — Initiële wachttijd na de eerste fout (standaard: 1s)
- **Maximale vertraging** — Bovengrens voor de maximale wachttijd (standaard: 30s)
- **Vermenigvuldigingsfactor** — Hoeveel de vertraging per opeenvolgende fout wordt verhoogd (standaard: 2x)

### Voorkomen van een thundering herd

Wanneer veel gelijktijdige aanvragen bij een provider met snelheidsbeperking terechtkomen, gebruikt OmniRoute een mutex plus automatische snelheidsbeperking om aanvragen sequentieel af te handelen en kettingreacties van fouten te voorkomen. Dit gebeurt automatisch voor providers met API-sleutels.

### Chataanvragen mislukken met 503 / chat_admission_busy

**Symptomen:**

- Het endpoint voor chataanvullingen retourneert een opnieuw uitvoerbaar `503`-antwoord waarvan de foutcode
  `chat_admission_busy` is.
- Het antwoord bevat `Retry-After`. Sinds #12135 wordt de waarde afgeleid van de waargenomen
  bezetting — de grootste waarde van het `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`-venster waarin de aanvraag al
  heeft gewacht en de tijd dat de huidige zware leases al worden vastgehouden — naar boven afgerond op hele
  seconden en begrensd op 60. Bij een inactieve poort blijven de historische minimumwaarden gelden: 2 seconden voor het
  op bytes gebaseerde pad, 1 seconde voor het op structuur gebaseerde pad (dat ook
  `reason: "structure_limit"` bevat).
- Dit kan gebeuren terwijl een andere zware chataanvraag of langlopende streamingrespons nog
  wordt verwerkt.

De op bytes gebaseerde antwoordbody is:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Het op structuur gebaseerde antwoord gebruikt hetzelfde type en dezelfde code, met het bericht
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
en `reason: "structure_limit"`.
Bij de standaarddrempels is een aanvraag structureel zwaar wanneer deze ten minste `200` berichten,
ten minste `64` tools of ten minste `32,000` geschatte tokens bevat, of wanneer de begrensde structuurschatting
de limieten van `10,000` bezochte knooppunten of diepte `12` bereikt.

**Oorzaak:** Dit is opzettelijke afstoting van belasting binnen OmniRoute, geen fout bij een upstreamprovider.
Elk proces gebruikt een proceslokale beveiliging om beperkte capaciteit voor zware aanvragen te reserveren voordat
een grote aanvraagbody wordt bewaard en geparseerd. Een zware lease blijft gedurende de levensduur van een SSE-
antwoord actief.

**#503-fan-out:** vóór deze oplossing beperkte de beveiliging de gelijktijdigheid tot een vast AANTAL aanvragen
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, standaard `1`), ongeacht het hostgeheugen, waardoor fan-out van coding-agents
(meerdere subagents/CLI's, bodies die routinematig groter zijn dan 256 KB) instortte tot een effectieve
gelijktijdigheid van circa 1 en onder volkomen normale belasting 503-fouten veroorzaakte. De beveiliging stemt zichzelf nu af: deze wordt begrensd
door een automatisch afgeleid BYTE-budget voor gegevensinvoer (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), dat wordt
bepaald op basis van de werkelijke geheugenlimiet van het proces, en raadpleegt daarnaast een actueel signaal voor resourcebelasting — zodat
belasting alleen wordt afgestoten wanneer de host daadwerkelijk onder geheugendruk staat, en niet alleen omdat er meer dan één
zware aanvraag tegelijk binnenkwam. De oude limiet voor het aantal aanvragen (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) wordt
nog steeds gerespecteerd, maar alleen als u deze expliciet instelt.

Wanneer de capaciteit bezet is, wacht een zware aanvraag eerst maximaal
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (standaard `2000`; `0` schakelt het wachten uit) totdat er een plaats vrijkomt,
voordat de opnieuw uitvoerbare `503` wordt geretourneerd. De begrensde wachttijd bestaat zodat agentachtige clients
(OpenCode, Claude Code, Cursor) die gelijktijdig zware subaanvragen uitwaaieren, de piek sequentieel verwerken
in plaats van hun volledige budget voor nieuwe pogingen te verbruiken aan onmiddellijke afwijzingen en halverwege de taak te stoppen.
De huidige bezetting door zware leases, het vastgestelde bytebudget en de actuele ernst van de druk worden
weergegeven via `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — controleer deze voordat u een omgevingsvariabele wijzigt.
Instellingen → Veerkracht → Aanvraagwachtrij → Gelijktijdige aanvragen regelt dit niet; die instelling
beheert een afzonderlijk wachtrijmechanisme voor provideraanvragen.

**Oplossing:**

1. Probeer het eerst opnieuw. Clients moeten `Retry-After` respecteren en back-off gebruiken in plaats van de aanvraag onmiddellijk
   te herhalen.
2. Controleer `/api/monitoring/health` → `chatAdmission` voordat u iets afstemt. `countCapEnabled:
false` en een ruim `maxInflightBytes` betekenen dat het automatisch afgeleide budget al correct
   functioneert; een `pressureSeverity` van `high`/`critical` betekent dat de host daadwerkelijk weinig geheugen heeft —
   dit kan niet worden opgelost met een omgevingsvariabele voor toelating; er is meer RAM of een kleinere werklast nodig.
3. Alleen als `/api/monitoring/health` aangeeft dat het automatisch afgeleide budget daadwerkelijk te klein is voor
   uw host (zeldzaam — het schaalt al van containers tot bare-metal), overschrijft u het rechtstreeks met
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` in plaats van terug te vallen op de verouderde limiet voor het aantal aanvragen.

Raadpleeg de [referentie voor omgevingsvariabelen](../reference/ENVIRONMENT.md#4-security--authentication)
voor de gezaghebbende toelatingsinstellingen.

## Optionele RAG-/LLM-fouttaxonomie (16 problemen)

Sommige OmniRoute-gebruikers plaatsen de gateway vóór RAG- of agentstacks. In dergelijke configuraties komt vaak een vreemd patroon voor: OmniRoute lijkt in orde (providers beschikbaar, routeringsprofielen correct, geen waarschuwingen over snelheidslimieten), maar het uiteindelijke antwoord is toch onjuist.

In de praktijk worden deze incidenten meestal veroorzaakt door de achterliggende RAG-pijplijn en niet door de gateway zelf.

Als je een gedeelde terminologie wilt gebruiken om deze fouten te beschrijven, kun je de WFGY ProblemMap gebruiken. Dit is een externe tekstbron met een MIT-licentie die zestien terugkerende RAG-/LLM-foutpatronen definieert. Op hoofdlijnen behandelt deze:

- afwijkingen bij het ophalen en verbroken contextgrenzen
- lege of verouderde indexen en vectorstores
- discrepanties tussen embeddings en semantiek
- problemen met promptassemblage en contextvensters
- instortende logica en overmoedige antwoorden
- fouten in lange ketens en agentcoördinatie
- geheugen- en rolafwijkingen bij meerdere agents
- problemen met implementatie- en opstartvolgordes

Het idee is eenvoudig:

1. Leg bij het onderzoeken van een onjuist antwoord het volgende vast:
   - gebruikerstaak en verzoek
   - route- of providercombinatie in OmniRoute
   - eventuele achterliggende RAG-context (opgehaalde documenten, toolaanroepen enzovoort)
2. Koppel het incident aan een of twee WFGY ProblemMap-nummers (`No.1` … `No.16`).
3. Sla het nummer naast de OmniRoute-logboeken op in je eigen dashboard, runbook of incidenttracker.
4. Gebruik de bijbehorende WFGY-pagina om te bepalen of je de RAG-stack, retriever of routeringsstrategie moet aanpassen.

De volledige tekst en concrete recepten zijn hier beschikbaar (MIT-licentie, alleen tekst):

[README van WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Je kunt deze sectie negeren als je geen RAG- of agentpijplijnen achter OmniRoute uitvoert.

## Bekende problemen in v3.8.0

Problemen die specifiek zijn voor de v3.8.0-release en de huidige tijdelijke oplossingen ervoor. Als een oplossing in een latere patch wordt opgenomen, wordt de vermelding bijgewerkt of verwijderd.

### Authenticatiefouten met Devin CLI

**Symptomen:**

- "Devin CLI niet gevonden" of "authenticatie mislukt" bij het aanroepen van tools die Devin gebruiken
- De runtimecontrole van de CLI rapporteert `installed=false`

**Oorzaken:**

- `CLI_DEVIN_BIN` verwijst naar een pad dat niet bestaat
- Devin CLI is niet geïnstalleerd op de host

**Oplossing:**

1. Installeer Devin CLI voor je platform
2. Stel `CLI_DEVIN_BIN=/usr/local/bin/devin` (of het daadwerkelijke pad) in `.env` in
3. Start OmniRoute opnieuw en test nogmaals via **Dashboard → CLI-tools**

### Model blijft in cooldown (handmatige reset)

**Symptomen:**

- Een model blijft als in cooldown vermeld staan, zelfs nadat de verlooptijd is verstreken
- Verzoeken slaan het model bij combinatieroutering nog steeds over, hoewel het tijdstempel in het verleden ligt

**Handmatige reset:**

- **Dashboard:** **Instellingen → Modelcooldowns** → klik op **Opnieuw inschakelen** op de betreffende kaart
- **API:** `DELETE /api/resilience/model-cooldowns` met headers voor beheerauthenticatie

### Verbinding met Command Code-provider mislukt met 403

**Symptomen:**

- 403 bij het testen van de verbinding met de Command Code-provider
- De providerkaart toont "niet geautoriseerd" nadat deze opnieuw is toegevoegd

**Oorzaak:** De OAuth-flow is niet voltooid (callback niet ontvangen of token niet opgeslagen).

**Oplossing:**

- Voer `omniroute providers` uit via de CLI om de OAuth-flow opnieuw te starten, of
- Voer OAuth opnieuw uit via **Dashboard → Providers → Command Code → Opnieuw verbinden**

### ModelScope retourneert agressieve 429-cooldowns

**Symptomen:**

- Zeer korte of onmiddellijke cooldowns voor ModelScope na een kleine reeks verzoeken
- Combinatieroutering slaat ModelScope eerder over dan verwacht

**Oorzaak:** ModelScope verstuurt providerspecifieke `Retry-After`-headers. v3.8.0 bevat speciale verwerking voor deze headers, waardoor oudere versies ze ten onrechte interpreteren als algemene aanwijzingen voor snelheidslimieten.

**Oplossing:**

- Zorg ervoor dat je v3.8.0 of hoger gebruikt
- Controleer onder **Instellingen → Tolerantie** of de schakelaar `useUpstream429BreakerHints` is ingeschakeld

### OMNIROUTE_WS_BRIDGE_SECRET ontbreekt in productie

**Symptomen:**

- 401 bij elk Codex/Responses-WebSocket-bridgeverzoek wanneer dit op een externe productiehost wordt uitgevoerd
- De WebSocket-bridgehandshake wordt onmiddellijk na het verbinden afgesloten

**Oorzaak:** De omgevingsvariabele `OMNIROUTE_WS_BRIDGE_SECRET` ontbreekt in de productieomgeving.

**Oplossing:**

1. Genereer een willekeurig geheim: `openssl rand -hex 32`
2. Stel `OMNIROUTE_WS_BRIDGE_SECRET=<willekeurig-geheim>` in de omgeving van de productieserver in (en op elke client die met de bridge communiceert)
3. Start OmniRoute opnieuw

### Responses API: achtergrondmodus teruggevallen op synchrone uitvoering

**Symptomen:**

- Waarschuwing vastgelegd: `background mode degraded to synchronous`
- Een verzoek met `background: true` retourneert een normale synchrone respons in plaats van een achtergrondtaak-handle

**Oorzaak:** v3.8.0 laat `background: true` voor de Responses API bewust terugvallen op synchrone uitvoering en geeft daarbij een waarschuwing. Volledige asynchrone achtergronduitvoering wordt in de toekomst opgeleverd.

**Oplossing:**

- Pas de client aan zodat deze de aanroep zonder `background` uitvoert, of
- Wacht op een latere release met een volledige asynchrone achtergrondmodus (volg de changelog)

## Langzaam opstarten / time-out voor gereedheid

Als de CLI `⚠ Server did not respond within 60s` weergeeft terwijl de server
wel degelijk werkt, is het budget voor de gereedheidscontrole te kort voor uw omgeving.

Dit gebeurt vaak op Windows (antivirussoftware, bestandssysteemwatchers) of in containers
met zware werklasten tijdens het opstarten.

**Oplossing — verhoog het budget:**

```bash
# Via omgevingsvariabele (blijft behouden bij volgende starts):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuten
omniroute serve

# Via CLI-vlag (eenmalig):
omniroute serve --ready-timeout 180000
```

De standaardwaarde is 60 000 ms (60 s). De waarschuwing is uitsluitend informatief; de server
blijft op de achtergrond opstarten en is bereikbaar zodra het opstartproces is voltooid.

Zie [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) voor volledige
informatie over `OMNIROUTE_READY_TIMEOUT_MS`.
