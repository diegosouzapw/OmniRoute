**Nieuw bij OmniRoute?** Begin hier — hiermee los je 90% van de problemen op:

| Ik zie dit                      | Wat het betekent                               | Wat je moet doen                                                                                     |
| ------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| "Kan geen verbinding maken"     | OmniRoute wordt niet uitgevoerd                | Voer `omniroute` of `docker restart omniroute` uit                                                   |
| "Ongeldige API-sleutel"         | Je sleutel is onjuist of verlopen              | Kopieer de sleutel opnieuw vanaf de website van de provider                                          |
| "Frequentielimiet overschreden" | Je verstuurt te veel verzoeken                 | Wacht 1 minuut of gebruik `model: "auto"` voor automatische uitwijking                               |

## Gedetailleerde probleemoplossing

### Frequentiebeperking bij gratis providers (429 / 400 / 401)

**Symptoom**: Wanneer je `model: "auto"` gebruikt met gratis providers/providers zonder authenticatie (opencode, auggie, enzovoort), krijg je af en toe `HTTP 429`, `400` of `401` in plaats van antwoorden. De verzoeken slagen wanneer je dezelfde prompt kort daarna opnieuw probeert, maar automatisering (cron-taken, agents, scripts) stopt bij de eerste fout.

**Hoofdoorzaak**: Drie onafhankelijke foutmodi stapelen zich op:

1. **Frequentielimiet van de provider (`429`)**: Gratis abonnementen kunnen een quotum per tijdsvenster afdwingen. Een piek van parallelle aanroepen put dit uit, waardoor het volgende verzoek wordt geweigerd totdat het venster opnieuw wordt ingesteld.
2. **Defect model bij passthrough (`400`/`401`)**: `auto/*`-pools kunnen passthrough-modellen van `opencode` bevatten die in de catalogus zijn geregistreerd, maar geen actieve aanmeldgegevens hebben (bijvoorbeeld `oc/north-mini-code-free` → `401`). De automatische router probeert er één, faalt, en de fout wordt doorgegeven voordat de uitwijking wordt geactiveerd.
3. **Versterking door gelijktijdigheid (`429` onder belasting)**: Wanneer meerdere agent-/cron-sessies tegelijk `auto` aanspreken, overschrijdt de totale aanvraagsnelheid wat gratis providers tolereren, waardoor legitieme aanroepen als misbruik worden aangemerkt.

**Geverifieerde oplossing (gemeld door de community, 2026-08-10)**: stel drie omgevingsvariabelen zo in dat rotatie, gelijktijdigheid en uitwijking de wisselvalligheid van gratis abonnementen opvangen in plaats van erop vast te lopen:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # ga bij 400/401 naar een ander model/een andere provider (slaat defecte passthrough-modellen over)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # expliciete toelatingslimiet voor zware verzoeken (standaard niet ingesteld: geen limiet voor het aantal verzoeken, zie opmerking hieronder)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # verhoog de begrensde wachttijd tot boven de standaardwaarde van RATE_LIMIT_MAX_WAIT_MS voor trage upstreams
```

Stel deze in binnen de procesomgeving van OmniRoute (de daemon, bijvoorbeeld via het LaunchAgent-plist-bestand of `systemctl edit`) en start OmniRoute vervolgens opnieuw. De rotatievlag heeft de grootste impact: deze zet een harde fout om in een transparante nieuwe poging bij een gezonde provider in de pool.

**Opmerking**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` beperkt hoeveel zware — long-context — verzoeken tegelijk worden uitgevoerd; de limiet is een toelatingspoort, geen frequentielimiet van een provider. **Update voor #503-fanout:** deze variabele wordt niet langer standaard ingesteld (de limiet geldt nu alleen wanneer deze expliciet wordt geconfigureerd, zoals hierboven) — de toelating van zware verzoeken wordt in plaats daarvan geregeld door een automatisch afgeleid bytebudget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) dat zichzelf schaalt op basis van de werkelijke geheugenlimiet van de host. Een nieuwe implementatie zou daardoor veel minder afwijzingen met `503 chat_admission_busy` moeten opleveren zonder dat deze variabele hoeft te worden ingesteld; expliciet instellen zoals hier beschreven werkt nog steeds precies zoals gedocumenteerd. Expliciete overschrijvingen van het bytebudget worden begrensd op 8 MiB–2 GiB. Een `413 body_exceeds_budget` is niet tijdelijk: verhoog dat bytebudget, verlaag `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` of verhoog de geheugenlimiet van het proces. Een afwijzing wegens `inflight_bytes_budget` is tijdelijke contention en kan opnieuw worden geprobeerd. De frequentiebeperking per provider (`open-sse/services/rateLimitManager.ts`) wordt afzonderlijk beheerd door `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` en `RATE_LIMIT_AUTO_ENABLE` — zie `.env.example`.

**Zo controleert u of het werkt**: voer uw agent/cron twee keer kort na elkaar uit en controleer of beide uitvoeringen slagen. Vóór de oplossing geeft de tweede uitvoering doorgaans een `429`/`401`-fout. Na de oplossing worden fouten (indien aanwezig) automatisch opnieuw geprobeerd en wordt de aanroep voltooid. U kunt ook `curl /monitoring/health` uitvoeren en het veld `rateLimitedUntil` bij de providerverbindingen en `circuitBreakers.providerBreakers[].state` voor de betrokken providers controleren — de status is `CLOSED`, `DEGRADED`, `OPEN` of `HALF_OPEN` (zie `src/shared/utils/circuitBreaker.ts`), en een provider die fouten blijft geven, schakelt van `CLOSED → DEGRADED → OPEN` voordat na het resetvenster een testaanroep wordt doorgelaten (`HALF_OPEN`).

**Als u nog steeds 429 ziet**: het actieve account voor die provider heeft daadwerkelijk zijn _quotum_ opgebruikt (niet alleen de frequentielimiet bereikt). Voeg in het OmniRoute-dashboard via Providers → Accounts een tweede account voor dezelfde provider toe, of voeg een andere gratis provider toe (bijvoorbeeld `routeway`, `auggie`). Rotatie helpt alleen bij tijdelijke frequentielimieten/400/401-fouten; als het quotum volledig is opgebruikt, is een tweede set inloggegevens of een andere provider vereist.

**Als u 403 ziet bij vision-modellen (`auto/vision`, `bazaarlink/*`)**: het verbonden account heeft geen betaald abonnement dat vision ondersteunt, of de API-sleutel heeft onvoldoende machtigingen. Controleer in het providerdashboard of de scope van de sleutel vision/multimodal omvat, of koppel een account met een betaald abonnement en behoud dit als vision-doel.

## npm install-waarschuwingen (ERESOLVE / peer / deprecated)

Wanneer u `npm install -g omniroute` uitvoert, ziet u mogelijk een hele reeks waarschuwingen, zoals `npm warn ERESOLVE`, meldingen over peer-afhankelijkheden en `deprecated`-berichten. **Deze zijn te verwachten en onschadelijk.** Uw installatie is geslaagd als u `added <N> packages` in de uitvoer ziet.

Gebruik de door OmniRoute ondersteunde installatievorm om waarschuwingen over het oplossen van peer-afhankelijkheden te onderdrukken:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` onderdrukt alleen `ERESOLVE` en meldingen over peer-afhankelijkheden. Meldingen over verouderde pakketten blijven zichtbaar omdat ze afkomstig zijn van transitieve pakketten van derden; ze betekenen niet dat de installatie is mislukt.

De waarschuwingen worden veroorzaakt door verouderde versiebereiken voor peer-afhankelijkheden in pakketten van derden waarover OmniRoute geen controle heeft:

1. **`marked-terminal` vereist `marked >=1 <16`, maar `marked@18` is gevonden** — werkt in de praktijk prima; het upstream-versiebereik voor de peer-afhankelijkheid is simpelweg verouderd.
2. **`deprecated prebuild-install@7.1.3`** — een transitieve helper voor het ophalen van native binaire bestanden. Deze wordt niet
   gebruikt om de vastgezette `wreq-js`-transportbinding te installeren en betekent niet dat de transportconfiguratie
   van de web-cookieprovider is mislukt.

**Geen actie nodig** — de waarschuwingen kunnen niet volledig worden onderdrukt zonder upstream-pakketten te forken.

## Waarschuwing voor geblokkeerde npm-installatiescripts (globale installatie)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

Wanneer u `npm install -g omniroute` uitvoert, blokkeren nieuwere npm-versies (v11+ en v12+) standaard pakketlevenscyclusscripts en tonen ze een waarschuwing over installatiescripts:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Kan deze waarschuwing worden genegeerd?

**Gedeeltelijk, maar uitvoering zonder scripts wordt niet aanbevolen.** OmniRoute bevat robuuste terugvalopties: als native `better-sqlite3`-bindingen niet vanuit de zelfstandige bundel kunnen worden geladen, valt de toepassing terug op alternatieve stuurprogramma's, zoals `node:sqlite` of `sql.js` (zie [SQLite-runtimebepaling](../ops/SQLITE_RUNTIME.md)). De server wordt nog steeds gestart, maar het gebruik van WASM-terugvalopties zoals `sql.js` schakelt de WAL-modus (Write-Ahead Logging) van SQLite uit en verhoogt het geheugen- en schijfsynchronisatiegebruik.

### Welke scripts zijn daadwerkelijk vereist?

Niet alle geblokkeerde scripts zijn essentieel voor het uitvoeren van OmniRoute:

- **Essentieel (`omniroute`, `better-sqlite3`):** OmniRoute wordt uitgevoerd vanuit een zelfstandige Next.js-toepassingsbundel (`dist/`). Tijdens de installatie downloadt of compileert npm het hostspecifieke native SQLite-stuurprogramma in `node_modules/better-sqlite3/` op het hoogste niveau. Het `postinstall`-script van OmniRoute (`scripts/build/postinstall.mjs`) verifieert en kopieert deze hostspecifieke binaire bestanden vervolgens naar `dist/node_modules/`, zodat de zelfstandige server er toegang toe heeft. Als het postinstall-script van `omniroute` wordt geblokkeerd, wordt deze kopieerstap overgeslagen.
- **Optioneel/transitief (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** Dit zijn bouwhulpmiddelen, bewakingstools of hulpprogramma's voor de systeem-sleutelhanger. Door ze toe te staan, voorkomt u buildwaarschuwingen, maar ze zijn niet vereist voor de belangrijkste routeringsfunctionaliteit.
- **Uitgesloten (`onnxruntime-node`):** Een optionele afhankelijkheid voor lokale AI-embeddings die **niet** vereist is om OmniRoute uit te voeren. Het postinstall-script downloadt ongeveer 300 MB aan CUDA-onderdelen van NuGet; voeg dit pakket niet toe aan de lijst met toegestane pakketten, tenzij u expliciet lokale ONNX-versnelling op ondersteunde hardware wilt gebruiken.

### Aanbevolen oplossing

Geef `--allow-scripts` door voor OmniRoute en de native afhankelijkheden om de vereiste installatiescripts tijdens een globale installatie toe te staan en waarschuwingen te onderdrukken:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

U kunt dit ook permanent configureren voor alle globale installaties onder uw gebruikersaccount:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### Controleer uw installatie

Voer na de installatie het ingebouwde diagnosehulpmiddel uit om te controleren of de native bindingen en de runtimeomgeving correct werken:

```bash
omniroute doctor
```

## Valse positieven van antivirussoftware

<a name="antivirus-false-positives"></a>

### Avast/AVG plaatst `README.md` in quarantaine met `MD:HttpRequest-inf[Susp]`

**Dit is een vals positief resultaat. Niets is geïnfecteerd en er is geen actie vereist.**

Avast en AVG gebruiken een heuristische detectie die platte tekst-/Markdown-bestanden markeert die veel
links bevatten die op HTTP-verzoeken lijken. OmniRoute's `README.md` wordt meegeleverd in het npm-pakket (het
staat vermeld in `package.json` → `files`), waardoor het bij een globale installatie terechtkomt in
`node_modules/omniroute/README.md` — en het bevat ongeveer 15 voorbeelden met `http://localhost:20128/...`
(de MCP HTTP/SSE-eindpunten, de A2A-URL onder `.well-known` en `curl`-fragmenten). Die hoeveelheid links is
voldoende om de heuristische detectie te activeren.

Als dit pas onlangs is begonnen: het soort bestand is niet veranderd. De tabel met eindpunten in de README is
uitgebreid (MCP HTTP + SSE + A2A zijn toegevoegd), evenals het aantal `curl`-voorbeelden, waardoor
de drempel werd overschreden.

Het bestand is passieve documentatie zonder uitvoerbare inhoud. U kunt het veilig herstellen
vanuit quarantaine.

**Wat te doen:**

1. **Stop de meldingen** — sluit de installatiemap uit in uw antivirussoftware
   (Avast: Instellingen → Uitzonderingen) door het pad naar uw globale `node_modules` en/of de
   OmniRoute-gegevensmap (`~/.omniroute/`) toe te voegen.
2. **Meld het valse positieve resultaat** — <https://www.avast.com/false-positive-file-form.php>
   en voeg het in quarantaine geplaatste `README.md` toe. Dit is de oplossing die iedereen helpt, aangezien het
   de heuristische detectie van de leverancier is die te sterk reageert op een tekstbestand.

**Waarom we dit niet aan onze kant "oplossen":** alle voorbeelden gebruiken `http://localhost`, en
localhost kan niet zonder problemen met zelfondertekende certificaten via `https` worden gebruikt. De documentatie
verminken om de heuristische detectie van één leverancier te omzeilen, zou iedere lezer benadelen om een fout in een scanner
tegemoet te komen.

### Kaspersky markeert de desktop-app als `PDM:Trojan.Win32.Generic`

**Dit is een vals positief resultaat van een gedragsheuristiek. Niets is geïnfecteerd.** Het
voorvoegsel `PDM:` van Kaspersky betekent dat het oordeel afkomstig is van de Proactive Defense Module (System Watcher),
die beoordeelt wat het installatieprogramma _doet_ in plaats van het te vergelijken met bekende malware. Wanneer
de detectie wordt geactiveerd, draait Kaspersky de volledige installatie "terug" — waarbij bestanden worden verwijderd die al
waren geschreven — waardoor de app beschadigd raakt of verdwijnt.

De bestanden die worden gemarkeerd, zijn standaardonderdelen van opgegeven opensource-afhankelijkheden die met de
desktop-app zijn gebundeld, bijvoorbeeld:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` en
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), de bibliotheek voor browserautomatisering
  die wordt gebruikt voor het aanmelden bij providers vanuit de app en voor chat via een browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — de vastgezette native binding van `wreq-js` die wordt gebruikt voor HTTP met een browservingerafdruk bij providers
  die webcookies gebruiken (`<arch>` is `x64` of `arm64`).

**Waarom dit wordt geactiveerd:** het Windows-installatieprogramma is **nog niet digitaal ondertekend**, waardoor een niet-ondertekend NSIS-
installatieprogramma geen reputatie heeft en gedragsheuristieken maximaal agressief worden uitgevoerd. In combinatie
met een gebundelde native DLL en honderden `.js`-bestanden die onder
`%LOCALAPPDATA%\Programs\OmniRoute` worden geschreven (waaronder pakketmappen met hash-achtervoegsels uit de
zelfstandige Next.js-build), is dat voldoende om de heuristische detectie te activeren. Codeondertekening staat gepland;
totdat dit is geïmplementeerd, kan dit bij nieuwe releases opnieuw gebeuren.

**Wat te doen:**

1. **Verifieer eerst uw download** (om een gemanipuleerd bestand uit te sluiten). Bij iedere release wordt
   `latest.yml` gepubliceerd, waarvan het veld `sha512` (base64) betrekking heeft op het installatieprogramma
   `OmniRoute.Setup.<version>.exe`. Voer in PowerShell, vanuit de map met het installatieprogramma, het volgende uit:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   De uitvoer moet overeenkomen met `latest.yml` → `sha512`. Als dit niet het geval is, verwijdert u het bestand en
   downloadt u het opnieuw, uitsluitend vanaf de [GitHub-releasepagina](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Herstel + sluit uit** — herstel de teruggedraaide items vanuit quarantaine en voeg een uitsluiting
   toe voor `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Instellingen → Bedreigingen en uitsluitingen),
   en installeer vervolgens opnieuw.
3. **Meld het valse positieve resultaat** — <https://opentip.kaspersky.com/>. Door gebruikers ingediende meldingen van
   valse positieven versnellen het toevoegen aan de toelatingslijst daadwerkelijk.

## Node.js-compatibiliteit

<a name="nodejs-compatibility"></a>

### Inlogpagina crasht of toont de foutmelding "Module self-registration"

**Oorzaak:** U gebruikt een Node.js-versie die buiten de door OmniRoute goedgekeurde veilige runtimegrenzen valt. Meestal gaat het om een oudere patchversie van Node 22 of 24 die onder de door OmniRoute vereiste beveiligde minimumversie valt.

**Symptomen:**

- De inlogpagina toont een leeg scherm of een serverfout
- De console toont `Error: Module did not self-register` of vergelijkbare fouten met native bindings
- De inlogpagina toont een **oranje waarschuwingsbanner** met uw Node-versie als de runtime buiten het ondersteunde beveiligingsbeleid valt

**Oplossing:**

1. Installeer een ondersteunde Node.js LTS-release (aanbevolen: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Controleer uw versie: `node --version` moet `v24.0.0` of nieuwer binnen de 24.x LTS-reeks tonen
3. Installeer OmniRoute opnieuw: `npm install -g omniroute`
4. Start opnieuw: `omniroute`

> **Ondersteunde veilige versies:** `>=22.22.2 <23` of `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) en Node.js 26 worden volledig ondersteund.

### npm v11+: `better-sqlite3` niet geïnstalleerd (module kan niet worden gevonden)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Oorzaak:** npm v11 (meegeleverd met Node.js 24+) blokkeert standaard installatiescripts voor optionele
afhankelijkheden. Omdat `better-sqlite3` in `optionalDependencies` staat
en native compilatie (`node-gyp rebuild`) vereist, slaat npm dit stilzwijgend over.

**Symptomen:**

- De server crasht tijdens het opstarten met `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` toont "No such file or directory"
- `npm ls better-sqlite3` toont `(empty)`

**Oplossing:**

1. Keur de installatiescripts goed en installeer opnieuw:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Of installeer het vooraf gebouwde pakket handmatig:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Controleer of het werkt: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Oorzaak:** Na een globale `npm install -g omniroute` kan het native binaire bestand van `better-sqlite3` in het pakket zijn gecompileerd voor een andere architectuur of Node.js-ABI dan lokaal wordt uitgevoerd. Dit komt vaak voor op macOS (zowel Apple Silicon als Intel) wanneer het vooraf gebouwde binaire bestand niet overeenkomt met uw omgeving.

**Symptomen:**

- De server stopt direct tijdens het opstarten met een `dlopen`-fout
- De fout bevat `slice is not valid mach-o file`
- Volledig voorbeeld:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Oplossing — opnieuw compileren voor uw lokale omgeving (geen downgrade van Node.js vereist):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Opmerking:** Hiermee wordt de native binding opnieuw gecompileerd voor uw lokale Node.js-versie en CPU-architectuur, waardoor het probleem met het niet-overeenkomende binaire bestand wordt opgelost. Het officieel ondersteunde runtimebereik is **`>=22.22.2 <23` of `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` in `src/shared/utils/nodeRuntimeSupport.ts`, afgestemd op het veld `engines` in `package.json`). Node.js 24.x LTS (Krypton) en Node.js 26 worden volledig ondersteund met `better-sqlite3` v12.x.

## Proxyproblemen

<a name="proxy-issues"></a>

### Providervalidatie geeft "fetch failed" weer

**Oorzaak:** Het validatie-eindpunt voor API-sleutels (`POST /api/providers/validate`) omzeilde voorheen de proxyconfiguratie, waardoor fouten optraden in omgevingen waarin proxyroutering vereist is.

**Oplossing (v3.5.5+):** Dit is nu opgelost. Providervalidatie wordt via `runWithProxyContext` gerouteerd, waarbij proxy-instellingen op provider- en globaal niveau automatisch worden gerespecteerd.

### Tokenstatuscontrole mislukt met "fetch failed"

**Oorzaak:** Bij het op de achtergrond vernieuwen van OAuth-tokens werd de proxyconfiguratie niet per verbinding bepaald.

**Oplossing (v3.5.5+):** De planner voor tokenstatuscontroles bepaalt nu vóór elke vernieuwingspoging de proxyconfiguratie per verbinding. Werk bij naar v3.5.5+.

### SOCKS5-proxy geeft "invalid onRequestStart method" als resultaat

**Oorzaak:** In Node.js 22 is de dispatcher van undici@8 niet compatibel met de ingebouwde implementatie van `fetch()` in Node.

**Oplossing (v3.5.5+):** OmniRoute gebruikt nu de eigen functie `fetch()` van undici wanneer een proxydispatcher actief is, wat consistent gedrag garandeert. Werk bij naar v3.5.5+.

### MITM-proxy onder WSL: desktop-apps op de Windows-host worden niet onderschept

**Oorzaak:** De MITM-proxy en het bijbehorende CA-certificaat worden geïnstalleerd in de omgeving waarin OmniRoute wordt uitgevoerd. Onder WSL is die omgeving de Linux-gast, terwijl de AI-desktop-apps (Kiro, Trae, Copilot, Zed, …) op de Windows-host worden uitgevoerd. De host-apps vertrouwen het certificaatarchief van de gast niet en routeren niet via de systeemproxy van de gast. Daardoor worden desktopverbindingen daar niet onderschept.

**Aanbeveling:** Voer OmniRoute rechtstreeks uit op hetzelfde besturingssysteem als de desktop-apps die u wilt onderscheppen (Windows voor Windows-apps; hetzelfde geldt voor macOS/Linux). Als u OmniRoute binnen WSL laat draaien terwijl u host-apps als doel gebruikt, moet u het gegenereerde CA-certificaat handmatig vertrouwen op de Windows-host en de netwerk-/proxy-instellingen van elke host-app naar het WSL-proxy-eindpunt laten verwijzen — een niet-ondersteunde, kwetsbare configuratie.

**Oplossing:**

2. Gebruik een combinatie met terugvalniveaus

**Oplossing:**

OmniRoute vernieuwt tokens automatisch. Als de problemen aanhouden:

1. Dashboard → Provider → Opnieuw verbinden

### Meerdere Kiro-accounts: het tweede account maakt het eerste ongeldig

**Oorzaak:** De backend van Kiro staat slechts één actieve sessie per OIDC-clientregistratie toe.
Wanneer twee accounts dezelfde geregistreerde client delen (verbindingen die vóór v3.8.0 zijn geïmporteerd),
maakt het vernieuwen van het token van het ene account het vernieuwingstoken van het andere account ongeldig.

**Oplossing (v3.8.0+):** Importeer de betrokken verbindingen opnieuw.

**sociale aanmelding met Google/GitHub** of **Automatisch importeren** wordt aangemaakt, automatisch een eigen
specifieke OIDC-client. De verbinding is daardoor volledig geïsoleerd en het vernieuwen van het ene
account heeft geen invloed op andere accounts.

Verbindingen die _vóór_ v3.8.0 zijn geïmporteerd, hebben geen clientregistratie per verbinding.
Die verbindingen blijven het gedeelde vernieuwingseindpunt voor sociale authenticatie gebruiken.
Om isolatie te verkrijgen, verwijdert u de oude verbinding via Dashboard → Providers en voegt u deze opnieuw toe
via een van de drie importmethoden.

Raadpleeg voor volledige details en stapsgewijze instructies voor het naast elkaar toevoegen van twee Kiro-accounts
[`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Docker-problemen

### Docker IPv6 / Verbinding opnieuw ingesteld

<a name="docker-ipv6"></a>

**Symptomen:** `curl http://localhost:20128/v1/models` retourneert `curl: (56) Recv failure: Connection reset by peer`. Het dashboard en niet-geverifieerde eindpunten werken, maar geverifieerde eindpunten mislukken — het lijkt op een authenticatieprobleem, maar dat is het niet.

**Oorzaak:** `docker run -p 20128:20128` publiceert op zowel `0.0.0.0` (IPv4) als `::` (IPv6), maar het proces in de container luistert alleen op IPv4. Op hosts waar `localhost` eerst naar `::1` wordt omgezet, komt de verbinding terecht op de gepubliceerde IPv6-poort zonder achterliggende listener → verbinding opnieuw ingesteld.

**Oplossing:**

1. **Snelle diagnose:** Voer `curl -4 http://localhost:20128/v1/models` uit. Als dit met `-4` werkt, maar zonder niet, is er sprake van een niet-overeenkomende IPv6-binding.
2. **Permanente oplossing:** Bind expliciet aan IPv4 door `-p 127.0.0.1:20128:20128` te gebruiken in uw `docker run`-opdracht:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Dit dwingt de IPv4-binding af en voorkomt ook dat de proxy op alle hostinterfaces wordt blootgesteld.

## Problemen met de circuit breaker

### Provider blijft hangen in de status OPEN

Wanneer de circuit breaker van een provider OPEN is, worden verzoeken geblokkeerd totdat de afkoelperiode is verstreken.

**Oplossing:**

1. Ga naar **Dashboard → Settings → Resilience**
2. Controleer de circuit-breakerkaart voor de betreffende provider
3. Klik op **Reset All** om alle circuit breakers te resetten, of wacht totdat de afkoelperiode is verstreken
4. Controleer of de provider daadwerkelijk beschikbaar is voordat u deze reset

### Provider activeert de circuit breaker steeds opnieuw

Als een provider herhaaldelijk de status OPEN krijgt:

1. Controleer **Dashboard → Health → Provider Health** om het foutpatroon te bekijken
2. Ga naar **Settings → Resilience → Provider Profiles** en verhoog de foutdrempel
3. Controleer of de provider de API-limieten heeft gewijzigd of opnieuw authenticatie vereist
4. Bekijk de latentietelemetrie — hoge latentie kan fouten door time-outs veroorzaken

## Instellingen voor veerkracht

### Automatische snelheidsbeperking wordt niet geactiveerd

- Automatische snelheidsbeperking is alleen van toepassing op providers met API-sleutels (niet op OAuth/abonnementen)
- Controleer of automatische snelheidsbeperking is ingeschakeld onder **Settings → Resilience → Provider Profiles**
- Controleer of de provider `429`-statuscodes of `Retry-After`-headers retourneert

### Exponentiële back-off afstemmen

Providerprofielen ondersteunen de volgende instellingen:

- **Base delay** — Initiële wachttijd na de eerste fout (standaard: 1s)
- **Max delay** — Maximale wachttijd (standaard: 30s)
- **Multiplier** — Hoeveel de wachttijd per opeenvolgende fout wordt verhoogd (standaard: 2x)

### Voorkomen van een thundering herd

Wanneer veel gelijktijdige verzoeken een provider met snelheidsbeperking bereiken, gebruikt OmniRoute een mutex en automatische snelheidsbeperking om verzoeken sequentieel te verwerken en opeenvolgende fouten te voorkomen. Dit gebeurt automatisch voor providers met API-sleutels.

### Chatverzoeken mislukken met 503 / chat_admission_busy

**Symptomen:**

- Het eindpunt voor chataanvullingen retourneert een opnieuw te proberen `503`-antwoord met de foutcode
  `chat_admission_busy`.
- Het antwoord bevat `Retry-After`. Sinds #12135 wordt de waarde afgeleid van de waargenomen
  bezetting: de grootste waarde van het `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`-venster waarin het verzoek al
  heeft gewacht en de tijd dat de huidige zwaargewichtleases zijn vastgehouden, naar boven afgerond op hele
  seconden en begrensd op 60. Bij een niet-belaste poort blijven de historische minimumwaarden gelden: 2 seconden voor het
  op bytes gebaseerde pad en 1 seconde voor het op structuur gebaseerde pad (dat ook
  `reason: "structure_limit"` bevat).
- Dit kan gebeuren terwijl een andere zwaargewichtchat of langlopende streamingrespons nog
  wordt verwerkt.

De op bytes gebaseerde antwoordbody is:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Het op structuur gebaseerde antwoord gebruikt hetzelfde type en dezelfde code, met het bericht
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
en `reason: "structure_limit"`.
Bij de standaarddrempelwaarden is een verzoek structureel zwaar wanneer het ten minste `200` berichten,
ten minste `64` tools of ten minste `32,000` geschatte tokens bevat, of wanneer de begrensde structuurschatting
de limieten van `10,000` bezochte knooppunten of een diepte van `12` bereikt.

**Oorzaak:** Dit is doelbewuste afschaling van belasting binnen OmniRoute, geen fout van een upstreamprovider.
Elk proces gebruikt een proceslokale bewaking om beperkte zwaargewichtcapaciteit te reserveren voordat
een grote verzoekbody wordt vastgehouden en geparseerd. Een zwaargewichtlease blijft gedurende de volledige levensduur van een SSE-
antwoord vastgehouden.

**#503-fanout:** vóór deze oplossing beperkte de bewaking de gelijktijdigheid tot een vast AANTAL verzoeken
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, standaard `1`), ongeacht het geheugen van de host. Daardoor werd
fan-out van coding-agents (meerdere subagents/CLI's, met bodies die doorgaans > 256 KB zijn) teruggebracht tot een effectieve
gelijktijdigheid van ongeveer 1 en resulteerde dit bij volkomen normale belasting in 503-fouten. De bewaking stemt zichzelf nu af: deze wordt aangestuurd
door een automatisch afgeleid BYTE-budget voor ingestie (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), dat wordt bepaald op basis van de
werkelijke geheugenlimiet van het proces. Daarnaast raadpleegt de bewaking een actueel signaal voor resourcebelasting, zodat
alleen wordt afgeschaald wanneer de host daadwerkelijk onder geheugendruk staat, en niet alleen omdat meer dan één
zwaar verzoek tegelijk is binnengekomen. De oude limiet voor het aantal verzoeken (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) wordt
nog steeds gerespecteerd, maar alleen als u deze expliciet instelt.

Wanneer de capaciteit bezet is, wacht een zwaargewichtverzoek eerst maximaal
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (standaard gelijk aan `RATE_LIMIT_MAX_WAIT_MS`; `0` schakelt het wachten uit) totdat er een plaats vrijkomt,
voordat het opnieuw te proberen `503`-antwoord wordt gegeven. De begrensde wachttijd bestaat zodat agentgebaseerde clients
(OpenCode, Claude Code, Cursor) die gelijktijdig zware subverzoeken uitwaaieren, de piek sequentieel verwerken
in plaats van hun volledige budget voor nieuwe pogingen te verspillen aan onmiddellijke afwijzingen en halverwege de taak te stoppen.
De huidige bezetting door zwaargewichtleases, het berekende bytebudget en de actuele ernst van de belasting zijn
beschikbaar via `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — controleer deze voordat u een omgevingsvariabele wijzigt.
Settings → Resilience → Request Queue → Concurrent Requests regelt dit niet; die instelling
beheert een afzonderlijk mechanisme voor de verzoekwachtrij van providers.

**Oplossing:**

1. Probeer het eerst opnieuw. Clients moeten `Retry-After` respecteren en back-off gebruiken in plaats van het verzoek onmiddellijk
   opnieuw te verzenden.
2. Controleer `/api/monitoring/health` → `chatAdmission` voordat u iets afstemt. `countCapEnabled:
false` en een ruim `maxInflightBytes` betekenen dat het automatisch afgeleide budget al correct
   werkt; een `pressureSeverity` van `high`/`critical` betekent dat de host daadwerkelijk weinig geheugen heeft —
   dit kan niet worden opgelost met een omgevingsvariabele voor toelating; er is meer RAM of een kleinere werkbelasting nodig.
3. Alleen als `/api/monitoring/health` aangeeft dat het automatisch afgeleide budget daadwerkelijk te klein is voor
   uw host (zeldzaam — het schaalt al van containers tot bare-metal), overschrijft u dit rechtstreeks met
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` in plaats van terug te vallen op de verouderde limiet voor het aantal verzoeken.

Raadpleeg de [referentie voor omgevingsvariabelen](../reference/ENVIRONMENT.md#4-security--authentication)
voor de gezaghebbende toelatingsinstellingen.

## Optionele RAG-/LLM-fouttaxonomie (16 problemen)

Sommige OmniRoute-gebruikers plaatsen de gateway vóór RAG- of agentstacks. In die configuraties komt vaak een vreemd patroon voor: OmniRoute lijkt correct te werken (providers beschikbaar, routeringsprofielen in orde, geen waarschuwingen over snelheidslimieten), maar het uiteindelijke antwoord is toch onjuist.

In de praktijk worden deze incidenten meestal veroorzaakt door de achterliggende RAG-pijplijn, niet door de gateway zelf.

Als je een gedeelde terminologie wilt gebruiken om die fouten te beschrijven, kun je de WFGY ProblemMap gebruiken. Dit is een externe tekstbron met een MIT-licentie die zestien terugkerende foutpatronen voor RAG/LLM definieert. Op hoofdlijnen behandelt deze:

- afwijkingen bij het ophalen en verbroken contextgrenzen
- lege of verouderde indexen en vectorstores
- discrepanties tussen embeddings en semantiek
- problemen met promptopbouw en contextvensters
- instortende logica en overmoedige antwoorden
- fouten in lange ketens en agentcoördinatie
- geheugen- en rolafwijkingen bij meerdere agents
- problemen met de volgorde van implementatie en initialisatie

Het idee is eenvoudig:

1. Leg bij het onderzoeken van een onjuist antwoord het volgende vast:
   - gebruikerstaak en verzoek
   - route- of providercombinatie in OmniRoute
   - alle RAG-context die verderop in de keten is gebruikt (opgehaalde documenten, toolaanroepen enzovoort)
2. Koppel het incident aan één of twee nummers uit de WFGY ProblemMap (`No.1` … `No.16`).
3. Sla het nummer naast de OmniRoute-logboeken op in je eigen dashboard, runbook of incidenttracker.
4. Gebruik de bijbehorende WFGY-pagina om te bepalen of je je RAG-stack, retriever of routeringsstrategie moet wijzigen.

De volledige tekst en concrete recepten zijn hier beschikbaar (MIT-licentie, alleen tekst):

[README van WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Je kunt deze sectie negeren als je geen RAG- of agentpijplijnen achter OmniRoute uitvoert.

## Bekende problemen in v3.8.0

Problemen die specifiek zijn voor de v3.8.0-release en de huidige tijdelijke oplossingen ervoor. Als een oplossing in een latere patch wordt uitgebracht, wordt het item bijgewerkt of verwijderd.

### Authenticatiefouten met Devin CLI

**Symptomen:**

- "Devin CLI niet gevonden" of "authenticatie mislukt" bij het aanroepen van tools die Devin gebruiken
- De CLI-runtimecontrole meldt `installed=false`

**Oorzaken:**

- `CLI_DEVIN_BIN` verwijst naar een pad dat niet bestaat
- Devin CLI is niet geïnstalleerd op de host

**Oplossing:**

1. Installeer Devin CLI voor je platform
2. Stel `CLI_DEVIN_BIN=/usr/local/bin/devin` (of het werkelijke pad) in `.env` in
3. Start OmniRoute opnieuw en test nogmaals via **Dashboard → CLI-tools**

### Model blijft in afkoelperiode staan (handmatige reset)

**Symptomen:**

- Een model blijft als in afkoelperiode vermeld staan, zelfs nadat de vervaltijd is verstreken
- Verzoeken slaan het model bij combinatieroutering nog steeds over, hoewel het tijdstip in het verleden ligt

**Handmatige reset:**

- **Dashboard:** **Instellingen → Afkoelperioden voor modellen** → klik op **Opnieuw inschakelen** op de betreffende kaart
- **API:** `DELETE /api/resilience/model-cooldowns` met headers voor beheerauthenticatie

### Verbinding met Command Code-provider mislukt met 403

**Symptomen:**

- 403 bij het testen van de verbinding met de Command Code-provider
- De providerkaart toont "niet geautoriseerd" nadat de provider opnieuw is toegevoegd

**Oorzaak:** De OAuth-flow is niet voltooid (callback niet ontvangen of token niet opgeslagen).

**Oplossing:**

- Voer `omniroute providers` uit via de CLI om de OAuth-flow opnieuw te activeren, of
- Voer OAuth opnieuw uit via **Dashboard → Providers → Command Code → Opnieuw verbinden**

### ModelScope retourneert agressieve 429-afkoelperioden

**Symptomen:**

- Zeer korte of onmiddellijke afkoelperioden bij ModelScope na een kleine piek in het aantal verzoeken
- Combinatieroutering slaat ModelScope eerder over dan verwacht

**Oorzaak:** ModelScope verzendt providerspecifieke `Retry-After`-headers. v3.8.0 bevat specifieke verwerking voor deze headers, waardoor oudere versies ze verkeerd interpreteren als algemene indicaties voor snelheidslimieten.

**Oplossing:**

- Zorg ervoor dat je v3.8.0 of later gebruikt
- Controleer onder **Instellingen → Veerkracht** of de schakeloptie `useUpstream429BreakerHints` is ingeschakeld

### OMNIROUTE_WS_BRIDGE_SECRET ontbreekt in productie

**Symptomen:**

- 401 bij elk Codex/Responses WebSocket-bridgeverzoek wanneer OmniRoute op een externe productiehost wordt uitgevoerd
- De handshake van de WebSocket-bridge wordt onmiddellijk na het verbinden beëindigd

**Oorzaak:** De omgevingsvariabele `OMNIROUTE_WS_BRIDGE_SECRET` ontbreekt in de productieomgeving.

**Oplossing:**

1. Genereer een willekeurig geheim: `openssl rand -hex 32`
2. Stel `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` in de omgeving van de productieserver in (en op elke client die met de bridge communiceert)
3. Start OmniRoute opnieuw

### Responses API: achtergrondmodus teruggevallen op synchrone uitvoering

**Symptomen:**

- Waarschuwing gelogd: `background mode degraded to synchronous`
- Een verzoek met `background: true` retourneert een normale synchrone respons in plaats van een handle voor een achtergrondtaak

**Oorzaak:** v3.8.0 laat `background: true` in de Responses API bewust terugvallen op synchrone uitvoering en geeft daarbij een waarschuwing. Volledige asynchrone uitvoering op de achtergrond wordt in de toekomst geleverd.

**Oplossing:**

- Pas de client aan zodat deze de aanroep zonder `background` uitvoert, of
- Wacht op een latere release met volledige asynchrone achtergrondmodus (volg de changelog)

## Traag opstarten / time-out voor gereedheid

Als de CLI `⚠ Server did not respond within 60s` weergeeft, maar de server
wel degelijk werkt, is het budget voor de gereedheidscontrole te kort voor uw omgeving.

Dit gebeurt vaak op Windows (antivirussoftware, bestandssysteemwatchers) of in containers
met zware opstartwerklasten.

**Oplossing — verhoog het budget:**

```bash
# Via omgevingsvariabele (blijft behouden tussen starts):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuten
omniroute serve

# Via CLI-vlag (eenmalig):
omniroute serve --ready-timeout 180000
```

De standaardwaarde is 60 000 ms (60 s). De waarschuwing is uitsluitend informatief; de server
blijft op de achtergrond opstarten en is bereikbaar zodra het opstartproces is voltooid.

Zie [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) voor volledige
informatie over `OMNIROUTE_READY_TIMEOUT_MS`.
