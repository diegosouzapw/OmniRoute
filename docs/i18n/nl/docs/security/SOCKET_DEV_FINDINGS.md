Dit document is de door de maintainer opgestelde attestatie voor de zes
bevindingen met `AI-detected potential malware` die zijn gemeld voor `omniroute@3.8.5` en
de mitigerende maatregelen die zijn toegepast in `omniroute@3.8.6`. Het bestaat zodat:

1. Beheerders van beveiligingspipelines één referentie hebben om aan te halen wanneer zij
   de bevindingen aan de daadwerkelijke broncode moeten toetsen.
2. Toekomstige AI-scanners de door de maintainer ondertekende verklaring kunnen detecteren dat elk
   gemarkeerd pad opzettelijk, opt-in en gedocumenteerd is.
3. We een schriftelijk verslag hebben van _waarom_ elke aanroeplocatie is vormgegeven zoals die is —
   zodat een toekomstige refactor niet per ongeluk opnieuw een patroon introduceert dat
   bewust is verwijderd.

Als u een scanner beheert die een van de onderstaande aanroeplocaties opnieuw markeert nadat de
mitigerende maatregelen van v3.8.6 zijn uitgebracht, open dan een issue met de scantrace; dan
breiden we de attestatie hier uit.

## §1 — Installatie van MITM-root-CA (`77484.js`)

**Bronbestanden**:

- `src/mitm/cert/install.ts` — publieke `installCert()` / `uninstallCert()`,
  platformspecifieke `installCertWindows/Mac/Linux`.
- `src/mitm/systemCommands.ts` — gedeelde `execFile`- / `spawn`- / PowerShell-
  helpers die door de installatiepaden worden gebruikt.

**Trigger**: de gebruiker klikt op "MITM-proxy inschakelen" in het lokale dashboard op
`/dashboard/cli-tools/mitm`. De route is uitsluitend toegankelijk via loopback — zie harde regel #17 in
`CLAUDE.md` en `src/server/authz/routeGuard.ts::isLocalOnlyPath()`. Een gelekte
JWT die via een tunnel is blootgesteld, **kan** dit codepad niet activeren.

**Uitgevoerde bevoorrechte bewerkingen (per platform)**:

| Besturingssysteem      | Opdracht(en)                                                                                                      |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | `certutil -addstore Root <cert>` via UAC                                                                          |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | update van de NSS-database per profiel via `certutil -d sql:<profile>`                                            |

Dit zijn dezelfde opdrachten die worden gebruikt door `mitmproxy`, Charles Proxy, Fiddler en
Caddy. Het feit dat ze in OmniRoute aanwezig zijn, is gedocumenteerd in
`docs/security/STEALTH_GUIDE.md`.

**Mitigerende maatregel in v3.8.6**:

- `runElevatedPowerShell()` gebruikt niet langer `-EncodedCommand <base64utf16le>`.
  De payload met verhoogde bevoegdheden wordt naar een tijdelijk `.ps1`-bestand per aanroep geschreven (modus 0o600,
  in een persoonlijke `mkdtempSync`-map) en via `-File` aangeroepen. Het
  bestand wordt in `finally` verwijderd. Hiermee wordt het klassieke
  patroon van base64-elevatie via PowerShell verwijderd dat door de AI-
  classifier van Socket.dev werd gemarkeerd.
- `installCertWindows` bevat een inline `SECURITY-AUDITOR-NOTE:`-blok
  dat hiernaar verwijst.

**Waarom we dit behouden**: de MITM-proxy is een gedocumenteerde functie die wordt gebruikt door
`docs/security/STEALTH_GUIDE.md` en `docs/frameworks/MITM-PROXY.md`. Verwijdering
ervan zou de functionaliteit van de agent-bridge verstoren.

## §2 — Import van Zed-referenties (`app/api/providers/zed/import/route.js`)

**Bronbestanden**:

- `src/app/api/providers/zed/discover/route.ts` _(nieuw in v3.8.6)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(nieuw in v3.8.6)_

**Trigger**: de gebruiker klikt op "Importeren uit Zed" op de pagina Providers
van het lokale dashboard. Het eindpunt wordt beveiligd door
`requireManagementAuth`. De Zed-editor zelf schrijft zijn API-sleutels van
providers naar de sleutelhanger van het besturingssysteem onder gedocumenteerde
servicenamen — zie https://zed.dev/docs/ai/llm-providers.

**Gedrag in v3.8.5 (de versie die door Socket.dev werd gemarkeerd)**:

`POST /import` ontdekte de referenties en sloeg deze tijdens één enkele
retouraanroep automatisch op in de lokale SQLite-opslag. Geen bevestiging per
account, geen vingerafdruk, alleen "N tokens gevonden, allemaal geïmporteerd."

**Beperkende maatregel in v3.8.6 — bevestiging in 2 stappen**:

1. **`POST /api/providers/zed/discover`** retourneert
   `{ candidates: [{ provider, service, account, fingerprint }] }`. Het
   onbewerkte token wordt **nooit** verzonden. De vingerafdruk is
   `sha256(service|account|token).slice(0,16)`.
2. Het dashboard geeft de lijst met kandidaten weer, de beheerder selecteert
   welke moeten worden geïmporteerd en verzendt
   `{ confirmedAccounts: [{ service, account, fingerprint }] }` naar
   **`POST /api/providers/zed/import`**.
3. Het importeindpunt **leest de sleutelhanger opnieuw uit op de server** en
   filtert op `(service, account, fingerprint)`. Een gemanipuleerd of opnieuw
   afgespeeld detectieantwoord kan het importeindpunt er niet toe brengen een
   niet-gerelateerd token op te slaan — als het actuele token sinds de detectie
   is gewijzigd, komt de vingerafdruk niet meer overeen en wordt de referentie
   overgeslagen.

Een omgevingsvlag `OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` behoudt het gedrag
van v3.8.5 voor beheerders die hun automatisering nog niet hebben bijgewerkt.
Deze wordt in v3.9 verwijderd.

**Waarom we dit behouden**: importeren vanuit Zed is het gebruiksvriendelijkste
introductietraject voor gebruikers die Zed al gebruiken en hun providersleutels
naar OmniRoute willen kopiëren zonder ze opnieuw te plakken.

## §3 — `execFile` / `spawn` / PowerShell met verhoogde rechten (`21843.js`)

**Bronbestanden**: `src/mitm/systemCommands.ts`.

**Waarom gemarkeerd**: de chunk exporteert `execFileWithPassword`,
`runElevatedPowerShell` en de gedeelde helper `quotePowerShell` opnieuw. De
AI-classificatie van Socket.dev ziet deze als een algemene "toolkit voor
uitvoering op de host en privilegeverhoging." Binnen OmniRoute worden ze alleen
gebruikt door het installatiepad voor MITM-certificaten (§1) en door
`execFileWithPassword` voor het uitvoeren van `sudo`-opdrachten.

**Beperkende maatregelen in v3.8.6**:

- Refactoring van `runElevatedPowerShell` (zie §1).
- Een inline `SECURITY-AUDITOR-NOTE:`-blok bij zowel
  `runElevatedPowerShell` als `execFileWithPassword` documenteert de
  toegestane aanroepers en de vastgelegde lijst met uitvoerbare bestanden.
- De `spawn()`-aanroep van `execFileWithPassword` bevat een `nosemgrep`-markering
  met de lijst van uitvoerbare bestanden die de helper mag ontvangen — er
  bestaat **geen pad van gebruikersinvoer naar `finalCommand`/`finalArgs`**.

## §4 / §6 — Servicesupervisor van 9router (`api/services/9router/{start,restart}/route.js`)

**Bronbestanden**:

- `src/app/api/services/9router/_lib.ts` — supervisorfactory.
- `src/app/api/services/9router/{start,stop,restart,status,install,update,auto-start}/route.ts`.
- `src/lib/services/ServiceSupervisor.ts` — generieke spawn-, statuspolling- en logbufferfunctionaliteit.

**Trigger**: de gebruiker klikt op "Installeren" / "Starten" op de pagina met
ingesloten services in het lokale dashboard.

**Reeds aanwezige beveiligingen**:

- Alle `/api/services/*`-routes zijn LOCAL_ONLY volgens
  `src/server/authz/routeGuard.ts` (harde regel #17). Loopback-controle vindt
  plaats vóór elke authenticatiecontrole — een gelekte JWT kan deze routes
  niet bereiken.
- De 9router-databaserij wordt geïnitialiseerd met
  `status='not_installed', auto_start=0` (zie
  `src/lib/db/migrations/071_services.sql:19`). De service start **niet**
  wanneer de applicatie voor het eerst wordt gestart.
- `spawn()` wordt aangeroepen met het binaire pad dat wordt geretourneerd door
  `resolveSpawnArgs(apiKey, PORT)` in
  `src/lib/services/installers/ninerouter.ts`, dat een vaste lijst met
  ondersteunde binaire bestanden gebruikt.
- Stdout/stderr wordt in het geheugen gebufferd (limiet van 5 MB, zie
  `_lib.ts`) — er wordt niets naar schijf geschreven, tenzij de gebruiker
  logboekregistratie via het dashboard inschakelt.

**Beperkende maatregel in v3.8.6**: geen functionele wijziging. Het minimale
buildprofiel (`OMNIROUTE_BUILD_PROFILE=minimal`) vervangt
`src/lib/services/installers/ninerouter.ts` door een stub voor gebruikers die
de paden met verhoogde rechten fysiek uit de bundel willen verwijderen.

**Waarom we dit behouden**: 9router is een optionele, lokaal installeerbare
begeleidende service (vergelijkbaar met een WordPress-plug-in) — uitsluitend na
expliciete inschakeling.

## §5 — Terugschrijven van OmniRoute Cloud Sync-inloggegevens (`api/keys/[id]/route.js`)

**Bronbestanden**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`.
- `src/app/api/keys/[id]/route.ts` — roept `syncKeysToCloudIfEnabled()` aan.

**Trigger**: `isCloudEnabled()` retourneert `true` (ingesteld via het dashboard) **en**
`CLOUD_URL` is geconfigureerd. Als beide zijn uitgeschakeld, wordt er geen uitgaande netwerkaanroep naar het Cloud-endpoint uitgevoerd.

**Gedrag in v3.8.5 (de bug die Socket.dev terecht detecteerde)**:

`updateLocalTokens()` overschreef `accessToken`, `refreshToken` en
`providerSpecificData` vanuit de Cloud-respons wanneer
`cloudUpdatedAt > localUpdatedAt`. Geen HMAC, geen handtekening, geen controlesom. Een
verkeerd geconfigureerde of kwaadwillende `CLOUD_URL` (of een MITM op het kanaal) kon
OAuth-tokens van providers ongemerkt vervangen.

**Oplossing in v3.8.6**:

1. **HMAC-verificatie**: `verifyCloudSignature(rawBody, sigHeader)` controleert
   de `X-Cloud-Sig`-header (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`) voordat de JSON wordt geparseerd. Als het geheim is ingesteld, is de handtekening
   verplicht. Zo niet (verouderde modus), wordt een waarschuwing gelogd en wordt de respons
   geaccepteerd — het geheim wordt verplicht in v3.9.
2. **Expliciete inschakeling van geheime velden**: `accessToken` / `refreshToken` /
   `providerSpecificData` worden **alleen** overschreven wanneer
   `OMNIROUTE_CLOUD_SYNC_SECRETS=true`. In de standaardmodus worden alleen
   metadata zonder inloggegevens gesynchroniseerd (`expiresAt`, `status`, `lastError*`,
   `rateLimitedUntil`, `updatedAt`). Dit is een **incompatibele wijziging** voor gebruikers
   die vertrouwden op externe tokensynchronisatie — zij moeten dit expliciet inschakelen.

**Waarom we dit behouden**: Cloud Sync is de enige manier waarop een OmniRoute Cloud-tenant
teamreferenties kan centraliseren. De oplossing maakt het dreigingsmodel duidelijk:
"server ondertekent, client verifieert, beheerder stemt ermee in."

## Bouwprofiel: `minimal`

Gebruikers die een Socket-vriendelijk artefact nodig hebben, kunnen dit bouwen met:

```bash
OMNIROUTE_BUILD_PROFILE=minimal npm run build
```

De webpack-`NormalModuleReplacementPlugin` wijst vier modules toe aan stubs:

| Module                                      | Stub                                             |
| ------------------------------------------- | ------------------------------------------------ |
| `src/mitm/cert/install.ts`                  | `src/mitm/cert/install.stub.ts`                  |
| `src/lib/zed-oauth/keychain-reader.ts`      | `src/lib/zed-oauth/keychain-reader.stub.ts`      |
| `src/lib/cloudSync.ts`                      | `src/lib/cloudSync.stub.ts`                      |
| `src/lib/services/installers/ninerouter.ts` | `src/lib/services/installers/ninerouter.stub.ts` |

Elke stub exporteert dezelfde interface, maar elke functie genereert tijdens runtime een
`featureDisabledError(name)`. Routes die afhankelijk zijn van de uitgeschakelde
module retourneren HTTP 503 met een duidelijke melding, in plaats van het
gevoelige codepad te activeren.

De resulterende bundel is bedoeld om als `omniroute-secure` te worden gepubliceerd. Zie
`docs/ops/PUBLISHING_SECURE.md` voor de publicatie-instructies.
