### Limitazzjoni tar-Rata fuq Fornituri Bla Ħlas (429 / 400 / 401)

**Sintomu**: Meta tuża `model: "auto"` ma' fornituri bla ħlas/li ma jeħtiġux awtentikazzjoni (opencode, auggie, eċċ.), kultant tirċievi `HTTP 429`, `400`, jew `401` minflok tweġibiet. It-talbiet jirnexxu meta terġa' tipprova l-istess prompt ftit mumenti wara, iżda l-awtomatizzazzjoni (kompiti cron, aġenti, skripts) tieqaf taħdem mal-ewwel falliment.

**Kawża ewlenija**: Tliet modi indipendenti ta' falliment jakkumulaw:

1. **Limitu tar-rata tal-fornitur (`429`)**: Il-livelli bla ħlas jistgħu jinfurzaw kwota għal kull perjodu. Mewġa ta' sejħiet paralleli teżawrixxiha, għalhekk it-talba li jmiss tiġi rrifjutata sakemm il-perjodu jiġi ssettjat mill-ġdid.
2. **Mudell difettuż fil-passthrough (`400`/`401`)**: Il-pools `auto/*` jistgħu jinkludu mudelli passthrough minn `opencode` li huma rreġistrati fil-katalgu iżda m'għandhomx kredenzjali attivi (eż. `oc/north-mini-code-free` → `401`). L-auto-router jipprova wieħed, ifalli, u l-iżball jiġi propagat qabel ma tibda l-alternattiva.
3. **Amplifikazzjoni tal-konkorrenza (`429` taħt tagħbija)**: Meta diversi sessjonijiet ta' aġenti/cron jaċċessaw `auto` fl-istess ħin, ir-rata aggregata tat-talbiet taqbeż dak li jittolleraw il-fornituri bla ħlas, u għalhekk sejħiet leġittimi jiġu mmarkati bħala abbużivi.

**Soluzzjoni vverifikata (irrappurtata mill-komunità, 2026-08-10)**: irranġa tliet varjabbli tal-ambjent sabiex ir-rotazzjoni, il-konkorrenza u l-alternattiva jassorbu l-instabbiltà tal-livell bla ħlas minflok jieqfu minħabba fiha:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # aqleb għal mudell/fornitur ieħor f'każ ta' 400/401 (taqbeż mudelli passthrough difettużi)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # limitu espliċitu għall-ammissjoni ta' xogħlijiet tqal (mhux issettjat b'mod predefinit: l-ebda limitu fuq l-għadd tat-talbiet, ara n-nota hawn taħt)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # żid l-istennija limitata lil hinn mill-valur predefinit ta' RATE_LIMIT_MAX_WAIT_MS għal sistemi upstream bil-mod
```

Issettja dawn fl-ambjent tal-proċess OmniRoute (id-daemon, eż. permezz tal-LaunchAgent plist jew `systemctl edit`), imbagħad erġa' ibda OmniRoute. Il-flag tar-rotazzjoni huwa l-aktar mekkaniżmu effettiv: jibdel falliment komplet f'tentattiv ġdid trasparenti ma' fornitur b'saħħtu fil-pool.

**Nota**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` jillimita kemm-il talba tqila — b'kuntest twil — tista' taħdem fl-istess ħin; il-limitu huwa punt ta' kontroll għall-ammissjoni, mhux limitatur tar-rata tal-fornitur. **Aġġornament #503-fanout:** din il-varjabbli m'għadhiex tiġi ssettjata b'mod predefinit (issa tapplika biss meta tiġi kkonfigurata b'mod espliċitu, bħal hawn fuq) — minflok, l-ammissjoni ta' talbiet tqal hija kkontrollata minn baġit tal-bytes derivat awtomatikament (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) li jadatta ruħu għal-limitu reali tal-memorja tal-host, għalhekk skjerament ġdid għandu jara ħafna inqas rifjuti `503 chat_admission_busy` mingħajr ma din il-varjabbli tiġi ssettjata; jekk tissettjaha b'mod espliċitu hawn, xorta taħdem eżattament kif dokumentat. Sostituzzjonijiet espliċiti tal-baġit tal-bytes jiġu limitati għal 8 MiB–2 GiB. `413 body_exceeds_budget` mhuwiex temporanju: żid dak il-baġit tal-bytes, naqqas `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`, jew żid il-limitu tal-memorja tal-proċess. Tnaqqis `inflight_bytes_budget` huwa kontenzjoni temporanja u jibqa' eliġibbli għal tentattiv mill-ġdid. Il-limitazzjoni tar-rata għal kull fornitur (`open-sse/services/rateLimitManager.ts`) hija rregolata separatament minn `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, u `RATE_LIMIT_AUTO_ENABLE` — ara `.env.example`.

**Kif tivverifika li ħadmet**: ħaddem l-agent/cron tiegħek darbtejn wara xulxin fi żmien qasir u kkonferma li t-tnejn jirnexxu. Qabel it-tiswija, it-tieni eżekuzzjoni tipikament tirritorna `429`/`401`. Wara t-tiswija, il-fallimenti (jekk ikun hemm) jerġgħu jiġu ppruvati b’mod trasparenti u s-sejħa titlesta. Tista’ wkoll tagħmel `curl /monitoring/health` u tosserva l-field `rateLimitedUntil` fuq il-konnessjonijiet tal-fornituri u `circuitBreakers.providerBreakers[].state` għall-fornituri affettwati — l-istat ikun wieħed minn `CLOSED`, `DEGRADED`, `OPEN`, jew `HALF_OPEN` (ara `src/shared/utils/circuitBreaker.ts`), u fornitur li jibqa’ jfalli jgħaddi minn `CLOSED → DEGRADED → OPEN` qabel ma l-intervall ta’ reset jippermetti li jgħaddi test (`HALF_OPEN`).

**Jekk xorta tara 429**: il-kont attiv għal dak il-fornitur ikun ġenwinament eżawrixxa l-_quota_ tiegħu (mhux biss il-limitu tar-rata). Żid kont ieħor għall-istess fornitur fid-dashboard ta’ OmniRoute → Providers → Accounts, jew inkludi fornitur bla ħlas ieħor (eż. `routeway`, `auggie`). Ir-rotazzjoni tgħin biss b’limitazzjonijiet temporanji tar-rata/400/401; l-eżawriment sħiħ tal-quota jeħtieġ kredenzjali oħra jew fornitur differenti.

**Jekk tara 403 fuq mudelli tal-viżjoni (`auto/vision`, `bazaarlink/*`)**: il-kont konness m’għandux pjan imħallas li jinkludi l-viżjoni, jew l-API key m’għandhiex permessi biżżejjed. Ivverifika fid-dashboard tal-fornitur li l-ambitu tal-key jinkludi l-viżjoni/multimodali, jew qabbad kont ta’ livell imħallas u żommu bħala l-mira għall-viżjoni.

## Twissijiet ta' npm install (ERESOLVE / peer / deprecated)

Meta tħaddem `npm install -g omniroute`, tista' tara għadd kbir ta' twissijiet bħal `npm warn ERESOLVE`, avviżi dwar dipendenzi peer, u messaġġi `deprecated`. **Dawn huma mistennija u ma jagħmlux ħsara.** L-installazzjoni tkun irnexxiet jekk tara `added <N> packages` fl-output.

Biex trażżan it-twissijiet dwar ir-riżoluzzjoni tad-dipendenzi peer, uża l-forma ta' installazzjoni appoġġjata minn OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` irażżan biss `ERESOLVE` u l-avviżi dwar id-dipendenzi peer. L-avviżi ta' deprekazzjoni jibqgħu jidhru għax ġejjin minn pakketti tranżittivi ta' partijiet terzi; dawn ma jindikawx li l-installazzjoni falliet.

It-twissijiet ġejjin minn meded skaduti ta' dipendenzi peer f'pakketti ta' partijiet terzi li OmniRoute ma jikkontrollax:

1. **`marked-terminal` jeħtieġ `marked >=1 <16`, iżda nstab `marked@18`** — fil-prattika jaħdem tajjeb; il-medda peer tal-proġett oriġinali sempliċement hija skaduta.
2. **`deprecated prebuild-install@7.1.3`** — utilità tranżittiva biex jinġabru binarji nattivi. Ma tintużax
   biex tinstalla l-binding tat-trasport iffissat `wreq-js` u ma tindikax li l-konfigurazzjoni tat-trasport
   tal-fornitur tal-web cookies falliet.

**Mhi meħtieġa l-ebda azzjoni** — it-twissijiet ma jistgħux jiġu mrażżna kompletament mingħajr ma jinħolqu forks tal-pakketti upstream.

## Twissija dwar Skripts ta' npm install Imblukkati (installazzjoni globali)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

Meta tħaddem `npm install -g omniroute`, verżjonijiet aktar ġodda ta' npm (v11+ u v12+) jimblukkaw awtomatikament l-iskripts taċ-ċiklu tal-ħajja tal-pakketti u juru twissija dwar l-iskripts tal-installazzjoni:

```
npm warn install-scripts 7 pakketti kellhom l-iskripts tal-installazzjoni tagħhom imblukkati għax mhumiex koperti minn allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Din it-twissija tista' tiġi injorata?

**Parzjalment, iżda mhuwiex irrakkomandat li tħaddem mingħajr skripts.** OmniRoute jinkludi alternattivi gradwali: jekk il-bindings nattivi ta' `better-sqlite3` ma jkunux jistgħu jitgħabbew mill-bundle awtonomu, l-applikazzjoni taqleb għal drivers alternattivi bħal `node:sqlite` jew `sql.js` (ara [Riżoluzzjoni tar-Runtime ta' SQLite](../ops/SQLITE_RUNTIME.md)). Is-server xorta jibda, iżda l-użu ta' alternattivi WASM bħal `sql.js` jiddiżattiva l-modalità WAL (Write-Ahead Logging) ta' SQLite u jżid l-ispiża addizzjonali tal-memorja u tas-sinkronizzazzjoni mad-diska.

### Liema skripts huma fil-fatt meħtieġa?

Mhux l-iskripts imblukkati kollha huma essenzjali biex jitħaddem OmniRoute:

- **Essenzjali (`omniroute`, `better-sqlite3`):** OmniRoute jitħaddem minn bundle awtonomu ta' applikazzjoni Next.js (`dist/`). Waqt l-installazzjoni, npm iniżżel jew jikkompila d-driver nattiv ta' SQLite speċifiku għall-host fil-`node_modules/better-sqlite3/` tal-ogħla livell. Imbagħad, l-iskript `postinstall` ta' OmniRoute (`scripts/build/postinstall.mjs`) jivverifika u jikkopja dawn il-binarji speċifiċi għall-host f'`dist/node_modules/` sabiex is-server awtonomu jkun jista' jaċċessahom. Jekk l-iskript postinstall ta' `omniroute` ikun imblukkat, dan il-pass tal-ikkupjar jinqabeż.
- **Fakultattivi/tranżittivi (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** Dawn huma utilitajiet tal-build, għodod ta' monitoraġġ, jew utilitajiet tal-keychain tas-sistema. Jekk tippermettilhom, jiġu evitati t-twissijiet tal-build, iżda mhumiex meħtieġa għall-funzjonalità ewlenija tar-routing.
- **Eskluż (`onnxruntime-node`):** Dipendenza fakultattiva għall-embeddings lokali tal-IA u **mhijiex** meħtieġa biex jitħaddem OmniRoute. L-iskript postinstall tagħha jniżżel madwar 300MB ta' assi CUDA minn NuGet; tinkludihiex fil-lista tal-permessi sakemm ma jkollokx l-intenzjoni espliċita li tuża aċċellerazzjoni ONNX lokali fuq hardware appoġġjat.

### Soluzzjoni rakkomandata

Biex tippermetti l-iskripts tal-installazzjoni meħtieġa waqt installazzjoni globali u trażżan it-twissijiet, għaddi `--allow-scripts` għal OmniRoute u d-dipendenzi nattivi tiegħu:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

Inkella, biex tikkonfigura dan b'mod permanenti għall-installazzjonijiet globali kollha fil-kont tal-utent tiegħek:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### Ivverifika l-installazzjoni tiegħek

Wara l-installazzjoni, ħaddem l-għodda dijanjostika integrata biex tiżgura li l-bindings nattivi u l-ambjent tar-runtime qed jaħdmu sew:

```bash
omniroute doctor
```

## Pożittivi Foloz tal-Antivirus

<a name="antivirus-false-positives"></a>

### Avast/AVG ipoġġu `README.md` fi kwarantina b’`MD:HttpRequest-inf[Susp]`

**Dan huwa pożittiv falz. Xejn mhu infettat, u mhi meħtieġa l-ebda azzjoni.**

Avast u AVG jużaw euristika li timmarka fajls b’test sempliċi/Markdown li jkun fihom ħafna
links li jixbhu talbiet HTTP. Il-`README.md` ta’ OmniRoute jiġi inkluż fil-pakkett npm (huwa
elenkat f’`package.json` → `files`), għalhekk jispiċċa f’`node_modules/omniroute/README.md`
waqt installazzjoni globali — u fih madwar 15-il eżempju `http://localhost:20128/...` (l-endpoints
HTTP/SSE tal-MCP, il-URL `.well-known` tal-A2A, u siltiet ta’ `curl`). Dik id-densità ta’ links
hija biżżejjed biex tattiva l-euristika.

Jekk dan beda reċentement biss: it-tip ta’ fajl ma nbidilx. Ir-README kabbar it-tabella
tal-endpoints tiegħu (ġew miżjuda MCP HTTP + SSE + A2A) u żdiedu aktar eżempji ta’ `curl`,
u b’hekk qabeż il-limitu.

Il-fajl huwa dokumentazzjoni inattiva mingħajr ebda kontenut eżegwibbli. Tista’ tirrestawrah
b’mod sigur mill-kwarantina.

**X’għandek tagħmel:**

1. **Waqqaf in-notifiki** — eskludi d-direttorju tal-installazzjoni mill-antivirus tiegħek
   (Avast: Settings → Exceptions), billi żżid il-path globali ta’ `node_modules` u/jew
   id-direttorju tad-data ta’ OmniRoute (`~/.omniroute/`).
2. **Irrapporta l-pożittiv falz** — <https://www.avast.com/false-positive-file-form.php>,
   u ehmeż il-`README.md` li jinsab fi kwarantina. Din hija s-soluzzjoni li tgħin lil kulħadd,
   peress li hija l-euristika tal-bejjiegħ li qed tirreaġixxi żżejjed għal fajl ta’ test.

**Għaliex ma “nsewwux” dan min-naħa tagħna:** l-eżempji kollha huma `http://localhost`, u
localhost ma jistax ikun `https` mingħajr id-diffikultajiet ta’ ċertifikat awtofirmat. Li
ngħawġu d-dokumentazzjoni biex nevitaw l-euristika ta’ bejjiegħ wieħed jagħmel ħsara lil kull
qarrej biex jikkumpensa għal bug fl-iskaner.

### Kaspersky jimmarka l-app tad-Desktop bħala `PDM:Trojan.Win32.Generic`

**Dan huwa pożittiv falz minn euristika tal-imġiba. Xejn mhu infettat.** Il-prefiss `PDM:`
ta’ Kaspersky jfisser li l-verdett ġej mill-Proactive Defense Module (System Watcher) tiegħu,
li jiġġudika x’_jagħmel_ l-installatur minflok iqabblu ma’ malware magħruf. Meta jiġi attivat,
Kaspersky “ireġġa’ lura” l-installazzjoni kollha — billi jħassar fajls li jkun diġà kiteb —
għalhekk l-app tispiċċa bil-ħsara jew nieqsa.

Il-fajls li jimmarka huma partijiet standard ta’ dipendenzi open-source ddikjarati u inklużi
mal-app tad-desktop, pereżempju:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` u
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), il-librerija
  tal-awtomazzjoni tal-browser użata għall-login mal-fornitur minn ġewwa l-app u għaċ-chat
  appoġġjat mill-browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — il-binding nattiv iffissat ta’ `wreq-js` użat għal HTTP b’marka tas-swaba’ tal-browser
  fuq fornituri b’cookies tal-web (`<arch>` huwa `x64` jew `arm64`).

**Għaliex jiġi attivat:** l-installatur tal-Windows **għadu mhux iffirmat bil-kodiċi**,
għalhekk installatur NSIS mhux iffirmat m’għandu ebda reputazzjoni u l-euristiċi tal-imġiba
joperaw bl-aggressività massima. Meta dan jingħaqad ma’ DLL nattiva inkluża u mijiet ta’
fajls `.js` miktuba taħt `%LOCALAPPDATA%\Programs\OmniRoute` (inklużi direttorji ta’ pakketti
b’hash miżjud mill-build standalone ta’ Next.js), dan ikun biżżejjed biex jattiva l-euristika.
L-iffirmar tal-kodiċi huwa ppjanat; sakemm jiġi implimentat, rilaxxi ġodda jistgħu jirrepetu dan.

**X’għandek tagħmel:**

1. **L-ewwel ivverifika d-download tiegħek** (dan jeskludi fajl li jkun ġie mbagħbas). Kull
   rilaxx jippubblika `latest.yml`, li l-field `sha512` tiegħu (base64) ikopri l-installatur
   `OmniRoute.Setup.<version>.exe`. F’PowerShell, mill-folder li fih l-installatur:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   L-output irid jaqbel ma’ `latest.yml` → `sha512`. Jekk ma jaqbilx, ħassar il-fajl u
   niżżlu mill-ġdid biss mill-[paġna tar-rilaxxi ta’ GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Irrestawra + eskludi** — irrestawra mill-kwarantina l-elementi li tneħħew meta l-installazzjoni
   treġġgħet lura u żid esklużjoni għal `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky →
   Settings → Threats and Exclusions), imbagħad installa mill-ġdid.
3. **Irrapporta l-pożittiv falz** — <https://opentip.kaspersky.com/>. Rapporti FP mibgħuta
   mill-utenti tassew iħaffu ż-żieda mal-lista ta’ permessi.

## Kompatibbiltà ma’ Node.js

<a name="nodejs-compatibility"></a>

### Il-paġna tal-login tiġġarraf jew turi l-iżball "Module self-registration"

**Kawża:** Qed tħaddem verżjoni ta’ Node.js barra mil-limitu minimu approvat minn OmniRoute għal ambjent ta’ eżekuzzjoni sigur. L-aktar każ komuni huwa meta titħaddem verżjoni ta’ patch eqdem ta’ Node 22 jew 24 li tkun taħt il-limitu tas-sigurtà bil-garżi meħtieġa minn OmniRoute.

**Sintomi:**

- Il-paġna tal-login turi skrin vojt jew żball tas-server
- Il-console turi `Error: Module did not self-register` jew żbalji simili marbuta ma’ bindings nattivi
- Il-paġna tal-login turi **strixxun ta’ twissija oranġjo** bil-verżjoni tiegħek ta’ Node jekk l-ambjent ta’ eżekuzzjoni jkun barra mill-politika sigura appoġġjata

**Soluzzjoni:**

1. Installa rilaxx LTS appoġġjat ta’ Node.js (rakkomandat: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Ivverifika l-verżjoni tiegħek: `node --version` għandu juri `v24.0.0` jew verżjoni aktar ġdida fil-linja LTS 24.x
3. Erġa’ installa OmniRoute: `npm install -g omniroute`
4. Erġa’ ibda: `omniroute`

> **Verżjonijiet siguri appoġġjati:** `>=22.22.2 <23` jew `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) u Node.js 26 huma appoġġjati bis-sħiħ.

### npm v11+: `better-sqlite3` mhux installat (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Kawża:** npm v11 (inkluż ma’ Node.js 24+) jimblokka b’mod awtomatiku l-iskripts tal-installazzjoni għal
dipendenzi fakultattivi. Minħabba li `better-sqlite3` jinsab elenkat f’`optionalDependencies`
u jeħtieġ kumpilazzjoni nattiva (`node-gyp rebuild`), npm jaqbżu mingħajr ma jagħti avviż.

**Sintomi:**

- Is-server jiġġarraf waqt l-istartjar b’`Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` juri "No such file or directory"
- `npm ls better-sqlite3` juri `(empty)`

**Soluzzjoni:**

1. Approva l-iskripts tal-installazzjoni u erġa’ installa:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Jew installa manwalment il-verżjoni kkumpilata minn qabel:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Ivverifika li taħdem: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Kawża:** Wara `npm install -g omniroute` globali, il-binarju nattiv ta’ `better-sqlite3` fil-pakkett jista’ jkun ġie kkumpilat għal arkitettura jew ABI ta’ Node.js differenti minn dak li jkun qed jitħaddem lokalment. Dan huwa komuni fuq macOS (kemm Apple Silicon kif ukoll Intel) meta l-binarju kkumpilat minn qabel ma jaqbilx mal-ambjent tiegħek.

**Sintomi:**

- Is-server jieqaf minnufih waqt l-istartjar bi żball `dlopen`
- L-iżball jinkludi `slice is not valid mach-o file`
- Eżempju sħiħ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Soluzzjoni — erġa’ kkompila għall-ambjent lokali tiegħek (m’hemmx għalfejn tmur lura għal verżjoni eqdem ta’ Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Nota:** Dan jerġa’ jikkompila l-binding nattiv skont il-verżjoni lokali tiegħek ta’ Node.js u l-arkitettura tas-CPU, u b’hekk isolvi n-nuqqas ta’ tqabbil tal-binarju. Il-firxa ta’ ambjent ta’ eżekuzzjoni appoġġjata uffiċjalment hija **`>=22.22.2 <23` jew `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` f’`src/shared/utils/nodeRuntimeSupport.ts`, allinjata mal-field `engines` ta’ `package.json`). Node.js 24.x LTS (Krypton) u Node.js 26 huma appoġġjati bis-sħiħ b’`better-sqlite3` v12.x.

## Problemi bil-Proxy

<a name="proxy-issues"></a>

### Il-validazzjoni tal-fornitur turi "fetch failed"

**Kawża:** L-endpoint għall-validazzjoni taċ-ċavetta API (`POST /api/providers/validate`) qabel kien qed jevita l-konfigurazzjoni tal-proxy, u dan kien jikkawża fallimenti f'ambjenti li jeħtieġu routing permezz ta' proxy.

**Soluzzjoni (v3.5.5+):** Dan issa ġie rranġat. Il-validazzjoni tal-fornitur tgħaddi minn `runWithProxyContext`, u awtomatikament tirrispetta s-settings tal-proxy fil-livell tal-fornitur u dawk globali.

### Il-verifika tal-istat tat-token tfalli b'"fetch failed"

**Kawża:** L-aġġornament fl-isfond tat-token OAuth ma kienx qed isolvi l-konfigurazzjoni tal-proxy għal kull konnessjoni.

**Soluzzjoni (v3.5.5+):** L-iskedatur tal-verifika tal-istat tat-token issa jsolvi l-konfigurazzjoni tal-proxy għal kull konnessjoni qabel ma jipprova jagħmel aġġornament. Aġġorna għal v3.5.5+.

### Il-proxy SOCKS5 jirritorna "invalid onRequestStart method"

**Kawża:** Fuq Node.js 22, id-dispatcher undici@8 mhuwiex kompatibbli mal-implimentazzjoni integrata ta' `fetch()` ta' Node.

**Soluzzjoni (v3.5.5+):** OmniRoute issa juża l-funzjoni `fetch()` ta' undici stess meta dispatcher tal-proxy jkun attiv, biex jiżgura mġiba konsistenti. Aġġorna għal v3.5.5+.

### Proxy MITM taħt WSL: l-apps tad-desktop fuq il-host Windows ma jiġux interċettati

**Kawża:** Il-proxy MITM u ċ-ċertifikat CA tiegħu jiġu installati fl-ambjent fejn jitħaddem OmniRoute. Taħt WSL, dak l-ambjent huwa l-guest Linux, filwaqt li l-apps tad-desktop tal-AI (Kiro, Trae, Copilot, Zed, …) jitħaddmu fuq il-host Windows. L-apps tal-host ma jafdawx il-maħżen taċ-ċertifikati tal-guest u ma jgħaddux mill-proxy tas-sistema tal-guest, għalhekk l-interċettazzjoni tad-desktop ma taħdimx hemmhekk.

**Rakkomandazzjoni:** Ħaddem OmniRoute b'mod nattiv fuq l-istess OS tal-apps tad-desktop li trid tinterċetta (Windows għall-apps ta' Windows; l-istess japplika għal macOS/Linux). Jekk iżżomm OmniRoute ġewwa WSL filwaqt li timmira l-apps tal-host, ikollok bżonn tafda manwalment iċ-ċertifikat CA ġġenerat fuq il-host Windows u tipponta s-settings tan-network/proxy ta' kull app tal-host lejn l-endpoint tal-proxy WSL — konfigurazzjoni mhux appoġġjata u fraġli.

## Problemi ta' Docker

### IPv6 ta' Docker / Konnessjoni Risettjata

<a name="docker-ipv6"></a>

**Sintomi:** `curl http://localhost:20128/v1/models` jirritorna `curl: (56) Recv failure: Connection reset by peer`. Id-dashboard u l-endpoints mhux awtentikati jaħdmu, iżda l-endpoints awtentikati jfallu — jidher qisu problema ta' awtentikazzjoni iżda mhuwiex hekk.

**Kawża:** `docker run -p 20128:20128` jippubblika kemm fuq `0.0.0.0` (IPv4) kif ukoll fuq `::` (IPv6), iżda l-proċess ġewwa l-container jisma' fuq IPv4 biss. Fuq hosts fejn `localhost` jiġi riżolt għal `::1` l-ewwel, il-konnessjoni tasal fil-port ippubblikat tal-IPv6 mingħajr listener warajh → il-konnessjoni tiġi risettjata.

**Soluzzjoni:**

1. **Dijanjożi ta' malajr:** Ħaddem `curl -4 http://localhost:20128/v1/models`. Jekk jaħdem b'`-4` iżda jfalli mingħajru, għandek nuqqas ta' qbil fil-bind tal-IPv6.
2. **Soluzzjoni permanenti:** Agħmel bind espliċitu ma' IPv4 billi tuża `-p 127.0.0.1:20128:20128` fil-kmand `docker run` tiegħek:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Dan jisforza l-bind tal-IPv4 u jevita wkoll li jesponi l-proxy fuq l-interfaces kollha tal-host.

## Settings tar-Reżiljenza

### Il-limitazzjoni awtomatika tar-rata mhijiex qed tiskatta

- Il-limitazzjoni awtomatika tar-rata tapplika biss għall-fornituri b’API key (mhux OAuth/abbonament)
- Ivverifika li **Settings → Resilience → Provider Profiles** għandha l-limitazzjoni awtomatika tar-rata attivata
- Iċċekkja jekk il-fornitur jirritornax kodiċijiet tal-istatus `429` jew headers `Retry-After`

### Irfinar tar-ritard esponenzjali

Il-profili tal-fornituri jappoġġjaw dawn is-settings:

- **Dewmien bażi** — Il-ħin inizjali ta’ stennija wara l-ewwel falliment (default: 1s)
- **Dewmien massimu** — Il-limitu massimu tal-ħin ta’ stennija (default: 30s)
- **Multiplikatur** — Kemm għandu jiżdied id-dewmien għal kull falliment konsekuttiv (default: 2x)

### Prevenzjoni tal-effett “thundering herd”

Meta ħafna talbiet konkorrenti jilħqu fornitur b’rata limitata, OmniRoute juża mutex + limitazzjoni awtomatika tar-rata biex jissekwenzjalizza t-talbiet u jipprevjeni fallimenti kaskata. Dan iseħħ awtomatikament għall-fornituri b’API key.

### It-talbiet taċ-chat ifallu b’503 / chat_admission_busy

**Sintomi:**

- L-endpoint tal-kompletamenti taċ-chat jirritorna tweġiba `503` li tista’ terġa’ tiġi ppruvata u li l-kodiċi tal-iżball tagħha huwa
  `chat_admission_busy`.
- It-tweġiba tinkludi `Retry-After`. Minn #12135 ’l hawn, il-valur jiġi dderivat mill-okkupanza osservata
  — l-akbar valur bejn it-tieqa `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` li t-talba diġà
  stenniet u ż-żmien li matulu nżammu l-heavyweight leases attwali — arrotondat ’il fuq għal
  sekondi sħaħ u limitat għal 60. Meta l-gate jkun inattiv, jinżammu l-limiti minimi storiċi: 2 sekondi fil-
  perkors ibbażat fuq il-bytes, u sekonda fil-perkors ibbażat fuq l-istruttura (li jinkludi wkoll
  `reason: "structure_limit"`).
- Dan jista’ jiġri waqt li chat heavyweight ieħor jew tweġiba ta’ streaming li ddum għaddejja tkun għadha
  qed tiġi pproċessata.

Il-body tat-tweġiba bbażata fuq il-bytes huwa:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

It-tweġiba bbażata fuq l-istruttura tuża l-istess tip u kodiċi, bil-messaġġ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
u `reason: "structure_limit"`.
Bil-limiti default, talba titqies strutturalment tqila meta jkollha mill-inqas `200` messaġġ,
mill-inqas `64` għodda, jew mill-inqas `32,000` token stmat, jew meta l-istima limitata tal-istruttura
teżawrixxi l-limiti tagħha ta’ `10,000` node miżjur jew fond ta’ `12`.

**Kawża:** Din hija tnaqqis intenzjonat tat-tagħbija fi ħdan OmniRoute, mhux falliment ta’ fornitur upstream.
Kull proċess juża guard lokali għall-proċess biex jirriżerva kapaċità heavyweight limitata qabel ma jżomm
u jipparsja body kbir ta’ talba. Heavyweight lease jibqa’ miżmum tul il-ħajja ta’ tweġiba SSE.

**#503-fanout:** qabel din il-korrezzjoni, il-guard kien jillimita l-konkorrenza għal GĦADD fiss ta’ talbiet
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, default `1`) irrispettivament mill-memorja tal-host, għalhekk il-
fan-out tal-coding agents (diversi subagents/CLIs, b’bodies li regolarment jaqbżu 256 KB) kien jispiċċa b’konkorrenza
effettiva ta’ ~1 u jirritorna 503 taħt tagħbija kompletament normali. Issa l-guard jirregola ruħu
awtomatikament: huwa kkontrollat minn baġit awtomatikament idderivat ta’ BYTES għall-ingestjoni (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) iddimensjonat skont il-
limitu reali tal-memorja tal-proċess, u jikkonsulta wkoll sinjal dirett tal-pressjoni fuq ir-riżorsi — għalhekk
inaqqas it-tagħbija biss meta l-host ikun ġenwinament taħt pressjoni tal-memorja, mhux sempliċement għax waslet aktar minn
talba tqila waħda fl-istess ħin. Il-limitu l-antik tal-għadd (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) għadu
jiġi rrispettat, iżda biss jekk tissettjah b’mod espliċitu.

Meta l-kapaċità tkun okkupata, talba heavyweight l-ewwel tistenna sa
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (default għal `RATE_LIMIT_MAX_WAIT_MS`; `0` jiddiżattiva l-istennija) sabiex jinħeles slot
qabel ma twieġeb bil-`503` li jista’ jerġa’ jiġi ppruvat. L-istennija limitata teżisti sabiex klijenti tat-tip agent
(OpenCode, Claude Code, Cursor) li jagħmlu fan-out ta’ sub-talbiet tqal b’mod konkorrenti jissekwenzjalizzaw il-burst
minflok jeżawrixxu l-baġit kollu tagħhom ta’ tentattivi mill-ġdid fuq rifjuti immedjati u jieqfu f’nofs il-kompitu.
L-okkupanza attwali tal-heavyweight leases, il-baġit tal-bytes riżolt, u s-severità diretta tal-pressjoni
jintwerew f’`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — iċċekkja dawn qabel tibdel kwalunkwe env var.
Settings → Resilience → Request Queue → Concurrent Requests ma jikkontrollax dan; dak is-setting
jirregola mekkaniżmu separat tal-kju tat-talbiet tal-fornitur.

**Soluzzjoni:**

1. L-ewwel erġa’ pprova. Il-klijenti għandhom jirrispettaw `Retry-After` u jużaw backoff minflok ma minnufih
   jirrepetu t-talba.
2. Iċċekkja `/api/monitoring/health` → `chatAdmission` qabel tirfina xi ħaġa. `countCapEnabled:
false` u `maxInflightBytes` ġeneruż ifissru li l-baġit idderivat awtomatikament diġà qed jagħmel
   xogħlu; `pressureSeverity` ta’ `high`/`critical` tfisser li l-host ġenwinament għandu ftit memorja —
   dan ma jistax jissewwa permezz ta’ env var tal-ammissjoni; jeħtieġ aktar RAM jew workload iżgħar.
3. Huwa biss jekk `/api/monitoring/health` juri li l-baġit idderivat awtomatikament huwa ġenwinament żgħir wisq għall-
   host tiegħek (ħaġa rari — diġà jiskala minn container sa bare-metal), li għandek tissovrascrivih direttament b’
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` minflok terġa’ lura għal-limitu legat ibbażat fuq l-għadd ta’ talbiet.

Ara r-[referenza tal-varjabbli tal-ambjent](../reference/ENVIRONMENT.md#4-security--authentication)
għas-settings awtorevoli tal-ammissjoni.

## Tassonomija fakultattiva tal-fallimenti ta' RAG / LLM (16-il problema)

Xi utenti ta' OmniRoute jqiegħdu l-gateway quddiem stacks ta' RAG jew aġenti. F'dawn il-konfigurazzjonijiet huwa komuni li jidher mudell stramb: OmniRoute jidher li qed jaħdem sew (il-fornituri attivi, il-profili tar-routing tajbin, l-ebda twissija dwar il-limitu tar-rata) iżda t-tweġiba finali xorta tkun ħażina.

Fil-prattika, dawn l-inċidenti normalment joriġinaw mill-pipeline RAG downstream, mhux mill-gateway innifsu.

Jekk trid vokabularju komuni biex tiddeskrivi dawk il-fallimenti, tista' tuża l-WFGY ProblemMap, riżorsa esterna ta' test b'liċenzja MIT li tiddefinixxi sittax-il mudell rikorrenti ta' falliment ta' RAG / LLM. Fuq livell ġenerali, tkopri:

- devjazzjoni fl-irkupru u konfini tal-kuntest miksura
- indiċijiet u vector stores vojta jew skaduti
- nuqqas ta' qbil bejn l-embedding u s-semantika
- problemi fl-assemblaġġ tal-prompt u fit-tieqa tal-kuntest
- kollass tal-loġika u tweġibiet kunfidenti żżejjed
- fallimenti f'katini twal u fil-koordinazzjoni tal-aġenti
- devjazzjoni fil-memorja u fir-rwoli ta' diversi aġenti
- problemi fl-ordni tad-deployment u tal-bootstrap

L-idea hija sempliċi:

1. Meta tinvestiga tweġiba ħażina, irreġistra:
   - il-kompitu u t-talba tal-utent
   - ir-rotta jew il-kombinazzjoni tal-fornituri f'OmniRoute
   - kwalunkwe kuntest RAG użat downstream (dokumenti rkuprati, sejħiet ta' għodod, eċċ.)
2. Assenja l-inċident lil numru wieħed jew tnejn tal-WFGY ProblemMap (`No.1` … `No.16`).
3. Aħżen in-numru fid-dashboard, fir-runbook, jew fit-tracker tal-inċidenti tiegħek ħdejn il-logs ta' OmniRoute.
4. Uża l-paġna korrispondenti ta' WFGY biex tiddeċiedi jekk għandekx bżonn tibdel l-istack RAG, ir-retriever, jew l-istrateġija tar-routing tiegħek.

## Problemi Magħrufa ta' v3.8.0

Problemi speċifiċi għar-rilaxx v3.8.0 u s-soluzzjonijiet temporanji attwali tagħhom. Jekk soluzzjoni tidħol f'patch aktar tard, l-entrata tiġi aġġornata jew imneħħija.

### Fallimenti fl-awtentikazzjoni tad-Devin CLI

**Sintomi:**

- "Devin CLI ma nstabx" jew "l-awtentikazzjoni falliet" meta jissejħu għodod ibbażati fuq Devin
- Il-verifika tar-runtime tas-CLI tirrapporta `installed=false`

**Kawżi:**

- `CLI_DEVIN_BIN` jindika path li ma jeżistix
- Devin CLI mhuwiex installat fuq il-host

**Soluzzjoni:**

1. Installa d-Devin CLI għall-pjattaforma tiegħek
2. Issettja `CLI_DEVIN_BIN=/usr/local/bin/devin` (jew il-path reali) f'`.env`
3. Erġa' ibda OmniRoute u erġa' ttestja minn **Dashboard → CLI Tools**

### Il-cooldown tal-mudell jibqa' mwaħħal (reset manwali)

**Sintomi:**

- Mudell jibqa' elenkat bħala li jinsab f'cooldown anki wara li jkun għadda l-ħin tal-iskadenza
- It-talbiet jibqgħu jaqbżu l-mudell fir-routing b'kombinazzjoni minkejja li t-timestamp ikun fil-passat

**Reset manwali:**

- **Dashboard:** **Settings → Model Cooldowns** → ikklikkja **Re-enable** fuq il-card affettwata
- **API:** `DELETE /api/resilience/model-cooldowns` b'headers tal-awtentikazzjoni tal-ġestjoni

### Il-konnessjoni mal-fornitur Command Code tfalli b'403

**Sintomi:**

- 403 meta tiġi ttestjata l-konnessjoni mal-fornitur Command Code
- Il-card tal-fornitur turi "mhux awtorizzat" wara żieda ġdida

**Kawża:** Il-fluss OAuth ma tlestiex (il-callback ma wasalx jew it-token ma ġiex ippersistit).

**Soluzzjoni:**

- Ħaddem `omniroute providers` mis-CLI biex terġa' tiskatta l-fluss OAuth, jew
- Erġa' ħaddem OAuth minn **Dashboard → Providers → Command Code → Reconnect**

### ModelScope jirritorna cooldowns aggressivi ta' 429

**Sintomi:**

- Cooldowns qosra ħafna jew immedjati fuq ModelScope wara għadd żgħir ta' talbiet f'daqqa
- Ir-routing b'kombinazzjoni jaqbeż lil ModelScope aktar kmieni milli mistenni

**Kawża:** ModelScope joħroġ headers `Retry-After` speċifiċi għall-fornitur. v3.8.0 jinkludi mmaniġġjar apposta għal dawk il-headers, għalhekk verżjonijiet eqdem jinterpretawhom ħażin bħala indikazzjonijiet ġeneriċi dwar il-limitu tar-rata.

**Soluzzjoni:**

- Kun żgur li qed tuża v3.8.0 jew verżjoni aktar reċenti
- Ivverifika li t-toggle `useUpstream429BreakerHints` huwa attivat taħt **Settings → Resilience**

### OMNIROUTE_WS_BRIDGE_SECRET nieqes fil-produzzjoni

**Sintomi:**

- 401 fuq kull talba lill-bridge WebSocket ta' Codex/Responses meta jkun qed jaħdem fuq host remot tal-produzzjoni
- Il-handshake tal-bridge WebSocket jingħalaq immedjatament wara l-konnessjoni

**Kawża:** L-env var `OMNIROUTE_WS_BRIDGE_SECRET` hija nieqsa mill-ambjent tal-produzzjoni.

**Soluzzjoni:**

1. Iġġenera secret każwali: `openssl rand -hex 32`
2. Issettja `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` fl-env tas-server tal-produzzjoni (u fi kwalunkwe client li jikkomunika mal-bridge)
3. Erġa' ibda OmniRoute

### Responses API: il-modalità fl-isfond degradata għal sinkronika

**Sintomi:**

- Twissija rreġistrata fil-log: `background mode degraded to synchronous`
- Talba `background: true` tirritorna tweġiba sinkronika normali minflok handle ta' job fl-isfond

**Kawża:** v3.8.0 intenzjonalment jiddegrada `background: true` fuq ir-Responses API għal eżekuzzjoni sinkronika filwaqt li joħroġ twissija. L-eżekuzzjoni asinkronika sħiħa fl-isfond hija funzjonalità ppjanata għall-futur.

**Soluzzjoni:**

- Aġġusta l-client biex jagħmel is-sejħa mingħajr `background`, jew
- Stenna rilaxx aktar tard li jinkludi l-modalità asinkronika sħiħa fl-isfond (segwi l-changelog)

## Startjar Bil-mod / Skadenza tal-Ħin ta’ Prontezza

Jekk is-CLI juri `⚠ Is-server ma rrispondiex fi żmien 60s` iżda s-server
fil-fatt qed jaħdem, il-limitu tas-sonda tal-prontezza huwa qasir wisq għall-ambjent tiegħek.

Dan jiġri spiss fuq Windows (antivirus, osservaturi tas-sistema tal-fajls) jew f’containers
b’tagħbijiet kbar waqt l-istartjar.

**Soluzzjoni — żid il-limitu:**

```bash
# Permezz ta’ varjabbli tal-ambjent (jippersisti bejn l-istartjar):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuti
omniroute serve

# Permezz ta’ flag tas-CLI (għal darba waħda):
omniroute serve --ready-timeout 180000
```

Il-valur predefinit huwa 60 000 ms (60 s). It-twissija hija biss informattiva; is-server
ikompli jistartja fl-isfond u jkun aċċessibbli ladarba jitlesta l-ibbutjar.

Ara [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) għad-dettalji kollha
dwar `OMNIROUTE_READY_TIMEOUT_MS`.
