## भाग 1 — निकाल आणि परिपक्वता वर्गीकरण

**एकूण श्रेणी: A− / "प्रगत". प्रकल्पांमधील सर्वोच्च ~5–10%.** ही प्रणाली उद्योगाने
स्पष्टपणे नामांकित केलेले अनेक पॅटर्न स्वतंत्रपणे अंमलात आणते — हा सुसंगततेचा सर्वांत
प्रबळ संकेत आहे (आम्ही तपासणी-सूचीची नक्कल केली नाही; योग्य पद्धतींवर स्वतंत्रपणे पोहोचलो).

## भाग 2 — चिकित्सक मूल्यमापन (बलस्थाने + प्रामाणिक उणिवा)

### बलस्थाने (सरासरीपेक्षा सरस असलेल्या बाबी)

1. **बहु-मेट्रिक रॅचेट इंजिन.** प्रणालीचा गाभा. `quality-baseline.json` मध्ये 24 मेट्रिक्स
   - 4 स्वतंत्र बेसलाइन्स, प्रत्येकामध्ये दिशा (`up`/`down`), सहनशीलता (`eps`), शिथिलता
     (`tightenSlack`) आणि `dedicatedGate` ध्वज आहे. ज्या गोष्टी दुरुस्त होतात त्या **दुरुस्तच राहतात** — हा
     कोडबेसमधील एंट्रॉपीवरील उतारा आहे.
2. **पुरवठा-साखळीसाठी बहुस्तरीय संरक्षण.** SAST (CodeQL/Sonar) + गुपिते (gitleaks सोबत
   `useDefault`) + SCA (osv/npm-audit/Trivy/Dependabot) + परवाने + lockfile + SBOM + SLSA
   उद्गमपुरावा + Scorecard + वर्कफ्लो दृढीकरण (zizmor). मोजक्याच कोडबेसमध्ये हा संपूर्ण संच असतो.
3. **Goodhart's Law विरुद्धचे उतारे.** कव्हरेजला लक्ष्य मानणे हा एक पारंपरिक प्रतिरूपविरोध आहे
   ("जेव्हा मापनच लक्ष्य बनते, तेव्हा ते चांगले मापन राहात नाही"). आपल्याकडे
   प्रतिसंतुलक आहेत: **म्युटेशन चाचणी** (चाचणी केवळ ओळ कार्यान्वित करते की प्रत्यक्षात दोष पकडते, हे
   मोजते), **`check-test-masking`** (उत्तीर्ण होण्यासाठी asserts कमकुवत करण्यास प्रतिबंध करते),
   **प्रत्येक मॉड्यूलसाठी कव्हरेजची किमान मर्यादा** (केवळ सोपे भाग नव्हे, तर HIGH-जोखमीच्या कोडची चाचणी करण्यास भाग पाडते) आणि
   **`check-pr-evidence`** (कठोर नियम #18).
4. **भासविरोधी / सुसंगतता गेट्स.** एक दुर्मीळ आणि मौल्यवान श्रेणी: `check-known-symbols`,
   `check-fetch-targets`, `check-openapi-routes`, `check-docs-symbols` हे सुनिश्चित करतात की दस्तऐवज, विनिर्देश आणि
   स्ट्रिंग डिस्पॅच अस्तित्वात असलेल्या सिम्बॉल्सकडे निर्देश करतात. lint/test ला न सापडणारी "कुज" पकडतात.
5. **सल्लागार→अवरोधक जीवनचक्र.** नवीन गेट्स सल्लागार स्वरूपात येतात (परिपक्व होत असताना
   मर्ज रोखत नाहीत), आणि नंतर चक्राच्या शेवटी अवरोधक होतात. कमाल मर्यादा न गमावता अडथळे कमी होतात.
6. **पायाभूत सुविधा उपलब्ध नसताना सुलभपणे वगळणे.** बायनरी/नेटवर्क
   अयशस्वी झाल्यास स्कॅनर्स (`--ratchet`) `exit 0` सह बाहेर पडतात — अपुरी पायाभूत सुविधा कोणताही वैध PR कधीही रोखत नाही. परिपक्व अभियांत्रिकी.
7. **संहिताबद्ध संस्कृती.** कठोर नियम + `trust-but-verify` + stale-allowlist + evidence-gate
   शिस्तीचे रूपांतर स्वयंचलित पडताळणीत करतात.

### प्रामाणिक उणिवा (वास्तविक त्रुटी)

1. **🔴 fast-gates विभाजनात अजूनही संरचनात्मक पोकळी आहे.** `quality.yml` (PR→`release/**`)
   आता कोड PR साठी typecheck, जलद निर्धारक चाचण्या आणि सल्लागार उत्पादन build चालवते,
   परंतु तरीही ते `ci.yml` मधील संपूर्ण release-PR व्याप्ती (कव्हरेज रॅचेट्स,
   पॅकेज आर्टिफॅक्ट, इंटिग्रेशन, E2E, SonarQube) चालवत नाही. प्रेरणा (वेग) वैध आहे, पण गेट
   मर्ज जिथे होते तिथेच असायला हवे (shift-left). **सर्वांत मोठी प्रलंबित संरचनात्मक सुधारणा.**
2. **🟠 गेट्सच्या अतिरेकाचा/थकव्याचा धोका.** ~46 गेट्स + 25 jobs हे खूपच जास्त आहे. Sonar स्वतः इशारा देते:
   अतिप्रमाणातील अटींमुळे "गेट थकवा" आणि प्राधान्यक्रमांवरील वाद निर्माण होतात, तसेच गेटकडे
   दुर्लक्ष होण्याचा धोका असतो. DORA इशारा देते की जड गेट्समुळे lead-time वाढतो. आपण सल्लागार स्तर आणि
   निरपेक्ष नसलेल्या रॅचेट्सद्वारे हा धोका कमी करतो, पण **प्रत्येक गेटचे नियतकालिक ROI पुनरावलोकन** उपलब्ध नाही (doc-sync साठीची काही सूक्ष्म-गेट्स
   एकत्रित करता येण्यासारखी आहेत).
3. **🟠 म्युटेशन स्कोअर अद्याप रॅचेट नाही.** कव्हरेजमध्ये फेरफार करण्याविरुद्धचा सर्वांत प्रभावी उतारा
   **सल्लागार** आहे. ही सर्वाधिक मूल्यवान प्रलंबित बाब आहे (आणि तिचे 90% काम आधीच पूर्ण झाले आहे).
4. **🟡 योग्य व्याप्तीत अवरोधक असायला हवेत असे सल्लागार.** गोठवलेल्या बेसलाइन्स असूनही `osv` (vulnCount) आणि `oasdiff`
   सल्लागार आहेत. osv-advisory योग्य ठरते (जुन्या dep वरील नवीन CVE मुळे
   असंबंधित PR रोखला जाईल) — पण एक मध्यममार्ग आहे (आपण Trivy सोबत केल्याप्रमाणे केवळ CRITICAL+fixable अवरोधित करा).
   oasdiff सल्लागार असल्यामुळे करार मोडणारा बदल पुढे जाऊ शकतो.
5. **🟡 रनटाइम सुरक्षा केवळ रात्री चालते.** schemathesis/garak/promptfoo/chaos/k6 रात्री चालतात.
   योग्य निर्णय (मंद आहेत, थेट सर्व्हर आवश्यक आहे), पण एखादा PR injection-guard मधील प्रतिगमन आणू शकतो,
   जे केवळ पुढील रात्री पकडले जाते.
6. **🟡 `main` वरील branch-protection बंद आहे.** `BRANCH_LOCK_TOKEN` _release_ शाखा लॉक करते, पण
   `main` स्वतः असुरक्षित आहे. Scorecard/DSOMM मध्ये यासाठी गुणकपात होते. मालकाची कृती आवश्यक.
7. **🟡 CodeQL default-setup; semgrep संहिताबद्ध नाही.** default-setup कार्य करते (0 alerts), पण
   committed `codeql.yml` अधिक नियंत्रण देते; semgrep हे रेपोमध्ये versioned नसून बाह्य क्लाउड प्लॅटफॉर्मद्वारे चालते.

## भाग 3 — गुणवत्ता तपासणी-बिंदूंची संपूर्ण सूची (पोर्टेबल)

खालील 12 श्रेणी म्हणजे पुनर्वापर करता येण्याजोग्या स्वरूपातील "गुणवत्ता प्रणाली" आहे. प्रत्येक श्रेणीत
**उद्दिष्ट** (कशाचे संरक्षण करायचे), **आम्ही वापरत असलेली साधने** आणि कोणत्याही स्टॅकवर त्याची पुनरावृत्ती करण्यासाठी **साधन-स्वतंत्र समतुल्य पर्याय**
दिले आहेत.

### 1. शैली आणि स्वरूपन (निर्धारित, जलद)

- **OmniRoute:** lint-staged द्वारे Prettier + ESLint (pre-commit), 2-स्पेस/दुहेरी अवतरणचिन्हे/100col.
- **सर्वसाधारण:** आपोआप दुरुस्त करता येणारा एक formatter + एक linter, staged फाइल्सवर pre-commit मध्ये चालणारे.

### 2. प्रकार

- **OmniRoute:** `typecheck:core` (अवरोधक) + `typecheck:noimplicit:core` (सल्लात्मक) + `type-coverage` रॅचेट 92.17% + प्रत्येक फाइलसाठी any-बजेट.
- **सर्वसाधारण:** CI मध्ये कठोर typecheck + रॅचेट केलेले type-coverage मेट्रिक + प्रत्येक फाइलसाठी `any`/escape-hatch बजेट.

### 3. चाचण्या (तीव्रता)

- **OmniRoute:** एकमेकांशी न ओव्हरलॅप होणारे 2 runners (Node native + vitest), 8 shards, जागतिक coverage 60/60/60/60 + रॅचेट ~76% + **महत्त्वपूर्ण modules साठी 8 प्रति-module किमान मर्यादा** + दररात्री property tests + दररात्री **mutation testing**.
- **सर्वसाधारण:** test runner(s) + **निरपेक्ष** coverage किमान मर्यादा (शून्य-विरोधी) + coverage **रॅचेट** (प्रतिगमन-विरोधी) + **उच्च-जोखीम कोडसाठी प्रति-module किमान मर्यादा** (Goodhart-विरोधी) + शुद्ध logic साठी property-based चाचण्या + चाचणी-गुणवत्तेचे खरे मोजमाप म्हणून दररात्री **mutation testing**.

### 4. चाचणी धोरण (फसवणूक-विरोधी)

- **OmniRoute:** `pr-test-policy` (उत्पादन कोडसाठी चाचणी आवश्यक), `check-test-masking` (कमकुवत केलेले asserts अवरोधित करते), `pr-evidence` (यशाच्या दाव्यासाठी पुरावा block आवश्यक), `test-discovery` (प्रत्येक चाचणी runner द्वारे संकलित केली जाते).
- **सर्वसाधारण:** "नवीन कोड ⇒ नवीन चाचणी" gate + काढलेले assert/tautology शोधक + पुराव्याची आवश्यकता (TDD किंवा सक्रिय चाचणी) + कोणतीही चाचणी globs च्या बाहेर अनाथ राहणार नाही याची हमी.

### 5. गुंतागुंत आणि कोडचे आरोग्य (रॅचेट्स)

- **OmniRoute:** ESLint-warnings (3769↓), jscpd duplication (5.72%↓), cyclomatic+max-lines complexity (1800↓), cognitive complexity sonarjs (753↓), dead-code/unused-exports knip (339↓), प्रति-फाइल file-size (गोठवलेले, केवळ कमी करता येणारे), circular-deps (सानुकूल Tarjan, अवरोधक).
- **सर्वसाधारण:** प्रत्येक आरोग्य मेट्रिक रॅचेट करा (warnings, duplication, cyclomatic **आणि** cognitive complexity, dead code, file size, import cycles). दिशा नेहमी "प्रतिगमन होऊ देऊ नका".

### 6. स्थिर सुरक्षा (SAST + secrets)

- **OmniRoute:** CodeQL (alerts रॅचेट = 0), gitleaks (`[extend] useDefault=true` — अत्यंत महत्त्वाचे!), SonarQube, सानुकूल सुरक्षा नियम (public-creds, error-helper, route-guard-membership, route-validation).
- **सर्वसाधारण:** alert रॅचेटसह SAST (CodeQL/Sonar/semgrep) + **वारशाने मिळालेल्या default ruleset** सह secrets scanner (default ला override करणारे custom config = अदृश्य त्रुटी) + प्रकल्प-विशिष्ट Hard Rule सुरक्षा gates.

### 7. पुरवठा-साखळी (dependencies)

- **OmniRoute:** osv-scanner + npm-audit + Trivy + Dependabot (SCA), license-checker (SPDX allowlist), lockfile-lint (HTTPS+sha512+registry), `check-deps` anti-slopsquatting (allowlist + वय ≥72h).
- **सर्वसाधारण:** बहु-स्रोत SCA + license allowlist + lockfile अखंडता तपासणी + वय/typosquatting तपासणीसह dependency allowlist + गटबद्ध update bot.

### 8. पुरवठा-साखळी (बिल्ड आणि रिलीझ)

- **OmniRoute:** SBOM (CycloneDX + syft), SLSA provenance (`--provenance`), OpenSSF Scorecard (साप्ताहिक), workflow hardening (zizmor: artipacked→`persist-credentials:false`, cache-poisoning, token-permissions).
- **सर्वसाधारण:** publish करताना SBOM तयार करा + स्वाक्षरी केलेले provenance (SLSA L2+) + नियोजित Scorecard + सर्व workflows मजबूत करा (किमान-विशेषाधिकार tokens, non-pusher checkout वर persisted credentials नाहीत, actions SHA द्वारे pin केलेले).

### 9. करार आणि API

- **OmniRoute:** oasdiff (breaking-change OpenAPI), schemathesis (दररात्री contract fuzz), openapi-coverage (% दस्तऐवजीकरण केलेले routes, रॅचेट 38.3%), openapi-security-tiers (spec विरुद्ध route-guard).
- **सर्वसाधारण:** breaking-change contract diff (oasdiff/buf) + spec विरुद्ध property-based fuzz (schemathesis) + रॅचेट केलेले documentation coverage + spec↔code सुसंगतता.

### 10. दस्तऐवज आणि i18n (कालबाह्यता-विरोधी)

- **OmniRoute:** docs-sync (प्रतिबिंबित आवृत्त्या), docs-counts-sync (दस्तऐवजांतील विरुद्ध कोडमधील संख्या), env-doc-sync, doc-links, fabricated-docs, cli-i18n, i18n-ui-coverage (`--threshold=65` + रॅचेट 80.1%).
- **सर्वसाधारण:** दस्तऐवज आणि कोड यांदरम्यान versions/counts/env-vars समक्रमित करा (gate, विश्वास नाही) + अंतर्गत links सत्यापित करा + रॅचेट केलेले i18n coverage.

### 11. भ्रमनिर्मिती-विरोधी / सुसंगतता (दुर्मीळ श्रेणी)

- **OmniRoute:** known-symbols (string dispatch ⇒ सक्रिय symbol), provider-consistency, fetch-targets (client fetch ⇒ वास्तविक route), docs-symbols, db-rules (Hard Rules #2/#5), migration-numbering.
- **सर्वसाधारण:** प्रत्येक "डुप्लिकेट केलेल्या सत्य-स्रोतासाठी" (registry, string dispatch, cross-layer references), दोन्ही बाजू जुळतात हे सिद्ध करणारे gate. typecheck/test ला न सापडणारा ऱ्हास हे पकडते.

### 12. लवचिकता आणि डोमेन (उत्पादन-विशिष्ट)

- **OmniRoute:** chaos (fault-injection), heap-growth (leak), k6 (soak), promptfoo+garak (LLM red-team OWASP LLM Top 10), लवचिकतेचे 3 नियम (circuit-breaker/cooldown/lockout).
- **सर्वसाधारण:** **तुमच्या** डोमेनमधील अपयशाचे प्रकार ओळखा आणि प्रत्येकासाठी एक gate ठेवा (जरी ते दररात्री चालणारे असले तरीही). AI apps साठी: injection red-team. distributed systems साठी: chaos + leak + soak.

## भाग 4 — कोणत्याही प्रकल्पासाठी प्रतिकृतीकरण योजना

**टप्प्यांमध्ये** तयार करा; प्रत्येक टप्प्याने स्वतंत्रपणे मूल्य दिले पाहिजे. सर्व 12 श्रेणी एकाच वेळी लागू करण्याचा प्रयत्न करू नका —
त्यामुळे भाग 2 मध्ये नमूद केलेला गेट थकवा नेमका निर्माण होतो. प्रत्येक नवीन गेट सुरुवातीला **सल्लात्मक** असतो आणि
स्थिर झाल्यावर **अवरोधक** बनतो.

### पुनर्वापरयोग्य केंद्रबिंदू: "रॅचेट गेटची रचना"

संपूर्ण प्रणाली या 3-फाइल नमुन्याभोवती फिरते. प्रथम त्याची प्रत बनवा:

1. **`baseline.json`** — स्थिर केलेले मेट्रिक मूल्य + `direction` (`up`/`down`) + `eps` (अनिश्चित चढ-उतार प्रतिबंध) + `tightenSlack` + `dedicatedGate`.
2. **`collect-metrics.<ext>`** — साधन चालवते, संख्या काढते आणि `metrics.json` लिहिते.
3. **`check-ratchet.<ext>`** — `metrics.json` ची `baseline.json` शी तुलना करते; `eps` च्या पलीकडे घसरण झाली **तरच** `exit 1`; साधन/पायाभूत सुविधा उपलब्ध नसल्यास `exit 0` (सुरळीत वगळणे); `--require-tighten` सह, बेसलाइन अद्ययावत न करता **सुधारणा** झाली असल्यास `exit 1` (झालेली सुधारणा कायम करते).

हे कार्यरत झाल्यावर, **प्रत्येक** नवीन मेट्रिक (कव्हरेज, जटिलता, चेतावण्या, SAST सूचना, बंडल आकार, म्युटेशन स्कोअर…) बेसलाइनमधील केवळ एक ओळ असते.

### टप्पा 0 — पाया (आठवडा 1)

CI अस्तित्वात आहे; फॉर्मॅटर + लिंटर + टाइपचेक + 1 टेस्ट रनर + कव्हरेजची **निरपेक्ष** किमान मर्यादा
(उदा., 60%). प्री-कमिटमध्ये जलद आणि आपोआप दुरुस्त करता येणाऱ्या तपासण्या चालतात. _निष्पत्ती: कोणताही PR मूलभूत बाबी बिघडवत नाही._

### टप्पा 1 — रॅचेट इंजिन (आठवडा 2) — **सर्व गोष्टींचा पाया**

वरील 3 फाइल्स अमलात आणा. पुढील गोष्टींसाठी बेसलाइन स्थिर करा: चेतावण्या, कव्हरेज, जटिलता, पुनरावृत्ती,
डेड कोड, फाइल आकार. _निष्पत्ती: यापुढे कोडबेसमध्ये केवळ सुधारणा होऊ शकते._

### टप्पा 2 — स्थिर विश्लेषणाची सखोलता (आठवडा 3)

सूचना रॅचेटसह SAST (CodeQL/Sonar/semgrep); सिक्रेट्स स्कॅनर (**डीफॉल्ट रूलसेट वारशाने घ्या**);
SCA (osv/Dependabot) + परवाना अनुमतिसूची + lockfile-lint. _निष्पत्ती: ज्ञात असुरक्षा आणि
उघड झालेली सिक्रेट्स तपासणी पार करत नाहीत._

### टप्पा 3 — बिल्ड पुरवठा-साखळी (आठवडा 4)

प्रकाशनाच्या वेळी SBOM + स्वाक्षरी केलेला उगम-पुरावा (SLSA L2) + नियोजित Scorecard + वर्कफ्लो मजबुतीकरण
(zizmor: किमान टोकन्स, कायमस्वरूपी क्रेडेन्शियल्स नाहीत, पिन केलेल्या ॲक्शन्स). _निष्पत्ती: शोध घेता येण्याजोगी आणि
छेडछाड-प्रतिरोधक प्रकाशने._

### टप्पा 4 — चाचणीची तीव्रता (आठवडे 5–6)

उपयुक्त असल्यास दुसरा रनर; **गंभीर मॉड्यूल्ससाठी प्रति-मॉड्यूल कव्हरेजच्या किमान मर्यादा** (Goodhart-विरोधी);
शुद्ध लॉजिकसाठी प्रॉपर्टी-आधारित चाचणी; **दररोज रात्री म्युटेशन चाचणी** → पहिला स्कोअर मिळाल्यावर,
`mutationScore` ला रॅचेट बनवा. _निष्पत्ती: कव्हरेज हे दिखाऊ मेट्रिक राहात नाही; चाचण्या बग शोधतात हे सिद्ध होते._

### टप्पा 5 — करार आणि डायनॅमिक विश्लेषण (आठवडा 7)

सार्वजनिक API असल्यास: oasdiff (ब्रेकिंग बदल, **अवरोधक**) + schemathesis (रात्रीचे फझिंग).
डोमेनसाठी योग्य असल्यास रात्री DAST/रेड-टीम चाचण्या. _निष्पत्ती: करार नकळत मोडत नाहीत._

### टप्पा 6 — भ्रम-प्रतिबंध आणि डोमेन (आठवडा 8)

प्रकल्पातील प्रत्येक "डुप्लिकेट सत्यासाठी" एक सुसंगतता गेट. डोमेन-विशिष्ट अपयश-प्रकार
गेट्स (AI साठी: इंजेक्शन रेड-टीम). _निष्पत्ती: संरचनात्मक ऱ्हास आणि डोमेन अपयशांसाठी सुरक्षा जाळे उपलब्ध असते._

### टप्पा 7 — प्रशासन (सतत)

- प्रत्येक नवीन गेटसाठी सल्लात्मक→अवरोधक चक्र.
- `stale-allowlist`: प्रत्येक अपवादासाठी समर्थनात्मक कारण + इश्यू असतो; कालबाह्य अपवाद शोधला जातो.
- `evidence-gate`: PR मधील यशाच्या दाव्यासाठी पुरावा (चाचणी किंवा सतत अद्ययावत राहणारी चाचणी) आवश्यक असतो.
- **प्रत्येक गेटचे तिमाही ROI पुनरावलोकन** (परतावा न देणारे गेट्स बंद करा/त्यांचा निधी थांबवा — यामुळे थकवा कमी होतो).
- आपल्या प्रकल्पातील कठोर नियमांचे अंमलबजावणीयोग्य गेट्समध्ये रूपांतर करा.

### सर्व टप्प्यांना लागू होणारी तत्त्वे (तडजोड न करण्याजोगी)

- **निरपेक्ष मर्यादा नव्हे, रॅचेट.** निश्चित संख्येऐवजी _घसरण होऊ न देणे_ गेट करा (शून्य-प्रतिबंधक किमान मर्यादा वगळता).
- **निरपेक्ष किमान मर्यादा आणि रॅचेट एकत्र.** किमान मर्यादा कोसळणे रोखते; रॅचेट हळूहळू होणारी घसरण रोखते.
- **रचनेतच Goodhart-विरोध.** प्रत्येक लक्ष्य मेट्रिकला प्रतिसंतुलन आवश्यक आहे (कव्हरेज ⇒ म्युटेशन + मास्किंग-प्रतिबंध; कठीण कोडची चाचणी करवून घेण्यासाठी प्रति-मॉड्यूल किमान मर्यादा).
- **सुरळीत वगळणे.** पायाभूत सुविधा उपलब्ध नसल्याने कधीही अडथळा येत नाही; केवळ वास्तविक घसरण अडथळा आणते.
- **खर्चिक मेट्रिक्ससाठी `dedicatedGate`.** बाह्य बायनरी आवश्यक असलेल्या मेट्रिक्सना मध्यवर्ती सिंक्रोनस रॅचेटच्या बाहेर, वगळण्याच्या सोयीसह स्वतंत्र स्क्रिप्ट मिळते.
- **जिथे मर्ज होते तिथे गेट लावा.** जलद गेट आणि प्रत्यक्ष मर्ज यांच्यात अंतर ठेवू नका (फास्ट-गेट्स विभाजनातून मिळालेला धडा).
- **मोजके आणि योग्य निवडलेले अवरोधक गेट्स.** Sonar/DORA: खूप अटी = थकवा. अवरोधक गेट्सच्या भिंतीपेक्षा सल्लात्मक गेट्स + रॅचेटला प्राधान्य द्या.

## भाग 5 — शिफारस केलेल्या सुधारणा (प्राधान्यक्रमानुसार, सुसंगत)

**P0 — सर्वाधिक ROI, जवळजवळ तयार**

1. **Mutation score ratchet** (पहिल्या nightly Stryker रनने मूल्ये तयार केल्यानंतर). coverage-Goodhart विरुद्धचा प्रमुख उपाय; ~90% पूर्ण.
2. **उर्वरित fast-gates त्रुटी दूर करा** — `quality.yml` मधील production build चा
   सल्लागार आठवडा पूर्ण झाल्यानंतर त्याला अनिवार्य करा आणि deterministic release-PR-only तपासण्या PR→release मार्गामध्ये हलवत राहा.
3. **`main` वर branch-protection** (मालकाचे setting) — Scorecard वाढवते, DSOMM मधील तफावत दूर करते.

**P1 — मौल्यवान** 4. **osv/oasdiff → योग्य व्याप्तीसह blocking** — osv केवळ CRITICAL+fixable (Trivy प्रमाणे दोन टप्प्यांत); oasdiff breaking-changes अवरोधित करते. 5. **`require-tighten` → blocking** (चक्राच्या शेवटी) — metric मधील सुधारणा कायम करते. 6. **`ci-summary` मध्ये प्रत्येक gate साठी ROI/timing पुनरावलोकन** — संथ/कमी-मूल्य असलेले gates शोधून काढा आणि हटवा.

**P2 — घटता परतावा** 7. **SLSA L3** — तुम्हाला L2 वरून पुढे जायचे असल्यास hermetic/reproducible builder (GitHub SLSA generator). 8. **Committed CodeQL config + versioned semgrep** — अधिक नियंत्रण/reproducibility. 9. **प्रत्येक PR साठी DAST smoke** — सर्वाधिक जोखमीच्या endpoints वर schemathesis/promptfoo चा जलद subset (केवळ nightly नाही). 10. **Flakiness dashboard + DORA metrics** — gates मुळे गती कमी होत नाही याची खात्री करा.

## भाग 6 — प्रत्यक्ष release मधून घेतलेले धडे (Phase 9 मध्ये जोडायचे gates)

> या विभागात release closure दरम्यान घडलेल्या अशा प्रत्यक्ष घटनांची नोंद आहे, जिथे एखादा gate **उपस्थित नव्हता**,
> तसेच ठोस पुरावे आणि प्रस्तावित gate दिले आहेत. प्रत्येक बाब भाग 5 साठी उमेदवार आहे.

### धडा v3.8.27 (2026-06-17) — "fast-gates hole" मुळे deterministic regressions release च्या दिवसापर्यंत पोहोचतात

**काय घडले.** v3.8.27 च्या `/generate-release` दरम्यान, release PR (`release/v3.8.27` → `main`)
हे एकत्रित चक्रातील संपूर्ण `ci.yml` matrix चे **पहिले** execution होते. परिणाम: एकाच वेळी 12 failures
— **3 deterministic tests** + ~9 flakes/env. यापैकी कोणतीही प्रत्यक्ष product regression नव्हती, परंतु
त्या सर्व दुर्लक्षित राहिल्या, कारण cycle PRs **Fast QG
(`quality.yml`)** द्वारे `release/**` मध्ये प्रवेश करतात; हे पूर्ण unit suite, `pr-test-policy` (test-masking),
पूर्ण integration suite किंवा schema parity checking यांपैकी काहीही चालवत नाही. त्या 3 deterministic समस्या:

1. **UI बदलामुळे test कालबाह्य** — `permissions modal switch buttons declare button type`:
   #4034 ने चौथा switch जोडला (`type="button"` ही a11y खूण कायम ठेवली); test मधील `=== 3` ही संख्या
   कालबाह्य झाली. Static analysis ने हे #4034 PR मध्येच शोधायला हवे होते.
2. **Packaging बदलामुळे test कालबाह्य** — `findMissingArtifactPaths ... root runtime files`:
   `dist/http-method-guard.cjs` हा योग्य required-path बनला; test ची अपेक्षित यादी
   कालबाह्य झाली.
3. **माहिती गमावणारी modularization divergence (सर्वात गंभीर)** — `settings schemas accept ... unprefixed
toggle`: **modularized** `updateSettingsSchema` (`schemas/settings.ts`, #3988 द्वारे तयार केलेले) हे
   canonical आवृत्तीपासून (`settingsSchemas.ts`) वेगळे झाले: **45 fields विरुद्ध 85 — 40 वगळलेले + 6 भिन्न (qdrant\*)**. ते
   **dead-code** होते (runtime canonical आवृत्ती वापरते), त्यामुळे प्रत्यक्ष परिणाम झाला नाही; मात्र केवळ हाताने लिहिलेल्या parity
   test ने हे शोधले. #4030 ने #3988/#3993 मधील याच प्रकारे वगळलेले 16 भाग पुनर्स्थापित केले, पण हे त्यातून निसटले.

**प्रस्तावित gates (Phase 9):**

- **G1 — fast-gates त्रुटी प्रत्यक्षात दूर करा (P0 #2 चा विस्तार).** `quality.yml` मध्ये (PR→`release/**`),
  typecheck + impacted tests व्यतिरिक्त **`pr-test-policy` (test-masking) + संपूर्ण deterministic
  unit suite** चालवा (किंवा किमान static/parity files, जे जलद आणि non-flaky आहेत).
  अशा प्रकारे कालबाह्य tests आणि assert removal यांना सादर करणाऱ्या PR मध्येच शोधले जाईल — release च्या
  दिवशी नाही. integration/e2e वगळा (संथ/flaky), परंतु deterministic layer केवळ
  PR→main मध्येच ठेवता येणार नाही.
- **G2 — Modularization parity gate (नवीन, सध्या समाविष्ट नाही).** modularized barrel (`src/shared/validation/schemas/*`, `providerRegistry`
  modules इत्यादी) द्वारे पुन्हा export केलेल्या प्रत्येक symbol साठी **shape** (`z.object` keys, registry entries) ची canonical
  source शी तुलना करणारी आणि **divergence आढळल्यास fail होणारी** तपासणी (वगळलेले/अतिरिक्त field). यामुळे #3988 मधील 40-field drop
  त्याच PR मध्ये शोधला गेला असता. हे हाताने लिहिलेल्या parity tests चे सामान्यीकरण करते (जे फक्त एखाद्याला ते लिहिण्याची
  आठवण झालेल्या ठिकाणीच अस्तित्वात आहेत). स्वस्त: दोन्ही import करून `Object.keys(shape)` मधील फरक तपासते.
- **G3 — Deterministic flake triage (साहाय्यक).** LiveWS-startup आणि integration-combo/breaker
  tests हे logic मुळे नव्हे, तर CI मधील server timeout/cascade (env) मुळे fail होतात. त्यांना
  `known-flaky` म्हणून चिन्हांकित करा (issue सह quarantined), जेणेकरून release-PR मधील red हे **केवळ खरे संकेत** दर्शवेल आणि
  मधोमध असलेल्या deterministic regressions ला झाकणारा गोंधळ नसेल.

**तत्त्व:** _जिथे merge होते तिथेच gate चालला पाहिजे_ ("Cross-cutting principles" मध्ये हे आधीच नमूद केले आहे).
v3.8.27 ची घटना दर्शवते की हे केवळ lint/typecheck साठीच नव्हे, तर **deterministic test layer** साठीही लागू होते —
अन्यथा कालबाह्य tests + माहिती गमावणाऱ्या modularization चे तांत्रिक कर्ज फक्त PR→main मध्ये, एकाच batch मध्ये आणि
सर्वात वाईट क्षणी समोर येते.
