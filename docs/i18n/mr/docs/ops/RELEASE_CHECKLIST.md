## npm Trusted Publishing (v3.8.51 पासून डीफॉल्ट) — विनंतीनुसार staged, पर्याय म्हणून direct

`npm-publish.yml` डीफॉल्टनुसार **npm Trusted Publishing (OIDC)** द्वारे प्रकाशित करते:
`stage-npm` job (github-hosted) त्या रनसाठी GitHub च्या id-token ची अल्पकालीन npm
credential शी देवाणघेवाण करते — repository secrets मध्ये दीर्घकालीन npm token नाही, 2FA prompt नाही आणि provenance जोडलेला असतो.
2FA वगळणारे token निवृत्त केले जात असल्यामुळे npm आता मान्य करत असलेला हा bypass आहे;
यामुळे WS1.3 ची हमी कायम ठेवत प्रकल्पात v3.8.48 पर्यंत असलेला पूर्णपणे स्वयंचलित
प्रवाह पुन्हा उपलब्ध होतो (लीक झालेला token एकट्याने प्रकाशित करू शकत नाही — कारण token अस्तित्वातच नाही).

**एकदाच करायचे सेटअप (मालक):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none). हे अस्तित्वात येईपर्यंत स्वयंचलित पायरी `ENEEDAUTH` सह अयशस्वी होते:
`publish_mode=staged` (खाली) किंवा `direct` वापरून पुन्हा dispatch करा.

### Staged प्रकाशन (विनंतीनुसार — `publish_mode=staged`)

npm-publish workflow आता थेट प्रकाशित करत नाही: ती पॅक केलेला tarball
(`check:pack-boot`) बूट करते आणि नंतर `npm stage publish` चालवते — नेमके तेच bytes registry वर ठेवले जातात,
परंतु मालकाने मंजुरी देईपर्यंत ते **इन्स्टॉल करता येत नाहीत**. मानवी 2FA तपासणी
पुराव्याआधी नव्हे, तर त्यानंतर हलवली आहे.

**workflow हिरवी झाल्यानंतरचा मालकाचा प्रवाह:**

1. `npm stage list omniroute` — stage id शोधा (तो workflow summary मध्येही छापला जातो).
2. staged bytes सत्यापित करा (शिफारस केलेले): `npm stage download <id>`, त्यानंतर डाउनलोड केलेला
   tarball तात्पुरत्या prefix मध्ये इन्स्टॉल करून तो बूट करा (`npm run check:pack-boot` CI मध्ये
   हाच pack→install→boot निकाल स्वयंचलित करते).
3. `npm stage approve <id>` — 2FA prompt म्हणजेच प्रकाशन. `npm stage reject <id>` ते रद्द करते.
4. प्रकाशनानंतरची सुरक्षा-जाळी: post-publish verifier (v3.8.49 योजनेतील WS1.4)
   सार्वजनिक registry मधून प्रकाशित आवृत्ती स्वच्छ container मध्ये इन्स्टॉल करून ती बूट करते.

**आणीबाणीतील पर्याय:** `publish_mode=direct` सह `workflow_dispatch` केल्यास जुने
तात्काळ `npm publish` पुनर्स्थापित होते (staging मध्येच बिघाड झाल्यास फक्त तेव्हाच वापरा; कारण नोंदवा).

**एकदाच करायचे hardening (मालक, npmjs.com):** `omniroute` साठी Trusted Publisher
stage-only mode मध्ये configure करा, जेणेकरून लीक झालेला दीर्घकालीन token कुठूनही थेट `npm publish`
करू शकणार नाही — CI केवळ stage करू शकते; फक्त मालकाचे 2FA रिलीज करू शकते.

**दोषपूर्ण artifact साठी playbook (अपरिवर्तित):** डीफॉल्ट प्रतिसाद म्हणून
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` वापरा (काही मिनिटांत, परत पूर्ववत करता येण्याजोगे);
`npm unpublish` फक्त 72h/no-dependents मर्यादेत आणि पहिली कृती म्हणून कधीही नाही. Docker:
आवृत्तीचा tag कधीही पुन्हा लिहू नका — rollback म्हणजे `latest` ला शेवटच्या योग्य digest कडे पुन्हा निर्देशित करणे.

**Docker Hub `latest` (प्रत्येक स्थिर SemVer प्रकाशनासाठी आवश्यक):**
`docker-publish` workflow ने **दोन्ही** `X.Y.Z` आणि,
`should-promote-latest.sh` ही सर्वात उच्च स्थिर SemVer आवृत्ती असल्याचे मान्य करत असेल तेव्हा, `:latest`
यांना **समान digest** सह tag करणे आवश्यक आहे. job नंतर: Hub वरील `latest` digest नवीन
SemVer digest च्या समान असतो आणि `last_updated` पुढे सरकलेले असते. रिलीज नोंदींमध्ये फक्त git वर
अस्तित्वात असलेल्या सुधारणांचा उल्लेख असताना `:latest` एखाद्या जुन्या build वर ठेवू नका. Compose
quickstart मध्ये `:latest` वापरले जाते; GitOps ने `X.Y.Z` pin करणे सुरू ठेवावे.
[Docker रिलीज channels](../guides/DOCKER_GUIDE.md#release-channels) आणि #10317 पहा.

## हॉटफिक्स फास्ट-लेन (`hotfix` लेबल)

`hotfix` लेबल असलेला PR जड CI मॅट्रिक्स (9-शार्ड E2E, coverage ratchet,
quality-gate, quality-extended) वगळतो आणि जलद, उच्च-सिग्नल गेट्स कायम ठेवतो: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
आणि tarball boot-smoke (`check:pack-boot`). लक्ष्य: ~33min ऐवजी ≤15min मध्ये यशस्वी निकाल.

**प्रवेश धोरण — चारही अटी आवश्यक (Chromium/VS Code/Node आपत्कालीन लेन्सवर आधारित):**

1. **तीव्रता**: production बंद पडले आहे — प्रकाशित artifact boot होताना क्रॅश होते /
   सुरक्षा दुरुस्ती / रिलीजचा प्रत्येक वापरकर्ता प्रभावित झाला आहे. "महत्त्वाचे" म्हणजे "बंद पडलेले" नव्हे.
2. **अधिकार**: फक्त repository मालक `hotfix` लेबल लावतो. लेबल हेच
   अनुमोदन आहे — campaign PR वर ते स्वतःहून कधीही वापरू नका.
3. **पुरावा**: PR body मध्ये मागील पूर्णपणे यशस्वी heavy run ची लिंक (वगळलेले jobs
   जी suite पुन्हा validate करतील) आणि त्या दुरुस्तीची स्वतःची आधी अपयशी व नंतर यशस्वी झालेली test दिलेली असते.
4. **व्याप्ती**: फक्त cherry-pick — किमान आवश्यक दुरुस्ती, refactors नाहीत, असंबंधित बदल नाहीत.

वगळलेली coverage/ratchet व्याप्ती release branch वरील पुढील पूर्ण run द्वारे
पुन्हा validate केली जाते (सतत release-green) — ही lane फक्त प्रतीक्षा वगळते, validation कधीही नाही.
फक्त tests मधील बदल (`tests/` अंतर्गत सर्व files, `tests/e2e/` अंतर्गत एकही नाही) कोणत्याही
लेबलशिवाय E2E मॅट्रिक्स आपोआप वगळतात.

- **pre-push:** जलद निर्धारक gates — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (2026-06-13 रोजी सक्रिय केले). `test:unit` हेतुपुरस्सर वगळले आहे (संथ; CI मधील `test-unit` job द्वारे समाविष्ट).

### Conventional Commits

रिलीजमध्ये जाणाऱ्या सर्व commits नी `type(scope): subject` format चे पालन केले पाहिजे.

**वैध scopes:** `db`, `sse`, `oauth`, `dashboard`, `api`, `cli`, `docker`, `ci`, `mcp`, `a2a`, `memory`, `skills`, `cloud-agent`, `guardrails`, `compression`, `auto-combo`, `resilience`, `providers`, `executors`, `translator`, `domain`, `authz`

### Build मांडणी

Repository तीन स्वतंत्र output directory वापरते — त्यांची कधीही सरमिसळ करू नका:

| Directory | उद्देश                                                                  | Track केलेले?     |
| --------- | ----------------------------------------------------------------------- | ----------------- |
| `src/`    | Application स्रोत (TypeScript / TSX)                                    | होय               |
| `.build/` | Build intermediate — `next build` output (`distDir`)                    | नाही (gitignored) |
| `dist/`   | वितरित करण्यायोग्य npm bundle — `assembleStandalone` द्वारे तयार केलेले | नाही (gitignored) |

> **Operator नोंद:** remote VPS वरील image directory अजूनही `/usr/lib/node_modules/omniroute/app/` आहे.
> केवळ **repository मधील** build output बदलले (`app/` → `dist/`). Deploy skill,
> `dist/` मधील सामग्री remote `app/` directory मध्ये rsync करतात — VPS path मध्ये कोणताही बदल आवश्यक नाही.

**एकल-build प्रवाह:**

```
npm run build:release
  └─ rm -rf .build dist          (स्वच्छता)
  └─ next build → .build/next/   (intermediate)
  └─ assembleStandalone          (standalone + static + public + natives → dist/ मध्ये कॉपी करते)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Deploy साठी `npm run build` चालवल्यानंतर स्वतंत्रपणे `npm run build:cli` चालवू नका — त्याऐवजी
`npm run build:release` वापरा, जे एका command मध्ये स्वच्छ rebuild + sentinel तयार करते.

v3.8.59 नंतरची पुढील आवृत्ती 3.9.0 आहे आणि तिचे टोक दोन दीर्घकाळ अस्तित्वात राहणाऱ्या शाखांमध्ये रूपांतरित होते:
`stable/v3` (v3 LTS शृंखला, npm `latest`) आणि `develop` (v4, 4.0.0 पर्यंत वाढवलेली, npm
`nightly`). शाखा/चॅनेल मॉडेल, फॉरवर्ड-पोर्ट आणि लेबल्स
[RELEASE_STRATEGY.md](./RELEASE_STRATEGY.md) मध्ये आहेत; योजना [ROADMAP](../../ROADMAP.md) (टप्पा 3) मध्ये आहे. हा कट एकदाच चालतो;
3.8.58 मध्ये फोर्कवर त्याचा सुरुवातीपासून शेवटपर्यंत पूर्वाभ्यास केला जातो आणि 3.8.59
[GO/NO-GO तपासणीसूची](./LTS_GO_NO_GO.md) सह पूर्ण होते.

### ड्राय-रन (केवळ-वाचन, कधीही सुरक्षित)

```bash
npm run release:dry-run-lts-cut                       # प्रत्यक्ष कट: HEAD पासून 3.9.0, मागील टॅग v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # स्रोत कमिट निश्चित करा
```

`scripts/release/dry-run-lts-cut.mjs` काहीही कार्यान्वित करत नाही: ते git आणि `gh` वाचते आणि
संपूर्ण क्रम छापते — पूर्वअटी (स्रोताचे निराकरण होते, मागील टॅग अस्तित्वात आहे, `package.json` मध्ये
लक्ष्य आवृत्ती आहे, एक `release-freeze` इश्यू उघडा आहे, अस्तित्वात असलेल्या रिलीज शाखेवर कोणताही उघडा
`Release branch not green` इश्यू नाही — अस्तित्वात नसलेल्या शाखेसाठी `?` अज्ञात असा अहवाल मिळतो, ती कधीही
हिरवी मानली जात नाही — Mergify `release` रांग कॉन्फिगर केलेली आहे (G11: `queue_rules`, `checks_timeout`,
लेबल `queue`), `release/*` नियमसंच अजूनही हटवणे आणि फोर्स-पुश अवरोधित करतो आणि
`stable/v3` व `develop` अद्याप अस्तित्वात नाहीत), दोन शाखा पायऱ्या, कोणते निष्क्रिय वर्कफ्लो
ट्रिगर आणि `if:` अटी सत्य होतात (आणि कोणते रिपॉझिटरी व्हेरिएबलद्वारे प्रतिबंधित राहतात किंवा
अधिकृत रिपॉझिटरीशी निश्चित केलेले राहतात), अपेक्षित dist-tags (`latest` → 3.9.0, `next` आणि
`nightly` रिकामे) आणि रोलबॅक. निर्गमन `0` = `RESULT: READY`, `1` = अवरोधक पूर्वअट
अयशस्वी (`✗`), `2` = वापरातील त्रुटी. `--advisory <id,...>` तपासणी न लपवता तिचा दर्जा
इशाऱ्यापर्यंत (`!`) कमी करते.

3.9.0 रिलीज फ्रीझ अद्याप खुला असतानाच प्रत्यक्ष कटचा ड्राय-रन चालवा — टॅगनंतर आणि
टप्पा 12c मध्ये फ्रीझ उठवण्यापूर्वी शाखा तयार केल्या जातात.

### 3.8.58 पूर्वाभ्यास (केवळ फोर्क)

```bash
# 1. पूर्वाभ्यासाच्या पॅरामीटर्ससह वर्तमान टोकावर ड्राय-रन करा
npm run release:dry-run-lts-cut -- --target-version 3.8.58 --previous-tag v3.8.57 \

# 3. फोर्कमधील निष्क्रिय वर्कफ्लोंची चाचणी करा (जिथे ड्राय-रन

node scripts/release/dry-run-lts-cut.mjs --execute --rollback --remote rehearsal \
  --target-version 3.8.58 --previous-tag v3.8.57 --advisory freeze,base-green
```

develop बंप कमिट git plumbing वापरून तयार केली जाते (वर्किंग ट्रीला स्पर्श केला जात नाही) आणि
सायकल-ओपन कमिटप्रमाणेच ही पाच फाइल्स बंप करते: `package.json`, `open-sse/package.json`,
`electron/package.json`, `package-lock.json` आणि `docs/openapi.yaml`. `[4.0.0]`
CHANGELOG विभाग आणि त्याचे i18n प्रतिबिंब नंतर `develop` वर, त्याच्या पहिल्या
PR पूर्वी उघडले जातात. स्क्रिप्ट npm dist-tags कधीही बदलत नाही — त्यांचा पूर्वाभ्यास एखाद्या तात्पुरत्या पॅकेजवर करा.

### PR पूर्वावलोकन आर्टिफॅक्ट (एकदाच बिल्ड करा, त्याच बाइट्सना पदोन्नत करा)

`.github/workflows/preview-artifact.yml` PR हेडपासून एक प्रॉडक्शन tarball बिल्ड करते आणि
त्याच अचूक बिल्डचे प्रमाणीकरण करते (#8084 भाग (a)). केवळ त्याच रिपॉझिटरीतील PR; काहीही प्रकाशित केले जात नाही.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # किंवा `preview-artifact` लेबल जोडा
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # पूर्वावलोकन इन्स्टॉल
```

रन `npm ci`, `npm run build:release`, `npm run check:pack-artifact` करतो, tarball पॅक करतो,
`npm run check:pack-boot` (बनावट सीक्रेट्स, तात्पुरती डेटा डिरेक्टरी) चालवतो, पुन्हा पॅक करतो आणि
डायजेस्ट तंतोतंत समान नसल्यास अयशस्वी होतो; त्यानंतर `artifact-identity.json` (हेड SHA, बेस
SHA, लॉकफाइल हॅश, प्लॅटफॉर्म, आर्किटेक्चर, node ABI, बंडलर, बिल्ड धोरण —
`scripts/release/artifact-identity.mjs`) नोंदवतो आणि वेगळ्या जॉबमध्ये tarball चे सत्यापन-प्रमाणपत्र तयार करतो. पूर्वावलोकनाला
पदोन्नत करणे म्हणजे तो tarball इन्स्टॉल करणे: स्रोतापासून पुन्हा बिल्ड करू नका.

### कट (3.9.0, GO नंतर)

1. [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md) मध्ये GO नोंदवलेला आहे.
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` हे `RESULT: READY` छापते.
3. ड्राय-रनने छापलेल्या कमांड्स वापरून `origin` वर शाखा स्वतः तयार करा — स्क्रिप्ट
   `origin` वर पुश करण्यास नकार देते. पुनरावलोकन केलेली develop कमिट पुन्हा वापरण्यासाठी, आधी आपल्या
   फोर्कवर 3.9.0 टोकासह `--execute` पूर्वाभ्यास चालवा; तो दोन्ही SHA छापतो आणि
   त्याच कमिट्स पुश करता येतात:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. पहिला PR मर्ज होण्यापूर्वी `stable/v3` आणि `develop` संरक्षित करा (नियमसंच + मर्ज रांग).
5. शाखा अस्तित्वात आल्यावर निष्क्रिय वर्कफ्लो सक्रिय होतात: `forward-port.yml` (`stable/v3` वर पुश),
   `validate-stable-pr.yml` (`stable/v3` कडे येणारे PR) आणि `nightly-v4-build.yml`
   (`develop` बिल्ड करते). प्रत्यक्ष वापर सुरू करण्यापूर्वी `secrets.FORWARD_PORT_TOKEN` रिपॉझिटरी सीक्रेट सेट करा (जेणेकरून
   फॉरवर्ड-पोर्ट PR वर CI चालेल); मालक रिपॉझिटरी व्हेरिएबल `vars.NIGHTLY_PUBLISH`
   `true` वर सेट करेपर्यंत आणि npm Trusted Publishing ने `nightly-v4-build.yml` स्वीकारेपर्यंत
   nightly प्रकाशन बंदच राहते. चॅनेल निराकरण `scripts/release/dist-tag.mjs` मध्ये आहे आणि तोच
   निराकरणकर्ता `npm-publish.yml` वापरते.
6. चॅनेल्सची पडताळणी करा: `npm view omniroute dist-tags --json` मध्ये `latest` = 3.9.0 दिसते आणि
   v4 प्रकाशित होईपर्यंत `next` / `nightly` नसतात.
7. आवश्यक असल्यास रोलबॅक करा: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   आणि `npm dist-tag add omniroute@3.8.59 latest`.

## रोलबॅक

रिलीजमध्ये गंभीर समस्या असल्यास:

1. `gh release edit vX.Y.Z --prerelease` (नवीनतम नसल्याचे चिन्हांकित करते)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (वापरकर्त्यांनी अद्याप स्वीकारले नसेल तरच)
3. किंवा: `release/vX.Y.0` वर हॉटफिक्स → पॅच रिलीज `vX.Y.(Z+1)`
4. GitHub Discussions आणि Discord मध्ये त्वरित कळवा

## कठोर नियम

- `main` वर कधीही थेट कमिट करू नका
- `main` किंवा `release/*` शाखांसाठी कधीही `git push --force` वापरू नका
- Husky हुक्स (`--no-verify`) कधीही वगळू नका
- गुपिते, क्रेडेन्शियल्स किंवा `.env` फाइल्स कधीही कमिट करू नका
- कव्हरेज ≥60/60/60/60 (स्टेटमेंट्स/ओळी/फंक्शन्स/शाखा) राहिले पाहिजे
- `src/`, `open-sse/`, `electron/` किंवा `bin/` मधील प्रॉडक्शन कोड बदलताना नेहमी चाचण्या समाविष्ट करा किंवा अद्ययावत करा
