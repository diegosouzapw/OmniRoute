पुल रिक्वेस्टसाठी सर्वात लहान, विश्वासार्ह विकास चक्र निवडण्यासाठी हे मार्गदर्शक वापरा. हे खाली लिंक केलेल्या
क्षेत्र-विशिष्ट आर्किटेक्चर आणि सुरक्षा दस्तऐवजांची जागा घेत नाही; ते प्रत्येक सामान्य
बदल प्रकाराला त्याच्या करारांशी, केंद्रित तपासण्यांशी आणि CI व्याप्तीशी जोडते.

## प्रत्येक बदलाचा मार्ग

1. **संपादन करण्यापूर्वी बेस निवडा.** सर्वाधिक सक्रिय `release/v*` शाखा शोधा आणि तिच्या
   टोकापासून शाखा तयार करा. `main` ऐवजी त्या शाखेला लक्ष्य करा. रिलीज फ्रीझ सक्रिय असल्यास, फ्रीझ केलेल्या
   शाखेला लक्ष्य करू नका; [शाखाकरण आणि रिलीज मॉडेल](BRANCHING_MODEL.md) मध्ये
   वर्णन केलेले पुढील सक्रिय चक्र वापरा.
2. **करारांची नावे नोंदवा.** बदलामुळे प्रभावित होणारा प्रत्येक कॅटलॉग, स्कीमा, व्युत्पन्न आर्टिफॅक्ट, सार्वजनिक API किंवा वापरकर्ता
   इंटरफेस ओळखा. खालील तक्त्यात किमान प्रारंभिक संच दिला आहे.
3. **केंद्रित चाचण्या लिहा किंवा अद्ययावत करा.** `src/`, `open-sse/`, `electron/` किंवा
   `bin/` मधील उत्पादन बदलांसाठी त्याच PR मध्ये स्वयंचलित चाचणी आवश्यक आहे. वर्तन सिद्ध करणाऱ्या सर्वात लहान चाचणी फायली
   चालवा आणि त्यानंतर सूचीबद्ध केंद्रित गेट्स चालवा.
4. **व्यापक मॅट्रिक्स CI ला चालवू द्या.** संपूर्ण युनिट शार्ड्स, Vitest, कव्हरेज रॅचेट आणि
   उत्पादन बिल्ड PR वर चालतात. केंद्रित अपयशामुळे व्यापक परिणाम सूचित होत असेल किंवा बदल अनेक उपप्रणाल्यांमध्ये
   पसरत असेल, तेव्हाच व्यापक संच स्थानिक पातळीवर चालवा.
5. **पुनरावलोकनापूर्वी ताळमेळ साधा.** सक्रिय बेस फेच करा, त्यातील नवीन कमिट्स आणि त्याच्या तुलनेतील तुमचा डिफ तपासा,
   त्यानंतर योगदानकर्ता कार्यप्रवाहानुसार बेस रीबेस किंवा मर्ज करा. व्युत्पन्न-फाइल
   आणि कॅटलॉगमधील संघर्ष त्यांच्या स्रोतापासून सोडवा, त्यांना पुन्हा व्युत्पन्न करा, केंद्रित चक्र पुन्हा चालवा आणि
   PR अजूनही सक्रिय रिलीज शाखेलाच लक्ष्य करत असल्याची खात्री करा.
6. **पुरावे नोंदवा.** PR टेम्प्लेटमध्ये चालवलेल्या कमांड्स, जोडलेली किंवा बदललेली प्रत्येक चाचणी फाइल,
   मायग्रेशन्स किंवा फीचर फ्लॅग्ज आणि अद्याप प्रलंबित असलेली कोणतीही केवळ-CI पडताळणी नोंदवा.

## बदलाच्या प्रकारानुसार आदर्श मार्ग

खालील कमांड्स या किमान केंद्रित तपासण्या आहेत; तुम्ही बदललेल्या वर्तनाचा थेट अंतर्भाव करणारी
चाचणी वगळण्याची परवानगी त्या देत नाहीत.

### प्रोव्हायडर

**करार**

- `src/shared/constants/providers/` मधील प्रोव्हायडरची व्याख्या आणि
  `src/shared/constants/providers.ts` मधील तिची रचना.
- `open-sse/config/providerRegistry.ts` किंवा त्यातून वेगळ्या काढलेल्या रजिस्ट्री फायलींमधील मॉडेल्स आणि क्षमता.
- लागू असेल तेव्हा एक्झिक्युटर/ट्रान्सलेटर निवड, OAuth किंवा API-की कॉन्फिगरेशन, डॅशबोर्ड अॅसेट्स आणि व्युत्पन्न
  प्रोव्हायडर संदर्भ.
- सार्वजनिक क्रेडेन्शियल्सनी `resolvePublicCred()` वापरणे आवश्यक आहे; त्रुटी प्रतिसादांनी सामायिक सॅनिटाइज्ड
  त्रुटी हेल्पर्स वापरणे आवश्यक आहे. `docs/security/PUBLIC_CREDS.md` (git; `/docs` मध्ये कम्पाइल केलेले नाही) आणि
  [त्रुटी सॅनिटायझेशन](../security/ERROR_SANITIZATION.md) पहा.

**केंद्रित चक्र**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # कॅटलॉग बदलल्यावर; व्युत्पन्न डिफ कमिट करा
npm run lint
```

प्रभावित झालेल्या प्रत्येक रिक्वेस्ट फॅमिलीचीही चाचणी करा: chat, Responses, images, embeddings, audio किंवा video.
व्युत्पन्न कॅटलॉग आणि गोल्डन डिफ्सचे करारातील बदल म्हणून पुनरावलोकन करा; ते डोळे झाकून स्वीकारू नका.

### राउटिंग

**करार**

- `src/shared/constants/routingStrategies.ts` मधील सार्वजनिक स्ट्रॅटेजी मूल्ये आणि UI मेटाडेटा.
- `open-sse/services/combo.ts` आणि `open-sse/services/combo/` अंतर्गत डिस्पॅच आणि क्रमवारी.
- कॉम्बो स्कीमा, पर्सिस्टन्स, रेझिलियन्स स्थिती, मॉडेल क्षमता आणि API/UI नियंत्रणे.
- वर्तन बदलल्यावर [ऑटो-कॉम्बो इंजिन](../routing/AUTO-COMBO.md) आणि रेझिलियन्स दस्तऐवजीकरण.

**केंद्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # स्ट्रॅटेजी किंवा डिस्पॅचमधील बदल
npm run check:known-symbols      # स्ट्रॅटेजी नोंदणीतील बदल
npm run lint
```

स्थानिक पातळीवर निर्धारक मॉक्ड-अपस्ट्रीम चाचण्या वापरा. लाइव्ह कॉम्बो स्मोक चाचण्यांसाठी क्रेडेन्शियल्स आवश्यक असून त्या
मॅन्युअल आहेत; त्या CI चा पर्याय नाहीत.

### UI / UX

**करार**

- `src/app/` आणि `src/shared/components/` अंतर्गत Next.js रूट/पेज आणि सामायिक कॉम्पोनंट सीमा.
- API प्रतिसादांचे आकार, लोडिंग/रिक्त/त्रुटी स्थिती, कीबोर्ड आणि स्क्रीन-रीडर वर्तन,
  प्रतिसादक्षम लेआउट, थीमिंग आणि लोकेल विस्तार.
- `src/i18n/messages/en.json` मधील इंग्रजी UI स्रोत स्ट्रिंग्स; वापरकर्त्याला दिसणारा नवीन मजकूर हार्ड-कोड करू नका.

**केंद्रित चक्र**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

इंटरॅक्शन किंवा दृश्यात्मक बदलांसाठी अॅप चालवा आणि अरुंद तसेच रुंद व्ह्यूपोर्ट तपासा. CI
उत्पादन बिल्ड आणि व्यापक संच चालवते; दृश्यात्मक वर्तनासाठी तरीही बदलाला अनुरूप केंद्रित कॉम्पोनंट, Playwright
किंवा दस्तऐवजीकृत मॅन्युअल तपासणी आवश्यक आहे.

### i18n

**करार**

- `src/i18n/messages/en.json` हा UI स्रोत आहे; `config/i18n.json` हा लोकेल स्रोत आहे.
- CLI कॅटलॉग्स `bin/cli/locales/` अंतर्गत स्वतंत्रपणे ठेवलेले आहेत.
- ICU प्लेसहोल्डर्स आणि टॅग्ज जसेच्या तसे जतन करा. उत्पादन/प्रोव्हायडर/मॉडेलची नावे,
  प्रोटोकॉल आणि हेडरची नावे, कमांड्स, कोड/JSON आयडेंटिफायर्स, URLs, एन्व्हायर्नमेंट व्हेरिएबल्स किंवा
  `OmniRoute`, `OAuth`, `MCP` आणि `A2A` यांसारख्या संरक्षित संज्ञांचे भाषांतर करू नका. सध्याची स्रोत सूची
  `scripts/i18n/glossary/protected-terms.json` आहे.

**केंद्रित चक्र**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI स्ट्रिंग्स/कॅटलॉग्स बदलल्यावर
npm run lint
```

हे विद्यमान प्रणालीसाठी मार्गदर्शन आहे; तिची साधनव्यवस्था किंवा की मॉडेल विस्तृत करण्याचे आमंत्रण नाही.
पर्यायी प्रणालीची रचना सुरू असताना i18n पॅचेस नेमके आणि मर्यादित ठेवा. टास्कमध्ये व्युत्पन्न भाषांतरे स्पष्टपणे आवश्यक नसल्यास आणि
परिणामी डिफचे तुम्ही पुनरावलोकन केलेले नसल्यास, बाह्य सेवा कॉल करणाऱ्या भाषांतर
कमांड्स चालवू नका.

### CLI

**करार**

- `bin/cli/` मधील सार्वजनिक कमांड्स आणि फ्लॅग्स, व्युत्पन्न केलेल्या API कमांड्स, exit codes, stdout/stderr आणि
  JSON आउटपुटचे स्वरूप, config/environment वर्तन आणि पॅकेज केलेल्या फाइल्स.
- CLI मधील वापरकर्त्याला दिसणाऱ्या स्ट्रिंग्सनी CLI i18n स्तर वापरला पाहिजे आणि `en`/`pt-BR` कॅटलॉग्स सुसंगत ठेवले पाहिजेत.
- समर्थित runtime म्हणून Node आणि प्रकाशित binary contract कायम ठेवा.

**केंद्रित लूप**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # व्युत्पन्न केलेले/बंडल केलेले CLI बदल
npm run check:pack-policy     # पॅकेजच्या सार्वजनिक पृष्ठभागातील बदल
npm run lint
```

जेव्हा वर्तन parsing, फाइल्स किंवा exit status वर अवलंबून असेल, तेव्हा तात्पुरत्या data directory मध्ये अचूक कमांड वापरा. CI अधिक व्यापक package artifact आणि ecosystem तपासण्या करते.

### डेटाबेस

**करार**

- `src/lib/db/` अंतर्गत domain modules; विशिष्ट modules थेट import करा (जुना `localDb.ts` re-export स्तर काढून टाकला आहे).
- `src/lib/db/migrations/` अंतर्गत क्रमांकित, idempotent SQL migrations, transaction सुरक्षा, upgrade
  वर्तन, indexes आणि schema मुळे प्रभावित होणारा प्रत्येक caller.
- Routes आणि handlers कधीही raw SQL थेट चालवत नाहीत.

**केंद्रित लूप**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

migration जोडताना नवीन database आणि आधीच्या schema वरून होणारे upgrade या दोन्हींची चाचणी करा. Database tests नी handles बंद केले पाहिजेत आणि cleanup दरम्यान `resetDbInstance()` कॉल केले पाहिजे. best-effort Bun adapter चा मार्ग बदलतो तेव्हाच `npm run test:bun:db` चालवा; Node हाच अधिकृत आधार राहतो.

### बिल्ड / डिप्लॉय

**करार**

- Root आणि workspace manifests/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/`
  package contents, Electron platform metadata, CI workflows आणि deployment sentinels.
- समर्थित Node ranges आणि `CLAUDE.md` मधील allow-listed Bun वापर अबाधित राहिला पाहिजे.
- Build artifacts ट्रॅक न केलेलेच राहतात; dependency, license, workflow आणि package policies लागू होतात.

**केंद्रित लूप**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency किंवा lockfile मधील बदल
npm run check:pack-policy      # प्रकाशित package surface मधील बदल
npm run lint
```

बदलामुळे compilation, standalone assembly, assets किंवा runtime bundling प्रभावित होत असेल तेव्हाच स्थानिकरीत्या `npm run build` वापरा. केवळ release/deploy प्रमाणीकरणासाठी `npm run build:release` वापरा. CI चे build हे अंतिम cross-platform संकेत आहे; platform-specific Electron बदलांसाठी संबंधित केंद्रित build किंवा smoke पुरावा आवश्यक आहे.

## स्थानिक लूप विरुद्ध CI

| प्रत्येक पॅचसाठी स्थानिकरित्या चालवा                                           | CI व्यापक संकेत पुरवते                                                        |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| वरील थेट वर्तन चाचण्या आणि श्रेणी गेट्स                                        | शार्ड केलेला संपूर्ण युनिट संच आणि क्रमिक चाचण्या                             |
| `npm run lint`                                                                 | Vitest संच आणि कव्हरेज/गुणवत्ता रॅचेट्स                                       |
| प्रभावित करारानुसार आवश्यक असेल तेव्हाच टाइपचेक किंवा बिल्ड                    | उत्पादन बिल्ड, सुरक्षा, दस्तऐवज, अवलंबित्व आणि PR-धोरण गेट्स                  |
| स्वयंचलन वर्तन सिद्ध करू शकत नसेल तेव्हाच मॅन्युअल परस्परसंवाद/लाइव्ह तपासण्या | वर्कफ्लोद्वारे कॉन्फिगर केलेल्या क्रॉस-जॉब इंटिग्रेशन आणि प्लॅटफॉर्म तपासण्या |

यशस्वी केंद्रित लूप हा बदललेल्या कराराबद्दलचा पुरावा आहे; असंबंधित CI तपासण्या
उत्तीर्ण होतील याचा तो पुरावा नाही. त्याचप्रमाणे, प्रत्येक स्थानिक संपादनासाठी संपूर्ण रिपॉझिटरी मॅट्रिक्स पूर्ण होईपर्यंत प्रतीक्षा करू नका.

## समेट तपासणीसूची

पुनरावलोकनाची विनंती करण्यापूर्वी:

- PR चा बेस अजूनही सर्वोच्च सक्रिय `release/v*` शाखा आहे याची खात्री करा.
- तो बेस फेच करा आणि तुम्ही शाखा तयार केल्यापासून समाविष्ट झालेल्या कमिट्सचे पुनरावलोकन करा.
- अनवधानाने झालेले किंवा व्युत्पन्न बदल शोधण्यासाठी `git diff <active-base>...HEAD` चे पुनरावलोकन करा.
- स्रोत अद्ययावत करून आणि आउटपुट पुन्हा व्युत्पन्न करून कॅटलॉग व व्युत्पन्न-दस्तऐवजांमधील संघर्ष सोडवा.
- समेटानंतर PR वर्णनात सूचीबद्ध केलेली प्रत्येक केंद्रित चाचणी/गेट पुन्हा चालवा.
- बदललेल्या बेसशी जुळवून घेण्यासाठी केवळ assertions कमकुवत करू नका किंवा आवश्यक चाचण्या काढून टाकू नका.

रिलीज-फ्रीझ आणि पुनर्लक्ष्यीकरणाच्या नियमांसाठी,
[शाखाकरण आणि रिलीज मॉडेल](BRANCHING_MODEL.md) वापरा. CI च्या संपूर्ण सूचीसाठी,
[गुणवत्ता गेट्स संदर्भ](../architecture/QUALITY_GATES.md) वापरा.
