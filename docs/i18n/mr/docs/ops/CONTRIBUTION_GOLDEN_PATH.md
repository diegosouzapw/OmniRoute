पुल रिक्वेस्टसाठी सर्वात लहान आणि विश्वासार्ह विकास लूप निवडण्यासाठी या मार्गदर्शकाचा वापर करा. हा मार्गदर्शक खाली लिंक केलेल्या क्षेत्र-विशिष्ट आर्किटेक्चर आणि सुरक्षा दस्तऐवजांची
जागा घेत नाही; तो प्रत्येक सामान्य बदल प्रकाराला त्याचे करार, लक्ष केंद्रित केलेल्या तपासण्या आणि CI व्याप्तीशी जोडतो.

## प्रत्येक बदल ज्या मार्गाचे अनुसरण करतो

1. **संपादन करण्यापूर्वी बेस निवडा.** सर्वाधिक आवृत्ती असलेली सक्रिय `release/v*` शाखा शोधा आणि
   तिच्या टोकापासून शाखा तयार करा. `main` ऐवजी त्या शाखेला लक्ष्य करा. रिलीज फ्रीझ सक्रिय असल्यास, फ्रीझ केलेल्या
   शाखेला लक्ष्य करू नका; [शाखाकरण आणि रिलीज मॉडेल](BRANCHING_MODEL.md) मध्ये वर्णन केलेले पुढील सक्रिय चक्र
   वापरा.
2. **करारांची नावे नोंदवा.** बदलामुळे प्रभावित होणारा प्रत्येक कॅटलॉग, स्कीमा, जनरेट केलेला आर्टिफॅक्ट, सार्वजनिक API किंवा वापरकर्ता
   इंटरफेस ओळखा. खालील तक्ता किमान प्रारंभिक संच देतो.
3. **लक्ष केंद्रित केलेल्या चाचण्या लिहा किंवा अद्ययावत करा.** `src/`, `open-sse/`, `electron/` किंवा
   `bin/` मधील प्रॉडक्शन बदलांसाठी त्याच PR मध्ये स्वयंचलित चाचणी आवश्यक आहे. वर्तन सिद्ध करणाऱ्या सर्वात लहान चाचणी फायली चालवा
   आणि त्यानंतर सूचीबद्ध लक्ष केंद्रित केलेले गेट्स चालवा.
4. **CI ला व्यापक मॅट्रिक्स चालवू द्या.** संपूर्ण युनिट शार्ड्स, Vitest, कव्हरेज रॅचेट आणि
   प्रॉडक्शन बिल्ड PR वर चालतात. जेव्हा लक्ष केंद्रित केलेले अपयश व्यापक परिणाम दर्शवते किंवा बदल अनेक उपप्रणाल्यांमध्ये
   पसरलेला असतो, तेव्हाच स्थानिक पातळीवर व्यापक संच चालवा.
5. **पुनरावलोकनापूर्वी ताळमेळ साधा.** सक्रिय बेस फेच करा, त्यातील नवीन कमिट्स आणि त्याच्या तुलनेत तुमचा डिफ तपासा,
   त्यानंतर योगदानकर्ता कार्यप्रवाहानुसार बेस रिबेस किंवा मर्ज करा. जनरेट केलेल्या फायली आणि कॅटलॉगमधील
   संघर्ष त्यांच्या स्त्रोतापासून सोडवा, ते पुन्हा जनरेट करा, लक्ष केंद्रित केलेला लूप पुन्हा चालवा आणि PR अजूनही सक्रिय रिलीज
   शाखेलाच लक्ष्य करतो याची पुष्टी करा.
6. **पुरावे नोंदवा.** PR टेम्पलेटमध्ये चालवलेल्या कमांड्स, जोडलेली किंवा बदललेली प्रत्येक चाचणी फाइल,
   मायग्रेशन्स किंवा फीचर फ्लॅग्स आणि अद्याप प्रलंबित असलेले केवळ-CI प्रमाणीकरण सूचीबद्ध करा.

## बदलाच्या प्रकारानुसार आदर्श मार्ग

खालील कमांड्स या किमान लक्ष केंद्रित केलेल्या तपासण्या आहेत; तुम्ही बदललेले वर्तन थेट तपासणारी चाचणी वगळण्याची
ही परवानगी नाही.

### प्रोव्हायडर

**करार**

- `src/shared/constants/providers/` मधील प्रोव्हायडरची व्याख्या आणि
  `src/shared/constants/providers.ts` मधील तिची रचना.
- `open-sse/config/providerRegistry.ts` किंवा त्यातून वेगळ्या काढलेल्या रजिस्ट्री फायलींमधील मॉडेल्स आणि क्षमता.
- लागू असल्यास एक्झिक्युटर/ट्रान्सलेटर निवड, OAuth किंवा API-की कॉन्फिगरेशन, डॅशबोर्ड मालमत्ता आणि जनरेट केलेला
  प्रोव्हायडर संदर्भ.
- सार्वजनिक क्रेडेन्शियल्सनी `resolvePublicCred()` वापरणे आवश्यक आहे; त्रुटी प्रतिसादांनी सामायिक सॅनिटाइज्ड
  त्रुटी सहाय्यक वापरणे आवश्यक आहे. `docs/security/PUBLIC_CREDS.md` (git; `/docs` मध्ये संकलित केलेले नाही) आणि
  [त्रुटी सॅनिटायझेशन](../security/ERROR_SANITIZATION.md) पहा.

**लक्ष केंद्रित केलेला लूप**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # कॅटलॉग बदलल्यावर; जनरेट केलेला डिफ कमिट करा
npm run lint
```

प्रभावित झालेल्या प्रत्येक विनंती प्रकाराचीही चाचणी करा: चॅट, Responses, प्रतिमा, एम्बेडिंग्ज, ऑडिओ किंवा व्हिडिओ.
जनरेट केलेले कॅटलॉग आणि गोल्डन डिफ्स यांचे करारातील बदल म्हणून पुनरावलोकन करा; ते डोळे झाकून स्वीकारू नका.

### रूटिंग

**करार**

- `src/shared/constants/routingStrategies.ts` मधील सार्वजनिक स्ट्रॅटेजी मूल्ये आणि UI मेटाडेटा.
- `open-sse/services/combo.ts` आणि `open-sse/services/combo/` अंतर्गत डिस्पॅच आणि क्रमवारी.
- कॉम्बो स्कीमा, पर्सिस्टन्स, रेझिलियन्स स्थिती, मॉडेल क्षमता आणि API/UI नियंत्रणे.
- वर्तन बदलल्यावर [ऑटो-कॉम्बो इंजिन](../routing/AUTO-COMBO.md) आणि रेझिलियन्स दस्तऐवजीकरण.

**लक्ष केंद्रित केलेला लूप**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # स्ट्रॅटेजी किंवा डिस्पॅचमधील बदल
npm run check:known-symbols      # स्ट्रॅटेजी नोंदणीमधील बदल
npm run lint
```

स्थानिक पातळीवर निर्धारक मॉक्ड-अपस्ट्रीम चाचण्या वापरा. लाइव्ह कॉम्बो स्मोक्सना क्रेडेन्शियल्स आवश्यक असतात आणि त्या
मॅन्युअल आहेत, CI चे पर्याय नाहीत.

### UI / UX

**करार**

- `src/app/` आणि `src/shared/components/` अंतर्गत Next.js रूट/पृष्ठ आणि सामायिक कॉम्पोनंटच्या सीमा.
- API प्रतिसादांचे आकार, लोडिंग/रिकामी/त्रुटी स्थिती, कीबोर्ड आणि स्क्रीन-रीडर वर्तन,
  प्रतिसादक्षम लेआउट, थीमिंग आणि लोकेल विस्तार.
- `src/i18n/messages/en.json` मधील इंग्रजी UI स्त्रोत स्ट्रिंग्स; नवीन वापरकर्ता-दृश्य मजकूर हार्ड-कोड करू नका.

**लक्ष केंद्रित केलेला लूप**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

परस्परसंवाद किंवा दृश्यात्मक बदलांसाठी अॅप चालवा आणि अरुंद तसेच रुंद व्ह्यूपोर्ट्स तपासा. CI
प्रॉडक्शन बिल्ड आणि व्यापक चाचणी संच चालवते; दृश्यात्मक वर्तनासाठी तरीही बदलाला अनुरूप अशी लक्ष केंद्रित केलेली कॉम्पोनंट चाचणी, Playwright
किंवा दस्तऐवजीकृत मॅन्युअल तपासणी आवश्यक आहे.

### i18n

**करार**

- `src/i18n/messages/en.json` हा UI स्त्रोत आहे; `config/i18n.json` हा लोकेल स्त्रोत आहे.
- CLI कॅटलॉग्स `bin/cli/locales/` अंतर्गत स्वतंत्रपणे ठेवलेले आहेत.
- ICU प्लेसहोल्डर्स आणि टॅग्ज तंतोतंत जतन करा. उत्पादन/प्रोव्हायडर/मॉडेलची नावे,
  प्रोटोकॉल आणि हेडरची नावे, कमांड्स, कोड/JSON आयडेंटिफायर्स, URLs, एन्व्हायर्नमेंट व्हेरिएबल्स किंवा
  `OmniRoute`, `OAuth`, `MCP` आणि `A2A` यांसारख्या संरक्षित संज्ञांचे भाषांतर करू नका. सध्याची स्त्रोत सूची
  `scripts/i18n/glossary/protected-terms.json` आहे.

**लक्ष केंद्रित केलेला लूप**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI स्ट्रिंग्स/कॅटलॉग्स बदलल्यावर
npm run lint
```

हे विद्यमान प्रणालीसाठी मार्गदर्शन आहे; तिची साधने किंवा की मॉडेल विस्तारित करण्याचे आमंत्रण नाही.
पर्यायी प्रणालीची रचना केली जात असताना i18n पॅचेस नेमके आणि मर्यादित ठेवा. कार्यात जनरेट केलेली भाषांतरे स्पष्टपणे आवश्यक नसतील आणि
तुम्ही परिणामी डिफचे पुनरावलोकन केले नसेल, तर बाह्य सेवा कॉल करणाऱ्या भाषांतर कमांड्स चालवू नका.

### CLI

**करार**

- `bin/cli/` मधील सार्वजनिक commands आणि flags, व्युत्पन्न केलेले API commands, exit codes, stdout/stderr आणि
  JSON output shapes, config/environment चे वर्तन आणि package केलेल्या files.
- CLI मधील वापरकर्त्यास दिसणाऱ्या strings नी CLI i18n layer वापरणे आवश्यक आहे आणि `en`/`pt-BR` catalogs परस्पर सुसंगत ठेवले पाहिजेत.
- समर्थित runtime म्हणून Node आणि प्रकाशित binary contract जतन करा.

**केंद्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # व्युत्पन्न केलेले/bundle केलेले CLI बदल
npm run check:pack-policy     # package surface मधील बदल
npm run lint
```

वर्तन parsing, files किंवा exit status वर अवलंबून असेल, तेव्हा तात्पुरत्या data directory मध्ये अचूक command वापरा. CI अधिक व्यापक package artifact आणि ecosystem तपासण्या करते.

### Database

**करार**

- `src/lib/db/` अंतर्गत domain modules; विशिष्ट modules थेट import करा (जुना `localDb.ts` re-export layer काढून टाकण्यात आला आहे).
- `src/lib/db/migrations/` अंतर्गत क्रमांकित, idempotent SQL migrations, transaction safety, upgrade
  वर्तन, indexes आणि schema मुळे प्रभावित होणारा प्रत्येक caller.
- Routes आणि handlers कधीही थेट raw SQL जारी करत नाहीत.

**केंद्रित चक्र**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migration जोडताना नवीन database आणि आधीच्या schema वरून upgrade या दोन्हींची चाचणी करा. Database tests नी cleanup दरम्यान handles बंद करणे आणि `resetDbInstance()` call करणे आवश्यक आहे. सर्वोत्तम प्रयत्नांवर आधारित Bun adapter path बदलतो तेव्हाच `npm run test:bun:db` चालवा; Node हेच अधिकृत राहते.

### Build / deploy

**करार**

- Root आणि workspace manifests/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/`
  package मधील सामग्री, Electron platform metadata, CI workflows आणि deployment sentinels.
- समर्थित Node ranges आणि `CLAUDE.md` मधील allow-listed Bun वापर अबाधित राहिला पाहिजे.
- Build artifacts untracked राहतात; dependency, license, workflow आणि package policies लागू होतात.

**केंद्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency किंवा lockfile मधील बदल
npm run check:pack-policy      # प्रकाशित package surface मधील बदल
npm run lint
```

बदल compilation, standalone assembly, assets किंवा runtime bundling वर परिणाम करत असेल, तेव्हाच स्थानिक पातळीवर `npm run build` वापरा. केवळ release/deploy validation साठी `npm run build:release` वापरा. CI चा build हा अंतिम cross-platform संकेत आहे; platform-specific Electron बदलांसाठी संबंधित केंद्रित build किंवा smoke पुरावा आवश्यक आहे.

## स्थानिक कॅन्डिडेट लूप

स्रोत चाचण्या पॅकेज केलेले आर्टिफॅक्ट सुरू होते हे सिद्ध करू शकत नाहीत: पॅकेजिंग याद्या, काढून टाकलेल्या डिपेंडन्सीज आणि नेटिव्ह बायनरीज यांमधील समस्या tarball इंस्टॉल करून सुरू केल्यानंतरच समोर येतात. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) ही RFC #8084 मधील एकदाच बिल्ड करा / सत्यापित करा / प्रमोट करा या प्रवाहाची स्थानिक बाजू आहे: ती एक कॅन्डिडेट बिल्ड करते, त्याच अचूक आर्टिफॅक्टचे सत्यापन करते, डिरेक्टरींची नावे बदलून त्याला प्रमोट करते आणि प्रमोट केलेल्या स्लॉटची आरोग्य तपासणी अयशस्वी झाल्यास त्याला रोल बॅक करते.

```bash
npm run dev:candidate -- run --dry-run --json  # योजना दाखवा, काहीही बदलू नका
npm run dev:candidate -- run                   # बिल्ड + सत्यापन + प्रमोशन, स्वयंचलित रोलबॅक
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ मध्ये इंस्टॉल करा
npm run dev:candidate -- validate --id <id>    # मोकळ्या पोर्टवर सुरू करा, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current आणि previous यांची अदलाबदल करा
npm run dev:candidate -- run --from-tarball <file.tgz>  # इतरत्र बिल्ड केलेला tarball पुन्हा वापरा (CI)
```

- **एकदाच बिल्ड करा.** `build` सध्याच्या ट्रीचे पॅकेज बनवते (त्यासाठी `dist/server.js` आवश्यक आहे, म्हणून आधी
  `npm run build:release` चालवा) किंवा `--from-tarball` ची प्रत बनवते आणि नंतर tarball एका
  विलग npm prefix मध्ये इंस्टॉल करते, कारण tarball मध्ये `node_modules` नसते. id म्हणजे लहान `HEAD`
  sha (ट्रीमध्ये स्थानिक बदल असल्यास `-dirty`) किंवा tarball साठी `tgz-<sha256>` असते. आधीच बिल्ड केलेला
  स्वच्छ id पुन्हा बिल्ड करण्याऐवजी पुनर्वापरला जातो; तो पुन्हा बिल्ड करण्यासाठी `--force` द्या.
- **स्रोताचे नव्हे, तर पॅकेजचे सत्यापन करा.** `validate` नवीन `DATA_DIR=<candidate>/data`, बनावट सिक्रेट्ससह इंस्टॉल केलेले CLI
  (`serve --port <free port>`) सुरू करते आणि ऑपरेटरची `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` व `INITIAL_PASSWORD`
  पर्यावरणातून काढून टाकते, जेणेकरून ते नव्या इंस्टॉलेशनच्या की-विरहित लूपबॅक स्थितीची तपासणी करेल. ते
  `GET /api/health` कडून 200 प्रतिसाद येईपर्यंत प्रतीक्षा करते, `GET /v1/models` कडून 200 प्रतिसाद मिळणे आवश्यक ठरवते, प्रोसेस ग्रुप थांबवते
  आणि tarball हॅशसह निकाल `validation.json` मध्ये नोंदवते.
- **त्याच आर्टिफॅक्टला प्रमोट करा.** सध्याच्या tarball हॅशसाठी यशस्वी सत्यापन नसलेला कॅन्डिडेट प्रमोट करण्यास `promote`
  नकार देते. डीफॉल्ट सक्रिय स्लॉट `_artifacts/candidate/current` आहे; `--target <dir>`
  त्याच फाइल सिस्टीमवरील दुसरी डिरेक्टरी निवडते आणि तिचा मागील स्लॉट `<dir>.previous` असतो.
  प्रत्येक नामांतर अणुस्वरूपी असते आणि प्रक्रियेच्या मध्यात अपयश आल्यास आधीच झालेली नामांतरे उलटवली जातात.
- **रोल बॅक करा.** `run` प्रमोट केलेल्या स्लॉटचे पुन्हा सत्यापन करते आणि ती तपासणी अयशस्वी झाल्यास
  `current` व `previous` यांची पुन्हा अदलाबदल करते. पहिल्या सत्यापनात अयशस्वी झालेला कॅन्डिडेट कधीही प्रमोट केला जात नाही.

सर्वकाही git द्वारे दुर्लक्षित `_artifacts/candidate/` अंतर्गत लिहिले जाते; विद्यमान OmniRoute
इंस्टॉलेशन आणि त्याची डेटा डिरेक्टरी यांना कधीही स्पर्श केला जात नाही. प्रमोट केलेले CLI
`_artifacts/candidate/current/prefix/bin/omniroute` आहे; ते वापरताना स्वतःच्या `DATA_DIR` सह सुरू करा.
एक्झिट कोड: `0` यश, `1` अयशस्वी सत्यापन किंवा प्रमोशन, `2` वापरातील त्रुटी किंवा बिल्ड उपलब्ध नाही.

यशस्वी होतील याचा तो पुरावा नाही. तसेच, प्रत्येक स्थानिक संपादनासाठी संपूर्ण रिपॉझिटरी मॅट्रिक्स पूर्ण होईपर्यंत प्रतीक्षा करू नका.

## समेट तपासणीसूची

पुनरावलोकनाची विनंती करण्यापूर्वी:

- PR चा बेस अजूनही सर्वाधिक सक्रिय `release/v*` शाखा आहे याची खात्री करा.
- तो बेस फेच करा आणि तुम्ही शाखा तयार केल्यापासून समाविष्ट झालेल्या कमिट्सचे पुनरावलोकन करा.
- अनवधानाने झालेले किंवा व्युत्पन्न बदल तपासण्यासाठी `git diff <active-base>...HEAD` चे पुनरावलोकन करा.
- स्रोत अद्यतनित करून आणि आउटपुट पुन्हा व्युत्पन्न करून कॅटलॉग व व्युत्पन्न दस्तऐवजांमधील संघर्ष सोडवा.
- समेटानंतर PR वर्णनात सूचीबद्ध केलेली प्रत्येक केंद्रित चाचणी/गेट पुन्हा चालवा.
- बदललेल्या बेसशी जुळवून घेण्यासाठी अभिकथने कधीही कमकुवत करू नका किंवा आवश्यक चाचण्या वगळू नका.

रिलीज-फ्रीझ आणि रीटार्गेटिंग नियमांसाठी,
[शाखाकरण आणि रिलीज मॉडेल](BRANCHING_MODEL.md) वापरा. संपूर्ण CI सूचीसाठी,
[गुणवत्ता गेट्स संदर्भ](../architecture/QUALITY_GATES.md) वापरा.
