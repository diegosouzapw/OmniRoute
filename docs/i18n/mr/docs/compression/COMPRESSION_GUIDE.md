> पात्र संदर्भावर स्वयंचलितपणे 15-95% बचत करा. झटपट आढाव्यासाठी, [README मधील Compression विभाग](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) पहा.

## आढावा

OmniRoute एक मॉड्युलर प्रॉम्प्ट कॉम्प्रेशन पाइपलाइन कार्यान्वित करते, जी विनंत्या अपस्ट्रीम प्रदात्यांपर्यंत पोहोचण्यापूर्वीच **सक्रियपणे** चालते. याचा अर्थ तुमची टोकन बचत पारदर्शकपणे होते — तुमच्या कार्यप्रवाहात कोणतेही बदल करण्याची आवश्यकता नाही.

```
क्लायंट विनंती
  → कॉम्प्रेशन धोरण निवडक
    → कॉम्बो ओव्हरराइड? → कॉम्बो सेटिंग वापरा
    → स्वयंचलित-ट्रिगर मर्यादा? → स्वयंचलित मोड वापरा
    → डीफॉल्ट मोड? → जागतिक सेटिंग वापरा
    → Off? → कॉम्प्रेशन वगळा
  → निवडलेला कॉम्प्रेशन मोड
    → Off: कॉम्प्रेशन नाही
    → Lite: सुरक्षित व्हाइटस्पेस/फॉरमॅटिंग स्वच्छता (~15%)
    → Standard: Caveman-शैलीतील अनावश्यक शब्द काढणे (~30%)
    → Aggressive: इतिहासाचे कालबाह्यीकरण + सारांशीकरण (~50%)
    → Ultra: ह्युरिस्टिक छाटणी + कोड-ब्लॉक विरळ करणे (~75%)
    → RTK: कमांड-जागरूक टर्मिनल/टूल-आउटपुट फिल्टरिंग (60-90% अपस्ट्रीम श्रेणी)
    → Stacked: क्रमबद्ध मल्टी-इंजिन पाइपलाइन, सहसा आधी RTK आणि नंतर Caveman (78-95% पात्र श्रेणी)
  → कॉम्प्रेस केलेली विनंती → प्रदाता
```

## कॉम्प्रेशन मोड

### Off

कोणतेही कॉम्प्रेशन लागू केले जात नाही. सर्व संदेश कोणताही बदल न करता पुढे पाठवले जातात.

### Lite मोड (~15% बचत, <1ms विलंब)

सर्वांत सुरक्षित मोड — अर्थामध्ये शून्य बदल, केवळ फॉरमॅटिंगची स्वच्छता:

| तंत्र                    | वर्णन                                                         |
| ------------------------ | ------------------------------------------------------------- |
| `collapseWhitespace`     | सलग रिकाम्या ओळी आणि ओळींच्या शेवटी असलेल्या स्पेस एकत्र करणे |
| `dedupSystemPrompt`      | डुप्लिकेट सिस्टीम संदेश काढून टाकणे                           |
| `compressToolResults`    | विस्तृत टूल/फंक्शन आउटपुट कॉम्प्रेस करणे                      |
| `removeRedundantContent` | पुनरावृत्ती झालेल्या सूचना काढून टाकणे                        |
| `replaceImageUrls`       | base64 प्रतिमा डेटा URI लहान करणे                             |

**यासाठी सर्वोत्तम:** नेहमी-सक्रिय वापर, सुरक्षिततेच्या दृष्टीने महत्त्वाचे कार्यप्रवाह.

### Standard मोड (~30% बचत)

[Caveman](https://github.com/JuliusBrussee/caveman) पासून प्रेरित — अर्थ कायम ठेवून अनावश्यक शब्द आणि पाल्हाळिक वाक्यरचना काढून टाकतो:

- अनावश्यक शब्द काढतो ("कृपया", "मला वाटते", "मूलतः", "प्रत्यक्षात")
- पाल्हाळिक वाक्यांश संक्षिप्त करतो ("करण्याच्या उद्देशाने" → "करण्यासाठी", "याचा परिणाम म्हणून" → "कारण")
- विनम्र पण संदिग्ध वाक्यरचना काढतो ("तुमची हरकत नसेल तर...", "तुम्हाला शक्य असल्यास...")
- कोडिंग प्रॉम्प्टसाठी अनुकूल केलेले 30+ regex नियम

**यासाठी सर्वोत्तम:** दैनंदिन कोडिंग कार्यप्रवाह, खर्चाबाबत जागरूक संघ.

### Aggressive मोड (~50% बचत)

दीर्घ सत्रांसाठी हुशार इतिहास व्यवस्थापन:

- **संदेश कालबाह्यीकरण** — जुने संदेश क्रमाक्रमाने अधिक कॉम्प्रेस केले जातात
- **टूल परिणाम कॉम्प्रेशन** — लांबलचक टूल आउटपुट कापले किंवा वगळले जातात (पहिल्या/शेवटच्या ओळी,
  जुळणाऱ्या ओळींचे फिल्टरिंग, JSON की संक्षिप्तीकरण)
- **संरचनात्मक अखंडता सुरक्षा** — `tool_use` + `tool_result` जोड्या सुसंगत राहतील याची खात्री करते
- **संदर्भ विंडो जागरूकता** — प्रत्येक मॉडेलची टोकन मर्यादा पाळते

**यासाठी सर्वोत्तम:** विस्तारित डीबगिंग सत्रे, मोठे कोडबेस.

### Ultra मोड (~75% बचत)

टोकनच्या दृष्टीने अत्यंत महत्त्वाच्या परिस्थितींसाठी कमाल कॉम्प्रेशन:

- **ह्युरिस्टिक छाटणी** — गद्य मजकुरातील टोकनची गुण-आधारित छाटणी
- **संरचना जतन** — फेन्स केलेले कोड ब्लॉक, इनलाइन कोड, URL आणि आयडेंटिफायर
  टॉम्बस्टोन करून शब्दशः पुन्हा जोडले जातात; त्यांची कधीही छाटणी केली जात नाही
- **पर्यायी SLM स्तर** — कॉन्फिगर केले असल्यास, लहान स्थानिक मॉडेल छाटणी अधिक परिष्कृत करू शकते
- Aggressive मोडपासून स्वतंत्र: तो संदेश कालबाह्यीकरण, टूल-परिणाम कॉम्प्रेशन
  किंवा फॉलबॅक सारांशकार चालवत नाही (केवळ SLM-स्तरातील अपयशामुळे फॉलबॅक पास
  aggressive मधून रूट केला जाऊ शकतो)

**यासाठी सर्वोत्तम:** जेव्हा तुम्ही वारंवार संदर्भ मर्यादेपर्यंत पोहोचता.

### RTK मोड (60-90% अपस्ट्रीम श्रेणी)

RTK मोड कोडिंग-एजंट सत्रांमध्ये दिसणाऱ्या विस्तृत टूल आउटपुटसाठी अनुकूलित केला आहे:

- `git status`, `git diff`, `git log`, चाचणी रनर,
  TypeScript/Vite/Webpack बिल्ड, ESLint/Biome/Prettier, npm ऑडिट/इन्स्टॉल, Docker लॉग, इन्फ्रा
  आउटपुट आणि सर्वसाधारण शेल आउटपुट यांसारखे कमांड/आउटपुट वर्ग शोधतो
- `open-sse/services/compression/engines/rtk/filters/` मधील JSON फिल्टर पॅक लागू करतो
- प्रकल्प किंवा जागतिक `filters.toml` फाइलमधून RTK TOML schema v1 फिल्टर आयात करतो, तसेच इनलाइन-चाचणी
  प्रमाणीकरण आणि प्रकल्प फाइलसाठी विश्वास-आधारित नियंत्रण लागू करतो
- इनलाइन पडताळणी नमुन्यांसह 55 अंगभूत फिल्टर पुरवतो
- ANSI नियंत्रण अनुक्रम, प्रगती पट्ट्या, पुनरावृत्ती झालेल्या ओळी आणि कृतीयोग्य नसलेला अनावश्यक मजकूर काढतो
- अपयश, त्रुटी, इशारे, बदललेल्या फाइल, सारांश आणि लांब आउटपुटचा शेवटचा भाग जतन करतो
- विश्वास-आधारित प्रकल्प फिल्टर, जागतिक फिल्टर आणि पर्यायी संपादित कच्चे-आउटपुट पुनर्प्राप्ती समर्थित करतो

**यासाठी सर्वोत्तम:** शेल, बिल्ड, चाचणी, git, grep आणि फाइल-आउटपुट प्रतिलेख असलेली एजंट सत्रे.

### Stacked मोड (78-95% पात्र श्रेणी)

Stacked मोड अनेक कॉम्प्रेशन इंजिन निश्चित क्रमाने चालवतो. डीफॉल्ट पाइपलाइन अशी आहे:

```txt
RTK -> Caveman
```

या क्रमामुळे प्रथम टर्मिनल/टूल आउटपुट संक्षिप्त ठेवले जाते आणि नंतर उर्वरित
नैसर्गिक-भाषेतील प्रॉम्प्टवर Caveman चे अर्थपूर्ण संक्षिप्तीकरण लागू केले जाते. Stacked पाइपलाइन जागतिक स्तरावर किंवा
रूटिंग कॉम्बोंना नियुक्त केलेल्या कॉम्प्रेशन कॉम्बोंद्वारे कॉन्फिगर केल्या जाऊ शकतात.

**यासाठी सर्वोत्तम:** मोठे टूल लॉग तसेच मानवी सूचना किंवा सहाय्यकाचे सारांश असलेला मिश्र संदर्भ.

## अपस्ट्रीम बचतीचे गणित

OmniRoute दोन स्रोतांमधून मिळणाऱ्या कॉम्प्रेशन बचतीचे दस्तऐवजीकरण करते: अपस्ट्रीम प्रकल्पांचे बेंचमार्क आणि
OmniRoute ची स्वतःची इंजिन रचना.

| स्रोत   | येथे वापरलेली अपस्ट्रीम README मधील संख्या                                                                      |
| ------- | --------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` कमी आउटपुट टोकन, बेंचमार्कमधील सरासरी आउटपुट बचत `65%`, `22-87%` श्रेणी आणि `~46%` इनपुट कॉम्प्रेशन साधन |
| RTK     | कमांड-आउटपुटमध्ये `60-90%` बचत; नमुना सत्रात `~118,000 -> ~23,900` टोकन, म्हणजे `79.7%` बचत (`~80%`)            |

एकमेकांवर आच्छादित होणाऱ्या टूल/कॉन्टेक्स्ट पेलोडसाठी, डीफॉल्ट OmniRoute कॉम्बो इंजिने एकावर एक लावतो:

```txt
RTK -> Caveman
```

एकत्रित बचत गुणाकारात्मक आहे, बेरीजात्मक नाही:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

जेव्हा RTK आणि Caveman दोन्ही एकाच इनपुट/कॉन्टेक्स्ट पेलोडचा आकार कमी करू शकतात, तेव्हा ती `78-95%` संख्या लागू होते.
Caveman चा प्रतिसाद आउटपुट मोड स्वतंत्र आहे: तो सक्षम केलेला असताना, Caveman ची स्वतःची आउटपुट बचत (`65%`
सरासरी, `~75%` प्रमुख दावा, `22-87%` श्रेणी) वापरा. एकूण बिलिंग बचत तुमच्या प्रॉम्प्ट/आउटपुट मिश्रणावर अवलंबून असते.

### "पात्र" असण्याचा नेमका अर्थ काय

15-95% ही प्रमुख श्रेणी वास्तविक आहे, परंतु ती फक्त **पुनरावृत्ती असलेल्या किंवा अनावश्यकरीत्या विस्तृत** मजकुरालाच लागू होते — वारंवार येणाऱ्या
त्रुटी ओळी, तोच इशारा सतत दाखवणारा बिल्ड लॉग, अतिमोठा `grep`/फाइल-रीड डंप. याचा अर्थ
प्रत्येक विनंतीमध्ये इतकी बचत होते असा **नाही**.

प्रत्यक्ष प्रयोगाद्वारे पडताळलेले (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300 एकसारख्या
त्रुटी ओळी असलेला Anthropic-स्वरूपाचा `tool_result` ब्लॉक `stacked` (RTK + Caveman) पद्धतीने चालवल्यावर
**95.93% टोकन बचत / 96.26% अक्षर बचत** मिळाली — म्हणजे ती जाहीर केलेल्या श्रेणीत ठामपणे येते.
परंतु हीच पाइपलाइन सामान्य, पुनरावृत्ती नसलेल्या टूल आउटपुटवर (स्वच्छ `grep` जुळणी सूची,
लहान फाइल रीड, सामान्य संभाषणात्मक मजकूर) चालवल्यावर योग्यरीत्या **जवळपास शून्य बचत** मिळते, कारण
काढून टाकण्यासारखी कोणतीही पुनरावृत्ती नसते आणि कोड ब्लॉक, URLs, शीर्षके, आवृत्त्या किंवा ALL-CAPS स्थिरांक आयडेंटिफायर
काढून टाकणारे अथवा बदलणारे पुनर्लेखन पाठवण्यास `validateCompression()` (`validation.ts`) नकार देते.

हे अपेक्षित आणि सुरक्षित वर्तन आहे, बग नाही: बहुतांश वेळा स्वच्छ फाइल्स वाचणारे/grep करणारे कोडिंग सत्र
कॉम्प्रेशन पूर्णपणे सक्षम असतानाही मर्यादित एकूण बचत दर्शवेल, तर अयशस्वी होणाऱ्या
लूपला किंवा अतिशय बोलक्या लिंटरला सामोरे जाणाऱ्या सत्रात त्या ट्रॅफिकवर पूर्ण 78-95% श्रेणीतील बचत दिसेल. कॉम्प्रेशन चुकीच्या पद्धतीने कॉन्फिगर केले आहे याचा पुरावा म्हणून
एकाच सत्रातील कमी एकत्रित बचत टक्केवारी वापरू नका — आधी मूळ
टूल आउटपुटमध्ये खरोखर पुनरावृत्ती होती का ते तपासा.

## कॉन्फिगरेशन

### डॅशबोर्ड

`Dashboard → Context & Cache` येथे जा:

- **Caveman** — मोड निवड, भाषा पॅक्स, पूर्वावलोकन आणि जागतिक डीफॉल्ट्स
- **RTK** — कमांड-फिल्टर पूर्वावलोकन, RTK सुरक्षा सेटिंग्ज आणि फिल्टर कॅटलॉग
- **Compression Combos** — रूटिंग कॉम्बोंना नियुक्त केलेल्या नामांकित इंजिन पाइपलाइन्स
- **Auto-Trigger Threshold** — टोकन संख्या मर्यादेपेक्षा जास्त झाल्यास कॉम्प्रेशन स्वयंचलितपणे सुरू करा

### प्रत्येक कॉम्बोसाठी ओव्हरराइड

`Dashboard → Context & Cache → Compression Combos` मध्ये, रूटिंग कॉम्बोला कॉम्प्रेशन कॉम्बो नियुक्त करा:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

यामुळे सशुल्क सबस्क्रिप्शन्सवर लाइट मोड कायम ठेवताना विनामूल्य/कोडिंग प्रोव्हायडर्सवर स्टॅक्ड कॉम्प्रेशन वापरता येते.

हे "Per-Combo Override" असाइनमेंट **routing-combo compression mode** ओव्हरराइडपेक्षा (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — या फील्डचे स्कीमा `rtk`, `stacked` आणि `omniglyph` देखील स्वीकारते) वेगळे नियंत्रण आहे — ते ओव्हरराइड नामांकित कॉम्प्रेशन-कॉम्बो पाइपलाइन निवडत नाही; ते केवळ `resolveCompressionPlan` द्वारे तपासले जाणारे `compressionMode` फील्ड सेट करते. ते कॉम्बो कार्डवर (`Dashboard → Combos`) किंवा #6760 पासून, वर दस्तऐवजीकरण केलेल्या पाइपलाइन-असाइनमेंट चेकबॉक्सच्या अगदी शेजारी `Dashboard → Context & Cache → Compression Combos` वरील "Assign to routing" सूचीमध्ये प्रत्येक रूटिंग कॉम्बोसाठी सेट करता येते. दोन्ही ठिकाणांवरील बदल समान `PUT /api/combos/{id}` एंडपॉइंटद्वारे कायम ठेवले जातात.

### प्रत्येक विनंतीसाठी ओव्हरराइड

एका विनंतीसाठी कॉम्प्रेशन प्लॅन ओव्हरराइड करण्याकरिता `x-omniroute-compression` विनंती हेडर पाठवा. त्याला सर्वोच्च प्राधान्य आहे — तो रूटिंग-कॉम्बो ओव्हरराइड, सक्रिय प्रोफाइल, ऑटो-ट्रिगर आणि पॅनेल Default यांवर मात करतो. अज्ञात मूल्यांकडे दुर्लक्ष केले जाते (विनंती कधीही नाकारली जात नाही) आणि जागतिक मास्टर स्विच तरीही सर्व गोष्टी नियंत्रित करतो: कॉम्प्रेशन जागतिक स्तरावर बंद असताना, हेडर ते सुरू करू शकत नाही. मूल्ये:

| मूल्य         | परिणाम                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------ |
| `off`         | या विनंतीसाठी कॉम्प्रेशन नाही.                                                                   |
| `default`     | पॅनेलमधून मिळालेले Default प्रोफाइल (सक्रिय प्रोफाइलकडे दुर्लक्ष करते). लॉसी इंजिने बंदच राहतात. |
| `safe`        | हेडर वगळण्यासारखेच: केवळ डीडुप आणि व्हाइटस्पेस फोल्डिंग.                                         |
| `allow-lossy` | सारांश, प्रासंगिकता फिल्टर्स आणि शैली पुनर्लेखनांसह या विनंतीचा ऑपरेटर प्लॅन कायम ठेवा.          |
| `engine:<id>` | सक्षम असताना एकच इंजिन, उदा. `engine:rtk`. त्या इंजिनसाठी हा प्रत्येक विनंतीनुसार ऑप्ट-इन आहे.   |
| `<combo>`     | नामांकित कॉम्बो, प्रथम नावानुसार (केस-असंवेदनशील), नंतर आयडीनुसार जुळवला जातो.                   |

`allow-lossy`, `engine:<id>` किंवा नामांकित कॉम्बोशिवाय, लॉसी इंजिने लागू केली जात नाहीत. कॉम्प्रेशन सुरू असताना विनंतीवर तरीही सेशन डीडुप आणि व्हाइटस्पेस फोल्डिंग लागू होते.

लागू केलेला प्लॅन `X-OmniRoute-Compression: <mode>; source=<source>` प्रतिसाद हेडरमध्ये परत दिला जातो, जिथे `<source>` हे `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` किंवा `off` यांपैकी एक असते.

## आभार

Standard मोडचे कॉम्प्रेशन नियम **[JuliusBrussee](https://github.com/JuliusBrussee)** यांच्या **[Caveman](https://github.com/JuliusBrussee/caveman)** (⭐ 51K+) पासून प्रेरित आहेत — हा व्हायरल "अनेक टोकन्स कशाला वापरायचे, जेव्हा काही टोकन्सने काम होते" प्रकल्प आहे. Caveman नुसार `~75%` कमी आउटपुट टोकन्स, बेंचमार्कमध्ये सरासरी `65%` आउटपुट बचत, `22-87%` आउटपुट श्रेणी आणि `~46%` इनपुट-कॉम्प्रेशन टूल मिळते.

RTK मोड **[RTK AI](https://github.com/rtk-ai)** यांच्या **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** पासून प्रेरित आहे — टर्मिनल, बिल्ड, टेस्ट, git आणि टूल-आउटपुट फिल्टरिंगसाठीचा उच्च-कार्यक्षमता कमांड-आउटपुट कॉम्प्रेशन प्रकल्प. RTK नुसार `60-90%` बचत होते, तर त्याच्या README मधील नमुना सत्रात `~80%` बचत दाखवली आहे.

## प्रगत कॉम्प्रेशन प्रणाली

वर वर्णन केलेल्या 7 मोड्सच्या पलीकडे (स्रोत `codex-responses` आणि
`omniglyph` मोड्सही स्वीकारतो, परंतु या मार्गदर्शिकेत त्यांचा समावेश नाही), खालील विभागांमध्ये
त्या मोड्समध्ये किंवा त्यांच्यासोबत कार्य करणारी वैशिष्ट्ये समाविष्ट आहेत: Tool Result Compression आणि Progressive Aging
हे aggressive इंजिनचे टप्पे 1 आणि 2 आहेत (Aggressive मोड आणि स्टॅक्ड पाइपलाइनमधील
`aggressive` टप्पा), Stacked Pipeline म्हणजे Stacked मोड कसा चालतो, Cache-Aware Compression
कॅशिंग प्रोव्हायडर्ससाठी कॉम्प्रेशन सुरू असताना `aggressive` आणि `ultra` यांना `standard` पर्यंत
डाउनग्रेड करते, आणि Caveman Output Mode व Output Styles या ऑप्ट-इन सिस्टम-प्रॉम्प्ट सूचना आहेत,
ज्या डीफॉल्टनुसार बंद असतात आणि विनंती कॉम्प्रेस करण्याऐवजी मॉडेलच्या आउटपुटला आकार देतात.

### कॅश-जागरूक कॉम्प्रेशन

काही प्रोव्हायडर्स (उदा. प्रॉम्प्ट कॅशिंगसह Anthropic) **प्रॉम्प्ट कॅशिंग** समर्थित करतात,
ज्यामुळे खर्च आणि विलंब कमी करण्यासाठी ते प्रॉम्प्टचे काही भाग कॅश करू शकतात. कॅशिंग
सक्षम असताना, aggressive कॉम्प्रेशन प्रत्यक्षात कार्यक्षमता **बिघडवू** शकते,
कारण ते कॅश केलेले टोकन्स बदलते आणि त्यामुळे कॅश अवैध होते.

`cachingAware.ts` मॉड्यूल **कॅशिंग कॉन्टेक्स्ट शोधून** आणि त्यानुसार
**कॉम्प्रेशन धोरण समायोजित करून** ही समस्या सोडवते.

#### हे कसे कार्य करते

1. **कॅशिंग कॉन्टेक्स्ट शोधा** — `cache_control` मार्कर्ससाठी विनंतीचा बॉडी स्कॅन करते
2. **कॅशिंग प्रोव्हायडर्स ओळखा** — लक्ष्य प्रोव्हायडर कॅशिंग समर्थित करतो का ते तपासते
3. **धोरण समायोजित करा** — कॅशिंग प्रोव्हायडर्ससाठी `aggressive`/`ultra` यांना `standard` पर्यंत डाउनग्रेड करते
4. **सिस्टम प्रॉम्प्ट वगळा** — सिस्टम प्रॉम्प्ट्स सामान्यतः कॅश केलेले असतात, त्यामुळे त्यांना कॉम्प्रेस करू नका

धोरण हेल्पर `deterministicOnly` फ्लॅगही परत करतो, परंतु प्लॅन बिल्डर
फक्त धोरण वापरतो — सध्या डाउनस्ट्रीममध्ये हा फ्लॅग कोठेही वाचला जात नाही.

#### कोडचे उदाहरण

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← कॅश मार्कर
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### कधी वापरावे

कॅश-जागरूक कॉम्प्रेशन **नेहमी सुरू असते** — कोणत्याही कॉन्फिगरेशनची गरज नाही. कॉम्प्रेशन
सुरू असताना आणि लक्ष्य प्रोव्हायडर प्रॉम्प्ट कॅशिंग (Anthropic, OpenAI,
इत्यादी) समर्थित करत असेल तेव्हा ते सक्रिय होते; स्पष्ट `cache_control` मार्कर्स आवश्यक नाहीत — केवळ
कॅशिंग प्रोव्हायडरमुळे डाउनग्रेड सुरू होते, आणि केवळ मार्कर्समुळे ते कधीही सुरू होत नाही (मार्कर डिटेक्शन
कॅश टेलिमेट्रीला डेटा पुरवते, धोरण निर्णयाला नाही).

### प्रोग्रेसिव्ह एजिंग

दीर्घ संभाषणांमध्ये अनेक मेसेज टर्न्स जमा होतात, परंतु जुने टर्न्स हळूहळू कमी
संबंधित ठरतात. `progressiveAging.ts` मॉड्यूल **टर्नच्या अंतरानुसार मेसेजेसची तपशीलवारता कमी करते**
(अंतर संभाषणाच्या शेवटापासून मोजले जाते). जारी केलेल्या डीफॉल्ट्ससह
(`verbatim: 2, light: 2, moderate: 3`):

- **शेवटची 2 वळणे (अंतर ≤ 2)**: जशीच्या तशी ठेवली जातात
- **अंतर 3**: Caveman संक्षेपण (अनावश्यक शब्द काढणे)
- **अंतर 4+**: सहाय्यकाचे संदेश सारांशित केले जातात; वापरकर्त्याचे संदेश त्यांच्या पहिल्या
  ओळीपर्यंत कमी केले जातात, कमाल 120 वर्ण; इतर भूमिका बदलल्या जात नाहीत. सिस्टम प्रॉम्प्ट, आधीच-जुने झालेले
  संदेश आणि वापरकर्त्याचा नवीनतम संदेश अंतर काहीही असले तरी नेहमी जसेच्या तसे ठेवले जातात.
  कोणतीही गोष्ट पूर्णपणे वगळली जात नाही आणि पुरवलेल्या डीफॉल्टसह `light`
  बँडपर्यंत पोहोचता येत नाही (`light` हे `verbatim` च्या बरोबरीचे आहे).

#### कोड उदाहरण

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... आणखी 50 वळणे ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // शेवटची 3 वळणे: जशीच्या तशी
  light: 8, // अंतर <= 8: हलके संक्षेपण
  moderate: 20, // अंतर <= 20: caveman संक्षेपण
  fullSummary: 5, // प्रकारासाठी आवश्यक, बँडिंग कोडद्वारे वाचले जात नाही
  // अंतर > 20: सारांशित (सहाय्यक) / पहिली ओळ ठेवली जाते (वापरकर्ता)
});

// saved = वाचवलेल्या टोकनची संख्या
```

#### कधी वापरावे

`aggressive` मोडसाठी प्रोग्रेसिव्ह एजिंग **नेहमी सुरू** असते — ही
`compressAggressive()` ची पायरी 2 आहे. Ultra मोड ते चालवत नाही. हे विशेषतः
पुढील बाबींसाठी प्रभावी आहे:

- दीर्घकाळ चालणारी कोडिंग सत्रे
- अनेक दिवस चालणारी संभाषणे
- अनेक टूल कॉल असलेले एजंटिक कार्यप्रवाह

### Caveman आउटपुट मोड

Caveman आउटपुट मोड **सिस्टम प्रॉम्प्ट सूचना** जोडतो ज्या मॉडेललाच
संक्षिप्त आउटपुट देण्यास सांगतात — `lite` पातळी पूर्ण वाक्ये कायम ठेवून संक्षिप्त उत्तरे देण्यास सांगते, `full`
पातळी "हुशार गुहामानवासारखे संक्षिप्त उत्तर द्या" असे सांगते आणि `ultra` तारसंदेशासारखे आउटपुट देण्यास सांगते;
सूचना केवळ विनंती करू शकतात, त्याची हमी देऊ शकत नाहीत. विनंत्यांना त्या
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) द्वारे मिळतात:
`open-sse/handlers/chatCore.ts` प्रथम बॅकवर्ड-कम्पॅटिबिलिटी शिमद्वारे निवड निश्चित करते
(`open-sse/services/compression/outputStyles/backCompat.ts` मधील
`resolveOutputStyleSelection()`), जे `outputStyles`
रिकामे असताना सक्षम केलेले `cavemanOutputMode`, `cavemanOutputMode.intensity` वरील
`terse-prose` आउटपुट शैलीशी मॅप करते (खालील बॅकवर्ड-कम्पॅटिबिलिटी पहा); रिकामी नसलेली `outputStyles`
निवड जशी आहे तशी वापरली जाते आणि त्यानंतर `cavemanOutputMode.enabled` व `intensity` यांचा
कोणताही परिणाम होत नाही, तर त्याचे `autoClarity` टॉगल अजूनही लागू होते. `outputMode.ts` मध्ये
सूचना मजकूर (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), सामग्री बायपास आणि
इंजेक्शन वापरत असलेला प्लेसमेंट हेल्पर असतात; त्याच्या स्वतःच्या `applyCavemanOutputMode()` इंजेक्टरला कोणताही
प्रॉडक्शन कॉलर नाही.

#### हे कसे कार्य करते

हा मोड इनपुट संक्षिप्त करत नाही. तो सिस्टम प्रॉम्प्टमध्ये एक सूचना ब्लॉक जोडतो
(खालील इंजेक्शन कसे कार्य करते ते पहा) आणि विनंतीसाठी निवडलेला कोणताही इनपुट संक्षेपण मोड
त्यानंतरही, आता तो ब्लॉक असलेल्या बॉडीवर चालतो. प्रत्येक पातळीच्या शेवटी येणाऱ्या सामायिक
मर्यादा कलमापूर्वी, इंग्रजी `full` पातळीवर असे लिहिलेले असते:

> "हुशार गुहामानवासारखे संक्षिप्त उत्तर द्या. उपपदे (a/an/the), अनावश्यक शब्द (just/really/basically/actually/simply), औपचारिक नम्रता आणि संदिग्धता दर्शवणारी भाषा वगळा. वाक्यांश चालतील. छोटे समानार्थी शब्द वापरा (extensive ऐवजी big, implement ऐवजी fix). सर्व तांत्रिक आशय, कोड, त्रुटी, URLs आणि आयडेंटिफायर हुबेहूब ठेवा."

हे विशेषतः पुढील बाबींसाठी चांगले कार्य करते:

- कोड निर्मिती (अधिक संक्षिप्त आउटपुट = कमी टोकन)
- झटपट प्रश्नोत्तरे (विस्तृत स्पष्टीकरणांची गरज नाही)
- बॅच प्रक्रिया (थ्रूपुट कमाल करणे)

#### कधी वापरावे

Caveman आउटपुट मोड **निवडल्यावरच सुरू होतो**. संक्षेपण सुरू असताना (`enabled: true`, Compression Settings पृष्ठावरील
मुख्य टॉगल), तो `cavemanOutputMode.enabled` वापरून सुरू करा; `intensity`
द्वारे `lite`, `full` किंवा `ultra` निवडले जाते:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

संक्षेपण कॉम्बोचे **आउटपुट मोड** टॉगल (`outputMode`, `outputModeIntensity` मधील पातळी)
तो कॉम्बो लागू होणाऱ्या विनंत्यांसाठी हाच स्विच सेट करते आणि
`omniroute_set_compression_engine` MCP टूल त्याच्या बुलियन `outputMode`
आर्ग्युमेंटद्वारे तो लिहिते. रिकामी नसलेल्या `outputStyles` निवडीला या स्विचपेक्षा प्राधान्य असते. डॅशबोर्डमध्ये
**संक्षिप्त गद्य** आउटपुट शैली सक्षम केल्याने हाच ब्लॉक इंजेक्ट केला जातो (खालील आउटपुट
शैली पहा).

### आउटपुट शैली (कॅटलॉग)

वरील Caveman आउटपुट मोड हा **लेगसी एकल-शैली मार्ग** आहे. फेज 4 ने त्याचे सामान्यीकरण
एकत्र वापरता येणाऱ्या आउटपुट शैलींच्या कॅटलॉगमध्ये केले: `open-sse/services/compression/outputStyles/catalog.ts`
मधील `OUTPUT_STYLE_CATALOG`. प्रत्येक शैली ही सिस्टम-प्रॉम्प्ट
सूचना आहे जी मॉडेललाच कमी खर्चिक आउटपुट देण्यास सांगते; शैली एकत्र
सक्षम करता येतात आणि त्या कॅटलॉगच्या क्रमाने इंजेक्ट केल्या जातात.

प्रत्येक शैलीमध्ये तीन तीव्रता स्तर दिलेले आहेत — `lite`, `full`, `ultra` — आणि प्रत्येक स्तराचा
शेवट सामायिक मर्यादा कलमाने (`outputMode.ts` मधील `SHARED_BOUNDARIES`) होतो, जे
कोड ब्लॉक्स, फाइल पथ, कमांड्स, त्रुटी आणि URLs अचूक ठेवते. `terse-prose` आणि
`terse-cjk` स्तरांच्या मजकुरात त्या सूचीमध्ये identifiers देखील जोडले जातात.

`terse-cjk` दोन ठिकाणी `zh` पर्यंत लोकेल-नियंत्रित आहे. Compression Settings पृष्ठावर
त्याची ओळ फक्त dashboard UI ची भाषा चिनी (`zh-CN` किंवा `zh-TW`) असताना दिसते, आणि
`applyOutputStyles()` ती फक्त विनंतीची निश्चित केलेली भाषा (खालील भाषा
निवड पाहा) `zh` असताना अंतर्भूत करते. ओळ लपवल्याने जतन केलेली `terse-cjk` निवड साफ होत नाही:
settings API कोणताही style id स्वीकारते आणि पृष्ठावर इतर शैली जतन केल्यास ती कायम राहते. विनंतीच्या
वेळी, `applyOutputStyles()` मधील भाषा तपासणी हेच एकमेव लोकेल नियंत्रण असते.

#### अंतर्भाव कसा कार्य करतो

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) निवडीचे
catalog विरुद्ध निराकरण करते (अज्ञात ids आणि लोकेलशी न जुळणाऱ्या शैली
वगळल्या जातात, त्या कधीही त्रुटी ठरत नाहीत; कोणत्याही शैलीत निराकरण न होणारी निवड body
न बदलता ठेवते आणि `no_styles` म्हणून वगळली जाते), निवडलेल्या सूचना catalog
क्रमाने जोडते,
मर्यादा कलम **एकदाच** जोडते (तसेच `less-code` किंवा `ponytail` निवडलेले असताना सुरक्षा
कलम, `SAFETY_BOUNDARIES` किंवा त्याचे भाषांतर), आणि ब्लॉकची सुरुवात एका
idempotency marker ने (`[OmniRoute Output Styles]`) करते, त्यामुळे पुन्हा लागू करणे no-op असते. जेव्हा
निश्चित केलेल्या भाषेसाठी (खालील भाषा निवड पाहा) भाषांतर उपलब्ध असते, तेव्हा इंग्रजीऐवजी
स्थानिकीकरण केलेली सूचना अंतर्भूत केली जाते.

रिक्त नसलेला `messages` array असलेल्या body वर, idempotency तपासणी
content bypass पूर्वी चालते: जेव्हा `[OmniRoute Output Styles]` marker आधीच top-level
`system` field मध्ये (string किंवा content-block array) किंवा string
content असलेल्या system message मध्ये असतो, तेव्हा body `already_applied` म्हणून न बदलता ठेवला जातो आणि keyword तपासणी चालत नाही.
अन्यथा content bypass (`open-sse/services/compression/outputMode.ts` मधील
`shouldBypassCavemanOutputMode()`) शेवटच्या तीन
messages चा मजकूर, त्यांची role कोणतीही असो, तपासतो आणि तो मजकूर सुरक्षा, अपरिवर्तनीय-कृती किंवा स्पष्टीकरणाच्या keywords शी जुळल्यास, किंवा
क्रम-संवेदनशील अनुक्रमाशी जुळल्यास संपूर्ण turn साठी शैली वगळतो: `first`, `then`, `after that`, `before`, `rollback` किंवा
`backup` यानंतर 240 characters च्या आत `delete`, `drop`, `migrate`, `deploy` किंवा
`release`. **Auto-Clarity Bypass** toggle
(`cavemanOutputMode.autoClarity`, डीफॉल्टनुसार सुरू) सुरू असताना bypass चालतो; toggle बंद केल्याने
keyword तपासणी वगळली जाते.

bypass ने turn पुढे जाऊ दिल्यावर, `placeSystemInstruction()` (तीच फाइल), जे
कधीही नवीन `messages[0]` तयार करत नाही, त्याला सापडणाऱ्या यापैकी पहिल्या ठिकाणी ब्लॉक ठेवते:

1. string content असलेला सुरुवातीचा system message: ब्लॉक त्याच्या मजकुरानंतर जोडला जातो.
2. top-level `system` field: ब्लॉक string च्या मजकुरानंतर जोडला जातो किंवा
   content-block array मध्ये नवीन text block म्हणून जोडला जातो.
3. string content असलेला त्यानंतरचा पहिला system message: ब्लॉक त्याच्या
   मजकुरानंतर जोडला जातो.
4. वरीलपैकी काहीही नाही: ब्लॉक `messages` च्या शेवटी नवीन system message मध्ये ठेवला जातो.

`messages` array नसलेल्या (किंवा रिकामा array असलेल्या) body वर content bypass चालत नाही आणि
top-level `system` field तपासले जात नाही. ब्लॉक string `instructions` field च्या मजकुरानंतर
जोडला जातो, जोपर्यंत त्या field मध्ये आधीच
`[OmniRoute Output Styles]` marker नसतो; असल्यास body `already_applied` म्हणून
न बदलता ठेवला जातो. body मध्ये string `instructions` field नसताना `input`
(string किंवा array) असल्यास, ब्लॉक `instructions` बनतो आणि त्या field मध्ये असलेले कोणतेही non-string value
बदलतो. string `instructions` field किंवा string अथवा array
`input` यांपैकी काहीही नसलेला body न बदलता ठेवला जातो आणि `no_messages` म्हणून वगळला जातो.

#### सक्षम कसे करावे

डॅशबोर्डमध्ये: **Compression Context → Compression Settings**
(`/dashboard/context/settings`), Output styles विभागात: प्रत्येक शैलीसाठी on/off
टॉगल आणि स्तर निवडक असलेली एक ओळ आहे. कॉम्प्रेशन स्वतः सुरू असताना शैली अंतःक्षेपित केल्या जातात (पृष्ठाचा
मुख्य टॉगल, `enabled`). **Auto-Clarity Bypass** टॉगल **Caveman**
पृष्ठावरील (`/dashboard/context/caveman`) त्याच्या **Output Mode** कार्डमध्ये आहे. प्रोग्रामद्वारे,
कॉम्प्रेशन कॉन्फिग निवड पुढीलप्रमाणे कायम ठेवते:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

बॅकवर्ड कम्पॅटिबिलिटी: `outputStyles` रिकामे असताना, लेगसी `cavemanOutputMode.enabled`
सेटिंग `cavemanOutputMode.intensity` वरील `terse-prose` शी मॅप होते. त्यानंतर ब्लॉकची सुरुवात
`[OmniRoute Output Styles]` मार्करने होते, जिथे लेगसी `applyCavemanOutputMode()`
इंजेक्टर `[OmniRoute Caveman Output Mode]` लिहीत असे. मार्करखालील मजकूर
en, pt-BR, es, de, fr, it, ru, id आणि vi मधील लेगसी अंतःक्षेपाशी जुळतो; ja आणि zh मध्ये सीमांच्या
क्लॉजपूर्वी एक अतिरिक्त स्पेस असते. `terse-prose` चे pt-BR, es, de,
fr, it, ru, zh, ja, id आणि vi मध्ये भाषांतर होते, त्यामुळे ज्याची निर्धारित भाषा `hu` आहे अशा विनंतीला
लेगसी इंजेक्टरने वापरलेल्या हंगेरियन मजकुराऐवजी इंग्रजी मजकूर मिळतो.

आउटपुट-शैलीची भाषा निवड (`outputStyles/apply.ts` मधील
`resolveOutputStyleLanguage()`): `languageConfig.enabled` सुरू असताना, `autoDetect` विनंतीच्या
`messages` अॅरेमधील मजकूर असलेल्या सर्वात अलीकडील वापरकर्ता संदेशाचा नमुना घेतो (स्ट्रिंग सामग्री किंवा
त्याच्या सामग्री भागांमधील `text`) आणि त्यावर Caveman इंजिनचा डिटेक्टर
(`detectCompressionLanguage()`) चालवतो. मजकुरात Han
अक्षरे असून kana नसल्यास डिटेक्टर `zh` परत करतो; अन्यथा `it`, `pt-BR`, `es`, `de`,
`fr`, `ru`, `ja`, `hu` आणि `id` यांपैकी ज्या भाषेसाठी सर्वाधिक संकेत जुळतात ती परत करतो, आणि कोणतेही संकेत न जुळल्यास `en`
परत करतो — वर्गीकरण न करता येणाऱ्या मजकुरासाठी `defaultLanguage` कधीही नाही, तर इंग्रजी वापरले जाते, आणि शैलींसोबत `vi` मजकूर
असला तरी `vi` कधीही शोधला जात नाही. Responses API बॉडी तिचे संवादक्रम
`input` मध्ये ठेवते, ज्याचा नमुना घेतला जात नाही, त्यामुळे तिला `defaultLanguage`, आणि नंतर इंग्रजी मिळते. जेव्हा
`messages` मधील कोणत्याही वापरकर्ता संदेशात मजकूर नसतो, किंवा `autoDetect` बंद असते, तेव्हा `defaultLanguage` लागू होते,
आणि नंतर इंग्रजी. `languageConfig.enabled` बंद असताना भाषा इंग्रजी असते — एखादा
कॉम्प्रेशन कॉम्बो विनंतीला लागू होत नसेल तरच (विनंतीच्या राउटिंग कॉम्बोला नियुक्त केलेला कॉम्बो,
किंवा अंगभूत स्टॅक्ड पाइपलाइनसाठी chatCore ज्यावर फॉलबॅक करतो तो डीफॉल्ट कॉम्प्रेशन कॉम्बो): कॉम्बो लागू केल्याने
त्या विनंतीसाठी `languageConfig.enabled` सुरू होते आणि कॉम्बोच्या भाषा पॅक्समधून
`defaultLanguage` सेट होते (जतन केलेले मूल्य कॉम्बोच्या पॅक्सपैकी एक असल्यास ते, अन्यथा कॉम्बोचा
पहिला पॅक, जो डीफॉल्टनुसार `en` असतो), तर जतन केलेले `autoDetect` (डीफॉल्टनुसार सुरू) तरीही लागू होते.
Caveman इनपुट इंजिन त्याची नियम-पॅक भाषा वेगळ्या प्रकारे निवडते — प्रत्येक मजकूर भागानुसार आणि,
ऑटो-डिटेक्ट बंद असताना, `enabledPacks` द्वारे नियंत्रित.

शैली × भाषा मॅट्रिक्स
`tests/unit/compression/output-styles-i18n-matrix.test.ts` द्वारे निश्चित केला आहे: प्रत्येक कॅटलॉग शैलीसाठी

### टूल परिणाम कॉम्प्रेशन

`open-sse/services/compression/toolResultCompressor.ts` मधील `compressToolResult()`
**5 धोरणांचा** वापर करून टूल-परिणाम मजकूर कॉम्प्रेस करते. ती ही धोरणे याच क्रमाने वापरून पाहते, आणि
ज्या पहिल्या सक्षम धोरणाची तपासणी सामग्रीशी जुळते ते परिणाम ठरवते:

1. **`fileContent`**: 3 किंवा अधिक ओळींचा मजकूर, ज्यामध्ये सुरुवातीचे इंडेंटेशन
   दुर्लक्षित केल्यावर किमान एक ओळ `import `, `export `, `function `, `class `,
   `const `, `let `, `var ` किंवा `return ` (कीवर्ड आणि त्यानंतर एक स्पेस) यांपैकी
   एकाने सुरू होते, किंवा `if`, `for` किंवा `while` यानंतर `(` किंवा ` (` येते,
   त्याच्या पहिल्या 20 आणि शेवटच्या 5 ओळी ठेवतो आणि वगळलेला मधला भाग चिन्हांकित करतो.
2. **`grepSearch`**: `<path>:<digits>:` या स्वरूपाची किमान एक ओळ असलेला मजकूर,
   ज्यामध्ये पहिल्या कोलनपूर्वीच्या मजकुरात कोणतीही व्हाइटस्पेस नसते, फक्त अशाच ओळी
   ठेवतो, कमाल 30, त्यानंतर आणखी जुळण्यांची संख्या आणि जुळलेल्या फाइल्सची यादी देतो;
   इतर प्रत्येक ओळ वगळली जाते. धोरण सक्रिय करण्यासाठी अशी एक ओळ पुरेशी आहे, त्यामुळे
   `12:30:45` सारख्या टाइमस्टॅम्पने सुरू होणारी लॉग ओळही गणली जाते.
3. **`shellOutput`**: ANSI CSI अनुक्रम (`ESC[` आणि त्यानंतर अंक किंवा
   सेमिकोलन व मग एक अक्षर, जसे कलर कोडमध्ये असते) किंवा मजकुरात कुठेही `$` नंतर
   व्हाइटस्पेस असलेले आउटपुट ते अनुक्रम गमावते (इतर एस्केप, जसे `ESC[?25l` किंवा
   OSC विंडो-शीर्षक अनुक्रम, ठेवले जातात) आणि सलग पुनरावृत्त ओळी एकत्र करून त्याच्या
   शेवटच्या 50 ओळी ठेवते. ही तपासणी `json` आणि `errorMessage` यांच्यापूर्वी होत
   असल्यामुळे, असा `$` असलेले JSON किंवा त्रुटी आउटपुट `shellOutput` सुरू असताना
   त्यांच्यापर्यंत कधीही पोहोचत नाही.
4. **`json`**: पर्यायी व्हाइटस्पेसनंतर `{` किंवा `[` ने सुरू होणारा आणि यशस्वीपणे
   पार्स होणारा 2,000 पेक्षा जास्त वर्णांचा JSON पेलोड संक्षिप्त केला जातो: 7 पेक्षा
   जास्त आयटम असलेला अॅरे त्याचे पहिले 5 आणि शेवटचे 2 आयटम व त्यांची एकूण संख्या
   ठेवतो, आणि ऑब्जेक्ट त्याच्या पहिल्या 20 की ठेवतो, ज्यामध्ये प्रत्येक नेस्टेड ऑब्जेक्ट
   किंवा अॅरे मूल्य `{…N keys}` प्लेसहोल्डरने बदलले जाते (अॅरेसाठी N म्हणजे त्याची
   लांबी) आणि पहिल्या 20 नंतर वगळलेल्या की मोजणारा `_remaining_<N>_keys` मार्कर
   असतो. स्केलर मूल्ये पूर्णपणे कॉपी केली जातात, त्यामुळे नेस्टेड मूल्ये नसलेला 20 किंवा
   कमी कींचा ऑब्जेक्ट फक्त पुन्हा इंडेंट केला जातो — मिनिफाय केलेल्या ऑब्जेक्टमध्ये
   वर्ण वाढतात आणि तो अपरिवर्तित राहतो.
5. **`errorMessage`**: कुठेही आणि अक्षरांच्या कोणत्याही केस-मिश्रणात `error:`,
   `error ` (`no error found` प्रमाणे शब्दानंतर स्पेस), `[error]`,
   `exception:`, `exception `, `[exception]` किंवा `traceback` असलेले आउटपुट
   त्याची पहिली ओळ, पुढील 10 ओळी आणि शेवटच्या 3 ओळी ठेवते, आणि त्यांच्या दरम्यानच्या
   ओळींच्या जागी `… [N frames elided] …` मार्कर ठेवते. पहिल्या ओळीनंतर 13 पेक्षा
   जास्त ओळी असतील तेव्हाच मार्कर दिसतो, त्यामुळे 14 किंवा त्यापेक्षा कमी ओळींचे त्रुटी
   आउटपुट लहान केले जात नाही (12 किंवा 13 ओळी असताना शेवटच्या 3 ओळी आधीच ठेवलेल्या
   ओळींची पुनरावृत्ती करतात).

एखादे धोरण जुळल्यानंतर, त्यातून काहीही बचत झाली नसली तरी, नंतरची धोरणे वापरून पाहिली
जात नाहीत. जेव्हा जुळणारे धोरण अंदाजे टोकनची कोणतीही बचत करत नाही (लांबी ÷ 4, वरच्या
पूर्णांकापर्यंत गोल केलेली) — उदाहरणार्थ, 25 किंवा कमी ओळींची कोडसदृश फाइल किंवा
2,000 पेक्षा जास्त वर्णांचा आणि 7 किंवा कमी आयटम असलेला JSON अॅरे — तेव्हा
अॅग्रेसिव्ह इंजिन मूळ टूल परिणाम ठेवते: दोन्ही कॉलर (`compressAggressive()` आणि
`compressAnthropicToolResultBlock()`) `saved` हे 0 किंवा त्यापेक्षा कमी असताना मूळ
परिणाम ठेवतात, तर `compressToolResult()` स्वतः तरीही त्या धोरणाचे आउटपुट परत करते.
टूल-परिणामाची पायरी अंतिम निर्णय नसते: इंजिनचा फॉलबॅक सारांशकर्ता तरीही 8,192
वर्णांपेक्षा मोठा `tool` किंवा `function` संदेश (`maxTokensPerMessage`, 2,048,
गुणिले 4) लहान करू शकतो.

#### कधी वापरावे

टूल परिणाम संक्षेपण ही अॅग्रेसिव्ह इंजिनची पायरी 1 आहे (`compressAggressive()` हे
`open-sse/services/compression/aggressive.ts` मध्ये), त्यामुळे ती Aggressive मोडमध्ये
आणि स्टॅक केलेल्या पाइपलाइनच्या `aggressive` पायरीमध्ये चालते. ती OpenAI-आकाराचे
`tool` आणि `function` संदेश तसेच Anthropic `tool_result` ब्लॉक्समधील मजकूर संक्षिप्त
करते. प्रत्येक धोरणासाठी `aggressive.toolStrategies` अंतर्गत स्वतंत्र स्विच आहे आणि
ते सर्व डीफॉल्टनुसार सुरू असतात. डॅशबोर्डमध्ये, संक्षेपण सुरू असताना आणि डीफॉल्ट मोड
Aggressive असताना हे स्विच Caveman पृष्ठाच्या **Advanced** दृश्यात असतात.

(टूल आउटपुटवर 60-90% बचत), त्यानंतर उर्वरित मजकुरावर Caveman (~46% इनपुट
बचत). एकत्रितपणे, ही **78-95% पात्र श्रेणी** आहे (वरील Upstream Savings Math
पाहा): `1 - (1 - 0.60..0.90) × (1 - 0.46)` ची सरासरी ≈89% आहे.

#### हे कसे कार्य करते

```
इनपुट (1000 टोकन)
  → RTK (कमांड-जाणकार फिल्टर) → 200 टोकन
    → Caveman (अनावश्यक मजकूर काढणे) → 108 टोकन
  → आउटपुट (108 टोकन, ~89% बचत)
```

#### कधी वापरावे

स्टॅक केलेला मोड यासाठी वापरा:

- टूल-केंद्रित कार्यप्रवाह (एजंटिक कोडिंग, संशोधन)
- खर्च-संवेदनशील बॅच प्रक्रिया
- जेव्हा तुम्हाला टोकनची कमाल बचत हवी असेल

स्टॅक केलेल्या पाइपलाइन जागतिक `stackedPipeline` संक्षेपण सेटिंगद्वारे किंवा रूटिंग
कॉम्बोला नियुक्त केलेल्या नामांकित कॉम्प्रेशन कॉम्बोद्वारे कॉन्फिगर केल्या जातात (वरील
Per-Combo Override पाहा) — auto-combo `modePack` द्वारे नाही (ते फील्ड फक्त
auto-combo मॉडेल निवडीचे वजन पुन्हा समायोजित करते आणि `stacked` हे वैध पॅक नाव नाही).

## कॉम्प्रेशन कॉम्बो ओव्हरराइड्स

वेगवेगळ्या वापराच्या परिस्थितींनुसार वर्तन अधिक अचूकपणे समायोजित करण्यासाठी तुम्ही जागतिक कॉम्प्रेशन मोड **प्रत्येक कॉम्बोसाठी** ओव्हरराइड करू शकता:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

हे पुढील गोष्टींसाठी उपयुक्त आहे:

- **कोडिंग कॉम्बो**: दीर्घ सत्रांसाठी `aggressive` मोड वापरा
- **झटपट प्रश्नोत्तर कॉम्बो**: जलद प्रतिसादांसाठी `lite` मोड वापरा
- **अधिक टूल्स वापरणारे कॉम्बो**: कमाल बचतीसाठी `stacked` मोड वापरा
- **प्रॉडक्शन कॉम्बो**: कॅशिंग प्रोव्हायडर्ससाठी ओव्हरराइड बंद ठेवा — नेहमी सक्रिय असलेले कॅश-जागरूक समायोजन `aggressive`/`ultra` ला आपोआप `standard` पर्यंत कमी करते
  (निवडता येण्याजोगा `cache-aware` मोड उपलब्ध नाही)
