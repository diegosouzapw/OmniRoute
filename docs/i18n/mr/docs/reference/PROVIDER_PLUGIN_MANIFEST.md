`open-sse/config/providerPluginManifest.ts` JSON-सुरक्षित provider
plugin contract परिभाषित करते. `open-sse/config/providerPluginManifestRegistry.ts` हा
contract Bifrost, CLIProxyAPI किंवा भविष्यातील Go/Rust router यांसारख्या sidecars साठी
सध्याच्या provider registry शी जोडते. TypeScript registry हा सत्याचा
अधिकृत स्रोत राहतो, परंतु sidecars executor code, OAuth defaults, headers किंवा
process environment state import न करता manifest वापरू शकतात.

हाच manifest स्वतंत्र process मध्ये चालणाऱ्या sidecars साठी HTTP वर
`GET /api/v1/provider-plugin-manifest` येथे उपलब्ध आहे.

OmniRoute त्या URL ची माहिती Bifrost आणि CLIProxyAPI ला
`X-OmniRoute-Provider-Manifest-Url` request header द्वारे देते. sidecar ला स्थानिक request
origin ऐवजी सार्वजनिक किंवा container network URL आवश्यक असल्यास
`OMNIROUTE_PROVIDER_MANIFEST_URL` सेट करा.

## Manifest रीफ्रेश करणे

HTTP endpoint `Cache-Control: public, max-age=60` आणि मजबूत
`ETag` परत करते. sidecar ने शेवटचा सत्यापित manifest जतन करून ठेवावा आणि रीफ्रेश करताना
त्याचा ETag `If-None-Match` मध्ये पाठवावा. `304 Not Modified` response मध्ये body नसते;
sidecar त्याचा cached manifest कायम ठेवतो. कोणताही सत्यापित cached manifest उपलब्ध नसल्यास,
sidecar ने `304` स्वीकारण्याऐवजी unconditional request पाठवली पाहिजे.

## उद्दिष्ट

provider metadata ला plugin contract च्या दिशेने नेणे, जेणेकरून भविष्यात कमी latency असलेला
sidecar सक्रिय request path हाताळू शकेल, तर OmniRoute कडे TypeScript route हा
policy gate आणि fallback म्हणून कायम राहील. manifest हा अतिरिक्त आहे: तो स्वतःहून
request routing बदलत नाही.

## Contract

manifest मध्ये पुढील गोष्टी असतात:

- provider id आणि alias
- upstream format आणि executor name
- auth type, auth header आणि पर्यायी auth prefix
- स्थिर endpoint metadata
- sidecar eligibility आणि provider ने TS वरच का राहावे याची स्पष्ट कारणे
- context length, vision/reasoning flags आणि unsupported params यांसारखे
  JSON-सुरक्षित model metadata
- `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` आणि `usage-supported` यांसह capability tags

manifest मध्ये हेतुपुरस्सर पुढील गोष्टी समाविष्ट केलेल्या नाहीत:

- OAuth client secrets आणि default secret values
- runtime environment resolution
- request headers आणि public credential helpers
- dynamic URL builders
- executor functions
- session pool internals

## Capability Tags

`capabilities` ही registry entry मधून मिळवलेल्या tags ची क्रमवारी लावलेली array आहे. Integrators नी
TypeScript sources पुन्हा वाचण्याऐवजी, "हा provider काय करू शकतो" या प्रश्नाचे
machine-readable उत्तर म्हणून तिचा वापर करावा.

| Tag                  | अर्थ                                                                              |
| -------------------- | --------------------------------------------------------------------------------- |
| `apikey`             | API key स्वीकारतो (`authType` हे `apikey` किंवा `optional` आहे).                  |
| `oauth`              | OAuth किंवा session flow वापरतो.                                                  |
| `responses`          | OpenAI Responses-API base URL उपलब्ध करून देतो.                                   |
| `passthrough-models` | स्थिर catalog ऐवजी थेट upstream मधून models उपलब्ध करून देतो.                     |
| `custom-executor`    | non-default executor चालवतो, त्यामुळे तो TypeScript path वर राहतो.                |
| `sidecar-candidate`  | `sidecar.eligible` प्रतिबिंबित करतो — sidecar import साठी विचार करण्यास सुरक्षित. |
| `usage-fetch`        | वापर किंवा quota fetcher (`getUsageForProvider`) जोडलेला आहे.                     |
| `usage-supported`    | usage API हा provider स्वीकारते (`isSupportedUsageConnection`).                   |

`usage-fetch` हे केवळ discovery साठी आहे. ते सूचित करते की OmniRoute ला त्या
provider चा usage कसा वाचायचा हे माहीत आहे; ते fetching सक्रिय करत नाही, quota semantics
बदलत नाही किंवा त्या provider साठी Dashboard quota widget सक्षम आहे असे सूचित करत नाही —
त्या widget वर स्वतंत्रपणे `USAGE_SUPPORTED_PROVIDERS` द्वारे नियंत्रण ठेवले जाते. सत्याचा
अधिकृत स्रोत `open-sse/services/usage/fetcherProviders.ts` मधील
`USAGE_FETCHER_PROVIDERS` आहे.

ती यादी usage dispatcher स्वीकारत असलेल्या strings नुसार keyed आहे, त्यामुळे ती canonical ids
आणि aliases यांचे मिश्रण करते आणि tagged providers च्या संख्येपेक्षा किंचित मोठी आहे: manifest
registry मध्ये chat providers नसलेल्या entries साठी (उदाहरणार्थ `firecrawl` search provider
आणि `amazon-q` ACP provider) tag करण्यासाठी कोणतीही manifest entry नाही.

`usage-supported` हे सांगते की server आणि Dashboard usage routes त्या provider साठी connection
स्वीकारतात का. ते `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
आणि `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`) प्रतिबिंबित करते;
दोन्हींवर `USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`) द्वारे
नियंत्रण ठेवले जाते. `usage-fetch` च्या विपरीत, ते फक्त provider id वरच emit केले जाते —
runtime guard कोणतेही alias resolution न करता
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` वापरतो, त्यामुळे manifest हाच
नियम कायम ठेवतो. या दोन tags च्या व्याप्ती वेगळ्या आहेत: 3 providers कडे फक्त
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) आहे आणि 1 कडे फक्त
`usage-supported` (`xiaomi-mimo-token-plan`) आहे, त्यामुळे एक tag असणे म्हणजे दुसराही
असेलच असे नाही.

## Sidecar चा वापर

Sidecar ने `sidecar.eligible` ला बिनशर्त राउटिंग निर्णय न मानता, सावधगिरीने निवडलेला संभाव्य उमेदवार दर्शवणारा सिग्नल मानावा. पहिल्या आयात लक्ष्यामध्ये डीफॉल्ट executor वापरणारे API-key, static-endpoint providers असावेत. कस्टम web executors, OAuth/session flows, dynamic URL builders किंवा pool config असलेले providers, sidecar ने समतुल्य वर्तन अंमलात आणेपर्यंत आणि telemetry ने समानता सिद्ध करेपर्यंत TypeScript fallback मार्गावरच राहतील.

सुचवलेले स्थलांतर टप्पे:

1. TS registry मधून provider plugin manifest व्युत्पन्न करा आणि त्याचे प्रमाणीकरण करा.
2. API-key/static providers साठी manifest आयात करण्यास Bifrost किंवा CLIProxyAPI ला सक्षम करा.
3. TS fallback सुरू ठेवून, `OMNIROUTE_RELAY_BACKEND` च्या मागे sidecar द्वारे पात्र providers रूट करा.
4. यशाचा दर, p99 latency, streaming वर्तन आणि unsupported-param हाताळणी TS मार्गाशी जुळते तेव्हाच providers ना पुढच्या स्तरावर न्या.
5. कस्टम executors साठी, एका वेळी एका provider family प्रमाणे sidecar-native plugins जोडा.

## Providers थेट Next मध्ये एम्बेड का करू नयेत

Next frontend कडे provider execution ची जबाबदारी नसावी. त्याने API boundary ला कॉल करावा. त्यानंतर backend हे TypeScript executor, Bifrost, CLIProxyAPI किंवा भविष्यातील native sidecar यांपैकी कशाचा वापर करायचा ते ठरवू शकतो. यामुळे कोणत्याही sidecar handoff पूर्वी request signing, allowlist checks, DB policy आणि fallback वर्तन केंद्रीकृत राहते.
