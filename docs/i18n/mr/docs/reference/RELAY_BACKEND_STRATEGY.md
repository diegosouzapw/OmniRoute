## सारांश

OmniRoute आता `/api/v1/relay/chat/completions` साठी तीन रिले मोडना समर्थन देते:

- `ts`: प्रक्रियेअंतर्गत TypeScript रिले वापरा.
- `bifrost`: Bifrost गेटवे सक्तीने वापरा.
- `auto`: उपलब्ध असताना Bifrost ला प्राधान्य द्या आणि अपयश आल्यास TypeScript वर फॉलबॅक करा.

तुम्ही उच्च विनंती दराने प्रणाली चालवत असताना (दररोज मोठ्या संख्येने टोकन, जवळपास सातत्यपूर्ण थ्रूपुट), फॉलबॅक मार्ग स्पष्ट आणि जलद ठेवणे ही सर्वोत्तम रणनीती आहे, जेणेकरून हॉट पाथ निष्क्रिय झालेल्या साइडकारमुळे कधीही ब्लॉक होणार नाही.

## मोडचे वर्तन

- `ts`
  - सर्वात कमी कार्यान्वयन गुंतागुंत.
  - सर्व रूटिंग आणि प्रमाणीकरण Node मध्ये चालते.
  - उपलब्धतेसाठी साइडकारवर कोणतेही अवलंबित्व नाही.
- `bifrost`
  - सर्व विनंत्या साइडकार गेटवेद्वारे सक्तीने पाठवा.
  - स्वयंचलित फॉलबॅक नाही.
  - साइडकारचे आरोग्य आणि विलंब निश्चित असतील तेव्हाच उपयुक्त.
- `auto`
  - साइडकारपर्यंत पोहोचता येत असेल आणि तो सक्षम असेल, तेव्हा त्याचा वापर केला जातो.
  - अयशस्वी प्रयत्नांमुळे फॉलबॅक हेडर ट्रिगर होतात आणि ट्रॅफिक TS कडे परत पाठवले जाते, ज्यामुळे विनंती यशस्वितेची मर्यादा कायम राहते.
  - कठोरपणे केवळ-साइडकार रूटिंगपेक्षा अपटाइम अधिक महत्त्वाचा असेल, तेव्हा प्रॉडक्शनसाठी हा मोड सर्वात सुरक्षित पर्याय आहे.

## सध्याची 9router विरुद्ध CLIPROXYAPI तुलना

9router आणि CLIPROXYAPI ही दोन्ही इंटिग्रेशन्स आहेत, जी पारंपरिकरीत्या अपस्ट्रीम प्रदात्यांसाठी सुसंगतता मार्ग उपलब्ध करून देत होती.

- 9router हा अपस्ट्रीम ऑर्केस्ट्रेशन आणि सुसंगतता वर्तनासाठी एम्बेड केलेला मार्ग आहे.
- CLIPROXYAPI हा CLI / SDK-शैलीतील ट्रॅफिकसाठी प्रॉक्सी API ब्रिज आहे.
- तुम्हाला समर्पित साइडकारसदृश हॉप आणि कमी-विलंबाचे स्थानिक डिस्पॅच आवश्यक असताना, बाह्यीकृत मार्ग म्हणून Bifrost स्थिर केला जात आहे.

तुम्ही सध्या 9router/CLIPROXYAPI ची तुलना करत असाल:

- हस्तांतरणापूर्वी API रूटमध्ये विनंती स्वाक्षरीकरण, अलाउलिस्ट तपासण्या आणि DB धोरण गेट्स ठेवा.
- वर्कफ्लोसाठी कठोर साइडकार वर्तन आणि प्रत्येक विनंतीतील कमी तफावत आवश्यक असल्यास, `OMNIROUTE_RELAY_BACKEND=bifrost` वापरा.
- घटनेच्या परिस्थितीत सुयोग्य अवनतीसह साइडकारची लवचिकता आवश्यक असल्यास, `OMNIROUTE_RELAY_BACKEND=auto` वापरा.

## बॅकएंड सीमा करार

स्थिर उत्पादन सीमा ही OmniRoute रिले API आहे, डॅशबोर्डची अंमलबजावणी नाही. Next.js डॅशबोर्ड स्थानिक सेवा स्थापित, कॉन्फिगर आणि पर्यवेक्षित करू शकतो; परंतु विनंती रूटिंगने रिले API द्वारे प्रवेश करून त्या सीमेच्या मागे हस्तांतरित केले पाहिजे.

दीर्घकालीन बॅकएंड पर्याय:

- प्रक्रियेअंतर्गत धोरण आणि फॉलबॅक मार्ग म्हणून TypeScript रिले कायम ठेवा. कोणत्याही बॅकएंड हस्तांतरणापूर्वी प्रमाणीकरण, अलाउलिस्ट, विनंती सामान्यीकरण, लेखांकन आणि सुरक्षितता तपासण्या येथेच ठेवा.
- डिप्लॉयमेंटला कमी रूटिंग तफावत, केंद्रीकृत प्रदाता रोटेशन किंवा अनेक OmniRoute प्रतिकृतींमध्ये स्केल-आउट आवश्यक असेल, तेव्हा Bifrost चा प्राधान्यकृत उच्च-थ्रूपुट Tier-1 साइडकार म्हणून वापर करा.
- 9router आणि CLIPROXYAPI यांना एम्बेड केलेल्या सुसंगतता सेवा म्हणून कायम ठेवा. त्या पर्यवेक्षित स्थानिक प्रक्रिया म्हणून चालतात आणि त्यांचे प्रदाता/CLI वर्तन अपेक्षित अडॅप्टर असेल तेव्हा उपयुक्त असतात; परंतु त्या डीफॉल्ट Tier-1 रूटिंग इंजिन बनू नयेत.
- डॅशबोर्डला हॉट पाथमध्ये मनमानी सेवा URL पाठवू देऊ नका. UI द्वारे दिलेल्या URL या कॉन्फिगरेशन इनपुट आहेत; रूटिंग कोडने सर्व्हर-साइड सेटिंग्ज आणि पर्यवेक्षक स्थितीमधून नोंदणीकृत, आरोग्य-तपासणी केलेले बॅकएंड शोधले पाहिजेत.
- आज पर्यवेक्षित सेवांसाठी लूपबॅक HTTP ला प्राधान्य द्या, कारण व्यवस्थापित प्रक्रिया आधीपासून HTTP-सुसंगत API उपलब्ध करून देतात, रूट गार्ड सीमेसाठी ऑडिट करू शकतो आणि अपयश/फॉलबॅक वर्तन विनंती लॉगमध्ये दृश्यमान असते. भविष्यातील SDK किंवा सॉकेट ट्रान्सपोर्टने आयसोलेशन किंवा फॉलबॅकची शब्दार्थरचना कमकुवत न करता p99 रूटिंग विलंब मोजता येण्याजोग्या प्रमाणात कमी केला, तरच तो जोडणे योग्य ठरेल.

म्हणूनच, अतिशय उच्च-थ्रूपुट डिप्लॉयमेंटसाठी Bifrost सक्षम असलेला `auto` हा डीफॉल्ट पर्याय आहे: यशाचा दर टिकवून ठेवण्यासाठी TypeScript फॉलबॅक जतन करताना हॉट पाथवर Go साइडकार वापरा. सुयोग्य अवनतीपेक्षा कठोर केवळ-साइडकार वर्तन अधिक महत्त्वाचे असेल, तेव्हाच `bifrost` वापरा.

## उच्च-थ्रूपुट मार्गदर्शन

सातत्यपूर्ण उच्च RPM/RPS आणि कठोर यशस्वितेच्या SLO साठी:

1. व्यावहारिक कूलडाउन आणि अपयश टेलिमेट्रीसह `auto` वापरा.
2. अपस्ट्रीम प्रमाणीकरण आणि API-की तपासण्या TypeScript रूट सीमेवर ठेवा.
3. स्पष्ट हेडर/काउंटर सक्षम करा, जेणेकरून तुमच्या अलर्टिंगला फॉलबॅकची वारंवारता आणि कारणे दिसतील.
4. कायम प्रतीक्षा करण्याऐवजी जलद अपयशी होण्यासाठी साइडकार टाइमआउट ट्यून करा.
5. सेवा स्वयंचलित-रीस्टार्ट आणि आरोग्य टेलिमेट्री लूप सुस्थितीत ठेवा, जेणेकरून फॉलबॅक खरोखरच अपवादात्मक राहील.

## सुचवलेली आधारभूत संरचना

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- API की, अलाउलिस्ट, सॅनिटायझर आणि दर-मर्यादा तपासण्या रूट हँडलरमध्ये सक्षम ठेवा (डाउनस्ट्रीम फॉरवर्डिंगपूर्वी त्या नेहमी चालतात).
- तुमच्या रिव्हर्स प्रॉक्सी आणि विनंती लॉगमधून फॉलबॅक मेट्रिक्स एक्सपोर्ट करा, जेणेकरून साइडकार आउटेज एका मिनिटाच्या आत दृश्यमान होतील.

## प्रदाता प्लगइन करार

TypeScript एक्झिक्युटरच्या अंतर्गत घटकांवर अवलंबून राहण्याऐवजी साइडकारने JSON-सुरक्षित प्रदाता प्लगइन
मॅनिफेस्टद्वारे प्रदाता मेटाडेटा इम्पोर्ट केला पाहिजे. साइडकारच्या
पात्रता करारासाठी आणि स्थलांतराच्या टप्प्यांसाठी [प्रदाता प्लगइन मॅनिफेस्ट](./PROVIDER_PLUGIN_MANIFEST.md) पहा.
