> **सत्याचा अधिकृत स्रोत:** `src/lib/plugins/` (`marketplace.ts`, `manager.ts`, `manifest.ts`,
> `scanner.ts`, `loader.ts`), `src/app/api/plugins/`, आणि
> `src/app/(dashboard)/dashboard/plugins/`
> **शेवटचे अद्यतन:** 2026-06-28 — v3.8.40

OmniRoute मध्ये WordPress-शैलीची प्लगइन प्रणाली समाविष्ट आहे. प्लगइन म्हणजे स्वतंत्र
डिरेक्टरी असतात — प्रत्येकामध्ये एक `plugin.json` मॅनिफेस्ट आणि एक एंट्री फाइल असते — ज्या
विनंती पाइपलाइनमध्ये (`onRequest` / `onResponse` / `onError`) आणि
जीवनचक्र इव्हेंटमध्ये (`onInstall` / `onActivate` / `onDeactivate` / `onUninstall`)
हुक होतात.

**Plugin Marketplace** हा त्या प्रणालीवरील शोध स्तर आहे. तो इन्स्टॉल करता येणाऱ्या
प्लगइनचा ब्राउझ करण्यायोग्य कॅटलॉग उपलब्ध करतो. डीफॉल्टनुसार कॅटलॉग ही एक
लहान, अंगभूत सीड रजिस्ट्री असते; ऑपरेटर त्यासाठी सानुकूल रिमोट
रजिस्ट्री URL निर्दिष्ट करू शकतो, अशा परिस्थितीत फेच DNS-रिझॉल्व्हिंग SSRF गार्डद्वारे
अधिक सुरक्षित केले जाते ([सुरक्षा](#security) पहा).

प्रत्येक प्लगइन रूट **केवळ लूपबॅकसाठी** (Tier 1 — `LOCAL_ONLY`) उपलब्ध असतो: प्लगइन
चाइल्ड प्रोसेसमध्ये कोड लोड आणि कार्यान्वित करतात, त्यामुळे प्रमाणीकरण असले तरीही
नॉन-लूपबॅक उगमावरून हे रूट उपलब्ध नसतात.
[`docs/security/ROUTE_GUARD_TIERS.md`](../security/ROUTE_GUARD_TIERS.md) पहा.

## हे सर्व एकत्र कसे कार्य करते

```
डॅशबोर्ड (/dashboard/plugins)
  ├─ "इन्स्टॉल केलेले" टॅब → GET /api/plugins            (listPlugins)
  │                          POST /api/plugins/scan      (pluginManager.scan)
  │                          POST /api/plugins/{name}/activate|deactivate
  │                          DELETE /api/plugins/{name}   (अनइन्स्टॉल)
  └─ "मार्केटप्लेस" टॅब    → GET /api/plugins/marketplace
                               → listMarketplacePlugins()
                                 ├─ सानुकूल URL नाही → अंगभूत SEED_REGISTRY
                                 └─ सानुकूल URL → isSafeMarketplaceUrl() SSRF गार्ड
                                               → safeOutboundFetch(guard:"public-only")
```

- **रजिस्ट्री स्तर** — `src/lib/plugins/marketplace.ts`: कॅटलॉगची सूची दाखवतो /
  शोध घेतो आणि कोणतेही अपयश आल्यास सीड रजिस्ट्री वापरतो.
- **जीवनचक्र स्तर** — `src/lib/plugins/manager.ts` (`pluginManager` सिंगलटन):
  इन्स्टॉल, अपग्रेड, सक्रिय करणे, निष्क्रिय करणे, अनइन्स्टॉल, स्कॅन आणि स्टार्टअपवेळी लोड करणे.
- **मॅनिफेस्ट स्तर** — `src/lib/plugins/manifest.ts`: `plugin.json` साठी
  Zod स्कीमा + डीफॉल्ट मूल्ये.
- **स्कॅनर** — `src/lib/plugins/scanner.ts`: प्लगइन डिरेक्टरीखालील
  डिस्कवरील प्लगइन शोधतो.
- **लोडर** — `src/lib/plugins/loader.ts`: प्रत्येक प्लगइन एका विलग
  चाइल्ड प्रोसेसमध्ये सुरू करतो आणि IPC वरून हुक कॉलची मध्यस्थी करतो.

## मार्केटप्लेस कॅटलॉग

`listMarketplacePlugins()` (`src/lib/plugins/marketplace.ts`) हे
`MarketplaceEntry` ऑब्जेक्टची सूची परत करते:

| फील्ड         | प्रकार   | नोंदी                                  |
| ------------- | -------- | -------------------------------------- |
| `name`        | string   | kebab-case प्लगइन नाव                  |
| `version`     | string   | semver                                 |
| `description` | string   | संक्षिप्त सारांश                       |
| `author`      | string   | लेखक / संस्था                          |
| `license`     | string   | SPDX-शैलीचा परवाना आयडी                |
| `downloadUrl` | string   | स्रोत डाउनलोड URL (रिकामा असू शकतो)    |
| `repository`  | string?  | पर्यायी रिपॉझिटरी URL                  |
| `tags`        | string[] | शोध/फिल्टर टॅग                         |
| `downloads`   | number   | डाउनलोड संख्या                         |
| `rating`      | number   | 0–5                                    |
| `verified`    | boolean  | नोंद सत्यापित म्हणून चिन्हांकित आहे का |
| `lastUpdated` | string   | ISO-सदृश दिनांक स्ट्रिंग               |

कोणताही सानुकूल रजिस्ट्री URL कॉन्फिगर केलेला नसल्यास, कॅटलॉग म्हणून अंगभूत
`SEED_REGISTRY` वापरली जाते (सध्या `request-logger`, `rate-limiter`, `cost-tracker`, आणि
`theme-manager`). सीड रजिस्ट्री नेहमी उपलब्ध असते — कॉन्फिगर केलेली रिमोट
रजिस्ट्री उपलब्ध नसल्यास, नॉन-`200` स्थिती परत केल्यास किंवा अपरिचित
बॉडी परत केल्यास, `listMarketplacePlugins()` एक इशारा लॉग करते आणि सीड सूचीचा वापर करते.

> टीप: मार्केटप्लेस **कॅटलॉग** (ब्राउझ/शोध) सुरुवातीपासून शेवटपर्यंत जोडलेला आहे, परंतु
> कॅटलॉगमधून एका क्लिकमध्ये मार्केटप्लेस **इन्स्टॉल** करण्याची सुविधा अद्याप लागू केलेली नाही —
> मार्केटप्लेस नोंदीवरील डॅशबोर्डचे "इन्स्टॉल" बटण सध्या
> "लवकरच उपलब्ध" अशी सूचना दाखवते. सध्या इन्स्टॉलेशन स्थानिक-पाथ इन्स्टॉल
> प्रवाहाद्वारे (`POST /api/plugins`) आणि डिस्कवरील शोधाद्वारे (`POST /api/plugins/scan`) केले जाते.

## REST API

सर्व एंडपॉइंट्ससाठी व्यवस्थापन प्रमाणीकरण (`requireManagementAuth`) आवश्यक आहे **आणि** ते
फक्त लूपबॅकसाठी उपलब्ध आहेत — `/api/plugins` आणि `/api/plugins/` यांची नोंद
`LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`) मध्ये आहे.

| एंडपॉइंट                         | पद्धत  | वर्णन                                                         |
| -------------------------------- | ------ | ------------------------------------------------------------- |
| `/api/plugins`                   | GET    | स्थापित प्लगइन्सची यादी करा (पर्यायी `?status=` फिल्टर)       |
| `/api/plugins`                   | POST   | निरपेक्ष स्थानिक पाथवरून प्लगइन स्थापित करा                   |
| `/api/plugins/scan`              | POST   | प्लगइन डिरेक्टरी स्कॅन करून नवीन प्लगइन्सची नोंदणी करा        |
| `/api/plugins/marketplace`       | GET    | मार्केटप्लेस कॅटलॉग नोंदींची यादी करा                         |
| `/api/plugins/[name]`            | GET    | स्थापित प्लगइनचे तपशील मिळवा                                  |
| `/api/plugins/[name]`            | DELETE | प्लगइन विस्थापित करा                                          |
| `/api/plugins/[name]/activate`   | POST   | सक्रिय करा (लोड करा + हुक्सची नोंदणी करा)                     |
| `/api/plugins/[name]/deactivate` | POST   | निष्क्रिय करा (`onDeactivate` चालवा, हुक्सची नोंदणी रद्द करा) |
| `/api/plugins/[name]/config`     | GET    | प्लगइन कॉन्फिग + कॉन्फिग स्कीमा मिळवा                         |
| `/api/plugins/[name]/config`     | PUT    | प्लगइन कॉन्फिग अद्ययावत करा (स्कीमाच्या आधारे प्रमाणित)       |

`GET /api/plugins` चा `status` फिल्टर
`installed` / `active` / `inactive` / `error` यांपैकी एक मूल्य स्वीकारतो. अवैध मूल्य दिल्यास `400` परत केले जाते.

### स्थापित प्लगइन्सची यादी करा

```bash
curl http://localhost:20128/api/plugins \
  -H "Cookie: auth_token=..."
```

### स्थानिक पाथवरून स्थापित करा

```bash
curl -X POST http://localhost:20128/api/plugins \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{ "path": "/absolute/path/to/my-plugin" }'
```

`path` **निरपेक्ष** असणे आवश्यक आहे आणि त्यामध्ये `..` ट्रॅव्हर्सल विभाग किंवा
नल बाइट्स असू शकत नाहीत (Zod द्वारे अंमलात आणले जाते). स्रोत डिरेक्टरीमध्ये वैध
`plugin.json` असणे आवश्यक आहे (किंवा ती अशा डिरेक्टरीची पालक असावी). यशस्वी झाल्यास प्रतिसादात
स्थापित प्लगइन पंक्तीसह `201` परत केले जाते.

### मार्केटप्लेस ब्राउझ करा

```bash
curl http://localhost:20128/api/plugins/marketplace \
  -H "Cookie: auth_token=..."
```

### प्लगइन कॉन्फिग अद्ययावत करा

```bash
curl -X PUT http://localhost:20128/api/plugins/my-plugin/config \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{ "config": { "level": "debug", "maxItems": 100 } }'
```

`PUT .../config` प्रत्येक दिलेल्या मूल्याचे प्लगइनच्या
`configSchema` च्या आधारे प्रमाणीकरण करते (मॅनिफेस्टमध्ये घोषित केलेले): `number` फील्ड्स `min`/`max` चे पालन करतात,
तर `select` फील्ड्स घोषित केलेल्या `enum` शी जुळणे आवश्यक आहे. स्कीमामध्ये नसलेल्या कीजना
परवानगी दिली जाते.

## कॉन्फिगरेशन

### प्लगइन डिरेक्टरी

प्लगइन्स OmniRoute डेटा डिरेक्टरीखाली असतात:

```
~/.omniroute/plugins/<plugin-name>/
  ├─ plugin.json
  └─ index.js          # (किंवा manifest.main ज्याकडे निर्देश करते ती फाइल)
```

`getDefaultPluginDir()` (`src/lib/plugins/scanner.ts`) ही डिरेक्टरी
तीन टप्प्यांत निर्धारित करते:

1. **`OMNIROUTE_PLUGINS_DIR`**, सेट केलेले असल्यास — `HOME` चे मूल्य काहीही असले तरी जसेच्या तसे वापरले जाते. Docker/K8s साठी
   हे स्पष्ट नियंत्रण आहे, जिथे प्लगइन ट्री अशा पाथवर बाइंड-माउंट केलेला असतो
   ज्याचा सामान्यतः कंटेनरच्या होम डिरेक्टरीशी काहीही संबंध नसतो (#11827).
2. `<home>/.omniroute/plugins`, जिथे `<home>` हे `HOME` / `USERPROFILE`
   पर्यावरण चलांमधून घेतले जाते.
3. `/tmp/.omniroute/plugins`, जेव्हा प्रक्रियेकडून कोणतीही होम डिरेक्टरी एक्सपोर्ट केली जात नाही.

निर्धारित डिरेक्टरी स्टार्टअपवेळी `scanner.dir_resolved` म्हणून एकदा लॉग केली जाते आणि
निवडलेले इनपुट (`OMNIROUTE_PLUGINS_DIR`, `home`, किंवा `no-home-fallback`) नमूद केले जाते — त्यामुळे एखादी इमेज
नकळत तिसऱ्या टप्प्यावर पोहोचल्यास, केवळ रिकामी प्लगइन यादी नोंदवण्याऐवजी तसे स्पष्टपणे सांगितले जाते.
`POST /api/plugins/scan` तेथील वैध `plugin.json` असलेली प्रत्येक सबडिरेक्टरी शोधून
तिची नोंदणी करते; हीच डिरेक्टरी `pluginManager.install()` प्लगइन्स कॉपी करण्यासाठी
रूट म्हणून वापरते, त्यामुळे ओव्हरराइड केल्यास शोध आणि स्थापना दोन्ही एकत्र स्थलांतरित होतात.

> **`OMNIROUTE_PLUGINS_DIR` हे `OMNIROUTE_PLUGIN_PATH` नाही.** नंतरचे मूल्य फक्त
> CLI कमांड-प्लगइन लोडर (`bin/cli/plugins.mjs`) द्वारे `omniroute` उपकमांड्स जोडणारी
> `omniroute-cmd-*` npm पॅकेजेस शोधण्यासाठी वाचले जाते — येथे वर्णन केलेल्या रनटाइम स्कॅनरवर
> त्याचा कोणताही परिणाम होत नाही. त्या भागासाठी [PLUGINS.md](./PLUGINS.md) पहा.

### सानुकूल मार्केटप्लेस रजिस्ट्री URL

मार्केटप्लेस कॅटलॉगचा स्रोत `pluginMarketplaceUrl` सेटिंगमधून वाचला जातो
(`src/lib/plugins/marketplace.ts` हे `settings.pluginMarketplaceUrl` वाचते). ते
`http(s)` URL वर सेट केलेले असल्यास, `listMarketplacePlugins()` त्या URL वरून डेटा आणते आणि
एकतर नोंदींचा शीर्ष-स्तरीय JSON अॅरे किंवा `plugins` अॅरे असलेला ऑब्जेक्ट स्वीकारते;
स्ट्रिंग `name` नसलेल्या नोंदी फिल्टर केल्या जातात. हे सेट केलेले नसल्यास (किंवा फेच
SSRF संरक्षकामुळे अयशस्वी झाल्यास / खराब प्रतिसाद मिळाल्यास), अंगभूत सीड रजिस्ट्री
वापरली जाते.

डॅशबोर्डवरील "Marketplace" टॅब या URL साठी एक फील्ड उपलब्ध करून देतो (जे
`GET /api/settings` मधून पुन्हा वाचले जाते).

> अंमलबजावणीविषयक टीप: डॅशबोर्डवरील "Save" क्रिया
> `pluginMarketplaceUrl` हे `PATCH /api/settings` कडे पाठवते. हे लिहित असताना ही
> की `updateSettingsSchema`
> (`src/shared/validation/settingsSchemas.ts`) मध्ये घोषित केलेली नाही, त्यामुळे तिच्यावर अवलंबून राहण्यापूर्वी
> तुमच्या रिलीजमध्ये ती कायम राहते का ते तपासा — सेटिंग्ज
> स्टोअरमध्ये की उपलब्ध झाल्यानंतर **वाचन** पाथ (`getSettings()` →
> `listMarketplacePlugins()`) तिचे पालन करतो.

## सुरक्षा

### रूट स्तर — केवळ लूपबॅक

प्लगइन स्पॉन केलेल्या चाइल्ड प्रोसेसमध्ये कोड कार्यान्वित करतात, त्यामुळे संपूर्ण `/api/plugins`
पृष्ठभाग `LOCAL_ONLY` (स्तर 1) म्हणून वर्गीकृत केला आहे. लूपबॅक अंमलबजावणी कोणत्याही प्रमाणीकरण तपासणीच्या
**आधी** बिनशर्त चालते, त्यामुळे टनेलमार्फत मशीनपर्यंत पोहोचलेले लीक झालेले व्यवस्थापन टोकनसुद्धा
प्लगइन इन्स्टॉल, सक्रिय किंवा अनइन्स्टॉल करू शकत नाही.
[`docs/security/ROUTE_GUARD_TIERS.md`](../security/ROUTE_GUARD_TIERS.md) आणि
कडक नियम #15 / #17 पहा.

### मार्केटप्लेस रजिस्ट्री SSRF संरक्षक

सानुकूल रजिस्ट्री URL हे हल्लेखोराच्या प्रभावाखाली येऊ शकणारे कॉन्फिगरेशन आहे, त्यामुळे
ते फेच करण्यापूर्वी `listMarketplacePlugins()` त्याची दोन स्तरांमधून तपासणी करते:

1. **`isSafeMarketplaceUrl(url)`** (`src/lib/plugins/marketplace.ts`):
   - `http:` / `https:` नसलेली कोणतीही गोष्ट नाकारते.
   - प्रमाणित `isPrivateHost`
     (`src/shared/network/outboundUrlGuard.ts`) वापरून प्रत्यक्ष खाजगी/लूपबॅक/लिंक-लोकल/ULA होस्ट (IPv4 **आणि** IPv6,
     तसेच IPv4-मॅप केलेले पत्ते) नाकारते.
   - **दोन्ही** `A` आणि `AAAA` रेकॉर्डचे रिझोल्यूशन करते आणि रिझोल्व्ह झालेला **कोणताही**
     पत्ता खाजगी असल्यास नाकारते — यामुळे सार्वजनिक-होस्टनेम → खाजगी-IP बायपास बंद होतो.
   - **सुरक्षिततेसाठी बंद राहते**: DNS रिझोल्यूशन अयशस्वी झाल्यास URL नाकारली जाते.
2. **`safeOutboundFetch(url, { guard: "public-only", timeoutMs: 5000 })`**
   (`src/shared/network/safeOutboundFetch.ts`): फेचच्या वेळी केवळ-सार्वजनिक URL
   संरक्षक पुन्हा लागू करते आणि **रीडायरेक्ट अवरोधित करते** (सार्वजनिक → खाजगी `30x`
   पिव्होट होऊ देत नाही).

यापैकी कोणत्याही स्तरावर अयशस्वी होणारी URL विनंती रद्द करत नाही — मार्केटप्लेस
मूकपणे अंगभूत सीड रजिस्ट्रीवर परत जाते आणि चेतावणी लॉग करते.

> हा संरक्षक PR #3774 मध्ये विशेषतः A + AAAA रिझोल्व्ह करण्यासाठी आणि
> केवळ-IPv4 तपासणीऐवजी प्रमाणित `isPrivateHost` वापरण्यासाठी अधिक मजबूत करण्यात आला.

### प्लगइन कार्यान्वयन विलगीकरण

- **प्रोसेस विलगीकरण** — `loadPlugin()` (`src/lib/plugins/loader.ts`) प्रत्येक
  प्लगइन स्वतंत्र Node.js चाइल्ड प्रोसेसमध्ये स्पॉन करते आणि IPC द्वारे संवाद साधते.
  हुक कॉलना `SIGTERM` → `SIGKILL` एस्कलेशनसह कालमर्यादा असते.
- **Env अनुमतीसूची** — चाइल्डला केवळ अनुमतीसूचीतील पर्यावरण
  चलांचा संच मिळतो; मॅनिफेस्टने `env` परवानगी मागितली असेल, तरच अधिक व्यापक संच दिला जातो.
- **पथ परिरोधन** — इन्स्टॉल/अपग्रेड/अनइन्स्टॉल करताना कोणत्याही कॉपी किंवा पुनरावर्ती हटवण्यापूर्वी प्लगइन
  डिरेक्टरी आणि `manifest.main` हे व्यवस्थापित प्लगइन रूटच्या **आतच** रिझोल्व्ह होत असल्याची खात्री केली जाते
  (छेडछाड केलेल्या DB पथांपासून आणि `manifest.main` मधील
  `../` ट्रॅव्हर्सलपासून संरक्षण करते). सक्रियकरण `realpath` द्वारे सिमलिंक रिझोल्व्ह करते
  आणि प्लगइन डिरेक्टरीबाहेर जाणारा एंट्री पॉइंट लोड करण्यास नकार देते.
- **पर्यायी अखंडता पिन** — मॅनिफेस्टमध्ये `integrity`
  (`sha256-<base64>`, SRI स्वरूप) फील्ड घोषित केले जाऊ शकते. ते उपस्थित असल्यास, लोडर
  लोडच्या वेळी एंट्री फाइलची हॅश पडताळतो आणि ती जुळत नसल्यास सक्रिय करण्यास नकार देतो. ही
  निवडीवर आधारित छेडछाड-शोध सुविधा आहे, सुरक्षा सीमा **नाही** — केवळ-लूपबॅक रूटिंग
  आणि परवानगी मॉडेल याच वास्तविक सीमा आहेत.

परवानग्या
`network` / `file-read` / `file-write` / `env` / `exec`
या enum मधून घेतल्या जातात.

## जीवनचक्र प्रवाह

```
install (POST /api/plugins, path)
  → मॅनिफेस्ट स्कॅन/प्रमाणित करा → स्टेजिंगमध्ये कॉपी करा → main निर्देशिकेच्या आत असल्याची खात्री करा
  → ~/.omniroute/plugins/<name> मध्ये अणुस्तरीय rename करा → DB पंक्ती समाविष्ट करा
  → onInstall ट्रिगर करा → enabledByDefault असल्यास: activate

activate (POST /api/plugins/{name}/activate)
  → realpath अंतर्भाव तपासणी → loadPlugin() (चाइल्ड प्रोसेस सुरू करा)
  → घोषित hooks नोंदणीकृत करा → status = "active" → onActivate ट्रिगर करा

deactivate (POST /api/plugins/{name}/deactivate)
  → onDeactivate ट्रिगर करा (नोंदणी रद्द करण्यापूर्वी) → hooks ची नोंदणी रद्द करा
  → चाइल्ड प्रोसेस समाप्त करा → status = "inactive"

uninstall (DELETE /api/plugins/{name})
  → सक्रिय असल्यास deactivate करा → onUninstall ट्रिगर करा
  → अंतर्भाव-तपासणीसह प्लगइन निर्देशिका पुनरावर्तीपणे हटवा → DB पंक्ती हटवा
```

ज्या निर्देशिकेतील मॅनिफेस्ट आवृत्ती स्थापित आवृत्तीपेक्षा **निश्चितपणे
नवीन** आहे, तिच्यावर `install` पुन्हा चालवल्यास स्वयंचलित अपग्रेड होते (स्वच्छ पुनर्स्थापना; कॉन्फिगरेशन
डीफॉल्ट मूल्यांवर रीसेट होते). समान किंवा जुनी आवृत्ती नाकारली जाते.

## डॅशबोर्ड

`/dashboard/plugins` येथील डॅशबोर्ड पृष्ठ
(`src/app/(dashboard)/dashboard/plugins/page.tsx`) दोन टॅब प्रदान करते:

- **स्थापित** — स्थापित प्लगइन त्यांच्या घोषित hooks सह सूचीबद्ध करते, तसेच
  activate/deactivate टॉगल, uninstall बटण आणि "प्लगइनसाठी स्कॅन करा"
  क्रिया (`POST /api/plugins/scan`) प्रदान करते.
- **मार्केटप्लेस** — `GET /api/plugins/marketplace` मधील कॅटलॉग आणि
  सानुकूल रजिस्ट्री URL सेट करण्यासाठी फील्ड दर्शवते.

प्रत्येक प्लगइनसाठी कॉन्फिगरेशन पृष्ठ `/dashboard/plugins/[name]/config`
(`src/app/(dashboard)/dashboard/plugins/[name]/config/page.tsx`) येथे आहे.
