> **थोडक्यात**: `open-sse/` हे OmniRoute मधील प्रत्येक LLM विनंतीला समर्थित करणारे मुख्य स्ट्रीमिंग इंजिन आहे. यामध्ये विनंती पाइपलाइन, एक्झिक्युटर्स, सेवा, MCP सर्व्हर आणि भाषांतर स्तर लागू करणाऱ्या ~1,400 फाइल्स आहेत. हे घटक एकमेकांशी कसे जोडलेले आहेत हे या मार्गदर्शकामध्ये स्पष्ट केले आहे.

**स्रोत:** `open-sse/` (वर्कस्पेस पॅकेज, ~1,440 चाचणी नसलेल्या `.ts` फाइल्स)

## स्वतंत्र वर्कस्पेस पॅकेज का?

`open-sse/` हे OmniRoute मोनोरेपोमधील एक **स्वतंत्र वर्कस्पेस** आहे, त्यामागे अनेक कारणे आहेत:

1. **पुनर्वापरक्षमता** — `open-sse` हे npm वर `@omniroute/open-sse` म्हणून प्रकाशित केले जाते, त्यामुळे इतर प्रकल्प ते स्वतंत्रपणे वापरू शकतात
2. **स्पष्ट सीमा** — स्ट्रीमिंग इंजिन OmniRoute-विशिष्ट UI/DB स्तरापासून विभक्त आहे
3. **कार्यक्षमता** — इंजिनमध्ये Next.js अवलंबित्वे नाहीत, ज्यामुळे CLI/सर्व्हरलेस संदर्भांमध्ये अधिक जलद कोल्ड स्टार्ट शक्य होतात
4. **आवृत्ती व्यवस्थापन** — `open-sse` स्वतःच्या वेळापत्रकानुसार रिलीज केले जाऊ शकते

```json
// package.json
"workspaces": ["open-sse"]
```

## विनंती पाइपलाइन

प्रत्येक LLM विनंती **5-टप्प्यांच्या पाइपलाइनमधून** जाते:

```
                              ┌──────────────┐
   HTTP विनंती                 │  1. राउट     │   कॉम्बो निराकरण, मॉडेल निवड
   (Next.js रूट)               └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. भाषांतर  │   स्वरूप रूपांतरण (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. अंमलबजावणी│   प्रदाता एक्झिक्युटर, HTTP, पुनर्प्रयत्न, ब्रेकर
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. स्ट्रीम   │   SSE रूपांतरण, बॅकप्रेशर
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. नोंद      │   वापराचा मागोवा, कॉल लॉग, त्रुटी वर्गीकरण
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP प्रतिसाद (SSE किंवा JSON)
```

### टप्पा 1: राउट (`services/combo.ts`)

**प्रवेशबिंदू**: `services/combo.ts` मधील `handleComboChat()`

विनंतीचे ठोस `(provider, model, account, credentials)` ट्युपलमध्ये निराकरण करते:

- ID नुसार कॉम्बो शोधणे (किंवा `auto/*` मॉडेल्ससाठी आभासी कॉम्बो तयार करणे)
- राउटिंग धोरण लागू करणे (प्राधान्य, भारित, राउंड-रॉबिन इत्यादी)
- अस्वस्थ प्रदाते वगळणे (सर्किट ब्रेकर)
- पुढील व्यवहार्य लक्ष्य निवडणे

`auto/*` मॉडेल्ससाठी हा टप्पा पुढील गोष्टीही करतो:

- **16-घटक स्कोअरिंग** अल्गोरिदम चालवतो (`services/autoCombo/`)
- आरोग्य, किंमत, विलंब इत्यादींच्या आधारे `provider+model` जोडी निवडतो

### टप्पा 2: भाषांतर (`translator/`)

स्रोत स्वरूप (उदा., OpenAI) लक्ष्य स्वरूपापेक्षा (उदा., Claude) वेगळे असल्यास, विनंतीचे **भाषांतर** केले जाते:

- सिस्टम प्रॉम्प्ट → सिस्टम संदेश
- साधन व्याख्या → प्रदाता-विशिष्ट साधन स्वरूप
- रिझनिंग/थिंकिंग पॅरामीटर्स → प्रदाता-विशिष्ट समतुल्य पॅरामीटर्स
- संदेश भूमिकांचे सामान्यीकरण (OpenAI व्यतिरिक्त इतरांसाठी `developer` → `system`)

`translator/index.ts` पुढील गोष्टी उपलब्ध करून देते:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### टप्पा 3: अंमलबजावणी (`executors/`)

**प्रवेशबिंदू**: `getExecutor(providerId).execute(request, options)`

सर्व प्रदाते `getExecutor()` फॅक्टरी फॉलबॅकद्वारे `DefaultExecutor` (`executors/default.ts`) वापरतात. एक्झिक्युटर:

- अपस्ट्रीम URL तयार करतो (`buildUrl()`)
- प्रदाता-विशिष्ट हेडर्स जोडतो (`buildHeaders()`)
- विनंती बॉडीचे रूपांतरण करतो (`transformRequest()`)
- पुनर्प्रयत्न आणि एक्स्पोनेन्शियल बॅकऑफसह HTTP विनंती पाठवतो
- आवश्यकता असल्यास प्रमाणीकरण रिफ्रेश हाताळतो (OAuth प्रदाते)

सर्व एक्झिक्युटर्स `BaseExecutor` (`executors/base.ts`, 1170 LOC) विस्तारित करतात, जो पुढील सुविधा पुरवतो:

- सामान्य पुनर्प्रयत्न तर्कशास्त्र
- प्रॉक्सी एकत्रीकरण
- सर्किट ब्रेकर एकत्रीकरण
- वापर नोंदवण्याचे हुक्स

### टप्पा 4: स्ट्रीम (`utils/stream.ts`)

स्ट्रीमिंग प्रतिसादांसाठी, एक्झिक्युटर एक **ReadableStream** परत करतो. हँडलर:

- SSE ट्रान्सफॉर्ममधून पाइप करतो (`createSSETransformStreamWithLogger`)
- निष्क्रिय कनेक्शन्स शोधण्यासाठी हार्टबीट पिंग्ज लागू करतो
- क्लायंट डिस्कनेक्ट सुरळीतपणे हाताळतो (`pipeWithDisconnect`)
- नॉन-स्ट्रीमिंग क्लायंट्ससाठी SSE → JSON रूपांतरण करतो

नॉन-स्ट्रीमिंग प्रतिसादांसाठी, एक्झिक्युटर पार्स केलेला JSON ऑब्जेक्ट परत करतो, जो कोणताही बदल न करता पुढे पाठवला जातो.

### टप्पा 5: नोंद (`services/usage.ts`)

प्रतिसादानंतर (यशस्वी किंवा अयशस्वी), वापराची नोंद केली जाते:

- प्रतिसादातील `prompt_tokens`, `completion_tokens`, `cached_tokens`
- किंमत डेटावरून गणना केलेले `cost_usd`
- अयशस्वी झाल्यास `latency_ms`, `status`, `error_class`
- `usage_history` तक्त्यात कायमस्वरूपी जतन केले जाते

कॉल लॉग आर्टिफॅक्ट्स (सक्षम असल्यास) `${DATA_DIR}/call_logs/` मध्ये लिहिले जातात.

## प्रमुख फाइल्सचा सखोल आढावा

### chatCore.ts (5977 ओळी)

**मुख्य विनंती हँडलर**. त्याचा आकार मोठा असूनही, त्याची रचना स्पष्ट आहे:

```ts
// chatCore.ts ची छद्म-रचना
export async function handleChat(request: NextRequest) {
  // 1. प्रमाणीकरण + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. विनंतीच्या मुख्य भागाचे प्रमाणीकरण
  const body = await parseRequestBody(request);

  // 3. स्वरूप शोधणे + रूपांतरण
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. कॉम्बो राउटिंग
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // पुढील लक्ष्याकडे सुरू ठेवा
    }
  }

  // 5. आपत्कालीन फॉलबॅक
  return await emergencyFallback(body);
}
```

एकच प्रचंड फंक्शन असूनही, ते 5-टप्प्यांच्या पाइपलाइनशी जुळणाऱ्या **टिप्पण्यांसह विभागांमध्ये** व्यवस्थित मांडलेले आहे.

### combo.ts (4456 LOC)

कॉम्बोचे क्रमबद्ध लक्ष्यांमध्ये निराकरण करणारे **राउटिंग इंजिन**.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("लक्ष्य अयशस्वी झाले, पुढील लक्ष्याचा प्रयत्न करत आहे", {
        target,
        err,
      });
    }
  }
  throw new ComboExhaustedError("सर्व लक्ष्ये अयशस्वी झाली");
}
```

**19 राउटिंग धोरणांना** समर्थन देते (`src/shared/constants/routingStrategies.ts` पाहा):

| धोरण                | वर्तन                                                                               |
| ------------------- | ----------------------------------------------------------------------------------- |
| `priority`          | पहिले लक्ष्य प्राधान्य असलेली क्रमबद्ध सूची                                         |
| `weighted`          | प्रत्येक लक्ष्याच्या वजनानुसार संभाव्यताधारित निवड                                  |
| `round-robin`       | लक्ष्यांमधून क्रमाने चक्राकार निवड                                                  |

- `buildUrl()` — डीफॉल्ट URL रचना (सानुकूल वर्तनासाठी उपवर्ग ओव्हरराइड करतात)

- `execute()` — पुनर्प्रयत्न/बॅकऑफ/ब्रेकर असलेले मुख्य HTTP लूप

// open-sse/executors/default.ts

## एक्झिक्युटर्स (75+ फाइल्स)

प्रत्येक provider साठी एक फाइल. हे सर्व `BaseExecutor` चा विस्तार करतात आणि जे वेगळे आहे ते ओव्हरराइड करतात.

### सामान्य पॅटर्न्स

Providers चे निराकरण `getExecutor(providerId)` द्वारे केले जाते, जे कॉन्फिगर केलेला executor परत करते. OpenAI/Anthropic-सुसंगत providers `DefaultExecutor` (`executors/default.ts`) वापरतात. Provider-विशिष्ट वर्तन (बेस URL, प्रमाणीकरण हेडर्स, API आवृत्ती) `open-sse/config/providers/` मध्ये कॉन्फिगर केले जाते, तर विनंती बॉडीची रूपांतरणे `open-sse/translator/` मध्ये हाताळली जातात.

**कस्टम URL** हे provider कॉन्फिगरेशनद्वारे सेट केले जाते:

```ts
// open-sse/config/providers/ मधील Provider कॉन्फिगरेशन
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**कस्टम प्रमाणीकरण** हे provider registry च्या प्रमाणीकरण कॉन्फिगरेशनद्वारे (API की, OAuth, हेडर प्रोफाइल्स) हाताळले जाते.

**कस्टम विनंती बॉडी** रूपांतरणे (उदा., Anthropic द्वारे `system` ला `messages` पासून वेगळे करणे) प्रत्येक provider साठी `open-sse/translator/` मध्ये नोंदवली जातात.

````

### Executor फॅक्टरी

`executors/index.ts`, `getExecutor(providerId)` एक्सपोर्ट करते:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

निराकरण `ExecutorRegistry` (`executors/registry.ts`) मार्फत होते: प्रत्येक विशेषीकृत executor ची घोषणा `executors/index.ts` च्या अंगभूत तक्त्यामध्ये केली जाते आणि मॉड्यूल लोड होताना `registerExecutor(alias, instance)` द्वारे नोंदणी केली जाते; `getExecutor()` registry तपासते आणि विशेषीकृत नोंद नसलेल्या कोणत्याही provider साठी मेमोइझ केलेला `DefaultExecutor` फॉलबॅक म्हणून वापरते. संपूर्ण alias → executor मॅपिंगची वैशिष्ट्ये गोल्डन टेस्ट `tests/unit/executor-map-golden.test.ts` द्वारे निश्चित केली जातात.

## भाषांतरकार

**3 स्वरूपांमध्ये** भाषांतर करा: OpenAI, Anthropic, Gemini, तसेच नवीन Responses API.

### भाषांतर कधी होते

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

सामान्य भाषांतरे:

- `OpenAI → Anthropic`: स्वतंत्र `system` फील्ड, `x-api-key` हेडर

- `OpenAI → Responses API`: `input` अॅरे, `previous_response_id` स्थिती

### हाताळलेली विशेष प्रकरणे

- `developer` भूमिका → OpenAI व्यतिरिक्त इतरांसाठी `system`

- विचारप्रक्रियेचे पॅरामीटर्स (o1, Claude) → प्रदाताविशिष्ट समतुल्य पर्याय

## ट्रान्सफॉर्मर्स

`open-sse/transformer/` **Chat Completions** आणि **Responses API** स्वरूपांदरम्यान रूपांतरण करते.

### स्वतंत्र ट्रान्सफॉर्मर का?

Responses API हे **स्थितीय संभाषणांसह** (`previous_response_id`) OpenAI चे नवीन स्वरूप आहे. क्लायंटने Responses विनंती पाठवल्यावर, OmniRoute:

1. अंतर्गतरीत्या Responses → Chat Completions मध्ये रूपांतरित करते
2. प्रदात्याकडे पाठवते (Chat Completions समर्थित करणारा कोणताही प्रदाता)
3. प्रतिसाद परत Responses स्वरूपात रूपांतरित करते
4. रूपांतरित प्रतिसाद क्लायंटकडे स्ट्रीम करते

ट्रान्सफॉर्मर (`transformer/responsesTransformer.ts`) पुढील गोष्ट प्रदान करतो:

```ts
createResponsesApiTransformStream(): TransformStream
```

हे पुढील बाबी हाताळते:

- `response.output_item.added` इव्हेंट्स
- `response.output_text.delta` इव्हेंट्स
- `response.completed` इव्हेंट
- टूल कॉल मॅपिंग (`function_call` ↔ `tool_calls`)

2. मुख्य हँडलर फंक्शन आणि आवश्यक कॉन्स्टंट्स एक्सपोर्ट करा
3. `tests/unit/services/[serviceName].test.mjs` मध्ये युनिट चाचण्या जोडा
4. राउटिंगशी संबंधित असल्यास, `handlers/chatCore.ts` मधील विनंती पाइपलाइनमध्ये एकत्रित करा

6. या फाइलमध्ये दस्तऐवजीकरण करा

2. `config/providerRegistry.ts` मध्ये नोंदणी करा
3. `executors/index.ts` फॅक्टरीमध्ये जोडा
4. एक्झिक्युटरसाठी युनिट चाचण्या जोडा
5. `docs/architecture/ARCHITECTURE.md` मध्ये दस्तऐवजीकरण करा
