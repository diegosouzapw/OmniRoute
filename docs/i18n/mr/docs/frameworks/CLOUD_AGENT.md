OmniRoute तृतीय-पक्षाच्या क्लाउड-होस्टेड कोडिंग एजंटना (Codex Cloud, Cursor,
Devin, Jules) दीर्घकाळ चालणाऱ्या कार्यांच्या स्वरूपात समन्वयित करते. प्रत्येक एजंटला एका समान इंटरफेसमागे समाविष्ट केले जाते, ज्यामुळे
क्लायंट प्रॉम्प्ट + रेपो URL सबमिट करू शकतात आणि
प्रदात्याच्या विशिष्ट API हाताळण्याची आवश्यकता नसताना परिणाम प्राप्त करू शकतात.

Cloud Agent कार्य हे नियमित चॅट पूर्णीकरण **नाही**. हे एक टिकाऊ, बहु-चरणीय
कार्य-एकक आहे, ज्याला काही मिनिटांपासून काही तासांपर्यंत वेळ लागू शकतो, जे त्याची
कलाकृती म्हणून Pull Request तयार करू शकते आणि फॉलो-अप संदेशांना व (काही प्रदात्यांमध्ये) योजना-मंजुरी गेट्सना समर्थन देते.

## आर्किटेक्चर

```
क्लायंट (Dashboard / CLI / API)
  → POST /api/v1/agents/tasks (व्यवस्थापन प्रमाणीकरण आवश्यक)
    → CreateCloudAgentTaskSchema प्रमाणीकरण (Zod)
    → registry.getAgent(providerId)
    → getCloudAgentCredentials(providerId)
      └─ getProviderConnections({ provider, isActive: true }) मधून आणते
         (प्रथम apiKey, अन्यथा accessToken)
    → agent.createTask({ prompt, source, options }, credentials)
      └─ अपस्ट्रीम प्रदाता API कडे HTTP POST
      └─ अंतर्गत id + externalId सह CloudAgentTask परत करते
    → cloud_agent_tasks (SQLite) मध्ये insertCloudAgentTask(...)

पोलिंग (वाचनावेळी लेझी सिंक):
  GET /api/v1/agents/tasks/[id]
    → getCloudAgentTaskById(id)
    → agent.getStatus(externalId, credentials)  // स्थिती + क्रियाकलाप रीफ्रेश करते
    → नवीन स्थिती, परिणाम, completed_at सह updateCloudAgentTask(...)
    → क्रमबद्ध केलेले कार्य परत करते

परस्परसंवाद:
  POST /api/v1/agents/tasks/[id]  body: { action: "approve" | "message" | "cancel" }
    → "approve" साठी agent.approvePlan(externalId, credentials)
    → "message" साठी agent.sendMessage(externalId, message, credentials)
    → "cancel" साठी स्थिती "cancelled" वर बदलते (केवळ स्थानिक)
```

सिंक **लेझी** आहे: प्रत्येक `GET /tasks/[id]` वर स्थिती अपस्ट्रीममधून रीफ्रेश केली जाते.
कोणताही बॅकग्राउंड पोलर नाही. अद्ययावत स्थिती आवश्यक असलेल्या डॅशबोर्डनी योग्य अंतराने GET
एंडपॉइंट पोल करावा.

## `CloudAgentBase` इंटरफेस

स्रोत: `src/lib/cloudAgent/baseAgent.ts`

```typescript
export interface AgentCredentials {
  apiKey: string;
  baseUrl?: string;
}

export interface CreateTaskParams {
  prompt: string;
  source: CloudAgentSource;
  options: {
    autoCreatePr?: boolean;
    planApprovalRequired?: boolean;
    environment?: Record<string, string>;
  };
}

export interface GetStatusResult {
  status: CloudAgentStatus;
  externalId?: string;
  result?: CloudAgentResult;
  activities: CloudAgentActivity[];
  error?: string;
}

export abstract class CloudAgentBase {
  abstract readonly providerId: string;
  abstract readonly baseUrl: string;

  abstract createTask(p: CreateTaskParams, c: AgentCredentials): Promise<CloudAgentTask>;
  abstract getStatus(externalId: string, c: AgentCredentials): Promise<GetStatusResult>;
  abstract approvePlan(externalId: string, c: AgentCredentials): Promise<void>;
  abstract sendMessage(
    externalId: string,
    message: string,
    c: AgentCredentials
  ): Promise<CloudAgentActivity>;
  abstract listSources(
    c: AgentCredentials
  ): Promise<{ name: string; url: string; branch?: string }[]>;

  protected mapStatus(raw: string): CloudAgentStatus; // ह्युरिस्टिक अपस्ट्रीम-स्ट्रिंग → enum
  protected generateTaskId(): string; // `task_<ts>_<rand>`
  protected generateActivityId(): string; // `act_<ts>_<rand>`
}
```

`CodexCloudAgent.approvePlan` हेतुपुरस्सर त्रुटी फेकते — Codex Cloud स्वयंचलितपणे योजना बनवते आणि त्यात
मंजुरीचा टप्पा नाही. `CodexCloudAgent.listSources` हे `[]` परत करते.

`CursorCloudAgent`, Cursor च्या अधिकृत REST API (`api.cursor.com/v0`) द्वारे त्याचे Background / Cloud Agents
**वापरकर्ता किंवा सेवा-खाते API key** वापरून चालवते — Cursor IDE चे OAuth सत्र पुन्हा वापरण्याच्या तुलनेत
हा अधिक सुरक्षित, प्रथम-पक्षीय पर्याय आहे (प्रदाता `cursor`, ज्यासोबत बंदीच्या जोखमीची चेतावणी आहे).
हा एक साधा REST अॅडॅप्टर आहे (`@cursor/sdk` ही नेटिव्ह अवलंबिता नाही).
`approvePlan` त्रुटी फेकते (Cursor एजंट स्वायत्तपणे चालतात); `listSources` key द्वारे प्रवेश करता येणाऱ्या
रिपॉझिटरीजची सूची देते. Cursor UPPERCASE स्थिती enum
(`CREATING`/`RUNNING`/`FINISHED`/`ERROR`) परत करते, जी सामायिक
`CloudAgentStatus` शी स्पष्टपणे मॅप केली जातात. `baseUrl` प्रत्येक क्रेडेन्शियलसाठी अधिलिखित करता येते,
ज्यामुळे कोडमध्ये बदल न करता API आवृत्ती/पथ दुरुस्त करता येतो.

## डोमेन प्रकार

```typescript
export const CLOUD_AGENT_STATUS = {
  QUEUED: "queued",
  RUNNING: "running",
  AWAITING_APPROVAL: "awaiting_approval",
  COMPLETED: "completed",
  FAILED: "failed",
  CANCELLED: "cancelled",
} as const;

export interface CloudAgentSource {
  repoName: string;
  repoUrl: string; // वैध URL असणे आवश्यक आहे
  branch?: string;
}

export interface CloudAgentResult {
  prUrl?: string;
  prNumber?: number;
  commitMessage?: string;
  diffUrl?: string;
  summary?: string;
  duration?: number; // सेकंद, धन पूर्णांक
  cost?: number; // धन फ्लोट
}

export interface CloudAgentActivity {
  id: string;
  type: "plan" | "command" | "code_change" | "message" | "error" | "completion";
  content: string;
  timestamp: string; // ISO 8601
  metadata?: Record<string, unknown>;
}

export interface CloudAgentTask {
  id: string; // अंतर्गत `task_...` id
  providerId: "jules" | "devin" | "codex-cloud" | "cursor-cloud";
  externalId?: string; // अपस्ट्रीम प्रदात्याचा id
  status: CloudAgentStatus;
  prompt: string; // 1..10000 अक्षरे
  source: CloudAgentSource;
  options: {
    autoCreatePr?: boolean;
    planApprovalRequired?: boolean;
    environment?: Record<string, string>;
  };
  result?: CloudAgentResult;
  activities: CloudAgentActivity[];
  error?: string;
  createdAt: string;
  updatedAt: string;
  completedAt?: string;
}
```

प्रमाणीकरण स्कीमा (`CreateCloudAgentTaskSchema`, `UpdateCloudAgentTaskSchema`) प्रकारांसोबत
निर्यात केल्या जातात आणि रूट हँडलर्सद्वारे वापरल्या जातात.

## डेटाबेस

स्रोत: `src/lib/cloudAgent/db.ts` — टेबल
`createCloudAgentTaskTable()` द्वारे आवश्यकतेनुसार तयार केले जाते (`src/lib/cloudAgent/index.ts` मधून
मॉड्यूल इंपोर्ट करतानाही कॉल केले जाते).

```sql
CREATE TABLE IF NOT EXISTS cloud_agent_tasks (
  id           TEXT PRIMARY KEY,
  provider_id  TEXT NOT NULL,
  external_id  TEXT,
  status       TEXT NOT NULL DEFAULT 'queued',
  prompt       TEXT NOT NULL,
  source       TEXT NOT NULL,             -- JSON
  options      TEXT DEFAULT '{}',         -- JSON
  result       TEXT,                       -- JSON
  activities   TEXT DEFAULT '[]',          -- JSON
  error        TEXT,
  created_at   TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at   TEXT NOT NULL DEFAULT (datetime('now')),
  completed_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_cloud_agent_tasks_provider ON cloud_agent_tasks(provider_id);
CREATE INDEX IF NOT EXISTS idx_cloud_agent_tasks_status   ON cloud_agent_tasks(status);
CREATE INDEX IF NOT EXISTS idx_cloud_agent_tasks_created  ON cloud_agent_tasks(created_at DESC);
```

SQL इंजेक्शन टाळण्यासाठी `updateCloudAgentTask` **कॉलम श्वेतसूची** लागू करते:
`status`, `prompt`, `source`, `options`, `result`, `activities`, `error`,
`completed_at`. आंशिक अपडेटमधील इतर कोणतीही की कोणतीही सूचना न देता वगळली जाते.

## REST API — टास्क जीवनचक्र

**प्रमाणीकरण:** सर्व `/api/v1/agents/tasks*` एंडपॉइंटसाठी **व्यवस्थापन प्रमाणीकरण**
आवश्यक आहे (`requireCloudAgentManagementAuth`,
`src/lib/api/requireManagementAuth` मधील `requireManagementAuth` ला रॅप करते).
हे commit `588a0333` नंतर लागू केले गेले आहे
(_"fix(auth): एजंट आणि कूलडाउन API साठी व्यवस्थापन प्रमाणीकरण आवश्यक करा"_).

| पद्धत   | पथ                            | उद्देश                                                        |
| ------- | ----------------------------- | ------------------------------------------------------------- |
| OPTIONS | `/api/v1/agents/tasks`        | CORS प्रीफ्लाइट                                               |
| GET     | `/api/v1/agents/tasks`        | टास्कची सूची (`provider`, `status`, `limit≤500` नुसार फिल्टर) |
| POST    | `/api/v1/agents/tasks`        | टास्क तयार करणे (अपस्ट्रीमकडे पाठवते + कायमस्वरूपी साठवते)    |
| DELETE  | `/api/v1/agents/tasks?id=...` | क्वेरी id नुसार टास्क हटवणे (अपस्ट्रीमवर **रद्द करत नाही**)   |
| OPTIONS | `/api/v1/agents/tasks/[id]`   | CORS प्रीफ्लाइट                                               |
| GET     | `/api/v1/agents/tasks/[id]`   | टास्क वाचणे + अपस्ट्रीमवरून स्थितीचे लेझी-सिंक करणे           |
| POST    | `/api/v1/agents/tasks/[id]`   | क्रिया: `approve` / `message` / `cancel`                      |
| DELETE  | `/api/v1/agents/tasks/[id]`   | पथ id नुसार टास्क हटवणे                                       |

### टास्क तयार करणे

```bash
curl -X POST http://localhost:20128/api/v1/agents/tasks \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{

    "prompt": "Fix the bug in src/foo.ts where the parser returns null",
    "source": {

      "branch": "main"

      "autoCreatePr": true,

    }
  }'
```

```bash
curl -X POST http://localhost:20128/api/v1/agents/tasks/<id> \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"action":"approve"}'
```

### पुढील संदेश पाठवणे

```bash
curl -X POST http://localhost:20128/api/v1/agents/tasks/<id> \
  -d '{"action":"message","message":"Also add a unit test for the parser"}'
```

### रद्द करणे (केवळ स्थानिक स्थिती)

```bash
curl -X POST http://localhost:20128/api/v1/agents/tasks/<id> \
  -d '{"action":"cancel"}'
```

`cancel` स्थानिक DB मधील `status` बदलून `"cancelled"` करते, परंतु
अपस्ट्रीम प्रदात्याला कॉल **करत नाही** — `CloudAgentBase` मध्ये abort RPC उपलब्ध नाही.
अपस्ट्रीम बिलिंग थांबवण्यासाठी, प्रदात्याच्या स्वतःच्या कन्सोलमध्ये टास्क समाप्त करा.

## REST API — क्लाउड प्रदाता प्लंबिंग

`src/app/api/cloud/` अंतर्गत असलेले हे सहाय्यक एंडपॉइंट्स दूरस्थ क्लायंटद्वारे
(CLI, Electron अॅप किंवा सिंक वर्कर्स) प्रदाता कनेक्शन मेटाडेटा वाचण्यासाठी
आणि मॉडेल उपनावे निराकरण करण्यासाठी वापरले जातात. कार्य एंडपॉइंट्सद्वारे वापरल्या जाणाऱ्या व्यवस्थापन प्रमाणीकरणाऐवजी, त्यांचे प्रमाणीकरण **नियमित API की**
(`validateApiKey` द्वारे) वापरून केले जाते.

| पद्धत | पथ                              | उद्देश                                                                      |
| ----- | ------------------------------- | --------------------------------------------------------------------------- |
| POST  | `/api/cloud/auth`               | API की सत्यापित करणे, मास्क केलेले कनेक्शन मेटाडेटा + मॉडेल उपनावे परत करणे |
| PUT   | `/api/cloud/credentials/update` | `accessToken` / `refreshToken` / `expiresAt` रीफ्रेश करणे                   |
| POST  | `/api/cloud/model/resolve`      | मॉडेल उपनावाचे `{ provider, model }` मध्ये निराकरण करणे                     |
| GET   | `/api/cloud/models/alias`       | सर्व मॉडेल उपनावे सूचीबद्ध करणे                                             |
| PUT   | `/api/cloud/models/alias`       | मॉडेल उपनाव सेट करणे (आणि सक्षम असल्यास Cloud शी स्वयं-सिंक करणे)           |

`/api/cloud/auth` कधीही कच्चे `apiKey` / `accessToken` / `refreshToken` परत करत नाही. ते
`hasApiKey`, `hasAccessToken`, `hasRefreshToken` आणि मास्क केलेले पूर्वावलोकन
(`maskedApiKey`: पहिले 4 + `****` + शेवटचे 4) परत करते.

## क्रेडेन्शियल्सचे निराकरण

`src/lib/cloudAgent/api.ts` मधील `getCloudAgentCredentials(providerId)`:

1. `getProviderConnections({ provider: providerId, isActive: true })` द्वारे सक्रिय प्रदाता कनेक्शन्स लोड करते.
2. प्रत्येक कनेक्शनसाठी `apiKey` (ट्रिम केलेली) प्राधान्याने वापरते. ती नसल्यास `accessToken` वापरते.
3. पहिला रिक्त नसलेला टोकन `{ apiKey: token }` म्हणून गुंडाळून परत करते.
4. वापरण्यायोग्य टोकन न सापडल्यास `null` परत करते — API `400` सह
   `"क्लाउड एजंट प्रदात्यासाठी कोणतीही सक्रिय क्रेडेन्शियल्स कॉन्फिगर केलेली नाहीत: <id>"` असा प्रतिसाद देते.

याचा अर्थ Cloud Agents नियमित LLM प्रदात्यांप्रमाणेच Provider Connection टेबलचा
पुनर्वापर करतात. Jules सक्षम करण्यासाठी, `provider: "jules"`
आणि भरलेली `apiKey` असलेले सक्रिय कनेक्शन तयार करा.

## डॅशबोर्ड

स्रोत: `src/app/(dashboard)/dashboard/cloud-agents/page.tsx`

एक `"use client"` React पृष्ठ जे:

- कार्ये सूचीबद्ध करते (`GET /api/v1/agents/tasks` द्वारे नियमितपणे तपासली जातात).
- `CreateCloudAgentTaskSchema` शी मॅप होणाऱ्या फॉर्मद्वारे नवीन कार्ये सबमिट करते.
- स्थिती बॅज (`queued`, `running`, `awaiting_approval`, `completed`,
  `failed`, `cancelled`) दाखवते आणि `activities[]` टाइमलाइन रेंडर करते.
- `status === "completed"` असताना `result.prUrl` / `commitMessage` / `summary` दर्शवते.

## A2A सह एकत्रीकरण

Cloud Agents ना A2A कौशल्ये म्हणून उपलब्ध करून देण्यासाठी असे A2A कौशल्य नोंदवा, जे
त्याचा `tasks/send` हँडलर `getAgent(...).createTask(...)` कडे सोपवते आणि A2A कार्य
स्थिती इव्हेंट्सचे JSON-RPC 2.0 प्रोटोकॉलमध्ये भाषांतर करते. [A2A-SERVER.md](./A2A-SERVER.md) पहा.

## नवीन Cloud Agent जोडणे

1. `CloudAgentBase` विस्तारित करणारी `src/lib/cloudAgent/agents/<name>.ts` तयार करा.
2. `createTask`, `getStatus`, `approvePlan` (किंवा लागू नसल्यास त्रुटी फेका),
   `sendMessage`, `listSources` अंमलात आणा. स्थिती सामान्यीकरणासाठी `this.mapStatus(...)` वापरा.
3. स्थिर `providerId` अंतर्गत `src/lib/cloudAgent/registry.ts` मध्ये नोंदणी करा.
4. `src/lib/cloudAgent/types.ts` मधील `providerId` लिटरल युनियन विस्तारित करा
   (`CloudAgentTask.providerId` आणि `CreateCloudAgentTaskSchema`).
5. कनेक्शन रेकॉर्ड आवश्यक असल्यास प्रदाता `src/shared/constants/providers.ts` मध्ये
   जोडा. OAuth-आधारित प्रदात्यांना `src/lib/oauth/providers/` देखील आवश्यक आहे.
6. `tests/unit/cloud-agent-*.test.ts` अंतर्गत चाचण्या जोडा.
7. हे दस्तऐवज आणि डॅशबोर्डचा `CLOUD_AGENTS` स्थिरांक अद्ययावत करा.

## कॉन्फिगरेशन

| पर्यावरणीय चल    | उद्देश                                                               |
| ---------------- | -------------------------------------------------------------------- |
| `DATA_DIR`       | `cloud_agent_tasks` असलेल्या SQLite डेटाबेसचे स्थान                  |
| `JWT_SECRET`     | टास्क एंडपॉइंट्सवरील व्यवस्थापन प्रमाणीकरणासाठी आवश्यक               |
| `API_KEY_SECRET` | संग्रहित प्रदाता कनेक्शन क्रेडेन्शियल्स एन्क्रिप्ट करण्यासाठी आवश्यक |

सध्या कोणतेही Cloud-Agent-विशिष्ट पर्यावरणीय चल अस्तित्वात नाहीत — प्रत्येक गुपित
`provider_connections` तक्त्यामध्ये असते.
