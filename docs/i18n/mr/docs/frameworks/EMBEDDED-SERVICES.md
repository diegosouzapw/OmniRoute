त्यांना प्रथम-श्रेणी रूटिंग लक्ष्ये म्हणून उपलब्ध करून देते. बाह्य प्रदात्यांप्रमाणे (ज्यांच्याशी इंटरनेटवरून
API की वापरून संपर्क साधला जातो) नसून, एम्बेडेड सेवा OmniRoute असलेल्या त्याच मशीनवर चालतात आणि लूपबॅकद्वारे संवाद साधतात.

## 1. आढावा

### एम्बेडेड सेवा का?

सहा सेवा एम्बेड केलेल्या आहेत:

| सेवा            | npm पॅकेज                        | डीफॉल्ट पोर्ट | उद्देश                                                                                                                                                                                               |
| --------------- | -------------------------------- | :-----------: | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **9Router**     | `9router`                        |     20130     | OmniRoute उप-प्रदाता म्हणून वापरू शकणारा AI राउटर. मॉडेल्स `9router/{sub}/{model}` या स्वरूपात उपलब्ध केली जातात                                                                                     |
| **CLIProxyAPI** | GitHub रिलीज बायनरी (`cliproxy`) |     8317      | Anthropic CLI प्रमाणीकरण प्रवाहांसाठी स्थानिक प्रॉक्सी अडॅप्टर. OAuth टोकन कालबाह्य झाल्यावर फॉलबॅक राउटिंग प्रदान करतो                                                                              |
| **Mux**         | `mux` (हेडलेस `mux server`)      |     8322      | स्थानिक एजंट-ऑर्केस्ट्रेशन डीमन (coder/mux). केवळ जीवनचक्र-व्यवस्थापित — राउटिंग लक्ष्य नाही (LLM प्रॉक्सीइंग नाही).                                                                                 |
| **Bifrost**     | `@maximhq/bifrost`               |     8080      | Go AI-गेटवे रिले बॅकएंड. सुरू असताना, रिले रूटद्वारे (`/v1/relay/`) स्वयंचलितपणे निवडला जातो                                                                                                         |
| **Dario**       | `@askalf/dario`                  |     3456      | Claude-सदस्यता प्रॉक्सी — Claude-Code-स्वरूपाच्या ट्रॅफिकसाठी CLIProxyAPI चा पर्याय/फेलओव्हर; इंजेक्ट केलेली की `DARIO_ADMIN_TOKEN` बनते आणि त्याच्या `/admin/*` OAuth नियंत्रण स्तराचे संरक्षण करते |
| **open-wa**     | `@open-wa/wa-automate`           |     8323      | WhatsApp Web स्वयंचलन (Puppeteer द्वारे हेडलेस Chromium). केवळ जीवनचक्र-व्यवस्थापित — राउटिंग लक्ष्य नाही.                                                                                           |

सर्व सहा सेवा समान पर्यवेक्षी मॉडेलचे अनुसरण करतात:

- OmniRoute त्यांना `DATA_DIR/services/{name}/` अंतर्गत स्थापित करते (OmniRoute च्या स्वतःच्या `package.json` पासून विलग)
- OmniRoute त्यांना चाइल्ड प्रोसेस म्हणून सुरू करते आणि त्यांचे निरीक्षण करते
- OmniRoute चाइल्ड प्रोसेसच्या वातावरणात तात्पुरती API की इंजेक्ट करते आणि सेवा बंद न करता ती बदलते (लागू असेल तेथे)
- सर्व व्यवस्थापन रूट्स (`/api/services/*`) **LOCAL_ONLY** आहेत — केवळ लूपबॅकवरून प्रवेशयोग्य (कठोर नियम #17)

### प्रमुख निर्णय (डिझाइन योजनेतून)

| निर्णय                                   | मूल्य                                                                                              |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 9Router च्या मूळ UI साठी डॅशबोर्ड प्रवेश | `/dashboard/providers/services/9router/embed/*` येथे रिव्हर्स प्रॉक्सी                             |
| स्थापना यंत्रणा                          | `execFile` द्वारे `npm install {package}` (शेल इंटरपोलेशन नाही)                                    |
| वापर पद्धत                               | राउटिंग इंजिनमध्ये `9router/{sub}/{model}` म्हणून नोंदणीकृत प्रदाता                                |
| API की व्यवस्थापन                        | OmniRoute व्युत्पन्न करते, स्थिर संचयनात एन्क्रिप्ट करते (AES-256-GCM) आणि env द्वारे इंजेक्ट करते |
| डॅशबोर्ड स्थान                           | `/dashboard/providers/services` (तीन टॅब)                                                          |
| स्वयंचलित प्रारंभ                        | प्रत्येक सेवेसाठी टॉगल, डीफॉल्टनुसार बंद                                                           |

## 3. लाइफसायकल स्थिती यंत्र

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
             हेल्थ प्रोब यशस्वी    │         क्रॅश / SIGTERM    │
                               ┌────▼─────┐  (5s आत एक्झिट)     │
                               │ running  │──── क्रॅश ──────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

स्थिती `version_manager` DB तक्त्यात (`status` स्तंभ) संग्रहित केली जाते आणि
`ServiceSupervisor` च्या इन-मेमरी स्थितीत प्रतिबिंबित केली जाते. चालू प्रक्रियेसाठी
इन-मेमरी स्थिती अधिकृत असते; बूटच्या वेळी DB स्थिती टिकाऊ फॉलबॅक असते.

### स्थिती संक्रमणे

| येथून           | घटना                                    | येथे                   |
| --------------- | --------------------------------------- | ---------------------- |
| `not_installed` | `install()` यशस्वी होते                 | `stopped`              |
| `stopped`       | `start()` कॉल केले जाते                 | `starting`             |
| `starting`      | हेल्थ प्रोब 200 परत करतो                | `running`              |
| `starting`      | निरोगी होण्यापूर्वी प्रक्रिया बंद होते  | `error`                |
| `running`       | `stop()` कॉल केले जाते                  | `stopping` → `stopped` |
| `running`       | प्रक्रिया अनपेक्षितपणे बंद होते (< 5 s) | `error` (जलद क्रॅश)    |
| `running`       | प्रक्रिया अनपेक्षितपणे बंद होते (> 5 s) | `error`                |
| `error`         | `start()` कॉल केले जाते                 | `starting`             |
| कोणतीही         | `stopping` असताना `stop()`              | कोणतीही कृती नाही      |

### ऑपरेशन लॉक

`ServiceSupervisor` असिंक्रोनस ऑपरेशन लॉकद्वारे (`withLock()`) लाइफसायकल ऑपरेशन्स
क्रमबद्ध करतो. एकाच सुपरवायझरवरील समवर्ती `start()` कॉल्समुळे नेमकी एकच प्रक्रिया
स्पॉन होते; दुसरा कॉलर प्रतीक्षा करतो आणि विद्यमान स्थिती परत करतो. उदाहरणार्थ,
ऑटो-स्टार्ट आणि UI बटण एकाच वेळी सक्रिय झाल्यास यामुळे रेस कंडिशन्स टाळल्या जातात.

## 4. API संदर्भ

`/api/services/` अंतर्गत असलेले सर्व मार्ग **LOCAL_ONLY** आहेत (केवळ loopback, कठोर नियम #17).

### 4.1 9Router endpoints (11 मार्ग)

#### `POST /api/services/9router/install`

npm वरून 9Router स्थापित करते. स्वतःचे `package.json` आणि `node_modules/` असलेली
`DATA_DIR/services/9router/` निर्देशिका तयार करते. OmniRoute च्या स्वतःच्या deps सोबत संघर्ष होत नाही.

**विनंतीचे body** (सर्व पर्यायी):

```json

```

| फील्ड     | प्रकार   | डीफॉल्ट    | वर्णन                                           |
| --------- | -------- | ---------- | ----------------------------------------------- |
| `version` | `string` | `"latest"` | स्थापित करण्यासाठी npm version tag किंवा semver |

**प्रतिसाद:**

| स्थिती | वर्णन                                                         |
| ------ | ------------------------------------------------------------- |
| `200`  | `{ ok: true, installedVersion: "x.y.z", path: "..." }`        |
| `400`  | अवैध विनंती body (Zod प्रमाणीकरण अयशस्वी)                     |
| `409`  | स्थापना आधीपासून सुरू आहे (lock धरलेले आहे)                   |
| `500`  | npm install अयशस्वी — अनुकूल त्रुटी संदेशासाठी `message` पाहा |

**टिपा:** `execFile('npm', [...])` वापरते — shell नाही, interpolation नाही (कठोर नियम #13).
EACCES त्रुटी अनुकूल संदेशांच्या स्वरूपात दाखवल्या जातात.

ऑथ हेडरची आवश्यकता नाही.

**पेअरिंग:** open-wa हे अनधिकृत असून WhatsApp शी संलग्न नाही — कनेक्ट केलेल्या
क्रमांकावर WhatsApp च्या स्वतःच्या ऑटोमेशन शोध प्रणालीमुळे बंदीचा धोका असतो.
पहिल्यांदा सुरू केल्यावर, पेअरिंग QR कोड stdout वर प्रिंट केला जातो आणि
विद्यमान लॉग पॅनेल/SSE स्ट्रीमद्वारे उपलब्ध केला जातो — या इंटिग्रेशनमध्ये अद्याप
स्वतंत्र QR-प्रतिमा एंडपॉइंट नाही.

### 4.7 रिव्हर्स प्रॉक्सी (9Router डॅशबोर्ड एम्बेड)

डॅशबोर्ड अंतर्गत रिव्हर्स प्रॉक्सीद्वारे 9Router वेब UI iframe मध्ये
एम्बेड करतो:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

हा प्रॉक्सी:

- विनंती `http://127.0.0.1:{port}/{path}` कडे फॉरवर्ड करतो (केवळ लूपबॅक)
- येणारे `cookie` आणि `authorization` हेडर काढून टाकतो (OmniRoute सेशनची गळती होत नाही)
- 9Router प्रमाणीकरणासाठी `Authorization: Bearer {apiKey}` अंतःक्षेपित करतो
- प्रतिसादातून `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*` काढून टाकतो
- `<base href>` अंतःक्षेपित करण्यासाठी आणि अॅब्सोल्यूट पाथ सामान्यीकृत करण्यासाठी (`/foo` → `/dashboard/.../embed/foo`) HTML प्रतिसाद पुनर्लिखित करतो

एम्बेड केलेल्या डॅशबोर्डसाठी WebSocket अपग्रेड स्वतंत्र पोर्टवरील
पूरक सर्व्हरद्वारे हाताळले जातात (`src/lib/services/embedWsProxy.ts` पहा).

**सुरक्षा:** एम्बेड प्रॉक्सी रूट्सना `LOCAL_ONLY_API_PREFIXES` अंतर्गत वर्गीकृत केले आहे
आणि त्यांना केवळ लूपबॅकवरून प्रवेश करता येतो. Cloudflare/Ngrok टनेलद्वारे
JWT मिळवणारा हल्लेखोर एम्बेड केलेल्या सेवांमध्ये प्रॉक्सी करू शकत नाही.

## 5. सुरक्षा

### LOCAL_ONLY अंमलबजावणी (कठोर नियम #17)

`/api/services/` आणि `/dashboard/providers/services/*/embed/` अंतर्गत सर्व मार्ग
`src/server/authz/routeGuard.ts` मध्ये LOCAL_ONLY म्हणून वर्गीकृत केले आहेत. कोणत्याही प्रमाणीकरण शाखेपूर्वी
लूपबॅक तपासणी बिनशर्त चालते:

```
विनंती येते
  → isLocalOnlyPath(path)?
      → लूपबॅक नसल्यास → 403 LOCAL_ONLY (नेहमी, प्रमाणीकरण तपासणीपूर्वी)
      → लूपबॅक असल्यास → सामान्य प्रमाणीकरणाकडे पुढे जा
```

यामुळे लीक झालेल्या JWT मुळे (उदा., टनेलद्वारे) `npm install` किंवा
प्रक्रिया सुरू होण्यास प्रतिबंध होतो. संपूर्ण स्तर
मॅट्रिक्ससाठी `docs/security/ROUTE_GUARD_TIERS.md` पहा.

### API की अंतःक्षेपण

9Router आणि Mux यांना त्यांच्या स्वतःच्या HTTP एंडपॉइंटसाठी API की/बेअरर टोकन आवश्यक आहे.
OmniRoute:

1. `crypto.randomBytes(32).toString("base64url")` द्वारे सेवा-विशिष्ट
   उपसर्गासह (`nr_` हा 9Router साठी, `mx_` हा Mux साठी) की निर्माण करते.
2. AES-256-GCM वापरून ती स्थिर संचयनात कूटबद्ध करते (प्रदाता क्रेडेन्शियल्ससाठी वापरलेले तेच सायफर).
3. प्रक्रिया सुरू करताना ती डिक्रिप्ट करून पर्यावरण चल म्हणून अंतःक्षेपित करते —
   9Router साठी `NINEROUTER_API_KEY`, Mux साठी `MUX_SERVER_AUTH_TOKEN` (CLI
   फ्लॅग म्हणून कधीही नाही, त्यामुळे टोकन `ps`/प्रक्रिया सूचीमध्ये कधीही दिसत नाही).
4. कोणत्याही HTTP प्रतिसादात साधा मजकूर असलेली की कधीही परत करत नाही.

CLIProxyAPI ला प्रक्रिया सुरू करताना अंतःक्षेपित केलेली समर्पित डेटा-प्लेन की मिळते
(`needsApiKey: true` — अॅडॅप्टरविरुद्ध मॉडेल समक्रमणासाठी वापरली जाते).

### SSRF संरक्षण

रिव्हर्स HTTP प्रॉक्सी (`/dashboard/.../embed/[...path]`) फक्त
`http://127.0.0.1:{port}` कडे अग्रेषित करण्यासाठी हार्डकोड केलेली आहे. ती लूपबॅक नसलेल्या
गंतव्यांकडे जाणाऱ्या पुनर्निर्देशनांचे कधीही अनुसरण करत नाही. लूपबॅक श्रेणीबाहेरील पत्त्यावर
रिझॉल्व्ह होणारी कोणतीही अपस्ट्रीम URL नाकारण्यासाठी `ssrf-req-filter` लायब्ररी वापरली जाते.

### शेल सुरक्षा (कठोर नियम #13)

`npm install` हे `execFile('npm', ['install', pkg, '--prefix', dir])` द्वारे चालवले जाते —
टेम्प्लेट लिटरल्स नाहीत, शेल नाही आणि बाह्य पथांचे कमांड स्ट्रिंगमध्ये इंटरपोलेशन नाही.
रनटाइम मूल्ये (पोर्ट्स, API की) चाइल्ड प्रक्रियेच्या `env` ऑब्जेक्टद्वारे दिली जातात.

### त्रुटी निर्जंतुकीकरण (कठोर नियम #12)

`/api/services/*` कडून येणारे सर्व त्रुटी प्रतिसाद `buildErrorBody()` किंवा
`sanitizeErrorMessage()` मधून जातात. अपरिष्कृत `err.stack` आणि `err.message` कधीही
कॉलरला जसेच्या तसे परत केले जात नाहीत.

### पायरी 2 — बूटस्ट्रॅपमध्ये नोंदणी करा

`src/lib/services/bootstrap.ts` मधील `SERVICES` अॅरेमध्ये एक `ServiceEntry` जोडा:

`cfg.tool === "myservice"` हाताळण्यासाठी `buildSpawnArgsFactory()` विस्तारित करा.

#### प्लग करता येणारा प्रदाता-प्लगइन करार (टप्पा 1, #7333)

`src/lib/services/providerPlugins/` मध्ये असा `ServiceProviderPlugin` करार सादर केला आहे,
जो एकाच बॅकएंडची रचना दोन असंबंधित फाइल्समध्ये स्वतंत्रपणे व्यक्त करण्याऐवजी, बॅकएंडच्या
`bootstrap.ts` मधील `ServiceEntry` फील्ड्स आणि `serviceBackends.ts` मधील
मॅनिफेस्ट-टेम्प्लेट फील्ड्स एका ऑब्जेक्टमध्ये पॅकेज करतो. हे लिहिताना **फक्त `9router`
स्थलांतरित केले आहे** — `bootstrap.ts`, `getServiceProviderPlugin("9router")`
(`src/lib/services/providerPlugins/registry.ts`) मधून त्याची `SERVICES[]` नोंद व्युत्पन्न करते;
प्लगइन कधीही अनुपस्थित असल्यास स्टार्टअप त्रुटी निर्माण होते. `cliproxy`, `mux`, आणि `bifrost`
यांमधील आधीपासून अस्तित्वात असलेले इनलाइन `SERVICES[]` लिटरल्स अपरिवर्तित राहतात.

`open-sse/config/providerPluginManifest.ts` मध्ये व्यवस्थित संरचित
`ProviderPluginManifestEntry` तयार करणारा अतिरिक्त
`createServiceBackendManifestEntry(pluginId, template)` हेल्परही जोडला गेला आहे, जो
`SERVICE_BACKEND_MANIFEST_TEMPLATE` नोंदीवरून ते तयार करतो — तो अद्याप कोणत्याही प्रत्यक्ष
विनंती मार्गाशी जोडलेला **नाही** (`generateProviderPluginManifestFromRegistry()` किंवा
`/v1/providers/[provider]/models` यांपैकी कोणत्याहीशी नाही); दुसऱ्या बॅकएंडसाठी करार
सिद्ध झाल्यानंतर हे पुढील काम म्हणून राहते.

समस्या #7333 अंतर्गत ट्रॅक केलेल्या पुढील PRs साठी पुढे ढकललेले काम: `cliproxyapi` चे
त्याच रजिस्ट्रीद्वारे स्थलांतर, `mux`/`bifrost` चे `ServiceBackendPluginId` युनियनमध्ये
सामान्यीकरण, एक्झिक्युटर-राउटिंगचे विशेष प्रकरण
(`open-sse/executors/index.ts`, `open-sse/handlers/chatCore/executorProxy.ts`) प्लगइन
करारामध्ये समाविष्ट करणे आणि `createServiceBackendManifestEntry()` ला प्रत्यक्ष
मॅनिफेस्ट/मॉडेल्स कोड मार्गाशी जोडणे.

## 7. समस्यानिवारण

### सेवा सुरू होत नाही

**लक्षणे:** Start बटण 503 प्रतिसाद देते, स्थिती `"error"` किंवा `"starting"` अशीच राहते.

**तपासणीसूची:**

1. `GET /api/services/{name}/logs` तपासा (किंवा डॅशबोर्डमधील Logs पॅनेल). `Error: ENOENT`, `address already in use`, किंवा `Cannot find module` यांसारख्या ओळी शोधा.
2. `npm` PATH मध्ये असल्याची खात्री करा: OmniRoute चालवणाऱ्या त्याच वापरकर्ता खात्यातून `which npm` चालवा.
3. सेवा इंस्टॉल केलेली असल्याची खात्री करा: `installedVersion` साठी `GET /api/services/{name}/status` तपासा. ते `null` असल्यास, प्रथम इंस्टॉलेशन चालवा.
4. `DATA_DIR/services/{name}/node_modules/` अस्तित्वात आहे आणि रिकामी नाही याची खात्री करा.
5. निर्गमनाचे शुद्धीकृत कारण पाहण्यासाठी स्थिती प्रतिसादातील `lastError` फील्ड तपासा.

### कोल्ड स्टार्ट मंद आहे (`running` स्थिती गाठण्यासाठी > 10 s)

**लक्षणे:** `"running"` किंवा `"error"` स्थितीत जाण्यापूर्वी स्थिती बराच वेळ `"starting"` अशीच राहते.

**स्पष्टीकरण:** 9Router च्या कोल्ड स्टार्टमध्ये मोठे अवलंबित्व-वृक्ष (DNS, टनेल, MITM मॉड्यूल्स) इम्पोर्ट करणे समाविष्ट असते. डीफॉल्ट आरोग्य-तपासणी अंतर 2 s आहे आणि पर्यवेक्षक टाइमआउट घोषित करण्यापूर्वी 3 प्रयत्न करतो (परंतु पोलिंग सुरू ठेवतो).

**उपाय:** `healthIntervalMs` आणि `waitForHealthy` टाइमआउट (`healthIntervalMs * 3`) हे `bootstrap.ts` मध्ये कॉन्फिगर करता येतात. सुरू होण्यासाठी अधिक वेळ लागणाऱ्या सेवांसाठी `healthIntervalMs` चे मूल्य 5000 आणि `stopTimeoutMs` चे मूल्य 30 000 करा.

---

### पोर्ट संघर्ष (`EADDRINUSE`)

**लक्षणे:** लॉगमध्ये `address already in use :::20130` दिसते.

**कारणे:**

- दुसरी एखादी प्रोसेस आधीपासून पोर्ट 20130 वापरत आहे.
- मागील 9Router प्रोसेस पूर्णपणे थांबवली गेली नाही (झॉम्बी PID).

**उपाय:**

1. `.env` मधील `NINEROUTER_PORT` पर्यावरणीय चलाद्वारे डीफॉल्ट पोर्ट बदला.
2. संघर्ष करणारी प्रोसेस शोधून बंद करा: `lsof -ti :20130 | xargs kill -9`.
3. `bootstrap.ts` मधील `port` फील्डद्वारे प्रत्येक सेवेसाठी स्वतंत्रपणे पोर्ट कॉन्फिगर करता येतो.

**टीप:** OmniRoute च्या डीफॉल्ट पोर्ट 20128 सोबत संघर्ष टाळण्यासाठी 9Router विशेषतः पोर्ट 20130 डीफॉल्ट म्हणून वापरतो.

---

### इंस्टॉलेशनदरम्यान परवानगी नाकारली (EACCES)

**लक्षणे:** इंस्टॉलेशन 500 प्रतिसाद देते, लॉगमध्ये `EACCES` किंवा `permission denied` दिसते.

**कारणे:**

- OmniRoute प्रोसेसला `DATA_DIR` किंवा तिच्या मूळ निर्देशिकेत लिहिण्याची परवानगी नाही.
- मॅप केलेल्या व्हॉल्यूमवर लेखन-अधिकार नसताना रूटलेस Docker मध्ये चालवले जात आहे.

**उपाय:**

1. `DATA_DIR` तपासा (डीफॉल्ट: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. OmniRoute प्रोसेसच्या वापरकर्त्याच्या मालकीची ही निर्देशिका असल्याची खात्री करा: `chown -R $USER ~/.omniroute/`
3. Docker मध्ये, व्हॉल्यूम माउंटला कंटेनर वापरकर्त्यासाठी योग्य परवानग्या असल्याची खात्री करा.

---

### अपडेट अयशस्वी होते (`npm install` टाइमआउट किंवा नेटवर्क त्रुटी)

**लक्षणे:** अपडेट `InstallError` सह 500 प्रतिसाद देते, लॉगमध्ये नेटवर्क टाइमआउट दिसतो.

**तपासणीसूची:**

1. npm रजिस्ट्रीशी संपर्क साधता येत असल्याची खात्री करा: `npm ping`.
2. कॉर्पोरेट प्रॉक्सी तपासा: `npm config get proxy`, `npm config get https-proxy`.
3. इंस्टॉलेशन स्वहस्ते करून पाहा: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`.
4. एअर-गॅपच्या मागे असल्यास, टारबॉल आधीच डाउनलोड करा आणि `npm install /path/to/tarball.tgz` वापरा.

---

### सुरू केल्यानंतर सेवा लगेच `"error"` स्थिती दर्शवते (जलद क्रॅश)

**लक्षणे:** स्थिती 5 सेकंदांपेक्षा कमी वेळात `"starting"` वरून `"error"` मध्ये बदलते. `lastError` मध्ये `"Fast crash (exited with code 1)"` दिसते.

**तपासणीसूची:**

1. लॉगचा संपूर्ण शेवटचा भाग वाचा: `GET /api/services/{name}/logs?tail=500`.
2. सामान्य कारण: सेवेला अपेक्षित असलेली पर्यावरणीय चले उपलब्ध नसणे.
3. 9Router साठी: स्पॉन करताना पास केलेल्या env मध्ये `NINEROUTER_DISABLE_MITM=true` आणि `NINEROUTER_DISABLE_TUNNEL=true` असल्याची खात्री करा (`installers/ninerouter.ts` मधील `resolveSpawnArgs` पाहा).

## 8. वारंवार विचारले जाणारे प्रश्न

**प्रश्न: एम्बेडेड सेवांचे endpoints मी non-loopback clients साठी उघड करू शकतो का?**

नाही. LOCAL_ONLY tier हेतुपुरस्सर ठेवलेला आहे (अपरिवर्तनीय नियम #17). `npm install` चालवू शकणारे किंवा `node` processes सुरू करू शकणारे routes non-loopback traffic मधून उपलब्ध असता कामा नयेत, कारण tunnel (Cloudflare, Ngrok, Tailscale) द्वारे JWT लीक झाल्यास अन्यथा कोणतेही processes सुरू करणे शक्य होईल. `/api/services/` साठी यामधून वगळण्याची कोणतीही तरतूद नाही — `/api/mcp/` च्या विपरीत, ते manage-scope bypass यादीतून वगळलेले आहे. `docs/security/ROUTE_GUARD_TIERS.md` पहा.

---

**प्रश्न: production/cloud deployments मध्ये 9Router आणि CLIProxyAPI उपलब्ध असतील का?**

होय. दोन्ही सेवा OmniRoute प्रमाणेच local-first मॉडेलचे अनुसरण करतात. त्या त्याच मशीनवर चालतात आणि loopback द्वारे परस्परांशी संवाद साधतात. येथे "Production" म्हणजे OmniRoute deploy केलेला VPS किंवा local server; remote cloud provider नव्हे.

---

**प्रश्न: supervisor debug कसा करावा?**

1. SSE log stream चे tail करा: `curl -N http://localhost:20128/api/services/9router/logs`.
2. OmniRoute च्या pino output मधील `service:supervisor` namespace नुसार filter केलेले structured logs तपासा.
3. DB row तपासा: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`.
4. सध्याची live state, PID, health आणि `lastError` एकाच call मध्ये पाहण्यासाठी `GET /api/services/9router/status` वापरा.

---

**प्रश्न: supervisor मध्ये `health: "degraded"` किंवा `health: "unknown"` दिसते, पण state `"running"` आहे. ही समस्या आहे का?**

`"degraded"` म्हणजे health probe ने non-200 response परत केला. `"unknown"` म्हणजे अद्याप कोणताही probe पूर्ण झालेला नाही (पहिल्या poll सोबत race). startup दरम्यान या दोन्ही स्थिती तात्पुरत्या असतात. `"running"` झाल्यानंतर `healthIntervalMs * 3` ms पेक्षा जास्त काळ health `"degraded"` राहिल्यास, embedded service चालू आहे, पण तिचे HTTP API प्रतिसाद देत नाही. status response मधील port योग्य आहे का आणि सेवा प्रत्यक्षात त्या port वर listen करत आहे का ते तपासा.

---

**प्रश्न: पूर्ण restart न करता मी 9Router API key बदलू शकतो का?**

नाही. spawn वेळी API key ही environment variable द्वारे 9Router ला दिली जाते. चालू process मधील environment variables बदलता येत नाहीत. नवीन key लागू करण्यासाठी `POST .../rotate-key` सेवा आपोआप थांबवते आणि पुन्हा सुरू करते. key rotation सेवेच्या `stopTimeoutMs` (default 15 s) आणि तिच्या startup वेळेच्या एकत्रित कालावधीत प्रभावी होते.

---

**प्रश्न: ring buffer ची मर्यादा किती आहे आणि तो भरल्यावर काय होते?**

प्रत्येक सेवेसाठी स्वतंत्र 5 MB ring buffer असतो. buffer भरल्यावर नवीन lines साठी जागा करण्यासाठी सर्वांत जुन्या log lines काढून टाकल्या जातात. SSE `snapshot` event हा `tail` मर्यादेतील सर्वांत अलीकडील lines परत करतो. DB row मध्ये `logsBufferPath` सेट केलेले नसल्यास logs disk वर कायमस्वरूपी जतन केले जात नाहीत.
