> **अधिकृत स्रोत:** `src/lib/skills/` आणि `src/app/api/skills/`
> **शेवटचे अद्यतन:** 2026-06-28 — v3.8.40

OmniRoute एक विस्तारक्षम Skills फ्रेमवर्क उपलब्ध करून देते, ज्यामुळे भाषा मॉडेल्सना (आणि ऑपरेटर्सना) पुन्हा वापरता येणाऱ्या क्षमता एकत्रित करता येतात — फाइलसिस्टम वाचन आणि HTTP विनंत्यांपासून ते सँडबॉक्समधील कोड अंमलबजावणी आणि निवडक मार्केटप्लेस स्किल्सपर्यंत.

स्किल हे आवृत्तीबद्ध, स्कीमाद्वारे परिभाषित केलेले कार्याचे एकक आहे. OmniRoute आउटबाउंड विनंत्यांमध्ये स्किल्सची टूल व्याख्या म्हणून भर घालू शकते, मॉडेलकडून परत येणारे टूल कॉल्स इंटरसेप्ट करू शकते, जुळणारा हँडलर चालवू शकते आणि निकाल पुन्हा मॉडेलला देऊ शकते, जेणेकरून संभाषण पुढे सुरू राहू शकेल. मॉडेलला अंमलबजावणी कधीही दिसत नाही — फक्त टूल इंटरफेस दिसतो.

## Agent Skills विरुद्ध Omni Skills

OmniRoute मध्ये दोन वेगळ्या, परंतु परस्परपूरक स्किल प्रणाली आहेत:

| परिमाण       | **Omni Skills** (हा दस्तऐवज)                                                    | **Agent Skills**                                                                            |
| :----------- | :------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------ |
| उद्देश       | LLM टूल इंजेक्शन + सँडबॉक्समधील अंमलबजावणी                                      | बाह्य एजंट्सना शोधण्यासाठी आणि वापरण्यासाठी SKILL.md कॅटलॉग                                 |
| अधिकृत स्रोत | `src/lib/skills/` + मार्केटप्लेस                                                | `src/lib/agentSkills/` + `skills/` डायरेक्टरी                                               |
| रनटाइम मोड   | आउटबाउंड विनंत्यांमध्ये इंजेक्ट केले जाते, टूल-कॉल इव्हेंट्सवर अंमलात आणले जाते | स्थिर markdown कॅटलॉग + REST/MCP/A2A डिस्कव्हरी एंडपॉइंट्स                                  |
| कोण वापरते   | स्वतः OmniRoute (कॉम्बो राउटिंग, इनबाउंड LLM कॉल्स)                             | बाह्य एजंट्स, MCP क्लायंट्स, A2A ऑर्केस्ट्रेटर्स                                            |
| संख्या       | बदलणारी (मार्केटप्लेसवर आधारित)                                                 | 45 कॅटलॉग नोंदी (23 API + 21 CLI + 1 कॉन्फिग)                                               |
| स्वरूप       | टूल स्कीमा + हँडलरसह `SkillDefinition`                                          | `SKILL.md` फ्रंटमॅटर + markdown मुख्य मजकूर                                                 |
| शोध          | `/api/skills/*` REST + `omniroute_skills_*` MCP टूल्स                           | `/api/agent-skills/*` REST + `omniroute_agent_skills_*` MCP टूल्स + A2A `list-capabilities` |

**Omni Skills** हे अंमलबजावणी इंजिन आहे — जेव्हा LLM एखादे टूल वापरते, तेव्हा OmniRoute _काय करू शकते_ हे ते परिभाषित करतात.

**Agent Skills** हा दस्तऐवजीकरण कॅटलॉग आहे — थेट एजंट प्रॉम्प्ट्समध्ये देता येतील अशा संरचित SKILL.md फाइल्सच्या माध्यमातून OmniRoute चे REST API आणि CLI _कसे वापरायचे_ हे ते बाह्य एजंट्सना समजावून सांगतात.

Agent Skills कॅटलॉग, जनरेटर, MCP टूल्स आणि A2A स्किलसाठी [docs/frameworks/AGENT-SKILLS.md](./AGENT-SKILLS.md) पहा.

## संकल्पना

### स्किल स्रोत

स्किल्सचे तीन स्रोत एकाच रजिस्ट्रीमध्ये एकत्र अस्तित्वात असतात:

1. **अंगभूत स्किल्स** (`src/lib/skills/builtins.ts`) — OmniRoute सोबत पुरवली जातात. सर्वसामान्य वापर प्रकरणांचा समावेश करतात:
   - `file_read`, `file_write` — `<DATA_DIR>/skills/workspaces/<hashed-key>/` अंतर्गत प्रत्येक API कीसाठी स्वतंत्र सँडबॉक्स वर्कस्पेस
   - `http_request` — `guard: "public-only"` सह `safeOutboundFetch` द्वारे आउटबाउंड HTTP
   - `web_search` — कॅशिंगसह प्लग करण्यायोग्य शोध प्रदाता (`executeWebSearch`)
   - `eval_code` — Docker-सँडबॉक्समधील `node` किंवा `python` अंमलबजावणी
   - `execute_command` — Docker-सँडबॉक्समधील शेल कमांड
   - `browser` — Playwright-आधारित स्कॅफोल्डिंग, डीफॉल्टनुसार अक्षम (`builtin/browser.ts`)
2. **SkillsMP** (OmniRoute मार्केटप्लेस) — `https://skillsmp.com/api/v1/skills/search` येथून प्राप्त केले जाते. Settings मध्ये `skillsmpApiKey` आवश्यक आहे.
3. **SkillsSH** (`skills.sh` समुदाय कॅटलॉग) — `https://skills.sh/api/search` येथून प्राप्त केले जाते. प्रमाणीकरणाची आवश्यकता नाही; SKILL.md मधील मजकूर GitHub raw मधून घेतला जातो.

डॅशबोर्ड कोणत्या कॅटलॉगमधून इंस्टॉल करतो, हे एकच "सक्रिय प्रदाता" नियंत्रित करतो (`src/lib/skills/providerSettings.ts`). **Settings → Memory & Skills** अंतर्गत तो बदला. डीफॉल्ट: `skillsmp`.

### स्किल ओळख

इन-मेमरी रजिस्ट्रीमध्ये (`src/lib/skills/registry.ts`) स्किल्सना `name@version` नुसार की दिली जाते. आवृत्ती semver (`^\d+\.\d+\.\d+$`) स्वरूपात असणे आवश्यक आहे. `resolveVersion()` हे `^`, `~`, `>`, `>=`, `<`, `<=`, `==` आणि तंतोतंत जुळणारी बंधने समजते.

### स्किल मोड

प्रत्येक स्किलचा एक रनटाइम मोड असतो, जो ते कधी इंजेक्ट केले जाईल हे नियंत्रित करतो:

| मोड    | वर्तन                                                                                                         |
| ------ | ------------------------------------------------------------------------------------------------------------- |
| `on`   | नेहमी टूल व्याख्या म्हणून इंजेक्ट केले जाते                                                                   |
| `off`  | कधीही इंजेक्ट केले जात नाही आणि कधीही अंमलात आणता येत नाही                                                    |
| `auto` | येणाऱ्या विनंतीच्या तुलनेत स्कोअर केले जाते; स्कोअर ≥ `AUTO_MIN_SCORE` (डीफॉल्ट 3) असल्यासच इंजेक्ट केले जाते |

मार्केटप्लेसमधून इंस्टॉल केलेल्या स्किल्ससाठी `auto` हा डीफॉल्ट आहे. `enabled=true` आणि `mode="off"` यांचा एकत्रित अर्थ "नोंदणीकृत, पण निष्क्रिय" असा होतो — जुन्या कोडपाथ्समध्येही सुसंगतता कायम राहावी म्हणून लेगसी कॉलमद्वारे `enabled` टॉगल केल्यावर `mode` देखील बदलला जातो (`src/app/api/skills/[id]/route.ts`).

### स्थिती (अंमलबजावणी)

स्किल अंमलबजावणींचा मागोवा `skill_executions` टेबलमध्ये खालील स्थितींसह घेतला जातो (`src/lib/skills/types.ts`):

```ts
enum SkillStatus {
  PENDING = "pending",
  RUNNING = "running",
  SUCCESS = "success",
  ERROR = "error",
  TIMEOUT = "timeout",
}
```

### रजिस्ट्री कॅशे

`SkillRegistry` हा 60-सेकंद TTL कॅशेसह (`registry.ts:14`) एक सिंगलटन आहे. `loadFromDatabase()` हे आयडेम्पोटंट आहे आणि `pendingLoad` द्वारे एकाच वेळी होणारे कॉल्स डीड्युप्लिकेट करते. कोणतेही लेखन (`register`/`unregister`/`unregisterById`) कॅशे अवैध करते. `getSkillVersions(name)` आणि `resolveVersion(name, constraint)` वापरून आवृत्त्या शोधा.

### प्रदाता-जागरूक इंजेक्शन

`src/lib/skills/injection.ts` मधील `injectSkills()` हा नोंदणीकृत स्किल्सना प्रदात्यानुसार विशिष्ट टूल व्याख्यांमध्ये रूपांतरित करणारा प्रवेशबिंदू आहे:

- **OpenAI** — `{ type: "function", function: { name, description, parameters } }`
- **Anthropic** — `{ name, description, input_schema }`
- **Google (Gemini)** — `{ name, description, parameters }`

टूलचे नाव `name@version` म्हणून एन्कोड केले जाते, जेणेकरून मॉडेल त्याला परत कॉल करते तेव्हा हँडलर योग्य आवृत्ती निवडू शकेल.

### AUTO स्कोअरिंग

जेव्हा `mode="auto"` असते, तेव्हा प्रत्येक उमेदवार स्किलला विनंतीच्या संदर्भानुसार स्कोअर दिला जातो (`injection.ts` मधील `scoreAutoSkill()`):

| संकेत                                              | गुण           |
| -------------------------------------------------- | ------------- |
| स्किलचे नाव संदर्भात जसेच्या तसे दिसते             | +6            |
| नावातील प्रत्येक टोकन संदर्भातील टोकनशी जुळते      | +2            |
| प्रत्येक टॅग उपस्ट्रिंग संदर्भाशी जुळते            | +3            |
| वर्णनातील प्रत्येक टोकन संदर्भाशी जुळते            | +1            |
| पार्श्वभूमीचे कारण नावातील टोकनशी जुळते            | प्रति टोकन +2 |
| पार्श्वभूमीचे कारण टॅगशी जुळते                     | प्रति टोकन +2 |
| टॅगमधील प्रदाता संकेत विनंतीच्या प्रदात्याशी जुळतो | +2 / −2       |

`score >= AUTO_MIN_SCORE = 3` असलेली सर्वोच्च `AUTO_MAX_SKILLS = 5` स्किल्स अंतःक्षेपित केली जातात. समान स्कोअर असल्यास, प्रथम `installCount` (उतरत्या क्रमाने), त्यानंतर नावाच्या वर्णक्रमानुसार निर्णय घेतला जातो (`injection.ts:225-235`).

### टूल कॉल इंटरसेप्शन

अपस्ट्रीमकडून टूल-कॉलिंग प्रतिसाद परत आल्यानंतर, चॅट हँडलरद्वारे `src/lib/skills/interception.ts` मधील `handleToolCallExecution()` कॉल केले जाते:

1. `extractToolCalls()` प्रदाता-विशिष्ट संरचना वाचते (OpenAI `tool_calls` / Responses `function_call`, Anthropic `tool_use`, Gemini `functionCalls`).
2. अंगभूत टूल उपनावे (उदा. `omniroute_web_search` → `web_search`) प्रथम निराकरण केली जातात. अंगभूत हँडलर्स इनलाइन चालतात.
3. इतर सर्व काही `skillExecutor.execute(name@version, args, { apiKeyId, sessionId })` द्वारे रूट केले जाते.
4. परिणाम योग्यतेनुसार प्रतिसादामध्ये पुन्हा समाविष्ट केले जातात — `tool_results`, `function_call_output` आयटम्स किंवा Anthropic `tool_result` ब्लॉक्स.

फक्त अंगभूत इंटरसेप्शनला अनुमती देण्यासाठी, एक्झिक्युशन संदर्भातील `customSkillExecutionEnabled` हे `false` वर सेट केले जाऊ शकते (वापरकर्त्यांनी परिभाषित केलेले हँडलर्स स्पष्टपणे अक्षम करणाऱ्या विनंती मार्गांद्वारे वापरले जाते).

## Docker सँडबॉक्स

अंतर्निर्मित नसलेले कोड पाथ (`eval_code`, `execute_command`) `SandboxRunner` (`src/lib/skills/sandbox.ts`) द्वारे Docker मध्ये चालतात. प्रत्येक कंटेनर पुढील पर्यायांसह सुरू केला जातो:

```
--rm --network none|bridge --cap-drop ALL
--security-opt no-new-privileges --pids-limit 100
--cpus <cpuLimit/1000> --memory <memoryLimit>m
--tmpfs /tmp:rw,noexec,nosuid,size=64m
--tmpfs /workspace:rw,noexec,nosuid,size=64m
--read-only (जेव्हा readOnly=true असते)
```

डीफॉल्ट मूल्ये (`SandboxRunner.DEFAULT_CONFIG`):

| फील्ड            | डीफॉल्ट         | नोंदी                                                     |
| ---------------- | --------------- | --------------------------------------------------------- |
| `cpuLimit`       | 100 (= 0.1 CPU) | `--cpus` कडे पाठवण्यापूर्वी 1000 ने भागले जाते            |
| `memoryLimit`    | 256 MB          | कठोर मर्यादा                                              |
| `timeout`        | 30000 ms        | `SIGTERM` + `docker kill` द्वारे सॉफ्ट किल                |
| `networkEnabled` | `false`         | `--network none` होते                                     |
| `readOnly`       | `true`          | रूट FS केवळ-वाचनीय; `/tmp` आणि `/workspace` हे tmpfs आहेत |

शटडाउनसाठी `SandboxRunner.kill(id)` आणि `killAll()` उपलब्ध करून दिले आहेत; चालू कंटेनरचा मागोवा `runningContainers: Map<string, ChildProcess>` मध्ये घेतला जातो.

### सँडबॉक्स पर्यावरण चल

`src/lib/skills/builtins.ts` मधील `process.env` द्वारे कॉन्फिगर केलेले:

| पर्यावरण चल                       | डीफॉल्ट          | उद्देश                                                                                           |
| --------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------ |
| `SKILLS_MAX_FILE_BYTES`           | `1048576` (1 MB) | `file_read` आणि `file_write` साठी मर्यादा                                                        |
| `SKILLS_MAX_HTTP_RESPONSE_BYTES`  | `256000`         | `http_request` प्रतिसादाच्या मुख्य भागासाठी मर्यादा                                              |
| `SKILLS_MAX_SANDBOX_OUTPUT_CHARS` | `100000`         | कॉलरला परत केल्या जाणाऱ्या stdout/stderr साठी मर्यादा                                            |
| `SKILLS_SANDBOX_TIMEOUT_MS`       | `10000`          | सँडबॉक्समधील कमांडसाठी डीफॉल्ट टाइमआउट; कमाल मर्यादा 60 s                                        |
| `SKILLS_SANDBOX_NETWORK_ENABLED`  | `false`          | बाह्य नेटवर्क प्रवेशासाठी मुख्य गेट. प्रत्येक कॉलनुसार संमती देण्यासाठी `1` किंवा `true` सेट करा |
| `SKILLS_ALLOWED_SANDBOX_IMAGES`   | (खाली पाहा)      | Docker इमेजची स्वल्पविरामाने विभक्त केलेली अनुमतीसूची                                            |

डीफॉल्टनुसार अनुमत इमेज: `alpine:3.20`, `node:22-alpine`, `python:3.12-alpine`. `SKILLS_ALLOWED_SANDBOX_IMAGES` द्वारे केलेली कोणतीही भर डीफॉल्ट इमेजसोबत विलीन केली जाते; अज्ञात इमेज `normalizeImage()` द्वारे नाकारल्या जातात.

> नोंद: स्वतंत्र `SKILLS_EXECUTION_TIMEOUT_MS` पर्यावरण चल नाही. सँडबॉक्सबाहेरील हँडलरचा टाइमआउट `SkillExecutor` (`executor.ts:13`) मध्ये 30 s असा हार्ड-कोड केलेला आहे, परंतु रनटाइममध्ये `skillExecutor.setTimeout(ms)` द्वारे तो बदलता येतो.

### वर्कस्पेस विलगीकरण

`file_read` आणि `file_write` प्रत्येक पाथचे निराकरण `<DATA_DIR>/skills/workspaces/<sha256(apiKeyId).slice(0,24)>/` येथील प्रत्येक API कीसाठी स्वतंत्र असलेल्या वर्कस्पेसच्या सापेक्ष करतात. कोणतेही डिस्क I/O होण्यापूर्वी पाथ ट्रॅव्हर्सल (`..`) आणि प्रतिबंधित सेगमेंट (`.env`, `.git`, `.ssh`, `.omniroute`, `.codex`, `secrets`) नाकारले जातात.

### HTTP सुदृढीकरण

`http_request` (`builtins.ts:257`):

- मेथड अनुमतीसूची: `GET, HEAD, POST, PUT, PATCH, DELETE`
- ब्लॉक केलेले आउटबाउंड हेडर: `host, connection, content-length, cookie, set-cookie, authorization, proxy-authorization`
- रीडायरेक्ट अक्षम (`allowRedirect: false`)
- `guard: "public-only"` सह `safeOutboundFetch` द्वारे रूट केले जाते (खाजगी/लूपबॅक रेंज ब्लॉक केल्या जातात)
- प्रतिसाद `SKILLS_MAX_HTTP_RESPONSE_BYTES` येथे छाटला जातो; क्लायंटला `truncated: true` दिसते

### उदाहरण: सानुकूल स्किल इन्स्टॉल करा

```bash
curl -X POST http://localhost:20128/api/skills/install \
  -H "Authorization: Bearer $OMNIROUTE_MGMT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "reverse-text",
    "version": "1.0.0",
    "description": "Reverses a string",
    "schema": {
      "input":  { "type": "object", "properties": { "text": { "type": "string" } }, "required": ["text"] },
      "output": { "type": "object", "properties": { "reversed": { "type": "string" } } }
    },
    "handlerCode": "echo-handler",
    "apiKeyId": "your-api-key-id"
  }'
```

`handlerCode` स्ट्रिंग ही **हँडलर नाव शोधण्याची कळ** आहे — ती अंमलबजावणीयोग्य कोड नाही. एक्झिक्युटर `skillExecutor.registerHandler(name, fn)` द्वारे तिचे मॅपिंग करतो (`executor.ts:25`). मार्केटप्लेस इन्स्टॉल्स या फील्डमध्ये SKILL.md मजकूर दस्तऐवजीकरण म्हणून साठवतात आणि मॉडेलने व्युत्पन्न केलेल्या टूल कॉल्सद्वारे अंमलबजावणी मार्गित करतात. वापरकर्त्याने पुरवलेल्या कोणत्याही स्वैर सोर्सचे eval केले जात नाही.

- **मुख्य स्विच:** `settings.skillsEnabled = false` सर्व कार्यान्वयने अवरोधित करते आणि `/api/skills/executions` वर HTTP `503` परत करते. रजिस्ट्री लोड होत राहते.
- **निर्गामी प्रवेश प्रतिबंधित करा:** पूर्णपणे एअर-गॅप्ड सँडबॉक्सिंगसाठी `SKILLS_SANDBOX_NETWORK_ENABLED` सेट न करता ठेवा (डीफॉल्ट). प्रत्येक कॉलवरील `networkEnabled: true` साठी तरीही मुख्य गेटची आवश्यकता असते.

- **कार्यान्वयनांचे ऑडिट करा:** `/dashboard/skills/executions` आणि `omniroute_skills_executions` हे दोन्ही `skill_executions` क्वेरी करतात. यशस्वी रनमध्ये `durationMs` समाविष्ट असते; अपयशांमध्ये `errorMessage` समाविष्ट असते.
- **कॅशे अमान्यीकरण:** मॅन्युअल DB संपादनानंतर `skillRegistry.invalidateCache()` कॉल करा; अन्यथा 60 s प्रतीक्षा करा.
- **अनामिक वर्कस्पेस:** `apiKeyId` रिकामे असताना, सर्व कॉल एकाच `"anonymous"` वर्कस्पेसवर हॅश होतात — शेअर-जागरूक कोडने नेहमी वास्तविक की पास केली पाहिजे.

## अंमलबजावणी जीवनचक्र (v3.8.16+)

`SkillExecutor` (`src/lib/skills/executor.ts`) हा **सिंगलटन** आहे, जो प्रत्येक स्किल आवाहन व्यवस्थापित करतो. टाइमआउट, पुनःप्रयत्न आणि अंमलबजावणी स्थिती डीबग करण्यासाठी त्याचे जीवनचक्र समजून घेणे अत्यंत महत्त्वाचे आहे.

### 5-टप्प्यांचे जीवनचक्र

```
   execute() कॉल केले
        │
        ▼
  ┌─────────────┐
  │  PENDING    │  ← रांगेत, अद्याप सुरू झालेले नाही (DB पंक्ती तयार केली)
  └──────┬──────┘
         │ हँडलर सुरू करा
         ▼
  ┌─────────────┐
  │  RUNNING    │  ← टाइमआउटसह हँडलरचे आवाहन केले
  └──────┬──────┘
         │
    ┌────┴────┬──────────┬──────────┐
    │         │          │          │
    ▼         ▼          ▼          ▼
  SUCCESS   ERROR     TIMEOUT   (अन्य मार्ग नाही — पालक प्रक्रियेद्वारे समाप्त)
    │         │          │
    └────┬────┴──────────┘
         │
         ▼
   स्थिती, आउटपुट, durationMs सह DB पंक्ती अद्ययावत केली
```

### डीफॉल्ट कॉन्फिगरेशन

| सेटिंग       | डीफॉल्ट       | याद्वारे कॉन्फिगर करता येते          |
| ------------ | ------------- | ------------------------------------ |
| `timeout`    | `30000` (30s) | `skillExecutor.setTimeout(ms)`       |
| `maxRetries` | `3`           | `skillExecutor.setMaxRetries(count)` |

> **महत्त्वाचे**: एक्झिक्युटर हा सिंगलटन आहे — `setTimeout()` कॉल केल्याने त्यानंतरच्या सर्व आवाहनांवर जागतिक स्तरावर परिणाम होतो. प्रत्येक स्किलसाठी स्वतंत्र टाइमआउट सध्या समर्थित नाहीत; तुम्हाला प्रत्येक स्किलसाठी वेगवेगळे टाइमआउट आवश्यक असल्यास, स्वतंत्र प्रक्रिया सबमिट करा किंवा एक्झिक्युटरचा फोर्क तयार करा.

### स्थिती मूल्ये

`src/lib/skills/types.ts` मधून:

```ts
enum SkillStatus {
  PENDING = "pending", // रांगेत, अद्याप सुरू झालेले नाही
  RUNNING = "running", // हँडलरचे आवाहन केले
  SUCCESS = "success", // हँडलरने वैध आउटपुट परत केले
  ERROR = "error", // हँडलरने अपवाद फेकला
  TIMEOUT = "timeout", // एक्झिक्युटरचा टाइमआउट ओलांडला
}
```

> **टीप**: `TIMEOUT` स्थिती enum मध्ये परिभाषित केलेली आहे, परंतु सध्याच्या एक्झिक्युटर अंमलबजावणीद्वारे ती **प्रत्यक्षात DB मध्ये लिहिली जात नाही** — टाइमआउट `"Skill execution timed out"` संदेशासह `ERROR` म्हणून दिसतात. स्थिती enum भविष्यातील वापरासाठी राखीव आहे.

### अंमलबजावण्यांची तपासणी

```ts
import { skillExecutor } from "omniroute/skills/executor";

// ID द्वारे विशिष्ट अंमलबजावणी मिळवा
const exec = skillExecutor.getExecution("exec-uuid-123");
if (exec) {
  console.log(`${exec.skillName}: ${exec.status} in ${exec.durationMs}ms`);
}

// API कीसाठी अलीकडील अंमलबजावण्यांची यादी मिळवा
const recent = skillExecutor.listExecutions("api-key-id", 50, 0);
for (const e of recent) {
  console.log(`${e.skillName} → ${e.status} (${e.durationMs}ms)`);
}

// एकूण अंमलबजावण्या मोजा
const total = skillExecutor.countExecutions("api-key-id");
```

### पुनःप्रयत्न वर्तन

`maxRetries` सेटिंग संचयित केली जाते, परंतु एक्झिक्युटरच्या `execute()` पद्धतीद्वारे ती **सध्या वापरली जात नाही** — ती केवळ एकच प्रयत्न करते. `maxRetries` मूल्य भविष्यातील अंमलबजावणीसाठी आणि ते वाचू इच्छिणाऱ्या हुक्ससाठी उपलब्ध केलेले आहे.

सध्या, पुनःप्रयत्नांची अंमलबजावणी स्किल हँडलरमध्येच करणे आवश्यक आहे. अंगभूत
स्किल्सची एक्झिक्युटरकडे नोंदणी केली जाते (उदा. `registerBuiltinSkills(executor)`
/ `registerBrowserSkill(executor)` हे `src/lib/skills/builtin/` मध्ये); तुम्ही नोंदणी
केलेला कोणताही हँडलर स्वतःची पुनःप्रयत्न लूप समाविष्ट करू शकतो:

```ts
// स्किल हँडलरच्या आत
async function handler(input, ctx) {
  const maxRetries = 3;
  let lastError: Error | null = null;

  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      return await fetchSomething(input);
    } catch (err) {
      lastError = err as Error;
      if (attempt < maxRetries) {
        await new Promise((r) => setTimeout(r, 1000 * attempt));
      }
    }
  }
  throw lastError;
}
```

## SkillMode सविस्तर

`SkillMode` enum (`src/lib/skills/types.ts`) कौशल्ये **केव्हा आणि कशी** वापरली जातात हे नियंत्रित करतो:

```ts
enum SkillMode {
  AUTO = "auto", // कौशल्य कधी कॉल करायचे हे LLM ठरवतो
  MANUAL = "manual", // केवळ वापरकर्त्याच्या स्पष्ट विनंतीवरून वापरले जाते
  HYBRID = "hybrid", // AUTO स्कोअरिंग + मॅन्युअल ओव्हरराइड
}
```

> **टीप**: कोडबेसमध्ये `SkillMode` (AUTO/MANUAL/HYBRID) परिभाषित केलेले आहे, तर `Skill.mode` फील्ड वेगळी रचना (`"on" | "off" | "auto"`) वापरते. ते संबंधित आहेत, परंतु एकसारखे नाहीत — `SkillMode` हे एक्झिक्युटर धोरणासाठी आहे, तर `Skill.mode` हे प्रत्येक कौशल्य स्वतंत्रपणे सक्षम करण्यासाठी आहे.

### प्रत्येक मोड कधी वापरावा

| मोड      | LLM चे वर्तन                                                              | वापराचे प्रकरण                                        |
| -------- | ------------------------------------------------------------------------- | ----------------------------------------------------- |
| `AUTO`   | LLM ला आवश्यक वाटल्यास तो कौशल्य कॉल करू शकतो                             | सर्वसाधारण वापराची कौशल्ये (फाइल वाचन, HTTP विनंत्या) |
| `MANUAL` | LLM कौशल्य कॉल करू शकत नाही; केवळ स्पष्ट `executeSkill` API कॉल ते वापरतो | संवेदनशील ऑपरेशन्स (डेटाबेस लेखन, पेमेंट्स)           |
| `HYBRID` | LLM कौशल्य सुचवू शकतो; वापरकर्त्याने पुष्टी करणे आवश्यक आहे               | दुष्परिणाम असलेली, परंतु धोकादायक नसलेली कौशल्ये      |

### AUTO स्कोअरिंग

`AUTO` मोड सक्रिय असताना, प्रत्येक संभाव्य कौशल्याला विनंतीच्या संदर्भाच्या तुलनेत
`src/lib/skills/injection.ts` मधील `scoreAutoSkill()` द्वारे गुण दिले जातात — ही एक बेरीज-आधारित,
पूर्णांक गुण-प्रणाली आहे (कौशल्याच्या नावाची जुळवणी, नाव/टॅग/वर्णनातील टोकनचे साम्य,
पार्श्वभूमी-कारणाचे संकेत, प्रोव्हायडर-संकेत बोनस/दंड). सर्वाधिक गुण असलेली
`AUTO_MAX_SKILLS = 5` कौशल्ये, ज्यांचा `score >= AUTO_MIN_SCORE = 3` आहे, कॉल करता येणारी
साधने म्हणून अंतःक्षेपित केली जातात; समान गुण असल्यास प्रथम `installCount` आणि नंतर नावानुसार क्रम ठरवला जातो. संपूर्ण गुण-तक्ता
या दस्तऐवजात आधी दिलेल्या [**टूल स्कीमा निर्मिती → AUTO स्कोअरिंग**](#auto-scoring) मध्ये
पाहा; येथे फ्लोट `0.6`-सारखी कोणतीही थ्रेशोल्ड नाही आणि `registry.ts` स्कोअरिंगही नाही.

## अंगभूत कौशल्यांची सूची

OmniRoute सोबत `src/lib/skills/builtin/` मध्ये निवडक अंगभूत कौशल्यांचा संच दिला जातो. सर्वाधिक वापरली जाणारी कौशल्ये:

### ब्राउझर ऑटोमेशन कौशल्य

ब्राउझर कौशल्य (`src/lib/skills/builtin/browser.ts`) Playwright/Puppeteer द्वारे हेडलेस ब्राउझर ऑटोमेशन प्रदान करते. **ते अंमलात आणलेले आहे, परंतु डीफॉल्ट कौशल्यांच्या सूचीमध्ये नाही** — ते वापरण्यासाठी ब्राउझर एक्स्टेंशन प्लगइन स्वतंत्रपणे इंस्टॉल करा.

```ts
// तुमच्या कॉन्फिगमध्ये सक्षम करा
const config: SkillConfig = {
  enabled: true,
  mode: SkillMode.MANUAL, // नेहमी स्पष्ट वापराची आवश्यकता ठेवा
  allowedSkills: ["browser"],
  timeout: 60000, // पृष्ठे लोड करण्यासाठी 60 सेकंद
  maxRetries: 1,
};
```

### इतर अंगभूत श्रेणी

| श्रेणी          | कौशल्ये                                             | मोड    |
| --------------- | --------------------------------------------------- | ------ |
| फाइल I/O        | `file_read`, `file_write`                           | AUTO   |
| HTTP            | `http_request`                                      | AUTO   |
| शोध             | `web_search`                                        | AUTO   |
| कोड एक्झिक्युशन | `eval_code` (सँडबॉक्स केलेले JavaScript/Python)     | HYBRID |
| सिस्टीम         | `execute_command` (सँडबॉक्स केलेले CLI एक्झिक्युशन) | MANUAL |

### कस्टम कौशल्य जोडणे

प्लगइन प्रणालीद्वारे कस्टम कौशल्य कसे जोडावे यासाठी [Plugin SDK आणि कौशल्य एकत्रीकरण](./PLUGIN_SDK.md) पहा.
