IDE सत्राशिवाय Cursor ला OmniRoute च्या मागे ठेवण्याचे दोन मार्ग:

1. **`cursor-api` प्रदाता** (कार्ड "Cursor API", उपनाव `cua`): API की
   प्रदाता, जो Cursor वापरकर्त्याची API की (`crsr_…`, येथे व्युत्पन्न केलेली
   `https://cursor.com/dashboard/api`) साठवतो. त्यानंतर कोणताही OmniRoute क्लायंट
   नेहमीच्या कोटा, फॉलबॅक आणि लॉगिंग स्तरांसह `/v1/chat/completions` द्वारे
   `cursor-api/<model>` किंवा `cua/<model>` म्हणून Cursor मॉडेल्स वापरू शकतो. IDE
   प्रदाता (`cursor`, OAuth/IDE सत्र) बदललेला नाही.
2. **Cursor CLI पासथ्रू**: Cursor CLI (`agent`) ला OmniRoute कडे निर्देशित करा,
   जेणेकरून CLI ने केलेला प्रत्येक RPC OmniRoute API कीने प्रमाणित केला जाईल,
   `cursor-api` कनेक्शनच्या क्रेडेन्शियलसह Cursor कडे फॉरवर्ड केला जाईल आणि
   Logs पृष्ठावर नोंदवला जाईल.

## कीची देवाणघेवाण का केली जाते

`api2.cursor.sh` कच्ची `crsr_…` की Bearer टोकन म्हणून नाकारते (401). Cursor
CLI प्रथम की `/auth/exchange_user_api_key` वर POST करते आणि एक तासानंतर कालबाह्य
होणारे सत्र JWT प्राप्त करते; परत आलेल्या `refreshToken` मध्येही तेच
`exp` असते, त्यामुळे रीफ्रेश करणे म्हणजे कीची पुन्हा देवाणघेवाण करणे.
`open-sse/services/cursorApiKeyAuth.ts` ही देवाणघेवाण करते, प्रत्येक कीसाठी एक
सत्र टोकन कॅश करते, कालबाह्य होण्याच्या पाच मिनिटे आधी पुन्हा देवाणघेवाण करते
आणि Cursor कडून 401 उत्तर मिळाल्यास कॅश केलेले टोकन काढून टाकते.
`CursorExecutor`, `cursor-api` कनेक्शनसाठी अपस्ट्रीम स्ट्रीम उघडण्याच्या अगदी
आधी त्याला कॉल करते.

## `cursor-api` प्रदाता

रजिस्ट्री: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"`, `cursor` प्रमाणेच `format`,
`baseUrl` आणि `models`). कॅटलॉग कार्ड:
`src/shared/constants/providers/apikey/specialty-media.ts`. एक्झिक्यूटर मॅप:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`).

डॅशबोर्ड: Providers → Cursor API → Add API key.

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

त्यानंतर:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

टीपा:

- `cursor-api` साठी मॉडेल सूची स्थिर Cursor रजिस्ट्रीमधून येते (IDE प्रदाता
  फॉलबॅक म्हणून वापरतो तीच सूची); OmniRoute होस्टवर `cursor-agent` इंस्टॉल
  करण्याची आवश्यकता नाही.
- `POST /api/providers/{id}/refresh-cursor` हे केवळ `cursor` IDE प्रदात्यासाठी
  आहे; `cursor-api` कनेक्शन्समध्ये नूतनीकरण करण्यासाठी IDE सत्र नसते.

## नेटिव्ह मॉडेल ID आणि प्रयत्न-पातळी

`cursor` / `cu` आणि `cursor-api` / `cua` साठी, सामायिक Claude प्रयत्न-पातळी
नॉर्मलायझर विनंती केलेला मॉडेल ID बदलत नाही. OmniRoute प्रयत्न-पातळी उपनावाऐवजी,
Cursor वास्तविक मॉडेल ID चा भाग म्हणून `-low` सारखा प्रत्यय जाहीर करू शकतो.
Cursor एक्झिक्यूटर अचूक लाइव्ह-कॅटलॉग जुळणी जतन करतो; जुळणी नसल्यास, त्याचा
विद्यमान मॉडेल रिझॉल्वर प्रत्यय-ते-पॅरामीटर फॉलबॅक हाताळतो.

यामुळे थेट Claude, Claude-सुसंगत किंवा Vertex मार्गांसाठी प्रयत्न-पातळी
नॉर्मलायझेशन बदलत नाही. उपलब्धता अद्याप निवडलेल्या Cursor खात्याच्या
कॅटलॉगवर आणि पात्रतेवर अवलंबून असते.

## Cursor CLI पासथ्रू

मार्ग: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`. `/api/cursor-cli/` हा उपसर्ग
`src/shared/constants/publicApiRoutes.ts` मध्ये नोंदणीकृत आहे, कारण हँडलर
स्वतःचे प्रमाणीकरण लागू करतो:

| मार्ग                                                                                                                          | CLI कडून अपेक्षित प्रमाणीकरण | OmniRoute काय करते                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /auth/exchange_user_api_key`                                                                                             | `Bearer <OmniRoute API key>` | कीची पडताळणी करते, 1 तासासाठी वैध असलेला HS256 JWT (`JWT_SECRET` ने स्वाक्षरी केलेला) तयार करते आणि तो परत करते                                                    |
| इतर प्रत्येक मार्ग (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`          | जारीकर्ता/प्रेक्षक/कालबाह्यता पडताळते, सक्रिय `cursor-api` कनेक्शन निवडते, Authorization हेडरमध्ये एक्सचेंज केलेला Cursor टोकन ठेवते आणि प्रतिसाद परत स्ट्रीम करते |

CLI ला मिळालेल्या कोणत्याही टोकनमधून ते `exp` डीकोड करते, त्यामुळे त्याला अपारदर्शक
टोकन दिल्यास ते जवळजवळ प्रत्येक विनंतीपूर्वी पुन्हा एक्सचेंज करते; तयार केलेला JWT
हे टाळतो. OmniRoute कडून 401 मिळाल्यास CLI पुन्हा एक्सचेंज करते.

### सेटअप

1. OmniRoute API की (Dashboard → API keys) आणि `cursor-api`
   कनेक्शन तयार करा.
2. एजंट स्ट्रीमसाठी HTTP/1.1 वापरण्यास CLI ला सांगा.
   `~/.cursor/cli-config.json` मध्ये:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   याशिवाय CLI स्वतंत्रपणे कॉन्फिगर केलेल्या एजंट होस्टशी HTTP/2 द्वारे एजंट टर्न
   सुरू करते आणि केवळ कंट्रोल-प्लेन RPCs एन्डपॉइंटमधून जातात.

3. OmniRoute विरुद्ध CLI चालवा:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

प्रत्येक हॉप Logs मध्ये प्रदाता `cursor-api`, विनंती प्रकार `cursor-cli`,
मार्ग `/api/cursor-cli/<rpc>` म्हणून नोंदवला जातो आणि तो OmniRoute API की व
विनंती हाताळणाऱ्या कनेक्शनला श्रेयांकित केला जातो.

### अपयशाचे प्रकार

| परिस्थिती                                      | CLI ला मिळणारा प्रतिसाद                                 |
| ---------------------------------------------- | ------------------------------------------------------- |
| अज्ञात OmniRoute की आणि `REQUIRE_API_KEY=true` | एक्सचेंजवेळी 401 `unauthenticated`                      |
| `REQUIRE_API_KEY=false`                        | अनामिक सत्र (`/v1/*` वर्तनासारखे)                       |
| कालबाह्य / बाह्य / छेडछाड केलेला सत्र JWT      | 401, CLI पुन्हा एक्सचेंज करते                           |
| एक्सचेंजनंतर OmniRoute API की रद्द केली        | पुढील RPC वर 401                                        |
| सक्रिय `cursor-api` कनेक्शन उपलब्ध नाही        | 503 `unavailable`                                       |
| Cursor ने कनेक्शनची की नाकारली                 | 401 `unauthenticated`, कॅश केलेले सत्र काढून टाकले जाते |
| अपस्ट्रीमशी संपर्क होऊ शकत नाही                | 502 `unavailable` (निर्जंतुक केलेला संदेश)              |
| `JWT_SECRET` सेट केलेले नाही                   | एक्सचेंजवेळी 503                                        |
