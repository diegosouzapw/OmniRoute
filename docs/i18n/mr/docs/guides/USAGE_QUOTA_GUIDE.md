> **TL;DR**: OmniRoute प्रत्येक विनंतीचा टोकन वापर ट्रॅक करते, खर्चाची गणना करते, प्रत्येक API कीसाठी कोटा लागू करते आणि डॅशबोर्डमध्ये विश्लेषण दाखवते. हे सर्व कसे कार्य करते, हे या मार्गदर्शकामध्ये स्पष्ट केले आहे.

**स्रोत:**

- `open-sse/services/usage.ts` (~70KB) — मुख्य वापर ट्रॅकिंग
- `src/lib/usageAnalytics.ts` (~10KB) — डॅशबोर्डसाठी एकत्रीकरण
- `src/lib/db/quotaSnapshots.ts` — ऐतिहासिक कोटा डेटा
- `src/lib/db/usage*.ts` — वापराशी संबंधित अनेक DB मॉड्यूल

---

## आढावा

OmniRoute मधून जाणारी प्रत्येक विनंती एक **वापर नोंद** तयार करते, ज्यामध्ये पुढील माहिती नोंदवली जाते:

- **ओळख**: कोणती API की, प्रदाता, मॉडेल, कॉम्बो
- **टोकन**: प्रॉम्प्ट टोकन, कम्प्लिशन टोकन, कॅश केलेले टोकन, एकूण
- **खर्च**: USD रक्कम (किंमत डेटावरून गणना केलेली)
- **वेळ**: विलंब, सुरुवात/समाप्ती टाइमस्टॅम्प
- **स्थिती**: यशस्वी, त्रुटी, दर-मर्यादित इत्यादी

या नोंदी एकत्रित करून **विश्लेषणे** तयार केली जातात, ती **कोटा स्नॅपशॉट्स** म्हणून कायमस्वरूपी साठवली जातात आणि **प्रत्येक कीसाठी अर्थसंकल्पीय मर्यादा** लागू करण्यासाठी वापरली जातात.

```
विनंती ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    विश्लेषण   कोटा    बिलिंग
                    (डॅशबोर्ड) (अंमलबजावणी) (निर्यात)
```

## काय नोंदवले जाते

`usage.ts` सेवा प्रत्येक विनंतीसाठी एक **वापर घटना** नोंदवते:

| फील्ड              | प्रकार  | स्रोत                                                      |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | नोंदणीवेळी तयार केलेला UUID                                |
| `apiKeyId`         | string  | विनंती सुरू करणारी API की                                  |
| `provider`         | string  | प्रदाता ID (openai, anthropic इत्यादी)                     |
| `model`            | string  | मॉडेल ID (gpt-5, claude-opus-4-6 इत्यादी)                  |
| `comboId`          | string? | कॉम्बोमार्फत रूट केले असल्यास कॉम्बो ID                    |
| `promptTokens`     | number  | अपस्ट्रीम प्रतिसादामधून                                    |
| `completionTokens` | number  | अपस्ट्रीम प्रतिसादामधून                                    |
| `cachedTokens`     | number  | कॅश हिट टोकन (Anthropic प्रॉम्प्ट कॅशिंग इत्यादी)          |
| `totalTokens`      | number  | प्रॉम्प्ट + कम्प्लिशन                                      |
| `costUsd`          | number  | किंमत डेटावरून गणना केलेला                                 |
| `latencyMs`        | number  | विनंतीचा सुरुवातीपासून शेवटपर्यंतचा कालावधी                |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | स्थिती success नसल्यास त्रुटी वर्ग                         |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | प्लगइनद्वारे समाविष्ट केलेला सानुकूल डेटा                  |

### टोकन कुठून येतात

**प्रतिसाद हँडलर**मध्ये अपस्ट्रीम प्रदात्याच्या प्रतिसादामधून टोकन काढली जातात:

```ts
// open-sse/handlers/chatCore.ts मधून
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

वापराची माहिती न देणाऱ्या प्रदात्यांसाठी (काही वेब-कुकी प्रदाते), OmniRoute `~4 chars per token` या अनुमानपद्धतीचा वापर करून टोकनचा **अंदाज** लावते (`open-sse/services/autoCombo/pipelineRouter.ts` पहा).

### कॅश केलेली टोकन

OmniRoute `cached_tokens` चा मागोवा `prompt_tokens` पासून स्वतंत्रपणे ठेवते, कारण:

- Anthropic प्रॉम्प्ट कॅशिंगमध्ये कॅश केलेल्या टोकनसाठी कमी दर आकारला जातो (सामान्य दराच्या 10%)
- काही प्रदाते `cache_read_input_tokens` परत करतात, ज्यांची किंमत वेगळ्या प्रकारे मोजली पाहिजे
- विश्लेषणामध्ये **कॅश हिट दर** = `cached_tokens / prompt_tokens` दाखवता येतो

## खर्चाची गणना

खर्चाची गणना LiteLLM वरून समक्रमित केलेल्या **किंमत डेटावरून** (`src/lib/pricingSync.ts`) केली जाते:

| मॉडेल             | इनपुट $/1M | आउटपुट $/1M | कॅश केलेले $/1M |
| ----------------- | ---------- | ----------- | --------------- |
| gpt-5             | $2.50      | $10.00      | —               |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50           |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30           |
| gemini-2.5-pro    | $1.25      | $10.00      | —               |

खर्चाचे सूत्र (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **प्रॉम्प्टमधून कॅश केलेले टोकन वजा का करायचे?** कॅश केलेल्या भागाची किंमत स्वतंत्रपणे मोजली जाते; संपूर्ण प्रॉम्प्टवर इनपुटची किंमत आकारल्यास खर्च जास्त मोजला जाईल.

### किंमत समक्रमण

`/api/pricing/sync` एंडपॉइंटद्वारे LiteLLM वरून किंमत डेटा स्वयंचलितपणे समक्रमित केला जातो (अंगभूत cron कार्याद्वारे ट्रिगर केला जातो, वापरकर्त्यांसाठी असलेल्या env var द्वारे नाही):

```bash
# स्वहस्ते ट्रिगर करा
curl -X POST http://localhost:20128/api/pricing/sync
```

ज्या मॉडेलसाठी किंमत डेटा उपलब्ध नाही, त्यांच्यासाठी OmniRoute अंतर्गत सरासरी दर वापरून **खर्चाचा अंदाज** लावते (हे दर LiteLLM च्या किंमत डेटावरून घेतलेले असतात).

## दिनांक श्रेणी एकत्रीकरण

`usageAnalytics.ts` मॉड्यूल कच्च्या वापर डेटावरून डॅशबोर्ड विजेटची गणना करते. ते 7 कालावधी श्रेणींना समर्थन देते:

| श्रेणी   | कालखंड                                         | उपयोग                          |
| -------- | ---------------------------------------------- | ------------------------------ |
| `1d`     | मागील 24 तास                                   | तासानुसार खर्चवाढ शोधणे        |
| `7d`     | मागील 7 दिवस                                   | साप्ताहिक आढावा                |
| `30d`    | मागील 30 दिवस                                  | मासिक बिलिंग                   |
| `90d`    | मागील 90 दिवस                                  | तिमाही विश्लेषण                |
| `ytd`    | चालू वर्षाच्या 1 जानेवारीपासून                 | वार्षिक बजेटचा मागोवा          |
| `all`    | सुरुवातीपासूनचा संपूर्ण कालावधी                | आजीवन आकडेवारी                 |
| `custom` | वापरकर्त्याने निर्धारित केलेली सुरुवात/समाप्ती | लेखापरीक्षणे, तात्कालिक क्वेरी |

### गणना केली जाणारी डॅशबोर्ड विजेट

कोणत्याही दिनांक श्रेणीसाठी, विश्लेषण स्तर पुढील बाबींची गणना करतो:

| विजेट                      | वर्णन                                                               |
| -------------------------- | ------------------------------------------------------------------- |
| **सारांश कार्ड**           | एकूण विनंत्या, एकूण खर्च, एकूण टोकन, यशाचा दर                       |
| **दैनंदिन कल आलेख**        | प्रत्येक दिवसाचा खर्च + टोकन, मॉडेलनुसार स्तरित                     |
| **क्रियाकलाप हीटमॅप**      | दिवसातील तास × आठवड्यातील दिवस यांची जाळी, रंग = विनंत्यांची संख्या |
| **मॉडेलनुसार विभागणी**     | मॉडेलनुसार खर्चाचा पाय चार्ट                                        |
| **प्रदात्यानुसार विभागणी** | प्रदात्यानुसार विनंत्यांचा बार चार्ट                                |
| **शीर्ष API की**           | खर्चानुसार शीर्ष 10 कींचे तक्ते                                     |
| **त्रुटी विश्लेषण**        | कालानुसार त्रुटी दर, शीर्ष त्रुटी वर्ग                              |

### प्रोग्रामद्वारे प्रवेश

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // वापर इतिहासाच्या नोंदी
  "7d",                 // कालावधी श्रेणी: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // प्रदाता कनेक्शन मॅप (connectionId → खात्याचे नाव)
  {
    startDate: "2025-01-01",  // पर्यायी: "custom" श्रेणीसाठी
    endDate: "2025-06-01",   // पर्यायी: "custom" श्रेणीसाठी
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (सेंट)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## कोटा अंमलबजावणी

प्रत्येक API कीसाठीचा कोटा दोन ठिकाणी लागू केला जातो:

1. **सौम्य मर्यादा** (`quotaWarnAt`): वापराने मर्यादा ओलांडल्यावर डॅशबोर्डवरील चेतावणी
2. **कठोर मर्यादा** (`quotaLimit`): मर्यादा ओलांडल्यावर विनंती HTTP 429 सह नाकारली जाते

### कॉन्फिगरेशन

```ts
// प्रत्येक API कीसाठी
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — चेतावणी दाखवा
  quotaLimit: 10_00,    // $10.00 — पूर्णपणे थांबवा
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### अंमलबजावणी प्रवाह

```
विनंती ──▶ quotaCheck()
              │
              ├── मर्यादेत आहे?  ──▶ अनुमती द्या
              │
              └── मर्यादेपेक्षा जास्त?  ──▶ 429 खूप जास्त विनंत्या
                                   Retry-After हेडरसह
```

### कोटा स्नॅपशॉट्स

`quotaSnapshots` तक्ता प्रवाह विश्लेषणासाठी **ऐतिहासिक कोटा स्थिती** संग्रहित करतो:

| फील्ड | वर्णन |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | ट्रॅक केली जात असलेली की |
| `window` | "day" | "week" | "month" |
| `used` | या कालखंडात वापरलेला खर्च (सेंटमध्ये) |
| `limit` | मर्यादा (सेंटमध्ये) |
| `resetAt` | कालखंड रीसेट होण्याची वेळ |
| `createdAt` | स्नॅपशॉट घेतल्याची वेळ |

> 0 खर्च असलेल्या **प्रत्येक विनंतीवर** स्नॅपशॉट घेतले जातात आणि त्यांचा वापर पुढील गोष्टींसाठी केला जातो:

- डॅशबोर्डमध्ये कोटा प्रगती पट्टी रेंडर करणे
- 30-दिवसांच्या कोटा प्रवाहाचे चार्ट दाखवणे
- वापर मर्यादेच्या जवळ आल्यावर सूचना ट्रिगर करणे

### वापर विश्लेषणाची क्वेरी करा

वापर डेटा थेट REST निर्यात एंडपॉइंट्सऐवजी डॅशबोर्ड किंवा MCP साधनांद्वारे अॅक्सेस केला जातो. उपलब्ध विश्लेषणे:

- **`/api/usage/analytics`** — एकत्रित वापर मेट्रिक्स (मॉडेल, प्रदाता, कीनुसार गटबद्ध)
- **`/api/usage/quota`** — प्रत्येक API कीची वर्तमान कोटा स्थिती
- **`/api/usage/history`** — विनंती इतिहास लॉग्स

## धारणा आणि स्वच्छता

वापराचा डेटा प्रत्येक विनंतीमागे ~1-10KB ने वाढतो. मोठ्या प्रमाणावर, हे लक्षणीय ठरू शकते.

### धारणा सेटिंग्ज

वापर इतिहासाची धारणा UI मधील Database Settings द्वारे किंवा `/api/settings/database` द्वारे कॉन्फिगर केली जाते.

डीफॉल्टनुसार, वापर इतिहास **90 दिवस** राखून ठेवला जातो.

### स्वच्छता

जुन्या नोंदी `src/lib/db/cleanup.ts` द्वारे साफ केल्या जातात:

- पार्श्वभूमीतील cron प्रक्रियेद्वारे सुरू केले जाते
- कॉन्फिगर केलेल्या `usageHistory` धारणा सेटिंगपेक्षा जुन्या `usage_history` मधील नोंदी हटवल्या जातात

### स्टोरेजचा अंदाज

| विनंती दर             | 30-दिवसांचे स्टोरेज | 90-दिवसांचे स्टोरेज |
| --------------------- | ------------------- | ------------------- |
| 100 विनंत्या/दिवस     | ~3MB                | ~9MB                |
| 1,000 विनंत्या/दिवस   | ~30MB               | ~90MB               |
| 10,000 विनंत्या/दिवस  | ~300MB              | ~900MB              |
| 100,000 विनंत्या/दिवस | ~3GB                | ~9GB                |

अतिशय जास्त ट्रॅफिकसाठी, पुढील बाबींचा विचार करा:

- Database Settings द्वारे धारणा कालावधी कमी करणे
- कच्च्या नोंदींऐवजी `aggregated_metrics` वापरणे (केवळ विश्लेषणासाठी)

## खर्च अनुकूलन टिपा

### 1. योग्य मॉडेल वापरा

```bash
# झटपट उत्तर — स्वस्त + जलद वापरा
curl -d '{"model":"auto/fast","messages":[...]}'

# गुंतागुंतीचे कार्य — गुणवत्तेला प्राधान्य द्या
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. कॅशिंग सक्षम करा

Anthropic prompt caching वारंवार वापरल्या जाणाऱ्या संदर्भावर **90% बचत करते**:

```ts
// कॅशिंग स्वयंचलित आहे — फक्त तोच मोठा system prompt समाविष्ट करा
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // स्वयंचलितपणे कॅश केले जाईल
  messages: [{ role: "user", content: "..." }],
});
```

### 3. कॉम्प्रेशन वापरा

RTK + Caveman compression हे टूल्सचा मोठ्या प्रमाणावर वापर असलेल्या सत्रांमध्ये **15-95% बचत करते**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. प्रत्येक कीसाठी कोटा सेट करा

अनियंत्रित खर्च टाळण्यासाठी नेहमी `quotaLimit` सेट करा:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // $10/महिना मर्यादा
```

### 5. सर्वाधिक वापर करणाऱ्यांचे ऑडिट करा

API कीनुसार गटबद्ध करण्यासाठी आणि खर्चानुसार क्रमवारी लावण्यासाठी डॅशबोर्ड किंवा **`/api/usage/analytics`** वापरा:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## समस्या निवारण

### "खर्च अपेक्षेपेक्षा जास्त आहे"

1. **`/api/usage/analytics?groupBy=model`** तपासा — महाग मॉडेल शोधा
2. **`/api/usage/analytics?groupBy=apiKey`** तपासा — जास्त वापर करणारा ग्राहक शोधा
3. किंमत डेटा अद्ययावत असल्याची खात्री करा: `POST /api/pricing/sync`

### "नोंदी उपलब्ध नाहीत"

- Dashboard → Database → Cleanup अंतर्गत DB धारणा सेटिंग्ज तपासा — जुन्या नोंदी नियतकालिक स्वच्छता कार्याद्वारे (`src/lib/db/cleanup.ts`) हटवल्या जातात
- `src/lib/db/usage*.ts` मधील त्रुटी तपासा — DB लेखनातील अपयशांची नोंद केली जाते, परंतु ती प्रदर्शित केली जात नाहीत
- विनंती प्रत्यक्षात `chatCore` पर्यंत पोहोचली असल्याची खात्री करा — combo routing तपासा

### "कोटा लागू होत नाही"

- कीचे `quotaLimit` सेटिंग तपासा
- `quotaWindow` योग्यरित्या सेट केले असल्याची खात्री करा
- `quotaSnapshots` नोंदी शोधा — त्या प्रत्येक विनंतीवर तयार केल्या गेल्या पाहिजेत
