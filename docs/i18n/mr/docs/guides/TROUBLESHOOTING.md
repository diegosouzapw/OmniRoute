## त्वरित संदर्भ

**OmniRoute पहिल्यांदाच वापरत आहात?** येथून सुरुवात करा — यामुळे 90% समस्या सुटतात:

| मला हे दिसते                 | याचा अर्थ काय आहे                              | काय करावे                                                                                                      |
| ---------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| "कनेक्ट करता येत नाही"       | OmniRoute सुरू नाही                            | `omniroute` चालवा किंवा `docker restart omniroute` चालवा                                                       |
| "अवैध API की"                | तुमची की चुकीची आहे किंवा कालबाह्य झाली आहे    | प्रदात्याच्या वेबसाइटवरून की पुन्हा कॉपी करा                                                                   |
| "दरमर्यादा ओलांडली"          | तुम्ही खूप जास्त विनंत्या पाठवत आहात           | 1 मिनिट थांबा किंवा स्वयंचलित फॉलबॅकसाठी `model: "auto"` वापरा                                                 |
| "कोटा ओलांडला"               | तुम्ही तुमचा मोफत/सशुल्क कोटा पूर्ण वापरला आहे | अधिक प्रदाते कनेक्ट करा किंवा मोफत प्रदाते (Kiro, Pollinations) वापरा                                          |
| "प्रतिसाद धीमे आहेत"         | प्रदाता व्यस्त आहे किंवा दूर आहे               | `model: "auto/fast"` वापरा किंवा अधिक वेगवान प्रदाता (Groq, Cerebras) कनेक्ट करा                               |
| "चुकीचा प्रदाता वापरला गेला" | `auto` ने वेगळा प्रदाता निवडला                 | हे सामान्य आहे! `auto` सर्वोत्तम प्रदाता निवडतो. `model: "openai/gpt-4o"` वापरून विशिष्ट प्रदाता सक्तीने निवडा |
| "502 Bad Gateway"            | प्रदाता बंद आहे                                | थांबून पुन्हा प्रयत्न करा किंवा प्रदाता बदलण्यासाठी `model: "auto"` वापरा                                      |
| "401 Unauthorized"           | तुमची प्रमाणीकरण माहिती चुकीची आहे             | तुमची API की तपासा किंवा OAuth वापरून पुन्हा प्रमाणीकरण करा                                                    |
| "omniroute ओळखले जात नाही"   | Windows PATH मध्ये जागतिक node मॉड्यूल्स नाहीत | तुमचा npm जागतिक प्रीफिक्स Windows PATH मध्ये जोडा. तो शोधण्यासाठी `npm config get prefix` वापरा.              |
| "429 Too Many Requests"      | दरमर्यादा लागू झाली आहे                        | 1 मिनिट थांबा किंवा अधिक प्रदाते कनेक्ट करा                                                                    |

## तपशीलवार समस्या निवारण

---

### मोफत प्रदात्यांवरील दरमर्यादा (429 / 400 / 401)

**लक्षण**: मोफत/प्रमाणीकरणाची आवश्यकता नसलेल्या प्रदात्यांसह (opencode, auggie इ.) `model: "auto"` वापरताना, काही वेळा उत्तरांऐवजी `HTTP 429`, `400` किंवा `401` मिळते. काही क्षणांनंतर त्याच प्रॉम्प्टचा पुन्हा प्रयत्न केल्यास विनंत्या यशस्वी होतात, परंतु स्वयंचलन (cron जॉब्स, एजंट्स, स्क्रिप्ट्स) पहिल्याच अपयशावर खंडित होते.

**मूळ कारण**: तीन स्वतंत्र अपयश-प्रकार एकत्रित होतात:

1. **प्रदात्याची दरमर्यादा (`429`)**: मोफत स्तर प्रत्येक कालखंडासाठी कोटा लागू करू शकतात. समांतर कॉल्सच्या अचानक वाढीमुळे तो संपतो, त्यामुळे कालखंड रीसेट होईपर्यंत पुढील विनंती नाकारली जाते.
2. **पासथ्रूमधील सदोष मॉडेल (`400`/`401`)**: `auto/*` पूलमध्ये `opencode` कडील अशी पासथ्रू मॉडेल्स असू शकतात जी कॅटलॉगमध्ये नोंदणीकृत आहेत, परंतु त्यांच्याकडे सक्रिय क्रेडेन्शियल्स नाहीत (उदा. `oc/north-mini-code-free` → `401`). ऑटो-राउटर त्यापैकी एक वापरून पाहतो, तो प्रयत्न अयशस्वी होतो आणि फॉलबॅक सुरू होण्यापूर्वीच त्रुटी प्रसारित होते.
3. **समवर्तीपणामुळे होणारी वाढ (`429` भाराखाली)**: एकाधिक एजंट/cron सत्रे एकाच वेळी `auto` वापरतात, तेव्हा एकत्रित विनंती-दर मोफत प्रदाते सहन करू शकतील त्यापेक्षा जास्त होतो, त्यामुळे वैध कॉल्सनादेखील गैरवापर म्हणून चिन्हांकित केले जाते.

**सत्यापित उपाय (समुदायाने नोंदवलेला, 2026-08-10)**: तीन पर्यावरणीय चल अशा प्रकारे समायोजित करा की रोटेशन, समवर्तीपणा आणि फॉलबॅक मोफत स्तरावरील चढ-उतारांमुळे बंद पडण्याऐवजी ते हाताळतील:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 आल्यास दुसऱ्या मॉडेल/प्रदात्याकडे जा (सदोष पासथ्रू मॉडेल्स वगळते)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # हेवीवेट प्रवेशाची स्पष्ट कमाल मर्यादा (डीफॉल्टनुसार सेट नसते: विनंती-संख्येवर मर्यादा नाही, खालील टीप पहा)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # तत्काळ पुन्हा प्रयत्न करण्यायोग्य 503 देण्याऐवजी हेवीवेट क्षमतेसाठी अधिक काळ मर्यादित प्रतीक्षा
```

ही चल OmniRoute प्रक्रियेच्या पर्यावरणात (डिमनमध्ये, उदा. LaunchAgent plist किंवा `systemctl edit` द्वारे) सेट करा, त्यानंतर OmniRoute रीस्टार्ट करा. रोटेशन फ्लॅगचा प्रभाव सर्वाधिक आहे: तो पूलमधील कार्यरत प्रदात्याकडे पारदर्शकपणे पुन्हा प्रयत्न करून गंभीर अपयशाचे रूपांतर यशस्वी प्रक्रियेत करतो.

**टीप**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` एकाच वेळी किती हेवीवेट — दीर्घ-कॉन्टेक्स्ट — विनंत्या चालतील यावर मर्यादा घालतो; ही मर्यादा प्रवेशद्वार आहे, प्रदात्याची दरमर्यादा नाही. **#503-fanout अद्यतन:** हे चल आता डीफॉल्टनुसार सेट केले जात नाही (वरीलप्रमाणे स्पष्टपणे कॉन्फिगर केल्यावरच ते आता लागू होते) — त्याऐवजी हेवीवेट प्रवेश स्वयंचलितपणे निर्धारित केलेल्या बाइट बजेटद्वारे (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) नियंत्रित केला जातो, जे होस्टच्या वास्तविक मेमरी मर्यादेनुसार स्वतःचे प्रमाण बदलते. त्यामुळे कोणतेही चल सेट न करता नवीन डिप्लॉयमेंटमध्ये `503 chat_admission_busy` नकार खूप कमी दिसायला हवेत; तरीही येथे ते स्पष्टपणे सेट केल्यास दस्तऐवजीकरणात नमूद केल्याप्रमाणेच ते कार्य करते. स्पष्ट बाइट-बजेट ओव्हरराइड्स 8 MiB–2 GiB पर्यंत मर्यादित केले जातात. `413 body_exceeds_budget` ही तात्पुरती स्थिती नाही: ते बाइट बजेट वाढवा, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` कमी करा किंवा प्रक्रियेची मेमरी मर्यादा वाढवा. `inflight_bytes_budget` शेड ही तात्पुरती संसाधन स्पर्धा आहे आणि तिच्यासाठी पुन्हा प्रयत्न करता येतो. प्रत्येक प्रदात्यासाठीची दरमर्यादा (`open-sse/services/rateLimitManager.ts`) स्वतंत्रपणे `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` आणि `RATE_LIMIT_AUTO_ENABLE` द्वारे नियंत्रित केली जाते — `.env.example` पहा.

**ते कार्यरत असल्याची पडताळणी कशी करावी**: तुमचा एजंट/cron सलग दोनदा त्वरित चालवा आणि दोन्ही वेळा ते यशस्वी होत असल्याची खात्री करा. सुधारणा करण्यापूर्वी, दुसऱ्या रनमध्ये सहसा `429`/`401` त्रुटी येते. सुधारणा केल्यानंतर, अपयशी प्रयत्न (असल्यास) पारदर्शकपणे पुन्हा केले जातात आणि कॉल पूर्ण होतो. तुम्ही `curl /monitoring/health` देखील चालवू शकता आणि प्रोव्हायडर कनेक्शन्सवरील `rateLimitedUntil` फील्ड तसेच प्रभावित प्रोव्हायडर्ससाठी `circuitBreakers.providerBreakers[].state` पाहू शकता — स्थिती `CLOSED`, `DEGRADED`, `OPEN`, किंवा `HALF_OPEN` यांपैकी एक असते (`src/shared/utils/circuitBreaker.ts` पहा), आणि सतत अपयशी ठरणारा प्रोव्हायडर रीसेट विंडोमधून प्रोबला जाऊ देण्यापूर्वी `CLOSED → DEGRADED → OPEN` अशा स्थितीत बदलेल (`HALF_OPEN`).

**तुम्हाला अजूनही 429 दिसत असल्यास**: त्या प्रोव्हायडरसाठी सक्रिय खात्याचा _कोटा_ खरोखरच संपला आहे (केवळ रेट मर्यादा गाठलेली नाही). OmniRoute डॅशबोर्डमध्ये → Providers → Accounts येथे त्याच प्रोव्हायडरसाठी दुसरे खाते जोडा किंवा आणखी एखादा मोफत प्रोव्हायडर वापरा (उदा. `routeway`, `auggie`). रोटेशन केवळ तात्पुरत्या रेट/400/401 समस्यांसाठी उपयुक्त ठरते; कोटा पूर्णपणे संपल्यास दुसरे क्रेडेन्शियल किंवा वेगळा प्रोव्हायडर आवश्यक असतो.

**व्हिजन मॉडेल्सवर (`auto/vision`, `bazaarlink/*`) 403 दिसत असल्यास**: कनेक्ट केलेल्या खात्याकडे व्हिजनचा समावेश असलेला सशुल्क प्लॅन नाही किंवा API कीकडे पुरेशा परवानग्या नाहीत. प्रोव्हायडर डॅशबोर्डमध्ये कीच्या स्कोपमध्ये व्हिजन/मल्टिमोडलचा समावेश असल्याची पडताळणी करा किंवा सशुल्क स्तराचे खाते कनेक्ट करून ते व्हिजन टार्गेट म्हणून कायम ठेवा.

## npm install चेतावण्या (ERESOLVE / peer / deprecated)

तुम्ही `npm install -g omniroute` चालवता तेव्हा तुम्हाला `npm warn ERESOLVE`, peer-dependency सूचना आणि `deprecated` संदेश अशा अनेक चेतावण्या दिसू शकतात. **या अपेक्षित आणि निरुपद्रवी आहेत.** आउटपुटमध्ये `added <N> packages` दिसल्यास तुमचे इंस्टॉलेशन यशस्वी झाले आहे.

peer-dependency निराकरणासंबंधीच्या चेतावण्या दडपण्यासाठी OmniRoute चे समर्थित इंस्टॉलेशन स्वरूप वापरा:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` केवळ `ERESOLVE` आणि peer-dependency सूचना दडपते. Deprecation सूचना दिसत राहतात, कारण त्या अप्रत्यक्ष तृतीय-पक्ष पॅकेजमधून येतात; त्या इंस्टॉलेशन अयशस्वी झाल्याचे दर्शवत नाहीत.

या चेतावण्या OmniRoute च्या नियंत्रणात नसलेल्या तृतीय-पक्ष पॅकेजमधील कालबाह्य peer-dependency श्रेणींमुळे येतात:

1. **`marked-terminal` ला `marked >=1 <16` हवे आहे, परंतु `marked@18` आढळले** — प्रत्यक्ष वापरात ते व्यवस्थित कार्य करते; upstream peer श्रेणी फक्त कालबाह्य आहे.
2. **`deprecated prebuild-install@7.1.3`** — हा अप्रत्यक्ष native-binary डाउनलोड सहाय्यक आहे. तो पिन केलेले `wreq-js` transport binding इंस्टॉल करण्यासाठी
   वापरला जात नाही आणि web-cookie
   provider transport सेटअप अयशस्वी झाल्याचे दर्शवत नाही.

**कोणतीही कृती आवश्यक नाही** — upstream पॅकेजचे fork तयार केल्याशिवाय या चेतावण्या पूर्णपणे बंद करता येत नाहीत.

## Gemini Web आणि Playwright Chromium

Gemini Web विनंतीने Playwright Chromium
इंस्टॉल नसल्याचा संदेश असलेला `503` प्रतिसाद दिल्यास, npm पॅकेज उपलब्ध आहे पण browser binary उपलब्ध नाही.
Playwright मुद्दाम browser डाउनलोड npm पॅकेज
इंस्टॉलेशनपासून वेगळे ठेवते, त्यामुळे browser इंस्टॉल होईपर्यंत हा प्रतिसाद अपेक्षित आहे.

global npm इंस्टॉलेशनसाठी, OmniRoute पॅकेजच्या
डिरेक्टरीमधून Chromium इंस्टॉल करा, जेणेकरून browser cache त्याच Playwright इंस्टॉलेशनशी संबंधित राहील:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

इंस्टॉलेशननंतर OmniRoute रीस्टार्ट करा आणि त्यानंतर Gemini Web विनंती पुन्हा वापरून पाहा. तुम्ही
Docker image मधून OmniRoute चालवत असल्यास, Chromium आणि त्याची dependencies समाविष्ट असलेली `-web` image (किंवा `runner-web`
build target) वापरा; base image मध्ये त्या
समाविष्ट नसतात.

## अँटीव्हायरसचे चुकीचे सकारात्मक निष्कर्ष

<a name="antivirus-false-positives"></a>

### Avast/AVG कडून `README.md` हे `MD:HttpRequest-inf[Susp]` म्हणून क्वारंटाइन केले जाते

**हा चुकीचा सकारात्मक निष्कर्ष आहे. कशालाही संसर्ग झालेला नाही आणि कोणतीही कारवाई आवश्यक नाही.**

Avast आणि AVG अशा साध्या मजकूर/Markdown फाइल्सना ध्वजांकित करणारी ह्युरिस्टिक चालवतात, ज्यांमध्ये
HTTP विनंत्यांसारख्या दिसणाऱ्या अनेक लिंक्स असतात. OmniRoute चे `README.md` npm पॅकेजमध्ये समाविष्ट असते (ते
`package.json` → `files` मध्ये सूचीबद्ध आहे), त्यामुळे ग्लोबल इन्स्टॉल केल्यावर ते
`node_modules/omniroute/README.md` येथे येते — आणि त्यात सुमारे 15 `http://localhost:20128/...`
उदाहरणे आहेत (MCP HTTP/SSE एंडपॉइंट्स, A2A `.well-known` URL आणि `curl` स्निपेट्स). लिंक्सची ही घनता
ह्युरिस्टिक सक्रिय होण्यासाठी पुरेशी आहे.

हे अगदी अलीकडेच सुरू झाले असल्यास: फाइलच्या स्वरूपात बदल झालेला नाही. README मधील
एंडपॉइंट्सचे टेबल वाढले (MCP HTTP + SSE + A2A जोडले गेले) आणि अधिक `curl` उदाहरणे समाविष्ट झाली,
ज्यामुळे ते मर्यादेपलीकडे गेले.

ही शून्य एक्झिक्युटेबल सामग्री असलेली निष्क्रिय दस्तऐवजीकरण फाइल आहे. तुम्ही ती क्वारंटाइनमधून
सुरक्षितपणे पुनर्स्थापित करू शकता.

**काय करावे:**

1. **सूचना थांबवा** — तुमच्या अँटीव्हायरसमध्ये इन्स्टॉलेशन डायरेक्टरी वगळा
   (Avast: Settings → Exceptions), त्यात तुमचा ग्लोबल `node_modules` पाथ आणि/किंवा
   OmniRoute डेटा डायरेक्टरी (`~/.omniroute/`) जोडा.
2. **चुकीचा सकारात्मक निष्कर्ष नोंदवा** — <https://www.avast.com/false-positive-file-form.php>,
   आणि क्वारंटाइन केलेली `README.md` संलग्न करा. यामुळे सर्वांना मदत होईल, कारण विक्रेत्याची
   ह्युरिस्टिक एका मजकूर फाइलवर अतिरेकी प्रतिक्रिया देत आहे.

**आम्ही आमच्या बाजूने हे "दुरुस्त" का करत नाही:** सर्व उदाहरणे `http://localhost` आहेत आणि
स्व-स्वाक्षरी केलेल्या प्रमाणपत्रांचा त्रास स्वीकारल्याशिवाय localhost हे `https` असू शकत नाही.
एका विक्रेत्याची ह्युरिस्टिक चुकवण्यासाठी दस्तऐवजीकरण विद्रूप केल्यास स्कॅनरमधील बगचे समाधान करताना
प्रत्येक वाचकाला त्रास होईल.

### Kaspersky कडून Desktop अॅपला `PDM:Trojan.Win32.Generic` म्हणून ध्वजांकित केले जाते

**हा वर्तनाधारित ह्युरिस्टिकमधून आलेला चुकीचा सकारात्मक निष्कर्ष आहे. कशालाही संसर्ग झालेला नाही.**
Kaspersky मधील `PDM:` उपसर्गाचा अर्थ हा निष्कर्ष त्याच्या Proactive Defense Module (System Watcher)
मधून आला आहे, जे इंस्टॉलरची ज्ञात मालवेअरशी जुळवणी करण्याऐवजी तो _काय करतो_ याचे मूल्यमापन करते.
ते सक्रिय झाल्यावर Kaspersky संपूर्ण इन्स्टॉलेशन "रोल बॅक" करते — आधीच लिहिलेल्या फाइल्स हटवते —
त्यामुळे अॅप बिघडते किंवा गायब होते.

ते ज्या फाइल्सना ध्वजांकित करते त्या Desktop अॅपसोबत बंडल केलेल्या घोषित, मुक्त-स्रोत
डिपेंडन्सीजचे प्रमाणित भाग आहेत, उदाहरणार्थ:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` आणि
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), अॅपमधील प्रोव्हायडर लॉगिन आणि
  ब्राउझर-आधारित चॅटसाठी वापरली जाणारी ब्राउझर-ऑटोमेशन लायब्ररी.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — वेब-कुकी प्रोव्हायडर्सवरील ब्राउझर-फिंगरप्रिंटेड HTTP साठी वापरली जाणारी पिन केलेली `wreq-js`
  नेटिव्ह बाइंडिंग (`<arch>` हे `x64` किंवा `arm64` असते).

**ते सक्रिय का होते:** Windows इंस्टॉलरवर **अद्याप कोड-स्वाक्षरी केलेली नाही**, त्यामुळे
स्वाक्षरी नसलेल्या NSIS इंस्टॉलरची प्रतिष्ठा शून्य असते आणि वर्तनाधारित ह्युरिस्टिक्स कमाल
आक्रमकतेने चालतात. त्यासोबत बंडल केलेली नेटिव्ह DLL आणि `%LOCALAPPDATA%\Programs\OmniRoute`
अंतर्गत लिहिलेल्या शेकडो `.js` फाइल्स (Next.js स्टँडअलोन बिल्डमधील हॅश-प्रत्यय असलेल्या पॅकेज
डायरेक्टरीजसह) यांचा संयोग ह्युरिस्टिक सक्रिय करण्यासाठी पुरेसा आहे. कोड स्वाक्षरी नियोजित आहे;
ती उपलब्ध होईपर्यंत नवीन रिलीझमध्ये हे पुन्हा घडू शकते.

**काय करावे:**

1. **प्रथम तुमच्या डाउनलोडची पडताळणी करा** (यामुळे फाइलमध्ये छेडछाड झाल्याची शक्यता वगळली जाते).
   प्रत्येक रिलीझमध्ये `latest.yml` प्रकाशित केले जाते, ज्यातील `sha512` फील्ड (base64)
   `OmniRoute.Setup.<version>.exe` इंस्टॉलरशी संबंधित असते. PowerShell मध्ये, इंस्टॉलर असलेल्या
   फोल्डरमधून:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   आउटपुट `latest.yml` → `sha512` शी जुळले पाहिजे. ते जुळत नसल्यास, फाइल हटवा आणि केवळ
   [GitHub रिलीझ पृष्ठावरून](https://github.com/diegosouzapw/OmniRoute/releases) पुन्हा डाउनलोड करा.
2. **पुनर्स्थापित करा + वगळा** — रोल बॅक केलेले घटक क्वारंटाइनमधून पुनर्स्थापित करा आणि
   `%LOCALAPPDATA%\Programs\OmniRoute` साठी अपवाद जोडा (Kaspersky → Settings → Threats and Exclusions),
   त्यानंतर पुन्हा इन्स्टॉल करा.
3. **चुकीचा सकारात्मक निष्कर्ष नोंदवा** — <https://opentip.kaspersky.com/>. वापरकर्त्यांनी सादर केलेले
   FP अहवाल खरोखरच अनुमत-सूचीत समावेश करण्याची प्रक्रिया वेगवान करतात.

## Node.js सुसंगतता

<a name="nodejs-compatibility"></a>

### लॉगिन पृष्ठ क्रॅश होते किंवा "Module self-registration" त्रुटी दाखवते

**कारण:** तुम्ही OmniRoute ने मंजूर केलेल्या सुरक्षित रनटाइमच्या किमान मर्यादेबाहेरील Node.js आवृत्ती चालवत आहात. सर्वात सामान्य प्रकरण म्हणजे OmniRoute ला आवश्यक असलेल्या पॅच केलेल्या सुरक्षा मर्यादेपेक्षा जुनी Node 22 किंवा 24 पॅच आवृत्ती चालवणे.

**लक्षणे:**

- लॉगिन पृष्ठावर रिकामी स्क्रीन किंवा सर्व्हर त्रुटी दिसते
- कन्सोलमध्ये `Error: Module did not self-register` किंवा तत्सम नेटिव्ह बाइंडिंग त्रुटी दिसतात
- रनटाइम समर्थित सुरक्षितता धोरणाच्या बाहेर असल्यास लॉगिन पृष्ठावर तुमच्या Node आवृत्तीसह **नारिंगी चेतावणी बॅनर** दिसतो

**उपाय:**

1. समर्थित Node.js LTS रिलीज इन्स्टॉल करा (शिफारस: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. तुमची आवृत्ती सत्यापित करा: `node --version` ने 24.x LTS मालिकेवरील `v24.0.0` किंवा त्यापेक्षा नवीन आवृत्ती दाखवली पाहिजे
3. OmniRoute पुन्हा इन्स्टॉल करा: `npm install -g omniroute`
4. रीस्टार्ट करा: `omniroute`

> **समर्थित सुरक्षित आवृत्त्या:** `>=22.22.2 <23` किंवा `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) आणि Node.js 26 पूर्णपणे समर्थित आहेत.

### npm v11+: `better-sqlite3` इन्स्टॉल झालेले नाही (मॉड्यूल सापडत नाही)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**कारण:** npm v11 (Node.js 24+ सोबत वितरित केलेले) डीफॉल्टनुसार पर्यायी
अवलंबनांसाठी इन्स्टॉल स्क्रिप्ट ब्लॉक करते. `better-sqlite3` हे `optionalDependencies`
मध्ये सूचीबद्ध असल्यामुळे आणि त्यासाठी नेटिव्ह कम्पाइलेशन (`node-gyp rebuild`) आवश्यक असल्यामुळे, npm ते कोणतीही सूचना न देता वगळते.

**लक्षणे:**

- सर्व्हर सुरू होताना `Cannot find module 'better-sqlite3'` त्रुटीसह क्रॅश होतो
- `ls node_modules/better-sqlite3` हे "अशी कोणतीही फाइल किंवा डिरेक्टरी नाही" असे दाखवते
- `npm ls better-sqlite3` हे `(रिकामे)` असे दाखवते

**उपाय:**

1. इन्स्टॉल स्क्रिप्टना मंजुरी द्या आणि पुन्हा इन्स्टॉल करा:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. किंवा पूर्वनिर्मित पॅकेज स्वतः इन्स्टॉल करा:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ते कार्य करते याची खात्री करा: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**कारण:** जागतिक स्तरावर `npm install -g omniroute` केल्यानंतर, पॅकेजमधील `better-sqlite3` नेटिव्ह बायनरी स्थानिकरित्या चालू असलेल्या आर्किटेक्चर किंवा Node.js ABI पेक्षा वेगळ्या आर्किटेक्चर किंवा ABI साठी कम्पाइल केलेली असू शकते. पूर्वनिर्मित बायनरी तुमच्या वातावरणाशी जुळत नसताना macOS वर (Apple Silicon आणि Intel दोन्हींवर) हे सामान्यपणे घडते.

**लक्षणे:**

- सर्व्हर सुरू होताच `dlopen` त्रुटीसह अयशस्वी होतो
- त्रुटीमध्ये `slice is not valid mach-o file` समाविष्ट असते
- संपूर्ण उदाहरण:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**उपाय — तुमच्या स्थानिक वातावरणासाठी पुन्हा बिल्ड करा (Node.js डाउनग्रेड करण्याची आवश्यकता नाही):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **टीप:** यामुळे तुमची स्थानिक Node.js आवृत्ती आणि CPU आर्किटेक्चर यांच्याशी सुसंगत नेटिव्ह बाइंडिंग पुन्हा कम्पाइल होते आणि बायनरी विसंगती दूर होते. अधिकृतपणे समर्थित रनटाइम श्रेणी **`>=22.22.2 <23` किंवा `>=24.0.0 <27`** आहे (`src/shared/utils/nodeRuntimeSupport.ts` मधील `SUPPORTED_NODE_RANGE`, `package.json` मधील `engines` फील्डशी संरेखित). Node.js 24.x LTS (Krypton) आणि Node.js 26 हे `better-sqlite3` v12.x सोबत पूर्णपणे समर्थित आहेत.

## प्रॉक्सी समस्या

<a name="proxy-issues"></a>

### प्रदाता प्रमाणीकरणात "fetch failed" दिसते

**कारण:** API की प्रमाणीकरण एंडपॉइंट (`POST /api/providers/validate`) यापूर्वी प्रॉक्सी कॉन्फिगरेशनला वगळत होता, ज्यामुळे प्रॉक्सी रूटिंग आवश्यक असलेल्या वातावरणांमध्ये अपयश येत होते.

**निराकरण (v3.5.5+):** ही समस्या आता सोडवण्यात आली आहे. प्रदाता प्रमाणीकरण `runWithProxyContext` मधून रूट होते आणि प्रदाता-स्तरीय व जागतिक प्रॉक्सी सेटिंग्जचे आपोआप पालन करते.

### टोकन स्थिती तपासणी "fetch failed" सह अयशस्वी होते

**कारण:** पार्श्वभूमीतील OAuth टोकन रिफ्रेश प्रत्येक कनेक्शनसाठी प्रॉक्सी कॉन्फिगरेशन निर्धारित करत नव्हता.

**निराकरण (v3.5.5+):** टोकन स्थिती तपासणी शेड्युलर आता रिफ्रेश करण्याचा प्रयत्न करण्यापूर्वी प्रत्येक कनेक्शनसाठी प्रॉक्सी कॉन्फिगरेशन निर्धारित करतो. v3.5.5+ वर अपडेट करा.

### SOCKS5 प्रॉक्सी "invalid onRequestStart method" परत करतो

**कारण:** Node.js 22 वर undici@8 डिस्पॅचर हा Node च्या अंगभूत `fetch()` अंमलबजावणीशी विसंगत आहे.

**निराकरण (v3.5.5+):** प्रॉक्सी डिस्पॅचर सक्रिय असताना OmniRoute आता undici चे स्वतःचे `fetch()` फंक्शन वापरते, ज्यामुळे सुसंगत वर्तन सुनिश्चित होते. v3.5.5+ वर अपडेट करा.

### WSL अंतर्गत MITM प्रॉक्सी: Windows होस्टवरील डेस्कटॉप अॅप्स इंटरसेप्ट होत नाहीत

**कारण:** MITM प्रॉक्सी आणि त्याचे CA प्रमाणपत्र OmniRoute ज्या वातावरणात चालते त्या वातावरणात इंस्टॉल होतात. WSL अंतर्गत ते वातावरण Linux गेस्ट असते, तर AI डेस्कटॉप अॅप्स (Kiro, Trae, Copilot, Zed, …) Windows होस्टवर चालतात. होस्ट अॅप्स गेस्टच्या प्रमाणपत्र स्टोअरवर विश्वास ठेवत नाहीत आणि गेस्टच्या सिस्टम प्रॉक्सीद्वारे रूट होत नाहीत, त्यामुळे तेथे डेस्कटॉप इंटरसेप्शन सक्रिय होत नाही.

**शिफारस:** तुम्हाला इंटरसेप्ट करायची असलेली डेस्कटॉप अॅप्स ज्या OS वर आहेत त्याच OS वर OmniRoute नेटिव्ह स्वरूपात चालवा (Windows अॅप्ससाठी Windows; त्याचप्रमाणे macOS/Linux). होस्ट अॅप्सना लक्ष्य करताना OmniRoute ला WSL मध्येच ठेवण्यासाठी, निर्माण केलेल्या CA प्रमाणपत्रावर Windows होस्टमध्ये व्यक्तिशः विश्वास स्थापित करावा लागतो आणि प्रत्येक होस्ट अॅपची नेटवर्क/प्रॉक्सी सेटिंग्ज WSL प्रॉक्सी एंडपॉइंटकडे निर्देशित करावी लागतात — ही असमर्थित आणि अस्थिर व्यवस्था आहे.

## क्लाउड समस्या

### क्लाउड सिंक त्रुटी

1. `BASE_URL` तुमच्या चालू इन्स्टन्सकडे निर्देश करत असल्याची खात्री करा (उदा., `http://localhost:20128`)
2. `CLOUD_URL` तुमच्या क्लाउड एंडपॉइंटकडे निर्देश करत असल्याची खात्री करा (उदा., `https://omniroute.dev`)

### क्लाउडवर `stream=false` मुळे 500 प्रतिसाद मिळतो

**लक्षण:** नॉन-स्ट्रीमिंग कॉलसाठी क्लाउड एंडपॉइंटवर `Unexpected token 'd'...`.

**कारण:** क्लायंटला JSON अपेक्षित असताना अपस्ट्रीम SSE पेलोड परत करतो.

**तात्पुरता उपाय:** क्लाउडवरील थेट कॉलसाठी `stream=true` वापरा. स्थानिक रनटाइममध्ये SSE→JSON फॉलबॅक समाविष्ट आहे.

### क्लाउड कनेक्टेड असल्याचे दाखवतो, पण "Invalid API key" म्हणतो

1. स्थानिक डॅशबोर्डवरून नवीन की तयार करा (`/api/keys`)
2. क्लाउड सिंक चालवा: Enable Cloud → Sync Now
3. जुन्या/सिंक न केलेल्या की अजूनही क्लाउडवर `401` परत करू शकतात

## Docker समस्या

### Docker IPv6 / कनेक्शन रीसेट

<a name="docker-ipv6"></a>

**लक्षणे:** `curl http://localhost:20128/v1/models` हे `curl: (56) Recv failure: Connection reset by peer` परत करते. डॅशबोर्ड आणि प्रमाणीकरणाची आवश्यकता नसलेले एंडपॉइंट कार्य करतात, परंतु प्रमाणीकृत एंडपॉइंट अयशस्वी होतात — ही प्रमाणीकरणाची समस्या असल्यासारखी दिसते, पण प्रत्यक्षात तशी नसते.

**कारण:** `docker run -p 20128:20128` हे `0.0.0.0` (IPv4) आणि `::` (IPv6) या दोन्हींवर प्रकाशित करते, परंतु कंटेनरमधील प्रक्रिया फक्त IPv4 वर ऐकते. ज्या होस्टवर `localhost` प्रथम `::1` मध्ये रिझॉल्व्ह होते, तेथे कनेक्शन मागे कोणताही लिसनर नसलेल्या प्रकाशित IPv6 पोर्टवर पोहोचते → कनेक्शन रीसेट होते.

**निराकरण:**

1. **त्वरित निदान:** `curl -4 http://localhost:20128/v1/models` चालवा. ते `-4` सह कार्य करत असेल, पण त्याशिवाय अयशस्वी होत असेल, तर IPv6 बाइंडमध्ये विसंगती आहे.
2. **कायमस्वरूपी निराकरण:** तुमच्या `docker run` कमांडमध्ये `-p 127.0.0.1:20128:20128` वापरून स्पष्टपणे IPv4 शी बाइंड करा:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   यामुळे IPv4 बाइंड सक्तीने वापरला जातो आणि सर्व होस्ट इंटरफेसवर प्रॉक्सी उघड होणेही टाळले जाते.

## डीबगिंग

### लॉग फाइल्स सक्षम करा

तुमच्या `.env` फाइलमध्ये `APP_LOG_TO_FILE=true` सेट करा. ॲप्लिकेशन लॉग्स `logs/` अंतर्गत लिहिले जातात.
सेटिंग्जमध्ये कॉल लॉग पाइपलाइन सक्षम असताना रिक्वेस्ट आर्टिफॅक्ट्स `${DATA_DIR}/call_logs/` अंतर्गत संग्रहित केले जातात.
पाइपलाइन कॅप्चर सक्षम असताना स्ट्रीम चंक पेलोड्स वगळण्यासाठी `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` सेट करा किंवा आर्टिफॅक्टची कमाल मर्यादा KB मध्ये बदलण्यासाठी `CALL_LOG_PIPELINE_MAX_SIZE_KB` समायोजित करा.

### प्रोव्हायडरची स्थिती तपासा

```bash
# हेल्थ डॅशबोर्ड
http://localhost:20128/dashboard/health

# API स्थिती तपासणी
curl http://localhost:20128/api/monitoring/health
```

### रनटाइम स्टोरेज

- मुख्य स्थिती: `${DATA_DIR}/storage.sqlite` (प्रोव्हायडर्स, कॉम्बोज, उपनावे, की, सेटिंग्ज)
- वापर: `storage.sqlite` मधील SQLite टेबल्स (`usage_history`, `call_logs`, `proxy_logs`) + पर्यायी `${DATA_DIR}/call_logs/`
- ॲप्लिकेशन लॉग्स: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` असताना)
- कॉल लॉग आर्टिफॅक्ट्स: कॉल लॉग पाइपलाइन सक्षम असताना `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs पृष्ठावरील **Clean history** कृती `call_logs`, जुने
`request_detail_logs` आणि स्थानिक `${DATA_DIR}/call_logs/` आर्टिफॅक्ट डायरेक्टरी साफ करते.

### चॅट विनंत्या 503 / chat_admission_busy सह अयशस्वी होतात

**लक्षणे:**

- चॅट पूर्णता एंडपॉइंट पुन्हा प्रयत्न करता येण्याजोगा `503` प्रतिसाद परत करतो, ज्याचा त्रुटी कोड
  `chat_admission_busy` असतो.
- प्रतिसादामध्ये `Retry-After` समाविष्ट असते. #12135 पासून हे मूल्य निरीक्षण केलेल्या
  व्यापावरून निर्धारित केले जाते — विनंतीने आधीच प्रतीक्षा केलेली `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` विंडो
  आणि सध्याचे हेवीवेट लीजेस जितका वेळ राखून ठेवले गेले आहेत त्यापैकी मोठे मूल्य — पूर्ण
  सेकंदापर्यंत वरच्या दिशेने पूर्णांकित केले जाते आणि 60 वर मर्यादित केले जाते. निष्क्रिय गेटवर ते ऐतिहासिक किमान मर्यादा कायम ठेवते: बाइट-आधारित
  मार्गावर 2 सेकंद, संरचना-आधारित मार्गावर 1 सेकंद (ज्यामध्ये
  `reason: "structure_limit"` हेदेखील समाविष्ट असते).
- दुसरे हेवीवेट चॅट किंवा दीर्घकाळ चालणारा स्ट्रीमिंग प्रतिसाद अजूनही
  प्रक्रियेत असताना हे घडू शकते.

बाइट-आधारित प्रतिसादाचा मुख्य भाग असा आहे:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

संरचना-आधारित प्रतिसाद समान प्रकार आणि कोड वापरतो, ज्यामध्ये संदेश
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
आणि `reason: "structure_limit"` असते.
डीफॉल्ट थ्रेशोल्ड्सवर, विनंतीमध्ये किमान `200` संदेश,
किमान `64` साधने किंवा किमान `32,000` अंदाजित टोकन्स असल्यास, अथवा मर्यादित संरचना अंदाजाने
भेट दिलेल्या `10,000` नोड्सची किंवा `12` खोलीची मर्यादा संपवल्यास ती संरचनात्मकदृष्ट्या हेवी मानली जाते.

**कारण:** हे OmniRoute अंतर्गत जाणूनबुजून केलेले लोड शेडिंग आहे, अपस्ट्रीम प्रदात्याचे अपयश नाही.
मोठ्या विनंतीचा मुख्य भाग राखून ठेवण्यापूर्वी आणि पार्स करण्यापूर्वी मर्यादित हेवीवेट क्षमता आरक्षित करण्यासाठी
प्रत्येक प्रक्रिया प्रक्रिया-स्थानिक गार्ड वापरते. SSE प्रतिसादाच्या संपूर्ण आयुष्यकाळासाठी हेवीवेट लीज
राखून ठेवले जाते.

**#503-फॅन-आउट:** या सुधारणेपूर्वी, गार्डने होस्ट मेमरीचा विचार न करता समवर्तीता एका निश्चित विनंती COUNT पर्यंत
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, डीफॉल्ट `1`) मर्यादित केली होती, त्यामुळे कोडिंग-एजंट
फॅन-आउट (एकाधिक सबएजंट्स/CLIs, नियमितपणे > 256 KB असलेले मुख्य भाग) प्रत्यक्ष
समवर्तीता ~1 पर्यंत घसरवत असे आणि पूर्णपणे सामान्य लोडमध्ये 503 त्रुटी निर्माण करत असे. आता गार्ड स्वतःचे समायोजन
करतो: तो प्रक्रियेच्या वास्तविक मेमरी मर्यादेवरून आकारमान ठरवलेल्या, स्वयंचलितपणे निर्धारित केलेल्या अंतर्ग्रहण BYTE बजेटद्वारे (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) नियंत्रित
होतो आणि थेट संसाधन-दबाव सिग्नलचाही विचार करतो — त्यामुळे एकाच वेळी एकापेक्षा जास्त
हेवी विनंत्या आल्या म्हणून नव्हे, तर होस्टवर खरोखरच मेमरीचा दबाव असतानाच तो लोड कमी करतो.
जुनी गणना मर्यादा (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) अजूनही मानली जाते, परंतु तुम्ही ती स्पष्टपणे सेट केली असेल तरच.

क्षमता व्यस्त असताना, हेवीवेट विनंती पुन्हा प्रयत्न करता येण्याजोगा `503` प्रतिसाद देण्यापूर्वी
स्लॉट मोकळा होण्यासाठी प्रथम `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` पर्यंत (डीफॉल्ट `2000`, `0` प्रतीक्षा अक्षम करते) प्रतीक्षा करते.
ही मर्यादित प्रतीक्षा यासाठी अस्तित्वात आहे की, हेवी उप-विनंत्या समवर्तीपणे फॅन-आउट करणारे एजंट-शैलीतील क्लायंट्स
(OpenCode, Claude Code, Cursor) त्वरित नकारांवर त्यांचे संपूर्ण पुनर्प्रयत्न बजेट खर्च करून कार्याच्या मध्यात बंद पडण्याऐवजी
या विनंती-संचावर क्रमाने प्रक्रिया करतील.
सध्याचा हेवीवेट लीज व्याप, निश्चित केलेले बाइट बजेट आणि थेट दबावाची तीव्रता
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) येथे दर्शवली जातात — कोणतेही env var बदलण्यापूर्वी हे तपासा.
Settings → Resilience → Request Queue → Concurrent Requests हे नियंत्रित करत नाही; ती सेटिंग
स्वतंत्र प्रदाता विनंती-रांग यंत्रणा नियंत्रित करते.

**उपाय:**

1. प्रथम पुन्हा प्रयत्न करा. क्लायंट्सनी विनंती त्वरित पुन्हा पाठवण्याऐवजी `Retry-After` चे पालन करून
   बॅकऑफ वापरावा.
2. काहीही समायोजित करण्यापूर्वी `/api/monitoring/health` → `chatAdmission` तपासा. `countCapEnabled:
false` आणि पुरेसे मोठे `maxInflightBytes` यांचा अर्थ स्वयंचलितपणे निर्धारित केलेले बजेट आधीच योग्य प्रकारे
   कार्य करत आहे; `high`/`critical` `pressureSeverity` चा अर्थ होस्टवर खरोखरच मेमरी कमी आहे —
   हे admission env var द्वारे दुरुस्त करता येत नाही; त्यासाठी अधिक RAM किंवा कमी कार्यभार आवश्यक आहे.
3. `/api/monitoring/health` मध्ये स्वयंचलितपणे निर्धारित केलेले बजेट तुमच्या होस्टसाठी खरोखरच खूप कमी असल्याचे
   दिसल्यासच (हे दुर्मिळ आहे — ते आधीच कंटेनरपासून बेअर-मेटलपर्यंत स्केल होते), जुन्या विनंती-गणना मर्यादेकडे परत जाण्याऐवजी
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` वापरून ते थेट ओव्हरराइड करा.

अधिकृत admission सेटिंग्जसाठी [पर्यावरण-चल संदर्भ](../reference/ENVIRONMENT.md#4-security--authentication)
पहा.

## पर्यायी RAG / LLM अपयश वर्गीकरण (16 समस्या)

काही OmniRoute वापरकर्ते गेटवेला RAG किंवा एजंट स्टॅक्सच्या पुढे ठेवतात. अशा सेटअपमध्ये एक विचित्र नमुना दिसणे सामान्य आहे: OmniRoute सुस्थितीत दिसते (प्रदाते कार्यरत, राउटिंग प्रोफाइल्स ठीक, दर-मर्यादेच्या सूचना नाहीत), पण अंतिम उत्तर तरीही चुकीचे असते.

प्रत्यक्षात, अशा घटना सामान्यतः गेटवेमुळे नव्हे, तर डाउनस्ट्रीम RAG पाइपलाइनमुळे घडतात.

त्या अपयशांचे वर्णन करण्यासाठी तुम्हाला सामायिक शब्दसंग्रह हवा असल्यास, तुम्ही WFGY ProblemMap वापरू शकता. हे MIT परवान्याअंतर्गत उपलब्ध असलेले बाह्य मजकूर संसाधन असून, त्यात वारंवार उद्भवणाऱ्या सोळा RAG / LLM अपयश नमुन्यांची व्याख्या केली आहे. व्यापक पातळीवर त्यात पुढील बाबी समाविष्ट आहेत:

- पुनर्प्राप्तीतील विचलन आणि तुटलेल्या संदर्भ सीमा
- रिकामे किंवा कालबाह्य इंडेक्स आणि व्हेक्टर स्टोअर्स
- एम्बेडिंग आणि अर्थविषयक जुळणीतील विसंगती
- प्रॉम्प्ट संयोजन आणि संदर्भ विंडोशी संबंधित समस्या
- तर्कशक्तीचे अपयश आणि अतिआत्मविश्वासपूर्ण उत्तरे
- दीर्घ साखळी आणि एजंट समन्वयातील अपयश
- मल्टी-एजंट मेमरी आणि भूमिकांमधील विचलन
- डिप्लॉयमेंट आणि बूटस्ट्रॅप क्रमाशी संबंधित समस्या

कल्पना सोपी आहे:

1. एखाद्या चुकीच्या प्रतिसादाची चौकशी करताना, पुढील माहिती नोंदवा:
   - वापरकर्त्याचे कार्य आणि विनंती
   - OmniRoute मधील रूट किंवा प्रदाता संयोजन
   - डाउनस्ट्रीममध्ये वापरलेला कोणताही RAG संदर्भ (पुनर्प्राप्त केलेले दस्तऐवज, टूल कॉल्स इत्यादी)
2. घटनेला एक किंवा दोन WFGY ProblemMap क्रमांकांशी (`No.1` … `No.16`) जोडा.
3. OmniRoute लॉग्जच्या शेजारी तो क्रमांक तुमच्या स्वतःच्या डॅशबोर्ड, रनबुक किंवा घटना ट्रॅकरमध्ये साठवा.
4. तुमचा RAG स्टॅक, रिट्रीव्हर किंवा राउटिंग धोरण बदलण्याची आवश्यकता आहे का हे ठरवण्यासाठी संबंधित WFGY पृष्ठ वापरा.

संपूर्ण मजकूर आणि ठोस कृतीपद्धती येथे उपलब्ध आहेत (MIT परवाना, केवळ मजकूर):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

तुम्ही OmniRoute च्या मागे RAG किंवा एजंट पाइपलाइन्स चालवत नसल्यास, हा विभाग दुर्लक्षित करू शकता.

## v3.8.0 मधील ज्ञात समस्या

v3.8.0 रिलीजशी संबंधित समस्या आणि त्यांवरील सध्याचे तात्पुरते उपाय. नंतरच्या पॅचमध्ये दुरुस्ती समाविष्ट झाल्यास, ही नोंद अद्ययावत केली जाईल किंवा काढून टाकली जाईल.

### Devin CLI प्रमाणीकरणातील अपयश

**लक्षणे:**

- CLI रनटाइम तपासणीत `installed=false` दिसते

**कारणे:**

- `CLI_DEVIN_BIN` अस्तित्वात नसलेल्या पाथकडे निर्देश करते
- होस्टवर Devin CLI इंस्टॉल केलेले नाही

**उपाय:**

1. तुमच्या प्लॅटफॉर्मसाठी Devin CLI इंस्टॉल करा
2. `.env` मध्ये `CLI_DEVIN_BIN=/usr/local/bin/devin` (किंवा वास्तविक पाथ) सेट करा
3. OmniRoute रीस्टार्ट करा आणि **Dashboard → CLI Tools** मधून पुन्हा चाचणी करा

### मॉडेल कूलडाउन अडकलेले आहे (मॅन्युअल रीसेट)

**लक्षणे:**

- टाइमस्टॅम्प भूतकाळातील असूनही संयोजन राउटिंगमध्ये विनंत्या त्या मॉडेलला वगळतात

**मॅन्युअल रीसेट:**

- **API:** व्यवस्थापन प्रमाणीकरण हेडर्ससह `DELETE /api/resilience/model-cooldowns`

### Command Code प्रदात्याचे कनेक्शन 403 सह अयशस्वी होते

**लक्षणे:**

- Command Code प्रदात्याच्या कनेक्शनची चाचणी करताना 403
- नव्याने जोडल्यानंतर प्रदाता कार्डवर "unauthorized" दिसते

**कारण:** OAuth प्रवाह पूर्ण झाला नाही (कॉलबॅक प्राप्त झाला नाही किंवा टोकन कायमस्वरूपी साठवले गेले नाही).

**उपाय:**

- OAuth प्रवाह पुन्हा सुरू करण्यासाठी CLI मधून `omniroute providers` चालवा, किंवा
- **Dashboard → Providers → Command Code → Reconnect** मधून OAuth पुन्हा चालवा

### ModelScope अतिशय आक्रमक 429 कूलडाउन परत करते

**लक्षणे:**

- विनंत्यांच्या छोट्या बर्स्टनंतर ModelScope वर अतिशय लहान किंवा तत्काळ कूलडाउन
- संयोजन राउटिंगमध्ये अपेक्षेपेक्षा लवकर ModelScope वगळले जाते

**कारण:** ModelScope प्रदाता-विशिष्ट `Retry-After` हेडर्स पाठवते. v3.8.0 मध्ये त्या हेडर्ससाठी स्वतंत्र हाताळणी समाविष्ट आहे, त्यामुळे जुन्या आवृत्त्या त्यांचा सर्वसाधारण दर-मर्यादा संकेत म्हणून चुकीचा अर्थ लावतात.

**उपाय:**

- तुम्ही v3.8.0 किंवा त्यानंतरची आवृत्ती वापरत असल्याची खात्री करा
- **Settings → Resilience** अंतर्गत `useUpstream429BreakerHints` टॉगल सक्षम असल्याचे सत्यापित करा

### प्रॉडक्शनमध्ये OMNIROUTE_WS_BRIDGE_SECRET उपलब्ध नाही

**लक्षणे:**

- रिमोट प्रॉडक्शन होस्टवर चालवताना प्रत्येक Codex/Responses WebSocket ब्रिज विनंतीवर 401
- कनेक्ट झाल्यानंतर WebSocket ब्रिज हँडशेक त्वरित बंद होते

**कारण:** प्रॉडक्शन एन्व्हायर्नमेंटमध्ये `OMNIROUTE_WS_BRIDGE_SECRET` एन्व्हायर्नमेंट व्हेरिएबल उपलब्ध नाही.

**उपाय:**

1. यादृच्छिक गुपित तयार करा: `openssl rand -hex 32`
2. प्रॉडक्शन सर्व्हर एन्व्हायर्नमेंटमध्ये (आणि ब्रिजशी संवाद साधणाऱ्या कोणत्याही क्लायंटमध्ये) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` सेट करा
3. OmniRoute रीस्टार्ट करा

### Responses API: बॅकग्राउंड मोड सिंक्रोनस मोडमध्ये अवनत झाला

**लक्षणे:**

- लॉग केलेली चेतावणी: `background mode degraded to synchronous`
- `background: true` असलेली विनंती बॅकग्राउंड जॉब हँडलऐवजी सामान्य सिंक्रोनस प्रतिसाद परत करते

**कारण:** v3.8.0 मध्ये Responses API वरील `background: true` हेतुपुरस्सर सिंक्रोनस अंमलबजावणीत अवनत केले जाते आणि त्याच वेळी एक चेतावणी दिली जाते. संपूर्ण असिंक्रोनस बॅकग्राउंड अंमलबजावणी भविष्यात उपलब्ध केली जाईल.

**उपाय:**

- `background` शिवाय कॉल करण्यासाठी क्लायंटमध्ये बदल करा, किंवा
- संपूर्ण असिंक्रोनस बॅकग्राउंड मोड समाविष्ट असलेल्या नंतरच्या रिलीजची प्रतीक्षा करा (चेंजलॉगचा मागोवा घ्या)

## संथ प्रारंभ / तत्परता कालबाह्यता

CLI ने `⚠ Server did not respond within 60s` छापले, पण सर्व्हर प्रत्यक्षात
कार्यरत असेल, तर तुमच्या वातावरणासाठी तत्परता तपासणीची कालमर्यादा खूप कमी आहे.

हे सामान्यतः Windows वर (अँटीव्हायरस, फाइलसिस्टम वॉचर्स) किंवा प्रारंभाच्या वेळी
मोठा कार्यभार असलेल्या कंटेनर्समध्ये घडते.

**उपाय — कालमर्यादा वाढवा:**

```bash
# पर्यावरणीय चलाद्वारे (प्रत्येक प्रारंभासाठी कायम राहते):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 मिनिटे
omniroute serve

# CLI फ्लॅगद्वारे (फक्त एकदाच):
omniroute serve --ready-timeout 180000
```

डीफॉल्ट कालमर्यादा 60 000 ms (60 s) आहे. ही सूचना केवळ माहितीसाठी आहे; सर्व्हर
पार्श्वभूमीत सुरू होत राहतो आणि बूट पूर्ण झाल्यानंतर उपलब्ध होईल.

`OMNIROUTE_READY_TIMEOUT_MS` विषयी संपूर्ण तपशीलांसाठी
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) पहा.
