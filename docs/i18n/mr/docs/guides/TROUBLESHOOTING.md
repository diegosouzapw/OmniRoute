## झटपट संदर्भ

**OmniRoute साठी नवीन आहात?** येथून सुरुवात करा — यामुळे 90% समस्या सुटतात:

| मला हे दिसते            | याचा अर्थ                                      | काय करावे                                                                                                      |
| ----------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| "कनेक्ट करता येत नाही"  | OmniRoute चालू नाही                            | `omniroute` किंवा `docker restart omniroute` चालवा                                                             |
| "अवैध API की"           | तुमची की चुकीची आहे किंवा कालबाह्य झाली आहे    | प्रदात्याच्या वेबसाइटवरून की पुन्हा कॉपी करा                                                                   |
| "दर मर्यादा ओलांडली"    | तुम्ही खूप जास्त विनंत्या पाठवत आहात           | 1 मिनिट प्रतीक्षा करा किंवा स्वयंचलित फॉलबॅकसाठी `model: "auto"` वापरा                                         |
| "कोटा ओलांडला"          | तुम्ही तुमचा मोफत/सशुल्क कोटा पूर्ण वापरला आहे | अधिक प्रदाते कनेक्ट करा किंवा मोफत प्रदाते (Kiro, Pollinations) वापरा                                          |
| "प्रतिसाद धीमे आहेत"    | प्रदाता व्यस्त आहे किंवा खूप दूर आहे           | `model: "auto/fast"` वापरा किंवा अधिक वेगवान प्रदाता (Groq, Cerebras) कनेक्ट करा                               |
| "चुकीचा प्रदाता वापरला" | `auto` ने वेगळा प्रदाता निवडला                 | हे सामान्य आहे! `auto` सर्वोत्तम प्रदाता निवडतो. `model: "openai/gpt-4o"` वापरून विशिष्ट प्रदाता सक्तीने निवडा |
| "502 Bad Gateway"       | प्रदाता बंद आहे                                | प्रतीक्षा करून पुन्हा प्रयत्न करा किंवा प्रदाते बदलण्यासाठी `model: "auto"` वापरा                              |
| "401 Unauthorized"      | तुमची क्रेडेन्शियल्स चुकीची आहेत               | तुमची API की तपासा किंवा OAuth वापरून पुन्हा प्रमाणीकरण करा                                                    |
| "429 Too Many Requests" | दर मर्यादा लागू झाली आहे                       | 1 मिनिट प्रतीक्षा करा किंवा अधिक प्रदाते कनेक्ट करा                                                            |

### मोफत प्रदात्यांवरील दर मर्यादा (429 / 400 / 401)

**लक्षण**: प्रमाणीकरणाची आवश्यकता नसलेल्या मोफत प्रदात्यांसह (opencode, auggie इ.) `model: "auto"` वापरताना, उत्तरांऐवजी अधूनमधून `HTTP 429`, `400` किंवा `401` मिळते. काही क्षणांनंतर त्याच प्रॉम्प्टसह पुन्हा प्रयत्न केल्यास विनंत्या यशस्वी होतात, परंतु ऑटोमेशन (cron जॉब्स, एजंट्स, स्क्रिप्ट्स) पहिल्याच अपयशामुळे खंडित होते.

**मूळ कारण**: तीन स्वतंत्र अपयश पद्धती एकत्रित होतात:

1. **प्रदात्याची दर मर्यादा (`429`)**: मोफत स्तर प्रत्येक कालखंडासाठी कोटा लागू करू शकतात. एकाच वेळी आलेल्या समांतर कॉल्समुळे तो संपतो, त्यामुळे कालखंड रीसेट होईपर्यंत पुढील विनंती नाकारली जाते.
2. **पासथ्रूमधील खराब मॉडेल (`400`/`401`)**: `auto/*` पूलमध्ये `opencode` ची अशी पासथ्रू मॉडेल्स समाविष्ट असू शकतात, जी कॅटलॉगमध्ये नोंदणीकृत आहेत पण त्यांच्याकडे सक्रिय क्रेडेन्शियल्स नाहीत (उदा. `oc/north-mini-code-free` → `401`). ऑटो-राउटर त्यापैकी एक वापरून पाहतो, तो प्रयत्न अयशस्वी होतो आणि फॉलबॅक सुरू होण्यापूर्वीच त्रुटी पुढे पाठवली जाते.
3. **समवर्तीपणामुळे वाढ (`429` भाराखाली)**: अनेक एजंट/cron सत्रे एकाच वेळी `auto` वापरतात तेव्हा एकत्रित विनंती दर मोफत प्रदाते सहन करू शकतील त्यापेक्षा जास्त होतो, त्यामुळे वैध कॉल्सनाही गैरवापर म्हणून चिन्हांकित केले जाते.

**सत्यापित उपाय (समुदायाने कळवलेला, 2026-08-10)**: तीन पर्यावरण चल अशा प्रकारे समायोजित करा की रोटेशन, समवर्तीपणा आणि फॉलबॅक मोफत स्तरावरील अस्थिरता हाताळतील आणि त्यामुळे प्रक्रिया बंद पडणार नाही:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 आल्यास दुसऱ्या मॉडेल/प्रदात्याकडे जा (खराब पासथ्रू मॉडेल्स वगळली जातात)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # हेवीवेट प्रवेशाची स्पष्ट कमाल मर्यादा (डीफॉल्टनुसार सेट नसते: विनंती-संख्येवर मर्यादा नाही, खालील टीप पहा)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # त्वरित पुन्हा प्रयत्न करता येणाऱ्या 503 ऐवजी हेवीवेट क्षमतेसाठी अधिक दीर्घ, मर्यादित प्रतीक्षा
```

हे OmniRoute प्रक्रियेच्या पर्यावरणात (डेमनमध्ये, उदा. LaunchAgent plist किंवा `systemctl edit` द्वारे) सेट करा, त्यानंतर OmniRoute रीस्टार्ट करा. रोटेशन फ्लॅग हा सर्वाधिक परिणामकारक पर्याय आहे: तो पूलमधील निरोगी प्रदात्याकडे पारदर्शकपणे पुन्हा प्रयत्न करून गंभीर अपयश टाळतो.

**टीप**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` एकाच वेळी किती हेवीवेट — दीर्घ-कॉन्टेक्स्ट — विनंत्या चालू शकतात यावर मर्यादा घालते; ही मर्यादा प्रवेशद्वार आहे, प्रदात्याची दर मर्यादा नव्हे. **#503-fanout अद्यतन:** हे चल आता डीफॉल्टनुसार सेट केले जात नाही (वरीलप्रमाणे स्पष्टपणे कॉन्फिगर केल्यावरच ते आता लागू होते) — त्याऐवजी हेवीवेट प्रवेश स्वयंचलितपणे निर्धारित केलेल्या बाइट बजेटद्वारे (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) नियंत्रित केला जातो, जे होस्टच्या वास्तविक मेमरी मर्यादेनुसार स्वतःचे प्रमाण ठरवते. त्यामुळे नवीन डिप्लॉयमेंटमध्ये हे चल अजिबात सेट न करताही खूप कमी `503 chat_admission_busy` नकार दिसायला हवेत; येथे ते स्पष्टपणे सेट केल्यास ते दस्तऐवजात नमूद केल्याप्रमाणेच कार्य करते. स्पष्ट बाइट-बजेट ओव्हरराइड्स 8 MiB–2 GiB पर्यंत मर्यादित केले जातात. `413 body_exceeds_budget` ही तात्पुरती समस्या नाही: ते बाइट बजेट वाढवा, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` कमी करा किंवा प्रक्रियेची मेमरी मर्यादा वाढवा. `inflight_bytes_budget` मुळे विनंती वगळली जाणे हा तात्पुरता संसाधन संघर्ष आहे आणि त्यावर पुन्हा प्रयत्न करता येतो. प्रत्येक प्रदात्याची दर मर्यादा (`open-sse/services/rateLimitManager.ts`) स्वतंत्रपणे `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` आणि `RATE_LIMIT_AUTO_ENABLE` द्वारे नियंत्रित केली जाते — `.env.example` पहा.

**उपाय कार्यरत असल्याची पडताळणी कशी करावी**: तुमचा एजंट/cron थोड्याच अंतराने दोनदा चालवा आणि दोन्ही प्रयत्न यशस्वी झाल्याची खात्री करा. उपाय लागू करण्यापूर्वी, दुसऱ्या रनमध्ये सामान्यतः `429`/`401` त्रुटी येते. उपाय लागू केल्यानंतर, अपयशांवर (असल्यास) पारदर्शकपणे पुन्हा प्रयत्न केला जातो आणि कॉल पूर्ण होतो. तुम्ही `curl /monitoring/health` देखील चालवू शकता आणि प्रदाता कनेक्शन्समधील `rateLimitedUntil` फील्ड तसेच प्रभावित प्रदात्यांसाठी `circuitBreakers.providerBreakers[].state` पाहू शकता — स्थिती `CLOSED`, `DEGRADED`, `OPEN` किंवा `HALF_OPEN` यांपैकी एक असते (`src/shared/utils/circuitBreaker.ts` पहा), आणि सतत अयशस्वी होणारा प्रदाता रीसेट कालखंडामुळे प्रोबला प्रवेश मिळण्यापूर्वी `CLOSED → DEGRADED → OPEN` असा बदलेल (`HALF_OPEN`).

**तुम्हाला अजूनही 429 दिसत असल्यास**: त्या provider साठी सक्रिय account ने त्याचा _quota_ खरोखरच पूर्णपणे वापरला आहे (केवळ rate नाही). OmniRoute dashboard → Providers → Accounts मध्ये त्याच provider साठी दुसरे account जोडा किंवा आणखी एखादा मोफत provider (उदा. `routeway`, `auggie`) वापरा. Rotation केवळ तात्पुरत्या rate/400/401 समस्यांसाठी उपयुक्त ठरते; quota पूर्णपणे संपल्यास दुसरे credential किंवा वेगळा provider आवश्यक असतो.

**vision models (`auto/vision`, `bazaarlink/*`) वर 403 दिसत असल्यास**: जोडलेल्या account कडे vision समाविष्ट असलेला paid plan नाही किंवा API key कडे पुरेशा permissions नाहीत. Provider dashboard मध्ये key scope मध्ये vision/multimodal समाविष्ट असल्याचे तपासा किंवा paid tier account जोडा आणि ते vision target म्हणून कायम ठेवा.

## npm install चेतावण्या (ERESOLVE / peer / deprecated)

तुम्ही `npm install -g omniroute` चालवता तेव्हा तुम्हाला `npm warn ERESOLVE`, peer-dependency सूचना आणि `deprecated` संदेशांसारख्या असंख्य चेतावण्या दिसू शकतात. **या अपेक्षित आणि निरुपद्रवी आहेत.** आउटपुटमध्ये `added <N> packages` दिसल्यास तुमचे इन्स्टॉलेशन यशस्वी झाले आहे.

peer-dependency रिझोल्यूशनच्या चेतावण्या दडपण्यासाठी, OmniRoute चे समर्थित इन्स्टॉलेशन स्वरूप वापरा:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` केवळ `ERESOLVE` आणि peer-dependency सूचना दडपते. कालबाह्यता सूचना दृश्यमान राहतात, कारण त्या अप्रत्यक्ष तृतीय-पक्ष पॅकेजमधून येतात; इन्स्टॉलेशन अयशस्वी झाल्याचे त्या दर्शवत नाहीत.

OmniRoute चे नियंत्रण नसलेल्या तृतीय-पक्ष पॅकेजमधील जुन्या peer-dependency श्रेणींमुळे या चेतावण्या येतात:

1. **`marked-terminal` ला `marked >=1 <16` हवे आहे, परंतु `marked@18` आढळले** — प्रत्यक्ष वापरात ते व्यवस्थित कार्य करते; upstream peer श्रेणी फक्त जुनी आहे.
2. **`deprecated prebuild-install@7.1.3`** — अप्रत्यक्ष native-binary प्राप्ती सहाय्यक. पिन केलेले `wreq-js` ट्रान्सपोर्ट बाइंडिंग इन्स्टॉल करण्यासाठी ते
   वापरले जात नाही आणि web-cookie प्रोव्हायडर ट्रान्सपोर्ट सेटअप अयशस्वी झाल्याचे ते दर्शवत
   नाही.

**कोणतीही कृती आवश्यक नाही** — upstream पॅकेज फोर्क केल्याशिवाय या चेतावण्या पूर्णपणे दडपता येत नाहीत.

## अँटीव्हायरसचे चुकीचे सकारात्मक निष्कर्ष

<a name="antivirus-false-positives"></a>

### Avast/AVG कडून `README.md` ला `MD:HttpRequest-inf[Susp]` म्हणून क्वारंटाइन केले जाते

**हा चुकीचा सकारात्मक निष्कर्ष आहे. कशालाही संसर्ग झालेला नाही आणि कोणतीही कृती आवश्यक नाही.**

Avast आणि AVG अनेक HTTP-विनंतींसारख्या दिसणाऱ्या लिंक्स असलेल्या साध्या-मजकूर/Markdown फाइल्सना धोकादायक ठरवणारी ह्युरिस्टिक चालवतात. OmniRoute ची `README.md` npm पॅकेजमध्ये समाविष्ट असते (ती `package.json` → `files` मध्ये सूचीबद्ध आहे), त्यामुळे जागतिक इंस्टॉल केल्यावर ती `node_modules/omniroute/README.md` येथे ठेवली जाते — आणि तिच्यामध्ये सुमारे 15 `http://localhost:20128/...` उदाहरणे आहेत (MCP HTTP/SSE एंडपॉइंट्स, A2A `.well-known` URL आणि `curl` स्निपेट्स). लिंक्सची ही घनता ह्युरिस्टिक सक्रिय करण्यासाठी पुरेशी आहे.

हे नुकतेच सुरू झाले असल्यास: फाइलच्या स्वरूपामध्ये बदल झालेला नाही. README मधील एंडपॉइंट्सचा तक्ता वाढला (MCP HTTP + SSE + A2A जोडले गेले) आणि अधिक `curl` उदाहरणे समाविष्ट झाली, ज्यामुळे त्यांची संख्या मर्यादेपलीकडे गेली.

ही शून्य एक्झिक्युटेबल सामग्री असलेली निष्क्रिय दस्तऐवजीकरण फाइल आहे. तुम्ही ती क्वारंटाइनमधून सुरक्षितपणे पुनर्संचयित करू शकता.

**काय करावे:**

1. **सूचना थांबवा** — तुमच्या अँटीव्हायरसमध्ये इंस्टॉल निर्देशिका वगळा
   (Avast: Settings → Exceptions), तुमचा जागतिक `node_modules` पथ आणि/किंवा
   OmniRoute डेटा निर्देशिका (`~/.omniroute/`) जोडा.
2. **चुकीच्या सकारात्मक निष्कर्षाची तक्रार करा** — <https://www.avast.com/false-positive-file-form.php>,
   आणि क्वारंटाइन केलेली `README.md` संलग्न करा. यामुळे सर्वांना मदत होईल, कारण विक्रेत्याची
   ह्युरिस्टिक एका मजकूर फाइलवर अतिप्रतिक्रिया करत आहे.

**आम्ही आमच्या बाजूने हे "दुरुस्त" का करत नाही:** सर्व उदाहरणे `http://localhost` आहेत आणि
स्वतः स्वाक्षरी केलेल्या प्रमाणपत्राचा त्रास घेतल्याशिवाय localhost वर `https` वापरता येत नाही. एका विक्रेत्याची ह्युरिस्टिक टाळण्यासाठी दस्तऐवजीकरण विकृत केल्यास स्कॅनरच्या त्रुटीची पूर्तता करण्यासाठी प्रत्येक वाचकाला त्रास होईल.

### Kaspersky कडून Desktop अॅपला `PDM:Trojan.Win32.Generic` म्हणून चिन्हांकित केले जाते

**हा वर्तन-आधारित ह्युरिस्टिकमुळे आलेला चुकीचा सकारात्मक निष्कर्ष आहे. कशालाही संसर्ग झालेला नाही.** Kaspersky मधील
`PDM:` उपसर्गाचा अर्थ असा आहे की हा निष्कर्ष त्याच्या Proactive Defense Module (System Watcher) मधून आला आहे, जे इंस्टॉलरची ज्ञात मालवेअरशी तुलना करण्याऐवजी तो _काय करतो_ याचे मूल्यमापन करते. ते सक्रिय झाल्यावर Kaspersky संपूर्ण इंस्टॉलेशन "रोल बॅक" करते — म्हणजे त्याने आधीच लिहिलेल्या फाइल्स हटवते — त्यामुळे अॅप बिघडते किंवा गायब होते.

त्याने चिन्हांकित केलेल्या फाइल्स या Desktop अॅपसोबत बंडल केलेल्या घोषित, मुक्त-स्रोत अवलंबितांचे प्रमाणित भाग आहेत, उदाहरणार्थ:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` आणि
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), अॅपमधील प्रदाता लॉगिन आणि ब्राउझर-आधारित चॅटसाठी वापरली जाणारी ब्राउझर-ऑटोमेशन लायब्ररी.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — वेब-कुकी प्रदात्यांवर ब्राउझर-फिंगरप्रिंटेड HTTP साठी वापरले जाणारे निश्चित आवृत्तीचे `wreq-js` नेटिव्ह बाइंडिंग (`<arch>` हे `x64` किंवा `arm64` असते).

**ते सक्रिय का होते:** Windows इंस्टॉलरवर **अद्याप कोड-स्वाक्षरी केलेली नाही**, त्यामुळे स्वाक्षरी नसलेल्या NSIS इंस्टॉलरची प्रतिष्ठा शून्य असते आणि वर्तन-आधारित ह्युरिस्टिक्स कमाल आक्रमकतेने चालतात. यासोबत बंडल केलेली नेटिव्ह DLL आणि
`%LOCALAPPDATA%\Programs\OmniRoute` अंतर्गत लिहिलेल्या शेकडो `.js` फाइल्स (Next.js स्वतंत्र बिल्डमधील हॅश-प्रत्यय असलेल्या पॅकेज निर्देशिकांसह) ह्युरिस्टिक सक्रिय करण्यासाठी पुरेशा आहेत. कोड स्वाक्षरी नियोजित आहे; ती लागू होईपर्यंत नवीन प्रकाशनांमध्ये हे पुन्हा घडू शकते.

**काय करावे:**

1. **प्रथम तुमचे डाउनलोड सत्यापित करा** (यामुळे फाइलमध्ये छेडछाड झाल्याची शक्यता नाकारता येते). प्रत्येक प्रकाशनासोबत
   `latest.yml` प्रकाशित केली जाते, जिचे `sha512` फील्ड (base64) `OmniRoute.Setup.<version>.exe`
   इंस्टॉलरला व्यापते. इंस्टॉलर असलेल्या फोल्डरमधून PowerShell मध्ये:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   आउटपुट `latest.yml` → `sha512` शी जुळले पाहिजे. ते जुळत नसल्यास, फाइल हटवा आणि
   केवळ [GitHub प्रकाशन पृष्ठावरून](https://github.com/diegosouzapw/OmniRoute/releases) पुन्हा डाउनलोड करा.
2. **पुनर्संचयित करा + वगळा** — रोल बॅक केलेले घटक क्वारंटाइनमधून पुनर्संचयित करा आणि
   `%LOCALAPPDATA%\Programs\OmniRoute` साठी अपवाद जोडा (Kaspersky → Settings → Threats and Exclusions),
   त्यानंतर पुन्हा इंस्टॉल करा.
3. **चुकीच्या सकारात्मक निष्कर्षाची तक्रार करा** — <https://opentip.kaspersky.com/>. वापरकर्त्यांनी सादर केलेले FP
   अहवाल अनुमत-सूचीत समाविष्ट करण्याची प्रक्रिया खरोखर वेगवान करतात.

## Node.js सुसंगतता

<a name="nodejs-compatibility"></a>

### लॉगिन पृष्ठ क्रॅश होते किंवा "Module self-registration" त्रुटी दाखवते

**कारण:** तुम्ही OmniRoute ने मंजूर केलेल्या सुरक्षित रनटाइमच्या किमान आवृत्तीच्या मर्यादेबाहेरील Node.js आवृत्ती वापरत आहात. यातील सर्वात सामान्य परिस्थिती म्हणजे Node 22 किंवा 24 ची अशी जुनी पॅच आवृत्ती वापरणे, जी OmniRoute ला आवश्यक असलेल्या पॅच केलेल्या सुरक्षा मर्यादेपेक्षा कमी आहे.

**लक्षणे:**

- लॉगिन पृष्ठावर रिकामी स्क्रीन किंवा सर्व्हर त्रुटी दिसते
- कन्सोलमध्ये `Error: Module did not self-register` किंवा तत्सम नेटिव्ह बाइंडिंग त्रुटी दिसतात
- रनटाइम समर्थित सुरक्षितता धोरणाच्या बाहेर असल्यास, लॉगिन पृष्ठावर तुमच्या Node आवृत्तीसह **नारिंगी चेतावणी बॅनर** दिसतो

**उपाय:**

1. समर्थित Node.js LTS रिलीझ इन्स्टॉल करा (शिफारस: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. तुमची आवृत्ती तपासा: `node --version` ने 24.x LTS शाखेवरील `v24.0.0` किंवा त्यापेक्षा नवीन आवृत्ती दाखवली पाहिजे
3. OmniRoute पुन्हा इन्स्टॉल करा: `npm install -g omniroute`
4. रीस्टार्ट करा: `omniroute`

> **समर्थित सुरक्षित आवृत्त्या:** `>=22.22.2 <23` किंवा `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) आणि Node.js 26 पूर्णपणे समर्थित आहेत.

### npm v11+: `better-sqlite3` इन्स्टॉल झालेले नाही (मॉड्यूल सापडत नाही)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**कारण:** npm v11 (Node.js 24+ सोबत उपलब्ध) डीफॉल्टनुसार पर्यायी
अवलंबित्वांसाठी इन्स्टॉल स्क्रिप्ट्स ब्लॉक करते. `better-sqlite3` हे `optionalDependencies`
मध्ये सूचीबद्ध असून त्यासाठी नेटिव्ह कंपाइलेशन (`node-gyp rebuild`) आवश्यक असल्यामुळे, npm ते कोणतीही सूचना न देता वगळते.

**लक्षणे:**

- स्टार्टअपवेळी सर्व्हर `Cannot find module 'better-sqlite3'` त्रुटीसह क्रॅश होतो
- `ls node_modules/better-sqlite3` "No such file or directory" दाखवते
- `npm ls better-sqlite3` `(empty)` दाखवते

**उपाय:**

1. इन्स्टॉल स्क्रिप्ट्सना मंजुरी द्या आणि पुन्हा इन्स्टॉल करा:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. किंवा पूर्वनिर्मित पॅकेज व्यक्तिचलितपणे इन्स्टॉल करा:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ते कार्य करते याची खात्री करा: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**कारण:** जागतिक स्तरावरील `npm install -g omniroute` नंतर, पॅकेजमधील `better-sqlite3` नेटिव्ह बायनरी स्थानिक पातळीवर चालू असलेल्या आर्किटेक्चर किंवा Node.js ABI पेक्षा वेगळ्या आर्किटेक्चर किंवा ABI साठी कंपाइल केलेली असू शकते. पूर्वनिर्मित बायनरी तुमच्या वातावरणाशी जुळत नसल्यास, macOS वर (Apple Silicon आणि Intel दोन्हींवर) ही समस्या सामान्यपणे उद्भवते.

**लक्षणे:**

- स्टार्टअपवेळी सर्व्हर `dlopen` त्रुटीसह त्वरित अयशस्वी होतो
- त्रुटीमध्ये `slice is not valid mach-o file` असते
- संपूर्ण उदाहरण:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**उपाय — तुमच्या स्थानिक वातावरणासाठी पुन्हा बिल्ड करा (Node.js डाउनग्रेड करण्याची आवश्यकता नाही):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **टीप:** हे नेटिव्ह बाइंडिंग तुमची स्थानिक Node.js आवृत्ती आणि CPU आर्किटेक्चर यांच्याशी सुसंगतपणे पुन्हा कंपाइल करते, ज्यामुळे बायनरी विसंगती दूर होते. अधिकृतपणे समर्थित रनटाइम श्रेणी **`>=22.22.2 <23` किंवा `>=24.0.0 <27`** आहे (`src/shared/utils/nodeRuntimeSupport.ts` मधील `SUPPORTED_NODE_RANGE`, जी `package.json` मधील `engines` फील्डशी संरेखित आहे). Node.js 24.x LTS (Krypton) आणि Node.js 26 या `better-sqlite3` v12.x सह पूर्णपणे समर्थित आहेत.

## प्रॉक्सी समस्या

<a name="proxy-issues"></a>

### प्रदाता प्रमाणीकरणामध्ये "fetch failed" दिसते

**कारण:** API की प्रमाणीकरण एंडपॉइंट (`POST /api/providers/validate`) पूर्वी प्रॉक्सी कॉन्फिगरेशनला वगळत होता, ज्यामुळे प्रॉक्सी राउटिंग आवश्यक असलेल्या वातावरणांमध्ये अपयश येत होते.

**निराकरण (v3.5.5+):** ही समस्या आता दुरुस्त करण्यात आली आहे. प्रदाता प्रमाणीकरण आता `runWithProxyContext` द्वारे रूट होते आणि प्रदाता-स्तरीय व जागतिक प्रॉक्सी सेटिंग्जचा आपोआप अवलंब करते.

### टोकन स्थिती तपासणी "fetch failed" सह अयशस्वी होते

**कारण:** पार्श्वभूमीतील OAuth टोकन रिफ्रेश प्रत्येक कनेक्शनसाठी प्रॉक्सी कॉन्फिगरेशन निश्चित करत नव्हते.

**निराकरण (v3.5.5+):** टोकन स्थिती तपासणीचे शेड्युलर आता रिफ्रेशचा प्रयत्न करण्यापूर्वी प्रत्येक कनेक्शनसाठी प्रॉक्सी कॉन्फिगरेशन निश्चित करते. v3.5.5+ वर अपडेट करा.

### SOCKS5 प्रॉक्सी "invalid onRequestStart method" परत करते

**कारण:** Node.js 22 वर undici@8 डिस्पॅचर Node च्या अंगभूत `fetch()` अंमलबजावणीशी सुसंगत नाही.

**निराकरण (v3.5.5+):** प्रॉक्सी डिस्पॅचर सक्रिय असताना OmniRoute आता undici चे स्वतःचे `fetch()` फंक्शन वापरते, ज्यामुळे सातत्यपूर्ण वर्तन सुनिश्चित होते. v3.5.5+ वर अपडेट करा.

### WSL अंतर्गत MITM प्रॉक्सी: Windows होस्टवरील डेस्कटॉप अॅप्स इंटरसेप्ट होत नाहीत

**कारण:** MITM प्रॉक्सी आणि त्याचे CA प्रमाणपत्र OmniRoute ज्या वातावरणात चालते त्या वातावरणात इंस्टॉल होतात. WSL अंतर्गत ते वातावरण Linux गेस्ट असते, तर AI डेस्कटॉप अॅप्स (Kiro, Trae, Copilot, Zed, …) Windows होस्टवर चालतात. होस्ट अॅप्स गेस्टच्या प्रमाणपत्र स्टोअरवर विश्वास ठेवत नाहीत आणि गेस्टच्या सिस्टीम प्रॉक्सीद्वारे रूट होत नाहीत, त्यामुळे तेथे डेस्कटॉप इंटरसेप्शन सक्रिय होत नाही.

**शिफारस:** तुम्हाला इंटरसेप्ट करायची असलेली डेस्कटॉप अॅप्स ज्या OS वर चालतात त्याच OS वर OmniRoute मूळ स्वरूपात चालवा (Windows अॅप्ससाठी Windows; त्याचप्रमाणे macOS/Linux). होस्ट अॅप्सना लक्ष्य करताना OmniRoute हे WSL मध्येच ठेवायचे असल्यास, तयार केलेल्या CA प्रमाणपत्रावर Windows होस्टमध्ये व्यक्तिशः विश्वास स्थापित करावा लागेल आणि प्रत्येक होस्ट अॅपच्या नेटवर्क/प्रॉक्सी सेटिंग्जना WSL प्रॉक्सी एंडपॉइंटकडे निर्देशित करावे लागेल — हे असमर्थित आणि नाजूक सेटअप आहे.

## क्लाउड समस्या

### क्लाउड सिंक त्रुटी

1. `BASE_URL` तुमच्या चालू इन्स्टन्सकडे निर्देश करत असल्याची खात्री करा (उदा., `http://localhost:20128`)
2. `CLOUD_URL` तुमच्या क्लाउड एंडपॉइंटकडे निर्देश करत असल्याची खात्री करा (उदा., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` मूल्ये सर्व्हर-साइड मूल्यांशी सुसंगत ठेवा

### क्लाउडवर `stream=false` मुळे 500 प्रतिसाद मिळतो

**लक्षण:** नॉन-स्ट्रीमिंग कॉलसाठी क्लाउड एंडपॉइंटवर `Unexpected token 'd'...` दिसते.

**कारण:** क्लायंटला JSON अपेक्षित असताना अपस्ट्रीम SSE पेलोड परत करते.

**तात्पुरता उपाय:** क्लाउडवरील थेट कॉलसाठी `stream=true` वापरा. स्थानिक रनटाइममध्ये SSE→JSON फॉलबॅक समाविष्ट आहे.

### क्लाउड कनेक्ट झाल्याचे दाखवते, पण "Invalid API key" दिसते

1. स्थानिक डॅशबोर्डवरून (`/api/keys`) नवीन की तयार करा
2. क्लाउड सिंक चालवा: Enable Cloud → Sync Now
3. जुन्या किंवा सिंक न झालेल्या कीजसाठी क्लाउडवर अजूनही `401` प्रतिसाद मिळू शकतो

### Docker IPv6 / कनेक्शन रीसेट

<a name="docker-ipv6"></a>

**लक्षणे:** `curl http://localhost:20128/v1/models` चालवल्यावर `curl: (56) Recv failure: Connection reset by peer` प्रतिसाद मिळतो. डॅशबोर्ड आणि प्रमाणीकरणाची आवश्यकता नसलेले एंडपॉइंट कार्य करतात, पण प्रमाणीकरण आवश्यक असलेले एंडपॉइंट अयशस्वी होतात — हे प्रमाणीकरणाशी संबंधित समस्येसारखे दिसते, पण प्रत्यक्षात तसे नसते.

**कारण:** `docker run -p 20128:20128` हे `0.0.0.0` (IPv4) आणि `::` (IPv6) या दोन्हींवर प्रकाशित करते, पण कंटेनरमधील प्रोसेस फक्त IPv4 वर ऐकते. ज्या होस्टवर `localhost` प्रथम `::1` मध्ये रिझॉल्व्ह होते, तिथे कनेक्शन मागे कोणताही लिसनर नसलेल्या प्रकाशित IPv6 पोर्टवर पोहोचते → कनेक्शन रीसेट होते.

**निराकरण:**

1. **त्वरित निदान:** `curl -4 http://localhost:20128/v1/models` चालवा. ते `-4` सह कार्य करत असेल, पण त्याशिवाय अयशस्वी होत असेल, तर तुमच्याकडे IPv6 बाइंड विसंगती आहे.
2. **कायमस्वरूपी निराकरण:** तुमच्या `docker run` कमांडमध्ये `-p 127.0.0.1:20128:20128` वापरून स्पष्टपणे IPv4 शी बाइंड करा:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   यामुळे IPv4 बाइंड सक्तीने वापरले जाते आणि सर्व होस्ट इंटरफेसवर प्रॉक्सी उघडी होण्याचेही टाळले जाते.

## डीबगिंग

### लॉग फाइल्स सक्षम करा

तुमच्या `.env` फाइलमध्ये `APP_LOG_TO_FILE=true` सेट करा. ॲप्लिकेशन लॉग्स `logs/` अंतर्गत लिहिले जातात.
सेटिंग्जमध्ये कॉल लॉग पाइपलाइन सक्षम केलेली असताना विनंती आर्टिफॅक्ट्स `${DATA_DIR}/call_logs/` अंतर्गत संग्रहित केले जातात.
पाइपलाइन कॅप्चर सक्षम असताना, स्ट्रीम चंक पेलोड्स वगळण्यासाठी `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` सेट करा किंवा आर्टिफॅक्टची KB मधील मर्यादा बदलण्यासाठी `CALL_LOG_PIPELINE_MAX_SIZE_KB` समायोजित करा.

### प्रोव्हायडरची स्थिती तपासा

```bash
# हेल्थ डॅशबोर्ड
http://localhost:20128/dashboard/health

# API स्थिती तपासणी
curl http://localhost:20128/api/monitoring/health
```

### रनटाइम स्टोरेज

- मुख्य स्थिती: `${DATA_DIR}/storage.sqlite` (प्रोव्हायडर्स, कॉम्बोज, उपनावे, कीज, सेटिंग्ज)
- वापर: `storage.sqlite` मधील SQLite टेबल्स (`usage_history`, `call_logs`, `proxy_logs`) + पर्यायी `${DATA_DIR}/call_logs/`
- ॲप्लिकेशन लॉग्स: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` असताना)
- कॉल लॉग आर्टिफॅक्ट्स: कॉल लॉग पाइपलाइन सक्षम असताना `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs पृष्ठावरील **Clean history** क्रिया `call_logs`, जुने
`request_detail_logs` आणि स्थानिक `${DATA_DIR}/call_logs/` आर्टिफॅक्ट डायरेक्टरी साफ करते.

## सर्किट ब्रेकरच्या समस्या

### प्रदाता OPEN स्थितीत अडकला आहे

प्रदात्याचा सर्किट ब्रेकर OPEN असताना, कूलडाउन कालावधी संपेपर्यंत विनंत्या अवरोधित केल्या जातात.

**निराकरण:**

1. **डॅशबोर्ड → सेटिंग्ज → रेझिलियन्स** येथे जा
2. प्रभावित प्रदात्यासाठीचे सर्किट ब्रेकर कार्ड तपासा
3. सर्व ब्रेकर साफ करण्यासाठी **सर्व रीसेट करा** वर क्लिक करा किंवा कूलडाउन कालावधी संपेपर्यंत प्रतीक्षा करा
4. रीसेट करण्यापूर्वी प्रदाता प्रत्यक्षात उपलब्ध असल्याची खात्री करा

### प्रदाता वारंवार सर्किट ब्रेकर ट्रिगर करतो

एखादा प्रदाता वारंवार OPEN स्थितीत जात असल्यास:

1. अपयशाचा नमुना पाहण्यासाठी **डॅशबोर्ड → हेल्थ → प्रदाता हेल्थ** तपासा
2. **सेटिंग्ज → रेझिलियन्स → प्रदाता प्रोफाइल्स** येथे जा आणि अपयशाची मर्यादा वाढवा
3. प्रदात्याने API मर्यादा बदलल्या आहेत किंवा पुन्हा प्रमाणीकरण आवश्यक आहे का ते तपासा
4. लेटन्सी टेलीमेट्रीचे पुनरावलोकन करा — जास्त लेटन्सीमुळे टाइमआउट-आधारित अपयश येऊ शकते

- **GLM/ERNIE `system` भूमिका नाकारते** — v1.x मध्ये निराकरण केले आहे; विसंगत मॉडेल्ससाठी भूमिका नॉर्मलायझर सिस्टम संदेश आपोआप वापरकर्ता संदेशांमध्ये विलीन करतो. हे अजूनही v3.x+ वर दिसत असल्यास, कृपया समस्या नोंदवा.
- **`developer` भूमिका ओळखली जात नाही** — v1.x मध्ये निराकरण केले आहे; OpenAI व्यतिरिक्त इतर प्रदात्यांसाठी ती आपोआप `system` मध्ये रूपांतरित केली जाते. हे अजूनही v3.x+ वर दिसत असल्यास, कृपया समस्या नोंदवा.
- **`json_schema` Gemini सोबत कार्य करत नाही** — v1.x मध्ये निराकरण केले आहे; `response_format` आता Gemini च्या `responseMimeType` + `responseSchema` मध्ये रूपांतरित केले जाते. हे अजूनही v3.x+ वर दिसत असल्यास, कृपया समस्या नोंदवा.

### चॅट विनंत्या 503 / chat_admission_busy सह अयशस्वी होतात

**लक्षणे:**

- चॅट पूर्णता एंडपॉइंट पुन्हा प्रयत्न करता येण्याजोगा `503` प्रतिसाद परत करतो, ज्याचा त्रुटी कोड
  `chat_admission_busy` असतो.
- प्रतिसादात `Retry-After` समाविष्ट असते. #12135 पासून हे मूल्य निरीक्षण केलेल्या
  व्यापावरून निर्धारित केले जाते — विनंतीने आधीच प्रतीक्षा केलेली `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` वेळ-चौकट
  आणि सध्याचे हेवीवेट लीझ जितका काळ धरून ठेवले गेले आहेत तो कालावधी, यांपैकी जो मोठा असेल तो — पूर्ण
  सेकंदांपर्यंत वरच्या दिशेने पूर्णांकित करून आणि 60 वर मर्यादित केला जातो. निष्क्रिय गेटवर ऐतिहासिक किमान मर्यादा कायम राहतात:
  बाइट-आधारित मार्गावर 2 सेकंद, संरचना-आधारित मार्गावर 1 सेकंद (ज्यात
  `reason: "structure_limit"` देखील समाविष्ट असते).
- दुसरा हेवीवेट चॅट किंवा दीर्घकाळ चालणारा स्ट्रीमिंग प्रतिसाद अद्याप
  प्रक्रियेत असताना हे घडू शकते.

बाइट-आधारित प्रतिसादाचा मुख्य भाग असा आहे:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

संरचना-आधारित प्रतिसाद समान प्रकार आणि कोड वापरतो, त्यातील संदेश
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
आणि `reason: "structure_limit"` असतो.
डीफॉल्ट मर्यादांवर, विनंतीमध्ये किमान `200` संदेश,
किमान `64` साधने किंवा किमान `32,000` अंदाजित टोकन्स असतील, किंवा मर्यादित संरचना अंदाजाने
`10,000` भेट दिलेल्या नोड्सची किंवा `12` खोलीची मर्यादा संपवली असेल, तर ती विनंती संरचनात्मकदृष्ट्या हेवी असते.

**कारण:** हे OmniRoute मधील जाणीवपूर्वक लोड कमी करणे आहे, अपस्ट्रीम-प्रदाता अपयश नाही.
मोठ्या विनंतीचा मुख्य भाग राखून ठेवण्यापूर्वी आणि पार्स करण्यापूर्वी मर्यादित हेवीवेट क्षमता आरक्षित करण्यासाठी
प्रत्येक प्रक्रिया प्रक्रिया-स्थानिक गार्ड वापरते. SSE प्रतिसादाच्या संपूर्ण आयुष्यभर
हेवीवेट लीझ धरून ठेवले जाते.

**#503-फॅनआउट:** या सुधारणेपूर्वी, होस्ट मेमरी विचारात न घेता गार्ड समकालीनतेला विनंत्यांच्या निश्चित संख्येपर्यंत
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, डीफॉल्ट `1`) मर्यादित करत असे, त्यामुळे कोडिंग-एजंट
फॅनआउट (अनेक सबएजंट्स/CLIs, सामान्यतः > 256 KB आकाराचे मुख्य भाग) प्रभावी
समकालीनता ~1 पर्यंत कमी करत असे आणि पूर्णपणे सामान्य लोडमध्येही 503 त्रुटी निर्माण होत असत. आता गार्ड स्वतःला समायोजित
करतो: तो प्रक्रियेच्या वास्तविक मेमरी मर्यादेनुसार आकार दिलेल्या, स्वयंचलितपणे निर्धारित होणाऱ्या इनजेस्ट BYTE बजेटद्वारे
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) नियंत्रित होतो आणि प्रत्यक्ष संसाधन-दबाव सिग्नलचाही विचार करतो — त्यामुळे
एकाच वेळी एकापेक्षा जास्त हेवी विनंत्या आल्या म्हणून नव्हे, तर होस्टवर खरोखर मेमरीचा दबाव असतानाच
तो लोड कमी करतो. जुनी संख्या मर्यादा (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) अजूनही
पाळली जाते, परंतु केवळ तुम्ही ती स्पष्टपणे सेट केली असेल तर.

क्षमता व्यस्त असताना, पुन्हा प्रयत्न करता येण्याजोगे `503` उत्तर देण्यापूर्वी हेवीवेट विनंती स्लॉट रिकामा होण्यासाठी
प्रथम `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` पर्यंत (डीफॉल्ट `2000`, `0` प्रतीक्षा अक्षम करते) प्रतीक्षा करते.
ही मर्यादित प्रतीक्षा यासाठी अस्तित्वात आहे की समकालीनपणे हेवी उप-विनंत्या फॅनआउट करणारे एजंट-शैलीचे क्लायंट्स
(OpenCode, Claude Code, Cursor) तात्काळ नकारांवर त्यांचे संपूर्ण पुनःप्रयत्न बजेट खर्च करून कामाच्या मध्यात बंद पडण्याऐवजी
विनंत्यांचा अचानक आलेला लोंढा क्रमाने हाताळतील.
सध्याचा हेवीवेट लीझ वापर, निर्धारित बाइट बजेट आणि प्रत्यक्ष दबावाची तीव्रता
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) येथे दर्शवली जाते — कोणतेही env var बदलण्यापूर्वी हे तपासा.
सेटिंग्ज → लवचिकता → विनंती रांग → समकालीन विनंत्या यावर नियंत्रण ठेवत नाही; ती सेटिंग
स्वतंत्र प्रदाता विनंती-रांग यंत्रणा नियंत्रित करते.

**उपाय:**

1. प्रथम पुन्हा प्रयत्न करा. विनंती त्वरित
   पुन्हा पाठवण्याऐवजी क्लायंट्सनी `Retry-After` चे पालन करून बॅकऑफ वापरावा.
2. काहीही समायोजित करण्यापूर्वी `/api/monitoring/health` → `chatAdmission` तपासा. `countCapEnabled:
false` आणि उदार `maxInflightBytes` याचा अर्थ स्वयंचलितपणे निर्धारित बजेट आधीच त्याचे
   काम करत आहे; `high`/`critical` असलेले `pressureSeverity` याचा अर्थ होस्टकडे खरोखरच मेमरी कमी आहे —
   हे admission env var ने दुरुस्त होऊ शकत नाही; त्यासाठी अधिक RAM किंवा लहान वर्कलोड आवश्यक आहे.
3. `/api/monitoring/health` तुमच्या होस्टसाठी स्वयंचलितपणे निर्धारित बजेट खरोखरच खूप कमी असल्याचे
   दाखवत असेल तरच (हे दुर्मिळ आहे — ते आधीच कंटेनरपासून बेअर-मेटलपर्यंत स्केल होते), जुन्या विनंती-संख्या मर्यादेकडे परत जाण्याऐवजी
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` वापरून ते थेट ओव्हरराइड करा.

अधिकृत admission सेटिंग्जसाठी [पर्यावरण-चल संदर्भ](../reference/ENVIRONMENT.md#4-security--authentication)
पहा.

## पर्यायी RAG / LLM अपयश वर्गीकरण (16 समस्या)

काही OmniRoute वापरकर्ते RAG किंवा एजंट स्टॅकच्या पुढे गेटवे ठेवतात. अशा सेटअपमध्ये एक विचित्र पॅटर्न दिसणे सामान्य आहे: OmniRoute व्यवस्थित कार्यरत दिसते (प्रदाते उपलब्ध, रूटिंग प्रोफाइल योग्य, दरमर्यादेचे कोणतेही इशारे नाहीत), परंतु अंतिम उत्तर तरीही चुकीचे असते.

प्रत्यक्षात, अशा घटना सहसा गेटवेऐवजी डाउनस्ट्रीम RAG पाइपलाइनमुळे उद्भवतात.

त्या अपयशांचे वर्णन करण्यासाठी तुम्हाला सामायिक शब्दसंग्रह हवा असल्यास, तुम्ही WFGY ProblemMap वापरू शकता. हे MIT परवान्याअंतर्गत उपलब्ध असलेले बाह्य मजकूर संसाधन आहे, जे वारंवार उद्भवणाऱ्या सोळा RAG / LLM अपयश पॅटर्नची व्याख्या करते. व्यापक स्तरावर, त्यामध्ये पुढील गोष्टी समाविष्ट आहेत:

- पुनर्प्राप्तीतील विचलन आणि खंडित संदर्भ सीमा
- रिकामे किंवा कालबाह्य इंडेक्स आणि व्हेक्टर स्टोअर
- एम्बेडिंग आणि अर्थविषयक आशय यांच्यातील विसंगती
- प्रॉम्प्ट संयोजन आणि संदर्भ विंडोशी संबंधित समस्या
- तर्कशृंखलेचे अपयश आणि अतिआत्मविश्वासपूर्ण उत्तरे
- दीर्घ शृंखला आणि एजंट समन्वयातील अपयश
- एकाधिक एजंटमधील मेमरी आणि भूमिकेचे विचलन
- डिप्लॉयमेंट आणि बूटस्ट्रॅप क्रमाशी संबंधित समस्या

कल्पना सोपी आहे:

1. तुम्ही एखाद्या चुकीच्या प्रतिसादाची तपासणी करता तेव्हा, पुढील गोष्टी नोंदवा:
   - वापरकर्त्याचे कार्य आणि विनंती
   - OmniRoute मधील रूट किंवा प्रदाता संयोजन
   - डाउनस्ट्रीममध्ये वापरलेला कोणताही RAG संदर्भ (पुनर्प्राप्त केलेले दस्तऐवज, टूल कॉल इत्यादी)
2. घटनेला एक किंवा दोन WFGY ProblemMap क्रमांकांशी (`No.1` … `No.16`) जोडा.
3. OmniRoute लॉगच्या शेजारी तो क्रमांक तुमच्या स्वतःच्या डॅशबोर्ड, रनबुक किंवा घटना ट्रॅकरमध्ये संग्रहित करा.
4. तुम्हाला तुमचा RAG स्टॅक, रिट्रीव्हर किंवा रूटिंग धोरण बदलण्याची आवश्यकता आहे का हे ठरवण्यासाठी संबंधित WFGY पृष्ठ वापरा.

संपूर्ण मजकूर आणि ठोस कृतीपद्धती येथे उपलब्ध आहेत (MIT परवाना, केवळ मजकूर):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

तुम्ही OmniRoute च्या मागे RAG किंवा एजंट पाइपलाइन चालवत नसल्यास, हा विभाग दुर्लक्षित करू शकता.

## v3.8.0 मधील ज्ञात समस्या

v3.8.0 रिलीजशी संबंधित समस्या आणि त्यांच्यासाठी सध्या उपलब्ध असलेले उपाय. नंतरच्या पॅचमध्ये निराकरण उपलब्ध झाल्यास, संबंधित नोंद अद्ययावत केली जाईल किंवा काढून टाकली जाईल.

### Devin CLI प्रमाणीकरण अपयश

**लक्षणे:**

- Devin-आधारित टूल्स वापरताना "Devin CLI not found" किंवा "auth failed"
- CLI रनटाइम तपासणीत `installed=false` नोंदवले जाते

**कारणे:**

- `CLI_DEVIN_BIN` अस्तित्वात नसलेल्या पाथकडे निर्देश करते
- होस्टवर Devin CLI इंस्टॉल केलेले नाही

**निराकरण:**

1. तुमच्या प्लॅटफॉर्मसाठी Devin CLI इंस्टॉल करा
2. `.env` मध्ये `CLI_DEVIN_BIN=/usr/local/bin/devin` (किंवा वास्तविक पाथ) सेट करा
3. OmniRoute रीस्टार्ट करा आणि **Dashboard → CLI Tools** मधून पुन्हा चाचणी करा

### मॉडेल कूलडाउन अडकलेले आहे (मॅन्युअल रीसेट)

**लक्षणे:**

- कालबाह्यता वेळ निघून गेल्यानंतरही एखादे मॉडेल कूलडाउनमध्ये असल्याचे दाखवले जाते
- टाइमस्टॅम्प भूतकाळातील असूनही कॉम्बो रूटिंगमधील विनंत्या त्या मॉडेलला वगळतात

**मॅन्युअल रीसेट:**

- **डॅशबोर्ड:** **Settings → Model Cooldowns** → प्रभावित कार्डवरील **Re-enable** वर क्लिक करा
- **API:** व्यवस्थापन प्रमाणीकरण हेडरसह `DELETE /api/resilience/model-cooldowns`

### Command Code प्रदाता कनेक्शन 403 सह अपयशी होते

**लक्षणे:**

- Command Code प्रदाता कनेक्शनची चाचणी करताना 403
- नव्याने जोडल्यानंतर प्रदाता कार्डवर "unauthorized" दिसते

**कारण:** OAuth प्रक्रिया पूर्ण झाली नाही (कॉलबॅक प्राप्त झाला नाही किंवा टोकन कायमस्वरूपी जतन झाले नाही).

**निराकरण:**

- OAuth प्रक्रिया पुन्हा सुरू करण्यासाठी CLI मधून `omniroute providers` चालवा, किंवा
- **Dashboard → Providers → Command Code → Reconnect** मधून OAuth पुन्हा चालवा

### ModelScope अतिआक्रमक 429 कूलडाउन परत करते

**लक्षणे:**

- विनंत्यांच्या छोट्या बर्स्टनंतर ModelScope वर अतिशय लहान किंवा त्वरित कूलडाउन
- कॉम्बो रूटिंग अपेक्षेपेक्षा लवकर ModelScope वगळते

**कारण:** ModelScope प्रदाता-विशिष्ट `Retry-After` हेडर पाठवते. v3.8.0 मध्ये त्या हेडरसाठी स्वतंत्र हाताळणी समाविष्ट आहे, त्यामुळे जुन्या आवृत्त्या त्यांचा सामान्य दरमर्यादा संकेत म्हणून चुकीचा अर्थ लावतात.

**निराकरण:**

- तुम्ही v3.8.0 किंवा त्यानंतरची आवृत्ती वापरत असल्याची खात्री करा
- **Settings → Resilience** अंतर्गत `useUpstream429BreakerHints` टॉगल सक्षम असल्याची खात्री करा

### उत्पादन वातावरणात OMNIROUTE_WS_BRIDGE_SECRET उपलब्ध नाही

**लक्षणे:**

- रिमोट उत्पादन होस्टवर चालवताना प्रत्येक Codex/Responses WebSocket ब्रिज विनंतीवर 401
- कनेक्ट झाल्यानंतर WebSocket ब्रिज हँडशेक त्वरित बंद होते

**कारण:** उत्पादन वातावरणातून `OMNIROUTE_WS_BRIDGE_SECRET` पर्यावरण चल उपलब्ध नाही.

**निराकरण:**

1. यादृच्छिक सीक्रेट निर्माण करा: `openssl rand -hex 32`
2. उत्पादन सर्व्हरच्या वातावरणात (आणि ब्रिजशी संवाद साधणाऱ्या कोणत्याही क्लायंटमध्ये) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` सेट करा
3. OmniRoute रीस्टार्ट करा

### Responses API: पार्श्वभूमी मोड सिंक्रोनस मोडमध्ये अवनत केला जातो

**लक्षणे:**

- लॉग केलेला इशारा: `background mode degraded to synchronous`
- `background: true` विनंती पार्श्वभूमी जॉब हँडलऐवजी सामान्य सिंक्रोनस प्रतिसाद परत करते

**कारण:** v3.8.0 मध्ये Responses API वरील `background: true` हेतुपुरस्सर सिंक्रोनस अंमलबजावणीत अवनत केले जाते आणि त्याच वेळी इशारा दिला जातो. पूर्णपणे असिंक्रोनस पार्श्वभूमी अंमलबजावणी भविष्यात उपलब्ध केली जाईल.

**निराकरण:**

- `background` शिवाय कॉल करण्यासाठी क्लायंट समायोजित करा, किंवा
- पूर्ण असिंक्रोनस पार्श्वभूमी मोड समाविष्ट असलेल्या नंतरच्या रिलीजची प्रतीक्षा करा (बदलनोंदीनुसार प्रगती तपासा)

## धीमे स्टार्टअप / तत्परता कालबाह्यता

CLI मध्ये `⚠ सर्व्हरने 60s च्या आत प्रतिसाद दिला नाही` असा संदेश दिसत असल्यास, परंतु सर्व्हर प्रत्यक्षात कार्यरत असल्यास, तुमच्या वातावरणासाठी तत्परता तपासणीची कालमर्यादा खूप कमी आहे.

हे सामान्यतः Windows वर (अँटीव्हायरस, फाइलसिस्टम वॉचर्स) किंवा स्टार्टअपच्या वेळी जास्त कार्यभार असलेल्या कंटेनर्समध्ये घडते.

**उपाय — कालमर्यादा वाढवा:**

```bash
# पर्यावरण चलाद्वारे (पुढील स्टार्ट्ससाठीही कायम राहते):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 मिनिटे
omniroute serve

# CLI फ्लॅगद्वारे (केवळ एकदाच):
omniroute serve --ready-timeout 180000
```

डीफॉल्ट कालमर्यादा 60 000 ms (60 s) आहे. ही चेतावणी केवळ माहितीपर आहे; सर्व्हर बॅकग्राउंडमध्ये सुरू होत राहतो आणि बूट पूर्ण झाल्यानंतर उपलब्ध होईल.

`OMNIROUTE_READY_TIMEOUT_MS` विषयी संपूर्ण तपशीलांसाठी [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) पहा.
