**OmniRoute प्रथमच वापरत आहात?** येथून सुरुवात करा — यामुळे 90% समस्यांचे निराकरण होते:

| मला हे दिसते                 | याचा अर्थ                                             | काय करावे                                                                                                      |
| ---------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| "कनेक्ट करता येत नाही"       | OmniRoute चालू नाही                                   | `omniroute` किंवा `docker restart omniroute` चालवा                                                             |
| "अवैध API key"               | तुमची key चुकीची आहे किंवा कालबाह्य झाली आहे          | प्रदात्याच्या वेबसाइटवरून key पुन्हा कॉपी करा                                                                  |
| "दरमर्यादा ओलांडली"          | तुम्ही खूप जास्त विनंत्या पाठवत आहात                  | 1 मिनिट प्रतीक्षा करा किंवा स्वयंचलित fallback साठी `model: "auto"` वापरा                                      |
| "कोटा ओलांडला"               | तुम्ही तुमचा मोफत/सशुल्क कोटा पूर्णपणे वापरला आहे     | आणखी प्रदाते कनेक्ट करा किंवा मोफत प्रदाते (Kiro, Pollinations) वापरा                                          |

| "चुकीचा प्रदाता वापरला गेला" | `auto` ने वेगळा प्रदाता निवडला                        | हे सामान्य आहे! `auto` सर्वोत्तम प्रदाता निवडते. `model: "openai/gpt-4o"` वापरून विशिष्ट प्रदाता सक्तीने निवडा |

| "401 Unauthorized"           | तुमची प्रमाणीकरण माहिती चुकीची आहे                    | तुमची API key तपासा किंवा OAuth द्वारे पुन्हा प्रमाणीकरण करा                                                   |
| "omniroute ओळखले जात नाही"   | Windows PATH मध्ये global node modules समाविष्ट नाहीत | तुमचा npm global prefix Windows PATH मध्ये जोडा. तो शोधण्यासाठी `npm config get prefix` वापरा.                 |

## तपशीलवार समस्या निवारण

---

### मोफत प्रदात्यांवरील दरमर्यादा (429 / 400 / 401)

**लक्षण**: मोफत/प्रमाणीकरणाची आवश्यकता नसलेले प्रदाते (opencode, auggie इत्यादी) यांच्यासह `model: "auto"` वापरताना, तुम्हाला अधूनमधून उत्तरांऐवजी `HTTP 429`, `400` किंवा `401` मिळते. काही क्षणांनंतर त्याच prompt चा पुन्हा प्रयत्न केल्यावर विनंत्या यशस्वी होतात, परंतु पहिल्या अपयशामुळे स्वयंचलन (cron jobs, agents, scripts) खंडित होते.

**मूळ कारण**: अपयशाचे तीन स्वतंत्र प्रकार एकत्रितपणे परिणाम करतात:

1. **प्रदात्याची दरमर्यादा (`429`)**: मोफत श्रेणी प्रत्येक कालावधीसाठी कोटा लागू करू शकते. समांतर calls च्या अचानक झालेल्या वाढीमुळे तो संपतो, त्यामुळे कालावधी रीसेट होईपर्यंत पुढील विनंती नाकारली जाते.
2. **passthrough मधील बिघडलेले model (`400`/`401`)**: `auto/*` pools मध्ये `opencode` कडील passthrough models समाविष्ट असू शकतात, जे catalog मध्ये नोंदणीकृत असतात परंतु त्यांच्याकडे सक्रिय credentials नसतात (उदा. `oc/north-mini-code-free` → `401`). auto-router त्यांपैकी एक वापरून पाहतो, तो प्रयत्न अयशस्वी होतो आणि fallback सुरू होण्यापूर्वीच त्रुटी पुढे पाठवली जाते.
3. **समवर्तीपणामुळे होणारी वाढ (`429` लोड अंतर्गत)**: अनेक agent/cron sessions एकाच वेळी `auto` वापरतात तेव्हा, एकत्रित विनंती-दर मोफत प्रदात्यांना सहन होणाऱ्या मर्यादेपेक्षा अधिक होतो, त्यामुळे वैध calls देखील गैरवापर म्हणून चिन्हांकित होतात.

**सत्यापित उपाय (समुदायाने नोंदवलेला, 2026-08-10)**: rotation, concurrency आणि fallback हे मोफत श्रेणीतील अस्थिरता हाताळतील व तिच्यामुळे प्रक्रिया बंद पडणार नाही, अशा प्रकारे तीन environment variables समायोजित करा:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 आल्यावर दुसऱ्या model/provider कडे जा (बिघडलेले passthrough models वगळते)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # heavyweight प्रवेशाची स्पष्ट कमाल मर्यादा (डीफॉल्टनुसार unset: विनंती-संख्येवर मर्यादा नाही, खालील नोंद पहा)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # संथ upstreams साठी मर्यादित प्रतीक्षा RATE_LIMIT_MAX_WAIT_MS च्या डीफॉल्टपेक्षा वाढवा
```

ही OmniRoute process environment मध्ये (daemon मध्ये, उदा. LaunchAgent plist किंवा `systemctl edit` द्वारे) सेट करा आणि नंतर OmniRoute रीस्टार्ट करा. rotation flag हा सर्वाधिक परिणामकारक उपाय आहे: तो गंभीर अपयशाचे pool मधील कार्यरत प्रदात्याविरुद्ध पारदर्शक रीट्रायमध्ये रूपांतर करतो.

**नोंद**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` एकाच वेळी किती heavyweight — दीर्घ-context — विनंत्या चालू शकतात यावर मर्यादा घालते; ही मर्यादा एक admission gate आहे, प्रदात्याची दरमर्यादा नाही. **#503-fanout अद्यतन:** हे var आता डीफॉल्टनुसार सेट केले जात नाही (आता ते केवळ वर दाखवल्याप्रमाणे स्पष्टपणे configure केल्यावरच लागू होते) — त्याऐवजी heavyweight admission हे आपोआप निर्धारित होणाऱ्या byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) द्वारे नियंत्रित केले जाते, जे host च्या वास्तविक memory ceiling नुसार स्वतःला समायोजित करते. त्यामुळे नवीन deployment मध्ये हे var अजिबात सेट न करताही `503 chat_admission_busy` नकारांची संख्या लक्षणीयरीत्या कमी असायला हवी; ते येथे स्पष्टपणे सेट करणे अजूनही दस्तऐवजात वर्णन केल्याप्रमाणेच कार्य करते. स्पष्ट byte-budget overrides 8 MiB–2 GiB या मर्यादेत ठेवले जातात. `413 body_exceeds_budget` तात्पुरते नाही: तो byte budget वाढवा, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` कमी करा किंवा process memory ceiling वाढवा. `inflight_bytes_budget` shed ही तात्पुरती स्पर्धा आहे आणि तिच्यासाठी पुन्हा प्रयत्न करता येतो. प्रत्येक प्रदात्याची दरमर्यादा (`open-sse/services/rateLimitManager.ts`) स्वतंत्रपणे `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` आणि `RATE_LIMIT_AUTO_ENABLE` द्वारे नियंत्रित केली जाते — `.env.example` पहा.

**ते कार्यरत असल्याची पडताळणी कशी करावी**: तुमचा एजंट/cron सलग दोनदा त्वरित चालवा आणि दोन्ही वेळा ते यशस्वी झाल्याची खात्री करा. दुरुस्तीपूर्वी, दुसऱ्या रनमध्ये सामान्यतः `429`/`401` त्रुटी येते. दुरुस्तीनंतर, अपयशांचा (असल्यास) पारदर्शकपणे पुनर्प्रयत्न केला जातो आणि कॉल पूर्ण होतो. तुम्ही `curl /monitoring/health` देखील वापरू शकता आणि प्रोव्हायडर कनेक्शन्सवरील `rateLimitedUntil` फील्ड तसेच प्रभावित प्रोव्हायडर्ससाठी `circuitBreakers.providerBreakers[].state` पाहू शकता — स्थिती `CLOSED`, `DEGRADED`, `OPEN`, किंवा `HALF_OPEN` यांपैकी एक असते (`src/shared/utils/circuitBreaker.ts` पाहा), आणि सतत अपयशी होणारा प्रोव्हायडर रीसेट विंडोमधून प्रोबला जाऊ देण्यापूर्वी `CLOSED → DEGRADED → OPEN` असा बदलेल (`HALF_OPEN`).

**तुम्हाला अजूनही 429 दिसत असल्यास**: त्या प्रोव्हायडरसाठी सक्रिय खात्याचा _कोटा_ खरोखरच संपला आहे (केवळ रेट मर्यादा गाठलेली नाही). OmniRoute डॅशबोर्ड → Providers → Accounts मध्ये त्याच प्रोव्हायडरसाठी दुसरे खाते जोडा किंवा आणखी एखादा मोफत प्रोव्हायडर समाविष्ट करा (उदा. `routeway`, `auggie`). रोटेशन केवळ तात्पुरत्या रेट/400/401 समस्यांमध्ये उपयुक्त ठरते; कोटा पूर्णपणे संपल्यास दुसरे क्रेडेन्शियल किंवा वेगळा प्रोव्हायडर आवश्यक असतो.

**व्हिजन मॉडेल्सवर (`auto/vision`, `bazaarlink/*`) तुम्हाला 403 दिसत असल्यास**: कनेक्ट केलेल्या खात्याकडे व्हिजनचा समावेश असलेला सशुल्क प्लॅन नाही किंवा API कीला पुरेशा परवानग्या नाहीत. कीच्या स्कोपमध्ये व्हिजन/मल्टिमोडलचा समावेश असल्याची प्रोव्हायडर डॅशबोर्डमध्ये पडताळणी करा किंवा सशुल्क टियरचे खाते कनेक्ट करून ते व्हिजन टार्गेट म्हणून ठेवा.

## npm install चेतावण्या (ERESOLVE / peer / deprecated)

तुम्ही `npm install -g omniroute` चालवता तेव्हा तुम्हाला `npm warn ERESOLVE`, peer-dependency सूचना आणि `deprecated` संदेश अशा अनेक चेतावण्या दिसू शकतात. **या अपेक्षित आणि निरुपद्रवी आहेत.** आउटपुटमध्ये `added <N> packages` दिसल्यास तुमची स्थापना यशस्वी झाली आहे.

peer-dependency निराकरणासंबंधी चेतावण्या दडपण्यासाठी OmniRoute चे समर्थित स्थापना स्वरूप वापरा:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` केवळ `ERESOLVE` आणि peer-dependency सूचना दडपते. कालबाह्यतेच्या सूचना दृश्यमान राहतात, कारण त्या transitive तृतीय-पक्षीय packages मधून येतात; त्यांचा अर्थ स्थापना अयशस्वी झाली असा होत नाही.

या चेतावण्या OmniRoute च्या नियंत्रणाबाहेरील तृतीय-पक्षीय packages मधील कालबाह्य peer-dependency ranges मुळे येतात:

1. **`marked-terminal` ला `marked >=1 <16` हवे आहे, परंतु `marked@18` आढळले** — प्रत्यक्ष वापरात हे व्यवस्थित कार्य करते; upstream peer range फक्त कालबाह्य आहे.
2. **`deprecated prebuild-install@7.1.3`** — हा transitive native-binary fetch helper आहे. pinned `wreq-js` transport binding स्थापित करण्यासाठी तो
   वापरला जात नाही आणि web-cookie provider transport चे सेटअप अयशस्वी झाल्याचे तो दर्शवत नाही.

**कोणतीही कृती आवश्यक नाही** — upstream packages fork केल्याशिवाय या चेतावण्या पूर्णपणे दडपता येत नाहीत.

## npm install-scripts अवरोधित केल्याची चेतावणी (global install)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` चालवताना, npm च्या नवीन आवृत्त्या (v11+ आणि v12+) package lifecycle scripts डीफॉल्टनुसार अवरोधित करतात आणि install-scripts चेतावणी दाखवतात:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### या चेतावणीकडे दुर्लक्ष करता येईल का?

**अंशतः, परंतु scripts शिवाय चालवण्याची शिफारस केली जात नाही.** OmniRoute मध्ये सुरक्षित पर्यायी व्यवस्था समाविष्ट आहेत: standalone bundle मधून native `better-sqlite3` bindings लोड करता आली नाहीत, तर application `node:sqlite` किंवा `sql.js` सारख्या पर्यायी drivers कडे वळते ([SQLite Runtime Resolution](../ops/SQLITE_RUNTIME.md) पहा). Server तरीही सुरू होईल, परंतु `sql.js` सारख्या WASM पर्यायांवर चालवल्यास SQLite WAL (Write-Ahead Logging) mode अक्षम होतो आणि memory व disk-sync वरील अतिरिक्त भार वाढतो.

### प्रत्यक्षात कोणते scripts आवश्यक आहेत?

OmniRoute चालवण्यासाठी सर्व अवरोधित scripts आवश्यक नाहीत:

- **अत्यावश्यक (`omniroute`, `better-sqlite3`):** OmniRoute हे Next.js standalone application bundle (`dist/`) मधून चालते. स्थापनेदरम्यान, npm शीर्ष-स्तरीय `node_modules/better-sqlite3/` मध्ये host-specific native SQLite driver डाउनलोड किंवा compile करते. त्यानंतर OmniRoute चे `postinstall` script (`scripts/build/postinstall.mjs`) या host-specific binaries ची पडताळणी करून त्यांना `dist/node_modules/` मध्ये copy करते, जेणेकरून standalone server त्यांचा वापर करू शकेल. `omniroute` चे postinstall script अवरोधित असल्यास, ही copy करण्याची पायरी वगळली जाते.
- **पर्यायी/transitive (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** हे build helpers, watcher tools किंवा system keychain utilities आहेत. त्यांना अनुमती दिल्यास build warnings टाळता येतात, परंतु core routing कार्यक्षमतेसाठी ते आवश्यक नाहीत.
- **वगळलेले (`onnxruntime-node`):** हे local AI embeddings साठीचे पर्यायी dependency आहे आणि OmniRoute चालवण्यासाठी **आवश्यक नाही**. त्याचे postinstall script NuGet वरून सुमारे 300MB CUDA assets डाउनलोड करते; समर्थित hardware वर local ONNX acceleration वापरण्याचा तुमचा स्पष्ट हेतू नसल्यास ते allow-list मध्ये समाविष्ट करू नका.

### शिफारस केलेला उपाय

global install दरम्यान आवश्यक install scripts ना अनुमती देण्यासाठी आणि चेतावण्या दडपण्यासाठी OmniRoute व त्याच्या native dependencies साठी `--allow-scripts` द्या:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

पर्यायाने, तुमच्या user account वरील सर्व global installations साठी हे कायमस्वरूपी configure करण्यासाठी:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### तुमच्या स्थापनेची पडताळणी करा

स्थापनेनंतर, native bindings आणि runtime environment योग्य स्थितीत असल्याची खात्री करण्यासाठी अंगभूत diagnostic tool चालवा:

```bash
omniroute doctor
```

## Gemini Web आणि Playwright Chromium

Gemini Web विनंतीने Playwright Chromium इंस्टॉल केलेले नसल्याचा संदेश देत `503` प्रतिसाद दिल्यास, npm पॅकेज उपलब्ध आहे, परंतु ब्राउझर बायनरी उपलब्ध नाही.
Playwright जाणीवपूर्वक ब्राउझर डाउनलोड npm पॅकेजच्या
इंस्टॉलेशनपासून वेगळे ठेवते, त्यामुळे ब्राउझर इंस्टॉल होईपर्यंत हा प्रतिसाद अपेक्षित आहे.

जागतिक npm इंस्टॉलेशनसाठी, OmniRoute पॅकेजच्या
डिरेक्टरीमधून Chromium इंस्टॉल करा, जेणेकरून ब्राउझर कॅश त्याच Playwright इंस्टॉलेशनशी संबंधित राहील:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

इंस्टॉलेशननंतर OmniRoute रीस्टार्ट करा आणि मग Gemini Web विनंतीचा पुन्हा प्रयत्न करा. तुम्ही
Docker इमेजमधून OmniRoute चालवत असल्यास, Chromium आणि त्याच्या अवलंबिता समाविष्ट असलेली `-web` इमेज (किंवा `runner-web`
बिल्ड लक्ष्य) वापरा; बेस इमेजमध्ये
त्या समाविष्ट नाहीत.

## अँटीव्हायरसचे खोटे सकारात्मक निष्कर्ष

<a name="antivirus-false-positives"></a>

### Avast/AVG कडून `README.md` ला `MD:HttpRequest-inf[Susp]` म्हणून क्वारंटाइन केले जाते

**हा खोटा सकारात्मक निष्कर्ष आहे. कशालाही संसर्ग झालेला नाही आणि कोणतीही कृती आवश्यक नाही.**

Avast आणि AVG अशा ह्युरिस्टिकचा वापर करतात, जी अनेक HTTP-विनंतीसारख्या दिसणाऱ्या लिंक्स असलेल्या साध्या-मजकूर/Markdown फायलींना धोकादायक म्हणून चिन्हांकित करते. OmniRoute ची `README.md` फाइल npm पॅकेजमध्ये समाविष्ट असते (ती `package.json` → `files` मध्ये सूचीबद्ध आहे), त्यामुळे जागतिक इन्स्टॉलमध्ये ती `node_modules/omniroute/README.md` येथे ठेवली जाते — आणि तिच्यात सुमारे 15 `http://localhost:20128/...` उदाहरणे आहेत (MCP HTTP/SSE एंडपॉइंट्स, A2A `.well-known` URL आणि `curl` स्निपेट्स). लिंक्सची ही घनता ह्युरिस्टिक सक्रिय होण्यासाठी पुरेशी आहे.

हे केवळ अलीकडेच सुरू झाले असल्यास: फाइलच्या स्वरूपात बदल झालेला नाही. README मधील एंडपॉइंट्सचे टेबल वाढले (MCP HTTP + SSE + A2A जोडले गेले) आणि अधिक `curl` उदाहरणे समाविष्ट झाली, ज्यामुळे ते निर्धारित मर्यादेपलीकडे गेले.

ही शून्य एक्झिक्युटेबल सामग्री असलेली निष्क्रिय दस्तऐवजीकरण फाइल आहे. तुम्ही ती क्वारंटाइनमधून सुरक्षितपणे पुनर्संचयित करू शकता.

**काय करावे:**

1. **सूचना थांबवा** — तुमच्या अँटीव्हायरसमध्ये इन्स्टॉल डिरेक्टरी वगळा
   (Avast: Settings → Exceptions), त्यात तुमचा जागतिक `node_modules` पाथ आणि/किंवा
   OmniRoute डेटा डिरेक्टरी (`~/.omniroute/`) जोडा.
2. **खोट्या सकारात्मक निष्कर्षाचा अहवाल द्या** — <https://www.avast.com/false-positive-file-form.php>,
   आणि क्वारंटाइन केलेली `README.md` संलग्न करा. यामुळे सर्वांना मदत होईल, कारण विक्रेत्याची
   ह्युरिस्टिक एका मजकूर फाइलवर अतिप्रतिक्रिया करत आहे.

**आम्ही आमच्या बाजूने हे "दुरुस्त" का करत नाही:** सर्व उदाहरणे `http://localhost` आहेत आणि
स्व-स्वाक्षरीकृत प्रमाणपत्रांच्या अडचणींशिवाय localhost साठी `https` वापरता येत नाही. एका
विक्रेत्याच्या ह्युरिस्टिकला चुकवण्यासाठी दस्तऐवजांची मोडतोड केल्यास स्कॅनरमधील बगचे समाधान
करण्यासाठी प्रत्येक वाचकाचे नुकसान होईल.

### Kaspersky कडून Desktop अॅपला `PDM:Trojan.Win32.Generic` म्हणून चिन्हांकित केले जाते

**हा वर्तनात्मक ह्युरिस्टिकमधून आलेला खोटा सकारात्मक निष्कर्ष आहे. कशालाही संसर्ग झालेला नाही.** Kaspersky चा
`PDM:` उपसर्ग दर्शवतो की हा निकाल त्याच्या Proactive Defense Module (System Watcher) मधून आला आहे,
जे इन्स्टॉलरला ज्ञात मालवेअरशी जुळवण्याऐवजी तो _काय करतो_ याचे मूल्यमापन करते. हे सक्रिय झाल्यावर
Kaspersky संपूर्ण इन्स्टॉलेशन "रोल बॅक" करते — आधीच लिहिलेल्या फायली हटवते — त्यामुळे अॅप
बिघडलेल्या स्थितीत राहते किंवा पूर्णपणे गायब होते.

त्याद्वारे चिन्हांकित केलेल्या फायली या Desktop अॅपसोबत बंडल केलेल्या घोषित, ओपन-सोर्स
अवलंबनांचे प्रमाणित भाग आहेत, उदाहरणार्थ:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` आणि
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), अॅपमधील प्रदाता लॉगिन आणि
  ब्राउझर-आधारित चॅटसाठी वापरली जाणारी ब्राउझर-ऑटोमेशन लायब्ररी.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — वेब-कुकी प्रदात्यांवर ब्राउझर-फिंगरप्रिंटेड HTTP साठी वापरले जाणारे पिन केलेले `wreq-js`
  नेटिव्ह बाइंडिंग (`<arch>` हे `x64` किंवा `arm64` असते).

**हे सक्रिय का होते:** Windows इन्स्टॉलर **अद्याप कोड-साइन केलेला नाही**, त्यामुळे स्वाक्षरी नसलेल्या NSIS
इन्स्टॉलरची प्रतिष्ठा शून्य असते आणि वर्तनात्मक ह्युरिस्टिक्स कमाल आक्रमकतेने चालतात. त्यासोबत
बंडल केलेली नेटिव्ह DLL आणि `%LOCALAPPDATA%\Programs\OmniRoute` अंतर्गत लिहिलेल्या शेकडो `.js`
फायली (Next.js स्वतंत्र बिल्डमधील हॅश-प्रत्यय असलेल्या पॅकेज डिरेक्टरींसह) ह्युरिस्टिक सक्रिय
होण्यासाठी पुरेशा आहेत. कोड साइनिंग नियोजित आहे; ते लागू होईपर्यंत नवीन रिलीजमध्ये हे पुन्हा होऊ शकते.

**काय करावे:**

1. **प्रथम तुमच्या डाउनलोडची पडताळणी करा** (यामुळे फाइलमध्ये छेडछाड झाल्याची शक्यता नाकारता येते). प्रत्येक रिलीजमध्ये
   `latest.yml` प्रकाशित होते, ज्यातील `sha512` फील्ड (base64) `OmniRoute.Setup.<version>.exe`
   इन्स्टॉलरला कव्हर करते. PowerShell मध्ये, इन्स्टॉलर असलेल्या फोल्डरमधून:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   आउटपुट `latest.yml` → `sha512` शी जुळले पाहिजे. तसे नसल्यास, फाइल हटवा आणि केवळ
   [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) वरून पुन्हा डाउनलोड करा.
2. **पुनर्संचयित करा + वगळा** — रोल बॅक केलेले घटक क्वारंटाइनमधून पुनर्संचयित करा आणि
   `%LOCALAPPDATA%\Programs\OmniRoute` साठी अपवाद जोडा (Kaspersky → Settings → Threats and Exclusions),
   त्यानंतर पुन्हा इन्स्टॉल करा.
3. **खोट्या सकारात्मक निष्कर्षाचा अहवाल द्या** — <https://opentip.kaspersky.com/>. वापरकर्त्यांनी सादर केलेले FP
   अहवाल खरोखरच अनुमत-सूचीत समावेश करण्याची प्रक्रिया वेगवान करतात.

## Node.js सुसंगतता

<a name="nodejs-compatibility"></a>

### लॉगिन पृष्ठ क्रॅश होते किंवा "Module self-registration" त्रुटी दाखवते

**कारण:** तुम्ही OmniRoute च्या मान्यताप्राप्त सुरक्षित रनटाइमच्या किमान मर्यादेबाहेरील Node.js आवृत्ती चालवत आहात. याचे सर्वात सामान्य उदाहरण म्हणजे OmniRoute ला आवश्यक असलेल्या पॅच केलेल्या सुरक्षा मर्यादेपेक्षा जुनी असलेली Node 22 किंवा 24 ची पॅच आवृत्ती चालवणे.

**लक्षणे:**

- लॉगिन पृष्ठावर रिकामी स्क्रीन किंवा सर्व्हर त्रुटी दिसते
- कन्सोलमध्ये `Error: Module did not self-register` किंवा तत्सम नेटिव्ह बाइंडिंग त्रुटी दिसतात
- रनटाइम समर्थित सुरक्षित धोरणाच्या बाहेर असल्यास लॉगिन पृष्ठावर तुमच्या Node आवृत्तीसह **नारिंगी चेतावणी बॅनर** दिसतो

**उपाय:**

1. समर्थित Node.js LTS रिलीज स्थापित करा (शिफारस केलेले: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. तुमची आवृत्ती तपासा: `node --version` ने 24.x LTS शाखेवरील `v24.0.0` किंवा त्याहून नवीन आवृत्ती दाखवली पाहिजे
3. OmniRoute पुन्हा स्थापित करा: `npm install -g omniroute`
4. रीस्टार्ट करा: `omniroute`

> **समर्थित सुरक्षित आवृत्त्या:** `>=22.22.2 <23` किंवा `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) आणि Node.js 26 पूर्णपणे समर्थित आहेत.

### npm v11+: `better-sqlite3` स्थापित झालेले नाही (मॉड्यूल सापडत नाही)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**कारण:** npm v11 (Node.js 24+ सोबत वितरित केलेले) डीफॉल्टनुसार पर्यायी
अवलंबनांसाठी इंस्टॉल स्क्रिप्ट ब्लॉक करते. `better-sqlite3` हे `optionalDependencies`
मध्ये सूचीबद्ध असल्यामुळे आणि त्यासाठी नेटिव्ह कंपाइलेशन (`node-gyp rebuild`) आवश्यक असल्यामुळे, npm त्याकडे कोणतीही सूचना न देता दुर्लक्ष करते.

**लक्षणे:**

- सर्व्हर सुरू होताना `Cannot find module 'better-sqlite3'` त्रुटीसह क्रॅश होतो
- `ls node_modules/better-sqlite3` हे "No such file or directory" दाखवते
- `npm ls better-sqlite3` हे `(empty)` दाखवते

**उपाय:**

1. इंस्टॉल स्क्रिप्टना मान्यता द्या आणि पुन्हा स्थापित करा:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. किंवा आधीच बिल्ड केलेले पॅकेज स्वतः स्थापित करा:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ते कार्य करते याची खात्री करा: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**कारण:** जागतिक स्तरावर `npm install -g omniroute` चालवल्यानंतर, पॅकेजमधील `better-sqlite3` नेटिव्ह बायनरी स्थानिक पातळीवर चालू असलेल्या आर्किटेक्चर किंवा Node.js ABI पेक्षा वेगळ्या आर्किटेक्चर किंवा ABI साठी कंपाइल केलेली असू शकते. आधीच बिल्ड केलेली बायनरी तुमच्या वातावरणाशी जुळत नसल्यास macOS वर (Apple Silicon आणि Intel या दोन्हींवर) हे सामान्यपणे घडते.

**लक्षणे:**

- सर्व्हर सुरू होताच `dlopen` त्रुटीसह अपयशी ठरतो
- त्रुटीमध्ये `slice is not valid mach-o file` असते
- संपूर्ण उदाहरण:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**उपाय — तुमच्या स्थानिक वातावरणासाठी पुन्हा बिल्ड करा (Node.js डाउनग्रेड करण्याची आवश्यकता नाही):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **टीप:** यामुळे नेटिव्ह बाइंडिंग तुमच्या स्थानिक Node.js आवृत्ती आणि CPU आर्किटेक्चरनुसार पुन्हा कंपाइल होते व बायनरीमधील विसंगती दूर होते. अधिकृतपणे समर्थित रनटाइम श्रेणी **`>=22.22.2 <23` किंवा `>=24.0.0 <27`** आहे (`src/shared/utils/nodeRuntimeSupport.ts` मधील `SUPPORTED_NODE_RANGE`, `package.json` मधील `engines` फील्डशी सुसंगत). Node.js 24.x LTS (Krypton) आणि Node.js 26 हे `better-sqlite3` v12.x सह पूर्णपणे समर्थित आहेत.

## प्रॉक्सी समस्या

<a name="proxy-issues"></a>

### प्रदाता प्रमाणीकरणात "fetch failed" दिसते

**कारण:** API की प्रमाणीकरण एंडपॉइंट (`POST /api/providers/validate`) पूर्वी प्रॉक्सी कॉन्फिगरेशन वगळत होता, ज्यामुळे प्रॉक्सी राउटिंग आवश्यक असलेल्या वातावरणांमध्ये अपयश येत होते.

**निराकरण (v3.5.5+):** ही समस्या आता दुरुस्त करण्यात आली आहे. प्रदाता प्रमाणीकरण आता `runWithProxyContext` द्वारे रूट केले जाते आणि प्रदाता-स्तरीय तसेच जागतिक प्रॉक्सी सेटिंग्जचा आपोआप आदर करते.

### टोकनची स्थिती तपासताना "fetch failed" त्रुटी येते

**कारण:** पार्श्वभूमीतील OAuth टोकन रिफ्रेश प्रत्येक कनेक्शनसाठी प्रॉक्सी कॉन्फिगरेशन निर्धारित करत नव्हते.

**निराकरण (v3.5.5+):** टोकन स्थिती तपासणी शेड्युलर आता रिफ्रेश करण्याचा प्रयत्न करण्यापूर्वी प्रत्येक कनेक्शनसाठी प्रॉक्सी कॉन्फिगरेशन निर्धारित करते. v3.5.5+ वर अपडेट करा.

### SOCKS5 प्रॉक्सी "invalid onRequestStart method" त्रुटी देते

**कारण:** Node.js 22 वर, undici@8 डिस्पॅचर Node च्या अंगभूत `fetch()` अंमलबजावणीशी सुसंगत नाही.

**निराकरण (v3.5.5+):** प्रॉक्सी डिस्पॅचर सक्रिय असताना OmniRoute आता undici चे स्वतःचे `fetch()` फंक्शन वापरते, ज्यामुळे सुसंगत वर्तन सुनिश्चित होते. v3.5.5+ वर अपडेट करा.

### WSL अंतर्गत MITM प्रॉक्सी: Windows होस्टवरील डेस्कटॉप अॅप्स इंटरसेप्ट होत नाहीत

**कारण:** MITM प्रॉक्सी आणि त्याचे CA प्रमाणपत्र OmniRoute ज्या वातावरणात चालते त्या वातावरणात इन्स्टॉल केले जातात. WSL अंतर्गत ते वातावरण Linux गेस्ट असते, तर AI डेस्कटॉप अॅप्स (Kiro, Trae, Copilot, Zed, …) Windows होस्टवर चालतात. होस्ट अॅप्स गेस्टच्या प्रमाणपत्र स्टोअरवर विश्वास ठेवत नाहीत आणि गेस्टच्या सिस्टम प्रॉक्सीद्वारे रूट होत नाहीत, त्यामुळे तेथे डेस्कटॉप इंटरसेप्शन सक्रिय होत नाही.

**शिफारस:** तुम्हाला इंटरसेप्ट करायची असलेली डेस्कटॉप अॅप्स ज्या OS वर आहेत, त्याच OS वर OmniRoute नेटिव्हरीत्या चालवा (Windows अॅप्ससाठी Windows; तसेच macOS/Linux साठीही). होस्ट अॅप्सना लक्ष्य करताना OmniRoute WSL मध्येच ठेवण्यासाठी, व्युत्पन्न केलेल्या CA प्रमाणपत्रावर Windows होस्टमध्ये व्यक्तिचलितरीत्या विश्वास ठेवावा लागतो आणि प्रत्येक होस्ट अॅपची नेटवर्क/प्रॉक्सी सेटिंग्ज WSL प्रॉक्सी एंडपॉइंटकडे निर्देशित करावी लागतात — ही असमर्थित आणि अविश्वसनीय व्यवस्था आहे.

## क्लाउड समस्या

### क्लाउड सिंक त्रुटी

1. `BASE_URL` तुमच्या चालू इंस्टन्सकडे निर्देश करत असल्याची खात्री करा (उदा., `http://localhost:20128`)
2. `CLOUD_URL` तुमच्या क्लाउड एंडपॉइंटकडे निर्देश करत असल्याची खात्री करा (उदा., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` मूल्ये सर्व्हर-साइड मूल्यांशी सुसंगत ठेवा

### क्लाउडवर `stream=false` मुळे 500 प्रतिसाद मिळतो

**लक्षण:** नॉन-स्ट्रीमिंग कॉलसाठी क्लाउड एंडपॉइंटवर `Unexpected token 'd'...` दिसते.

**कारण:** क्लायंटला JSON अपेक्षित असताना अपस्ट्रीम SSE पेलोड परत करते.

**तात्पुरता उपाय:** क्लाउडवरील थेट कॉलसाठी `stream=true` वापरा. स्थानिक रनटाइममध्ये SSE→JSON फॉलबॅक समाविष्ट आहे.

### क्लाउड कनेक्ट झाल्याचे दाखवते, पण "Invalid API key" दिसते

1. स्थानिक डॅशबोर्डवरून नवीन की तयार करा (`/api/keys`)
2. क्लाउड सिंक चालवा: Cloud सक्षम करा → Sync Now
3. जुन्या/सिंक न केलेल्या की अजूनही क्लाउडवर `401` परत करू शकतात

## Docker समस्या

### Docker IPv6 / कनेक्शन रीसेट

<a name="docker-ipv6"></a>

**लक्षणे:** `curl http://localhost:20128/v1/models` हे `curl: (56) Recv failure: Connection reset by peer` परत करते. डॅशबोर्ड आणि प्रमाणीकरण न लागणारे एंडपॉइंट कार्य करतात, परंतु प्रमाणीकृत एंडपॉइंट अयशस्वी होतात — ही प्रमाणीकरणाची समस्या असल्यासारखे दिसते, पण प्रत्यक्षात तसे नसते.

**कारण:** `docker run -p 20128:20128` हे `0.0.0.0` (IPv4) आणि `::` (IPv6) या दोन्हींवर प्रकाशित होते, परंतु कंटेनरमधील प्रोसेस फक्त IPv4 वर ऐकते. ज्या होस्टवर `localhost` प्रथम `::1` मध्ये रिझॉल्व्ह होते, तिथे कनेक्शन IPv6 प्रकाशित पोर्टवर पोहोचते, पण त्यामागे कोणताही लिसनर नसतो → कनेक्शन रीसेट होते.

**उपाय:**

1. **द्रुत निदान:** `curl -4 http://localhost:20128/v1/models` चालवा. ते `-4` सह कार्य करत असेल, पण त्याशिवाय अयशस्वी होत असेल, तर IPv6 बाइंड जुळत नाही.
2. **कायमस्वरूपी उपाय:** तुमच्या `docker run` कमांडमध्ये `-p 127.0.0.1:20128:20128` वापरून स्पष्टपणे IPv4 शी बाइंड करा:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   यामुळे IPv4 बाइंड सक्तीने वापरला जातो आणि सर्व होस्ट इंटरफेसवर प्रॉक्सी उघडी पडणेही टाळले जाते.

## डीबगिंग

### लॉग फाइल्स सक्षम करा

तुमच्या `.env` फाइलमध्ये `APP_LOG_TO_FILE=true` सेट करा. ॲप्लिकेशन लॉग `logs/` अंतर्गत लिहिले जातात.
सेटिंग्जमध्ये कॉल लॉग पाइपलाइन सक्षम असताना विनंतीशी संबंधित आर्टिफॅक्ट `${DATA_DIR}/call_logs/` अंतर्गत संग्रहित केले जातात.
पाइपलाइन कॅप्चर सक्षम असताना, स्ट्रीम चंक पेलोड वगळण्यासाठी `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` सेट करा किंवा KB मधील आर्टिफॅक्ट मर्यादा बदलण्यासाठी `CALL_LOG_PIPELINE_MAX_SIZE_KB` समायोजित करा.

### प्रोव्हायडरची स्थिती तपासा

```bash
# स्थिती डॅशबोर्ड
http://localhost:20128/dashboard/health

# API स्थिती तपासणी
curl http://localhost:20128/api/monitoring/health
```

### रनटाइम स्टोरेज

- मुख्य स्थिती: `${DATA_DIR}/storage.sqlite` (प्रोव्हायडर, कॉम्बो, उपनावे, की, सेटिंग्ज)
- वापर: `storage.sqlite` मधील SQLite टेबल्स (`usage_history`, `call_logs`, `proxy_logs`) + पर्यायी `${DATA_DIR}/call_logs/`
- ॲप्लिकेशन लॉग: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` असताना)
- कॉल लॉग आर्टिफॅक्ट: कॉल लॉग पाइपलाइन सक्षम असताना `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs पृष्ठावरील **Clean history** कृती `call_logs`, लेगसी
`request_detail_logs` आणि स्थानिक `${DATA_DIR}/call_logs/` आर्टिफॅक्ट डायरेक्टरी साफ करते.

### प्रदाता OPEN स्थितीत अडकला आहे

प्रदात्याचा सर्किट ब्रेकर OPEN असताना, कूलडाउन कालावधी संपेपर्यंत विनंत्या अवरोधित केल्या जातात.

**निराकरण:**

1. **डॅशबोर्ड → सेटिंग्ज → लवचिकता** येथे जा
2. प्रभावित प्रदात्यासाठी सर्किट ब्रेकर कार्ड तपासा
3. सर्व ब्रेकर साफ करण्यासाठी **सर्व रीसेट करा** वर क्लिक करा किंवा कूलडाउन कालावधी संपेपर्यंत प्रतीक्षा करा

2. **सेटिंग्ज → लवचिकता → प्रदाता प्रोफाइल्स** येथे जाऊन बिघाडाची मर्यादा वाढवा
3. प्रदात्याने API मर्यादा बदलल्या आहेत किंवा पुन्हा प्रमाणीकरण आवश्यक आहे का ते तपासा
4. विलंबाची टेलिमेट्री तपासा — जास्त विलंबामुळे टाइमआउट-आधारित बिघाड होऊ शकतात

- **SDK ऑब्जेक्टऐवजी रॉ स्ट्रिंग परत करते** — v1.x मध्ये निराकरण केले आहे; प्रतिसाद सॅनिटायझर OpenAI SDK Pydantic प्रमाणीकरण बिघाडास कारणीभूत असलेली मानक-बाह्य फील्ड (`x_groq`, `usage_breakdown`, इ.) काढून टाकतो. तरीही v3.x+ वर ही समस्या दिसत असल्यास, कृपया समस्या नोंदवा.
- **GLM/ERNIE `system` भूमिका नाकारते** — v1.x मध्ये निराकरण केले आहे; विसंगत मॉडेल्ससाठी भूमिका नॉर्मलायझर सिस्टम संदेश आपोआप वापरकर्ता संदेशांमध्ये विलीन करतो. तरीही v3.x+ वर ही समस्या दिसत असल्यास, कृपया समस्या नोंदवा.
- **`developer` भूमिका ओळखली जात नाही** — v1.x मध्ये निराकरण केले आहे; OpenAI व्यतिरिक्त इतर प्रदात्यांसाठी ती आपोआप `system` मध्ये रूपांतरित केली जाते. तरीही v3.x+ वर ही समस्या दिसत असल्यास, कृपया समस्या नोंदवा.
- **`json_schema` Gemini सोबत कार्य करत नाही** — v1.x मध्ये निराकरण केले आहे; `response_format` आता Gemini च्या `responseMimeType` + `responseSchema` मध्ये रूपांतरित केले जाते. तरीही v3.x+ वर ही समस्या दिसत असल्यास, कृपया समस्या नोंदवा.

- स्वयंचलित दर-मर्यादा केवळ API की प्रदात्यांना लागू होते (OAuth/सदस्यतेला नाही)
- **सेटिंग्ज → लवचिकता → प्रदाता प्रोफाइल्स** मध्ये स्वयंचलित दर-मर्यादा सक्षम असल्याची खात्री करा
- प्रदाता `429` स्थिती कोड किंवा `Retry-After` हेडर्स परत करतो का ते तपासा

### एक्स्पोनेन्शियल बॅकऑफचे ट्यूनिंग

प्रदाता प्रोफाइल्समध्ये या सेटिंग्ज उपलब्ध आहेत:

- **मूलभूत विलंब** — पहिल्या अपयशानंतरचा प्रारंभिक प्रतीक्षा कालावधी (डीफॉल्ट: 1s)
- **कमाल विलंब** — कमाल प्रतीक्षा कालावधीची मर्यादा (डीफॉल्ट: 30s)
- **गुणक** — प्रत्येक सलग अपयशानंतर विलंब किती वाढवायचा (डीफॉल्ट: 2x)

### अँटी-थंडरिंग हर्ड

अनेक समकालीन विनंत्या दर-मर्यादित प्रदात्यापर्यंत पोहोचतात तेव्हा, विनंत्या क्रमवार हाताळण्यासाठी आणि साखळी स्वरूपातील अपयशे टाळण्यासाठी OmniRoute म्युटेक्स + स्वयंचलित दर-मर्यादा वापरते. API की प्रदात्यांसाठी हे स्वयंचलित असते.

### चॅट विनंत्या 503 / chat_admission_busy सह अयशस्वी होतात

**लक्षणे:**

- चॅट पूर्णता एंडपॉइंट पुन्हा प्रयत्न करता येण्याजोगा `503` प्रतिसाद परत करतो, ज्याचा त्रुटी कोड
  `chat_admission_busy` असतो.
- प्रतिसादात `Retry-After` समाविष्ट असतो. #12135 पासून त्याचे मूल्य निरीक्षण केलेल्या
  व्यापलेपणावरून ठरवले जाते — विनंतीने आधीच प्रतीक्षा केलेली `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  विंडो आणि सध्याच्या हेवीवेट लीजेस धारण केलेला कालावधी, यांपैकी मोठे मूल्य — पूर्ण
  सेकंदांपर्यंत वरच्या दिशेने पूर्णांकित करून 60 वर मर्यादित केले जाते. निष्क्रिय गेटवर ते ऐतिहासिक
  किमान मर्यादा कायम ठेवते: बाइट-आधारित मार्गावर 2 सेकंद, संरचना-आधारित मार्गावर 1 सेकंद
  (ज्यामध्ये `reason: "structure_limit"` देखील समाविष्ट असते).
- दुसरे हेवीवेट चॅट किंवा दीर्घकाळ चालणारा स्ट्रीमिंग प्रतिसाद अद्याप
  सुरू असताना असे होऊ शकते.

बाइट-आधारित प्रतिसादाचा मुख्य भाग असा आहे:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

संरचना-आधारित प्रतिसादामध्ये समान प्रकार आणि कोड वापरला जातो, तसेच संदेश
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
आणि `reason: "structure_limit"` असतात.
डीफॉल्ट थ्रेशोल्ड्सनुसार, एखाद्या विनंतीमध्ये किमान `200` संदेश,
किमान `64` टूल्स किंवा किमान `32,000` अंदाजित टोकन्स असल्यास, किंवा मर्यादित संरचना अंदाजाने
भेट दिलेल्या `10,000` नोड्सची किंवा `12` खोलीची मर्यादा संपवल्यास, ती विनंती संरचनात्मकदृष्ट्या हेवी मानली जाते.

**कारण:** हे OmniRoute अंतर्गत हेतुपुरस्सर केलेले लोड शेडिंग आहे, अपस्ट्रीम-प्रदाता अपयश नाही.
मोठ्या विनंतीचा मुख्य भाग राखून ठेवण्यापूर्वी आणि पार्स करण्यापूर्वी मर्यादित हेवीवेट क्षमता आरक्षित
करण्यासाठी प्रत्येक प्रक्रिया प्रक्रिया-स्थानिक गार्ड वापरते. SSE प्रतिसादाच्या संपूर्ण जीवनकाळात
हेवीवेट लीज धारण केली जाते.

**#503-फॅनआउट:** या निराकरणापूर्वी, होस्ट मेमरीचा विचार न करता गार्ड समवर्तीपणाला विनंत्यांच्या निश्चित COUNT पर्यंत
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, डीफॉल्ट `1`) मर्यादित करत होता, त्यामुळे कोडिंग-एजंट
फॅन-आउट (अनेक सबएजंट्स/CLIs, नियमितपणे 256 KB पेक्षा मोठे मुख्य भाग) प्रभावी
समवर्तीपणा ~1 पर्यंत घसरवत असे आणि पूर्णपणे सामान्य लोडमध्येही 503 त्रुटी देत असे. आता गार्ड स्वतःचे ट्यूनिंग
करतो: तो प्रक्रियेच्या वास्तविक मेमरी कमाल मर्यादेवरून आकार दिलेल्या, स्वयंचलितपणे व्युत्पन्न केलेल्या इनजेस्ट BYTE बजेटने
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) नियंत्रित केला जातो आणि तो थेट संसाधन-दबाव सिग्नलचाही
विचार करतो — त्यामुळे एकाच वेळी एकापेक्षा अधिक हेवी विनंत्या आल्या म्हणून नव्हे, तर होस्टवर खरोखरच
मेमरीचा दबाव असेल तेव्हाच तो लोड कमी करतो. जुनी संख्या मर्यादा (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
अद्याप पाळली जाते, परंतु तुम्ही ती स्पष्टपणे सेट केली असेल तरच.

क्षमता व्यस्त असताना, हेवीवेट विनंती पुन्हा प्रयत्न करता येण्याजोगा `503` प्रतिसाद देण्यापूर्वी
स्लॉट मोकळा होण्यासाठी प्रथम `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` पर्यंत प्रतीक्षा करते
(डीफॉल्ट `RATE_LIMIT_MAX_WAIT_MS`; `0` प्रतीक्षा अक्षम करते).
ही मर्यादित प्रतीक्षा यासाठी आहे की समकालीनपणे हेवी उप-विनंत्यांचा फॅन-आउट करणारे एजंट-शैलीतील क्लायंट्स
(OpenCode, Claude Code, Cursor), तात्काळ नकारांवर त्यांचे संपूर्ण पुनर्प्रयत्न बजेट खर्च करून
कार्याच्या मध्यात बंद पडण्याऐवजी, त्या बर्स्टला क्रमवार हाताळतील.
सध्याचे हेवीवेट लीज व्यापलेपण, निश्चित केलेले बाइट बजेट आणि थेट दबावाची तीव्रता
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) येथे दर्शवली जाते — कोणतेही env var बदलण्यापूर्वी
हे तपासा.
सेटिंग्ज → लवचिकता → विनंती रांग → समकालीन विनंत्या हे नियंत्रित करत नाही; ती सेटिंग
स्वतंत्र प्रदाता विनंती-रांग यंत्रणा नियंत्रित करते.

**निराकरण:**

1. प्रथम पुन्हा प्रयत्न करा. क्लायंट्सनी विनंती त्वरित
   पुन्हा पाठवण्याऐवजी `Retry-After` चे पालन करावे आणि बॅकऑफ वापरावा.
2. काहीही ट्यून करण्यापूर्वी `/api/monitoring/health` → `chatAdmission` तपासा. `countCapEnabled:
false` आणि पुरेसे मोठे `maxInflightBytes` यांचा अर्थ स्वयंचलितपणे व्युत्पन्न केलेले बजेट आधीच आपले
   काम करत आहे; `high`/`critical` `pressureSeverity` याचा अर्थ होस्टकडे खरोखरच कमी मेमरी आहे —
   हे अॅडमिशन env var ने दुरुस्त करता येत नाही; यासाठी अधिक RAM किंवा कमी कार्यभार आवश्यक आहे.
3. `/api/monitoring/health` मध्ये स्वयंचलितपणे व्युत्पन्न केलेले बजेट तुमच्या होस्टसाठी खरोखरच खूप कमी
   असल्याचे दिसल्यासच (हे दुर्मीळ आहे — ते आधीच कंटेनरपासून बेअर-मेटलपर्यंत स्केल होते), लेगसी विनंती-संख्या मर्यादेकडे परत
   जाण्याऐवजी ते थेट `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ने ओव्हरराइड करा.

अधिकृत अॅडमिशन सेटिंग्जसाठी [पर्यावरण-चल संदर्भ](../reference/ENVIRONMENT.md#4-security--authentication)
पहा.

## पर्यायी RAG / LLM अपयश वर्गीकरण (16 समस्या)

काही OmniRoute वापरकर्ते RAG किंवा एजंट स्टॅकच्या पुढे गेटवे ठेवतात. अशा सेटअपमध्ये एक विचित्र नमुना सामान्यपणे दिसतो: OmniRoute व्यवस्थित कार्यरत असल्याचे दिसते (प्रदाते उपलब्ध, रूटिंग प्रोफाइल योग्य, दर-मर्यादेच्या सूचना नाहीत), परंतु अंतिम उत्तर तरीही चुकीचे असते.

प्रत्यक्षात, या घटना सहसा स्वतः गेटवेमुळे नव्हे, तर डाउनस्ट्रीम RAG पाइपलाइनमुळे घडतात.

त्या अपयशांचे वर्णन करण्यासाठी तुम्हाला सामायिक शब्दावली हवी असल्यास, तुम्ही WFGY ProblemMap वापरू शकता. हे MIT परवान्याअंतर्गत उपलब्ध असलेले बाह्य मजकूर संसाधन असून, त्यात वारंवार आढळणाऱ्या सोळा RAG / LLM अपयश नमुन्यांची व्याख्या केली आहे. व्यापक स्तरावर त्यात पुढील बाबी समाविष्ट आहेत:

- पुनर्प्राप्तीतील विचलन आणि तुटलेल्या संदर्भ सीमा
- रिक्त किंवा कालबाह्य निर्देशांक आणि व्हेक्टर स्टोअर्स
- एम्बेडिंग आणि अर्थविषयक जुळणीतील विसंगती
- प्रॉम्प्ट संरचना आणि संदर्भ विंडोशी संबंधित समस्या
- तर्कशक्तीचे अपयश आणि अतिआत्मविश्वासाने दिलेली उत्तरे
- लांब साखळी आणि एजंट समन्वयातील अपयश
- एकाधिक एजंटमधील स्मृती आणि भूमिकेचे विचलन
- डिप्लॉयमेंट आणि बूटस्ट्रॅप क्रमाशी संबंधित समस्या

कल्पना सोपी आहे:

1. एखाद्या चुकीच्या प्रतिसादाची तपासणी करताना, पुढील माहिती नोंदवा:
   - वापरकर्त्याचे कार्य आणि विनंती
   - OmniRoute मधील रूट किंवा प्रदाता संयोजन
   - डाउनस्ट्रीममध्ये वापरलेला कोणताही RAG संदर्भ (पुनर्प्राप्त केलेले दस्तऐवज, टूल कॉल्स इत्यादी)
2. घटनेची एक किंवा दोन WFGY ProblemMap क्रमांकांशी (`No.1` … `No.16`) सांगड घाला.
3. OmniRoute लॉगच्या शेजारी हा क्रमांक तुमच्या स्वतःच्या डॅशबोर्ड, रनबुक किंवा घटना ट्रॅकरमध्ये साठवा.
4. तुमच्या RAG स्टॅक, रिट्रीव्हर किंवा रूटिंग धोरणात बदल करण्याची आवश्यकता आहे का हे ठरवण्यासाठी संबंधित WFGY पृष्ठ वापरा.

संपूर्ण मजकूर आणि ठोस कृतीपद्धती येथे उपलब्ध आहेत (MIT परवाना, केवळ मजकूर):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

तुम्ही OmniRoute च्या मागे RAG किंवा एजंट पाइपलाइन चालवत नसल्यास, तुम्ही हा विभाग दुर्लक्षित करू शकता.

### Devin CLI प्रमाणीकरणातील अपयश

**लक्षणे:**

- Devin-आधारित टूल्स वापरताना "Devin CLI सापडले नाही" किंवा "प्रमाणीकरण अयशस्वी झाले"
- CLI रनटाइम तपासणीत `installed=false` नोंदवले जाते

**कारणे:**

- `CLI_DEVIN_BIN` अस्तित्वात नसलेल्या पाथकडे निर्देश करते
- होस्टवर Devin CLI इंस्टॉल केलेले नाही

**उपाय:**

1. तुमच्या प्लॅटफॉर्मसाठी Devin CLI इंस्टॉल करा
2. `.env` मध्ये `CLI_DEVIN_BIN=/usr/local/bin/devin` (किंवा वास्तविक पाथ) सेट करा
3. OmniRoute रीस्टार्ट करा आणि **Dashboard → CLI Tools** मधून पुन्हा चाचणी करा

### मॉडेल कूलडाउन अडकलेले आहे (मॅन्युअल रीसेट)

**लक्षणे:**

- कालबाह्यता वेळ उलटून गेल्यानंतरही मॉडेल कूलडाउनमध्ये असल्याचे दाखवले जाते
- टाइमस्टॅम्प भूतकाळातील असूनही कॉम्बो रूटिंगमधील विनंत्या त्या मॉडेलला वगळतात

**मॅन्युअल रीसेट:**

- **डॅशबोर्ड:** **Settings → Model Cooldowns** → प्रभावित कार्डवरील **Re-enable** वर क्लिक करा
- **API:** व्यवस्थापन प्रमाणीकरण हेडर्ससह `DELETE /api/resilience/model-cooldowns`

### Command Code प्रदात्याचे कनेक्शन 403 सह अयशस्वी होते

**लक्षणे:**

- Command Code प्रदात्याच्या कनेक्शनची चाचणी करताना 403
- नवीन प्रदाता जोडल्यानंतर प्रदाता कार्डवर "अनधिकृत" दाखवले जाते

**कारण:** OAuth प्रवाह पूर्ण झाला नाही (कॉलबॅक प्राप्त झाला नाही किंवा टोकन कायमस्वरूपी साठवले गेले नाही).

**उपाय:**

- OAuth प्रवाह पुन्हा सुरू करण्यासाठी CLI मधून `omniroute providers` चालवा, किंवा
- **Dashboard → Providers → Command Code → Reconnect** मधून OAuth पुन्हा चालवा

### ModelScope कडून आक्रमक 429 कूलडाउन मिळतात

**लक्षणे:**

- विनंत्यांच्या छोट्या बर्स्टनंतर ModelScope वर अतिशय लहान किंवा त्वरित कूलडाउन
- कॉम्बो रूटिंग अपेक्षेपेक्षा लवकर ModelScope वगळते

**कारण:** ModelScope प्रदाता-विशिष्ट `Retry-After` हेडर्स पाठवते. v3.8.0 मध्ये त्या हेडर्ससाठी विशेष हाताळणी समाविष्ट आहे, त्यामुळे जुन्या आवृत्त्या त्यांचा सामान्य दर-मर्यादा सूचनांप्रमाणे चुकीचा अर्थ लावतात.

**उपाय:**

- तुम्ही v3.8.0 किंवा त्यानंतरची आवृत्ती वापरत असल्याची खात्री करा
- **Settings → Resilience** अंतर्गत `useUpstream429BreakerHints` टॉगल सक्षम असल्याची खात्री करा

### उत्पादन वातावरणात OMNIROUTE_WS_BRIDGE_SECRET उपलब्ध नाही

**लक्षणे:**

- रिमोट उत्पादन होस्टवर चालवताना प्रत्येक Codex/Responses WebSocket ब्रिज विनंतीवर 401
- कनेक्ट झाल्यानंतर WebSocket ब्रिज हँडशेक त्वरित बंद होते

**कारण:** उत्पादन वातावरणातून `OMNIROUTE_WS_BRIDGE_SECRET` पर्यावरण चल उपलब्ध नाही.

**उपाय:**

1. यादृच्छिक गुपित निर्माण करा: `openssl rand -hex 32`
2. उत्पादन सर्व्हरच्या वातावरणात (आणि ब्रिजशी संवाद साधणाऱ्या कोणत्याही क्लायंटमध्ये) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` सेट करा
3. OmniRoute रीस्टार्ट करा

### Responses API: पार्श्वभूमी मोड सिंक्रोनस मोडमध्ये अवनत झाला

**लक्षणे:**

- लॉग केलेली चेतावणी: `background mode degraded to synchronous`
- `background: true` विनंती पार्श्वभूमी जॉब हँडलऐवजी सामान्य सिंक्रोनस प्रतिसाद देते

**कारण:** v3.8.0 मध्ये चेतावणी पाठवताना Responses API वरील `background: true` हेतुपुरस्सर सिंक्रोनस अंमलबजावणीत अवनत केले जाते. पूर्ण असिंक्रोनस पार्श्वभूमी अंमलबजावणी भविष्यात उपलब्ध होईल.

**उपाय:**

- `background` शिवाय कॉल करण्यासाठी क्लायंट समायोजित करा, किंवा
- पूर्ण असिंक्रोनस पार्श्वभूमी मोडसह येणाऱ्या नंतरच्या रिलीझची प्रतीक्षा करा (चेंजलॉगचा मागोवा घ्या)

## संथ प्रारंभ / सज्जता कालबाह्यता

जर CLI वर `⚠ Server did not respond within 60s` असे दिसत असेल, परंतु सर्व्हर
प्रत्यक्षात कार्यरत असेल, तर तुमच्या वातावरणासाठी सज्जता तपासणीची कालमर्यादा खूप कमी आहे.

हे सामान्यतः Windows वर (अँटीव्हायरस, फाइलसिस्टम निरीक्षक) किंवा प्रारंभाच्या वेळी
मोठा कार्यभार असलेल्या कंटेनर्समध्ये घडते.

**उपाय — कालमर्यादा वाढवा:**

```bash
# पर्यावरण चलाद्वारे (पुढील प्रारंभांमध्येही कायम राहते):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 मिनिटे
omniroute serve

# CLI फ्लॅगद्वारे (फक्त एकदाच):
omniroute serve --ready-timeout 180000
```

डीफॉल्ट मूल्य 60 000 ms (60 s) आहे. ही चेतावणी केवळ माहितीसाठी आहे; सर्व्हर
पार्श्वभूमीत सुरू होत राहतो आणि बूट पूर्ण झाल्यावर उपलब्ध होईल.

`OMNIROUTE_READY_TIMEOUT_MS` विषयी संपूर्ण तपशीलांसाठी
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) पहा.
