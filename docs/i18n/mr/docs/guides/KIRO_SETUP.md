या मार्गदर्शकामध्ये OmniRoute मध्ये Kiro (AWS द्वारे होस्ट केलेला AI कोडिंग सहाय्यक) खाती जोडण्याची माहिती दिली आहे,
ज्यामध्ये सत्रांमधील संघर्ष टाळून एकाच वेळी अनेक खाती चालवण्यावर भर दिला आहे.

---

## पार्श्वभूमी: Kiro खात्यांमध्ये संघर्ष का होऊ शकतो

Kiro चे बॅकएंड सक्रिय सत्रांचा मागोवा घेण्यासाठी AWS SSO OIDC क्लायंट नोंदणी वापरते.
महत्त्वाची मर्यादा: **प्रत्येक OIDC क्लायंट नोंदणी एका वेळी फक्त एका सक्रिय
सत्राला समर्थन देते**. त्याच नोंदणीकृत क्लायंटचा वापर करून दुसरे डिव्हाइस किंवा वापरकर्ता प्रमाणीकरण करतो तेव्हा
बॅकएंड पहिल्या खात्याचे रिफ्रेश टोकन अवैध करते.

दुसरे Kiro खाते आधीपासून साइन इन केलेल्या मशीनवर `kiro-cli login` चालवताना
समस्या निर्माण करणारी हीच यंत्रणा आहे — नवीन लॉगिनमुळे
पहिल्या खात्याचे टोकन रद्द होते.

---

## OmniRoute ही समस्या कशी सोडवते (v3.8.0+)

v3.8.0 पासून, प्रत्येक Kiro कनेक्शन आयात करताना OmniRoute `registerClient()` (AWS SSO OIDC)
कॉल करते. यामुळे प्रत्येक OmniRoute कनेक्शनला स्वतःची समर्पित OIDC
क्लायंट नोंदणी मिळते. प्रत्येक क्लायंट नोंदणी स्वतंत्र असल्यामुळे, एका खात्याचे टोकन रिफ्रेश करणे किंवा
पुन्हा प्रमाणीकरण करणे इतर कोणत्याही खात्याच्या रिफ्रेश टोकनवर परिणाम करत नाही.

हे विलगीकरण रिफ्रेश-टोकन आयात पद्धतींना लागू होते आणि API-की प्रमाणीकरणामध्ये
OIDC रिफ्रेश सत्रे पूर्णपणे टाळली जातात:

| आयात पद्धत                                           | विलगीकरण स्थिती                                                                        |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------- |
| AWS Builder ID / IDC डिव्हाइस-कोड प्रवाह             | डिव्हाइस-कोड प्रवाह सादर केल्यापासून विलग                                              |
| **टोकन आयात करा** (रिफ्रेश टोकन स्वहस्ते पेस्ट करणे) | v3.8.0 पासून विलग                                                                      |
| **Google / GitHub सोशल लॉगिन**                       | v3.8.0 पासून विलग                                                                      |
| **स्वयं-आयात** (kiro-cli SQLite)                     | v3.8.0 पासून विलग (SQLite पथ आधीपासून विलग होता; SSO-कॅश पर्यायी पद्धतही आता विलग आहे) |
| **API की** (दीर्घकालीन CodeWhisperer की)             | रिफ्रेश सत्र नाही; कीची पडताळणी करून ती बेअरर क्रेडेन्शियल म्हणून संग्रहित केली जाते   |

## v3.8.0 पूर्वी तयार केलेल्या कनेक्शनसाठी स्थलांतर सूचना

v3.8.0 पूर्वी आयात केलेल्या कनेक्शनमध्ये समर्पित OIDC क्लायंट नोंदणी
`providerSpecificData` मध्ये संग्रहित केलेली नसते. ही कनेक्शन कार्यरत राहतात, परंतु सामायिक
सोशल-ऑथ रिफ्रेश एंडपॉइंट वापरतात, याचा अर्थ अशी दोन कनेक्शन अजूनही परस्परांना
अवैध करू शकतात.

**विलगीकरण मिळवण्यासाठी:** **डॅशबोर्ड → प्रदाते** मधून जुने कनेक्शन हटवा आणि
समर्थित आयात प्रवाहांपैकी कोणताही वापरून ते पुन्हा आयात करा. नव्याने तयार केलेल्या सर्व कनेक्शनना
स्वतःची क्लायंट नोंदणी आपोआप मिळेल.

## दोन Kiro खाती एकत्र जोडणे

### पूर्वापेक्षा

- OmniRoute v3.8.0 किंवा त्यानंतरची आवृत्ती.
- कार्यरत Kiro खाते (ईमेल + पासवर्ड, Google किंवा GitHub लॉगिन).
- पर्यायाने दुसरे Kiro खाते.

### पायरी 1: पहिले खाते आयात करा

1. **डॅशबोर्ड → प्रदाते → प्रदाता जोडा → Kiro** उघडा.
2. यांपैकी एक पर्याय निवडा:
   - **टोकन आयात करा** — `aorAAAAAG` ने सुरू होणारे रिफ्रेश टोकन पेस्ट करा.
   - **API की** — दीर्घकालीन Kiro / CodeWhisperer API की पेस्ट करा.
   - **Google / GitHub लॉगिन** — ब्राउझरमध्ये OAuth प्रवाह पूर्ण करा.
   - **स्वयं-आयात** — बटणावर क्लिक करा; OmniRoute स्थानिक kiro-cli डेटाबेस किंवा
     `~/.aws/sso/cache` मधून क्रेडेन्शियल वाचते.
3. कनेक्शन जतन केले जाते. रिफ्रेश-टोकन प्रवाह समर्पित
   OIDC क्लायंटची आपोआप नोंदणी करतात. API-की प्रवाह AWS वापरून कीची पडताळणी करतात आणि रिफ्रेश टोकन संग्रहित करत नाहीत.

### पायरी 2: दुसरे खाते आयात करा

दुसऱ्या खात्यासाठी पायरी 1 पुन्हा करा. प्रत्येक आयात स्वतंत्र OIDC
क्लायंट नोंदणी तयार करत असल्यामुळे, दोन्ही कनेक्शन पूर्णपणे विलग असतात.

### पायरी 3: दोन्ही कनेक्शन सक्रिय असल्याची खात्री करा

1. **डॅशबोर्ड → प्रदाते** — दोन्ही Kiro कनेक्शनची स्थिती **सक्रिय** म्हणून दिसली पाहिजे.
2. **डॅशबोर्ड → आरोग्य** — दोन्ही कनेक्शन त्यांच्या टोकन आरोग्य तपासणीत उत्तीर्ण झाली पाहिजेत.

### पायरी 4: खात्यांदरम्यान रूट करण्यासाठी कॉम्बो वापरा

लोड-बॅलन्स करण्यासाठी किंवा एका खात्यात समस्या आल्यास दुसऱ्या खात्यावर जाण्यासाठी, दोन्ही कनेक्शन लक्ष्य म्हणून असलेला कॉम्बो तयार करा:

```
kiro/kiro-dev → kiro/kiro-pro
```

कॉम्बो कॉन्फिगरेशनसाठी [FEATURES.md](./FEATURES.md) आणि रूटिंग दस्तऐवजीकरण पहा.

## Enterprise / IDC वापरकर्ते

AWS IAM Identity Center (IDC) खात्यांसाठी, **डॅशबोर्ड → प्रदाते → Kiro → डिव्हाइस कोड** येथील **AWS Builder ID / IDC डिव्हाइस-कोड** प्रवाह वापरा. डिव्हाइस-कोड प्रवाह नेहमीच पूर्णपणे विलग राहिला आहे. या कनेक्शनसाठी पुन्हा आयात करण्याची आवश्यकता नाही.

डीफॉल्ट नसलेल्या AWS प्रदेशात कार्यरत असलेले Enterprise वापरकर्ते Import Token API द्वारे आयात करताना प्रदेश निर्दिष्ट करू शकतात:

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

`region` फील्ड वगळल्यास त्याचे डीफॉल्ट मूल्य `us-east-1` असते.

## API-Key आयात प्रवाह

API-key प्रमाणीकरण दीर्घकाळ वैध राहणाऱ्या Kiro / AWS CodeWhisperer bearer क्रेडेन्शियल्ससाठी आहे. ते OAuth refresh वापरत नाही, त्यामुळे सामायिक OIDC सत्र अवैध होणे टाळले जाते.

### डॅशबोर्ड

1. **डॅशबोर्ड -> प्रदाते -> Kiro** उघडा.
2. **API Key** निवडा.
3. API key आणि पर्यायी AWS प्रदेश (`us-east-1` हे डीफॉल्ट) पेस्ट करा.
4. OmniRoute key ची वैधता तपासते आणि कनेक्शन जतन करते.

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### अंतर्गत करार

API route, `KiroService.validateApiKey()` कॉल करून key ची वैधता तपासतो; ही पद्धत संबंधित प्रदेशाशी जुळणाऱ्या CodeWhisperer/Amazon Q endpoint विरुद्ध `ListAvailableProfiles` वापरते आणि `profileArn` निर्धारित करते.

जतन केलेले कनेक्शन पुढील रचना वापरते:

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

रनटाइममध्ये, `KiroExecutor.buildHeaders()` key ला `Authorization: Bearer <key>` म्हणून पाठवते आणि `tokentype: API_KEY` जोडते. कोटा/प्रोफाइल कॉल्सही हाच मार्कर वापरतात, त्यामुळे AWS त्या bearer ला OIDC किंवा social access token ऐवजी दीर्घकाळ वैध राहणारी API key मानते.

## OIDC Client ची कालबाह्यता

AWS SSO OIDC public clients सामान्यतः 90 दिवसांनंतर कालबाह्य होतात (`clientSecretExpiresAt`). निरीक्षणक्षमतेसाठी OmniRoute हा timestamp `providerSpecificData` मध्ये साठवते. एखादे कनेक्शन ~90 दिवसांनंतर refresh होणे थांबले, तर नवीन OIDC client registration मिळवण्यासाठी ते कनेक्शन पुन्हा आयात करा. कालबाह्य झाल्यानंतर स्वयंचलित पुनर्नोंदणी ही भावी सुधारणा म्हणून नोंदवलेली आहे.

API-key कनेक्शनना OIDC client expiry नसते, कारण ती AWS SSO OIDC द्वारे refresh होत नाहीत.

## समस्या निवारण

### दुसरे खाते सतत लॉग आउट होत आहे

- **डॅशबोर्ड → प्रदाते** मधील दोन्ही कनेक्शन तपासा आणि प्रत्येकाच्या raw JSON मध्ये (माहिती चिन्हाद्वारे दृश्यमान) null नसलेला `clientId` दिसत असल्याची खात्री करा. कोणत्याही कनेक्शनमध्ये `clientId` नसल्यास, ते v3.8.0 पूर्वी आयात केले गेले होते — ते पुन्हा आयात करा.

### "Token validation failed" या संदेशासह आयात अयशस्वी होते

- refresh token ची सुरुवात `aorAAAAAG` ने होत असल्याची खात्री करा.
- OmniRoute ला `https://oidc.us-east-1.amazonaws.com` (किंवा कॉन्फिगर केलेला प्रदेश) उपलब्ध असल्याची खात्री करा. तुम्ही कॉर्पोरेट proxy मागे असल्यास, **डॅशबोर्ड → सेटिंग्ज → Proxies** मध्ये provider-level proxy सेट करा.

### API-key आयात अयशस्वी होते

- ही key refresh token नसून Kiro / CodeWhisperer API key असल्याची खात्री करा.
- AWS प्रदेश key/खात्याशी जुळत असल्याची खात्री करा. `us-east-1` हा डीफॉल्ट आहे.
- key ला `ListAvailableProfiles` कॉल करता आला पाहिजे; अन्यथा OmniRoute आवश्यक `profileArn` निर्धारित करू शकत नाही.

इतर समस्यांसाठी, मुख्य [TROUBLESHOOTING.md](./TROUBLESHOOTING.md) पहा.
