OpenAI-सुसंगत बॅकएंड म्हणून OmniRoute कडे निर्देशित केलेला Codex CLI वापरण्यासाठी संपूर्ण मार्गदर्शक.

---

> **TOML हे एकमेव प्रभावी स्वरूप आहे.** आधुनिक Codex केवळ `~/.codex/config.toml`
> वाचतो (codex-cli 0.147.0 सह पडताळलेले: `codex --help` मध्ये
> `-c/--config` अधिलिखित मूल्ये "`~/.codex/config.toml` मधून लोड केली जातात" असे नमूद केले आहे). जुनी
> `~/.codex/config.yaml` फाइल लेगसी npm CLI ची होती आणि तिच्याकडे कोणतीही सूचना न देता दुर्लक्ष केले जाते.
> डॅशबोर्ड जनरेटर (`/api/cli-tools/apply`, साधन `codex`) सावधगिरीने विलीनीकरण करून TOML लिहितो —
> विद्यमान की आणि इतर प्रदाता ब्लॉक जतन केले जातात,
> API की `OMNIROUTE_API_KEY` मध्येच राहते (फाइलमध्ये कधीही नाही), आणि उरलेली लेगसी
> `config.yaml` फाइल न बदलता स्थलांतर नोंद म्हणून दर्शवली जाते.

## थेट पेस्ट करण्यासाठी तयार config.toml

`<YOUR_HOST>` आणि `<YOUR_KEY>` यांच्या जागी तुमची मूल्ये वापरा:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # प्रत्येक साधन कॉलसाठी इतिहास संचयनाची कमाल मर्यादा

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc किंवा ~/.zshrc — प्रत्यक्ष की मूल्य, config.toml मध्ये कधीही नाही
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT अॅपमध्ये समाविष्ट केलेला Codex

तुम्ही ChatGPT डेस्कटॉप अॅपद्वारे Codex स्थापित केला असल्यास, `codex` बायनरी
केवळ अॅप बंडलमध्ये असू शकते आणि अद्याप तुमच्या शेल `PATH` मध्ये नसू शकते. तुमच्या
शेल स्टार्टअप फाइलमध्ये रिसोर्सेस डायरेक्टरी जोडा:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

नवीन शेल उघडा आणि नंतर पडताळा:

```bash
command -v codex
codex --version
```

### प्रमाणीकरण नसलेला स्थानिक OmniRoute: प्लेसहोल्डर की पुरेशी आहे

पहिली विनंती CLI मधून बाहेर जाण्यापूर्वीच `env_key` ने निर्दिष्ट केलेले
एन्व्हायर्नमेंट व्हेरिएबल अस्तित्वात आहे की नाही, हे Codex तपासतो.
तुमच्या **स्थानिक** OmniRoute इन्स्टन्सला प्रमाणीकरणाची आवश्यकता नसल्यास,
कोणतेही रिक्त नसलेले प्लेसहोल्डर चालेल:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

तुमचा OmniRoute सर्व्हर संरक्षित किंवा दूरस्थ असल्यास त्याऐवजी खरी की वापरा.

> **सामान्य होस्ट पर्याय**
>
> | प्रवेश          | URL                           |
> | --------------- | ----------------------------- |
> | स्थानिक नेटवर्क | `http://192.168.0.1:20128/v1` |
> | Tailscale       | `http://100.x.x.x:20128/v1`   |
> | लूपबॅक          | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — ते सर्व मॉडेलसाठी का कार्य करते

Codex CLI ने फेब्रुवारी 2026 मध्ये `wire_api = "chat"` (Chat Completions) कालबाह्य केले आणि आता `wire_api = "responses"` (OpenAI Responses API) **आवश्यक** आहे. v0.138 पासून `wire_api = "chat"` सेट केल्यास स्टार्टअपच्या वेळी त्वरित क्रॅश होते.

GLM आणि Kimi यांच्यासह अनेक प्रदाते अजूनही फक्त Chat Completions एंडपॉइंट उपलब्ध करतात. DeepSeek V4 आता मूळ Responses API तसेच Anthropic-सुसंगत एंडपॉइंट उपलब्ध करतो; OmniRoute डीफॉल्टनुसार Responses वापरतो आणि प्रत्येक DeepSeek कनेक्शनला Anthropic सुसंगतता निवडण्याची अनुमती देतो.

**OmniRoute हे पारदर्शकपणे हाताळतो:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute प्रदात्याचा मूळ प्रोटोकॉल निवडतो आणि आवश्यकतेनुसार भाषांतर करतो
    → POST /responses (DeepSeek V4) किंवा /chat/completions (Mistral / GLM / Kimi / इतर)
```

OmniRoute वापरताना तुम्हाला स्वतंत्र भाषांतर प्रॉक्सीची कधीही आवश्यकता नसते. **सर्व मॉडेल `wire_api = "responses"` वापरतात** — उर्वरित सर्वकाही OmniRoute हाताळतो.

> **`wire_api` हे डीफॉल्ट आहे** — या फील्डचे डीफॉल्ट मूल्य `"responses"` आहे आणि ते `config.toml` मधून पूर्णपणे वगळता येते. हेतूचे दस्तऐवजीकरण करायचे असल्यासच ते स्पष्टपणे सेट करा.

## संदर्भ विंडो आणि संक्षेपण

### टोकन कॉन्फिगरेशन फील्ड

| फील्ड                            | वर्णन                                                                                                                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `model_context_window`           | सक्रिय मॉडेलसाठी एकूण टोकन मर्यादा. मॉडेलच्या घोषित मर्यादेवर सेट करा.                                                                                                                                                   |
| `model_auto_compact_token_limit` | स्वयंचलित इतिहास संक्षेपण सुरू करणारी मर्यादा. **कमाल: `model_context_window`च्या 90%** — 90% पेक्षा जास्त मूल्ये कोणतीही सूचना न देता दुर्लक्षित केली जातात.                                                            |
| `tool_output_token_limit`        | इतिहासात प्रत्येक टूल कॉलच्या आउटपुटसाठी संग्रहित केल्या जाणाऱ्या टोकनची कमाल मर्यादा. एकाच मोठ्या टूल प्रतिसादामुळे संपूर्ण विंडो भरली जाणे टाळते. **ही कमाल आउटपुट मर्यादा नाही** — ही इतिहासातील संग्रहण मर्यादा आहे. |
| `compact_prompt`                 | संक्षेपणादरम्यान वापरल्या जाणाऱ्या सिस्टम प्रॉम्प्टसाठी इनलाइन ओव्हरराइड (v0.138+).                                                                                                                                      |

> **`model_max_output_tokens` विषयी नोंद**: हे फील्ड **Codex CLI कॉन्फिग स्कीमाचा भाग नाही** (Codex Rust कोडबेसमध्ये अनुपस्थित). ते सेट केले असल्यास कोणतीही सूचना न देता दुर्लक्षित केले जाते. त्यावर अवलंबून राहू नका — इतिहासात किती टूल आउटपुट संग्रहित केले जाईल हे नियंत्रित करण्यासाठी `tool_output_token_limit` वापरा.

## तर्कशक्तीचा प्रयत्न

प्रतिसाद देण्यापूर्वी मॉडेल किती "विचार" करते हे नियंत्रित करते.

| मूल्य    | यासाठी वापरा                                      |
| -------- | ------------------------------------------------- |
| `none`   | तर्कशक्ती नाही — थेट प्रतिसाद                     |
| `low`    | किरकोळ कार्ये (नामांतर, स्वरूपन)                  |
| `medium` | निर्दिष्ट न केल्यास **सर्व्हर डीफॉल्ट**           |
| `high`   | मध्यम स्तरावरील कार्ये (रिफॅक्टरिंग, डीबग)        |
| `xhigh`  | आर्किटेक्चर, सखोल विश्लेषण, गुंतागुंतीच्या समस्या |

```bash
# प्रत्येक आवाहनासाठी ओव्हरराइड
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

Desktop केवळ एन्क्रिप्ट केलेले ब्लॉब्स न दाखवता विचारांचा मजकूर रेंडर करू शकेल यासाठी तर्कशक्तीचा **सारांश** देखील सेट करा:

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # किंवा समर्थित असताना ultra
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute विचार बजेट (सर्व्हर सेटिंग)

OmniRoute होस्टवर, Codex चा प्रयत्न/सारांश अपस्ट्रीमपर्यंत पोहोचण्यासाठी **Settings → AI → Thinking Budget** हे **`passthrough`** असणे आवश्यक आहे. **`auto` मोड** सर्व क्लायंट `reasoning` / `reasoning_effort` फील्ड्स काढून टाकतो आणि Codex योग्यरीत्या कॉन्फिगर केलेले असतानाही विचार पॅनेल्स रिकामे ठेवतो.

संपूर्ण मार्गदर्शक: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

कॉम्प्रेशन आणि प्रॉम्प्ट कॅश स्वतंत्र आहेत आणि `passthrough` अंतर्गत कार्यरत राहतात.

## प्रोफाइल्स — प्रत्येक मॉडेल/वर्कफ्लोसाठी नामांकित कॉन्फिगरेशन्स

प्रोफाइल्समुळे तुम्ही एका फ्लॅगने मॉडेल + कॉन्टेक्स्ट विंडो बदलू शकता. प्रत्येक प्रोफाइल ही एक सपाट
`~/.codex/<name>.config.toml` फाइल असते, जी मूलभूत `config.toml` वर ओव्हरले केली जाते.

> **नामकरण नियम (Codex CLI v0.137+):** फाइल `~/.codex/<name>.config.toml` असली पाहिजे — **`profile-` उपसर्ग नसावा**.
> CLI `-p kimi-k27` → `~/.codex/kimi-k27.config.toml` असे निराकरण करते. फाइल न सापडल्यास, डीफॉल्ट कोणतीही सूचना न देता लागू होते.

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # जलद, स्वस्त
```

## `omniroute setup-codex` वापरून प्रोफाइल स्वयंचलितपणे तयार करणे

तुम्ही OmniRoute एखाद्या VPS वर चालवत असल्यास, थेट मॉडेल कॅटलॉगमधून प्रोफाइल फाइल्स स्वयंचलितपणे तयार करू शकता:

```bash
# VPS वरून (पोर्ट 20128 वरील स्थानिक OmniRoute वापरते)
omniroute setup-codex

# कोणत्याही मशीनवरून — तुमच्या VPS कडे निर्देशित करा
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# फाइल्स न लिहिता पूर्वावलोकन करा
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# फक्त GLM आणि Kimi प्रोफाइल तयार करा
omniroute setup-codex --only glm,kimi

# सानुकूल डिरेक्टरीमध्ये लिहा
omniroute setup-codex --codex-home /path/to/.codex
```

ही कमांड `/v1/models` मिळवते, ज्ञात मॉडेल्ससाठी अनुकूलित प्रोफाइल वापरते, इतर सुसंगत मजकूर मॉडेल्ससाठी कॅटलॉग मेटाडेटाचा पर्याय म्हणून वापर करते आणि प्रत्येकासाठी `~/.codex/<name>.config.toml` लिहिते. ही आयडेम्पोटंट आहे — पुन्हा चालवणे सुरक्षित आहे.

यशस्वी प्रदाता मॉडेल शोध/आयात प्रक्रियेमुळे थेट कॅटलॉग बदलल्यानंतर OmniRoute याच प्रोफाइल फाइल्स **स्वयंचलितपणे समक्रमित** देखील करू शकते. हे **निवड-आधारित असून डीफॉल्टनुसार बंद असते**: **CLI Code dashboard** मधून ते टॉगल करा ("CLI profile auto-sync" → Codex), किंवा `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` सेट करा (हे `CLI_ALLOW_CONFIG_WRITES` चादेखील आदर करते, जे डीफॉल्टनुसार सुरू असते). सक्षम केल्यावर ते फक्त स्वतंत्र `~/.codex/*.config.toml` प्रोफाइल फाइल्स लिहिते; ते सक्रिय/डीफॉल्ट `~/.codex/config.toml`, Codex-lb सेटिंग्ज, प्रमाणीकरण किंवा प्रदाता निवड कधीही बदलत नाही.

## `omniroute launch-codex` वापरून Codex सुरू करणे

Codex सुरू करण्यापूर्वी तुमच्या OmniRoute इंस्टन्सची आरोग्य-तपासणी करते:

```bash
# स्थानिक OmniRoute विरुद्ध सुरू करा (डीफॉल्ट पोर्ट 20128)
omniroute launch-codex

omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# codex ला अतिरिक्त आर्ग्युमेंट्स द्या
omniroute launch-codex --profile glm52 -- --yolo "fix this bug"
```

Codex हे दोन सर्वसाधारण मॅनिफेस्ट-आधारित प्रवेशबिंदूंचेदेखील लक्ष्य आहे

```bash
omniroute configure codex

# -c फ्लॅगद्वारे omniroute प्रदाता अंतःक्षेपित करून codex सुरू करा (कोणतेही कॉन्फिग लिहिले जात नाही)
omniroute run codex
```

## दीर्घकाळ चालणारी कार्ये

OmniRoute ची दोन डीफॉल्ट मूल्ये अनेक तास चालणारी Codex CLI सत्रे कोणतीही सूचना न देता बिघडवू शकतात. यापैकी कोणतेही Codex CLI सेटिंग नाही — दोन्ही OmniRoute च्या बाजूला असतात. खाती पिन करणाऱ्या आणि निष्क्रियता कटऑफ अक्षम करणाऱ्या अपस्ट्रीम प्रॉक्सीवरून कॉन्फिगरेशन स्थलांतरित करणाऱ्या वापरकर्त्यांना अनेकदा या दोन्ही समस्या येतात आणि ते असा निष्कर्ष काढतात की OmniRoute “दीर्घ सत्र टिकवून ठेवू शकत नाही.”

| लक्षण                                                                         | संभाव्य कारण                                                                          | नियंत्रण                 |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------ |
| सत्र सतत खाती बदलते / टर्नदरम्यान प्रॉम्प्ट-कॅश सातत्य हरवते                  | सत्र अॅफिनिटी TTL `0` आहे (अक्षम)                                                     | `sessionAffinityTtlMs`   |
| क्लायंटला दिसणाऱ्या कोणत्याही प्रॉम्प्टशिवाय रिझनिंगच्या मध्यात कनेक्शन तुटते | कोणताही अपस्ट्रीम चंक न आल्याने 10 मिनिटांनंतर स्ट्रीम निष्क्रियता वॉचडॉग सक्रिय झाला | `STREAM_IDLE_TIMEOUT_MS` |

संबंधित चर्चा: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (दीर्घ कार्य खंडित होणे), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (अॅफिनिटी डीफॉल्टनुसार बंद का असते). ट्रॅकिंग: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. सत्र अॅफिनिटी — एक संभाषण एका खात्याशी पिन करा

**डीफॉल्ट:** `sessionAffinityTtlMs = 0` (अक्षम).

**ते कुठे सेट करावे**

- डॅशबोर्ड → **सेटिंग्ज → राउटिंग** → **सत्र अॅफिनिटी** → **अॅफिनिटी TTL (सेकंद)** (`ComboDefaultsTab`)
- किंवा **मिलिसेकंदांमध्ये** `sessionAffinityTtlMs` सह PATCH सेटिंग्ज (Zod श्रेणी `0`–`86_400_000`, म्हणजे कमाल 24 तास)

> #7274 मध्ये Codex-पुरत्या `codexSessionAffinityTtlMs` वरून नाव बदलले. जुनी की अजूनही केवळ-वाचन उपनाव म्हणून स्वीकारली जाते; नवीन कॉन्फिगरेशनने `sessionAffinityTtlMs` वापरावे. TTL `0` पेक्षा जास्त झाल्यानंतर अॅफिनिटी आता केवळ Codex नव्हे, तर **कोणत्याही** प्रोव्हायडरला लागू होते — [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → सत्र अॅफिनिटी पहा.

**ते 0 वर राहिल्यास काय बिघडते**

अनेक टर्न असलेल्या Codex संभाषणाचा प्रत्येक टर्न सक्रिय कॉम्बो धोरणाद्वारे स्वतंत्रपणे राउट केला जातो आणि **प्रत्येक टर्नला वेगळ्या खात्यावर** जाऊ शकतो. यामुळे अपस्ट्रीम सत्र / प्रॉम्प्ट-कॅश सातत्य बिघडते. TTL `0` पेक्षा जास्त असेल तेव्हाच OmniRoute Codex सत्र हेडर (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) आणि `prompt_cache_key` / `session_id` सारखी बॉडी फील्ड तपासते (`src/sse/services/auth.ts` मधील `extractSessionAffinityKey`).

**अनेक तास चालणाऱ्या एकाच कार्यासाठी शिफारस**

TTL हे **कार्याच्या अपेक्षित वास्तविक कालावधीपेक्षा जास्त** सेट करा (UI मधील कमाल मर्यादा **86400 सेकंद** = 24 तास आहे):

| अपेक्षित कार्य कालावधी | अॅफिनिटी TTL (UI, सेकंद) | `sessionAffinityTtlMs` |
| ---------------------- | ------------------------ | ---------------------- |
| काही तास               | `14400` (4 तास)          | `14400000`             |
| रात्रभर / ~12 तास      | `43200` (12 तास)         | `43200000`             |
| पूर्ण दिवस             | `86400` (24 तास, कमाल)   | `86400000`             |

निवडाधारित वापर हेतुपुरस्सर आहे: अॅफिनिटी अक्षम केल्यास खात्यांमधील लोड-बॅलन्सिंगला प्राधान्य मिळते; ती सक्षम केल्यास एका दीर्घ एजंट सत्राच्या सातत्याला प्राधान्य मिळते. हे मार्गदर्शक डीफॉल्ट **बदलत नाही** — दीर्घ Codex कार्ये चालवणाऱ्या ऑपरेटरनी ते स्वतः सक्षम करणे आवश्यक आहे.

### 2. स्ट्रीम निष्क्रियता कालबाह्यता — शांत रिझनिंग टर्न बंद करू नका

**डीफॉल्ट:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 मिनिटे). सेट केलेले नसल्यास ते `REQUEST_TIMEOUT_MS` कडून मूल्य वारशाने घेते; सामायिक आधाररेखादेखील 600000 आहे. [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → कालबाह्यता पहा.

**डीफॉल्टवर काय बिघडते**

10 मिनिटांपेक्षा जास्त वेळ **एकही वास्तविक अपस्ट्रीम चंक न मिळता** शांत राहणारी Codex रीझनिंग / टूल टर्न SSE निष्क्रियता वॉचडॉगद्वारे (`open-sse/utils/stream.ts`) सक्तीने बंद केली जाते. क्लायंटला अनेकदा कोणत्याही संदेशाशिवाय कनेक्शन तुटल्याचे दिसते — जे “कोणतीही सूचना न देता आपोआप थांबले” याच्याशी जुळते.

महत्त्वाचा तपशील: OmniRoute चे कृत्रिम SSE **हार्टबीट निष्क्रियतेचे घड्याळ रीसेट करत नाही**. केवळ वास्तविक अपस्ट्रीम बॉडी चंक `lastChunkTime` अद्ययावत करतो. अद्याप “विचार करत” असलेले शांत मॉडेल वॉचडॉगच्या दृष्टीने अडकलेल्या अपस्ट्रीमसारखेच दिसते.

संबंधित Undici बॉडी निष्क्रियता: `FETCH_BODY_TIMEOUT_MS` (याचे डीफॉल्टही समान 10-मिनिटांची आधारमर्यादा आहे; `0` ते अक्षम करते). स्ट्रीमिंगसाठी, `FETCH_TIMEOUT_MS` फक्त कनेक्शन सेटअप / प्रारंभिक हेडर्सचा कालावधी व्यापते — स्ट्रीम सक्रिय झाल्यानंतर, अडथळे `STREAM_IDLE_TIMEOUT_MS` आणि `FETCH_BODY_TIMEOUT_MS` द्वारे नियंत्रित केले जातात.

**अनेक तास चालणाऱ्या एका टास्कसाठी शिफारस**

OmniRoute प्रोसेस एन्व्हायर्नमेंटमध्ये (`.env` / compose / systemd):

```bash
# दीर्घ रीझनिंग टर्नसाठी स्ट्रीम निष्क्रियता + बॉडी निष्क्रियता कटऑफ अक्षम करा
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

किंवा तुम्हाला अपेक्षित असलेल्या सर्वांत दीर्घ शांत कालखंडापेक्षा त्यांची मूल्ये जास्त ठेवा (मूल्ये मिलिसेकंदांत आहेत):

```bash
# उदाहरण: अपस्ट्रीम चंक्सदरम्यान कमाल 2 तासांच्या शांततेला अनुमती द्या
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

ही एन्व्हायर्नमेंट व्हेरिएबल्स बदलल्यानंतर OmniRoute रीस्टार्ट करा.

### ठोस कृतीक्रम — अनेक तास चालणारा Codex टास्क

1. **अकाउंट पिन करा:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12 तास) किंवा `86400` (कमाल 24 तास).
2. OmniRoute च्या एन्व्हायर्नमेंटमध्ये **निष्क्रियता कटऑफ वाढवा / अक्षम करा**:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. नेहमीचे Codex `config.toml` (`wire_api = "responses"`, योग्य `base_url`, `OMNIROUTE_API_KEY`) कायम ठेवा — या दोन वर्तनांसाठी Codex कडे affinity/idle नियंत्रणे उपलब्ध नाहीत.
4. OmniRoute रीस्टार्ट करा, त्यानंतर दीर्घ Codex टास्क सुरू करा.

### डीफॉल्ट्सबाबत निर्णय (#7287)

| नियंत्रण                 | पाठवले जाणारे डीफॉल्ट | या मार्गदर्शिकेत बदलायचे?                                                                             |
| ------------------------ | --------------------- | ----------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (बंद)             | **नाही** — पर्यायीच राहते (लोड-बॅलन्सिंग विरुद्ध सातत्य; Discussion #5718 पहा)                        |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 मिनिटे)  | **नाही** — सर्वसाधारण ट्रॅफिकसाठी 10 मिनिटेच राहते; दीर्घ Codex चालवणारे ते वाढवतात किंवा अक्षम करतात |

यापैकी कोणतेही डीफॉल्ट जागतिक स्तरावर उलटवल्यास केवळ Codex साठी नव्हे, तर इन्स्टन्सच्या प्रत्येक क्लायंटसाठी वर्तन बदलेल. या नियंत्रणांचे दस्तऐवजीकरण करा; स्पष्ट ऑपरेटर निर्णय वेगळे सांगत नाही तोपर्यंत डीफॉल्ट्स तसेच ठेवा.

### निष्क्रियतेमुळे होणारे कटऑफ निदान करणे

निष्क्रियता वॉचडॉग सक्रिय झाल्यावर, OmniRoute खालील स्वरूपाची ओळ लॉग करते:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

`Idle timeout: no data from` शोधण्यासाठी grep वापरा (किंवा कोड `stream_idle_timeout` / त्रुटीचे नाव `StreamIdleTimeoutError`). प्रोव्हायडर सेगमेंट हे त्या विनंतीसाठी OmniRoute ने वापरलेले मूल्य असते (`codex`, दुसरा प्रोव्हायडर आयडी, किंवा अज्ञात असल्यास `provider`) — ते नेहमी अक्षरशः `codex` असेलच असे नाही.

## समस्यानिवारण

**`Error: wire_api = "chat" यापुढे समर्थित नाही`**
तुमच्या कॉन्फिगमधून `wire_api = "chat"` काढून टाका. `wire_api = "responses"` सेट करा किंवा हे फील्ड वगळा (v0.138 पासून डीफॉल्ट मूल्य `"responses"` आहे).

**`Error: model सापडले नाही`**
योग्य प्रिफिक्ससह मॉडेल OmniRoute मध्ये अस्तित्वात असल्याची खात्री करा. `omniroute models list` वापरा किंवा `/dashboard/providers/<provider>` उघडा.

**`प्रमाणीकरण त्रुटी`**
`OMNIROUTE_API_KEY` एक्सपोर्ट केले आहे याची खात्री करा: `echo $OMNIROUTE_API_KEY`.

**`ERROR: आवश्यक पर्यावरणीय चल उपलब्ध नाही: OMNIROUTE_API_KEY`**
पहिली विनंती करण्यापूर्वी env var अस्तित्वात असल्याची Codex खात्री करतो. संरक्षित सर्व्हरसाठी
वास्तविक की एक्सपोर्ट करा किंवा तुमच्या **स्थानिक** OmniRoute इन्स्टन्सला
प्रमाणीकरणाची आवश्यकता नसल्यास `OMNIROUTE_API_KEY=local` सारखे रिक्त नसलेले प्लेसहोल्डर वापरा.
तुम्ही ते `~/.bashrc` किंवा `~/.zshrc` मध्ये जोडले असल्यास शेल रीस्टार्ट करा.

**`कनेक्शन नाकारले`**
OmniRoute सुरू असल्याची आणि `base_url` मधील होस्ट/पोर्ट तुमच्या नेटवर्कसाठी (स्थानिक विरुद्ध Tailscale विरुद्ध VPS) योग्य असल्याची खात्री करा.

**कॉन्टेक्स्ट मर्यादेजवळ सत्र क्रॅश होते**
`model_context_window` आणि `model_auto_compact_token_limit` स्पष्टपणे सेट करा. वरील कॉन्टेक्स्ट विंडो तक्ता पाहा.

**कॉम्पॅक्शन खूप उशिरा सुरू होते**
`model_auto_compact_token_limit` विंडोच्या 80–85% पर्यंत कमी करा. ते कधीही 90% पेक्षा जास्त सेट करू नका.

**प्रोफाइल लोड होत नाही (`-p <name>` शांतपणे दुर्लक्षित केले जाते)**
फाइल `~/.codex/<name>.config.toml` येथे अस्तित्वात असल्याची खात्री करा (`profile-` प्रिफिक्स नसावा). `ls ~/.codex/*.config.toml` चालवा.

**दीर्घ Codex कार्य अर्ध्यातच खंडित होते / टर्नदरम्यान खाती बदलली जातात**
[दीर्घकाळ चालणारी कार्ये](#long-running-tasks) पाहा. सत्र-अफिनिटी सक्षम करा (TTL हा कार्याच्या कालावधीपेक्षा जास्त ठेवा) आणि `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS` वाढवा किंवा अक्षम करा. `Idle timeout: no data from` शोधण्यासाठी OmniRoute लॉगवर grep वापरा.
