> निवड केल्यावरच सक्षम, डीफॉल्टनुसार बंद (`modelVisibilityAllowlist`/`modelVisibilityDenylist` दोन्ही रिकामे असल्यास
> `/v1/models` कॅटलॉग आणि प्रत्येक `auto/*` उमेदवार पूल बाइट-टू-बाइट समान राहतो). खर्चाशी काहीही संबंध
> नसलेल्या कारणांसाठी निवडक मॉडेल यादी हवी असलेल्या ऑपरेटरसाठी हे
> `hidePaidModels`/`hideAutoCombos` (`src/lib/db/settings.ts`) चे समकक्ष सेटिंग आहे.

## हे का अस्तित्वात आहे

`hidePaidModels` "हे मॉडेल विनामूल्य आहे का?" याचे उत्तर देते आणि `hideAutoCombos` "`auto/*`
व्हर्च्युअल ids ची जाहिरात करावी का?" याचे उत्तर देते — यांपैकी कोणतेही सेटिंग ऑपरेटरला
मॉडेल्सचा कोणताही उपसंच निवडण्याची मुभा देत नाही (उदा. किंमतीपासून स्वतंत्रपणे, एखाद्या विशिष्ट
Claude Code / OpenCode क्लायंटला नेमकी कोणती मॉडेल्स दिसावीत ते सादर करणे). #11481 मध्ये ही
क्षमता दोन स्वतंत्र, निवड केल्यावरच सक्षम होणाऱ्या string-array सेटिंग्जच्या स्वरूपात जोडली आहे.

## सेटिंग्ज

| की                         | प्रकार     | डीफॉल्ट | अर्थ                                                              |
| -------------------------- | ---------- | ------- | ----------------------------------------------------------------- |
| `modelVisibilityDenylist`  | `string[]` | `[]`    | उमेदवाराशी जुळणाऱ्या नोंदी त्याला कॅटलॉग/उमेदवार पूलमधून लपवतात.  |
| `modelVisibilityAllowlist` | `string[]` | `[]`    | रिकामी नसल्यास, केवळ उमेदवाराशी जुळणाऱ्या नोंदीच दृश्यमान राहतात. |

दोन्ही सेटिंग्जमध्ये प्रत्येकी कमाल 200 वर्णांच्या जास्तीत जास्त 500 नोंदी स्वीकारल्या जातात
(`src/shared/validation/settingsSchemas.ts` मध्ये Zod-द्वारे प्रमाणीकरण केले जाते). नोंद खालीलपैकी एक असते:

- अचूक कॅटलॉग id — `"gpt-4o"` (मूळ model id) किंवा `"openai/gpt-4o"` (provider-prefix असलेला), किंवा
- `*`/`?` वापरणारा glob नमुना — उदा. `"openai/gpt-4*"` किंवा `"anthropic/*"` — याचे निराकरण
  त्याच सामायिक `globToRegex()` matcher (`src/shared/utils/globPattern.ts`) द्वारे केले जाते, जो
  आधीपासूनच `ModelRoutingSection` च्या प्रत्येक मॉडेलसाठीच्या combo mappings आणि
  `freeModels.ts::matchesOnlyPaidModels` द्वारे वापरला जातो.

प्राधान्यक्रम: denylist प्रथम तपासली जाते (नाकारलेली नोंद allowlist शी जुळली तरी ती नेहमी लपवली
जाते); allowlist रिकामी नसल्यास, केवळ तिच्याशी जुळणाऱ्या नोंदीच टिकून राहतात.

## एक नव्हे, दोन नियंत्रणबिंदू

#6512 मधून मिळालेला धडा (केवळ `hidePaidModels` आधारित कॅटलॉग फिल्टर असूनही `auto/*` ला सशुल्क
मॉडेलकडे रूट करता येत होते, कारण combo उमेदवार पूल स्वतंत्रपणे तयार केला जात होता) येथेही
तंतोतंत लागू होतो. जुळणी करणारे predicate `isModelExposureAllowed()`
(`src/shared/utils/modelExposureList.ts`) खालील दोन्ही ठिकाणांहून कॉल केले जाते:

- `src/app/api/v1/models/catalog.ts` — स्वतः `/v1/models` सूचीमध्ये, ज्या प्रत्येक स्रोताच्या त्याच
  5 नियंत्रणबिंदूंवर `shouldHidePaid()` आधीपासूनच नियंत्रण करते (स्थिर `PROVIDER_MODELS`,
  समक्रमित provider rows, custom rows, alias-backed rows, managed-fallback rows).
- `open-sse/services/autoCombo/modelExposureFilter.ts::filterModelExposureCandidates()` — याला
  `virtualFactory.ts::buildPreparedPool` मधून, समतुल्य `filterPaidOnlyCandidates()` कॉलनंतर लगेच
  कॉल केले जाते, जेणेकरून नाकारलेले मॉडेल कोणत्याही `auto/*` उमेदवार पूलमध्ये कधीही निवडले जाऊ नये.

## काय फिल्टर केले जात नाही

`hideAutoCombos` च्या विद्यमान वर्तनाप्रमाणे: **स्पष्टपणे** पाठवलेला model id (`auto/*` द्वारे
नव्हे आणि कॅटलॉग सूचीद्वारे शोधलेला नसलेला) dispatch च्या वेळी कधीही अवरोधित केला जात नाही —
फक्त जाहिरात/उमेदवार-पूल सदस्यता फिल्टर केली जाते. हे `hidePaidModels` पासून स्वतंत्र आहे;
ऑपरेटरला खर्चाशी काहीही संबंध नसलेल्या कारणांसाठी निवडक संच हवा असू शकतो, त्यामुळे दोन्ही
सेटिंग्ज स्वतंत्र AND-ed filters म्हणून एकत्र लागू होतात, अगदी `catalog.ts` मधील विद्यमान
multi-flag composition प्रमाणे.

सेटिंग्ज export (`GET /api/settings/export-json`) मध्ये इतर कोणत्याही settings field प्रमाणे
दोन्ही arrays जशाच्या तशा समाविष्ट होतात — `hidePaidModels` च्या combo-step export filter पेक्षा
वेगळे, येथे re-hydration चा कोणताही धोका नाही: export केलेल्या combo step मध्ये अंतर्भूत केलेला
नाकारलेला id ही ऑपरेटरची स्वतःची स्पष्ट routing निवड आहे, export boundary ने काढून टाकण्याची
गरज असलेली गोष्ट नाही.
