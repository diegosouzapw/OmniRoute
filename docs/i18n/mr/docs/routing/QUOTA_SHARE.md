## आढावा

कोटा शेअरिंग इंजिन प्रदात्याचा कालावधी-आधारित कोटा (उदा. Codex
ची 5-तासांची विंडो, Kimi 1500 req/h) समान कनेक्शन सामायिक करणाऱ्या अनेक API
कींमध्ये न्याय्य रीतीने वितरित करते.

**हे सोडवत असलेली समस्या:** OmniRoute एकाच अपस्ट्रीम प्रदाता खात्यासाठी अनेक API
की प्रॉक्सी करते. सामायिकरणाचे तर्कशास्त्र नसल्यास, की A कडून अचानक मोठ्या प्रमाणात आलेल्या विनंत्या
त्या तासासाठीचा प्रदाता कोटा संपवू शकतात, ज्यामुळे विंडो रीसेट होईपर्यंत की B आणि C अवरोधित राहतात.
इंजिन हे पुढील प्रकारे प्रतिबंधित करते:

1. प्रत्येक परिमाणासाठी (%, विनंत्या, टोकन, $) प्रत्येक कीच्या रोलिंग वापराचा मागोवा घेणे.
2. कार्य-संरक्षण करणारा न्याय्य-वाटा अल्गोरिदम लागू करणे: जागतिक पूल संतृप्त नसताना की निष्क्रिय
   वाट्यांमधून उधार घेऊ शकते.
3. विनंती अपस्ट्रीम एक्झिक्युटरपर्यंत पोहोचण्यापूर्वी हॉट पाथमध्ये (`chatCore.ts`) परिणामाची
   अंमलबजावणी करणे.

## अल्गोरिदम: कार्य-संरक्षण करणारा न्याय्य वाटा

`src/lib/quota/fairShare.ts` मध्ये अंमलात आणले आहे.

### मोड

| अट                                         | मोड      | वर्तन                                                                        |
| ------------------------------------------ | -------- | ---------------------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **उदार** | की जागतिक मर्यादेतून एकूण वापर वजा करून उरलेल्या मर्यादेपर्यंत उधार घेऊ शकते |
| `globalUsedPercent >= saturationThreshold` | **कठोर** | वैयक्तिक न्याय्य वाट्याची कठोरपणे अंमलबजावणी करा                             |

डीफॉल्ट `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`).

### प्रत्येक परिमाणासाठी निर्णय

पूलमधील प्रत्येक सक्रिय परिमाणासाठी, इंजिन पुढील गणना करते:

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

त्यानंतर:

- **`policy = hard`**: जर `consumed > fairShareAllowed` आणि मोड कठोर असेल → **अवरोधित करा**.
- **`policy = soft`**: जर `consumed > fairShareAllowed` आणि मोड कठोर असेल → **दंड लागू करा** (कॉम्बोमध्ये प्राधान्य कमी करा; कधीही पूर्णपणे अवरोधित करू नका).
- **`policy = burst`**: न्याय्य वाट्याकडे दुर्लक्ष करून जागतिक अतिरिक्त क्षमता उपलब्ध असेपर्यंत अनुमती द्या.

### निरपेक्ष कमाल मर्यादा

वाटपावरील `capValue` + `capUnit` ही मोड किंवा धोरणापासून स्वतंत्र असलेली कठोर कमाल मर्यादा आहे.
ज्या कोणत्याही परिमाणामध्ये `consumed >= capValue` असेल, ते नेहमी विनंती **अवरोधित करते**.

### बहु-परिमाण तपासणी

पूलमधील **कोणतेही** परिमाण विनंती अवरोधित करत असल्यास ती विनंती अवरोधित केली जाते. परिमाणे
स्वतंत्र असतात — 5h% संपल्याने weekly% परिमाणावर परिणाम होत नाही.

### उधार घेणे

उदार मोडमध्ये, ज्या कीचा वाटप केलेला हिस्सा पूर्णपणे वापरलेला नाही, ती इतर कींच्या
न वापरलेल्या वाट्यांमधील अतिरिक्त क्षमता वापरू शकते. सूत्र असे आहे:

```
maxAllowed = globalLimit - consumedByOtherKeys
```

येथे `consumedByOtherKeys = consumedTotal - consumedByThisKey`. जागतिक कमाल मर्यादा
(त्या परिमाणासाठी पूलची `limit`) नेहमीच कठोर कमाल मर्यादा असते.

## स्लाइडिंग विंडो काउंटर

`src/lib/quota/sqliteQuotaStore.ts` आणि `redisQuotaStore.ts` मध्ये अंमलात आणले आहे.

प्रत्येक `(apiKeyId, dimensionKey)` साठी दोन बकेट:

- `curr`: वर्तमान बकेट (`floor(nowMs / windowMs)`)
- `prev`: मागील बकेट (`curr - 1`)

प्रभावी रोलिंग मूल्य:

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**अचूकता**: ~99% अचूक. बकेटच्या सीमेवर त्रुटी ही विंडोच्या आकाराच्या कमाल 1%
असू शकते (2-बकेट अंदाज पद्धतीची अंतर्निहित मर्यादा).

### समवर्ती प्रक्रिया

SQLite ड्रायव्हर: प्रत्येक `(apiKeyId | dimensionKey)` कीसाठी इन-मेमरी म्युटेक्स
रीड-मॉडिफाय-राइट रेस प्रतिबंधित करते. हा पॅटर्न `src/sse/services/auth.ts` मधील
anti-thundering-herd पद्धतीसारखा आहे.

Redis ड्रायव्हर: अणुस्तरीय इन्क्रिमेंटसाठी Lua EVAL स्क्रिप्ट — एकाच Redis कमांडच्या रूपात चालते.

## ड्रायव्हर्स

### SQLite (डीफॉल्ट, 0-इन्स्टॉल)

- टेबल: `quota_consumption` (मायग्रेशन `073_quota_pools.sql` / `074_quota_consumption.sql` पहा).
- एकल-इन्स्टन्स डिप्लॉयमेंटसाठी सर्वोत्तम.
- सर्व कायमस्वरूपी डेटा विद्यमान OmniRoute SQLite DB (`DATA_DIR/storage.sqlite`) मध्ये असतो.

### Redis (पर्यायी, मल्टी-इन्स्टन्स)

- `ioredis` npm पॅकेज आवश्यक आहे.
- काउंटर Redis मध्ये संग्रहित केले जातात; मेटाडेटा (पूल्स/अलोकेशन्स) अजूनही SQLite मध्ये असतो.
- जिथे काउंटर सामायिक करणे आवश्यक आहे अशा मल्टी-रेप्लिका डिप्लॉयमेंटसाठी सर्वोत्तम.

### ड्रायव्हर्स बदलणे

सेटिंग्ज UI (`/dashboard/settings` → कोटा स्टोअर) द्वारे किंवा env vars द्वारे:

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

DB सेटिंगला env पेक्षा प्राधान्य असते. `driver=redis` असल्यास, परंतु URL उपलब्ध नसल्यास किंवा
`ioredis` इन्स्टॉल केलेले नसल्यास, फॅक्टरी SQLite वर परत जाते आणि इशारा लॉग करते.

ड्रायव्हर निवडीचा क्रम:

1. DB सेटिंग `quotaStore.driver`
2. Env `QUOTA_STORE_DRIVER`
3. डीफॉल्ट: `sqlite`

## बहु-आयाम

एका पूलमध्ये अनेक आयाम असू शकतात. प्रत्येक आयाम स्वतंत्र असतो:

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // या आयामासाठी ग्लोबल पूलची कमाल मर्यादा
}
```

**उदाहरण: Codex प्लॅन** (5h% + weekly%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

अनुमती मिळण्यासाठी विनंतीने सर्व आयामांच्या अटी पूर्ण केल्या पाहिजेत.

## पाइपलाइन इंटिग्रेशन

### PRE हुक (`open-sse/handlers/chatCore.ts`)

ऑथ आणि पॉलिसी तपासण्यांनंतर, अपस्ट्रीम एक्झिक्युटरच्या आधी चालतो:

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → प्रत्येक आयामासाठी getQuotaStore().peek()
      → fairShare.decideFairShare()
      → ब्लॉक असल्यास → 429 परत करा (buildErrorBody, कठोर नियम #12)
      → अनुमती + प्राधान्य कमी करणे असल्यास → उमेदवारावर quotaSoftPenalty=true सेट करा
  → executor.execute()
```

**फेल-ओपन**: `enforceQuotaShare` ने त्रुटी निर्माण केल्यास, `pino.warn` लॉगसह
विनंतीला पुढे जाण्याची अनुमती दिली जाते. यामुळे कोटा-इंजिनमधील बग सर्व
ट्रॅफिक ब्लॉक करण्यापासून प्रतिबंधित होतो.

### POST हुक (वापराची नोंद करा)

यशस्वी प्रतिसादानंतर:

```
एक्झिक्युटर यश परत करतो
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → प्रत्येक आयामासाठी getQuotaStore().consume()
      → फेल-ओपन: त्रुटी pino.warn म्हणून लॉग केल्या जातात, क्लायंटपर्यंत कधीही पोहोचवल्या जात नाहीत
```

**ड्रिफ्ट नोंद**: प्रतिसादानंतर `consume` अयशस्वी झाल्यास, रोलिंग काउंटर वास्तविक संख्येपेक्षा कमी मोजतो.
प्रदात्याकडून मिळणारा सॅच्युरेशन सिग्नल (उदा. `anthropic-ratelimit-unified-5h-utilization`)
पुढील विनंतीवर ग्लोबल अंदाज दुरुस्त करतो.

### कॉम्बो सॉफ्ट पेनल्टी (`open-sse/services/combo.ts`)

जेव्हा `decision.deprioritize === true` असते:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // डीफॉल्ट 0.7
}
```

इतर सर्व स्कोअरिंग घटकांनंतर पेनल्टी लागू केली जाते. ती सॅच्युरेट झालेली की
हार्ड-ब्लॉक न करता तिची निवड करण्याची ऑटो-कॉम्बो संभाव्यता कमी करते.

| `DimensionBar`         | प्रत्येक डायमेन्शनसाठी स्टॅक केलेला बार: प्रत्येक कीचा हिस्सा + एकूण वापर |

पृष्ठाचे हुक्स:

- `usePools` — दर 30 सेकंदांनी `GET /api/quota/pools` प्राप्त करतो.
- `usePoolUsage` — मागणीनुसार `GET /api/quota/pools/[id]/usage` प्राप्त करतो.
- `useLocalStoragePoolMigration` — लेगसी LS डेटा स्थलांतरित करण्यासाठी माउंट होताना एकदा चालतो.

### `/dashboard/costs/quota-share/plans` — प्रदाता प्लॅन कॉन्फिगरेशन

- `ProviderPlanConfigClient.tsx`: प्रदाता निवडण्यासाठी, निश्चित केलेला प्लॅन
  (कॅटलॉगमधून स्वयंचलित किंवा मॅन्युअल ओव्हरराइड) पाहण्यासाठी आणि डायमेन्शन्स संपादित करण्यासाठी ड्रॉपडाउन.

## समस्या निवारण

### Redis कॉन्फिगर केलेले आहे, परंतु कनेक्ट होत नाही

`ioredis` इन्स्टॉल केलेले आहे (`npm ls ioredis`) आणि `QUOTA_STORE_REDIS_URL`
पर्यंत पोहोचता येते हे तपासा. कनेक्शन अयशस्वी झाल्यास फॅक्टरी SQLite वर
फॉलबॅक करते (`warn` स्तरावर नोंद केली जाते).

### `peek` जुना डेटा परत करते / फेल-ओपन होते

`peek` ने अपवाद दिल्यास, `enforceQuotaShare` परिणामाला "परवानगी द्या" (फेल-ओपन)
असे मानते. मूळ कारण ओळखण्यासाठी `pino` लॉगमधील `quota:enforce` आणि
`quota:factory` नोंदी तपासा.

### वापर काउंटरमध्ये तफावत

प्रत्यक्ष प्रदाता वापर काउंटर्सपेक्षा वेगळा असल्यास ते अपेक्षित आहे — 2-बकेट
स्लाइडिंग विंडोमध्ये विंडो सीमांवर ~1% त्रुटी असते आणि `consume` हे
प्रतिसादानंतर फायर-अँड-फरगेट पद्धतीने चालते. सॅच्युरेशन सिग्नल
(`saturationSignals.ts`) 30 सेकंदांच्या TTL सह प्रदात्याचा प्रत्यक्ष वापर
वाचतो आणि त्यानुसार `globalUsedPercent` समायोजित करतो.

### पूलच्या वापर-दरासाठी "डेटा नाही" दिसते

`computeBurnRate` साठी किमान 2 ऐतिहासिक नमुने आवश्यक आहेत. पूर्वीचे `consume`
कॉल नसलेल्या नवीन पूलमध्ये `tokensPerSecond: 0` आणि `timeToExhaustionMs: null`
दिसेल.

## localStorage मधून स्थलांतर

`/dashboard/costs/quota-share` प्रथम लोड झाल्यावर, `useLocalStoragePoolMigration` हुक पुढील बाबी तपासतो:

1. `localStorage.getItem("omniroute:quota-share:pools")` रिक्त नाही.
2. `GET /api/quota/pools` हे `[]` परत करते (DB रिक्त आहे).

दोन्ही अटी सत्य असल्यास, तो प्रत्येक लेगसी पूल बॅचमध्ये `POST /api/quota/pools` वर पोस्ट करतो आणि त्यानंतर localStorage की काढून टाकतो. हे स्थलांतर आयडेम्पोटंट आहे: अट 2 पुन्हा स्थलांतर होण्यापासून प्रतिबंध करते.

## अंतर्गत धोरण वर्गीकरण

`quota-share` हे **केवळ-अंतर्गत** राउटिंग धोरण आहे (`src/shared/constants/routingStrategies.ts` मधील `INTERNAL_ROUTING_STRATEGY_VALUES`). ते केवळ सिस्टीमद्वारे तयार केलेल्या `qtSd/` पूल कॉम्बोंसाठी वापरले जाते आणि ते `ROUTING_STRATEGY_VALUES` मधून जाणीवपूर्वक वगळले आहे, जेणेकरून ते UI किंवा API मध्ये वापरकर्त्याला निवडता येणारा पर्याय म्हणून कधीही दिसणार नाही.

## DB स्कीमाचा सारांश

`078`, `079` आणि `085` स्थलांतरांद्वारे तीन टेबल जोडले आहेत:
