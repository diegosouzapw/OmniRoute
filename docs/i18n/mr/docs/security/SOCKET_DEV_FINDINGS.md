हा दस्तऐवज `omniroute@3.8.5` विरुद्ध नोंदवलेल्या सहा
`AI-द्वारे आढळलेले संभाव्य मालवेअर` निष्कर्षांसाठी आणि
`omniroute@3.8.6` मध्ये लागू केलेल्या उपाययोजनांसाठी देखभालकर्त्याने लिहिलेले सत्यापन आहे. हा दस्तऐवज यासाठी अस्तित्वात आहे:

1. सुरक्षा-पाइपलाइन संचालकांना प्रत्यक्ष स्रोताच्या संदर्भात निष्कर्षांचे
   मूल्यमापन करताना उद्धृत करण्यासाठी एकच संदर्भ उपलब्ध असावा.
2. भविष्यातील AI स्कॅनर्सना देखभालकर्त्याने स्वाक्षरी केलेला हा दावा ओळखता यावा की
   चिन्हांकित केलेला प्रत्येक मार्ग हेतुपुरस्सर, स्वेच्छेने निवडण्यायोग्य आणि दस्तऐवजीकृत आहे.
3. प्रत्येक कॉल साइटची रचना अशी _का_ आहे याची लिखित नोंद आमच्याकडे असावी —
   जेणेकरून भविष्यातील रिफॅक्टरिंगमुळे जाणीवपूर्वक काढून टाकलेला फिंगरप्रिंट
   चुकून पुन्हा निर्माण होणार नाही.

v3.8.6 मधील उपाययोजना जारी झाल्यानंतर खालीलपैकी कोणतीही कॉल साइट पुन्हा
चिन्हांकित करणारा स्कॅनर तुम्ही चालवत असल्यास, कृपया स्कॅन ट्रेससह एक इश्यू उघडा आणि
आम्ही येथे सत्यापनाचा विस्तार करू.

## §1 — MITM रूट-CA स्थापना (`77484.js`)

**स्रोत फाइल्स**:

- `src/mitm/cert/install.ts` — सार्वजनिक `installCert()` / `uninstallCert()`,
  प्रत्येक प्लॅटफॉर्मसाठी `installCertWindows/Mac/Linux`.
- `src/mitm/systemCommands.ts` — स्थापना मार्गांद्वारे वापरले जाणारे सामायिक `execFile` / `spawn` / PowerShell
  सहाय्यक.

**ट्रिगर**: वापरकर्ता स्थानिक डॅशबोर्डमधील
`/dashboard/cli-tools/mitm` येथे "MITM प्रॉक्सी सक्षम करा" वर क्लिक करतो. हा रूट केवळ लूपबॅकसाठी आहे —
`CLAUDE.md` मधील कठोर नियम #17 आणि `src/server/authz/routeGuard.ts::isLocalOnlyPath()` पहा. टनेलद्वारे उघड झालेला
JWT हा कोड मार्ग ट्रिगर **करू शकत नाही**.

**केलेल्या विशेषाधिकारप्राप्त क्रिया (प्रत्येक प्लॅटफॉर्मनुसार)**:

| OS                     | कमांड                                                                                                             |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | UAC द्वारे `certutil -addstore Root <cert>`                                                                       |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | `certutil -d sql:<profile>` द्वारे प्रत्येक प्रोफाइलसाठी NSS DB अद्यतन                                            |

या त्याच कमांड `mitmproxy`, Charles Proxy, Fiddler आणि
Caddy द्वारे वापरल्या जातात. त्या OmniRoute मध्ये अस्तित्वात आहेत ही बाब
`docs/security/STEALTH_GUIDE.md` येथे दस्तऐवजीकृत आहे.

**v3.8.6 मधील उपाययोजना**:

- `runElevatedPowerShell()` आता `-EncodedCommand <base64utf16le>` वापरत नाही.
  उन्नत विशेषाधिकारांसह चालवायचा पेलोड प्रत्येक कॉलसाठीच्या तात्पुरत्या `.ps1` फाइलमध्ये लिहिला जातो (मोड 0o600,
  खासगी `mkdtempSync` डिरेक्टरीमध्ये) आणि `-File` द्वारे संदर्भित केला जातो.
  `finally` मध्ये फाइल अनलिंक केली जाते. यामुळे Socket.dev च्या AI
  क्लासिफायरने चिन्हांकित केलेला PowerShell-द्वारे-base64-एलिव्हेशनचा प्रचलित फिंगरप्रिंट काढून टाकला जातो.
- `installCertWindows` मध्ये येथे निर्देश करणारा इनलाइन `SECURITY-AUDITOR-NOTE:` ब्लॉक
  आहे.

**आम्ही हे का ठेवतो**: MITM प्रॉक्सी हे
`docs/security/STEALTH_GUIDE.md` आणि `docs/frameworks/MITM-PROXY.md` द्वारे वापरले जाणारे दस्तऐवजीकृत वैशिष्ट्य आहे. ते काढून टाकल्यास
एजंट-ब्रिज वैशिष्ट्यांचा संच कार्य करणार नाही.

## §2 — Zed क्रेडेन्शियल आयात (`app/api/providers/zed/import/route.js`)

**स्रोत फाइल्स**:

- `src/app/api/providers/zed/discover/route.ts` _(v3.8.6 मध्ये नवीन)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(v3.8.6 मध्ये नवीन)_

**ट्रिगर**: वापरकर्ता स्थानिक डॅशबोर्डच्या Providers पृष्ठावरील "Zed मधून आयात करा" यावर क्लिक करतो. एंडपॉइंट `requireManagementAuth` द्वारे संरक्षित आहे. Zed एडिटर स्वतःच्या प्रोव्हायडर API कीज दस्तऐवजीकृत सेवा नावांखाली OS कीचेनमध्ये लिहितो — https://zed.dev/docs/ai/llm-providers पहा.

**v3.8.5 मधील वर्तन (जे Socket.dev ने ध्वजांकित केले)**:

`POST /import` क्रेडेन्शियल्स शोधून एका फेरीत स्थानिक SQLite स्टोअरमध्ये आपोआप जतन करत असे. प्रत्येक खात्यासाठी स्वतंत्र पुष्टीकरण नाही, फिंगरप्रिंट नाही; फक्त "N टोकन सापडले, सर्व आयात केले."

**v3.8.6 मधील शमन — 2-टप्प्यांचे पुष्टीकरण**:

1. **`POST /api/providers/zed/discover`**
   `{ candidates: [{ provider, service, account, fingerprint }] }` परत करते. मूळ
   टोकन **कधीही** प्रसारित केले जात नाही. फिंगरप्रिंट
   `sha256(service|account|token).slice(0,16)` आहे.
2. डॅशबोर्ड उमेदवारांची यादी प्रदर्शित करतो, ऑपरेटर आयात करायची खाती निवडतो
   आणि `{ confirmedAccounts: [{ service, account, fingerprint }] }`
   **`POST /api/providers/zed/import`** कडे पोस्ट करतो.
3. आयात एंडपॉइंट **सर्व्हरवर कीचेन पुन्हा वाचतो** आणि
   `(service, account, fingerprint)` नुसार फिल्टर करतो. फेरफार केलेला किंवा पुन्हा वापरलेला discover
   प्रतिसाद आयात एंडपॉइंटला असंबंधित टोकन जतन करण्यास भाग पाडू शकत नाही —
   discover नंतर प्रत्यक्ष टोकन बदलले असल्यास, फिंगरप्रिंट यापुढे जुळत नाही
   आणि ते क्रेडेन्शियल वगळले जाते.

`OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` env फ्लॅग, ज्यांनी अद्याप त्यांचे ऑटोमेशन अद्ययावत केलेले नाही अशा ऑपरेटर्ससाठी v3.8.5 मधील वर्तन कायम ठेवतो. तो v3.9 मध्ये काढून टाकला जाईल.

**आम्ही ते का ठेवतो**: जे वापरकर्ते आधीपासून Zed वापरतात आणि त्यांच्या प्रोव्हायडर कीज पुन्हा पेस्ट न करता OmniRoute मध्ये प्रतिबिंबित करू इच्छितात, त्यांच्यासाठी Zed आयात हा सर्वांत सुलभ ऑनबोर्डिंग मार्ग आहे.

## §3 — `execFile` / `spawn` / उन्नत PowerShell (`21843.js`)

**स्रोत फाइल्स**: `src/mitm/systemCommands.ts`.

**ध्वजांकित करण्याचे कारण**: हा चंक `execFileWithPassword`,
`runElevatedPowerShell` आणि सामायिक `quotePowerShell` हेल्पर पुन्हा निर्यात करतो. Socket.dev चा
AI क्लासिफायर त्यांना सर्वसाधारण "होस्ट एक्झिक्युशन + विशेषाधिकार उन्नयन
टूलकिट" म्हणून ओळखतो. OmniRoute मध्ये ते केवळ MITM प्रमाणपत्र इंस्टॉल मार्गाद्वारे
(§1) आणि `sudo` कमांड एक्झिक्युशनसाठी `execFileWithPassword` द्वारे वापरले जातात.

**v3.8.6 मधील शमन**:

- `runElevatedPowerShell` चे रिफॅक्टरिंग (§1 पहा).
- `runElevatedPowerShell` आणि `execFileWithPassword` या दोन्ही ठिकाणी असलेला इनलाइन
  `SECURITY-AUDITOR-NOTE:` ब्लॉक अनुमत-सूचीतील कॉलर्स आणि निश्चित एक्झिक्युटेबल्सची यादी
  दस्तऐवजीकृत करतो.
- `execFileWithPassword` मधील `spawn()` कॉलमध्ये हेल्परला स्वीकारण्याची परवानगी असलेल्या
  एक्झिक्युटेबल्सच्या अनुमत-सूचीसह `nosemgrep` मार्कर आहे — वापरकर्ता इनपुटपासून
  `finalCommand`/`finalArgs` पर्यंत **कोणताही मार्ग नाही**.

## §4 / §6 — 9router सेवा पर्यवेक्षक (`api/services/9router/{start,restart}/route.js`)

**स्रोत फाइल्स**:

- `src/app/api/services/9router/_lib.ts` — पर्यवेक्षक फॅक्टरी.
- `src/app/api/services/9router/{start,stop,restart,status,install,update,auto-start}/route.ts`.
- `src/lib/services/ServiceSupervisor.ts` — सर्वसाधारण spawn / आरोग्य-पोल / लॉग-बफर.

**ट्रिगर**: वापरकर्ता स्थानिक डॅशबोर्डमधील एम्बेडेड सेवा पृष्ठावर "इंस्टॉल करा" / "सुरू करा" यावर क्लिक करतो.

**आधीपासून अस्तित्वात असलेली संरक्षणे**:

- `src/server/authz/routeGuard.ts` नुसार सर्व `/api/services/*` रूट्स LOCAL_ONLY आहेत
  (कठोर नियम #17). कोणत्याही प्रमाणीकरण तपासणीपूर्वी लूपबॅकची अंमलबजावणी
  होते — लीक झालेला JWT त्यांच्यापर्यंत पोहोचू शकत नाही.
- 9router DB रांग `status='not_installed', auto_start=0` अशा मूल्यांसह सीड केली जाते
  (`src/lib/db/migrations/071_services.sql:19` पहा). सेवा पहिल्यांदा सुरू करताना
  **सुरू होत नाही**.
- `spawn()` ला
  `src/lib/services/installers/ninerouter.ts` मधील `resolveSpawnArgs(apiKey, PORT)` ने परत केलेल्या बायनरी पाथसह कॉल केले जाते,
  जी समर्थित बायनरीजची निश्चित अनुमत-सूची आहे.
- Stdout/stderr मेमरीमध्ये बफर केले जाते (5 MB मर्यादा, `_lib.ts` पहा) — वापरकर्त्याने
  डॅशबोर्डमधून लॉगिंग सक्षम केल्याशिवाय डिस्कवर काहीही लिहिले जात नाही.

**v3.8.6 मधील शमन**: कोणताही कार्यात्मक बदल नाही. किमान बिल्ड प्रोफाइल
(`OMNIROUTE_BUILD_PROFILE=minimal`), ज्या वापरकर्त्यांना विशेषाधिकार असलेले मार्ग बंडलमधून
प्रत्यक्ष काढून टाकायचे आहेत त्यांच्यासाठी `src/lib/services/installers/ninerouter.ts`
ऐवजी स्टब वापरते.

**आम्ही ते का ठेवतो**: 9router ही वैकल्पिक, स्थानिकरीत्या इंस्टॉल करता येणारी सहयोगी
सेवा आहे (उदाहरणार्थ: WordPress-शैलीतील प्लगइन) — काटेकोरपणे स्वेच्छेने सक्षम करायची.

## §5 — OmniRoute Cloud Sync क्रेडेन्शियल राइट-बॅक (`api/keys/[id]/route.js`)

**स्रोत फाइल्स**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`.
- `src/app/api/keys/[id]/route.ts` — `syncKeysToCloudIfEnabled()` ला कॉल करते.

**ट्रिगर**: `isCloudEnabled()` हे `true` परत करते (डॅशबोर्डवरून सेट केलेले) **आणि**
`CLOUD_URL` कॉन्फिगर केलेले असते. दोन्ही बंद असल्यास, Cloud एंडपॉइंटवर कोणताही
आउटबाउंड नेटवर्क कॉल केला जात नाही.

**v3.8.5 मधील वर्तन (Socket.dev ने योग्य प्रकारे शोधलेला बग)**:

`cloudUpdatedAt > localUpdatedAt` असताना, `updateLocalTokens()` हे Cloud
प्रतिसादातील `accessToken`, `refreshToken`, आणि `providerSpecificData` वापरून
स्थानिक मूल्ये अधिलिखित करत होते. HMAC नाही, स्वाक्षरी नाही, चेकसम नाही.
चुकीच्या प्रकारे कॉन्फिगर केलेले किंवा दुर्भावनायुक्त `CLOUD_URL` (किंवा
चॅनेलवरील MITM) प्रोव्हायडरचे OAuth टोकन कोणतीही सूचना न देता बदलू शकत होते.

**v3.8.6 मधील उपाययोजना**:

1. **HMAC पडताळणी**: JSON पार्स करण्यापूर्वी `verifyCloudSignature(rawBody, sigHeader)`
   हे `X-Cloud-Sig` हेडरची (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`) पडताळणी करते. सीक्रेट सेट केलेले असल्यास, स्वाक्षरी आवश्यक असते.
   ते सेट केलेले नसल्यास (लेगसी मोड), चेतावणी लॉग केली जाते आणि प्रतिसाद
   स्वीकारला जातो — v3.9 मध्ये सीक्रेट अनिवार्य असेल.
2. **गोपनीय फील्डसाठी स्पष्ट संमती**: `accessToken` / `refreshToken` /
   `providerSpecificData` ही फील्ड **फक्त**
   `OMNIROUTE_CLOUD_SYNC_SECRETS=true` असताना अधिलिखित केली जातात. डीफॉल्ट
   मोडमध्ये फक्त क्रेडेन्शियल नसलेला मेटाडेटा (`expiresAt`, `status`,
   `lastError*`, `rateLimitedUntil`, `updatedAt`) सिंक केला जातो. रिमोट टोकन
   सिंकवर अवलंबून असलेल्या वापरकर्त्यांसाठी हा **ब्रेकिंग बदल** आहे — त्यांनी
   त्यासाठी स्पष्टपणे संमती द्यावी लागेल.

**आम्ही हे का ठेवले आहे**: टीमची क्रेडेन्शियल्स केंद्रीकृत करण्यासाठी OmniRoute
Cloud टेनंटकडे Cloud Sync हा एकमेव मार्ग आहे. या सुधारणेमुळे धोक्याचे मॉडेल
स्पष्ट होते: "सर्व्हर स्वाक्षरी करतो, क्लायंट पडताळणी करतो, ऑपरेटर संमती देतो."

## बिल्ड प्रोफाइल: `minimal`

Socket-अनुकूल आर्टिफॅक्ट आवश्यक असलेल्या वापरकर्त्यांनी पुढीलप्रमाणे बिल्ड करावे:

```bash
OMNIROUTE_BUILD_PROFILE=minimal npm run build
```

webpack मधील `NormalModuleReplacementPlugin` चार मॉड्यूल्सना स्टब्सशी जोडतो:

| मॉड्यूल                                     | स्टब                                             |
| ------------------------------------------- | ------------------------------------------------ |
| `src/mitm/cert/install.ts`                  | `src/mitm/cert/install.stub.ts`                  |
| `src/lib/zed-oauth/keychain-reader.ts`      | `src/lib/zed-oauth/keychain-reader.stub.ts`      |
| `src/lib/cloudSync.ts`                      | `src/lib/cloudSync.stub.ts`                      |
| `src/lib/services/installers/ninerouter.ts` | `src/lib/services/installers/ninerouter.stub.ts` |

प्रत्येक स्टब समान इंटरफेस एक्सपोर्ट करतो, परंतु रनटाइममध्ये प्रत्येक फंक्शन
`featureDisabledError(name)` थ्रो करते. अक्षम केलेल्या मॉड्यूलवर अवलंबून असलेले
रूट्स संवेदनशील कोड पाथ सक्रिय करण्याऐवजी स्पष्ट संदेशासह HTTP 503 परत करतात.

तयार होणारे बंडल `omniroute-secure` म्हणून प्रकाशित करण्यासाठी आहे. प्रकाशनाच्या
सूचनांसाठी `docs/ops/PUBLISHING_SECURE.md` पहा.
