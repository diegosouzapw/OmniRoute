TPROXY पारदर्शक डिक्रिप्ट हा OmniRoute च्या
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM स्टॅकसाठीचा **5वा कॅप्चर मोड** आहे. तो Linux वर kernel TPROXY + policy routing वापरून
स्थानिक आउटबाउंड HTTPS ट्रॅफिक इंटरसेप्ट आणि **डिक्रिप्ट** करतो — `/etc/hosts` ची
स्पूफिंग **न करता** आणि संपूर्ण OS वरील system-proxy सेटिंग्जमध्ये बदल **न करता**.
तो हेडलेस वातावरणासाठी अनुकूल आहे (साफ करण्यासाठी DNS बदल नसतात) आणि रीबूट झाल्यावर
फायरवॉल नियम आपोआप फ्लश होतात.

इतर कॅप्चर मोड्सच्या विपरीत, TPROXY साठी प्रत्येक होस्टनुसार स्वतंत्र सेटअप आवश्यक नसतो:
तो लक्ष्य पोर्टवरील **कोणत्याही** गंतव्य होस्टला जाणारे ट्रॅफिक पारदर्शकपणे इंटरसेप्ट करतो,
प्रत्येक SNI होस्टनावासाठी तत्काळ जारी केलेल्या लीफ सर्टिफिकेटद्वारे TLS समाप्त करतो,
डिक्रिप्ट केलेली देवाणघेवाण कॅप्चर करतो आणि विनंती मूळ गंतव्याकडे पुन्हा एन्क्रिप्ट करून पाठवतो.

> **केवळ Linux, केवळ root, ऑप्ट-इन.** या मोडसाठी Linux, C toolchain सह बिल्ड केलेले
> native addon आणि **CAP_NET_ADMIN** क्षमता (सामान्यतः root) आवश्यक आहे. हा मोड
> केवळ loopback साठी असलेल्या AgentBridge API मागे नियंत्रित केला जातो आणि डीफॉल्टनुसार
> अक्षम असतो. कोणत्याही होस्टसाठी स्वाक्षरी करू शकणारा विश्वसनीय MITM CA ही एक शक्तिशाली
> क्षमता आहे — [§6 सुरक्षा](#6-security) पहा.

**स्रोत:** `src/mitm/tproxy/`

## §1 हे काय आहे आणि ते कधी वापरावे

इतर चार कॅप्चर मोड्सपैकी प्रत्येकाची एक मर्यादा आहे:

| मोड                          | ट्रॅफिक कसे मार्गस्थ केले जाते                 | मर्यादा                                                   |
| ---------------------------- | ---------------------------------------------- | --------------------------------------------------------- |
| AgentBridge                  | निश्चित होस्ट संचाची `/etc/hosts` DNS स्पूफिंग | केवळ नोंदणीकृत IDE-agent होस्ट्स                          |
| सानुकूल होस्ट्स              | प्रत्येक होस्टसाठी `/etc/hosts` DNS स्पूफिंग   | प्रत्येक होस्टसाठी एक नोंद; hosts संपादित करण्यासाठी sudo |
| HTTP_PROXY                   | `HTTP_PROXY`/`HTTPS_PROXY` env                 | केवळ env var चे पालन करणारे ॲप्स                          |
| संपूर्ण प्रणालीसाठी प्रॉक्सी | OS प्रॉक्सी सेटिंग्ज                           | जागतिक स्थिती बदलते; पूर्ववत करणे आवश्यक                  |

त्याऐवजी TPROXY पारदर्शक डिक्रिप्ट **kernel** स्तरावर ट्रॅफिक मार्गस्थ करतो.
तो `mangle OUTPUT` साखळीत लक्ष्य पोर्टकडे (डीफॉल्ट `443`) जाणाऱ्या नवीन स्थानिक आउटबाउंड
TCP कनेक्शन्सना चिन्हांकित करतो, `ip rule` चिन्हांकित पॅकेट्सना स्थानिक वितरणाकडे
पुन्हा मार्गस्थ करतो आणि पुन्हा प्रवेश केल्यावर `mangle PREROUTING` मधील `TPROXY`
लक्ष्य ती पॅकेट्स **IP_TRANSPARENT** लिसनरकडे सोपवते — जो नंतर TLS समाप्त करून
प्लेनटेक्स्ट कॅप्चर करतो.

खालील वैशिष्ट्ये असलेल्या प्रक्रियेतील ट्रॅफिक कॅप्चर आणि डिक्रिप्ट करायचे असल्यास तो वापरा:

- ती AgentBridge मध्ये नोंदणीकृत नसलेल्या होस्टशी संवाद साधते, आणि
- ती `HTTP_PROXY` चे पालन करत नाही, आणि
- system-wide proxy बदल करून त्या प्रक्रियेत व्यत्यय आणायचा नाही.

इंटरसेप्शन kernel मध्ये होत असल्यामुळे, मूळ प्रक्रियेला **कोणताही कॉन्फिगरेशन बदल**
आवश्यक नसतो — मात्र प्रक्रियेने OmniRoute द्वारे स्थापित केलेल्या डायनॅमिक CA वर
विश्वास ठेवणे आवश्यक आहे ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) पहा).

## §2 आवश्यकता

| आवश्यकता           | तपशील                                                                                                                                                                   |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**             | केवळ Linux — **IP_TRANSPARENT** हा फक्त Linux वर उपलब्ध असलेला socket पर्याय आहे. इतर प्रत्येक प्लॅटफॉर्मवर loader "अनुपलब्ध" परत करतो.                                 |
| **विशेषाधिकार**    | transparent socket तयार करण्यासाठी आणि `iptables`/`ip` नियम लागू करण्यासाठी **CAP_NET_ADMIN** capability — प्रत्यक्ष वापरात, root म्हणून चालवा.                         |
| **Native addon**   | एक छोटा N-API addon (`src/mitm/tproxy/native/transparent.c`) build केलेला किंवा prebuild म्हणून पुरवलेला असणे आवश्यक आहे. [§3](#3-the-native-ip_transparent-addon) पहा. |
| **Kernel modules** | `TPROXY`, `mangle`, आणि `mark` match समर्थनासह `iptables` (kernel 6.8.0 वर पडताळलेले).                                                                                  |

**सुरळीत अवनती:** कोणतीही आवश्यकता उपलब्ध नसल्यास (Linux नसणे, toolchain नसणे,
addon build केलेला नसणे), addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
अपवाद फेकण्याऐवजी `null` परत करतो. त्यानंतर capture-mode स्थिती
`available: false` नोंदवते, dashboard toggle
"TPROXY decrypt साठी Linux + root + native addon आवश्यक आहे" या tooltip सह **अक्षम** केले जाते,
आणि OmniRoute चे उर्वरित कार्य सुरू राहते.

## §3 Native IP_TRANSPARENT addon

Node चे `net` module `bind()` करण्यापूर्वी `setsockopt(IP_TRANSPARENT)` करू शकत नाही,
आणि TPROXY साठी ते आवश्यक आहे (अन्यथा kernel redirect केलेली packets वगळतो). हा addon
(`src/mitm/tproxy/native/transparent.c`, `binding.gyp` द्वारे build केलेला) एक छोटा N-API
module आहे, जो तीन functions उघड करतो आणि त्या `transparentSocket.ts` द्वारे वापरल्या जातात:

| Addon function                        | Socket चे कार्य                                                                             | वापर                                                                            |
| ------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, raw fd परत करतो | transparent capture listener (Node `server.listen({ fd })` द्वारे fd स्वीकारतो) |
| `setSocketMark(fd, mark)`             | अस्तित्वात असलेल्या fd वर `setsockopt` **SO_MARK**                                          | anti-loop (proxy चे स्वतःचे sockets mark करणे)                                  |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()` च्या **आधी** `socket()` + **SO_MARK**, fd परत करतो                 | पुन्हा encrypt केलेले upstream forwarding (SYN सोबत mark असतो)                  |

मूळ destination `socket.localAddress`/`localPort` मधून वाचले जाते — TPROXY
ते जतन करतो, त्यामुळे **SO_ORIGINAL_DST**/NAT lookup आवश्यक नसतो.

### Addon build करणे

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- `npm run build` दरम्यान, `scripts/build/build-tproxy-native.mjs` हे `node-gyp
rebuild` चालवते. ते **केवळ Linux साठी असून अयशस्वी झाल्यास घातक नसते** — toolchain उपलब्ध नसल्यास
  capture mode फक्त अनुपलब्ध राहतो.
- `assembleStandalone.mjs` हे `build/Release/transparent.node` standalone
  bundle मध्ये copy करते; `transparentSocket.ts` त्याचे module-relative आणि
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`) अशा दोन्ही प्रकारे निराकरण करते.
- `build/` आणि `prebuilds/` git-ignored आहेत — binary **build केली जाते, कधीही
  commit केली जात नाही**.

Loader खालील प्राधान्यक्रमाने तपासणी करतो:
`native/build/Release/transparent.node`, त्यानंतर `native/prebuilds/transparent.node`
(दोन्ही module-relative आणि `<cwd>/src/mitm/tproxy/` अंतर्गत).

## §4 प्रति-SNI डायनॅमिक CA आणि ट्रस्ट-स्टोअर इंस्टॉलर

> **#6684 अद्यतन:** AgentBridge स्टॅटिक सर्व्हर (`src/mitm/server.cjs`) आता
> एकाच स्टॅटिक स्व-स्वाक्षरीकृत लीफऐवजी हाच CA/लीफ आर्किटेक्चर नमुना
> वापरतो. तो **स्वतंत्र** CA इन्स्टन्स
> (`src/mitm/cert/rootCa.ts`, `<DATA_DIR>/mitm/ca.key`/`ca.crt` येथे कायमस्वरूपी जतन केलेला)
> वापरतो आणि आधीपासून अस्तित्वात असलेल्या `omniroute-mitm.crt` ट्रस्ट-स्टोअर स्लॉटमध्ये
> इन्स्टॉल करतो (तेथील जुना एकमेव लीफ बदलून — दुहेरी-ट्रस्ट साफसफाईची गरज नाही),
> जो खालील TPROXY च्या स्वतःच्या `omniroute-tproxy-ca.crt` स्लॉटपासून पूर्णपणे वेगळा
> ठेवला जातो. नवीन AgentBridge इंस्टॉलेशन्सना CA मॉडेल आपोआप मिळते; जुना स्टॅटिक
> लीफ आधीपासून विश्वासार्ह मानणारे इंस्टॉलेशन, ऑपरेटरने
> `MITM_ROOT_CA_ENABLED=true` द्वारे निवड करेपर्यंत तोच वापरत राहते
> (`src/mitm/cert/migration.ts` पहा) — **कोणत्याही** होस्टसाठी लीफवर स्वाक्षरी करू
> शकणारा विश्वासार्ह MITM CA हा जुन्या निश्चित-SAN लीफपेक्षा लक्षणीयरीत्या अधिक
> शक्तिशाली आहे, त्यामुळे आधीपासून विश्वासार्ह असलेल्या इंस्टॉलेशनसाठी हे
> संक्रमण कधीही शांतपणे होत नाही.

ऐतिहासिकदृष्ट्या, स्टॅटिक AgentBridge MITM प्रमाणपत्र केवळ यामुळे कार्य करत होते
की AgentBridge **निश्चित** होस्ट संचासाठी DNS स्पूफिंग करतो (आता तो खालील
मॉडेलशी एकत्रित केला आहे). TPROXY **स्वेच्छेच्या** होस्टना इंटरसेप्ट करतो, त्यामुळे
क्लायंटने मागितलेल्या कोणत्याही SNI साठी त्याच्या लिसनरने वैध लीफ सादर करणे
आवश्यक आहे — हीच आवश्यकता आता AgentBridge ला केवळ 4 antigravity होस्टऐवजी
संपूर्ण `MITM_TOOL_HOSTS` संचासाठी (9 टूल नोंदी) लागू होते.

### डायनॅमिक CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` स्थानिक CA चालवतो (`selfsigned` डिपेंडन्सीवर आधारित), जो:

- `generateMitmCa()` द्वारे दीर्घकालीन CA जनरेट करतो (CN `"OmniRoute MITM CA"`,
  10 वर्षांची वैधता, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-बिट RSA / SHA-256).
- `issueLeafCert()` द्वारे **प्रत्येक SNI होस्टनावासाठी मागणीनुसार लीफ** जारी करतो
  (1 वर्षाची वैधता, `subjectAltName` = SNI होस्ट) आणि प्रत्येक होस्टनावासाठी एक
  `tls.SecureContext` कॅश करतो.
- TLS-टर्मिनेटिंग सर्व्हरसाठी `createSNICallback()` उपलब्ध करतो
  ([§5](#5-how-decrypt-and-capture-work) पहा).
- रीस्टार्टदरम्यान CA स्थिर ठेवण्यासाठी `existingCa` सह तयार केला जाऊ शकतो
  (त्यामुळे ट्रस्ट स्टोअर पुन्हा इन्स्टॉल करण्याची गरज पडत नाही).

CA खाजगी की **कधीही मशीनबाहेर जात नाही**.

### ट्रस्ट-स्टोअर इंस्टॉलर (`src/mitm/tproxy/caTrust.ts`)

इंटरसेप्ट केलेल्या क्लायंटने डायनॅमिक CA वर विश्वास ठेवणे आवश्यक आहे, म्हणून कॅप्चर
मोड सुरू केल्यावर CA प्रमाणपत्र OS ट्रस्ट स्टोअरमधील **समर्पित स्लॉटमध्ये** —
`omniroute-tproxy-ca.crt` (स्थिरांक `TPROXY_CA_CERT_NAME`) — इन्स्टॉल केले जाते.
हा स्लॉट स्टॅटिक MITM प्रमाणपत्राच्या स्लॉटपासून (`omniroute-mitm.crt`) वेगळा
ठेवला जातो, जेणेकरून दोन्ही कधीही एकमेकांवर अधिलेखित होणार नाहीत.

`installTproxyCa(caPem, sudoPassword?)` डिस्ट्रोची अँकर डिरेक्टरी ओळखतो
(क्रमाने: प्रथम Debian-शैलीची) आणि जुळणारी रिफ्रेश कमांड चालवतो:

| अँकर डिरेक्टरी                              | रिफ्रेश कमांड            |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

इंस्टॉलेशन प्रथम PEM एका तात्पुरत्या फाइलमध्ये ठेवते, त्यानंतर (विशेषाधिकारांसह)
अँकर डिरेक्टरीवर `mkdir -p` चालवते, स्टेज केलेली फाइल त्यात `cp` करते आणि रिफ्रेश
कमांड चालवते. `uninstallTproxyCa()` फक्त समर्पित स्लॉट काढून टाकते (स्टॅटिक MITM
प्रमाणपत्राला स्पर्श न करता) आणि रिफ्रेश करते — Linux व्यतिरिक्त इतर प्रणालींवर
ही क्रिया निष्प्रभावी असते.

सर्व विशेषाधिकारप्राप्त कमांड्स `execFileWithPassword`
(`src/mitm/systemCommands.ts`) द्वारे चालतात — **आर्ग्युमेंट अॅरेसह `spawn`,
शेल नाही, स्ट्रिंग इंटरपोलेशन नाही** (कठोर नियम #13). प्रक्रिया root म्हणून
चालत असताना (उदा. VPS), लक्ष्य थेट चालवले जाते आणि पासवर्डची गरज नसते;
root नसलेल्या डेस्कटॉपवर `sudoPassword`, stdin वरील `sudo -S` द्वारे पाठवला जातो.

> ट्रस्ट-स्टोअर इंस्टॉलेशनला अधिकृत करण्यासाठी डेस्कटॉपचा `sudoPassword` POST
> बॉडीमध्ये दिला जातो; प्रक्रिया root म्हणून चालत असल्यास त्याकडे पूर्णपणे
> दुर्लक्ष केले जाते.

## §5 डिक्रिप्ट आणि कॅप्चर कसे कार्य करतात

पाइपलाइन (सर्व काही `src/mitm/tproxy/` अंतर्गत):

```
स्थानिक अॅप  ──TCP/443──▶  mangle OUTPUT कनेक्शनला चिन्हांकित करते (fwmark)
                          ip rule → स्थानिक रूट टेबल → lo
                          mangle PREROUTING TPROXY → IP_TRANSPARENT लिसनर (पोर्ट 8443)
                              │  captureMode.ts: socket.localAddress मधून मूळ गंतव्य वाचते
                              ▼
                          tlsCapture.ts:
                            1. प्रति-SNI लीफसह CLIENT चे TLS-टर्मिनेशन करते (dynamicCert)
                            2. अंतर्गत http.Server डिक्रिप्ट केलेला प्लेनटेक्स्ट पार्स करतो
                            3. कॅप्चर → source: "tproxy" सह globalTrafficBuffer.push()
                               (sanitizeHeaders + maskSecret लागू केलेले)
                            4. बायपास-चिन्हांकित सॉकेटवरून मूळ गंतव्याकडे
                               पुन्हा एनक्रिप्ट करून फॉरवर्ड करते (connectMarked, अँटी-लूप)
                              │
                              ▼
                          मूळ अपस्ट्रीम (api.example.com)
```

- **TLS टर्मिनेशन** (`createTlsCaptureServer`): डायनॅमिक CA चा SNI कॉलबॅक वापरून,
  कच्च्या इंटरसेप्ट केलेल्या सॉकेटला सर्व्हर-साइड `tls.TLSSocket` मध्ये रॅप करते,
  त्यानंतर डिक्रिप्ट केलेला स्ट्रीम अंतर्गत `http.Server` कडे सोपवते (ही प्रमाणित MITM
  टर्मिनेशन युक्ती आहे). सॉकेटचे आयुष्य `MITM_IDLE_TIMEOUT_MS` द्वारे मर्यादित केलेले
  असल्यामुळे अडकलेला टनेल फाइल डिस्क्रिप्टर संपवू शकत नाही.
- **कॅप्चर** (`handleDecryptedRequest`): `source: "tproxy"` आणि सुरुवातीचे स्टेटस
  `"in-flight"` असलेली `InterceptedRequest` पुश करते; बफरमध्ये जाण्यापूर्वी हेडर्सवर
  `sanitizeHeaders()` आणि बॉडीजवर `maskSecret()` लागू केले जाते. त्यानंतर नोंद
  प्रतिसाद, आकार आणि विलंबासह अद्ययावत केली जाते.
- **पुन्हा एनक्रिप्ट केलेले फॉरवर्डिंग** (`createForward` / `realForward`): मूळ
  गंतव्याकडे पुन्हा एनक्रिप्ट करते. `rejectUnauthorized` चे डीफॉल्ट मूल्य **`true`**
  आहे (डीफॉल्टनुसार सुरक्षित) — क्लायंटने विनंती केलेल्या SNI/Host विरुद्ध अपस्ट्रीम
  प्रमाणपत्र पडताळले जाते, त्यामुळे मूळ क्लायंटने जे नाकारले असते तेच प्रॉक्सी नाकारते.

### अँटी-लूप (SO_MARK)

नियम नवीन स्थानिक आउटबाउंड कनेक्शन्सना चिन्हांकित करत असल्यामुळे, प्रॉक्सीचे **स्वतःचे**
पुन्हा एनक्रिप्ट केलेले फॉरवर्ड सामान्यतः पुन्हा इंटरसेप्ट झाले असते — म्हणजे एक अनंत लूप.
फॉरवर्ड मार्ग बायपास सॉकेट मार्क (**SO_MARK**) वापरून यापासून संरक्षण करतो:

- `realForward` त्याचे अपस्ट्रीम सॉकेट `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  द्वारे उघडते — `DEFAULT_BYPASS_MARK = 0x539` — जे `connect()` च्या **आधी**
  **SO_MARK** सेट करते, त्यामुळे फॉरवर्डचा SYN बायपास मार्कसह जातो.
- `mangle OUTPUT` नियम आधीपासून बायपास मार्क असलेली कनेक्शन्स वगळतो
  (`-m mark ! --mark <bypassMark>`), त्यामुळे प्रॉक्सीचे फॉरवर्ड पुन्हा चिन्हांकित
  केले जात **नाही** आणि ते TPROXY मध्ये पुन्हा प्रवेश करत नाही.

> अंमलबजावणीविषयक नोंद: बायपास-चिन्हांकित सॉकेट एजंटच्या `createConnection` वर
> स्थापित करणे आवश्यक आहे (`https.request({ createConnection })` कडे एजंट उपस्थित
> असताना दुर्लक्ष केले जाते), अन्यथा फॉरवर्ड चिन्हांकित नसलेले सॉकेट उघडेल आणि
> लूप पुन्हा सुरू होईल. हा e2e-पडताळलेला अँटी-लूप उपाय होता.

## §7 व्यवहारात्मक फायरवॉल लागू करणे / पूर्ववत करणे

क्रॅश झाल्यास `mangle` नियम किंवा कालबाह्य रूट कधीही मागे राहू नये. कमांड बिल्डर
(`src/mitm/tproxy/commands.ts`) आणि रनर (`src/mitm/tproxy/setup.ts`) याची हमी देतात की
**पूर्ववत करणे हे लागू करण्याचे अचूक व्यस्त रूप असून त्याचा क्रम उलट असतो**.

`applyTproxy(cfg)` लागू करण्याच्या कमांड क्रमाने चालवते; **कोणतेही** अपयश आल्यास ती
सर्वोत्तम प्रयत्नाने संपूर्ण `revertTproxy(cfg)` चालवते आणि त्रुटी पुन्हा फेकते — त्यामुळे फायरवॉल
एकतर पूर्णपणे लागू केलेला असतो किंवा पूर्णपणे पूर्ववत केलेला असतो, कधीही अंशतः लागू केलेला नसतो. `revertTproxy(cfg)`
व्यस्त कमांड उलट क्रमाने चालवते आणि अपयशांकडे दुर्लक्ष करते (आयडेम्पोटंट — कोणत्याही अटीशिवाय
कॉल करणे सुरक्षित, उदा. AgentBridge च्या `repairMitm()` क्लीनअपमधून).

कोणतीही कमांड चालवण्यापूर्वी `validateTproxyConfig(cfg)` चालते: पोर्ट `1–65535`
असणे आवश्यक आहे, `mark`/`routeTable`/`bypassMark` हे धन पूर्णांक असणे आवश्यक आहे आणि `bypassMark`
हे `mark` पेक्षा वेगळे असणे आवश्यक आहे (लूप-विरोधी).

### लागू करण्याच्या कमांड (क्रमाने)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

पूर्ववत करताना त्या उलट क्रमाने हटवल्या जातात: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> ही कृतीपद्धती **OUTPUT-आधारित** आहे, कारण MITM वापराचे प्रकरण हे _स्थानिक_ आउटबाउंड
> ट्रॅफिकचे आहे (त्याच होस्टवरील अॅप्स), जे केवळ `PREROUTING` मधील TPROXY ला
> दिसत नाही — `PREROUTING` ला फक्त फॉरवर्ड केलेले ट्रॅफिक दिसते. `OUTPUT` चेन नवीन
> स्थानिक कनेक्शनना मार्क करते, `ip rule` त्यांना स्थानिक वितरणासाठी (`lo`) पुन्हा रूट करते आणि
> त्यानंतर `PREROUTING` त्यांना पारदर्शक लिसनरकडे सोपवते.

## §8 कॉन्फिगरेशन

प्रारंभ विनंती (`POST /api/tools/agent-bridge/tproxy`) खालील
फील्ड स्वीकारते, ज्यांचे प्रमाणीकरण `StartTproxyBodySchema` (`tproxy/route.ts`) द्वारे केले जाते. सर्व फील्ड ऐच्छिक
असून, ती दिली नसल्यास त्यांची डीफॉल्ट मूल्ये वापरली जातात:

| फील्ड            | प्रकार             | डीफॉल्ट  | नोंदी                                                                                                                    |
| ---------------- | ------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------ |
| **dport**        | int (1–65535)      | `443`    | पारदर्शकपणे इंटरसेप्ट करायचा गंतव्य TCP पोर्ट                                                                            |
| **mark**         | int (≥1)           | `0x2333` | `OUTPUT` वर सेट केलेला आणि `ip rule` + `PREROUTING` द्वारे जुळवला जाणारा फायरवॉल मार्क                                   |
| **onPort**       | int (1–65535)      | `8443`   | पारदर्शक (**IP_TRANSPARENT**) लिसनर ज्या पोर्टशी बाइंड होतो                                                              |
| **routeTable**   | int (≥1)           | `233`    | `local 0.0.0.0/0` रूट धारण करणारा पॉलिसी-रूटिंग टेबल आयडी                                                                |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | प्रॉक्सीने स्वतःच्या अपस्ट्रीम कनेक्शनवर सेट केलेला बायपास सॉकेट मार्क (**SO_MARK**); `OUTPUT` मधून वगळलेला (लूप-विरोधी) |
| **sudoPassword** | string             | —        | फक्त रूट नसलेल्या डेस्कटॉपसाठी: ट्रस्ट-स्टोअर इंस्टॉलेशनला अधिकृत करते; रूट असताना दुर्लक्षित केले जाते                  |

TPROXY साठी **कोणतेही पर्यावरणीय चल नाहीत** — सर्व कॉन्फिगरेशन
POST बॉडीद्वारे किंवा वरील डीफॉल्टद्वारे केले जाते.

## §9 ट्रॅफिक इन्स्पेक्टरमधून सक्षम करणे

1. **ट्रॅफिक इन्स्पेक्टर** (`/dashboard/tools/traffic-inspector`) उघडा.
2. कॅप्चर-मोड टूलबारमध्ये, **"TPROXY डिक्रिप्ट"** ⚠ बटण शोधा
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - "TPROXY डिक्रिप्टसाठी Linux + root + नेटिव्ह ॲडऑन आवश्यक आहे" या टूलटिपसह ते
     **अक्षम** असल्यास, या होस्टवर नेटिव्ह ॲडऑन उपलब्ध नाही (Linux नसणे,
     टूलचेन नसणे किंवा ॲडऑन बिल्ड केलेले नसणे). [§2](#2-requirements) आणि [§3](#3-the-native-ip_transparent-addon) पहा.
3. बटणावर क्लिक करा. ते `startTproxyCaptureMode()`
   (`src/lib/inspector/tproxyCaptureApi.ts`) द्वारे `POST /api/tools/agent-bridge/tproxy`
   कॉल करते, जे: डायनॅमिक CA बिल्ड करते, ट्रान्सपरंट लिसनर उघडते, फायरवॉल
   नियम लागू करते आणि OS ट्रस्ट स्टोअरमध्ये CA इंस्टॉल करते.
4. सुरू असताना, टॉगल अंबर रंगाचे होते आणि थेट इंटरसेप्ट संख्या
   (`· <interceptCount>`) दाखवते. इंटरसेप्ट केलेल्या विनंत्या विनंती सूचीमध्ये
   `source: "tproxy"` सह दिसतात.
5. थांबवण्यासाठी पुन्हा क्लिक करा — `stopTproxyCaptureMode()` द्वारे
   `DELETE /api/tools/agent-bridge/tproxy` लिसनर बंद करते, CA अनइंस्टॉल करते आणि
   फायरवॉल नियम पूर्ववत करते.

कॅप्चर-मोडची स्थिती (सुरू / उपलब्ध / इंटरसेप्ट संख्या / लिसनर पोर्ट)
`GET /api/tools/agent-bridge/tproxy` मधून मिळते (`src/mitm/tproxy/captureManager.ts`
मधील `getCaptureStatus()`). एका वेळी फक्त **एक** TPROXY सत्र चालते —
दुसरे सत्र सुरू करण्याचा प्रयत्न "TPROXY कॅप्चर मोड आधीच सुरू आहे" या संदेशासह नाकारला जातो.

## §10 समस्यानिवारण

### टॉगल अक्षम आहे

नेटिव्ह ॲडऑन लोड करता येत नाही. याची खात्री करा: तुम्ही Linux वर आहात, तुम्ही ॲडऑन
बिल्ड केले आहे (`npm run build:native:tproxy`) आणि प्रक्रिया `transparent.node`
लोड करू शकते. `isTransparentSocketAvailable()` टॉगलची उपलब्धता नियंत्रित करते;
ॲडऑन उपलब्ध नसताना `GET /api/tools/agent-bridge/tproxy` हे `available: false`
परत करते.

### काहीही कॅप्चर होत नाही

- इंटरसेप्ट केलेली प्रक्रिया प्रत्यक्षात कॉन्फिगर केलेल्या `dport` शी
  (डीफॉल्ट `443`) कनेक्ट होते याची खात्री करा.
- प्रक्रिया डायनॅमिक CA वर विश्वास ठेवते याची खात्री करा. CA
  `omniroute-tproxy-ca.crt` अंतर्गत इंस्टॉल केले जाते; स्वतःचे ट्रस्ट स्टोअर
  (Firefox/Chrome NSS) असलेल्या ॲप्समध्ये ते प्रमाणपत्र तिथेही जोडावे लागू शकते.
- प्रमाणपत्र-विश्वसनीयता / सर्व्हर आरोग्य तपासण्यांसाठी AgentBridge **निदान**
  स्वयं-चाचणी चालवा ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md) पहा).

### क्रॅशनंतर उरलेले फायरवॉल नियम

`revertTproxy()` हे लागू करण्याच्या क्रियेचे नेमके व्यस्त रूप आहे आणि ते आयडेम्पोटंट आहे.
मोड थांबवल्याने नियम पूर्ववत होतात; OmniRoute सत्राच्या मध्यात बंद झाले असल्यास,
अनाथ सिस्टम स्थिती (DNS स्पूफ, root CA, सिस्टम प्रॉक्सी) पूर्ववत करण्यासाठी
AgentBridge **दुरुस्ती** क्रिया (`POST /api/tools/agent-bridge/repair`) वापरा.
TPROXY `mangle` नियम आणि रूट रीबूट झाल्यावरही आपोआप फ्लश होतात.

### अनंत लूप / प्रॉक्सी स्वतःचेच फॉरवर्ड इंटरसेप्ट करते

ही अँटी-लूप स्थिती आहे. `bypassMark` हे `mark` पेक्षा वेगळे आहे याची खात्री करा
(प्रमाणीकरण याची अंमलबजावणी करते) आणि फॉरवर्ड `connectMarked` वापरते याची खात्री
करा (`realForward` मध्ये ते वापरले जाते). [§5 अँटी-लूप](#anti-loop-so_mark) पहा.
