## आढावा

सर्व OmniRoute व्यवस्थापन API मार्गांचे संरक्षणाच्या तीन स्तरांपैकी एका स्तरात
वर्गीकरण केले जाते. वर्गीकरण स्थिर आहे, ते `src/server/authz/routeGuard.ts` मध्ये
परिभाषित केलेले आहे आणि इतर कोणतीही प्रमाणीकरण शाखा चालण्यापूर्वी त्याचे मूल्यमापन केले जाते.

## स्तर

### स्तर 1 — LOCAL_ONLY

**याद्वारे अंमलात आणलेले:** `isLocalOnlyPath(path)` → लूपबॅक होस्ट तपासणी  
**बायपास:** डीफॉल्टनुसार कोणताही नाही. विनंतीसोबत `manage` व्याप्ती असलेली वैध API की असल्यास, `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` मधील पथांसाठी मर्यादित अपवाद आहे ([Manage-scope अपवाद](#manage-scope-carve-out) पहा).

हे मार्ग चाइल्ड प्रोसेसेस सुरू करतात किंवा रनटाइम कोड कार्यान्वित करतात. ते नॉन-लूपबॅक ट्रॅफिकसाठी उघड केल्यास, वैध JWT मिळवलेला हल्लेखोर (उदा., Cloudflared/Ngrok टनेलद्वारे) प्रोसेस सुरू करण्यास प्रवृत्त करू शकतो — हा एक ज्ञात CVE वर्ग आहे ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj म्हणजे काय (हल्ल्याचा वर्ग):** व्यवस्थापन/एजंट सर्व्हर असा एन्डपॉइंट उघड करतो, जो सबप्रोसेस (`npm install`, `node`, ब्राउझर, प्रॉक्सी, `git`, `tar`, …) सुरू करतो. जर त्या एन्डपॉइंटपर्यंत होस्टच्या बाहेरून पोहोचता येत असेल — ऑपरेटरने OmniRoute हे nginx/Cloudflare/Tailscale टनेलच्या मागे ठेवले आणि JWT लीक झाला किंवा प्रमाणीकरण चुकीच्या पद्धतीने कॉन्फिगर केले गेले — तर हल्लेखोर "API कॉल करणे" याचे रूपांतर "होस्टवर कमांड चालवणे" (दूरस्थ कोड कार्यान्वयन) यात करतो. OmniRoute प्रत्येक प्रोसेस सुरू करण्यास सक्षम मार्गावर **कोणत्याही प्रमाणीकरण तपासणीपूर्वी, बिनशर्त लूपबॅक होस्ट तपासणी** लागू करून हे रोखते: टनेलवरून लीक झालेला टोकनदेखील प्रोसेस सुरू करण्यापर्यंत पोहोचू शकत नाही.

**संपूर्ण LOCAL_ONLY संच.** अधिकृत स्रोत `src/server/authz/routeGuard.ts` मधील `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` आहे; खालील तक्ता सद्यस्थिती प्रतिबिंबित करतो. `check-route-guard-membership` गेट प्रोसेस सुरू करण्यास सक्षम असलेल्या प्रत्येक प्रीफिक्सअंतर्गत सर्व `route.ts` फाइल्सची गणना करते आणि त्यांपैकी कोणतीही फाइल केवळ-स्थानिक म्हणून वर्गीकृत नसल्यास CI अयशस्वी करते.

#### व्यवस्थापन-व्याप्तीचा अपवाद

LOCAL_ONLY मार्गांच्या उपसंचाला नॉन-लूपबॅकवरूनही प्रवेश करता येऊ शकतो, जर आणि
फक्त जर विनंतीमध्ये `Authorization: Bearer <api-key>` असेल आणि त्याच्या
मेटाडेटामध्ये `manage` व्याप्ती (किंवा `admin`) समाविष्ट असेल. हा अपवाद
प्रत्येक मार्गासाठी `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` द्वारे स्पष्टपणे
नियंत्रित केला जातो, त्यामुळे कोणत्याही नवीन LOCAL_ONLY मार्गासाठी डीफॉल्ट
कठोर-लूपबॅकच राहतो. प्रमाणीकरण नसलेल्या विनंत्या आणि व्यवस्थापन-व्याप्ती
नसलेल्या की असलेल्या विनंत्या अजूनही `403 LOCAL_ONLY` सह नाकारल्या जातात.

सध्या बायपास करता येणारा एकमेव उपसर्ग `/api/mcp/` आहे. `/api/cli-tools/runtime/` आणि
`/api/services/` हे हेतुपुरस्सर वगळले आहेत, कारण ते कोणत्याही उपप्रक्रिया
(`npm install`, `node`) सुरू करू शकतात; नेमक्या याच CVE वर्गाला प्रतिबंध
करण्यासाठी LOCAL_ONLY स्तर अस्तित्वात आहे.

**#7895 — `mcp:connect` संकुचित व्याप्ती:** `/api/mcp/` अपवाद
संकुचित `mcp:connect` व्याप्ती असलेली Bearer कीदेखील स्वीकारतो
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), जिची तपासणी
`src/server/authz/policies/management.ts` मधील `hasMcpConnectOrManageScope()`
द्वारे केली जाते. ही व्याप्ती केवळ `/api/mcp/` पुरती मर्यादित आहे —
`mcp:connect` इतर कोणत्याही व्यवस्थापन मार्गावर काहीही परवानगी देत नाही
(भविष्यात जोडल्या जाणाऱ्या इतर प्रत्येक LOCAL_ONLY बायपास उपसर्गासह), आणि
तिला मुद्दाम `MANAGEMENT_API_KEY_SCOPES` मधून वगळले आहे. `manage`/`admin`
असलेली की पूर्वीप्रमाणेच या अपवादातून पुढे जाते; व्यापक व्यवस्थापन प्रवेशाची
गरज नसलेल्या, केवळ दूरस्थ MCP कॉल करणाऱ्यांसाठी `mcp:connect` हा
कमी-विशेषाधिकार असलेला पर्याय आहे.

| विनंती                                          | मार्ग                      | परिणाम                          |
| ----------------------------------------------- | -------------------------- | ------------------------------- |
| नॉन-लूपबॅक, Bearer नाही                         | `/api/mcp/*`               | 403 LOCAL_ONLY                  |
| नॉन-लूपबॅक, `manage` व्याप्तीसह Bearer          | `/api/mcp/*`               | परवानगी                         |
| नॉन-लूपबॅक, `mcp:connect` व्याप्तीसह Bearer     | `/api/mcp/*`               | परवानगी                         |
| नॉन-लूपबॅक, `manage`/`mcp:connect` शिवाय Bearer | `/api/mcp/*`               | 403 LOCAL_ONLY                  |
| नॉन-लूपबॅक, `mcp:connect` व्याप्तीसह Bearer     | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                  |
| नॉन-लूपबॅक, `manage` व्याप्तीसह Bearer          | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                  |
| लूपबॅक, कोणताही/Bearer नाही                     | कोणताही LOCAL_ONLY         | परवानगी (द्वार तपासणी उत्तीर्ण) |

#### ऑपरेटर मार्गदर्शन आणि लेखापरीक्षण

तुम्ही OmniRoute हे रिव्हर्स प्रॉक्सी किंवा टनेलच्या (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) मागे चालवत असल्यास, लूपबॅक तपासणी तरीही वरील
प्रक्रिया-सुरू-करू-शकणाऱ्या मार्गांचे संरक्षण करते — ज्या विनंतीचा क्लायंट
पत्ता नॉन-लूपबॅक आहे ती विनंती **प्रमाणीकरण चालण्यापूर्वीच**
`403 LOCAL_ONLY` सह नाकारली जाते, त्यामुळे लीक झालेला JWT प्रक्रिया सुरू
करण्यापर्यंत पोहोचू शकत नाही. ऑपरेटरच्या दोन जबाबदाऱ्या कायम राहतात:

- **क्लायंट IP लूपबॅक असल्याचे बनावट दाखवून 403 "दुरुस्त" करू नका.**
  `X-Forwarded-For: 127.0.0.1` सेट करणे किंवा स्रोत पत्ता लूपबॅक म्हणून
  पुनर्लेखित करणारा प्रॉक्सी वापरणे, हा स्तर बंद करत असलेला नेमका RCE वर्ग
  पुन्हा खुला करते. डॅशबोर्ड/API प्रॉक्सीद्वारे उघड करा — प्रक्रिया-सुरू-करू-शकणारे
  मार्ग कधीही उघड करू नका.
- **व्यवस्थापन-व्याप्तीचा बायपास कमीत कमी ठेवा.** केवळ `/api/mcp/` बायपास
  करता येतो आणि तोही फक्त `manage`-व्याप्ती असलेल्या API कीसह.
  `SPAWN_CAPABLE_PREFIXES` कधीही बायपास सूचीमध्ये जोडता येत नाहीत — zod
  स्कीमा त्यांना नाकारते आणि `isLocalOnlyBypassableByManageScope` रनटाइमच्या
  वेळी त्यांना नाकारते (बहुस्तरीय संरक्षण); डॅशबोर्डवरील "बायपास करण्यायोग्य
  बनवता येत नाही" याचा हाच अर्थ आहे. `/api/providers/` अंतर्गत
  डायनॅमिक-सेगमेंट आणि स्थिर-पथ असलेले प्रक्रिया-सुरू-करू-शकणारे मार्ग
  (उदा. `/login`, `/refresh-cursor`) सपाट `SPAWN_CAPABLE_PREFIXES` अॅरेऐवजी
  `src/shared/constants/spawnCapablePrefixes.ts` मधील regex-आधारित
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` सहयोगीद्वारे
  कव्हर केले जातात — त्यांना पकडण्यासाठी सपाट अॅरेमध्ये संपूर्ण
  `/api/providers/` उपसर्ग समाविष्ट करावा लागेल, ज्यामुळे दूरस्थ डॅशबोर्ड
  प्रदाता CRUD साठी वैधपणे वापरत असलेल्या मार्ग-वृक्षाची व्याप्ती अनावश्यकपणे
  वाढेल.

**प्रवेशाचे लेखापरीक्षण** — होस्टबाहेरील कोणीही या मार्गांपर्यंत पोहोचत नसल्याची पडताळणी करण्यासाठी:

- `/dashboard/settings/security` वरील **अधिकृतता इन्व्हेंटरी** उघडा: ती
  प्रत्यक्ष LOCAL_ONLY उपसर्ग सूची, कोणते उपसर्ग बायपास करता येतात आणि कंपाइल-वेळी निश्चित केलेला
  spawn-सक्षम ("बायपास करण्यायोग्य बनवता येत नाही") संच दाखवते.
- वरील उपसर्गांसोबत नॉन-लूपबॅक क्लायंट पत्ता असलेल्या नोंदींसाठी तुमचे रिव्हर्स-प्रॉक्सी /
  ॲक्सेस लॉग Grep करा. अशा कोणत्याही विनंतीला `403 LOCAL_ONLY` ऐवजी `200`
  मिळाले असल्यास, प्रॉक्सी वास्तविक क्लायंट IP लपवत आहे — प्रॉक्सी दुरुस्त करा.
- यांपैकी एखाद्या पथासाठी OmniRoute च्या लॉगमध्ये असलेला `403 LOCAL_ONLY` म्हणजे संरक्षक
  अपेक्षेप्रमाणे कार्यरत आहे; दडपून टाकण्याची ती त्रुटी नाही.

### स्तर 2 — ALWAYS_PROTECTED

**याद्वारे अंमलबजावणी:** `isAlwaysProtectedPath(path)` → `requireLogin=false` बायपास वगळा
**बायपास:** `requireLogin=false` असताना कोणताही नाही; JWT नेहमी आवश्यक

हे मार्ग विनाशकारी किंवा अपरिवर्तनीय आहेत. "पासवर्ड नसलेल्या"
इंस्टॉलेशनमध्ये त्यांना परवानगी दिल्यास, त्याच LAN वरील कोणीही डेटाबेस पुसू शकते किंवा
सर्व्हर प्रक्रिया बंद करू शकते.

| पथ                                        | कारण                                                                           |
| ----------------------------------------- | ------------------------------------------------------------------------------ |
| `/api/shutdown`                           | सर्व्हर प्रक्रिया समाप्त करतो                                                  |
| `/api/settings/database`                  | डेटाबेस एक्सपोर्ट, इंपोर्ट आणि पूर्णपणे पुसणे                                  |
| `/api/db-backups`                         | संपूर्ण डेटाबेस बॅकअप संग्रहात प्रवेश                                          |
| `/api/settings/export-json`               | संपूर्ण सेटिंग्ज ब्लॉब एक्सपोर्ट करतो (गुपितांसह)                              |
| `/api/settings/import-json`               | संपूर्ण सेटिंग्ज ब्लॉब बदलतो                                                   |
| `/api/providers/health-autopilot/actions` | ऑटोपायलट सुधारात्मक कृती कार्यान्वित करतो                                      |
| `/api/settings/obsidian`                  | कोणत्याही व्हॉल्ट रूटसाठी पुन्हा वापरता येणारी WebDAV क्रेडेन्शियल्स जारी करतो |

**उल्लंघन झाल्यास प्रतिसाद:** `401 Authentication required`

`/api/settings/obsidian` त्याचा `/webdav` चाइल्ड समाविष्ट करतो: `POST` हा WebDAV फाइल सेवेला —
जी या पाइपलाइनच्या बाहेर, Next.js पूर्वी कस्टम Node स्तराद्वारे पुरवली जाते — कॉलरने निवडलेल्या रूटकडे
निर्देशित करतो आणि नव्याने जारी केलेली Basic क्रेडेन्शियल्स प्रतिसादात परत पाठवतो, `DELETE` ती बदलतो,
आणि पॅरेंट `POST` Obsidian REST API टोकन संचयित करतो. GHSA-62vw ने फक्त `GET` मधील पासवर्ड उघड होणे
लपवले होते; जारी करण्याची प्रक्रिया अजूनही फेल-ओपन स्तरावर होती (GHSA-7pq4-8pvv-rx7r).
`enableObsidianVaultSync()` याव्यतिरिक्त डेटा डायरेक्टरीच असलेला, तिच्या आत असलेला किंवा तिला
समाविष्ट करणारा व्हॉल्ट नाकारतो.

### नवीन इंस्टॉलेशनचे बूटस्ट्रॅप केवळ लूपबॅकसाठी — `Host` नव्हे, तर वास्तविक पीअरनुसार

व्यवस्थापन पासवर्ड कॉन्फिगर केलेला नसताना (आणि `INITIAL_PASSWORD` नसताना),
`src/shared/utils/apiAuth.ts` मधील `isAuthRequired()` अनामिक बूटस्ट्रॅप **फक्त लूपबॅक पीअर्ससाठी**
उघडा ठेवतो. लूपबॅकचा निर्णय विश्वसनीय पीअर संकेतांवरून या क्रमाने घेतला जातो: टोकन-स्टॅम्प केलेला
वास्तविक TCP पीअर (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, जो धोरणाला दिसतो), पाइपलाइनचा स्वतःचा
`AUTHZ_HEADER_PEER_LOCALITY` निर्णय (जो रूट हँडलर्सना दिसतो आणि केवळ
`OMNIROUTE_PEER_STAMP_TOKEN` सेट असताना विश्वसनीय मानला जातो), किंवा थेट कॉलर्ससाठी वास्तविक
सॉकेट पीअर. `Host` / `nextUrl.hostname` यांचा कधीही विचार केला जात नाही आणि पहिल्या पासवर्डची नोंद
(`POST /api/settings/require-login`) प्रत्येक नेटवर्क पीअरसाठी खुली ठेवण्याऐवजी त्याच निर्बंधाखाली
असते (GHSA-7pq4-8pvv-rx7r). `managementPolicy` स्वतःचा `peerContext` निर्णय स्पष्टपणे पुढे पाठवते,
म्हणून ORIGINAL (स्ट्रिप करण्यापूर्वीच्या) विनंतीचे हेडर्स त्याचा निर्णय कधीही घेत नाहीत.

### स्तर 3 — MANAGEMENT (डीफॉल्ट)

इतर सर्व व्यवस्थापन मार्ग. `requireLogin=false` कॉन्फिगर केलेले नसल्यास प्रमाणीकरण
आवश्यक आहे. CLI टोकन्स या मार्गांचे प्रमाणीकरण करू शकतात (लूपबॅक + वैध HMAC).

## मूल्यमापन क्रम

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → लूपबॅक                                  → पुढे जा
     → नॉन-लूपबॅक, manage-scope Bearer
        आणि isLocalOnlyBypassableByManageScope   → परवानगी द्या (management_key)
     → अन्यथा                                   → 403 LOCAL_ONLY सह नाकारा
  2. isInternalModelSyncRequest(ctx)?
     → परवानगी द्या (system)
  3. hasValidCliToken(headers)?
     → परवानगी द्या (cli) [लूपबॅक + timingSafeEqual HMAC तपासणी]
  4. isAlwaysProtectedPath(path) किंवा requireLogin=true?
     → isDashboardSessionAuthenticated?
        → परवानगी द्या (dashboard_session)
     → बायपास न करता येणाऱ्या पथावर manage-scope Bearer?
        → परवानगी द्या (management_key)
     → 401/403 सह नाकारा
  5. requireLogin=false?
     → परवानगी द्या (anonymous)
```

पायरी 1 मधील manage-scope शाखा हा एकमेव प्रमाणीकरण केलेला पथ आहे जो
LOCAL_ONLY मार्गाची अट पूर्ण करू शकतो; auth-backend अयशस्वी झाल्यास 503 (403 नव्हे) परत केला जातो, जेणेकरून
कालबाह्य झालेला DB अप्रत्यक्षपणे "नाकारा" या स्थितीत अवनत होणार नाही.

## स्पॉन करू शकणारा नवीन मार्ग जोडणे

1. `src/server/authz/routeGuard.ts` मधील `LOCAL_ONLY_API_PREFIXES` मध्ये पथाचा उपसर्ग जोडा
2. `tests/unit/authz/routeGuard.test.ts` मध्ये नवीन उपसर्गासाठी
   `isLocalOnlyPath()` true परत करते असे प्रतिपादन करणारी चाचणी जोडा
3. **ही पायरी कधीही वगळू नका** — `CLAUDE.md` मधील कठोर नियम #15 पहा
4. ठरवा: हा मार्ग `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` मध्येही समाविष्ट करायचा आहे का?
   डीफॉल्ट उत्तर **नाही** आहे. मार्ग manage-scope धारकास उपलब्ध करून देणे सुरक्षित असेल
   (म्हणजेच, तो वापरकर्त्याद्वारे नियंत्रित केलेला कोणताही स्वेच्छेचा कोड स्पॉन करत नसेल) तरच निवड करून समाविष्ट करा.

## manage-scope द्वारे बायपास करता येणारा पथ जोडणे

1. मार्ग वापरकर्त्याने पुरवलेला कोड किंवा कमांड कार्यान्वित करत नाही याची खात्री करा. जर तो
   तसे करत असेल, तर थांबा — हा अपवाद त्यासाठी योग्य साधन नाही.
2. `src/server/authz/routeGuard.ts` मधील
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` मध्ये उपसर्ग जोडा
3. `tests/unit/authz/management-policy.test.ts` मध्ये चारही
   विनंती प्रकारांसाठी कव्हरेज जोडा: Bearer नाही (403), manage Bearer (परवानगी), non-manage Bearer
   (403), आणि manage Bearer असतानाही `/api/cli-tools/runtime/*`
   strict-loopback राहते याची प्रत्येक उपसर्गासाठी प्रतिगमन चाचणी.

## OpenAPI मध्ये सुरक्षा स्तरांचे दस्तऐवजीकरण

`docs/openapi.yaml` मध्ये नवीन मार्ग जोडताना, मार्गाचे वर्गीकरण `routeGuard.ts` द्वारे केले असल्यास त्यास संबंधित
विक्रेता विस्तार लागू करा:

| routeGuard.ts वर्गीकरण                        | YAML भाष्य                 | अंमलबजावणी                                         |
| --------------------------------------------- | -------------------------- | -------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                     | `x-loopback-only: true`    | नॉन-लूपबॅकवरून बिनशर्त अवरोधित                     |
| `ALWAYS_PROTECTED_API_PATHS`                  | `x-always-protected: true` | `requireLogin=false` असतानाही प्रमाणीकरण आवश्यक    |
| अंतर्गत admin/debug मार्ग                     | `x-internal: true`         | डीफॉल्टनुसार /dashboard/api-endpoints मधून लपवलेला |
| काहीही नाही (सार्वजनिक / प्रमाणित प्रमाणीकरण) | (भाष्य आवश्यक नाही)        | मानक `requireLogin`-नियंत्रित प्रवेश               |

### प्रमाणीकरण

दोन स्क्रिप्ट्स YAML भाष्ये आणि `routeGuard.ts` यांच्यातील सुसंगतता अंमलात आणतात:

- `scripts/check/check-openapi-coverage.mjs` — कव्हरेज < 99% असल्यास अयशस्वी होते
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` किंवा
  `x-always-protected` भाष्ये compile-time स्थिरांकांपेक्षा भिन्न असल्यास अयशस्वी होते

दोन्ही स्क्रिप्ट्स pre-commit hook आणि CI मध्ये चालतात.

### चुकीच्या सकारात्मक निकालाचा नियम

`routeGuard.ts` स्थिरांकामध्ये नसलेल्या मार्गावर `x-always-protected` किंवा `x-loopback-only` भाष्य केले असल्यास,
कव्हरेज स्क्रिप्ट अयशस्वी होते. याचे निराकरण नेहमी YAML ला `routeGuard.ts` प्रत्यक्षात जे लागू करते त्याच्याशी संरेखित करणे हे आहे — अंमलबजावणी तर्कही लागू न करता
`routeGuard.ts` मध्ये मार्ग जोडणे नव्हे.
