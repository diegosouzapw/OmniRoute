OmniRoute npm + Docker आर्टिफॅक्ट्स प्रकाशित करते. हे गेट्स प्रोव्हेनन्स, इन्व्हेंटरी (SBOM) आणि CVE स्कॅनिंग प्रदान करतात, हे सर्व OSS आहेत आणि रिलीझ वर्कफ्लोमध्ये समाकलित केलेले आहेत. **सल्लागार-प्रथम** भूमिका — ते आता अहवाल देतात, आणि पहिल्या यशस्वी (green) रिलीझनंतर ब्लॉक करण्याच्या स्थितीत जातात.

| गेट                     | टूल                                            | कुठे                          | ब्लॉक करते का?                | आउटपुट                                           |
| ----------------------- | ---------------------------------------------- | ----------------------------- | ----------------------------- | ------------------------------------------------ |
| SLSA प्रोव्हेनन्स (npm) | `npm --provenance` (OIDC)                      | `npm-publish.yml`             | केवळ प्रकाशन अयशस्वी झाल्यास  | बॅज npmjs / `npm audit signatures`               |
| SBOM npm                | `@cyclonedx/cyclonedx-npm`                     | `npm-publish.yml`             | केवळ निर्मिती अयशस्वी झाल्यास | रिलीझ ॲसेट + आर्टिफॅक्ट                          |
| SBOM इमेज               | `anchore/sbom-action` (syft)                   | `docker-publish.yml` (merge)  | सल्लागार                      | CycloneDX आर्टिफॅक्ट                             |
| Trivy CVE (SARIF)       | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | सल्लागार                      | SARIF (HIGH+CRITICAL) → सुरक्षा टॅब              |
| Trivy CRITICAL गेट      | `aquasecurity/trivy-action`                    | `docker-publish.yml` (merge)  | **ब्लॉक करणारे**              | दुरुस्त करण्यायोग्य CRITICAL वर `exit-code: '1'` |
| osv vulnCount           | `osv-scanner` (`check:vuln-ratchet --ratchet`) | `ci.yml` (`quality-extended`) | **ब्लॉक करणारे**              | `metrics.vulnCount` (दिशा:खाली) रॅचेट करते       |
| OpenSSF Scorecard       | `ossf/scorecard-action`                        | `scorecard.yml` (cron)        | सल्लागार                      | SARIF → सुरक्षा + बॅज                            |

इमेज CVE रॅचेट `docker-publish.yml` मध्ये **दोन पायऱ्या** वापरते: SARIF पायरी (`HIGH,CRITICAL`, `exit-code: 0`) HIGH+CRITICAL ला सुरक्षा टॅबमध्ये ब्लॉक न करता दृश्यमान ठेवते; _CRITICAL गेट_ पायरी (`severity: CRITICAL`, `ignore-unfixed: true`, `exit-code: 1`) उपलब्ध दुरुस्तीसह (fix) असलेल्या CRITICAL CVE वर रिलीझ अयशस्वी करते. `ignore-unfixed` हे अपस्ट्रीम पॅच नसलेल्या बेस-इमेज CVE साठी रिलीझ ब्लॉक होण्यापासून प्रतिबंधित करते.

## ⚠️ CVE भिन्नता (osv/Trivy गेट्स ब्लॉक करणारे)

osv आणि Trivy अवलंबित्व (deps) ची तुलना CVE डेटाबेसशी करतात जे **सतत वाढत असतात**. एक PR जो **कोणत्याही अवलंबित्वला स्पर्श करत नाही** तो अचानक लाल होऊ शकतो कारण विद्यमान अवलंबित्वमध्ये एक नवीन CVE उघड झाला (osv: मोजलेले `vulnCount` > बेसलाइन; Trivy: इमेजमध्ये एक नवीन दुरुस्त करण्यायोग्य CRITICAL). **हे ब्लॉक करणाऱ्या CVE गेटचे अपेक्षित कार्यात्मक वर्तन आहे, उत्पादनातील दोष (regression) नाही.**

जेव्हा नव्याने उघड झालेल्या CVE मुळे osv किंवा Trivy लाल होतात, तेव्हा उपाय खालीलप्रमाणे आहे:

1.  **प्रभावित अवलंबित्व (dep) वाढवा** (प्राधान्यकृत) — `package.json` `overrides` (ट्रान्झिटिव्ह deps) द्वारे पॅच केलेल्या आवृत्तीमध्ये अपग्रेड करा किंवा पॅच केलेल्या बेसवर इमेज पुन्हा तयार करा.
2.  **जर अपस्ट्रीम दुरुस्ती (fix) उपलब्ध नसेल तर:**
    - **osv:** `config/quality/quality-baseline.json` मध्ये `metrics.vulnCount` पुन्हा बेसलाइन करा (`npm run quality:ratchet -- --update` समर्पित गेट्सना कव्हर करत नाही — मूल्य स्वतः संपादित करा, `direction:down`) समर्थन नोट आणि ट्रॅकिंग इशूसह.
    - **Trivy:** `.trivyignore` मध्ये (प्रत्येक ओळीवर CVE-ID) समर्थन टिप्पणी आणि ट्रॅकिंग इशूसह एक एंट्री जोडा. `ignore-unfixed: true` पॅच नसलेल्या CVEs ला आपोआप कव्हर करते.

जेव्हा टूल अनुपस्थित असते किंवा मोजमाप अयशस्वी होते (osv-scanner PATH मध्ये नाही, osv.dev/network पोहोचण्यायोग्य नाही, अवैध JSON) तेव्हा दोन्ही गेट्स **सभ्यपणे वगळले जातात** (exit 0) — **मोजमाप** अयशस्वी होणे कधीही ब्लॉक करत नाही, केवळ **मोजलेले** रिग्रेशन ब्लॉक करते.

## ज्ञात स्वीकारलेले धोके

### extract-zip 2.0.1 — GHSA-7pqw-9j4j-h8q3 / GHSA-jmr9-qjv8-65gv (#14482)

`extract-zip@2.0.1` मध्ये दोन अनपॅच केलेले उच्च-गंभीरतेचे सिम्लिंक-ट्रॅव्हर्सल सल्लागार आहेत.
वरील CVE व्हेरिएन्स उपायाच्या "नो अपस्ट्रीम फिक्स" शाखेनुसार, हा एक
**स्वीकृत धोका** आहे, अपग्रेड नाही:

- **साखळी:** `promptfoo` (devDependency) → `@openai/codex-security` → `extract-zip@2.0.1`.
  `package-lock.json` द्वारे पुष्टी झाली — संपूर्ण डिपेंडन्सी
  ट्रीमध्ये (`@openai/codex-security`) फक्त एक पॅकेज `extract-zip` घोषित करते, आणि फक्त एक पॅकेज
  (`promptfoo`) `@openai/codex-security` घोषित करते.
- **साखळीत कुठेही निश्चित रिलीज अस्तित्वात नाही.** `extract-zip@2.0.1` (2020 मध्ये प्रकाशित) हे पॅकेजचे अंतिम रिलीज आहे — ते अनमेन्टेन्ड आहे. `@openai/codex-security` चे
  सध्याचे npm-latest (`0.1.29`) अजूनही `extract-zip@2.0.1` वापरते.
- **उत्पादनापासून पोहोचण्यायोग्य नाही.** `promptfoo` हे केवळ devDependency आहे (कधीही `dependencies` अंतर्गत सूचीबद्ध नाही), आणि `src/`, `open-sse/`, किंवा `bin/` अंतर्गत कोणतीही फाइल
  `extract-zip` npm पॅकेज आयात करत नाही — OmniRoute चा स्वतःचा `extractZip()` हेल्पर
  (`src/lib/versionManager/binaryManager.ts:93`) मूळ `unzip`/`tar` ला शेल करतो
  आणि तो असंबंधित आहे. `@openai/codex-security` देखील extract-zip च्या onEntry कॉलबॅकच्या वर स्वतःचा सिम्लिंक-ट्रॅव्हर्सल गार्ड पाठवतो.
- `package.json` `overrides` द्वारे `extract-zip` ला उपनाव **देऊ नका** — एकमेव व्यवहार्य
  ड्रॉप-इन रिप्लेसमेंट हे इलेक्ट्रॉन-ऑर्ग-इंटर्नल आहे आणि `@openai/codex-security` च्या स्वतःच्या onEntry/defaultDirMode/defaultFileMode तपासण्यांशी API-असंगत आहे;
  त्याला ओव्हरराइड केल्यास त्या पॅकेजच्या सुरक्षा तपासण्या शांतपणे खंडित होतील.
- **बेसलाइन:** मोजलेले osv `vulnCount` (3) आधीच गोठवलेल्या
  `config/quality/quality-baseline.json` बेसलाइन (27) च्या खूप खाली आहे — रॅचेट बदलाची आवश्यकता नाही.
- **रिग्रेशन गार्ड:** `tests/unit/extract-zip-14482-exposure.test.ts` वरील साखळी आणि नो-प्रॉडक्शन-इम्पोर्ट इन्व्हेरिएंटची पुष्टी करते; जर कधीही काही खंडित झाले (उदा. भविष्यातील PR `extract-zip` ला उत्पादनापासून पोहोचण्यायोग्य बनवते) तर ते CI अयशस्वी करते.
- **ट्रॅकिंग:** समस्या #14482.
