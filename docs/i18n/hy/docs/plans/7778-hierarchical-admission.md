1. Նպատակային թեստերով ամրագրեք գոյություն ունեցող մեկ բանալիով semaphore-ի պայմանագիրը և նոր՝ ատոմային բազմաբանալի պայմանագիրը՝ առանց մասնակի ամրագրումների, FIFO հերթագրում, ընդհատում, ժամանակի սպառում, հերթի լցվածություն, idempotent ազատում, վիճակագրություն և մաքրում։
2. Տեղում ընդհանրացրեք գոյություն ունեցող հաշվի semaphore-ը։ Պահպանեք `acquire()`-ը որպես `acquireMany()`-ի շուրջ համատեղելիության wrapper․ մի՛ ավելացրեք երկրորդ scheduler կամ dependency։
3. `chatCore`-ում միայն հաշվի համար կատարվող ձեռքբերումը փոխարինեք մեկ կուտակային գլոբալ/provider/account ձեռքբերմամբ՝ անմիջապես `withRateLimit`-ից առաջ։ Երբ հաշվի rotation-ը փոխում է connection-ը, կրկին ձեռք բերեք ամբողջ հավաքածուն և պահպանեք release-ը մինչև streaming-ի ավարտը։
4. Ընդլայնեք resilience-ի գոյություն ունեցող կարգավորումների pipeline-ը (types, defaults, normalization, schema, API response, UI և translations)՝ ավելացնելով գլոբալ և provider սահմանաչափերը։ Հին Bottleneck concurrency control-ը վերանվանեք որպես connection/quota-scope concurrency, որպեսզի դրա իրական scope-ը հստակ լինի։
5. Գործարկեք նպատակային թեստերը, lint-ը, typecheck-ը, static checks-ը և ամբողջական թեստային փաթեթը․ վարքագծային փոփոխությունը փաստաթղթավորեք changelog-ում։

Դիտավորյալ պահպանվող վարքագիծը՝ զրոյական/null concurrency-ն շրջանցում է gate-ը, միայն հաշվի հետ աշխատող կանչողները շարունակում են օգտագործել `acquire()`-ը, արգելափակված հաշիվների controls-ը պահպանում է իրենց key format-ը և API-ն, իսկ provider-ի rate-limit queue-ի վարքագիծը մնում է անփոփոխ։
