Այս փաստաթուղթը նկարագրում է OmniRoute-ում ավելացված՝ հետադարձ կապով կառավարվող հարմարվողական երթուղավորման հիմքը։ Այն միտումնավոր փոքր է․ ներմուծում է տիպավորված երթուղավորման արդյունքների ալիք, առցանց որակի ազդանշան, որը փոխանցվում է գոյություն ունեցող auto-combo գնահատիչին, ընտրովի OpenTelemetry արտահանիչ և բացատրելիության endpoint։ Այն **չի** փոխարինում գոյություն ունեցող կայունության շերտին (circuit breaker, կապի cooldown, մոդելի lockout, առողջական վիճակի մատրից, autopilot), այլ լրացնում է այն։

## 1. Ճարտարապետական համատեքստ

OmniRoute-ը տվյալների հարթություն է՝ **հարցումների թեժ ուղով** և **կառավարման/ինտելեկտի հարթությամբ**։ Թեժ ուղին պետք է մնա արագ, հիշողության օգտագործման առումով արդյունավետ, ասինխրոն, խափանումների նկատմամբ կայուն և կանխատեսելի։ Գնահատումը, որակի գնահատականների հաշվարկը, փորձարկումները և պատմական վերլուծությունը պատկանում են կառավարման հարթությանը։

```
AI գործակալ / IDE
      │
      ▼
┌─────────────────────┐
│    OmniRoute        │   տվյալների հարթություն (արագ, սինքրոն, հիշողության մեջ)
│  երթուղավորում /    │
│  պահուստային անցում │
│  առողջություն /     │
│  պաշտպանիչ սահման   │
│  քեշ / հոսքային     │
│  փոխանցում          │
└──────────┬──────────┘
           │ RoutingEvent (ուղարկել և չսպասել, ~0.2µs)
           ▼
┌─────────────────────┐
│ Հետադարձ կապի sinks │   կառավարման հարթություն (ասինխրոն, լավագույն ջանքով)
│ որակի հետագծիչ      │
│ OTel արտահանիչ      │
│ բացատրությունների    │
│ պահոց               │
└──────────┬──────────┘
           ▼  որակի գնահատական
      auto-combo գնահատիչ
```

### Ինչն արդեն առկա էր (աուդիտված, չկրկնօրինակված)

| Հասկացություն                                         | Գոյություն ունեցող իրականացում                                                                                  |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Հասանելիություն (կարո՞ղ ենք տրաֆիկ ուղարկել)          | Circuit breaker (CLOSED/DEGRADED/OPEN/HALF_OPEN, պահպանված DB-ում), կապի cooldown, մոդելի lockout               |
| Առողջական վիճակի հաշվետվություն                       | `providerHealthMatrix.ts`, `providerHealthAutopilot.ts`                                                         |
| Ստվերային տրաֆիկ                                      | `open-sse/services/combo/shadowRouting.ts`                                                                      |
| Պաշտպանիչ սահմաններ                                   | `src/lib/guardrails/` (նախնական/հետադարձ hooks)                                                                 |
| Ճշգրիտ քեշ                                            | `src/lib/semanticCache.ts` (ստորագրության վրա հիմնված)                                                          |
| Գնահատիչներ / գնահատումներով կառավարվող երթուղավորում | `src/lib/evals/`, `open-sse/services/evalRouting.ts`                                                            |
| Combo որոշումների բացատրելիություն                    | `open-sse/services/combo/decisionTrace.ts`                                                                      |
| Dashboard-ի իրական ժամանակի իրադարձություններ         | `src/lib/events/eventBus.ts` (UI ծանուցումների ալիք, `unknown` payload-ներ, 100 գրառումից բաղկացած պատմություն) |

Երթուղավորման իրադարձությունների շերտը `eventBus`-ի վերաիրականացում **չէ**․ այդ bus-ը dashboard-ի իրական ժամանակի ծանուցումների ալիքն է (տիպավորված _իրադարձությունների անուններ_, անթափանց payload-ներ, UI սպառողներ)։ `RoutingEvent`-ը տիպավորված _արդյունքի_ կառուցվածք է (ուշացում/token-ներ/արժեք/արդյունք/ավարտի պատճառ), որը սպառվում է կառավարման հարթության հետադարձ կապի sinks-ի կողմից (որակի հետագծիչ, OTel արտահանիչ, բացատրությունների պահոց)։

### Ինչն էր բացակայում (ավելացվել է այստեղ)

1. **Տիպավորված երթուղավորման արդյունքի իրադարձության + sink-ի աբստրակցիա** (`RoutingEvent` /
   `RoutingEventSink`)։ `decisionTrace`-ը սահմանափակված է combo-ով և միայն հիշողության մեջ է,
   `comboMetrics`-ը կուտակային հաշվիչներ են, իսկ `call_logs`-ը՝ չմշակված ասինխրոն պահպանում։
   Դրանցից ոչ մեկը տիպավորված, sink-ի վրա հիմնված արդյունքների ալիք չէ, որին կարող են բաժանորդագրվել որակի հետագծիչը, OTel
   արտահանիչը կամ Future-AGI-ի ոճով գնահատիչը։
2. Արդյունքի որակի **առցանց որակի ազդանշան** (EWMA)․ նախկինում գնահատիչը
   «որակը» մոտարկում էր միայն առաջադրանքի ստատիկ համապատասխանության և ըստ ցանկության միացվող գնահատումների անցման տոկոսների միջոցով։
3. GenAI-ի իմաստային համաձայնություններն օգտագործող **ընտրովի, կախվածություններից զերծ OTel արտահանիչ**։
4. Իրական երթուղավորման որոշումները և որակի վիճակը վերադարձնող **բացատրելիության endpoint**։

## 2. Երթուղավորման իրադարձություններ (հետադարձ կապի հիմք)

Ֆայլեր՝ `open-sse/services/routing/events.ts`, `.../index.ts`

`RoutingEvent`-ը պարունակում է միայն երթուղավորման մետատվյալներ․

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ...
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // թույլատրելի արժեքների միավորում
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

`RoutingEventSink`-ը TypeScript-ում `Send+Sync` ոճի trait է․

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // պետք է լինի O(1), առանց համաժամանակյա I/O-ի
}
```

Թեժ ուղին յուրաքանչյուր ավարտված հարցման համար մեկ անգամ կանչում է `emitRoutingEvent(event)`
(հոսքային ավարտի callback-ը, ոչ հոսքային հաջողության ուղին և
`handleChatCore`-ի սխալ ձևաչափված 200 պատասխանի ձախողման ուղին)։ Տարածումը կատարվում է
համաժամանակյա fan-out եղանակով դեպի գրանցված sink-երը, սակայն յուրաքանչյուր sink միայն
հերթագրում է կամ թարմացնում հիշողության մեջ պահվող վիճակը։ **Թեժ ուղու վրա չկան
տվյալների բազայում համաժամանակյա գրառումներ կամ ցանցային I/O։**

Լռելյայն sink-եր․

- `MemoryRoutingEventStore` — սահմանափակված (500) օղակաձև բուֆեր՝ նորերից հներին
  դասավորված, explain endpoint-ի համար։
- `QualityTracker` սպառիչ — թարմացնում է որակի EWMA գնահատականը։
- `OtlpHttpsEventSink` — ընտրովի է և միացվում է միայն այն դեպքում, երբ սահմանված է
  `OMNIROUTE_OTEL_ENDPOINT` (կամ `OTEL_EXPORTER_OTLP_ENDPOINT`)։

### Չափված հավելադիր ծախսը (ազնիվ համեմատություն)

`npm run bench:routing-events` այս աշխատանքային կայանում (100k կրկնություն․ ենթա-µs
գործողությունները չափվել են որպես համախառն µs/op, քանի որ մեկ գործողության
պրոցենտիլները ցածր են `performance.now()` ժամանակաչափի ճշգրտությունից)․

| Սցենար                                        | µs/op  | ops/s  |
| --------------------------------------------- | ------ | ------ |
| ելակետային (միայն գնահատում)                  | ~0.045 | ~22 M  |
| ելակետային + RoutingEvent (2 sink)            | ~0.168 | ~5.9 M |
| ելակետային + իրադարձություն + OTel հերթագրում | ~0.163 | ~6.1 M |
| զուգահեռ (8 հերթագայված պոռթկում)             | ~0.18  | —      |

Իրադարձությունների տարածման տարբերությունը ելակետային գնահատման նկատմամբ կազմում է
~0.12 µs/հարցում․ OTel sink-ը միայն հերթագրում է (O(1) բուֆերային push)՝ չավելացնելով
չափելի ծախս։ Այս թվերը հատուկ են տվյալ մեքենային և հարաբերական են՝ դրանք արտադրական
երաշխիք չեն։ v1-ի «~0.2 µs» ցուցանիշը համախառն գնահատական էր․ այս մեթոդաբանությունն
առանձնացնում է գնահատման ելակետային ծախսն իրադարձությունների տարածման ծախսից։

## 3. Որակի ազդանշան (հետադարձ կապով կառավարվող մատակարարի վիճակ)

Ֆայլեր՝ `open-sse/services/routing/quality.ts`

v2-ը տարանջատում է **գործառնական** որակը **իմաստային** որակից․

- **Գործառնական** — ստացվում է երթուղավորման թեժ ուղուց (HTTP 4xx/5xx, կապի
  խափանումներ, 429 պատասխաններ, սխալ ձևաչափված պատասխաններ, հոսքի ընդհատումներ,
  `finish_reason=length`, զրոյական ելքով հաջողություններ, ուշացման/TTFT EWMA)։
  200 պատասխանը ՉԻ համարվում իմաստային որակ։
- **Իմաստային** — գեներացված ելքի իրական արժեքը։ Այն ՄԻԱՅՆ գնահատիչի կողմից է
  արտադրվում՝ `setSemanticQuality()`-ի միջոցով։ Այն `null` է, քանի դեռ որևէ գնահատիչ
  արժեք չի տրամադրել, և երբեք չի ներթափանցում գործառնական գնահատականի մեջ։

Յուրաքանչյուր (մատակարար, մոդել) զույգի վիճակը (EWMA + սահմանափակ հաշվիչներ)․

- `successEwma` — արդյունքի հաջողության EWMA (α=0.2)։
- `latencyEwma` / `ttftEwma` — ուշացման EWMA (α=0.1)։
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`։
- `recencyMs` — որքան վերջերս է մոդելը վերջին անգամ դիտարկվել։

### Վստահություն / նմուշների քանակի հաշվառում

`confidence = clamp01(samples / 50)`, իսկ գնահատիչին վերադարձվող միավորը
մոտեցվում է չեզոք միջնակետին․

```
score = 0.5 + confidence * (operational - 0.5)
```

Հետևանքները (ստուգված թեստերով)․

- Սառը մատակարարը (0 նմուշ) ստանում է **0.5** միավոր՝ առանց անարդար տուգանման, սակայն
  չի կարող գերազանցել հազարավոր կայուն դիտարկումներ ունեցող մատակարարին։
- 7 պատահական հաջողություն ունեցող մատակարարի միավորը մոտեցվում է 0.5-ին (այն երբեք
  չի գերակայում լավատեսական սկզբնական արժեքավորման շնորհիվ)։
- 50+ նմուշ ունեցող մատակարարը համընկնում է իր իրական գործառնական գնահատականին։
- Վատթարացումն ու վերականգնումը աստիճանական են (EWMA), և մեկ առանձին ձախողումը
  չի ոչնչացնում առողջ մատակարարին։

`ProviderQuality`-ը տրամադրում է `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }`։

Սա փոխանցվում է auto-combo գնահատիչին՝ որպես `quality` գնահատման գործոն․

- `ScoringFactors.quality` / `ScoringWeights.quality`՝
  `open-sse/services/autoCombo/scoring.ts`-ում։
- `DEFAULT_WEIGHTS`՝ `health` 0.1905 → 0.1605, `quality` 0.03։ Գումարը մնում է 1.0։
- `buildAutoCandidates`-ը tracker-ից լրացնում է `candidate.quality`-ը․ տվյալներ
  չունեցող թեկնածուների համար լռելյայն օգտագործվում է չեզոք **0.5** արժեքը (սառը
  թեկնածուն ո՛չ խրախուսվում է, ո՛չ էլ տուգանվում)։

Փակ օղակը․

```
RoutingEvent → QualityTracker → getQualityScore → auto-combo-ի quality գործոն
      ↑                                                    │
      └────── հարցման արդյունք (handleChatCore) ←───────────┘
```

### Կոշտ բացառում ընդդեմ մեղմ տուգանքի

Որակի ազդանշանը միայն **մեղմ հարմարվողական նախապատվություն** է։ Կոշտ բացառումը մնում է
գոյություն ունեցող դիմակայունության շերտի պատասխանատվության ներքո՝ circuit breaker-ի
OPEN վիճակ, սպառված քվոտա, նույնականացման ձախողում, մոդելի արգելափակում․ դրանցից ոչ մեկի
վրա որակի գնահատականը չի ազդում։ Մատակարարը, որի որակի գնահատականը ժամանակավորապես
նվազել է, ստանում է ավելի ցածր նախապատվություն, բայց երբեք կոշտ ձևով չի անջատվում։

## 3b. Հոսքի կանոնական ժամանակաչափում (TTFT / ITL)

Ֆայլեր՝ `open-sse/utils/streamTiming.ts`

`createStreamTiming()`-ը հոսքային ուղու գործիքավորման միասնական կետն է,
որը միացված է `createSSEStream`-ին (open-sse/utils/stream.ts)՝

- `markByte()` — ստացվել է վերին հոսքի առաջին հատվածը։
- `markForward()` — առաջին հատվածը փոխանցվել է հաճախորդին (օգտագործվում է TTFT-ի համար)։
- `markInterrupted()` — հոսքի ժամկետի սպառում/ընդհատում/սխալ՝ մինչև մաքուր ավարտը։
- `ttft()` = առաջին փոխանցված SSE հատվածի ուշացում։ **Սա token-ի մակարդակի TTFT ՉԷ** —
  մեկ SSE հատվածը կարող է պարունակել զրո/մեկ/բազմաթիվ token-ներ։ Հստակ փաստաթղթավորված է։
- `avgItlMs()` = հատվածների միջև բացերի միջինը (ITL-ի համար հատվածի ուշացման մոտարկիչ)։

TTFT/ITL/interrupted տվյալները փոխանցվում են `RoutingEvent`-ին (`ttftMs`, `itlMs`) և
OTel sink-ի միջոցով արտահանվում են որպես GenAI/OmniRoute span-ի հատկանիշներ։

## 4. OpenTelemetry / GenAI դիտարկելիություն

Ֆայլեր՝ `open-sse/services/routing/otel.ts`

- Առանց կախվածությունների OTLP/HTTP JSON արտահանիչ (օգտագործում է գլոբալ `fetch`, առանց
  `@opentelemetry/*` SDK-ի)։
- Span-ները հետևում են GenAI իմաստաբանական պայմանավորվածություններին (`gen_ai.provider.name`,
  `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`,
  `gen_ai.completion.finish_reason`, `gen_ai.system`), ինչպես նաև OmniRoute-ի երթուղավորման
  հատկանիշներին (արդյունք, կարգավիճակ, ttft, կրկնափորձեր, պահուստային տարբերակ)։
- `record()`-ը միայն ավելացնում է տարրը սահմանափակ բուֆերում (O(1)). ֆոնային ժամանակաչափն
  ասինխրոն կերպով դատարկում է այն՝ `POST {endpoint}/v1/traces` հարցման միջոցով։ Գերբեռնվածության
  դեպքում ամենահին իրադարձությունները հեռացվում են (`dropped` հաշվիչ)՝ երբեք հակաճնշում
  չստեղծելով տվյալների հարթության վրա։
- **Անջատված է, եթե կազմաձևված չէ։** `OMNIROUTE_OTEL_ENDPOINT`-ը (կամ
  `OTEL_EXPORTER_OTLP_ENDPOINT`-ը) պետք է սահմանված լինի, հակառակ դեպքում sink-ը չի
  գրանցվում, և OTel-ի ոչ մի կոդ չի գործարկվում։

## 5. Բացատրելիություն

- `GET /v1/explain/routing`-ը վերադարձնում է վերջին `RoutingEvent`-ները (իրական
  որոշումները՝ սկզբում ամենանորերը) և ըստ մատակարարի/մոդելի որակի պատկերը։
- Նույնականացումը համարժեք է `/v1/combos`-ին (Bearer API բանալի կամ վահանակի աշխատաշրջան,
  իսկ `REQUIRE_API_KEY=false`-ով մեկ օգտատիրոջ տեղային տեղակայումներում՝ անանուն հասանելիություն)։
- Յուրաքանչյուր կանչի combo-մակարդակի հետքերը շարունակում են հասանելի լինել գոյություն ունեցող
  `decisionTrace.ts`-ի միջոցով (`X-OmniRoute-Combo-Trace` վերնագիր)։
- Անվտանգություն՝ իրադարձությունները պարունակում են միայն երթուղավորման մետատվյալներ և երբեք
  չեն պարունակում prompt-ներ/մարմիններ/նույնականացման տվյալներ։

## 6. Գնահատման հարթության ինտեգրում (պատրաստվածություն Future AGI-ի համար)

OmniRoute-ը դիտարկում է Future AGI-ն (կամ ցանկացած գնահատիչ) որպես **հնարավոր
ինտելեկտային/գնահատման հետնամաս, այլ ոչ թե կախվածություն**։ Ինտեգրման կետերն են՝

- `RoutingEventSink`-ը կարող է իրադարձություններն ասինխրոն կերպով փոխանցել գնահատիչին։
- `MemoryRoutingEventStore`-ը և որակի պատկերը գնահատիչին տրամադրում են որոշումների չմշակված
  հոսքը։
- Ապագա `Evaluator`-ը (դետերմինիստական, տեղային դատավոր, HTTP, WASM) կսպառի
  իրադարձությունները/հետքերը և կվերադարձնի `QualityScore`, որը կփոխանցվի նույն
  `getQualityScore`/որակի գործակցի ուղուն։
- Գնահատման վրա հիմնված առկա երթուղավորումը (`open-sse/services/evalRouting.ts`) միացված
  լինելու դեպքում արդեն վերադասավորում է combo թիրախները՝ ըստ `eval_runs`-ի հաջող անցման
  գործակիցների։

Ոչ մի գնահատում համաժամանակյա չի կատարվում հարցման ուղու վրա, և gateway-ն ամբողջությամբ
գործում է նաև գնահատիչի բացակայության դեպքում։

## 7. Վերջնական ճարտարապետական վերանայում

1. **Ի՞նչ է մնում համաժամանակյա թեժ ուղու վրա։** Երթուղավորում/միավորների հաշվարկ, guardrail-ի
   նախնական ստուգումներ, cache-ի որոնում և մեկ `emitRoutingEvent` fan-out (ելակետային
   միավորների հաշվարկի համեմատ՝ ~0.12 µs) դեպի հիշողության մեջ գտնվող sink-երը։
2. **Ի՞նչ է տեղափոխվել ասինխրոն մշակման։** OTel արտահանում (ժամանակաչափ + fetch),
   `call_logs`/օգտագործման պահպանություն, semantic-cache-ի գրառումներ, իսկ որակը պահվում է
   հիշողության մեջ և O(1) է (ասինխրոն մշակում անհրաժեշտ չէ)։
3. **Ինչպե՞ս է երթուղավորման արդյունքը դառնում հետադարձ կապ։** `handleChatCore`-ը ստեղծում է
   `RoutingEvent` → `QualityTracker`-ը թարմացնում է EWMA վիճակը → `getQualityScore`-ը
   տվյալներ է մատակարարում auto-combo-ի `quality` գործակցին։
4. **Ինչպե՞ս է որակն ազդում հետագա երթուղավորման վրա։** Որակի ցածր միավորը նվազեցնում է
   տվյալ մատակարարի/մոդելի կշռված միավորը `scoreAutoTargets`-ում, ուստի վատթարացած
   մոդելներն աստիճանաբար ավելի քիչ են նախընտրվում և վերականգնում են իրենց դիրքը՝ EWMA-ի
   բարելավմանը զուգընթաց։
5. **Ինչպե՞ս կարող է Future AGI-ն ինտեգրվել՝ առանց կախվածություն դառնալու։**
   `RoutingEventSink` ինտերֆեյսի / ապագա `Evaluator` ադապտերի միջոցով՝ առանց կոշտ
   կոդավորված կախվածության։
6. **Ի՞նչ է տեղի ունենում, երբ գնահատիչն անհասանելի է։** Երթուղավորումը չի ազդվում.
   դիտարկված ազդանշան չունեցող մոդելների համար որակը վերադառնում է չեզոք արժեքի (1.0)։
7. **Ի՞նչ է տեղի ունենում, երբ հեռաչափությունն անհասանելի է։** OTel sink-ը պարզապես չի
   գրանցվում. երթուղավորման շերտի մնացած մասը շարունակում է աշխատել անփոփոխ։
8. **Ի՞նչ է տեղի ունենում գերբեռնվածության դեպքում։** OTel բուֆերը հեռացնում է ամենահին
   իրադարձությունները. որակը և օղակաձև բուֆերը կառուցվածքով սահմանափակ են. հակաճնշում չկա։
9. **Ինչպե՞ս է մատակարարի վիճակը վերականգնվում վատթարացումից հետո։** EWMA-ն կրկին
   կոնվերգացվում է հաջողությունների կուտակմանը զուգընթաց. warmup-ը նոր մոդելները պահում է
   չեզոք վիճակում, իսկ circuit breaker-ն անկախ վերականգնվում է HALF_OPEN փորձարկումների
   միջոցով։
10. **Առաջարկված ո՞ր գործառույթները միտումնավոր ՉԵՆ իրականացվել և ինչո՞ւ։**
    - Ստվերային երթևեկություն / փորձարկումներ — արդեն իրականացված է
      (`combo/shadowRouting.ts`). կրկին չի կառուցվել։
    - Guardrail-ներ — արդեն իրականացված են (`src/lib/guardrails/`). չեն կրկնօրինակվել։
    - Semantic cache — արդեն իրականացված է (`src/lib/semanticCache.ts`). չի
      կրկնօրինակվել։
    - Փորձարկումների կառավարման ամբողջական հարթակ, տվյալների հավաքածուների գործիքակազմ,
      prompt-ների օպտիմալացման հարթակ, վեկտորային DB կամ պարտադիր արտաքին OTel
      ենթակառուցվածք — դուրս են թեթև տվյալների հարթության շրջանակից։
    - Rust-ի `RoutingEvent` struct — տվյալների հարթությունը TypeScript-ով է. TS տիպը
      հարմարեցված համարժեքն է։

  դասակարգում, սահմանափակված օղակաձև բուֆեր, ընդունիչների բազմաուղղում + մեկուսացում։

  անոմալիաների տույժեր, 429 անցողիկ պատասխանի մշակում, ակնթարթային պատկեր, վերակայում։

  լռելյայն արժեք, որակի գործոնով դասակարգում։
- `tests/unit/routing-otel.test.ts` — միացման պայմանավորում, GenAI span-ի օգտակար բեռ, ասինխրոն
  դատարկում, գերբեռնվածության դեպքում բաց թողում։

  բուֆերի սահմանափակվածություն, բացառություն նետող ընդունիչի մեկուսացում, հերթագայված ասինխրոն պոռթկումներ,

  `scoreAutoTargets` գնահատիչի միջոցով՝ առողջ → վատթարացում → վերականգնում → կարճատև խափանում, ինչպես նաև
