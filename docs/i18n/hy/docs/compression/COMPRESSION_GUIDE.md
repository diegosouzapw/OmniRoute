## Ակնարկ

OmniRoute-ն իրականացնում է հուշումների սեղմման մոդուլային խողովակաշար, որը գործարկվում է **նախապես**՝ մինչև հարցումների վերին մակարդակի մատակարարներին հասնելը։ Սա նշանակում է, որ տոկենների խնայողությունը կատարվում է թափանցիկ կերպով՝ առանց ձեր աշխատանքային հոսքը փոխելու անհրաժեշտության։

```
Հաճախորդի հարցում
  → Սեղմման ռազմավարության ընտրիչ
    → Կոմբոյի վերասահմանո՞ւմ → Օգտագործել կոմբոյի կարգավորումը
    → Ինքնաշխատ գործարկման շե՞մ → Օգտագործել ինքնաշխատ ռեժիմը
    → Լռելյայն ռեժի՞մ → Օգտագործել գլոբալ կարգավորումը
    → Անջատվա՞ծ է → Բաց թողնել սեղմումը
  → Ընտրված սեղմման ռեժիմ
    → Անջատված․ առանց սեղմման
    → Թեթև․ բացատների/ձևաչափման անվտանգ մաքրում (~15%)
    → Ստանդարտ․ պարզունակ խոսքի ոճով ավելորդ բառերի հեռացում (~30%)
    → Ագրեսիվ․ պատմության հնացում + ամփոփում (~50%)
    → Ուլտրա․ էվրիստիկ կրճատում + կոդի բլոկների նոսրացում (~75%)
    → RTK․ հրամանները հաշվի առնող տերմինալի/գործիքի ելքի զտում (վերին մակարդակում՝ 60-90% միջակայք)
    → Շերտավորված․ կարգավորված բազմաշարժիչ խողովակաշար, սովորաբար՝ RTK, ապա Caveman (համապատասխան մասի 78-95% միջակայք)
  → Սեղմված հարցում → Մատակարար
```

## Սեղմման ռեժիմներ

### Անջատված

Սեղմում չի կիրառվում։ Բոլոր հաղորդագրությունները փոխանցվում են անփոփոխ։

### Թեթև ռեժիմ (~15% խնայողություն, <1ms ուշացում)

Ամենաանվտանգ ռեժիմը՝ առանց իմաստային որևէ փոփոխության, միայն ձևաչափման մաքրում․

| Տեխնիկա                  | Նկարագրություն                                                      |
| ------------------------ | ------------------------------------------------------------------- |
| `collapseWhitespace`     | Միավորել իրար հաջորդող դատարկ տողերը և հեռացնել տողավերջի բացատները |
| `dedupSystemPrompt`      | Հեռացնել կրկնվող համակարգային հաղորդագրությունները                  |
| `compressToolResults`    | Սեղմել գործիքների/ֆունկցիաների ծավալուն ելքերը                      |
| `removeRedundantContent` | Հեռացնել կրկնվող հրահանգները                                        |
| `replaceImageUrls`       | Կրճատել base64 պատկերի տվյալների URI-ները                           |

**Լավագույնն է՝** մշտապես միացված օգտագործման և անվտանգության համար կրիտիկական աշխատանքային հոսքերի համար։

### Ստանդարտ ռեժիմ (~30% խնայողություն)

Ոգեշնչված է [Caveman-ից](https://github.com/JuliusBrussee/caveman)՝ հեռացնում է ավելորդ բառերն ու ծավալուն ձևակերպումները՝ պահպանելով իմաստը․

- Հեռացնում է ավելորդ բառերը («please», «I think», «basically», «actually»)
- Խտացնում է ծավալուն արտահայտությունները («in order to» → «to», «as a result of» → «because»)
- Հեռացնում է քաղաքավարի անորոշ ձևակերպումները («Would you mind...», «If you could possibly...»)
- Կոդավորման հուշումների համար կարգաբերված 30-ից ավելի կանոնավոր արտահայտության կանոններ

**Լավագույնն է՝** ամենօրյա կոդավորման աշխատանքային հոսքերի և ծախսերը վերահսկող թիմերի համար։

### Ագրեսիվ ռեժիմ (~50% խնայողություն)

Պատմության խելացի կառավարում երկարատև աշխատաշրջանների համար․

- **Հաղորդագրությունների հնացում** — ավելի հին հաղորդագրություններն աստիճանաբար ավելի են սեղմվում
- **Գործիքների արդյունքների ամփոփում** — գործիքների երկար ելքերը փոխարինվում են ամփոփումներով
- **Կառուցվածքային ամբողջականության պաշտպանիչ միջոցներ** — ապահովում են, որ `tool_use` + `tool_result` զույգերը մնան համահունչ
- **Համատեքստի պատուհանի հաշվառում** — պահպանում է յուրաքանչյուր մոդելի տոկենների սահմանաչափերը

**Լավագույնն է՝** երկարատև վրիպազերծման աշխատաշրջանների և մեծ կոդային բազաների համար։

### Ուլտրա ռեժիմ (~75% խնայողություն)

Առավելագույն սեղմում՝ տոկենների առումով կրիտիկական սցենարների համար․

- **Էվրիստիկ կրճատում** — հեռացնում է համապատասխանության շեմից ցածր հաղորդագրությունները
- **Կոդի բլոկների նոսրացում** — սեղմում է կրկնվող կոդի օրինակները
- **Երկուական որոնմամբ հատում** — գտնում է համատեքստի պատուհանի կտրման օպտիմալ կետը
- Ներառում է Ագրեսիվ ռեժիմի բոլոր հնարավորությունները

**Լավագույնն է՝** երբ բազմիցս հասնում եք համատեքստի սահմանաչափերին։

### RTK ռեժիմ (վերին մակարդակում՝ 60-90% միջակայք)

RTK ռեժիմը օպտիմիզացված է կոդավորման գործակալների աշխատաշրջաններում հանդիպող գործիքների ծավալուն ելքերի համար․

- Հայտնաբերում է հրամանների/ելքերի այնպիսի դասեր, ինչպիսիք են `git status`, `git diff`, `git log`, թեստերի գործարկիչները,
  TypeScript/Vite/Webpack կառուցումները, ESLint/Biome/Prettier-ը, npm-ի աուդիտները/տեղադրումները, Docker-ի մատյանները, ենթակառուցվածքի
  ելքը և ընդհանուր կեղևի ելքը
- Կիրառում է JSON զտիչների փաթեթները `open-sse/services/compression/engines/rtk/filters/`-ից
- Ներմուծում է RTK TOML schema v1 զտիչները նախագծի կամ գլոբալ `filters.toml` ֆայլերից՝ ներկառուցված թեստերի
  վավերացմամբ և նախագծային ֆայլերի վստահության ստուգմամբ
- Տրամադրվում է ներկառուցված ստուգման օրինակներ պարունակող 49 զտիչով
- Հեռացնում է ANSI կառավարման հաջորդականությունները, առաջընթացի ցուցիչները, կրկնվող տողերը և գործնական նշանակություն չունեցող աղմուկը
- Պահպանում է ձախողումները, սխալները, զգուշացումները, փոփոխված ֆայլերը, ամփոփումները և երկար ելքի վերջնամասը
- Աջակցում է վստահության ստուգմամբ նախագծային զտիչներին, գլոբալ զտիչներին և ընտրովի՝ խմբագրված չմշակված ելքի վերականգնմանը

**Լավագույնն է՝** shell-ի, կառուցման, թեստավորման, git-ի, grep-ի և ֆայլային ելքերի գրառումներով գործակալի աշխատաշրջանների համար։

### Շերտավորված ռեժիմ (համապատասխան մասի 78-95% միջակայք)

Շերտավորված ռեժիմը որոշակի հերթականությամբ գործարկում է սեղմման մի քանի շարժիչ։ Լռելյայն խողովակաշարն է՝

```txt
RTK -> Caveman
```

Այս հերթականությունը նախ սեղմ է պահում տերմինալի/գործիքի ելքը, ապա մնացած բնական լեզվով հուշման նկատմամբ կիրառում է Caveman-ի իմաստային խտացումը։ Շերտավորված խողովակաշարերը կարող են կազմաձևվել գլոբալ կերպով կամ երթուղավորման կոմբոներին նշանակված սեղմման կոմբոների միջոցով։

**Լավագույնն է՝** գործիքների մեծ մատյաններ և մարդկային հրահանգներ կամ օգնականի ամփոփումներ պարունակող խառը համատեքստի համար։

## Վերադաս նախագծերի խնայողությունների հաշվարկ

OmniRoute-ը փաստագրում է սեղմումից ստացվող խնայողությունները՝ հիմնվելով երկու աղբյուրի վրա՝ վերադաս նախագծերի չափորոշիչների և
OmniRoute-ի սեփական շարժիչների համադրման։

| Աղբյուր | Այստեղ օգտագործված՝ վերադաս նախագծի README-ի ցուցանիշը                                                                                      |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | ելքային թոքենների `~75%`-ով պակաս քանակ, չափորոշիչներում ելքի միջին `65%` խնայողություն, `22-87%` միջակայք և մուտքը `~46%`-ով սեղմող գործիք |
| RTK     | հրամանների ելքի `60-90%` խնայողություն․ օրինակելի աշխատաշրջանում՝ `~118,000 -> ~23,900` թոքեն, կամ `79.7%` խնայողություն (`~80%`)           |

Գործիքի/համատեքստի համընկնող օգտակար բեռների դեպքում OmniRoute-ի լռելյայն համակցությունը շարժիչները դասավորում է հետևյալ կերպ․

```txt
RTK -> Caveman
```

Համակցված խնայողությունները բազմապատկական են, ոչ թե գումարային․

```txt
համակցված = 1 - (1 - RTK-ի խնայողություն) * (1 - Caveman-ի մուտքային խնայողություն)
միջին     = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
միջակայք  = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

Այդ `78-95%` ցուցանիշը կիրառելի է, երբ և՛ RTK-ն, և՛ Caveman-ը կարող են կրճատել միևնույն մուտքային/համատեքստային օգտակար բեռը։
Caveman-ի պատասխանի ելքային ռեժիմն առանձին է․ երբ այն միացված է, օգտագործեք Caveman-ի սեփական ելքային խնայողությունները (`65%`
միջին, `~75%` գլխավոր ցուցանիշ, `22-87%` միջակայք)։ Ընդհանուր վճարային խնայողությունները կախված են ձեր հուշումների/ելքերի հարաբերակցությունից։

### Ի՞նչ է իրականում նշանակում «կիրառելի»

Գլխավոր `15-95%` միջակայքն իրական է, սակայն այն կիրառվում է միայն **կրկնվող կամ չափազանց ծավալուն** բովանդակության նկատմամբ՝ կրկնվող
սխալի տողեր, նույն նախազգուշացումը բազմիցս արտածող կառուցման մատյան, չափազանց մեծ `grep`/ֆայլի ընթերցման արտածում։ Դա
**չի** նշանակում, որ յուրաքանչյուր հարցում այդքան խնայողություն է ապահովում։

Փորձնականորեն հաստատված է (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`)․ Anthropic-ի ձևաչափով `tool_result` բլոկի նկատմամբ, որը պարունակում էր սխալի 300 նույնական
տող, `stacked` (RTK + Caveman) գործարկումն ապահովել է **թոքենների 95.93% խնայողություն / նիշերի 96.26% խնայողություն**՝ ճշգրտորեն տեղավորվելով հայտարարված
միջակայքում։ Սակայն նույն շղթայի գործարկումը սովորական, չկրկնվող գործիքի ելքի նկատմամբ (`grep`-ի համապատասխանությունների մաքուր ցանկ,
ֆայլի կարճ ընթերցում, սովորական զրույցի տեքստ) իրավացիորեն ապահովում է **գրեթե զրոյական խնայողություն**, քանի որ
հեռացնելու կրկնվող տարրեր չկան, իսկ `validateCompression()`-ը (`validation.ts`) թույլ չի տալիս ուղարկել այնպիսի
վերաշարադրում, որը կհեռացնի կամ կփոփոխի կոդի բլոկներ, URL-ներ, վերնագրեր, տարբերակներ կամ ALL-CAPS հաստատունների նույնացուցիչներ։

Սա սպասվող և անվտանգ վարքագիծ է, ոչ թե սխալ․ ծրագրավորման աշխատաշրջանը, որը հիմնականում ընթերցում/որոնում է մաքուր ֆայլեր,
կունենա ընդհանուր համեստ խնայողություններ, նույնիսկ երբ սեղմումը լիովին միացված է, մինչդեռ խափանվող
ցիկլի կամ շատախոս լինտերի հանդիպող աշխատաշրջանն այդ տվյալահոսքի համար կունենա ամբողջական `78-95%` խնայողությունը։ Մի՛ օգտագործեք մեկ աշխատաշրջանի
ցածր ընդհանուր խնայողության տոկոսը՝ որպես սեղմման սխալ կազմաձևման ապացույց․ նախ ստուգեք՝ արդյոք
հիմքում ընկած գործիքի ելքն իրականում կրկնվող էր։

## Կարգավորում

### Կառավարման վահանակ

Անցեք `Dashboard → Context & Cache`:

- **Caveman** — ռեժիմի ընտրություն, լեզվական փաթեթներ, նախադիտում և գլոբալ լռելյայն արժեքներ
- **RTK** — հրաման-ֆիլտրի նախադիտում, RTK անվտանգության կարգավորումներ և ֆիլտրերի կատալոգ
- **Compression Combos** — անվանական շարժիչի խողովակաշարեր, որոնք նշանակված են երթուղային կոմբինացիաներին
- **Auto-Trigger Threshold** — ավտոմատ կերպով միացնել սեղմումը, երբ թոքենների քանակը գերազանցում է շեմը

### Կոմբինացիայի համար գերակայություն

`Dashboard → Context & Cache → Compression Combos` բաժնում սեղմման կոմբինացիան նշանակեք երթուղային
կոմբինացիային:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

Սա թույլ է տալիս օգտագործել շերտավորված սեղմում անվճար/կոդավորման մատակարարների վրա՝ միաժամանակ պահպանելով լայթ ռեժիմը վճարովի բաժանորդագրությունների համար:

Այս «Կոմբինացիայի համար գերակայություն» նշանակումը տարբեր վերահսկողություն է **երթուղային-կոմբինացիայի սեղմման ռեժիմի** գերակայությունից (Default/Off/Lite/Standard/Aggressive/Ultra) — այդ գերակայությունը չի ընտրում անվանական սեղմման-կոմբինացիայի խողովակաշար; այն պարզապես սահմանում է `compressionMode` դաշտը, որը խորհրդակցվում է `resolveCompressionPlan`-ի կողմից: Այն կարող է սահմանվել կամ կոմբինացիայի քարտի վրա (`Dashboard → Combos`) կամ, #6760-ից ի վեր, յուրաքանչյուր երթուղային կոմբինացիայի համար «Assign to routing» ցուցակում՝ `Dashboard → Context & Cache → Compression Combos` բաժնում, անմիջապես վերևում փաստաթղթավորված խողովակաշարի նշանակման վանդակաճաղի կողքին: Երկու մակերեսներն էլ պահպանվում են նույն `PUT /api/combos/{id}` վերջնակետի միջոցով:

### Հարցման համար գերակայություն

Ուղարկեք `x-omniroute-compression` հարցման վերնագիրը՝ մեկ հարցման համար սեղմման պլանը գերակայելու համար: Այն ունի ամենաբարձր առաջնահերթությունը — այն գերազանցում է երթուղային-կոմբինացիայի գերակայությանը, ակտիվ պրոֆիլին, ավտոմատ գործարկմանը և վահանակի լռելյայն արժեքին: Անհայտ արժեքներն անտեսվում են (հարցումը երբեք չի մերժվում), և գլոբալ հիմնական անջատիչը դեռևս ամեն ինչ վերահսկում է. երբ սեղմումն անջատված է գլոբալ մակարդակում, վերնագիրը չի կարող այն միացնել: Արժեքներ:

| Արժեք         | Ազդեցություն                                                                                                     |
| ------------- | ---------------------------------------------------------------------------------------------------------------- |
| `off`         | Այս հարցման համար սեղմում չկա:                                                                                   |
| `default`     | Վահանակից ստացված լռելյայն պրոֆիլը (անտեսում է ակտիվ պրոֆիլը): Կորուստներով շարժիչներն անջատված են մնում:        |
| `safe`        | Նույնն է, ինչ վերնագիրը բաց թողնելը. միայն կրկնօրինակում և բացատների ծալում:                                     |
| `allow-lossy` | Պահպանել այս հարցման օպերատորի պլանը, ներառյալ ամփոփագրերը, համապատասխանության ֆիլտրերը և ոճի վերաշարադրումները: |
| `engine:<id>` | Մեկ շարժիչ, երբ միացված է, օրինակ՝ `engine:rtk`: Սա այդ շարժիչի համար հարցման համար ընտրովի միացումն է:          |
| `<combo>`     | Անվանական կոմբինացիա, որը համընկնում է նախ անունով (առանց մեծատառերի տարբերակման), ապա ID-ով:                    |

Առանց `allow-lossy`, `engine:<id>` կամ անվանական կոմբինացիայի, կորուստներով շարժիչները չեն կիրառվում: Հարցումը դեռևս ստանում է նիստի կրկնօրինակում և բացատների ծալում, երբ սեղմումը միացված է:

Կիրառված պլանը արձագանքվում է `X-OmniRoute-Compression: <mode>; source=<source>` պատասխան վերնագրում, որտեղ `<source>`-ը `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` կամ `off` է:

### API

```bash
# Ստանալ սեղմման կարգավորումները
curl http://localhost:20128/api/settings/compression
```

Standard ռեժիմի սեղմման կանոնները ներշնչված են **[JuliusBrussee](https://github.com/JuliusBrussee)**-ի **[Caveman](https://github.com/JuliusBrussee/caveman)** (⭐ 51K+) նախագծից՝ լայն տարածում ստացած «ինչու օգտագործել շատ թոքեն, երբ քիչ թոքենն էլ գործ է անում» նախագծից։ Caveman-ը հաղորդում է ելքային թոքենների `~75%` կրճատման, հենանիշային թեստերում ելքի միջինը `65%` խնայողության, ելքի `22-87%` միջակայքի և մուտքի սեղմման `~46%` գործիքի մասին։

## Ընդլայնված սեղմման համակարգեր

7 ստանդարտ ռեժիմներից բացի, OmniRoute-ը ներառում է մի քանի առաջադեմ սեղմման համակարգեր, որոնք ավտոմատ կերպով աշխատում են՝ հիմնվելով համատեքստի վրա։

### Քեշ-գիտակցված սեղմում

Որոշ մատակարարներ (ինչպես Anthropic-ը՝ հուշումների քեշավորմամբ) աջակցում են **հուշումների քեշավորմանը**, ինչը թույլ է տալիս նրանց քեշավորել հուշումների մասերը՝ ծախսերը և ուշացումները նվազեցնելու համար։ Երբ քեշավորումը միացված է, ագրեսիվ սեղմումը կարող է իրականում **վնասել** կատարողականին, քանի որ այն փոխում է քեշավորված թոքենները՝ անվավեր դարձնելով քեշը։

`cachingAware.ts` մոդուլը լուծում է այս խնդիրը՝ **հայտնաբերելով քեշավորման համատեքստը** և **համապատասխանաբար կարգավորելով սեղմման ռազմավարությունը**։

#### Ինչպես է այն աշխատում

1. **Հայտնաբերել քեշավորման համատեքստը** — Սկանավորում է հարցման մարմինը `cache_control` մարկերների համար
2. **Բացահայտել քեշավորող մատակարարներին** — Ստուգում է, թե արդյոք թիրախային մատակարարը աջակցում է քեշավորմանը
3. **Կարգավորել ռազմավարությունը** — `aggressive`/`ultra` ռեժիմները իջեցնում է `standard` քեշավորող մատակարարների համար
4. **Բաց թողնել համակարգի հուշումը** — Համակարգի հուշումները սովորաբար քեշավորվում են, ուստի մի սեղմեք դրանք
5. **Օգտագործել դետերմինիստական փոխակերպումներ** — Օգտագործել միայն այն փոխակերպումները, որոնք ապահովում են հետևողական արդյունք

#### Կոդի օրինակ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Քեշի մարկեր
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### Երբ օգտագործել

Քեշ-գիտակցված սեղմումը **միշտ միացված է** — կարգավորում չի պահանջվում։ Այն միայն ակտիվանում է, երբ.

- Հարցումն ունի `cache_control` մարկերներ
- Թիրախային մատակարարը աջակցում է հուշումների քեշավորմանը (Anthropic, OpenAI և այլն)

### Պրոգրեսիվ ծերացում

Երկար զրույցները կուտակում են բազմաթիվ հաղորդագրությունների շրջադարձեր, սակայն հին շրջադարձերը դառնում են պակաս արդիական։ `progressiveAging.ts` մոդուլը **վատթարացնում է հաղորդագրությունները՝ ըստ շրջադարձի հեռավորության**.

- **Վերջին շրջադարձեր (0-3)**. Պահպանվում են բառացիորեն (ամբողջական մանրամասներով)
- **Միջին շրջադարձեր (4-8)**. Թեթև սեղմում (բացատների, ձևաչափման մաքրում)
- **Հին շրջադարձեր (9+)**. Քարանձավային սեղմում (լցոնիչների հեռացում, ամփոփում)
- **Շատ հին շրջադարձեր (20+)**. Ծանր ամփոփված կամ բաց թողնված

#### Կոդի օրինակ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 ավելի շրջադարձեր ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // Առաջին 3 շրջադարձերը՝ բառացի
  light: 8, // 4-8 շրջադարձերը՝ թեթև սեղմում
  moderate: 20, // 9-20 շրջադարձերը՝ քարանձավային սեղմում
  // 21+ շրջադարձերը՝ ծանր ամփոփում
});

// saved = պահպանված թոքենների քանակը
```

#### Երբ օգտագործել

Պրոգրեսիվ ծերացումը **միշտ միացված է** `aggressive` և `ultra` ռեժիմների համար։ Այն հատկապես արդյունավետ է հետևյալի համար.

- Երկարատև կոդավորման սեանսներ
- Բազմօրյա զրույցներ
- Գործակալական աշխատանքային հոսքեր՝ բազմաթիվ գործիքների կանչերով

### Քարանձավային ելքային ռեժիմ

`outputMode.ts` մոդուլը ներարկում է **համակարգի հուշման հրահանգներ**՝ մոդելին ստիպելու համար արտադրել սեղմված, հակիրճ արդյունք («քարանձավային» ոճով)։

#### Ինչպես է այն աշխատում

Մուտքը սեղմելու փոխարեն, այս ռեժիմը ավելացնում է համակարգի հուշում, ինչպիսին է.

> «Պատասխանեք նվազագույն բառերով։ Բաց թողեք քաղաքավարությունները։ Օգտագործեք կարճ նախադասություններ»։

Սա հատկապես լավ է աշխատում հետևյալի համար.

- Կոդի ստեղծում (ավելի հակիրճ արդյունք = ավելի քիչ թոքեններ)
- Արագ հարցուպատասխան (կարիք չկա մանրամասն բացատրությունների)
- Խմբաքանակային մշակում (առավելագույն թողունակություն)

#### Երբ օգտագործել

Քարանձավային ելքային ռեժիմը **ընտրովի է** — այն կարգավորվում է կոմբո կոնֆիգուրացիայի միջոցով.

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "outputMode": "caveman"
    }
  }
}
```

### Ելքային ոճեր (կատալոգ)

Վերոնշյալ քարանձավային ելքային ռեժիմը **ժառանգական մեկ ոճի ուղին է**։ Փուլ 4-ը այն ընդհանրացրեց՝ դարձնելով կոմպոզիցիոն ելքային ոճերի կատալոգ՝ `OUTPUT_STYLE_CATALOG` `open-sse/services/compression/outputStyles/catalog.ts` ֆայլում։ Յուրաքանչյուր ոճ համակարգի հուշման հրահանգ է, որը մոդելին ստիպում է արտադրել ավելի էժան արդյունք. ոճերը կարող են միացվել միասին և ներարկվում են կատալոգի կարգով։

| Ոճ | `id` | Ինչ է անում | Հրահանգների լեզուներ |

Յուրաքանչյուր ոճ ունի երեք ինտենսիվության մակարդակ՝ `lite`, `full`, `ultra`, և յուրաքանչյուր մակարդակ
ավարտվում է ընդհանուր սահմանների կետով, որը կոդի բլոկները, ֆայլերի ուղիները, հրամանները,
սխալների տողերը, URL-ները և նույնացուցիչները թողնում է անփոփոխ։

#### Ինչպես է աշխատում ներարկումը

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) լուծում է
ընտրությունը կատալոգի դեմ (անհայտ ID-ները և տեղայնացմանը չհամապատասխանող ոճերը
անտեսվում են, երբեք սխալ չեն առաջացնում), միացնում է ընտրված հրահանգները կատալոգի կարգով,
միացնում է սահմանների կետը **մեկ անգամ**, և արդյունքը տեղադրում է համակարգի հուշման մեջ
մեկ իդեմպոտենտության մարկերի հետևում (`[OmniRoute Output Styles]`) — կրկնակի կիրառումը
ոչինչ չի փոխում։ Երբ հայտնաբերված հարցման լեզուն ունի թարգմանություն, ներարկվում է
տեղայնացված հրահանգը՝ անգլերենի փոխարեն։

#### Ինչպես միացնել

Կառավարման վահանակում՝ **Context → Settings → Compression** — յուրաքանչյուր ոճի համար մեկ տող՝
միացման/անջատման անջատիչով և մակարդակի ընտրիչով։ Ծրագրային առումով, սեղմման կոնֆիգուրացիան
պահպանում է ընտրությունը որպես.

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

Հետադարձ համատեղելիություն. հին `outputMode: "caveman"` համակցված կարգավորումը դեռ աշխատում է և
քարտեզագրվում է `terse-prose`-ին, բայթ-առ-բայթ նույնական է հին ներարկմանը յուրաքանչյուր հին լեզվով։

Լեզվի ընտրություն. երբ `languageConfig.enabled` միացված է, `autoDetect`-ը ընտրում է
վերջին օգտատիրոջ հաղորդագրության լեզուն (նույն դետեկտորը, ինչ մուտքային շարժիչները);
`autoDetect`-ը անջատելը ամրացնում է `defaultLanguage`-ը։ Անջատված → Անգլերեն։

Ոճի × լեզվի մատրիցը ամրացված է
`tests/unit/compression/output-styles-i18n-matrix.test.ts`-ով. նոր ոճը չի կարող թողարկվել
առանց առնվազն pt-BR թարգմանության (կամ բացահայտ հետևվող բացառության), և
գոյություն ունեցող ոճը չի կարող աննկատ կորցնել տեղայնացումը։ Ոճ ավելացնելու համար տես
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style)։

### Գործիքի արդյունքի սեղմում

`toolResultCompressor.ts` մոդուլը տրամադրում է **5 մասնագիտացված սեղմման ռազմավարություն**
գործիքի արդյունքների համար (ֆունկցիայի կանչեր, գործակալի ելքեր, որոնման արդյունքներ և այլն).

1. **Որոնման արդյունքների սեղմում** — Հեռացնում է ավելորդ արդյունքները, պահպանում է լավագույն N-ը
2. **Ֆայլի ընթերցման սեղմում** — Կտրում է մեծ ֆայլերը, պահպանում է վերնագրերը/ներմուծումները
3. **Կոդի կատարման սեղմում** — Պահպանում է միայն էական stdout/stderr
4. **Տվյալների բազայի հարցման սեղմում** — Սահմանափակում է տողերը, հեռացնում է մանրամասն մետատվյալները
5. **API պատասխանի սեղմում** — Հեռացնում է null դաշտերը, խտացնում է զանգվածները

#### Երբ օգտագործել

Գործիքի արդյունքի սեղմումը **միշտ միացված է**, երբ գործիքի կանչեր կան։ Կարգավորում
անհրաժեշտ չէ։

### Շերտավորված խողովակաշար

Շերտավորված ռեժիմը գործարկում է **մի քանի շարժիչներ հաջորդաբար** — սովորաբար նախ RTK
(60-90% խնայողություն գործիքի ելքի վրա), այնուհետև Caveman (30% լրացուցիչ խնայողություն
մնացած տեքստի վրա)։ Սա հասնում է **78-95% ընդհանուր խնայողության**։

#### Ինչպես է աշխատում

```
Մուտք (1000 թոքեն)
  → RTK (հրաման-գիտակցող ֆիլտր) → 200 թոքեն
    → Caveman (լրացուցիչի հեռացում) → 140 թոքեն
  → Ելք (140 թոքեն, 86% խնայողություն)
```

#### Երբ օգտագործել

Օգտագործեք շերտավորված ռեժիմը հետևյալի համար.

- Գործիքներով հագեցած աշխատանքային հոսքեր (գործակալական կոդավորում, հետազոտություն)
- Ծախսերի նկատմամբ զգայուն խմբաքանակային մշակում
- Երբ անհրաժեշտ է թոքենների առավելագույն խնայողություն

Կարգավորել համակցված միջոցով.

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "modePack": "stacked"
    }
  }
}
```

## Կոմպրեսիայի համակցությունների վերասահմանումներ

Դուք կարող եք վերասահմանել կոմպրեսիայի գլոբալ ռեժիմը **յուրաքանչյուր համակցության համար առանձին**՝ տարբեր օգտագործման դեպքերի վարքագիծը ճշգրտելու նպատակով.

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "auto": {
      "weights": { "taskFit": 0.5 },
      "modePack": "quality-first"
    }
  },
  "compressionOverride": {
    "mode": "aggressive",
    "stackedPipelines": ["rtk", "caveman"],
    "preserveToolDefinitions": true
  }
}
```

Սա օգտակար է հետևյալ դեպքերում.

- **Կոդավորման համակցություններ**. Երկար աշխատաշրջանների համար օգտագործեք `aggressive` ռեժիմը
- **Արագ հարցուպատասխանի համակցություններ**. Արագ պատասխանների համար օգտագործեք `lite` ռեժիմը
- **Գործիքներով հագեցած համակցություններ**. Առավելագույն խնայողության համար օգտագործեք `stacked` ռեժիմը
- **Արտադրական համակցություններ**. Քեշավորում ապահովող մատակարարների համար օգտագործեք `cache-aware` ռեժիմը
