> Համապատասխան կոնտեքստի վրա ավտոմատ խնայեք 15-95%։ Արագ ակնարկի համար տե՛ս [README-ի սեղմման բաժինը](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically)։

## Ակնարկ

OmniRoute-ն իրականացնում է հուշումների սեղմման մոդուլային շղթա, որն աշխատում է **նախապես**՝ մինչև հարցումների՝ վերին մակարդակի մատակարարներին հասնելը։ Սա նշանակում է, որ թոքենների խնայողությունը կատարվում է թափանցիկ՝ առանց ձեր աշխատանքային գործընթացը փոխելու անհրաժեշտության։

```
Հաճախորդի հարցում
  → Սեղմման ռազմավարության ընտրիչ
    → Կոմբոյի վերասահմանո՞ւմ → Օգտագործել կոմբոյի կարգավորումը
    → Ավտոմատ գործարկման շե՞մ → Օգտագործել ավտոմատ ռեժիմը
    → Լռելյայն ռեժի՞մ → Օգտագործել գլոբալ կարգավորումը
    → Անջատվա՞ծ է → Բաց թողնել սեղմումը
  → Ընտրված սեղմման ռեժիմ
    → Անջատված․ առանց սեղմման
    → Թեթև․ բացատների/ձևաչափման անվտանգ մաքրում (~15%)
    → Ստանդարտ․ պարզունակ խոսքի ոճով ավելորդ բառերի հեռացում (~30%)
    → Ագրեսիվ․ պատմության հնեցում + ամփոփում (~50%)
    → Ուլտրա․ էվրիստիկ կրճատում + կոդային բլոկների նոսրացում (~75%)
    → RTK․ հրամանները հաշվի առնող տերմինալի/գործիքների ելքի զտում (վերին մակարդակում՝ 60-90% միջակայք)
    → Շերտավորված․ կարգավորված բազմաշարժիչ շղթա, սովորաբար RTK, ապա Caveman (համապատասխան կոնտեքստի 78-95% միջակայք)
  → Սեղմված հարցում → Մատակարար
```

## Սեղմման ռեժիմներ

### Անջատված

Սեղմում չի կիրառվում։ Բոլոր հաղորդագրությունները փոխանցվում են անփոփոխ։

### Թեթև ռեժիմ (~15% խնայողություն, <1ms ուշացում)

Ամենաանվտանգ ռեժիմը՝ իմաստային որևէ փոփոխություն չկա, կատարվում է միայն ձևաչափման մաքրում։

| Մեթոդ                    | Նկարագրություն                                          |
| ------------------------ | ------------------------------------------------------- |
| `collapseWhitespace`     | Միավորել հաջորդական դատարկ տողերը և վերջնային բացատները |
| `dedupSystemPrompt`      | Հեռացնել կրկնվող համակարգային հաղորդագրությունները      |
| `compressToolResults`    | Սեղմել ծավալուն գործիքի/ֆունկցիայի ելքերը               |
| `removeRedundantContent` | Հեռացնել կրկնվող հրահանգները                            |
| `replaceImageUrls`       | Կրճատել base64 պատկերների տվյալների URI-ները            |

**Լավագույնն է՝** մշտապես միացված օգտագործման և անվտանգության առումով կրիտիկական աշխատանքային գործընթացների համար։

### Ստանդարտ ռեժիմ (~30% խնայողություն)

Ոգեշնչված է [Caveman-ից](https://github.com/JuliusBrussee/caveman)՝ հեռացնում է ավելորդ բառերն ու երկարաբան ձևակերպումները՝ պահպանելով իմաստը։

- Հեռացնում է ավելորդ բառերը («խնդրում եմ», «կարծում եմ», «հիմնականում», «իրականում»)
- Խտացնում է երկարաբան արտահայտությունները («որպեսզի» → «համար», «արդյունքում» → «քանի որ»)
- Հեռացնում է չափազանց քաղաքավարի մեղմացումները («Դեմ չէի՞ք լինի...», «Եթե հնարավոր լիներ...»)
- Ներառում է ծրագրավորման հուշումների համար հարմարեցված 30+ կանոնավոր արտահայտության կանոն

**Լավագույնն է՝** ամենօրյա ծրագրավորման աշխատանքային գործընթացների և ծախսերին ուշադիր թիմերի համար։

### Ագրեսիվ ռեժիմ (~50% խնայողություն)

Պատմության խելացի կառավարում երկարատև աշխատաշրջանների համար։

- **Հաղորդագրությունների հնեցում** — ավելի հին հաղորդագրություններն աստիճանաբար ավելի շատ են սեղմվում
- **Գործիքի արդյունքների սեղմում** — երկար գործիքային ելքերը հատվում կամ բաց են թողնվում (առաջին/վերջին տողեր,
  համընկնող տողերի զտում, JSON բանալիների խտացում)
- **Կառուցվածքային ամբողջականության պաշտպանիչ մեխանիզմներ** — ապահովում են `tool_use` + `tool_result` զույգերի համապատասխանությունը
- **Կոնտեքստային պատուհանի հաշվառում** — պահպանում է յուրաքանչյուր մոդելի թոքենների սահմանաչափերը

**Լավագույնն է՝** երկարատև վրիպազերծման աշխատաշրջանների և մեծ կոդային բազաների համար։

### Ուլտրա ռեժիմ (~75% խնայողություն)

Առավելագույն սեղմում թոքենների առումով կրիտիկական սցենարների համար։

- **Էվրիստիկ կրճատում** — արձակի՝ գնահատականների վրա հիմնված թոքենային կրճատում
- **Կառուցվածքի պահպանում** — սահմանազատված կոդային բլոկները, ներկառուցված կոդը, URL-ները և նույնացուցիչները
  ժամանակավորապես փոխարինվում են նշիչներով և այնուհետև բառացիորեն վերականգնվում՝ առանց կրճատման
- **Ընտրովի SLM մակարդակ** — կազմաձևման դեպքում փոքր տեղային մոդելը կարող է ճշգրտել կրճատումը
- Անկախ է Ագրեսիվ ռեժիմից․ այն չի կիրառում հաղորդագրությունների հնեցում, գործիքի արդյունքների սեղմում
  կամ պահուստային ամփոփիչ (միայն SLM մակարդակի խափանման դեպքում պահուստային անցումը կարող է ուղղվել
  ագրեսիվ ռեժիմով)

**Լավագույնն է՝** երբ պարբերաբար հասնում եք կոնտեքստի սահմանաչափերին։

### RTK ռեժիմ (վերին մակարդակում՝ 60-90% միջակայք)

RTK ռեժիմը օպտիմալացված է ծրագրավորման գործակալների աշխատաշրջաններում հանդիպող ծավալուն գործիքային ելքերի համար։

- Հայտնաբերում է հրամանների/ելքերի դասեր, օրինակ՝ `git status`, `git diff`, `git log`, թեստային գործարկիչներ,
  TypeScript/Vite/Webpack կառուցումներ, ESLint/Biome/Prettier, npm աուդիտներ/տեղադրումներ, Docker մատյաններ, ենթակառուցվածքային
  ելք և ընդհանուր shell ելք
- Կիրառում է `open-sse/services/compression/engines/rtk/filters/`-ի JSON զտիչների փաթեթները
- Ներմուծում է RTK TOML schema v1 զտիչները նախագծի կամ գլոբալ `filters.toml` ֆայլերից՝ ներկառուցված թեստերի
  վավերացմամբ և նախագծային ֆայլերի վստահության ստուգմամբ
- Ներառում է 55 ներկառուցված զտիչ՝ ներկառուցված ստուգման օրինակներով
- Հեռացնում է ANSI կառավարման հաջորդականությունները, առաջընթացի գոտիները, կրկնվող տողերը և ոչ օգտակար աղմուկը
- Պահպանում է խափանումները, սխալները, նախազգուշացումները, փոփոխված ֆայլերը, ամփոփումները և երկար ելքի վերջնամասը
- Աջակցում է վստահության ստուգմամբ նախագծային զտիչներին, գլոբալ զտիչներին և, ըստ ցանկության, խմբագրված չմշակված ելքի վերականգնմանը

**Լավագույնն է՝** shell, կառուցման, թեստավորման, git, grep և ֆայլային ելքերի արձանագրություններ պարունակող գործակալային աշխատաշրջանների համար։

### Շերտավորված ռեժիմ (համապատասխան կոնտեքստի 78-95% միջակայք)

Շերտավորված ռեժիմը սեղմման մի քանի շարժիչներ գործարկում է որոշակիացված հերթականությամբ։ Լռելյայն շղթան հետևյալն է։

```txt
RTK -> Caveman
```

Այս հերթականությունը նախ խտացնում է տերմինալի/գործիքի ելքը, այնուհետև կիրառում է Caveman-ի իմաստային խտացումը
մնացած բնական լեզվով հուշման նկատմամբ։ Շերտավորված շղթաները կարող են կազմաձևվել գլոբալ կերպով կամ
ուղղորդման կոմբոներին վերագրված սեղմման կոմբոների միջոցով։

**Լավագույնն է՝** մեծ գործիքային մատյաններ և մարդկային հրահանգներ կամ օգնականի ամփոփումներ պարունակող խառը կոնտեքստի համար։

## Սկզբնաղբյուր նախագծերի խնայողությունների հաշվարկը

OmniRoute-ը ներկայացնում է սեղմման խնայողությունները՝ հիմնվելով երկու աղբյուրի վրա՝ սկզբնաղբյուր նախագծերի չափորոշիչների և
OmniRoute-ի սեփական շարժիչների համադրման։

| Աղբյուր | Այստեղ օգտագործված՝ սկզբնաղբյուր README-ի ցուցանիշը                                                                                |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%`-ով պակաս ելքային թոքեններ, չափորոշիչներում ելքի միջին `65%` խնայողություն, `22-87%` միջակայք և մուտքի `~46%` սեղմման գործիք |
| RTK     | Հրամանների ելքի `60-90%` խնայողություն․ օրինակելի աշխատաշրջանում՝ `~118,000 -> ~23,900` թոքեն, կամ `79.7%` խնայողություն (`~80%`)  |

Գործիքների/համատեքստի համընկնող բովանդակության դեպքում OmniRoute-ի լռելյայն համակցությունը շարժիչները կիրառում է հաջորդաբար․

```txt
RTK -> Caveman
```

Համակցված խնայողությունները բազմապատկվում են, ոչ թե գումարվում․

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

Այդ `78-95%` ցուցանիշը կիրառելի է, երբ և՛ RTK-ն, և՛ Caveman-ը կարող են կրճատել նույն մուտքային/համատեքստային բովանդակությունը։
Caveman-ի պատասխանների ելքային ռեժիմն առանձին է․ երբ այն միացված է, օգտագործեք Caveman-ի ելքային խնայողության սեփական ցուցանիշները (`65%`
միջին, `~75%` հիմնական ցուցանիշ, `22-87%` միջակայք)։ Վճարումների ընդհանուր խնայողությունը կախված է ձեր հուշումների և ելքերի հարաբերակցությունից։

### Ինչ է իրականում նշանակում «կիրառելի»

Հիմնական 15-95% միջակայքն իրական է, սակայն այն կիրառելի է միայն **կրկնվող կամ չափազանց ծավալուն** բովանդակության համար՝ կրկնվող
սխալի տողեր, նույն նախազգուշացումը շարունակաբար արտածող կառուցման մատյան կամ չափազանց մեծ `grep`/ֆայլի ընթերցման արտածում։ Դա
**չի** նշանակում, որ յուրաքանչյուր հարցում այդքան խնայողություն է ապահովում։

Փորձնականորեն հաստատված է (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`)․ Anthropic-ի ձևաչափով `tool_result` բլոկի նկատմամբ,
որը պարունակում էր սխալի 300 նույնական տող, `stacked` (RTK + Caveman) գործարկումն ապահովել է **թոքենների 95.93% խնայողություն / նիշերի 96.26% խնայողություն**՝ լիովին
տեղավորվելով հայտարարված միջակայքում։ Սակայն նույն մշակաշարը սովորական, չկրկնվող գործիքային ելքի նկատմամբ գործարկելիս (`grep`-ի համընկնումների մաքուր ցանկ,
ֆայլի կարճ ընթերցում, սովորական զրույցի տեքստ) ճիշտ կերպով ապահովում է **գրեթե զրոյական խնայողություն**, քանի որ
հեռացնելու ենթակա կրկնվող բովանդակություն չկա, իսկ `validateCompression()`-ը (`validation.ts`) հրաժարվում է տրամադրել այնպիսի
վերաշարադրում, որը կհեռացներ կամ կփոխեր կոդի բլոկները, URL-ները, վերնագրերը, տարբերակները կամ ԱՄԲՈՂՋՈՎԻՆ ՄԵԾԱՏԱՌ հաստատունների նույնացուցիչները։

Սա ակնկալվող և անվտանգ վարքագիծ է, ոչ թե սխալ․ ծրագրավորման աշխատաշրջանը, որը հիմնականում մաքուր ֆայլեր է ընթերցում կամ դրանցում որոնում կատարում,
կունենա ընդհանուր համեստ խնայողություն՝ նույնիսկ լիովին միացված սեղմման դեպքում, մինչդեռ խափանվող
ցիկլի կամ չափազանց շատ հաղորդագրություններ արտածող linter-ի հանդիպած աշխատաշրջանն այդ տվյալների հոսքի համար կապահովի ամբողջ 78-95% միջակայքը։ Մի օգտագործեք առանձին աշխատաշրջանի
ընդհանուր խնայողության ցածր տոկոսը որպես ապացույց, որ սեղմումը սխալ է կազմաձևված․ նախ ստուգեք՝ արդյոք
գործիքի սկզբնական ելքն իրականում կրկնվող էր։

## Կազմաձևում

### Կառավարման վահանակ

Անցեք `Կառավարման վահանակ → Համատեքստ և քեշ` բաժին՝

- **Caveman** — ռեժիմի ընտրություն, լեզվական փաթեթներ, նախադիտում և գլոբալ լռելյայն կարգավորումներ
- **RTK** — հրամանների զտման նախադիտում, RTK-ի անվտանգության կարգավորումներ և զտիչների կատալոգ
- **Սեղմման համակցություններ** — անվանված շարժիչային շղթաներ, որոնք վերագրված են երթուղավորման համակցություններին
- **Ավտոմատ գործարկման շեմ** — ավտոմատ կերպով միացնել սեղմումը, երբ թոքենների քանակը գերազանցում է շեմը

### Յուրաքանչյուր համակցման համար վերագրում

`Կառավարման վահանակ → Համատեքստ և քեշ → Սեղմման համակցություններ` բաժնում սեղմման համակցություն վերագրեք երթուղավորման
համակցությանը՝

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

Սա թույլ է տալիս անվճար/ծրագրավորման մատակարարների դեպքում օգտագործել շղթայված սեղմում՝ վճարովի
բաժանորդագրությունների համար պահպանելով թեթև ռեժիմը։

Այս «Յուրաքանչյուր համակցման համար վերագրում» կարգավորումը տարբերվում է **երթուղավորման համակցման սեղմման
ռեժիմի** վերագրումից (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — դաշտի
սխեման նաև ընդունում է `rtk`, `stacked` և `omniglyph`)․ այդ վերագրումը չի ընտրում անվանված
սեղմման համակցման շղթա, այլ պարզապես սահմանում է `compressionMode` դաշտը, որն օգտագործվում է
`resolveCompressionPlan`-ի կողմից։ Այն կարելի է սահմանել կա՛մ համակցման քարտում (`Կառավարման վահանակ → Համակցություններ`), կա՛մ, սկսած
#6760-ից, յուրաքանչյուր երթուղավորման համակցման համար՝ «Վերագրել երթուղավորմանը» ցանկում՝
`Կառավարման վահանակ → Համատեքստ և քեշ → Սեղմման համակցություններ` բաժնում՝ անմիջապես վերևում նկարագրված շղթայի վերագրման նշատուփի
կողքին։ Երկու միջերեսների փոփոխություններն էլ պահպանվում են նույն `PUT /api/combos/{id}` վերջնակետի միջոցով։

### Յուրաքանչյուր հարցման համար վերագրում

Ուղարկեք `x-omniroute-compression` հարցման վերնագիրը՝ մեկ հարցման համար սեղմման պլանը վերագրելու նպատակով։
Այն ունի ամենաբարձր առաջնահերթությունը՝ գերակայում է երթուղավորման համակցման վերագրմանը, ակտիվ պրոֆիլին,
ավտոմատ գործարկմանը և վահանակի Default կարգավորմանը։ Անհայտ արժեքներն անտեսվում են (հարցումը երբեք չի մերժվում), իսկ
գլոբալ գլխավոր անջատիչը շարունակում է վերահսկել ամեն ինչ․ երբ սեղմումը գլոբալ կերպով անջատված է, վերնագիրը չի կարող
այն միացնել։ Արժեքներն են՝

| Արժեք         | Արդյունք                                                                                                                 |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `off`         | Այս հարցման համար սեղմում չի կիրառվում։                                                                                  |
| `default`     | Վահանակից ստացված Default պրոֆիլը (անտեսում է ակտիվ պրոֆիլը)։ Կորուստներով աշխատող շարժիչները մնում են անջատված։         |
| `safe`        | Նույնն է, ինչ վերնագիրը բաց թողնելը՝ միայն կրկնօրինակների հեռացում և բացատների միավորում։                                |
| `allow-lossy` | Պահպանում է այս հարցման օպերատորի պլանը՝ ներառյալ ամփոփումները, համապատասխանության զտիչները և ոճի վերաշարադրումները։     |
| `engine:<id>` | Մեկ շարժիչ, եթե այն միացված է, օրինակ՝ `engine:rtk`։ Սա տվյալ շարժիչը յուրաքանչյուր հարցման համար միացնելու տարբերակն է։ |
| `<combo>`     | Անվանված համակցություն, որը նախ համընկեցվում է ըստ անվան՝ առանց տառաչափը հաշվի առնելու, ապա՝ ըստ id-ի։                   |

Առանց `allow-lossy`, `engine:<id>` կամ անվանված համակցման՝ կորուստներով աշխատող շարժիչները չեն կիրառվում։
Եթե սեղմումը միացված է, հարցման համար միևնույն է կիրառվում են աշխատաշրջանի կրկնօրինակների հեռացումը և բացատների միավորումը։

Կիրառված պլանը վերադարձվում է նաև `X-OmniRoute-Compression: <mode>; source=<source>` պատասխանի
վերնագրում, որտեղ `<source>`-ը հետևյալներից մեկն է՝ `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default` կամ `off`։

### API

```bash
# Ստանալ սեղմման կարգավորումները
curl http://localhost:20128/api/settings/compression

# Թարմացնել սեղմման կարգավորումները
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# Նախադիտել որոշակի RTK/stacked օգտակար բեռ
curl -X POST http://localhost:20128/api/compression/preview \
  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# Ցուցադրել RTK զտիչների փաթեթները
curl http://localhost:20128/api/context/rtk/filters

# Անմիջապես փորձարկել RTK-ն՝ հրամանի ոչ պարտադիր մետատվյալներով
curl -X POST http://localhost:20128/api/context/rtk/test \
  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

## Սեղմման առաջադեմ համակարգեր

Վերը նկարագրված 7 ռեժիմներից բացի (սկզբնաղբյուրը նաև ընդունում է `codex-responses` և
`omniglyph` ռեժիմները, որոնք այս ուղեցույցում չեն ներկայացվում), ստորև բերված բաժիններն ընդգրկում են գործառույթներ,
որոնք աշխատում են այդ ռեժիմների ներսում կամ դրանց զուգահեռ։ Գործիքի արդյունքի սեղմումը և պրոգրեսիվ հնացումը
ագրեսիվ շարժիչի 1-ին և 2-րդ քայլերն են (Aggressive ռեժիմում և շարված խողովակաշարի
`aggressive` քայլում), շարված խողովակաշարն այն եղանակն է, որով աշխատում է Stacked ռեժիմը, քեշը հաշվի առնող սեղմումը
քեշավորում իրականացնող մատակարարների համար `aggressive` և `ultra` ռեժիմներն իջեցնում է մինչև `standard`, քանի դեռ սեղմումը
միացված է, իսկ Caveman ելքի ռեժիմը և ելքի ոճերը ըստ ցանկության միացվող համակարգային հուշման հրահանգներ են,
որոնք լռելյայն անջատված են և հարցումը սեղմելու փոխարեն ձևավորում են մոդելի ելքը։

### Քեշը հաշվի առնող սեղմում

Որոշ մատակարարներ (օրինակ՝ Anthropic-ը՝ հուշումների քեշավորմամբ) աջակցում են **հուշումների քեշավորմանը**,
ինչը նրանց թույլ է տալիս քեշավորել հուշման մասերը՝ ծախսերն ու ուշացումը նվազեցնելու համար։ Երբ
քեշավորումը միացված է, ագրեսիվ սեղմումն իրականում կարող է **վատթարացնել** արդյունավետությունը,
քանի որ այն փոխում է քեշավորված թոքենները՝ անվավեր դարձնելով քեշը։

`cachingAware.ts` մոդուլը լուծում է այս խնդիրը՝ **հայտնաբերելով քեշավորման համատեքստը** և
համապատասխանաբար **կարգավորելով սեղմման ռազմավարությունը**։

#### Ինչպես է այն աշխատում

1. **Հայտնաբերել քեշավորման համատեքստը** — Հարցման մարմնում որոնում է `cache_control` նշիչներ
2. **Որոշել քեշավորում իրականացնող մատակարարներին** — Ստուգում է՝ արդյոք նպատակային մատակարարն աջակցում է քեշավորմանը
3. **Կարգավորել ռազմավարությունը** — Քեշավորում իրականացնող մատակարարների համար `aggressive`/`ultra`-ն իջեցնում է մինչև `standard`
4. **Բաց թողնել համակարգային հուշումը** — Համակարգային հուշումները սովորաբար քեշավորվում են, ուստի դրանք պետք չէ սեղմել

Ռազմավարության օժանդակ ֆունկցիան նաև վերադարձնում է `deterministicOnly` դրոշակը, սակայն պլանի կառուցիչն օգտագործում է
միայն ռազմավարությունը. ներկայում ներքևի հոսքի ոչ մի բաղադրիչ չի կարդում այդ դրոշակը։

#### Կոդի օրինակ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Քեշի նշիչ
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### Երբ օգտագործել

Քեշը հաշվի առնող սեղմումը **միշտ միացված է**. որևէ կազմաձևում անհրաժեշտ չէ։ Այն գործարկվում է ամեն անգամ,
երբ սեղմումը միացված է, և նպատակային մատակարարն աջակցում է հուշումների քեշավորմանը (Anthropic, OpenAI
և այլն)։ Բացահայտ `cache_control` նշիչները պարտադիր չեն. միայն քեշավորում իրականացնող մատակարարի առկայությունն
արդեն իսկ գործարկում է մակարդակի իջեցումը, իսկ միայն նշիչները երբեք դա չեն անում (նշիչների հայտնաբերումն օգտագործվում է քեշի
հեռաչափության, այլ ոչ թե ռազմավարության որոշման համար)։

### Պրոգրեսիվ հնացում

Երկար զրույցներում կուտակվում են հաղորդագրությունների բազմաթիվ հերթափոխեր, սակայն ավելի հին հերթափոխերը դառնում են պակաս
արդիական։ `progressiveAging.ts` մոդուլը **նվազեցնում է հաղորդագրությունների մանրամասնությունը՝ ըստ հերթափոխի հեռավորության**
(հեռավորությունը չափվում է զրույցի ավարտից)։ Թողարկված լռելյայն արժեքներով
(`verbatim: 2, light: 2, moderate: 3`)՝

- **Վերջին 2 հերթափոխերը (հեռավորություն ≤ 2)**․ Պահվում են բառացի
- **Հեռավորություն 3**․ Քարանձավային սեղմում (լցոնիչ բառերի հեռացում)
- **Հեռավորություն 4+**․ Օգնականի հաղորդագրություններն ամփոփվում են, օգտատիրոջ հաղորդագրությունները կրճատվում են մինչև իրենց առաջին
  տողը՝ առավելագույնը 120 նիշով, իսկ մյուս դերերը մնում են անփոփոխ։ Համակարգային հուշումները, արդեն հնեցված
  հաղորդագրությունները և օգտատիրոջ վերջին հաղորդագրությունը միշտ պահվում են բառացի՝ անկախ հեռավորությունից։
  Ոչինչ ամբողջությամբ չի հեռացվում, իսկ `light`
  միջակայքն անհասանելի է մատակարարվող լռելյայն կարգավորումներով (`light`-ը հավասար է `verbatim`-ին)։

#### Կոդի օրինակ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... ևս 50 հերթափոխ ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // վերջին 3 հերթափոխերը՝ բառացի
  light: 8, // հեռավորություն <= 8՝ թեթև սեղմում
  moderate: 20, // հեռավորություն <= 20՝ քարանձավային սեղմում
  fullSummary: 5, // պահանջվում է տեսակի կողմից, սակայն չի կարդացվում միջակայքերի բաժանման կոդով
  // հեռավորություն > 20՝ ամփոփվում է (օգնական) / պահվում է առաջին տողը (օգտատեր)
});

// saved = խնայված թոքենների քանակը
```

#### Երբ օգտագործել

Պրոգրեսիվ հնեցումը **միշտ միացված է** `aggressive` ռեժիմում․ այն
`compressAggressive()`-ի 2-րդ քայլն է։ Ultra ռեժիմը այն չի գործարկում։ Այն
հատկապես արդյունավետ է հետևյալի համար․

- Երկարատև կոդավորման աշխատաշրջաններ
- Մի քանի օր տևող զրույցներ
- Բազմաթիվ գործիքների կանչերով գործակալային աշխատանքային հոսքեր

### Քարանձավային ելքի ռեժիմ

Քարանձավային ելքի ռեժիմն ավելացնում է **համակարգային հուշման հրահանգներ**, որոնք մոդելին խնդրում են
հակիրճ ելք տալ․ `lite` մակարդակը խնդրում է տալ հակիրճ պատասխաններ՝ պահպանելով ամբողջական նախադասությունները, `full`
մակարդակը խնդրում է «պատասխանել հակիրճ՝ խելացի քարանձավաբնակ մարդու պես», իսկ `ultra` մակարդակը՝ հեռագրային ելք տալ։
Հրահանգները միայն խնդրում են և չեն կարող դա երաշխավորել։ Հարցումները դրանք ստանում են
`applyOutputStyles()`-ի միջոցով (`open-sse/services/compression/outputStyles/apply.ts`)․
`open-sse/handlers/chatCore.ts`-ը նախ որոշում է ընտրությունը հետադարձ համատեղելիության միջանկյալ շերտի միջոցով
(`resolveOutputStyleSelection()`՝
`open-sse/services/compression/outputStyles/backCompat.ts`-ում), որը, քանի դեռ `outputStyles`-ը
դատարկ է, միացված `cavemanOutputMode`-ը համապատասխանեցնում է `terse-prose` ելքի ոճին՝
`cavemanOutputMode.intensity` ինտենսիվությամբ (տե՛ս ստորև՝ Հետադարձ համատեղելիություն)։ Ոչ դատարկ `outputStyles`
ընտրությունն օգտագործվում է անփոփոխ, և այդ դեպքում `cavemanOutputMode.enabled`-ն ու `intensity`-ն
ազդեցություն չունեն, մինչդեռ դրա `autoClarity` փոխարկիչը շարունակում է կիրառվել։ `outputMode.ts`-ը պարունակում է
հրահանգների տեքստերը (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), բովանդակության շրջանցումն ու
տեղադրման օժանդակ գործառույթը, որն օգտագործվում է ներարկման ժամանակ։ Դրա սեփական `applyCavemanOutputMode()` ներարկիչը
արտադրական միջավայրում կանչող չունի։

#### Ինչպես է այն աշխատում

Այս ռեժիմը չի սեղմում մուտքային տվյալները։ Այն համակարգային հուշմանը հրահանգների բլոկ է ավելացնում
(տե՛ս ստորև՝ Ինչպես է աշխատում ներարկումը), իսկ հարցման համար ընտրված մուտքային տվյալների սեղմման ցանկացած ռեժիմ
դրանից հետո շարունակում է գործել այն մարմնի վրա, որն արդեն պարունակում է այդ բլոկը։ Ընդհանուր
սահմանափակումների դրույթից առաջ, որով ավարտվում է յուրաքանչյուր մակարդակ, անգլերեն `full` մակարդակում գրված է․

> «Պատասխանիր հակիրճ՝ խելացի քարանձավաբնակ մարդու պես։ Բաց թող հոդերը (a/an/the), լցոնիչ բառերը (just/really/basically/actually/simply), քաղաքավարության արտահայտությունները և անվստահություն արտահայտող ձևակերպումները։ Հատվածները ընդունելի են։ Օգտագործիր կարճ հոմանիշներ (big, ոչ թե extensive, fix, ոչ թե implement)։ Ամբողջ տեխնիկական բովանդակությունը, կոդը, սխալները, URL-ները և նույնացուցիչները պահիր ճշգրիտ»։

Սա հատկապես լավ է աշխատում հետևյալի համար․

- Կոդի ստեղծում (ավելի հակիրճ ելք = ավելի քիչ թոքեններ)
- Արագ հարցուպատասխան (մանրամասն բացատրությունների կարիք չկա)
- Փաթեթային մշակում (առավելագույն թողունակություն)

#### Երբ օգտագործել

Քարանձավային ելքի ռեժիմը **ըստ ցանկության է միացվում**։ Երբ սեղմումը միացված է (`enabled: true`՝ Compression Settings էջի
գլխավոր փոխարկիչը), միացրեք այն `cavemanOutputMode.enabled`-ի միջոցով։ `intensity`-ն
ընտրում է `lite`, `full` կամ `ultra`․

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

Սեղմման համադրության **Ելքի ռեժիմ** փոխարկիչը (`outputMode`, իսկ մակարդակը՝ `outputModeIntensity`-ում)
նույն փոխարկիչն է սահմանում այն հարցումների համար, որոնց վրա կիրառվում է այդ համադրությունը, իսկ
`omniroute_set_compression_engine` MCP գործիքը այն գրանցում է իր բուլյան `outputMode`
արգումենտի միջոցով։ Ոչ դատարկ `outputStyles` ընտրությունը գերակայում է այս փոխարկիչի նկատմամբ։ Կառավարման
վահանակում **Հակիրճ արձակ** ելքի ոճի միացումը ներարկում է նույն բլոկը (տե՛ս ստորև՝ Ելքի ոճեր)։

### Ելքի ոճեր (կատալոգ)

Վերևում նկարագրված քարանձավային ելքի ռեժիմը **մեկ ոճով աշխատող հին ուղին** է։ 4-րդ փուլում այն
ընդհանրացվել է՝ դառնալով համատեղելի ելքի ոճերի կատալոգ՝ `OUTPUT_STYLE_CATALOG`-ը
`open-sse/services/compression/outputStyles/catalog.ts`-ում։ Յուրաքանչյուր ոճ համակարգային հուշման

Յուրաքանչյուր ոճ տրամադրվում է ինտենսիվության երեք մակարդակով՝ `lite`, `full`, `ultra`, և յուրաքանչյուր մակարդակ
ավարտվում է ընդհանուր սահմանների դրույթով (`SHARED_BOUNDARIES`՝ `outputMode.ts`-ում), որը
կոդի բլոկները, ֆայլերի ուղիները, հրամանները, սխալները և URL-ները պահպանում է ճշգրիտ։ `terse-prose` և
`terse-cjk` մակարդակների տեքստերն այդ ցանկում ավելացնում են նաև նույնացուցիչները։

`terse-cjk`-ն երկու տեղում սահմանափակված է ըստ locale-ի՝ միայն `zh`-ի համար։ Սեղմման կարգավորումների էջը
դրա տողը ցուցադրում է միայն այն ժամանակ, երբ կառավարման վահանակի միջերեսի լեզուն չինարեն է (`zh-CN` կամ `zh-TW`), իսկ
`applyOutputStyles()`-ն այն ներառում է միայն այն դեպքում, երբ հարցման որոշված լեզուն (տե՛ս ստորև՝ Լեզվի
ընտրություն) `zh` է։ Տողը թաքցնելը չի մաքրում պահպանված `terse-cjk` ընտրությունը․
կարգավորումների API-ն ընդունում է ոճի ցանկացած id, իսկ էջում այլ ոճերի պահպանումը պահպանում է այն։ Հարցման
մշակման պահին `applyOutputStyles()`-ի լեզվի ստուգումը locale-ի միակ սահմանափակումն է։

#### Ինչպես է կատարվում ներառումը

`applyOutputStyles()`-ը (`open-sse/services/compression/outputStyles/apply.ts`) ընտրությունը համադրում է
կատալոգի հետ (անհայտ id-ները և locale-ին չհամապատասխանող ոճերը
դուրս են թողնվում և երբեք սխալ չեն առաջացնում․ եթե ընտրությունից որևէ ոճ չի որոշվում, մարմինը
մնում է անփոփոխ՝ բաց թողնվելով որպես `no_styles`), ընտրված հրահանգները միավորում է կատալոգի
հերթականությամբ,
սահմանների դրույթը վերջում ավելացնում է **մեկ անգամ** (ինչպես նաև անվտանգության դրույթը՝ `SAFETY_BOUNDARIES`-ը կամ դրա
թարգմանությունը, երբ ընտրված է `less-code` կամ `ponytail`) և բլոկը սկսում է
իդեմպոտենտության մեկ նշիչով (`[OmniRoute Output Styles]`), ուստի կրկնակի կիրառումը ոչինչ չի փոխում։ Երբ
որոշված լեզվի համար (տե՛ս ստորև՝ Լեզվի ընտրություն) թարգմանություն կա, անգլերենի փոխարեն ներառվում է
տեղայնացված հրահանգը։

Ոչ դատարկ `messages` զանգված ունեցող մարմնի դեպքում իդեմպոտենտության ստուգումը կատարվում է բովանդակության
շրջանցումից առաջ․ երբ `[OmniRoute Output Styles]` նշիչն արդեն առկա է վերին մակարդակի
`system` դաշտում (տող կամ բովանդակության բլոկների զանգված) կամ տողային
բովանդակությամբ համակարգային հաղորդագրության մեջ, մարմինը մնում է անփոփոխ՝ որպես `already_applied`, և հիմնաբառերի ստուգում չի կատարվում։
Հակառակ դեպքում բովանդակության շրջանցումը (`shouldBypassCavemanOutputMode()`՝
`open-sse/services/compression/outputMode.ts`-ում) ստուգում է վերջին երեք
հաղորդագրությունների տեքստը՝ անկախ դրանց դերից, և ամբողջ ընթացիկ քայլի համար բաց է թողնում ոճերը, երբ այդ տեքստը
համընկնում է անվտանգության, անդառնալի գործողության կամ պարզաբանում պահանջող հիմնաբառերին, կամ
հերթականությունից կախված շղթային՝ `first`, `then`, `after that`, `before`, `rollback` կամ
`backup`, որին 240 նիշի սահմաններում հաջորդում է `delete`, `drop`, `migrate`, `deploy` կամ
`release`։ Շրջանցումը գործում է, քանի դեռ **Auto-Clarity Bypass** փոխարկիչը
(`cavemanOutputMode.autoClarity`, լռելյայն միացված) միացված է․ փոխարկիչն անջատելը բաց է թողնում
հիմնաբառերի ստուգումը։

Երբ շրջանցումը թույլ է տալիս մշակել ընթացիկ քայլը, `placeSystemInstruction()`-ը (նույն ֆայլում), որը
երբեք նոր `messages[0]` չի ստեղծում, բլոկը տեղադրում է իր գտած հետևյալ տարբերակներից առաջինում․

1. Սկզբում գտնվող՝ տողային բովանդակությամբ համակարգային հաղորդագրություն․ բլոկը կցվում է դրա տեքստից հետո։
2. Վերին մակարդակի `system` դաշտը․ բլոկը կցվում է տողի տեքստից հետո կամ
   ավելացվում է որպես նոր տեքստային բլոկ՝ բովանդակության բլոկների զանգվածում։
3. Հետագայում հանդիպող առաջին՝ տողային բովանդակությամբ համակարգային հաղորդագրություն․ բլոկը կցվում է դրա
   տեքստից հետո։
4. Վերը նշվածներից ոչ մեկը․ բլոկը տեղադրվում է `messages`-ի վերջում ավելացված նոր համակարգային հաղորդագրության մեջ։

`messages` զանգված չունեցող (կամ դատարկ զանգված ունեցող) մարմնի դեպքում բովանդակության շրջանցում չի կատարվում, և
վերին մակարդակի `system` դաշտը չի ստուգվում։ Բլոկը կցվում է տողային `instructions` դաշտի
տեքստից հետո, եթե այդ դաշտն արդեն չի պարունակում
`[OmniRoute Output Styles]` նշիչը, որի դեպքում մարմինը մնում է անփոփոխ՝ որպես
`already_applied`։ Երբ մարմինը չունի տողային `instructions` դաշտ, բայց պարունակում է `input`
(տող կամ զանգված), բլոկը դառնում է `instructions`՝ փոխարինելով այդ դաշտի նախկին ոչ տողային արժեքը։
Մարմինը, որը չունի ո՛չ տողային `instructions` դաշտ, ո՛չ էլ տողային կամ զանգվածային
`input`, մնում է անփոփոխ և բաց է թողնվում որպես `no_messages`։

#### Ինչպես միացնել

Վահանակում՝ **Compression Context → Compression Settings**
(`/dashboard/context/settings`), Output styles բաժնում յուրաքանչյուր ոճի համար կա մեկ տող՝
միացման/անջատման փոխարկիչով և մակարդակի ընտրիչով։ Ոճերը ներարկվում են, երբ սեղմումն ինքնին
միացված է (էջի գլխավոր փոխարկիչը՝ `enabled`)։ **Auto-Clarity Bypass** փոխարկիչը գտնվում է
**Caveman** էջում (`/dashboard/context/caveman`)՝ դրա **Output Mode** քարտում։ Ծրագրային
մակարդակում սեղմման կազմաձևը պահպանում է ընտրությունն այսպես․

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

Հետադարձ համատեղելիություն․ քանի դեռ `outputStyles`-ը դատարկ է, հին
`cavemanOutputMode.enabled` կարգավորումը համապատասխանեցվում է `terse-prose`-ին՝
`cavemanOutputMode.intensity` ինտենսիվությամբ։ Այնուհետև բլոկը սկսվում է
`[OmniRoute Output Styles]` նշիչով, մինչդեռ հին `applyCavemanOutputMode()`
ներարկիչը գրում էր `[OmniRoute Caveman Output Mode]`։ Նշիչից ներքև տեքստը
համընկնում է հին ներարկման հետ en, pt-BR, es, de, fr, it, ru, id և vi լեզուներում,
իսկ ja և zh լեզուներում սահմանների դրույթից առաջ կա մեկ լրացուցիչ բացատ։
`terse-prose`-ը թարգմանված է pt-BR, es, de, fr, it, ru, zh, ja, id և vi լեզուներով,
ուստի այն հարցումը, որի որոշված լեզուն `hu` է, ստանում է անգլերեն տեքստը, մինչդեռ հին
ներարկիչն օգտագործում էր դրա հունգարերեն տարբերակը։

Ելքային ոճի լեզվի ընտրությունը (`resolveOutputStyleLanguage()`՝
`outputStyles/apply.ts`-ում)․ երբ `languageConfig.enabled`-ը միացված է, `autoDetect`-ը
հարցման `messages` զանգվածից ընտրում է տեքստ պարունակող ամենավերջին օգտատիրոջ
հաղորդագրությունը (տողային բովանդակությունը կամ դրա բովանդակության մասերի `text`-ը) և
դրա վրա գործարկում Caveman շարժիչի հայտնաբերիչը (`detectCompressionLanguage()`)։
Հայտնաբերիչը վերադարձնում է `zh`, եթե տեքստը պարունակում է Han նիշեր և չի պարունակում
kana, հակառակ դեպքում վերադարձնում է `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`,
`hu` և `id` լեզուներից այն մեկը, որն ունի հուշումների ամենաշատ համընկնումները, իսկ երբ
համընկնում չկա՝ `en`․ տեքստը, որը հնարավոր չէ դասակարգել, ստանում է անգլերեն, երբեք՝
`defaultLanguage`, իսկ `vi`-ն երբեք չի հայտնաբերվում, թեև ոճերը ներառում են `vi`
տեքստ։ Responses API-ի մարմինը պահում է իր հերթերը `input`-ում, որը նմուշառման չի
ենթարկվում, ուստի այն ստանում է `defaultLanguage`, ապա՝ անգլերեն։ Երբ `messages`-ում
օգտատիրոջ ոչ մի հաղորդագրություն տեքստ չի պարունակում, կամ երբ `autoDetect`-ն անջատված
է, կիրառվում է `defaultLanguage`, ապա՝ անգլերեն։ Երբ `languageConfig.enabled`-ն
անջատված է, լեզուն անգլերենն է, եթե միայն հարցման նկատմամբ չի կիրառվում սեղմման
կոմբինացիա (հարցման երթուղավորման կոմբինացիային նշանակված կոմբինացիա կամ սեղմման
լռելյայն կոմբինացիան, որին chatCore-ը հետադարձորեն անցնում է ներկառուցված շերտավորված
խողովակաշարի համար)․ կոմբինացիայի կիրառումը տվյալ հարցման համար միացնում է
`languageConfig.enabled`-ը և `defaultLanguage`-ը սահմանում կոմբինացիայի լեզվային
փաթեթներից (պահված արժեքը, եթե այն կոմբինացիայի փաթեթներից մեկն է, հակառակ դեպքում՝
կոմբինացիայի առաջին փաթեթը, որի լռելյայն արժեքը `en` է), մինչդեռ պահպանված
`autoDetect`-ը (լռելյայն միացված) շարունակում է կիրառվել։ Caveman մուտքային շարժիչն իր
կանոնների փաթեթի լեզուն ընտրում է այլ կերպ՝ յուրաքանչյուր տեքստային մասի համար առանձին
և, երբ ավտոմատ հայտնաբերումն անջատված է, `enabledPacks`-ով սահմանափակված։

Ոճ × լեզու մատրիցը ամրագրված է
`tests/unit/compression/output-styles-i18n-matrix.test.ts`-ով․ կատալոգի յուրաքանչյուր
ոճ պետք է գրառում ունենա թեստի `BASELINE_LANGUAGES`-ում, տեղայնացմամբ չսահմանափակված
ոճը պետք է ունենա pt-BR թարգմանություն (տեղայնացմամբ սահմանափակված `terse-cjk`-ն
ազատված է այս կանոնից), եթե այն նշված չէ `KNOWN_ENGLISH_ONLY`-ում, որտեղ կարող են լինել
միայն ընդհանրապես թարգմանություններ չունեցող ոճեր․ ցանկում ներառված ոճը, որն ունի որևէ
թարգմանություն, չի անցնում թեստը, և ոճը չի անցնում թեստը, երբ կորցնում է իր
`BASELINE_LANGUAGES` գրառման մեջ թվարկված լեզուներից մեկը։ Ոճ ավելացնելու համար տե՛ս
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style)։

### Գործիքի արդյունքի սեղմում

`open-sse/services/compression/toolResultCompressor.ts`-ում գտնվող
`compressToolResult()`-ը սեղմում է գործիքի արդյունքի տեքստը՝ օգտագործելով **5
ռազմավարություն**։ Այն փորձում է դրանք այս հերթականությամբ, և առաջին միացված
ռազմավարությունը, որի ստուգումը համապատասխանում է բովանդակությանը, որոշում է արդյունքը․

1. **`fileContent`**․ 3 կամ ավելի տողից բաղկացած բովանդակություն, որում առնվազն մեկ տող՝
   անտեսելով սկզբի նահանջը, սկսվում է `import `, `export `, `function `, `class `,
   `const `, `let `, `var ` կամ `return ` արտահայտություններից որևէ մեկով (բանալի բառը՝
   գումարած բացատ), կամ `if`, `for` կամ `while` բառերից որևէ մեկով, որին հաջորդում է
   `(` կամ ` (`․ պահպանում է առաջին 20 և վերջին 5 տողերը՝ բաց թողնված միջին հատվածը
   նշելով։
2. **`grepSearch`**․ բովանդակություն, որն ունի `<path>:<digits>:` ձևաչափի առնվազն մեկ
   տող, որտեղ առաջին երկու կետից առաջ գտնվող տեքստը բացատանիշ չի պարունակում․
   պահպանում է միայն այդպիսի տողերը՝ առավելագույնը 30, որից հետո նշում է հետագա
   համընկնումների քանակը և համընկած ֆայլերի ցանկը։ Մնացած բոլոր տողերը հեռացվում են։
   Այդպիսի մեկ տողը բավական է ռազմավարությունը գործարկելու համար, ուստի ժամանակային
   դրոշմով սկսվող մատյանի տողը, օրինակ՝ `12:30:45`, նույնպես հաշվի է առնվում։
3. **`shellOutput`**․ արտածումը, որը տեքստի որևէ մասում պարունակում է ANSI CSI
   հաջորդականություն (`ESC[`, որին հաջորդում են թվեր կամ կետ-ստորակետեր, ապա՝ տառ,
   ինչպես գունային կոդերում) կամ `$`, որին հաջորդում է բացատանիշ, կորցնում է այդ
   հաջորդականությունները (այլ escape հաջորդականությունները, օրինակ՝ `ESC[?25l` կամ
   պատուհանի վերնագրի OSC հաջորդականությունը, պահպանվում են), և պահպանվում են դրա
   վերջին 50 տողերը՝ իրար հաջորդող կրկնվող տողերը միավորելով։ Քանի որ այս ստուգումը
   կատարվում է `json`-ից և `errorMessage`-ից առաջ, այդպիսի `$` պարունակող JSON-ը կամ
   սխալի արտածումը երբեք դրանց չի հասնում, քանի դեռ `shellOutput`-ը միացված է։
4. **`json`**․ 2,000 նիշը գերազանցող JSON տվյալային բեռը, որը կամընտիր
   բացատանիշներից հետո սկսվում է `{`-ով կամ `[`-ով և հաջողությամբ վերլուծվում է,
   ամփոփվում է․ 7-ից ավելի տարր ունեցող զանգվածի դեպքում պահպանվում են առաջին 5 և
   վերջին 2 տարրերը և տարրերի ընդհանուր քանակը, իսկ օբյեկտի դեպքում՝ առաջին 20
   բանալիները, ընդ որում՝ յուրաքանչյուր ներդրված օբյեկտի կամ զանգվածի արժեքը
   փոխարինվում է `{…N keys}` տեղապահով (զանգվածի դեպքում N-ը դրա երկարությունն է) և
   ավելացվում է `_remaining_<N>_keys` նշիչ, որը ցույց է տալիս առաջին 20-ից հետո
   հեռացված բանալիների քանակը։ Սկալյար արժեքներն ամբողջությամբ պատճենվում են, ուստի
   20 կամ ավելի քիչ բանալի ունեցող և ներդրված արժեքներ չպարունակող օբյեկտը պարզապես
   նոր նահանջավորում է ստանում․ փոքրացված տարբերակը նիշեր է ավելացնում և մնում է
   անփոփոխ։
5. **`errorMessage`**․ արտածումը, որն իր որևէ մասում և տառերի ցանկացած ռեգիստրով
   պարունակում է `error:`, `error ` (`error` բառը, որին հաջորդում է բացատ, ինչպես
   `no error found`-ում), `[error]`, `exception:`, `exception `, `[exception]` կամ
   `traceback`, պահպանում է առաջին տողը, հաջորդ 10 տողերը և վերջին 3-ը՝ դրանց միջև
   գտնվող տողերի փոխարեն տեղադրելով `… [N frames elided] …` նշիչը։ Նշիչը հայտնվում
   է միայն այն դեպքում, երբ առաջին տողից հետո կա ավելի քան 13 տող, ուստի 14 կամ
   ավելի քիչ տող ունեցող սխալի արտածումը չի կրճատվում (12 կամ 13 տողի դեպքում վերջին
   3 տողերը կրկնում են արդեն պահպանված տողերը)։

Ռազմավարություններից որևէ մեկի համընկնելուց հետո, նույնիսկ եթե այն ոչինչ չի խնայում,
հաջորդ ռազմավարությունները չեն փորձարկվում։ Երբ համընկած ռազմավարությունը գնահատված
թոքեններ չի խնայում (երկարությունը ÷ 4՝ կլորացված դեպի վեր), օրինակ՝ կոդանման ֆայլը
25 կամ ավելի քիչ տող ունի, կամ 2,000 նիշը գերազանցող JSON զանգվածն ունի 7 կամ ավելի
քիչ տարր, ագրեսիվ շարժիչը պահպանում է գործիքի սկզբնական արդյունքը․ երկու կանչողներն
էլ (`compressAggressive()` և `compressAnthropicToolResultBlock()`) պահպանում են
սկզբնականը, երբ `saved`-ը 0 կամ պակաս է, մինչդեռ `compressToolResult()`-ն ինքը
շարունակում է վերադարձնել տվյալ ռազմավարության արտածումը։ Գործիքի արդյունքի փուլը
վերջնականը չէ․ շարժիչի պահուստային ամփոփիչը դեռ կարող է կրճատել 8,192 նիշը
գերազանցող `tool` կամ `function` հաղորդագրությունը (`maxTokensPerMessage`՝ 2,048,
բազմապատկած 4-ով)։

#### Երբ օգտագործել

Գործիքի արդյունքի սեղմումը ագրեսիվ շարժիչի 1-ին քայլն է (`compressAggressive()`՝
`open-sse/services/compression/aggressive.ts`-ում), ուստի այն գործարկվում է Aggressive
ռեժիմում և շարված խողովակաշարի `aggressive` քայլում։ Այն սեղմում է OpenAI ձևաչափի
`tool` և `function` հաղորդագրությունները, ինչպես նաև Anthropic-ի `tool_result`
բլոկների ներսում եղած տեքստը։ Յուրաքանչյուր ռազմավարություն ունի իր անջատիչը
`aggressive.toolStrategies`-ի ներքո, և բոլորը լռելյայն միացված են։ Կառավարման
վահանակում անջատիչները գտնվում են Caveman էջի **Advanced** տեսքում, երբ սեղմումը
միացված է, իսկ լռելյայն ռեժիմը Aggressive է։

### Շարված խողովակաշար

Շարված ռեժիմը **հաջորդաբար գործարկում է մի քանի շարժիչ**՝ սովորաբար սկզբում RTK-ն
(գործիքի արտածման 60-90% խնայողություն), ապա՝ Caveman-ը՝ մնացած տեքստի վրա (~46%
մուտքային խնայողություն)։ Համակցված արդյունքը **78-95% կիրառելի միջակայքն** է (տե՛ս
վերևում՝ Upstream Savings Math)․ `1 - (1 - 0.60..0.90) × (1 - 0.46)`-ը միջինում
կազմում է ≈89%։

#### Ինչպես է այն աշխատում

```
Մուտք (1000 թոքեն)
  → RTK (հրամանները հաշվի առնող զտիչ) → 200 թոքեն
    → Caveman (լցոնող տեքստի հեռացում) → 108 թոքեն
  → Ելք (108 թոքեն, ~89% խնայողություն)
```

#### Երբ օգտագործել

Օգտագործեք շարված ռեժիմը՝

- Գործիքներով ծանրաբեռնված աշխատանքային հոսքերի համար (գործակալային ծրագրավորում, հետազոտություն)
- Ծախսերի նկատմամբ զգայուն փաթեթային մշակման համար
- Երբ անհրաժեշտ է թոքենների առավելագույն խնայողություն

Շարված խողովակաշարերը կազմաձևվում են գլոբալ `stackedPipeline` սեղմման կարգավորման
միջոցով կամ անվանված սեղմման համակցությամբ, որը վերագրված է երթուղավորման
համակցությանը (տե՛ս վերևում՝ Per-Combo Override), այլ ոչ թե ավտոմատ համակցության
`modePack`-ի միջոցով (այդ դաշտը միայն փոխում է ավտոմատ համակցության մոդելի ընտրության
կշիռները, իսկ `stacked`-ը փաթեթի վավեր անուն չէ)։

## Կոմպրեսիայի համակցությունների վերասահմանումներ

Դուք կարող եք վերասահմանել կոմպրեսիայի գլոբալ ռեժիմը **յուրաքանչյուր համակցության համար առանձին**՝ տարբեր օգտագործման դեպքերում վարքագիծը ճշգրտելու նպատակով.

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

Սա օգտակար է հետևյալ դեպքերում.

- **Ծրագրավորման համակցություններ**. երկարատև աշխատաշրջանների համար օգտագործեք `aggressive` ռեժիմը
- **Արագ հարցուպատասխանի համակցություններ**. արագ պատասխանների համար օգտագործեք `lite` ռեժիմը
- **Գործիքների ինտենսիվ օգտագործմամբ համակցություններ**. առավելագույն խնայողության համար օգտագործեք `stacked` ռեժիմը
- **Արտադրական համակցություններ**. քեշավորում ապահովող մատակարարների դեպքում վերասահմանումն անջատված թողեք. մշտապես միացված՝ քեշավորումը հաշվի առնող ճշգրտումն ավտոմատ կերպով իջեցնում է `aggressive`/`ultra` ռեժիմները մինչև `standard`
  (ընտրելի `cache-aware` ռեժիմ գոյություն չունի)
