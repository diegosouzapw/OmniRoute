## Ակնարկ

OmniRoute-ն իրականացնում է հուշումների սեղմման մոդուլային խողովակաշար, որը գործարկվում է **նախապես**՝ մինչև հարցումների վերին մակարդակի մատակարարներին հասնելը։ Սա նշանակում է, որ տոկենների խնայողությունը կատարվում է թափանցիկ կերպով՝ առանց ձեր աշխատանքային հոսքը փոխելու անհրաժեշտության։

```
Հաճախորդի հարցում
  → Սեղմման ռազմավարության ընտրիչ
    → Կոմբոյի վերասահմանո՞ւմ → Օգտագործել կոմբոյի կարգավորումը
    → Ինքնաշխատ գործարկման շե՞մ → Օգտագործել ինքնաշխատ ռեժիմը
    → Լռելյայն ռեժի՞մ → Օգտագործել գլոբալ կարգավորումը
    → Անջատվա՞ծ է → Բաց թողնել սեղմումը
  → Ընտրված սեղմման ռեժիմ
    → Անջատված․ առանց սեղմման
    → Թեթև․ բացատների/ձևաչափման անվտանգ մաքրում (~15%)
    → Ստանդարտ․ պարզունակ խոսքի ոճով ավելորդ բառերի հեռացում (~30%)
    → Ագրեսիվ․ պատմության հնացում + ամփոփում (~50%)
    → Ուլտրա․ էվրիստիկ կրճատում + կոդի բլոկների նոսրացում (~75%)
    → RTK․ հրամանները հաշվի առնող տերմինալի/գործիքի ելքի զտում (վերին մակարդակում՝ 60-90% միջակայք)
    → Շերտավորված․ կարգավորված բազմաշարժիչ խողովակաշար, սովորաբար՝ RTK, ապա Caveman (համապատասխան մասի 78-95% միջակայք)
  → Սեղմված հարցում → Մատակարար
```

## Սեղմման ռեժիմներ

### Անջատված

Սեղմում չի կիրառվում։ Բոլոր հաղորդագրությունները փոխանցվում են անփոփոխ։

### Թեթև ռեժիմ (~15% խնայողություն, <1ms ուշացում)

Ամենաանվտանգ ռեժիմը՝ առանց իմաստային որևէ փոփոխության, միայն ձևաչափման մաքրում․

| Տեխնիկա                  | Նկարագրություն                                                      |
| ------------------------ | ------------------------------------------------------------------- |
| `collapseWhitespace`     | Միավորել իրար հաջորդող դատարկ տողերը և հեռացնել տողավերջի բացատները |
| `dedupSystemPrompt`      | Հեռացնել կրկնվող համակարգային հաղորդագրությունները                  |
| `compressToolResults`    | Սեղմել գործիքների/ֆունկցիաների ծավալուն ելքերը                      |
| `removeRedundantContent` | Հեռացնել կրկնվող հրահանգները                                        |
| `replaceImageUrls`       | Կրճատել base64 պատկերի տվյալների URI-ները                           |

**Լավագույնն է՝** մշտապես միացված օգտագործման և անվտանգության համար կրիտիկական աշխատանքային հոսքերի համար։

### Ստանդարտ ռեժիմ (~30% խնայողություն)

Ոգեշնչված է [Caveman-ից](https://github.com/JuliusBrussee/caveman)՝ հեռացնում է ավելորդ բառերն ու ծավալուն ձևակերպումները՝ պահպանելով իմաստը․

- Հեռացնում է ավելորդ բառերը («please», «I think», «basically», «actually»)
- Խտացնում է ծավալուն արտահայտությունները («in order to» → «to», «as a result of» → «because»)
- Հեռացնում է քաղաքավարի անորոշ ձևակերպումները («Would you mind...», «If you could possibly...»)
- Կոդավորման հուշումների համար կարգաբերված 30-ից ավելի կանոնավոր արտահայտության կանոններ

**Լավագույնն է՝** ամենօրյա կոդավորման աշխատանքային հոսքերի և ծախսերը վերահսկող թիմերի համար։

### Ագրեսիվ ռեժիմ (~50% խնայողություն)

Պատմության խելացի կառավարում երկարատև աշխատաշրջանների համար․

- **Հաղորդագրությունների հնացում** — ավելի հին հաղորդագրություններն աստիճանաբար ավելի են սեղմվում
- **Գործիքների արդյունքների ամփոփում** — գործիքների երկար ելքերը փոխարինվում են ամփոփումներով
- **Կառուցվածքային ամբողջականության պաշտպանիչ միջոցներ** — ապահովում են, որ `tool_use` + `tool_result` զույգերը մնան համահունչ
- **Համատեքստի պատուհանի հաշվառում** — պահպանում է յուրաքանչյուր մոդելի տոկենների սահմանաչափերը

**Լավագույնն է՝** երկարատև վրիպազերծման աշխատաշրջանների և մեծ կոդային բազաների համար։

### Ուլտրա ռեժիմ (~75% խնայողություն)

Առավելագույն սեղմում՝ տոկենների առումով կրիտիկական սցենարների համար․

- **Էվրիստիկ կրճատում** — հեռացնում է համապատասխանության շեմից ցածր հաղորդագրությունները
- **Կոդի բլոկների նոսրացում** — սեղմում է կրկնվող կոդի օրինակները
- **Երկուական որոնմամբ հատում** — գտնում է համատեքստի պատուհանի կտրման օպտիմալ կետը
- Ներառում է Ագրեսիվ ռեժիմի բոլոր հնարավորությունները

**Լավագույնն է՝** երբ բազմիցս հասնում եք համատեքստի սահմանաչափերին։

### RTK ռեժիմ (վերին մակարդակում՝ 60-90% միջակայք)

RTK ռեժիմը օպտիմիզացված է կոդավորման գործակալների աշխատաշրջաններում հանդիպող գործիքների ծավալուն ելքերի համար․

- Հայտնաբերում է հրամանների/ելքերի այնպիսի դասեր, ինչպիսիք են `git status`, `git diff`, `git log`, թեստերի գործարկիչները,
  TypeScript/Vite/Webpack կառուցումները, ESLint/Biome/Prettier-ը, npm-ի աուդիտները/տեղադրումները, Docker-ի մատյանները, ենթակառուցվածքի
  ելքը և ընդհանուր կեղևի ելքը
- Կիրառում է JSON զտիչների փաթեթները `open-sse/services/compression/engines/rtk/filters/`-ից
- Ներմուծում է RTK TOML schema v1 զտիչները նախագծի կամ գլոբալ `filters.toml` ֆայլերից՝ ներկառուցված թեստերի
  վավերացմամբ և նախագծային ֆայլերի վստահության ստուգմամբ
- Տրամադրվում է ներկառուցված ստուգման օրինակներ պարունակող 49 զտիչով
- Հեռացնում է ANSI կառավարման հաջորդականությունները, առաջընթացի ցուցիչները, կրկնվող տողերը և գործնական նշանակություն չունեցող աղմուկը
- Պահպանում է ձախողումները, սխալները, զգուշացումները, փոփոխված ֆայլերը, ամփոփումները և երկար ելքի վերջնամասը
- Աջակցում է վստահության ստուգմամբ նախագծային զտիչներին, գլոբալ զտիչներին և ընտրովի՝ խմբագրված չմշակված ելքի վերականգնմանը

**Լավագույնն է՝** shell-ի, կառուցման, թեստավորման, git-ի, grep-ի և ֆայլային ելքերի գրառումներով գործակալի աշխատաշրջանների համար։

### Շերտավորված ռեժիմ (համապատասխան մասի 78-95% միջակայք)

Շերտավորված ռեժիմը որոշակի հերթականությամբ գործարկում է սեղմման մի քանի շարժիչ։ Լռելյայն խողովակաշարն է՝

```txt
RTK -> Caveman
```

Այս հերթականությունը նախ սեղմ է պահում տերմինալի/գործիքի ելքը, ապա մնացած բնական լեզվով հուշման նկատմամբ կիրառում է Caveman-ի իմաստային խտացումը։ Շերտավորված խողովակաշարերը կարող են կազմաձևվել գլոբալ կերպով կամ երթուղավորման կոմբոներին նշանակված սեղմման կոմբոների միջոցով։

**Լավագույնն է՝** գործիքների մեծ մատյաններ և մարդկային հրահանգներ կամ օգնականի ամփոփումներ պարունակող խառը համատեքստի համար։

## Վերադաս նախագծերի խնայողությունների հաշվարկ

OmniRoute-ը փաստագրում է սեղմումից ստացվող խնայողությունները՝ հիմնվելով երկու աղբյուրի վրա՝ վերադաս նախագծերի չափորոշիչների և
OmniRoute-ի սեփական շարժիչների համադրման։

| Աղբյուր | Այստեղ օգտագործված՝ վերադաս նախագծի README-ի ցուցանիշը                                                                                      |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | ելքային թոքենների `~75%`-ով պակաս քանակ, չափորոշիչներում ելքի միջին `65%` խնայողություն, `22-87%` միջակայք և մուտքը `~46%`-ով սեղմող գործիք |
| RTK     | հրամանների ելքի `60-90%` խնայողություն․ օրինակելի աշխատաշրջանում՝ `~118,000 -> ~23,900` թոքեն, կամ `79.7%` խնայողություն (`~80%`)           |

Գործիքի/համատեքստի համընկնող օգտակար բեռների դեպքում OmniRoute-ի լռելյայն համակցությունը շարժիչները դասավորում է հետևյալ կերպ․

```txt
RTK -> Caveman
```

Համակցված խնայողությունները բազմապատկական են, ոչ թե գումարային․

```txt
համակցված = 1 - (1 - RTK-ի խնայողություն) * (1 - Caveman-ի մուտքային խնայողություն)
միջին     = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
միջակայք  = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

Այդ `78-95%` ցուցանիշը կիրառելի է, երբ և՛ RTK-ն, և՛ Caveman-ը կարող են կրճատել միևնույն մուտքային/համատեքստային օգտակար բեռը։
Caveman-ի պատասխանի ելքային ռեժիմն առանձին է․ երբ այն միացված է, օգտագործեք Caveman-ի սեփական ելքային խնայողությունները (`65%`
միջին, `~75%` գլխավոր ցուցանիշ, `22-87%` միջակայք)։ Ընդհանուր վճարային խնայողությունները կախված են ձեր հուշումների/ելքերի հարաբերակցությունից։

### Ի՞նչ է իրականում նշանակում «կիրառելի»

Գլխավոր `15-95%` միջակայքն իրական է, սակայն այն կիրառվում է միայն **կրկնվող կամ չափազանց ծավալուն** բովանդակության նկատմամբ՝ կրկնվող
սխալի տողեր, նույն նախազգուշացումը բազմիցս արտածող կառուցման մատյան, չափազանց մեծ `grep`/ֆայլի ընթերցման արտածում։ Դա
**չի** նշանակում, որ յուրաքանչյուր հարցում այդքան խնայողություն է ապահովում։

Փորձնականորեն հաստատված է (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`)․ Anthropic-ի ձևաչափով `tool_result` բլոկի նկատմամբ, որը պարունակում էր սխալի 300 նույնական
տող, `stacked` (RTK + Caveman) գործարկումն ապահովել է **թոքենների 95.93% խնայողություն / նիշերի 96.26% խնայողություն**՝ ճշգրտորեն տեղավորվելով հայտարարված
միջակայքում։ Սակայն նույն շղթայի գործարկումը սովորական, չկրկնվող գործիքի ելքի նկատմամբ (`grep`-ի համապատասխանությունների մաքուր ցանկ,
ֆայլի կարճ ընթերցում, սովորական զրույցի տեքստ) իրավացիորեն ապահովում է **գրեթե զրոյական խնայողություն**, քանի որ
հեռացնելու կրկնվող տարրեր չկան, իսկ `validateCompression()`-ը (`validation.ts`) թույլ չի տալիս ուղարկել այնպիսի
վերաշարադրում, որը կհեռացնի կամ կփոփոխի կոդի բլոկներ, URL-ներ, վերնագրեր, տարբերակներ կամ ALL-CAPS հաստատունների նույնացուցիչներ։

Սա սպասվող և անվտանգ վարքագիծ է, ոչ թե սխալ․ ծրագրավորման աշխատաշրջանը, որը հիմնականում ընթերցում/որոնում է մաքուր ֆայլեր,
կունենա ընդհանուր համեստ խնայողություններ, նույնիսկ երբ սեղմումը լիովին միացված է, մինչդեռ խափանվող
ցիկլի կամ շատախոս լինտերի հանդիպող աշխատաշրջանն այդ տվյալահոսքի համար կունենա ամբողջական `78-95%` խնայողությունը։ Մի՛ օգտագործեք մեկ աշխատաշրջանի
ցածր ընդհանուր խնայողության տոկոսը՝ որպես սեղմման սխալ կազմաձևման ապացույց․ նախ ստուգեք՝ արդյոք
հիմքում ընկած գործիքի ելքն իրականում կրկնվող էր։

## Կազմաձևում

### Կառավարման վահանակ

Անցեք `Կառավարման վահանակ → Համատեքստ և քեշ`․

- **Caveman** — ռեժիմի ընտրություն, լեզվային փաթեթներ, նախադիտում և գլոբալ լռելյայն կարգավորումներ
- **RTK** — հրամանների զտիչի նախադիտում, RTK-ի անվտանգության կարգավորումներ և զտիչների կատալոգ
- **Սեղմման համակցություններ** — անվանակոչված շարժիչների խողովակաշարեր, որոնք նշանակվում են երթուղավորման համակցություններին
- **Ավտոմատ գործարկման շեմ** — ավտոմատ կերպով միացնել սեղմումը, երբ թոքենների քանակը գերազանցում է շեմը

### Յուրաքանչյուր համակցության համար վերասահմանում

`Կառավարման վահանակ → Համատեքստ և քեշ → Սեղմման համակցություններ` բաժնում սեղմման համակցություն նշանակեք երթուղավորման
համակցությանը․

```txt
Համակցություն: "free-tier-fallback"
  Սեղմման համակցություն: "coding-agent-stack"
  Խողովակաշար: RTK -> Caveman
  Թիրախներ:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

Սա թույլ է տալիս օգտագործել բազմաստիճան սեղմում անվճար/ծրագրավորման մատակարարների համար՝ միաժամանակ վճարովի
բաժանորդագրությունների դեպքում պահպանելով թեթև ռեժիմը։

Այս «Յուրաքանչյուր համակցության համար վերասահմանում» նշանակումը տարբերվում է **երթուղավորման համակցության սեղմման
ռեժիմի** վերասահմանումից (Default/Off/Lite/Standard/Aggressive/Ultra)․ այդ վերասահմանումը չի ընտրում անվանակոչված
սեղմման համակցության խողովակաշար, այլ պարզապես սահմանում է `compressionMode` դաշտը, որն օգտագործվում է
`resolveCompressionPlan`-ի կողմից։ Այն կարող է սահմանվել կամ համակցության քարտում (`Կառավարման վահանակ → Համակցություններ`), կամ, սկսած
#6760-ից, յուրաքանչյուր երթուղավորման համակցության համար՝ «Նշանակել երթուղավորմանը» ցանկում՝
`Կառավարման վահանակ → Համատեքստ և քեշ → Սեղմման համակցություններ` բաժնում՝ անմիջապես վերևում նկարագրված խողովակաշարի նշանակման նշավանդակի
կողքին։ Երկու միջերեսների փոփոխություններն էլ պահպանվում են նույն `PUT /api/combos/{id}` վերջնակետի միջոցով։

### Յուրաքանչյուր հարցման համար վերասահմանում

Ուղարկեք `x-omniroute-compression` հարցման վերնագիրը՝ մեկ հարցման համար սեղմման պլանը վերասահմանելու նպատակով։
Այն ունի ամենաբարձր առաջնահերթությունը՝ գերակայելով երթուղավորման համակցության վերասահմանմանը, ակտիվ պրոֆիլին,
ավտոմատ գործարկմանը և վահանակի Default կարգավորմանը։ Անհայտ արժեքներն անտեսվում են (հարցումը երբեք չի մերժվում), իսկ
գլոբալ գլխավոր անջատիչը շարունակում է վերահսկել ամեն ինչ․ երբ սեղմումը գլոբալ առումով անջատված է, վերնագիրը չի կարող
այն միացնել։ Արժեքները՝

| Արժեք         | Ազդեցություն                                                                                                   |
| ------------- | -------------------------------------------------------------------------------------------------------------- |
| `off`         | Այս հարցման համար սեղմում չի կիրառվում։                                                                        |
| `default`     | Վահանակից ստացված Default պրոֆիլը (ակտիվ պրոֆիլն անտեսվում է)։                                                 |
| `engine:<id>` | Մեկ շարժիչ, եթե այն միացված է, օրինակ՝ `engine:rtk`։                                                           |
| `<combo>`     | Անվանակոչված համակցություն․ սկզբում համընկնումն ըստ անվան (առանց մեծատառ/փոքրատառ տարբերակման), ապա՝ ըստ id-ի։ |

Կիրառված պլանը վերադարձվում է `X-OmniRoute-Compression: <mode>; source=<source>` պատասխանի
վերնագրում, որտեղ `<source>`-ը `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default` կամ `off` արժեքներից մեկն է։

### API

```bash
# Ստանալ սեղմման կարգավորումները
curl http://localhost:20128/api/settings/compression

# Թարմացնել սեղմման կարգավորումները
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# Նախադիտել որոշակի RTK/բազմաստիճան օգտակար բեռ
curl -X POST http://localhost:20128/api/compression/preview \
  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# Ցուցակել RTK զտիչների փաթեթները
curl http://localhost:20128/api/context/rtk/filters

# Անմիջապես փորձարկել RTK-ն՝ հրամանի կամընտրական մետատվյալներով
curl -X POST http://localhost:20128/api/context/rtk/test \
  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

## Երախտագիտություն

Standard ռեժիմի սեղմման կանոնները ներշնչված են **[JuliusBrussee](https://github.com/JuliusBrussee)**-ի **[Caveman](https://github.com/JuliusBrussee/caveman)** (⭐ 51K+) նախագծից՝ լայն տարածում ստացած «ինչու օգտագործել շատ թոքեն, երբ քիչ թոքենն էլ գործ է անում» նախագծից։ Caveman-ը հաղորդում է ելքային թոքենների `~75%` կրճատման, հենանիշային թեստերում ելքի միջինը `65%` խնայողության, ելքի `22-87%` միջակայքի և մուտքի սեղմման `~46%` գործիքի մասին։

RTK ռեժիմը ներշնչված է **[RTK AI](https://github.com/rtk-ai)**-ի **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** նախագծից՝ տերմինալի, կառուցման, թեստավորման, git-ի և գործիքների ելքի զտման համար նախատեսված բարձր արտադրողականությամբ հրամանների ելքի սեղմման նախագծից։ RTK-ն հաղորդում է `60-90%` խնայողության մասին, իսկ դրա README-ի նմուշային աշխատաշրջանը ցույց է տալիս `~80%` խնայողություն։

## Սեղմման առաջադեմ համակարգեր

7 ստանդարտ ռեժիմներից բացի, OmniRoute-ը ներառում է սեղմման մի քանի առաջադեմ
համակարգեր, որոնք ավտոմատ կերպով աշխատում են՝ ըստ համատեքստի։

### Քեշը հաշվի առնող սեղմում

Որոշ մատակարարներ (օրինակ՝ Anthropic-ը՝ հուշումների քեշավորմամբ) աջակցում են **հուշումների քեշավորմանը**,
որը նրանց թույլ է տալիս քեշավորել հուշման մասերը՝ ծախսերն ու ուշացումը նվազեցնելու համար։ Երբ
քեշավորումը միացված է, ագրեսիվ սեղմումը կարող է իրականում **վատթարացնել** արդյունավետությունը,
քանի որ այն փոխում է քեշավորված թոքենները՝ անվավեր դարձնելով քեշը։

`cachingAware.ts` մոդուլը լուծում է սա՝ **հայտնաբերելով քեշավորման համատեքստը** և
համապատասխանաբար **կարգավորելով սեղմման ռազմավարությունը**։

#### Ինչպես է այն աշխատում

1. **Քեշավորման համատեքստի հայտնաբերում** — Հարցման մարմնում որոնում է `cache_control` նշիչներ
2. **Քեշավորում աջակցող մատակարարների որոշում** — Ստուգում է՝ արդյոք թիրախային մատակարարն աջակցում է քեշավորմանը
3. **Ռազմավարության կարգավորում** — Քեշավորում աջակցող մատակարարների համար `aggressive`/`ultra` ռեժիմներն իջեցնում է մինչև `standard`
4. **Համակարգային հուշման բացթողում** — Համակարգային հուշումները սովորաբար քեշավորվում են, ուստի դրանք չեն սեղմվում
5. **Դետերմինիստական փոխակերպումների օգտագործում** — Օգտագործում է միայն այնպիսի փոխակերպումներ, որոնք ստեղծում են հետևողական ելք

#### Կոդի օրինակ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Քեշի նշիչ
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### Երբ օգտագործել

Քեշը հաշվի առնող սեղմումը **միշտ միացված է**՝ կազմաձևում չի պահանջվում։ Այն ակտիվանում է միայն,
երբ՝

- Հարցումն ունի `cache_control` նշիչներ
- Թիրախային մատակարարն աջակցում է հուշումների քեշավորմանը (Anthropic, OpenAI և այլն)

### Աստիճանական հնացում

Երկար խոսակցությունները կուտակում են հաղորդագրությունների բազմաթիվ հերթեր, սակայն ավելի հին հերթերը դառնում են պակաս
արդիական։ `progressiveAging.ts` մոդուլը **նվազեցնում է հաղորդագրությունների մանրամասնությունը՝ ըստ հերթերի հեռավորության**՝

- **Վերջին հերթեր (0-3)**: Պահվում են բառացիորեն (ամբողջական մանրամասներով)
- **Միջին հերթեր (4-8)**: Lite սեղմում (բացատների և ձևաչափման մաքրում)
- **Հին հերթեր (9+)**: Caveman սեղմում (ավելորդ մասերի հեռացում, ամփոփում)
- **Շատ հին հերթեր (20+)**: Խիստ ամփոփվում կամ հեռացվում են

#### Կոդի օրինակ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... ևս 50 հերթ ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // Առաջին 3 հերթերը՝ բառացիորեն
  light: 8, // 4-8-րդ հերթերը՝ lite սեղմում
  moderate: 20, // 9-20-րդ հերթերը՝ caveman սեղմում
  // 21-րդ և հաջորդ հերթերը՝ խիստ ամփոփում
});

// saved = խնայված թոքենների քանակը
```

#### Երբ օգտագործել

Պրոգրեսիվ հնացումը **միշտ միացված է** `aggressive` և `ultra` ռեժիմների համար։ Այն
հատկապես արդյունավետ է՝

- Երկարատև ծրագրավորման աշխատաշրջանների համար
- Մի քանի օր տևող խոսակցությունների համար
- Բազմաթիվ գործիքային կանչերով գործակալային աշխատանքային հոսքերի համար

### Քարանձավային ելքի ռեժիմ

`outputMode.ts` մոդուլը ներարկում է **համակարգային հուշման հրահանգներ**, որպեսզի
մոդելն ինքն արտադրի սեղմված, հակիրճ ելք («քարանձավային» ոճով)։

#### Ինչպես է այն աշխատում

Մուտքային տվյալները սեղմելու փոխարեն այս ռեժիմն ավելացնում է հետևյալին նման համակարգային հուշում՝

> «Պատասխանիր նվազագույն քանակի բառերով։ Բաց թող քաղաքավարի ձևակերպումները։ Օգտագործիր կարճ նախադասություններ»։

Սա հատկապես լավ է աշխատում հետևյալ դեպքերում՝

- Կոդի գեներացում (ավելի հակիրճ ելք = ավելի քիչ տոկեններ)
- Արագ հարցուպատասխան (մանրամասն բացատրությունների կարիք չկա)
- Փաթեթային մշակում (առավելագույն թողունակություն)

#### Երբ օգտագործել

Քարանձավային ելքի ռեժիմը **ըստ ցանկության է միացվում**․ այն սահմանեք համակցված կազմաձևի միջոցով՝

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "outputMode": "caveman"
    }
  }
}
```

### Ելքի ոճեր (կատալոգ)

Վերևում նկարագրված քարանձավային ելքի ռեժիմը **հին՝ մեկ ոճով ուղին է**։ 4-րդ փուլում այն ընդհանրացվեց՝
վերածվելով համակցելի ելքային ոճերի կատալոգի՝ `OUTPUT_STYLE_CATALOG`,
որը գտնվում է `open-sse/services/compression/outputStyles/catalog.ts`-ում։ Յուրաքանչյուր ոճ համակարգային հուշման
հրահանգ է, որը ստիպում է մոդելին արտադրել ավելի քիչ ծախսատար ելք․ ոճերը կարող են միացվել
միաժամանակ և ներարկվում են կատալոգում նշված հերթականությամբ։

| Ոճ                                | `id`          | Ինչ է անում                                                                                                                                                                                                                                     | Հրահանգների լեզուներ                                                                        |
| --------------------------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |

Յուրաքանչյուր ոճ տրամադրվում է ինտենսիվության երեք մակարդակով՝ `lite`, `full`, `ultra`, և յուրաքանչյուր մակարդակ
ավարտվում է սահմանների ընդհանուր դրույթով, որը կոդի բլոկները, ֆայլերի ուղիները, հրամանները,
սխալի տողերը, URL-ներն ու նույնացուցիչները պահպանում է անփոփոխ։

#### Ինչպես է աշխատում ներարկումը

`applyOutputStyles()`-ը (`open-sse/services/compression/outputStyles/apply.ts`) ընտրությունը
համադրում է կատալոգի հետ (անհայտ id-ները և տեղայնացմանը չհամապատասխանող ոճերը
անտեսվում են և երբեք սխալ չեն առաջացնում), ընտրված հրահանգները միավորում է կատալոգում նշված հերթականությամբ,
սահմանների դրույթն ավելացնում է **մեկ անգամ** և արդյունքը տեղադրում է համակարգային
հուշման սկզբում՝ մեկ իդեմպոտենտության նշիչից (`[OmniRoute Output Styles]`) հետո․ կրկին կիրառելը
ոչինչ չի փոխում։ Երբ հայտնաբերված հարցման լեզվի համար առկա է թարգմանություն, անգլերենի փոխարեն
ներարկվում է տեղայնացված հրահանգը։

#### Ինչպես միացնել

Կառավարման վահանակում՝ **Համատեքստ → Կարգավորումներ → Սեղմում**․ յուրաքանչյուր ոճի համար մեկ տող՝
միացման/անջատման փոխարկիչով և մակարդակի ընտրիչով։ Ծրագրային եղանակով սեղմման կազմաձևը
ընտրությունը պահպանում է հետևյալ տեսքով՝

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

Հետադարձ համատեղելիություն․ հին `outputMode: "caveman"` համակցված կարգավորումը շարունակում է աշխատել և համապատասխանեցվում է
`terse-prose`-ին՝ բոլոր հին լեզուներում բայթ առ բայթ նույնական լինելով նախկին ներարկմանը։

Լեզվի ընտրություն․ երբ `languageConfig.enabled`-ը միացված է, `autoDetect`-ը ընտրում է
օգտատիրոջ վերջին հաղորդագրության լեզուն (օգտագործելով մուտքային շարժիչների նույն հայտնաբերիչը)․
`autoDetect`-ի անջատումը ամրագրում է `defaultLanguage`-ը։ Անջատված լինելու դեպքում՝ անգլերեն։

Ոճ × լեզու մատրիցը ամրագրված է
`tests/unit/compression/output-styles-i18n-matrix.test.ts`-ով․ նոր ոճը չի կարող թողարկվել
առանց առնվազն pt-BR թարգմանության (կամ հստակորեն հետևվող բացառության), իսկ
գոյություն ունեցող ոճը չի կարող աննկատ կորցնել որևէ տեղայնացում։ Ոճ ավելացնելու համար տե՛ս
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style)։

### Գործիքի արդյունքների սեղմում

`toolResultCompressor.ts` մոդուլը գործիքների արդյունքների համար տրամադրում է **սեղմման 5 մասնագիտացված ռազմավարություն**
(ֆունկցիաների կանչեր, գործակալների ելքեր, որոնման արդյունքներ և այլն)՝

1. **Որոնման արդյունքների սեղմում** — Հեռացնում է կրկնվող արդյունքները, պահպանում լավագույն N-ը
2. **Ֆայլի ընթերցման սեղմում** — Կրճատում է մեծ ֆայլերը, պահպանում վերնագրերն ու ներմուծումները
3. **Կոդի կատարման սեղմում** — Պահպանում է միայն անհրաժեշտ stdout/stderr-ը
4. **Տվյալների բազայի հարցման սեղմում** — Սահմանափակում է տողերը, հեռացնում մանրամասն մետատվյալները
5. **API պատասխանի սեղմում** — Հեռացնում է null դաշտերը, սեղմում զանգվածները

#### Երբ օգտագործել

Գործիքի արդյունքների սեղմումը **միշտ միացված է**, երբ առկա են գործիքային կանչեր։ Որևէ
կազմաձևում անհրաժեշտ չէ։

### Շերտավորված մշակման շղթա

Շերտավորված ռեժիմը **մի քանի շարժիչներ աշխատեցնում է հաջորդաբար**․ սովորաբար նախ RTK-ն
(գործիքի ելքում 60-90% խնայողություն), ապա Caveman-ը (մնացած տեքստում ևս 30%
խնայողություն)։ Այս եղանակով ստացվում է **78-95% ընդհանուր խնայողություն**։

#### Ինչպես է այն աշխատում

```
Մուտք (1000 տոկեն)
  → RTK (հրամանները հաշվի առնող զտիչ) → 200 տոկեն
    → Caveman (ավելորդ բառերի հեռացում) → 140 տոկեն
  → Ելք (140 տոկեն, 86% խնայողություն)
```

#### Երբ օգտագործել

Օգտագործեք շերտավորված ռեժիմը հետևյալ դեպքերում՝

- Գործիքներով հագեցած աշխատանքային հոսքեր (գործակալային ծրագրավորում, հետազոտություն)
- Ծախսերի նկատմամբ զգայուն փաթեթային մշակում
- Երբ անհրաժեշտ է տոկենների առավելագույն խնայողություն

Կազմաձևեք համակցված կարգավորման միջոցով՝

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "modePack": "stacked"
    }
  }
}
```

## Կոմպրեսիայի համակցությունների վերասահմանումներ

Դուք կարող եք վերասահմանել կոմպրեսիայի գլոբալ ռեժիմը **յուրաքանչյուր համակցության համար առանձին**՝ տարբեր օգտագործման դեպքերի վարքագիծը ճշգրտելու նպատակով.

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "auto": {
      "weights": { "taskFit": 0.5 },
      "modePack": "quality-first"
    }
  },
  "compressionOverride": {
    "mode": "aggressive",
    "stackedPipelines": ["rtk", "caveman"],
    "preserveToolDefinitions": true
  }
}
```

Սա օգտակար է հետևյալ դեպքերում.

- **Կոդավորման համակցություններ**. Երկար աշխատաշրջանների համար օգտագործեք `aggressive` ռեժիմը
- **Արագ հարցուպատասխանի համակցություններ**. Արագ պատասխանների համար օգտագործեք `lite` ռեժիմը
- **Գործիքներով հագեցած համակցություններ**. Առավելագույն խնայողության համար օգտագործեք `stacked` ռեժիմը
- **Արտադրական համակցություններ**. Քեշավորում ապահովող մատակարարների համար օգտագործեք `cache-aware` ռեժիմը
