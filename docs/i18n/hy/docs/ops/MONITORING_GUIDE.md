> **Կարճ ասած**․ OmniRoute-ը տրամադրվում է ներկառուցված առողջական վիճակի մշտադիտարկմամբ, մատակարարների ավտոպիլոտով, քվոտաների հետագծմամբ և դիտարկելիության ինտեգրման կետերով։ Այս ուղեցույցն անդրադառնում է կառավարման վահանակին, ծանուցումներին և խնդիրների ախտորոշմանը։

**Աղբյուրներ․**

- `src/lib/monitoring/observability.ts` — դիտարկելիության ակնթարթային պատկեր
- `src/lib/monitoring/comboHealthAutopilot.ts` — կոմբինացիաների առողջական վիճակի ավտոպիլոտ
- `src/lib/monitoring/providerHealthAutopilot.ts` — մատակարարների ավտոպիլոտ
- `src/lib/monitoring/providerHealthMatrix.ts` — մատակարարների առողջական վիճակի մատրից
- `src/lib/localHealthCheck.ts` — տեղային առողջական վիճակի ստուգում
- `src/lib/tokenHealthCheck.ts` — թոքենի թարմացման առողջական վիճակ
- `src/lib/proxyHealth.ts` — պրոքսիի առողջական վիճակի քեշ (նկարագրված է PROXY_GUIDE.md-ում)

## Կառավարման վահանակի էջեր

### `/dashboard/health` (Համակարգի առողջական վիճակ)

Առողջական վիճակի վերին մակարդակի կառավարման վահանակը ցուցադրում է․

| Բաժին                       | Ինչ է ցուցադրում                                        |
| --------------------------- | ------------------------------------------------------- |
| **Սերվերի վիճակ**           | Աշխատաժամանակ, տարբերակ, պորտ, ակտիվ կապեր              |
| **Տվյալների բազա**          | Կապ, ամբողջականություն, WAL-ի չափ, վերջին միգրացիաներ   |
| **Մատակարարների ամփոփում**  | Ակտիվների քանակ, առողջների քանակ, բաց անջատիչների քանակ |
| **Քվոտայի մշտադիտարկիչներ** | Ակտիվ աշխատաշրջաններ, ծանուցումներ, սպառված քվոտաներ    |
| **Վերջին սխալներ**          | Վերջին 10 սխալները՝ կանչերի ստեկերով                    |
| **Ռեսուրսների օգտագործում** | Հիշողություն, CPU, կույտի ճնշման ցուցիչ                 |

### `/dashboard/providers` (Մատակարարների առողջական վիճակ)

Կառավարման վահանակ՝ ըստ մատակարարի․

| Սյունակ      | Նկարագրություն                                       |
| ------------ | ---------------------------------------------------- |
| Մատակարար    | Մատակարարի ID-ն + ցուցադրվող անունը                  |
| Առողջություն | Կանաչ/դեղին/կարմիր վիճակ                             |
| Շղթա         | Բաց/փակ/կիսաբաց վիճակ                                |
| Կապեր        | Կապերի քանակը, վերջին թարմացումը                     |
| Մոդելներ     | Հասանելի մոդելներ, առողջությունն ըստ մոդելի          |
| Արժեք        | Այսօրվա արժեքը, 7-օրյա միտումը                       |
| Սխալներ      | Վերջին 24 ժամվա սխալների քանակը, սխալի հիմնական դասը |

Սեղմեք մատակարարի վրա՝ տեսնելու համար․

- Վերջին հարցումները՝ ուշացման մանրամասներով
- Առողջության գնահատականներ՝ ըստ կապի
- Արգելափակումներ՝ ըստ մոդելի
- Ավտոպիլոտի առաջարկություններ

### `/dashboard/quota` (Քվոտաների հետագծում)

Յուրաքանչյուր API բանալու համար․

- Հաջորդ զրոյացման ժամանակը
- Ծանուցումների պատմությունը

### `/dashboard/combos` (Կոմբինացիաների առողջական վիճակ)

Յուրաքանչյուր կոմբինացիայի համար․

- Ռազմավարություն + թիրախներ
- Յուրաքանչյուր թիրախի առողջական վիճակը

- Հաջողության գործակիցը (24 ժ, 7 օր, 30 օր)

## Առողջության ստուգման API

OmniRoute-ը տրամադրում է HTTP առողջության ստուգման **երկու** մակերես։ Դրանք փոխարինելի չեն օրկեստրատորների համար։

| Ուղի                         | Նպատակ                                                                       | Ծանրություն                                    | Օգտագործում                                                                                     |
| ---------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `GET /healthz`               | Կենսացիկլի կենսունակություն/պատրաստություն (`ok` / `starting` / `stopping`)  | Չնչին (միայն փուլի դրոշակ)                     | Kubernetes-ի **պատրաստություն**․ մեղմ **կենսունակություն**, եթե պարտադիր պետք է օգտագործեք HTTP |
| `GET /api/monitoring/health` | Համակարգի և մատակարարների խորացված ամփոփում (DB, heap, կատալոգի քանակներ, …) | Ծանր (համաժամանակյա DB / մոնիթորինգի աշխատանք) | Վահանակներ, blackbox խորացված ստուգումներ, Docker-ի ներկառուցված healthcheck                    |

> **Նշում․** Մատակարարների առողջության մատրիցները, autopilot-ի խնդիրները, քվոտաների մոնիթորները, թոքենների առողջությունը և `/api/monitoring/health`-ից ավելի մանրամասն հապաղման տվյալները հասանելի են **MCP գործիքի**՝ `observability_snapshot`-ի կամ **վահանակի** էջերի միջոցով․ դրանց համար առանձնացված REST երթուղիներ չկան։

Երկու երթուղիներն էլ աշխատում են հարցումների մշակման հետ **նույն Node իրադարձությունների ցիկլում**։ CPU-ի վրա ծանրաբեռնված ուղին (մեծ `GET /v1/models` կատալոգի մշակում, երկար համատեքստի սեղմում / թոքենների հաշվում) կարող է ուշացնել HTTP-ի **բոլոր** մշակիչները, ներառյալ `/healthz`-ը։ Իրադարձությունների ցիկլի զբաղված լինելը ≠ գործընթացի դադարած լինելը։ Նախընտրելի է շտկել ծանրաբեռնվածության աղբյուրը․ զոնդի կարգավորումը միայն նվազեցնում է սխալ դադարեցումները։

### Թեթև օրկեստրատորի զոնդ

```bash
GET /healthz
# կամ HEAD /healthz
```

- **200** + `ok` մարմին, երբ սերվերի կենսացիկլի փուլը պատրաստ է
- **503** + `starting` / `stopping`՝ գործարկման կամ անջատման ընթացքում
- Իրականացում՝ `src/app/healthz/route.ts` (առանց DB ping-ի)

```json
}
```

#### `credentialHealth`․ զոնդի քեշն ընդդեմ SQLite-ի `test_status`-ի

`GET /api/monitoring/health` → `credentialHealth`-ը **հիշողության մեջ պահվող զոնդի քեշի
չափիչն է**, այլ ոչ թե `provider_connections.test_status`-ի ընթացիկ արտահանումը։ #12532-ից հետո
հարցման ուղին կարդում է միայն `getCachedCredentialHealthSummary()`-ը․ ֆոնային զոնդերը
թարմացնում են քեշը՝ իրադարձությունների ցիկլից դուրս։

| Շերտ                          | Որտեղ                                                                 | Ինչ է այն նշանակում                                                                                                                                                                                                                     |
| ----------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Զոնդի քեշի չափիչ              | `credentialHealth.total` / `healthy` / `failed` / `unknown` / `stale` | Հաշվառման տվյալների առողջության զոնդի վերջին արդյունքները, որոնք դեռ պահվում են գործընթացի հիշողության մեջ։ `source`-ը միշտ `probe-cache` է։                                                                                            |
| Խափանված կապի մանրամասներ     | `credentialHealth.failedConnections`                                  | Առկա է **միայն երբ `failed > 0`**։ `status=error` ունեցող քեշի տողերի սահմանափակ ցուցակ (`connectionId`, `status`, մաքրված `lastError` / `lastErrorType`)։ `failedOmitted`-ը սահմանվում է, երբ ցուցակը կրճատվել է սահմանաչափի պատճառով։ |
| SQLite-ի պահպանվող կարգավիճակ | `credentialHealth.staleDbNonOkCount`                                  | **Ակտիվ** (`is_active=1`) կապի տողերի քանակը, որոնց պահպանված `test_status`-ը հայտնի ոչ նորմալ արժեք է (`error`, `expired`, `credits_exhausted`, `banned`, `deactivated`, `unavailable`)։                                               |

Երկու շերտերը կարող են միտումնավոր չհամընկնել․

- Չափիչում `failed=0`, մինչդեռ `staleDbNonOkCount>0`․ SQLite-ում դեռ պահպանվում է
  `test_status`-ի արժեք (օրինակ՝ `expired` կամ `credits_exhausted`), որը զոնդի քեշի վերջին
  պատկերը չի հաշվում որպես `status=error`։
- Չափիչում `failed>0`, մինչդեռ SQLite-ը առողջ է թվում․ վերջին զոնդը ձախողվել և
  քեշավորվել է, իսկ DB տողը չի թարմացվել կամ ավելի ուշ մաքրվել է։

Այս վերջնակետից տվյալներ հավաքելիս զգուշացում մի ստեղծեք՝ հիմնվելով միայն
`provider_connections.test_status`-ի վրա։ Ընթացիկ զոնդային ձախողումների համար օգտագործեք `failed` + `failedConnections`,
իսկ պահպանված կարգավիճակների քանակի անհրաժեշտության դեպքում՝ `staleDbNonOkCount`։

### Kubernetes-ի զոնդերի առաջարկություններ

OmniRoute-ը **մեկ Node գործընթաց է** (մեկ իրադարձությունների ցիկլ)։ Docker-ի ստանդարտ `HEALTHCHECK`-ը թիրախավորում է թեթև `/healthz`-ը։ `/api/monitoring/health`-ը **չափազանց ծանր է** kubelet-ի կենսունակության ստուգման միջակայքերի համար։

| Զոնդ                      | Առաջարկվող թիրախ                                                                         | Նշումներ                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Մեկնարկային**           | HTTP `GET /healthz`՝ երկար `failureThreshold`-ով (կամ մեծ `startPeriod`-ով)              | Սառը մեկնարկը + SQLite-ի միգրացիան կարող են տևել մի քանի վայրկյանից ավելի                                                                                                                                                                                                                                                                                                                                                                                           |
| **Պատրաստություն**        | HTTP `GET /healthz`                                                                      | Կենսացիկլ՝ `ok` / `starting` / `stopping` (200՝ ընդդեմ 503-ի)։ Այնուամենայնիվ, վիճակը տատանվում է, եթե ցիկլը արգելափակված է պրոցեսորային աշխատանքով։ **Մի քանի վայրկյանից ստացված 200-ը առողջ վիճակ չէ** (#10303). դա նշանակում է, որ իրադարձությունների ցիկլը ռեսուրս չի ստացել՝ նախքան 3 բայթանոց մշակիչի գործարկումը                                                                                                                                             |
| **Կենսունակություն**      | HTTP `GET /livez`, **կամ TCP**՝ հիմնական ծառայության պորտում (`PORT`, լռելյայն՝ `20128`) | `/livez`-ը ստուգում է միայն պրոցեսի կենսունակությունը (միշտ 200, եթե մշակիչը գործարկվում է)։ Այն նույնպես օգտագործում է նույն իրադարձությունների ցիկլը. զբաղված ≠ մեռած, և իրադարձությունների ցիկլի ռեսուրսային սովը (#10303) չի հայտնաբերում TCP-ից ավելի լավ։ Նախընտրեք **TCP**, եթե HTTP զոնդերի սպասման ժամանակը սպառվում է կատալոգի/սեղմման բեռնվածության դեպքում. երկու դեպքում էլ **մի՛** դադարեցրեք pod-ը իրադարձությունների ցիկլի կարճատև կանգերի պատճառով |
| **Խորացված առողջություն** | `GET /api/monitoring/health`՝ արտաքին ստուգիչից                                          | Նախատեսված չէ kubelet-ի `livenessProbe`-ի / խիստ `readinessProbe`-ի համար                                                                                                                                                                                                                                                                                                                                                                                           |

Կառուցվածքի օրինակ (շեմերը հարմարեցրեք ձեր սառը մեկնարկին և սեղմման բեռնվածությանը).

```yaml
ports:
  - name: http
    containerPort: 20128
startupProbe:
  httpGet:
    path: /healthz
    port: http
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /healthz
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 6
livenessProbe:
  httpGet:
    path: /livez
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 6
  # Իրադարձությունների ցիկլի կանգի դեպքում HTTP /livez-ի սպասման ժամանակը
  # նույնպես կարող է սպառվել։ TCP-ն պահպանողական այլընտրանքն է.
  # tcpSocket:
  #   port: http
```

kubelet-ի **կենսունակության** ստուգումը **մի՛** ուղղեք դեպի `/api/monitoring/health`։ Այդ ուղին իրական աշխատանք է կատարում ՏԲ-ի/մոնիթորինգի հետ և բեռնվածության պայմաններում կեղծ դրական արդյունք կտա։

Առնչվող՝ [#10052](https://github.com/diegosouzapw/OmniRoute/issues/10052) (զոնդեր, երբ իրադարձությունների ցիկլը զբաղված է), [#9685](https://github.com/diegosouzapw/OmniRoute/issues/9685) / [#10055](https://github.com/diegosouzapw/OmniRoute/pull/10055) (կատալոգի գնագոյացման ռեսուրսակլան աշխատանք), [#10117](https://github.com/diegosouzapw/OmniRoute/issues/10117) (սեղմման թոքենների հաշվարկի ռեսուրսակլան աշխատանք)։

### Հարցման ուղու ընտրովի աշխատանքներ (հիշողություն, հմտություններ, թոքենի թարմացում)

Հիշողության քաղումը, հմտությունների ներարկումը և OAuth թոքենի թարմացումը `/healthz`-ի հետ համատեղ օգտագործում են **Node-ի հիմնական իրադարձությունների ցիկլը**։ Դրանք կառավարման վահանակից փոխարկվող գործառույթներ են (`memoryEnabled`, `skillsEnabled`), այլ ոչ թե աշխատող պրոցեսների ավազան։ Տե՛ս [Միջավայր — իրադարձությունների ցիկլի ծախս](../reference/ENVIRONMENT.md#event-loop-cost-of-memory-skills-and-token-refresh-10349)։

### Մատակարարի առողջություն

> **REST վերջնակետ չկա։** Մատակարարի առողջության տվյալները հասանելի են MCP-ի `observability_snapshot` գործիքի կամ կառավարման վահանակի `/dashboard/providers` էջի միջոցով։

### Մատակարարի մանրամասներ

> **REST վերջնակետ չկա։** Յուրաքանչյուր մատակարարի մանրամասները հասանելի են կառավարման վահանակի `/dashboard/providers` էջի միջոցով։

## Մատակարարի առողջության ավտոպիլոտ

`providerHealthAutopilot.ts` մոդուլը **ինքնավերականգնվող համակարգ** է, որը՝

1. Հայտնաբերում է մատակարարի խնդիրները (շղթայի բաց վիճակ, սպասման ժամանակահատվածներ, արգելափակումներ, քվոտայի նախազգուշացումներ)
2. Ստեղծում է դրանք լուծելու համար **առաջարկվող գործողություններ**
3. Ընտրովի կերպով **ինքնաշխատ կատարում է** ցածր ռիսկով գործողությունները

### Հայտնաբերվող խնդիրների տեսակները

| Խնդրի տեսակ                  | Լրջություն     | Պայմանի օրինակ                             |
| ---------------------------- | -------------- | ------------------------------------------ |
| `provider_circuit_open`      | կրիտիկական     | Շղթայի անջատիչը բաց է 5 ձախողումից հետո    |
| `provider_circuit_half_open` | նախազգուշացում | Շղթան ստուգում է վերականգնումը             |
| `connection_cooldown`        | նախազգուշացում | Միացումը սպասման ռեժիմում է 429-ից հետո    |
| `stale_connection_error`     | նախազգուշացում | Վերջին թարմացումը ձախողվել է 30+ րոպե առաջ |
| `terminal_connection_error`  | կրիտիկական     | OAuth-ը հետ է կանչվել, բանալին անվավեր է   |
| `inactive_connection`        | տեղեկատվական   | Միացումն անջատված է կարգավորումներում      |
| `model_lockout`              | նախազգուշացում | Որոշակի մոդել կարանտինում է                |
| `quota_monitor_warning`      | նախազգուշացում | Քվոտայի օգտագործումը 80%+ է                |

### Ստեղծվող գործողությունների տեսակները

| Գործողություն                  | Ռիսկ  | Նկարագրություն                           |
| ------------------------------ | ----- | ---------------------------------------- |
| `clear_provider_breaker`       | միջին | Շղթայի անջատիչը վերակայել փակ վիճակի     |
| `clear_connection_cooldown`    | ցածր  | Հեռացնել միացման սպասման ժամանակահատվածը |
| `clear_stale_connection_error` | ցածր  | Մաքրել հնացած սխալի դրոշակը              |
| `clear_model_lockout`          | ցածր  | Կրկին միացնել կարանտինում գտնվող մոդելը  |
| `reactivate_connection`        | միջին | Կրկին միացնել ապաակտիվացված միացումը     |
| `deactivate_connection`        | բարձր | Անջատել խնդրահարույց միացումը            |

### API

> **REST վերջնակետ չկա։** Ավտոպիլոտի խնդիրները հասանելի են MCP-ի `observability_snapshot` գործիքի կամ կառավարման վահանակի միջոցով։ Ավտոպիլոտն աշխատում է ներքին մակարդակում․ դրա վարքագիծը կարգավորվում է կարգավորումների DB-ի միջոցով (յուրաքանչյուր միացման `autopilotMode` դաշտով), ոչ թե միջավայրի փոփոխականներով. ավտոպիլոտի ռեժիմի միջավայրի փոփոխականի համար `grep -rn`-ը վերադարձնում է զրո արդյունք։

### Ավտոպիլոտի ռեժիմ

Լռելյայնորեն ավտոպիլոտն աշխատում է **ձեռքով ռեժիմում**․ այն հայտնաբերում է խնդիրները և ստեղծում առաջարկվող գործողություններ, սակայն դրանք ինքնաշխատ չի կիրառում։ Գործողությունները կարելի է կիրառել կառավարման վահանակի միջոցով։

## Համակցությունների առողջության ավտոպիլոտ

`comboHealthAutopilot.ts`-ը մատակարարի ավտոպիլոտի՝ **համակցություններին հատուկ** համարժեքն է։ Այն՝

- Հայտնաբերում է անառողջ համակցությունները
- Առաջարկում է վերադասավորել թիրախները
- Առաջարկում է անջատել չաշխատող թիրախները
- N ձախողումից հետո ինքնաշխատ հեռացնում է չգործող թիրախները

```
├─ Թիրախ 1: openai/gpt-5 (առողջ)
├─ Թիրախ 2: anthropic/claude-opus-4-6 (⚠️ մոդելն արգելափակված է մինչև 14:00)
└─ Թիրախ 3: kiro/claude-sonnet-4-5 (առողջ)

Առաջարկվող գործողություն․ վերադասավորել՝ kiro-ն տեղափոխել anthropic-ից վերև՝ մինչև արգելափակման ավարտը
```

## Քվոտայի մոնիտորներ

`observability.ts`-ը տրամադրում է **յուրաքանչյուր աշխատաշրջանին հատուկ քվոտայի մոնիտորներ** բաժանորդագրային մատակարարների համար (Claude Code, Codex, GitHub Copilot)․

```ts
interface QuotaMonitorSnapshot {
  sessionId: string;
  provider: string;
  accountId: string;
  status: "starting" | "idle" | "healthy" | "warning" | "exhausted" | "error";
  lastQuotaPercent: number | null; // 0-100
  lastQuotaUsed: number | null;
  lastQuotaTotal: number | null;
  lastResetAt: string | null;
  nextPollAt: string | null;
  totalPolls: number;
  totalAlerts: number;
  consecutiveFailures: number;
}
```

### Կարգավիճակների նշանակությունները

| Կարգավիճակ  | Երբ                              | UI գործողություն                                   |
| ----------- | -------------------------------- | -------------------------------------------------- |
| `starting`  | Սկզբնական հարցումն ընթացքի մեջ է | Բեռնման պտտվող ցուցիչ                              |
| `idle`      | Վերջերս ակտիվություն չի եղել     | Թաքցված է կառավարման վահանակից                     |
| `healthy`   | Մնացել է քվոտայի > 50%-ը         | Կանաչ կետ                                          |
| `warning`   | Մնացել է քվոտայի < 50%-ը         | Դեղին նախազգուշացում                               |
| `exhausted` | Քվոտան = 0% է                    | Կարմիր արգելափակում, ուղղորդում հաջորդ մատակարարին |
| `error`     | Հարցումը ձախողվել է              | Կարմիր կետ, շուտով կրկնել                          |

### API

> **REST վերջնակետ չկա։** Քվոտայի մոնիտորի տվյալները հասանելի են MCP-ի `observability_snapshot` գործիքի կամ կառավարման վահանակի միջոցով։

## Թոքենի վիճակի ստուգում

OAuth մատակարարներին (Claude Code, GitHub Copilot, Cursor) անհրաժեշտ է **թոքենների պարբերական թարմացում**։ `src/lib/tokenHealthCheck.ts`-ը գործարկում է ֆոնային ժամանակացույց.

- **Ստուգման ցիկլ**. յուրաքանչյուր 60 վայրկյանը մեկ (`TICK_MS = 60 * 1000` ստուգման ցիկլը՝ `src/lib/tokenHealthCheck.ts:30`-ում)
- **Յուրաքանչյուր կապի վիճակի ստուգման միջակայք**. լռելյայն՝ 60 րոպե (`DEFAULT_HEALTH_CHECK_INTERVAL_MIN = 60`), կարգավորվում է կարգավորումների DB-ի միջոցով
- **Կանխարգելիչ թարմացում 401-ի դեպքում**. մշակվում է յուրաքանչյուր կապի interceptor-ի կողմից

### Թոքենի վիճակի կարգավիճակ

```ts
interface TokenHealth {
  connectionId: string;
  provider: string;
  status: "valid" | "expiring_soon" | "expired" | "refresh_failed";
  expiresAt: string;
  lastRefresh: string;
  nextRefresh: string;
  consecutiveFailures: number;
}
```

### Կազմաձևում

Թոքենի վիճակի ստուգման կազմաձևումը ներքին կերպով մշակվում է `tokenHealthCheck.ts`-ի կողմից։

### Թոքենի վիճակ

> **REST վերջնակետ չկա։** Թոքենի վիճակի տվյալները հասանելի են կառավարման վահանակի կամ MCP-ի `observability_snapshot` գործիքի միջոցով։

## Խնդիրների ախտորոշում

### «Մատակարարը նշված է որպես առողջ, բայց հարցումները ձախողվում են»

1. Ստուգեք **ինքնավար կառավարման խնդիրները**. հնարավոր է՝ որևէ մոդել արգելափակված է
2. Դիտեք **վերջին սխալները**՝ սխալի կոնկրետ դասը պարզելու համար
3. Փորձեք մատակարարի քարտում առկա **կապի ստուգումը**
4. Ստուգեք՝ արդյոք մատակարարը **վերին մակարդակում արագության սահմանափակման տակ է** (տեղային մակարդակում տեսանելի չէ)

### «Քվոտան առողջ է նշված, բայց ես տեսնում եմ 429 սխալներ»

- 429-ը նշանակում է, որ, ըստ մատակարարի, դուք սպառել եք ձեր քվոտան
- OmniRoute-ի քվոտայի հետևման տվյալները կարող են **հնացած** լինել. հավաստի տվյալները գտնվում են մատակարարի կողմում
- Քվոտայի տվյալներն ավտոմատ թարմացվում են ներքին քվոտայի մոնիթորի միջոցով

### «Համակցությունը ձախողվում է, բայց բոլոր թիրախներն առողջ են երևում»

- Թիրախների դասավորման խնդիրների համար ստուգեք **համակցության առողջության** կառավարման վահանակը
- Դիտեք **պահուստային տարբերակին անցնելու իրադարձությունները**. հնարավոր է՝ համակցությունը չափազանց արագ է սպառում բոլոր տարբերակները
- Համոզվեք, որ **ռազմավարությունը** համապատասխանում է ձեր օգտագործման դեպքին (առաջնահերթություն, հերթափոխային բաշխում կամ ավտոմատ)

### «Տվյալների բազայի առողջության ստուգումը ձախողվում է»

- Գործարկեք `sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"`
- Եթե արդյունքը "ok" է՝ սա կեղծ տագնապ է, առողջության ստուգումը չափազանց խիստ է
- Ցանկացած այլ արդյունքի դեպքում **կանգնեցրեք OmniRoute-ը** և հետևեք [աղետից վերականգնման ուղեցույցին](./DATABASE_GUIDE.md#disaster-recovery)

### «Հիշողության կույտի ճնշումը կրիտիկական է»

```bash
# Ստուգեք կույտի ընթացիկ վիճակը
node -e "console.log(process.memoryUsage())"

# Գործարկեք GC-ն ձեռքով (եթե օգտագործվում է --expose-gc)
node --expose-gc -e "global.gc(); console.log(process.memoryUsage())"

# Նվազեցրեք միաժամանակյա հարցումների քանակը (սահմանեք կառավարման վահանակի Settings էջի միջոցով, ոչ թե միջավայրի փոփոխականով)
# `MAX_CONCURRENT_REQUESTS` միջավայրի փոփոխական գոյություն չունի. կազմաձևեք այն Settings → Concurrency բաժնում։
```
