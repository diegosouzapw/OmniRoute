Սկսած v3.8.49-ից (որակի/արագության պլանի WS3.2/WS3.4)՝ վերանայված PR-ները
`release/vX.Y.Z`-ում միավորելու լռելյայն ուղին **Mergify-ի միավորման հերթն** է (`.mergify.yml`),
իսկ ստորև փաստաթղթավորված **ձեռքով կառավարվող միավորման գնացքը** ՊԱՀՈՒՍՏԱՅԻՆ տարբերակն է՝ միջադեպերի,
թողարկման սառեցումների ժամանակ կամ եթե Mergify Open Source պլանը երբևէ փոխվի։

## Լռելյայն ուղի․ Mergify-ի հերթը

1. PR-ը վերանայվում է/ստանում է կանաչ կարգավիճակ արշավների միջոցով և հաստատվում սեփականատիրոջ՝
   միավորումից առաջ գործող ⭐ վերահսկիչ անցակետով (հաշվետվությունը + յուրաքանչյուր տարրի վերաբերյալ որոշումը՝
   տե՛ս `/merge-prs` քայլ 0.75-ը)։
2. Սեփականատերը (կամ սեփականատիրոջ որոշման հիման վրա գործող աշխատաշրջանը) կիրառում է **`queue`**
   պիտակը։ Պիտակը ՀԵՆՑ միավորման հաստատումն է, իսկ Mergify-ն միայն կատարում է այն։
3. Mergify-ն խմբավորում է հերթում գտնվող մինչև 10 PR, ստուգում է խումբը արագ վերահսկիչ
   անցակետերով և միավորում է (squash)։ Կարմիր խումբը **ինքնաբերաբար կիսվում է**․ խնդրահարույց PR-ը
   մեկուսացվում է մոտավորապես log2(N) կրկնակի ստուգումների միջոցով և հեռացվում հերթից, իսկ մնացածը շարունակվում են։
4. Միավորումից հետո անընդհատ release-green աշխատանքային հոսքը push-ի ժամանակ ստուգում է նոր ծայրը
   և բացում է վերագրման խնդիր, եթե համադրությունը հետընթաց է առաջացրել (երբեք ինքնաբերաբար հետ չի շրջում)։

Պաշտպանիչ կանոններ (կրկնում են `CLAUDE.md`-ի խիստ կանոններ #21/#22-ը)․

- **Թողարկման սառեցումը բաց է** → ՄԻ՛ պիտակավորեք սառեցված ճյուղը թիրախավորող PR-ները․ նախ փոխեք
  թիրախը ակտիվ `release/vX+1`-ի։
- **Մեկ այլ աշխատաշրջանի ընթացքի մեջ գտնվող PR** → երբեք մի՛ պիտակավորեք այն․ միայն սեփականատեր աշխատաշրջանն է
  հերթագրում իր աշխատանքը։
- Միայն թեստեր պարունակող տարբերությունները և `hotfix` պիտակով PR-ներն արդեն գործարկում են կրճատված CI (տե՛ս
  `RELEASE_CHECKLIST.md` → Hotfix Fast-Lane)․ հերթի պայմաններն ընդունում են փաստացի գործարկված
  ստուգումների ցանկացած հավաքածու (`#check-failure=0` + `#check-pending=0`)։

## Պահուստային տարբերակ․ ձեռքով կառավարվող միավորման գնացքը

Օգտագործվում է, երբ հերթն անհասանելի է։ Սա կանոնակարգում է այն գործելակերպը, որով v3.8.47 ցիկլի
ընթացքում մեկ օրում մշակվել է 33 PR․

1. **Կազմեք խումբը** (մոտավորապես 10–30 վերանայված+հաստատված PR)։ Ստուգեք `linked:` բախումները
   (նույն `tap.testFiles`, CHANGELOG-ի նույն հատվածները) և դրանք մշակեք հաջորդաբար։
2. **Ստուգեք ՄԵԿ ԱՆԳԱՄ**․ թողարկման ծայրից ստեղծված մեկուսացված worktree-ում տեղային կերպով միավորեք խմբի բոլոր
   head-երը, ապա գործարկեք թողարկմանը համարժեք հավաքածուն
   (`npm run check:release-green`, իսկ թողարկումից առաջ ավելացրեք `--with-build`)։
   `scripts/release/merge-train.sh <base> <PR#>…`-ը ավտոմատացնում է 1–2-րդ քայլերը (բախվող
   PR-ները հեռացվում են, գնացքը շարունակում է)։ Ամբողջական ռեժիմը գործարկում է `npm run test:unit`՝
   մեքենայի համար օպտիմալացված գործարկիչը (`--test-concurrency=20`), **ոչ թե** CI-ի երկու հաջորդական 4-միջուկանի
   shard-երը, որոնք գերիշխող փուլում օգտագործում էին 16-միջուկանի մեքենայի մոտ 25%-ը (շտկվել է
   2026-07-18-ին)։ `--fast`-ը (նույն օրվա ընթացքում mega-train-ների մշակման համար, սեփականատիրոջ կողմից հաստատված՝ 2026-07-18-ին)
   պահպանում է յուրաքանչյուր ստատիկ վերահսկիչ անցակետը + vitest-ը, բայց գործարկում է միայն գնացք ներառված PR-ների կողմից
   փոփոխված node:test ֆայլերը․ ԱՄԲՈՂՋԱԿԱՆ հավաքածուն, միևնույն է, պետք է առնվազն օրական մեկ անգամ գործարկվի
   կուտակված ծայրի վրա (մեկ գնացք՝ առանց `--fast`-ի)։
3. **Կանաչ** → հերթականությամբ միավորեք PR-ները (յուրաքանչյուրից առաջ կրկին ստուգելով `state,headRefOid`-ը․
   PR-ը, որի head-ը տեղաշարժվել է, վերադառնում է վերանայման փուլ)։ Ապացուցեք, որ յուրաքանչյուր միավորման զուտ տարբերությունը
   հենց տվյալ PR-ի փոփոխությունն է (չկան ինքնալուծման հետևանքով հետշրջումներ․ ստուգեք `git diff --stat`-ը՝
   շրջանակից դուրս ջնջումների համար)։
4. **Կարմիր** → բաժանեք խումբը կեսերի (ստուգեք յուրաքանչյուր կեսը)՝ մեկ առ մեկ կրկին ստուգելու փոխարեն․
   խնդրահարույց PR-ը ապացույցների հետ վերադարձրեք վերանայման հերթ։
5. **Երբեք**․ սառեցման ժամանակ մի՛ միավորեք սառեցված ճյուղում, որևէ տեղ մի՛ օգտագործեք `git stash`,
   և մի՛ վերագործարկեք ամբողջ CI-ն՝ հուսալով, որ կարմիրը կվերանա (կանոն․ կարմիրը տեղեկություն է)։

## Մակարդակավորում (ինչու է հերթն անվտանգ միայն արագ վերահսկիչ անցակետերով)

- **Յուրաքանչյուր PR-ի համար** (quality.yml-ի արագ վերահսկիչ անցակետեր)․ TIA-ի ազդեցության տակ գտնվող թեստեր + ամբողջական unit 4-shard +
  vitest + lint հավաքածու + typecheck + փաստաթղթերի/փոփոխությունների մատյանի ամբողջականություն։
- **Յուրաքանչյուր խմբի/ծայրի համար** (անընդհատ release-green)․ `--quick` ԿՈՇՏ վերահսկիչ անցակետեր թողարկման
  ճյուղի յուրաքանչյուր push-ի ժամանակ, ամբողջական `--with-build --full-ci` ստուգումներ՝ օրական 3 անգամ։
- **Յուրաքանչյուր թողարկման համար** (ci.yml-ը թողարկման PR-ում)․ ամբողջական մատրիցը՝ ներառյալ E2E ×9,
  package-artifact + tarball boot-smoke, coverage/ratchets։

Ոչինչ չի ստուգվում նախկինից պակաս․ ծանր մակերեսը պարզապես գործարկվում է յուրաքանչյուր խմբի/ծայրի համար՝
յուրաքանչյուր PR-ի փոխարեն, և հենց դա է վերացնում O(N) կրկնակի շրջափուլերը։
