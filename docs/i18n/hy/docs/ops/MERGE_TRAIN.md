v3.8.49-ից սկսած (որակի/արագության պլանի WS3.2/WS3.4) վերանայված PR-ները
`release/vX.Y.Z`-ում միավորելու լռելյայն ուղին **Mergify-ի միավորման հերթն** է (`.mergify.yml`);
ստորև փաստագրված **ձեռքով կառավարվող միավորման գնացքը** ՊԱՀԵՍՏԱՅԻՆ ՏԱՐԲԵՐԱԿ է՝ կիրառվող միջադեպերի,
թողարկման սառեցումների ժամանակ կամ եթե Mergify Open Source պլանը երբևէ փոխվի։

## Լռելյայն ուղի՝ Mergify-ի հերթը

1. PR-ը ստուգվում/կանաչ կարգավիճակ է ստանում արշավների կողմից և հաստատվում է սեփականատիրոջ՝ միաձուլումից առաջ կիրառվող ⭐
   անցակետով (հաշվետվությունը + յուրաքանչյուր տարրի վերաբերյալ որոշումը՝ տե՛ս `/merge-prs`-ի քայլ 0.75-ը)։
2. Սեփականատերը (կամ սեփականատիրոջ որոշման հիման վրա գործող աշխատաշրջանը) կիրառում է **`queue`**
   պիտակը։ Այդ պիտակն ԻՆՔՆԻՆ միաձուլման հաստատումն է. Mergify-ն միայն կատարում է այն։
3. Mergify-ն հերթում գտնվող PR-ները վավերացնում է **հաջորդաբար** (միաժամանակ՝ մեկական)՝ արագ անցակետերի
   նկատմամբ, ապա միաձուլում է (squash)։ Խմբաքանակավորումը + ավտոմատ երկատումը հասանելի են Mergify-ի վճարովի մակարդակում
   («Cannot use Merge Queue batch»՝ անվճար պլանում, #7220), ուստի `.mergify.yml`-ում
   `batch_size` սահմանված չէ. խմբաքանակավորումը մնում է ստորև նկարագրված ձեռքով կառավարվող միաձուլման գնացքի խնդիրը։ Այն PR-ը, որի
   ստուգումները `checks_timeout`-ից հետո դեռ ընթացքի մեջ են (240 րոպե = `quality.yml`-ի
   չափված p95-ի 2×-ը), հեռացվում է հերթից՝ այն կանգնեցնելու փոխարեն։
4. Միաձուլումից հետո անընդհատ release-green աշխատահոսքը push-ի ժամանակ վավերացնում է նոր գագաթը
   և վերագրման issue է բացում, եթե համակցությունը հետընթաց է գրանցել (երբեք ավտոմատ հետադարձում չի կատարում)։

Պաշտպանիչ սահմանափակումներ (`CLAUDE.md`-ի Խիստ կանոններ #21/#22-ի արտացոլումը).

- **Թողարկման սառեցումն ակտիվ է** → ՄԻ՛ պիտակավորեք սառեցված ճյուղը թիրախավորող PR-ները. նախ փոխեք թիրախը
  ակտիվ `release/vX+1`-ի։
- **Մեկ այլ աշխատաշրջանի ընթացքի մեջ գտնվող PR** → երբեք մի՛ պիտակավորեք այն. միայն սեփականատեր աշխատաշրջանն է հերթագրում
  իր աշխատանքը։
- Միայն թեստեր պարունակող տարբերությունները և `hotfix` պիտակով PR-ներն արդեն գործարկում են կրճատված CI (տե՛ս
  `RELEASE_CHECKLIST.md` → Hotfix Fast-Lane). հերթի պայմաններն ընդունում են փաստացի գործարկված
  ստուգումների ցանկացած հավաքածու (`#check-failure=0` + `#check-pending=0`)։

## Պահեստային տարբերակ՝ ձեռքով կառավարվող միավորման գնացքը

Օգտագործվում է, երբ հերթը հասանելի չէ։ Սա կանոնակարգում է այն գործելակերպը, որով v3.8.47 ցիկլի
ընթացքում մեկ օրում մշակվել է 33 PR.

1. **Կազմեք խումբը** (մոտ 10–30 վերանայված+հաստատված PR)։ Ստուգեք `linked:` բախումները
   (նույն `tap.testFiles`, CHANGELOG-ի նույն հատվածները) և դրանք մշակեք հաջորդաբար։
2. **Ստուգեք ՄԵԿ ԱՆԳԱՄ**. թողարկման վերջնակետից ստեղծված մեկուսացված worktree-ում տեղային եղանակով միավորեք խմբի բոլոր
   head-երը, ապա գործարկեք թողարկմանը համարժեք հավաքածուն
   (`npm run check:release-green`, թողարկումից առաջ ավելացրեք `--with-build`)։
   `scripts/release/merge-train.sh <base> <PR#>…`-ն ավտոմատացնում է 1–2 քայլերը (բախվող
   PR-ները դուրս են մղվում, իսկ գնացքը շարունակում է աշխատանքը)։ Ամբողջական ռեժիմը գործարկում է `npm run test:unit`՝
   տվյալ մեքենայի համար կարգավորված գործարկիչը (`--test-concurrency=20`), **ոչ թե** հաջորդաբար աշխատող երկու 4-միջուկանի CI
   հատվածները, որոնց պատճառով գերակշռող փուլն օգտագործում էր 16-միջուկանի մեքենայի մոտ 25%-ը (շտկվել է
   2026-07-18-ին)։ `--fast`-ը (մեկ օրվա ընթացքում մեգա-գնացքների մշակում, սեփականատիրոջ կողմից հաստատված 2026-07-18-ին)
   պահպանում է բոլոր ստատիկ անցակետերը + vitest-ը, սակայն գործարկում է միայն նստեցված PR-ների կողմից փոփոխված
   node:test ֆայլերը. ԱՄԲՈՂՋԱԿԱՆ հավաքածուն, այնուամենայնիվ, պետք է օրական առնվազն մեկ անգամ գործարկվի
   կուտակված վերջնակետի վրա (մեկ գնացք՝ առանց `--fast`-ի)։
3. **Կանաչ** → հերթականությամբ միավորեք PR-ները (յուրաքանչյուրից առաջ կրկին ստուգելով `state,headRefOid`-ը.
   PR-ը, որի head-ը փոխվել է, վերադառնում է վերանայման)։ Ապացուցեք, որ յուրաքանչյուր միավորման զուտ տարբերությունը
   տվյալ PR-ի սեփական փոփոխությունն է (չկան ինքնալուծմամբ կատարված հետշրջումներ. ստուգեք `git diff --stat`-ը՝
   շրջանակից դուրս ջնջումների հայտնաբերման համար)։
4. **Կարմիր** → խումբը բաժանեք երկու մասի (ստուգեք յուրաքանչյուր կեսը)՝ մեկ առ մեկ կրկնակի ստուգելու
   փոխարեն. խնդրահարույց PR-ը ապացույցների հետ վերադարձրեք վերանայման հերթ։
5. **Երբեք մի՛ արեք հետևյալը**. սառեցման ժամանակ միավորել սառեցված ճյուղի մեջ, որևէ տեղում կիրառել `git stash`,
   համատարած վերագործարկել CI-ն՝ հուսալով, որ կարմիր կարգավիճակը կվերանա (կանոն՝ կարմիրը տեղեկատվություն է)։

## Մակարդակավորում (ինչու է հերթն անվտանգ միայն արագ անցակետերով)

- **Յուրաքանչյուր PR-ի համար** (quality.yml-ի արագ անցակետեր). TIA-ի ազդեցությանը ենթարկված թեստեր + ամբողջական unit 4-shard +
  vitest + lint փաթեթ + typecheck + փաստաթղթերի/changelog-ի ամբողջականություն։
- **Յուրաքանչյուր խմբի/վերջնակետի համար** (շարունակական release-green). `--quick` ԿՈՇՏ անցակետեր թողարկման ճյուղի յուրաքանչյուր push-ի ժամանակ.
  ամբողջական `--with-build --full-ci` ստուգումներ՝ օրական 3 անգամ։
- **Յուրաքանչյուր թողարկման համար** (ci.yml-ը թողարկման PR-ում). ամբողջական մատրիցը՝ ներառյալ E2E ×9-ը,
  package-artifact + tarball boot-smoke-ը, coverage/ratchets-ը։

Նախկինի համեմատ ոչինչ ավելի քիչ չի ստուգվում. ծանր մակերեսը պարզապես գործարկվում է յուրաքանչյուր խմբի/վերջնակետի,
այլ ոչ թե յուրաքանչյուր PR-ի համար, ինչն էլ վերացնում է O(N) հետադարձ փուլերը։

## Նոր checkout-ի նախապայմանները `merge-train.sh`-ի համար

Սկրիպտը հիմնական checkout-ում (նախքան worktree-ի հետ որևէ աշխատանք) գործարկում է սխալի դեպքում անմիջապես դադարող
**նախնական ստուգում**, որպեսզի խափանված տեղադրումը երբեք չներկայանա որպես կարմիր գնացք.

1. `npm ci`, ապա գործարկեք `bun`-ի այն postinstall-ը, որն արգելափակում է npm-ը.
   `(cd node_modules/bun && node install.js)` — հակառակ դեպքում `check:provider-consistency`-ն
   ու `check:known-symbols`-ը (երկուսն էլ՝ `bun scripts/…`) ձախողվում են ԵՎ՛ գնացքի, ԵՎ՛ հիմքի վրա՝
   առանց խախտման տողի։
2. Չպետք է լինի կողմնակի `node_modules/node_modules` (կրկնօրինակ կախվածությունների ծառ. React-ը բեռնվում է երկու անգամ,
   և UI vitest հավաքածուներն անմիջապես ձախողվում են)։
3. `node_modules/.bin/tsc`-ն առկա է և գործարկելի է (մասնակի տեղադրման դեպքում այն բացակայում է)։

Գնացքը գործարկում է արգելափակող `npm run check:cycles:ratchet`-ը. սովորական `npm run check:cycles`-ը
խորհրդատվական է (այն ցուցադրում է SCC-ները և ավարտվում ոչ զրոյական կոդով նույնիսկ առողջ հիմքի վրա)։
