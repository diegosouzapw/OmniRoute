Օգտագործեք այս ուղեցույցը՝ pull request-ի համար ամենափոքր հուսալի մշակման ցիկլն ընտրելու նպատակով։ Այն չի
փոխարինում ստորև հղված՝ առանձին ոլորտներին վերաբերող ճարտարապետական և անվտանգության փաստաթղթերին․ այն կապում է յուրաքանչյուր տարածված
փոփոխության տեսակը դրա պայմանագրերի, նպատակային ստուգումների և CI ծածկույթի հետ։

## Յուրաքանչյուր փոփոխության անցած ուղին

1. **Ընտրեք բազային ճյուղը՝ նախքան խմբագրելը։** Գտեք ամենաբարձր ակտիվ `release/v*` ճյուղը և ստեղծեք նոր ճյուղ
   դրա վերջին commit-ից։ Որպես թիրախ ընտրեք այդ ճյուղը, ոչ թե `main`-ը։ Եթե թողարկման սառեցումն ակտիվ է, որպես թիրախ մի ընտրեք սառեցված
   ճյուղը․ օգտագործեք հաջորդ ակտիվ ցիկլը, որը նկարագրված է
   [Ճյուղավորման և թողարկման մոդելում](BRANCHING_MODEL.md)։
2. **Նշեք պայմանագրերը։** Բացահայտեք յուրաքանչյուր կատալոգ, սխեմա, գեներացված արտեֆակտ, հանրային API կամ օգտատիրոջ
   միջերես, որի վրա ազդում է փոփոխությունը։ Ստորև բերված աղյուսակը ներկայացնում է նվազագույն մեկնարկային հավաքածուն։
3. **Գրեք կամ թարմացրեք նպատակային թեստերը։** `src/`, `open-sse/`, `electron/` կամ
   `bin/` պանակներում արտադրական կոդի փոփոխությունները պահանջում են ավտոմատացված թեստ նույն PR-ում։ Գործարկեք վարքագիծը հաստատող
   ամենափոքր թեստային ֆայլերը, այնուհետև՝ նշված նպատակային ստուգումները։
4. **Թույլ տվեք CI-ին գործարկել լայն մատրիցը։** Ամբողջական unit shard-երը, Vitest-ը, ծածկույթի շեմի վերահսկումը և
   արտադրական build-ը գործարկվում են PR-ում։ Լայն թեստային հավաքածուն տեղային միջավայրում գործարկեք միայն այն դեպքում, երբ նպատակային ձախողումը ցույց է տալիս
   ավելի լայն ազդեցություն, կամ երբ փոփոխությունն ընդգրկում է մի քանի ենթահամակարգ։
5. **Համաձայնեցրեք փոփոխությունները վերանայումից առաջ։** Ներբեռնեք ակտիվ բազային ճյուղի թարմացումները, ուսումնասիրեք դրա նոր commit-ները և ձեր տարբերությունները
   դրա նկատմամբ, ապա կատարեք rebase կամ merge՝ համաձայն ներդրողների աշխատանքային հոսքի։ Գեներացված ֆայլերի
   և կատալոգների հակասությունները լուծեք դրանց սկզբնաղբյուրում, վերագեներացրեք դրանք, կրկին գործարկեք նպատակային ցիկլը և համոզվեք, որ
   PR-ը դեռևս թիրախավորում է ակտիվ թողարկման ճյուղը։
6. **Գրանցեք ապացույցները։** PR-ի ձևանմուշում նշեք գործարկված հրամանները, ավելացված կամ փոփոխված յուրաքանչյուր թեստային ֆայլը,
   միգրացիաները կամ feature flag-երը և միայն CI-ում կատարվելիք՝ դեռևս սպասվող վավերացումները։

## Հիմնական ուղիներն ըստ փոփոխության տեսակի

Ստորև բերված հրամանները նվազագույն նպատակային ստուգումներ են, այլ ոչ թե թույլտվություն՝ բաց թողնելու այն թեստը, որն ուղղակիորեն ծածկում է ձեր
փոփոխած վարքագիծը։

### Մատակարար

**Պայմանագրեր**

- Մատակարարի սահմանումը `src/shared/constants/providers/` պանակում և դրա կազմավորումը
  `src/shared/constants/providers.ts` ֆայլում։
- Մոդելներն ու հնարավորությունները `open-sse/config/providerRegistry.ts` ֆայլում կամ դրանից առանձնացված ռեեստրի ֆայլերում։
- Executor/translator-ի ընտրությունը, OAuth-ի կամ API key-ի կազմաձևումը, կառավարման վահանակի ռեսուրսները և գեներացված
  մատակարարի տեղեկատուն՝ կիրառելի լինելու դեպքում։
- Հանրային հավատարմագրերը պետք է օգտագործեն `resolvePublicCred()`-ը, իսկ սխալների պատասխանները՝ ընդհանուր մաքրված
  սխալների օգնականները։ Տե՛ս `docs/security/PUBLIC_CREDS.md` (git-ում է, չի կոմպիլացվում `/docs`-ում) և
  [Սխալների մաքրում](../security/ERROR_SANITIZATION.md)։

**Նպատակային ցիկլ**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # երբ կատալոգը փոխվում է․ ներառեք գեներացված տարբերությունը commit-ում
npm run lint
```

Թեստավորեք նաև յուրաքանչյուր ազդեցություն կրած հարցումների ընտանիքը՝ chat, Responses, images, embeddings, audio կամ video։
Գեներացված կատալոգի և golden տարբերությունները վերանայեք որպես պայմանագրային փոփոխություններ․ դրանք կուրորեն մի ընդունեք։

### Ուղղորդում

**Պայմանագրեր**

- Հանրային ռազմավարությունների արժեքները և UI մետատվյալները `src/shared/constants/routingStrategies.ts` ֆայլում։
- Ուղարկումն ու հերթականությունը `open-sse/services/combo.ts` ֆայլում և `open-sse/services/combo/` պանակում։
- Combo սխեմաները, պահպանումը, դիմակայունության վիճակը, մոդելների հնարավորությունները և API/UI կառավարիչները։
- [Auto-Combo շարժիչը](../routing/AUTO-COMBO.md) և դիմակայունության փաստաթղթերը, երբ վարքագիծը փոխվում է։

**Նպատակային ցիկլ**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ռազմավարության կամ ուղարկման փոփոխություններ
npm run check:known-symbols      # ռազմավարության գրանցման փոփոխություններ
npm run lint
```

Տեղային միջավայրում օգտագործեք վերին հոսքի deterministic mock-երով թեստեր։ Live combo smoke թեստերը հավատարմագրեր են պահանջում և
ձեռքով են կատարվում․ դրանք չեն փոխարինում CI-ին։

### UI / UX

**Պայմանագրեր**

- Next.js route/page-ը և ընդհանուր component-ների սահմանները `src/app/` և
  `src/shared/components/` պանակներում։
- API պատասխանների կառուցվածքները, բեռնման/դատարկ/սխալի վիճակները, ստեղնաշարի և էկրանի ընթերցիչի վարքագիծը,
  արձագանքող դասավորությունը, թեմաները և տեղայնացումների ընդլայնումը։
- UI-ի անգլերեն սկզբնաղբյուր տողերը `src/i18n/messages/en.json` ֆայլում․ մի՛ գրեք օգտատիրոջը ցուցադրվող նոր տեքստը անմիջապես կոդում։

**Նպատակային ցիկլ**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Փոխազդեցության կամ տեսողական փոփոխությունների դեպքում գործարկեք հավելվածը և ստուգեք ինչպես նեղ, այնպես էլ լայն դիտման տիրույթներում։ CI-ը գործարկում է
արտադրական build-ը և ավելի լայն թեստային հավաքածուները, սակայն տեսողական վարքագիծը դեռևս պահանջում է փոփոխությանը համապատասխան նպատակային component-ի, Playwright-ի
կամ փաստաթղթավորված ձեռքով ստուգում։

### i18n

**Պայմանագրեր**

- `src/i18n/messages/en.json`-ը UI-ի սկզբնաղբյուրն է, իսկ `config/i18n.json`-ը՝ locale-ների սկզբնաղբյուրը։
- CLI կատալոգներն առանձին են գտնվում `bin/cli/locales/` պանակում։
- Պահպանեք ICU placeholder-ներն ու tag-երը ճշգրտորեն։ Մի թարգմանեք ապրանքների/մատակարարների/մոդելների անունները,
  protocol-ների և header-ների անունները, հրամանները, code/JSON identifier-ները, URL-ները, environment variable-ները կամ
  պաշտպանված եզրույթները, ինչպիսիք են `OmniRoute`, `OAuth`, `MCP` և `A2A`։ Ընթացիկ սկզբնաղբյուր ցանկը գտնվում է
  `scripts/i18n/glossary/protected-terms.json` ֆայլում։

**Նպատակային ցիկլ**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # երբ CLI տողերը/կատալոգները փոխվում են
npm run lint
```

Սա գործող համակարգի ուղեցույց է, ոչ թե դրա գործիքակազմը կամ key model-ը ընդլայնելու հրավեր։
i18n patch-երը պահեք հնարավորինս սահմանափակ, քանի դեռ փոխարինող համակարգը նախագծվում է։ Մի գործարկեք արտաքին ծառայություններ
կանչող թարգմանության հրամաններ, եթե առաջադրանքը հստակորեն չի պահանջում գեներացված թարգմանություններ, և դուք չեք
վերանայել ստացված տարբերությունը։

### CLI

**Պայմանագրեր**

- `bin/cli/`-ի հանրային հրամաններն ու դրոշակները, գեներացված API հրամանները, ելքի կոդերը, stdout/stderr-ը և
  JSON ելքի կառուցվածքները, կարգավորումների/միջավայրի վարքագիծը և փաթեթավորված ֆայլերը։
- CLI-ի՝ օգտատիրոջը ցուցադրվող տողերը պետք է օգտագործեն CLI i18n շերտը, իսկ `en`/`pt-BR` կատալոգները պետք է համահունչ մնան։
- Պահպանեք Node-ը որպես աջակցվող գործարկման միջավայր և հրապարակված բինար ֆայլի պայմանագիրը։

**Կենտրոնացված ցիկլ**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # գեներացված/փաթեթավորված CLI-ի փոփոխություններ
npm run check:pack-policy     # փաթեթի հանրային մակերեսի փոփոխություններ
npm run lint
```

Օգտագործեք ճշգրիտ հրամանը տվյալների ժամանակավոր գրացուցակում, երբ վարքագիծը կախված է վերլուծումից, ֆայլերից կամ ելքի
կարգավիճակից։ CI-ն կատարում է փաթեթի արտեֆակտների և էկոհամակարգի ավելի լայն ստուգումները։

### Տվյալների բազա

**Պայմանագրեր**

- Դոմենային մոդուլները գտնվում են `src/lib/db/`-ում․ ներմուծեք կոնկրետ մոդուլներն անմիջապես (`localDb.ts`-ի հին վերաարտահանման շերտը հեռացվել է)։
- Համարակալված, իդեմպոտենտ SQL միգրացիաները՝ `src/lib/db/migrations/`-ում, տրանզակցիաների անվտանգությունը, թարմացման
  վարքագիծը, ինդեքսները և սխեմայից ազդված յուրաքանչյուր կանչող։
- Երթուղիներն ու մշակիչները երբեք անմիջապես raw SQL չեն կատարում։

**Կենտրոնացված ցիկլ**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Միգրացիա ավելացնելիս թեստավորեք թե՛ նոր տվյալների բազան, թե՛ նախորդ սխեմայից թարմացումը։ Տվյալների բազայի թեստերը
մաքրման ընթացքում պետք է փակեն հենդլները և կանչեն `resetDbInstance()`։ Գործարկեք `npm run test:bun:db` միայն այն դեպքում,
երբ փոխվում է Bun ադապտերի՝ լավագույն ջանքով աջակցվող ուղին․ Node-ը մնում է հեղինակավոր։

### Կառուցում / տեղակայում

**Պայմանագրեր**

- Արմատային և աշխատանքային տարածքների մանիֆեստները/կողպման ֆայլը, `scripts/build/`-ը, Next.js-ի ինքնուրույն հավաքումը, `dist/`
  փաթեթի բովանդակությունը, Electron հարթակի մետատվյալները, CI աշխատանքային հոսքերը և տեղակայման սենտինելները։
- Node-ի աջակցվող միջակայքերը և `CLAUDE.md`-ում Bun-ի՝ թույլատրված ցանկում ներառված օգտագործումը պետք է անփոփոխ մնան։
- Կառուցման արտեֆակտները չեն ներառվում տարբերակների վերահսկման մեջ․ կիրառվում են կախվածությունների, արտոնագրերի, աշխատանքային հոսքերի և փաթեթների քաղաքականությունները։

**Կենտրոնացված ցիկլ**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # կախվածության կամ կողպման ֆայլի փոփոխություններ
npm run check:pack-policy      # հրապարակված փաթեթի մակերեսի փոփոխություններ
npm run lint
```

Օգտագործեք `npm run build` տեղային միջավայրում միայն այն դեպքում, երբ փոփոխությունն ազդում է կոմպիլյացիայի, ինքնուրույն հավաքման, ռեսուրսների
կամ գործարկման ժամանակի փաթեթավորման վրա։ Օգտագործեք `npm run build:release` միայն թողարկման/տեղակայման վավերացման համար։ CI-ի կառուցումը
վերջնական միջհարթակային ազդանշանն է․ Electron-ի՝ հարթակին հատուկ փոփոխությունները պահանջում են համապատասխան կենտրոնացված կառուցման
կամ smoke թեստի ապացույց։

## Տեղային ցիկլն ընդդեմ CI-ի

| Յուրաքանչյուր փոփոխության համար տեղային գործարկում                                                  | CI-ն ապահովում է լայնածավալ ազդանշանը                                                                  |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Վերոնշյալ վարքագծի ուղիղ թեստերը և կատեգորիայի ստուգիչները                                          | Մասերի բաժանված ամբողջական մոդուլային թեստերի հավաքածուն և հաջորդական թեստերը                          |
| `npm run lint`                                                                                      | Vitest թեստային հավաքածուները և ծածկույթի/որակի աստիճանական շեմերը                                     |
| Տիպերի ստուգում կամ կառուցում՝ միայն երբ դա պահանջում է ազդակիր պայմանագիրը                         | Արտադրական կառուցման, անվտանգության, փաստաթղթերի, կախվածությունների և PR-ի քաղաքականության ստուգիչները |
| Ձեռքով փոխազդեցության/աշխատանքային ստուգումներ՝ միայն երբ ավտոմատացումը չի կարող հաստատել վարքագիծը | Աշխատանքային հոսքով կազմաձևված՝ առաջադրանքների միջև ինտեգրման և հարթակի ստուգումները                   |

Կանաչ արդյունքով թիրախային ցիկլը փոխված պայմանագրի վերաբերյալ ապացույց է, այլ ոչ թե երաշխիք, որ միմյանց հետ կապ չունեցող CI ստուգումները
կանցնեն։ Մյուս կողմից՝ մի ստիպեք, որ յուրաքանչյուր տեղային խմբագրում սպասի պահոցի ամբողջական մատրիցի ավարտին։

## Համապատասխանեցման ստուգացանկ

Նախքան վերանայում խնդրելը՝

- Հաստատեք, որ PR-ի բազային ճյուղը դեռևս ամենաբարձր ակտիվ `release/v*` ճյուղն է։
- Ներբեռնեք այդ բազային ճյուղի փոփոխությունները և վերանայեք ձեր ճյուղավորման պահից ի վեր ավելացված commit-ները։
- Ստուգեք `git diff <active-base>...HEAD`-ը՝ պատահական կամ գեներացված ավելորդ փոփոխությունների համար։
- Լուծեք կատալոգի և գեներացված փաստաթղթերի հակասությունները՝ թարմացնելով աղբյուրը և վերագեներացնելով արդյունքը։
- Համապատասխանեցումից հետո կրկին գործարկեք PR-ի նկարագրության մեջ նշված յուրաքանչյուր թիրախային թեստ/ստուգիչ։
- Երբեք մի թուլացրեք ստուգման պայմանները կամ մի հեռացրեք պարտադիր թեստերը՝ պարզապես փոփոխված բազային ճյուղին համապատասխանելու համար։

Թողարկման սառեցման և վերահասցեավորման կանոնների համար օգտագործեք
[Ճյուղավորման և թողարկման մոդելը](BRANCHING_MODEL.md)։ CI-ի ամբողջական ցանկի համար օգտագործեք
[Որակի ստուգիչների տեղեկատուն](../architecture/QUALITY_GATES.md)։
