Օգտագործեք այս ուղեցույցը՝ pull request-ի համար մշակման ամենափոքր հուսալի ցիկլն ընտրելու նպատակով։ Այն չի
փոխարինում ստորև հղված՝ առանձին ոլորտներին վերաբերող ճարտարապետական և անվտանգության փաստաթղթերին․ այն կապում է փոփոխությունների յուրաքանչյուր տարածված
տեսակն իր պայմանագրերի, նպատակային ստուգումների և CI ծածկույթի հետ։

## Յուրաքանչյուր փոփոխության անցած ուղին

1. **Խմբագրելուց առաջ ընտրեք բազային ճյուղը։** Գտեք ամենաբարձր ակտիվ `release/v*` ճյուղը և ստեղծեք նոր ճյուղ
   դրա վերջին commit-ից։ Որպես թիրախ ընտրեք այդ ճյուղը, ոչ թե `main`-ը։ Եթե թողարկման սառեցում է գործում, որպես թիրախ մի ընտրեք սառեցված
   ճյուղը․ օգտագործեք հաջորդ ակտիվ ցիկլը, որը նկարագրված է
   [Ճյուղավորման և թողարկման մոդելում](BRANCHING_MODEL.md)։
2. **Նշեք պայմանագրերը։** Որոշեք յուրաքանչյուր կատալոգ, սխեմա, գեներացված արտեֆակտ, հանրային API կամ օգտատիրոջ
   միջերես, որի վրա ազդում է փոփոխությունը։ Ստորև բերված աղյուսակը ներկայացնում է նվազագույն մեկնարկային հավաքածուն։
3. **Գրեք կամ թարմացրեք նպատակային թեստերը։** `src/`, `open-sse/`, `electron/` կամ
   `bin/` պանակներում արտադրական փոփոխությունները պահանջում են ավտոմատացված թեստ նույն PR-ում։ Գործարկեք վարքագիծը հաստատող ամենափոքր թեստային ֆայլերը,
   այնուհետև՝ թվարկված նպատակային ստուգումները։
4. **Թույլ տվեք CI-ին գործարկել լայն մատրիցը։** Ամբողջական unit shard-երը, Vitest-ը, ծածկույթի սահմանաչափի ստուգումը և
   արտադրական build-ը գործարկվում են PR-ում։ Լայն թեստային փաթեթը տեղային միջավայրում գործարկեք միայն այն դեպքում, երբ նպատակային ձախողումը ցույց է տալիս
   ավելի լայն ազդեցություն, կամ երբ փոփոխությունն ընդգրկում է մի քանի ենթահամակարգ։
5. **Համապատասխանեցրեք մինչև վերանայումը։** Ներբեռնեք ակտիվ բազային ճյուղը, ստուգեք դրա նոր commit-ները և դրա նկատմամբ ձեր diff-ը,
   ապա rebase կամ merge կատարեք բազային ճյուղը՝ համաձայն ներդրողների աշխատանքային հոսքի։ Գեներացված ֆայլերի
   և կատալոգների կոնֆլիկտները լուծեք դրանց սկզբնաղբյուրում, կրկին գեներացրեք դրանք, վերագործարկեք նպատակային ցիկլը և հաստատեք, որ
   PR-ը դեռ ուղղված է ակտիվ թողարկման ճյուղին։
6. **Գրանցեք ապացույցները։** PR ձևանմուշում թվարկեք գործարկված հրամանները, ավելացված կամ փոփոխված յուրաքանչյուր թեստային ֆայլ,
   միգրացիաները կամ ֆունկցիոնալ դրոշները և միայն CI-ում կատարվող՝ դեռևս սպասվող ցանկացած վավերացում։

## Հիմնական ուղիներն ըստ փոփոխության տեսակի

Ստորև բերված հրամանները նվազագույն նպատակային ստուգումներ են և թույլտվություն չեն՝ բաց թողնելու ձեր փոխած
վարքագիծն ուղղակիորեն ծածկող թեստը։

### Մատակարար

**Պայմանագրեր**

- Մատակարարի սահմանումը `src/shared/constants/providers/`-ում և դրա կազմավորումը
  `src/shared/constants/providers.ts`-ում։
- Մոդելներն ու հնարավորությունները `open-sse/config/providerRegistry.ts`-ում կամ դրանից առանձնացված ռեեստրի ֆայլերում։
- Executor/translator-ի ընտրությունը, OAuth-ի կամ API key-ի կազմաձևումը, dashboard-ի ռեսուրսները և գեներացված
  մատակարարի տեղեկատուն՝ կիրառելիության դեպքում։
- Հանրային հավատարմագրերը պետք է օգտագործեն `resolvePublicCred()`-ը, իսկ սխալի պատասխանները՝ ընդհանուր սանիտիզացված
  սխալի օգնականները։ Տե՛ս `docs/security/PUBLIC_CREDS.md` (git-ում է, չի կոմպիլացվում `/docs`-ում) և
  [Սխալների սանիտիզացումը](../security/ERROR_SANITIZATION.md)։

**Նպատակային ցիկլ**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # երբ կատալոգը փոխվում է․ commit արեք գեներացված diff-ը
npm run lint
```

Թեստավորեք նաև յուրաքանչյուր ազդված հարցումների խումբ՝ chat, Responses, images, embeddings, audio կամ video։
Գեներացված կատալոգի և golden diff-երը վերանայեք որպես պայմանագրային փոփոխություններ․ մի ընդունեք դրանք առանց ստուգելու։

### Երթուղավորում

**Պայմանագրեր**

- Հանրային ռազմավարության արժեքները և UI մետատվյալները `src/shared/constants/routingStrategies.ts`-ում։
- Ուղարկումն ու հերթականությունը `open-sse/services/combo.ts`-ում և `open-sse/services/combo/`-ում։
- Combo սխեմաները, պահպանումը, դիմակայունության վիճակը, մոդելի հնարավորությունները և API/UI կառավարման տարրերը։
- [Auto-Combo շարժիչը](../routing/AUTO-COMBO.md) և դիմակայունության փաստաթղթերը, երբ վարքագիծը փոխվում է։

**Նպատակային ցիկլ**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ռազմավարության կամ ուղարկման փոփոխություններ
npm run check:known-symbols      # ռազմավարության գրանցման փոփոխություններ
npm run lint
```

Տեղային միջավայրում օգտագործեք կանխորոշելի, նմանակված upstream-ով թեստեր։ Կենդանի combo smoke թեստերը հավատարմագրեր են պահանջում և
կատարվում են ձեռքով․ դրանք չեն փոխարինում CI-ին։

### UI / UX

**Պայմանագրեր**

- Next.js route/page-ը և ընդհանուր component-ների սահմանները `src/app/`-ում և
  `src/shared/components/`-ում։
- API պատասխանի կառուցվածքները, բեռնման/դատարկ/սխալի վիճակները, ստեղնաշարով և էկրանի ընթերցիչով աշխատանքը,
  արձագանքող դասավորությունը, թեմաները և տեղայնացումների ընդլայնումը։
- Անգլերեն UI սկզբնաղբյուր տողերը `src/i18n/messages/en.json`-ում․ օգտատիրոջը ցուցադրվող նոր տեքստը մի գրեք անմիջապես կոդում։

**Նպատակային ցիկլ**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Փոխազդեցության կամ տեսողական փոփոխությունների դեպքում գործարկեք հավելվածը և ստուգեք ինչպես նեղ, այնպես էլ լայն դիտարկման տիրույթներում։ CI-ն գործարկում է
արտադրական build-ը և ավելի լայն թեստային փաթեթները․ տեսողական վարքագիծը, այնուամենայնիվ, պահանջում է փոփոխությանը համապատասխան նպատակային component-ի կամ Playwright-ի
թեստ կամ փաստաթղթավորված ձեռքով ստուգում։

### i18n

**Պայմանագրեր**

- `src/i18n/messages/en.json`-ը UI-ի սկզբնաղբյուրն է, իսկ `config/i18n.json`-ը՝ տեղայնացումների սկզբնաղբյուրը։
- CLI կատալոգները գտնվում են առանձին՝ `bin/cli/locales/`-ում։
- Պահպանեք ICU տեղապահներն ու tag-երը ճիշտ նույնությամբ։ Մի թարգմանեք արտադրանքի/մատակարարի/մոդելի անունները,
  պրոտոկոլների և header-ների անունները, հրամանները, կոդի/JSON-ի նույնացուցիչները, URL-ները, միջավայրի փոփոխականները կամ
  պաշտպանված եզրույթները, ինչպիսիք են `OmniRoute`, `OAuth`, `MCP` և `A2A`։ Ընթացիկ սկզբնաղբյուր ցանկը
  `scripts/i18n/glossary/protected-terms.json`-ն է։

**Նպատակային ցիկլ**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # երբ CLI տողերը/կատալոգները փոխվում են
npm run lint
```

Սա առկա համակարգի ուղեցույց է, ոչ թե դրա գործիքակազմը կամ բանալիների մոդելն ընդլայնելու հրավեր։
i18n փոփոխությունները պահեք խիստ նպատակային, քանի դեռ փոխարինող համակարգը նախագծվում է։ Մի գործարկեք թարգմանության
հրամաններ, որոնք դիմում են արտաքին ծառայությունների, եթե խնդիրը բացահայտորեն չի պահանջում գեներացված թարգմանություններ, և
դուք չեք վերանայել ստացված diff-ը։

### CLI

**Պայմանագրեր**

- Հանրային հրամաններն ու դրոշակները `bin/cli/`-ում, գեներացված API հրամանները, ելքի կոդերը, stdout/stderr-ը և
  JSON ելքի կառուցվածքները, կազմաձևման/միջավայրի վարքագիծը և փաթեթավորված ֆայլերը։
- CLI-ի՝ օգտատիրոջը ցուցադրվող տողերը պետք է օգտագործեն CLI i18n շերտը, իսկ `en`/`pt-BR` կատալոգները պետք է համաժամեցված լինեն։
- Պահպանեք Node-ը՝ որպես աջակցվող կատարման միջավայր, ինչպես նաև հրապարակված բինար ֆայլի պայմանագիրը։

**Կենտրոնացված ցիկլ**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # գեներացված/փաթեթավորված CLI-ի փոփոխություններ
npm run check:pack-policy     # փաթեթի հանրային մակերեսի փոփոխություններ
npm run lint
```

Օգտագործեք ճշգրիտ հրամանը տվյալների ժամանակավոր գրացուցակում, երբ վարքագիծը կախված է վերլուծումից, ֆայլերից կամ ելքի
կարգավիճակից։ CI-ն կատարում է փաթեթի արտեֆակտների և էկոհամակարգի ավելի լայն ստուգումները։

### Տվյալների բազա

**Պայմանագրեր**

- Դոմենային մոդուլները գտնվում են `src/lib/db/`-ում․ ներմուծեք կոնկրետ մոդուլներն ուղղակիորեն (հին `localDb.ts` վերաարտահանման շերտը հեռացվել է)։
- Համարակալված, իդեմպոտենտ SQL միգրացիաները՝ `src/lib/db/migrations/`-ում, գործարքների անվտանգությունը, արդիականացման
  վարքագիծը, ինդեքսները և սխեմայից կախված յուրաքանչյուր կանչող։
- Երթուղիներն ու մշակիչները երբեք ուղղակիորեն չպետք է կատարեն չմշակված SQL։

**Կենտրոնացված ցիկլ**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Միգրացիա ավելացնելիս փորձարկեք և՛ նոր տվյալների բազան, և՛ նախորդ սխեմայից արդիականացումը։ Տվյալների բազայի թեստերը
պետք է փակեն բռնակները և մաքրման ընթացքում կանչեն `resetDbInstance()`։ Գործարկեք `npm run test:bun:db` միայն այն ժամանակ, երբ
փոխվում է լավագույն ջանքով աջակցվող Bun ադապտերի ուղին․ Node-ը մնում է հեղինակավոր։

### Կառուցում / տեղակայում

**Պայմանագրեր**

- Արմատային և աշխատանքային տարածքների մանիֆեստները/կողպման ֆայլը, `scripts/build/`-ը, Next.js-ի ինքնաբավ հավաքումը, `dist/`
  փաթեթի բովանդակությունը, Electron-ի հարթակային մետատվյալները, CI աշխատանքային հոսքերը և տեղակայման պահապանները։
- Node-ի աջակցվող միջակայքերը և `CLAUDE.md`-ում Bun-ի թույլատրված օգտագործման ցանկը պետք է անփոփոխ մնան։
- Կառուցման արտեֆակտները չեն ներառվում տարբերակների վերահսկման մեջ․ կիրառվում են կախվածությունների, արտոնագրերի, աշխատանքային հոսքերի և փաթեթների քաղաքականությունները։

**Կենտրոնացված ցիկլ**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # կախվածության կամ կողպման ֆայլի փոփոխություններ
npm run check:pack-policy      # հրապարակված փաթեթի հանրային մակերեսի փոփոխություններ
npm run lint
```

Տեղային միջավայրում օգտագործեք `npm run build` միայն այն դեպքում, երբ փոփոխությունն ազդում է կոմպիլացման, ինքնաբավ հավաքման, ռեսուրսների
կամ կատարման ժամանակի փաթեթավորման վրա։ Օգտագործեք `npm run build:release` միայն թողարկման/տեղակայման վավերացման համար։ CI-ի կառուցումը
վերջնական միջհարթակային ազդանշանն է․ Electron-ի հարթակին հատուկ փոփոխությունների համար անհրաժեշտ է համապատասխան կենտրոնացված կառուցման
կամ արագ ստուգման ապացույց։

## Լոկալ թեկնածուի ցիկլ

Սկզբնաղբյուրի թեստերը չեն կարող ապացուցել, որ փաթեթավորված արտեֆակտը գործարկվում է. փաթեթավորման ցանկերի, հեռացված կախվածությունների և նատիվ բինար ֆայլերի հետ կապված խնդիրներն ի հայտ են գալիս միայն այն ժամանակ, երբ tarball-ը տեղադրվում և գործարկվում է։ `npm run dev:candidate`
-ը (`scripts/dev/candidate.mjs`) RFC #8084-ում նկարագրված՝ մեկ անգամ կառուցելու / վավերացնելու / առաջ մղելու հոսքի լոկալ մասն է. այն կառուցում է մեկ թեկնածու, վավերացնում է հենց այդ արտեֆակտը, առաջ է մղում այն՝ վերանվանելով պանակները, և հետ է վերադարձնում, երբ առաջ մղված բնիկը չի անցնում առողջության ստուգումը։

```bash
npm run dev:candidate -- run --dry-run --json  # տպել պլանը՝ ոչինչ չփոխելով
npm run dev:candidate -- run                   # կառուցել + վավերացնել + առաջ մղել՝ ավտոմատ հետվերադարձով
npm run dev:candidate -- build                 # npm pack + տեղադրում _artifacts/candidate/<id>/ պանակում
npm run dev:candidate -- validate --id <id>    # գործարկել ազատ պորտով, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # փոխատեղել current-ը և previous-ը
npm run dev:candidate -- run --from-tarball <file.tgz>  # վերօգտագործել այլ տեղում (CI) կառուցված tarball-ը
```

- **Կառուցեք մեկ անգամ։** `build`-ը փաթեթավորում է ընթացիկ ծառը (դրա համար անհրաժեշտ է `dist/server.js`, ուստի նախ գործարկեք
  `npm run build:release`) կամ պատճենում է `--from-tarball`-ը, ապա tarball-ը տեղադրում է մեկուսացված npm prefix-ում, քանի որ tarball-ը չի պարունակում `node_modules`։ id-ն `HEAD`-ի կարճ sha-ն է (`-dirty`, երբ ծառում կան լոկալ փոփոխություններ) կամ tarball-ի համար՝ `tgz-<sha256>`։ Արդեն կառուցված մաքուր id-ն վերօգտագործվում է՝ կրկին կառուցվելու փոխարեն. այն վերակառուցելու համար փոխանցեք `--force`։
- **Վավերացրեք փաթեթը, ոչ թե սկզբնաղբյուրը։** `validate`-ը գործարկում է տեղադրված CLI-ը
  (`serve --port <free port>`)՝ նոր `DATA_DIR=<candidate>/data`-ով և կեղծ գաղտնիքներով՝ օպերատորի `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` և `INITIAL_PASSWORD` արժեքները միջավայրից հեռացնելուց հետո, որպեսզի ստուգի նոր տեղադրման՝ առանց բանալու loopback դիրքավորումը։ Այն սպասում է, մինչև
  `GET /api/health`-ը վերադարձնի 200, պահանջում է, որ `GET /v1/models`-ը վերադարձնի 200, կանգնեցնում է պրոցեսների խումբը և արդյունքը tarball-ի hash-ի հետ գրանցում է `validation.json`-ում։
- **Առաջ մղեք նույն արտեֆակտը։** `promote`-ը մերժում է այն թեկնածուին, որը չունի իր ընթացիկ tarball hash-ի հաջող վավերացում։ Լռելյայն ակտիվ բնիկը `_artifacts/candidate/current`-ն է. `--target <dir>`-ն ընտրում է նույն ֆայլային համակարգում գտնվող մեկ այլ պանակ, իսկ դրա նախորդ բնիկը `<dir>.previous`-ն է։
  Յուրաքանչյուր վերանվանում ատոմական է, իսկ միջանկյալ ձախողման դեպքում արդեն կատարված վերանվանումները հակադարձվում են։
- **Հետ վերադարձրեք։** `run`-ը կրկին վավերացնում է առաջ մղված բնիկը և, եթե այդ ստուգումը ձախողվում է, կրկին փոխատեղում է `current`-ը և `previous`-ը։ Առաջին վավերացումը չանցած թեկնածուն երբեք առաջ չի մղվում։

Ամեն ինչ գրվում է git-ի կողմից անտեսվող `_artifacts/candidate/` պանակում. գոյություն ունեցող OmniRoute-ի տեղադրումը և դրա տվյալների պանակը երբեք չեն փոփոխվում։ Առաջ մղված CLI-ը
`_artifacts/candidate/current/prefix/bin/omniroute`-ն է. այն օգտագործելիս գործարկեք ձեր սեփական `DATA_DIR`-ով։ Ելքի կոդերը՝ `0`՝ հաջողություն, `1`՝ ձախողված վավերացում կամ առաջ մղում, `2`՝ օգտագործման սխալ կամ բացակայող կառուցում։

## Տեղային ցիկլն ընդդեմ CI-ի

| Յուրաքանչյուր փոփոխության համար գործարկել տեղային միջավայրում                                   | CI-ն տրամադրում է համապարփակ ազդանշան                                                                  |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Վերը նշված վարքագծի ուղիղ թեստերը և կատեգորիաների ստուգիչները                                   | Մասերի բաժանված ամբողջական միավորային թեստերի փաթեթը և հաջորդական թեստերը                              |
| `npm run lint`                                                                                  | Vitest թեստային փաթեթները և ծածկույթի/որակի աստիճանական շեմերը                                         |
| Տիպերի ստուգում կամ կառուցում՝ միայն երբ դա պահանջում է փոփոխված պայմանագիրը                    | Արտադրական կառուցման, անվտանգության, փաստաթղթերի, կախվածությունների և PR-ի քաղաքականության ստուգիչները |
| Ձեռքով փոխազդեցության/կենդանի ստուգումներ՝ միայն երբ ավտոմատացումը չի կարող ապացուցել վարքագիծը | Աշխատանքների միջև ինտեգրման և հարթակի ստուգումները, որոնք կազմաձևված են աշխատանքային հոսքով            |

Կանաչ արդյունքով նպատակային ցիկլը փոփոխված պայմանագրի վերաբերյալ ապացույց է, ոչ թե երաշխիք, որ
CI-ի՝ դրա հետ կապ չունեցող ստուգումները կհաջողվեն։ Մյուս կողմից՝ մի ստիպեք, որ յուրաքանչյուր տեղային փոփոխություն սպասի շտեմարանի ամբողջական մատրիցի ավարտին։

## Համաձայնեցման ստուգաթերթ

Վերանայում խնդրելուց առաջ՝

- Հաստատեք, որ PR-ի բազային ճյուղը դեռևս ամենաբարձր ակտիվ `release/v*` ճյուղն է։
- Ներբեռնեք այդ բազային ճյուղը և վերանայեք այն commit-ները, որոնք ավելացվել են ձեր ճյուղավորելուց հետո։
- Ստուգեք `git diff <active-base>...HEAD`-ը՝ պատահական կամ գեներացված ավելորդ փոփոխությունների առկայության համար։
- Լուծեք կատալոգի և գեներացված փաստաթղթերի հակասությունները՝ թարմացնելով սկզբնաղբյուրը և կրկին գեներացնելով արդյունքը։
- Համաձայնեցումից հետո կրկին գործարկեք PR-ի նկարագրության մեջ նշված յուրաքանչյուր նպատակային թեստ/ստուգիչ։
- Երբեք մի թուլացրեք ստուգումները կամ մի հեռացրեք պարտադիր թեստերը միայն փոփոխված բազային ճյուղին համապատասխանելու համար։

Թողարկման սառեցման և վերաթիրախավորման կանոնների համար օգտագործեք
[Ճյուղավորման և թողարկման մոդելը](BRANCHING_MODEL.md)։ CI-ի ամբողջական ցանկի համար օգտագործեք
[Որակի ստուգիչների տեղեկատուն](../architecture/QUALITY_GATES.md)։
