Հոմոլոգացման VPS-ում աշխատող OmniRoute տեղակայման իրական միջավայրում E2E վավերացում
(`HOMOLOG_BASE_URL`, օրինակ՝ `http://192.168.0.15:20128`)։ Մեկ հրամանը փոխարինում է թողարկման
STOP #2 ձեռքով ստուգաթերթը՝ ավտոմատացված, ապացույցներ ստեղծող գործարկմամբ։

## Նախապայմաններ

1. Պատճենեք `.env.homolog.example`-ը որպես `.env.homolog` (անտեսվում է git-ի կողմից՝ երբեք մի commit արեք այն) և լրացրեք՝
   - `HOMOLOG_BASE_URL` — թիրախային deploy-ը, օրինակ՝ `http://192.168.0.15:20128`։
   - `HOMOLOG_ADMIN_PASSWORD` — տվյալ deploy-ի dashboard-ի կառավարման գաղտնաբառը։
   - `HOMOLOG_CRITICAL_PROVIDERS` — ստորակետերով բաժանված provider-ի նախածանցներ, որոնց համար ուղարկվում է իրական
     smoke chat հարցում (օրինակ՝ `openai,anthropic,gemini,codex,grok,glm,deepseek,openrouter`)։
   - `HOMOLOG_API_KEY` — սովորական գործարկումների ժամանակ թողեք դատարկ․ հավաքակազմն ինքն է ստեղծում և չեղարկում իր
     ժամանակավոր բանալին։ Սահմանեք այն միայն առանձին շերտը մեկուսացված կերպով կարգաբերելու համար։
2. Գործարկեք `npm install` repository-ում (հավաքակազմի կախվածությունները՝ `httpyac`, `promptfoo`,
   `playwright-ctrf-json-reporter`, `junit-to-ctrf`, `ctrf`, սովորական devDependencies են)։
3. Գործարկեք `npx playwright install`, եթե browser-ի binary ֆայլերն արդեն առկա չեն։

## Գործարկման եղանակը

```bash
npm run homolog
```

Այն deploy-ի նկատմամբ ստուգում կատարելու համար, որի տարբերակը չի համապատասխանում տեղական `package.json`-ին
(օրինակ՝ homologation միջավայր, որը դեռևս նախորդ patch release-ի վրա է), բացահայտորեն վերասահմանեք ակնկալվող
տարբերակը՝

```bash
HOMOLOG_EXPECT_VERSION=3.8.47 npm run homolog
```

Գործարկումն ավարտվում է ոչ զրոյական կոդով, եթե որևէ շերտ ձախողվում է, և միշտ փորձում է չեղարկել իր ստեղծած ժամանակավոր
API բանալին, նույնիսկ ձախողման դեպքում (`finally` բլոկը՝ `scripts/homolog/run.mjs`-ում)։

## Հաշվետվության ընթերցումը

Ամբողջ արդյունքը պահվում է `homolog-report/`-ում (անտեսվում է git-ի կողմից)՝

- `summary.md` — նույն աղյուսակը, որը տպվում է stdout-ում՝ մեկ տող յուրաքանչյուր շերտի համար (✅/❌ + մանրամասներ)։
- `homolog-ctrf.json` — միասնական CTRF հաշվետվությունը (API/SSE-ի, provider smoke ստուգումների և
  UI արդյունքների միավորում)․ սա այն artifact-ն է, որը պետք է կցել release-ի STOP #2 ստուգաթերթին։
- `httpyac-junit.xml`, `api-ctrf.json`, `providers-ctrf.json`, `ui-ctrf.json` — յուրաքանչյուր
  շերտի սկզբնական/միջանկյալ հաշվետվությունները։
- `promptfooconfig.yaml`, `provider-misses.json` — ընթացիկ գործարկման համար գեներացված promptfoo-ի կազմաձևը
  և live catalog-ից բացակայող ցանկացած կրիտիկական provider։

L0-ի ձախողումն անմիջապես ընդհատում է աշխատանքը (ժամանակավոր բանալի չի ստեղծվում), քանի որ տարբերակի/առողջության
անհամապատասխանությունը նշանակում է, որ ներքևի բոլոր շերտերը ստուգելու էին սխալ deploy-ը։

## Baseline-ի թարմացումը UI-ի օրինական փոփոխությունների դեպքում

L4b-ը (route smoke) և L4c-ը (API բանալու UI հոսք) կառավարվում են իրական DOM locator-ներով, ոչ թե
snapshot-ներով, ուստի UI-ի օրինական փոփոխությունների մեծ մասը հավաքակազմի որևէ թարմացում չի պահանջում։ Երբ որևէ փոփոխություն
այնուամենայնիվ խախտում է locator-ը (օրինակ՝ button-ի վերանվանված label կամ տեղափոխված settings էջ)՝

1. Կրկին հաստատեք locator-ը՝ համեմատելով ընթացիկ source-ի հետ (spec-երում արդեն փաստաթղթավորված է, թե յուրաքանչյուր
   locator-ը որ file/line-ի նկատմամբ է հաստատվել․ հետևեք նույն ձևաչափին, մի գուշակեք)։
2. Թարմացրեք spec-ը `tests/homolog/ui/`-ում։
3. VPS-ի նկատմամբ կրկին գործարկեք `npm run homolog`-ը (կամ միայն համապատասխան Playwright spec-ը)՝
   ուղղումը հաստատելու համար, ապա commit արեք։

Այս հավաքակազմում visual/pixel baseline չկա (F1)․ դրա համար տե՛ս Roadmap-ը։

## Ճանապարհային քարտեզ (F2 / F3)

Նախագիծը և փուլային ներդրումը ներկայացված են ներքին պլանավորման spec-ում՝
`_tasks/superpowers/specs/2026-07-13-homolog-e2e-suite-design.md` (հղում չի տրված․ սա ներքին
`_tasks/` artifact է և այս repository-ի վերահսկվող փաստաթղթերի մաս չէ)։ Ամփոփում՝
