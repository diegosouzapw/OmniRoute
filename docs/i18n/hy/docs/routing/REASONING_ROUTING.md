Reasonողության երթուղման կանոններն ընդլայնում են մոդելների և կոմբինացիաների առկա երթուղումը։ Երբ որևէ ակտիվ կանոն չի համընկնում,
առկա մտածողության, վերջածանցի, կապի լռելյայն և մատակարարի փոխակերպման վարքագիծը մնում է
անփոփոխ։

## Կառավարում

Կանոնների կառավարումը հասանելի է **Կարգավորումներ → Գլոբալ երթուղում** բաժնում։ API բանալու խմբագրիչը տրամադրում է
նույն կառավարման միջերեսը՝ զտված ըստ ընտրված բանալու։

Կառավարման API-ն հասանելի է հետևյալ երթուղիներով․

- `GET` և `POST`՝ `/api/settings/reasoning-routing-rules` հասցեում
- `GET`, `PATCH` և `DELETE`՝ `/api/settings/reasoning-routing-rules/[id]` հասցեում
- `POST`՝ `/api/settings/reasoning-routing-rules/simulate` հասցեում

Բոլոր երթուղիներն օգտագործում են `requireManagementAuth`։ Մուտքային տվյալները վավերացվում են
`src/shared/validation/schemas/reasoningRouting.ts` ֆայլում գտնվող սխեմաներով։ Սիմուլյատորը երբեք վերադաս ծառայության հարցում չի կատարում։

## Կանոնի որոշում

Վաղ գնահատումն ընտրում է ճիշտ մեկ կանոն։ Գործողության տիրույթները ստուգվում են հետևյալ հերթականությամբ․

1. `apiKey`
2. `combo`
3. `model`
4. `global`

Գործողության տիրույթի ներսում սկզբում հաղթում է ավելի բարձր `priority` ունեցող կանոնը, այնուհետև՝ մոդելի ճշգրիտ համընկնումը glob ձևանմուշի նկատմամբ,
ապա՝ կայուն `createdAt` և `id` դասավորությունը։ `requestTags`-ը կարդացվում է բացառապես `metadata.tags`-ից
և աջակցում է `any` կամ `all` համընկնմանը։

`connection` կանոնը գնահատվում է միայն այն դեպքում, երբ վաղ կանոններից ոչ մեկը չի հաղթել, և արդեն ընտրվել է
մատակարարի կոնկրետ կապ։ Այն կարող է փոխել միայն ջանքի մակարդակը և բյուջեն։

## Ջանք և բյուջե

`sourceEffort`-ն ընդունում է `any`, `missing`, `none`, `low`, `medium`, `high`, `xhigh`, `max` և
`ultra` արժեքները։ `missing`-ը նշանակում է, որ հարցումը չի պարունակում ո՛չ ջանքի առանձին մակարդակ, ո՛չ մտածողության փոխարկիչ
կամ մտածողության բյուջե։ Հետևաբար, միայն բյուջե պարունակող ազդանշանը համընկնում է միայն `any`-ի հետ։

`effortMode`-ն ունի երեք տարբերակ․

- `inherit`-ը պահպանում է հաճախորդի ջանքի մակարդակը՝ միաժամանակ թույլ տալով փոխել մոդելը կամ կոմբինացիան։
- `default`-ը սահմանում է `targetEffort`-ը միայն այն դեպքում, երբ մտածողության բացահայտ ազդանշան առկա չէ։
- `force`-ը ջանքի առանձին մակարդակը փոխարինում է `targetEffort`-ով։

Անկախ դրանից՝ `budgetAction`-ը կարող է լինել `preserve`, `remove` կամ `set`։ `force`-ը `none`-ի հետ հեռացնում է
ջանքի և բյուջեի բոլոր ճանաչված դաշտերը։ `none`-ը `set`-ի հետ անվավեր է։

Հայտնի անհամատեղելի մոդելներին ուղղված հարցումները մերժվում են մինչև վերադաս ծառայության կանչը։ Կոմբինացիա
թիրախավորելու դեպքում անհամատեղելի տարրերը հեռացվում են․ եթե ոչ մեկը չի մնում, հարցումը վերադարձնում է `400` կարգավիճակը։
Հնարավորությունների անհայտ տվյալները ստեղծում են նախազգուշացում և կանոնը թողնում ակտիվ։

## Անվտանգություն և փոխադրամիջոցներ

Սկզբնաղբյուր և թիրախային մոդելները կամ սկզբնաղբյուր և թիրախային կոմբինացիաները շարունակում են ենթարկվել API բանալու
առկա քաղաքականությանը։ Reasoning կանոնը երբեք չի ընդլայնում մոդելի, կոմբինացիայի կամ քվոտայի թույլտվությունները։

Շարժիչը ինտեգրված է Chat Completions, Responses, Anthropic Messages և ներքին
Codex WebSocket ուղիներում։ WebSocket ուղին ընդունում է միայն Codex թիրախային մոդելներ․ կոմբինացիա թիրախները չեն կարող
այնտեղ կատարվել։ Կանոնի որոշումը պահվում է երթուղու առկա հետագծում՝ առանց գաղտնիքների։

## Պահպանում

`src/lib/db/migrations/126_reasoning_routing_rules.sql` միգրացիան ստեղծում է
`reasoning_routing_rules` աղյուսակը։ Կանոնները հղվում են պահպանված API բանալիներին, կոմբինացիաներին և մատակարարի կապերին։
Ջնջումները մաքրում են կապված կանոնները։ `src/lib/db/reasoningRoutingRules.ts`-ի տվյալների բազայի հասանելիության շերտը
հարցումների ուղու համար պահպանում է անվավեր ճանաչելի քեշ։

Կանոնները ներառվում են SQLite պահուստային պատճեններում, տվյալների բազայի ամբողջական արտահանման և կազմաձևման համաժամացման փաթեթում։
`reconcileReasoningRulesForSync`-ն անջատում է բացակայող հղումներով ներմուծված կանոնները և հաղորդում է այդ
հակասությունների մասին։
