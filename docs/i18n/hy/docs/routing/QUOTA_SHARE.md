## Ընդհանուր նկարագրություն

Քվոտաների համօգտագործման շարժիչը մատակարարի՝ ժամանակի վրա հիմնված քվոտան (օրինակ՝ Codex-ի
5-ժամյա պատուհանը, Kimi-ի 1500 հարցում/ժամը) արդարացիորեն բաշխում է միևնույն
միացումը համօգտագործող մի քանի API բանալիների միջև։

**Լուծվող խնդիրը.** OmniRoute-ը բազմաթիվ API բանալիների հարցումները պրոքսիավորում է դեպի միևնույն վերին մակարդակի
մատակարարի հաշիվ։ Առանց համօգտագործման տրամաբանության՝ A բանալուց հարցումների կտրուկ աճը կարող է սպառել
մատակարարի ժամային քվոտան՝ B և C բանալիներն արգելափակված թողնելով մինչև պատուհանի զրոյացումը։
Շարժիչը կանխում է դա՝

1. Հետևելով յուրաքանչյուր բանալու սահող սպառմանը՝ ըստ չափման միավորի (%, հարցումներ, թոքեններ, $)։
2. Կիրառելով աշխատանքը պահպանող արդար բաժանման ալգորիթմ. բանալին կարող է փոխառել չօգտագործվող
   բաժիններից, քանի դեռ ընդհանուր պաշարը հագեցած չէ։
3. Արդյունքը կիրառելով թեժ ուղում (`chatCore.ts`)՝ նախքան հարցումը
   կհասնի վերին մակարդակի կատարիչին։

## Ալգորիթմ. աշխատանքը պահպանող արդար բաժանում

Իրականացված է `src/lib/quota/fairShare.ts`-ում։

### Ռեժիմներ

| Պայման                                     | Ռեժիմ         | Վարքագիծ                                                                   |
| ------------------------------------------ | ------------- | -------------------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **Առատաձեռն** | Բանալին կարող է փոխառել մինչև ընդհանուր սահմանաչափից հանած ամբողջ սպառումը |
| `globalUsedPercent >= saturationThreshold` | **Խիստ**      | Խստորեն կիրառել անհատական արդար բաժինը                                     |

Լռելյայն՝ `saturationThreshold = 0.5` (միջավայրի փոփոխական՝ `QUOTA_SATURATION_THRESHOLD`)։

### Որոշում՝ ըստ չափման միավորի

Պաշարի յուրաքանչյուր ակտիվ չափման միավորի համար շարժիչը հաշվարկում է՝

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = այս բանալու ընթացիկ սահող արժեքը (QuotaStore.peek-ից)
remaining       = fairShareAllowed - consumed
```

Այնուհետև՝

- **`policy = hard`**. եթե `consumed > fairShareAllowed`, իսկ ռեժիմը խիստ է → **արգելափակել**։
- **`policy = soft`**. եթե `consumed > fairShareAllowed`, իսկ ռեժիմը խիստ է → **տույժ կիրառել** (նվազեցնել առաջնահերթությունը համակցման մեջ, երբեք կոշտ չարգելափակել)։
- **`policy = burst`**. թույլատրել, քանի դեռ ընդհանուր պաշարում ազատ ծավալ կա՝ անկախ արդար բաժնից։

### Բացարձակ վերին սահմանաչափ

Հատկացման `capValue` + `capUnit`-ը կոշտ վերին սահմանաչափ է՝ անկախ ռեժիմից կամ
քաղաքականությունից։ Ցանկացած չափման միավոր, որի համար `consumed >= capValue`, միշտ **արգելափակում է** հարցումը։

### Բազմաչափ ստուգում

Հարցումն արգելափակվում է, եթե պաշարի չափման միավորներից **որևէ մեկը** պետք է արգելափակի այն։ Չափման միավորներն
անկախ են. 5h% չափման միավորի սպառումը չի ազդում weekly% չափման միավորի վրա։

### Փոխառում

Առատաձեռն ռեժիմում իր հատկացումը թերի օգտագործած բանալին կարող է օգտվել
այլ բանալիների չօգտագործված բաժինների ավելցուկից։ Բանաձևն է՝

```
maxAllowed = globalLimit - consumedByOtherKeys
```

որտեղ `consumedByOtherKeys = consumedTotal - consumedByThisKey`։ Ընդհանուր վերին սահմանաչափը
(տվյալ չափման միավորի համար պաշարի `limit`-ը) միշտ կոշտ սահմանաչափ է։

## Սահող պատուհանի հաշվիչ

Իրականացված է `src/lib/quota/sqliteQuotaStore.ts`-ում և `redisQuotaStore.ts`-ում։

Երկու հատված յուրաքանչյուր `(apiKeyId, dimensionKey)`-ի համար՝

- `curr`՝ ընթացիկ հատված (`floor(nowMs / windowMs)`)
- `prev`՝ նախորդ հատված (`curr - 1`)

Արդյունավետ սահող արժեքը՝

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**Ճշգրտություն**՝ մոտ 99%։ Սխալն առավելագույնը պատուհանի չափի 1%-ն է՝
հատվածների սահմանի մոտ (երկու հատվածով մոտարկման անխուսափելի հետևանք)։

### Զուգահեռություն

SQLite դրայվեր. `(apiKeyId | dimensionKey)` յուրաքանչյուր բանալու համար հիշողության մեջ պահվող mutex-ը կանխում է
կարդալ-փոփոխել-գրել մրցավիճակը։ Կաղապարը կրկնում է `src/sse/services/auth.ts`-ի՝ միաժամանակյա զանգվածային հարցումները կանխելու մոտեցումը։

Redis դրայվեր. ատոմային ավելացման համար օգտագործվում է Lua EVAL սկրիպտ, որն աշխատում է որպես մեկ Redis հրաման։

## Դրայվերներ

### SQLite (լռելյայն, տեղադրում չի պահանջվում)

- Աղյուսակ՝ `quota_consumption` (տե՛ս `073_quota_pools.sql` / `074_quota_consumption.sql` միգրացիաները)։
- Լավագույնն է մեկ ինստանսով տեղակայումների համար։
- Բոլոր տվյալները պահպանվում են գոյություն ունեցող OmniRoute SQLite ՏԲ-ում (`DATA_DIR/storage.sqlite`)։

### Redis (ըստ ցանկության, բազմաինստանս)

- Պահանջում է `ioredis` npm փաթեթը։
- Հաշվիչները պահվում են Redis-ում, իսկ մետատվյալները (փուլերը/բաշխումները)՝ դեռևս SQLite-ում։
- Լավագույնն է մի քանի ռեպլիկայով տեղակայումների համար, երբ հաշվիչները պետք է համօգտագործվեն։

### Դրայվերների փոխարկում

Կարգավորումների միջերեսի միջոցով (`/dashboard/settings` → Quota Store) կամ միջավայրի փոփոխականների միջոցով՝

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

ՏԲ-ի կարգավորումն առաջնահերթ է միջավայրի փոփոխականի նկատմամբ։ Եթե `driver=redis`, բայց URL-ը բացակայում է կամ
`ioredis`-ը տեղադրված չէ, ֆաբրիկան անցնում է SQLite-ի և գրանցում նախազգուշացում։

Դրայվերի ընտրության հերթականությունը՝

1. ՏԲ-ի `quotaStore.driver` կարգավորումը
2. Միջավայրի `QUOTA_STORE_DRIVER` փոփոխականը
3. Լռելյայն՝ `sqlite`

## Բազմաչափություն

Փուլը կարող է ունենալ մի քանի չափում։ Յուրաքանչյուր չափում անկախ է՝

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // այս չափման համար փուլի ընդհանուր վերին սահմանը
}
```

**Օրինակ՝ Codex պլան** (5h% + weekly%)՝

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

Հարցումը թույլատրելու համար այն պետք է բավարարի բոլոր չափումների պահանջները։

## Պլանի որոշիչ

Իրականացված է `src/lib/quota/planResolver.ts`-ում։

Առաջնահերթությունը (բարձրից ցածր)՝

1. **ՏԲ-ի ձեռքով վերասահմանում** — `provider_plans` աղյուսակ՝ ըստ յուրաքանչյուր `connectionId`-ի։
2. **Հայտնի կատալոգ** — `src/lib/quota/planRegistry.ts` (միայն տվյալներ)։
3. **Դատարկ պլան** — չափումներ չկան, պահանջվում է ձեռքով կազմաձևում։

### Հայտնի կատալոգ

| Մատակարար             | Չափումներ                                                     |
| --------------------- | ------------------------------------------------------------- |
| `codex`               | `percent/5h/100`, `percent/weekly/100`                        |
| `glm`                 | `tokens/5h` (limit=0, անհայտ), `tokens/weekly`                |
| `minimax`             | `tokens/5h`, `tokens/weekly`                                  |
| `bailian`             | `percent/5h/100`, `percent/weekly/100`, `percent/monthly/100` |
| `kimi`                | `requests/hourly/1500`                                        |
| `alibaba`             | `requests/monthly/90000`                                      |
| `openai`, `anthropic` | Լռելյայն արժեք չկա — պահանջվում է ձեռքով կազմաձևում           |

## Կոնվեյերի ինտեգրում

### PRE հուկ (`open-sse/handlers/chatCore.ts`)

Գործարկվում է վերընթաց կատարիչից առաջ՝ նույնականացման և քաղաքականության ստուգումներից հետո՝

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek()՝ յուրաքանչյուր չափման համար
      → fairShare.decideFairShare()
      → եթե արգելափակել → վերադարձնել 429 (buildErrorBody, Խիստ կանոն #12)
      → եթե թույլատրել + իջեցնել առաջնահերթությունը → թեկնածուի համար սահմանել quotaSoftPenalty=true
  → executor.execute()
```

**Խափանման դեպքում թույլատրում**․ եթե `enforceQuotaShare`-ը բացառություն է գեներացնում, հարցումը
թույլատրվում է՝ իրադարձությունը գրանցելով `pino.warn`-ով։ Սա կանխում է քվոտաների շարժիչի սխալի պատճառով
ամբողջ թրաֆիկի արգելափակումը։

### POST հուկ (սպառման գրանցում)

Հաջող պատասխանից հետո՝

```
executor-ը վերադարձնում է հաջողություն
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume()՝ յուրաքանչյուր չափման համար
      → խափանման դեպքում թույլատրում․ սխալները գրանցվում են որպես pino.warn և երբեք չեն փոխանցվում հաճախորդին
```

**Շեղման նշում**․ եթե պատասխանից հետո `consume`-ը ձախողվում է, սահող հաշվիչը սպառումը թերհաշվում է։
Մատակարարի հագեցվածության ազդանշանը (օրինակ՝ `anthropic-ratelimit-unified-5h-utilization`)
ուղղում է ընդհանուր գնահատականը հաջորդ հարցման ժամանակ։

### Combo-ի մեղմ տույժ (`open-sse/services/combo.ts`)

Երբ `decision.deprioritize === true`՝

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // լռելյայն՝ 0.7
}
```

Տույժը կիրառվում է գնահատման մյուս բոլոր գործոններից հետո։ Այն նվազեցնում է հագեցած բանալու
ավտոմատ համակցությամբ ընտրության հավանականությունը՝ առանց այն խիստ արգելափակելու։

## Խնդիրների ախտորոշում

### Redis-ը կազմաձևված է, բայց չի միանում

Ստուգեք, որ `ioredis`-ը տեղադրված է (`npm ls ioredis`), և `QUOTA_STORE_REDIS_URL`-ը
հասանելի է։ Միացման ձախողման դեպքում ֆաբրիկան անցնում է SQLite-ի օգտագործմանը
(գրանցվում է `warn` մակարդակով)։

### `peek`-ը վերադարձնում է հնացած տվյալներ / աշխատում է բաց թողնելու սկզբունքով

Եթե `peek`-ը սխալ է նետում, `enforceQuotaShare`-ը արդյունքը դիտարկում է որպես «թույլատրել»
(ձախողման դեպքում՝ բաց թողնել)։ Հիմնական պատճառը բացահայտելու համար `pino` մատյաններում
ստուգեք `quota:enforce` և `quota:factory` գրառումները։

### Սպառման հաշվիչի շեղում

Եթե մատակարարի փաստացի օգտագործումը տարբերվում է հաշվիչների տվյալներից, դա սպասելի է․
2 բաքեթով սահող պատուհանը պատուհանների սահմաններին ունի մոտ 1% սխալ, իսկ `consume`-ը
պատասխանից հետո գործարկվում է առանց ավարտին սպասելու։ Հագեցվածության ազդանշանը (`saturationSignals.ts`)
30 վրկ. TTL-ով կարդում է մատակարարի իրական օգտագործումը և համապատասխանաբար ճշգրտում `globalUsedPercent`-ը։

### Փուլը սպառման արագության համար ցույց է տալիս «տվյալներ չկան»

`computeBurnRate`-ը պահանջում է առնվազն 2 պատմական նմուշ։ Առանց նախորդ
`consume` կանչերի նոր փուլերը ցույց կտան `tokensPerSecond: 0` և `timeToExhaustionMs: null`։

## Տեղափոխում localStorage-ից

Երբ `/dashboard/costs/quota-share`-ն առաջին անգամ բեռնվում է, `useLocalStoragePoolMigration` հուքը ստուգում է՝

1. `localStorage.getItem("omniroute:quota-share:pools")`-ը դատարկ չէ։
2. `GET /api/quota/pools`-ը վերադարձնում է `[]` (DB-ն դատարկ է)։

Եթե երկու պայմաններն էլ ճշմարիտ են, այն խմբաքանակով ուղարկում է յուրաքանչյուր հին փուլը դեպի `POST /api/quota/pools`, ապա հեռացնում է localStorage-ի բանալին։ Տեղափոխումն իդեմպոտենտ է․ 2-րդ պայմանը կանխում է կրկնակի տեղափոխումը։

## Ներքին ստրատեգիայի դասակարգում

`quota-share`-ը **միայն ներքին օգտագործման** երթուղավորման ստրատեգիա է (`INTERNAL_ROUTING_STRATEGY_VALUES`՝

չհայտնվի որպես օգտատիրոջ կողմից ընտրվող տարբերակ UI-ում կամ API-ում։

## DB սխեմայի ամփոփում

`078`, `079` և `085` տեղափոխումներով ավելացված երեք աղյուսակ․

- `quota_pools` + `quota_allocations` — փուլի սահմանումներ և յուրաքանչյուր բանալու համար հատկացումներ։
- `quota_consumption` — սահող 2-բաքային հաշվիչներ յուրաքանչյուր `(apiKeyId, dimensionKey)`-ի համար։
- `provider_plans` — մատակարարի պլանի ձեռքով վերագրումներ (չափումների JSON՝ յուրաքանչյուր connectionId-ի համար)։

Բոլոր աղյուսակներն ավելացվել են իդեմպոտենտ `CREATE TABLE IF NOT EXISTS` տեղափոխումների միջոցով։
