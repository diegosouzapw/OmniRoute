## Առանց կազմաձևման ավտոմատ երթուղավորում (`auto/` նախածանց)

> **ՆՈՐՈՒԹՅՈՒՆ․** Համակցում ստեղծելու անհրաժեշտություն չկա։ Անմիջապես օգտագործեք `auto/` նախածանցը ցանկացած հաճախորդում։

### Արագ օրինակներ

| Մոդելի ID      | Տարբերակ | Վարքագիծ                                                                                                          |
| -------------- | -------- | ----------------------------------------------------------------------------------------------------------------- |
| `auto`         | լռելյայն | Բոլոր միացված մատակարարները, LKGP ռազմավարություն, հավասարակշռված կշիռներ                                         |
| `auto/coding`  | coding   | Որակն առաջնահերթ համարող կշիռներ, հարմար է կոդի գեներացման համար                                                  |
| `auto/fast`    | fast     | Փոքր ուշացումով կշռված ընտրություն                                                                                |
| `auto/cheap`   | cheap    | Ծախսերի համար օպտիմալացված երթուղավորում (նախ՝ նվազագույն արժեքը)                                                 |
| `auto/offline` | offline  | Նախապատվությունը տալիս է քվոտայի առավելագույն հասանելիություն ունեցող մատակարարներին                              |
| `auto/smart`   | smart    | Որակն առաջնահերթ համարող մոտեցում + հետազոտման ավելի բարձր մակարդակ (10%)՝ մոդելների ավելի լավ հայտնաբերման համար |
| `auto/lkgp`    | lkgp     | Հստակ LKGP (նույնը, ինչ լռելյայն `auto`-ն)                                                                        |
| `auto/chaos`   | chaos    | Խափանումների ներարկման կշիռներ՝ դիմակայունության փորձարկման համար (քաոսային ճարտարագիտություն)                    |

### Կատեգորիա × մակարդակ համակցություն (`auto/<category>:<tier>`)

OpenRouter-ի ոճով վերջածանցները տարանջատում են **երթուղու տեսակը** (կատեգորիա) և **դրա օպտիմալացման եղանակը** (մակարդակ), այնպես որ կարող եք դրանք ազատորեն համակցել (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`)․

- **Կատեգորիաներ** (հնարավորությունների հիման վրա զտում են թեկնածուների բազմությունը)՝ `coding` · `reasoning` · `vision` · `chat` · `multimodal`։ `vision`/`multimodal`-ը պահպանում են տեսողական հնարավորություններով մոդելները, իսկ `reasoning`-ը՝ տրամաբանող/մտածող մոդելները։
- **Մակարդակներ** (ընտրում են գնահատման կշիռները / բազմության զտիչը)՝ `fast` (արագ թողարկում) · `cheap` (`floor` կեղծանուն, ծախսերի խնայողություն) · `reliable` (շղթայի անջատիչի առողջություն + ուշացման կայունություն) · `free` / `pro` (զտում են բազմությունն ըստ մոդելի մակարդակի՝ `classifyTier`-ի միջոցով՝ անվճար մակարդակն ընդդեմ պրեմիումի)։

| Օրինակ                 | Վերածվում է                                                                        |
| ---------------------- | ---------------------------------------------------------------------------------- |
| `auto/coding:fast`     | coding բազմություն, փոքր ուշացման կշիռներ                                          |
| `auto/coding:cheap`    | coding բազմություն, ծախսերի համար օպտիմալացված (`auto/coding:floor` կեղծանուն)     |
| `auto/reasoning:pro`   | միայն տրամաբանող/մտածող մոդելներ, պրեմիում մակարդակ                                |
| `auto/vision`          | տեսողական հնարավորություններով մոդելներ (առանց մակարդակի → հավասարակշռված կշիռներ) |
| `auto/multimodal:free` | բազմամոդալ հնարավորություններով մոդելներ, միայն անվճար մակարդակ                    |

Ցանկացած վավեր `auto/<category>[:<tier>]` լուծվում է ըստ պահանջի․ ընտրված ենթաբազմությունը ցուցադրվում է `/v1/models`-ում և կառավարման վահանակում (`AUTO_SUFFIX_VARIANTS`՝ `open-sse/services/autoCombo/builtinCatalog.ts`-ում)։ Զտումն աշխատում է **fail-open** սկզբունքով․ եթե որևէ սահմանափակման չի համապատասխանում միացված մոդելներից ոչ մեկը, օգտագործվում է ամբողջ բազմությունը, որպեսզի երթուղավորումը երբեք չխափանվի։ Հիմնական գնահատիչը (`combo.ts`) չի փոփոխվել․ կատեգորիայի/մակարդակի զտիչը կիրառվում է `buildAutoCandidates`-ում։

> **Մոդելների իրական ժամանակի վերլուծություն․** երբ `ARENA_ELO_SYNC_ENABLED` դրոշը միացված է, ավտոմատ երթուղավորման համապատասխանությունը որոշելիս օգտագործվում են **Arena ELO**-ի իրական ժամանակի վարկանիշները + **models.dev**-ի մակարդակների տվյալները (հակառակ դեպքում օգտագործվում է համապատասխանության ստատիկ քարտեզը)։

**Ինչպես օգտագործել․**

```bash
# OpenAI ձևաչափն աջակցող ցանկացած IDE կամ CLI գործիք
Base URL: http://localhost:20128/v1
API Key:  <ձեր-վերջնակետի-բանալին>

# Ձեր կոդում/կազմաձևում մոդելը սահմանեք հետևյալ կերպ․
model: "auto"                 # հավասարակշռված լռելյայն տարբերակ
model: "auto/coding"          # լավագույնը ծրագրավորման առաջադրանքների համար
model: "auto/fast"            # հասանելիներից ամենաարագը
model: "auto/cheap"           # ամենաէժանը մեկ տոկենի հաշվով
```

**Ինչ է տեղի ունենում․**

1. OmniRoute-ը հայտնաբերում է `auto/` նախածանցը `src/sse/handlers/chat.ts`-ում
2. Տվյալների բազայից հարցում է բոլոր **ակտիվ մատակարարների միացումների** մասին
3. Զտում և պահպանում է վավեր հավատարմագրեր (API բանալի կամ OAuth թոքեն) ունեցողները
4. Որոշում է յուրաքանչյուր միացման մոդելը (`connection.defaultModel` կամ մատակարարի առաջին մոդելը)
5. Հիշողության մեջ կառուցում է **վիրտուալ համակցում** (չի պահվում ՏԲ-ում)
6. Երթուղավորում է՝ օգտագործելով ընտրված տարբերակի կշիռների պրոֆիլը + LKGP ռազմավարությունը

**Հիմնական հատկություններ․**

- ✅ **Միշտ միացված․** Փոխարկիչ, համակցման ստեղծում կամ կազմաձևում անհրաժեշտ չէ
- ✅ **Դինամիկ․** Ավտոմատ կերպով արտացոլում է ներկայում միացված մատակարարներին
- ✅ **Նիստի կայուն կապակցում․** LKGP-ն ապահովում է վերջին հաջող մատակարարի առաջնահերթությունը
- ✅ **Հաշվի է առնում բազմաթիվ հաշիվները․** Մատակարարի յուրաքանչյուր միացում դառնում է առանձին թեկնածու
- ✅ **Առանց ՏԲ-ում գրանցումների․** Վիրտուալ համակցումը գոյություն ունի միայն հարցման ընթացքում՝ պահպանման զրոյական հավելյալ ծախսով

### Ըստ բանալու թեկնածուների կառավարում (#7819, մակարդակ 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/`-ից հետո եկող վերջածանցը կամ
բազային ալիքի համար բառացի `auto` արժեքը) **միայն կարդալու համար** նախատեսված վերջնակետ է, որը թվարկում է
`auto/*` ալիքի թեկնածուների ընթացիկ բազմությունը՝ լրացված իրական ժամանակի հասանելիության տվյալներով և վերօգտագործելով
դիմակայունության առկա ընթերցումները (երբեք ոչ անջատիչի չմշակված `state`-ը)․

- մատակարարի շղթայի անջատիչ՝ `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- միացման դադարի շրջան՝ `rateLimitedUntil` / `testStatus` լուծված
  `provider_connections` տողում
- մոդելի արգելափակում՝ `isModelLocked(provider, connectionId, model)`

Յուրաքանչյուր թեկնածու կրում է նաև այս API բանալու `excluded` դրոշակը։ Բացառումները պահվում են
յուրաքանչյուր API բանալու համար առանձին (`auto_candidate_overrides` աղյուսակ, միգրացիա `128`)․ OmniRoute-ը
մեկ վարձակալի համար նախատեսված համակարգ է և չունի `users` աղյուսակ, ուստի `apiKeyId`-ն իրական՝ յուրաքանչյուր կանչողի
ինքնությանը համապատասխանող ամենամոտ նույնացուցիչն է։ Բացառումները կիրառվում են թեկնածուների հավաքածուի առանցքային կետում՝
`open-sse/services/autoCombo/virtualFactory.ts`-ում, մաքուր և միավորային թեստերով ստուգված
`filterExcludedCandidates()`-ի միջոցով (`open-sse/services/autoCombo/candidateOverrides.ts`)։
Զտիչը **ձախողման դեպքում բաց է**․ չսահմանված apiKeyId/channel-ը կամ DB հարցման ձախողումը
թողնում են հավաքածուն չզտված, այնպես որ առանց վերագրումների կազմաձևման օպերատորը ստանում է այս հնարավորությունից առաջ եղածին
բայթ առ բայթ նույնական երթուղավորում։

**Հետաձգված է հետագա խնդրի համար․** յուրաքանչյուր թեկնածուի կշիռներ + բացահայտ դասակարգում (Մակարդակ 3
— փոխանցվում է առկա կշռված/առաջնահերթության ռազմավարությունների ուղիներին) և յուրաքանչյուր `auto/*` ալիքի համար կոնկրետ
`combo.ts` ռազմավարության ամրակցում (Մակարդակ 4)։ Տե՛ս #7819 պլանը՝ այն բաց հարցի վերաբերյալ, թե արդյոք վերագրումները պետք է մնան յուրաքանչյուր API բանալու համար առանձին, թե դառնան գլոբալ՝ հաշվի առնելով
մեկ վարձակալի մոդելը։

**Կուլիսների հետևում․**

```txt
Հարցում․ { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts-ը հայտնաբերում է նախածանցը
   ↓
createVirtualAutoCombo('coding') → candidatePool՝ ակտիվ կապերից
   ↓
handleComboChat (նույն շարժիչը, ինչ պահպանվող համակցությունների համար)
   ↓
Ավտոմատ գնահատումն ընտրում է լավագույն մատակարարին/մոդելը յուրաքանչյուր հարցման համար
```

**Իրականացման ֆայլեր․**

| Ֆայլ                                                      | Նպատակ                                                 |
| --------------------------------------------------------- | ------------------------------------------------------ |
| `open-sse/services/autoCombo/autoPrefix.ts`               | Նախածանցի վերլուծիչ (`parseAutoPrefix`)                |
| `open-sse/services/autoCombo/virtualFactory.ts`           | Ստեղծում է վիրտուալ `AutoComboConfig` օբյեկտներ        |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | Թեստային կցակետ՝ մատակարարների ռեեստրի նմանակման համար |
| `src/sse/handlers/chat.ts`                                | Ինտեգրում՝ auto նախածանցի կարճ միացում                 |
| `src/shared/constants/providers.ts`                       | `SYSTEM_PROVIDERS.auto` համակարգային գրառում           |

## Համակցությունների անուններ, որոնք համընկնում են իրական մոդելի ID-ի հետ

Համակցությունը, որի `name`-ը նույնական է մոդելի պարզ ID-ին (օրինակ՝
`gpt-5.5` անունով համակցությունը), **կանխամտածված և աջակցվող ձևանմուշ է**, ոչ թե վրիպակ․ սա
յուրաքանչյուր մոդելի ID-ի համար մատակարարի պահուստային ընտրության մեխանիզմն է, որը փաստագրված է
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940)-ում։ Քանի որ համակցության
լուծումը ստուգվում է մոդելի պարզ ID-ի լուծումից առաջ
(`getComboForModel()`՝ `src/sse/services/model.ts`-ում), պարզ
`gpt-5.5` ID-ով հարցումն ուղղորդվում է համակցության թիրախներով (օրինակ՝
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`), այլ ոչ թե անմիջապես
մեկ մատակարարի մոտ․ սա կրկին օգտագործում է համակցությունը վերագրումից առաջ մշակելու առաջնահերթությունը, որը ստեղծվել է
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227)-ի համար և
ռեգրեսիոն եղանակով ստուգվում է `tests/unit/responses-combo-resolution-3227.test.ts` և
`tests/unit/combo-name-codex-responses-rewrite.test.ts` թեստերով։

Իրական մոդելի ID-ն ստվերող անունով համակցության ստեղծումը կամ վերանվանումը
**երբեք չի մերժվում**․ դա կխախտեր այս փաստագրված աշխատանքային հոսքը։ Փոխարենը
(#8530), `POST /api/combos`-ը և `PUT /api/combos/[id]`-ն ավելացնում են չարգելափակող
`warning` դաշտ պատասխանին, երբ (նոր) անունը համընկնում է իրական
մոդելի ID-ի հետ․

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

Գործարկման ժամանակ `scanComboModelNameCollisionsAtBoot()`-ը
(`src/instrumentation-node.ts`) նաև գրանցամատյանում ավելացնում է մեկ տողանոց `[STARTUP]` նախազգուշացում՝
թվարկելով մոդելի ID ստվերող բոլոր առկա համակցությունները, որպեսզի այն օպերատորները, որոնք
դրան բախվել են պատահաբար (այլ ոչ թե կանխամտածված՝ համաձայն #6940-ի), ազդանշան ստանան։
Հայտնաբերման օժանդակ գործառույթը գտնվում է `src/lib/combos/modelNameCollision.ts`-ում։

## Հաճախորդից հատուկ համակցության կանչում

Պահպանված համակցությունները (Կարգավորումներ → Համակցություններ) օգտագործվում են միայն այն դեպքում, երբ հաճախորդը `model` դաշտում ուղարկում է համակցության **ճշգրիտ անունը**․ համակցության անվան մոտավոր կամ մասնակի համընկնում չկա, և `auto/` նախածանց չի օգտագործվում։ Լուծման հերթականությունը (`getComboForModel()`՝ `src/sse/services/model.ts`-ում)․

1. համակցության անվան ճշգրիտ համընկնում (`model: "my-combo"`),
2. `combo/<name>` նախածանց (`model: "combo/my-combo"`),
3. model→combo glob համապատասխանեցումներ (`/api/model-combo-mappings`)։

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

Երկու տարածված սխալ․

- **`auto`-ն չի օգտագործում ձեր համակցությունները։** `auto`/`auto/*`-ն ստեղծում է իր սեփական՝ զրոյական կազմաձևմամբ թեկնածուների հավաքածուն և պահպանված համակցություններին դիմում է միայն այն դեպքում, երբ որևէ համակցություն բառացիորեն անվանված է `auto` (խորհուրդ չի տրվում)։ Համակցության միջոցով ուղղորդելու համար ուղարկեք դրա ճշգրիտ անունը, ոչ թե `auto`։
- **`openrouter/auto`-ն OpenRouter-ի իրական վճարովի արտադրանք է** («Ավտոմատ կերպով լավագույն հասանելին»), ոչ թե OmniRoute-ի կեղծանուն։ Այն OpenRouter-ի գրանցամատյանի միակ ստատիկ մոդելային գրառումն է (`open-sse/config/providers/registry/openrouter/index.ts`) և առանձին է վճարագրվում։ Օգտագործեք Կարգավորումներ → Ուղղորդում → Թաքցնել վճարովի մոդելները՝ այն `auto` հավաքածուներից բացառելու համար։

Այս փաստաթղթում նկարագրված սկզբնական շփոթության վերաբերյալ տե՛ս [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) և [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111)։

## Ինչպես է այն աշխատում (պահպանվող ավտոմատ կոմբինացիաներ)

Auto-Combo Engine-ը յուրաքանչյուր հարցման համար դինամիկորեն ընտրում է լավագույն մատակարարին/մոդելը՝ օգտագործելով **16 գործոնով գնահատման ֆունկցիա** (սահմանված է `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`-ում)։ Լռելյայն կշիռների գումարը `1.0` է, իսկ հատուկ կշիռները վերանորմավորվում են `normalizeScoringWeights()`-ի միջոցով։ Տասնվեց գործոններից երկուսը՝ `cacheAffinity`-ն և `resetWindowAffinity`-ն, ունեն `0` լռելյայն կշիռ։ `reliability`-ն `DEFAULT_WEIGHTS`-ում ունի `0`, սակայն ընդհանուր նշանակության փաթեթներում՝ `0.03`, իսկ `reliability-first`-ում՝ `0.04`, մինչդեռ `quality`-ն փաթեթներում ունի `0.02` (`quality-first`-ում՝ `0.03`)։ Դրանք, այնուամենայնիվ, հաշվարկվում են յուրաքանչյուր թեկնածուի համար, իսկ `cacheAffinity`-ն գնահատականից դուրս կառավարում է հուշման քեշի կրկնօրինակների հեռացումը, ուստի զրոյական լռելյայն կշռով գործոնները պարզապես լռելյայն չեն մասնակցում գնահատմանը, մինչդեռ փաթեթներում մասնակցում են։

### `weighted`-ի իմաստաբանությունը

`weighted`-ը **յուրաքանչյուր հարցման համար համամասնական պատահական ընտրություն է**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), այլ ոչ թե հավասարեցման մեխանիզմ.

- Յուրաքանչյուր հարցում ընտրում է **մեկ** քայլ՝ `weight / totalWeight` հավանականությամբ, իսկ մնացած քայլերը
  տվյալ հարցման համար դասավորվում են ըստ կշռի նվազման՝ որպես պահուստային անցումների շղթա։
- Այն քայլը, որի կշիռը `0` է (կամ բացակայում է), **երբեք չի ընտրվում**, քանի դեռ որևէ այլ քայլի
  կշիռը > 0 է. այն կարող է գործել միայն որպես պահուստային տարբերակ՝ ընտրված քայլի ձախողումից հետո։ Ընտրությունը հավասարաչափ է դառնում միայն այն դեպքում, երբ **բոլոր**
  կշիռները 0 են։
- Այն քայլերը, որոնց բոլոր թիրախներն անհասանելի են՝ մատակարարի circuit breaker-ը `OPEN` է, կապը
  cooldown-ի մեջ է, կամ մոդելն արգելափակված է, հեռացվում են ընտրությունից նախքան այն կատարելը
  (`open-sse/services/combo/targetResolution.ts`), ուստի մեկ հասանելի քայլ կարող է ժամանակավորապես
  հաղթել յուրաքանչյուր հարցման դեպքում։
- `stickyWeightedLimit`-ը (կոմբինացիայի կարգավորում, լռելյայն՝ `1` = անջատված) ամրակցում է ընտրված քայլը նշված քանակի
  հաջորդական հաջողությունների համար՝ նախքան նոր ընտրությունը։

Խիստ հերթափոխի համար օգտագործեք `round-robin`. `weighted`-ի հավասար կշիռներն ապահովում են վիճակագրական, այլ ոչ թե
խիստ հավասարակշռություն։

## Միաձուլման ռազմավարություն

`fusion`-ը միակ ռազմավարությունն է, որը **չի** ընտրում մեկ թիրախ։ Այն հարցումը
զուգահեռ ուղարկում է **պանելի բոլոր մոդելներին**, որից հետո կարգավորվող **դատավոր մոդելը**
պանելի բոլոր պատասխաններից սինթեզում է մեկ վերջնական պատասխան։ Փոխադրվել է սկզբնաղբյուր `decolua/9router`-ից
(OpenRouter-ի Fusion նախագծում)․ իրականացումը գտնվում է `open-sse/services/fusion.ts`-ում։

Աշխատանքի սկզբունքը՝

0. **Գործիքներ պարունակող հարցումների շրջանցում** — այն հարցումը, որը պարունակում է ոչ դատարկ `tools` զանգված,
   իսկ `tool_choice`-ը հստակորեն սահմանված չէ որպես `"none"`, ամբողջությամբ շրջանցում է պանելը․ այն անմիջապես ուղղորդվում է
   մեկ մոդելի (կարգավորված դատավորին կամ `panel[0]`-ին), իսկ `tools`/`tool_choice`-ը
   փոխանցվում են առանց փոփոխության։ Պանելի անդամները գործիքների հասանելիություն չունեն, իսկ դատավորի
   սինթեզման հրահանգը խրախուսում է չարտածել գործիքի կանչեր, ուստի գործակալային/գործիք կանչող հաճախորդները
   սինթեզված արձակի փոխարեն ստանում են գործիքի կանչի իրական որոշում (#6771)։
1. **Զուգահեռ բաշխում** (միայն գործիքներ չպարունակող հարցումների համար) — հարցումը միաժամանակ ուղարկվում է պանելի
   բոլոր մոդելներին՝ հարկադրաբար ոչ հոսքային ռեժիմով և հեռացված գործիքներով (սինթեզման համար դատավորին անհրաժեշտ է
   ամբողջական տեքստ)։
2. **Քվորումից հետո արտոնյալ ժամանակով հավաքագրում** — հենց ստացվում է `minPanel` քանակով պատասխան,
   ուշացող մասնակիցների համար գործարկվում է կարճ արտոնյալ ժամանակաչափ, ապա միաձուլումը շարունակվում է հավաքված
   բոլոր պատասխաններով։ Սա սահմանափակում է ամենադանդաղ մոդելի ազդեցությունը ընդհանուր կատարման ժամանակի վրա՝
   կոշտ ժամանակային սահմանաչափի շրջանակում։
3. **Դատավորի սինթեզում** — պանելի պատասխաններն անանունացվում են (`Source 1`, `Source 2`, … — որպեսզի
   դատավորը գնահատի բովանդակությունը, ոչ թե մոդելի ապրանքանիշը) և փոխանցվում դատավորին, որն ուսումնասիրում է
   համաձայնությունը / հակասությունները / մասնակի ընդգրկումը / եզակի դիտարկումները / բացթողումները, ապա
   գրում է **մեկ** հեղինակավոր պատասխան։ Դատավորի կանչը պահպանում է հաճախորդի սկզբնական
   `stream` դրոշը և գործիքները, ուստի հոսքային փոխանցումն ու հետագա գործիքների օգտագործումը շարունակում են աշխատել։
4. **Սահուն վատթարացում** — պանելի 0 պատասխան → `503`; ուղիղ 1 պահպանված պատասխան → այդ պատասխանը
   վերադարձվում է անմիջապես (միաձուլելու ոչինչ չկա)․ մեկ մոդելից բաղկացած պանելն անմիջապես պատասխանում է։

Պանելի անդամը կարող է նաև լինել `combo-ref` քայլ (`{kind: "combo-ref", comboName: "..."}`), որը հղվում է
մեկ այլ կոմբոյի․ այն լուծվում է որպես **մեկ ամբողջական պանելի ձայն** (լիարժեք ռեկուրսիվ ուղղորդում դեպի
հղված կոմբոն, այլ ոչ թե այդ կոմբոյի սեփական թիրախներին զուգահեռ բաշխում)՝ խորությունից/ցիկլերից պաշտպանության
նույն մեխանիզմով, որն արդեն օգտագործում են `combo-ref` կիրառող մյուս բոլոր ռազմավարությունները (#6764)։

### Կազմաձևում

Կարգավորվում է կոմբոյի `config` բլոբում (սխեմայի տեղափոխում չի պահանջվում՝ այն կրկին օգտագործում է գոյություն ունեցող
`combos` աղյուսակը)․

| Դաշտ                                     | Տեսակ    | Լռելյայն             | Նպատակ                                                                                                                     |
| :--------------------------------------- | :------- | :------------------- | :------------------------------------------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | պանելի առաջին մոդելը | Վերջնական պատասխանը սինթեզող մոդել                                                                                         |
| `config.fusionTuning.minPanel`           | `number` | `2`                  | Մինչև արտոնյալ ժամանակաչափի գործարկումը պահանջվող հաջող պատասխանների քանակը (սահմանափակվում է `[2, panelSize]` միջակայքով) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`               | Քվորումի հասնելուց հետո ուշացողներին սպասելու տևողությունը                                                                 |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`              | Բացարձակ սահմանաչափ, որպեսզի կախված մեկ մոդելը չկասեցնի հարցումը                                                           |

Լռելյայն արժեքները գտնվում են `FUSION_DEFAULTS`-ում (`open-sse/services/fusion.ts`)։

### Օրինակ

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

Այնուհետև կանչեք այն ինչպես ցանկացած կոմբո՝ `{"model":"fusion-panel","messages":[...]}`։

## Վիրտուալ Auto-Combo գործարան

Auto Combo շարժիչը չի պահանջում նախապես սահմանված կոմբոներ։ Փոխարենը, `open-sse/services/autoCombo/virtualFactory.ts`-ը թեկնածուներ է կառուցում դինամիկ կերպով.

1. Կանչում է `getProviderConnections({ isActive: true })`-ը (բոլոր միացված կապերը)
2. Զտում է՝ թողնելով վավեր հավատարմագրեր ունեցողները (API բանալի կամ `hasUsableOAuthToken()`-ի միջոցով ստուգված՝ ժամկետը չլրացած OAuth թոքեն)
3. Համադրում է `getProviderRegistry()`-ի հետ՝ մոդելների հասանելիության և գնագոյացման համար
4. Յուրաքանչյուր `(provider, model, connection)` եռյակի համար կառուցում է `VirtualAutoComboCandidate`
5. Որպես ուղարկման թիրախ ընտրում է `connection.defaultModel`-ը (կամ ռեեստրի առաջին մոդելը)
6. Գնահատում է յուրաքանչյուր թեկնածուի՝ օգտագործելով 16 գործոնով `scorePool()`-ը և տարբերակի կշիռների փաթեթը
7. Վերադարձնում է ստացված՝ հիշողության մեջ գտնվող `AutoComboConfig`-ը `handleComboChat()`-ի համար՝ այն երբեք չպահպանելով DB-ում

Սա նշանակում է, որ **`auto/*`-ը միացված նոր մատակարարի ավելացումն ինքնաբերաբար ընդլայնում է թեկնածուների բազմությունը**՝ առանց կոմբոն ձեռքով խմբագրելու անհրաժեշտության։ Վիրտուալ կոմբոն վերակառուցվում է յուրաքանչյուր հարցման համար, ուստի նոր ավելացված կամ նորից առողջ դարձած կապերն անմիջապես ներառվում են։

## Ինքնավերականգնում

- **Ժամանակավոր բացառում**․ միավոր < 0.2 → բացառվում է 5 րոպեով (աստիճանական հետաձգում, առավելագույնը՝ 30 րոպե)
- **Circuit breaker-ի վիճակի հաշվառում**․ OPEN → ինքնաբերաբար բացառվում է, HALF_OPEN → փորձնական հարցումներ
- **Միջադեպի ռեժիմ**․ >50% OPEN → անջատել ուսումնասիրումը, առավելագույնի հասցնել կայունությունը
- **Վերականգնում հովացման շրջանից հետո**․ բացառումից հետո առաջին հարցումը «փորձնական» է՝ կրճատված ժամանակային սահմանափակմամբ

## Բանդիտային ուսումնասիրում

Հարցումների 5%-ը (կարգավորվող) ուսումնասիրելու նպատակով ուղղորդվում է պատահական մատակարարների։ Միջադեպի ռեժիմում սա անջատված է։

## API

**Առանձին `POST /api/combos/auto` վերջնակետ գոյություն չունի**․ Auto-Combo-ն օգտագործվում է երկու եղանակով.

1. **Առանց կարգավորման (խորհուրդ է տրվում)․** Ուղարկեք զրույցի լրացման ցանկացած հարցում՝ `model: "auto"` կամ `model: "auto/<variant>"` արժեքով։ Վիրտուալ գործարանը յուրաքանչյուր հարցման համար կառուցում է կոմբոն՝ առանց պահպանման և առանց API կանչերի անհրաժեշտության։

2. **Պահպանվող կոմբո՝ `strategy: "auto"`-ով․** Ստեղծեք սովորական կոմբո `POST /api/combos`-ի միջոցով և սահմանեք `strategy: "auto"`, ինչպես նաև `config.auto.weights` / `config.auto.candidatePool`։ Օգտագործվում է նույն գնահատման շարժիչը․ կոմբոն պահվում է `combos`-ում և կարող է կրկին օգտագործվել ID-ով։

Հայտնաբերման համար `GET /api/combos/auto`-ն թվարկում է յուրաքանչյուր տարբերակ՝ իր հաշվարկված թեկնածուների բազմության, ինչպես նաև `context_length` / `max_output_tokens` արժեքների հետ․ դրանք թեկնածուների բազմության պատուհանների միջև ԱՌԱՎԵԼԱԳՈՒՅՆ արժեքներն են։ Հաճախորդները (օրինակ՝ opencode հավելումը) պետք է հրապարակեն այս արժեքները `0`-ի փոխարեն․ զրոյական համատեքստն ամբողջությամբ անջատում է opencode-ի ավտոմատ սեղմումը՝ թույլ տալով, որ նստաշրջաններն աճեն այնքան ժամանակ, մինչև gateway-ի պատմության մաքրումը ոչնչացնի համատեքստը։ ԱՌԱՎԵԼԱԳՈՒՅՆ արժեքը հրապարակելն անվտանգ է, քանի որ auto-combo-ի համատեքստի նախնական զտիչը չափազանց մեծ հարցումներն ուղղորդում է մեծ պատուհան ունեցող թեկնածուներին։

```bash
# Օգտագործում առանց կարգավորման (առանց կոմբո ստեղծելու)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Պահպանվող auto կոմբո՝ սովորական combos վերջնակետի միջոցով
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto երթուղիչի ռազմավարություններ

Պահպանվող `strategy: "auto"` կոմբոները կարող են `config.routerStrategy`-ն (կամ հին
`config.auto.routerStrategy`-ն) սահմանել հետևյալ արժեքներից մեկով.

- `rules` — լռելյայն կշռված գնահատում
- `score` — ընտրում է կարգավորված ամենաբարձր կշռված միավորը։ Ճշգրիտ հավասարության դեպքում պահպանվում է կարգավորված
  թեկնածուների հերթականությունը, իսկ գոյություն ունեցող `explorationRate`-ը նմուշառում է ամբողջ դասակարգված բազմությունից։
- `cost` / `eco` — ամենաէժան առողջ մատակարարը
- `latency` / `fast` — նվազագույն p95 ուշացում՝ հուսալիության տուգանքով
- `sla-aware` / `sla` — նախապատվություն է տալիս այն թեկնածուներին, որոնք բավարարում են p95 ուշացման, սխալների հաճախականության և ընտրովի
  ծախսային SLO-ների պահանջները
- `lkgp` — սկզբում վերջին հայտնի լավ մատակարարը

### Երթուղիչի ռազմավարությունները մանրամասն

Auto-combo շարժիչը տրամադրում է 6 փոխարինելի **RouterStrategy** իրականացումներ, որոնք
կարող եք փոխել `config.routerStrategy`-ի (կամ հին `config.auto.routerStrategy`-ի) միջոցով։
Յուրաքանչյուր ռազմավարություն թեկնածուների բազմությունից ընտրում է մեկ մատակարար՝ ստանալով `RoutingContext`
(առաջադրանքի տեսակ, գործիքների/տեսողության հուշումներ, թոքենների գնահատված քանակ, ընտրովի SLA քաղաքականություն, ընտրովի
վերջին հայտնի լավ մատակարար)։

#### 1. `rules` (լռելյայն) — 16 գործոնով կշռված գնահատում

Փաթաթում է գոյություն ունեցող գնահատման շարժիչը։ Զտում և հեռացնում է `OPEN` վիճակում գտնվող circuit-breaker
թեկնածուներին, ապա գործարկում է `scorePool()`-ը՝ ընթացիկ առաջադրանքի տեսակով և `getTaskFitness()`-ով՝
ընտրելով ամենաբարձր միավորն ունեցող մատակարարին։

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**Երբ օգտագործել**․ Լռելյայն տարբերակն է։ Օգտագործեք, երբ ցանկանում եք հավասարակշռված փոխզիջում բոլոր ազդանշանների միջև։

**Այլանուն**․ `rules` (այլանուն չունի)

---

#### 2. `cost` / `eco` — ամենաէժան առողջ մատակարարը

Թեկնածուների բազմությունը դասավորում է ըստ `costPer1MTokens`-ի (աճման կարգով) և ընտրում ամենաէժանը։
Նախ զտում և հեռացնում է `OPEN` թեկնածուներին։

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Երբ օգտագործել**․ Ծախսերի նկատմամբ զգայուն աշխատանքային բեռների, փաթեթային մշակման կամ ֆոնային առաջադրանքների համար։

**Այլանուններ**․ `cost`, `eco`

---

#### 3. `latency` / `fast` — նվազագույն p95 ուշացում՝ հուսալիության տուգանքով

Տեսակավորում է ըստ `p95LatencyMs + (errorRate * 1000)` արժեքի։ Սխալների մակարդակի տույժն ապահովում է, որ
անվստահելի մատակարարներն ավելի ցածր դասակարգվեն, նույնիսկ եթե նրանց անվանական ուշացումը փոքր է։

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Երբ օգտագործել**․ Ուշացման նկատմամբ զգայուն աշխատանքային բեռնվածությունների համար, ինչպիսիք են իրական ժամանակի զրույցը, ինքնալրացումը կամ
ծրագրավորման ինտերակտիվ օգնականները։

**Այլընտրանքային անուններ**․ `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — ուշացման/սխալների/արժեքի SLO-ին համապատասխանություն

Յուրաքանչյուր թեկնածուին գնահատական է տալիս՝ ըստ այն բանի, թե որքանով է այն բավարարում կազմաձևված SLO քաղաքականությանը․

| Գործոն                  | Կշիռ | Բանաձև                                               |
| ----------------------- | ---- | ---------------------------------------------------- |
| Ուշացման գնահատական     | 35%  | `threshold / max(value, ε)`                          |
| Սխալների գնահատական     | 35%  | `threshold / max(value, ε)`                          |
| Առողջության գնահատական  | 15%  | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)    |
| Արժեքի գնահատական       | 10%  | `threshold / max(value, ε)` կամ հակադարձ նորմավորված |
| Կայունության գնահատական | 5%   | ուշացման ստանդարտ շեղման հակադարձ նորմավորված արժեք  |

Երբ `hardConstraints: true` է, թեկնածուները նախ դասակարգվում են ըստ **խախտման գնահատականի**
(թե որքանով են նրանք գերազանցում որևէ SLO), այնուհետև՝ ըստ համակցված գնահատականի։ Հակառակ դեպքում օգտագործվում է միայն
համակցված գնահատականը։

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... յուրաքանչյուր թեկնածուին գնահատում է քաղաքականության համեմատ՝ { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA դաշտեր** (սահմանվում են համակցված կազմաձևում)․

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**Երբ օգտագործել**․ Խիստ ուշացման, սխալների մակարդակի կամ արժեքի սահմանաչափեր ունեցող արտադրական աշխատանքային բեռնվածությունների համար։

**Այլընտրանքային անուններ**․ `sla-aware`, `sla`

---

#### 5. `lkgp` — նախ՝ վերջին հայտնի աշխատող մատակարարը

Սկզբում փորձում է օգտագործել **վերջին հայտնի աշխատող մատակարարին** (եթե սահմանված է), ապա հետադարձ անցում է կատարում դեպի
`rules` ռազմավարությունը։ Օգտակար է աշխատաշրջանի կպչունության համար․ զրույցի հետագա
հարցումները մշակում է նույն մատակարարը։

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Հետադարձ անցում դեպի rules ռազմավարությունը
    return getStrategy("rules").select(pool, context);
  }
}
```

**Երբ օգտագործել**․ Բազմափուլ զրույցների համար, երբ ցանկանում եք, որ նույն մատակարարը մշակի
հետագա հարցումները (օրինակ՝ քեշավորման, համատեքստի շարունակականության կամ գնագոյացման հետևողականության համար)։

**Այլընտրանքային անուն**․ `lkgp` (այլընտրանքային անուն չկա)

---

### Ուղղորդիչի հատուկ ռազմավարություններ

Հանրային API-ի միջոցով կարող եք գրանցել `RouterStrategy`-ի ձեր սեփական իրականացումը․

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Ուղղորդման ձեր տրամաբանությունն այստեղ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

Այնուհետև օգտագործեք այն․

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

---

### Ուղղորդիչի ռազմավարության ընտրության ուղեցույց

| Օգտագործման դեպք              | Ռազմավարություն | Պատճառ                                    |
| ----------------------------- | --------------- | ----------------------------------------- |
| Հավասարակշռված բեռնվածություն | `rules`         | Լռելյայն․ հաշվի է առնում բոլոր գործոնները |
| Նվազագույնի հասցնել արժեքը    | `cost`          | Միշտ ընտրում է ամենաէժանը                 |
| Նվազագույնի հասցնել ուշացումը | `latency`       | Ընտրում է ամենաարագ վստահելի մատակարարին  |
| Խիստ SLO-ներ                  | `sla-aware`     | Զտում է ըստ p95/սխալների/արժեքի շեմերի    |
| Բազմափուլ զրույց              | `lkgp`          | Աշխատաշրջանի կպչունություն                |

SLA-ին իրազեկ դաշտեր․

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

## Առաջադրանքներին համապատասխանություն

30-ից ավելի մոդելներ գնահատվել են առաջադրանքների 6 տեսակների համար (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`)։ Աջակցվում են wildcard ձևանմուշները (օրինակ՝ `*-coder` → կոդավորման բարձր գնահատական)։

## Auto տարբերակների ամփոփում

Ներառյալ պարզ `auto`-ն (կանխադրված) և `autoPrefix.ts`-ում հայտարարված 6 `AutoVariant` արժեքները՝ կան **կանչման ենթակա մոդելների 7 ID-ներ**․

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant`-ն ինքնին թվարկում է 6 արժեք․ 7-րդ տարբերակը «առանց տարբերակի» պարզ `auto`-ն է, որը `parseAutoPrefix()`-ը մշակում է որպես `variant: undefined`։)

## Ինչպես են մակարդակները ներառվում Auto-Combo-ում

16 գործոնից բաղկացած գնահատման գործառույթը (`open-sse/services/autoCombo/scoring.ts`) մակարդակի
պատկանելությունը դիտարկում է որպես երկու ազդանշան՝ `tierPriority` (0.0476) և `tierAffinity` (0.0476)։ Ամբողջական
`DEFAULT_WEIGHTS` հավաքածուի համար տե՛ս վերևում ներկայացված կանոնական [գնահատման գործոնների աղյուսակը](#how-it-works-persisted-auto-combos)․ ըստ փաթեթների վերագրումները (ship-fast/cost-saver/quality-first/
offline-friendly) նշված են «Քաշերի պրոֆիլներն ըստ փաթեթի» աղյուսակում։

Միայն մակարդակը **չի** պարտադրում, որ Tier 1-ն ընտրվի առաջինը․ եթե Tier 1-ի ուշացումը մեծ է կամ
արժեք-որակ հարաբերակցությունը ոչ օպտիմալ է, ընտրվում է Tier 2-ը։ Մակարդակների հերթականությունը պարտադրելու համար օգտագործեք կոմբոյի
`priority` ռազմավարությունը և մատակարարներին դասավորեք ըստ մակարդակի։

Tier 1-ը (բաժանորդագրություն) մեծապես նախընտրելու համար ավելացրեք `tierPriority`-ի քաշը․

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

Մակարդակների սահմանումների և մատակարարների դասակարգման համար տե՛ս `docs/marketing/TIERS.md`։

## Թեստավորում և ծածկույթ

### Ուղղորդման որոշումների դետերմինիստական մատրից (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts`-ը ապացուցում է բոլոր 19
հանրային ռազմավարությունների ուղղորդման **որոշումը**՝ սկզբից մինչև վերջ իրական կոմբո-խողովակաշարի միջոցով՝ ընդօրինակված վերին հոսանքով։
Ծածկույթը ներառում է․

- Բոլոր 19 `ROUTING_STRATEGY_VALUES` ռազմավարությունները (ordered, weighted, cost, context, fusion, …)։
- `quota-share`-ը (ներքին)՝ սկզբից մինչև վերջ․ DRR-ի արդարություն + հագեցվածության դեպքում առաջնահերթության նվազեցում՝ իրական
  `selectQuotaShareTarget` միջերեսի միջոցով (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`)։
- `context-relay`-ի համընդհանուր փոխանցման ծածկույթը՝ թիրախների յուրաքանչյուր քանակի համար։

Այս թեստային փաթեթը գործարկվում է CI-ում (`test:integration` առաջադրանք)՝ `--test-concurrency=1` և
`--test-force-exit` դրոշներով, ուստի այն դետերմինիստական է և չի պահանջում իրական հավատարմագրեր։

### Պայմանական իրական smoke թեստեր (CI-ում ՉԵՆ գործարկվում՝ իրական մատակարարներ)

| Հրաման                                 | Ինչ է այն անում                                                                                              |
| :------------------------------------- | :----------------------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | Իրական ուղղորդում նույն գործընթացի ներսում՝ `RUN_COMBO_LIVE=1`-ով․ ստեղծում է գործող OmniRoute DB-ի snapshot |
| `npm run test:combo:live:vps`          | HTTP կանչեր գործող OmniRoute սերվերին (սահմանեք `COMBO_LIVE_BASE_URL`)                                       |
| `npm run test:combo:live:vps:failover` | Նույնը՝ նախապես նախատեսված failover սցենարներով                                                              |

Այս smoke թեստերը ստուգում են իրական հաղորդակցման ուղին (կոմբո → մատակարար → ավարտ)։ Դրանք
միտումնավոր բացառված են CI-ից, քանի որ պահանջում են իրական հավատարմագրեր և VPS հասանելիություն։
