## Ընդհանուր նկարագիր

OmniRoute-ի կառավարման API-ի բոլոր երթուղիները դասակարգվում են պաշտպանության
երեք մակարդակներից մեկում։ Դասակարգումը ստատիկ է, սահմանված է `src/server/authz/routeGuard.ts`-ում
և գնահատվում է նախքան նույնականացման որևէ այլ ճյուղի գործարկումը։

## Մակարդակներ

### Մակարդակ 1 — LOCAL_ONLY

**Կիրառվում է՝** `isLocalOnlyPath(path)` → loopback հոսթի ստուգում
**Շրջանցում:** Լռելյայնորեն՝ ոչինչ։ Նեղ բացառություն `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ում գտնվող ուղիների համար, երբ հարցումը պարունակում է վավեր API բանալի `manage` տիրույթով (տե՛ս [Կառավարման տիրույթի բացառություն](#manage-scope-carve-out))։

Այս երթուղիները ստեղծում են ենթապրոցեսներ կամ կատարում են runtime կոդ։ Դրանք ոչ-loopback տրաֆիկին բացահայտելը թույլ կտա հարձակվողին, ով ստացել է վավեր JWT (օրինակ՝ Cloudflared/Ngrok թունելի միջոցով), գործարկել պրոցեսների ստեղծումը՝ հայտնի CVE դաս ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))։

**Ինչ է GHSA-fhh6-4qxv-rpqj-ը (հարձակման դասը):** կառավարման/գործակալի սերվերը բացահայտում է վերջնակետ, որը գործարկում է ենթապրոցես (`npm install`, `node`, բրաուզեր, պրոքսի, `git`, `tar`, …)։ Եթե այդ վերջնակետը հասանելի է հոսթից դուրս՝ քանի որ օպերատորը OmniRoute-ը դրել է nginx/Cloudflare/Tailscale թունելի հետևում, և JWT-ն արտահոսել է, կամ աուտենտիֆիկացիան սխալ է կազմաձևվել՝ հարձակվողը «կանչել API»-ն վերածում է «կատարել հրաման հոսթի վրա» (հեռակա կոդի կատարում)։ OmniRoute-ը սա կանխում է՝ կիրառելով **loopback հոսթի ստուգում անվերապահորեն, ցանկացած աուտենտիֆիկացիայի ստուգումից առաջ**, յուրաքանչյուր spawn-ի հնարավորություն ունեցող երթուղու վրա. թունելի միջոցով արտահոսած թոքենը դեռ չի կարող հասնել spawn-ին։

**LOCAL_ONLY-ի ամբողջական հավաքածուն։** Հեղինակավոր աղբյուրը `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`-ն է `src/server/authz/routeGuard.ts`-ում. ստորև բերված աղյուսակը արտացոլում է ներկայիս վիճակը։ `check-route-guard-membership` դարպասը թվարկում է յուրաքանչյուր `route.ts` spawn-ի հնարավորություն ունեցող պրեֆիքսների տակ և ձախողում է CI-ը, եթե որևէ մեկը դասակարգված չէ որպես local-only։

#### Կառավարման շրջանակի բացառություն

`LOCAL_ONLY` ուղիների ենթաբազմությանը ԿԱՐՈՂ է մուտք գործվել նաև ոչ-loopback-ից, եթե և միայն եթե հարցումը պարունակում է `Authorization: Bearer <api-key>`, որի մետատվյալները ներառում են `manage` շրջանակը (կամ `admin`): Բացառությունը հստակորեն սահմանափակված է յուրաքանչյուր ուղու համար `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ի միջոցով, այնպես որ ցանկացած նոր `LOCAL_ONLY` ուղու համար լռելյայնը մնում է խիստ-loopback: Անվավեր հարցումները և ոչ-manage բանալիներով հարցումները դեռ մերժվում են `403 LOCAL_ONLY` պատասխանով:

Այսօր միակ շրջանցելի նախածանցը `/api/mcp/` է: `/api/cli-tools/runtime/` և `/api/services/` դիտավորյալ բացառված են, քանի որ դրանք կարող են ստեղծել կամայական ենթապրոցեսներ (`npm install`, `node`), ինչը հենց այն `CVE` դասն է, որը `LOCAL_ONLY` մակարդակը գոյություն ունի կանխելու համար:

**#7895 — `mcp:connect` նեղ շրջանակ.** `/api/mcp/` բացառությունը ԸՆԴՈՒՆՈՒՄ է նաև Bearer բանալի, որը պարունակում է նեղ `mcp:connect` շրջանակը (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), որը ստուգվում է `hasMcpConnectOrManageScope()` ֆունկցիայի միջոցով `src/server/authz/policies/management.ts`-ում: Սա վերաբերում է ՄԻԱՅՆ `/api/mcp/`-ին — `mcp:connect`-ը ոչինչ չի տրամադրում որևէ այլ կառավարման երթուղու վրա (ներառյալ ցանկացած այլ `LOCAL_ONLY` շրջանցման նախածանց, եթե երբևէ ավելացվի), և այն դիտավորյալ բացառված է `MANAGEMENT_API_KEY_SCOPES`-ից: `manage`/`admin` պարունակող բանալին դեռ անցնում է բացառությունը ճիշտ նույն կերպ, ինչպես նախկինում. `mcp:connect`-ը ավելի ցածր արտոնություն ունեցող այլընտրանք է հեռավոր MCP-միայն զանգահարողների համար, ովքեր չպետք է լայն կառավարման մուտքի կարիք ունենան:

| Հարցում                                          | Ուղի                       | Արդյունք                       |
| ------------------------------------------------ | -------------------------- | ------------------------------ |
| Ոչ-loopback, առանց Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY                 |
| Ոչ-loopback, Bearer `manage` շրջանակով           | `/api/mcp/*`               | Թույլատրել                     |
| Ոչ-loopback, Bearer `mcp:connect` շրջանակով      | `/api/mcp/*`               | Թույլատրել                     |
| Ոչ-loopback, Bearer առանց `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                 |
| Ոչ-loopback, Bearer `mcp:connect` շրջանակով      | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                 |
| Ոչ-loopback, Bearer `manage` շրջանակով           | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                 |
| Loopback, ցանկացած/առանց Bearer                  | ցանկացած LOCAL_ONLY        | Թույլատրել (դարպասն անցնում է) |

#### Օպերատորի ուղեցույց և աուդիտ

Եթե դուք գործարկում եք OmniRoute-ը հակադարձ պրոքսիի կամ թունելի հետևում (nginx, Caddy, Cloudflare Tunnel, Tailscale, Ngrok), loopback ստուգումը դեռ պաշտպանում է վերոնշյալ spawn-ունակ երթուղիները — հարցումը, որի հաճախորդի հասցեն ոչ-loopback է, մերժվում է `403 LOCAL_ONLY` պատասխանով նախքան նույնականացումը, այնպես որ արտահոսած JWT-ն չի կարող հասնել spawn-ի: Մնում են օպերատորի երկու պարտականությունները.

- **Մի "շտկեք" `403` սխալը՝ հաճախորդի IP-ն որպես loopback կեղծելով:** `X-Forwarded-For: 127.0.0.1` սահմանելը, կամ պրոքսի, որը վերագրում է աղբյուրի հասցեն loopback-ի, վերաբացում է հենց այն `RCE` դասը, որը փակում է այս մակարդակը: Բացահայտեք կառավարման վահանակը/API-ն պրոքսիի միջոցով — երբեք spawn-ունակ երթուղիները:
- **Պահպանեք `manage`-շրջանակի շրջանցումը նվազագույնի:** Միայն `/api/mcp/`-ն է շրջանցելի, և միայն `manage`-շրջանակի API բանալիով: `SPAWN_CAPABLE_PREFIXES`-ը երբեք չի կարող ավելացվել շրջանցման ցուցակին — `zod` սխեման մերժում է դրանք, իսկ `isLocalOnlyBypassableByManageScope`-ը մերժում է դրանք գործարկման ժամանակ (խորը պաշտպանություն), ինչը նշանակում է կառավարման վահանակի "չի կարող շրջանցելի դարձվել" արտահայտությունը: Դինամիկ-սեգմենտ և ստատիկ-ուղի spawn-ունակ երթուղիները `/api/providers/`-ի տակ (օրինակ՝ `/login`, `/refresh-cursor`) ծածկված են `regex`-ի վրա հիմնված `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` ուղեկցողով `src/shared/constants/spawnCapablePrefixes.ts`-ում, այլ ոչ թե հարթ `SPAWN_CAPABLE_PREFIXES` զանգվածով — հարթ զանգվածը պետք է ծածկեր ամբողջ `/api/providers/` նախածանցը դրանք բռնելու համար, ինչը չափազանց կընդլայնի երթուղիների ծառը, որը հեռավոր կառավարման վահանակները օրինականորեն օգտագործում են մատակարարի `CRUD`-ի համար:

**Մուտքի աուդիտ** — ստուգելու համար, որ ոչինչ հեռավոր հոստից չի հասնում այս երթուղիներին:

- Բացեք **Թույլտվությունների Գույքագրումը** `/dashboard/settings/security` հասցեում. այն ցուցադրում է `LOCAL_ONLY` պրեֆիքսների իրական ցուցակը, որ պրեֆիքսները շրջանցելի են, և կոմպիլյացիայի ժամանակի ստեղծման հնարավորություն ունեցող («չի կարող շրջանցելի դարձվել») հավաքածուն։
- Որոնեք ձեր հակադարձ պրոքսիի / մուտքի մատյաններում վերոնշյալ պրեֆիքսները՝ զուգորդված ոչ-loopback հաճախորդի հասցեի հետ։ Ցանկացած նման հարցում, որը վերադարձրել է `200`՝ `403 LOCAL_ONLY`-ի փոխարեն, նշանակում է, որ պրոքսին թաքցնում է իրական հաճախորդի IP-ն. շտկեք պրոքսին։
- `403 LOCAL_ONLY` OmniRoute-ի մատյաններում այս ուղիներից մեկի համար պաշտպանության համակարգն է, որն աշխատում է ինչպես նախատեսված է, այլ ոչ թե սխալ, որը պետք է ճնշել։

### Մակարդակ 2 — ALWAYS_PROTECTED

**Իրականացվում է՝** `isAlwaysProtectedPath(path)` → բաց թողնել `requireLogin=false` շրջանցումը
**Շրջանցում՝** Ոչինչ, երբ `requireLogin=false`; `JWT` միշտ պահանջվում է

Այս ուղիները կործանարար են կամ անդառնալի։ Դրանք թույլատրելը «առանց գաղտնաբառի» տեղադրման դեպքում կնշանակեր, որ նույն LAN-ի ցանկացած անձ կարող է ջնջել տվյալների բազան կամ անջատել սերվերի պրոցեսը։

| Ուղի                                      | Պատճառ                                                                             |
| :---------------------------------------- | :--------------------------------------------------------------------------------- |
| `/api/shutdown`                           | Ավարտում է սերվերի պրոցեսը                                                         |
| `/api/settings/database`                  | Տվյալների բազայի արտահանում, ներմուծում և ջնջում                                   |
| `/api/db-backups`                         | Տվյալների բազայի ամբողջական կրկնօրինակման արխիվի մուտք                             |
| `/api/settings/export-json`               | Արտահանում է կարգավորումների ամբողջական բլոբը (ներառյալ գաղտնիքները)               |
| `/api/settings/import-json`               | Փոխարինում է կարգավորումների ամբողջական բլոբը                                      |
| `/api/providers/health-autopilot/actions` | Կատարում է ավտոպիլոտի վերականգնման գործողություններ                                |
| `/api/settings/obsidian`                  | Ստեղծում է բազմակի օգտագործման `WebDAV` հավատարմագրեր ցանկացած պահոցի արմատի համար |

**Պատասխան խախտման դեպքում՝** `401 Authentication required`

`/api/settings/obsidian`-ը ներառում է իր `/webdav` ենթաուղին. `POST`-ը `WebDAV` ֆայլային ծառայությունը (որը մատուցվում է հատուկ `Node` շերտի կողմից `Next.js`-ից առաջ, այս խողովակաշարից դուրս) ուղղում է զանգողի կողմից ընտրված արմատին և արտացոլում է նոր ստեղծված Basic հավատարմագրերը, `DELETE`-ը պտտում է դրանք, իսկ ծնող `POST`-ը պահում է Obsidian REST API թոքենը։ `GHSA-62vw`-ը միայն քողարկել է `GET` գաղտնաբառի բացահայտումը. թողարկումը դեռևս գտնվում էր fail-open մակարդակում (`GHSA-7pq4-8pvv-rx7r`)։ `enableObsidianVaultSync()`-ը լրացուցիչ մերժում է այն պահոցը, որը գտնվում է տվյալների գրացուցակի ներսում կամ պարունակում է այն։

### Նոր տեղադրման բութստրապը միայն loopback է — իրական հավասարի կողմից, ոչ թե `Host`-ի

Երբ կառավարման գաղտնաբառը կազմաձևված չէ (և չկա `INITIAL_PASSWORD`), `src/shared/utils/apiAuth.ts`-ում `isAuthRequired()` ֆունկցիան անանուն բութստրապը բաց է պահում **միայն loopback հավասարների համար**։ Loopback-ը որոշվում է վստահելի հավասարի ազդանշաններից, հերթականությամբ՝ թոքենով դրոշմված իրական TCP հավասարը (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ինչը տեսնում է քաղաքականությունը), խողովակաշարի սեփական `AUTHZ_HEADER_PEER_LOCALITY` որոշումը (ինչը տեսնում են երթուղու մշակողները, վստահելի է միայն այն դեպքում, երբ `OMNIROUTE_PEER_STAMP_TOKEN`-ը սահմանված է), կամ իրական սոքեթի հավասարը ուղղակի զանգողների համար։ `Host` / `nextUrl.hostname`-ը երբեք հաշվի չեն առնվում, և առաջին գաղտնաբառի գրումը (`POST /api/settings/require-login`) ենթարկվում է նույն սահմանափակմանը, այլ ոչ թե բաց է ցանցի յուրաքանչյուր հավասարի համար (`GHSA-7pq4-8pvv-rx7r`)։ `managementPolicy`-ն իր `peerContext` որոշումը բացահայտորեն փոխանցում է ներքև, այնպես որ ՕՐԻԳԻՆԱԼ (նախքան հեռացումը) հարցման վերնագրերը երբեք չեն որոշում այն։

### Մակարդակ 3 — MANAGEMENT (լռելյայն)

Բոլոր մյուս կառավարման ուղիները։ Նույնականացումը պահանջվում է, եթե `requireLogin=false`-ը կազմաձևված չէ։ `CLI` թոքենները կարող են նույնականացնել այս ուղիները (loopback + վավեր `HMAC`)։

## Գնահատման հերթականությունը

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → անցնել հաջորդ քայլին
     → ոչ loopback, manage շրջանակով Bearer
        ԵՎ isLocalOnlyBypassableByManageScope    → թույլատրել (management_key)
     → հակառակ դեպքում                           → մերժել 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → թույլատրել (system)
  3. hasValidCliToken(headers)?
     → թույլատրել (cli) [loopback + timingSafeEqual HMAC ստուգում]
  4. isAlwaysProtectedPath(path) կամ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → թույլատրել (dashboard_session)
     → manage շրջանակով Bearer՝ շրջանցում չթույլատրող ուղու վրա?
        → թույլատրել (management_key)
     → մերժել 401/403
  5. requireLogin=false?
     → թույլատրել (anonymous)
```

Քայլ 1-ի manage շրջանակի ճյուղը միակ նույնականացված ուղին է, որը կարող է բավարարել
LOCAL_ONLY երթուղու պահանջները։ Նույնականացման backend-ի խափանման դեպքում վերադարձվում է 503 (ոչ թե 403), որպեսզի
ժամկետանց DB-ն աննկատ չանցնի «մերժել» ռեժիմի։

## Կատարողական գործընթաց գործարկելու ունակ նոր երթուղու ավելացում

1. Ուղու նախածանցն ավելացրեք `LOCAL_ONLY_API_PREFIXES`-ում՝
   `src/server/authz/routeGuard.ts`
2. `tests/unit/authz/routeGuard.test.ts`-ում ավելացրեք թեստ, որը հաստատում է, որ
   `isLocalOnlyPath()`-ը նոր նախածանցի համար վերադարձնում է true
3. **Երբեք մի բաց թողեք այս քայլը** — տե՛ս Խիստ կանոն #15-ը `CLAUDE.md`-ում
4. Որոշեք՝ արդյո՞ք այս երթուղին ՆԱԵՎ պետք է ներառվի `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ում։
   Լռելյայն պատասխանը **ոչ** է։ Միացրեք միայն այն դեպքում, երբ երթուղին անվտանգ է
   manage շրջանակի տիրապետողին հասանելի դարձնելու համար (այսինքն՝ ՉԻ գործարկում օգտատիրոջ կողմից վերահսկվող կամայական կոդ)։

## Manage շրջանակով շրջանցելի ուղու ավելացում

1. Հաստատեք, որ երթուղին չի կատարում օգտատիրոջ տրամադրած կոդ կամ հրամաններ։ Եթե
   կատարում է, կանգ առեք․ այս բացառությունը ճիշտ գործիքը չէ։
2. Նախածանցն ավելացրեք `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ին՝
   `src/server/authz/routeGuard.ts`
3. `tests/unit/authz/management-policy.test.ts`-ում ավելացրեք ծածկույթ հարցման բոլոր չորս
   ձևերի համար՝ առանց Bearer-ի (403), manage Bearer (թույլատրել), ոչ manage Bearer
   (403), ինչպես նաև յուրաքանչյուր նախածանցի հետընթացի թեստ, որը հաստատում է, որ `/api/cli-tools/runtime/*`-ը
   նույնիսկ manage Bearer-ի դեպքում մնում է միայն խիստ loopback-ի համար։

## Անվտանգության մակարդակների փաստաթղթավորումը OpenAPI-ում

`docs/openapi.yaml`-ում նոր երթուղի ավելացնելիս կիրառեք համապատասխան
vendor ընդլայնումը, եթե երթուղին դասակարգված է `routeGuard.ts`-ի կողմից.

| routeGuard.ts դասակարգում                | YAML ծանոթագրություն           | Կիրարկում                                                        |
| ---------------------------------------- | ------------------------------ | ---------------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                | `x-loopback-only: true`        | Անվերապահորեն արգելափակվում է ոչ loopback հարցումների համար      |
| `ALWAYS_PROTECTED_API_PATHS`             | `x-always-protected: true`     | Նույնականացումը պարտադիր է նույնիսկ `requireLogin=false` դեպքում |
| Ներքին admin/debug երթուղի               | `x-internal: true`             | Լռելյայն թաքցված է /dashboard/api-endpoints-ից                   |
| Չկա (հանրային / ստանդարտ նույնականացում) | (ծանոթագրություն անհրաժեշտ չէ) | Ստանդարտ՝ `requireLogin`-ով կառավարվող հասանելիություն           |

### Վավերացում

Երկու սկրիպտ ապահովում են YAML ծանոթագրությունների և `routeGuard.ts`-ի միջև համապատասխանությունը.

- `scripts/check/check-openapi-coverage.mjs` — ձախողվում է, եթե ծածկույթը < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — ձախողվում է, եթե `x-loopback-only` կամ
  `x-always-protected` ծանոթագրությունները շեղվում են կոմպիլյացիայի ժամանակի հաստատուններից

Երկու սկրիպտներն էլ գործարկվում են pre-commit hook-ում և CI-ում։

### Կեղծ դրական արդյունքի կանոն

Եթե `x-always-protected`-ը կամ `x-loopback-only`-ը նշված է այնպիսի երթուղու վրա, որը ՉԿԱ
`routeGuard.ts` հաստատունում, ծածկույթի սկրիպտը ձախողվում է։ Լուծումը միշտ YAML-ը
`routeGuard.ts`-ի կողմից փաստացի կիրառվող կանոններին համապատասխանեցնելն է, ոչ թե երթուղիները `routeGuard.ts`-ում
ավելացնելը՝ առանց կիրարկման տրամաբանությունը նույնպես իրականացնելու։
