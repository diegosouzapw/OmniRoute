## Ընդհանուր նկարագիր

OmniRoute-ի կառավարման API-ի բոլոր երթուղիները դասակարգվում են պաշտպանության
երեք մակարդակներից մեկում։ Դասակարգումը ստատիկ է, սահմանված է `src/server/authz/routeGuard.ts`-ում
և գնահատվում է նախքան նույնականացման որևէ այլ ճյուղի գործարկումը։

## Մակարդակներ

### Մակարդակ 1 — LOCAL_ONLY

**Կիրարկվում է՝** `isLocalOnlyPath(path)` → loopback հոսթի ստուգում
**Շրջանցում՝** Լռելյայն չկա։ Սահմանափակ բացառություն է նախատեսված
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ում գտնվող ուղիների համար, երբ հարցումն ունի
`manage` տիրույթով վավեր API բանալի (տե՛ս [Manage տիրույթի բացառությունը](#manage-scope-carve-out))։

Այս երթուղիները ստեղծում են ենթապրոցեսներ կամ կատարում են գործարկման միջավայրի կոդ։ Դրանք
ոչ loopback տրաֆիկի համար հասանելի դարձնելը վավեր JWT ձեռք բերած հարձակվողին (օրինակ՝
Cloudflared/Ngrok թունելի միջոցով) թույլ կտար նախաձեռնել պրոցեսների ստեղծում՝ հայտնի CVE
դաս ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))։

**Ինչ է GHSA-fhh6-4qxv-rpqj-ը (հարձակման դասը)՝** կառավարման/գործակալային սերվերը
բացահայտում է վերջնակետ, որը գործարկում է ենթապրոցես (`npm install`, `node`, դիտարկիչ,
պրոքսի, `git`, `tar`, …)։ Եթե այդ վերջնակետը հասանելի է հոսթից դուրս, քանի որ
օպերատորը OmniRoute-ը տեղադրել է nginx/Cloudflare/Tailscale թունելի հետևում և JWT-ն
արտահոսել է, կամ նույնականացումը սխալ է կազմաձևվել, հարձակվողը «API կանչը» վերածում է
«հոսթի վրա հրաման գործարկելուն» (հեռավար կոդի կատարում)։ OmniRoute-ը կանխում է սա՝
պրոցես ստեղծելու ունակ յուրաքանչյուր երթուղու համար **անվերապահորեն՝ նույնականացման
ցանկացած ստուգումից առաջ, կիրառելով loopback հոսթի ստուգում**․ թունելի միջոցով
արտահոսած թոքենը միևնույն է չի կարող հասնել պրոցեսի ստեղծմանը։

**LOCAL_ONLY-ի ամբողջական բազմությունը։** Հեղինակավոր աղբյուրը
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`-ն է՝
`src/server/authz/routeGuard.ts`-ում․ ստորև բերված աղյուսակն արտացոլում է ընթացիկ վիճակը։
`check-route-guard-membership` դարպասը թվարկում է պրոցես ստեղծելու ունակ
նախածանցների տակ գտնվող յուրաքանչյուր `route.ts` և ձախողում է CI-ն, եթե դրանցից որևէ մեկը

**Պատասխան խախտման դեպքում՝** `403 LOCAL_ONLY`

#### Բացառություն՝ manage շրջանակի համար

LOCAL_ONLY ուղիների ենթաբազմությունը ԿԱՐՈՂ Է հասանելի լինել նաև ոչ loopback հասցեից, եթե և
միայն եթե հարցումը պարունակում է `Authorization: Bearer <api-key>`, որի
մետատվյալները ներառում են `manage` շրջանակը (կամ `admin`)։ Բացառությունը յուրաքանչյուր ուղու
համար բացահայտորեն կառավարվում է `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ի միջոցով, որպեսզի
ցանկացած նոր LOCAL_ONLY ուղու լռելյայն վարքագիծը մնա խիստ loopback։ Չնույնականացված
հարցումները և ոչ manage բանալիներով հարցումները նախկինի պես մերժվում են
`403 LOCAL_ONLY` պատասխանով։

Այս պահին շրջանցելի միակ նախածանցը `/api/mcp/`-ն է։ `/api/cli-tools/runtime/`-ը և
`/api/services/`-ը միտումնավոր բացառված են, քանի որ կարող են գործարկել կամայական
ենթագործընթացներ (`npm install`, `node`), իսկ LOCAL_ONLY մակարդակը ստեղծվել է հենց
այդ CVE դասը կանխելու համար։

**#7895 — `mcp:connect` նեղ շրջանակ՝** `/api/mcp/` բացառությունը ՆԱԵՎ ընդունում է
նեղ `mcp:connect` շրջանակ ունեցող Bearer բանալի
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), որը ստուգվում է
`src/server/authz/policies/management.ts`-ում գտնվող `hasMcpConnectOrManageScope()`-ի միջոցով։
Սա սահմանափակված է ՄԻԱՅՆ `/api/mcp/`-ով. `mcp:connect`-ը որևէ այլ
կառավարման երթուղու համար ոչ մի թույլտվություն չի տալիս (ներառյալ LOCAL_ONLY-ի շրջանցման ցանկացած այլ նախածանց,
եթե երբևէ այդպիսին ավելացվի), և այն միտումնավոր բացառված է
`MANAGEMENT_API_KEY_SCOPES`-ից։ `manage`/`admin` ունեցող բանալին նախկինի պես անցնում է
բացառությամբ. `mcp:connect`-ը նվազ արտոնյալ այլընտրանք է
հեռավար, միայն MCP օգտագործող կանչողների համար, որոնց չպետք է անհրաժեշտ լինի կառավարման լայն հասանելիություն։

#### Օպերատորի ուղեցույց և աուդիտ

Եթե OmniRoute-ը գործարկում եք հակադարձ պրոքսիի կամ թունելի հետևում (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), loopback ստուգումը շարունակում է պաշտպանել վերոնշյալ՝
գործընթացներ գործարկելու ունակ երթուղիները. այն հարցումը, որի հաճախորդի հասցեն loopback չէ, մերժվում է
`403 LOCAL_ONLY` պատասխանով՝ **մինչև նույնականացման գործարկումը**, ուստի արտահոսած JWT-ն չի կարող հասնել գործընթացի գործարկմանը։ Մնում է
օպերատորի երկու պարտականություն՝

- **Մի՛ «շտկեք» 403-ը՝ հաճախորդի IP-ն կեղծելով որպես loopback։** Սահմանելով
  `X-Forwarded-For: 127.0.0.1` կամ օգտագործելով պրոքսի, որը աղբյուրի հասցեն վերագրում է որպես
  loopback, կրկին բացվում է հենց այն RCE դասը, որը փակում է այս մակարդակը։ Պրոքսիի
  միջոցով հասանելի դարձրեք կառավարման վահանակը/API-ն, բայց երբեք՝ գործընթացներ գործարկելու ունակ երթուղիները։
- **Manage շրջանակի շրջանցումը պահեք նվազագույնի վրա։** Շրջանցելի է միայն `/api/mcp/`-ն և
  միայն `manage` շրջանակով API բանալիով։ `SPAWN_CAPABLE_PREFIXES`-ը երբեք չի կարող
  ավելացվել շրջանցման ցանկում. zod սխեման մերժում է դրանք, իսկ
  `isLocalOnlyBypassableByManageScope`-ը մերժում է դրանք գործարկման ժամանակ (խորքային պաշտպանություն),
  ինչը կառավարման վահանակում արտահայտված է որպես «չի կարող շրջանցելի դառնալ»։ Դինամիկ հատվածներով
  և ստատիկ ուղիներով՝ գործընթացներ գործարկելու ունակ երթուղիները `/api/providers/`-ի ներքո (օրինակ՝ `/login`,
  `/refresh-cursor`) ծածկվում են կանոնավոր արտահայտությունների վրա հիմնված `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` ուղեկիցով՝
  `src/shared/constants/spawnCapablePrefixes.ts`-ում, այլ ոչ թե հարթ
  `SPAWN_CAPABLE_PREFIXES` զանգվածով. դրանք որսալու համար հարթ զանգվածը պետք է ընդգրկեր
  ամբողջ `/api/providers/` նախածանցը, ինչը չափազանց կընդլայներ այն երթուղիների ծառը,
  որը հեռավար կառավարման վահանակներն օրինաչափորեն օգտագործում են մատակարարների CRUD գործողությունների համար։

**Հասանելիության աուդիտ** — համոզվելու համար, որ հոսթից դուրս ոչինչ չի հասնում այս երթուղիներին՝

- Բացեք **Authorization Inventory**-ն `/dashboard/settings/security` հասցեում․ այնտեղ ցուցադրվում են
  ընթացիկ LOCAL_ONLY նախածանցների ցանկը, շրջանցելի նախածանցները և կոմպիլյացիայի պահին
  սահմանված՝ գործընթացներ գործարկելու ունակ («չեն կարող շրջանցելի դարձվել») հավաքածուն։
- Ձեր reverse-proxy-ի / հասանելիության մատյաններում փնտրեք վերոնշյալ նախածանցները՝ զուգակցված
  ոչ loopback հաճախորդի հասցեի հետ։ Ցանկացած նման հարցում, որը `403 LOCAL_ONLY`-ի փոխարեն
  վերադարձրել է `200`, նշանակում է, որ proxy-ն քողարկում է հաճախորդի իրական IP-ն․ շտկեք proxy-ն։
- Այս ուղիներից որևէ մեկի համար OmniRoute-ի մատյաններում առկա `403 LOCAL_ONLY`-ը նշանակում է,
  որ պաշտպանությունն աշխատում է նախատեսվածի համաձայն, այլ ոչ թե սխալ է, որը պետք է անտեսել։

### Մակարդակ 2 — ALWAYS_PROTECTED

**Պատասխան խախտման դեպքում՝** `401 Authentication required`

`/api/settings/obsidian`-ը ներառում է իր `/webdav` ենթուղին․ `POST`-ը WebDAV ֆայլային ծառայությունը,
որը սպասարկվում է հատուկ Node շերտի կողմից՝ Next.js-ից առաջ և այս հոսքագծից դուրս, ուղղորդում է կանչողի
ընտրած արմատային պանակին և վերադարձնում նոր ստեղծված Basic հավատարմագրերը, `DELETE`-ը փոխարինում է դրանք,
իսկ ծնող `POST`-ը պահպանում է Obsidian REST API թոքենը։ GHSA-62vw-ն միայն քողարկում էր `GET`-ով գաղտնաբառի
բացահայտումը․ տրամադրումը դեռևս fail-open մակարդակում էր (GHSA-7pq4-8pvv-rx7r)։ `enableObsidianVaultSync()`-ը
նաև մերժում է այն պահոցը, որը տվյալների պանակն է, գտնվում է դրա ներսում կամ պարունակում է այն։

### Նոր տեղակայման սկզբնական կարգավորումը միայն loopback-ի համար է՝ ըստ իրական peer-ի, ոչ թե `Host`-ի

Եթե կառավարման գաղտնաբառ սահմանված չէ (և չկա `INITIAL_PASSWORD`), ապա
`src/shared/utils/apiAuth.ts`-ում գտնվող `isAuthRequired()`-ը անանուն սկզբնական կարգավորումը բաց է պահում
**միայն loopback peer-ների համար**։ Loopback-ը որոշվում է վստահելի peer ազդանշաններից՝ հետևյալ հերթականությամբ․
թոքենով դրոշմված իրական TCP peer-ը (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, որը տեսնում է քաղաքականությունը),
հոսքագծի սեփական `AUTHZ_HEADER_PEER_LOCALITY` որոշումը (որը տեսնում են երթուղու մշակիչները և որին վստահում են միայն,
երբ `OMNIROUTE_PEER_STAMP_TOKEN`-ը սահմանված է), կամ ուղղակի կանչողների իրական socket peer-ը։ `Host` /
`nextUrl.hostname`-ը երբեք չի օգտագործվում, իսկ առաջին գաղտնաբառի գրանցումը
(`POST /api/settings/require-login`) ենթարկվում է նույն սահմանափակմանը՝ բոլոր
ցանցային peer-ների համար բաց լինելու փոխարեն (GHSA-7pq4-8pvv-rx7r)։ `managementPolicy`-ն իր սեփական `peerContext`
որոշումը բացահայտորեն փոխանցում է ներքև, որպեսզի ORIGINAL (մինչև մաքրումը) հարցման վերնագրերը երբեք չորոշեն այն։

### Մակարդակ 3 — MANAGEMENT (լռելյայն)

Կառավարման մնացած բոլոր երթուղիները։ Նույնականացումը պարտադիր է, եթե
`requireLogin=false` կարգավորված չէ։ CLI թոքենները կարող են նույնականացնել այս երթուղիները (loopback + վավեր HMAC)։

## Գնահատման հերթականությունը

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → անցնել հաջորդ քայլին
     → ոչ loopback, manage շրջանակով Bearer
        ԵՎ isLocalOnlyBypassableByManageScope    → թույլատրել (management_key)
     → հակառակ դեպքում                           → մերժել 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → թույլատրել (system)
  3. hasValidCliToken(headers)?
     → թույլատրել (cli) [loopback + timingSafeEqual HMAC ստուգում]
  4. isAlwaysProtectedPath(path) կամ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → թույլատրել (dashboard_session)
     → manage շրջանակով Bearer՝ շրջանցում չթույլատրող ուղու վրա?
        → թույլատրել (management_key)
     → մերժել 401/403
  5. requireLogin=false?
     → թույլատրել (anonymous)
```

Քայլ 1-ի manage շրջանակի ճյուղը միակ նույնականացված ուղին է, որը կարող է բավարարել
LOCAL_ONLY երթուղու պահանջները։ Նույնականացման backend-ի խափանման դեպքում վերադարձվում է 503 (ոչ թե 403), որպեսզի
ժամկետանց DB-ն աննկատ չանցնի «մերժել» ռեժիմի։

## Կատարողական գործընթաց գործարկելու ունակ նոր երթուղու ավելացում

1. Ուղու նախածանցն ավելացրեք `LOCAL_ONLY_API_PREFIXES`-ում՝
   `src/server/authz/routeGuard.ts`
2. `tests/unit/authz/routeGuard.test.ts`-ում ավելացրեք թեստ, որը հաստատում է, որ
   `isLocalOnlyPath()`-ը նոր նախածանցի համար վերադարձնում է true
3. **Երբեք մի բաց թողեք այս քայլը** — տե՛ս Խիստ կանոն #15-ը `CLAUDE.md`-ում
4. Որոշեք՝ արդյո՞ք այս երթուղին ՆԱԵՎ պետք է ներառվի `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ում։
   Լռելյայն պատասխանը **ոչ** է։ Միացրեք միայն այն դեպքում, երբ երթուղին անվտանգ է
   manage շրջանակի տիրապետողին հասանելի դարձնելու համար (այսինքն՝ ՉԻ գործարկում օգտատիրոջ կողմից վերահսկվող կամայական կոդ)։

## Manage շրջանակով շրջանցելի ուղու ավելացում

1. Հաստատեք, որ երթուղին չի կատարում օգտատիրոջ տրամադրած կոդ կամ հրամաններ։ Եթե
   կատարում է, կանգ առեք․ այս բացառությունը ճիշտ գործիքը չէ։
2. Նախածանցն ավելացրեք `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ին՝
   `src/server/authz/routeGuard.ts`
3. `tests/unit/authz/management-policy.test.ts`-ում ավելացրեք ծածկույթ հարցման բոլոր չորս
   ձևերի համար՝ առանց Bearer-ի (403), manage Bearer (թույլատրել), ոչ manage Bearer
   (403), ինչպես նաև յուրաքանչյուր նախածանցի հետընթացի թեստ, որը հաստատում է, որ `/api/cli-tools/runtime/*`-ը
   նույնիսկ manage Bearer-ի դեպքում մնում է միայն խիստ loopback-ի համար։

## Անվտանգության մակարդակների փաստաթղթավորումը OpenAPI-ում

`docs/openapi.yaml`-ում նոր երթուղի ավելացնելիս կիրառեք համապատասխան
vendor ընդլայնումը, եթե երթուղին դասակարգված է `routeGuard.ts`-ի կողմից.

| routeGuard.ts դասակարգում                | YAML ծանոթագրություն           | Կիրարկում                                                        |
| ---------------------------------------- | ------------------------------ | ---------------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                | `x-loopback-only: true`        | Անվերապահորեն արգելափակվում է ոչ loopback հարցումների համար      |
| `ALWAYS_PROTECTED_API_PATHS`             | `x-always-protected: true`     | Նույնականացումը պարտադիր է նույնիսկ `requireLogin=false` դեպքում |
| Ներքին admin/debug երթուղի               | `x-internal: true`             | Լռելյայն թաքցված է /dashboard/api-endpoints-ից                   |
| Չկա (հանրային / ստանդարտ նույնականացում) | (ծանոթագրություն անհրաժեշտ չէ) | Ստանդարտ՝ `requireLogin`-ով կառավարվող հասանելիություն           |

### Վավերացում

Երկու սկրիպտ ապահովում են YAML ծանոթագրությունների և `routeGuard.ts`-ի միջև համապատասխանությունը.

- `scripts/check/check-openapi-coverage.mjs` — ձախողվում է, եթե ծածկույթը < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — ձախողվում է, եթե `x-loopback-only` կամ
  `x-always-protected` ծանոթագրությունները շեղվում են կոմպիլյացիայի ժամանակի հաստատուններից

Երկու սկրիպտներն էլ գործարկվում են pre-commit hook-ում և CI-ում։

### Կեղծ դրական արդյունքի կանոն

Եթե `x-always-protected`-ը կամ `x-loopback-only`-ը նշված է այնպիսի երթուղու վրա, որը ՉԿԱ
`routeGuard.ts` հաստատունում, ծածկույթի սկրիպտը ձախողվում է։ Լուծումը միշտ YAML-ը
`routeGuard.ts`-ի կողմից փաստացի կիրառվող կանոններին համապատասխանեցնելն է, ոչ թե երթուղիները `routeGuard.ts`-ում
ավելացնելը՝ առանց կիրարկման տրամաբանությունը նույնպես իրականացնելու։
