OmniRoute-ը կենտրոնացված թույլատրված ցանկի միջոցով վերահսկում է, թե որ **դիտարկիչի սկզբնաղբյուրները** կարող են կարդալ այլ սկզբնաղբյուրներից ստացված պատասխանները։ Մոդելը **լռելյայն արգելափակող է**․
ոչ մի սկզբնաղբյուր թույլատրված չէ, քանի դեռ այն հստակ չեք թույլատրել։ Այս էջը նկարագրում է, թե ինչպես է որոշվում թույլատրված ցանկը,
ինչ է իրականում հասանելի դարձնում `CORS_ALLOW_ALL=true`-ը (և, որ կարևոր է, ինչ
**չի** հասանելի դարձնում), ինչպես անվտանգ կարգավորել մշակման ու արտադրական միջավայրերը, և կատարման ժամանակի այն նախազգուշացումը,
որը կառավարման վահանակը ցուցադրում է, երբ համընդհանուր թույլտվությունն ակտիվ է։

**Ճշմարտության աղբյուր՝** `src/server/cors/origins.ts` (`resolveAllowedOrigin`,
`applyCorsHeaders`, `getCorsStatus`)։ Թույլատրված ցանկը կիրառվում է մեկ անգամ՝
միջանկյալ ծրագրաշարում (`src/server/authz/pipeline.ts`)․ առանձին երթուղիների մշակիչներն ինքնուրույն չեն սահմանում
`Access-Control-Allow-Origin`։

## Ինչպես է որոշվում սկզբնաղբյուրը

Յուրաքանչյուր հարցման համար միջանկյալ ծրագրաշարը հաշվարկում է `Access-Control-Allow-Origin`-ի արժեքը
հետևյալ հերթականությամբ․

1. **`CORS_ALLOW_ALL=true`** (կամ հին `CORS_ORIGIN=*`) → հետ ուղարկել կանչողի
   `Origin`-ը (կամ `*`, երբ `Origin` վերնագիր չկա)՝ ավելացնելով `Vary: Origin`,
   որպեսզի քեշերը ճիշտ աշխատեն։ Նույն `applyCorsHeaders()` նեղ անցակետը նաև
   `Vary: Accept-Encoding` է ավելացնում token-ով նույնականացվող
   `/v1*`/`/v1beta*` մակերեսի՝ մարմին պարունակող յուրաքանչյուր 2xx պատասխանին (`relaxForTokenAuth`, RFC 9110 §12.5.5, խնդիր #6737), որպեսզի
   ստորին մակարդակի/ընդհանուր քեշերը կարողանան ճիշտ տարբերակել սեղմված և չսեղմված
   տարբերակները։
2. Հակառակ դեպքում հարցման `Origin`-ը նորմալացվում է (վերածվում փոքրատառերի, իսկ վերջի շեղ գիծը
   հեռացվում է) և համեմատվում **միավորված թույլատրված ցանկի** հետ․
   - env **`CORS_ALLOWED_ORIGINS`** — ստորակետերով բաժանված ցանկ, և
   - կատարման ժամանակի **`corsOrigins`** կարգավորումը (Կառավարման վահանակ → Անվտանգություն → _CORS-ի թույլատրված
     սկզբնաղբյուրներ_), որը ներմուծվում է `setRuntimeAllowedOrigins()`-ի միջոցով՝
     `src/lib/config/runtimeSettings.ts`-ից։
3. Համընկնում չկա → **`Access-Control-Allow-Origin` վերնագիր չի ուղարկվում**։ Դիտարկիչն
   արգելափակում է այլ սկզբնաղբյուրից ընթերցումը։ Սա նախատեսված լռելյայն արգելափակող վարքագիծն է։

| Միջավայրի փոփոխական    | Նշանակություն                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------------------ |
| `CORS_ALLOWED_ORIGINS` | Թույլատրվող ճշգրիտ սկզբնաղբյուրների CSV ցանկ (խորհուրդ է տրվում)։                                      |
| `CORS_ALLOW_ALL`       | `true`/`1` → հետ ուղարկել ցանկացած սկզբնաղբյուր (համընդհանուր թույլտվություն)։ Միայն մշակման համար։    |
| `CORS_ORIGIN`          | Հին տարբերակ։ `*`-ը գործում է `CORS_ALLOW_ALL`-ի նման, իսկ մեկ արժեքն ավելացվում է թույլատրված ցանկին։ |

## Սպառնալիքների մոդել — ինչ է իրականում հասանելի դարձնում `CORS_ALLOW_ALL=true`-ը

OWASP-ի ընդհանուր նախազգուշացումը («համընդհանուր CORS = ցանկացած կայք կարող է կանչել ձեր API-ն») արժե
լուրջ ընդունել, սակայն OmniRoute-ի ազդեցության շրջանակը **ավելի նեղ է, քան ընդհանուր դեպքում**՝
իրականացման մեկ կոնկրետ հանգամանքի պատճառով․

> **Կենտրոնական `applyCorsHeaders()`-ը երբեք չի ուղարկում
> `Access-Control-Allow-Credentials`։** Դիտարկիչը չի տրամադրի այլ սկզբնաղբյուրից ստացված _հավաստագրված_
> (cookie պարունակող) պատասխանը, եթե սերվերը չուղարկի
> `Access-Control-Allow-Credentials: true`։ OmniRoute-ի ընդհանուր CORS ուղին դա երբեք
> չի անում։

Ահա թե դա ինչ է նշանակում յուրաքանչյուր մակերեսի համար՝ նույնիսկ `CORS_ALLOW_ALL=true`-ի դեպքում․

| Մակերես                                      | Նույնականացման մեխանիզմ       | Համընդհանուր CORS-ի ազդեցությունը                                                                                                                                                                                                                                                     |
| -------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Կառավարման վահանակ / MANAGEMENT `/api/*`     | Cookie-ով աշխատաշրջան         | Սկզբնաղբյուրը հետ է ուղարկվում, սակայն **առանց `Allow-Credentials`-ի** դիտարկիչը **արգելափակում է** հավաստագրված ընթերցումը։ Վնասաբեր այլ սկզբնաղբյուրի կայքը **չի կարող կարդալ** ձեր նույնականացված կառավարման վահանակի պատասխանները, իսկ աշխատաշրջանի cookie-ն հասանելի չի դառնում։ |
| Հաճախորդի API `/v1/*`, `/v1beta/*`           | Bearer / `x-api-key` վերնագիր | Արդեն իսկ **նախագծմամբ թույլատրող է** (`relaxForTokenAuth`)․ դիտարկիչները երբեք ինքնաբերաբար չեն կցում `Authorization`/`x-api-key`, ուստի հարձակվողի էջը չի կարող տրամադրել ձեր բանալին։ `CORS_ALLOW_ALL`-ը չի ընդլայնում սա։                                                         |
| Հանրային, միայն ընթերցման (`/api/health`, …) | Չկա                           | Գաղտնի չէ․ համընդհանուր թույլտվությունն անվնաս է։                                                                                                                                                                                                                                     |

Այսպիսով, `CORS_ALLOW_ALL=true`-ի **մնացորդային** ազդեցությունը սահմանափակվում է հետևյալով․ (ա)
արդեն իսկ առանց նույնականացման հասանելի տվյալների՝ ոչ հավաստագրված, այլ սկզբնաղբյուրից կատարվող **ընթերցումներ**, և (բ)
կառավարման երթուղիներում CORS-ի **նախնական հարցման անցնելու** թույլտվություն, որոնք, միևնույն է, պահանջում են նույնականացում,
որը այլ սկզբնաղբյուրի էջը չի կարող տրամադրել։ Ընդհանուր CORS ուղու վրա սա **չի** հանդիսանում աշխատաշրջանի զավթման կամ
հավաստագրերի գողության ուղի։

### Մեկ իրական բացառություն — `/api/v1/agents/`

Cloud-Agent-ի երթուղիները (`/api/v1/agents/{health,credentials,tasks,tasks/[id]}`) սահմանում են
իրենց **սեփական** CORS վերնագրերը
(`src/lib/cloudAgent/api.ts`, `getCloudAgentCorsHeaders`) և **ուղարկում են**
`Access-Control-Allow-Origin: <origin>|*`-ը՝
`Access-Control-Allow-Credentials: true`-ի հետ միասին։ Սա միակ մակերեսն է, որտեղ
սկզբնաղբյուրի հետուղարկումն ու հավաստագրերը համատեղվում են, և այն **կախված չէ
`CORS_ALLOW_ALL`-ից**։ Այս երթուղիները կառավարման նույնականացում են պահանջում
(`requireManagementAuth`)․ այն օպերատորները, որոնք կառավարման վահանակը հասանելի են դարձնում հոսթից դուրս, պետք է
իմանան, որ սա միակ տեղն է, որտեղ պատասխանի վերնագրերը թույլ են տալիս այլ սկզբնաղբյուրից հավաստագրված ընթերցում։
Այն ճշգրիտ թույլատրված ցանկով սահմանափակելը հետևվում է
CORS-ի այս ուղեցույցից առանձին։

## Արտադրական միջավայրի ստուգացանկ

- **Արտադրական միջավայրում երբեք մի սահմանեք `CORS_ALLOW_ALL=true`։** Թողեք այն չսահմանված։
- Սահմանեք սկզբնաղբյուրների **հստակ** ցանկ՝ կամ միջավայրի փոփոխականի, կամ Security ներդիրի դաշտի միջոցով.

  ```bash
  CORS_ALLOWED_ORIGINS="https://app.example.com, https://admin.example.com"
  ```

- Եթե OmniRoute-ն աշխատում է հակադարձ պրոքսիի / թունելի (nginx, Caddy, Cloudflare
  Tunnel, Tailscale) հետևում, CORS-ը ձեր միակ վերահսկման միջոցը **չէ**․ loopback երթուղիների
  պաշտպանիչ մեխանիզմը շարունակում է պաշտպանել գործընթացներ մեկնարկելու ունակ երթուղիները (տե՛ս
  [ROUTE_GUARD_TIERS](./ROUTE_GUARD_TIERS.md))։ Մի կեղծեք
  `X-Forwarded-For: 127.0.0.1`-ը՝ 403 սխալը «շտկելու» համար․ դա կրկին բացում է RCE դասի
  խոցելիությունը, որը փակում է երթուղիների պաշտպանիչ մեխանիզմը։
- Ստուգեք կատարման միջավայրի վիճակը․ վահանակը **մշտական սաթագույն ազդագիր** է ցուցադրում
  Dashboard → Security → Authorization Inventory բաժնում, երբ
  `CORS_ALLOW_ALL=true`-ն ակտիվ է, իսկ `/api/settings/authz-inventory`-ը վերադարձնում է
  `cors: { allowAll, allowedOrigins }` փաթեթ, որը մոնիթորինգի գործիքները կարող են պարբերաբար հարցնել։

## Մշակման հարմարություն — թույլատրեք կոնկրետ տեղային սկզբնաղբյուրներ

Նույնիսկ մշակման միջավայրում համընդհանուր նշանի կարիքը հազվադեպ է լինում։ Թույլատրեք միայն ձեր օգտագործած մշակման սերվերները.

```bash
# Vite (5173) + Next.js (3000) մշակման սերվերներ, որոնք դիմում են տեղային OmniRoute-ին
CORS_ALLOWED_ORIGINS="http://localhost:5173, http://localhost:3000"
```

Սկզբնաղբյուրները համեմատվում են՝ առանց տառաչափը հաշվի առնելու և վերջի շեղագիծն անտեսելով, ուստի
`http://localhost:3000`-ը և `http://localhost:3000/`-ը համարժեք են։ Նույն CSV-ն
կարելի է կատարման ժամանակ սահմանել **Dashboard → Security → CORS Allowed Origins** բաժնում՝ առանց
վերագործարկման։

## API բանալիներն ընդդեմ cookie նստաշրջանների

- **Bearer / `x-api-key` (`/v1/*` ինֆերենսի մակերեսը).** դիտարկիչները երբեք
  դրանք ինքնաբերաբար չեն կցում։ Այստեղ CORS-ը նշանակալի արգելք չէ․ արգելքը API բանալին է,
  ինչի պատճառով այդ մակերեսը միտումնավոր թույլատու է, որպեսզի դիտարկիչի և
  Electron հաճախորդները կարողանան կարդալ պատասխանները, որոնց հասանելիության իրավունքն արդեն ունեն։
- **Cookie նստաշրջան (վահանակը).** պաշտպանված է լռելյայն՝ մերժմամբ փակվող վարքագծով **և**
  ընդհանուր ուղու վրա `Access-Control-Allow-Credentials`-ի բացակայությամբ։ Որևէ թույլատու
  կազմաձևում մի ներառեք կառավարման/վահանակի սկզբնաղբյուրները․ դրանք պետք է շարունակեն
  ճշգրտորեն մերժմամբ փակ մնալ։

## Օրինակ․ հակադարձ պրոքսի OmniRoute-ի առջև

CORS-ը կիրարկվում է հենց OmniRoute-ի կողմից, ուստի պրոքսին սովորաբար **չպետք է** ավելացնի կամ
վերագրի `Access-Control-*` վերնագրերը (կրկնակի վերնագրերը խախտում են դիտարկիչների աշխատանքը)։ Ավարտեք TLS-ը
և վերահասցեագրեք հարցումները՝ թողնելով, որ OmniRoute-ը պատասխանի նախնական հարցմանը.

```nginx
# nginx — վերահասցեագրել OmniRoute-ին․ այստեղ ՉՆԵՐՄՈՒԾԵԼ Access-Control-*
location / {
    proxy_pass http://127.0.0.1:20128;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    # X-Forwarded-For-ը ՉՍԱՀՄԱՆԵԼ 127.0.0.1-ի․ դա չեզոքացնում է loopback երթուղիների պաշտպանիչ մեխանիզմը։
}
```

Թույլատրված դիտարկիչային սկզբնաղբյուրները սահմանեք OmniRoute-ում (`CORS_ALLOWED_ORIGINS` կամ
Security ներդիր), այլ ոչ թե պրոքսիում։
