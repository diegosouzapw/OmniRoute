OmniRoute-ը հրապարակում է npm + Docker արտեֆակտներ։ Այս վերահսկիչները ապահովում են ծագման ապացույցներ,
գույքագրում (SBOM) և CVE սկանավորում․ դրանք բոլորն էլ OSS են և ինտեգրված են թողարկման աշխատանքային հոսքերին։
**Նախ՝ խորհրդատվական** մոտեցում — այժմ դրանք միայն հաղորդում են խնդիրների մասին, իսկ 1-ին
հաջող թողարկումից հետո կդառնան արգելափակող։

| Վերահսկիչ                | Գործիք                                         | Որտեղ                            | Արգելափակո՞ւմ է                | Արդյունք                                                             |
| ------------------------ | ---------------------------------------------- | -------------------------------- | ------------------------------ | -------------------------------------------------------------------- |
| SLSA ծագում (npm)        | `npm --provenance` (OIDC)                      | `npm-publish.yml`                | միայն եթե հրապարակումը ձախողվի | npmjs կրծքանշան / `npm audit signatures`                             |
| npm SBOM                 | `@cyclonedx/cyclonedx-npm`                     | `npm-publish.yml`                | միայն եթե ստեղծումը ձախողվի    | Թողարկման ակտիվ + արտեֆակտ                                           |
| Պատկերի SBOM             | `anchore/sbom-action` (syft)                   | `docker-publish.yml` (միավորում) | խորհրդատվական                  | CycloneDX արտեֆակտ                                                   |
| Trivy CVE (SARIF)        | `aquasecurity/trivy-action`                    | `docker-publish.yml` (միավորում) | խորհրդատվական                  | SARIF (HIGH+CRITICAL) → Անվտանգության ներդիր                         |
| Trivy CRITICAL վերահսկիչ | `aquasecurity/trivy-action`                    | `docker-publish.yml` (միավորում) | **արգելափակող**                | `exit-code: '1'`՝ ուղղելի CRITICAL-ի դեպքում                         |
| osv vulnCount            | `osv-scanner` (`check:vuln-ratchet --ratchet`) | `ci.yml` (`quality-extended`)    | **արգելափակող**                | աստիճանաբար խստացնում է `metrics.vulnCount`-ը (ուղղություն՝ նվազում) |
| OpenSSF Scorecard        | `ossf/scorecard-action`                        | `scorecard.yml` (cron)           | խորհրդատվական                  | SARIF → Անվտանգություն + կրծքանշան                                   |

Պատկերի CVE աստիճանական սահմանափակումը `docker-publish.yml`-ում օգտագործում է **երկու քայլ**․ SARIF քայլը
(`HIGH,CRITICAL`, `exit-code: 0`) HIGH+CRITICAL խնդիրները տեսանելի է պահում Անվտանգության ներդիրում՝
առանց արգելափակման, իսկ _CRITICAL վերահսկիչի_ քայլը (`severity: CRITICAL`, `ignore-unfixed: true`,
`exit-code: 1`) ձախողում է թողարկումը, եթե կա CRITICAL CVE, **որի համար հասանելի է ուղղում**։ `ignore-unfixed`-ը
կանխում է թողարկման արգելափակումը բազային պատկերի այն CVE-ի պատճառով, որի համար վերին հոսքում շտկում չկա։

## ⚠️ CVE փոփոխականություն (արգելափակող osv/Trivy վերահսկիչներ)

osv-ն և Trivy-ն կախվածությունները համեմատում են CVE տվյալների բազաների հետ, որոնք **շարունակաբար աճում են**։ Այն PR-ը,
որը **որևէ կախվածություն չի փոփոխում**, կարող է հանկարծ ձախողվել, քանի որ գոյություն ունեցող կախվածության մեջ
բացահայտվել է նոր CVE (osv՝ չափված `vulnCount` > ելակետային արժեք, Trivy՝ պատկերում հայտնվել է նոր
ուղղելի CRITICAL)։ **Սա արգելափակող CVE վերահսկիչի ՍՊԱՍՎՈՂ գործառնական վարքագիծն է,
ոչ թե արտադրանքի հետընթաց։**

Երբ osv-ն կամ Trivy-ն ձախողվում են նոր բացահայտված CVE-ի պատճառով, լուծումը հետևյալն է․

1. **Թարմացրեք խնդրահարույց կախվածությունը** (նախընտրելի տարբերակ) — անցեք շտկված տարբերակին՝ օգտագործելով `package.json`-ի
   `overrides`-ը (անցումային կախվածությունների համար), կամ վերակառուցեք պատկերը շտկված բազային պատկերի հիման վրա։
2. **Եթե վերին հոսքում շտկում չկա՝**
   - **osv․** վերահաստատեք `metrics.vulnCount`-ի ելակետը `config/quality/quality-baseline.json`-ում
     (`npm run quality:ratchet -- --update`-ը չի ներառում առանձին վերահսկիչները․ արժեքը փոփոխեք
     ձեռքով՝ `direction:down`)՝ ավելացնելով հիմնավորման նշում + հետևման խնդիր։
   - **Trivy․** `.trivyignore`-ում ավելացրեք գրառում (յուրաքանչյուր տողում՝ CVE-ID)՝ հիմնավորման
     մեկնաբանությամբ + հետևման խնդրով։ `ignore-unfixed: true`-ն արդեն ավտոմատ կերպով ներառում է
     շտկումներ չունեցող CVE-ները։

Երկու վերահսկիչներն էլ **անվտանգ կերպով ԲԱՑ ԵՆ ԹՈՂՆՈՒՄ** (ելք 0), երբ գործիքը բացակայում է կամ չափումը
ձախողվում է (osv-scanner-ը PATH-ում չէ, osv.dev/ցանցն անհասանելի է, JSON-ն անվավեր է)․
**չափման** ձախողումը երբեք չի արգելափակում, արգելափակում է միայն **չափված** հետընթացը։

## Հետագա աշխատանքներ․ Scorecard-ի խորհրդատվական ռեժիմից → արգելափակող

Scorecard-ի հաշվետվությամբ 1-ին հաջող թողարկումից հետո՝

- Scorecard․ գնահատականի աստիճանական սահմանափակում (ամրագրում է չափված գնահատականը․ այն չի կարող նվազել)։

Լրացնում է 7-րդ փուլի վերահսկիչները (osv-scanner, gitleaks, actionlint+zizmor)․ zizmor-ը
ստուգում է հենց աշխատանքային հոսքերը, իսկ Scorecard-ը չափում է շտեմարանի ընդհանուր վիճակը։
