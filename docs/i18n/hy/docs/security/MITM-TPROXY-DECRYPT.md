TPROXY թափանցիկ վերծանումը OmniRoute-ի **5-րդ որսման ռեժիմն** է՝ նախատեսված
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM ստեկի համար։ Այն Linux-ում որսում և **վերծանում է** տեղային ելքային HTTPS տրաֆիկը՝
օգտագործելով միջուկի TPROXY-ը և քաղաքականությունների վրա հիմնված երթուղավորումը՝ **առանց** `/etc/hosts`-ը կեղծելու և
**առանց** ՕՀ-ի համահամակարգային պրոքսիի կարգավորումները փոփոխելու։ Այն հարմար է առանց գրաֆիկական միջերեսի
աշխատանքային միջավայրերի համար (չկան DNS փոփոխություններ, որոնք պետք է մաքրել), իսկ firewall-ի կանոններն ինքնաբերաբար մաքրվում են վերագործարկման ժամանակ։

Ի տարբերություն որսման մյուս ռեժիմների՝ TPROXY-ը չի պահանջում առանձին կարգավորում յուրաքանչյուր հոսթի համար․ այն թափանցիկ կերպով
որսում է նպատակային պորտին ուղղված **կամայական** նպատակակետային հոսթերի տրաֆիկը, դադարեցնում է TLS կապը՝
օգտագործելով յուրաքանչյուր SNI հոսթի անվան համար անմիջապես իր թողարկած վերջնական սերտիֆիկատը, որսում է վերծանված
փոխանակումը և կրկին գաղտնագրում հարցումը՝ այն սկզբնական նպատակակետին ուղարկելու համար։

> **Միայն Linux-ի համար, միայն root-ի իրավունքներով, ըստ ցանկության ակտիվացվող։** Այս ռեժիմի համար պահանջվում է Linux, C գործիքաշարով
> կառուցված բնիկ հավելում և **CAP_NET_ADMIN** հնարավորությունը (սովորաբար՝ root)։ Դրա հասանելիությունը սահմանափակված է
> միայն loopback-ի միջոցով հասանելի AgentBridge API-ով, և այն լռելյայն անջատված է։ Վստահելի
> MITM CA-ն, որը կարող է ստորագրել ցանկացած հոսթի համար, հզոր հնարավորություն է․ տե՛ս [§6 Անվտանգություն](#6-security)։

## §1 Ինչ է այն և երբ օգտագործել

Որսման մյուս չորս ռեժիմներից յուրաքանչյուրն ունի իր սահմանափակումը․

| Ռեժիմ                   | Ինչպես է ուղղորդվում տրաֆիկը                                  | Սահմանափակում                                                         |
| ----------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------- |
| AgentBridge             | Հոսթերի ֆիքսված բազմության DNS կեղծում `/etc/hosts`-ի միջոցով | միայն գրանցված IDE գործակալի հոսթերը                                  |
| Հատուկ հոսթեր           | Յուրաքանչյուր հոսթի DNS կեղծում `/etc/hosts`-ի միջոցով        | մեկ գրառում յուրաքանչյուր հոսթի համար, հոսթերը խմբագրելու համար՝ sudo |
| HTTP_PROXY              | `HTTP_PROXY`/`HTTPS_PROXY` միջավայրի փոփոխականներ             | միայն միջավայրի փոփոխականը հաշվի առնող հավելվածները                   |
| Համահամակարգային պրոքսի | ՕՀ-ի պրոքսիի կարգավորումներ                                   | փոփոխում է գլոբալ վիճակը, պահանջում է հետարկում                       |

Փոխարենը TPROXY թափանցիկ վերծանումն ուղղորդում է տրաֆիկը **միջուկի** մակարդակում։ Այն
`mangle OUTPUT` շղթայում նշում է նպատակային պորտին (լռելյայն՝ `443`) ուղղված նոր տեղային ելքային TCP կապերը,
`ip rule`-ը նշված փաթեթները վերահասցեավորում է տեղային առաքման,
իսկ կրկին մուտք գործելիս `mangle PREROUTING`-ի `TPROXY` թիրախը դրանք փոխանցում է
**IP_TRANSPARENT** ընդունիչին, որն այնուհետև դադարեցնում է TLS կապը և որսում բաց տեքստը։

Օգտագործեք այն, երբ ցանկանում եք որսալ և վերծանել այնպիսի գործընթացի տրաֆիկը, որը՝

- հաղորդակցվում է AgentBridge-ի կողմից չգրանցված հոսթի հետ, և
- հաշվի չի առնում `HTTP_PROXY`-ը, և
- չեք ցանկանում խանգարել՝ փոխելով համահամակարգային պրոքսին։

Քանի որ որսումը տեղի է ունենում միջուկում, սկզբնավորող գործընթացը **կարգավորման որևէ
փոփոխության** կարիք չունի, սակայն գործընթացը պետք է վստահի OmniRoute-ի տեղադրած դինամիկ CA-ին
(տե՛ս [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer))։

## §2 Պահանջներ

| Պահանջ                | Մանրամասներ                                                                                                                                                             |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ՕՀ**                | Միայն Linux — **IP_TRANSPARENT**-ը միայն Linux-ում հասանելի սոկետի ընտրանք է։ Բեռնիչը բոլոր այլ հարթակներում վերադարձնում է «անհասանելի»։                               |
| **Արտոնություն**      | Թափանցիկ սոկետ ստեղծելու և `iptables`/`ip` կանոններ կիրառելու համար անհրաժեշտ է **CAP_NET_ADMIN** հնարավորությունը․ գործնականում՝ գործարկեք root-ի իրավունքներով։       |
| **Բնիկ հավելում**     | Պետք է հավաքվի կամ նախապես հավաքված տարբերակով մատակարարվի փոքր N-API հավելում (`src/mitm/tproxy/native/transparent.c`)։ Տե՛ս [§3](#3-the-native-ip_transparent-addon)։ |
| **Միջուկի մոդուլներ** | `iptables՝ `TPROXY`, `mangle`և`mark` համընկնումների աջակցությամբ (ստուգված է 6.8.0 միջուկի հետ)։                                                                        |

**Սահուն դեգրադացիա․** եթե պահանջներից որևէ մեկը բացակայում է (ոչ Linux,
գործիքաշարի բացակայություն, չհավաքված հավելում), հավելման բեռնիչը
(`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`) բացառություն
առաջացնելու փոխարեն վերադարձնում է `null`։ Այնուհետև զավթման ռեժիմի կարգավիճակը
հաղորդում է `available: false`, կառավարման վահանակի փոխարկիչը **անջատված է**՝
«TPROXY ապակոդավորման համար անհրաժեշտ են Linux + root + բնիկ հավելումը»
հուշումով, իսկ OmniRoute-ի մնացած մասը շարունակում է աշխատել։

## §3 Բնիկ IP_TRANSPARENT հավելումը

Node-ի `net` մոդուլը չի կարող `setsockopt(IP_TRANSPARENT)` կանչել _նախքան_
`bind()`-ը, ինչը պահանջվում է TPROXY-ի համար (հակառակ դեպքում միջուկը մերժում է
վերաուղղորդված փաթեթները)։ Հավելումը
(`src/mitm/tproxy/native/transparent.c`, հավաքվում է `binding.gyp`-ի միջոցով)
փոքր N-API մոդուլ է, որը տրամադրում է երեք ֆունկցիա՝ օգտագործվող
`transparentSocket.ts`-ի միջոցով.

| Հավելման ֆունկցիա                     | Աշխատանք սոկետի հետ                                                                                  | Օգտագործման նպատակը                                                                   |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, վերադարձնում է անմշակ fd | թափանցիկ զավթման ունկնդիր (Node-ը ընդունում է fd-ն `server.listen({ fd })`-ի միջոցով) |
| `setSocketMark(fd, mark)`             | Կիրառում է `setsockopt` **SO_MARK** գոյություն ունեցող fd-ի վրա                                      | հանգույցի կանխարգելում (պրոքսիի սեփական սոկետների նշագրում)                           |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK**՝ չարգելափակող `connect()`-ից **առաջ**, վերադարձնում է fd                    | վերագաղտնագրված վերահաղորդում դեպի վերին հանգույց (SYN-ը կրում է նշումը)              |

Սկզբնական նպատակակետը կարդացվում է `socket.localAddress`/`localPort`-ից․ TPROXY-ն
պահպանում է այն, ուստի **SO_ORIGINAL_DST**/NAT որոնման անհրաժեշտություն չկա։

## §4 Յուրաքանչյուր SNI-ի համար դինամիկ CA-ն և վստահության պահոցի տեղադրիչը

> **#6684 թարմացում․** AgentBridge-ի ստատիկ սերվերը (`src/mitm/server.cjs`) այժմ
> մեկ ստատիկ ինքնաստորագրված leaf վկայագրի փոխարեն նույնպես օգտագործում է
> CA/leaf ճարտարապետության այս նույն ձևանմուշը։ Այն օգտագործում է **առանձին** CA օրինակ
> (`src/mitm/cert/rootCa.ts`, պահպանվում է `<DATA_DIR>/mitm/ca.key`/`ca.crt`-ում)
> և տեղադրվում է վստահության պահոցի՝ արդեն գոյություն ունեցող
> `omniroute-mitm.crt` դիրքում (այնտեղ փոխարինելով հին մեկ leaf վկայագրին․
> կրկնակի վստահության մաքրում անհրաժեշտ չէ), ամբողջությամբ առանձին մնալով
> ստորև նշված TPROXY-ի սեփական `omniroute-tproxy-ca.crt` դիրքից։
> AgentBridge-ի նոր տեղադրումներն ավտոմատ կերպով ստանում են CA մոդելը, իսկ այն
> տեղադրումը, որն արդեն վստահում էր հին ստատիկ leaf վկայագրին, շարունակում է
> օգտագործել այն, մինչև օպերատորը միացնի `MITM_ROOT_CA_ENABLED=true`
> (`src/mitm/cert/migration.ts`)․ վստահելի MITM CA-ն, որը կարող է leaf վկայագիր
> ստորագրել **ցանկացած** հոսթի համար, էապես ավելի հզոր է, քան հին՝ ֆիքսված SAN-երով
> leaf վկայագիրը, ուստի արդեն վստահելի տեղադրման դեպքում անցումը երբեք
> աննկատ չի կատարվում։

Պատմականորեն AgentBridge-ի ստատիկ MITM վկայագիրն աշխատում էր միայն այն պատճառով,
որ AgentBridge-ը DNS կեղծում է հոսթերի **ֆիքսված** բազմության համար (որն այժմ
միավորված է ստորև ներկայացված մոդելի հետ)։ TPROXY-ը միջնորդում է **կամայական**
հոսթեր, ուստի դրա listener-ը պետք է ներկայացնի վավեր leaf վկայագիր՝ հաճախորդի
հարցրած ցանկացած SNI-ի համար․ նույն պահանջն այժմ AgentBridge-ն ունի
`MITM_TOOL_HOSTS`-ի ամբողջ բազմության համար (գործիքների 9 գրառում), այլ ոչ թե
միայն 4 antigravity հոսթերի։

### Դինամիկ CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore`-ը գործարկում է տեղային CA (կառուցված `selfsigned` կախվածության
հիման վրա), որը՝

- Ստեղծում է երկարաժամկետ CA՝ `generateMitmCa()`-ի միջոցով (CN՝
  `"OmniRoute MITM CA"`, վավերականությունը՝ 10 տարի,
  `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-բիթանոց RSA / SHA-256)։
- Ըստ պահանջի տրամադրում է **մեկ leaf վկայագիր յուրաքանչյուր SNI հոսթանվան համար**՝
  `issueLeafCert()`-ի միջոցով (վավերականությունը՝ 1 տարի,
  `subjectAltName` = SNI հոսթ) և յուրաքանչյուր հոսթանվան համար քեշավորում է մեկ
  `tls.SecureContext`։
- TLS-ը տերմինացնող սերվերի համար տրամադրում է `createSNICallback()` (տե՛ս
  [§5](#5-how-decrypt-and-capture-work))։
- Կարող է ստեղծվել `existingCa`-ով՝ վերագործարկումների միջև CA-ն կայուն պահելու
  համար (որպեսզի վստահության պահոցը կրկին տեղադրելու կարիք չլինի)։

CA-ի մասնավոր բանալին **երբեք չի լքում մեքենան**։

### Վստահության պահոցի տեղադրիչ (`src/mitm/tproxy/caTrust.ts`)

Միջնորդված հաճախորդը պետք է վստահի դինամիկ CA-ին, ուստի գրանցման ռեժիմը
գործարկելիս CA վկայագիրը տեղադրվում է ՕՀ-ի վստահության պահոցում՝ **հատուկ
դիրքում**՝ `omniroute-tproxy-ca.crt` (`TPROXY_CA_CERT_NAME` հաստատունը), որը
պահվում է ստատիկ MITM վկայագրի դիրքից (`omniroute-mitm.crt`) առանձին, որպեսզի
դրանք երբեք չվերագրեն միմյանց։

`installTproxyCa(caPem, sudoPassword?)`-ը հայտնաբերում է դիստրիբուտիվի anchor
գրացուցակը (ըստ հերթականության՝ նախ Debian ոճը) և գործարկում համապատասխան
թարմացման հրամանը․

| Anchor գրացուցակ                            | Թարմացման հրաման         |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Տեղադրման ընթացքում PEM-ը նախ տեղադրվում է ժամանակավոր ֆայլում, այնուհետև
(արտոնյալ իրավունքներով) `mkdir -p`-ով ստեղծվում է anchor գրացուցակը,
`cp`-ով նախապատրաստված ֆայլը պատճենվում է այնտեղ, և գործարկվում է թարմացման
հրամանը։ `uninstallTproxyCa()`-ը հեռացնում է միայն հատուկ դիրքը (անփոփոխ
թողնելով ստատիկ MITM վկայագիրը) և թարմացնում է պահոցը․ ոչ Linux համակարգերում
այն ոչինչ չի անում։

Բոլոր արտոնյալ հրամանները գործարկվում են `execFileWithPassword`-ի
(`src/mitm/systemCommands.ts`) միջոցով՝ `spawn`՝ **արգումենտների զանգվածներով,
առանց shell-ի և առանց տողային ինտերպոլյացիայի** (Խիստ կանոն #13)։
Երբ պրոցեսն աշխատում է root-ի իրավունքներով (օրինակ՝ VPS-ում), թիրախային
հրամանը գործարկվում է անմիջապես, և գաղտնաբառ անհրաժեշտ չէ։ Ոչ root
իրավունքներով աշխատող աշխատասեղանային համակարգում `sudoPassword`-ը փոխանցվում
է stdin-ի միջոցով՝ `sudo -S` հրամանով։

> Աշխատասեղանային համակարգի `sudoPassword`-ը փոխանցվում է POST հարցման մարմնում՝
> վստահության պահոցի տեղադրումը լիազորելու համար։ Այն ամբողջությամբ անտեսվում է,
> երբ պրոցեսն աշխատում է root-ի իրավունքներով։

## §5 Ինչպես են աշխատում վերծանումն ու գրանցումը

Գործընթացաշարը (ամբողջությամբ՝ `src/mitm/tproxy/`-ում).

```
տեղային հավելված  ──TCP/443──▶  mangle OUTPUT-ը նշում է կապը (fwmark)
                                ip rule → տեղային երթուղավորման աղյուսակ → lo
                                mangle PREROUTING TPROXY → IP_TRANSPARENT սպասարկիչ (պորտ 8443)
                                    │  captureMode.ts. սկզբնական նպատակակետը կարդում է socket.localAddress-ից
                                    ▼
                                tlsCapture.ts.
                                  1. TLS-ով ավարտում է ՀԱՃԱԽՈՐԴԻ կապը՝ յուրաքանչյուր SNI-ի համար առանձին leaf վկայագրով (dynamicCert)
                                  2. ներքին http.Server-ը վերլուծում է վերծանված բաց տեքստը
                                  3. գրանցում → globalTrafficBuffer.push()՝ source: "tproxy"-ով
                                     (կիրառվում են sanitizeHeaders + maskSecret)
                                  4. վերակոդավորում և փոխանցում սկզբնական նպատակակետին
                                     շրջանցման նշումով socket-ի միջոցով (connectMarked, anti-loop)
                                    │
                                    ▼
                                սկզբնական վերին հանգույց (api.example.com)
```

- **TLS-ի ավարտ** (`createTlsCaptureServer`). սկզբնական CA-ի SNI callback-ն օգտագործելով՝ չմշակված կալանված
  socket-ը փաթաթում է սերվերային `tls.TLSSocket`-ի մեջ,
  ապա վերծանված հոսքը փոխանցում է ներքին `http.Server`-ին (MITM-ի
  ավարտման ստանդարտ հնարքը)։ Socket-ների կյանքի տևողությունը սահմանափակվում է `MITM_IDLE_TIMEOUT_MS`-ով, որպեսզի
  կախված թունելը չկարողանա սպառել ֆայլային դեսկրիպտորները։
- **Գրանցում** (`handleDecryptedRequest`). ավելացնում է `InterceptedRequest`՝
  `source: "tproxy"`-ով և սկզբնական `"in-flight"` կարգավիճակով, ընդ որում՝ վերնագրերը
  բուֆեր մուտք գործելուց առաջ մշակվում են `sanitizeHeaders()`-ով, իսկ մարմինները՝
  `maskSecret()`-ով։ Այնուհետև գրառումը թարմացվում է պատասխանով, չափերով և հապաղմամբ։
- **Վերակոդավորված փոխանցում** (`createForward` / `realForward`). վերակոդավորում և փոխանցում է
  սկզբնական նպատակակետին։ `rejectUnauthorized`-ի լռելյայն արժեքը **`true`** է (լռելյայն
  անվտանգ)․ վերին հանգույցի վկայագիրը ստուգվում է հաճախորդի պահանջած SNI/Host-ի
  նկատմամբ, ուստի պրոքսին մերժում է հենց այն, ինչը կմերժեր սկզբնական հաճախորդը։

### Օղակից պաշտպանություն (SO_MARK)

Քանի որ կանոնները նշում են տեղային նոր ելքային կապերը, պրոքսիի **սեփական**
վերակոդավորված փոխանցումը սովորաբար կրկին կկալանվեր՝ ստեղծելով անվերջ օղակ։ Փոխանցման
ուղին դրանից պաշտպանվում է շրջանցման socket-ի նշումով (**SO_MARK**).

- `realForward`-ն իր վերին հանգույցի socket-ը բացում է `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`-ի միջոցով
  — `DEFAULT_BYPASS_MARK = 0x539` — որը **SO_MARK**-ը սահմանում է **նախքան** `connect()`-ը,
  այնպես որ փոխանցման SYN-ը կրում է շրջանցման նշումը։
- `mangle OUTPUT` կանոնը բացառում է այն կապերը, որոնք արդեն կրում են շրջանցման նշումը
  (`-m mark ! --mark <bypassMark>`), ուստի պրոքսիի փոխանցումը **կրկին չի նշվում**
  և նորից չի մտնում TPROXY։

> Իրականացման նշում․ շրջանցման նշումով socket-ը պետք է տեղադրվի agent-ի
> `createConnection`-ում (`https.request({ createConnection })`-ն աննկատ անտեսվում է,
> երբ առկա է agent), այլապես փոխանցումը կբացի չնշված socket, և
> օղակը կվերադառնա։ Սա e2e-ով վավերացված՝ օղակից պաշտպանության ուղղումն էր։

հստակորեն միացված, միայն տեղային TPROXY որսման ռեժիմում, լռելյայն անջատված է, իսկ վստահության պահոցի
գրառումը հեռացվում է ռեժիմը դադարեցնելիս։

## §7 Firewall-ի տրանզակցիոն կիրառում / հետարկում

Խափանումը երբեք չպետք է թողնի `mangle` կանոն կամ հնացած երթուղի։ Հրամանների կառուցիչը
(`src/mitm/tproxy/commands.ts`) և գործարկիչը (`src/mitm/tproxy/setup.ts`) երաշխավորում են, որ
**հետարկումը կիրառման ճշգրիտ հակադարձ գործողությունն է՝ հակառակ հերթականությամբ**։

`applyTproxy(cfg)`-ը կիրառման հրամանները գործարկում է հերթականությամբ․ **ցանկացած** ձախողման դեպքում այն հնարավորինս կատարում է ամբողջական `revertTproxy(cfg)` և կրկին նետում է սխալը, այնպես որ firewall-ը կա՛մ ամբողջությամբ կիրառված է, կա՛մ ամբողջությամբ հետարկված՝ երբեք մասնակի կիրառված չէ։ `revertTproxy(cfg)`-ը հակադարձ հրամանները գործարկում է հակառակ հերթականությամբ և անտեսում է ձախողումները (իդեմպոտենտ է՝ անվտանգ է կանչել առանց նախապայմանի, օրինակ՝ AgentBridge-ի `repairMitm()` մաքրման գործողությունից)։

`validateTproxyConfig(cfg)`-ը գործարկվում է ցանկացած հրամանից առաջ․ պորտերը պետք է լինեն `1–65535` միջակայքում, `mark`/`routeTable`/`bypassMark` արժեքները պետք է լինեն դրական ամբողջ թվեր, իսկ `bypassMark`-ը պետք է տարբերվի `mark`-ից (օղակավորման կանխարգելում)։

### Կիրառման հրամանները (հերթականությամբ)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Հետարկումը ջնջում է դրանք հակառակ հերթականությամբ՝ `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`։

> Ընթացակարգը հիմնված է **OUTPUT**-ի վրա, քանի որ MITM-ի կիրառման դեպքը _տեղային_ ելքային
> թրաֆիկն է (նույն հոսթի հավելվածներից), որը միայն `PREROUTING`-ում գործող TPROXY-ն չի
> տեսնում․ `PREROUTING`-ը տեսնում է միայն վերահասցեավորվող թրաֆիկը։ `OUTPUT` շղթան նշագրում է նոր
> տեղային միացումները, `ip rule`-ը դրանք վերաերթուղավորում է դեպի տեղային առաքում (`lo`), իսկ
> `PREROUTING`-ն այնուհետև դրանք հատկացնում է թափանցիկ ունկնդրին։

## §8 Կազմաձևում

Մեկնարկի հարցումը (`POST /api/tools/agent-bridge/tproxy`) ընդունում է հետևյալ
դաշտերը, որոնք վավերացվում են `StartTproxyBodySchema`-ով (`tproxy/route.ts`)։ Բոլորն ընտրովի են
և չտրամադրվելու դեպքում օգտագործում են իրենց լռելյայն արժեքները․

| Դաշտ             | Տիպ                | Լռելյայն | Նշումներ                                                                                                                                            |
| ---------------- | ------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`    | Նպատակակետային TCP պորտը, որը պետք է թափանցիկորեն ընդհատել                                                                                          |
| **mark**         | int (≥1)           | `0x2333` | Firewall-ի նշիչը, որը սահմանվում է `OUTPUT`-ում և համընկեցվում `ip rule` + `PREROUTING` կանոններով                                                  |
| **onPort**       | int (1–65535)      | `8443`   | Պորտը, որին կապվում է թափանցիկ (**IP_TRANSPARENT**) ունկնդիրը                                                                                       |
| **routeTable**   | int (≥1)           | `233`    | Քաղաքականության վրա հիմնված երթուղավորման աղյուսակի id-ն, որը պարունակում է `local 0.0.0.0/0` երթուղին                                              |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | Շրջանցման socket-ի նշիչը (**SO_MARK**), որը proxy-ն սահմանում է իր վերին հոսքի միացումների վրա․ բացառվում է `OUTPUT`-ում (օղակավորման կանխարգելում) |
| **sudoPassword** | string             | —        | Միայն ոչ root աշխատասեղանների համար․ թույլատրում է վստահության պահոցի տեղադրումը, իսկ root-ի դեպքում անտեսվում է                                    |

TPROXY-ի համար **միջավայրի փոփոխականներ չկան**․ ամբողջ կազմաձևումը կատարվում է
POST մարմնի կամ վերը նշված լռելյայն արժեքների միջոցով։

## §9 Միացում Traffic Inspector-ից

1. Բացեք **Traffic Inspector**-ը (`/dashboard/tools/traffic-inspector`)։
2. Գրանցման ռեժիմների գործիքագոտում գտեք **"TPROXY Decrypt"** ⚠ կոճակը
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`)։
   - Եթե այն **անջատված է**՝ "TPROXY decrypt requires Linux + root +
     the native addon" հուշումով, ապա բնիկ հավելումը հասանելի չէ այս հոսթում (ոչ Linux,
     գործիքաշղթան բացակայում է կամ հավելումը չի կառուցվել)։ Տե՛ս [§2](#2-requirements) և [§3](#3-the-native-ip_transparent-addon)։
3. Սեղմեք կոճակը։ Այն կանչում է `POST /api/tools/agent-bridge/tproxy`՝
   `startTproxyCaptureMode()`-ի միջոցով (`src/lib/inspector/tproxyCaptureApi.ts`), որը՝
   կառուցում է դինամիկ CA-ն, բացում թափանցիկ ունկնդիրը, կիրառում firewall-ի
   կանոնները և տեղադրում CA-ն ՕՀ-ի վստահության պահոցում։
4. Աշխատելու ընթացքում փոխարկիչը դառնում է սաթագույն և ցուցադրում է ընթացիկ որսումների քանակը
   (`· <interceptCount>`)։ Որսված հարցումները հայտնվում են հարցումների ցանկում՝
   `source: "tproxy"` արժեքով։
5. Դադարեցնելու համար կրկին սեղմեք՝ `DELETE /api/tools/agent-bridge/tproxy`-ը
   `stopTproxyCaptureMode()`-ի միջոցով փակում է ունկնդիրը, ապատեղադրում CA-ն և հետ է շրջում
   firewall-ի կանոնները։

Գրանցման ռեժիմի կարգավիճակը (աշխատում է / հասանելի է / որսումների քանակ / ունկնդրի պորտ) ստացվում է
`GET /api/tools/agent-bridge/tproxy`-ից (`getCaptureStatus()`՝
`src/mitm/tproxy/captureManager.ts`-ում)։ Միաժամանակ աշխատում է միայն **մեկ** TPROXY աշխատաշրջան․
երկրորդը գործարկելու փորձը մերժվում է "TPROXY capture mode is already running" հաղորդագրությամբ։

## §10 Խնդիրների վերացում

### Փոխարկիչն անջատված է

Բնիկ հավելումը հնարավոր չէ բեռնել։ Համոզվեք, որ օգտագործում եք Linux, կառուցել եք հավելումը
(`npm run build:native:tproxy`), և պրոցեսը կարող է բեռնել `transparent.node`-ը։
`isTransparentSocketAvailable()`-ը վերահսկում է փոխարկիչի հասանելիությունը, իսկ `GET /api/tools/agent-bridge/tproxy`-ը
վերադարձնում է `available: false`, երբ հավելումը բացակայում է։

### Ոչինչ չի գրանցվում

- Համոզվեք, որ որսվող պրոցեսն իրականում միանում է կազմաձևված `dport`-ին
  (լռելյայն՝ `443`)։
- Համոզվեք, որ պրոցեսը վստահում է դինամիկ CA-ին։ CA-ն տեղադրվում է
  `omniroute-tproxy-ca.crt` անվամբ․ սեփական վստահության պահոց ունեցող հավելվածներում (Firefox/Chrome NSS)
  հնարավոր է՝ հավաստագիրը նույնպես անհրաժեշտ լինի ավելացնել այդ պահոցում։
- Գործարկեք AgentBridge-ի **Diagnose** ինքնաստուգումը (տե՛ս
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md))՝ հավաստագրի վստահելիությունը / սերվերի
  առողջական վիճակը ստուգելու համար։

### Խափանումից հետո մնացած firewall-ի կանոններ

`revertTproxy()`-ն կիրառման ճշգրիտ հակադարձ գործողությունն է և իդեմպոտենտ է։ Ռեժիմը
դադարեցնելը հետ է շրջում կանոնները։ Եթե OmniRoute-ը հարկադրաբար դադարեցվել է աշխատաշրջանի ընթացքում, օգտագործեք AgentBridge-ի
**Repair** գործողությունը (`POST /api/tools/agent-bridge/repair`)՝ համակարգում մնացած
վիճակը (DNS-ի կեղծում, արմատային CA, համակարգային պրոքսի) չեղարկելու համար։ TPROXY-ի `mangle`
կանոնները և երթուղին նույնպես ինքնաբերաբար մաքրվում են վերագործարկման ժամանակ։

### Անվերջ ցիկլ / պրոքսին որսում է իր իսկ վերահասցեավորումը

Սա ցիկլի կանխարգելման դեպքն է։ Համոզվեք, որ `bypassMark`-ը տարբերվում է `mark`-ից (վավերացումը
պարտադրում է դա), և որ վերահասցեավորումն օգտագործում է `connectMarked` (այն օգտագործվում է `realForward`-ում)։
Տե՛ս [§5 Ցիկլի կանխարգելում](#anti-loop-so_mark)։
