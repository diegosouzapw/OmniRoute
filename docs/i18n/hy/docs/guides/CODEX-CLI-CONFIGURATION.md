OmniRoute-ը որպես OpenAI-ի հետ համատեղելի հետնամաս օգտագործելու համար Codex CLI-ի ամբողջական ուղեցույց։

---

> **TOML-ը միակ արդյունավետ ձևաչափն է։** Ժամանակակից Codex-ը կարդում է բացառապես
> `~/.codex/config.toml`-ը (ստուգված է codex-cli 0.147.0-ի համար․ `codex --help`-ում
> նշվում է, որ `-c/--config` վերագրումները «բեռնվում են `~/.codex/config.toml`-ից»)։
> Հին `~/.codex/config.yaml`-ը պատկանում էր նախկին npm CLI-ին և աննկատ
> անտեսվում է։ Կառավարման վահանակի գեներատորը (`/api/cli-tools/apply`, գործիք՝
> `codex`) TOML-ը գրանցում է պահպանողական միավորմամբ՝ առկա բանալիները և այլ
> մատակարարների բլոկները պահպանվում են, API բանալին մնում է `OMNIROUTE_API_KEY`-ում
> (երբեք՝ ֆայլում), իսկ մնացած հին `config.yaml`-ը ներկայացվում է որպես
> տեղափոխման նշում՝ առանց փոփոխվելու։

## Տեղադրման համար պատրաստ config.toml

Փոխարինեք `<YOUR_HOST>`-ը և `<YOUR_KEY>`-ը ձեր արժեքներով․

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # յուրաքանչյուր գործիքի կանչի պատմության պահպանման սահմանաչափը

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc կամ ~/.zshrc — բանալու իրական արժեքը, երբեք՝ config.toml-ում
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS․ ChatGPT հավելվածում ներառված Codex-ը

Եթե Codex-ը տեղադրել եք ChatGPT աշխատասեղանի հավելվածի միջոցով, `codex` երկուական
ֆայլը կարող է գտնվել միայն հավելվածի փաթեթի ներսում և դեռ հասանելի չլինել ձեր
shell-ի `PATH`-ում։ Ռեսուրսների պանակն ավելացրեք ձեր shell-ի մեկնարկային ֆայլին․

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Բացեք նոր shell, ապա ստուգեք․

```bash
command -v codex
codex --version
```

### Տեղային՝ նույնականացում չպահանջող OmniRoute․ փոխարինող բանալին բավարար է

Codex-ը ստուգում է, որ `env_key`-ով նշված միջավայրի փոփոխականը գոյություն ունի
**նախքան** առաջին հարցումը CLI-ից դուրս կուղարկվի։ Եթե ձեր **տեղային** OmniRoute
օրինակը նույնականացում չի պահանջում, ցանկացած ոչ դատարկ փոխարինող արժեք բավարար է․

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Եթե ձեր OmniRoute սերվերը պաշտպանված է կամ հեռադիր, փոխարենն օգտագործեք իրական բանալի։

> **Հանգույցի տարածված տարբերակներ**
>
> | Հասանելիություն | URL                           |
> | --------------- | ----------------------------- |
> | Տեղային ցանց    | `http://192.168.0.1:20128/v1` |
> | Tailscale       | `http://100.x.x.x:20128/v1`   |
> | Հետադարձ կապ    | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — ինչու է այն աշխատում բոլոր մոդելների համար

Codex CLI-ն 2026 թվականի փետրվարին հնացած հայտարարեց `wire_api = "chat"`-ը (Chat Completions) և այժմ **պահանջում է** `wire_api = "responses"` (OpenAI Responses API)։ `wire_api = "chat"` սահմանելը v0.138-ից սկսած գործարկման պահին անմիջապես հանգեցնում է խափանման։

Շատ մատակարարներ, ներառյալ GLM-ը և Kimi-ն, դեռ տրամադրում են միայն Chat Completions վերջնակետ։ DeepSeek V4-ն այժմ տրամադրում է ինչպես բնիկ Responses API, այնպես էլ Anthropic-ի հետ համատեղելի վերջնակետ․ OmniRoute-ը լռելյայն օգտագործում է Responses-ը և թույլ է տալիս DeepSeek-ի յուրաքանչյուր կապի համար ընտրել Anthropic-ի հետ համատեղելիությունը։

**OmniRoute-ը սա լուծում է թափանցիկ կերպով․**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute-ն ընտրում է մատակարարի բնիկ արձանագրությունը և անհրաժեշտության դեպքում փոխակերպում է
    → POST /responses (DeepSeek V4) կամ /chat/completions (Mistral / GLM / Kimi / այլք)
```

OmniRoute-ն օգտագործելիս առանձին փոխակերպման միջնորդ սերվեր երբեք անհրաժեշտ չէ։ **Բոլոր մոդելներն օգտագործում են `wire_api = "responses"`** — մնացածը մշակում է OmniRoute-ը։

> **`wire_api`-ը լռելյայն արժեքն է** — դաշտի լռելյայն արժեքը `"responses"` է, և այն կարելի է ամբողջությամբ բաց թողնել `config.toml`-ից։ Այն բացահայտ սահմանեք միայն այն դեպքում, երբ փաստաթղթավորում եք մտադրությունը։

## Համատեքստի պատուհան և սեղմում

### Թոքենների կազմաձևման դաշտեր

| Դաշտ                             | Նկարագրություն                                                                                                                                                                                                      |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Ակտիվ մոդելի թոքենների ընդհանուր բյուջեն։ Սահմանեք մոդելի հայտարարված սահմանաչափին։                                                                                                                                 |
| `model_auto_compact_token_limit` | Ինքնաշխատ կերպով գործարկվող պատմության սեղմման շեմը։ **Առավելագույնը՝ `model_context_window`-ի 90%-ը** — 90%-ից բարձր արժեքներն աննկատ անտեսվում են։                                                                |
| `tool_output_token_limit`        | Պատմության մեջ յուրաքանչյուր գործիքի կանչի ելքում պահվող թոքենների սահմանաչափը։ Կանխում է պատուհանի լցվելը գործիքի մեկ մեծ պատասխանից։ **Սա ելքի առավելագույն չափը չէ** — սա պատմության մեջ պահպանման սահմանաչափ է։ |
| `compact_prompt`                 | Սեղմման ժամանակ օգտագործվող համակարգային հուշման ներդրված վերասահմանում (v0.138+)։                                                                                                                                  |

> **Նշում `model_max_output_tokens`-ի մասին**․ այս դաշտը **Codex CLI-ի կազմաձևման սխեմայի մաս չէ** (բացակայում է Codex-ի Rust կոդային բազայից)։ Սահմանման դեպքում այն աննկատ անտեսվում է։ Մի՛ հիմնվեք դրա վրա․ օգտագործեք `tool_output_token_limit`՝ վերահսկելու համար, թե գործիքի ելքից որքանն է պահվում պատմության մեջ։

> **Սեղմման բանաձև․** `effective_window = model_context_window - min(tool_output_token_limit, 20000)`։ 20k-ից բարձր արժեքները չեն փոխում սեղմման գործարկման շեմը։

> **Գործնական կանոն․** սահմանեք `model_auto_compact_token_limit`-ը `model_context_window`-ի 85–88%-ին։ Երբեք մի՛ գերազանցեք 90%-ը․ այն աննկատ կանտեսվի։

## Դատողության ինտենսիվություն

Կառավարում է, թե որքան է մոդելը «մտածում» նախքան պատասխանելը։

| Արժեքը   | Օգտագործեք հետևյալի համար                                    |
| -------- | ------------------------------------------------------------ |
| `none`   | Առանց դատողության՝ ուղղակի պատասխան                          |
| `low`    | Պարզագույն առաջադրանքներ (վերանվանում, ձևաչափում)            |
| `medium` | **Սերվերի լռելյայն արժեքը**, երբ նշված չէ                    |
| `high`   | Միջին բարդության առաջադրանքներ (վերակառուցում, վրիպազերծում) |
| `xhigh`  | Ճարտարապետություն, խորքային վերլուծություն, բարդ խնդիրներ    |

```bash
# Վերասահմանում յուրաքանչյուր կանչի համար
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

Սահմանեք նաև դատողության **ամփոփումը**, որպեսզի Desktop-ը կարողանա ցուցադրել մտածողության տեքստը (ոչ միայն գաղտնագրված բլոբները).

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # կամ ultra, երբ այն աջակցվում է
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute-ի մտածողության բյուջեն (սերվերի կարգավորում)

OmniRoute հոսթում **Settings → AI → Thinking Budget** պարամետրը պետք է լինի **`passthrough`**, որպեսզի Codex-ի ինտենսիվությունը/ամփոփումը հասնի վերին հոսքի ծառայությանը։ **`auto` ռեժիմը հեռացնում է** հաճախորդի բոլոր `reasoning` / `reasoning_effort` դաշտերը և դատարկ կթողնի մտածողության վահանակները, նույնիսկ երբ Codex-ը ճիշտ է կազմաձևված։

Ամբողջական ուղեցույց՝ [THINKING_BUDGET.md](./THINKING_BUDGET.md)։

Սեղմումը և հուշումների քեշը միմյանցից անկախ են և շարունակում են աշխատել `passthrough` ռեժիմում։

## Պրոֆիլների ավտոմատ ստեղծում `omniroute setup-codex`-ի միջոցով

Եթե OmniRoute-ն աշխատեցնում եք VPS-ում, կարող եք գործող մոդելների կատալոգից ավտոմատ ստեղծել պրոֆիլների ֆայլեր․

```bash
# VPS-ից (օգտագործում է տեղային OmniRoute-ը՝ 20128 պորտով)
omniroute setup-codex

# Ցանկացած համակարգչից՝ նշեք ձեր VPS-ը
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Նախադիտում՝ առանց ֆայլեր գրելու
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Ստեղծել միայն GLM և Kimi պրոֆիլները
omniroute setup-codex --only glm,kimi

# Գրել հատուկ գրացուցակում
omniroute setup-codex --codex-home /path/to/.codex
```

Հրամանը ստանում է `/v1/models`-ը, հայտնի մոդելների համար օգտագործում է ճշգրտված պրոֆիլներ, մյուս համատեղելի տեքստային մոդելների համար կիրառում է կատալոգի մետատվյալները և յուրաքանչյուրի համար գրում է `~/.codex/<name>.config.toml`։ Գործողությունն իդեմպոտենտ է՝ այն անվտանգ է կրկին գործարկել։

OmniRoute-ը կարող է նաև **ավտոմատ համաժամացնել** այս նույն պրոֆիլային ֆայլերը, երբ մատակարարի մոդելների հաջող հայտնաբերումը/ներմուծումը փոփոխում է գործող կատալոգը։ Սա **միացվում է ըստ ցանկության և լռելյայն անջատված է**․ միացրեք այն **CLI Code կառավարման վահանակից** («CLI պրոֆիլների ավտոմատ համաժամացում» → Codex) կամ սահմանեք `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (այն նաև հաշվի է առնում `CLI_ALLOW_CONFIG_WRITES`-ը, որը լռելյայն միացված է)։ Միացված լինելու դեպքում այն գրում է միայն առանձին `~/.codex/*.config.toml` պրոֆիլային ֆայլեր․ այն երբեք չի փոխում ակտիվ/լռելյայն `~/.codex/config.toml`-ը, Codex-lb-ի կարգավորումները, նույնականացումը կամ մատակարարի ընտրությունը։

## Codex-ի գործարկում `omniroute launch-codex`-ի միջոցով

Նախքան Codex-ը գործարկելը ստուգում է ձեր OmniRoute օրինակի աշխատանքային վիճակը․

```bash
# Գործարկել տեղային OmniRoute-ի հետ (լռելյայն պորտը՝ 20128)
omniroute launch-codex

# Գործարկել որոշակի պրոֆիլով
omniroute launch-codex --profile kimi-k27

# Գործարկել հեռակա VPS-ի հետ
omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# Լրացուցիչ արգումենտներ փոխանցել codex-ին
omniroute launch-codex --profile glm52 -- --yolo "fix this bug"
```

Codex-ը նաև մանիֆեստով կառավարվող երկու ընդհանուր մուտքային կետերի թիրախ է
(`bin/cli/cli-manifest.mjs`)․

```bash
# Մոդելի ինտերակտիվ ընտրիչ → գրում է ~/.codex/<name>.config.toml (TOML, env_key)
omniroute configure codex

# Գործարկել codex-ը՝ -c դրոշների միջոցով ներդնելով omniroute մատակարարին (կարգավորում չի գրվում)
omniroute run codex
```

## Երկարատև առաջադրանքներ

OmniRoute-ի երկու լռելյայն կարգավորումներ կարող են աննկատ խափանել Codex CLI-ի բազմաժամյա աշխատաշրջանները։ Դրանցից ոչ մեկը Codex CLI-ի կարգավորում չէ․ երկուսն էլ գտնվում են OmniRoute-ի կողմում։ Այն օգտատերերը, որոնք կազմաձևումը տեղափոխում են վերին մակարդակի պրոքսիներից, որոնք հաշիվներն ամրակցում են և անջատում անգործության սահմանափակումները, հաճախ բախվում են երկուսին էլ և եզրակացնում, որ OmniRoute-ը «չի կարող պահպանել երկարատև աշխատաշրջանը»։

| Ախտանիշ                                                                                                 | Հավանական պատճառ                                                                       | Կարգավորիչ               |
| ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------ |
| Աշխատաշրջանը շարունակ փոխում է հաշիվները / հարցումների քեշի շարունակականությունը կորչում է քայլերի միջև | Աշխատաշրջանի կապակցվածության TTL-ը `0` է (անջատված)                                    | `sessionAffinityTtlMs`   |
| Կապն ընդհատվում է դատողության ընթացքում՝ առանց հաճախորդին ցուցադրվող հուշման                            | Հոսքի անգործության հսկիչը գործարկվել է վերին մակարդակից 10 րոպե հատված չստանալուց հետո | `STREAM_IDLE_TIMEOUT_MS` |

Առնչվող քննարկումներ՝ [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (երկարատև առաջադրանքների ընդհատումներ), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (ինչու է կապակցվածությունը լռելյայն անջատված)։ Հետագծում՝ [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287)։

### 1. Աշխատաշրջանի կապակցվածություն — մեկ խոսակցությունն ամրակցեք մեկ հաշվին

**Լռելյայն՝** `sessionAffinityTtlMs = 0` (անջատված)։

**Որտեղ սահմանել այն**

- Կառավարման վահանակ → **Կարգավորումներ → Երթուղավորում** → **Աշխատաշրջանի կապակցվածություն** → **Կապակցվածության TTL (վայրկյաններ)** (`ComboDefaultsTab`)
- Կամ PATCH հարցմամբ կարգավորեք `sessionAffinityTtlMs`-ը **միլիվայրկյաններով** (Zod-ի միջակայքը՝ `0`–`86_400_000`, այսինքն՝ մինչև 24 ժամ)

> #7274-ում վերանվանվել է միայն Codex-ի համար նախատեսված `codexSessionAffinityTtlMs`-ից։ Հնացած բանալին դեռ ընդունվում է որպես միայն կարդալու կեղծանուն․ նոր կազմաձևերը պետք է օգտագործեն `sessionAffinityTtlMs`։ Այժմ կապակցվածությունը կիրառվում է **ցանկացած** մատակարարի նկատմամբ, երբ TTL-ը `0`-ից մեծ է, ոչ միայն Codex-ի․ տե՛ս [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Աշխատաշրջանի կապակցվածություն։

**Ինչ է խափանվում, երբ այն մնում է 0**

Codex-ի բազմաքայլ խոսակցության յուրաքանչյուր քայլ անկախորեն երթուղավորվում է ակտիվ համակցված ռազմավարությամբ և յուրաքանչյուր քայլում կարող է հասնել **այլ հաշվի**։ Դա խախտում է վերին մակարդակի աշխատաշրջանի / հարցումների քեշի շարունակականությունը։ OmniRoute-ը Codex-ի աշխատաշրջանի վերնագրերը (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) և մարմնի այնպիսի դաշտերը, ինչպիսիք են `prompt_cache_key` / `session_id`, հաշվի է առնում միայն այն դեպքում, երբ TTL-ը `0`-ից մեծ է (`extractSessionAffinityKey`՝ `src/sse/services/auth.ts`-ում)։

**Խորհուրդ է տրվում բազմաժամյա մեկ առաջադրանքի համար**

Սահմանեք TTL-ը **առաջադրանքի՝ ըստ ժամացույցի ակնկալվող տևողությունից մեծ** (UI-ի առավելագույնը **86400 վայրկյան** է = 24 ժամ)։

| Առաջադրանքի ակնկալվող տևողություն | Կապակցվածության TTL (UI, վայրկյաններ) | `sessionAffinityTtlMs` |
| --------------------------------- | ------------------------------------- | ---------------------- |
| Մի քանի ժամ                       | `14400` (4 ժ)                         | `14400000`             |
| Ամբողջ գիշեր / ~12 ժ              | `43200` (12 ժ)                        | `43200000`             |
| Ամբողջ օր                         | `86400` (24 ժ, առավելագույնը)         | `86400000`             |

Կամավոր միացումը կանխամտածված է․ կապակցվածության անջատումը նպաստում է հաշիվների միջև բեռնվածության հավասարակշռմանը, իսկ միացումը՝ մեկ երկարատև գործակալի աշխատաշրջանի շարունակականությանը։ Այս ուղեցույցը **չի** փոխում լռելյայն արժեքը․ Codex-ի երկարատև առաջադրանքներ իրականացնող օպերատորները պետք է այն կամավոր միացնեն։

### 2. Հոսքի անգործության ժամանակի սպառում — մի ընդհատեք դատողության լուռ քայլերը

**Լռելյայն՝** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 րոպե)։ Երբ այն սահմանված չէ, ժառանգվում է `REQUEST_TIMEOUT_MS`-ից․ ընդհանուր ելակետային արժեքը նույնպես 600000 է։ Տե՛ս [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Ժամանակի սպառումներ։

**Ինչ է խափանվում լռելյայն արժեքի դեպքում**

Codex-ի reasoning / գործիքային քայլը, որն ավելի քան 10 րոպե լուռ է մնում՝ առանց **իրական upstream chunk-ի**, հարկադրաբար փակվում է SSE-ի անգործության watchdog-ի կողմից (`open-sse/utils/stream.ts`)։ Հաճախ հաճախորդը տեսնում է պարզապես կապի խզում, ինչը համապատասխանում է «ավտոմատ դադարեցվել է՝ առանց որևէ ծանուցման» նկարագրությանը։

Կարևոր մանրամասն․ OmniRoute-ի սինթետիկ SSE **heartbeat-ը չի զրոյացնում** անգործության ժամանակաչափը։ Միայն իրական upstream body chunk-ն է թարմացնում `lastChunkTime`-ը։ Լուռ մոդելը, որը դեռ «մտածում» է, watchdog-ի տեսանկյունից չի տարբերվում կանգ առած upstream-ից։

Undici-ի body-ի անգործության հետ կապված կարգավորում՝ `FETCH_BODY_TIMEOUT_MS` (այն նույնպես լռելյայն օգտագործում է նույն 10 րոպեանոց բազային արժեքը, իսկ `0`-ն անջատում է այն)։ Streaming-ի դեպքում `FETCH_TIMEOUT_MS`-ը վերաբերում է միայն կապի հաստատմանը / առաջին headers-ի ստացմանը․ stream-ի ակտիվացումից հետո կանգերը կառավարվում են `STREAM_IDLE_TIMEOUT_MS`-ով և `FETCH_BODY_TIMEOUT_MS`-ով։

**Խորհուրդ է տրվում մի քանի ժամ տևող մեկ առաջադրանքի համար**

OmniRoute գործընթացի միջավայրում (`.env` / compose / systemd)․

```bash
# Անջատել stream-ի անգործության և body-ի անգործության սահմանափակումները երկար reasoning քայլերի համար
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Կամ ավելացրեք դրանք՝ ձեր ակնկալած ամենաերկար լուռ ընդմիջումից ավելի բարձր արժեք սահմանելով (արժեքները միլիվայրկյաններով են)․

```bash
# Օրինակ՝ թույլատրել մինչև 2 ժամ լռություն upstream chunk-երի միջև
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Այս environment variable-ները փոխելուց հետո վերագործարկեք OmniRoute-ը։

### Կոնկրետ քայլեր՝ մի քանի ժամ տևող Codex առաջադրանքի համար

1. **Ամրագրեք հաշիվը․** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12 ժամ) կամ `86400` (առավելագույնը՝ 24 ժամ)։
2. **Բարձրացրեք / անջատեք անգործության սահմանափակումները** OmniRoute-ի միջավայրում․

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Պահպանեք սովորական Codex `config.toml`-ը (`wire_api = "responses"`, ճիշտ `base_url`, `OMNIROUTE_API_KEY`)․ այս երկու վարքագծերի համար Codex-ի կողմում affinity/idle կարգավորումներ չկան։
4. Վերագործարկեք OmniRoute-ը, այնուհետև մեկնարկեք երկարատև Codex առաջադրանքը։

### Լռելյայն արժեքների վերաբերյալ որոշում (#7287)

| Կարգավորում              | Թողարկվող լռելյայն արժեք | Փոփոխե՞լ այս ուղեցույցում                                                                                       |
| ------------------------ | ------------------------ | --------------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (անջատված)           | **Ոչ** — մնում է ըստ ցանկության միացվող (բեռի հավասարակշռում ընդդեմ շարունակականության․ տե՛ս Discussion #5718)  |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 րոպե)       | **Ոչ** — ընդհանուր տրաֆիկի համար մնում է 10 րոպե․ երկարատև Codex-ի օպերատորները բարձրացնում կամ անջատում են այն |

Այս լռելյայն արժեքներից որևէ մեկի գլոբալ փոփոխությունը կփոխի instance-ի յուրաքանչյուր հաճախորդի վարքագիծը, ոչ միայն Codex-ի։ Փաստաթղթավորեք կարգավորումները, սակայն լռելյայն արժեքները թողեք անփոփոխ, մինչև օպերատորի հստակ որոշմամբ այլ բան սահմանվի։

### Անգործության պատճառով ընդհատումների ախտորոշում

Երբ անգործության watchdog-ը գործարկվում է, OmniRoute-ը գրանցում է մոտավորապես այսպիսի տող․

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Փնտրեք `Idle timeout: no data from` արտահայտությունը (կամ `stream_idle_timeout` կոդը / `StreamIdleTimeoutError` սխալի անունը)։ Provider հատվածն այն արժեքն է, որն OmniRoute-ն օգտագործել է տվյալ հարցման համար (`codex`, մեկ այլ provider id կամ `provider`, եթե անհայտ է)․ այն միշտ չէ, որ բառացիորեն `codex` տողն է։

## Խնդիրների վերացում

**`Error: wire_api = "chat" is no longer supported`**
Հեռացրեք `wire_api = "chat"`-ը ձեր կազմաձևից։ Սահմանեք `wire_api = "responses"` կամ բաց թողեք դաշտը (`v0.138`-ից ի վեր լռելյայն արժեքը `"responses"` է)։

**`Error: model not found`**
Համոզվեք, որ մոդելը գոյություն ունի OmniRoute-ում՝ ճիշտ նախածանցով։ Օգտագործեք `omniroute models list` կամ բացեք `/dashboard/providers/<provider>`։

**`Authentication error`**
Համոզվեք, որ `OMNIROUTE_API_KEY`-ն արտահանված է՝ `echo $OMNIROUTE_API_KEY`։

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex-ը նախքան առաջին հարցումն ուղարկելը ստուգում է, որ միջավայրի փոփոխականը գոյություն ունի։ Պաշտպանված սերվերների համար արտահանեք
իրական բանալի, իսկ երբ ձեր **տեղային** OmniRoute օրինակը նույնականացում չի
պահանջում՝ օգտագործեք ոչ դատարկ տեղապահ արժեք, օրինակ՝
`OMNIROUTE_API_KEY=local`։ Վերագործարկեք հրամանային թաղանթը, եթե այն ավելացրել եք `~/.bashrc` կամ `~/.zshrc` ֆայլում։

**`Connection refused`**
Համոզվեք, որ OmniRoute-ն աշխատում է, իսկ `base_url`-ի հոսթը/պորտը ճիշտ է ձեր ցանցի համար (տեղային, Tailscale կամ VPS)։

**Աշխատաշրջանը խափանվում է համատեքստի սահմանաչափին մոտ**
Հստակ սահմանեք `model_context_window`-ն ու `model_auto_compact_token_limit`-ը։ Տե՛ս վերևում ներկայացված համատեքստի պատուհանի աղյուսակը։

**Կոմպակտացումը չափազանց ուշ է գործարկվում**
Նվազեցրեք `model_auto_compact_token_limit`-ը մինչև պատուհանի 80–85%-ը։ Երբեք մի սահմանեք 90%-ից բարձր։

**Պրոֆիլը չի բեռնվում (`-p <name>`-ն աննկատ անտեսվում է)**
Համոզվեք, որ `~/.codex/<name>.config.toml` ֆայլը գոյություն ունի (`profile-` նախածանց չպետք է լինի)։ Գործարկեք `ls ~/.codex/*.config.toml`։

**Codex-ի երկարատև առաջադրանքն ընդհատվում է կատարման ընթացքում / քայլերի միջև փոխում է հաշիվները**
Տե՛ս [Երկարատև առաջադրանքներ](#long-running-tasks)։ Միացրեք աշխատաշրջանի կապակցումը (TTL-ը պետք է գերազանցի առաջադրանքի տևողությունը) և ավելացրեք կամ անջատեք `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`։ OmniRoute-ի գրանցամատյաններում `grep`-ով որոնեք `Idle timeout: no data from`։
