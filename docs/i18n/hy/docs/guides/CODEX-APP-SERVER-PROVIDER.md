OmniRoute-ը տրամադրում է OpenAI Codex-ն օգտագործելու **երկու** եղանակ.

| Մատակարար              | Ինչպես է հաղորդակցվում OpenAI-ի հետ                                                                                                                                                                                        | Օգտագործման սահմանափակում                                                                    |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **`codex`**            | Ձեր ChatGPT/OpenAI OAuth թոքենն անմիջապես վերարտադրում է Responses API-ում                                                                                                                                                 | **Այո** — պաշտոնական աշխատաշրջանը թույլատրված չէ պրոքսիի/երթուղիչի միջոցով օգտագործման համար |
| **`codex-app-server`** | JSON-RPC/WebSocket-ի միջոցով կառավարում է **Codex CLI-ի սեփական `codex app-server`-ը**. CLI-ն ինքն է տնօրինում և ավտոմատ թարմացնում իր OAuth-ը (`~/.codex/auth.json`)՝ ճիշտ այնպես, ինչպես ինտերակտիվ `codex` աշխատաշրջանը | **Ոչ** — OmniRoute-ը երբեք թոքեն չի վերարտադրում API-ում                                     |

Քանի որ `codex-app-server`-ը երբեք թոքեն չի վերարտադրում, դրա վրա չի տարածվում
աշխատաշրջանի վերարտադրմամբ օգտագործման սահմանափակումը։ Այն պահանջում է, որ
**Codex CLI-ն հասանելի լինի կազմաձևված app-server URL-ով**, և այդ CLI-ում պետք է
**մուտք գործած լինել**։

## 1. Ճարտարապետություն

```
┌─ OmniRoute հավելված ─────────────┐        ┌─ codex-app-server կողային կոնտեյներ ─┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                    │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456          │
│  (+ հնարավորությունների թոքեն)    │  JSON  │  --ws-auth capability-token          │
│                                  │  RPC   │  ինքնուրույն կառավարում է OpenAI OAuth-ը │
└──────────────────────────────────┘        │  (~/.codex/auth.json, ավտոթարմացում) │
        │ համօգտագործվում է (compose հատորներ) └─────────────────────────────────────┘
        ▼
  codex-appserver-token   → WS հնարավորությունների թոքենը (երկուսն էլ միացնում են այն)
  codex-appserver-home    → ~/.codex (auth.json-ը գրվում է կառավարման վահանակի կողմից,
                             կարդացվում է կողային կոնտեյների codex app-server-ի կողմից)
```

- Կողային կոնտեյները հասանելի է **միայն** ներքին compose ցանցում
  (`ws://codex-app-server:1456`)՝ հնարավորությունների թոքենով պաշտպանված։ Այն
  **երբեք** չի հրապարակվում հոսթում կամ համացանցում։
- Codex CLI-ն ներառված է `omniroute:base`-ում, ուստի կողային կոնտեյներն
  աշխատեցնելիս հոսթում կամ օգտատիրոջ համակարգչում codex տեղադրելու կարիք չկա։

## 2. Գործարկում

```bash
# Գործարկեք ստեկը codex app-server կողային կոնտեյների պրոֆիլով.
docker compose --profile base --profile codex-app-server up -d
# (podman՝ podman compose --profile base --profile codex-app-server up -d)
```

Առաջին մեկնարկի ժամանակ կողային կոնտեյներն ստեղծում է իր WS
հնարավորությունների թոքենը (համօգտագործվող `codex-appserver-token` հատորում),
իսկ հավելվածը նույն թոքենը կարդում է
`OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`-ի միջոցով։ Թոքենի ձեռքով միացում
անհրաժեշտ չէ։

## 3. Միացում և մուտք

1. Կառավարման վահանակում ավելացրեք միացում **OpenAI Codex (App-Server)**-ի
   համար։ API բանալի կամ թոքեն չի պահանջվում (սա նույնականացում չպահանջող
   մատակարար է. նույնականացումը տնօրինում է կողային կոնտեյները)։
2. Եթե կողային կոնտեյների Codex CLI-ում **դեռ մուտք գործած չեք**, միացման
   վիճակի ստուգումը հաղորդում է _«աշխատում է, բայց մուտք գործած չէ»_ (ոչ թե
   նույնականացման կարմիր սխալ)։ Օգտագործեք **Մուտք գործել ChatGPT-ով** տարբերակը.
   այն դիտարկիչում գործարկում է Codex-ի ստանդարտ սարքային OAuth-ը, ապա
   **Կիրառել նույնականացումը** գործողության միջոցով գրում է
   `~/.codex/auth.json`-ը համօգտագործվող հատորում (նույն մուտքը սպասարկում է
   և՛ `codex`, և՛ `codex-app-server` մատակարարներին)։
3. Մուտք գործելուց հետո վիճակի ստուգումը կանաչ է դառնում (այն ստուգում է և՛
   `/readyz`-ը, **և՛** `account/read`-ը, այսինքն՝ ծառայությունը միաժամանակ
   գործարկված **և** նույնականացված է), և համակարգը սկսում է աշխատել։

Կառավարման վահանակը երբեք չի վերագրում գործող `~/.codex/auth.json`-ը. այն գրում
է միայն այն դեպքում, երբ ֆայլը բացակայում է կամ դրա թոքենը հնացած է (միշտ
ստեղծվում է պահուստային պատճեն)։

## 4. Տեղակայման սցենարներ

- **Արդեն նույնականացված Codex CLI ունեցող օպերատոր** — ձեր հոսթի
  `~/.codex`-ը միացրեք կողային կոնտեյներին (`codex-appserver-home`) և բաց թողեք
  մուտքի քայլը։
- **Հանրային օգտատեր, որի տեղային համակարգում codex տեղադրված չէ** — դա
  նշանակություն չունի. CLI-ն առկա է կողային կոնտեյներում։ Օգտատերը
  նույնականացվում է միայն կառավարման վահանակի միջոցով։
- **Անմիջապես հոսթում աշխատող OmniRoute (առանց կողային կոնտեյների, հոսթային codex)** —
  `OMNIROUTE_CODEX_APPSERVER_WS`-ը ուղղեք ձեր սեփական `codex app-server`-ին և
  համոզվեք, որ հոսթային codex-ում մուտք գործած եք. եթե գործարկվող ֆայլը
  բացակայում է, ցուցադրվում է «codex-ը տեղադրված չէ» հուշումը։

## 5. Բնակելի / UDP ելքային կապ (օպերատորի հավելում, չի մատակարարվում)

Վերևում նկարագրված ընդհանրական կողային կոնտեյների ելքային կապն անցնում է
կոնտեյների սովորական ցանցով։ Օպերատորը, որին անհրաժեշտ է Codex-ի տրաֆիկն
ուղղել **բնակելի ելքի** միջոցով (օրինակ՝ TUN tailscale կողային կոնտեյներով, որը
փոխադրում է TCP + UDP/QUIC), դա գործարկում է որպես առանձին compose վերասահմանում։
Այն միտումնավոր **ներառված չէ** մատակարարվող `codex-app-server` պրոֆիլում։
Այդ կարգավորման համար տես ներքին գործառնական ուղեցույցը։
