Ռելեները (Vercel, Deno, Cloudflare) ավարտում են վերին հոսքի կապը serverless բեքենդում, որպեսզի OmniRoute-ը կարողանա ելքային կապ հաստատել կայուն տարածաշրջանից՝ միաժամանակ պրովայդերի API բանալին պահելով սերվերի կողմում։ Այս փաստաթուղթը նկարագրում է արտադրական միջավայրում օպերատորների հանդիպած երկու խափանման ռեժիմները և դրանցից յուրաքանչյուրի համար OmniRoute-ի տրամադրած վերականգնման ուղիները։

## Ինչպես է պահվում ռելեի իսկորոշումը

Երբ ռելե եք տեղակայում **Settings → Proxy Pool → Deploy Relay** բաժնից, տեղակայման հոսքը ռելեի իսկորոշման թոքենը պահում է պրոքսիի `notes` JSON դաշտում․

- Եթե `STORAGE_ENCRYPTION_KEY`-ը սահմանված է, թոքենը գրվում է որպես `relayAuthEnc`
  (պահպանման ժամանակ AES-ով գաղտնագրված)։
- Հակառակ դեպքում այն գրվում է բաց տեքստով՝ որպես `relayAuth`։

Հարցման պահին `extractRelayAuth(notes)`-ը վերադարձնում է առկա տարբերակը, այնպես որ ռելեն շարունակում է աշխատել վերագործարկումներից հետո։

## Խափանման ռեժիմ 1 — բանալու ռոտացիայից հետո չվերծանվող թոքեն

**Ախտանիշ․** նախկինում աշխատող ռելեներն այժմ վերադարձնում են վերին հոսքի `401`/իսկորոշման սխալներ՝ միջավայրում կամ գաղտնիքների կառավարման համակարգում `STORAGE_ENCRYPTION_KEY`-ի ռոտացիայից հետո։ Պահված `relayAuthEnc` բլոբն այլևս հնարավոր չէ վերծանել, ուստի `extractRelayAuth`-ը վերադարձնում է դատարկ տող, և ռելեն իսկորոշման տվյալներ չի ուղարկում։

**Վերականգնում — տեղում վերանորոգում (առանց վերատեղակայման)․**

1. Բացեք **Settings → Proxy Pool**։
2. Իսկորոշումը բացակայող ռելեների տողերում ցուցադրվում է դեղին `auth missing` նշան և
   **Repair** կոճակ։
3. Սեղմեք **Repair**։ OmniRoute-ը կանչում է
   `POST /api/settings/proxies/[id]/repair-relay`, որը՝
   - վերծանում է `relayAuthEnc`-ը **ընթացիկ** բանալիով,
   - բաց տեքստով `relayAuth`-ը կրկին գրում է `notes`-ում,
   - վերադարձնում է `{ repaired: true, mode: "recovered" }`։

Ռելեն վերսկսում է սպասարկումը՝ առանց տեղակայման որևէ հավատարմագրի կրկնակի մուտքագրման։

Սա աշխատում է միայն այն դեպքում, երբ ընթացիկ `STORAGE_ENCRYPTION_KEY`-ը դեռ կարող է վերծանել բլոբը։ Եթե բանալին ռոտացիայի եք ենթարկել **առանց** միգրացիայի, բլոբը վերականգնել հնարավոր չէ։

## Խափանման ռեժիմ 2 — անվերականգնելի թոքեն (բանալին փոխարինվել է ռոտացիայի արդյունքում)

**Ախտանիշ․** սեղմել եք **Repair** և ստացել
`{ repaired: false, mode: "redeploy", status: 409 }`։

**Վերականգնում — վերատեղակայում․**

Պահված թոքենը հնարավոր չէ վերականգնել ընթացիկ բանալիով։ Կրկին տեղակայեք ռելեն այն նույն մոդալ պատուհանից, որն ի սկզբանե օգտագործել եք (**Deploy Relay** ընտրացանկ → Vercel / Deno
/ Cloudflare)։ Տեղակայման հոսքը գրում է նոր թոքեն (ընթացիկ բանալիով գաղտնագրված), և տողի `auth missing` նշանն անհետանում է։

UI-ում **Repair** կոճակն ինքն է բացում վերատեղակայման մոդալ պատուհանը, երբ թոքենն անվերականգնելի է, այնպես որ այն ձեռքով փնտրելու կարիք երբեք չի լինում։

## Խափանման ռեժիմ 3 — ռելեն հասանելի է, բայց անառողջ

**Ախտանիշ․** պրոքսիի ստուգումը (`speed` կոճակը) ցույց է տալիս, որ ռելեն հասանելի է, սակայն հարցումները դեռ ընդհատումներով ձախողվում են։

Ստուգեք ռելեի իրազեկման վերնագրերը, որոնք վերադարձվում են OmniRoute-ի ավտոմատ ստուգման հարցման կողմից (տե՛ս **Settings → Proxy Pool** և `relayTested` / `relayAlive` հաշվիչները)․

- `x-relay-url` — ռելեի որ բեքենդն է պատասխանել։
- `x-relay-mode` — տվյալ հարցման համար `ts` | `bifrost` | `auto`։
- `x-relay-attempts` — քանի ռելե-անցում է փորձարկվել մինչև հաջողությունը։
- `x-relay-fallback` — `true`, երբ հարցումը նախընտրելի բեքենդից անցել է պահուստային TypeScript ռելեին։

`x-relay-fallback`-ի բարձր հաճախականությունը՝ ցածր `relayAlive`-ի հետ միասին, նշանակում է, որ sidecar բեքենդն անառողջ է, և դուք պետք է կամ շտկեք այն, կամ ռելեի բեքենդի ռազմավարությունը փոխեք `ts`-ի (տե՛ս `RELAY_BACKEND_STRATEGY.md`)։

## API տեղեկատու

| Մեթոդ  | Ուղի                                      | Մարմին                  | Հաջողություն                                                                                                                              | Ձախողում                                                                            |
| ------ | ----------------------------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }`՝ կրկին ստանալու դեպքում, `200 { repaired: false, mode: "noop" }`՝ երբ բաց տեքստն արդեն առկա է | `409 { mode: "redeploy" }`՝ անվերականգնելի, `400`՝ ռելեի տեսակ չէ, `404`՝ չի գտնվել |

Ցանկի `GET /api/settings/proxies` երթուղին յուրաքանչյուր տարրին կցում է գաղտնիքներ չպարունակող `relayInfo: { isRelay, authMissing, repairMode }`, որպեսզի կառավարման վահանակը կարողանա ցուցադրել վերանորոգման հնարավորությունը՝ երբեք չբացահայտելով թոքենը։
