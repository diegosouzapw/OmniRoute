`open-sse/config/providerPluginManifest.ts`-ը սահմանում է JSON-ի համար անվտանգ՝ մատակարարի
փլագինի պայմանագիրը։ `open-sse/config/providerPluginManifestRegistry.ts`-ը կապում է այդ
պայմանագիրը մատակարարների ընթացիկ ռեեստրի հետ՝ Bifrost-ի,
CLIProxyAPI-ի կամ ապագա Go/Rust երթուղիչի նման կողմնակի ծառայությունների համար։ TypeScript-ի ռեեստրը մնում է
ճշմարտության աղբյուրը, սակայն կողմնակի ծառայությունները կարող են օգտագործել մանիֆեստը՝ առանց
կատարիչի կոդը, OAuth-ի լռելյայն արժեքները, վերնագրերը կամ պրոցեսի միջավայրի վիճակը ներմուծելու։

Նույն մանիֆեստը հասանելի է նաև HTTP-ով՝
`GET /api/v1/provider-plugin-manifest` հասցեում՝ առանձին պրոցեսում աշխատող կողմնակի ծառայությունների համար։

OmniRoute-ն այդ URL-ը փոխանցում է Bifrost-ին և CLIProxyAPI-ին՝
`X-OmniRoute-Provider-Manifest-Url` հարցման վերնագրի միջոցով։ Սահմանեք
`OMNIROUTE_PROVIDER_MANIFEST_URL`, երբ կողմնակի ծառայությանը տեղական հարցման սկզբնաղբյուրի փոխարեն
անհրաժեշտ է հանրային կամ կոնտեյներային ցանցի URL։

## Մանիֆեստի թարմացումը

HTTP վերջնակետը վերադարձնում է `Cache-Control: public, max-age=60` և ուժեղ
`ETag`։ Կողմնակի ծառայությունը պետք է պահպանի վերջին վավերացված մանիֆեստը և թարմացնելիս ուղարկի դրա ETag-ը
`If-None-Match`-ում։ `304 Not Modified` պատասխանը մարմին չունի․
կողմնակի ծառայությունը շարունակում է օգտագործել քեշավորված մանիֆեստը։ Եթե վավերացված քեշավորված մանիֆեստ չկա,
կողմնակի ծառայությունը `304` ընդունելու փոխարեն պետք է ուղարկի առանց պայմանների հարցում։

## Նպատակ

Մատակարարների մետատվյալները տեղափոխել դեպի փլագինային պայմանագիր, որպեսզի հարցումների թեժ ուղին
հետագայում կարողանա սպասարկվել ավելի ցածր ուշացմամբ կողմնակի ծառայության կողմից, մինչդեռ OmniRoute-ը
TypeScript երթուղին պահպանում է որպես քաղաքականության վերահսկիչ շերտ և պահուստային տարբերակ։ Մանիֆեստը հավելում է․ այն
ինքնին չի փոխում հարցումների երթուղավորումը։

## Պայմանագիր

Մանիֆեստը պարունակում է՝

- մատակարարի id-ն և այլանունը
- վերին հոսքի ձևաչափը և կատարիչի անունը
- նույնականացման տեսակը, նույնականացման վերնագիրը և ոչ պարտադիր նույնականացման նախածանցը
- վերջնակետի ստատիկ մետատվյալները
- կողմնակի ծառայության համար համապատասխանությունը և հստակ պատճառները, երբ մատակարարը պետք է մնա TS ուղու վրա
- JSON-ի համար անվտանգ մոդելի մետատվյալներ, օրինակ՝ համատեքստի երկարությունը, տեսողական/դատողության դրոշները և
  չաջակցվող պարամետրերը
- հնարավորությունների պիտակներ, ներառյալ `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` և `usage-supported`

Մանիֆեստը միտումնավոր բացառում է՝

- OAuth հաճախորդի գաղտնիքները և լռելյայն գաղտնի արժեքները
- կատարման ժամանակ միջավայրի որոշումը
- հարցման վերնագրերը և հանրային հավատարմագրերի օժանդակ գործիքները
- դինամիկ URL կառուցիչները
- կատարիչի ֆունկցիաները
- աշխատաշրջանների ավազանի ներքին կառուցվածքը

## Հնարավորությունների պիտակներ

`capabilities`-ը ռեեստրի գրառումից ստացված պիտակների տեսակավորված զանգված է։ Ինտեգրողները
պետք է այն դիտարկեն որպես «ի՞նչ կարող է անել այս մատակարարը» հարցի մեքենայաընթեռնելի պատասխան՝
TypeScript-ի սկզբնաղբյուրները կրկին կարդալու փոխարեն։

| Պիտակ                | Նշանակություն                                                                                  |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| `apikey`             | Ընդունում է API բանալի (`authType`-ը `apikey` կամ `optional` է)։                               |
| `oauth`              | Օգտագործում է OAuth կամ աշխատաշրջանի հոսք։                                                     |
| `responses`          | Տրամադրում է OpenAI Responses API-ի բազային URL։                                               |
| `passthrough-models` | Ստատիկ կատալոգի փոխարեն մոդելները տրամադրում է անմիջապես վերին հոսքից։                         |
| `custom-executor`    | Գործարկում է ոչ լռելյայն կատարիչ, ուստի մնում է TypeScript ուղու վրա։                          |
| `sidecar-candidate`  | Արտացոլում է `sidecar.eligible`-ը՝ անվտանգ է դիտարկել կողմնակի ծառայություն ներմուծելու համար։ |
| `usage-fetch`        | Ունի միացված օգտագործման կամ քվոտայի ստացման մեխանիզմ (`getUsageForProvider`)։                 |
| `usage-supported`    | Օգտագործման API-ն ընդունում է այս մատակարարին (`isSupportedUsageConnection`)։                  |

`usage-fetch`-ը միայն հայտնաբերման համար է։ Այն հայտնում է, որ OmniRoute-ը գիտի՝ ինչպես կարդալ
մատակարարի օգտագործման տվյալները․ այն չի ակտիվացնում ստացումը, չի փոխում քվոտայի իմաստաբանությունը և չի ենթադրում, որ
Dashboard-ի քվոտայի վիջեթը միացված է մատակարարի համար․ այդ վիջեթն առանձին վերահսկվում է
`USAGE_SUPPORTED_PROVIDERS`-ով։ Ճշմարտության աղբյուրը `USAGE_FETCHER_PROVIDERS`-ն է՝
`open-sse/services/usage/fetcherProviders.ts`-ում։

Այդ ցանկը բանալիներով կապված է օգտագործման դիսպետչերի ընդունած տողերի հետ, ուստի այն խառնում է կանոնական id-ները
այլանունների հետ և մի փոքր ավելի երկար է, քան պիտակավորված մատակարարների քանակը․ այն գրառումները, որոնք
մանիֆեստի ռեեստրում զրույցի մատակարարներ չեն (օրինակ՝ `firecrawl` որոնման մատակարարը
և `amazon-q` ACP մատակարարը), չունեն մանիֆեստի գրառում, որին կարելի է պիտակ կցել։

`usage-supported`-ը պատասխանում է՝ արդյոք սերվերի և Dashboard-ի օգտագործման երթուղիներն ընդունում են
մատակարարի կապը։ Այն արտացոլում է `isSupportedUsageConnection()`-ը (`src/lib/usage/providerLimits.ts`)
և `supportsProviderQuota()`-ն (`src/shared/utils/providerQuotaVisibility.ts`), որոնք երկուսն էլ վերահսկվում են
`USAGE_SUPPORTED_PROVIDERS`-ով (`open-sse/services/usage/supportedProviders.ts`)։ Ի տարբերություն
`usage-fetch`-ի՝ այն ստեղծվում է միայն մատակարարի id-ի հիման վրա․ կատարման ժամանակի պաշտպանիչ ստուգումը կատարում է
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)`՝ առանց այլանունների լուծման, ուստի մանիֆեստը
պահպանում է նույն կանոնը։ Երկու պիտակներն ունեն տարբեր ընդգրկումներ․ 3 մատակարար ունեն միայն
`usage-fetch` (`opencode`, `opencode-zen`, `xai`), իսկ 1-ը՝ միայն
`usage-supported` (`xiaomi-mimo-token-plan`), հետևաբար մեկը չի ենթադրում մյուսը։

## Sidecar-ի օգտագործումը

Sidecar-ները պետք է `sidecar.eligible`-ը դիտարկեն որպես թեկնածության պահպանողական ազդանշան, այլ ոչ թե որպես երթուղավորման անվերապահ որոշում։ Ներմուծման առաջին թիրախը պետք է լինեն API բանալի և ստատիկ վերջնակետ օգտագործող պրովայդերները, որոնք կիրառում են լռելյայն executor-ը։ Հատուկ web executor-ներ, OAuth/session հոսքեր, դինամիկ URL կառուցիչներ կամ pool-ի կազմաձևում ունեցող պրովայդերները մնում են TypeScript-ի պահուստային ուղու վրա, մինչև որևէ sidecar կիրականացնի համարժեք վարքագիծ, իսկ հեռաչափությունը կհաստատի համարժեքությունը։

Առաջարկվող միգրացիոն փուլերը՝

1. Ստեղծել և վավերացնել պրովայդերի plugin manifest-ը TS registry-ից։
2. Սովորեցնել Bifrost-ին կամ CLIProxyAPI-ին ներմուծել manifest-ը API բանալի/ստատիկ վերջնակետ օգտագործող պրովայդերների համար։
3. Համապատասխան պրովայդերները երթուղավորել sidecar-ի միջոցով՝ `OMNIROUTE_RELAY_BACKEND`-ի հետևում, միաժամանակ միացված պահելով TS-ի պահուստային ուղին։
4. Պրովայդերներն առաջ մղել միայն այն դեպքում, երբ հաջողության գործակիցը, p99 ուշացումը, հոսքային փոխանցման վարքագիծը և չաջակցվող պարամետրերի մշակումը համընկնում են TS ուղու հետ։
5. Հատուկ executor-ների համար ավելացնել sidecar-ին բնորոշ plugin-ներ՝ միաժամանակ մեկ պրովայդերների ընտանիքի համար։
