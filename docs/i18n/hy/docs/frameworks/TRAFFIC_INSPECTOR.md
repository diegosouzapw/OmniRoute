Traffic Inspector-ը OmniRoute-ի ներկառուցված HTTPS տրաֆիկի վրիպազերծիչն է՝ Charles Proxy-ին / mitmweb-ին / HTTP Toolkit-ին նման գործիք, որը **տեղեկացված է LLM-ների մասին** և **տեղեկացված է գործակալների մասին**։ Այն հասանելի է `/dashboard/tools/traffic-inspector` հասցեում և իրական ժամանակում տրաֆիկ է ստանում միաժամանակ մինչև 5 հավաքագրման աղբյուրից։

**Վահանակի տեղադրությունը՝** `/dashboard/tools/traffic-inspector`
**Կողագոտու խումբը՝** Գործիքներ (AgentBridge-ից հետո)
**Տես նաև՝** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge-ը հավաքագրման 1-ին ռեժիմն է։

### Ճարտարապետությունը՝ մեկ պարբերությամբ

`TrafficBuffer`-ը (`src/mitm/inspector/buffer.ts`) ընդհանուր, հիշողության մեջ պահվող օղակաձև բուֆեր է (լռելյայն՝ 1000 գրառում, կարգավորվում է `INSPECTOR_BUFFER_SIZE`-ի միջոցով)։ Հավաքագրման բոլոր աղբյուրները դրանում տվյալներ են գրում `push()`-ի միջոցով։ Բուֆերը դասակարգում է յուրաքանչյուր գրառում՝ օգտագործելով `kindDetector.ts`-ը (որոշում է՝ արդյոք դա LLM հարցում է), հաշվարկում է `contextKey`-ը (համակարգային հուշման SHA-256 մատնահետքը) և `globalTrafficBuffer.subscribe()`-ի միջոցով հեռարձակում է բոլոր WebSocket բաժանորդներին։ Վահանակը միանում է `GET /api/tools/traffic-inspector/ws`-ի միջոցով և միանալիս ստանում է ակնթարթային պատճեն, որին հաջորդում են `new`/`update`/`clear` իրադարձությունները։

## §2 Գրանցման ռեժիմներ

Traffic Inspector-ն աջակցում է **միաժամանակյա գրանցման 5 աղբյուր**։ Յուրաքանչյուրը կարելի է միացնել կամ անջատել՝ մյուսներից անկախ։ Յուրաքանչյուր `InterceptedRequest`-ի (`src/mitm/inspector/types.ts`) `source` դաշտը կարող է լինել `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"` կամ `"tproxy"`։

### Ռեժիմ 1 — AgentBridge (լռելյայն, միշտ միացված)

**Աղբյուր՝** AgentBridge մշակիչներ (`src/mitm/handlers/base.ts`)
**Մեխանիզմ՝** `MitmHandlerBase`-ում յուրաքանչյուր `intercept()` կանչ վերահասցեավորումից առաջ կանչում է `hookBufferStart()`, իսկ ավարտից հետո՝ `hookBufferUpdate()`։ Լրացուցիչ կարգավորում չի պահանջվում. աշխատում է AgentBridge-ի գործարկումից անմիջապես հետո։
**Ընդգրկում՝** AgentBridge-ում կազմաձևված 9 IDE գործակալները
**Նշում՝** `InterceptedRequest`-ի `source` դաշտը = `"agent-bridge"`

### Ռեժիմ 2 — Հատուկ հոսթեր (DNS վերահղում)

**Աղբյուր՝** Օգտատիրոջ սահմանած հոսթերի ցանկ (`inspector_custom_hosts` աղյուսակ)
**Մեխանիզմ՝** UI-ի միջոցով հոսթ ավելացնելիս `/etc/hosts`-ում ավելացվում է `127.0.0.1 <host>` (պահանջում է sudo)։ Գոյություն ունեցող AgentBridge MITM սերվերը (պորտ 443) նոր հոսթի համար դինամիկորեն ստեղծում է SNI վկայական։
**Ընդգրկում՝** Ավելացված հոսթն օգտագործող ցանկացած հավելված. հավելվածի կազմաձևումը փոխելու կարիք չկա
**Նշում՝** `source` = `"custom-host"`

Օգտագործման օրինակներ՝

- Վերահսկել `api.openai.com`-ը Python սկրիպտներից
- Կարգաբերել `my-internal-llm.company.com`-ը
- Գրանցել նույն ցանցում գտնվող շարժական սարքերի թրաֆիկը (ARP spoofing-ի միջոցով՝ առաջադեմ տարբերակ)

### Ռեժիմ 3 — HTTP_PROXY ունկնդրիչ (պորտ 8080)

**Աղբյուր՝** `HTTP_PROXY`/`HTTPS_PROXY` միջավայրի փոփոխականներն օգտագործող հավելվածներ
**Մեխանիզմ՝** 8080 պորտում գործող երկրորդական ունկնդրիչ (`src/mitm/inspector/httpProxyServer.ts`), որը գործում է որպես ստանդարտ բացահայտ HTTP/HTTPS պրոքսի։ Ընդունում է `CONNECT` թունելներ (HTTPS) և անմիջական HTTP հարցումներ։
**Ընդգրկում՝** `HTTP_PROXY` միջավայրի փոփոխականը հաշվի առնող ցանկացած հավելված. DNS-ի փոփոխություն և sudo չեն պահանջվում
**Նշում՝** `source` = `"http-proxy"`

```bash
# Մեկ հրամանի արագ գրանցում՝
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# Մշտական գրանցում shell աշխատաշրջանում՝
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**TLS սահմանափակում՝** HTTPS `CONNECT` թունելների համար գրանցվում են միայն մետատվյալները (հոսթ, պորտ, ժամանակային տվյալներ). TLS բովանդակությունը լռելյայն չի վերծանվում։ Ամբողջական բովանդակությունը ստուգելու համար միացրեք «Վերծանել HTTPS-ը պրոքսիի ռեժիմում» փոխարկիչը (ըստ ցանկության, պահանջում է, որ AgentBridge-ի վկայականը լինի վստահելի)։

**Պորտի բախում՝** Եթե 8080 պորտն օգտագործվում է, AgentBridge-ը վերադարձնում է 409՝ կառուցվածքավորված սխալով։ Փոխեք պորտը `INSPECTOR_HTTP_PROXY_PORT` միջավայրի փոփոխականի միջոցով։

### Ռեժիմ 4 — Համակարգային պրոքսի (առաջադեմ, ըստ ցանկության)

**Աղբյուր՝** ՕՀ-ի մակարդակի պրոքսիի կարգավորումներ (կիրառվում է մեքենայի բոլոր հավելվածների նկատմամբ)
**Մեխանիզմ՝** ՕՀ-ի API-ների միջոցով ամբողջ HTTP/HTTPS թրաֆիկը վերահղում է HTTP_PROXY ունկնդրիչով՝

- **macOS՝** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux՝** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows՝** `netsh winhttp set proxy 127.0.0.1:8080`
  **Ընդգրկում՝** Մեքենայի՝ համակարգային պրոքսիի կարգավորումները հաշվի առնող յուրաքանչյուր հավելված
  **Նշում՝** `source` = `"system-proxy"`

**Անվտանգության մեխանիզմներ՝**

- Ավտոմատ անջատման ժամանակաչափ (լռելյայն՝ 30 րոպե, կազմաձևվում է `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES`-ի միջոցով)
- Համակարգային պրոքսիի նախորդ վիճակը պահվում է DB-ում և վերականգնվում է հետադարձման ժամանակ
- Եթե օգտատերը համակարգային պրոքսիի ակտիվ լինելու ընթացքում հեռանում է էջից, կառավարման վահանակը ցուցադրում է «Հետադարձնել համակարգային պրոքսին» հուշումը
- UI-ն ցուցադրում է `⚠ Առաջադեմ` նշան + հաստատման բացահայտ նշավանդակ

### Ռեժիմ 5 — TPROXY թափանցիկ վերծանում (Linux, root, ըստ ցանկության)

**Աղբյուր՝** Միջուկի TPROXY + քաղաքականության հիման վրա երթուղավորում (`src/mitm/tproxy/`)
**Մեխանիզմ՝** `mangle OUTPUT`-ում նշում է դեպի թիրախային պորտը (լռելյայն՝ `443`) ստեղծվող նոր տեղային ելքային TCP կապերը, `ip rule`-ը նշված փաթեթները վերաուղղորդում է տեղային առաքման, իսկ `mangle PREROUTING`-ի `TPROXY` թիրախը դրանք փոխանցում է թափանցիկ (**IP_TRANSPARENT**) ունկնդրիչին (լռելյայն պորտ՝ `8443`)։ Ունկնդրիչը դադարեցնում է TLS-ը՝ օգտագործելով դինամիկ CA-ի կողմից **յուրաքանչյուր SNI հոսթի անվան համար ըստ պահանջի** տրամադրված վերջնական վկայական, գրանցում է վերծանված փոխանակումը և հարցումը վերահասցեավորում է սկզբնական նպատակակետին՝ կրկին գաղտնագրված։
**Ընդգրկում՝** Թիրախային պորտում գտնվող **ցանկացած** նպատակակետ հոսթեր. `/etc/hosts`-ի կեղծում, `HTTP_PROXY` միջավայրի փոփոխական և համակարգային պրոքսիի փոփոխություն չեն պահանջվում։ Ընդհատվող գործընթացի կազմաձևումը փոխելու կարիք չկա, սակայն այն պետք է վստահի դինամիկ CA-ին։
**Նշում՝** `source` = `"tproxy"`

**Պահանջներ՝** Միայն Linux (**IP_TRANSPARENT**-ը հասանելի է միայն Linux-ում), **CAP_NET_ADMIN** հնարավորություն (root) և տեղային N-API հավելում, որը պետք է կառուցվի C գործիքաշարով (`npm run build:native:tproxy`)։ Անհասանելի լինելու դեպքում կառավարման վահանակի փոխարկիչն անջատված է, իսկ հուշումը հայտնում է՝ «TPROXY վերծանումը պահանջում է Linux + root + տեղային հավելում»։ Firewall-ի կանոնները կիրառվում/հետադարձվում են տրանզակցիոն եղանակով (խափանման հետևանքով երբեք չի մնում `mangle` կանոն) և մաքրվում են վերագործարկման ժամանակ։ SO_MARK-ի վրա հիմնված հակաշրջապտույտը կանխում է պրոքսիի սեփական՝ կրկին գաղտնագրված վերահասցեավորման կրկնակի ընդհատումը։

Սա ծավալուն ենթահամակարգ է՝ իր առանձին օպերատորի ուղեցույցով. firewall-ի ամբողջական բաղադրատոմսի, յուրաքանչյուր SNI-ի համար դինամիկ CA-ի + վստահության պահոցի տեղադրիչի, միայն տեղային երթուղու, հակաշրջապտույտի մանրամասների և կազմաձևման սխեմայի համար տե՛ս `docs/security/MITM-TPROXY-DECRYPT.md` (git-ում, չի կազմարկվում `/docs`-ում)։ Փոխարկիչը կառավարվում է `GET / POST / DELETE /api/tools/agent-bridge/tproxy`-ի միջոցով (նշում՝ երթուղին գտնվում է AgentBridge նախածանցի ներքո, ոչ թե Traffic Inspector-ի նախածանցի)։

- Ցանկը և մանրամասների վահանակը բաժանված են քաշելու բռնակով
- Ցանկի լայնությունը՝ նվազագույնը 280px, առավելագույնը 720px, պահպանվում է `localStorage`-ում (`inspector.listWidth`)
- Կարող է ծալվել մինչև 48px լայնությամբ շերտ (միայն պատկերակներ)․ ընդարձակելու համար սեղմեք շերտի որևէ տողի վրա

## §4 LLM-ին հարմարեցված գործառույթներ

### 4.1 Տեսակի որոշիչ (`src/mitm/inspector/kindDetector.ts`)

Յուրաքանչյուր հարցում դասակարգում է որպես `"llm"`, `"app"` կամ `"unknown"`՝ օգտագործելով 4 ազդանշան.

1. **Հոսթերի գրանցամատյան** — LLM API-ների մոտ 18 հայտնի հոսթի անուններ (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot և այլն)
2. **Ուղու ձևանմուշներ** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses` և այլն
3. **Մարմնի կառուցվածք** — հայտնաբերում է `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input` դաշտերը
4. **User-agent-ի հուշումներ** — `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor`՝ UA տողում

Mode 2-ի միջոցով ավելացված հատուկ հոսթերը ժառանգում են իրենց `kind`-ը ձևի մուտքագրումից (լռելյայն՝ `"custom"`):

### 4.2 SSE միավորիչ (`src/mitm/inspector/sseMerger.ts`)

**Անկախ, զրոյից իրականացված տարբերակ։** Իրադարձությունների վերլուծումը հետևում է
[WHATWG-ի՝ սերվերից ուղարկվող իրադարձությունների ալգորիթմին](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream),
իսկ վերակառուցումը՝ [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) և
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent)
հանրային հոսքային սխեմաներին։

Վերակառուցում է օգնականի վերջնական հաղորդագրությունը SSE-ի չմշակված դելտա իրադարձություններից.

- **Anthropic**: կուտակում է `content_block_delta`-ն ըստ ինդեքսի, մշակում է `text_delta`, `input_json_delta` (գործիքների կանչեր), `thinking_delta`
- **OpenAI**: կուտակում է Chat Completions-ի ընտրանքները/գործիքների կանչերը և Responses API-ի ելքային տարրերը՝
  ըստ ինդեքսի
- **Gemini**: կուտակում է `candidates[i].content.parts`
- **Անհայտ**: վերադարձնում է չմշակված իրադարձություններն առանց փոփոխության

Response ներդիրը ցուցադրում է փոխարկիչ՝ **«Չմշակված իրադարձություններ ↔ Միավորված»**։

### 4.3 Զրույցի նորմալացուցիչ (`src/mitm/inspector/conversationNormalizer.ts`)

**Անկախ, զրոյից իրականացված տարբերակ։** Նորմալացումը սահմանվում է տեղային սև արկղի
պայմանագրերով և OpenAI, Anthropic ու Gemini հաղորդագրությունների հանրային սխեմաներով. վերին հոսքի
իրականացման սկզբնաղբյուր չի օգտագործվում։

OpenAI, Anthropic և Gemini հաղորդագրությունների ձևաչափերը ցուցադրումից առաջ փոխակերպում է միասնական `NormalizedConversation`-ի.

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // հարցման մարմնի messages / contents / prompt
  response: NormalizedTurn[]; // օգնականի պատասխանը (միավորված է sseMerger-ի միջոցով)
  contextKey: string | null; // համակարգային հուշման SHA-256 մատնահետք
}
```

Բլոկների տեսակները՝ `text`, `tool_use`, `tool_result`։ Conversation ներդիրն օգտագործում է այս կառուցվածքը՝ անկախ մատակարարից։

### 4.4 Համատեքստային բանալու գունավորում (`src/mitm/inspector/contextKey.ts`)

- Հաշվում է համակարգային հուշման `SHA-256`-ը (առաջին `role:system` հաղորդագրությունը կամ `system` դաշտը կամ Gemini-ի `systemInstruction`-ը)
- Վերադարձնում է 12 նիշանոց տասնվեցական նախածանց (`"a3f9c2..."`)
- Օգտագործողի միջերեսը բանալին համապատասխանեցնում է որոշակի HSL գույնի՝ ձախ եզրագծի գոտու համար
- **«Նույն համատեքստը» զտիչ**. `ctx #a3f` նշիչի վրա սեղմելն ավելացնում է զտիչ՝ միայն նույն մատնահետքով հարցումները ցուցադրելու համար

Սա հեշտացնում է նույն գործակալի աշխատաշրջանում կատարվող տարբեր «կերպարների» կամ առաջադրանքների տեսողական տարբերակումը։

### 4.5 LLM մետատվյալների դուրսբերում

LLM հարցումների դեպքում LLM Details ներդիրը դուրս է բերում.

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // հարցման մարմնից կամ պատասխանից
  messages: number; // հերթափոխերի քանակը
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // true, եթե պատասխանը SSE է
  mappedTo: string | null; // x-omniroute-mapped վերնագիր
  costEstimateUsd: number | null; // OmniRoute-ի գնագոյացման հիման վրա գնահատված արժեքը
}
```

### 4.6 Ընթացիկ հարցումների իրական ժամանակի զտիչ

Հարցման `status` դաշտի տեսակը `number | "in-flight" | "error"` է. հարցումը սկսվելուն պես գրառումն
ավելացվում է որպես `"in-flight"` և **տեղում թարմացվում է**,
երբ հասնում է պատասխանը (կամ սխալը)։ Գործիքագոտու **«Ուղիղ եթեր»** փոխարկիչը
(`liveOnly`, i18n բանալի՝ `trafficInspector.liveOnly`) սահմանափակում է ցանկը՝ թողնելով միայն այն գրառումները,
որոնց `status === "in-flight"` է, ինչը թույլ է տալիս իրական ժամանակում հետևել բաց կապերին։

Զտիչը զուտ հաճախորդի կողմում գործող պրեդիկատ է՝
`src/lib/inspector/matchesTrafficFilter.ts`-ում.

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

Փոխարկիչի վիճակը պահվում է `useTrafficFilters`-ում (տեսուչի վահանակի հուքերում) և
համակցվում է մյուս զտիչների հետ (պրոֆիլ, հոսթ, գործակալ, աղբյուր, կարգավիճակ, համատեքստ)։

### 4.7 Գործընթացի վերագրում (Linux)

Linux-ում յուրաքանչյուր որսված հարցում կարող է վերագրվել **այն սկզբնավորած տեղային
գործընթացին**։ `InterceptedRequest`-ին ավելացվում են երկու ոչ պարտադիր դաշտեր.

```ts
pid?: number;          // սկզբնավորող գործընթացի id-ն (միայն Linux)
processName?: string;  // սկզբնավորող գործընթացի անունը (միայն Linux)
```

`src/mitm/inspector/processAttribution.ts`-ը կապի _հաճախորդի_
էֆեմերային պորտը համապատասխանեցնում է PID-ի և անվան՝ հետևյալ կերպ.

1. Կարդում է `/proc/net/tcp` և `/proc/net/tcp6`՝ պորտի socket inode-ը գտնելու համար
   (`parseProcNetTcpForInode`, ֆիքսչերներով զուտ փորձարկելի վերլուծիչ)։
2. Սկանավորում է `/proc/<pid>/fd/`-ը՝ `socket:[<inode>]`-ին ուղղված սիմվոլիկ հղում գտնելու համար։
3. Կարդում է գործընթացի անունը `/proc/<pid>/comm`-ից։

1 վայրկյան TTL-ով քեշը սահմանափակում է procfs-ի սկանավորման ծախսը ծանրաբեռնվածության պայմաններում։ Վերագրումն
իրականացվում է **հնարավորության սահմաններում**. ցանկացած ձախողման դեպքում արդյունքը `null` է, և որսումը երբեք չի արգելափակվում։
macOS/Windows-ում ֆունկցիան վերադարձնում է `null` (ժամանակավոր իրականացում. `lsof`/`GetExtendedTcpTable`
աջակցությունը նախատեսված է հետագա աշխատանքի համար)։

## §5 Սեսիաներ

### 5.1 Սեսիայի գրանցում

1. Գործիքագոտում սեղմեք **«● Գրանցել սեսիան»** → մուտքագրեք անուն (ըստ ցանկության)
2. Ուղիղ հոսքը շարունակվում է սովորական ձևով․ կարմիր թարթող ցուցիչը ցույց է տալիս `◉ ԳՐԱՆՑՈՒՄ · <անուն> · 00:42 · 23 հարցում`
3. Սեղմեք **«⏹ Դադարեցնել»** → սեսիայի պատկերը պահվում է `inspector_sessions` + `inspector_session_requests` աղյուսակներում

### 5.2 Գրանցված սեսիայի դիտում

Գործիքագոտու **Սեսիաներ** բացվող ցանկում ցուցադրվում են պահպանված սեսիաները։ Դրանցից մեկն ընտրելիս՝

- Բեռնվում է սեսիայի պատկերը (սառեցված վիճակ)
- Ցուցադրվում է պաստառ՝ `Դիտվում է գրանցված «<անուն>» սեսիան — [Վերադառնալ ուղիղ հոսքին]`
- Հասանելի է դառնում «Վիճակագրություն» ներդիրը՝ Recharts-ի համախմբված տվյալներով

### 5.3 Արտահանման ձևաչափեր

Յուրաքանչյուր սեսիա կարող է արտահանվել հետևյալ ձևաչափերով․

| Ձևաչափ                     | Օգտագործում                                                                                     |
| -------------------------- | ----------------------------------------------------------------------------------------------- |
| **HAR** (HTTP Archive 1.2) | Համատեղելի է Chrome DevTools-ի, Charles-ի և Fiddler-ի հետ՝ ներմուծեք անցանց վերլուծության համար |
| **JSONL**                  | Մեկ `InterceptedRequest`՝ յուրաքանչյուր տողում, համատեղելի է `llm-interceptor` ձևաչափի հետ      |

Արտահանեք `GET /api/tools/traffic-inspector/sessions/{id}/export.har`-ի կամ «Սեսիաներ» բացվող ցանկի ⬇ կոճակի միջոցով։

## §6 Անվտանգություն

Traffic Inspector-ը ցուցադրում է **ամբողջ կալանված HTTPS թրաֆիկը**, ներառյալ նույնականացման վերնագրերն ու հարցումների մարմինները։ Գործում են հետևյալ վերահսկման միջոցները․

| Վերահսկման միջոց              | Մանրամասներ                                                                                                                                                                            |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LOCAL_ONLY**                | Բոլոր երթուղիները և WebSocket վերջնակետը հասանելի են միայն loopback-ից (պարտադրվում է `routeGuard.ts`-ում՝ նախքան նույնականացումը)                                                     |
| **Գաղտնիքների քողարկում**     | Գծային `maskSecret()` սկանավորիչը RFC 6750 Bearer հավատարմագրերը, մատակարարի նախածանցով բանալիները և երկար, անթափանց թոքենները խմբագրում է նախքան `TrafficBuffer.push()`-ը             |
| **Մարմնի չափի սահմանափակում** | `INSPECTOR_MAX_BODY_KB`-ից մեծ մարմինները (լռելյայն՝ 1024 KB) կրճատվում են՝ ավելացնելով `"(կրճատված է արդյունավետության համար)"` ծանուցումը                                            |
| **Վերնագրերի մաքրում**        | Անունները փոխակերպվում են փոքրատառի, framing/hop-by-hop և proxy-auth վերնագրերը հեռացվում են, cookie-ներն ամբողջությամբ խմբագրվում են, իսկ հավատարմագրերի արժեքները՝ `maskSecret()`-ով |
| **CSP**                       | Traffic Inspector-ի էջերում կիրառվում է խիստ Content Security Policy՝ ներդրված պատասխանի մարմինների միջոցով XSS-ը կանխելու համար                                                       |
| **Լռելյայն պահպանում չկա**    | `TrafficBuffer`-ը գտնվում է հիշողության մեջ և կորչում է սերվերի վերագործարկումից հետո։ Սեսիաները պահպանվում են միայն հստակորեն գրանցվելու դեպքում                                      |

### Կիրառվող խիստ կանոններ

| Կանոն                             | Կիրառում                                                                                      |
| --------------------------------- | --------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | Traffic Inspector-ի երթուղիներից ստացվող բոլոր HTTP սխալի պատասխանները մաքրվում են            |
| **#15 + #17** `isLocalOnlyPath()` | `/api/tools/traffic-inspector/`-ը LOCAL_ONLY + SPAWN_CAPABLE է (համակարգային proxy հրամաններ) |

### Հայտնի սահմանափակումներ

- **Համակարգային proxy ռեժիմը** ազդում է սարքի բոլոր հավելվածների վրա՝ ներառյալ VPN հաճախորդներն ու SSO-ն։ Միշտ օգտագործեք ավտոմատ անջատման ժամաչափով։ Մի օգտագործեք ընդհանուր օգտագործման սարքերում։
- **CONNECT թունելի HTTPS**․ 3-րդ ռեժիմը (HTTP_PROXY) HTTPS նպատակակետերի համար կալանում է միայն թունելի մետատվյալները, եթե TLS կալանումը միացված չէ։ Սա նախատեսված վարքագիծ է․ առանց AgentBridge-ի հավաստագրի վստահելի լինելու՝ թափանցիկ կալանումը կխախտեր այդ հավելվածների TLS ստուգումը։
- **Որոշ բաղադրիչներում կոշտ կոդավորված տողեր**․ UI-ի որոշ բաղադրիչներում (F7/F8) կան փոքրաթիվ կոշտ կոդավորված տողեր, որոնք դեռ ընդգրկված չեն i18n բանալիներով։ Դրանք i18n բացերի հաշվետվությունում փաստագրված են որպես հայտնի սահմանափակում և կտեղափոխվեն հետագա փուլում։ Ազդեցության ենթակա տողերը UI-ի դեկորատիվ պիտակներ են, որոնք գործառնական օգտագործման համար թարգմանություն չեն պահանջում։

## §7 Խնդիրների լուծում

### WebSocket-ի անջատում

Եթե ուղիղ հոսքում ցուցադրվում է «Անջատված է»՝

1. Ստուգեք, որ սերվերը դեռ աշխատում է՝ `GET /api/tools/traffic-inspector/capture-modes`
2. Վերբեռնեք էջը. WebSocket-ը նորից կմիանա և կստանա թարմ վիճակապատկեր
3. Եթե սերվերը վերագործարկվել է, հիշողության բուֆերը մաքրվել է. հին գրառումներն այլևս չկան, եթե աշխատաշրջան չի գրանցվել

### 8080 միացքի հակասություն

Եթե HTTP_PROXY ռեժիմը չի գործարկվում՝

```bash
lsof -i :8080    # գտնել գործընթացը
```

Փոխեք միացքը՝

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### Համակարգային պրոքսին չի վերադարձվել նախնական վիճակին

Եթե OmniRoute-ը խափանվում է, երբ համակարգային պրոքսիի ռեժիմն ակտիվ է՝

**macOS՝**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME)՝**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows՝**

```cmd
netsh winhttp reset proxy
```

Հաջորդ բեռնման ժամանակ կառավարման վահանակը նաև կառաջարկի «Վերադարձնել համակարգային պրոքսին նախնական վիճակին», եթե հայտնաբերի, որ DB-ի վիճակը ցույց է տալիս, որ պրոքսին ակտիվ է եղել։

### Բուֆերը լիքն է

Երբ բուֆերը հասնում է `INSPECTOR_BUFFER_SIZE`-ին (լռելյայն՝ 1000), նոր գրառումները հերթով դուրս են մղում ամենահները։ Եթե կարևոր հարցումները կորչում են՝

- Մեծացրեք `INSPECTOR_BUFFER_SIZE`-ը (օրինակ՝ 5000). սա մեծացնում է պահպանման տևողությունը՝ հիշողության ծախսի հաշվին
- Գրանցեք աշխատաշրջան՝ համապատասխան ժամանակահատվածը DB-ում պահպանելու համար
