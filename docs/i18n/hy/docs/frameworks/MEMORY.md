> **Ճշմարտության աղբյուր՝** `src/lib/memory/` և `src/app/api/memory/`
> **Վերջին թարմացումը՝** 2026-06-28 — v3.8.40 (լռելյայն անջատված + int8 քվանտացման լրացում)

OmniRoute-ը տրամադրում է մշտական խոսակցական հիշողություն, որը կապվում է API բանալուն (և
ըստ ցանկության՝ աշխատաշրջանի id-ին)։ Հիշողություններն ավտոմատ կերպով դուրս են բերվում LLM-ի պատասխաններից՝
թեթև regex ձևանմուշների համադրման միջոցով, և կրկին ներարկվում են հետագա
հարցումներում՝ որպես սկզբնական համակարգային հաղորդագրություն (կամ առաջին օգտատիրոջ հաղորդագրություն այն մատակարարների համար, որոնք
մերժում են համակարգային դերը)։

> **Հիշողությունը լռելյայն ԱՆՋԱՏՎԱԾ է (v3.8.30+)։** `DEFAULT_MEMORY_SETTINGS.enabled`-ն
> այժմ `false` է (`src/lib/memory/settings.ts`)։ Հիշողությունը միացնելիս ստացված համատեքստից մինչև
> `maxTokens` (~2k) ներարկվում է **յուրաքանչյուր** զրույցի հարցման մեջ, ինչը
> վճարովի է՝ անսպասելի ծախս նոր տեղադրումների և սեփական համատեքստը կառավարող
> հաճախորդների համար։ Հստակորեն միացրեք այն **Կարգավորումներ → Հիշողություն** բաժնում (
> `MemorySkillsTab`-ը ցուցադրում է թոքենների արժեքի մասին նախազգուշացում, երբ հիշողությունը միացված է)։
> Հաճախորդը կարող է անջատել այն մեկ հարցման համար՝ օգտագործելով `x-omniroute-no-memory`
> հարցման վերնագիրը (`true`/`1`/`yes`)․ տե՛ս հարցման վերնագրերի աղյուսակը
> [API_REFERENCE.md](../reference/API_REFERENCE.md)-ում։ Առանց հիշողության հարցումը
> սահմանում է `memoryOwnerId = null`, ինչը տվյալ հարցման համար անջատում է **թե՛** հիշողության, **թե՛** հմտությունների ներարկումը
> (`open-sse/handlers/chatCore/headers.ts::isNoMemoryRequested`)։

Հիշողությունը **տարանջատվում է ըստ API բանալու**, այլ ոչ թե ըստ օգտատիրոջ․ նույն API բանալիով նույնականացված
յուրաքանչյուր հարցում օգտագործում է հիշողությունների նույն շտեմարանը՝ ըստ ցանկության լրացուցիչ
տարանջատմամբ՝ `sessionId`-ի միջոցով։

## Ճարտարապետություն

```
Հաճախորդ → /v1/chat/completions (apiKeyInfo-ն որոշվում է վերին մակարդակում)
  → handleChatCore() [open-sse/handlers/chatCore.ts]
    → resolveMemoryOwnerId(apiKeyInfo)        # դուրս է բերում id-ն
    → getMemorySettings()                     # քեշավորված կարգավորումներ
    → shouldInjectMemory(body, {enabled})     # անցման պայման
    → retrieveMemories(apiKeyId, config)      # SQL + FTS5 + ըստ ցանկության՝ վեկտոր
    → injectMemory(body, memories, provider)  # համակարգային կամ օգտատիրոջ հաղորդագրություն
  → հարցում վերին մակարդակի մատակարարին
  → պատասխանից հետո՝ extractFacts(text, apiKeyId, sessionId)  # չարգելափակող
    → setImmediate → createMemory(fact) յուրաքանչյուր համընկնման համար
                   → embed(content) + upsertVector(id, vec)
```

Ներարկման և դուրսբերման կանչերի կետերը միացված են
`open-sse/handlers/chatCore.ts`-ում (փնտրեք `retrieveMemories`, `injectMemory`
և `extractFacts`)։

## Շարժիչի ճարտարապետություն (3-մակարդակ լուծում)

Memory Engine-ը կատարման պահին որոշում է որոնման ուղին՝ հասանելի
ենթակառուցվածքի և կարգավորումների հիման վրա։ Առկա է երեք մակարդակ, որոնք կիրառվում են ըստ առաջնահերթության՝

```
  ┌─────────────────────────────────────────────────────────────┐
  │  ՄԱԿԱՐԴԱԿ 0 — Հիմնաբառ (FTS5)                               │
  │  Հասանելիությունը որոշվում է ստուգմամբ․ FTS5, երբ SQLite-ի    │
  │  կառուցվածքն աջակցում է այն (better-sqlite3 / node:sqlite /  │
  │  bun:sqlite), հասանելի չէ առանց FTS5 կառուցվածքներում        │
  │  (օր.՝ sql.js/WASM — "no such module: fts5")։ Օգտագործվում է,│
  │  երբ strategy = "exact", կամ որպես պահուստային տարբերակ․     │
  │  engine-status-ի keyword-ը արտացոլում է ստուգման արդյունքը։ │
  └──────────────────────────────────┬──────────────────────────┘
                                     │ strategy = semantic|hybrid?
                                     ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  ՄԱԿԱՐԴԱԿ 1 — Ներկառուցված վեկտոր (sqlite-vec)              │
  │  sqlite-vec v0.1.9-ը բեռնվում է db.loadExtension()-ով։       │
  │  KNN ամբողջական որոնում Float32 վեկտորների վրա։ Ակտիվ է, երբ՝│
  │   • sqlite-vec loadExtension-ը հաջողվում է                   │
  │   • Հասանելի է ներդրման աղբյուր (remote | static |           │
  │     transformers), որը կարող է ստեղծել Float32Array          │
  │   • vec_memories աղյուսակը գոյություն ունի (ստեղծվում է      │
  │     առաջին ready()-ի ժամանակ)                               │
  └──────────────────────────────────┬──────────────────────────┘
                                     │ qdrant.enabled?
                                     ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  ՄԱԿԱՐԴԱԿ 2 — Qdrant (ըստ ցանկության արտաքին վեկտորային ԲՏ) │
  │  Միացված լինելու դեպքում semantic/hybrid-ի համար փոխարինում │
  │  է sqlite-vec-ին։ Պահանջում է աշխատող Qdrant օրինակ և        │
```

Ստորին մակարդակին անցումը կատարվում է ավտոմատ և աննկատ․

- Եթե sqlite-vec-ը չի բեռնվում, 1-ին մակարդակն անհասանելի է → համակարգն անցնում է 0-րդ մակարդակին։
- Եթե ներդրման աղբյուրը սխալ է վերադարձնում, 1-ին մակարդակն անցնում է 0-րդ մակարդակին։
- Եթե Qdrant-ը պատշաճ չի աշխատում, 2-րդ մակարդակն անցնում է 1-ին մակարդակին (կամ 0-րդ մակարդակին, եթե 1-ին մակարդակը
  նույնպես անհասանելի է)։

## Ներդրման աղբյուրներ

Ներդրման շերտը (`src/lib/memory/embedding/`) որոշում է, թե որ աղբյուրը պետք է օգտագործվի՝
հիմնվելով `MemorySettingsExtended.embeddingSource`-ի վրա.

| Աղբյուր        | Նկարագրություն                                                                            | Բանալին պարտադիր է | Սառը մեկնարկ     |
| -------------- | ----------------------------------------------------------------------------------------- | ------------------ | ---------------- |
| `remote`       | Օգտագործում է կազմաձևված մատակարարի ներդրման API-ն (OpenAI, Cohere և այլն)                | Այո                | Չկա              |
| `static`       | Տեղային որոնման աղյուսակով ներդրում՝ `potion-base-8M`-ի միջոցով (WordPiece + միջինացում)  | Ոչ                 | ~200ms           |
| `transformers` | Տեղային ONNX արտածում՝ `@huggingface/transformers` v4, `all-MiniLM-L6-v2` միջոցով         | Ոչ                 | ~3s + ~400MB RAM |
| `auto`         | Կատարման ժամանակի ընտրություն՝ remote (եթե բանալին առկա է) → static → transformers → null | Կախված է           | Կախված է         |

**`auto`-ի ընտրության հերթականությունը.**

1. Գտնել `listEmbeddingProviders()`-ի առաջին մատակարարին, որի համար `hasKey === true` է → `remote`.
2. Եթե `settings.staticEnabled === true` → `static`.
3. Եթե `settings.transformersEnabled === true` → `transformers`.
4. Հակառակ դեպքում → `null` (անցում է կատարվում FTS5 հիմնաբառային որոնման):

Ներդրման քեշը (`src/lib/memory/embedding/cache.ts`) օգտագործում է հիշողության մեջ պահվող
LRU քարտեզ՝ `${source}:${model}:${dim}:${sha256(text)}` բանալիով, առավելագույնը՝
`MEMORY_EMBEDDING_CACHE_MAX` գրառում (լռելյայն՝ 1000), և
`MEMORY_EMBEDDING_CACHE_TTL_MS` TTL-ով (լռելյայն՝ 5 րոպե): Այն համօգտագործվում է
բոլոր կանչողների միջև՝ յուրաքանչյուր գործընթացի կենսափուլի ընթացքում:

## Հիբրիդային RRF (k=60)

Երբ `strategy = "hybrid"` է, և վեկտորային պահոցը հասանելի է, առբերումը
օգտագործում է Reciprocal Rank Fusion՝ FTS5-ի և վեկտորային արդյունքները միավորելու համար.

```
RRF(d) = Σ  1 / (k + rank_i(d))      որտեղ k = 60 (կարգավորվում է MEMORY_RRF_K-ի միջոցով)
          i
```

Մասնավորապես.

1. Կատարել FTS5 որոնում → դասակարգված ցանկ `R_fts` (դիրքերը՝ 1..N):
2. Կատարել KNN վեկտորային որոնում → դասակարգված ցանկ `R_vec` (դիրքերը՝ 1..M):
3. Յուրաքանչյուր եզակի `memoryId`-ի համար՝  
   `rrf_score = 1/(60 + fts_rank)` + `1/(60 + vec_rank)` (0, եթե ցանկում չկա):
4. Դասավորել ըստ `rrf_score`-ի՝ նվազման կարգով, ապա կիրառել թոքենների բյուջեի հաջորդական շրջանցում:

Հայտնի է, որ RRF-ն արդյունավետ է՝ առանց տարասեռ որոնման համակարգերի միջև
գնահատականների նորմալացման անհրաժեշտության: Լռելյայն `k=60` արժեքը վերցված է
Cormack և այլոց սկզբնական հոդվածից և լավ է աշխատում փոքր կորպուսների համար (<10k հիշողություն):

## Հետլրացում (ծույլ + վերաինդեքսավորում)

Երբ ներդրման մոդելը փոխվում է (`embedding_signature`-ի միջոցով հայտնաբերված),
վեկտորային պահոցը վերակառուցվում է, իսկ առկա բոլոր հիշողությունները `memories`
աղյուսակում նշվում են `needs_reindex = 1` արժեքով:

**Ծույլ հետլրացում**. Հաջորդ առբերման ժամանակ վեկտորային գրառում չունեցող
ցանկացած հիշողություն ներդրվում և ավելացվում է `vec_memories`-ում՝ նախքան որոնման
մեկնարկը: Սա բաշխում է հետլրացման ծախսը իրական հարցումների միջև՝ առանց մեկնարկն
արգելափակելու:

**Բացահայտ վերաինդեքսավորում**. `/dashboard/memory`-ի Engine ներդիրում առկա է
«Վերաինդեքսավորել հիմա» կոճակ, որը կանչում է `POST /api/memory/reindex`:
Մշակիչը կանչում է `src/lib/memory/reindex.ts`-ի `runReindexBatch()`-ը, որը
յուրաքանչյուր հարցման ընթացքում մշակում է մինչև `limit` սպասող գրառում: Առաջընթացը
կարելի է պարբերաբար ստուգել `GET /api/memory/engine-status`-ի միջոցով
(`vectorStore.needsReindex`):

`memory_vec_meta` աղյուսակը (`083_memory_vec.sql` միգրացիա) պահպանում է.

- `active_dim` — վեկտորի ընթացիկ չափայնությունը (null = դեռ տրամաչափված չէ):
- `embedding_signature` — փոփոխությունները հայտնաբերելու համար օգտագործվող `${source}:${model}:${dim}`:
- `last_reset_at` — վերջին ամբողջական վերակայման ժամանակային դրոշմը:
- `vec_loaded` — 0/1 դրոշ, որը ցույց է տալիս՝ արդյոք sqlite-vec-ը հաջողությամբ բեռնվել է:

## Կարգավորումների ընդլայնում

Ներդրման և վեկտորային ինը դաշտ հասանելի է `MemorySettingsExtended`-ում՝
`src/shared/schemas/memory.ts` ֆայլում, և պահպանվում է `src/lib/db/settings.ts`-ի միջոցով․

| Դաշտ                     | Տեսակ                                              | Լռելյայն | Նկարագրություն                                                                      |
| ------------------------ | -------------------------------------------------- | -------- | ----------------------------------------------------------------------------------- |
| `embeddingSource`        | `"remote" \| "static" \| "transformers" \| "auto"` | `"auto"` | Օգտագործվող ներդրման աղբյուրը                                                       |
| `embeddingProviderModel` | `string \| null`                                   | `null`   | Մատակարար/մոդել՝ `provider/model` ձևաչափով                                          |
| `customBaseUrl`          | `string \| null`                                   | `null`   | Միայն հիշողության համար նախատեսված՝ OpenAI-ի հետ համատեղելի վերջնակետի հիմնական URL |
| `customModelId`          | `string \| null`                                   | `null`   | Հատուկ վերջնակետին ուղարկվող մոդելի ID                                              |
| `transformersEnabled`    | `boolean`                                          | `false`  | Transformers.js-ի օգտագործման համաձայնություն (MiniLM, ~400MB)                      |
| `staticEnabled`          | `boolean`                                          | `false`  | Տեղային ստատիկ potion-base-8M մոդելի օգտագործման համաձայնություն                    |
| `rerankEnabled`          | `boolean`                                          | `false`  | Միացնել վերադասավորման քայլը (ավելացնում է +200-500ms/req)                          |
| `rerankProviderModel`    | `string \| null`                                   | `null`   | Վերադասավորման մատակարար/մոդել՝ `provider/model` ձևաչափով                           |

`rerankProviderModel`-ը որոշվում է `POST /v1/rerank`-ի միջոցով (կանչվում է loopback կապով), ուստի այն ընդունում է այդ երթուղու կողմից ընդունվող ցանկացած արժեք՝ նախապես ընտրված ամպային վերադասավորման մոդել (`cohere/rerank-v3.5`, `jina-ai/jina-reranker-v3.5`, …) կամ OpenAI-ի հետ համատեղելի մատակարարի հանգույց՝ `<node-prefix>/<model>` ձևաչափով (օրինակ՝ `skilled-mini/bge-reranker-v2-m3`՝ TEI/Infinity սերվերի համար)։ Loopback հանգույցները միշտ հասանելի են․ այլ հոսթում գտնվող հանգույցի (LAN, Tailscale) համար լրացուցիչ պահանջվում է `RERANK_REMOTE_PROVIDER_NODES` գործառույթի դրոշակը, և այն պետք է համապատասխանի մատակարարի ելքային URL-ների քաղաքականությանը․ տե՛ս [Գործառույթի դրոշակներ](../reference/FEATURE_FLAGS.md)։ Կառավարման վահանակի ընտրիչը ցուցադրում է նախապես ընտրված մատակարարները և տեղային հանգույցները․ ցանկացած վավեր `provider/model` տող կարող է ուղղակիորեն սահմանվել `PUT /api/settings/memory`-ի միջոցով։
| `vectorStore` | `"sqlite-vec" \| "qdrant" \| "auto"` | `"auto"` | Օգտագործվող վեկտորային հետնամասը |

Դրանք հասանելի են `GET /PUT /api/settings/memory`-ի միջոցով (`MemorySettingsExtendedSchema` սխեմա)։

`remote` աղբյուրի համար Հիշողությունն ընդունում է նաև կամընտիր `customBaseUrl` և
`customModelId` կարգավորումները։ Դրանք միասին ընտրում են OpenAI-ի հետ համատեղելի `/embeddings`
վերջնակետն ու մոդելը՝ առանց ներդրումների համընդհանուր գրանցամատյանը փոխելու։ Օգտագործումից
առաջ վերջնակետը նորմալացվում և ստուգվում է մատակարարի ելքային URL-ների քաղաքականության համաձայն․
HTTP(S)-ը պարտադիր է, ներկառուցված նույնականացման տվյալներն ու հարցման տողերը մերժվում են,
իսկ ամպային մետատվյալների հասցեները շարունակում են արգելափակված մնալ։ Դատարկ արժեքները պահպանում
են գրանցամատյանի ընտրված մատակարարին։ Կառավարման վահանակին վերադարձվող սխալները մաքրվում են,
իսկ վերջնակետի նույնականացման տվյալները երբեք չեն գրանցվում մատյաններում։

> **ԱՆԵԼԻՔ (D20):** `global` ընդգրկույթը (հիշողությունների համօգտագործում բոլոր API բանալիների միջև)
> այս թողարկման մեջ իրականացված չէ։ Այն պահանջում է սխեմայի փոփոխություններ և համընդհանուր որոնման
> ուղի։ Հետևել առանձին։

## Պահպանման շերտեր

### Հիմնական՝ SQLite (`memories` աղյուսակ)

Ստեղծվում է `015_create_memories.sql` միգրացիայով.

| Սյունակ                     | Տիպ                | Նշումներ                                                                                 |
| --------------------------- | ------------------ | ---------------------------------------------------------------------------------------- |
| `id`                        | `TEXT PRIMARY KEY` | `crypto.randomUUID()`-ի միջոցով ստեղծվող UUID                                            |
| `api_key_id`                | `TEXT NOT NULL`    | Սեփականատեր API բանալին                                                                  |
| `session_id`                | `TEXT`             | Ըստ զրույցի կամընտիր տիրույթ                                                             |
| `type`                      | `TEXT NOT NULL`    | `factual`, `episodic`, `procedural`, `semantic` արժեքներից մեկը                          |
| `key`                       | `TEXT`             | Կայուն upsert բանալի, օրինակ՝ `preference:i_prefer_python`                               |
| `content`                   | `TEXT NOT NULL`    | Փաստի փաստացի տեքստը                                                                     |
| `metadata`                  | `TEXT`             | JSON բլոբ (`category`, `extractedAt`, `source`, ...)                                     |
| `created_at` / `updated_at` | `TEXT`             | ISO 8601 տողեր                                                                           |
| `expires_at`                | `TEXT`             | Կամընտիր ժամկետի ավարտ. `NULL`-ը նշանակում է մշտական                                     |
| `memory_id`                 | `INTEGER UNIQUE`   | Ավելացվել է `023_fix_memory_fts_uuid.sql`-ով՝ UUID-ները ↔ FTS5 rowid-ներին կապելու համար |

Ինդեքսներ՝ `api_key_id`, `session_id`, `type`, `expires_at`, ինչպես նաև եզակի
`memory_id` ինդեքսը։

**Upsert-ի իմաստաբանություն**. `createMemory()`-ն փնտրում է նույն
`(api_key_id, key)`-ով գոյություն ունեցող տող և գտնելու դեպքում այն թարմացնում է տեղում
(`metadata`-ն միավորելով մակերեսային տարածման միջոցով)։ Սա թույլ չի տալիս, որ կրկնվող
նախապատվության հայտարարությունների պատճառով աղյուսակն անսահման աճի։

### Լիատեքստային որոնում (`memory_fts` վիրտուալ աղյուսակ)

`022_add_memory_fts5.sql`-ը ստեղծում է FTS5 վիրտուալ աղյուսակ՝ `content` և
`key` դաշտերի համար։ `023_fix_memory_fts_uuid.sql`-ը շտկում է իրական օգտագործման ընթացքում
հանդիպած սխալը, որի պատճառով UUID հիմնական բանալին չէր միակցվում FTS5-ի ամբողջ թվային rowid-ին.
միգրացիան ավելացնում է `memory_id` սյունակը, վերստեղծում է FTS աղյուսակը և կապակցում
թրիգերներ (`memory_fts_ai`, `memory_fts_ad`, `memory_fts_au`), որոնք INSERT, DELETE և UPDATE
գործողությունների ժամանակ FTS-ը պահում են համաժամեցված վիճակում։

Օգտագործվում է `retrieval.ts`-ի կողմից՝ `semantic` և `hybrid` ռազմավարությունների համար
(տե՛ս ստորև)։ Որոնման կոդը ստուգում է `hasTable("memory_fts")`-ով և անցնում է
ժամանակագրական դասավորության, եթե FTS աղյուսակը բացակայում է կամ FTS հարցումը սխալ է վերադարձնում։

### Կամընտիր՝ Qdrant (վեկտորային պահոցի 2-րդ մակարդակ)

`src/lib/memory/qdrant.ts`-ն իրականացնում է Qdrant-ի կամընտիր ինտեգրում՝ որպես 2-րդ մակարդակի
վեկտորային պահոց։ Որոնումը դեպի Qdrant է ուղղվում միայն այն դեպքում, երբ շարժիչի ընտրիչը
`memoryVectorStore === "qdrant"` է. լռելյայն `"auto"`-ն (և `"sqlite-vec"`-ը)
**երբեք** չեն ընտրում Qdrant-ը։ Engine ներդիրի փոխարկիչը միասին սահմանում է **երկուսն էլ**՝
`qdrantEnabled` և `memoryVectorStore`. միացնելիս Qdrant-ը դառնում է հիմնական պահոցը, իսկ
անջատելիս արժեքը վերակայվում է `"auto"`-ի (#5597 — մինչ այդ շտկումը միացումն ազդեցություն
չուներ, քանի որ ոչինչ չէր գրանցում շարժիչի ընտրիչի արժեքը)։ Եթե Qdrant-ը անհասանելի է կամ
ոչինչ չի վերադարձնում, որոնումն անցնում է sqlite-vec → FTS5։

- `upsertSemanticMemoryPoint()` — ներկառուցում է `key + content`-ը կարգավորված
  ներկառուցման մոդելով, համոզվում է, որ հավաքածուն գոյություն ունի (առաջին
  օգտագործման ժամանակ ստեղծում է կոսինուսային հեռավորությամբ վեկտորներ), և
  ավելացնում կամ թարմացնում է կետը՝ `{memoryId,
apiKeyId, sessionId, key, content, metadata, createdAtUnix, expiresAtUnix}` բեռնվածքով։
- `searchSemanticMemory(query, topK, scope)` — ներկառուցում է հարցումը, որոնում
  հավաքածուում՝ զտելով ըստ `kind = "omniroute_memory"`-ի և, ըստ անհրաժեշտության,
  ըստ `apiKeyId` / `sessionId`-ի։ Սահմանափակում է `topK`-ն `[1, 20]` միջակայքով։
- `deleteSemanticMemoryPoint(id)` — մեկ կետի ջնջում։ Կանչվում է
  `deleteMemory()`-ի կողմից՝ SQLite-ի տողը հեռացնելուց հետո (D15)։
- `cleanupSemanticMemoryPoints({retentionDays})` — զանգվածաբար ջնջում է այն կետերը,
  որոնց `expiresAtUnix`-ն անցյալում է, կամ որոնց `createdAtUnix`-ը պահպանման
  սահմանային ամսաթվից հին է։ Նախ հաշվում է կետերը, որպեսզի վահանակը կարողանա
  ցուցադրել իրական թվերը։
- `checkQdrantHealth()` — `GET /readyz` առողջական վիճակի ստուգում՝ ուշացմամբ։

Կարգավորումների միջերեսը հասանելի է դարձնում Qdrant-ի կարգավորումը, առողջական
վիճակի ստուգումը, իմաստաբանական որոնման փորձարկումը և մաքրումը
`/dashboard/memory`-ի **Engine ներդիրում**։ `src/app/api/settings/qdrant/`-ի
համապատասխան երթուղիները լիովին միացված են՝ սկսած v3.8.6-ից․

| Երթուղի                                 | Մեթոդ         | Նկարագրություն                              |
| --------------------------------------- | ------------- | ------------------------------------------- |
| `/api/settings/qdrant`                  | `GET` / `PUT` | Կարդալ / թարմացնել Qdrant-ի կարգավորումները |
| `/api/settings/qdrant/health`           | `GET`         | Կենսունակության ստուգում + ուշացում         |
| `/api/settings/qdrant/search`           | `POST`        | Իմաստաբանական որոնման փորձարկում            |
| `/api/settings/qdrant/cleanup`          | `POST`        | Հեռացնել ժամկետանց / հին կետերը             |
| `/api/settings/qdrant/embedding-models` | `GET`         | Թվարկել հասանելի ներկառուցման մոդելները     |

**Վարքագծի նշումներ (ինչ ակնկալել).**

- **Շարժիչի ընտրություն** — Engine ներդիրում Qdrant-ը միացնելիս այն դառնում է
  հիմնական պահոցը (սահմանվում է `memoryVectorStore="qdrant"`), իսկ անջատելիս
  արժեքը վերակայվում է `"auto"`-ի (#5597)։
- **Հետադարձ լրացում չկա** — միայն Qdrant-ը միացնելուց **հետո** ստեղծված/թարմացված
  հիշողություններն են գրվում այնտեղ (չսպասող կրկնակի գրառում)։ Նախապես գոյություն
  ունեցող SQLite հիշողությունները **չեն** տեղափոխվում․ «Reindex Now»-ն վերակառուցում
  է միայն sqlite-vec ինդեքսը, ոչ թե Qdrant-ը։
- **Վեկտորի չափողականությունը ինքնաբերաբար է հայտնաբերվում** առաջին օգտագործման
  ժամանակ՝ ըստ փաստացի ներկառուցման․ լրացնելու համար չափողականության դաշտ չկա։
  Հավաքածուի ստեղծումից հետո ներկառուցման մոդելի փոփոխությունը ինքնաբերաբար
  **չի** մշակվում․ գոյություն ունեցող հավաքածուն մնում է անփոփոխ, չափողականությունների
  անհամապատասխանությամբ գրառումներն ու որոնումները ձախողվում են և հետ են անցնում
  sqlite-vec-ի։ Ներկառուցման այլ մոդելի անցնելու համար վերստեղծեք հավաքածուն
  (օգտագործեք նոր անուն կամ ջնջեք այն Qdrant-ում)։
- **Հեռավորության չափանիշ** — միշտ **Cosine** է (կոշտ կոդավորված է հավաքածուի
  ստեղծման ժամանակ և կարգավորելի չէ)։
- **Նույնականացում** — միայն API բանալի (ուղարկվում է որպես `api-key` վերնագիր․
  պարտադիր չէ նույնականացում չպահանջող տեղային Docker-ի համար)։ JWT/RBAC-ը չեն
  օգտագործվում։
- **Կարգավորման դաշտեր** — միջերեսը հասանելի է դարձնում `host`, `port`,
  `collection`, `embeddingModel`, `apiKey` դաշտերը։ `vectorSize` /
  `hnswEfConstruct`-ը հասանելի են միայն env/DB-ի միջոցով, իսկ `vectorSize`-ը չի
  օգտագործվում հավաքածու ստեղծելիս (չափողականությունը որոշվում է ներկառուցումից)։

### Վեկտորների քվանտացում (int8 — ընտրովի, երկու հետնամասերում)

Վեկտորային երկու հետնամասերն էլ աջակցում են **ընտրովի int8 քվանտացմանը**՝ պահվող
վեկտորների հիշողության ծավալը նվազեցնելու համար (Float32-ից մոտ 4× փոքր)՝
վերհիշման որակի փոքր կորստի գնով։ Երկուսում էլ լռելյայն **անջատված** է․ վեկտորները
պահպանում են ամբողջ ճշգրտությունը, եթե գործառույթը բացահայտորեն միացված չէ։

| Հետնամաս   | Կարգավորում                      | Տեսակ                          | Լռելյայն | Որտեղ է ընթերցվում                                          |
| ---------- | -------------------------------- | ------------------------------ | -------- | ----------------------------------------------------------- |
| Qdrant     | `qdrantQuantization` (DB բանալի) | `"none" \| "int8" \| "binary"` | `"none"` | `src/lib/memory/qdrant.ts::normalizeQdrantConfig()`         |
| sqlite-vec | `MEMORY_VEC_QUANTIZATION` (env)  | `"none" \| "int8"`             | `"none"` | `src/lib/memory/vectorStore.ts::requestedVecQuantization()` |

- **Qdrant**-ը կարգավորվում է յուրաքանչյուր օրինակի համար առանձին՝
  `qdrantQuantization` կարգավորման բանալու միջոցով (`PUT /api/settings/qdrant`-ում
  հասանելի է որպես `quantization` դաշտ)։ `"int8"` արժեքի դեպքում
  `buildQuantizationConfig()`-ը պահանջում է սկալյար քվանտացում (`always_ram`,
  քվանտիլ՝ `0.99`), իսկ որոնումները միացնում են `rescore: true`-ն, որպեսզի
  ամբողջական ճշգրտությամբ վեկտորները ճշգրտեն int8 թեկնածուների բազմությունը։
- **sqlite-vec**-ի քվանտացումը հասանելի է **միայն միջավայրի միջոցով** (DB
  կարգավորում չէ)․ սահմանեք `MEMORY_VEC_QUANTIZATION=int8`, որպեսզի տեղային
  վեկտորները պահվեն որպես `int8[dim]` սյունակ՝ `vec_quantize_int8(?, 'unit')`-ի
  միջոցով։ Ընտրված ռեժիմը ներառվում է `embedding_signature`-ում (`:int8`
  վերջածանցով), ուստի ռեժիմների փոփոխությունը գործարկում է `vec_memories`
  աղյուսակի ամբողջական վերաինդեքսավորում՝ նույն հետաձգված հետադարձ լրացման
  ուղիով, որն օգտագործվում է ներկառուցման մոդելը փոխելիս։

## Հիշողության տեսակներ

`MemoryType` (`src/lib/memory/types.ts`)՝

| Տեսակ        | Օգտագործվում է                                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------- |
| `factual`    | Նախապատվություններ, օգտատիրոջ կայուն փաստեր, վարքագծային օրինաչափություններ                     |
| `episodic`   | Որոշակի պահի հետ կապված որոշումներ («Ես ընտրեցի Postgres-ը»)                                    |
| `procedural` | Աշխատանքային հոսքի / կատարման եղանակի հիշողություն (վերապահված է․ ներկայում ինքնաարտահանիչ չկա) |
| `semantic`   | Վերապահված է վեկտորային պահոցի գրառումների համար                                                |

`MemoryConfig`-ի որոնման ռազմավարությունը `exact`, `semantic` կամ `hybrid`
տարբերակներից մեկն է, իսկ տիրույթը՝ `session`, `apiKey` կամ `global`
տարբերակներից մեկը։ `getMemorySettings()`-ից ստացվող լռելյայն տիրույթը
`apiKey` է։

## Փաստերի արտահանում (`extraction.ts`)

Արտահանումը հիմնված է **կանոնավոր արտահայտությունների վրա**, ոչ թե LLM-ի վրա․ այն կատարվում է պրոցեսի ներսում
`setImmediate()`-ի միջոցով, ուստի երբեք չի արգելափակում պատասխանի հոսքը՝

- **Նախապատվությունների օրինաչափություններ** → `MemoryType.FACTUAL`
  (օրինակ՝ `Ես նախընտրում եմ …`, `Ինձ իսկապես դուր է գալիս …`, `իմ սիրելին … է`, `Ես ատում եմ …`)
- **Որոշումների օրինաչափություններ** → `MemoryType.EPISODIC`
  (օրինակ՝ `Ես կօգտագործեմ …`, `Ես ընտրեցի …`, `Ես կանգ առա …-ի վրա`, `Ես պատրաստվում եմ ընդունել …`)
- **Վարքագծային օրինաչափություններ** → `MemoryType.FACTUAL`
  (օրինակ՝ `Ես սովորաբար …`, `Ես միշտ …`, `Ես հակված եմ …`)

Յուրաքանչյուր համընկնում մաքրվում է (`trim`, բացատների միավորում, առավելագույնը՝ 500 նիշ),
փաթեթի ներսում ապակրկնօրինակվում է կայուն `factKey(category, content)`-ի միջոցով և
պահվում `createMemory()`-ի միջոցով՝
`{category, extractedAt, source: "llm_response"}` մետատվյալներով։ Մուտքային տեքստը սահմանափակվում է
64 KiB-ով (`MAX_EXTRACTION_TEXT_LENGTH`)․ ավելի երկար լինելու դեպքում օգտագործվում է տեքստի **վերջնամասը**,
որպեսզի օգնականի ամենավերջին բովանդակությունը միշտ մասնակցի մշակմանը։

`extractFactsFromText(text)`-ը արտահանվում է թեստերի համար և վերադարձնում է կառուցվածքավորված
փաստերը՝ առանց դրանք պահելու։

## Առբերում (`retrieval.ts`)

`retrieveMemories(apiKeyId, config)`-ը հիմնական մուտքի կետն է։ Այն՝

1. Նորմալացնում և վավերացնում է կարգավորումները `MemoryConfigSchema`-ի միջոցով։
2. Անմիջապես վերադարձնում է `[]`, երբ `enabled`-ը false է կամ `maxTokens <= 0`։
3. Սահմանափակում է `maxTokens`-ը `[1, 8000]` միջակայքում։
4. Հայտնաբերում է՝ արդյոք առկա է ժամանակակից `memories` աղյուսակը (ժառանգական `memory`
   աղյուսակի փոխարեն), որպեսզի հին տվյալների բազաները շարունակեն աշխատել։
5. Կազմում է հիմնական հարցումը՝ ժամկետի ավարտի ստուգմամբ
   (`expires_at IS NULL OR datetime(expires_at) > datetime('now')`), ընտրովի
   նստաշրջանի տիրույթով և ընտրովի `retentionDays` սահմանաչափով։
6. Ճյուղավորվում է ըստ ռազմավարության՝
   - **`exact`** (լռելյայն)՝ ժամանակագրական `ORDER BY created_at DESC LIMIT 100`։
   - **`semantic`**՝ եթե առկա են `config.query`-ն և `memory_fts`-ը, կատարում է JOIN
     `memory_fts MATCH ?` և դասավորում ըստ FTS վարկանիշի․ վերադառնում է ժամանակագրական
     տարբերակին, երբ FTS-ը վերադարձնում է 0 տող։
   - **`hybrid`**՝ FTS արդյունքների (ավելի բարձր համապատասխանությամբ) և
     ժամանակագրական բազմության միավորում՝ ապակրկնօրինակված ըստ id-ի։
7. Հաշվարկում է հիմնաբառային համապատասխանության գնահատական (`getRelevanceScore`)՝
   `content`, `key` և `metadata` JSON դաշտերի հիման վրա, երբ հարցում է տրամադրված։ Զրոյական
   գնահատականով տողերը զտվում են։
8. Դասավորում է նախ ըստ գնահատականի՝ նվազման կարգով, ապա ըստ `createdAt`-ի՝ նվազման կարգով։
9. Անցնում է դասակարգված ցանկով և ընդունում գրառումները, քանի դեռ կուտակային
   `estimateTokens(content)`-ը (մոտավորապես `length / 4`) չի գերազանցում սահմանաչափը։ Եթե որևէ
   համընկնում կա, միշտ վերադարձնում է առնվազն մեկ գրառում։

`estimateTokens`-ը արտահանվում և օգտագործվում է առբերման, ամփոփման և MCP-ի
`omniroute_memory_search` գործիքի կողմից։

## Ներդրում (`injection.ts`)

`injectMemory(request, memories, provider)`՝

1. Միավորում է հիշողությունների ամբողջ բովանդակությունը մեկ `Memory context: …` տողի մեջ։
2. Ընտրում է ռազմավարություն՝ ըստ մատակարարի անվան.
   - **Համակարգային հաղորդագրություն** (կանխադրված՝ OpenAI-ի, Anthropic-ի, Gemini-ի և այլոց համար) — ավելացնում է
     `{role: "system", content: memoryText}`-ը գոյություն ունեցող բոլոր համակարգային
     հաղորդագրություններից առաջ, որպեսզի օգտատիրոջ համակարգային հուշումները շարունակեն գերակայություն ունենալ։
   - **Օգտատիրոջ հաղորդագրություն** (պահուստային տարբերակ) —
     `PROVIDERS_WITHOUT_SYSTEM_MESSAGE`-ում ներառված մատակարարների համար՝ `o1`, `o1-mini`, `o1-preview`,
     `glm`, `glmt`, `glm-cn`, `zai`, `qianfan`։ Սրանք մերժում են համակարգային դերը,
     և հակառակ դեպքում կվերադարձնեն 400 սխալ (տե՛ս GLM/Zhipu-ի վերաբերյալ խնդիր #1701-ը)։
3. Գրանցամատյանում `memory.injection.injected` անվան ներքո գրանցում է քանակը, ռազմավարությունը և մոդելը։

`providerSupportsSystemMessage(provider)`-ն արտահանվում է այն կանչողների համար, որոնց անհրաժեշտ է
ինքնուրույն երթուղավորման որոշումներ կայացնել։ Անհայտ մատակարարների համար անվտանգության նպատակով կանխադրված արժեքը `true` է
(համակարգային դերը թույլատրված է)։

## Կարգավորումներ (`settings.ts`)

Հիշողության կազմաձևումը **պահվում է ՏԲ-ի կարգավորումների աղյուսակում**, այլ ոչ թե միջավայրի փոփոխականներում։
`getMemorySettings()`-ը կարդում է `getSettings()`-ից և արդյունքը քեշավորում է
ընթացիկ պրոցեսում․ գրառումներից հետո կարգավորումների PUT
երթուղին կանչում է `invalidateMemorySettingsCache()`-ը։

## Ամփոփում (`summarization.ts`)

`summarizeMemories(apiKeyId, sessionId?, maxTokens = 4000)`-ը սեղմում է հին
բովանդակությունը, երբ որևէ բանալու հիշողությունների ընթացիկ թոքենների ընդհանուր
քանակը գերազանցում է սահմանված բյուջեն։ Այն տողերը շրջանցում է `created_at`-ի
նվազման կարգով, պահպանում է տեղավորվող տողերը, իսկ մնացածի `content`-ը տեղում
փոխարինում է բնօրինակի առաջին երեք նախադասություններով։ `tokensSaved`-ը հին և
նոր բովանդակության `estimateTokens` արժեքների տարբերությունն է։

Այս ընթացակարգը **հասանելի է, բայց ընթացիկ զրույցի մշակման շղթայում ինքնաշխատ
չի կանչվում**․ ընթացիկ սեղմումն ապահովելու համար այն կանչեք cron-ից,
ադմինիստրատորի գործողությունից կամ `MemoryConfig.autoSummarize` կապակցող
տրամաբանությունից։ Տվյալների կորուստն անշրջելի է․ բնօրինակ տեքստը վերագրվում է։

## REST API

Բոլոր վերջնակետերը պահանջում են կառավարման նույնականացում (`requireManagementAuth`)։

### Հիշողության հիմնական վերջնակետեր (գոյություն ունեցող + թարմացված)

| Մեթոդ    | Ուղի                 | Նկարագրություն                                                                                                                                                                                              |
| -------- | -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`    | `/api/memory`        | Էջակալված ցանկ՝ հետևյալ զտիչներով․ `apiKeyId`, `type`, `sessionId`, `q`, `limit`, `page`, `offset`։ Պատասխանը ներառում է `stats.total`, `stats.tokensUsed`, `stats.hitRate`, `cacheStats`                   |
| `POST`   | `/api/memory`        | Ստեղծում է գրառում (Zod-ով վավերացվող՝ `content`, `key`, ոչ պարտադիր՝ `type`, `sessionId`, `apiKeyId`, `metadata`, `expiresAt`)։ Կանչում է `createMemory()`-ն, որը կատարում է upsert՝ ըստ `(apiKeyId, key)` |
| `GET`    | `/api/memory/[id]`   | Ստանում է մեկ գրառում՝ ըստ UUID-ի                                                                                                                                                                           |
| `PUT`    | `/api/memory/[id]`   | Թարմացնում է գրառման դաշտերը (`type`, `key`, `content`, `metadata`)։ Մարմին՝ `MemoryUpdatePutSchema`։ Նաև համաժամացնում է վեկտորը, եթե հասանելի է embedding-ի աղբյուրը։                                     |
| `DELETE` | `/api/memory/[id]`   | Ջնջում է գրառումը, ինչպես նաև այն ջնջում է `vec_memories`-ից (D15) և հնարավորության սահմաններում՝ Qdrant-ից։ Բացակայության դեպքում վերադարձնում է 404։                                                      |

## MCP գործիքներ (`open-sse/mcp-server/tools/memoryTools.ts`)

Երբ MCP սերվերը միացված է, գրանցվում են հիշողության երեք գործիքներ.

- `omniroute_memory_search` — `{apiKeyId, query?, type?, maxTokens?, limit?}`
  → ներքին կանչով օգտագործում է `retrieveMemories()`-ը։ v3.8.6-ից (D16) սկսած՝ `strategy`-ն
  կարդացվում է `getMemorySettings()`-ից՝ `"exact"` արժեքով կոշտ կոդավորված լինելու
  փոխարեն։ Եթե տրամադրված է `query`, իսկ `strategy`-ն `semantic` կամ `hybrid` է,
  հասանելիության դեպքում օգտագործվում է վեկտորային պահոցը։
- `omniroute_memory_add` — `{apiKeyId, sessionId?, type, key, content,
metadata?}` → ներքին կանչով օգտագործում է `createMemory()`-ը։ Ընդունում է միայն 4 կանոնական տեսակները՝
  `factual`, `episodic`, `procedural`, `semantic` (D17)։
- `omniroute_memory_clear` — `{apiKeyId, type?, olderThan?}` → ցուցակագրում է համապատասխան
  գրառումները, ըստ ցանկության զտում է մինչև նշված ժամանակային դրոշմը ստեղծվածները, ապա յուրաքանչյուրը
  ջնջում է `deleteMemory()`-ի միջոցով (որը նաև հեռացնում է վեկտորները sqlite-vec-ից + Qdrant-ից)։

Փոխադրման և տեսանելիության տիրույթի մանրամասների համար տե՛ս [MCP-SERVER.md](./MCP-SERVER.md)։

## Կառավարման վահանակ (Memory Studio)

`src/app/(dashboard)/dashboard/memory/page.tsx`-ն այժմ **3 ներդիրով Studio** է.

### Ներդիր՝ Հիշողություններ

- Հայեցակարգի քարտ (ծալվող «Ինչպես է այն աշխատում» բացատրությամբ)։
- Իրական ժամանակում թարմացվող ցուցակ, որոնում և էջավորում (300 ms ուշացմամբ)։
- Տեսակի զտիչ (`factual` / `episodic` / `procedural` / `semantic` / բոլորը)։
- Հիշողություն ավելացնելու մոդալ պատուհան (բանալի, բովանդակություն, տեսակ)։
- Ներկառուցված խմբագրում (մատիտի կոճակ → `PUT /api/memory/[id]`)։
- Ջնջում յուրաքանչյուր տողի համար (հաստատման երկխոսության պատուհանով)։
- Ընթացիկ էջի JSON արտահանում, JSON ներմուծում՝ ֆայլի ընտրիչի միջոցով։
- Վիճակագրական քարտեր՝ `totalEntries`, `tokensUsed`, `hitRate`։
- «Սեղմել հները» կոճակ → `POST /api/memory/summarize` (նախ փորձնական գործարկումը
  ցույց է տալիս թեկնածուների քանակը, ապա պահանջում է հաստատում)։
- Կանաչ/կարմիր վիճակի ցուցիչ, որը կառավարվում է `GET /api/memory/health`-ի միջոցով։

### Ներդիր՝ Փորձադաշտ

- Հարցման մուտքագրում + ռազմավարության ընտրիչ (Ճշգրիտ / Իմաստային / Հիբրիդային) + թոքենների բյուջե։
- «Մոդելավորել» → `POST /api/memory/retrieve-preview` — ցուցադրում է դասակարգված արդյունքները՝
  `score`, `tier`, `tokens`, `vecScore`, `ftsScore` դաշտերով։
- Որոշման վահանակ, որը ցույց է տալիս, թե ներդրման որ աղբյուրը / վեկտորային պահոցն է օգտագործվել, և
  արդյոք տեղի է ունեցել պահուստային տարբերակի կիրառում։

### Ներդիր՝ Շարժիչ

- Շարժիչի վիճակի վահանակ (հիմնաբառային FTS5 նշապիտակ, ներդրման նշապիտակ, վեկտորային պահոցի նշապիտակ,
  Qdrant-ի վիճակի նշապիտակ, վերադասակարգման նշապիտակ)։
- «Վերաինդեքսավորել հիմա» կոճակ → `POST /api/memory/reindex`։
- Ներդրման աղբյուրի ընտրիչ (ավտոմատ / հեռակա / ստատիկ / տրանսֆորմերներ + փոխարկիչներ)։
- Qdrant-ի կազմաձևման քարտ (միացման փոխարկիչ, հոսթ/պորտ/հավաքածու/բանալի, կապի ստուգում,
  իմաստային որոնման ստուգում, մաքրում)։
- Վերադասակարգման կազմաձևման քարտ (միացման փոխարկիչ, մատակարարի/մոդելի ընտրիչ)։

Հիշողության և Qdrant-ի կարգավորումները հասանելի են նաև
`/dashboard/settings → Memory & Skills` (`MemorySkillsTab.tsx`) բաժնում՝
ժառանգական/գլոբալ կարգավորումների միջերեսի համար։

## Քեշավորում

`src/lib/memory/store.ts`-ը պահպանում է պրոցեսի ներսում գործող LRU-ին նման քեշ
(`MEMORY_CACHE_TTL = 1 min`, `MEMORY_MAX_CACHE_SIZE = 500`, ամենահին 20 %-ի
դուրսմղմամբ)՝ `getMemory(id)` ընթերցումների համար, ինչպես նաև ընդհանուր բանալի/արժեք
`memoryCache` շերտ (`src/lib/memory/cache.ts`)՝ `get`/`set`/`invalidate`
մեթոդներով, որն օգտագործվում է սեփական տեսանելիության տիրույթով քեշ ցանկացող կանչողների կողմից (1 000 գրառումով LRU,
լռելյայն TTL-ը՝ 5 min)։

## Գաղտնիություն և կյանքի ցիկլ

- Հիշողության սեփականատերը API բանալու նույնացուցիչն է (`resolveMemoryOwnerId`՝
  `chatCore.ts`-ում)։ Առանց `apiKeyInfo.id`-ի չեն կատարվում ո՛չ որոնումը, ո՛չ ներարկումը,
  ո՛չ էլ արտահանումը։
- Ապագա `expires_at` ունեցող գրառումները զտվում և չեն ներառվում որոնման արդյունքներում, իսկ
  `retentionDays`-ից ավելի հին գրառումները բացառվում են
  `retrieveMemories`-ի `created_at >= cutoff` պայմանի միջոցով։
- Վերջնական ջնջման համար օգտագործեք `DELETE /api/memory/[id]` կամ `omniroute_memory_clear`։
- Արտահանումը կատարվում է «գործարկել և չսպասել» սկզբունքով՝ `setImmediate`-ի միջոցով․ ձախողումները գրանցվում են
  `memory.extraction.background.failed` անվան տակ և երբեք չեն փոխանցվում կանչողին։
- Ստուգման ամբողջական ցիկլերը (`verifyExtractionPipeline`) մաքրում են իրենց սեփական
  թեստային գրառումները `finally` բլոկում։

## Ներդրման մատակարարի ընտրություն (v3.8.16+)

OmniRoute-ի հիշողության շարժիչն աջակցում է **ներդրման չորս աղբյուրի** (`src/lib/memory/embedding/`)։ Յուրաքանչյուրն ունի տարբեր փոխզիջումներ՝ կապված **ուշացման, արժեքի, մոդելի որակի և կարգավորման բարդության** հետ։

### Ներդրման աղբյուրները

| Մատակարար      | Աղբյուր                                                | Ուշացում                                                  | Արժեք               | Որակ                                         | Կարգավորում                         |
| -------------- | ------------------------------------------------------ | --------------------------------------------------------- | ------------------- | -------------------------------------------- | ----------------------------------- |
| `transformers` | Տեղային ONNX մոդել (Xenova/all-MiniLM-L6-v2)           | ~50-150ms (CPU)                                           | Անվճար              | Լավ                                          | Միայն `npm install`                 |
| `static`       | Նախապես հաշվարկված վեկտորներ (քեշավորված)              | <1ms                                                      | Անվճար              | Կիրառելի չէ (կախված է քեշում առկայությունից) | Չկա                                 |
| `remote`       | OpenAI / Cohere / Voyage API                           | ~100-300ms                                                | $0.02-0.10/1M թոքեն | Գերազանց                                     | API բանալի                          |
| `auto`         | Կատարման պահին ընտրում է լավագույն հասանելի աղբյուրը   | Նույնն է, ինչ ընտրված աղբյուրինը                          | Անվճար              | Նույնն է, ինչ ընտրված աղբյուրինը             | Չկա                                 |
| _(քեշ)_        | Հիշողության մեջ գտնվող LRU շերտ՝ ցանկացած աղբյուրի վրա | <1ms (առկայություն), ամբողջական ուշացում (բացակայություն) | Անվճար              | Նույնն է, ինչ հիմքում ընկած աղբյուրինը       | Միշտ միացված է (ընտրելի աղբյուր չէ) |

### Տվյալների բազայի և API-ի կազմաձևում

Հիշողության ներդրման ընտրանքները կազմաձևվում են Settings API/UI-ի միջոցով, այլ ոչ թե միջավայրի փոփոխականներով։ Settings-ում համապատասխան կարգավորումների տվյալների բազայի բանալիները (`normalizeMemorySettings`՝ `src/lib/memory/settings.ts`-ում) հետևյալն են․

- `memoryEmbeddingSource`: `"transformers"` (տեղային), `"remote"` (API-ի վրա հիմնված, օրինակ՝ OpenAI), `"static"` (արտաքին պահոց) կամ `"auto"`
- `memoryEmbeddingProviderModel`: Հեռավար/ստատիկ աղբյուրների մոդելի նույնացուցիչը (օրինակ՝ `"text-embedding-3-small"`)
- `memoryTransformersEnabled`: `true` | `false`
- `memoryStaticEnabled`: `true` | `false`
- `memoryVectorStore`: `"sqlite-vec"`, `"qdrant"` կամ `"auto"`

#### Տեղային մոդել (`transformers`)

Տեղային մոդելները գործարկելու համար ներքին մակարդակում օգտագործում է transformers.js․

```bash
# Կոդում ընթերցվող միջավայրի փոփոխականները (src/lib/memory/embedding/index.ts)․
MEMORY_TRANSFORMERS_MODEL=Xenova/all-MiniLM-L6-v2  # HF մոդելի պահոց
MEMORY_STATIC_MODEL=minishlab/potion-base-8M       # HF ստատիկ potion մոդել
MEMORY_STATIC_CACHE_DIR=<DATA_DIR>/embeddings      # Քեշի գրացուցակ
```

#### LRU ներդրման քեշ

Քեշը լռելյայն միշտ միացված է և կազմաձևվում է միջավայրի փոփոխականների միջոցով․

```bash
MEMORY_EMBEDDING_CACHE_MAX=1000                    # Քեշավորված տարրերի առավելագույն քանակը
MEMORY_EMBEDDING_CACHE_TTL_MS=300000               # TTL (5 րոպե)
```

## Փաստերի դուրսբերման ձևանմուշներ (v3.8.16+)

`extraction.ts` մոդուլը (`src/lib/memory/extraction.ts`) օգտագործում է **կանոնավոր արտահայտությունների ձևանմուշների համընկեցում**՝ զրույցի հաղորդագրություններից կառուցվածքային փաստեր դուրս բերելու համար։ Այս ձևանմուշները հասկանալն օգնում է հարմարեցնել դուրսբերման որակը ձեր օգտագործման դեպքին։

### Լռելյայն ձևանմուշների կատեգորիաներ

| Կատեգորիա           | Ձևանմուշի օրինակ                                                        | Դուրս է բերում                    |
| ------------------- | ----------------------------------------------------------------------- | --------------------------------- |
| PREFERENCE_PATTERNS | `"Ես նախընտրում եմ <X>"`, `"Ինձ դուր է գալիս <X>"`, `"Ես ատում եմ <X>"` | Օգտատիրոջ նախապատվությունները     |
| DECISION_PATTERNS   | `"Ես կօգտագործեմ <X>"`, `"Ես որոշեցի <X>"`, `"Ես ընտրեցի <X>"`          | Օգտատիրոջ որոշումները (դրվագային) |
| PATTERN_PATTERNS    | `"Ես սովորաբար <X>"`, `"Ես միշտ <X>"`, `"Ես երբեք <X>"`                 | Վարքագծի կայուն ձևանմուշները      |

### Ձևանմուշների օրինակներ (պարզեցված)

```ts
// src/lib/memory/extraction.ts-ից
const PREFERENCE_PATTERNS = [
  /\bI\s+(?:really\s+)?prefer\s+([^.,\n]+)/gi,
  /\bI\s+(?:really\s+)?like\s+([^.,\n]+)/gi,
  /\bI\s+(?:hate|dislike|avoid)\s+([^.,\n]+)/gi,
];
const DECISION_PATTERNS = [
  /\bI'?(?:ll|will)\s+use\s+([^.,\n]+)/gi,
  /\bI\s+(?:have\s+)?decided\s+(?:to\s+)?([^.,\n]+)/gi,
];
const PATTERN_PATTERNS = [/\bI\s+usually\s+([^.,\n]+)/gi, /\bI\s+always\s+([^.,\n]+)/gi];
```

### Ինչ է դուրս բերվում

Երբ օգտատերն ասում է․

> "Ես նախընտրում եմ TypeScript-ը։ Այս նախագծի համար կօգտագործեմ Postgres։ Ես միշտ commit եմ անում նախքան push անելը։ Ինձ դուր չի գալիս Python-ը։"
> Դուրսբերման արդյունքում ստեղծվում է 4 հիշողություն․
>
> | Բանալի                               | Կատեգորիա  | Տեսակ    | Բովանդակություն              |
> | ------------------------------------ | ---------- | -------- | ---------------------------- |
> | `preference:typescript`              | preference | factual  | "TypeScript"                 |
> | `decision:postgres_for_this_project` | decision   | episodic | "Postgres այս նախագծի համար" |
> | `pattern:commit_before_pushing`      | pattern    | factual  | "commit նախքան pushing-ը"    |
> | `preference:python`                  | preference | factual  | "Python"                     |

### Դուրսբերման սահմանափակումներ

Անվերահսկելի դուրսբերումը կանխելու համար կիրառվում են հետևյալ սահմանափակումները․

| Բովանդակության նվազագույն երկարություն | 3 նիշ |
| Բովանդակության առավելագույն երկարություն | 500 նիշ |

### Երբ անջատել դուրսբերումը

Դուրսբերումն ավտոմատ գործարկվում է ամեն անգամ, երբ հիշողությունը միացված է․ միայն
դուրսբերման համար առանձին փոխանջատիչ չկա։ Այն անջատելու համար ամբողջությամբ անջատեք հիշողությունը (`enabled: false`
արժեքով՝ `PUT /api/settings/memory`-ի միջոցով)։ Դիտարկեք դա անելու հնարավորությունը, երբ՝

- Հաղորդագրությունների ծավալը մեծ է, իսկ դուրսբերման ծախսը՝ ոչ աննշան
- Ձեր զրույցները հիմնականում ժամանակավոր են (զրույց, վրիպազերծում) և երկարաժամկետ արժեք չունեն
- Դուք արդեն պահպանում եք համատեքստը հատուկ հավելումների միջոցով

## Հիբրիդային RRF-ի կարգավորում (v3.8.16+)

**Reciprocal Rank Fusion (RRF)** ալգորիթմը համատեղում է FTS5-ի (հիմնաբառային) և վեկտորային (իմաստաբանական) արդյունքները։ `k` պարամետրը վերահսկում է, թե որքան կշիռ է տրվում ավելի ցածր դասակարգված արդյունքներին։

### Բանաձևը

Յուրաքանչյուր թեկնածու հիշողության համար RRF միավորը հետևյալն է․

```
RRF(d) = Σ  1 / (k + rank_i(d))
```

Որտեղ՝

- `k`-ն հաստատունն է (լռելյայն՝ 60)
- `rank_i(d)`-ն `d` փաստաթղթի դիրքն է i-րդ որոնման համակարգում (FTS, վեկտորային)
- Գումարումը կատարվում է բոլոր որոնման համակարգերով

### Ինչպես է `k`-ն ազդում արդյունքների վրա

| `k` արժեքը            | Ազդեցություն                                                                                            | Առավել հարմար է                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `k=0`                 | Դիրքերի զուտ միավորում (առանց հարթեցման)                                                                | Տեսական ելակետ                                          |
| `k=10-30`             | Մեծ կշիռ է տալիս լավագույն արդյունքներին, ցածր դիրքերը գրեթե չեն նպաստում                               | Երբ լավագույն 3 արդյունքները սովորաբար ճիշտ են          |
| **`k=60`** (լռելյայն) | Հավասարակշռված է՝ լավագույն 10 արդյունքներն էականորեն նպաստում են                                       | Ընդհանուր նշանակության որոնում                          |
| `k=100+`              | Ավելի հարթ է՝ նույնիսկ ցածր դիրքերով արդյունքները կարող են գերակշռել, եթե առկա են մի քանի համակարգերում | Երբ ամբողջականությունը > ճշգրտությունից և խիստ կարևոր է |

### `k`-ի կարգավորումը գործնականում

```bash
# Լռելյայն
MEMORY_RRF_K=60

# Ագրեսիվ ճշգրտություն (փոքր հիշողություն, քիչ փաստաթղթեր)
MEMORY_RRF_K=20

# Առավելագույն ամբողջականություն (մեծ հիշողություն, բազմազան հարցումներ)
MEMORY_RRF_K=120
```

**Օրինակ՝ `k=20`-ի դեպքում․**

- FTS դիրք 1 → ներդրում՝ `1/21 = 0.048`
- FTS դիրք 10 → ներդրում՝ `1/30 = 0.033`
- Վեկտորային դիրք 1 → ներդրում՝ `0.048`
- Համակցված առավելագույնը՝ `0.096`

**Օրինակ՝ `k=60`-ի դեպքում․**

- FTS դիրք 1 → ներդրում՝ `1/61 = 0.016`
- FTS դիրք 10 → ներդրում՝ `1/70 = 0.014`
- Վեկտորային դիրք 1 → ներդրում՝ `0.016`
- Համակցված առավելագույնը՝ `0.033`

Ավելի բարձր `k`-ի դեպքում լավագույն 1-ին և 10-րդ դիրքերի միջև **հարաբերական տարբերությունը** փոքրանում է, ուստի ալգորիթմն ավելի շատ է հիմնվում **որոնման համակարգերի միջև համաձայնության**, քան բարձր դիրքի նկատմամբ վստահության վրա։

### Երբ փոխել `k`-ն

| Ախտանիշ                                                            | Փորձեք                                                                                           |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| Լավագույն արդյունը միշտ հաղթում է, բայց սխալ է                     | **Նվազեցնել** k-ն (օրինակ՝ 20) — բարձր դիրքի նկատմամբ վստահությունն ավելի մեծ նշանակություն ունի |
| Ճիշտ պատասխանը լավագույն 5-ում է, բայց ոչ առաջին տեղում            | **Բարձրացնել** k-ն (օրինակ՝ 100) — ավելի հարթ գնահատումը խրախուսում է համաձայնությունը           |
| Ամբողջականությունը բարձր է, բայց ճշգրտությունը՝ ցածր               | **Նվազեցնել** k-ն՝ դասակարգումն ավելի հստակ դարձնելու համար                                      |
| Ամբողջականությունը ցածր է (համապատասխան փաստաթղթերը բացակայում են) | **Բարձրացնել** k-ն՝ ցածր դիրք ունեցող փաստաթղթերին հնարավորություն տալու համար                   |

### RRF-ի կշռում

Փոխադարձ դիրքերի միավորումն իմաստաբանական վեկտորային դիրքի և ամբողջական տեքստային որոնման դիրքի համար օգտագործում է հավասար կշիռներ․

```
RRF(d) = 1/(k + rank_vector) + 1/(k + rank_fts)
```

Առանձին կշիռները կարգավորելու համար միջավայրի փոփոխականներ չկան (`MEMORY_RRF_VECTOR_WEIGHT`/`MEMORY_RRF_FTS_WEIGHT` գոյություն չունեն)։

## Ամփոփման ռազմավարություն (v3.8.16+)

`summarization.ts` մոդուլը (`src/lib/memory/summarization.ts`) սեղմում է ավելի հին հիշողությունները՝ ակտիվ հավաքածուն փոքր պահելու և միաժամանակ վերհիշման հնարավորությունը պահպանելու համար։

### Երբ է գործարկվում ամփոփումը

| Գործարկիչ                | Շեմային արժեք (լռելյայն) |
| ------------------------ | ------------------------ |
| Ձեռքով գործարկում API-ով | կիրառելի չէ              |

### Ինչն է ամփոփվում

`summarization.ts`-ից արտահանվում են երկու մուտքային ֆունկցիաներ․

- **`summarizeMemories(apiKeyId, sessionId?, maxTokens = 4000)`** — սեղմում է
  աշխատաշրջանի հիշողությունները մեկ ամփոփ տեքստի մեջ՝ սահմանափակված թոքենների բյուջեով։
- **`summarizeMemoriesOlderThan(apiKeyId, days, dryRun)`** — API-ի կողմից
  օգտագործվող՝ տարիքի վրա հիմնված սեղմումը․ այն ընտրում է `days`-ից ավելի հին
  յուրաքանչյուր հիշողություն, դրանցից ստեղծում մեկ սեղմ ամփոփ հիշողություն և
  (երբ `dryRun`-ը `false` է) ջնջում բնօրինակները։ Փոխանցեք `dryRun: true`՝
  թեկնածուների հավաքածուն և թոքենների ընդհանուր քանակը նախադիտելու համար՝
  առանց որևէ բան փոփոխելու։

Չկա թեգերի/բանալիների խմբավորման փուլ կամ յուրաքանչյուր հիշողության համար «հիմնականն ընդդեմ ամփոփելիի» գնահատում․
ընտրությունը կատարվում է բացառապես տարիքային շեմով, իսկ ամփոփ տեքստը յուրաքանչյուր
թեկնածուի համար տեսակի նախածանցով սեղմ տող է։

### Ամփոփման գործարկում

Ամփոփումը **ձեռքով գործարկվող / ընտրովի** է․ `autoSummarize` կարգավորումը
լռելյայն `false` է, ուստի ոչինչ ինքնաբերաբար չի սեղմվում։ Գործարկեք այն API-ի միջոցով․

```bash
curl -X POST http://localhost:20128/api/memory/summarize \
  -H "Authorization: Bearer $OMNIROUTE_KEY"
```

Այն անջատված թողնելու համար պարզապես պահպանեք `autoSummarize`-ի լռելյայն արժեքը (`false`)։

### Ամփոփման որակի խորհուրդներ

- **Նախ նախադիտեք `dryRun`-ով**․ `summarizeMemoriesOlderThan(..., true)`-ը վերադարձնում է
  թեկնածուների ցանկը և թոքենների ընդհանուր քանակը, որպեսզի նախքան բնօրինակները ջնջելը
  կարողանաք հաստատել, թե ինչ է միավորվելու։
- **Ամփոփումը գործարկեք ցածր ծանրաբեռնվածության ժամերին**, եթե ունեք հիշողությունների մեծ շտեմարան․ LLM կանչը գործընթացի դանդաղ մասն է։

```bash
# Cron ոճով․ ամփոփել ամեն օր՝ ժամը 3-ին
0 3 * * * curl -X POST http://localhost:20128/api/memory/summarize \
  -H "Authorization: Bearer $OMNIROUTE_KEY"
```

## MemoryBackend մատակարարի օրինաչափություն

> **Ճշմարտության աղբյուր՝** `src/lib/memory/backend.ts`, `src/lib/memory/genericBackend.ts`, `src/lib/memory/manager.ts`
> **Թեստեր՝** `src/lib/memory/__tests__/generic-backend.test.ts`

MemoryBackend մատակարարի օրինաչափությունը գոյություն ունեցող հիշողության շարժիչի վրա ավելացնում է **փոխարինելի հետնամասի վերացարկման շերտ**։ Պահեստավորման մեկ իրականացումից կախված լինելու փոխարեն՝ հիշողության համակարգն այժմ աջակցում է մի քանի հետնամասերի (SQLite, Obsidian, Notion, հատուկ HTTP հետնամասեր)՝ կարգավորվող հիմնական/պահուստային երթուղավորմամբ։

### Ճարտարապետություն

```
┌──────────────────────────────────────────────────────────┐
│                    API երթուղիներ                         │
│            (src/app/api/memory/route.ts)                  │
└──────────────────────┬───────────────────────────────────┘
                       │
┌──────────────────────▼───────────────────────────────────┐
│                   MemoryManager                           │
│        Եզակի օրքեստրատոր (manager.ts)                    │
│                                                          │
│  Հիմնական ──► Հետնամաս A  (օր.՝ SQLite)                 │
│  Պահուստային ► Հետնամաս B  (օր.՝ Obsidian)              │
│                Հետնամաս C  (օր.՝ Notion՝ GenericBackend-ի միջոցով) │
└──────────────────────┬───────────────────────────────────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
┌────────────┐ ┌────────────┐ ┌──────────────────┐
│ SQLite     │ │ Obsidian   │ │ GenericMemory    │
│ հետնամաս   │ │ հետնամաս   │ │ հետնամաս (HTTP) │
└────────────┘ └────────────┘ └──────────────────┘
```

#### Հիմնական ինտերֆեյս (`backend.ts`)

Յուրաքանչյուր հետնամաս պետք է իրականացնի `MemoryBackend` ինտերֆեյսը․

```typescript
interface MemoryBackend {
  readonly id: string;
  readonly displayName: string;

  // CRUD
  create(input: CreateMemoryInput): Promise<Memory>;
  get(id: string): Promise<Memory | null>;
  update(id: string, updates: Partial<...>): Promise<boolean>;
  delete(id: string): Promise<boolean>;
  list(filter: MemoryFilter): Promise<{ data: Memory[]; total: number; byType: Record<string, number> }>;

  // Որոնում
  search(config: SearchConfig): Promise<Memory[]>;

  // Աշխատունակություն
  health(): Promise<HealthCheckResult>;

  // Կենսացիկլ (ընտրովի)
  initialize?(): Promise<void>;
  shutdown?(): Promise<void>;
}
```

#### MemoryManager (`manager.ts`)

Եզակի օրքեստրատոր, որը՝

- **Գրանցում է** հետնամասերը `register(backend)`-ի միջոցով․ կանչվում է գործարկման պահին `index.ts`-ից
- **Կարգավորում է** հիմնական և պահուստային հետնամասերը `configure(primary, fallbacks)`-ի միջոցով
- **Երթուղավորում է** CRUD/որոնման գործողությունները դեպի հիմնական հետնամաս՝ ձախողման դեպքում օգտագործելով պահուստային շղթան
- Պարբերաբար կատարում է բոլոր հետնամասերի **աշխատունակության ստուգումներ**

**Պահուստային վարքագիծ․**

| Գործողություն | Հիմնական                | Պահուստայիններ                        |
| ------------- | ----------------------- | ------------------------------------- |
| `create`      | ✅ Միայն հիմնականը      | ❌                                    |
| `get`         | ✅ Նախ փորձել հիմնականը | ✅ Պահուստայինը, եթե արդյունքը null է |
| `update`      | ✅ Միայն հիմնականը      | ✅ Չսպասող համաժամացում               |
| `delete`      | ✅ Միայն հիմնականը      | ✅ Չսպասող համաժամացում               |
| `list`        | ✅ Միայն հիմնականը      | ❌                                    |
| `search`      | ✅ Նախ հիմնականը        | ✅ Սխալի դեպքում՝ պահուստայինը        |

#### GenericMemoryBackend (`genericBackend.ts`)

Ընդհանուր HTTP կապակցիչ, որը ցանկացած REST API հարմարեցնում է MemoryBackend-ի։ Օգտակար է հետևյալի համար․

- **Notion** — միացում Notion API-ի միջոցով
- **Obsidian** — միացում Obsidian Local REST API-ի միջոցով
- **Հատուկ հետնամասեր** — RESTful հիշողության API տրամադրող ցանկացած ծառայություն

**Կազմաձևում․**

```typescript
interface GenericBackendConfig {
  baseUrl: string;           // Բեքենդի API-ի բազային URL-ը
  apiKey?: string;           // Bearer թոքեն՝ նույնականացման համար
  headers?: Record<string, string>;  // Հատուկ HTTP վերնագրեր
  timeout?: number;          // Հարցման սպասման առավելագույն ժամանակը (լռելյայն՝ 30000ms)
  backendType?: string;      // Լոգավորման համար

  // Վերջնակետերի վերասահմանումներ (լռելյայն արժեքները հետևում են REST սկզբունքներին)
  endpoints?: {
    search?: string;   // լռելյայն՝ "/memories/search"
    create?: string;   // լռելյայն՝ "/memories"
    list?: string;     // լռելյայն՝ "/memories"
    get?: string;      // լռելյայն՝ "/memories/{id}"
    update?: string;   // լռելյայն՝ "/memories/{id}"
    delete?: string;   // լռելյայն՝ "/memories/{id}"
    health?: string;   // լռելյայն՝ "/health"
  };

  // Հարցման պարամետրերի անունների համապատասխանեցումներ
  queryParams?: {
    query?/apiKeyId?/limit?/offset?/strategy?/maxTokens?/type?/sessionId?/orderBy?/orderDir?/options?
  };

  // Ուղու պարամետրերի անունների համապատասխանեցումներ
  pathParams?: {
    id?/memoryId?
  };
}
```

**Հայտնի բեքենդները** նախապես կարգավորված են `KNOWN_BACKENDS`-ում.

```typescript
createKnownBackend("obsidian"); // → GenericMemoryBackend՝ ուղղված localhost:27123-ին
createKnownBackend("notion"); // → GenericMemoryBackend՝ ուղղված api.notion.com/v1-ին
```

#### Ներկառուցված բեքենդներ

```typescript
import { sqliteBackend } from "./sqliteBackend";
memoryManager.register(sqliteBackend);
```

##### ObsidianBackend (`obsidianBackend.ts`)

Փաթաթում է գոյություն ունեցող Obsidian ինտեգրումը (`src/lib/memory/obsidianBackend.ts`)։ Միանում է Obsidian պահոցին Obsidian Local REST API-ի միջոցով։

### Կարգավորումներ

Հիշողության բեքենդի կարգավորումները պահվում են հավելվածի կարգավորումների աղյուսակում և կառավարվում `src/lib/memory/settings.ts`-ի միջոցով.

| Կարգավորում           | Միջավայրի/կազմաձևման բանալի | Լռելյայն   | Նկարագրություն                                    |
| --------------------- | --------------------------- | ---------- | ------------------------------------------------- |
| Հիմնական բեքենդ       | `memoryPrimaryBackend`      | `"sqlite"` | Հիմնական բեքենդի ID-ն                             |
| Պահուստային բեքենդներ | `memoryFallbackBackends`    | `[]`       | Պահուստային բեքենդների դասավորված ID-ներ          |
| Բեքենդի կազմաձևումներ | `memoryBackendConfigs`      | `{}`       | Յուրաքանչյուր բեքենդի կազմաձևման վերասահմանումներ |

Կարգավորումները նորմալացվում են `normalizeMemorySettings()`-ի միջոցով և քեշավորվում `getMemorySettings()`-ում։

### Նախնականացման հոսք

```
Հավելվածի սկզբնական բեռնում
  → index.ts ներմուծումներ (կողմնակի ազդեցությամբ). գրանցում է SQLiteBackend-ը
  → initMemoryBackends()-ը կանչվում է հավելվածի կենսացիկլից.
      1. Բեռնել կարգավորումները (getMemorySettings)
      2. Կարգավորել հիմնական + պահուստային բեքենդները
      3. Նախնականացնել բոլոր բեքենդները (առողջական վիճակի ստուգում)
      4. Պատրաստ է հարցումների համար
```

### Նոր բեքենդի ավելացում

1. **Իրագործեք `MemoryBackend`** ինտերֆեյսը `src/lib/memory/<name>Backend.ts`-ում
2. **Արտահանեք** `src/lib/memory/index.ts`-ից
3. **Գրանցեք** `memoryManager.register(yourBackend)`-ի միջոցով՝ մեկնարկի ժամանակ
4. **Կարգավորեք** կարգավորումների միջոցով՝ `memoryPrimaryBackend`-ը սահմանելով ձեր բեքենդի ID-ին
5. **Թեստավորեք**՝ որպես օրինակ օգտագործելով `src/lib/memory/__tests__/generic-backend.test.ts`-ը

#### Օրինակ՝ Brain բեքենդ

```typescript
import { createGenericMemoryBackend } from "./genericBackend";

const brainBackend = createGenericMemoryBackend("brain", "BK-Brain", {
  baseUrl: process.env.BRAIN_API_URL || "http://localhost:9099",
  apiKey: process.env.BRAIN_API_KEY,
  endpoints: {
    search: "/api/memory/search",
    create: "/api/memory",
    health: "/api/health",
  },
});

memoryManager.register(brainBackend);
```
