OmniRoute-ը տրամադրում է գնահատման ընդհանրական ֆրեյմվորք, որը կարող եք օգտագործել երթուղավորման կազմաձևերը, առանձին մատակարարները/մոդելները կամ փաթեթում ներառված «ոսկե հավաքածուի» փաթեթները չափորոշիչների հիման վրա գնահատելու համար։
Օգտագործեք այն՝ երթուղավորման փոփոխությունները ստուգելու, նոր մատակարարները վավերացնելու և թողարկումները վերահսկելու համար՝ նախքան դրանք արտադրական տրաֆիկում կիրառելը։

Ֆրեյմվորքն իրականացված է հետևյալ բաղադրիչներով՝

- Մաքուր գործարկիչ (`src/lib/evals/evalRunner.ts`), որը գրանցում է հիշողության մեջ պահվող
  ներկառուցված փաթեթները, գնահատում է արդյունքները՝ ըստ ակնկալվող չափանիշների, և համախմբում
  գնահատման քարտերը։
- Պահպանման շերտ (`src/lib/db/evals.ts`)՝ հատուկ (օգտատիրոջ կողմից սահմանված) փաթեթների
  և SQLite-ում պատմական գործարկումների համար։
- Կազմակերպման շերտ (`src/lib/evals/runtime.ts`), որը կատարում է յուրաքանչյուր դեպք՝
  իրական կանչեր ուղարկելով `POST /v1/chat/completions` հասցեին, գրանցում է ուշացումն
  ու արդյունքները և պահպանում գործարկումը։
- REST վերջնակետեր՝ `/api/evals/*`-ի ներքո (միայն կառավարման նույնականացմամբ)։
- Վահանակի բաժին՝ `Dashboard → Usage → Evals` հասցեում (`EvalsTab.tsx`)։

## Հասկացություններ

### Փաթեթ

Փաթեթը թեստային դեպքերի անվանված հավաքածու է՝ `description`-ով և մեկ կամ
մի քանի դեպքերով։ Փաթեթները ստացվում են երկու աղբյուրից՝

| Աղբյուր    | Որտեղ է սահմանված                                              | Փոփոխելի՞ է գործարկման ընթացքում |
| ---------- | -------------------------------------------------------------- | -------------------------------- |
| `built-in` | Մեկնարկի ժամանակ գրանցվում է `registerSuite()`-ի միջոցով       | Ոչ (սահմանված է կոդում)          |
| `custom`   | Պահվում է SQLite-ի `eval_suites` + `eval_cases` աղյուսակներում | Այո (API/UI-ի միջոցով)           |

Ընթացիկ ներկառուցված փաթեթները (տե՛ս `src/lib/evals/evalRunner.ts`)՝

- `golden-set` — 10 ելակետային դեպք՝ ողջույնի/մաթեմատիկայի/թարգմանության/անվտանգության ոլորտներում
- `coding-proficiency` — Python/JS/SQL/TS/սխալների հայտնաբերում
- `reasoning-logic` — սիլլոգիզմներ, տեքստային խնդիրներ, օրինաչափությունների ճանաչում
- `multilingual` — թարգմանություն և լեզվի հայտնաբերում
- `safety-guardrails` — PII, jailbreak, մերժում, կողմնակալության գիտակցում
- `instruction-following` — միայն JSON, համարակալված ցուցակներ, լեզվական սահմանափակումներ
- `codex-comparison` — դեմ առ դեմ համեմատման համար նախատեսված ծրագրավորման առաջադրանքներ

### Դեպք

Յուրաքանչյուր դեպք պարունակում է՝

| Դաշտ       | Նկարագրություն                                                                           |
| ---------- | ---------------------------------------------------------------------------------------- |
| `id`       | Կայուն նույնացուցիչ (օգտագործվում է արդյունքներն ու չափիչները բանալիներով կապելու համար) |
| `name`     | Մարդու համար ընթեռնելի պիտակ                                                             |
| `model`    | Լռելյայն մոդել, երբ գործարկումն օգտագործում է `suite-default` թիրախավորում               |
| `input`    | `{ messages, max_tokens? }` — ուղարկվում է `/v1/chat/completions` հասցեին                |
| `expected` | `{ strategy, value }` — գնահատման չափանիշ (տե՛ս ստորև)                                   |
| `tags`     | Ընտրովի պիտակներ (օրինակ՝ `safety`, `pii`, `jailbreak`)                                  |

### Թիրախ

Նույն փաթեթը կարող է գործարկվել տարբեր թիրախների նկատմամբ։ Թիրախի սխեման
`evalTargetSchema`-ն է՝ `src/shared/validation/schemas.ts`-ում՝

| Թիրախի տեսակ    | `id`            | Վարքագիծ                                                                                |
| --------------- | --------------- | --------------------------------------------------------------------------------------- |
| `suite-default` | `null`          | Յուրաքանչյուր դեպք օգտագործում է իր ներկառուցված `model` դաշտը                          |
| `model`         | մոդելի անուն    | Յուրաքանչյուր դեպք հարկադրաբար ուղղել մեկ անմիջական մոդելի միջոցով (օրինակ՝ `gpt-4o`)   |
| `combo`         | համակցման անուն | Յուրաքանչյուր դեպք գործարկել մեկ համակցման միջոցով (գործարկում է երթուղավորման շարժիչը) |

`model`-ի և `combo`-ի համար `id` դաշտը պարտադիր է (պարտադրվում է Zod-ի
`superRefine`-ով)։ Երբ տրամադրվում է `compareTarget`, երկու թիրախները պետք է տարբեր լինեն․
գործարկիչը երկու գործարկումներն էլ պահպանում է նույն `runGroupId`-ի ներքո՝ A/B համեմատության համար։

## Գնահատման չափանիշներ

Իրականացված է `evaluateCase()`-ում (evalRunner.ts)․

| Ռազմավարություն | Անցնում է, երբ…                                                                                     |
| --------------- | --------------------------------------------------------------------------------------------------- |
| `exact`         | `actualOutput === expected.value`                                                                   |
| `contains`      | `actualOutput.toLowerCase().includes(expected.value.toLowerCase())`                                 |
| `regex`         | `new RegExp(expected.value).test(actualOutput)`-ը ճշմարիտ է                                         |
| `custom`        | `expected.fn(actualOutput, evalCase)`-ը վերադարձնում է ճշմարիտ արժեք (միայն ներկառուցվածների համար) |

**Նշում․** Հատուկ ֆունկցիայով գնահատումը նախատեսված է կոդով սահմանված (ներկառուցված)
հավաքածուների համար, քանի որ ֆունկցիաները չեն կարող սերիալացվել API-ի միջոցով։
`evalCaseBuilderSchema`-ն օգտատերերի ստեղծած հավաքածուների համար ընդունում է միայն
`contains | exact | regex`։

Այս պահին չկա ո՛չ LLM-ը որպես դատավոր, ո՛չ էլ embedding-ի վրա հիմնված նմանության գնահատիչ․ դա
կարող է լինել `evaluateCase()`-ի ընդլայնման հարմար կետ։

## Տվյալների բազայի սխեմա

Երեք աղյուսակ (միգրացիաներ՝ `030_create_eval_runs.sql` և
`031_create_eval_suites.sql`)․

| Աղյուսակ      | Նպատակ                                                                                                                             |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `eval_suites` | Հատուկ հավաքածուի մետատվյալներ (`id`, `name`, `description`)                                                                       |
| `eval_cases`  | Յուրաքանչյուր հավաքածուի դեպքերը՝ `input_json`, `expected_*`, `tags_json`                                                          |
| `eval_runs`   | Պատմական գործարկումներ՝ `pass_rate`, `total`, `passed`, `failed`, `avg_latency_ms`, `summary_json`, `results_json`, `outputs_json` |

Ներկառուցված հավաքածուները **չեն** պահվում DB-ում։ Դրանք գտնվում են հիշողության մեջ և
վերագրանցվում են ամեն անգամ, երբ `evalRunner.ts`-ը ներմուծվում է։

## REST API

Բոլոր endpoint-ները պահանջում են կառավարման նույնականացում (`requireManagementAuth`)․ դրանք
հանրային proxy մակերեսի մաս չեն կազմում։

| Endpoint                      | Մեթոդ    | Նկարագրություն                                                                          |
| ----------------------------- | -------- | --------------------------------------------------------------------------------------- |
| `/api/evals`                  | `GET`    | Ցուցադրել հավաքածուները + վերջին գործարկումները + գնահատաթերթը + թիրախները + բանալիները |
| `/api/evals`                  | `POST`   | Գործարկել հավաքածու (առանձին կամ համեմատական)՝ `evalRunSuiteSchema` սխեմայով            |
| `/api/evals/{suiteId}`        | `GET`    | Ստանալ մեկ հավաքածու (ներկառուցված կամ հատուկ)                                          |
| `/api/evals/suites`           | `POST`   | Ստեղծել հատուկ հավաքածու՝ `evalSuiteSaveSchema` սխեմայով                                |
| `/api/evals/suites/{suiteId}` | `GET`    | Ստանալ հատուկ հավաքածու                                                                 |
| `/api/evals/suites/{suiteId}` | `PUT`    | Փոխարինել հատուկ հավաքածուն (դեպքերը կրկին զետեղվում են)                                |
| `/api/evals/suites/{suiteId}` | `DELETE` | Ջնջել հատուկ հավաքածուն և դրա դեպքերը                                                   |

### Հավաքածուի գործարկում

```bash
curl -X POST http://localhost:20128/api/evals \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "suiteId": "golden-set",
    "target": { "type": "combo", "id": "my-combo" },
    "apiKeyId": "optional-api-key-uuid"
  }'
```

Ընտրովի դաշտեր․

- `outputs` — նախապես հաշվարկված ելքերի `Record<caseId, string>`։ Տրամադրվելու դեպքում
  գործարկիչը **բաց է թողնում ուղարկումը** և միայն գնահատում է քեշավորված ելքերը (օգտակար է
  անցանց գնահատման համար)։
- `compareTarget` — զուգահեռ գործարկվող երկրորդ թիրախը․ երկու գործարկումներն էլ
  առերես համեմատական դիտման համար օգտագործում են ընդհանուր գեներացված `runGroupId`։
- `apiKeyId` — ներքին API բանալի, որն օգտագործվում է ուղարկված
  `/v1/chat/completions` կանչերը նույնականացնելու համար։ Պարտադիր է, երբ `REQUIRE_API_KEY`-ը միացված է։

### Հատուկ հավաքածուի ստեղծում

```bash
curl -X POST http://localhost:20128/api/evals/suites \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
```

## Ուղարկման կոնվեյեր

`runEvalSuiteAgainstTarget()` (`src/lib/evals/runtime.ts`)՝

1. Որոշում է թեստային փաթեթը (ներկառուցված կամ հատուկ)։
2. Յուրաքանչյուր դեպքի համար ստեղծում է `Request` դեպի `/v1/chat/completions`՝ դեպքի
   `messages`-ով, որոշված `model`-ով, `stream: false`-ով և `max_tokens: 512`-ով
   (կամ տվյալ դեպքի վերասահմանված արժեքով)։
3. Ուղղակիորեն կանչում է չատի մշակիչը (նույն գործընթացի ներսում՝ առանց լրացուցիչ HTTP անցման)։
4. Գրանցում է ուշացումը և արտածում տեքստը կա՛մ `choices[0].message.content`-ից,
   կա՛մ Responses-API-ի `output[]` բեռնվածքից։
5. Գնահատում է բոլոր ելքերը `runSuite()`-ի միջոցով, ապա պահպանում է `saveEvalRun()`-ի միջոցով։

Դեպքերը կատարվում են **հաջորդաբար**։ Ներկայում զուգահեռության դրոշակ չկա։

## Կառավարման վահանակ

UI-ը գտնվում է `Dashboard → Usage → Evals` բաժնում
(`src/app/(dashboard)/dashboard/usage/components/EvalsTab.tsx`)։ Այնտեղից կարող եք՝

- Դիտարկել ներկառուցված և հատուկ թեստային փաթեթները՝ յուրաքանչյուր դեպքի նախադիտմամբ։
- Դեպքերի կառուցչի միջոցով ստեղծել/խմբագրել/ջնջել հատուկ թեստային փաթեթներ։
- Ընտրել թիրախ (փաթեթի լռելյայն կարգավորումներ / մոդել / համակցություն), ըստ ցանկության՝ երկրորդ
  `compareTarget`, ըստ ցանկության՝ API բանալի, ապա գործարկել ըստ պահանջի։
- Ուսումնասիրել գործարկումների պատմությունը, յուրաքանչյուր դեպքի անցնել/ձախողել կարգավիճակը, ուշացումը և գրանցված ելքերը։
- Տեսնել ընթացիկ գնահատաթերթը՝ ագրեգացված յուրաքանչյուր
  `(suite, target)` շրջանակի վերջին գործարկման հիման վրա։

## Կապը Auto-Assessment RFC-ի հետ

Առանձին, ավելի նեղ գնահատման ենթահամակարգ է գտնվում `src/domain/assessment/`-ում
(գործող գնահատման շարժիչի համար տե՛ս նաև [AUTO-COMBO.md](../routing/AUTO-COMBO.md))։
Այդ ենթահամակարգը նախատեսված է Auto Combo շարժիչի համար՝ ավտոմատ կերպով գնահատելով մատակարարներին և
մոդելները, որպեսզի համակցությունները կարողանան ինքնավերականգնվել վերին մակարդակի ծառայությունների խափանման դեպքում։ Այն օգտագործում է իր սեփական գործարկիչը,
իր սեփական դասակարգիչը և իր սեփական գնահատման տրամաբանությունը։

Այստեղ փաստագրված Evals շրջանակը **ավելի լայն, ընդհանուր նշանակության
թեստավորման միջավայր է**։ Նախընտրեք այն կամայական ռեգրեսիոն փաթեթների, A/B համեմատությունների
և յուրաքանչյուր թողարկման արագ ստուգման թեստերի համար։ Օգտագործեք Auto-Assessment ենթահամակարգը, երբ անհրաժեշտ է,
որ մատակարարի իրական ժամանակի առողջական վիճակն ազդի երթուղավորման որոշումների վրա։

## CI ինտեգրում

Ներկայում առանձին `eval:ci` npm սկրիպտ չկա։ Գոյություն ունի երկու ուղի, եթե ցանկանում եք
թողարկումները պայմանավորել գնահատման արդյունքներով՝

- **HTTP ուղի**․ գործարկեք սերվերը, ուղարկեք հարցում `POST /api/evals` հասցեին՝ հայտնի
  `suiteId` + `target`-ով, և պատասխանում ստուգեք, որ `runs[].summary.passRate >= N`։
- **Ներքին գործընթացի ուղի**․ սկրիպտից ներմուծեք `runEvalSuiteAgainstTarget()`-ը
  `@/lib/evals/runtime`-ից, գործարկեք թեստային DB-ի նկատմամբ և ստուգեք վերադարձված
  `PersistedEvalRun.summary`-ն։

Երթուղին և պատմությունն ընդգրկող թեստերը գտնվում են
`tests/unit/evals-route.test.ts` և `tests/unit/evals-history.test.ts` ֆայլերում։

## Ընդլայնման կետեր

Տարածված փոփոխությունները և դրանց կատարման վայրերը՝

- **Գնահատման նոր ռազմավարություն** — ընդլայնեք `switch (evalCase.expected.strategy)`
  բլոկը `evaluateCase()`-ում (`evalRunner.ts`) և ընդլայնեք `EvalCaseStrategy`-ն
  `src/lib/db/evals.ts`-ում, ինչպես նաև `evalCaseBuilderSchema`-ն `schemas.ts`-ում։
- **Նոր ներկառուցված թեստային փաթեթ** — սահմանեք փաթեթի օբյեկտ և կանչեք `registerSuite()`-ը
  `evalRunner.ts`-ի վերջում։ Այն ավտոմատ կերպով կհայտնաբերվի `listSuites()`-ի միջոցով։
- **Զուգահեռ գործարկում** — փոխարինեք հաջորդական `for` ցիկլը
  `runEvalSuiteAgainstTarget()`-ում սահմանափակված `Promise.all`-ով (ներկայում
  զուգահեռության կառավարում չկա)։
- **Հոսքային/գործիքների կանչերով դեպքեր** — ներկայում գործարկիչը պարտադրում է `stream: false`։
  Հոսքային կամ գործիքների կանչերը հաշվի առնող գնահատումը կպահանջի փոփոխություններ `runtime.ts`-ում
  (գնահատումից առաջ որսալ և միավորել SSE հատվածները)։
