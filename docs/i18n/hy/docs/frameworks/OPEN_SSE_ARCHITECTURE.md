> **Կարճ ասած**․ `open-sse/`-ն հիմնական հոսքային շարժիչն է, որն ապահովում է OmniRoute-ի յուրաքանչյուր LLM հարցման աշխատանքը։ Այն պարունակում է մոտ 1,400 ֆայլ, որոնք իրականացնում են հարցումների մշակման շղթան, կատարիչները, ծառայությունները, MCP սերվերը և թարգմանության շերտը։ Այս ուղեցույցը բացատրում է, թե ինչպես են այս բաղադրիչները փոխկապակցվում։

**Աղբյուր՝** `open-sse/` (աշխատանքային տարածքի փաթեթ, մոտ 1,440 ոչ թեստային `.ts` ֆայլ)

---

## Ինչո՞ւ առանձին աշխատանքային տարածքի փաթեթ

`open-sse/`-ն OmniRoute մոնոռեպոզիտորի **ինքնուրույն աշխատանքային տարածք** է՝ մի քանի պատճառով․

1. **Վերօգտագործելիություն** — `open-sse`-ը npm-ում հրապարակվում է որպես `@omniroute/open-sse`, ուստի այլ նախագծեր կարող են այն օգտագործել անկախ կերպով
2. **Հստակ սահմաններ** — հոսքային շարժիչն առանձնացված է OmniRoute-ին հատուկ UI/DB շերտից
3. **Արտադրողականություն** — շարժիչը չունի Next.js կախվածություններ, ինչը CLI/սերվերազուրկ միջավայրերում ապահովում է ավելի արագ սառը մեկնարկ
4. **Տարբերակների կառավարում** — `open-sse`-ը կարող է թողարկումներ կատարել իր սեփական ժամանակացույցով

```json
// package.json
"workspaces": ["open-sse"]
```

```
├── executors/            # Յուրաքանչյուր մատակարարի HTTP կատարիչներ (67 + base.ts/index.ts)
```

## Հարցումների մշակման շղթան

Յուրաքանչյուր LLM հարցում անցնում է **5 փուլից բաղկացած մշակման շղթայով**․

```
                              ┌────────────────┐
   HTTP հարցում                │  1. ՈՒՂՂՈՐԴՈՒՄ │   combo-ի որոշում, մոդելի ընտրություն
   (Next.js երթուղի)           └───────┬────────┘
                                      │
                                      ▼
                              ┌────────────────┐
                              │  2. ԹԱՐԳՄԱՆՈՒՄ │   ձևաչափի փոխակերպում (OpenAI ↔ Claude ↔ Gemini)
                              └───────┬────────┘
                                      │
                                      ▼
                              ┌────────────────┐
                              │  3. ԿԱՏԱՐՈՒՄ   │   մատակարարի կատարիչ, HTTP, կրկնափորձ, անջատիչ
                              └───────┬────────┘
                                      │
                                      ▼
                              ┌────────────────┐
                              │  4. ՀՈՍՔ       │   SSE փոխակերպում, հակաճնշում
                              └───────┬────────┘
                                      │
                                      ▼
                              ┌────────────────┐
                              │  5. ԳՐԱՆՑՈՒՄ   │   օգտագործման հետևում, կանչերի մատյան, սխալների դասակարգում
                              └───────┬────────┘
                                      │
                                      ▼
                              HTTP պատասխան (SSE կամ JSON)
```

### Փուլ 1․ Ուղղորդում (services/combo.ts)

**Մուտքի կետ**՝ `handleComboChat()`՝ `services/combo.ts`-ում

Հարցումը համապատասխանեցնում է կոնկրետ `(provider, model, account, credentials)` բազմյակին․

- Գտնել combo-ն ըստ ID-ի (կամ կառուցել վիրտուալ combo՝ `auto/*` մոդելների համար)
- Կիրառել ուղղորդման ռազմավարությունը (առաջնահերթություն, կշռված, շրջանաձև և այլն)
- Բացառել անառողջ մատակարարներին (շղթայի անջատիչ)
- Ընտրել հաջորդ կենսունակ թիրախը

`auto/*` մոդելների դեպքում այս փուլը նաև՝

- Գործարկում է **16 գործոնով գնահատման** ալգորիթմը (`services/autoCombo/`)
- Ընտրում է `provider+model` զույգը՝ հիմնվելով հասանելիության, արժեքի, ուշացման և այլ գործոնների վրա

### Փուլ 2․ Թարգմանում (translator/)

Եթե սկզբնաղբյուր ձևաչափը (օրինակ՝ OpenAI) տարբերվում է նպատակային ձևաչափից (օրինակ՝ Claude), հարցումը **թարգմանվում է**․

- Համակարգային հուշում → համակարգային հաղորդագրություն
- Գործիքների սահմանումներ → մատակարարին հատուկ գործիքների ձևաչափ
- Դատողության/մտածողության պարամետրեր → մատակարարին հատուկ համարժեքներ
- Հաղորդագրությունների դերերի նորմալացում (`developer` → `system`՝ ոչ OpenAI մատակարարների համար)

`translator/index.ts`-ը տրամադրում է՝

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Փուլ 3․ Կատարում (executors/)

**Մուտքի կետ**՝ `getExecutor(providerId).execute(request, options)`

Բոլոր մատակարարներն օգտագործում են `DefaultExecutor`-ը (`executors/default.ts`)՝ `getExecutor()` գործարանի պահուստային տարբերակի միջոցով։ Կատարիչը՝

- Կառուցում է վերին հոսքի URL-ը (`buildUrl()`)
- Ավելացնում է մատակարարին հատուկ վերնագրեր (`buildHeaders()`)
- Փոխակերպում է հարցման մարմինը (`transformRequest()`)
- Ուղարկում է HTTP հարցումը՝ կրկնափորձով և էքսպոնենցիալ ուշացմամբ
- Անհրաժեշտության դեպքում կատարում է նույնականացման տվյալների թարմացում (OAuth մատակարարներ)

Բոլոր կատարիչներն ընդլայնում են `BaseExecutor`-ը (`executors/base.ts`, 1170 տող կոդ), որը տրամադրում է՝

- Կրկնափորձերի ընդհանուր տրամաբանություն
- Պրոքսիի ինտեգրում
- Շղթայի անջատիչի ինտեգրում
- Օգտագործման գրանցման հանգույցներ

### Փուլ 4․ Հոսք (utils/stream.ts)

Հոսքային պատասխանների դեպքում կատարիչը վերադարձնում է **ReadableStream**։ Մշակիչը՝

- Անցկացնում է այն SSE փոխակերպիչով (`createSSETransformStreamWithLogger`)
- Կիրառում է պարբերական ազդանշաններ՝ ընդհատված կապերը հայտնաբերելու համար
- Պատշաճ կերպով մշակում է հաճախորդի անջատումը (`pipeWithDisconnect`)
- Ոչ հոսքային հաճախորդների համար փոխակերպում է SSE → JSON

### chatCore.ts (5977 տող)

**Հարցումների հիմնական մշակիչը**։ Չնայած իր ծավալին՝ այն ունի հստակ կառուցվածք․

```ts
// chatCore.ts-ի կեղծ կառուցվածքը
export async function handleChat(request: NextRequest) {
  // 1. Նույնականացում + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Մարմնի վավերացում
  const body = await parseRequestBody(request);

  // 3. Ձևաչափի հայտնաբերում + փոխակերպում
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Կոմբոյի երթուղավորում
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Շարունակել հաջորդ թիրախով
    }
  }

  // 5. Արտակարգ պահուստային տարբերակ
  return await emergencyFallback(body);
}
```

### Երբ է կատարվում թարգմանությունը


Տարածված թարգմանություններ՝

- `OpenAI → Anthropic`՝ առանձին `system` դաշտ, `x-api-key` վերնագիր
- `OpenAI → Gemini`՝ `messages`-ի փոխարեն `contents`, `systemInstruction`
- `OpenAI → Responses API`՝ `input` զանգված, `previous_response_id` վիճակ

### Մշակվող սահմանային դեպքեր

- `developer` դեր → `system`՝ ոչ OpenAI մատակարարների համար
- `system` դեր → միավորվում է առաջին օգտատիրոջ հաղորդագրության հետ՝ GLM/ERNIE-ի համար
- `json_schema` → Gemini-ի `responseMimeType` + `responseSchema`
- `tools` → մատակարարին հատուկ գործիքի ձևաչափ
- Մտածողության պարամետրեր (o1, Claude) → մատակարարին հատուկ համարժեքներ

## MCP սերվեր

`open-sse/mcp-server/`-ն իրականացնում է **Model Context Protocol** սերվերը՝

- **110 գործիք** (մատակարարների կառավարում, համակցություններ, հիշողություն, քեշ, սեղմում, պրոքսի, հմտություններ, գեյմիֆիկացիա, փլագիններ, Notion, Obsidian, տեղային կորպուս)
- **3 փոխադրման եղանակ**՝ stdio, SSE, Streamable HTTP
- **33 տիրույթ**՝ մանրամասն թույլտվությունների կառավարման համար

### Գործիքների գրանցում

Գործիքները գրանցվում են որպես առանձին ֆայլեր `open-sse/mcp-server/tools/`-ում, որոնցից յուրաքանչյուրն արտահանում է անուն, սխեմա, մշակիչ և տիրույթ՝

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Ստանալ համակարգի առողջական վիճակի պատկերը",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Փոխադրման եղանակներ

```ts
// stdio (CLI-ի օգտագործում)
startMcpStdio(server);

// SSE (HTTP-ի վրա հիմնված հոսքային փոխանցում)
startMcpSse(server, port);

// Streamable HTTP (ժամանակակից MCP)
startMcpStreamable(server, port);
```

### Թույլտվությունների ստուգում

Գործիքի յուրաքանչյուր կանչ անցնում է տիրույթի ստուգումներ (`open-sse/mcp-server/auth/`)՝

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Անբավարար տիրույթ");
}
```

## Փոխակերպիչներ

`open-sse/transformer/`-ը փոխակերպում է **Chat Completions** և **Responses API** ձևաչափերի միջև։

### Ինչո՞ւ առանձին փոխակերպիչ

Responses API-ն OpenAI-ի նոր ձևաչափն է՝ **վիճակ պահպանող զրույցներով** (`previous_response_id`)։ Երբ հաճախորդն ուղարկում է Responses հարցում, OmniRoute-ը՝

1. Ներքին մակարդակում փոխակերպում է Responses → Chat Completions
2. Ուղարկում է մատակարարին (Chat Completions աջակցող ցանկացած մատակարարի)
3. Պատասխանը հետ է փոխակերպում Responses ձևաչափի
4. Փոխակերպված պատասխանը հոսքով փոխանցում է հաճախորդին

Փոխակերպիչը (`transformer/responsesTransformer.ts`) տրամադրում է՝

```ts
createResponsesApiTransformStream(): TransformStream
```

Այն մշակում է՝

- `response.output_item.added` իրադարձությունները
- `response.output_text.delta` իրադարձությունները
- `response.completed` իրադարձությունը
- Գործիքների կանչերի համապատասխանեցումը (`function_call` ↔ `tool_calls`)

## Կազմաձևում

`open-sse/config/`-ը պարունակում է կազմաձևման շերտը՝

| Ֆայլ                                 | Նպատակ                                                                |
| ------------------------------------ | --------------------------------------------------------------------- |
| `providerRegistry.ts`                | Զրույցի մոդելների ռեեստր՝ 352 մատակարարից բաղկացած կատալոգի հիման վրա |
| `providerModels.ts`                  | Մոդելների այլանուններ, ձևաչափերի համապատասխանեցում                    |
| `constants.ts`                       | Սպասման ժամանակներ, սահմանաչափեր, վիճակի կոդեր                        |
| `defaultThinkingSignature.ts`        | Claude-ի մտածողության լռելյայն ստորագրություն                         |
| `modelStrip.ts` (ծառայություններում) | Դաշտերի հեռացում՝ ըստ մատակարարի                                      |

### Մատակարարների ռեեստրի սխեմա

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Մոդուլի բեռնման ժամանակ Zod-ի վավերացումն ապահովում է, որ մատակարարների բոլոր կազմաձևերը վավեր են։

## Արտադրողականության սահմանափակումներ

Ուղղորդման շարժիչն ունի արտադրողականության խիստ սահմանաչափեր.

| Գործողություն                                 | Թիրախ | Չափում                           |
| --------------------------------------------- | ----- | -------------------------------- |
| Համակցությունների որոշում                     | <10ms | 50 թիրախի համար                  |
| Հաճախականության սահմանաչափի ստուգում          | <1ms  | Հիշողության մեջ token bucket     |
| Մոդելների ընտանիքի պահուստային ընտրություն    | <5ms  | Քեշավորված ընտանիքի սահմանումներ |
| Հարցման ուղղորդման փոխանցում                  | <2ms  | Թեժ ուղի                         |
| **Ուղղորդման թեժ ուղում արգելափակող I/O չկա** | —     | Ամբողջությամբ ասինխրոն           |

## Հակապատկերներ

❌ **Սինխրոն DB կանչեր `combo.ts`-ում** — նախապես հաշվարկեք և քեշավորեք
❌ **Կրկնափորձի տրամաբանություն մշակիչներում** — օգտագործեք դիմակայունության ծառայության `retry()`-ը
❌ **Մատակարարի կազմաձևին անմիջական հասանելիություն** — օգտագործեք `providerRegistry`-ի getter-ները
❌ **Կոշտ կոդավորված պահուստային շղթաներ** — սահմանեք `modelFamilyFallback.ts`-ում
❌ **Վիճակի փոփոխություններ զուգահեռ հարցումների միջև** — օգտագործեք միայն հարցման շրջանակով համատեքստ

## Նոր բաղադրիչի ավելացում

### Նոր ծառայության ավելացում

1. Ստեղծեք `open-sse/services/[serviceName].ts`՝ հստակ սահմանված պատասխանատվությամբ
2. Արտահանեք հիմնական մշակիչ ֆունկցիան և բոլոր հաստատունները
3. Ավելացրեք միավորային թեստեր `tests/unit/services/[serviceName].test.mjs`-ում
4. Ինտեգրեք հարցումների մշակման հոսքաշարին՝ `handlers/chatCore.ts`-ում (եթե կապված է ուղղորդման հետ)
5. Թարմացրեք ուղղորդման տրամաբանությունը `combo.ts`-ում, եթե ծառայությունն ազդում է թիրախի ընտրության վրա
6. Փաստաթղթավորեք այս ֆայլում

### Նոր կատարիչի ավելացում

1. Ստեղծեք `open-sse/executors/[provider].ts`, որը ընդլայնում է `BaseExecutor`-ը
2. Գրանցեք `config/providerRegistry.ts`-ում
3. Ավելացրեք `executors/index.ts` գործարանին
4. Ավելացրեք կատարիչի միավորային թեստեր
5. Փաստաթղթավորեք `docs/architecture/ARCHITECTURE.md`-ում

### Նոր MCP գործիքի ավելացում

1. Ստեղծեք կամ թարմացրեք `open-sse/mcp-server/tools/[category]Tools.ts`
2. Սահմանեք մուտքային տվյալների Zod սխեման
3. Գրանցեք գործիքը `mcp-server/index.ts`-ում
4. Ավելացրեք `mcp-server/auth/`-ի հասանելիության շրջանակների մատրիցում
5. Ավելացրեք միավորային թեստեր
