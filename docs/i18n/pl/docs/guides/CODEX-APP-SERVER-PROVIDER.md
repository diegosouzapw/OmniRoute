OmniRoute udostępnia **dwa** sposoby korzystania z OpenAI Codex:

| Dostawca               | Sposób komunikacji z OpenAI                                                                                                                                                                                                             | Zastrzeżenie dotyczące użytkowania                                                  |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| **`codex`**            | Przekazuje Twój token OAuth ChatGPT/OpenAI bezpośrednio do Responses API                                                                                                                                                                | **Tak** — oficjalna sesja nie jest autoryzowana do użycia przez serwer proxy/router |
| **`codex-app-server`** | Steruje **własnym procesem `codex app-server` narzędzia Codex CLI** przez JSON-RPC/WebSocket; CLI zarządza swoim uwierzytelnianiem OAuth i samodzielnie je odświeża (`~/.codex/auth.json`) dokładnie tak jak interaktywna sesja `codex` | **Nie** — OmniRoute nigdy nie przekazuje tokenu do API                              |

Ponieważ `codex-app-server` nigdy nie przekazuje tokenu, nie dotyczy go
zastrzeżenie związane z przekazywaniem sesji. Wymaga jednak, aby **Codex CLI był
dostępny pod skonfigurowanym adresem URL app-server**, a CLI musi być
**zalogowany**.

---

## 1. Architektura

```
┌─ Aplikacja OmniRoute ────────────┐        ┌─ Kontener pomocniczy codex-app-server ┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                     │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456           │
│  (+ token dostępu)               │  JSON  │  --ws-auth capability-token           │
│                                  │  RPC   │  samodzielnie zarządza OAuth OpenAI    │
└──────────────────────────────────┘        │  (~/.codex/auth.json, autom. odśwież.) │
        │ współdzieli (woluminy compose)     └────────────────────────────────────────┘
        ▼
  codex-appserver-token   → token dostępu WS (montowany przez oba kontenery)
  codex-appserver-home    → ~/.codex (auth.json zapisywany przez panel,
                             odczytywany przez codex app-server w kontenerze pomocniczym)
```

- Kontener pomocniczy nasłuchuje **wyłącznie** w wewnętrznej sieci compose
  (`ws://codex-app-server:1456`) i jest chroniony tokenem dostępu. **Nigdy** nie
  jest udostępniany hostowi ani w internecie.
- Codex CLI jest wbudowany w `omniroute:base`, więc podczas uruchamiania kontenera
  pomocniczego nie trzeba instalować codex na hoście ani na komputerze użytkownika.

## 2. Uruchomienie

```bash
# Uruchom stos Z profilem kontenera pomocniczego codex app-server:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

Przy pierwszym uruchomieniu kontener pomocniczy generuje swój token dostępu WS
(w udostępnionym woluminie `codex-appserver-token`), a aplikacja odczytuje ten
sam token za pośrednictwem `OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`. Nie jest
wymagana żadna ręczna konfiguracja tokenu.

## 3. Połączenie i logowanie

1. W panelu dodaj połączenie dla **OpenAI Codex (App-Server)**. Klucz API ani
   token nie są wymagane (jest to dostawca bez uwierzytelniania — uwierzytelnianiem
   zarządza kontener pomocniczy).
2. Jeśli Codex CLI w kontenerze pomocniczym **nie jest jeszcze zalogowany**,
   kontrola stanu połączenia zgłasza _„uruchomiony, ale niezalogowany”_ (zamiast
   czerwonego błędu uwierzytelniania). Użyj opcji **Zaloguj się przez ChatGPT**:
   spowoduje to uruchomienie standardowego uwierzytelniania OAuth urządzenia Codex
   w przeglądarce, a następnie zapisanie `~/.codex/auth.json` w udostępnionym
   woluminie za pomocą opcji **Zastosuj dane uwierzytelniające** (to samo
   logowanie obsługuje zarówno dostawcę `codex`, jak i `codex-app-server`).
3. Po zalogowaniu kontrola stanu zmienia kolor na zielony (weryfikuje zarówno
   `/readyz`, **jak i** `account/read`, czyli sprawdza, czy usługa działa
   _i_ jest uwierzytelniona), po czym zaczyna działać.

Panel nigdy nie nadpisuje prawidłowego istniejącego pliku
`~/.codex/auth.json` — zapisuje go tylko wtedy, gdy plik nie istnieje lub jego
token jest nieaktualny (zawsze tworzona jest kopia zapasowa).

## 4. Scenariusze wdrożenia

- **Operator z już uwierzytelnionym Codex CLI** — zamontuj katalog `~/.codex`
  hosta w kontenerze pomocniczym (`codex-appserver-home`) i pomiń etap logowania.
- **Użytkownik publiczny bez lokalnie zainstalowanego codex** — nie ma to
  znaczenia: kontener pomocniczy zawiera CLI. Użytkownik uwierzytelnia się
  wyłącznie przez panel.
- **OmniRoute na serwerze fizycznym (bez kontenera pomocniczego, codex na
  hoście)** — ustaw `OMNIROUTE_CODEX_APPSERVER_WS` na własny `codex app-server`
  i upewnij się, że codex na hoście jest zalogowany; jeśli brakuje pliku
  wykonywalnego, pojawi się wskazówka „codex nie jest zainstalowany”.

## 5. Wyjście przez sieć domową / UDP (rozszerzenie operatora, niedostarczane)

Opisany powyżej ogólny kontener pomocniczy kieruje ruch wychodzący przez zwykłą
sieć kontenera. Operator, który potrzebuje, aby ruch Codex wychodził przez
**łącze domowe** (np. kontener pomocniczy tailscale w trybie TUN, obsługujący
TCP + UDP/QUIC), uruchamia go za pomocą osobnego nadpisania compose; celowo
**nie** jest ono częścią dostarczanego profilu `codex-app-server`. Instrukcje
dotyczące tej konfiguracji znajdują się w wewnętrznym podręczniku operacyjnym.
