## Pipeline tłumaczeń (zalecany — v3.8.0)

OmniRoute używa inkrementalnego tłumacza dokumentów opartego na haszach, z backendem w postaci
endpointu LLM zgodnego z OpenAI (zwykle `cx/gpt-5.4-mini` przez OmniRoute
Cloud):

```bash
# Run translations (incremental — only touches changed sources)
npm run i18n:run

# Limit to one locale
npm run i18n:run -- --locale=pt-BR

# Specific files (comma-separated, repo-relative paths)
npm run i18n:run -- --files=CLAUDE.md,docs/architecture/ARCHITECTURE.md

# Force retranslate everything (expensive)
npm run i18n:run -- --force

# Preview what would happen (no API calls, no writes)
npm run i18n:run:dry

# CI gate — exits non-zero if state is drifting
npm run i18n:check
```

**Źródło prawdy.** `config/i18n.json` wymienia każdy locale (UI + docs) oraz
zestaw RTL i kody `docsExcluded`. Konfiguracja runtime w
`src/i18n/config.ts` to cienki adapter nad tym JSON-em.

**Backend.** Konfigurowany przez env (ustaw w `.env`, nigdy nie commituj):

| Zmienna                             | Przeznaczenie                          |
| ----------------------------------- | -------------------------------------- |
| `OMNIROUTE_TRANSLATION_API_URL`     | Bazowy URL zgodny z OpenAI, np. `…/v1` |
| `OMNIROUTE_TRANSLATION_API_KEY`     | token bearer (nie trafia do logów)     |
| `OMNIROUTE_TRANSLATION_MODEL`       | id modelu, np. `cx/gpt-5.4-mini`       |
| `OMNIROUTE_TRANSLATION_TIMEOUT_MS`  | opcjonalnie, domyślnie `60000`         |
| `OMNIROUTE_TRANSLATION_CONCURRENCY` | opcjonalnie, domyślnie `4`             |

**Śledzenie stanu.** `.i18n-state.json` (commitowany) trzyma hasze SHA-256 per
źródło + per locale. Wykrywanie dryfu jest automatyczne i deterministyczne — bez wywołań API
w `i18n:check`.

**Kształt wyjścia.** Każdy przetłumaczony plik dostaje nagłówek najwyższego poziomu `# <heading>
(<native>)`, pasek `🌐 Languages: …`, separator `---` oraz
przetłumaczoną treść. Ten układ jest zgodny z tym, co `scripts/check/check-docs-sync.mjs`
już wymusza dla luster `llm.txt` i `CHANGELOG.md`.

### Skrypty legacy (przestarzałe)

Starszy skrypt Python (`scripts/i18n/i18n_autotranslate.py`) oraz
generator oparty na Google Translate (`scripts/i18n/generate-multilang.mjs`)
nadal istnieją z banerem deprecacji. Zostaną usunięte w v3.10. Tryby
`messages` i `readme` w `generate-multilang.mjs` (stringi UI + warianty
README w root) nie są jeszcze obsługiwane przez nowy pipeline i nadal są używane.

## Architektura

![Inkrementalny pipeline i18n oparty na haszach](../diagrams/exported/i18n-flow.svg)

### Źródło prawdy

- **Stringi UI**: `src/i18n/messages/en.json` (źródło angielskie, ~2800 kluczy)
- **Pliki locale**: `src/i18n/messages/{locale}.json` (30 tłumaczeń)
- **Framework**: `next-intl` z resolucją locale na podstawie cookie
- **Config**: `src/i18n/config.ts` — definiuje wszystkie 30 locale, nazwy języków, flagi

### Przepływ runtime

1. Użytkownik wybiera język → ustawiane jest cookie `NEXT_LOCALE`
2. `src/i18n/request.ts` rozwiązuje locale: cookie → nagłówek `Accept-Language` → fallback `en`
3. Dynamiczny import ładuje `messages/{locale}.json`
4. Komponenty używają `useTranslations("namespace")` oraz `t("key")`

## Dodawanie nowego języka

### 1. Zarejestruj locale

Edytuj `src/i18n/config.ts`:

```ts
// Add to LOCALES array
"xx",
// Add to LANGUAGES array
{ code: "xx", label: "XX", name: "Language Name", flag: "🏳️" },
```

### 2. Dodaj do generatora

Edytuj `scripts/i18n/generate-multilang.mjs` — dodaj wpis do `LOCALE_SPECS`:

```js
{
  code: "xx",
  googleTl: "xx",
  label: "XX",
  flag: "🏳️",
  languageName: "Language Name",
  readmeName: "Language Name",
  docsName: "Language Name",
},
```

### 3. Wygeneruj początkowe tłumaczenie

```bash
node scripts/i18n/generate-multilang.mjs messages
```

Tworzy to `src/i18n/messages/xx.json` automatycznie przetłumaczone z `en.json` przez Google Translate.

### 4. Przejrzyj i popraw auto-tłumaczenia

Auto-tłumaczenia to punkt wyjścia. Przejrzyj ręcznie pod kątem:

- Poprawności technicznej
- Terminologii adekwatnej do kontekstu
- Poprawnej obsługi placeholderów (`{count}`, `{value}` itd.)

### 5. Walidacja

```bash
python3 scripts/i18n/validate_translation.py quick -l xx
python3 scripts/i18n/validate_translation.py diff common -l xx
```

### 6. Wygeneruj przetłumaczoną dokumentację

```bash
node scripts/i18n/generate-multilang.mjs docs
```

## Pipeline auto-tłumaczenia

### generate-multilang.mjs (Google Translate)

**Główny silnik auto-tłumaczenia** — używa darmowego API Google Translate do generowania tłumaczeń stringów UI, README i dokumentacji.

```bash
node scripts/i18n/generate-multilang.mjs [messages|readme|docs|all]
```

| Tryb       | Co robi                                                                          |
| ---------- | -------------------------------------------------------------------------------- |
| `messages` | Tłumaczy brakujące klucze w `src/i18n/messages/{locale}.json` z `en.json`        |
| `readme`   | Tłumaczy `README.md` na wszystkie locale jako `README.{code}.md` w root projektu |
| `docs`     | Tłumaczy `DOC_SOURCE_FILES` do `docs/i18n/{locale}/{docName}`                    |
| `all`      | Uruchamia wszystkie trzy tryby                                                   |

**Funkcje:**

- **Ochrona tekstu**: Maskuje bloki kodu (` ``` `), kod inline (`` ` ``), linki/obrazy markdown (`[text](url)`), tagi HTML, tabele oraz placeholdery ICU (`{count}`, `{value}`, `{total}` itd.) przed tłumaczeniem, a potem je przywraca
- **Batchowanie w chunkach**: Łączy wiele stringów delimiterami `__OMNIROUTE_I18N_SEPARATOR__`, aby zminimalizować wywołania API (max 1800 znaków na request)
- **Cache w pamięci**: Unika zbędnych wywołań API dla powtarzających się stringów w ramach sesji
- **Logika ponowień**: Exponential backoff (do 5 prób z opóźnieniem 300ms × numer próby) dla błędów 429/5xx
- **Timeout**: 20 sekund na request
- **Pomijanie istniejących**: Jeśli plik docelowy już istnieje, **nie** jest nadpisywany

**Ważne zachowania:**

- `docs/i18n/README.md` jest **regenerowany** przy każdym uruchomieniu — to auto-generowany indeks wszystkich docs
- Rootowe pliki `README.{code}.md` powstają tylko, jeśli nie istnieją (pomija locale z `EXISTING_README_CODES`)
- Paski językowe (`🌐 **Languages:** ...`) są automatycznie wstawiane/aktualizowane we wszystkich przetłumaczonych docs

### i18n_autotranslate.py (oparty na LLM)

**Drugi tłumacz** — używa dowolnego API LLM zgodnego z OpenAI (w tym samego OmniRoute) do tłumaczenia istniejących plików markdown w `docs/i18n/`. Najlepszy do dopracowania lub ponownego tłumaczenia docs z lepszą jakością niż Google Translate.

```bash
python3 scripts/i18n/i18n_autotranslate.py \
  --api-url http://localhost:20128/v1 \
  --api-key sk-your-key \
  --model gpt-4o
```

**Funkcje:**

- Skanuje pliki markdown w `docs/i18n/` w poszukiwaniu angielskich akapitów
- Pomija bloki kodu, tabele i już przetłumaczoną treść
- Wysyła akapity do LLM z system promptem do tłumaczenia technicznego
- Obsługuje wszystkie 43 języki

## CLI i18n

CLI `omniroute` ma własną warstwę i18n, oddzielną od dashboardu Next.js.

### Jak to działa

- Każdy string widoczny dla użytkownika w komendach CLI przechodzi przez `t("module.key", vars)` z `bin/cli/i18n.mjs`.
- Katalogi to pliki JSON w `bin/cli/locales/` — 43 dostarczane od razu.
- Locale spada do `en` dla każdego brakującego klucza, więc częściowe tłumaczenia są poprawne.
- Źródłem prawdy dla dostępnych locale jest `config/i18n.json` (współdzielone z dashboardem).

### Wybór locale

Kolejność detekcji (wygrywa pierwsze dopasowanie):

| Priorytet | Źródło                       | Przykład                                |
| --------- | ---------------------------- | --------------------------------------- |
| 1         | flaga `--lang`               | `omniroute --lang de status`            |
| 2         | zmienna env `OMNIROUTE_LANG` | `OMNIROUTE_LANG=ja omniroute providers` |
| 3         | systemowe env `LC_ALL`       | auto-wykrywane z locale terminala       |
| 4         | systemowe env `LC_MESSAGES`  | auto-wykrywane z locale terminala       |
| 5         | systemowe env `LANG`         | auto-wykrywane z locale terminala       |
| 6         | Fallback                     | `en`                                    |

Kody locale z podkreśleniami (`pt_BR`) są normalizowane do formy z myślnikiem (`pt-BR`).
Kody locale są walidowane względem `/^[a-zA-Z0-9-]+$/` — path traversal jest odrzucany.

### Zapisywanie preferencji językowej

```bash
# Set language and save to ~/.omniroute/.env (persists across sessions)
omniroute config lang set pt-BR

# View current language
omniroute config lang get

# List all 42 available languages
omniroute config lang list

# JSON output
omniroute config lang list --output json
```

Zapisana preferencja jest zapisywana atomowo do `~/.omniroute/.env` i ładowana przez
bootstrap CLI przed uruchomieniem dowolnej komendy.

### Jednorazowe nadpisanie

```bash
# Override for one command only (not persisted)
omniroute --lang de providers list
```

Uwaga: flaga `--lang` **nie** zapisuje do pliku env — wpływa tylko na bieżące
wywołanie. Użyj `config lang set`, aby utrwalić wybór.

### Dostępne locale

43 pliki locale są dostarczane w `bin/cli/locales/`. Pełne tłumaczenia: `en`, `pt-BR`.
Tylko scaffold (wszystkie klucze spadają do `en`): `bn`, `gu`, `he`, `in`, `mr`, `ms`, `phi`, `sw`, `ta`, `te`, `ur`.
Pozostałe 29 locale ma przetłumaczone klucze `common` + `program`.

### Dodawanie nowego locale CLI

1. Dodaj wpis locale do `config/i18n.json`.
2. Uruchom `node bin/cli/scripts/generate-locales.mjs` — tworzy plik locale.
3. Przetłumacz klucze (lub zostaw jako `{}` dla scaffoldu z fallbackiem do en).
4. PR-y muszą dodawać stringi do `en.json` i `pt-BR.json`; pozostałe pliki są best-effort.

## Walidacja i QA

### validate_translation.py

**Walidator tłumaczeń** — porównuje dowolny JSON locale z `en.json` i zgłasza problemy.

```bash
# Quick check (counts only)
python3 scripts/i18n/validate_translation.py quick -l cs
# Output:
# Missing: 0
# Untranslated: 0
# Ignored (UNTRANSLATABLE_KEYS): 236

# Detailed diff by category
python3 scripts/i18n/validate_translation.py diff common -l cs
python3 scripts/i18n/validate_translation.py diff settings -l cs

# Export to CSV
python3 scripts/i18n/validate_translation.py csv -l cs > report.csv

# Export to Markdown
python3 scripts/i18n/validate_translation.py md -l cs > report.md

# Full report (default)
python3 scripts/i18n/validate_translation.py -l cs
```

**Wykrywa:**

- **Brakujące klucze** — klucze w `en.json`, których nie ma w pliku locale
- **Dodatkowe klucze** — klucze w pliku locale, których nie ma w `en.json`
- **Nieprzetłumaczone klucze** — klucze, gdzie wartość locale równa się angielskiemu źródłu (z wyłączeniem allowlisty)
- **Niezgodności placeholderów** — placeholdery ICU, które nie pasują między źródłem a tłumaczeniem

**Kody wyjścia:**

| Kod | Znaczenie                                 |
| --- | ----------------------------------------- |
| 0   | OK                                        |
| 1   | Błąd ogólny                               |
| 2   | Brakujące stringi (błąd twardy)           |
| 3   | Ostrzeżenie o braku tłumaczenia (miękkie) |

**Środowisko:** Ustaw `TRANSLATION_LANG=cs` albo użyj flagi `-l cs`.

### check_translations.py

**Checker kluczy kod→JSON** — skanuje `src/**/*.tsx` i `src/**/*.ts` w poszukiwaniu wywołań `useTranslations()` i weryfikuje, że wszystkie referencjonowane klucze istnieją w `en.json`.

```bash
# Basic check
python3 scripts/i18n/check_translations.py

# Verbose output
python3 scripts/i18n/check_translations.py --verbose

# Auto-fix (adds missing keys to en.json)
python3 scripts/i18n/check_translations.py --fix
```

### generate-qa-checklist.mjs

**QA analizy statycznej** — skanuje pliki stron Next.js pod kątem metryk ryzyka i18n i generuje raport Markdown.

```bash
node scripts/i18n/generate-qa-checklist.mjs
```

**Sprawdza:**

- Użycie klas o stałej szerokości (ryzyko overflow)
- Kierunkowe klasy left/right (ryzyko RTL)
- Wzorce podatne na clipping
- Parzystość locale (brakujące/dodatkowe klucze vs `en.json`)
- Paski wyboru języka w README w priorytetowych locale (`es`, `fr`, `de`, `ja`, `ar`)

**Wyjście:** `docs/reports/i18n-qa-checklist-{date}.md`

### run-visual-qa.mjs

**Visual QA przez Playwright** — robi screenshoty wszystkich tras dashboardu w wielu locale i viewportach, a następnie ocenia kondycję strony.

```bash
# Default: es, fr, de, ja, ar, zh-CN on localhost:20128
node scripts/i18n/run-visual-qa.mjs

# Custom base URL and locales
QA_BASE_URL=http://staging.example.com QA_LOCALES=de,fr node scripts/i18n/run-visual-qa.mjs

# Custom routes
QA_ROUTES=/dashboard/settings,/dashboard/providers node scripts/i18n/run-visual-qa.mjs
```

**Wykrywa:**

- Overflow tekstu
- Clipping elementów
- Niezgodności layoutu RTL

**Wyjście:** `docs/reports/i18n-visual-qa-{date}.md` + raport JSON

## Zarządzanie kluczami nieprzetłumaczalnymi

### untranslatable-keys.json

**Plik:** `scripts/i18n/untranslatable-keys.json`

Allowlista kluczy, które powinny pozostać identyczne ze źródłem angielskim. Używana przez `validate_translation.py`, aby uniknąć fałszywie pozytywnych ostrzeżeń o „braku tłumaczenia”.

```json
{
  "description": "Keys that should remain untranslated...",
  "keys": [
    "common.model",
    "common.oauth",
    "health.cpu",
    ...
  ]
}
```

**Co tu należy:**

- Nazwy brandów/produktów: `landing.brandName`, `common.social-github`
- Terminy techniczne/akronimy: `health.cpu`, `mcpDashboard.pid`, `settings.ai`
- Stringi ICU/format: `apiManager.modelsCount`, `health.millisecondsShort`
- Wartości placeholderów: `providers.openaiBaseUrlPlaceholder`, `cliTools.baseUrlPlaceholder`
- Nazwy protokołów: `common.http`, `common.oauth`, `providers.oauth2Label`
- Sekcje nawigacji: `sidebar.primarySection`, `sidebar.cliSection`

**Aby dodać klucz:** Edytuj tablicę `keys` w `scripts/i18n/untranslatable-keys.json` i ponownie uruchom walidację.

## Słownik terminologii

Poza parzystością kluczy (`check-ui-keys-coverage.mjs`) i poprawnością ICU
(`validate_translation.py`) utrzymywana warstwa terminologii per-locale
wyłapuje dryf semantyczny, którego te dwie bramki nie widzą — np. ten sam
angielski koncept („provider”) oddany dwoma różnymi, równie poprawnymi
chińskimi słowami (提供商 vs 提供者) w tysiącach stringów. #8038 dodał
tę warstwę, zaczynając od zh-CN.

### scripts/i18n/glossary/\<locale\>.json

Wersjonowany słownik powtarzających się konceptów (provider, connection, routing,
fallback, quota, context window, reasoning, tool call, cache, circuit
breaker…) dla danego locale. Każdy koncept ma tłumaczenie `canonical` oraz
opcjonalną listę `synonyms` — każdy synonim znaleziony w katalogu jest flagowany jako
dryf. Koncept z pustą tablicą `synonyms` jest udokumentowany, ale jeszcze nie
egzekwowany (katalog nadal ma dla niego uzasadnione mieszane użycie; normalizacja
to follow-up, nie zadanie tej bramki).

`scripts/i18n/glossary/zh-CN.json` zasiewa dziesięć powyższych konceptów; `provider`
jest jedynym obecnie egzekwowanym, po jednorazowym
przejściu normalizacji 提供商→提供者 (analogicznie do przejścia zh-TW z #8024) w
`src/i18n/messages/zh-CN.json` i `bin/cli/locales/zh-CN.json`.

### scripts/i18n/glossary/protected-terms.json

Płaska lista nazw produktów/providerów/modeli/protokołów/CLI/env/identyfikatorów
(`OmniRoute`, `OAuth`, `MCP`, `A2A`, `DATA_DIR`, …), które muszą pojawiać się dosłownie
wewnątrz dowolnej przetłumaczonej wartości. To inna granularność niż
`untranslatable-keys.json` (który wyklucza całe KLUCZE z checków parity/ICU)
— chronione terminy są sprawdzane wszędzie, gdzie pojawią się w wartości,
kluczowane po koncepcie, a nie po ścieżce klucza.

### check-glossary-consistency.mjs

```bash
# zh-CN by default
npm run i18n:check-glossary

# explicit locale, JSON report, or non-failing report mode
node scripts/i18n/check-glossary-consistency.mjs --locale=zh-CN
node scripts/i18n/check-glossary-consistency.mjs --locale=zh-CN --json
node scripts/i18n/check-glossary-consistency.mjs --locale=zh-CN --report
```

Eksportuje czystą funkcję `checkGlossaryConsistency(localeMessages, glossary,
protectedTerms)` (analogicznie do `evaluateFileSizes` w
`check-file-size.mjs`) zwracającą `{ violations: [...] }` —
naruszenie `glossary-synonym` dla niekanonicznego terminu albo
naruszenie `protected-term-altered` dla błędnie przetłumaczonej chronionej nazwy.
Podpięte do CI jako job `i18n-glossary-zhcn` (ta sama bramka co
`i18n-ui-coverage`: pomija draft PR-y, uruchamia się przy zmianach i18n lub kodu).

## Dobre praktyki

### Przy edycji tłumaczeń

1. **Zawsze najpierw edytuj `en.json`** — to źródło prawdy
2. **Uruchom `generate-multilang.mjs messages`**, aby rozpropagować nowe klucze do wszystkich locale
3. **Przejrzyj auto-tłumaczenia** — Google Translate to punkt wyjścia, nie wersja finalna
4. **Waliduj przed commitem** — `python3 scripts/i18n/validate_translation.py quick -l <lang>`
5. **Zaktualizuj `untranslatable-keys.json`**, jeśli klucz powinien pozostać po angielsku

### Bezpieczeństwo placeholderów

- Placeholdery ICU (`{count}`, `{value}`, `{total}`, `{seconds}`) muszą być zachowane dokładnie
- Formaty plural (`{count, plural, one {# model} other {# models}}`) muszą zachować strukturę
- Walidator automatycznie wykrywa niezgodności placeholderów

### Dodawanie nowych kluczy tłumaczeń w kodzie

```tsx
// Use namespaced keys
const t = useTranslations("settings");
t("cacheSettings"); // maps to settings.cacheSettings in JSON

// Run check_translations.py to verify keys exist
python3 scripts/i18n/check_translations.py --verbose
```

### Uwagi dotyczące RTL

- Arabski (`ar`) i hebrajski (`he`) to locale RTL
- Unikaj hardcodowanego CSS `left`/`right` — używaj logicznych właściwości `start`/`end`
- Visual QA wyłapuje niezgodności layoutu RTL przez `run-visual-qa.mjs`

## Znane problemy i historia

### Poprawka `in.json` → `hi.json`

Generator pierwotnie używał `code: "in"` (przestarzały kod Google Translate) dla hindi zamiast poprawnego ISO 639-1 `hi`. To utworzyło osierocony duplikat `in.json` względem `hi.json`. Naprawione przez zmianę `code: "in"` na `code: "hi"` w `generate-multilang.mjs` i usunięcie osieroconego pliku.

> ⚠️ **Audyt (2026-05-13):** Katalog `docs/i18n/in/` nadal istnieje na dysku (pełny duplikat `hi/`). Generator tłumaczeń już do niego nie zapisuje, ale historyczne drzewo nie zostało usunięte. Bezpiecznie usunąć przez `rm -rf docs/i18n/in/` po potwierdzeniu, że żadne zewnętrzne linki nie wskazują starej ścieżki.

### `docs/i18n/README.md` jest auto-generowany

Plik `docs/i18n/README.md` jest w całości regenerowany przez `generate-multilang.mjs docs`. Wszelkie ręczne edycje zostaną utracone. Używaj `docs/guides/I18N.md` (ten plik) do ręcznie pisanej dokumentacji, która ma pozostać.

### Zewnętrzna lista kluczy nieprzetłumaczalnych

Allowlista `untranslatable-keys.json` została przeniesiona z wbudowanego zbioru Pythona w `validate_translation.py` do zewnętrznego pliku JSON dla łatwiejszej utrzymywalności. Walidator ładuje ją w runtime.

### Poprawka kodu hindi w `generate-multilang.mjs`

Generator pierwotnie używał `code: "in"` (przestarzały kod Google Translate) dla hindi zamiast poprawnego ISO 639-1 `hi`. Wprowadzone w upstreamowym commicie `952b0b22c` przez `diegosouzapw`. Naprawione przez zmianę `code: "in"` na `code: "hi"` w tablicy `LOCALE_SPECS` i usunięcie osieroconego pliku `in.json`.

### Wyjście zliczania ignorowanych w `validate_translation.py`

Check `quick` wyświetla teraz liczbę ignorowanych kluczy z `untranslatable-keys.json`:

```
Missing: 0
Untranslated: 0
Ignored (UNTRANSLATABLE_KEYS): <varies per release>
```
