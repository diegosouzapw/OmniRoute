## Szybka ściągawka

**Zaczynasz korzystać z OmniRoute?** Zacznij tutaj — te rozwiązania usuwają 90% problemów:

| Widzę ten komunikat     | Co to oznacza                       | Co zrobić                                                                                              |
| ----------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------ |
| "Can't connect"         | OmniRoute nie jest uruchomiony      | Uruchom `omniroute` lub `docker restart omniroute`                                                     |
| "Invalid API key"       | Klucz jest nieprawidłowy lub wygasł | Ponownie skopiuj klucz ze strony dostawcy                                                              |
| "Rate limit exceeded"   | Wysyłasz zbyt wiele żądań           | Poczekaj 1 minutę lub użyj `model: "auto"`, aby automatycznie przełączyć się na inną opcję             |
| "Quota exceeded"        | Wykorzystano bezpłatny/płatny limit | Połącz więcej dostawców lub użyj bezpłatnych dostawców (Kiro, Pollinations)                            |
| "Slow responses"        | Dostawca jest zajęty lub odległy    | Użyj `model: "auto/fast"` lub połącz szybszego dostawcę (Groq, Cerebras)                               |
| "Wrong provider used"   | `auto` wybrało innego dostawcę      | To normalne! `auto` wybiera najlepszego. Wymuś konkretnego dostawcę za pomocą `model: "openai/gpt-4o"` |
| "502 Bad Gateway"       | Dostawca nie działa                 | Poczekaj i spróbuj ponownie lub użyj `model: "auto"`, aby przełączyć dostawcę                          |
| "401 Unauthorized"      | Dane uwierzytelniające są błędne    | Sprawdź klucz API lub ponownie uwierzytelnij się za pomocą OAuth                                       |
| "429 Too Many Requests" | Osiągnięto limit liczby żądań       | Poczekaj 1 minutę lub połącz więcej dostawców                                                          |

**Problem nadal występuje?** Zapoznaj się ze [szczegółowym rozwiązywaniem problemów](#szczegółowe-rozwiązywanie-problemów) poniżej lub zapytaj na [Discordzie](https://discord.gg/U47eFqAXCn).

## Szczegółowe rozwiązywanie problemów

---

### Ograniczanie liczby żądań u bezpłatnych dostawców (429 / 400 / 401)

**Objaw**: Podczas korzystania z `model: "auto"` z bezpłatnymi dostawcami lub dostawcami niewymagającymi uwierzytelnienia (opencode, auggie itp.) sporadycznie otrzymujesz `HTTP 429`, `400` lub `401` zamiast odpowiedzi. Żądania kończą się powodzeniem po ponowieniu tego samego promptu chwilę później, ale automatyzacja (zadania cron, agenci, skrypty) przestaje działać po pierwszym błędzie.

**Główna przyczyna**: Nakładają się na siebie trzy niezależne tryby awarii:

1. **Limit żądań dostawcy (`429`)**: Bezpłatne plany mogą narzucać limit na określone okno czasowe. Seria równoległych wywołań wyczerpuje limit, dlatego kolejne żądanie jest odrzucane do czasu zresetowania okna.
2. **Niedziałający model w trybie passthrough (`400`/`401`)**: Pule `auto/*` mogą obejmować modele passthrough z `opencode`, które są zarejestrowane w katalogu, ale nie mają aktywnych danych uwierzytelniających (np. `oc/north-mini-code-free` → `401`). Automatyczny router próbuje użyć jednego z nich, próba kończy się niepowodzeniem, a błąd jest propagowany, zanim mechanizm przełączania awaryjnego zacznie działać.
3. **Wzmocnienie przez współbieżność (`429` pod obciążeniem)**: Gdy wiele sesji agenta lub zadań cron jednocześnie korzysta z `auto`, łączna częstotliwość żądań przekracza poziom tolerowany przez bezpłatnych dostawców, przez co prawidłowe wywołania zostają oznaczone jako nadużycie.

**Zweryfikowane rozwiązanie (zgłoszone przez społeczność, 2026-08-10)**: dostosuj trzy zmienne środowiskowe, aby rotacja, współbieżność i przełączanie awaryjne kompensowały niestabilność bezpłatnych planów zamiast powodować zakończenie z błędem:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # przejdź do innego modelu/dostawcy po błędzie 400/401 (pomija niedziałające modele passthrough)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # jawny limit przyjmowania ciężkich żądań (domyślnie nieustawiony: brak limitu liczby żądań, patrz uwaga poniżej)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # dłuższe ograniczone oczekiwanie na dostępność obsługi ciężkich żądań zamiast natychmiastowego, możliwego do ponowienia błędu 503
```

Ustaw je w środowisku procesu OmniRoute (demona, np. za pomocą pliku plist LaunchAgent lub `systemctl edit`), a następnie uruchom OmniRoute ponownie. Flaga rotacji ma zdecydowanie największy wpływ: zamienia krytyczny błąd w niewidoczną dla użytkownika ponowną próbę z użyciem sprawnego dostawcy z puli.

**Uwaga**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ogranicza liczbę ciężkich — wykorzystujących długi kontekst — żądań wykonywanych jednocześnie; ograniczenie to jest bramą przyjmowania żądań, a nie mechanizmem limitowania ich liczby przez dostawcę. **Aktualizacja dotycząca zwielokrotniania błędów #503:** ta zmienna nie jest już ustawiana domyślnie (obowiązuje teraz tylko wtedy, gdy zostanie jawnie skonfigurowana, jak powyżej) — przyjmowanie ciężkich żądań jest zamiast tego kontrolowane przez automatycznie wyznaczany budżet bajtów (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), który skaluje się zgodnie z rzeczywistym limitem pamięci hosta, dlatego w nowym wdrożeniu powinno występować znacznie mniej odrzuceń `503 chat_admission_busy`, nawet jeśli ta zmienna nie zostanie w ogóle ustawiona; jej jawne ustawienie nadal działa dokładnie tak, jak opisano. Jawne nadpisania budżetu bajtów są ograniczane do zakresu 8 MiB–2 GiB. Błąd `413 body_exceeds_budget` nie jest przejściowy: zwiększ ten budżet bajtów, zmniejsz `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` lub zwiększ limit pamięci procesu. Odrzucenie `inflight_bytes_budget` wynika z tymczasowego przeciążenia i nadal można ponowić żądanie. Limity liczby żądań dla poszczególnych dostawców (`open-sse/services/rateLimitManager.ts`) są kontrolowane oddzielnie przez `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` i `RATE_LIMIT_AUTO_ENABLE` — zobacz `.env.example`.

**Jak sprawdzić, czy rozwiązanie zadziałało**: uruchom agenta lub zadanie cron dwukrotnie w krótkim odstępie i upewnij się, że oba wykonania zakończyły się powodzeniem. Przed zastosowaniem rozwiązania drugie uruchomienie zwykle zgłasza `429`/`401`. Po zastosowaniu rozwiązania błędy (jeśli wystąpią) są automatycznie ponawiane, a wywołanie zostaje ukończone. Możesz również wykonać `curl /monitoring/health` i obserwować pole `rateLimitedUntil` w połączeniach dostawców oraz `circuitBreakers.providerBreakers[].state` w przypadku dostawców, których dotyczy problem — stan przyjmuje jedną z wartości `CLOSED`, `DEGRADED`, `OPEN` lub `HALF_OPEN` (zobacz `src/shared/utils/circuitBreaker.ts`), a dostawca, którego wywołania nadal kończą się niepowodzeniem, przejdzie kolejno przez stany `CLOSED → DEGRADED → OPEN`, zanim okno resetowania umożliwi wykonanie żądania próbnego (`HALF_OPEN`).

**Jeśli nadal widzisz błąd 429**: aktywne konto tego dostawcy rzeczywiście wyczerpało swój _limit_ (nie tylko limit szybkości żądań). Dodaj drugie konto tego samego dostawcy w panelu OmniRoute → Providers → Accounts albo dodaj innego bezpłatnego dostawcę (np. `routeway`, `auggie`). Rotacja pomaga tylko w przypadku przejściowych błędów limitu szybkości żądań/400/401; całkowite wyczerpanie limitu wymaga drugich danych uwierzytelniających lub innego dostawcy.

**Jeśli widzisz błąd 403 w modelach wizyjnych (`auto/vision`, `bazaarlink/*`)**: połączone konto nie ma płatnego planu obejmującego modele wizyjne albo klucz API ma niewystarczające uprawnienia. Sprawdź w panelu dostawcy, czy zakres klucza obejmuje funkcje wizyjne/multimodalne, albo połącz konto z płatnym planem i pozostaw je jako docelowe konto dla modeli wizyjnych.

## Ostrzeżenia podczas npm install (ERESOLVE / peer / deprecated)

Po uruchomieniu `npm install -g omniroute` możesz zobaczyć mnóstwo ostrzeżeń, takich jak `npm warn ERESOLVE`, komunikaty dotyczące zależności równorzędnych oraz komunikaty `deprecated`. **Są one oczekiwane i nieszkodliwe.** Instalacja zakończyła się powodzeniem, jeśli w danych wyjściowych widzisz komunikat `added <N> packages`.

Ostrzeżenia wynikają z nieaktualnych zakresów zależności równorzędnych w pakietach zewnętrznych, nad którymi OmniRoute nie ma kontroli:

1. **`marked-terminal` wymaga `marked >=1 <16`, ale znaleziono `marked@18`** — w praktyce działa prawidłowo; zakres zależności równorzędnej w pakiecie źródłowym jest po prostu nieaktualny.
2. **`deprecated prebuild-install@7.1.3`** — przechodnie narzędzie pomocnicze do pobierania natywnych plików binarnych. Nie jest
   używane do instalowania przypiętego powiązania transportowego `wreq-js` i nie oznacza, że konfiguracja transportu
   dostawcy plików cookie sieci Web zakończyła się niepowodzeniem.

**Nie są wymagane żadne działania** — tych ostrzeżeń nie można całkowicie wyciszyć bez utworzenia forków pakietów źródłowych.

## Fałszywe alarmy programu antywirusowego

<a name="antivirus-false-positives"></a>

### Avast/AVG przenosi `README.md` do kwarantanny z oznaczeniem `MD:HttpRequest-inf[Susp]`

**To fałszywy alarm. Żaden plik nie jest zainfekowany i nie trzeba podejmować żadnych działań.**

Avast i AVG stosują heurystykę, która oznacza pliki tekstowe/Markdown zawierające wiele
linków wyglądających jak żądania HTTP. Plik `README.md` OmniRoute jest dołączony do pakietu npm
(jest wymieniony w `package.json` → `files`), więc podczas instalacji globalnej trafia do
`node_modules/omniroute/README.md` — a zawiera około 15 przykładów
`http://localhost:20128/...` (punkty końcowe HTTP/SSE protokołu MCP, adres URL A2A
`.well-known` oraz fragmenty poleceń `curl`). Tak duże zagęszczenie linków wystarcza, aby
uruchomić tę heurystykę.

Jeśli problem pojawił się dopiero niedawno: charakter pliku się nie zmienił. W pliku README
rozbudowano tabelę punktów końcowych (dodano MCP HTTP + SSE + A2A) oraz więcej przykładów
`curl`, przez co przekroczony został próg heurystyki.

Ten plik to nieaktywna dokumentacja, która nie zawiera żadnej wykonywalnej zawartości. Można
go bezpiecznie przywrócić z kwarantanny.

**Co zrobić:**

1. **Wyłącz powiadomienia** — wyklucz katalog instalacyjny w programie antywirusowym
   (Avast: Ustawienia → Wyjątki), dodając ścieżkę do globalnego katalogu `node_modules`
   lub katalog danych OmniRoute (`~/.omniroute/`).
2. **Zgłoś fałszywy alarm** — <https://www.avast.com/false-positive-file-form.php>,
   dołączając objęty kwarantanną plik `README.md`. To rozwiązanie pomoże wszystkim, ponieważ
   źródłem problemu jest heurystyka producenta, która nadmiernie reaguje na plik tekstowy.

**Dlaczego nie „naprawiamy” tego po naszej stronie:** wszystkie przykłady używają
`http://localhost`, a host lokalny nie może korzystać z `https` bez komplikacji związanych
z certyfikatami z podpisem własnym. Zniekształcanie dokumentacji w celu ominięcia heurystyki
jednego producenta zaszkodziłoby każdemu czytelnikowi tylko po to, aby obejść błąd skanera.

### Kaspersky oznacza aplikację desktopową jako `PDM:Trojan.Win32.Generic`

**To fałszywy alarm pochodzący z heurystyki behawioralnej. Żaden plik nie jest zainfekowany.**
Prefiks `PDM:` w Kaspersky oznacza, że werdykt pochodzi z modułu Proactive Defense Module
(System Watcher), który ocenia to, co instalator _robi_, zamiast porównywać go ze znanym
złośliwym oprogramowaniem. Po wykryciu zagrożenia Kaspersky „wycofuje” całą instalację —
usuwając pliki, które zostały już zapisane — przez co aplikacja przestaje działać lub znika.

Oznaczane pliki są standardowymi częściami zadeklarowanych zależności open source dołączonych
do aplikacji desktopowej, na przykład:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` oraz
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), biblioteka do automatyzacji
  przeglądarki używana do logowania w aplikacji do usługodawców i obsługi czatu za
  pośrednictwem przeglądarki.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — przypięte natywne powiązanie `wreq-js`, używane do wysyłania żądań HTTP z odciskiem
  przeglądarki w przypadku usługodawców korzystających z internetowych plików cookie
  (`<arch>` to `x64` lub `arm64`).

**Dlaczego jest oznaczany:** instalator dla systemu Windows **nie jest jeszcze podpisany
cyfrowo**, więc niepodpisany instalator NSIS nie ma żadnej reputacji, a heurystyki behawioralne
działają z maksymalną agresywnością. W połączeniu z dołączoną natywną biblioteką DLL oraz
setkami plików `.js` zapisywanymi w katalogu `%LOCALAPPDATA%\Programs\OmniRoute` (w tym
katalogami pakietów z sufiksami skrótów z autonomicznej kompilacji Next.js) wystarcza to do
uruchomienia heurystyki. Podpisywanie kodu jest planowane; do czasu jego wdrożenia problem
może się powtarzać w nowych wydaniach.

**Co zrobić:**

1. **Najpierw zweryfikuj pobrany plik** (pozwala to wykluczyć jego zmodyfikowanie). Każde
   wydanie zawiera plik `latest.yml`, którego pole `sha512` (base64) obejmuje instalator
   `OmniRoute.Setup.<version>.exe`. W PowerShell, w folderze zawierającym instalator:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Wynik musi być zgodny z `latest.yml` → `sha512`. Jeśli nie jest, usuń plik i pobierz go
   ponownie wyłącznie ze [strony wydań w serwisie GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Przywróć + wyklucz** — przywróć z kwarantanny elementy usunięte wskutek wycofania zmian
   i dodaj wykluczenie dla `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Ustawienia →
   Zagrożenia i wykluczenia), a następnie ponownie przeprowadź instalację.
3. **Zgłoś fałszywy alarm** — <https://opentip.kaspersky.com/>. Zgłoszenia fałszywych
   alarmów przesyłane przez użytkowników rzeczywiście przyspieszają dodawanie plików do
   listy dozwolonych.

## Zgodność z Node.js

<a name="nodejs-compatibility"></a>

### Strona logowania ulega awarii lub wyświetla błąd „Module self-registration”

**Przyczyna:** Używasz wersji Node.js spoza zatwierdzonego przez OmniRoute minimalnego bezpiecznego środowiska uruchomieniowego. Najczęściej dotyczy to starszej wersji poprawkowej Node 22 lub 24, która nie spełnia minimalnych wymagań bezpieczeństwa OmniRoute.

**Objawy:**

- Strona logowania wyświetla pusty ekran lub błąd serwera
- Konsola wyświetla `Error: Module did not self-register` lub podobne błędy natywnych powiązań
- Strona logowania wyświetla **pomarańczowy baner ostrzegawczy** z używaną wersją Node, jeśli środowisko uruchomieniowe nie spełnia obsługiwanych zasad bezpieczeństwa

**Rozwiązanie:**

1. Zainstaluj obsługiwaną wersję LTS Node.js (zalecana: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Sprawdź wersję: `node --version` powinno wyświetlić `v24.0.0` lub nowszą wersję z linii LTS 24.x
3. Ponownie zainstaluj OmniRoute: `npm install -g omniroute`
4. Uruchom ponownie: `omniroute`

> **Obsługiwane bezpieczne wersje:** `>=22.22.2 <23` lub `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) i Node.js 26 są w pełni obsługiwane.

### npm v11+: `better-sqlite3` nie jest zainstalowany (nie można znaleźć modułu)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Przyczyna:** npm v11 (dostarczany z Node.js 24+) domyślnie blokuje skrypty instalacyjne opcjonalnych
zależności. Ponieważ `better-sqlite3` znajduje się na liście `optionalDependencies`
i wymaga natywnej kompilacji (`node-gyp rebuild`), npm pomija go bez wyświetlania komunikatu.

**Objawy:**

- Serwer ulega awarii podczas uruchamiania z błędem `Cannot find module 'better-sqlite3'`
- Polecenie `ls node_modules/better-sqlite3` wyświetla „No such file or directory”
- Polecenie `npm ls better-sqlite3` wyświetla `(empty)`

**Rozwiązanie:**

1. Zatwierdź skrypty instalacyjne i zainstaluj ponownie:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Możesz też ręcznie zainstalować gotowy pakiet binarny:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Sprawdź, czy działa: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file”

<a name="macos-native-module-rebuild"></a>

**Przyczyna:** Po globalnym wykonaniu `npm install -g omniroute` natywny plik binarny `better-sqlite3` znajdujący się w pakiecie mógł zostać skompilowany dla innej architektury lub innego ABI Node.js niż używane lokalnie. Jest to częste w systemie macOS (zarówno na komputerach Apple Silicon, jak i Intel), gdy gotowy plik binarny nie jest zgodny z używanym środowiskiem.

**Objawy:**

- Serwer ulega awarii natychmiast podczas uruchamiania z błędem `dlopen`
- Błąd zawiera komunikat `slice is not valid mach-o file`
- Pełny przykład:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Rozwiązanie — skompiluj ponownie dla lokalnego środowiska (obniżenie wersji Node.js nie jest wymagane):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Uwaga:** Powoduje to ponowną kompilację natywnego powiązania dla lokalnej wersji Node.js i architektury procesora, eliminując niezgodność pliku binarnego. Oficjalnie obsługiwany zakres środowiska uruchomieniowego to **`>=22.22.2 <23` lub `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` w pliku `src/shared/utils/nodeRuntimeSupport.ts`, zgodny z polem `engines` w pliku `package.json`). Node.js 24.x LTS (Krypton) i Node.js 26 są w pełni obsługiwane z `better-sqlite3` v12.x.

## Problemy z proxy

<a name="proxy-issues"></a>

### Walidacja dostawcy wyświetla komunikat „fetch failed”

**Przyczyna:** Punkt końcowy walidacji klucza API (`POST /api/providers/validate`) wcześniej pomijał konfigurację proxy, powodując błędy w środowiskach wymagających routingu przez proxy.

**Rozwiązanie (v3.5.5+):** Problem został naprawiony. Walidacja dostawcy jest teraz kierowana przez `runWithProxyContext`, automatycznie uwzględniając ustawienia proxy na poziomie dostawcy i ustawienia globalne.

### Kontrola poprawności tokenu kończy się błędem „fetch failed”

**Przyczyna:** Odświeżanie tokenu OAuth w tle nie rozpoznawało konfiguracji proxy dla poszczególnych połączeń.

**Rozwiązanie (v3.5.5+):** Harmonogram kontroli poprawności tokenów rozpoznaje teraz konfigurację proxy dla każdego połączenia przed próbą odświeżenia. Zaktualizuj do wersji v3.5.5+.

### Proxy SOCKS5 zwraca komunikat „invalid onRequestStart method”

**Przyczyna:** W Node.js 22 dyspozytor undici@8 jest niezgodny z wbudowaną w Node funkcją `fetch()`.

**Rozwiązanie (v3.5.5+):** Gdy dyspozytor proxy jest aktywny, OmniRoute korzysta teraz z własnej funkcji `fetch()` biblioteki undici, zapewniając spójne działanie. Zaktualizuj do wersji v3.5.5+.

### Proxy MITM w środowisku WSL: aplikacje desktopowe na hoście Windows nie są przechwytywane

**Przyczyna:** Proxy MITM i jego certyfikat CA są instalowane w środowisku, w którym działa OmniRoute. W przypadku WSL tym środowiskiem jest gościnny system Linux, podczas gdy aplikacje desktopowe AI (Kiro, Trae, Copilot, Zed, …) działają na hoście Windows. Aplikacje hosta nie ufają magazynowi certyfikatów systemu gościnnego ani nie kierują ruchu przez systemowe proxy tego systemu, dlatego przechwytywanie aplikacji desktopowych nie działa.

**Zalecenie:** Uruchom OmniRoute natywnie w tym samym systemie operacyjnym co aplikacje desktopowe, które chcesz przechwytywać (Windows dla aplikacji Windows; analogicznie macOS/Linux). Utrzymywanie OmniRoute wewnątrz WSL przy jednoczesnym kierowaniu go na aplikacje hosta wymaga ręcznego dodania wygenerowanego certyfikatu CA do zaufanych na hoście Windows oraz wskazania punktu końcowego proxy WSL w ustawieniach sieci/proxy każdej aplikacji hosta — jest to nieobsługiwana i podatna na problemy konfiguracja.

znajdziesz w pliku [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Problemy z chmurą

### Błędy synchronizacji z chmurą

1. Sprawdź, czy `BASE_URL` wskazuje na uruchomioną instancję (np. `http://localhost:20128`)
2. Sprawdź, czy `CLOUD_URL` wskazuje na punkt końcowy chmury (np. `https://omniroute.dev`)
3. Upewnij się, że wartości `NEXT_PUBLIC_*` są zgodne z wartościami po stronie serwera

### Chmura zwraca 500 dla `stream=false`

**Objaw:** `Unexpected token 'd'...` w punkcie końcowym chmury dla wywołań bez strumieniowania.

**Przyczyna:** Usługa nadrzędna zwraca dane SSE, podczas gdy klient oczekuje formatu JSON.

**Obejście:** Użyj `stream=true` dla bezpośrednich wywołań chmury. Lokalne środowisko uruchomieniowe zawiera mechanizm awaryjnej konwersji SSE→JSON.

### Chmura zgłasza połączenie, ale wyświetla „Invalid API key”

1. Utwórz nowy klucz w lokalnym panelu (`/api/keys`)
2. Uruchom synchronizację z chmurą: Włącz chmurę → Synchronizuj teraz
3. Stare lub niezsynchronizowane klucze mogą nadal zwracać `401` w chmurze

## Problemy z Dockerem

### Docker IPv6 / resetowanie połączenia

<a name="docker-ipv6"></a>

**Objawy:** `curl http://localhost:20128/v1/models` zwraca `curl: (56) Recv failure: Connection reset by peer`. Panel i nieuwierzytelnione punkty końcowe działają, ale uwierzytelnione punkty końcowe nie działają — wygląda to na problem z uwierzytelnianiem, ale nim nie jest.

**Przyczyna:** `docker run -p 20128:20128` publikuje port zarówno na `0.0.0.0` (IPv4), jak i `::` (IPv6), ale proces wewnątrz kontenera nasłuchuje tylko przez IPv4. Na hostach, na których `localhost` jest najpierw rozwiązywany do `::1`, połączenie trafia na opublikowany port IPv6, za którym nie ma procesu nasłuchującego → połączenie zostaje zresetowane.

**Rozwiązanie:**

1. **Szybka diagnostyka:** Uruchom `curl -4 http://localhost:20128/v1/models`. Jeśli działa z `-4`, ale bez tej flagi nie działa, występuje niezgodność powiązania IPv6.
2. **Trwałe rozwiązanie:** Powiąż port jawnie z IPv4, używając `-p 127.0.0.1:20128:20128` w poleceniu `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Wymusza to powiązanie z IPv4, a także zapobiega udostępnianiu proxy na wszystkich interfejsach hosta.

### Wysokie koszty

## Debugowanie

### Włączanie plików dziennika

Ustaw `APP_LOG_TO_FILE=true` w pliku `.env`. Dzienniki aplikacji są zapisywane w katalogu `logs/`.
Artefakty żądań są przechowywane w `${DATA_DIR}/call_logs/`, gdy potok dziennika wywołań jest
włączony w ustawieniach.
Gdy przechwytywanie przez potok jest włączone, ustaw `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false`, aby pominąć
ładunki fragmentów strumienia, lub dostosuj `CALL_LOG_PIPELINE_MAX_SIZE_KB`, aby zmienić limit rozmiaru artefaktów w KB.

### Sprawdzanie kondycji dostawcy

```bash
# Panel kondycji
http://localhost:20128/dashboard/health

# Kontrola kondycji API
curl http://localhost:20128/api/monitoring/health
```

### Pamięć masowa środowiska uruchomieniowego

- Stan główny: `${DATA_DIR}/storage.sqlite` (dostawcy, kombinacje, aliasy, klucze, ustawienia)
- Użycie: tabele SQLite w `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + opcjonalnie `${DATA_DIR}/call_logs/`
- Dzienniki aplikacji: `<repo>/logs/...` (gdy `APP_LOG_TO_FILE=true`)
- Artefakty dziennika wywołań: `${DATA_DIR}/call_logs/YYYY-MM-DD/...`, gdy potok dziennika wywołań jest włączony

Akcja **Wyczyść historię** na stronie Dzienniki żądań usuwa dane z `call_logs`, starszego
`request_detail_logs` oraz lokalnego katalogu artefaktów `${DATA_DIR}/call_logs/`.

3. Sprawdź, czy dostawca zmienił limity API lub wymaga ponownego uwierzytelnienia
4. Przejrzyj telemetrię opóźnień — duże opóźnienia mogą powodować błędy przekroczenia limitu czasu

## Debugowanie translatora

Użyj sekcji **Panel → Translator**, aby debugować problemy z translacją formatów:

| Tryb                   | Kiedy używać                                                                                                          |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **Środowisko testowe** | Porównuj formaty wejściowe i wyjściowe obok siebie — wklej żądanie powodujące błąd, aby zobaczyć, jak jest tłumaczone |
| **Tester czatu**       | Wysyłaj wiadomości na żywo i analizuj pełne dane żądania/odpowiedzi wraz z nagłówkami                                 |
| **Zestaw testów**      | Uruchamiaj testy wsadowe dla różnych kombinacji formatów, aby znaleźć niedziałające translacje                        |
| **Monitor na żywo**    | Obserwuj przepływ żądań w czasie rzeczywistym, aby wychwycić sporadyczne problemy z translacją                        |

### Typowe problemy z formatami

- **Znaczniki myślenia nie są wyświetlane** — sprawdź, czy dostawca docelowy obsługuje myślenie, oraz ustawienie budżetu myślenia
- **Wywołania narzędzi znikają** — niektóre translacje formatów mogą usuwać nieobsługiwane pola; sprawdź to w trybie środowiska testowego
- **Brak monitu systemowego** — Claude i Gemini inaczej obsługują monity systemowe; sprawdź wynik translacji
- **SDK zwraca nieprzetworzony ciąg znaków zamiast obiektu** — rozwiązano w v1.x; mechanizm oczyszczania odpowiedzi usuwa niestandardowe pola (`x_groq`, `usage_breakdown` itd.), które powodują błędy walidacji Pydantic w SDK OpenAI. Jeśli problem nadal występuje w v3.x+, zgłoś go.
- **GLM/ERNIE odrzuca rolę `system`** — rozwiązano w v1.x; normalizator ról automatycznie łączy komunikaty systemowe z komunikatami użytkownika w przypadku niezgodnych modeli. Jeśli problem nadal występuje w v3.x+, zgłoś go.
- **Rola `developer` nie jest rozpoznawana** — rozwiązano w v1.x; jest automatycznie konwertowana na `system` w przypadku dostawców innych niż OpenAI. Jeśli problem nadal występuje w v3.x+, zgłoś go.
- **`json_schema` nie działa z Gemini** — rozwiązano w v1.x; `response_format` jest teraz konwertowany na `responseMimeType` + `responseSchema` Gemini. Jeśli problem nadal występuje w v3.x+, zgłoś go.

## Ustawienia odporności

### Automatyczne ograniczanie liczby żądań nie jest uruchamiane

- Automatyczne ograniczanie liczby żądań dotyczy tylko dostawców korzystających z kluczy API (nie OAuth/subskrypcji)
- Sprawdź, czy w sekcji **Ustawienia → Odporność → Profile dostawców** włączono automatyczne ograniczanie liczby żądań
- Sprawdź, czy dostawca zwraca kody stanu `429` lub nagłówki `Retry-After`

### Dostrajanie wykładniczego mechanizmu ponawiania

Profile dostawców obsługują następujące ustawienia:

- **Opóźnienie bazowe** — Początkowy czas oczekiwania po pierwszym niepowodzeniu (domyślnie: 1s)
- **Maksymalne opóźnienie** — Górny limit czasu oczekiwania (domyślnie: 30s)
- **Mnożnik** — Stopień zwiększenia opóźnienia po każdym kolejnym niepowodzeniu (domyślnie: 2x)

### Zapobieganie efektowi thundering herd

Gdy wiele równoczesnych żądań trafia do dostawcy z ograniczoną liczbą żądań, OmniRoute używa muteksu i automatycznego ograniczania liczby żądań, aby przetwarzać je szeregowo i zapobiegać kaskadowym awariom. W przypadku dostawców korzystających z kluczy API odbywa się to automatycznie.

### Żądania czatu kończą się niepowodzeniem 503 / chat_admission_busy

**Objawy:**

- Punkt końcowy uzupełnień czatu zwraca możliwą do ponowienia odpowiedź `503`, której kod błędu to
  `chat_admission_busy`.
- Odpowiedź zawiera `Retry-After`. Od wersji #12135 wartość jest wyznaczana na podstawie zaobserwowanego
  obciążenia — jest to większa z dwóch wartości: okno `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`, przez które żądanie już
  oczekiwało, oraz czas utrzymywania bieżących dzierżaw dla żądań o dużym obciążeniu — zaokrąglona w górę do pełnych
  sekund i ograniczona do 60. Gdy brama jest bezczynna, zachowane są historyczne wartości minimalne: 2 sekundy dla
  ścieżki opartej na bajtach i 1 sekunda dla ścieżki opartej na strukturze (która zawiera również
  `reason: "structure_limit"`).
- Może się to zdarzyć, gdy inny czat o dużym obciążeniu lub długotrwała odpowiedź strumieniowa jest nadal
  w trakcie obsługi.

Treść odpowiedzi opartej na bajtach:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Odpowiedź oparta na strukturze używa tego samego typu i kodu, z komunikatem
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
oraz `reason: "structure_limit"`.
Przy domyślnych progach żądanie jest uznawane za obciążające strukturalnie, jeśli zawiera co najmniej `200` wiadomości,
co najmniej `64` narzędzia lub co najmniej `32,000` szacowanych tokenów albo gdy ograniczone szacowanie struktury
wyczerpie limity `10,000` odwiedzonych węzłów lub głębokości `12`.

**Przyczyna:** Jest to celowe odrzucanie nadmiarowego obciążenia wewnątrz OmniRoute, a nie awaria dostawcy nadrzędnego.
Każdy proces używa lokalnego dla procesu mechanizmu ochronnego, aby zarezerwować ograniczoną przepustowość dla żądań o dużym obciążeniu przed zachowaniem
i przeanalizowaniem dużej treści żądania. Dzierżawa dla żądania o dużym obciążeniu pozostaje aktywna przez cały czas trwania odpowiedzi
SSE.

**#503-fanout:** przed tą poprawką mechanizm ochronny ograniczał współbieżność do stałej LICZBY żądań
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, domyślnie `1`) niezależnie od pamięci hosta, dlatego rozproszenie zadań agenta programistycznego
(wiele podagentów/CLI, treści regularnie > 256 KB) obniżało efektywną
współbieżność do ~1 i powodowało błędy 503 przy całkowicie normalnym obciążeniu. Mechanizm ochronny dostraja się teraz automatycznie: jest sterowany
przez automatycznie wyznaczany BUDŻET bajtów danych wejściowych (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), którego rozmiar jest ustalany na podstawie
rzeczywistego limitu pamięci procesu, a ponadto uwzględnia bieżący sygnał presji na zasoby — dzięki czemu
odrzuca żądania tylko wtedy, gdy host rzeczywiście znajduje się pod presją pamięci, a nie tylko dlatego, że jednocześnie
nadeszło więcej niż jedno żądanie o dużym obciążeniu. Stary limit liczby żądań (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) jest
nadal respektowany, ale tylko wtedy, gdy zostanie jawnie ustawiony.

Gdy przepustowość jest zajęta, żądanie o dużym obciążeniu najpierw oczekuje maksymalnie przez
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (domyślnie `2000`, wartość `0` wyłącza oczekiwanie) na zwolnienie miejsca,
zanim zostanie zwrócona możliwa do ponowienia odpowiedź `503`. Ograniczony czas oczekiwania istnieje po to, aby klienci działający jak agenci
(OpenCode, Claude Code, Cursor), którzy równocześnie rozsyłają obciążające podżądania, przetwarzali tę serię szeregowo,
zamiast wyczerpywać cały budżet ponowień na natychmiastowe odrzucenia i przerywać działanie w trakcie zadania.
Bieżące wykorzystanie dzierżaw dla żądań o dużym obciążeniu, ustalony budżet bajtów i aktualny poziom presji są
dostępne pod adresem `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — sprawdź je przed zmianą jakiejkolwiek zmiennej środowiskowej.
Ustawienia → Odporność → Kolejka żądań → Równoczesne żądania nie sterują tym mechanizmem; to ustawienie
kontroluje osobny mechanizm kolejki żądań dostawcy.

**Rozwiązanie:**

1. Najpierw ponów próbę. Klienci powinni respektować `Retry-After` i stosować mechanizm ponawiania zamiast natychmiast
   powtarzać żądanie.
2. Przed dostrojeniem czegokolwiek sprawdź `/api/monitoring/health` → `chatAdmission`. `countCapEnabled:
false` oraz duża wartość `maxInflightBytes` oznaczają, że automatycznie wyznaczany budżet już prawidłowo spełnia swoje
   zadanie; wartość `pressureSeverity` równa `high`/`critical` oznacza, że hostowi rzeczywiście brakuje pamięci —
   nie można tego naprawić za pomocą zmiennej środowiskowej sterującej dopuszczaniem żądań; potrzeba więcej pamięci RAM lub mniejszego obciążenia.
3. Tylko jeśli `/api/monitoring/health` wskazuje, że automatycznie wyznaczony budżet jest rzeczywiście zbyt mały dla
   hosta (co zdarza się rzadko — skaluje się on już od kontenerów po systemy bare-metal), zastąp go bezpośrednio za pomocą
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, zamiast wracać do starszego limitu liczby żądań.

Autorytatywne ustawienia dopuszczania żądań opisano w [dokumentacji zmiennych środowiskowych](../reference/ENVIRONMENT.md#4-security--authentication).

## Opcjonalna taksonomia błędów RAG / LLM (16 problemów)

Niektórzy użytkownicy OmniRoute umieszczają bramę przed stosami RAG lub agentowymi. W takich konfiguracjach często można zaobserwować nietypową sytuację: OmniRoute wygląda na sprawny (dostawcy są dostępni, profile routingu są poprawne, brak alertów o limitach żądań), ale końcowa odpowiedź nadal jest błędna.

W praktyce takie incydenty wynikają zazwyczaj z dalszego potoku RAG, a nie z samej bramy.

Jeśli potrzebujesz wspólnego słownictwa do opisywania takich błędów, możesz użyć WFGY ProblemMap — zewnętrznego zasobu tekstowego na licencji MIT, który definiuje szesnaście powtarzających się wzorców błędów RAG / LLM. Ogólnie obejmuje on:

- dryf wyszukiwania i uszkodzone granice kontekstu
- puste lub nieaktualne indeksy i magazyny wektorowe
- rozbieżność między osadzeniami a semantyką
- problemy ze składaniem promptów i oknem kontekstu
- załamanie logiki i odpowiedzi udzielane z nadmierną pewnością
- błędy długich łańcuchów i koordynacji agentów
- dryf pamięci i ról w systemach wieloagentowych
- problemy z kolejnością wdrażania i inicjalizacji

Założenie jest proste:

1. Podczas badania błędnej odpowiedzi zbierz:
   - zadanie i żądanie użytkownika
   - trasę lub kombinację dostawców w OmniRoute
   - wszelki kontekst RAG użyty w dalszym potoku (wyszukane dokumenty, wywołania narzędzi itd.)
2. Przypisz incydent do jednego lub dwóch numerów WFGY ProblemMap (`No.1` … `No.16`).
3. Zapisz numer we własnym panelu, podręczniku operacyjnym lub systemie śledzenia incydentów obok dzienników OmniRoute.
4. Skorzystaj z odpowiedniej strony WFGY, aby zdecydować, czy należy zmienić stos RAG, mechanizm wyszukiwania lub strategię routingu.

Pełny tekst i konkretne procedury znajdują się tutaj (licencja MIT, tylko tekst):

[README WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Możesz pominąć tę sekcję, jeśli za OmniRoute nie działają żadne potoki RAG ani agentowe.

## Znane problemy w v3.8.0

Problemy specyficzne dla wydania v3.8.0 oraz ich aktualne obejścia. Jeśli poprawka pojawi się w późniejszej wersji poprawkowej, wpis zostanie zaktualizowany lub usunięty.

### Błędy uwierzytelniania Devin CLI

**Objawy:**

- „Nie znaleziono Devin CLI” lub „uwierzytelnianie nie powiodło się” podczas wywoływania narzędzi opartych na Devin
- Kontrola środowiska uruchomieniowego CLI zgłasza `installed=false`

**Przyczyny:**

- `CLI_DEVIN_BIN` wskazuje ścieżkę, która nie istnieje
- Devin CLI nie jest zainstalowany na hoście

**Rozwiązanie:**

1. Zainstaluj Devin CLI dla swojej platformy
2. Ustaw `CLI_DEVIN_BIN=/usr/local/bin/devin` (lub rzeczywistą ścieżkę) w `.env`
3. Uruchom ponownie OmniRoute i ponów test z poziomu **Panel → Narzędzia CLI**

### Model zablokowany w okresie karencji (reset ręczny)

**Objawy:**

- Model pozostaje na liście modeli objętych okresem karencji nawet po upływie czasu wygaśnięcia
- Żądania nadal pomijają model w routingu kombinowanym, mimo że znacznik czasu wskazuje przeszłość

**Reset ręczny:**

- **Panel:** **Ustawienia → Okresy karencji modeli** → kliknij **Włącz ponownie** na karcie modelu, którego dotyczy problem
- **API:** `DELETE /api/resilience/model-cooldowns` z nagłówkami uwierzytelniania administracyjnego

### Połączenie z dostawcą Command Code kończy się błędem 403

**Objawy:**

- Błąd 403 podczas testowania połączenia z dostawcą Command Code
- Po ponownym dodaniu karta dostawcy wyświetla komunikat „brak autoryzacji”

**Przyczyna:** Przepływ OAuth nie został ukończony (nie odebrano wywołania zwrotnego lub token nie został zapisany).

**Rozwiązanie:**

- Uruchom `omniroute providers` z poziomu CLI, aby ponownie wyzwolić przepływ OAuth, lub
- Ponownie uruchom OAuth z poziomu **Panel → Dostawcy → Command Code → Połącz ponownie**

### ModelScope zwraca zbyt agresywne okresy karencji po błędach 429

**Objawy:**

- Bardzo krótkie lub natychmiastowe okresy karencji w ModelScope po niewielkiej serii żądań
- Routing kombinowany pomija ModelScope wcześniej, niż oczekiwano

**Przyczyna:** ModelScope emituje specyficzne dla dostawcy nagłówki `Retry-After`. Wersja v3.8.0 zawiera dedykowaną obsługę tych nagłówków, dlatego starsze wersje błędnie interpretują je jako ogólne wskazówki dotyczące limitu żądań.

**Rozwiązanie:**

- Upewnij się, że używasz wersji v3.8.0 lub nowszej
- Sprawdź, czy przełącznik `useUpstream429BreakerHints` jest włączony w sekcji **Ustawienia → Odporność**

### Brak OMNIROUTE_WS_BRIDGE_SECRET w środowisku produkcyjnym

**Objawy:**

- Błąd 401 przy każdym żądaniu do mostu WebSocket Codex/Responses podczas pracy na zdalnym hoście produkcyjnym
- Uzgadnianie połączenia mostu WebSocket zostaje zamknięte natychmiast po nawiązaniu połączenia

**Przyczyna:** W środowisku produkcyjnym brakuje zmiennej środowiskowej `OMNIROUTE_WS_BRIDGE_SECRET`.

**Rozwiązanie:**

1. Wygeneruj losowy sekret: `openssl rand -hex 32`
2. Ustaw `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` w środowisku serwera produkcyjnego (oraz na każdym kliencie komunikującym się z mostem)
3. Uruchom ponownie OmniRoute

### Responses API: tryb działania w tle ograniczony do trybu synchronicznego

**Objawy:**

- W dzienniku pojawia się ostrzeżenie: `background mode degraded to synchronous`
- Żądanie `background: true` zwraca zwykłą odpowiedź synchroniczną zamiast uchwytu zadania działającego w tle

**Przyczyna:** Wersja v3.8.0 celowo ogranicza `background: true` w Responses API do wykonywania synchronicznego, jednocześnie emitując ostrzeżenie. Pełne asynchroniczne wykonywanie zadań w tle zostanie udostępnione w przyszłości.

**Rozwiązanie:**

- Dostosuj klienta tak, aby wykonywał wywołania bez `background`, lub
- Poczekaj na późniejsze wydanie zawierające pełny asynchroniczny tryb działania w tle (śledź dziennik zmian)

## Powolne uruchamianie / przekroczenie limitu czasu gotowości

Jeśli CLI wyświetla komunikat `⚠ Server did not respond within 60s`, ale serwer
w rzeczywistości działa, limit czasu sondy gotowości jest zbyt krótki dla Twojego środowiska.

Zdarza się to często w systemie Windows (oprogramowanie antywirusowe, mechanizmy monitorowania systemu plików) lub w kontenerach
z dużym obciążeniem podczas uruchamiania.

**Rozwiązanie — zwiększ limit czasu:**

```bash
# Za pomocą zmiennej środowiskowej (obowiązuje przy kolejnych uruchomieniach):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuty
omniroute serve

# Za pomocą flagi CLI (jednorazowo):
omniroute serve --ready-timeout 180000
```

Wartość domyślna to 60 000 ms (60 s). Ostrzeżenie ma wyłącznie charakter informacyjny; serwer
kontynuuje uruchamianie w tle i będzie dostępny po zakończeniu procesu rozruchu.

Pełne informacje na temat `OMNIROUTE_READY_TIMEOUT_MS` znajdziesz w pliku
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
