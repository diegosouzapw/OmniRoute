## Skrócona instrukcja

**Dopiero zaczynasz korzystać z OmniRoute?** Zacznij tutaj — te rozwiązania usuwają 90% problemów:

| Widoczny komunikat                | Co oznacza                                                      | Co zrobić                                                                                                 |
| --------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| „Nie można się połączyć”          | OmniRoute nie jest uruchomiony                                  | Uruchom `omniroute` lub `docker restart omniroute`                                                        |
| „Nieprawidłowy klucz API”         | Twój klucz jest nieprawidłowy lub wygasł                        | Ponownie skopiuj klucz ze strony dostawcy                                                                 |
| „Przekroczono limit żądań”        | Wysyłasz zbyt wiele żądań                                       | Odczekaj 1 minutę lub użyj `model: "auto"`, aby automatycznie przełączyć się na inne rozwiązanie          |
| „Przekroczono limit użycia”       | Wykorzystano bezpłatny lub płatny limit                         | Połącz więcej dostawców lub użyj bezpłatnych dostawców (Kiro, Pollinations)                               |
| „Wolne odpowiedzi”                | Dostawca jest przeciążony lub znajduje się daleko               | Użyj `model: "auto/fast"` lub połącz szybszego dostawcę (Groq, Cerebras)                                  |
| „Użyto niewłaściwego dostawcy”    | `auto` wybrało innego dostawcę                                  | To normalne! `auto` wybiera najlepszego. Wymuś konkretnego dostawcę za pomocą `model: "openai/gpt-4o"`    |
| „502 Bad Gateway”                 | Dostawca nie działa                                             | Poczekaj i spróbuj ponownie lub użyj `model: "auto"`, aby przełączyć dostawcę                             |
| „401 Unauthorized”                | Twoje dane uwierzytelniające są nieprawidłowe                   | Sprawdź klucz API lub ponownie uwierzytelnij się za pomocą OAuth                                          |
| „omniroute nie jest rozpoznawane” | W zmiennej PATH systemu Windows brakuje globalnych modułów node | Dodaj globalny prefiks npm do zmiennej PATH systemu Windows. Znajdź go za pomocą `npm config get prefix`. |
| „429 Too Many Requests”           | Osiągnięto limit żądań                                          | Odczekaj 1 minutę lub połącz więcej dostawców                                                             |

**Problem nadal występuje?** Zapoznaj się ze [szczegółowym rozwiązywaniem problemów](#detailed-troubleshooting) poniżej lub zapytaj na [Discordzie](https://discord.gg/U47eFqAXCn).

## Szczegółowe rozwiązywanie problemów

---

### Ograniczanie liczby żądań u bezpłatnych dostawców (429 / 400 / 401)

**Objaw**: Podczas używania `model: "auto"` z bezpłatnymi dostawcami lub dostawcami niewymagającymi uwierzytelniania (opencode, auggie itd.) sporadycznie otrzymujesz błędy `HTTP 429`, `400` lub `401` zamiast odpowiedzi. Żądania kończą się powodzeniem po ponowieniu tego samego promptu chwilę później, ale automatyzacja (zadania cron, agenci, skrypty) przestaje działać po pierwszym niepowodzeniu.

**Główna przyczyna**: Nakładają się trzy niezależne tryby awarii:

1. **Limit żądań dostawcy (`429`)**: Bezpłatne plany mogą wymuszać limit w określonym przedziale czasowym. Seria równoległych wywołań wyczerpuje go, więc kolejne żądanie zostaje odrzucone do czasu zresetowania limitu.
2. **Niedziałający model w trybie przekazywania (`400`/`401`)**: Pule `auto/*` mogą zawierać modele przekazywane z `opencode`, które są zarejestrowane w katalogu, ale nie mają aktywnych danych uwierzytelniających (np. `oc/north-mini-code-free` → `401`). Router automatyczny próbuje użyć takiego modelu, próba kończy się niepowodzeniem, a błąd jest zwracany, zanim zadziała mechanizm przełączania awaryjnego.
3. **Wzmocnienie przez współbieżność (`429` pod obciążeniem)**: Gdy wiele sesji agentów lub zadań cron korzysta jednocześnie z `auto`, łączna częstotliwość żądań przekracza poziom tolerowany przez bezpłatnych dostawców, dlatego prawidłowe wywołania zostają oznaczone jako nadużycie.

**Zweryfikowane rozwiązanie (zgłoszone przez społeczność, 2026-08-10)**: dostosuj trzy zmienne środowiskowe, aby rotacja, współbieżność i przełączanie awaryjne pochłaniały niestabilność bezpłatnych planów zamiast powodować awarię:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # przejdź do innego modelu/dostawcy po błędzie 400/401 (pomija niedziałające modele przekazywane)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # jawny maksymalny limit przyjęć ciężkich żądań (domyślnie nieustawiony: brak limitu liczby żądań, patrz uwaga poniżej)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # wydłuż ograniczony czas oczekiwania ponad domyślną wartość RATE_LIMIT_MAX_WAIT_MS dla wolnych usług nadrzędnych
```

Ustaw je w środowisku procesu OmniRoute (demona, np. za pomocą pliku plist LaunchAgent lub `systemctl edit`), a następnie uruchom ponownie OmniRoute. Flaga rotacji zapewnia największą poprawę: przekształca nieodwracalną awarię w niewidoczne dla użytkownika ponowienie próby u sprawnego dostawcy z puli.

**Uwaga**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ogranicza liczbę ciężkich — korzystających z długiego kontekstu — żądań wykonywanych jednocześnie; jest to mechanizm kontroli przyjęć, a nie ogranicznik liczby żądań dostawcy. **Aktualizacja dotycząca rozchodzenia się błędów #503:** ta zmienna nie jest już ustawiana domyślnie (obowiązuje teraz tylko wtedy, gdy zostanie jawnie skonfigurowana, jak powyżej) — przyjmowanie ciężkich żądań jest zamiast tego kontrolowane przez automatycznie wyznaczany budżet bajtów (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), który skaluje się zgodnie z rzeczywistym limitem pamięci hosta, dlatego w nowym wdrożeniu powinno występować znacznie mniej odrzuceń `503 chat_admission_busy` bez konieczności ustawiania tej zmiennej; jej jawne ustawienie nadal działa dokładnie tak, jak opisano. Jawne nadpisania budżetu bajtów są ograniczane do zakresu od 8 MiB do 2 GiB. Błąd `413 body_exceeds_budget` nie jest przejściowy: zwiększ ten budżet bajtów, zmniejsz `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` lub zwiększ limit pamięci procesu. Odrzucenie `inflight_bytes_budget` wynika z tymczasowej rywalizacji o zasoby i nadal można ponowić próbę. Ograniczanie liczby żądań osobno dla każdego dostawcy (`open-sse/services/rateLimitManager.ts`) jest niezależnie kontrolowane przez `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` i `RATE_LIMIT_AUTO_ENABLE` — zobacz `.env.example`.

**Jak sprawdzić, czy rozwiązanie działa**: uruchom agenta/zadanie cron dwa razy w krótkim odstępie czasu i upewnij się, że oba uruchomienia kończą się powodzeniem. Przed wprowadzeniem poprawki drugie uruchomienie zazwyczaj zwraca błąd `429`/`401`. Po wprowadzeniu poprawki nieudane żądania (jeśli wystąpią) są automatycznie ponawiane, a wywołanie zostaje ukończone. Możesz również wywołać `curl /monitoring/health` i obserwować pole `rateLimitedUntil` w połączeniach z dostawcami oraz `circuitBreakers.providerBreakers[].state` dla dostawców, których dotyczy problem — stan przyjmuje jedną z wartości: `CLOSED`, `DEGRADED`, `OPEN` lub `HALF_OPEN` (zobacz `src/shared/utils/circuitBreaker.ts`), a dostawca, który nadal zgłasza błędy, przejdzie przez stany `CLOSED → DEGRADED → OPEN`, zanim po upływie okna resetowania zostanie przepuszczone żądanie testowe (`HALF_OPEN`).

**Jeśli nadal widzisz błąd 429**: aktywne konto tego dostawcy rzeczywiście wyczerpało swój _limit_ (nie chodzi jedynie o limit częstotliwości żądań). Dodaj drugie konto tego samego dostawcy w panelu OmniRoute → Providers → Accounts albo dodaj innego bezpłatnego dostawcę (np. `routeway`, `auggie`). Rotacja pomaga tylko w przypadku przejściowych błędów limitu częstotliwości żądań/400/401; całkowite wyczerpanie limitu wymaga drugich danych uwierzytelniających lub innego dostawcy.

**Jeśli widzisz błąd 403 w modelach wizyjnych (`auto/vision`, `bazaarlink/*`)**: połączone konto nie ma płatnego planu obejmującego funkcje wizyjne albo klucz API ma niewystarczające uprawnienia. Sprawdź w panelu dostawcy, czy zakres klucza obejmuje funkcje wizyjne/multimodalne, albo podłącz konto z płatnym planem i zachowaj je jako docelowe konto dla funkcji wizyjnych.

## Ostrzeżenia npm install (ERESOLVE / peer / deprecated)

Po uruchomieniu `npm install -g omniroute` możesz zobaczyć wiele ostrzeżeń, takich jak `npm warn ERESOLVE`, komunikaty dotyczące zależności równorzędnych oraz komunikaty `deprecated`. **Są one spodziewane i nieszkodliwe.** Instalacja zakończyła się powodzeniem, jeśli w danych wyjściowych widnieje komunikat `added <N> packages`.

Aby ukryć ostrzeżenia dotyczące rozwiązywania zależności równorzędnych, użyj obsługiwanej przez OmniRoute formy instalacji:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` ukrywa wyłącznie komunikaty `ERESOLVE` i powiadomienia dotyczące zależności równorzędnych. Powiadomienia o wycofaniu pozostają widoczne, ponieważ pochodzą z przechodnich pakietów innych firm; nie oznaczają one, że instalacja się nie powiodła.

Ostrzeżenia wynikają z nieaktualnych zakresów zależności równorzędnych w pakietach innych firm, nad którymi OmniRoute nie ma kontroli:

1. **`marked-terminal` wymaga `marked >=1 <16`, ale znaleziono `marked@18`** — w praktyce działa poprawnie; zakres zależności równorzędnej w pakiecie źródłowym jest po prostu nieaktualny.
2. **`deprecated prebuild-install@7.1.3`** — przechodnie narzędzie pomocnicze do pobierania natywnych plików binarnych. Nie jest
   używane do instalowania przypiętego powiązania transportowego `wreq-js` i nie oznacza, że konfiguracja
   transportu dostawcy web-cookie zakończyła się niepowodzeniem.

**Nie są wymagane żadne działania** — ostrzeżeń nie można całkowicie wyciszyć bez utworzenia forków pakietów źródłowych.

## Ostrzeżenie o zablokowanych skryptach npm install (instalacja globalna)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

Podczas uruchamiania `npm install -g omniroute` nowsze wersje npm (v11+ i v12+) domyślnie blokują skrypty cyklu życia pakietów i wyświetlają ostrzeżenie dotyczące skryptów instalacyjnych:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Czy to ostrzeżenie można zignorować?

**Częściowo, ale uruchamianie bez skryptów nie jest zalecane.** OmniRoute zawiera mechanizmy łagodnego przełączania awaryjnego: jeśli natywnych powiązań `better-sqlite3` nie można załadować z samodzielnego pakietu, aplikacja korzysta kolejno z alternatywnych sterowników, takich jak `node:sqlite` lub `sql.js` (zobacz [Rozpoznawanie środowiska uruchomieniowego SQLite](../ops/SQLITE_RUNTIME.md)). Serwer nadal się uruchomi, ale korzystanie z rozwiązań awaryjnych opartych na WASM, takich jak `sql.js`, wyłącza tryb WAL (Write-Ahead Logging) SQLite oraz zwiększa zużycie pamięci i narzut związany z synchronizacją dysku.

### Które skrypty są rzeczywiście wymagane?

Nie wszystkie zablokowane skrypty są niezbędne do działania OmniRoute:

- **Niezbędne (`omniroute`, `better-sqlite3`):** OmniRoute działa z samodzielnego pakietu aplikacji Next.js (`dist/`). Podczas instalacji npm pobiera lub kompiluje właściwy dla danego hosta natywny sterownik SQLite w katalogu najwyższego poziomu `node_modules/better-sqlite3/`. Następnie skrypt `postinstall` OmniRoute (`scripts/build/postinstall.mjs`) weryfikuje i kopiuje te właściwe dla hosta pliki binarne do `dist/node_modules/`, aby samodzielny serwer mógł uzyskać do nich dostęp. Jeśli skrypt postinstall pakietu `omniroute` zostanie zablokowany, ten etap kopiowania zostanie pominięty.
- **Opcjonalne/przechodnie (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** Są to narzędzia pomocnicze do kompilacji, narzędzia monitorujące lub narzędzia systemowego magazynu kluczy. Zezwolenie na ich uruchamianie zapobiega ostrzeżeniom podczas kompilacji, ale nie są one wymagane do podstawowego działania routingu.
- **Wykluczone (`onnxruntime-node`):** Opcjonalna zależność do lokalnych osadzeń AI, która **nie** jest wymagana do działania OmniRoute. Jej skrypt postinstall pobiera z NuGet około 300 MB zasobów CUDA; nie umieszczaj jej na liście dozwolonych, chyba że wyraźnie zamierzasz korzystać z lokalnej akceleracji ONNX na obsługiwanym sprzęcie.

### Zalecane rozwiązanie

Aby zezwolić na wymagane skrypty instalacyjne podczas instalacji globalnej i wyciszyć ostrzeżenia, przekaż `--allow-scripts` dla OmniRoute oraz jego natywnych zależności:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

Alternatywnie, aby skonfigurować to na stałe dla wszystkich globalnych instalacji na swoim koncie użytkownika:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### Zweryfikuj instalację

Po instalacji uruchom wbudowane narzędzie diagnostyczne, aby upewnić się, że natywne powiązania i środowisko uruchomieniowe działają prawidłowo:

```bash
omniroute doctor
```

Jeśli żądanie Gemini Web zwraca błąd `503` z komunikatem, że Playwright Chromium

Playwright:

```bash

npx playwright install chromium
```

Po instalacji uruchom ponownie OmniRoute, a następnie ponów żądanie Gemini Web. Jeśli
uruchamiasz OmniRoute z obrazu Docker, użyj obrazu `-web` (lub celu kompilacji
`runner-web`), który zawiera Chromium i jego zależności; obraz bazowy ich
nie zawiera.

## Fałszywe alarmy programu antywirusowego

<a name="antivirus-false-positives"></a>

### Avast/AVG poddaje kwarantannie plik `README.md` z oznaczeniem `MD:HttpRequest-inf[Susp]`

**To fałszywy alarm. Nic nie jest zainfekowane i nie są wymagane żadne działania.**

Avast i AVG używają heurystyki, która oznacza pliki tekstowe/Markdown zawierające wiele
linków przypominających żądania HTTP. Plik `README.md` OmniRoute jest dołączony do pakietu npm
(jest wymieniony w `package.json` → `files`), więc podczas instalacji globalnej trafia do
`node_modules/omniroute/README.md` — i zawiera około 15 przykładów
`http://localhost:20128/...` (punkty końcowe HTTP/SSE MCP, adres URL `.well-known` A2A oraz
fragmenty z poleceniem `curl`). Takie zagęszczenie linków wystarcza do uruchomienia heurystyki.

Jeśli problem pojawił się dopiero niedawno: charakter pliku się nie zmienił. W README
rozbudowano tabelę punktów końcowych (dodano MCP HTTP + SSE + A2A) oraz dodano więcej
przykładów z poleceniem `curl`, przez co przekroczony został próg heurystyki.

Ten plik jest statyczną dokumentacją i nie zawiera żadnej wykonywalnej zawartości. Można go
bezpiecznie przywrócić z kwarantanny.

**Co zrobić:**

1. **Wyłącz powiadomienia** — dodaj katalog instalacyjny do wyjątków programu antywirusowego
   (Avast: Ustawienia → Wyjątki), wskazując ścieżkę do globalnego katalogu `node_modules`
   i/lub katalogu danych OmniRoute (`~/.omniroute/`).
2. **Zgłoś fałszywy alarm** — <https://www.avast.com/false-positive-file-form.php>,
   załączając poddany kwarantannie plik `README.md`. To rozwiązanie pomoże wszystkim,
   ponieważ problem wynika ze zbyt agresywnej heurystyki producenta reagującej na plik tekstowy.

**Dlaczego nie „naprawiamy” tego po naszej stronie:** wszystkie przykłady używają
`http://localhost`, a localhost nie może korzystać z `https` bez komplikacji związanych
z certyfikatem z podpisem własnym. Zniekształcanie dokumentacji w celu ominięcia heurystyki
jednego producenta pogorszyłoby jej jakość dla każdego czytelnika tylko po to, by obejść błąd
skanera.

### Kaspersky oznacza aplikację komputerową jako `PDM:Trojan.Win32.Generic`

**To fałszywy alarm heurystyki behawioralnej. Nic nie jest zainfekowane.** Prefiks `PDM:`
w Kaspersky oznacza, że werdykt pochodzi z modułu Proactive Defense Module (System Watcher),
który ocenia, co instalator _robi_, zamiast porównywać go ze znanym złośliwym oprogramowaniem.
Po wykryciu Kaspersky „wycofuje” całą instalację — usuwając pliki, które zdążył już zapisać —
przez co aplikacja przestaje działać lub znika.

Oznaczane pliki to standardowe elementy zadeklarowanych zależności open source dołączonych
do aplikacji komputerowej, na przykład:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` oraz
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), biblioteka do automatyzacji
  przeglądarki używana do logowania u dostawców w aplikacji i obsługi czatu za pośrednictwem
  przeglądarki.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — przypięte natywne powiązanie `wreq-js`, używane do obsługi protokołu HTTP z odciskiem
  przeglądarki u dostawców korzystających z internetowych plików cookie (`<arch>` to `x64`
  lub `arm64`).

**Dlaczego jest oznaczany:** instalator dla systemu Windows **nie jest jeszcze podpisany
cyfrowo**, więc niepodpisany instalator NSIS nie ma żadnej reputacji, a heurystyki
behawioralne działają z maksymalną agresywnością. W połączeniu z dołączoną natywną
biblioteką DLL i setkami plików `.js` zapisywanych w
`%LOCALAPPDATA%\Programs\OmniRoute` (w tym katalogami pakietów z sufiksami skrótów z
samodzielnej kompilacji Next.js) wystarcza to do uruchomienia heurystyki. Podpisywanie kodu
jest planowane; do czasu jego wdrożenia problem może powtarzać się w nowych wydaniach.

**Co zrobić:**

1. **Najpierw zweryfikuj pobrany plik** (pozwala to wykluczyć, że został zmodyfikowany).
   Każde wydanie zawiera plik `latest.yml`, którego pole `sha512` (base64) obejmuje instalator
   `OmniRoute.Setup.<version>.exe`. W PowerShell, w folderze zawierającym instalator:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Wynik musi być zgodny z `latest.yml` → `sha512`. Jeśli nie jest, usuń plik i pobierz go
   ponownie wyłącznie ze [strony wydań w serwisie GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Przywróć + dodaj wyjątek** — przywróć z kwarantanny elementy usunięte podczas wycofywania
   instalacji i dodaj wyjątek dla `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Ustawienia
   → Zagrożenia i wykluczenia), a następnie zainstaluj ponownie.
3. **Zgłoś fałszywy alarm** — <https://opentip.kaspersky.com/>. Zgłoszenia fałszywych alarmów
   przesyłane przez użytkowników rzeczywiście przyspieszają dodawanie plików do listy dozwolonych.

## Zgodność z Node.js

<a name="nodejs-compatibility"></a>

### Strona logowania ulega awarii lub wyświetla błąd „Module self-registration”

**Przyczyna:** Używasz wersji Node.js spoza zatwierdzonego przez OmniRoute minimalnego bezpiecznego środowiska uruchomieniowego. Najczęściej dotyczy to starszej wersji poprawkowej Node 22 lub 24, która nie spełnia minimalnego poziomu zabezpieczeń wymaganego przez OmniRoute.

**Objawy:**

- Strona logowania wyświetla pusty ekran lub błąd serwera
- W konsoli pojawia się komunikat `Error: Module did not self-register` lub podobne błędy natywnych powiązań
- Jeśli środowisko uruchomieniowe nie jest zgodne z obsługiwaną polityką bezpieczeństwa, strona logowania wyświetla **pomarańczowy baner ostrzegawczy** z używaną wersją Node

**Rozwiązanie:**

1. Zainstaluj obsługiwaną wersję LTS Node.js (zalecana: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Sprawdź wersję: `node --version` powinno wyświetlić `v24.0.0` lub nowszą wersję z linii LTS 24.x
3. Zainstaluj ponownie OmniRoute: `npm install -g omniroute`
4. Uruchom ponownie: `omniroute`

> **Obsługiwane bezpieczne wersje:** `>=22.22.2 <23` lub `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) i Node.js 26 są w pełni obsługiwane.

### npm v11+: pakiet `better-sqlite3` nie został zainstalowany (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Przyczyna:** npm v11 (dostarczany z Node.js 24+) domyślnie blokuje skrypty instalacyjne opcjonalnych
zależności. Ponieważ `better-sqlite3` znajduje się na liście `optionalDependencies`
i wymaga natywnej kompilacji (`node-gyp rebuild`), npm pomija go bez wyświetlania komunikatu.

**Objawy:**

- Serwer ulega awarii podczas uruchamiania z komunikatem `Cannot find module 'better-sqlite3'`
- Polecenie `ls node_modules/better-sqlite3` wyświetla „No such file or directory”
- Polecenie `npm ls better-sqlite3` wyświetla `(empty)`

**Rozwiązanie:**

1. Zatwierdź skrypty instalacyjne i wykonaj ponowną instalację:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Możesz też ręcznie zainstalować gotowy pakiet binarny:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Sprawdź, czy działa: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file”

<a name="macos-native-module-rebuild"></a>

**Przyczyna:** Po globalnej instalacji za pomocą `npm install -g omniroute` natywny plik binarny `better-sqlite3` znajdujący się w pakiecie mógł zostać skompilowany dla innej architektury lub innego ABI Node.js niż używane lokalnie. Jest to częsty problem w systemie macOS (zarówno na układach Apple Silicon, jak i Intel), gdy gotowy plik binarny nie pasuje do używanego środowiska.

**Objawy:**

- Serwer ulega awarii natychmiast podczas uruchamiania, wyświetlając błąd `dlopen`
- Błąd zawiera komunikat `slice is not valid mach-o file`
- Pełny przykład:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Rozwiązanie — skompiluj ponownie dla lokalnego środowiska (obniżenie wersji Node.js nie jest wymagane):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Uwaga:** Powoduje to ponowną kompilację natywnego powiązania dla lokalnej wersji Node.js i architektury procesora, eliminując niezgodność plików binarnych. Oficjalnie obsługiwany zakres środowiska uruchomieniowego to **`>=22.22.2 <23` lub `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` w `src/shared/utils/nodeRuntimeSupport.ts`, zgodny z polem `engines` w `package.json`). Node.js 24.x LTS (Krypton) i Node.js 26 są w pełni obsługiwane z `better-sqlite3` v12.x.

## Problemy z proxy

<a name="proxy-issues"></a>

### Walidacja dostawcy wyświetla błąd „fetch failed”

**Przyczyna:** Punkt końcowy walidacji klucza API (`POST /api/providers/validate`) wcześniej pomijał konfigurację proxy, powodując błędy w środowiskach wymagających routingu przez proxy.

**Rozwiązanie (v3.5.5+):** Problem został naprawiony. Walidacja dostawcy jest teraz kierowana przez `runWithProxyContext`, automatycznie uwzględniając ustawienia proxy na poziomie dostawcy i ustawienia globalne.

### Kontrola stanu tokena kończy się błędem „fetch failed”

**Przyczyna:** Odświeżanie tokena OAuth w tle nie ustalało konfiguracji proxy dla poszczególnych połączeń.

**Rozwiązanie (v3.5.5+):** Harmonogram kontroli stanu tokenów ustala teraz konfigurację proxy dla każdego połączenia przed próbą odświeżenia. Zaktualizuj do wersji v3.5.5+.

### Proxy SOCKS5 zwraca błąd „invalid onRequestStart method”

**Przyczyna:** W Node.js 22 dyspozytor undici@8 jest niezgodny z wbudowaną w Node funkcją `fetch()`.

**Rozwiązanie (v3.5.5+):** Gdy aktywny jest dyspozytor proxy, OmniRoute używa teraz funkcji `fetch()` z biblioteki undici, zapewniając spójne działanie. Zaktualizuj do wersji v3.5.5+.

### Proxy MITM w WSL: aplikacje komputerowe na hoście Windows nie są przechwytywane

**Przyczyna:** Proxy MITM i jego certyfikat CA są instalowane w środowisku, w którym działa OmniRoute. W przypadku WSL tym środowiskiem jest system gościa Linux, natomiast aplikacje komputerowe AI (Kiro, Trae, Copilot, Zed, …) działają na hoście Windows. Aplikacje hosta nie ufają magazynowi certyfikatów gościa i nie kierują ruchu przez systemowe proxy gościa, dlatego przechwytywanie ruchu aplikacji komputerowych nie działa.

**Zalecenie:** Uruchom OmniRoute natywnie w tym samym systemie operacyjnym co aplikacje komputerowe, których ruch chcesz przechwytywać (Windows dla aplikacji Windows; analogicznie macOS/Linux). Pozostawienie OmniRoute w WSL przy jednoczesnym przechwytywaniu aplikacji hosta wymaga ręcznego dodania wygenerowanego certyfikatu CA do zaufanych na hoście Windows oraz skierowania ustawień sieciowych/proxy każdej aplikacji hosta na punkt końcowy proxy WSL — jest to nieobsługiwana i podatna na błędy konfiguracja.

### „Language model did not provide messages”

**Rozwiązanie:**

2. Użyj kombinacji z poziomami zapasowymi

### Token OAuth wygasł

OmniRoute automatycznie odświeża tokeny. Jeśli problemy nadal występują:

1. Panel → Dostawca → Połącz ponownie
2. Usuń połączenie z dostawcą i dodaj je ponownie

### Wiele kont Kiro: drugie konto unieważnia pierwsze

**Przyczyna:** Zaplecze Kiro wymusza pojedynczą aktywną sesję dla każdej rejestracji klienta OIDC.
Gdy dwa konta współdzielą tego samego zarejestrowanego klienta (połączenia zaimportowane przed v3.8.0),
odświeżenie tokena jednego konta unieważnia token odświeżania drugiego.

**Rozwiązanie (v3.8.0+):** Ponownie zaimportuj połączenia, których dotyczy problem.
Począwszy od v3.8.0, każde nowe połączenie Kiro utworzone za pomocą funkcji **Importuj token**,
**Logowanie społecznościowe Google/GitHub** lub **Automatyczny import** automatycznie rejestruje własnego,
dedykowanego klienta OIDC. Dzięki temu połączenie jest w pełni odizolowane, a odświeżenie jednego
konta nie ma wpływu na żadne inne konto.

Połączenia zaimportowane _przed_ v3.8.0 nie mają rejestracji klienta przypisanej do konkretnego
połączenia. Nadal korzystają one ze współdzielonego punktu końcowego odświeżania uwierzytelniania społecznościowego.
Aby uzyskać izolację, usuń stare połączenie w obszarze Panel → Dostawcy i dodaj je ponownie
przy użyciu dowolnego z trzech sposobów importowania.

Pełne informacje i szczegółowe instrukcje dotyczące dodawania dwóch kont Kiro obok siebie
znajdziesz w pliku [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Problemy z Dockerem

### Docker IPv6 / resetowanie połączenia

<a name="docker-ipv6"></a>

**Objawy:** `curl http://localhost:20128/v1/models` zwraca `curl: (56) Recv failure: Connection reset by peer`. Panel i punkty końcowe niewymagające uwierzytelnienia działają, ale uwierzytelnione punkty końcowe nie działają — wygląda to na problem z uwierzytelnianiem, ale nim nie jest.

**Przyczyna:** `docker run -p 20128:20128` publikuje port zarówno na `0.0.0.0` (IPv4), jak i `::` (IPv6), ale proces wewnątrz kontenera nasłuchuje wyłącznie na IPv4. Na hostach, na których `localhost` jest najpierw rozwiązywany jako `::1`, połączenie trafia na opublikowany port IPv6, za którym nie ma procesu nasłuchującego → połączenie zostaje zresetowane.

**Rozwiązanie:**

1. **Szybka diagnostyka:** Uruchom `curl -4 http://localhost:20128/v1/models`. Jeśli działa z `-4`, ale nie działa bez tej flagi, występuje niezgodność powiązania IPv6.
2. **Trwałe rozwiązanie:** Jawnie powiąż port z IPv4, używając `-p 127.0.0.1:20128:20128` w poleceniu `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Wymusza to powiązanie z IPv4, a także zapobiega udostępnianiu serwera proxy na wszystkich interfejsach hosta.

Użyj sekcji **Panel → Translator**, aby debugować problemy z translacją formatów:

| Tryb             | Kiedy używać                                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------------------------------- |
| **Playground**   | Porównuj formaty wejściowe i wyjściowe obok siebie — wklej żądanie powodujące błąd, aby zobaczyć wynik translacji |

### Typowe problemy z formatem

- **Znaczniki myślenia nie są wyświetlane** — Sprawdź, czy docelowy dostawca obsługuje myślenie, oraz ustawienie budżetu myślenia
- **Wywołania narzędzi są pomijane** — Niektóre translacje formatów mogą usuwać nieobsługiwane pola; zweryfikuj to w trybie Playground
- **Brak monitu systemowego** — Claude i Gemini inaczej obsługują monity systemowe; sprawdź wynik translacji

- **GLM/ERNIE odrzuca rolę `system`** — Rozwiązano w v1.x; mechanizm normalizacji ról automatycznie scala komunikaty systemowe z komunikatami użytkownika w przypadku niezgodnych modeli. Jeśli problem nadal występuje w v3.x+, zgłoś go.
- **Rola `developer` nie jest rozpoznawana** — Rozwiązano w v1.x; w przypadku dostawców innych niż OpenAI jest automatycznie konwertowana na `system`. Jeśli problem nadal występuje w v3.x+, zgłoś go.
- **`json_schema` nie działa z Gemini** — Rozwiązano w v1.x; `response_format` jest teraz konwertowany na `responseMimeType` + `responseSchema` Gemini. Jeśli problem nadal występuje w v3.x+, zgłoś go.

## Ustawienia odporności

### Automatyczne ograniczanie szybkości nie uruchamia się

- Automatyczne ograniczanie szybkości dotyczy tylko dostawców korzystających z kluczy API (nie OAuth/subskrypcji)
- Sprawdź, czy w **Ustawienia → Odporność → Profile dostawców** włączono automatyczne ograniczanie szybkości
- Sprawdź, czy dostawca zwraca kody stanu `429` lub nagłówki `Retry-After`

### Dostrajanie wykładniczego wycofywania

Profile dostawców obsługują następujące ustawienia:

- **Opóźnienie bazowe** — Początkowy czas oczekiwania po pierwszym niepowodzeniu (domyślnie: 1s)
- **Maksymalne opóźnienie** — Górny limit czasu oczekiwania (domyślnie: 30s)
- **Mnożnik** — Stopień zwiększania opóźnienia po każdym kolejnym niepowodzeniu (domyślnie: 2x)

### Zapobieganie efektowi „thundering herd”

Gdy wiele równoczesnych żądań trafia do dostawcy z ograniczeniem szybkości, OmniRoute używa mutexu oraz automatycznego ograniczania szybkości, aby serializować żądania i zapobiegać kaskadowym awariom. W przypadku dostawców korzystających z kluczy API odbywa się to automatycznie.

### Żądania czatu kończą się błędem 503 / chat_admission_busy

**Objawy:**

- Punkt końcowy uzupełnień czatu zwraca możliwą do ponowienia odpowiedź `503`, której kod błędu to
  `chat_admission_busy`.
- Odpowiedź zawiera `Retry-After`. Od wersji #12135 wartość jest wyznaczana na podstawie zaobserwowanego
  obciążenia — jako większa z wartości: okno `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`, przez które żądanie już
  oczekiwało, oraz czas utrzymywania bieżących dzierżaw ciężkich żądań — zaokrąglona w górę do pełnych
  sekund i ograniczona do 60. Gdy brama jest bezczynna, zachowywane są historyczne wartości minimalne: 2 sekundy
  dla ścieżki opartej na bajtach i 1 sekunda dla ścieżki opartej na strukturze (która zawiera również
  `reason: "structure_limit"`).
- Może się to zdarzyć, gdy inny ciężki czat lub długotrwała odpowiedź strumieniowa jest nadal
  przetwarzana.

Treść odpowiedzi opartej na bajtach wygląda następująco:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Odpowiedź oparta na strukturze używa tego samego typu i kodu, z komunikatem
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
oraz `reason: "structure_limit"`.
Przy domyślnych progach żądanie jest uznawane za strukturalnie ciężkie, jeśli zawiera co najmniej `200` wiadomości,
co najmniej `64` narzędzia lub co najmniej `32,000` szacowanych tokenów albo gdy ograniczone szacowanie struktury
wyczerpie swoje limity wynoszące `10,000` odwiedzonych węzłów lub głębokość `12`.

**Przyczyna:** Jest to celowe odrzucanie nadmiernego obciążenia wewnątrz OmniRoute, a nie awaria dostawcy nadrzędnego.
Każdy proces używa lokalnego dla procesu mechanizmu ochronnego, aby zarezerwować ograniczoną przepustowość dla ciężkich żądań przed zachowaniem
i przeanalizowaniem dużej treści żądania. Dzierżawa ciężkiego żądania pozostaje utrzymana przez cały czas trwania odpowiedzi
SSE.

**Rozsyłanie błędów #503:** przed tą poprawką mechanizm ochronny ograniczał współbieżność do stałej LICZBY żądań
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, domyślnie `1`) niezależnie od pamięci hosta, przez co rozsyłanie zadań przez
agentów programistycznych (wiele podagentów/CLI, treści zwykle > 256 KB) ograniczało efektywną
współbieżność do ~1 i powodowało błędy 503 przy całkowicie normalnym obciążeniu. Mechanizm ochronny dostraja się teraz
automatycznie: jest kontrolowany przez automatycznie wyznaczany BUDŻET bajtów wejściowych (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), którego rozmiar
wynika z rzeczywistego limitu pamięci procesu, a także uwzględnia bieżący sygnał presji na zasoby — dzięki czemu
odrzuca żądania tylko wtedy, gdy host rzeczywiście znajduje się pod presją pamięci, a nie jedynie dlatego, że jednocześnie
nadeszło więcej niż jedno ciężkie żądanie. Stary limit liczby żądań (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) jest
nadal respektowany, ale tylko wtedy, gdy zostanie ustawiony jawnie.

Gdy przepustowość jest zajęta, ciężkie żądanie najpierw oczekuje maksymalnie przez
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (domyślnie `RATE_LIMIT_MAX_WAIT_MS`; `0` wyłącza oczekiwanie) na zwolnienie miejsca,
zanim zwrócona zostanie możliwa do ponowienia odpowiedź `503`. Ograniczone oczekiwanie istnieje po to, aby klienty działające w stylu agentów
(OpenCode, Claude Code, Cursor), które równolegle rozsyłają ciężkie podżądania, serializowały nagły wzrost obciążenia,
zamiast zużywać cały budżet ponownych prób na natychmiastowe odrzucenia i przerywać działanie w trakcie zadania.
Bieżące wykorzystanie dzierżaw ciężkich żądań, wyznaczony budżet bajtów oraz aktualny poziom presji są
widoczne pod adresem `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — sprawdź je przed zmianą jakiejkolwiek zmiennej środowiskowej.
Ustawienia → Odporność → Kolejka żądań → Równoczesne żądania nie kontroluje tego mechanizmu; to ustawienie
zarządza osobnym mechanizmem kolejki żądań dostawcy.

**Rozwiązanie:**

1. Najpierw ponów próbę. Klienty powinny respektować `Retry-After` i stosować wycofywanie zamiast natychmiast
   powtarzać żądanie.
2. Przed dostrajaniem czegokolwiek sprawdź `/api/monitoring/health` → `chatAdmission`. `countCapEnabled:
false` oraz duża wartość `maxInflightBytes` oznaczają, że automatycznie wyznaczony budżet już działa
   prawidłowo; wartość `pressureSeverity` równa `high`/`critical` oznacza, że hostowi rzeczywiście brakuje pamięci —
   tego nie da się naprawić za pomocą zmiennej środowiskowej mechanizmu dopuszczania; potrzeba więcej pamięci RAM lub mniejszego obciążenia.
3. Tylko jeśli `/api/monitoring/health` wskazuje, że automatycznie wyznaczony budżet jest rzeczywiście zbyt mały dla
   Twojego hosta (co zdarza się rzadko — jest już skalowany od kontenerów po maszyny fizyczne), nadpisz go bezpośrednio za pomocą
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, zamiast wracać do starszego limitu liczby żądań.

Autorytatywne ustawienia mechanizmu dopuszczania znajdziesz w [dokumentacji zmiennych środowiskowych](../reference/ENVIRONMENT.md#4-security--authentication).

## Opcjonalna taksonomia błędów RAG / LLM (16 problemów)

Niektórzy użytkownicy OmniRoute umieszczają bramę przed stosami RAG lub agentów. W takich konfiguracjach często można zaobserwować nietypowy schemat: OmniRoute wygląda na sprawny (dostawcy działają, profile routingu są poprawne, brak alertów o limitach szybkości), ale ostateczna odpowiedź nadal jest błędna.

W praktyce takie incydenty wynikają zazwyczaj z potoku RAG działającego za bramą, a nie z samej bramy.

Jeśli potrzebujesz wspólnego słownictwa do opisywania tych błędów, możesz użyć WFGY ProblemMap — zewnętrznego zasobu tekstowego na licencji MIT, który definiuje szesnaście powtarzających się wzorców błędów RAG / LLM. Ogólnie obejmuje on:

- dryf wyszukiwania i uszkodzone granice kontekstu
- puste lub nieaktualne indeksy i magazyny wektorowe
- niezgodność osadzeń z semantyką
- problemy ze składaniem promptów i oknem kontekstu
- załamanie logiki i odpowiedzi udzielane z nadmierną pewnością
- błędy długich łańcuchów i koordynacji agentów
- dryf pamięci i ról w systemach wieloagentowych
- problemy z kolejnością wdrażania i inicjalizacji

Zasada jest prosta:

1. Podczas badania nieprawidłowej odpowiedzi zarejestruj:
   - zadanie i żądanie użytkownika
   - trasę lub kombinację dostawców w OmniRoute
   - wszelki kontekst RAG używany w dalszym potoku (wyszukane dokumenty, wywołania narzędzi itp.)
2. Przypisz incydent do jednego lub dwóch numerów WFGY ProblemMap (`No.1` … `No.16`).
3. Zapisz numer we własnym panelu, podręczniku operacyjnym lub systemie śledzenia incydentów obok logów OmniRoute.
4. Użyj odpowiedniej strony WFGY, aby określić, czy należy zmienić stos RAG, mechanizm wyszukiwania czy strategię routingu.

Pełny tekst i konkretne procedury znajdują się tutaj (licencja MIT, wyłącznie tekst):

[README WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Możesz pominąć tę sekcję, jeśli za OmniRoute nie uruchamiasz potoków RAG ani agentów.

**Objawy:**

- „Devin CLI not found” lub „auth failed” podczas wywoływania narzędzi korzystających z Devin
- Kontrola środowiska uruchomieniowego CLI zgłasza `installed=false`

**Przyczyny:**

- `CLI_DEVIN_BIN` wskazuje ścieżkę, która nie istnieje
- Devin CLI nie jest zainstalowany na hoście

**Rozwiązanie:**

1. Zainstaluj Devin CLI dla swojej platformy
2. Ustaw `CLI_DEVIN_BIN=/usr/local/bin/devin` (lub rzeczywistą ścieżkę) w `.env`
3. Uruchom ponownie OmniRoute i przeprowadź ponowny test z poziomu **Panel → Narzędzia CLI**

### Model zablokowany w okresie oczekiwania (reset ręczny)

**Objawy:**

- Model pozostaje na liście modeli w okresie oczekiwania nawet po upływie czasu wygaśnięcia
- Żądania nadal pomijają model w routingu kombinowanym, mimo że znacznik czasu wskazuje przeszłość

**Reset ręczny:**

- **Panel:** **Ustawienia → Okresy oczekiwania modeli** → kliknij **Włącz ponownie** na karcie danego modelu
- **API:** `DELETE /api/resilience/model-cooldowns` z nagłówkami uwierzytelniania administracyjnego

### Połączenie z dostawcą Command Code kończy się błędem 403

**Objawy:**

- Błąd 403 podczas testowania połączenia z dostawcą Command Code
- Po ponownym dodaniu karta dostawcy wyświetla stan „unauthorized”

**Przyczyna:** Przepływ OAuth nie został ukończony (nie odebrano wywołania zwrotnego lub token nie został zapisany).

**Rozwiązanie:**

- Uruchom `omniroute providers` z poziomu CLI, aby ponownie rozpocząć przepływ OAuth, lub
- Ponownie uruchom OAuth z poziomu **Panel → Dostawcy → Command Code → Połącz ponownie**

### ModelScope zwraca agresywne okresy oczekiwania 429

**Objawy:**

- Bardzo krótkie lub natychmiastowe okresy oczekiwania w ModelScope po niewielkiej serii żądań
- Routing kombinowany pomija ModelScope wcześniej, niż oczekiwano

**Przyczyna:** ModelScope emituje specyficzne dla dostawcy nagłówki `Retry-After`. v3.8.0 zawiera dedykowaną obsługę tych nagłówków, dlatego starsze wersje błędnie interpretują je jako ogólne wskazówki dotyczące limitów szybkości.

**Rozwiązanie:**

- Upewnij się, że używasz v3.8.0 lub nowszej wersji
- Sprawdź, czy przełącznik `useUpstream429BreakerHints` jest włączony w sekcji **Ustawienia → Odporność**

### Brak OMNIROUTE_WS_BRIDGE_SECRET w środowisku produkcyjnym

**Objawy:**

- Błąd 401 przy każdym żądaniu do mostu WebSocket Codex/Responses podczas działania na zdalnym hoście produkcyjnym
- Uzgadnianie połączenia z mostem WebSocket zostaje zamknięte natychmiast po połączeniu

**Przyczyna:** W środowisku produkcyjnym brakuje zmiennej środowiskowej `OMNIROUTE_WS_BRIDGE_SECRET`.

**Rozwiązanie:**

1. Wygeneruj losowy sekret: `openssl rand -hex 32`
2. Ustaw `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` w środowisku serwera produkcyjnego (oraz w każdym kliencie komunikującym się z mostem)
3. Uruchom ponownie OmniRoute

### Responses API: tryb działania w tle ograniczony do trybu synchronicznego

**Objawy:**

- Zarejestrowane ostrzeżenie: `background mode degraded to synchronous`
- Żądanie `background: true` zwraca zwykłą odpowiedź synchroniczną zamiast uchwytu zadania działającego w tle

**Przyczyna:** W v3.8.0 ustawienie `background: true` w Responses API jest celowo obsługiwane przez wykonanie synchroniczne i wygenerowanie ostrzeżenia. Pełna obsługa asynchronicznego wykonywania w tle zostanie dostarczona w przyszłości.

**Rozwiązanie:**

- Dostosuj klienta tak, aby wykonywał wywołania bez `background`, lub
- Poczekaj na późniejsze wydanie zawierające pełny asynchroniczny tryb działania w tle (śledź dziennik zmian)

## Powolne uruchamianie / przekroczenie limitu czasu gotowości

Jeśli CLI wyświetla komunikat `⚠ Server did not respond within 60s`, ale serwer
w rzeczywistości działa, limit czasu sondy gotowości jest zbyt krótki dla Twojego środowiska.

Zwykle zdarza się to w systemie Windows (program antywirusowy, mechanizmy monitorowania systemu plików) lub w kontenerach
z dużym obciążeniem podczas uruchamiania.

**Rozwiązanie — zwiększ limit czasu:**

```bash
# Za pomocą zmiennej środowiskowej (obowiązuje przy kolejnych uruchomieniach):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuty
omniroute serve

# Za pomocą flagi CLI (jednorazowo):
omniroute serve --ready-timeout 180000
```

Wartość domyślna to 60 000 ms (60 s). Ostrzeżenie ma wyłącznie charakter informacyjny; serwer
nadal uruchamia się w tle i będzie dostępny po zakończeniu rozruchu.

Pełne informacje na temat `OMNIROUTE_READY_TIMEOUT_MS` znajdziesz w pliku
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
