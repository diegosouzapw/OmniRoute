Kompletny przewodnik dotyczący używania Codex CLI skonfigurowanego tak, aby korzystał z OmniRoute jako backendu zgodnego z OpenAI.

---

> **TOML jest jedynym obsługiwanym formatem.** Współczesny Codex odczytuje wyłącznie
> `~/.codex/config.toml` (zweryfikowano z codex-cli 0.147.0: `codex --help` dokumentuje
> nadpisania `-c/--config` jako „wczytywane z `~/.codex/config.toml`”). Stary plik
> `~/.codex/config.yaml` należał do starszej wersji CLI instalowanej przez npm i jest po cichu ignorowany.
> Generator w panelu (`/api/cli-tools/apply`, narzędzie `codex`) zapisuje TOML,
> ostrożnie scalając konfigurację — istniejące klucze i bloki innych dostawców są zachowywane,
> klucz API pozostaje w `OMNIROUTE_API_KEY` (nigdy w pliku), a pozostały starszy plik
> `config.yaml` jest zgłaszany jako uwaga dotycząca migracji, bez jego modyfikowania.

## Gotowy do wklejenia plik config.toml

Zastąp `<YOUR_HOST>` i `<YOUR_KEY>` własnymi wartościami:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # limit przechowywania historii dla pojedynczego wywołania narzędzia

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc lub ~/.zshrc — rzeczywista wartość klucza, nigdy w config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex dołączony do aplikacji ChatGPT

Jeśli Codex został zainstalowany za pośrednictwem aplikacji komputerowej ChatGPT, plik binarny `codex` może
znajdować się wyłącznie wewnątrz pakietu aplikacji i nie być jeszcze dostępny w zmiennej `PATH` powłoki. Dodaj
katalog zasobów do pliku uruchamianego przy starcie powłoki:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Otwórz nową powłokę, a następnie sprawdź:

```bash
command -v codex
codex --version
```

### Lokalny OmniRoute bez uwierzytelniania: wystarczy klucz zastępczy

Codex sprawdza, czy zmienna środowiskowa wskazana przez `env_key` istnieje,
**zanim** pierwsze żądanie opuści CLI. Jeśli Twoja **lokalna** instancja OmniRoute
nie wymaga uwierzytelniania, wystarczy dowolna niepusta wartość zastępcza:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Jeśli serwer OmniRoute jest chroniony lub zdalny, użyj zamiast tego prawdziwego klucza.

> **Typowe opcje hosta**
>
> | Dostęp        | URL                           |
> | ------------- | ----------------------------- |
> | Sieć lokalna  | `http://192.168.0.1:20128/v1` |
> | Tailscale     | `http://100.x.x.x:20128/v1`   |
> | Pętla zwrotna | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — dlaczego działa ze wszystkimi modelami

Codex CLI wycofał obsługę `wire_api = "chat"` (Chat Completions) w lutym 2026 roku i obecnie **wymaga** ustawienia `wire_api = "responses"` (OpenAI Responses API). Ustawienie `wire_api = "chat"` powoduje natychmiastową awarię podczas uruchamiania od wersji v0.138.

Wielu dostawców, w tym GLM i Kimi, nadal udostępnia wyłącznie punkt końcowy Chat Completions. DeepSeek V4 udostępnia obecnie natywne Responses API, a także punkt końcowy zgodny z Anthropic; OmniRoute domyślnie używa Responses i pozwala każdemu połączeniu DeepSeek wybrać zgodność z Anthropic.

**OmniRoute rozwiązuje to w sposób całkowicie transparentny:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute wybiera natywny protokół dostawcy i w razie potrzeby wykonuje translację
    → POST /responses (DeepSeek V4) lub /chat/completions (Mistral / GLM / Kimi / inni)
```

Podczas korzystania z OmniRoute nigdy nie potrzebujesz osobnego proxy translacyjnego. **Wszystkie modele używają `wire_api = "responses"`** — OmniRoute zajmuje się resztą.

> **`wire_api` jest ustawieniem domyślnym** — pole ma domyślną wartość `"responses"` i może zostać całkowicie pominięte w `config.toml`. Ustawiaj je jawnie tylko wtedy, gdy chcesz udokumentować zamierzoną konfigurację.

## Okno kontekstu i kompaktowanie

### Pola konfiguracji tokenów

| Pole                             | Opis                                                                                                                                                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Całkowity budżet tokenów dla aktywnego modelu. Ustaw na limit deklarowany dla modelu.                                                                                                                                                                   |
| `model_auto_compact_token_limit` | Próg wyzwalający automatyczne kompaktowanie historii. **Maksymalnie: 90% wartości `model_context_window`** — wartości powyżej 90% są po cichu ignorowane.                                                                                               |
| `tool_output_token_limit`        | Limit tokenów przechowywanych w historii dla wyniku pojedynczego wywołania narzędzia. Zapobiega zapełnieniu okna przez jedną dużą odpowiedź narzędzia. **Nie jest to maksymalny rozmiar danych wyjściowych** — jest to limit przechowywania w historii. |
| `compact_prompt`                 | Bezpośrednie nadpisanie monitu systemowego używanego podczas kompaktowania (v0.138+).                                                                                                                                                                   |

> **Uwaga dotycząca `model_max_output_tokens`**: To pole **nie jest częścią schematu konfiguracji Codex CLI** (nie występuje w bazie kodu Codex napisanej w języku Rust). Jeśli zostanie ustawione, jest po cichu ignorowane. Nie polegaj na nim — użyj `tool_output_token_limit`, aby kontrolować ilość danych wyjściowych narzędzi przechowywanych w historii.

## Nakład rozumowania

Określa, jak dużo model „myśli” przed udzieleniem odpowiedzi.

| Wartość  | Zastosowanie                                              |
| -------- | --------------------------------------------------------- |
| `none`   | Bez rozumowania — bezpośrednia odpowiedź                  |
| `low`    | Trywialne zadania (zmiana nazwy, formatowanie)            |
| `medium` | **Domyślna wartość serwera**, jeśli jej nie podano        |
| `high`   | Zadania średniozaawansowane (refaktoryzacja, debugowanie) |
| `xhigh`  | Architektura, dogłębna analiza, złożone problemy          |

```bash
# Nadpisanie dla pojedynczego wywołania
codex -c model_reasoning_effort=low "zmień nazwę zmiennej x na count"
codex -c model_reasoning_effort=xhigh "zaprojektuj moduł uwierzytelniania"
```

Ustaw także **podsumowanie** rozumowania, aby aplikacja Desktop mogła wyświetlać tekst procesu myślowego (a nie tylko zaszyfrowane bloki):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # lub ultra, jeśli jest obsługiwane
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### Budżet myślenia OmniRoute (ustawienie serwera)

Na hoście OmniRoute ustawienie **Settings → AI → Thinking Budget** musi mieć wartość **`passthrough`**, aby ustawienia nakładu/podsumowania Codex docierały do dostawcy nadrzędnego. Tryb **`auto` usuwa** wszystkie pola klienta `reasoning` / `reasoning_effort`, przez co panele procesu myślowego pozostają puste, nawet gdy Codex jest poprawnie skonfigurowany.

Pełny przewodnik: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Kompresja i pamięć podręczna promptów są niezależne i nadal działają w trybie `passthrough`.

## Profile — nazwane konfiguracje dla poszczególnych modeli/przepływów pracy

Profile umożliwiają zmianę modelu i okna kontekstu za pomocą jednej flagi. Każdy profil to płaski plik
`~/.codex/<name>.config.toml`, którego ustawienia są nakładane na bazowy plik `config.toml`.

> **Reguła nazewnictwa (Codex CLI v0.137+):** plik musi mieć nazwę `~/.codex/<name>.config.toml` — **bez prefiksu `profile-`**.
> CLI przekształca `-p kimi-k27` na `~/.codex/kimi-k27.config.toml`. Jeśli plik nie zostanie znaleziony, bez ostrzeżenia zastosowane zostaną ustawienia domyślne.

```bash
codex --profile kimi-k27 "przeanalizuj 10 tys. wierszy tej bazy kodu"
codex -p glm52 "przegląd architektury"
codex --profile deepseek-flash "zmień nazwę zmiennej"   # szybko, tanio
```

### Profile nakładu (ten sam model, różny nakład)

```bash
codex -p low      # cx/gpt-5.5, nakład=low
codex -p medium   # cx/gpt-5.5, nakład=medium
codex -p high     # cx/gpt-5.5, nakład=high
codex -p xhigh    # cx/gpt-5.5, nakład=xhigh (domyślnie)
codex -p chat     # cx/gpt-5.5, nakład nieustawiony (wartość domyślna serwera)
```

## Automatyczne generowanie profili za pomocą `omniroute setup-codex`

Jeśli uruchamiasz OmniRoute na serwerze VPS, możesz automatycznie wygenerować pliki profili na podstawie aktywnego katalogu modeli:

```bash
# Z serwera VPS (używa lokalnego OmniRoute na porcie 20128)
omniroute setup-codex

# Z dowolnego komputera — wskaż swój serwer VPS
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Podgląd bez zapisywania plików
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Wygeneruj tylko profile GLM i Kimi
omniroute setup-codex --only glm,kimi

# Zapisz w niestandardowym katalogu
omniroute setup-codex --codex-home /path/to/.codex
```

Polecenie pobiera `/v1/models`, używa dostrojonych profili dla znanych modeli, w przypadku innych zgodnych modeli tekstowych korzysta z metadanych katalogu i zapisuje plik `~/.codex/<name>.config.toml` dla każdego z nich. Operacja jest idempotentna — można ją bezpiecznie uruchamiać ponownie.

OmniRoute może również **automatycznie synchronizować** te same pliki profili, gdy pomyślne wykrycie lub zaimportowanie modeli dostawcy zmieni aktywny katalog. Ta funkcja jest **opcjonalna i domyślnie wyłączona**: włącz ją w panelu **CLI Code** („Automatyczna synchronizacja profili CLI” → Codex) albo ustaw `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (uwzględnia również `CLI_ALLOW_CONFIG_WRITES`, domyślnie włączone). Po włączeniu zapisuje wyłącznie oddzielne pliki profili `~/.codex/*.config.toml`; nigdy nie zmienia aktywnego/domyślnego pliku `~/.codex/config.toml`, ustawień Codex-lb, uwierzytelniania ani wyboru dostawcy.

## Długotrwałe zadania

Dwie wartości domyślne OmniRoute mogą niepostrzeżenie zakłócać wielogodzinne sesje Codex CLI. Żadna z nich nie jest ustawieniem Codex CLI — obie znajdują się po stronie OmniRoute. Użytkownicy przenoszący konfigurację z nadrzędnych serwerów proxy, które przypisują konta na stałe i wyłączają limity bezczynności, często napotykają oba problemy i dochodzą do wniosku, że OmniRoute „nie potrafi utrzymać długiej sesji”.

| Objaw                                                                                   | Prawdopodobna przyczyna                                                                                   | Ustawienie               |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------ |
| Sesja stale przełącza konta / ciągłość pamięci podręcznej promptów zanika między turami | TTL koligacji sesji wynosi `0` (wyłączony)                                                                | `sessionAffinityTtlMs`   |
| Połączenie zrywa się w trakcie rozumowania bez komunikatu widocznego dla klienta        | Mechanizm nadzorujący bezczynność strumienia zadziałał po 10 minutach bez fragmentu z serwera nadrzędnego | `STREAM_IDLE_TIMEOUT_MS` |

Powiązane dyskusje: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (przerywanie długich zadań), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (dlaczego koligacja jest domyślnie wyłączona). Śledzenie: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Koligacja sesji — przypisz jedną konwersację do jednego konta

**Domyślnie:** `sessionAffinityTtlMs = 0` (wyłączona).

**Gdzie ją ustawić**

- Panel → **Ustawienia → Routing** → **Koligacja sesji** → **TTL koligacji (sekundy)** (`ComboDefaultsTab`)
- Lub zaktualizuj ustawienia metodą PATCH, podając `sessionAffinityTtlMs` w **milisekundach** (zakres Zod `0`–`86_400_000`, tj. maksymalnie 24 godziny)

> Nazwa została zmieniona w #7274 z `codexSessionAffinityTtlMs`, przeznaczonego wyłącznie dla Codex. Starszy klucz jest nadal akceptowany jako alias tylko do odczytu; nowe konfiguracje powinny używać `sessionAffinityTtlMs`. Koligacja ma teraz zastosowanie do **każdego** dostawcy, gdy TTL jest większy niż `0`, a nie tylko do Codex — zobacz [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Koligacja sesji.

**Co przestaje działać, gdy wartość pozostaje równa 0**

Każda tura wieloturowej konwersacji Codex jest kierowana niezależnie zgodnie z aktywną strategią kombinacji i może trafić do **innego konta w każdej turze**. Powoduje to przerwanie ciągłości sesji / pamięci podręcznej promptów po stronie serwera nadrzędnego. OmniRoute uwzględnia nagłówki sesji Codex (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) oraz pola treści, takie jak `prompt_cache_key` / `session_id`, tylko wtedy, gdy TTL jest większy niż `0` (`extractSessionAffinityKey` w `src/sse/services/auth.ts`).

**Zalecenia dla pojedynczego zadania trwającego wiele godzin**

Ustaw TTL na wartość **większą niż przewidywany rzeczywisty czas trwania zadania** (maksymalna wartość w interfejsie to **86400 sekund** = 24 godziny):

| Przewidywany czas zadania | TTL koligacji (interfejs, sekundy) | `sessionAffinityTtlMs` |
| ------------------------- | ---------------------------------- | ---------------------- |
| Kilka godzin              | `14400` (4 godz.)                  | `14400000`             |
| Przez noc / ~12 godz.     | `43200` (12 godz.)                 | `43200000`             |
| Pełna doba                | `86400` (24 godz., maksimum)       | `86400000`             |

Włączenie tej funkcji jest celowo opcjonalne: wyłączenie koligacji sprzyja równoważeniu obciążenia między kontami, natomiast jej włączenie sprzyja ciągłości jednej długiej sesji agenta. Ten przewodnik **nie** zmienia wartości domyślnej — operatorzy uruchamiający długie zadania Codex muszą samodzielnie włączyć tę funkcję.

### 2. Limit czasu bezczynności strumienia — nie przerywaj tur z długimi okresami cichego rozumowania

**Domyślnie:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 minut). Jeśli zmienna nie jest ustawiona, dziedziczy wartość z `REQUEST_TIMEOUT_MS`; wspólna wartość bazowa również wynosi 600000. Zobacz [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Limity czasu.

**Co przestaje działać przy wartości domyślnej**

Tura rozumowania / użycia narzędzia Codex, która pozostaje bezczynna przez ponad 10 minut i nie otrzymuje **żadnego rzeczywistego fragmentu danych ze źródła**, jest przymusowo zamykana przez mechanizm monitorujący bezczynność SSE (`open-sse/utils/stream.ts`). Klient często widzi jedynie zerwanie połączenia — co odpowiada sytuacji „zatrzymano automatycznie bez żadnego powiadomienia”.

Istotny szczegół: syntetyczny **heartbeat SSE OmniRoute nie resetuje** licznika bezczynności. Tylko rzeczywisty fragment treści ze źródła aktualizuje `lastChunkTime`. Cichy model, który nadal „myśli”, z punktu widzenia mechanizmu monitorującego wygląda identycznie jak źródło, które przestało odpowiadać.

Powiązana bezczynność treści w Undici: `FETCH_BODY_TIMEOUT_MS` (również domyślnie korzysta z tej samej wartości bazowej wynoszącej 10 minut; `0` ją wyłącza). W przypadku streamingu `FETCH_TIMEOUT_MS` obejmuje jedynie ustanawianie połączenia / pierwsze nagłówki — po aktywowaniu strumienia przestoje są kontrolowane przez `STREAM_IDLE_TIMEOUT_MS` i `FETCH_BODY_TIMEOUT_MS`.

**Zalecane ustawienia dla pojedynczego zadania trwającego wiele godzin**

W środowisku procesu OmniRoute (`.env` / compose / systemd):

```bash
# Wyłącz limity bezczynności strumienia i treści dla długich tur rozumowania
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Możesz też zwiększyć je powyżej najdłuższej oczekiwanej przerwy bez aktywności (wartości podawane są w milisekundach):

```bash
# Przykład: zezwól na maksymalnie 2 godziny ciszy między fragmentami danych ze źródła
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Po zmianie tych zmiennych środowiskowych uruchom ponownie OmniRoute.

### Konkretna procedura — wielogodzinne zadanie Codex

1. **Przypnij konto:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12 godz.) lub `86400` (maks. 24 godz.).
2. **Zwiększ / wyłącz limity bezczynności** w środowisku OmniRoute:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Zachowaj standardową konfigurację Codex w pliku `config.toml` (`wire_api = "responses"`, prawidłowy `base_url`, `OMNIROUTE_API_KEY`) — po stronie Codex nie istnieją ustawienia koligacji sesji ani bezczynności dotyczące tych dwóch zachowań.
4. Uruchom ponownie OmniRoute, a następnie rozpocznij długie zadanie Codex.

### Decyzja dotycząca wartości domyślnych (#7287)

| Ustawienie               | Domyślna wartość  | Zmienić w tym przewodniku?                                                                                            |
| ------------------------ | ----------------- | --------------------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (wyłączone)   | **Nie** — pozostaje opcjonalne (równoważenie obciążenia a ciągłość; patrz Discussion #5718)                           |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 min) | **Nie** — pozostaje 10 minut dla zwykłego ruchu; operatorzy długich zadań Codex zwiększają ten limit lub go wyłączają |

Globalna zmiana którejkolwiek wartości domyślnej wpłynęłaby na zachowanie wszystkich klientów danej instancji, a nie tylko Codex. Należy udokumentować te ustawienia, ale pozostawić wartości domyślne bez zmian, dopóki operator nie podejmie wyraźnej decyzji o ich zmianie.

### Diagnozowanie przerwań z powodu bezczynności

Gdy mechanizm monitorujący bezczynność zostanie uruchomiony, OmniRoute zapisuje w logach wiersz o następującym formacie:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Wyszukaj za pomocą grep ciąg `Idle timeout: no data from` (albo kod `stream_idle_timeout` / nazwę błędu `StreamIdleTimeoutError`). Segment dostawcy odpowiada temu, którego OmniRoute użył dla danego żądania (`codex`, identyfikator innego dostawcy albo `provider`, jeśli dostawca jest nieznany) — nie zawsze jest to dosłownie ciąg `codex`.

## Rozwiązywanie problemów

**`Error: wire_api = "chat" is no longer supported`**
Usuń `wire_api = "chat"` z konfiguracji. Ustaw `wire_api = "responses"` lub pomiń to pole (od wersji v0.138 wartością domyślną jest `"responses"`).

**`Error: model not found`**
Sprawdź, czy model istnieje w OmniRoute i ma prawidłowy prefiks. Użyj `omniroute models list` lub otwórz `/dashboard/providers/<provider>`.

**`Authentication error`**
Upewnij się, że zmienna `OMNIROUTE_API_KEY` jest wyeksportowana: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex sprawdza przed wysłaniem pierwszego żądania, czy zmienna środowiskowa istnieje. Wyeksportuj
prawdziwy klucz dla chronionych serwerów lub niepustą wartość zastępczą, taką jak
`OMNIROUTE_API_KEY=local`, jeśli Twoja **lokalna** instancja OmniRoute nie
wymaga uwierzytelniania. Uruchom ponownie powłokę, jeśli zmienna została dodana do `~/.bashrc` lub `~/.zshrc`.

**`Connection refused`**
Sprawdź, czy OmniRoute jest uruchomiony oraz czy host i port w `base_url` są prawidłowe dla Twojej sieci (lokalnej, Tailscale lub VPS).

**Sesja ulega awarii w pobliżu limitu kontekstu**
Ustaw jawnie `model_context_window` i `model_auto_compact_token_limit`. Zobacz powyższą tabelę okna kontekstu.

**Kompaktowanie uruchamia się zbyt późno**
Zmniejsz `model_auto_compact_token_limit` do 80–85% rozmiaru okna. Nigdy nie ustawiaj wartości powyżej 90%.

**Profil nie jest wczytywany (`-p <name>` jest po cichu ignorowane)**
Upewnij się, że plik istnieje pod ścieżką `~/.codex/<name>.config.toml` (bez prefiksu `profile-`). Uruchom `ls ~/.codex/*.config.toml`.

**Długotrwałe zadanie Codex zostaje przerwane / przełącza konta między turami**
Zobacz [Długotrwałe zadania](#long-running-tasks). Włącz przypisanie sesji (TTL dłuższy niż czas trwania zadania) oraz zwiększ lub wyłącz `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`. Przeszukaj logi OmniRoute pod kątem `Idle timeout: no data from`.
