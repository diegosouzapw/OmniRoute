## Podsumowanie

OmniRoute obsługuje teraz trzy tryby przekazywania dla `/api/v1/relay/chat/completions`:

- `ts`: używa przekaźnika TypeScript w ramach procesu.
- `bifrost`: wymusza użycie bramy Bifrost.
- `auto`: preferuje Bifrost, gdy jest dostępny, a w razie awarii przełącza się na TypeScript.

Przy dużej częstotliwości żądań (duża liczba tokenów dziennie, niemal stała przepustowość) najlepszą strategią jest zapewnienie jawnej i szybkiej ścieżki awaryjnej, aby ścieżka krytyczna nigdy nie blokowała się na niedziałającym procesie pomocniczym.

## Zachowanie trybów

- `ts`
  - Najmniejsza złożoność operacyjna.
  - Całe trasowanie i sprawdzanie poprawności odbywa się w Node.
  - Dostępność nie zależy od procesu pomocniczego.
- `bifrost`
  - Wymusza przekazywanie wszystkich żądań przez bramę procesu pomocniczego.
  - Brak automatycznego przełączania awaryjnego.
  - Przydatny tylko wtedy, gdy zagwarantowane są prawidłowy stan i małe opóźnienia procesu pomocniczego.
- `auto`
  - Proces pomocniczy jest używany, gdy można się z nim połączyć i jest włączony.
  - Nieudane próby powodują dodanie nagłówków przełączenia awaryjnego i skierowanie ruchu z powrotem do TS, dzięki czemu czas pomyślnej obsługi żądania pozostaje ograniczony.
  - Ten tryb jest najbezpieczniejszym wyborem dla środowiska produkcyjnego, gdy czas dostępności jest ważniejszy niż ścisłe trasowanie wyłącznie przez proces pomocniczy.

## 9router a CLIPROXYAPI obecnie

9router i CLIPROXYAPI to integracje, które historycznie udostępniały ścieżki zgodności dla dostawców nadrzędnych.

- 9router to wbudowana ścieżka do orkiestracji dostawców nadrzędnych i obsługi zgodności.
- CLIPROXYAPI to most proxy API dla ruchu w stylu CLI / SDK.
- Bifrost jest stabilizowany jako zewnętrzna ścieżka na potrzeby dedykowanego przeskoku przez proces pomocniczy i lokalnego przekazywania z małym opóźnieniem.

Jeśli obecnie porównujesz 9router/CLIPROXYAPI:

- Zachowaj podpisywanie żądań, sprawdzanie listy dozwolonych elementów oraz bramy zasad bazy danych w trasie API przed przekazaniem żądania.
- Jeśli przepływ pracy wymaga ścisłego działania procesu pomocniczego i mniejszej zmienności między żądaniami, użyj `OMNIROUTE_RELAY_BACKEND=bifrost`.
- Jeśli potrzebujesz odporności procesu pomocniczego z łagodną degradacją podczas incydentów, użyj `OMNIROUTE_RELAY_BACKEND=auto`.

## Kontrakt granicy backendu

Stabilną granicą produktu jest API przekaźnika OmniRoute, a nie implementacja panelu. Panel Next.js może instalować, konfigurować i nadzorować usługi lokalne, ale trasowanie żądań powinno rozpoczynać się w API przekaźnika, a przekazanie powinno następować za tą granicą.

Długoterminowe opcje backendu:

- Zachowaj przekaźnik TypeScript jako działającą w ramach procesu ścieżkę zasad i przełączania awaryjnego. Uwierzytelnianie, listy dozwolonych elementów, normalizacja żądań, rozliczanie i kontrole bezpieczeństwa pozostają tutaj przed przekazaniem do dowolnego backendu.
- Używaj Bifrost jako preferowanego procesu pomocniczego Tier-1 o wysokiej przepustowości, gdy wdrożenie wymaga mniejszej zmienności trasowania, scentralizowanej rotacji dostawców lub skalowania między wieloma replikami OmniRoute.
- Zachowaj 9router i CLIPROXYAPI jako wbudowane usługi zgodności. Działają one jako nadzorowane procesy lokalne i są przydatne, gdy ich sposób obsługi dostawców/CLI jest pożądanym adapterem, ale nie powinny stawać się domyślnym mechanizmem trasowania Tier-1.
- Nie pozwalaj panelowi przekazywać dowolnych adresów URL usług do ścieżki krytycznej. Adresy URL podawane przez interfejs użytkownika są danymi konfiguracyjnymi; kod trasujący powinien rozpoznawać zarejestrowane backendy ze sprawdzonym stanem na podstawie ustawień serwerowych i stanu nadzorcy.
- Obecnie preferuj HTTP przez interfejs pętli zwrotnej dla nadzorowanych usług, ponieważ zarządzane procesy już udostępniają interfejsy API zgodne z HTTP, strażnik trasy może kontrolować tę granicę, a zachowanie w przypadku awarii i przełączania awaryjnego jest widoczne w dziennikach żądań. Dodanie w przyszłości transportu opartego na SDK lub gniazdach będzie uzasadnione tylko wtedy, gdy w mierzalny sposób zmniejszy opóźnienie trasowania p99 bez osłabiania izolacji ani semantyki przełączania awaryjnego.

Dlatego dla wdrożenia o bardzo wysokiej przepustowości domyślną odpowiedzią jest `auto` z włączonym Bifrost: używaj procesu pomocniczego Go na ścieżce krytycznej, zachowując przełączanie awaryjne na TypeScript w celu utrzymania wysokiego współczynnika powodzenia. Używaj `bifrost` tylko wtedy, gdy ścisłe działanie wyłącznie przez proces pomocniczy jest ważniejsze niż łagodna degradacja.

## Zalecenia dotyczące wysokiej przepustowości

W przypadku utrzymującego się wysokiego RPM/RPS i rygorystycznego SLO dotyczącego powodzenia:

1. Używaj `auto` z praktycznym czasem odczekania i telemetrią awarii.
2. Zachowaj weryfikację dostawców nadrzędnych i sprawdzanie kluczy API na granicy trasy TypeScript.
3. Włącz jawne nagłówki/liczniki, aby system alertów monitorował częstotliwość i przyczyny przełączeń awaryjnych.
4. Skonfiguruj limity czasu procesu pomocniczego tak, aby awaria następowała szybko, zamiast oczekiwać bez końca.
5. Utrzymuj automatyczne ponowne uruchamianie usług i pętlę telemetrii stanu w prawidłowym działaniu, aby przełączanie awaryjne było rzeczywiście wyjątkowym zdarzeniem.

## Sugerowana konfiguracja bazowa

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- Pozostaw włączone sprawdzanie kluczy API, listy dozwolonych elementów, mechanizmu oczyszczania danych i limitów częstotliwości w procedurach obsługi tras (są one zawsze wykonywane przed przekazaniem dalej).
- Eksportuj metryki przełączeń awaryjnych z odwrotnego proxy i dzienników żądań, aby awarie procesu pomocniczego były widoczne w ciągu jednej minuty.

## Kontrakt wtyczki dostawcy

Procesy pomocnicze powinny importować metadane dostawców za pośrednictwem bezpiecznego dla JSON manifestu wtyczki dostawcy, zamiast polegać na wewnętrznych mechanizmach wykonawczych TypeScript. Kontrakt kwalifikowalności procesu pomocniczego i etapy migracji opisano w dokumencie [Manifest wtyczki dostawcy](./PROVIDER_PLUGIN_MANIFEST.md).
