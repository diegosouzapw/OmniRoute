Przekaźniki (Vercel, Deno, Cloudflare) kończą połączenie z dostawcą na
backendzie serverless, dzięki czemu OmniRoute może kierować ruch wychodzący ze
stabilnego regionu, jednocześnie przechowując klucz API dostawcy po stronie
serwera. Ten dokument opisuje dwa tryby awarii występujące w środowisku
produkcyjnym oraz dostarczane przez OmniRoute sposoby ich usuwania.

## Jak przechowywane jest uwierzytelnianie przekaźnika

Gdy wdrażasz przekaźnik za pomocą opcji **Settings → Proxy Pool → Deploy Relay**,
proces wdrażania zapisuje token uwierzytelniający przekaźnika w polu JSON
`notes` serwera proxy:

- Jeśli ustawiono `STORAGE_ENCRYPTION_KEY`, token jest zapisywany jako
  `relayAuthEnc` (zaszyfrowany algorytmem AES podczas przechowywania).
- W przeciwnym razie jest zapisywany jako zwykły tekst w `relayAuth`.

Podczas obsługi żądania funkcja `extractRelayAuth(notes)` zwraca dostępną
postać tokenu, dzięki czemu przekaźnik działa również po ponownym uruchomieniu.

## Tryb awarii 1 — token niemożliwy do odszyfrowania po rotacji klucza

**Objaw:** przekaźniki, które wcześniej działały, zwracają teraz błędy
`401`/uwierzytelniania od dostawcy po rotacji zmiennej
`STORAGE_ENCRYPTION_KEY` w środowisku lub menedżerze sekretów. Zapisanego bloku
`relayAuthEnc` nie można już odszyfrować, dlatego `extractRelayAuth` zwraca
pusty ciąg, a przekaźnik nie wysyła danych uwierzytelniających.

**Rozwiązanie — naprawa w miejscu (bez ponownego wdrażania):**

1. Otwórz **Settings → Proxy Pool**.
2. Wiersze przekaźników bez danych uwierzytelniających zawierają żółtą etykietę
   `auth missing` oraz przycisk **Repair**.
3. Kliknij **Repair**. OmniRoute wywoła
   `POST /api/settings/proxies/[id]/repair-relay`, co spowoduje:
   - odszyfrowanie `relayAuthEnc` przy użyciu **bieżącego** klucza,
   - ponowne zapisanie `relayAuth` jako zwykłego tekstu w `notes`,
   - zwrócenie `{ repaired: true, mode: "recovered" }`.

Przekaźnik wznawia obsługę żądań bez konieczności ponownego wprowadzania
danych uwierzytelniających wdrożenia.

To rozwiązanie działa tylko wtedy, gdy bieżący `STORAGE_ENCRYPTION_KEY` nadal
może odszyfrować blok. Jeśli klucz został obrócony **bez** migracji, bloku nie
można odzyskać.

## Tryb awarii 2 — token niemożliwy do odzyskania (stary klucz został zastąpiony)

**Objaw:** po kliknięciu przycisku **Repair** otrzymujesz
`{ repaired: false, mode: "redeploy", status: 409 }`.

**Rozwiązanie — ponowne wdrożenie:**

Zapisanego tokenu nie można odzyskać przy użyciu bieżącego klucza. Wdróż
przekaźnik ponownie z tego samego okna modalnego, którego użyto pierwotnie
(menu **Deploy Relay** → Vercel / Deno / Cloudflare). Proces wdrażania zapisze
nowy token (zaszyfrowany przy użyciu bieżącego klucza), a etykieta
`auth missing` zniknie z wiersza.

Gdy tokenu nie można odzyskać, przycisk **Repair** w interfejsie sam otwiera
okno modalne ponownego wdrożenia, więc nie trzeba go szukać ręcznie.

## Tryb awarii 3 — przekaźnik jest osiągalny, ale działa nieprawidłowo

**Objaw:** test serwera proxy (przycisk `speed`) wskazuje, że przekaźnik jest
dostępny, ale żądania nadal sporadycznie kończą się niepowodzeniem.

Sprawdź nagłówki diagnostyczne przekaźnika zwracane przez sondę automatycznego
testu OmniRoute (zobacz **Settings → Proxy Pool** oraz liczniki `relayTested` /
`relayAlive`):

- `x-relay-url` — backend przekaźnika, który odpowiedział.
- `x-relay-mode` — `ts` | `bifrost` | `auto` dla danego żądania.
- `x-relay-attempts` — liczba wypróbowanych etapów przekaźnika przed
  powodzeniem.
- `x-relay-fallback` — `true`, gdy żądanie zostało przełączone z preferowanego
  backendu na przekaźnik TypeScript.

Wysoki odsetek `x-relay-fallback` przy niskiej wartości `relayAlive` oznacza,
że backend sidecar działa nieprawidłowo. Należy go naprawić albo zmienić
strategię backendu przekaźnika na `ts` (zobacz `RELAY_BACKEND_STRATEGY.md`).

## Dokumentacja API

| Metoda | Ścieżka                                   | Treść                   | Powodzenie                                                                                                                                | Niepowodzenie                                                                                                    |
| ------ | ----------------------------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }` po ponownym uzyskaniu; `200 { repaired: false, mode: "noop" }`, gdy zwykły tekst już istnieje | `409 { mode: "redeploy" }` — brak możliwości odzyskania; `400` — typ inny niż przekaźnik; `404` — nie znaleziono |

Trasa listy `GET /api/settings/proxies` dołącza do każdego elementu pozbawiony
sekretów obiekt `relayInfo: { isRelay, authMissing, repairMode }`, dzięki czemu
panel może wyświetlić opcję naprawy bez ujawniania tokenu.
