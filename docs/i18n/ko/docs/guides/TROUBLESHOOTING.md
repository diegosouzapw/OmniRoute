## 빠른 참조

**OmniRoute가 처음이신가요?** 여기서 시작하세요. 다음 내용으로 문제의 90%를 해결할 수 있습니다.

| 표시되는 메시지         | 의미                            | 해결 방법                                                                                                   |
| ----------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| "연결할 수 없음"        | OmniRoute가 실행되고 있지 않음  | `omniroute` 또는 `docker restart omniroute` 실행                                                            |
| "잘못된 API 키"         | 키가 잘못되었거나 만료됨        | 제공업체 웹사이트에서 키를 다시 복사                                                                        |
| "요청 한도 초과"        | 너무 많은 요청을 보내고 있음    | 1분간 기다리거나 자동 폴백을 위해 `model: "auto"` 사용                                                      |
| "할당량 초과"           | 무료/유료 할당량을 모두 사용함  | 제공업체를 더 연결하거나 무료 제공업체(Kiro, Pollinations) 사용                                             |
| "응답이 느림"           | 제공업체가 혼잡하거나 멀리 있음 | `model: "auto/fast"`를 사용하거나 더 빠른 제공업체(Groq, Cerebras) 연결                                     |
| "잘못된 제공업체 사용"  | `auto`가 다른 제공업체를 선택함 | 정상입니다! `auto`는 최적의 제공업체를 선택합니다. 특정 제공업체를 강제하려면 `model: "openai/gpt-4o"` 사용 |
| "502 잘못된 게이트웨이" | 제공업체가 중단됨               | 기다렸다가 다시 시도하거나 `model: "auto"`를 사용하여 제공업체 전환                                         |
| "401 인증되지 않음"     | 자격 증명이 잘못됨              | API 키를 확인하거나 OAuth로 다시 인증                                                                       |
| "429 너무 많은 요청"    | 요청 한도가 적용됨              | 1분간 기다리거나 제공업체를 더 연결                                                                         |

**아직 해결되지 않았나요?** 아래의 [자세한 문제 해결](#detailed-troubleshooting)을 확인하거나 [Discord](https://discord.gg/U47eFqAXCn)에서 질문하세요.

## 자세한 문제 해결

---

### 무료 제공업체의 요청 한도 제한(429 / 400 / 401)

**증상**: 인증이 필요 없는 무료 제공업체(opencode, auggie 등)에서 `model: "auto"`를 사용할 때 응답 대신 간헐적으로 `HTTP 429`, `400` 또는 `401`이 발생합니다. 잠시 후 같은 프롬프트를 다시 시도하면 요청에 성공하지만, 자동화 작업(cron 작업, 에이전트, 스크립트)은 첫 번째 실패 시 중단됩니다.

**근본 원인**: 서로 독립적인 세 가지 실패 유형이 겹쳐 발생합니다.

1. **제공업체 요청 한도(`429`)**: 무료 등급에는 시간 구간별 할당량이 적용될 수 있습니다. 병렬 호출이 한꺼번에 몰리면 할당량이 소진되어, 해당 시간 구간이 초기화될 때까지 다음 요청이 거부됩니다.
2. **패스스루의 작동하지 않는 모델(`400`/`401`)**: `auto/*` 풀에는 카탈로그에는 등록되어 있지만 유효한 자격 증명이 없는 `opencode`의 패스스루 모델이 포함될 수 있습니다(예: `oc/north-mini-code-free` → `401`). 자동 라우터가 해당 모델을 시도했다가 실패하면, 폴백이 시작되기 전에 오류가 그대로 전파됩니다.
3. **동시성 증폭(부하 상황의 `429`)**: 여러 에이전트/cron 세션이 동시에 `auto`를 호출하면 전체 요청 속도가 무료 제공업체가 허용하는 수준을 초과하여 정상적인 호출도 악성 요청으로 간주될 수 있습니다.

**검증된 해결 방법(커뮤니티 보고, 2026-08-10)**: 순환, 동시성 및 폴백이 무료 등급의 변동을 흡수하고 중단되지 않도록 다음 세 가지 환경 변수를 조정하세요.

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 발생 시 다른 모델/제공업체로 전환(작동하지 않는 패스스루 모델 건너뛰기)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # 명시적인 고부하 요청 허용 한도(기본값은 미설정: 요청 수 제한 없음, 아래 참고 사항 참조)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # 즉시 재시도 가능한 503을 반환하는 대신 고부하 요청 수용 여유가 생길 때까지 제한된 시간 동안 더 오래 대기
```

OmniRoute 프로세스 환경(예: LaunchAgent plist 또는 `systemctl edit`을 통해 설정한 데몬 환경)에 이 값들을 설정한 다음 OmniRoute를 다시 시작하세요. 순환 플래그가 가장 큰 효과를 내는 단일 설정입니다. 이 플래그는 치명적인 실패를 풀에 있는 정상 제공업체를 대상으로 투명하게 재시도하도록 바꿉니다.

**참고**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`는 동시에 실행되는 고부하 요청, 즉 긴 컨텍스트 요청의 수를 제한합니다. 이 제한은 요청 수용 게이트이지 제공업체 요청 한도 제한기가 아닙니다. **#503-fanout 업데이트:** 이 변수는 더 이상 기본값으로 설정되지 않습니다. 이제 위와 같이 명시적으로 구성한 경우에만 적용됩니다. 대신 고부하 요청 수용 여부는 호스트의 실제 메모리 한도에 따라 자동 조정되는 바이트 예산(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`)으로 제어되므로, 새 배포에서는 이 변수를 전혀 설정하지 않아도 `503 chat_admission_busy` 거부가 훨씬 적게 발생해야 합니다. 다만 여기서 명시적으로 설정하면 문서에 설명된 대로 계속 정확히 작동합니다. 명시적인 바이트 예산 재정의 값은 8 MiB~2 GiB 범위로 제한됩니다. `413 body_exceeds_budget`은 일시적인 오류가 아닙니다. 해당 바이트 예산을 늘리거나, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`를 낮추거나, 프로세스 메모리 한도를 늘리세요. `inflight_bytes_budget`으로 인한 부하 차단은 일시적인 경합이며 계속 재시도할 수 있습니다. 제공업체별 요청 한도 제한(`open-sse/services/rateLimitManager.ts`)은 `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, `RATE_LIMIT_AUTO_ENABLE`에 의해 별도로 제어됩니다. 자세한 내용은 `.env.example`을 참조하세요.

**작동 여부 확인 방법**: 에이전트/cron을 짧은 간격으로 두 번 실행하여 두 실행 모두 성공하는지 확인하세요. 수정 전에는 일반적으로 두 번째 실행에서 `429`/`401`이 발생합니다. 수정 후에는 실패가 발생하더라도 투명하게 재시도되어 호출이 완료됩니다. 또한 `curl /monitoring/health`를 실행하여 제공업체 연결의 `rateLimitedUntil` 필드와 영향을 받는 제공업체의 `circuitBreakers.providerBreakers[].state`를 확인할 수 있습니다. 상태는 `CLOSED`, `DEGRADED`, `OPEN`, `HALF_OPEN` 중 하나이며(`src/shared/utils/circuitBreaker.ts` 참조), 계속 실패하는 제공업체는 재설정 시간 구간이 프로브 요청을 허용하기 전에 `CLOSED → DEGRADED → OPEN`으로 전환되고, 이후 `HALF_OPEN` 상태가 됩니다.

**여전히 429가 표시되는 경우**: 해당 제공업체의 활성 계정이 단순히 속도 제한에 걸린 것이 아니라 실제로 _할당량_을 모두 소진한 것입니다. OmniRoute 대시보드 → Providers → Accounts에서 동일한 제공업체의 두 번째 계정을 추가하거나, 다른 무료 제공업체(예: `routeway`, `auggie`)를 함께 사용하세요. 로테이션은 일시적인 속도 제한/400/401 오류에만 도움이 됩니다. 할당량이 완전히 소진된 경우에는 두 번째 자격 증명이나 다른 제공업체가 필요합니다.

**비전 모델(`auto/vision`, `bazaarlink/*`)에서 403이 표시되는 경우**: 연결된 계정에 비전 기능이 포함된 유료 플랜이 없거나 API 키의 권한이 부족한 것입니다. 제공업체 대시보드에서 키 범위에 비전/멀티모달 권한이 포함되어 있는지 확인하거나, 유료 티어 계정을 연결하고 해당 계정을 비전 대상으로 유지하세요.

## npm install 경고 (ERESOLVE / peer / deprecated)

`npm install -g omniroute`를 실행하면 `npm warn ERESOLVE`, 피어 종속성 알림 및 `deprecated` 메시지와 같은 수많은 경고가 표시될 수 있습니다. **이는 예상된 동작이며 문제가 없습니다.** 출력에 `added <N> packages`가 표시되면 설치가 성공한 것입니다.

이러한 경고는 OmniRoute에서 제어할 수 없는 서드파티 패키지의 오래된 피어 종속성 범위로 인해 발생합니다.

1. **`marked-terminal`은 `marked >=1 <16`을 요구하지만 `marked@18`이 발견됨** — 실제로는 정상적으로 작동하며, 업스트림 피어 범위가 오래되었을 뿐입니다.
2. **`deprecated prebuild-install@7.1.3`** — 전이적으로 사용되는 네이티브 바이너리 가져오기 도우미입니다. 이는 고정된 버전의 `wreq-js` 전송 바인딩을 설치하는 데
   사용되지 않으며, 웹 쿠키 공급자 전송 설정이 실패했음을 의미하지도 않습니다.

**별도의 조치는 필요하지 않습니다** — 업스트림 패키지를 포크하지 않고는 이러한 경고를 완전히 숨길 수 없습니다.

## 백신 오탐

<a name="antivirus-false-positives"></a>

### Avast/AVG가 `README.md`를 `MD:HttpRequest-inf[Susp]`로 격리함

**이는 오탐입니다. 어떤 파일도 감염되지 않았으며, 별도의 조치가 필요하지 않습니다.**

Avast와 AVG는 HTTP 요청처럼 보이는 링크가 많이 포함된 일반 텍스트/Markdown 파일을 표시하는 휴리스틱 검사를 실행합니다. OmniRoute의 `README.md`는 npm 패키지에 포함되어 배포되므로(`package.json` → `files`에 나열됨), 전역 설치 시 `node_modules/omniroute/README.md`에 위치하게 됩니다. 이 파일에는 약 15개의 `http://localhost:20128/...` 예시(MCP HTTP/SSE 엔드포인트, A2A `.well-known` URL, `curl` 예시)가 포함되어 있습니다. 이러한 링크 밀도만으로도 휴리스틱 검사가 작동할 수 있습니다.

최근에야 이 문제가 발생하기 시작했다면, 파일의 성격 자체가 바뀐 것은 아닙니다. README의 엔드포인트 표에 MCP HTTP + SSE + A2A가 추가되고 `curl` 예시가 늘어나면서 임계값을 넘게 된 것입니다.

이 파일은 실행 가능한 콘텐츠가 전혀 없는 정적인 문서입니다. 격리된 파일을 안전하게 복원할 수 있습니다.

**조치 방법:**

1. **알림 중지** — 백신에서 설치 디렉터리를 제외 항목으로 추가하세요(Avast: 설정 → 예외). 전역 `node_modules` 경로 및/또는 OmniRoute 데이터 디렉터리(`~/.omniroute/`)를 추가하면 됩니다.
2. **오탐 신고** — <https://www.avast.com/false-positive-file-form.php>에서 격리된 `README.md`를 첨부하여 신고하세요. 텍스트 파일에 공급업체의 휴리스틱이 과민 반응하는 문제이므로, 이는 모든 사용자에게 도움이 되는 해결 방법입니다.

**프로젝트 측에서 이를 "수정"하지 않는 이유:** 모든 예시는 `http://localhost`를 사용하며, localhost에서는 자체 서명 인증서로 인한 불편 없이 `https`를 사용할 수 없습니다. 특정 공급업체의 휴리스틱을 피하려고 문서를 변형하면 스캐너 버그에 대응하기 위해 모든 독자의 사용성을 해치게 됩니다.

### Kaspersky가 데스크톱 앱을 `PDM:Trojan.Win32.Generic`으로 표시함

**이는 동작 기반 휴리스틱으로 인한 오탐입니다. 어떤 파일도 감염되지 않았습니다.** Kaspersky의 `PDM:` 접두사는 해당 판정이 알려진 멀웨어와의 일치 여부가 아니라 설치 프로그램이 _수행하는 작업_을 판단하는 Proactive Defense Module(System Watcher)에서 내려졌음을 의미합니다. 이 기능이 작동하면 Kaspersky는 전체 설치를 "롤백"하여 이미 기록한 파일까지 삭제하므로, 앱이 손상되거나 사라지게 됩니다.

표시되는 파일은 데스크톱 앱과 함께 번들로 제공되는, 명시된 오픈 소스 의존성의 표준 구성 요소입니다. 예를 들면 다음과 같습니다.

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` 및
  `workerProcessEntry.js` — 앱 내 공급자 로그인 및 브라우저 기반 채팅에 사용되는 브라우저 자동화 라이브러리인 [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — 웹 쿠키 공급자에서 브라우저 지문 기반 HTTP를 위해 사용하는 고정 버전의 `wreq-js` 네이티브 바인딩(`<arch>`는 `x64` 또는 `arm64`).

**작동 이유:** Windows 설치 프로그램은 **아직 코드 서명이 되어 있지 않으므로**, 서명되지 않은 NSIS 설치 프로그램은 평판이 전혀 없으며 동작 기반 휴리스틱이 가장 공격적인 수준으로 실행됩니다. 여기에 번들로 포함된 네이티브 DLL과 `%LOCALAPPDATA%\Programs\OmniRoute` 아래에 기록되는 수백 개의 `.js` 파일(Next.js 독립 실행형 빌드에서 생성된 해시 접미사 패키지 디렉터리 포함)이 결합되면 휴리스틱이 작동하기에 충분합니다. 코드 서명은 계획되어 있으며, 적용되기 전까지는 새 릴리스에서도 이 문제가 반복될 수 있습니다.

**조치 방법:**

1. **먼저 다운로드 파일 확인**(파일 변조 가능성을 배제). 모든 릴리스는 `latest.yml`을 게시하며, 해당 파일의 `sha512` 필드(base64)는 `OmniRoute.Setup.<version>.exe` 설치 프로그램을 대상으로 합니다. PowerShell에서 설치 프로그램이 있는 폴더로 이동한 후 다음을 실행하세요.
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   출력값은 `latest.yml` → `sha512`와 일치해야 합니다. 일치하지 않으면 파일을 삭제하고 [GitHub 릴리스 페이지](https://github.com/diegosouzapw/OmniRoute/releases)에서만 다시 다운로드하세요.
2. **복원 + 제외** — 롤백되어 격리된 항목을 복원하고 `%LOCALAPPDATA%\Programs\OmniRoute`를 제외 항목으로 추가한 다음(Kaspersky → 설정 → 위협 및 제외) 다시 설치하세요.
3. **오탐 신고** — <https://opentip.kaspersky.com/>에서 신고하세요. 사용자가 제출한 오탐 보고는 실제로 허용 목록 등록을 앞당기는 데 도움이 됩니다.

## Node.js 호환성

<a name="nodejs-compatibility"></a>

### 로그인 페이지가 중단되거나 "Module self-registration" 오류가 표시됨

**원인:** OmniRoute에서 승인한 안전한 런타임의 최소 버전 범위를 벗어난 Node.js 버전을 실행하고 있습니다. 가장 흔한 경우는 OmniRoute가 요구하는 보안 패치 최소 버전보다 낮은 이전 Node 22 또는 24 패치 버전을 실행하는 것입니다.

**증상:**

- 로그인 페이지에 빈 화면이나 서버 오류가 표시됨
- 콘솔에 `Error: Module did not self-register` 또는 이와 유사한 네이티브 바인딩 오류가 표시됨
- 런타임이 지원되는 보안 정책 범위를 벗어난 경우 로그인 페이지에 사용 중인 Node 버전과 함께 **주황색 경고 배너**가 표시됨

**해결 방법:**

1. 지원되는 Node.js LTS 릴리스를 설치합니다(권장: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. 버전을 확인합니다. `node --version`은 24.x LTS 계열에서 `v24.0.0` 이상을 표시해야 합니다
3. OmniRoute를 다시 설치합니다: `npm install -g omniroute`
4. 다시 시작합니다: `omniroute`

> **지원되는 보안 버전:** `>=22.22.2 <23` 또는 `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) 및 Node.js 26은 완전히 지원됩니다.

### npm v11+: `better-sqlite3`이 설치되지 않음(Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**원인:** npm v11(Node.js 24+에 포함됨)은 기본적으로 선택적
종속성의 설치 스크립트를 차단합니다. `better-sqlite3`은 `optionalDependencies`에
등록되어 있고 네이티브 컴파일(`node-gyp rebuild`)이 필요하므로 npm이 이를 별도의 알림 없이 건너뜁니다.

**증상:**

- 서버 시작 시 `Cannot find module 'better-sqlite3'` 오류와 함께 중단됨
- `ls node_modules/better-sqlite3` 실행 시 "No such file or directory"가 표시됨
- `npm ls better-sqlite3` 실행 시 `(empty)`가 표시됨

**해결 방법:**

1. 설치 스크립트를 승인하고 다시 설치합니다:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. 또는 사전 빌드된 패키지를 수동으로 설치합니다:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. 정상적으로 작동하는지 확인합니다: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**원인:** 전역 `npm install -g omniroute` 실행 후 패키지 내부의 `better-sqlite3` 네이티브 바이너리가 로컬에서 실행 중인 환경과 다른 아키텍처 또는 Node.js ABI용으로 컴파일되어 있을 수 있습니다. 이는 사전 빌드된 바이너리가 사용자의 환경과 일치하지 않을 때 macOS(Apple Silicon 및 Intel 모두)에서 흔히 발생합니다.

**증상:**

- 서버 시작 즉시 `dlopen` 오류와 함께 실패함
- 오류에 `slice is not valid mach-o file`이 포함됨
- 전체 예시:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**해결 방법 — 로컬 환경에 맞게 다시 빌드합니다(Node.js 다운그레이드 불필요):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **참고:** 이 작업은 로컬 Node.js 버전 및 CPU 아키텍처에 맞춰 네이티브 바인딩을 다시 컴파일하여 바이너리 불일치 문제를 해결합니다. 공식적으로 지원되는 런타임 범위는 **`>=22.22.2 <23` 또는 `>=24.0.0 <27`**입니다(`src/shared/utils/nodeRuntimeSupport.ts`의 `SUPPORTED_NODE_RANGE`, `package.json`의 `engines` 필드와 일치). Node.js 24.x LTS (Krypton) 및 Node.js 26은 `better-sqlite3` v12.x에서 완전히 지원됩니다.

## 프록시 문제

<a name="proxy-issues"></a>

### 공급자 검증 시 "fetch failed"가 표시됨

**원인:** 이전에는 API 키 검증 엔드포인트(`POST /api/providers/validate`)가 프록시 구성을 우회했기 때문에, 프록시 라우팅이 필요한 환경에서 오류가 발생했습니다.

**해결 방법(v3.5.5+):** 이제 이 문제가 해결되었습니다. 공급자 검증 요청은 `runWithProxyContext`를 통해 라우팅되며, 공급자 수준 및 전역 프록시 설정이 자동으로 적용됩니다.

### 토큰 상태 확인이 "fetch failed" 오류와 함께 실패함

**원인:** 백그라운드 OAuth 토큰 갱신 시 연결별 프록시 구성을 확인하지 않았습니다.

**해결 방법(v3.5.5+):** 이제 토큰 상태 확인 스케줄러는 갱신을 시도하기 전에 연결별 프록시 구성을 확인합니다. v3.5.5+로 업데이트하세요.

### SOCKS5 프록시에서 "invalid onRequestStart method" 오류가 반환됨

**원인:** Node.js 22에서는 undici@8 디스패처가 Node의 기본 제공 `fetch()` 구현과 호환되지 않습니다.

**해결 방법(v3.5.5+):** 이제 OmniRoute는 프록시 디스패처가 활성화된 경우 undici 자체의 `fetch()` 함수를 사용하여 일관된 동작을 보장합니다. v3.5.5+로 업데이트하세요.

### WSL의 MITM 프록시: Windows 호스트의 데스크톱 앱이 가로채지지 않음

**원인:** MITM 프록시와 해당 CA 인증서는 OmniRoute가 실행되는 환경에 설치됩니다. WSL에서는 이 환경이 Linux 게스트인 반면, AI 데스크톱 앱(Kiro, Trae, Copilot, Zed, …)은 Windows 호스트에서 실행됩니다. 호스트 앱은 게스트의 인증서 저장소를 신뢰하지 않으며 게스트의 시스템 프록시를 통해 라우팅되지 않으므로, 데스크톱 트래픽 가로채기가 작동하지 않습니다.

**권장 사항:** 가로채려는 데스크톱 앱과 동일한 OS에서 OmniRoute를 네이티브로 실행하세요(Windows 앱은 Windows에서, macOS/Linux도 마찬가지). OmniRoute를 WSL 내부에서 계속 실행하면서 호스트 앱을 대상으로 삼으려면, 생성된 CA 인증서를 Windows 호스트에서 수동으로 신뢰하도록 설정하고 각 호스트 앱의 네트워크/프록시 설정이 WSL 프록시 엔드포인트를 가리키도록 해야 합니다. 이는 지원되지 않으며 안정성이 낮은 구성입니다.

## 공급자 문제

### "Language model did not provide messages"

**원인:** 공급자 할당량이 소진되었습니다.

**해결 방법:**

1. 대시보드의 할당량 추적기 확인
2. 대체 티어가 포함된 콤보 사용
3. 더 저렴하거나 무료인 티어로 전환

### 요청 속도 제한

**원인:** 구독 할당량이 소진되었습니다.

**해결 방법:**

- 대체 경로 추가: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- GLM/MiniMax를 저렴한 백업으로 사용

### OAuth 토큰 만료

OmniRoute는 토큰을 자동으로 갱신합니다. 문제가 계속되면 다음을 수행하세요.

1. 대시보드 → 공급자 → 다시 연결
2. 공급자 연결을 삭제한 후 다시 추가

### Kiro 다중 계정: 두 번째 계정이 첫 번째 계정을 무효화함

**원인:** Kiro의 백엔드는 OIDC 클라이언트 등록당 하나의 활성 세션만 허용합니다.
두 계정이 동일하게 등록된 클라이언트를 공유하면(v3.8.0 이전에 가져온 연결),
한 계정의 토큰을 갱신할 때 다른 계정의 갱신 토큰이 무효화됩니다.

**해결 방법(v3.8.0+):** 영향을 받는 연결을 다시 가져오세요.
v3.8.0부터 **토큰 가져오기**,
**Google/GitHub 소셜 로그인** 또는 **자동 가져오기**를 통해 생성된 모든 새 Kiro 연결은 자동으로
자체 전용 OIDC 클라이언트를 등록합니다. 따라서 연결이 완전히 격리되며, 한
계정을 갱신해도 다른 계정에는 아무런 영향을 주지 않습니다.

v3.8.0 _이전_에 가져온 연결에는 연결별 클라이언트
등록이 포함되어 있지 않습니다. 이러한 연결은 계속해서 공유 소셜 인증 갱신 엔드포인트를 사용합니다.
격리를 적용하려면 대시보드 → 공급자에서 기존 연결을 삭제한 후
세 가지 가져오기 흐름 중 하나를 통해 다시 추가하세요.

두 Kiro 계정을 함께 추가하는 방법에 대한 전체 세부 정보와 단계별 지침은
[`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md)를 참조하세요.

## 클라우드 문제

### 클라우드 동기화 오류

1. `BASE_URL`이 실행 중인 인스턴스를 가리키는지 확인하세요(예: `http://localhost:20128`)
2. `CLOUD_URL`이 클라우드 엔드포인트를 가리키는지 확인하세요(예: `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` 값을 서버 측 값과 일치하도록 유지하세요

### 클라우드에서 `stream=false` 사용 시 500 반환

**증상:** 비스트리밍 호출을 위해 클라우드 엔드포인트를 사용할 때 `Unexpected token 'd'...`가 발생합니다.

**원인:** 클라이언트는 JSON을 예상하지만 업스트림에서 SSE 페이로드를 반환합니다.

**해결 방법:** 클라우드 직접 호출에는 `stream=true`를 사용하세요. 로컬 런타임에는 SSE→JSON 폴백이 포함되어 있습니다.

### 클라우드에서 연결되었다고 표시되지만 "Invalid API key"가 발생함

1. 로컬 대시보드에서 새 키를 생성하세요(`/api/keys`)
2. 클라우드 동기화를 실행하세요: 클라우드 활성화 → 지금 동기화
3. 이전 키 또는 동기화되지 않은 키는 클라우드에서 여전히 `401`을 반환할 수 있습니다

## Docker 문제

### Docker IPv6 / 연결 재설정

<a name="docker-ipv6"></a>

**증상:** `curl http://localhost:20128/v1/models`가 `curl: (56) Recv failure: Connection reset by peer`를 반환합니다. 대시보드와 인증되지 않은 엔드포인트는 작동하지만 인증된 엔드포인트는 실패합니다. 인증 문제처럼 보이지만 실제로는 그렇지 않습니다.

**원인:** `docker run -p 20128:20128`는 `0.0.0.0`(IPv4)과 `::`(IPv6) 모두에 포트를 게시하지만, 컨테이너 내부의 프로세스는 IPv4에서만 수신합니다. `localhost`가 `::1`로 먼저 해석되는 호스트에서는 연결이 뒤쪽에 리스너가 없는 IPv6 게시 포트로 전달되어 연결이 재설정됩니다.

**해결 방법:**

1. **빠른 진단:** `curl -4 http://localhost:20128/v1/models`를 실행하세요. `-4`를 사용하면 작동하지만 사용하지 않으면 실패하는 경우 IPv6 바인딩 불일치 문제가 있는 것입니다.
2. **영구적인 해결 방법:** `docker run` 명령에서 `-p 127.0.0.1:20128:20128`을 사용하여 IPv4에 명시적으로 바인딩하세요:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   이렇게 하면 IPv4 바인딩이 강제되며 모든 호스트 인터페이스에 프록시가 노출되는 것도 방지할 수 있습니다.

## 디버깅

### 로그 파일 활성화

`.env` 파일에서 `APP_LOG_TO_FILE=true`를 설정하세요. 애플리케이션 로그는 `logs/` 아래에 기록됩니다.
설정에서 호출 로그 파이프라인이 활성화된 경우 요청 아티팩트는 `${DATA_DIR}/call_logs/` 아래에 저장됩니다.
파이프라인 캡처가 활성화된 경우 스트림 청크 페이로드를 제외하려면 `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false`를 설정하거나, KB 단위의 아티팩트 크기 제한을 변경하려면 `CALL_LOG_PIPELINE_MAX_SIZE_KB`를 조정하세요.

### 제공자 상태 확인

```bash
# 상태 대시보드
http://localhost:20128/dashboard/health

# API 상태 확인
curl http://localhost:20128/api/monitoring/health
```

### 런타임 저장소

- 기본 상태: `${DATA_DIR}/storage.sqlite`(제공자, 조합, 별칭, 키, 설정)
- 사용량: `storage.sqlite`의 SQLite 테이블(`usage_history`, `call_logs`, `proxy_logs`) + 선택적 `${DATA_DIR}/call_logs/`
- 애플리케이션 로그: `<repo>/logs/...`(`APP_LOG_TO_FILE=true`인 경우)
- 호출 로그 아티팩트: 호출 로그 파이프라인이 활성화된 경우 `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

요청 로그 페이지의 **기록 정리** 작업은 `call_logs`, 레거시
`request_detail_logs`, 로컬 `${DATA_DIR}/call_logs/` 아티팩트 디렉터리를 삭제합니다.

## 서킷 브레이커 문제

### 공급자가 OPEN 상태에서 멈춤

공급자의 서킷 브레이커가 OPEN 상태이면 쿨다운이 만료될 때까지 요청이 차단됩니다.

**해결 방법:**

1. **대시보드 → 설정 → 복원력**으로 이동합니다
2. 영향을 받은 공급자의 서킷 브레이커 카드를 확인합니다
3. 모든 브레이커를 초기화하려면 **모두 초기화**를 클릭하거나 쿨다운이 만료될 때까지 기다립니다
4. 초기화하기 전에 공급자를 실제로 사용할 수 있는지 확인합니다

### 공급자가 계속 서킷 브레이커를 작동시킴

공급자가 반복적으로 OPEN 상태가 되는 경우:

1. **대시보드 → 상태 → 공급자 상태**에서 실패 패턴을 확인합니다
2. **설정 → 복원력 → 공급자 프로필**로 이동하여 실패 임계값을 높입니다
3. 공급자가 API 제한을 변경했거나 재인증이 필요한지 확인합니다
4. 지연 시간 텔레메트리를 검토합니다. 지연 시간이 길면 시간 초과로 인한 실패가 발생할 수 있습니다

## 오디오 트랜스크립션 문제

### "지원되지 않는 모델" 오류

- 지원되는 오디오 형식을 확인합니다: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`

| **채팅 테스터**    | 실시간 메시지를 전송하고 헤더를 포함한 전체 요청/응답 페이로드를 검사합니다              |
| **테스트 벤치**    | 형식 조합 전반에 걸쳐 일괄 테스트를 실행하여 어떤 변환에 문제가 있는지 찾습니다          |
| **실시간 모니터**  | 실시간 요청 흐름을 관찰하여 간헐적인 변환 문제를 포착합니다                              |

### 일반적인 형식 문제

- **사고 태그가 표시되지 않음** — 대상 공급자가 사고 기능을 지원하는지와 사고 예산 설정을 확인합니다
- **도구 호출이 누락됨** — 일부 형식 변환 과정에서 지원되지 않는 필드가 제거될 수 있습니다. 플레이그라운드 모드에서 확인합니다
- **시스템 프롬프트가 누락됨** — Claude와 Gemini는 시스템 프롬프트를 서로 다르게 처리합니다. 변환 결과를 확인합니다
- **SDK가 객체 대신 원시 문자열을 반환함** — v1.x에서 해결되었습니다. 응답 정리기가 OpenAI SDK Pydantic 유효성 검사 실패를 유발하는 비표준 필드(`x_groq`, `usage_breakdown` 등)를 제거합니다. v3.x+에서도 이 문제가 계속 발생하면 이슈를 등록해 주세요.
- **GLM/ERNIE가 `system` 역할을 거부함** — v1.x에서 해결되었습니다. 역할 정규화기가 호환되지 않는 모델에 대해 시스템 메시지를 사용자 메시지에 자동으로 병합합니다. v3.x+에서도 이 문제가 계속 발생하면 이슈를 등록해 주세요.
- **`developer` 역할이 인식되지 않음** — v1.x에서 해결되었습니다. OpenAI 이외의 공급자에서는 자동으로 `system`으로 변환됩니다. v3.x+에서도 이 문제가 계속 발생하면 이슈를 등록해 주세요.
- **Gemini에서 `json_schema`가 작동하지 않음** — v1.x에서 해결되었습니다. 이제 `response_format`이 Gemini의 `responseMimeType` + `responseSchema`로 변환됩니다. v3.x+에서도 이 문제가 계속 발생하면 이슈를 등록해 주세요.

## 복원력 설정

### 자동 속도 제한이 트리거되지 않음

- 자동 속도 제한은 API 키 제공자에만 적용됩니다(OAuth/구독에는 적용되지 않음).
- **Settings → Resilience → Provider Profiles**에서 자동 속도 제한이 활성화되어 있는지 확인하세요.
- 제공자가 `429` 상태 코드 또는 `Retry-After` 헤더를 반환하는지 확인하세요.

### 지수 백오프 조정

제공자 프로필은 다음 설정을 지원합니다.

- **기본 지연 시간** — 첫 번째 실패 후의 초기 대기 시간(기본값: 1s)
- **최대 지연 시간** — 최대 대기 시간 상한(기본값: 30s)
- **배수** — 연속 실패마다 지연 시간을 늘리는 비율(기본값: 2x)

### 동시 요청 폭주 방지

속도가 제한된 제공자에 다수의 동시 요청이 도달하면 OmniRoute는 뮤텍스와 자동 속도 제한을 사용하여 요청을 직렬화하고 연쇄적인 실패를 방지합니다. API 키 제공자에는 이 기능이 자동으로 적용됩니다.

### 채팅 요청이 503 / chat_admission_busy로 실패함

**증상:**

- 채팅 완성 엔드포인트가 오류 코드가 `chat_admission_busy`인 재시도 가능한 `503`
  응답을 반환합니다.
- 응답에 `Retry-After`가 포함됩니다. #12135부터 이 값은 관찰된 점유 상태를 바탕으로
  계산됩니다. 요청이 이미 대기한 `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` 기간과 현재
  고부하 리스가 유지된 시간 중 더 큰 값을 사용하며, 정수 초 단위로 올림하고 최대
  60으로 제한합니다. 게이트가 유휴 상태이면 기존의 최솟값을 유지합니다. 바이트 기반
  경로에서는 2초, 구조 기반 경로에서는 1초이며, 후자의 응답에는
  `reason: "structure_limit"`도 포함됩니다.
- 다른 고부하 채팅 또는 장시간 실행되는 스트리밍 응답이 아직 처리 중일 때 이런
  문제가 발생할 수 있습니다.

바이트 기반 응답 본문은 다음과 같습니다.

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

구조 기반 응답은 동일한 유형과 코드를 사용하며, 메시지는
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
이고 `reason: "structure_limit"`가 포함됩니다.
기본 임계값에서 요청에 메시지가 `200`개 이상, 도구가 `64`개 이상, 예상 토큰이
`32,000`개 이상 있거나, 제한된 구조 추정이 방문 노드 `10,000`개 또는 깊이 `12`의
한도에 도달하면 구조적으로 고부하인 요청으로 간주됩니다.

**원인:** 이는 업스트림 제공자의 장애가 아니라 OmniRoute 내부의 의도적인 부하 차단입니다.
각 프로세스는 대용량 요청 본문을 보관하고 파싱하기 전에 프로세스 로컬 가드를 사용하여
제한된 고부하 처리 용량을 예약합니다. 고부하 리스는 SSE 응답의 전체 수명 동안 유지됩니다.

**#503 팬아웃:** 이 수정 전에는 호스트 메모리와 관계없이 가드가 고정된 요청 개수
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, 기본값 `1`)로 동시성을 제한했기 때문에 코딩 에이전트
팬아웃(여러 하위 에이전트/CLI, 통상적으로 256 KB를 초과하는 본문)의 실질적인 동시성이
약 1로 떨어졌고 완전히 정상적인 부하에서도 503 오류가 발생했습니다. 이제 가드는
자체 조정됩니다. 프로세스의 실제 메모리 상한을 바탕으로 크기가 결정되는, 자동 산출된 수집
바이트 예산(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`)으로 제어되며 실시간 리소스 압력 신호도
참조합니다. 따라서 여러 고부하 요청이 동시에 도착했다는 이유만으로 차단하지 않고,
호스트에 실제로 메모리 압력이 있을 때만 차단합니다. 이전 개수 상한
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)도 계속 적용되지만 명시적으로 설정한 경우에만
적용됩니다.

용량이 사용 중이면 고부하 요청은 재시도 가능한 `503`으로 응답하기 전에 슬롯이 확보될
때까지 최대 `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`(기본값 `2000`, `0`이면 대기 비활성화) 동안
먼저 대기합니다. 이 제한된 대기는 고부하 하위 요청을 동시에 팬아웃하는 에이전트 방식
클라이언트(OpenCode, Claude Code, Cursor)가 즉시 거부되어 전체 재시도 예산을 소진하고
작업 도중 종료되는 대신 요청 폭주를 직렬화하도록 하기 위해 존재합니다.
현재 고부하 리스 점유 상태, 확정된 바이트 예산 및 실시간 압력 심각도는
`GET /api/monitoring/health` → `chatAdmission`의 (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`)에 표시됩니다. 환경 변수를 변경하기
전에 이를 확인하세요. Settings → Resilience → Request Queue → Concurrent Requests로는
이를 제어할 수 없습니다. 해당 설정은 별도의 제공자 요청 큐 메커니즘을 제어합니다.

**해결 방법:**

1. 먼저 재시도하세요. 클라이언트는 요청을 즉시 반복하지 말고 `Retry-After`를 준수하며
   백오프를 사용해야 합니다.
2. 설정을 조정하기 전에 `/api/monitoring/health` → `chatAdmission`을 확인하세요. `countCapEnabled:
false`이고 `maxInflightBytes`가 충분히 크다면 자동 산출된 예산이 이미 제대로 작동하고
   있다는 의미입니다. `pressureSeverity`가 `high`/`critical`이면 호스트의 메모리가 실제로
   부족하다는 의미입니다. 이는 어드미션 환경 변수로 해결할 수 없으며 RAM을 추가하거나
   워크로드를 줄여야 합니다.
3. `/api/monitoring/health`에서 자동 산출된 예산이 실제로 해당 호스트에 비해 너무 작다는
   것이 확인된 경우에만(드문 경우이며, 컨테이너부터 베어메탈까지 이미 자동으로 확장됨)
   레거시 요청 개수 상한으로 되돌아가는 대신 `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`를 사용하여
   직접 재정의하세요.

공식 어드미션 설정은 [환경 변수 참조](../reference/ENVIRONMENT.md#4-security--authentication)를
확인하세요.

## 선택 사항: RAG / LLM 장애 분류 체계(16가지 문제)

일부 OmniRoute 사용자는 RAG 또는 에이전트 스택 앞에 게이트웨이를 배치합니다. 이러한 구성에서는 이상한 패턴이 흔히 나타납니다. OmniRoute는 정상으로 보이지만(제공자 정상 작동, 라우팅 프로필 정상, 속도 제한 알림 없음) 최종 답변은 여전히 잘못되는 경우입니다.

실제로 이러한 문제는 대개 게이트웨이 자체가 아니라 다운스트림 RAG 파이프라인에서 발생합니다.

이러한 장애를 설명하기 위한 공통 용어가 필요하다면 WFGY ProblemMap을 사용할 수 있습니다. 이는 반복적으로 발생하는 16가지 RAG / LLM 장애 패턴을 정의한 외부 MIT 라이선스 텍스트 리소스입니다. 개략적으로 다음 항목을 다룹니다.

- 검색 편향 및 손상된 컨텍스트 경계
- 비어 있거나 오래된 인덱스 및 벡터 저장소
- 임베딩과 의미 간의 불일치
- 프롬프트 구성 및 컨텍스트 창 문제
- 논리 붕괴 및 과도하게 확신하는 답변
- 긴 체인 및 에이전트 조정 실패
- 멀티 에이전트 메모리 및 역할 편향
- 배포 및 부트스트랩 순서 문제

개념은 간단합니다.

1. 잘못된 응답을 조사할 때 다음 정보를 수집합니다.
   - 사용자 작업 및 요청
   - OmniRoute의 경로 또는 제공자 조합
   - 다운스트림에서 사용된 모든 RAG 컨텍스트(검색된 문서, 도구 호출 등)
2. 장애를 하나 또는 두 개의 WFGY ProblemMap 번호(`No.1` … `No.16`)에 매핑합니다.
3. 해당 번호를 OmniRoute 로그 옆에 있는 자체 대시보드, 런북 또는 장애 추적기에 저장합니다.
4. 해당 WFGY 페이지를 사용하여 RAG 스택, 검색기 또는 라우팅 전략 중 무엇을 변경해야 하는지 결정합니다.

전체 내용과 구체적인 해결 방법은 여기에서 확인할 수 있습니다(MIT 라이선스, 텍스트 전용).

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute 뒤에서 RAG 또는 에이전트 파이프라인을 실행하지 않는다면 이 섹션을 무시해도 됩니다.

## v3.8.0 알려진 문제

v3.8.0 릴리스에만 해당하는 문제와 현재의 해결 방법입니다. 이후 패치에 수정 사항이 포함되면 해당 항목이 업데이트되거나 제거됩니다.

### Devin CLI 인증 실패

**증상:**

- Devin 기반 도구를 호출할 때 "Devin CLI를 찾을 수 없음" 또는 "인증 실패"가 표시됨
- CLI 런타임 검사에서 `installed=false`가 보고됨

**원인:**

- `CLI_DEVIN_BIN`이 존재하지 않는 경로를 가리킴
- 호스트에 Devin CLI가 설치되어 있지 않음

**해결 방법:**

1. 사용 중인 플랫폼에 맞는 Devin CLI를 설치합니다
2. `.env`에서 `CLI_DEVIN_BIN=/usr/local/bin/devin`(또는 실제 경로)을 설정합니다
3. OmniRoute를 다시 시작하고 **Dashboard → CLI Tools**에서 다시 테스트합니다

### 모델 쿨다운이 해제되지 않음(수동 초기화)

**증상:**

- 만료 시간이 지난 후에도 모델이 계속 쿨다운 상태로 표시됨
- 타임스탬프가 과거인데도 조합 라우팅에서 해당 모델을 계속 건너뜀

**수동 초기화:**

- **대시보드:** **Settings → Model Cooldowns** → 영향을 받은 카드에서 **Re-enable**을 클릭합니다
- **API:** 관리 인증 헤더와 함께 `DELETE /api/resilience/model-cooldowns`를 호출합니다

### Command Code 제공자 연결이 403으로 실패함

**증상:**

- Command Code 제공자 연결을 테스트할 때 403이 발생함
- 새로 추가한 후 제공자 카드에 "인증되지 않음"이 표시됨

**원인:** OAuth 흐름이 완료되지 않았습니다(콜백을 받지 못했거나 토큰이 저장되지 않음).

**해결 방법:**

- CLI에서 `omniroute providers`를 실행하여 OAuth 흐름을 다시 시작하거나
- **Dashboard → Providers → Command Code → Reconnect**에서 OAuth를 다시 실행합니다

### ModelScope가 과도한 429 쿨다운을 반환함

**증상:**

- 소량의 요청이 몰린 후 ModelScope에서 매우 짧거나 즉각적인 쿨다운이 발생함
- 조합 라우팅이 예상보다 일찍 ModelScope를 건너뜀

**원인:** ModelScope는 제공자별 `Retry-After` 헤더를 전송합니다. v3.8.0에는 이러한 헤더를 위한 전용 처리 기능이 포함되어 있으므로 이전 버전에서는 이를 일반적인 속도 제한 힌트로 잘못 해석합니다.

**해결 방법:**

- v3.8.0 이상을 사용하고 있는지 확인합니다
- **Settings → Resilience**에서 `useUpstream429BreakerHints` 토글이 활성화되어 있는지 확인합니다

### 프로덕션에서 OMNIROUTE_WS_BRIDGE_SECRET 누락

**증상:**

- 원격 프로덕션 호스트에서 실행할 때 모든 Codex/Responses WebSocket 브리지 요청에서 401이 발생함
- 연결 직후 WebSocket 브리지 핸드셰이크가 종료됨

**원인:** 프로덕션 환경에 `OMNIROUTE_WS_BRIDGE_SECRET` 환경 변수가 없습니다.

**해결 방법:**

1. 무작위 비밀 값을 생성합니다: `openssl rand -hex 32`
2. 프로덕션 서버 환경 및 브리지와 통신하는 모든 클라이언트에 `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>`을 설정합니다
3. OmniRoute를 다시 시작합니다

### Responses API: 백그라운드 모드가 동기식으로 저하됨

**증상:**

- 다음 경고가 기록됨: `background mode degraded to synchronous`
- `background: true` 요청이 백그라운드 작업 핸들 대신 일반적인 동기식 응답을 반환함

**원인:** v3.8.0에서는 Responses API의 `background: true`를 의도적으로 동기식 실행으로 저하시키면서 경고를 표시합니다. 완전한 비동기 백그라운드 실행은 향후 제공될 예정입니다.

**해결 방법:**

- `background` 없이 호출하도록 클라이언트를 조정하거나
- 완전한 비동기 백그라운드 모드가 포함된 이후 릴리스를 기다립니다(변경 로그 추적)

## 느린 시작 / 준비 상태 시간 초과

CLI에 `⚠ Server did not respond within 60s`가 표시되지만 서버가 실제로 작동하고 있다면, 현재 환경에 설정된 준비 상태 프로브의 제한 시간이 너무 짧은 것입니다.

이 문제는 일반적으로 Windows(바이러스 백신, 파일 시스템 감시 프로그램) 또는 시작 시 작업 부하가 큰 컨테이너에서 발생합니다.

**해결 방법 — 제한 시간 늘리기:**

```bash
# 환경 변수를 통해 설정(시작할 때마다 유지됨):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3분
omniroute serve

# CLI 플래그를 통해 설정(일회성):
omniroute serve --ready-timeout 180000
```

기본값은 60 000ms(60초)입니다. 이 경고는 정보 제공용일 뿐이며, 서버는 백그라운드에서 계속 시작되고 부팅이 완료되면 접속할 수 있습니다.

`OMNIROUTE_READY_TIMEOUT_MS`에 대한 자세한 내용은 [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md)를 참조하세요.
