이 가이드를 사용하여 풀 리퀘스트에 적합한, 신뢰할 수 있는 최소 개발 루프를 선택하세요. 이 가이드는
아래에 링크된 영역별 아키텍처 및 보안 문서를 대체하지 않으며, 일반적인 각 변경 유형을
관련 계약, 집중 검사 및 CI 적용 범위에 연결합니다.

## 모든 변경이 따르는 경로

1. **편집하기 전에 기준 브랜치를 선택하세요.** 활성 상태인 가장 높은 `release/v*` 브랜치를 찾아 해당 브랜치의
   최신 커밋에서 브랜치를 생성하세요. `main`이 아니라 해당 브랜치를 대상으로 지정하세요. 릴리스 동결이 진행 중이라면 동결된
   브랜치를 대상으로 지정하지 말고,
   [브랜칭 및 릴리스 모델](BRANCHING_MODEL.md)에 설명된 다음 활성 주기를 사용하세요.
2. **계약을 명시하세요.** 변경의 영향을 받는 모든 카탈로그, 스키마, 생성된 산출물, 공개 API 또는 사용자
   인터페이스를 식별하세요. 아래 표는 최소 시작 항목을 제시합니다.
3. **집중 테스트를 작성하거나 업데이트하세요.** `src/`, `open-sse/`, `electron/` 또는
   `bin/`의 프로덕션 변경에는 동일한 PR에 자동화된 테스트가 필요합니다. 동작을 입증하는 최소한의 테스트 파일을
   실행한 다음, 나열된 집중 게이트를 실행하세요.
4. **광범위한 매트릭스는 CI에서 실행하세요.** 전체 단위 테스트 샤드, Vitest, 커버리지 래칫 및
   프로덕션 빌드는 PR에서 실행됩니다. 집중 테스트의 실패가 더 광범위한 영향을 시사하거나 변경이 여러
   하위 시스템에 걸쳐 있는 경우에만 광범위한 스위트를 로컬에서 실행하세요.
5. **리뷰 전에 기준 브랜치와 조정하세요.** 활성 기준 브랜치를 가져오고, 해당 브랜치의 새 커밋과 그에 대한 변경 사항을
   검사한 다음, 기여자 워크플로에 따라 기준 브랜치를 리베이스하거나 병합하세요. 생성된 파일 및
   카탈로그 충돌은 원본에서 해결하고, 다시 생성하고, 집중 루프를 다시 실행한 후 PR이 여전히
   활성 릴리스 브랜치를 대상으로 하는지 확인하세요.
6. **근거를 기록하세요.** PR 템플릿에 실행한 명령, 추가하거나 변경한 모든 테스트 파일,
   마이그레이션 또는 기능 플래그, 아직 대기 중인 CI 전용 검증을 나열하세요.

## 변경 유형별 표준 경로

아래 명령은 최소한의 집중 검사이며, 변경한 동작을 직접 검증하는 테스트를
생략해도 된다는 의미가 아닙니다.

### 공급자

**계약**

- `src/shared/constants/providers/`의 공급자 정의 및
  `src/shared/constants/providers.ts`에서의 구성.
- `open-sse/config/providerRegistry.ts` 또는 분리된 레지스트리 파일의 모델 및 기능.
- 해당하는 경우 실행기/변환기 선택, OAuth 또는 API 키 구성, 대시보드 자산 및 생성된
  공급자 참조.
- 공개 자격 증명에는 `resolvePublicCred()`를 사용해야 하며, 오류 응답에는 공유된 정제
  오류 헬퍼를 사용해야 합니다. `docs/security/PUBLIC_CREDS.md`(git에 포함되지만 `/docs`에는 컴파일되지 않음) 및
  [오류 정제](../security/ERROR_SANITIZATION.md)를 참조하세요.

**집중 루프**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # 카탈로그가 변경될 때 실행하고, 생성된 차이를 커밋하세요
npm run lint
```

영향을 받는 모든 요청 계열(chat, Responses, images, embeddings, audio 또는 video)도 테스트하세요.
생성된 카탈로그 및 골든 차이는 계약 변경으로 검토하고, 무조건 수용하지 마세요.

### 라우팅

**계약**

- `src/shared/constants/routingStrategies.ts`의 공개 전략 값 및 UI 메타데이터.
- `open-sse/services/combo.ts` 및 `open-sse/services/combo/`의 디스패치와 순서 지정.
- Combo 스키마, 영속성, 복원력 상태, 모델 기능 및 API/UI 컨트롤.
- 동작이 변경되는 경우 [Auto-Combo 엔진](../routing/AUTO-COMBO.md) 및 복원력 문서.

**집중 루프**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # 전략 또는 디스패치 변경
npm run check:known-symbols      # 전략 등록 변경
npm run lint
```

로컬에서는 결정론적으로 모킹된 업스트림 테스트를 사용하세요. 라이브 combo 스모크 테스트에는 자격 증명이 필요하며
수동으로 수행해야 하므로 CI를 대체할 수 없습니다.

### UI / UX

**계약**

- `src/app/` 및 `src/shared/components/` 아래의 Next.js 라우트/페이지 및
  공유 컴포넌트 경계.
- API 응답 형태, 로딩/빈 상태/오류 상태, 키보드 및 화면 읽기 프로그램 동작,
  반응형 레이아웃, 테마 및 로케일 확장.
- `src/i18n/messages/en.json`의 영어 UI 원본 문자열. 사용자에게 표시되는 새 문구를 하드코딩하지 마세요.

**집중 루프**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

상호작용 또는 시각적 변경의 경우 앱을 실행하고 좁은 뷰포트와 넓은 뷰포트를 모두 확인하세요. CI는
프로덕션 빌드와 더 광범위한 스위트를 실행하지만, 시각적 동작에는 여전히 변경에 적합한 집중 컴포넌트 테스트,
Playwright 테스트 또는 문서화된 수동 검사가 필요합니다.

### i18n

**계약**

- `src/i18n/messages/en.json`은 UI 원본이며, `config/i18n.json`은 로케일 원본입니다.
- CLI 카탈로그는 `bin/cli/locales/` 아래에 별도로 있습니다.
- ICU 자리표시자와 태그를 정확히 보존하세요. 제품/공급자/모델 이름,
  프로토콜 및 헤더 이름, 명령, 코드/JSON 식별자, URL, 환경 변수 또는
  `OmniRoute`, `OAuth`, `MCP`, `A2A`와 같은 보호 용어는 번역하지 마세요. 현재 원본 목록은
  `scripts/i18n/glossary/protected-terms.json`입니다.

**집중 루프**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI 문자열/카탈로그가 변경될 때
npm run lint
```

이는 기존 시스템을 위한 지침이지, 도구나 키 모델을 확장하라는 의미가 아닙니다.
대체 시스템을 설계하는 동안 i18n 패치는 필요한 부분만 정밀하게 변경하세요. 작업에서 생성된 번역을 명시적으로 요구하고
결과 차이를 검토한 경우가 아니라면 외부 서비스를 호출하는 번역 명령을 실행하지 마세요.

### CLI

**계약**

- `bin/cli/`의 공개 명령 및 플래그, 생성된 API 명령, 종료 코드, stdout/stderr 및
  JSON 출력 구조, 설정/환경 동작, 패키지에 포함된 파일.
- CLI 사용자 대상 문자열은 CLI i18n 계층을 사용해야 하며 `en`/`pt-BR` 카탈로그를 일치하도록 유지해야 합니다.
- Node를 지원 런타임으로 유지하고 게시된 바이너리 계약을 보존해야 합니다.

**집중 검증 루프**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # 생성된/번들된 CLI 변경 사항
npm run check:pack-policy     # 패키지 공개 영역 변경 사항
npm run lint
```

동작이 파싱, 파일 또는 종료 상태에 따라 달라지는 경우 임시 데이터 디렉터리에서 정확한 명령을 사용하세요. CI는 더 광범위한 패키지 아티팩트 및 생태계 검사를 수행합니다.

### 데이터베이스

**계약**

- `src/lib/db/` 아래의 도메인 모듈. 특정 모듈을 직접 가져오세요(기존 `localDb.ts` 재내보내기 계층은 제거되었습니다).
- `src/lib/db/migrations/` 아래의 번호가 지정된 멱등성 SQL 마이그레이션, 트랜잭션 안전성, 업그레이드
  동작, 인덱스 및 스키마의 영향을 받는 모든 호출자.
- 라우트와 핸들러는 절대로 원시 SQL을 직접 실행하지 않습니다.

**집중 검증 루프**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

마이그레이션을 추가할 때는 새 데이터베이스와 이전 스키마에서의 업그레이드를 모두 테스트하세요. 데이터베이스 테스트는 정리 과정에서 핸들을 닫고 `resetDbInstance()`를 호출해야 합니다. 최선형 지원인 Bun 어댑터 경로가 변경되는 경우에만 `npm run test:bun:db`를 실행하세요. Node가 여전히 기준입니다.

### 빌드 / 배포

**계약**

- 루트 및 워크스페이스 매니페스트/잠금 파일, `scripts/build/`, Next.js 독립 실행형 어셈블리, `dist/`
  패키지 콘텐츠, Electron 플랫폼 메타데이터, CI 워크플로 및 배포 센티널.
- 지원되는 Node 범위와 `CLAUDE.md`에서 허용 목록에 포함된 Bun 사용은 그대로 유지해야 합니다.
- 빌드 아티팩트는 추적하지 않으며, 종속성, 라이선스, 워크플로 및 패키지 정책이 적용됩니다.

**집중 검증 루프**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # 종속성 또는 잠금 파일 변경 사항
npm run check:pack-policy      # 게시된 패키지 공개 영역 변경 사항
npm run lint
```

변경 사항이 컴파일, 독립 실행형 어셈블리, 애셋 또는 런타임 번들링에 영향을 주는 경우에만 로컬에서 `npm run build`를 사용하세요. 릴리스/배포 검증에만 `npm run build:release`를 사용하세요. CI 빌드는 최종 크로스 플랫폼 신호입니다. 플랫폼별 Electron 변경 사항에는 해당하는 집중 빌드 또는 스모크 테스트 증거가 필요합니다.

## 로컬 후보 루프

소스 테스트만으로는 패키징된 아티팩트가 정상적으로 부팅되는지 입증할 수 없습니다. 패키징 목록, 제거된 종속성,
네이티브 바이너리와 관련된 문제는 tarball을 설치하고 시작한 후에야 드러납니다. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`)는 RFC #8084에 정의된 한 번 빌드 / 검증 / 승격 흐름의 로컬 측 구현입니다.
하나의 후보를 빌드하고, 바로 그 아티팩트를 검증한 후 디렉터리 이름 변경을 통해 승격하며, 승격된 슬롯이
상태 확인에 실패하면 롤백합니다.

```bash
npm run dev:candidate -- run --dry-run --json  # 계획만 출력하고 아무것도 변경하지 않음
npm run dev:candidate -- run                   # 빌드 + 검증 + 승격, 자동 롤백
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/에 설치
npm run dev:candidate -- validate --id <id>    # 사용 가능한 포트에서 부팅, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current와 previous 교체
npm run dev:candidate -- run --from-tarball <file.tgz>  # 다른 곳에서 빌드된 tarball 재사용(CI)
```

- **한 번만 빌드합니다.** `build`는 현재 트리를 패키징하거나(`dist/server.js`가 필요하므로 먼저
  `npm run build:release`를 실행해야 함) `--from-tarball`을 복사한 다음, tarball에는
  `node_modules`가 포함되지 않으므로 격리된 npm prefix에 설치합니다. id는 짧은 `HEAD` sha이며
  (트리에 로컬 변경 사항이 있으면 `-dirty`가 붙음), tarball의 경우 `tgz-<sha256>`입니다. 이미
  빌드된 깨끗한 id는 다시 빌드하지 않고 재사용합니다. 다시 빌드하려면 `--force`를 전달하십시오.
- **소스가 아니라 패키지를 검증합니다.** `validate`는 새로운 `DATA_DIR=<candidate>/data`, 가짜
  시크릿을 사용하고 운영자의 `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY`, `INITIAL_PASSWORD`를
  환경에서 제거한 상태로 설치된 CLI(`serve --port <free port>`)를 시작하여, 새 설치의 키 없는
  루프백 보안 상태를 확인합니다. `GET /api/health`가 200을 반환할 때까지 기다리고,
  `GET /v1/models`가 200을 반환하는지 확인한 다음 프로세스 그룹을 중지하고, tarball 해시와 함께
  판정 결과를 `validation.json`에 기록합니다.
- **동일한 아티팩트를 승격합니다.** `promote`는 현재 tarball 해시에 대한 검증을 통과하지 않은 후보의
  승격을 거부합니다. 기본 활성 슬롯은 `_artifacts/candidate/current`이며, `--target <dir>`을
  사용하면 동일한 파일 시스템의 다른 디렉터리를 선택할 수 있고 해당 디렉터리의 이전 슬롯은
  `<dir>.previous`가 됩니다. 각 이름 변경은 원자적으로 수행되며, 도중에 실패하면 이미 수행된 이름
  변경을 되돌립니다.
- **롤백합니다.** `run`은 승격된 슬롯을 다시 검증하고, 해당 확인이 실패하면 `current`와 `previous`를
  다시 교체합니다. 첫 번째 검증에 실패한 후보는 승격되지 않습니다.

모든 항목은 git에서 무시되는 `_artifacts/candidate/` 아래에 기록됩니다. 기존 OmniRoute 설치 및 해당
데이터 디렉터리는 절대 변경되지 않습니다. 승격된 CLI는
`_artifacts/candidate/current/prefix/bin/omniroute`입니다. 이를 사용할 때는 자체 `DATA_DIR`을
지정하여 시작하십시오. 종료 코드: `0` 성공, `1` 검증 또는 승격 실패, `2` 사용법 오류 또는 빌드 누락.

## 로컬 루프와 CI 비교

| 각 패치에서 로컬로 실행                                           | CI가 제공하는 광범위한 신호                         |
| ----------------------------------------------------------------- | --------------------------------------------------- |
| 위의 직접 동작 테스트 및 카테고리 게이트                          | 샤딩된 전체 단위 테스트 스위트 및 직렬 테스트       |
| `npm run lint`                                                    | Vitest 스위트 및 커버리지/품질 래칫                 |
| 영향을 받는 계약에서 요구하는 경우에만 타입 검사 또는 빌드        | 프로덕션 빌드, 보안, 문서, 종속성 및 PR 정책 게이트 |
| 자동화로 동작을 검증할 수 없는 경우에만 수동 상호작용/라이브 검사 | 워크플로에서 구성된 작업 간 통합 및 플랫폼 검사     |

집중된 로컬 루프가 성공했다는 것은 변경된 계약에 대한 증거이지, 관련 없는 CI 검사가
통과한다는 보장은 아닙니다. 반대로 로컬에서 수정할 때마다 전체 저장소 매트릭스가 완료될 때까지 기다리지 마세요.

## 조정 체크리스트

검토를 요청하기 전에 다음을 수행하세요.

- PR 베이스가 여전히 활성 상태인 `release/v*` 브랜치 중 가장 높은 버전인지 확인합니다.
- 해당 베이스를 가져오고 브랜치를 만든 이후 반영된 커밋을 검토합니다.
- `git diff <active-base>...HEAD`를 검토하여 의도하지 않은 변경이나 생성된 파일의 불필요한 변경이 있는지 확인합니다.
- 소스를 업데이트하고 출력을 다시 생성하여 카탈로그 및 생성된 문서의 충돌을 해결합니다.
- 조정 후 PR 설명에 나열된 모든 집중 테스트/게이트를 다시 실행합니다.
- 변경된 베이스에 맞추기 위해 어설션을 약화하거나 필수 테스트를 제거해서는 안 됩니다.

릴리스 동결 및 대상 변경 규칙은
[브랜칭 및 릴리스 모델](BRANCHING_MODEL.md)을 참조하세요. 전체 CI 목록은
[품질 게이트 참조](../architecture/QUALITY_GATES.md)를 참조하세요.
