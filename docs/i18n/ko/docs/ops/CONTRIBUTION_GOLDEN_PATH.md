이 가이드를 사용하여 풀 리퀘스트에 적합한, 신뢰할 수 있는 최소 개발 루프를 선택하세요. 이 가이드는
아래에 링크된 영역별 아키텍처 및 보안 문서를 대체하지 않으며, 각 일반적인
변경 유형을 관련 계약, 집중 검사 및 CI 적용 범위와 연결합니다.

## 모든 변경이 따르는 경로

1. **편집하기 전에 베이스를 선택하세요.** 활성 상태인 가장 높은 `release/v*` 브랜치를 찾아 해당 브랜치의
   최신 커밋에서 분기하세요. `main`이 아니라 해당 브랜치를 대상으로 지정하세요. 릴리스 동결이 진행 중이라면 동결된
   브랜치를 대상으로 지정하지 말고,
   [브랜칭 및 릴리스 모델](BRANCHING_MODEL.md)에 설명된 다음 활성 주기를 사용하세요.
2. **계약을 명시하세요.** 변경의 영향을 받는 모든 카탈로그, 스키마, 생성된 아티팩트, 공개 API 또는 사용자
   인터페이스를 식별하세요. 아래 표에는 최소 시작 집합이 나와 있습니다.
3. **집중 테스트를 작성하거나 업데이트하세요.** `src/`, `open-sse/`, `electron/` 또는
   `bin/`의 프로덕션 변경에는 동일한 PR에 자동화 테스트가 필요합니다. 동작을 입증하는 최소한의 테스트 파일을
   실행한 다음, 나열된 집중 게이트를 실행하세요.
4. **광범위한 매트릭스는 CI에서 실행하세요.** 전체 단위 테스트 샤드, Vitest, 커버리지 래칫 및
   프로덕션 빌드는 PR에서 실행됩니다. 집중 테스트의 실패가 더 넓은 영향을 가리키거나 변경이 여러
   하위 시스템에 걸쳐 있는 경우에만 광범위한 제품군을 로컬에서 실행하세요.
5. **리뷰 전에 동기화하세요.** 활성 베이스를 가져오고, 베이스의 새 커밋과 베이스를 기준으로 한 자신의 diff를
   검토한 다음, 기여자 워크플로에 따라 베이스를 rebase하거나 merge하세요. 생성된 파일 및
   카탈로그 충돌은 원본에서 해결하고, 다시 생성한 뒤, 집중 루프를 재실행하고, PR이 여전히 활성 릴리스 브랜치를
   대상으로 하는지 확인하세요.
6. **근거를 기록하세요.** PR 템플릿에 실행한 명령, 추가하거나 변경한 모든 테스트 파일,
   마이그레이션 또는 기능 플래그, 아직 대기 중인 CI 전용 검증을 기재하세요.

## 변경 유형별 골든 패스

아래 명령은 최소한의 집중 검사이며, 변경한 동작을 직접 다루는 테스트를 건너뛰어도 된다는
의미가 아닙니다.

### 프로바이더

**계약**

- `src/shared/constants/providers/`의 프로바이더 정의와
  `src/shared/constants/providers.ts`에서의 구성.
- `open-sse/config/providerRegistry.ts` 또는 여기서 추출된 레지스트리 파일의 모델 및 기능.
- 해당하는 경우 실행기/변환기 선택, OAuth 또는 API 키 구성, 대시보드 자산 및 생성된
  프로바이더 참조.
- 공개 자격 증명은 `resolvePublicCred()`를 사용해야 하며, 오류 응답은 공유되는 정제된
  오류 헬퍼를 사용해야 합니다. `docs/security/PUBLIC_CREDS.md`(git에 포함되지만 `/docs`로 컴파일되지 않음)와
  [오류 정제](../security/ERROR_SANITIZATION.md)를 참조하세요.

**집중 루프**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # 카탈로그가 변경될 때 실행하고 생성된 diff를 커밋
npm run lint
```

영향을 받는 모든 요청 계열도 테스트하세요: 채팅, Responses, 이미지, 임베딩, 오디오 또는 비디오.
생성된 카탈로그와 골든 diff를 계약 변경으로 검토하고, 무조건 수용하지 마세요.

### 라우팅

**계약**

- `src/shared/constants/routingStrategies.ts`의 공개 전략 값 및 UI 메타데이터.
- `open-sse/services/combo.ts` 및 `open-sse/services/combo/` 아래의 디스패치와 순서 지정.
- 콤보 스키마, 영속성, 복원력 상태, 모델 기능 및 API/UI 컨트롤.
- 동작이 변경되는 경우 [자동 콤보 엔진](../routing/AUTO-COMBO.md) 및 복원력 문서.

**집중 루프**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # 전략 또는 디스패치 변경
npm run check:known-symbols      # 전략 등록 변경
npm run lint
```

로컬에서는 결정론적인 모의 업스트림 테스트를 사용하세요. 라이브 콤보 스모크 테스트에는 자격 증명이 필요하며
수동으로 실행해야 하므로 CI를 대체할 수 없습니다.

### UI / UX

**계약**

- `src/app/` 및 `src/shared/components/` 아래의 Next.js 라우트/페이지와
  공유 컴포넌트 경계.
- API 응답 형식, 로딩/빈 상태/오류 상태, 키보드 및 화면 읽기 프로그램 동작,
  반응형 레이아웃, 테마 및 로케일 확장.
- `src/i18n/messages/en.json`의 영어 UI 원본 문자열. 사용자에게 표시되는 새로운 문구를 하드코딩하지 마세요.

**집중 루프**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

상호작용 또는 시각적 변경의 경우 앱을 실행하고 좁은 뷰포트와 넓은 뷰포트를 모두 확인하세요. CI는
프로덕션 빌드와 더 광범위한 제품군을 실행하지만, 시각적 동작에는 여전히 변경에 적합한 집중 컴포넌트 테스트,
Playwright 또는 문서화된 수동 검사가 필요합니다.

### i18n

**계약**

- `src/i18n/messages/en.json`은 UI 원본이며, `config/i18n.json`은 로케일 원본입니다.
- CLI 카탈로그는 `bin/cli/locales/` 아래에 별도로 있습니다.
- ICU 플레이스홀더와 태그를 정확히 보존하세요. 제품/프로바이더/모델 이름,
  프로토콜 및 헤더 이름, 명령, 코드/JSON 식별자, URL, 환경 변수 또는
  `OmniRoute`, `OAuth`, `MCP`, `A2A`와 같은 보호 용어를 번역하지 마세요. 현재 원본 목록은
  `scripts/i18n/glossary/protected-terms.json`입니다.

**집중 루프**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI 문자열/카탈로그가 변경될 때
npm run lint
```

이는 기존 시스템에 대한 지침이며, 도구 또는 키 모델을 확장하라는 의미가 아닙니다.
대체 시스템을 설계하는 동안 i18n 패치는 필요한 부분만 정밀하게 변경하세요. 작업에서 생성된 번역을
명시적으로 요구하고 결과 diff를 검토한 경우가 아니라면 외부 서비스를 호출하는 번역 명령을 실행하지 마세요.

### CLI

**계약**

- `bin/cli/`의 공개 명령 및 플래그, 생성된 API 명령, 종료 코드, stdout/stderr 및
  JSON 출력 구조, 설정/환경 동작, 패키지에 포함되는 파일.
- CLI 사용자 대상 문자열은 CLI i18n 계층을 사용해야 하며 `en`/`pt-BR` 카탈로그를 일치시켜야 합니다.
- Node를 지원 런타임으로 유지하고 게시된 바이너리 계약을 보존합니다.

**집중 검증 루프**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # 생성되거나 번들링된 CLI 변경 사항
npm run check:pack-policy     # 패키지 공개 영역 변경 사항
npm run lint
```

동작이 파싱, 파일 또는 종료 상태에 따라 달라지는 경우 임시 데이터 디렉터리에서 정확한 명령을 사용하세요.
CI는 더 광범위한 패키지 아티팩트 및 생태계 검사를 수행합니다.

### 데이터베이스

**계약**

- `src/lib/db/` 아래의 도메인 모듈. 특정 모듈을 직접 가져오세요(기존 `localDb.ts` 재내보내기 계층은 제거되었습니다).
- `src/lib/db/migrations/` 아래의 번호가 지정된 멱등성 SQL 마이그레이션, 트랜잭션 안전성, 업그레이드
  동작, 인덱스 및 스키마의 영향을 받는 모든 호출자.
- 라우트 및 핸들러는 원시 SQL을 직접 실행하지 않습니다.

**집중 검증 루프**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

마이그레이션을 추가할 때는 새 데이터베이스와 이전 스키마로부터의 업그레이드를 모두 테스트하세요. 데이터베이스 테스트는
정리 중에 핸들을 닫고 `resetDbInstance()`를 호출해야 합니다. 최선형 지원인 Bun 어댑터 경로가 변경될 때만
`npm run test:bun:db`를 실행하세요. Node가 계속 기준 구현입니다.

### 빌드 / 배포

**계약**

- 루트 및 워크스페이스 매니페스트/잠금 파일, `scripts/build/`, Next.js 독립 실행형 어셈블리, `dist/`
  패키지 내용, Electron 플랫폼 메타데이터, CI 워크플로 및 배포 센티널.
- 지원되는 Node 버전 범위와 `CLAUDE.md`에서 허용 목록에 포함된 Bun 사용은 그대로 유지해야 합니다.
- 빌드 아티팩트는 추적하지 않으며 종속성, 라이선스, 워크플로 및 패키지 정책을 적용합니다.

**집중 검증 루프**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # 종속성 또는 잠금 파일 변경 사항
npm run check:pack-policy      # 게시된 패키지 공개 영역 변경 사항
npm run lint
```

변경 사항이 컴파일, 독립 실행형 어셈블리, 애셋 또는 런타임 번들링에 영향을 미치는 경우에만 로컬에서 `npm run build`를 사용하세요.
릴리스/배포 검증에만 `npm run build:release`를 사용하세요. CI 빌드는 최종 크로스 플랫폼 신호이며,
플랫폼별 Electron 변경에는 해당하는 집중 빌드 또는 스모크 테스트 증거가 필요합니다.

## 로컬 루프와 CI 비교

| 각 패치에서 로컬로 실행                                                | CI가 제공하는 광범위한 신호                         |
| ---------------------------------------------------------------------- | --------------------------------------------------- |
| 위의 직접 동작 테스트 및 카테고리 게이트                               | 샤딩된 전체 단위 테스트 스위트 및 직렬 테스트       |
| `npm run lint`                                                         | Vitest 스위트 및 커버리지/품질 래칫                 |
| 영향을 받는 계약에서 요구하는 경우에만 타입 검사 또는 빌드 수행        | 프로덕션 빌드, 보안, 문서, 종속성 및 PR 정책 게이트 |
| 자동화로 동작을 입증할 수 없는 경우에만 수동 상호작용/라이브 검사 수행 | 워크플로에 구성된 작업 간 통합 및 플랫폼 검사       |

집중된 로컬 루프의 통과는 변경된 계약에 관한 근거일 뿐, 관련 없는 CI 검사가
통과할 것이라는 증거는 아닙니다. 반대로, 모든 로컬 편집이 전체 저장소 매트릭스를 기다리게 하지 마세요.

## 조정 체크리스트

리뷰를 요청하기 전에 다음을 확인하세요.

- PR 베이스가 여전히 가장 높은 활성 `release/v*` 브랜치인지 확인합니다.
- 해당 베이스를 가져오고 브랜치를 만든 이후 반영된 커밋을 검토합니다.
- 의도하지 않은 변경이나 생성된 파일의 불필요한 변동이 있는지 `git diff <active-base>...HEAD`를 검토합니다.
- 소스를 업데이트하고 출력을 다시 생성하여 카탈로그 및 생성된 문서의 충돌을 해결합니다.
- 조정 후 PR 설명에 나열된 모든 집중 테스트/게이트를 다시 실행합니다.
- 변경된 베이스에 맞추기 위해 어설션을 약화하거나 필수 테스트를 제거하지 마세요.

릴리스 동결 및 리타기팅 규칙은
[브랜칭 및 릴리스 모델](BRANCHING_MODEL.md)을 참조하세요. 전체 CI 목록은
[품질 게이트 참조](../architecture/QUALITY_GATES.md)를 참조하세요.
