## 개요

모든 OmniRoute 관리 API 경로는 세 가지 보호 계층 중 하나로 분류됩니다. 분류는 정적이며 `src/server/authz/routeGuard.ts`에 정의되어 있고, 다른 모든 인증 분기가 실행되기 전에 평가됩니다.

## 계층

### 계층 1 — LOCAL_ONLY

**적용 방식:** `isLocalOnlyPath(path)` → 루프백 호스트 검사  
**우회:** 기본적으로 없음. 요청에 `manage` 범위가 포함된 유효한 API 키가 있는 경우 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`에 속하는 경로에 한해 제한적으로 예외가 적용됩니다([관리 범위 예외](#manage-scope-carve-out) 참조).

이 경로들은 자식 프로세스를 생성하거나 런타임 코드를 실행합니다. 이를 비루프백 트래픽에 노출하면 유효한 JWT를 획득한 공격자(예: Cloudflared/Ngrok 터널을 통해 획득)가 프로세스 생성을 유발할 수 있습니다. 이는 알려진 CVE 유형입니다([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj의 의미(공격 유형):** 관리/에이전트 서버가 하위 프로세스(`npm install`, `node`, 브라우저, 프록시, `git`, `tar`, …)를 실행하는 엔드포인트를 노출합니다. 운영자가 OmniRoute를 nginx/Cloudflare/Tailscale 터널 뒤에 배치한 상태에서 JWT가 유출되거나 인증이 잘못 구성되어 해당 엔드포인트에 호스트 외부에서 접근할 수 있게 되면, 공격자는 "API 호출"을 "호스트에서 명령 실행"으로 바꿀 수 있습니다(원격 코드 실행). OmniRoute는 프로세스 생성이 가능한 모든 경로에서 **인증 검사 전에 항상 루프백 호스트 검사를 적용**하여 이를 차단합니다. 따라서 터널을 통해 토큰이 유출되더라도 프로세스 생성 기능에는 접근할 수 없습니다.

**전체 LOCAL_ONLY 집합.** 기준이 되는 공식 소스는 `src/server/authz/routeGuard.ts`의 `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`이며, 아래 표는 현재 상태를 그대로 반영합니다. `check-route-guard-membership` 게이트는 프로세스 생성이 가능한 접두사 아래의 모든 `route.ts`를 열거하며, 그중 하나라도 로컬 전용으로 분류되지 않은 경우 CI를 실패 처리합니다.

#### 관리 범위 예외

LOCAL_ONLY 경로 중 일부는 요청에 `manage` 범위(또는 `admin`)가 메타데이터에
포함된 `Authorization: Bearer <api-key>`가 있는 경우에만 루프백이 아닌
주소에서도 접근할 수 있습니다. 이 예외는 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`를
통해 경로별로 명시적으로 제한되므로, 새로 추가되는 모든 LOCAL_ONLY 경로의
기본값은 계속 엄격한 루프백 전용입니다. 인증되지 않은 요청과 `manage` 권한이
없는 키를 사용한 요청은 여전히 `403 LOCAL_ONLY`로 거부됩니다.

현재 우회 가능한 접두사는 `/api/mcp/`뿐입니다. `/api/cli-tools/runtime/`과
`/api/services/`는 임의의 하위 프로세스(`npm install`, `node`)를 실행할 수
있으므로 의도적으로 제외됩니다. 이는 바로 LOCAL_ONLY 계층이 방지하기 위해
존재하는 CVE 유형입니다.

**#7895 — `mcp:connect`의 제한된 범위:** `/api/mcp/` 예외는
제한된 `mcp:connect` 범위를 보유한 Bearer 키도 허용합니다
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`). 이 검사는
`src/server/authz/policies/management.ts`의 `hasMcpConnectOrManageScope()`를
통해 수행됩니다. 이는 `/api/mcp/`에만 한정됩니다. `mcp:connect`는 다른
어떤 관리 경로에서도 권한을 부여하지 않으며(향후 추가될 수 있는 다른 모든
LOCAL_ONLY 우회 접두사 포함), 의도적으로 `MANAGEMENT_API_KEY_SCOPES`에서
제외됩니다. `manage`/`admin`을 보유한 키는 이전과 동일하게 이 예외를
통과합니다. `mcp:connect`는 광범위한 관리 액세스가 필요하지 않은 원격
MCP 전용 호출자를 위한 더 낮은 권한의 대안입니다.

| 요청                                           | 경로                       | 결과              |
| ---------------------------------------------- | -------------------------- | ----------------- |
| 비루프백, Bearer 없음                          | `/api/mcp/*`               | 403 LOCAL_ONLY    |
| 비루프백, `manage` 범위가 있는 Bearer          | `/api/mcp/*`               | 허용              |
| 비루프백, `mcp:connect` 범위가 있는 Bearer     | `/api/mcp/*`               | 허용              |
| 비루프백, `manage`/`mcp:connect`가 없는 Bearer | `/api/mcp/*`               | 403 LOCAL_ONLY    |
| 비루프백, `mcp:connect` 범위가 있는 Bearer     | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY    |
| 비루프백, `manage` 범위가 있는 Bearer          | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY    |
| 루프백, Bearer 유무와 무관                     | 모든 LOCAL_ONLY            | 허용(게이트 통과) |

#### 운영자 지침 및 감사

OmniRoute를 역방향 프록시나 터널(nginx, Caddy, Cloudflare Tunnel, Tailscale,
Ngrok) 뒤에서 실행하더라도 루프백 검사는 위의 프로세스 실행 가능 경로를 계속
보호합니다. 클라이언트 주소가 루프백이 아닌 요청은 **인증이 실행되기 전에**
`403 LOCAL_ONLY`로 거부되므로, JWT가 유출되더라도 프로세스 실행에 도달할 수
없습니다. 운영자에게는 다음 두 가지 책임이 남습니다.

- **클라이언트 IP를 루프백으로 위조해 403을 "수정"하지 마십시오.**
  `X-Forwarded-For: 127.0.0.1`로 설정하거나 소스 주소를 루프백으로 다시 쓰는
  프록시를 사용하면 이 계층이 차단하는 바로 그 RCE 유형을 다시 허용하게
  됩니다. 프록시를 통해 대시보드/API를 노출하되, 프로세스 실행 가능 경로는
  절대로 노출하지 마십시오.
- **관리 범위 우회를 최소한으로 유지하십시오.** 우회 가능한 것은
  `/api/mcp/`뿐이며, `manage` 범위의 API 키가 있어야 합니다.
  `SPAWN_CAPABLE_PREFIXES`는 절대로 우회 목록에 추가할 수 없습니다. zod
  스키마가 이를 거부하고 `isLocalOnlyBypassableByManageScope`가 런타임에
  이를 차단하는데(심층 방어), 이것이 대시보드에서 "우회 가능하게 만들 수
  없음"이라고 표시하는 의미입니다. `/api/providers/` 아래에서 동적 세그먼트와
  정적 경로를 사용하는 프로세스 실행 가능 라우트(예: `/login`,
  `/refresh-cursor`)는 단순 `SPAWN_CAPABLE_PREFIXES` 배열이 아니라
  `src/shared/constants/spawnCapablePrefixes.ts`의 정규식 기반
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` 보조 항목으로
  처리됩니다. 단순 배열로 이를 포착하려면 전체 `/api/providers/` 접두사를
  포함해야 하며, 그렇게 하면 원격 대시보드가 공급자 CRUD에 정당하게 사용하는
  라우트 트리까지 지나치게 광범위하게 제한하게 됩니다.

**액세스 감사** — 호스트 외부에서 이러한 라우트에 접근하지 못하고 있는지 확인하려면:

- `/dashboard/settings/security`에서 **인증 인벤토리**를 여세요. 여기에는 실시간 LOCAL_ONLY 접두사 목록, 우회 가능한 접두사, 그리고 컴파일 시점에 결정되는 프로세스 생성 가능("우회 가능하게 만들 수 없음") 집합이 표시됩니다.
- 위 접두사와 비루프백 클라이언트 주소가 함께 나타나는지 리버스 프록시/액세스 로그를 grep으로 검색하세요. 이러한 요청이 `403 LOCAL_ONLY` 대신 `200`을 반환했다면 프록시가 실제 클라이언트 IP를 숨기고 있다는 의미이므로 프록시를 수정하세요.
- 이러한 경로 중 하나에 대해 OmniRoute 로그에 기록된 `403 LOCAL_ONLY`는 가드가 의도대로 작동한 결과이지, 억제해야 할 오류가 아닙니다.

### 티어 2 — ALWAYS_PROTECTED

**적용 주체:** `isAlwaysProtectedPath(path)` → `requireLogin=false` 우회 건너뛰기
**우회:** `requireLogin=false`인 경우에도 없음. JWT가 항상 필요함

이러한 라우트는 파괴적이거나 되돌릴 수 없는 작업을 수행합니다. "비밀번호 없음"으로 설치된 환경에서 이를 허용하면 같은 LAN에 있는 누구나 데이터베이스를 삭제하거나 서버 프로세스를 종료할 수 있습니다.

| 경로                                      | 이유                                                                  |
| ----------------------------------------- | --------------------------------------------------------------------- |
| `/api/shutdown`                           | 서버 프로세스를 종료함                                                |
| `/api/settings/database`                  | 데이터베이스 내보내기, 가져오기 및 삭제                               |
| `/api/db-backups`                         | 전체 데이터베이스 백업 아카이브 액세스                                |
| `/api/settings/export-json`               | 전체 설정 블롭 내보내기(비밀 포함)                                    |
| `/api/settings/import-json`               | 전체 설정 블롭 교체                                                   |
| `/api/providers/health-autopilot/actions` | 자동 복구 작업 실행                                                   |
| `/api/settings/obsidian`                  | 임의의 볼트 루트에 사용할 수 있는 재사용 가능한 WebDAV 자격 증명 발급 |

**위반 시 응답:** `401 Authentication required`

`/api/settings/obsidian`은 하위 경로인 `/webdav`도 포괄합니다. `POST`는 이 파이프라인 외부에서 Next.js보다 먼저 커스텀 Node 계층이 제공하는 WebDAV 파일 서비스가 호출자가 선택한 루트를 가리키도록 하고, 새로 발급된 Basic 자격 증명을 응답으로 반환합니다. `DELETE`는 해당 자격 증명을 교체하며, 상위 경로의 `POST`는 Obsidian REST API 토큰을 저장합니다. GHSA-62vw는 `GET`을 통한 비밀번호 노출만 차단했으며, 발급 기능은 여전히 장애 시 허용되는 티어에 있었습니다(GHSA-7pq4-8pvv-rx7r). 또한 `enableObsidianVaultSync()`는 데이터 디렉터리 자체이거나, 그 내부에 있거나, 데이터 디렉터리를 포함하는 볼트를 거부합니다.

### 신규 설치 부트스트랩은 루프백 전용 — `Host`가 아닌 실제 피어 기준

관리 비밀번호가 구성되어 있지 않고 `INITIAL_PASSWORD`도 없는 경우, `src/shared/utils/apiAuth.ts`의 `isAuthRequired()`는 **루프백 피어에 대해서만** 익명 부트스트랩을 열린 상태로 유지합니다. 루프백 여부는 신뢰할 수 있는 다음 피어 신호를 순서대로 사용하여 결정합니다. 토큰이 스탬프된 실제 TCP 피어(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, 정책에서 확인하는 값), 파이프라인 자체의 `AUTHZ_HEADER_PEER_LOCALITY` 판정(라우트 핸들러에서 확인하는 값이며 `OMNIROUTE_PEER_STAMP_TOKEN`이 설정된 동안에만 신뢰함), 또는 직접 호출자의 실제 소켓 피어입니다. `Host` / `nextUrl.hostname`은 절대 참조하지 않으며, 최초 비밀번호 설정(`POST /api/settings/require-login`)에도 모든 네트워크 피어에 개방하는 대신 동일한 제약이 적용됩니다(GHSA-7pq4-8pvv-rx7r). `managementPolicy`는 자체 `peerContext` 판정을 명시적으로 하위 계층에 전달하므로, ORIGINAL(제거 전) 요청의 헤더가 이를 결정하는 일은 없습니다.

### 티어 3 — MANAGEMENT(기본값)

그 밖의 모든 관리 라우트입니다. `requireLogin=false`로 구성하지 않는 한 인증이 필요합니다. CLI 토큰으로 이러한 라우트를 인증할 수 있습니다(루프백 + 유효한 HMAC).

## 평가 순서

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → 루프백                                  → 다음 단계로 진행
     → 비루프백, manage 범위 Bearer
        AND isLocalOnlyBypassableByManageScope   → 허용 (management_key)
     → 그 외                                    → 거부 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → 허용 (system)
  3. hasValidCliToken(headers)?
     → 허용 (cli) [루프백 + timingSafeEqual HMAC 검사]
  4. isAlwaysProtectedPath(path) 또는 requireLogin=true?
     → isDashboardSessionAuthenticated?
        → 허용 (dashboard_session)
     → 우회할 수 없는 경로에서 manage 범위 Bearer?
        → 허용 (management_key)
     → 거부 401/403
  5. requireLogin=false?
     → 허용 (anonymous)
```

1단계의 manage 범위 분기만이 LOCAL_ONLY 경로를 충족할 수 있는 유일한 인증 경로입니다. 인증 백엔드 실패 시 만료된 DB로 인해 조용히 "거부"로 강등되지 않도록 403이 아닌 503을 반환합니다.

## OpenAPI에서 보안 계층 문서화

`docs/openapi.yaml`에 새 경로를 추가할 때, 해당 경로가 `routeGuard.ts`에 의해 분류되는 경우 그에 해당하는 벤더 확장을 적용하세요.

| routeGuard.ts 분류           | YAML 주석                  | 적용 방식                                    |
| ---------------------------- | -------------------------- | -------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | 비루프백에서 무조건 차단                     |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | `requireLogin=false`인 경우에도 인증 필요    |
| 내부 관리자/디버그 경로      | `x-internal: true`         | 기본적으로 /dashboard/api-endpoints에서 숨김 |
| 없음(공개/표준 인증)         | (주석 불필요)              | 표준 `requireLogin` 제어 접근                |

### 검증

두 스크립트가 YAML 주석과 `routeGuard.ts` 간의 일관성을 강제합니다.

- `scripts/check/check-openapi-coverage.mjs` — 커버리지가 99% 미만이면 실패
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` 또는
  `x-always-protected` 주석이 컴파일 타임 상수와 일치하지 않으면 실패

두 스크립트 모두 pre-commit 훅과 CI에서 실행됩니다.

### 오탐 규칙

`routeGuard.ts` 상수에 포함되지 않은 경로에 `x-always-protected` 또는 `x-loopback-only`가 지정되어 있으면 커버리지 스크립트가 실패합니다. 해결 방법은 항상 YAML을 `routeGuard.ts`에서 실제로 적용하는 내용에 맞추는 것입니다. 적용 로직도 구현하지 않은 채 경로를 `routeGuard.ts`에 추가해서는 안 됩니다.
