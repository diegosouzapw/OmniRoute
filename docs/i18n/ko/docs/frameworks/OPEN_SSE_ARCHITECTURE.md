> **요약**: `open-sse/`는 OmniRoute의 모든 LLM 요청을 처리하는 핵심 스트리밍 엔진입니다. 요청 파이프라인, 실행기, 서비스, MCP 서버 및 변환 계층을 구현하는 약 1,400개의 파일로 구성되어 있습니다. 이 가이드에서는 각 구성 요소가 어떻게 연동되는지 설명합니다.

**소스:** `open-sse/`(워크스페이스 패키지, 테스트를 제외한 `.ts` 파일 약 1,440개)

---

## 별도의 워크스페이스 패키지를 사용하는 이유

`open-sse/`는 다음과 같은 여러 이유로 OmniRoute 모노레포에서 **독립형 워크스페이스**로 구성됩니다.

1. **재사용성** — `open-sse`는 npm에 `@omniroute/open-sse`로 게시되므로 다른 프로젝트에서도 독립적으로 사용할 수 있습니다
2. **명확한 경계** — 스트리밍 엔진이 OmniRoute 전용 UI/DB 계층과 분리되어 있습니다
3. **성능** — 엔진에 Next.js 종속성이 없어 CLI/서버리스 환경에서 더 빠른 콜드 스타트가 가능합니다
4. **버전 관리** — `open-sse`는 자체 주기에 따라 릴리스할 수 있습니다

```json
// package.json
"workspaces": ["open-sse"]
```

## 요청 파이프라인

모든 LLM 요청은 **5단계 파이프라인**을 거칩니다.

```
                              ┌──────────────┐
   HTTP 요청                   │  1. 라우팅    │   콤보 해석, 모델 선택
   (Next.js 라우트)            └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. 변환      │   형식 변환(OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. 실행      │   제공자 실행기, HTTP, 재시도, 차단기
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. 스트리밍  │   SSE 변환, 백프레셔
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. 기록      │   사용량 추적, 호출 로그, 오류 분류
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP 응답(SSE 또는 JSON)
```

### 1단계: 라우팅(services/combo.ts)

**진입점**: `services/combo.ts`의 `handleComboChat()`

요청을 구체적인 `(provider, model, account, credentials)` 튜플로 해석합니다.

- ID로 콤보를 조회하거나 `auto/*` 모델을 위한 가상 콤보 생성
- 라우팅 전략 적용(우선순위, 가중치, 라운드 로빈 등)
- 비정상 제공자 제외(서킷 브레이커)
- 사용 가능한 다음 대상 선택

`auto/*` 모델의 경우 이 단계에서 다음 작업도 수행합니다.

- **16개 요소 기반 점수 산정** 알고리즘 실행(`services/autoCombo/`)
- 상태, 비용, 지연 시간 등을 기준으로 `provider+model` 쌍 선택

### 2단계: 변환(translator/)

소스 형식(예: OpenAI)이 대상 형식(예: Claude)과 다르면 요청이 **변환**됩니다.

- 시스템 프롬프트 → 시스템 메시지
- 도구 정의 → 제공자별 도구 형식
- 추론/사고 매개변수 → 제공자별 대응 항목
- 메시지 역할 정규화(OpenAI 이외의 경우 `developer` → `system`)

`translator/index.ts`는 다음을 노출합니다.

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### 3단계: 실행(executors/)

**진입점**: `getExecutor(providerId).execute(request, options)`

모든 제공자는 `getExecutor()` 팩토리의 폴백을 통해 `DefaultExecutor`(`executors/default.ts`)를 사용합니다. 실행기는 다음 작업을 수행합니다.

- 업스트림 URL 구성(`buildUrl()`)
- 제공자별 헤더 추가(`buildHeaders()`)
- 요청 본문 변환(`transformRequest()`)
- 재시도 및 지수 백오프를 적용하여 HTTP 요청 전송
- 필요한 경우 인증 갱신 처리(OAuth 제공자)

모든 실행기는 `BaseExecutor`(`executors/base.ts`, 1170 LOC)를 확장하며, 다음 기능을 제공받습니다.

- 공통 재시도 로직
- 프록시 통합
- 서킷 브레이커 통합
- 사용량 기록 훅

### 4단계: 스트리밍(utils/stream.ts)

스트리밍 응답의 경우 실행기는 **ReadableStream**을 반환합니다. 핸들러는 다음 작업을 수행합니다.

- SSE 변환을 통해 파이프 처리(`createSSETransformStreamWithLogger`)
- 비활성 연결을 감지하기 위한 하트비트 핑 적용
- 클라이언트 연결 해제를 정상적으로 처리(`pipeWithDisconnect`)
- 비스트리밍 클라이언트를 위해 SSE → JSON 변환

비스트리밍 응답의 경우 실행기는 파싱된 JSON 객체를 반환하며, 이 객체는 변경 없이 그대로 전달됩니다.

### 5단계: 기록(services/usage.ts)

응답 후(성공 또는 실패), 사용량이 기록됩니다:

- 응답의 `prompt_tokens`, `completion_tokens`, `cached_tokens`
- 가격 데이터를 기반으로 계산된 `cost_usd`
- 실패한 경우 `latency_ms`, `status`, `error_class`
- `usage_history` 테이블에 저장됨

호출 로그 아티팩트가 활성화된 경우 `${DATA_DIR}/call_logs/`에 기록됩니다.

## 핵심 파일 심층 분석

### chatCore.ts (5977줄)

**메인 요청 핸들러**. 크기에도 불구하고 명확한 구조를 갖추고 있습니다:

```ts
// chatCore.ts의 의사 구조
export async function handleChat(request: NextRequest) {
  // 1. 인증 + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. 본문 검증
  const body = await parseRequestBody(request);

  // 3. 포맷 감지 + 변환
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. 콤보 라우팅
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // 다음 타겟으로 계속 진행
    }
  }

  // 5. 긴급 폴백
  return await emergencyFallback(body);
}
```

하나의 거대한 함수임에도 불구하고, 5단계 파이프라인에 대응하는 **주석으로 구분된 섹션**들로 조직되어 있습니다.

### combo.ts (4456 LOC)

콤보를 순서가 정해진 타겟들로 해석하는 **라우팅 엔진**.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

**21가지 라우팅 전략**을 지원합니다 (`src/shared/constants/routingStrategies.ts` 참조):

| `priority`          | 첫 번째 타겟부터 순서대로 시도                                           |
| `weighted`          | 타겟별 가중치에 따른 확률적 선택                                         |
| `round-robin`       | 타겟을 순서대로 순환                                                     |
| `context-relay`     | 타겟 간에 컨텍스트 전달                                                  |
| `fill-first`        | 다음으로 넘어가기 전에 할당량을 먼저 채움                                |
| `p2c`               | 두 후보 중 더 나은 쪽을 선택 (power of two choices)                      |
| `random`            | 균등 랜덤                                                                |
| `least-used`        | 최근 사용 횟수가 가장 적은 타겟 선택                                     |
| `cost-optimized`    | 정상 상태인 타겟 중 가장 저렴한 것 우선                                  |
| `reset-aware`       | 프로바이더 리셋 윈도우를 고려                                            |
| `reset-window`      | 리셋 윈도우 기반 라우팅                                                  |
| `expiry-first`      | 그대로 두면 사용되지 않고 만료될 할당량을 가진 계정을 먼저 사용합니다    |
| `headroom`          | 남은 할당량 여유분이 가장 많은 타겟 우선                                 |
| `quota-weighted`    | 소진된 계정을 건너뛰고, 남은 할당량 ÷ 처리 중인 부하로 추첨              |
| `strict-random`     | 완전한 균등 분포 (품질 가중치 없음)                                      |

| `lkgp`              | 마지막으로 정상 동작했던 프로바이더 우선                                 |
| `context-optimized` | 긴 컨텍스트 요청에 최적                                                  |
| `cache-optimized`   | 재사용 가능한 각 프롬프트 접두사를 동일 계정에 고정 (프롬프트 캐시 히트) |

### base.ts (1170 LOC)

모든 executor 클래스가 (직접적으로든 `DefaultExecutor` 및 다른 서브클래스를 통해서든) 상속하는 **추상 executor**. 다음을 포함합니다:

- `buildUrl()` — 기본 URL 구성 (커스텀이 필요하면 서브클래스에서 오버라이드)
- `buildHeaders()` — 기본 헤더 (인증, content-type)
- `transformRequest()` — 기본적으로 패스스루
- `execute()` — 재시도/백오프/브레이커가 포함된 메인 HTTP 루프

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // 모든 OpenAI/Anthropic 호환 프로바이더를 처리
  // 프로바이더는 설정(URL, 인증, 헤더)을 등록하지만 executor 로직은 공유
}
```

프로바이더별 동작(인증 헤더, 기본 URL, 버전 헤더)은 별도의 executor 클래스가 아니라 프로바이더 레지스트리를 통해 설정됩니다.

## 실행기 (모듈 150개)

대부분 프로바이더당 하나의 파일입니다. 실행기 클래스는 모두 `BaseExecutor`를 확장하고 차이가 있는 부분만 오버라이드합니다. 나머지 모듈은 프로바이더별 헬퍼(도구 스키마, fetch/TTS 어댑터, 특이 동작 핸들러)입니다.

### 공통 패턴

프로바이더는 `getExecutor(providerId)`를 통해 해석되며, 이 함수는 구성된 실행기를 반환합니다. OpenAI/Anthropic 호환 프로바이더는 `DefaultExecutor`(`executors/default.ts`)를 사용합니다. 프로바이더별 동작(base URL, 인증 헤더, API 버전)은 `open-sse/config/providers/`에서 구성하고, 요청 본문 변환은 `open-sse/translator/`에서 처리합니다.

**커스텀 URL**은 프로바이더 구성을 통해 설정합니다:

```ts
// open-sse/config/providers/의 프로바이더 구성
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**커스텀 인증**은 프로바이더 레지스트리의 인증 구성(API 키, OAuth, 헤더 프로필)을 통해 처리됩니다.

**커스텀 요청 본문** 변환(예: Anthropic이 `system`을 `messages`와 분리하는 경우)은 `open-sse/translator/`에 프로바이더별로 등록합니다.

````

### 실행기 팩토리

`executors/index.ts`는 `getExecutor(providerId)`를 내보냅니다:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

해석(resolution)은 `ExecutorRegistry`(`executors/registry.ts`)를 통해 이루어집니다. 모든 특화 실행기는 `executors/index.ts`의 내장 테이블에 선언되고, 모듈 로드 시 `registerExecutor(alias, instance)`를 통해 등록됩니다. `getExecutor()`는 레지스트리를 조회하고, 특화 항목이 없는 프로바이더에 대해서는 메모이즈된 `DefaultExecutor`로 폴백합니다. 전체 alias → 실행기 매핑은 골든 테스트 `tests/unit/executor-map-golden.test.ts`로 특성화됩니다.

## 변환기

**3가지 형식**인 OpenAI, Anthropic, Gemini와 새로운 Responses API 간에 변환합니다.

### 변환이 수행되는 시점

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

일반적인 변환:

- `OpenAI → Anthropic`: 별도의 `system` 필드, `x-api-key` 헤더
- `OpenAI → Gemini`: `messages` 대신 `contents`, `systemInstruction`
- `OpenAI → Responses API`: `input` 배열, `previous_response_id` 상태

### 처리되는 엣지 케이스

- `developer` 역할 → OpenAI 이외의 경우 `system`
- `system` 역할 → GLM/ERNIE의 경우 첫 번째 사용자 메시지에 병합
- `json_schema` → Gemini의 `responseMimeType` + `responseSchema`
- `tools` → 제공자별 도구 형식
- 사고 매개변수(o1, Claude) → 제공자별 대응 항목

## MCP 서버

`open-sse/mcp-server/`는 **Model Context Protocol** 서버를 구현합니다.

- **110개의 도구**(제공자 관리, 조합, 메모리, 캐시, 압축, 프록시, 스킬, 게임화, 플러그인, Notion, Obsidian, 로컬 코퍼스)
- **3가지 전송 방식**: stdio, SSE, Streamable HTTP
- 세분화된 권한 부여를 위한 **33개의 범위**

### 도구 등록

도구는 `open-sse/mcp-server/tools/`에 독립형 파일로 등록되며, 각 파일은 이름, 스키마, 핸들러 및 범위를 내보냅니다.

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### 전송 방식

```ts
// stdio(CLI 사용)
startMcpStdio(server);

// SSE(HTTP 기반 스트리밍)
startMcpSse(server, port);

// Streamable HTTP(최신 MCP)
startMcpStreamable(server, port);
```

### 권한 부여

모든 도구 호출은 범위 검사(`open-sse/mcp-server/auth/`)를 거칩니다.

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## 변환기

`open-sse/transformer/`는 **Chat Completions**와 **Responses API** 형식 간에 변환합니다.

### 별도의 변환기가 필요한 이유

Responses API는 **상태 유지 대화**(`previous_response_id`)를 지원하는 OpenAI의 새로운 형식입니다. 클라이언트가 Responses 요청을 보내면 OmniRoute는 다음을 수행합니다.

1. 내부적으로 Responses → Chat Completions로 변환
2. 제공자(Chat Completions를 지원하는 모든 제공자)에게 전송
3. 응답을 다시 Responses 형식으로 변환
4. 변환된 응답을 클라이언트에 스트리밍

변환기(`transformer/responsesTransformer.ts`)는 다음을 제공합니다.

```ts
createResponsesApiTransformStream(): TransformStream
```

다음을 처리합니다.

- `response.output_item.added` 이벤트
- `response.output_text.delta` 이벤트
- `response.completed` 이벤트
- 도구 호출 매핑(`function_call` ↔ `tool_calls`)

## 새 컴포넌트 추가

### 새 서비스 추가

1. 명확한 단일 책임을 갖는 `open-sse/services/[serviceName].ts` 생성
2. 기본 핸들러 함수와 필요한 상수 내보내기
3. `tests/unit/services/[serviceName].test.mjs`에 단위 테스트 추가
4. 라우팅과 관련된 경우 `handlers/chatCore.ts`의 요청 파이프라인에 통합
5. 서비스가 대상 선택에 영향을 주는 경우 `combo.ts`의 라우팅 로직 업데이트
6. 이 파일에 문서화

1. `BaseExecutor`를 확장하는 `open-sse/executors/[provider].ts` 생성
2. `config/providerRegistry.ts`에 등록
3. `executors/index.ts` 팩토리에 추가
4. 실행기 단위 테스트 추가
5. `docs/architecture/ARCHITECTURE.md`에 문서화

### 새 MCP 도구 추가

1. `open-sse/mcp-server/tools/[category]Tools.ts` 생성 또는 업데이트
2. 입력용 Zod 스키마 정의
3. `mcp-server/index.ts`에 도구 등록
4. `mcp-server/auth/`의 범위 매트릭스에 추가
5. 단위 테스트 추가
