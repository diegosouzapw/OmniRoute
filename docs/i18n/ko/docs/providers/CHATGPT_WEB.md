`chatgpt-web-codex`(별칭 `cgpt-codex`)는 인증된 ChatGPT 브라우저 세션을 통해 Codex Responses 턴을 중계합니다. 이 공급자는 지원 종료된 공용 `chatgpt-web` 공급자와 독립적이며, 업스트림 v4.0.7 커밋 `b59d7dc51b84fb1f465ff1d00f5207f3b2b4a494`까지 갱신된 `open-sse/vendor/codex-chatgpt-web/`의 MIT 고지 구현을 사용합니다.

## 공용 공급자 지원 종료

기존 공용 공급자 ID인 `chatgpt-web` 및 `cgpt-web`은 pre-key/작업 증명 구현의 출처를 명확히 확인할 수 없어 더 이상 제공되지 않습니다. 슬래시 접두사가 붙은 모델 ID 및 저장된 별칭을 포함하여 두 ID 중 하나를 명시적으로 요청하면 업스트림 요청을 전송하기 전에 HTTP `410`과 코드 **PROVIDER_RETIRED**로 차단됩니다.

마이그레이션 `168_retire_chatgpt_web.sql`은 일치하는 공급자 연결을 삭제 표시하고 활성 세션 임대를 무효화합니다. 연결 기록과 API 키 허용 목록은 보존하지만, 허용 목록에 대체 액세스를 추가하지는 않습니다. Codex 공급자와 해당 연결은 이 지원 종료의 대상이 아닙니다.

## 사전 요구 사항

- 로그인된 ChatGPT 세션의 전체 Cookie 헤더
- npm, systemd 및 PM2 설치를 위한 Chrome 또는 Chromium과 그래픽 세션이나 Xvfb 디스플레이
- Docker `web` 프로필을 사용하는 경우 `docker-compose.yml`의 내부 Chromium 서비스
- 로컬 Codex 도구를 위한 OpenAI `tunnel-client` v0.0.13 및 ChatGPT 사용자 지정 커넥터

터널은 도구 턴에만 필요합니다. 터널과 커넥터가 구성되어 있으면 `pro`를 포함해 나열된 모든 경로에서 동일한 턴 바인딩 로컬 도구 기능을 사용할 수 있습니다.

## 대시보드 설정

1. **ChatGPT Web (Codex)** 공급자를 열고 연결을 추가합니다.
2. 전체 ChatGPT Cookie 헤더, 터널 ID, 런타임 키 및 사용자 지정 커넥터 이름을 붙여 넣습니다. 새로운 도구 지원 설정에서는 정확히 `OmniRoute Codex v2`라는 이름으로 새로 생성한 커넥터를 사용해야 하며, Authentication은 None으로, Permissions는 Allow all actions로 설정해야 합니다.
3. 연결 검사를 실행합니다. OmniRoute가 브라우저 기반 Temporary Chat을 열고 해당 계정에서 Sol과 Pro를 사용할 수 있는지 감지합니다.
4. 연결을 저장합니다. OmniRoute는 붙여 넣은 쿠키를 검증된 Playwright 저장소 상태로 대체하고, 암호화된 자격 증명 추상화를 통해 런타임 키와 함께 저장합니다.

성공적으로 저장된 후에는 원시 쿠키가 보관되지 않습니다. 세션이 만료되면 연결을 열고 새로운 전체 Cookie 헤더를 붙여 넣은 다음 검사를 다시 실행합니다. 편집 대화 상자의 doctor 상태는 브라우저, 저장소 상태, 로그인, Temporary Chat, 터널, 커넥터 및 도구 왕복 상태를 각각 보고합니다.

> 실제 쿠키, 런타임 키, 저장소 상태 또는 기능 토큰을 절대로 커밋하지 마세요. 테스트 및
> 문서 값에는 항상 자리표시자를 사용해야 합니다.

## 모델 및 콤보

고정 모델 경로는 다음과 같습니다.

- `chatgpt-web-codex/luna` — GPT-5.6 Luna, 낮은 추론 수준
- `chatgpt-web-codex/think` — GPT-5.6 Luna, 중간 추론 수준
- `chatgpt-web-codex/instant`
- `chatgpt-web-codex/medium`
- `chatgpt-web-codex/high`
- `chatgpt-web-codex/extra-high`
- `chatgpt-web-codex/pro`

다른 모델과 마찬가지로 이 중 하나를 콤보에 추가합니다. Codex 앱은 일반 Responses 엔드포인트 `/v1/responses`에 콤보 이름을 `model`로 전송합니다. 별도의 Codex 엔드포인트나 모드 전환은 없습니다.

Free/Go 계정에서는 Luna 경로를 사용할 수 있습니다. Sol 지원 계정에서는 Instant부터 High까지 사용할 수 있으며, Pro 지원 계정에서는 Extra High와 Pro도 추가로 사용할 수 있습니다. 각 경로에는 고정된 백엔드 모델과 추론 수준이 지정되어 있습니다. 이와 충돌하는 Responses 추론 수준을 명시적으로 지정하면 선택한 브라우저 모드를 암묵적으로 변경하는 대신 요청이 차단됩니다.

이전 `Codex Native` 또는 `OmniRoute Codex` 커넥터의 이름을 변경하거나 재사용하지 마세요. ChatGPT는 커넥터 ID를 기준으로 공개 MCP 계약을 캐시하지만, 갱신된 브리지는 새로운 직접 턴 토큰 계약을 사용합니다. 런타임은 이러한 레거시 ID를 거부하며 새로운 `OmniRoute Codex v2` 커넥터를 요구합니다.

## 보안 모델

- 네이티브 경로에는 Responses 요청, 인식된 Codex 클라이언트, 그리고 일치하는 스레드 및 턴 ID가 필요합니다.
- 워크스페이스, 샌드박스, 승인 정책 및 도구 카탈로그는 네이티브 Codex 셸에서 제공되며, 자유 형식 프롬프트 텍스트에는 이를 결정할 권한이 없습니다.
- ChatGPT는 턴마다 수명이 짧은 capability만 받습니다. MCP 브로커는 Codex가 해당 턴에 제공한 도구만 허용합니다.
- **Allow once**를 자동 확인하면 도구 요청이 Codex로 반환될 뿐입니다. 승인 및 실행 여부는 Codex만 결정합니다.
- 첫 번째 출력 전에는 콤보가 다른 호환 대상에서 대체 처리될 수 있습니다. 출력이 시작된 후에는 턴이 완료될 때까지 공급자, 모델, 연결 및 브라우저 턴이 고정됩니다.
- 쿠키, 런타임 키, 스토리지 상태 및 capability 토큰은 공급자 응답이나 요청 로그에 나타나지 않습니다.

## 디스플레이 없는 VPS 및 Docker

npm, systemd 및 PM2 설치의 경우 OmniRoute가 일반적인 Chrome 및 Chromium 경로를 감지합니다. 또는 `CHATGPT_WEB_CODEX_CHROME_PATH`를 설정할 수 있습니다. ChatGPT는 실제 헤드리스 브라우저 형태를 거부하므로 런타임 턴에서는 의도적으로 헤드 모드 Chrome을 사용합니다. 따라서 디스플레이가 없는 호스트에서는 비공개 Xvfb 디스플레이를 사용하여 OmniRoute를 실행해야 하며, Chrome 경로만 설정해서는 디스플레이가 제공되지 않습니다.

Docker `web` 프로필은 내부 Compose 네트워크에서 `chatgpt-web-codex-browser`를 시작합니다. 사이드카는 Xvfb 내부에서 헤드 모드 Chrome을 실행하므로 물리적 디스플레이가 필요하지 않습니다. CDP 포트는 호스트에 게시되지 않습니다. 보호된 브라우저 프로필 볼륨은 OmniRoute 데이터 볼륨과 분리되어 있으며, 브라우저에는 충분한 공유 메모리가 할당됩니다. 내부 CDP 프록시는 Compose 네트워크 내부의 포트 `9223`에서만 수신 대기하며, Chrome은 사이드카의 루프백에 계속 바인딩됩니다.

`DATA_DIR` 아래의 감독자 리스는 여러 OmniRoute 프로세스가 동일한 터널 및 브로커 상태를 소유하지 못하도록 방지합니다. 충돌은 doctor에서 보고됩니다.

## 대화형 복구

자동화된 Docker 경로에는 호스트에서 볼 수 있는 창이 없지만, Chrome 자체는 비공개 Xvfb 디스플레이 내에서 헤드 모드로 실행됩니다. ChatGPT에서 대화형 로그인이나 챌린지가 필요할 때 기존 VNC 브라우저 인프라를 복구에 사용할 수 있습니다. 브라우저 UI와 CDP는 루프백, 인증된 관리 연결 또는 SSH 터널을 통해서만 접근할 수 있어야 하며, 정상 작동 중에는 noVNC가 비활성화된 상태로 유지됩니다.

## WebSocket 대체 처리

콤보에 ChatGPT Web (Codex)이 포함된 경우 Responses WebSocket 브리지는 업스트림에 연결하기 전에 HTTP/SSE 대체 처리를 요청합니다. 이후 전송은 `/v1/responses`를 통해 이루어집니다.
