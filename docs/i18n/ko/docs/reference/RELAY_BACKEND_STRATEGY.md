## 요약

OmniRoute는 이제 `/api/v1/relay/chat/completions`에 대해 세 가지 릴레이 모드를 지원합니다.

- `ts`: TypeScript 릴레이를 프로세스 내에서 사용합니다.
- `bifrost`: Bifrost 게이트웨이를 강제로 사용합니다.
- `auto`: 사용 가능한 경우 Bifrost를 우선 사용하고, 실패 시 TypeScript로 폴백합니다.

높은 요청 속도(일일 토큰 수가 많고 처리량이 거의 일정한 경우)로 운영할 때 가장 좋은 전략은 폴백 경로를 명시적이고 빠르게 유지하여, 핵심 경로가 작동하지 않는 사이드카 때문에 차단되지 않도록 하는 것입니다.

## 모드 동작

- `ts`
  - 운영 복잡도가 가장 낮습니다.
  - 모든 라우팅과 검증이 Node에서 실행됩니다.
  - 가용성을 위해 사이드카에 의존하지 않습니다.
- `bifrost`
  - 모든 요청이 사이드카 게이트웨이를 통과하도록 강제합니다.
  - 자동 폴백이 없습니다.
  - 사이드카의 상태와 지연 시간이 보장되는 경우에만 유용합니다.
- `auto`
  - 사이드카가 활성화되어 있고 연결할 수 있을 때 사용됩니다.
  - 시도가 실패하면 폴백 헤더가 추가되고 트래픽이 TS로 반환되어 요청 성공이 일정 범위 내에서 보장됩니다.
  - 엄격한 사이드카 전용 라우팅보다 가동 시간이 중요한 프로덕션 환경에서 가장 안전한 선택입니다.

## 현재의 9router와 CLIPROXYAPI 비교

9router와 CLIPROXYAPI는 모두 과거부터 업스트림 제공자를 위한 호환성 경로를 제공해 온 통합 기능입니다.

- 9router는 업스트림 오케스트레이션과 호환성 동작을 위한 임베디드 경로입니다.
- CLIPROXYAPI는 CLI / SDK 스타일 트래픽을 위한 프록시 API 브리지입니다.
- Bifrost는 전용 사이드카 형태의 홉과 지연 시간이 짧은 로컬 디스패치가 필요할 때 사용할 수 있는 외부화된 경로로 안정화되고 있습니다.

현재 9router/CLIPROXYAPI를 비교하고 있다면 다음을 따르십시오.

- 핸드오프 전에 API 라우트에서 요청 서명, 허용 목록 검사 및 DB 정책 게이트를 유지합니다.
- 워크플로에 엄격한 사이드카 동작과 더 낮은 요청별 편차가 필요하다면 `OMNIROUTE_RELAY_BACKEND=bifrost`를 사용합니다.
- 장애 상황에서 정상적인 성능 저하를 제공하는 사이드카 복원력이 필요하다면 `OMNIROUTE_RELAY_BACKEND=auto`를 사용합니다.

## 백엔드 경계 계약

안정적인 제품 경계는 대시보드 구현이 아니라 OmniRoute 릴레이 API입니다. Next.js 대시보드는 로컬 서비스를 설치, 구성 및 감독할 수 있지만, 요청 라우팅은 릴레이 API를 통해 진입하고 해당 경계 뒤에서 핸드오프되어야 합니다.

장기적인 백엔드 선택지는 다음과 같습니다.

- TypeScript 릴레이를 프로세스 내 정책 및 폴백 경로로 유지합니다. 인증, 허용 목록, 요청 정규화, 사용량 집계 및 안전성 검사는 모든 백엔드 핸드오프 전에 여기에서 유지됩니다.
- 배포 환경에서 라우팅 편차 감소, 중앙 집중식 제공자 순환 또는 여러 OmniRoute 복제본으로의 스케일 아웃이 필요한 경우 Bifrost를 선호되는 고처리량 Tier-1 사이드카로 사용합니다.
- 9router와 CLIPROXYAPI는 임베디드 호환성 서비스로 유지합니다. 이들은 감독되는 로컬 프로세스로 실행되며 해당 제공자/CLI 동작이 원하는 어댑터인 경우 유용하지만, 기본 Tier-1 라우팅 엔진이 되어서는 안 됩니다.
- 대시보드가 임의의 서비스 URL을 핵심 경로에 전달하도록 만들지 마십시오. UI에서 제공하는 URL은 구성 입력값이며, 라우팅 코드는 서버 측 설정과 슈퍼바이저 상태를 기반으로 등록되고 상태 검사를 통과한 백엔드를 확인해야 합니다.
- 현재는 감독되는 프로세스가 이미 HTTP 호환 API를 노출하고, 라우트 가드가 경계를 감사할 수 있으며, 실패/폴백 동작이 요청 로그에 표시되므로 감독되는 서비스에 루프백 HTTP를 사용하는 것이 좋습니다. 향후 SDK 또는 소켓 전송은 격리나 폴백 의미 체계를 약화하지 않으면서 p99 라우팅 지연 시간을 측정 가능할 정도로 줄이는 경우에만 추가할 가치가 있습니다.

따라서 처리량이 매우 높은 배포 환경의 기본 선택은 Bifrost가 활성화된 `auto`입니다. 핵심 경로에서는 Go 사이드카를 사용하면서 성공률을 위해 TypeScript 폴백을 유지합니다. 정상적인 성능 저하보다 엄격한 사이드카 전용 동작이 더 중요한 경우에만 `bifrost`를 사용하십시오.

## 고처리량 운영 지침

지속적으로 높은 RPM/RPS와 엄격한 성공 SLO를 달성하려면 다음을 따르십시오.

1. 실용적인 쿨다운 및 실패 텔레메트리와 함께 `auto`를 사용합니다.
2. 업스트림 검증과 API 키 검사는 TypeScript 라우트 경계에서 유지합니다.
3. 알림 시스템이 폴백 빈도와 원인을 파악할 수 있도록 명시적인 헤더/카운터를 활성화합니다.
4. 사이드카 타임아웃을 무한정 기다리지 않고 빠르게 실패하도록 조정합니다.
5. 폴백이 실제로 예외적인 상황에서만 발생하도록 서비스 자동 재시작 및 상태 텔레메트리 루프를 정상적으로 유지합니다.

## 권장 기준 구성

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- 라우트 핸들러에서 API 키, 허용 목록, 새니타이저 및 속도 제한 검사를 활성화된 상태로 유지합니다(이러한 검사는 다운스트림 전달 전에 항상 실행됩니다).
- 사이드카 중단을 1분 이내에 확인할 수 있도록 리버스 프록시와 요청 로그에서 폴백 메트릭을 내보냅니다.

## 제공자 플러그인 계약

사이드카는 TypeScript 실행기 내부 구현에 의존하는 대신 JSON-safe 제공자 플러그인
매니페스트를 통해 제공자 메타데이터를 가져와야 합니다. 사이드카
적격성 계약 및 마이그레이션 단계에 대해서는
[Provider Plugin Manifest](./PROVIDER_PLUGIN_MANIFEST.md)를 참조하십시오.
