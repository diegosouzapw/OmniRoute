릴레이(Vercel, Deno, Cloudflare)는 서버리스 백엔드에서 업스트림 연결을 종료하므로, OmniRoute는 제공업체 API 키를 서버 측에 유지하면서 안정적인 리전에서 외부로 연결할 수 있습니다. 이 문서에서는 운영자가 프로덕션 환경에서 겪는 두 가지 장애 모드와 각 장애에 대해 OmniRoute가 제공하는 복구 경로를 설명합니다.

## 릴레이 인증 정보 저장 방식

**Settings → Proxy Pool → Deploy Relay**에서 릴레이를 배포하면 배포 과정에서 릴레이의 인증 토큰을 프록시의 `notes` JSON 필드에 저장합니다.

- `STORAGE_ENCRYPTION_KEY`가 설정되어 있으면 토큰은 `relayAuthEnc`로 기록됩니다
  (저장 시 AES로 암호화됨).
- 그렇지 않으면 평문 `relayAuth`로 기록됩니다.

요청 시 `extractRelayAuth(notes)`는 존재하는 형식의 값을 반환하므로, 릴레이는 재시작 후에도 계속 작동합니다.

## 장애 모드 1 — 키 교체 후 복호화할 수 없는 토큰

**증상:** 이전에 작동하던 릴레이가 환경 또는 비밀 관리자에서
`STORAGE_ENCRYPTION_KEY`를 교체한 후 업스트림 `401`/인증 오류를 반환합니다. 저장된 `relayAuthEnc` 블롭을 더 이상 복호화할 수 없으므로 `extractRelayAuth`가 빈 문자열을 반환하고 릴레이가 인증 정보를 전송하지 않습니다.

**복구 — 현재 상태에서 복구(재배포 불필요):**

1. **Settings → Proxy Pool**을 엽니다.
2. 인증 정보가 없는 릴레이 행에는 노란색 `auth missing` 배지와
   **Repair** 버튼이 표시됩니다.
3. **Repair**를 클릭합니다. OmniRoute는
   `POST /api/settings/proxies/[id]/repair-relay`를 호출하며, 이 API는 다음 작업을 수행합니다.
   - **현재** 키로 `relayAuthEnc`를 복호화합니다.
   - 평문 `relayAuth`를 `notes`에 다시 기록합니다.
   - `{ repaired: true, mode: "recovered" }`를 반환합니다.

배포 자격 증명을 다시 입력하지 않아도 릴레이가 서비스를 재개합니다.

이 방법은 현재 `STORAGE_ENCRYPTION_KEY`로 여전히 해당 블롭을 복호화할 수 있는 경우에만 작동합니다. 마이그레이션 **없이** 키를 교체했다면 블롭을 복구할 수 없습니다.

## 장애 모드 2 — 복구할 수 없는 토큰(이전 키가 폐기됨)

**증상:** **Repair**를 클릭했는데
`{ repaired: false, mode: "redeploy", status: 409 }`가 반환됩니다.

**복구 — 재배포:**

현재 키로는 저장된 토큰을 복구할 수 없습니다. 처음 사용했던 것과 동일한 모달(**Deploy Relay** 메뉴 → Vercel / Deno / Cloudflare)에서 릴레이를 다시 배포합니다. 배포 과정에서 새 토큰을 기록하며(현재 키로 암호화됨), 해당 행의 `auth missing` 배지가 사라집니다.

UI에서는 토큰을 복구할 수 없는 경우 **Repair** 버튼 자체가 재배포 모달을 열기 때문에 사용자가 직접 찾아갈 필요가 없습니다.

## 장애 모드 3 — 릴레이에 연결할 수 있지만 정상적으로 작동하지 않음

**증상:** 프록시 테스트(`speed` 버튼)에서는 릴레이가 작동 중인 것으로 표시되지만 요청이 여전히 간헐적으로 실패합니다.

OmniRoute의 자동 테스트 프로브가 반환하는 릴레이 인식 헤더를 확인하세요
(**Settings → Proxy Pool** 및 `relayTested` / `relayAlive` 카운터 참조).

- `x-relay-url` — 응답한 릴레이 백엔드입니다.
- `x-relay-mode` — 해당 요청의 모드로, `ts` | `bifrost` | `auto` 중 하나입니다.
- `x-relay-attempts` — 성공하기 전에 시도한 릴레이 홉 수입니다.
- `x-relay-fallback` — 요청이 선호 백엔드에서 TypeScript 릴레이로 폴백된 경우 `true`입니다.

`relayAlive`가 낮으면서 `x-relay-fallback` 비율이 높다면 사이드카 백엔드가 비정상인 것이므로 이를 수정하거나 릴레이 백엔드 전략을 `ts`로 전환해야 합니다
(`RELAY_BACKEND_STRATEGY.md` 참조).

## API 참조

| 메서드 | 경로                                      | 본문                    | 성공                                                                                                                        | 실패                                                                                                  |
| ------ | ----------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | 다시 도출한 경우 `200 { repaired: true, mode: "recovered" }`; 평문이 이미 있는 경우 `200 { repaired: false, mode: "noop" }` | 복구 불가능한 경우 `409 { mode: "redeploy" }`; 릴레이 유형이 아닌 경우 `400`; 찾을 수 없는 경우 `404` |

목록 라우트 `GET /api/settings/proxies`는 각 항목에 비밀 정보가 포함되지 않은
`relayInfo: { isRelay, authMissing, repairMode }`를 추가하므로, 대시보드는 토큰을 노출하지 않고도 복구 기능을 표시할 수 있습니다.
