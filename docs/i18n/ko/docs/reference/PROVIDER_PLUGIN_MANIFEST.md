`open-sse/config/providerPluginManifest.ts`는 JSON 안전 제공자 플러그인
계약을 정의합니다. `open-sse/config/providerPluginManifestRegistry.ts`는 해당
계약을 Bifrost, CLIProxyAPI 또는 향후 Go/Rust 라우터와 같은 사이드카를 위한
현재 제공자 레지스트리에 연결합니다. TypeScript 레지스트리는 계속해서
신뢰 가능한 원본이지만, 사이드카는 실행기 코드, OAuth 기본값, 헤더 또는
프로세스 환경 상태를 가져오지 않고도 매니페스트를 사용할 수 있습니다.

프로세스 외부에서 실행되는 사이드카를 위해 같은 매니페스트를 HTTP의
`GET /api/v1/provider-plugin-manifest`에서도 사용할 수 있습니다.

OmniRoute는 `X-OmniRoute-Provider-Manifest-Url` 요청 헤더를 통해 해당 URL을
Bifrost와 CLIProxyAPI에 알립니다. 사이드카에서 로컬 요청 오리진 대신 공개
또는 컨테이너 네트워크 URL이 필요한 경우 `OMNIROUTE_PROVIDER_MANIFEST_URL`을
설정하세요.

## 매니페스트 새로 고침

HTTP 엔드포인트는 `Cache-Control: public, max-age=60`과 강력한 `ETag`를
반환합니다. 사이드카는 마지막으로 검증된 매니페스트를 유지하고 새로 고칠
때 해당 ETag를 `If-None-Match`에 포함해 전송해야 합니다. `304 Not Modified`
응답에는 본문이 없으며, 사이드카는 캐시된 매니페스트를 계속 사용합니다.
검증된 캐시 매니페스트가 없으면 사이드카는 `304`를 수락하는 대신 조건 없는
요청을 보내야 합니다.

## 목표

핫 요청 경로를 궁극적으로 지연 시간이 더 짧은 사이드카가 담당할 수 있도록
제공자 메타데이터를 플러그인 계약 형태로 전환하는 한편, OmniRoute는
TypeScript 경로를 정책 게이트 및 폴백으로 유지합니다. 매니페스트는 부가적인
기능으로, 그 자체로 요청 라우팅을 변경하지 않습니다.

## 계약

매니페스트에는 다음 정보가 포함됩니다.

- 제공자 ID 및 별칭
- 업스트림 형식 및 실행기 이름
- 인증 유형, 인증 헤더 및 선택적 인증 접두사
- 정적 엔드포인트 메타데이터
- 사이드카 적격 여부 및 제공자가 TS에 유지되어야 하는 경우의 명시적 사유
- 컨텍스트 길이, 비전/추론 플래그 및 지원되지 않는 매개변수와 같은 JSON 안전 모델 메타데이터
- `apikey`, `oauth`, `custom-executor`, `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch`, `usage-supported`를 포함한 기능 태그

매니페스트에서는 의도적으로 다음 항목을 제외합니다.

- OAuth 클라이언트 시크릿 및 기본 시크릿 값
- 런타임 환경 확인
- 요청 헤더 및 공개 자격 증명 헬퍼
- 동적 URL 빌더
- 실행기 함수
- 세션 풀 내부 구조

## 기능 태그

`capabilities`는 레지스트리 항목에서 파생된 정렬된 태그 배열입니다. 통합
구현자는 TypeScript 소스를 다시 읽는 대신 이를 "이 제공자는 무엇을 할 수
있는가"에 대한 기계 판독 가능한 답으로 취급해야 합니다.

| 태그                 | 의미                                                                             |
| -------------------- | -------------------------------------------------------------------------------- |
| `apikey`             | API 키를 허용합니다(`authType`은 `apikey` 또는 `optional`).                      |
| `oauth`              | OAuth 또는 세션 흐름을 사용합니다.                                               |
| `responses`          | OpenAI Responses-API 기본 URL을 노출합니다.                                      |
| `passthrough-models` | 정적 카탈로그 대신 업스트림의 모델을 그대로 제공합니다.                          |
| `custom-executor`    | 기본값이 아닌 실행기를 실행하므로 TypeScript 경로에 유지됩니다.                  |
| `sidecar-candidate`  | `sidecar.eligible`을 반영합니다. 사이드카 가져오기 대상으로 고려해도 안전합니다. |
| `usage-fetch`        | 사용량 또는 할당량 페처(`getUsageForProvider`)가 연결되어 있습니다.              |
| `usage-supported`    | 사용량 API가 이 제공자를 허용합니다(`isSupportedUsageConnection`).               |

`usage-fetch`는 검색 용도로만 사용됩니다. 이는 OmniRoute가 해당 제공자의
사용량을 읽는 방법을 알고 있음을 나타낼 뿐이며, 가져오기를 활성화하거나
할당량 의미 체계를 변경하거나 해당 제공자에 대해 Dashboard 할당량 위젯이
활성화되었음을 의미하지 않습니다. 해당 위젯은 별도로
`USAGE_SUPPORTED_PROVIDERS`에 의해 제한됩니다. 신뢰 가능한 원본은
`open-sse/services/usage/fetcherProviders.ts`의 `USAGE_FETCHER_PROVIDERS`입니다.

이 목록은 사용량 디스패처가 허용하는 문자열을 키로 사용하므로 정규 ID와
별칭이 혼합되어 있으며 태그가 지정된 제공자 수보다 약간 더 깁니다. 매니페스트
레지스트리의 채팅 제공자가 아닌 항목(예: `firecrawl` 검색 제공자 및
`amazon-q` ACP 제공자)에는 태그를 지정할 매니페스트 항목이 없습니다.

`usage-supported`는 서버 및 Dashboard 사용량 경로가 해당 제공자의 연결을
허용하는지를 나타냅니다. 이는 `isSupportedUsageConnection()`
(`src/lib/usage/providerLimits.ts`) 및 `supportsProviderQuota()`
(`src/shared/utils/providerQuotaVisibility.ts`)를 반영하며, 둘 다
`USAGE_SUPPORTED_PROVIDERS`
(`open-sse/services/usage/supportedProviders.ts`)에 의해 제한됩니다.
`usage-fetch`와 달리 이 태그는 제공자 ID에만 적용됩니다. 런타임 가드는 별칭
확인 없이 `USAGE_SUPPORTED_PROVIDERS.includes(providerId)`를 수행하므로
매니페스트도 같은 규칙을 유지합니다. 두 태그의 적용 범위는 서로 다릅니다.
3개 제공자(`opencode`, `opencode-zen`, `xai`)에는 `usage-fetch`만 있고,
1개 제공자(`xiaomi-mimo-token-plan`)에는 `usage-supported`만 있으므로
어느 한쪽이 다른 쪽을 암시하지 않습니다.

## 사이드카 사용

사이드카는 `sidecar.eligible`을 무조건적인 라우팅 결정이 아니라 보수적인 후보 신호로 취급해야 합니다. 첫 번째 가져오기 대상은 기본 실행기를 사용하는 API 키/정적 엔드포인트 공급자여야 합니다. 사용자 지정 웹 실행기, OAuth/세션 흐름, 동적 URL 빌더 또는 풀 설정을 사용하는 공급자는 사이드카가 동등한 동작을 구현하고 텔레메트리를 통해 동등성이 입증될 때까지 TypeScript 폴백 경로를 유지합니다.

권장 마이그레이션 단계:

1. TS 레지스트리에서 공급자 플러그인 매니페스트를 생성하고 검증합니다.
2. Bifrost 또는 CLIProxyAPI가 API 키/정적 엔드포인트 공급자의 매니페스트를 가져올 수 있도록 구현합니다.
3. TS 폴백을 활성화된 상태로 유지하면서 `OMNIROUTE_RELAY_BACKEND` 뒤의 사이드카를 통해 적격 공급자를 라우팅합니다.
4. 성공률, p99 지연 시간, 스트리밍 동작 및 지원되지 않는 매개변수 처리 방식이 TS 경로와 일치하는 경우에만 공급자를 승격합니다.
5. 사용자 지정 실행기를 위한 사이드카 네이티브 플러그인을 공급자 제품군별로 하나씩 추가합니다.

## Next에 공급자를 직접 포함하지 않는 이유

Next 프런트엔드는 공급자 실행을 담당해서는 안 됩니다. 대신 API 경계를 호출해야 합니다. 그러면 백엔드가 TypeScript 실행기, Bifrost, CLIProxyAPI 또는 향후 네이티브 사이드카 중 무엇을 사용할지 결정할 수 있습니다. 이를 통해 사이드카로 전달하기 전에 요청 서명, 허용 목록 검사, DB 정책 및 폴백 동작을 중앙에서 관리할 수 있습니다.
