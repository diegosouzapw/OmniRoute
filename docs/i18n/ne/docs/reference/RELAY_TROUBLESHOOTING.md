रिलेहरू (Vercel, Deno, Cloudflare) ले अपस्ट्रिम जडानलाई
सर्भरलेस ब्याकएन्डमा समाप्त गर्छन्, जसले OmniRoute लाई प्रदायकको API कुञ्जी
सर्भर-साइडमै राख्दै स्थिर क्षेत्रबाट इग्रेस गर्न सक्षम बनाउँछ। यस कागजातले
सञ्चालकहरूले प्रोडक्सनमा सामना गर्ने दुई विफलता मोड र प्रत्येकका लागि
OmniRoute सँग उपलब्ध पुनःप्राप्ति मार्गहरू समेट्छ।

## रिले प्रमाणीकरण कसरी भण्डारण गरिन्छ

तपाईंले **Settings → Proxy Pool → Deploy Relay** बाट रिले डिप्लोय गर्दा,
डिप्लोय प्रक्रियाले रिलेको प्रमाणीकरण टोकनलाई प्रोक्सीको `notes` JSON फिल्डमा भण्डारण गर्छ:

- यदि `STORAGE_ENCRYPTION_KEY` सेट गरिएको छ भने, टोकनलाई `relayAuthEnc`
  का रूपमा लेखिन्छ (भण्डारण अवस्थामा AES द्वारा इन्क्रिप्ट गरिएको)।
- अन्यथा यसलाई प्लेनटेक्स्ट `relayAuth` का रूपमा लेखिन्छ।

अनुरोधको समयमा `extractRelayAuth(notes)` ले उपलब्ध जुनसुकै रूप फिर्ता गर्छ,
त्यसैले पुनः सुरु भएपछि पनि रिलेले काम गरिरहन्छ।

## विफलता मोड 1 — कुञ्जी रोटेसनपछि डिक्रिप्ट गर्न नसकिने टोकन

**लक्षण:** पहिले काम गरिरहेका रिलेहरूले अब
`STORAGE_ENCRYPTION_KEY` को वातावरण वा सिक्रेट-म्यानेजर रोटेसनपछि अपस्ट्रिम `401`/प्रमाणीकरण
त्रुटिहरू फिर्ता गर्छन्। भण्डारण गरिएको `relayAuthEnc` ब्लब अब
डिक्रिप्ट गर्न सकिँदैन, त्यसैले `extractRelayAuth` ले खाली स्ट्रिङ फिर्ता गर्छ र रिलेले
कुनै प्रमाणीकरण पठाउँदैन।

**पुनःप्राप्ति — सोही स्थानमा मर्मत गर्नुहोस् (पुनः डिप्लोय आवश्यक छैन):**

1. **Settings → Proxy Pool** खोल्नुहोस्।
2. प्रमाणीकरण नभएका रिले पङ्क्तिहरूले पहेँलो `auth missing` ब्याज र
   **Repair** बटन देखाउँछन्।
3. **Repair** मा क्लिक गर्नुहोस्। OmniRoute ले
   `POST /api/settings/proxies/[id]/repair-relay` कल गर्छ, जसले:
   - **हालको** कुञ्जी प्रयोग गरी `relayAuthEnc` डिक्रिप्ट गर्छ,
   - प्लेनटेक्स्ट `relayAuth` लाई पुनः `notes` मा लेख्छ,
   - `{ repaired: true, mode: "recovered" }` फिर्ता गर्छ।

कुनै पनि डिप्लोय क्रेडेन्सियल पुनः प्रविष्ट नगरी रिलेले सेवा दिन पुनः सुरु गर्छ।

हालको `STORAGE_ENCRYPTION_KEY` ले अझै पनि उक्त ब्लब डिक्रिप्ट गर्न सक्ने अवस्थामा मात्र
यसले काम गर्छ। यदि तपाईंले माइग्रेसन **बिना** कुञ्जी रोटेट गर्नुभयो भने, उक्त ब्लब
पुनःप्राप्त गर्न सकिँदैन।

## विफलता मोड 2 — पुनःप्राप्त गर्न नसकिने टोकन (कुञ्जी रोटेट भएर हटेको)

**लक्षण:** तपाईंले **Repair** मा क्लिक गर्नुभयो र
`{ repaired: false, mode: "redeploy", status: 409 }` प्राप्त गर्नुभयो।

**पुनःप्राप्ति — पुनः डिप्लोय गर्नुहोस्:**

भण्डारण गरिएको टोकनलाई हालको कुञ्जीबाट पुनःप्राप्त गर्न सकिँदैन। तपाईंले सुरुमा प्रयोग गरेको
सोही मोडलबाट रिले पुनः डिप्लोय गर्नुहोस् (**Deploy Relay** मेनु → Vercel / Deno
/ Cloudflare)। डिप्लोय प्रक्रियाले नयाँ टोकन लेख्छ (हालको
कुञ्जीबाट इन्क्रिप्ट गरिएको) र पङ्क्तिको `auth missing` ब्याज हट्छ।

UI मा, टोकन पुनःप्राप्त गर्न नसकिने हुँदा **Repair** बटनले नै पुनः डिप्लोय मोडल खोल्छ,
त्यसैले तपाईंले यसलाई म्यानुअल रूपमा खोजिरहनु पर्दैन।

## विफलता मोड 3 — रिले पहुँचयोग्य भए पनि अस्वस्थ

**लक्षण:** प्रोक्सी परीक्षण (`speed` बटन) ले रिले सञ्चालनमा रहेको देखाउँछ तर अनुरोधहरू
अझै पनि बीच-बीचमा विफल हुन्छन्।

OmniRoute को स्वचालित-परीक्षण प्रोबले फिर्ता गरेका रिले अवेयरनेस हेडरहरू जाँच गर्नुहोस्
(**Settings → Proxy Pool** र `relayTested` / `relayAlive` काउन्टरहरू हेर्नुहोस्):

- `x-relay-url` — कुन रिले ब्याकएन्डले जवाफ दियो।
- `x-relay-mode` — उक्त अनुरोधका लागि `ts` | `bifrost` | `auto`।
- `x-relay-attempts` — सफलता प्राप्त हुनुअघि कति वटा रिले हप प्रयास गरिए।
- `x-relay-fallback` — अनुरोध रुचाइएको
  ब्याकएन्डबाट TypeScript रिलेमा फलब्याक हुँदा `true`।

कम `relayAlive` सहित उच्च `x-relay-fallback` दर हुनुको अर्थ साइडकार
ब्याकएन्ड अस्वस्थ छ र तपाईंले यसलाई ठीक गर्नुपर्छ वा रिले ब्याकएन्ड
रणनीतिलाई `ts` मा परिवर्तन गर्नुपर्छ (`RELAY_BACKEND_STRATEGY.md` हेर्नुहोस्)।

## API सन्दर्भ

| विधि   | पथ                                        | बडी                     | सफलता                                                                                                                                          | विफलता                                                                                              |
| ------ | ----------------------------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | पुनः व्युत्पन्न हुँदा `200 { repaired: true, mode: "recovered" }`; प्लेनटेक्स्ट पहिले नै उपस्थित हुँदा `200 { repaired: false, mode: "noop" }` | पुनःप्राप्त गर्न नसकिने अवस्थामा `409 { mode: "redeploy" }`; रिले प्रकार नभए `400`; फेला नपरे `404` |

सूची रुट `GET /api/settings/proxies` ले प्रत्येक वस्तुमा सिक्रेट-रहित
`relayInfo: { isRelay, authMissing, repairMode }` संलग्न गर्छ, जसले गर्दा ड्यासबोर्डले
टोकन कहिल्यै उजागर नगरी मर्मत सुविधा रेन्डर गर्न सक्छ।
