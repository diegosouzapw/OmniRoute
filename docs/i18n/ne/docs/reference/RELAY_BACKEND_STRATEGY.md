## सारांश

OmniRoute ले अब `/api/v1/relay/chat/completions` का लागि तीनवटा रिले मोड समर्थन गर्छ:

- `ts`: प्रक्रियाभित्रै TypeScript रिले प्रयोग गर्नुहोस्।
- `bifrost`: Bifrost गेटवे अनिवार्य रूपमा प्रयोग गर्नुहोस्।
- `auto`: उपलब्ध हुँदा Bifrost लाई प्राथमिकता दिनुहोस् र विफल भएमा TypeScript मा फर्कनुहोस्।

तपाईं उच्च अनुरोध दरमा (ठूलो सङ्ख्यामा tokens/day, लगभग निरन्तर थ्रुपुट) सञ्चालन गर्दै हुनुहुन्छ भने, सबैभन्दा राम्रो रणनीति भनेको फलब्याक मार्गलाई स्पष्ट र छिटो राख्नु हो, ताकि मुख्य मार्ग कहिल्यै निष्क्रिय sidecar का कारण अवरुद्ध नहोस्।

## मोडको व्यवहार

- `ts`
  - सबैभन्दा कम सञ्चालन जटिलता।
  - सबै राउटिङ र प्रमाणीकरण Node मा चल्छन्।
  - उपलब्धताका लागि sidecar मा कुनै निर्भरता हुँदैन।
- `bifrost`
  - सबै अनुरोधलाई अनिवार्य रूपमा sidecar गेटवे हुँदै पठाउँछ।
  - स्वचालित फलब्याक हुँदैन।
  - sidecar को स्वास्थ्य र विलम्बता सुनिश्चित हुँदा मात्र उपयोगी हुन्छ।
- `auto`
  - sidecar पहुँचयोग्य र सक्षम हुँदा यसको प्रयोग गरिन्छ।
  - विफल प्रयासहरूले फलब्याक हेडरहरू ट्रिगर गर्छन् र ट्राफिकलाई TS मा फर्काउँछन्, जसले अनुरोधको सफलता सीमाबद्ध राख्छ।
  - अपटाइम कडाइका साथ sidecar-मा-मात्र राउटिङभन्दा महत्त्वपूर्ण हुँदा उत्पादनका लागि यो मोड सबैभन्दा सुरक्षित विकल्प हो।

## हालको 9router र CLIPROXYAPI को तुलना

9router र CLIPROXYAPI दुवै त्यस्ता एकीकरण हुन्, जसले ऐतिहासिक रूपमा upstream प्रदायकहरूका लागि अनुकूलता मार्गहरू उपलब्ध गराएका छन्।

- 9router upstream समन्वयन र अनुकूलता व्यवहारका लागि अन्तर्निर्मित मार्ग हो।
- CLIPROXYAPI CLI / SDK शैलीको ट्राफिकका लागि proxy API ब्रिज हो।
- समर्पित sidecar-जस्तो hop र कम विलम्बताको स्थानीय dispatch आवश्यक हुँदा प्रयोग गरिने बाह्यीकृत मार्गका रूपमा Bifrost लाई स्थिर बनाइँदै छ।

यदि तपाईं हाल 9router/CLIPROXYAPI तुलना गर्दै हुनुहुन्छ भने:

- handoff अघि API route मै अनुरोध हस्ताक्षर, allowlist जाँच र DB नीति gate हरू राख्नुहोस्।
- कुनै कार्यप्रवाहलाई कडा sidecar व्यवहार र प्रत्येक अनुरोधमा कम उतारचढाव आवश्यक भएमा `OMNIROUTE_RELAY_BACKEND=bifrost` प्रयोग गर्नुहोस्।
- घटनाका अवस्थाहरूमा सहज अवनतिसहित sidecar लचिलोपन आवश्यक भएमा `OMNIROUTE_RELAY_BACKEND=auto` प्रयोग गर्नुहोस्।

## ब्याकएन्ड सीमा सम्झौता

स्थिर उत्पादन सीमा OmniRoute relay API हो, dashboard कार्यान्वयन होइन। Next.js dashboard ले स्थानीय सेवाहरू स्थापना, कन्फिगर र सुपरिवेक्षण गर्न सक्छ, तर अनुरोध राउटिङ relay API बाट प्रवेश गरी उक्त सीमापछाडि handoff हुनुपर्छ।

दीर्घकालीन ब्याकएन्ड विकल्पहरू:

- TypeScript relay लाई प्रक्रियाभित्रको नीति तथा फलब्याक मार्गका रूपमा राख्नुहोस्। कुनै पनि ब्याकएन्ड handoff अघि auth, allowlists, अनुरोध सामान्यीकरण, लेखाङ्कन र सुरक्षा जाँचहरू यहीँ रहन्छन्।
- deployment लाई राउटिङमा कम उतारचढाव, केन्द्रीकृत प्रदायक rotation वा धेरै OmniRoute replicas मा scale-out आवश्यक हुँदा Bifrost लाई प्राथमिक उच्च-थ्रुपुट Tier-1 sidecar का रूपमा प्रयोग गर्नुहोस्।
- 9router र CLIPROXYAPI लाई अन्तर्निर्मित अनुकूलता सेवाका रूपमा राख्नुहोस्। तिनीहरू सुपरिवेक्षित स्थानीय प्रक्रियाका रूपमा चल्छन् र तिनको प्रदायक/CLI व्यवहार नै अपेक्षित adapter हुँदा उपयोगी हुन्छन्, तर तिनीहरूलाई पूर्वनिर्धारित Tier-1 राउटिङ इन्जिन बनाउनु हुँदैन।
- dashboard लाई मुख्य मार्गमा स्वेच्छाचारी सेवा URL हरू पठाउन नदिनुहोस्। UI बाट प्रदान गरिएका URL हरू कन्फिगरेसन इनपुट हुन्; राउटिङ कोडले सर्भर-साइड सेटिङहरू र supervisor अवस्थाबाट दर्ता गरिएका तथा स्वास्थ्य-जाँच गरिएका ब्याकएन्डहरू समाधान गर्नुपर्छ।
- हालका लागि सुपरिवेक्षित सेवाहरूमा loopback HTTP लाई प्राथमिकता दिनुहोस्, किनभने व्यवस्थित प्रक्रियाहरूले पहिले नै HTTP-अनुकूल API हरू उपलब्ध गराउँछन्, route guard ले सीमा अडिट गर्न सक्छ र विफलता/फलब्याक व्यवहार अनुरोध लगहरूमा देखिन्छ। भविष्यको SDK वा socket transport ले isolation वा फलब्याक semantics कमजोर नबनाई मापनयोग्य रूपमा p99 राउटिङ विलम्बता घटाउँछ भने मात्र यसलाई थप्नु उचित हुन्छ।

त्यसैले अत्यन्त उच्च-थ्रुपुट deployment का लागि पूर्वनिर्धारित उत्तर Bifrost सक्षम गरिएको `auto` हो: सफलता दर कायम राख्न TypeScript फलब्याक सुरक्षित राख्दै मुख्य मार्गमा Go sidecar प्रयोग गर्नुहोस्। सहज अवनतिभन्दा कडाइका साथ sidecar-मा-मात्र सीमित व्यवहार बढी महत्त्वपूर्ण हुँदा मात्र `bifrost` प्रयोग गर्नुहोस्।

## उच्च-थ्रुपुटसम्बन्धी मार्गदर्शन

दिगो उच्च RPM/RPS र कडा सफलता SLO का लागि:

1. व्यावहारिक cooldown र विफलता telemetry सहित `auto` प्रयोग गर्नुहोस्।
2. upstream प्रमाणीकरण र API-key जाँचहरू TypeScript route सीमामै राख्नुहोस्।
3. तपाईंको alerting ले फलब्याकको आवृत्ति र कारणहरू देख्न सक्ने गरी स्पष्ट हेडर/काउन्टरहरू सक्षम गर्नुहोस्।
4. सधैँ पर्खिरहनुको सट्टा छिटो विफल हुने गरी sidecar timeout हरू मिलाउनुहोस्।
5. सेवा auto-restart र स्वास्थ्य telemetry loop स्वस्थ राख्नुहोस्, ताकि फलब्याक साँच्चिकै अपवाद मात्र रहोस्।

## सुझाव गरिएको आधाररेखा

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- route handler हरूमा API keys, allowlist, sanitizer र rate-limit जाँचहरू सक्षम राख्नुहोस् (तिनीहरू downstream forwarding अघि सधैँ चल्छन्)।
- sidecar का अवरोधहरू एक मिनेटभित्रै देखिने गरी आफ्नो reverse proxy र अनुरोध लगहरूबाट फलब्याक metrics निर्यात गर्नुहोस्।

manifest मार्फत प्रदायक metadata आयात गर्नुपर्छ। sidecar को
योग्यता सम्झौता र migration चरणहरूका लागि
