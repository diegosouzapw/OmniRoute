`open-sse/config/providerPluginManifest.ts` ले JSON-सुरक्षित प्रदायक
प्लगइन अनुबन्ध परिभाषित गर्छ। `open-sse/config/providerPluginManifestRegistry.ts` ले उक्त
अनुबन्धलाई Bifrost, CLIProxyAPI, वा भविष्यको Go/Rust राउटरजस्ता साइडकारहरूका लागि
हालको प्रदायक रजिस्ट्रीसँग बाँध्छ। TypeScript रजिस्ट्री नै सत्यको
मूल स्रोत रहन्छ, तर साइडकारहरूले executor कोड, OAuth पूर्वनिर्धारितहरू, हेडरहरू, वा
प्रक्रिया वातावरणको अवस्था आयात नगरीकन म्यानिफेस्ट प्रयोग गर्न सक्छन्।

प्रक्रियाबाहिर चल्ने साइडकारहरूका लागि यही म्यानिफेस्ट HTTP मार्फत
`GET /api/v1/provider-plugin-manifest` मा पनि उपलब्ध छ।

OmniRoute ले उक्त URL लाई Bifrost र CLIProxyAPI समक्ष
`X-OmniRoute-Provider-Manifest-Url` अनुरोध हेडरमार्फत उपलब्ध गराउँछ। साइडकारलाई स्थानीय अनुरोधको मूल URL को सट्टा
सार्वजनिक वा कन्टेनर नेटवर्क URL आवश्यक हुँदा
`OMNIROUTE_PROVIDER_MANIFEST_URL` सेट गर्नुहोस्।

## म्यानिफेस्ट ताजा गर्ने

HTTP एन्डपोइन्टले `Cache-Control: public, max-age=60` र बलियो
`ETag` फर्काउँछ। साइडकारले पछिल्लो प्रमाणीकरण गरिएको म्यानिफेस्ट सुरक्षित राख्नुपर्छ र ताजा गर्दा त्यसको ETag
`If-None-Match` मा पठाउनुपर्छ। `304 Not Modified` प्रतिक्रियामा बडी हुँदैन;
साइडकारले आफ्नो क्यास गरिएको म्यानिफेस्ट कायम राख्छ। यदि कुनै प्रमाणीकरण गरिएको क्यास म्यानिफेस्ट उपलब्ध छैन भने,
साइडकारले `304` स्वीकार गर्नुको सट्टा सर्तरहित अनुरोध पठाउनुपर्छ।

## लक्ष्य

प्रदायक मेटाडेटालाई प्लगइन अनुबन्धतर्फ लैजानु, ताकि अन्ततः उच्च-गतिशील अनुरोध मार्गको
स्वामित्व कम विलम्बता भएको साइडकारले लिन सकोस्, जबकि OmniRoute ले
TypeScript रुटलाई नीति गेट र फलब्याकका रूपमा कायम राखोस्। म्यानिफेस्ट थपात्मक हो: यसले
आफैं अनुरोध राउटिङ परिवर्तन गर्दैन।

## अनुबन्ध

म्यानिफेस्टमा निम्न समावेश हुन्छन्:

- प्रदायक id र उपनाम
- अपस्ट्रिम ढाँचा र executor नाम
- प्रमाणीकरण प्रकार, प्रमाणीकरण हेडर, र वैकल्पिक प्रमाणीकरण उपसर्ग
- स्थिर एन्डपोइन्ट मेटाडेटा
- साइडकार योग्यता र कुनै प्रदायक TS मै रहनुपर्ने हुँदा स्पष्ट कारणहरू
- कन्टेक्स्ट लम्बाइ, भिजन/रिजनिङ फ्ल्यागहरू, र
  असमर्थित प्यारामिटरहरूजस्ता JSON-सुरक्षित मोडेल मेटाडेटा
- `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch`, र `usage-supported` सहितका क्षमता ट्यागहरू

म्यानिफेस्टले जानाजानी निम्न कुरा समावेश गर्दैन:

- OAuth क्लाइन्ट गोप्य मानहरू र पूर्वनिर्धारित गोप्य मानहरू
- रनटाइम वातावरण रिजोल्युसन
- अनुरोध हेडरहरू र सार्वजनिक क्रेडेन्सियल सहायकहरू
- गतिशील URL बिल्डरहरू
- executor फङ्सनहरू
- सेसन पूलका आन्तरिक विवरणहरू

## क्षमता ट्यागहरू

`capabilities` रजिस्ट्री प्रविष्टिबाट व्युत्पन्न गरिएका ट्यागहरूको क्रमबद्ध एरे हो। एकीकर्ताहरूले
TypeScript स्रोतहरू पुनः पढ्नुको सट्टा यसलाई "यो प्रदायकले के गर्न सक्छ" भन्ने प्रश्नको
मेसिन-पठनीय उत्तरका रूपमा लिनुपर्छ।

| ट्याग                | अर्थ                                                                            |
| -------------------- | ------------------------------------------------------------------------------- |
| `apikey`             | API कुञ्जी स्वीकार गर्छ (`authType` भनेको `apikey` वा `optional` हो)।           |
| `oauth`              | OAuth वा सेसन प्रवाह प्रयोग गर्छ।                                               |
| `responses`          | OpenAI Responses-API को आधार URL उपलब्ध गराउँछ।                                 |
| `passthrough-models` | स्थिर क्याटलगको सट्टा सिधै अपस्ट्रिमबाट मोडेलहरू उपलब्ध गराउँछ।                 |
| `custom-executor`    | गैर-पूर्वनिर्धारित executor चलाउँछ, त्यसैले यो TypeScript मार्गमै रहन्छ।        |
| `sidecar-candidate`  | `sidecar.eligible` प्रतिबिम्बित गर्छ — साइडकार आयातका लागि विचार गर्न सुरक्षित। |
| `usage-fetch`        | जडान गरिएको उपयोग वा कोटा fetcher (`getUsageForProvider`) छ।                    |
| `usage-supported`    | उपयोग API ले यो प्रदायक स्वीकार गर्छ (`isSupportedUsageConnection`)।            |

`usage-fetch` केवल खोजका लागि हो। यसले OmniRoute लाई प्रदायकको उपयोग कसरी पढ्ने भन्ने थाहा छ भनी
जनाउँछ; यसले fetching सक्रिय गर्दैन, कोटा semantics परिवर्तन गर्दैन, वा
प्रदायकका लागि Dashboard कोटा विजेट सक्षम छ भन्ने जनाउँदैन — उक्त विजेटलाई
`USAGE_SUPPORTED_PROVIDERS` ले छुट्टै गेट गर्छ। सत्यको स्रोत
`open-sse/services/usage/fetcherProviders.ts` मा रहेको `USAGE_FETCHER_PROVIDERS` हो।

उक्त सूची usage dispatcher ले स्वीकार गर्ने स्ट्रिङहरूद्वारा keyed गरिएको छ, त्यसैले यसले canonical ids लाई
उपनामहरूसँग मिसाउँछ र ट्याग गरिएका प्रदायकहरूको सङ्ख्याभन्दा अलि लामो छ: म्यानिफेस्ट रजिस्ट्रीमा
च्याट प्रदायक नभएका प्रविष्टिहरू (उदाहरणका लागि `firecrawl` खोज प्रदायक
र `amazon-q` ACP प्रदायक) सँग ट्याग गर्नका लागि कुनै म्यानिफेस्ट प्रविष्टि हुँदैन।

`usage-supported` ले सर्भर र Dashboard का उपयोग रुटहरूले प्रदायकको कनेक्सन
स्वीकार गर्छन् कि गर्दैनन् भन्ने उत्तर दिन्छ। यसले `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
र `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`) लाई प्रतिबिम्बित गर्छ, र दुवैलाई
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`) ले गेट गर्छ। `usage-fetch`
भन्दा फरक रूपमा, यो प्रदायक id मा मात्र उत्सर्जित हुन्छ — रनटाइम गार्डले
कुनै उपनाम रिजोल्युसनबिना `USAGE_SUPPORTED_PROVIDERS.includes(providerId)` गर्छ, त्यसैले म्यानिफेस्टले
उही नियम कायम राख्छ। यी दुई ट्यागका दायराहरू फरक छन्: 3 प्रदायकमा केवल
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) छ र 1 मा केवल
`usage-supported` (`xiaomi-mimo-token-plan`) छ, त्यसैले एउटाले अर्को निहित गर्दैन।

## Sidecar को प्रयोग

Sidecar हरूले `sidecar.eligible` लाई सर्तरहित राउटिङ निर्णयका रूपमा नभई सावधानीपूर्ण उम्मेदवार सङ्केतका रूपमा लिनुपर्छ। पहिलो आयात लक्ष्य default executor प्रयोग गर्ने API-key, static-endpoint providers हुनुपर्छ। custom web executors, OAuth/session flows, dynamic URL builders, वा pool config भएका providers तबसम्म TypeScript fallback path मै रहनुपर्छ, जबसम्म कुनै sidecar ले समकक्ष व्यवहार कार्यान्वयन गर्दैन र telemetry ले समानता प्रमाणित गर्दैन।

सुझाइएका माइग्रेसन चरणहरू:

1. TS registry बाट provider plugin manifest उत्पन्न गरी प्रमाणीकरण गर्नुहोस्।
2. API-key/static providers का लागि manifest आयात गर्न Bifrost वा CLIProxyAPI लाई सक्षम बनाउनुहोस्।
3. TS fallback सक्षम राख्दै `OMNIROUTE_RELAY_BACKEND` पछाडि sidecar मार्फत योग्य providers लाई राउट गर्नुहोस्।
4. सफलता दर, p99 latency, streaming व्यवहार, र unsupported-param handling TS path सँग मेल खाँदा मात्र providers लाई प्रवर्द्धन गर्नुहोस्।
5. एक पटकमा एउटा provider family का custom executors का लागि sidecar-native plugins थप्नुहोस्।

## Providers लाई सिधै Next मा किन समावेश नगर्ने

Next frontend ले provider execution को जिम्मेवारी लिनु हुँदैन। यसले API boundary लाई कल गर्नुपर्छ। त्यसपछि backend ले TypeScript executor, Bifrost, CLIProxyAPI, वा भविष्यको native sidecar मध्ये कुन प्रयोग गर्ने भनेर निर्णय गर्न सक्छ। यसले कुनै पनि sidecar handoff अघि request signing, allowlist checks, DB policy, र fallback behavior लाई केन्द्रीकृत राख्छ।
