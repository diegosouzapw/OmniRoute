यो दस्तावेज `omniroute@3.8.5` विरुद्ध उठाइएका छवटा
`AI-detected potential malware` निष्कर्षहरू र `omniroute@3.8.6` मा लागू गरिएका
न्यूनीकरणहरूका लागि मर्मतकर्ताद्वारा लेखिएको प्रमाणीकरण हो। यसको उद्देश्य:

1. सुरक्षा-पाइपलाइन सञ्चालकहरूले निष्कर्षहरूलाई वास्तविक स्रोतसँग
   मूल्याङ्कन गर्न आवश्यक पर्दा उद्धृत गर्न सक्ने एउटै सन्दर्भ उपलब्ध गराउनु।
2. भविष्यका AI स्क्यानरहरूले चिन्ह लगाइएको प्रत्येक पथ जानाजानी राखिएको,
   स्वेच्छिक रूपमा सक्रिय गरिने, र दस्तावेजीकृत हो भन्ने मर्मतकर्ताद्वारा
   हस्ताक्षरित दाबी पहिचान गर्न सकून्।
3. प्रत्येक कल साइटलाई _किन_ त्यसरी संरचना गरिएको हो भन्ने लिखित अभिलेख राख्नु —
   ताकि भविष्यको कुनै रिफ्याक्टरले जानाजानी हटाइएको फिङ्गरप्रिन्टलाई
   भूलवश पुनः नल्याओस्।

यदि तपाईंले v3.8.6 का न्यूनीकरणहरू जारी भइसकेपछि तलका कुनै पनि कल साइटलाई
पुनः चिन्ह लगाउने स्क्यानर सञ्चालन गर्नुहुन्छ भने, कृपया स्क्यान ट्रेससहित
एउटा इश्यू खोल्नुहोस् र हामी यहाँको प्रमाणीकरण विस्तार गर्नेछौँ।

## §1 — MITM root-CA स्थापना (`77484.js`)

**स्रोत फाइलहरू**:

- `src/mitm/cert/install.ts` — सार्वजनिक `installCert()` / `uninstallCert()`,
  प्रत्येक प्लेटफर्मका लागि `installCertWindows/Mac/Linux`।
- `src/mitm/systemCommands.ts` — स्थापना पथहरूले प्रयोग गर्ने साझा `execFile` /
  `spawn` / PowerShell सहायकहरू।

**ट्रिगर**: प्रयोगकर्ताले `/dashboard/cli-tools/mitm` मा रहेको स्थानीय
ड्यासबोर्डमा "MITM प्रोक्सी सक्षम गर्नुहोस्" क्लिक गर्छ। यो रुट
loopback-only हो — `CLAUDE.md` को कडा नियम #17 र
`src/server/authz/routeGuard.ts::isLocalOnlyPath()` हेर्नुहोस्। टनेलमार्फत
उजागर भएको JWT ले यो कोड पथ ट्रिगर गर्न **सक्दैन**।

**सम्पादन गरिने विशेषाधिकारयुक्त कार्यहरू (प्रत्येक प्लेटफर्मअनुसार)**:

| OS                     | आदेश(हरू)                                                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | UAC मार्फत `certutil -addstore Root <cert>`                                                                       |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | `certutil -d sql:<profile>` मार्फत प्रत्येक प्रोफाइलको NSS DB अद्यावधिक                                           |

यी `mitmproxy`, Charles Proxy, Fiddler, र Caddy ले प्रयोग गर्ने उही आदेशहरू
हुन्। OmniRoute मा तिनीहरू रहेको तथ्य
`docs/security/STEALTH_GUIDE.md` मा दस्तावेजीकृत छ।

**v3.8.6 न्यूनीकरण**:

- `runElevatedPowerShell()` ले अब `-EncodedCommand <base64utf16le>` प्रयोग
  गर्दैन। विशेषाधिकारयुक्त पेलोडलाई प्रत्येक कलका लागि अस्थायी `.ps1` फाइलमा
  (मोड 0o600, निजी `mkdtempSync` डाइरेक्टरीभित्र) लेखिन्छ र `-File` मार्फत
  सन्दर्भित गरिन्छ। उक्त फाइललाई `finally` मा अनलिङ्क गरिन्छ। यसले
  Socket.dev को AI वर्गीकारकले चिन्ह लगाएको PowerShell मार्फत base64-विशेषाधिकार
  वृद्धिको प्रचलित फिङ्गरप्रिन्ट हटाउँछ।
- `installCertWindows` मा यहाँ सङ्केत गर्ने इनलाइन `SECURITY-AUDITOR-NOTE:`
  ब्लक समावेश छ।

**हामीले यसलाई किन राखेका छौँ**: MITM प्रोक्सी
`docs/security/STEALTH_GUIDE.md` र `docs/frameworks/MITM-PROXY.md` द्वारा
प्रयोग गरिने दस्तावेजीकृत सुविधा हो। यसलाई हटाउँदा agent-bridge सुविधा-समूह
बिग्रिनेछ।

## §2 — Zed क्रेडेन्सियल आयात (`app/api/providers/zed/import/route.js`)

**स्रोत फाइलहरू**:

- `src/app/api/providers/zed/discover/route.ts` _(v3.8.6 मा नयाँ)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(v3.8.6 मा नयाँ)_

**ट्रिगर**: प्रयोगकर्ताले स्थानीय ड्यासबोर्डको Providers
पृष्ठमा "Zed बाट आयात गर्नुहोस्" क्लिक गर्छन्। यो एन्डपोइन्ट `requireManagementAuth` द्वारा
सुरक्षित छ। Zed एडिटरले स्वयं आफ्ना प्रदायक API कुञ्जीहरूलाई दस्तावेजीकृत सेवा
नामहरूअन्तर्गत OS कीचेनमा लेख्छ — https://zed.dev/docs/ai/llm-providers हेर्नुहोस्।

**v3.8.5 को व्यवहार (Socket.dev ले फ्ल्याग गरेको)**:

`POST /import` ले क्रेडेन्सियलहरू पत्ता लगाएर एउटै राउन्ड-ट्रिपमा तिनलाई स्थानीय
SQLite स्टोरमा स्वतः सेभ गर्थ्यो। प्रत्येक खाताका लागि पुष्टि थिएन, फिङ्गरप्रिन्ट थिएन,
केवल "N वटा टोकन फेला परे, सबै आयात गरिए।"

**v3.8.6 न्यूनीकरण — २-चरणीय पुष्टि**:

1. **`POST /api/providers/zed/discover`** ले
   `{ candidates: [{ provider, service, account, fingerprint }] }` फर्काउँछ। कच्चा
   टोकन **कहिल्यै** पठाइँदैन। फिङ्गरप्रिन्ट
   `sha256(service|account|token).slice(0,16)` हो।
2. ड्यासबोर्डले उम्मेदवारहरूको सूची देखाउँछ, अपरेटरले आयात गर्नुपर्नेहरू चयन गर्छ,
   र `{ confirmedAccounts: [{ service, account, fingerprint }] }`
   लाई **`POST /api/providers/zed/import`** मा पोस्ट गर्छ।
3. आयात एन्डपोइन्टले **सर्भरमा कीचेन पुनः पढ्छ** र
   `(service, account, fingerprint)` का आधारमा फिल्टर गर्छ। छेडछाड गरिएको वा पुनः प्रयोग गरिएको discover
   प्रतिक्रियाले आयात एन्डपोइन्टलाई असम्बन्धित टोकन सेभ गर्न झुक्याउन सक्दैन —
   discover पछि लाइभ टोकन परिवर्तन भएको छ भने फिङ्गरप्रिन्ट अब
   मेल खाँदैन र उक्त क्रेडेन्सियल छोडिन्छ।

`OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` env फ्ल्यागले अझै आफ्नो स्वचालन अद्यावधिक
नगरेका अपरेटरहरूका लागि v3.8.5 को व्यवहार कायम राख्छ। यसलाई
v3.9 मा हटाइनेछ।

**हामीले यसलाई किन राखेका छौँ**: पहिले नै Zed प्रयोग गर्ने र आफ्ना प्रदायक कुञ्जीहरू
पुनः पेस्ट नगरी OmniRoute मा प्रतिलिपि गर्न चाहने प्रयोगकर्ताहरूका लागि Zed आयात
सबैभन्दा सहज अनबोर्डिङ मार्ग हो।

## §3 — `execFile` / `spawn` / उन्नत PowerShell (`21843.js`)

**स्रोत फाइलहरू**: `src/mitm/systemCommands.ts`।

**फ्ल्याग गरिनुको कारण**: यो चङ्कले `execFileWithPassword`,
`runElevatedPowerShell`, र साझा `quotePowerShell` सहायकलाई पुनः निर्यात गर्छ। Socket.dev को
AI वर्गीकारकले तिनलाई सामान्य "होस्ट कार्यान्वयन + विशेषाधिकार उन्नयन
टुलकिट" का रूपमा देख्छ। OmniRoute भित्र तिनलाई MITM प्रमाणपत्र स्थापना मार्ग
(§1) र `sudo` कमान्ड कार्यान्वयनका लागि `execFileWithPassword` ले मात्र प्रयोग गर्छ।

**v3.8.6 न्यूनीकरण**:

- `runElevatedPowerShell` को रिफ्याक्टर (§1 हेर्नुहोस्)।
- `runElevatedPowerShell` र `execFileWithPassword` दुवैमा रहेको इनलाइन
  `SECURITY-AUDITOR-NOTE:` ब्लकले अनुमति-सूचीमा रहेका कलरहरू र पिन गरिएको
  कार्यान्वयनयोग्य फाइलहरूको सूची दस्तावेजीकृत गर्छ।
- `execFileWithPassword` को `spawn()` कलमा सहायकले प्राप्त गर्न अनुमति पाएका
  कार्यान्वयनयोग्य फाइलहरूको अनुमति-सूचीसहित `nosemgrep` मार्कर छ — प्रयोगकर्ता
  इनपुटबाट `finalCommand`/`finalArgs` सम्म पुग्ने **कुनै मार्ग छैन**।

## §4 / §6 — 9router सेवा सुपरभाइजर (`api/services/9router/{start,restart}/route.js`)

**स्रोत फाइलहरू**:

- `src/app/api/services/9router/_lib.ts` — सुपरभाइजर फ्याक्ट्री।
- `src/app/api/services/9router/{start,stop,restart,status,install,update,auto-start}/route.ts`।
- `src/lib/services/ServiceSupervisor.ts` — सामान्य spawn / स्वास्थ्य-जाँच / लग-बफर।

**ट्रिगर**: प्रयोगकर्ताले स्थानीय ड्यासबोर्डको एम्बेडेड सेवा पृष्ठमा
"स्थापना गर्नुहोस्" / "सुरु गर्नुहोस्" क्लिक गर्छन्।

**पहिलेदेखि लागू सुरक्षाहरू**:

- सबै `/api/services/*` रुटहरू
  `src/server/authz/routeGuard.ts` अनुसार LOCAL_ONLY छन् (कडा नियम #17)। लुपब्याक कार्यान्वयन
  कुनै पनि प्रमाणीकरण जाँचभन्दा पहिले हुन्छ — लिक भएको JWT ले तिनमा पहुँच पाउन सक्दैन।
- 9router DB पङ्क्ति `status='not_installed', auto_start=0` का रूपमा सिड गरिएको छ (
  `src/lib/db/migrations/071_services.sql:19` हेर्नुहोस्)। सेवा पहिलो पटक
  सुरु गर्दा **चल्दैन**।
- `spawn()` लाई
  `src/lib/services/installers/ninerouter.ts` भित्रको `resolveSpawnArgs(apiKey, PORT)` ले फर्काएको बाइनरी पथसहित कल गरिन्छ,
  जुन समर्थित बाइनरीहरूको निश्चित अनुमति-सूची हो।
- Stdout/stderr मेमोरीमा बफर गरिन्छ (5 MB सीमा, `_lib.ts` हेर्नुहोस्) — प्रयोगकर्ताले
  ड्यासबोर्डबाट लगिङ सक्षम नगरेसम्म डिस्कमा लेखिँदैन।

**v3.8.6 न्यूनीकरण**: कुनै कार्यात्मक परिवर्तन छैन। न्यूनतम बिल्ड प्रोफाइल
(`OMNIROUTE_BUILD_PROFILE=minimal`) ले
`src/lib/services/installers/ninerouter.ts` लाई स्टबसँग प्रतिस्थापन गर्छ, ती प्रयोगकर्ताहरूका लागि
जो विशेषाधिकारयुक्त मार्गहरूलाई बन्डलबाट भौतिक रूपमा हटाउन चाहन्छन्।

**हामीले यसलाई किन राखेका छौँ**: 9router वैकल्पिक रूपमा स्थानीय स्तरमा स्थापना गर्न मिल्ने सहायक
सेवा हो (यसलाई WordPress-शैलीको प्लगइनजस्तो सम्झनुहोस्) — कडा अप्ट-इन।

## §5 — OmniRoute Cloud Sync क्रेडेन्सियल राइट-ब्याक (`api/keys/[id]/route.js`)

**स्रोत फाइलहरू**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`।
- `src/app/api/keys/[id]/route.ts` — `syncKeysToCloudIfEnabled()` आह्वान गर्छ।

**ट्रिगर**: `isCloudEnabled()` ले `true` फर्काउँछ (ड्यासबोर्डबाट सेट गरिएको) **र**
`CLOUD_URL` कन्फिगर गरिएको छ। दुवै बन्द हुँदा, Cloud एन्डपोइन्टमा कुनै बाह्य
नेटवर्क कल गरिँदैन।

**v3.8.5 को व्यवहार (Socket.dev ले सही रूपमा पत्ता लगाएको बग)**:

`cloudUpdatedAt > localUpdatedAt` हुँदा `updateLocalTokens()` ले Cloud प्रतिक्रियाबाट
`accessToken`, `refreshToken`, र `providerSpecificData` अधिलेखन गर्थ्यो।
कुनै HMAC, हस्ताक्षर वा चेकसम थिएन। गलत रूपमा कन्फिगर गरिएको वा दुर्भावनापूर्ण
`CLOUD_URL` (वा च्यानलमा रहेको MITM) ले प्रदायकका OAuth टोकनहरू चुपचाप
साट्न सक्थ्यो।

**v3.8.6 न्यूनीकरण**:

1. **HMAC प्रमाणीकरण**: JSON पार्स गर्नुअघि `verifyCloudSignature(rawBody, sigHeader)` ले
   `X-Cloud-Sig` हेडर (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`) जाँच गर्छ। सेक्रेट सेट गरिएको छ भने हस्ताक्षर अनिवार्य हुन्छ।
   यदि सेट गरिएको छैन भने (लेगेसी मोड), चेतावनी लग गरिन्छ र प्रतिक्रिया
   स्वीकार गरिन्छ — v3.9 मा सेक्रेट अनिवार्य हुनेछ।
2. **गोप्य फिल्ड अप्ट-इन**: `accessToken` / `refreshToken` /
   `providerSpecificData` लाई **केवल** `OMNIROUTE_CLOUD_SYNC_SECRETS=true`
   हुँदा मात्र अधिलेखन गरिन्छ। पूर्वनिर्धारित मोडले क्रेडेन्सियल नभएका
   मेटाडेटा (`expiresAt`, `status`, `lastError*`, `rateLimitedUntil`,
   `updatedAt`) मात्र सिङ्क गर्छ। रिमोट टोकन सिङ्कमा निर्भर प्रयोगकर्ताहरूका
   लागि यो एउटा **ब्रेकिङ परिवर्तन** हो — उनीहरूले स्पष्ट रूपमा अप्ट-इन गर्नुपर्छ।

**हामीले यसलाई किन कायम राख्छौँ**: टोलीका क्रेडेन्सियलहरू केन्द्रीकृत गर्न
OmniRoute Cloud टेनेन्टका लागि Cloud Sync नै एक मात्र तरिका हो। यो समाधानले
थ्रेट मोडेललाई स्पष्ट बनाउँछ: "सर्भरले हस्ताक्षर गर्छ, क्लाइन्टले प्रमाणीकरण
गर्छ, अपरेटरले अप्ट-इन गर्छ।"

## बिल्ड प्रोफाइल: `minimal`

Socket-अनुकूल आर्टिफ्याक्ट चाहिने प्रयोगकर्ताहरूले यसरी बिल्ड गर्नुहोस्:

```bash
OMNIROUTE_BUILD_PROFILE=minimal npm run build
```

webpack को `NormalModuleReplacementPlugin` ले चारवटा मोड्युललाई स्टबहरूसँग एलियास गर्छ:

| मोड्युल                                     | स्टब                                             |
| ------------------------------------------- | ------------------------------------------------ |
| `src/mitm/cert/install.ts`                  | `src/mitm/cert/install.stub.ts`                  |
| `src/lib/zed-oauth/keychain-reader.ts`      | `src/lib/zed-oauth/keychain-reader.stub.ts`      |
| `src/lib/cloudSync.ts`                      | `src/lib/cloudSync.stub.ts`                      |
| `src/lib/services/installers/ninerouter.ts` | `src/lib/services/installers/ninerouter.stub.ts` |

प्रत्येक स्टबले उही सर्फेस एक्सपोर्ट गर्छ, तर हरेक फङ्सनले रनटाइममा
`featureDisabledError(name)` थ्रो गर्छ। निष्क्रिय पारिएको मोड्युलमा निर्भर
रुटहरूले संवेदनशील कोड पाथ सक्रिय गर्नुको सट्टा स्पष्ट सन्देशसहित HTTP 503
फर्काउँछन्।

नतिजास्वरूप प्राप्त बन्डललाई `omniroute-secure` का रूपमा प्रकाशित गर्ने उद्देश्य
राखिएको छ। प्रकाशन विधिका लागि `docs/ops/PUBLISHING_SECURE.md` हेर्नुहोस्।
