TPROXY पारदर्शी डिक्रिप्ट [Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM स्ट्याकका लागि OmniRoute को **5औँ क्याप्चर मोड** हो। यसले Linux मा स्थानीय रूपमा बाहिर जाने HTTPS ट्राफिकलाई
kernel TPROXY + policy routing प्रयोग गरेर अवरोध गरी **डिक्रिप्ट** गर्छ — `/etc/hosts` स्पूफ
**नगरी** र OS-व्यापी system-proxy सेटिङहरू परिवर्तन **नगरी**। यो headless वातावरणमैत्री छ
(सफा गर्नुपर्ने DNS सम्पादनहरू हुँदैनन्) र firewall नियमहरू reboot हुँदा स्वतः फ्लस हुन्छन्।

अन्य क्याप्चर मोडहरूभन्दा फरक, TPROXY लाई प्रत्येक होस्टका लागि छुट्टाछुट्टै सेटअप आवश्यक पर्दैन: यसले लक्षित पोर्टमा रहेका
**जुनसुकै** गन्तव्य होस्टहरूलाई पारदर्शी रूपमा अवरोध गर्छ, प्रत्येक SNI hostname का लागि तत्काल जारी गरिएको
leaf certificate मार्फत TLS समाप्त गर्छ, डिक्रिप्ट गरिएको आदानप्रदान क्याप्चर गर्छ,
र अनुरोधलाई मूल गन्तव्यतर्फ पुनः इन्क्रिप्ट गर्छ।

> **Linux मा मात्र, root का लागि मात्र, opt-in।** यो मोडका लागि Linux, C toolchain मार्फत
> build गरिएको native addon, र **CAP_NET_ADMIN** capability (सामान्यतया root) आवश्यक पर्छ। यो
> loopback-only AgentBridge API पछाडि सीमित छ र पूर्वनिर्धारित रूपमा निष्क्रिय हुन्छ। कुनै पनि
> होस्टका लागि sign गर्न सक्ने विश्वसनीय MITM CA एक शक्तिशाली capability हो — [§6 सुरक्षा](#6-security) हेर्नुहोस्।

**स्रोत:** `src/mitm/tproxy/`

## §1 यो के हो र कहिले प्रयोग गर्ने

अन्य चार क्याप्चर मोडमध्ये प्रत्येकको एउटा सीमा छ:

| मोड               | ट्राफिक कसरी निर्देशित गरिन्छ                | सीमा                                                      |
| ----------------- | -------------------------------------------- | --------------------------------------------------------- |
| AgentBridge       | निश्चित होस्ट समूहको `/etc/hosts` DNS spoof  | दर्ता गरिएका IDE-agent होस्टहरू मात्र                     |
| Custom Hosts      | प्रत्येक होस्टका लागि `/etc/hosts` DNS spoof | प्रत्येक होस्टका लागि एउटा entry; hosts सम्पादन गर्न sudo |
| HTTP_PROXY        | `HTTP_PROXY`/`HTTPS_PROXY` env               | env var लाई मान्ने apps मात्र                             |
| System-wide proxy | OS proxy सेटिङहरू                            | global state परिवर्तन गर्छ; revert आवश्यक पर्छ            |

यसको सट्टा TPROXY पारदर्शी डिक्रिप्टले **kernel** तहमा ट्राफिक निर्देशित गर्छ। यसले
`mangle OUTPUT` chain मा लक्षित पोर्ट (पूर्वनिर्धारित `443`) तर्फ जाने नयाँ स्थानीय outbound TCP connection हरूलाई
चिन्ह लगाउँछ, `ip rule` ले चिन्ह लगाइएका packet हरूलाई स्थानीय delivery तर्फ पुनः route गर्छ,
र पुनः प्रवेश गर्दा `mangle PREROUTING` को `TPROXY` target ले तिनलाई
**IP_TRANSPARENT** listener लाई हस्तान्तरण गर्छ — जसले त्यसपछि TLS समाप्त गरेर plaintext क्याप्चर गर्छ।

निम्न कार्य गर्ने process बाट ट्राफिक क्याप्चर र डिक्रिप्ट गर्न चाहँदा यसलाई प्रयोग गर्नुहोस्:

- AgentBridge ले दर्ता नगरेको होस्टसँग सञ्चार गर्छ, र
- `HTTP_PROXY` लाई मान्दैन, र
- जसलाई तपाईं system-wide proxy परिवर्तन गरेर बाधा पुर्याउन चाहनुहुन्न।

अवरोध kernel मै हुने भएकाले, सुरु गर्ने process लाई **कुनै
configuration परिवर्तन** आवश्यक पर्दैन — तर उक्त process ले OmniRoute ले
स्थापना गर्ने dynamic CA लाई विश्वास गर्नुपर्छ ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) हेर्नुहोस्)।

## §2 आवश्यकताहरू

| आवश्यकता           | विवरण                                                                                                                                                                            |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**             | Linux मात्र — **IP_TRANSPARENT** Linux मा मात्र उपलब्ध socket विकल्प हो। अन्य सबै प्लेटफर्ममा loader ले "उपलब्ध छैन" फर्काउँछ।                                                   |
| **विशेषाधिकार**    | पारदर्शी socket सिर्जना गर्न र `iptables`/`ip` नियमहरू लागू गर्न **CAP_NET_ADMIN** capability आवश्यक हुन्छ — व्यवहारमा, root का रूपमा चलाउनुहोस्।                                |
| **Native addon**   | एउटा सानो N-API addon (`src/mitm/tproxy/native/transparent.c`) निर्माण गरिएको वा prebuild का रूपमा उपलब्ध गराइएको हुनुपर्छ। [§3](#3-the-native-ip_transparent-addon) हेर्नुहोस्। |
| **Kernel modules** | `TPROXY`, `mangle`, र `mark` match समर्थनसहितको `iptables` (kernel 6.8.0 विरुद्ध प्रमाणीकरण गरिएको)।                                                                             |

**सहज अवनति:** यदि कुनै आवश्यकता पूरा भएको छैन भने (गैर-Linux, toolchain छैन,
addon निर्माण भएको छैन), addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
ले त्रुटि फ्याँक्नुको सट्टा `null` फर्काउँछ। त्यसपछि capture-mode स्थितिले
`available: false` रिपोर्ट गर्छ, dashboard toggle
"TPROXY decrypt का लागि Linux + root + native addon आवश्यक छ" tooltip सहित **निष्क्रिय** हुन्छ,
र OmniRoute का बाँकी भागहरू चलिरहन्छन्।

## §3 Native IP_TRANSPARENT addon

Node को `net` module ले `bind()` गर्नुअघि `setsockopt(IP_TRANSPARENT)` गर्न सक्दैन, जुन
TPROXY लाई आवश्यक हुन्छ (अन्यथा kernel ले redirect गरिएका packet हरू छोडिदिन्छ)। यो addon
(`src/mitm/tproxy/native/transparent.c`, `binding.gyp` मार्फत निर्माण गरिएको) एउटा सानो N-API
module हो, जसले तीनवटा function उपलब्ध गराउँछ र तिनलाई `transparentSocket.ts` मार्फत प्रयोग गरिन्छ:

| Addon function                        | Socket को कार्य                                                                             | प्रयोग                                                                           |
| ------------------------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, raw fd फर्काउँछ | पारदर्शी capture listener (Node ले `server.listen({ fd })` मार्फत fd ग्रहण गर्छ) |
| `setSocketMark(fd, mark)`             | अवस्थित fd मा `setsockopt` **SO_MARK**                                                      | anti-loop (proxy का आफ्नै socket हरूमा mark लगाउन)                               |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()` **अघि** `socket()` + **SO_MARK**, fd फर्काउँछ                      | पुनः-encrypt गरिएको upstream forward (SYN ले mark बोक्छ)                         |

मूल destination लाई `socket.localAddress`/`localPort` बाट पढिन्छ — TPROXY ले
यसलाई जोगाइराख्छ, त्यसैले **SO_ORIGINAL_DST**/NAT lookup आवश्यक हुँदैन।

### Addon निर्माण गर्ने

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- `npm run build` का क्रममा, `scripts/build/build-tproxy-native.mjs` ले `node-gyp
rebuild` चलाउँछ। यो **Linux मा मात्र चल्ने र असफल हुँदा घातक नहुने** प्रक्रिया हो — toolchain नभएमा
  capture mode मात्र अनुपलब्ध रहन्छ।
- `assembleStandalone.mjs` ले `build/Release/transparent.node` लाई
  standalone bundle मा प्रतिलिपि गर्छ; `transparentSocket.ts` ले यसलाई module-relative र
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`) दुवै रूपमा resolve गर्छ।
- `build/` र `prebuilds/` git-ignored छन् — binary **निर्माण गरिन्छ, कहिल्यै
  commit गरिँदैन**।

Loader ले प्राथमिकताको क्रममा यी स्थानहरू जाँच्छ:
`native/build/Release/transparent.node`, त्यसपछि `native/prebuilds/transparent.node`
(दुवै module-relative र `<cwd>/src/mitm/tproxy/` अन्तर्गत)।

## §4 प्रति-SNI डायनामिक CA र ट्रस्ट-स्टोर इन्स्टलर

> **#6684 अद्यावधिक:** AgentBridge को स्ट्याटिक सर्भर (`src/mitm/server.cjs`) ले अब
> एउटै स्ट्याटिक self-signed leaf को सट्टा यही CA/leaf आर्किटेक्चर ढाँचा
> साझा गर्छ। यसले एउटा **छुट्टै** CA इन्स्ट्यान्स
> (`src/mitm/cert/rootCa.ts`, `<DATA_DIR>/mitm/ca.key`/`ca.crt` मा स्थायी रूपमा भण्डारण गरिएको)
> प्रयोग गर्छ र पहिलेबाट रहेको `omniroute-mitm.crt` ट्रस्ट-स्टोर स्लटअन्तर्गत
> इन्स्टल गर्छ (त्यहाँको पुरानो एकल leaf लाई प्रतिस्थापन गर्दै — दोहोरो-ट्रस्ट सफाइ आवश्यक छैन),
> र यसलाई तलको TPROXY को आफ्नै `omniroute-tproxy-ca.crt` स्लटबाट पूर्ण रूपमा
> अलग राखिन्छ। नयाँ AgentBridge इन्स्टलहरूले CA मोडेल स्वतः प्राप्त गर्छन्; पुरानो
> स्ट्याटिक leaf लाई पहिले नै विश्वास गरेको इन्स्टलले अपरेटरले
> `MITM_ROOT_CA_ENABLED=true` मार्फत सहमति नदिएसम्म त्यसैलाई प्रयोग गरिरहन्छ
> (`src/mitm/cert/migration.ts` हेर्नुहोस्) — **कुनै पनि** होस्टका लागि leaf साइन गर्न सक्ने
> विश्वसनीय MITM CA पुरानो निश्चित-SAN leaf भन्दा उल्लेखनीय रूपमा बढी
> शक्तिशाली हुन्छ, त्यसैले पहिले नै विश्वास गरिएको इन्स्टलमा यो परिवर्तन कहिल्यै
> मौन रूपमा हुँदैन।

ऐतिहासिक रूपमा, स्ट्याटिक AgentBridge MITM प्रमाणपत्रले AgentBridge ले
DNS-spoof गर्ने होस्टहरूको **निश्चित** सेटका कारण मात्र काम गर्थ्यो (अब तलको मोडेलसँग
एकीकृत गरिएको छ)। TPROXY ले **जुनसुकै** होस्टहरू इन्टरसेप्ट गर्छ, त्यसैले यसको
लिस्नरले क्लाइन्टले अनुरोध गरेको जुनसुकै SNI का लागि मान्य leaf प्रस्तुत गर्नुपर्छ —
अब AgentBridge का लागि पनि केवल 4 वटा antigravity होस्टको सट्टा सम्पूर्ण
`MITM_TOOL_HOSTS` सेट (9 वटा उपकरण प्रविष्टि) का लागि यही आवश्यकता लागू हुन्छ।

### डायनामिक CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` ले स्थानीय CA चलाउँछ (`selfsigned` dependency मा निर्मित), जसले:

- `generateMitmCa()` मार्फत दीर्घकालीन CA सिर्जना गर्छ (CN `"OmniRoute MITM CA"`,
  10-वर्षको वैधता, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-bit RSA / SHA-256)।
- `issueLeafCert()` मार्फत **मागअनुसार प्रत्येक SNI होस्टनामका लागि एउटा leaf**
  जारी गर्छ (1-वर्षको वैधता, `subjectAltName` = SNI होस्ट) र प्रत्येक होस्टनामका
  लागि एउटा `tls.SecureContext` क्यास गर्छ।
- TLS-टर्मिनेटिङ सर्भरका लागि `createSNICallback()` उपलब्ध गराउँछ ([§5](#5-how-decrypt-and-capture-work) हेर्नुहोस्)।
- पुनः सुरु गर्दा पनि CA स्थिर राख्न `existingCa` सहित निर्माण गर्न सकिन्छ
  (ताकि ट्रस्ट स्टोर पुनः इन्स्टल गर्नु नपरोस्)।

CA को निजी कुञ्जीले **मेसिन कहिल्यै छोड्दैन**।

### ट्रस्ट-स्टोर इन्स्टलर (`src/mitm/tproxy/caTrust.ts`)

इन्टरसेप्ट गरिएको क्लाइन्टले डायनामिक CA लाई विश्वास गर्नुपर्छ, त्यसैले क्याप्चर मोड
सुरु गर्दा CA प्रमाणपत्रलाई OS ट्रस्ट स्टोरमा एउटा **समर्पित स्लट** —
`omniroute-tproxy-ca.crt` (स्थिरांक `TPROXY_CA_CERT_NAME`) — अन्तर्गत इन्स्टल गरिन्छ।
यसलाई स्ट्याटिक MITM प्रमाणपत्रको स्लट (`omniroute-mitm.crt`) बाट अलग राखिन्छ,
ताकि यी दुईले कहिल्यै एक-अर्कालाई अधिलेखन नगरून्।

`installTproxyCa(caPem, sudoPassword?)` ले डिस्ट्रोको एङ्कर डाइरेक्टरी
(क्रमअनुसार: पहिले Debian शैली) पत्ता लगाउँछ र त्यससँग मिल्ने रिफ्रेस कमान्ड चलाउँछ:

| एङ्कर डाइरेक्टरी                            | रिफ्रेस कमान्ड           |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

इन्स्टल प्रक्रियाले PEM लाई अस्थायी फाइलमा स्टेज गर्छ, त्यसपछि (विशेषाधिकारसहित)
एङ्कर डाइरेक्टरीमा `mkdir -p` चलाउँछ, स्टेज गरिएको फाइललाई त्यसमा `cp` गर्छ,
र रिफ्रेस कमान्ड चलाउँछ। `uninstallTproxyCa()` ले समर्पित स्लट मात्र हटाउँछ
(स्ट्याटिक MITM प्रमाणपत्रलाई नछोई) र रिफ्रेस गर्छ — गैर-Linux प्रणालीमा यसले
कुनै काम गर्दैन।

सबै विशेषाधिकारयुक्त कमान्डहरू `execFileWithPassword` (`src/mitm/systemCommands.ts`)
मार्फत चल्छन् — **आर्गुमेन्ट एरेसहित, shell बिना, string interpolation बिना**
`spawn` (कडा नियम #13)। प्रक्रिया root हुँदा (जस्तै VPS मा), लक्ष्य सीधै चल्छ र
पासवर्ड आवश्यक पर्दैन; गैर-root डेस्कटपमा `sudoPassword` लाई stdin मा
`sudo -S` मार्फत पठाइन्छ।

> डेस्कटपको `sudoPassword` ट्रस्ट-स्टोर इन्स्टललाई अधिकार प्रदान गर्न POST body मा
> पठाइन्छ; प्रक्रिया root हुँदा यसलाई पूर्ण रूपमा बेवास्ता गरिन्छ।

## §5 डिक्रिप्ट र क्याप्चरले कसरी काम गर्छन्

पाइपलाइन (सबै `src/mitm/tproxy/` अन्तर्गत):

```
स्थानीय एप  ──TCP/443──▶  mangle OUTPUT ले जडानलाई चिन्ह लगाउँछ (fwmark)
                           ip rule → स्थानीय रुट तालिका → lo
                           mangle PREROUTING TPROXY → IP_TRANSPARENT लिसनर (पोर्ट 8443)
                               │  captureMode.ts: socket.localAddress बाट मूल गन्तव्य पढ्छ
                               ▼
                           tlsCapture.ts:
                             1. प्रति-SNI लिफ (dynamicCert) प्रयोग गरेर CLIENT को TLS-टर्मिनेट गर्छ
                             2. आन्तरिक http.Server ले डिक्रिप्ट गरिएको प्लेनटेक्स्ट पार्स गर्छ
                             3. क्याप्चर → globalTrafficBuffer.push(), source: "tproxy" सहित
                                (sanitizeHeaders + maskSecret लागू गरिएको)
                             4. बाइपास-चिन्ह लगाइएको सकेटमार्फत मूल गन्तव्यमा
                                पुनः-इन्क्रिप्ट गरी फर्वार्ड गर्छ (connectMarked, एन्टी-लुप)
                               │
                               ▼
                           मूल अपस्ट्रिम (api.example.com)
```

- **TLS टर्मिनेसन** (`createTlsCaptureServer`): डाइनामिक CA को SNI कलब्याक प्रयोग गरेर
  कच्चा इन्टरसेप्ट गरिएको सकेटलाई सर्भर-साइड `tls.TLSSocket` मा र्याप गर्छ,
  त्यसपछि डिक्रिप्ट गरिएको स्ट्रिमलाई आन्तरिक `http.Server` मा हस्तान्तरण गर्छ (मानक MITM
  टर्मिनेसन तरिका)। सकेटको जीवनकाल `MITM_IDLE_TIMEOUT_MS` द्वारा सीमित हुन्छ, ताकि
  अड्किएको टनेलले फाइल डिस्क्रिप्टरहरू समाप्त गर्न नसकोस्।
- **क्याप्चर** (`handleDecryptedRequest`): `source: "tproxy"`, `"in-flight"` बाट सुरु हुने
  स्थिति, `sanitizeHeaders()` मार्फत प्रशोधन गरिएका हेडरहरू र बफरमा प्रवेश गर्नुअघि
  `maskSecret()` मार्फत प्रशोधन गरिएका बडीहरूसहित एउटा `InterceptedRequest` पुश गर्छ।
  त्यसपछि उक्त प्रविष्टि रेस्पोन्स, साइजहरू र विलम्बतासहित अद्यावधिक गरिन्छ।
- **पुनः-इन्क्रिप्ट गरिएको फर्वार्ड** (`createForward` / `realForward`): मूल
  गन्तव्यमा पुनः-इन्क्रिप्ट गर्छ। `rejectUnauthorized` पूर्वनिर्धारित रूपमा **`true`**
  हुन्छ (पूर्वनिर्धारित रूपमा सुरक्षित) — अपस्ट्रिम सर्टिफिकेट क्लाइन्टले अनुरोध गरेको
  SNI/Host विरुद्ध प्रमाणीकरण गरिन्छ, त्यसैले मूल क्लाइन्टले अस्वीकार गर्ने कुरा नै
  प्रोक्सीले पनि अस्वीकार गर्छ।

### एन्टी-लुप (SO_MARK)

नियमहरूले नयाँ स्थानीय आउटबाउन्ड जडानहरूलाई चिन्ह लगाउने भएकाले, प्रोक्सीको **आफ्नै**
पुनः-इन्क्रिप्ट गरिएको फर्वार्ड सामान्यतया फेरि इन्टरसेप्ट हुन्थ्यो — अर्थात् अनन्त लुप।
फर्वार्ड पथले बाइपास सकेट मार्क (**SO_MARK**) प्रयोग गरेर यसबाट सुरक्षा गर्छ:

- `realForward` ले `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` मार्फत आफ्नो अपस्ट्रिम सकेट खोल्छ
  — `DEFAULT_BYPASS_MARK = 0x539` — जसले `connect()` भन्दा **अघि** **SO_MARK** सेट गर्छ,
  त्यसैले फर्वार्डको SYN ले बाइपास मार्क बोक्छ।
- `mangle OUTPUT` नियमले पहिले नै बाइपास मार्क बोकेका जडानहरूलाई बाहेक राख्छ
  (`-m mark ! --mark <bypassMark>`), त्यसैले प्रोक्सीको फर्वार्डमा **पुनः** मार्क लगाइँदैन
  र त्यो TPROXY मा पुनः प्रवेश गर्दैन।

> कार्यान्वयनसम्बन्धी टिप्पणी: बाइपास-चिन्ह लगाइएको सकेट एजेन्टको
> `createConnection` मा स्थापना गरिनुपर्छ (`https.request({ createConnection })` लाई एजेन्ट
> उपस्थित हुँदा कुनै सूचना नदिई बेवास्ता गरिन्छ), अन्यथा फर्वार्डले चिन्ह नलगाइएको सकेट
> खोल्नेछ र लुप फेरि फर्किनेछ। यो e2e-प्रमाणित एन्टी-लुप समाधान थियो।

## §7 लेनदेनात्मक फायरवाल लागू / पूर्ववत्

क्र्यास हुँदा कुनै पनि `mangle` नियम वा पुरानो रुट बाँकी रहनु हुँदैन। कमान्ड बिल्डर
(`src/mitm/tproxy/commands.ts`) र रनर (`src/mitm/tproxy/setup.ts`) ले
**पूर्ववत् प्रक्रिया लागू प्रक्रियाको ठीक उल्टो, विपरीत क्रममा हुने** सुनिश्चित गर्छन्।

`applyTproxy(cfg)` ले लागू गर्ने कमान्डहरू क्रमअनुसार चलाउँछ; **कुनै पनि** विफलता हुँदा यसले
सम्भव भएसम्म पूर्ण `revertTproxy(cfg)` चलाउँछ र त्रुटि पुनः फ्याँक्छ — त्यसैले फायरवाल
कि त पूर्ण रूपमा लागू हुन्छ वा पूर्ण रूपमा पूर्ववत् हुन्छ, कहिल्यै आंशिक रूपमा लागू हुँदैन।
`revertTproxy(cfg)` ले विपरीत कमान्डहरू उल्टो क्रममा चलाउँछ र विफलताहरूलाई बेवास्ता गर्छ
(इडेम्पोटेन्ट — निःसर्त रूपमा कल गर्न सुरक्षित, जस्तै AgentBridge को `repairMitm()`
क्लिनअपबाट)।

`validateTproxyConfig(cfg)` कुनै पनि कमान्डभन्दा पहिले चल्छ: पोर्टहरू `1–65535`
हुनुपर्छ, `mark`/`routeTable`/`bypassMark` धनात्मक पूर्णाङ्क हुनुपर्छ, र
`bypassMark`, `mark` भन्दा फरक हुनुपर्छ (एन्टि-लूप)।

### लागू गर्ने कमान्डहरू (क्रमअनुसार)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

पूर्ववत् प्रक्रियाले तिनलाई उल्टो क्रममा मेटाउँछ: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`।

> यो विधि **OUTPUT-आधारित** छ किनभने MITM प्रयोगको अवस्था _स्थानीय_ आउटबाउन्ड
> ट्राफिक (उही होस्टमा भएका एपहरू) हो, जसलाई `PREROUTING` मा भएको TPROXY ले मात्र
> देख्दैन — `PREROUTING` ले फर्वार्ड गरिएको ट्राफिक मात्र देख्छ। `OUTPUT` चेनले नयाँ
> स्थानीय जडानहरूमा चिन्ह लगाउँछ, `ip rule` ले तिनलाई स्थानीय डेलिभरी (`lo`) तर्फ
> पुनःरुट गर्छ, र त्यसपछि `PREROUTING` ले तिनलाई पारदर्शी लिसनरमा तोक्छ।

## §8 कन्फिगरेसन

सुरु गर्ने अनुरोध (`POST /api/tools/agent-bridge/tproxy`) ले निम्न
फिल्डहरू स्वीकार गर्छ, जसलाई `StartTproxyBodySchema` (`tproxy/route.ts`) द्वारा प्रमाणीकरण
गरिन्छ। सबै वैकल्पिक हुन् र नदिइएमा तिनका पूर्वनिर्धारित मान प्रयोग हुन्छन्:

| फिल्ड            | प्रकार             | पूर्वनिर्धारित | टिप्पणी                                                                                                               |
| ---------------- | ------------------ | -------------- | --------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`          | पारदर्शी रूपमा इन्टरसेप्ट गरिने गन्तव्य TCP पोर्ट                                                                     |
| **mark**         | int (≥1)           | `0x2333`       | `OUTPUT` मा सेट गरिने र `ip rule` + `PREROUTING` द्वारा मिलान गरिने फायरवाल चिन्ह                                     |
| **onPort**       | int (1–65535)      | `8443`         | पारदर्शी (**IP_TRANSPARENT**) लिसनर बाइन्ड हुने पोर्ट                                                                 |
| **routeTable**   | int (≥1)           | `233`          | `local 0.0.0.0/0` रुट राख्ने नीति-रुटिङ तालिका id                                                                     |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`        | प्रोक्सीले आफ्नै अपस्ट्रिम जडानहरूमा सेट गर्ने बाइपास सकेट चिन्ह (**SO_MARK**); `OUTPUT` मा समावेश नगरिने (एन्टि-लूप) |
| **sudoPassword** | string             | —              | गैर-root डेस्कटपका लागि मात्र: ट्रस्ट-स्टोर स्थापना अधिकृत गर्छ; root हुँदा बेवास्ता गरिन्छ                           |

TPROXY का लागि **कुनै वातावरण चरहरू छैनन्** — सबै कन्फिगरेसन
POST बडी वा माथिका पूर्वनिर्धारित मानहरूमार्फत हुन्छ।

## §9 ट्राफिक इन्स्पेक्टरबाट सक्षम गर्ने

1. **ट्राफिक इन्स्पेक्टर** (`/dashboard/tools/traffic-inspector`) खोल्नुहोस्।
2. क्याप्चर-मोड टुलबारमा **"TPROXY डिक्रिप्ट"** ⚠ बटन फेला पार्नुहोस्
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`)।
   - यदि यो "TPROXY डिक्रिप्टका लागि Linux + root + नेटिभ एडअन आवश्यक छ" भन्ने टुलटिपसहित
     **अक्षम** छ भने, यस होस्टमा नेटिभ एडअन उपलब्ध छैन (Linux नभएको,
     टुलचेन नभएको वा एडअन बिल्ड नगरिएको)। [§2](#2-requirements) र [§3](#3-the-native-ip_transparent-addon) हेर्नुहोस्।
3. बटनमा क्लिक गर्नुहोस्। यसले
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`) मार्फत
   `POST /api/tools/agent-bridge/tproxy` कल गर्छ, जसले:
   डाइनामिक CA निर्माण गर्छ, ट्रान्सपरेन्ट लिसनर खोल्छ, फायरवाल नियमहरू
   लागू गर्छ र OS ट्रस्ट स्टोरमा CA इन्स्टल गर्छ।
4. चलिरहेको बेला, टगल एम्बर रङको हुन्छ र लाइभ इन्टरसेप्ट सङ्ख्या
   (`· <interceptCount>`) देखाउँछ। इन्टरसेप्ट गरिएका अनुरोधहरू अनुरोध सूचीमा
   `source: "tproxy"` सहित देखिन्छन्।
5. रोक्नका लागि फेरि क्लिक गर्नुहोस् — `stopTproxyCaptureMode()` मार्फत
   `DELETE /api/tools/agent-bridge/tproxy` ले लिसनर बन्द गर्छ, CA अनइन्स्टल गर्छ
   र फायरवाल नियमहरू उल्टाउँछ।

क्याप्चर-मोडको स्थिति (चलिरहेको / उपलब्ध / इन्टरसेप्ट सङ्ख्या / लिसनर पोर्ट)
`GET /api/tools/agent-bridge/tproxy` बाट आउँछ (`src/mitm/tproxy/captureManager.ts` मा
`getCaptureStatus()`)। एक पटकमा **एउटा मात्र** TPROXY सेसन चल्छ —
दोस्रो सुरु गर्न खोज्दा "TPROXY क्याप्चर मोड पहिले नै चलिरहेको छ" भन्ने त्रुटिसहित अस्वीकार हुन्छ।

## §10 समस्या निवारण

### टगल अक्षम छ

नेटिभ एडअन लोड गर्न सकिँदैन। पुष्टि गर्नुहोस्: तपाईं Linux मा हुनुहुन्छ, तपाईंले एडअन
बिल्ड गर्नुभएको छ (`npm run build:native:tproxy`) र प्रक्रियाले `transparent.node`
लोड गर्न सक्छ। `isTransparentSocketAvailable()` ले टगललाई नियन्त्रण गर्छ;
एडअन नभएको अवस्थामा `GET /api/tools/agent-bridge/tproxy` ले `available: false` फर्काउँछ।

### केही पनि क्याप्चर हुँदैन

- इन्टरसेप्ट गरिएको प्रक्रियाले वास्तवमै कन्फिगर गरिएको `dport`
  (पूर्वनिर्धारित `443`) मा जडान गर्छ भनी पुष्टि गर्नुहोस्।
- प्रक्रियाले डाइनामिक CA लाई विश्वास गर्छ भनी पुष्टि गर्नुहोस्। CA
  `omniroute-tproxy-ca.crt` अन्तर्गत इन्स्टल हुन्छ; आफ्नै ट्रस्ट स्टोर भएका एपहरूमा
  (Firefox/Chrome NSS) पनि सर्टिफिकेट थप्नुपर्ने हुन सक्छ।
- सर्टिफिकेट-विश्वसनीयता / सर्भर स्वास्थ्य जाँचका लागि AgentBridge को
  **निदान** स्व-परीक्षण चलाउनुहोस् (
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md) हेर्नुहोस्)।

### क्र्यासपछि बाँकी रहेका फायरवाल नियमहरू

`revertTproxy()` लागू गर्ने कार्यको ठ्याक्कै उल्टो हो र आइडेम्पोटेन्ट छ। मोड रोक्दा
नियमहरू उल्टाइन्छन्; यदि OmniRoute सेसनको बीचमै बन्द गरिएको थियो भने, अनाथ प्रणाली
स्थिति (DNS स्पुफ, root CA, सिस्टम प्रोक्सी) उल्टाउन AgentBridge को
**मर्मत** कार्य (`POST /api/tools/agent-bridge/repair`) प्रयोग गर्नुहोस्। TPROXY का
`mangle` नियमहरू र रुट पनि रिबुट हुँदा स्वतः फ्लस हुन्छन्।

### अनन्त लुप / प्रोक्सीले आफ्नै फर्वार्डलाई इन्टरसेप्ट गर्छ

यो एन्टी-लुप अवस्था हो। `bypassMark`, `mark` भन्दा फरक छ भनी पुष्टि गर्नुहोस्
(प्रमाणीकरणले यसलाई लागू गराउँछ) र फर्वार्डले `connectMarked` प्रयोग गर्छ भनी
पुष्टि गर्नुहोस् (`realForward` मा यसले प्रयोग गर्छ)।
[§5 एन्टी-लुप](#anti-loop-so_mark) हेर्नुहोस्।
