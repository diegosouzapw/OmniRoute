Web Cookie प्रदायकहरूले OmniRoute लाई API key को सट्टा तपाईंको विद्यमान ब्राउजर सत्रमार्फत AI सेवा प्रयोग गर्न दिन्छन्। तपाईंले कुनै सेवाको वेबसाइटमार्फत पहिले नै पहुँच पाउनुभएको छ र OmniRoute ले पनि त्यही प्रमाणीकरण गरिएको सत्र प्रयोग गरोस् भन्ने चाहनुहुन्छ भने तिनीहरू उपयोगी हुन्छन्।

API-key प्रदायकहरूभन्दा फरक, Web Cookie प्रदायकहरूले तपाईंको ब्राउजरले वेबसाइटमा पठाउने प्रमाणहरू प्रयोग गरेर प्रमाणीकरण गर्छन्।

---

# सुरु गर्नुअघि

> **महत्त्वपूर्ण:** प्रमाणहरू सधैँ **प्रत्यक्ष नेटवर्क अनुरोध**बाट प्रतिलिपि गर्नुहोस्, तपाईंको ब्राउजरको cookie भण्डारणबाट **होइन**।

धेरै प्रमाणीकरण समस्याहरू गलत स्थानबाट cookies प्रतिलिपि गर्दा उत्पन्न हुन्छन्।

## Cookie भण्डारणबाट प्रतिलिपि नगर्नुहोस्

धेरैजसो ब्राउजरहरूले भण्डारण गरिएका cookies निम्न स्थानमार्फत देखाउँछन्:

```
DevTools
→ Application (वा Storage)
→ Cookies
```

यी cookies सही देखिए पनि, तिनीहरू निम्न हुन सक्छन्:

- पुराना
- अपूर्ण
- प्रमाणीकरण गरिएका अनुरोधहरूमा मात्र पठाइने cookies नभएका

यी मानहरू मान्य देखिए पनि तिनको प्रयोगले प्रमाणीकरण असफल हुन सक्छ।

## प्रत्यक्ष अनुरोधबाट प्रतिलिपि गर्नुहोस्

यसको सट्टा, सफल अनुरोधका cookies प्रयोग गर्नुहोस्:

```
DevTools
→ Network
→ पृष्ठ पुनः लोड गर्नुहोस्
→ chat वा conversation अनुरोध खोल्नुहोस्
→ Request Headers
→ Cookie
```

`Cookie` अनुरोध header मा तपाईंको ब्राउजरले सफलतापूर्वक प्रयोग गरेको ठ्याक्कै प्रमाणीकरण जानकारी हुन्छ।

धेरैजसो Web Cookie प्रदायकहरूका लागि, OmniRoute मा टाँस्नुपर्ने मान यही हो।

# सामान्य सेटअप

धेरैजसो Web Cookie प्रदायकहरूका लागि सेटअप प्रक्रिया समान हुन्छ।

1. प्रदायकको वेबसाइटमा साइन इन गर्नुहोस्।
2. ब्राउजरको Developer Tools खोल्नुहोस्।
3. **Network** tab खोल्नुहोस्।
4. पृष्ठ पुनः लोड गर्नुहोस्।
5. प्रमाणीकरण गरिएको chat वा conversation अनुरोध खोल्नुहोस्।
6. आवश्यक प्रमाणीकरण प्रमाणहरू प्रतिलिपि गर्नुहोस्।
7. OmniRoute खोल्नुहोस्।
8. **Providers → Add Provider** मा जानुहोस्।
9. आफ्नो Web Cookie प्रदायक चयन गर्नुहोस्।
10. प्रमाणहरू टाँस्नुहोस्।
11. **Test Connection** मा क्लिक गर्नुहोस्।
12. प्रदायक सुरक्षित गर्नुहोस्।

आवश्यक पर्ने ठ्याक्कै प्रमाणहरू प्रदायकअनुसार फरक हुन्छन्।

# प्रदायकका प्रमाण ढाँचाहरू

विभिन्न वेबसाइटहरूले प्रमाणीकरण जानकारी फरक-फरक तरिकाले भण्डारण गर्छन्। केहीलाई cookies मात्र आवश्यक पर्छ, जबकि अन्यलाई थप headers वा tokens पनि आवश्यक पर्न सक्छ।

| प्रदायक                         | प्रमाण ढाँचा                  | प्रदायक मार्गदर्शिका             |
| ------------------------------- | ----------------------------- | -------------------------------- |
| Claude Web                      | पूर्ण Cookie अनुरोध header    | `docs/providers/CLAUDE_WEB.md`   |
| ChatGPT Web (Codex)             | पूर्ण Cookie header           | `docs/providers/CHATGPT_WEB.md`  |
| Gemini Web                      | _(प्रमाणीकरण गर्नुहोस्)_      |                                  |
| Copilot Web                     | _(प्रमाणीकरण गर्नुहोस्)_      | `docs/providers/COPILOT-M365.md` |
| Microsoft 365 Copilot (BizChat) | WS access_token + chathubPath | `docs/providers/COPILOT-M365.md` |
| Grok Web                        | _(प्रमाणीकरण गर्नुहोस्)_      |                                  |
| ...                             | ...                           | ...                              |

> नयाँ Web Cookie प्रदायकहरू थपिँदा वा विद्यमान प्रदायकहरूका प्रमाणीकरण आवश्यकताहरू परिवर्तन हुँदा यो तालिका अद्यावधिक गर्नुहोस्।

## NoTrack (notrack-web)

NoTrack ([notrack.ai](https://notrack.ai)) साइनअप आवश्यक नपर्ने निःशुल्क उपभोक्ता च्याट प्लेटफर्म हो — पहिलो भ्रमणमा सत्र अज्ञात रूपमा सिर्जना हुन्छ र तीनवटा कुकीमार्फत कायम रहन्छ: `uid`, `si_usr_id`, र `si_ses_id`। OmniRoute ले एउटै मोडेल आईडी (`notrack-c`, उपनाम `ntw`) मार्फत उही `/api/dispatch` एन्डपोइन्टलाई प्रोक्सी गर्छ।

### जडान गर्ने चरणहरू

1. आफ्नो ब्राउजरमा [notrack.ai](https://notrack.ai) खोल्नुहोस् र अज्ञात सत्र कुकी सेट हुन दिनुहोस्।
2. **DevTools → Network** खोल्नुहोस्, पृष्ठ रिफ्रेस गर्नुहोस्, र कुनै पनि `/api` अनुरोधमा क्लिक गर्नुहोस्।
3. **Request Headers** मा पूर्ण `Cookie` हेडरको मान प्रतिलिपि गर्नुहोस्।
4. OmniRoute मा **Providers → Add Provider → NoTrack Web (Free)** मा जानुहोस्।
5. कुकी स्ट्रिङलाई `apiKey` फिल्डमा टाँस्नुहोस् र **Save** गर्नुहोस्।

OmniRoute ले टाँसिएको स्ट्रिङबाट `uid`, `si_usr_id`, र `si_ses_id` निकाल्छ र ती जोडीहरू मात्र भएको सफा `Cookie` हेडर पुनर्निर्माण गर्छ — साथै, उपस्थित हुँदा `nt_session` (लगइन गरिएका खाताहरूका लागि सेट गरिएको `ntk_…` टोकन) पनि समावेश गर्छ। यी तीनमध्ये कुनै एउटा नभएमा, अपरेटरहरूले वैकल्पिक संरचनाहरूसँग प्रयोग गर्न सकून् भनेर टाँसिएको मूल स्ट्रिङलाई अपरिवर्तित रूपमा फर्वार्ड गरिन्छ।

### मोडेल आईडीहरू

| मोडेल आईडी  | प्रदर्शन नाम | टिप्पणी                                             |
| ----------- | ------------ | --------------------------------------------------- |
| `notrack-c` | NoTrack C    | पूर्वनिर्धारित — अपस्ट्रिम डिस्प्याच मोडेल `C`।     |
| `C`         | NoTrack C    | `notrack-c` को उपनाम (मूल अपस्ट्रिम डिस्प्याच कोड)। |
| `notrack`   | NoTrack C    | `notrack-c` को उपनाम।                               |
| `ntw`       | NoTrack C    | `notrack-c` को छोटो उपनाम।                          |

चारैवटा मोडेल आईडी एउटै अपस्ट्रिम डिस्प्याच मोडेल (`C`) मा म्याप हुन्छन्।

### अनुरोध विकल्पहरू

एक्जिक्युटरले अनुरोध बडीमा यी वैकल्पिक फिल्डहरू स्वीकार गर्छ:

| बडी फिल्ड             | पूर्वनिर्धारित | उद्देश्य                                                                       |
| --------------------- | -------------- | ------------------------------------------------------------------------------ |
| `notrack_mode`        | `usual`        | डिस्प्याच मोड (स्वतन्त्र-ढाँचाको स्ट्रिङ; अपस्ट्रिमले `usual`, … स्वीकार गर्छ) |
| `notrack_max_turns`   | `6`            | जवाफ दिनुअघि अपस्ट्रिमले लिन सक्ने आन्तरिक टर्नहरूको सङ्ख्या।                  |
| `notrack_chat_id`     | `null`         | अवस्थित अपस्ट्रिम च्याट पुनः सुरु गर्नुहोस् (नयाँ च्याटका लागि नराख्नुहोस्)।   |
| `notrack_attachments` | `[]`           | अपस्ट्रिम एट्याचमेन्ट डिस्क्रिप्टरहरूको पास-थ्रु एरे।                          |
| `notrack_regenerate`  | `false`        | अघिल्लो टर्नका लागि पुनः उत्पन्न गरिएको जवाफ अनुरोध गर्न `true` सेट गर्नुहोस्। |

### क्षमताहरू

- **स्ट्रिमिङ र गैर-स्ट्रिमिङ** च्याट कम्प्लिसनहरू।
- **टुल कलिङ** — अनुरोधमा `tools: [...]` सेट गर्नुहोस्; एक्जिक्युटरले तिनलाई टुल-कल एनभेलप सम्झौतामा क्रमबद्ध गर्छ र मोडेलका प्रतिक्रियाहरूलाई पुनः OpenAI `tool_calls` मा पार्स गर्छ।
- **`response_format`** — `json_object` र `json_schema` समर्थित छन्। एक्जिक्युटरले मोडेलको जवाफबाट पहिलो JSON वस्तु निकाल्छ र फिर्ता गर्नुअघि त्यसलाई स्ट्रिङमा रूपान्तरण गर्छ।
- **रिजनिङ सङ्केत** — अपस्ट्रिमले `thinking` इभेन्ट पठाउँदा एक्जिक्युटरले `reasoning` डेल्टा उत्सर्जन गर्छ।

### सीमितताहरू

- अपस्ट्रिमले अज्ञात प्रयोगका कोटाहरू लागू गर्छ — सीमा नाघेमा, एक्जिक्युटरले प्रयोगकर्तामैत्री सन्देशसहित 429 देखाउँछ।
- सबै मोडेल आईडीहरू एउटै अपस्ट्रिम डिस्प्याच मोडेलमा समाधान हुन्छन्; प्रत्येक मोडेलका लागि छुट्टै स्विच छैन।
- एक्जिक्युटरले अपस्ट्रिमको `/api/chats` एन्डपोइन्ट कल गर्दैन, त्यसैले च्याट इतिहास / सत्रहरू स्वतः व्यवस्थापन हुँदैनन्। अवस्थित अपस्ट्रिम च्याट पुनः सुरु गर्न `notrack_chat_id` प्रयोग गर्नुहोस्।

# वेब कुकी प्रदायकहरूले के गर्न सक्छन् र के गर्न सक्दैनन्

वेब कुकी प्रदायकहरूले वेबसाइटको च्याट इन्टरफेस पुनः प्रयोग गर्छन्। तिनले आधिकारिक API हरूजस्तै समान क्षमताहरू **प्रदान गर्दैनन्**।

## समर्थित

- तपाईंको विद्यमान ब्राउजर सत्र प्रयोग गरेर प्रमाणीकरण गर्ने
- तपाईंको खातामार्फत उपलब्ध मोडेलहरूमा पहुँच गर्ने
- च्याट प्रतिक्रियाहरू स्ट्रिम गर्ने
- API कुञ्जी आवश्यक नपर्ने

## समर्थित छैन

- फङ्सन कलिङ
- टुल कलिङ
- स्वचालित फाइल सम्पादन
- एजेन्टिक IDE कार्यप्रवाहहरू
- API-मा मात्र उपलब्ध सुविधाहरू

यो अपेक्षित व्यवहार हो र **बग होइन**।

यदि तपाईंलाई टुल कार्यान्वयन, स्वचालित फाइल सम्पादन वा अन्य एजेन्ट कार्यप्रवाहहरू आवश्यक छन् भने, Web Cookie प्रदायकको सट्टा **API-key प्रदायक** प्रयोग गर्नुहोस्।

# प्रमाणीकरणसम्बन्धी सावधानी

सफल **Test Connection** वा कुकी प्रमाणीकरणले उपलब्ध गराइएका प्रमाणहरू अपेक्षित ढाँचामा देखिन्छन् भन्ने मात्र पुष्टि गर्छ।

Issue #7857 समाधान नभएसम्म, सफल प्रमाणीकरणले प्रदायक सफलतापूर्वक प्रमाणीकृत हुनेछ भन्ने **ग्यारेन्टी गर्दैन**।

यदि प्रमाणीकरण अझै असफल हुन्छ भने, तपाईंले प्रमाणहरू ब्राउजरको कुकी भण्डारणबाट नभई सक्रिय नेटवर्क अनुरोधबाट प्रतिलिपि गर्नुभएको हो भनी सुनिश्चित गर्नुहोस्।

---

# समस्या निवारण

## प्रमाणीकरण असफल हुन्छ

प्रमाणहरू यहाँबाट प्रतिलिपि गरिएको हो भनी सुनिश्चित गर्नुहोस्:

```
Network
→ Request Headers
→ Cookie
```

र यहाँबाट **होइन**:

```
Application
→ Cookies
```

---

## कुकी ब्राउजरमा काम गर्छ तर OmniRoute मा गर्दैन

केही प्रदायकहरूले प्रमाणीकृत अनुरोधहरूका क्रममा मात्र पठाइने कुकीहरू समावेश गर्छन्।

कुनै वार्तालाप सफलतापूर्वक खोलेपछि नयाँ नेटवर्क अनुरोधबाट प्रमाणहरू पुनः प्रतिलिपि गर्नुहोस्।

---

## सत्रको म्याद समाप्त भयो

Web Cookie प्रदायकहरूले तपाईंको विद्यमान ब्राउजर सत्र प्रयोग गर्छन्।

यदि तपाईंको ब्राउजर सत्रको म्याद समाप्त हुन्छ वा तपाईं साइन आउट गर्नुहुन्छ भने, तपाईंले प्रमाणहरूको नयाँ सेट प्रतिलिपि गर्नुपर्छ। समर्थित वेब प्रदायकहरूका लागि कुकी नवीकरण स्वचालित गर्न, सहायक टुल [Browser Session Sync Extension](../guides/SESSION-SYNC-EXTENSION.md) हेर्नुहोस्।

## Test Connection सफल हुन्छ तर अनुरोधहरू असफल हुन्छन्

Issue #7857 समाधान नभएसम्म, प्रमाणीकरण सफल हुनुले प्रमाणीकरण अनुरोध सफल हुनेछ भन्ने ग्यारेन्टी गर्दैन।

थप समस्या निवारण गर्नुअघि नयाँ प्रमाणीकृत अनुरोधबाट आफ्ना प्रमाणहरू पुनः प्रतिलिपि गर्नुहोस्।

# प्रदायकको उदाहरण

प्रदायक-विशिष्ट पूर्ण चरणबद्ध निर्देशनका लागि, हेर्नुहोस्:

- **Claude Web** — `docs/providers/CLAUDE_WEB.md`

Claude Web गाइडले Web Cookie प्रदायकका लागि पूर्ण सेटअप प्रक्रिया प्रदर्शन गर्छ र सन्दर्भ कार्यान्वयनको रूपमा काम गर्छ।

# उत्तम अभ्यासहरू

- नयाँ प्रमाणीकृत अनुरोधबाट प्रमाणहरू प्रतिलिपि गर्नुहोस्।
- पुराना कुकीहरू पुनः प्रयोग नगर्नुहोस्।
- Web Cookie प्रदायकहरू प्रयोग गर्दा आफ्नो ब्राउजर सत्र सक्रिय राख्नुहोस्।
- प्रतिलिपि गरिएका कुकीहरूलाई संवेदनशील प्रमाणका रूपमा व्यवहार गर्नुहोस्।
- तपाईंलाई फङ्सन कलिङ वा एजेन्ट कार्यप्रवाहहरू आवश्यक हुँदा API-key प्रदायकहरू प्रयोग गर्नुहोस्।
