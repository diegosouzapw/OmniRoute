## शून्य-कन्फिग स्वतः-राउटिङ (`auto/` उपसर्ग)

> **नयाँ:** कम्बो सिर्जना गर्न आवश्यक छैन। कुनै पनि क्लाइन्टमा सीधै `auto/` उपसर्ग प्रयोग गर्नुहोस्।

### द्रुत उदाहरणहरू

| मोडेल ID       | भेरियन्ट       | व्यवहार                                                             |
| -------------- | -------------- | ------------------------------------------------------------------- |
| `auto`         | पूर्वनिर्धारित | सबै जडान भएका प्रदायकहरू, LKGP रणनीति, सन्तुलित भारहरू              |
| `auto/coding`  | कोडिङ          | गुणस्तर-प्राथमिक भारहरू, कोड उत्पादनका लागि उपयुक्त                 |
| `auto/fast`    | छिटो           | न्यून-विलम्बता भारित छनोट                                           |
| `auto/cheap`   | सस्तो          | लागत-अनुकूलित राउटिङ (सबैभन्दा कम लागत पहिले)                       |
| `auto/offline` | अफलाइन         | सबैभन्दा बढी कोटा उपलब्धता भएका प्रदायकहरूलाई प्राथमिकता दिन्छ      |
| `auto/smart`   | स्मार्ट        | अझ राम्रो मोडेल खोजका लागि गुणस्तर-प्राथमिक + उच्च अन्वेषण दर (10%) |
| `auto/lkgp`    | lkgp           | स्पष्ट LKGP (पूर्वनिर्धारित `auto` सरह)                             |
| `auto/chaos`   | केअस           | दृढता परीक्षणका लागि त्रुटि-इन्जेक्सन भारहरू (केअस इन्जिनियरिङ)     |

### श्रेणी × टियर संयोजन (`auto/<category>:<tier>`)

OpenRouter-शैलीका प्रत्ययहरूले **कस्तो प्रकारको रुट** (श्रेणी) लाई **यसलाई कसरी अनुकूलन गर्ने** (टियर) बाट अलग गर्छन्, त्यसैले तपाईंले तिनलाई स्वतन्त्र रूपमा संयोजन गर्न सक्नुहुन्छ (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **श्रेणीहरू** (क्षमताका आधारमा उम्मेदवार पूल फिल्टर गर्नुहोस्): `coding` · `reasoning` · `vision` · `chat` · `multimodal`। `vision`/`multimodal` ले भिजन-समर्थ मोडेलहरू राख्छन्; `reasoning` ले तर्क/चिन्तन मोडेलहरू राख्छ।
- **टियरहरू** (स्कोरिङ भारहरू / पूल फिल्टर छान्नुहोस्): `fast` (द्रुत-वितरण) · `cheap` (उपनाम `floor`, लागत-बचतकर्ता) · `reliable` (सर्किट-ब्रेकर स्वास्थ्य + विलम्बता स्थिरता) · `free` / `pro` (`classifyTier` मार्फत मोडेल टियरअनुसार पूल फिल्टर गर्नुहोस् — निःशुल्क-टियर बनाम प्रिमियम)।

| उदाहरण                 | यसमा समाधान हुन्छ                                    |
| ---------------------- | ---------------------------------------------------- |
| `auto/coding:fast`     | कोडिङ पूल, न्यून-विलम्बता भारहरू                     |
| `auto/coding:cheap`    | कोडिङ पूल, लागत-अनुकूलित (उपनाम `auto/coding:floor`) |
| `auto/reasoning:pro`   | तर्क/चिन्तन मोडेलहरू मात्र, प्रिमियम टियर            |
| `auto/vision`          | भिजन-समर्थ मोडेलहरू (टियर छैन → सन्तुलित भारहरू)     |
| `auto/multimodal:free` | मल्टिमोडल-समर्थ मोडेलहरू, निःशुल्क टियर मात्र        |

कुनै पनि मान्य `auto/<category>[:<tier>]` मागअनुसार समाधान हुन्छ; छनोट गरिएको उपसमूह `/v1/models` र ड्यासबोर्डमा विज्ञापित हुन्छ (`open-sse/services/autoCombo/builtinCatalog.ts` मा `AUTO_SUFFIX_VARIANTS`)। फिल्टरिङ **फेल-ओपन** हुन्छ — यदि कुनै बाधासँग कुनै पनि जडान भएको मोडेल मेल खाँदैन भने, राउटिङ कहिल्यै नबिग्रियोस् भनेर पूर्ण पूल प्रयोग गरिन्छ। मुख्य स्कोरर (`combo.ts`) अपरिवर्तित छ; श्रेणी/टियर फिल्टर `buildAutoCandidates` मा लागू गरिन्छ।

> **लाइभ मोडेल इन्टेलिजेन्स:** `ARENA_ELO_SYNC_ENABLED` फ्ल्याग सक्रिय हुँदा स्वतः-राउटिङको उपयुक्तता लाइभ **Arena ELO** र्याङ्किङहरू + **models.dev** टियर डेटाद्वारा निर्देशित हुन्छ (अन्यथा स्थिर फिटनेस म्यापमा फर्किन्छ)।

**कसरी प्रयोग गर्ने:**

```bash
# OpenAI ढाँचा समर्थन गर्ने कुनै पनि IDE वा CLI उपकरण
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# आफ्नो कोड/कन्फिगमा मोडेल यसरी सेट गर्नुहोस्:
model: "auto"                 # सन्तुलित पूर्वनिर्धारित
model: "auto/coding"          # कोडिङ कार्यहरूका लागि उत्कृष्ट
model: "auto/fast"            # उपलब्धमध्ये सबैभन्दा छिटो
model: "auto/cheap"           # प्रति टोकन सबैभन्दा सस्तो
```

**के हुन्छ:**

1. OmniRoute ले `src/sse/handlers/chat.ts` मा `auto/` उपसर्ग पत्ता लगाउँछ
2. डेटाबेसबाट सबै **सक्रिय प्रदायक जडानहरू** क्वेरी गर्छ
3. मान्य क्रेडेन्सियलहरू (API कुञ्जी वा OAuth टोकन) भएकाहरूमा फिल्टर गर्छ
4. प्रत्येक जडानका लागि मोडेल निर्धारण गर्छ (`connection.defaultModel` वा प्रदायकको पहिलो मोडेल)
5. मेमोरीमै **भर्चुअल कम्बो** निर्माण गर्छ (DB मा भण्डारण गरिँदैन)
6. चयन गरिएको भेरियन्टको भार प्रोफाइल + LKGP रणनीति प्रयोग गरेर रुट गर्छ

**मुख्य विशेषताहरू:**

- ✅ **सधैँ सक्रिय:** कुनै टगल, कम्बो सिर्जना वा कन्फिगरेसन आवश्यक छैन
- ✅ **गतिशील:** हाल जडान भएका प्रदायकहरूलाई स्वचालित रूपमा प्रतिबिम्बित गर्छ
- ✅ **सत्र स्थायित्व:** LKGP ले पछिल्लो सफल प्रदायकलाई प्राथमिकता दिइने सुनिश्चित गर्छ
- ✅ **बहु-खाता सचेत:** प्रत्येक प्रदायक जडान छुट्टै उम्मेदवार बन्छ
- ✅ **DB लेखन हुँदैन:** भर्चुअल कम्बो अनुरोधका लागि मात्र अस्तित्वमा रहन्छ, स्थायित्वसम्बन्धी अतिरिक्त भार शून्य हुन्छ

### प्रति-कुञ्जी उम्मेदवार नियन्त्रण (#7819, स्तर 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` पछिको प्रत्यय, वा
आधार च्यानलका लागि शाब्दिक `auto`) एउटा **पढ्न-मात्र** एन्डपोइन्ट हो जसले
अवस्थित दृढता रिडहरू पुनः प्रयोग गर्दै (`state` को कच्चा ब्रेकर कहिल्यै होइन), लाइभ पहुँचयोग्यतासहित सजाइएको
`auto/*` च्यानलको हालको उम्मेदवार पूल सूचीबद्ध गर्छ:

- प्रदायक सर्किट ब्रेकर — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- जडान कूलडाउन — समाधान गरिएको
  `provider_connections` पङ्क्तिमा `rateLimitedUntil` / `testStatus`
- मोडेल लकआउट — `isModelLocked(provider, connectionId, model)`

प्रत्येक candidate ले यस API कुञ्जीको `excluded` flag पनि बोक्छ। Exclusion हरू
प्रति-API-कुञ्जी (`auto_candidate_overrides` table, migration `128`) का आधारमा भण्डारण गरिन्छन् — OmniRoute
मा `users` table नभएको single-tenant संरचना छ, त्यसैले `apiKeyId` नै सबैभन्दा नजिकको वास्तविक प्रति-caller
पहिचान हो — र pure, unit-tested
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) मार्फत
`open-sse/services/autoCombo/virtualFactory.ts` को candidate-pool chokepoint मा लागू गरिन्छ।
यो filter **fail-open** हो: सेट नगरिएको apiKeyId/channel वा DB lookup failure दुवैले
pool लाई filter नगरिएको अवस्थामै छोड्छन्, त्यसैले कुनै override configure नगरेको operator ले routing लाई
यस feature अघिको जस्तै byte-identical रूपमा देख्छ।

**Follow-up issue का लागि स्थगित:** प्रति-candidate weight + स्पष्ट ordering (Level 3
— विद्यमान weighted/priority strategy path हरूमा feed हुन्छ) र प्रत्येक `auto/*` channel का लागि कुनै विशिष्ट
`combo.ts` strategy pin गर्ने (Level 4)। Single-tenant model लाई विचार गर्दा override हरू
प्रति-API-कुञ्जी नै रहनुपर्छ वा global हुनुपर्छ भन्ने खुला प्रश्नका लागि #7819 plan हेर्नुहोस्।

**पर्दा पछाडि:**

```txt
अनुरोध: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts ले prefix पत्ता लगाउँछ
   ↓
createVirtualAutoCombo('coding') → सक्रिय connection हरूबाट candidatePool
   ↓
handleComboChat (persisted combo हरूमा प्रयोग हुने उही engine)
   ↓
Auto-scoring ले प्रत्येक अनुरोधका लागि उत्कृष्ट provider/model चयन गर्छ
```

## वास्तविक Model Id सँग मेल खाने Combo नामहरू

कुनै combo को `name` ठ्याक्कै bare model id सँग समान हुनु (उदाहरणका लागि, `gpt-5.5` नाम भएको combo) **जानाजानी प्रयोग गरिने, समर्थित ढाँचा** हो, bug होइन: यो [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) मा दस्तावेज गरिएको प्रत्येक model-id का लागि provider fallback संयन्त्र हो। bare-model-id resolution भन्दा पहिले combo resolution जाँचिने भएकाले (`src/sse/services/model.ts` मा `getComboForModel()`), bare id `gpt-5.5` को अनुरोधलाई सिधै एउटै provider तर्फ पठाउनुको सट्टा combo का targets (उदाहरणका लागि, `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) मार्फत route गरिन्छ — यसले [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) का लागि बनाइएको combo-before-rewrite precedence पुनः प्रयोग गर्छ र `tests/unit/responses-combo-resolution-3227.test.ts` तथा `tests/unit/combo-name-codex-responses-rewrite.test.ts` द्वारा regression परीक्षण गरिएको छ।

वास्तविक model id लाई छायामा पार्ने नामसहित combo सिर्जना वा पुनःनामकरण गर्दा त्यसलाई **कहिल्यै अस्वीकार गरिँदैन** — त्यसो गर्दा यो दस्तावेज गरिएको workflow बिग्रन्थ्यो। यसको सट्टा (#8530), (नयाँ) नाम वास्तविक model id सँग बाझिँदा `POST /api/combos` र `PUT /api/combos/[id]` ले response मा non-blocking `warning` field संलग्न गर्छन्:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

Boot हुँदा, `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) ले model id लाई छायामा पार्ने प्रत्येक विद्यमान combo सूचीकृत गर्दै एक-लाइनको `[STARTUP]` warning पनि log गर्छ, जसले जानाजानी (#6940 अनुसार) नभई संयोगवश यस्तो अवस्थामा पुगेका operators लाई संकेत दिन्छ। Detection helper `src/lib/combos/modelNameCollision.ts` मा छ।

## Client बाट Custom Combo कल गर्ने

Persist गरिएका combos (Settings → Combos) client ले `model` field मा combo को **ठ्याक्कै मिल्ने नाम** पठाउँदा मात्र प्रयोग हुन्छन् — combo नामको fuzzy वा partial matching हुँदैन, र `auto/` prefix पनि संलग्न हुँदैन। Resolution क्रम (`src/sse/services/model.ts` मा `getComboForModel()`):

1. combo नामको ठ्याक्कै match (`model: "my-combo"`),
2. `combo/<name>` prefix (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`)।

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

दुईवटा सामान्य समस्या:

- **`auto` ले तपाईंका combos प्रयोग गर्दैन।** `auto`/`auto/*` ले आफ्नै zero-config candidate pool बनाउँछ र कुनै combo को नाम अक्षरशः `auto` भएमा मात्र persist गरिएका combos हेर्छ (सिफारिस गरिँदैन)। combo मार्फत route गर्न, त्यसको ठ्याक्कै नाम पठाउनुहोस् — `auto` होइन।
- **`openrouter/auto` एउटा वास्तविक सशुल्क OpenRouter product** ("Auto Best Available") हो, OmniRoute alias होइन। यो OpenRouter registry (`open-sse/config/providers/registry/openrouter/index.ts`) को एकल static model entry हो र यसको billing छुट्टै हुन्छ। यसलाई `auto` pools बाट हटाउन Settings → Routing → Hide paid models प्रयोग गर्नुहोस्।

यहाँ दस्तावेज गरिएको मूल अन्योलबारे [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) र [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) हेर्नुहोस्।

## यसले कसरी काम गर्छ (स्थायी रूपमा भण्डारण गरिएका Auto-Combos)

Auto-Combo Engine ले **16-कारक स्कोरिङ प्रकार्य** (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` मा परिभाषित) प्रयोग गरेर प्रत्येक अनुरोधका लागि उत्कृष्ट प्रदायक/मोडेल गतिशील रूपमा चयन गर्छ। पूर्वनिर्धारित भारहरूको योगफल `1.0` हुन्छ; अनुकूलन गरिएका भारहरूलाई `normalizeScoringWeights()` द्वारा पुनः सामान्यीकरण गरिन्छ। सोह्रमध्ये दुई — `cacheAffinity` र `resetWindowAffinity` — को पूर्वनिर्धारित भार `0` छ; `reliability` को भार `DEFAULT_WEIGHTS` मा `0` भए पनि सामान्य प्याकहरूमा `0.03` र `reliability-first` मा `0.04` छ, र `quality` को भार प्याकहरूमा `0.02` (`quality-first` मा `0.03`) छ: तिनलाई अझै पनि प्रत्येक उम्मेदवारका लागि गणना गरिन्छ, र `cacheAffinity` ले स्कोरबाहिर prompt-cache डिडुप्लिकेसनलाई नियन्त्रित गर्छ, त्यसैले शून्य-पूर्वनिर्धारित कारकहरूले पूर्वनिर्धारित रूपमा मत दिँदैनन् तर प्याकहरूले दिन्छन्।

| `X-OmniRoute-Effort`          | `auto` (अन्य मानहरू आरक्षित छन्)                                                                                                                                                              | अनुकूलनीय सोच बजेट: अनुरोधमा कुनै पनि स्वरूपको रिजनिङ फिल्ड (`reasoning_effort`, `reasoning`, `thinking`) **नहुँदा**, गेटवेले निर्धारणात्मक अनुरोध-संरचना सङ्केतहरू (अन्तिम-प्रयोगकर्ता-सन्देशको लम्बाइ, अन्तिम प्रयोगकर्ता सन्देशसम्मको कन्टेक्स्ट आकार, अघिल्ला टुल परिणामहरू, टुल-लुपको गहिराइ) बाट `auto` लाई `low`/`medium`/`high` मा निर्धारण गर्छ। सङ्केतहरू हालको टर्नमा सीमित हुन्छन् — अन्तिम प्रयोगकर्ता सन्देशपछिका सबै कुरा बेवास्ता गरिन्छन् — त्यसैले टुल लुपको हरेक अनुरोध एउटै स्तरमा निर्धारण हुन्छ (प्रति-टर्न स्टेटलेस पिन, कुनै सेसन स्टेट हुँदैन, अपस्ट्रिम प्रम्प्ट-क्यास प्रिफिक्सहरू बिगार्ने मध्य-लुप एस्केलेसन हुँदैन)। क्लाइन्टले स्पष्ट रूपमा दिएको रिजनिङ फिल्डले सधैँ प्राथमिकता पाउँछ। यो ती अनुरोधहरूमा सीमित छ जसको अपस्ट्रिम डिस्प्याच OpenAI Chat Completions स्वरूप (`targetFormat === FORMATS.OPENAI`) मा निर्धारण हुन्छ — `reasoning_effort` OpenAI-स्वरूपको फिल्ड भएकाले Claude वा Gemini लाई लक्षित अनुरोधमा यो हेडरले कुनै प्रभाव पार्दैन (`open-sse/handlers/chatCore/adaptiveEffortWiring.ts` हेर्नुहोस्)। |

```bash
# सबैभन्दा छिटो प्रोफाइल प्रयोग गर्न बाध्य पार्नुहोस्, यो अनुरोधलाई $0.05 मा सीमित गर्नुहोस्, र सीमाभन्दा बढी खर्च गर्नुको सट्टा पूर्ण रूपमा रोक्नुहोस्
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "X-OmniRoute-Mode: fast" \
  -H "X-OmniRoute-Budget: 0.05" \
  -H "X-OmniRoute-Budget-Fallback: strict" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hi"}]}'
```

रिजोल्युसन एउटा शुद्ध फङ्सन (`open-sse/services/autoCombo/requestControls.ts`) हो; समाधान गरिएका मानहरू इन्जिनका विद्यमान `config.modePack` / `config.budgetCap` /
`config.budgetFallback` इनपुटहरूमा पठाइन्छन्। कुनै कम्बोमा भण्डारण गरिएको `config.budgetFallback` ("strict" |
"cheapest") ले स्थायी नीति सेट गर्छ; हेडरले त्यसलाई एउटै अनुरोधका लागि ओभरराइड गर्छ।

### `weighted` को व्यवहार

`weighted` भनेको **प्रत्येक अनुरोधका लागि अनुपातिक यादृच्छिक ड्र** हो
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), बराबरी गर्ने संयन्त्र होइन:

- प्रत्येक अनुरोधले `weight / totalWeight` सम्भावनाका साथ **एउटा** चरण ड्र गर्छ; बाँकी चरणहरूलाई
  त्यस अनुरोधको फलब्याक शृङ्खलाका रूपमा भारको घट्दो क्रममा राखिन्छ।
- `0` भार भएको (वा भार उल्लेख नभएको) चरणलाई, अन्य कुनै चरणको
  भार > 0 हुँदासम्म, **कहिल्यै ड्र गरिँदैन** — ड्र गरिएको चरण असफल भएपछि मात्र त्यसले फलब्याकका रूपमा काम गर्न सक्छ। **सबै**
  भारहरू 0 हुँदा मात्र चयन समान सम्भावनायुक्त हुन्छ।
- पूर्ण रूपमा अनुपलब्ध लक्ष्य भएका चरणहरू — प्रदायक सर्किट ब्रेकर `OPEN`, जडान
  कूलडाउन, मोडेल लकआउट — ड्र हुनुअघि नै हटाइन्छन्
  (`open-sse/services/combo/targetResolution.ts`), त्यसैले एउटा मात्र स्वस्थ चरणले अस्थायी रूपमा
  प्रत्येक अनुरोध जित्न सक्छ।
- `stickyWeightedLimit` (कम्बो कन्फिग, पूर्वनिर्धारित `1` = बन्द) ले पुनः ड्र गर्नुअघि ड्र गरिएको चरणलाई त्यति नै
  लगातार सफलताहरूका लागि स्थिर राख्छ।

कडा चक्रीय क्रमका लागि `round-robin` प्रयोग गर्नुहोस्; `weighted` मा समान भारहरूले सांख्यिकीय सन्तुलन दिन्छन् —
कडा सन्तुलन होइन।

## फ्युजन रणनीति

`fusion` एउटा यस्तो रणनीति हो जसले कुनै एकल लक्ष्य चयन **गर्दैन**। यसले प्रम्प्टलाई
**प्रत्येक प्यानल मोडेलमा समानान्तर रूपमा** पठाउँछ, त्यसपछि कन्फिगर गर्न मिल्ने **निर्णायक मोडेल** ले
सबै प्यानल प्रतिक्रियाबाट एउटा अन्तिम उत्तर संश्लेषण गर्छ। यो upstream `decolua/9router`
(OpenRouter को Fusion डिजाइन) बाट पोर्ट गरिएको हो; यसको कार्यान्वयन `open-sse/services/fusion.ts` मा छ।

यसले कसरी काम गर्छ:

0. **उपकरणयुक्त बाइपास** — गैर-रिक्त `tools` एरे भएको र `tool_choice` लाई स्पष्ट रूपमा
   `"none"` नतोकिएको अनुरोधले प्यानललाई पूर्ण रूपमा छोड्छ: यो अपरिवर्तित रूपमा पास गरिएका
   `tools`/`tool_choice` सहित सिधै एउटा मोडेलमा (कन्फिगर गरिएको निर्णायक, वा `panel[0]`)
   रुट हुन्छ। प्यानल सदस्यहरूसँग उपकरण पहुँच हुँदैन र निर्णायकको संश्लेषण निर्देशनले
   उपकरण-कल उत्सर्जनलाई निरुत्साहित गर्छ, त्यसैले एजेन्टिक/उपकरण-कल गर्ने क्लाइन्टहरूले
   संश्लेषित गद्यको सट्टा वास्तविक उपकरण-कल निर्णय प्राप्त गर्छन् (#6771)।
1. **फ्यान-आउट** (उपकरणरहित अनुरोधहरूमा मात्र) — प्रम्प्टलाई सबै प्यानल
   मोडेलमा एकैपटक पठाइन्छ, उपकरणहरू हटाएर नन-स्ट्रिमिङ हुन बाध्य पारिन्छ (निर्णायकलाई
   संश्लेषण गर्न पूर्ण गद्य चाहिन्छ)।
2. **कोरम-ग्रेस सङ्कलन** — `minPanel` उत्तरहरू प्राप्त हुनेबित्तिकै पछाडि परेकाहरूका लागि
   छोटो ग्रेस टाइमर सुरु हुन्छ, त्यसपछि सङ्कलन भएका उत्तरहरू लिएर फ्युजन अगाडि बढ्छ।
   यसले सबैभन्दा ढिलो मोडेलका कारण कुल प्रतीक्षा समयमा पर्ने असरलाई सीमित गर्छ, जुन
   हार्ड टाइमआउटद्वारा बाँधिएको हुन्छ।
3. **निर्णायक संश्लेषण** — प्यानल उत्तरहरूलाई अज्ञातीकृत गरिन्छ (`Source 1`, `Source 2`, … — ताकि
   निर्णायकले मोडेल ब्रान्ड होइन, विषयवस्तुको महत्त्व मूल्याङ्कन गरोस्) र निर्णायकलाई दिइन्छ, जसले
   सहमति / विरोधाभास / आंशिक समेटाइ / अद्वितीय अन्तर्दृष्टि / छुटेका पक्षहरूको विश्लेषण गर्छ, त्यसपछि
   **एउटा** आधिकारिक उत्तर लेख्छ। निर्णायक कलले क्लाइन्टको मूल
   `stream` फ्ल्याग + उपकरणहरू कायम राख्छ, त्यसैले स्ट्रिमिङ र डाउनस्ट्रिम उपकरण प्रयोग अझै काम गर्छ।
4. **सहज अवनति** — 0 प्यानल उत्तर → `503`; ठ्याक्कै 1 बाँकी उत्तर → त्यो उत्तर
   सिधै फर्काइन्छ (फ्युज गर्न केही हुँदैन); एकल-मोडेल प्यानलले सिधै उत्तर दिन्छ।

प्यानल सदस्य अर्को कम्बोलाई सन्दर्भ गर्ने `combo-ref` चरण (`{kind: "combo-ref", comboName: "..."}`) पनि हुन सक्छ
— यो **एउटा ब्ल्याक-बक्स प्यानल आवाज** का रूपमा समाधान हुन्छ (सन्दर्भित कम्बोमा पूर्ण पुनरावर्ती डिस्प्याच,
त्यस कम्बोका आफ्नै लक्ष्यहरूको फ्यान-आउट होइन), र यसमा अन्य हरेक combo-ref प्रयोग गर्ने रणनीतिले
पहिलेदेखि प्रयोग गर्ने उही गहिराइ/चक्र सुरक्षा लागू हुन्छ (#6764)।

| `config.fusionTuning.minPanel`           | `number` | `2`                | ग्रेस टाइमर सुरु हुनुअघि आवश्यक सफल उत्तरहरू (`[2, panelSize]` भित्र सीमित गरिन्छ) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`             | कोरम पुगेपछि पछाडि परेकाहरूका लागि कति समय पर्खने                                  |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`            | एउटा अड्किएको मोडेलले अनुरोध रोक्न नसकोस् भनेर तोकिएको पूर्ण अधिकतम सीमा           |

पूर्वनिर्धारित मानहरू `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) मा छन्।

## भर्चुअल अटो-कम्बो फ्याक्ट्री

Auto Combo इन्जिनलाई पूर्व-परिभाषित कम्बोहरू आवश्यक पर्दैन। यसको सट्टा, `open-sse/services/autoCombo/virtualFactory.ts` ले तत्कालै उम्मेदवारहरू निर्माण गर्छ:

1. `getProviderConnections({ isActive: true })` (सबै सक्षम जडानहरू) प्राप्त गर्छ
2. वैध क्रेडेन्सियल भएका जडानहरूमा फिल्टर गर्छ (API key वा `hasUsableOAuthToken()` मार्फत म्याद नसकिएको OAuth token)
3. मोडेल उपलब्धता + मूल्य निर्धारणका लागि `getProviderRegistry()` सँग क्रस-रेफरेन्स गर्छ
4. प्रत्येक `(provider, model, connection)` ट्युपलका लागि, एउटा `VirtualAutoComboCandidate` निर्माण गर्छ
5. डिस्प्याच लक्ष्यका रूपमा `connection.defaultModel` (वा registry को पहिलो मोडेल) चयन गर्छ
6. 16-कारक `scorePool()` र भेरियन्टको weight pack प्रयोग गरेर प्रत्येक उम्मेदवारलाई स्कोर गर्छ
7. `handleComboChat()` का लागि नतिजास्वरूप प्राप्त इन-मेमोरी `AutoComboConfig` फर्काउँछ — DB मा कहिल्यै स्थायी रूपमा भण्डारण हुँदैन

यसको अर्थ **`auto/*` सक्षम गरिएको नयाँ provider थप्दा उम्मेदवार पूल स्वतः विस्तार हुन्छ** — म्यानुअल रूपमा कम्बो सम्पादन गर्नुपर्दैन। भर्चुअल कम्बो प्रत्येक अनुरोधमा पुनःनिर्माण हुन्छ, त्यसैले भर्खरै थपिएका वा पुनः स्वस्थ भएका जडानहरू तत्काल समावेश हुन्छन्।

## स्व-उपचार

- **अस्थायी बहिष्करण**: स्कोर < 0.2 → 5 मिनेटका लागि बहिष्कृत (क्रमिक backoff, अधिकतम 30 मिनेट)
- **Circuit breaker सचेतना**: OPEN → स्वतः बहिष्कृत; HALF_OPEN → परीक्षण अनुरोधहरू
- **घटना मोड**: >50% OPEN → अन्वेषण निष्क्रिय गर्ने, स्थिरता अधिकतम बनाउने
- **Cooldown पुनःप्राप्ति**: बहिष्करणपछि, पहिलो अनुरोध घटाइएको timeout सहितको "probe" हुन्छ

## Bandit अन्वेषण

5% अनुरोधहरू (कन्फिगर गर्न मिल्ने) अन्वेषणका लागि अनियमित provider हरूमा रुट गरिन्छन्। घटना मोडमा यो निष्क्रिय हुन्छ।

## API

त्यहाँ **कुनै समर्पित `POST /api/combos/auto` endpoint छैन** — Auto-Combo दुई तरिकाले प्रयोग गरिन्छ:

1. **शून्य-कन्फिग (सिफारिस गरिएको):** `model: "auto"` वा `model: "auto/<variant>"` सहित कुनै पनि chat completion अनुरोध पठाउनुहोस्। भर्चुअल फ्याक्ट्रीले प्रत्येक अनुरोधका लागि कम्बो निर्माण गर्छ — स्थायी भण्डारण वा API कलहरू आवश्यक पर्दैन।

2. **`strategy: "auto"` सहितको स्थायी कम्बो:** `POST /api/combos` मार्फत नियमित कम्बो सिर्जना गर्नुहोस् र `strategy: "auto"` का साथै `config.auto.weights` / `config.auto.candidatePool` सेट गर्नुहोस्। उही स्कोरिङ इन्जिन प्रयोग हुन्छ; कम्बो `combos` मा भण्डारण हुन्छ र ID द्वारा पुनः प्रयोग गर्न सकिन्छ।

खोजका लागि, `GET /api/combos/auto` ले प्रत्येक भेरियन्टलाई यसको समाधान गरिएको उम्मेदवार पूलका साथै `context_length` / `max_output_tokens` सहित सूचीबद्ध गर्छ — जुन उम्मेदवार पूलका window हरूमध्येको MAX हो। क्लाइन्टहरू (जस्तै opencode plugin) ले `0` को सट्टा यी मानहरू विज्ञापन गर्नुपर्छ: शून्य context ले opencode को auto-compaction पूर्ण रूपमा निष्क्रिय गर्छ, जसका कारण gateway को history purge ले context नष्ट नगरुन्जेल session हरू बढिरहन्छन्। MAX विज्ञापन गर्न सुरक्षित छ किनभने auto-combo context pre-filter ले अत्यधिक ठूला अनुरोधहरूलाई ठूलो-window भएका उम्मेदवारहरूमा रुट गर्छ।

```bash
# शून्य-कन्फिग प्रयोग (कम्बो सिर्जना नगरी)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# नियमित combos endpoint मार्फत स्थायी auto combo
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto router रणनीतिहरू

स्थायी `strategy: "auto"` कम्बोहरूले `config.routerStrategy` (वा पुरानो
`config.auto.routerStrategy`) लाई निम्नमध्ये एउटामा सेट गर्न सक्छन्:

- `rules` — पूर्वनिर्धारित भारित स्कोरिङ
- `score` — कन्फिगर गरिएको सबैभन्दा उच्च भारित स्कोर चयन गर्छ। ठ्याक्कै बराबरी हुँदा कन्फिगर गरिएको
  उम्मेदवार क्रम कायम रहन्छ; विद्यमान `explorationRate` ले पूर्ण श्रेणीबद्ध पूलबाट नमुना लिन्छ।
- `cost` / `eco` — सबैभन्दा सस्तो स्वस्थ provider
- `latency` / `fast` — reliability penalty सहितको सबैभन्दा कम p95 latency
- `sla-aware` / `sla` — p95 latency, error-rate, र वैकल्पिक
  cost SLOs पूरा गर्ने उम्मेदवारहरूलाई प्राथमिकता दिने
- `lkgp` — पछिल्लो ज्ञात राम्रो provider पहिले

### Router रणनीतिहरूको विस्तृत विवरण

Auto-combo इन्जिनले 6 वटा प्लग गर्न मिल्ने **RouterStrategy** कार्यान्वयनहरू उपलब्ध गराउँछ, जसलाई
तपाईं `config.routerStrategy` (वा पुरानो `config.auto.routerStrategy`) मार्फत परिवर्तन गर्न सक्नुहुन्छ।
प्रत्येक रणनीतिले `RoutingContext`
(task type, tool/vision hints, token estimate, वैकल्पिक SLA policy, वैकल्पिक
last-known-good provider) का आधारमा उम्मेदवार पूलबाट एउटा provider चयन गर्छ।

#### 1. `rules` (पूर्वनिर्धारित) — 16-कारक भारित स्कोरिङ

विद्यमान स्कोरिङ इन्जिनलाई wrap गर्छ। `OPEN` circuit-breaker भएका
उम्मेदवारहरूलाई फिल्टर गर्छ, त्यसपछि हालको task type र `getTaskFitness()` सहित `scorePool()` चलाउँछ,
र सबैभन्दा उच्च स्कोर भएको provider चयन गर्छ।

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**कहिले प्रयोग गर्ने**: पूर्वनिर्धारित। सबै संकेतहरूबीच सन्तुलित सम्झौता चाहिँदा प्रयोग गर्नुहोस्।

**उपनाम**: `rules` (कुनै उपनाम छैन)

---

#### 2. `cost` / `eco` — सबैभन्दा सस्तो स्वस्थ provider

उम्मेदवार पूललाई `costPer1MTokens` अनुसार (बढ्दो क्रममा) क्रमबद्ध गर्छ र सबैभन्दा सस्तो चयन गर्छ।
पहिले `OPEN` उम्मेदवारहरूलाई फिल्टर गर्छ।

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**कहिले प्रयोग गर्ने**: लागत-संवेदनशील workload, batch processing, वा background job हरूका लागि।

**उपनामहरू**: `cost`, `eco`

---

#### 3. `latency` / `fast` — reliability penalty सहितको सबैभन्दा कम p95 latency

`p95LatencyMs + (errorRate * 1000)` अनुसार क्रमबद्ध गर्छ। त्रुटि-दर दण्डले नाममात्रको विलम्बता कम भए पनि
अविश्वसनीय प्रदायकहरूलाई तल्लो क्रममा राखिने सुनिश्चित गर्छ।

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**कहिले प्रयोग गर्ने**: वास्तविक-समय च्याट, स्वतःपूर्णता वा
अन्तरक्रियात्मक कोडिङ सहायकजस्ता विलम्बता-संवेदनशील कार्यभारहरूका लागि।

**उपनामहरू**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — विलम्बता/त्रुटि/लागत SLO अनुपालन

प्रत्येक उम्मेदवारले कन्फिगर गरिएको SLO नीति कति राम्रोसँग पूरा गर्छ भन्ने आधारमा स्कोर दिन्छ:

| कारक            | भार | सूत्र                                                 |
| --------------- | --- | ----------------------------------------------------- |
| विलम्बता स्कोर  | 35% | `threshold / max(value, ε)`                           |
| त्रुटि स्कोर    | 35% | `threshold / max(value, ε)`                           |
| स्वास्थ्य स्कोर | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)     |
| लागत स्कोर      | 10% | `threshold / max(value, ε)` वा व्युत्क्रम सामान्यीकृत |
| स्थिरता स्कोर   | 5%  | विलम्बता मानक विचलनको व्युत्क्रम सामान्यीकृत मान      |

`hardConstraints: true` हुँदा उम्मेदवारहरूलाई मुख्य रूपमा **उल्लङ्घन स्कोर**
(उनीहरूले कुनै SLO लाई कति नाघ्छन्) का आधारमा र त्यसपछि संयुक्त स्कोरका आधारमा क्रमबद्ध गरिन्छ। अन्यथा,
संयुक्त स्कोर मात्र प्रयोग गरिन्छ।

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... प्रत्येक उम्मेदवारलाई यस नीतिअनुसार स्कोर दिन्छ: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA फिल्डहरू** (कम्बो कन्फिगमा सेट गरिने):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**कहिले प्रयोग गर्ने**: कडा विलम्बता, त्रुटि-दर वा लागत बजेट भएका उत्पादन कार्यभारहरूका लागि।

**उपनामहरू**: `sla-aware`, `sla`

---

#### 5. `lkgp` — अन्तिम ज्ञात राम्रो प्रदायक पहिले

यदि सेट गरिएको छ भने **अन्तिम ज्ञात राम्रो प्रदायक** लाई पहिले प्रयास गर्छ, त्यसपछि
`rules` रणनीति प्रयोग गर्छ। यो सत्र स्थिरताका लागि उपयोगी छ — संवादमा
पछिल्ला अनुरोधहरू पनि उही प्रदायकले सम्हाल्छ।

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // rules रणनीति प्रयोग गर्नुहोस्
    return getStrategy("rules").select(pool, context);
  }
}
```

**कहिले प्रयोग गर्ने**: पछिल्ला अनुरोधहरू उही प्रदायकले सम्हालोस् भन्ने चाहिने
बहु-चरणीय संवादहरूमा (जस्तै, क्यासिङ, सन्दर्भ निरन्तरता वा मूल्य निर्धारणको एकरूपताका लागि)।

**उपनाम**: `lkgp` (उपनाम छैन)

### अनुकूलित राउटर रणनीतिहरू

तपाईंले सार्वजनिक API मार्फत आफ्नै `RouterStrategy` कार्यान्वयन दर्ता गर्न सक्नुहुन्छ:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // तपाईंको राउटिङ तर्क यहाँ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

त्यसपछि यसलाई प्रयोग गर्नुहोस्:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

### राउटर रणनीति छनोट मार्गदर्शिका

| प्रयोगको अवस्था    | रणनीति      | कारण                                    |
| ------------------ | ----------- | --------------------------------------- |
| सन्तुलित कार्यभार  | `rules`     | पूर्वनिर्धारित — सबै कारकहरू विचार गर्छ |
| लागत न्यूनीकरण     | `cost`      | सधैँ सबैभन्दा सस्तो विकल्प छान्छ        |
| विलम्बता न्यूनीकरण | `latency`   | सबैभन्दा छिटो विश्वसनीय प्रदायक छान्छ   |
| कडा SLO हरू        | `sla-aware` | p95/त्रुटि/लागत सीमा अनुसार फिल्टर गर्छ |
| बहु-चरणीय च्याट    | `lkgp`      | सत्र स्थिरता                            |

SLA-सचेत फिल्डहरू:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

## कार्य उपयुक्तता

6 प्रकारका कार्यहरू (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) मा 30+ मोडेलहरूको मूल्याङ्कन गरिएको छ। वाइल्डकार्ड ढाँचाहरूलाई समर्थन गर्छ (उदाहरणका लागि, `*-coder` → उच्च कोडिङ स्कोर)।

## Auto भेरियन्टहरूको पुनरावलोकन

मूल `auto` (पूर्वनिर्धारित) सहित `autoPrefix.ts` मा घोषणा गरिएका 6 वटा `AutoVariant` मानहरू जोड्दा, **आह्वान गर्न मिल्ने 7 वटा मोडेल ID** छन्:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ले आफैंमा 6 वटा मानहरू सूचीबद्ध गर्छ; सातौँ विकल्प "भेरियन्ट छैन" — मूल `auto` — हो, जसलाई `parseAutoPrefix()` ले `variant: undefined` का रूपमा व्यवस्थापन गर्छ।)

## टियरहरू Auto-Combo मा कसरी समाहित हुन्छन्

16-कारक स्कोरिङ प्रकार्य (`open-sse/services/autoCombo/scoring.ts`) ले टियर
सदस्यतालाई दुईवटा सङ्केतका रूपमा लिन्छ: `tierPriority` (0.0476) र `tierAffinity` (0.0476)। पूर्ण
`DEFAULT_WEIGHTS` सेटका लागि माथिको प्रामाणिक [स्कोरिङ कारक तालिका](#how-it-works-persisted-auto-combos) हेर्नुहोस् — प्रत्येक प्याकका ओभरराइडहरू (ship-fast/cost-saver/quality-first/
offline-friendly) "प्रत्येक प्याकका तौल प्रोफाइलहरू" तालिकामा सूचीबद्ध छन्।

टियरले मात्रै Tier 1 लाई पहिले चयन गर्न **बाध्य पार्दैन** — यदि Tier 1 को विलम्बता खराब छ वा
लागतको तुलनामा गुणस्तर अनुकूलतम छैन भने, Tier 2 ले जित्छ। टियर क्रम बाध्य पार्न, कम्बो
रणनीति `priority` प्रयोग गर्नुहोस् र प्रदायकहरूलाई टियरअनुसार क्रमबद्ध गर्नुहोस्।

Tier 1 (सदस्यता) लाई बलियो प्राथमिकता दिन, `tierPriority` को तौल बढाउनुहोस्:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

टियरका परिभाषाहरू र प्रदायक वर्गीकरणका लागि `docs/marketing/TIERS.md` हेर्नुहोस्।

## परीक्षण र कभरेज

### निर्धारणात्मक राउटिङ-निर्णय म्याट्रिक्स (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` ले नक्कली अपस्ट्रिमसहितको वास्तविक कम्बो पाइपलाइनमार्फत सबै 19
सार्वजनिक रणनीतिहरूको राउटिङ **निर्णय**लाई सुरुदेखि अन्त्यसम्म प्रमाणित गर्छ।
कभरेजमा निम्न समावेश छन्:

- सबै 19 वटा `ROUTING_STRATEGY_VALUES` रणनीतिहरू (ordered, weighted, cost, context, fusion, …)।
- `quota-share` (आन्तरिक) सुरुदेखि अन्त्यसम्म: वास्तविक `selectQuotaShareTarget` सीम (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`) मार्फत DRR निष्पक्षता + संतृप्ति प्राथमिकीकरण न्यूनीकरण।
- प्रत्येक लक्षित सङ्ख्यामा `context-relay` को विश्वव्यापी हस्तान्तरण कभरेज।

यो सुइट CI (`test:integration` कार्य) मा `--test-concurrency=1` र
`--test-force-exit` सहित चल्छ, त्यसैले यो निर्धारणात्मक हुन्छ र यसलाई प्रत्यक्ष प्रमाण-पत्रहरू आवश्यक पर्दैनन्।

### गेट गरिएको प्रत्यक्ष स्मोक परीक्षण (CI मा छैन — वास्तविक प्रदायकहरू)

| आदेश                                   | यसले के गर्छ                                                                                  |
| :------------------------------------- | :-------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` सहित इन-प्रोसेस वास्तविक राउटिङ; प्रत्यक्ष OmniRoute DB को स्न्यापसट लिन्छ |
| `npm run test:combo:live:vps`          | प्रत्यक्ष OmniRoute सर्भरविरुद्ध HTTP कलहरू (`COMBO_LIVE_BASE_URL` सेट गर्नुहोस्)             |
| `npm run test:combo:live:vps:failover` | उही, जानाजानी सिर्जना गरिएका फेलओभर परिदृश्यहरूसहित                                           |

प्रमाण-पत्रहरू र VPS पहुँच आवश्यक पर्ने भएकाले तिनीहरूलाई जानाजानी CI बाट बाहिर राखिएको छ।
