पुल अनुरोधका लागि सबैभन्दा सानो भरपर्दो विकास चक्र छनोट गर्न यो मार्गदर्शिका प्रयोग गर्नुहोस्। यसले तल लिङ्क गरिएका क्षेत्र-विशिष्ट आर्किटेक्चर र सुरक्षा कागजातहरूलाई प्रतिस्थापन गर्दैन; यसले प्रत्येक सामान्य परिवर्तन प्रकारलाई त्यसका अनुबन्धहरू, लक्षित जाँचहरू र CI कभरेजसँग जोड्छ।

## प्रत्येक परिवर्तनले पछ्याउने मार्ग

1. **सम्पादन गर्नुअघि आधार छनोट गर्नुहोस्।** सबैभन्दा उच्च सक्रिय `release/v*` शाखा फेला पार्नुहोस् र त्यसको अन्तिम बिन्दुबाट शाखा बनाउनुहोस्। `main` लाई होइन, उक्त शाखालाई लक्षित गर्नुहोस्। यदि रिलिज फ्रिज सक्रिय छ भने, फ्रिज गरिएको शाखालाई लक्षित नगर्नुहोस्; [शाखाकरण र रिलिज मोडेल](BRANCHING_MODEL.md) मा वर्णन गरिएको अर्को सक्रिय चक्र प्रयोग गर्नुहोस्।
2. **अनुबन्धहरूको नाम उल्लेख गर्नुहोस्।** परिवर्तनले प्रभाव पार्ने प्रत्येक क्याटलग, स्किमा, उत्पन्न आर्टिफ्याक्ट, सार्वजनिक API वा प्रयोगकर्ता इन्टरफेस पहिचान गर्नुहोस्। तलको तालिकाले न्यूनतम प्रारम्भिक सेट दिन्छ।
3. **लक्षित परीक्षणहरू लेख्नुहोस् वा अद्यावधिक गर्नुहोस्।** `src/`, `open-sse/`, `electron/` वा `bin/` मा गरिएका उत्पादन परिवर्तनका लागि सोही PR मा स्वचालित परीक्षण आवश्यक हुन्छ। व्यवहार प्रमाणित गर्ने सबैभन्दा साना परीक्षण फाइलहरू चलाउनुहोस्, त्यसपछि सूचीबद्ध लक्षित गेटहरू चलाउनुहोस्।
4. **CI लाई विस्तृत म्याट्रिक्स चलाउन दिनुहोस्।** पूर्ण युनिट शार्डहरू, Vitest, कभरेज र्याचेट र उत्पादन बिल्ड PR मा चल्छन्। लक्षित असफलताले व्यापक प्रभावतर्फ सङ्केत गर्दा वा परिवर्तनले धेरै उपप्रणालीहरू समेट्दा मात्र स्थानीय रूपमा विस्तृत सुइट चलाउनुहोस्।
5. **समीक्षाअघि समन्वय गर्नुहोस्।** सक्रिय आधार फेच गर्नुहोस्, त्यसका नयाँ कमिटहरू र त्यसको सापेक्षमा आफ्नो डिफ निरीक्षण गर्नुहोस्, त्यसपछि योगदानकर्ता कार्यप्रवाहअनुसार आधारलाई रिबेस वा मर्ज गर्नुहोस्। उत्पन्न फाइल र क्याटलगका द्वन्द्वहरू तिनको स्रोतबाट समाधान गर्नुहोस्, तिनलाई पुनः उत्पन्न गर्नुहोस्, लक्षित चक्र पुनः चलाउनुहोस् र PR ले अझै सक्रिय रिलिज शाखालाई लक्षित गरेको पुष्टि गर्नुहोस्।
6. **प्रमाण अभिलेख गर्नुहोस्।** PR टेम्प्लेटमा चलाइएका कमाण्डहरू, थपिएका वा परिवर्तन गरिएका प्रत्येक परीक्षण फाइल, माइग्रेसन वा फिचर फ्ल्यागहरू र अझै बाँकी रहेका कुनै पनि CI-मात्र प्रमाणीकरण सूचीबद्ध गर्नुहोस्।

## परिवर्तन प्रकारअनुसार आदर्श मार्गहरू

तलका कमाण्डहरू न्यूनतम लक्षित जाँचहरू हुन्; यी तपाईंले परिवर्तन गरेको व्यवहारलाई प्रत्यक्ष रूपमा समेट्ने परीक्षण छोड्ने अनुमति होइनन्।

### प्रदायक

**अनुबन्धहरू**

- `src/shared/constants/providers/` मा रहेको प्रदायक परिभाषा र `src/shared/constants/providers.ts` मा यसको संयोजन।
- `open-sse/config/providerRegistry.ts` वा त्यसबाट निकालिएका रजिस्ट्री फाइलहरूमा रहेका मोडेल र क्षमताहरू।
- लागू हुँदा एक्जिक्युटर/ट्रान्सलेटर छनोट, OAuth वा API-key कन्फिगरेसन, ड्यासबोर्ड एसेटहरू र उत्पन्न गरिएको प्रदायक सन्दर्भ।
- सार्वजनिक क्रेडेन्सियलहरूले `resolvePublicCred()` प्रयोग गर्नुपर्छ; त्रुटि प्रतिक्रियाहरूले साझा स्यानिटाइज्ड त्रुटि हेल्परहरू प्रयोग गर्नुपर्छ। `docs/security/PUBLIC_CREDS.md` (git मा; `/docs` मा कम्पाइल गरिएको छैन) र [त्रुटि स्यानिटाइजेसन](../security/ERROR_SANITIZATION.md) हेर्नुहोस्।

**लक्षित चक्र**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # क्याटलग परिवर्तन हुँदा; उत्पन्न गरिएको डिफ कमिट गर्नुहोस्
npm run lint
```

प्रभावित प्रत्येक अनुरोध परिवारको पनि परीक्षण गर्नुहोस्: chat, Responses, images, embeddings, audio वा video। उत्पन्न क्याटलग र गोल्डेन डिफहरूलाई अनुबन्ध परिवर्तनका रूपमा समीक्षा गर्नुहोस्; तिनलाई अन्धाधुन्ध स्वीकार नगर्नुहोस्।

### राउटिङ

**अनुबन्धहरू**

- `src/shared/constants/routingStrategies.ts` मा रहेका सार्वजनिक रणनीति मानहरू र UI मेटाडेटा।
- `open-sse/services/combo.ts` र `open-sse/services/combo/` अन्तर्गतको डिस्प्याच र क्रम निर्धारण।
- कम्बो स्किमाहरू, पर्सिस्टेन्स, रेजिलिएन्स अवस्था, मोडेल क्षमताहरू र API/UI नियन्त्रणहरू।
- व्यवहार परिवर्तन हुँदा [Auto-Combo इन्जिन](../routing/AUTO-COMBO.md) र रेजिलिएन्ससम्बन्धी कागजात।

**लक्षित चक्र**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # रणनीति वा डिस्प्याच परिवर्तनहरू
npm run check:known-symbols      # रणनीति दर्ता परिवर्तनहरू
npm run lint
```

स्थानीय रूपमा निर्धारणात्मक mocked-upstream परीक्षणहरू प्रयोग गर्नुहोस्। प्रत्यक्ष कम्बो स्मोक परीक्षणलाई क्रेडेन्सियलहरू आवश्यक पर्छन् र ती म्यानुअल हुन्, CI का विकल्प होइनन्।

### UI / UX

**अनुबन्धहरू**

- `src/app/` र `src/shared/components/` अन्तर्गतका Next.js रुट/पृष्ठ र साझा कम्पोनेन्ट सीमाहरू।
- API प्रतिक्रिया आकारहरू, लोडिङ/खाली/त्रुटि अवस्थाहरू, किबोर्ड र स्क्रिन-रिडर व्यवहार, रेस्पोन्सिभ लेआउट, थिमिङ र लोकेल विस्तार।
- `src/i18n/messages/en.json` मा रहेका अङ्ग्रेजी UI स्रोत स्ट्रिङहरू; प्रयोगकर्ताले देख्ने नयाँ पाठ हार्ड-कोड नगर्नुहोस्।

**लक्षित चक्र**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

अन्तरक्रिया वा दृश्य परिवर्तनका लागि एप चलाउनुहोस् र साँघुरा तथा फराकिला दुवै भ्युपोर्ट जाँच गर्नुहोस्। CI ले उत्पादन बिल्ड र विस्तृत सुइटहरू चलाउँछ; दृश्य व्यवहारका लागि अझै पनि परिवर्तनअनुकूल लक्षित कम्पोनेन्ट, Playwright वा अभिलेख गरिएको म्यानुअल जाँच आवश्यक हुन्छ।

### i18n

**अनुबन्धहरू**

- `src/i18n/messages/en.json` UI स्रोत हो; `config/i18n.json` लोकेल स्रोत हो।
- CLI क्याटलगहरू `bin/cli/locales/` अन्तर्गत छुट्टै रहन्छन्।
- ICU प्लेसहोल्डर र ट्यागहरू ठ्याक्कै जोगाउनुहोस्। उत्पादन/प्रदायक/मोडेलका नाम, प्रोटोकल र हेडरका नाम, कमाण्ड, कोड/JSON आइडेन्टिफायर, URL, वातावरण चर वा `OmniRoute`, `OAuth`, `MCP` र `A2A` जस्ता संरक्षित शब्दहरू अनुवाद नगर्नुहोस्। हालको स्रोत सूची `scripts/i18n/glossary/protected-terms.json` हो।

**लक्षित चक्र**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI स्ट्रिङ/क्याटलगहरू परिवर्तन हुँदा
npm run lint
```

यो विद्यमान प्रणालीका लागि मार्गदर्शन हो, यसको टुलिङ वा की मोडेल विस्तार गर्ने निमन्त्रणा होइन। प्रतिस्थापन प्रणाली डिजाइन भइरहँदा i18n प्याचहरूलाई सर्जिकल र सीमित राख्नुहोस्। कार्यले स्पष्ट रूपमा उत्पन्न अनुवादहरू आवश्यक नपारेसम्म र तपाईंले परिणामी डिफ समीक्षा नगरेसम्म बाह्य सेवाहरू कल गर्ने अनुवाद कमाण्डहरू नचलाउनुहोस्।

### CLI

**अनुबन्धहरू**

- `bin/cli/` का सार्वजनिक command र flag हरू, उत्पन्न गरिएका API command हरू, exit code हरू, stdout/stderr र
  JSON output का संरचनाहरू, config/environment को व्यवहार, र प्याकेज गरिएका file हरू।
- CLI का प्रयोगकर्ताले देख्ने string हरूले CLI i18n तह प्रयोग गर्नुपर्छ र `en`/`pt-BR` catalog हरूलाई समक्रमित राख्नुपर्छ।
- Node लाई समर्थित runtime का रूपमा र प्रकाशित binary contract लाई यथावत् राख्नुहोस्।

**केन्द्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # उत्पन्न गरिएको/bundle गरिएको CLI का परिवर्तनहरू
npm run check:pack-policy     # package surface का परिवर्तनहरू
npm run lint
```

व्यवहार parsing, file, वा exit status मा निर्भर हुँदा, अस्थायी data directory मा ठ्याक्कै उही command प्रयोग गर्नुहोस्।
CI ले अझ व्यापक package artifact र ecosystem जाँचहरू गर्छ।

### Database

**Contract हरू**

- `src/lib/db/` अन्तर्गतका domain module हरू; निश्चित module हरू सिधै import गर्नुहोस् (पुरानो `localDb.ts` re-export तह हटाइएको छ)।
- `src/lib/db/migrations/` अन्तर्गतका नम्बर दिइएका, idempotent SQL migration हरू, transaction safety, upgrade
  व्यवहार, index हरू, र schema बाट प्रभावित प्रत्येक caller।
- Route र handler हरूले कहिल्यै सिधै raw SQL चलाउँदैनन्।

**केन्द्रित चक्र**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

migration थप्दा नयाँ database र अघिल्लो schema बाट हुने upgrade दुवैको परीक्षण गर्नुहोस्। Database परीक्षणहरूले
cleanup का क्रममा handle हरू बन्द गर्नुपर्छ र `resetDbInstance()` call गर्नुपर्छ। best-effort Bun adapter को path
परिवर्तन हुँदा मात्र `npm run test:bun:db` चलाउनुहोस्; Node नै आधिकारिक रहन्छ।

### Build / deploy

**Contract हरू**

- Root र workspace manifest/lockfile, `scripts/build/`, Next.js standalone assembly, `dist/`
  package का सामग्री, Electron platform metadata, CI workflow हरू, र deployment sentinel हरू।
- समर्थित Node range हरू र `CLAUDE.md` मा allow-list गरिएको Bun प्रयोग यथावत् रहनुपर्छ।
- Build artifact हरू track नगरिएका रहन्छन्; dependency, license, workflow, र package policy हरू लागू हुन्छन्।

**केन्द्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency वा lockfile का परिवर्तनहरू
npm run check:pack-policy      # प्रकाशित package surface का परिवर्तनहरू
npm run lint
```

परिवर्तनले compilation, standalone assembly, asset, वा runtime bundling लाई असर गर्दा मात्र स्थानीय रूपमा `npm run build` प्रयोग गर्नुहोस्।
release/deploy प्रमाणीकरणका लागि मात्र `npm run build:release` प्रयोग गर्नुहोस्। CI को build नै अन्तिम cross-platform संकेत हो;
platform-specific Electron परिवर्तनहरूका लागि सम्बन्धित केन्द्रित build वा smoke प्रमाण आवश्यक हुन्छ।

## स्थानीय क्यान्डिडेट लूप

स्रोत परीक्षणहरूले प्याकेज गरिएको आर्टिफ्याक्ट बुट हुन्छ भनेर प्रमाणित गर्न सक्दैनन्: प्याकेजिङ सूचीहरू, हटाइएका डिपेन्डेन्सीहरू,
र नेटिभ बाइनरीहरू टारबल स्थापना गरी सुरु गरेपछि मात्र असफल हुन्छन्। `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) RFC #8084 को एकपटक बिल्ड गर्ने / प्रमाणीकरण गर्ने / प्रवर्द्धन गर्ने प्रवाहको
स्थानीय भाग हो: यसले एउटा क्यान्डिडेट बिल्ड गर्छ, ठ्याक्कै त्यही आर्टिफ्याक्टलाई प्रमाणीकरण गर्छ, डाइरेक्टरीको
नाम परिवर्तन गरेर त्यसलाई प्रवर्द्धन गर्छ, र प्रवर्द्धित स्लटको स्वास्थ्य जाँच असफल भएमा त्यसलाई रोलब्याक गर्छ।

```bash
npm run dev:candidate -- run --dry-run --json  # योजना देखाउनुहोस्, केही पनि परिवर्तन नगर्नुहोस्
npm run dev:candidate -- run                   # बिल्ड + प्रमाणीकरण + प्रवर्द्धन, स्वचालित रोलब्याक
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ मा स्थापना
npm run dev:candidate -- validate --id <id>    # खाली पोर्टमा बुट, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current र previous साट्नुहोस्
npm run dev:candidate -- run --from-tarball <file.tgz>  # अन्यत्र (CI मा) बिल्ड गरिएको टारबल पुनः प्रयोग गर्नुहोस्
```

- **एकपटक बिल्ड गर्नुहोस्।** `build` ले हालको ट्री प्याक गर्छ (यसलाई `dist/server.js` चाहिन्छ, त्यसैले पहिले
  `npm run build:release` चलाउनुहोस्) वा `--from-tarball` लाई प्रतिलिपि गर्छ, त्यसपछि टारबललाई अलग गरिएको
  npm प्रिफिक्समा स्थापना गर्छ, किनकि टारबलमा `node_modules` हुँदैन। id छोटो `HEAD`
  sha (ट्रीमा स्थानीय परिवर्तनहरू हुँदा `-dirty`) वा टारबलका लागि `tgz-<sha256>` हुन्छ। पहिले नै बिल्ड
  गरिएको सफा id लाई पुनः बिल्ड गर्नुको सट्टा पुनः प्रयोग गरिन्छ; त्यसलाई पुनः बिल्ड गर्न `--force` दिनुहोस्।
- **स्रोतलाई होइन, प्याकेजलाई प्रमाणीकरण गर्नुहोस्।** `validate` ले स्थापना गरिएको CLI
  (`serve --port <free port>`) लाई नयाँ `DATA_DIR=<candidate>/data`, नक्कली गोप्य मानहरू, र अपरेटरका
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` तथा `INITIAL_PASSWORD` वातावरणबाट हटाएर सुरु गर्छ,
  जसले गर्दा यसले नयाँ स्थापनाको keyless loopback अवस्था जाँच गर्छ। यसले `GET /api/health` ले 200
  फर्काउने समयसम्म प्रतीक्षा गर्छ, `GET /v1/models` ले 200 फर्काउनै पर्ने बनाउँछ, प्रोसेस समूह रोक्छ,
  र टारबल ह्याससँगै निर्णयलाई `validation.json` मा अभिलेख गर्छ।
- **उही आर्टिफ्याक्ट प्रवर्द्धन गर्नुहोस्।** हालको टारबल ह्यासका लागि सफल प्रमाणीकरण नभएको क्यान्डिडेटलाई
  `promote` ले अस्वीकार गर्छ। पूर्वनिर्धारित सक्रिय स्लट `_artifacts/candidate/current` हो; `--target <dir>`
  ले उही फाइलसिस्टममा अर्को डाइरेक्टरी चयन गर्छ, र त्यसको अघिल्लो स्लट `<dir>.previous` हुन्छ।
  प्रत्येक नाम परिवर्तन एटोमिक हुन्छ, र बीचमै असफल भएमा पहिले नै सम्पन्न भएका नाम परिवर्तनहरू उल्टाइन्छन्।
- **रोलब्याक गर्नुहोस्।** `run` ले प्रवर्द्धित स्लटलाई फेरि प्रमाणीकरण गर्छ र त्यो जाँच असफल हुँदा
  `current` र `previous` लाई पुनः साट्छ। पहिलो प्रमाणीकरणमै असफल हुने क्यान्डिडेटलाई कहिल्यै प्रवर्द्धन गरिँदैन।

सबै कुरा gitignore गरिएको `_artifacts/candidate/` अन्तर्गत लेखिन्छ; अवस्थित OmniRoute
स्थापना र त्यसको डेटा डाइरेक्टरीलाई कहिल्यै छोइँदैन। प्रवर्द्धित CLI
`_artifacts/candidate/current/prefix/bin/omniroute` हो; यसलाई प्रयोग गर्दा आफ्नै `DATA_DIR` सहित
सुरु गर्नुहोस्। निकास कोडहरू: `0` सफलता, `1` असफल प्रमाणीकरण वा प्रवर्द्धन, `2` प्रयोगसम्बन्धी त्रुटि वा बिल्ड अनुपस्थित।

## स्थानीय लुप बनाम CI

| प्रत्येक प्याचका लागि स्थानीय रूपमा चलाउनुहोस्                                 | CI ले व्यापक सङ्केत प्रदान गर्छ                                       |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| माथिका प्रत्यक्ष व्यवहार परीक्षण र श्रेणी गेटहरू                               | शार्ड गरिएको पूर्ण युनिट सुइट र क्रमिक परीक्षणहरू                     |
| `npm run lint`                                                                 | Vitest सुइटहरू र कभरेज/गुणस्तर र्याचेटहरू                             |
| प्रभावित कन्ट्र्याक्टले आवश्यक ठहर्याउँदा मात्र टाइपचेक वा बिल्ड               | प्रोडक्सन बिल्ड, सुरक्षा, डक्स, डिपेन्डेन्सी र PR-नीति गेटहरू         |
| स्वचालनले व्यवहार प्रमाणित गर्न नसक्दा मात्र म्यानुअल अन्तरक्रिया/लाइभ जाँचहरू | वर्कफ्लोद्वारा कन्फिगर गरिएका क्रस-जव इन्टिग्रेसन र प्लेटफर्म जाँचहरू |

सफल केन्द्रित लुप परिवर्तन गरिएको कन्ट्र्याक्टबारे प्रमाण हो, असम्बन्धित CI जाँचहरू
उत्तीर्ण हुनेछन् भन्ने प्रमाण होइन। त्यसैगरी, प्रत्येक स्थानीय सम्पादनलाई पूर्ण रिपोजिटरी म्याट्रिक्सका लागि प्रतीक्षा नगराउनुहोस्।

## समायोजन चेकलिस्ट

समीक्षा अनुरोध गर्नुअघि:

- PR को बेस अझै पनि सबैभन्दा उच्च सक्रिय `release/v*` ब्रान्च हो भनी पुष्टि गर्नुहोस्।
- उक्त बेस फेच गर्नुहोस् र तपाईंले ब्रान्च बनाएयता थपिएका कमिटहरू समीक्षा गर्नुहोस्।
- आकस्मिक वा जेनेरेट गरिएको अनावश्यक परिवर्तनका लागि `git diff <active-base>...HEAD` समीक्षा गर्नुहोस्।
- स्रोत अद्यावधिक गरेर र आउटपुट पुनः जेनेरेट गरेर क्याटलग तथा जेनेरेट गरिएका डकुमेन्टका द्वन्द्वहरू समाधान गर्नुहोस्।
- समायोजनपछि PR विवरणमा सूचीबद्ध प्रत्येक केन्द्रित परीक्षण/गेट पुनः चलाउनुहोस्।
- सरेको बेससँग मिलाउनका लागि मात्र एसर्शनहरू कहिल्यै कमजोर नबनाउनुहोस् वा आवश्यक परीक्षणहरू नहटाउनुहोस्।

[ब्रान्चिङ र रिलिज मोडेल](BRANCHING_MODEL.md) प्रयोग गर्नुहोस्। पूर्ण CI सूचीका लागि
[गुणस्तर गेट सन्दर्भ](../architecture/QUALITY_GATES.md) प्रयोग गर्नुहोस्।
