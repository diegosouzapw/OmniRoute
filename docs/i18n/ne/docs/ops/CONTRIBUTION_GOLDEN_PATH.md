पुल अनुरोधका लागि सबैभन्दा सानो भरपर्दो विकास चक्र छनोट गर्न यो मार्गदर्शिका प्रयोग गर्नुहोस्। यसले
तल लिङ्क गरिएका क्षेत्र-विशिष्ट वास्तुकला र सुरक्षा कागजातहरूलाई प्रतिस्थापन गर्दैन; यसले प्रत्येक सामान्य
परिवर्तन प्रकारलाई त्यसका अनुबन्धहरू, केन्द्रित जाँचहरू र CI कभरेजसँग जोड्छ।

## प्रत्येक परिवर्तनले अनुसरण गर्ने मार्ग

1. **सम्पादन गर्नुअघि आधार छनोट गर्नुहोस्।** सबैभन्दा उच्च सक्रिय `release/v*` शाखा फेला पार्नुहोस् र
   त्यसको टुप्पोबाट शाखा बनाउनुहोस्। `main` होइन, त्यही शाखालाई लक्षित गर्नुहोस्। यदि रिलिज फ्रिज सक्रिय छ भने, फ्रिज गरिएको
   शाखालाई लक्षित नगर्नुहोस्; [शाखाकरण र रिलिज मोडेल](BRANCHING_MODEL.md) मा वर्णन गरिएको
   अर्को सक्रिय चक्र प्रयोग गर्नुहोस्।
2. **अनुबन्धहरू उल्लेख गर्नुहोस्।** परिवर्तनले असर गर्ने प्रत्येक क्याटलग, स्किमा, उत्पन्न आर्टिफ्याक्ट, सार्वजनिक API वा प्रयोगकर्ता
   इन्टरफेस पहिचान गर्नुहोस्। तलको तालिकाले न्यूनतम सुरुवाती सेट दिन्छ।
3. **केन्द्रित परीक्षणहरू लेख्नुहोस् वा अद्यावधिक गर्नुहोस्।** `src/`, `open-sse/`, `electron/` वा
   `bin/` मा गरिएका उत्पादन परिवर्तनहरूका लागि उही PR मा स्वचालित परीक्षण आवश्यक हुन्छ। व्यवहार प्रमाणित गर्ने सबैभन्दा साना
   परीक्षण फाइलहरू चलाउनुहोस्, त्यसपछि सूचीबद्ध केन्द्रित गेटहरू चलाउनुहोस्।
4. **CI लाई विस्तृत म्याट्रिक्स चलाउन दिनुहोस्।** पूर्ण युनिट शार्डहरू, Vitest, कभरेज र्याचेट र
   उत्पादन बिल्ड PR मा चल्छन्। केन्द्रित विफलताले व्यापक प्रभाव सङ्केत गर्दा वा परिवर्तनले
   धेरै उपप्रणालीहरू समेट्दा मात्र स्थानीय रूपमा विस्तृत सुइट चलाउनुहोस्।
5. **समीक्षाअघि समायोजन गर्नुहोस्।** सक्रिय आधार फेच गर्नुहोस्, त्यसका नयाँ कमिटहरू र त्यससँग तुलना गरिएको आफ्नो डिफ निरीक्षण
   गर्नुहोस्, त्यसपछि योगदानकर्ता कार्यप्रवाहअनुसार आधारलाई रिबेस वा मर्ज गर्नुहोस्। उत्पन्न फाइल
   र क्याटलगका द्वन्द्वहरू तिनको स्रोतबाट समाधान गर्नुहोस्, तिनलाई पुनः उत्पन्न गर्नुहोस्, केन्द्रित चक्र पुनः चलाउनुहोस् र
   PR ले अझै सक्रिय रिलिज शाखालाई लक्षित गरेको पुष्टि गर्नुहोस्।
6. **प्रमाण अभिलेख गर्नुहोस्।** PR टेम्प्लेटमा चलाइएका कमान्डहरू, थपिएका वा परिवर्तन गरिएका प्रत्येक परीक्षण फाइल,
   माइग्रेसन वा फिचर फ्ल्यागहरू र अझै बाँकी रहेको कुनै पनि CI-मात्र प्रमाणीकरण सूचीबद्ध गर्नुहोस्।

## परिवर्तन प्रकारअनुसारका आदर्श मार्गहरू

तलका कमान्डहरू न्यूनतम केन्द्रित जाँचहरू हुन्, तपाईंले परिवर्तन गरेको व्यवहारलाई प्रत्यक्ष रूपमा समेट्ने परीक्षण छोड्ने
अनुमति होइनन्।

### प्रदायक

**अनुबन्धहरू**

- `src/shared/constants/providers/` मा प्रदायक परिभाषा र
  `src/shared/constants/providers.ts` मा त्यसको संयोजन।
- `open-sse/config/providerRegistry.ts` वा त्यसका निकालिएका रजिस्ट्री फाइलहरूमा मोडेल र क्षमताहरू।
- लागू हुँदा एक्जिक्युटर/ट्रान्सलेटर छनोट, OAuth वा API-key कन्फिगरेसन, ड्यासबोर्ड एसेटहरू र उत्पन्न
  प्रदायक सन्दर्भ।
- सार्वजनिक क्रेडेन्सियलहरूले `resolvePublicCred()` प्रयोग गर्नैपर्छ; त्रुटि प्रतिक्रियाहरूले साझा स्यानिटाइज गरिएका
  त्रुटि हेल्परहरू प्रयोग गर्नैपर्छ। `docs/security/PUBLIC_CREDS.md` (git; `/docs` मा कम्पाइल गरिएको छैन) र
  [त्रुटि स्यानिटाइजेसन](../security/ERROR_SANITIZATION.md) हेर्नुहोस्।

**केन्द्रित चक्र**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # क्याटलग परिवर्तन हुँदा; उत्पन्न डिफ कमिट गर्नुहोस्
npm run lint
```

प्रभावित प्रत्येक अनुरोध परिवार पनि परीक्षण गर्नुहोस्: च्याट, Responses, इमेज, एम्बेडिङ, अडियो वा भिडियो।
उत्पन्न क्याटलग र गोल्डेन डिफहरूलाई अनुबन्ध परिवर्तनका रूपमा समीक्षा गर्नुहोस्; तिनलाई आँखा चिम्लेर स्वीकार नगर्नुहोस्।

### राउटिङ

**अनुबन्धहरू**

- `src/shared/constants/routingStrategies.ts` मा सार्वजनिक स्ट्राटेजी मानहरू र UI मेटाडेटा।
- `open-sse/services/combo.ts` र `open-sse/services/combo/` अन्तर्गत डिस्प्याच र क्रमबद्धता।
- कम्बो स्किमाहरू, स्थायित्व, रेजिलिएन्स अवस्था, मोडेल क्षमताहरू र API/UI नियन्त्रणहरू।
- व्यवहार परिवर्तन हुँदा [Auto-Combo इन्जिन](../routing/AUTO-COMBO.md) र रेजिलिएन्स कागजात।

**केन्द्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # स्ट्राटेजी वा डिस्प्याच परिवर्तनहरू
npm run check:known-symbols      # स्ट्राटेजी दर्ता परिवर्तनहरू
npm run lint
```

स्थानीय रूपमा निर्धारणात्मक नक्कली-अपस्ट्रिम परीक्षणहरू प्रयोग गर्नुहोस्। प्रत्यक्ष कम्बो स्मोक परीक्षणहरूलाई क्रेडेन्सियल आवश्यक पर्छ र ती
म्यानुअल हुन्, CI का विकल्प होइनन्।

### UI / UX

**अनुबन्धहरू**

- `src/app/` र `src/shared/components/` अन्तर्गत Next.js रुट/पृष्ठ तथा साझा कम्पोनेन्ट सीमाहरू।
- API प्रतिक्रिया संरचनाहरू, लोडिङ/खाली/त्रुटि अवस्थाहरू, किबोर्ड र स्क्रिन-रिडर व्यवहार,
  रेस्पोन्सिभ लेआउट, थिमिङ र लोकेल विस्तार।
- `src/i18n/messages/en.json` मा अङ्ग्रेजी UI स्रोत स्ट्रिङहरू; प्रयोगकर्ताले देख्ने नयाँ पाठ हार्ड-कोड नगर्नुहोस्।

**केन्द्रित चक्र**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

अन्तरक्रिया वा दृश्य परिवर्तनहरूका लागि एप चलाउनुहोस् र साँघुरा तथा फराकिला दुवै भ्युपोर्ट जाँच गर्नुहोस्। CI ले
उत्पादन बिल्ड र विस्तृत सुइटहरू चलाउँछ; दृश्य व्यवहारलाई अझै पनि परिवर्तनअनुकूल केन्द्रित कम्पोनेन्ट, Playwright
वा अभिलेख गरिएको म्यानुअल जाँच आवश्यक हुन्छ।

### i18n

**अनुबन्धहरू**

- `src/i18n/messages/en.json` UI स्रोत हो; `config/i18n.json` लोकेल स्रोत हो।
- CLI क्याटलगहरू `bin/cli/locales/` अन्तर्गत छुट्टै रहन्छन्।
- ICU प्लेसहोल्डर र ट्यागहरू जस्ताको तस्तै राख्नुहोस्। उत्पादन/प्रदायक/मोडेलका नाम,
  प्रोटोकल र हेडरका नाम, कमान्ड, कोड/JSON पहिचायक, URL, वातावरण चर वा
  `OmniRoute`, `OAuth`, `MCP` र `A2A` जस्ता संरक्षित पदहरू अनुवाद नगर्नुहोस्। हालको स्रोत सूची
  `scripts/i18n/glossary/protected-terms.json` हो।

**केन्द्रित चक्र**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI स्ट्रिङ/क्याटलगहरू परिवर्तन हुँदा
npm run lint
```

यो विद्यमान प्रणालीका लागि मार्गदर्शन हो, यसको टुलिङ वा key मोडेल विस्तार गर्ने निमन्त्रणा होइन।
प्रतिस्थापन प्रणाली डिजाइन भइरहँदा i18n प्याचहरूलाई सटीक र सीमित राख्नुहोस्। कार्यले स्पष्ट रूपमा उत्पन्न अनुवादहरू आवश्यक नबताएसम्म र
तपाईंले परिणामी डिफ समीक्षा नगरेसम्म बाह्य सेवाहरू कल गर्ने अनुवाद कमान्डहरू नचलाउनुहोस्।

### CLI

**अनुबन्धहरू**

- `bin/cli/` का सार्वजनिक कमाण्ड र फ्ल्यागहरू, उत्पन्न गरिएका API कमाण्डहरू, निकास कोडहरू, stdout/stderr र
  JSON आउटपुटका संरचनाहरू, कन्फिगरेसन/वातावरणको व्यवहार, र प्याकेज गरिएका फाइलहरू।
- CLI का प्रयोगकर्ताले देख्ने स्ट्रिङहरूले CLI i18n तह प्रयोग गर्नुपर्छ र `en`/`pt-BR` क्याटलगहरू समक्रमित राख्नुपर्छ।
- Node लाई समर्थित रनटाइमको रूपमा र प्रकाशित बाइनरी सम्झौतालाई यथावत् राख्नुहोस्।

**केन्द्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # उत्पन्न/बन्डल गरिएको CLI का परिवर्तनहरू
npm run check:pack-policy     # प्याकेज-सतहका परिवर्तनहरू
npm run lint
```

व्यवहार पार्सिङ, फाइलहरू वा निकास स्थितिमा निर्भर हुँदा अस्थायी डेटा डाइरेक्टरीमा ठ्याक्कै सोही कमाण्ड प्रयोग गर्नुहोस्।
CI ले अझ व्यापक प्याकेज आर्टिफ्याक्ट र इकोसिस्टम जाँचहरू गर्छ।

### डेटाबेस

**सम्झौताहरू**

- `src/lib/db/` अन्तर्गतका डोमेन मोड्युलहरू; निर्दिष्ट मोड्युलहरू सिधै आयात गर्नुहोस् (पुरानो `localDb.ts` पुनः-निर्यात तह हटाइएको छ)।
- `src/lib/db/migrations/` अन्तर्गतका क्रमाङ्कित, आइडेम्पोटेन्ट SQL माइग्रेसनहरू, ट्रान्ज्याक्सन सुरक्षा, अपग्रेड
  व्यवहार, इन्डेक्सहरू, र स्किमाबाट प्रभावित प्रत्येक कलर।
- रुट र ह्यान्डलरहरूले कहिल्यै सिधै कच्चा SQL चलाउँदैनन्।

**केन्द्रित चक्र**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

माइग्रेसन थप्दा नयाँ डेटाबेस र अघिल्लो स्किमाबाट हुने अपग्रेड दुवै परीक्षण गर्नुहोस्। डेटाबेस परीक्षणहरूले
ह्यान्डलहरू बन्द गर्नुपर्छ र सफाइका क्रममा `resetDbInstance()` कल गर्नुपर्छ। सक्दो प्रयासमा आधारित Bun एडाप्टर मार्ग
परिवर्तन हुँदा मात्र `npm run test:bun:db` चलाउनुहोस्; Node नै आधिकारिक रहन्छ।

### बिल्ड / डिप्लोय

**सम्झौताहरू**

- रुट र वर्कस्पेस म्यानिफेस्टहरू/लकफाइल, `scripts/build/`, Next.js स्ट्यान्डअलोन असेम्बली, `dist/`
  प्याकेज सामग्री, Electron प्लेटफर्म मेटाडेटा, CI वर्कफ्लोहरू, र डिप्लोयमेन्ट सेन्टिनलहरू।
- समर्थित Node दायराहरू र `CLAUDE.md` मा अनुमति-सूचीमा राखिएको Bun को प्रयोग यथावत् रहनुपर्छ।
- बिल्ड आर्टिफ्याक्टहरू ट्र्याक नगरिएका रहन्छन्; डिपेन्डेन्सी, लाइसेन्स, वर्कफ्लो, र प्याकेज नीतिहरू लागू हुन्छन्।

**केन्द्रित चक्र**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # डिपेन्डेन्सी वा लकफाइलका परिवर्तनहरू
npm run check:pack-policy      # प्रकाशित प्याकेज सतहका परिवर्तनहरू
npm run lint
```

परिवर्तनले कम्पाइलेसन, स्ट्यान्डअलोन असेम्बली, एसेटहरू वा रनटाइम बन्डलिङलाई असर गर्दा मात्र स्थानीय रूपमा `npm run build` प्रयोग गर्नुहोस्।
रिलिज/डिप्लोय प्रमाणीकरणका लागि मात्र `npm run build:release` प्रयोग गर्नुहोस्। CI को बिल्ड नै अन्तिम क्रस-प्लेटफर्म सङ्केत हो;
प्लेटफर्म-विशिष्ट Electron परिवर्तनहरूका लागि सम्बन्धित केन्द्रित बिल्ड वा स्मोक प्रमाण आवश्यक हुन्छ।

## स्थानीय लूप बनाम CI

| प्रत्येक प्याचका लागि स्थानीय रूपमा चलाउनुहोस्                                           | CI ले व्यापक सङ्केत प्रदान गर्छ                                                    |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| माथिका प्रत्यक्ष व्यवहार परीक्षणहरू र श्रेणी गेटहरू                                      | शार्ड गरिएको पूर्ण युनिट सुइट र सिरियल परीक्षणहरू                                  |
| `npm run lint`                                                                           | Vitest सुइटहरू र कभरेज/गुणस्तर र्याचेटहरू                                          |
| प्रभावित कन्ट्र्याक्टले आवश्यक ठहर्याउँदा मात्र टाइपचेक वा बिल्ड गर्नुहोस्               | प्रोडक्सन बिल्ड, सुरक्षा, डक्स, डिपेन्डेन्सी र PR-नीति गेटहरू                      |
| अटोमेसनले व्यवहार प्रमाणित गर्न नसक्दा मात्र म्यानुअल अन्तरक्रिया/लाइभ जाँचहरू गर्नुहोस् | वर्कफ्लोद्वारा कन्फिगर गरिएका क्रस-जबसँग सम्बन्धित इन्टिग्रेसन र प्लेटफर्म जाँचहरू |

हरियो देखिएको केन्द्रित लूप परिवर्तन गरिएको कन्ट्र्याक्टसम्बन्धी प्रमाण हो, असम्बन्धित CI जाँचहरू
पास हुनेछन् भन्ने प्रमाण होइन। त्यसैगरी, प्रत्येक स्थानीय सम्पादनलाई पूर्ण रिपोजिटरी म्याट्रिक्सका लागि प्रतीक्षा नगराउनुहोस्।

## पुनर्मिलान चेकलिस्ट

समीक्षाका लागि अनुरोध गर्नुअघि:

- PR को आधार अझै पनि सबैभन्दा उच्च सक्रिय `release/v*` ब्रान्च हो भनी पुष्टि गर्नुहोस्।
- उक्त आधार फेच गर्नुहोस् र तपाईंले ब्रान्च बनाएपछि त्यसमा समावेश भएका कमिटहरू समीक्षा गर्नुहोस्।
- अनपेक्षित वा जेनेरेट गरिएको अनावश्यक परिवर्तनका लागि `git diff <active-base>...HEAD` समीक्षा गर्नुहोस्।
- स्रोत अपडेट गरेर र आउटपुट पुनः जेनेरेट गरेर क्याटलग तथा जेनेरेट गरिएका डकुमेन्टका द्वन्द्वहरू समाधान गर्नुहोस्।
- पुनर्मिलानपछि PR विवरणमा सूचीबद्ध प्रत्येक केन्द्रित परीक्षण/गेट पुनः चलाउनुहोस्।
- सरेको आधारसँग मिलाउनकै लागि एसर्शनहरू कहिल्यै कमजोर नबनाउनुहोस् वा आवश्यक परीक्षणहरू नहटाउनुहोस्।

रिलिज-फ्रिज र रिटार्गेटिङ नियमहरूका लागि,
[ब्रान्चिङ र रिलिज मोडेल](BRANCHING_MODEL.md) प्रयोग गर्नुहोस्। पूर्ण CI सूचीका लागि,
[गुणस्तर गेट सन्दर्भ](../architecture/QUALITY_GATES.md) प्रयोग गर्नुहोस्।
