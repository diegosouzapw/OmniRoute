> योग्य कन्टेक्स्टमा स्वचालित रूपमा 15-95% बचत गर्नुहोस्। द्रुत अवलोकनका लागि, [README Compression खण्ड](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) हेर्नुहोस्।

## अवलोकन

OmniRoute ले एउटा मोड्युलर प्रम्प्ट कम्प्रेसन पाइपलाइन कार्यान्वयन गर्छ, जुन अनुरोधहरू अपस्ट्रिम प्रदायकहरूमा पुग्नुअघि नै **सक्रिय रूपमा** चल्छ। यसको अर्थ तपाईंको टोकन बचत पारदर्शी रूपमा हुन्छ — तपाईंको कार्यप्रवाहमा कुनै परिवर्तन आवश्यक पर्दैन।

```
क्लाइन्ट अनुरोध
  → कम्प्रेसन रणनीति चयनकर्ता
    → कम्बो ओभरराइड? → कम्बो सेटिङ प्रयोग गर्नुहोस्
    → स्वतः-ट्रिगर सीमा? → स्वतः मोड प्रयोग गर्नुहोस्
    → पूर्वनिर्धारित मोड? → ग्लोबल सेटिङ प्रयोग गर्नुहोस्
    → बन्द? → कम्प्रेसन छोड्नुहोस्
  → चयन गरिएको कम्प्रेसन मोड
    → बन्द: कम्प्रेसन हुँदैन
    → हल्का: सुरक्षित ह्वाइटस्पेस/ढाँचा सफाइ (~15%)
    → मानक: टुक्रे शैलीका अनावश्यक शब्द हटाउने (~30%)
    → आक्रामक: इतिहासको समयानुसार सङ्कुचन + सारांश (~50%)
    → अल्ट्रा: ह्युरिस्टिक छाँटकाँट + कोड-ब्लक सङ्कुचन (~75%)
    → RTK: कमान्ड-सचेत टर्मिनल/उपकरण-आउटपुट फिल्टरिङ (60-90% अपस्ट्रिम दायरा)
    → स्ट्याक्ड: क्रमबद्ध बहु-इन्जिन पाइपलाइन, सामान्यतया पहिले RTK अनि Caveman (78-95% योग्य दायरा)
  → कम्प्रेस गरिएको अनुरोध → प्रदायक
```

## कम्प्रेसन मोडहरू

### बन्द

कुनै कम्प्रेसन लागू गरिँदैन। सबै सन्देशहरू अपरिवर्तित रूपमा पार हुन्छन्।

### हल्का मोड (~15% बचत, <1ms विलम्बता)

सबैभन्दा सुरक्षित मोड — अर्थमा कुनै परिवर्तन नगरी, ढाँचाको सफाइ मात्र:

| प्रविधि                  | विवरण                                                   |
| ------------------------ | ------------------------------------------------------- |
| `collapseWhitespace`     | लगातारका खाली लाइन र लाइनको अन्त्यका स्पेसहरू मर्ज गर्छ |
| `dedupSystemPrompt`      | दोहोरिएका सिस्टम सन्देशहरू हटाउँछ                       |
| `compressToolResults`    | विस्तृत उपकरण/फङ्सन आउटपुटहरू कम्प्रेस गर्छ             |
| `removeRedundantContent` | दोहोरिएका निर्देशनहरू हटाउँछ                            |
| `replaceImageUrls`       | base64 छवि डेटा URI हरू छोट्याउँछ                       |

**यसका लागि उत्तम:** सधैँ सक्रिय रहने प्रयोग, सुरक्षा-महत्त्वपूर्ण कार्यप्रवाहहरू।

### मानक मोड (~30% बचत)

[Caveman](https://github.com/JuliusBrussee/caveman) बाट प्रेरित — अर्थ जोगाउँदै अनावश्यक शब्द र लामा वाक्यांशहरू हटाउँछ:

- अनावश्यक शब्दहरू ("please", "I think", "basically", "actually") हटाउँछ
- लामा वाक्यांशहरू सङ्क्षिप्त बनाउँछ ("in order to" → "to", "as a result of" → "because")
- विनम्र अनिश्चयात्मक अभिव्यक्तिहरू ("Would you mind...", "If you could possibly...") हटाउँछ
- कोडिङ प्रम्प्टहरूका लागि अनुकूलित 30+ regex नियमहरू

**यसका लागि उत्तम:** दैनिक कोडिङ कार्यप्रवाहहरू, लागतप्रति सचेत टोलीहरू।

### आक्रामक मोड (~50% बचत)

लामा सत्रहरूका लागि स्मार्ट इतिहास व्यवस्थापन:

- **सन्देशको समयानुसार सङ्कुचन** — पुराना सन्देशहरू क्रमशः थप कम्प्रेस हुन्छन्
- **उपकरण नतिजा कम्प्रेसन** — लामा उपकरण आउटपुटहरू छोट्याइन्छन् वा हटाइन्छन् (सुरु/अन्त्यका लाइनहरू,
  मिल्ने लाइनको फिल्टरिङ, JSON कुञ्जी सङ्कुचन)
- **संरचनात्मक अखण्डता सुरक्षा** — `tool_use` + `tool_result` जोडीहरू सुसङ्गत रहने सुनिश्चित गर्छ
- **कन्टेक्स्ट विन्डो सचेतना** — प्रत्येक मोडेलका टोकन सीमाहरू पालना गर्छ

**यसका लागि उत्तम:** विस्तारित डिबगिङ सत्रहरू, ठूला कोडबेसहरू।

### अल्ट्रा मोड (~75% बचत)

टोकन-महत्त्वपूर्ण अवस्थाहरूका लागि अधिकतम कम्प्रेसन:

- **ह्युरिस्टिक छाँटकाँट** — गद्यको स्कोरमा आधारित टोकन छाँटकाँट
- **संरचना संरक्षण** — फेन्स गरिएका कोड ब्लक, इनलाइन कोड, URL र आइडेन्टिफायरहरूलाई
  टुम्बस्टोन बनाएर जस्ताको तस्तै पुनः जोडिन्छ, कहिल्यै छाँटिँदैन
- **वैकल्पिक SLM तह** — कन्फिगर गरिएको अवस्थामा सानो स्थानीय मोडेलले छाँटकाँटलाई अझ परिष्कृत गर्न सक्छ
- आक्रामक मोडबाट स्वतन्त्र: यसले सन्देशको समयानुसार सङ्कुचन, उपकरण-नतिजा कम्प्रेसन
  वा फलब्याक सारांशकर्ता चलाउँदैन (SLM-तहको विफलताले मात्र फलब्याक पासलाई
  आक्रामक मोडमार्फत रुट गर्न सक्छ)

**यसका लागि उत्तम:** तपाईं बारम्बार कन्टेक्स्ट सीमामा पुग्दा।

### RTK मोड (60-90% अपस्ट्रिम दायरा)

RTK मोड कोडिङ-एजेन्ट सत्रहरूमा देखिने विस्तृत उपकरण आउटपुटहरूका लागि अनुकूलित गरिएको छ:

- `git status`, `git diff`, `git log`, परीक्षण रनरहरू,
  TypeScript/Vite/Webpack बिल्डहरू, ESLint/Biome/Prettier, npm अडिट/इन्स्टल, Docker लगहरू, इन्फ्रा
  आउटपुट र सामान्य शेल आउटपुटजस्ता कमान्ड/आउटपुट वर्गहरू पत्ता लगाउँछ
- `open-sse/services/compression/engines/rtk/filters/` बाट JSON फिल्टर प्याकहरू लागू गर्छ
- परियोजना वा ग्लोबल `filters.toml` फाइलहरूबाट RTK TOML schema v1 फिल्टरहरू आयात गर्छ, जसमा इनलाइन-परीक्षण
  प्रमाणीकरण र परियोजना फाइलहरूका लागि विश्वास-गेटिङ समावेश हुन्छ
- इनलाइन प्रमाणीकरण नमुनाहरूसहित 55 वटा बिल्ट-इन फिल्टर प्रदान गर्छ
- ANSI नियन्त्रण अनुक्रमहरू, प्रगति बारहरू, दोहोरिएका लाइनहरू र कारबाही गर्न नसकिने अनावश्यक सामग्री हटाउँछ
- विफलता, त्रुटि, चेतावनी, परिवर्तन गरिएका फाइल, सारांश र लामो आउटपुटको अन्तिम भाग सुरक्षित राख्छ
- विश्वास-गेट गरिएका परियोजना फिल्टरहरू, ग्लोबल फिल्टरहरू र वैकल्पिक रूपमा सम्पादन गरिएको कच्चा-आउटपुट पुनःप्राप्ति समर्थन गर्छ

**यसका लागि उत्तम:** शेल, बिल्ड, परीक्षण, git, grep र फाइल-आउटपुट ट्रान्सक्रिप्टहरू भएका एजेन्ट सत्रहरू।

### स्ट्याक्ड मोड (78-95% योग्य दायरा)

स्ट्याक्ड मोडले धेरै कम्प्रेसन इन्जिनहरू निश्चित क्रममा चलाउँछ। पूर्वनिर्धारित पाइपलाइन यस्तो छ:

```txt
RTK -> Caveman
```

यस क्रमले पहिले टर्मिनल/उपकरण आउटपुटलाई सङ्क्षिप्त राख्छ, त्यसपछि बाँकी प्राकृतिक-भाषा प्रम्प्टमा Caveman को अर्थगत सङ्कुचन लागू गर्छ। स्ट्याक्ड पाइपलाइनहरूलाई ग्लोबल रूपमा वा राउटिङ कम्बोहरूमा तोकिएका कम्प्रेसन कम्बोहरूमार्फत कन्फिगर गर्न सकिन्छ।

**यसका लागि उत्तम:** ठूला उपकरण लगहरूका साथै मानवीय निर्देशन वा सहायकका सारांशहरू भएको मिश्रित कन्टेक्स्ट।

## अपस्ट्रिम बचतको गणना

OmniRoute ले दुई स्रोतबाट हुने कम्प्रेसन बचतको अभिलेख राख्छ: अपस्ट्रिम परियोजनाका बेन्चमार्कहरू र
OmniRoute को आफ्नै इन्जिन संयोजन।

| स्रोत   | यहाँ प्रयोग गरिएको अपस्ट्रिम README को सङ्ख्या                                                         |
| ------- | ------------------------------------------------------------------------------------------------------ |
| Caveman | `~75%` कम आउटपुट टोकन, `65%` बेन्चमार्क औसत आउटपुट बचत, `22-87%` दायरा, र `~46%` इनपुट कम्प्रेसन उपकरण |
| RTK     | कमाण्ड-आउटपुटमा `60-90%` बचत; नमुना सत्रमा `~118,000 -> ~23,900` टोकन, अर्थात् `79.7%` बचत (`~80%`)    |

एक-अर्कासँग खप्टिने उपकरण/कन्टेक्स्ट पेलोडहरूका लागि, पूर्वनिर्धारित OmniRoute कम्बोले इन्जिनहरूलाई यसरी स्ट्याक गर्छ:

```txt
RTK -> Caveman
```

संयुक्त बचत गुणात्मक हुन्छ, योगात्मक होइन:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

त्यो `78-95%` सङ्ख्या RTK र Caveman दुवैले एउटै इनपुट/कन्टेक्स्ट पेलोड घटाउन सक्ने अवस्थामा लागू हुन्छ।
Caveman प्रतिक्रिया आउटपुट मोड छुट्टै हो: यो सक्षम हुँदा, Caveman कै आफ्नै आउटपुट बचत (`65%`
औसत, `~75%` प्रमुख आँकडा, `22-87%` दायरा) प्रयोग गर्नुहोस्। कुल बिलिङ बचत तपाईंको प्रम्प्ट/आउटपुट मिश्रणमा निर्भर हुन्छ।

### "योग्य" भन्नाले वास्तवमा के बुझिन्छ

15-95% को प्रमुख दायरा वास्तविक हो, तर यो **अनावश्यक रूपमा दोहोरिएको वा विस्तृत** सामग्रीमा मात्र लागू हुन्छ — दोहोरिएका
त्रुटि पङ्क्तिहरू, एउटै चेतावनी बारम्बार देखाउने बिल्ड लग, आवश्यकताभन्दा ठूलो `grep`/फाइल-रिड डम्प। यसको अर्थ
हरेक अनुरोधले त्यति नै बचत गर्छ भन्ने **होइन**।

प्रयोगात्मक रूपमा प्रमाणित (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300 वटा समान
त्रुटि पङ्क्ति समावेश भएको Anthropic-आकारको `tool_result` ब्लकमा चलाइएको `stacked` (RTK + Caveman) रनले
**95.93% टोकन बचत / 96.26% क्यारेक्टर बचत** उत्पन्न गर्यो — जुन विज्ञापित
दायराभित्र स्पष्ट रूपमा पर्छ। तर सामान्य, अनावश्यक दोहोरिन नभएको उपकरण आउटपुट (सफा `grep` मिलान सूची,
छोटो फाइल रिड, सामान्य संवादात्मक पाठ) मा चलाइएको उही पाइपलाइनले सही रूपमा **लगभग शून्य बचत** उत्पन्न गर्छ, किनभने
हटाउनुपर्ने दोहोरिएको सामग्री हुँदैन र `validateCompression()` (`validation.ts`) ले कोड ब्लक, URL, शीर्षक, संस्करण, वा ALL-CAPS स्थिर पहिचानकर्ता हटाउने वा परिवर्तन गर्ने
पुनर्लेखन पठाउन अस्वीकार गर्छ।

यो अपेक्षित, सुरक्षित व्यवहार हो, बग होइन: मुख्यतः सफा फाइलहरू पढ्ने/grep गर्ने कोडिङ सत्रमा
कम्प्रेसन पूर्ण रूपमा सक्षम हुँदा पनि कुल बचत सामान्य हुनेछ, जबकि असफल भइरहने
लुप वा धेरै आउटपुट दिने लिन्टर सामना गर्ने सत्रले त्यस्तो ट्राफिकमा पूर्ण 78-95% दायरा देख्नेछ। एउटै सत्रको
कम समग्र बचत प्रतिशतलाई कम्प्रेसन गलत कन्फिगर भएको प्रमाणका रूपमा प्रयोग नगर्नुहोस् — पहिले अन्तर्निहित
उपकरण आउटपुट वास्तवमै अनावश्यक रूपमा दोहोरिएको थियो कि थिएन जाँच गर्नुहोस्।

## कन्फिगरेसन

### ड्यासबोर्ड

`Dashboard → Context & Cache` मा जानुहोस्:

- **Caveman** — मोड छनोट, भाषा प्याकहरू, पूर्वावलोकन र विश्वव्यापी पूर्वनिर्धारितहरू
- **RTK** — कमाण्ड-फिल्टर पूर्वावलोकन, RTK सुरक्षा सेटिङहरू र फिल्टर सूची
- **Compression Combos** — राउटिङ कम्बोहरूमा तोकिएका नामयुक्त इन्जिन पाइपलाइनहरू
- **Auto-Trigger Threshold** — टोकन सङ्ख्याले थ्रेसहोल्ड नाघ्दा कम्प्रेसन स्वतः सक्रिय गर्ने

### प्रत्येक कम्बोको ओभरराइड

`Dashboard → Context & Cache → Compression Combos` मा, राउटिङ कम्बोलाई एउटा कम्प्रेसन कम्बो तोक्नुहोस्:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

यसले सशुल्क सदस्यताहरूमा लाइट मोड कायम राख्दै निःशुल्क/कोडिङ प्रदायकहरूमा स्ट्याक गरिएको कम्प्रेसन प्रयोग गर्न दिन्छ।

यो "Per-Combo Override" असाइनमेन्ट **routing-combo compression mode** ओभरराइड (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — फिल्डको स्किमाले `rtk`, `stacked` र `omniglyph` पनि स्वीकार गर्छ) भन्दा फरक नियन्त्रण हो — त्यस ओभरराइडले नामयुक्त compression-combo पाइपलाइन चयन गर्दैन; यसले केवल `resolveCompressionPlan` द्वारा प्रयोग गरिने `compressionMode` फिल्ड सेट गर्छ। यसलाई कम्बो कार्ड (`Dashboard → Combos`) मा वा #6760 देखि, माथि दस्तावेजीकरण गरिएको पाइपलाइन-असाइनमेन्ट चेकबक्सको ठीक छेउमा रहेको `Dashboard → Context & Cache → Compression Combos` को "Assign to routing" सूचीमा प्रत्येक राउटिङ कम्बोका लागि सेट गर्न सकिन्छ। दुवै सतहका सेटिङहरू एउटै `PUT /api/combos/{id}` एन्डपोइन्टमार्फत स्थायी रूपमा सुरक्षित हुन्छन्।

### प्रत्येक अनुरोधको ओभरराइड

एउटा अनुरोधका लागि कम्प्रेसन योजना ओभरराइड गर्न `x-omniroute-compression` अनुरोध हेडर पठाउनुहोस्। यसको प्राथमिकता सबैभन्दा उच्च हुन्छ — यसले राउटिङ-कम्बो ओभरराइड, सक्रिय प्रोफाइल, स्वतः-ट्रिगर र प्यानलको Default लाई उछिन्छ। अज्ञात मानहरू बेवास्ता गरिन्छन् (अनुरोध कहिल्यै अस्वीकार गरिँदैन) र विश्वव्यापी मुख्य स्विचले अझै पनि सबै कुरा नियन्त्रण गर्छ: कम्प्रेसन विश्वव्यापी रूपमा बन्द हुँदा, हेडरले यसलाई सक्रिय गर्न सक्दैन। मानहरू:

| मान           | प्रभाव                                                                                                       |
| ------------- | ------------------------------------------------------------------------------------------------------------ |
| `off`         | यस अनुरोधका लागि कम्प्रेसन हुँदैन।                                                                           |
| `default`     | प्यानलबाट व्युत्पन्न Default प्रोफाइल (सक्रिय प्रोफाइललाई बेवास्ता गर्छ)। क्षतियुक्त इन्जिनहरू बन्द रहन्छन्। |
| `safe`        | हेडर नपठाएसरह: डिडुप र ह्वाइटस्पेस फोल्डिङ मात्र।                                                            |
| `allow-lossy` | सारांश, सान्दर्भिकता फिल्टर र शैली पुनर्लेखनसहित यस अनुरोधको अपरेटर योजना कायम राख्छ।                        |
| `engine:<id>` | सक्षम हुँदा एउटा मात्र इन्जिन, जस्तै `engine:rtk`। यो त्यस इन्जिनका लागि प्रत्येक अनुरोधको अप्ट-इन हो।       |
| `<combo>`     | नामद्वारा (केस-असंवेदनशील रूपमा) पहिले र त्यसपछि id द्वारा मिलाइने नामयुक्त कम्बो।                           |

`allow-lossy`, `engine:<id>`, वा नामयुक्त कम्बोबिना क्षतियुक्त इन्जिनहरू लागू हुँदैनन्। कम्प्रेसन सक्रिय हुँदा अनुरोधमा अझै पनि सेसन डिडुप र ह्वाइटस्पेस फोल्डिङ लागू हुन्छ।

लागू गरिएको योजना `X-OmniRoute-Compression: <mode>; source=<source>` प्रतिक्रिया हेडरमा फिर्ता पठाइन्छ, जहाँ `<source>` भनेको `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, वा `off` मध्ये एक हो।

## आभार

मानक मोडका कम्प्रेसन नियमहरू **[JuliusBrussee](https://github.com/JuliusBrussee)** को **[Caveman](https://github.com/JuliusBrussee/caveman)** (⭐ 51K+) — भाइरल "धेरै टोकन किन प्रयोग गर्ने, जब थोरै टोकनले काम गर्छ" परियोजनाबाट प्रेरित छन्। Caveman ले आउटपुट टोकनहरूमा `~75%` कमी, बेन्चमार्कको औसत आउटपुट बचत `65%`, आउटपुट दायरा `22-87%`, र `~46%` इनपुट-कम्प्रेसन उपकरण रिपोर्ट गर्छ।

RTK मोड **[RTK AI](https://github.com/rtk-ai)** को **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** — टर्मिनल, बिल्ड, परीक्षण, git, र उपकरण-आउटपुट फिल्टरिङका लागि उच्च-प्रदर्शनयुक्त कमान्ड-आउटपुट कम्प्रेसन परियोजनाबाट प्रेरित छ। RTK ले `60-90%` बचत रिपोर्ट गर्छ, र यसको README को नमुना सत्रले `~80%` बचत देखाउँछ।

## उन्नत कम्प्रेसन प्रणालीहरू

माथि वर्णन गरिएका 7 मोडहरूबाहेक (स्रोतले `codex-responses` र
`omniglyph` मोडहरू पनि स्वीकार गर्छ, जसलाई यो मार्गदर्शिकाले समेट्दैन), तलका खण्डहरूले
ती मोडहरूभित्र वा तिनका साथमा काम गर्ने सुविधाहरू समेट्छन्: उपकरण परिणाम कम्प्रेसन र प्रोग्रेसिभ एजिङ
आक्रामक इन्जिनका चरण 1 र 2 हुन् (आक्रामक मोड र
स्ट्याक्ड पाइपलाइनको एउटा `aggressive` चरण), स्ट्याक्ड पाइपलाइन भनेको स्ट्याक्ड मोड चल्ने तरिका हो, क्यास-सचेत कम्प्रेसनले कम्प्रेसन
सक्रिय हुँदा क्यासिङ प्रदायकहरूका लागि `aggressive` र `ultra` लाई `standard` मा
घटाउँछ, र Caveman आउटपुट मोड तथा आउटपुट शैलीहरू वैकल्पिक प्रणाली-प्रम्प्ट निर्देशनहरू हुन्,
जुन पूर्वनिर्धारित रूपमा बन्द हुन्छन् र अनुरोध कम्प्रेस गर्नुको सट्टा मोडेलको आउटपुटलाई आकार दिन्छन्।

### क्यास-सचेत कम्प्रेसन

केही प्रदायकहरू (जस्तै प्रम्प्ट क्यासिङसहितको Anthropic) ले **प्रम्प्ट क्यासिङ**
समर्थन गर्छन्, जसले लागत र विलम्बता घटाउन प्रम्प्टका केही भाग क्यास गर्न दिन्छ। जब
क्यासिङ सक्षम हुन्छ, आक्रामक कम्प्रेसनले वास्तवमै कार्यसम्पादनमा **हानि** पुर्याउन सक्छ
किनकि यसले क्यास गरिएका टोकनहरू परिवर्तन गरेर क्यासलाई अमान्य बनाउँछ।

`cachingAware.ts` मोड्युलले **क्यासिङ कन्टेक्स्ट पत्ता लगाएर** र
त्यसअनुसार **कम्प्रेसन रणनीति समायोजन गरेर** यो समस्या समाधान गर्छ।

#### यसले कसरी काम गर्छ

1. **क्यासिङ कन्टेक्स्ट पत्ता लगाउने** — `cache_control` मार्करहरूका लागि अनुरोध बडी स्क्यान गर्छ
2. **क्यासिङ प्रदायकहरू पहिचान गर्ने** — लक्षित प्रदायकले क्यासिङ समर्थन गर्छ कि गर्दैन जाँच्छ
3. **रणनीति समायोजन गर्ने** — क्यासिङ प्रदायकहरूका लागि `aggressive`/`ultra` लाई `standard` मा घटाउँछ
4. **प्रणाली प्रम्प्ट छोड्ने** — प्रणाली प्रम्प्टहरू सामान्यतया क्यास गरिन्छन्, त्यसैले तिनलाई कम्प्रेस नगर्नुहोस्

रणनीति सहायकले `deterministicOnly` फ्ल्याग पनि फर्काउँछ, तर योजना निर्माताले
रणनीति मात्र प्रयोग गर्छ — हाल त्यसपछिको कुनै पनि भागले उक्त फ्ल्याग पढ्दैन।

#### कोड उदाहरण

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← क्यास मार्कर
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### कहिले प्रयोग गर्ने

क्यास-सचेत कम्प्रेसन **सधैं सक्रिय हुन्छ** — कुनै कन्फिगरेसन आवश्यक पर्दैन। कम्प्रेसन
सक्रिय हुँदा र लक्षित प्रदायकले प्रम्प्ट क्यासिङ (Anthropic, OpenAI,
आदि) समर्थन गर्दा यो लागू हुन्छ; स्पष्ट `cache_control` मार्करहरू आवश्यक पर्दैनन् — क्यासिङ प्रदायक मात्रैले
डाउनग्रेड ट्रिगर गर्छ, र मार्करहरू मात्रैले कहिल्यै गर्दैनन् (मार्कर पहिचानले क्यास
टेलिमेट्रीमा डेटा दिन्छ, रणनीतिको निर्णयमा होइन)।

### प्रोग्रेसिभ एजिङ

लामा कुराकानीहरूमा धेरै सन्देश पालोहरू जम्मा हुन्छन्, तर पुराना पालोहरू क्रमशः कम
सान्दर्भिक बन्छन्। `progressiveAging.ts` मोड्युलले **पालो दूरीअनुसार सन्देशहरू घटाउँछ**
(दूरी कुराकानीको अन्त्यबाट मापन गरिन्छ)। जारी गरिएका पूर्वनिर्धारित मानहरूसँग
(`verbatim: 2, light: 2, moderate: 3`):

- **अन्तिम 2 पालाहरू (दूरी ≤ 2)**: जस्ताको तस्तै राखिन्छ
- **दूरी 3**: केभम्यान सङ्कुचन (अनावश्यक शब्द हटाउने)
- **दूरी 4+**: सहायकका सन्देशहरू सारांशित गरिन्छन्; प्रयोगकर्ताका सन्देशहरूलाई तिनको पहिलो
  पङ्क्तिमा सीमित गरिन्छ, अधिकतम 120 वर्णसम्म; अन्य भूमिकाहरूलाई नछोइन्छ। प्रणाली प्रम्प्टहरू, पहिले नै पुराना बनाइएका
  सन्देशहरू र नवीनतम प्रयोगकर्ता सन्देश दूरी जति भए पनि सधैँ जस्ताको तस्तै राखिन्छन्।
  कुनै पनि कुरा पूर्ण रूपमा हटाइँदैन, र उपलब्ध गराइएका पूर्वनिर्धारित मानहरूमा `light`
  ब्यान्डसम्म पुग्न सकिँदैन (`light`, `verbatim` बराबर हुन्छ)।

#### कोड उदाहरण

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... थप 50 पालाहरू ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // अन्तिम 3 पालाहरू: जस्ताको तस्तै
  light: 8, // दूरी <= 8: हल्का सङ्कुचन
  moderate: 20, // दूरी <= 20: केभम्यान सङ्कुचन
  fullSummary: 5, // प्रकारका लागि आवश्यक, ब्यान्डिङ कोडले पढ्दैन
  // दूरी > 20: सारांशित (सहायक) / पहिलो पङ्क्ति राखिने (प्रयोगकर्ता)
});

// saved = बचत भएका टोकनहरूको सङ्ख्या
```

#### कहिले प्रयोग गर्ने

प्रगतिशील एजिङ `aggressive` मोडका लागि **सधैँ सक्रिय** हुन्छ — यो
`compressAggressive()` को चरण 2 हो। Ultra मोडले यसलाई चलाउँदैन। यो विशेष गरी
निम्न अवस्थामा प्रभावकारी हुन्छ:

- लामो समयसम्म चल्ने कोडिङ सत्रहरू
- धेरै दिनसम्म चल्ने कुराकानीहरू
- धेरै टुल कल भएका एजेन्टिक कार्यप्रवाहहरू

### केभम्यान आउटपुट मोड

केभम्यान आउटपुट मोडले **प्रणाली प्रम्प्ट निर्देशनहरू** थप्छ, जसले मोडेललाई नै
संक्षिप्त आउटपुट दिन आग्रह गर्छ — `lite` स्तरले पूर्ण वाक्यहरू कायम राख्दै संक्षिप्त उत्तर माग्छ, `full`
ले यसलाई "बुद्धिमान केभम्यानजस्तै संक्षिप्त जवाफ दिन" भन्छ, र `ultra` ले तार-सन्देश शैलीको आउटपुट माग्छ;
निर्देशनहरूले आग्रह मात्र गर्छन्, यसको प्रत्याभूति दिन सक्दैनन्। अनुरोधहरूले तिनलाई
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) मार्फत प्राप्त गर्छन्:
`open-sse/handlers/chatCore.ts` ले पहिले पश्चगामी-अनुकूलता शिम
(`open-sse/services/compression/outputStyles/backCompat.ts` मा रहेको `resolveOutputStyleSelection()`)
मार्फत चयन निर्धारण गर्छ, जसले `outputStyles`
खाली हुँदा सक्षम गरिएको `cavemanOutputMode` लाई
`cavemanOutputMode.intensity` मा `terse-prose` आउटपुट शैलीसँग म्याप गर्छ (तलको पश्चगामी-अनुकूलता हेर्नुहोस्);
खाली नभएको `outputStyles`
चयन जस्ताको तस्तै प्रयोग गरिन्छ, र त्यसपछि `cavemanOutputMode.enabled` तथा `intensity` ले कुनै
प्रभाव पार्दैनन्, यद्यपि यसको `autoClarity` टगल अझै लागू हुन्छ। `outputMode.ts` मा
निर्देशन पाठहरू (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), सामग्री बाइपास र
इन्जेक्सनले प्रयोग गर्ने प्लेसमेन्ट सहायक छन्; यसको आफ्नै `applyCavemanOutputMode()` इन्जेक्टरको कुनै
उत्पादन कलर छैन।

#### यसले कसरी काम गर्छ

यो मोडले इनपुट सङ्कुचित गर्दैन। यसले प्रणाली प्रम्प्टमा एउटा निर्देशन ब्लक थप्छ
(तलको इन्जेक्सनले कसरी काम गर्छ हेर्नुहोस्), र अनुरोधका लागि चयन गरिएको कुनै पनि इनपुट सङ्कुचन मोड
त्यसपछि पनि चल्छ, अब उक्त ब्लक समावेश भएको बडीमा। प्रत्येक स्तरको अन्त्यमा आउने साझा
सीमासम्बन्धी खण्डअघि, अङ्ग्रेजी `full` स्तर यस्तो छ:

> "बुद्धिमान केभम्यानजस्तै संक्षिप्त जवाफ दिनुहोस्। उपपदहरू (a/an/the), अनावश्यक शब्दहरू (just/really/basically/actually/simply), शिष्टाचारका अभिव्यक्तिहरू र अनिश्चितता जनाउने भाषा हटाउनुहोस्। वाक्यांशहरू स्वीकार्य छन्। छोटा पर्यायवाची प्रयोग गर्नुहोस् (extensive होइन big, implement होइन fix)। सबै प्राविधिक सारतत्त्व, कोड, त्रुटिहरू, URLs र पहिचानकर्ताहरू हुबहु राख्नुहोस्।"

यसले विशेष गरी निम्नका लागि राम्रोसँग काम गर्छ:

- कोड उत्पादन (अझ संक्षिप्त आउटपुट = कम टोकन)
- छोटो प्रश्नोत्तर (विस्तृत व्याख्या आवश्यक पर्दैन)
- ब्याच प्रशोधन (थ्रुपुट अधिकतम बनाउने)

#### कहिले प्रयोग गर्ने

केभम्यान आउटपुट मोड **स्वेच्छिक** हो। सङ्कुचन सक्रिय हुँदा (`enabled: true`, Compression Settings पृष्ठमा रहेको मुख्य टगल
सक्रिय हुँदा), यसलाई `cavemanOutputMode.enabled` मार्फत सक्रिय गर्नुहोस्; `intensity`
ले `lite`, `full` वा `ultra` छान्छ:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

सङ्कुचन कम्बोको **आउटपुट मोड** टगल (`outputMode`, स्तर `outputModeIntensity` मा)
ले उक्त कम्बो लागू हुने अनुरोधहरूका लागि उही स्विच सेट गर्छ, र
`omniroute_set_compression_engine` MCP टुलले आफ्नो बुलियन `outputMode`
आर्गुमेन्टमार्फत यसलाई लेख्छ। खाली नभएको `outputStyles` चयनले यस स्विचभन्दा प्राथमिकता पाउँछ। ड्यासबोर्डमा
**संक्षिप्त गद्य** आउटपुट शैली सक्षम गर्दा उही ब्लक इन्जेक्ट हुन्छ (तलको आउटपुट शैलीहरू हेर्नुहोस्)।

### आउटपुट शैलीहरू (क्याटलग)

माथिको केभम्यान आउटपुट मोड **पुरानो एकल-शैली मार्ग** हो। चरण 4 ले यसलाई
संयोजन गर्न मिल्ने आउटपुट शैलीहरूको क्याटलगमा सामान्यीकरण गर्यो:
`open-sse/services/compression/outputStyles/catalog.ts` मा रहेको `OUTPUT_STYLE_CATALOG`। प्रत्येक शैली प्रणाली-प्रम्प्ट
निर्देशन हो, जसले मोडेललाई नै कम खर्चिलो आउटपुट दिन आग्रह गर्छ; शैलीहरूलाई
सँगसँगै सक्षम गर्न सकिन्छ र तिनीहरू क्याटलगको क्रममा इन्जेक्ट हुन्छन्।

प्रत्येक शैलीमा तीनवटा तीव्रता स्तर — `lite`, `full`, `ultra` — उपलब्ध छन् र प्रत्येक स्तर
साझा सीमा खण्ड (`outputMode.ts` मा `SHARED_BOUNDARIES`) सँग समाप्त हुन्छ, जसले
कोड ब्लक, फाइल पथ, आदेश, त्रुटि र URL हरू ठ्याक्कै कायम राख्छ। `terse-prose` र
`terse-cjk` स्तरका पाठहरूले उक्त सूचीमा पहिचायकहरू पनि थप्छन्।

`terse-cjk` दुई ठाउँमा `zh` लोकेलमा सीमित छ। Compression Settings पृष्ठले
ड्यासबोर्ड UI को भाषा चिनियाँ (`zh-CN` वा `zh-TW`) हुँदा मात्र यसको पङ्क्ति देखाउँछ, र
`applyOutputStyles()` ले अनुरोधको निर्धारित भाषा (तलको भाषा चयन हेर्नुहोस्) `zh`
हुँदा मात्र यसलाई इन्जेक्ट गर्छ। पङ्क्ति लुकाउँदा सुरक्षित गरिएको `terse-cjk` चयन हट्दैन:
सेटिङ्स API ले कुनै पनि शैली id स्वीकार गर्छ, र पृष्ठमा अन्य शैलीहरू सुरक्षित गर्दा पनि यो कायम रहन्छ। अनुरोधको
समयमा, `applyOutputStyles()` को भाषा जाँच नै एकमात्र लोकेल सीमा हो।

#### इन्जेक्सनले कसरी काम गर्छ

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ले
क्याटलगअनुसार चयन निर्धारण गर्छ (अज्ञात ids र लोकेल नमिलेका शैलीहरू
हटाइन्छन्, कहिल्यै त्रुटि हुँदैन; कुनै शैलीमा निर्धारण नहुने चयनले body लाई
अपरिवर्तित छोड्छ, `no_styles` का रूपमा छोडिन्छ), चयन गरिएका निर्देशनहरूलाई क्याटलगको
क्रममा जोड्छ,
सीमा खण्ड **एकपटक** थप्छ (`less-code` वा `ponytail` चयन गरिएको बेला सुरक्षा खण्ड, `SAFETY_BOUNDARIES` वा यसको
अनुवाद पनि थपिन्छ), र ब्लकलाई
एउटै idempotency marker (`[OmniRoute Output Styles]`) बाट सुरु गर्छ, त्यसैले पुनः लागू गर्दा कुनै प्रभाव पर्दैन। जब
निर्धारित भाषा (तलको भाषा चयन हेर्नुहोस्) को अनुवाद उपलब्ध हुन्छ, अंग्रेजीको सट्टा स्थानीयकृत
निर्देशन इन्जेक्ट गरिन्छ।

खाली नभएको `messages` array भएको body मा, idempotency जाँच
सामग्री bypass अघि चल्छ: शीर्ष-स्तरीय `system` field (string वा content-block array) मा वा
string content भएको system message मा `[OmniRoute Output Styles]` marker पहिले नै भएमा,
body लाई `already_applied` का रूपमा अपरिवर्तित छोडिन्छ र कुनै keyword जाँच चल्दैन।
अन्यथा content bypass (`open-sse/services/compression/outputMode.ts` मा
`shouldBypassCavemanOutputMode()`) ले अन्तिम तीन
messages को text, तिनको role जेसुकै भए पनि, जाँच गर्छ र उक्त text ले security, irreversible-action वा clarification keywords, वा
क्रम-संवेदनशील अनुक्रमसँग मेल खाँदा सम्पूर्ण turn का लागि styles छोड्छ: `first`, `then`, `after that`, `before`, `rollback` वा
`backup` पछि 240 characters भित्र `delete`, `drop`, `migrate`, `deploy` वा
`release`। bypass **Auto-Clarity Bypass** toggle
(`cavemanOutputMode.autoClarity`, पूर्वनिर्धारित रूपमा सक्रिय) सक्रिय रहँदा चल्छ; toggle बन्द गर्दा
keyword जाँच छोडिन्छ।

bypass ले turn लाई अघि बढ्न दिँदा, `placeSystemInstruction()` (उही file), जसले
कहिल्यै नयाँ `messages[0]` बनाउँदैन, आफूले फेला पारेको पहिलो स्थानमा block राख्छ:

1. string content भएको सुरुको system message: block त्यसको text पछि थपिन्छ।
2. शीर्ष-स्तरीय `system` field: block string को text पछि थपिन्छ, वा
   content-block array मा नयाँ text block का रूपमा थपिन्छ।
3. string content भएको त्यसपछिको पहिलो system message: block त्यसको
   text पछि थपिन्छ।
4. माथिका कुनै पनि नभएमा: block `messages` को अन्त्यमा नयाँ system message भित्र राखिन्छ।

`messages` array नभएको (वा खाली भएको) body मा कुनै content bypass चल्दैन र
शीर्ष-स्तरीय `system` field हेरिँदैन। block लाई string `instructions` field को text पछि
थपिन्छ, तर उक्त field मा `[OmniRoute Output Styles]` marker पहिले नै भएमा
body लाई `already_applied` का रूपमा अपरिवर्तित छोडिन्छ। body मा string
`instructions` field नभए पनि `input` (string वा array) भएमा, block
`instructions` बन्छ र त्यस field मा रहेको कुनै पनि non-string value प्रतिस्थापन गर्छ। string
`instructions` field वा string वा array `input` दुवै नभएको body लाई अपरिवर्तित छोडिन्छ र
`no_messages` का रूपमा छोडिन्छ।

#### कसरी सक्षम गर्ने

ड्यासबोर्डमा: **Compression Context → Compression Settings**
(`/dashboard/context/settings`), Output styles खण्डमा: प्रत्येक शैलीका लागि अन/अफ
टगल र स्तर चयनकर्ता भएको एउटा पङ्क्ति हुन्छ। कम्प्रेसन स्वयं सक्रिय हुँदा (पृष्ठको
मुख्य टगल, `enabled`) शैलीहरू इन्जेक्ट हुन्छन्। **Auto-Clarity Bypass** टगल **Caveman**
पृष्ठ (`/dashboard/context/caveman`) को **Output Mode** कार्डमा हुन्छ। प्रोग्राममार्फत,
कम्प्रेसन कन्फिगले चयनलाई यसरी कायम राख्छ:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

पछाडि-सङ्गतता: `outputStyles` खाली रहँदा, पुरानो `cavemanOutputMode.enabled`
सेटिङ `cavemanOutputMode.intensity` मा `terse-prose` सँग म्याप हुन्छ। त्यसपछि ब्लक
`[OmniRoute Output Styles]` मार्करबाट सुरु हुन्छ, जहाँ पुरानो `applyCavemanOutputMode()`
इन्जेक्टरले `[OmniRoute Caveman Output Mode]` लेख्थ्यो। मार्करमुनिको पाठ en, pt-BR,
es, de, fr, it, ru, id र vi मा पुरानो इन्जेक्सनसँग मेल खान्छ; ja र zh मा सीमाहरूको
खण्डअघि एउटा अतिरिक्त स्पेस हुन्छ। `terse-prose` लाई pt-BR, es, de, fr, it, ru, zh,
ja, id र vi मा अनुवाद गरिएको छ, त्यसैले रिजोल्भ गरिएको भाषा `hu` भएको अनुरोधले
अङ्ग्रेजी पाठ पाउँछ, जबकि पुरानो इन्जेक्टरले त्यसको हङ्गेरियन पाठ प्रयोग गर्थ्यो।

Output-style भाषा चयन (`outputStyles/apply.ts` मा `resolveOutputStyleLanguage()`):
`languageConfig.enabled` सक्रिय हुँदा, `autoDetect` ले अनुरोधको `messages` एरेमा पाठ
भएको सबैभन्दा पछिल्लो प्रयोगकर्ता सन्देश (स्ट्रिङ सामग्री, वा त्यसका सामग्री भागहरूको
`text`) नमुनाका रूपमा लिन्छ र त्यसमा Caveman इन्जिनको डिटेक्टर
(`detectCompressionLanguage()`) चलाउँछ। डिटेक्टरले हान वर्ण तर काना नभएको पाठका लागि
`zh` फर्काउँछ; अन्यथा यसले `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` र `id`
मध्ये सबैभन्दा धेरै सङ्केत मेल भएको भाषा फर्काउँछ, र कुनै पनि मेल नखाँदा `en`
फर्काउँछ — यसले वर्गीकरण गर्न नसकेको पाठले अङ्ग्रेजी पाउँछ, कहिल्यै
`defaultLanguage` होइन, र शैलीहरूमा `vi` पाठ उपलब्ध भए पनि `vi` कहिल्यै पत्ता लाग्दैन।
Responses API बडीले आफ्ना टर्नहरू `input` मा राख्छ, जसलाई नमुनाका रूपमा लिइँदैन, त्यसैले
यसले `defaultLanguage`, अनि अङ्ग्रेजी पाउँछ। `messages` मा कुनै पनि प्रयोगकर्ता सन्देशमा
पाठ नभएमा, वा `autoDetect` निष्क्रिय हुँदा, `defaultLanguage` लागू हुन्छ, त्यसपछि
अङ्ग्रेजी। `languageConfig.enabled` निष्क्रिय हुँदा, भाषा अङ्ग्रेजी हुन्छ — अनुरोधमा
कुनै कम्प्रेसन कम्बो लागू भएको अवस्थाबाहेक (अनुरोधको राउटिङ कम्बोमा तोकिएको कम्बो, वा
बिल्ट-इन स्ट्याक्ड पाइपलाइनका लागि chatCore ले फलब्याक गर्ने पूर्वनिर्धारित कम्प्रेसन
कम्बो): कम्बो लागू गर्दा उक्त अनुरोधका लागि `languageConfig.enabled` सक्रिय हुन्छ र
कम्बोका भाषा प्याकहरूबाट `defaultLanguage` सेट हुन्छ (सुरक्षित गरिएको मान कम्बोका
प्याकहरूमध्ये एक भएमा त्यही मान, अन्यथा कम्बोको पहिलो प्याक, जुन पूर्वनिर्धारित रूपमा
`en` हुन्छ), जबकि सुरक्षित गरिएको `autoDetect` (पूर्वनिर्धारित रूपमा सक्रिय) अझै लागू
हुन्छ। Caveman इनपुट इन्जिनले आफ्नो नियम-प्याकको भाषा फरक तरिकाले चयन गर्छ — प्रत्येक
पाठ भागअनुसार र, स्वतः-पहिचान निष्क्रिय हुँदा, `enabledPacks` द्वारा गेट गरिएको रूपमा।

शैली × भाषा म्याट्रिक्सलाई
`tests/unit/compression/output-styles-i18n-matrix.test.ts` ले स्थिर गर्छ: प्रत्येक
क्याटलग शैलीका लागि परीक्षणको `BASELINE_LANGUAGES` मा प्रविष्टि हुनुपर्छ; लोकेलद्वारा
गेट नगरिएको शैलीसँग pt-BR अनुवाद हुनैपर्छ (लोकेलद्वारा गेट गरिएको `terse-cjk` यस
नियमबाट मुक्त छ), जबसम्म त्यो `KNOWN_ENGLISH_ONLY` मा सूचीबद्ध छैन, जसमा कुनै पनि
अनुवाद नभएका शैलीहरू मात्र रहन सक्छन् — सूचीबद्ध शैलीसँग कुनै पनि अनुवाद भए परीक्षण
असफल हुन्छ; र शैलीले आफ्नो `BASELINE_LANGUAGES` प्रविष्टिमा सूचीबद्ध भाषा गुमाएमा
परीक्षण असफल हुन्छ। शैली थप्न,
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) हेर्नुहोस्।

### उपकरण परिणाम कम्प्रेसन

`open-sse/services/compression/toolResultCompressor.ts` मा रहेको
`compressToolResult()` ले उपकरण-परिणाम पाठलाई **5 रणनीतिहरू** प्रयोग गरेर कम्प्रेस
गर्छ। यसले तिनलाई यस क्रममा प्रयास गर्छ, र जाँच सामग्रीसँग मेल खाने पहिलो सक्रिय
रणनीतिले परिणाम निर्धारण गर्छ:

1. **`fileContent`**: 3 वा बढी पङ्क्ति भएको सामग्री, जसमा प्रारम्भिक इन्डेन्टेसनलाई बेवास्ता गर्दा कम्तीमा एउटा पङ्क्ति `import `, `export `, `function `, `class `,
   `const `, `let `, `var ` वा `return ` (कुञ्जीशब्द र एउटा खाली ठाउँ) बाट, वा `if`,
   `for` वा `while` पछि `(` वा ` (` आएर सुरु हुन्छ, त्यसले आफ्ना सुरुका 20 र अन्तिम 5 पङ्क्ति राख्छ र
   हटाइएको बीचको भागलाई चिन्ह लगाउँछ।
2. **`grepSearch`**: `<path>:<digits>:` ढाँचाको कम्तीमा एउटा पङ्क्ति भएको सामग्री,
   जहाँ पहिलो कोलोनअघिको पाठमा कुनै खाली ठाउँ हुँदैन, त्यसले बढीमा 30 वटासम्म त्यस्ता पङ्क्तिहरू मात्र राख्छ र
   त्यसपछि थप मिलानहरूको सङ्ख्या तथा मिलान भएका फाइलहरूको सूची राख्छ;
   अन्य प्रत्येक पङ्क्ति हटाइन्छ। रणनीति सक्रिय गर्न यस्तो एउटा पङ्क्ति नै पर्याप्त हुन्छ, त्यसैले
   `12:30:45` जस्तो टाइमस्ट्याम्पबाट सुरु हुने लग पङ्क्ति पनि गणना हुन्छ।
3. **`shellOutput`**: ANSI CSI अनुक्रम (`ESC[` पछि अङ्क वा
   अर्धविराम र त्यसपछि एउटा अक्षर, जस्तै रङ कोडमा) वा पाठको जुनसुकै ठाउँमा खाली ठाउँपछि आउने `$` भएको आउटपुटले
   ती अनुक्रमहरू गुमाउँछ (अन्य एस्केपहरू, जस्तै `ESC[?25l` वा
   OSC विन्डो-शीर्षक अनुक्रम, राखिन्छन्) र लगातार दोहोरिएका पङ्क्तिहरूलाई एउटामा समेटेर आफ्ना अन्तिम 50 पङ्क्ति राख्छ।
   यो जाँच `json` र `errorMessage` भन्दा पहिले चल्ने भएकाले, यस्तो `$` भएको JSON वा त्रुटि आउटपुट
   `shellOutput` सक्रिय हुँदा तिनीसम्म कहिल्यै पुग्दैन।
4. **`json`**: वैकल्पिक खाली ठाउँपछि `{` वा `[` बाट सुरु हुने, पार्स हुन सक्ने र 2,000 क्यारेक्टरभन्दा लामो JSON पेलोडलाई
   सङ्क्षेप गरिन्छ: 7 भन्दा बढी आइटम भएको एरेले आफ्ना सुरुका 5 र अन्तिम 2 आइटम तथा कुल सङ्ख्या राख्छ,
   र एउटा अब्जेक्टले आफ्ना सुरुका 20 कुञ्जी राख्छ, जहाँ प्रत्येक नेस्टेड अब्जेक्ट वा एरे मानलाई
   `{…N keys}` प्लेसहोल्डरले प्रतिस्थापन गरिन्छ
   (एरेका लागि N त्यसको लम्बाइ हो) र सुरुका 20 पछि हटाइएका कुञ्जीहरूको सङ्ख्या जनाउने
   `_remaining_<N>_keys` मार्कर राखिन्छ। स्केलर मानहरू पूर्ण रूपमा प्रतिलिपि गरिन्छन्, त्यसैले नेस्टेड मान नभएको
   20 वा कम कुञ्जी भएको अब्जेक्टलाई केवल पुनः इन्डेन्ट गरिन्छ — मिनिफाइ गरिएको अब्जेक्टमा क्यारेक्टर थपिन्छन्
   र त्यो अपरिवर्तित रहन्छ।
5. **`errorMessage`**: जुनसुकै ठाउँमा र अक्षरको जुनसुकै केसमा `error:`,
   `error ` (`no error found` मा जस्तै शब्दपछि खाली ठाउँ), `[error]`,
   `exception:`, `exception `, `[exception]` वा `traceback` समावेश भएको आउटपुटले आफ्नो पहिलो पङ्क्ति,
   त्यसपछिका 10 पङ्क्ति र अन्तिम 3 पङ्क्ति राख्छ, र तिनीहरूबीचका पङ्क्तिहरूको ठाउँमा
   `… [N frames elided] …` मार्कर राख्छ। पहिलो पङ्क्तिपछि 13 भन्दा बढी पङ्क्ति हुँदा मात्र
   मार्कर देखिन्छ, त्यसैले 14 वा कम पङ्क्तिको त्रुटि आउटपुट छोट्याइँदैन (12 वा 13 पङ्क्ति हुँदा
   अन्तिम 3 ले पहिले नै राखिएका पङ्क्तिहरू दोहोर्याउँछन्)।

एउटा रणनीति मिलेपछि, त्यसले केही पनि बचत नगरे पनि, पछिल्ला रणनीतिहरू
प्रयास गरिँदैनन्। मिलेको रणनीतिले कुनै अनुमानित टोकन (लम्बाइ ÷ 4, माथिल्लो पूर्णाङ्कमा गोलाकार गरिएको) बचत नगर्दा —
उदाहरणका लागि 25 वा कम पङ्क्ति भएको कोड-जस्तो फाइल, वा 7 वा कम आइटम भएको 2,000 भन्दा बढी
क्यारेक्टरको JSON एरे — आक्रामक इन्जिनले मूल टुल परिणाम
राख्छ: दुवै कलर (`compressAggressive()` र `compressAnthropicToolResultBlock()`)
ले `saved` 0 वा कम हुँदा मूल सामग्री राख्छन्, जबकि `compressToolResult()` आफैँले अझै पनि
त्यो रणनीतिको आउटपुट फर्काउँछ। टुल-परिणाम चरण अन्तिम निर्णय होइन:
इन्जिनको फलब्याक सारांशकर्ताले अझै पनि 8,192 क्यारेक्टरभन्दा लामो `tool` वा `function` सन्देशलाई
छोट्याउन सक्छ (`maxTokensPerMessage`, 2,048, गुणा 4)।

#### कहिले प्रयोग गर्ने

टुल परिणाम कम्प्रेसन आक्रामक इन्जिनको चरण 1 हो (`compressAggressive()` in
`open-sse/services/compression/aggressive.ts`), त्यसैले यो Aggressive मोडमा र स्ट्याक गरिएको पाइपलाइनको
`aggressive` चरणमा चल्छ। यसले OpenAI-आकारका `tool` र `function`
सन्देशहरू तथा Anthropic का `tool_result` ब्लकभित्रको पाठ कम्प्रेस गर्छ। प्रत्येक रणनीतिको
`aggressive.toolStrategies` अन्तर्गत आफ्नै स्विच हुन्छ, र सबै पूर्वनिर्धारित रूपमा सक्रिय हुन्छन्। ड्यासबोर्डमा,
कम्प्रेसन सक्रिय हुँदा र पूर्वनिर्धारित मोड Aggressive हुँदा स्विचहरू Caveman पृष्ठको **Advanced** दृश्यमा हुन्छन्।

### स्ट्याक गरिएको पाइपलाइन

स्ट्याक गरिएको मोडले **धेरै इन्जिनहरू क्रमशः** चलाउँछ — सामान्यतया पहिले RTK
(टुल आउटपुटमा 60-90% बचत), त्यसपछि बाँकी पाठमा Caveman (~46% इनपुट
बचत)। संयुक्त रूपमा, त्यो **78-95% योग्य दायरा** हो (माथिको Upstream Savings Math हेर्नुहोस्):
`1 - (1 - 0.60..0.90) × (1 - 0.46)` को औसत ≈89% हुन्छ।

#### यसले कसरी काम गर्छ

```
इनपुट (1000 टोकन)
  → RTK (कमाण्ड-सचेत फिल्टर) → 200 टोकन
    → Caveman (अनावश्यक सामग्री हटाउने) → 108 टोकन
  → आउटपुट (108 टोकन, ~89% बचत)
```

#### कहिले प्रयोग गर्ने

स्ट्याक गरिएको मोड निम्नका लागि प्रयोग गर्नुहोस्:

- धेरै टुल प्रयोग हुने कार्यप्रवाहहरू (एजेन्टिक कोडिङ, अनुसन्धान)
- लागत-संवेदनशील ब्याच प्रशोधन
- तपाईंलाई अधिकतम टोकन बचत आवश्यक हुँदा

स्ट्याक गरिएका पाइपलाइनहरू विश्वव्यापी `stackedPipeline` कम्प्रेसन
सेटिङमार्फत, वा राउटिङ कम्बोमा तोकिएको नामयुक्त कम्प्रेसन कम्बोमार्फत कन्फिगर गरिन्छ (माथिको
Per-Combo Override हेर्नुहोस्) — auto-combo `modePack` मार्फत होइन (त्यो फिल्डले
auto-combo मोडेल चयनको भार मात्र पुनःसमायोजन गर्छ, र `stacked` मान्य प्याक नाम होइन)।

## कम्प्रेसन कम्बो ओभरराइडहरू

फरक प्रयोग अवस्थाहरूका लागि व्यवहारलाई सूक्ष्म रूपमा समायोजन गर्न तपाईंले विश्वव्यापी कम्प्रेसन मोडलाई **प्रत्येक कम्बोअनुसार** ओभरराइड गर्न सक्नुहुन्छ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

यो निम्नका लागि उपयोगी छ:

- **कोडिङ कम्बोहरू**: लामा सत्रहरूका लागि `aggressive` मोड प्रयोग गर्नुहोस्
- **द्रुत प्रश्नोत्तर कम्बोहरू**: छिटो प्रतिक्रियाहरूका लागि `lite` मोड प्रयोग गर्नुहोस्
- **धेरै उपकरण प्रयोग हुने कम्बोहरू**: अधिकतम बचतका लागि `stacked` मोड प्रयोग गर्नुहोस्
- **उत्पादन कम्बोहरू**: क्यासिङ प्रदायकहरूका लागि ओभरराइड बन्द राख्नुहोस् — सधैँ सक्रिय रहने
  क्यास-सचेत समायोजनले `aggressive`/`ultra` लाई स्वतः `standard` मा डाउनग्रेड गर्छ
  (छनोट गर्न मिल्ने `cache-aware` मोड छैन)
