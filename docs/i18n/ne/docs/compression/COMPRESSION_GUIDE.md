> योग्य सन्दर्भमा स्वचालित रूपमा 15-95% बचत गर्नुहोस्। द्रुत अवलोकनका लागि [README को सङ्कुचन खण्ड](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) हेर्नुहोस्।

## अवलोकन

OmniRoute ले मोड्युलर प्रम्प्ट सङ्कुचन पाइपलाइन कार्यान्वयन गर्छ, जुन अनुरोधहरू अपस्ट्रिम प्रदायकहरूमा पुग्नुअघि नै **सक्रिय रूपमा** चल्छ। यसको अर्थ तपाईंको टोकन बचत पारदर्शी रूपमा हुन्छ — तपाईंको कार्यप्रवाहमा कुनै परिवर्तन आवश्यक पर्दैन।

```
क्लाइन्ट अनुरोध
  → सङ्कुचन रणनीति चयनकर्ता
    → कम्बो ओभरराइड? → कम्बो सेटिङ प्रयोग गर्ने
    → स्वतः-ट्रिगर थ्रेसहोल्ड? → स्वतः मोड प्रयोग गर्ने
    → पूर्वनिर्धारित मोड? → ग्लोबल सेटिङ प्रयोग गर्ने
    → बन्द? → सङ्कुचन छोड्ने
  → चयन गरिएको सङ्कुचन मोड
    → बन्द: कुनै सङ्कुचन छैन
    → हल्का: सुरक्षित ह्वाइटस्पेस/ढाँचा सफाइ (~15%)
    → मानक: गुफामानव-जस्तो बोलीका अनावश्यक शब्द हटाउने (~30%)
    → आक्रामक: इतिहासको पुरानोपन व्यवस्थापन + सारांशकरण (~50%)
    → अल्ट्रा: ह्युरिस्टिक छाँटकाँट + कोड-ब्लक पातलो बनाउने (~75%)
    → RTK: कमाण्ड-सचेत टर्मिनल/उपकरण-आउटपुट फिल्टरिङ (60-90% अपस्ट्रिम दायरा)
    → स्ट्याक्ड: क्रमबद्ध बहु-इन्जिन पाइपलाइन, सामान्यतया पहिले RTK अनि Caveman (78-95% योग्य दायरा)
  → सङ्कुचित अनुरोध → प्रदायक
```

## सङ्कुचन मोडहरू

### बन्द

कुनै सङ्कुचन लागू हुँदैन। सबै सन्देशहरू अपरिवर्तित रूपमा पठाइन्छन्।

### हल्का मोड (~15% बचत, <1ms विलम्बता)

सबैभन्दा सुरक्षित मोड — अर्थमा कुनै परिवर्तन नगरी, ढाँचा मात्र सफा गर्छ:

| प्रविधि                  | विवरण                                               |
| ------------------------ | --------------------------------------------------- |
| `collapseWhitespace`     | लगातारका खाली पङ्क्ति र अन्त्यका स्पेसहरू मर्ज गर्छ |
| `dedupSystemPrompt`      | दोहोरिएका सिस्टम सन्देशहरू हटाउँछ                   |
| `compressToolResults`    | विस्तृत उपकरण/फङ्क्सन आउटपुटहरू सङ्कुचित गर्छ       |
| `removeRedundantContent` | दोहोरिएका निर्देशनहरू हटाउँछ                        |
| `replaceImageUrls`       | base64 छवि डेटा URI हरू छोट्याउँछ                   |

**यसका लागि उत्तम:** सधैँ सक्रिय रहने प्रयोग, सुरक्षा-महत्त्वपूर्ण कार्यप्रवाहहरू।

### मानक मोड (~30% बचत)

[Caveman](https://github.com/JuliusBrussee/caveman) बाट प्रेरित — अर्थ जोगाउँदै अनावश्यक शब्दहरू र अनावश्यक रूपमा लम्ब्याइएका वाक्यांशहरू हटाउँछ:

- अनावश्यक शब्दहरू ("कृपया", "मलाई लाग्छ", "मूलतः", "वास्तवमा") हटाउँछ
- अनावश्यक रूपमा लम्ब्याइएका वाक्यांशहरू सङ्क्षिप्त गर्छ ("गर्नका लागि" → "गर्न", "को परिणामस्वरूप" → "किनभने")
- विनम्रताका लागि प्रयोग गरिएका घुमाउरा अभिव्यक्तिहरू हटाउँछ ("के तपाईंलाई आपत्ति हुन्छ...", "यदि तपाईंले सम्भवतः गर्न सक्नुहुन्छ भने...")
- कोडिङ प्रम्प्टहरूका लागि अनुकूलित 30+ regex नियमहरू

**यसका लागि उत्तम:** दैनिक कोडिङ कार्यप्रवाहहरू, लागतप्रति सचेत टोलीहरू।

### आक्रामक मोड (~50% बचत)

लामा सत्रहरूका लागि स्मार्ट इतिहास व्यवस्थापन:

- **सन्देशको पुरानोपन व्यवस्थापन** — पुराना सन्देशहरू क्रमिक रूपमा अझ बढी सङ्कुचित हुन्छन्
- **उपकरण परिणाम सारांशकरण** — लामा उपकरण आउटपुटहरूलाई सारांशले प्रतिस्थापन गर्छ
- **संरचनात्मक अखण्डता सुरक्षा** — `tool_use` + `tool_result` जोडीहरू सुसङ्गत रहेको सुनिश्चित गर्छ
- **कन्टेक्स्ट विन्डो सचेतना** — प्रत्येक मोडेलको टोकन सीमा पालना गर्छ

**यसका लागि उत्तम:** विस्तारित डिबगिङ सत्रहरू, ठूला कोडबेसहरू।

### अल्ट्रा मोड (~75% बचत)

टोकन-महत्त्वपूर्ण परिदृश्यहरूका लागि अधिकतम सङ्कुचन:

- **ह्युरिस्टिक छाँटकाँट** — सान्दर्भिकता थ्रेसहोल्डभन्दा तलका सन्देशहरू हटाउँछ
- **कोड ब्लक पातलो बनाउने** — दोहोरिने कोड उदाहरणहरू सङ्कुचित गर्छ
- **बाइनरी खोजद्वारा काटछाँट** — कन्टेक्स्ट विन्डोका लागि उपयुक्त काट्ने बिन्दु पत्ता लगाउँछ
- आक्रामक मोडका सबै सुविधाहरू समावेश छन्

**यसका लागि उत्तम:** तपाईं बारम्बार कन्टेक्स्ट सीमामा पुगिरहनुभएको अवस्थामा।

### RTK मोड (60-90% अपस्ट्रिम दायरा)

RTK मोड कोडिङ-एजेन्ट सत्रहरूमा देखा पर्ने विस्तृत उपकरण आउटपुटहरूका लागि अनुकूलित छ:

- `git status`, `git diff`, `git log`, परीक्षण रनरहरू,
  TypeScript/Vite/Webpack बिल्डहरू, ESLint/Biome/Prettier, npm अडिट/स्थापनाहरू, Docker लगहरू, पूर्वाधार
  आउटपुट, र सामान्य शेल आउटपुटजस्ता कमाण्ड/आउटपुट वर्गहरू पहिचान गर्छ
- `open-sse/services/compression/engines/rtk/filters/` बाट JSON फिल्टर प्याकहरू लागू गर्छ
- इनलाइन-परीक्षण प्रमाणीकरण र परियोजना फाइलहरूका लागि विश्वास-गेटिङसहित परियोजना वा ग्लोबल `filters.toml` फाइलहरूबाट RTK TOML schema v1 फिल्टरहरू आयात गर्छ
- इनलाइन प्रमाणीकरण नमुनाहरूसहित 49 वटा अन्तर्निर्मित फिल्टरहरू उपलब्ध गराउँछ
- ANSI नियन्त्रण अनुक्रमहरू, प्रगति पट्टीहरू, दोहोरिएका पङ्क्तिहरू, र कार्ययोग्य नभएका अनावश्यक सामग्री हटाउँछ
- विफलताहरू, त्रुटिहरू, चेतावनीहरू, परिवर्तन गरिएका फाइलहरू, सारांशहरू, र लामो आउटपुटको अन्तिम भाग सुरक्षित राख्छ
- विश्वास-गेट गरिएका परियोजना फिल्टरहरू, ग्लोबल फिल्टरहरू, र वैकल्पिक रूपमा संवेदनशील विवरण हटाइएको कच्चा-आउटपुट पुनर्प्राप्ति समर्थन गर्छ

**यसका लागि उत्तम:** शेल, बिल्ड, परीक्षण, git, grep, र फाइल-आउटपुट ट्रान्सक्रिप्टहरू भएका एजेन्ट सत्रहरू।

### स्ट्याक्ड मोड (78-95% योग्य दायरा)

स्ट्याक्ड मोडले निर्धार्य क्रममा धेरै सङ्कुचन इन्जिनहरू चलाउँछ। पूर्वनिर्धारित पाइपलाइन यस्तो छ:

```txt
RTK -> Caveman
```

त्यो क्रमले पहिले टर्मिनल/उपकरण आउटपुटलाई सङ्क्षिप्त राख्छ, त्यसपछि
बाँकी प्राकृतिक-भाषा प्रम्प्टमा Caveman को अर्थगत सङ्क्षेपीकरण लागू गर्छ। स्ट्याक्ड पाइपलाइनहरूलाई ग्लोबल रूपमा वा राउटिङ कम्बोहरूमा तोकिएका
सङ्कुचन कम्बोहरूमार्फत कन्फिगर गर्न सकिन्छ।

**यसका लागि उत्तम:** ठूला उपकरण लगहरूका साथै मानवीय निर्देशन वा सहायकका सारांशहरू भएको मिश्रित सन्दर्भ।

## अपस्ट्रिम बचतको गणना

OmniRoute ले दुई स्रोतबाट प्राप्त कम्प्रेसन बचतलाई अभिलेखीकरण गर्छ: अपस्ट्रिम परियोजनाका बेन्चमार्कहरू र
OmniRoute को आफ्नै इन्जिन संयोजन।

| स्रोत   | यहाँ प्रयोग गरिएको अपस्ट्रिम README को आँकडा                                                              |
| ------- | --------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` कम आउटपुट टोकनहरू, `65%` बेन्चमार्क औसत आउटपुट बचत, `22-87%` दायरा, र `~46%` इनपुट कम्प्रेसन उपकरण |
| RTK     | `60-90%` कमाण्ड-आउटपुट बचत; नमुना सत्रमा `~118,000 -> ~23,900` टोकन, वा `79.7%` बचत (`~80%`)              |

ओभरल्याप हुने उपकरण/कन्टेक्स्ट पेलोडहरूका लागि, पूर्वनिर्धारित OmniRoute कम्बोले इन्जिनहरूलाई यसरी स्ट्याक गर्छ:

```txt
RTK -> Caveman
```

संयुक्त बचत गुणात्मक हुन्छ, योगात्मक होइन:

```txt
संयुक्त = 1 - (1 - RTK बचत) * (1 - Caveman इनपुट बचत)
औसत   = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
दायरा  = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

त्यो `78-95%` आँकडा दुवै RTK र Caveman ले एउटै इनपुट/कन्टेक्स्ट पेलोड घटाउन सक्दा लागू हुन्छ।
Caveman प्रतिक्रिया आउटपुट मोड अलग हुन्छ: सक्षम पारिएको अवस्थामा, Caveman कै आफ्नै आउटपुट बचत (`65%`
औसत, `~75%` मुख्य आँकडा, `22-87%` दायरा) प्रयोग गर्नुहोस्। कुल बिलिङ बचत तपाईंको प्रम्प्ट/आउटपुट मिश्रणमा निर्भर हुन्छ।

### वास्तवमा "योग्य" भन्नाले के बुझिन्छ

15-95% को मुख्य दायरा वास्तविक हो, तर यो **दोहोरो वा अनावश्यक रूपमा विस्तृत** सामग्रीमा मात्र लागू हुन्छ — दोहोरिएका
त्रुटि लाइनहरू, एउटै चेतावनी बारम्बार देखाउने बिल्ड लग, अत्यधिक ठूलो `grep`/फाइल-रिड डम्प। यसको अर्थ
हरेक अनुरोधले त्यति नै बचत गर्छ भन्ने **होइन**।

प्रयोगात्मक रूपमा प्रमाणित (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300 वटा उस्तै
त्रुटि लाइन समावेश भएको Anthropic-आकारको `tool_result` ब्लकमाथि चलाइएको `stacked` (RTK + Caveman)
रनले **95.93% टोकन बचत / 96.26% क्यारेक्टर बचत** हासिल गर्यो — जुन विज्ञापन गरिएको
दायराभित्र स्पष्ट रूपमा पर्छ। तर सामान्य, नदोहोरिएको उपकरण आउटपुट (सफा `grep` मिलान सूची,
छोटो फाइल रिड, सामान्य संवादात्मक पाठ) माथि चलाइएको उही पाइपलाइनले सही रूपमा **लगभग-शून्य बचत** दिन्छ, किनभने
हटाउनुपर्ने कुनै दोहोरिएको सामग्री हुँदैन र `validateCompression()` (`validation.ts`) ले कोड ब्लकहरू, URLs, शीर्षकहरू, संस्करणहरू, वा सबै-अक्षर-ठूला स्थिर पहिचानकर्ताहरू हटाउने वा परिवर्तन गर्ने
पुनर्लेखन पठाउन अस्वीकार गर्छ।

यो अपेक्षित, सुरक्षित व्यवहार हो, बग होइन: प्रायः सफा फाइलहरू पढ्ने/grep गर्ने कोडिङ सत्रले
कम्प्रेसन पूर्ण रूपमा सक्षम हुँदा पनि सामान्य कुल बचत देख्नेछ, जबकि असफल भइरहने
लुप वा अत्यधिक आउटपुट दिने लिन्टर सामना गर्ने सत्रले त्यस्तो ट्राफिकमा पूर्ण 78-95% दायरा देख्नेछ। कम्प्रेसन गलत कन्फिगर गरिएको प्रमाणका रूपमा कुनै एक सत्रको
न्यून समग्र बचत प्रतिशत प्रयोग नगर्नुहोस् — पहिले अन्तर्निहित उपकरण आउटपुट वास्तवमै दोहोरिएको थियो कि थिएन जाँच गर्नुहोस्।

## कन्फिगरेसन

### ड्यासबोर्ड

`ड्यासबोर्ड → सन्दर्भ र क्यास` मा जानुहोस्:

- **केभम्यान** — मोड चयन, भाषा प्याक, पूर्वावलोकन, र विश्वव्यापी पूर्वनिर्धारित
- **RTK** — कमाण्ड-फिल्टर पूर्वावलोकन, RTK सुरक्षा सेटिङहरू, र फिल्टर क्याटलग
- **कम्प्रेसन कम्बोज** — रुटिङ कम्बोजमा तोकिएको नाम दिइएको इन्जिन पाइपलाइनहरू
- **स्वत: ट्रिगर थ्रेसहोल्ड** — टोकन गणना थ्रेसहोल्ड भन्दा बढी हुँदा स्वचालित रूपमा कम्प्रेसन संलग्न गर्नुहोस्

### प्रति-कम्बो ओभरराइड

`ड्यासबोर्ड → सन्दर्भ र क्यास → कम्प्रेसन कम्बोज` मा, रुटिङ कम्बोमा कम्प्रेसन कम्बो असाइन गर्नुहोस्:

```txt
कम्बो: "free-tier-fallback"
  कम्प्रेसन कम्बो: "coding-agent-stack"
  पाइपलाइन: RTK -> केभम्यान
  लक्ष्यहरू:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

यसले तपाईंलाई सशुल्क सदस्यताहरूमा लाइट मोड राख्दै निःशुल्क/कोडिङ प्रदायकहरूमा स्ट्याक्ड कम्प्रेसन प्रयोग गर्न दिन्छ।

यो "प्रति-कम्बो ओभरराइड" असाइनमेन्ट **रुटिङ-कम्बो कम्प्रेसन मोड** ओभरराइड (पूर्वनिर्धारित/बन्द/लाइट/मानक/आक्रामक/अल्ट्रा) भन्दा फरक नियन्त्रण हो — त्यो ओभरराइडले नाम दिइएको कम्प्रेसन-कम्बो पाइपलाइन चयन गर्दैन; यसले `resolveCompressionPlan` द्वारा परामर्श गरिएको `compressionMode` फिल्ड मात्र सेट गर्दछ। यसलाई कम्बो कार्ड (`ड्यासबोर्ड → कम्बोज`) मा वा, #6760 देखि, `ड्यासबोर्ड → सन्दर्भ र क्यास → कम्प्रेसन कम्बोज` मा "रुटिङमा असाइन गर्नुहोस्" सूचीमा प्रति रुटिङ कम्बो, माथि दस्तावेज गरिएको पाइपलाइन-असाइनमेन्ट चेकबक्सको ठीक छेउमा सेट गर्न सकिन्छ। दुबै सतहहरू एउटै `PUT /api/combos/{id}` एन्डपोइन्ट मार्फत रहन्छन्।

### प्रति-अनुरोध ओभरराइड

एकल अनुरोधको लागि कम्प्रेसन योजना ओभरराइड गर्न `x-omniroute-compression` अनुरोध हेडर पठाउनुहोस्। यसको उच्चतम प्राथमिकता छ — यसले रुटिङ-कम्बो ओभरराइड, सक्रिय प्रोफाइल, स्वत: ट्रिगर, र प्यानल पूर्वनिर्धारितलाई हराउँछ। अज्ञात मानहरू बेवास्ता गरिन्छ (अनुरोध कहिल्यै अस्वीकृत हुँदैन) र विश्वव्यापी मास्टर स्विचले अझै पनि सबै कुरा नियन्त्रण गर्दछ: जब कम्प्रेसन विश्वव्यापी रूपमा बन्द हुन्छ, हेडरले यसलाई अन गर्न सक्दैन। मानहरू:

| मान           | प्रभाव                                                                                                                |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| `off`         | यस अनुरोधको लागि कुनै कम्प्रेसन छैन।                                                                                  |
| `default`     | प्यानल-व्युत्पन्न पूर्वनिर्धारित प्रोफाइल (सक्रिय प्रोफाइललाई बेवास्ता गर्दछ)। नोक्सानपूर्ण इन्जिनहरू बन्द राखिन्छन्। |
| `safe`        | हेडर छोड्नु जस्तै: डुप्लिकेसन र खाली ठाउँ फोल्डिङ मात्र।                                                              |
| `allow-lossy` | यस अनुरोधको अपरेटर योजना राख्नुहोस्, सारांश, सान्दर्भिकता फिल्टर, र शैली पुनर्लेखन सहित।                              |
| `engine:<id>` | सक्षम हुँदा एकल इन्जिन, जस्तै `engine:rtk`। यो त्यो इन्जिनको लागि प्रति-अनुरोध अप्ट-इन हो।                            |
| `<combo>`     | नामद्वारा (केस-संवेदनशील) पहिले, त्यसपछि id द्वारा मिलाइएको नाम दिइएको कम्बो।                                         |

`allow-lossy`, `engine:<id>`, वा नाम दिइएको कम्बो बिना, नोक्सानपूर्ण इन्जिनहरू लागू हुँदैनन्। कम्प्रेसन अन हुँदा अनुरोधले अझै पनि सत्र डुप्लिकेसन र खाली ठाउँ फोल्डिङ पाउँछ।

लागू गरिएको योजना `X-OmniRoute-Compression: <mode>; source=<source>` प्रतिक्रिया हेडरमा प्रतिध्वनित हुन्छ, जहाँ `<source>` `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, वा `off` मध्ये एक हो।

## आभार

मानक मोडका कम्प्रेसन नियमहरू **[JuliusBrussee](https://github.com/JuliusBrussee)** को **[Caveman](https://github.com/JuliusBrussee/caveman)** (⭐ 51K+) बाट प्रेरित छन् — भाइरल "धेरै टोकन किन प्रयोग गर्ने, जब थोरै टोकनले काम गर्छ" परियोजना। Caveman ले `~75%` कम आउटपुट टोकन, बेन्चमार्कमा औसत `65%` आउटपुट बचत, `22-87%` को आउटपुट दायरा र `~46%` इनपुट-कम्प्रेसन टुल रिपोर्ट गर्छ।

RTK मोड **[RTK AI](https://github.com/rtk-ai)** को **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** बाट प्रेरित छ — टर्मिनल, बिल्ड, टेस्ट, git र टुल-आउटपुट फिल्टरिङका लागि उच्च-प्रदर्शन कमान्ड-आउटपुट कम्प्रेसन परियोजना। RTK ले `60-90%` बचत रिपोर्ट गर्छ, र यसको README नमुना सत्रले `~80%` बचत भएको देखाउँछ।

## उन्नत सङ्कुचन प्रणालीहरू

७ मानक मोडहरूभन्दा बाहिर, OmniRoute मा धेरै उन्नत सङ्कुचन प्रणालीहरू समावेश छन् जुन सन्दर्भको आधारमा स्वचालित रूपमा काम गर्छन्।

### क्यास-सचेत सङ्कुचन

केही प्रदायकहरू (जस्तै Anthropic prompt caching सहित) **prompt caching** लाई समर्थन गर्छन्, जसले तिनीहरूलाई लागत र विलम्बता कम गर्न prompt का केही भागहरू क्यास गर्न दिन्छ। जब क्यासिङ सक्षम हुन्छ, आक्रामक सङ्कुचनले वास्तवमा कार्यसम्पादनलाई **हानि** पुर्याउन सक्छ किनभने यसले क्यास गरिएका टोकनहरू परिवर्तन गर्छ, जसले क्यासलाई अमान्य बनाउँछ।

`cachingAware.ts` मोड्युलले **क्यासिङ सन्दर्भ पत्ता लगाएर** र तदनुसार **सङ्कुचन रणनीति समायोजन गरेर** यो समस्या समाधान गर्छ।

#### यसले कसरी काम गर्छ

१. **क्यासिङ सन्दर्भ पत्ता लगाउनुहोस्** — `cache_control` मार्करहरूको लागि अनुरोध बडी स्क्यान गर्छ
२. **क्यासिङ प्रदायकहरू पहिचान गर्नुहोस्** — लक्षित प्रदायकले क्यासिङलाई समर्थन गर्छ कि गर्दैन जाँच गर्छ
३. **रणनीति समायोजन गर्नुहोस्** — क्यासिङ प्रदायकहरूको लागि `aggressive`/`ultra` लाई `standard` मा डाउनग्रेड गर्छ
४. **प्रणाली prompt छोड्नुहोस्** — प्रणाली prompt हरू सामान्यतया क्यास गरिएका हुन्छन्, त्यसैले तिनीहरूलाई सङ्कुचन नगर्नुहोस्
५. **निर्धारक रूपान्तरणहरू प्रयोग गर्नुहोस्** — केवल सुसंगत आउटपुट उत्पादन गर्ने रूपान्तरणहरू प्रयोग गर्नुहोस्

#### कोड उदाहरण

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Cache marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### कहिले प्रयोग गर्ने

क्यास-सचेत सङ्कुचन **सधैं अन** हुन्छ — कुनै कन्फिगरेसन आवश्यक पर्दैन। यो तब मात्र सक्रिय हुन्छ जब:

- अनुरोधमा `cache_control` मार्करहरू छन्
- लक्षित प्रदायकले prompt caching लाई समर्थन गर्छ (Anthropic, OpenAI, आदि)

### प्रगतिशील बुढ्यौली

लामो कुराकानीहरूमा धेरै सन्देश पालोहरू जम्मा हुन्छन्, तर पुराना पालोहरू कम सान्दर्भिक हुन्छन्। `progressiveAging.ts` मोड्युलले **सन्देशहरूलाई पालो दूरी अनुसार घटाउँछ**:

- **हालका पालोहरू (०-३)**: जस्ताको तस्तै राखिएको (पूर्ण विवरण)
- **मध्यम पालोहरू (४-८)**: हल्का सङ्कुचन (खाली ठाउँ, ढाँचा सफा गर्ने)
- **पुराना पालोहरू (९+)**: केभम्यान सङ्कुचन (फिलर हटाउने, सारांश)
- **धेरै पुराना पालोहरू (२०+)**: धेरै सारांशित वा हटाइएको

#### कोड उदाहरण

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... 50 more turns ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // First 3 turns: verbatim
  light: 8, // Turns 4-8: lite compression
  moderate: 20, // Turns 9-20: caveman compression
  // Turns 21+: heavy summarization
});

// saved = number of tokens saved
```

#### कहिले प्रयोग गर्ने

प्रगतिशील बुढ्यौली `aggressive` र `ultra` मोडहरूको लागि **सधैं अन** हुन्छ। यो विशेष गरी निम्नका लागि प्रभावकारी हुन्छ:

- लामो समयसम्म चल्ने कोडिङ सत्रहरू
- धेरै दिनका कुराकानीहरू
- धेरै उपकरण कलहरू सहितको एजेन्टिक कार्यप्रवाहहरू

### केभम्यान आउटपुट मोड

`outputMode.ts` मोड्युलले **प्रणाली prompt निर्देशनहरू** इन्जेक्ट गर्छ जसले मोडेललाई आफैंले सङ्कुचित, संक्षिप्त आउटपुट (एक "केभम्यान" शैली) उत्पादन गर्न लगाउँछ।

#### यसले कसरी काम गर्छ

इनपुटलाई सङ्कुचन गर्नुको सट्टा, यो मोडले प्रणाली prompt थप्छ जस्तै:

> "न्यूनतम शब्दहरूमा जवाफ दिनुहोस्। शिष्टाचार छोड्नुहोस्। छोटो वाक्यहरू प्रयोग गर्नुहोस्।"

यो विशेष गरी निम्नका लागि राम्रोसँग काम गर्छ:

- कोड जेनेरेसन (संक्षिप्त आउटपुट = कम टोकनहरू)
- द्रुत Q&A (विस्तृत व्याख्याहरूको आवश्यकता पर्दैन)
- ब्याच प्रशोधन (अधिकतम थ्रुपुट)

#### कहिले प्रयोग गर्ने

केभम्यान आउटपुट मोड **अप-इन** हो — यसलाई कम्बो कन्फिग मार्फत सेट गर्नुहोस्:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "outputMode": "caveman"
    }
  }
}
```

### आउटपुट शैलीहरू (क्याटलग)

माथिको केभम्यान आउटपुट मोड **लेगेसी एकल-शैली मार्ग** हो। चरण ४ ले यसलाई कम्पोजेबल आउटपुट शैलीहरूको क्याटलगमा सामान्यीकरण गर्यो: `open-sse/services/compression/outputStyles/catalog.ts` मा `OUTPUT_STYLE_CATALOG`। प्रत्येक शैली एक प्रणाली-prompt निर्देशन हो जसले मोडेललाई आफैंले सस्तो आउटपुट उत्पादन गर्न लगाउँछ; शैलीहरू सँगै सक्षम गर्न सकिन्छ र क्याटलग क्रममा इन्जेक्ट गरिन्छ।

| शैली                      | `id`          | यसले के गर्छ                                                                                                                                                                                                    | निर्देशन भाषाहरू                                                            |
| :------------------------ | :------------ | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------- |
| संक्षिप्त गद्य            | `terse-prose` | फिलर/लेख/हेजिङ हटाउनुहोस्; प्राविधिक सार सटीक राख्नुहोस्। लिगेसी केभम्यान आउटपुट मोड (सन्दर्भित, पुन: टाइप नगरिएको) जस्तै पाठ।                                                                                  | en, pt-BR, es, de, fr, it, ru, zh, ja, id, vi                               |
| कम कोड                    | `less-code`   | YAGNI सीढी: सबैभन्दा सानो काम गर्ने परिवर्तन, कुनै अनावश्यक अमूर्तता छैन।                                                                                                                                       | en, pt-BR, es, de, fr, it, ru, zh, ja, id, vi                               |
| पोनीटेल (आलसी वरिष्ठ देव) | `ponytail`    | "सबैभन्दा राम्रो कोड कहिल्यै नलेखिएको कोड हो": पुन:लेख्नु भन्दा पुन:प्रयोग, लक्षण भन्दा मूल कारण, सबैभन्दा छोटो काम गर्ने भिन्नता।                                                                              | en, pt-BR, es, de, fr, it, ru, zh, ja, id, vi                               |
| मलाई ADHD छ (कार्य-पहिलो) | `i-have-adhd` | कार्य पहिले (गद्य अघि आदेश/पथ/स्निपेट), संख्याबद्ध सीमित चरणहरू, एउटा ठोस अर्को चरण, कुनै प्रस्तावना/पुनरावलोकन/समापनकर्ता छैन। [ayghri/i-have-adhd](https://github.com/ayghri/i-have-adhd) (MIT) बाट अनुकूलित। | en, pt-BR, es, de, fr, it, ru, zh, ja, id, vi                               |

प्रत्येक शैलीमा तीन तीव्रता स्तरहरू छन् — `lite`, `full`, `ultra` — र प्रत्येक स्तर
साझा सीमा खण्डको साथ समाप्त हुन्छ, जसले कोड ब्लकहरू, फाइल पथहरू, आदेशहरू,
त्रुटि स्ट्रिङहरू, URL हरू र पहिचानकर्ताहरूलाई यथावत राख्छ।

#### इंजेक्शनले कसरी काम गर्छ

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ले
क्याटलग विरुद्ध चयनलाई समाधान गर्छ (अज्ञात आईडीहरू र स्थान-मिल्दो नभएका शैलीहरू
हटाइन्छ, कहिल्यै त्रुटि हुँदैन), क्याटलग क्रममा चयन गरिएका निर्देशनहरूलाई जोड्छ,
सीमा खण्ड **एक पटक** थप्छ, र एकल आइडम्पोटेन्सी मार्कर (`[OmniRoute Output Styles]`) पछाडि प्रणाली
प्रम्प्टमा परिणामलाई अगाडि-लोड गर्छ — पुन: लागू गर्नु नो-ओप हो। जब पत्ता लागेको अनुरोध भाषामा
अनुवाद हुन्छ, स्थानीयकृत निर्देशन अंग्रेजीको सट्टा इन्जेक्ट गरिन्छ।

#### कसरी सक्षम गर्ने

ड्यासबोर्डमा: **सन्दर्भ → सेटिङ्स → कम्प्रेसन** — अन/अफ टगल र स्तर चयनकर्ताको साथ प्रति शैली एक पङ्क्ति। प्रोग्रामेटिक रूपमा, कम्प्रेसन कन्फिगले चयनलाई यसरी कायम राख्छ:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

पछाडि-अनुकूलता: लिगेसी `outputMode: "caveman"` कम्बो सेटिङले अझै पनि काम गर्छ र
`terse-prose` मा म्याप गर्छ, प्रत्येक लिगेसी भाषामा पुरानो इंजेक्शनसँग बाइट-समान।

भाषा चयन: `languageConfig.enabled` अन हुँदा, `autoDetect` ले नवीनतम प्रयोगकर्ता सन्देशको
भाषा छान्छ (इनपुट इन्जिनहरू जस्तै डिटेक्टर); `autoDetect` बन्द गर्दा `defaultLanguage` पिन गर्छ।
बन्द → अंग्रेजी।

शैली × भाषा म्याट्रिक्स `tests/unit/compression/output-styles-i18n-matrix.test.ts` द्वारा पिन गरिएको छ:
नयाँ शैली कम्तिमा pt-BR अनुवाद (वा स्पष्ट ट्र्याक गरिएको अपवाद) बिना शिप गर्न सक्दैन, र
अवस्थित शैलीले चुपचाप स्थान गुमाउन सक्दैन। शैली थप्नको लागि, [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) हेर्नुहोस्।

### उपकरण परिणाम कम्प्रेसन

`toolResultCompressor.ts` मोड्युलले उपकरण परिणामहरू (फंक्शन कलहरू, एजेन्ट आउटपुटहरू, खोज परिणामहरू, आदि) को लागि **५ विशेष कम्प्रेसन रणनीतिहरू** प्रदान गर्दछ:

१. **खोज परिणाम कम्प्रेसन** — अनावश्यक परिणामहरू हटाउँछ, शीर्ष-N राख्छ
२. **फाइल पढ्ने कम्प्रेसन** — ठूला फाइलहरू काट्छ, हेडर/आयातहरू सुरक्षित गर्छ
३. **कोड कार्यान्वयन कम्प्रेसन** — आवश्यक stdout/stderr मात्र राख्छ
४. **डाटाबेस क्वेरी कम्प्रेसन** — पङ्क्तिहरू सीमित गर्छ, विस्तृत मेटाडेटा हटाउँछ
५. **API प्रतिक्रिया कम्प्रेसन** — शून्य फिल्डहरू हटाउँछ, एरेहरूलाई संकुचित गर्छ

#### कहिले प्रयोग गर्ने

उपकरण परिणाम कम्प्रेसन **सधैं अन** हुन्छ जब उपकरण कलहरू उपस्थित हुन्छन्। कुनै
कन्फिगरेसन आवश्यक छैन।

### स्ट्याक्ड पाइपलाइन

स्ट्याक्ड मोडले **धेरै इन्जिनहरूलाई क्रमबद्ध रूपमा** चलाउँछ — सामान्यतया पहिले RTK
(उपकरण आउटपुटमा ६०-९०% बचत), त्यसपछि केभम्यान (बाँकी पाठमा ३०% अतिरिक्त बचत)। यसले
**७८-९५% कुल बचत** प्राप्त गर्छ।

#### यसले कसरी काम गर्छ

```
इनपुट (१००० टोकन)
  → RTK (आदेश-सचेत फिल्टर) → २०० टोकन
    → केभम्यान (फिलर हटाउने) → १४० टोकन
  → आउटपुट (१४० टोकन, ८६% बचत)
```

#### कहिले प्रयोग गर्ने

स्ट्याक्ड मोड निम्नका लागि प्रयोग गर्नुहोस्:

- उपकरण-भारी कार्यप्रवाहहरू (एजेन्टिक कोडिङ, अनुसन्धान)
- लागत-संवेदनशील ब्याच प्रशोधन
- जब तपाईंलाई अधिकतम टोकन बचत चाहिन्छ

कम्बो मार्फत कन्फिगर गर्नुहोस्:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "modePack": "stacked"
    }
  }
}
```

## कम्प्रेसन कम्बो ओभरराइडहरू

फरक प्रयोग अवस्थाहरूका लागि व्यवहारलाई सूक्ष्म रूपमा समायोजन गर्न तपाईंले ग्लोबल कम्प्रेसन मोडलाई **प्रत्येक कम्बोअनुसार** ओभरराइड गर्न सक्नुहुन्छ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "auto": {
      "weights": { "taskFit": 0.5 },
      "modePack": "quality-first"
    }
  },
  "compressionOverride": {
    "mode": "aggressive",
    "stackedPipelines": ["rtk", "caveman"],
    "preserveToolDefinitions": true
  }
}
```

यो निम्नका लागि उपयोगी हुन्छ:

- **कोडिङ कम्बोहरू**: लामो सत्रहरूका लागि `aggressive` मोड प्रयोग गर्नुहोस्
- **द्रुत प्रश्नोत्तर कम्बोहरू**: छिटो प्रतिक्रियाहरूका लागि `lite` मोड प्रयोग गर्नुहोस्
- **धेरै टुल प्रयोग हुने कम्बोहरू**: अधिकतम बचतका लागि `stacked` मोड प्रयोग गर्नुहोस्
- **प्रोडक्सन कम्बोहरू**: क्यासिङ प्रदायकहरूका लागि `cache-aware` मोड प्रयोग गर्नुहोस्
