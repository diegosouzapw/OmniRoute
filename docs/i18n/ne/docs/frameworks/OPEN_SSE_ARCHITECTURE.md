> **TL;DR**: `open-sse/` OmniRoute मा हुने प्रत्येक LLM अनुरोधलाई सञ्चालन गर्ने मुख्य स्ट्रिमिङ इन्जिन हो। यसमा अनुरोध पाइपलाइन, एक्जिक्युटरहरू, सेवाहरू, MCP सर्भर र अनुवाद तह कार्यान्वयन गर्ने ~1,400 फाइलहरू छन्। यस गाइडले यी भागहरू कसरी एकसाथ काम गर्छन् भन्ने व्याख्या गर्छ।

**स्रोत:** `open-sse/` (वर्कस्पेस प्याकेज, ~1,440 गैर-परीक्षण `.ts` फाइलहरू)

## छुट्टै वर्कस्पेस प्याकेज किन?

`open-sse/` धेरै कारणले OmniRoute मोनोरेपोभित्रको **स्वतन्त्र वर्कस्पेस** हो:

1. **पुनः प्रयोगयोग्यता** — `open-sse` लाई npm मा `@omniroute/open-sse` का रूपमा प्रकाशित गरिन्छ, त्यसैले अन्य परियोजनाहरूले यसलाई स्वतन्त्र रूपमा प्रयोग गर्न सक्छन्
2. **स्पष्ट सीमाहरू** — स्ट्रिमिङ इन्जिनलाई OmniRoute-विशिष्ट UI/DB तहबाट अलग राखिएको छ
3. **कार्यसम्पादन** — इन्जिनमा कुनै Next.js निर्भरता छैन, जसले CLI/serverless सन्दर्भहरूमा छिटो कोल्ड स्टार्ट सम्भव बनाउँछ
4. **संस्करण व्यवस्थापन** — `open-sse` ले आफ्नै तालिकाअनुसार रिलिज गर्न सक्छ

```json
// package.json
"workspaces": ["open-sse"]
```

## अनुरोध पाइपलाइन

प्रत्येक LLM अनुरोध **५-चरणीय पाइपलाइन** हुँदै प्रवाहित हुन्छ:

```
                              ┌────────────────┐
   HTTP अनुरोध                 │  १. राउट        │   कम्बो समाधान, मोडेल चयन
   (Next.js रुट)               └──────┬─────────┘
                                      │
                                      ▼
                              ┌────────────────┐
                              │  २. अनुवाद      │   ढाँचा रूपान्तरण (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬─────────┘
                                      │
                                      ▼
                              ┌────────────────┐
                              │  ३. कार्यान्वयन │   प्रदायक एक्जिक्युटर, HTTP, पुनः प्रयास, ब्रेकर
                              └──────┬─────────┘
                                      │
                                      ▼
                              ┌────────────────┐
                              │  ४. स्ट्रिम      │   SSE रूपान्तरण, ब्याकप्रेसर
                              └──────┬─────────┘
                                      │
                                      ▼
                              ┌────────────────┐
                              │  ५. अभिलेख      │   प्रयोग ट्र्याकिङ, कल लग, त्रुटि वर्गीकरण
                              └──────┬─────────┘
                                      │
                                      ▼
                              HTTP प्रतिक्रिया (SSE वा JSON)
```

### चरण १: राउट (services/combo.ts)

**प्रवेश बिन्दु**: `services/combo.ts` मा रहेको `handleComboChat()`

अनुरोधलाई ठोस `(provider, model, account, credentials)` ट्युपलमा समाधान गर्छ:

- ID द्वारा कम्बो खोज्ने (वा `auto/*` मोडेलहरूका लागि भर्चुअल कम्बो बनाउने)
- राउटिङ रणनीति लागू गर्ने (प्राथमिकता, भारित, राउन्ड-रोबिन, आदि)
- अस्वस्थ प्रदायकहरूलाई हटाउने (सर्किट ब्रेकर)
- अर्को प्रयोगयोग्य लक्ष्य चयन गर्ने

`auto/*` मोडेलहरूका लागि यस चरणले निम्न कार्य पनि गर्छ:

- **१६-कारक स्कोरिङ** एल्गोरिदम (`services/autoCombo/`) चलाउँछ
- स्वास्थ्य, लागत, विलम्बता आदिका आधारमा `provider+model` जोडी चयन गर्छ

### चरण २: अनुवाद (translator/)

यदि स्रोत ढाँचा (जस्तै, OpenAI) लक्ष्य ढाँचा (जस्तै, Claude) भन्दा फरक छ भने अनुरोधलाई **अनुवाद** गरिन्छ:

- सिस्टम प्रम्प्ट → सिस्टम सन्देश
- उपकरण परिभाषाहरू → प्रदायक-विशिष्ट उपकरण ढाँचा
- रिजनिङ/थिङ्किङ प्यारामिटरहरू → प्रदायक-विशिष्ट समकक्षहरू
- सन्देश भूमिका सामान्यीकरण (गैर-OpenAI का लागि `developer` → `system`)

`translator/index.ts` ले निम्न उपलब्ध गराउँछ:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### चरण ३: कार्यान्वयन (executors/)

**प्रवेश बिन्दु**: `getExecutor(providerId).execute(request, options)`

सबै प्रदायकहरूले `getExecutor()` फ्याक्ट्री फलब्याकमार्फत `DefaultExecutor` (`executors/default.ts`) प्रयोग गर्छन्। एक्जिक्युटरले:

- अपस्ट्रिम URL बनाउँछ (`buildUrl()`)
- प्रदायक-विशिष्ट हेडरहरू थप्छ (`buildHeaders()`)
- अनुरोध बडी रूपान्तरण गर्छ (`transformRequest()`)
- पुनः प्रयास + एक्सपोनेन्सियल ब्याकअफसहित HTTP अनुरोध पठाउँछ
- आवश्यक भएमा प्रमाणीकरण रिफ्रेस सम्हाल्छ (OAuth प्रदायकहरू)

सबै एक्जिक्युटरहरूले `BaseExecutor` (`executors/base.ts`, 1170 LOC) विस्तार गर्छन्, जसले निम्न उपलब्ध गराउँछ:

- साझा पुनः प्रयास तर्क
- प्रोक्सी एकीकरण
- सर्किट ब्रेकर एकीकरण
- प्रयोग अभिलेखन हुकहरू

### चरण ४: स्ट्रिम (utils/stream.ts)

स्ट्रिमिङ प्रतिक्रियाहरूका लागि एक्जिक्युटरले **ReadableStream** फर्काउँछ। ह्यान्डलरले:

- SSE रूपान्तरण (`createSSETransformStreamWithLogger`) मार्फत पाइप गर्छ
- निष्क्रिय जडानहरू पत्ता लगाउन हार्टबिट पिङहरू लागू गर्छ
- क्लाइन्ट विच्छेदलाई सहज रूपमा सम्हाल्छ (`pipeWithDisconnect`)
- गैर-स्ट्रिमिङ क्लाइन्टहरूका लागि SSE → JSON रूपान्तरण गर्छ

गैर-स्ट्रिमिङ प्रतिक्रियाहरूका लागि एक्जिक्युटरले पार्स गरिएको JSON वस्तु फर्काउँछ, जसलाई कुनै परिवर्तन नगरी अगाडि पठाइन्छ।

### चरण ५: अभिलेख (services/usage.ts)

प्रतिक्रिया (सफल वा असफल) पछि, प्रयोग रेकर्ड गरिन्छ:

- प्रतिक्रियाबाट `prompt_tokens`, `completion_tokens`, `cached_tokens`
- मूल्य निर्धारण डेटाबाट गणना गरिएको `cost_usd`
- असफल भएमा `latency_ms`, `status`, `error_class`
- `usage_history` तालिकामा सुरक्षित गरिन्छ

कल लग आर्टिफ्याक्टहरू (सक्षम पारिएको भए) `${DATA_DIR}/call_logs/` मा लेखिन्छन्।

## मुख्य फाइलहरूको गहन विश्लेषण

### chatCore.ts (5977 लाइन)

**मुख्य अनुरोध ह्यान्डलर**। यसको आकार ठूलो भए पनि यसको संरचना स्पष्ट छ:

```ts
// chatCore.ts को छद्म-संरचना
export async function handleChat(request: NextRequest) {
  // 1. प्रमाणीकरण + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. अनुरोध बडीको प्रमाणीकरण
  const body = await parseRequestBody(request);

  // 3. ढाँचा पहिचान + रूपान्तरण
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. कम्बो राउटिङ
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // अर्को लक्ष्यमा जारी राख्नुहोस्
    }
  }

  // 5. आपत्कालीन फलब्याक
  return await emergencyFallback(body);
}
```

एउटै विशाल फङ्सन भए पनि, यसलाई 5-चरणीय पाइपलाइनसँग मेल खाने **टिप्पणी गरिएका खण्डहरूमा** व्यवस्थित गरिएको छ।

### combo.ts (4456 LOC)

कम्बोलाई क्रमबद्ध लक्ष्यहरूमा समाधान गर्ने **राउटिङ इन्जिन**।

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

यसले **19 वटा राउटिङ रणनीतिहरू** समर्थन गर्छ (`src/shared/constants/routingStrategies.ts` हेर्नुहोस्):

| रणनीति              | व्यवहार                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------- |
| `priority`          | पहिलो-लक्ष्यलाई प्राथमिकता दिइएको क्रमबद्ध सूची                                             |
| `weighted`          | प्रत्येक लक्ष्यको तौलअनुसार सम्भाव्यतामा आधारित                                             |
| `round-robin`       | लक्ष्यहरूलाई क्रमअनुसार चक्रीय रूपमा प्रयोग गर्ने                                           |
| `context-relay`     | लक्ष्यहरूबीच कन्टेक्स्ट हस्तान्तरण गर्ने                                                    |
| `fill-first`        | अर्कोमा जानुअघि कोटा पूरा गर्ने                                                             |
| `p2c`               | दुई विकल्पको शक्ति                                                                          |

### साझा ढाँचाहरू

प्रदायकहरूलाई `getExecutor(providerId)` मार्फत रिजल्भ गरिन्छ, जसले कन्फिगर गरिएको एक्जिक्युटर फर्काउँछ। OpenAI/Anthropic-संगत प्रदायकहरूले `DefaultExecutor` (`executors/default.ts`) प्रयोग गर्छन्। प्रदायक-विशिष्ट व्यवहार (आधार URL, प्रमाणीकरण हेडर, API संस्करण) `open-sse/config/providers/` मा कन्फिगर गरिन्छ, जबकि अनुरोध बडी रूपान्तरणहरू `open-sse/translator/` मा ह्यान्डल गरिन्छन्।

**अनुकूलन URL** प्रदायक कन्फिगरेसनमार्फत सेट गरिन्छ:

```ts
// open-sse/config/providers/ मा प्रदायक कन्फिगरेसन
export default {

}
````

};

## ट्रान्सफर्मरहरू

`open-sse/transformer/` ले **Chat Completions** र **Responses API** ढाँचाहरूबीच रूपान्तरण गर्छ।

### छुट्टै ट्रान्सफर्मर किन?

Responses API **अवस्था कायम रहने कुराकानीहरू** (`previous_response_id`) सहितको OpenAI को नयाँ ढाँचा हो। क्लाइन्टले Responses अनुरोध पठाउँदा, OmniRoute ले:

1. आन्तरिक रूपमा Responses → Chat Completions मा रूपान्तरण गर्छ
2. प्रदायकलाई पठाउँछ (Chat Completions समर्थन गर्ने कुनै पनि प्रदायक)
3. प्रतिक्रियालाई पुनः Responses ढाँचामा रूपान्तरण गर्छ
4. रूपान्तरित प्रतिक्रिया क्लाइन्टमा स्ट्रिम गर्छ

ट्रान्सफर्मर (`transformer/responsesTransformer.ts`) ले निम्न उपलब्ध गराउँछ:

```ts
createResponsesApiTransformStream(): TransformStream
```

यसले निम्न व्यवस्थापन गर्छ:

- `response.output_item.added` घटनाहरू
- `response.output_text.delta` घटनाहरू
- `response.completed` घटना
- टुल कल म्यापिङ (`function_call` ↔ `tool_calls`)

## नयाँ कम्पोनेन्ट थप्ने

### नयाँ सेवा थप्ने

1. केन्द्रित जिम्मेवारीसहित `open-sse/services/[serviceName].ts` सिर्जना गर्नुहोस्
2. मुख्य ह्यान्डलर फङ्सन र कुनै पनि कन्स्ट्यान्टहरू एक्सपोर्ट गर्नुहोस्
3. `tests/unit/services/[serviceName].test.mjs` मा युनिट परीक्षणहरू थप्नुहोस्
4. `handlers/chatCore.ts` को अनुरोध पाइपलाइनमा एकीकृत गर्नुहोस् (यदि राउटिङसँग सम्बन्धित छ भने)
5. सेवाले लक्ष्य छनोटमा प्रभाव पार्छ भने `combo.ts` मा राउटिङ तर्क अद्यावधिक गर्नुहोस्
6. यस फाइलमा दस्तावेजीकरण गर्नुहोस्

### नयाँ एक्जिक्युटर थप्ने

1. `BaseExecutor` विस्तार गर्ने `open-sse/executors/[provider].ts` सिर्जना गर्नुहोस्
