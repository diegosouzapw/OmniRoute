Traffic Inspector, OmniRoute मा अन्तर्निर्मित HTTPS ट्राफिक डिबगर हो — यो Charles Proxy / mitmweb / HTTP Toolkit-जस्तै उपकरण हो, जुन **LLM-सचेत** र **एजेन्ट-सचेत** छ। यो `/dashboard/tools/traffic-inspector` मा उपलब्ध छ र एकैपटक बढीमा ५ वटा क्याप्चर स्रोतबाट प्रत्यक्ष ट्राफिक प्राप्त गर्छ।

**ड्यासबोर्ड स्थान:** `/dashboard/tools/traffic-inspector`
**साइडबार समूह:** Tools (AgentBridge पछि)
**यो पनि हेर्नुहोस्:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge क्याप्चर मोड १ हो।

### एक अनुच्छेदमा वास्तुकला

`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) एउटा साझा इन-मेमोरी रिङ बफर हो (पूर्वनिर्धारित रूपमा 1000 प्रविष्टिहरू, `INSPECTOR_BUFFER_SIZE` मार्फत कन्फिगर गर्न मिल्ने)। सबै क्याप्चर स्रोतहरूले `push()` मार्फत यसमा लेख्छन्। बफरले `kindDetector.ts` प्रयोग गरी प्रत्येक प्रविष्टिलाई वर्गीकृत गर्छ (यो LLM अनुरोध हो कि होइन भनेर निर्धारण गर्छ), एउटा `contextKey` गणना गर्छ (सिस्टम प्रम्प्टको SHA-256 फिङ्गरप्रिन्ट), र `globalTrafficBuffer.subscribe()` मार्फत सबै WebSocket सदस्यहरूमा प्रसारण गर्छ। ड्यासबोर्डले `GET /api/tools/traffic-inspector/ws` मार्फत जडान गर्छ र जडान हुँदा एउटा स्न्यापसट प्राप्त गर्छ, त्यसपछि `new`/`update`/`clear` इभेन्टहरू प्राप्त गर्छ।

## §2 क्याप्चर मोडहरू

Traffic Inspector ले **एकैसाथ 5 वटा क्याप्चर स्रोतहरू** समर्थन गर्छ। प्रत्येकलाई स्वतन्त्र रूपमा टगल गर्न सकिन्छ। प्रत्येक `InterceptedRequest` (`src/mitm/inspector/types.ts`) को `source` फिल्ड `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"`, वा `"tproxy"` मध्ये एउटा हुन्छ।

### मोड 1 — AgentBridge (पूर्वनिर्धारित, सधैँ सक्रिय)

**स्रोत:** AgentBridge ह्यान्डलरहरू (`src/mitm/handlers/base.ts`)
**कार्यविधि:** `MitmHandlerBase` मा हुने प्रत्येक `intercept()` कलले फर्वार्ड गर्नुअघि `hookBufferStart()` र पूरा भएपछि `hookBufferUpdate()` कल गर्छ। कुनै अतिरिक्त कन्फिगरेसन आवश्यक पर्दैन — AgentBridge चल्नासाथ काम गर्छ।
**पहुँच:** AgentBridge मा कन्फिगर गरिएका 9 वटा IDE एजेन्टहरू
**टिप्पणी:** `InterceptedRequest` मा रहेको `source` फिल्ड = `"agent-bridge"`

### मोड 2 — अनुकूलन होस्टहरू (DNS रिडाइरेक्ट)

**स्रोत:** प्रयोगकर्ताद्वारा परिभाषित होस्ट सूची (`inspector_custom_hosts` तालिका)
**कार्यविधि:** UI मार्फत होस्ट थप्दा `/etc/hosts` मा `127.0.0.1 <host>` थपिन्छ (sudo आवश्यक हुन्छ)। विद्यमान AgentBridge MITM सर्भरले (पोर्ट 443) नयाँ होस्टका लागि गतिशील रूपमा SNI प्रमाणपत्र सिर्जना गर्छ।
**पहुँच:** थपिएको होस्ट प्रयोग गर्ने कुनै पनि अनुप्रयोग — एप कन्फिगरेसन परिवर्तन गर्नुपर्दैन
**टिप्पणी:** `source` = `"custom-host"`

प्रयोगका उदाहरणहरू:

- Python स्क्रिप्टहरूबाट `api.openai.com` निगरानी गर्ने
- `my-internal-llm.company.com` डिबग गर्ने
- एउटै नेटवर्कमा रहेका मोबाइल यन्त्रहरूबाट ट्राफिक क्याप्चर गर्ने (ARP स्पुफिङमार्फत — उन्नत)

### मोड 3 — HTTP_PROXY लिसनर (पोर्ट 8080)

**स्रोत:** `HTTP_PROXY`/`HTTPS_PROXY` वातावरणीय चरहरू प्रयोग गर्ने अनुप्रयोगहरू
**कार्यविधि:** पोर्ट 8080 मा रहेको सहायक लिसनर (`src/mitm/inspector/httpProxyServer.ts`), जसले मानक स्पष्ट HTTP/HTTPS प्रोक्सीका रूपमा काम गर्छ। यसले `CONNECT` टनेलहरू (HTTPS) र प्रत्यक्ष HTTP अनुरोधहरू स्वीकार गर्छ।
**पहुँच:** `HTTP_PROXY` वातावरणीय चर पालना गर्ने कुनै पनि अनुप्रयोग — DNS परिवर्तन वा sudo आवश्यक पर्दैन
**टिप्पणी:** `source` = `"http-proxy"`

```bash
# एउटै कमान्डका लागि द्रुत क्याप्चर:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# शेल सत्रमा स्थायी क्याप्चर:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**TLS सीमा:** HTTPS `CONNECT` टनेलहरू मेटाडेटा (होस्ट, पोर्ट, समय) का रूपमा मात्र क्याप्चर हुन्छन् — पूर्वनिर्धारित रूपमा TLS बडी डिक्रिप्ट हुँदैन। पूर्ण बडी निरीक्षणका लागि "प्रोक्सी मोडमा HTTPS डिक्रिप्ट गर्नुहोस्" टगल सक्षम गर्नुहोस् (स्वैच्छिक, AgentBridge प्रमाणपत्र विश्वसनीय हुन आवश्यक छ)।

**पोर्ट द्वन्द्व:** यदि पोर्ट 8080 प्रयोगमा छ भने, AgentBridge ले संरचित त्रुटिसहित 409 फर्काउँछ। `INSPECTOR_HTTP_PROXY_PORT` वातावरणीय चरमार्फत पोर्ट परिवर्तन गर्नुहोस्।

### मोड 4 — प्रणाली-व्यापी प्रोक्सी (उन्नत, स्वैच्छिक)

**स्रोत:** OS-स्तरीय प्रोक्सी सेटिङहरू (मेसिनका सबै एपहरूमा लागू हुन्छ)
**कार्यविधि:** सबै HTTP/HTTPS ट्राफिकलाई HTTP_PROXY लिसनरमार्फत रिडाइरेक्ट गर्न OS API हरू प्रयोग गर्छ:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **पहुँच:** प्रणाली प्रोक्सी सेटिङहरू पालना गर्ने मेसिनका प्रत्येक अनुप्रयोग
  **टिप्पणी:** `source` = `"system-proxy"`

**सुरक्षा संयन्त्रहरू:**

- स्वतः-असक्षम हुने टाइमर (पूर्वनिर्धारित 30 मिनेट, `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES` मार्फत कन्फिगर गर्न सकिने)
- अघिल्लो प्रणाली प्रोक्सी अवस्था DB मा सुरक्षित गरिन्छ र उल्टाउँदा पुनर्स्थापना गरिन्छ
- सक्रिय हुँदा प्रयोगकर्ता अन्यत्र गएमा ड्यासबोर्डले "प्रणाली प्रोक्सी उल्टाइँदै छ" भन्ने सन्देश देखाउँछ
- UI ले `⚠ उन्नत` ब्याज + स्पष्ट पुष्टिकरण चेकबक्स देखाउँछ

### मोड 5 — TPROXY पारदर्शी डिक्रिप्सन (Linux, root, स्वैच्छिक)

**स्रोत:** कर्नेल TPROXY + नीति राउटिङ (`src/mitm/tproxy/`)
**कार्यविधि:** `mangle OUTPUT` मा लक्षित पोर्टतर्फ (पूर्वनिर्धारित `443`) जाने नयाँ स्थानीय आउटबाउन्ड TCP जडानहरूलाई चिन्ह लगाउँछ, एउटा `ip rule` ले चिन्ह लगाइएका प्याकेटहरूलाई स्थानीय डेलिभरीतर्फ पुनःरुट गर्छ, र `mangle PREROUTING` को `TPROXY` लक्ष्यले तिनलाई पारदर्शी (**IP_TRANSPARENT**) लिसनरलाई (पूर्वनिर्धारित पोर्ट `8443`) हस्तान्तरण गर्छ। लिसनरले गतिशील CA द्वारा **मागअनुसार प्रत्येक SNI होस्टनामका लागि** जारी गरिएको लीफ प्रमाणपत्र प्रयोग गरी TLS समाप्त गर्छ, डिक्रिप्ट गरिएको आदानप्रदान क्याप्चर गर्छ, र अनुरोधलाई पुनःइन्क्रिप्ट गरेर मूल गन्तव्यतर्फ फर्वार्ड गर्छ।
**पहुँच:** लक्षित पोर्टमा रहेका **जुनसुकै** गन्तव्य होस्टहरू — `/etc/hosts` स्पुफ आवश्यक पर्दैन, `HTTP_PROXY` वातावरणीय चर आवश्यक पर्दैन, र प्रणाली-व्यापी प्रोक्सी परिवर्तन आवश्यक पर्दैन। इन्टरसेप्ट गरिएको प्रक्रियामा कुनै कन्फिगरेसन परिवर्तन आवश्यक पर्दैन, तर यसले गतिशील CA लाई विश्वास गर्नुपर्छ।
**टिप्पणी:** `source` = `"tproxy"`

**आवश्यकताहरू:** Linux मात्र (**IP_TRANSPARENT** Linux मा मात्र उपलब्ध छ), **CAP_NET_ADMIN** क्षमता (root), र C टुलचेनसँग बिल्ड गर्नुपर्ने नेटिभ N-API एडअन (`npm run build:native:tproxy`)। उपलब्ध नभएको अवस्थामा, "TPROXY डिक्रिप्सनका लागि Linux + root + नेटिभ एडअन आवश्यक छ" टुलटिपसहित ड्यासबोर्ड टगल असक्षम हुन्छ। फायरवाल नियमहरू लेनदेनात्मक रूपमा लागू/उल्टाइन्छन् (क्र्यास हुँदा कुनै `mangle` नियम बाँकी रहँदैन) र रिबुट हुँदा हट्छन्। SO_MARK-आधारित एन्टी-लुपले प्रोक्सीको आफ्नै पुनःइन्क्रिप्ट गरिएको फर्वार्डलाई पुनःइन्टरसेप्ट हुनबाट रोक्छ।

यो आफ्नै समर्पित अपरेटर गाइड भएको एउटा महत्वपूर्ण उपप्रणाली हो — पूर्ण फायरवाल विधि, प्रत्येक SNI का लागि गतिशील CA + ट्रस्ट-स्टोर इन्स्टलर, स्थानीय-मात्र रुट, एन्टी-लुप विवरणहरू, र कन्फिगरेसन स्किमाका लागि `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs` मा कम्पाइल गरिएको छैन) हेर्नुहोस्। टगल `GET / POST / DELETE /api/tools/agent-bridge/tproxy` द्वारा सञ्चालित हुन्छ (टिप्पणी: रुट Traffic Inspector प्रिफिक्सअन्तर्गत नभई AgentBridge प्रिफिक्सअन्तर्गत रहन्छ)।

## §4 LLM-सचेत सुविधाहरू

### 4.1 प्रकार पहिचानकर्ता (`src/mitm/inspector/kindDetector.ts`)

४ वटा सङ्केत प्रयोग गरेर प्रत्येक अनुरोधलाई `"llm"`, `"app"`, वा `"unknown"` का रूपमा वर्गीकृत गर्छ:

1. **होस्ट रजिस्ट्री** — ~१८ वटा ज्ञात LLM API होस्टनामहरू (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot, आदि)
2. **पाथ ढाँचाहरू** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses`, आदि।
3. **बडीको संरचना** — `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input` फिल्डहरू पत्ता लगाउँछ
4. **युजर-एजेन्ट सङ्केतहरू** — UA स्ट्रिङमा `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor`

Mode 2 मार्फत थपिएका अनुकूलन होस्टहरूले फाराम इनपुटबाट आफ्नो `kind` प्राप्त गर्छन् (पूर्वनिर्धारित मान `"custom"` हुन्छ)।

### 4.2 SSE मर्जर (`src/mitm/inspector/sseMerger.ts`)

**स्वतन्त्र क्लिन-रुम कार्यान्वयन।** इभेन्ट पार्सिङले
[WHATWG server-sent events algorithm](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)
अनुसरण गर्छ, जबकि पुनर्निर्माणले सार्वजनिक [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming), र
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent)
स्ट्रिमिङ स्किमाहरू अनुसरण गर्छ।

कच्चा SSE डेल्टा इभेन्टहरूबाट अन्तिम सहायक सन्देश पुनर्निर्माण गर्छ:

- **Anthropic**: अनुक्रमणिकाअनुसार `content_block_delta` सञ्चित गर्छ; `text_delta`, `input_json_delta` (उपकरण कलहरू), `thinking_delta` ह्यान्डल गर्छ
- **OpenAI**: Chat Completions का विकल्प/उपकरण कलहरू र Responses API का आउटपुट आइटमहरू
  अनुक्रमणिकाअनुसार सञ्चित गर्छ
- **Gemini**: `candidates[i].content.parts` सञ्चित गर्छ
- **Unknown**: कच्चा इभेन्टहरू जस्ताको तस्तै फर्काउँछ

Response ट्याबले एउटा टगल देखाउँछ: **"कच्चा इभेन्टहरू ↔ मर्ज गरिएको"**।

### 4.3 वार्तालाप सामान्यीकारक (`src/mitm/inspector/conversationNormalizer.ts`)

**स्वतन्त्र क्लिन-रुम कार्यान्वयन।** सामान्यीकरण स्थानीय ब्ल्याक-बक्स
सम्झौताहरू र सार्वजनिक OpenAI, Anthropic, र Gemini सन्देश स्किमाहरूद्वारा परिभाषित हुन्छ; कुनै अपस्ट्रिम
कार्यान्वयनको स्रोत प्रयोग गरिएको छैन।

रेन्डर गर्नुअघि OpenAI, Anthropic, र Gemini सन्देश ढाँचाहरूलाई एउटै `NormalizedConversation` मा रूपान्तरण गर्छ:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // अनुरोध बडीका सन्देश / सामग्री / प्रम्प्ट
  response: NormalizedTurn[]; // सहायकको प्रतिक्रिया (sseMerger मार्फत मर्ज गरिएको)
  contextKey: string | null; // SHA-256 प्रणाली-प्रम्प्ट फिङ्गरप्रिन्ट
}
```

ब्लकका प्रकारहरू: `text`, `tool_use`, `tool_result`। प्रदायक जुनसुकै भए पनि Conversation ट्याबले यही संरचना प्रयोग गर्छ।

### 4.4 कन्टेक्स्ट कुञ्जीको रङ निर्धारण (`src/mitm/inspector/contextKey.ts`)

- प्रणाली प्रम्प्टको `SHA-256` गणना गर्छ (पहिलो `role:system` सन्देश, वा `system` फिल्ड, वा Gemini `systemInstruction`)
- १२-वर्णको हेक्स उपसर्ग (`"a3f9c2..."`) फर्काउँछ
- फ्रन्टएन्डले बायाँ-किनाराको बारका लागि कुञ्जीलाई निर्धार्य HSL रङमा म्याप गर्छ
- **"उही कन्टेक्स्ट" फिल्टर**: `ctx #a3f` चिप क्लिक गर्दा उही फिङ्गरप्रिन्ट भएका अनुरोधहरू मात्र देखाउने फिल्टर थपिन्छ

यसले एउटै एजेन्ट सत्रमा चलिरहेका फरक "व्यक्तित्वहरू" वा कार्यहरूलाई दृश्यात्मक रूपमा छुट्याउन सजिलो बनाउँछ।

### 4.5 LLM मेटाडेटा निष्कर्षण

LLM अनुरोधहरूका लागि, LLM Details ट्याबले निम्न विवरण निकाल्छ:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // अनुरोध बडी वा प्रतिक्रियाबाट
  messages: number; // टर्न सङ्ख्या
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // SSE प्रतिक्रिया भए true
  mappedTo: string | null; // x-omniroute-mapped हेडर
  costEstimateUsd: number | null; // OmniRoute मूल्य निर्धारणमा आधारित अनुमानित लागत
}
```

### 4.6 प्रत्यक्ष प्रक्रियामा रहेको अनुरोध फिल्टर

अनुरोधको `status` फिल्ड `number | "in-flight" | "error"` हुन्छ — अनुरोध सुरु हुनेबित्तिकै एउटा प्रविष्टि
`"in-flight"` का रूपमा पुश गरिन्छ र प्रतिक्रिया (वा त्रुटि) आएपछि **सोही स्थानमा अद्यावधिक**
गरिन्छ। टुलबारको **"प्रत्यक्ष"** टगल
(`liveOnly`, i18n कुञ्जी `trafficInspector.liveOnly`) ले सूचीलाई
`status === "in-flight"` भएका प्रविष्टिहरूमा सीमित गर्छ, जसले खुला जडानहरू वास्तविक समयमा हेर्न दिन्छ।

फिल्टर
`src/lib/inspector/matchesTrafficFilter.ts` मा रहेको शुद्ध, क्लाइन्ट-साइड प्रेडिकेट हो:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

टगलको अवस्था `useTrafficFilters` (इन्स्पेक्टर ड्यासबोर्ड हुकहरू) मा रहन्छ र
अन्य फिल्टरहरू (प्रोफाइल, होस्ट, एजेन्ट, स्रोत, स्थिति, कन्टेक्स्ट) सँग संयोजन हुन्छ।

### 4.7 प्रक्रिया श्रेयाङ्कन (Linux)

Linux मा, प्रत्येक अवरोध गरिएको अनुरोधलाई **उत्पत्ति गर्ने स्थानीय
प्रक्रिया** सँग सम्बद्ध गर्न सकिन्छ। `InterceptedRequest` मा दुईवटा वैकल्पिक फिल्ड थपिएका छन्:

```ts
pid?: number;          // उत्पत्ति गर्ने प्रक्रियाको id (Linux मा मात्र)
processName?: string;  // उत्पत्ति गर्ने प्रक्रियाको नाम (Linux मा मात्र)
```

`src/mitm/inspector/processAttribution.ts` ले जडानको _क्लाइन्ट_
अस्थायी पोर्टलाई PID + नाममा निम्न तरिकाले म्याप गर्छ:

1. पोर्टका लागि सकेट inode फेला पार्न `/proc/net/tcp` र `/proc/net/tcp6` पढेर
   (`parseProcNetTcpForInode`, स्थिर नमुनाहरूसँग परीक्षण गर्न मिल्ने शुद्ध पार्सर)।
2. `socket:[<inode>]` तर्फको सिमलिङ्कका लागि `/proc/<pid>/fd/` स्क्यान गरेर।
3. `/proc/<pid>/comm` बाट प्रक्रियाको नाम पढेर।

१-सेकेन्डको TTL क्यासले लोडअन्तर्गत procfs स्क्यानको लागत सीमित गर्छ। श्रेयाङ्कन
**सकेसम्म उत्तम प्रयासमा आधारित** हुन्छ — कुनै पनि विफलताले `null` प्रदान गर्छ र क्याप्चरलाई कहिल्यै रोक्दैन।
macOS/Windows मा प्रकार्यले `null` फर्काउँछ (स्टब; `lsof`/`GetExtendedTcpTable`
समर्थन अनुवर्ती कार्य हो)।

### 5.1 सत्र रेकर्ड गर्ने

1. उपकरणपट्टीमा रहेको **"● सत्र रेकर्ड गर्नुहोस्"** मा क्लिक गर्नुहोस् → नाम प्रविष्ट गर्नुहोस् (वैकल्पिक)

- Recharts समष्टिहरूसहित तथ्याङ्क ट्याब उपलब्ध हुन्छ

### 5.3 निर्यात ढाँचाहरू

## §7 समस्या निवारण

### WebSocket विच्छेदन

यदि लाइभ टेलले "विच्छेद भयो" देखाउँछ भने:

1. सर्भर अझै चलिरहेको छ कि छैन जाँच गर्नुहोस्: `GET /api/tools/traffic-inspector/capture-modes`
2. पृष्ठ पुनः लोड गर्नुहोस् — WebSocket पुनः जडान हुन्छ र नयाँ स्न्यापसट प्राप्त गर्छ
3. यदि सर्भर पुनः सुरु गरिएको थियो भने, इन-मेमोरी बफर खाली भएको हुन्छ — सेसन रेकर्ड गरिएको थिएन भने पुराना प्रविष्टिहरू हराइसकेका हुन्छन्

### पोर्ट 8080 द्वन्द्व

यदि HTTP_PROXY मोड सुरु हुन असफल भयो भने:

```bash
lsof -i :8080    # प्रक्रिया पत्ता लगाउनुहोस्
```

पोर्ट परिवर्तन गर्नुहोस्:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### सिस्टम प्रोक्सी पूर्वस्थितिमा नफर्किएको

सिस्टम-व्यापी प्रोक्सी मोड सक्रिय हुँदा OmniRoute क्र्यास भएमा:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

यदि DB अवस्थाले प्रोक्सी सक्रिय थियो भन्ने सङ्केत गरेको पत्ता लगायो भने, अर्को पटक लोड हुँदा ड्यासबोर्डले "सिस्टम प्रोक्सी पूर्वस्थितिमा फर्काउनुहोस्" विकल्प पनि प्रदान गर्नेछ।

### बफर भरिएको

बफर `INSPECTOR_BUFFER_SIZE` (पूर्वनिर्धारित 1000) मा पुगेपछि, नयाँ प्रविष्टिहरूले सबैभन्दा पुराना प्रविष्टिहरूलाई हटाउँदै जान्छन्। महत्त्वपूर्ण अनुरोधहरू हराइरहेका छन् भने:

- `INSPECTOR_BUFFER_SIZE` बढाउनुहोस् (जस्तै, 5000) — यसले बढी समयसम्म राख्न थप मेमोरी प्रयोग गर्छ
- सम्बन्धित समयावधिलाई DB मा कायम राख्न सेसन रेकर्ड गर्नुहोस्
