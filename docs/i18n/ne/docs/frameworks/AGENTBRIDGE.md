AgentBridge भनेको OmniRoute को MITM (Man-in-the-Middle) प्रोक्सी हो, जसले IDE AI एजेन्टहरूबाट आउने HTTPS ट्राफिकलाई अवरोध गरी OmniRoute को एकीकृत राउटिङ इन्जिनमार्फत पुनःरुट गर्छ। यसले **10 IDE एजेन्टहरू** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code, र Trae (अनुसन्धान भइरहेको) — लाई समर्थन गर्छ, जसले OmniRoute लाई बजारमा AI कोडिङ सहायकहरूका लागि सबैभन्दा व्यापक कभरेज भएको MITM प्रोक्सी बनाउँछ।

**ड्यासबोर्ड स्थान:** `/dashboard/tools/agent-bridge`
**साइडबार समूह:** Tools (Cloud Agents पछि)
**यो पनि हेर्नुहोस्:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — अवरोध गरिएको सम्पूर्ण ट्राफिकलाई वास्तविक समयमा अनुगमन गर्नुहोस्; `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs` मा कम्पाइल गरिएको छैन) — `/api/tools/agent-bridge/tproxy` रुटद्वारा सञ्चालित Linux TPROXY पारदर्शी-डिक्रिप्ट क्याप्चर मोड।

## §1 सिंहावलोकन

### AgentBridge के हो?

जब कुनै IDE एजेन्टले (जस्तै, GitHub Copilot, Cursor, Claude Code) API कल गर्छ, त्यो सिधै अपस्ट्रिम AI प्रदायकसँग (OpenAI, Anthropic, आदि) जडान हुन्छ। AgentBridge ले कुनै पनि एजेन्ट कन्फिगरेसन परिवर्तन आवश्यक नपर्ने गरी TLS तहमा उक्त जडानलाई पारदर्शी रूपमा अवरोध गर्छ — र अनुरोधलाई OmniRoute मार्फत पुनर्लेखन गर्छ।

यसको अर्थ तपाईंले निम्न कार्यहरू गर्न सक्नुहुन्छ:

- **कुनै पनि एजेन्टलाई कुनै पनि प्रदायकतर्फ पुनःरुट गर्नुहोस्**: Copilot ले OpenAI सँग सञ्चार गर्दैछ? यसलाई Anthropic Claude, Gemini, वा OmniRoute का 352 प्रदायकमध्ये कुनै एकतर्फ रिडाइरेक्ट गर्नुहोस्।
- **मोडेल म्यापिङहरू लागू गर्नुहोस्**: ह्यान्डलर तहमा `gemini-3-flash` → `claude-sonnet-4.7` पारदर्शी रूपमा।
- **एजेन्टको सम्पूर्ण ट्राफिक अवलोकन गर्नुहोस्**: अवरोध गरिएको प्रत्येक अनुरोध [Traffic Inspector](./TRAFFIC_INSPECTOR.md) मा प्रकाशित हुन्छ।
- **OmniRoute को प्रत्यास्थता लागू गर्नुहोस्**: कम्बो राउटिङ, सर्किट ब्रेकरहरू, फलब्याकहरू, र लागत ट्र्याकिङले IDE एजेन्ट ट्राफिकका लागि पनि काम गर्छन्।

## §2 आर्किटेक्चर

### 2.1 कम्पोनेन्टहरूको अवलोकन

```
IDE Agent (VS Code / Cursor / आदि)
    │  HTTPS (पोर्ट 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← DNS रिडाइरेक्ट
    │
    ▼
src/mitm/server.cjs  (पोर्ट 443, CJS चाइल्ड प्रोसेस)
    │  Host हेडर SNI द्वारा लक्ष्य निर्धारण गर्छ
    │  AgentBridge CA द्वारा हस्ताक्षरित प्रति-SNI TLS प्रमाणपत्र उत्पन्न गर्छ
    ├── बाइपास सूचीसँग मेल खान्छ? → TCP पासथ्रु (डिक्रिप्ट नगर्ने)
    ├── लक्ष्यसँग मेल खान्छ? → fetch → OmniRoute राउटर (पोर्ट 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── अनुरोध बडी/हेडरहरूमा maskSecrets()
    │               ├── TrafficBuffer.push() — Traffic Inspector मा प्रकाशित गर्छ
    │               └── fetchRouter() → /v1/chat/completions
    └── मेल खाँदैन? → TCP पासथ्रु (डिक्रिप्ट नगर्ने)
```

### 2.2 MITM सर्भर (`src/mitm/server.cjs`)

मुख्य MITM सर्भर Node.js CJS चाइल्ड प्रोसेसका रूपमा चल्छ (अवस्थित CJS कोडबेस पुनर्लेखन गर्नबाट बच्न)। यसले:

- पोर्ट 443 मा सुन्छ (विशेषाधिकार वा `authbind`/`setcap` आवश्यक हुन्छ)
- OS बाट CONNECT टनेलहरू प्राप्त गर्छ (`/etc/hosts` DNS रिडाइरेक्टमार्फत)
- AgentBridge CA (`DATA_DIR/mitm/ca.crt`) द्वारा हस्ताक्षरित प्रति-SNI TLS प्रमाणपत्रहरू उत्पन्न गर्छ
- `targets/index.ts` रजिस्ट्रीमार्फत Host हेडरका आधारमा लक्षित एजेन्ट निर्धारण गर्छ
- HTTP मार्फत `http://127.0.0.1:20128` मा रहेको TypeScript ह्यान्डलर तहमा पठाउँछ

`TARGET_HOSTS`, `DATA_DIR/mitm/targets.json` बाट लोड गरिन्छ (बुट हुँदा `targets/index.ts` द्वारा लेखिएको), जसले CJS सर्भर पुनः सुरु नगरी डाइनामिक अपडेटहरू गर्न दिन्छ।

> **रुट-CA मोडेल (#6684)।** माथि वर्णन गरिएको CA द्वारा हस्ताक्षरित प्रति-SNI प्रमाणपत्र
> #6684 मा थपिएको स्थायी रुट-CA मोडेल हो (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, `src/mitm/tproxy/dynamicCert.ts` मा TPROXY का लागि
> पहिले नै प्रमाणित CA/leaf क्रिप्टो पुनः प्रयोग गर्दै) — यसले पुरानो एकल स्थिर स्व-हस्ताक्षरित
> leaf (`src/mitm/cert/generate.ts`, अझै पनि antigravity होस्टहरूमा मात्र सीमित) लाई
> प्रतिस्थापन गर्छ, जसको सङ्केत डिस्कमा रहेको सामान्य `server.crt`/`server.key` जोडीले गर्छ।
> **माइग्रेसन व्यवहार**: नयाँ इन्स्टलमा (पहिलेको `server.crt` नभएको) रुट-CA मोडेल स्वतः
> लागू हुन्छ; पुरानो स्थिर leaf लाई पहिल्यै विश्वास गरेको इन्स्टलले अपरेटरले
> `MITM_ROOT_CA_ENABLED=true` सेट गरेर ब्रिज पुनः सुरु नगरेसम्म त्यसैको प्रयोग जारी राख्छ
> (`src/mitm/cert/migration.ts` शुद्ध निर्णय फङ्सन हो — **कुनै पनि** होस्टका लागि leaf मा
> हस्ताक्षर गर्न सक्ने विश्वसनीय MITM CA पुरानो निश्चित-SAN leaf भन्दा उल्लेखनीय रूपमा
> बढी शक्तिशाली हुन्छ, त्यसैले पहिल्यै विश्वसनीय बनाइएको इन्स्टलमा स्विच कहिल्यै
> मौन रूपमा हुँदैन)। CA प्रमाणपत्र पुरानो leaf ले प्रयोग गरेको उही
> `omniroute-mitm.crt` ट्रस्ट-स्टोर स्लटमा इन्स्टल हुन्छ
> (`cert/install.ts::installCaCert`) — दोहोरो-विश्वास सफाइ आवश्यक पर्दैन।

### 2.3 ह्यान्डलर आधार (`src/mitm/handlers/base.ts`)

सबै एजेन्ट ह्यान्डलरहरूले `MitmHandlerBase` विस्तार गर्छन्:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // सुरक्षित सहायकहरू: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

प्रत्येक ह्यान्डलरले प्रोक्सी गर्नुअघि `hookBufferStart()` र पूरा भएपछि `hookBufferUpdate()` कल गर्छ। यिनले `InterceptedRequest` प्रविष्टिहरूलाई `globalTrafficBuffer` मा पठाउँछन् ([Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4 हेर्नुहोस्)।

### 2.4 लक्ष्य रजिस्ट्री (`src/mitm/targets/`)

प्रत्येक एजेन्टको एउटा घोषणात्मक लक्ष्य फाइल हुन्छ:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

रजिस्ट्री (`targets/index.ts`) ले `ALL_TARGETS` निर्यात गर्छ र बुट हुँदा `DATA_DIR/mitm/targets.json` उत्सर्जन गर्छ।

### 2.5 पासथ्रु र बाइपास सूची (`src/mitm/passthrough.ts`)

**बाइपास सूची** (लक्ष्य मिलानभन्दा प्राथमिकता दिएर पहिले जाँच गरिन्छ):

- पूर्वनिर्धारित ढाँचाहरू: बैंकिङ होस्टहरू, `.gov.`, OAuth/SSO प्रदायकहरू (Okta, Auth0), आदि
- प्रयोगकर्ता ढाँचाहरू: DB तालिका `agent_bridge_bypass` मा भण्डारण गरिन्छन्
- बाइपास गरिएका होस्टहरूले पारदर्शी TCP टनेल प्राप्त गर्छन् — TLS **कहिल्यै डिक्रिप्ट गरिँदैन**

**पूर्वनिर्धारित पासथ्रु** (लक्ष्यसँग मेल नखाने र बाइपासमा पनि नभएको):

- यसले पनि TCP टनेल प्राप्त गर्छ — जडानहरू कहिल्यै तोडिँदैनन्
- AgentBridge ले प्रणालीको सामान्य HTTPS ट्राफिकमा अवरोध पुर्याउनबाट रोक्छ

राउटिङ प्राथमिकता:

```
बाइपास सूची → लक्ष्य मिलान → पासथ्रु
```

### 2.6 अपस्ट्रिम CA प्रमाणपत्र (`src/mitm/upstreamTrust.ts`)

कस्टम CA भएका कर्पोरेट नेटवर्क वातावरणहरूका लागि:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

सेट गरिएको अवस्थामा, अतिरिक्त CA प्रमाणपत्रसहित `undici` को ग्लोबल डिस्प्याचर कन्फिगर गर्छ, जसले AgentBridge लाई कर्पोरेट TLS टर्मिनेसन प्रोक्सीहरूमार्फत अपस्ट्रिम प्रदायकहरूमा पुग्न दिन्छ।

### 2.7 गोप्य जानकारी मास्किङ (`src/mitm/maskSecrets.ts`)

स्वतन्त्र क्लिन-रुम स्क्यानर अनुरोध बडीहरू र क्रेडेन्सियल हेडरहरूमा तिनीहरू
Traffic Inspector बफर वा कुनै लगमा प्रवेश गर्नुभन्दा **अघि** लागू गरिन्छ। यसले एकल रैखिक पास गर्छ:

- `sk-` / `ak-` / `pk-` उपसर्ग भएका टोकनहरू (OpenAI/Anthropic-शैली)
- सम्पूर्ण-टोकन प्राथमिकतासहित RFC 6750 `Authorization: Bearer <token>` क्रेडेन्सियलहरू
- डट भएका र प्याड गरिएका स्वरूपहरूसहित सामान्य लामा अपारदर्शी टोकनहरू (≥40 क्यारेक्टर)

`sanitizeHeaders()` ले कायम राखिएका नामहरूलाई लोअरकेसमा बदल्छ, एरे मानहरूलाई निर्धारणात्मक रूपमा जोड्छ,
साझा हप-बाइ-हप/फ्रेमिङ अस्वीकृति सूची (प्रोक्सी प्रमाणीकरणसहित) हटाउँछ, `cookie` र
`set-cookie` लाई पूर्ण रूपमा लुकाउँछ, र क्रेडेन्सियल मानहरू स्क्यानरलाई सुम्पन्छ।

### 3.2 प्रमाणपत्रलाई विश्वसनीय बनाउने

IDE हरूले MITM जडान स्वीकार गर्नुअघि AgentBridge CA प्रमाणपत्रलाई OS ले विश्वसनीय मानेको हुनुपर्छ।

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

वा ड्यासबोर्डको "प्रमाणपत्र विश्वसनीय बनाउनुहोस्" बटन प्रयोग गर्नुहोस् (यसले आवश्यक परे sudo प्रम्प्टसहित तपाईंको OS का लागि उपयुक्त कमाण्ड चलाउँछ)।

#### Electron-आधारित IDE हरूले OS को विश्वसनीयता भण्डारलाई बेवास्ता गर्छन् (`NODE_EXTRA_CA_CERTS`)

केही IDE हरू — विशेषगरी **Antigravity IDE**, र Electron / VS Code बाट व्युत्पन्न अन्य एपहरू — ले
आफ्नै Node.js रनटाइम समावेश गर्छन्, जसले बाहिर जाने `fetch`/HTTPS का लागि **OS को विश्वसनीयता भण्डार प्रयोग गर्दैन**।
OS/NSS स्तरमा CA लाई विश्वसनीय बनाउनु IDE को नेटिभ **ब्याकइन्ड**
(उदाहरणका लागि, OS CA बन्डल प्रयोग गर्ने Go भाषा सर्भर) का लागि पर्याप्त हुन्छ, तर **Electron फ्रन्टइन्ड** मा
TLS अझै असफल हुन्छ — MITM लगमा ब्याकइन्डका बुटस्ट्र्याप कलहरूले `200` फर्काएको देखिए पनि
एपमा _लग आउट भएको_ वा _"जडान त्रुटि"_ देखिएको रूपमा यो प्रकट हुन्छ। दुई चरण आवश्यक छन्,
र दुवै महत्त्वपूर्ण छन्:

1. रनटाइमलाई स्पष्ट रूपमा CA तर्फ निर्देशित गर्नुहोस्:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **त्यही शेलबाट IDE सुरु गर्नुहोस्।** डेस्कटप आइकन / Dock / Start मेनुबाट सुरु गर्दा
   शेल एक्सपोर्टहरू इनहेरिट हुँदैनन्, र `~/.config/environment.d/*.conf` नयाँ ग्राफिकल लगइनपछि मात्र
   लागू हुन्छ। पहिले IDE लाई पूर्ण रूपमा बन्द गर्नुहोस् — Electron को सिङ्गलटन लकका कारण दोस्रोपटक
   सुरु गर्दा विद्यमान प्रोसेसमा मात्र फोकस हुन्छ र नयाँ वातावरणलाई बेवास्ता गरिन्छ।

माथिको OS-विश्वसनीयता + NSS चरण अझै आवश्यक छ (केही प्रमाणीकरण फ्लोहरूले प्रयोग गर्ने Chromium
नेटवर्क स्ट्याकले प्रत्येक प्रयोगकर्ताको NSS भण्डार पढ्छ, र `*.googleapis.com` का लागि यसको आफ्नै
स्थिर पिनहरू हुन्छन्, जसलाई स्थानीय रूपमा विश्वसनीय बनाइएको CA ले ओभरराइड गर्छ)।
`NODE_EXTRA_CA_CERTS` ले यसका अतिरिक्त Node को `fetch` पथ समेट्छ।

### 3.3 DNS राउटिङ

तपाईंले इन्टरसेप्ट गर्न चाहनुभएको प्रत्येक एजेन्टका API होस्ट(हरू) `127.0.0.1` मा रिजल्भ हुनुपर्छ। सेटअप विजार्डमा कुनै एजेन्टका लागि DNS टगल गर्दा AgentBridge ले `/etc/hosts` प्रविष्टिहरू स्वचालित रूपमा व्यवस्थापन गर्छ।

GitHub Copilot का लागि `/etc/hosts` प्रविष्टिहरूको उदाहरण:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 मोडेल म्यापिङ

स्रोत → लक्ष्य म्यापिङ परिभाषित गर्न प्रत्येक एजेन्ट कार्डको मोडेल म्यापिङ तालिका प्रयोग गर्नुहोस्:

| स्रोत मोडेल (एजेन्टको नेटिभ) | लक्ष्य मोडेल (OmniRoute) |
| ---------------------------- | ------------------------ |
| `gpt-4o`                     | `claude-sonnet-4.7`      |
| `*` (वाइल्डकार्ड)            | `claude-haiku-4.7`       |

वाइल्डकार्ड `*` ले पहिचान नभएको कुनै पनि मोडेललाई निर्दिष्ट लक्ष्यमा म्याप गर्छ। यो `agent_bridge_mappings` तालिकामा सुरक्षित रहन्छ।

> **सुझाव — एजेन्टका वास्तविक मोडेल ID हरू पत्ता लगाउनुहोस्।** IDE ले आफ्नो UI का लेबलहरूभन्दा फरक
> र प्रमुख संस्करणहरूबीच परिवर्तन हुने मोडेल नामहरू पठाउन सक्छ। उदाहरणका लागि **Antigravity 2** ले
> नेटवर्कमार्फत `gemini-3.1-pro-low`, `gemini-pro-agent`, र `gemini-3.1-flash-lite` पठाउँछ — पुराना
> कागजातमा देखाइएको `gemini-2.5-pro` होइन। मिल्ने म्यापिङ नराखी एउटा च्याट पठाउनुहोस्: MITM ले
> आगमनको सटीक `model:` लग गर्छ र अनुरोधलाई यथावत् अगाडि पठाउँछ। त्यो शाब्दिक मान म्याप गर्नुहोस्, त्यसपछि
> अर्को अनुरोध इन्टरसेप्ट भएर तपाईंको लक्ष्यमा रुट हुन्छ।

### 3.5 जोखिम सूचना

AgentBridge ले IDE ले अपस्ट्रिम प्रदायकहरूसँग प्रमाणीकरण गर्न प्रयोग गर्ने क्रेडेन्सियलहरू (OAuth टोकन, API कीहरू) इन्टरसेप्ट गर्छ। यी **लग गर्नुअघि मास्क गरिन्छन्** (§2.7 हेर्नुहोस्), तर OmniRoute को MITM तहलाई देखिन्छन्। प्रत्येक एजेन्टलाई पहिलोपटक सक्रिय गर्दा हटाउन मिल्ने जोखिम सूचना मोडल देखाइन्छ।

### 3.6 मर्मतसम्भार र निदान

ड्यासबोर्डले **मर्मतसम्भार र निदान** कार्ड (`AgentBridgeMaintenanceCard`, `src/app/(dashboard)/dashboard/tools/agent-bridge/components/` मा) उपलब्ध गराउँछ, जसले पहिले UI नभएका सञ्चालनसम्बन्धी MITM रुटहरू देखाउँछ। यसको उपशीर्षक: _"क्याप्चर पाइपलाइनको स्व-परीक्षण गर्नुहोस्, बाँकी रहेको प्रणाली अवस्था पूर्ववत् गर्नुहोस्, र आफ्नो सेटअप मेसिनहरूबीच सार्नुहोस्।"_ कार्डका क्लाइन्ट हेल्परहरू `src/lib/inspector/agentBridgeMaintenanceApi.ts` मा छन्।

| बटन                          | रुट                                    | यसले के गर्छ                                                                                                                                                                                      |
| ---------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **निदान गर्नुहोस्**          | `GET /api/tools/agent-bridge/diagnose` | क्याप्चर-पाइपलाइनको स्व-परीक्षण चलाउँछ र प्रत्येक जाँचको रिपोर्ट देखाउँछ (✓/✗ + समाधान सङ्केत)।                                                                                                   |
| **मर्मत गर्नुहोस्**          | `POST /api/tools/agent-bridge/repair`  | क्र्यास वा SIGKILL ले छाडेको अनाथ MITM प्रणाली अवस्था (DNS स्पूफ प्रविष्टिहरू, रुट CA, प्रणाली प्रोक्सी) पूर्ववत् गर्छ। इडेम्पोटेन्ट — अवस्था सफा हुँदा "मर्मत गर्नुपर्ने केही छैन" रिपोर्ट गर्छ। |
| **CA हटाउनुहोस्**            | `DELETE /api/tools/agent-bridge/cert`  | OS ट्रस्ट स्टोरबाट MITM रुट CA लाई अविश्वसनीय बनाउँछ र हटाउँछ (स्पष्ट, इडेम्पोटेन्ट)। CA हाल विश्वसनीय भएको अवस्थामा मात्र देखाइन्छ; इनलाइन "CA हटाउने?" पुष्टिकरण आवश्यक हुन्छ।                  |
| **कन्फिग निर्यात गर्नुहोस्** | `GET /api/tools/agent-bridge/config`   | पोर्टेबल कन्फिग JSON डाउनलोड गर्छ (§3.7 हेर्नुहोस्)।                                                                                                                                              |
| **कन्फिग आयात गर्नुहोस्**    | `POST /api/tools/agent-bridge/config`  | पहिले निर्यात गरिएको कन्फिग JSON अपलोड गर्छ (§3.7 हेर्नुहोस्)।                                                                                                                                    |

**निदान जाँचहरू** (`src/mitm/inspector/diagnostics.ts` मा रहेको `summarizeDiagnostics()`)। रुटले प्रत्येकका लागि प्रभावयुक्त प्रोब चलाउँछ र बूलियन मानहरू शुद्ध सारांशकर्तामा पठाउँछ; एउटा `healthy` निर्णयका साथै प्रत्येक विफलताका लागि सङ्केत फर्काइन्छ:

| जाँचको नाम         | यसले के प्रमाणित गर्छ                                       | विफलतामा सङ्केत                                                                                                                                                               |
| ------------------ | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | MITM सर्भर प्रक्रिया सक्रिय छ                               | "MITM सर्भर चलिरहेको छैन। यसलाई AgentBridge ट्याबबाट सुरु गर्नुहोस्।"                                                                                                         |
| `server-reachable` | MITM सर्भरले आफ्नो पोर्टमा जडानहरू स्वीकार गर्छ (TCP प्रोब) | "MITM सर्भरले आफ्नो पोर्टमा जडानहरू स्वीकार गरिरहेको छैन। पोर्ट खाली छ र त्यसमा बाइन्ड गर्न तपाईंसँग विशेषाधिकार छ भनी जाँच गर्नुहोस्।"                                       |
| `cert-exists`      | MITM प्रमाणपत्र डिस्कमा उत्पन्न गरिएको छ                    | "अहिलेसम्म कुनै MITM प्रमाणपत्र उत्पन्न गरिएको छैन। AgentBridge ट्याबबाट एउटा उत्पन्न गर्नुहोस्।"                                                                             |
| `cert-trusted`     | MITM रुट CA OS ट्रस्ट स्टोरमा छ                             | "MITM रुट CA लाई OS स्टोरले विश्वास गरेको छैन, त्यसैले TLS इन्टरसेप्सन विफल हुनेछ। AgentBridge ट्याबबाट प्रमाणपत्रलाई विश्वास गर्नुहोस्।"                                     |
| `dns-configured`   | लक्षित होस्टनेमहरू `/etc/hosts` मा स्पूफ गरिएका छन्         | "लक्षित होस्टनेमहरू /etc/hosts मा स्पूफ गरिएका छैनन्, त्यसैले ट्राफिक कहिल्यै प्रोक्सीसम्म पुग्दैन। तपाईंले क्याप्चर गर्न चाहनुभएको एजेन्ट(हरू) का लागि DNS सक्षम गर्नुहोस्।" |

**अनाथ-अवस्था ब्यानर:** पृष्ठले क्र्यासका कारण बाँकी रहेको अवस्था (DNS स्पूफ / CA / प्रणाली प्रोक्सी) पत्ता लगाउँदा, कार्डले एम्बर ब्यानर देखाउँछ — _"अघिल्लो सत्रले प्रणालीको अवस्था बाँकी छाडेको छ (DNS स्पूफ, CA, वा प्रणाली प्रोक्सी)। यसलाई सफा गर्न मर्मत चलाउनुहोस्।"_ — र **मर्मत गर्नुहोस्** बटनलाई हाइलाइट गर्छ। `Repair`, ProxyBridge को `--cleanup` फ्ल्यागको अनुप्रयोग-तह समकक्ष हो (यसले `src/mitm/manager.ts` मा रहेको `repairMitm()` लाई प्रत्यायोजन गर्छ)।

> पटक-पटक sudo प्रम्प्ट आउनबाट जोगिन MITM रुट CA लाई रोक्ने/सुरु गर्ने प्रक्रियाहरूका बीचमा
> इन्स्टल गरिएको अवस्थामै राखिन्छ (mitmproxy/Charles जस्तै व्यवहार), त्यसैले यसलाई हटाउनु भनेको
> रोक्दा स्वतः हुने कार्य नभई स्पष्ट **CA हटाउनुहोस्** कार्य हो।

### 3.7 पोर्टेबल कन्फिग आयात/निर्यात

AgentBridge ले **अपरेटरद्वारा समायोजन गर्न मिल्ने** अवस्थालाई संस्करणयुक्त JSON ब्लबमा क्रमबद्ध गर्न सक्छ, जसले गर्दा सेटअपलाई विभिन्न मेसिनहरूमा प्रतिकृति बनाउन सकिन्छ। सिरियलाइजर `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`) हो, जसलाई `AgentBridgeConfigSchema` ले प्रमाणीकरण गर्छ।

निर्यातमा ठ्याक्कै तीन भागहरू समावेश हुन्छन् (अन्तर्निर्मित पूर्वनिर्धारित मानहरू जानाजानी **निर्यात गरिँदैनन्**, जसले गर्दा आयात गर्दा तिनको कहिल्यै नक्कल हुँदैन वा तिनसँग द्वन्द्व हुँदैन):

| फिल्ड            | स्रोत                                                              | टिप्पणी                                                                   |
| ---------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| `bypassPatterns` | प्रयोगकर्ताद्वारा परिभाषित बाइपास ढाँचाहरू (`agent_bridge_bypass`) | पूर्वनिर्धारित bank/gov/okta ढाँचाहरू समावेश गरिँदैनन्                    |
| `customHosts`    | Traffic Inspector का अनुकूलन होस्टहरू (`inspector_custom_hosts`)   | प्रत्येक: `{ host, kind: "llm"\|"app"\|"custom", label? }`                |
| `agentMappings`  | प्रत्येक एजेन्टका मोडेल म्यापिङहरू (`agent_bridge_mappings`)       | म्यापिङ भएका प्रत्येक एजेन्टका लागि `{ [agentId]: [{ source, target }] }` |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**आयात व्यवहार** (`POST /api/tools/agent-bridge/config`): बाइपास ढाँचाहरू र प्रत्येक एजेन्टका म्यापिङहरू **पूर्ण रूपमा प्रतिस्थापन हुन्छन्**; अनुकूलन होस्टहरू **इडेम्पोटेन्ट रूपमा** थपिन्छन् (`INSERT OR IGNORE`)। प्रतिक्रियाले प्रत्येकमध्ये कतिवटा लागू गरिए भन्ने रिपोर्ट गर्छ:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

कन्फिगमा **नभएका** कुराहरू: सर्भर चलिरहेको अवस्था, प्रमाणपत्रका पथहरू, प्रत्येक एजेन्टको DNS अवस्था, अपस्ट्रिम CA पथ, र TPROXY सेटिङहरू — यी पोर्टेबल प्राथमिकताहरू होइनन्, होस्ट/रनटाइम अवस्था हुन्।

### संवेदनशील होस्टहरूका लागि बाइपास सूची

बाइपास सूचीले वित्तीय संस्थाहरू, OAuth/SSO प्रदायकहरू र अन्य संवेदनशील होस्टहरू **कहिल्यै डिक्रिप्ट नहुने** सुनिश्चित गर्छ। तिनको TLS ट्राफिक पारदर्शी TCP टनेलका रूपमा पार हुन्छ — OmniRoute ले कहिल्यै प्लेनटेक्स्ट देख्दैन।

पूर्वनिर्धारित बाइपास ढाँचाहरूमा यी समावेश छन्:

- `*.bank.*`, `*.gov.*` (वित्तीय/सरकारी)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/पहिचान)
- `*.apple.com`, `*.icloud.com` (Apple प्रणाली सेवाहरू)

प्रयोगकर्ताले थपेका बाइपास ढाँचाहरू `agent_bridge_bypass` तालिकामा भण्डारण गरिन्छन् र तिनले अरू सबैमाथि प्राथमिकता पाउँछन्।

### गोप्य जानकारी मास्किङ

`src/mitm/maskSecrets.ts` बाट `maskSecrets()` लागू गरिन्छ:

- `TrafficBuffer.push()` अघि प्रत्येक अनुरोध बडीमा
- लगिङ वा प्रसारणअघि प्रत्येक हेडरमा

ढाँचाहरू: `sk-`/`ak-`/`pk-` उपसर्ग भएका टोकनहरू, `Bearer` टोकनहरू, र कम्तीमा ४० क्यारेक्टर भएका सामान्य टोकनहरू।

### अपस्ट्रिम CA प्रमाणपत्र

`AGENTBRIDGE_UPSTREAM_CA_CERT` सेट गरिएको बेला, फाइल स्टार्टअपमा पढिन्छ। पथ अवस्थित भए पनि फाइल पढ्न नसकिने छ भने, AgentBridge ले स्पष्ट त्रुटि लग गर्छ र सुरु हुन अस्वीकार गर्छ (यसले कर्पोरेट वातावरणमा मौन TLS विफलता रोक्छ)।

### ज्ञात सीमितताहरू

- **पोर्ट 443 लाई विशेषाधिकार आवश्यक पर्छ**: Linux मा, AgentBridge लाई Node बाइनरीमा `setcap 'cap_net_bind_service=+ep'` आवश्यक पर्छ, वा `authbind` मार्फत चलाउनुपर्छ। सेटअप विजार्डले OS-विशिष्ट निर्देशनहरू देखाउँछ।
- **IDE पुनः सुरु गर्न आवश्यक छ**: DNS रिडाइरेक्टपछि, नयाँ होस्ट रिजोल्युसन प्रभावकारी बनाउन IDE पुनः सुरु गर्नुपर्छ।
- **हार्डकोड गरिएका OAuth टोकनहरू**: केही एजेन्टहरू (Kiro, Antigravity) ले OAuth रिफ्रेस टोकनहरू स्थानीय रूपमा भण्डारण गर्छन्। यी AgentBridge का लागि पारदर्शी हुन्छन् — यसले प्रत्येक अनुरोधमा Bearer टोकन देख्छ, जसलाई लगिङअघि मास्क गरिन्छ।
- **Electron फ्रन्टएन्डहरूलाई `NODE_EXTRA_CA_CERTS` आवश्यक पर्छ**: बन्डल गरिएको Node/Electron रनटाइममा फ्रन्टएन्ड चलाउने IDE हरूले OS/NSS ट्रस्ट स्टोर बेवास्ता गर्छन् र `NODE_EXTRA_CA_CERTS` सेट गरिएको शेलबाट सुरु गरिनुपर्छ (§3.2 हेर्नुहोस्)। यो नभएको लक्षण: IDE ब्याकएन्ड प्रमाणीकरण हुन्छ (MITM ले `200` हरू देखाउँछ) तर UI लगआउट अवस्थामै रहन्छ।
- **एउटै IDE का धेरै स्थापनाहरू स्वतन्त्र हुन्छन्**: प्रणाली स्थापना (जस्तै `/usr/share/antigravity/antigravity`) र प्रयोगकर्ता-स्थानीय "Full" स्थापना (जस्तै `~/AntigravityIDE_Full/antigravity-ide`) आफ्नै रनटाइम भएका अलग-अलग प्रक्रियाहरू हुन् — प्रत्येकलाई CA इन्जेक्ट गरेर पुनः सुरु गर्नुपर्छ। पुनः सुरु गर्नुअघि कुन चलिरहेको छ भनेर त्यसको बाइनरी पथबाट पहिचान गर्नुहोस्।
- **पहिचान रुट गरिएको मोडेलले होइन, एजेन्टको सिस्टम प्रम्प्टले सेट गर्छ**: तपाईंले एजेन्टको मोडेललाई फरक प्रदायकमा रिम्याप गर्दा पनि, जवाफले एजेन्टको मूल पहिचान नै दाबी गर्छ (जस्तै Antigravity ले "म Gemini द्वारा सञ्चालित छु" भन्छ), किनभने IDE ले त्यो कुरा सिस्टम प्रम्प्टमा इन्जेक्ट गर्छ। वास्तविक ब्याकएन्डको पुष्टि मोडेललाई ऊ को हो भनेर सोधेर होइन, `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`) मा गर्नुहोस्।

## §6 समस्या समाधान

### पोर्ट 443 द्वन्द्व

यदि अर्को प्रक्रिया पहिले नै पोर्ट 443 मा सुनिरहेको छ भने (वेब सर्भर, VPN, आदि):

```bash
lsof -i :443          # प्रक्रिया पत्ता लगाउनुहोस्
sudo fuser -k 443/tcp  # जबर्जस्ती बन्द गर्नुहोस् (सावधानीपूर्वक प्रयोग गर्नुहोस्)
```

वैकल्पिक रूपमा, AgentBridge सेटिङहरूमा गैर-विशेषाधिकार प्राप्त पोर्ट कन्फिगर गर्नुहोस् र `iptables` / `pf` रिडाइरेक्ट नियमहरू सेटअप गर्नुहोस्।

### प्रमाणपत्र विश्वसनीय छैन

AgentBridge सुरु गरेपछि IDE ले TLS त्रुटिहरू देखाउँछ भने:

1. प्रमाणपत्र स्थापना भएको पुष्टि गर्नुहोस्: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) वा `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. केही एपहरूले आफ्नै विश्वसनीयता भण्डार कायम राख्छन् (Firefox, Linux मा Chrome)। "Trust Cert" फेरि चलाउनुहोस् र NSS/Firefox-विशिष्ट प्रमाणपत्र भण्डार जाँच गर्नुहोस्।
3. विश्वसनीय बनाएपछि IDE पुनः सुरु गर्नुहोस् — चलिरहेका TLS सत्रहरूले पुरानै विश्वसनीयता अवस्था प्रयोग गर्छन्।

### विश्वसनीय CA हुँदाहुँदै पनि IDE लग आउट भएको / "connection error"

लक्षण: DNS रिडाइरेक्ट गरेपछि र CA लाई विश्वसनीय बनाएपछि, Electron-आधारित IDE (जस्तै Antigravity)
**लग आउट भएको** अवस्थामा खुल्छ वा प्रमाणीकरण/जडान त्रुटि देखाउँछ, तर MITM लगले
बुटस्ट्र्याप कलहरू (`loadCodeAssist`, `fetchAvailableModels`, …) ले `200` फर्काइरहेको देखाउँछ।

कारण: IDE को **बन्डल गरिएको Node/Electron रनटाइमले OS को विश्वसनीयता भण्डारलाई बेवास्ता गर्छ**। नेटिभ
ब्याकइन्ड (Go भाषा सर्भर) ले OS CA लाई विश्वास गर्छ र प्रमाणीकरण हुन्छ, तर Electron फ्रन्टइन्डले
विश्वास गर्दैन — त्यसैले UI ले आफू अफलाइन भएको ठान्छ।

समाधान (दुवै चरण): `NODE_EXTRA_CA_CERTS=<ca.crt>` निर्यात गर्नुहोस् **र त्यही
शेलबाट IDE पुनः सुरु गर्नुहोस्**, डेस्कटप आइकनबाट होइन। पहिले IDE पूर्ण रूपमा बन्द गर्नुहोस् — Electron को सिङ्गलटन लकका कारण
दोस्रो पटक सुरु गर्दा केवल विद्यमान प्रक्रिया फोकस हुन्छ र नयाँ वातावरण बेवास्ता गरिन्छ। §3.2 हेर्नुहोस्।
यो त्यस्तो खुला अपस्ट्रिम रिपोर्टसँग मेल खान्छ जहाँ स्ट्यान्डअलोन एजेन्ट MITM मार्फत काम गर्छ तर IDE
भेरियन्ट उही सेटअपमा असफल हुन्छ।

### DNS प्रसारित भएन

`/etc/hosts` अद्यावधिक भएको जाँच गर्नुहोस्:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

DNS क्यास खाली गर्नुहोस्:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE पत्ता लागेन

स्वतः-पहिचानले सामान्य स्थापना पथहरू प्रयोग गर्छ। IDE स्थापित भए पनि पहिचान असफल भएमा:

- IDE बाइनरी गैर-मानक स्थानमा छ कि जाँच गर्नुहोस्
- Setup Wizard ले अझै पनि काम गर्छ — पहिचान असफल हुनुको अर्थ ब्याजले स्थापना पथ नदेखाउने मात्र हो

### ह्यान्डलर त्रुटिहरू (अपस्ट्रिम फेच असफल)

AgentBridge ले इन्टरसेप्ट गरे पनि सबै अनुरोधहरू असफल भएमा:

1. `/dashboard/providers` मा कम्तीमा एउटा प्रदायक जडान भएको पुष्टि गर्नुहोस्
2. OmniRoute सर्भर लगहरू जाँच गर्नुहोस्: `.env` मा `APP_LOG_LEVEL=debug`
3. `OMNIROUTE_BASE_URL` ले सही राउटर एन्डपोइन्टतर्फ सङ्केत गरेको पुष्टि गर्नुहोस् (पूर्वनिर्धारित: `http://127.0.0.1:20128`)

## §8 मार्गचित्र

### Trae अनुसन्धान

Trae तुलनात्मक रूपमा नयाँ AI कोडिङ सहायक हो। ह्यान्डलर कार्यान्वयन गर्नुअघि:

1. VS Code / JetBrains मार्केटप्लेसहरूमा वा स्ट्यान्डअलोन एपका रूपमा बाइनरी/एक्सटेन्सन पहिचान गर्नुहोस्
2. API होस्टहरू र एन्डपोइन्टका संरचनाहरू पत्ता लगाउन mitmproxy मार्फत ट्राफिक क्याप्चर गर्नुहोस्
3. प्रमाणीकरण संयन्त्र निर्धारण गर्नुहोस्
4. TOS र API पत्ता लगाउन सकिने अवस्थाका आधारमा अगाडि बढ्ने/नबढ्ने मूल्याङ्कन गर्नुहोस्

अनुसन्धान पूरा नभएसम्म, ड्यासबोर्डमा रहेको Trae कार्डले "सम्भाव्यता रिपोर्ट गर्नुहोस्" लिङ्कसहित "अनुसन्धान जारी छ" ब्याज देखाउँछ। `src/mitm/handlers/trae.ts` मा रहेको ह्यान्डलर स्टबले संरचित `अझै कार्यान्वयन गरिएको छैन` त्रुटि उत्पन्न गर्छ।

### ब्याकलग एजेन्टहरू (MITM आवश्यक — अनुकूलन आधार URL समर्थन छैन)

निम्न उपकरणहरूले आफ्ना हालका संस्करणहरूमा अनुकूलन आधार URL हरू समर्थन गर्दैनन्, जसले MITM लाई अवरोधनको एक मात्र मार्ग बनाउँछ। सम्भाव्यता मूल्याङ्कन विचाराधीन छ:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — Kiro IDE भन्दा अलग)
- **Cowork** (Anthropic डेस्कटप)

नोट: GitHub Copilot CLI ≥v1.0.19 ले `COPILOT_PROVIDER_BASE_URL` समर्थन गर्छ — त्यस उपकरणका लागि MITM को सट्टा प्रत्यक्ष कन्फिगरेसन प्रयोग गर्नुहोस्।
