> **संक्षेपमा**: OmniRoute ले प्रत्येक अनुरोधको टोकन प्रयोग ट्र्याक गर्छ, लागत गणना गर्छ, प्रत्येक API कुञ्जीको कोटा लागू गर्छ, र ड्यासबोर्डमा विश्लेषण देखाउँछ। यो गाइडले यी सबै कसरी काम गर्छन् भनेर व्याख्या गर्छ।

**स्रोतहरू:**

- `open-sse/services/usage.ts` (~70KB) — मुख्य प्रयोग ट्र्याकिङ
- `src/lib/usageAnalytics.ts` (~10KB) — ड्यासबोर्डका लागि एकत्रीकरण
- `src/lib/db/quotaSnapshots.ts` — ऐतिहासिक कोटा डेटा
- `src/lib/db/usage*.ts` — प्रयोगसँग सम्बन्धित विभिन्न DB मोड्युलहरू

## अवलोकन

OmniRoute मार्फत प्रवाहित हुने प्रत्येक अनुरोधले एउटा **प्रयोग रेकर्ड** उत्पन्न गर्छ, जसले निम्न कुराहरू समेट्छ:

- **पहिचान**: कुन API कुञ्जी, प्रदायक, मोडेल, कम्बो
- **टोकनहरू**: प्रम्प्ट टोकनहरू, कम्प्लिसन टोकनहरू, क्यास गरिएका टोकनहरू, कुल
- **लागत**: USD रकम (मूल्य निर्धारण डेटाबाट गणना गरिएको)
- **समय**: विलम्बता, सुरु/अन्त्यका टाइमस्ट्याम्पहरू
- **स्थिति**: सफल, त्रुटि, दर-सीमित, आदि।

यी रेकर्डहरूलाई **विश्लेषण** मा एकत्रित गरिन्छ, **कोटा स्न्यापसटहरू** का रूपमा स्थायी रूपमा भण्डारण गरिन्छ, र **प्रत्येक कुञ्जीका बजेट सीमाहरू** लागू गर्न प्रयोग गरिन्छ।

```
अनुरोध ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    विश्लेषण    कोटा    बिलिङ
                    (ड्यासबोर्ड) (लागू)  (निर्यात)
```

## के रेकर्ड गरिन्छ

`usage.ts` सेवाले प्रत्येक अनुरोधका लागि एउटा **प्रयोग घटना** समेट्छ:

| फिल्ड              | प्रकार  | स्रोत                                                      |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | रेकर्ड गर्दा उत्पन्न गरिएको UUID                           |
| `apiKeyId`         | string  | अनुरोध सुरु गर्ने API कुञ्जी                               |
| `provider`         | string  | प्रदायक ID (openai, anthropic, आदि)                        |
| `model`            | string  | मोडेल ID (gpt-5, claude-opus-4-6, आदि)                     |
| `comboId`          | string? | कम्बोमार्फत रुट गरिएको भए कम्बो ID                         |
| `promptTokens`     | number  | अपस्ट्रिम प्रतिक्रियाबाट                                   |
| `completionTokens` | number  | अपस्ट्रिम प्रतिक्रियाबाट                                   |
| `cachedTokens`     | number  | क्यास हिट टोकनहरू (Anthropic प्रम्प्ट क्यासिङ, आदि)        |
| `totalTokens`      | number  | प्रम्प्ट + कम्प्लिसन                                       |
| `costUsd`          | number  | मूल्य निर्धारण डेटाबाट गणना गरिएको                         |
| `latencyMs`        | number  | अनुरोधको सुरुदेखि अन्त्यसम्मको अवधि                        |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | स्थिति success नभएमा त्रुटि वर्ग                           |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | अनुकूलन प्लगइनद्वारा प्रविष्ट गरिएको डेटा                  |

### टोकनहरू कहाँबाट आउँछन्

टोकनहरू **प्रतिक्रिया ह्यान्डलर** मा अपस्ट्रिम प्रदायकको प्रतिक्रियाबाट निकालिन्छन्:

```ts
// open-sse/handlers/chatCore.ts बाट
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

प्रयोग विवरण नफर्काउने प्रदायकहरूका लागि (केही वेब-कुकी प्रदायकहरू), OmniRoute ले `~4 chars per token` अनुमान-विधि प्रयोग गरेर टोकनहरूको **अनुमान** गर्छ (`open-sse/services/autoCombo/pipelineRouter.ts` हेर्नुहोस्)।

### क्यास गरिएका टोकनहरू

OmniRoute ले `cached_tokens` लाई `prompt_tokens` बाट अलग ट्र्याक गर्छ, किनभने:

- Anthropic प्रम्प्ट क्यासिङले क्यास गरिएका टोकनहरूका लागि घटाइएको दर (सामान्यको 10%) लिन्छ
- केही प्रदायकहरूले `cache_read_input_tokens` फर्काउँछन्, जसको मूल्य फरक तरिकाले निर्धारण गरिनुपर्छ
- विश्लेषणले **क्यास हिट दर** = `cached_tokens / prompt_tokens` देखाउन सक्छ

## लागत गणना

लागतहरू LiteLLM बाट सिंक गरिएको **मूल्य निर्धारण डेटा** (`src/lib/pricingSync.ts`) बाट गणना गरिन्छ:

| मोडेल             | इनपुट $/1M | आउटपुट $/1M | क्यास गरिएको $/1M |
| ----------------- | ---------- | ----------- | ----------------- |
| gpt-5             | $2.50      | $10.00      | —                 |
| claude-opus-4-6   | $15.00     | $75.00      | $1.50             |
| claude-sonnet-4-5 | $3.00      | $15.00      | $0.30             |
| gemini-2.5-pro    | $1.25      | $10.00      | —                 |

लागत सूत्र (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **प्रम्प्टबाट क्यास गरिएको भाग किन घटाइन्छ?** क्यास गरिएको भागको मूल्य छुट्टै निर्धारण गरिन्छ; सम्पूर्ण प्रम्प्टमा इनपुट मूल्य लगाउँदा लागत बढी गणना हुन्छ।

### मूल्य निर्धारण सिंक

मूल्य निर्धारण डेटा `/api/pricing/sync` एन्डपोइन्टमार्फत LiteLLM बाट स्वतः सिंक हुन्छ (यो बिल्ट-इन cron कार्यद्वारा ट्रिगर हुन्छ, प्रयोगकर्ताले प्रयोग गर्ने env var द्वारा होइन):

```bash
# म्यानुअल रूपमा ट्रिगर गर्नुहोस्
curl -X POST http://localhost:20128/api/pricing/sync
```

मूल्य निर्धारण डेटा नभएका मोडेलहरूका लागि, OmniRoute ले आन्तरिक औसत दरहरू (LiteLLM को मूल्य निर्धारण डेटाबाट लिइएको) प्रयोग गरेर **लागत अनुमान** गर्छ।

## मिति दायरा एकत्रीकरण

`usageAnalytics.ts` मोड्युलले कच्चा प्रयोग डेटाबाट ड्यासबोर्ड विजेटहरू गणना गर्छ। यसले 7 वटा समय दायरा समर्थन गर्छ:

| दायरा    | अवधि                                     | प्रयोगको अवस्था                 |
| -------- | ---------------------------------------- | ------------------------------- |
| `1d`     | पछिल्लो 24 घण्टा                         | प्रतिघण्टा लागत वृद्धिको पहिचान |
| `7d`     | पछिल्ला 7 दिन                            | साप्ताहिक समीक्षा               |
| `30d`    | पछिल्ला 30 दिन                           | मासिक बिलिङ                     |
| `90d`    | पछिल्ला 90 दिन                           | त्रैमासिक विश्लेषण              |
| `ytd`    | चालु वर्षको जनवरी 1 देखि                 | वार्षिक बजेट ट्र्याकिङ          |
| `all`    | सम्पूर्ण समय                             | हालसम्मका तथ्याङ्क              |
| `custom` | प्रयोगकर्ताले परिभाषित गरेको सुरु/अन्त्य | अडिट, तदर्थ क्वेरीहरू           |

### गणना गरिने ड्यासबोर्ड विजेटहरू

कुनै पनि मिति दायराका लागि, एनालिटिक्स तहले निम्न गणना गर्छ:

| विजेट                     | विवरण                                                |
| ------------------------- | ---------------------------------------------------- |
| **सारांश कार्डहरू**       | कुल अनुरोध, कुल लागत, कुल टोकन, सफलता दर             |
| **दैनिक प्रवृत्ति चार्ट** | मोडेलअनुसार स्ट्याक गरिएको प्रतिदिनको लागत + टोकन    |
| **गतिविधि हिटम्याप**      | दिनको घण्टा × हप्ताको दिन ग्रिड, रङ = अनुरोध सङ्ख्या |
| **मोडेल विभाजन**          | मोडेलअनुसार लागतको पाई चार्ट                         |
| **प्रदायक विभाजन**        | प्रदायकअनुसार अनुरोधहरूको बार चार्ट                  |
| **शीर्ष API कुञ्जीहरू**   | लागतअनुसार शीर्ष 10 कुञ्जीहरूको तालिका               |
| **त्रुटि विश्लेषण**       | समयक्रममा त्रुटि दर, शीर्ष त्रुटि वर्गहरू            |

### प्रोग्रामेटिक पहुँच

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // प्रयोग इतिहासका रेकर्डहरू
  "7d",                 // समय दायरा: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // प्रदायक जडान नक्सा (connectionId → खाताको नाम)
  {
    startDate: "2025-01-01",  // वैकल्पिक: "custom" दायराका लागि
    endDate: "2025-06-01",   // वैकल्पिक: "custom" दायराका लागि
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (सेन्ट)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## कोटा कार्यान्वयन

प्रति-API-कुञ्जी कोटा दुई स्थानमा कार्यान्वयन गरिन्छ:

1. **सफ्ट सीमा** (`quotaWarnAt`): प्रयोगले थ्रेसहोल्ड नाघ्दा ड्यासबोर्डमा चेतावनी
2. **हार्ड सीमा** (`quotaLimit`): सीमा नाघ्दा अनुरोध HTTP 429 सहित अस्वीकार गरिन्छ

### कन्फिगरेसन

```ts
// प्रति API कुञ्जी
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — चेतावनी देखाउनुहोस्
  quotaLimit: 10_00,    // $10.00 — पूर्ण रोक
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### कार्यान्वयन प्रवाह

```
अनुरोध ──▶ quotaCheck()
              │
              ├── सीमाभित्र छ?  ──▶ अनुमति दिनुहोस्
              │
              └── सीमा नाघ्यो?  ──▶ 429 Too Many Requests
                                   Retry-After हेडरसहित
```

### कोटा स्न्यापसटहरू

`quotaSnapshots` तालिकाले प्रवृत्ति विश्लेषणका लागि **ऐतिहासिक कोटा अवस्था** भण्डारण गर्छ:

| फिल्ड | विवरण |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | ट्र्याक भइरहेको कुञ्जी |
| `window` | "day" | "week" | "month" |
| `used` | यो विन्डोमा प्रयोग भएको लागत (सेन्टमा) |
| `limit` | सीमा (सेन्टमा) |
| `resetAt` | विन्डो रिसेट हुने समय |
| `createdAt` | स्न्यापसट लिइएको समय |

> 0 लागत प्रयोग गर्ने **हरेक अनुरोधमा** स्न्यापसटहरू लिइन्छन्, र तिनलाई निम्न कार्यका लागि प्रयोग गरिन्छ:

- ड्यासबोर्डमा कोटा प्रगति पट्टी रेन्डर गर्न
- 30-दिने कोटा प्रवृत्ति चार्टहरू देखाउन
- प्रयोग सीमाको नजिक पुग्दा अलर्टहरू ट्रिगर गर्न

### प्रयोग एनालिटिक्स क्वेरी गर्नुहोस्

प्रयोगसम्बन्धी डेटा प्रत्यक्ष REST निर्यात एन्डपोइन्टहरूबाट नभई ड्यासबोर्ड वा MCP उपकरणहरूबाट पहुँच गरिन्छ। उपलब्ध एनालिटिक्स:

- **`/api/usage/analytics`** — समग्र प्रयोग मेट्रिक्स (मोडेल, प्रदायक, कुञ्जीअनुसार समूहबद्ध)
- **`/api/usage/quota`** — प्रत्येक API कुञ्जीको हालको कोटा अवस्था
- **`/api/usage/history`** — अनुरोध इतिहास लगहरू

## अवधारण र सफाइ

प्रयोगसम्बन्धी डेटा प्रत्येक अनुरोधमा ~1-10KB ले बढ्छ। ठूलो परिमाणमा, यो उल्लेखनीय हुन सक्छ।

### अवधारण सेटिङहरू

प्रयोग इतिहासको अवधारण UI मा रहेको Database Settings मार्फत वा `/api/settings/database` मार्फत कन्फिगर गरिन्छ।

पूर्वनिर्धारित रूपमा, प्रयोग इतिहास **90 दिनसम्म** राखिन्छ।

### सफाइ

पुराना रेकर्डहरू `src/lib/db/cleanup.ts` द्वारा सफा गरिन्छन्:

- पृष्ठभूमिको cron प्रक्रियाद्वारा ट्रिगर हुन्छ
- कन्फिगर गरिएको `usageHistory` अवधारण सेटिङभन्दा पुराना `usage_history` का रेकर्डहरू मेटाउँछ

### भण्डारण अनुमान

| अनुरोध दर          | 30-दिने भण्डारण | 90-दिने भण्डारण |
| ------------------ | --------------- | --------------- |
| 100 अनुरोध/दिन     | ~3MB            | ~9MB            |
| 1,000 अनुरोध/दिन   | ~30MB           | ~90MB           |
| 10,000 अनुरोध/दिन  | ~300MB          | ~900MB          |
| 100,000 अनुरोध/दिन | ~3GB            | ~9GB            |

अत्यधिक ट्राफिकका लागि, निम्न विकल्पहरू विचार गर्नुहोस्:

- Database Settings मार्फत अवधारण अवधि घटाउने
- कच्चा रेकर्डहरूको सट्टा `aggregated_metrics` प्रयोग गर्ने (विश्लेषणका लागि मात्र)

## लागत अनुकूलन सुझावहरू

### 1. सही मोडेल प्रयोग गर्नुहोस्

```bash
# द्रुत उत्तर — सस्तो + छिटो प्रयोग गर्नुहोस्
curl -d '{"model":"auto/fast","messages":[...]}'

# जटिल कार्य — गुणस्तरीय मोडेल प्रयोग गर्नुहोस्
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. क्यासिङ सक्षम गर्नुहोस्

Anthropic prompt caching ले **दोहोरिएको सन्दर्भमा 90% बचत गर्छ**:

```ts
// क्यासिङ स्वचालित छ — उही ठूलो system prompt समावेश गर्नुहोस्
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // स्वचालित रूपमा क्यास गरिनेछ
  messages: [{ role: "user", content: "..." }],
});
```

### 3. कम्प्रेसन प्रयोग गर्नुहोस्

RTK + Caveman कम्प्रेसनले **धेरै टुल प्रयोग हुने सत्रहरूमा 15-95% बचत गर्छ**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. प्रत्येक कुञ्जीका लागि कोटा सेट गर्नुहोस्

अनियन्त्रित लागत रोक्न सधैं `quotaLimit` सेट गर्नुहोस्:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // $10/महिनाको सीमा
```

### 5. शीर्ष उपभोक्ताहरूको अडिट गर्नुहोस्

API कुञ्जीअनुसार समूहबद्ध गर्न र लागतअनुसार क्रमबद्ध गर्न ड्यासबोर्ड वा **`/api/usage/analytics`** प्रयोग गर्नुहोस्:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## समस्या निवारण

### "लागत अपेक्षाभन्दा बढी छ"

1. **`/api/usage/analytics?groupBy=model`** जाँच गर्नुहोस् — महँगो मोडेल पत्ता लगाउनुहोस्
2. **`/api/usage/analytics?groupBy=apiKey`** जाँच गर्नुहोस् — धेरै प्रयोग गर्ने उपभोक्ता पत्ता लगाउनुहोस्
3. मूल्य निर्धारण डेटा अद्यावधिक छ भनी प्रमाणित गर्नुहोस्: `POST /api/pricing/sync`

### "रेकर्डहरू हराइरहेका छन्"

- Dashboard → Database → Cleanup अन्तर्गत DB अवधारण सेटिङहरू जाँच गर्नुहोस् — आवधिक सफाइ कार्य (`src/lib/db/cleanup.ts`) द्वारा पुराना रेकर्डहरू मेटाइन्छन्
- `src/lib/db/usage*.ts` मा त्रुटिहरू जाँच गर्नुहोस् — DB लेखन विफलताहरू लग गरिन्छन् तर बाहिर देखाइँदैनन्
- अनुरोध वास्तवमै `chatCore` सम्म पुगेको थियो भनी प्रमाणित गर्नुहोस् — combo routing जाँच गर्नुहोस्

### "कोटा लागू भइरहेको छैन"

- कुञ्जीको `quotaLimit` सेटिङ जाँच गर्नुहोस्
- `quotaWindow` सही रूपमा सेट गरिएको छ भनी प्रमाणित गर्नुहोस्
- `quotaSnapshots` रेकर्डहरू खोज्नुहोस् — ती प्रत्येक अनुरोधमा सिर्जना हुनुपर्छ
