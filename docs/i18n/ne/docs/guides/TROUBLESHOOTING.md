## द्रुत सन्दर्भ

**OmniRoute मा नयाँ हुनुहुन्छ?** यहाँबाट सुरु गर्नुहोस् — यी उपायहरूले 90% समस्याहरू समाधान गर्छन्:

| मैले यो देख्छु                | यसको अर्थ                                         | के गर्ने                                                                                                                             |
| ----------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| "Can't connect"               | OmniRoute चलिरहेको छैन                            | `omniroute` चलाउनुहोस् वा `docker restart omniroute` चलाउनुहोस्                                                                      |
| "Invalid API key"             | तपाईंको कुञ्जी गलत छ वा म्याद सकिएको छ            | प्रदायकको वेबसाइटबाट कुञ्जी पुनः प्रतिलिपि गर्नुहोस्                                                                                 |
| "Rate limit exceeded"         | तपाईंले अत्यधिक अनुरोधहरू पठाइरहनुभएको छ          | 1 मिनेट पर्खनुहोस्, वा स्वचालित फलब्याकका लागि `model: "auto"` प्रयोग गर्नुहोस्                                                      |
| "Quota exceeded"              | तपाईंले आफ्नो निःशुल्क/सशुल्क कोटा सक्नुभएको छ    | थप प्रदायकहरू जडान गर्नुहोस्, वा निःशुल्क प्रदायकहरू (Kiro, Pollinations) प्रयोग गर्नुहोस्                                           |
| "Slow responses"              | प्रदायक व्यस्त छ वा धेरै टाढा छ                   | `model: "auto/fast"` प्रयोग गर्नुहोस् वा छिटो प्रदायक (Groq, Cerebras) जडान गर्नुहोस्                                                |
| "Wrong provider used"         | `auto` ले फरक प्रदायक रोज्यो                      | यो सामान्य हो! `auto` ले सबैभन्दा राम्रो प्रदायक रोज्छ। `model: "openai/gpt-4o"` प्रयोग गरेर कुनै निश्चित प्रदायक अनिवार्य गर्नुहोस् |
| "502 Bad Gateway"             | प्रदायक बन्द छ                                    | पर्खेर पुनः प्रयास गर्नुहोस्, वा प्रदायक परिवर्तन गर्न `model: "auto"` प्रयोग गर्नुहोस्                                              |
| "401 Unauthorized"            | तपाईंका प्रमाणहरू गलत छन्                         | आफ्नो API कुञ्जी जाँच्नुहोस् वा OAuth मार्फत पुनः प्रमाणीकरण गर्नुहोस्                                                               |
| "omniroute is not recognized" | Windows PATH मा विश्वव्यापी node मोड्युलहरू छैनन् | आफ्नो npm विश्वव्यापी prefix लाई Windows PATH मा थप्नुहोस्। यसलाई `npm config get prefix` प्रयोग गरेर पत्ता लगाउनुहोस्।              |
| "429 Too Many Requests"       | दर सीमा लागू भएको छ                               | 1 मिनेट पर्खनुहोस्, वा थप प्रदायकहरू जडान गर्नुहोस्                                                                                  |

## विस्तृत समस्या निवारण

---

### निःशुल्क प्रदायकहरूमा दर सीमितता (429 / 400 / 401)

**लक्षण**: निःशुल्क/प्रमाणीकरण नचाहिने प्रदायकहरू (opencode, auggie, आदि) सँग `model: "auto"` प्रयोग गर्दा, कहिलेकाहीँ उत्तरको सट्टा `HTTP 429`, `400`, वा `401` प्राप्त हुन्छ। केही क्षणपछि उही प्रम्प्ट पुनः प्रयास गर्दा अनुरोधहरू सफल हुन्छन्, तर स्वचालन (cron jobs, agents, scripts) पहिलो असफलतामै रोकिन्छ।

**मूल कारण**: तीनवटा स्वतन्त्र असफलता अवस्थाहरू एकसाथ थपिन्छन्:

1. **प्रदायकको दर सीमा (`429`)**: निःशुल्क तहहरूले प्रत्येक समयावधिका लागि कोटा लागू गर्न सक्छन्। समानान्तर कलहरूको अचानक वृद्धिले यसलाई समाप्त गर्छ, त्यसैले समयावधि रिसेट नभएसम्म अर्को अनुरोध अस्वीकार गरिन्छ।
2. **passthrough मा बिग्रिएको मोडेल (`400`/`401`)**: `auto/*` पूलहरूमा `opencode` का त्यस्ता passthrough मोडेलहरू समावेश हुन सक्छन्, जुन क्याटलगमा दर्ता भएका छन् तर सक्रिय प्रमाणहरू छैनन् (जस्तै `oc/north-mini-code-free` → `401`)। auto-router ले एउटा प्रयास गर्छ, असफल हुन्छ, र फलब्याक सुरु हुनुअघि नै त्रुटि प्रसारित हुन्छ।
3. **समवर्तीता प्रवर्धन (लोडमा `429`)**: धेरै agent/cron सत्रहरूले एकैपटक `auto` प्रयोग गर्दा, समग्र अनुरोध दर निःशुल्क प्रदायकहरूले सहन सक्ने सीमाभन्दा बढी हुन्छ, जसका कारण वैध कलहरूलाई पनि दुरुपयोगका रूपमा चिन्ह लगाइन्छ।

**प्रमाणित समाधान (समुदायद्वारा रिपोर्ट गरिएको, 2026-08-10)**: rotation, concurrency, र fallback ले निःशुल्क तहको अस्थिरतालाई विफल हुनुको सट्टा सम्हाल्न सकून् भनेर तीनवटा environment variables मिलाउनुहोस्:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 मा अर्को मोडेल/प्रदायकमा जानुहोस् (बिग्रिएका passthrough मोडेलहरू छोड्छ)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # heavyweight प्रवेशको स्पष्ट अधिकतम सीमा (पूर्वनिर्धारित रूपमा सेट हुँदैन: अनुरोध-सङ्ख्यामा सीमा छैन, तलको टिप्पणी हेर्नुहोस्)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # ढिला upstream हरूका लागि सीमित प्रतीक्षालाई RATE_LIMIT_MAX_WAIT_MS को पूर्वनिर्धारित मानभन्दा माथि बढाउनुहोस्
```

यी मानहरू OmniRoute process environment मा सेट गर्नुहोस् (daemon मा, जस्तै LaunchAgent plist वा `systemctl edit` मार्फत), त्यसपछि OmniRoute पुनः सुरु गर्नुहोस्। rotation flag सबैभन्दा बढी प्रभाव पार्ने एकल उपाय हो: यसले पूर्ण असफलतालाई पूलको स्वस्थ प्रदायकमा गरिने पारदर्शी पुनः प्रयासमा रूपान्तरण गर्छ।

**टिप्पणी**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ले एकैपटक चल्ने heavyweight — long-context — अनुरोधहरूको सङ्ख्या सीमित गर्छ; यो सीमा प्रवेश-द्वार हो, प्रदायकको दर सीमक होइन। **#503-fanout अद्यावधिक:** यो var अब पूर्वनिर्धारित रूपमा सेट हुँदैन (माथि देखाइएझैँ स्पष्ट रूपमा कन्फिगर गर्दा मात्र अब लागू हुन्छ) — यसको सट्टा heavyweight प्रवेशलाई स्वचालित रूपमा निर्धारण गरिएको byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) द्वारा नियन्त्रण गरिन्छ, जसले host को वास्तविक memory ceiling अनुसार आफूलाई मापन गर्छ। त्यसैले नयाँ deployment मा यो var बिल्कुलै सेट नगर्दा पनि निकै कम `503 chat_admission_busy` अस्वीकारहरू देखिनुपर्छ; यसलाई यहाँ स्पष्ट रूपमा सेट गर्दा अझै पनि दस्तावेजमा वर्णन गरिएअनुसार नै काम गर्छ। स्पष्ट byte-budget overrides लाई 8 MiB–2 GiB मा सीमित गरिन्छ। `413 body_exceeds_budget` अस्थायी होइन: त्यो byte budget बढाउनुहोस्, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` घटाउनुहोस्, वा process memory ceiling बढाउनुहोस्। `inflight_bytes_budget` shed अस्थायी स्रोत प्रतिस्पर्धा हो र पुनः प्रयास गर्न मिल्छ। प्रत्येक प्रदायकको दर सीमितता (`open-sse/services/rateLimitManager.ts`) लाई `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, र `RATE_LIMIT_AUTO_ENABLE` द्वारा छुट्टै नियन्त्रण गरिन्छ — `.env.example` हेर्नुहोस्।

**यसले काम गरेको छ कि छैन भनेर कसरी प्रमाणित गर्ने**: आफ्नो agent/cron लाई छोटो अन्तरालमा दुई पटक चलाउनुहोस् र दुवै पटक सफल भएको पुष्टि गर्नुहोस्। समाधान लागू गर्नुअघि, दोस्रो पटक चलाउँदा सामान्यतया `429`/`401` त्रुटि आउँछ। समाधान लागू गरेपछि, असफलताहरू (यदि कुनै भएमा) पारदर्शी रूपमा पुनः प्रयास गरिन्छन् र कल पूरा हुन्छ। तपाईं `curl /monitoring/health` पनि चलाउन सक्नुहुन्छ र provider connections मा रहेको `rateLimitedUntil` फिल्ड तथा प्रभावित providers का लागि `circuitBreakers.providerBreakers[].state` हेर्न सक्नुहुन्छ — state `CLOSED`, `DEGRADED`, `OPEN`, वा `HALF_OPEN` मध्ये एउटा हुन्छ (`src/shared/utils/circuitBreaker.ts` हेर्नुहोस्), र निरन्तर असफल भइरहने provider, reset window ले probe लाई पास हुन दिनुअघि, `CLOSED → DEGRADED → OPEN` मा परिवर्तन हुनेछ (`HALF_OPEN`)।

**यदि तपाईंले अझै पनि 429 देख्नुभयो भने**: उक्त provider को सक्रिय account ले वास्तवमै आफ्नो _quota_ समाप्त गरिसकेको छ (केवल rate मात्र होइन)। OmniRoute dashboard → Providers → Accounts मा सोही provider का लागि दोस्रो account थप्नुहोस्, वा अर्को निःशुल्क provider (जस्तै `routeway`, `auggie`) समावेश गर्नुहोस्। Rotation ले अस्थायी rate/400/401 समस्यामा मात्र मद्दत गर्छ; quota पूर्ण रूपमा समाप्त भएको अवस्थामा दोस्रो credential वा फरक provider आवश्यक पर्छ।

**यदि vision models (`auto/vision`, `bazaarlink/*`) मा 403 देख्नुभयो भने**: जडान गरिएको account सँग vision समावेश भएको paid plan छैन, वा API key का permissions अपर्याप्त छन्। provider dashboard मा key scope ले vision/multimodal समावेश गरेको पुष्टि गर्नुहोस्, वा paid tier account जडान गरेर त्यसलाई vision target का रूपमा राख्नुहोस्।

## npm install चेतावनीहरू (ERESOLVE / peer / deprecated)

तपाईंले `npm install -g omniroute` चलाउँदा `npm warn ERESOLVE`, peer-dependency सूचनाहरू र `deprecated` सन्देशहरूजस्ता चेतावनीहरूको लामो सूची देख्न सक्नुहुन्छ। **यी अपेक्षित र हानिरहित हुन्।** आउटपुटमा `added <N> packages` देखिएमा तपाईंको स्थापना सफल भएको हो।

peer-dependency समाधानसम्बन्धी चेतावनीहरू दबाउन OmniRoute को समर्थित स्थापना स्वरूप प्रयोग गर्नुहोस्:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` ले `ERESOLVE` र peer-dependency सूचनाहरू मात्र दबाउँछ। अप्रचलनसम्बन्धी सूचनाहरू देखिइरहन्छन्, किनभने ती अप्रत्यक्ष तेस्रो-पक्ष प्याकेजहरूबाट आउँछन्; तिनले स्थापना असफल भएको संकेत गर्दैनन्।

यी चेतावनीहरू OmniRoute को नियन्त्रणबाहिरका तेस्रो-पक्ष प्याकेजहरूमा भएका पुराना peer-dependency दायराहरूका कारण आउँछन्:

1. **`marked-terminal` लाई `marked >=1 <16` चाहिन्छ, तर `marked@18` फेला पर्यो** — व्यवहारमा ठीकसँग काम गर्छ; upstream peer दायरा मात्र पुरानो हो।
2. **`deprecated prebuild-install@7.1.3`** — एउटा अप्रत्यक्ष native-binary प्राप्त गर्ने सहायक हो। यसलाई
   स्थिर गरिएको `wreq-js` transport binding स्थापना गर्न प्रयोग गरिँदैन र यसले web-cookie
   provider transport सेटअप असफल भएको संकेत गर्दैन।

**कुनै कारबाही आवश्यक छैन** — upstream प्याकेजहरूलाई fork नगरी यी चेतावनीहरू पूर्ण रूपमा दबाउन सकिँदैन।

## npm install-scripts अवरुद्ध भएको चेतावनी (विश्वव्यापी स्थापना)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` चलाउँदा npm का नयाँ संस्करणहरू (v11+ र v12+) ले पूर्वनिर्धारित रूपमा प्याकेज lifecycle scripts अवरुद्ध गर्छन् र install-scripts चेतावनी देखाउँछन्:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### के यो चेतावनी बेवास्ता गर्न सकिन्छ?

**आंशिक रूपमा, तर scripts बिना चलाउन सिफारिस गरिँदैन।** OmniRoute मा सहज fallback हरू समावेश छन्: यदि standalone bundle बाट native `better-sqlite3` bindings लोड गर्न सकिएन भने, अनुप्रयोगले `node:sqlite` वा `sql.js` जस्ता वैकल्पिक drivers प्रयोग गर्छ ([SQLite Runtime Resolution](../ops/SQLITE_RUNTIME.md) हेर्नुहोस्)। server अझै सुरु हुनेछ, तर `sql.js` जस्ता WASM fallback मा चलाउँदा SQLite WAL (Write-Ahead Logging) mode निष्क्रिय हुन्छ र memory तथा disk-sync overhead बढ्छ।

### वास्तवमा कुन scripts आवश्यक छन्?

अवरुद्ध गरिएका सबै scripts OmniRoute चलाउन अनिवार्य हुँदैनन्:

- **अनिवार्य (`omniroute`, `better-sqlite3`):** OmniRoute एउटा Next.js standalone application bundle (`dist/`) बाट चल्छ। स्थापनाका क्रममा npm ले शीर्ष-स्तरको `node_modules/better-sqlite3/` मा host-specific native SQLite driver डाउनलोड वा compile गर्छ। त्यसपछि OmniRoute को `postinstall` script (`scripts/build/postinstall.mjs`) ले यी host-specific binaries लाई प्रमाणित गरेर `dist/node_modules/` मा प्रतिलिपि गर्छ, ताकि standalone server ले तिनमा पहुँच गर्न सकोस्। यदि `omniroute` को postinstall script अवरुद्ध भयो भने, यो प्रतिलिपि गर्ने चरण छोडिन्छ।
- **वैकल्पिक/अप्रत्यक्ष (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** यी build helpers, watcher tools वा system keychain utilities हुन्। तिनलाई अनुमति दिँदा build चेतावनीहरू रोकिन्छन्, तर मूल routing कार्यक्षमताका लागि ती आवश्यक छैनन्।
- **बहिष्कृत (`onnxruntime-node`):** स्थानीय AI embeddings का लागि एउटा वैकल्पिक dependency हो र OmniRoute चलाउन **आवश्यक छैन**। यसको postinstall script ले NuGet बाट लगभग 300MB का CUDA assets डाउनलोड गर्छ; समर्थित hardware मा स्थानीय ONNX acceleration प्रयोग गर्ने स्पष्ट उद्देश्य नभएसम्म यसलाई allow-list मा समावेश नगर्नुहोस्।

### सिफारिस गरिएको समाधान

विश्वव्यापी स्थापनाका क्रममा आवश्यक install scripts लाई अनुमति दिन र चेतावनीहरू दबाउन OmniRoute र यसका native dependencies का लागि `--allow-scripts` प्रयोग गर्नुहोस्:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

वैकल्पिक रूपमा, तपाईंको user account का सबै विश्वव्यापी स्थापनाहरूका लागि यसलाई स्थायी रूपमा configure गर्न:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### आफ्नो स्थापना प्रमाणित गर्नुहोस्

स्थापनापछि native bindings र runtime environment स्वस्थ छन् भनी सुनिश्चित गर्न built-in diagnostic tool चलाउनुहोस्:

```bash
omniroute doctor
```

## Gemini Web र Playwright Chromium

यदि Gemini Web अनुरोधले Playwright Chromium स्थापना गरिएको छैन भन्ने सन्देशसहित `503` फर्काउँछ भने, npm प्याकेज उपलब्ध छ तर ब्राउजर बाइनरी छैन।
Playwright ले जानाजानी ब्राउजर डाउनलोडलाई npm प्याकेज स्थापनाबाट अलग राख्छ, त्यसैले ब्राउजर स्थापना नभएसम्म यो प्रतिक्रिया अपेक्षित हो।

विश्वव्यापी npm स्थापनाका लागि, OmniRoute प्याकेजको डाइरेक्टरीबाट Chromium स्थापना गर्नुहोस्, ताकि ब्राउजर क्यास सोही Playwright स्थापनासँग सम्बन्धित होस्:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

स्थापनापछि OmniRoute पुनः सुरु गर्नुहोस्, अनि Gemini Web अनुरोध पुनः प्रयास गर्नुहोस्। यदि तपाईं Docker इमेजबाट OmniRoute चलाउनुहुन्छ भने, Chromium र यसका निर्भरताहरू समावेश भएको `-web` इमेज (वा `runner-web` बिल्ड लक्ष्य) प्रयोग गर्नुहोस्; आधार इमेजमा ती समावेश हुँदैनन्।

## एन्टिभाइरसका गलत सकारात्मक परिणामहरू

<a name="antivirus-false-positives"></a>

### Avast/AVG ले `README.md` लाई `MD:HttpRequest-inf[Susp]` का रूपमा क्वारेन्टिन गर्छ

**यो गलत सकारात्मक परिणाम हो। कुनै पनि कुरा सङ्क्रमित छैन, र कुनै कारबाही आवश्यक छैन।**

Avast र AVG ले धेरै HTTP अनुरोधजस्ता देखिने लिङ्कहरू भएका सादा-पाठ/Markdown फाइलहरूलाई चिन्ह लगाउने ह्युरिस्टिक चलाउँछन्। OmniRoute को `README.md` npm प्याकेजभित्र समावेश हुन्छ (यो `package.json` → `files` मा सूचीबद्ध छ), त्यसैले ग्लोबल इन्स्टल गर्दा यो `node_modules/omniroute/README.md` मा पुग्छ — र यसमा करिब 15 वटा `http://localhost:20128/...` उदाहरणहरू छन् (MCP HTTP/SSE एन्डपोइन्टहरू, A2A `.well-known` URL, र `curl` स्निपेटहरू)। लिङ्कहरूको यति धेरै घनत्व ह्युरिस्टिक सक्रिय गराउन पर्याप्त हुन्छ।

यदि यो हालसालै मात्र सुरु भएको हो भने: फाइलको प्रकृति परिवर्तन भएको छैन। README मा एन्डपोइन्टहरूको तालिका विस्तार गरिएको थियो (MCP HTTP + SSE + A2A थपिएका थिए) र थप `curl` उदाहरणहरू राखिएका थिए, जसले यसलाई सीमाभन्दा माथि पुर्यायो।

यो शून्य कार्यान्वयनयोग्य सामग्री भएको निष्क्रिय दस्तावेज हो। तपाईं यसलाई क्वारेन्टिनबाट सुरक्षित रूपमा पुनर्स्थापना गर्न सक्नुहुन्छ।

**के गर्ने:**

1. **सूचनाहरू रोक्नुहोस्** — आफ्नो एन्टिभाइरसमा इन्स्टल डाइरेक्टरीलाई अपवादमा राख्नुहोस्
   (Avast: Settings → Exceptions), र आफ्नो ग्लोबल `node_modules` पथ र/वा
   OmniRoute डेटा डाइरेक्टरी (`~/.omniroute/`) थप्नुहोस्।
2. **गलत सकारात्मक परिणाम रिपोर्ट गर्नुहोस्** — <https://www.avast.com/false-positive-file-form.php>,
   र क्वारेन्टिन गरिएको `README.md` संलग्न गर्नुहोस्। यसले सबैलाई मद्दत गर्ने समाधान प्रदान गर्छ, किनकि यो
   पाठ फाइलप्रति विक्रेताको ह्युरिस्टिकको अतिरञ्जित प्रतिक्रिया हो।

**हामी आफ्नो पक्षबाट यसलाई किन "ठीक" गर्दैनौँ:** सबै उदाहरणहरू `http://localhost` हुन्, र
स्व-हस्ताक्षरित प्रमाणपत्रसम्बन्धी झन्झटबिना localhost लाई `https` बनाउन सकिँदैन। एउटै विक्रेताको ह्युरिस्टिकबाट
जोगिन दस्तावेजलाई विकृत गर्दा स्क्यानरको बगलाई सन्तुष्ट पार्न हरेक पाठकलाई हानि पुग्छ।

### Kaspersky ले Desktop एपलाई `PDM:Trojan.Win32.Generic` का रूपमा चिन्ह लगाउँछ

**यो व्यवहारगत ह्युरिस्टिकबाट आएको गलत सकारात्मक परिणाम हो। कुनै पनि कुरा सङ्क्रमित छैन।** Kaspersky को
`PDM:` उपसर्गले निर्णय यसको Proactive Defense Module (System Watcher) बाट आएको जनाउँछ,
जसले इन्स्टलरलाई ज्ञात मालवेयरसँग तुलना गर्नुको सट्टा त्यसले के _गर्छ_ भन्ने आधारमा मूल्याङ्कन गर्छ। यो
सक्रिय हुँदा Kaspersky ले सम्पूर्ण इन्स्टलेसनलाई "रोल ब्याक" गर्छ — पहिले नै लेखिसकेका फाइलहरू मेटाउँछ —
त्यसैले अन्ततः एप बिग्रिएको वा हराएको हुन्छ।

यसले चिन्ह लगाउने फाइलहरू डेस्कटप एपसँग बन्डल गरिएका घोषित, खुला-स्रोत डिपेन्डेन्सीका मानक भागहरू हुन्, उदाहरणका लागि:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` र
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), एपभित्र प्रदायक लगइन र ब्राउजरमा आधारित च्याटका लागि प्रयोग हुने
  ब्राउजर-अटोमेसन लाइब्रेरी।
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — वेब-कुकी प्रदायकहरूमा ब्राउजर-फिङ्गरप्रिन्ट गरिएको HTTP का लागि प्रयोग हुने निश्चित संस्करणको `wreq-js` नेटिभ बाइन्डिङ
  (`<arch>` भनेको `x64` वा `arm64` हो)।

**यो किन सक्रिय हुन्छ:** Windows इन्स्टलरमा **अहिलेसम्म कोड-हस्ताक्षर गरिएको छैन**, त्यसैले हस्ताक्षर नगरिएको NSIS
इन्स्टलरको कुनै प्रतिष्ठा हुँदैन र व्यवहारगत ह्युरिस्टिकहरू अधिकतम आक्रामकतासहित चल्छन्। यससँगै बन्डल गरिएको
नेटिभ DLL र `%LOCALAPPDATA%\Programs\OmniRoute` अन्तर्गत लेखिने सयौँ `.js` फाइलहरू
(Next.js स्ट्यान्डअलोन बिल्डका ह्यास-प्रत्यय भएका प्याकेज डाइरेक्टरीहरू सहित) ह्युरिस्टिक सक्रिय गराउन पर्याप्त हुन्छन्।
कोड हस्ताक्षर गर्ने योजना छ; त्यो लागू नभएसम्म नयाँ रिलिजहरूमा यो दोहोरिन सक्छ।

**के गर्ने:**

1. **पहिले आफ्नो डाउनलोड प्रमाणित गर्नुहोस्** (यसले फाइलमा छेडछाड भएको सम्भावना हटाउँछ)। प्रत्येक रिलिजले
   `latest.yml` प्रकाशित गर्छ, जसको `sha512` फिल्ड (base64) ले `OmniRoute.Setup.<version>.exe`
   इन्स्टलरलाई समेट्छ। PowerShell मा, इन्स्टलर भएको फोल्डरबाट:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   आउटपुट `latest.yml` → `sha512` सँग मिल्नैपर्छ। नमिलेमा फाइल मेटाउनुहोस् र
   [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) बाट मात्र पुनः डाउनलोड गर्नुहोस्।
2. **पुनर्स्थापना गर्नुहोस् + अपवादमा राख्नुहोस्** — रोल ब्याक गरिएका वस्तुहरूलाई क्वारेन्टिनबाट पुनर्स्थापना गर्नुहोस् र
   `%LOCALAPPDATA%\Programs\OmniRoute` लाई अपवादमा थप्नुहोस् (Kaspersky → Settings → Threats and Exclusions),
   त्यसपछि पुनः इन्स्टल गर्नुहोस्।
3. **गलत सकारात्मक परिणाम रिपोर्ट गर्नुहोस्** — <https://opentip.kaspersky.com/>। प्रयोगकर्ताले पेस गरेका गलत सकारात्मक परिणामसम्बन्धी
   रिपोर्टहरूले वास्तवमै अनुमति-सूचीमा समावेश गर्ने प्रक्रिया छिटो बनाउँछन्।

## Node.js अनुकूलता

<a name="nodejs-compatibility"></a>

### लगइन पृष्ठ क्र्यास हुन्छ वा "Module self-registration" त्रुटि देखाउँछ

**कारण:** तपाईं OmniRoute ले स्वीकृत गरेको सुरक्षित रनटाइमको न्यूनतम सीमाभन्दा बाहिरको Node.js संस्करण चलाइरहनुभएको छ। सबैभन्दा सामान्य अवस्था भनेको OmniRoute लाई आवश्यक पर्ने प्याच गरिएको सुरक्षा सीमाभन्दा तल पर्ने Node 22 वा 24 को पुरानो प्याच स्तर चलाउनु हो।

**लक्षणहरू:**

- लगइन पृष्ठले खाली स्क्रिन वा सर्भर त्रुटि देखाउँछ
- कन्सोलले `Error: Module did not self-register` वा यस्तै नेटिभ बाइन्डिङ त्रुटिहरू देखाउँछ
- रनटाइम समर्थित सुरक्षित नीतिभन्दा बाहिर भएमा लगइन पृष्ठले तपाईंको Node संस्करणसहितको **सुन्तला रङको चेतावनी ब्यानर** देखाउँछ

**समाधान:**

1. समर्थित Node.js LTS रिलिज स्थापना गर्नुहोस् (सिफारिस गरिएको: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. आफ्नो संस्करण जाँच गर्नुहोस्: `node --version` ले 24.x LTS शृङ्खलामा `v24.0.0` वा सोभन्दा नयाँ संस्करण देखाउनुपर्छ
3. OmniRoute पुनः स्थापना गर्नुहोस्: `npm install -g omniroute`
4. पुनः सुरु गर्नुहोस्: `omniroute`

> **समर्थित सुरक्षित संस्करणहरू:** `>=22.22.2 <23` वा `>=24.0.0 <27`। Node.js 24.x LTS (Krypton) र Node.js 26 पूर्ण रूपमा समर्थित छन्।

### npm v11+: `better-sqlite3` स्थापना भएको छैन (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**कारण:** npm v11 (Node.js 24+ सँग उपलब्ध हुने) ले पूर्वनिर्धारित रूपमा वैकल्पिक
डिपेन्डेन्सीहरूका स्थापना स्क्रिप्टहरूलाई रोक्छ। `better-sqlite3` लाई `optionalDependencies`
मा सूचीबद्ध गरिएको र यसलाई नेटिभ कम्पाइलेसन (`node-gyp rebuild`) आवश्यक पर्ने भएकाले, npm ले यसलाई कुनै सूचना नदिई छोड्छ।

**लक्षणहरू:**

- सर्भर सुरु हुँदा `Cannot find module 'better-sqlite3'` सहित क्र्यास हुन्छ
- `ls node_modules/better-sqlite3` ले "No such file or directory" देखाउँछ
- `npm ls better-sqlite3` ले `(empty)` देखाउँछ

**समाधान:**

1. स्थापना स्क्रिप्टहरूलाई स्वीकृति दिनुहोस् र पुनः स्थापना गर्नुहोस्:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. वा पहिले नै निर्माण गरिएको प्याकेज म्यानुअल रूपमा स्थापना गर्नुहोस्:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. यसले काम गर्छ कि गर्दैन जाँच गर्नुहोस्: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**कारण:** विश्वव्यापी `npm install -g omniroute` पछि, प्याकेजभित्रको `better-sqlite3` नेटिभ बाइनरी स्थानीय रूपमा चलिरहेकोभन्दा फरक आर्किटेक्चर वा Node.js ABI का लागि कम्पाइल गरिएको हुन सक्छ। पहिले नै निर्माण गरिएको बाइनरी तपाईंको वातावरणसँग नमिल्दा macOS (Apple Silicon र Intel दुवै) मा यो सामान्य रूपमा हुन्छ।

**लक्षणहरू:**

- सर्भर सुरु हुनेबित्तिकै `dlopen` त्रुटिसहित असफल हुन्छ
- त्रुटिमा `slice is not valid mach-o file` समावेश हुन्छ
- पूर्ण उदाहरण:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**समाधान — आफ्नो स्थानीय वातावरणका लागि पुनः निर्माण गर्नुहोस् (Node.js को संस्करण घटाउनु पर्दैन):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **नोट:** यसले तपाईंको स्थानीय Node.js संस्करण र CPU आर्किटेक्चरअनुसार नेटिभ बाइन्डिङ पुनः कम्पाइल गरी बाइनरी बेमेल समाधान गर्छ। आधिकारिक रूपमा समर्थित रनटाइम दायरा **`>=22.22.2 <23` वा `>=24.0.0 <27`** हो (`src/shared/utils/nodeRuntimeSupport.ts` मा रहेको `SUPPORTED_NODE_RANGE`, `package.json` को `engines` फिल्डसँग मिलाइएको)। Node.js 24.x LTS (Krypton) र Node.js 26 लाई `better-sqlite3` v12.x सँग पूर्ण रूपमा समर्थन गरिन्छ।

## प्रोक्सीसम्बन्धी समस्याहरू

<a name="proxy-issues"></a>

### प्रदायक प्रमाणीकरणले "fetch failed" देखाउँछ

**कारण:** API कुञ्जी प्रमाणीकरण एन्डपोइन्ट (`POST /api/providers/validate`) ले पहिले प्रोक्सी कन्फिगरेसनलाई बेवास्ता गरिरहेको थियो, जसका कारण प्रोक्सी राउटिङ आवश्यक पर्ने वातावरणहरूमा त्रुटि हुन्थ्यो।

**समाधान (v3.5.5+):** यो अब समाधान गरिएको छ। प्रदायक प्रमाणीकरण `runWithProxyContext` मार्फत रुट हुन्छ र प्रदायक-स्तर तथा ग्लोबल प्रोक्सी सेटिङहरू स्वतः पालना गर्छ।

### टोकन स्वास्थ्य जाँच "fetch failed" का साथ असफल हुन्छ

**कारण:** पृष्ठभूमिमा हुने OAuth टोकन रिफ्रेसले प्रत्येक कनेक्सनका लागि प्रोक्सी कन्फिगरेसन निर्धारण गरिरहेको थिएन।

**समाधान (v3.5.5+):** टोकन स्वास्थ्य जाँच शेड्युलरले अब रिफ्रेस गर्ने प्रयास गर्नुअघि प्रत्येक कनेक्सनका लागि प्रोक्सी कन्फिगरेसन निर्धारण गर्छ। v3.5.5+ मा अद्यावधिक गर्नुहोस्।

### SOCKS5 प्रोक्सीले "invalid onRequestStart method" फर्काउँछ

**कारण:** Node.js 22 मा undici@8 डिस्प्याचर Node को अन्तर्निर्मित `fetch()` कार्यान्वयनसँग असङ्गत छ।

**समाधान (v3.5.5+):** प्रोक्सी डिस्प्याचर सक्रिय हुँदा OmniRoute ले अब undici कै `fetch()` प्रकार्य प्रयोग गर्छ, जसले एकरूप व्यवहार सुनिश्चित गर्छ। v3.5.5+ मा अद्यावधिक गर्नुहोस्।

### WSL अन्तर्गतको MITM प्रोक्सी: Windows होस्टका डेस्कटप एपहरू इन्टरसेप्ट हुँदैनन्

**कारण:** MITM प्रोक्सी र यसको CA प्रमाणपत्र OmniRoute चल्ने वातावरणमा स्थापना हुन्छन्। WSL अन्तर्गत त्यो वातावरण Linux गेस्ट हो, जबकि AI डेस्कटप एपहरू (Kiro, Trae, Copilot, Zed, …) Windows होस्टमा चल्छन्। होस्ट एपहरूले गेस्टको प्रमाणपत्र स्टोरलाई विश्वास गर्दैनन् र गेस्टको प्रणाली प्रोक्सीमार्फत रुट हुँदैनन्, त्यसैले त्यहाँ डेस्कटप इन्टरसेप्सन सक्रिय हुँदैन।

**सिफारिस:** तपाईंले इन्टरसेप्ट गर्न चाहनुभएका डेस्कटप एपहरू चल्ने सोही OS मा OmniRoute नेटिभ रूपमा चलाउनुहोस् (Windows एपहरूका लागि Windows; macOS/Linux का लागि पनि सोहीअनुसार)। होस्ट एपहरूलाई लक्षित गर्दै OmniRoute लाई WSL भित्रै राख्नका लागि उत्पन्न गरिएको CA प्रमाणपत्रलाई Windows होस्टमा म्यानुअल रूपमा विश्वसनीय बनाउनुपर्छ र प्रत्येक होस्ट एपको नेटवर्क/प्रोक्सी सेटिङलाई WSL प्रोक्सी एन्डपोइन्टतर्फ निर्देशित गर्नुपर्छ — यो असमर्थित र अस्थिर सेटअप हो।

## क्लाउडसम्बन्धी समस्याहरू

### क्लाउड सिंक त्रुटिहरू

1. `BASE_URL` ले चलिरहेको तपाईंको इन्स्ट्यान्सलाई जनाउँछ भन्ने पुष्टि गर्नुहोस् (जस्तै, `http://localhost:20128`)
2. `CLOUD_URL` ले तपाईंको क्लाउड एन्डपोइन्टलाई जनाउँछ भन्ने पुष्टि गर्नुहोस् (जस्तै, `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` का मानहरूलाई सर्भर-साइड मानहरूसँग मिल्दो राख्नुहोस्

### क्लाउडमा `stream=false` ले 500 फर्काउँछ

**लक्षण:** नन-स्ट्रिमिङ कलहरूका लागि क्लाउड एन्डपोइन्टमा `Unexpected token 'd'...`।

**कारण:** क्लाइन्टले JSON अपेक्षा गर्दा अपस्ट्रिमले SSE पेलोड फर्काउँछ।

**अस्थायी समाधान:** क्लाउडमा प्रत्यक्ष कलहरूका लागि `stream=true` प्रयोग गर्नुहोस्। स्थानीय रनटाइममा SSE→JSON फलब्याक समावेश छ।

### क्लाउडले जडान भएको देखाउँछ तर "अमान्य API कुञ्जी" भन्छ

1. स्थानीय ड्यासबोर्ड (`/api/keys`) बाट नयाँ कुञ्जी सिर्जना गर्नुहोस्
2. क्लाउड सिंक चलाउनुहोस्: क्लाउड सक्षम गर्नुहोस् → अहिले सिंक गर्नुहोस्
3. पुराना/सिंक नगरिएका कुञ्जीहरूले क्लाउडमा अझै पनि `401` फर्काउन सक्छन्

## Docker सम्बन्धी समस्याहरू

### Docker IPv6 / जडान रिसेट

<a name="docker-ipv6"></a>

**लक्षणहरू:** `curl http://localhost:20128/v1/models` ले `curl: (56) Recv failure: Connection reset by peer` फर्काउँछ। ड्यासबोर्ड र प्रमाणीकरण आवश्यक नपर्ने एन्डपोइन्टहरूले काम गर्छन्, तर प्रमाणीकरण आवश्यक पर्ने एन्डपोइन्टहरू असफल हुन्छन् — यो प्रमाणीकरणको समस्या जस्तो देखिन्छ, तर वास्तवमा होइन।

**कारण:** `docker run -p 20128:20128` ले `0.0.0.0` (IPv4) र `::` (IPv6) दुवैमा प्रकाशन गर्छ, तर कन्टेनरभित्रको प्रक्रियाले IPv4 मा मात्र सुन्छ। `localhost` पहिले `::1` मा रिजोल्भ हुने होस्टहरूमा, जडान IPv6 मा प्रकाशित पोर्टमा पुग्छ जहाँ त्यसको पछाडि कुनै लिसनर हुँदैन → जडान रिसेट हुन्छ।

**समाधान:**

1. **द्रुत निदान:** `curl -4 http://localhost:20128/v1/models` चलाउनुहोस्। यदि यसले `-4` सहित काम गर्छ तर त्यसबिना असफल हुन्छ भने, तपाईंसँग IPv6 बाइन्ड नमिल्ने समस्या छ।
2. **स्थायी समाधान:** तपाईंको `docker run` कमान्डमा `-p 127.0.0.1:20128:20128` प्रयोग गरेर स्पष्ट रूपमा IPv4 मा बाइन्ड गर्नुहोस्:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   यसले IPv4 बाइन्ड बाध्यकारी बनाउँछ र सबै होस्ट इन्टरफेसहरूमा प्रोक्सी एक्सपोज हुनबाट पनि रोक्छ।

## डिबगिङ

### लग फाइलहरू सक्षम गर्नुहोस्

तपाईंको `.env` फाइलमा `APP_LOG_TO_FILE=true` सेट गर्नुहोस्। एप्लिकेसन लगहरू `logs/` अन्तर्गत लेखिन्छन्।
सेटिङहरूमा कल लग पाइपलाइन सक्षम हुँदा अनुरोधका आर्टिफ्याक्टहरू `${DATA_DIR}/call_logs/` अन्तर्गत भण्डारण हुन्छन्।
पाइपलाइन क्याप्चर सक्षम हुँदा, स्ट्रिम चङ्क पेलोडहरू हटाउन `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` सेट गर्नुहोस्, वा KB मा आर्टिफ्याक्ट सीमा परिवर्तन गर्न `CALL_LOG_PIPELINE_MAX_SIZE_KB` समायोजन गर्नुहोस्।

### प्रदायकको स्वास्थ्य जाँच गर्नुहोस्

```bash
# स्वास्थ्य ड्यासबोर्ड
http://localhost:20128/dashboard/health

# API स्वास्थ्य जाँच
curl http://localhost:20128/api/monitoring/health
```

### रनटाइम भण्डारण

- मुख्य अवस्था: `${DATA_DIR}/storage.sqlite` (प्रदायकहरू, कम्बोहरू, एलियासहरू, कुञ्जीहरू, सेटिङहरू)
- प्रयोग: `storage.sqlite` मा रहेका SQLite तालिकाहरू (`usage_history`, `call_logs`, `proxy_logs`) + वैकल्पिक `${DATA_DIR}/call_logs/`
- एप्लिकेसन लगहरू: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` हुँदा)
- कल लग आर्टिफ्याक्टहरू: कल लग पाइपलाइन सक्षम हुँदा `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

अनुरोध लग पृष्ठको **इतिहास सफा गर्नुहोस्** कार्यले `call_logs`, पुरानो
`request_detail_logs`, र स्थानीय `${DATA_DIR}/call_logs/` आर्टिफ्याक्ट डाइरेक्टरी खाली गर्छ।

## सर्किट ब्रेकरसम्बन्धी समस्याहरू

### प्रदायक OPEN अवस्थामा अड्किएको छ

प्रदायकको सर्किट ब्रेकर OPEN हुँदा, कूलडाउन समाप्त नभएसम्म अनुरोधहरू रोकिएका हुन्छन्।

**समाधान:**

1. **ड्यासबोर्ड → सेटिङहरू → रेजिलियन्स** मा जानुहोस्
2. प्रभावित प्रदायकको सर्किट ब्रेकर कार्ड जाँच गर्नुहोस्
3. सबै ब्रेकरहरू खाली गर्न **सबै रिसेट गर्नुहोस्** मा क्लिक गर्नुहोस्, वा कूलडाउन समाप्त नहुँदासम्म पर्खनुहोस्
4. रिसेट गर्नुअघि प्रदायक वास्तवमै उपलब्ध छ भनी पुष्टि गर्नुहोस्

### प्रदायकले बारम्बार सर्किट ब्रेकर ट्रिप गराउँछ

यदि कुनै प्रदायक बारम्बार OPEN अवस्थामा प्रवेश गर्छ भने:

1. विफलताको ढाँचा हेर्न **ड्यासबोर्ड → स्वास्थ्य → प्रदायकको स्वास्थ्य** जाँच गर्नुहोस्
2. **सेटिङहरू → रेजिलियन्स → प्रदायक प्रोफाइलहरू** मा जानुहोस् र विफलताको सीमा बढाउनुहोस्
3. प्रदायकले API सीमाहरू परिवर्तन गरेको छ वा पुनः प्रमाणीकरण आवश्यक छ कि छैन जाँच गर्नुहोस्
4. विलम्बता टेलिमेट्री समीक्षा गर्नुहोस् — उच्च विलम्बताले टाइमआउटमा आधारित विफलताहरू निम्त्याउन सक्छ

### ढाँचासम्बन्धी सामान्य समस्याहरू

- **थिङ्किङ ट्यागहरू नदेखिने** — लक्षित प्रदायकले थिङ्किङ समर्थन गर्छ कि गर्दैन र थिङ्किङ बजेट सेटिङ जाँच गर्नुहोस्
- **टुल कलहरू हराउने** — केही ढाँचा अनुवादहरूले असमर्थित फिल्डहरू हटाउन सक्छन्; प्लेग्राउन्ड मोडमा पुष्टि गर्नुहोस्
- **सिस्टम प्रम्प्ट हराएको** — Claude र Gemini ले सिस्टम प्रम्प्टहरू फरक तरिकाले व्यवस्थापन गर्छन्; अनुवाद आउटपुट जाँच गर्नुहोस्
- **SDK ले वस्तुको सट्टा कच्चा स्ट्रिङ फर्काउँछ** — v1.x मा समाधान गरिएको छ; प्रतिक्रिया स्यानिटाइजरले OpenAI SDK Pydantic प्रमाणीकरण विफल गराउने गैर-मानक फिल्डहरू (`x_groq`, `usage_breakdown`, आदि) हटाउँछ। यदि तपाईंले अझै पनि v3.x+ मा यो देख्नुभयो भने, कृपया एउटा समस्या दर्ता गर्नुहोस्।
- **GLM/ERNIE ले `system` भूमिका अस्वीकार गर्छ** — v1.x मा समाधान गरिएको छ; भूमिका नर्मलाइजरले असङ्गत मोडेलहरूका लागि सिस्टम सन्देशहरू स्वचालित रूपमा प्रयोगकर्ता सन्देशहरूमा मर्ज गर्छ। यदि तपाईंले अझै पनि v3.x+ मा यो देख्नुभयो भने, कृपया एउटा समस्या दर्ता गर्नुहोस्।
- **`developer` भूमिका पहिचान भएन** — v1.x मा समाधान गरिएको छ; गैर-OpenAI प्रदायकहरूका लागि स्वचालित रूपमा `system` मा रूपान्तरण गरिन्छ। यदि तपाईंले अझै पनि v3.x+ मा यो देख्नुभयो भने, कृपया एउटा समस्या दर्ता गर्नुहोस्।
- **`json_schema` ले Gemini सँग काम नगर्ने** — v1.x मा समाधान गरिएको छ; `response_format` अब Gemini को `responseMimeType` + `responseSchema` मा रूपान्तरण गरिन्छ। यदि तपाईंले अझै पनि v3.x+ मा यो देख्नुभयो भने, कृपया एउटा समस्या दर्ता गर्नुहोस्।

## लचिलोपन सेटिङहरू

### स्वतः दर-सीमा ट्रिगर नहुनु

- स्वतः दर-सीमा API कुञ्जी प्रदायकहरूमा मात्र लागू हुन्छ (OAuth/सदस्यतामा होइन)
- **Settings → Resilience → Provider Profiles** मा स्वतः दर-सीमा सक्षम गरिएको छ भनी पुष्टि गर्नुहोस्
- प्रदायकले `429` स्थिति कोड वा `Retry-After` हेडरहरू फर्काउँछ कि जाँच गर्नुहोस्

### एक्सपोनेन्सियल ब्याकअफ समायोजन

प्रदायक प्रोफाइलहरूले यी सेटिङहरू समर्थन गर्छन्:

- **आधारभूत विलम्ब** — पहिलो विफलतापछिको प्रारम्भिक प्रतीक्षा समय (पूर्वनिर्धारित: 1s)
- **अधिकतम विलम्ब** — प्रतीक्षा समयको अधिकतम सीमा (पूर्वनिर्धारित: 30s)
- **गुणक** — प्रत्येक लगातार विफलतामा विलम्ब कति बढाउने (पूर्वनिर्धारित: 2x)

### थन्डरिङ हर्ड रोकथाम

धेरै समवर्ती अनुरोधहरू दर-सीमित प्रदायकमा पुग्दा, OmniRoute ले अनुरोधहरूलाई क्रमबद्ध गर्न र शृङ्खलाबद्ध विफलताहरू रोक्न mutex + स्वतः दर-सीमा प्रयोग गर्छ। API कुञ्जी प्रदायकहरूका लागि यो स्वचालित हुन्छ।

### च्याट अनुरोधहरू 503 / chat_admission_busy का साथ विफल हुन्छन्

**लक्षणहरू:**

- च्याट कम्प्लिसन एन्डपोइन्टले पुनः प्रयास गर्न मिल्ने `503` प्रतिक्रिया फर्काउँछ, जसको त्रुटि कोड
  `chat_admission_busy` हुन्छ।
- प्रतिक्रियामा `Retry-After` समावेश हुन्छ। #12135 देखि यसको मान अवलोकन गरिएको
  अकुपेन्सीबाट निर्धारण गरिन्छ — अनुरोधले पहिल्यै प्रतीक्षा गरेको `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  विन्डो र हालका हेभीवेट लिजहरू कायम रहेको समयमध्ये ठूलो मान — पूरा
  सेकेन्डमा माथितिर राउन्ड गरी अधिकतम 60 मा सीमित गरिन्छ। निष्क्रिय गेटमा यसले ऐतिहासिक न्यूनतमहरू कायम राख्छ:
  बाइट-आधारित पथमा 2 सेकेन्ड, संरचना-आधारित पथमा 1 सेकेन्ड (जसमा
  `reason: "structure_limit"` पनि समावेश हुन्छ)।
- अर्को हेभीवेट च्याट वा लामो समय चल्ने स्ट्रिमिङ प्रतिक्रिया अझै
  प्रक्रियामै हुँदा यस्तो हुन सक्छ।

बाइट-आधारित प्रतिक्रियाको बडी यस्तो हुन्छ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

संरचना-आधारित प्रतिक्रियाले उही प्रकार र कोड प्रयोग गर्छ, सन्देश
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
र `reason: "structure_limit"` सहित।
पूर्वनिर्धारित थ्रेसहोल्डहरूमा, अनुरोधमा कम्तीमा `200` सन्देश,
कम्तीमा `64` उपकरण, वा कम्तीमा `32,000` अनुमानित टोकन भएमा, वा सीमित संरचना अनुमानले
`10,000` भ्रमण गरिएका नोड वा गहिराइ `12` को सीमा समाप्त गरेमा, त्यो अनुरोध संरचनात्मक रूपमा भारी हुन्छ।

**कारण:** यो OmniRoute भित्र जानाजानी गरिएको लोड न्यूनीकरण हो, अपस्ट्रिम-प्रदायकको विफलता होइन।
प्रत्येक प्रक्रियाले ठूलो अनुरोध बडी राख्न र पार्स गर्नुअघि सीमित हेभीवेट क्षमता आरक्षित गर्न
प्रक्रिया-स्थानीय गार्ड प्रयोग गर्छ। SSE प्रतिक्रियाको सम्पूर्ण जीवनकालभरि हेभीवेट लिज
कायम रहन्छ।

**#503-फ्यानआउट:** यो सुधारअघि, गार्डले होस्ट मेमोरीलाई बेवास्ता गरी समवर्तितालाई निश्चित अनुरोध सङ्ख्यामा
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, पूर्वनिर्धारित `1`) सीमित गर्थ्यो, त्यसैले कोडिङ-एजेन्ट
फ्यानआउट (धेरै सबएजेन्ट/CLI, नियमित रूपमा > 256 KB का बडीहरू) प्रभावकारी
समवर्तिता ~1 मा झर्थ्यो र पूर्ण रूपमा सामान्य लोडमै 503 त्रुटि दिन्थ्यो। अब गार्ड स्वयं-समायोजित हुन्छ: यसलाई
प्रक्रियाको वास्तविक मेमोरी सीमाअनुसार आकार निर्धारण गरिएको स्वतः-व्युत्पन्न इन्जेस्ट बाइट बजेट
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ले नियन्त्रण गर्छ, र यसले प्रत्यक्ष स्रोत-दबाब सङ्केतलाई पनि
हेर्छ — त्यसैले एकैपटक एकभन्दा बढी भारी अनुरोध आएको कारणले मात्र होइन, होस्ट वास्तवमै मेमोरी
दबाबमा हुँदा मात्र यसले लोड घटाउँछ। पुरानो सङ्ख्या सीमा (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) अझै
पालना गरिन्छ, तर तपाईंले यसलाई स्पष्ट रूपमा सेट गर्नुभएको अवस्थामा मात्र।

क्षमता व्यस्त हुँदा, हेभीवेट अनुरोधले पुनः प्रयास गर्न मिल्ने `503` प्रतिक्रिया दिनुअघि
स्लट खाली होस् भनेर पहिले अधिकतम
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` सम्म प्रतीक्षा गर्छ (पूर्वनिर्धारित मान `RATE_LIMIT_MAX_WAIT_MS`; `0` ले प्रतीक्षा निष्क्रिय गर्छ)।
यो सीमित प्रतीक्षा राखिएको हो ताकि भारी उप-अनुरोधहरू समवर्ती रूपमा फ्यानआउट गर्ने एजेन्ट-शैलीका क्लाइन्टहरू
(OpenCode, Claude Code, Cursor) ले तुरुन्त अस्वीकृतिहरूमा आफ्नो सम्पूर्ण पुनः प्रयास बजेट खर्च गरेर
कार्यको बीचमै विफल हुनुको सट्टा बर्स्टलाई क्रमबद्ध गर्न सकून्।
हालको हेभीवेट लिज अकुपेन्सी, निर्धारित बाइट बजेट, र प्रत्यक्ष दबाबको गम्भीरता
`GET /api/monitoring/health` → `chatAdmission` मा देखाइन्छ (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — कुनै पनि env var परिवर्तन गर्नुअघि यी जाँच गर्नुहोस्।
Settings → Resilience → Request Queue → Concurrent Requests ले यसलाई नियन्त्रण गर्दैन; त्यो सेटिङले
अलग प्रदायक अनुरोध-कतार संयन्त्र नियन्त्रण गर्छ।

**समाधान:**

1. पहिले पुनः प्रयास गर्नुहोस्। क्लाइन्टहरूले अनुरोध तुरुन्तै
   दोहोर्याउनुको सट्टा `Retry-After` पालना गर्नुपर्छ र ब्याकअफ प्रयोग गर्नुपर्छ।
2. कुनै पनि कुरा समायोजन गर्नुअघि `/api/monitoring/health` → `chatAdmission` जाँच गर्नुहोस्। `countCapEnabled:
false` र पर्याप्त ठूलो `maxInflightBytes` को अर्थ स्वतः-व्युत्पन्न बजेटले आफ्नो
   काम पहिल्यै गरिरहेको छ; `high`/`critical` को `pressureSeverity` को अर्थ होस्टमा वास्तवमै मेमोरी कम छ —
   यसलाई एडमिसन env var द्वारा समाधान गर्न सकिँदैन; थप RAM वा सानो वर्कलोड आवश्यक हुन्छ।
3. `/api/monitoring/health` ले स्वतः-व्युत्पन्न बजेट तपाईंको होस्टका लागि वास्तवमै धेरै सानो भएको
   देखाएमा मात्र (यो दुर्लभ हो — यो कन्टेनरदेखि बेयर-मेटलसम्म पहिल्यै स्केल हुन्छ), पुरानो अनुरोध-सङ्ख्या सीमामा
   फर्किनुको सट्टा `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` मार्फत यसलाई सिधै ओभरराइड गर्नुहोस्।

आधिकारिक एडमिसन सेटिङहरूका लागि [वातावरण-चल सन्दर्भ](../reference/ENVIRONMENT.md#4-security--authentication)
हेर्नुहोस्।

## वैकल्पिक RAG / LLM विफलता वर्गीकरण (१६ समस्याहरू)

केही OmniRoute प्रयोगकर्ताहरूले गेटवेलाई RAG वा एजेन्ट स्ट्याकहरूको अगाडि राख्छन्। त्यस्ता सेटअपहरूमा एउटा अनौठो ढाँचा देखिनु सामान्य हो: OmniRoute स्वस्थ देखिन्छ (प्रदायकहरू सञ्चालनमा छन्, राउटिङ प्रोफाइलहरू ठीक छन्, दर-सीमा चेतावनीहरू छैनन्) तर अन्तिम उत्तर अझै पनि गलत हुन्छ।

व्यवहारमा यी घटनाहरू सामान्यतया गेटवेबाट नभई डाउनस्ट्रिम RAG पाइपलाइनबाट उत्पन्न हुन्छन्।

यदि तपाईं ती विफलताहरू वर्णन गर्न साझा शब्दावली चाहनुहुन्छ भने, तपाईं WFGY ProblemMap प्रयोग गर्न सक्नुहुन्छ। यो बाह्य MIT इजाजतपत्रअन्तर्गतको पाठ स्रोत हो, जसले बारम्बार देखिने सोह्रवटा RAG / LLM विफलता ढाँचाहरू परिभाषित गर्छ। उच्च स्तरमा यसले निम्न विषयहरू समेट्छ:

- पुनर्प्राप्ति विचलन र बिग्रिएका सन्दर्भ सीमाहरू
- खाली वा पुराना इन्डेक्स तथा भेक्टर स्टोरहरू
- एम्बेडिङ र अर्थगत आशयबीचको बेमेल
- प्रम्प्ट संयोजन र सन्दर्भ विन्डोसम्बन्धी समस्याहरू
- तार्किक पतन र अत्यधिक आत्मविश्वासी उत्तरहरू
- लामो शृङ्खला र एजेन्ट समन्वयका विफलताहरू
- बहु-एजेन्ट मेमोरी र भूमिका विचलन
- डिप्लोयमेन्ट र बुटस्ट्र्याप क्रमसम्बन्धी समस्याहरू

विचार सरल छ:

1. खराब प्रतिक्रियाको अनुसन्धान गर्दा निम्न कुरा सुरक्षित गर्नुहोस्:
   - प्रयोगकर्ताको कार्य र अनुरोध
   - OmniRoute मा प्रयोग भएको रुट वा प्रदायक संयोजन
   - डाउनस्ट्रिममा प्रयोग गरिएको कुनै पनि RAG सन्दर्भ (पुनर्प्राप्त गरिएका कागजातहरू, टुल कलहरू आदि)
2. घटनालाई एक वा दुईवटा WFGY ProblemMap नम्बर (`No.1` … `No.16`) सँग मिलाउनुहोस्।
3. OmniRoute लगहरूको छेउमा रहेको आफ्नो ड्यासबोर्ड, रनबुक वा घटना ट्र्याकरमा उक्त नम्बर भण्डारण गर्नुहोस्।
4. आफ्नो RAG स्ट्याक, रिट्रिभर वा राउटिङ रणनीति परिवर्तन गर्नुपर्ने हो कि होइन भन्ने निर्णय गर्न सम्बन्धित WFGY पृष्ठ प्रयोग गर्नुहोस्।

पूर्ण पाठ र ठोस विधिहरू यहाँ उपलब्ध छन् (MIT इजाजतपत्र, पाठ मात्र):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

यदि तपाईं OmniRoute पछाडि RAG वा एजेन्ट पाइपलाइनहरू चलाउनुहुन्न भने, यो खण्ड बेवास्ता गर्न सक्नुहुन्छ।

## v3.8.0 का ज्ञात समस्याहरू

v3.8.0 रिलिजसँग सम्बन्धित समस्याहरू र तिनका हालका वैकल्पिक समाधानहरू। यदि पछिल्लो प्याचमा समाधान समावेश भयो भने, प्रविष्टि अद्यावधिक गरिनेछ वा हटाइनेछ।

### Devin CLI प्रमाणीकरण विफलताहरू

**लक्षणहरू:**

- Devin-समर्थित टुलहरू चलाउँदा "Devin CLI फेला परेन" वा "प्रमाणीकरण विफल भयो"
- CLI रनटाइम जाँचले `installed=false` देखाउँछ

**कारणहरू:**

- `CLI_DEVIN_BIN` ले अस्तित्वमा नभएको पाथलाई जनाउँछ
- होस्टमा Devin CLI इन्स्टल गरिएको छैन

**समाधान:**

1. आफ्नो प्लेटफर्मका लागि Devin CLI इन्स्टल गर्नुहोस्
2. `.env` मा `CLI_DEVIN_BIN=/usr/local/bin/devin` (वा वास्तविक पाथ) सेट गर्नुहोस्
3. OmniRoute पुनः सुरु गर्नुहोस् र **ड्यासबोर्ड → CLI टुलहरू** बाट पुनः परीक्षण गर्नुहोस्

### मोडेल कुलडाउन अड्किएको (म्यानुअल रिसेट)

**लक्षणहरू:**

- म्याद सकिने समय बितिसकेपछि पनि मोडेल कुलडाउनमा सूचीकृत रहन्छ
- टाइमस्ट्याम्प विगतमा हुँदासमेत संयोजन राउटिङका अनुरोधहरूले मोडेललाई अझै छोड्छन्

**म्यानुअल रिसेट:**

- **ड्यासबोर्ड:** **सेटिङहरू → मोडेल कुलडाउनहरू** → प्रभावित कार्डमा **पुनः सक्षम गर्नुहोस्** क्लिक गर्नुहोस्
- **API:** व्यवस्थापन प्रमाणीकरण हेडरहरूसहित `DELETE /api/resilience/model-cooldowns`

### Command Code प्रदायकको जडान 403 सहित विफल हुन्छ

**लक्षणहरू:**

- Command Code प्रदायकको जडान परीक्षण गर्दा 403
- नयाँ रूपमा थपेपछि प्रदायक कार्डले "अनधिकृत" देखाउँछ

**कारण:** OAuth प्रवाह पूरा भएन (कल्ब्याक प्राप्त भएन वा टोकन सुरक्षित भएन)।

**समाधान:**

- OAuth प्रवाह पुनः ट्रिगर गर्न CLI बाट `omniroute providers` चलाउनुहोस्, वा
- **ड्यासबोर्ड → प्रदायकहरू → Command Code → पुनः जडान गर्नुहोस्** बाट OAuth पुनः चलाउनुहोस्

### ModelScope ले आक्रामक 429 कुलडाउनहरू फर्काउँछ

**लक्षणहरू:**

- अनुरोधहरूको सानो बर्स्टपछि ModelScope मा अत्यन्त छोटो वा तत्काल कुलडाउनहरू
- संयोजन राउटिङले अपेक्षाभन्दा चाँडो ModelScope लाई छोड्छ

**कारण:** ModelScope ले प्रदायक-विशिष्ट `Retry-After` हेडरहरू उत्सर्जन गर्छ। v3.8.0 मा ती हेडरहरूका लागि समर्पित ह्यान्डलिङ समावेश छ, त्यसैले पुराना संस्करणहरूले तिनलाई सामान्य दर-सीमा सङ्केतका रूपमा गलत बुझ्छन्।

**समाधान:**

- तपाईं v3.8.0 वा त्यसपछिको संस्करणमा हुनुहुन्छ भन्ने सुनिश्चित गर्नुहोस्
- **सेटिङहरू → रेजिलिएन्स** अन्तर्गत `useUpstream429BreakerHints` टगल सक्षम छ भनी प्रमाणित गर्नुहोस्

### उत्पादनमा OMNIROUTE_WS_BRIDGE_SECRET हराइरहेको छ

**लक्षणहरू:**

- रिमोट उत्पादन होस्टमा चलाउँदा प्रत्येक Codex/Responses WebSocket ब्रिज अनुरोधमा 401
- जडान भएपछि WebSocket ब्रिज ह्यान्डशेक तुरुन्तै बन्द हुन्छ

**कारण:** उत्पादन वातावरणमा `OMNIROUTE_WS_BRIDGE_SECRET` env var छैन।

**समाधान:**

1. एउटा अनियमित गोप्य मान उत्पन्न गर्नुहोस्: `openssl rand -hex 32`
2. उत्पादन सर्भरको env मा (र ब्रिजसँग सञ्चार गर्ने कुनै पनि क्लाइन्टमा) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` सेट गर्नुहोस्
3. OmniRoute पुनः सुरु गर्नुहोस्

### Responses API: पृष्ठभूमि मोडलाई सिंक्रोनसमा सीमित गरिएको छ

**लक्षणहरू:**

- लग गरिएको चेतावनी: `background mode degraded to synchronous`
- `background: true` अनुरोधले पृष्ठभूमि जब ह्यान्डलको सट्टा सामान्य सिंक्रोनस प्रतिक्रिया फर्काउँछ

**कारण:** v3.8.0 ले चेतावनी उत्सर्जन गर्दै Responses API मा `background: true` लाई जानाजानी सिंक्रोनस कार्यान्वयनमा सीमित गर्छ। पूर्ण असिंक्रोनस पृष्ठभूमि कार्यान्वयन भविष्यमा उपलब्ध गराइनेछ।

**समाधान:**

- `background` बिना कल गर्न क्लाइन्ट समायोजन गर्नुहोस्, वा
- पूर्ण असिंक्रोनस पृष्ठभूमि मोड समावेश भएको पछिल्लो रिलिजको प्रतीक्षा गर्नुहोस् (चेन्जलग पछ्याउनुहोस्)

## ढिलो स्टार्टअप / तयारी टाइमआउट

यदि CLI ले `⚠ Server did not respond within 60s` प्रिन्ट गर्छ तर सर्भरले
वास्तवमा काम गरिरहेको छ भने, तपाईंको वातावरणका लागि तयारी जाँचको समयसीमा निकै छोटो छ।

यो प्रायः Windows (एन्टिभाइरस, फाइलसिस्टम वाचरहरू) वा धेरै स्टार्टअप कार्यभार
भएका कन्टेनरहरूमा हुन्छ।

**समाधान — समयसीमा बढाउनुहोस्:**

```bash
# वातावरणीय भेरिएबलमार्फत (स्टार्टहरूबीच कायम रहन्छ):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 मिनेट
omniroute serve

# CLI फ्ल्यागमार्फत (एक पटकका लागि):
omniroute serve --ready-timeout 180000
```

पूर्वनिर्धारित मान 60 000 ms (60 s) हो। चेतावनी जानकारीमूलक मात्र हो; सर्भर
पृष्ठभूमिमा सुरु भइरहन्छ र बुट पूरा भएपछि पहुँचयोग्य हुनेछ।

`OMNIROUTE_READY_TIMEOUT_MS` सम्बन्धी पूर्ण विवरणका लागि
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) हेर्नुहोस्।
