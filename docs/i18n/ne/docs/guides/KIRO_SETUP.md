यो मार्गदर्शिकाले OmniRoute मा Kiro (AWS द्वारा होस्ट गरिएको AI कोडिङ सहायक) खाताहरू थप्ने प्रक्रिया समेट्छ,
विशेषगरी सेसन द्वन्द्वबिना एकैसाथ धेरै खाताहरू चलाउने कुरामा केन्द्रित हुँदै।

---

## पृष्ठभूमि: Kiro खाताहरू किन द्वन्द्वमा पर्न सक्छन्

Kiro को ब्याकएन्डले सक्रिय सेसनहरू ट्र्याक गर्न AWS SSO OIDC क्लाइन्ट दर्ताहरू प्रयोग गर्छ।
महत्त्वपूर्ण सीमितता: **प्रत्येक OIDC क्लाइन्ट दर्ताले एक पटकमा एउटा सक्रिय
सेसनलाई मात्र समर्थन गर्छ**। जब दोस्रो उपकरण वा प्रयोगकर्ताले उही
दर्ता गरिएको क्लाइन्ट प्रयोग गरेर प्रमाणीकरण गर्छ, ब्याकएन्डले पहिलो खाताको रिफ्रेस टोकन अमान्य बनाउँछ।

अर्को Kiro खाता पहिले नै साइन इन भएको मेसिनमा `kiro-cli login` चलाउँदा
समस्या निम्त्याउने संयन्त्र पनि यही हो — नयाँ लगइनले
पहिलो खाताको टोकन रद्द गर्छ।

## OmniRoute ले यसलाई कसरी समाधान गर्छ (v3.8.0+)

v3.8.0 देखि, OmniRoute ले प्रत्येक
Kiro जडान आयातका क्रममा `registerClient()` (AWS SSO OIDC) कल गर्छ। यसले प्रत्येक OmniRoute जडानलाई आफ्नै समर्पित OIDC
क्लाइन्ट दर्ता प्रदान गर्छ। प्रत्येक क्लाइन्ट दर्ता स्वतन्त्र हुने भएकाले, एउटा खाता रिफ्रेस वा
पुनः प्रमाणीकरण गर्दा अन्य कुनै खाताको रिफ्रेस टोकनमा असर पर्दैन।

यो पृथकीकरण रिफ्रेस-टोकन आयात विधिहरूमा लागू हुन्छ, र API-key प्रमाणीकरणले
OIDC रिफ्रेस सेसनहरूलाई पूर्ण रूपमा बेवास्ता गर्छ:

| आयात विधि                                           | पृथकीकरण स्थिति                                                                        |
| --------------------------------------------------- | -------------------------------------------------------------------------------------- |
| AWS Builder ID / IDC डिभाइस-कोड प्रवाह              | डिभाइस-कोड प्रवाह प्रस्तुत गरिएदेखि पृथक्                                              |
| **टोकन आयात** (रिफ्रेस टोकन म्यानुअल रूपमा टाँस्ने) | v3.8.0 देखि पृथक्                                                                      |
| **Google / GitHub सामाजिक लगइन**                    | v3.8.0 देखि पृथक्                                                                      |
| **स्वतः आयात** (kiro-cli SQLite)                    | v3.8.0 देखि पृथक् (SQLite मार्ग पहिले नै पृथक् थियो; SSO-cache फलब्याक पनि अब पृथक् छ) |
| **API Key** (दीर्घकालीन CodeWhisperer कुञ्जी)       | रिफ्रेस सेसन हुँदैन; कुञ्जी प्रमाणीकरण गरी bearer क्रेडेन्सियलका रूपमा भण्डारण गरिन्छ  |

## v3.8.0 अघि सिर्जना गरिएका जडानहरूका लागि माइग्रेसन टिप्पणी

v3.8.0 अघि आयात गरिएका जडानहरूमा `providerSpecificData` भित्र
समर्पित OIDC क्लाइन्ट दर्ता भण्डारण गरिएको हुँदैन। यी जडानहरूले काम गरिरहन्छन् तर साझा
सामाजिक-प्रमाणीकरण रिफ्रेस इन्डपोइन्ट प्रयोग गर्छन्, जसको अर्थ यस्ता दुई जडानले अझै पनि एकअर्कालाई
अमान्य बनाउन सक्छन्।

**पृथकीकरण प्राप्त गर्न:** पुरानो जडानलाई **ड्यासबोर्ड → प्रदायकहरू** बाट मेटाउनुहोस् र
समर्थित कुनै पनि आयात प्रवाह प्रयोग गरेर पुनः आयात गर्नुहोस्। नयाँ सिर्जना गरिएका सबै जडानहरूले
स्वचालित रूपमा आफ्नै क्लाइन्ट दर्ता प्राप्त गर्नेछन्।

## दुई Kiro खाताहरू सँगसँगै थप्ने

### पूर्वापेक्षाहरू

- OmniRoute v3.8.0 वा पछिल्लो संस्करण।
- काम गरिरहेको Kiro खाता (इमेल + पासवर्ड, Google, वा GitHub लगइन)।
- वैकल्पिक रूपमा दोस्रो Kiro खाता।

### चरण 1: पहिलो खाता आयात गर्नुहोस्

1. **ड्यासबोर्ड → प्रदायकहरू → प्रदायक थप्नुहोस् → Kiro** खोल्नुहोस्।
2. निम्नमध्ये एउटा छान्नुहोस्:
   - **टोकन आयात** — `aorAAAAAG` बाट सुरु हुने रिफ्रेस टोकन टाँस्नुहोस्।
   - **API Key** — दीर्घकालीन Kiro / CodeWhisperer API कुञ्जी टाँस्नुहोस्।
   - **Google / GitHub लगइन** — ब्राउजरमा OAuth प्रवाह पूरा गर्नुहोस्।
   - **स्वतः आयात** — बटन क्लिक गर्नुहोस्; OmniRoute ले स्थानीय kiro-cli डेटाबेस वा
     `~/.aws/sso/cache` बाट क्रेडेन्सियलहरू पढ्छ।
3. जडान सुरक्षित हुन्छ। रिफ्रेस-टोकन प्रवाहहरूले स्वचालित रूपमा समर्पित
   OIDC क्लाइन्ट दर्ता गर्छन्। API-key प्रवाहहरूले AWS मार्फत कुञ्जी प्रमाणीकरण गर्छन् र रिफ्रेस टोकन भण्डारण गर्दैनन्।

### चरण 2: दोस्रो खाता आयात गर्नुहोस्

दोस्रो खाताका लागि चरण 1 दोहोर्याउनुहोस्। प्रत्येक आयातले छुट्टै OIDC
क्लाइन्ट दर्ता सिर्जना गर्ने भएकाले, दुई जडानहरू पूर्ण रूपमा पृथक् हुन्छन्।

### चरण 3: दुवै जडान सक्रिय छन् भनी प्रमाणित गर्नुहोस्

1. **ड्यासबोर्ड → प्रदायकहरू** — दुवै Kiro जडानले **सक्रिय** स्थिति देखाउनुपर्छ।
2. **ड्यासबोर्ड → स्वास्थ्य** — दुवै जडान आफ्नो टोकन स्वास्थ्य जाँचमा सफल हुनुपर्छ।

### चरण 4: खाताहरूबीच रुट गर्न कम्बो प्रयोग गर्नुहोस्

लोड-ब्यालेन्स गर्न वा एउटाबाट अर्कोमा फलब्याक गर्न दुवै जडानलाई लक्ष्यका रूपमा राखेर कम्बो सिर्जना गर्नुहोस्:

```
kiro/kiro-dev → kiro/kiro-pro
```

कम्बो कन्फिगरेसनका लागि [FEATURES.md](./FEATURES.md) र रुटिङ दस्तावेज हेर्नुहोस्।

## Enterprise / IDC प्रयोगकर्ताहरू

AWS IAM Identity Center (IDC) खाताहरूका लागि, **Dashboard → Providers → Kiro → Device Code** बाट **AWS Builder ID / IDC device-code** प्रवाह प्रयोग गर्नुहोस्। device-code प्रवाह सधैँ पूर्ण रूपमा पृथक रहँदै आएको छ। यी जडानहरूका लागि पुनः आयात आवश्यक छैन।

गैर-पूर्वनिर्धारित AWS क्षेत्रमा सञ्चालन गर्ने Enterprise प्रयोगकर्ताहरूले Import Token API मार्फत आयात गर्दा क्षेत्र निर्दिष्ट गर्न सक्छन्:

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

`region` नदिइएमा यसको पूर्वनिर्धारित मान `us-east-1` हुन्छ।

## API-Key आयात प्रवाह

API-key प्रमाणीकरण दीर्घकालीन Kiro / AWS CodeWhisperer bearer प्रमाणहरूका लागि हो। यसले OAuth refresh प्रयोग गर्दैन, त्यसैले साझा OIDC session अमान्य हुने समस्याबाट जोगिन्छ।

### Dashboard

1. **Dashboard -> Providers -> Kiro** खोल्नुहोस्।
2. **API Key** चयन गर्नुहोस्।
3. API key र वैकल्पिक AWS region टाँस्नुहोस् (पूर्वनिर्धारित रूपमा `us-east-1`)।
4. OmniRoute ले key प्रमाणीकरण गर्छ र जडान सुरक्षित गर्छ।

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### आन्तरिक सम्झौता

API route ले `KiroService.validateApiKey()` कल गरेर key प्रमाणीकरण गर्छ, जसले क्षेत्रसँग मेल खाने CodeWhisperer/Amazon Q endpoint मा `ListAvailableProfiles` प्रयोग गर्छ र एउटा `profileArn` निर्धारण गर्छ।

सुरक्षित गरिएको जडानले निम्न प्रयोग गर्छ:

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

runtime मा, `KiroExecutor.buildHeaders()` ले key लाई `Authorization: Bearer <key>` का रूपमा पठाउँछ र `tokentype: API_KEY` थप्छ। Quota/profile कलहरूले पनि उही marker प्रयोग गर्छन्, जसले गर्दा AWS ले bearer लाई OIDC वा social access token का सट्टा दीर्घकालीन API key का रूपमा व्यवहार गर्छ।

## OIDC Client को म्याद समाप्ति

AWS SSO OIDC public clients सामान्यतया 90 दिनपछि म्याद सकिन्छन् (`clientSecretExpiresAt`)। अवलोकनयोग्यताका लागि OmniRoute ले यो timestamp `providerSpecificData` मा भण्डारण गर्छ। यदि कुनै जडानले ~90 दिनपछि refresh गर्न छाड्छ भने, नयाँ OIDC client registration प्राप्त गर्न जडान पुनः आयात गर्नुहोस्। म्याद सकिएपछि हुने automatic re-registration लाई भावी सुधारका रूपमा ट्र्याक गरिएको छ।

API-key जडानहरूको OIDC client म्याद सकिँदैन, किनभने तिनीहरूले AWS SSO OIDC मार्फत refresh गर्दैनन्।

## समस्या निवारण

### दोस्रो खाता बारम्बार लग आउट भइरहेको छ

- **Dashboard → Providers** मा दुवै जडान जाँच्नुहोस् र प्रत्येकको raw JSON मा non-null `clientId` देखिएको पुष्टि गर्नुहोस् (info icon मार्फत हेर्न सकिन्छ)। यदि कुनै जडानमा `clientId` छैन भने, त्यो v3.8.0 अघि आयात गरिएको थियो — त्यसलाई पुनः आयात गर्नुहोस्।

### "Token validation failed" सँग आयात असफल हुन्छ

- refresh token `aorAAAAAG` बाट सुरु भएको सुनिश्चित गर्नुहोस्।
- OmniRoute ले `https://oidc.us-east-1.amazonaws.com` (वा कन्फिगर गरिएको region) मा पहुँच गर्न सक्ने सुनिश्चित गर्नुहोस्। यदि तपाईं corporate proxy पछाडि हुनुहुन्छ भने, **Dashboard → Settings → Proxies** मा provider-level proxy सेट गर्नुहोस्।

### API-key आयात असफल हुन्छ

- key refresh token नभई Kiro / CodeWhisperer API key भएको पुष्टि गर्नुहोस्।
- AWS region key/account सँग मेल खाने पुष्टि गर्नुहोस्। `us-east-1` पूर्वनिर्धारित हो।
- key ले `ListAvailableProfiles` कल गर्न सक्नुपर्छ; अन्यथा OmniRoute ले आवश्यक `profileArn` निर्धारण गर्न सक्दैन।

अन्य समस्याहरूका लागि, मुख्य [TROUBLESHOOTING.md](./TROUBLESHOOTING.md) हेर्नुहोस्।
