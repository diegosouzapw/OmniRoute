OmniRoute लाई OpenAI-संगत ब्याकएन्डका रूपमा प्रयोग गर्न Codex CLI सम्बन्धी पूर्ण मार्गदर्शिका।

---

> **TOML नै एकमात्र प्रभावकारी ढाँचा हो।** आधुनिक Codex ले विशेष रूपमा
> `~/.codex/config.toml` पढ्छ (codex-cli 0.147.0 मा प्रमाणित: `codex --help` ले
> `-c/--config` ओभरराइडहरू "`~/.codex/config.toml` बाट लोड गरिएका" भनेर उल्लेख गर्छ)। पुरानो
> `~/.codex/config.yaml` लिगेसी npm CLI को थियो र यसलाई कुनै सूचना नदिई बेवास्ता गरिन्छ।
> ड्यासबोर्ड जेनेरेटरले (`/api/cli-tools/apply`, उपकरण `codex`) सावधानीपूर्वक मर्ज गर्दै TOML लेख्छ —
> विद्यमान कुञ्जीहरू र अन्य प्रदायक ब्लकहरू सुरक्षित राखिन्छन्,
> API कुञ्जी `OMNIROUTE_API_KEY` मै रहन्छ (फाइलमा कहिल्यै राखिँदैन), र बाँकी रहेको लिगेसी
> `config.yaml` लाई नछोई माइग्रेसन नोटका रूपमा रिपोर्ट गरिन्छ।

## सीधै टाँस्न मिल्ने config.toml

`<YOUR_HOST>` र `<YOUR_KEY>` लाई आफ्ना मानहरूले प्रतिस्थापन गर्नुहोस्:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # प्रत्येक उपकरण कलका लागि इतिहास भण्डारण सीमा

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc वा ~/.zshrc — वास्तविक कुञ्जी मान, config.toml मा कहिल्यै नराख्नुहोस्
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT एपभित्र समावेश गरिएको Codex

यदि तपाईंले ChatGPT डेस्कटप एपमार्फत Codex स्थापना गर्नुभएको हो भने, `codex` बाइनरी
एप बन्डलभित्र मात्र हुन सक्छ र अहिलेसम्म तपाईंको शेल `PATH` मा नहुन सक्छ। आफ्नो
शेल स्टार्टअप फाइलमा रिसोर्स डाइरेक्टरी थप्नुहोस्:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

नयाँ शेल खोल्नुहोस्, त्यसपछि प्रमाणीकरण गर्नुहोस्:

```bash
command -v codex
codex --version
```

### स्थानीय प्रमाणीकरणरहित OmniRoute: प्लेसहोल्डर कुञ्जी पर्याप्त हुन्छ

Codex ले पहिलो अनुरोध CLI बाट बाहिरिनु **अघि** `env_key` द्वारा नाम दिइएको
वातावरण चल अवस्थित छ कि छैन भनेर प्रमाणीकरण गर्छ। यदि तपाईंको **स्थानीय** OmniRoute
इन्स्ट्यान्सलाई प्रमाणीकरण आवश्यक पर्दैन भने, कुनै पनि खाली नभएको प्लेसहोल्डरले काम गर्छ:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

तपाईंको OmniRoute सर्भर सुरक्षित वा रिमोट छ भने यसको सट्टा वास्तविक कुञ्जी प्रयोग गर्नुहोस्।

> **सामान्य होस्ट विकल्पहरू**
>
> | पहुँच           | URL                           |
> | --------------- | ----------------------------- |
> | स्थानीय नेटवर्क | `http://192.168.0.1:20128/v1` |
> | Tailscale       | `http://100.x.x.x:20128/v1`   |
> | लुपब्याक        | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — यसले सबै मोडेलका लागि किन काम गर्छ

Codex CLI ले फेब्रुअरी 2026 मा `wire_api = "chat"` (Chat Completions) लाई अप्रचलित बनायो र अब `wire_api = "responses"` (OpenAI Responses API) **आवश्यक** पर्छ। `wire_api = "chat"` सेट गर्दा v0.138 देखि स्टार्टअपमै तुरुन्त क्र्यास हुन्छ।

GLM र Kimi सहित धेरै प्रदायकहरूले अझै पनि Chat Completions इन्डपोइन्ट मात्र उपलब्ध गराउँछन्। DeepSeek V4 ले अब Anthropic-संगत इन्डपोइन्टका साथै नेटिभ Responses API पनि उपलब्ध गराउँछ; OmniRoute ले पूर्वनिर्धारित रूपमा Responses प्रयोग गर्छ र प्रत्येक DeepSeek जडानलाई Anthropic अनुकूलता चयन गर्न दिन्छ।

**OmniRoute ले यसलाई पारदर्शी रूपमा समाधान गर्छ:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute ले प्रदायकको नेटिभ प्रोटोकल चयन गर्छ र आवश्यक पर्दा अनुवाद गर्छ
    → POST /responses (DeepSeek V4) वा /chat/completions (Mistral / GLM / Kimi / अन्य)
```

OmniRoute प्रयोग गर्दा तपाईंलाई कहिल्यै छुट्टै अनुवाद प्रोक्सी आवश्यक पर्दैन। **सबै मोडेलले `wire_api = "responses"` प्रयोग गर्छन्** — बाँकी काम OmniRoute ले सम्हाल्छ।

> **`wire_api` पूर्वनिर्धारित हो** — यो फिल्ड पूर्वनिर्धारित रूपमा `"responses"` हुन्छ र यसलाई `config.toml` बाट पूर्ण रूपमा हटाउन सकिन्छ। उद्देश्य दस्तावेजीकरण गर्दै हुनुहुन्छ भने मात्र यसलाई स्पष्ट रूपमा सेट गर्नुहोस्।

## कन्टेक्स्ट विन्डो र कम्प्याक्सन

### टोकन कन्फिगरेसन फिल्डहरू

| फिल्ड                            | विवरण                                                                                                                                                                                      |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `model_context_window`           | सक्रिय मोडेलका लागि कुल टोकन बजेट। मोडेलद्वारा घोषित सीमामा सेट गर्नुहोस्।                                                                                                                 |
| `model_auto_compact_token_limit` | स्वचालित हिस्ट्री कम्प्याक्सन ट्रिगर गर्ने थ्रेसहोल्ड। **अधिकतम: `model_context_window` को 90%** — 90% भन्दा माथिका मानहरू कुनै सूचना नदिई बेवास्ता गरिन्छन्।                              |
| `tool_output_token_limit`        | हिस्ट्रीमा प्रत्येक टुल कलको आउटपुटका लागि भण्डारण गरिने टोकनको सीमा। यसले एउटा ठूलो टुल प्रतिक्रियाले पूरै विन्डो भरिनबाट रोक्छ। **यो अधिकतम आउटपुट होइन** — यो हिस्ट्री भण्डारण सीमा हो। |
| `compact_prompt`                 | कम्प्याक्सनका क्रममा प्रयोग गरिने सिस्टम प्रम्प्टका लागि इनलाइन ओभरराइड (v0.138+)।                                                                                                         |

> **`model_max_output_tokens` सम्बन्धी टिप्पणी**: यो फिल्ड **Codex CLI कन्फिग स्किमाको भाग होइन** (Codex Rust कोडबेसमा अनुपस्थित)। सेट गरिएको भए कुनै सूचना नदिई बेवास्ता गरिन्छ। यसमा निर्भर नहुनुहोस् — हिस्ट्रीमा कति टुल आउटपुट भण्डारण गर्ने भनेर नियन्त्रण गर्न `tool_output_token_limit` प्रयोग गर्नुहोस्।

## तर्कको प्रयास

प्रतिक्रिया दिनुअघि मोडेलले कति "सोच्छ" भन्ने नियन्त्रण गर्छ।

| मान      | प्रयोग गर्ने अवस्था                                 |
| -------- | --------------------------------------------------- |
| `none`   | कुनै तर्क नगर्ने — प्रत्यक्ष प्रतिक्रिया            |
| `low`    | सामान्य कार्यहरू (नाम फेर्ने, ढाँचा मिलाउने)        |
| `medium` | निर्दिष्ट नगरिएको अवस्थामा **सर्भर पूर्वनिर्धारित** |
| `high`   | मध्यवर्ती कार्यहरू (रिफ्याक्टरिङ, डिबग)             |
| `xhigh`  | आर्किटेक्चर, गहन विश्लेषण, जटिल समस्याहरू           |

```bash
# प्रत्येक आह्वानका लागि ओभरराइड
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

Desktop ले सोचसम्बन्धी पाठ (इन्क्रिप्ट गरिएका ब्लबहरू मात्र होइन) रेन्डर गर्न सकोस् भनेर तर्कको **सारांश** पनि सेट गर्नुहोस्:

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # वा समर्थित हुँदा ultra
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute सोच बजेट (सर्भर सेटिङ)

OmniRoute होस्टमा, Codex को प्रयास/सारांश अपस्ट्रिमसम्म पुग्नका लागि **Settings → AI → Thinking Budget** अनिवार्य रूपमा **`passthrough`** हुनुपर्छ। **`auto` मोडले** क्लाइन्टका सबै `reasoning` / `reasoning_effort` फिल्ड हटाउँछ र Codex सही रूपमा कन्फिगर गरिएको भए पनि सोच प्यानलहरू खाली बनाउँछ।

पूर्ण मार्गदर्शिका: [THINKING_BUDGET.md](./THINKING_BUDGET.md)।

कम्प्रेसन र प्रम्प्ट क्यास स्वतन्त्र छन् र `passthrough` अन्तर्गत पनि काम गरिरहन्छन्।

## प्रोफाइलहरू — प्रत्येक मोडेल/कार्यप्रवाहका लागि नाम दिइएका कन्फिगरेसनहरू

प्रोफाइलहरूले तपाईंलाई एउटै फ्ल्यागमार्फत मोडेल + कन्टेक्स्ट विन्डो परिवर्तन गर्न दिन्छन्। प्रत्येक प्रोफाइल एउटा समतल
`~/.codex/<name>.config.toml` हो, जुन आधारभूत `config.toml` माथि ओभरले हुन्छ।

> **नामकरण नियम (Codex CLI v0.137+):** फाइल `~/.codex/<name>.config.toml` नै हुनुपर्छ — **`profile-` उपसर्ग हुनु हुँदैन**।
> CLI ले `-p kimi-k27` → `~/.codex/kimi-k27.config.toml` का रूपमा समाधान गर्छ। फाइल फेला परेन भने, पूर्वनिर्धारित कन्फिगरेसन मौन रूपमा लागू हुन्छ।

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # छिटो, सस्तो
```

## `omniroute setup-codex` मार्फत प्रोफाइलहरू स्वतः उत्पन्न गर्ने

यदि तपाईं VPS मा OmniRoute चलाउनुहुन्छ भने, प्रत्यक्ष मोडेल क्याटलगबाट प्रोफाइल फाइलहरू स्वतः उत्पन्न गर्न सक्नुहुन्छ:

```bash
# VPS बाट (पोर्ट 20128 मा स्थानीय OmniRoute प्रयोग गर्छ)
omniroute setup-codex

# कुनै पनि मेसिनबाट — आफ्नो VPS निर्दिष्ट गर्नुहोस्
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# फाइलहरू नलेखी पूर्वावलोकन गर्नुहोस्
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# GLM र Kimi प्रोफाइलहरू मात्र उत्पन्न गर्नुहोस्
omniroute setup-codex --only glm,kimi

# आफूले रोजेको डाइरेक्टरीमा लेख्नुहोस्
omniroute setup-codex --codex-home /path/to/.codex
```

यो कमान्डले `/v1/models` प्राप्त गर्छ, ज्ञात मोडेलहरूका लागि अनुकूलित प्रोफाइलहरू प्रयोग गर्छ, अन्य मिल्दो टेक्स्ट मोडेलहरूका लागि क्याटलग मेटाडेटामा फर्कन्छ, र प्रत्येकका लागि `~/.codex/<name>.config.toml` लेख्छ। यो आइडेम्पोटेन्ट छ — पुनः चलाउन सुरक्षित छ।

सफल प्रदायक मोडेल खोज/आयातपछि प्रत्यक्ष क्याटलग परिवर्तन हुँदा OmniRoute ले यिनै प्रोफाइल फाइलहरू **स्वतः सिंक** पनि गर्न सक्छ। यो **स्वेच्छिक हो र पूर्वनिर्धारित रूपमा बन्द हुन्छ**: यसलाई **CLI Code dashboard** बाट सक्रिय गर्नुहोस् ("CLI profile auto-sync" → Codex), वा `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` सेट गर्नुहोस् (यसले पूर्वनिर्धारित रूपमा सक्रिय `CLI_ALLOW_CONFIG_WRITES` लाई पनि पालना गर्छ)। सक्रिय हुँदा यसले छुट्टाछुट्टै `~/.codex/*.config.toml` प्रोफाइल फाइलहरू मात्र लेख्छ; यसले सक्रिय/पूर्वनिर्धारित `~/.codex/config.toml`, Codex-lb सेटिङहरू, प्रमाणीकरण वा प्रदायक छनोट कहिल्यै परिवर्तन गर्दैन।

## `omniroute launch-codex` मार्फत Codex सुरु गर्ने

Codex सुरु गर्नुअघि तपाईंको OmniRoute इन्स्ट्यान्सको स्वास्थ्य जाँच गर्छ:

```bash
# स्थानीय OmniRoute विरुद्ध सुरु गर्नुहोस् (पूर्वनिर्धारित पोर्ट 20128)
omniroute launch-codex

omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx
```

```bash
omniroute configure codex

# -c फ्ल्यागहरूमार्फत omniroute प्रदायक इन्जेक्ट गरी codex सुरु गर्छ (कुनै कन्फिग लेखिँदैन)
```

## लामो समयसम्म चल्ने कार्यहरू

OmniRoute का दुई पूर्वनिर्धारित मानहरूले बहु-घण्टे Codex CLI सेसनहरूलाई थाहै नदिई विफल बनाउन सक्छन्। यीमध्ये कुनै पनि Codex CLI सेटिङ होइन — दुवै OmniRoute पक्षमा हुन्छन्। अकाउन्टहरूलाई निश्चित गर्ने र निष्क्रियता कटअफ असक्षम गर्ने अपस्ट्रिम प्रोक्सीहरूबाट कन्फिग माइग्रेट गर्ने प्रयोगकर्ताहरूले प्रायः दुवै समस्याको सामना गर्छन् र OmniRoute ले “लामो सेसन कायम राख्न सक्दैन” भन्ने निष्कर्ष निकाल्छन्।

| लक्षण                                                                        | सम्भावित कारण                                                                | नब                       |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------ |
| सेसनले निरन्तर अकाउन्टहरू बदल्छ / टर्नहरूबीच प्रम्प्ट-क्यास निरन्तरता हराउँछ | सेसन एफिनिटी TTL `0` (असक्षम) छ                                              | `sessionAffinityTtlMs`   |
| क्लाइन्टतर्फ कुनै प्रम्प्ट नदेखाई रिजनिङकै बीचमा कनेक्सन टुट्छ               | 10 मिनेटसम्म कुनै अपस्ट्रिम चङ्क नआएपछि स्ट्रिम निष्क्रियता वाचडग सक्रिय भयो | `STREAM_IDLE_TIMEOUT_MS` |

सम्बन्धित छलफलहरू: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (लामो कार्य ड्रपहरू), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (एफिनिटी पूर्वनिर्धारित रूपमा किन बन्द हुन्छ)। ट्र्याकिङ: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287)।

### 1. सेसन एफिनिटी — एउटै वार्तालापलाई एउटै अकाउन्टमा निश्चित गर्नुहोस्

**पूर्वनिर्धारित:** `sessionAffinityTtlMs = 0` (असक्षम)।

**यसलाई कहाँ सेट गर्ने**

- ड्यासबोर्ड → **सेटिङहरू → राउटिङ** → **सेसन एफिनिटी** → **एफिनिटी TTL (सेकेन्ड)** (`ComboDefaultsTab`)
- वा **मिलिसेकेन्डमा** `sessionAffinityTtlMs` सहित सेटिङहरू PATCH गर्नुहोस् (Zod दायरा `0`–`86_400_000`, अर्थात् 24 घण्टासम्म)

> #7274 मा Codex-मात्र `codexSessionAffinityTtlMs` बाट नाम परिवर्तन गरिएको हो। लिगेसी की अझै पनि पढ्न-मात्र मिल्ने उपनामका रूपमा स्वीकार गरिन्छ; नयाँ कन्फिगहरूले `sessionAffinityTtlMs` प्रयोग गर्नुपर्छ। TTL `0` भन्दा माथि भएपछि एफिनिटी अब Codex मा मात्र नभई **कुनै पनि** प्रदायकमा लागू हुन्छ — [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → सेसन एफिनिटी हेर्नुहोस्।

**यो 0 मै रहँदा के बिग्रन्छ**

बहु-टर्न Codex वार्तालापको प्रत्येक टर्नलाई सक्रिय कम्बो रणनीतिद्वारा स्वतन्त्र रूपमा राउट गरिन्छ र त्यो **हरेक टर्नमा फरक अकाउन्टमा** पुग्न सक्छ। यसले अपस्ट्रिम सेसन / प्रम्प्ट-क्यास निरन्तरता बिगार्छ। TTL `0` भन्दा ठूलो हुँदा मात्र OmniRoute ले Codex सेसन हेडरहरू (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) र `prompt_cache_key` / `session_id` जस्ता बडी फिल्डहरू जाँच गर्छ (`src/sse/services/auth.ts` मा `extractSessionAffinityKey`)।

**बहु-घण्टे एकल कार्यका लागि सिफारिस**

TTL लाई **कार्यको अपेक्षित वास्तविक अवधिभन्दा बढी** सेट गर्नुहोस् (UI को अधिकतम **86400 सेकेन्ड** = 24 घण्टा हो):

| अपेक्षित कार्य अवधि | एफिनिटी TTL (UI, सेकेन्ड) | `sessionAffinityTtlMs` |
| ------------------- | ------------------------- | ---------------------- |
| केही घण्टा          | `14400` (4h)              | `14400000`             |
| रातभरि / ~12h       | `43200` (12h)             | `43200000`             |
| पूरा दिन            | `86400` (24h, अधिकतम)     | `86400000`             |

अप्ट-इन जानाजानी राखिएको हो: एफिनिटी असक्षम गर्दा अकाउन्टहरूबीच लोड-ब्यालेन्सिङलाई प्राथमिकता मिल्छ; यसलाई सक्षम गर्दा एउटा लामो एजेन्ट सेसनको निरन्तरतालाई प्राथमिकता मिल्छ। यस गाइडले पूर्वनिर्धारित मान **परिवर्तन गर्दैन** — लामो Codex कार्यहरू चलाउने अपरेटरहरूले अप्ट-इन गर्नैपर्छ।

### 2. स्ट्रिम निष्क्रियता टाइमआउट — शान्त रिजनिङ टर्नहरू समाप्त नगर्नुहोस्

**पूर्वनिर्धारित:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 मिनेट)। सेट नगरिएको अवस्थामा यसले `REQUEST_TIMEOUT_MS` बाट मान प्राप्त गर्छ; साझा आधारभूत मान पनि 600000 नै हो। [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → टाइमआउटहरू हेर्नुहोस्।

**पूर्वनिर्धारित मानमा के बिग्रन्छ**

10 मिनेटभन्दा बढी समयसम्म **कुनै वास्तविक upstream chunk बिना** मौन रहने Codex reasoning / tool turn लाई SSE idle watchdog (`open-sse/utils/stream.ts`) ले जबरजस्ती बन्द गर्छ। क्लाइन्टले प्रायः कुनै सन्देशबिनाको connection drop मात्र देख्छ — जुन “कुनै सूचना नदिई स्वचालित रूपमा रोकियो” भन्ने अवस्थासँग मेल खान्छ।

महत्त्वपूर्ण विवरण: OmniRoute को synthetic SSE **heartbeat ले idle clock reset गर्दैन**। वास्तविक upstream body chunk ले मात्र `lastChunkTime` अद्यावधिक गर्छ। अझै “सोचिरहेको” शान्त मोडेल watchdog को दृष्टिकोणबाट रोकिएको upstream जस्तै देखिन्छ।

सम्बन्धित Undici body inactivity: `FETCH_BODY_TIMEOUT_MS` (यसको पूर्वनिर्धारित मान पनि उही 10-मिनेटको baseline हो; `0` ले यसलाई निष्क्रिय गर्छ)। Streaming का लागि, `FETCH_TIMEOUT_MS` ले connection setup / पहिलो headers सम्म मात्र समेट्छ — stream सक्रिय भएपछि, अवरोधहरू `STREAM_IDLE_TIMEOUT_MS` र `FETCH_BODY_TIMEOUT_MS` द्वारा नियन्त्रित हुन्छन्।

**धेरै घण्टा चल्ने एउटै task का लागि सिफारिस**

OmniRoute process environment (`.env` / compose / systemd) मा:

```bash
# लामो reasoning turn का लागि stream idle + body inactivity cutoff निष्क्रिय गर्नुहोस्
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

वा तपाईंले अपेक्षा गरेको सबैभन्दा लामो शान्त अवधिभन्दा माथि तिनका मान बढाउनुहोस् (मानहरू milliseconds मा छन्):

```bash
# उदाहरण: upstream chunk हरूबीच अधिकतम 2 घण्टाको मौनता अनुमति दिनुहोस्
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

यी env vars परिवर्तन गरेपछि OmniRoute restart गर्नुहोस्।

### ठोस विधि — धेरै घण्टा चल्ने Codex task

1. **Account pin गर्नुहोस्:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12h) वा `86400` (अधिकतम 24h)।
2. OmniRoute को environment मा **idle cutoff बढाउनुहोस् / निष्क्रिय गर्नुहोस्**:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. सामान्य Codex `config.toml` (`wire_api = "responses"`, सही `base_url`, `OMNIROUTE_API_KEY`) कायम राख्नुहोस् — यी दुई व्यवहारका लागि Codex-पक्षमा affinity/idle knobs छैनन्।
4. OmniRoute restart गर्नुहोस्, त्यसपछि लामो Codex task सुरु गर्नुहोस्।

### पूर्वनिर्धारित मानसम्बन्धी निर्णय (#7287)

| Knob                     | पठाइने पूर्वनिर्धारित मान | यस guide मा परिवर्तन गर्ने?                                                                                            |
| ------------------------ | ------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (बन्द)                | **होइन** — opt-in नै रहन्छ (load-balancing बनाम continuity; Discussion #5718 हेर्नुहोस्)                               |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 मिनेट)       | **होइन** — सामान्य traffic का लागि 10 मिनेट नै रहन्छ; लामो Codex सञ्चालन गर्नेहरूले यसलाई बढाउँछन् वा निष्क्रिय गर्छन् |

कुनै पनि पूर्वनिर्धारित मानलाई विश्वव्यापी रूपमा परिवर्तन गर्दा Codex मात्र नभई instance का प्रत्येक client को व्यवहार परिवर्तन हुन्छ। Knobs लाई दस्तावेजीकरण गर्नुहोस्; स्पष्ट operator निर्णयले अन्यथा नभनेसम्म पूर्वनिर्धारित मानहरू यथावत् राख्नुहोस्।

### Idle cut को निदान

Idle watchdog सक्रिय हुँदा, OmniRoute ले यस प्रकारको line log गर्छ:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

`Idle timeout: no data from` (वा code `stream_idle_timeout` / error name `StreamIdleTimeoutError`) खोज्न Grep प्रयोग गर्नुहोस्। Provider segment भनेको उक्त request का लागि OmniRoute ले प्रयोग गरेको मान हो (`codex`, अर्को provider id, वा अज्ञात भएमा `provider`) — यो सधैँ ठ्याक्कै `codex` string हुँदैन।

## समस्या निवारण

**`Error: wire_api = "chat" is no longer supported`**
आफ्नो कन्फिगरेसनबाट `wire_api = "chat"` हटाउनुहोस्। `wire_api = "responses"` सेट गर्नुहोस् वा यो फिल्ड नलेख्नुहोस् (v0.138 देखि पूर्वनिर्धारित मान `"responses"` हो)।

**`Error: model not found`**
सही प्रिफिक्ससहित मोडेल OmniRoute मा अवस्थित छ भनी पुष्टि गर्नुहोस्। `omniroute models list` प्रयोग गर्नुहोस् वा `/dashboard/providers/<provider>` खोल्नुहोस्।

**`Authentication error`**
`OMNIROUTE_API_KEY` एक्सपोर्ट गरिएको छ भनी पुष्टि गर्नुहोस्: `echo $OMNIROUTE_API_KEY`।

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex ले पहिलो अनुरोध गर्नुअघि env var अवस्थित छ कि छैन भनी जाँच गर्छ। सुरक्षित सर्भरहरूका लागि
वास्तविक कुञ्जी एक्सपोर्ट गर्नुहोस्, वा तपाईंको **स्थानीय** OmniRoute इन्स्ट्यान्सलाई
प्रमाणीकरण आवश्यक नपर्दा `OMNIROUTE_API_KEY=local` जस्तो खाली नभएको प्लेसहोल्डर प्रयोग गर्नुहोस्।
तपाईंले यसलाई `~/.bashrc` वा `~/.zshrc` मा थप्नुभएको हो भने शेल पुनः सुरु गर्नुहोस्।

**`Connection refused`**
OmniRoute चलिरहेको छ र `base_url` को होस्ट/पोर्ट तपाईंको नेटवर्कका लागि सही छ भनी पुष्टि गर्नुहोस् (स्थानीय, Tailscale वा VPS)।

**सन्दर्भ सीमा नजिक पुग्दा सेसन क्र्यास हुन्छ**
`model_context_window` र `model_auto_compact_token_limit` स्पष्ट रूपमा सेट गर्नुहोस्। माथिको सन्दर्भ विन्डो तालिका हेर्नुहोस्।

**कम्प्याक्सन धेरै ढिलो सुरु हुन्छ**
`model_auto_compact_token_limit` लाई विन्डोको 80–85% मा घटाउनुहोस्। यसलाई कहिल्यै 90% भन्दा माथि सेट नगर्नुहोस्।

**प्रोफाइल लोड हुँदैन (`-p <name>` चुपचाप बेवास्ता गरिन्छ)**
फाइल `~/.codex/<name>.config.toml` मा अवस्थित छ भनी पुष्टि गर्नुहोस् (`profile-` प्रिफिक्सबिना)। `ls ~/.codex/*.config.toml` चलाउनुहोस्।

**लामो Codex कार्य चलिरहँदा बीचमै रोकिन्छ / टर्नहरूबीच खाता परिवर्तन हुन्छ**
[लामो समयसम्म चल्ने कार्यहरू](#long-running-tasks) हेर्नुहोस्। सेसन अफिनिटी (कार्य अवधिभन्दा लामो TTL) सक्षम पार्नुहोस् र `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS` बढाउनुहोस् वा असक्षम पार्नुहोस्। `Idle timeout: no data from` का लागि OmniRoute लगहरूमा grep गर्नुहोस्।
