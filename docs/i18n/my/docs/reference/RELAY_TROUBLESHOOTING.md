Relay များ (Vercel, Deno, Cloudflare) သည် serverless backend တစ်ခုပေါ်တွင် upstream ချိတ်ဆက်မှုကို အဆုံးသတ်ပေးသဖြင့် OmniRoute သည် provider API key ကို server-side တွင် ထိန်းသိမ်းထားရင်း တည်ငြိမ်သော region တစ်ခုမှ egress ပြုလုပ်နိုင်သည်။ ဤစာတမ်းတွင် production ပတ်ဝန်းကျင်၌ operator များ ကြုံတွေ့ရလေ့ရှိသော failure mode နှစ်မျိုးနှင့် တစ်မျိုးစီအတွက် OmniRoute တွင် ပါဝင်သည့် ပြန်လည်ထူထောင်ရေးနည်းလမ်းများကို ဖော်ပြထားသည်။

## Relay auth ကို သိမ်းဆည်းပုံ

**Settings → Proxy Pool → Deploy Relay** မှ relay တစ်ခုကို deploy လုပ်သည့်အခါ deploy flow သည် relay ၏ auth token ကို proxy `notes` JSON field ထဲတွင် သိမ်းဆည်းသည်-

- `STORAGE_ENCRYPTION_KEY` ကို သတ်မှတ်ထားပါက token ကို `relayAuthEnc`
  အဖြစ် ရေးသားသည် (သိမ်းဆည်းထားစဉ် AES ဖြင့် ကုဒ်ဝှက်ထားသည်)။
- ထိုသို့မဟုတ်ပါက plaintext `relayAuth` အဖြစ် ရေးသားသည်။

Request ပြုလုပ်ချိန်တွင် `extractRelayAuth(notes)` သည် ရှိနေသည့်ပုံစံကို ပြန်ပေးသောကြောင့် restart ပြုလုပ်ပြီးနောက်တွင်လည်း relay က ဆက်လက်အလုပ်လုပ်နိုင်သည်။

## Failure mode 1 — key rotation ပြီးနောက် ကုဒ်ဖြည်၍မရသော token

**လက္ခဏာ:** ယခင်က အလုပ်လုပ်ခဲ့သော relay များသည် environment သို့မဟုတ် secret-manager တွင် `STORAGE_ENCRYPTION_KEY` ကို rotate လုပ်ပြီးနောက် upstream `401`/auth error များ ပြန်ပေးလာသည်။ သိမ်းဆည်းထားသော `relayAuthEnc` blob ကို ကုဒ်ဖြည်၍ မရတော့သဖြင့် `extractRelayAuth` သည် string အလွတ်ကို ပြန်ပေးပြီး relay က auth မပို့တော့ပါ။

**ပြန်လည်ထူထောင်ခြင်း — နေရာတင်ပြုပြင်ခြင်း (ပြန်လည် deploy လုပ်ရန်မလို):**

1. **Settings → Proxy Pool** ကို ဖွင့်ပါ။
2. Auth ပျောက်ဆုံးနေသော relay row များတွင် အဝါရောင် `auth missing` badge နှင့်
   **Repair** ခလုတ်ကို ပြသထားသည်။
3. **Repair** ကို နှိပ်ပါ။ OmniRoute သည်
   `POST /api/settings/proxies/[id]/repair-relay` ကို ခေါ်ဆိုပြီး အောက်ပါတို့ကို လုပ်ဆောင်သည်-
   - **လက်ရှိ** key ဖြင့် `relayAuthEnc` ကို ကုဒ်ဖြည်သည်၊
   - plaintext `relayAuth` ကို `notes` ထဲသို့ ပြန်ရေးသည်၊
   - `{ repaired: true, mode: "recovered" }` ကို ပြန်ပေးသည်။

Deploy credential များကို ပြန်လည်ထည့်သွင်းရန်မလိုဘဲ relay သည် ဝန်ဆောင်မှုကို ပြန်လည်စတင်သည်။

လက်ရှိ `STORAGE_ENCRYPTION_KEY` က blob ကို ကုဒ်ဖြည်နိုင်သေးမှသာ ဤနည်းလမ်း အလုပ်လုပ်မည်။ Migration မပြုလုပ်ဘဲ key ကို rotate လုပ်ခဲ့ပါက blob ကို ပြန်လည်ရယူ၍ မရနိုင်ပါ။

## Failure mode 2 — ပြန်လည်ရယူ၍မရသော token (key အဟောင်း မရှိတော့ခြင်း)

**လက္ခဏာ:** **Repair** ကို နှိပ်ပြီးနောက်
`{ repaired: false, mode: "redeploy", status: 409 }` ကို ရရှိသည်။

**ပြန်လည်ထူထောင်ခြင်း — ပြန်လည် deploy လုပ်ခြင်း:**

သိမ်းဆည်းထားသော token ကို လက်ရှိ key ဖြင့် ပြန်လည်ရယူ၍ မရနိုင်ပါ။ မူလက အသုံးပြုခဲ့သော modal မှ relay ကို ပြန်လည် deploy လုပ်ပါ (**Deploy Relay** menu → Vercel / Deno / Cloudflare)။ Deploy flow သည် token အသစ်တစ်ခုကို ရေးသားပြီး (လက်ရှိ key ဖြင့် ကုဒ်ဝှက်ထားသည်) row ရှိ `auth missing` badge သည် ပျောက်သွားမည်။

Token ကို ပြန်လည်ရယူ၍မရနိုင်သည့်အခါ UI ရှိ **Repair** ခလုတ်ကိုယ်တိုင်က redeploy modal ကို ဖွင့်ပေးသောကြောင့် ၎င်းကို ကိုယ်တိုင်ရှာဖွေရန် မလိုပါ။

## Failure mode 3 — relay ကို ချိတ်ဆက်နိုင်သော်လည်း အခြေအနေမကောင်းခြင်း

**လက္ခဏာ:** Proxy test (`speed` ခလုတ်) တွင် relay အလုပ်လုပ်နေကြောင်း ပြသသော်လည်း request များသည် ရံဖန်ရံခါ မအောင်မြင်သေးပါ။

OmniRoute ၏ auto-test probe က ပြန်ပေးသော relay awareness header များကို စစ်ဆေးပါ
(**Settings → Proxy Pool** နှင့် `relayTested` / `relayAlive` counter များကို ကြည့်ပါ)-

- `x-relay-url` — မည်သည့် relay backend က တုံ့ပြန်ခဲ့သည်။
- `x-relay-mode` — ထို request အတွက် `ts` | `bifrost` | `auto`။
- `x-relay-attempts` — မအောင်မြင်မီ relay hop မည်မျှ စမ်းသပ်ခဲ့သည်။
- `x-relay-fallback` — preferred backend မှ TypeScript relay သို့ request က fallback ပြုလုပ်သည့်အခါ `true` ဖြစ်သည်။

`relayAlive` နည်းနေစဉ် `x-relay-fallback` နှုန်း မြင့်မားနေခြင်းသည် sidecar backend ၏ အခြေအနေမကောင်းကြောင်း ဆိုလိုသည်။ ၎င်းကို ပြုပြင်ပါ သို့မဟုတ် relay backend strategy ကို `ts` သို့ ပြောင်းပါ (`RELAY_BACKEND_STRATEGY.md` ကို ကြည့်ပါ)။

## API ကိုးကားချက်

| Method | Path                                      | Body                    | အောင်မြင်မှု                                                                                                                        | မအောင်မြင်မှု                                                                                  |
| ------ | ----------------------------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | ပြန်လည်ရယူနိုင်ပါက `200 { repaired: true, mode: "recovered" }`; plaintext ရှိပြီးသားဖြစ်ပါက `200 { repaired: false, mode: "noop" }` | ပြန်လည်ရယူ၍မရပါက `409 { mode: "redeploy" }`; relay အမျိုးအစားမဟုတ်ပါက `400`; ရှာမတွေ့ပါက `404` |

List route ဖြစ်သော `GET /api/settings/proxies` သည် item တစ်ခုစီတွင် လျှို့ဝှက်ချက်မပါသော `relayInfo: { isRelay, authMissing, repairMode }` ကို ပူးတွဲပေးသဖြင့် dashboard သည် token ကို မည်သည့်အခါမျှ ဖော်ထုတ်ခြင်းမရှိဘဲ ပြုပြင်ရေးလုပ်ဆောင်ချက်ကို ပြသနိုင်သည်။
