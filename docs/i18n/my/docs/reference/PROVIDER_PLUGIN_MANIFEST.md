`open-sse/config/providerPluginManifest.ts` သည် JSON-safe provider plugin contract ကို သတ်မှတ်ပေးသည်။
`open-sse/config/providerPluginManifestRegistry.ts` သည် ထို contract ကို Bifrost၊
CLIProxyAPI သို့မဟုတ် အနာဂတ် Go/Rust router ကဲ့သို့သော sidecar များအတွက်
လက်ရှိ provider registry နှင့် ချိတ်ဆက်ပေးသည်။ TypeScript registry သည်
source of truth အဖြစ် ဆက်လက်တည်ရှိသော်လည်း sidecar များသည် executor code၊
OAuth default များ၊ header များ သို့မဟုတ် process environment state ကို import
မလုပ်ဘဲ manifest ကို အသုံးပြုနိုင်သည်။

အလားတူ manifest ကို process ပြင်ပတွင် လည်ပတ်သော sidecar များအတွက် HTTP မှတစ်ဆင့်
`GET /api/v1/provider-plugin-manifest` တွင် ရရှိနိုင်သည်။

OmniRoute သည် ထို URL ကို `X-OmniRoute-Provider-Manifest-Url` request header မှတစ်ဆင့်
Bifrost နှင့် CLIProxyAPI သို့ အသိပေးသည်။ sidecar က local request origin အစား
public URL သို့မဟုတ် container network URL လိုအပ်သည့်အခါ
`OMNIROUTE_PROVIDER_MANIFEST_URL` ကို သတ်မှတ်ပါ။

## Manifest ကို Refresh လုပ်ခြင်း

HTTP endpoint သည် `Cache-Control: public, max-age=60` နှင့် strong
`ETag` တစ်ခုကို ပြန်ပေးသည်။ sidecar သည် နောက်ဆုံးအတည်ပြုပြီးသော manifest ကို
သိမ်းထားသင့်ပြီး refresh လုပ်သည့်အခါ ၎င်း၏ ETag ကို `If-None-Match` ထဲတွင်
ပေးပို့သင့်သည်။ `304 Not Modified` response တွင် body မပါဝင်ပါ။
sidecar သည် ၎င်း၏ cached manifest ကို ဆက်လက်အသုံးပြုသည်။ အတည်ပြုပြီးသော
cached manifest မရှိပါက sidecar သည် `304` ကို လက်ခံမည့်အစား
unconditional request တစ်ခု ပြုလုပ်ရမည်။

## ရည်ရွယ်ချက်

OmniRoute က TypeScript route ကို policy gate နှင့် fallback အဖြစ် ဆက်လက်ထားရှိစဉ်
latency ပိုနည်းသော sidecar က hot request path ကို နောက်ဆုံးတွင် တာဝန်ယူနိုင်ရန်
provider metadata ကို plugin contract ပုံစံသို့ ရွှေ့ပြောင်းရန် ဖြစ်သည်။
manifest သည် additive ဖြစ်ပြီး ၎င်းတစ်ခုတည်းဖြင့် request routing ကို
ပြောင်းလဲခြင်းမရှိပါ။

## Contract

manifest တွင် အောက်ပါတို့ ပါဝင်သည်-

- provider id နှင့် alias
- upstream format နှင့် executor name
- auth type၊ auth header နှင့် optional auth prefix
- static endpoint metadata
- sidecar eligibility နှင့် provider တစ်ခုကို TS ပေါ်တွင် ဆက်ထားသင့်သည့်အခါအတွက် တိကျသောအကြောင်းပြချက်များ
- context length၊ vision/reasoning flag များနှင့် unsupported param များကဲ့သို့သော JSON-safe model metadata
- `apikey`၊ `oauth`၊ `custom-executor`၊
  `passthrough-models`၊ `responses`၊ `sidecar-candidate`၊ `usage-fetch` နှင့် `usage-supported` အပါအဝင် capability tag များ

manifest သည် အောက်ပါတို့ကို ရည်ရွယ်ချက်ရှိရှိ မထည့်သွင်းထားပါ-

- OAuth client secret များနှင့် default secret value များ
- runtime environment resolution
- request header များနှင့် public credential helper များ
- dynamic URL builder များ
- executor function များ
- session pool အတွင်းပိုင်းအချက်အလက်များ

## Capability Tag များ

`capabilities` သည် registry entry မှ ဆင်းသက်လာသော tag များ၏ အစဉ်လိုက်စီထားသည့် array ဖြစ်သည်။ Integrator
များသည် TypeScript source များကို ပြန်လည်ဖတ်ရှုမည့်အစား ၎င်းကို "ဤ provider က ဘာလုပ်နိုင်သလဲ" ဟူသည့်
မေးခွန်းအတွက် machine-readable အဖြေအဖြစ် သတ်မှတ်သင့်သည်။

| Tag                  | အဓိပ္ပာယ်                                                                                  |
| -------------------- | ------------------------------------------------------------------------------------------ |
| `apikey`             | API key ကို လက်ခံသည် (`authType` သည် `apikey` သို့မဟုတ် `optional` ဖြစ်သည်)။               |
| `oauth`              | OAuth သို့မဟုတ် session flow ကို အသုံးပြုသည်။                                              |
| `responses`          | OpenAI Responses-API base URL ကို ဖော်ထုတ်ပေးသည်။                                          |
| `passthrough-models` | static catalog အစား upstream မှ model များကို တိုက်ရိုက်ဝန်ဆောင်မှုပေးသည်။                 |
| `custom-executor`    | non-default executor ကို အသုံးပြုသောကြောင့် TypeScript path ပေါ်တွင် ဆက်ရှိနေသည်။          |
| `sidecar-candidate`  | `sidecar.eligible` ကို ထင်ဟပ်ပေးသည် — sidecar import အတွက် ထည့်သွင်းစဉ်းစားရန် စိတ်ချရသည်။ |
| `usage-fetch`        | ချိတ်ဆက်ထားသော usage သို့မဟုတ် quota fetcher (`getUsageForProvider`) ရှိသည်။               |
| `usage-supported`    | usage API က ဤ provider ကို လက်ခံသည် (`isSupportedUsageConnection`)။                        |

`usage-fetch` သည် ရှာဖွေသိရှိရန်အတွက်သာ ဖြစ်သည်။ OmniRoute က provider အတွက် usage ကို
မည်သို့ဖတ်ရမည်ကို သိကြောင်း ဖော်ပြခြင်းသာဖြစ်ပြီး fetching ကို အသက်သွင်းခြင်း၊ quota semantics ကို
ပြောင်းလဲခြင်း သို့မဟုတ် Dashboard quota widget ကို provider အတွက် ဖွင့်ထားကြောင်း သွယ်ဝိုက်ညွှန်ပြခြင်း
မဟုတ်ပါ — ထို widget ကို `USAGE_SUPPORTED_PROVIDERS` ဖြင့် သီးခြားထိန်းချုပ်ထားသည်။
source of truth မှာ `open-sse/services/usage/fetcherProviders.ts` ရှိ
`USAGE_FETCHER_PROVIDERS` ဖြစ်သည်။

ထိုစာရင်းကို usage dispatcher က လက်ခံသော string များဖြင့် key သတ်မှတ်ထားသောကြောင့် canonical id
များနှင့် alias များ ရောနှောပါဝင်ပြီး tag တပ်ထားသော provider အရေအတွက်ထက် အနည်းငယ်ပိုရှည်သည်-
manifest registry တွင် chat provider မဟုတ်သော entry များ (ဥပမာ `firecrawl` search provider
နှင့် `amazon-q` ACP provider) အတွက် tag တပ်ရန် manifest entry မရှိပါ။

`usage-supported` သည် server နှင့် Dashboard usage route များက provider အတွက် connection
တစ်ခုကို လက်ခံခြင်းရှိမရှိ ဖြေကြားပေးသည်။ ၎င်းသည် `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
နှင့် `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`) ကို ထင်ဟပ်ပြီး နှစ်ခုစလုံးကို
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`) ဖြင့် ထိန်းချုပ်ထားသည်။
`usage-fetch` နှင့် မတူဘဲ ၎င်းကို provider id တစ်ခုတည်းအပေါ် အခြေခံ၍ ထုတ်ပေးသည် — runtime guard သည်
alias resolution မပါဘဲ `USAGE_SUPPORTED_PROVIDERS.includes(providerId)` ကို လုပ်ဆောင်သောကြောင့် manifest
သည်လည်း အလားတူစည်းမျဉ်းကို ဆက်လက်ထိန်းသိမ်းထားသည်။ tag နှစ်ခု၏ အကျုံးဝင်နယ်ပယ်များမှာ ကွဲပြားသည်-
provider 3 ခုတွင် `usage-fetch` သာ ပါရှိပြီး (`opencode`၊ `opencode-zen`၊ `xai`)၊ 1 ခုတွင်
`usage-supported` (`xiaomi-mimo-token-plan`) သာ ပါရှိသောကြောင့် တစ်ခုရှိခြင်းက အခြားတစ်ခုလည်း
ရှိကြောင်း မဆိုလိုပါ။

## Sidecar အသုံးပြုမှု

Sidecar များသည် `sidecar.eligible` ကို ခြွင်းချက်မရှိ routing ဆုံးဖြတ်ချက်တစ်ခုအဖြစ် မယူဆဘဲ သတိထားရွေးချယ်ထားသော candidate signal တစ်ခုအဖြစ် သတ်မှတ်သင့်သည်။ ပထမဆုံး import ပြုလုပ်မည့် target သည် default executor ကို အသုံးပြုသော API-key/static-endpoint provider များ ဖြစ်သင့်သည်။ Custom web executor များ၊ OAuth/session flow များ၊ dynamic URL builder များ သို့မဟုတ် pool config များရှိသော provider များကို sidecar တစ်ခုက တူညီသော behavior ကို အကောင်အထည်ဖော်ပြီး telemetry ဖြင့် parity ရှိကြောင်း သက်သေပြနိုင်သည်အထိ TypeScript fallback path တွင် ဆက်လက်ထားရှိရမည်။

အကြံပြုထားသော migration အဆင့်များ-

1. TS registry မှ provider plugin manifest ကို generate လုပ်ပြီး validate လုပ်ပါ။
2. API-key/static provider များအတွက် manifest ကို import လုပ်နိုင်ရန် Bifrost သို့မဟုတ် CLIProxyAPI ကို ပြင်ဆင်ပါ။
3. TS fallback ကို ဆက်လက်ဖွင့်ထားပြီး `OMNIROUTE_RELAY_BACKEND` နောက်ကွယ်ရှိ sidecar မှတစ်ဆင့် eligible provider များကို route လုပ်ပါ။
4. Success rate၊ p99 latency၊ streaming behavior နှင့် unsupported-param handling တို့သည် TS path နှင့် ကိုက်ညီမှသာ provider များကို promote လုပ်ပါ။
5. Provider family တစ်ခုချင်းစီအလိုက် custom executor များအတွက် sidecar-native plugin များကို ထည့်သွင်းပါ။

## Provider များကို Next အတွင်း တိုက်ရိုက် မထည့်သွင်းသင့်သည့် အကြောင်းရင်း

Next frontend သည် provider execution ကို မပိုင်ဆိုင်သင့်ပါ။ ၎င်းသည် API boundary ကိုသာ ခေါ်ဆိုသင့်သည်။ ထို့နောက် backend က TypeScript executor၊ Bifrost၊ CLIProxyAPI သို့မဟုတ် အနာဂတ် native sidecar တစ်ခုကို အသုံးပြုမည်လား ဆုံးဖြတ်နိုင်သည်။ ဤနည်းလမ်းဖြင့် sidecar သို့ လွှဲပြောင်းမှုတစ်စုံတစ်ရာ မပြုလုပ်မီ request signing၊ allowlist စစ်ဆေးမှုများ၊ DB policy နှင့် fallback behavior တို့ကို ဗဟိုမှ စီမံထားနိုင်သည်။
