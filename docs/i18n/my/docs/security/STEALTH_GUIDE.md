OmniRoute သည် တရားဝင်မဟုတ်သော client များကို ၎င်းတို့၏ edge များက တက်ကြွစွာ fingerprint ပြုလုပ်သည့် provider များနှင့် ချိတ်ဆက်ပေါင်းစည်းထားသည် (TLS JA3/JA4၊ header အစီအစဉ်၊ JSON body ပုံသဏ္ဌာန်၊ integrity token များ)။ ဤစာမျက်နှာတွင် OmniRoute က ဖော်ထုတ်ပေးထားသော stealth မျက်နှာပြင်များနှင့် ၎င်းတို့ကို အကောင်အထည်ဖော်ထားသည့်နေရာများကို မှတ်တမ်းတင်ထားသည်။

## ဥပဒေနှင့် ကျင့်ဝတ်ဆိုင်ရာ အသိပေးချက်

Stealth အင်္ဂါရပ်များသည် သုံးစွဲသူပိုင် တရားဝင် account များ (Claude Code CLI, Codex, Antigravity, Cursor စသည်တို့) နှင့် OmniRoute ၏ ပေါင်းစည်းထားသော API ကြားတွင် OmniRoute က compatibility layer တစ်ခုအဖြစ် လုပ်ဆောင်နိုင်ရန် တည်ရှိခြင်းဖြစ်သည်။ ၎င်းတို့သည် လိမ်လည်မှုရှာဖွေခြင်းကို ရှောင်လွှဲရန်၊ အထောက်အထားများကို မျှဝေရန် သို့မဟုတ် provider ၏ ဝန်ဆောင်မှုစည်းမျဉ်းများကို ချိုးဖောက်ရန်အတွက် **မဟုတ်ပါ**။ ထိန်းသိမ်းသူများသည် operator များအနေဖြင့် account များဖန်တီးစဉ် လက်မှတ်ရေးထိုးသဘောတူခဲ့သော upstream ToS ကို လိုက်နာရန် မျှော်လင့်ထားသည်။

## TLS Fingerprinting Layer

### `open-sse/utils/tlsClient.ts` — wreq-js (Chrome 124)

တည်တံ့သော `wreq-js` session များကို account scope တစ်ခုချင်းစီနှင့် ဖြေရှင်းသတ်မှတ်ပြီးသော proxy တစ်ခုချင်းစီအလိုက် လိုအပ်သည့်အချိန်မှသာ ဖန်တီးသည်။ Process တစ်ခုလုံးအတိုင်းအတာရှိ `TlsClient` သည် Cloudflare နောက်ကွယ်ရှိ upstream များအတွက် **macOS ပေါ်ရှိ Chrome 124** အဖြစ် အယောင်ဆောင်သော session အများဆုံး 128 ခုကို pool ပြုလုပ်ထားသည်။ Native runtime ကို မရရှိနိုင်သည့်အခါ `TlsClient.fetch()` သည် fail closed ဖြစ်သည်။ ခေါ်ယူသူသည် ဤ wrapper ၏ အပြင်ဘက်တွင် fallback တစ်ခုကို အတိအလင်း ရွေးချယ်နိုင်သည်။

- Session profile: `browser: "chrome_124", os: "macos"`
- Proxy ဖြေရှင်းသတ်မှတ်မှု (ဦးစားပေးအစီအစဉ်): `HTTPS_PROXY` → `HTTP_PROXY` → `ALL_PROXY` (စာလုံးအသေးပုံစံများလည်း ပါဝင်သည်)
- Timeout: `TLS_CLIENT_TIMEOUT_MS` (`FETCH_TIMEOUT_MS` မှ အမွေဆက်ခံပြီး မူလတန်ဖိုးမှာ 600000 ဖြစ်သည်)
- `wreq-js` Response သည် fetch နှင့် ကိုက်ညီသည် (`headers`, `text()`, `json()`, `clone()`, `body`)။
- ပထမ byte စောင့်ကြည့်စနစ် (`open-sse/utils/tlsFirstByteWatchdog.ts`, #12656): Upstream header များရောက်ရှိသည်နှင့် `TlsClient.fetch()` သည် ဖြေရှင်းပြီးဖြစ်သောကြောင့် `TLS_CLIENT_TIMEOUT_MS` တစ်ခုတည်းဖြင့် ပထမ byte ကို လုံးဝမပေးသော body တစ်ခုကို အချိန်ကန့်သတ်၍ မရနိုင်ပါ။ `guardTlsFirstByte()` သည် body ၏ ပထမဆုံး `read()` နှင့် `TLS_FIRST_BYTE_WATCHDOG_MS` (မူလတန်ဖိုး `10000`၊ `0` ဖြင့် ပိတ်နိုင်သည်) တို့ကို အပြိုင်လုပ်ဆောင်စေသည်။ အခြေအနေကောင်းမွန်သော body ကို သက်ရောက်မှုမရှိသော်လည်း ရပ်တန့်နေသော body အတွက် wreq reader ကို ပယ်ဖျက်ပြီး `proxyFetch` ၏ ရှိပြီးသား TLS-fallback logic ကို direct/proxy dispatcher သို့ ဆက်လက်ကျရောက်စေသည် (ပြန်လည်ပေးပို့ရန် မလုံခြုံသော request၊ ဥပမာ body ပါသည့် POST သည် အသံတိတ်ပြန်လည်ကြိုးစားခြင်းမရှိဘဲ error ပစ်ဆဲဖြစ်သည်)။

### Web-cookie provider transport — wreq-js 3.2.0

`open-sse/services/tlsClientBase.ts` သည် အောက်ပါ အထူးပြု web-cookie transport ငါးခုအတွက် မျှဝေအသုံးပြုသော adapter ဖြစ်သည်။ ပါးလွှာသော provider wrapper တစ်ခုချင်းစီသည် browser/OS profile တစ်ခုကို ရွေးချယ်သည်။ Adapter သည် `open-sse/utils/tlsClient.ts` ထဲရှိ တစ်ခုတည်းသော wreq runtime loader နှင့် transport pool ကို အသုံးပြုပြီး profile + OS + ဖြေရှင်းသတ်မှတ်ပြီးသော proxy ဖြင့် key သတ်မှတ်ထားကာ request တိုင်းတွင် `cookieMode: "ephemeral"` ကို အသုံးပြုသည်။ ထို့ကြောင့် account များနှင့် request များသည် transport အဆင့် connection များကို မျှဝေသော်လည်း wreq session သို့မဟုတ် cookie jar ကို မည်သည့်အခါမျှ မမျှဝေပါ။

| Provider   | Profile       | အတုယူထားသော OS | Stream EOF မူဝါဒ                        |
| ---------- | ------------- | -------------- | --------------------------------------- |
| Claude     | `chrome_146`  | Linux          | `[DONE]` ကို ထည့်သွင်းသည်               |
| Perplexity | `firefox_148` | macOS          | `event: end_of_stream` ကို ထည့်သွင်းသည် |
| Grok       | `chrome_146`  | Linux          | `[DONE]` ကို ဖယ်ထုတ်သည်                 |
| Notion     | `chrome_146`  | Windows        | `[DONE]` ကို ထည့်သွင်းသည်               |
| LMArena    | `chrome_146`  | Windows        | sentinel မရှိ၊ native EOF တွင် ပိတ်သည်  |

- Streaming သည် native response `ReadableStream` ကို တိုက်ရိုက်သုံးစွဲသည်။ ယာယီဖိုင် သို့မဟုတ် sidecar ကို မဖန်တီးပါ။
- Stream ကို ဖော်ထုတ်မပေးမီ ကနဦး byte 256 ခုအထိ စစ်ဆေးသည်။ SSE provider များသည် SSE မဟုတ်သော error များကို buffer လုပ်သည်။ Grok/LMArena သည် Cloudflare challenge များကို `403` သို့လည်းကောင်း၊ HTML interstitial များကို `502` သို့လည်းကောင်း ချိတ်ဆက်သတ်မှတ်သည်။
- Native request timeout ကို အကြွင်းမဲ့ JS hard deadline ဖြင့် ဆက်လက် wrap လုပ်ထားသည်။ Hang ဖြစ်ခြင်းသည် သက်ရောက်မှုရှိသော profile/OS/proxy transport ကိုသာ ပျက်ပြယ်စေပြီး ပိတ်သည်။ ထို့နောက် နောက် request မတိုင်မီ ၎င်းကို ပြန်လည်ဖန်တီးသည်။
- Proxy ဖြေရှင်းသတ်မှတ်မှု၏ ဦးစားပေးအစီအစဉ်မှာ ခေါ်ယူမှုတစ်ခုချင်းစီ၏ `proxyUrl` → request အလိုက် account/dashboard context → `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` (စာလုံးအသေးပုံစံများ အပါအဝင်) ဖြစ်သည်။ ဖြေရှင်းသတ်မှတ်မှု error များသည် direct connection တစ်ခု ပေါက်ကြားသွားခြင်းမရှိစေရန် fail closed ဖြစ်သည်။ LMArena သည် ရည်ရွယ်ချက်ရှိရှိ `arena.ai` နှင့် ဆက်စပ်၍ ဖြေရှင်းသတ်မှတ်သည်။
- `byteResponse` သည် UTF-8 ပျက်စီးမှုမရှိဘဲ content type သတ်မှတ်ထားသော `data:` URL တစ်ခုကို ပြန်ပေးသည်။
- Error များမှာ `TlsClientUnavailableError` (package/addon ကို မရရှိနိုင်ခြင်း)၊ `TlsClientHangError` (deadline ကျော်လွန်ခြင်း) နှင့် ကန့်သတ်ထားသော profile/OS/proxy slot 128 ခုလုံး အသုံးပြုနေသည် သို့မဟုတ် ပိတ်နေဆဲဖြစ်သည့်အခါ `WreqTransportCapacityError` (မျှဝေအသုံးပြုသော session-capacity error code) တို့ဖြစ်သည်။

အထက်ပါ ယေဘုယျ `TlsClient` session သည် တည်တံ့သော browser-backed cookie state အတွက် အထူးပြုထားဆဲဖြစ်သည်။ လမ်းကြောင်းနှစ်ခုလုံးသည် cache လုပ်ထားသော wreq module loader တစ်ခုနှင့် process lifecycle hook တစ်ခုကို ပြန်လည်အသုံးပြုသည်။ သို့သော် ၎င်းတို့၏ cookie သက်တမ်းများကို ရည်ရွယ်ချက်ရှိရှိ မတူညီအောင် သတ်မှတ်ထားသောကြောင့် ၎င်းတို့၏ pool များကို သီးခြားထားသည်။

Profile များကို pin လုပ်ထားသော package က ပံ့ပိုးပေးသော်လည်း တကယ့် WAF လက်ခံနိုင်မှုသည် local contract test များနှင့် သီးခြားစီ ပြောင်းလဲနိုင်သည်။ Upstream browser တစ်ခုနှင့် တူညီမှုရှိကြောင်း မဆိုမီ fingerprint ပြောင်းလဲမှုများကို အတိအလင်း ခွင့်ပြုထားသော live account တစ်ခုဖြင့် စစ်ဆေးအတည်ပြုပါ။

## Claude Code Stealth Bundle

`cliCompatMode` ကို ဖွင့်ထားသည့်အခါ OmniRoute သည် အပြင်သို့ပို့မည့် Claude တောင်းဆိုမှုများကို `claude-cli` traffic နှင့် ခွဲခြားမရအောင် ပြန်လည်ပုံဖော်ပေးသည်။ Module သုံးခုက ပူးပေါင်းလုပ်ဆောင်သည်-

### `claudeCodeFingerprint.ts`

Billing header ထဲတွင် ထည့်သွင်းထားသည့် စာလုံး 3 လုံးပါ `cc_version` fingerprint ကို တွက်ချက်သည်-

```
SHA256(SALT + msg[4] + msg[7] + msg[20] + version)[:3]
```

- `FINGERPRINT_SALT = "59cf53e54c78"` (code ထဲတွင် အတိအကျသတ်မှတ်ထားပြီး တရားဝင် client နှင့် ကိုက်ညီသည်)
- Input များ- ပထမဆုံး user message စာသား၏ index 4၊ 7၊ 20 ရှိ စာလုံးများ + version string
- Output- စာလုံး 3 လုံးပါ hex prefix

### `claudeCodeCCH.ts` (Client Content Hash)

တရားဝင် Claude Code CLI က Bun/Zig မှတစ်ဆင့် တွက်ချက်သည့် server-side integrity check ဖြစ်သည်။ OmniRoute က ၎င်းကို `xxhash-wasm` ဖြင့် ပြန်လည်အကောင်အထည်ဖော်ထားသည်-

1. Body ကို `cch=00000;` placeholder ဖြင့် serialize လုပ်ပါ
2. `xxhash64(bytes, seed) & 0xFFFFF`
3. အရှေ့တွင် သုညဖြည့်ထားသည့် စာလုံး 5 လုံးပါ lowercase hex
4. `cch=00000;` ကို တွက်ချက်ရရှိသည့် token ဖြင့် အစားထိုးပါ

ကိန်းသေများ-

- Seed: `0x6e52736ac806831e`
- Pattern: `/\bcch=([0-9a-f]{5});/`

### `claudeCodeObfuscation.ts`

Upstream filter များက grep ဖြင့် ရှာမတွေ့နိုင်စေရန် "အရေးကြီးသော" client အမည်များ၏ ပထမစာလုံးနောက်တွင် Unicode **zero-width joiner** (`U+200D`) တစ်ခု ထည့်သွင်းသည်။ မူလ word list-

```
opencode, open-code, cline, roo-cline, roo_cline, cursor, windsurf,
aider, continue.dev, copilot, avante, codecompanion
```

အသုံးချသည့်နေရာများ- `system` block များ၊ `messages[].content` အားလုံးနှင့် `tools[].description` / `tools[].function.description`။ Operator က `setSensitiveWords()` မှတစ်ဆင့် လိုသလို အစားထိုးသတ်မှတ်နိုင်သည်။

### `claudeCodeCompatible.ts` — `anthropic-compatible-cc-*` provider များ

"Claude Code အစစ်" traffic ကိုသာ လက်ခံသည့် third-party Anthropic relay များအတွက်-

- `CLAUDE_CODE_COMPATIBLE_USER_AGENT = "claude-cli/2.1.258 (external, sdk-cli)"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_PACKAGE_VERSION = "0.112.1"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_RUNTIME_VERSION = "v26.3.0"`
- မူလအတိုင်း `anthropic-beta = "claude-code-20250219,interleaved-thinking-2025-05-14,effort-2025-11-24"`
- CC Compatible upstream တစ်ခုက redacted thinking stream များကို အထူးလိုအပ်သည့်အခါ connection တစ်ခုချင်းစီအလိုက် "Enable redact-thinking beta" toggle သည် `redact-thinking-2026-02-12` ကို ထည့်ပေးသည်
- Connection တစ်ခုချင်းစီအလိုက် "Enable summarized thinking display" toggle သည် `providerSpecificData.requestDefaults.summarizeThinking` ကို သိမ်းဆည်းပြီး display mode မသတ်မှတ်ရသေးသော CC Compatible thinking တောင်းဆိုမှုများတွင် `display: "summarized"` ကို ထည့်ပေးသည်
- `CONTEXT_1M_BETA_HEADER = "context-1m-2025-08-07"` (Opus/Sonnet 4.x မျိုးဆက်)
- မူလ path- `/v1/messages?beta=true`

Bundle တစ်ခုတည်းထဲရှိ ဆက်စပ် module များ-

- `claudeCodeConstraints.ts` — temperature + cache-control စည်းမျဉ်းများ
- `claudeCodeToolRemapper.ts` — tool အမည် ပြန်လည် mapping လုပ်ခြင်း
- `claudeCodeExtraRemap.ts` — နောက်ထပ် payload normalization

## Antigravity Stealth

Antigravity တောင်းဆိုမှုများသည် ခေါ်ဆိုသူ၏စာသားကို byte-for-byte မပြောင်းလဲဘဲ ထိန်းသိမ်းထားသည်။ OmniRoute သည် prompt များထဲသို့ zero-width စာလုံးများ မထည့်သွင်းသလို IDE client တစ်ခုကို တုပရန် tool များ၏အမည်ကို ပြောင်းခြင်း/ထည့်သွင်းခြင်းလည်း မပြုလုပ်ပါ။

### `antigravityHeaderScrub.ts`

Forward မလုပ်မီ Stainless SDK marker များ (`x-stainless-lang`, `x-stainless-package-version`, `x-stainless-os`, `x-stainless-arch`, `x-stainless-runtime`, `x-stainless-runtime-version`, `x-stainless-timeout`, `x-stainless-retry-count`, `x-stainless-helper-method`) ကို ဖယ်ရှားသည်။

### ⚠️ အန္တရာယ်- `ANTIGRAVITY_CREDITS=always` (account ပိတ်ပင်ခံရနိုင်ခြေ အလွန်မြင့်သောနေရာ)

`ANTIGRAVITY_CREDITS=always` (`open-sse/executors/antigravity.ts` က အသုံးပြုသည်) သည် Google ၏ free-tier quota ဖြင့် ကန့်သတ်ခွင့်ပြုမည့်အစား တောင်းဆိုမှု **တိုင်းကို** Antigravity AI Credit Overages (အခပေး Google credit များ) မှတစ်ဆင့် route လုပ်သည်။ ၎င်းကို feature တစ်ခုအဖြစ် မှတ်တမ်းတင်ထားသော်လည်း **ကျွန်ုပ်တို့တွေ့ရသည့် ToS ချိုးဖောက်မှုဆိုင်ရာ report များထဲတွင် အဖြစ်အများဆုံး တစ်ခုတည်းသောအကြောင်းရင်းဖြစ်သည်** — `=always` ဖြင့် နာရီအနည်းငယ် အသုံးပြုပြီးနောက် Google Ultra account အများအပြားသည် `403 / "service disabled for ToS violation" / insufficient_quota` ဖြင့် ပိတ်ပင်ခံခဲ့ရသည်။

Upstream enforcement သည် OmniRoute က ကာကွယ်နိုင်သည့်အရာမဟုတ်ဘဲ **Google ဘက်တွင်** ဖြစ်သည်။ Env var အမည်နှင့် ရှိပြီးသား docs များကြောင့် ၎င်းသည် ဘေးကင်းစွာ ပြောင်းဖွင့်နိုင်သည့် setting တစ်ခုဟု ထင်ရသော်လည်း အမှန်မှာ မဟုတ်ပါ။

**ဤအရာက free-tier သီးသန့်အသုံးပြုမှုထက် abuse detection ကို ပိုမိုပြင်းထန်စွာ ဖြစ်စေသည့်အကြောင်းရင်းများ-**

- Google account တစ်ခုတည်းတွင် အလိုအလျောက် ငွေသုံးစွဲမှုကို ဆက်တိုက်လုပ်ဆောင်ခြင်းသည် free-tier က quota ပြည့်ပြီး ရပ်သွားခြင်းနှင့်မတူဘဲ အခြားပုံစံဖြင့် flag လုပ်ခံရသည်။
- Credit overage များတွင် rate အမြင့်ဆုံးကန့်သတ်ချက် မရှိသောကြောင့် မှားယွင်းစွာ configure လုပ်ထားသည့် client တစ်ခုသည် မိနစ်ပိုင်းအတွင်း USD ရာပေါင်းများစွာ ကုန်ဆုံးစေနိုင်ပြီး API key ပြန်လည်ရောင်းချခြင်း သို့မဟုတ် bot traffic ကဲ့သို့ မြင်ရနိုင်သည်။
- တူညီသော external IP မှ OmniRoute user အများအပြားက overage credit များကို ပြိုင်တူအသုံးပြုခြင်းသည် သံသယဖြစ်စေသည့် signal ကို ပိုမိုပြင်းထန်စေသည်။

**အကြံပြုထားသော ရပ်တည်ချက်-**

1. Operator က အခပေး credit နှင့် account enforcement အန္တရာယ်ကို အတိအကျ လက်ခံထားခြင်းမရှိပါက မူလ `ANTIGRAVITY_CREDITS=off` ကို ဆက်ထားပါ။ `retry` သည် ပုံမှန်တောင်းဆိုမှုကို ဦးစွာပို့ပြီး သတ်မှတ်ချက်ပြည့်မီသည့် quota 429 ရရှိပြီးနောက် အများဆုံးတစ်ကြိမ်သာ credit များ ထည့်သွင်းသည်။ `always` သည် ပထမဆုံးတောင်းဆိုမှုတွင်ပင် credit များကို ထည့်သွင်းသည်။
2. Antigravity account တစ်ခုတည်းကို အပြည့်အဝ ဖိအားပေးမည့်အစား **Auto-Combo မှတစ်ဆင့် provider များအကြား load ကို ဖြန့်ဝေပါ** (`model: "auto"` သို့မဟုတ် `kr/glm/etc`-combo)။
3. Antigravity provider ၏ edit page တွင် **connection တစ်ခုချင်းစီအလိုက် RPM ကန့်သတ်ချက်များ သတ်မှတ်ပါ** (Dashboard → Providers → Antigravity → connection → rate limit)။ ဆက်တိုက်အသုံးပြုမှုအတွက် 30–60 RPM သည် ကာကွယ်ပြောဆိုနိုင်သော အမြင့်ဆုံးကန့်သတ်ချက်ဖြစ်သည်။
4. **Operator က ထိန်းချုပ်ထားသည့် တည်ငြိမ်သော upstream networking ကို အသုံးပြုပါ**၊ ထို့အပြင် ဆက်စပ်မှုမရှိသည့် user များ သို့မဟုတ် workload များကြားတွင် account တစ်ခုတည်းကို မျှဝေခြင်းမှ ရှောင်ကြဉ်ပါ။
5. **ပိတ်ပင်ခံရပါက**- Google က ပေးပို့သည့် `quota_exceeded` / `service disabled` response body အတိအကျနှင့်အတူ `support.google.com` → "Restore Workspace/Account access" မှတစ်ဆင့် အယူခံဝင်ပါ။ ပြန်လည်ဖွင့်ပေးမည်ဟု အာမခံချက်မရှိပါ။

Environment reference တွင် credits mode တစ်ခုချင်းစီ၏ account နှင့် ငွေသုံးစွဲမှုဆိုင်ရာ သက်ရောက်မှုများကို မှတ်တမ်းတင်ထားသည်။

သက်ဆိုင်ရာနေရာများ-

- `open-sse/executors/antigravity.ts` — `process.env.ANTIGRAVITY_CREDITS` ကို ဖတ်သည်
- `src/lib/oauth/providers/antigravity.ts` — credential ချိတ်ဆက်စီမံမှု
- မူရင်း incident report- Discussion [#1183](https://github.com/diegosouzapw/OmniRoute/discussions/1183)

## CLI Fingerprint Registry — `open-sse/config/cliFingerprints.ts`

တရားဝင် CLI များ၏ mitmproxy trace များမှ ဖမ်းယူထားသော header အစီအစဉ်နှင့် JSON body field အစီအစဉ်ကို **အတိအကျ** သတ်မှတ်ထားသည့် provider အလိုက် ဇယားဖြစ်သည်။ လက်ရှိ မှတ်ပုံတင်ထားသည်များမှာ `codex`, `claude` နှင့် `antigravity`, `github` တို့အတွက် `providerHeaderProfiles.ts` ထဲရှိ runtime မှ ရယူဖန်တီးထားသော profile များ ဖြစ်သည်။

```ts
interface CliFingerprint {
  headerOrder: string[]; // စာလုံးအကြီးအသေး ခွဲခြားသည်
  bodyFieldOrder: string[]; // ထိပ်ဆုံးအဆင့် JSON key များ
  userAgent?: string | (() => string);
  extraHeaders?: Record<string, string>;
}
```

Provider တစ်ခုချင်းစီအတွက် env မှတစ်ဆင့် ဖွင့်/ပိတ်နိုင်သည် (အောက်တွင် ကြည့်ပါ)။ ပိတ်ထားသည့်အခါ header/body key များသည် Node/JSON က ပေးသည့် မည်သည့်အစီအစဉ်အတိုင်းမဆို ပေါ်လာမည်ဖြစ်ပြီး fingerprint ဖော်ထုတ်ရန် လွယ်ကူသည်။

## MITM Proxy (Antigravity, Linux/macOS/Windows)

Binary များကို `OPENAI_BASE_URL` မှတစ်ဆင့် လမ်းကြောင်းပြောင်း၍မရသော CLI များအတွက် OmniRoute သည် TLS ကို အဆုံးသတ်ပေးသည့် local proxy တစ်ခုကို လုပ်ဆောင်သည်။ Endpoint များသည် `src/app/api/cli-tools/antigravity-mitm/` အောက်တွင် ရှိသည်။

| နည်းလမ်း | Endpoint                                | ရည်ရွယ်ချက်                                              |
| -------- | --------------------------------------- | -------------------------------------------------------- |
| GET      | `/api/cli-tools/antigravity-mitm`       | အခြေအနေ — လုပ်ဆောင်နေမှု၊ pid၊ dnsConfigured၊ certExists |
| POST     | `/api/cli-tools/antigravity-mitm`       | MITM စတင်ရန် (`apiKey` + `sudoPassword` လိုအပ်သည်)       |
| DELETE   | `/api/cli-tools/antigravity-mitm`       | MITM ရပ်တန့်ရန်                                          |
| GET      | `/api/cli-tools/antigravity-mitm/alias` | Model alias များကို စာရင်းပြုစုရန်                       |
| PUT      | `/api/cli-tools/antigravity-mitm/alias` | Tool တစ်ခုအတွက် model alias များကို သိမ်းဆည်းရန်         |

ကြားဖြတ်ဖမ်းယူမည့် ပစ်မှတ် host: **`daily-cloudcode-pa.googleapis.com`** (Antigravity ၏ upstream)။

### စတင်မှု အစီအစဉ် (`src/mitm/manager.ts::startMitm`)

1. `selfsigned` မှတစ်ဆင့် self-signed certificate ထုတ်လုပ်ရန် (RSA-2048, SHA-256, 1y) — `cert/generate.ts`
2. Certificate ကို system trust store ထဲသို့ ထည့်သွင်းရန် — `cert/install.ts`
3. Hosts entry `127.0.0.1 daily-cloudcode-pa.googleapis.com` ကို ထည့်ရန် — `dns/dnsConfig.ts`
4. `ROUTER_API_KEY` + `MITM_LOCAL_PORT` (မူလတန်ဖိုး `443`) ဖြင့် `src/mitm/server.cjs` ကို spawn လုပ်ရန်
5. PID ကို `<DATA_DIR>/mitm/.mitm.pid` တွင် အမြဲတမ်းသိမ်းဆည်းရန်

### Linux dynamic trust-store ရှာဖွေခြင်း — `cert/install.ts`

`getLinuxCertConfig()` သည် ဦးစားပေးစာရင်းတစ်ခုကို အစဉ်လိုက် စစ်ဆေးပြီး ပထမဆုံးတွေ့ရှိသော directory ကို ရွေးချယ်သည်။

| Distro မျိုးနွယ်         | Directory                                   | Update command           |
| ------------------------ | ------------------------------------------- | ------------------------ |
| Debian / Ubuntu          | `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| Arch / CachyOS / Manjaro | `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| Fedora / RHEL / CentOS   | `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| openSUSE                 | `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Certificate ဖိုင်အမည်: `omniroute-mitm.crt`။ `getCertFingerprint()` မှတစ်ဆင့် fingerprint ကိုက်ညီမှု စစ်ဆေးသည် (DER ၏ SHA-1)။

ထို့အပြင် `certutil` ကို အသုံးပြုနိုင်သည့်အခါ `updateNssDatabases()` သည် အသုံးပြုသူတစ်ဦးချင်းစီ၏ NSS DB များဖြစ်သော `~/.pki/nssdb`, `~/snap/chromium/.../nssdb` နှင့် Firefox profile အားလုံး (snap အပါအဝင်) ထဲသို့ **`OmniRoute MITM Root CA`** ဟူသော nickname ဖြင့် ထည့်သွင်းသည်။

### macOS / Windows

- **macOS:** `security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain`
- **Windows:** အဆင့်မြှင့်ခွင့်ဖြင့် PowerShell → `certutil -addstore Root`

### Auth

MITM endpoint အားလုံးတွင် စီမံခန့်ခွဲမှု auth (`requireCliToolsAuth`) လိုအပ်သည်။ sudo password ကို module scope ထဲတွင် cache လုပ်ထားပြီး (`globalThis` တွင် မည်သည့်အခါမျှ မထားပါ) `stopMitm()` ခေါ်သည့်အခါ ရှင်းလင်းသည်။

## ဝင်လာသော Header များကို သန့်စင်ခြင်း

OmniRoute သည် request တစ်ခု Cursor မှ ဝင်ရောက်လာသည့်အခါ `User-Agent: Cursor/X.Y.Z` ကို Claude upstream သို့ မပေါက်ကြားစေရန် မပို့မီ ဝင်လာသော client header များကို ဖယ်ရှားသန့်စင်သည်။ Zod schema များနှင့် unit test များနှင့် အမြဲတစ်ပြေးညီ ထိန်းသိမ်းထားသော denylist ကို `src/shared/constants/upstreamHeaders.ts` တွင် ကြည့်ပါ။

## Provider တစ်ခုက Fingerprint ပြောင်းသည့်အခါ အပ်ဒိတ်လုပ်ခြင်း

1. `mitmproxy` ဖြင့် တရားဝင် CLI traffic ကို ဖမ်းယူပါ (TLS interception + dump)
2. JA3/JA4 နှင့် header အစီအစဉ်အတိအကျကို ထုတ်ယူပါ
3. သက်ဆိုင်ရာ `CLI_FINGERPRINTS[...]` entry ကို အပ်ဒိတ်လုပ်ပါ
4. `.env.example` ရှိ ကိုက်ညီသော `*_USER_AGENT` မူလတန်ဖိုးကို မြှင့်တင်ပါ
5. TLS handshake ကိုယ်တိုင် ပြောင်းလဲသွားပါက သက်ဆိုင်ရာ provider wrapper သို့မဟုတ် wreq-js `browser:` option ကို အပ်ဒိတ်လုပ်ပါ
6. Provider သီးသန့် TLS test များနှင့် လက်ရှိအသုံးပြုနေသော provider အပေါ် manual canary စမ်းသပ်မှုတစ်ခုကို လုပ်ဆောင်ပါ
7. Patch release ဖြင့် ထုတ်ပြန်ပြီး `CHANGELOG.md` တွင် မှတ်တမ်းတင်ပါ
