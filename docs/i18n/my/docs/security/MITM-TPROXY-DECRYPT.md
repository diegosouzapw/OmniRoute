TPROXY transparent decrypt သည် [Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM stack အတွက် OmniRoute ၏ **5 ခုမြောက် capture mode** ဖြစ်သည်။ ၎င်းသည် Linux ပေါ်ရှိ
local outbound HTTPS traffic ကို kernel TPROXY + policy routing အသုံးပြု၍ ကြားဖြတ်ဖမ်းယူပြီး
**decrypt** လုပ်သည် — `/etc/hosts` ကို spoof လုပ်ရန် **မလိုအပ်သလို**
OS တစ်ခုလုံးနှင့်သက်ဆိုင်သည့် system-proxy settings များကို ပြောင်းလဲရန်လည်း **မလိုအပ်ပါ**။
၎င်းသည် headless environment များတွင် အဆင်ပြေပြီး
(ရှင်းလင်းရန်လိုသော DNS ပြင်ဆင်မှုများမရှိပါ) reboot လုပ်သည့်အခါ firewall rules များသည် အလိုအလျောက် flush ဖြစ်သည်။

အခြား capture mode များနှင့်မတူဘဲ TPROXY သည် host တစ်ခုချင်းစီအတွက် setup လုပ်ရန် မလိုအပ်ပါ။ ၎င်းသည်
သတ်မှတ်ထားသော target port တစ်ခုရှိ **မည်သည့်** destination host ကိုမဆို ပွင့်လင်းမြင်သာစွာ
ကြားဖြတ်ဖမ်းယူပြီး၊ SNI hostname တစ်ခုချင်းစီအတွက် runtime တွင် ထုတ်ပေးသော leaf certificate ဖြင့်
TLS ကို အဆုံးသတ်ကာ၊ decrypt လုပ်ထားသည့် exchange ကို ဖမ်းယူပြီး request ကို မူလ destination သို့
ပြန်လည် encrypt လုပ်၍ ပို့သည်။

> **Linux-only၊ root-only၊ opt-in။** ဤ mode သည် Linux၊ C toolchain ဖြင့်
> build လုပ်ထားသော native addon နှင့် **CAP_NET_ADMIN** capability (ပုံမှန်အားဖြင့် root) တို့ လိုအပ်သည်။ ၎င်းကို
> loopback-only AgentBridge API နောက်ကွယ်တွင် ကန့်သတ်ထားပြီး ပုံမှန်အားဖြင့် ပိတ်ထားသည်။ မည်သည့် host ကိုမဆို
> လက်မှတ်ရေးထိုးပေးနိုင်သော ယုံကြည်စိတ်ချရသည့် MITM CA သည် အလွန်အစွမ်းထက်သော capability တစ်ခုဖြစ်သည် — [§6 လုံခြုံရေး](#6-security) ကို ကြည့်ပါ။

## §1 ၎င်းသည် ဘာလဲ၊ မည်သည့်အချိန်တွင် အသုံးပြုသင့်သလဲ

အခြား capture mode လေးခုစီတွင် ကန့်သတ်ချက်တစ်ခုစီရှိသည်-

| Mode              | Traffic ကို လမ်းကြောင်းပြောင်းပုံ                  | ကန့်သတ်ချက်                                                            |
| ----------------- | -------------------------------------------------- | ---------------------------------------------------------------------- |
| AgentBridge       | သတ်မှတ်ထားသော host အစုအတွက် `/etc/hosts` DNS spoof | register လုပ်ထားသော IDE-agent host များသာ                              |
| Custom Hosts      | host တစ်ခုချင်းစီအတွက် `/etc/hosts` DNS spoof      | host တစ်ခုလျှင် entry တစ်ခု၊ hosts ကို ပြင်ရန် sudo လိုအပ်သည်          |
| HTTP_PROXY        | `HTTP_PROXY`/`HTTPS_PROXY` env                     | env var ကို လိုက်နာသော app များသာ                                      |
| System-wide proxy | OS proxy settings                                  | global state ကို ပြောင်းလဲသည်၊ မူလအခြေအနေသို့ ပြန်ပြောင်းရန် လိုအပ်သည် |

TPROXY transparent decrypt သည် traffic ကို **kernel** layer တွင် လမ်းကြောင်းပြောင်းပေးသည်။ ၎င်းသည်
`mangle OUTPUT` chain တွင် target port (မူလသတ်မှတ်ချက် `443`) သို့သွားသည့် local outbound TCP connection အသစ်များကို
mark လုပ်ပြီး၊ `ip rule` တစ်ခုက mark လုပ်ထားသော packet များကို local delivery သို့ ပြန်လည်လမ်းကြောင်းသတ်မှတ်ပေးသည်။
ပြန်လည်ဝင်ရောက်လာသည့်အခါ `mangle PREROUTING` ရှိ `TPROXY` target က ၎င်းတို့ကို
**IP_TRANSPARENT** listener တစ်ခုထံ လွှဲပေးသည် — ထို listener သည် TLS ကို အဆုံးသတ်ပြီး plaintext ကို ဖမ်းယူသည်။

အောက်ပါအခြေအနေများနှင့် ကိုက်ညီသော process တစ်ခုမှ traffic ကို ဖမ်းယူပြီး decrypt လုပ်လိုသည့်အခါ အသုံးပြုပါ-

- AgentBridge တွင် register မလုပ်ထားသော host တစ်ခုနှင့် ဆက်သွယ်ပြီး
- `HTTP_PROXY` ကို မလိုက်နာသည့်အပြင်
- system-wide proxy ပြောင်းလဲမှုဖြင့် မနှောင့်ယှက်လိုသည့်အခါ။

ကြားဖြတ်ဖမ်းယူမှုသည် kernel အတွင်းတွင် ဖြစ်ပေါ်သောကြောင့် မူလ process တွင် **configuration
ပြောင်းလဲရန်မလိုအပ်ပါ** — သို့သော် ထို process သည် OmniRoute က install လုပ်ထားသော dynamic CA ကို
ယုံကြည်ရမည် ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) ကို ကြည့်ပါ)။

## §2 လိုအပ်ချက်များ

| လိုအပ်ချက်         | အသေးစိတ်အချက်                                                                                                                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**             | Linux တွင်သာ — **IP_TRANSPARENT** သည် Linux အတွက်သာဖြစ်သော socket option တစ်ခုဖြစ်သည်။ အခြား platform အားလုံးတွင် loader က "အသုံးမပြုနိုင်ပါ" ဟု ပြန်ပေးသည်။                                |
| **Privilege**      | transparent socket ဖန်တီးရန်နှင့် `iptables`/`ip` စည်းမျဉ်းများကို အသုံးချရန် **CAP_NET_ADMIN** capability လိုအပ်သည် — လက်တွေ့တွင် root အဖြစ် run ပါ။                                       |
| **Native addon**   | N-API addon အသေးစားတစ်ခု (`src/mitm/tproxy/native/transparent.c`) ကို build လုပ်ထားရမည် သို့မဟုတ် prebuild အဖြစ် ထည့်သွင်းပေးထားရမည်။ [§3](#3-the-native-ip_transparent-addon) ကို ကြည့်ပါ။ |
| **Kernel modules** | `TPROXY`, `mangle` နှင့် `mark` match support ပါဝင်သော `iptables` (kernel 6.8.0 ဖြင့် စစ်ဆေးအတည်ပြုထားသည်)။                                                                                 |

**ချို့ယွင်းမှုရှိချိန်တွင် ပုံမှန်အတိုင်း ဆက်လက်အလုပ်လုပ်ခြင်း:** လိုအပ်ချက်တစ်ခုခု မရှိပါက (Linux မဟုတ်ခြင်း၊ toolchain မရှိခြင်း၊
addon ကို build မလုပ်ထားခြင်း) addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
သည် exception ပစ်မည့်အစား `null` ကို ပြန်ပေးသည်။ ထို့နောက် capture-mode status တွင်
`available: false` ဟု ဖော်ပြပြီး dashboard toggle ကို
"TPROXY decrypt အတွက် Linux + root + native addon လိုအပ်သည်" ဟူသော tooltip ဖြင့် **ပိတ်ထားမည်**ဖြစ်ကာ
OmniRoute ၏ ကျန်အစိတ်အပိုင်းများသည် ဆက်လက်အလုပ်လုပ်နေမည်ဖြစ်သည်။

## §3 Native IP_TRANSPARENT addon

Node ၏ `net` module သည် `bind()` မတိုင်မီ `setsockopt(IP_TRANSPARENT)` ကို မလုပ်နိုင်ပါ။ TPROXY
အတွက် ယင်းကို မဖြစ်မနေ လိုအပ်သည် (မဟုတ်ပါက kernel က redirect လုပ်ထားသော packet များကို စွန့်ပစ်သည်)။ Addon
(`src/mitm/tproxy/native/transparent.c`၊ `binding.gyp` မှတစ်ဆင့် build လုပ်ထားသည်) သည် function သုံးခုကို ဖော်ထုတ်ပေးသော N-API
module အသေးစားတစ်ခုဖြစ်ပြီး `transparentSocket.ts` မှတစ်ဆင့် အသုံးပြုသည်-

| Addon function                        | Socket လုပ်ဆောင်ချက်                                                                                               | အသုံးပြုသည့်နေရာ                                                                                  |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()` ကို လုပ်ဆောင်ပြီး raw fd ကို ပြန်ပေးသည် | transparent capture listener (Node သည် `server.listen({ fd })` မှတစ်ဆင့် fd ကို လက်ခံအသုံးပြုသည်) |
| `setSocketMark(fd, mark)`             | ရှိပြီးသား fd တစ်ခုပေါ်တွင် `setsockopt` **SO_MARK** ကို သတ်မှတ်သည်                                                | loop တားဆီးခြင်း (proxy ၏ ကိုယ်ပိုင် socket များကို mark သတ်မှတ်ခြင်း)                            |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()` မတိုင်မီ `socket()` + **SO_MARK** ကို လုပ်ဆောင်ပြီး fd ကို ပြန်ပေးသည်                     | ပြန်လည် encrypt လုပ်ထားသော upstream forward (SYN တွင် mark ပါဝင်သည်)                              |

မူလ destination ကို `socket.localAddress`/`localPort` မှ ဖတ်ယူသည် — TPROXY က
၎င်းကို ထိန်းသိမ်းထားသောကြောင့် **SO_ORIGINAL_DST**/NAT lookup မလိုအပ်ပါ။

### Addon ကို build လုပ်ခြင်း

```bash
npm run build:native:tproxy      # src/mitm/tproxy/native သို့ ဝင်ပြီး node-gyp rebuild လုပ်ပါ
                                 # -> native/build/Release/transparent.node
```

- `npm run build` လုပ်နေစဉ် `scripts/build/build-tproxy-native.mjs` သည် `node-gyp
rebuild` ကို လုပ်ဆောင်သည်။ ၎င်းသည် **Linux အတွက်သာဖြစ်ပြီး ပျက်ကွက်လျှင်လည်း အဓိက build ကို မရပ်တန့်စေပါ** — toolchain မရှိပါက
  capture mode ကို အသုံးမပြုနိုင်ဘဲသာ ကျန်ရှိမည်ဖြစ်သည်။
- `assembleStandalone.mjs` သည် `build/Release/transparent.node` ကို
  standalone bundle ထဲသို့ ကူးယူသည်။ `transparentSocket.ts` က ၎င်းကို module-relative နှင့်
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`) နည်းလမ်းနှစ်မျိုးလုံးဖြင့် ရှာဖွေဖြေရှင်းသည်။

  ဘယ်သောအခါမှ commit မလုပ်ပါ**။

Loader သည် အောက်ပါ ဦးစားပေးအစီအစဉ်အတိုင်း စမ်းသပ်ရှာဖွေသည်-

## §4 SNI တစ်ခုချင်းစီအလိုက် dynamic CA နှင့် trust-store ထည့်သွင်းကိရိယာ

> **#6684 အပ်ဒိတ်:** AgentBridge static server (`src/mitm/server.cjs`) သည် ယခုအခါ
> static self-signed leaf တစ်ခုတည်းအစား ဤတူညီသော CA/leaf ဗိသုကာပုံစံကို
> မျှဝေအသုံးပြုပါသည်။ ၎င်းသည် **သီးခြား** CA instance
> (`src/mitm/cert/rootCa.ts`၊ `<DATA_DIR>/mitm/ca.key`/`ca.crt` တွင် အမြဲတမ်းသိမ်းဆည်းထားသည်)
> ကို အသုံးပြုပြီး ယခင်ကတည်းကရှိသော `omniroute-mitm.crt` trust-store slot အောက်တွင်
> ထည့်သွင်းပါသည် (ထိုနေရာရှိ ယခင် leaf တစ်ခုတည်းကို အစားထိုးခြင်းဖြစ်ပြီး dual-trust
> ရှင်းလင်းမှု မလိုအပ်ပါ)။ ၎င်းကို အောက်ပါ TPROXY ၏ ကိုယ်ပိုင်
> `omniroute-tproxy-ca.crt` slot နှင့် လုံးဝသီးခြားထားပါသည်။
> AgentBridge အသစ်ထည့်သွင်းမှုများသည် CA model ကို အလိုအလျောက်ရရှိပါသည်။ ယခင် static
> leaf ကို ယုံကြည်ထားပြီးသား ထည့်သွင်းမှုတစ်ခုသည် operator က
> `MITM_ROOT_CA_ENABLED=true` မှတစ်ဆင့် ရွေးချယ်ဖွင့်မချင်း ၎င်းကို ဆက်လက်အသုံးပြုသည်
> (`src/mitm/cert/migration.ts` ကို ကြည့်ပါ) — **မည်သည့်** host အတွက်မဆို leaf တစ်ခုကို
> လက်မှတ်ရေးထိုးပေးနိုင်သော ယုံကြည်ရသည့် MITM CA သည် ယခင် fixed-SAN leaf ထက်
> သိသိသာသာ ပိုမိုအစွမ်းထက်သောကြောင့် ယုံကြည်ထားပြီးသား ထည့်သွင်းမှုတစ်ခုအတွက်
> ဤပြောင်းလဲမှုကို အသိပေးခြင်းမရှိဘဲ ဘယ်တော့မှ မလုပ်ဆောင်ပါ။

ယခင်က static AgentBridge MITM cert အလုပ်လုပ်ခဲ့ခြင်းမှာ AgentBridge က
**သတ်မှတ်ထားသော** host အစုကို DNS-spoof လုပ်သောကြောင့်သာ ဖြစ်သည် (ယခု ၎င်းကို
အောက်ပါ model နှင့် ပေါင်းစည်းထားသည်)။ TPROXY သည် **မည်သည့်** host ကိုမဆို
ကြားဖြတ်ဖမ်းယူသဖြင့် ၎င်း၏ listener သည် client တောင်းဆိုသည့် SNI တိုင်းအတွက်
မှန်ကန်သော leaf ကို တင်ပြရမည် — antigravity host 4 ခုသာမဟုတ်ဘဲ
`MITM_TOOL_HOSTS` အစုအပြည့်အစုံ (tool entry 9 ခု) အတွက် AgentBridge တွင်
ယခုလိုအပ်သည့် အလားတူသတ်မှတ်ချက်ဖြစ်သည်။

### Dynamic CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` သည် `selfsigned` dependency ပေါ်တွင် တည်ဆောက်ထားသော local CA
တစ်ခုကို လည်ပတ်စေပြီး အောက်ပါတို့ကို လုပ်ဆောင်သည်-

- `generateMitmCa()` မှတစ်ဆင့် သက်တမ်းရှည် CA တစ်ခုကို ထုတ်ပေးသည် (CN
  `"OmniRoute MITM CA"`၊ သက်တမ်း 10 နှစ်၊ `basicConstraints CA=true` +
  `keyUsage keyCertSign,cRLSign`၊ 2048-bit RSA / SHA-256)။
- `issueLeafCert()` မှတစ်ဆင့် **SNI hostname တစ်ခုချင်းစီအတွက် လိုအပ်ချိန်တွင် leaf
  တစ်ခု ထုတ်ပေးသည်** (သက်တမ်း 1 နှစ်၊ `subjectAltName` = SNI host)၊ ထို့နောက်
  hostname တစ်ခုစီအတွက် `tls.SecureContext` တစ်ခုကို cache လုပ်ထားသည်။
- TLS အဆုံးသတ်ပေးသော server အတွက် `createSNICallback()` ကို ထုတ်ပေးသည်
  ([§5](#5-how-decrypt-and-capture-work) ကို ကြည့်ပါ)။
- restart များကြားတွင် CA ကို မပြောင်းလဲဘဲ တည်ငြိမ်စေရန် `existingCa` ဖြင့်
  တည်ဆောက်နိုင်သည် (ထို့ကြောင့် trust store ကို ပြန်လည်ထည့်သွင်းရန် မလိုအပ်ပါ)။

CA private key သည် **စက်အပြင်သို့ လုံးဝထွက်မသွားပါ**။

### Trust-store ထည့်သွင်းကိရိယာ (`src/mitm/tproxy/caTrust.ts`)

ကြားဖြတ်ဖမ်းယူခံရသော client သည် dynamic CA ကို ယုံကြည်ရမည်ဖြစ်သောကြောင့် capture
mode ကို စတင်သည့်အခါ CA cert ကို OS trust store အတွင်းရှိ **သီးသန့် slot** —
`omniroute-tproxy-ca.crt` (constant `TPROXY_CA_CERT_NAME`) — တွင် ထည့်သွင်းပါသည်။
၎င်းကို static MITM cert ၏ slot (`omniroute-mitm.crt`) နှင့် သီးခြားထားသဖြင့်
တစ်ခုက အခြားတစ်ခုကို ဘယ်တော့မှ ထပ်ရေးမည်မဟုတ်ပါ။

`installTproxyCa(caPem, sudoPassword?)` သည် distro ၏ anchor directory ကို
(အစဉ်လိုက်: Debian ပုံစံကို ဦးစွာ) ရှာဖွေစစ်ဆေးပြီး ကိုက်ညီသော refresh command ကို
လုပ်ဆောင်သည်-

| Anchor directory                            | Refresh command          |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

ထည့်သွင်းမှုတွင် PEM ကို ယာယီဖိုင်တစ်ခုသို့ အဆင့်ဆင့်ပြင်ဆင်ပြီးနောက် anchor dir ကို
အထူးအခွင့်အရေးဖြင့် `mkdir -p` လုပ်သည်၊ ပြင်ဆင်ထားသောဖိုင်ကို ထိုနေရာသို့ `cp`
လုပ်ပြီး refresh command ကို လုပ်ဆောင်သည်။ `uninstallTproxyCa()` သည် သီးသန့် slot
ကိုသာ ဖယ်ရှားပြီး (static MITM cert ကို မထိခိုက်စေဘဲ) refresh လုပ်သည် —
Linux မဟုတ်သောစနစ်များတွင် မည်သည့်လုပ်ဆောင်ချက်မျှ မလုပ်ပါ။

အထူးအခွင့်အရေးလိုအပ်သော command အားလုံးကို `execFileWithPassword`
(`src/mitm/systemCommands.ts`) မှတစ်ဆင့် လုပ်ဆောင်သည် — **argument array များဖြင့်၊
shell မပါဘဲ၊ string interpolation မပါဘဲ** `spawn` ကို အသုံးပြုသည်
(Hard Rule #13)။ Process သည် root ဖြစ်သည့်အခါ (ဥပမာ VPS) target ကို တိုက်ရိုက်
လုပ်ဆောင်ပြီး password မလိုအပ်ပါ။ root မဟုတ်သော desktop တွင် `sudoPassword` ကို
stdin ပေါ်ရှိ `sudo -S` မှတစ်ဆင့် ပေးပို့သည်။

> Desktop ၏ `sudoPassword` ကို trust-store ထည့်သွင်းမှုအား ခွင့်ပြုရန် POST body
> ထဲတွင် ပေးပို့သည်။ Process သည် root ဖြစ်ပါက ၎င်းကို လုံးဝလျစ်လျူရှုသည်။

## §5 ကုဒ်ဖြည်ခြင်းနှင့် ဖမ်းယူခြင်း အလုပ်လုပ်ပုံ

Pipeline (`src/mitm/tproxy/` အောက်တွင် အားလုံးရှိသည်):

```
စက်တွင်း app  ──TCP/443──▶  mangle OUTPUT က ချိတ်ဆက်မှုကို အမှတ်အသားပြုသည် (fwmark)
                            ip rule → local route table → lo
                            mangle PREROUTING TPROXY → IP_TRANSPARENT listener (port 8443)
                                │  captureMode.ts: မူလပန်းတိုင်ကို socket.localAddress မှ ဖတ်သည်
                                ▼
                            tlsCapture.ts:
                              1. per-SNI leaf (dynamicCert) ဖြင့် CLIENT ၏ TLS ကို အဆုံးသတ်သည်
                              2. အတွင်းပိုင်း http.Server က ကုဒ်ဖြည်ထားသော plaintext ကို parse လုပ်သည်
                              3. capture → source: "tproxy" ဖြင့် globalTrafficBuffer.push()
                                 (sanitizeHeaders + maskSecret ကို အသုံးပြုထားသည်)
                              4. bypass-marked socket (connectMarked, anti-loop) မှတစ်ဆင့်
                                 မူလပန်းတိုင်သို့ ပြန်လည်ကုဒ်ဝှက်ပြီး forward လုပ်သည်
                                │
                                ▼
                            မူလ upstream (api.example.com)
```

- **TLS အဆုံးသတ်ခြင်း** (`createTlsCaptureServer`): dynamic CA ၏ SNI callback ကို အသုံးပြုပြီး ကြားဖြတ်ဖမ်းယူထားသော raw socket ကို server-side `tls.TLSSocket` ဖြင့် wrap လုပ်ကာ၊ ထို့နောက် ကုဒ်ဖြည်ထားသော stream ကို အတွင်းပိုင်း `http.Server` သို့ လွှဲပေးသည် (စံ MITM အဆုံးသတ်နည်းလမ်း)။ တုံ့ဆိုင်းနေသော tunnel ကြောင့် file descriptor များ ကုန်ခန်းမသွားစေရန် socket များ၏ သက်တမ်းကို `MITM_IDLE_TIMEOUT_MS` ဖြင့် ကန့်သတ်ထားသည်။
- **ဖမ်းယူခြင်း** (`handleDecryptedRequest`): `source: "tproxy"`၊ `"in-flight"` မှ စတင်သော status၊ `sanitizeHeaders()` ဖြင့် စီမံထားသော header များနှင့် `maskSecret()` ဖြင့် စီမံထားသော body များပါဝင်သည့် `InterceptedRequest` တစ်ခုကို buffer ထဲ မဝင်မီ push လုပ်သည်။ ထို့နောက် entry ကို response၊ size များနှင့် latency တို့ဖြင့် update လုပ်သည်။
- **ပြန်လည်ကုဒ်ဝှက်ထားသော forward** (`createForward` / `realForward`): မူလပန်းတိုင်သို့ ပြန်လည်ကုဒ်ဝှက်ပေးသည်။ `rejectUnauthorized` သည် ပုံမှန်အားဖြင့် **`true`** ဖြစ်သည် (ပုံမှန်အတိုင်း လုံခြုံသည်) — upstream cert ကို client တောင်းဆိုခဲ့သည့် SNI/Host နှင့် တိုက်ဆိုင်စစ်ဆေးသောကြောင့် မူလ client က ငြင်းပယ်မည့်အရာကို proxy ကလည်း အတိအကျ ငြင်းပယ်သည်။

### Loop ကာကွယ်ခြင်း (SO_MARK)

Rule များသည် စက်တွင်းမှ အသစ်ထွက်သည့် ချိတ်ဆက်မှုများကို အမှတ်အသားပြုသောကြောင့် proxy ၏ **ကိုယ်ပိုင်** ပြန်လည်ကုဒ်ဝှက်ထားသော forward သည် ပုံမှန်အားဖြင့် ပြန်လည်ကြားဖြတ်ဖမ်းယူခံရမည်ဖြစ်ပြီး — အဆုံးမရှိ loop ဖြစ်ပေါ်စေမည်။ Forward လမ်းကြောင်းသည် bypass socket mark (**SO_MARK**) ဖြင့် ယင်းကို ကာကွယ်သည်-

- `realForward` သည် ၎င်း၏ upstream socket ကို `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` မှတစ်ဆင့် ဖွင့်သည် — `DEFAULT_BYPASS_MARK = 0x539` — ၎င်းသည် `connect()` မလုပ်မီ **SO_MARK** ကို သတ်မှတ်ပေးသောကြောင့် forward ၏ SYN တွင် bypass mark ပါဝင်လာသည်။
- `mangle OUTPUT` rule သည် bypass mark ရှိပြီးသား ချိတ်ဆက်မှုများကို ဖယ်ထုတ်ထားသည် (`-m mark ! --mark <bypassMark>`)။ ထို့ကြောင့် proxy ၏ forward ကို ပြန်လည်အမှတ်အသားပြုခြင်း **မရှိဘဲ** TPROXY ထဲသို့ ပြန်လည်ဝင်ရောက်မည်မဟုတ်ပါ။

> အကောင်အထည်ဖော်မှု မှတ်ချက်- bypass အမှတ်အသားပြုထားသော socket ကို agent ၏
> `createConnection` တွင် ထည့်သွင်းရမည် (`https.request({ createConnection })` သည် agent
> ရှိနေသောအခါ မည်သည့်အကြောင်းကြားချက်မျှမရှိဘဲ လျစ်လျူရှုခံရသည်)။ သို့မဟုတ်ပါက forward သည်
> အမှတ်အသားမရှိသော socket တစ်ခုကို ဖွင့်ပြီး loop ပြန်လည်ဖြစ်ပေါ်လာမည်။ ဤအရာသည် e2e ဖြင့်
> အတည်ပြုထားသော anti-loop ပြင်ဆင်ချက်ဖြစ်သည်။

## §7 Transactional firewall apply / revert

ပျက်စီးရပ်တန့်မှုတစ်ခုကြောင့် `mangle` rule သို့မဟုတ် မလိုအပ်တော့သည့် route တစ်ခု ကျန်ရှိမနေစေရပါ။ Command builder
(`src/mitm/tproxy/commands.ts`) နှင့် runner (`src/mitm/tproxy/setup.ts`) တို့က
**revert သည် apply ၏ အတိအကျ ပြောင်းပြန်ဖြစ်ပြီး ပြောင်းပြန်အစီအစဉ်ဖြင့် လုပ်ဆောင်ကြောင်း** အာမခံသည်။

`applyTproxy(cfg)` သည် apply command များကို အစီအစဉ်အတိုင်း လုပ်ဆောင်သည်။ **မည်သည့်**
လုပ်ဆောင်မှုမဆို မအောင်မြင်ပါက အပြည့်အစုံဖြစ်သည့် `revertTproxy(cfg)` ကို တတ်နိုင်သမျှ လုပ်ဆောင်ပြီး error ကို ပြန်လည်ထုတ်ပေးသည် — ထို့ကြောင့် firewall ကို
အပြည့်အဝ apply လုပ်ထားခြင်း သို့မဟုတ် အပြည့်အဝ revert လုပ်ထားခြင်းသာ ဖြစ်မည်ဖြစ်ပြီး တစ်စိတ်တစ်ပိုင်း apply လုပ်ထားခြင်း လုံးဝမဖြစ်ပါ။ `revertTproxy(cfg)` သည်
ပြောင်းပြန် command များကို ပြောင်းပြန်အစီအစဉ်ဖြင့် လုပ်ဆောင်ကာ failure များကို လျစ်လျူရှုသည် (idempotent ဖြစ်သဖြင့်
ခြွင်းချက်မရှိ ခေါ်ယူရန် ဘေးကင်းသည်၊ ဥပမာ AgentBridge `repairMitm()` cleanup မှ ခေါ်ယူနိုင်သည်)။

မည်သည့် command ကိုမျှ မလုပ်ဆောင်မီ `validateTproxyConfig(cfg)` ကို လုပ်ဆောင်သည်။ port များသည် `1–65535`
အတွင်း ဖြစ်ရမည်၊ `mark`/`routeTable`/`bypassMark` တို့သည် အပေါင်းကိန်းပြည့်များ ဖြစ်ရမည်၊ ထို့ပြင် `bypassMark` သည်
`mark` နှင့် မတူရပါ (loop တားဆီးရန်)။

### Apply command များ (အစီအစဉ်အတိုင်း)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Revert သည် ၎င်းတို့ကို ပြောင်းပြန်အစီအစဉ်ဖြင့် ဖျက်သည်: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`။

> ဤလုပ်ဆောင်နည်းသည် **OUTPUT-based** ဖြစ်သည်။ အဘယ်ကြောင့်ဆိုသော် MITM အသုံးပြုမှုသည် _local_ outbound
> traffic (တူညီသော host ပေါ်ရှိ app များ) အတွက်ဖြစ်ပြီး `PREROUTING` တစ်ခုတည်းရှိ TPROXY က ထို traffic ကို
> မမြင်နိုင်သောကြောင့်ဖြစ်သည် — `PREROUTING` သည် forwarded traffic ကိုသာ မြင်သည်။ `OUTPUT` chain သည် local
> connection အသစ်များကို mark လုပ်သည်၊ `ip rule` က ၎င်းတို့ကို local delivery (`lo`) သို့ ပြန်လည် route လုပ်ပြီး
> ထို့နောက် `PREROUTING` က ၎င်းတို့ကို transparent listener သို့ သတ်မှတ်ပေးသည်။

## §8 ဖွဲ့စည်းသတ်မှတ်မှု

Start request (`POST /api/tools/agent-bridge/tproxy`) သည် အောက်ပါ
field များကို လက်ခံပြီး `StartTproxyBodySchema` (`tproxy/route.ts`) ဖြင့် validate လုပ်သည်။ အားလုံးသည် optional
ဖြစ်ပြီး မသတ်မှတ်ထားပါက ၎င်းတို့၏ default တန်ဖိုးများကို အသုံးပြုသည်:

| Field            | Type               | Default  | မှတ်ချက်                                                                                                                                        |
| ---------------- | ------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`    | Transparent နည်းဖြင့် ကြားဖြတ်ရယူမည့် destination TCP port                                                                                      |
| **mark**         | int (≥1)           | `0x2333` | `OUTPUT` တွင် သတ်မှတ်ပြီး `ip rule` + `PREROUTING` တို့က ကိုက်ညီစစ်ဆေးသည့် firewall mark                                                        |
| **onPort**       | int (1–65535)      | `8443`   | Transparent (**IP_TRANSPARENT**) listener က bind လုပ်သည့် port                                                                                  |
| **routeTable**   | int (≥1)           | `233`    | `local 0.0.0.0/0` route ကို ထိန်းသိမ်းထားသည့် policy-routing table id                                                                           |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | Proxy က ၎င်း၏ကိုယ်ပိုင် upstream connection များတွင် သတ်မှတ်သည့် bypass socket mark (**SO_MARK**); `OUTPUT` တွင် ဖယ်ထုတ်ထားသည် (loop တားဆီးရန်) |
| **sudoPassword** | string             | —        | Root မဟုတ်သည့် desktop များအတွက်သာ: trust-store install ကို ခွင့်ပြုသည်; root ဖြစ်သည့်အခါ လျစ်လျူရှုသည်                                         |

TPROXY အတွက် **environment variable မရှိပါ** — ဖွဲ့စည်းသတ်မှတ်မှုအားလုံးကို
POST body သို့မဟုတ် အထက်ပါ default တန်ဖိုးများမှတစ်ဆင့် ပြုလုပ်သည်။

## §9 Traffic Inspector မှ ဖွင့်ခြင်း

1. **Traffic Inspector** (`/dashboard/tools/traffic-inspector`) ကို ဖွင့်ပါ။
2. capture-modes toolbar တွင် **"TPROXY Decrypt"** ⚠ ခလုတ်ကို ရှာပါ
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`)။
   - "TPROXY decrypt အတွက် Linux + root + native addon လိုအပ်သည်" ဟူသော tooltip ဖြင့်
     ခလုတ်ကို **ပိတ်ထားပါက** ဤ host တွင် native addon ကို အသုံးမပြုနိုင်ပါ (Linux မဟုတ်ခြင်း၊
     toolchain မရှိခြင်း သို့မဟုတ် addon ကို build မလုပ်ထားခြင်း)။ [§2](#2-requirements) နှင့် [§3](#3-the-native-ip_transparent-addon) ကို ကြည့်ပါ။
3. ခလုတ်ကို နှိပ်ပါ။ ၎င်းသည်
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`) မှတစ်ဆင့်
   `POST /api/tools/agent-bridge/tproxy` ကို ခေါ်ပြီး dynamic CA ကို တည်ဆောက်ခြင်း၊

   OS trust store တွင် CA ကို ထည့်သွင်းခြင်းတို့ကို လုပ်ဆောင်သည်။
4. လည်ပတ်နေချိန်တွင် toggle သည် ပယင်းရောင်သို့ ပြောင်းသွားပြီး လက်ရှိ intercept အရေအတွက်

   `source: "tproxy"` ဖြင့် ပေါ်လာသည်။
5. ရပ်တန့်ရန် ထပ်မံနှိပ်ပါ — `stopTproxyCaptureMode()` မှတစ်ဆင့်
   `DELETE /api/tools/agent-bridge/tproxy` သည် listener ကို ပိတ်ခြင်း၊ CA ကို ဖယ်ရှားခြင်းနှင့်
   firewall စည်းမျဉ်းများကို ပြန်လည်ဖယ်ရှားခြင်းတို့ ပြုလုပ်သည်။

capture-mode အခြေအနေ (လည်ပတ်နေခြင်း / ရရှိနိုင်ခြင်း / intercept အရေအတွက် / listener port) ကို
`src/mitm/tproxy/captureManager.ts` ရှိ `GET /api/tools/agent-bridge/tproxy`
(`getCaptureStatus()`) မှ ရရှိသည်။ တစ်ကြိမ်လျှင် TPROXY session **တစ်ခုသာ** လည်ပတ်နိုင်ပြီး —
ဒုတိယတစ်ခုကို စတင်ပါက "TPROXY capture mode လည်ပတ်နေပြီးဖြစ်သည်" ဟူသော အမှားဖြင့် ငြင်းပယ်မည်။

## §10 ပြဿနာဖြေရှင်းခြင်း

### Toggle ကို ပိတ်ထားသည်

native addon ကို load မလုပ်နိုင်ပါ။ အောက်ပါတို့ကို အတည်ပြုပါ—Linux ပေါ်တွင် ရှိနေခြင်း၊ addon ကို
(`npm run build:native:tproxy`) ဖြင့် build လုပ်ထားခြင်းနှင့် process က `transparent.node` ကို
load လုပ်နိုင်ခြင်း။ `isTransparentSocketAvailable()` က toggle ကို ထိန်းချုပ်ပြီး addon မရှိပါက
`GET /api/tools/agent-bridge/tproxy` သည် `available: false` ကို ပြန်ပေးသည်။

### မည်သည့်အရာမျှ ဖမ်းယူမရပါ

- ကြားဖြတ်ဖမ်းယူမည့် process သည် သတ်မှတ်ထားသော `dport`
  (မူလတန်ဖိုး `443`) သို့ အမှန်တကယ် ချိတ်ဆက်ကြောင်း အတည်ပြုပါ။
- process က dynamic CA ကို ယုံကြည်ကြောင်း အတည်ပြုပါ။ CA ကို
  `omniroute-tproxy-ca.crt` အဖြစ် ထည့်သွင်းထားသည်။ ကိုယ်ပိုင် trust store (Firefox/Chrome NSS)
  ရှိသော app များတွင် cert ကို ထိုနေရာ၌လည်း ထည့်သွင်းရန် လိုအပ်နိုင်သည်။
- cert ယုံကြည်မှု / server ကျန်းမာရေး စစ်ဆေးမှုများအတွက် AgentBridge **Diagnose**
  ကိုယ်တိုင်စမ်းသပ်မှုကို လုပ်ဆောင်ပါ
  ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md) ကို ကြည့်ပါ)။

### Crash ဖြစ်ပြီးနောက် ကျန်ရှိနေသော firewall စည်းမျဉ်းများ

`revertTproxy()` သည် apply လုပ်ဆောင်ချက်၏ အတိအကျ ဆန့်ကျင်ဘက်ဖြစ်ပြီး idempotent ဖြစ်သည်။ mode ကို
ရပ်တန့်ခြင်းဖြင့် စည်းမျဉ်းများကို ပြန်လည်ဖယ်ရှားသည်။ session အလယ်တွင် OmniRoute ကို အဆုံးသတ်ခံခဲ့ရပါက
မိဘမဲ့ system state (DNS spoof၊ root CA၊ system proxy) ကို ပြန်လည်ဖယ်ရှားရန် AgentBridge
**Repair** လုပ်ဆောင်ချက် (`POST /api/tools/agent-bridge/repair`) ကို အသုံးပြုပါ။ TPROXY `mangle`
စည်းမျဉ်းများနှင့် route သည် reboot လုပ်သည့်အခါလည်း အလိုအလျောက် ရှင်းလင်းသွားသည်။

### အဆုံးမဲ့ loop / proxy က ၎င်း၏ကိုယ်ပိုင် forward ကို ကြားဖြတ်ဖမ်းယူသည်

ဤသည်မှာ anti-loop အခြေအနေဖြစ်သည်။ `bypassMark` သည် `mark` နှင့် မတူကြောင်း
အတည်ပြုပါ (validation က ဤအချက်ကို မဖြစ်မနေ စစ်ဆေးသည်)။ ထို့ပြင် forward က
`connectMarked` ကို အသုံးပြုကြောင်း အတည်ပြုပါ (`realForward` တွင် အသုံးပြုထားသည်)။
[§5 Anti-loop](#anti-loop-so_mark) ကို ကြည့်ပါ။
