OmniRoute သည် စီမံခန့်ခွဲရေးဆိုင်ရာ လုပ်ဆောင်ချက်များ၊ စစ်မှန်ကြောင်းအတည်ပြုမှု ဖြစ်ရပ်များ၊ ဝန်ဆောင်မှုပေးသူ၏ အထောက်အထား အချက်အလက် သက်တမ်းစက်ဝန်းဆိုင်ရာ ပြောင်းလဲမှုများနှင့် MCP ကိရိယာ ခေါ်ယူအသုံးပြုမှုများကို SQLite အခြေပြု စာရင်းစစ်ဇယားများတွင် မှတ်တမ်းတင်သည်။ ဤစာမျက်နှာတွင် မည်သည့်အရာများကို မှတ်တမ်းတင်သည်၊ မည်သည့်နေရာတွင် သိမ်းဆည်းထားသည်၊ မည်မျှကြာ ထိန်းသိမ်းထားသည်၊ API key များက မှတ်တမ်းတင်ခြင်းမှ မည်သို့ ငြင်းပယ်ရွေးချယ်နိုင်သည်နှင့် ဒေတာကို မည်သို့ ရှာဖွေစစ်ဆေးရမည်တို့ကို ဖော်ပြထားသည်။

အကောင်အထည်ဖော်မှုသည် `src/lib/compliance/index.ts` (T-43 — "လိုက်နာမှု ထိန်းချုပ်ရေးများ") နှင့် `src/lib/compliance/providerAudit.ts` တွင် ရှိသည်။ စာရင်းစစ် ရေးသားမှုများသည် မည်သည့်အခါမျှ ခြွင်းချက်မပစ်ပါ။ မည်သည့် ချို့ယွင်းမှုဖြစ်စေ ခေါ်ဆိုမှုကို တိတ်တဆိတ် လျစ်လျူရှုသဖြင့် စာရင်းစစ်မှတ်တမ်းတင်ခြင်းက ပင်မတောင်းဆိုမှု စီးဆင်းပုံကို မထိခိုက်စေနိုင်ပါ။

## မှတ်တမ်းတင်သည့်အရာများ

### စီမံခန့်ခွဲရေးဆိုင်ရာ စာရင်းစစ်ဖြစ်ရပ်များ (`audit_log`)

`logAuditEvent({ action, actor, target, details, ... })` ကို ခေါ်ဆိုမှုတိုင်းက အတန်းတစ်တန်း ဖန်တီးသည်။ လုပ်ဆောင်ချက် စာသားများသည် `domain.verb` (သို့မဟုတ် `domain.verb.outcome`) ပုံစံကို လိုက်နာသည်။ လက်ရှိ source tree အတွင်း အတည်ပြုထားသည့် လုပ်ဆောင်ချက် အမျိုးအစားများတွင် အောက်ပါတို့ ပါဝင်သည်-

| လုပ်ဆောင်ချက်                        | ရင်းမြစ်                                |
| ------------------------------------ | --------------------------------------- |
| `auth.login.success`                 | `src/app/api/auth/login/route.ts`       |
| `auth.login.failed`                  | `src/app/api/auth/login/route.ts`       |
| `auth.login.locked`                  | `src/app/api/auth/login/route.ts`       |
| `auth.login.error`                   | `src/app/api/auth/login/route.ts`       |

| `auth.login.setup_required`          | `src/app/api/auth/login/route.ts`       |
| `auth.logout.success`                | `src/app/api/auth/logout/route.ts`      |
| `provider.credentials.created`       | `src/app/api/providers/route.ts`        |
| `provider.credentials.updated`       | `src/app/api/providers/[id]/route.ts`   |
| `provider.credentials.revoked`       | `src/app/api/providers/[id]/route.ts`   |

မှတ်တမ်းတစ်ခုစီတွင် `action`၊ `actor` (မူလတန်ဖိုးမှာ `"system"`)၊ `target`၊ `details`/`metadata` (JSON)၊ `ip_address`၊ `resource_type`၊ `status`၊ `request_id` နှင့် `timestamp` တို့ကို ဖမ်းယူသိမ်းဆည်းသည်။ အရေးကြီးသော key များ (`apiKey`၊ `accessToken`၊ `refreshToken`၊ `password`၊ `*token`/`*secret`/`*apikey` နှင့် ကိုက်ညီသည့် မည်သည့်အရာမဆို စသည်တို့) ကို အတန်းမရေးသားမီ `"[redacted]"` အဖြစ် အဆင့်ဆင့် ပြန်လည်ရှာဖွေ၍ ဖုံးကွယ်ထားသည်။

### MCP ကိရိယာ ခေါ်ဆိုမှုများ (`mcp_tool_audit`)

MCP ကိရိယာ ခေါ်ယူအသုံးပြုမှုတိုင်းသည် `open-sse/mcp-server/audit.ts` မှတစ်ဆင့် အတန်းတစ်တန်း ရေးသားသည်။ Schema (`src/lib/db/migrations/002_mcp_a2a_tables.sql` မှ)-

| ကော်လံ           | မှတ်ချက်များ                                   |
| ---------------- | ---------------------------------------------- |
| `id`             | အလိုအလျောက် တိုးမြှင့်မှု                      |
| `tool_name`      | MCP ကိရိယာ အမှတ်အသား                           |
| `input_hash`     | input ၏ sha256 (payload ကို မသိမ်းဆည်းပါ)      |
| `output_summary` | တိုတောင်း၍ ဖြတ်တောက်ထားသော အကျဉ်းချုပ်         |
| `duration_ms`    | အမှန်တကယ် ကြာချိန်                             |
| `api_key_id`     | ခေါ်ဆိုသူ (null ဖြစ်နိုင်သည်)                  |
| `success`        | `1` / `0`                                      |
| `error_code`     | ချို့ယွင်းမှုဖြစ်ချိန်ရှိ နောက်ဆုံး error code |
| `created_at`     | ISO timestamp                                  |

### တောင်းဆိုမှု / အသုံးပြုမှု မှတ်တမ်းများ

၎င်းတို့သည် လုပ်ငန်းလည်ပတ်မှုဆိုင်ရာ telemetry များဖြစ်ပြီး (တိတိကျကျဆိုရလျှင် စီမံခန့်ခွဲရေး စာရင်းစစ်မဟုတ်ပါ) တူညီသော ထိန်းသိမ်းမှု pipeline ကို အသုံးပြုသည်-

- `usage_history` — တောင်းဆိုမှုတစ်ခုချင်းအလိုက် အသုံးပြုမှု စုစည်းချက်
- `call_logs` — တောင်းဆိုမှုတစ်ခုချင်းအလိုက် မှတ်တမ်းအပြည့်အစုံ (အတန်းအရေအတွက် ကန့်သတ်ချက်ရှိသည်၊ အောက်တွင်ကြည့်ပါ)
- `proxy_logs` — proxy traffic မှတ်တမ်း (အတန်းအရေအတွက် ကန့်သတ်ချက်ရှိသည်)
- `request_detail_logs` — ယခင်စနစ်မှ အသေးစိတ် တောင်းဆိုမှုမှတ်တမ်း (ရှိနေသေးပါက ဆက်လက်ရှင်းလင်းဖယ်ရှားသည်)

## သိမ်းဆည်းမှု Schema

`audit_log` ကို ပထမဆုံးအသုံးပြုချိန်တွင် `ensureAuditLogSchema()` က လိုအပ်မှသာ ဖန်တီးသည်-

```sql
CREATE TABLE IF NOT EXISTS audit_log (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  timestamp     TEXT NOT NULL DEFAULT (datetime('now')),
  action        TEXT NOT NULL,
  actor         TEXT NOT NULL DEFAULT 'system',
  target        TEXT,
  details       TEXT,
  ip_address    TEXT,
  resource_type TEXT,
  status        TEXT,
  request_id    TEXT,
  metadata      TEXT
);
```

Index များကို `timestamp`, `action`, `actor`, `resource_type`, `status` နှင့် `request_id` တို့တွင် ဖန်တီးထားသည်။ ယခင် DB များတွင် မရှိသေးသော column များကို လိုအပ်သည့်အချိန်တွင် `ALTER TABLE` မှတစ်ဆင့် ထည့်သွင်းသည်။

## ထိန်းသိမ်းမှုနှင့် ရှင်းလင်းမှု

သီးခြားထိန်းသိမ်းမှုကာလ နှစ်ခုကို လိုက်နာသည်-

| ပတ်ဝန်းကျင် variable        | မူလတန်ဖိုး | သက်ရောက်သည့်အရာများ                                               |
| --------------------------- | ---------- | ----------------------------------------------------------------- |
| `APP_LOG_RETENTION_DAYS`    | `7`        | `audit_log`, `mcp_tool_audit`                                     |
| `CALL_LOG_RETENTION_DAYS`   | `7`        | `usage_history`, `call_logs`, `proxy_logs`, `request_detail_logs` |
| `CALL_LOGS_TABLE_MAX_ROWS`  | `100000`   | `call_logs` အတွက် အများဆုံး row အရေအတွက်အလိုက် ဖြတ်တောက်မှု       |
| `PROXY_LOGS_TABLE_MAX_ROWS` | `100000`   | `proxy_logs` အတွက် အများဆုံး row အရေအတွက်အလိုက် ဖြတ်တောက်မှု      |

`cleanupExpiredLogs()` သည် ထိန်းသိမ်းမှုလုပ်ငန်းစဉ်ကို လုပ်ဆောင်သည်။ Server စတင်ချိန်တွင် `src/instrumentation-node.ts` မှ ၎င်းကို ခေါ်ယူသည်။ လုပ်ဆောင်မှုတစ်ကြိမ်စီတွင် table တစ်ခုချင်းစီအလိုက် ဖျက်လိုက်သည့်အရေအတွက်များနှင့်အတူ `compliance.cleanup` audit event တစ်ခုကို မှတ်တမ်းတင်သည်။ အချိန်ကြာမြင့်သော write lock များကို ရှောင်ရှားရန် proxy/call log ဖြတ်တောက်မှုကို အစုလိုက် (`BATCH_SIZE = 5000`) လုပ်ဆောင်သည်။

Request history ကို ကိုယ်တိုင်ရှင်းလင်းခြင်းသည် ထိန်းသိမ်းမှုလုပ်ငန်းစဉ်နှင့် သီးခြားဖြစ်သည်။ Request Logs စာမျက်နှာသည် `POST /api/settings/purge-request-history` ကို ခေါ်ယူပြီး `call_logs`, အဟောင်း `request_detail_logs` နှင့် `${DATA_DIR}/call_logs/` အောက်ရှိ local request artifact များကို ဖျက်သည်။

မူလတန်ဖိုးများကို `src/lib/logEnv.ts` တွင် သတ်မှတ်ထားသည် (`DEFAULT_APP_LOG_RETENTION_DAYS = 7`, `DEFAULT_CALL_LOG_RETENTION_DAYS = 7`)။

## `noLog` မှတ်တမ်းတင်မှုမှ ဖယ်ထုတ်ခြင်း (API key တစ်ခုချင်းစီအလိုက်)

API key များကို ၎င်းတို့၏ downstream call traffic အား မှတ်တမ်းမတင်ရန် အမှတ်အသားပြုနိုင်သည်။ အဆိုပါ flag ကို `api_keys` table (`no_log INTEGER DEFAULT 0`) တွင် သိမ်းဆည်းထားပြီး hot-path lookup များအတွက် memory အတွင်းရှိ set တစ်ခုသို့လည်း တစ်ပြိုင်တည်း ထည့်သွင်းထားသည်။

```bash
# မှတ်တမ်းမတင်သည့် key တစ်ခု ဖန်တီးရန် (စီမံခန့်ခွဲရေး authentication လိုအပ်သည်)
curl -X POST http://localhost:20128/api/keys \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"name": "Privacy key", "noLog": true}'
```

အကူ function များ (`src/lib/compliance/index.ts`)-

- `setNoLog(apiKeyId, true|false)` — memory အတွင်းရှိ entry ကို ဖွင့် သို့မဟုတ် ပိတ်ရန်
- `isNoLog(apiKeyId)` — request လမ်းကြောင်းတွင် စစ်ဆေးသည်၊ မရရှိပါက `api_keys.no_log` မှ 30 s ကြာ cache လုပ်ထားသော ဖတ်ရှုမှုကို အသုံးပြုသည်
- `NO_LOG_API_KEY_IDS` (env၊ ကော်မာဖြင့် ပိုင်းခြားထားသည်) — boot လုပ်ချိန်တွင် memory အတွင်းရှိ set သို့ ကြိုတင်ထည့်သွင်းသည်၊ column ကို တိုက်ရိုက်ပြောင်းလဲ၍မရသည့်အခါ အသုံးဝင်သည်

စီမံခန့်ခွဲရေး audit event များ (login၊ provider ပြောင်းလဲမှုများ၊ MCP tool ခေါ်ယူမှုများ စသည်တို့) ကို `noLog` က **မသက်ရောက်ပါ** — request တစ်ခုချင်းစီ၏ traffic မှတ်တမ်းတင်မှုကိုသာ ဖယ်ထုတ်ခြင်းဖြစ်သည်။

### `/api/compliance/audit-log` ကို Query လုပ်ခြင်း

ပံ့ပိုးထားသော query params များ (အားလုံး မဖြစ်မနေ မဟုတ်ပါ၊ စာသားစစ်ထုတ်မှုအားလုံးအတွက်
`LIKE %value%` ကိုက်ညီမှုကို အသုံးပြုသည်):

- `action`, `actor`, `target`, `resourceType` (သို့မဟုတ် `resource_type`),
  `status`, `requestId` (သို့မဟုတ် `request_id`)
- `from` / `since`, `to` / `until` — ISO timestamp များ
- `limit` (ပုံသေ `50`၊ အနည်းဆုံး `1`၊ အများဆုံး `500`)
- `offset` (ပုံသေ `0`၊ အများဆုံး `10_000`)

တုံ့ပြန်ချက်သည် JSON array တစ်ခုဖြစ်သည်။ စာမျက်နှာခွဲခြင်း metadata ကို header များတွင် ပြန်ပေးသည်:
`x-total-count`, `x-page-limit`, `x-page-offset`။

```bash
curl "http://localhost:20128/api/compliance/audit-log?action=provider.credentials&from=2026-05-01" \
  -H "Cookie: auth_token=..."
```

## Dashboard

Dashboard တွင် စာရင်းစစ်ဒေတာကို **`/dashboard/audit`**
(`src/app/(dashboard)/dashboard/audit/page.tsx`) ၌ ရရှိနိုင်သည်။ စာမျက်နှာတွင် tab နှစ်ခုရှိသည်:

- **လိုက်နာမှု** (`ComplianceTab.tsx`) — `/api/compliance/audit-log` မှ
  စီမံခန့်ခွဲသူ စာရင်းစစ်ဖြစ်ရပ်များ။ ဖြစ်ရပ်အမျိုးအစား၊ ပြင်းထန်မှု (info / warning
  / critical၊ action + status မှ ဆင်းသက်တွက်ချက်သည်) နှင့် ရက်စွဲအပိုင်းအခြားအလိုက် စစ်ထုတ်နိုင်သည်။ ပြင်းထန်မှုကို
  action/status string များမှ client ဘက်တွင် တွက်ချက်သည်။
- **MCP** (`McpAuditTab.tsx`) — `/api/mcp/audit` မှ MCP ကိရိယာ စာရင်းစစ်၊
  ကိရိယာအမည်နှင့် အောင်မြင်/မအောင်မြင်မှုအလိုက် စစ်ထုတ်နိုင်သည်။

Tab နှစ်ခုလုံးသည် စာမျက်နှာတစ်မျက်နှာလျှင် `50` (လိုက်နာမှု) နှင့် `25` (MCP) ဖြင့်
စာမျက်နှာခွဲထားသည်။

## Provider Credential Helper များ

`src/lib/compliance/providerAudit.ts` သည် credential ဖြစ်ရပ်များ ထုတ်လွှတ်သည့်အခါ
provider စီမံခန့်ခွဲမှု route များက အသုံးပြုသော ပုံဖော်ပြင်ဆင်မှု helper များကို ပံ့ပိုးသည်:

- `summarizeProviderConnectionForAudit(connection)` — connection snapshot ကို
  `details` သို့ မရေးမီ `apiKey`, `accessToken`, `refreshToken`, `idToken` နှင့်
  `providerSpecificData.consoleApiKey` တို့ကို ဖယ်ရှားသည်။
- `getProviderAuditTarget(connection)` — `target` field အတွက် တည်ငြိမ်သော
  `"<provider>:<name|id>"` string ကို ပေါင်းစပ်ဖန်တီးသည်။
- `extractProviderWarnings(...payloads)` — provider တုံ့ပြန်ချက်များထဲမှ
  မူဝါဒ/ဘေးကင်းရေး သတိပေးချက်များ (`[sanitizer]`, `prompt injection detected`,
  `content has been filtered`, `safety filter`, `policy violation`) ကို ရှာဖွေပြီး
  တွေ့ရှိချက် ၅ ခုအထိ ဖော်ပြပေးသည်၊ တစ်ခုစီကို စာလုံးရေ 400 အထိ ဖြတ်တောက်ထားသည်။

## အကောင်းဆုံး လုပ်ထုံးလုပ်နည်းများ

- PII (ဥပဒေရေးရာ၊ ဆေးဘက်ဆိုင်ရာ စသည်) ကို ကိုင်တွယ်သော API key များကို `noLog: true` ဖြင့် အမှတ်အသားပြုပါ။
- သင်၏ ထိန်းသိမ်းမှုမူဝါဒနှင့် ကိုက်ညီစေရန် `APP_LOG_RETENTION_DAYS` /
  `CALL_LOG_RETENTION_DAYS` ကို ချိန်ညှိပါ။ ပုံသေ ၇ ရက်သည် သတိထားသော သတ်မှတ်ချက်ဖြစ်သည်။
- သင်၏ လိုက်နာမှုအစီအစဉ်က လိုအပ်သည့် အချိန်ဇယားအတိုင်း စာရင်းစစ်ဇယားကို platform ပြင်ပသို့
  (`sqlite3 dump`) ထုတ်ယူပါ — ထည့်သွင်းပေးထားသော မော်ကွန်းသိမ်းဆည်းမှု မရှိပါ။
- brute-force တိုက်ခိုက်မှုကို ရှာဖွေရန် `auth.login.failed` နှင့်
  `auth.login.locked` အရေအတွက်များကို စောင့်ကြည့်ပါ။
- စီမံခန့်ခွဲသူ endpoint အသစ်များ ထည့်သွင်းသည့်အခါ တည်ငြိမ်သော
  `domain.verb.outcome` action string ဖြင့် `logAuditEvent({ ... })` ကို ခေါ်ပြီး IP နှင့် `requestId` ကို
  အလိုအလျောက် ဖမ်းယူနိုင်ရန် request context ကို
  `getAuditRequestContext(request)` မှတစ်ဆင့် ပေးပို့ပါ။
