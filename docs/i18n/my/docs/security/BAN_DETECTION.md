OmniRoute သည် provider **အကောင့် အပြီးအပိုင် အသုံးမပြုနိုင်တော့ကြောင်း** (ဆိုင်းငံ့ခံရခြင်း / ပိတ်သိမ်းခံရခြင်း / ToS ချိုးဖောက်မှုကြောင့် ပိတ်ပင်ခံရခြင်း) ဖော်ပြသည့် အချက်ပြများကို ရှာဖွေရန် upstream error response များကို စစ်ဆေးပြီး၊ ကိုက်ညီမှုရှိသည့်အခါ အဆိုပါ connection ကို **အဆုံးသတ် `banned` အခြေအနေ** သို့ ရွှေ့ပေးသဖြင့် request များအတွက် ထပ်မံရွေးချယ်တော့မည် မဟုတ်ပါ။ ဤအရာကို **Security → Banned Keywords** settings card က စီစဉ်သတ်မှတ်ပေးသည် ("အကောင့်ကို အပြီးအပိုင် ပိတ်ပင်ထားကြောင်း စစ်ဆေးဖော်ထုတ်မှုကို ဖြစ်ပေါ်စေသည့် ထပ်ဆောင်း keyword များ။ Built-in keyword များသည် အမြဲတမ်း သက်ရောက်သည်။")။

ဤစာမျက်နှာတွင် built-in list၊ စစ်ဆေးဖော်ထုတ်မှု လုပ်ငန်းစဉ်၊ ၎င်း၏ သက်ရောက်မှုနယ်ပယ်၊ custom keyword များကို ဘေးကင်းစွာ ထည့်သွင်းနည်းနှင့် အမှတ်အသားပြုခံထားရသော connection ကို ပြန်လည်အသုံးပြုနိုင်အောင် ပြုလုပ်နည်းတို့ကို မှတ်တမ်းတင်ထားသည်။ အဆိုပါ အဆုံးသတ်အခြေအနေသည် resilience model ၏ အစိတ်အပိုင်းတစ်ခုဖြစ်သည် — [RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) ("အဆုံးသတ်အခြေအနေများ") ကို ကြည့်ပါ။

**အမှန်တကယ် ကိုးကားရမည့် source:** `open-sse/services/accountFallback.ts`
(`ACCOUNT_DEACTIVATED_SIGNALS`, `getMergedBannedSignals()`, `isAccountDeactivated()`),
ထို့အပြင် အဆုံးသတ်မဟုတ်သော အတည်ပြုမှု class
(`ACCOUNT_VERIFICATION_REQUIRED_SIGNALS` / `isAccountVerificationRequired()`) နှင့် ၎င်းကို အသုံးပြုသည့် 403 branch အတွက် `open-sse/services/errorClassifier.ts` ကို ကိုးကားပါ။

## ထည့်သွင်းပါရှိပြီးသား သော့ချက်စကားလုံးများ

စိတ်ကြိုက်စာရင်းတစ်ခုခုနှင့် မသက်ဆိုင်ဘဲ အောက်ပါ substring 7 ခုသည် အမြဲတမ်း အကျုံးဝင်သည် (စာလုံးအကြီးအသေး မခွဲခြားပါ) -

```
account_deactivated
account has been deactivated
account has been disabled
your account has been suspended
this account is deactivated
this service has been disabled in this account for violation    (Antigravity)
this service has been disabled in this account                  (Antigravity)
```

> Provider များ၏ ban ဆိုင်ရာ အသုံးအနှုန်းများ ပြောင်းလဲလာသည်နှင့်အမျှ ဤစာရင်းလည်း ပြောင်းလဲတိုးတက်နေသည်။
> အတည်ပြုကိုးကားရမည့် မူရင်းမှာ `open-sse/services/accountFallback.ts` ရှိ
> `ACCOUNT_DEACTIVATED_SIGNALS` ဖြစ်ပြီး၊ အထက်ပါ block ကို လက်ရှိအခြေအနေ၏ snapshot အဖြစ်သာ သတ်မှတ်ပါ။

### Ban မဟုတ်သောအရာ - operator က ဆောင်ရွက်ဖြေရှင်းနိုင်သည့် verification prompt များ

`verify your account to continue` သည် ယခင်က အထက်ပါစာရင်းထဲတွင် **ပါဝင်ခဲ့သည်**။ ၎င်းသည် ban
signal မဟုတ်ဘဲ ယခုအခါ `ACCOUNT_VERIFICATION_REQUIRED_SIGNALS` ထဲတွင် ရှိပြီး၊ connection ကို
terminal အခြေအနေသို့ ပြောင်းလဲစေမည့်အစား ပြန်လည်ရယူနိုင်သော `PROJECT_ROUTE_ERROR` အဖြစ် အမျိုးအစားခွဲသည်။

Google Cloud Code / Antigravity က ၎င်းကို `403 VALIDATION_REQUIRED` အဖြစ် ပြန်ပေးသည်။ ၎င်းသည်
**ယာယီသာဖြစ်ပြီး quota အပြည့်ရှိသည့် ပုံမှန်အလုပ်လုပ်နေသော account များတွင်လည်း ဖြစ်ပေါ်သည်** —
တိုက်ရိုက် deployment တစ်ခုတွင် တိုင်းတာထားချက်အရ (2026-09-25၊ `proxy_logs`) Antigravity
connection တစ်ခုသည် 10 မိနစ်အတွင်း ထို 403 များကို 33 ကြိမ် ပြန်ပေးခဲ့သော်လည်း `active`
အခြေအနေတွင် ဆက်ရှိနေခဲ့သည်။ ထိုအချိန်တွင် window 17 ခုလုံး၌ ၎င်း၏ quota 100 % ရှိနေသော
အခြား sibling connection တစ်ခုမှာမူ ထိုအရာကို **တစ်ကြိမ်တည်း** ရရှိပြီး အပြီးတိုင် ban ခံခဲ့ရသည်။
တစ်ခုတည်းသော ကွာခြားချက်မှာ မည်သည့် attempt ကို တုံ့ပြန်ပေးခဲ့သည်ဆိုသည့်အချက်သာ ဖြစ်သည်။

Terminal match တစ်ခုသည် `permanent: true` ဖြစ်ပြီး (1 နှစ် cooldown၊ အလိုအလျောက် မည်သည့်အခါမျှ
ပြန်မကောင်းလာပါ)၊ verification prompt ကိုမူ operator က browser ထဲတွင် ဖြေရှင်းနိုင်သောကြောင့်
ဤခွဲခြားချက်သည် အရေးကြီးသည်။ ထိုစကားစုကို ban စာရင်းထဲတွင် ဆက်လက်ထားရှိခြင်းက
`classifyProviderError` ရှိ ပြန်လည်ရယူနိုင်သော cloud-code 403 branch ကိုလည်း ဤအသုံးအနှုန်းအတွက်
ရောက်ရှိ၍မရအောင် ဖြစ်စေခဲ့သည်။ အကြောင်းမှာ `accountDeactivated` ကို ဦးစွာ စစ်ဆေးသောကြောင့်ဖြစ်ပြီး —
ထို့ကြောင့် Gemini Code Assist အတွက်
[#868](https://github.com/diegosouzapw/OmniRoute/pull/868) နှင့်
[#6452](https://github.com/diegosouzapw/OmniRoute/pull/6452) တို့တွင် ထည့်သွင်းခဲ့သော project-route
ပြန်လည်ရယူရေး logic သည် မည်သည့်အခါမျှ အလုပ်လုပ်နိုင်မည်မဟုတ်ပါ။

အနီးကပ်တည်ရှိသော်လည်း **သီးခြားစီဖြစ်သော** အောက်ပါ signal table သုံးခုသည် banned-keyword
စစ်ဆေးခြင်း၏ အစိတ်အပိုင်း _မဟုတ်ပါ_ -

- `CREDITS_EXHAUSTED_SIGNALS` — billing/quota ကုန်ဆုံးနေခြင်း (`insufficient_quota`,
  `credit_balance_too_low`, `payment required`, …) → terminal `credits_exhausted`။
- `OAUTH_INVALID_TOKEN_SIGNALS` — **non-terminal** ဖြစ်ပြီး token refresh လုပ်ခြင်းဖြင့် ပြန်လည်ရယူနိုင်သည်။
- `ACCOUNT_VERIFICATION_REQUIRED_SIGNALS` — **non-terminal** ဖြစ်ပြီး operator က upstream တွင်
  account ကို ပြန်လည် verify လုပ်ရမည်။ `open-sse/services/errorClassifier.ts` တွင် ရှိသည်
  (အခြားနှစ်ခုမှာ `accountFallback.ts` တွင် ရှိသည်)။ အထက်ပါအပိုင်းကို ကြည့်ပါ။

မှတ်ချက် - **`rate limit`** / `429` ကဲ့သို့ အဖြစ်များသော ယာယီစကားစုများကို
rate-limit / connection-cooldown လမ်းကြောင်းက ကိုင်တွယ်ပြီး ၎င်းတို့သည် ban signal များ
**မဟုတ်ပါ**။

## ဖော်ထုတ်မှု လုပ်ငန်းစဉ်

```
upstream error response
  → body ကို string အဖြစ်ပြောင်းပြီး စာလုံးအသေးပြောင်းခြင်း
  → isAccountDeactivated(body): getMergedBannedSignals().some(sig => body.includes(sig))   [substring ကိုက်ညီမှု]
  → ကိုက်ညီမှုရှိသလား?
      → connection testStatus = "banned"      (အမြဲတမ်း — 1-year cooldown၊ အလိုအလျောက် ဘယ်တော့မှ ပြန်မကောင်းလာပါ)
      → setting `autoDisableBannedAccounts` ကို ဖွင့်ထားပြီး `autoDisableBannedScope` တွင်
        ဤ connection ပါဝင်ပါက (`all` သို့မဟုတ် OAuth/cookie/session အတွက် `subscription`)
        → isActive = false ဟုလည်း သတ်မှတ်သည်။ Scope သည်
        `subscription` ဖြစ်သည့်အခါ Prepaid API key များကို active အဖြစ် ဆက်လက်ထားရှိသည်။
      → account ရွေးချယ်စဉ် connection ကို ကျော်သွားသည် (ပေါင်းစပ်ထားသော QUOTA_BLOCKING status များ)
```

- ကိုက်ညီမှုရှာဖွေခြင်းသည် response **body** ပေါ်တွင် **စာလုံးအကြီးအသေး မခွဲခြားသော substring** ရှာဖွေမှုဖြစ်သည်
  (`isAccountDeactivated`, `accountFallback.ts`)။
- Banned-signal body တွေ့ရှိပါက **မည်သည့် HTTP status တွင်မဆို** အပြီးတိုင် `banned` အဖြစ် သတ်မှတ်ခြင်းကို လုပ်ဆောင်သည် (`markAccountUnavailable` → `checkFallbackError` မှတစ်ဆင့်)။ ပိုမိုကျဉ်းမြောင်းသော **`deactivated`** label (connection တွင် အပို API key မရှိသည့်အခါ `isActive=false`) ကို inline `chatCore.ts` လမ်းကြောင်းက **HTTP 401 / 403** တွင် ရေးသားသည် (`classifyProviderError` → `ACCOUNT_DEACTIVATED` မှတစ်ဆင့် အမျိုးအစားခွဲခြားသည်)။ `markAccountUnavailable()` လမ်းကြောင်းသည် တူညီသော `ACCOUNT_DEACTIVATED` signal အတွက် (`resolveTerminalConnectionStatus` မှတစ်ဆင့်) _မတူညီသော_ အပြီးသတ် status ဖြစ်သည့် **`expired`** ကို ရေးသားကြောင်း သတိပြုပါ။ ထို့ကြောင့် response ကို ကိုင်တွယ်ခဲ့သည့် လမ်းကြောင်းပေါ် မူတည်၍ တူညီသော ban သည် `deactivated` သို့မဟုတ် `expired` အဖြစ် ပေါ်လာနိုင်သည်။ (Code comment အဟောင်းတွင် "401 body တစ်ခု၌ ဤ string များ ပါဝင်သည့်အခါ" ဟု ဆိုထားသည် — ယင်းသည် လက်ရှိ လုပ်ဆောင်ပုံကို ပြည့်စုံစွာ မဖော်ပြနိုင်ပါ။)
- အပြီးသတ် status များကို စစ်ထုတ်ထားသည့် နေရာတိုင်းတွင် `banned` connection ကို ရွေးချယ်မှုမှ ဖယ်ထုတ်ထားသည် (`isTerminalConnectionStatus`, ပေါင်းစပ်ထားသော `QUOTA_BLOCKING_CONNECTION_STATUSES`)။

## နယ်ပယ် — မည်သည့် provider များကို စစ်ဆေးသနည်း

**Provider အားလုံး။** စစ်ဆေးမှုသည် မအောင်မြင်သော upstream request တိုင်း ဖြတ်သန်းသည့် ယေဘုယျ error-handling pipeline တွင် လုပ်ဆောင်သည် — ၎င်းကို OAuth/subscription scraper များအတွက်သာ **ကန့်သတ်ထားခြင်း မရှိပါ**။ ရလဒ်အဖြစ် သတ်မှတ်သည့် terminal state သည် provider အလိုက် မဟုတ်ဘဲ **connection** အလိုက် ဖြစ်သည်။

သို့သော် ထည့်သွင်းပေးထားသော _string_ များသည် အမှန်တကယ် ban ခံရနိုင်ခြေရှိသည့် subscription/OAuth provider များ (ChatGPT Web Codex, Claude Web, Codex, Muse Spark, Antigravity) အတွက် အဓိက ရည်ရွယ်ထားသည်။ API-key provider တစ်ခု၏ error body တွင် substring များထဲမှ တစ်ခု အတိအကျ ပါဝင်မှသာ detector ကို trigger လုပ်မည်။

`autoDisableBannedScope` (`all` | `subscription`, မူလတန်ဖိုး `all`) သည် match ဖြစ်ပါက `isActive=false` သို့ပါ ပြောင်းမပြောင်းကို ထိန်းချုပ်သည်။ `subscription` ဆိုသည်မှာ login ပုံစံ seat များ (အခပေး subscription များနှင့် အခမဲ့ account များ၊ web-cookie session များအပါအဝင်) ကို ဆိုလိုသည်။ Prepaid API key များအတွက် `testStatus=banned` ကို မှတ်တမ်းတင်ဆဲဖြစ်သော်လည်း routing pool ထဲတွင် ဆက်ထားပေးသည်။ ရေရှည်တည်တံ့သည့် ဒီဇိုင်းမှာ provider အလိုက်နှင့် account အလိုက် override လုပ်နိုင်ခြင်းဖြစ်ပြီး global enum သည် ပထမအဆင့် အကောင်အထည်ဖော်မှုဖြစ်သည်။

## စိတ်ကြိုက် banned keyword များ

**Security → Banned Keywords** တွင် keyword များကို ထည့်ပါ သို့မဟုတ် ဖယ်ရှားပါ (`PATCH /api/settings` မှတစ်ဆင့် global `customBannedSignals` setting အဖြစ် သိမ်းဆည်းထားသည်)။ ၎င်းတို့ကို ထည့်သွင်းပေးထားသော list ထဲသို့ **ထပ်ပေါင်းသည်** — မည်သည့်အခါမျှ အစားမထိုးပါ — ထို့ပြင် သိမ်းဆည်းသည့်အခါ (နှင့် startup အချိန်တွင်) `setCustomBannedSignals()` မှတစ်ဆင့် hot-reload လုပ်သည်။ Keyword တစ်ခုစီကို စာလုံးရေ 200 အထိ ကန့်သတ်ထားပြီး array အရှည်ကို ကန့်သတ်ထားခြင်း မရှိပါ။

**⚠ မှားယွင်းစွာ positive ဖြစ်နိုင်ခြေ — တိကျသော စကားစုများကို ရွေးချယ်ပါ။** Detection သည် response body တစ်ခုလုံးပေါ်တွင် raw substring match လုပ်ခြင်းဖြစ်ပြီး match ဖြစ်သွားပါက **အမြဲတမ်း အကျိုးသက်ရောက်သည်** (1 နှစ် cooldown၊ ကိုယ်တိုင် recovery လုပ်ရမည်)။ ကျယ်ပြန့်လွန်းသော keyword တစ်ခုသည် လုံးဝ ကောင်းမွန်နေသည့် connection ကို ban လုပ်နိုင်သည်-

- **မကောင်းသော ဥပမာ:** `quota`, `limit`, `error`, `denied` — ယာယီ error အများအပြားတွင် ပါဝင်တတ်သည်။
- **ကောင်းသော ဥပမာ:** ban လုပ်ထားကြောင်း အပြည့်အစုံ ဖော်ပြသည့် စာကြောင်းများ၊ ဥပမာ `your account has been suspended for`,
  `account permanently banned`, `violation of our terms`။

Provider က အမှန်တကယ် ban လုပ်သည့်အခါ ပြန်ပေးသော အဓိပ္ပာယ်မရှုပ်ထွေးသည့် အရှည်ဆုံး စကားစုကို ဦးစားပေးပါ။ မသေချာပါက connection ၏ `lastError` ကို ဦးစွာ စောင့်ကြည့်ပြီးနောက် အတိအကျ ဖော်ပြထားသည့် စကားလုံးများကို ထည့်ပါ။

## Flag လုပ်ထားသော connection ကို ပြန်လည်ရယူခြင်း

Terminal `banned` / `deactivated` state များသည် **အလိုအလျောက် ဘယ်တော့မှ recover မဖြစ်ပါ** (၎င်းတို့ကို proactive-recovery tick မှ ဖယ်ထုတ်ထားသည် — `unavailable` cooldown များသာ အလိုအလျောက် recover ဖြစ်သည်)။ Operator တစ်ဦးက ၎င်းတို့ကို အတိအလင်း ရှင်းလင်းရမည်-

1. **Connection ကို ပြန်လည်စမ်းသပ်ပါ** — dashboard ၏ **Test** action
   (`POST /api/providers/{id}/test`)၊ probe အောင်မြင်ပါက `testStatus` ကို
   `active` သို့ ပြန်သတ်မှတ်ပြီး error field များကို ရှင်းလင်းသည်။
2. **ပြန်လည် authenticate လုပ်ပါ / credential များကို ပြင်ဆင်ပါ** — OAuth provider များအတွက် login
   / refresh flow ကို ပြန်လည်လုပ်ဆောင်ပါ၊ provider create/import route များသည် `isActive = true` ဟု သတ်မှတ်သည်။
3. **Connection ကို ပြန်ဖွင့်ပါ** — auto-disable က `isActive = false` ဟု သတ်မှတ်ခဲ့ပါက
   (scope `all`၊ သို့မဟုတ် OAuth/cookie/session connection အတွက် `subscription`)
   account ကို ပြင်ဆင်ပြီးနောက် ပြန်ဖွင့်ပါ။

သီးခြား "clear ban flag" ခလုတ် မရှိပါ — recovery ဆိုသည်မှာ re-test၊ re-auth သို့မဟုတ် re-enable လုပ်ခြင်းဖြစ်ပြီး [RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) ရှိ ယေဘုယျ terminal-state စည်းမျဉ်းနှင့် ကိုက်ညီသည်။

## Probe သီးခြားခွဲထားခြင်း (model test-all)

`runAsProbe` အတွင်း လုပ်ဆောင်သော model test-all / health-check dispatch များမှ ဖြစ်ပေါ်လာသည့် **probe-origin failure** သည် connection တစ်ခုကို pool မှ ဘယ်တော့မှ မဖယ်ရှားပါ (#9817)။ ၎င်းကို **မြင်နိုင်စေရန် မှတ်တမ်းတင်ထားသည်** (`last_error`, `last_error_type`, `error_code`,
`last_error_at`)၊ သို့သော် routing ပြောင်းလဲမှု **အားလုံး** — cooldown များ၊ terminal
status (`banned` / `deactivated` / `credits_exhausted`)၊ model အလိုက် lockout များ၊
provider circuit breaker၊ 5-minute quota cache၊ OAuth token refresh
နှင့် auto-disable — ကို ကျော်သွားသည်။ အမှန်တကယ် request-path failure ဖြစ်မှသာ deactive လုပ်သည်။ မှတ်တမ်းတင်ထားသည့် error ကြောင့် flag လုပ်ထားသော account သည် traffic ကို ဆက်လက်ဆောင်ရွက်ပေးနေစဉ် dashboard တွင် မြင်နိုင်သည်။

ဆုံးဖြတ်ချက်ချသည့် တစ်ခုတည်းသောနေရာမှာ `shouldIsolateProbeFailures()`
(`src/shared/utils/probeOrigin.ts`) ဖြစ်ပြီး probe-origin failure မှ routing state ကို ပြောင်းလဲနိုင်သည့် နေရာ **တိုင်း** က ၎င်းကို စစ်ဆေးအသုံးပြုသည်-

- `markAccountUnavailable` (`auth.ts`) — မှတ်တမ်းတင်ခြင်းသာ လုပ်သည် (`lastError` raw text,
  `lastErrorType`, `errorCode`, `lastErrorAt`၊ selection-time auto-decay ကို trigger လုပ်ပြီး
  မှတ်တမ်းကို ဖျက်သွားစေနိုင်သည့် `backoffLevel` ကို တမင်တကာ **မထည့်ထားပါ**)
- `maybeAutoDisableBannedAccount` — auto-disable မလုပ်ပါ
- `chatCore` — FORBIDDEN, ACCOUNT_DEACTIVATED, QUOTA_EXHAUSTED (မှတ်တမ်းတင်ခြင်းသာ လုပ်ပြီး
  terminal `credits_exhausted` မသတ်မှတ်ပါ)၊ GEO_BLOCKED (24h exclusion မရှိပါ)၊
  MODEL_NOT_FOUND (`lockModel` မလုပ်ပါ)၊ codex 429 account-rotation failover
  (`markCodexScopeRateLimited` မလုပ်ပါ၊ သိမ်းဆည်းထားသော `rate_limited_until` မရှိပါ၊
  session-affinity ကို မရှင်းလင်းပါ)၊ `persistCodexQuotaState` (quota-state ကို မရေးပါ၊
  cache invalidation မလုပ်ပါ)၊ `recordKeyHealthStatus` (key-health rotator ကို
  မထိပါ)
- OAuth refresh — executor base ရှိ proactive refresh
  (`base.ts` `execute()`၊ refresh-token rotation ကို အသုံးမပြုပါ) နှင့်
  `chatCore` ရှိ reactive 401/403 path (`expired` deactivation မလုပ်ပါ) နှစ်ခုစလုံး
- `chat.ts` — provider circuit breaker နှင့် 5-minute quota cache
  (`markAccountExhaustedFrom429`) ကို ဘယ်တော့မှ အားမလျော့စေပါ

မှတ်တမ်းတင်ထားသည့် error ကြောင့် flag လုပ်ထားသော account သည် traffic ကို ဆက်လက်ဆောင်ရွက်ပေးနေစဉ် dashboard တွင် မြင်နိုင်သည်။ မှတ်ချက်- probe record သည် အမှန်တကယ် path ၏ `slice(0,100)` ဖြတ်တောက်မှုနှင့် မတူဘဲ **raw**
(မဖြတ်တောက်ထားသော) error text ကို သိမ်းဆည်းသည်။

Test-all ကို maintenance tool အဖြစ် အသုံးပြုသည့် operator များသည် အောက်ပါနည်းလမ်း တစ်ခုခုဖြင့် ယခင်အပြုအမူ (probe ကို အမှန်တကယ် generation တစ်ခုအဖြစ် ရေတွက်ခြင်း) ကို ပြန်လည်ထားရှိနိုင်သည်-

- `probeCanDisable` setting (`{"probeCanDisable": true}` ဖြင့်
  `POST /api/settings`၊ သို့မဟုတ် `key_value` DB ကို တိုက်ရိုက်ပြင်ဆင်ခြင်း)၊ သို့မဟုတ်
- feature flag **`PROBE_CAN_DISABLE=true`** (env သို့မဟုတ် DB override၊ setting ထက် ဦးစားပေးသည်)။

Fail-safe- flag သို့မဟုတ် settings lookup က exception ဖြစ်ပေါ်စေပါက isolation သည် ON အဖြစ် ဆက်ရှိနေမည်။
