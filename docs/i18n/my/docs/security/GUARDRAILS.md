> **နောက်ဆုံးမွမ်းမံထားသည့်ရက်:** 2026-08-29 — v3.8.51 (Video Bridge transcript ၏ မူလရင်းမြစ်ကို ခေါ်ယူသူက ကြေညာသတ်မှတ်ထားခြင်းဖြစ်ပြီး၊
> server က အတည်ပြုစစ်ဆေးထားခြင်း မရှိသေးပါ — #11661 အရ ရှင်းလင်းထားသည်)

Guardrail များသည် OmniRoute နှင့် upstream provider များကြား နယ်နိမိတ်တွင်
ဘေးကင်းလုံခြုံမှု၊ မူဝါဒနှင့် အကြောင်းအရာပြောင်းလဲမှုများကို အတည်ပြုကျင့်သုံးစေသည်။ Guardrail တစ်ခုစီသည် request payload များကို (`preCall`) နှင့်
upstream response များကို (`postCall`) စစ်ဆေးနိုင်ပြီး (လိုအပ်ပါက
ငြင်းပယ်ခြင်း၊ ပြောင်းလဲခြင်း သို့မဟုတ် မှတ်ချက်ထည့်ခြင်းတို့ကို ပြုလုပ်နိုင်သည်)။

စနစ်သည် **fail-open** ဖြစ်သည်။ Guardrail တစ်ခုကို လုပ်ဆောင်နေစဉ် exception ဖြစ်ပေါ်ပါက registry သည်
error ကို မှတ်တမ်းတင်ပြီး request ကို ပျက်ကွက်စေမည့်အစား နောက် guardrail ဖြင့်
ဆက်လက်လုပ်ဆောင်သည်။ ပိတ်ဆို့ခြင်းသည် မတော်တဆဖြစ်ပေါ်ခြင်း မဟုတ်ဘဲ တိကျရှင်းလင်းသော ဆုံးဖြတ်ချက် (`block: true`) ဖြစ်သည်။

## အသင့်ပါ Guardrail များ

Import ပြုလုပ်သည့်အခါ registry သည် ဦးစားပေးအစီအစဉ်အလိုက် guardrail ခြောက်ခုကို အလိုအလျောက်တင်သွင်းသည်
(`registry.ts` → `registerDefaultGuardrails()` ကို ကြည့်ပါ):

| ဦးစားပေးမှု | အမည်                | အဆင့်(များ)    | ဖိုင်                 |
| ----------- | ------------------- | -------------- | --------------------- |
| `5`         | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`         | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`         | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`        | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`        | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`        | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ဦးစားပေးနံပါတ် နိမ့်သောအရာများကို **ဦးစွာ** လုပ်ဆောင်သည်။

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

**Vision မပံ့ပိုးသော model များ** သို့ ဦးတည်ထားသည့် image ပါဝင်သော request များကို ကြားဖြတ်ပြီး
request တစ်ခုလုံးကို vision အသုံးပြုနိုင်သော model တစ်ခုသို့ လမ်းကြောင်းပြောင်းပေးသည် သို့မဟုတ်
upstream call မပြုလုပ်မီ image အပိုင်းများကို စိတ်ကြိုက်ပြင်ဆင်နိုင်သော vision model တစ်ခုမှ ထုတ်လုပ်ပေးသည့်
စာသားဖော်ပြချက်များဖြင့် အစားထိုးသည်။ ဤနည်းအားဖြင့် text-only provider များသည်
multimodal payload များကို ပွင့်လင်းမြင်သာစွာ ကိုင်တွယ်နိုင်သည်။

လုပ်ငန်းစဉ်:

1. ပစ်မှတ် model သည် vision ကို ပံ့ပိုးပြီးသားဖြစ်ပါက ကျော်သွားသည် (၎င်းသည်
   အတင်းအကျပ် bridge လုပ်ရန် စာရင်း `isVisionBridgeForcedModel` တွင် ပါဝင်နေခြင်းမှလွဲ၍)။
2. `extractImageParts(messages)` မှတစ်ဆင့် image အပိုင်းများကို ထုတ်ယူသည်
   (`visionBridgeHelpers.ts`)။ ၎င်းသည် combo compatibility filter နှင့် မျှဝေအသုံးပြုသော
   တစ်ခုတည်းသော အမှန်တရားရင်းမြစ်ဖြစ်သည့် `open-sse/utils/mediaParts.ts` ထဲရှိ **ပေါင်းစည်းထားသော media
   detector** `detectMediaParts()` သို့ လွှဲအပ်သည်။
   ထုတ်ယူမှုကို `replaceImageParts` က ပြန်လည်ထည့်သွင်းပေါင်းစပ်နိုင်သည့် ပုံစံများ၏
   top-level အပိုင်းများသာ ပါဝင်သော allowlist ဖြင့် ကန့်သတ်ထားသည် (extract↔replace သဘောတူစာချုပ်): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` နှင့် Responses API `input_image`။ အတွင်းပိုင်းတွင် ထပ်ဆင့်ပါဝင်နေသော ကိုက်ညီမှုများနှင့်
   indicator-only ပုံစံများသည် combo-filter အတွက်သာဖြစ်ပြီး မည်သည့်အခါမျှ ထုတ်ယူခြင်းမပြုပါ။
   တစ်ခုမျှမတွေ့ပါက ကျော်သွားသည်။
3. `resolveVisionBridgeRuntimeSettings()` မှတစ်ဆင့် runtime config ကို ဖြေရှင်းသတ်မှတ်သည်
   (`src/shared/constants/modalityBridgeDefaults.ts`): `modalityBridge*`
   settings key အသစ်များကို ဦးစားပေးသည်။ အဟောင်း `visionBridge*` key များသည် **စက်ဝန်းတစ်ခုစာ
   fallback** (rollback window) အဖြစ် ဆက်လက်တည်ရှိသည်။ Bridge ကို ပိတ်ထားပါက
   media traversal တစ်ခုခု မပြုလုပ်မီ ကျော်သွားသည်။
4. Mode selector (`modalityBridgeVisionMode`၊ အောက်ပါဇယားကို ကြည့်ပါ) သည်
   reroute လုပ်မည်လား describe လုပ်မည်လား ဆုံးဖြတ်သည်။ Reroute သည် `model` ကိုသာ
   ပြောင်းထားသော `modifiedPayload` နှင့်အတူ meta `{ rerouted, fromModel, toModel, imagesKept }` ကို ပြန်ပေးသည်။
5. Describe လမ်းကြောင်း: Image များကို `maxImages` အရေအတွက်အထိ ကန့်သတ်ပြီး၊ task-aware prompt ကို ဖွဲ့စည်းကာ၊
   describe cache ကို စစ်ဆေးပြီး vision model ကို **တစ်ပြိုင်နက်တည်း**
   (`Promise.allSettled`) ခေါ်ယူကာ ၎င်းတို့၏နေရာတွင် `[Image N]: <description>` စာသားအပိုင်းများကို
   ထည့်သွင်းသည်။ Describe မအောင်မြင်ပါက `null` ကို ထုတ်ပေးပြီး မူရင်း image အပိုင်းကို
   **ဆက်လက်ထိန်းသိမ်းထားသည်** (#4012) — သို့သော် describe အားလုံး မအောင်မြင်သည့် combo describe လမ်းကြောင်းတွင်မူ
   vision မပံ့ပိုးကြောင်း အတည်ပြုထားသည့် upstream အတွက်
   `(မရရှိနိုင်ပါ — vision အသုံးပြုနိုင်သော provider ချိတ်ဆက်ထားခြင်းမရှိပါ)` stub ကို အစားထိုးအသုံးပြုသည် (#8430)။
6. `modifiedPayload` + meta (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) ကို ပြန်ပေးသည်။

#### Mode selector (`modalityBridgeVisionMode`)

| Mode       | မူလသတ်မှတ်ချက် | အပြုအမူ                                                                                                                                                                                                                                                                                                                                |
| ---------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔              | ပြင်ဆင်မထားသော အဟောင်း heuristic (#6640/#7204): မူရင်း model တွင် အသုံးပြုနိုင်သော credential များရှိပြီးသား မဟုတ်လျှင် non-combo/`auto/` model များကို အကောင်းဆုံး vision model သို့ reroute လုပ်သည် (credential များရှိပြီးသားဆိုလျှင် describe လုပ်သည်)။ Combo ပစ်မှတ်များကို အမြဲ describe လုပ်သည်။                                |
| `describe` |                | အမြဲ describe လုပ်သည် — reroute block တစ်ခုလုံးကို ကျော်သွားသည်။ အသုံးပြုသူရွေးချယ်ထားသော model က အမြဲတမ်း အဖြေပေးသည်။                                                                                                                                                                                                                 |
| `reroute`  |                | Reroute ကို အတင်းသတ်မှတ်သည်။ credential ရှိသော model ကို ထိန်းသိမ်းထားသည့် guard ကို ကျော်လွှားသည်။ Reroute **ပစ်မှတ်** credential guard သည် ဆက်လက်သက်ရောက်သည် — အသုံးပြုနိုင်သော vision ပစ်မှတ်မရှိပါက raw image များသည် text-only backend သို့ မည်သည့်အခါမျှ မရောက်ရှိစေရန် request သည် describe သို့ ဆက်လက်ရောက်ရှိသွားသည် (#8430)။ |

အတင်းသတ်မှတ်ထားသော mode များသည် auto heuristic မလုပ်ဆောင်မီ **short-circuit** လုပ်သည်။
`auto` အပြုအမူသည် PR-1 မတိုင်မီ guardrail နှင့် byte အလိုက် တစ်ထပ်တည်းဖြစ်သည်။

#### Task-aware describe prompt (`modalityBridgeVisionTaskAware`)

မူလသတ်မှတ်ချက်မှာ **true** ဖြစ်သည်။ `composeVisionPrompt()` (`visionBridgeHelpers.ts`) သည်
**နောက်ဆုံး user message** ၏ စာသားကို (စာလုံး 500 အထိ ဖြတ်တောက်ထားပြီး) အခြေခံ
describe prompt တွင် ထပ်ပေါင်းသည်။ ထိုသို့ပြုလုပ်ခြင်းဖြင့် ဖော်ပြချက်ကို အသုံးပြုသူ အမှန်တကယ် မေးမြန်းထားသည့်အရာဆီသို့
ဦးတည်စေပြီး (codex-vision-proxy ပုံစံ) မြင်ရသောစာသားကို ကူးရေးပေးရန် vision model ကို တောင်းဆိုသည်။
Flag ကို ပိတ်ထားပါက — သို့မဟုတ် user စာသားမရှိပါက — အခြေခံ prompt ကို မပြောင်းလဲဘဲ အသုံးပြုသည်။

describe self-loop ၏ ကိုယ်ပိုင် OpenAI-compatible request (`visionBridgeHelpers.ts`
ရှိ `callVisionModelSingle()`) သည် `image_url.detail: "high"` ကို အမြဲတမ်း
တောင်းဆိုသည် — caller/provider တိုင်းအတွက် ခြွင်းချက်မရှိ တောင်းဆိုပြီး မည်သည့်

Low-detail sampling သည် ဤ prompt က တောင်းဆိုထားသည့် စာသားကူးရေးခြင်း
လုပ်ငန်းအတွက် OCR တိကျမှုကို လျော့ကျစေသောကြောင့် မူလ inbound request က
မည်သည့် detail level ကို အသုံးပြုထားသည်ဖြစ်စေ describe call ကိုယ်တိုင်က high
detail ကို အမြဲတမ်း တောင်းဆိုသည်။ ဤအရာသည် internal describe request body ကိုသာ
သက်ရောက်ပြီး primary request တွင် caller ၏ ကိုယ်ပိုင် `image_url.detail` ကို
OmniRoute က forward လုပ်ပုံကို မပြောင်းလဲပါ — ထို default ကို
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) တွင်
သီးခြား အသုံးချပြီး detect လုပ်ထားသော OpenCode clients များအတွက်သာ အသုံးပြုသည်။

မည်သည့် default ကြောင့်မျှ သက်ရောက်မှု မရှိပါ။

ကိုက်ညီသည်)။ ထို့ကြောင့် vision model မြင်ရသည့်အရာကို မပြောင်းလဲဘဲ upload
bytes/latency ကို လျှော့ချပေးသည်။ Resizing သည် dynamic import မှတစ်ဆင့် load
လုပ်ထားသော `sharp` ကို အသုံးပြုသည်။ ၎င်း၏ native binary ကို load လုပ်ရန်

မပစ်လွှတ်ပါ** — မူလ bytes များကို မပြောင်းလဲဘဲ ဆက်လက်ပေးပို့သည့် fallback ကို

fetch) များကိုလည်း မပြောင်းလဲဘဲ ဆက်လက်ပေးပို့သည်။ ဤ normalization သည် bridge

အဆိုပါ credential အတိအကျများအတွက်သာ လက်ခံသဖြင့် ပြင်ပ client များက admission ကို ကျော်ရန်
header ကို အသုံးပြု၍ မရနိုင်ပါ။

Legacy default များကို `src/shared/constants/visionBridgeDefaults.ts` တွင် ထားရှိပြီး၊
mode/task-aware/cache default အသစ်များနှင့် settings resolver ကို
`src/shared/constants/modalityBridgeDefaults.ts` တွင် ထားရှိသည်။ Guardrail တွင်
`deps` constructor option ကို ပံ့ပိုးထားသဖြင့် test များက `getSettings` နှင့်
`callVisionModel` implementation အတုများကို inject လုပ်နိုင်သည်။

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Audio input ကို လက်ခံနိုင်ကြောင်း မသိရှိရသေးသော target တစ်ခုသို့ audio ပါဝင်သည့် chat request များ
မရောက်မီ ကြားဖြတ်သည်။ ၎င်းသည် chat request ကို မည်သည့်အခါမျှ reroute မလုပ်ပါ။ Audio part များကို
ရှိပြီးသား OpenAI-compatible multipart endpoint မှတစ်ဆင့် transcription ပြုလုပ်ပြီး
ရွေးချယ်ထားသော chat model သည် စာသား transcript များဖြင့် ဆက်လက်လုပ်ဆောင်သည်။

လုပ်ငန်းစဉ်:

1. `getResolvedModelCapabilities()` မှတစ်ဆင့် `supportsAudio` ကို ဖြေရှင်းသတ်မှတ်သည်။ အတိအလင်း
   provider-registry metadata ကို ဦးစားပေးပြီး၊ ထို့နောက် static model metadata၊ ထို့နောက် sync လုပ်ထားသော
   `modalities_input` ကို အသုံးပြုသည်။ ကြေညာထားသော input စာရင်းတွင် `audio` မပါလျှင် `false` ဖြစ်ပြီး၊
   capability အထောက်အထား မရှိလျှင် `null` အဖြစ် ကျန်ရှိသည်။ `false` နှင့် `null` နှစ်ခုစလုံးသည်
   အန္တရာယ်ကင်းရေးကို ဦးစားပေးသော bridge ကို အသက်သွင်းပြီး `true` ဖြစ်လျှင် ၎င်းကို ကျော်သွားသည်။
2. `modalityBridgeAudio*` setting များကို ဖြေရှင်းသတ်မှတ်ပြီး မျှဝေထားသော `detectMediaParts()`
   detector မှတစ်ဆင့် message တိုင်းမှ splice လုပ်နိုင်သော top-level
   audio part များကို ထုတ်ယူသည်။ ပံ့ပိုးထားသော wire shape များမှာ OpenAI `input_audio`, `audio_url` နှင့်
   `source.media_type: "audio/*"` တို့ဖြစ်သည်။ အဆင့်ဆင့်ထည့်သွင်းထားသော audio ကို routing အတွက် ရှာဖွေတွေ့ရှိသော်လည်း
   splice path က မဖယ်ရှားပါ။ လုပ်ဆောင်မှုကို `modalityBridgeAudioMaxClips` ဖြင့် ကန့်သတ်ထားပြီး၊
   နောက်ပိုင်း part များကို မပြောင်းလဲဘဲ ထားရှိသည်။
3. သတ်မှတ်ထားသော `provider/model` ကို အသုံးပြုပါ၊ သို့မဟုတ် `selectAudioBridgeModel()` က
   `AUDIO_TRANSCRIPTION_PROVIDERS` ကို တည်ငြိမ်သော catalog အစီအစဉ်အတိုင်း လှည့်လည်ကြည့်ရှုပြီး အသုံးပြုနိုင်သော
   active provider credential ရှိသည့် ပထမဆုံး model ကို ရွေးချယ်စေသည်။
4. `callAudioTranscription()` သည် base64/data-URI audio ကို multipart
   `file` အဖြစ် ပြောင်းလဲခြင်း သို့မဟုတ် DNS pinning နှင့် 25 MB ကန့်သတ်ချက်ပါသော public-only outbound
   guard မှတစ်ဆင့် remote `audio_url` ကို download လုပ်ခြင်း ပြုလုပ်သည်။ ထို့နောက် file နှင့် ရွေးချယ်ထားသော
   model ကို ဒေသတွင်း `/v1/audio/transcriptions` self-loop သို့ POST လုပ်ပြီး
   `resolveSelfLoopBearer()` ဖြင့် authentication ပြုလုပ်သည်။ ရှိပြီးသား transcription route သည် ပုံမှန်
   credential ရှာဖွေမှု၊ cooldown/rate-limit ကိုင်တွယ်မှုနှင့် provider dispatch ကို လုပ်ဆောင်သည်။
5. အောင်မြင်သော call များသည် သက်ဆိုင်ရာ part များကို `[Audio N]: <transcript>` ဖြင့် အစားထိုးသည်။ Call များကို
   `Promise.allSettled` ဖြင့် လုပ်ဆောင်သည်။ တစ်ခုချင်းစီ မအောင်မြင်ပါက မူလ
   audio part ကို ထိန်းသိမ်းထားသည် (#4012 contract)။ Call အားလုံး မအောင်မြင်ဘဲ target သည်
   `supportsAudio === false` ဖြစ်ကြောင်း သက်သေပြထားပါက part များသည်
   `[Audio N]: (မရရှိနိုင်ပါ — ချိတ်ဆက်ထားသော STT provider မရှိပါ)` ဖြစ်လာသည် (#8430 contract)။ အမည်မသိ
   target (`null`) တစ်ခုအတွက် အားလုံးမအောင်မြင်သော ရလဒ်ကို မပြောင်းလဲဘဲ ထားရှိသည်။ အသုံးပြုနိုင်သော
   STT credential မရှိသည့် စာသားသီးသန့် target အဖြစ် သက်သေပြထားပါက network call မပြုလုပ်ဘဲ တူညီသော ရှင်းလင်းသည့်
   stub ကို ရရှိသည်။

အောင်မြင်သော transcript များသည် process တစ်ခုလုံးတွင် မျှဝေသုံးစွဲသော Modality Bridge LRU/TTL cache ကို အသုံးပြုသည်။
Key သည် audio reference၊ တည်ငြိမ်သော `audio-transcription` operation
label နှင့် ရွေးချယ်ထားသော STT model တို့ကို ပေါင်းစပ်ထားသည်။ မအောင်မြင်မှုများကို မည်သည့်အခါမျှ cache မလုပ်ပါ။ Audio attempt များသည်
မျှဝေထားသော `bridged`, `cacheHits`, `failures` နှင့် `lastUsedAt` counter များကို update လုပ်သည်။
ပြောင်းလဲထားသော response များတွင်
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ပါဝင်ပြီး၊ မပြောင်းလဲထားသော
request များတွင် Audio Bridge segment မပါဝင်ပါ။

Runtime setting များကို DB တွင် သိမ်းဆည်းပြီး Zod ဖြင့် စစ်ဆေးအတည်ပြုထားသည်:

| Key                           | မူလတန်ဖိုး | အပိုင်းအခြား          |
| ----------------------------- | ---------- | --------------------- |
| `modalityBridgeAudioEnabled`  | `true`     | —                     |
| `modalityBridgeAudioModel`    | `""`       | Auto သို့မဟုတ် STT ID |
| `modalityBridgeAudioTimeout`  | `60000`    | 1000–300000           |
| `modalityBridgeAudioMaxClips` | `3`        | 1–10                  |

မျှဝေထားသော cache ကို `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` နှင့် `modalityBridgeCacheMaxEntries` တို့ဖြင့် ဆက်လက်ထိန်းချုပ်သည်။

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

မူလ video ပံ့ပိုးမှုရှိကြောင်း မသိရသေးသော ပစ်မှတ်တစ်ခုကို ခေါ်ယူခြင်းမပြုမီ Chat Completions `messages` နှင့် Responses
API `input` တို့အတွင်းရှိ အပေါ်ဆုံးအဆင့် video အစိတ်အပိုင်းများကို ကြားဖြတ်ရယူသည်။
ပံ့ပိုးထားသော ပုံစံများမှာ `input_video`, `video_url`, `video_source`, HTTPS URLs
နှင့် `data:video/*;base64,...` data URIs တို့ဖြစ်သည်။ စာသားအတွင်းရှိ သာမန် filename များကို
video အဖြစ် မသတ်မှတ်ပါ။

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) သည် request traversal၊
capability/policy စစ်ဆေးမှု၊ request တစ်ခုချင်းအလိုက် စုစည်းမှုနှင့် response payload တို့ကို တာဝန်ယူသည်။
Video တစ်ခုချင်းစီအတွက် လုပ်ဆောင်မှုများ — ရယူခြင်း၊ ရလဒ်တစ်ခုလုံးဆိုင်ရာ cache၊
frame sequence ကို ဖော်ပြခြင်း (ခေါ်ယူသူက ကြေညာထားသည့် audio transcript ရှိပါက ၎င်းကို ပေါင်းစပ်သည်)
နှင့် ကြိုးပမ်းမှုတစ်ကြိမ်ချင်းစီဆိုင်ရာ metrics/abort/cleanup — ကို
`videoBridgePipeline.ts` ရှိ `processVideoPart` နောက်ကွယ်တွင် ဝှက်ထားပြီး `preCall` ၏ loop အတွင်း
video အစိတ်အပိုင်းတစ်ခုလျှင် တစ်ကြိမ်ခေါ်သည်။
ထို module သည် ရှင်းလင်းစွာ သတ်မှတ်ထားသော port boundary များဖြစ်သည့် `VideoMediaBrokerPort`
(bytes များရယူခြင်းနှင့် နမူနာယူထားသော frames များ ထုတ်ယူခြင်း)၊ `VideoAudioTranscriptionPort`
(ခေါ်ယူသူက ကြေညာထားသည့် audio transcript ကို နမူနာယူထားသော caption များနှင့် ပေါင်းစပ်ခြင်း) နှင့်
`VideoDrilldownPort` (frame drill-down persistence boundary; `processVideoPart` နှင့် မချိတ်ဆက်ရသေးပါ —
လက်ရှိတွင် သီးခြား `/api/modality-bridge/video/drilldown` route ကသာ drill-down entry များကို ရေးသားသည်)
တို့ကိုလည်း သတ်မှတ်သည်။

အများသုံး `/v1` request path သည် subprocess ကို မည်သည့်အခါမျှ import သို့မဟုတ် invoke မလုပ်ပါ။
Remote video များကို 50 MiB ကန့်သတ်ချက်အောက်တွင် download လုပ်သည်။ Inline base64 video များအတွက်မူ
model/messages/framing envelope သည် အများသုံး JSON request လက်ခံမှုကန့်သတ်ချက် 50 MiB အတွင်း
ဆက်လက်ရှိနေနိုင်စေရန် video တစ်ခုလျှင် decode လုပ်ပြီး အရွယ်အစားကို သတိထားကန့်သတ်ထားသော 36 MiB cap
သတ်မှတ်ထားသည်။ Memory ခွဲဝေမှုမပြုမီ inline အရှည်နှင့် decode လုပ်ပြီး အရွယ်အစား ခန့်မှန်းချက်များကို
စစ်ဆေးသည်။ အစပိုင်း remote URL နှင့် redirect တစ်ခုချင်းစီတွင် HTTPS ကို မဖြစ်မနေ အသုံးပြုရပြီး
DNS pinning ပါရှိသော လက်ရှိ public-only outbound guard ကို အသုံးပြုသည်။ ထို့နောက် bytes များသည် တိကျသော
အတွင်းပိုင်း `POST /api/modality-bridge/video/extract` broker boundary ကို ဖြတ်သန်းသည်။ ထို route သည်
`LOCAL_ONLY` နှင့် `SPAWN_CAPABLE` နှစ်မျိုးစလုံးဖြစ်ပြီး process တစ်ခုချင်းစီအလိုက် အထောက်အထားစစ်ပြီးသား
ယုံကြည်ရသော loopback request ကိုသာ လက်ခံကာ URL၊ filesystem path၊ executable သို့မဟုတ် argument list
တို့ကို မည်သည့်အခါမျှ လက်မခံပါ။ API body-size pipeline နှင့် handler ၏ incremental body reader တို့သည်
50 MiB broker input cap ကို သီးခြားစီ ပြဋ္ဌာန်းသည်။ ၎င်း၏ ကန့်သတ်ထားသော queue သည် extraction တစ်ခုကိုသာ
တစ်ကြိမ်လျှင် လုပ်ဆောင်ပြီး စောင့်ဆိုင်းနေသော job လေးခုအထိ ခွင့်ပြုကာ စောင့်ဆိုင်းနေသော input ကို
100 MiB အထိ ကန့်သတ်ထားသည်။

Broker အတွင်းတွင် `ffprobe` သည် သီးသန့် local file တစ်ခုကို ဖတ်သည်။ သတ်မှတ်ထားသော format allowlist သည်
playlist နှင့် manifest format များကို ဖယ်ထုတ်ထားသည်။ ခွင့်ပြုထားသော MOV-family container များအတွက်
ပြင်ပ MOV data reference များကို မူလအတိုင်း ပိတ်ထားပြီး သတ်မှတ်ထားသော command သည် ၎င်းတို့ကို
ဖွင့်အသုံးပြုရန် ရွေးချယ်ထားခြင်းမရှိပါ။ `ffprobe` နှင့် `ffmpeg` နှစ်ခုစလုံးသည် `file`-only protocol
whitelist၊ thread တစ်ခု၊ သတ်မှတ်ထားသော argument array များ၊ shell မပါဝင်ခြင်းတို့ကို အသုံးပြုပြီး
executable များကို `PATH` မှ ရှာဖွေသတ်မှတ်သည်။ Attached-picture cover stream များသည် ပြန်ဖွင့်နိုင်သော
candidate များ မဟုတ်ပါ။ ပြန်ဖွင့်နိုင်သော stream အားလုံးသည် ကန့်သတ်ချက်များနှင့် ကိုက်ညီရမည်ဖြစ်ပြီး
deterministic အနိမ့်ဆုံး index fallback မတိုင်မီ ရှင်းလင်းစွာ သတ်မှတ်ထားသော default stream ကို ဦးစားပေးသည်။
Video များကို 600 စက္ကန့်၊ dimension တစ်ခုလျှင် 8,192 pixels နှင့် source pixels 33,554,432 အထိ
ကန့်သတ်ထားသည်။ FFmpeg သည် midpoint JPEG frame 1–16 ခုကို နမူနာယူပြီး ပိုသေးသော input များကို
အရွယ်အစားမမြှင့်ဘဲ အရှည်ဆုံး edge ကို အများဆုံး 1,024 pixels အထိ လျှော့ချကာ URL ကို မည်သည့်အခါမျှ
လက်ခံရရှိခြင်းမရှိပါ။ မူလအားဖြင့် နမူနာယူမှုသည် `uniform` ဖြစ်သည်။ ရွေးချယ်နိုင်သော `scene_aware` နှင့်
စမ်းသပ်ဆဲ `segment_aware` policy များသည် စစ်ဆေးအတည်ပြုပြီးသား local stream ပေါ်တွင် သတ်မှတ်ထားသော
FFmpeg pass နောက်ထပ်တစ်ကြိမ်ကို လုပ်ဆောင်ပြီး ကန့်သတ်ထားသော `showinfo` scene timestamp များကို ရွေးချယ်ကာ
detector ပျက်ကွက်ခြင်း၊ timeout ဖြစ်ခြင်း၊ output ပုံစံမှားယွင်းခြင်း သို့မဟုတ် candidate set ဗလာဖြစ်ခြင်းတို့တွင်
တူညီသော uniform midpoint များသို့ deterministic နည်းလမ်းဖြင့် fallback လုပ်သည်။ Segment-aware mode သည်
စစ်ဆေးအတည်ပြုပြီးသော scene interval များ၏ အချိုးအစားအလိုက် midpoint နမူနာများကို ခွဲဝေသည်။
Segment-aware evidence နှင့် fallback အပြုအမူတို့ကို အောက်တွင် အသေးစိတ်ဖော်ပြထားသည်။ Policy တိုင်းတွင်
ရွေးချယ်မှုပြီးနောက် ခိုင်မာသော 16-frame cap ကို အသုံးပြုသည်။ Scene-aware request တစ်ခုတွင် frame တစ်ခုစာ
budget သာရှိပါက လက်ရှိ full-video သို့မဟုတ် focus window ၏ uniform midpoint ကို အသုံးပြုပြီး
`policyEffective: uniform` ဟု အစီရင်ခံသည်။ ရွေးချယ်ထားသော scene frame တစ်ခုတည်းသည် အချိန်ကာလဆိုင်ရာ
အစွန်းနှစ်ဖက်လုံးကို မထိန်းသိမ်းနိုင်ပါ။ ခေါ်ယူသူသည် အဆုံးရှိသော focus window (`start`/`end` စက္ကန့်)
ကို ရွေးချယ်ပေးနိုင်သည်။ Bound များကို media duration အတွင်းသို့ clamp လုပ်ပြီး ပြောင်းပြန်ဖြစ်နေသော
သို့မဟုတ် အဆုံးမရှိသော window များကို ပယ်ချကာ sampling policy အားလုံးကို normalized interval အတွင်း၌သာ
လုပ်ဆောင်သည်။ ရလဒ် window ကို sampling metadata နှင့် မယုံကြည်ရသော description prefix ထဲတွင်
ထည့်သွင်းထားသောကြောင့် downstream model များသည် focus လုပ်ထားသော အပိုင်းကို timeline အပြည့်နှင့်
ခွဲခြားနိုင်သည်။

Semantic caption focus သည် သီးခြားဖြစ်ပြီး ရှင်းလင်းစွာ သတ်မှတ်ရသော setting တစ်ခုဖြစ်သည်။ မူလ `full`
analysis mode သည် လက်ရှိ frame prompt ကို ထိန်းသိမ်းထားပြီး request စာသားကို caption model ထံ
မည်သည့်အခါမျှ မပို့ပါ။ `focused` mode တွင် bridge သည် Chat သို့မဟုတ် Responses container တစ်ခုတည်းအတွင်းမှ
နောက်ဆုံးပေါ်၊ ဗလာမဟုတ်သော၊ user ရေးသားထားသည့် `text`/`input_text` ကိုသာ ဖတ်ပြီး NFC သို့ normalize လုပ်ကာ
control character များနှင့် whitespace များကို ပေါင်းစည်းပြီး Unicode code point 500 အထိ ကန့်သတ်သည်။
ရလဒ်ဗလာဖြစ်ပါက တိကျသော `full` prompt သို့ fallback လုပ်သည်။ အသုံးပြုနိုင်သော hint ကို သီးသန့်
untrusted-user-context block တစ်ခုအတွင်း JSON အဖြစ် serialize လုပ်ပြီး မြင်တွေ့နိုင်သော အသေးစိတ်အချက်များကိုသာ
ဦးစားပေးနိုင်သည်။ Media အတွင်း မြင်ရသော သို့မဟုတ် ကြားရသော ညွှန်ကြားချက်များကို မလိုက်နာရန် သီးခြား
သတိပေးချက်ကို ၎င်းက လွှမ်းမိုးပယ်ဖျက်၍ မရပါ။ Textual focus သည် `start`/`end` ကို မည်သည့်အခါမျှ
ခန့်မှန်းသတ်မှတ်ခြင်းမပြုသကဲ့သို့ temporal sampler ကိုလည်း မပြောင်းလဲပါ။

#### FU-07 ဖွဲ့စည်းပုံဆိုင်ရာ segment evidence

`segment_aware` သည် စစ်ဆေးအတည်ပြုပြီးသား local video stream ပေါ်တွင် ကန့်သတ်ထားသော pre-analysis pass
တစ်ကြိမ်ကို အသုံးပြုသည်။ သတ်မှတ်ထားသော filter chain သည် ဦးစွာ အကျယ်ကို အများဆုံး 320 pixels အထိ
လျှော့ချပြီး scene အပြောင်းအလဲများနှင့် ရပ်တန့်နေသော interval များကို ရှာဖွေကာ ထို့နောက် blur၊ ပျမ်းမျှ luma
နှင့် spatial/temporal information တို့အတွက် တစ်စက္ကန့်လျှင် frame 1 ခုနှုန်းဖြင့် နမူနာယူသည်။ Pass ကို
ဖွဲ့စည်းပုံဆိုင်ရာ နမူနာ 600 ခု၊ FFmpeg/filter thread တစ်ခု၊ တူညီသော `file`-only protocol နှင့် container
allowlist များ၊ process output 1 MiB နှင့် broker ၏ မျှဝေထားသော abort/deadline အတွင်း အများဆုံး 30 စက္ကန့်ဟူ၍
ကန့်သတ်ထားသည်။ ၎င်းသည် request မှ command၊ filter၊ path သို့မဟုတ် URL ကို မည်သည့်အခါမျှ လက်မခံပါ။

ဖွဲ့စည်းပုံဆိုင်ရာ တန်ဖိုးများသည် အဓိပ္ပာယ်အခြေပြု ဗီဒီယိုနားလည်မှု မဟုတ်ဘဲ အတိအကျ ပြန်လည်ရရှိနိုင်သော နမူနာရွေးချယ်မှုဆိုင်ရာ အထောက်အထားများသာ ဖြစ်သည်။ ၎င်းတို့သည် အကြောင်းအရာရှိ ပုဂ္ဂိုလ်/အရာဝတ္ထုများ၊ လုပ်ဆောင်ချက်များ၊ စာတန်းများ၊ စကားပြောဆိုမှု သို့မဟုတ် အသုံးပြုသူ၏ ရည်ရွယ်ချက်ကို ကောက်ချက်မချပါ။ Scene နှင့် freeze boundary များက segment များကို ဖွဲ့စည်းပြီး၊ freeze coverage၊ blur၊ exposure၊ spatial detail နှင့် temporal change တို့သည် ရှိပြီးသား frame 1–16 ခု budget ကို မည်သို့ခွဲဝေမည်ကိုသာ သက်ရောက်စေသည်။ လုံးဝ ရပ်တန့်နေသော segment တစ်ခုကို frame တစ်ခုအထိသာ ကန့်သတ်ပြီး၊ ရပ်တန့်မနေသော segment များသည် ကျန်ရှိသည့် budget ကို ရရှိရန် ယှဉ်ပြိုင်ကြသည်။ Boundary အရေအတွက်က frame အရေအတွက်ထက် များနေသည့်အခါ အစပိုင်းရှိ လျင်မြန်သော cut များကြောင့် နောက်ဆုံးရှိ ရှည်လျားသော segment ကို မဖုံးကွယ်နိုင်စေရန် timeline တစ်လျှောက် တစ်ပြေးညီ coverage ကို ဆက်လက်ထိန်းသိမ်းထားသည်။ Freeze boundary ၏ 1-second analysis resolution အတွင်းရှိ scene boundary များကို ပေါင်းစည်းသည်။

Filter မရှိခြင်း၊ ပုံစံမမှန်သော/ဗလာဖြစ်သော အထောက်အထား၊ detector error သို့မဟုတ် အချိန်ကန့်သတ်ထားသည့် pre-analysis timeout တို့ ဖြစ်ပေါ်ပါက တိကျသည့် uniform midpoint policy သို့ fail open လုပ်သည်။ Caller abort သို့မဟုတ် broker deadline သည် fail open မလုပ်ပါ။ ၎င်းသည် လက်ရှိလုပ်ဆောင်နေသော subprocess ကို ရပ်တန့်စေပြီး၊ နောက်ဆက်တွဲ frame extraction ကို တားဆီးကာ private temporary tree ကို `finally` တွင် ဖယ်ရှားသည်။

`scripts/perf/video-bridge-fu07-eval.ts` သည် deduplication ပြီးနောက် caption call လျှော့ချနိုင်မှု၊ dense-motion budget ခွဲဝေမှု၊ blur/exposure/SI-TI အထောက်အထား၊ ရှည်လျားသော နောက်ဆုံးပိုင်းပါသည့် လျင်မြန်သော cut များနှင့် တဖြည်းဖြည်း fade ဖြစ်မှုကြောင့် ဖြစ်ပေါ်သော false positive များအတွက် အတိအကျ ပြန်လည်ရရှိနိုင်သည့် အမှန်တကယ် FFmpeg fixture များကို ထုတ်လုပ်သည်။ ၎င်းသည် pre-analysis wall time ကို မှတ်တမ်းတင်ပြီး `/usr/bin/time` ရရှိနိုင်သည့်နေရာတွင် child CPU နှင့် peak RSS ကိုလည်း မှတ်တမ်းတင်သည်။ ၎င်း၏ quality check များသည် ဖွဲ့စည်းပုံဆိုင်ရာ oracle များသာ ဖြစ်သည်။ ဤ harness တွင် ခွင့်ပြုထားသော endpoint သို့မဟုတ် freeze လုပ်ထားသည့် judge မရှိသောကြောင့် အမှန်တကယ် caption model အရည်အသွေးသည် `HOLD` အဖြစ် ဆက်လက်ရှိသည်။ `--caption-cost-per-call-usd` ဖြင့် call တစ်ခုလျှင် အပြုသဘောဆောင်သော ခန့်မှန်းကုန်ကျစရိတ်ကို တိတိကျကျ မပေးထားပါက ငွေကြေးဆိုင်ရာ ချွေတာမှုသည်လည်း `HOLD` အဖြစ် ဆက်လက်ရှိသည်။ Script သည် ရလဒ်နှစ်မျိုးစလုံးကို ဘယ်သောအခါမျှ လုပ်ကြံဖန်တီးခြင်း မပြုပါ။

Frame တစ်ခုစီကို 4 MiB အထိ၊ raw frame အားလုံးပေါင်းကို 23 MiB အထိနှင့် serialized broker response ကို 32 MiB အထိ ကန့်သတ်ထားသည်။ Private temporary directory ကို `finally` တွင် ဖယ်ရှားသည်။ OmniRoute တွင် FFmpeg ကို ပူးတွဲထည့်သွင်းထားခြင်း မရှိသလို custom executable path ကိုလည်း လက်မခံပါ။ Caption မပြုလုပ်မီ bridge သည် ရှေးရိုးဆန်သော visual deduplication pass တစ်ခုကို အသုံးပြုသည်။ JPEG တစ်ခုစီကို 16×16 grayscale buffer အဖြစ် လျှော့ချပြီး နောက်ဆုံး ထိန်းသိမ်းထားသော frame နှင့်သာ နှိုင်းယှဉ်သည်။ တောင်းဆိုထားသော caption budget သည် frame တစ်ခုထက်များပါက extraction သည် ထို budget ၏ နှစ်ဆအထိဖြစ်ပြီး frame 16 ခုထက် ဘယ်သောအခါမျှ မပိုသော ကန့်သတ်ထားသည့် candidate pool ကို ပေးသည်။ တောင်းဆိုထားသော cap ကို deduplication ပြီးနောက်မှသာ အသုံးချပြီး၊ budget သည် အနည်းဆုံး နှစ်ခုရှိပါက နောက်ဆုံး thinning လုပ်စဉ် ပထမဆုံးနှင့် နောက်ဆုံး ရွေးချယ်ထားသော candidate များကို ထိန်းသိမ်းထားသည်။ Version သတ်မှတ်ထားသော `grayscale-16x16-mean-cells-v2` policy သည် mean luma delta နှင့် normalized delta အနည်းဆုံး 0.05 ရှိသော thumbnail cell များ၏ အချိုးတို့အနက် ပိုကြီးသည့်တန်ဖိုးကို အသုံးပြုသည်။ Duplicate threshold သည် constant 0.04 ဖြစ်ပြီး runtime setting အဖြစ် ဖော်ထုတ်ပေးရန်ထက် ကြိုတင်ခန့်မှန်းနိုင်မှုအတွက် ရွေးချယ်ထားခြင်း ဖြစ်သည်။ ဤ ဒုတိယ high-contrast signal သည် mean-only comparison ကြောင့် ဖုံးကွယ်သွားနိုင်သည့် သေးငယ်သော လှုပ်ရှားမှုနှင့် မြင်နိုင်သောစာသား ပြောင်းလဲမှုများကို ထိန်းသိမ်းပေးသည်။ Comparator သို့မဟုတ် decoder error များ ဖြစ်ပေါ်ပါက fail open လုပ်ပြီး coverage ကို ထိန်းသိမ်းထားသည်။ Output metadata တွင် extracted candidate များ၊ အောင်မြင်စွာ အသုံးပြုခဲ့သော frame များနှင့် ဖယ်ရှားခဲ့သော visual duplicate များကို သီးခြားခွဲပြထားသည်။

အတိအလင်း အမှတ်အသားပြုထားသော video part တစ်ခုသည် timestamp ပါသည့် contact sheet ကို တောင်းဆိုနိုင်သည်။ Bridge သည် column 4 ခုနှင့် frame 16 ခုအထိပါဝင်သော JPEG grid ကို တည်ဆောက်သည်။ 512-pixel cell တစ်ခုစီသည် ၎င်း၏ source timestamp ကို high-contrast အောက်ခြေ band ထဲတွင် ပုံပေါ်သို့ အမြဲတမ်းထည့်သွင်းပြီး၊ downstream association နှင့် audit အတွက် ထို timestamp များကို textual metadata ထဲတွင်လည်း ဆက်လက်ထားရှိသည်။ JPEG အပြည့်အစုံကို 32 MiB အထိသာ ကန့်သတ်ထားသည်။ `sharp` သည် grid ကို decode သို့မဟုတ် compose မလုပ်နိုင်ပါက bridge သည် JPEG frame တစ်ခုချင်းစီသို့ fallback လုပ်သည်။ Client abort ဖြစ်ပါက sheet operation တစ်လျှောက် ဆက်လက် propagate ဖြစ်သည်။

Promotion အထောက်အထားကို synthetic composition microbenchmark နှင့် ရည်ရွယ်ချက်ရှိရှိ သီးခြားခွဲထားသည်။ `scripts/perf/video-bridge-contact-sheet-eval.ts` သည် အမှန်တကယ် OpenAI-compatible vision model များအတွက် schema version သတ်မှတ်ထားသော A/B harness တစ်ခုကို သတ်မှတ်သည်။ ၎င်းသည် provider က အစီရင်ခံသော token များ၊ end-to-end wall latency (sheet composition အပါအဝင်)၊ model call အရေအတွက်နှင့် manifest က သတ်မှတ်ထားသော fact retention တို့ကို တိုင်းတာသည်။ Raw model response များကို report ထဲသို့ မရေးဘဲ SHA-256 digest များနှင့် ကိုက်ညီသော fact ID များကိုသာ ထိန်းသိမ်းထားသည်။ `--execute-real` ကို ပေးထားပြီး `--model`၊ `OMNIROUTE_BASE_URL` နှင့် `OMNIROUTE_API_KEY` တို့ကို configure လုပ်ထားမှသာ harness သည် network call သို့မဟုတ် အခကြေးငွေပေးရသော model call ကို ပြုလုပ်သည်။ ထိုကဲ့သို့ အတိအလင်း သတ်မှတ်ထားသော အမှန်တကယ် run မရှိပါက ၎င်း၏ machine-readable verdict သည် `HOLD` အဖြစ် ဆက်လက်ရှိသည်။ Synthetic payload/call-count တိုင်းတာမှုများသာရှိခြင်းသည် promotion အထောက်အထား မဟုတ်ပါ။

Caller များတွင် ချိန်ညှိပြီးသား စာသားရှိပါက ပံ့ပိုးထားသော video part တစ်ခုသို့ optional `transcript.cues` array ကို ထည့်သွင်းနိုင်သည်။ Cue တစ်ခုစီတွင် `text`၊ probe လုပ်ထားသော duration အတွင်းရှိ အကန့်အသတ်ရှိသည့် `start`/`end` interval နှင့် whitelist လုပ်ထားသော `source` (`client`၊ `embedded` သို့မဟုတ် `audio-bridge`) တို့ ပါရှိရမည်။ `confidence` ၏ default တန်ဖိုးမှာ `1` ဖြစ်ပြီး `0` နှင့် `1` ကြားတွင်သာ ရှိရမည်။ လုံးဝတူညီသော cue များကို ပေါင်းစည်းသည်။ OmniRoute သည် ဤ metadata မှ transcription ကို ဘယ်သောအခါမျှ စတင်ခြင်းမပြုပါ။ Validate လုပ်ပြီးသော cue များကို source၊ confidence နှင့် interval တို့နှင့်အတူ ဖော်ပြထားသော result ထဲသို့ ကူးယူပြီး frame caption များနှင့်အတူ မယုံကြည်ရသေးသော observation များအဖြစ် render လုပ်သည်။ မမှန်ကန်သော၊ range ပြင်ပရောက်နေသော သို့မဟုတ် provenance မရှိသော စာသားကို caption stream ထဲသို့ ရောနှောမည့်အစား ငြင်းပယ်သည်။ လက်ရှိတွင် `source` field ကို server က အတည်ပြုထားခြင်း မဟုတ်ဘဲ caller က ကြေညာထားခြင်းသာ ဖြစ်သည်။ OmniRoute သည် တန်ဖိုးက ခွင့်ပြုထားသော string သုံးခုအနက် တစ်ခုဖြစ်ကြောင်း အတည်ပြုသော်လည်း `embedded` သို့မဟုတ် `audio-bridge` label သည် server ပိုင် extraction တစ်ခုမှ အမှန်တကယ် ရရှိလာကြောင်း cryptographic နည်းဖြင့် အတည်မပြုရသေးပါ။ ထိုအတည်ပြုမှု မရရှိမချင်း `source` ကို မယုံကြည်ရသေးသော hint တစ်ခုအဖြစ် သဘောထားပါ။ ၎င်းကို အခြေခံ၍ authorization ဆုံးဖြတ်ချက်များ မတည်ဆောက်ပါနှင့်။

`start`/`end` read များ သို့မဟုတ် အတိအလင်း session deletion ကို ပံ့ပိုးသည်။

principal တစ်ခုချင်းစီကို entry 16 ခုနှင့် canonical JPEG data 64 MiB အထိ ကန့်သတ်ထားသည်။ ထို

global accounting နှစ်ခုလုံးမှ ရှင်းလင်းပစ်ပြီး cancellation နှင့် validation failure တို့သည်

Cache သည် canonical မဟုတ်သော Base64၊ အလွန်အကျွံ padding၊ JPEG မဟုတ်သော media၊ ပုံစံမှားယွင်းသော သို့မဟုတ်

decode ပြုလုပ်စဉ် warning တစ်ခု ဖြစ်ပေါ်စေသော JPEG များကို ငြင်းပယ်သည်။ လက်ခံထားသော image တစ်ခုချင်းစီကို canonical JPEG အဖြစ် ပြန်လည် encode လုပ်ပြီး caller field များကို မယုံကြည်ဘဲ decoded byte များမှ width နှင့် height ကို
derive လုပ်ကာ နောက်တွဲ polyglot byte များကို ထိန်းသိမ်းမထားဘဲ

အမှန်တကယ်အသုံးပြုမည့် vision-capable မော်ဒယ်ကို ရွေးချယ်သည်။ အောင်မြင်စွာ ဖန်တီးထားသော စာတန်းများသည် မူလ part ကို တည်ငြိမ်သော `[Video description:` prefix ဖြင့် အစားထိုးသည်။ ထို prefix သည် စာသားကို ယုံကြည်စိတ်ချ၍မရသော မီဒီယာမှ ရရှိသည့် လေ့လာချက်တစ်ခုအဖြစ်လည်း မှတ်သားပြီး မီဒီယာအတွင်း တွေ့ရှိသော ညွှန်ကြားချက်များကို မလိုက်နာရန် downstream မော်ဒယ်များအား အသိပေးသည်။ Frame-caption cache key များတွင် JPEG bytes၊ prompt၊ timestamp နှင့် အမှန်တကယ်အသုံးပြုသည့် မော်ဒယ်တို့ ပါဝင်ပြီး အောင်မြင်သော caption များကိုသာ cache လုပ်သည်။ Cache entry များတွင် fallback မော်ဒယ်အပါအဝင် အမှန်တကယ်အောင်မြင်စွာ ထုတ်လုပ်ပေးခဲ့သည့် မော်ဒယ်ကို ထိန်းသိမ်းထားသည်။ မတူညီသော frame များကို မတူညီသော မော်ဒယ်များက ထုတ်လုပ်ထားသည့်အခါ bridge သည် `mixed` ဟု အစီရင်ခံသည်။ Cache hit ဖြစ်ပါက တောင်းဆိုထားသော routing plan အဖြစ် label ပြန်တပ်ခြင်းမပြုဘဲ ထို producer identity ကို ပြန်လည်အသုံးပြုသည်။ ဗီဒီယိုတစ်ခုလုံး၏ result cache ကို output ပြောင်းလဲစေနိုင်သည့် input အားလုံး — prompt၊ အမှန်တကယ်အသုံးပြုသည့် မော်ဒယ်၊ sampling policy၊ frame အရေအတွက်၊ semantic analysis mode၊ normalized focus hint ၏ SHA-256 fingerprint၊ focus window၊ `transcript`၊ `audioTranscript` နှင့် contact-sheet flag — ဖြင့် key သတ်မှတ်ထားသည်။ ထို့ကြောင့် ထို dimension များအနက် တစ်ခုခု ပြောင်းလဲပါက cache miss ဖြစ်ပြီး ဟောင်းနေသောရလဒ်ကို မည်သည့်အခါမျှ ပြန်လည်အသုံးမပြုပါ။ Visual dedup policy version၊ threshold နှင့် ကန့်သတ်ထားသော candidate-frame အရေအတွက်တို့ကိုလည်း result-cache key နှင့် metadata တွင် အတိအလင်း ထည့်သွင်းထားသည်။ ထို့ကြောင့် policy ပြောင်းလဲမှုတစ်ခုသည် ဟောင်းနေသော ဗီဒီယိုတစ်ခုလုံး၏ ဖော်ပြချက်ကို ပြန်လည်အသုံးမပြုနိုင်ပါ။ Result-cache v4 metadata သည် mode နှင့် fingerprint ကို ထိန်းသိမ်းထားသော်လည်း အသုံးပြုသူ၏ task အကြမ်းကို မည်သည့်အခါမျှ မသိမ်းဆည်းပါ။ Guardrail metadata သည် တောင်းဆိုထားသော analysis mode နှင့် အမှန်တကယ်အသုံးပြုသော analysis mode နှစ်ခုစလုံးကို အစီရင်ခံသည်။ အသုံးပြုနိုင်သော user text မရှိဘဲ `focused` mode ကို တောင်းဆိုထားပါက အမှန်တကယ် `full` အဖြစ် အသုံးပြုကြောင်း Guardrail သည် ပံ့ပိုးထားသော video part အားလုံးကို ထုတ်ယူသော်လည်း `modalityBridgeVideoMaxVideos` ထက်ပို၍ မဖော်ပြပါ။ `supportsVideo === false` ဖြစ်ကြောင်း အတည်ပြုထားသော target အတွက် မအောင်မြင်သော ဗီဒီယိုများနှင့် သတ်မှတ်အရေအတွက်ကျော်လွန်သော ဗီဒီယိုများကို ရှင်းလင်းသော ဘေးကင်းသည့် စာသား marker များအဖြစ် ပြောင်းလဲပေးသဖြင့် raw video မကျန်ရှိပါ။ Capability ကို မသိရသည့်အခါ ထို part များကို မပြောင်းလဲဘဲ ထားရှိသည်။ `supportsVideo === true` ဖြစ်သော target များသည် bridge ကို ကျော်သွားသည်။ Client request abort signal သည် download၊ broker queue၊ subprocess များနှင့် caption call များတစ်လျှောက် ဆက်လက်သက်ရောက်သည်။ Abort များသည် ဗီဒီယိုတစ်ခုနှင့်တစ်ခုကြားတွင် လုပ်ဆောင်မှုကို ရပ်တန့်စေပြီး raw media ကို ခွင့်ပြု၍ ဆက်လက်လုပ်ဆောင်ခြင်း မရှိပါ။

| Key                                 | ပုံသေတန်ဖိုး | အပိုင်းအခြား / လုပ်ဆောင်ပုံ                                                                                                              |
| ----------------------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`      | ရွေးချယ်နိုင်သော runtime၊ opt-in လုပ်မှသာ အသုံးပြုသည်                                                                                    |
| `modalityBridgeVideoAnalysisMode`   | `"full"`     | `full` သည် ယေဘုယျ caption များကို ထိန်းသိမ်းသည်။ `focused` သည် ကန့်သတ်ထားပြီး ယုံကြည်စိတ်ချ၍မရသော နောက်ဆုံး user context ကို အသုံးပြုသည် |
| `modalityBridgeVideoModel`          | `""`         | Vision Bridge မော်ဒယ်ကို ဆက်ခံအသုံးပြုသည်                                                                                                |
| `modalityBridgeVideoFrameCount`     | `8`          | 1–16                                                                                                                                     |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`  | `uniform`၊ `scene_aware` သို့မဟုတ် အချိုးကျ `segment_aware`။ detector မအောင်မြင်ပါက `uniform` သို့ ပြန်ပြောင်းသည်                        |
| `modalityBridgeVideoMaxVideos`      | `1`          | 1–4                                                                                                                                      |
| `modalityBridgeVideoTimeout`        | `120000`     | 1000–120000 ms                                                                                                                           |

ယခင်က သိမ်းဆည်းထားသော စက္ကန့် 120 အထက် Video timeout တန်ဖိုးများကို broker deadline အထိ ကန့်သတ်လျှော့ချသည်။ ထိုကန့်သတ်ချက်ထက်ကျော်သော ဆက်တင်အသစ်များကို သိမ်းဆည်းရန် ကြိုးပမ်းပါက ပယ်ချသည်။ `GET /api/modality-bridge/video/runtime` သည် authentication သို့မဟုတ် runtime probing မပြုလုပ်မီ ယုံကြည်စိတ်ချရသော stamped loopback locality ကို လိုအပ်ပြီး ထို့နောက် management auth ကို လိုအပ်သည်။ ၎င်းသည် `available`၊ သန့်စင်ထားသော FFmpeg/ffprobe version များနှင့် runtime မရနိုင်သည့်အခါ သတ်မှတ်ထားသော reason တစ်ခုကိုသာ ပြန်ပေးသည်။ Internal extraction endpoint သည် အများသုံး upload API မဟုတ်ပါ။ Queue ပြည့်ကျပ်နေပါက `503` နှင့် `Retry-After` ကို ပြန်ပေးသည်၊ caller disconnect ဖြစ်ပါက `499` ကို ပြန်ပေးပြီး သတ်မှတ်ထားသော broker deadline ပြည့်ပါက `504` ကို ပြန်ပေးသည်။ ပြောင်းလဲပြီးသော response များသည် Vision သို့မဟုတ် Audio segment များကို မဖယ်ရှားဘဲ ဗဟို `x-omniroute-modality-bridge` header ထဲသို့ `video->text;model=<visionModel>;parts=<videos>` ကို ထည့်သွင်းသည်။

### PII ဖုံးကွယ်ကိရိယာ (`piiMasker.ts`)

Stage **နှစ်ခုစလုံး** တွင် လုပ်ဆောင်သည်။

- **`preCall`** သည် payload ကို clone လုပ်ပြီး `system`၊ `messages`၊ `input` နှင့် `prompt` တို့ကို (သာမန် string item များအပါအဝင်) လှည့်လည်စစ်ဆေးကာ string `content`/`text` field များတွင် (`@/shared/utils/inputSanitizer` မှ) `processPII()` ကို အသုံးပြုသည်။ `PII_REDACTION_ENABLED=true` ဖြစ်ပါက တွေ့ရှိထားသော PII ကို outbound payload တွင် ဖျက်ကွယ်သည်။ ၎င်းသည် prompt-injection policy ကိုသာ ထိန်းချုပ်သည့် `INPUT_SANITIZER_MODE` နှင့် သီးခြားဖြစ်သည်။ ဖျက်ကွယ်မှုကို ပိတ်ထားပါက content ကို ပြန်မရေးဘဲ တွေ့ရှိမှုအရေအတွက်များကို call က မှတ်တမ်းတင်သည်။
- **`postCall`** သည် response ကို deep-clone လုပ်ပြီး `sanitizePIIResponse()` နှင့် Responses-API-shape masker (`maskResponsesOutput` — `output_text` နှင့် `output[].content[].text` တို့ကို အကျုံးဝင်သည်) ကို လုပ်ဆောင်သည်။ ဖျက်ကွယ်မှုတစ်ခုခု ဖြစ်ပေါ်ပါက ပြုပြင်ထားသော response ဖြင့် မူလ response ကို အစားထိုးသည်။

Guardrail သည် မည်သည့်အခါမျှ ပိတ်ဆို့ခြင်းမပြုပါ။ ၎င်းသည် annotation (`meta.detections`၊ `meta.redacted`) ထည့်ခြင်း သို့မဟုတ် ပြန်လည်ရေးသားခြင်းသာ ပြုလုပ်သည်။

### Prompt Injection (`promptInjection.ts`)

အသုံးပြုသူပေးပို့သော content အတွင်းရှိ တိုက်ခိုက်ရန်ရည်ရွယ်သည့် structure များကို ရှာဖွေပြီး သတ်မှတ်ပြင်ဆင်ထားသော policy ကို မဖြစ်မနေ လိုက်နာစေသည်။ လုပ်ဆောင်ပုံကို environment variable များနှင့် constructor option များက ထိန်းချုပ်သည်-

| ဆက်တင်                      | Env var                                                                                               | ပုံသေ  | သက်ရောက်မှု                                                                                                                                                                                                                       |
| --------------------------- | ----------------------------------------------------------------------------------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ဖွင့်ထားခြင်း               | `INPUT_SANITIZER_ENABLED`                                                                             | `true` | `false` ဖြစ်သည့်အခါ guardrail သည် ချက်ချင်းကျော်သွားသည်။                                                                                                                                                                          |
| မုဒ်                        | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn` | Injection မူဝါဒ- `block`, `warn` သို့မဟုတ် `log`။ (`redact` ကို နောက်ကြောင်းပြန်လိုက်ဖက်မှုအတွက် လက်ခံသော်လည်း injection စာသားကို **မ**ဖယ်ရှားပါ။ request PII ပြန်လည်ရေးသားခြင်းကို `PII_REDACTION_ENABLED` ဖြင့် ထိန်းချုပ်သည်။) |
| ပိတ်ဆို့မှု အနိမ့်ဆုံးအဆင့် | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high` | ပိတ်ဆို့ရန် လိုအပ်သည့် အနိမ့်ဆုံး ပြင်းထန်မှုအဆင့်။ ပုံသေဆက်တင်တွင် Medium သည် စောင့်ကြည့်ရုံသာ ဖြစ်သည်။                                                                                                                          |

**မုဒ် ဦးစားပေးအစီအစဉ်** (`getMode`)- ခေါ်ယူသူ၏ `options.mode` →
`INJECTION_GUARD_MODE` **DB feature-flag override** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`။ ထို့ကြောင့် dashboard override သည် env vars များထက် ဦးစားပေးသဖြင့် Feature
Flags UI မှ လက်ရှိလည်ပတ်နေသော guard ကို တိုက်ရိုက်ထိန်းချုပ်နိုင်သည် (ပြန်လည်စတင်ရန် မလိုပါ)။ DB ဖတ်ရှုမှုသည် fail-safe
ဖြစ်သည်- error ဖြစ်ပါက guard သည် env အခြေခံ အပြုအမူသို့ ပြန်လည်အသုံးပြုပြီး
override သတ်မှတ်ထားခြင်းမရှိပါက အပြုအမူသည် env-only ဖြေရှင်းမှုနှင့် အတူတူပင်
ဖြစ်သည်။

ရှာဖွေသတ်မှတ်မှု ရင်းမြစ်များ-

1. `@/shared/utils/inputSanitizer` မှ `sanitizeRequest()` (pipeline ၏ အခြားနေရာများတွင်
   အသုံးပြုသည့် မျှဝေ detector အစု)။
2. Built-in `DEFAULT_GUARD_PATTERNS` (လက်ရှိတွင် `system_override_inline` နှင့်
   `markdown_system_block` ဖြစ်ပြီး နှစ်ခုစလုံး၏ ပြင်းထန်မှုမှာ `high` ဖြစ်သည်)။
3. Constructor options မှတစ်ဆင့် ပေးပို့သော ရွေးချယ်နိုင်သည့် `customPatterns` (strings, regex
   သို့မဟုတ် `{ name, pattern, severity }` records)။

`mode === "block"` ဖြစ်ပြီး **ထို့အပြင်** အနည်းဆုံး ရှာဖွေတွေ့ရှိမှုတစ်ခုသည် ပြင်းထန်မှု
အနိမ့်ဆုံးအဆင့်နှင့် ကိုက်ညီပါက `preCall` က `{ block: true, message: "Request rejected:
suspicious content detected" }` ကို ပြန်ပေးသည်။ `warn`/`log` မုဒ်များတွင် guardrail သည် log
မှတ်တမ်းတင်သော်လည်း ခေါ်ယူမှုကို ခွင့်ပြုသည်။ Registry မှတစ်ဆင့် မလုပ်ဆောင်ဘဲ prompt များကို
အကဲဖြတ်ရန် လိုအပ်သော ခေါ်ယူသူများအတွက် မျှဝေ helper `evaluatePromptInjection()` ကိုလည်း export
လုပ်ထားသည်။

**စစ်ဆေးမှု အကန့်အသတ် (v3.8.20)-** detector သည် ပေါင်းစပ်ထားသော prompt စာသား၏ **ပထမ 16 KB** ကိုသာ
စစ်ဆေးသည် — `src/shared/utils/inputSanitizer.ts` ရှိ
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes)။ `detectInjection()` နှင့်
`evaluatePromptInjection()` နှစ်ခုစလုံးသည် pattern loop ကို မလုပ်ဆောင်မီ
`slice(0, MAX_INJECTION_SCAN_BYTES)` ပြုလုပ်သည်။ Injection directives များသည် input တစ်ခု၏ အပေါ်ပိုင်းအနီးတွင်
ရှိတတ်သောကြောင့် multi-hundred-KB payloads များတွင် ရှာဖွေတွေ့ရှိမှုကို အားနည်းစေခြင်းမရှိဘဲ regex CPU/GC ကို
ကန့်သတ်ပေးသည် (cf.
#3932, #4041)။

### အထောက်အထား ဖုံးကွယ်ကိရိယာ (`credentialMasker.ts`)

အဆင့် **နှစ်ခုစလုံး** တွင် ပုံသေ chain ၏ နောက်ဆုံး (ဦးစားပေး `95`) အဖြစ် လုပ်ဆောင်သည်။ Outbound payload (message
content, tool-call arguments, tool results) **နှင့်** provider response တို့မှ
လူသိများသော API-key / secret-token pattern များကို ဖုံးကွယ်သည်။ ထို့ကြောင့် prompt ထဲသို့ paste လုပ်ထားသော
credential (သို့မဟုတ် tool result မှ ပြန်လည်ထုတ်ပြသော credential) သည် upstream provider သို့မဟုတ် client ထံ
ပြန်လည်ပေါက်ကြားခြင်း မရှိပါ။

- **ကိုယ်တိုင်ဖွင့်မှသာ အသုံးပြုသည်**၊ PII redaction နှင့် တူညီသော သဘောတူညီချက် (Hard Rule #20 နှင့်ဆက်စပ်)-
  `settings.credentialRedactionEnabled === true` **သို့မဟုတ်**
  `CREDENTIAL_REDACTION_ENABLED=true` မဖြစ်ပါက ပိတ်ထားသည်။ ၎င်းကို ပိတ်ထားလျှင် guardrail သည် no-op ဖြစ်သည် —
  မည်သည့်အခါမျှ ပိတ်ဆို့ခြင်း သို့မဟုတ် ပြန်လည်ရေးသားခြင်း မပြုပါ။
- `redactCredentials()` သည် payload/response tree တစ်ခုလုံးကို ဖြတ်သန်းသည် (`walkValue()`,
  prototype-pollution-safe ဖြစ်ပြီး `WeakSet` ဖြင့် cycle-safe ဖြစ်သည်)။ တွေ့ရှိသော ကိုက်ညီမှုများကို
  `[REDACTED:<type>]` placeholder ဖြင့် အစားထိုးပြီး အမှန်တကယ်
  ပြောင်းလဲခဲ့သော branch များကိုသာ clone လုပ်သည်။
- `CREDENTIAL_PATTERNS` သည် LLM provider keys (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate)၊ VCS/SaaS tokens (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord)၊ payment keys (Stripe, Square)၊ cloud
  keys (AWS access key, Twilio, SendGrid, Mailgun)၊ private keys / JWTs၊
  credential ပါဝင်သော connection strings (`mongodb://user:pass@...` စသည်) နှင့်
  ယေဘုယျ `Authorization`/`x-api-key`/`api-key`/`apikey` header-value
  pattern တို့ကို လွှမ်းခြုံသည်။ Header ပုံစံ keys (`authorization`, `x-api-key`, `api-key`,
  `apikey`) များကို ယေဘုယျ text regex ဖြင့်မဟုတ်ဘဲ ဖွဲ့စည်းပုံအလိုက် ဖုံးကွယ်သည် (value ကိုသာ ဖုံးကွယ်ပြီး
  `Bearer `/`Basic ` ကဲ့သို့သော scheme prefix ကို မူလအတိုင်း ထိန်းသိမ်းထားသည်)။
- Guardrail သည် မည်သည့်အခါမျှ မပိတ်ဆို့ဘဲ ပြန်လည်ရေးသားခြင်း (`modifiedPayload` /
  `modifiedResponse`) နှင့် annotation ထည့်ခြင်း (`meta.credentialsRedacted`, `meta.count`) တို့ကိုသာ ပြုလုပ်သည်။

## အခြေခံ Contract (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ဖြစ်ပါက chain ကို ချက်ချင်းရပ်တန့်စေသည်
  message?: string; // ပိတ်ဆို့သည့်အခါ ဖော်ပြသည်
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // request ကို ပြန်လည်ရေးသားရန် preCall မှ ပြန်ပေးသည်
  modifiedResponse?: TValue; // response ကို ပြန်လည်ရေးသားရန် postCall မှ ပြန်ပေးသည်
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Guardrail တစ်ခုသည် `void`၊ `{}` သို့မဟုတ် `{ block: false }` တစ်ခုခုကို
ပြန်ပေးခြင်းဖြင့် "ပြောင်းလဲမှုမရှိ" ကြောင်း အချက်ပြသည်။ `modifiedPayload`/`modifiedResponse`
ကို ပြန်ပေးခြင်းသည် နောက်ဆက်တွဲ guardrail များသို့ chain တစ်လျှောက် စီးဆင်းနေသော
တန်ဖိုးကို အစားထိုးသည်။ `signal?: AbortSignal` သည် ခေါ်ဆိုသူ၏ lifecycle ကို
guardrail များသို့ သယ်ဆောင်ပေးသည်။ Request ကို ရပ်ဆိုင်းခြင်းသည် ရည်ရွယ်ထားသော
fail-open ခြွင်းချက်ဖြစ်သည်—media bridge များသည် အလုပ်လုပ်ခြင်းကို ရပ်တန့်ပြီး cleanup
ပြုလုပ်ကာ raw media ကို ပံ့ပိုးနိုင်ခြင်းမရှိကြောင်း သိထားသော target တစ်ခုသို့
ပြန်လည်မထည့်သွင်းပါ။

## Registry (`registry.ts`)

Singleton `guardrailRegistry` တွင် အောက်ပါတို့ ပါဝင်သည်-

- `register(guardrail)` — guardrail တစ်ခုကို ထည့်သွင်းပြီး (သို့မဟုတ် normalize လုပ်ထားသော
  name အလိုက် အစားထိုးပြီး) `priority` ငယ်ရာမှ ကြီးရာသို့ ပြန်လည်စီသည်။
- `clear()` / `list()` — စီမံခန့်ခွဲရေး အကူ method များ။
- `runPreCallHooks(payload, context)` — အသက်ဝင်နေသော guardrail များကို တစ်ခုပြီးတစ်ခု
  လုပ်ဆောင်ကာ payload ကို `modifiedPayload` မှတစ်ဆင့် လက်ဆင့်ကမ်းပြီး ပထမဆုံး
  `block: true` တွင် ရပ်တန့်သည်။
- `runPostCallHooks(response, context)` — response ဘက်တွင် အလားတူ flow ကို လုပ်ဆောင်သည်။
- `resetGuardrailsForTests({ registerDefaults })` — test တစ်ခုချင်းစီကို သီးခြားသန့်ရှင်းစွာ
  လုပ်ဆောင်နိုင်ရန် state ကို ရှင်းလင်းပြီး ရွေးချယ်မှုအလိုက် မူလ guardrail များကို
  ပြန်လည် register လုပ်သည်။

Runner နှစ်ခုစလုံးသည် `{ blocked, payload|response, results, guardrail?, message? }`
ကို ပြန်ပေးသည်။ ဤနေရာတွင် `results` သည် guardrail တစ်ခုချင်းစီ၏ `blocked`,
`skipped`, `modified`, `error` နှင့် `meta` field များ ပါဝင်သော
`GuardrailExecutionResult` record များ၏ array ဖြစ်ပြီး tracing အတွက် အသုံးဝင်သည်။

### Request တစ်ခုချင်းစီအလိုက် Guardrail များကို ပိတ်ခြင်း

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` သည် လက်ရှိ request အတွက်
ကျော်သွားသင့်သော guardrail name များကို ထပ်နေမှုမရှိအောင် စုစည်းပေးသည်။
ရင်းမြစ်များအားလုံးသည် မဖြစ်မနေ မဟုတ်ဘဲ ပေါင်းစည်းအသုံးပြုသည်-

- `apiKeyInfo.disabledGuardrails`
- Request body ၏ ထိပ်ဆုံးအဆင့်ရှိ `disabledGuardrails`
- Request body ၏ `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (သို့မဟုတ် အဟောင်းဖြစ်သော
  `x-disabled-guardrails`)

တန်ဖိုးများသည် string array များ သို့မဟုတ် ကော်မာဖြင့် ခွဲထားသော string တစ်ခု
ဖြစ်နိုင်သည်။ Name များကို စာလုံးအသေး kebab-case အဖြစ် normalize လုပ်သည်
(`pii_masker` → `pii-masker`)။ ရလဒ်ကို `context.disabledGuardrails` မှတစ်ဆင့်
registry သို့ ပေးပို့ပြီး ၎င်း registry က ကိုက်ညီသော guardrail များကို ကျော်သွားသည်
(`results` ထဲတွင် `skipped: true`)။

## လုပ်ဆောင်မှု အစီအစဉ်

`src/sse/handlers/chat.ts` နှင့်
`open-sse/handlers/chatCore.ts` တို့မှတစ်ဆင့် ဖြတ်သန်းသည့် request တစ်ခုစီအတွက်-

1. `resolveDisabledGuardrails(...)` သည် API key၊ body နှင့် headers တို့မှ skip list ကို တည်ဆောက်သည်။
2. `guardrailRegistry.runPreCallHooks(body, ctx)` သည် guardrails များကို priority ငယ်စဉ်ကြီးလိုက်ဖြင့် လုပ်ဆောင်သည်-
   - ပိတ်ထားသော guardrails များကို `skipped` အဖြစ် မှတ်တမ်းတင်သည်။
   - Guardrail တစ်ခုစီ၏ `preCall` သည် `modifiedPayload` မှတစ်ဆင့် payload ကို ပြန်လည်ရေးသားနိုင်သည်။
   - ပထမဆုံး `block: true` သည် chain ကို ချက်ချင်းရပ်တန့်စေပြီး handler က guardrail ငြင်းပယ်မှု response ကို ပြန်ပေးသည်။
3. (ပြန်လည်ရေးသားထားနိုင်သည့်) payload သည် combo routing နှင့် upstream dispatch ထဲသို့ စီးဆင်းသွားသည်။
4. Response ကို စုစည်းပြီးနောက် `guardrailRegistry.runPostCallHooks(...)` သည် response ပေါ်တွင် တူညီသော chain ကို လုပ်ဆောင်သည်။ ဤနေရာရှိ `block: true` သည် upstream response ကို စွန့်ပစ်သည်။

Exception ပစ်သော guardrails များကို `error: <message>` ဖြင့် မှတ်တမ်းတင်ပြီး
`logger.warn` မှတစ်ဆင့် log ရေးသော်လည်း chain သည် ဆက်လက်လုပ်ဆောင်သည် — ဒီဇိုင်းအရ fail-open ဖြစ်သည်။

## စိတ်ကြိုက် Guardrail များ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

အဆင့်များ-

1. `BaseGuardrail` ကို တိုးချဲ့ထားသော `src/lib/guardrails/myGuardrail.ts` ကို ဖန်တီးပါ။
2. `preCall` နှင့်/သို့မဟုတ် `postCall` ကို အကောင်အထည်ဖော်ပါ။
3. Import ပြုလုပ်ချိန်တွင် register လုပ်ပါ (`registerDefaultGuardrails` မှ push လုပ်ခြင်း) သို့မဟုတ်
   runtime တွင် `guardrailRegistry.register(...)` ကို ခေါ်ပါ — registry သည် normalized name တူညီသည့်
   ယခင် guardrail တစ်ခုခုကို အစားထိုးပါမည်။
4. `tests/unit/` အောက်တွင် test များ ထည့်ပါ (ရှိပြီးသား နမူနာများ-
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)။

## Injection-guard route လွှမ်းခြုံမှုနှင့် red-team (Phase 8 · Block D)

Injection-guard (`createInjectionGuard` / `withInjectionGuard`) သည် user prompt များကို
လက်ခံသည့် route အားလုံးကို လွှမ်းခြုံသည်။ ၎င်းသည် `INJECTION_GUARD_MODE` ကို လိုက်နာသည် (မူလ `warn` = log သာရေးခြင်း၊
`block` = HTTP 400 `SECURITY_001` ကို ပြန်ပေးခြင်း)။

| အမျိုးအစား        | Route များ                                                                                                                                           | မူလ mode |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| Text (ရှိပြီးသား) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn     |
| Generative        | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn     |
| Data              | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn     |

စာသားထုတ်ယူမှု (`extractMessageContents`) သည် `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ကို လွှမ်းခြုံသည်။

**Red-team (ညစဉ်၊ `nightly-llm-security.yml`):** promptfoo သည် route တစ်ခုစီက
`INJECTION_GUARD_MODE=block` တွင် OWASP-LLM corpus ကို ပိတ်ဆို့ကြောင်း အတည်ပြုသည်။ garak သည် probe များကို လုပ်ဆောင်သည် (secret မရှိပါက ကျော်သွားသည်)။
`moderations` ကို တစ်သမတ်တည်းဖြစ်စေရန် ထည့်သွင်းထားသည် — block-mode ကို အသုံးပြုသည့် operator များသည်
`resolveDisabledGuardrails` မှတစ်ဆင့် ၎င်းကို ကင်းလွတ်ခွင့်ပေးနိုင်သည်။

ညစဉ် workflow (`.github/workflows/nightly-llm-security.yml`, cron + manual
dispatch) တွင် job နှစ်ခု ပါဝင်သည်-

- **`promptfoo-guard` (ပိတ်ဆို့နိုင်သော)** — `INJECTION_GUARD_MODE=block` ဖြင့်
  `promptfoo eval -c promptfooconfig.yaml` ကို လုပ်ဆောင်သည်။ ရန်လိုသော case တစ်ခုစီ (ဥပမာ "ယခင်
  ညွှန်ကြားချက်အားလုံးကို လျစ်လျူရှုပါ…"၊ DAN ပုံစံ jailbreak များ) သည် response တွင်
  `error.code === "SECURITY_001"` ပါဝင်ကြောင်း အတည်ပြုသည်။ ဆိုလိုသည်မှာ guard က request ကို အမှန်တကယ် ငြင်းပယ်ခဲ့ခြင်းဖြစ်သည်။
- **`garak` (အကြံပြုချက်သဘော)** — local OmniRoute instance (`http://localhost:20128/v1`) ကို ဆန့်ကျင်၍
  garak `--probes promptinject,dan,leakreplay` ကို လုပ်ဆောင်သည်။ Provider secret
  (`PROMPTFOO_PROVIDER_KEY`) ပေါ် မူတည်၍ ထိန်းချုပ်ထားသည်။ secret မရှိပါက အဆင်ပြေစွာ ကျော်သွားပြီး
  `|| true` ကို နောက်ဆက်တွဲထားသောကြောင့် CI ကို ကျရှုံးစေခြင်းမရှိဘဲ အစီရင်ခံပေးသည်။

Guard helper (`createInjectionGuard` / `withInjectionGuard`) ၏ လွှမ်းခြုံမှုသည်
prompt ပါဝင်သော `/v1` route အားလုံးအထိ ရောက်ရှိသည်။ Prompt စာသားကို
`src/shared/utils/inputSanitizer.ts` ရှိ `extractMessageContents()` က
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` မှ ထုတ်ယူသည်။
