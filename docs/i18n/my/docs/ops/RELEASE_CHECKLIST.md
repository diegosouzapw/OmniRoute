```bash
# 2. အရည်အသွေးစစ်ဆေးမှုကို စက်တွင်း၌ လုပ်ဆောင်ပါ

# 4. ဖြန့်ချိမှုကို ထုတ်ပေးပါ (စွမ်းရည်)
/generate-release-cc

# 5. Deploy လုပ်ပါ (စွမ်းရည်)

/capture-release-evidences-cc
```

## npm Trusted Publishing (v3.8.51 မှစ၍ ပုံသေ) — တောင်းဆိုမှုအရ staged၊ အရန်နည်းလမ်းအဖြစ် direct

`npm-publish.yml` သည် ပုံသေအားဖြင့် **npm Trusted Publishing (OIDC)** မှတစ်ဆင့် ထုတ်ဝေသည်- `stage-npm` အလုပ် (github-hosted) သည် ထိုလုပ်ဆောင်မှုအတွက် GitHub ၏ id-token ကို သက်တမ်းတို npm အထောက်အထားတစ်ခုနှင့် လဲလှယ်သည် — repository secrets များထဲတွင် သက်တမ်းရှည် npm token မရှိ၊ 2FA တောင်းဆိုချက်မရှိဘဲ provenance ကို ပူးတွဲထားသည်။
2FA ကို ကျော်လွှားသည့် token များကို ရပ်ဆိုင်းနေပြီဖြစ်သောကြောင့် ယခု npm က ခွင့်ပြုထားသည့် ကျော်လွှားနည်းမှာ ယင်းပင်ဖြစ်သည်။
၎င်းသည် WS1.3 အာမခံချက်ကို ထိန်းသိမ်းထားစဉ် v3.8.48 အထိ ပရောဂျက်တွင် ရှိခဲ့သည့် အပြည့်အဝ အလိုအလျောက်လုပ်ဆောင်မှုကို ပြန်လည်ရရှိစေသည် (ပေါက်ကြားသွားသော token တစ်ခုတည်းဖြင့် ထုတ်ဝေ၍မရပါ — token လုံးဝမရှိပါ)။

**တစ်ကြိမ်သာ ပြင်ဆင်သတ်မှတ်ခြင်း (ပိုင်ရှင်):** npmjs.com → package `omniroute` → Settings → _Trusted Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none)။ ၎င်းမရှိသေးသရွေ့ အလိုအလျောက်အဆင့်သည် `ENEEDAUTH` ဖြင့် မအောင်မြင်ပါ-
`publish_mode=staged` (အောက်တွင်) သို့မဟုတ် `direct` ဖြင့် ပြန်လည် dispatch လုပ်ပါ။

### Staged ထုတ်ဝေခြင်း (တောင်းဆိုမှုအရ — `publish_mode=staged`)

npm-publish workflow သည် တိုက်ရိုက် ထုတ်ဝေခြင်းမပြုတော့ပါ- ၎င်းသည် pack လုပ်ထားသည့် tarball ကို စတင်စစ်ဆေးပြီး
(`check:pack-boot`) ထို့နောက် `npm stage publish` ကို လုပ်ဆောင်သည် — တိကျစွာ တူညီသည့် bytes များကို registry တွင် သိမ်းဆည်းထားပြီး ပိုင်ရှင်က အတည်ပြုသည်အထိ **ထည့်သွင်းအသုံးပြု၍ မရပါ**။ လူမှလုပ်ဆောင်ရသည့် 2FA စစ်ဆေးချက်ကို အထောက်အထားမတင်မီ မဟုတ်ဘဲ တင်ပြီးနောက်သို့ ရွှေ့ထားသည်။

**Workflow အောင်မြင်ပြီးနောက် ပိုင်ရှင်၏ လုပ်ငန်းစဉ်:**

1. `npm stage list omniroute` — stage id ကို ရှာပါ (workflow အနှစ်ချုပ်တွင်လည်း ဖော်ပြထားသည်)။
2. staged bytes များကို စစ်ဆေးပါ (အကြံပြုထားသည်)- `npm stage download <id>`၊ ထို့နောက် ဒေါင်းလုဒ်လုပ်ထားသည့် tarball ကို ယာယီ prefix တစ်ခုတွင် ထည့်သွင်းပြီး စတင်ပါ (`npm run check:pack-boot` သည် တူညီသော pack→install→boot စစ်ဆေးဆုံးဖြတ်ချက်ကို CI တွင် အလိုအလျောက်လုပ်ဆောင်ပေးသည်)။
3. `npm stage approve <id>` — 2FA တောင်းဆိုချက်သည်ပင် ထုတ်ဝေခြင်းဖြစ်သည်။ `npm stage reject <id>` သည် ပယ်ဖျက်သည်။
4. ထုတ်ဝေပြီးနောက် လုံခြုံရေးပိုက်ကွန်- ထုတ်ဝေပြီးနောက် စစ်ဆေးကိရိယာ (v3.8.49 အစီအစဉ်၏ WS1.4) သည် public registry မှ ထုတ်ဝေထားသည့်ဗားရှင်းကို သန့်ရှင်းသော container တစ်ခုတွင် ထည့်သွင်းပြီး စတင်စစ်ဆေးသည်။

**အရေးပေါ် အရန်နည်းလမ်း:** `publish_mode=direct` ပါသည့် `workflow_dispatch` သည် ယခင်ပုံစံ ချက်ချင်း `npm publish` ကို ပြန်လည်အသုံးပြုစေသည် (staging ကိုယ်တိုင် ချို့ယွင်းမှသာ အသုံးပြုပြီး အကြောင်းရင်းကို မှတ်တမ်းတင်ပါ)။

**တစ်ကြိမ်သာ လုံခြုံရေးမြှင့်တင်ခြင်း (ပိုင်ရှင်၊ npmjs.com):** ပေါက်ကြားသွားသော သက်တမ်းရှည် token တစ်ခုက မည်သည့်နေရာမှမဆို တိုက်ရိုက် `npm publish` မလုပ်နိုင်စေရန် `omniroute` အတွက် Trusted Publisher ကို stage-only mode ဖြင့် သတ်မှတ်ပါ — CI သည် stage သာ လုပ်နိုင်ပြီး ပိုင်ရှင်၏ 2FA ကသာ ဖြန့်ချိနိုင်သည်။

**ပျက်စီးနေသော artifact အတွက် လုပ်ဆောင်ရန်နည်းလမ်း (မပြောင်းလဲ):** ပုံသေလုပ်ဆောင်ချက်အဖြစ် `npm deprecate omniroute@<bad> "<reason> — use <fixed>"` ကို အသုံးပြုပါ (မိနစ်ပိုင်းအတွင်း လုပ်ဆောင်နိုင်ပြီး ပြန်ပြောင်းနိုင်သည်)။ `npm unpublish` ကို 72h/no-dependents ကာလအတွင်းသာ အသုံးပြုပြီး ပထမဦးဆုံး လုပ်ဆောင်ချက်အဖြစ် ဘယ်တော့မှ မသုံးပါနှင့်။ Docker အတွက် ဗားရှင်း tag တစ်ခုကို ဘယ်တော့မှ ပြန်မရေးပါနှင့် — rollback ဆိုသည်မှာ `latest` ကို နောက်ဆုံး ကောင်းမွန်သည့် digest သို့ ပြန်ညွှန်ခြင်းဖြစ်သည်။

**Docker Hub `latest` (တည်ငြိမ်သော SemVer ကို ထုတ်ဝေတိုင်း မဖြစ်မနေလိုအပ်သည်):**
`docker-publish` workflow သည် `X.Y.Z` ကို tag လုပ်ရမည့်အပြင် `should-promote-latest.sh` က ၎င်းသည် အမြင့်ဆုံး တည်ငြိမ်သော SemVer ဖြစ်ကြောင်း သဘောတူသည့်အခါ `:latest` ကိုလည်း **တူညီသော digest** ဖြင့် tag လုပ်ရမည်။
အလုပ်ပြီးနောက် Hub `latest` digest သည် SemVer digest အသစ်နှင့် တူညီပြီး `last_updated` သည်လည်း ပြောင်းလဲထားရမည်။ release notes များက git တွင်သာရှိသော ပြင်ဆင်ချက်များအကြောင်း ဖော်ပြနေစဉ် `:latest` ကို build အဟောင်းတွင် မထားခဲ့ပါနှင့်။
Compose quickstart များသည် `:latest` ကို အသုံးပြုသည်။ GitOps သည် `X.Y.Z` ကို ဆက်လက် pin လုပ်ထားသင့်သည်။ [Docker ဖြန့်ချိမှု channel များ](../guides/DOCKER_GUIDE.md#release-channels) နှင့် #10317 ကို ကြည့်ပါ။

## Hotfix အမြန်လမ်းကြောင်း (label `hotfix`)

`hotfix` label တပ်ထားသော PR သည် အလေးချိန်ကြီးမားသည့် CI matrix (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) ကို ကျော်သွားပြီး မြန်ဆန်ကာ အရေးကြီးသော အချက်ပြမှုများပေးသည့် gate များဖြစ်သော build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
နှင့် tarball boot-smoke (`check:pack-boot`) တို့ကို ဆက်လက်ထားရှိသည်။ ရည်မှန်းချက်မှာ ~33min အစား ≤15min အတွင်း green ဖြစ်ရန်ဖြစ်သည်။

**ဝင်ခွင့်မူဝါဒ — လေးချက်စလုံး လိုအပ်သည် (Chromium/VS Code/Node အရေးပေါ်လမ်းကြောင်းများကို စံနမူနာယူထားသည်):**

1. **ပြင်းထန်မှု**: production ပျက်နေသည် — ထုတ်ဝေထားသော artifact သည် boot လုပ်ချိန်တွင် crash ဖြစ်ခြင်း /
   လုံခြုံရေးပြင်ဆင်ချက်တစ်ခု / release အသုံးပြုသူတိုင်း ထိခိုက်ခြင်း။ "အရေးကြီးသည်" ဆိုသည်မှာ "ပျက်နေသည်" ဟု မဆိုလိုပါ။
2. **လုပ်ပိုင်ခွင့်**: repository ပိုင်ရှင်သာ `hotfix` label ကို တပ်နိုင်သည်။ ထို label သည်
   အတည်ပြုချက်ပင်ဖြစ်သည် — campaign PR တွင် မိမိဘာသာ ဘယ်တော့မှ မတပ်ရ။
3. **အထောက်အထား**: PR body တွင် ယခင် fully-green heavy run (ကျော်ထားသည့် job များက
   ပြန်လည်စစ်ဆေးမည့် suite) နှင့် ပြင်ဆင်ချက်၏ ကိုယ်ပိုင် failing-then-passing test ကို link ချိတ်ထားရမည်။
4. **နယ်ပယ်**: cherry-pick သီးသန့် — အနည်းဆုံးလိုအပ်သော ပြင်ဆင်ချက်သာ၊ refactor မပါရ၊ ဆက်စပ်မဟုတ်သော ပြောင်းလဲမှုများ မထည့်ရ။

ကျော်ထားသည့် coverage/ratchet မျက်နှာပြင်ကို
release branch ပေါ်ရှိ နောက်ထပ် full run (continuous release-green) က ပြန်လည်စစ်ဆေးသည် — ဤလမ်းကြောင်းသည် စောင့်ဆိုင်းရမှုကိုသာ ကျော်ပြီး validation ကို ဘယ်တော့မှ မကျော်ပါ။
Tests-only diff များ (`tests/` အောက်ရှိ file အားလုံးဖြစ်ပြီး `tests/e2e/` အောက်တွင် မည်သည့် file မှမရှိခြင်း) သည် မည်သည့် label မှမလိုဘဲ E2E
matrix ကို အလိုအလျောက် ကျော်သည်။

### Hook များ (Husky ဖြင့် အတည်ပြုထားသည်)

Husky hook များသည် `.husky/` တွင်ရှိပြီး git operation များအတွင်း အလိုအလျောက် run သည်။

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** မြန်ဆန်ပြီး ရလဒ်အမြဲတူညီသော gate များ — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (2026-06-13 တွင် အသက်သွင်းခဲ့သည်)။ `test:unit` ကို ရည်ရွယ်ချက်ရှိရှိ ချန်လှပ်ထားသည် (နှေးကွေးပြီး CI `test-unit` job က လွှမ်းခြုံထားသည်)။
  - release branch များကို push မလုပ်မီ `npm run test:unit` ကို ကိုယ်တိုင် run ပါ။

Hook တစ်ခု fail ဖြစ်ပါက: အရင်းခံပြဿနာကို ပြင်ဆင်ပါ၊ `--no-verify` ဖြင့် မကျော်ပါနှင့်။

### Conventional Commit များ

**တရားဝင် scope များ:** `db`, `sse`, `oauth`, `dashboard`, `api`, `cli`, `docker`, `ci`, `mcp`, `a2a`, `memory`, `skills`, `cloud-agent`, `guardrails`, `compression`, `auto-combo`, `resilience`, `providers`, `executors`, `translator`, `domain`, `authz`

Breaking change များ: `BREAKING CHANGE:` footer ထည့်ပါ သို့မဟုတ် scope နောက်တွင် `!` ထည့်ပါ (ဥပမာ `feat(api)!: drop /v0`)။

### Build ဖွဲ့စည်းပုံ

Repository သည် သီးခြား output directory သုံးခုကို အသုံးပြုသည် — ၎င်းတို့ကို မည်သည့်အခါမျှ မရောထွေးပါနှင့်:

| Directory | ရည်ရွယ်ချက်                                                           | Track လုပ်ထားသလား                 |
| --------- | --------------------------------------------------------------------- | --------------------------------- |
| `src/`    | Application source (TypeScript / TSX)                                 | လုပ်ထားသည်                        |
| `.build/` | Build အလယ်ဆင့်ဖိုင်များ — `next build` output (`distDir`)             | မလုပ်ထားပါ (gitignore လုပ်ထားသည်) |
| `dist/`   | ဖြန့်ချိနိုင်သော npm bundle — `assembleStandalone` ဖြင့် စုစည်းထားသည် | မလုပ်ထားပါ (gitignore လုပ်ထားသည်) |

> **Operator မှတ်ချက်:** remote VPS image directory သည် `/usr/lib/node_modules/omniroute/app/` အဖြစ် ဆက်လက်တည်ရှိသည်။
> **Repository အတွင်းရှိ** build output သာ ရွှေ့ထားသည် (`app/` → `dist/`)။ Deploy skill များက
> `dist/` ထဲရှိ အကြောင်းအရာများကို remote `app/` directory သို့ rsync လုပ်သည် — VPS path ပြောင်းလဲရန် မလိုအပ်ပါ။

**တစ်ကြိမ်တည်း build လုပ်သည့် flow:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Deploy လုပ်ရန် `npm run build` ကို run ပြီးနောက် `npm run build:cli` ကို သီးခြားထပ်မံ run ခြင်း မလုပ်ပါနှင့် —
clean rebuild + sentinel ကို command တစ်ခုတည်းဖြင့် လုပ်ဆောင်ပေးသည့် `npm run build:release` ကို အသုံးပြုပါ။

## နောက်ပြန်ပြန်ပြောင်းခြင်း

Release တွင် အရေးကြီးသော ပြဿနာရှိပါက-

1. `gh release edit vX.Y.Z --prerelease` (နောက်ဆုံးဗားရှင်းမဟုတ်ကြောင်း သတ်မှတ်သည်)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (အသုံးပြုသူများက မသုံးစွဲရသေးမှသာ)
3. သို့မဟုတ်- `release/vX.Y.0` တွင် hotfix ပြုလုပ်ပြီး → patch release `vX.Y.(Z+1)` ထုတ်ပါ
4. GitHub Discussions နှင့် Discord တွင် ချက်ချင်း အသိပေးပါ

## တင်းကျပ်သော စည်းမျဉ်းများ

- `main` သို့ ဘယ်သောအခါမျှ တိုက်ရိုက် commit မလုပ်ပါနှင့်
- `main` သို့မဟုတ် `release/*` branch များတွင် `git push --force` ကို ဘယ်သောအခါမျှ အသုံးမပြုပါနှင့်
- Husky hook များကို (`--no-verify`) သုံး၍ ဘယ်သောအခါမျှ ကျော်မသွားပါနှင့်
- လျှို့ဝှက်အချက်အလက်များ၊ အထောက်အထားများ သို့မဟုတ် `.env` file များကို ဘယ်သောအခါမျှ commit မလုပ်ပါနှင့်
- Coverage သည် ≥60/60/60/60 (statement/line/function/branch) တွင် ဆက်လက်ရှိနေရမည်
- `src/`၊ `open-sse/`၊ `electron/` သို့မဟုတ် `bin/` ရှိ production code ကို ပြောင်းလဲသည့်အခါ test များကို အမြဲထည့်သွင်းပါ သို့မဟုတ် အပ်ဒိတ်လုပ်ပါ
