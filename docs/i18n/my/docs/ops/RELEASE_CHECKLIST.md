## npm Trusted Publishing (v3.8.51 မှစ၍ default) — တောင်းဆိုမှုရှိပါက staged၊ အရန်နည်းလမ်းအဖြစ် direct

`npm-publish.yml` သည် default အနေဖြင့် **npm Trusted Publishing (OIDC)** မှတစ်ဆင့် publish လုပ်ပါသည်။ `stage-npm` job (github-hosted) သည် ထို run အတွက် GitHub ၏ id-token ကို သက်တမ်းတို npm credential တစ်ခုနှင့် လဲလှယ်ပါသည် — repository secrets များထဲတွင် သက်တမ်းရှည် npm token မရှိ၊ 2FA prompt မရှိဘဲ provenance ကို ပူးတွဲထားပါသည်။
2FA ကို ကျော်လွှားနိုင်သည့် token များကို ရပ်ဆိုင်းနေပြီဖြစ်သောကြောင့် ယခုနည်းလမ်းသည် npm က ခွင့်ပြုထားသည့် bypass ဖြစ်ပါသည်။ ၎င်းသည် WS1.3 အာမခံချက်ကို ဆက်လက်ထိန်းသိမ်းရင်း project တွင် v3.8.48 အထိ ရှိခဲ့သည့် အပြည့်အဝ အလိုအလျောက် flow ကို ပြန်လည်ရရှိစေပါသည် (token ပေါက်ကြားမှုတစ်ခုတည်းဖြင့် publish မလုပ်နိုင်ပါ — အဘယ်ကြောင့်ဆိုသော် token လုံးဝမရှိသောကြောင့် ဖြစ်သည်)။

**တစ်ကြိမ်သာ setup လုပ်ရန် (owner):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none)။ ၎င်းမရှိသေးမီအထိ အလိုအလျောက်အဆင့်သည် `ENEEDAUTH` ဖြင့် ကျရှုံးမည်ဖြစ်ပြီး `publish_mode=staged` (အောက်တွင်ကြည့်ပါ) သို့မဟုတ် `direct` ဖြင့် ပြန်လည် dispatch လုပ်ပါ။

### Staged publishing (တောင်းဆိုမှုရှိပါက — `publish_mode=staged`)

npm-publish workflow သည် ယခုအခါ တိုက်ရိုက် publish မလုပ်တော့ပါ။ ၎င်းသည် ထုပ်ပိုးထားသော tarball ကို boot လုပ်ပြီး (`check:pack-boot`) ထို့နောက် `npm stage publish` ကို လုပ်ဆောင်ပါသည် — byte အတိအကျကို registry တွင် သိမ်းဆည်းထားသော်လည်း owner က အတည်ပြုမချင်း **install လုပ်၍မရနိုင်ပါ**။ လူကိုယ်တိုင်လုပ်ဆောင်ရသည့် 2FA gate ကို သက်သေပြမှုမတိုင်မီမှ သက်သေပြပြီးနောက်သို့ ရွှေ့ထားပါသည်။

**Workflow green ဖြစ်ပြီးနောက် owner လုပ်ဆောင်ရန် flow:**

1. `npm stage list omniroute` — stage id ကို ရှာပါ (workflow summary တွင်လည်း ဖော်ပြထားသည်)။
2. Staged bytes များကို အတည်ပြုပါ (အကြံပြုသည်): `npm stage download <id>` ကို လုပ်ဆောင်ပြီးနောက် download လုပ်ထားသော tarball ကို ယာယီ prefix တစ်ခုထဲတွင် install လုပ်၍ boot လုပ်ပါ (`npm run check:pack-boot` သည် အလားတူ pack→install→boot အဆုံးအဖြတ်ကို CI တွင် အလိုအလျောက်လုပ်ဆောင်ပေးသည်)။
3. `npm stage approve <id>` — 2FA prompt သည် publish လုပ်ခြင်းပင် ဖြစ်သည်။ `npm stage reject <id>` သည် စွန့်ပစ်ပါသည်။
4. Publish လုပ်ပြီးနောက် အကာအကွယ်: post-publish verifier (v3.8.49 plan ၏ WS1.4) သည် publish လုပ်ထားသော version ကို public registry မှ clean container တစ်ခုထဲတွင် install လုပ်ပြီး boot လုပ်ပါသည်။

**အရေးပေါ်အရန်နည်းလမ်း:** `publish_mode=direct` ဖြင့် `workflow_dispatch` လုပ်ခြင်းသည် ယခင် `npm publish` ကို ချက်ချင်းလုပ်ဆောင်သည့် နည်းလမ်းအား ပြန်လည်အသုံးပြုနိုင်စေပါသည် (staging ကိုယ်တိုင် မှားယွင်းလုပ်ဆောင်နေမှသာ အသုံးပြုပြီး အကြောင်းရင်းကို မှတ်တမ်းတင်ပါ)။

**တစ်ကြိမ်သာ hardening လုပ်ရန် (owner, npmjs.com):** ပေါက်ကြားသွားသော သက်တမ်းရှည် token ဖြင့် မည်သည့်နေရာမှမဆို `npm publish` ကို တိုက်ရိုက်မလုပ်နိုင်စေရန် `omniroute` အတွက် Trusted Publisher ကို stage-only mode ဖြင့် configure လုပ်ပါ — CI သည် stage သာ လုပ်နိုင်ပြီး owner ၏ 2FA ဖြင့်သာ release လုပ်နိုင်ပါသည်။

**ပျက်စီးနေသော artifact အတွက် လုပ်ဆောင်ရန်အစီအစဉ် (မပြောင်းလဲပါ):** Default တုံ့ပြန်ဆောင်ရွက်မှုအဖြစ် `npm deprecate omniroute@<bad> "<reason> — use <fixed>"` ကို အသုံးပြုပါ (မိနစ်ပိုင်းအတွင်း ပြီးမြောက်ပြီး ပြန်ပြင်နိုင်သည်)။ `npm unpublish` ကို 72h/no-dependents အချိန်ကန့်သတ်ချက်အတွင်းသာ အသုံးပြုပြီး ပထမဆုံးလုပ်ဆောင်ချက်အဖြစ် မည်သည့်အခါမျှ မသုံးပါနှင့်။ Docker: version tag ကို မည်သည့်အခါမျှ ပြန်လည်မရေးပါနှင့် — rollback ဆိုသည်မှာ `latest` ကို နောက်ဆုံးကောင်းမွန်သော digest သို့ ပြန်ညွှန်းခြင်းဖြစ်သည်။

**Docker Hub `latest` (stable SemVer publish တိုင်းတွင် မဖြစ်မနေလိုအပ်သည်):** `docker-publish` workflow သည် `X.Y.Z` နှင့် `should-promote-latest.sh` က ၎င်းသည် အမြင့်ဆုံး stable SemVer ဖြစ်ကြောင်း သဘောတူသည့်အခါ `:latest` နှစ်ခုစလုံးကို **တူညီသော digest** ဖြင့် tag လုပ်ရမည်။ Job ပြီးနောက် Hub `latest` digest သည် SemVer အသစ်၏ digest နှင့် တူညီရမည်ဖြစ်ပြီး `last_updated` လည်း ပြောင်းလဲထားရမည်။ Release notes များက git ပေါ်တွင်သာရှိသည့် ပြင်ဆင်ချက်များအကြောင်း ဖော်ပြနေချိန်တွင် `:latest` ကို build အဟောင်းတွင် မထားခဲ့ပါနှင့်။ Compose quickstarts များသည် `:latest` ကို အသုံးပြုပြီး GitOps ကမူ `X.Y.Z` ကို ဆက်လက် pin လုပ်ထားသင့်သည်။ [Docker release channels](../guides/DOCKER_GUIDE.md#release-channels) နှင့် #10317 ကို ကြည့်ပါ။

## အရေးပေါ်ပြင်ဆင်မှု အမြန်လမ်းကြောင်း (label `hotfix`)

`hotfix` label တပ်ထားသော PR သည် လေးလံသည့် CI matrix (9-shard E2E၊ coverage ratchet၊
quality-gate၊ quality-extended) ကို ကျော်ပြီး မြန်ဆန်ကာ အရေးကြီးသည့် ပြဿနာများကို ကောင်းစွာဖော်ထုတ်နိုင်သော gate များဖြစ်သည့် build၊
unit shard များ၊ integration၊ vitest၊ lint/typecheck၊ docs-sync၊ `check:pack-artifact`
နှင့် tarball boot-smoke (`check:pack-boot`) တို့ကို ဆက်လက်ထားရှိသည်။ ရည်မှန်းချက်မှာ ~33min အစား ≤15min အတွင်း green ဖြစ်ရန်ဖြစ်သည်။

**ဝင်ရောက်ခွင့်မူဝါဒ — လေးချက်စလုံး လိုအပ်သည် (Chromium/VS Code/Node အရေးပေါ်လမ်းကြောင်းများကို စံနမူနာယူထားသည်):**

1. **ပြင်းထန်မှု**: production ပျက်နေခြင်း — ထုတ်ဝေထားသော artifact သည် boot လုပ်စဉ် crash ဖြစ်ခြင်း /
   လုံခြုံရေးပြင်ဆင်ချက်ဖြစ်ခြင်း / release အသုံးပြုသူတိုင်း ထိခိုက်ခြင်း။ "အရေးကြီးသည်" ဆိုသည်မှာ "ပျက်နေသည်" မဟုတ်ပါ။
2. **လုပ်ပိုင်ခွင့်**: repository owner တစ်ဦးတည်းသာ `hotfix` label ကို တပ်ရမည်။ ထို label ကိုယ်တိုင်က
   အတည်ပြုချက် ဖြစ်သည် — campaign PR တစ်ခုတွင် မိမိဘာသာ မည်သည့်အခါမျှ မတပ်ရ။
3. **အထောက်အထား**: PR body တွင် ယခင် fully-green heavy run (ကျော်ထားသော job များက
   ထပ်မံစစ်ဆေးမည့် suite) အပြင် ပြင်ဆင်ချက်ကိုယ်တိုင်၏ failing-then-passing test ကိုပါ link ချိတ်ထားရမည်။
4. **အတိုင်းအတာ**: cherry-pick-only — အနည်းဆုံးလိုအပ်သော ပြင်ဆင်ချက်သာဖြစ်ပြီး refactor များနှင့် မသက်ဆိုင်သော အပြောင်းအလဲများ မပါရ။

ကျော်ထားသော coverage/ratchet မျက်နှာပြင်ကို release branch ရှိ နောက်ထပ် full run
(စဉ်ဆက်မပြတ် release-green) က ပြန်လည်စစ်ဆေးသည် — ဤလမ်းကြောင်းသည် စောင့်ဆိုင်းချိန်ကိုသာ ကျော်ပြီး စစ်ဆေးအတည်ပြုမှုကို မည်သည့်အခါမျှ မကျော်ပါ။
Test သီးသန့် diff များ (`tests/` အောက်ရှိ file အားလုံးဖြစ်ပြီး `tests/e2e/` အောက်တွင် တစ်ခုမျှမရှိခြင်း) သည် မည်သည့် label မလိုဘဲ E2E
matrix ကို အလိုအလျောက် ကျော်သည်။

### Hook များ (Husky ဖြင့် စစ်ဆေးထားသည်)

Husky hook များသည် `.husky/` တွင်ရှိပြီး git operation များလုပ်သည့်အခါ အလိုအလျောက် run သည်။

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** မြန်ဆန်ပြီး ရလဒ်တည်ငြိမ်သော gate များ — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (2026-06-13 တွင် စတင်အသုံးပြုခဲ့သည်)။ `test:unit` ကို ရည်ရွယ်ချက်ရှိရှိ ဖယ်ထားသည် (နှေးသောကြောင့်၊ CI `test-unit` job က စစ်ဆေးပေးသည်)။
  - Release branch များကို push မလုပ်မီ `npm run test:unit` ကို ကိုယ်တိုင် run ပါ။

Hook တစ်ခု fail ဖြစ်ပါက အရင်းခံပြဿနာကို ပြင်ဆင်ပါ၊ `--no-verify` ဖြင့် မကျော်ပါနှင့်။

### Build ဖွဲ့စည်းပုံ

repository သည် မတူညီသော output directory သုံးခုကို အသုံးပြုသည် — ၎င်းတို့ကို မည်သည့်အခါမျှ ရောထွေးမသုံးပါနှင့်:

| Directory | ရည်ရွယ်ချက်                                                           | ခြေရာခံထားသလား?                |
| --------- | --------------------------------------------------------------------- | ------------------------------ |
| `src/`    | Application source (TypeScript / TSX)                                 | ဟုတ်သည်                        |
| `.build/` | Build ကြားခံဖိုင်များ — `next build` output (`distDir`)               | မဟုတ်ပါ (gitignore လုပ်ထားသည်) |
| `dist/`   | ဖြန့်ချိနိုင်သော npm bundle — `assembleStandalone` ဖြင့် စုစည်းထားသည် | မဟုတ်ပါ (gitignore လုပ်ထားသည်) |

> **Operator မှတ်ချက်:** remote VPS image directory သည် `/usr/lib/node_modules/omniroute/app/` အဖြစ် ဆက်လက်ရှိနေသည်။
> **repository အတွင်းရှိ** build output သာ ရွှေ့ထားသည် (`app/` → `dist/`)။ deploy skill များသည်
> `dist/` ရှိ အကြောင်းအရာများကို remote `app/` directory သို့ rsync လုပ်သည် — VPS path ပြောင်းလဲရန် မလိုအပ်ပါ။

**တစ်ကြိမ်တည်း build လုပ်ဆောင်မှု:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

deploy လုပ်ရန် `npm run build` ကို လုပ်ဆောင်ပြီးနောက် သီးခြား `npm run build:cli` ကို မလုပ်ဆောင်ပါနှင့် —
သန့်ရှင်းစွာ ပြန်လည် build လုပ်ခြင်း + sentinel ရေးသားခြင်းကို command တစ်ခုတည်းဖြင့် လုပ်ဆောင်ပေးသော `npm run build:release` ကို အသုံးပြုပါ။

### အစမ်းပြေးခြင်း (ဖတ်ရန်သာ၊ အချိန်မရွေး ဘေးကင်းစွာ လုပ်ဆောင်နိုင်သည်)

`scripts/release/dry-run-lts-cut.mjs` သည် မည်သည့်လုပ်ဆောင်ချက်မျှ မပြုလုပ်ပါ။ ၎င်းသည် git နှင့် `gh` ကို ဖတ်ရှုပြီး
လုပ်ငန်းစဉ်တစ်ခုလုံးကို ပုံနှိပ်ပြသသည် — ကြိုတင်လိုအပ်ချက်များ (source ကို ရှာဖွေသတ်မှတ်နိုင်ခြင်း၊ ယခင် tag ရှိခြင်း၊ `package.json` သည်
ပစ်မှတ်ဗားရှင်း ဖြစ်ခြင်း၊ `release-freeze` issue တစ်ခု ဖွင့်ထားခြင်း၊ လက်ရှိ release branch တစ်ခုတွင် ဖွင့်ထားသော `Release branch not green` issue
မရှိခြင်း — မရှိသေးသော branch တစ်ခုကို green ဟု ဘယ်သောအခါမျှ မသတ်မှတ်ဘဲ `?` unknown ဟု
ဖော်ပြခြင်း — Mergify `release` queue ကို စီစဉ်သတ်မှတ်ထားခြင်း (G11: `queue_rules`, `checks_timeout`,
label `queue`)၊ `release/*` ruleset က deletion နှင့် force-push ကို ဆက်လက်ပိတ်ပင်ထားခြင်းနှင့်
`stable/v3`၊ `develop` တို့ မရှိသေးခြင်း)၊ branch အဆင့်နှစ်ခု၊ မည်သည့် dormant-workflow
trigger များနှင့် `if:` အခြေအနေများ true ဖြစ်လာသည် (ထို့ပြင် မည်သည်တို့က repository variable ဖြင့် ဆက်လက်ကန့်သတ်ထားသည် သို့မဟုတ်
canonical repository တွင် ပုံသေသတ်မှတ်ထားသည်)၊ မျှော်လင့်ထားသော dist-tag များ (`latest` → 3.9.0၊ `next` နှင့်
`nightly` ဗလာ) နှင့် rollback တို့ ဖြစ်သည်။ Exit `0` = `RESULT: READY`၊ `1` = ပိတ်ဆို့သော ကြိုတင်လိုအပ်ချက်
မအောင်မြင် (`✗`)၊ `2` = အသုံးပြုပုံအမှား။ `--advisory <id,...>` သည် စစ်ဆေးမှုတစ်ခုကို မဖျောက်ဘဲ သတိပေးချက် (`!`)
အဆင့်သို့ လျှော့ချပေးသည်။

### PR preview artifact (တစ်ကြိမ်တည်ဆောက်ပြီး တူညီသော byte များကို အဆင့်မြှင့်တင်ပါ)

`.github/workflows/preview-artifact.yml` သည် PR head တစ်ခုမှ production tarball တစ်ခုကို တည်ဆောက်ပြီး
ထိုတည်ဆောက်မှုအတိအကျကို စစ်ဆေးအတည်ပြုသည် (#8084 slice (a))။ Repository တစ်ခုတည်းမှ PR များအတွက်သာဖြစ်ပြီး မည်သည့်အရာကိုမျှ publish မလုပ်ပါ။

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # သို့မဟုတ် `preview-artifact` label ကို ထည့်ပါ
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # preview ကို install လုပ်ပါ
```

Run သည် `npm ci`, `npm run build:release`, `npm run check:pack-artifact` တို့ကို လုပ်ဆောင်ပြီး tarball ကို pack လုပ်ကာ
`npm run check:pack-boot` (အတု secret များ၊ ယာယီ data dir) ကို လုပ်ဆောင်သည်။ ထို့နောက် ပြန်လည် pack လုပ်ပြီး
digest မတူညီပါက မအောင်မြင်ကြောင်း သတ်မှတ်ကာ `artifact-identity.json` (head SHA၊ base
SHA၊ lockfile hash၊ platform၊ arch၊ node ABI၊ bundler၊ build policy —
`scripts/release/artifact-identity.mjs`) ကို မှတ်တမ်းတင်ပြီး သီးခြား job တစ်ခုတွင် tarball ကို ထောက်ခံအတည်ပြုသည်။ Preview တစ်ခုကို အဆင့်မြှင့်တင်ခြင်းဆိုသည်မှာ
ထို tarball ကို install လုပ်ခြင်းဖြစ်သည်။ source မှ ဘယ်သောအခါမျှ ပြန်လည်မတည်ဆောက်ပါနှင့်။

### ခွဲထုတ်ခြင်း (3.9.0၊ GO ပြီးနောက်)

1. GO ကို [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md) တွင် မှတ်တမ်းတင်ထားသည်။
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` က `RESULT: READY` ဟု ပုံနှိပ်ပြသသည်။
3. Dry-run က ပုံနှိပ်ပြသသော command များဖြင့် `origin` ပေါ်တွင် branch များကို ကိုယ်တိုင်ဖန်တီးပါ — script သည်
   `origin` သို့ push လုပ်ရန် ငြင်းပယ်သည်။ Review လုပ်ထားသော develop commit တစ်ခုကို ပြန်လည်အသုံးပြုရန်
   သင်၏ fork တွင် 3.9.0 tip အပေါ် `--execute` အစမ်းလေ့ကျင့်မှုကို ဦးစွာလုပ်ဆောင်ပါ။ ၎င်းက SHA နှစ်ခုစလုံးကို ပုံနှိပ်ပြသပြီး
   တူညီသော commit များကို push လုပ်နိုင်သည်-

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. ပထမဆုံး PR မဝင်ရောက်မီ `stable/v3` နှင့် `develop` ကို ကာကွယ်ပါ (ruleset များ + merge queue)။
5. Branch ရှိလာသည်နှင့် dormant workflow များ စတင်အလုပ်လုပ်သည်- `forward-port.yml` (`stable/v3` သို့ push)၊
   `validate-stable-pr.yml` (`stable/v3` သို့ PR များ) နှင့် `nightly-v4-build.yml`
   (`develop` ကို တည်ဆောက်သည်)။ Go-live မတိုင်မီ `secrets.FORWARD_PORT_TOKEN` repository secret ကို သတ်မှတ်ပါ (သို့မှသာ forward-port PR များတွင်
   CI လည်ပတ်မည်)။ ပိုင်ရှင်က repository variable `vars.NIGHTLY_PUBLISH` ကို `true` ဟု မသတ်မှတ်မချင်းနှင့် npm Trusted Publishing က
   `nightly-v4-build.yml` ကို လက်မခံမချင်း nightly publishing ကို ပိတ်ထားမည်။
   Channel resolution မှာ `scripts/release/dist-tag.mjs` ဖြစ်ပြီး `npm-publish.yml` ကလည်း အလားတူ resolver ကို အသုံးပြုသည်။
6. Channel များကို စစ်ဆေးပါ- `npm view omniroute dist-tags --json` တွင် `latest` = 3.9.0 ဟု ပြသပြီး
   v4 ကို publish မလုပ်မချင်း `next` / `nightly` မရှိကြောင်း အတည်ပြုပါ။
7. လိုအပ်ပါက rollback လုပ်ရန်- `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   နှင့် `npm dist-tag add omniroute@3.8.59 latest` ကို လုပ်ဆောင်ပါ။

3. သို့မဟုတ်- `release/vX.Y.0` တွင် hotfix ပြုလုပ်ပြီး → patch release `vX.Y.(Z+1)` ထုတ်ပါ
4. GitHub Discussions နှင့် Discord တွင် ချက်ချင်း အသိပေးပါ

## တင်းကျပ်သော စည်းမျဉ်းများ

- `main` သို့ တိုက်ရိုက် commit ဘယ်တော့မှ မလုပ်ပါနှင့်
- `main` သို့မဟုတ် `release/*` branch များသို့ `git push --force` ဘယ်တော့မှ မသုံးပါနှင့်
- Husky hook များကို (`--no-verify`) အသုံးပြု၍ ဘယ်တော့မှ ကျော်မသွားပါနှင့်
- လျှို့ဝှက်ချက်များ၊ အထောက်အထားများ သို့မဟုတ် `.env` ဖိုင်များကို ဘယ်တော့မှ commit မလုပ်ပါနှင့်
- Coverage ကို ≥60/60/60/60 (statements/lines/functions/branches) တွင် ဆက်လက်ထိန်းသိမ်းထားရမည်
- `src/`, `open-sse/`, `electron/` သို့မဟုတ် `bin/` ရှိ production code ကို ပြောင်းလဲသည့်အခါ test များကို အမြဲထည့်သွင်းပါ သို့မဟုတ် အပ်ဒိတ်လုပ်ပါ

## အလိုအလျောက် Sync စစ်ဆေးမှု

PR မဖွင့်မီ docs sync guard ကို local တွင် run ပါ-

```bash
npm run check:docs-sync
```

CI သည်လည်း ဤစစ်ဆေးမှုကို `.github/workflows/ci.yml` (lint job) တွင် run ပါသည်။
