Cloudflare မှတစ်ဆင့် စီမံခန့်ခွဲထားသော ဒိုမိန်းဖြင့် VM (VPS) ပေါ်တွင် OmniRoute ကို ထည့်သွင်းပြီး စီစဉ်သတ်မှတ်ရန် လမ်းညွှန်အပြည့်အစုံ။

---

## ကြိုတင်လိုအပ်ချက်များ

| အမျိုးအစား | အနည်းဆုံး                         | အကြံပြုချက်      |
| ---------- | --------------------------------- | ---------------- |
| **CPU**    | 1 vCPU                            | 2 vCPU           |
| **RAM**    | 1 GB                              | 2 GB             |
| **Disk**   | 10 GB SSD                         | 25 GB SSD        |
| **OS**     | Ubuntu 22.04 LTS                  | Ubuntu 24.04 LTS |
| **Domain** | Cloudflare တွင် မှတ်ပုံတင်ထားရမည် | —                |
| **Docker** | Docker Engine 24+                 | Docker 27+       |

**စမ်းသပ်ထားသော ဝန်ဆောင်မှုပေးသူများ**: Akamai (Linode), DigitalOcean, Vultr, Hetzner, AWS Lightsail။

## 1. VM ကို စီစဉ်သတ်မှတ်ခြင်း

### 1.1 Instance ကို ဖန်တီးခြင်း

သင်နှစ်သက်ရာ VPS ဝန်ဆောင်မှုပေးသူတွင်-

- Ubuntu 24.04 LTS ကို ရွေးချယ်ပါ
- အနည်းဆုံးအစီအစဉ် (1 vCPU / 1 GB RAM) ကို ရွေးချယ်ပါ
- ခိုင်မာသော root စကားဝှက်တစ်ခု သတ်မှတ်ပါ သို့မဟုတ် SSH key ကို စီစဉ်သတ်မှတ်ပါ
- **public IP** ကို မှတ်သားထားပါ (ဥပမာ၊ `203.0.113.10`)

### 1.2 SSH မှတစ်ဆင့် ချိတ်ဆက်ခြင်း

```bash
ssh root@203.0.113.10
```

### 1.3 စနစ်ကို အပ်ဒိတ်လုပ်ခြင်း

```bash
apt update && apt upgrade -y
```

### 1.4 Docker ကို ထည့်သွင်းခြင်း

```bash
# မှီခိုပက်ကေ့ဂျ်များကို ထည့်သွင်းပါ
apt install -y ca-certificates curl gnupg

# တရားဝင် Docker repository ကို ထည့်သွင်းပါ
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | gpg --dearmor -o /etc/apt/keyrings/docker.gpg
chmod a+r /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $ (. /etc/os-release && echo "$VERSION_CODENAME") stable" | tee /etc/apt/sources.list.d/docker.list > /dev/null
apt update
apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
```

### 1.5 nginx ကို ထည့်သွင်းခြင်း

```bash
apt install -y nginx
```

### 1.6 Firewall (UFW) ကို စီစဉ်သတ်မှတ်ခြင်း

```bash
ufw default deny incoming
ufw default allow outgoing
ufw allow 22/tcp    # SSH
ufw allow 80/tcp    # HTTP (လမ်းကြောင်းပြောင်းခြင်း)
ufw allow 443/tcp   # HTTPS
ufw enable
```

> **အကြံပြုချက်**: လုံခြုံရေးအမြင့်ဆုံးရရှိရန် port 80 နှင့် 443 ကို Cloudflare IP များသာ ဝင်ရောက်နိုင်အောင် ကန့်သတ်ပါ။ [အဆင့်မြင့်လုံခြုံရေး](#advanced-security) ကဏ္ဍကို ကြည့်ပါ။

## 2. OmniRoute ကို ထည့်သွင်းခြင်း

### 2.1 Configuration directory ကို ဖန်တီးခြင်း

```bash
mkdir -p /opt/omniroute
```

### 2.2 Environment variables ဖိုင်ကို ဖန်တီးခြင်း

```bash
cat > /opt/omniroute/.env << 'EOF'
# === လုံခြုံရေး ===
JWT_SECRET=CHANGE-TO-A-UNIQUE-64-CHAR-SECRET-KEY
INITIAL_PASSWORD=YourSecurePassword123!
API_KEY_SECRET=REPLACE-WITH-ANOTHER-SECRET-KEY
STORAGE_ENCRYPTION_KEY=REPLACE-WITH-THIRD-SECRET-KEY
STORAGE_ENCRYPTION_KEY_VERSION=v1
MACHINE_ID_SALT=CHANGE-TO-A-UNIQUE-SALT
OMNIROUTE_WS_BRIDGE_SECRET=REPLACE-WITH-WS-BRIDGE-SECRET  # production တွင် လိုအပ်သည်- Codex Responses WS bridge က အသုံးပြုသည်

# === အက်ပ် ===
PORT=20128
NODE_ENV=production
HOSTNAME=0.0.0.0
DATA_DIR=/app/data
APP_LOG_TO_FILE=true
AUTH_COOKIE_SECURE=true
REQUIRE_API_KEY=false

# === URL များ (သင့် domain သို့ ပြောင်းပါ) ===
# အချိန်ဇယားသတ်မှတ်ထားသော လုပ်ဆောင်ချက်များ / self-fetch များအတွက် အတွင်းပိုင်း server-to-server base URL။
BASE_URL=http://127.0.0.1:20128
# OAuth callback များ၊ dashboard link များနှင့် ဖန်တီးထားသော public URL များအတွက် အသုံးပြုသည့် browser-facing URL။
NEXT_PUBLIC_BASE_URL=https://llms.seudominio.com
# ဖန်တီးထားသော public asset URL များအတွက် ရွေးချယ်အသုံးပြုနိုင်သည့် explicit public origin override။
# OMNIROUTE_PUBLIC_BASE_URL=https://llms.seudominio.com

# === Cloud Sync (ရွေးချယ်နိုင်သည်) ===
# CLOUD_URL=https://cloud.omniroute.online
# NEXT_PUBLIC_CLOUD_URL=https://cloud.omniroute.online
EOF
```

> ⚠️ **အရေးကြီးသည်**: တစ်ခုနှင့်တစ်ခုမတူသော secret key များကို ဖန်တီးပါ။ Key တစ်ခုစီအတွက် `openssl rand -hex 32` ကို အသုံးပြုပါ။

### 2.3 Container ကို စတင်ခြင်း

```bash
docker pull diegosouzapw/omniroute:latest

docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --env-file /opt/omniroute/.env \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

### 2.4 လည်ပတ်နေကြောင်း စစ်ဆေးခြင်း

```bash
docker ps | grep omniroute
```

## 3. nginx ကို သတ်မှတ်ပြင်ဆင်ခြင်း (Reverse Proxy)

### 3.1 SSL certificate ထုတ်ပေးခြင်း (Cloudflare Origin)

Cloudflare dashboard တွင် အောက်ပါအတိုင်း လုပ်ဆောင်ပါ။

1. **SSL/TLS → Origin Server** သို့ သွားပါ
2. **Create Certificate** ကို နှိပ်ပါ
3. မူလသတ်မှတ်ချက်များကို ဆက်လက်အသုံးပြုပါ (15 နှစ်၊ \*.yourdomain.com)
4. **Origin Certificate** နှင့် **Private Key** ကို ကူးယူပါ

```bash
mkdir -p /etc/nginx/ssl

# Certificate ကို ထည့်သွင်းပါ
nano /etc/nginx/ssl/origin.crt

# Private key ကို ထည့်သွင်းပါ
nano /etc/nginx/ssl/origin.key

chmod 600 /etc/nginx/ssl/origin.key
```

### 3.2 Nginx သတ်မှတ်ပြင်ဆင်ခြင်း

```bash
cat > /etc/nginx/sites-available/omniroute << 'NGINX'
# မူလ server — IP မှတစ်ဆင့် တိုက်ရိုက်ဝင်ရောက်မှုကို ပိတ်ဆို့သည်
server {
    listen 80 default_server;
    listen [::]:80 default_server;
    listen 443 ssl default_server;
    listen [::]:443 ssl default_server;
    ssl_certificate     /etc/nginx/ssl/origin.crt;
    ssl_certificate_key /etc/nginx/ssl/origin.key;
    server_name _;
    return 444;
}

# OmniRoute — HTTPS
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    server_name llms.yourdomain.com;  # သင့် domain သို့ ပြောင်းလဲပါ

    ssl_certificate     /etc/nginx/ssl/origin.crt;
    ssl_certificate_key /etc/nginx/ssl/origin.key;
    ssl_protocols TLSv1.2 TLSv1.3;

    client_max_body_size 100M;

    location / {
        proxy_pass http://127.0.0.1:20128;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket ပံ့ပိုးမှု
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        # SSE (Server-Sent Events) — AI တုံ့ပြန်မှုများကို streaming လုပ်ခြင်း
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 600s;
        proxy_send_timeout 600s;
    }
}

# HTTP → HTTPS သို့ ပြန်လည်ညွှန်းပို့ခြင်း
server {
    listen 80;
    listen [::]:80;
    server_name llms.yourdomain.com;
    return 301 https://$server_name$request_uri;
}
NGINX
```

Reverse-proxy stream timeout များကို သင့် OmniRoute timeout env vars များနှင့် ကိုက်ညီအောင် ထားပါ။ အကယ်၍
`FETCH_TIMEOUT_MS` / `STREAM_IDLE_TIMEOUT_MS` ကို တိုးမြှင့်ပါက `proxy_read_timeout` / `proxy_send_timeout`
ကိုလည်း တူညီသော သတ်မှတ်ကန့်သတ်ချက်ထက် မြင့်အောင် တိုးမြှင့်ပါ။

OmniRoute သည် OAuth callback များနှင့် ထုတ်ပေးထားသော အများသုံး link များအတွက် browser မှ အသုံးပြုမည့် စံသတ်မှတ်ထားသော origin အဖြစ် `NEXT_PUBLIC_BASE_URL` ကို အသုံးပြုသည်။ အထောက်အထားစိစစ်ပြီးသော dashboard write များသည် same-origin request များနှင့် session-bound CSRF ကာကွယ်မှုကို အသုံးပြုသောကြောင့် static public base URL မလိုအပ်ပါ။ အထက်ပါ `X-Forwarded-*` header များသည် routing metadata အဖြစ် အသုံးဝင်ဆဲဖြစ်သော်လည်း OAuth သို့မဟုတ် ထုတ်ပေးထားသော browser link များအတွက် လိုအပ်သည့်အခါ အများသုံး URL ကို တိတိကျကျ သတ်မှတ်ခြင်းအား အစားမထိုးနိုင်ပါ။ Client များက OmniRoute ကို တိုက်ရိုက်မဝင်ရောက်နိုင်ဘဲ သင့် proxy က ဝင်လာသော forwarded header များကို ဖယ်ရှားပြီး ပြန်လည်တည်ဆောက်ပေးသည့်အခါမှသာ `OMNIROUTE_TRUST_PROXY` ကို ဖွင့်ပါ။

## Memory နည်းသော / VPS အသေးစားအတွက် အကောင်းဆုံးဖြစ်အောင် ချိန်ညှိခြင်း

VPS instance အသေးစားများ (RAM 1 GB သို့မဟုတ် ထို့ထက်နည်းသော) ပေါ်တွင် ဖြန့်ချိအသုံးပြုရန်အတွက်-

- **နောက်ခံဝန်ဆောင်မှုများကို ပိတ်ပါ** — scheduler၊ MCP server နှင့် အချိန်မှန် ထိန်းသိမ်းရေးလုပ်ငန်းများကို ကျော်ရန် `OMNIROUTE_DISABLE_BACKGROUND_SERVICES=1` ဟု သတ်မှတ်ပါ။ `docs/reference/ENVIRONMENT.md` ကို ကြည့်ပါ။
- **SQLite WAL mode ကို အသုံးပြုပါ** — ပုံသေအားဖြင့် ဖွင့်ထားပြီး တစ်ပြိုင်နက်ဖတ်ရှုမှုများအတွင်း အမြင့်ဆုံး memory အသုံးပြုမှုကို လျှော့ချပေးသည်။
- **V8 heap ကို ကန့်သတ်ပါ** — runtime က VM ထက် ပိုကြီးသော အများဆုံးကန့်သတ်ချက်ကို ချိန်ညှိမသွားစေရန် `OMNIROUTE_MEMORY_MB` (ဥပမာ `512`) ကို သတ်မှတ်ပါ။ `docs/reference/ENVIRONMENT.md` ကို ကြည့်ပါ။
- **အလေးချိန်မြင့် request လက်ခံမှုသည် heap ကန့်သတ်ချက်နှင့်အညီ အလိုအလျောက် တိုးလျှော့သည်** -- အထက်တွင် `OMNIROUTE_MEMORY_MB` ကို သတ်မှတ်ပြီးသည်နှင့် ingest byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) သည် ထိုကန့်သတ်ချက်တစ်ခုတည်းမှ အလိုအလျောက် တွက်ချက်သတ်မှတ်သည်။ ထို့ကြောင့် memory ကန့်သတ်ထားသော VM သည် အပိုချိန်ညှိမှုမလိုဘဲ တစ်ပြိုင်နက် request budget ပိုနည်းစွာ ရရှိပြီး၊ ပိုလျှံသော request များသည် memory အတွက် အပြိုင်အဆိုင် အသုံးပြုမည့်အစား ပြန်လည်ကြိုးစားနိုင်သော `503` နှင့် `Retry-After` ကို ရရှိမည်ဖြစ်သည်။ ၎င်းအပြင် တိကျသော အများဆုံးကန့်သတ်ချက်တစ်ခု လိုအပ်မှသာ ယခင် `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` request အရေအတွက်ကန့်သတ်ချက်ကို သတ်မှတ်ပါ။
- **VPS ပေါ်တွင် `next build` ပြုလုပ်ခြင်းကို ရှောင်ကြဉ်ပါ** — local စက်တွင် build ပြုလုပ်ပြီး standalone output (`.next/standalone/`) ကို ဖြန့်ချိပါ။
- **`top` / `free -m` ဖြင့် စောင့်ကြည့်ပါ** — OmniRoute သည် ပုံမှန်အားဖြင့် 1 GB VM ပေါ်တွင် အလုပ်မလုပ်ဘဲ စောင့်နေချိန်၌ RSS 200-400 MB ခန့် အသုံးပြုသည်။
