> **ဤစာတမ်းက ဘာလဲ။** OmniRoute ၏ quality-gate စနစ်ကို လုပ်ငန်းနယ်ပယ်၏ အကောင်းဆုံးလုပ်ထုံးလုပ်နည်းများနှင့်
> နှိုင်းယှဉ်ထားသော အကဲဖြတ်သုံးသပ်ချက်တစ်ခုဖြစ်ပြီး၊ **ထို့အပြင်** quality checkpoint အားလုံး၏ ပြည့်စုံသော
> စာရင်းနှင့် တူညီသောစနစ်ကို မည်သည့် project တွင်မဆို အသုံးချနိုင်ရန် **tool နှင့်မသက်ဆိုင်သော ပုံတူပွားအစီအစဉ်**
> တစ်ခုလည်း ပါဝင်သည်။ မှတ်ဉာဏ်အပေါ် အခြေခံထားခြင်းမဟုတ်ဘဲ အမှန်တကယ် repository အခြေအနေမှ 2026-06-16 တွင် ထုတ်လုပ်ထားသည်။
>
> စံနှိုင်းယှဉ်ချက်များ: OWASP DSOMM · OpenSSF Scorecard · SLSA · SonarQube "Clean as You Code" ·
> Quality-Ratchet pattern · DORA 2024 · OWASP LLM Top 10 (2025) · mutation-testing အကောင်းဆုံးလုပ်ထုံးလုပ်နည်းများ။
>

> policy ကွာခြားချက်၊ blocking နှင့် advisory ကွာခြားချက်) ကို

## အပိုင်း 1 — အဆုံးအဖြတ်နှင့် ရင့်ကျက်မှုအဆင့် သတ်မှတ်ချက်

**ခြုံငုံအဆင့်: A− / "အဆင့်မြင့်"။ Project များ၏ ထိပ်တန်း ~5–10% အတွင်း။** ဤစနစ်သည် လုပ်ငန်းနယ်ပယ်က
တိကျစွာ အမည်ပေးထားသည့် pattern အများအပြားကို သီးခြားလွတ်လပ်စွာ အကောင်အထည်ဖော်ထားသည် — ယင်းသည်
လိုက်လျောညီထွေမှုအတွက် အခိုင်မာဆုံးအချက်ပြမှုဖြစ်သည် (ကျွန်ုပ်တို့သည် checklist တစ်ခုကို ကူးယူခဲ့ခြင်းမဟုတ်ဘဲ မှန်ကန်သောလုပ်ထုံးလုပ်နည်းများဆီသို့ တူညီစွာ ရောက်ရှိခဲ့ခြင်းဖြစ်သည်)။

| ကိုးကားမူဘောင်                                 | ကျွန်ုပ်တို့၏ လက်ရှိအခြေအနေ                                                                                                                                                                                                                                                                    | အဆင့်                            |

## အပိုင်း 2 — အရေးပါသော အကဲဖြတ်ချက် (အားသာချက်များ + ပွင့်လင်းရိုးသားသော အားနည်းချက်များ)

### အားသာချက်များ (ပျမ်းမျှထက် ပိုကောင်းသည့်အရာများ)

1. **မက်ထရစ်မျိုးစုံသုံး ratchet အင်ဂျင်။** စနစ်၏ အဓိကဗဟိုချက်ဖြစ်သည်။ `quality-baseline.json` တွင် မက်ထရစ် 24 ခုရှိသည်
   - သီးသန့် baseline 4 ခုရှိပြီး တစ်ခုစီတွင် ဦးတည်ချက် (`up`/`down`), သည်းခံနိုင်မှု (`eps`), ဖြေလျှော့ခွင့်
     (`tightenSlack`) နှင့် `dedicatedGate` flag ပါရှိသည်။ ပြင်ဆင်ပြီးသောအရာများသည် **ဆက်လက်**
     ပြင်ဆင်ပြီးသားအဖြစ် တည်ရှိနေသည် — ၎င်းသည် codebase ယိုယွင်းပျက်စီးမှုကို ကာကွယ်ပေးသည့် ဖြေဆေးဖြစ်သည်။
2. **Supply-chain အတွက် အလွှာစုံကာကွယ်ရေး။** SAST (CodeQL/Sonar) + လျှို့ဝှက်ချက်များ (`useDefault` ဖြင့် gitleaks)
   - SCA (osv/npm-audit/Trivy/Dependabot) + လိုင်စင်များ + lockfile + SBOM + SLSA
     provenance + Scorecard + workflow ခိုင်မာရေး (zizmor)။ ဤမျှပြည့်စုံသော stack ရှိသည့် codebase များမှာ အနည်းငယ်သာရှိသည်။
3. **Goodhart's Law ကို တန်ပြန်သည့် ဖြေဆေးများ။** Coverage ကို ပစ်မှတ်တစ်ခုအဖြစ် သတ်မှတ်ခြင်းသည် ရိုးရာ anti-pattern တစ်ခုဖြစ်သည်
   ("တိုင်းတာချက်ကို ပစ်မှတ်အဖြစ် သတ်မှတ်လိုက်သောအခါ ၎င်းသည် ကောင်းမွန်သောတိုင်းတာချက် မဟုတ်တော့ပါ")။ ကျွန်ုပ်တို့တွင်
   ဟန်ချက်ညီစေမည့်အရာများ ရှိသည်- **mutation testing** (test က line ကို run ရုံသာမဟုတ်ဘဲ bug ကို အမှန်တကယ်
   ဖမ်းနိုင်ခြင်းရှိမရှိ တိုင်းတာသည်), **`check-test-masking`** (pass ရရန် assert များကို အားနည်းစေခြင်းကို ပိတ်ပင်သည်),
   **module တစ်ခုချင်းစီအလိုက် coverage အနိမ့်ဆုံးသတ်မှတ်ချက်များ** (လွယ်ကူသည့်အပိုင်းများသာမဟုတ်ဘဲ HIGH-risk code ကိုပါ test လုပ်ရန် တွန်းအားပေးသည်) နှင့်
   **`check-pr-evidence`** (Hard Rule #18)။
4. **အချက်အလက်မရှိဘဲ ဖန်တီးပြောဆိုမှုကို တားဆီးသည့် / တစ်သမတ်တည်းဖြစ်မှု စစ်ဆေးရေး gate များ။** ရှားပါးပြီး တန်ဖိုးရှိသော အမျိုးအစားတစ်ခုဖြစ်သည်- `check-known-symbols`,
   `check-fetch-targets`, `check-openapi-routes`, `check-docs-symbols` တို့သည် docs, specs နှင့်
   string dispatch များက လက်ရှိအသုံးပြုနိုင်သေးသော symbol များကို ညွှန်းဆိုကြောင်း သေချာစေသည်။ lint/test မဖမ်းနိုင်သည့် "ယိုယွင်းပျက်စီးမှု" ကို ဖမ်းယူပေးသည်။
5. **Advisory→blocking ဘဝစက်ဝန်း။** Gate အသစ်များကို advisory အဖြစ် စတင်ထည့်သွင်းသည် (ရင့်ကျက်လာသည့်ကာလအတွင်း
   merge များကို မပိတ်ပင်ပါ)၊ ထို့နောက် cycle အဆုံးတွင် blocking အဖြစ် ပြောင်းလဲသည်။ အမြင့်ဆုံးစံနှုန်းကို မဆုံးရှုံးစေဘဲ အတားအဆီးများကို လျှော့ချပေးသည်။
6. **Infra မရှိသည့်အခါ ချောမွေ့စွာ skip လုပ်ခြင်း။** Binary/network ပျက်ကွက်လျှင် scanner များ (`--ratchet`) သည်
   `exit 0` ဖြင့် ထွက်သည် — infra မရှိခြင်းကြောင့် တရားဝင် PR တစ်ခုကို မည်သည့်အခါမျှ မပိတ်ပင်ပါ။ ရင့်ကျက်သော engineering ဖြစ်သည်။
7. **စည်းမျဉ်းအဖြစ် ပုံဖော်ထားသော ယဉ်ကျေးမှု။** Hard Rules + `trust-but-verify` + stale-allowlist + evidence-gate
   တို့က စည်းကမ်းလိုက်နာမှုကို အလိုအလျောက်စစ်ဆေးအတည်ပြုမှုအဖြစ် ပြောင်းလဲပေးသည်။

### ပွင့်လင်းရိုးသားသော အားနည်းချက်များ (အမှန်တကယ်ရှိနေသော လစ်ဟာချက်များ)

1. **🔴 Fast-gates ခွဲထားမှုတွင် ဖွဲ့စည်းပုံဆိုင်ရာ လစ်ဟာချက်တစ်ခု ရှိနေဆဲဖြစ်သည်။** `quality.yml` (PR→`release/**`)
   သည် ယခုအခါ code PR များအတွက် typecheck, မြန်ဆန်ပြီး အဖြေတိကျသည့် test များနှင့် advisory production build တစ်ခုကို
   run သော်လည်း `ci.yml` မှ release-PR စစ်ဆေးမှုအားလုံး (coverage ratchet များ,
   package artifact, integration, E2E, SonarQube) ကို မ run သေးပါ။ အကြောင်းရင်း (မြန်နှုန်း) သည် သင့်လျော်သော်လည်း gate ကို
   merge ဖြစ်ပေါ်သည့်နေရာတွင် ထားသင့်သည် (shift-left)။ **ပြင်ဆင်ရန် ကျန်ရှိနေသေးသည့် အကြီးမားဆုံး ဖွဲ့စည်းပုံဆိုင်ရာ ပြဿနာဖြစ်သည်။**
2. **🟠 Gate များ အလွန်များပြားလာခြင်း/ပင်ပန်းနွမ်းနယ်မှု အန္တရာယ်။** Gate ~46 ခု + job 25 ခုသည် အလွန်များပြားသည်။ Sonar ကိုယ်တိုင်က
   သတိပေးထားသည်မှာ- သတ်မှတ်ချက်များ အလွန်များလွန်းခြင်းကြောင့် "gate fatigue" နှင့် ဦးစားပေးမှုဆိုင်ရာ အငြင်းပွားမှုများ ဖြစ်ပေါ်နိုင်ပြီး gate တစ်ခုကို
   လျစ်လျူရှုမိနိုင်သည့် အန္တရာယ်ရှိသည်။ လေးလံသော gate များက lead-time ကို ပိုမိုကြာမြင့်စေကြောင်း DORA က သတိပေးထားသည်။ ကျွန်ုပ်တို့သည် advisory tier များနှင့်
   absolute မဟုတ်သော ratchet များဖြင့် လျော့ပါးစေသော်လည်း **gate တစ်ခုချင်းစီအတွက် အချိန်မှန် ROI ပြန်လည်သုံးသပ်မှု** မရှိသေးပါ (doc-sync အတွက်
   micro-gate အချို့ကို ပေါင်းစည်းနိုင်သည်)။
3. **🟠 Mutation score သည် ratchet မဖြစ်သေးပါ။** Coverage ကို လှည့်စားခြင်းအား တန်ပြန်ရန် အားအကောင်းဆုံး ဖြေဆေးသည်
   **advisory** ဖြစ်နေဆဲဖြစ်သည်။ ၎င်းသည် ပြီးစီးရန်ကျန်ရှိသော အရာများအနက် တန်ဖိုးအမြင့်ဆုံးဖြစ်သည် (ထို့ပြင် 90% တည်ဆောက်ပြီးဖြစ်သည်)။
4. **🟡 သင့်လျော်သော scope ဖြင့် block လုပ်သင့်သည့် advisory များ။** `osv` (vulnCount) နှင့် `oasdiff` တို့သည်
   baseline များကို ပုံသေသတ်မှတ်ထားသော်လည်း advisory ဖြစ်နေဆဲဖြစ်သည်။ osv-advisory သည် အဓိပ္ပာယ်ရှိသည် (dependency အဟောင်းတစ်ခုတွင် CVE အသစ်ပေါ်လာပါက
   မသက်ဆိုင်သော PR တစ်ခုကို ပိတ်ပင်သွားမည်) — သို့သော် အလယ်အလတ်နည်းလမ်းတစ်ခု ရှိသည် (Trivy နှင့် လုပ်ဆောင်ခဲ့သကဲ့သို့
   CRITICAL+fixable ကိုသာ ပိတ်ပင်ရန်)။ oasdiff ကို advisory အဖြစ်ထားခြင်းကြောင့် contract ကို ချိုးဖောက်သော ပြောင်းလဲမှုတစ်ခု pass နိုင်သည်။
5. **🟡 Runtime security ကို ညပိုင်းတွင်သာ စစ်ဆေးသည်။** schemathesis/garak/promptfoo/chaos/k6 တို့ကို ညဘက်တွင် run သည်။
   ဤဆုံးဖြတ်ချက်သည် မှန်ကန်သည် (နှေးကွေးပြီး live server တစ်ခု လိုအပ်သည်)၊ သို့သော် PR တစ်ခုသည် နောက်တစ်ညရောက်မှသာ
   ဖမ်းမိမည့် injection-guard regression တစ်ခုကို ထည့်သွင်းနိုင်သည်။
6. **🟡 `main` ပေါ်ရှိ branch-protection သည် OFF ဖြစ်နေသည်။** `BRANCH_LOCK_TOKEN` သည် _release_ branch များကို lock လုပ်သော်လည်း
   `main` ကိုယ်တိုင်မှာ ကာကွယ်မှုမရှိပါ။ Scorecard/DSOMM အကဲဖြတ်ချက် ကျဆင်းစေသည်။ Owner က လုပ်ဆောင်ရန် လိုအပ်သည်။
7. **🟡 CodeQL default-setup; semgrep ကို စည်းမျဉ်းအဖြစ် မသတ်မှတ်ထားပါ။** default-setup သည် အလုပ်လုပ်သည် (alert 0 ခု)၊ သို့သော်
   commit လုပ်ထားသည့် `codeql.yml` က ပိုမိုထိန်းချုပ်နိုင်စေသည်။ semgrep သည် ပြင်ပ cloud platform မှတစ်ဆင့် run ပြီး
   repo အတွင်း version ထိန်းချုပ်ထားခြင်းမရှိပါ။

## အပိုင်း 3 — အရည်အသွေး စစ်ဆေးရေးဂိတ်များ၏ အပြည့်အစုံစာရင်း (နေရာမရွေး အသုံးပြုနိုင်သော)

အောက်ပါ အမျိုးအစား 12 ခုသည် ပြန်လည်အသုံးပြုနိုင်သော ပုံစံဖြင့် ဖော်ပြထားသည့် "အရည်အသွေးစနစ်" ဖြစ်သည်။ တစ်ခုချင်းစီတွင်
**ရည်ရွယ်ချက်** (ကာကွယ်ရမည့်အရာ)၊ **ကျွန်ုပ်တို့အသုံးပြုသည့် ကိရိယာများ** နှင့် မည်သည့်နည်းပညာစုစည်းမှုတွင်မဆို ပြန်လည်အကောင်အထည်ဖော်နိုင်ရန် **သီးခြားကိရိယာအပေါ် မမူတည်သော အလားတူနည်းလမ်း** တို့ကို ဖော်ပြထားသည်။

### 1. စတိုင်နှင့် ဖော်မတ်ချခြင်း (တစ်သမတ်တည်း ရလဒ်ထွက်ပြီး မြန်ဆန်သော)

- **OmniRoute:** lint-staged မှတစ်ဆင့် Prettier + ESLint (pre-commit)၊ 2-spaces/double-quotes/100col။
- **ယေဘုယျ:** အလိုအလျောက်ပြင်ဆင်နိုင်သော formatter တစ်ခု + linter တစ်ခုကို staged files များအတွက် pre-commit တွင် လည်ပတ်စေခြင်း။

### 2. အမျိုးအစားများ

- **OmniRoute:** `typecheck:core` (မအောင်မြင်ပါက တားဆီးခြင်း) + `typecheck:noimplicit:core` (အကြံပြုချက်အဖြစ်) + `type-coverage` ratchet 92.17% + ဖိုင်တစ်ခုချင်းစီအလိုက် any-budget။
- **ယေဘုယျ:** CI တွင် တင်းကျပ်သော typecheck + နောက်ပြန်မဆုတ်စေရန် သတ်မှတ်ထားသော type-coverage မက်ထရစ် + ဖိုင်တစ်ခုချင်းစီအလိုက် `any`/escape-hatch ဘတ်ဂျက်။

### 3. စမ်းသပ်မှုများ (ပြင်းအား)

- **OmniRoute:** ထပ်မနေသော runner 2 ခု (Node native + vitest)၊ shard 8 ခု၊ global coverage 60/60/60/60 + ratchet ~76% + **အရေးကြီး module များအတွက် module တစ်ခုချင်းစီအလိုက် အနိမ့်ဆုံးသတ်မှတ်ချက် 8 ခု** + ညစဉ် property tests + ညစဉ် **mutation testing**။
- **ယေဘုယျ:** test runner များ + **အတိအကျသတ်မှတ်ထားသော** coverage အနိမ့်ဆုံးတန်ဖိုး (သုညဖြစ်ခြင်းကို ကာကွယ်ရန်) + coverage **ratchet** (နောက်ပြန်ဆုတ်ခြင်းကို ကာကွယ်ရန်) + **အန္တရာယ်မြင့် code အတွက် module တစ်ခုချင်းစီအလိုက် အနိမ့်ဆုံးသတ်မှတ်ချက်များ** (Goodhart ပြဿနာကို ကာကွယ်ရန်) + pure logic အတွက် property-based စမ်းသပ်မှု + စမ်းသပ်မှုအရည်အသွေး၏ အမှန်တကယ်တိုင်းတာချက်အဖြစ် ညစဉ် **mutation testing**။

### 4. စမ်းသပ်မှု မူဝါဒ (စနစ်ကို လှည့်စားခြင်းမှ ကာကွယ်ရန်)

- **OmniRoute:** `pr-test-policy` (production code တွင် test တစ်ခု လိုအပ်သည်)၊ `check-test-masking` (အားပျော့အောင်လုပ်ထားသော assert များကို ပိတ်ပင်သည်)၊ `pr-evidence` (အောင်မြင်ကြောင်း အခိုင်အမာဆိုပါက အထောက်အထား block လိုအပ်သည်)၊ `test-discovery` (test တိုင်းကို runner တစ်ခုက စုဆောင်းထားကြောင်း သေချာစေသည်)။
- **ယေဘုယျ:** "code အသစ် ⇒ test အသစ်" gate + ဖယ်ရှားထားသော assert/အမြဲမှန်နေသော စစ်ဆေးချက် detector + အထောက်အထားလိုအပ်ချက် (TDD သို့မဟုတ် လက်ရှိအခြေအနေကို ထင်ဟပ်သည့် test) + မည်သည့် test မျှ glob များ၏ ပြင်ပတွင် ကျန်ရစ်မနေကြောင်း အာမခံချက်။

### 5. ရှုပ်ထွေးမှုနှင့် code ကျန်းမာရေး (ratchet များ)

- **OmniRoute:** ESLint-warnings (3769↓)၊ jscpd duplication (5.72%↓)၊ cyclomatic+max-lines complexity (1800↓)၊ cognitive complexity sonarjs (753↓)၊ dead-code/unused-exports knip (339↓)၊ ဖိုင်တစ်ခုချင်းစီအလိုက် file-size (လက်ရှိတန်ဖိုးတွင် ထိန်းထားပြီး လျှော့ချမှုသာ ခွင့်ပြုသည်)၊ circular-deps (စိတ်ကြိုက် Tarjan၊ မအောင်မြင်ပါက တားဆီးခြင်း)။
- **ယေဘုယျ:** ကျန်းမာရေးမက်ထရစ်တိုင်းကို ratchet ပြုလုပ်ခြင်း (warnings၊ duplication၊ cyclomatic **နှင့်** cognitive complexity၊ dead code၊ file size၊ import cycles)။ ဦးတည်ချက်သည် အမြဲတမ်း "နောက်ပြန်မဆုတ်ရန်" ဖြစ်သည်။

### 6. Static security (SAST + secrets)

- **OmniRoute:** CodeQL (ratchet alerts = 0)၊ gitleaks (`[extend] useDefault=true` — အလွန်အရေးကြီးသည်!)၊ SonarQube၊ စိတ်ကြိုက် security rules (public-creds၊ error-helper၊ route-guard-membership၊ route-validation)။
- **ယေဘုယျ:** alert ratchet ပါသော SAST (CodeQL/Sonar/semgrep) + **မူလ ruleset ကို အမွေဆက်ခံအသုံးပြုသည့်** secrets scanner (မူလသတ်မှတ်ချက်ကို override လုပ်သော စိတ်ကြိုက် config သည် စစ်ဆေးမှုကွက်လပ် ဖြစ်စေသည်) + project အလိုက် သီးခြား Hard Rule security gates။

### 7. Supply-chain (dependencies)

- **OmniRoute:** osv-scanner + npm-audit + Trivy + Dependabot (SCA)၊ license-checker (SPDX allowlist)၊ lockfile-lint (HTTPS+sha512+registry)၊ `check-deps` anti-slopsquatting (allowlist + age ≥72h)။
- **ယေဘုယျ:** ရင်းမြစ်မျိုးစုံမှ SCA + license allowlist + lockfile integrity စစ်ဆေးမှု + အသက်နှင့် typosquatting စစ်ဆေးမှုပါသော dependency allowlist + update များကို အုပ်စုဖွဲ့ဆောင်ရွက်သည့် bot။

### 8. Supply-chain (build နှင့် release)

- **OmniRoute:** SBOM (CycloneDX + syft)၊ SLSA provenance (`--provenance`)၊ OpenSSF Scorecard (အပတ်စဉ်)၊ workflow hardening (zizmor: artipacked→`persist-credentials:false`၊ cache-poisoning၊ token-permissions)။
- **ယေဘုယျ:** publish လုပ်သည့်အခါ SBOM ထုတ်လုပ်ခြင်း + လက်မှတ်ထိုးထားသော provenance (SLSA L2+) + အချိန်ဇယားဖြင့် လည်ပတ်သော Scorecard + workflow အားလုံးကို လုံခြုံအောင် တင်းကျပ်ခြင်း (အနည်းဆုံးလိုအပ်သည့် အခွင့်အရေးသာရှိသော token များ၊ push မလုပ်မည့် checkout တွင် credentials များကို မသိမ်းဆည်းခြင်း၊ actions များကို SHA ဖြင့် pin လုပ်ခြင်း)။

### 9. Contracts နှင့် API

- **OmniRoute:** oasdiff (breaking-change OpenAPI)၊ schemathesis (ညစဉ် contract fuzz)၊ openapi-coverage (မှတ်တမ်းတင်ထားသော route ရာခိုင်နှုန်း၊ ratchet 38.3%)၊ openapi-security-tiers (spec နှင့် route-guard နှိုင်းယှဉ်မှု)။
- **ယေဘုယျ:** breaking-change contract diff (oasdiff/buf) + spec ကို အခြေခံသော property-based fuzz (schemathesis) + နောက်ပြန်မဆုတ်စေရန် သတ်မှတ်ထားသော documentation coverage + spec↔code တစ်သမတ်တည်းဖြစ်မှု။

### 10. Docs နှင့် i18n (ဆွေးမြေ့ပျက်စီးမှုမှ ကာကွယ်ရန်)

- **OmniRoute:** docs-sync (ပုံတူထားသော version များ)၊ docs-counts-sync (docs နှင့် code ရှိ ကိန်းဂဏန်းများ)၊ env-doc-sync၊ doc-links၊ fabricated-docs၊ cli-i18n၊ i18n-ui-coverage (`--threshold=65` + ratchet 80.1%)။
- **ယေဘုယျ:** docs နှင့် code အကြား version/count/env-vars များကို တစ်ပြေးညီဖြစ်အောင် sync လုပ်ခြင်း (ယုံကြည်ရုံမဟုတ်ဘဲ gate ဖြင့် စစ်ဆေးခြင်း) + internal links များကို အတည်ပြုစစ်ဆေးခြင်း + နောက်ပြန်မဆုတ်စေရန် သတ်မှတ်ထားသော i18n coverage။

### 11. ဖန်တီးထင်ယောင်မှုကို ကာကွယ်ခြင်း / တစ်သမတ်တည်းဖြစ်မှု (တွေ့ရခဲသော အမျိုးအစား)

- **OmniRoute:** known-symbols (string dispatch ⇒ အမှန်တကယ်တည်ရှိသော symbol)၊ provider-consistency၊ fetch-targets (client fetch ⇒ အမှန်တကယ်တည်ရှိသော route)၊ docs-symbols၊ db-rules (Hard Rules #2/#5)၊ migration-numbering။
- **ယေဘုယျ:** "ပုံတူဖြစ်နေသော source of truth" တိုင်းအတွက် (registry၊ string dispatch၊ layer များအကြား အပြန်အလှန်ရည်ညွှန်းချက်များ) နှစ်ဖက်လုံး ကိုက်ညီကြောင်း သက်သေပြသည့် gate တစ်ခု ထားရှိခြင်း။ ၎င်းသည် typecheck/test တို့ မဖမ်းမိသော ဆွေးမြေ့ပျက်စီးမှုများကို ဖမ်းယူနိုင်သည်။

### 12. ကြံ့ခိုင်ခံနိုင်ရည်နှင့် domain (product အလိုက် သီးခြား)

- **OmniRoute:** chaos (fault-injection)၊ heap-growth (leak)၊ k6 (soak)၊ promptfoo+garak (LLM red-team OWASP LLM Top 10)၊ resilience law 3 ခု (circuit-breaker/cooldown/lockout)။
- **ယေဘုယျ:** **သင့်** domain ၏ ပျက်ကွက်နိုင်သည့် ပုံစံများကို ဖော်ထုတ်ပြီး တစ်ခုချင်းစီအတွက် gate တစ်ခု (ညစဉ်သာ လည်ပတ်သည်ဖြစ်စေ) ထားရှိပါ။ AI app များအတွက် injection red-team ပြုလုပ်ပါ။ Distributed system များအတွက် chaos + leak + soak ပြုလုပ်ပါ။

## အပိုင်း 4 — မည်သည့် Project အတွက်မဆို ပြန်လည်အသုံးချနိုင်သော အစီအစဉ်

**အဆင့်များ** ခွဲ၍ တည်ဆောက်ပါ။ အဆင့်တစ်ခုစီသည် သီးခြားတန်ဖိုးတစ်ခု ပေးနိုင်ရမည်။ အမျိုးအစား 12 ခုလုံးကို တစ်ပြိုင်နက် မကြိုးစားပါနှင့် —
ထိုသို့လုပ်ခြင်းသည် အပိုင်း 2 တွင် သတိပေးထားသော gate ပင်ပန်းနွမ်းနယ်မှုကို အတိအကျ ဖြစ်စေသည်။ Gate အသစ်တိုင်းသည် အစတွင် **အကြံပြုအဆင့်** ဖြင့် စတင်ပြီး
တည်ငြိမ်လာသောအခါ **ပိတ်ဆို့တားဆီးသည့်အဆင့်** သို့ ပြောင်းရမည်။

### ပြန်လည်အသုံးပြုနိုင်သော အဓိကအစိတ်အပိုင်း: "ratchet gate တစ်ခု၏ ဖွဲ့စည်းပုံ"

စနစ်တစ်ခုလုံးသည် ဤ file 3 ခုပါ pattern ကို ဗဟိုပြုထားသည်။ ၎င်းကို ဦးစွာ ကူးယူပါ:

1. **`baseline.json`** — ပြောင်းလဲမထားသည့် metric တန်ဖိုး + `direction` (`up`/`down`) + `eps` (မတည်ငြိမ်မှု ကာကွယ်ရေး) + `tightenSlack` + `dedicatedGate`။
2. **`collect-metrics.<ext>`** — tool ကို run ပြီး ကိန်းဂဏန်းကို ထုတ်ယူကာ `metrics.json` တွင် ရေးသားသည်။
3. **`check-ratchet.<ext>`** — `metrics.json` နှင့် `baseline.json` ကို နှိုင်းယှဉ်သည်။ `eps` ထက်ကျော်၍ နောက်ဆုတ်သွားမှသာ `exit 1` လုပ်သည်။ tool/infra မရှိခဲ့ပါက `exit 0` ဖြင့် ချောမွေ့စွာ ကျော်သွားသည်။ `--require-tighten` ပါလျှင် baseline ကို update မလုပ်ဘဲ **တိုးတက်လာခဲ့ပါက** `exit 1` လုပ်သည် (ရရှိသော တိုးတက်မှုကို ထိန်းသိမ်းထားသည်)။

ဤအရာကို ပြင်ဆင်ပြီးသည်နှင့် metric အသစ် **တိုင်း** (coverage၊ complexity၊ warnings၊ SAST alerts၊ bundle size၊ mutation score…) သည် baseline ထဲရှိ စာကြောင်းတစ်ကြောင်းမျှသာ ဖြစ်သည်။

### အဆင့် 0 — အခြေခံအုတ်မြစ် (အပတ် 1)

CI ရှိရမည်။ formatter + linter + typecheck + test runner 1 ခု + **အကြွင်းမဲ့** coverage အနိမ့်ဆုံးသတ်မှတ်ချက်
(ဥပမာ၊ 60%) ပါဝင်ရမည်။ Pre-commit တွင် မြန်ဆန်ပြီး အလိုအလျောက်ပြင်ဆင်နိုင်သော စစ်ဆေးမှုများကို run ရမည်။ _ရလဒ်: မည်သည့် PR ကမျှ အခြေခံစနစ်များကို မပျက်စီးစေပါ။_

### အဆင့် 1 — Ratchet engine (အပတ် 2) — **အရာအားလုံး၏ အခြေခံအုတ်မြစ်**

အထက်ပါ file 3 ခုကို အကောင်အထည်ဖော်ပါ။ warnings၊ coverage၊ complexity၊ duplication၊
dead code၊ file size တို့အတွက် baseline များကို သတ်မှတ်ထိန်းသိမ်းပါ။ _ရလဒ်: codebase သည် ဤနေရာမှစ၍ တိုးတက်ရန်သာ ဖြစ်နိုင်သည်။_

### အဆင့် 2 — Static စစ်ဆေးမှု အတိမ်အနက် (အပတ် 3)

Alert ratchet ပါသော SAST (CodeQL/Sonar/semgrep)၊ secrets scanner (**မူလ ruleset ကို ဆက်ခံအသုံးပြုပါ**)၊
SCA (osv/Dependabot) + license allowlist + lockfile-lint။ _ရလဒ်: သိရှိထားသော အားနည်းချက်များနှင့်
ပေါက်ကြားသွားသော secret များကို ဖြတ်သန်းခွင့်မပြုပါ။_

### အဆင့် 3 — Build supply-chain (အပတ် 4)

Publish လုပ်ချိန်တွင် SBOM + လက်မှတ်ထိုးထားသော provenance (SLSA L2) + အချိန်ဇယားဖြင့် run သော Scorecard + workflow အားကောင်းစေခြင်း
(zizmor: အနည်းဆုံး token များ၊ သိမ်းဆည်းထားသော credential မရှိခြင်း၊ version သတ်မှတ်ထားသော action များ)။ _ရလဒ်: ခြေရာခံနိုင်ပြီး
လက်ဆော့ပြင်ဆင်၍မရသော release များ။_

### အဆင့် 4 — Test အင်အားမြှင့်တင်ခြင်း (အပတ် 5–6)

အသုံးဝင်ပါက 2nd runner ထည့်ပါ။ **အရေးကြီး module များအတွက် module တစ်ခုချင်းစီ၏ coverage အနိမ့်ဆုံးသတ်မှတ်ချက်များ** (anti-Goodhart) ထည့်ပါ။
Pure logic အတွက် property-based testing လုပ်ပါ။ **ညစဉ် mutation testing** လုပ်ပါ → ပထမ score ရလာသောအခါ
`mutationScore` ကို ratchet တစ်ခု ပြုလုပ်ပါ။ _ရလဒ်: coverage သည် အပြင်ပန်းကြည့်ကောင်းရန်အတွက်သာ အသုံးပြုသော metric မဖြစ်တော့ဘဲ test များက bug များကို အမှန်တကယ် ဖမ်းမိကြောင်း သက်သေပြနိုင်သည်။_

### အဆင့် 5 — Contract နှင့် dynamic စစ်ဆေးမှု (အပတ် 7)

Public API ရှိပါက: oasdiff (breaking-change၊ **ပိတ်ဆို့တားဆီးသည့်အဆင့်**) + schemathesis (ညစဉ် fuzz testing)။
Domain နှင့် သင့်လျော်သလို DAST/red-team ကို ညစဉ် run ပါ။ _ရလဒ်: contract များသည် သတိမပြုမိဘဲ မပျက်စီးနိုင်ပါ။_

### အဆင့် 6 — Hallucination ကာကွယ်ရေးနှင့် domain စစ်ဆေးမှု (အပတ် 8)

Project ထဲရှိ "ထပ်နေသော အမှန်တရား" တစ်ခုစီအတွက် consistency gate တစ်ခု ထားပါ။ Domain အလိုက် failure-mode
gate များ ထားပါ (AI အတွက်: injection red-team)။ _ရလဒ်: ဖွဲ့စည်းပုံ ယိုယွင်းမှုနှင့် domain ဆိုင်ရာ ပျက်ကွက်မှုများအတွက် အကာအကွယ်စနစ် ရှိလာသည်။_

### အဆင့် 7 — အုပ်ချုပ်မှု (ဆက်လက်လုပ်ဆောင်ရန်)

- Gate အသစ်တိုင်းအတွက် အကြံပြုအဆင့်→ပိတ်ဆို့တားဆီးသည့်အဆင့် စက်ဝန်းကို အသုံးပြုပါ။
- `stale-allowlist`: ခြွင်းချက်တားဆီးမှုတိုင်းတွင် အကြောင်းပြချက် + issue ပါရမည်။ အသုံးမဝင်တော့သော ခြွင်းချက်တားဆီးမှုကို ဖမ်းမိရမည်။
- `evidence-gate`: PR တစ်ခုရှိ အောင်မြင်မှုဆိုင်ရာ အဆိုပြုချက်တိုင်းတွင် သက်သေ (test သို့မဟုတ် living test) လိုအပ်သည်။
- **Gate တစ်ခုချင်းစီအတွက် သုံးလတစ်ကြိမ် ROI ပြန်လည်သုံးသပ်မှု** (အကျိုးမပေးသော gate များကို ဖယ်ရှားပါ/ရန်ပုံငွေရပ်ပါ — ပင်ပန်းနွမ်းနယ်မှုကို တိုက်ဖျက်သည်)။
- သင့် project ၏ Hard Rules များကို အကောင်အထည်ဖော် run နိုင်သော gate များအဖြစ် မြှင့်တင်ပါ။

### ကဏ္ဍအားလုံးနှင့် သက်ဆိုင်သော အခြေခံမူများ (မဖြစ်မနေလိုက်နာရန်)

- **အကြွင်းမဲ့တန်ဖိုးမဟုတ်ဘဲ ratchet ကို သုံးပါ။** သတ်မှတ်ကိန်းဂဏန်းတစ်ခုကို gate လုပ်မည့်အစား _နောက်မဆုတ်ရေး_ ကို gate လုပ်ပါ (သုညမဖြစ်စေရန် အနိမ့်ဆုံးသတ်မှတ်ချက်များမှအပ)။
- **အကြွင်းမဲ့ အနိမ့်ဆုံးသတ်မှတ်ချက် + ratchet ကို တွဲသုံးပါ။** အနိမ့်ဆုံးသတ်မှတ်ချက်က ပြိုလဲမှုကို ကာကွယ်ပြီး ratchet က တဖြည်းဖြည်း ယိုယွင်းမှုကို ကာကွယ်သည်။
- **Anti-Goodhart ကို ရည်ရွယ်ချက်ရှိရှိ ဒီဇိုင်းလုပ်ပါ။** ပစ်မှတ် metric တိုင်းတွင် ဟန်ချက်ညီစေမည့် အတိုင်းအတာတစ်ခု လိုအပ်သည် (coverage ⇒ mutation + anti-masking၊ စမ်းသပ်ရန်ခက်ခဲသော code များကို မဖြစ်မနေ စမ်းသပ်စေရန် module တစ်ခုချင်းစီ၏ အနိမ့်ဆုံးသတ်မှတ်ချက်များ)။
- **ချောမွေ့စွာ ကျော်သွားခြင်း။** Infra မရှိခြင်းကြောင့် မည်သည့်အခါမျှ မပိတ်ဆို့ရ။ အမှန်တကယ် နောက်ဆုတ်မှုရှိမှသာ ပိတ်ဆို့ရမည်။
- **ဈေးကြီးသော metric များအတွက် `dedicatedGate`။** ပြင်ပ binary လိုအပ်သော metric များသည် synchronous central ratchet ၏ အပြင်ဘက်တွင် ကိုယ်ပိုင် script (skip ပါဝင်သော) ရှိရမည်။
- **Merge ဖြစ်သည့်နေရာတွင် gate လုပ်ပါ။** မြန်ဆန်သော gate နှင့် အမှန်တကယ် merge လုပ်ခြင်းကြားတွင် ကွာဟချက် မထားပါနှင့် (fast-gates ခွဲခြားမှုမှ ရရှိသော သင်ခန်းစာ)။
- **ပိတ်ဆို့တားဆီးသော gate များကို အနည်းငယ်သာ ထားပြီး ကောင်းစွာရွေးချယ်ပါ။** Sonar/DORA: condition များလွန်းခြင်း = ပင်ပန်းနွမ်းနယ်မှု။ ပိတ်ဆို့တားဆီးသော gate များစွာဖြင့် နံရံတစ်ခုဆောက်ခြင်းထက် advisory + ratchet ကို ဦးစားပေးပါ။

## အပိုင်း 5 — အကြံပြုထားသော တိုးတက်ကောင်းမွန်မှုများ (ဦးစားပေးအစီအစဉ်အလိုက်၊ တွဲဖက်အသုံးပြုနိုင်သော)

**P0 — ROI အမြင့်ဆုံး၊ အဆင်သင့်ဖြစ်လုနီးပါး**

1. **Mutation score ratchet** (ပထမဆုံး nightly Stryker က တန်ဖိုးများ ထုတ်ပေးပြီးနောက်)။ coverage-Goodhart ကို တန်ပြန်ရန် အဓိကနည်းလမ်းဖြစ်ပြီး ~90% ပြီးစီးထားသည်။
2. **ကျန်ရှိနေသေးသော fast-gates အဟကို ပိတ်ရန်** — `quality.yml` production build ကို ၎င်း၏
   advisory week ပြီးနောက် မြှင့်တင်ပြီး deterministic ဖြစ်သော release-PR-only စစ်ဆေးမှုများကို PR→release လမ်းကြောင်းထဲသို့ ဆက်လက်ရွှေ့ပါ။
3. **`main` တွင် Branch-protection ထားရန်** (owner setting) — Scorecard ကို မြှင့်တင်ပြီး DSOMM အဟကို ပိတ်ပေးသည်။

**P1 — တန်ဖိုးရှိသော** 4. **osv/oasdiff → သင့်လျော်သော scope ဖြင့် blocking ပြုလုပ်ရန်** — osv တွင် CRITICAL+fixable ကိုသာ သုံးရန် (Trivy ကဲ့သို့ အဆင့်နှစ်ဆင့်)၊ oasdiff က breaking-changes များကို ပိတ်ဆို့ရန်။ 5. **`require-tighten` → blocking ပြုလုပ်ရန်** (cycle အဆုံးတွင်) — metric တိုးတက်မှုများကို ခိုင်မာစေသည်။ 6. **Gate တစ်ခုချင်းစီအတွက် ROI/timing review** ကို `ci-summary` တွင် ထည့်ရန် — နှေးကွေးပြီး တန်ဖိုးနည်းသော gate များကို ရှာဖွေဖယ်ရှားရန်။

**P2 — အကျိုးပြန်ရရှိမှု လျော့နည်းလာသောအပိုင်း** 7. **SLSA L3** — L2 မှ အထက်သို့ တက်လိုပါက hermetic/reproducible builder (GitHub SLSA generator) ကို အသုံးပြုရန်။ 8. **Commit လုပ်ထားသော CodeQL config + versioned semgrep** — ထိန်းချုပ်နိုင်မှုနှင့် ပြန်လည်ထုတ်လုပ်နိုင်မှု ပိုကောင်းစေရန်။ 9. **PR တစ်ခုချင်းစီအတွက် DAST smoke** — အန္တရာယ်အမြင့်ဆုံး endpoint များတွင် schemathesis/promptfoo ၏ လျင်မြန်သော subset ကို လုပ်ဆောင်ရန် (nightly တစ်ခုတည်းသာ မဟုတ်)။ 10. **Flakiness dashboard + DORA metrics** — gate များကြောင့် မြန်နှုန်း မကျဆင်းသွားကြောင်း သေချာစေရန်။

## အပိုင်း 6 — လက်တွေ့ကျသော release သင်ခန်းစာများ (Phase 9 တွင် ထည့်သွင်းရန် gate များ)

> ဤအပိုင်းတွင် gate တစ်ခု **မရှိခဲ့သော** release ပိတ်သိမ်းမှုများမှ လက်တွေ့ဖြစ်ရပ်များကို
> တိကျသော အထောက်အထားနှင့် အဆိုပြုထားသော gate တို့ဖြင့် မှတ်တမ်းတင်ထားသည်။ အချက်တစ်ခုစီသည် အပိုင်း 5 အတွက် ထည့်သွင်းစဉ်းစားနိုင်သည့် အရာဖြစ်သည်။

### သင်ခန်းစာ v3.8.27 (2026-06-17) — "fast-gates hole" ကြောင့် deterministic regression များသည် release နေ့အထိ ရောက်ရှိသွားနိုင်သည်

**ဖြစ်ပျက်ခဲ့သည့်အရာ။** v3.8.27 `/generate-release` အတွင်း release PR (`release/v3.8.27` → `main`)
သည် ပေါင်းစည်းထားသော cycle ထဲတွင် `ci.yml` matrix အပြည့်အစုံကို **ပထမဆုံး** လုပ်ဆောင်ခြင်းဖြစ်ခဲ့သည်။ ရလဒ်မှာ failure 12 ခု
တစ်ပြိုင်နက် ပေါ်လာခဲ့သည် — **deterministic test 3 ခု** + flake/env ~9 ခု။ မည်သည့်အရာမျှ လက်ရှိ product regression မဟုတ်ခဲ့သော်လည်း
cycle PR များသည် **Fast QG
(`quality.yml`)** မှတစ်ဆင့် `release/**` ထဲသို့ ဝင်ရောက်သောကြောင့် အားလုံးကို သတိမပြုမိခဲ့ပါ။ ယင်းသည် unit suite အပြည့်အစုံ၊ `pr-test-policy` (test-masking)၊
integration suite အပြည့်အစုံနှင့် schema parity စစ်ဆေးမှုတို့ကို မလုပ်ဆောင်ပါ။ deterministic ဖြစ်သော 3 ခုမှာ-

1. **UI ပြောင်းလဲမှုကြောင့် test ခေတ်နောက်ကျသွားခြင်း** — `permissions modal switch buttons declare button type`:
   #4034 က 4 ခုမြောက် switch တစ်ခု ထည့်ခဲ့သည် (a11y `type="button"` ကို ဆက်လက်ထိန်းသိမ်းထားသည်)၊ test ၏ `=== 3` count သည်
   ခေတ်နောက်ကျသွားခဲ့သည်။ Static analysis သည် #4034 PR အတွင်း ဤအရာကို ဖမ်းမိသင့်ခဲ့သည်။
2. **Packaging ပြောင်းလဲမှုကြောင့် test ခေတ်နောက်ကျသွားခြင်း** — `findMissingArtifactPaths ... root runtime files`:
   `dist/http-method-guard.cjs` သည် တရားဝင်လိုအပ်သော path တစ်ခု ဖြစ်လာခဲ့ပြီး test ၏ မျှော်မှန်းထားသော list သည်
   ခေတ်နောက်ကျသွားခဲ့သည်။
3. **အချက်အလက်ဆုံးရှုံးစေသော modularization ကွဲလွဲမှု (အလေးအနက်ဆုံး)** — `settings schemas accept ... unprefixed
toggle`: **modularized** လုပ်ထားသော `updateSettingsSchema` (`schemas/settings.ts`, #3988 ဖြင့် ဖန်တီးထားသည်) သည်
   canonical ဖြစ်သော (`settingsSchemas.ts`) နှင့် ကွဲလွဲသွားခဲ့သည်- **field 45 ခုနှင့် 85 ခု — 40 ခု ပျောက်ဆုံး + 6 ခု ကွဲလွဲ (qdrant\*)**။ ၎င်းသည်
   **dead-code** ဖြစ်ခဲ့သည် (runtime က canonical ဖြစ်သောအရာကို အသုံးပြုသည်)၊ ထို့ကြောင့် လက်ရှိအသုံးပြုမှုအပေါ် သက်ရောက်မှုမရှိခဲ့သော်လည်း ကိုယ်တိုင်ရေးသားထားသော parity
   test ကသာ ၎င်းကို ဖမ်းမိခဲ့သည်။ #4030 က #3988/#3993 မှ အလားတူ ပျောက်ဆုံးမှု 16 ခုကို ပြန်လည်ထည့်သွင်းခဲ့သော်လည်း ဤတစ်ခုက လွတ်သွားခဲ့သည်။

**အဆိုပြုထားသော gate များ (Phase 9):**

- **G1 — fast-gates အဟကို အမှန်တကယ် ပိတ်ရန် (P0 #2 ကို တိုးချဲ့ခြင်း)။** `quality.yml` (PR→`release/**`) တွင်
  typecheck + impacted tests အပြင် **`pr-test-policy` (test-masking) + deterministic
  unit suite အပြည့်အစုံ** ကို လုပ်ဆောင်ပါ (သို့မဟုတ် အနည်းဆုံး လျင်မြန်ပြီး flake မဖြစ်သော static/parity file များကို လုပ်ဆောင်ပါ)။
  ဤသို့ဖြင့် ခေတ်နောက်ကျသော test များနှင့် assert ဖယ်ရှားမှုများကို release နေ့အထိ မစောင့်ဘဲ ၎င်းတို့ကို စတင်ဖြစ်ပေါ်စေသော PR ထဲတွင် ဖမ်းမိနိုင်မည်။
  integration/e2e ကို မထည့်ပါနှင့် (နှေးကွေး/flake ဖြစ်လွယ်သည်)၊ သို့သော် deterministic layer ကို
  PR→main တွင်သာ ဆက်ထား၍ **မဖြစ်နိုင်ပါ**။
- **G2 — Modularization parity gate (အသစ်၊ ယနေ့တွင် မပါဝင်သေး)။** Modularized barrel (`src/shared/validation/schemas/*`, `providerRegistry`
  modules စသည်) တစ်ခုက re-export လုပ်သော symbol တစ်ခုချင်းစီအတွက် **shape** (`z.object` keys, registry entries) ကို canonical
  source နှင့် နှိုင်းယှဉ်ပြီး **ကွဲလွဲမှုရှိပါက fail လုပ်သော** စစ်ဆေးမှု (ပျောက်ဆုံး/ပိုနေသော field)။ ယင်းသည် #3988 မှ field 40 ခု ပျောက်ဆုံးမှုကို
  ထို PR ထဲတွင်ပင် ဖမ်းမိစေမည်ဖြစ်သည်။ ကိုယ်တိုင်ရေးသားထားသော parity test များကို ယေဘုယျအသုံးချနိုင်အောင် တိုးချဲ့ပေးသည် (တစ်စုံတစ်ဦးက
  ရေးသားရန် သတိရသည့်နေရာများတွင်သာ ယင်း test များ ရှိသည်)။ ကုန်ကျစရိတ်နည်းသည်- နှစ်ခုလုံးကို import လုပ်ပြီး `Object.keys(shape)` ကို diff လုပ်ရုံသာဖြစ်သည်။
- **G3 — Deterministic flake triage (အထောက်အကူပြု)။** LiveWS-startup နှင့် integration-combo/breaker
  test များသည် logic ကြောင့်မဟုတ်ဘဲ CI ရှိ server timeout/cascade (env) ကြောင့် fail ဖြစ်သည်။ ၎င်းတို့ကို
  `known-flaky` (issue နှင့်အတူ quarantine လုပ်ထားသော) အဖြစ် သတ်မှတ်ပါ၊ သို့မှသာ release-PR ၏ အနီရောင်အခြေအနေသည် deterministic regression များကို
  အလယ်တွင် ဖုံးကွယ်သည့် noise မဟုတ်ဘဲ **တကယ့် signal များသာ** ဖြစ်မည်။

**မူဝါဒ:** _merge ဖြစ်ပေါ်သည့်နေရာတွင် gate ကို run ရမည်_ ("Cross-cutting principles" တွင် ပါရှိပြီးဖြစ်သည်)။
v3.8.27 ဖြစ်ရပ်က ဤအချက်သည် lint/typecheck အတွက်သာမက **deterministic test layer** အတွက်လည်း သက်ရောက်ကြောင်း ပြသသည် —
မဟုတ်ပါက ခေတ်နောက်ကျသော test များ + အချက်အလက်ဆုံးရှုံးစေသော modularization တို့၏ အကြွေးသည် အဆိုးရွားဆုံးအချိန်တွင်
