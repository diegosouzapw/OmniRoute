Pull request တစ်ခုအတွက် ယုံကြည်စိတ်ချရပြီး အနည်းဆုံးဖြစ်သည့် development loop ကို ရွေးချယ်ရန် ဤလမ်းညွှန်ကို အသုံးပြုပါ။ ဤလမ်းညွှန်သည်
အောက်တွင် လင့်ခ်ချိတ်ထားသည့် သက်ဆိုင်ရာနယ်ပယ်အလိုက် architecture နှင့် security စာရွက်စာတမ်းများကို
အစားထိုးခြင်းမဟုတ်ဘဲ အသုံးများသည့် ပြောင်းလဲမှုအမျိုးအစားတစ်ခုစီကို ၎င်း၏ contracts၊ အဓိကထားစစ်ဆေးမှုများနှင့် CI coverage တို့ဖြင့် ချိတ်ဆက်ပေးခြင်းဖြစ်သည်။

## ပြောင်းလဲမှုတိုင်း လိုက်နာရမည့် လမ်းကြောင်း

1. **မပြင်ဆင်မီ base ကို ရွေးချယ်ပါ။** လက်ရှိအသုံးပြုနေသော အမြင့်ဆုံး `release/v*` branch ကိုရှာပြီး
   ၎င်း၏ tip မှ branch ခွဲပါ။ `main` ကိုမဟုတ်ဘဲ ထို branch ကို target လုပ်ပါ။ Release freeze လုပ်ထားပါက freeze လုပ်ထားသော
   branch ကို target မလုပ်ပါနှင့်။ [Branching & Release Model](BRANCHING_MODEL.md) တွင် ဖော်ပြထားသည့်
   နောက်ထပ် active cycle ကို အသုံးပြုပါ။
2. **Contracts များကို သတ်မှတ်ဖော်ပြပါ။** ပြောင်းလဲမှုကြောင့် သက်ရောက်မှုရှိမည့် catalog၊ schema၊ generated artifact၊ public API သို့မဟုတ် user
   interface အားလုံးကို ဖော်ထုတ်ပါ။ အောက်ပါဇယားတွင် အနည်းဆုံး စတင်ရမည့်အစုကို ဖော်ပြထားသည်။
3. **အဓိကထားသော tests များကို ရေးသားပါ သို့မဟုတ် အပ်ဒိတ်လုပ်ပါ။** `src/`, `open-sse/`, `electron/` သို့မဟုတ်
   `bin/` ရှိ production ပြောင်းလဲမှုများအတွက် တူညီသော PR ထဲတွင် automated test တစ်ခု လိုအပ်သည်။ လုပ်ဆောင်ချက်မှန်ကန်ကြောင်း သက်သေပြနိုင်သည့်
   အနည်းဆုံး test files များကို ဦးစွာ run ပြီးနောက် ဖော်ပြထားသည့် focused gates များကို run ပါ။
4. **ကျယ်ပြန့်သော matrix ကို CI ဖြင့် run ပါ။** ပြည့်စုံသော unit shards၊ Vitest၊ coverage ratchet နှင့်
   production build တို့ကို PR ပေါ်တွင် run မည်။ Focused failure တစ်ခုက ပိုမိုကျယ်ပြန့်သော သက်ရောက်မှုရှိကြောင်း ညွှန်ပြသည့်အခါ သို့မဟုတ် ပြောင်းလဲမှုသည် subsystem အများအပြားကို
   ဖြတ်ကျော်သည့်အခါမှသာ broad suite ကို local တွင် run ပါ။
5. **Review မတိုင်မီ ညှိနှိုင်းပေါင်းစည်းပါ။** Active base ကို fetch လုပ်ပြီး ၎င်း၏ commit အသစ်များနှင့်
   ၎င်းနှင့်နှိုင်းယှဉ်ထားသော သင့် diff ကို စစ်ဆေးပါ၊ ထို့နောက် contributor workflow အတိုင်း base ကို rebase သို့မဟုတ် merge လုပ်ပါ။ Generated-file
   နှင့် catalog conflicts များကို မူလ source မှ ဖြေရှင်းပြီး ၎င်းတို့ကို regenerate လုပ်ကာ focused loop ကို ပြန်လည် run ပြီး
   PR သည် active release branch ကို ဆက်လက် target လုပ်ထားကြောင်း အတည်ပြုပါ။
6. **အထောက်အထားများကို မှတ်တမ်းတင်ပါ။** PR template တွင် run ခဲ့သည့် commands များ၊ ထည့်သွင်းထားသော သို့မဟုတ် ပြောင်းလဲထားသော test file အားလုံး၊
   migrations သို့မဟုတ် feature flags များနှင့် မပြီးစီးသေးသော CI-only validation များကို စာရင်းပြုစုပါ။

## ပြောင်းလဲမှုအမျိုးအစားအလိုက် စံလမ်းကြောင်းများ

အောက်ပါ commands များသည် အနည်းဆုံး focused checks များသာဖြစ်ပြီး သင်ပြောင်းလဲခဲ့သော
လုပ်ဆောင်ချက်ကို တိုက်ရိုက်စစ်ဆေးသည့် test တစ်ခုအား ကျော်လွှားခွင့်ပြုထားခြင်း မဟုတ်ပါ။

### Provider

**Contracts**

- `src/shared/constants/providers/` ရှိ Provider definition နှင့်
  `src/shared/constants/providers.ts` ရှိ ၎င်း၏ composition။
- `open-sse/config/providerRegistry.ts` သို့မဟုတ် ၎င်းမှ ခွဲထုတ်ထားသော registry files များရှိ Models နှင့် capabilities။
- သက်ဆိုင်သည့်အခါ Executor/translator selection၊ OAuth သို့မဟုတ် API-key configuration၊ dashboard assets နှင့် generated
  provider reference။
- Public credentials များသည် `resolvePublicCred()` ကို အသုံးပြုရမည်။ Error responses များသည် မျှဝေထားသော sanitized
  error helpers များကို အသုံးပြုရမည်။ `docs/security/PUBLIC_CREDS.md` (git ထဲတွင်သာရှိပြီး `/docs` ထဲသို့ compile မလုပ်ပါ) နှင့်
  [Error Sanitization](../security/ERROR_SANITIZATION.md) ကို ကြည့်ပါ။

**Focused loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog ပြောင်းလဲသည့်အခါ၊ generated diff ကို commit လုပ်ပါ
npm run lint
```

သက်ရောက်မှုရှိသော request family တစ်ခုစီဖြစ်သည့် chat၊ Responses၊ images၊ embeddings၊ audio သို့မဟုတ် video တို့ကိုလည်း test လုပ်ပါ။
Generated catalog နှင့် golden diffs များကို contract ပြောင်းလဲမှုများအဖြစ် review လုပ်ပါ။ ၎င်းတို့ကို မစစ်ဆေးဘဲ လက်မခံပါနှင့်။

### Routing

**Contracts**

- `src/shared/constants/routingStrategies.ts` ရှိ Public strategy values နှင့် UI metadata။
- `open-sse/services/combo.ts` နှင့် `open-sse/services/combo/` အောက်ရှိ Dispatch နှင့် ordering။
- Combo schemas၊ persistence၊ resilience state၊ model capabilities နှင့် API/UI controls။
- လုပ်ဆောင်ပုံ ပြောင်းလဲသည့်အခါ [Auto-Combo Engine](../routing/AUTO-COMBO.md) နှင့် resilience documentation။

**Focused loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy သို့မဟုတ် dispatch ပြောင်းလဲမှုများ
npm run check:known-symbols      # strategy registration ပြောင်းလဲမှုများ
npm run lint
```

Local တွင် deterministic mocked-upstream tests များကို အသုံးပြုပါ။ Live combo smokes များသည် credentials လိုအပ်ပြီး
manual ဖြစ်သဖြင့် CI ကို အစားထိုးနိုင်ခြင်းမရှိပါ။

### UI / UX

**Contracts**

- `src/app/` နှင့် `src/shared/components/` အောက်ရှိ Next.js route/page နှင့် shared component boundaries။
- API response shapes၊ loading/empty/error states၊ keyboard နှင့် screen-reader behavior၊
  responsive layout၊ theming နှင့် locale expansion။
- `src/i18n/messages/en.json` ရှိ English UI source strings။ အသုံးပြုသူမြင်ရမည့် copy အသစ်ကို hard-code မလုပ်ပါနှင့်။

**Focused loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction သို့မဟုတ် visual ပြောင်းလဲမှုများအတွက် app ကို run ပြီး ကျဉ်းသောနှင့် ကျယ်သော viewports နှစ်မျိုးစလုံးကို စစ်ဆေးပါ။ CI သည်
production build နှင့် ပိုမိုကျယ်ပြန့်သော suites များကို run သော်လည်း visual behavior အတွက် ပြောင်းလဲမှုနှင့်သင့်လျော်သော focused component၊ Playwright
သို့မဟုတ် မှတ်တမ်းတင်ထားသည့် manual check တစ်ခု လိုအပ်ဆဲဖြစ်သည်။

### i18n

**Contracts**

- `src/i18n/messages/en.json` သည် UI source ဖြစ်ပြီး `config/i18n.json` သည် locale source ဖြစ်သည်။
- CLI catalogs များကို `bin/cli/locales/` အောက်တွင် သီးခြားထားရှိသည်။
- ICU placeholders နှင့် tags များကို မပြောင်းလဲဘဲ အတိအကျ ထိန်းသိမ်းပါ။ Product/provider/model names၊
  protocol နှင့် header names၊ commands၊ code/JSON identifiers၊ URLs၊ environment variables သို့မဟုတ်
  `OmniRoute`, `OAuth`, `MCP` နှင့် `A2A` ကဲ့သို့သော protected terms များကို ဘာသာမပြန်ပါနှင့်။ လက်ရှိ source list သည်
  `scripts/i18n/glossary/protected-terms.json` ဖြစ်သည်။

**Focused loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI strings/catalogs ပြောင်းလဲသည့်အခါ
npm run lint
```

ဤအရာသည် လက်ရှိစနစ်အတွက် လမ်းညွှန်ချက်ဖြစ်ပြီး ၎င်း၏ tooling သို့မဟုတ် key model ကို တိုးချဲ့ရန် ဖိတ်ခေါ်ခြင်းမဟုတ်ပါ။
အစားထိုးစနစ်ကို ဒီဇိုင်းရေးဆွဲနေစဉ် i18n patches များကို လိုအပ်သလောက်သာ တိတိကျကျ ပြင်ဆင်ပါ။ Task က generated translations များကို အတိအကျလိုအပ်ပြီး
ထွက်ပေါ်လာသော diff ကို သင် review လုပ်ပြီးသားမဟုတ်ပါက external services များကို ခေါ်ဆိုသည့် translation
commands များကို မ run ပါနှင့်။

### CLI

**Contracts**

- `bin/cli/` ရှိ အများသုံး command များနှင့် flag များ၊ ထုတ်လုပ်ထားသော API command များ၊ exit code များ၊ stdout/stderr နှင့်
  JSON output ပုံသဏ္ဌာန်များ၊ config/environment အပြုအမူနှင့် package ထဲထည့်ထားသော file များ။
- CLI အသုံးပြုသူမြင်ရသော စာသားများသည် CLI i18n layer ကို အသုံးပြုရမည်ဖြစ်ပြီး `en`/`pt-BR` catalog များကို ကိုက်ညီအောင် ထိန်းသိမ်းထားရမည်။
- Node ကို ပံ့ပိုးထားသော runtime အဖြစ် ဆက်လက်ထိန်းသိမ်းပြီး ထုတ်ဝေထားသော binary contract ကို မပြောင်းလဲဘဲ ထိန်းသိမ်းပါ။

**ဦးတည်စစ်ဆေးမှု လုပ်ငန်းစဉ်**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # ထုတ်လုပ်ထားသော/စုစည်းထားသော CLI ပြောင်းလဲမှုများ
npm run check:pack-policy     # package မျက်နှာပြင်ဆိုင်ရာ ပြောင်းလဲမှုများ
npm run lint
```

အပြုအမူသည် parsing၊ file များ သို့မဟုတ် exit status အပေါ် မူတည်သည့်အခါ ယာယီ data directory တစ်ခုအတွင်း အတိအကျတူညီသော command ကို အသုံးပြုပါ။ CI သည် ပိုမိုကျယ်ပြန့်သော package artifact နှင့် ecosystem စစ်ဆေးမှုများကို လုပ်ဆောင်သည်။

### ဒေတာဘေ့စ်

**Contract များ**

- `src/lib/db/` အောက်ရှိ domain module များ၊ သီးခြား module များကို တိုက်ရိုက် import လုပ်ပါ (`localDb.ts` re-export layer အဟောင်းကို ဖယ်ရှားထားသည်)။
- `src/lib/db/migrations/` အောက်ရှိ နံပါတ်စဉ်တပ်ထားသော၊ idempotent ဖြစ်သော SQL migration များ၊ transaction ဘေးကင်းမှု၊ upgrade
  အပြုအမူ၊ index များနှင့် schema ကြောင့် သက်ရောက်မှုရှိသည့် caller အားလုံး။
- Route များနှင့် handler များသည် raw SQL ကို မည်သည့်အခါမျှ တိုက်ရိုက် မထုတ်ပြန်ရ။

**ဦးတည်စစ်ဆေးမှု လုပ်ငန်းစဉ်**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migration တစ်ခု ထည့်သွင်းသည့်အခါ အသစ်ဖြစ်သော database နှင့် ယခင် schema မှ upgrade လုပ်ခြင်း နှစ်မျိုးလုံးကို စမ်းသပ်ပါ။ Database test များသည် handle များကို ပိတ်ပြီး cleanup လုပ်စဉ် `resetDbInstance()` ကို ခေါ်ရမည်။ အကောင်းဆုံးကြိုးပမ်းမှုအဖြစ်သာ ပံ့ပိုးထားသော Bun adapter လမ်းကြောင်း ပြောင်းလဲသည့်အခါမှသာ `npm run test:bun:db` ကို လုပ်ဆောင်ပါ။ Node သည် အဓိကစံအဖြစ် ဆက်လက်ရှိသည်။

### Build / deploy

**Contract များ**

- Root နှင့် workspace manifest/lockfile များ၊ `scripts/build/`၊ Next.js standalone စုစည်းမှု၊ `dist/`
  package အကြောင်းအရာများ၊ Electron platform metadata၊ CI workflow များနှင့် deployment sentinel များ။
- ပံ့ပိုးထားသော Node range များနှင့် `CLAUDE.md` ထဲရှိ ခွင့်ပြုစာရင်းသွင်းထားသော Bun အသုံးပြုမှုကို မပြောင်းလဲဘဲ ထိန်းသိမ်းရမည်။
- Build artifact များကို version control ဖြင့် ခြေရာမခံရပါ။ dependency၊ license၊ workflow နှင့် package policy များ အကျုံးဝင်သည်။

**ဦးတည်စစ်ဆေးမှု လုပ်ငန်းစဉ်**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency သို့မဟုတ် lockfile ပြောင်းလဲမှုများ
npm run check:pack-policy      # ထုတ်ဝေထားသော package မျက်နှာပြင် ပြောင်းလဲမှုများ
npm run lint
```

ပြောင်းလဲမှုသည် compilation၊ standalone စုစည်းမှု၊ asset များ သို့မဟုတ် runtime bundling အပေါ် သက်ရောက်သည့်အခါမှသာ local တွင် `npm run build` ကို အသုံးပြုပါ။ Release/deploy အတည်ပြုစစ်ဆေးမှုအတွက်သာ `npm run build:release` ကို အသုံးပြုပါ။ CI ၏ build သည် နောက်ဆုံး cross-platform အချက်ပြမှုဖြစ်သည်။ Platform အလိုက် သီးခြား Electron ပြောင်းလဲမှုများအတွက် သက်ဆိုင်ရာ ဦးတည် build သို့မဟုတ် smoke စစ်ဆေးမှု အထောက်အထား လိုအပ်သည်။

## Local loop နှင့် CI နှိုင်းယှဉ်ချက်

| Patch တစ်ခုစီအတွက် local တွင် run ရန်                                                                | CI က ကျယ်ပြန့်သော signal ကို ပံ့ပိုးပေးသည်                                        |
| ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| အထက်ပါ တိုက်ရိုက် behavior test များနှင့် category gate များ                                         | Shard ခွဲထားသော unit suite အပြည့်အစုံနှင့် serial test များ                       |
| `npm run lint`                                                                                       | Vitest suite များနှင့် coverage/quality ratchet များ                              |
| သက်ရောက်မှုရှိသော contract က လိုအပ်သည့်အခါမှသာ typecheck သို့မဟုတ် build လုပ်ရန်                     | Production build၊ security၊ docs၊ dependency နှင့် PR-policy gate များ            |
| Automation ဖြင့် behavior ကို အတည်မပြုနိုင်သည့်အခါမှသာ manual interaction/live check များ ပြုလုပ်ရန် | Workflow ဖြင့် စီစဉ်သတ်မှတ်ထားသော cross-job integration နှင့် platform check များ |

အာရုံစိုက်ထားသော loop အောင်မြင်နေခြင်းသည် ပြောင်းလဲထားသော contract နှင့်ပတ်သက်သည့် အထောက်အထားဖြစ်ပြီး၊ သက်ဆိုင်မှုမရှိသော CI check များ
အောင်မြင်မည်ဟု သက်သေပြခြင်းမဟုတ်ပါ။ အပြန်အလှန်အားဖြင့်လည်း local edit တစ်ခုစီတိုင်းကို repository matrix အပြည့်အစုံ ပြီးဆုံးသည်အထိ မစောင့်ဆိုင်းစေပါနှင့်။

## ပြန်လည်ညှိနှိုင်းရေး checklist

Review တောင်းခံခြင်းမပြုမီ-

- PR base သည် လက်ရှိအသုံးပြုနေသော `release/v*` branch များအနက် အမြင့်ဆုံး branch ဖြစ်နေသေးကြောင်း အတည်ပြုပါ။
- ထို base ကို fetch လုပ်ပြီး သင် branch ခွဲခဲ့သည့်အချိန်မှစ၍ ထည့်သွင်းထားသော commit များကို review လုပ်ပါ။
- မတော်တဆ သို့မဟုတ် အလိုအလျောက် generate လုပ်ထားသော မလိုအပ်သည့် အပြောင်းအလဲများရှိမရှိ စစ်ဆေးရန် `git diff <active-base>...HEAD` ကို review လုပ်ပါ။
- Source ကို update လုပ်ပြီး output ကို ပြန်လည် generate လုပ်ခြင်းဖြင့် catalog နှင့် generate လုပ်ထားသော document conflict များကို ဖြေရှင်းပါ။
- ပြန်လည်ညှိနှိုင်းပြီးနောက် PR description တွင် ဖော်ပြထားသော အာရုံစိုက်ထားသည့် test/gate တစ်ခုစီကို ပြန်လည် run ပါ။
- Base ပြောင်းရွှေ့သွားခြင်းနှင့် ကိုက်ညီစေရန်အတွက် assertion များကို အားနည်းစေခြင်း သို့မဟုတ် လိုအပ်သော test များကို ဖယ်ရှားခြင်း လုံးဝမပြုလုပ်ပါနှင့်။

Release-freeze နှင့် retargeting စည်းမျဉ်းများအတွက်
[Branching & Release Model](BRANCHING_MODEL.md) ကို အသုံးပြုပါ။ CI inventory အပြည့်အစုံအတွက်
[Quality Gates Reference](../architecture/QUALITY_GATES.md) ကို အသုံးပြုပါ။
