Pull request တစ်ခုအတွက် အသေးဆုံးနှင့် ယုံကြည်စိတ်ချရသော development loop ကို ရွေးချယ်ရန် ဤလမ်းညွှန်ကို အသုံးပြုပါ။ ဤလမ်းညွှန်သည်
အောက်တွင် လင့်ခ်ချိတ်ထားသည့် သက်ဆိုင်ရာနယ်ပယ်အလိုက် architecture နှင့် security စာရွက်စာတမ်းများကို
အစားမထိုးပါ။ ၎င်းသည် အသုံးများသော ပြောင်းလဲမှုအမျိုးအစားတစ်ခုစီကို သက်ဆိုင်ရာ contracts များ၊ ဦးတည်စစ်ဆေးမှုများနှင့် CI coverage တို့ဖြင့် ချိတ်ဆက်ပေးသည်။

## ပြောင်းလဲမှုတိုင်း လိုက်နာရမည့် လမ်းကြောင်း

1. **မပြင်ဆင်မီ base ကို ရွေးချယ်ပါ။** လက်ရှိအသုံးပြုနေသော အမြင့်ဆုံး `release/v*` branch ကို ရှာပြီး
   ၎င်း၏ tip မှ branch ခွဲပါ။ `main` ကို မဟုတ်ဘဲ ထို branch ကို ပစ်မှတ်ထားပါ။ Release freeze လုပ်ထားပါက freeze ဖြစ်နေသော
   branch ကို ပစ်မှတ်မထားပါနှင့်။ [Branching & Release Model](BRANCHING_MODEL.md) တွင် ဖော်ပြထားသည့်
   နောက်ထပ် active cycle ကို အသုံးပြုပါ။
2. **Contracts များကို အမည်တပ်ဖော်ထုတ်ပါ။** ပြောင်းလဲမှုက သက်ရောက်မှုရှိသည့် catalog၊ schema၊ generated artifact၊ public API သို့မဟုတ် user
   interface တစ်ခုစီကို ဖော်ထုတ်ပါ။ အောက်ပါဇယားတွင် အနည်းဆုံး စတင်အသုံးပြုရမည့် အစုကို ဖော်ပြထားသည်။
3. **ဦးတည်စမ်းသပ်မှုများကို ရေးသားပါ သို့မဟုတ် အပ်ဒိတ်လုပ်ပါ။** `src/`၊ `open-sse/`၊ `electron/` သို့မဟုတ်
   `bin/` ရှိ production ပြောင်းလဲမှုများအတွက် PR တစ်ခုတည်းအတွင်း automated test တစ်ခု လိုအပ်သည်။ လုပ်ဆောင်ပုံမှန်ကန်ကြောင်း သက်သေပြနိုင်သည့်
   အသေးဆုံး test file များကို ဦးစွာ run ပြီးနောက် စာရင်းပြုထားသည့် focused gates များကို run ပါ။
4. **ကျယ်ပြန့်သော matrix ကို CI ဖြင့် run ပါ။** ပြည့်စုံသော unit shards၊ Vitest၊ coverage ratchet နှင့်
   production build တို့ကို PR ပေါ်တွင် run သည်။ Focused failure တစ်ခုက ပိုမိုကျယ်ပြန့်သော သက်ရောက်မှုရှိကြောင်း ပြသသည့်အခါ သို့မဟုတ်
   ပြောင်းလဲမှုက subsystem အများအပြားကို လွှမ်းခြုံသည့်အခါမှသာ ကျယ်ပြန့်သော suite ကို local တွင် run ပါ။
5. **Review မလုပ်မီ ပြန်လည်ညှိနှိုင်းပါ။** Active base ကို fetch လုပ်ပါ၊ ၎င်း၏ commit အသစ်များနှင့် ၎င်းနှင့်နှိုင်းယှဉ်ထားသော သင့် diff ကို စစ်ဆေးပါ၊
   ထို့နောက် contributor workflow အတိုင်း base ကို rebase သို့မဟုတ် merge လုပ်ပါ။ Generated file
   နှင့် catalog conflict များကို ၎င်းတို့၏ source မှ ဖြေရှင်းပြီး ပြန်လည် generate လုပ်ပါ၊ focused loop ကို ပြန် run ပါ၊ ထို့နောက်
   PR သည် active release branch ကို ဆက်လက်ပစ်မှတ်ထားကြောင်း အတည်ပြုပါ။
6. **အထောက်အထားများကို မှတ်တမ်းတင်ပါ။** PR template တွင် run ခဲ့သည့် command များ၊ ထည့်သွင်းထားသော သို့မဟုတ် ပြောင်းလဲထားသော test file တိုင်း၊
   migration သို့မဟုတ် feature flag များနှင့် pending ဖြစ်နေသေးသော CI-only validation များကို စာရင်းပြုစုပါ။

## ပြောင်းလဲမှုအမျိုးအစားအလိုက် Golden paths

အောက်ပါ command များသည် အနည်းဆုံး focused checks များဖြစ်ပြီး သင်ပြောင်းလဲထားသော
လုပ်ဆောင်ပုံကို တိုက်ရိုက်စစ်ဆေးသည့် test ကို ကျော်သွားရန် ခွင့်ပြုချက်မဟုတ်ပါ။

### Provider

**Contracts**

- `src/shared/constants/providers/` ရှိ Provider definition နှင့်
  `src/shared/constants/providers.ts` ရှိ ၎င်း၏ composition။
- `open-sse/config/providerRegistry.ts` သို့မဟုတ် ၎င်းမှ ခွဲထုတ်ထားသော registry file များရှိ model နှင့် capability များ။
- သက်ဆိုင်သည့်အခါ executor/translator ရွေးချယ်မှု၊ OAuth သို့မဟုတ် API-key configuration၊ dashboard asset များနှင့် generated
  provider reference။
- Public credential များသည် `resolvePublicCred()` ကို အသုံးပြုရမည်။ Error response များသည် မျှဝေသုံးစွဲထားသော sanitized
  error helper များကို အသုံးပြုရမည်။ `docs/security/PUBLIC_CREDS.md` (git တွင်ရှိပြီး `/docs` ထဲသို့ compile မလုပ်ပါ) နှင့်
  [Error Sanitization](../security/ERROR_SANITIZATION.md) ကို ကြည့်ပါ။

**Focused loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog ပြောင်းလဲသည့်အခါ၊ generated diff ကို commit လုပ်ပါ
npm run lint
```

သက်ရောက်မှုရှိသည့် request family တိုင်းဖြစ်သော chat၊ Responses၊ images၊ embeddings၊ audio သို့မဟုတ် video ကိုလည်း စမ်းသပ်ပါ။
Generated catalog နှင့် golden diff များကို contract ပြောင်းလဲမှုများအဖြစ် review လုပ်ပါ။ မစစ်ဆေးဘဲ လက်မခံပါနှင့်။

### Routing

**Contracts**

- `src/shared/constants/routingStrategies.ts` ရှိ public strategy value များနှင့် UI metadata။
- `open-sse/services/combo.ts` နှင့် `open-sse/services/combo/` အောက်ရှိ dispatch နှင့် ordering။
- Combo schema များ၊ persistence၊ resilience state၊ model capability များနှင့် API/UI control များ။
- လုပ်ဆောင်ပုံ ပြောင်းလဲသည့်အခါ [Auto-Combo Engine](../routing/AUTO-COMBO.md) နှင့် resilience စာရွက်စာတမ်းများ။

**Focused loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy သို့မဟုတ် dispatch ပြောင်းလဲမှုများ
npm run check:known-symbols      # strategy registration ပြောင်းလဲမှုများ
npm run lint
```

Local တွင် deterministic mocked-upstream test များကို အသုံးပြုပါ။ Live combo smoke test များသည် credential လိုအပ်ပြီး
manual ဖြစ်သဖြင့် CI ကို အစားထိုးခြင်းမဟုတ်ပါ။

### UI / UX

**Contracts**

- `src/app/` နှင့် `src/shared/components/` အောက်ရှိ Next.js route/page နှင့် shared component boundary များ။
- API response shape များ၊ loading/empty/error state များ၊ keyboard နှင့် screen-reader လုပ်ဆောင်ပုံ၊
  responsive layout၊ theming နှင့် locale တိုးချဲ့မှု။
- `src/i18n/messages/en.json` ရှိ အင်္ဂလိပ် UI source string များ။ User-facing copy အသစ်ကို hard-code မလုပ်ပါနှင့်။

**Focused loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction သို့မဟုတ် visual ပြောင်းလဲမှုများအတွက် app ကို run ပြီး ကျဉ်းသော viewport နှင့် ကျယ်သော viewport နှစ်မျိုးစလုံးကို စစ်ဆေးပါ။ CI သည်
production build နှင့် ပိုမိုကျယ်ပြန့်သော suite များကို run သော်လည်း visual လုပ်ဆောင်ပုံအတွက် ပြောင်းလဲမှုနှင့် သင့်လျော်သည့် focused component၊ Playwright
သို့မဟုတ် မှတ်တမ်းတင်ထားသော manual check လိုအပ်ဆဲဖြစ်သည်။

### i18n

**Contracts**

- `src/i18n/messages/en.json` သည် UI source ဖြစ်ပြီး `config/i18n.json` သည် locale source ဖြစ်သည်။
- CLI catalog များကို `bin/cli/locales/` အောက်တွင် သီးခြားထားသည်။
- ICU placeholder နှင့် tag များကို အတိအကျ ထိန်းသိမ်းပါ။ Product/provider/model အမည်များ၊
  protocol နှင့် header အမည်များ၊ command များ၊ code/JSON identifier များ၊ URL များ၊ environment variable များ သို့မဟုတ်
  `OmniRoute`၊ `OAuth`၊ `MCP` နှင့် `A2A` ကဲ့သို့ protected term များကို မဘာသာပြန်ပါနှင့်။ လက်ရှိ source list သည်
  `scripts/i18n/glossary/protected-terms.json` ဖြစ်သည်။

**Focused loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI string/catalog များ ပြောင်းလဲသည့်အခါ
npm run lint
```

ဤသည်မှာ လက်ရှိ system အတွက် လမ်းညွှန်ချက်ဖြစ်ပြီး ၎င်း၏ tooling သို့မဟုတ် key model ကို တိုးချဲ့ရန် ဖိတ်ခေါ်ခြင်းမဟုတ်ပါ။
အစားထိုးမည့် system ကို ဒီဇိုင်းဆွဲနေစဉ် i18n patch များကို တိကျပြီး အနည်းဆုံးသာ ပြုလုပ်ပါ။ Task က generated translation များကို
အတိအကျလိုအပ်ပြီး ထွက်ပေါ်လာသော diff ကို သင် review လုပ်ပြီးသား မဟုတ်ပါက external service များကို ခေါ်ဆိုသည့် translation
command များကို မ run ပါနှင့်။

### CLI

**Contracts**

- `bin/cli/` ရှိ အများသုံး command များနှင့် flag များ၊ ထုတ်လုပ်ထားသော API command များ၊ exit code များ၊ stdout/stderr နှင့်
  JSON output ပုံစံများ၊ config/environment အပြုအမူနှင့် package တွင် ပါဝင်သော file များ။
- CLI အသုံးပြုသူမြင်ရသည့် string များသည် CLI i18n layer ကို အသုံးပြုရမည်ဖြစ်ပြီး `en`/`pt-BR` catalog များကို တစ်ပြေးညီ ထိန်းသိမ်းထားရမည်။
- Node ကို ပံ့ပိုးထားသော runtime အဖြစ်နှင့် ထုတ်ဝေထားသော binary contract ကို ဆက်လက်ထိန်းသိမ်းပါ။

**အဓိကထား စစ်ဆေးသည့် လုပ်ငန်းစဉ်**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # ထုတ်လုပ်ထားသော/စုစည်းထားသော CLI ပြောင်းလဲမှုများ
npm run check:pack-policy     # package မျက်နှာပြင်ဆိုင်ရာ ပြောင်းလဲမှုများ
npm run lint
```

အပြုအမူသည် parsing၊ file များ သို့မဟုတ် exit status ပေါ် မူတည်သည့်အခါ ယာယီ data directory တစ်ခုအတွင်း command အတိအကျကို အသုံးပြုပါ။ CI သည် ပိုမိုကျယ်ပြန့်သော package artifact နှင့် ecosystem စစ်ဆေးမှုများကို ဆောင်ရွက်သည်။

### Database

**Contract များ**

- `src/lib/db/` အောက်ရှိ domain module များ၊ သီးခြား module များကို တိုက်ရိုက် import လုပ်ပါ (`localDb.ts` re-export layer အဟောင်းကို ဖယ်ရှားပြီးဖြစ်သည်)။
- `src/lib/db/migrations/` အောက်ရှိ နံပါတ်စဉ်တပ်ထားပြီး idempotent ဖြစ်သော SQL migration များ၊ transaction ဘေးကင်းမှု၊ upgrade
  အပြုအမူ၊ index များနှင့် schema ကြောင့် သက်ရောက်မှုရှိသော caller အားလုံး။
- Route များနှင့် handler များသည် raw SQL ကို တိုက်ရိုက် လုံးဝ မထုတ်ပြန်ရ။

**အဓိကထား စစ်ဆေးသည့် လုပ်ငန်းစဉ်**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Migration တစ်ခု ထည့်သွင်းသည့်အခါ database အသစ်နှင့် ယခင် schema မှ upgrade လုပ်ခြင်း နှစ်မျိုးစလုံးကို စမ်းသပ်ပါ။ Database test များသည် cleanup ပြုလုပ်နေစဉ် handle များကို ပိတ်ပြီး `resetDbInstance()` ကို ခေါ်ရမည်။ အကောင်းဆုံးကြိုးပမ်းမှုအဖြစ်ထားရှိသော Bun adapter လမ်းကြောင်း ပြောင်းလဲသည့်အခါမှသာ `npm run test:bun:db` ကို run ပါ၊ Node သည် အတည်ပြုဆုံး စံအဖြစ် ဆက်ရှိသည်။

### Build / deploy

**Contract များ**

- Root နှင့် workspace manifest/lockfile များ၊ `scripts/build/`၊ Next.js standalone စုစည်းမှု၊ `dist/`
  package အကြောင်းအရာများ၊ Electron platform metadata၊ CI workflow များနှင့် deployment sentinel များ။
- ပံ့ပိုးထားသော Node range များနှင့် `CLAUDE.md` တွင် allow-list ထည့်ထားသော Bun အသုံးပြုမှုကို မပျက်မကွက် ထိန်းသိမ်းထားရမည်။
- Build artifact များကို track မလုပ်ထားရ၊ dependency၊ license၊ workflow နှင့် package policy များကို လိုက်နာရမည်။

**အဓိကထား စစ်ဆေးသည့် လုပ်ငန်းစဉ်**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency သို့မဟုတ် lockfile ပြောင်းလဲမှုများ
npm run check:pack-policy      # ထုတ်ဝေထားသော package မျက်နှာပြင်ဆိုင်ရာ ပြောင်းလဲမှုများ
npm run lint
```

ပြောင်းလဲမှုသည် compilation၊ standalone စုစည်းမှု၊ asset များ သို့မဟုတ် runtime bundling ကို သက်ရောက်သည့်အခါမှသာ local တွင် `npm run build` ကို အသုံးပြုပါ။ Release/deploy အတည်ပြုခြင်းအတွက်သာ `npm run build:release` ကို အသုံးပြုပါ။ CI ၏ build သည် နောက်ဆုံး cross-platform အချက်ပြမှုဖြစ်ပြီး platform-specific Electron ပြောင်းလဲမှုများအတွက် သက်ဆိုင်ရာ focused build သို့မဟုတ် smoke အထောက်အထား လိုအပ်သည်။

## ဒေသတွင်း candidate လုပ်ငန်းစဉ်

Source test များက packaged artifact ကို အမှန်တကယ် စတင်နိုင်ကြောင်း သက်သေမပြနိုင်ပါ။ packaging list များ၊ ဖယ်ရှားထားသော dependency များနှင့် native binary များ၏ ပြဿနာများသည် tarball ကို install လုပ်ပြီး စတင်သည့်အခါမှသာ ပေါ်လာပါသည်။ `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) သည် RFC #8084 ရှိ build-once / validate / promote လုပ်ငန်းစဉ်၏ ဒေသတွင်းဘက်ခြမ်းဖြစ်သည်။ ၎င်းသည် candidate တစ်ခုကို build လုပ်ပြီး ထို artifact အတိအကျကို validate လုပ်ကာ directory အမည်ပြောင်းခြင်းများဖြင့် promote လုပ်ပြီး၊ promote လုပ်ထားသော slot ၏ health check မအောင်မြင်ပါက rollback ပြန်လုပ်ပေးသည်။

```bash
npm run dev:candidate -- run --dry-run --json  # အစီအစဉ်ကို ပြသပြီး မည်သည့်အရာကိုမျှ မပြောင်းလဲပါ
npm run dev:candidate -- run                   # build + validate + promote လုပ်ပြီး အလိုအလျောက် rollback လုပ်ပါ
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ ထဲသို့ install လုပ်ပါ
npm run dev:candidate -- validate --id <id>    # အားနေသော port တစ်ခုပေါ်တွင် စတင်ပြီး /api/health + /v1/models ကို စစ်ဆေးပါ
npm run dev:candidate -- promote --id <id>     # <id> → current၊ current → previous
npm run dev:candidate -- rollback              # current နှင့် previous ကို နေရာလဲပါ
npm run dev:candidate -- run --from-tarball <file.tgz>  # အခြားနေရာတွင် build လုပ်ထားသော tarball ကို ပြန်လည်အသုံးပြုပါ (CI)
```

- **တစ်ကြိမ်သာ build လုပ်ပါ။** `build` သည် လက်ရှိ tree ကို package လုပ်သည် (၎င်းအတွက် `dist/server.js` လိုအပ်သောကြောင့်
  `npm run build:release` ကို ဦးစွာ run ပါ) သို့မဟုတ် `--from-tarball` ကို copy လုပ်ပြီး၊ ထို့နောက် tarball တွင် `node_modules` မပါဝင်သောကြောင့် tarball ကို သီးခြားခွဲထားသည့် npm prefix တစ်ခုထဲသို့ install လုပ်သည်။ id သည် `HEAD` ၏ အတိုကောက် sha ဖြစ်ပြီး (tree တွင် ဒေသတွင်းအပြောင်းအလဲများရှိပါက `-dirty` ပါဝင်မည်) tarball အတွက်မူ `tgz-<sha256>` ဖြစ်သည်။ build လုပ်ပြီးသား clean id တစ်ခုကို ပြန်လည် build မလုပ်ဘဲ ပြန်လည်အသုံးပြုသည်။ ၎င်းကို ပြန်လည် build လုပ်ရန် `--force` ကို ထည့်သွင်းပါ။
- **Source ကိုမဟုတ်ဘဲ package ကို validate လုပ်ပါ။** `validate` သည် install လုပ်ထားသော CLI
  (`serve --port <free port>`) ကို အသစ်ဖန်တီးထားသည့် `DATA_DIR=<candidate>/data`၊ အတု secret များဖြင့် စတင်ပြီး operator ၏ `OMNIROUTE_API_KEY`၊ `STORAGE_ENCRYPTION_KEY` နှင့် `INITIAL_PASSWORD` တို့ကို environment မှ ဖယ်ရှားထားသည်။ ထို့ကြောင့် fresh install တစ်ခု၏ key မလိုသော loopback အခြေအနေကို စစ်ဆေးနိုင်သည်။ ၎င်းသည်
  `GET /api/health` က 200 ပြန်ပေးသည်အထိ စောင့်ပြီး `GET /v1/models` က 200 ပြန်ပေးရန် လိုအပ်ကြောင်း သတ်မှတ်ကာ process group ကို ရပ်တန့်ပြီး ရလဒ်ကို tarball hash နှင့်အတူ `validation.json` တွင် မှတ်တမ်းတင်သည်။
- **တူညီသော artifact ကို promote လုပ်ပါ။** `promote` သည် ၎င်း၏ လက်ရှိ tarball hash အတွက် အောင်မြင်သော validation မရှိသည့် candidate ကို လက်မခံပါ။ မူလ active slot သည် `_artifacts/candidate/current` ဖြစ်သည်။ `--target <dir>` သည် တူညီသော filesystem ပေါ်ရှိ အခြား directory တစ်ခုကို ရွေးချယ်ပြီး ၎င်း၏ previous slot သည် `<dir>.previous` ဖြစ်သည်။ rename တစ်ခုချင်းစီသည် atomic ဖြစ်ပြီး လုပ်ငန်းစဉ်အလယ်တွင် မအောင်မြင်ပါက လုပ်ဆောင်ပြီးသား rename များကို ပြန်လှန်ပေးသည်။
- **Rollback ပြန်လုပ်ပါ။** `run` သည် promote လုပ်ထားသော slot ကို ထပ်မံ validate လုပ်ပြီး ထိုစစ်ဆေးမှု မအောင်မြင်ပါက `current` နှင့် `previous` ကို မူလနေရာသို့ ပြန်လဲပေးသည်။ ပထမ validation မအောင်မြင်သော candidate ကို မည်သည့်အခါမျှ promote မလုပ်ပါ။

အရာအားလုံးကို gitignore လုပ်ထားသည့် `_artifacts/candidate/` အောက်တွင် ရေးသားသည်။ ရှိပြီးသား OmniRoute installation နှင့် ၎င်း၏ data directory ကို မည်သည့်အခါမျှ ထိခိုက်မည်မဟုတ်ပါ။ Promote လုပ်ထားသော CLI သည်
`_artifacts/candidate/current/prefix/bin/omniroute` ဖြစ်သည်။ ၎င်းကို အသုံးပြုသည့်အခါ သင့်ကိုယ်ပိုင် `DATA_DIR` ဖြင့် စတင်ပါ။ Exit code များမှာ `0` သည် အောင်မြင်ခြင်း၊ `1` သည် validation သို့မဟုတ် promotion မအောင်မြင်ခြင်း၊ `2` သည် အသုံးပြုပုံအမှား သို့မဟုတ် build မရှိခြင်းကို ဆိုလိုသည်။

| သက်ရောက်မှုရှိသော contract က လိုအပ်သည့်အခါမှသာ typecheck သို့မဟုတ် build လုပ်ရန်                                   | ထုတ်လုပ်မှု build၊ လုံခြုံရေး၊ docs၊ dependency နှင့် PR-policy စစ်ဆေးဂိတ်များ         |
| automation ဖြင့် အပြုအမူကို သက်သေမပြနိုင်သည့်အခါမှသာ ကိုယ်တိုင် အပြန်အလှန်စမ်းသပ်မှု/live စစ်ဆေးမှုများ ပြုလုပ်ရန် | workflow ဖြင့် သတ်မှတ်ထားသော job အချင်းချင်း ပေါင်းစည်းမှုနှင့် platform စစ်ဆေးမှုများ |

အာရုံစိုက်ထားသော စက်တွင်း လည်ပတ်စမ်းသပ်မှု အောင်မြင်ခြင်းသည် ပြောင်းလဲထားသော contract နှင့် ပတ်သက်သည့် အထောက်အထားဖြစ်ပြီး၊ မသက်ဆိုင်သော CI စစ်ဆေးမှုများ
အောင်မြင်မည်ဟု သက်သေပြခြင်း မဟုတ်ပါ။ အပြန်အလှန်အားဖြင့် စက်တွင်းပြင်ဆင်မှုတိုင်းကို repository matrix အပြည့်အစုံ ပြီးဆုံးသည်အထိ မစောင့်ဆိုင်းပါနှင့်။

## ပြန်လည်ညှိနှိုင်းစစ်ဆေးရန် စာရင်း

ပြန်လည်သုံးသပ်ပေးရန် မတောင်းဆိုမီ-

- PR base သည် အသုံးပြုနေဆဲ `release/v*` branch များအနက် အမြင့်ဆုံးဖြစ်နေသေးကြောင်း အတည်ပြုပါ။
- ထို base ကို fetch လုပ်ပြီး သင် branch ခွဲထွက်ပြီးနောက် ထည့်သွင်းခဲ့သော commit များကို ပြန်လည်သုံးသပ်ပါ။
- မတော်တဆ သို့မဟုတ် အလိုအလျောက် ထုတ်လုပ်ထားသော မလိုလားအပ်သည့် အပြောင်းအလဲများ ရှိမရှိ စစ်ဆေးရန် `git diff <active-base>...HEAD` ကို ပြန်လည်သုံးသပ်ပါ။
- source ကို update လုပ်ပြီး output ကို ပြန်လည် generate လုပ်ခြင်းဖြင့် catalog နှင့် အလိုအလျောက် ထုတ်လုပ်ထားသော document conflict များကို ဖြေရှင်းပါ။
- ပြန်လည်ညှိနှိုင်းပြီးနောက် PR ဖော်ပြချက်တွင် စာရင်းပြုစုထားသော အာရုံစိုက်စမ်းသပ်မှု/စစ်ဆေးဂိတ်တိုင်းကို ပြန်လည်လုပ်ဆောင်ပါ။
- ပြောင်းလဲသွားသော base နှင့် ကိုက်ညီစေရန်သာ assertion များကို မည်သည့်အခါမျှ အားမလျှော့ပါနှင့် သို့မဟုတ် လိုအပ်သော စမ်းသပ်မှုများကို မဖယ်ရှားပါနှင့်။
