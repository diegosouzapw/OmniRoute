Homologation VPS ပေါ်တွင် လည်ပတ်နေသော OmniRoute deploy ကို လက်တွေ့ပတ်ဝန်းကျင်၌ E2E စစ်ဆေးအတည်ပြုခြင်း
(`HOMOLOG_BASE_URL`၊ ဥပမာ `http://192.168.0.15:20128`)။ Command တစ်ခုတည်းဖြင့် release STOP #2 ကို ကိုယ်တိုင်စစ်ဆေးရသည့် checklist အစား အထောက်အထားများ အလိုအလျောက်ထုတ်ပေးသော run တစ်ခုဖြင့် အစားထိုးပေးသည်။

AI သည် အနာဂတ် maintenance လုပ်ငန်းများတွင်သာ ပါဝင်မည် (အောက်ရှိ Roadmap ကို ကြည့်ပါ)။

## ကြိုတင်လိုအပ်ချက်များ

1. `.env.homolog.example` ကို `.env.homolog` သို့ ကူးယူပြီး (gitignored ဖြစ်သောကြောင့် လုံးဝ commit မလုပ်ပါနှင့်) အောက်ပါတို့ကို ဖြည့်ပါ-
   - `HOMOLOG_BASE_URL` — ပစ်မှတ် deploy၊ ဥပမာ `http://192.168.0.15:20128`။
   - `HOMOLOG_ADMIN_PASSWORD` — ထို deploy အတွက် dashboard စီမံခန့်ခွဲမှု စကားဝှက်။
   - `HOMOLOG_CRITICAL_PROVIDERS` — အမှန်တကယ် smoke chat request ရရှိမည့် ကော်မာဖြင့် ခွဲထားသော provider prefix များ
     (ဥပမာ `openai,anthropic,gemini,codex,grok,glm,deepseek,openrouter`)။
   - `HOMOLOG_API_KEY` — ပုံမှန် run များတွင် ဗလာထားပါ။ suite သည် ၎င်း၏ကိုယ်ပိုင် ယာယီ key ကို ဖန်တီးပြီး ပြန်လည်ရုပ်သိမ်းပါသည်။
     သီးခြား layer တစ်ခုတည်းကို အခြားအရာများနှင့် ခွဲ၍ debug လုပ်ရန်သာ ဤတန်ဖိုးကို သတ်မှတ်ပါ။
2. Repo အတွင်း `npm install` ကို run ပါ (suite ၏ dependency များဖြစ်သော `httpyac`, `promptfoo`,
   `playwright-ctrf-json-reporter`, `junit-to-ctrf`, `ctrf` တို့သည် ပုံမှန် devDependencies များဖြစ်သည်)။
3. Browser binary များ မရှိသေးပါက `npx playwright install` ကို run ပါ။

## Run ပြုလုပ်နည်း

```bash
npm run homolog
```

Local `package.json` နှင့် version မကိုက်ညီသော deploy တစ်ခုကို စစ်ဆေးရန်
(ဥပမာ ယခင် patch release တွင် ရှိနေသေးသော homologation box) မျှော်မှန်းထားသည့်
version ကို အောက်ပါအတိုင်း အတိအကျ override လုပ်ပါ-

```bash
HOMOLOG_EXPECT_VERSION=3.8.47 npm run homolog
```

Layer တစ်ခုခု မအောင်မြင်ပါက run သည် non-zero ဖြင့် ထွက်မည်ဖြစ်ပြီး ပျက်ကွက်ခဲ့လျှင်ပင်
၎င်းဖန်တီးထားသော ယာယီ API key ကို အမြဲတမ်း ပြန်လည်ရုပ်သိမ်းရန် ကြိုးစားပါသည်
(`scripts/homolog/run.mjs` ရှိ `finally` block)။

## Report ကို ဖတ်ရှုခြင်း

Output အားလုံးကို `homolog-report/` (gitignored) တွင် ထည့်သွင်းထားသည်-

- `summary.md` — stdout သို့ print ထုတ်ထားသည့် table နှင့် တူညီပြီး layer တစ်ခုလျှင် row တစ်ခု
  (✅/❌ + အသေးစိတ်) ဖြစ်သည်။
- `homolog-ctrf.json` — ပေါင်းစည်းထားသော CTRF report (API/SSE၊ provider-smoke နှင့်
  UI ရလဒ်များကို ပေါင်းစည်းထားခြင်း) — ၎င်းသည် release STOP #2 checklist တွင် ပူးတွဲရမည့် artifact ဖြစ်သည်။
- `httpyac-junit.xml`, `api-ctrf.json`, `providers-ctrf.json`, `ui-ctrf.json` — layer
  တစ်ခုချင်းစီအတွက် raw/intermediate report များ။
- `promptfooconfig.yaml`, `provider-misses.json` — လက်ရှိ run အတွက် ထုတ်လုပ်ထားသော promptfoo config နှင့်
  live catalog တွင် ပျောက်ဆုံးနေသည့် အရေးကြီး provider များ။

L0 မအောင်မြင်ပါက ချက်ချင်း ရပ်ဆိုင်းသည် (ယာယီ key ကို မဖန်တီးပါ)။ အဘယ်ကြောင့်ဆိုသော် version/health
မကိုက်ညီခြင်းသည် နောက်ဆက်တွဲ layer တိုင်းက မှားယွင်းသော deploy ကို စစ်ဆေးနေမည်ဟု ဆိုလိုသောကြောင့်ဖြစ်သည်။

## UI သည် တရားဝင်ပြောင်းလဲသည့်အခါ baseline ကို ပြန်လည်သတ်မှတ်ခြင်း

L4b (route smoke) နှင့် L4c (API-key UI flow) တို့သည် snapshot များမဟုတ်ဘဲ အမှန်တကယ် DOM locator များဖြင့်
လည်ပတ်သောကြောင့် တရားဝင် UI ပြောင်းလဲမှုအများစုအတွက် suite ကို update လုပ်ရန် မလိုအပ်ပါ။ ပြောင်းလဲမှုတစ်ခုကြောင့်
locator ပျက်သွားသည့်အခါ (ဥပမာ အမည်ပြောင်းထားသော button label သို့မဟုတ် နေရာရွှေ့ထားသော settings page)-

1. လက်ရှိ source နှင့် locator ကို ထပ်မံအတည်ပြုပါ (spec များတွင် locator တစ်ခုစီကို မည်သည့်
   file/line နှင့် အတည်ပြုထားသည်ကို မှတ်တမ်းတင်ထားပြီးဖြစ်သည် — အလားတူပုံစံကို လိုက်နာပါ၊ မခန့်မှန်းပါနှင့်)။
2. `tests/homolog/ui/` ရှိ spec ကို update လုပ်ပါ။
3. ပြင်ဆင်မှုကို အတည်ပြုရန် VPS နှင့် ယှဉ်၍ `npm run homolog` (သို့မဟုတ် သက်ရောက်မှုရှိသော Playwright spec ကိုသာ)
   ပြန် run ပြီးနောက် commit လုပ်ပါ။

ဤ suite (F1) တွင် visual/pixel baseline မရှိပါ — ယင်းအတွက် Roadmap ကို ကြည့်ပါ။

## လမ်းပြမြေပုံ (F2 / F3)

ဒီဇိုင်းနှင့် အဆင့်လိုက် rollout ကို internal planning spec
`_tasks/superpowers/specs/2026-07-13-homolog-e2e-suite-design.md` တွင် ထည့်သွင်းထားသည် (link မချိတ်ထားပါ — internal
`_tasks/` artifact ဖြစ်ပြီး ဤ repo ၏ tracked docs အစိတ်အပိုင်း မဟုတ်ပါ)။ အကျဉ်းချုပ်-

- **F2** — walkthrough အပြည့်အစုံကို record လုပ်ခြင်း → Playwright Test Agents (`planner`/`generator`) က
  ၎င်းကို flow spec များ (combo ဖန်တီးခြင်း၊ provider စမ်းသပ်ခြင်း၊ settings တည်းဖြတ်ခြင်း၊ MCP tools) အဖြစ် ပြောင်းလဲခြင်း +
