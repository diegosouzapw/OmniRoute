## ခြုံငုံသုံးသပ်ချက်

OmniRoute သည် request များ upstream provider များထံ မရောက်ရှိမီ **ကြိုတင်လုပ်ဆောင်သည့်** modular prompt compression pipeline တစ်ခုကို အကောင်အထည်ဖော်ထားသည်။ ဆိုလိုသည်မှာ token ချွေတာမှုကို မသိသာဘဲ အလိုအလျောက် ရရှိမည်ဖြစ်ပြီး သင်၏ workflow ကို ပြောင်းလဲရန် မလိုအပ်ပါ။

```
Client Request
  → Compression Strategy Selector
    → Combo override ရှိသလား? → combo setting ကို အသုံးပြုရန်
    → Auto-trigger threshold ပြည့်သလား? → auto mode ကို အသုံးပြုရန်
    → Default mode ရှိသလား? → global setting ကို အသုံးပြုရန်
    → Off ဖြစ်သလား? → compression ကို ကျော်ရန်
  → ရွေးချယ်ထားသော Compression Mode
    → Off: Compression မပြုလုပ်ပါ
    → Lite: ဘေးကင်းသော whitespace/formatting ရှင်းလင်းမှု (~15%)
    → Standard: Caveman ပုံစံ မလိုအပ်သည့် စကားလုံးများ ဖယ်ရှားမှု (~30%)
    → Aggressive: History aging + အကျဉ်းချုပ်ခြင်း (~50%)
    → Ultra: Heuristic pruning + code-block thinning (~75%)
    → RTK: Command ကို နားလည်သော terminal/tool-output စစ်ထုတ်မှု (upstream အပိုင်းအခြား 60-90%)
    → Stacked: အစီအစဉ်တကျ multi-engine pipeline၊ ပုံမှန်အားဖြင့် RTK ပြီးနောက် Caveman (သတ်မှတ်ချက်နှင့် ကိုက်ညီသော အပိုင်းအခြား 78-95%)
  → ချုံ့ထားသော Request → Provider
```

## Compression Mode များ

### Off

Compression မပြုလုပ်ပါ။ Message အားလုံးကို ပြောင်းလဲခြင်းမရှိဘဲ ဖြတ်သန်းစေသည်။

### Lite Mode (~15% ချွေတာမှု၊ latency <1ms)

အလုံခြုံဆုံး mode ဖြစ်ပြီး အဓိပ္ပာယ်ပိုင်းဆိုင်ရာ ပြောင်းလဲမှု လုံးဝမရှိဘဲ formatting ကိုသာ ရှင်းလင်းသည်-

| နည်းလမ်း                 | ဖော်ပြချက်                                                                        |
| ------------------------ | --------------------------------------------------------------------------------- |
| `collapseWhitespace`     | ဆက်တိုက်ဖြစ်နေသော စာကြောင်းလွတ်များနှင့် နောက်ဆုံးရှိ space များကို ပေါင်းစည်းသည် |
| `dedupSystemPrompt`      | ထပ်နေသော system message များကို ဖယ်ရှားသည်                                        |
| `compressToolResults`    | စာရှည်သော tool/function output များကို ချုံ့သည်                                   |
| `removeRedundantContent` | ထပ်ခါတလဲလဲပါသော ညွှန်ကြားချက်များကို ဖယ်ရှားသည်                                   |
| `replaceImageUrls`       | base64 image data URI များကို အတိုချုံ့သည်                                        |

**အသင့်တော်ဆုံး:** အမြဲဖွင့်ထားသော အသုံးပြုမှုနှင့် ဘေးကင်းလုံခြုံရေး အလွန်အရေးကြီးသော workflow များ။

### Standard Mode (~30% ချွေတာမှု)

[Caveman](https://github.com/JuliusBrussee/caveman) ကို အခြေခံထားပြီး အဓိပ္ပာယ်ကို ထိန်းသိမ်းလျက် မလိုအပ်သော စကားလုံးများနှင့် စကားရှည်အသုံးအနှုန်းများကို ဖယ်ရှားသည်-

- မလိုအပ်သော စကားလုံးများ ("please", "I think", "basically", "actually") ကို ဖယ်ရှားသည်
- စကားရှည်အသုံးအနှုန်းများကို တိုစေသည် ("in order to" → "to", "as a result of" → "because")
- ယဉ်ကျေးသိမ်မွေ့စွာ မရေမရာပြောဆိုမှုများ ("Would you mind...", "If you could possibly...") ကို ဖယ်ရှားသည်
- coding prompt များအတွက် ချိန်ညှိထားသော regex rule 30 ကျော် ပါဝင်သည်

**အသင့်တော်ဆုံး:** နေ့စဉ် coding workflow များနှင့် ကုန်ကျစရိတ်ကို အလေးထားသော အဖွဲ့များ။

### Aggressive Mode (~50% ချွေတာမှု)

ကြာရှည် session များအတွက် စမတ်ကျသော history စီမံခန့်ခွဲမှု-

- **Message Aging** — message အဟောင်းများကို တဖြည်းဖြည်း ပိုမိုချုံ့သည်
- **Tool Result Summarization** — ရှည်လျားသော tool output များကို အကျဉ်းချုပ်များဖြင့် အစားထိုးသည်
- **Structural Integrity Guards** — `tool_use` + `tool_result` အတွဲများ တစ်သမတ်တည်းရှိကြောင်း သေချာစေသည်
- **Context Window Awareness** — model တစ်ခုချင်းစီ၏ token ကန့်သတ်ချက်များကို လိုက်နာသည်

**အသင့်တော်ဆုံး:** ရက်ရှည် debugging session များနှင့် ကြီးမားသော codebase များ။

### Ultra Mode (~75% ချွေတာမှု)

Token အလွန်အရေးကြီးသော အခြေအနေများအတွက် အမြင့်ဆုံး compression-

- **Heuristic Pruning** — ဆက်စပ်မှု threshold အောက်ရှိ message များကို ဖယ်ရှားသည်
- **Code Block Thinning** — ထပ်တလဲလဲဖြစ်နေသော code ဥပမာများကို ချုံ့သည်
- **Binary Search Truncation** — context window အတွက် အကောင်းဆုံး ဖြတ်တောက်ရမည့်နေရာကို ရှာဖွေသည်
- Aggressive mode ၏ feature အားလုံး ပါဝင်သည်

**အသင့်တော်ဆုံး:** Context limit ကို ထပ်ခါတလဲလဲ ပြည့်သွားသည့်အခါ။

### RTK Mode (upstream အပိုင်းအခြား 60-90%)

RTK mode ကို coding-agent session များတွင် ပေါ်လာသည့် စာရှည်သော tool output များအတွက် အထူးပြုထားသည်-

- `git status`, `git diff`, `git log`, test runner များ၊
  TypeScript/Vite/Webpack build များ၊ ESLint/Biome/Prettier၊ npm audit/install များ၊ Docker log များ၊ infra
  output နှင့် ယေဘုယျ shell output ကဲ့သို့ command/output အမျိုးအစားများကို ရှာဖွေသိရှိသည်
- `open-sse/services/compression/engines/rtk/filters/` မှ JSON filter pack များကို အသုံးပြုသည်
- Project သို့မဟုတ် global `filters.toml` file များမှ RTK TOML schema v1 filter များကို inline-test
  validation နှင့် project file များအတွက် trust-gating တို့ဖြင့် import လုပ်သည်
- Inline verify sample များပါဝင်သော built-in filter 49 ခုကို ထည့်သွင်းပေးထားသည်
- ANSI control sequence များ၊ progress bar များ၊ ထပ်နေသော စာကြောင်းများနှင့် အရေးယူရန်မလိုသော noise များကို ဖယ်ရှားသည်
- Failure များ၊ error များ၊ warning များ၊ ပြောင်းလဲထားသော file များ၊ အကျဉ်းချုပ်များနှင့် ရှည်လျားသော output ၏ နောက်ဆုံးပိုင်းကို ထိန်းသိမ်းထားသည်
- Trust-gated project filter များ၊ global filter များနှင့် ရွေးချယ်နိုင်သော redacted raw-output recovery ကို ပံ့ပိုးသည်

**အသင့်တော်ဆုံး:** Shell၊ build၊ test၊ git၊ grep နှင့် file-output transcript များ ပါဝင်သော agent session များ။

### Stacked Mode (သတ်မှတ်ချက်နှင့် ကိုက်ညီသော အပိုင်းအခြား 78-95%)

Stacked mode သည် compression engine အများအပြားကို တိကျသတ်မှတ်ထားသော အစီအစဉ်အတိုင်း လုပ်ဆောင်သည်။ မူလ pipeline မှာ-

```txt
RTK -> Caveman
```

ထိုအစီအစဉ်သည် terminal/tool output ကို ဦးစွာ ကျစ်လျစ်စေပြီးနောက် ကျန်ရှိသော သဘာဝဘာသာစကား prompt အပေါ် Caveman semantic condensation ကို အသုံးပြုသည်။ Stacked pipeline များကို global အနေဖြင့်ဖြစ်စေ၊ routing combo များတွင် သတ်မှတ်ထားသော compression combo များမှတစ်ဆင့်ဖြစ်စေ ပြင်ဆင်သတ်မှတ်နိုင်သည်။

**အသင့်တော်ဆုံး:** ကြီးမားသော tool log များနှင့် လူသား၏ ညွှန်ကြားချက်များ သို့မဟုတ် assistant အကျဉ်းချုပ်များ ရောနှောပါဝင်သော context များ။

## Upstream ချွေတာမှု တွက်ချက်ပုံ

OmniRoute သည် ချုံ့ခြင်းကြောင့် ရရှိသည့် ချွေတာမှုများကို ရင်းမြစ်နှစ်ခုဖြစ်သော upstream ပရောဂျက် benchmark များနှင့်
OmniRoute ၏ ကိုယ်ပိုင် engine ပေါင်းစပ်မှုတို့မှ မှတ်တမ်းတင်ဖော်ပြထားသည်။

| ရင်းမြစ် | ဤနေရာတွင် အသုံးပြုထားသည့် Upstream README ကိန်းဂဏန်း                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman  | output token `~75%` ပိုနည်းခြင်း၊ benchmark ပျမ်းမျှ output ချွေတာမှု `65%`၊ အပိုင်းအခြား `22-87%` နှင့် input ချုံ့ခြင်း tool `~46%` |
| RTK      | command output ချွေတာမှု `60-90%`၊ နမူနာ session တွင် token `~118,000 -> ~23,900` သို့မဟုတ် `79.7%` ချွေတာမှု (`~80%`)                |

ထပ်နေသော tool/context payload များအတွက် ပုံသေ OmniRoute ပေါင်းစပ်မှုသည် engine များကို အောက်ပါအတိုင်း အဆင့်ဆင့် အသုံးပြုသည်-

```txt
RTK -> Caveman
```

ပေါင်းစပ်ချွေတာမှုသည် ပေါင်းခြင်းမဟုတ်ဘဲ မြှောက်ခြင်းပုံစံဖြင့် တွက်ချက်သည်-

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ထို `78-95%` ကိန်းဂဏန်းသည် RTK နှင့် Caveman နှစ်ခုစလုံးက တူညီသော input/context payload ကို လျှော့ချနိုင်သည့်အခါတွင် အကျုံးဝင်သည်။
Caveman ၏ response output mode သည် သီးခြားဖြစ်သည်။ ၎င်းကို ဖွင့်ထားသည့်အခါ Caveman ၏ ကိုယ်ပိုင် output ချွေတာမှုများ (ပျမ်းမျှ `65%`၊
အဓိကဖော်ပြချက် `~75%`၊ အပိုင်းအခြား `22-87%`) ကို အသုံးပြုပါ။ စုစုပေါင်း billing ချွေတာမှုသည် သင်၏ prompt/output အချိုးအစားပေါ် မူတည်သည်။

### "eligible" ဟူသည် အမှန်တကယ် ဘာကို ဆိုလိုသနည်း

အဓိကဖော်ပြထားသော 15-95% အပိုင်းအခြားသည် အမှန်ဖြစ်သော်လည်း **ထပ်နေသော သို့မဟုတ် အလွန်ရှည်လျားသော** အကြောင်းအရာများအတွက်သာ အကျုံးဝင်သည် — ထပ်ခါတလဲလဲဖြစ်နေသော
error စာကြောင်းများ၊ တူညီသော warning ကို အလွန်အကျွံ ထုတ်ပြသည့် build log၊ အရွယ်အစားအလွန်ကြီးသော `grep`/file-read dump တို့ဖြစ်သည်။ ၎င်းသည်
request တိုင်းတွင် ထိုမျှလောက် ချွေတာနိုင်သည်ဟု **မ** ဆိုလိုပါ။

လက်တွေ့စမ်းသပ်ပြီး အတည်ပြုထားသည် (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`)။ တူညီသော
error စာကြောင်း 300 ပါဝင်သည့် Anthropic ပုံစံ `tool_result` block အပေါ် `stacked` (RTK + Caveman) run တစ်ခုက
**token ချွေတာမှု 95.93% / character ချွေတာမှု 96.26%** ကို ရရှိစေခဲ့ပြီး ကြော်ငြာထားသည့်
အပိုင်းအခြားအတွင်း အပြည့်အဝ ရှိနေသည်။ သို့သော် တူညီသော pipeline ကို ပုံမှန်၊ မထပ်နေသော tool output (ရှင်းလင်းသည့် `grep` ကိုက်ညီမှုစာရင်း၊
တိုတောင်းသော file read၊ ပုံမှန် စကားပြောစာသား) အပေါ် run သည့်အခါတွင် မှန်ကန်စွာ **သုညနီးပါး ချွေတာမှု** သာ ရရှိသည်။ အဘယ်ကြောင့်ဆိုသော်
ဖယ်ရှားရန် ထပ်နေသောအရာ မရှိသည့်အပြင် `validateCompression()` (`validation.ts`) သည် code block များ၊ URL များ၊ heading များ၊ version များ သို့မဟုတ် ALL-CAPS constant identifier များကို ဖယ်ရှားခြင်း သို့မဟုတ် ပြောင်းလဲခြင်းဖြစ်စေမည့်
ပြန်လည်ရေးသားမှုကို ပေးပို့ရန် ငြင်းပယ်သောကြောင့် ဖြစ်သည်။

၎င်းသည် မျှော်လင့်ထားသည့် ဘေးကင်းသော လုပ်ဆောင်ချက်ဖြစ်ပြီး bug မဟုတ်ပါ။ ရှင်းလင်းသော file များကို အဓိကအားဖြင့် ဖတ်ရှုခြင်း/grep လုပ်ခြင်းသာရှိသည့် coding session တစ်ခုတွင်
ချုံ့ခြင်းကို အပြည့်အဝ ဖွင့်ထားသော်လည်း စုစုပေါင်းချွေတာမှု အနည်းငယ်သာ တွေ့ရမည်ဖြစ်ပြီး၊ fail ဖြစ်နေသည့်
loop သို့မဟုတ် output အလွန်များသော linter နှင့် ကြုံတွေ့ရသည့် session တစ်ခုတွင်မူ ထို traffic အတွက် 78-95% အပိုင်းအခြားအပြည့်ကို ရရှိမည်ဖြစ်သည်။ Session တစ်ခုတည်း၏

## စီစဉ်သတ်မှတ်ခြင်း

### ဒက်ရှ်ဘုတ်

`Dashboard → Context & Cache` သို့ သွားပါ-

- **Caveman** — မုဒ်ရွေးချယ်မှု၊ ဘာသာစကားပက်ကေ့ချ်များ၊ ကြိုတင်ကြည့်ရှုခြင်းနှင့် ကမ္ဘာလုံးဆိုင်ရာ မူရင်းများ
- **RTK** — ကွန်မန်း-ဖစ်လ်တာ ကြိုတင်ကြည့်ရှုခြင်း၊ RTK ဘေးကင်းရေး ဆက်တင်များနှင့် ဖစ်လ်တာ ကတ်တလောက်
- **Compression Combos** — ရောက်တာ ကွန်ဘိုများသို့ သတ်မှတ်ထားသော အမည်ရှိ အင်ဂျင် ပိုက်လိုင်းများ
- **Auto-Trigger Threshold** — တိုကင်အရေအတွက် သတ်မှတ်ထားသော ကန့်သတ်ချက်ထက် ကျော်လွန်ပါက အလိုအလျောက် ဖိသိပ်မှုကို စတင်လုပ်ဆောင်ခြင်း

### ကွန်ဘိုတစ်ခုချင်းစီအတွက် ထပ်ဆင့်သတ်မှတ်ခြင်း

`Dashboard → Context & Cache → Compression Combos` တွင်၊ ရောက်တာ ကွန်ဘိုတစ်ခုသို့ ဖိသိပ်မှု ကွန်ဘိုတစ်ခုကို သတ်မှတ်ပါ-

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

၎င်းသည် အခမဲ့/ကုဒ်ရေးသားခြင်း ပံ့ပိုးပေးသူများတွင် စုစည်းထားသော ဖိသိပ်မှုကို အသုံးပြုနိုင်ပြီး အခပေး စာရင်းသွင်းမှုများတွင် lite မုဒ်ကို ထားရှိနိုင်စေသည်။

ဤ "Per-Combo Override" သတ်မှတ်မှုသည် **routing-combo compression mode** override (Default/Off/Lite/Standard/Aggressive/Ultra) နှင့် ကွဲပြားသော ထိန်းချုပ်မှုတစ်ခုဖြစ်သည်။ ထို override သည် အမည်ရှိ ဖိသိပ်မှု-ကွန်ဘို ပိုက်လိုင်းကို ရွေးချယ်ခြင်းမဟုတ်ဘဲ `resolveCompressionPlan` မှ တိုင်ပင်သော `compressionMode` field ကိုသာ သတ်မှတ်သည်။ ၎င်းကို ကွန်ဘိုကတ် (`Dashboard → Combos`) တွင် သို့မဟုတ် #6760 မှစ၍ `Dashboard → Context & Cache → Compression Combos` ရှိ "Assign to routing" စာရင်းတွင် ရောက်တာ ကွန်ဘိုတစ်ခုချင်းစီအတွက်၊ အထက်တွင် မှတ်တမ်းတင်ထားသော ပိုက်လိုင်း-သတ်မှတ်မှု အမှန်ခြစ်ဘောက်စ်ဘေးတွင် သတ်မှတ်နိုင်သည်။ မျက်နှာပြင်နှစ်ခုလုံးသည် တူညီသော `PUT /api/combos/{id}` endpoint မှတစ်ဆင့် ဆက်လက်တည်ရှိနေသည်။

### တောင်းဆိုမှုတစ်ခုချင်းစီအတွက် ထပ်ဆင့်သတ်မှတ်ခြင်း

တောင်းဆိုမှုတစ်ခုတည်းအတွက် ဖိသိပ်မှု အစီအစဉ်ကို ထပ်ဆင့်သတ်မှတ်ရန် `x-omniroute-compression` တောင်းဆိုမှု ခေါင်းစီးကို ပေးပို့ပါ။ ၎င်းသည် အမြင့်ဆုံး ဦးစားပေးမှုရှိသည် — ၎င်းသည် routing-combo override၊ active profile၊ auto-trigger နှင့် panel Default တို့ကို ကျော်လွန်သည်။ မသိသော တန်ဖိုးများကို လျစ်လျူရှုသည် (တောင်းဆိုမှုကို ဘယ်တော့မှ ပယ်ချမည်မဟုတ်ပါ) နှင့် ကမ္ဘာလုံးဆိုင်ရာ မာစတာခလုတ်သည် အရာအားလုံးကို ဆက်လက်ထိန်းချုပ်သည်- ဖိသိပ်မှုကို ကမ္ဘာလုံးဆိုင်ရာ ပိတ်ထားသောအခါ၊ ခေါင်းစီးသည် ၎င်းကို ဖွင့်၍မရပါ။ တန်ဖိုးများ-

| တန်ဖိုး       | အကျိုးသက်ရောက်မှု                                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `off`         | ဤတောင်းဆိုမှုအတွက် ဖိသိပ်မှုမရှိပါ။                                                                                            |
| `default`     | panel မှ ဆင်းသက်လာသော Default profile (active profile ကို လျစ်လျူရှုသည်)။ Lossy engines များကို ပိတ်ထားသည်။                    |
| `safe`        | ခေါင်းစီးကို ချန်လှပ်ထားခြင်းနှင့် တူညီသည်- dedup နှင့် whitespace folding သာ။                                                 |
| `allow-lossy` | ဤတောင်းဆိုမှု၏ operator plan ကို ထားရှိပါ၊ ၎င်းတွင် အကျဉ်းချုပ်များ၊ သက်ဆိုင်ရာ filter များနှင့် style rewrites များ ပါဝင်သည်။ |
| `engine:<id>` | ဖွင့်ထားသောအခါ အင်ဂျင်တစ်ခုတည်း၊ ဥပမာ `engine:rtk`။ ၎င်းသည် ထိုအင်ဂျင်အတွက် တောင်းဆိုမှုတစ်ခုချင်းစီ opt-in ဖြစ်သည်။           |
| `<combo>`     | အမည်ရှိ ကွန်ဘိုတစ်ခု၊ အမည်ဖြင့် (case-insensitive) ဦးစွာ ကိုက်ညီပြီးနောက် id ဖြင့် ကိုက်ညီသည်။                                 |

`allow-lossy`၊ `engine:<id>` သို့မဟုတ် အမည်ရှိ ကွန်ဘိုမပါဘဲ၊ lossy engines များကို အသုံးမပြုပါ။ ဖိသိပ်မှုကို ဖွင့်ထားသောအခါ တောင်းဆိုမှုသည် session dedup နှင့် whitespace folding ကို ဆက်လက်ရရှိသည်။

အသုံးပြုထားသော အစီအစဉ်ကို `X-OmniRoute-Compression: <mode>; source=<source>` တုံ့ပြန်မှု ခေါင်းစီးတွင် ပြန်လည်ပဲ့တင်ထပ်သည်၊ ၎င်းတွင် `<source>` သည် `request-header`၊ `routing-override`၊ `active-profile`၊ `auto-trigger`၊ `default` သို့မဟုတ် `off` တို့မှ တစ်ခုဖြစ်သည်။

## အသိအမှတ်ပြုမှုများ

Standard မုဒ်၏ ချုံ့ခြင်းစည်းမျဉ်းများသည် **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ 51K+) ဖန်တီးသော **[Caveman](https://github.com/JuliusBrussee/caveman)** — လူကြိုက်များပျံ့နှံ့ခဲ့သည့် "တိုကင်နည်းနည်းဖြင့် အလုပ်ဖြစ်လျှင် တိုကင်အများကြီးကို ဘာကြောင့်သုံးမလဲ" ပရောဂျက်မှ စိတ်ကူးရယူထားသည်။ Caveman ၏ အစီရင်ခံချက်အရ အထွက်တိုကင် `~75%` လျော့နည်းခြင်း၊ စံနှုန်းတိုင်းတာမှု ပျမ်းမျှအထွက် ချွေတာမှု `65%`၊ အထွက်အပိုင်းအခြား `22-87%` နှင့် အဝင်ချုံ့ခြင်းကိရိယာ `~46%` ရှိသည်။

RTK မုဒ်သည် **[RTK AI](https://github.com/rtk-ai)** ဖန်တီးသော **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** — terminal၊ build၊ test၊ git နှင့် tool-output စစ်ထုတ်ခြင်းတို့အတွက် စွမ်းဆောင်ရည်မြင့် command-output ချုံ့ခြင်းပရောဂျက်မှ စိတ်ကူးရယူထားသည်။ RTK ၏ အစီရင်ခံချက်အရ ချွေတာမှု `60-90%` ရှိပြီး ၎င်း၏ README နမူနာ session တွင် `~80%` ချွေတာထားကြောင်း ဖော်ပြထားသည်။

## အဆင့်မြင့် ဖိသိပ်မှုစနစ်များ

စံမုဒ် 7 ခုအပြင်၊ OmniRoute တွင် အကြောင်းအရာအခြေအနေပေါ်မူတည်၍ အလိုအလျောက် အလုပ်လုပ်သော အဆင့်မြင့် ဖိသိပ်မှုစနစ်များစွာ ပါဝင်သည်။

### ကက်ရှ်ကို ထည့်သွင်းစဉ်းစားသော ဖိသိပ်မှု

အချို့သော ဝန်ဆောင်မှုပေးသူများ (prompt caching ပါသော Anthropic ကဲ့သို့) သည် prompt ၏ အစိတ်အပိုင်းများကို ကက်ရှ်သိမ်းထားခြင်းဖြင့် ကုန်ကျစရိတ်နှင့် တုံ့ပြန်ချိန်ကို လျှော့ချပေးသည့် **prompt caching** ကို ပံ့ပိုးပေးသည်။ ကက်ရှ်သိမ်းခြင်းကို ဖွင့်ထားချိန်တွင် ပြင်းထန်သော ဖိသိပ်မှုသည် ကက်ရှ်သိမ်းထားသော token များကို ပြောင်းလဲစေပြီး ကက်ရှ်ကို အသုံးမဝင်ဖြစ်စေသောကြောင့် စွမ်းဆောင်ရည်ကို အမှန်တကယ် **ထိခိုက်စေနိုင်သည်**။

`cachingAware.ts` module သည် **ကက်ရှ်အသုံးပြုနေသည့် အခြေအနေကို ရှာဖွေသိရှိခြင်း** နှင့် ၎င်းနှင့်အညီ **ဖိသိပ်မှုနည်းဗျူဟာကို ချိန်ညှိခြင်း** ဖြင့် ဤပြဿနာကို ဖြေရှင်းပေးသည်။

#### အလုပ်လုပ်ပုံ

1. **ကက်ရှ်အသုံးပြုမှုအခြေအနေကို ရှာဖွေခြင်း** — request body အတွင်းရှိ `cache_control` marker များကို စစ်ဆေးသည်
2. **ကက်ရှ်အသုံးပြုနိုင်သော ဝန်ဆောင်မှုပေးသူများကို ခွဲခြားခြင်း** — ရည်ရွယ်ထားသော ဝန်ဆောင်မှုပေးသူသည် ကက်ရှ်သိမ်းခြင်းကို ပံ့ပိုးခြင်းရှိမရှိ စစ်ဆေးသည်
3. **နည်းဗျူဟာကို ချိန်ညှိခြင်း** — ကက်ရှ်အသုံးပြုနိုင်သော ဝန်ဆောင်မှုပေးသူများအတွက် `aggressive`/`ultra` ကို `standard` သို့ လျှော့ချသည်
4. **system prompt ကို ကျော်ခြင်း** — System prompt များကို အများအားဖြင့် ကက်ရှ်သိမ်းထားသောကြောင့် ၎င်းတို့ကို မဖိသိပ်ပါ
5. **သတ်မှတ်ရလဒ်တူညီသော ပြောင်းလဲမှုများကို အသုံးပြုခြင်း** — အမြဲတမ်း တစ်သမတ်တည်းသော output ထုတ်ပေးသည့် ပြောင်းလဲမှုများကိုသာ အသုံးပြုသည်

#### ကုဒ်နမူနာ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← ကက်ရှ် marker
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### အသုံးပြုရမည့်အချိန်

ကက်ရှ်ကို ထည့်သွင်းစဉ်းစားသော ဖိသိပ်မှုသည် **အမြဲတမ်း ဖွင့်ထားသည်** — မည်သည့် configuration မျှ မလိုအပ်ပါ။ အောက်ပါအခြေအနေများတွင်သာ စတင်အလုပ်လုပ်သည်-

- request တွင် `cache_control` marker များ ပါရှိသောအခါ
- ရည်ရွယ်ထားသော ဝန်ဆောင်မှုပေးသူသည် prompt caching ကို ပံ့ပိုးသောအခါ (Anthropic၊ OpenAI စသည်)

### အဆင့်ဆင့် အိုမင်းစေခြင်း

ရှည်လျားသော စကားဝိုင်းများတွင် message turn များစွာ စုလာသော်လည်း အဟောင်း turn များသည် တဖြည်းဖြည်း ဆက်စပ်မှုနည်းလာသည်။ `progressiveAging.ts` module သည် **turn အကွာအဝေးအလိုက် message များကို အသေးစိတ်မှု လျှော့ချသည်**-

- **မကြာသေးမီ turn များ (0-3)**: မူရင်းအတိုင်း ထားရှိသည် (အသေးစိတ်အပြည့်အစုံ)
- **အလယ်အလတ် turn များ (4-8)**: Lite compression (whitespace နှင့် formatting ရှင်းလင်းခြင်း)
- **အဟောင်း turn များ (9+)**: Caveman compression (ဖြည့်စွက်စကားလုံးများ ဖယ်ရှားခြင်း၊ အနှစ်ချုပ်ခြင်း)
- **အလွန်ဟောင်းသော turn များ (20+)**: အလွန်တိုတောင်းစွာ အနှစ်ချုပ်ခြင်း သို့မဟုတ် ဖယ်ရှားခြင်း

#### ကုဒ်နမူနာ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... နောက်ထပ် turn 50 ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // ပထမ turn 3 ခု- မူရင်းအတိုင်း
  light: 8, // Turn 4-8- lite compression
  moderate: 20, // Turn 9-20- caveman compression
  // Turn 21+- အလွန်တိုတောင်းစွာ အနှစ်ချုပ်ခြင်း
});

// saved = ချွေတာနိုင်ခဲ့သော token အရေအတွက်
```

#### အသုံးပြုရမည့်အချိန်

အဆင့်ဆင့် အိုမင်းစေခြင်းသည် `aggressive` နှင့် `ultra` မုဒ်များအတွက် **အမြဲတမ်း ဖွင့်ထားသည်**။ အောက်ပါအခြေအနေများအတွက် အထူးထိရောက်သည်-

- အချိန်ကြာမြင့်စွာ လုပ်ဆောင်နေသော coding session များ
- ရက်ပေါင်းများစွာ ကြာမြင့်သော စကားဝိုင်းများ
- tool call များစွာပါဝင်သော agentic workflow များ

### Caveman Output မုဒ်

`outputMode.ts` module သည် model ကိုယ်တိုင် ဖိသိပ်ပြီး တိုတောင်းသော output (“caveman” ပုံစံ) ထုတ်လုပ်စေရန် **system prompt ညွှန်ကြားချက်များ** ကို ထည့်သွင်းပေးသည်။

#### အလုပ်လုပ်ပုံ

input ကို ဖိသိပ်မည့်အစား ဤမုဒ်သည် အောက်ပါကဲ့သို့သော system prompt တစ်ခုကို ထည့်သွင်းသည်-

> "စကားလုံးအနည်းဆုံးဖြင့် တုံ့ပြန်ပါ။ ယဉ်ကျေးစကားများကို ချန်လှပ်ပါ။ ဝါကျတိုများကို အသုံးပြုပါ။"

ဤနည်းလမ်းသည် အောက်ပါတို့အတွက် အထူးကောင်းမွန်စွာ အလုပ်လုပ်သည်-

- ကုဒ်ထုတ်လုပ်ခြင်း (ပိုတိုသော output = token ပိုနည်းခြင်း)
- အမြန် အမေးအဖြေ (အသေးစိတ်ရှင်းလင်းချက်များ မလိုအပ်ခြင်း)
- Batch processing (throughput ကို အမြင့်ဆုံးဖြစ်စေခြင်း)

#### အသုံးပြုရမည့်အချိန်

Caveman output မုဒ်သည် **ရွေးချယ်ဖွင့်ရသော** မုဒ်ဖြစ်သည် — combo config မှတစ်ဆင့် သတ်မှတ်ပါ-

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "outputMode": "caveman"
    }
  }
}
```

#### ထည့်သွင်းပုံ

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) သည်
ရွေးချယ်မှုကို catalog နှင့် တိုက်ဆိုင်စစ်ဆေး၍ ဖြေရှင်းသတ်မှတ်သည် (မသိသော id များနှင့် locale မကိုက်ညီသော စတိုင်များကို
ဖယ်ရှားပြီး error အဖြစ် ဘယ်တော့မှ မသတ်မှတ်ပါ)၊ ရွေးချယ်ထားသော ညွှန်ကြားချက်များကို catalog အစီအစဉ်အတိုင်း ဆက်စပ်ပေါင်းစည်းကာ
ကန့်သတ်ချက် clause ကို **တစ်ကြိမ်သာ** နောက်ဆက်တွဲထည့်ပြီး block ကို idempotency
marker တစ်ခုတည်း (`[OmniRoute Output Styles]`) ဖြင့် စတင်သောကြောင့် ထပ်မံအသုံးချခြင်းက မည်သည့်ပြောင်းလဲမှုမျှ မဖြစ်စေပါ။ ဖြေရှင်းသတ်မှတ်ထားသော
ဘာသာစကားအတွက် (အောက်ပါ ဘာသာစကားရွေးချယ်မှုကို ကြည့်ပါ) ဘာသာပြန်ဆိုချက်ရှိပါက အင်္ဂလိပ်ညွှန်ကြားချက်အစား
ဒေသသုံးဘာသာစကားဖြင့် ရေးထားသော ညွှန်ကြားချက်ကို ထည့်သွင်းသည်။

`messages` ပါသော body တစ်ခုတွင် content bypass (`shouldBypassCavemanOutputMode()` ကို
`open-sse/services/compression/outputMode.ts` တွင် ကြည့်ပါ) သည် နောက်ဆုံး message သုံးခုကို စစ်ဆေးပြီး
၎င်းတို့သည် လုံခြုံရေး၊ ပြန်ပြင်မရသော လုပ်ဆောင်ချက်၊ ရှင်းလင်းချက်တောင်းခံမှု သို့မဟုတ် အစီအစဉ်အပေါ်မူတည်သော keyword များနှင့် ကိုက်ညီပါက
အဆိုပါ turn တစ်ခုလုံးအတွက် စတိုင်များကို ကျော်သွားသည်။ Dashboard ၏
**Auto-Clarity Bypass** toggle (`cavemanOutputMode.autoClarity`) ကို မည်သို့သတ်မှတ်ထားသည်ဖြစ်စေ bypass က လည်ပတ်သည်။

bypass က turn ကို ဖြတ်သန်းခွင့်ပြုသောအခါ `placeSystemInstruction()` (ဖိုင်တူတူတွင်ရှိသည်) သည်
`messages[0]` အသစ်ကို ဘယ်တော့မှ မဖန်တီးဘဲ block ကို အောက်ပါအစီအစဉ်အတိုင်း ပထမဆုံးတွေ့ရှိသည့်နေရာတွင် ထည့်သည်-

1. အစတွင်ရှိပြီး string content ပါသော system message- ၎င်း၏စာသားနောက်တွင် block ကို ဆက်ထည့်သည်။
2. ထိပ်တန်းအဆင့် `system` field- string ဖြစ်ပါက ၎င်း၏စာသားနောက်တွင် block ကို ဆက်ထည့်သည်၊ သို့မဟုတ်
   content-block array ထဲသို့ text block အသစ်အဖြစ် ထည့်သည်။
3. နောက်ပိုင်းတွင် ပထမဆုံးတွေ့ရပြီး string content ပါသော system message- ၎င်း၏
   စာသားနောက်တွင် block ကို ဆက်ထည့်သည်။
4. အထက်ပါအခြေအနေများ မရှိပါက- `messages` ၏အဆုံးတွင် system message အသစ်တစ်ခုထဲသို့ block ကို ထည့်သည်။

`messages` မပါသော body တစ်ခုတွင် block ကို string `instructions` field နောက်တွင် ဆက်ထည့်သည်၊
သို့မဟုတ် body တွင် `input` (string သို့မဟုတ် array) ပါရှိပါက `instructions` အဖြစ် သတ်မှတ်သည်။
`instructions` နှင့် `input` နှစ်ခုစလုံး မပါသော body ကို `no_messages` အဖြစ် ကျော်သွားသည်။

#### ဖွင့်သုံးပုံ

Dashboard တွင် **Context → Settings → Compression** သို့ သွားပါ—စတိုင်တစ်ခုစီအတွက်
ဖွင့်/ပိတ် toggle နှင့် အဆင့်ရွေးချယ်ကိရိယာပါသော row တစ်ခုစီ ရှိသည်။ ပရိုဂရမ်ဖြင့် သတ်မှတ်ရာတွင် compression config က
ရွေးချယ်မှုကို အောက်ပါအတိုင်း သိမ်းဆည်းထားသည်-

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

နောက်ပြန်လိုက်ဖက်ညီမှု- ယခင် `outputMode: "caveman"` ပေါင်းစပ် setting သည် ဆက်လက်အလုပ်လုပ်ပြီး
`terse-prose` သို့ mapping လုပ်သည်။ ယခင်ဘာသာစကားအားလုံးတွင် အဟောင်း injection နှင့် byte အလိုက် တစ်ထပ်တည်း ဖြစ်သည်။

ဘာသာစကားရွေးချယ်မှု- `languageConfig.enabled` ကို ဖွင့်ထားပါက `autoDetect` သည်
နောက်ဆုံး user message ၏ ဘာသာစကားကို ရွေးချယ်သည် (input engine များနှင့် detector တူသည်)။
`autoDetect` ကို ပိတ်လိုက်ပါက `defaultLanguage` ကို ပုံသေသတ်မှတ်သည်။ ပိတ်ထားလျှင် → အင်္ဂလိပ်။

စတိုင် × ဘာသာစကား matrix ကို
`tests/unit/compression/output-styles-i18n-matrix.test.ts` ဖြင့် ပုံသေထိန်းထားသည်- စတိုင်အသစ်တစ်ခုသည်
အနည်းဆုံး pt-BR ဘာသာပြန်ဆိုချက် (သို့မဟုတ် ခြေရာခံထားသော ခြွင်းချက်တစ်ခု) မရှိဘဲ ထုတ်ပေး၍မရသလို
ရှိပြီးသားစတိုင်တစ်ခုမှ locale တစ်ခုကို အသိပေးခြင်းမရှိဘဲ ဖယ်ရှား၍မရပါ။ စတိုင်တစ်ခုထည့်ရန်
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) ကို ကြည့်ပါ။

### Tool Result Compression

`toolResultCompressor.ts` module သည် tool result များ (function call များ၊ agent output များ၊ search result များ စသည်) အတွက်
**အထူးပြု compression strategy ၅ မျိုး** ကို ပံ့ပိုးသည်-

1. **Search result compression** — ထပ်နေသော result များကို ဖယ်ရှားပြီး ထိပ်ဆုံး-N ခုကို ထိန်းသိမ်းသည်
2. **File read compression** — ဖိုင်ကြီးများကို ဖြတ်တောက်ပြီး header/import များကို ထိန်းသိမ်းသည်
3. **Code execution compression** — မရှိမဖြစ် stdout/stderr ကိုသာ ထိန်းသိမ်းသည်
4. **Database query compression** — row အရေအတွက်ကို ကန့်သတ်ပြီး ရှည်လျားလွန်းသော metadata ကို ဖယ်ရှားသည်
5. **API response compression** — null field များကို ဖယ်ရှားပြီး array များကို ချုံ့သည်

#### အသုံးပြုသင့်သည့်အချိန်

Tool call များ ပါရှိသည့်အခါ tool result compression သည် **အမြဲတမ်း ဖွင့်ထားသည်**။ Configuration ပြုလုပ်ရန် မလိုအပ်ပါ။

### အဆင့်ဆင့် Pipeline

Stacked mode သည် **engine အများအပြားကို အစဉ်လိုက်** လုပ်ဆောင်သည် — ပုံမှန်အားဖြင့် RTK ကို ဦးစွာအသုံးပြုပြီး
(tool output တွင် 60-90% ချွေတာနိုင်သည်)၊ ထို့နောက် Caveman ကို အသုံးပြုသည် (ကျန်ရှိသော
စာသားတွင် နောက်ထပ် 30% ချွေတာနိုင်သည်)။ ဤနည်းဖြင့် **စုစုပေါင်း 78-95% ချွေတာမှု** ရရှိသည်။

#### အလုပ်လုပ်ပုံ

```
Input (1000 tokens)
  → RTK (command ကို နားလည်သော filter) → 200 tokens
    → Caveman (မလိုအပ်သော စာသားများ ဖယ်ရှားခြင်း) → 140 tokens
  → Output (140 tokens၊ 86% ချွေတာမှု)
```

#### အသုံးပြုသင့်သည့်အချိန်

Stacked mode ကို အောက်ပါအခြေအနေများတွင် အသုံးပြုပါ-

- Tool ကို အများအပြားအသုံးပြုသော workflow များ (agentic coding၊ သုတေသန)
- ကုန်ကျစရိတ်ကို အလေးထားသော batch processing
- Token ချွေတာမှု အများဆုံး လိုအပ်သည့်အခါ

Combo မှတစ်ဆင့် configure လုပ်ပါ-

```json
{
  "strategy": "auto",
  "config": {
    "auto": {

    }
  }
}
```

## Compression Combo ကို အလိုက်သင့် အစားထိုးသတ်မှတ်ခြင်း

မတူညီသော အသုံးပြုမှုအခြေအနေများအတွက် လုပ်ဆောင်ပုံကို အသေးစိတ်ချိန်ညှိရန် ကမ္ဘာလုံးဆိုင်ရာ compression mode ကို **combo တစ်ခုချင်းစီအလိုက်** အစားထိုးသတ်မှတ်နိုင်သည်-

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "auto": {
      "weights": { "taskFit": 0.5 },
      "modePack": "quality-first"
    }
  },
  "compressionOverride": {
    "mode": "aggressive",
    "stackedPipelines": ["rtk", "caveman"],
    "preserveToolDefinitions": true
  }
}
```

ဤအရာသည် အောက်ပါအခြေအနေများတွင် အသုံးဝင်သည်-

- **Coding combo များ**: ကြာမြင့်သော session များအတွက် `aggressive` mode ကို အသုံးပြုပါ
- **အမြန် အမေးအဖြေ combo များ**: မြန်ဆန်သော တုံ့ပြန်ချက်များအတွက် `lite` mode ကို အသုံးပြုပါ
- **Tool အများအပြားသုံးသော combo များ**: ချွေတာမှုအများဆုံးရရှိရန် `stacked` mode ကို အသုံးပြုပါ
- **Production combo များ**: Caching provider များအတွက် `cache-aware` mode ကို အသုံးပြုပါ
