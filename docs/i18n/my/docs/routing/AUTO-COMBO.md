## Zero-Config အလိုအလျောက် လမ်းကြောင်းရွေးချယ်ခြင်း (`auto/` ရှေ့ဆက်)

> **အသစ်:** combo ဖန်တီးရန် မလိုအပ်ပါ။ မည်သည့် client တွင်မဆို `auto/` ရှေ့ဆက်ကို တိုက်ရိုက်အသုံးပြုပါ။

### အမြန်နမူနာများ

| -------------- | ------- | ----------------------------------------------------------------------------------------------------- |

| `auto/coding`  | coding  | အရည်အသွေးဦးစားပေး weights၊ code ထုတ်လုပ်ခြင်းအတွက် သင့်လျော်သည်                                       |

| `auto/cheap`   | cheap   | ကုန်ကျစရိတ်အကောင်းဆုံးဖြစ်အောင် လမ်းကြောင်းရွေးချယ်ခြင်း (အနည်းဆုံးကုန်ကျစရိတ်ကို ဦးစွာရွေးသည်)       |
| `auto/offline` | offline | quota ရရှိနိုင်မှု အမြင့်ဆုံး provider များကို ဦးစားပေးသည်                                            |
| `auto/smart`   | smart   | ပိုမိုကောင်းမွန်သော model ရှာဖွေမှုအတွက် အရည်အသွေးဦးစားပေး + ပိုမြင့်သော စမ်းသပ်ရှာဖွေမှုနှုန်း (10%) |
| `auto/lkgp`    | lkgp    | တိကျစွာသတ်မှတ်ထားသော LKGP (မူလ `auto` နှင့် တူညီသည်)                                                  |
| `auto/chaos`   | chaos   | အပြိုင် fan-out၊ provider တစ်ခုလျှင် model တစ်ခု (ချို့ယွင်းချက်ထည့်သွင်းခြင်း မဟုတ်ပါ)               |

### Category × Tier ပေါင်းစပ်မှု (`auto/<category>:<tier>`)

OpenRouter ပုံစံ suffix များသည် **မည်သည့်လမ်းကြောင်းအမျိုးအစားဖြစ်သည်** (category) ကို **မည်သို့ အကောင်းဆုံးဖြစ်အောင် ပြုလုပ်မည်** (tier) နှင့် ခွဲခြားပေးသောကြောင့် ၎င်းတို့ကို လွတ်လပ်စွာ ပေါင်းစပ်နိုင်သည် (#4235 Phase B၊ `open-sse/services/autoCombo/suffixComposition.ts`)：

- **Categories** (စွမ်းဆောင်ရည်အလိုက် ရွေးချယ်နိုင်သော pool ကို စစ်ထုတ်သည်): `coding` · `reasoning` · `vision` · `chat` · `multimodal`။ `vision`/`multimodal` သည် vision စွမ်းရည်ရှိသော model များကို ထိန်းသိမ်းထားပြီး `reasoning` သည် reasoning/thinking model များကို ထိန်းသိမ်းထားသည်။
- **Tiers** (အမှတ်ပေး weights / pool filter ကို ရွေးချယ်သည်): `fast` (လျင်မြန်စွာ ထုတ်ပေးခြင်း) · `cheap` (`floor` ၏ alias၊ ကုန်ကျစရိတ်ချွေတာမှု) · `reliable` (circuit-breaker ကျန်းမာရေး + latency တည်ငြိမ်မှု) · `free` / `pro` (`classifyTier` မှတစ်ဆင့် model tier အလိုက် pool ကို စစ်ထုတ်သည် — free-tier နှင့် premium)။

| နမူနာ                  | ဖြေရှင်းသတ်မှတ်ပုံ                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| `auto/coding:fast`     | coding pool၊ latency နည်းသော weights                                                     |
| `auto/coding:cheap`    | coding pool၊ ကုန်ကျစရိတ်အကောင်းဆုံးဖြစ်အောင် ပြုလုပ်ထားသည် (`auto/coding:floor` ၏ alias) |
| `auto/reasoning:pro`   | reasoning/thinking model များသာ၊ premium tier                                            |
| `auto/vision`          | vision စွမ်းရည်ရှိသော model များ (tier မရှိ → ချိန်ညှိထားသော weights)                    |
| `auto/multimodal:free` | multimodal စွမ်းရည်ရှိသော model များ၊ free tier သာ                                       |

တရားဝင်သော `auto/<category>[:<tier>]` မှန်သမျှကို လိုအပ်သည့်အချိန်တွင် ဖြေရှင်းသတ်မှတ်ပေးသည်။ စီစဉ်ရွေးချယ်ထားသော အစုခွဲတစ်ခုကို `/v1/models` နှင့် dashboard တွင် ဖော်ပြထားသည် (`open-sse/services/autoCombo/builtinCatalog.ts` ရှိ `AUTO_SUFFIX_VARIANTS`)။ စစ်ထုတ်ခြင်းသည် **fail-open** ဖြစ်သည် — constraint တစ်ခုနှင့် ကိုက်ညီသော ချိတ်ဆက်ထားသည့် model မရှိပါက လမ်းကြောင်းရွေးချယ်မှု မပျက်စေရန် pool အပြည့်အစုံကို အသုံးပြုသည်။ အဓိက scorer (`combo.ts`) သည် မပြောင်းလဲဘဲ category/tier filter ကို `buildAutoCandidates` တွင် အသုံးချထားသည်။

> **တိုက်ရိုက် model အသိဉာဏ်:** `ARENA_ELO_SYNC_ENABLED` flag ဖွင့်ထားသည့်အခါ အလိုအလျောက်လမ်းကြောင်းရွေးချယ်မှု၏ သင့်လျော်မှုကို တိုက်ရိုက် **Arena ELO** အဆင့်သတ်မှတ်ချက်များ + **models.dev** tier data တို့ဖြင့် ဆုံးဖြတ်သည် (မဟုတ်ပါက static fitness map ကို ပြန်လည်အသုံးပြုသည်)။

**အသုံးပြုနည်း:**

```bash
# OpenAI format ကို ပံ့ပိုးသော မည်သည့် IDE သို့မဟုတ် CLI tool မဆို
Base URL: http://localhost:20128/v1
API Key:  <သင့်-endpoint-key>

# သင့် code/config တွင် model ကို အောက်ပါအတိုင်း သတ်မှတ်ပါ:
model: "auto"                 # ချိန်ညှိထားသော မူလရွေးချယ်မှု
model: "auto/coding"          # coding လုပ်ငန်းများအတွက် အကောင်းဆုံး
model: "auto/fast"            # ရရှိနိုင်သည့်အထဲတွင် အမြန်ဆုံး
model: "auto/cheap"           # token တစ်ခုလျှင် ဈေးအသက်သာဆုံး
```

**ဖြစ်ပျက်ပုံ:**

1. OmniRoute သည် `src/sse/handlers/chat.ts` တွင် `auto/` ရှေ့ဆက်ကို ရှာဖွေသိရှိသည်
2. database မှ **အသုံးပြုနေသော provider ချိတ်ဆက်မှုများ** အားလုံးကို query ပြုလုပ်သည်
3. တရားဝင် credentials (API key သို့မဟုတ် OAuth token) ရှိသည့်အရာများကို စစ်ထုတ်သည်
4. ချိတ်ဆက်မှုတစ်ခုစီအတွက် model ကို ဆုံးဖြတ်သည် (`connection.defaultModel` သို့မဟုတ် provider ၏ ပထမဆုံး model)
5. memory အတွင်း **virtual combo** တစ်ခုကို တည်ဆောက်သည် (DB တွင် မသိမ်းဆည်းပါ)
6. ရွေးချယ်ထားသော မူကွဲ၏ weight profile + LKGP နည်းဗျူဟာကို အသုံးပြု၍ လမ်းကြောင်းရွေးချယ်သည်

**အဓိကဂုဏ်သတ္တိများ:**

- ✅ **အမြဲဖွင့်ထားသည်:** toggle မလို၊ combo ဖန်တီးရန် မလို၊ configuration မလိုအပ်ပါ
- ✅ **Dynamic:** လက်ရှိချိတ်ဆက်ထားသော provider များကို အလိုအလျောက် ထင်ဟပ်ပေးသည်
- ✅ **Session stickiness:** LKGP သည် နောက်ဆုံးအောင်မြင်ခဲ့သော provider ကို ဦးစားပေးရန် သေချာစေသည်
- ✅ **အကောင့်အများအပြားကို သိရှိစီမံနိုင်သည်:** provider ချိတ်ဆက်မှုတစ်ခုစီသည် သီးခြား candidate တစ်ခု ဖြစ်လာသည်
- ✅ **DB ရေးသားမှုမရှိ:** Virtual combo သည် request အတွက်သာ တည်ရှိပြီး persistence overhead လုံးဝမရှိပါ

### Key တစ်ခုချင်းစီအလိုက် candidate ထိန်းချုပ်မှု (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` နောက်ရှိ suffix သို့မဟုတ်
အခြေခံ channel အတွက် တိုက်ရိုက် `auto`) သည် ရှိပြီးသား resilience reads များကို
ပြန်လည်အသုံးပြုကာ တိုက်ရိုက် reachability ဖြင့် ဖြည့်စွက်ဖော်ပြထားသည့် `auto/*` channel ၏
လက်ရှိ candidate pool ကို စာရင်းပြုစုသော **ဖတ်ရှုရန်သီးသန့်** endpoint ဖြစ်သည် (breaker `state` အကြမ်းကို မည်သည့်အခါမျှ မသုံးပါ):

- provider circuit breaker — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- ချိတ်ဆက်မှု cooldown — ဖြေရှင်းသတ်မှတ်ထားသော `provider_connections` row ရှိ
  `rateLimitedUntil` / `testStatus`
- model lockout — `isModelLocked(provider, connectionId, model)`

Candidate တစ်ခုစီတွင် ဤ API key ၏ `excluded` flag လည်း ပါဝင်သည်။ ဖယ်ထုတ်မှုများကို
API key တစ်ခုချင်းစီအလိုက် သိမ်းဆည်းထားသည် (`auto_candidate_overrides` table၊ migration `128`) — OmniRoute သည်
`users` table မရှိသော single-tenant ဖြစ်သောကြောင့် `apiKeyId` သည် တကယ့် caller တစ်ဦးချင်းစီ၏
identity နှင့် အနီးစပ်ဆုံးဖြစ်သည် — ထို့ပြင် သီးခြားယူနစ်စမ်းသပ်ထားသော
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) မှတစ်ဆင့်
`open-sse/services/autoCombo/virtualFactory.ts` ရှိ candidate-pool chokepoint တွင် အတင်းအကျပ် အသုံးချသည်။
Filter သည် **fail-open** ဖြစ်သည်: apiKeyId/channel ကို မသတ်မှတ်ထားခြင်း သို့မဟုတ် DB lookup ပျက်ကွက်ခြင်း နှစ်မျိုးစလုံးတွင်
pool ကို စစ်ထုတ်ခြင်းမပြုဘဲ ထားရှိသောကြောင့် override များ မစီစဉ်ထားသည့် operator တစ်ဦးသည် ဤ feature မတိုင်မီကနှင့်
byte အဆင့်အထိ တစ်ပုံစံတည်းဖြစ်သော လမ်းကြောင်းရွေးချယ်မှုကို တွေ့မြင်ရသည်။

**နောက်ဆက်တွဲ issue တစ်ခုသို့ ရွှေ့ဆိုင်းထားသည်:** candidate တစ်ခုချင်းစီအလိုက် weight များ + တိကျစွာ သတ်မှတ်ထားသော အစီအစဉ် (Level 3
— လက်ရှိ weighted/priority strategy လမ်းကြောင်းများသို့ ထည့်သွင်းပေးသည်) နှင့် `auto/*` channel တစ်ခုချင်းစီအတွက် သတ်မှတ်ထားသော
`combo.ts` strategy တစ်ခုကို pin လုပ်ခြင်း (Level 4)။ single-tenant model ကို ထည့်သွင်းစဉ်းစားလျှင် override များကို API key တစ်ခုချင်းစီအလိုက် ဆက်လက်ထားရှိသင့်သလား သို့မဟုတ် global အဖြစ် ပြောင်းလဲသင့်သလားဆိုသည့် အဖြေမရှိသေးသော
မေးခွန်းအတွက် #7819 plan ကို ကြည့်ပါ။

**နောက်ကွယ်ရှိ လုပ်ငန်းစဉ်:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

| `open-sse/services/autoCombo/virtualFactory.ts`           | Virtual `AutoComboConfig` object များကို ဖန်တီးသည် |

## အမှန်တကယ်ရှိသော Model Id နှင့် ကိုက်ညီသည့် Combo အမည်များ

`name` သည် bare model id တစ်ခုနှင့် တူညီနေသော combo (ဥပမာ `gpt-5.5` ဟု အမည်ပေးထားသည့် combo) သည် bug မဟုတ်ဘဲ **ရည်ရွယ်ချက်ရှိရှိ ပံ့ပိုးထားသော ပုံစံတစ်ခု** ဖြစ်သည်။ ၎င်းသည် [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) တွင် မှတ်တမ်းတင်ထားသည့် model-id တစ်ခုချင်းအလိုက် provider fallback ပြုလုပ်ရန် ယန္တရားဖြစ်သည်။ Bare-model-id resolution မတိုင်မီ combo resolution ကို စစ်ဆေးသောကြောင့် (`src/sse/services/model.ts` ရှိ `getComboForModel()`) bare id `gpt-5.5` အတွက် request ကို provider တစ်ခုတည်းထံ တိုက်ရိုက်ပို့မည့်အစား combo ၏ targets များ (ဥပမာ `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) မှတစ်ဆင့် route လုပ်သည် — ဤလုပ်ဆောင်ချက်သည် [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) အတွက် တည်ဆောက်ထားသော combo-before-rewrite ဦးစားပေးအစီအစဉ်ကို ပြန်လည်အသုံးပြုထားပြီး `tests/unit/responses-combo-resolution-3227.test.ts` နှင့် `tests/unit/combo-name-codex-responses-rewrite.test.ts` တို့ဖြင့် regression test ပြုလုပ်ထားသည်။

အမှန်တကယ်ရှိသော model id ကို ဖုံးကွယ်သည့် အမည်တစ်ခုဖြင့် combo ဖန်တီးခြင်း သို့မဟုတ် အမည်ပြောင်းခြင်းကို **မည်သည့်အခါမျှ ငြင်းပယ်မည်မဟုတ်ပါ** — ထိုသို့ပြုလုပ်ပါက မှတ်တမ်းတင်ထားသော ဤ workflow ကို ပျက်စီးစေမည်ဖြစ်သည်။ ထိုအစား (#8530)၊ (အသစ်သတ်မှတ်ထားသော) အမည်သည် အမှန်တကယ်ရှိသော model id နှင့် တိုက်ဆိုင်သည့်အခါ `POST /api/combos` နှင့် `PUT /api/combos/[id]` တို့သည် request ကို ပိတ်ဆို့ခြင်းမရှိသော `warning` field တစ်ခုကို response တွင် ထည့်သွင်းပေးသည်-

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

စနစ်စတင်ချိန်တွင် `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) သည် model id ကို ဖုံးကွယ်နေသည့် လက်ရှိ combo တိုင်းကို စာရင်းပြုစုထားသော တစ်ကြောင်းတည်းပါ `[STARTUP]` သတိပေးချက်ကိုလည်း log လုပ်ပေးသည်။ ထို့ကြောင့် #6940 အရ ရည်ရွယ်ချက်ရှိရှိ ပြုလုပ်ခြင်းမဟုတ်ဘဲ မတော်တဆ ကြုံတွေ့ရသော operator များအတွက် သတိပြုနိုင်သည့် အချက်ပြမှုတစ်ခု ရရှိစေသည်။ Detection helper သည် `src/lib/combos/modelNameCollision.ts` တွင် ရှိသည်။

## Client မှ Custom Combo တစ်ခုကို ခေါ်ယူခြင်း

သိမ်းဆည်းထားသော combo များ (Settings → Combos) ကို client က combo ၏ **အမည်အတိအကျ** ကို `model` field တွင် ပို့သည့်အခါမှသာ အသုံးပြုသည် — combo အမည်အတွက် fuzzy သို့မဟုတ် partial matching မရှိသည့်အပြင် `auto/` prefix လည်း မပါဝင်ပါ။ Resolution အစီအစဉ် (`src/sse/services/model.ts` ရှိ `getComboForModel()`)-

1. combo အမည်နှင့် အတိအကျကိုက်ညီမှု (`model: "my-combo"`),
2. `combo/<name>` prefix (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`)။

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

အဖြစ်များသော သတိပြုရမည့်အချက်နှစ်ခု-

- **`auto` သည် သင့် combo များကို အသုံးမပြုပါ။** `auto`/`auto/*` သည် ၎င်းကိုယ်ပိုင် zero-config candidate pool ကို တည်ဆောက်ပြီး `auto` ဟု အမည်အတိအကျ ပေးထားသည့် combo ရှိမှသာ သိမ်းဆည်းထားသော combo များကို အသုံးပြုသည် (မအကြံပြုပါ)။ Combo မှတစ်ဆင့် route လုပ်ရန် `auto` ကို မပို့ဘဲ ၎င်း၏ အမည်အတိအကျကို ပို့ပါ။
- **`openrouter/auto` သည် အမှန်တကယ်ရှိသော အခပေး OpenRouter product** ("Auto Best Available") ဖြစ်ပြီး OmniRoute alias မဟုတ်ပါ။ ၎င်းသည် OpenRouter registry (`open-sse/config/providers/registry/openrouter/index.ts`) ၏ တစ်ခုတည်းသော static model entry ဖြစ်ပြီး သီးခြားငွေတောင်းခံသည်။ ၎င်းကို `auto` pools များမှ ဖယ်ထုတ်ရန် Settings → Routing → Hide paid models ကို အသုံးပြုပါ။

ဤမှတ်တမ်းတွင် ရှင်းလင်းထားသော မူလရှုပ်ထွေးမှုအကြောင်းကို [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) နှင့် [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) တို့တွင် ကြည့်ပါ။

## အလုပ်လုပ်ပုံ (သိမ်းဆည်းထားသော Auto-Combo များ)

Auto-Combo Engine သည် request တစ်ခုချင်းစီအတွက် အသင့်တော်ဆုံး provider/model ကို **အချက် 16 ချက်ပါ scoring function** (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` တွင် သတ်မှတ်ထားသည်) အသုံးပြုပြီး အလိုအလျောက် ရွေးချယ်ပေးသည်။ မူလ weight များ၏ စုစုပေါင်းသည် `1.0` ဖြစ်ပြီး custom weight များကို `normalizeScoringWeights()` ဖြင့် ပြန်လည်စံသတ်မှတ်သည်။ အချက် ဆယ့်ခြောက်ချက်အနက် `cacheAffinity` နှင့် `resetWindowAffinity` နှစ်ခု၏ မူလ weight သည် `0` ဖြစ်သည်။ `reliability` ၏ weight သည် `DEFAULT_WEIGHTS` တွင် `0` ဖြစ်သော်လည်း ယေဘုယျ pack များတွင် `0.03` နှင့် `reliability-first` တွင် `0.04` ဖြစ်ပြီး၊ `quality` ၏ weight သည် pack များတွင် `0.02` (`quality-first` တွင် `0.03`) ဖြစ်သည်။ ၎င်းတို့ကို candidate တစ်ခုချင်းစီအတွက် တွက်ချက်ဆဲဖြစ်ပြီး `cacheAffinity` သည် score ပြင်ပရှိ prompt-cache ထပ်နေမှုဖယ်ရှားခြင်းကို ထိန်းချုပ်သည်။ ထို့ကြောင့် မူလတန်ဖိုး သုညဖြစ်သော အချက်များသည် ပုံမှန်အားဖြင့် မဲမပေးသော်လည်း pack များကမူ မဲပေးသည်။

```bash
  -H "X-OmniRoute-Budget: 0.05" \
  -H "X-OmniRoute-Budget-Fallback: strict" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hi"}]}'
```

သတ်မှတ်ဖြေရှင်းမှုသည် pure function (`open-sse/services/autoCombo/requestControls.ts`) တစ်ခုဖြစ်ပြီး၊
သတ်မှတ်ပြီးသားတန်ဖိုးများကို engine ၏ လက်ရှိ `config.modePack` / `config.budgetCap` /
`config.budgetFallback` input များထဲသို့ ထည့်သွင်းသည်။ Combo တစ်ခု၏ သိမ်းဆည်းထားသော `config.budgetFallback` ("strict" |
"cheapest") သည် အမြဲတမ်းသုံးမည့် မူဝါဒကို သတ်မှတ်ပြီး၊ header က တောင်းဆိုချက်တစ်ခုတည်းအတွက် ၎င်းကို အစားထိုးသတ်မှတ်သည်။

### `weighted` ၏ အဓိပ္ပာယ်သတ်မှတ်ချက်

`weighted` သည် အချိုးကျညှိပေးသည့် နည်းလမ်းမဟုတ်ဘဲ **request တစ်ခုချင်းစီအတွက် အချိုးကျ ကျပန်းရွေးချယ်မှု** ဖြစ်သည်
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`)၊

- request တစ်ခုစီသည် ဖြစ်နိုင်ခြေ `weight / totalWeight` ဖြင့် အဆင့် **တစ်ခု**ကို ရွေးချယ်သည်၊ ကျန်အဆင့်များကို ထို request အတွက် အရန်အစီအစဉ်အဖြစ် weight ကြီးစဉ်ငယ်လိုက်
  စီထားသည်။
- weight `0` ဖြစ်သော (သို့မဟုတ် weight မရှိသော) အဆင့်ကို အခြားအဆင့်တစ်ခုခု၌
  weight > 0 ရှိနေသရွေ့ **လုံးဝရွေးချယ်မည်မဟုတ်ပါ** — ရွေးချယ်ထားသောအဆင့် မအောင်မြင်ပြီးနောက်မှသာ အရန်အဖြစ် အသုံးပြုနိုင်သည်။ weight **အားလုံး**
  0 ဖြစ်သည့်အခါမှသာ ဖြစ်နိုင်ခြေတူညီသော ရွေးချယ်မှု ဖြစ်လာသည်။
- target အားလုံး အသုံးမပြုနိုင်သည့် အဆင့်များ — provider circuit breaker `OPEN` ဖြစ်ခြင်း၊ connection
  cooldown ဖြစ်ခြင်း၊ model lockout ဖြစ်ခြင်း — ကို ရွေးချယ်မှုမပြုလုပ်မီ ဖယ်ရှားသည်
  (`open-sse/services/combo/targetResolution.ts`)၊ ထို့ကြောင့် ကောင်းမွန်စွာ အလုပ်လုပ်နေသော အဆင့်တစ်ခုတည်းက request တိုင်းအတွက် ယာယီရွေးချယ်ခံရနိုင်သည်။
- `stickyWeightedLimit` (combo config၊ မူလတန်ဖိုး `1` = ပိတ်ထားသည်) သည် ပြန်လည်ရွေးချယ်ခြင်းမပြုမီ ရွေးချယ်ထားသောအဆင့်ကို သတ်မှတ်ထားသည့် အကြိမ်ရေမျှ ဆက်တိုက်အောင်မြင်မှုများအတွက် ချိတ်ထားသည်။

တင်းကျပ်သော အလှည့်ကျအသုံးပြုမှုအတွက် `round-robin` ကို အသုံးပြုပါ။ `weighted` တွင် အလေးချိန်များ တူညီစွာ သတ်မှတ်ခြင်းသည် စာရင်းအင်းအရ ဟန်ချက်ညီမှုကိုသာ ပေးပြီး တင်းကျပ်သော ဟန်ချက်ညီမှုကို မပေးပါ။

### အေးဂျင့်အခြေပြု pipeline မုဒ်

မော်ဒယ် အနည်းဆုံးနှစ်ခုပါဝင်သော `pipeline` ပေါင်းစပ်မှုတစ်ခုသည်
`config.agenticOrchestration.enabled` ဖြင့် planner/executor လမ်းကြောင်းခွဲခြင်းကို ရွေးချယ်ဖွင့်နိုင်သည်။ ပထမ target သည် အစီအစဉ်ရေးဆွဲခြင်းနှင့် နောက်ဆုံးအဖြေများကို တာဝန်ယူပြီး၊
ဒုတိယ target သည် client ၏ မူရင်းပုံစံ tool call များကို ထုတ်ပေးသည်။ OmniRoute သည် request protocol မှ tool-result ဆက်လက်လုပ်ဆောင်မှုများကို ရှာဖွေသိရှိပြီး၊ နောက်ထပ် tool အလှည့်တစ်ခု လိုအပ်ခြင်းရှိမရှိ planner ကို မေးမြန်းကာ executor သို့မဟုတ် planner ကို client ထံ ပြသမည့် နောက်ဆုံးအဆင့်အဖြစ် အခြေအနေအလိုက် သတ်မှတ်ပေးသည်။

ဒုတိယ target နောက်တွင် ထည့်ထားသော မော်ဒယ်များသည် အစဉ်လိုက် executor အရန်များဖြစ်သည်။ မအောင်မြင်သော
HTTP response သို့မဟုတ် သယ်ယူပို့ဆောင်ရေးဆိုင်ရာ exception တစ်ခု ဖြစ်ပေါ်ပါက၊ တူညီသော planner ဆုံးဖြတ်ချက်နှင့် မူရင်း tools များကို ဆက်လက်သယ်ဆောင်သော်လည်း ထို executor ၏ ကိုယ်ပိုင်အဆင့် prompt နှင့် ဖြေရှင်းသတ်မှတ်ထားသော connection ကို အသုံးပြု၍ နောက် executor သို့ ရွှေ့သည်။ ပထမဆုံး အောင်မြင်သော response ကို
SSE streaming အပါအဝင် မပြောင်းလဲဘဲ ပြန်ပေးသည်။ အောင်မြင်သော stream စတင်ပြီးနောက် ဖြစ်ပေါ်သည့် မအောင်မြင်မှုများကို ဤနေရာတွင် ထပ်မံကြိုးစား၍ မရပါ။
executor အားလုံး မအောင်မြင်ပါက နောက်ဆုံး မအောင်မြင်မှုကို ပြန်ပေးသည်။ Client မှ ပယ်ဖျက်လိုက်ပါက dispatch လုပ်ခြင်း ရပ်တန့်သည်။

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

executor သည် response တစ်ခုတည်းတွင် သီးခြားလွတ်လပ်သော call များစွာကို ထုတ်ပေးနိုင်သည်။ အချင်းချင်း မှီခိုသော call များကို နောက်ပိုင်း client tool-result အလှည့်များတွင် ကိုင်တွယ်ပြီး planner က result တစ်ခုချင်းစီကို ပြန်လည်သုံးသပ်သည်။
`maxToolRounds` ၏ မူလတန်ဖိုးသည် `8` ဖြစ်ပြီး `1`–`32` ကို လက်ခံသည်။ သတ်မှတ်ထားသော အရေအတွက်သို့ ရောက်သည်နှင့် planner သည် လက်ရှိရရှိနိုင်သော အကောင်းဆုံး နောက်ဆုံးအဖြေကို ထုတ်ပေးရမည်။ အတွင်းပိုင်း planner ဆုံးဖြတ်ချက်များကို buffer လုပ်ထားပြီး၊ ရွေးချယ်ထားသော client ထံ ပြသမည့် response သည် မူလ streaming ဦးစားပေးသတ်မှတ်ချက်ကို ဆက်လက်ထိန်းသိမ်းထားသည်။

### `round-robin` ၏ sticky batch နှင့် account ချဲ့ထွင်မှု

Round-robin သည် request တစ်ခုလျှင် အဆင့်တစ်ခုစီ မဟုတ်ဘဲ batch အလိုက် လုပ်ဆောင်သည်-

- `stickyRoundRobinLimit` (ပထမ combo config၊ ထို့နောက် `comboStickyRoundRobinLimit`၊ ထို့နောက်
  `settings.stickyRoundRobinLimit`၊ မူလတန်ဖိုး **3**) သည် အလှည့်မပြောင်းမီ ဆက်တိုက်အောင်မြင်မှု အရေအတွက် သတ်မှတ်ချက်အတိုင်း တူညီသော target ကို ဆက်လက်အသုံးပြုသည်။ request တစ်ခုစီအလိုက် အလှည့်ပြောင်းရန် combo override ကို `1` ဟု သတ်မှတ်ပါ။ Combo editor တွင် လက်တွေ့သက်ရောက်နေသော တန်ဖိုးနှင့် ၎င်းရရှိလာသည့် layer ကို ပြသသည်။
- `connectionAwareExpansion` (ပထမ combo config၊ ထို့နောက် settings၊ မူလတန်ဖိုး **false**) သည်
  အလှည့်မပြောင်းမီ provider အဆင့် step တစ်ခုစီကို account တစ်ခုချင်းစီအလိုက် target များအဖြစ် ချဲ့ထွင်သည်။ Group-B strategy များ
  (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp,
  fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion,
  pipeline) သည် ဤအရာကို ဖွင့်မထားသရွေ့ provider အဆင့်မြင်ကွင်းကို ဆက်လက်အသုံးပြုသည်။ Combo editor တွင်
  inherit / on / off ကို ရွေးချယ်နိုင်သည်။ inherit သည် global မူလတန်ဖိုး (off) ကို အသုံးပြုသည်။
- Prompt-cache locality routing (`promptCacheAffinityEnabled`၊ မူလတန်ဖိုး **true**) သည်
  ကိုက်ညီသော cache key များကို account တစ်ခုတည်းတွင် ထားရှိနိုင်ရန် pinned connection များကို အစီအစဉ်ပြန်စီသည်။ ၎င်းသည် pinned per-account step များကြားရှိ
  round-robin နှင့် weighted အလှည့်ပြောင်းခြင်းထက် ဦးစားပေးသည်။ တင်းကျပ်သော အလှည့်ပြောင်းမှု လိုအပ်ပါက
  Settings → Combo defaults အောက်တွင် ၎င်းကို ပိတ်ပါ။ Combo တစ်ခုချင်းစီအလိုက် override မရှိပါ။

မော်ဒယ်တစ်ခုတည်းရှိ account အများအပြားကြား အလှည့်ပြောင်းရန် `connectionId` အလွတ်နှင့် pool တစ်ခုလုံးပါဝင်သော **dynamic-account step တစ်ခု** ကို sticky limit `1` ဖြင့် အသုံးပြုခြင်းသည် pinned `connectionId` သုံးခုကို အသုံးပြုခြင်းထက် ပိုသင့်လျော်သည်။
Pinned step များနှင့် affinity ကို တွဲသုံးပါက RR counter ဆက်လက်တိုးနေသော်လည်း account တစ်ခုတည်းပေါ်တွင် စုစည်းသွားသည်။

## Fusion မဟာဗျူဟာ

`fusion` သည် ပစ်မှတ်တစ်ခုတည်းကို **မရွေးချယ်သည့်** တစ်ခုတည်းသော မဟာဗျူဟာဖြစ်သည်။ ၎င်းသည် prompt ကို
**panel model အားလုံးထံ တစ်ပြိုင်နက်တည်း** ဖြန့်ပို့ပြီးနောက် ပြင်ဆင်သတ်မှတ်နိုင်သော **judge model** က
panel တုံ့ပြန်ချက်အားလုံးမှ နောက်ဆုံးအဖြေတစ်ခုတည်းကို ပေါင်းစပ်ထုတ်ပေးသည်။ မူရင်း `decolua/9router`
(OpenRouter ၏ Fusion ဒီဇိုင်း) မှ ပြောင်းရွှေ့ယူထားပြီး အကောင်အထည်ဖော်မှုမှာ `open-sse/services/fusion.ts` တွင်ရှိသည်။

အလုပ်လုပ်ပုံ-

0. **Tool ပါဝင်သော တောင်းဆိုမှုကို ကျော်လွှားခြင်း** — အလွတ်မဟုတ်သော `tools` array ပါဝင်ပြီး
   `tool_choice` ကို `"none"` ဟု တိတိကျကျ မသတ်မှတ်ထားသော တောင်းဆိုမှုသည် panel ကို လုံးဝကျော်သွားသည်။ ၎င်းကို
   model တစ်ခုတည်း (ပြင်ဆင်သတ်မှတ်ထားသော judge သို့မဟုတ် `panel[0]`) ထံသို့ `tools`/`tool_choice`
   ကို မပြောင်းလဲဘဲ တိုက်ရိုက်လမ်းကြောင်းပေးသည်။ Panel အဖွဲ့ဝင်များသည် tool အသုံးပြုခွင့်မရှိသည့်အပြင် judge ၏
   ပေါင်းစပ်ရေးသားမှု ညွှန်ကြားချက်က tool-call ထုတ်လွှတ်ခြင်းကို အားမပေးသောကြောင့် agentic/tool-calling client များသည်
   ပေါင်းစပ်ရေးသားထားသော စာသားအစား တကယ့် tool-call ဆုံးဖြတ်ချက်ကို ရရှိသည် (#6771)။
1. **ဖြန့်ခွဲပို့ခြင်း** (tool မပါသော တောင်းဆိုမှုများသာ) — prompt ကို panel
   model အားလုံးထံ တစ်ပြိုင်နက်တည်း ပို့ပြီး tools များကို ဖယ်ရှားကာ non-streaming ဖြစ်ရန် အတင်းသတ်မှတ်သည် (judge သည်
   ပေါင်းစပ်ရေးသားရန် စာသားအပြည့်အစုံ လိုအပ်သည်)။
2. **Quorum-grace စုဆောင်းခြင်း** — `minPanel` အဖြေများ ရောက်လာသည်နှင့် ကျန်နေသူများအတွက်
   grace timer အတိုတစ်ခု စတင်ပြီးနောက် ရရှိစုဆောင်းထားသမျှဖြင့် fusion ကို ဆက်လက်လုပ်ဆောင်သည်။
   ဤနည်းဖြင့် အနှေးဆုံး model ကြောင့် wall time တွင် ဖြစ်ပေါ်သော နှောင့်နှေးမှုကို ကန့်သတ်ပေးပြီး hard timeout ဖြင့် အမြင့်ဆုံးကန့်သတ်ထားသည်။
3. **Judge ဖြင့် ပေါင်းစပ်ရေးသားခြင်း** — panel အဖြေများကို အမည်မဖော်ဘဲ (`Source 1`, `Source 2`, … — ထို့ကြောင့်
   judge သည် model အမှတ်တံဆိပ်မဟုတ်ဘဲ အကြောင်းအရာကို အလေးထားသည်) judge ထံ လွှဲပေးသည်။ ထို့နောက် judge က
   သဘောတူညီချက် / ဆန့်ကျင်ကွဲလွဲချက်များ / တစ်စိတ်တစ်ပိုင်းသာ ခြုံငုံမိမှု / ထူးခြားသော ထိုးထွင်းသိမြင်မှုများ / မမြင်မိသော အချက်များကို ခွဲခြမ်းစိတ်ဖြာပြီး
   ယုံကြည်အားထားရသော အဖြေ **တစ်ခုတည်း** ကို ရေးသားသည်။ Judge call သည် client ၏ မူလ
   `stream` flag နှင့် tools များကို ဆက်လက်ထိန်းသိမ်းထားသောကြောင့် streaming နှင့် downstream tool အသုံးပြုမှုတို့ ဆက်လက်အလုပ်လုပ်သည်။
4. **ချောမွေ့စွာ အဆင့်လျှော့လုပ်ဆောင်ခြင်း** — panel အဖြေ 0 ခု → `503`; အဖြေ 1 ခုတည်းသာ ကျန်ရှိခြင်း → ထိုအဖြေကို
   တိုက်ရိုက်ပြန်ပေးသည် (ပေါင်းစပ်စရာမရှိပါ); model တစ်ခုတည်းပါသော panel သည် တိုက်ရိုက်ဖြေဆိုသည်။

Panel အဖွဲ့ဝင်တစ်ခုသည် အခြား combo ကို ရည်ညွှန်းသော `combo-ref` အဆင့် (`{kind: "combo-ref", comboName: "..."}`) လည်း ဖြစ်နိုင်သည် —
၎င်းကို **black-box panel အသံတစ်ခုတည်း** အဖြစ် ဖြေရှင်းသည် (ရည်ညွှန်းထားသော combo သို့ အပြည့်အဝ recursive dispatch လုပ်ခြင်းဖြစ်ပြီး
ထို combo ၏ ကိုယ်ပိုင်ပစ်မှတ်များကို ဖြန့်ခွဲပို့ခြင်းမဟုတ်ပါ)။ ထို့ပြင် အခြား combo-ref အသုံးပြုသည့် မဟာဗျူဟာတိုင်းတွင် ရှိပြီးသား
တူညီသော depth/cycle ကာကွယ်မှုကို အသုံးပြုသည် (#6764)။

### ပြင်ဆင်သတ်မှတ်မှု

Combo ၏ `config` blob တွင် ပြင်ဆင်သတ်မှတ်သည် (schema migration မလိုအပ်ပါ — ရှိပြီးသား
`combos` table ကို ပြန်လည်အသုံးပြုသည်)-

| Field                                    | Type     | Default         | Purpose                                                                                                |
| :--------------------------------------- | :------- | :-------------- | :----------------------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | ပထမ panel model | နောက်ဆုံးအဖြေကို ပေါင်းစပ်ရေးသားသည့် model                                                             |
| `config.fusionTuning.minPanel`           | `number` | `2`             | grace timer မစတင်မီ လိုအပ်သော အောင်မြင်သည့်အဖြေ အရေအတွက် (`[2, panelSize]` အတွင်း ကန့်သတ်ထားသည်)       |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`          | quorum ပြည့်ပြီးနောက် နောက်ကျနေသူများကို စောင့်ဆိုင်းမည့်ကြာချိန်                                      |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`         | model တစ်ခု ရပ်တန့်နေခြင်းကြောင့် တောင်းဆိုမှု တစ်ခုလုံး မနှောင့်နှေးစေရန် အကြွင်းမဲ့အချိန်ကန့်သတ်ချက် |

မူလတန်ဖိုးများကို `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) တွင် ထည့်သွင်းထားသည်။

### ဥပမာ

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

ထို့နောက် မည်သည့် combo ကိုမဆို ခေါ်သကဲ့သို့ ၎င်းကို ခေါ်ပါ- `{"model":"fusion-panel","messages":[...]}`။

## Virtual Auto-Combo Factory

Auto Combo အင်ဂျင်သည် ကြိုတင်သတ်မှတ်ထားသော combo များကို မလိုအပ်ပါ။ ယင်းအစား `open-sse/services/autoCombo/virtualFactory.ts` သည် candidate များကို လိုအပ်သည့်အချိန်တွင် ချက်ချင်းတည်ဆောက်သည်-

1. `getProviderConnections({ isActive: true })` (ဖွင့်ထားသော connection အားလုံး) ကို ရယူသည်
2. မှန်ကန်သော credential များရှိသည့် connection များကို စစ်ထုတ်သည် (API key သို့မဟုတ် `hasUsableOAuthToken()` မှတစ်ဆင့် သက်တမ်းမကုန်သေးသော OAuth token)
3. Model ရရှိနိုင်မှုနှင့် ဈေးနှုန်းအတွက် `getProviderRegistry()` နှင့် အပြန်အလှန်တိုက်ဆိုင်စစ်ဆေးသည်
4. `(provider, model, connection)` tuple တစ်ခုစီအတွက် `VirtualAutoComboCandidate` တစ်ခု တည်ဆောက်သည်
5. Dispatch target အဖြစ် `connection.defaultModel` (သို့မဟုတ် registry ၏ ပထမဆုံး model) ကို ရွေးချယ်သည်
6. 16-factor `scorePool()` နှင့် variant ၏ weight pack ကို အသုံးပြု၍ candidate တစ်ခုစီကို အမှတ်ပေးသည်
7. `handleComboChat()` အတွက် ရရှိလာသော memory အတွင်းရှိ `AutoComboConfig` ကို ပြန်ပေးသည် — DB ထဲသို့ မည်သည့်အခါမျှ သိမ်းဆည်းထားခြင်းမရှိပါ

ဆိုလိုသည်မှာ **`auto/*` ဖွင့်ထားသော provider အသစ်တစ်ခုကို ထည့်သွင်းခြင်းသည် candidate pool ကို အလိုအလျောက်ချဲ့ထွင်ပေးသည်** — combo ကို ကိုယ်တိုင်ပြင်ဆင်ရန် မလိုအပ်ပါ။ Virtual combo ကို request တစ်ခုစီအတွက် ပြန်လည်တည်ဆောက်သောကြောင့် အသစ်ထည့်ထားသော သို့မဟုတ် ပြန်လည်ကျန်းမာလာသော connection များကို ချက်ချင်းရွေးချယ်နိုင်သည်။

## ကိုယ်တိုင်ပြန်လည်ပြုပြင်ခြင်း

- **ယာယီဖယ်ထုတ်ခြင်း**: Score < 0.2 → 5 min ကြာ ဖယ်ထုတ်မည် (တဖြည်းဖြည်းတိုးလာသော backoff၊ အများဆုံး 30 min)
- **Circuit breaker အခြေအနေကို သိရှိခြင်း**: OPEN → အလိုအလျောက်ဖယ်ထုတ်မည်၊ HALF_OPEN → စမ်းသပ် request များ
- **Incident mode**: >50% OPEN → exploration ကို ပိတ်ပြီး တည်ငြိမ်မှုကို အမြင့်ဆုံးဖြစ်စေမည်
- **Cooldown ပြီးနောက် ပြန်လည်ကောင်းမွန်ခြင်း**: ဖယ်ထုတ်မှုအပြီး ပထမဆုံး request သည် timeout လျှော့ထားသော "probe" တစ်ခုဖြစ်သည်

## Bandit Exploration

Request များ၏ 5% (ပြင်ဆင်သတ်မှတ်နိုင်သည်) ကို exploration အတွက် ကျပန်း provider များထံ လမ်းကြောင်းပြောင်းပို့သည်။ Incident mode တွင် ပိတ်ထားသည်။

## API

**သီးသန့် `POST /api/combos/auto` endpoint မရှိပါ** — Auto-Combo ကို နည်းလမ်းနှစ်မျိုးဖြင့် အသုံးပြုနိုင်ပါသည်-

1. **Zero-config (အကြံပြုထားသည်)-** `model: "auto"` သို့မဟုတ် `model: "auto/<variant>"` ဖြင့် မည်သည့် chat completion request ကိုမဆို ပေးပို့ပါ။ Virtual factory သည် request တစ်ခုချင်းစီအတွက် combo ကို တည်ဆောက်ပေးသည် — persistence မလိုအပ်သလို API call များလည်း မလိုအပ်ပါ။

2. **`strategy: "auto"` ပါဝင်သော persisted combo:** `POST /api/combos` မှတစ်ဆင့် ပုံမှန် combo တစ်ခု ဖန်တီးပြီး `strategy: "auto"` အပြင် `config.auto.weights` / `config.auto.candidatePool` ကို သတ်မှတ်ပါ။ တူညီသော scoring engine ကို အသုံးပြုသည်။ Combo ကို `combos` ထဲတွင် သိမ်းဆည်းထားပြီး ID ဖြင့် ပြန်လည်အသုံးပြုနိုင်သည်။

ရှာဖွေကြည့်ရှုရန်အတွက် `GET /api/combos/auto` သည် variant တစ်ခုချင်းစီကို ၎င်း၏ ဖြေရှင်းသတ်မှတ်ပြီးသား candidate pool နှင့်အတူ `context_length` / `max_output_tokens` တို့ဖြင့် စာရင်းပြုစုဖော်ပြသည် — ထိုတန်ဖိုးများသည် candidate pool ၏ window များအနက် အမြင့်ဆုံးတန်ဖိုးဖြစ်သည်။ Client များ (ဥပမာ opencode plugin) သည် `0` အစား ဤတန်ဖိုးများကို ကြေညာရမည်။ Context သုညဖြစ်ပါက opencode ၏ auto-compaction ကို လုံးဝပိတ်ထားသဖြင့် session များသည် gateway ၏ history purge ကြောင့် context ပျက်စီးသွားသည်အထိ ကြီးထွားလာနိုင်သည်။ MAX ကို ကြေညာခြင်းသည် ဘေးကင်းသည်၊ အကြောင်းမှာ auto-combo context pre-filter သည် အရွယ်အစားကျော်လွန်သော request များကို window အကြီးစား candidate များဆီ လမ်းကြောင်းပေးသောကြောင့်ဖြစ်သည်။

```bash
# Zero-config အသုံးပြုမှု (combo ဖန်တီးရန်မလို)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# ပုံမှန် combos endpoint မှတစ်ဆင့် persisted auto combo
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto router strategy များ

Persisted `strategy: "auto"` combo များတွင် `config.routerStrategy` (သို့မဟုတ် အဟောင်း
`config.auto.routerStrategy`) ကို အောက်ပါတို့အနက် တစ်ခုအဖြစ် သတ်မှတ်နိုင်သည်-

- `rules` — မူလ weighted scoring
- `score` — configure လုပ်ထားသော weighted score အမြင့်ဆုံးကို ရွေးချယ်သည်။ Score အတိအကျတူညီပါက configure လုပ်ထားသော
  candidate အစီအစဉ်ကို ထိန်းသိမ်းထားပြီး ရှိပြီးသား `explorationRate` သည် အဆင့်သတ်မှတ်ထားသော pool အပြည့်အစုံမှ နမူနာရွေးချယ်သည်။
- `cost` / `eco` — ကျန်းမာရေးကောင်းမွန်သော provider များအနက် စျေးအသက်သာဆုံး
- `latency` / `fast` — reliability penalty ပါဝင်သော အနိမ့်ဆုံး p95 latency
- `sla-aware` / `sla` — p95 latency၊ error-rate နှင့် ရွေးချယ်နိုင်သော
  cost SLO များကို ပြည့်မီသည့် candidate များအား ဦးစားပေးသည်
- `lkgp` — နောက်ဆုံးအကြိမ် အလုပ်လုပ်ကြောင်း သိရှိထားသော provider ကို ဦးစွာရွေးချယ်သည်
- `nadir` — prompt အတွက် pool ထဲရှိ မည်သည့် model လိုအပ်ကြောင်း [Nadir](https://getnadir.com) ၏ decision API ကို
  မေးမြန်းသည်။ အသုံးပြုရန် ရွေးချယ်ဖွင့်ထားရပြီး မအောင်မြင်ပါက `rules` သို့ fail-open လုပ်သည်

### Router strategy များ၏ အသေးစိတ်

Auto-combo engine သည် `config.routerStrategy` (သို့မဟုတ် အဟောင်း `config.auto.routerStrategy`)
မှတစ်ဆင့် အပြန်အလှန်လဲလှယ်အသုံးပြုနိုင်သော **RouterStrategy** implementation 7 ခုကို ဖော်ထုတ်ပေးသည်။
Strategy တစ်ခုချင်းစီသည် `RoutingContext`
(task အမျိုးအစား၊ tool/vision hint များ၊ token ခန့်မှန်းချက်၊ ရွေးချယ်နိုင်သော SLA policy၊ ရွေးချယ်နိုင်သော
နောက်ဆုံးအကြိမ် အလုပ်လုပ်ကြောင်း သိရှိထားသည့် provider) ကို အခြေခံ၍ candidate pool ထဲမှ provider တစ်ခုကို ရွေးချယ်သည်။

#### 1. `rules` (မူလ) — factor 16 ခုပါဝင်သော weighted scoring

လက်ရှိ scoring engine ကို ထုပ်ပိုးအသုံးပြုသည်။ `OPEN` circuit-breaker
candidate များကို ဖယ်ထုတ်ပြီး လက်ရှိ task အမျိုးအစားနှင့် `getTaskFitness()` ကို အသုံးပြု၍ `scorePool()` ကို လုပ်ဆောင်ကာ
score အမြင့်ဆုံး provider ကို ရွေးချယ်သည်။

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**အသုံးပြုသင့်သည့်အချိန်**: မူလရွေးချယ်မှုဖြစ်သည်။ Signal အားလုံးအကြား ဟန်ချက်ညီသော အပေးအယူကို လိုချင်သည့်အခါ အသုံးပြုပါ။

**Alias**: `rules` (alias မရှိ)

---

#### 2. `cost` / `eco` — ကျန်းမာရေးကောင်းမွန်သော provider များအနက် စျေးအသက်သာဆုံး

Candidate pool ကို `costPer1MTokens` အလိုက် (ငယ်စဉ်ကြီးလိုက်) စီပြီး စျေးအသက်သာဆုံးကို ရွေးချယ်သည်။
`OPEN` candidate များကို ဦးစွာ ဖယ်ထုတ်သည်။

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**အသုံးပြုသင့်သည့်အချိန်**: ကုန်ကျစရိတ်အထိခိုက်မခံနိုင်သော workload များ၊ batch processing သို့မဟုတ် background job များ။

**Alias များ**: `cost`, `eco`

---

#### 3. `latency` / `fast` — reliability penalty ပါဝင်သော အနိမ့်ဆုံး p95 latency

`p95LatencyMs + (errorRate * 1000)` အလိုက် စီသည်။ Error-rate penalty ကြောင့်
ယုံကြည်စိတ်ချရမှုမရှိသော provider များ၏ nominal latency နည်းနေလျှင်ပင် အဆင့်နိမ့်သွားစေသည်။

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**အသုံးပြုသင့်သည့်အချိန်**: Real-time chat၊ autocomplete သို့မဟုတ်
အပြန်အလှန်တုံ့ပြန်သည့် coding assistant ကဲ့သို့ latency အထိခိုက်မခံနိုင်သော workload များ။

**Alias များ**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — latency/error/cost SLO လိုက်နာမှု

Configure လုပ်ထားသော SLO policy ကို candidate တစ်ခုချင်းစီက မည်မျှကောင်းမွန်စွာ ပြည့်မီကြောင်းအပေါ် မူတည်၍ score သတ်မှတ်သည်-

| အချက်               | အလေးချိန် | ဖော်မြူလာ                                                                |
| ------------------- | --------- | ------------------------------------------------------------------------ |
| တုံ့ပြန်ချိန် ရမှတ် | 35%       | `threshold / max(value, ε)`                                              |
| အမှား ရမှတ်         | 35%       | `threshold / max(value, ε)`                                              |
| ကျန်းမာရေး ရမှတ်    | 15%       | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)                        |
| ကုန်ကျစရိတ် ရမှတ်   | 10%       | `threshold / max(value, ε)` သို့မဟုတ် ပြောင်းပြန် စံသတ်မှတ်ထားသောတန်ဖိုး |
| တည်ငြိမ်မှု ရမှတ်   | 5%        | တုံ့ပြန်ချိန် စံသွေဖည်မှု၏ ပြောင်းပြန် စံသတ်မှတ်ထားသောတန်ဖိုး            |

`hardConstraints: true` ဖြစ်သည့်အခါ၊ candidate များကို အဓိကအားဖြင့် **ချိုးဖောက်မှု ရမှတ်**
(SLO တစ်ခုခုကို မည်မျှကျော်လွန်သည်) အလိုက် စီပြီးနောက် ပေါင်းစပ်ရမှတ်အလိုက် စီသည်။ မဟုတ်ပါက
ပေါင်းစပ်ရမှတ်တစ်ခုတည်းကိုသာ အသုံးပြုသည်။

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... candidate တစ်ခုစီကို policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints } နှင့် နှိုင်းယှဉ်၍ ရမှတ်ပေးသည်
  }
}
```

**SLA field များ** (combo config တွင် သတ်မှတ်ရန်):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**အသုံးပြုသင့်သည့်အချိန်**: တုံ့ပြန်ချိန်၊ အမှားနှုန်း သို့မဟုတ် ကုန်ကျစရိတ် budget များကို တင်းကျပ်စွာ ကန့်သတ်ထားသော production workload များ။

**Alias များ**: `sla-aware`, `sla`

---

#### 5. `lkgp` — နောက်ဆုံးသိရှိထားသော ကောင်းမွန်သည့် provider ကို ဦးစွာအသုံးပြုခြင်း

သတ်မှတ်ထားပါက **နောက်ဆုံးသိရှိထားသော ကောင်းမွန်သည့် provider** ကို ဦးစွာ စမ်းသပ်ပြီးနောက်
`rules` strategy သို့ fallback လုပ်သည်။ Session stickiness အတွက် အသုံးဝင်ပြီး စကားဝိုင်းတစ်ခုရှိ
နောက်ဆက်တွဲ request များကို provider တစ်ခုတည်းက ကိုင်တွယ်ပေးသည်။

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // rules strategy သို့ fallback လုပ်သည်
    return getStrategy("rules").select(pool, context);
  }
}
```

**အသုံးပြုသင့်သည့်အချိန်**: နောက်ဆက်တွဲ request များကို provider တစ်ခုတည်းက ကိုင်တွယ်စေလိုသည့်
အကြိမ်များစွာ အပြန်အလှန်ပြောဆိုသော စကားဝိုင်းများ (ဥပမာ caching၊ context ဆက်လက်တည်ရှိမှု သို့မဟုတ် ဈေးနှုန်းတည်ငြိမ်မှုအတွက်)။

**Alias**: `lkgp` (alias မရှိပါ)

#### 6. `nadir` — Nadir မှတစ်ဆင့် prompt ကို အခြေခံသည့် model ရွေးချယ်မှု

အထက်ပါ strategy တိုင်းသည် မိမိတို့၏ telemetry အလိုက် candidate များကို အဆင့်သတ်မှတ်ပြီး ၎င်းတို့ထဲမှ မည်သည့် strategy ကမျှ
request ကို မဖတ်ပါ။ `nadir` သည် နောက်ဆုံး user turn နှင့် pool ၏ model id များကို
[Nadir](https://getnadir.com) ၏ ဆုံးဖြတ်ချက် API (`POST /v1/bucket`) သို့ ပေးပို့ပြီး ထိုစာရင်းမှ Nadir
ရွေးချယ်သည့် model ဆီသို့ route လုပ်သည် (`simple` → လုပ်ဆောင်နိုင်သည့် ဈေးအသက်သာဆုံး model၊ `complex` →
frontier model)။ ထို model ကို ဝန်ဆောင်မှုပေးသည့် connection ကို `rules` ကပင် ရွေးချယ်သောကြောင့် quota၊
ကျန်းမာရေးအခြေအနေနှင့် ကုန်ကျစရိတ်တို့က မည်သည့် account ကို အသုံးပြုမည်ကို ဆက်လက်ဆုံးဖြတ်သည်။

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` နှင့် `OMNIROUTE_NADIR_BASE_URL` တို့သည် string နှစ်ခုအတွက် env fallback များဖြစ်သည်။
`baseUrl` သည် self-hosted Nadir အတွက်သာ လိုအပ်သည် (နောက်ဆုံးတွင် `/v1` ပါရှိခြင်းကို လက်ခံသည်)။
Key မပါသော call များသည် IP တစ်ခုချင်းအလိုက် rate limit လုပ်ထားသည့် Nadir ၏ anonymous tier သို့ ရောက်ရှိသည်။

စက်အပြင်သို့ ထွက်သွားသည့်အရာများမှာ နောက်ဆုံး user message ၏ စာသား (ပထမ စာလုံးရေ 16k)၊ candidate
model id များနှင့် `source: "omniroute"` channel tag တို့ဖြစ်သည်။ System prompt၊ history၊ tool သို့မဟုတ်
header များ မပါဝင်ပါ။

Failure အပြုအမူသည် fail-open ဖြစ်သည်။ Timeout (မူလသတ်မှတ်ချက် 2000 ms)၊ non-2xx၊ ဆက်သွယ်၍မရသော
host၊ ပုံစံမမှန်သည့် response သို့မဟုတ် pool ပြင်ပရှိ ရွေးချယ်မှုတစ်ခု ဖြစ်ပေါ်ပါက `rules`
ဆုံးဖြတ်ချက်ကို အသုံးပြုပြီး အကြောင်းရင်း၏ရှေ့တွင် `NadirStrategy: fallback (…)` ကို ထည့်သွင်းသည်။ Call မအောင်မြင်ပြီးနောက်
strategy သည် network ကို 30 s ကြာ ကျော်သွားမည်ဖြစ်သဖြင့် service ပြတ်တောက်မှုတစ်ခုသည် request တိုင်းအတွက် timeout တစ်ကြိမ်စီ ဖြစ်စေမည့်အစား
30 s လျှင် timeout တစ်ကြိမ်သာ ဖြစ်စေသည်။ Nadir က အမှန်တကယ် ရွေးချယ်မှုပြုလုပ်ခဲ့သည့်အခါမှသာ routing event များက
`strategy: "nadir"` ဟု အစီရင်ခံသည်။

**အသုံးပြုသင့်သည့်အချိန်**: model tier များ (အသေးစား၊ အလယ်အလတ်နှင့် frontier model တစ်ခုစီ) ပါဝင်သော pool တွင်
ခက်ခဲမှုအဆင့်မျိုးစုံရှိသည့် traffic ကို ကိုင်တွယ်ရာ၌ အမြဲတမ်း frontier model အသုံးပြုခြင်းကြောင့် ဖြစ်ပေါ်သည့် ကုန်ကျစရိတ်ကို လျှော့ချလိုသည့်အခါ။

**Alias**: `nadir` (alias မရှိပါ)

### စိတ်ကြိုက် router strategy များ

Public API မှတစ်ဆင့် သင်၏ကိုယ်ပိုင် `RouterStrategy` implementation ကို register လုပ်နိုင်သည်-

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // သင်၏ routing logic ကို ဤနေရာတွင် ထည့်ပါ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

ထို့နောက် ၎င်းကို အသုံးပြုပါ-

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

### Router strategy ရွေးချယ်မှု လမ်းညွှန်

| အသုံးပြုမှုအခြေအနေ                      | Strategy    | အကြောင်းရင်း                                              |
| --------------------------------------- | ----------- | --------------------------------------------------------- |
| မျှတသော workload                        | `rules`     | မူလသတ်မှတ်ချက် — အချက်အားလုံးကို ထည့်သွင်းစဉ်းစားသည်      |
| ကုန်ကျစရိတ် အနည်းဆုံးဖြစ်စေရန်          | `cost`      | ဈေးအသက်သာဆုံးကို အမြဲရွေးချယ်သည်                          |
| တုံ့ပြန်ချိန် အနည်းဆုံးဖြစ်စေရန်        | `latency`   | အမြန်ဆုံးနှင့် ယုံကြည်စိတ်ချရသော provider ကို ရွေးချယ်သည် |
| တင်းကျပ်သော SLO များ                    | `sla-aware` | p95/error/cost threshold များအလိုက် စစ်ထုတ်သည်            |
| အကြိမ်များစွာ အပြန်အလှန်ပြောဆိုသော chat | `lkgp`      | Session stickiness                                        |
| ခက်ခဲမှုအဆင့်မျိုးစုံ                   | `nadir`     | Prompt တစ်ခုချင်းအလိုက် model tier ကို ရွေးချယ်သည်        |

```json
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

## Auto Variant များ အကျဉ်းချုပ်

မူရင်းဖြစ်သည့် သီးသန့် `auto` နှင့် `autoPrefix.ts` တွင် ကြေညာထားသော `AutoVariant` တန်ဖိုး 6 ခုအပါအဝင်၊ **ခေါ်ယူအသုံးပြုနိုင်သော model ID 7 ခု** ရှိသည်-

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ကိုယ်တိုင်သည် တန်ဖိုး 6 ခုကို စာရင်းပြုထားသည်။ 7 ခုမြောက်ရွေးချယ်စရာမှာ "variant မရှိခြင်း" — သီးသန့် `auto` — ဖြစ်ပြီး `parseAutoPrefix()` က `variant: undefined` အဖြစ် ကိုင်တွယ်သည်။)

## အဆင့်များသည် Auto-Combo နှင့် မည်သို့ ကိုက်ညီသနည်း

အချက် 16 ချက်ပါ အမှတ်ပေးလုပ်ဆောင်ချက် (`open-sse/services/autoCombo/scoring.ts`) သည် အဆင့်အဖွဲ့ဝင်ဖြစ်မှုကို အချက်ပြမှုနှစ်ခုအဖြစ် သတ်မှတ်သည်- `tierPriority` (0.0476) နှင့် `tierAffinity` (0.0476) တို့ဖြစ်သည်။ `DEFAULT_WEIGHTS` အစုအပြည့်အစုံအတွက် အထက်ပါ စံသတ်မှတ်ထားသော [အမှတ်ပေးအချက်ဇယား](#how-it-works-persisted-auto-combos) ကို ကြည့်ပါ — pack တစ်ခုချင်းစီအလိုက် အစားထိုးသတ်မှတ်ချက်များ (ship-fast/cost-saver/quality-first/
offline-friendly) ကို "Pack တစ်ခုချင်းစီအလိုက် Weight profile များ" ဇယားတွင် ဖော်ပြထားသည်။

အဆင့်တစ်ခုတည်းကြောင့် Tier 1 ကို ဦးစွာအသုံးပြုရန် **အတင်းအကျပ် မသတ်မှတ်ပါ** — Tier 1 ၏ တုံ့ပြန်ကြာချိန် မကောင်းပါက သို့မဟုတ် ကုန်ကျစရိတ်နှင့် အရည်အသွေး အချိုးအစား မသင့်တော်ပါက Tier 2 က ရွေးချယ်ခံရမည်ဖြစ်သည်။ အဆင့်အစဉ်ကို အတင်းအကျပ်သတ်မှတ်ရန် combo မဟာဗျူဟာ `priority` ကို အသုံးပြုပြီး provider များကို အဆင့်အလိုက် စီစဉ်ပါ။

Tier 1 (subscription) ကို အထူးဦးစားပေးရန် `tierPriority` weight ကို တိုးမြှင့်ပါ-

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

အဆင့်သတ်မှတ်ချက်များနှင့် provider အမျိုးအစားခွဲခြားမှုအတွက် [`docs/guides/TIERS.md`](../guides/TIERS.md) ကို ကြည့်ပါ။
