## ခြုံငုံသုံးသပ်ချက်

Quota Sharing Engine သည် ချိတ်ဆက်မှုတစ်ခုတည်းကို မျှဝေသုံးစွဲသည့် API key အများအပြားအကြား provider ၏ အချိန်အခြေပြု quota (ဥပမာ Codex ၏ 5 နာရီ window၊ Kimi ၏ တစ်နာရီလျှင် request 1500) ကို မျှတစွာ ခွဲဝေပေးသည်။

**ဖြေရှင်းပေးသည့် ပြဿနာ:** OmniRoute သည် upstream provider account တစ်ခုတည်းသို့ API key အများအပြားကို proxy ပြုလုပ်ပေးသည်။ မျှဝေခြင်းဆိုင်ရာ logic မရှိပါက key A မှ ရုတ်တရက်များပြားလာသော အသုံးပြုမှုသည် တစ်နာရီအတွက် provider quota ကို ကုန်ဆုံးစေနိုင်ပြီး window ပြန်လည်သတ်မှတ်ချိန်အထိ key B နှင့် C တို့ကို ပိတ်ဆို့ထားစေနိုင်သည်။ Engine သည် အောက်ပါနည်းလမ်းများဖြင့် ယင်းကို ကာကွယ်သည်-

1. Dimension တစ်ခုချင်းစီ (ရာခိုင်နှုန်း၊ request များ၊ token များ၊ $) အလိုက် key တစ်ခုချင်းစီ၏ rolling consumption ကို ခြေရာခံခြင်း။
2. Work-conserving fair-share algorithm ကို အသုံးပြုခြင်း- global pool ပြည့်နှက်မနေသေးသရွေ့ key တစ်ခုသည် အသုံးမပြုထားသော share များမှ ချေးယူနိုင်သည်။
3. Request သည် upstream executor သို့ မရောက်ရှိမီ hot path (`chatCore.ts`) တွင် ရလဒ်ကို မဖြစ်မနေလိုက်နာစေခြင်း။

## Algorithm: Fair-Share Work-Conserving

`src/lib/quota/fairShare.ts` တွင် အကောင်အထည်ဖော်ထားသည်။

### Mode များ

| အခြေအနေ                                    | Mode         | လုပ်ဆောင်ပုံ                                                                     |
| ------------------------------------------ | ------------ | -------------------------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **Generous** | Key သည် သုံးစွဲပြီးသော စုစုပေါင်းကို နုတ်ထားသည့် global limit အထိ ချေးယူနိုင်သည် |
| `globalUsedPercent >= saturationThreshold` | **Strict**   | တစ်ခုချင်းစီ၏ မျှတသော share ကို တင်းကျပ်စွာ လိုက်နာစေသည်                         |

မူလသတ်မှတ်ထားသော `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`) ဖြစ်သည်။

### Dimension တစ်ခုချင်းစီအလိုက် ဆုံးဖြတ်ချက်

Pool အတွင်းရှိ အသုံးပြုနေသော dimension တစ်ခုချင်းစီအတွက် engine သည် အောက်ပါတို့ကို တွက်ချက်သည်-

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

ထို့နောက်-

- **`policy = hard`**: `consumed > fairShareAllowed` ဖြစ်ပြီး mode သည် strict ဖြစ်ပါက → **ပိတ်ဆို့မည်**။
- **`policy = soft`**: `consumed > fairShareAllowed` ဖြစ်ပြီး mode သည် strict ဖြစ်ပါက → **ပြစ်ဒဏ်သတ်မှတ်မည်** (combo အတွင်း ဦးစားပေးမှုလျှော့ချမည်၊ hard-block လုံးဝမလုပ်ပါ)။
- **`policy = burst`**: fair share ကို မထည့်သွင်းစဉ်းစားဘဲ global headroom ရှိနေသရွေ့ ခွင့်ပြုမည်။

### အကြွင်းမဲ့ ကန့်သတ်ချက်

Allocation တစ်ခုရှိ `capValue` + `capUnit` သည် mode သို့မဟုတ် policy နှင့် မသက်ဆိုင်သော အမြင့်ဆုံး hard ceiling ဖြစ်သည်။ `consumed >= capValue` ဖြစ်သည့် မည်သည့် dimension မဆို request ကို အမြဲတမ်း **ပိတ်ဆို့မည်**။

### Dimension များစွာကို စစ်ဆေးခြင်း

Pool အတွင်းရှိ dimension တစ်ခုခုက ပိတ်ဆို့မည်ဆိုပါက request ကို ပိတ်ဆို့မည်။ Dimension များသည် တစ်ခုနှင့်တစ်ခု သီးခြားဖြစ်သည် — 5h% ကုန်ဆုံးခြင်းသည် weekly% dimension ကို မသက်ရောက်ပါ။

### ချေးယူခြင်း

Generous mode တွင် မိမိ၏ allocation ကို အပြည့်အဝ မသုံးစွဲရသေးသော key သည် အခြား key များ၏ အသုံးမပြုရသေးသော share များမှ ပိုလျှံမှုကို အသုံးပြုနိုင်သည်။ Formula မှာ-

```
maxAllowed = globalLimit - consumedByOtherKeys
```

ဤနေရာတွင် `consumedByOtherKeys = consumedTotal - consumedByThisKey` ဖြစ်သည်။ Global ceiling (ထို dimension အတွက် pool `limit`) သည် အမြဲတမ်း အမြင့်ဆုံး hard ceiling ဖြစ်သည်။

## Sliding Window Counter

`src/lib/quota/sqliteQuotaStore.ts` နှင့် `redisQuotaStore.ts` တို့တွင် အကောင်အထည်ဖော်ထားသည်။

`(apiKeyId, dimensionKey)` တစ်ခုလျှင် bucket နှစ်ခုရှိသည်-

- `curr`: လက်ရှိ bucket (`floor(nowMs / windowMs)`)
- `prev`: ယခင် bucket (`curr - 1`)

ထိရောက်သော rolling value-

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**တိကျမှု**: ~99% တိကျသည်။ Bucket များအကြား နယ်နိမိတ်တွင် အမှားပမာဏသည် window အရွယ်အစား၏ အများဆုံး 1% ဖြစ်သည် (bucket 2 ခုဖြင့် ခန့်မှန်းခြင်းတွင် ပင်ကိုအားဖြင့် ရှိနေသည့် အမှားဖြစ်သည်)။

### တစ်ပြိုင်နက်လုပ်ဆောင်မှု

SQLite driver: `(apiKeyId | dimensionKey)` key တစ်ခုချင်းစီအတွက် in-memory mutex သည် read-modify-write race ကို ကာကွယ်ပေးသည်။ Pattern သည် `src/sse/services/auth.ts` ၏ anti-thundering-herd ပုံစံအတိုင်း ဖြစ်သည်။

Redis driver: atomic increment အတွက် Lua EVAL script ကို အသုံးပြုသည် — Redis command တစ်ခုတည်းအဖြစ် လုပ်ဆောင်သည်။

## Driver များ

### SQLite (မူလသတ်မှတ်ချက်၊ ထည့်သွင်းရန်မလို)

- Table: `quota_consumption` (migration `073_quota_pools.sql` / `074_quota_consumption.sql` ကို ကြည့်ပါ)။
- Instance တစ်ခုတည်း အသုံးပြုသည့် deployment များအတွက် အသင့်တော်ဆုံးဖြစ်သည်။
- Persistence အားလုံးကို လက်ရှိ OmniRoute SQLite DB (`DATA_DIR/storage.sqlite`) တွင် သိမ်းဆည်းထားသည်။

### Redis (ရွေးချယ်နိုင်၊ instance အများအပြား)

- `ioredis` npm package လိုအပ်သည်။
- Counter များကို Redis တွင် သိမ်းဆည်းပြီး metadata (pool/allocation များ) ကို SQLite တွင် ဆက်လက်သိမ်းဆည်းသည်။
- Counter များကို အတူမျှဝေရန်လိုအပ်သည့် replica အများအပြားပါသော deployment များအတွက် အသင့်တော်ဆုံးဖြစ်သည်။

### Driver များ ပြောင်းလဲခြင်း

Settings UI (`/dashboard/settings` → Quota Store) မှတစ်ဆင့် သို့မဟုတ် env var များမှတစ်ဆင့် ပြောင်းလဲနိုင်သည်-

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

DB setting သည် env ထက် ဦးစားပေးသည်။ `driver=redis` ဖြစ်သော်လည်း URL မရှိလျှင် သို့မဟုတ်
`ioredis` ကို ထည့်သွင်းမထားလျှင် factory သည် SQLite သို့ ပြန်လည်အသုံးပြုပြီး သတိပေးချက်တစ်ခုကို log မှတ်တမ်းတင်သည်။

Driver ရွေးချယ်မှုအစဉ်-

1. DB setting `quotaStore.driver`
2. Env `QUOTA_STORE_DRIVER`
3. မူလသတ်မှတ်ချက်- `sqlite`

## Dimension အများအပြား

Pool တစ်ခုတွင် dimension အများအပြား ရှိနိုင်သည်။ Dimension တစ်ခုစီသည် သီးခြားလွတ်လပ်သည်-

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // ဤ dimension အတွက် pool တစ်ခုလုံး၏ အများဆုံးကန့်သတ်ချက်
}
```

**ဥပမာ- Codex plan** (5h% + weekly%)-

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

Request တစ်ခုကို ခွင့်ပြုရန် dimension အားလုံး၏ သတ်မှတ်ချက်များကို ပြည့်မီရမည်။

## Pipeline ပေါင်းစည်းမှု

### PRE hook (`open-sse/handlers/chatCore.ts`)

Auth နှင့် policy စစ်ဆေးမှုများပြီးနောက်၊ upstream executor မတိုင်မီ လုပ်ဆောင်သည်-

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → dimension တစ်ခုစီအတွက် getQuotaStore().peek()
      → fairShare.decideFairShare()
      → block ဖြစ်လျှင် → 429 ကို ပြန်ပို့ (buildErrorBody၊ Hard Rule #12)
      → allow + deprioritize ဖြစ်လျှင် → candidate တွင် quotaSoftPenalty=true သတ်မှတ်
  → executor.execute()
```

**Fail-open**- `enforceQuotaShare` က error ဖြစ်လျှင် request ကို ဆက်လက်ဖြတ်သန်းခွင့်ပြုပြီး
`pino.warn` log တစ်ခု မှတ်တမ်းတင်သည်။ ယင်းက quota-engine bug တစ်ခုကြောင့် traffic
အားလုံး ပိတ်ဆို့ခံရခြင်းကို ကာကွယ်ပေးသည်။

### POST hook (သုံးစွဲမှုကို မှတ်တမ်းတင်ခြင်း)

အောင်မြင်သော response တစ်ခုပြီးနောက်-

```
executor က success ပြန်ပေးသည်
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → dimension တစ်ခုစီအတွက် getQuotaStore().consume()
      → fail-open- error များကို pino.warn အဖြစ် log မှတ်တမ်းတင်ပြီး client ထံ မည်သည့်အခါမျှ ဆက်လက်မပို့
```

**Drift မှတ်ချက်**- response ပြန်ပို့ပြီးနောက် `consume` မအောင်မြင်လျှင် rolling counter သည်
အမှန်ထက် လျော့နည်းရေတွက်သည်။ Provider ထံမှ saturation signal (ဥပမာ
`anthropic-ratelimit-unified-5h-utilization`) သည် နောက် request တွင် global estimate ကို
ပြင်ဆင်ပေးသည်။

### Combo soft penalty (`open-sse/services/combo.ts`)

`decision.deprioritize === true` ဖြစ်သည့်အခါ-

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // မူလသတ်မှတ်ချက် 0.7
}
```

Penalty ကို အခြား scoring factor အားလုံးပြီးနောက် အသုံးချသည်။ ၎င်းသည် ပြည့်လုနီးပါးဖြစ်နေသော key တစ်ခုကို
အပြီးတိုင်ပိတ်ဆို့ခြင်းမရှိဘဲ auto-combo က ရွေးချယ်နိုင်ခြေကို လျှော့ချပေးသည်။

## Environment Variable များ

| Variable                           | မူလတန်ဖိုး | ဖော်ပြချက်                                                                              |
| ---------------------------------- | ---------- | --------------------------------------------------------------------------------------- |
| `QUOTA_STORE_DRIVER`               | `sqlite`   | အသုံးပြုမည့် driver- `sqlite` သို့မဟုတ် `redis`                                         |
| `QUOTA_STORE_REDIS_URL`            | _(အလွတ်)_  | Redis URL၊ ဥပမာ `redis://localhost:6379`                                                |
| `QUOTA_SATURATION_THRESHOLD`       | `0.5`      | 0..1; `>= threshold` ဖြစ်ပါက strict mode ကို ဖွင့်သည်                                   |
| `QUOTA_SOFT_DEPRIORITIZE_FACTOR`   | `0.7`      | 0..1; soft-policy combo score အတွက် မြှောက်ဖော်ကိန်း                                    |
| `QUOTA_CONSUMPTION_RETENTION_DAYS` | `14`       | GC က `quota_consumption` bucket အဟောင်းများကို မဖယ်ရှားမီ ထိန်းသိမ်းထားမည့် ရက်အရေအတွက် |

DB setting များ (`quotaStore.*`) သည် env var များထက် ဦးစားပေးသည်။

## ပြဿနာဖြေရှင်းခြင်း

### Redis ကို စီစဉ်သတ်မှတ်ထားသော်လည်း ချိတ်ဆက်၍မရခြင်း

`ioredis` ကို ထည့်သွင်းထားကြောင်း (`npm ls ioredis`) နှင့် `QUOTA_STORE_REDIS_URL`
ကို ဆက်သွယ်နိုင်ကြောင်း စစ်ဆေးပါ။ ချိတ်ဆက်မှု မအောင်မြင်ပါက factory သည် SQLite သို့ ပြန်လည်အသုံးပြုမည် (`warn`
အဆင့်ဖြင့် log မှတ်တမ်းတင်သည်)။

### `peek` က ဒေတာဟောင်းကို ပြန်ပေးခြင်း / fail-open ဖြစ်ခြင်း

`peek` က error ပစ်ပါက `enforceQuotaShare` သည် ရလဒ်ကို "ခွင့်ပြုသည်" (fail-open) ဟု သတ်မှတ်သည်။
အခြေခံအကြောင်းရင်းကို ဖော်ထုတ်ရန် `pino` log များထဲရှိ `quota:enforce` နှင့် `quota:factory` entry များကို
စစ်ဆေးပါ။

### သုံးစွဲမှု counter ကွာဟခြင်း

Provider ၏ အမှန်တကယ်အသုံးပြုမှုသည် counter များနှင့် ကွာခြားပါက မျှော်လင့်ထားသည့် အခြေအနေဖြစ်သည် —
2-bucket sliding window တွင် window နယ်နိမိတ်များ၌ ~1% အမှားရှိပြီး `consume` ကို
response ပြန်ပေးပြီးနောက် fire-and-forget ပုံစံဖြင့် လုပ်ဆောင်သည်။ Saturation signal (`saturationSignals.ts`)
သည် အမှန်တကယ် provider အသုံးပြုမှုကို 30 စက္ကန့် TTL ဖြင့် ဖတ်ရှုပြီး `globalUsedPercent`
ကို လိုက်လျောညီထွေ ချိန်ညှိသည်။

### Pool တွင် burn rate အတွက် "ဒေတာမရှိ" ဟု ပြခြင်း

`computeBurnRate` သည် အနည်းဆုံး သမိုင်းဆိုင်ရာ sample 2 ခု လိုအပ်သည်။ ယခင်
`consume` call မရှိသော pool အသစ်များတွင် `tokensPerSecond: 0` နှင့် `timeToExhaustionMs: null` ဟု ပြမည်။

## localStorage မှ ရွှေ့ပြောင်းခြင်း

`/dashboard/costs/quota-share` ကို ပထမဆုံး ဖွင့်သည့်အခါ hook ဖြစ်သော `useLocalStoragePoolMigration` က အောက်ပါတို့ကို စစ်ဆေးသည်-

1. `localStorage.getItem("omniroute:quota-share:pools")` သည် ဗလာမဟုတ်ပါ။
2. `GET /api/quota/pools` က `[]` ကို ပြန်ပေးသည် (DB သည် ဗလာဖြစ်သည်)။

နှစ်ချက်စလုံး မှန်ကန်ပါက legacy pool တစ်ခုစီကို batch အဖြစ် `POST /api/quota/pools` သို့ ပို့ပြီးနောက်
localStorage key ကို ဖယ်ရှားသည်။ ဤရွှေ့ပြောင်းမှုသည် idempotent ဖြစ်သည်- အခြေအနေ 2 က
ထပ်မံရွှေ့ပြောင်းခြင်းကို တားဆီးပေးသည်။

## အတွင်းပိုင်း Strategy အမျိုးအစားခွဲခြားခြင်း

`quota-share` သည် **အတွင်းပိုင်းအတွက်သာ** အသုံးပြုသည့် routing strategy ဖြစ်သည် (`src/shared/constants/routingStrategies.ts` ရှိ
`INTERNAL_ROUTING_STRATEGY_VALUES`)။ ၎င်းကို system မှ ထုတ်ပေးသော
`qtSd/` pool combo များအတွက်သာ သီးသန့်အသုံးပြုပြီး UI သို့မဟုတ် API တွင် အသုံးပြုသူရွေးချယ်နိုင်သည့်
option အဖြစ် မည်သည့်အခါမျှ မပေါ်စေရန် `ROUTING_STRATEGY_VALUES` မှ တမင်ဖယ်ထုတ်ထားသည်။

## DB Schema အနှစ်ချုပ်

migration `078`, `079` နှင့် `085` တို့က ထည့်သွင်းထားသော table သုံးခု-

- `quota_pools` + `quota_allocations` — pool သတ်မှတ်ချက်များနှင့် key တစ်ခုချင်းစီအလိုက် allocation များ။
- `quota_consumption` — `(apiKeyId, dimensionKey)` တစ်စုံစီအတွက် အလှည့်ကျ 2-bucket counter များ။
- `provider_plans` — provider plan ကို ကိုယ်တိုင် override လုပ်ထားမှုများ (connectionId တစ်ခုစီအတွက် dimensions JSON)။

table အားလုံးကို idempotent ဖြစ်သော `CREATE TABLE IF NOT EXISTS` migration များမှတစ်ဆင့် ထည့်သွင်းထားသည်။
