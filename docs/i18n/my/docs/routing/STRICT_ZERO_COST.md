> အလိုအလျောက်မဖွင့်ထားဘဲ အသုံးပြုသူက ရွေးချယ်ဖွင့်ရမည် (`settings.freeAccessPolicy !== "strict"` ဖြစ်ပါက `auto/*`
> candidate pool တိုင်းသည် byte တစ်ခုချင်းအထိ လုံးဝမပြောင်းလဲပါ)။ ငွေကြေးအပိုကုန်ကျမှု မည်သည့်အမျိုးအစားကိုမဆို
> လုံးဝမဖြစ်စေရန် ခိုင်မာသောအာမခံချက် လိုအပ်သည့် operator များအတွက် `hidePaidModels`
> (`open-sse/services/autoCombo/paidModelFilter.ts`, #6512) ထက် ပိုမိုတင်းကျပ်သော sibling တစ်ခုဖြစ်ပြီး
> "အခမဲ့ဟု စာတမ်းတွင် ဖော်ပြထားခြင်း" တစ်ခုတည်းကိုသာ အခြေမခံပါ။

## ဤအရာ ရှိရသည့်အကြောင်းရင်းနှင့် `hidePaidModels` တစ်ခုတည်းဖြင့် မလုံလောက်သည့်အကြောင်းရင်း

`hidePaidModels` သည် "ယခုအချိန်တွင် ဤ model ကို `FREE_MODEL_BUDGETS` ထဲ၌ အခမဲ့အဖြစ်
အမျိုးအစားခွဲထားသလား?" ဆိုသည်ကို ဖြေကြားပေးသည် — ၎င်းသည် အချိန်တစ်ခုအတွင်းရှိ catalog အချက်အလက်ဖြစ်ပြီး
`isFreeModel()`/`providerHasFreeModels()` (`src/shared/utils/freeModels.ts`) မှတစ်ဆင့် စစ်ဆေးသည်။
သို့သော် အောက်ပါ လက်တွေ့အန္တရာယ်နှစ်ခုအကြောင်းကို မည်သည့်အရာမျှ မဖော်ပြပါ-

1. `recurring-*`/`one-time-initial` free tier ၏ ခွင့်ပြုအသုံးပြုနိုင်သည့် ပမာဏသည်
   **ကုန်ဆုံးသွားနိုင်သည်** — catalog တွင် model ကို အခမဲ့အဖြစ် ဆက်လက်ဖော်ပြနေသော်လည်း
   ၎င်းနောက်ကွယ်ရှိ account တွင် ဆက်လက်အသုံးပြုနိုင်သည့် ပမာဏ မကျန်တော့ပါ။
2. Free tier ကို ကျော်လွန်အသုံးပြုခြင်းသည် အမြဲတမ်း ရပ်တန့်သွားမည်ဟု မဆိုလိုပါ။ အချို့ provider များက
   payment method ကို လုံးဝချိတ်ဆက်၍မရနိုင်ကြောင်း ("credit card မလိုအပ်ပါ") အတိအလင်း
   ဖော်ပြထားသော်လည်း အခြား provider များက မဖော်ပြထားပါ။ အနည်းငယ်သော provider များသည်
   အခမဲ့ခွင့်ပြုချက် ကျော်လွန်သွားပါက အလိုအလျောက် ငွေကောက်ခံပါသည်။

`hidePaidModels` သည် ဤအခြေအနေများကို ခွဲခြား၍မရပါ — ထိုသို့ပြုလုပ်ရန် အစကတည်းက ရည်ရွယ်ထားခြင်း
မဟုတ်ပါ။ STRICT_ZERO_COST သည် category/tier အဆင့်သတ်မှတ်ခြင်း **မပြုမီ** နှင့်
dispatch **မပြုမီ** candidate တစ်ခုချင်းစီအလိုက် ဤစစ်ဆေးမှုနှစ်ခုကို တိတိကျကျ ထည့်သွင်းပေးသည် —
request ထွက်သွားပြီးနောက်မှ မည်သည့်အခါမျှ စစ်ဆေးခြင်းမပြုပါ။

## Candidate အမျိုးအစားခွဲခြားခြင်း

Pool အတွင်းရှိ candidate တိုင်းအတွက် (`open-sse/services/autoCombo/virtualFactory.ts::buildPreparedPool`,
`filterPaidOnlyCandidates` ပြီးပြီးချင်း)-

1. **`FREE_MODEL_BUDGETS` ထဲတွင် လုံးဝမရှိပါက** → ဖယ်ထုတ်မည်။ ၎င်းသည် အမှန်တကယ် အခကြေးငွေပေးရသော
   model များနှင့် OmniRoute က မခွဲခြားရသေးသော provider/model များအားလုံးကို အကျုံးဝင်သည် —
   candidate အသစ်များကို ထည့်သွင်းထားခြင်းမဟုတ်ဘဲ ဖယ်ထုတ်ထားခြင်းဖြင့် စတင်သည်။
2. **`freeType: "keyless"`** → ချက်ချင်း အောင်မြင်မည်၊ **သို့သော် no-auth path မှ အမှန်တကယ်
   ဝင်ရောက်လာသော candidate အတွက်သာ** ဖြစ်သည် (`connectionId === SYNTHETIC_NOAUTH_CONNECTION_ID`,
   `open-sse/services/autoCombo/resilienceCandidateFilter.ts`)။ ထို candidate အတွက် credential
   မရှိသဖြင့် ၎င်းကို အသုံးပြုသည့် request တစ်ခုအတွက် မည်သည့်အခါမျှ ငွေကောက်ခံ၍မရပါ —
   runtime စစ်ဆေးမှု မလိုအပ်သကဲ့သို့ ပြုလုပ်၍လည်း မရပါ။ Catalog တွင် `keyless` အဖြစ် သတ်မှတ်ထားသော
   တူညီသည့် provider/model ကို **အမှန်တကယ်ရှိသော** DB connection မှတစ်ဆင့် ရယူထားပါက
   (`connectionId` သည် အမှန်တကယ်ရှိသော connection id ဖြစ်ခြင်း သို့မဟုတ် candidate တွင်
   `allowedConnectionIds` ပါရှိခြင်း) ဤ shortcut ကို **မရပါ** — `keyless` metadata သည်
   provider တစ်ခုလုံးကို မဟုတ်ဘဲ no-auth path ကိုသာ သီးသန့်ဖော်ပြပြီး အမှန်တကယ် credential
   အသုံးပြုထားသော account ကို မည်သည့်အခါမျှ ခွင့်ပြုမပေးပါ။ ထိုကဲ့သို့သော candidate သည်
   အခြား candidate များကဲ့သို့ စစ်ဆေးမှု 3 သို့ ဆက်လက်ရောက်ရှိပြီး catalog entry တွင်
   `hardStopGuaranteed: true` ကို သီးခြားထည့်သွင်းထားခြင်းမရှိပါက ဖယ်ထုတ်ခံရမည်
   (အမှန်တကယ်ရှိသော `keyless` entry များတွင် ယင်းတန်ဖိုး မည်သည့်အခါမျှ မပါဝင်ပါ —
   shortcut သည် ၎င်းတို့အတွက် တစ်ခုတည်းသော ဘေးကင်းသည့်လမ်းကြောင်းဖြစ်သည်)။
3. **အခြားမည်သည့် `freeType` မဆို** (`recurring-daily`, `recurring-monthly`, `recurring-credit`,
   `recurring-uncapped`, `one-time-initial` နှင့် ဤ module က အထူးကိုင်တွယ်ခြင်းမပြုသည့်
   အနာဂတ် type များ) → အောက်ပါအချက်များ **အားလုံး** ပြည့်မီမှသာ အောင်မြင်မည်-
   - Catalog entry (`FreeModelBudget.hardStopGuaranteed`,
     `open-sse/config/freeModelCatalog.ts`) တွင် `hardStopGuaranteed: true` သတ်မှတ်ထားရမည် —
     ၎င်းသည် provider ကိုယ်တိုင် ထုတ်ပြန်ထားသော စည်းကမ်းချက်များ (ဥပမာ အတိအလင်းဖော်ပြထားသော
     "credit card မလိုအပ်ပါ" ဆိုသည့် ကြေညာချက်) နှင့်ပတ်သက်သည့် **စိစစ်ရွေးချယ်ပြီး
     ကိုယ်တိုင်သတ်မှတ်ထားသော အချက်အလက်** ဖြစ်သည်။ `freeType` သို့မဟုတ် live API response မှ
     မည်သည့်အခါမျှ ဆင်းသက်တွက်ချက်ထားခြင်း မဟုတ်ပါ။ မသတ်မှတ်ထားခြင်း (`undefined`) နှင့်
     `false` နှစ်မျိုးစလုံးကို "အာမခံမထားပါ" ဟု သတ်မှတ်သည်။
   - `USAGE_FETCHER_PROVIDERS` (`open-sse/services/usage.ts`) ထဲတွင် provider အတွက်
     usage adapter ရှိရမည် — ၎င်းသည် quota dashboard နှင့် `getUsageForProvider()` တို့ကို
     ပံ့ပိုးပေးနေပြီးသား registry နှင့် တစ်ခုတည်းဖြစ်သည်။ Adapter မရှိပါက → adapter
     ထည့်သွင်းသည့်အချိန်အထိ အမြဲတမ်း ဖယ်ထုတ်ထားမည်။
   - **လက်ရှိ အမှန်တကယ် အကဲဖြတ်နေသော သီးခြား connection** အတွက် live cached
     `FreeAccessState` သည် `status: "SAFE"` ဖြစ်ရမည်၊
     `settings.autoRefreshProviderQuotaInterval` အတွင်း စစ်ဆေးထားရမည်
     (မူလတန်ဖိုး 180s — နံပါတ်အသစ်မဟုတ်ဘဲ ရှိပြီးသား setting)၊ ထို့ပြင်
     `remainingFreeAllowance` သည် အနည်းငယ်သော ဘေးကင်းရေးအရန်ပမာဏထက် ပိုများကြောင်း
     ဖော်ပြရမည်။
4. **`freeType: "discontinued"`** → အမြဲတမ်း ဖယ်ထုတ်မည်။

## ချိတ်ဆက်မှု ဘေးကင်းရေး (ချိတ်ဆက်မှုတစ်ခုချင်းအလိုက် စစ်ဆေးခြင်း၊ candidate တစ်ခုချင်းအလိုက် မဟုတ်ပါ)

auto-combo pool ထဲရှိ candidate တစ်ခုသည် ချိတ်ဆက်မှုတစ်ခုတည်းနှင့် အမြဲတမ်း ချိတ်ဆက်ထားသည် မဟုတ်ပါ။ "logical" candidate တစ်ခု
(`connectionId: null`) တွင် `allowedConnectionIds` allowlist တစ်ခု ပါဝင်ပြီး — ယင်း၌ တောင်းဆိုမှုကို ဖြည့်ဆည်းပေးနိုင်သည့် အမှန်တကယ်
provider ချိတ်ဆက်မှုများ/အကောင့်များ တစ်ခု သို့မဟုတ် တစ်ခုထက်ပို၍ ပါဝင်သည် — အမှန်တကယ် အသုံးပြုမည့် အကောင့်ကိုမူ နောက်ပိုင်း dispatch ပြုလုပ်ချိန်တွင် `open-sse/services/combo/autoStrategy.ts`
က ဆုံးဖြတ်သည် (`allowedConnectionIds` ကို ၎င်း၏ ကိုယ်ပိုင် ချိတ်ဆက်မှုရွေးချယ်ရေး logic နှင့် intersection လုပ်ခြင်း၊ ~line 315-331)။

STRICT_ZERO_COST သည် ထို allowlist ထဲရှိ **ချိတ်ဆက်မှုတစ်ခုချင်းစီ၏ free-access အခြေအနေကို
သီးခြားစီ** စစ်ဆေးပြီး (`strictZeroCostFilter.ts` ထဲရှိ `evaluateCandidateConnections()`) `allowedConnectionIds` ကို `SAFE` ပြန်ရရှိခဲ့သည့် subset အတိအကျသာ ကျန်ရှိအောင် ပြန်လည်ရေးသားသည် — မူလစာရင်း အပြည့်အစုံကို ဘယ်တော့မှ မသုံးသကဲ့သို့ ကျပန်းရွေးချယ်ထားသည့် member တစ်ခုတည်းကိုလည်း ဘယ်တော့မှ မသုံးပါ။ အတိအကျအားဖြင့်-

- Account A သည် `SAFE` ဖြစ်ပြီး account B သည် `UNKNOWN`/ကုန်ဆုံးသွားခြင်း/ငွေကောက်ခံနိုင်ခြင်း ဖြစ်ပါက → A တစ်ခုတည်းသာ ရွေးချယ်နိုင်တော့သည်။
- အကောင့်အားလုံး `UNKNOWN` ဖြစ်ပါက → candidate ကို လုံးဝဖယ်ရှားသည် (safe set အလွတ်)။
- မအောင်မြင်သည့် single-connection candidate (`connectionId` ကို တိုက်ရိုက်သတ်မှတ်ထားပြီး allowlist မရှိခြင်း) ကို ချက်ချင်းဖယ်ရှားကာ `allowedConnectionIds` အလွတ်ဖြင့် ဘယ်တော့မှ ပြန်မပေးပါ။

`autoStrategy.ts` သည် dispatch လုပ်မည့် ချိတ်ဆက်မှုကို မရွေးချယ်မီ `allowedConnectionIds` ကို hard allowlist အဖြစ် ရှိပြီးသားအတိုင်း enforce လုပ်ထားသောကြောင့် ၎င်းကို စစ်ဆေးပြီးသော `SAFE` subset ဖြင့် ပြန်လည်ရေးသားခြင်းက dispatch ပြုလုပ်ရာတွင် အမှန်တကယ် အသုံးပြုသည့် ချိတ်ဆက်မှုသည် ဤ filter ကိုယ်တိုင် စစ်ဆေးထားသည့် ချိတ်ဆက်မှု အမြဲဖြစ်ကြောင်း အာမခံရန် လုံလောက်သည် — တူညီသော candidate ပေါ်ရှိ အခြား မစစ်ဆေးရသေးသည့် အကောင့်တစ်ခု ဘယ်တော့မှ မဖြစ်ပါ။ regression အထောက်အထားအတွက်
`tests/unit/autoCombo/strict-zero-cost-connection-safety.test.ts` ကို ကြည့်ပါ
(keyless-bypass case A/B/C၊ multi-account case 1-5)။

`discovered automatically` ဆိုသည်မှာ မှန်ကန်သော metadata ပါရှိသည့် provider/model တစ်ခုကို နောက်တစ်နေ့တွင် ထုတ်ပေးလိုက်ပါက (catalog ထဲတွင်ရှိခြင်း၊ usage adapter ပါရှိခြင်း၊ `hardStopGuaranteed: true` ဖြစ်ခြင်း) OmniRoute က ၎င်းကို သိရှိသည်နှင့် ချက်ချင်းအသုံးပြုနိုင်ခြင်းကို ဆိုလိုသည် — code ပြောင်းလဲရန် မလို၊ whitelist entry ထည့်ရန် မလိုသကဲ့သို့ ဤ module ထဲတွင်လည်း မည်သည့်အရာကိုမျှ ပြင်ဆင်ရန် မလိုပါ။ catalog မှ ဖယ်ရှားလိုက်သည့်အရာသည်လည်း အလားတူပင် ပျောက်ကွယ်သွားသည်။ regression အထောက်အထားအတွက်
`tests/unit/autoCombo/strict-zero-cost-autodiscovery.test.ts` ကို ကြည့်ပါ (တကယ့် catalog ကို ပြောင်းလဲခြင်းမဟုတ်ဘဲ injectable fixture များမှတစ်ဆင့် စမ်းသပ်ထားသည်)။

## Quota cache ပြုလုပ်ခြင်း (`open-sse/services/autoCombo/freeAccessQuota.ts`)

`getUsageForProvider()` ကို ပြန်လည်အသုံးပြုသည် — ဒုတိယ quota စနစ် မရှိပါ။ တောင်းဆိုမှုနှုန်းသည် Telegram အရွယ်အစားအထိ မြင့်မားနေသော်လည်း တောင်းဆိုမှုတစ်ခုစီရှိ candidate တစ်ခုစီအတွက် live billing-API call တစ်ခု မဖြစ်ပေါ်စေရန် ၎င်း၏ရှေ့တွင် သက်တမ်းတိုသော၊ in-memory၊
process-lifetime cache တစ်ခု ထားရှိထားသည် (TTL သည် မူလသတ်မှတ်ထားသော
`autoRefreshProviderQuotaInterval` နှင့် ညီသည်)။ ဖတ်ရှုမှုများသည် synchronous ဖြစ်သည်။ cache miss တစ်ခုသည်
`undefined` ကို ပြန်ပေးပြီး (→ ဖယ်ထုတ်ခြင်း၊ fail-closed) _နောက်တစ်ကြိမ်_ ဖတ်ရှုမှုအတွက် background refresh တစ်ခု စတင်ပေးသည် —
candidate-pool တည်ဆောက်သည့် လမ်းကြောင်းထဲရှိ မည်သည့်အရာကမျှ network call တစ်ခုကို စောင့်ဆိုင်းခြင်း မရှိပါ။

ချိတ်ဆက်မှုတစ်ခုသည် မည်သည့်အကြောင်းကြောင့်မဆို မအောင်မြင်သည့်အချိန်တွင်
`src/sse/services/auth.ts::markAccountUnavailable()` မှ
`invalidateFreeAccessState(provider, connectionId)` ကို ခေါ်သည်။ ထို့ကြောင့် နောက်တစ်ကြိမ် pool တည်ဆောက်ရာတွင် stale ဖြစ်နေသော `SAFE` entry အစား သန့်ရှင်းသော cache miss တစ်ခုကို ချက်ချင်းဖတ်ယူသည် —
402/403/quota-exhausted response တစ်ခု ရရှိပြီးနောက် TTL ကုန်ဆုံးသည်အထိ စောင့်ဆိုင်းရန် မလိုပါ။

## ToS အကာအကွယ် (စီးပွားရေးဆိုင်ရာ ဘေးကင်းမှုနှင့် သီးခြားဖြစ်သည်)

(`FreeModelBudget.tos`) က `"avoid"` ဖြစ်သည့် မည်သည့် candidate ကိုမဆို ဖယ်ရှားသည် — `hidePaidModels` နှင့် အဆင့်တူ docs ဖြစ်သော

`freeAccessPolicy` နှင့် ရည်ရွယ်ချက်ရှိရှိ သီးခြားခွဲထားသည်- candidate တစ်ခုသည် စီးပွားရေးအရ `SAFE` ဖြစ်နိုင်သော်လည်း စာချုပ်ဆိုင်ရာ

နှစ်ခုစလုံး တူညီနေခဲ့သည် — candidate သည် ရိုးရှင်းစွာ ပျောက်ကွယ်သွားခြင်းသာ ဖြစ်သည်။

**ကွာဟချက်တစ်ခု ကျန်ရှိနေဆဲဖြစ်ပြီး၊ ယင်းမှာ ရည်ရွယ်ချက်ရှိရှိ ချန်ထားခြင်းဖြစ်သည်။** `excludeTosAvoid` သည် listing ကို
မတည်ဆောက်မီ candidate များကို ဖယ်ရှားနေဆဲဖြစ်သောကြောင့် `tos: "avoid"` ဟု စိစစ်သတ်မှတ်ထားသော model သည် အကြောင်းပြချက်မဖော်ပြဘဲ
မပါရှိတော့ပါ — ဤအပိုင်းက zero-cost အကာအကွယ်အတွက် ယခုလေးတင် ဖြေရှင်းလိုက်သည့် မမြင်နိုင်မှုနှင့် အတူတူပင်ဖြစ်သည်။
၎င်းကိုပါ ဖြေရှင်းရန် ToS ကြောင့် ဖယ်ရှားမှုတွင် မည်သည့်အရာကို အစီရင်ခံသင့်ကြောင်း ဆုံးဖြတ်ရန်လိုပြီး၊ ယင်းသည် စီးပွားရေးဆိုင်ရာ
ဘေးကင်းမှုနှင့် သီးခြားမေးခွန်းတစ်ခုဖြစ်သည်။ ဤစာမျက်နှာသည် ကွာဟချက်မရှိဟု ဟန်ဆောင်မည့်အစား ၎င်းကို ဖော်ပြထားသည်။

offline before/after စစ်ဆေးမှုအတွက် `npx tsx scripts/ad-hoc/dry-run-strict-zero-cost.ts` သည် live instance တစ်ခု၏
candidates output နှင့် အလုပ်လုပ်နေဆဲဖြစ်သည်။ ၎င်းသည် candidate တစ်ခုချင်းစီ၏ အမှန်တကယ် `connectionId` ကို ဖတ်သောကြောင့်
connection-safety path ကိုလည်း စမ်းသပ်သည်။ Keyless candidate များသည် connection အစစ်မဟုတ်ဘဲ ပုံတူဖန်တီးထားသော
no-auth `connectionId` ဖြင့်သာ ရောက်ရှိရမည်။ လက်ရှိ ထည့်သွင်းပေးထားသော keyless auto path သည် OpenCode Free ဖြစ်သည်။ candidate အရေအတွက်အတိအကျသည်
live model discovery အပေါ် မူတည်နေဆဲဖြစ်ပြီး run အဟောင်းတစ်ခုမှ ကူးယူမည့်အစား ပစ်မှတ် deployment တွင် တိုင်းတာသင့်သည်။
`recurring-*` candidate တစ်ခုသည် စာရင်းသွင်းထားသော usage adapter နှင့် `hardStopGuaranteed: true` နှစ်ခုစလုံးရှိမှသာ
အောင်မြင်သည်။ မပြည့်စုံသော metadata သည် fail-closed အဖြစ် ဆက်လက်ရှိနေသည်။

`excludeTosAvoid: true` ဖြင့် `tos: "avoid"` ဟု စိစစ်သတ်မှတ်ထားသော candidate တိုင်းကို ဖယ်ရှားသည်။ OpenCode Free
တွင် လက်ရှိ ထိုဆုံးဖြတ်ချက် ရှိနေသောကြောင့် အကာအကွယ်ကို ဖွင့်ခြင်းသည် deployment တစ်ခု၏ ကျန်ရှိသော keyless
pool ကို ဗလာဖြစ်စေနိုင်သည်။ ဤသည်မှာ bug မဟုတ်ဘဲ ToS အကာအကွယ်ကို ဖွင့်ခြင်းကြောင့် မျှော်လင့်ထားသည့် အလဲအလှယ်တစ်ခုဖြစ်သည်။
အတိအကျ ဤအကြောင်းပြချက်ကြောင့် အကာအကွယ်၏ မူလတန်ဖိုးသည် `false` ဖြစ်သည် (အထက်ရှိ "ToS အကာအကွယ်" ကို ကြည့်ပါ)။

## ဖွင့်ထားခြင်း

```json
PUT /api/settings
{ "freeAccessPolicy": "strict", "excludeTosAvoid": false }
```

ဆက်တင်အသစ်နှစ်ခုစလုံးသည် အင်္ဂါရပ်မထည့်သွင်းမီက တန်ဖိုးများ (`"off"` / `false`) ကို မူလတန်ဖိုးအဖြစ် အသုံးပြုသည် — ထို့ကြောင့် နှစ်ခုစလုံးကို မဖွင့်ထားပါက လက်ရှိ `auto/*` လမ်းကြောင်းရွေးချယ်မှု အပြုအမူများကို ပြောင်းလဲမည်မဟုတ်ပါ။
