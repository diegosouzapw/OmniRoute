Web Cookie ပံ့ပိုးသူများသည် OmniRoute အား API key အစား သင့်လက်ရှိ browser session မှတစ်ဆင့် AI ဝန်ဆောင်မှုတစ်ခုကို အသုံးပြုနိုင်စေသည်။ ဝန်ဆောင်မှုတစ်ခုကို ၎င်း၏ website မှတစ်ဆင့် အသုံးပြုခွင့်ရှိပြီးဖြစ်ကာ OmniRoute ကိုလည်း အလားတူ အထောက်အထားစိစစ်ပြီးသော session ကို အသုံးပြုစေလိုသည့်အခါ ၎င်းတို့သည် အသုံးဝင်သည်။

API-key ပံ့ပိုးသူများနှင့်မတူဘဲ Web Cookie ပံ့ပိုးသူများသည် သင့် browser က website သို့ ပေးပို့သည့် အထောက်အထားများကို အသုံးပြု၍ အထောက်အထားစိစစ်သည်။

# မစတင်မီ

> **အရေးကြီးသည်:** အထောက်အထားများကို browser ၏ cookie storage မှ ကူးယူခြင်းမပြုဘဲ **တိုက်ရိုက် network request** တစ်ခုမှသာ အမြဲကူးယူပါ။

အထောက်အထားစိစစ်ခြင်းဆိုင်ရာ ပြဿနာအများအပြားသည် နေရာမှားမှ cookie များကို ကူးယူခြင်းကြောင့် ဖြစ်ပေါ်သည်။

## Cookie Storage မှ မကူးယူပါနှင့်

Browser အများစုသည် သိမ်းဆည်းထားသော cookie များကို အောက်ပါနေရာမှတစ်ဆင့် ပြသပေးသည်-

```
DevTools
→ Application (သို့မဟုတ် Storage)
→ Cookies
```

ဤ cookie များသည် မှန်ကန်သည့်ပုံပေါ်သော်လည်း ၎င်းတို့သည်-

- သက်တမ်းလွန်နေနိုင်သည်
- မပြည့်စုံနိုင်သည်
- အထောက်အထားစိစစ်ထားသော request များတွင်သာ ပေးပို့သည့် cookie များ မပါဝင်နိုင်သည်

ဤတန်ဖိုးများသည် မှန်ကန်သည့်ပုံပေါ်နေသော်လည်း ၎င်းတို့ကို အသုံးပြုပါက အထောက်အထားစိစစ်ခြင်း မအောင်မြင်နိုင်ပါ။

## တိုက်ရိုက် Request တစ်ခုမှ ကူးယူပါ

ထိုသို့မလုပ်ဘဲ အောင်မြင်သော request တစ်ခုမှ cookie များကို အသုံးပြုပါ-

```
DevTools
→ Network
→ စာမျက်နှာကို ပြန်လည်စတင်ပါ
→ chat သို့မဟုတ် conversation request တစ်ခုကို ဖွင့်ပါ
→ Request Headers
→ Cookie
```

`Cookie` request header တွင် သင့် browser က အောင်မြင်စွာ အသုံးပြုခဲ့သည့် အတိအကျ အထောက်အထားစိစစ်မှု အချက်အလက်များ ပါဝင်သည်။

Web Cookie ပံ့ပိုးသူအများစုအတွက် ဤတန်ဖိုးကို OmniRoute ထဲသို့ ကူးထည့်သင့်သည်။

# အထွေထွေ ပြင်ဆင်သတ်မှတ်မှု

Web Cookie ပံ့ပိုးသူအများစုအတွက် ပြင်ဆင်သတ်မှတ်မှု လုပ်ငန်းစဉ်သည် အတူတူပင်ဖြစ်သည်။

1. ပံ့ပိုးသူ၏ website သို့ ဝင်ရောက်ပါ။
2. Browser ၏ Developer Tools ကို ဖွင့်ပါ။
3. **Network** tab ကို ဖွင့်ပါ။
4. စာမျက်နှာကို ပြန်လည်စတင်ပါ။
5. အထောက်အထားစိစစ်ထားသော chat သို့မဟုတ် conversation request တစ်ခုကို ဖွင့်ပါ။
6. လိုအပ်သော အထောက်အထားစိစစ်မှု အချက်အလက်များကို ကူးယူပါ။
7. OmniRoute ကို ဖွင့်ပါ။
8. **Providers → Add Provider** သို့ သွားပါ။
9. သင်၏ Web Cookie ပံ့ပိုးသူကို ရွေးချယ်ပါ။
10. အထောက်အထားများကို ကူးထည့်ပါ။
11. **Test Connection** ကို နှိပ်ပါ။
12. ပံ့ပိုးသူကို သိမ်းဆည်းပါ။

လိုအပ်သော အထောက်အထား အတိအကျသည် ပံ့ပိုးသူအပေါ် မူတည်သည်။

> Web Cookie ပံ့ပိုးသူအသစ်များ ထည့်သွင်းသည့်အခါ သို့မဟုတ် လက်ရှိပံ့ပိုးသူများ၏ အထောက်အထားစိစစ်မှု လိုအပ်ချက်များ ပြောင်းလဲသည့်အခါ ဤဇယားကို အပ်ဒိတ်လုပ်ပါ။

## NoTrack (notrack-web)

NoTrack ([notrack.ai](https://notrack.ai)) သည် အကောင့်ဖွင့်ရန် မလိုအပ်သော အခမဲ့ အသုံးပြုသူသုံး chat platform တစ်ခုဖြစ်သည် — ပထမဆုံး ဝင်ရောက်ချိန်တွင် session ကို အမည်မဖော်ဘဲ ဖန်တီးပြီး `uid`, `si_usr_id` နှင့် `si_ses_id` ဟူသော cookie သုံးခုမှတစ်ဆင့် ဆက်လက်တည်ရှိစေသည်။ OmniRoute သည် model id တစ်ခုတည်း (`notrack-c`, alias `ntw`) မှတစ်ဆင့် တူညီသော `/api/dispatch` endpoint ကို proxy လုပ်ပေးသည်။

### ချိတ်ဆက်ရန် အဆင့်များ

1. သင့် browser တွင် [notrack.ai](https://notrack.ai) ကိုဖွင့်ပြီး အမည်မဖော်သော session cookie ကို သတ်မှတ်ခွင့်ပြုပါ။
2. **DevTools → Network** ကိုဖွင့်ပြီး စာမျက်နှာကို refresh လုပ်ကာ `/api` request တစ်ခုခုကို နှိပ်ပါ။
3. **Request Headers** တွင် `Cookie` header တန်ဖိုးအပြည့်အစုံကို ကူးယူပါ။
4. OmniRoute တွင် **Providers → Add Provider → NoTrack Web (Free)** သို့သွားပါ။
5. Cookie string ကို `apiKey` field ထဲသို့ ကူးထည့်ပြီး **Save** လုပ်ပါ။

OmniRoute သည် ကူးထည့်ထားသော string မှ `uid`, `si_usr_id` နှင့် `si_ses_id` တို့ကို ထုတ်ယူပြီး အဆိုပါအတွဲများသာ ပါဝင်သည့် သန့်ရှင်းသော `Cookie` header ကို ပြန်လည်တည်ဆောက်သည် — ထို့အပြင် ရှိနေပါက `nt_session` (အကောင့်ဝင်ထားသော account များအတွက် သတ်မှတ်ထားသည့် `ntk_…` token) ကိုလည်း ထည့်သွင်းသည်။ သုံးခုအနက် တစ်ခုခု မပါရှိပါက operator များက အခြားပုံစံများဖြင့် စမ်းသပ်နိုင်ရန် မူရင်းကူးထည့်ထားသော string ကို မပြောင်းလဲဘဲ ဆက်လက်ပေးပို့သည်။

### Model id များ

| Model id    | ပြသမည့်အမည် | မှတ်ချက်များ                                             |
| ----------- | ----------- | -------------------------------------------------------- |
| `notrack-c` | NoTrack C   | မူလသတ်မှတ်ချက် — upstream dispatch model `C`။            |
| `C`         | NoTrack C   | `notrack-c` အတွက် alias (မူရင်း upstream dispatch code)။ |
| `notrack`   | NoTrack C   | `notrack-c` အတွက် alias။                                 |
| `ntw`       | NoTrack C   | `notrack-c` အတွက် အတိုကောက် alias။                       |

Model id လေးခုစလုံးသည် တူညီသော upstream dispatch model (`C`) သို့ ချိတ်ဆက်သည်။

### Request ရွေးချယ်စရာများ

Executor သည် request body ပေါ်ရှိ အောက်ပါ optional field များကို လက်ခံသည်-

| Body field            | မူလတန်ဖိုး | ရည်ရွယ်ချက်                                                                                 |
| --------------------- | ---------- | ------------------------------------------------------------------------------------------- |
| `notrack_mode`        | `usual`    | Dispatch mode (လွတ်လပ်စွာ သတ်မှတ်နိုင်သော string; upstream သည် `usual`, … တို့ကို လက်ခံသည်) |
| `notrack_max_turns`   | `6`        | အဖြေမပေးမီ upstream က ပြုလုပ်နိုင်သည့် အတွင်းပိုင်း turn အရေအတွက်။                          |
| `notrack_chat_id`     | `null`     | ရှိပြီးသား upstream chat ကို ပြန်လည်ဆက်လက်လုပ်ဆောင်ရန် (chat အသစ်အတွက် မထည့်ပါနှင့်)။       |
| `notrack_attachments` | `[]`       | Upstream attachment descriptor များ၏ ဖြတ်သန်းပေးပို့မည့် array။                             |
| `notrack_regenerate`  | `false`    | ယခင် turn အတွက် အဖြေကို ပြန်လည်ထုတ်ပေးရန် တောင်းဆိုလိုပါက `true` ဟု သတ်မှတ်ပါ။              |

### စွမ်းဆောင်ရည်များ

- **Streaming နှင့် non-streaming** chat completion များ။
- **Tool calling** — request တွင် `tools: [...]` ကို သတ်မှတ်ပါ။ Executor သည် ၎င်းတို့ကို tool-call envelope contract အဖြစ် serialize လုပ်ပြီး model ၏ response များကို OpenAI `tool_calls` အဖြစ် ပြန်လည် parse လုပ်သည်။
- **`response_format`** — `json_object` နှင့် `json_schema` တို့ကို ပံ့ပိုးထားသည်။ Executor သည် model ၏ reply မှ ပထမဆုံး JSON object ကို ထုတ်ယူကာ မပြန်ပို့မီ string အဖြစ် ပြောင်းလဲသည်။
- **Reasoning hint** — upstream က `thinking` event တစ်ခု ပေးပို့သည့်အခါ executor သည် `reasoning` delta တစ်ခုကို ထုတ်ပေးသည်။

### ကန့်သတ်ချက်များ

- Upstream သည် အမည်မဖော်သော အသုံးပြုမှု quota များကို ကန့်သတ်ထားသည် — ကန့်သတ်ချက်ပြည့်သွားပါက executor သည် နားလည်ရလွယ်ကူသော message တစ်ခုနှင့်အတူ 429 ကို ဖော်ပြသည်။
- Model id အားလုံးသည် တူညီသော upstream dispatch model သို့သာ ညွှန်းဆိုသည်။ Model တစ်ခုချင်းစီအလိုက် ပြောင်းလဲရွေးချယ်နိုင်ခြင်း မရှိပါ။
- Executor သည် upstream ၏ `/api/chats` endpoint ကို မခေါ်သောကြောင့် chat history / session များကို အလိုအလျောက် စီမံမပေးပါ။ ရှိပြီးသား upstream chat ကို ပြန်လည်ဆက်လက်လုပ်ဆောင်ရန် `notrack_chat_id` ကို အသုံးပြုပါ။

# Web Cookie Provider များ လုပ်ဆောင်နိုင်သည့်အရာနှင့် မလုပ်ဆောင်နိုင်သည့်အရာ

Web Cookie provider များသည် website တစ်ခု၏ chat interface ကို ပြန်လည်အသုံးပြုသည်။ ၎င်းတို့သည် တရားဝင် API များနှင့် တူညီသော စွမ်းဆောင်ရည်များကို **မပေးပါ**။

## ပံ့ပိုးထားသော လုပ်ဆောင်ချက်များ

- လက်ရှိ browser session ကို အသုံးပြု၍ authentication ပြုလုပ်ခြင်း
- သင့်အကောင့်မှ ရရှိနိုင်သော models များကို အသုံးပြုခြင်း
- Chat တုံ့ပြန်ချက်များကို stream လုပ်ခြင်း
- API key မလိုအပ်ခြင်း

## ပံ့ပိုးမထားသော လုပ်ဆောင်ချက်များ

- Function calling
- Tool calling
- အလိုအလျောက် file editing
- Agentic IDE workflows
- API တွင်သာ ရရှိနိုင်သော လုပ်ဆောင်ချက်များ

ဤသည်မှာ မျှော်လင့်ထားသည့် လုပ်ဆောင်ပုံဖြစ်ပြီး **bug မဟုတ်ပါ**။

Tool execution၊ အလိုအလျောက် file editing သို့မဟုတ် အခြား agent workflows များ လိုအပ်ပါက Web Cookie provider အစား **API-key provider** ကို အသုံးပြုပါ။

# Validation ဆိုင်ရာ သတိပြုရန်အချက်

**Test Connection** အောင်မြင်ခြင်း သို့မဟုတ် cookie validation အောင်မြင်ခြင်းသည် ပေးထားသော credentials များသည် မျှော်လင့်ထားသည့် format နှင့် ကိုက်ညီပုံရကြောင်းကိုသာ အတည်ပြုပေးပါသည်။

Issue #7857 ကို မဖြေရှင်းရသေးသရွေ့ validation အောင်မြင်ခြင်းက provider သည် authentication အောင်မြင်မည်ဟု **အာမမခံပါ**။

Authentication မအောင်မြင်သေးပါက credentials များကို browser cookie storage မှ ကူးယူထားခြင်းမဟုတ်ဘဲ လက်ရှိအသုံးပြုနေသော network request တစ်ခုမှ ကူးယူထားကြောင်း စစ်ဆေးပါ။

---

# ပြဿနာဖြေရှင်းခြင်း

## Authentication မအောင်မြင်ခြင်း

Credentials များကို အောက်ပါနေရာမှ ကူးယူထားကြောင်း စစ်ဆေးပါ-

```
Network
→ Request Headers
→ Cookie
```

အောက်ပါနေရာမှ **မဟုတ်ရပါ**-

```
Application
→ Cookies
```

---

## Cookie သည် Browser တွင် အလုပ်လုပ်သော်လည်း OmniRoute တွင် အလုပ်မလုပ်ခြင်း

Provider အချို့တွင် authenticated requests ပြုလုပ်သည့်အချိန်၌သာ ပေးပို့သော cookies များ ပါဝင်ပါသည်။

Conversation တစ်ခုကို အောင်မြင်စွာ ဖွင့်ပြီးနောက် network request အသစ်တစ်ခုမှ credentials များကို ထပ်မံကူးယူပါ။

---

## Session သက်တမ်းကုန်ဆုံးခြင်း

Web Cookie providers များသည် သင့်လက်ရှိ browser session ကို အသုံးပြုပါသည်။

သင့် browser session သက်တမ်းကုန်ဆုံးသွားပါက သို့မဟုတ် sign out လုပ်လိုက်ပါက credentials အသစ်တစ်စုံကို ကူးယူရပါမည်။ ပံ့ပိုးထားသော web providers များအတွက် cookie သက်တမ်းတိုးခြင်းကို အလိုအလျောက်လုပ်ဆောင်ရန် [Browser Session Sync Extension](../guides/SESSION-SYNC-EXTENSION.md) companion tool ကို ကြည့်ပါ။

---

## Test Connection အောင်မြင်သော်လည်း Requests များ မအောင်မြင်ခြင်း

Issue #7857 ကို မဖြေရှင်းရသေးသရွေ့ validation အောင်မြင်ခြင်းက authentication request အောင်မြင်မည်ဟု အာမမခံပါ။

နောက်ထပ်ပြဿနာမဖြေရှင်းမီ authenticated request အသစ်တစ်ခုမှ သင့် credentials များကို ထပ်မံကူးယူပါ။

---

# Provider နမူနာ

Provider အလိုက် ပြည့်စုံသော လုပ်ဆောင်ပုံအဆင့်ဆင့်အတွက် အောက်ပါတို့ကို ကြည့်ပါ-

- **Claude Web** — `docs/providers/CLAUDE_WEB.md`

Claude Web လမ်းညွှန်သည် Web Cookie provider တစ်ခုအတွက် ပြည့်စုံသော setup လုပ်ငန်းစဉ်ကို သရုပ်ပြထားပြီး reference implementation အဖြစ် အသုံးပြုနိုင်ပါသည်။

---

# အကောင်းဆုံး လုပ်ဆောင်နည်းများ

- လက်ရှိ authenticated request အသစ်တစ်ခုမှ credentials များကို ကူးယူပါ။
- Cookies အဟောင်းများကို ပြန်လည်အသုံးပြုခြင်းမှ ရှောင်ကြဉ်ပါ။
- Web Cookie providers များကို အသုံးပြုနေစဉ် သင့် browser session ကို active ဖြစ်နေအောင် ထားပါ။
- ကူးယူထားသော cookies များကို အရေးကြီးလျှို့ဝှက် credentials များအဖြစ် သဘောထားပါ။
- Function calling သို့မဟုတ် agent workflows များ လိုအပ်သည့်အခါ API-key providers များကို အသုံးပြုပါ။
