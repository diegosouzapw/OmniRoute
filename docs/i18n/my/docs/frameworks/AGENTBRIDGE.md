AgentBridge သည် IDE AI agent များထံမှ HTTPS traffic ကို ကြားဖြတ်ဖမ်းယူပြီး OmniRoute ၏ တစ်စုတစ်စည်းတည်းသော routing engine မှတစ်ဆင့် လမ်းကြောင်းပြန်ညွှန်းပေးသည့် OmniRoute ၏ MITM (Man-in-the-Middle) proxy ဖြစ်သည်။ ၎င်းသည် Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code နှင့် Trae (စုံစမ်းလေ့လာနေဆဲ) ဟူသော **IDE agent 10 ခု** ကို ပံ့ပိုးထားပြီး စျေးကွက်ရှိ AI coding assistant များအတွက် အကျယ်ပြန့်ဆုံး လွှမ်းခြုံပေးသည့် MITM proxy အဖြစ် OmniRoute ကို ရပ်တည်စေသည်။

**Dashboard တည်နေရာ:** `/dashboard/tools/agent-bridge`
**Sidebar အုပ်စု:** Tools (Cloud Agents နောက်တွင်)
**ထပ်မံကြည့်ရှုရန်:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — ကြားဖြတ်ဖမ်းယူထားသော traffic အားလုံးကို အချိန်နှင့်တစ်ပြေးညီ စောင့်ကြည့်ရန်၊ `docs/security/MITM-TPROXY-DECRYPT.md` (git တွင်ရှိပြီး `/docs` ထဲသို့ compile မလုပ်ထားပါ) — `/api/tools/agent-bridge/tproxy` route မှ မောင်းနှင်သည့် Linux TPROXY transparent-decrypt ဖမ်းယူမှု mode။

## §1 ခြုံငုံသုံးသပ်ချက်

### AgentBridge ဆိုတာဘာလဲ?

IDE agent တစ်ခု (ဥပမာ GitHub Copilot, Cursor, Claude Code) က API ခေါ်ဆိုမှုတစ်ခု ပြုလုပ်သည့်အခါ၊ ၎င်းသည် upstream AI provider (OpenAI, Anthropic စသည်) ထံ တိုက်ရိုက်ချိတ်ဆက်သည်။ AgentBridge သည် agent ၏ configuration ကို ပြောင်းလဲရန် မလိုအပ်ဘဲ TLS အဆင့်တွင် ထိုချိတ်ဆက်မှုကို ပွင့်လင်းစွာ ကြားဖြတ်ဖမ်းယူပြီး request ကို OmniRoute မှတစ်ဆင့် ပြန်လည်ရေးသားပေးသည်။

ထို့ကြောင့် အောက်ပါတို့ကို လုပ်ဆောင်နိုင်သည်-

- **မည်သည့် agent ကိုမဆို မည်သည့် provider ထံမဆို လမ်းကြောင်းပြန်ညွှန်းနိုင်သည်**: Copilot က OpenAI နှင့် ဆက်သွယ်နေပါသလား? ၎င်းကို Anthropic Claude, Gemini သို့မဟုတ် OmniRoute ၏ provider 352 ခုအနက် မည်သည့် provider ထံမဆို ပြန်ညွှန်းနိုင်သည်။
- **Model mapping များ အသုံးချနိုင်သည်**: handler အဆင့်တွင် `gemini-3-flash` → `claude-sonnet-4.7` သို့ ပွင့်လင်းစွာ mapping ပြုလုပ်နိုင်သည်။
- **Agent traffic အားလုံးကို စောင့်ကြည့်နိုင်သည်**: ကြားဖြတ်ဖမ်းယူထားသော request တိုင်းကို [Traffic Inspector](./TRAFFIC_INSPECTOR.md) ထံ ထုတ်လွှင့်ပေးသည်။
- **OmniRoute ၏ ခံနိုင်ရည်စွမ်းရည်များကို အသုံးချနိုင်သည်**: combo routing, circuit breaker များ၊ fallback များနှင့် ကုန်ကျစရိတ်ခြေရာခံခြင်းတို့သည် IDE agent traffic အတွက်လည်း အလုပ်လုပ်သည်။

## §2 ဗိသုကာဖွဲ့စည်းပုံ

### 2.1 အစိတ်အပိုင်းများ၏ ခြုံငုံသုံးသပ်ချက်

```
IDE Agent (VS Code / Cursor / စသည်)
    │  HTTPS (port 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← DNS လမ်းကြောင်းပြောင်းခြင်း
    │
    ▼
src/mitm/server.cjs  (port 443, CJS child process)
    │  Host header SNI ဖြင့် ပစ်မှတ်ကို ရှာဖွေသတ်မှတ်သည်
    │  AgentBridge CA ဖြင့် လက်မှတ်ထိုးထားသည့် SNI တစ်ခုချင်းစီအတွက် TLS cert ထုတ်ပေးသည်
    ├── Bypass list နှင့် ကိုက်ညီသလား? → TCP passthrough (စာဝှက်ဖြည်ခြင်းမရှိ)
    ├── Target နှင့် ကိုက်ညီသလား? → fetch → OmniRoute router (port 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── request body/headers များတွင် maskSecrets()
    │               ├── TrafficBuffer.push() — Traffic Inspector သို့ ထုတ်လွှင့်သည်
    │               └── fetchRouter() → /v1/chat/completions
    └── မကိုက်ညီဘူးလား? → TCP passthrough (စာဝှက်ဖြည်ခြင်းမရှိ)
```

### 2.2 MITM server (`src/mitm/server.cjs`)

အဓိက MITM server သည် Node.js CJS child process အဖြစ် အလုပ်လုပ်သည် (ရှိပြီးသား CJS codebase ကို ပြန်လည်ရေးသားရန် မလိုအပ်စေရန်)။ ၎င်းသည်-

- port 443 တွင် စောင့်ကြည့်သည် (အထူးလုပ်ပိုင်ခွင့် သို့မဟုတ် `authbind`/`setcap` လိုအပ်သည်)
- OS ထံမှ CONNECT tunnel များကို လက်ခံသည် (`/etc/hosts` DNS လမ်းကြောင်းပြောင်းခြင်းမှတစ်ဆင့်)
- AgentBridge CA (`DATA_DIR/mitm/ca.crt`) ဖြင့် လက်မှတ်ထိုးထားသည့် SNI တစ်ခုချင်းစီအတွက် TLS certificate များကို ထုတ်ပေးသည်
- `targets/index.ts` registry မှတစ်ဆင့် Host header ကို အသုံးပြု၍ ပစ်မှတ် agent ကို ရှာဖွေသတ်မှတ်သည်
- `http://127.0.0.1:20128` သို့ HTTP ဖြင့် TypeScript handler layer ထံ လွှဲပြောင်းပေးသည်

`TARGET_HOSTS` ကို `DATA_DIR/mitm/targets.json` (`targets/index.ts` က စတင်ချိန်တွင် ရေးသားသည်) မှ တင်သွင်းထားသောကြောင့် CJS server ကို ပြန်လည်စတင်ရန်မလိုဘဲ အပြောင်းအလဲများကို ပြုလုပ်နိုင်သည်။

> **Root-CA မော်ဒယ် (#6684)။** အထက်တွင် ဖော်ပြထားသည့် CA တစ်ခုဖြင့် လက်မှတ်ထိုးထားသော SNI တစ်ခုချင်းစီအလိုက် certificate မော်ဒယ်သည်
> #6684 တွင် ထည့်သွင်းခဲ့သည့် သိမ်းဆည်းတည်မြဲသော root-CA မော်ဒယ်ဖြစ်သည် (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`၊ `src/mitm/tproxy/dynamicCert.ts` တွင်
> TPROXY အတွက် အတည်ပြုပြီးသား CA/leaf crypto ကို ပြန်လည်အသုံးပြုထားသည်) — ၎င်းသည်
> disk ပေါ်တွင် `server.crt`/`server.key` အတွဲတစ်တွဲရှိနေခြင်းက ညွှန်ပြသည့်
> ယခင် static self-signed leaf တစ်ခုတည်း (`src/mitm/cert/generate.ts`၊ ယခုထိ
> antigravity host များအတွက်သာ သတ်မှတ်ထားသည်) ကို အစားထိုးသည်။ **ရွှေ့ပြောင်းမှု အပြုအမူ**- အသစ်ထည့်သွင်းမှုတစ်ခု (ယခင်
> `server.crt` မရှိသေးသော) သည် root-CA မော်ဒယ်ကို အလိုအလျောက်ရရှိသည်။ ယခင် static leaf ကို
> ယုံကြည်ထားပြီးသား ထည့်သွင်းမှုတစ်ခုသည် အော်ပရေတာက
> `MITM_ROOT_CA_ENABLED=true` သတ်မှတ်ပြီး bridge ကို ပြန်လည်စတင်သည့်အချိန်အထိ ၎င်းကို ဆက်လက်အသုံးပြုသည် (`src/mitm/cert/migration.ts`
> သည် သီးသန့်ဆုံးဖြတ်ချက် function ဖြစ်သည် — **မည်သည့်** host အတွက်မဆို leaf ကို လက်မှတ်ထိုးနိုင်သည့်
> ယုံကြည်ထားသော MITM CA သည် အဟောင်း fixed-SAN leaf ထက် အမှန်တကယ် ပိုမိုအစွမ်းထက်သောကြောင့်
> ယုံကြည်ထားပြီးသား ထည့်သွင်းမှုတစ်ခုအတွက် ပြောင်းလဲမှုကို အသိမပေးဘဲ မည်သည့်အခါမျှ မလုပ်ဆောင်ပါ)။ CA cert ကို
> အဟောင်း leaf အသုံးပြုခဲ့သည့် `omniroute-mitm.crt` trust-store နေရာတစ်ခုတည်းတွင်
> ထည့်သွင်းသည် (`cert/install.ts::installCaCert`) — dual-trust ရှင်းလင်းမှု မလိုအပ်ပါ။

### 2.3 Handler အခြေခံ (`src/mitm/handlers/base.ts`)

Agent handler အားလုံးသည် `MitmHandlerBase` ကို တိုးချဲ့အသုံးပြုသည်-

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // ကာကွယ်ထားသော helper များ- fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

Handler တစ်ခုစီသည် proxy မလုပ်မီ `hookBufferStart()` ကို ခေါ်ပြီး ပြီးဆုံးချိန်တွင် `hookBufferUpdate()` ကို ခေါ်သည်။ ၎င်းတို့က `InterceptedRequest` entry များကို `globalTrafficBuffer` အတွင်းသို့ ထည့်သွင်းသည် ([Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4 ကိုကြည့်ပါ)။

### 2.4 Targets registry (`src/mitm/targets/`)

Agent တစ်ခုစီတွင် ဖော်ပြချက်ပုံစံ target file တစ်ခုရှိသည်-

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

Registry (`targets/index.ts`) သည် `ALL_TARGETS` ကို export လုပ်ပြီး စတင်ချိန်တွင် `DATA_DIR/mitm/targets.json` ကို ထုတ်ပေးသည်။

### 2.5 Passthrough နှင့် bypass list (`src/mitm/passthrough.ts`)

**Bypass list** (target နှင့် ကိုက်ညီမှုထက် ဦးစားပေး၍ ပထမဦးစွာ စစ်ဆေးသည်)-

- မူလ pattern များ- ဘဏ်လုပ်ငန်း host များ၊ `.gov.`၊ OAuth/SSO provider များ (Okta၊ Auth0) စသည်
- အသုံးပြုသူ pattern များ- DB table `agent_bridge_bypass` တွင် သိမ်းဆည်းထားသည်
- Bypass လုပ်ထားသော host များသည် ပွင့်လင်းမြင်သာသည့် TCP tunnel တစ်ခုကို ရရှိသည် — TLS ကို **မည်သည့်အခါမျှ စာဝှက်မဖြည်ပါ**

**Passthrough မူလအပြုအမူ** (target နှင့် မကိုက်ညီသည့်အပြင် bypass ထဲတွင်လည်း မပါဝင်ပါက)-

- TCP tunnel တစ်ခုကိုလည်း ရရှိသည် — ချိတ်ဆက်မှုများကို မည်သည့်အခါမျှ မဖြတ်တောက်ပါ
- AgentBridge က စနစ်၏ ယေဘုယျ HTTPS traffic ကို အနှောင့်အယှက်ဖြစ်စေခြင်းမှ တားဆီးသည်

Routing ဦးစားပေးအစဉ်-

```
bypass list → target နှင့် ကိုက်ညီမှု → passthrough
```

### 2.6 Upstream CA cert (`src/mitm/upstreamTrust.ts`)

စိတ်ကြိုက် CA ပါရှိသော လုပ်ငန်းသုံးကွန်ရက် ပတ်ဝန်းကျင်များအတွက်-

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

သတ်မှတ်ထားပါက အပို CA cert ဖြင့် `undici` ၏ global dispatcher ကို စီစဉ်သတ်မှတ်ပေးပြီး AgentBridge အနေဖြင့် လုပ်ငန်းသုံး TLS termination proxy များမှတစ်ဆင့် upstream provider များထံ ရောက်ရှိနိုင်စေသည်။

### 2.7 လျှို့ဝှက်ချက် ဖုံးကွယ်ခြင်း (`src/mitm/maskSecrets.ts`)

သီးခြားလွတ်လပ်စွာ တည်ဆောက်ထားသည့် clean-room scanner ကို Traffic Inspector buffer သို့မဟုတ် မည်သည့် log အတွင်းမဆို
မဝင်ရောက်မီ request body များနှင့် credential header များတွင် အသုံးပြုသည်။ ၎င်းသည် တစ်ကြိမ်တည်း linear pass ပြုလုပ်သည်-

- `sk-` / `ak-` / `pk-` prefix ပါ token များ (OpenAI/Anthropic ပုံစံ)
- RFC 6750 `Authorization: Bearer <token>` credential များ၊ token တစ်ခုလုံးကို ဦးစားပေးသည်
- အစက်ပါဝင်သည့်ပုံစံနှင့် padding ပါဝင်သည့်ပုံစံများအပါအဝင် ယေဘုယျ ရှည်လျားပြီး အဓိပ္ပာယ်မမြင်သာသော token များ (≥40 chars)

`sanitizeHeaders()` သည် ထိန်းသိမ်းထားသော အမည်များကို စာလုံးအသေးပြောင်းပေးသည်၊ array value များကို သတ်မှတ်ထားသောတစ်သမတ်တည်းနည်းဖြင့် ချိတ်ဆက်သည်၊
proxy authentication အပါအဝင် မျှဝေထားသည့် hop-by-hop/framing denylist ကို ဖယ်ရှားသည်၊ `cookie` နှင့်
`set-cookie` တို့ကို အပြည့်အဝ ဖုံးကွယ်ပြီး credential value များကို scanner ထံ လွှဲပေးသည်။

## §3 စနစ်ထည့်သွင်းခြင်း

### 3.1 MITM ဆာဗာကို စတင်ခြင်း/ရပ်တန့်ခြင်း

`/dashboard/tools/agent-bridge` ရှိ AgentBridge Server Card ကို အသုံးပြုပါ-

| လုပ်ဆောင်ချက်                      | ဖော်ပြချက်                                                                                           |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------- |
| ဆာဗာစတင်ရန်                        | Port 443 တွင် `src/mitm/server.cjs` ကို စတင်လုပ်ဆောင်စေသည်                                           |
| ဆာဗာရပ်တန့်ရန်                     | Child process ကို စနစ်တကျ ပိတ်သည်                                                                    |
| ဆာဗာပြန်လည်စတင်ရန်                 | ရပ်တန့်ခြင်း + စတင်ခြင်း (target ပြောင်းလဲမှုများကို ထည့်သွင်းအသုံးပြုသည်)                           |
| Certificate ကို ယုံကြည်ရန်         | `DATA_DIR/mitm/ca.crt` ကို OS trust store ထဲသို့ ထည့်သွင်းသည်                                        |
| Certificate ကို ဒေါင်းလုဒ်ရန်      | ကိုယ်တိုင်ထည့်သွင်းရန် `ca.crt` ကို ဒေါင်းလုဒ်လုပ်သည်                                                |
| Certificate ကို ပြန်လည်ထုတ်လုပ်ရန် | CA keypair အသစ်တစ်ခု ဖန်တီးသည် (ရှိပြီးသား agent တစ်ခုချင်းစီ၏ certificate အားလုံး အကျုံးမဝင်တော့ပါ) |

### 3.2 Certificate ကို ယုံကြည်စိတ်ချရအဖြစ် သတ်မှတ်ခြင်း

IDE များက MITM ချိတ်ဆက်မှုကို လက်ခံနိုင်ရန် AgentBridge CA certificate ကို OS က ယုံကြည်စိတ်ချရအဖြစ် သတ်မှတ်ထားရမည်။

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

သို့မဟုတ် dashboard ရှိ "Certificate ကို ယုံကြည်ရန်" ခလုတ်ကို အသုံးပြုပါ (သင့် OS အတွက် သင့်လျော်သည့် command ကို လုပ်ဆောင်ပြီး လိုအပ်ပါက sudo prompt ပြသမည်)။

#### Electron အခြေခံ IDE များသည် OS trust store ကို လျစ်လျူရှုသည် (`NODE_EXTRA_CA_CERTS`)

အချို့ IDE များ — အထူးသဖြင့် **Antigravity IDE** နှင့် အခြား Electron / VS Code မှ ဆင်းသက်လာသော app များ — သည် outbound
`fetch`/HTTPS အတွက် **OS trust store ကို စစ်ဆေးအသုံးမပြုသည့်** ကိုယ်ပိုင် Node.js runtime ကို ပူးတွဲထည့်သွင်းထားသည်။
OS/NSS အဆင့်တွင် CA ကို ယုံကြည်စိတ်ချရအဖြစ် သတ်မှတ်ခြင်းသည် IDE ၏ မူရင်း **backend**
(ဥပမာ OS CA bundle ကို အသုံးပြုသည့် Go language server) အတွက် လုံလောက်သော်လည်း **Electron frontend** တွင်
TLS ဆက်လက်ပျက်ကွက်နေမည် — MITM log တွင် backend ၏ bootstrap call များက `200` ပြန်ပေးနေသော်လည်း
app တွင် _အကောင့်မှ ထွက်ထားသည်_ ဟု ပြသခြင်း သို့မဟုတ် _"ချိတ်ဆက်မှု အမှား"_ ကို ပြသခြင်းအဖြစ်
ပေါ်လာသည်။ အဆင့်နှစ်ဆင့် လိုအပ်ပြီး နှစ်ခုစလုံး အရေးကြီးသည်-

1. Runtime ကို CA ထံ တိတိကျကျ ညွှန်ပေးပါ-
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **ထို shell မှ IDE ကို စတင်ပါ။** Desktop icon / Dock / Start menu မှ စတင်ခြင်းသည်
   shell export များကို **ဆက်ခံမည်မဟုတ်ပါ**။ ထို့ပြင် `~/.config/environment.d/*.conf` သည်
   graphical login အသစ်ပြုလုပ်ပြီးမှသာ သက်ရောက်သည်။ IDE ကို ဦးစွာ အပြည့်အဝ ပိတ်ပါ — Electron ၏ singleton lock ကြောင့်
   ဒုတိယအကြိမ် စတင်ခြင်းသည် ရှိပြီးသား process ကိုသာ focus လုပ်ပြီး environment အသစ်ကို လျစ်လျူရှုမည်ဖြစ်သည်။

အထက်ပါ OS-trust + NSS အဆင့်သည် ဆက်လက်လိုအပ်သည် (အချို့ auth
flow များက အသုံးပြုသည့် Chromium network stack သည် အသုံးပြုသူတစ်ဦးချင်းစီ၏ NSS store ကို ဖတ်ရှုပြီး
စက်တွင်းမှ ယုံကြည်ထားသော CA က override လုပ်ပေးနိုင်သည့် `*.googleapis.com` အတွက် ကိုယ်ပိုင် static pin များလည်း ရှိသည်)။
`NODE_EXTRA_CA_CERTS` သည် ထိုအဆင့်အပြင် Node `fetch` လမ်းကြောင်းကိုပါ လွှမ်းခြုံပေးသည်။

### 3.3 DNS လမ်းကြောင်းသတ်မှတ်ခြင်း

ကြားဖြတ်ရယူလိုသော agent တစ်ခုချင်းစီအတွက် ၎င်း၏ API host(များ) သည် `127.0.0.1` သို့ resolve ဖြစ်ရမည်။ Setup Wizard တွင် agent တစ်ခုအတွက် DNS ကို အဖွင့်/အပိတ် ပြောင်းသည့်အခါ AgentBridge က `/etc/hosts` entry များကို အလိုအလျောက် စီမံပေးသည်။

GitHub Copilot အတွက် `/etc/hosts` entry နမူနာများ-

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 Model mapping

အရင်းအမြစ် → ပစ်မှတ် mapping များကို သတ်မှတ်ရန် agent card တစ်ခုချင်းစီရှိ Model Mapping Table ကို အသုံးပြုပါ-

| အရင်းအမြစ် model (agent မူရင်း) | ပစ်မှတ် model (OmniRoute) |
| ------------------------------- | ------------------------- |
| `gpt-4o`                        | `claude-sonnet-4.7`       |
| `*` (wildcard)                  | `claude-haiku-4.7`        |

Wildcard `*` သည် အသိအမှတ်မပြုသော model မည်သည့်အမျိုးအစားကိုမဆို သတ်မှတ်ထားသည့် target ထံ map လုပ်သည်။ `agent_bridge_mappings` table တွင် အမြဲတမ်းသိမ်းဆည်းထားသည်။

> **အကြံပြုချက် — agent ၏ အမှန်တကယ် model ID များကို ရှာဖွေပါ။** IDE တစ်ခုသည် ၎င်း၏
> UI label များနှင့် ကွဲပြားပြီး major version များအကြား ပြောင်းလဲနိုင်သော model အမည်များကို ပေးပို့နိုင်သည်။ ဥပမာ **Antigravity 2** သည်
> ယခင် docs များတွင် ပြထားသော `gemini-2.5-pro` မဟုတ်ဘဲ `gemini-3.1-pro-low`, `gemini-pro-agent` နှင့်
> `gemini-3.1-flash-lite` ကို network မှတစ်ဆင့် ပေးပို့သည်။ ကိုက်ညီသော mapping မရှိဘဲ chat တစ်ခု ပေးပို့ပါ-
> MITM သည် ဝင်လာသည့် `model:` အတိအကျကို log မှတ်တမ်းတင်ပြီး request ကို ဖြတ်သန်းခွင့်ပေးမည်။ ထို literal value ကို map လုပ်ပါ၊ ထို့နောက်
> နောက်ထပ် request ကို ကြားဖြတ်ရယူပြီး သင့် target ထံ လမ်းကြောင်းပြောင်းပေးမည်။

### 3.5 အန္တရာယ် အသိပေးချက်

AgentBridge သည် upstream provider များနှင့် စစ်မှန်ကြောင်းအတည်ပြုရန် IDE က အသုံးပြုသည့် credential များ (OAuth token များ၊ API key များ) ကို ကြားဖြတ်ရယူသည်။ ၎င်းတို့ကို **log မှတ်တမ်းမတင်မီ ဖုံးကွယ်ထားသည်** (§2.7 ကို ကြည့်ပါ)၊ သို့သော် OmniRoute ၏ MITM layer တွင် မြင်နိုင်သည်။ Agent တစ်ခုချင်းစီကို ပထမဆုံး activate လုပ်သောအခါ ပိတ်နိုင်သည့် အန္တရာယ်အသိပေး modal တစ်ခုကို ပြသသည်။

### 3.6 ထိန်းသိမ်းခြင်းနှင့် ပြဿနာရှာဖွေစစ်ဆေးခြင်း

Dashboard တွင် ယခင်က UI မရှိခဲ့သည့် လုပ်ငန်းလည်ပတ်မှုဆိုင်ရာ MITM route များကို ဖော်ပြပေးသော **Maintenance & Diagnostics** card (`AgentBridgeMaintenanceCard`၊ `src/app/(dashboard)/dashboard/tools/agent-bridge/components/` တွင်) ပါရှိသည်။ ၎င်း၏ စာတန်းငယ်မှာ _"ဖမ်းယူမှု pipeline ကို ကိုယ်တိုင်စမ်းသပ်ပါ၊ ကျန်ရှိနေသော system state ကို ပြန်ဖျက်ပါ၊ သင့် setup ကို စက်များအကြား ရွှေ့ပြောင်းပါ။"_ ဖြစ်သည်။ Card client helper များသည် `src/lib/inspector/agentBridgeMaintenanceApi.ts` တွင် ရှိသည်။

| ခလုတ်                  | Route                                  | လုပ်ဆောင်ပုံ                                                                                                                                                                                                                |
| ---------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **စစ်ဆေးရန်**          | `GET /api/tools/agent-bridge/diagnose` | capture-pipeline ကိုယ်တိုင်စမ်းသပ်မှုကို လုပ်ဆောင်ပြီး စစ်ဆေးမှုတစ်ခုချင်းစီအလိုက် အစီရင်ခံစာ (✓/✗ + ဖြေရှင်းနည်းအကြံပြုချက်) ကို ပြသသည်။                                                                                   |
| **ပြုပြင်ရန်**         | `POST /api/tools/agent-bridge/repair`  | crash သို့မဟုတ် SIGKILL ကြောင့် ကျန်ရစ်ခဲ့သော ပိုင်ရှင်မဲ့ MITM စနစ်အခြေအနေ (DNS spoof entry များ၊ root CA၊ system proxy) ကို ပြန်ဖျက်ပေးသည်။ Idempotent ဖြစ်ပြီး အခြေအနေရှင်းလင်းနေပါက "ပြုပြင်ရန် မရှိပါ" ဟု အစီရင်ခံသည်။ |
| **CA ဖယ်ရှားရန်**      | `DELETE /api/tools/agent-bridge/cert`  | OS trust store ထဲမှ MITM root CA ကို မယုံကြည်တော့အောင် ပြုလုပ်ပြီး ဖယ်ရှားသည် (တိကျစွာတောင်းဆိုရပြီး idempotent ဖြစ်သည်)။ CA ကို လက်ရှိယုံကြည်ထားသည့်အခါမှသာ ပြသပြီး inline "CA ကို ဖယ်ရှားမည်လား?" အတည်ပြုချက် လိုအပ်သည်။  |
| **Config ထုတ်ယူရန်**   | `GET /api/tools/agent-bridge/config`   | သယ်ဆောင်အသုံးပြုနိုင်သော config JSON ကို ဒေါင်းလုဒ်လုပ်သည် (§3.7 ကို ကြည့်ပါ)။                                                                                                                                              |
| **Config တင်သွင်းရန်** | `POST /api/tools/agent-bridge/config`  | ယခင်က ထုတ်ယူထားသော config JSON ကို အပ်လုဒ်လုပ်သည် (§3.7 ကို ကြည့်ပါ)။                                                                                                                                                       |

**Diagnostics စစ်ဆေးမှုများ** (`src/mitm/inspector/diagnostics.ts` ရှိ `summarizeDiagnostics()`)။ Route သည် တစ်ခုချင်းစီအတွက် အကျိုးသက်ရောက်မှုရှိသော probe ကို လုပ်ဆောင်ပြီး boolean များကို pure summarizer ထဲသို့ ထည့်ပေးသည်။ `healthy` ဆုံးဖြတ်ချက်တစ်ခုတည်းနှင့် မအောင်မြင်မှုတစ်ခုချင်းစီအတွက် အကြံပြုချက်ကို ပြန်ပေးသည်-

| စစ်ဆေးမှုအမည်      | အတည်ပြုစစ်ဆေးသည့်အရာ                                                    | မအောင်မြင်ပါက အကြံပြုချက်                                                                                                                                   |
| ------------------ | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | MITM server process လည်ပတ်နေခြင်း                                       | "MITM server လည်ပတ်မနေပါ။ AgentBridge tab မှ စတင်ပါ။"                                                                                                       |
| `server-reachable` | MITM server က ၎င်း၏ port တွင် connection များကို လက်ခံခြင်း (TCP probe) | "MITM server က ၎င်း၏ port တွင် connection များကို လက်မခံပါ။ port အားလပ်နေကြောင်းနှင့် ၎င်းကို bind လုပ်ရန် သင့်တွင် အခွင့်အရေးများရှိကြောင်း စစ်ဆေးပါ။"     |
| `cert-exists`      | MITM certificate ကို disk ပေါ်တွင် ထုတ်လုပ်ပြီးဖြစ်ခြင်း                | "MITM certificate ကို မထုတ်လုပ်ရသေးပါ။ AgentBridge tab မှ တစ်ခုထုတ်လုပ်ပါ။"                                                                                 |
| `cert-trusted`     | MITM root CA သည် OS trust store ထဲတွင် ရှိခြင်း                         | "MITM root CA ကို OS store က မယုံကြည်သောကြောင့် TLS ကြားဖြတ်ဖမ်းယူမှု မအောင်မြင်ပါမည်။ AgentBridge tab မှ certificate ကို ယုံကြည်အောင် ပြုလုပ်ပါ။"          |
| `dns-configured`   | ပစ်မှတ် hostname များကို `/etc/hosts` တွင် spoof လုပ်ထားခြင်း           | "ပစ်မှတ် hostname များကို /etc/hosts တွင် spoof မလုပ်ထားသောကြောင့် traffic သည် proxy သို့ လုံးဝမရောက်ရှိပါ။ ဖမ်းယူလိုသည့် agent များအတွက် DNS ကို ဖွင့်ပါ။" |

**ပိုင်ရှင်မဲ့အခြေအနေ banner:** စာမျက်နှာက crash ကြောင့် ကျန်ရစ်ခဲ့သော အခြေအနေ (DNS spoof / CA / system proxy) ကို တွေ့ရှိသောအခါ card တွင် ပယင်းရောင် banner — _"ယခင် session တစ်ခုက စနစ်အခြေအနေ (DNS spoof၊ CA သို့မဟုတ် system proxy) ကို ချန်ထားခဲ့သည်။ ၎င်းကို ရှင်းလင်းရန် ပြုပြင်ရန်ကို လုပ်ဆောင်ပါ။"_ — ကို ပြသပြီး **ပြုပြင်ရန်** ခလုတ်ကို ထင်ရှားစေသည်။ `Repair` သည် ProxyBridge ၏ `--cleanup` flag နှင့် application layer အဆင့်တွင် တူညီသည့်အရာဖြစ်သည် (`src/mitm/manager.ts` ရှိ `repairMitm()` သို့ လွှဲပေးသည်)။

> ထပ်ခါတလဲလဲ sudo prompt များကို ရှောင်ရှားရန် MITM root CA ကို stop/start များအကြား
> ဆက်လက်ထည့်သွင်းထားသည် (mitmproxy/Charles နှင့် တူညီသော လုပ်ဆောင်ပုံဖြစ်သည်)။ ထို့ကြောင့် ၎င်းကို ဖယ်ရှားခြင်းသည်
> stop လုပ်သည့်အခါ အလိုအလျောက်ဖြစ်ပေါ်သည့်အရာမဟုတ်ဘဲ တိကျစွာတောင်းဆိုရသော **CA ဖယ်ရှားရန်**
> လုပ်ဆောင်ချက်ဖြစ်သည်။

### 3.7 သယ်ဆောင်အသုံးပြုနိုင်သော config တင်သွင်းခြင်း/ထုတ်ယူခြင်း

စက်တစ်လုံးတွင် ပြုလုပ်ထားသော setup ကို အခြားစက်များတွင် ပုံတူပြုလုပ်နိုင်ရန် AgentBridge သည် **အော်ပရေတာက ချိန်ညှိနိုင်သော** အခြေအနေကို version ပါသည့် JSON blob အဖြစ် serialize လုပ်နိုင်သည်။ Serializer သည် `src/lib/inspector/configPortability.ts` ရှိ (`exportConfig()` / `importConfig()`) ဖြစ်ပြီး `AgentBridgeConfigSchema` ဖြင့် validate လုပ်ထားသည်။

Export တွင် အပိုင်းသုံးခုတိတိ ပါဝင်သည် (ထည့်သွင်းပါရှိပြီးသား default များကို ရည်ရွယ်ချက်ရှိရှိ **မထုတ်ယူပါ**။ ထို့ကြောင့် import လုပ်ခြင်းက ၎င်းတို့ကို မိတ္တူပွားခြင်း သို့မဟုတ် ၎င်းတို့နှင့် ပဋိပက္ခဖြစ်ခြင်း လုံးဝမရှိပါ)-

| Field            | အရင်းအမြစ်                                                            | မှတ်ချက်များ                                                           |
| ---------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `bypassPatterns` | အသုံးပြုသူသတ်မှတ်ထားသော bypass pattern များ (`agent_bridge_bypass`)   | မူလ bank/gov/okta pattern များကို မထည့်သွင်းပါ                         |
| `customHosts`    | Traffic Inspector custom host များ (`inspector_custom_hosts`)         | တစ်ခုချင်းစီမှာ- `{ host, kind: "llm"\|"app"\|"custom", label? }`      |
| `agentMappings`  | agent တစ်ခုချင်းစီအလိုက် model mapping များ (`agent_bridge_mappings`) | mapping ရှိသော agent တိုင်းအတွက် `{ [agentId]: [{ source, target }] }` |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**Import လုပ်ဆောင်ပုံ** (`POST /api/tools/agent-bridge/config`)- bypass pattern များနှင့် agent တစ်ခုချင်းစီအလိုက် mapping များကို **တစ်ခုလုံး အစားထိုးသည်**။ custom host များကို **idempotent ပုံစံဖြင့်** ထည့်သွင်းသည် (`INSERT OR IGNORE`)။ Response သည် အမျိုးအစားတစ်ခုချင်းစီအလိုက် မည်မျှအသုံးချခဲ့သည်ကို အစီရင်ခံသည်-

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

config ထဲတွင် **မပါဝင်သော** အရာများမှာ server လည်ပတ်နေမှုအခြေအနေ၊ cert path များ၊ agent တစ်ခုချင်းစီ၏ DNS အခြေအနေ၊ upstream CA path နှင့် TPROXY setting များဖြစ်သည် — ၎င်းတို့သည် အခြားနေရာသို့ သယ်ဆောင်အသုံးပြုနိုင်သော preference များမဟုတ်ဘဲ host/runtime အခြေအနေများဖြစ်သည်။

### စနစ်ထည့်သွင်းမှု Wizard အဆင့်များ (Agent တစ်ခုချင်းစီအလိုက်)

Agent ကတ်တစ်ခုစီတွင် အဆင့် 3 ဆင့်ပါ စနစ်ထည့်သွင်းမှု Wizard ရှိသည်-

1. **လိုအပ်ချက်များကို စစ်ဆေးပါ** — Server လည်ပတ်နေပါသလား။ Cert ကို ယုံကြည်ထားပါသလား။ IDE ထည့်သွင်းထားပါသလား (အလိုအလျောက် ရှာဖွေစစ်ဆေးသည်)။
2. **DNS ကို ဖွင့်ပါ** — `/etc/hosts` entry များကို ထည့်သွင်းသည် (sudo လိုအပ်သည်)။ ထည့်သွင်းမည့် စာကြောင်းများကို အတိအကျ ပြသသည်။
3. **Model များကို ချိတ်ဆက်ပါ** — ရွေးချယ်နိုင်သော model ချိတ်ဆက်မှုဇယား။ Wildcard များကို လက်ခံသည်။

### Agent ရှာဖွေစစ်ဆေးခြင်း

Agent 1–8 အတွက် AgentBridge သည် IDE ထည့်သွင်းထားခြင်းရှိမရှိ အလိုအလျောက် ရှာဖွေစစ်ဆေးရန် ကြိုးစားသည်-

```ts
export async function detectAgent(agentId: AgentId): Promise<DetectionResult>;
// ပြန်ပေးသည်- { installed: boolean, version?: string, path?: string }
```

ရှာဖွေစစ်ဆေးမှုတွင် OS အလိုက် သတ်မှတ်ထားသော လမ်းကြောင်းများနှင့် binary စစ်ဆေးမှုများကို အသုံးပြုသည် (ဥပမာ Copilot အတွက် `code --list-extensions | grep github.copilot`၊ Antigravity အတွက် `~/.config/antigravity/`)။

| **#13** Shell env မှတစ်ဆင့် ပေးပို့ခြင်း | `/etc/hosts` ပြင်ဆင်မှုများသည် `env` option ကို အသုံးပြုသည် — လမ်းကြောင်းများကို string interpolation မပြုလုပ်ပါ      |

### အရေးကြီးသော Host များအတွက် Bypass စာရင်း

Bypass စာရင်းသည် ငွေကြေးအဖွဲ့အစည်းများ၊ OAuth/SSO provider များနှင့် အခြားအရေးကြီးသော host များကို **မည်သည့်အခါမျှ ကုဒ်ဖြေမည်မဟုတ်ကြောင်း** သေချာစေသည်။ ၎င်းတို့၏ TLS traffic သည် ပွင့်လင်းမြင်သာသော TCP tunnel အဖြစ် ဖြတ်သန်းသွားသည် — OmniRoute သည် plaintext ကို မည်သည့်အခါမျှ မမြင်ရပါ။

မူလ bypass pattern များတွင် အောက်ပါတို့ ပါဝင်သည်-

- `*.bank.*`, `*.gov.*` (ဘဏ္ဍာရေး/အစိုးရ)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/အထောက်အထား)
- `*.apple.com`, `*.icloud.com` (Apple စနစ်ဝန်ဆောင်မှုများ)

အသုံးပြုသူထည့်သွင်းထားသော bypass pattern များကို `agent_bridge_bypass` table တွင် သိမ်းဆည်းပြီး အခြားအရာအားလုံးထက် ဦးစားပေးသည်။

### Secret ဖုံးကွယ်ခြင်း

`src/mitm/maskSecrets.ts` မှ `maskSecrets()` ကို အောက်ပါအတိုင်း အသုံးပြုသည်-

- `TrafficBuffer.push()` မပြုလုပ်မီ request body တိုင်းတွင်
- Logging သို့မဟုတ် broadcasting မပြုလုပ်မီ header တိုင်းတွင်

Pattern များ- `sk-`/`ak-`/`pk-` prefix ပါသော token များ၊ `Bearer` token များနှင့် စာလုံးရေ 40 နှင့်အထက်ရှိသော ယေဘုယျ token များ။

### Upstream CA cert

`AGENTBRIDGE_UPSTREAM_CA_CERT` ကို သတ်မှတ်ထားသောအခါ ဖိုင်ကို စတင်ချိန်တွင် ဖတ်သည်။ လမ်းကြောင်းရှိသော်လည်း ဖိုင်ကို ဖတ်၍မရပါက AgentBridge သည် ရှင်းလင်းသော error တစ်ခုကို log လုပ်ပြီး စတင်ရန် ငြင်းဆိုသည် (လုပ်ငန်းသုံး ပတ်ဝန်းကျင်များတွင် အသံတိတ် TLS ချို့ယွင်းမှုများကို ကာကွယ်ပေးသည်)။

### သိရှိထားသော ကန့်သတ်ချက်များ

- **Port 443 သည် privilege လိုအပ်သည်**- Linux တွင် AgentBridge သည် Node binary ပေါ်၌ `setcap 'cap_net_bind_service=+ep'` သတ်မှတ်ထားရန် သို့မဟုတ် `authbind` မှတစ်ဆင့် လည်ပတ်ရန် လိုအပ်သည်။ Setup Wizard သည် OS အလိုက် ညွှန်ကြားချက်များကို ပြသသည်။
- **IDE ကို ပြန်လည်စတင်ရန် လိုအပ်သည်**- DNS redirect ပြုလုပ်ပြီးနောက် host resolution အသစ် အသက်ဝင်ရန် IDE ကို ပြန်လည်စတင်ရမည်။
- **Hardcoded OAuth token များ**- Agent အချို့ (Kiro၊ Antigravity) သည် OAuth refresh token များကို စက်အတွင်း သိမ်းဆည်းသည်။ ဤအရာများသည် AgentBridge အတွက် ပွင့်လင်းမြင်သာသည် — ၎င်းသည် request တစ်ခုစီရှိ Bearer token ကို မြင်ရသော်လည်း logging မပြုလုပ်မီ ဖုံးကွယ်ထားသည်။
- **Electron frontend များတွင် `NODE_EXTRA_CA_CERTS` လိုအပ်သည်**- Bundle လုပ်ထားသော Node/Electron runtime ပေါ်တွင် frontend လည်ပတ်သည့် IDE များသည် OS/NSS trust store ကို လျစ်လျူရှုပြီး `NODE_EXTRA_CA_CERTS` သတ်မှတ်ထားသော shell မှ စတင်ရမည် (§3.2 ကို ကြည့်ပါ)။ မရှိသည့်အခါ ဖြစ်ပေါ်သော လက္ခဏာမှာ IDE backend သည် အထောက်အထားစစ်ဆေးမှု အောင်မြင်သော်လည်း (MITM တွင် `200` များကို ပြသသည်) UI မှာ logged out အခြေအနေတွင် ဆက်ရှိနေခြင်းဖြစ်သည်။
- **IDE တစ်ခုတည်းကို အကြိမ်များစွာ ထည့်သွင်းထားခြင်းများသည် တစ်ခုနှင့်တစ်ခု သီးခြားဖြစ်သည်**- စနစ်အဆင့် ထည့်သွင်းမှု (ဥပမာ `/usr/share/antigravity/antigravity`) နှင့် အသုံးပြုသူ၏ local "Full" ထည့်သွင်းမှု (ဥပမာ `~/AntigravityIDE_Full/antigravity-ide`) တို့သည် ကိုယ်ပိုင် runtime များပါရှိသော သီးခြား process များဖြစ်သည် — တစ်ခုစီကို CA ထည့်သွင်းပြီး ပြန်လည်စတင်ရမည်။ ပြန်လည်စတင်မလုပ်မီ လက်ရှိလည်ပတ်နေသည့်အရာကို ၎င်း၏ binary path ဖြင့် ခွဲခြားသတ်မှတ်ပါ။
- **Identity ကို routing လုပ်ထားသော model က မဟုတ်ဘဲ Agent ၏ system prompt က သတ်မှတ်သည်**- Agent တစ်ခု၏ model ကို အခြား provider တစ်ခုသို့ ပြန်လည်ချိတ်ဆက်သည့်အခါ အဖြေသည် Agent ၏ မူရင်း identity ကို ဆက်လက်ဖော်ပြနေမည် (ဥပမာ Antigravity က "I am powered by Gemini" ဟု ဖြေဆိုသည်)၊ အကြောင်းမှာ IDE က ၎င်းကို system prompt ထဲသို့ ထည့်သွင်းထားသောကြောင့်ဖြစ်သည်။ Model ကို မည်သူဖြစ်ကြောင်း မေးခြင်းအစား အမှန်တကယ် backend ကို `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`) တွင် အတည်ပြုပါ။

## §6 ပြဿနာဖြေရှင်းခြင်း

### Port 443 ပဋိပက္ခ

အခြား process တစ်ခုက port 443 တွင် ချိတ်ဆက်မှုများကို စောင့်ဆိုင်းနေပြီးသားဖြစ်ပါက (web server၊ VPN စသည်):

```bash
lsof -i :443          # process ကို ရှာရန်
sudo fuser -k 443/tcp  # အတင်းအကျပ် ရပ်တန့်ရန် (သတိထား၍ အသုံးပြုပါ)
```

တနည်းအားဖြင့် AgentBridge settings တွင် အထူးအခွင့်အရေးမလိုသော port တစ်ခုကို configure လုပ်ပြီး `iptables` / `pf` redirect rules များကို သတ်မှတ်ပါ။

### Certificate ကို မယုံကြည်ပါ

AgentBridge ကို စတင်ပြီးနောက် IDE တွင် TLS errors များ ပြသပါက:

1. cert ကို install လုပ်ထားခြင်းရှိမရှိ စစ်ဆေးပါ: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) သို့မဟုတ် `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. အချို့ app များသည် ၎င်းတို့၏ကိုယ်ပိုင် trust store ကို ထိန်းသိမ်းထားသည် (Firefox၊ Linux ပေါ်ရှိ Chrome)။ "Trust Cert" ကို ထပ်မံလုပ်ဆောင်ပြီး NSS/Firefox သီးသန့် cert store ကို စစ်ဆေးပါ။
3. ယုံကြည်မှုပေးပြီးနောက် IDE ကို restart လုပ်ပါ — လက်ရှိလုပ်ဆောင်နေသော TLS sessions များသည် trust state အဟောင်းကို အသုံးပြုသည်။

### ယုံကြည်ရသော CA ရှိသော်လည်း IDE မှ logged out ဖြစ်ခြင်း / "connection error" ဖြစ်ခြင်း

လက္ခဏာ: DNS ကို redirect လုပ်ပြီး CA ကို ယုံကြည်မှုပေးပြီးနောက် Electron အခြေခံ IDE (ဥပမာ Antigravity)
သည် **logged out** အခြေအနေဖြင့် ဖွင့်လာသည် သို့မဟုတ် authentication/connection error ကို ပြသသည်၊ သို့သော် MITM log တွင်
bootstrap calls (`loadCodeAssist`, `fetchAvailableModels`, …) က `200` ပြန်ပေးနေသည်ကို တွေ့ရသည်။

အကြောင်းရင်း: IDE ၏ **တွဲဖက်ပါရှိသော Node/Electron runtime က OS trust store ကို လျစ်လျူရှုသည်**။ မူရင်း
backend (Go language server တစ်ခု) သည် OS CA ကို ယုံကြည်ပြီး authenticate လုပ်နိုင်သော်လည်း Electron frontend
က မယုံကြည်ပါ — ထို့ကြောင့် UI က offline ဖြစ်နေသည်ဟု ယူဆသည်။

ဖြေရှင်းနည်း (အဆင့်နှစ်ခုလုံး): `NODE_EXTRA_CA_CERTS=<ca.crt>` ကို export လုပ်ပြီး **ထို shell မှ IDE ကို ပြန်လည်ဖွင့်ပါ**၊
desktop icon မှ မဖွင့်ပါနှင့်။ ဦးစွာ IDE ကို အပြည့်အဝပိတ်ပါ — Electron ၏ singleton lock ကြောင့်
ဒုတိယအကြိမ် ဖွင့်ခြင်းသည် ရှိပြီးသား process ကိုသာ focus လုပ်မည်ဖြစ်ပြီး environment အသစ်ကို လျစ်လျူရှုမည်ဖြစ်သည်။ §3.2 ကို ကြည့်ပါ။
၎င်းသည် standalone agent တစ်ခုက MITM မှတစ်ဆင့် အလုပ်လုပ်သော်လည်း တူညီသော setup အောက်တွင် IDE
variant က မအောင်မြင်ကြောင်း ဖော်ပြထားသည့် လက်ရှိဖွင့်ထားသော upstream report တစ်ခုနှင့် ကိုက်ညီသည်။

### DNS ပြောင်းလဲမှု မပျံ့နှံ့ခြင်း

`/etc/hosts` ကို update လုပ်ထားခြင်းရှိမရှိ စစ်ဆေးပါ:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

DNS cache ကို ရှင်းလင်းပါ:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE ကို မတွေ့ရှိခြင်း

အလိုအလျောက်ရှာဖွေခြင်းသည် ပုံမှန် installation paths များကို အသုံးပြုသည်။ IDE ကို install လုပ်ထားသော်လည်း ရှာဖွေမှု မအောင်မြင်ပါက:

- IDE binary သည် ပုံမှန်မဟုတ်သော တည်နေရာတွင် ရှိမရှိ စစ်ဆေးပါ
- Setup Wizard ကို ဆက်လက်အသုံးပြုနိုင်သည် — ရှာဖွေမှု မအောင်မြင်ခြင်းကြောင့် badge တွင် install path ကို မပြခြင်းသာ ဖြစ်သည်

### Handler errors (upstream fetch မအောင်မြင်ခြင်း)

AgentBridge က ကြားဖြတ်ဖမ်းယူသော်လည်း request အားလုံး မအောင်မြင်ပါက:

1. `/dashboard/providers` တွင် provider အနည်းဆုံးတစ်ခု ချိတ်ဆက်ထားကြောင်း စစ်ဆေးပါ
2. OmniRoute server logs ကို စစ်ဆေးပါ: `.env` ထဲရှိ `APP_LOG_LEVEL=debug`
3. `OMNIROUTE_BASE_URL` က မှန်ကန်သော router endpoint ကို ညွှန်ပြထားကြောင်း စစ်ဆေးပါ (ပုံသေ: `http://127.0.0.1:20128`)

## §7 API ကိုးကားချက်

Route အားလုံးသည် `LOCAL_ONLY` (loopback တွင်သာ အသုံးပြုနိုင်ပြီး auth မတိုင်မီ အတည်ပြုကန့်သတ်ထားသည်) နှင့် `SPAWN_CAPABLE` ဖြစ်သည်။ `src/server/authz/routeGuard.ts` ကို ကြည့်ပါ။

အခြေခံ path: `/api/tools/agent-bridge/`

| နည်းလမ်း            | လမ်းကြောင်း                                    | ဖော်ပြချက်                                                                                                                                                    |

## §8 လုပ်ငန်းလမ်းပြမြေပုံ

### Trae စုံစမ်းလေ့လာမှု

Trae သည် အတော်လေးအသစ်ဖြစ်သော AI ကုဒ်ရေးသားမှု အကူကိရိယာတစ်ခုဖြစ်သည်။ handler တစ်ခုကို အကောင်အထည်မဖော်မီ-

1. VS Code / JetBrains marketplace များတွင် သို့မဟုတ် သီးခြား app တစ်ခုအဖြစ် binary/extension ကို ဖော်ထုတ်ပါ
2. API host များနှင့် endpoint ပုံစံများကို ရှာဖွေဖော်ထုတ်ရန် mitmproxy ဖြင့် traffic ကို ဖမ်းယူပါ
3. authentication ယန္တရားကို သတ်မှတ်ဖော်ထုတ်ပါ
4. TOS နှင့် API ကို ရှာဖွေဖော်ထုတ်နိုင်မှုအပေါ် အခြေခံ၍ ဆက်လက်လုပ်ဆောင်သင့်/မသင့်ကို အကဲဖြတ်ပါ

စုံစမ်းလေ့လာမှု မပြီးဆုံးမချင်း dashboard ရှိ Trae card တွင် "ဖြစ်နိုင်ခြေကို အစီရင်ခံရန်" link နှင့်အတူ "စုံစမ်းလေ့လာနေဆဲ" badge ကို ပြသထားသည်။ `src/mitm/handlers/trae.ts` ရှိ handler stub သည် ဖွဲ့စည်းပုံသတ်မှတ်ထားသော `အကောင်အထည်မဖော်ရသေးပါ` error ကို ထုတ်ပေးသည်။

### လုပ်ဆောင်ရန်စာရင်းရှိ agent များ (MITM လိုအပ်သည် — စိတ်ကြိုက် base URL ပံ့ပိုးမှုမရှိပါ)

အောက်ပါကိရိယာများ၏ လက်ရှိ version များတွင် စိတ်ကြိုက် base URL များကို ပံ့ပိုးမထားသဖြင့် MITM သည် တစ်ခုတည်းသော ကြားဖြတ်ဖမ်းယူမှုနည်းလမ်း ဖြစ်သည်။ အသုံးပြုနိုင်ခြေ အကဲဖြတ်မှုကို စောင့်ဆိုင်းနေဆဲဖြစ်သည်-

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — Kiro IDE နှင့် သီးခြားဖြစ်သည်)
- **Cowork** (Anthropic desktop)

မှတ်ချက်- GitHub Copilot CLI ≥v1.0.19 သည် `COPILOT_PROVIDER_BASE_URL` ကို ပံ့ပိုးသည် — ထိုကိရိယာအတွက် MITM အစား တိုက်ရိုက် configuration ကို အသုံးပြုပါ။
