## အများပြည်သူဆိုင်ရာ ကြေညာချက် ဖတ်ရှုစနစ်

ယေဘုယျ ကြေညာချက် ဖတ်ရှုစနစ်သည် Radar feature flag နှင့် သီးခြားဖြစ်သည်။ Dashboard Home နှင့်
Changelog viewer တို့သည် သာမန် `GET` ဖြင့် repository ၏ အများပြည်သူသုံး `news.json` ကို
`NEWS_JSON_URL` (`src/shared/utils/releaseNotes.ts`) မှ ရယူသည်။ ၎င်းတို့သည် Radar setting၊ prompt၊ provider
configuration၊ usage record သို့မဟုတ် local dismissal state တစ်ခုမျှ မပို့ပါ။

`news.json` သည် `parseNewsPayload()` ဖြင့် အကောင်အထည်ဖော်ထားသော ပိတ်ထားသည့် v2 schema ကို အသုံးပြုသည်-

- `schemaVersion: 2` နှင့် အရေအတွက် ကန့်သတ်ထားသော `items[]` collection၊
- တည်ငြိမ်ပြီး ထပ်တူမရှိသော ကြေညာချက် `id` တန်ဖိုးများ၊
- အတိအလင်း သတ်မှတ်ထားသော `active` နှင့် ISO `publishedAt` field များ၊
- မဖြစ်မနေပါဝင်ရမည့် အင်္ဂလိပ်စာသားနှင့် ရွေးချယ်ထည့်သွင်းနိုင်သော ဒေသန္တရဘာသာပြန်စာသား၊
- ရွေးချယ်ထည့်သွင်းနိုင်သော credential မလိုအပ်သည့် HTTPS link များနှင့် allowlist တွင် ပါဝင်သော icon၊
- အသစ်ဆုံး active item ကို ဦးစွာရွေးချယ်ခြင်း၊ locale မရရှိပါက အင်္ဂလိပ်သို့ fallback လုပ်ခြင်းနှင့် ID တစ်ခုချင်းအလိုက် local dismissal။

Fork အဟောင်းများသည် Changelog view ပျက်စီးခြင်းမရှိဘဲ migrate လုပ်နိုင်စေရန် parser သည် ယခင် singular
`{ active, title, message, ... }` ပုံစံကို ယာယီလက်ခံသည်။ မမှန်ကန်သော feed များသည် သက်ရောက်မှုမရှိပါ။ Radar launch
entry ကို `active: false` ဖြင့် ဖြန့်ချိထားသည်။ ၎င်းကို `true` သို့ ပြောင်းလဲခြင်းသည် merge ပြီး၊ deploy ပြီးနောက်
သီးခြားလုပ်ဆောင်ရသော release action ဖြစ်ပြီး `RADAR_ENABLED` သို့မဟုတ် သီးခြား feed-sync opt-in ကို မပြောင်းလဲပါ။

## Flag: `RADAR_ENABLED` (မူလအခြေအနေတွင် ပိတ်ထားသည်)

Radar ကို `RADAR_ENABLED` feature flag ဖြင့် အစမှအဆုံး ထိန်းချုပ်ထားသည်
(`src/shared/constants/featureFlagDefinitions.ts`, category `policies`,
`defaultValue: "false"`)။

**Flag ပိတ်ထားသည့်အခါ ဤမျက်နှာပြင်များ လုံးဝမရှိပါ-**

- Local model-state read နှင့် write များအပါအဝင် `/api/radar/*` endpoint အားလုံးသည်
  Radar module တစ်ခုခုကို မထိတွေ့မီ `404` ပြန်ပေးသည်။
- Dashboard screen များ (`/dashboard/radar`, `/dashboard/radar/setup`,
  `/dashboard/radar/combos`, `/dashboard/radar/offers`, `/dashboard/radar/intel`) သည်
  `notFound()` ကို render လုပ်သည်။
- `getRadarCatalog()` (`src/lib/radar/index.ts`) သည် မူလ baseline ကို မပြောင်းလဲဘဲ ပြန်ပေးသည် —
  entry အရေအတွက်တူ၊ တန်ဖိုးများတူပြီး entry တိုင်းတွင် `origin: "baseline"` ဟု tag လုပ်ထားကာ —
  feed cache ကို မည်သည့်အခါမျှ မဖတ်ပါ။
- Radar network call ကို မည်သည့်အခါမျှ မပြုလုပ်ပါ။ Sync module တစ်ခုချင်းစီသည် `fetch` ကို
  မထိတွေ့မီ `{ status: "disabled" }` ကို ပြန်ပေးသည်။

၎င်းသည် တင်းကျပ်သော superset gate ဖြစ်သည်။ Flag ကို ဖွင့်ခြင်းက _screen များ_ ကိုသာ
အသုံးပြုခွင့်ပေးပြီး အခြားအရာများကို မလုပ်ဆောင်ပါ။ Data ကို upload မလုပ်ပါ၊ background sync ကို မစတင်ပါ၊
routing သို့မဟုတ် model selection ကိုလည်း မပြောင်းပါ — အောက်ပါ သီးခြား opt-in ကို ကြည့်ပါ။

## Data sync သည် သီးခြား opt-in ဖြစ်သည် — ကိုယ်ရေးအချက်အလက် ကာကွယ်ရေး ကတိကဝတ်

`RADAR_ENABLED` ကို ဖွင့်ခြင်းသည် UI ကိုသာ အသုံးပြုခွင့်ပေးသည်။ Feed ကို sync လုပ်ရန်
`radar_settings.opt_in` (`src/lib/db/radar.ts`,
migration `136_radar_cache_settings.sql`) တွင် သိမ်းဆည်းထားသော ဒုတိယမြောက် သီးခြား opt-in လိုအပ်သည်။ `syncRadar()` သည် network call တစ်ခုခု မပြုလုပ်မီ flag _နှင့်_ opt-in နှစ်ခုစလုံးကို စစ်ဆေးသည်-

```
Flag ပိတ်ထားသည်      → { status: "disabled" }   — network call မရှိ
Opt-in false ဖြစ်သည်  → { status: "opt_out" }    — network call မရှိ
```

နှစ်ခုစလုံး ဖွင့်ထားသည့်အခါ sync လမ်းကြောင်းမှာ-

1. `x-omniroute-radar-schema: 2` နှင့် ရွေးချယ်ထည့်သွင်းနိုင်သော
   `Authorization: Bearer <supporter key>` header (အောက်တွင်ကြည့်ပါ) ကို အသုံးပြု၍
   `GET <feed base URL>/v1/catalog/latest` ကို ခေါ်သည်။ Schema header မပါရှိသည့်အခါ server များသည်
   သီးခြားလက်မှတ်ထိုးထားသော v1 transition artifact ကို မူလအဖြစ် အသုံးပြုသောကြောင့် ထည့်သွင်းပြီးသား client
   အဟောင်းများသည် update များကို ဆက်လက်ရရှိနိုင်သည်။
2. ၎င်းသည် download-only application flow ဖြစ်သော်လည်း HTTPS request တစ်ခု ဖြစ်နေဆဲဖြစ်သည်။ Hosted
   infrastructure သည် source IP ကဲ့သို့သော ပုံမှန် connection metadata ကို လက်ခံရရှိသည်။ Supporter
   key တစ်ခု configure လုပ်ထားပါက service က entitlement ကို ဆုံးဖြတ်နိုင်ရန် sync သည် ထို key ကို
   Bearer header ထဲတွင်ပါ ပို့သည်။ အထက်ရှိ evidence boundary တွင် ဖော်ပြထားသော တိကျသည့် private-server revision အရ
   feed-request accounting သည် manual abuse review အတွက် key hash များ၊ စုစုပေါင်း usage နှင့်
   နေ့စဉ်ပြောင်းလဲသော IP ၏ ဖြတ်တောက်ထားသည့် HMAC ကို အသုံးပြုသည်။ ထို table များသည် key သို့မဟုတ် IP ကို raw form ဖြင့်
   မသိမ်းဆည်းပါ။ Infrastructure access log များနှင့် encrypted delivery outbox သည် သီးခြား operational
   boundary များဖြစ်သည်။
3. OmniRoute သည် prompt များ၊ response များ၊ conversation များ၊ provider credential များ၊ model traffic၊
   uptime၊ latency သို့မဟုတ် local provider configuration တို့ကို Radar service သို့ မည်သည့်အခါမျှ မပို့ပါ။
4. Response ကို verify လုပ်ခြင်း၊ validate လုပ်ခြင်းနှင့် local တွင် cache လုပ်ခြင်းတို့ ပြုလုပ်သည် (
   [လုံခြုံရေးပုံစံ](#security-model) ကို ကြည့်ပါ)။ Radar တွင် server-side network path လေးခုသာရှိသည်-
   Catalog အတွက် `syncRadar()`၊ referral များအတွက် `syncRadarReferrals()` နှင့်
   supporter များအတွက်သာဖြစ်သော offer နှင့် Intel အတွက် `syncRadarOffers()` / `syncRadarIntel()` တို့ဖြစ်သည်။

**Supporter key** သည် feed service က မည်သည့် tier ကို ပေးရမည်ဟု ဆုံးဖြတ်နိုင်စေသော ရွေးချယ်ထည့်သွင်းနိုင်သည့် Bearer token
(`radar_settings.supporter_key`) ဖြစ်သည် (
[Tier များ](#tiers-community-and-live) ကို ကြည့်ပါ)။ ၎င်းကို-

- Provider credential များအတွက် အသုံးပြုသော တူညီသည့် AES-256-GCM `encrypt()`/`decrypt()`
  helper များ (`src/lib/db/encryption.ts`) ဖြင့် **သိမ်းဆည်းထားချိန်တွင် encrypt လုပ်ထားသည်**။
- `POST /api/radar/settings` (`{ supporterKey: "omr_" + 40 hex chars }`) မှတစ်ဆင့် သတ်မှတ်ပြီး
  **မည်သည့်အခါမျှ ပြန်လည်မဖော်ပြပါ** — response သည် ဖုံးကွယ်ထားသောပုံစံ (`omr_****abcd`) ကို ပြန်ပေးသည်။
- ပြောင်းလဲခြင်း သို့မဟုတ် ဖယ်ရှားခြင်းသည် catalog၊ referral၊ offer နှင့် Intel cache များကို atomic ပုံစံဖြင့် invalidate လုပ်သည်။ နောက်တစ်ကြိမ်
  sync/read လုပ်သည့်အခါ entitlement အသစ်ကို server-side တွင် ဆုံးဖြတ်သည်။ Key တစ်ခု save လုပ်ခြင်းသည်
  network request ကို ကိုယ်တိုင်မပြုလုပ်သလို single-use activation key ကိုလည်း အသုံးမပြုပါ။
- Sync GET ပြုလုပ်ချိန်တွင် feed service သို့ Bearer token အဖြစ် ပို့သည် — key နှင့်ပတ်သက်သော အခြားမည်သည့်အရာမျှ
  client မှ ထွက်မသွားပါ။

ပေးအပ်ပြီးသောအချိန်ကို နောက်ကြောင်းပြန်၍ ရုပ်သိမ်းခြင်း သို့မဟုတ် လျှော့ချခြင်း မပြုပါ။

hosted license သည် ကိုယ်ရေးကိုယ်တာသုံးအတွက်ဖြစ်ပြီး အသုံးပြုသူအား အသိပေးထားသော စည်းမျဉ်းမှာ တစ်ချိန်လျှင် လက်ရှိအသုံးပြုနေသည့် installation တစ်ခုသာ ခွင့်ပြုခြင်းဖြစ်သည်။ ဤ
release သည် **hardware lock ရှိသည်ဟု မဆိုပါ**။ OSS sync သည် hardware fingerprint ဖမ်းယူခြင်း သို့မဟုတ်
cryptographic device lease ကို ထိန်းသိမ်းခြင်း မပြုပါ။ အထက်တွင်ဖော်ပြထားသော အတည်ပြုပြီးသည့် private-server revision တွင် အကောင်အထည်ဖော်ထားသော ထိန်းချုပ်မှုမှာ
ရပိုင်ခွင့်အတည်ပြုခြင်းနှင့် 24 နာရီအတွင်း မတူညီသော IP လေးခုမြောက်မှ တူညီသည့် live key ကို တွေ့ရှိပါက manual review ပြုလုပ်ရန် signal ပေးခြင်းတို့ဖြစ်သည်။
ထို signal သည် key ကို အလိုအလျောက် ပိတ်ပင်ခြင်း သို့မဟုတ် ရုပ်သိမ်းခြင်း လုံးဝမပြုပါ။ Recovery လုပ်ဆောင်ချက်သည်
ပျောက်ဆုံးသွားသော key ကို ရုပ်သိမ်းပြီး အစားထိုးပေးကာ လက်ရှိသက်တမ်းကုန်ဆုံးချိန်ကို ဆက်လက်ထိန်းသိမ်းထားသည်။ ဝယ်ယူထားသော သို့မဟုတ် ပေးအပ်ထားသော
ကာလကို အစမှပြန်စခြင်း မပြုပါ။

Live offers များကို ကိုယ်တိုင်ရွေးချယ်စီမံထားပြီး ပြောင်းလဲနိုင်သကဲ့သို့ သက်တမ်းကုန်ဆုံးနိုင်သည်။ ပါဝင်ရန် သဘောတူသည့် screen တွင် တိကျသော
ကိုယ်ရေးအချက်အလက်ဆိုင်ရာ နယ်နိမိတ်ကိုလည်း ဖော်ပြထားသည်။ လက်မှတ်ရေးထိုးထားသော catalog/referral metadata ကို download လုပ်သည်။ အကျုံးဝင်သော key သည် ထို့အပြင်
လက်မှတ်ရေးထိုးထားသော offers နှင့် Intel ကို အသုံးပြုခွင့်ဖွင့်ပေးသည်။ Bearer key နှင့် ပုံမှန် connection metadata တို့သည် hosted service သို့ ရောက်ရှိသည်။
prompt များ၊ response များ၊ conversation များ၊ provider credential များ၊ model traffic၊ uptime၊ latency နှင့် local
provider configuration တို့သည် ရောက်ရှိခြင်းမရှိပါ။

## ထောက်ပံ့သူ key ရယူခြင်း

အသက်သွင်းမှု မျက်နှာပြင် (`/dashboard/radar`) တွင် ထောက်ပံ့သူ key ကို **ရယူရန်** လုပ်ငန်းစဉ်နှစ်ခုသို့ ချိတ်ဆက်ထားသည်။ OSS repo ကိုယ်တိုင်က key မထုတ်ပေးသကဲ့သို့ ငွေပေးချေမှု code ကိုလည်း မလုပ်ဆောင်ပါ၊ ထို့ပြင် **စျေးနှုန်းကို မည်သည့်အခါမျှ မဖော်ပြပါ** — စျေးနှုန်းသတ်မှတ်ခြင်းနှင့် ပြသခြင်းကို ဤ repo အတွင်းမဟုတ်ဘဲ သွားရောက်မည့် စာမျက်နှာများတွင်သာ အပြည့်အဝ ဆောင်ရွက်သည် (သတ်မှတ်ချက် ဆုံးဖြတ်ချက် D14)။

- **"ကျွန်ုပ်သည် ပါဝင်ကူညီသူဖြစ်သည်"** — သီးသန့် Radar server တွင် လက်ခံဆောင်ရွက်ထားသော GitHub OAuth တောင်းဆိုမှု လုပ်ငန်းစဉ်ဖြစ်သည့် `RADAR_CONTRIBUTOR_CLAIM_URL` (မူလသတ်မှတ်ချက်
  `https://radar.omniroute.online/auth/github`) ကို ဖွင့်သည်။ ၎င်းသည် နောက်ဆုံးပြီးစီးထားသော အပတ်စဉ်အဆင့်သတ်မှတ်ချက်ကို စစ်ဆေးသည်။ ထိပ်ဆုံး 10 ဦးသည် 365 ရက် ရရှိပြီး
  အဆင့် 11–100 သည် 90 ရက် ရရှိသည်။ ထိပ်ဆုံး 100 ပြင်ပတွင် PR အရေအတွက်ကြောင့် ဝင်ရောက်ခွင့်ကို မည်သည့်အခါမျှ မပေးပါ။ ယင်းအစား သီးခြား star + follow တစ်ကြိမ်သုံး အဆင့်ကို လုပ်ငန်းစဉ်က စစ်ဆေးသည်။
- **"ပရောဂျက်ကို ထောက်ပံ့မည်"** — တစ်ကြိမ်ပေးချေသည့် 6 လ၊ 1 နှစ်နှင့်
  တစ်သက်တာ ရွေးချယ်စရာများအတွက် လက်ခံဆောင်ရွက်ထားသော စာမျက်နှာဖြစ်သည့် `RADAR_SUPPORTER_PLANS_URL` (မူလသတ်မှတ်ချက်
  `https://radar.omniroute.online/planos`) ကို ဖွင့်သည်။ OSS စာမျက်နှာတွင် ငွေကြေးတန်ဖိုးကို မပြသသေးပါ။

URL နှစ်ခုစလုံးကို server ဘက်တွင် ဖြေရှင်းသတ်မှတ်ထားပြီး (`src/lib/radar/links.ts`၊ `RADAR_FEED_URL` နှင့်တူညီသော env-override
ပုံစံ) ရှိပြီးသား `GET /api/radar/settings` တုံ့ပြန်ချက် (`contributorClaimUrl`, `supporterPlansUrl`) မှတစ်ဆင့် dashboard သို့ လက်ဆင့်ကမ်းပေးသည် — client component သည် `process.env` ကို ကိုယ်တိုင် မည်သည့်အခါမျှ မဖတ်ပါ။

| Var                           | ရည်ရွယ်ချက်                                                                                                        |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `RADAR_CONTRIBUTOR_CLAIM_URL` | ပါဝင်ကူညီသူ တောင်းဆိုမှု URL ကို အစားထိုးသတ်မှတ်သည် (မူလသတ်မှတ်ချက် `https://radar.omniroute.online/auth/github`)။ |
| `RADAR_SUPPORTER_PLANS_URL`   | ထောက်ပံ့သူ အစီအစဉ်များ URL ကို အစားထိုးသတ်မှတ်သည် (မူလသတ်မှတ်ချက် `https://radar.omniroute.online/planos`)။        |

### ပျောက်ဆုံးသွားသော ထောက်ပံ့သူ key ကို ပြန်လည်ရယူခြင်း

လက်ခံဆောင်ရွက်ထားသော ဝန်ဆောင်မှု၏ ပြန်လည်ရယူရေး ဝင်ပေါက်မှာ `https://radar.omniroute.online/recover` ဖြစ်ပြီး ၎င်းကို အစီအစဉ်များ စာမျက်နှာမှလည်း ချိတ်ဆက်ထားသည်။ ဒေသတွင်းထည့်သွင်းမှုသည် ဝယ်ယူသူ/ပါဝင်ကူညီသူ၏ အီးမေးလ်ကို မည်သည့်အခါမျှ လက်ခံမရရှိသည့်အပြင် ၎င်း၏ ကုဒ်ဝှက်ထားသော ဆက်တင်များမှ မူရင်း key ကို ပြန်လည်တည်ဆောက်၍ မရနိုင်သောကြောင့် ပြန်လည်ရယူခြင်းသည် OSS client ၏ ပြင်ပတွင်သာ အပြည့်အဝ ရှိနေသည်။

1. key နှင့်ဆက်စပ်သော အီးမေးလ်ကို တင်သွင်းပါ။ ပြန်လည်ရယူနိုင်သော လိုင်စင် ရှိသည်ဖြစ်စေ မရှိသည်ဖြစ်စေ ဝန်ဆောင်မှုသည် တူညီသော လက်ခံပြီး စာမျက်နှာကို ပြန်ပေးသဖြင့် form က account များကို စာရင်းထုတ်ဖော်မပြပါ။
2. အရည်အချင်းပြည့်မီပါက ပေးပို့ရေး worker သည် သက်တမ်းတိုပြီး တစ်ကြိမ်သုံး link တစ်ခုကို ပေးပို့သည်။ ၎င်းကို ဖွင့်လိုက်သည်နှင့် token ကို ယာယီ ကုဒ်ဝှက်ထားသော `HttpOnly`/`Secure` cookie သို့ ချက်ချင်းရွှေ့ပြီး သန့်ရှင်းသော
   `/recover` URL သို့ ပြန်ညွှန်းသည်။ စာမျက်နှာတွင် token၊ အီးမေးလ်၊ key အဟောင်း သို့မဟုတ် အစားထိုး key တို့ မပါဝင်ပါ။
3. ပြန်လည်ရုပ်သိမ်းမှုကို အတည်ပြုပါ။ သီးသန့်ဝန်ဆောင်မှုသည် ယခင် key ကို ပြန်လည်ရုပ်သိမ်းပြီး တူညီသော အစီအစဉ်/သက်တမ်းကုန်ဆုံးရက်ဖြင့် အစားထိုး key ကို ဖန်တီးကာ transaction တစ်ခုတည်းအတွင်း အီးမေးလ်ဖြင့်ပို့ရန် တန်းစီထားသည်။ အစားထိုး key ကို browser သို့ မည်သည့်အခါမျှ ပြန်မပို့ပါ။
4. အစားထိုး key ကို `/dashboard/radar` ထဲသို့ ကူးထည့်ပါ။ ယခု key အဟောင်းသည် `community` သို့ အဆင့်လျော့သွားရမည်ဖြစ်ပြီး အစားထိုး key သည် အတည်ပြုထားသော `live` sync ကို ထုတ်ပေးရမည်။ တူညီသော ပြန်လည်ရယူရေး link ကို ပြန်ဖွင့်ပါက ယေဘုယျ မမှန်ကန်/သက်တမ်းကုန် တုံ့ပြန်ချက်ဖြင့် မအောင်မြင်ရပါမည်။

လက်ခံဆောင်ရွက်ထားသော ပြန်လည်ရယူရေး route နှင့် mail worker သည် code ထဲတွင် ရှိနိုင်သော်လည်း deployment တစ်ခုခုတွင် အသုံးမပြုနိုင်သေးခြင်း ဖြစ်နိုင်သည်။ server ကို deploy လုပ်ပြီး၊ ပေးပို့ရေး provider ကို ထိန်းချုပ်ထားသော လက်ခံသူဖြင့် ပြင်ဆင်သတ်မှတ်ပြီး၊ တစ်ကြိမ်သုံး link အပြည့်အစုံကို စမ်းသပ်ပြီးသည်အထိ ဤလုပ်ငန်းစဉ်ကို ထုတ်လုပ်ရေးအတွက် အသင့်ဖြစ်ပြီဟု မသတ်မှတ်ပါနှင့်။

လာရောက်သူတစ်ဦးတွင် key (`omr_` + hex အက္ခရာ 40 လုံး) ရှိလာသည်နှင့် အသက်သွင်းမှု မျက်နှာပြင်
(`src/app/(dashboard)/dashboard/radar/page.tsx`) တွင် key ကူးထည့်ရန် input ကို အဓိကလမ်းကြောင်းအဖြစ် ထားရှိသည်။ key တစ်ခုကို ကူးထည့်ပြီး တင်သွင်းခြင်းသည် ခေါ်ဆိုမှုတစ်ခုတည်းဖြင့် `POST /api/radar/settings`
(`{ optIn: true, supporterKey }`) ကို ပေးပို့သည် — key ကူးထည့်ခြင်းသည် ၎င်းကို သတ်မှတ်ပေးသည့်အပြင် ပါဝင်ရန်လည်း ရွေးချယ်ပေးကာ မျက်နှာပြင်ကို လော့ခ်ဖွင့်ပေးသည်။ ပုံစံ (`omr_` + hex အက္ခရာ 40 လုံး) ကို UX အဆင်ပြေစေရန် မျှဝေထားသော `isValidSupporterKeyFormat()` helper (`src/lib/radar/supporterKey.ts`) ဖြင့် client ဘက်တွင် ဦးစွာ စစ်ဆေးသည်။ မည်သို့ပင်ဖြစ်စေ server ၏ Zod schema သည် အဆုံးအဖြတ်ပေးသည့် စစ်ဆေးမှုဖြစ်သည်။ key တစ်ခု သတ်မှတ်ပြီးသည်နှင့် အသက်သွင်းမှု မျက်နှာပြင်သည် input အလွတ်အစား ဖုံးကွယ်ထားသော ပုံစံ (`GET /api/radar/settings` မှ `supporterKeyMasked`) ကို ပြသပြီး key အသစ်တစ်ခု ကူးထည့်နိုင်ရန် "key ပြောင်းရန်" ထိန်းချုပ်မှုတစ်ခု ပါရှိသည် — မူရင်း key ကို မည်သည့်အခါမျှ ပြန်လည်မပြသပါ။ အထက်ပါ တောင်းဆိုမှု/အစီအစဉ် ခလုတ်နှစ်ခုသည် အစကတည်းက key တစ်ခုကို _ရယူရန်_ နည်းလမ်းများအဖြစ် ဆက်ရှိနေသည်။ ဤ input သည် key ရှိပြီးသား operator တစ်ဦးက ၎င်းကို အသက်သွင်းသည့်နေရာဖြစ်သည်။

### အစမှအဆုံး အသက်သွင်းခြင်းနှင့် လမ်းညွှန်ထားသော ပြင်ဆင်သတ်မှတ်မှု

သီးသန့် feed ဝန်ဆောင်မှုနှင့် ဤ OSS client ကြားတွင် ရည်ရွယ်ချက်ရှိရှိ ကျဉ်းမြောင်းသော နယ်နိမိတ်တစ်ခု ရှိသည်။ ဝန်ဆောင်မှုက ထောက်ပံ့သူ key ကို ထုတ်ပေးပြီး အတည်ပြုသော်လည်း ဒေသတွင်း OmniRoute ထည့်သွင်းမှုက key ကို ကုဒ်ဝှက်ခြင်း၊ လက်မှတ်ထိုးထားသော artifact များကို server ဘက်တွင် sync လုပ်ခြင်းနှင့် provider ပြင်ဆင်သတ်မှတ်မှုကို လမ်းညွှန်ခြင်းတို့ ပြုလုပ်သည်။ အကူအညီဖြင့် အတည်ပြုသည့် အစီအစဉ်မှာ-

1. ပံ့ပိုးသူအဖြစ် အတည်ပြုတောင်းဆိုမှု၊ အစီအစဉ်များ/ငွေရှင်းမှု၊ ပြန်လည်ရယူရေးလုပ်ငန်းစဉ် သို့မဟုတ် ခွင့်ပြုထားသော သီးသန့်ဆာဗာ အော်ပရေတာထံမှ အသစ်ထုတ်ပေးထားသော သို့မဟုတ် ပြန်လည်ရယူထားသော ကီးတစ်ခုကို ရယူပါ။ ကီးအကြမ်းကို မှတ်တမ်းများ၊
   ဖန်သားပြင်ဓာတ်ပုံများ၊ ပြဿနာမှတ်ချက်များ သို့မဟုတ် command-line argument များထဲသို့ မကူးထည့်ပါနှင့်။
2. စက်တွင်း OmniRoute ထည့်သွင်းမှုတွင် `RADAR_ENABLED` feature flag ကို ဖွင့်ပါ။ ၎င်းသည် UI ကို
   အသုံးပြုနိုင်စေသော်လည်း သီးခြားခွင့်ပြုချက်ကို သိမ်းဆည်းမထားမချင်း ကွန်ရက်လုပ်ဆောင်မှု မရှိသေးပါ။
3. `/dashboard/radar` ကိုဖွင့်၍ ကီးကိုကူးထည့်ပြီး အသက်သွင်းပါ။ ဘရောက်ဇာသည် စက်တွင်း
   `POST /api/radar/settings` တစ်ကြိမ်ကို `{ optIn: true, supporterKey }` ဖြင့် ပေးပို့သည်။ ကီးကို စက်တွင်း၌ ကုဒ်ဝှက်ထားပြီး
   တုံ့ပြန်ချက်တွင် `omr_****<last4>` သာ ပါဝင်သည်။
4. အသက်သွင်းမှုမျက်နှာပြင်ကို ၎င်း၏ catalog sync လုပ်ငန်းစဉ် ပြီးဆုံးအောင် လုပ်ဆောင်ခွင့်ပြုပါ သို့မဟုတ် **ယခု Sync လုပ်ရန်** ကို ရွေးပါ။ စာမျက်နှာတွင်
   `live`၊ feed ဗားရှင်းတစ်ခုနှင့် ရယူခဲ့သည့်အချိန်ကို ဖော်ပြထားကြောင်း အတည်ပြုပါ။ အထောက်အထားစိစစ်ပြီးဖြစ်သော စက်တွင်း diagnostic အတွက်
   `GET /api/radar/status` သည် ကီးကို ပြန်မပေးဘဲ opt-in/ကီး ရှိမရှိနှင့် cache အခြေအနေလေးမျိုးကို ဖော်ပြသည်။
   `POST /api/radar/sync-all` ဖြင့် catalog၊ referrals၊ offers နှင့် Intel တို့ကို တိတိကျကျ ပြန်လည်ရယူနိုင်သည်။
5. `/dashboard/radar/setup?provider=<provider>` ကို ဖွင့်ပါ။ ပံ့ပိုးသူက စီမံပိုင်ဆိုင်သည့် credential URL သို့ သွား၍
   **API ကီးထည့်ရန်** ကို ရွေးပါ၊ ပံ့ပိုးသူ၏ အမှန်တကယ် form မှတစ်ဆင့် သိမ်းဆည်းပါ၊ လမ်းညွှန်သို့ ပြန်လာပြီး
   **ချိတ်ဆက်မှုကို စမ်းသပ်ရန်** ကို လုပ်ဆောင်ပါ။ လမ်းညွှန်သည် ပုံမှန် `/api/providers` နှင့်
   `/api/providers/<connection-id>/test` route များကို အသုံးပြုသည်။ ၎င်းသည် သီးခြား Radar credential တစ်ခုကို မဖန်တီးပါ။
6. လိုက်ဖက်သော ပံ့ပိုးသူချိတ်ဆက်မှု အနည်းဆုံးနှစ်ခု အသက်ဝင်ပြီးနောက် `/dashboard/radar/combos` ကို ဖွင့်ပါ။
   အကြံပြုထားသော အုပ်စုကို သုံးသပ်ပြီး ရှိပြီးသား combo API မှတစ်ဆင့် combo ကို ဖန်တီးပါ။ Offers နှင့်
   Intel တို့သည် သီးခြား live-only signed cache များအဖြစ် ဆက်လက်ရှိနေပြီး ၎င်းတို့၏ သီးသန့် Radar စာမျက်နှာများတွင် စစ်ဆေးနိုင်သည်။
7. `/dashboard/radar` နှင့် setup စာမျက်နှာကို ပြန်လည်ဖွင့်ပါ။ opt-in၊ ဖုံးကွယ်ထားသောကီး အခြေအနေ၊ အတည်ပြုပြီးသော cache၊ သိမ်းဆည်းထားသည့်
   ပံ့ပိုးသူချိတ်ဆက်မှုနှင့် စမ်းသပ်လုပ်ဆောင်ချက်တို့သည် ပြန်လည်ဖွင့်ပြီးနောက် ဆက်လက်တည်ရှိရမည်။ ကီးအကြမ်းနှင့် ပံ့ပိုးသူ credential တို့ကို
   မမြင်ရတော့သည့်နောက်မှသာ အထောက်အထားကို မှတ်တမ်းတင်ပါ။

ကီးတစ်ခုကို သိမ်းဆည်းခြင်းတစ်ခုတည်းသည် live အသုံးပြုခွင့်ရှိကြောင်း သက်သေမဟုတ်ပါ။ သက်သေမှာ သီးသန့်
ဝန်ဆောင်မှု၏ `GET /v1/license/check` ရလဒ်၊ OSS catalog က ပေးပို့သည့် `live` tier၊ အတည်ပြုပြီးသော signed
cache နှင့် အမှန်တကယ် ပံ့ပိုးသူချိတ်ဆက်မှု/စမ်းသပ်မှု လုပ်ငန်းစဉ်တို့ ပေါင်းစပ်ထားခြင်း ဖြစ်သည်။ မမှန်ကန်သော၊ သက်တမ်းကုန်သော သို့မဟုတ် ရုပ်သိမ်းထားသော ကီးသည်
catalog ကို `community` သို့ ဘေးကင်းစွာ အဆင့်လျှော့ပေးသည်။ ၎င်းကို live ကီး စစ်ဆေးအတည်ပြုမှု အောင်မြင်သည်ဟု မဖော်ပြရပါ။

### သီးသန့် admin-panel လင့်ခ်

`RADAR_ADMIN_URL` သည် Costs sidebar အပိုင်းရှိ အသုံးပြုသူမြင်နိုင်သော
Radar အရာ၏နောက်တွင် **Radar Admin ↗** ကို ရွေးချယ်စရာအဖြစ် ချက်ချင်းထည့်ပေးသည်။ ၎င်းတွင် ရည်ရွယ်ချက်ရှိရှိ မူလတန်ဖိုး မသတ်မှတ်ထားပါ။ variable ကို
မသတ်မှတ်ထားသည့်အခါ သို့မဟုတ် မမှန်ကန်သည့်အခါ static sidebar၊ command palette နှင့် sidebar-customization မျက်နှာပြင်တို့တွင်
admin အရာနှင့် သီးသန့် URL တို့ မပါဝင်ပါ။

တန်ဖိုးကို ဆာဗာဘက်တွင် ဖြေရှင်းပြီး စီမံခန့်ခွဲမှုဆိုင်ရာ အထောက်အထားစိစစ်ထားသော
`GET /api/settings` တုံ့ပြန်ချက်မှတစ်ဆင့် အထောက်အထားစိစစ်ပြီးသော dashboard session သို့သာ သို့မဟုတ် စက်တွင်း login မလိုသော bootstrap အတွင်း ယုံကြည်ရသည့်
loopback ပိုင်ရှင်ထံသို့သာ ပေးပို့သည်။ CLI၊ internal-service နှင့် manage-scope API-key
အထောက်အထားစိစစ်မှုတို့သည် ၎င်းကို လက်ခံရရှိမည်မဟုတ်ပါ။ ဘရောက်ဇာသည် `noopener noreferrer` ဖြင့် ဖွင့်သည့်
ပြင်ပလင့်ခ်ကို ဖန်တီးမပြသမီ တုံ့ပြန်ချက်ကို ထပ်မံစစ်ဆေးအတည်ပြုသည်။

credential မပါသော HTTPS tunnel/tailnet URL ကို အသုံးပြုပါ။ `http://127.0.0.1:9351` ကဲ့သို့ loopback SSH
forward အတွက်သာ plain HTTP ကို လက်ခံသည်။ အခြား scheme များ၊ ထည့်သွင်းထားသော credential များ၊ ပုံစံမမှန်သော URL များနှင့်
အဝေးမှ HTTP destination များသည် လုံခြုံစွာ ပိတ်သွားပြီး လမ်းညွှန်သွားလာမှုကို လုပ်ဆောင်နိုင်ခြင်းမရှိစေပါ။

## လုံခြုံရေးပုံစံ

### အတိအကျ byte များအပေါ် Ed25519 လက်မှတ်

Feed payload ကို Ed25519 ဖြင့် လက်မှတ်ထိုးထားသည်။ `verifyFeedBytes()`
(`src/lib/radar/verify.ts`) သည် ကွန်ရက်မှတစ်ဆင့် လက်ခံရရှိသော **အတိအကျ response byte များ**
အပေါ်တွင် လက်မှတ်ကို အတည်ပြုသည် — အတည်မပြုမီ payload ကို မည်သည့်အခါမျှ ပြန်လည် serialize မလုပ်သောကြောင့်
byte-for-byte ပြန်လည် encoding လုပ်ခြင်းသည် လက်မှတ်စစ်ဆေးမှုကို သတိမပြုမိဘဲ ပျက်ပြယ်စေခြင်း သို့မဟုတ် ကျော်လွှားခြင်း
မပြုနိုင်ပါ။ အတည်ပြုမှု မအောင်မြင်ခြင်း (`invalid_signature`) သည် payload ကို
parse သို့မဟုတ် cache မလုပ်မီ sync ကို ရပ်တန့်စေသည်။

### ပုံသေသတ်မှတ်ထားသော public key + အစားထိုးလည်ပတ်ခြင်း

အတည်ပြုရန်အသုံးပြုသည့် public key ကို `src/lib/radar/pinnedKeys.ts`
(`PINNED_FEED_PUBLIC_KEYS`) တွင် ပုံသေသတ်မှတ်ထားသည်။ ၎င်းသည် array တစ်ခုဖြစ်သဖြင့် key
အစားထိုးလည်ပတ်မှုမတိုင်မီ key အသစ်ကို ရှေ့ဆုံးတွင် ထည့်နိုင်ပြီး၊ ယခင် key ဖြင့် လက်မှတ်ထိုးထားသော
cache ထဲရှိ feed အဟောင်းများသည် ပြန်လည် sync မလုပ်မချင်း ဆက်လက် အကျုံးဝင်နေမည်ဖြစ်သည်။

### Fork များအတွက် အဆင်ပြေသော env override များ

အောက်ပါ env var နှစ်ခုက fork ပြုလုပ်သူများနှင့် ကိုယ်တိုင် host လုပ်သူများအား client ကို
မူလ OmniRoute ဝန်ဆောင်မှုအစား ၎င်းတို့၏ကိုယ်ပိုင် feed သို့ ညွှန်ပေးနိုင်စေသည် — အောက်ရှိ
[Feed တစ်ခုကို ကိုယ်တိုင် host လုပ်နည်း](#how-to-self-host-a-feed) ကို ကြည့်ပါ-

| Var                 | ရည်ရွယ်ချက်                                                                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `RADAR_FEED_URL`    | Feed base URL ကို override လုပ်သည် (မူလ `https://radar.omniroute.online`)။                                                                       |
| `RADAR_FEED_PUBKEY` | ပုံသေသတ်မှတ်ထားသော public key ကို override လုပ်ပြီး (base64-DER SPKI သို့မဟုတ် PEM) ထည့်သွင်းထားသည့် array ကို ဤ key တစ်ခုတည်းဖြင့် အစားထိုးသည်။ |

### အနိမ့်ဆုံး version သတ်မှတ်ချက်

`syncRadar()` သည် လက်ရှိ cache ထဲရှိ version ထက် `version` က တိတိကျကျ ပိုသစ်မနေသော
download လုပ်ထားသည့် feed ကို ပယ်ချသည် (`compareVersions()`, အစက်ဖြင့်ခွဲထားသော `YYYY.MM.DD.n` နှိုင်းယှဉ်မှု) —
`{ status: "stale" }`။ ၎င်းက ထိခိုက်ပျက်စီးနေသော သို့မဟုတ် မှားယွင်းစွာ စီစဉ်ထားသော feed endpoint တစ်ခုမှ
client ကို ပိုဟောင်းပြီး မတူညီသော လက်မှတ်ပါရှိသည့် payload သို့ ပြန်လည်လျှော့ချခြင်းကို တားဆီးသည်။

### ရက်စွဲနှစ်ခုနှင့် နှစ်ခုစလုံးကို ထိန်းသိမ်းထားရသည့်အကြောင်းရင်း

Cache ထဲရှိ feed တစ်ခုတွင် ကွဲပြားသော ရက်စွဲနှစ်ခု ပါဝင်ပြီး၊ ၎င်းတို့ကို ရောထွေးမှတ်ယူနိုင်ခြင်းကြောင့်ပင်
နှစ်ခုစလုံးကို ထိန်းသိမ်းထားခြင်းဖြစ်သည်-

| Field         | ရရှိသည့်နေရာ                | ဖြေဆိုပေးသည့်အရာ                                              |
| ------------- | --------------------------- | ------------------------------------------------------------- |
| `generatedAt` | လက်မှတ်ထိုးထားသော feed body | **ဒေတာ** မည်မျှဟောင်းနေပြီလဲ                                  |
| `fetchedAt`   | ဤ install ၏ နာရီ            | ဤ install က ၎င်းကို မည်သည့်အချိန်တွင် **download** လုပ်ခဲ့သလဲ |

မိနစ်ပိုင်းအတွင်း ရယူထားသော feed တစ်ခုတွင် ရက်သတ္တပတ်များစွာ ဟောင်းနေသည့် ကိန်းဂဏန်းများ ပါဝင်နိုင်သဖြင့်
`fetchedAt` တစ်ခုတည်းဖြင့် overlay သည် ၎င်းအခြေခံထားသော baseline ထက် ပိုမိုသစ်လွင်မှုရှိမရှိကို
operator တစ်ဦးအား မပြောနိုင်ပါ။ နှစ်ခုစလုံးကို `radar_feed_cache` တွင် အမြဲတမ်းသိမ်းထားပြီး
`getRadarCatalog().meta` မှ ပြန်ပေးကာ `GET /api/radar/status` မှ သီးခြားစီ
အစီရင်ခံသည်။ `generated_at` column မရှိမီ (migration 163) cache လုပ်ထားသော row တစ်ခုကို
ပြန်ဖတ်သည့်အခါ `null` အဖြစ် ရရှိသည် — မသိရှိသောအရာသည် fetch လုပ်ချိန်ကို ယူသုံးမည့်အစား
မသိရှိသည့်အတိုင်း ဆက်ရှိနေသည်။ `radar_referrals_cache` သည် migration 142 ကတည်းက
၎င်း၏ကိုယ်ပိုင် `generated_at` ကို ထိန်းသိမ်းထားသည်။

အထက်ပါ အနိမ့်ဆုံး version သတ်မှတ်ချက်သည် ရက်စွဲတစ်ခုခုမဟုတ်ဘဲ `version` ကို နှိုင်းယှဉ်သည်။

ကွာဟချက်နှစ်ခု ကျန်ရှိနေပြီး နှစ်ခုစလုံးကို ရည်ရွယ်ချက်ရှိရှိ ချန်ထားခြင်းဖြစ်သည်- dashboard တွင်
`Last fetched` ကိုသာ ပြသနေဆဲဖြစ်သဖြင့် ထိုနေရာ၌ build ရက်စွဲကို ဖတ်ရှုနိုင်ရန် label အသစ်တစ်ခု
(နှင့် ၎င်း၏ locale entry 41 ခု) လိုအပ်သည်။ ထို့အပြင် offers နှင့် intel cache များ၏ feed schema များတွင်
build ရက်စွဲပါဝင်သော်လည်း ၎င်းတို့က build ရက်စွဲကို လုံးဝမသိမ်းထားပါ — ထို့ကြောင့် `GET
/api/radar/status` သည် "မသိရှိ" ဟု အဓိပ္ပာယ်ရနိုင်သည့် `null` ကို အစီရင်ခံမည့်အစား
ထိုနှစ်ခုအတွက် field ကို ချန်လှပ်ထားသည်။

### Schema အတည်ပြုခြင်း

Download လုပ်ထားသော byte များကို လက်မှတ်အတည်ပြုပြီးနောက် **မှသာ**
`RadarFeedSchema` (`src/lib/radar/feedSchema.ts`, Zod schema တစ်ခု) နှင့်ကိုက်ညီမှုရှိမရှိ
parse လုပ်ပြီး အတည်ပြုသည်။ Schema မကိုက်ညီပါက `{ status: "invalid_schema" }` ကို ပြန်ပေးပြီး
cache ကို မပြောင်းလဲဘဲထားသည်။ Cache ထဲရှိ payload ကို ဖတ်ရှုတိုင်း (`getRadarCatalog()`)
ကြိုတင်ကာကွယ်ရေးအနေဖြင့် ထပ်မံအတည်ပြုသည် — ပျက်စီးနေသော သို့မဟုတ် လက်ဖြင့်ပြင်ဆင်ထားသော
cache row တစ်ခုကို ပေးပို့မည့်အစား baseline သို့ ပြန်လည်အသုံးပြုသည်။

### Response အရွယ်အစား ကန့်သတ်ချက် (10 MB)

`syncRadar()` သည် feed response body အပေါ် **10 MB အမြင့်ဆုံးကန့်သတ်ချက်** ကို တင်းကျပ်စွာ
သတ်မှတ်ထားသည် — လက်မှတ်ထိုးထားသော feed သည် KB အရွယ်အစားရှိ JSON document တစ်ခုဖြစ်သောကြောင့်
ဤအရွယ်အစားထက်ကျော်လွန်သည့်အရာသည် တရားဝင် catalog မဟုတ်ဘဲ မှားယွင်းစွာ စီစဉ်ထားသော သို့မဟုတ်
အန္တရာယ်ပြုလိုသော `RADAR_FEED_URL` (သို့မဟုတ် အဓိပ္ပာယ်မရှိသောဒေတာ ပေးပို့နေသည့် upstream) ကို
ညွှန်ပြသည်။ ကန့်သတ်ချက်ကို အလွှာနှစ်ထပ်ဖြင့် အကောင်အထည်ဖော်ထားသည်-

1. `Content-Length` preflight စစ်ဆေးမှုသည် header တွင် ကန့်သတ်ချက်ထက်ကျော်သော တန်ဖိုးကို
   ကြေညာထားပြီးဖြစ်ပါက body ကို လုံးဝမဖတ်ဘဲ ကျော်သွားသည်။
2. Body ကို ဖတ်နေစဉ် စုစုပေါင်းအရွယ်အစားကို ဆက်တိုက်စစ်ဆေးခြင်းက `Content-Length`
   မပါရှိသည့်အခါ သို့မဟုတ် တကယ့်အရွယ်အစားထက် လျော့နည်းစွာ ဖော်ပြထားသည့်အခါတွင်ပင်
   ကန့်သတ်ချက်ကို အသက်ဝင်စေသည် — header တစ်ခုတည်းကို မည်သည့်အခါမျှ ယုံကြည်အားထားခြင်းမရှိပါ။
   စုဆောင်းထားသော chunk များကို ဆက်စပ်ပေါင်းစည်းခြင်းဖြင့် နောက်ပိုင်း Ed25519 လက်မှတ်စစ်ဆေးမှုအတွက်
   လိုအပ်သော အတိအကျ byte များကို ထိန်းသိမ်းထားသည်။

ကန့်သတ်ချက်ကျော်လွန်ပါက `{ status: "too_large" }` ကို ပြန်ပေးပြီး cache ကို မပြောင်းလဲဘဲထားကာ၊
အခြား sync မအောင်မြင်မှုတိုင်း (`invalid_signature`, `invalid_schema`, `stale`) ကဲ့သို့ပင်
မူလအခြေအနေကို မဖျက်ဆီးသော ပုံစံအတိုင်း လုပ်ဆောင်သည်။

## အဆင့်များ: `community` နှင့် `live`

Feed schema တွင် `tier: "community" | "live"` field ပါဝင်ပြီး၊ request ကို အခြေခံ၍
(supporter key ရှိ၊ မရှိနှင့် မှန်ကန်မှုအပေါ် မူတည်ကာ) feed service က **server-side**
တွင် ဆုံးဖြတ်သည် — client က မိမိ၏ tier ကို ဘယ်တော့မှ ကိုယ်တိုင် မဆုံးဖြတ်ပါ။

- **`community`** — နောက်ဆုံးပေါ် data ထက် ရက် 30 ခန့် နောက်ကျသော အခမဲ့ catalog ဖြစ်သည်။
  Authentication မလုပ်ထားသော request သို့မဟုတ် မမှန်ကန်သော key ပါသည့် request က ဤ catalog ကို ရရှိသည်။
- **`live`** — မှန်ကန်သော supporter key ပါသည့် request များအတွက် ပေးပို့သည့် နောက်ဆုံးပေါ်
  catalog ဖြစ်သည်။

**မမှန်ကန်သော သို့မဟုတ် သက်တမ်းကုန်သွားသော supporter key သည် `community` သို့ အဆင့်လျှော့သွားမည်ဖြစ်ပြီး
error လုံးဝ မဖြစ်ပါ။** Sync လမ်းကြောင်းသည် signature/schema/version ဆိုင်ရာ ချို့ယွင်းမှုများ
(အားလုံး ပြန်လည်ပြင်ဆင်နိုင်ပြီး၊ cached state အတွက် fatal မဖြစ်ပါ) နှင့် အောင်မြင်သော `{ status:
"updated", version, tier }` ကိုသာ ခွဲခြားသည်။ Client က ကိုင်တွယ်ရန်လိုသော tier သီးသန့် error
လမ်းကြောင်း မရှိပါ။

### ပေးပို့ထားသော tier သည် signed body မှမဟုတ်ဘဲ response header မှ လာသည်

Signed feed **body** ၏ `tier` field သည် အမြဲတမ်း `"live"` ဖြစ်သည် — feed service သည်
**version တစ်ခုစီအတွက် signed artifact နှစ်ခု** ပေးပို့သည်- live တွင် လက်ရှိ campaign များ
ပါဝင်ပြီး community တွင် ၎င်းတို့ကို ချန်လှပ်ထားသည်။ Artifact တစ်ခုစီကို ၎င်း၏ byte များအတိုင်း
အတိအကျ sign လုပ်ထားသည်။ Body သည် entitlement ဆိုင်ရာ ဆုံးဖြတ်ချက်အဖြစ် မဆောင်ရွက်သေးပါ။
Request တစ်ခုအတွက် အမှန်တကယ် ရွေးချယ်ထားသော tier ကို request ၏ `Authorization` key မှ
server-side တွင် ဆုံးဖြတ်ပြီး **`x-omniroute-feed-tier` response header** ထဲတွင် ထည့်သွင်းပေးသည်။

`syncRadar()` (`src/lib/radar/sync.ts::parseServedTierHeader()`) သည် client က ယုံကြည်သင့်သော
tier ကို ဖြေရှင်းသတ်မှတ်သည့် တစ်ခုတည်းသော နေရာဖြစ်သည်-

1. `x-omniroute-feed-tier` ကို `RadarTierSchema` (Zod) ဖြင့် parse လုပ်သည် — header မရှိခြင်း
   သို့မဟုတ် value သည် `"community"` သို့မဟုတ် `"live"` အတိအကျ မဟုတ်ခြင်းကို **မရှိသကဲ့သို့**
   သတ်မှတ်သည် (မူလအတိုင်း cache/UI ထဲသို့ ဘယ်တော့မှ မယုံကြည်ဘဲ ထည့်သွင်းမည်မဟုတ်ပါ၊
   ၎င်းသည် ဤ header မရှိသေးမီက feed server အဟောင်းများကိုလည်း လွှမ်းခြုံသည်)။
2. အဆင့် 1 မှ မည်သည့်အရာမျှ မရရှိမှသာ signed body ၏ `tier` field (အမြဲတမ်း `"live"`) ကို
   fallback အဖြစ် အသုံးပြုသည်။
3. ဖြေရှင်းသတ်မှတ်ထားသော tier ကိုသာ cache လုပ်ပြီး `{ status: "updated",
version, tier }` အဖြစ် ပြန်ပေးသည် — dashboard က ပြသသည့် value သည် ဤ value ဖြစ်ပြီး၊
   မူရင်း body field မဟုတ်ပါ။

## ဖတ်ရှုချိန် overlay ပေါင်းစည်းမှု စည်းမျဉ်းများ

`applyFeed()` (`src/lib/radar/applyFeed.ts`) သည် `getRadarCatalog()` အတွင်း **ဖတ်ရှုချိန်** တွင်
cached feed ကို static baseline **ပေါ်သို့** ပေါင်းစည်းသည်။ Baseline array
(`FREE_MODEL_BUDGETS`) ကို ဘယ်တော့မှ ပြောင်းလဲခြင်းမပြုပါ — call တစ်ကြိမ်စီတိုင်းတွင်
`MergedEntry[]` အသစ်တစ်ခုကို တွက်ချက်သည်။

ဦးစားပေးအစဉ်အလိုက် စည်းမျဉ်း လေးခုမှာ-

1. **Feed သည် local override ကို ဘယ်တော့မှ အစားမထိုးပါ။** Field တစ်ခုချင်းစီအလိုက်-
   operator က entry တစ်ခုရှိ field ကို စိတ်ကြိုက်ပြင်ဆင်ထားပါက (`localOverrides` map ကို
   `provider:modelId` ဖြင့် key သတ်မှတ်ထားသည်) ထို field အတွက် feed ၏ value ကို ကျော်သွားပြီး
   operator ၏ value က အနိုင်ရသည်။
2. **`enabled: false` သည် မူလရင်းမြစ်အချက်အလက်နှင့်အတူ entry ကို ပိတ်သည်။** Entry တစ်ခုကို
   ပိတ်သည့် feed entry သည် ပေါင်းစည်းထားသော result တွင် `enabled: false` နှင့်
   `disabledBy: "radar"` ကို သတ်မှတ်သောကြောင့် entry တစ်ခု available မှ disabled သို့
   _အဘယ်ကြောင့်_ ပြောင်းသွားသည်ကို UI က ရှင်းပြနိုင်သည်။
3. **Feed ထဲတွင် မရှိသော user က ထည့်သွင်းထားသည့် entry သည် မပြောင်းလဲဘဲ ဆက်လက်တည်ရှိသည်။**
   Baseline တွင်သာ ရှိသော (သို့မဟုတ် local တွင် ထည့်ထားသော)၊ သက်ဆိုင်ရာ feed entry မရှိသည့်
   entry များကို မပြောင်းလဲဘဲ ဆက်လက်အသုံးပြုသည်။
4. **Tombstone လုပ်ထားသော entry ကို ဘယ်တော့မှ ပြန်လည်အသက်သွင်းမည်မဟုတ်ပါ။** Operator က
   entry တစ်ခုကို တိတိကျကျ ဖျက်ထားပါက (`tombstones` set) နောက်ပိုင်း version တစ်ခုတွင် feed က
   ထို `provider:modelId` ကို ပြန်လည်ထည့်သွင်းသော်လည်း ၎င်းကို ပြန်လည်မဖော်ပြပါ။

ပြင်ဆင်နိုင်သော field များနှင့် tombstone များကို
`radar_local_model_state` (migration `153_radar_local_model_state.sql`) တွင် သိမ်းဆည်းထားသည်။
Public DB adapter (`src/lib/db/radar.ts`) သည် ထို row များကို `applyFeed()` က အသုံးပြုသည့်
`localOverrides` map နှင့် `tombstones` set အဖြစ် ပြောင်းလဲသည်။ Production
`getRadarCatalog()` သည် flag၊ cache နှင့် schema gate များကို အောင်မြင်ပြီးနောက် ထို state ကို
load လုပ်သည်။ `displayName` နှင့် `enabled` ကိုသာ operator က ပြင်ဆင်နိုင်သည်။
Provider/model identity၊ feed provenance၊ quota၊ capabilities၊ ToS နှင့် setup data တို့ကို
ဤ surface မှတစ်ဆင့် ရေးသား၍မရပါ။

Dashboard တွင် local action လေးခု ပါရှိသည်-

- **ပြင်ဆင်ရန်** သည် local display name နှင့် enabled state ကို ပြောင်းလဲသည်။
- **Local ပြောင်းလဲမှုများကို ပြန်လည်သတ်မှတ်ရန်** သည် tombstone ကို မပြောင်းလဲဘဲ
  ပြင်ဆင်နိုင်သော field နှစ်ခုလုံးကို ရှင်းလင်းသည်။
- **ဖျောက်ရန်** သည် tombstone တစ်ခုကို ဖန်တီးသဖြင့် နောက်ပိုင်း feed update များက row ကို
  ပြန်လည်ဖန်တီး၍ မရနိုင်ပါ။
- **ပြန်လည်ရယူရန်** သည် tombstone ကို ဖယ်ရှားသည်၊ သီးခြားသိမ်းဆည်းထားသော override ရှိပါက
  ဆက်လက်သက်ရောက်နေမည်ဖြစ်သည်။

Feed `enabled: false` သည် ဘေးကင်းရေးဆိုင်ရာ ခြွင်းချက်အဖြစ် ဆက်ရှိသည်- ၎င်းသည် ဟောင်းနေသော
local `enabled: true` ထက် အနိုင်ရပြီး၊ ပေါင်းစည်းထားသော entry ကို disabled အဖြစ် ဆက်ထားကာ
`disabledBy: "radar"` ဟု မှတ်တမ်းတင်သည်။

Catalog publication များသည် `schemaVersion: 2` ကို အသုံးပြုသည်။ `contextWindow` နှင့်
`tools`၊ `vision`၊ `thinking` တစ်ခုချင်းစီသည် သီးခြား `number | null` / `boolean | null`
ဖြစ်သည်- `null` သည် မသိရသေးကြောင်း ဆိုလိုပြီး၊ `false` သည် capability မရှိကြောင်း
D16 အတည်ပြုထားသည့် တရားဝင် provider source က အတိအလင်း ဖော်ပြထားခြင်းကို ဆိုလိုသည်။
Internal OmniRoute registry/model-spec flag များကို feed fact များအဖြစ် တိုက်ရိုက်
မြှင့်တင်အသုံးမပြုပါ။ Client သည် v1 snapshot များကို ဆက်လက်လက်ခံသည်။ Builder အဟောင်းက
`false` ကို မရှိခြင်းဆိုင်ရာ placeholder အဖြစ် အသုံးပြုခဲ့သောကြောင့် v1 `false` ကို
မသိရသေးသောအခြေအနေအဖြစ် normalize လုပ်ပြီး v1 `true` ကိုမူ အချက်အလက်မှန်အဖြစ် ဆက်ထားသည်။
မသိသော schema version များသည် လုံခြုံမှုရှိစွာ ပိတ်သွားပြီး နောက်ဆုံးမှန်ကန်သော cache ကို
ဆက်လက်အသုံးပြုနိုင်သည်။ Null မဟုတ်သော context/capability ပါရှိသည့် v2 model တိုင်းတွင်
credential မလိုအပ်သော HTTPS `metadataEvidenceUrls[]` ပါဝင်ရမည်၊ မပါဝင်ပါက schema validation
မအောင်မြင်ဘဲ cache ကို အစားမထိုးပါ။ Catalog table သည် state သုံးမျိုးလုံးကို `✓`၊ `✕` နှင့်
`?` အဖြစ် ဖော်ပြသည်။

### လမ်းညွှန်ပေးသော combo များနှင့် MCP အသုံးပြုခွင့်

အတည်ပြုထားသော `familyId` value များသည် ဖတ်ရှုချိန် overlay ကို ကျော်လွန်ပြီး ဆက်လက်တည်ရှိကာ
pure `buildRadarComboSuggestions()` module (`src/lib/radar/comboSuggestions.ts`) ကို
မောင်းနှင်သည်။ မတူညီသော provider အနည်းဆုံး နှစ်ခုတွင် active connection များရှိပြီး
တိကျစွာ ရွေးချယ်ထားသော model ID ကို ဖော်ပြမှသာ family တစ်ခုကို အကြံပြုသည်။ Disabled model
များ၊ inactive provider များ၊ ပျောက်ဆုံးနေသော model ID များ၊ တစ်ခုတည်းသာရှိသော family များနှင့်
မရှင်းလင်းသော alias/prefix match များသည် လုံခြုံမှုရှိစွာ ပိတ်သွားသည်။ အကြံပြုချက်များသည်
ရှိပြီးသား `priority` strategy ကို အသုံးပြုပြီး ထပ်တလဲလဲရရှိသော လစဉ် budget အများဆုံးကို
ပထမဦးစွာ စီစဉ်သည်။ UI သည် ၎င်းတို့ကို `POST /api/combos` မှတစ်ဆင့်သာ ဖန်တီးသည်။

လမ်းညွှန်ပါ UI သည် `/dashboard/radar/combos` တွင် တည်ရှိသည်။ ၎င်းသည် စက်တွင်း
`GET /api/radar/catalog` နှင့် `GET /api/combos/builder/options` endpoint များကိုသာ ဖတ်ရှုသည်။ ၎င်းသည် Radar sync ကို မည်သည့်အခါမျှ အစပြုခြင်းမရှိသကဲ့သို့၊
ဝန်ဆောင်မှုပေးသူ၏ အထောက်အထားများကို ဖတ်ရှုခြင်း သို့မဟုတ် combo database သို့ တိုက်ရိုက်ရေးသားခြင်းလည်း မပြုလုပ်ပါ။

MCP client များသည် အလားတူ စက်တွင်း projection ကို `omniroute_radar_catalog` (`read:radar`) ဖြင့် ဖတ်ရှုနိုင်သည်။ ရွေးချယ်အသုံးပြုနိုင်သော
`provider`, `familyId` နှင့် `enabledOnly` filter များကို စက်တွင်း
`GET /api/radar/catalog` ဖတ်ရှုမှုတစ်ကြိမ် ပြုလုပ်ပြီးနောက် စစ်ဆေးအသုံးပြုသည်။ ၎င်း၏ ကန့်သတ်ထားသော output တွင် catalog metadata အပြင် provider/model၊
ပြသမည့်အမည်၊ `familyId`၊ quota၊ စွမ်းဆောင်ရည်များ၊ ဖွင့်ထားမှုအခြေအနေ၊ origin နှင့် `disabledBy` တို့ ပါဝင်သည်။ setup URL များ၊
အဆင့်များ၊ ချိတ်ဆက်မှုများ၊ အီးမေးလ်လိပ်စာများ၊ key များနှင့် referral data များကို မည်သည့်အခါမျှ ပြန်မပေးပါ။ ဤ tool သည်
ဖတ်ရှုရန်သက်သက်ဖြစ်ပြီး `/api/radar/sync` ကို မည်သည့်အခါမျှ ခေါ်ယူအသုံးပြုခြင်းမရှိပါ။

| `/api/radar/status`            | GET    | လျှို့ဝှက်ချက်များ မပါဝင်ဘဲ catalog၊ referrals၊ offers နှင့် Intel တို့အတွက် read-only local settings/cache status ကို ပြန်ပေးသည်။                 |
| `/api/radar/sync-all`          | POST   | Server-side sync module လေးခုစလုံးကို လုပ်ဆောင်ပြီး feed တစ်ခုစီအတွက် သီးခြား status ကို ပြန်ပေးသည်။                                               |
| `/api/radar/local-model-state` | GET    | Edit/restore control များအတွက် သိမ်းဆည်းထားသော override နှင့် tombstone များကို စာရင်းပြုစုဖော်ပြသည်။                                              |
| `/api/radar/local-model-state` | PATCH  | အတည်ပြုထားသော `displayName`/`enabled` override field များကို သတ်မှတ်ခြင်း သို့မဟုတ် ရှင်းလင်းခြင်း ပြုလုပ်သည်။                                     |
| `/api/radar/local-model-state` | PUT    | `{ provider, modelId, tombstoned }` ဖြင့် tombstone တစ်ခုကို ဖန်တီးခြင်း သို့မဟုတ် ဖယ်ရှားခြင်း ပြုလုပ်သည်။                                        |
| `/api/radar/local-model-state` | DELETE | ရှိပြီးသား tombstone ကို ဆက်လက်ထိန်းသိမ်းထားကာ ပြင်ဆင်နိုင်သော override field များကို ရှင်းလင်းသည်။                                                |

**တင်းကျပ်သော စည်းမျဉ်း- ဤ route များသည် feed service ကို မည်သည့်အခါမျှ proxy မလုပ်ပါ။** Browser သည်
local OmniRoute server နှင့်သာ ဆက်သွယ်သည်။ Radar service ကို အသုံးပြုသော module လေးခုမှာ
`src/lib/radar/sync.ts` (catalog)၊ `src/lib/radar/referralsSync.ts` (referrals)၊
`src/lib/radar/offersSync.ts` (offers) နှင့် `src/lib/radar/intelSync.ts` (Intel) တို့ဖြစ်ပြီး အားလုံးသည်
client-side တွင် မည်သည့်အခါမျှ မလုပ်ဆောင်ဘဲ server-side တွင်သာ လုပ်ဆောင်သည်။ ဤသို့ဖြင့်
feed URL နှင့် supporter key တစ်ခုခုကို client-facing network traffic ထဲ လုံးဝမပါဝင်စေရန် ထိန်းသိမ်းထားသည်။

`RADAR_ENABLED` ကို ပိတ်ထားသည့်အခါ Radar endpoint အားလုံးသည် `404` ကို ပြန်ပေးသည် (အထက်ရှိ
[Flag](#flag-radar_enabled-default-off) ကို ကြည့်ပါ)။ ထို့ပြင် repo တစ်ခုလုံးအတွက် သတ်မှတ်ထားသော error-sanitization စည်းမျဉ်း
(`docs/security/ERROR_SANITIZATION.md`) အရ route error response များကို
`buildErrorBody()`/`sanitizeErrorMessage()` မှတစ်ဆင့် ကိုင်တွယ်သည်။

### Authentication

Radar endpoint အားလုံးသည် `isAuthenticated()`
(`src/shared/utils/apiAuth.ts`) မှတစ်ဆင့် authentication လိုအပ်သည် — dashboard session cookie သို့မဟုတ် management scope ပါဝင်သော
API key ကို အသုံးပြုပြီး `/api/settings/*` ၏ ကျန်အစိတ်အပိုင်းများကို ကာကွယ်ပေးသည့် gate နှင့် အတူတူဖြစ်သည်။ Flag ပိတ်ထားမှုအတွက်
`404` စစ်ဆေးခြင်းသည် auth စစ်ဆေးခြင်း **မတိုင်မီ** အမြဲလုပ်ဆောင်သည်။ ထို့ကြောင့် `RADAR_ENABLED`
ပိတ်ထားသည့် installation သည် byte-identical အတိုင်း ဆက်ရှိနေသည် (ဤ surface မရှိကြောင်း သိရန်အတွက်ပင် auth prompt ပြမည်မဟုတ်ပါ)။
Flag ကို ဖွင့်လိုက်သည်နှင့် authentication မလုပ်ထားသော request သည် DB ဖတ်ခြင်း သို့မဟုတ်
ရေးခြင်းတစ်စုံတစ်ရာ မလုပ်မီ `401` ကို ရရှိမည်ဖြစ်သည်။ Auth state မည်သို့ရှိသည်ဖြစ်စေ `GET /api/radar/settings` သည် raw supporter key ကို
မည်သည့်အခါမျှ ပြန်မပေးပါ — masked form နှင့် `hasSupporterKey` boolean ကိုသာ ပြန်ပေးသည်။

## ပံ့ပိုးသူ ကမ်းလှမ်းချက်များ

ကမ်းလှမ်းချက်များသည် ၎င်းတို့၏ ကိုယ်ပိုင်လက်မှတ်ရေးထိုးထားသော artifact ဖြစ်သည့် `GET /v1/offers/latest` ကို အသုံးပြုပြီး catalog သို့မဟုတ်
referrals cache ကို မည်သည့်အခါမျှ မျှဝေမသုံးပါ။ Server endpoint သည် တရားဝင်၍ လက်ရှိအသုံးပြုနိုင်သော ပံ့ပိုးသူ Bearer key တစ်ခု လိုအပ်ပြီး
community fallback မရှိပါ။ ထို့ကြောင့် feature flag ကို ပိတ်ထားလျှင်၊ operator က ပါဝင်အသုံးပြုရန် သဘောမတူထားလျှင် သို့မဟုတ် ပံ့ပိုးသူ key ကို မသတ်မှတ်ထားလျှင်
`syncRadarOffers()` သည် network သို့ မဆက်သွယ်မီ ရပ်တန့်ပါသည်။

GET အောင်မြင်ပြီးနောက် client သည် response bytes အတိအကျပေါ်ရှိ Ed25519 signature ကို အတည်ပြုစစ်ဆေးပြီး၊
`RadarOffersFeedSchema` ကို validate လုပ်ကာ၊ လက်မှတ်ရေးထိုးထားသော body နှင့်
`x-omniroute-feed-tier` header နှစ်ခုစလုံးတွင် `live` ဟု ဖော်ပြထားရန် လိုအပ်စေပြီး၊ အစက်ဖြင့် ပိုင်းခြားထားသော version သည် တိတိကျကျ ပိုသစ်ကြောင်း သေချာစေကာ ထို့နောက်မှသာ
`radar_offers_cache` ကို atomic နည်းဖြင့် အစားထိုးပါသည် (migration `144_radar_offers_cache.sql`)။ အခြား feed များတွင် အသုံးပြုသည့် တူညီသော 10 MB
header-plus-stream ကန့်သတ်ချက်ကိုလည်း သက်ရောက်စေပါသည်။ Signature၊ schema၊ tier၊ replay၊ size၊ HTTP
နှင့် network ချို့ယွင်းမှုအားလုံးတွင် နောက်ဆုံးအတည်ပြုထားသော cache ကို မပြောင်းလဲဘဲ ထိန်းသိမ်းထားပါသည်။

ပိတ်ထားသော offer ပုံစံသည် နှိုင်းယှဉ်နိုင်သည့် အကျိုးခံစားခွင့် အမျိုးအစားသုံးမျိုးကို ပံ့ပိုးသည်—basis points ဖြင့် ရာခိုင်နှုန်း၊
ငွေကြေး၏ အသေးဆုံးယူနစ်ဖြင့် credit သို့မဟုတ် စမ်းသပ်အသုံးပြုရက်များ။ Partner offer တစ်ခုတွင် အမျိုးအစားတူ public baseline တစ်ခု ပါဝင်ရမည်ဖြစ်ပြီး
၎င်း၏ အကျိုးခံစားခွင့်သည် ထို baseline ထက် တိတိကျကျ ပိုများရမည်။ Official offer များတွင် partner baseline မရှိပါ။ URL များသည်
အထောက်အထားများမပါသော HTTPS ဖြစ်ရမည်။ `getRadarOffers()` သည် cache လုပ်ထားသော payload ကို ကြိုတင်ကာကွယ်ရေးအဖြစ် ပြန်လည် validate လုပ်ပြီး
local read ပြုလုပ်တိုင်း သက်တမ်းကုန်ဆုံးနေသော entry များကို စစ်ထုတ်ပါသည်။ `/dashboard/radar/offers` သည် render မလုပ်မီ
သက်တမ်းကုန်ဆုံးမှုကို ထပ်မံစစ်ထုတ်ပြီး၊ Portuguese စာသား ရရှိပါက အသုံးပြုကာ မရရှိပါက English ကို fallback အဖြစ် အသုံးပြုပြီး partner offer များကို အတိအလင်း label တပ်ပါသည်။

Browser သည် local route များကိုသာ ခေါ်ဆိုပါသည်။ ၎င်းသည် ဖုံးကွယ်ထားသော settings snapshot ကို ဖတ်ပြီး၊ server-side တွင် refresh လုပ်ရန်
`POST /api/radar/offers/sync` ကို တောင်းဆိုကာ၊ ထို့နောက် `GET /api/radar/offers` ကို ဖတ်ပါသည်။ Key မရှိပါက
feed request ပြုလုပ်ရန် မကြိုးစားဘဲ ရှိပြီးသား contributor/support link များကို ပြသပါသည်။ ပြင်ပ
offer link များကို `noopener noreferrer` ဖြင့် tab အသစ်တွင် ဖွင့်ပါသည်။ ဤ release တွင် `radar_offers` MCP tool ကို မဖော်ထုတ်ထားပါ။

## Radar Intel၊ ပံ့ပိုးသူ badge နှင့် CLI

Intel သည် `GET /v1/intel/latest` တွင် ရရှိနိုင်သော လက်မှတ်ရေးထိုးထားသည့် artifact တစ်ခု ဖြစ်ပါသည်။ ပိတ်ထားသော `RadarIntelFeedSchema` သည်
အတည်ပြုထားသော နှိုင်းယှဉ်မှုများမှ private curator က ရယူတွက်ချက်ထားသည့် Radar ပိုင် ELO ranking များနှင့် လက်မှတ်ရေးထိုးထားသော catalog snapshot များမှ ရယူထားသည့်
အချက်အလက်အခြေပြု catalog အသက်/count ကွာခြားချက်များကိုသာ လက်ခံပါသည်။ နည်းစနစ်ကို ကနဦး rating 1000 နှင့် K=32 အဖြစ် ပုံသေသတ်မှတ်ထားပါသည်။
နှိုင်းယှဉ်မှုတစ်ခုမျှ အတည်မပြုရသေးသည့်အခါ ranking အလွတ်သည် တရားဝင်ပြီး client က ranking တစ်ခုကို မည်သည့်အခါမျှ အလိုအလျောက် ဖန်တီးမပေးပါ။

`syncRadarIntel()` သည် offer များကဲ့သို့ တူညီသော server-side Bearer၊ 30-second timeout၊ 10 MiB streamed cap၊
exact-byte Ed25519 verification၊ strict schema၊ body/header နှစ်ခုစလုံးတွင် `live` ဖြစ်ရန် သတ်မှတ်ချက်၊ version floor နှင့်
နောက်ဆုံးကောင်းမွန်သော cache ကို ထိန်းသိမ်းခြင်းတို့ကို အသုံးပြုပါသည်။ အတည်ပြုပြီးသော live snapshot ကို သိမ်းဆည်းပြီးနောက် client သည်
`radar:<sha256(supporter key)>` ကို ရယူတွက်ချက်ကာ၊ ထို one-way identity ကိုသာ သိမ်းဆည်းပြီး သီးသန့်
`radar_supporter` recognition event ကို ထုတ်လွှတ်ပါသည်။ ၎င်း၏ `radar-supporter` badge သည် idempotent ဖြစ်ပြီး XP သုညသာ ပေးပါသည်။
၎င်းသည် leaderboard များကို မည်သည့်အခါမျှ update မလုပ်သကဲ့သို့ `token_share` ကိုလည်း ပြန်လည်အသုံးမပြုပါ။ `/dashboard/radar/intel` သည် အတည်ပြုထားသော
local cache metadata မှသာ badge ကို render လုပ်ပါသည်။

CLI သည် `omniroute radar status` နှင့် `omniroute radar sync` ကို ဖော်ထုတ်ပေးပါသည်။ နှစ်ခုစလုံးသည်
local OmniRoute API နှင့်သာ ဆက်သွယ်ပါသည်။ `status` သည် read-only `GET /api/radar/status` ကို ပြုလုပ်ပြီး၊ `sync` သည်
`POST /api/radar/sync-all` တစ်ကြိမ် ပေးပို့ကာ feed တစ်ခုစီအတွက် ရလဒ်ကို print ထုတ်ပါသည်။ Command နှစ်ခုလုံးသည်
ပံ့ပိုးသူ key ကို ဖတ်ခြင်း၊ လက်ခံခြင်း သို့မဟုတ် print ထုတ်ခြင်း မပြုသကဲ့သို့ Radar service ကိုလည်း တိုက်ရိုက် မဆက်သွယ်ပါ။

## ရည်ညွှန်းလင့်ခ်များ (အခမဲ့ခရက်ဒစ်များ)

ရည်ညွှန်းလင့်ခ်များကို ကတ်တလောက် feed နှင့် သီးခြားဖြစ်သော **သီးခြားရပ်တည်ပြီး အမြဲနောက်ဆုံးအခြေအနေရှိသည့်** feed —
`GET /v1/referrals/latest` — မှ ပေးပို့သည်။ ဤသို့ပြုလုပ်ထားခြင်းမှာ ရည်ရွယ်ချက်ရှိပါသည်။ community tier ရှိ
ကတ်တလောက် feed သည် ရက် 30 အထိ ဟောင်းနေနိုင်သည့် snapshot တစ်ခုဖြစ်သောကြောင့်၊
၎င်းမှ ထုတ်ယူထားသော ရည်ညွှန်းလင့်ခ်သည် ဆာဗာ၏ အမှန်တကယ်လင့်ခ်စာရင်းထက် ထိုပမာဏအတိုင်း
နောက်ကျလေ့ရှိခဲ့သည် (အသစ်ထည့်ထားသော ရည်ညွှန်းလင့်ခ်သည် အခမဲ့/community အသုံးပြုသူထံ ရောက်ရှိရန်
တစ်လအထိ ကြာနိုင်ခဲ့သည်)။ ရည်ညွှန်းချက် feed သည် ၎င်းကိုယ်တိုင် ပိုမိုတိုတောင်းသော အကြိမ်နှုန်းဖြင့်
စင့်ခ်လုပ်ခြင်းအားဖြင့် ထိုနှောင့်နှေးမှုကို ဖယ်ရှားပေးသည်။

```ts
// GET /v1/referrals/latest တုံ့ပြန်ချက် body (Ed25519 ဖြင့် လက်မှတ်ထိုးထားပြီး
// ကတ်တလောက် feed နှင့် တူညီသော pinned key ကို အသုံးပြုသည်):
{
  feed: "omniroute-radar-referrals",
  schemaVersion: 1,
  generatedAt: string,           // ISO — တိကျသတ်မှတ်နိုင်သည်- ရည်ညွှန်းလင့်ခ်အားလုံးရှိ max(updatedAt)
                                  // ဖြစ်သောကြောင့် တူညီသည့် တောင်းဆိုချက်နှစ်ခုသည် လုံးဝတူညီသော
                                  // လက်မှတ်ထိုးထားသည့် bytes/signature ကို ထုတ်ပေးသည်
  referrals: {
    fixed: RadarReferral[],      // no-auth/community အပါအဝင် tier အားလုံးတွင် ပါရှိသည်
    campaigns: RadarReferral[],  // တရားဝင်ပြီး အသုံးပြုဆဲ (supporter) Bearer key အတွက်သာ ဖြည့်ပေးသည်၊
                                  // no-auth/သက်တမ်းကုန်-key တောင်းဆိုချက်များသည် [] ကို ရရှိသည်
  },
}
// RadarReferral = { provider, url, kind: "fixo" | "campanha", validUntil,
//                    requiredAction, isDefault }
```

ကတ်တလောက် feed နှင့်မတူဘဲ ဤ body တွင် `tier` field လုံးဝမပါရှိပါ — တောင်းဆိုချက်တစ်ခုချင်းစီအတွက်
ဘာများထည့်သွင်းရမည်ကို ဆာဗာက `Authorization` key အပေါ် အခြေခံ၍ ဆုံးဖြတ်သောကြောင့်၊
`x-omniroute-feed-tier` တုံ့ပြန်ချက် header သည် ပေးပို့ထားသော tier အတွက် တစ်ခုတည်းသော ရင်းမြစ်ဖြစ်သည်
(`referralsSync.ts::syncRadarReferrals`)။ header မရှိခြင်း သို့မဟုတ် အသိအမှတ်မပြုနိုင်ခြင်းဖြစ်ပါက
အခွင့်အရေးအနည်းဆုံးဟု ယူဆသည့် `"community"` သို့ လျှော့ချသတ်မှတ်သည်။ `RadarReferralsFeedSchema`
(`src/lib/radar/referralsFeedSchema.ts`) သည် body တစ်ခုလုံးကို စစ်ဆေးအတည်ပြုပြီး၊ feed နှစ်ခုလုံးက
ရည်ညွှန်းချက်တစ်ခုချင်းစီကို တူညီစွာ စစ်ဆေးအတည်ပြုနိုင်ရန် `feedSchema.ts` မှ export လုပ်ထားသော
ရည်ညွှန်းချက်တစ်ခုချင်းဆိုင်ရာ `RadarReferralSchema` ကို ပြန်လည်အသုံးပြုသည်။ `RadarReferral.url`
တိုင်းသည် `https://` ဖြစ်ရမည် — `http://` url သည် schema စစ်ဆေးအတည်ပြုမှု မအောင်မြင်ပါ။

`RadarFeedSchema` (`feedSchema.ts`) ပေါ်ရှိ ကတ်တလောက်ထဲ ထည့်သွင်းထားခဲ့သော အဟောင်း
`referrals` field ကို cache လုပ်ထားပြီးသား ကတ်တလောက် feed များနှင့် နောက်ပြန်လိုက်ဖက်မှုရှိစေရန်
ဆက်လက်ထားရှိထားသော်လည်း `getRadarReferrals()` က ၎င်းကို မဖတ်တော့ပါ — အောက်ပါ
[Accessor](#accessor) ကို ကြည့်ပါ။

### စင့်ခ်လုပ်ခြင်း

`syncRadarReferrals()` (`src/lib/radar/referralsSync.ts`) သည် ရည်ညွှန်းချက်များအတွက် ကွန်ရက်ကို
ထိတွေ့သည့် တစ်ခုတည်းသော module ဖြစ်ပြီး `syncRadar()` ၏ contract ကို အတိအကျ ပုံတူလိုက်နာသည်-
flag ပိတ်ထားလျှင် → `disabled`; opt-in သည် false ဖြစ်လျှင် → `opt_out`;
`${RADAR_FEED_URL}/v1/referrals/latest` ကို ဒေါင်းလုဒ်လုပ်သည် (ကတ်တလောက်နှင့် တူညီသော
`RADAR_FEED_URL`/`RADAR_FEED_PUBKEY` fork override များ)၊ တုံ့ပြန်ချက် bytes အတိအကျပေါ်ရှိ
Ed25519 signature ကို (`verifyFeedBytes`) စစ်ဆေးသည်၊ `RadarReferralsFeedSchema` နှင့်
စစ်ဆေးအတည်ပြုပြီး `radar_referrals_cache` table (`142_radar_referrals_cache.sql` migration)
ထဲသို့ cache လုပ်သည် — ဤ table သည် ကတ်တလောက်၏ `radar_feed_cache` နှင့် လုံးဝသီးခြားဖြစ်သည်။
10 MB တုံ့ပြန်ချက်ကန့်သတ်ချက်နှင့် `generatedAt` အနိမ့်ဆုံးကန့်သတ်ချက်တို့သည် cache လုပ်ထားသည့်
feed ထက် ပိုဟောင်းသော ဝင်လာသည့် feed ကို ငြင်းပယ်ပြီး၊ အဟောင်းဖြစ်သော လက်မှတ်ထိုးထားသည့်
artifact ကို ပြန်လည်အသုံးချခြင်းမှ ကာကွယ်ပေးသည်။ timestamp တူညီခြင်းကို လက်ခံသည်- ဆာဗာသည်
community နှင့် live ရည်ညွှန်းချက် variant များကို တူညီသော တိကျသတ်မှတ်နိုင်သည့် `generatedAt`
အား ရည်ရွယ်ချက်ရှိရှိ ပေးထားသောကြောင့်၊ အခြေခံလင့်ခ်အစုအဝေး မပြောင်းလဲဘဲ supporter-key
ပြောင်းလဲပြီးနောက် လက်မှတ်ထိုးထားသော payload နှင့် ပေးပို့သည့် tier တို့ ပြောင်းလဲနိုင်သည်။
မည်သည့်အခါမျှ exception မပစ်ပါ — status object တစ်ခုကို အမြဲပြန်ပေးသည်။ error များ၏
`reason` တွင် stack trace လုံးဝမပါရှိပါ။

trigger နှစ်ခုက ရည်ညွှန်းချက် cache ကို နွေးနေစေပြီး၊ နှစ်ခုလုံးသည် ကတ်တလောက်၏ ကိုယ်ပိုင်
24h အကြိမ်နှုန်းနှင့် သီးခြားလွတ်လပ်သည်-

- **ဖတ်သည့်အချိန်တွင် စင့်ခ်လုပ်ခြင်း** — cache မရှိသည့်အခါ သို့မဟုတ်
  `REFERRALS_STALE_MS` (1h, `shouldSyncReferralsOnRead()`) ထက် ပိုဟောင်းသည့်အခါတိုင်း
  `GET /api/radar/referrals` ကိုယ်တိုင်က တုံ့ပြန်ချက်မပေးမီ `syncRadarReferrals()` ကို
  inline ခေါ်သည်။ ထို့ကြောင့် နောက်ခံ timer တစ်ခုခုကို စောင့်စရာမလိုဘဲ နောက်တစ်ကြိမ်
  dashboard ဖွင့်သည့်အခါ fixed လင့်ခ်များသည် "အမြဲနောက်ဆုံးအခြေအနေ" ဖြစ်နေသည်။
- **Scheduler ဘေးတွဲစင့်ခ်** — `radarSchedulerTick()` (`scheduler.ts`) သည် ကတ်တလောက်အတွက်
  အသုံးပြုသည့် တစ်နာရီခြား tick တစ်ခုတည်းပေါ်တွင် ရည်ညွှန်းချက်များ ဟောင်းနွမ်းမှုကို သီးခြားစီ
  အကဲဖြတ်ပြီး လုပ်ဆောင်ရန်အချိန်ကျပါက `syncRadarReferrals()` ကို ခေါ်သည်။ ၎င်းသည် ထို tick တွင်
  ကတ်တလောက်ကိုယ်တိုင် လုပ်ဆောင်ရန်အချိန်ကျသည်ဖြစ်စေ မကျသည်ဖြစ်စေ လုပ်ဆောင်ပြီး
  `RadarTickResult` ၏ ပုံသဏ္ဌာန်ကို မည်သည့်အခါမျှ မထိခိုက်ပါ (အကောင်းဆုံးကြိုးစားသည့်
  ဘေးထွက်သက်ရောက်မှုသာဖြစ်ပြီး error ဖြစ်ပါက မျိုသိပ်ထားသည်)။

### Accessor

`src/lib/radar/index.ts` သည် ဖတ်ရှုရန်သီးသန့် accessor နှစ်ခုကို export လုပ်ထားပြီး၊ နှစ်ခုလုံးသည်
မည်သည့်အခါမျှ exception မပစ်ပါ (`getRadarCatalog()` နှင့် တူညီသော ကာကွယ်ရေး contract —
flag ပိတ်ထားခြင်း၊ cache မရှိခြင်း သို့မဟုတ် cache လုပ်ထားသော payload ပျက်စီးနေခြင်းအားလုံးသည်
error အစား အလွတ်ပုံသဏ္ဌာန်ကို ပြန်ပေးသည်)-

- `getRadarReferrals()` → `{ fixed: RadarReferral[], campaigns: RadarReferral[] }`,
  `radar_referrals_cache` မှ (`getRadarReferralsCache()` မှတစ်ဆင့်) ဖတ်ပြီး
  `RadarReferralsFeedSchema` ဖြင့် စစ်ဆေးအတည်ပြုသည် — ကတ်တလောက် cache မှ **မဟုတ်ပါ**။
- `getDefaultReferralFor(provider)` → ထို provider အတွက် `isDefault: true` ဖြစ်သော `fixed`
  ရည်ညွှန်းချက် သို့မဟုတ် `null` ကို ပြန်ပေးသည်။ `fixed` ကိုသာ ကြည့်သည် — campaign တစ်ခုကို
  provider ၏ "ပုံသေ" လင့်ခ်အဖြစ် မည်သည့်အခါမျှ အသုံးမပြုပါ။

အမှန်တကယ် "provider တစ်ခုအတွက် မည်သည့်ရည်ညွှန်းချက်က ပုံသေဖြစ်သလဲ" ဟူသော စည်းမျဉ်းသည်
`findDefaultReferral()` (`src/lib/radar/referrals.ts`) ထဲတွင် ရှိပြီး၊ ၎င်းသည် **DB import မရှိသော**
သေးငယ်သည့် pure function တစ်ခုဖြစ်သည် — `"use client"` component တစ်ခုထဲသို့ စိတ်ချစွာ
import လုပ်နိုင်သည်။ `getRadarReferrals`/`getDefaultReferralFor` (`index.ts` ထဲရှိ) တို့သည်
`@/lib/db/radar` ကို ထည့်သွင်းဆွဲယူသောကြောင့် server-only အဖြစ် ဆက်ရှိနေသည်။ browser bundle ထဲသို့
`better-sqlite3` မပါဝင်စေရန် providers dashboard သည် `index.ts` အစား `referrals.ts` ကို
တိုက်ရိုက် import လုပ်သည် (အောက်တွင် ကြည့်ပါ)။

### `GET /api/radar/referrals`

အခြား Radar route အားလုံးနှင့် အတိအကျတူညီသော gate အစီအစဉ်ကို လိုက်နာသည်- `RADAR_ENABLED` ပိတ်ထားပါက →
`404` (ဦးစွာ စစ်ဆေးပြီး byte အဆင့်အထိ တူညီသော အပြုအမူကို ထိန်းသိမ်းထားသည်); authentication မပြုလုပ်ထားပါက → `401`; အခြားအခြေအနေများတွင်
ဒေတာဟောင်းနေပါက sync-on-read ကို (အထက်တွင်ကြည့်ပါ) စတင်ပြီးနောက်
`{ fixed, campaigns, tier }` နှင့်အတူ `200` ကို ပြန်ပေးသည် — `tier` သည် (ယခုလေးတင် refresh လုပ်ထားနိုင်သည့်)
cache row မှ တိုက်ရိုက်ရရှိပြီး အချက်အလက်ပေးရန်သက်သက်သာဖြစ်သည် (အောက်ပါ UI ၏ soft upsell စာသားကို ထိန်းချုပ်သည်)။ Feed server သို့ မည်သည့်အခါမျှ
တိုက်ရိုက် proxy မလုပ်ပါ — route ၏ ကိုယ်ပိုင် source တွင် `fetch(` call မပါဝင်ပါ;
network ချိတ်ဆက်မှုသည် `syncRadarReferrals()` အတွင်း၌သာ အမြဲဖြစ်ပေါ်ပြီး
`/api/radar/catalog` ကဲ့သို့ local-cache-only မူဝါဒကိုပင် လိုက်နာသည်။

**Catalog** (လက်ရှိ table) နှင့် **Free credits** ကို ပြသသည်-

- Fixed link များကို provider အလိုက် အုပ်စုဖွဲ့ထားပြီး တစ်ခုစီတွင် `requiredAction` (ရှိပါက)
  နှင့် referral URL သို့သွားသည့် `target="_blank" rel="noopener noreferrer"` button တစ်ခုကို ပြသသည်။
- Campaign များတွင်လည်း အလားတူအချက်များအပြင် `validUntil` ရှိပါက ၎င်းကိုပါ ပြသသည်။
- `campaigns` သည် ဗလာဖြစ်ပြီး ပြန်ပေးထားသော tier သည် `community` ဖြစ်သည့်အခါ UI သည်
  အတိုချုံး upsell မှတ်ချက် ("အချိန်ကန့်သတ်ထားသော campaign များသည် supporter အပိုအကျိုးခံစားခွင့်ဖြစ်သည်") ကို ပြသသည် — ၎င်းသည်
  tier အားလုံးအတွက် အပြည့်အစုံ ဆက်လက်ပြသထားသည့် fixed links စာရင်းကို **မည်သည့်အခါမျှ**
  ဖျောက်ထားခြင်း သို့မဟုတ် ပိတ်ပင်ခြင်း မပြုပါ။ Upsell သည် သိမ်မွေ့သော အသိပေးစာသားသာဖြစ်ပြီး မည်သည့်အခါမျှ အတားအဆီးတစ်ခု မဟုတ်ပါ။

### Provider name ပေါ်ရှိ referral link (providers dashboard)

`ProviderPageHeader` (`src/app/(dashboard)/dashboard/providers/[id]/components/`) သည်
`providerInfo.website` ရှိပါက provider name ကို ယင်း website နှင့် ချိတ်ဆက်ထားပြီးဖြစ်သည့်အပြင်
ဝင်ငွေရှာဖွေသည့် link အတွက် ရှေ့နမူနာတစ်ခုလည်း ရှိသည်- Kimi (Moonshot AI) partner-link မှတ်ချက်
(`providers.kimiPartnerLinkNote` i18n key)။ D28 သည် key အသစ်တစ်ခု မိတ်ဆက်မည့်အစား Radar default referral များအတွက်
အဆိုပါ သိမ်မွေ့သော မှတ်ချက်ပုံစံကို အတိအကျပင် ပြန်လည်အသုံးပြုသည်။

ရည်ရွယ်ချက်ရှိရှိ loose coupling လုပ်ထားသည်-

- `resolveProviderHeaderLink()` (`src/app/(dashboard)/dashboard/providers/providerPageUtils.ts`)
  သည် `@/lib/radar` သို့မဟုတ် `@/lib/db/*` ပေါ်တွင် dependency မရှိသော **pure** function
  — `(staticWebsite, referralUrl) => { website, isReferralLink }` — ဖြစ်သည်။ `providerPageUtils.ts`
  တစ်ခုလုံးတွင်လည်း အဆိုပါ import များ မပါဝင်ပါ (`tests/unit/provider-header-referral-link.test.ts` ဖြင့်
  အတည်ပြုထားသည်)။
- `ProviderDetailPageClient.tsx` (`"use client"` component တစ်ခု) သည် Radar data ကို fetch လုပ်ခွင့်ရှိသည့်
  တစ်ခုတည်းသောနေရာဖြစ်သည် — Radar dashboard page ကိုယ်တိုင်အသုံးပြုသည့် local-route pattern အတိုင်း
  `fetch("/api/radar/referrals")` မှတစ်ဆင့် fetch လုပ်ပြီး DB နှင့် မချိတ်ဆက်ထားသော
  `src/lib/radar/referrals.ts` မှ `findDefaultReferral()` ကို အသုံးပြု၍ default referral ကို
  client-side တွင် တွက်ချက်သည်။
- `RADAR_ENABLED` ပိတ်ထားသည့်အခါ fetch သည် 404 ပြန်လာပြီး `referralUrl` သည် `null` အဖြစ် ဆက်ရှိနေကာ
  `resolveProviderHeaderLink()` သည် static catalog `website` ကို မပြောင်းလဲဘဲ ပြန်ပေးသည် — provider page သည်
  ဤ feature မရှိမီကအတိုင်း byte အဆင့်အထိ တူညီနေသည်။ Cache မရှိသေးသည့်အခါ သို့မဟုတ်
  ထို provider အတွက် default referral မရှိသည့်အခါလည်း အလားတူရလဒ်ပင် ဖြစ်သည်။
- Default referral သက်ရောက်သည့်အခါ `ProviderPageHeader` သည် `isReferralLink` ကို လက်ခံရရှိပြီး
  Kimi partner link နှင့် တူညီသော သိမ်မွေ့သည့် မှတ်ချက်/tooltip ကို (`providers.kimiPartnerLinkNote` key အား ပြန်လည်အသုံးပြု၍)
  ပြသသည် — အသစ်ဖြစ်ပြီး သီးခြားခွဲထွက်နေသော visual treatment ကို မည်သည့်အခါမျှ မသုံးပါ။

## Feed ကို ကိုယ်တိုင် host ပြုလုပ်နည်း

Catalog ကို အပြည့်အဝ ထိန်းချုပ်လိုသော fork သို့မဟုတ် self-hoster သည် client code ကို ပြင်ဆင်ရန်မလိုဘဲ မိမိတို့၏ ကိုယ်ပိုင် feed service ကို အသုံးပြုနိုင်သည်-

1. `RadarFeedSchema` (`src/lib/radar/feedSchema.ts`) နှင့် ကိုက်ညီသော JSON body ကို ပြန်ပေးသည့် `GET /v1/catalog/latest` endpoint တစ်ခုကို ဝန်ဆောင်မှုပေးပါ — ထိပ်ဆုံးအဆင့်ရှိ `feed:
"omniroute-radar"`, `schemaVersion: 2`, `version`, `tier`, `providers`, `models`,
   `quirks` နှင့် `totals` တို့ ပါဝင်ရမည်။ `x-omniroute-radar-schema: 2` ကို လိုက်နာပါ။ ကူးပြောင်းမှုနှင့် ကိုက်ညီသော server တစ်ခုသည် ၎င်းမပါဝင်သည့် request များအတွက် သီးခြား လက်မှတ်ထိုးထားသော v1 artifact ကို မူလတန်ဖိုးအဖြစ် သတ်မှတ်သင့်သည်။
2. တိကျသည့် response byte များကို Ed25519 key pair ဖြင့် လက်မှတ်ထိုးပြီး base64 signature ကို `x-omniroute-feed-signature` response header တွင် ပြန်ပေးပါ။
3. `RADAR_FEED_URL` ကို base URL အသစ်အဖြစ်၊ `RADAR_FEED_PUBKEY` ကို သက်ဆိုင်ရာ public key (base64-DER SPKI သို့မဟုတ် PEM) အဖြစ် သတ်မှတ်ပါ — [env var ကိုးကားချက်](../reference/ENVIRONMENT.md#27-radar-feed-self-hosting) ကို ကြည့်ပါ။
4. `RADAR_ENABLED` ကို ဖွင့်ပြီး `POST /api/radar/settings`
   (`{ optIn: true }`) မှတစ်ဆင့် ပါဝင်ရန် ရွေးချယ်ပါ။

အခြား code ပြောင်းလဲမှုများ မလိုအပ်ပါ — `verifyFeedBytes()` သည် override ကို အလိုအလျောက် ရယူအသုံးပြုသည် (`src/lib/radar/pinnedKeys.ts` ရှိ `getFeedPublicKeys()`)၊ ထို့အပြင် version နှိုင်းယှဉ်ခြင်း၊ schema စစ်ဆေးအတည်ပြုခြင်းနှင့် ပေါင်းစည်းခြင်းဆိုင်ရာ စည်းမျဉ်းများကို self-hosted feed တွင်လည်း အလားတူ အသုံးပြုသည်။

Referral link များ (အထက်ရှိ [Referral links (အခမဲ့ credit များ)](#referral-links-free-credits) ကို ကြည့်ပါ) သည် သီးခြား၊ ရွေးချယ်နိုင်သော artifact တစ်ခုဖြစ်သည်။ `/v1/catalog/latest` ကိုသာ ဝန်ဆောင်မှုပေးသည့် fork တစ်ခုသည် အပြည့်အဝ ဆက်လက်အလုပ်လုပ်သည် — `/v1/referrals/latest` မှ `404` ရရှိပါက `syncRadarReferrals()` သည် `{ status: "error" }` သို့ အဆင့်လျှော့ပြောင်းပြီး cache သည် ရှင်းလင်းနေမည်ဖြစ်သောကြောင့် `GET /api/radar/referrals` သည် စာမျက်နှာ၏ အခြားအစိတ်အပိုင်းများကို ပျက်ကွက်စေမည့်အစား `{ fixed: [], campaigns: [], tier: null }` ကို ဆက်လက်ပြန်ပေးသည်။ Referral link များကိုလည်း ပေးလိုပါက `RadarReferralsFeedSchema` (`src/lib/radar/referralsFeedSchema.ts`) နှင့် ကိုက်ညီသော `GET /v1/referrals/latest` ကို ဝန်ဆောင်မှုပေးပြီး catalog feed အတွက် အသုံးပြုသည့် Ed25519 key pair အတူတူဖြင့် လက်မှတ်ထိုးပါ။

ပံ့ပိုးသူ offer များသည် နောက်ထပ် ရွေးချယ်နိုင်သော artifact တစ်ခုဖြစ်သည်။ ၎င်းတို့ကို ဝန်ဆောင်မှုပေးရန် ပိတ်ထားသော `RadarOffersFeedSchema` (`src/lib/radar/offersFeedSchema.ts`) ဖြင့် `GET /v1/offers/latest` ကို အကောင်အထည်ဖော်ပါ၊ အသက်ဝင်နေသော entitlement ကို လိုအပ်ချက်အဖြစ် သတ်မှတ်ပါ၊ `x-omniroute-feed-tier: live` ကို ပြန်ပေးပြီး တိကျသည့် byte များကို တူညီသော key ဖြင့် လက်မှတ်ထိုးပါ။ ဤ endpoint ကို ချန်လှပ်ထားသည့် fork တစ်ခုတွင် catalog/referrals အပြုအမူသည် မပြောင်းလဲဘဲ ရှိနေမည်။ Offer refresh သည် ရှိပြီးသားအချက်အလက်များကို မဖျက်ဆီးဘဲ ပျက်ကွက်မည်ဖြစ်ပြီး နောက်ဆုံးအတည်ပြုထားသည့် local offer cache ကို ဆက်လက်အသုံးပြုနိုင်မည်ဖြစ်သည်။

Intel သည်လည်း အလားတူ ရွေးချယ်နိုင်သည်။ Self-hoster တစ်ခုသည် `RadarIntelFeedSchema` (`src/lib/radar/intelFeedSchema.ts`) ကို အသုံးပြု၍ `GET /v1/intel/latest` ကို ဝန်ဆောင်မှုပေးနိုင်ပြီး အသက်ဝင်နေသော entitlement ကို လိုအပ်ချက်အဖြစ် သတ်မှတ်ကာ `x-omniroute-feed-tier: live` ကို ပြန်ပေးပြီး တိကျသည့် byte များကို မျှဝေသုံးစွဲထားသော Ed25519 key ဖြင့် လက်မှတ်ထိုးနိုင်သည်။ Endpoint ကို ချန်လှပ်ထားခြင်းသည် catalog၊ referrals နှင့် offers တို့ကို မပြောင်းလဲစေပါ။ Intel refresh သည် နောက်ဆုံးအတည်ပြုထားသည့် local snapshot ရှိပါက ၎င်းကို ဆက်လက်ထိန်းသိမ်းထားသည်။
