OmniRoute တွင် အသုံးပြုသူများက ပလက်ဖောင်းနှင့် အပြန်အလှန်လုပ်ဆောင်ခြင်း — တောင်းဆိုမှုများပြုလုပ်ခြင်း၊ ပံ့ပိုးသူများ ပြောင်းလဲခြင်း၊ combo များဖန်တီးခြင်း၊ token များမျှဝေခြင်းနှင့် အသိုင်းအဝိုင်းအတွက် ပါဝင်ကူညီခြင်းတို့ကို ဆုချီးမြှင့်သည့် local-first gamification အလွှာတစ်ခု ပါဝင်သည်။ အခြေအနေဒေတာအားလုံးကို SQLite တွင် သိမ်းဆည်းထားပြီး အသိုင်းအဝိုင်းဆာဗာများနှင့် federation ပြုလုပ်ခြင်းသည် မိမိဆန္ဒအလျောက် ဖွင့်သုံးရကာ push-based ဖြစ်သည်။

စနစ်ကို **အဓိကလုပ်ဆောင်မှုလမ်းကြောင်းတွင် ကြာချိန်လုံးဝမရှိစေရန်** ဒီဇိုင်းထုတ်ထားသည် — gamification event များကို request pipeline မှ စေလွှတ်ပြီး တုံ့ပြန်ချက်ကို မစောင့်ဘဲ ဆက်လက်လုပ်ဆောင်ကာ LLM တုံ့ပြန်ချက်ကို မည်သည့်အခါမျှ ပိတ်ဆို့မထားပါ။

## ခြုံငုံသုံးသပ်ချက်

### ရည်ရွယ်ချက်

မြင်သာသည့် တိုးတက်မှု (XP၊ level များ၊ badge များ)၊ လူမှုဆိုင်ရာ ယုံကြည်မှုအထောက်အထား (leaderboard များ) နှင့် စီးပွားရေးဆိုင်ရာ မက်လုံးများ (token မျှဝေခြင်း၊ ဖိတ်ခေါ်မှုဆုများ) ကို ပံ့ပိုးပေးခြင်းဖြင့် အသုံးပြုသူ ပါဝင်ဆောင်ရွက်မှုနှင့် ဆက်လက်အသုံးပြုမှုကို တိုးမြှင့်ရန်။

### လုပ်ဆောင်ချက်နယ်ပယ်

| လုပ်ဆောင်ချက်                          | ဖော်ပြချက်                                                                           |
| -------------------------------------- | ------------------------------------------------------------------------------------ |
| XP နှင့် Level များ                    | လုပ်ဆောင်ချက်တစ်ခုစီအတွက် XP ရယူပြီး polynomial curve တစ်ခုအတိုင်း level တက်ခြင်း    |
| Badge များ                             | ရှားပါးမှုအဆင့် 4 ဆင့်ပါဝင်သည့် အမျိုးအစား 5 မျိုးရှိ achievement 20 ကျော်           |
| Streak များ                            | လက်ရှိနှင့် အရှည်ကြာဆုံး streak ပါဝင်သည့် နေ့စဉ်တက်ကြွအသုံးပြုမှု ခြေရာခံခြင်း       |
| Leaderboard များ                       | ကမ္ဘာလုံးဆိုင်ရာ၊ အပတ်စဉ်၊ လစဉ်၊ token မျှဝေမှုနှင့် ပါဝင်ကူညီမှုဆိုင်ရာ နယ်ပယ်များ  |
| Token မျှဝေခြင်း                       | double-entry ledger မှတစ်ဆင့် အသုံးပြုသူများအကြား credit များ လွှဲပြောင်းခြင်း       |
| ဖိတ်ခေါ်ခြင်းနှင့် Redeem ပြုလုပ်ခြင်း | SHA-256 hash ဖြင့် သိမ်းဆည်းထားသည့် referral code များ                               |
| အသိုင်းအဝိုင်းဆာဗာများ                 | ပြင်ပ OmniRoute instance များနှင့် federation ပြုလုပ်ခြင်း                           |
| လိမ်လည်မှုတားဆီးရေး                    | ဆာဗာဘက်မှ အမှတ်တွက်ချက်ခြင်း၊ နှုန်းကန့်သတ်ခြင်းနှင့် z-score မူမမှန်မှု ရှာဖွေခြင်း |

### ဒီဇိုင်းမူများ

1. **Local-first** — အခြေအနေဒေတာအားလုံးကို SQLite တွင် သိမ်းဆည်းပြီး ပြင်ပဝန်ဆောင်မှုများ မလိုအပ်ပါ။
2. **ပိတ်ဆို့မှုမရှိခြင်း** — event များကို စေလွှတ်ပြီး တုံ့ပြန်ချက်ကို မစောင့်ဘဲ ဆက်လက်လုပ်ဆောင်သည်၊ LLM တုံ့ပြန်မှုလမ်းကြောင်းသည်
   gamification logic ကြောင့် မည်သည့်အခါမျှ နှောင့်နှေးခြင်းမရှိပါ။
3. **ဆာဗာက အဆုံးအဖြတ်ပေးခြင်း** — XP ကို ဆာဗာဘက်တွင်သာ တွက်ချက်ပြီး client များက
   ရမှတ်များကို အတုအယောင် တိုးမြှင့်၍မရပါ။
4. **ကိုယ်ရေးအချက်အလက်ကို လေးစားခြင်း** — leaderboard တွင် ပါဝင်မှုသည် မိမိဆန္ဒအလျောက်ဖြစ်ပြီး အသုံးပြုသူများက
   ၎င်းတို့၏ profile ကို ဖျောက်ထားနိုင်သည်။
5. **Federation အသင့်ဖြစ်ခြင်း** — အသိုင်းအဝိုင်းဆာဗာများသည် လက်မှတ်ထိုးထားသော API မှတစ်ဆင့် ရမှတ်များကို push လုပ်နိုင်ပြီး
   sync ပြုလုပ်ခြင်းသည် ပေါင်းထည့်ခြင်းမဟုတ်ဘဲ ထပ်ရေးခြင်းဖြစ်သည်။

## တည်ဆောက်ပုံ

### အဆင့်မြင့် လုပ်ဆောင်မှုစီးဆင်းပုံ

```
Client တောင်းဆိုမှု
  → /v1/chat/completions
    → handleChatCore()                      [open-sse/handlers/chatCore.ts]
      → ... (ရှိပြီးသား pipeline) ...
      → upstream တုံ့ပြန်ချက်ကို client ထံ ပေးပို့ခြင်း
      → setImmediate (စေလွှတ်ပြီး တုံ့ပြန်ချက်ကို မစောင့်ခြင်း):
        → emitGamificationEvent()           [src/lib/gamification/events.ts]
          → awardXp()                       [src/lib/gamification/xp.ts]
          → updateStreak()                  [src/lib/gamification/streaks.ts]
          → evaluateBadges()                [src/lib/gamification/badges.ts]
          → updateLeaderboard()             [src/lib/gamification/leaderboard.ts]
          → checkAnomalies()                [src/lib/gamification/antiCheat.ts]
```

event emitter သည် ပေါင်းစည်းမှုအတွက် တစ်ခုတည်းသော ချိတ်ဆက်ရာနေရာဖြစ်သည်။ တုံ့ပြန်ချက်ကို ပေးပို့ပြီးနောက် `chatCore.ts` က
`emitGamificationEvent()` ကို ခေါ်ဆိုကာ event module သည်
XP၊ streak၊ badge၊ leaderboard နှင့် လိမ်လည်မှုတားဆီးရေး subsystem များသို့ ဖြန့်ခွဲပေးသည်။

### Module မှီခိုမှုဂရပ်

```
src/lib/gamification/
  events.ts          ← အဝင်နေရာ (chatCore.ts မှ ခေါ်ဆိုသည်)
    ├── xp.ts        ← XP တွက်ချက်ခြင်းနှင့် level သတ်မှတ်ခြင်း
    ├── streaks.ts   ← နေ့စဉ်တက်ကြွအသုံးပြုမှု streak ကို ခြေရာခံခြင်း
    ├── badges.ts    ← badge သတ်မှတ်ချက်များကို အကဲဖြတ်ခြင်း
    ├── leaderboard.ts ← အဆင့်တွက်ချက်ခြင်းနှင့် SSE ထုတ်လွှင့်ခြင်း
    ├── antiCheat.ts ← နှုန်းကန့်သတ်ခြင်းနှင့် မူမမှန်မှု ရှာဖွေခြင်း
    ├── sharing.ts   ← token လွှဲပြောင်းမှု ledger
    ├── invites.ts   ← ဖိတ်ခေါ်မှု/redeem code စီမံခန့်ခွဲခြင်း
    ├── servers.ts   ← အသိုင်းအဝိုင်းဆာဗာ federation
    └── notifications.ts ← SSE အသိပေးချက် stream

src/lib/db/
  gamification.ts    ← CRUD လုပ်ဆောင်ချက်အားလုံး (ဇယား 8 ခု)

src/app/api/gamification/
  leaderboard/       ← GET အဆင့်များ၊ POST ကိုယ်တိုင် refresh ပြုလုပ်ခြင်း
  leaderboard/stream ← SSE အချိန်နှင့်တစ်ပြေးညီ update များ
  transfer/          ← GET မှတ်တမ်း၊ POST token များပေးပို့ခြင်း
  invite/            ← GET/POST code များ၊ DELETE ပြန်လည်ရုပ်သိမ်းခြင်း
  invite/redeem/     ← POST code တစ်ခုကို redeem ပြုလုပ်ခြင်း
  servers/           ← GET/POST/DELETE အသိုင်းအဝိုင်းဆာဗာများ
  federation/score/  ← POST ရမှတ်ကို ဆာဗာသို့ push လုပ်ခြင်း
  federation/leaderboard/ ← GET leaderboard ကို ဆာဗာမှ pull လုပ်ခြင်း
  notifications/     ← SSE badge/level-up အသိပေးချက်များ
  anomalies/         ← GET မူမမှန်မှုအစီရင်ခံစာများ (admin)
  rotate/            ← POST ဖိတ်ခေါ်မှု token secret များကို လဲလှယ်ခြင်း
```

### ဆုပေးသည့် လုပ်ငန်းစဉ်

```typescript
export async function awardXp(
  apiKeyId: string,
  action: XpAction,
  metadata?: Record<string, unknown>
): Promise<{ xp: number; level: number; title: string; levelUp: boolean }>;
```

1. XP ပမာဏကို ရယူရန် `XP_REWARDS[action]` တွင် ရှာဖွေပါ။
2. `checkRateLimit()` မှတစ်ဆင့် စစ်ဆေးပါ (မသမာမှုတားဆီးရေး- key တစ်ခုလျှင် တစ်မိနစ်အတွင်း အများဆုံး 1000 XP)။
3. transaction တစ်ခု ဖွင့်ပါ-
   - လက်ရှိ `user_levels` row ကို ဖတ်ပါ။
   - XP ထည့်ပြီး `levelFromXp(totalXp)` မှတစ်ဆင့် level ကို ပြန်လည်တွက်ချက်ပါ။
   - level ပြောင်းလဲသွားပါက `levelUp = true` ဟု သတ်မှတ်ပါ။
   - `user_levels` row ကို update လုပ်ပါ။
   - `xp_audit_log` ထဲသို့ ထည့်သွင်းပါ။
4. ရလဒ်ကို ပြန်ပေးပါ။ ခေါ်ယူသူက အသိပေးချက်များကို ကိုင်တွယ်သည်။

### အကူ function- `levelFromXp(totalXp)`

Level 1..100 ကို အစဉ်လိုက် လှည့်ပတ်ပြီး စုစုပေါင်း XP က `totalXp` ထက် ကျော်လွန်သည်အထိ `xp_for_level(n)` ကို ပေါင်းထည့်သည်။ သတ်မှတ်ချက်ပြည့်မီသည့် အမြင့်ဆုံး level ကို ပြန်ပေးသည်။
Level များကို 100 အထိသာ ကန့်သတ်ထားသောကြောင့် ၎င်းသည် O(100) ဖြစ်ပြီး လက်ခံနိုင်သည်။

### အကဲဖြတ်သည့် လုပ်ငန်းစဉ်

```
emitGamificationEvent(event)
  → evaluateBadges(apiKeyId, event)
    → getBadgeDefinitions()           # သတ်မှတ်ချက်အားလုံး
    → getUserBadges(apiKeyId)         # ရရှိပြီးသားများ (ကျော်သွားရန်)
    → မရရှိသေးသော badge တစ်ခုစီအတွက်-
       → matchesCriteria(badge, event, userState)
       → ကိုက်ညီပါက- awardBadge(apiKeyId, badgeId)
         → အသိပေးချက် payload ကို ပြန်ပေးသည်
```

အကဲဖြတ်မှုသည် **event-driven** ဖြစ်သည် — gamification event တစ်ခုစီပြီးနောက် လုပ်ဆောင်သော်လည်း event action နှင့် ကိုက်ညီသော `criteria.type` ရှိသည့် badge များကိုသာ စစ်ဆေးသည်။ ထို့ကြောင့် အကဲဖြတ်မှုသည် မြန်ဆန်နေသည် (event အများစုအတွက် < 5ms)။

### `matchesCriteria(badge, event, userState)`

| စံသတ်မှတ်ချက် အမျိုးအစား | စစ်ဆေးမှု                                               |
| ------------------------ | ------------------------------------------------------- |
| `action_count`           | `getActionCount(apiKeyId, action) >= count`             |
| `streak`                 | `getCurrentStreak(apiKeyId) >= days`                    |
| `unique_count`           | `getUniqueCount(apiKeyId, field) >= n`                  |
| `rank`                   | `getRank(apiKeyId, scope) <= n`                         |
| `first`                  | ဤ action type အတွက် ယခင် `xp_audit_log` entry မရှိခြင်း |
| `hidden`                 | သင့်လျော်သော စစ်ဆေးမှုခွဲထံ လွှဲပေးသည်                  |

## ဆက်တိုက်အသုံးပြုမှု ခြေရာခံစနစ်

**ဖိုင်:** `src/lib/gamification/streaks.ts`

### ဒေတာပုံစံ

ဆက်တိုက်အသုံးပြုမှုဒေတာများကို namespace ခွဲထားသော key များဖြင့် `key_value`
ဇယား (မျှဝေသုံးစွဲသည့် utility ဇယား) တွင် သိမ်းဆည်းထားသည်-

| Key                           | တန်ဖိုး                          | ဖော်ပြချက်                    |
| ----------------------------- | -------------------------------- | ----------------------------- |
| `gamification:streak:{keyId}` | `{current},{longest},{lastDate}` | လက်ရှိဆက်တိုက်အသုံးပြုမှုဒေတာ |

### လုပ်ဆောင်ပုံ

```typescript
export async function updateStreak(
  apiKeyId: string
): Promise<{ current: number; longest: number; milestone: boolean }>;
```

1. `key_value` မှ ဆက်တိုက်အသုံးပြုမှုမှတ်တမ်းကို ဖတ်ပါ။
2. `{current}`, `{longest}`, `{lastDate}` (ISO ရက်စွဲစာသား) တို့ကို parse လုပ်ပါ။
3. `lastDate === today` ဖြစ်ပါက — အပြောင်းအလဲမရှိပါ (ယနေ့အတွက် ရေတွက်ပြီးဖြစ်သည်)။
4. `lastDate === yesterday` ဖြစ်ပါက — `current` ကို တိုးပါ၊ လိုအပ်လျှင် `longest` ကို အပ်ဒိတ်လုပ်ပါ။
5. `lastDate < yesterday` ဖြစ်ပါက — `current = 1` သို့ ပြန်လည်သတ်မှတ်ပါ (ဆက်တိုက်အသုံးပြုမှု ပြတ်တောက်သွားသည်)။
6. အပ်ဒိတ်လုပ်ထားသောမှတ်တမ်းကို ရေးသားပါ။
7. 7၊ 14၊ 30၊ 60၊ 90၊ 180၊ 365 ရက် မှတ်တိုင်များကို စစ်ဆေးပါ။ မှတ်တိုင်တစ်ခုကို ကျော်လွန်ခဲ့ပါက
   `milestone = true` ဟု သတ်မှတ်ပါ (ခေါ်ယူသူက XP ပေးအပ်ပြီး badge များကို စစ်ဆေးသည်)။

### အစွန်းအခြေအနေများ

- **အချိန်ဇုန်**: ဆက်တိုက်အသုံးပြုမှုများတွင် UTC ရက်စွဲများကို အသုံးပြုသည် (`new Date().toISOString().slice(0, 10)`)။
  ၎င်းသည် ရည်ရွယ်ထားသော လုပ်ဆောင်ချက်ဖြစ်သည် — စံအချိန်ဇုန်တစ်ခုတည်းကို အသုံးပြုခြင်းက
  အချိန်ဇုန်များ ပြောင်းလဲခြင်းဖြင့် စနစ်ကို အခွင့်ကောင်းယူမှုအား တားဆီးပေးသည်။
- **အသုံးပြုသူအသစ်များ**: ဆက်တိုက်အသုံးပြုမှုမှတ်တမ်း မရှိသေးပါ။ ပထမဆုံးတောင်းဆိုမှုက
  `current=1, longest=1, lastDate=today` ဖြင့် မှတ်တမ်းတစ်ခု ဖန်တီးပေးသည်။
- **တစ်ရက်အတွင်း တောင်းဆိုမှုအများအပြား**: UTC ရက်၏ ပထမဆုံးတောင်းဆိုမှုကသာ
  ဆက်တိုက်အသုံးပြုမှုကို တိုးပေးသည်။

export async function getLeaderboard(

### ကာလလှည့်ပြောင်းမှု

အပတ်စဉ်နှင့် လစဉ် အဆင့်သတ်မှတ်ချက်ဇယားများသည် အလိုအလျောက် လှည့်ပြောင်းသည်-

1. **မှတ်တမ်းတင်သိမ်းဆည်းခြင်း**: ကာလအပိုင်းအခြားသို့ ရောက်သောအခါ လက်ရှိ entry များကို
   ကာလအညွှန်းနှင့်အတူ `leaderboard_archive` သို့ ကူးယူပါ။
2. **ပြန်လည်သတ်မှတ်ခြင်း**: သက်တမ်းကုန်ဆုံးသွားသော ကာလ၏ entry များကို ဖျက်ပါ။
3. **အစပျိုးမှု**: `updateLeaderboard()` ကို ခေါ်ယူတိုင်း စစ်ဆေးသည်။ ကာလအသစ်၏
   ပထမဆုံးတောင်းဆိုမှုက လှည့်ပြောင်းမှုကို အစပျိုးသည်။

ဤနည်းဖြင့် အပတ်စဉ်ဇယားများသည် တနင်္လာနေ့တိုင်း 00:00 UTC တွင် ပြန်လည်သတ်မှတ်ပြီး လစဉ်ဇယားများသည်

### SSE အချိန်နှင့်တပြေးညီ အပ်ဒိတ်များ

**Endpoint:** `GET /api/gamification/stream`

```
Client → GET /api/gamification/stream
  → SSE ချိတ်ဆက်မှု တည်ဆောက်ပြီး
  → Server က ထိပ်ဆုံး ၁၀ ဦးပါ အဆင့်သတ်မှတ်ချက်ဇယား snapshot ကို ချက်ချင်းပေးပို့သည်
  → ၅ စက္ကန့်တိုင်း- အပြောင်းအလဲရှိပါက အပ်ဒိတ်လုပ်ထားသော ထိပ်ဆုံး ၁၀ ဦးစာရင်းကို push လုပ်သည်
  → ၁၅ စက္ကန့်တိုင်း- heartbeat comment (": heartbeat\n\n")
  → Client ချိတ်ဆက်မှုဖြတ်တောက်သည် → ရှင်းလင်းခြင်း (listener ကို ဖယ်ရှားသည်)
```

Event ပုံစံ-

```
event: leaderboard
data: {"scope":"global","entries":[...]}

event: leaderboard
data: {"scope":"weekly","entries":[...]}

: heartbeat
```

SSE manager သည် ချိတ်ဆက်ထားသော client များကို scope အလိုက် ခြေရာခံပြီး နောက်ဆုံး push လုပ်ခဲ့သည့်
အချိန်မှစ၍ အဆင့်သတ်မှတ်ချက်ဇယားဒေတာ အမှန်တကယ်ပြောင်းလဲမှသာ အပ်ဒိတ်များ ပေးပို့သည်။

## တိုကင် မျှဝေခြင်း

**ဖိုင်:** `src/lib/gamification/sharing.ts`

### နှစ်ဖက်စာရင်းသွင်း စာရင်းကိုင်စနစ်

လွှဲပြောင်းမှုတစ်ခုစီသည် `token_ledger` တွင် အတန်းနှစ်တန်း ဖန်တီးသည်-

| အတန်း        | `from_key_id` | `to_key_id` | `amount` |
| ------------ | ------------- | ----------- | -------- |
| ထုတ်ယူမှု    | ပေးပို့သူ     | လက်ခံသူ     | +amount  |
| ထည့်သွင်းမှု | လက်ခံသူ       | ပေးပို့သူ   | -amount  |

ခဏစောင့်ပါ — သတ်မှတ်ထားသော ပုံစံမှာ-

| အတန်း        | `from_key_id` | `to_key_id` | `amount` | အဓိပ္ပာယ်             |
| ------------ | ------------- | ----------- | -------- | --------------------- |
| ပေးပို့ခြင်း | ပေးပို့သူ     | လက်ခံသူ     | +amount  | ပေးပို့သူထံမှ ထွက်ငွေ |
| လက်ခံခြင်း   | လက်ခံသူ       | ပေးပို့သူ   | +amount  | လက်ခံသူထံသို့ ဝင်ငွေ  |

လက်ကျန်ကို အောက်ပါအတိုင်း တွက်ချက်သည်-

```sql
SELECT
  COALESCE(SUM(CASE WHEN to_key_id = ? THEN amount ELSE 0 END), 0)
  - COALESCE(SUM(CASE WHEN from_key_id = ? THEN amount ELSE 0 END), 0)
  AS balance
FROM token_ledger
WHERE from_key_id = ? OR to_key_id = ?
```

### လွှဲပြောင်းမှု လုပ်ငန်းစဉ်

```typescript
export async function transferTokens(
  fromKeyId: string,
  toKeyId: string,
  amount: number,
  idempotencyKey: string
): Promise<{ success: boolean; balance: number }>;
```

1. **အတည်ပြုစစ်ဆေးခြင်း**: `amount > 0`, `fromKeyId !== toKeyId`။
2. **ထပ်ခါတလဲလဲလုပ်ဆောင်မှုကို ကာကွယ်ခြင်း**: `idempotency_key` သည် ledger ထဲတွင် ရှိပြီးသား ဟုတ်မဟုတ် စစ်ဆေးပါ။
   ရှိပြီးသားဖြစ်ပါက သိမ်းဆည်းထားသော ရလဒ်ကို ပြန်ပေးပါ။
3. **Transaction** (SQLite transaction တစ်ခုတည်း)-
   a. ပေးပို့သူ၏ လက်ကျန်ကို တွက်ချက်ပါ။
   b. `balance < amount` ဖြစ်ပါက ရပ်ဆိုင်းပါ (လက်ကျန်မလုံလောက်ပါ)။
   c. ပေးပို့မှုအတန်းကို ထည့်သွင်းပါ (`from=sender,` ကို ပြန်ပေးပါ။

### နှုန်းကန့်သတ်ခြင်း

- API key တစ်ခုလျှင် တစ်မိနစ်အတွင်း လွှဲပြောင်းမှု အများဆုံး 10 ကြိမ်။
- လွှဲပြောင်းမှုတစ်ကြိမ်လျှင် တိုကင် အများဆုံး 10,000။
- API key တစ်ခုလျှင် တစ်ရက်အတွင်း လွှဲပြောင်းနိုင်သော တိုကင် အများဆုံး 100,000။

## ဖိတ်ကြားခြင်းနှင့် တိုကင်များ ထုတ်ယူအသုံးပြုခြင်း

**ဖိုင်:** `src/lib/gamification/invites.ts`

### ကုဒ်ပုံစံ

- **ကုဒ်**: အက္ခရာနှင့် ဂဏန်း 8 လုံးပါဝင်ပြီး (ဥပမာ `A3K9-X7M2`) လူဖတ်ရှုရလွယ်ကူကာ
  အသုံးပြုသူထံ ပြသသည်။
- **တိုကင်**: 32-byte ကျပန်းတိုကင်ဖြစ်ပြီး SHA-256 hash အဖြစ် သိမ်းဆည်းသည်။
  ပရိုဂရမ်ဖြင့် ထုတ်ယူအသုံးပြုရန် (ဥပမာ URL လင့်ခ်များ) အသုံးပြုသည်။

### သိမ်းဆည်းမှု

| ကော်လံ       | တန်ဖိုး                                           |
| ------------ | ------------------------------------------------- |
| `code`       | `A3K9X7M2` (တစ်မူထူးခြားပြီး index ပြုလုပ်ထားသည်) |
| `token_hash` | SHA-256(raw_token)                                |

တိုကင်အကြမ်းကို ဖန်တီးချိန်တွင် အသုံးပြုသူထံ တစ်ကြိမ်တည်းသာ ပြန်ပေးသည်။ OmniRoute သည်
၎င်းကို နောက်တစ်ကြိမ် သိမ်းဆည်းခြင်း သို့မဟုတ် ပြသခြင်း လုံးဝမပြုလုပ်ပါ — hash ကိုသာ ဆက်လက်သိမ်းဆည်းထားသည်။

### မိမိကိုယ်ကို ရည်ညွှန်းခြင်းမှ ကာကွယ်မှု

အသုံးပြုသူတစ်ဦးက ကုဒ်တစ်ခုကို ထုတ်ယူအသုံးပြုသောအခါ စနစ်သည် အောက်ပါတို့ကို စစ်ဆေးသည်-

1. ကုဒ်သည် မတူညီသော `api_key_id` တစ်ခုနှင့် သက်ဆိုင်ရမည်။
2. ထုတ်ယူအသုံးပြုသူသည် တူညီသော ရည်ညွှန်းသူထံမှ မည်သည့်ကုဒ်ကိုမျှ ယခင်က
   ထုတ်ယူအသုံးပြုထားခြင်း မရှိရပါ (`invite_tokens` နှင့် redemption log ကို join လုပ်၍ စစ်ဆေးသည်)။

စစ်ဆေးချက်တစ်ခုခု မအောင်မြင်ပါက ရှင်းလင်းသော အမှားမက်ဆေ့ချ်ဖြင့် ထုတ်ယူအသုံးပြုမှုကို ငြင်းပယ်သည်။

### သက်တမ်းကုန်ဆုံးမှုနှင့် ကန့်သတ်ချက်များ

- ပုံသေ `max_uses`: 10 (ဖန်တီးချိန်တွင် ပြင်ဆင်သတ်မှတ်နိုင်သည်)။
- ပုံသေ `expires_at`: ဖန်တီးချိန်မှ ရက် 30။
- သက်တမ်းကုန်ဆုံးသွားသော သို့မဟုတ် အသုံးပြုခွင့်ပြည့်သွားသော ကုဒ်များသည် HTTP 410 Gone ကို ပြန်ပေးသည်။

## ကွန်မြူနတီဆာဗာ အဖွဲ့ချိတ်ဆက်မှု

**ဖိုင်:** `src/lib/gamification/servers.ts`

### ချိတ်ဆက်ခြင်း

ကွန်မြူနတီဆာဗာတစ်ခုကို အဝေးရှိဆာဗာက ထုတ်ပေးသော ဖိတ်ကြားမှုတိုကင်မှတစ်ဆင့် မှတ်ပုံတင်သည်။ စက်တွင်း instance သည်-

1. ဖိတ်ကြားမှုတိုကင်ကို လက်ခံရရှိသည် (ဥပမာ၊ dashboard ထဲသို့ ကူးထည့်ခြင်း)။
2. တိုကင်ကို စစ်ဆေးအတည်ပြုပြီး လက်ရှိ leaderboard ကို ရယူရန် အဝေးရှိဆာဗာ၏ `POST /api/gamification/federation/leaderboard` ကို ခေါ်ဆိုသည်။
3. ဆာဗာမှတ်တမ်းကို `status: connected` ဖြင့် သိမ်းဆည်းသည်။

### စင့်ခ်လုပ်ဆောင်မှုပုံစံ

Federation သည် ထပ်ပေါင်းသည့်ပုံစံမဟုတ်ဘဲ **အစားထိုးရေးသားသည့် စင့်ခ်လုပ်ဆောင်မှုပုံစံ** ကို အသုံးပြုသည်-

```
စက်တွင်း Instance                ကွန်မြူနတီဆာဗာ
     │                              │
     ├── ရမှတ် ပို့ခြင်း ───────────►│  POST /federation/score
     │   { api_key_id, score }      │  (ဆာဗာက တိုကင် hash ကို စစ်ဆေးအတည်ပြုသည်)
     │                              │
     ├── leaderboard ရယူခြင်း ─────►│  GET /federation/leaderboard
     │◄── ထိပ်ဆုံး N ခု ────────────┤  (စက်တွင်း cache ကို အစားထိုးရေးသားသည်)
     │                              │
     └── ကျန်းမာရေး စစ်ဆေးခြင်း ───►│  GET /federation/health
         (60s တိုင်း၊ timeout 5s)   │
```

### စစ်မှန်ကြောင်းအတည်ပြုခြင်း

Federation တောင်းဆိုမှုများတွင် အောက်ပါတို့ ပါဝင်သည်-

```
Authorization: Bearer <raw_token>
X-Federation-Version: 1
```

အဝေးရှိဆာဗာသည် တိုကင်ကို hash လုပ်ပြီး ကိုက်ညီသည့် `community_servers` row ကို ရှာဖွေသည်။ ထို့ကြောင့် သိမ်းဆည်းထားသော hash ကို ပို့လွှတ်ရန် မလိုအပ်ပါ။

### ကျန်းမာရေး စောင့်ကြည့်ခြင်း

ဆာဗာမှတ်တမ်းတစ်ခုစီသည် အောက်ပါတို့ကို ခြေရာခံသည်-

| Field       | ဖော်ပြချက်                                          |
| ----------- | --------------------------------------------------- |
| `status`    | `connected`, `degraded`, `unreachable`              |
| `last_sync` | နောက်ဆုံး စင့်ခ်အောင်မြင်ခဲ့သည့် ISO အချိန်မှတ်တမ်း |
| `failures`  | ဆက်တိုက် ကျန်းမာရေးစစ်ဆေးမှု မအောင်မြင်သည့်အကြိမ်ရေ |

ဆက်တိုက် 5 ကြိမ် မအောင်မြင်ပြီးနောက် status သည် `unreachable` သို့ ပြောင်းလဲသွားပြီး ကိုယ်တိုင်ပြုလုပ်သော ကျန်းမာရေးစစ်ဆေးမှု အောင်မြင်သည်အထိ စင့်ခ်လုပ်ဆောင်မှုကို ခေတ္တရပ်ထားသည်။

## လိမ်လည်မှု တားဆီးရေး

**ဖိုင်:** `src/lib/gamification/antiCheat.ts`

### ဆာဗာဘက်မှ ရမှတ်တွက်ချက်ခြင်း

XP တွက်ချက်မှုအားလုံးကို `src/lib/gamification/xp.ts` တွင် လုပ်ဆောင်သည်။ Client များသည် ရမှတ်ကို မပေးပို့ပါ—၎င်းတို့သည် လုပ်ဆောင်ချက်များကို ပေးပို့ပြီး ဆာဗာက XP ကို တွက်ချက်သည်။ `leaderboard.score` column ကို ဆာဗာဘက်ရှိ code ကသာ ရေးသားနိုင်သည်။

### နှုန်းထား ကန့်သတ်ခြင်း

| ကန့်သတ်ချက်                            | တန်ဖိုး | သက်ရောက်မှုနယ်ပယ်        |
| -------------------------------------- | ------- | ------------------------ |
| တစ်မိနစ်လျှင် အများဆုံး XP             | 1,000   | API key တစ်ခုလျှင်       |
| တစ်မိနစ်လျှင် အများဆုံး လွှဲပြောင်းမှု | 10      | API key တစ်ခုလျှင်       |
| အများဆုံး လွှဲပြောင်းပမာဏ              | 10,000  | လွှဲပြောင်းမှုတစ်ခုလျှင် |
| နေ့စဉ် အများဆုံး လွှဲပြောင်းမှု        | 100,000 | API key တစ်ခုလျှင်       |

နှုန်းထားကန့်သတ်မှုများသည် memory အတွင်းရှိ sliding window ကို အသုံးပြုသည် (`open-sse/services/` ရှိ `RateLimitManager` နှင့် တူညီသောပုံစံ)။ Process ပြန်လည်စတင်ပါက SQLite ဖြင့် ထောက်ပံ့ထားသော counter များကို အရန်အဖြစ် အသုံးပြုသည်။

### Z-Score ဖြင့် မူမမှန်မှု ရှာဖွေခြင်း

API key တစ်ခုစီအတွက် စနစ်သည် တစ်နာရီလျှင် ရရှိသော XP ၏ နောက်ဆုံး 7 ရက်စာ ရွေ့လျား window ကို ထိန်းသိမ်းထားသည်။ XP ချီးမြှင့်မှုတစ်ခုစီတွင်-

1. အသုံးပြုသူ၏ လက်ရှိ တစ်နာရီလျှင် XP ရရှိနှုန်းကို တွက်ချက်သည်။
2. လူအစုအဝေး၏ ပျမ်းမျှနှင့် စံသွေဖည်မှုကို တွက်ချက်သည်။
3. `z = (user_rate - mean) / stddev` ကို တွက်ချက်သည်။
4. `z > 3.0` (စံသွေဖည်မှု 3 ခု) ဖြစ်ပါက မူမမှန်မှုအဖြစ် အမှတ်အသားပြုသည်။

မူမမှန်မှုများကို `action = 'anomaly_detected'` ဖြင့် `xp_audit_log` သို့ မှတ်တမ်းတင်ပြီး admin dashboard ပေါ်တွင် ဖော်ပြသည်။

### စစ်ဆေးမှတ်တမ်း

XP ချီးမြှင့်မှု၊ လွှဲပြောင်းမှု၊ badge ရရှိမှုနှင့် မူမမှန်မှုရှာဖွေမှုတိုင်းကို အောက်ပါအချက်အလက်များနှင့်အတူ `xp_audit_log` သို့ မှတ်တမ်းတင်သည်-

| Field        | ဖော်ပြချက်                                                            |
| ------------ | --------------------------------------------------------------------- |
| `api_key_id` | မည်သူ                                                                 |
| `action`     | ဖြစ်ပျက်ခဲ့သည့်အရာ (xp_award, transfer, anomaly, …)                   |
| `xp_awarded` | ပမာဏ (XP မဟုတ်သော ဖြစ်ရပ်များအတွက် 0)                                 |
| `metadata`   | ဆက်စပ်အကြောင်းအရာပါဝင်သည့် JSON (လုပ်ဆောင်ချက်အမျိုးအစား၊ ပစ်မှတ်၊ …) |
| `created_at` | မည်သည့်အချိန် (ISO 8601)                                              |

Admin များသည် `GET /api/gamification/anomalies` မှတစ်ဆင့် စစ်ဆေးမှတ်တမ်းအပြည့်အစုံကို query ပြုလုပ်နိုင်သည်။

## API လမ်းကြောင်းများ

လမ်းကြောင်းအားလုံးသည် စံ OmniRoute ပုံစံကို လိုက်နာသည်-

```
Route → CORS ကြိုတင်စစ်ဆေးမှု → Body အတည်ပြုခြင်း (Zod) → Auth (extractApiKey)
  → Handler
```

### Endpoint များ

| Method | Path                                       | ဖော်ပြချက်                                                 | Auth         |
| ------ | ------------------------------------------ | ---------------------------------------------------------- | ------------ |
| GET    | `/api/gamification/leaderboard`            | ဦးဆောင်သူစာရင်းကို ရယူရန် (နယ်ပယ်၊ ကာလ၊ စာမျက်နှာခွဲခြင်း) | မလိုအပ်လည်းရ |
| POST   | `/api/gamification/leaderboard`            | ဦးဆောင်သူစာရင်း cache ကို အတင်းအကျပ် ပြန်လည်ဆန်းသစ်ရန်     | လိုအပ်သည်    |
| GET    | `/api/gamification/stream`                 | SSE အချိန်နှင့်တစ်ပြေးညီ ဦးဆောင်သူစာရင်း အပ်ဒိတ်များ       | မလိုအပ်လည်းရ |

## Pipeline ပေါင်းစည်းမှု

### ပေါင်းစည်းသည့်နေရာ

Gamification သည် `open-sse/handlers/chatCore.ts` ရှိ တစ်ခုတည်းသောနေရာတွင် request pipeline နှင့် ချိတ်ဆက်သည်-

```typescript
// တုံ့ပြန်ချက်ကို client ထံ ပေးပို့ပြီးနောက်-
setImmediate(() => {
  emitGamificationEvent({
    type: "request.completed",
    apiKeyId,
    metadata: {
      provider: selectedProvider,
      model: selectedModel,
      comboId: resolvedCombo?.id,
      compressionUsed: compressionStats?.applied,
      skillUsed: skillExecution?.name,
    },
  }).catch(() => {
    // စတင်ပြီး မစောင့်ဆိုင်းပါ- မှတ်တမ်းတင်သော်လည်း client ထံ လုံးဝ မဖြန့်ပို့ပါ
  });
});
```

### Event အမျိုးအစားများ

| Event အမျိုးအစား    | ထုတ်လွှတ်သည့်အချိန်                                               |
| ------------------- | ----------------------------------------------------------------- |
| `request.completed` | အောင်မြင်သော LLM တုံ့ပြန်ချက်ကို ပေးပို့ပြီးချိန်                 |
| `provider.switch`   | Provider ပြောင်းလဲသည့်အချိန် (combo fallback များကို ထည့်တွက်သည်) |
| `combo.created`     | Combo ပြင်ဆင်သတ်မှတ်မှုအသစ်ကို သိမ်းဆည်းပြီးချိန်                 |
| `combo.used`        | Combo ပစ်မှတ်ကို အောင်မြင်စွာ ထိမှန်ချိန်                         |
| `badge.earned`      | တံဆိပ်အကဲဖြတ်မှုက ကိုက်ညီမှုတစ်ခုကို တွေ့ရှိချိန်                 |
| `streak.milestone`  | ဆက်တိုက်မှတ်တမ်း သတ်မှတ်အဆင့်ကို ကျော်လွန်ချိန်                   |
| `transfer.sent`     | တိုကင်လွှဲပြောင်းမှု ပြီးစီးချိန်                                 |
| `referral.redeemed` | ဖိတ်ကြားကုဒ်ကို အောင်မြင်စွာ အသုံးပြုပြီးချိန်                    |
| `compression.used`  | Prompt ချုံ့ခြင်းကို အသုံးပြုချိန်                                |
| `skill.executed`    | Skill လုပ်ဆောင်မှု ပြီးစီးချိန်                                   |
| `model.first_use`   | ပြီးခဲ့သော 7 ရက်အတွင်း အသုံးမပြုခဲ့သည့် Model ကို အသုံးပြုချိန်   |

### ပိတ်ဆို့မှုမရှိကြောင်း အာမခံချက်

`setImmediate` + `.catch(() => {})` ပုံစံသည် အောက်ပါတို့ကို သေချာစေသည်-

1. Gamification မလုပ်ဆောင်မီ တုံ့ပြန်ချက်ကို အပြည့်အဝ ပေးပို့ပြီးဖြစ်သည်။
2. Gamification အမှားများကို client ထံ လုံးဝ မဖော်ပြပါ။
3. Event လုပ်ဆောင်မှုသည် inline မဟုတ်ဘဲ နောက်လာမည့် microtask တွင် လုပ်ဆောင်သည်။

| လွှဲပြောင်းမှု လိမ်လည်ခြင်း               | Double-entry ledger၊ atomic transaction များ၊ rate limit များ                                                 |
| ကိုယ်တိုင် referral ပြုလုပ်ခြင်း          | ရယူအသုံးပြုချိန်တွင် `api_key_id` ကို အပြန်အလှန်စစ်ဆေးခြင်း                                                   |
| ဦးဆောင်သူစာရင်း ခြယ်လှယ်ခြင်း             | Z-score မူမမှန်မှု ရှာဖွေခြင်း၊ admin မူမမှန်မှု dashboard                                                    |
| Federation token ခိုးယူမှု                | SHA-256 ဖြင့် hash လုပ်ထားသော သိမ်းဆည်းမှု၊ မူရင်း token ကို တစ်ကြိမ်သာ ပြသခြင်း                              |
| ဖိတ်ကြားကုဒ်များကို brute force လုပ်ခြင်း | ရယူအသုံးပြုသည့် endpoint တွင် rate limit သတ်မှတ်ခြင်း၊ စာလုံး 8 လုံးပါ entropy                                |
| ပြသအမည်များမှ XSS                         | ပြသအမည်များကို သန့်စင်ခြင်း၊ ဦးဆောင်သူစာရင်း entry များကို escape လုပ်ခြင်း                                   |
| Hash များအပေါ် timing attack              | token hash နှိုင်းယှဉ်မှုအတွက် `crypto.timingSafeEqual` ကို အသုံးပြုခြင်း                                     |

### အထောက်အထားစိစစ်မှု လိုအပ်ချက်များ

- **အများပြည်သူအသုံးပြုနိုင်** (အထောက်အထားစိစစ်မှု မလိုအပ်): `GET /leaderboard`, `GET /stream` (ဖတ်ရန်သာ
  ဦးဆောင်သူစာရင်းများ)။
- **API key လိုအပ်သည်**: ရေးသားသည့် လုပ်ဆောင်ချက်အားလုံး၊ profile၊ လွှဲပြောင်းမှုများ၊ ဖိတ်ကြားမှုများ။
- **Admin သာ**: မူမမှန်မှု dashboard၊ audit log ကြည့်ရှုကိရိယာ။
- **Federation**: `Authorization`
  header ထဲရှိ မူရင်း token ကို အသုံးပြုသော သီးခြား အထောက်အထားစိစစ်ရေး လမ်းကြောင်းဖြင့် သိမ်းဆည်းထားသည့် SHA-256 hash နှင့် တိုက်ဆိုင်စစ်ဆေးသည်။

## အနာဂတ်တွင် ထည့်သွင်းစဉ်းစားရန်များ

- **ရာသီအလိုက် အစီအစဉ်များ**: အချိန်ကန့်သတ်ထားသော တံဆိပ်အစုံများနှင့် ဦးဆောင်သူစာရင်း ရာသီများ။
- **အသင်းလိုက် ဦးဆောင်သူစာရင်းများ**: အသုံးပြုသူများကို အဖွဲ့အစည်း သို့မဟုတ် combo အလိုက် အုပ်စုဖွဲ့ခြင်း။
- **XP ဆတိုးများ**: ပရိုမိုးရှင်းကာလများအတွင်း XP ကို မြှင့်တင်ခြင်း။
- **အောင်မြင်မှု မျှဝေခြင်း**: မျှဝေနိုင်သော တံဆိပ်ကတ်များ (OpenGraph ပုံများ) ကို ဖန်တီးခြင်း။
- **မိုဘိုင်း push အသိပေးချက်များ**: တံဆိပ်/အဆင့် ဖြစ်ရပ်များအတွက် webhook အခြေခံ အသိပေးချက်များ။
- **ဦးဆောင်သူစာရင်း API**: ပြင်ပအဖွဲ့အစည်း ပေါင်းစည်းမှုများအတွက် အများသုံး API။
