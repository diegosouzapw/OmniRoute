Traffic Inspector သည် OmniRoute တွင် အသင့်ပါဝင်သော HTTPS traffic debugger ဖြစ်ပြီး Charles Proxy / mitmweb / HTTP Toolkit ကဲ့သို့သော tool တစ်ခုဖြစ်ကာ **LLM-aware** နှင့် **agent-aware** ဖြစ်သည်။ ၎င်းကို `/dashboard/tools/traffic-inspector` တွင် တွေ့နိုင်ပြီး တစ်ပြိုင်နက်တည်း capture source ၅ ခုအထိမှ live traffic ကို လက်ခံရရှိနိုင်သည်။

**Dashboard တည်နေရာ:** `/dashboard/tools/traffic-inspector`
**Sidebar အုပ်စု:** Tools (AgentBridge ၏နောက်တွင်)
**ထပ်မံကြည့်ရှုရန်:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge သည် capture mode 1 ဖြစ်သည်။

### Architecture ကို စာပိုဒ်တစ်ပိုဒ်ဖြင့် ရှင်းလင်းချက်

`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) သည် မျှဝေအသုံးပြုသည့် in-memory ring buffer တစ်ခုဖြစ်သည် (မူလသတ်မှတ်ချက်အရ entry 1000၊ `INSPECTOR_BUFFER_SIZE` မှတစ်ဆင့် ပြင်ဆင်သတ်မှတ်နိုင်သည်)။ Capture source အားလုံးသည် `push()` မှတစ်ဆင့် ၎င်းထဲသို့ ရေးသားကြသည်။ Buffer သည် entry တစ်ခုချင်းစီကို `kindDetector.ts` အသုံးပြု၍ အမျိုးအစားခွဲခြားပြီး (၎င်းသည် LLM request ဟုတ်မဟုတ် ဆုံးဖြတ်သည်) `contextKey` တစ်ခုကို တွက်ချက်ကာ (system prompt ၏ SHA-256 fingerprint) `globalTrafficBuffer.subscribe()` မှတစ်ဆင့် WebSocket subscriber အားလုံးထံ broadcast လုပ်သည်။ Dashboard သည် `GET /api/tools/traffic-inspector/ws` မှတစ်ဆင့် ချိတ်ဆက်ပြီး ချိတ်ဆက်ချိန်တွင် snapshot တစ်ခုကို လက်ခံရရှိကာ ထို့နောက် `new`/`update`/`clear` event များကို ဆက်လက်လက်ခံရရှိသည်။

## §2 ဖမ်းယူမှုမုဒ်များ

Traffic Inspector သည် **တစ်ပြိုင်နက်တည်း ဖမ်းယူနိုင်သော ရင်းမြစ် 5 ခု** ကို ပံ့ပိုးပေးသည်။ တစ်ခုချင်းစီကို သီးခြားစီ ဖွင့်/ပိတ်နိုင်သည်။ `InterceptedRequest` တိုင်းရှိ `source` အကွက် (`src/mitm/inspector/types.ts`) သည် `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"` သို့မဟုတ် `"tproxy"` တစ်ခုခုဖြစ်သည်။

### မုဒ် 1 — AgentBridge (ပုံသေ၊ အမြဲဖွင့်ထားသည်)

**ရင်းမြစ်:** AgentBridge handler များ (`src/mitm/handlers/base.ts`)
**လုပ်ဆောင်ပုံ:** `MitmHandlerBase` ရှိ `intercept()` ခေါ်ဆိုမှုတိုင်းသည် ဆက်လက်ပေးပို့ခြင်းမပြုမီ `hookBufferStart()` ကို ခေါ်ပြီး ပြီးဆုံးချိန်တွင် `hookBufferUpdate()` ကို ခေါ်သည်။ ထပ်ဆောင်း configuration လုံးဝမလိုအပ်ဘဲ AgentBridge စတင်လည်ပတ်သည်နှင့် အလုပ်လုပ်သည်။
**လွှမ်းခြုံမှု:** AgentBridge တွင် configure လုပ်ထားသည့် IDE agent 9 ခု
**မှတ်ချက်:** `InterceptedRequest` ရှိ `source` အကွက် = `"agent-bridge"`

### မုဒ် 2 — စိတ်ကြိုက် Host များ (DNS redirect)

**ရင်းမြစ်:** အသုံးပြုသူသတ်မှတ်ထားသော host စာရင်း (`inspector_custom_hosts` table)
**လုပ်ဆောင်ပုံ:** UI မှတစ်ဆင့် host တစ်ခုထည့်ခြင်းသည် `/etc/hosts` ထဲသို့ `127.0.0.1 <host>` ကို ထည့်ပေးသည် (sudo လိုအပ်သည်)။ ရှိပြီးသား AgentBridge MITM server (port 443) သည် host အသစ်အတွက် SNI cert တစ်ခုကို အလိုအလျောက် ဖန်တီးပေးသည်။
**လွှမ်းခြုံမှု:** ထည့်ထားသော host ကို အသုံးပြုသည့် မည်သည့် application မဆို — app configuration ပြောင်းလဲရန် မလိုအပ်ပါ
**မှတ်ချက်:** `source` = `"custom-host"`

အသုံးပြုမှုနမူနာများ-

- Python script များမှ `api.openai.com` ကို စောင့်ကြည့်ခြင်း
- `my-internal-llm.company.com` ကို debug လုပ်ခြင်း
- ကွန်ရက်တစ်ခုတည်းရှိ mobile device များမှ traffic ကို ဖမ်းယူခြင်း (ARP spoofing မှတစ်ဆင့် — အဆင့်မြင့်)

### မုဒ် 3 — HTTP_PROXY listener (port 8080)

**ရင်းမြစ်:** `HTTP_PROXY`/`HTTPS_PROXY` environment variable များကို အသုံးပြုသည့် application များ
**လုပ်ဆောင်ပုံ:** စံ explicit HTTP/HTTPS proxy အဖြစ် လုပ်ဆောင်သည့် port 8080 ရှိ ဒုတိယ listener (`src/mitm/inspector/httpProxyServer.ts`) ဖြစ်သည်။ `CONNECT` tunnel များ (HTTPS) နှင့် တိုက်ရိုက် HTTP request များကို လက်ခံသည်။
**လွှမ်းခြုံမှု:** `HTTP_PROXY` environment variable ကို လိုက်နာသည့် မည်သည့် application မဆို — DNS ပြောင်းလဲရန်မလို၊ sudo မလိုပါ
**မှတ်ချက်:** `source` = `"http-proxy"`

```bash
# Command တစ်ခုတည်းအတွက် အမြန်ဖမ်းယူခြင်း-
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# Shell session တစ်လျှောက် အမြဲတမ်းဖမ်းယူခြင်း-
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**TLS ကန့်သတ်ချက်:** HTTPS `CONNECT` tunnel များကို metadata (host, port, timing) အဖြစ်သာ ဖမ်းယူသည် — ပုံမှန်အားဖြင့် TLS body ကို decrypt မလုပ်ပါ။ Body အပြည့်အစုံကို စစ်ဆေးရန် "Proxy မုဒ်တွင် HTTPS ကို Decrypt လုပ်ရန်" toggle ကို ဖွင့်ပါ (ကိုယ်တိုင်ရွေးချယ်ဖွင့်ရပြီး AgentBridge cert ကို ယုံကြည်ထားရန် လိုအပ်သည်)။

**Port ပဋိပက္ခ:** port 8080 ကို အသုံးပြုနေပါက AgentBridge သည် ဖွဲ့စည်းထားသော error တစ်ခုနှင့်အတူ 409 ကို ပြန်ပေးသည်။ `INSPECTOR_HTTP_PROXY_PORT` environment variable မှတစ်ဆင့် port ကို ပြောင်းပါ။

### မုဒ် 4 — စနစ်တစ်ခုလုံးသက်ရောက်သော proxy (အဆင့်မြင့်၊ ကိုယ်တိုင်ရွေးချယ်ဖွင့်ရန်)

**ရင်းမြစ်:** OS အဆင့် proxy setting များ (စက်ရှိ app အားလုံးအပေါ် သက်ရောက်သည်)
**လုပ်ဆောင်ပုံ:** HTTP/HTTPS traffic အားလုံးကို HTTP_PROXY listener မှတစ်ဆင့် redirect လုပ်ရန် OS API များကို အသုံးပြုသည်-

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **လွှမ်းခြုံမှု:** System proxy setting များကို လိုက်နာသည့် စက်ရှိ application အားလုံး
  **မှတ်ချက်:** `source` = `"system-proxy"`

**ဘေးကင်းရေး လုပ်ဆောင်ချက်များ:**

- အလိုအလျောက်ပိတ်ပေးသည့် timer (ပုံသေ 30 မိနစ်၊ `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES` မှတစ်ဆင့် configure လုပ်နိုင်သည်)
- ယခင် system proxy အခြေအနေကို DB တွင် သိမ်းဆည်းပြီး revert လုပ်သည့်အခါ ပြန်လည်ထားရှိပေးသည်
- ဖွင့်ထားစဉ် အသုံးပြုသူက အခြားနေရာသို့ သွားပါက Dashboard တွင် "System proxy ကို မူလအခြေအနေသို့ ပြန်ထားနေသည်" prompt ကို ပြသသည်
- UI တွင် `⚠ အဆင့်မြင့်` badge နှင့် အတည်ပြုချက် checkbox ကို အတိအလင်း ပြသသည်

### မုဒ် 5 — TPROXY transparent decrypt (Linux၊ root၊ ကိုယ်တိုင်ရွေးချယ်ဖွင့်ရန်)

**ရင်းမြစ်:** Kernel TPROXY + policy routing (`src/mitm/tproxy/`)
**လုပ်ဆောင်ပုံ:** `mangle OUTPUT` ထဲတွင် သတ်မှတ်ထားသော port (ပုံသေ `443`) သို့ အသစ်ထွက်ခွာသည့် local TCP connection များကို အမှတ်အသားပြုသည်။ `ip rule` တစ်ခုက အမှတ်အသားပြုထားသော packet များကို local delivery သို့ လမ်းကြောင်းပြောင်းပေးပြီး `mangle PREROUTING` ၏ `TPROXY` target က ၎င်းတို့ကို transparent (**IP_TRANSPARENT**) listener (ပုံသေ port `8443`) သို့ လွှဲပေးသည်။ Listener သည် dynamic CA မှ **တောင်းဆိုလာသည့်အခါ SNI hostname တစ်ခုချင်းစီအတွက်** ထုတ်ပေးသော leaf certificate ဖြင့် TLS ကို အဆုံးသတ်ပြီး၊ decrypt လုပ်ထားသော အပြန်အလှန်ဆက်သွယ်မှုကို ဖမ်းယူကာ request ကို မူလ destination သို့ ပြန်လည် encrypt လုပ်ပြီး ပေးပို့သည်။
**လွှမ်းခြုံမှု:** သတ်မှတ်ထားသော port ရှိ **မည်သည့်** destination host မဆို — `/etc/hosts` spoof မလို၊ `HTTP_PROXY` environment variable မလို၊ system-wide proxy ကို ပြောင်းလဲရန် မလိုပါ။ Intercept လုပ်ခံရသော process တွင် configuration ပြောင်းလဲရန် မလိုသော်လည်း dynamic CA ကို ယုံကြည်ထားရမည်။
**မှတ်ချက်:** `source` = `"tproxy"`

**လိုအပ်ချက်များ:** Linux တွင်သာ အသုံးပြုနိုင်ပြီး (**IP_TRANSPARENT** သည် Linux အတွက်သာ ဖြစ်သည်)၊ **CAP_NET_ADMIN** capability (root) နှင့် C toolchain ဖြင့် build လုပ်ရမည့် native N-API addon (`npm run build:native:tproxy`) လိုအပ်သည်။ မရရှိနိုင်ပါက dashboard toggle ကို ပိတ်ထားပြီး "TPROXY decrypt အတွက် Linux + root + native addon လိုအပ်သည်" ဟူသော tooltip ကို ပြသသည်။ Firewall rule များကို transaction ပုံစံဖြင့် apply/revert လုပ်သည် (crash ဖြစ်ပါက `mangle` rule တစ်ခုကို မည်သည့်အခါမျှ ချန်ထားမည်မဟုတ်ပါ)၊ reboot လုပ်သည့်အခါ ရှင်းလင်းပေးသည်။ SO_MARK အခြေပြု anti-loop က proxy ၏ ကိုယ်ပိုင် ပြန်လည် encrypt လုပ်ထားသော forward ကို ထပ်မံ intercept မဖြစ်စေရန် ကာကွယ်ပေးသည်။

ဤအရာသည် သီးခြား operator guide ပါရှိသော ကြီးမားသည့် subsystem တစ်ခုဖြစ်သည် — firewall recipe အပြည့်အစုံ၊ SNI တစ်ခုချင်းစီအလိုက် dynamic CA + trust-store installer၊ local-only route၊ anti-loop အသေးစိတ်အချက်များနှင့် configuration schema အတွက် `docs/security/MITM-TPROXY-DECRYPT.md` (git တွင်သာရှိပြီး `/docs` ထဲသို့ compile မလုပ်ထားပါ) ကို ကြည့်ပါ။ Toggle ကို `GET / POST / DELETE /api/tools/agent-bridge/tproxy` က ထိန်းချုပ်သည် (မှတ်ချက်- route သည် Traffic Inspector prefix အောက်တွင်မဟုတ်ဘဲ AgentBridge prefix အောက်တွင် ရှိသည်)။

### 3.2 တောင်းဆိုချက်စာရင်း (ဘယ်ဘက်အကန့်)

- **Virtualized** (`useVirtualList` + `ResizeObserver`): ရပ်တန့်သွားခြင်းမရှိဘဲ အကြောင်းအရာ 1000 ကို ကိုင်တွယ်နိုင်သည်
- စစ်ဆေးနေစဉ် ခေတ္တရပ်ထားနိုင်သော ခလုတ်ပါသည့် **အလိုအလျောက် လှိမ့်ခြင်း**
- **အခြေအနေအလိုက် အရောင်ခွဲခြားခြင်း**: အစိမ်းရောင် (2xx)၊ အဝါရောင် (3xx)၊ အနီရောင် (4xx/5xx)၊ မီးခိုးရောင် (လုပ်ဆောင်ဆဲ)
- **Agent အီမိုဂျီ**: 🔵 Antigravity၊ 🟢 Copilot၊ 🟠 Kiro၊ 🟣 Codex၊ 🔷 Cursor၊ 🟤 Zed၊ 🟡 Claude Code၊ ⚫ Open Code၊ 🌐 စိတ်ကြိုက် host
- **Context အရောင်ဘား**: `contextKey` (system prompt ၏ SHA-256) အလိုက် အရောင်သတ်မှတ်ထားသော 1px ဘယ်ဘက်ဘောင် — ဆက်စပ်သည့် စကားဝိုင်းများကို မြင်သာစွာ အုပ်စုဖွဲ့ပေးသည်
- **လိုအပ်မှ body ကို ရယူခြင်း**: ရွေးချယ်ထားသော တောင်းဆိုချက်၏ body ကိုသာ အသေးစိတ် tab များတွင် ဖော်ပြရန် ပြင်ဆင်သည် (1MB body 1000 ခုကို render လုပ်ခြင်းမှ ရှောင်ရှားသည်)

- 48px rail အဖြစ် ခေါက်သိမ်းနိုင်သည် (အိုင်ကွန်သာပါဝင်သည်)၊ ချဲ့ရန် rail ရှိ row တစ်ခုကို နှိပ်ပါ

## §4 LLM-aware လုပ်ဆောင်ချက်များ

### 4.1 အမျိုးအစား ခွဲခြားကိရိယာ (`src/mitm/inspector/kindDetector.ts`)

တောင်းဆိုချက်တစ်ခုစီကို အချက်ပြမှု 4 မျိုး အသုံးပြု၍ `"llm"`, `"app"` သို့မဟုတ် `"unknown"` အဖြစ် ခွဲခြားသည်-

1. **Host registry** — လူသိများသော LLM API hostname ~18 ခု (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot စသည်)
2. **Path pattern များ** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses` စသည်
3. **Body ပုံစံ** — `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input` field များကို စစ်ဆေးသိရှိသည်
4. **User-agent အရိပ်အမြွက်များ** — UA string ထဲရှိ `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor`

Mode 2 မှတစ်ဆင့် ထည့်သွင်းထားသော custom host များသည် form input မှ ၎င်းတို့၏ `kind` ကို ဆက်ခံသည် (မူလတန်ဖိုးမှာ `"custom"` ဖြစ်သည်)။

### 4.2 SSE ပေါင်းစည်းကိရိယာ (`src/mitm/inspector/sseMerger.ts`)

**သီးခြား clean-room အကောင်အထည်ဖော်မှု။** Event ခွဲခြမ်းစိတ်ဖြာခြင်းသည်
[WHATWG server-sent events algorithm](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream) ကို လိုက်နာပြီး၊
ပြန်လည်တည်ဆောက်ခြင်းသည် အများပြည်သူသုံး [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) နှင့်
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent)
streaming schema များကို လိုက်နာသည်။

Raw SSE delta event များမှ နောက်ဆုံး assistant message ကို ပြန်လည်တည်ဆောက်သည်-

- **Anthropic**: `content_block_delta` ကို index အလိုက် စုစည်းသည်၊ `text_delta`, `input_json_delta` (tool call များ), `thinking_delta` တို့ကို ကိုင်တွယ်သည်
- **OpenAI**: Chat Completions ၏ choice/tool call များနှင့် Responses API ၏ output item များကို index အလိုက် စုစည်းသည်
- **Gemini**: `candidates[i].content.parts` ကို စုစည်းသည်
- **Unknown**: raw event များကို မူလအတိုင်း ပြန်ပေးသည်

Response tab တွင် **"Raw events ↔ Merged"** toggle တစ်ခုကို ပြသသည်။

### 4.3 Conversation normalizer (`src/mitm/inspector/conversationNormalizer.ts`)

**သီးခြား clean-room အကောင်အထည်ဖော်မှု။** Normalization ကို local black-box
contract များနှင့် အများပြည်သူသုံး OpenAI, Anthropic နှင့် Gemini message schema များအပေါ် အခြေခံ၍ သတ်မှတ်ထားသည်၊ upstream
implementation source ကို အသုံးမပြုပါ။

Render မလုပ်မီ OpenAI, Anthropic နှင့် Gemini message format များကို တစ်ခုတည်းသော `NormalizedConversation` အဖြစ် ပြောင်းလဲသည်-

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // request body မှ messages / contents / prompt
  response: NormalizedTurn[]; // assistant response (sseMerger မှတစ်ဆင့် ပေါင်းစည်းထားသည်)
  contextKey: string | null; // SHA-256 system-prompt fingerprint
}
```

Block အမျိုးအစားများ- `text`, `tool_use`, `tool_result`။ Conversation tab သည် provider မည်သည့်အရာဖြစ်စေ ဤပုံစံကို အသုံးပြုသည်။

### 4.4 Context key အရောင်သတ်မှတ်ခြင်း (`src/mitm/inspector/contextKey.ts`)

- System prompt (ပထမဆုံး `role:system` message သို့မဟုတ် `system` field သို့မဟုတ် Gemini `systemInstruction`) ၏ `SHA-256` ကို တွက်ချက်သည်
- စာလုံး 12 လုံးပါ hex prefix (`"a3f9c2..."`) ကို ပြန်ပေးသည်
- Frontend သည် ဘယ်ဘက် border bar အတွက် key ကို တသမတ်တည်းဖြစ်သော HSL အရောင်တစ်ခုသို့ ချိတ်ဆက်သတ်မှတ်သည်
- **"တူညီသော context" filter**: `ctx #a3f` chip ကို နှိပ်ခြင်းဖြင့် တူညီသော fingerprint ရှိသည့် request များကိုသာ ပြသရန် filter တစ်ခု ထည့်သွင်းသည်

၎င်းကြောင့် agent session တစ်ခုတည်းအတွင်း လုပ်ဆောင်နေသော မတူညီသည့် "persona" များ သို့မဟုတ် task များကို မြင်သာစွာ အလွယ်တကူ ခွဲခြားနိုင်သည်။

### 4.5 LLM metadata ထုတ်ယူခြင်း

LLM request များအတွက် LLM Details tab သည် အောက်ပါတို့ကို ထုတ်ယူသည်-

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // request body သို့မဟုတ် response မှ
  messages: number; // turn အရေအတွက်
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // SSE response ဖြစ်လျှင် true
  mappedTo: string | null; // x-omniroute-mapped header
  costEstimateUsd: number | null; // OmniRoute ဈေးနှုန်းပေါ် အခြေခံ၍ ခန့်မှန်းထားသော ကုန်ကျစရိတ်
}
```

### 4.6 လက်ရှိဆောင်ရွက်နေသော request များအတွက် live filter

Request ၏ `status` field သည် `number | "in-flight" | "error"` ဖြစ်သည် — request စတင်သည်နှင့် entry တစ်ခုကို
`"in-flight"` အဖြစ် ထည့်သွင်းပြီး response (သို့မဟုတ် error) ရောက်ရှိလာသောအခါ **မူလနေရာတွင်ပင် အပ်ဒိတ်လုပ်သည်**။
Toolbar ၏ **"Live"** toggle
(`liveOnly`, i18n key `trafficInspector.liveOnly`) သည် list ကို
`status === "in-flight"` ဖြစ်သော entry များသာ ပါဝင်စေရန် ကန့်သတ်ပေးပြီး၊ ဖွင့်ထားဆဲ connection များကို အချိန်နှင့်တစ်ပြေးညီ စောင့်ကြည့်နိုင်စေသည်။

Filter သည်
`src/lib/inspector/matchesTrafficFilter.ts` အတွင်းရှိ client-side predicate သက်သက်ဖြစ်သည်-

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

Toggle state သည် `useTrafficFilters` (inspector dashboard hook များ) တွင် ရှိပြီး
အခြား filter များ (profile, host, agent, source, status, context) နှင့် ပေါင်းစပ်အလုပ်လုပ်သည်။

### 4.7 Process ချိတ်ဆက်သတ်မှတ်ခြင်း (Linux)

Linux တွင် ကြားဖြတ်ဖမ်းယူထားသော request တစ်ခုစီကို **မူလစတင်ပေးပို့သည့် local
process** နှင့် ချိတ်ဆက်သတ်မှတ်နိုင်သည်။ Optional field နှစ်ခုကို `InterceptedRequest` ထဲသို့ ထည့်သွင်းထားသည်-

```ts
pid?: number;          // မူလစတင်ပေးပို့သည့် process id (Linux တွင်သာ)
processName?: string;  // မူလစတင်ပေးပို့သည့် process name (Linux တွင်သာ)
```

`src/mitm/inspector/processAttribution.ts` သည် connection ၏ _client_
ephemeral port ကို အောက်ပါအတိုင်း PID + name နှင့် ချိတ်ဆက်သတ်မှတ်သည်-

1. Port အတွက် socket inode ကို ရှာဖွေရန် `/proc/net/tcp` နှင့် `/proc/net/tcp6` ကို ဖတ်သည်
   (`parseProcNetTcpForInode` သည် fixture ဖြင့် စမ်းသပ်နိုင်သော သီးသန့် parser ဖြစ်သည်)။
2. `socket:[<inode>]` သို့ ညွှန်ပြသည့် symlink ကို ရှာဖွေရန် `/proc/<pid>/fd/` ကို စစ်ဆေးသည်။
3. `/proc/<pid>/comm` မှ process name ကို ဖတ်သည်။

1-second TTL cache သည် ဝန်များနေချိန်တွင် procfs စစ်ဆေးမှု ကုန်ကျစရိတ်ကို ကန့်သတ်ပေးသည်။ Attribution သည်
**အတတ်နိုင်ဆုံးကြိုးပမ်းသည့်ပုံစံ** ဖြစ်သည် — မည်သည့် မအောင်မြင်မှုမဆို `null` အဖြစ် ပြေလည်သွားပြီး capture ကို မည်သည့်အခါမျှ မပိတ်ဆို့ပါ။ macOS/Windows တွင် function သည် `null` ကို ပြန်ပေးသည် (stub ဖြစ်ပြီး `lsof`/`GetExtendedTcpTable`
ပံ့ပိုးမှုကို နောက်ဆက်တွဲအဖြစ် ထည့်သွင်းမည်)။

## §5 ဆက်ရှင်များ

### 5.1 ဆက်ရှင်တစ်ခုကို မှတ်တမ်းတင်ခြင်း

1. ကိရိယာဘားရှိ **"● ဆက်ရှင်ကို မှတ်တမ်းတင်ရန်"** ကို နှိပ်ပါ → အမည်တစ်ခု ထည့်ပါ (မထည့်လည်းရသည်)
2. တိုက်ရိုက် tail သည် ပုံမှန်အတိုင်း ဆက်လက်လုပ်ဆောင်နေမည်ဖြစ်ပြီး အနီရောင် မှိတ်တုတ်မှိတ်တုတ် အညွှန်းက `◉ REC · <name> · 00:42 · 23 reqs` ဟု ပြသမည်
3. **"⏹ ရပ်ရန်"** ကို နှိပ်ပါ → ဆက်ရှင် snapshot ကို `inspector_sessions` + `inspector_session_requests` တွင် သိမ်းဆည်းမည်

### 5.2 မှတ်တမ်းတင်ထားသော ဆက်ရှင်ကို ကြည့်ရှုခြင်း

ကိရိယာဘားရှိ **ဆက်ရှင်များ** dropdown တွင် သိမ်းဆည်းထားသော ဆက်ရှင်များကို စာရင်းပြုထားသည်။ တစ်ခုကို ရွေးချယ်သည့်အခါ-

- ဆက်ရှင်၏ snapshot (ရပ်တန့်ထားသော အခြေအနေ) ကို ဖွင့်ပေးမည်
- Banner တစ်ခုတွင် `မှတ်တမ်းတင်ထားသော ဆက်ရှင် "<name>" ကို ကြည့်ရှုနေသည် — [တိုက်ရိုက်သို့ ပြန်သွားရန်]` ဟု ပြသမည်
- Recharts အနှစ်ချုပ်ကိန်းဂဏန်းများပါဝင်သော Stats tab ကို အသုံးပြုနိုင်လာမည်

### 5.3 ထုတ်ယူနိုင်သော ဖော်မတ်များ

ဆက်ရှင်တစ်ခုစီကို အောက်ပါအတိုင်း ထုတ်ယူနိုင်သည်-

| ဖော်မတ်                    | အသုံးပြုပုံ                                                                                                        |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **HAR** (HTTP Archive 1.2) | Chrome DevTools၊ Charles၊ Fiddler တို့နှင့် တွဲဖက်အသုံးပြုနိုင်သည် — အော့ဖ်လိုင်း ခွဲခြမ်းစိတ်ဖြာရန် import လုပ်ပါ |
| **JSONL**                  | စာကြောင်းတစ်ကြောင်းလျှင် `InterceptedRequest` တစ်ခု — `llm-interceptor` ဖော်မတ်နှင့် တွဲဖက်အသုံးပြုနိုင်သည်        |

`GET /api/tools/traffic-inspector/sessions/{id}/export.har` မှတစ်ဆင့် သို့မဟုတ် Sessions dropdown ရှိ ⬇ ခလုတ်ဖြင့် ထုတ်ယူပါ။

## §6 လုံခြုံရေး

Traffic Inspector သည် authorization header များနှင့် request body များအပါအဝင် **ကြားဖြတ်ဖမ်းယူထားသော HTTPS traffic အားလုံးကို** ပြသသည်။ အောက်ပါ ထိန်းချုပ်မှုများကို အသုံးပြုထားသည်-

| ထိန်းချုပ်မှု                           | အသေးစိတ်အချက်အလက်များ                                                                                                                                                                                  |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **LOCAL_ONLY**                          | Route များအားလုံးနှင့် WebSocket endpoint ကို loopback မှသာ ဝင်ရောက်နိုင်သည် (`routeGuard.ts` တွင် auth မတိုင်မီ အတည်ပြုကန့်သတ်ထားသည်)                                                                 |
| **လျှို့ဝှက်ချက် ဖုံးကွယ်ခြင်း**        | Linear `maskSecret()` scanner သည် RFC 6750 Bearer အထောက်အထားများ၊ provider prefix ပါသော key များနှင့် ရှည်လျားသော opaque token များကို `TrafficBuffer.push()` မတိုင်မီ ဖယ်ရှားဖုံးကွယ်ပေးသည်           |
| **Body အရွယ်အစား ကန့်သတ်ချက်**          | `INSPECTOR_MAX_BODY_KB` ထက်ကြီးသော body များကို (မူလသတ်မှတ်ချက် 1024 KB) `"(စွမ်းဆောင်ရည်အတွက် ဖြတ်တောက်ထားသည်)"` အသိပေးချက်ဖြင့် ဖြတ်တောက်ထားမည်                                                      |
| **Header သန့်စင်ခြင်း**                 | အမည်များကို စာလုံးအသေးပြောင်းထားသည်၊ framing/hop-by-hop နှင့် proxy-auth header များကို ဖယ်ရှားထားသည်၊ cookie များကို အပြည့်အဝ ဖုံးကွယ်ထားသည်၊ အထောက်အထားတန်ဖိုးများကို `maskSecret()` သို့ လွှဲပေးသည် |
| **CSP**                                 | ထည့်သွင်းထားသော response body များမှတစ်ဆင့် XSS ဖြစ်ပေါ်ခြင်းကို ကာကွယ်ရန် Traffic Inspector စာမျက်နှာများတွင် တင်းကျပ်သော Content Security Policy ကို အသုံးပြုထားသည်                                  |
| **မူလအားဖြင့် အမြဲတမ်းမသိမ်းဆည်းခြင်း** | `TrafficBuffer` သည် memory အတွင်း၌သာရှိပြီး server ပြန်လည်စတင်သည့်အခါ ပျောက်ဆုံးသွားသည်။ ဆက်ရှင်များကို အတိအလင်း မှတ်တမ်းတင်သည့်အခါမှသာ အမြဲတမ်း သိမ်းဆည်းထားသည်                                       |

### အသုံးချထားသော မဖြစ်မနေလိုက်နာရမည့် စည်းမျဉ်းများ

| စည်းမျဉ်း                         | အသုံးချပုံ                                                                                         |
| --------------------------------- | -------------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | Traffic Inspector route များမှ HTTP error response အားလုံးကို သန့်စင်ထားသည်                        |
| **#15 + #17** `isLocalOnlyPath()` | `/api/tools/traffic-inspector/` သည် LOCAL_ONLY + SPAWN_CAPABLE ဖြစ်သည် (system proxy command များ) |

### သိရှိထားသော ကန့်သတ်ချက်များ

- **စနစ်တစ်ခုလုံး အကျုံးဝင်သော proxy mode** သည် VPN client များနှင့် SSO အပါအဝင် စက်ပေါ်ရှိ application အားလုံးကို သက်ရောက်စေသည်။ auto-disable timer နှင့်အတူ အမြဲတမ်း အသုံးပြုပါ။ မျှဝေသုံးစွဲသော စက်များတွင် မသုံးပါနှင့်။
- **CONNECT tunnel HTTPS**: TLS interception ကို ဖွင့်မထားပါက Mode 3 (HTTP_PROXY) သည် HTTPS destination များအတွက် tunnel metadata ကိုသာ ဖမ်းယူသည်။ ၎င်းသည် ရည်ရွယ်ချက်ရှိရှိ ဒီဇိုင်းပြုလုပ်ထားခြင်းဖြစ်သည် — ထို app များက AgentBridge cert ကို ယုံကြည်စိတ်ချရသည်ဟု လက်မခံထားပါက transparent capture ပြုလုပ်ခြင်းသည် TLS verification ကို ပျက်စီးစေမည်ဖြစ်သည်။
- **Component အချို့ရှိ hardcoded string များ**: UI component အချို့ (F7/F8) တွင် i18n key များဖြင့် မလွှမ်းခြုံရသေးသော hardcoded string အနည်းငယ်ရှိသည်။ ၎င်းတို့ကို i18n gap report တွင် သိရှိထားသော ကန့်သတ်ချက်အဖြစ် မှတ်တမ်းတင်ထားပြီး နောက်ဆက်တွဲ pass တစ်ခုတွင် ပြောင်းရွှေ့မည်ဖြစ်သည်။ သက်ရောက်မှုရှိသော string များသည် လုပ်ဆောင်ချက်အရ အသုံးပြုရန်အတွက် ဘာသာပြန်ရန်မလိုအပ်သော UI အလှဆင် label များဖြစ်သည်။

## §7 ပြဿနာဖြေရှင်းခြင်း

### WebSocket ချိတ်ဆက်မှုပြတ်တောက်ခြင်း

တိုက်ရိုက် tail တွင် "ချိတ်ဆက်မှုပြတ်တောက်သွားသည်" ဟု ပြသပါက-

1. ဆာဗာ ဆက်လက်လည်ပတ်နေကြောင်း စစ်ဆေးပါ- `GET /api/tools/traffic-inspector/capture-modes`
2. စာမျက်နှာကို ပြန်တင်ပါ — WebSocket သည် ပြန်လည်ချိတ်ဆက်ပြီး snapshot အသစ်တစ်ခုကို လက်ခံရရှိပါမည်
3. ဆာဗာကို ပြန်လည်စတင်ထားပါက memory အတွင်းရှိ buffer ကို ရှင်းလင်းပြီးဖြစ်သည် — session တစ်ခုအဖြစ် မှတ်တမ်းတင်ထားခြင်းမရှိပါက entry အဟောင်းများ ပျောက်ဆုံးသွားပါမည်

### Port 8080 ပဋိပက္ခ

HTTP_PROXY mode ကို စတင်၍မရပါက-

```bash
lsof -i :8080    # process ကို ရှာပါ
```

Port ကို ပြောင်းပါ-

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### System proxy ကို မူလအခြေအနေသို့ ပြန်မထားနိုင်ခြင်း

System-wide proxy mode အသုံးပြုနေစဉ် OmniRoute ရပ်တန့်ပျက်စီးသွားပါက-

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

DB state က proxy အသုံးပြုနေခဲ့ကြောင်း ဖော်ပြသည်ကို dashboard က တွေ့ရှိပါက နောက်တစ်ကြိမ် load လုပ်သည့်အခါ "System proxy ကို မူလအခြေအနေသို့ ပြန်ထားရန်" ရွေးချယ်မှုကိုလည်း ပေးပါမည်။

### Buffer ပြည့်ခြင်း

Buffer သည် `INSPECTOR_BUFFER_SIZE` (မူလတန်ဖိုး 1000) သို့ ရောက်သည့်အခါ entry အသစ်များသည် အဟောင်းဆုံး entry များကို ဖယ်ထုတ်၍ အစားထိုးပါမည်။ အရေးကြီးသော request များ ပျောက်ဆုံးနေပါက-

- `INSPECTOR_BUFFER_SIZE` ကို တိုးပါ (ဥပမာ 5000) — သိမ်းဆည်းထားနိုင်ချိန် ပိုရရန် memory ကို ပိုမိုအသုံးပြုပါမည်
- သက်ဆိုင်ရာ အချိန်အပိုင်းအခြားကို DB တွင် အမြဲတမ်းသိမ်းဆည်းရန် session တစ်ခုကို မှတ်တမ်းတင်ပါ
