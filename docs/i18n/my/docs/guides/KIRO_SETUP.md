ဤလမ်းညွှန်တွင် Kiro (AWS မှ လက်ခံဆောင်ရွက်ပေးထားသော AI ကုဒ်ရေးသားမှု အကူအညီပေးစနစ်) အကောင့်များကို OmniRoute သို့ ထည့်သွင်းပုံကို ဖော်ပြထားပြီး၊ session ပဋိပက္ခများ မဖြစ်ပေါ်စေဘဲ အကောင့်များစွာကို တစ်ပြိုင်နက် အသုံးပြုနိုင်ရေးကို အဓိကထား ရှင်းလင်းထားသည်။

---

## နောက်ခံအကြောင်းအရာ- Kiro အကောင့်များ ပဋိပက္ခဖြစ်နိုင်သည့် အကြောင်းရင်း

Kiro ၏ backend သည် အသုံးပြုနေဆဲ session များကို ခြေရာခံရန် AWS SSO OIDC client registration များကို အသုံးပြုသည်။
အရေးကြီးသော ကန့်သတ်ချက်မှာ- **OIDC client registration တစ်ခုစီသည် တစ်ချိန်လျှင် အသုံးပြုနေဆဲ session တစ်ခုကိုသာ ပံ့ပိုးပေးနိုင်သည်**။ ဒုတိယ device သို့မဟုတ် အသုံးပြုသူက တူညီသော registered client ကို အသုံးပြုပြီး authentication ပြုလုပ်သည့်အခါ backend သည် ပထမအကောင့်၏ refresh token ကို ပျက်ပြယ်စေသည်။

၎င်းသည် အခြား Kiro အကောင့်တစ်ခု ဝင်ရောက်ထားပြီးသား စက်ပေါ်တွင် `kiro-cli login` ကို လုပ်ဆောင်သည့်အခါ ပြဿနာဖြစ်စေသော ယန္တရားနှင့် တူညီသည် — အသစ်ဝင်ရောက်ခြင်းက ပထမအကောင့်၏ token ကို ရုပ်သိမ်းလိုက်သည်။

---

## OmniRoute က ဤပြဿနာကို ဖြေရှင်းပုံ (v3.8.0+)

v3.8.0 မှစတင်၍ OmniRoute သည် Kiro connection တစ်ခုစီကို import လုပ်သည့်အခါ `registerClient()` (AWS SSO OIDC) ကို ခေါ်ဆိုသည်။ ထို့ကြောင့် OmniRoute connection တစ်ခုစီတွင် ၎င်းအတွက် သီးသန့် OIDC client registration ရရှိသည်။ Client registration တစ်ခုစီသည် သီးခြားလွတ်လပ်သောကြောင့် အကောင့်တစ်ခုကို refresh ပြုလုပ်ခြင်း သို့မဟုတ် authentication ပြန်လည်ပြုလုပ်ခြင်းသည် အခြားမည်သည့်အကောင့်၏ refresh token ကိုမျှ သက်ရောက်မှုမရှိစေပါ။

ဤသီးခြားခွဲထားမှုသည် refresh-token import နည်းလမ်းများနှင့် သက်ဆိုင်ပြီး API-key authentication သည် OIDC refresh session များကို လုံးဝအသုံးမပြုပါ-

| Import နည်းလမ်း                                             | သီးခြားခွဲထားမှု အခြေအနေ                                                                                                         |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| AWS Builder ID / IDC device-code flow                       | device-code flow ကို စတင်မိတ်ဆက်ကတည်းက သီးခြားခွဲထားသည်                                                                          |
| **Import Token** (refresh token ကို ကိုယ်တိုင်ကူးထည့်ခြင်း) | v3.8.0 မှစ၍ သီးခြားခွဲထားသည်                                                                                                     |
| **Google / GitHub social login**                            | v3.8.0 မှစ၍ သီးခြားခွဲထားသည်                                                                                                     |
| **Auto-Import** (kiro-cli SQLite)                           | v3.8.0 မှစ၍ သီးခြားခွဲထားသည် (SQLite လမ်းကြောင်းသည် ယခင်ကတည်းက သီးခြားဖြစ်ပြီး၊ SSO-cache fallback ကိုလည်း ယခု သီးခြားခွဲထားသည်) |
| **API Key** (သက်တမ်းရှည် CodeWhisperer key)                 | Refresh session မရှိပါ၊ key ကို စစ်ဆေးအတည်ပြုပြီး bearer credential အဖြစ် သိမ်းဆည်းသည်                                           |

## v3.8.0 မတိုင်မီ ဖန်တီးထားသော Connection များအတွက် ပြောင်းရွှေ့ခြင်းဆိုင်ရာ မှတ်ချက်

v3.8.0 မတိုင်မီ import လုပ်ထားသော connection များတွင် သီးသန့် OIDC client registration ကို `providerSpecificData` အတွင်း သိမ်းဆည်းထားခြင်း မရှိပါ။ ဤ connection များသည် ဆက်လက်အလုပ်လုပ်နိုင်သော်လည်း မျှဝေထားသော social-auth refresh endpoint ကို အသုံးပြုသောကြောင့် ထိုကဲ့သို့သော connection နှစ်ခုသည် တစ်ခုနှင့်တစ်ခုကို ပျက်ပြယ်စေနိုင်ဆဲ ဖြစ်သည်။

**သီးခြားခွဲထားမှု ရရှိရန်-** **Dashboard → Providers** မှ connection အဟောင်းကို ဖျက်ပြီး ပံ့ပိုးထားသော import flow တစ်ခုခုကို အသုံးပြု၍ ပြန်လည် import လုပ်ပါ။ အသစ်ဖန်တီးသော connection အားလုံးသည် ၎င်းတို့၏ကိုယ်ပိုင် client registration ကို အလိုအလျောက် ရရှိမည်ဖြစ်သည်။

## Kiro အကောင့်နှစ်ခုကို အတူတကွ ထည့်သွင်းခြင်း

### ကြိုတင်လိုအပ်ချက်များ

- OmniRoute v3.8.0 သို့မဟုတ် နောက်ပိုင်းဗားရှင်း။
- အလုပ်လုပ်နေသော Kiro အကောင့်တစ်ခု (အီးမေးလ် + စကားဝှက်၊ Google သို့မဟုတ် GitHub login)။
- လိုအပ်ပါက ဒုတိယ Kiro အကောင့်တစ်ခု။

### အဆင့် 1- ပထမအကောင့်ကို import လုပ်ပါ

1. **Dashboard → Providers → Add Provider → Kiro** ကို ဖွင့်ပါ။
2. အောက်ပါနည်းလမ်းများထဲမှ တစ်ခုကို ရွေးချယ်ပါ-
   - **Import Token** — `aorAAAAAG` ဖြင့် စတင်သော refresh token ကို ကူးထည့်ပါ။
   - **API Key** — သက်တမ်းရှည် Kiro / CodeWhisperer API key ကို ကူးထည့်ပါ။
   - **Google / GitHub login** — browser အတွင်း OAuth flow ကို အပြီးသတ်ပါ။
   - **Auto-Import** — ခလုတ်ကို နှိပ်ပါ၊ OmniRoute သည် local kiro-cli database သို့မဟုတ် `~/.aws/sso/cache` မှ credential များကို ဖတ်ယူမည်။
3. Connection ကို သိမ်းဆည်းမည်။ Refresh-token flow များသည် သီးသန့် OIDC client တစ်ခုကို အလိုအလျောက် register လုပ်သည်။ API-key flow များသည် key ကို AWS ဖြင့် စစ်ဆေးအတည်ပြုပြီး refresh token ကို သိမ်းဆည်းခြင်းမပြုပါ။

### အဆင့် 2- ဒုတိယအကောင့်ကို import လုပ်ပါ

ဒုတိယအကောင့်အတွက် အဆင့် 1 ကို ထပ်မံလုပ်ဆောင်ပါ။ Import တစ်ခုစီက သီးခြား OIDC client registration တစ်ခုကို ဖန်တီးသောကြောင့် connection နှစ်ခုသည် အပြည့်အဝ သီးခြားခွဲထားမည်ဖြစ်သည်။

### အဆင့် 3- Connection နှစ်ခုစလုံး အသုံးပြုနေဆဲဖြစ်ကြောင်း စစ်ဆေးပါ

1. **Dashboard → Providers** — Kiro connection နှစ်ခုစလုံးသည် **Active** အခြေအနေကို ပြသသင့်သည်။
2. **Dashboard → Health** — connection နှစ်ခုစလုံးသည် ၎င်းတို့၏ token health check ကို အောင်မြင်သင့်သည်။

### အဆင့် 4- အကောင့်များအကြား route လုပ်ရန် combo တစ်ခုကို အသုံးပြုပါ

Load-balance လုပ်ရန် သို့မဟုတ် တစ်ခုမအောင်မြင်ပါက အခြားတစ်ခုသို့ fallback လုပ်ရန် connection နှစ်ခုစလုံးကို target များအဖြစ် ထည့်သွင်းထားသော combo တစ်ခုကို ဖန်တီးပါ-

```
kiro/kiro-dev → kiro/kiro-pro
```

Combo configuration အတွက် [FEATURES.md](./FEATURES.md) နှင့် routing documentation ကို ကြည့်ပါ။

## လုပ်ငန်းသုံး / IDC အသုံးပြုသူများ

AWS IAM Identity Center (IDC) အကောင့်များအတွက် **ဒက်ရှ်ဘုတ် → ပံ့ပိုးသူများ → Kiro → စက်ကုဒ်** မှ **AWS Builder ID / IDC device-code**
လုပ်ငန်းစဉ်ကို အသုံးပြုပါ။ device-code လုပ်ငန်းစဉ်သည် အစဉ်အမြဲ အပြည့်အဝ သီးခြားခွဲထားပါသည်။
ဤချိတ်ဆက်မှုများအတွက် ထပ်မံတင်သွင်းရန် မလိုအပ်ပါ။

မူလသတ်မှတ်ထားသော AWS region မဟုတ်သည့် region တွင် အသုံးပြုနေသော လုပ်ငန်းသုံးအသုံးပြုသူများသည်
Import Token API မှတစ်ဆင့် တင်သွင်းသည့်အခါ region ကို သတ်မှတ်နိုင်သည်-

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

`region` အကွက်ကို ချန်လှပ်ထားပါက မူလတန်ဖိုးအဖြစ် `us-east-1` ကို အသုံးပြုသည်။

## API-Key တင်သွင်းမှုလုပ်ငန်းစဉ်

API-key အထောက်အထားစစ်ဆေးခြင်းသည် သက်တမ်းရှည်အသုံးပြုနိုင်သော Kiro / AWS CodeWhisperer bearer အထောက်အထားများအတွက် ဖြစ်သည်။ ၎င်းသည်
OAuth refresh ကို အသုံးမပြုသဖြင့် မျှဝေထားသော OIDC session ပျက်ပြယ်မှုကို ရှောင်ရှားနိုင်သည်။

### ဒက်ရှ်ဘုတ်

1. **ဒက်ရှ်ဘုတ် -> ပံ့ပိုးသူများ -> Kiro** ကို ဖွင့်ပါ။
2. **API Key** ကို ရွေးချယ်ပါ။
3. API key နှင့် ရွေးချယ်နိုင်သော AWS region (မူလတန်ဖိုးမှာ `us-east-1`) ကို ထည့်သွင်းပါ။
4. OmniRoute သည် key ကို စစ်ဆေးအတည်ပြုပြီး ချိတ်ဆက်မှုကို သိမ်းဆည်းသည်။

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### အတွင်းပိုင်း သဘောတူညီချက်

API route သည် `KiroService.validateApiKey()` ကို ခေါ်ဆိုခြင်းဖြင့် key ကို စစ်ဆေးအတည်ပြုသည်။ ၎င်းသည်
region နှင့် ကိုက်ညီသော CodeWhisperer/Amazon Q endpoint တွင် `ListAvailableProfiles` ကို အသုံးပြုပြီး `profileArn` တစ်ခုကို သတ်မှတ်ရယူသည်။

သိမ်းဆည်းထားသော ချိတ်ဆက်မှုတွင် အောက်ပါတို့ကို အသုံးပြုသည်-

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

အလုပ်လုပ်နေချိန်တွင် `KiroExecutor.buildHeaders()` သည် key ကို
`Authorization: Bearer <key>` အဖြစ် ပို့ပြီး `tokentype: API_KEY` ကို ထည့်သွင်းသည်။ Quota/profile ခေါ်ဆိုမှုများသည်လည်း
တူညီသော အမှတ်အသားကို အသုံးပြုသဖြင့် AWS သည် bearer ကို OIDC သို့မဟုတ် လူမှုကွန်ရက် access token အဖြစ်မဟုတ်ဘဲ
သက်တမ်းရှည် API key အဖြစ် သတ်မှတ်သည်။

## OIDC Client သက်တမ်းကုန်ဆုံးမှု

AWS SSO OIDC public client များသည် ပုံမှန်အားဖြင့် ရက် 90 ကြာပြီးနောက် သက်တမ်းကုန်ဆုံးသည်
(`clientSecretExpiresAt`)။ OmniRoute သည် စောင့်ကြည့်လေ့လာနိုင်ရန် ဤ timestamp ကို `providerSpecificData`
တွင် သိမ်းဆည်းထားသည်။ ချိတ်ဆက်မှုတစ်ခုသည် ရက် 90 ခန့်အကြာတွင် refresh မလုပ်နိုင်တော့ပါက
OIDC client registration အသစ်တစ်ခု ရရှိရန် ချိတ်ဆက်မှုကို ပြန်လည်တင်သွင်းပါ။ သက်တမ်းကုန်ဆုံးချိန်တွင်
အလိုအလျောက် ပြန်လည်မှတ်ပုံတင်ခြင်းကို အနာဂတ်တိုးတက်မှုအဖြစ် မှတ်တမ်းတင်ထားသည်။

API-key ချိတ်ဆက်မှုများသည် AWS SSO OIDC မှတစ်ဆင့် refresh မလုပ်သောကြောင့် OIDC client သက်တမ်းကုန်ဆုံးမှု
မရှိပါ။

## ပြဿနာဖြေရှင်းခြင်း

### ဒုတိယအကောင့်သည် အမြဲတမ်း အကောင့်မှ ထွက်နေသည်

- **ဒက်ရှ်ဘုတ် → ပံ့ပိုးသူများ** တွင် ချိတ်ဆက်မှုနှစ်ခုလုံးကို စစ်ဆေးပြီး တစ်ခုစီ၏ raw JSON တွင် null မဟုတ်သော
  `clientId` တစ်ခု ပြသထားကြောင်း အတည်ပြုပါ (အချက်အလက် အိုင်ကွန်မှတစ်ဆင့် ကြည့်နိုင်သည်)။ ချိတ်ဆက်မှုတစ်ခုခုတွင်
  `clientId` မရှိပါက ၎င်းကို v3.8.0 မတိုင်မီ တင်သွင်းထားခြင်းဖြစ်သည် — ပြန်လည်တင်သွင်းပါ။

### "Token စစ်ဆေးအတည်ပြုမှု မအောင်မြင်ပါ" ဟု ပြသပြီး တင်သွင်းမှု မအောင်မြင်ခြင်း

- refresh token သည် `aorAAAAAG` ဖြင့် စတင်ကြောင်း သေချာပါစေ။
- OmniRoute သည် `https://oidc.us-east-1.amazonaws.com` (သို့မဟုတ် စီစဉ်သတ်မှတ်ထားသော
  region) ကို ဆက်သွယ်နိုင်ကြောင်း သေချာပါစေ။ လုပ်ငန်းသုံး proxy နောက်ကွယ်တွင် ရှိနေပါက
  **ဒက်ရှ်ဘုတ် → ဆက်တင်များ → Proxy များ** တွင် ပံ့ပိုးသူအဆင့် proxy တစ်ခုကို သတ်မှတ်ပါ။

### API-key တင်သွင်းမှု မအောင်မြင်ခြင်း

- key သည် refresh token မဟုတ်ဘဲ Kiro / CodeWhisperer API key ဖြစ်ကြောင်း အတည်ပြုပါ။
- AWS region သည် key/account နှင့် ကိုက်ညီကြောင်း အတည်ပြုပါ။ `us-east-1` သည် မူလတန်ဖိုးဖြစ်သည်။
- key သည် `ListAvailableProfiles` ကို ခေါ်ဆိုနိုင်ရမည်။ မဟုတ်ပါက OmniRoute သည် လိုအပ်သော
  `profileArn` ကို သတ်မှတ်ရယူနိုင်မည် မဟုတ်ပါ။

အခြားပြဿနာများအတွက် ပင်မ [TROUBLESHOOTING.md](./TROUBLESHOOTING.md) ကို ကြည့်ပါ။
