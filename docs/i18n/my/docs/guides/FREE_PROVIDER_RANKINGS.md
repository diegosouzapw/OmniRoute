> **အကျဉ်းချုပ်**: OmniRoute သည် ၎င်း၏ **အခမဲ့** provider များကို model အရည်အသွေးအလိုက် **Arena AI
> (LMArena ပုံစံ) ELO score များ** အသုံးပြု၍ အဆင့်သတ်မှတ်ပါသည်။ သင့်လုပ်ငန်းအတွက် အကောင်းဆုံး model များကို
> ပံ့ပိုးပေးသည့် အခမဲ့ provider များကို ကြည့်ရန် dashboard ရှိ **Free Provider Rankings** စာမျက်နှာကို ဖွင့်ပါ —
> အားလုံးကို ခြုံငုံ၍ဖြစ်စေ၊ အမျိုးအစားအလိုက် (coding, review, documentation, debugging) စစ်ထုတ်၍ဖြစ်စေ ကြည့်နိုင်ပါသည်။

## ၎င်းသည် အဘယ်အရာဖြစ်သနည်း

OmniRoute တွင် provider 329 ခုကို စာရင်းသွင်းထားပြီး၊ ၎င်းတို့အနက် catalog entry 155 ခုကို **free/no-auth**
(no-auth၊
free-tier OAuth သို့မဟုတ် free-tier API key —
[Free Tiers Guide](../getting-started/FREE-TIERS-GUIDE.md) နှင့်
[Free Tiers directory](../reference/FREE_TIERS.md) အပြည့်အစုံကို ကြည့်ပါ) ဟု သတ်မှတ်ထားပါသည်။ သို့သော် ပြဿနာမှာ အခမဲ့ provider များ၏
model အရည်အသွေးသည် အလွန်ကွာခြားခြင်းဖြစ်သည်။ ထိပ်တန်း frontier model ကို ပံ့ပိုးသည့် no-auth provider သည်
အရွယ်အစားသေးငယ်သော legacy model ကို ပံ့ပိုးသည့် provider ထက် များစွာပို၍ အသုံးဝင်ပါသည်။

**Free Provider Rankings** သည် အခမဲ့ provider တစ်ခုချင်းစီ၏ catalog ကို
**Arena AI leaderboard** မှ **လူအများပူးပေါင်းပေးထားသော အရည်အသွေး score များ** (လူသားနှစ်သက်မှုအခြေပြု ELO၊ LMArena
chatbot arena ၏ နောက်ကွယ်ရှိ အယူအဆနှင့် တူညီသည်) နှင့် ပေါင်းစပ်ခြင်းဖြင့် "**ဘယ်အခမဲ့ provider က အကောင်းဆုံး model ကို ပေးသလဲ?**" ဆိုသည့် မေးခွန်းကို
ဖြေကြားပေးပါသည်။ ထို့နောက် provider များကို ၎င်းတို့၏ **အကောင်းဆုံး အခမဲ့ model** ၏ စွမ်းဆောင်ရည်အပေါ် အခြေခံ၍ အဆင့်သတ်မှတ်ပါသည်။

အဆင့်သတ်မှတ်ချက်ကို အမှန်တကယ်ရှိသော source သုံးခုမှ တွက်ချက်ပါသည်-

1. အခမဲ့ provider စာရင်းများ — `NOAUTH_PROVIDERS` နှင့် `hasFree` ဟု သတ်မှတ်ထားသော `OAUTH_PROVIDERS` /
   `APIKEY_PROVIDERS` entry များ
   (`src/shared/constants/providers.ts`)။
2. Provider registry မှ provider တစ်ခုချင်းစီ၏ model catalog
   (`open-sse/config/providerRegistry.ts`)။
3. Arena ELO sync engine (`src/lib/arenaEloSync.ts`) က `model_intelligence` DB table တွင်
   သိမ်းဆည်းထားသော ELO မှ ဆင်းသက်လာသည့် task-fit score များ။

ပေါင်းစပ်သည့် logic ကို `src/lib/freeProviderRankings.ts` တွင် ထားရှိပါသည်။

## ဝင်ရောက်အသုံးပြုနည်း

### Dashboard စာမျက်နှာ

Dashboard ကို ဖွင့်ပြီး **Costs → Free Provider Rankings** သို့ သွားပါ၊ သို့မဟုတ် အောက်ပါလမ်းကြောင်းသို့ တိုက်ရိုက်သွားပါ-

```
/dashboard/free-provider-rankings
```

စာမျက်နှာ (`src/app/(dashboard)/dashboard/free-provider-rankings/page.tsx`) တွင် အောက်ပါတို့ကို ပြသထားပါသည်-

- အဆင့်အမြင့်ဆုံး အခမဲ့ provider များ၏ **ထိပ်ဆုံး 3 ခု podium** (🥇 🥈 🥉)။
- **Rank**, **Provider**, **Top Model**,
  **Score**, **Avg Score**, **Models**, **Type** column များပါဝင်သော **အဆင့်သတ်မှတ်ချက်ဇယား** အပြည့်အစုံ။
- **အမျိုးအစား filter button များ**: _အမျိုးအစားအားလုံး_, _မူလ_, _Coding_, _Review_,
  _Documentation_, _Debugging_။

Provider တစ်ခုချင်းစီ၏ **Type** badge သည် ၎င်းကို မည်သို့ အခမဲ့အသုံးပြုနိုင်ကြောင်း ဖော်ပြပါသည်-

| Badge    | အဓိပ္ပာယ်                                        |
| -------- | ------------------------------------------------ |
| `NOAUTH` | အမြဲတမ်း အခမဲ့ဖြစ်ပြီး credential များ မလိုအပ်ပါ |
| `OAUTH`  | အခမဲ့ tier (`hasFree`) ပါဝင်သော OAuth provider   |
| `APIKEY` | အခမဲ့ tier (`hasFree`) ပါဝင်သော API-key provider |

Score များကို ကိန်းဂဏန်းအကြမ်းများအစား လူဖတ်ရှုနားလည်နိုင်သော label များ (ဥပမာ _ထိပ်တန်း_, _အလွန်ကောင်းမွန်_, _အရမ်းကောင်း_,
_ကောင်း_, _ပျမ်းမျှ_) အဖြစ် ပြသထားပါသည်၊ အဘယ်ကြောင့်ဆိုသော် အခြေခံတန်ဖိုးသည် ရာခိုင်နှုန်းမဟုတ်ဘဲ နှိုင်းယှဉ်အဆင့်သတ်မှတ်သည့်
အရည်အသွေးဖြစ်သောကြောင့် ဖြစ်ပါသည်။

### API endpoint

ဤစာမျက်နှာသည် public read endpoint
(`src/app/api/free-provider-rankings/route.ts`) ကို အသုံးပြုထားပါသည်-

```
GET /api/free-provider-rankings
GET /api/free-provider-rankings?category=coding
GET /api/free-provider-rankings?category=coding&limit=20
```

Query parameter များ (Zod ဖြင့် စစ်ဆေးအတည်ပြုထားသည်)-

| Parameter  | အမျိုးအစား | မူလတန်ဖိုး | မှတ်ချက်                                                                                                                      |
| ---------- | ---------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `category` | string     | (မရှိ)     | `default`, `coding`, `review`, `documentation`, `debugging` တို့အနက် တစ်ခု။ ပေါင်းစပ်အဆင့်သတ်မှတ်ချက်အတွက် မထည့်ဘဲ ချန်ထားပါ။ |
| `limit`    | number     | `50`       | `1–100` အကွာအဝေးအတွင်း ကန့်သတ်ထားသည်။                                                                                         |

Response ပုံစံ-

```json
{
  "rankings": [
    {
      "id": "<provider-id>",
      "name": "<provider name>",
      "icon": "<icon>",
      "color": "<hex color>",
      "textIcon": "<short label>",
      "category": "noauth | oauth | apikey",
      "topModel": {
        "modelId": "<registry model id>",
        "modelName": "<model display name>",
        "score": 0.0,
        "eloRaw": 0,
        "confidence": "high | medium | low",
        "category": "<task category>"
      },
      "averageScore": 0.0,
      "modelCount": 0
    }
  ]
}
```

`eloRaw` သည် မူရင်း Arena ELO တန်ဖိုးဖြစ်ပြီး၊ `score` သည် ပုံမှန်ပြုလုပ်ထားသော task-fit တန်ဖိုးဖြစ်သည်
(အောက်တွင် ကြည့်ပါ)။ Score သတ်မှတ်ထားသော model မရှိသည့် provider များကို response မှ ချန်လှပ်ထားပါသည်။

## ရမှတ်များ အလုပ်လုပ်ပုံ

### ရင်းမြစ်: Arena AI leaderboard

Arena ELO စင့်ခ်အင်ဂျင် (`src/lib/arenaEloSync.ts`) သည် Arena AI leaderboard API
(`https://api.wulong.dev/arena-ai-leaderboards/v1/leaderboard`) မှ leaderboard နှစ်ခုဖြစ်သော `text`
နှင့် `code` ကို ရယူသည်။ Leaderboard ထည့်သွင်းချက်တစ်ခုစီတွင် မော်ဒယ်အမည်၊ ထုတ်လုပ်သူ၊ ELO `score`၊ ယုံကြည်မှုကြားကာလနှင့် မဲအရေအတွက်တို့ ပါဝင်သည်။

Leaderboard အမျိုးအစားများကို OmniRoute လုပ်ဆောင်ချက်အမျိုးအစားများနှင့် အောက်ပါအတိုင်း ချိတ်ဆက်ထားသည်-

| Arena leaderboard | OmniRoute လုပ်ဆောင်ချက်အမျိုးအစားများ             |
| ----------------- | ------------------------------------------------- |
| `text`            | `default`, `review`, `documentation`, `debugging` |
| `code`            | `coding`                                          |

### စံညှိခြင်း (လုပ်ဆောင်ချက်နှင့် ကိုက်ညီမှုရမှတ်)

မူရင်း ELO ရမှတ်များကို leaderboard တစ်ခုစီအလိုက် **`[0.4, 0.98]` အတွင်းရှိ လုပ်ဆောင်ချက်နှင့် ကိုက်ညီမှုတန်ဖိုး** အဖြစ် စံညှိထားသည်-

```
taskFit = 0.4 + 0.58 * ((elo - minElo) / (maxElo - minElo))
```

ရမှတ်သည် `0` သို့မဟုတ် `1` သို့ မည်သည့်အခါမျှ မရောက်ရှိသဖြင့် အသုံးပြုသူ၏ ကိုယ်တိုင်သတ်မှတ်ပြင်ဆင်မှုများအတွက် နေရာချန်ထားပေးသည်။ ၎င်းသည် API တုံ့ပြန်ချက်တွင် မြင်ရသည့် `score` အကွက်နှင့် dashboard ပေါ်တွင် ပြသထားသည့် အညွှန်းဖြစ်သည်။

### ယုံကြည်မှုအဆင့်

ထည့်သွင်းချက်တစ်ခုစီသည် Arena မဲအရေအတွက်အပေါ် အခြေခံ၍ ယုံကြည်မှုအဆင့်တစ်ခု ရရှိသည်-

| ယုံကြည်မှုအဆင့် | မဲအရေအတွက် |
| --------------- | ---------- |
| `high`          | ≥ 5,000    |
| `medium`        | ≥ 1,000    |
| `low`           | < 1,000    |

### သိမ်းဆည်းမှုနှင့် ဒေတာသစ်လွင်မှု

စံညှိထားသော ထည့်သွင်းချက်များကို `source = "arena_elo"` ဖြင့် `model_intelligence` DB ဇယားတွင် ရေးသားသိမ်းဆည်းသည် (`src/lib/db/modelIntelligence.ts`)။ ထည့်သွင်းချက်များသည် **7 ရက်ကြာပြီးနောက် သက်တမ်းကုန်ဆုံးသည်**။ ထို့ကြောင့် စင့်ခ်လုပ်ခြင်းရပ်တန့်သွားသော ပံ့ပိုးသူသည် ဒေတာအဟောင်းများကို ဆက်လက်ပေးပို့နေမည့်အစား နောက်ဆုံးတွင် စာရင်းမှ ပျောက်ကွယ်သွားမည်ဖြစ်သည်။

စင့်ခ်လုပ်ခြင်းသည် **မူလအတိုင်း ဖွင့်ထားသည်**-

- ဆာဗာစတင်ချိန်တွင် တစ်ကြိမ် လုပ်ဆောင်ပြီးနောက် အချိန်မှန် timer ဖြင့် ဆက်လက်လုပ်ဆောင်သည်
  (`src/lib/arenaEloSync.ts`၊ `src/instrumentation-node.ts` မှ ချိတ်ဆက်ထားသည်)။
- ၎င်းသည် **ပိတ်ဆို့မှုမဖြစ်စေဘဲ မည်သည့်အခါမျှ စနစ်ရပ်တန့်စေမည်မဟုတ်ပါ** — မူလရင်းမြစ်မှ ဒေတာရယူမှု မအောင်မြင်ပါက OmniRoute သည် ဆက်လက်လည်ပတ်နေပြီး အဆင့်သတ်မှတ်ချက်များတွင် နောက်ဆုံးရရှိခဲ့သော မှန်ကန်သည့်ဒေတာကိုသာ ပြသမည် (သို့မဟုတ် ဒေတာမရှိသော အခြေအနေကို ပြသမည်) ဖြစ်သည်။

ပတ်ဝန်းကျင် variable နှစ်ခုဖြင့် ၎င်းကို ထိန်းချုပ်သည် ([`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) တွင် မှတ်တမ်းတင်ထားသည်)-

| Variable                  | မူလတန်ဖိုး    | ရည်ရွယ်ချက်                                                   |
| ------------------------- | ------------- | ------------------------------------------------------------- |
| `ARENA_ELO_SYNC_ENABLED`  | `true`        | ပြင်ပသို့ စင့်ခ်လုပ်ခြင်းမှ နုတ်ထွက်ရန် `false` ဟု သတ်မှတ်ပါ။ |
| `ARENA_ELO_SYNC_INTERVAL` | `86400` (24h) | စင့်ခ်ကြားကာလကို စက္ကန့်ဖြင့် သတ်မှတ်သည်။                     |

### ကိုယ်တိုင်စင့်ခ်လုပ်ခြင်း / အခြေအနေ / ရှင်းလင်းခြင်း

စီမံခန့်ခွဲသူများအတွက် အထောက်အထားစစ်ဆေးထားသော management endpoint တစ်ခုမှ ကိုယ်တိုင်ထိန်းချုပ်နိုင်စွမ်းကို ပေးထားသည်
(`src/app/api/intelligence/sync/route.ts` — management auth လိုအပ်သည်)-

```
GET    /api/intelligence/sync          # လက်ရှိစင့်ခ်အခြေအနေ (enabled, lastSync, nextSync, intervalMs)
POST   /api/intelligence/sync          # ကိုယ်တိုင်စင့်ခ်လုပ်မှု စတင်ရန်၊ မရေးသားမီ အစမ်းကြည့်ရန် body: { "dryRun": true }
DELETE /api/intelligence/sync          # စင့်ခ်လုပ်ထားသော arena_elo intelligence ထည့်သွင်းချက်အားလုံးကို ရှင်းလင်းရန်
```

အဆင့်သတ်မှတ်ချက်စာမျက်နှာတွင် ဒေတာမရှိပါက `POST /api/intelligence/sync` ကို ကိုယ်တိုင်လုပ်ဆောင်ခြင်း (သို့မဟုတ် ဆာဗာကို ရိုးရှင်းစွာ ပြန်လည်စတင်ခြင်း) ဖြင့် ဒေတာများကို ပြန်လည်ဖြည့်သွင်းပေးသည်။

### မော်ဒယ်များကို leaderboard နှင့် ကိုက်ညီအောင် ရှာဖွေခြင်း

Registry မော်ဒယ် ID များနှင့် Arena မော်ဒယ်အမည်များသည် အမြဲတမ်း အတိအကျ တူညီလေ့မရှိပါ။ အဆင့်သတ်မှတ်ချက်သည် ပြောင်းလွယ်ပြင်လွယ်ရှိသော ကိုက်ညီမှုရှာဖွေခြင်းကို အသုံးပြုသည် (`src/lib/freeProviderRankings.ts` ရှိ `findMatchingIntelligence`)-

1. စံညှိထားသော မော်ဒယ် ID နှင့် အတိအကျ ကိုက်ညီမှု။
2. နောက်ဆုံးရှိ version suffix ကို ဖယ်ရှားပြီးနောက် ကိုက်ညီမှု (ဥပမာ `kimi-k2.6` → `kimi-k2`)။
3. Prefix ကိုက်ညီမှု (leaderboard မော်ဒယ်အမည်သည် registry ID ၏ prefix ဖြစ်ခြင်း)။

စင့်ခ်ဘက်တွင် လူသိများသော ထုတ်လုပ်သူ prefix များ (`anthropic/`, `openai/`, `google/`, …) ကို ဖယ်ရှားပြီး alias map အသေးစားတစ်ခုက စံသတ်မှတ်ထားသောအမည်များကို OmniRoute အတွင်းပိုင်း၌ အသုံးပြုသည့် အမည်မူကွဲများအဖြစ် ချဲ့ထွင်ပေးသည်။ ထို့ကြောင့် မည်သည့်အမည်ဖြင့်မဆို မော်ဒယ်များကို ရှာဖွေနိုင်သည်။

### ပံ့ပိုးသူတစ်ဦးကို အဆင့်သတ်မှတ်ပုံ

အခမဲ့ပံ့ပိုးသူတစ်ဦးစီအတွက် အင်ဂျင်သည် ၎င်း၏ catalog ထဲရှိ မော်ဒယ်တိုင်းကို ရမှတ်ပေးပြီးနောက်-

- **ထိပ်တန်းမော်ဒယ်** = ပံ့ပိုးသူ၏ ရမှတ်အမြင့်ဆုံး မော်ဒယ်။
- **ပျမ်းမျှရမှတ်** = ထိုပံ့ပိုးသူ၏ ရမှတ်ရရှိထားသော မော်ဒယ်အားလုံး၏ ပျမ်းမျှရမှတ်။
- **မော်ဒယ်များ** = ပံ့ပိုးသူ၏ မော်ဒယ်များအနက် Arena ရမှတ်ရှိသော မော်ဒယ်အရေအတွက်။

ပံ့ပိုးသူများကို ဦးစွာ **ထိပ်တန်းမော်ဒယ်ရမှတ်** အလိုက်၊ ထို့နောက် ပျမ်းမျှရမှတ်အလိုက် စီစဉ်သည်။ ဤနည်းလမ်းသည် အရည်အသွေးကောင်းမွန်သော အခမဲ့မော်ဒယ် အနည်းဆုံးတစ်ခု ပေးထားသည့် ပံ့ပိုးသူကို အားပေးသည်။

## အခမဲ့ Provider များကို ရွေးချယ်ရန် အသုံးပြုခြင်း

1. **မှန်ကန်သော အမျိုးအစားကို ရွေးချယ်ပါ။** Agentic/code workload များအတွက် **Coding** filter ကို အသုံးပြုပါ၊ သို့မဟုတ်
   ယေဘုယျ chat အတွက် **All Categories** / **Default** အတိုင်း ထားပါ။ Leaderboard တစ်ခုချင်းစီအလိုက်
   ထိပ်တန်း model ကွဲပြားသောကြောင့် provider တစ်ခုတည်းပင် အမျိုးအစားအလိုက်
   အဆင့်ကွဲပြားနိုင်သည်။
2. **တစ်ကြိမ်တည်း စီစဉ်ချိတ်ဆက်မှုများအတွက် ထိပ်ဆုံးအဆင့်များကို ဦးစားပေးပါ။** အခမဲ့
   provider တစ်ခု သို့မဟုတ် နှစ်ခုသာ ချိတ်ဆက်လိုပါက သင့်အမျိုးအစားအတွက် ထိပ်ဆုံးအဆင့်ရ provider များဖြင့် စတင်ပါ။
3. **Type badge ကို စစ်ဆေးပါ။** `NOAUTH` provider များသည် ချိတ်ဆက်ရန် အမြန်ဆုံးဖြစ်သည်
   (အထောက်အထားများ မလိုအပ်ပါ)။ `OAUTH` / `APIKEY` အခမဲ့အဆင့်များသည် အလျင်အမြန် စာရင်းသွင်းရန် လိုအပ်သော်လည်း
   ပိုမိုအားကောင်းသော model များကို အသုံးပြုခွင့်ပေးလေ့ရှိသည်။ ချိတ်ဆက်ရန် အဆင့်များအတွက်
   [အခမဲ့အဆင့်များ လမ်းညွှန်](../getting-started/FREE-TIERS-GUIDE.md) ကို ကြည့်ပါ။
4. **အများအပြားကို ချိတ်ဆက်ပြီး Auto-Combo ကို ဆုံးဖြတ်ခွင့်ပေးပါ။** ဤစာမျက်နှာကို ထောက်ပံ့ပေးသည့်
   Arena ELO data သည် Auto-Combo scoring engine ၏ **လုပ်ဆောင်ချက်နှင့် ကိုက်ညီမှု အချက်** ကိုလည်း
   ပံ့ပိုးပေးသည် (`open-sse/services/autoCombo/taskFitness.ts`၊ resolution အစဉ်
   `user_override → arena_elo → models_dev_tier → static table`)။ ထို့ကြောင့် ထိပ်တန်း အခမဲ့ provider များကို
   ချိတ်ဆက်ပြီးနောက် `model: "auto"` (ဥပမာ `auto/coding`) ဖြင့် routing ပြုလုပ်ပါက
   request တစ်ခုချင်းစီအလိုက် အရည်အသွေးပိုမြင့်သော အခမဲ့ model များကို အလိုအလျောက် ဦးစားပေးမည်ဖြစ်သည်။ အချက် 16 ချက်ပါ
   scoring အပြည့်အစုံအတွက် [Auto-Combo](../routing/AUTO-COMBO.md) ကို ကြည့်ပါ။
