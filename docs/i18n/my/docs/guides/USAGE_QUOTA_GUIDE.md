## အနှစ်ချုပ်

OmniRoute မှတစ်ဆင့် ဖြတ်သန်းသော request တစ်ခုချင်းစီသည် အောက်ပါတို့ကို မှတ်တမ်းတင်သည့် **usage record** တစ်ခုကို ထုတ်ပေးသည်-

- **အထောက်အထား**: မည်သည့် API key၊ provider၊ model နှင့် combo ဖြစ်သည်
- **Token များ**: prompt token များ၊ completion token များ၊ cache လုပ်ထားသော token များနှင့် စုစုပေါင်း
- **ကုန်ကျစရိတ်**: USD ပမာဏ (pricing ဒေတာမှ တွက်ချက်ထားသည်)
- **အချိန်ဆိုင်ရာအချက်အလက်**: latency၊ စတင်/ပြီးဆုံး timestamp များ
- **အခြေအနေ**: အောင်မြင်မှု၊ error၊ rate limit သတ်မှတ်ခံရမှု စသည်တို့

ဤ record များကို **analytics** အဖြစ် စုစည်းတွက်ချက်ပြီး **quota snapshot** များအဖြစ် အမြဲတမ်းသိမ်းဆည်းကာ **key တစ်ခုချင်းစီ၏ budget limit** ကို သတ်မှတ်ကျင့်သုံးရန် အသုံးပြုသည်။

```
Request ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    analytics  quota   billing
                    (dashboard) (သတ်မှတ်ကျင့်သုံး) (ထုတ်ယူရန်)
```

## မှတ်တမ်းတင်သည့်အရာများ

`usage.ts` service သည် request တစ်ခုချင်းစီအတွက် **usage event** တစ်ခုကို မှတ်တမ်းတင်သည်-

| Field              | Type    | ရင်းမြစ်                                                     |
| ------------------ | ------- | ------------------------------------------------------------ |
| `id`               | string  | မှတ်တမ်းတင်ချိန်တွင် ထုတ်ပေးသော UUID                         |
| `apiKeyId`         | string  | request ကို စတင်ခဲ့သည့် API key                              |
| `provider`         | string  | Provider ID (openai, anthropic စသည်)                         |
| `model`            | string  | Model ID (gpt-5, claude-opus-4-6 စသည်)                       |
| `comboId`          | string? | combo မှတစ်ဆင့် route လုပ်ထားပါက Combo ID                    |
| `promptTokens`     | number  | upstream response မှရရှိသည်                                  |
| `completionTokens` | number  | upstream response မှရရှိသည်                                  |
| `cachedTokens`     | number  | cache hit ဖြစ်သော token များ (Anthropic prompt caching စသည်) |
| `totalTokens`      | number  | prompt + completion                                          |
| `costUsd`          | number  | pricing ဒေတာမှ တွက်ချက်ထားသည်                                |
| `latencyMs`        | number  | အစမှအဆုံး request ကြာချိန်                                   |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`   |
| `errorClass`       | string? | status != success ဖြစ်ပါက Error class                        |
| `timestamp`        | string  | ISO 8601 UTC                                                 |
| `metadata`         | object  | plugin မှ ထည့်သွင်းပေးသော စိတ်ကြိုက်ဒေတာ                     |

### Token များ၏ ရင်းမြစ်

Token များကို **response handler** အတွင်းရှိ upstream provider ၏ response မှ ထုတ်ယူသည်-

```ts
// open-sse/handlers/chatCore.ts မှ
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

Usage ကို ပြန်မပေးသော provider များအတွက် (web-cookie provider အချို့) OmniRoute သည် `~4 chars per token` heuristic ကို အသုံးပြု၍ token များကို **ခန့်မှန်းတွက်ချက်သည်** (`open-sse/services/autoCombo/pipelineRouter.ts` ကို ကြည့်ပါ)။

### Cache လုပ်ထားသော Token များ

OmniRoute သည် `cached_tokens` ကို `prompt_tokens` မှ သီးခြားစီ ခြေရာခံသည်။ အကြောင်းရင်းများမှာ-

- Anthropic prompt caching သည် cache လုပ်ထားသော token များအတွက် လျှော့ချထားသည့်နှုန်းထား (ပုံမှန်နှုန်း၏ 10%) ကို ကောက်ခံသောကြောင့်
- အချို့ provider များသည် ကွဲပြားသောနှုန်းထားဖြင့် တွက်ချက်သင့်သည့် `cache_read_input_tokens` ကို ပြန်ပေးသောကြောင့်
- Analytics တွင် **cache hit rate** = `cached_tokens / prompt_tokens` ကို ပြသနိုင်သောကြောင့်

## ကုန်ကျစရိတ် တွက်ချက်ခြင်း

ကုန်ကျစရိတ်များကို LiteLLM မှ စင့်ခ်လုပ်ထားသော **ဈေးနှုန်းဒေတာ** (`src/lib/pricingSync.ts`) ကို အသုံးပြု၍ တွက်ချက်သည်-

| မော်ဒယ်           | ထည့်သွင်းမှု $/1M | ထုတ်ပေးမှု $/1M | ကက်ရှ်လုပ်ထားမှု $/1M |
| ----------------- | ----------------- | --------------- | --------------------- |
| gpt-5             | $2.50             | $10.00          | —                     |
| claude-opus-4-6   | $15.00            | $75.00          | $1.50                 |
| claude-sonnet-4-5 | $3.00             | $15.00          | $0.30                 |
| gemini-2.5-pro    | $1.25             | $10.00          | —                     |

ကုန်ကျစရိတ် ဖော်မြူလာ (`src/lib/usage/costCalculator.ts`)-

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **ကက်ရှ်လုပ်ထားသည့် ပမာဏကို prompt မှ အဘယ်ကြောင့် နုတ်သနည်း။** ကက်ရှ်လုပ်ထားသည့် အပိုင်းအတွက် ဈေးနှုန်းကို သီးခြားတွက်ချက်သောကြောင့် prompt တစ်ခုလုံးအပေါ် ထည့်သွင်းမှုဈေးနှုန်း ကောက်ခံပါက ထပ်တိုးတွက်ချက်မိမည်ဖြစ်သည်။

### ဈေးနှုန်း စင့်ခ်လုပ်ခြင်း

ဈေးနှုန်းဒေတာကို `/api/pricing/sync` endpoint မှတစ်ဆင့် LiteLLM ထံမှ အလိုအလျောက် စင့်ခ်လုပ်သည် (အသုံးပြုသူအတွက် ရည်ရွယ်ထားသော env var ဖြင့်မဟုတ်ဘဲ ထည့်သွင်းပေးထားသည့် cron task ဖြင့် အစပျိုးသည်)-

```bash
# ကိုယ်တိုင် အစပျိုးခြင်း
curl -X POST http://localhost:20128/api/pricing/sync
```

ဈေးနှုန်းဒေတာမရှိသည့် မော်ဒယ်များအတွက် OmniRoute သည် အတွင်းပိုင်း ပျမ်းမျှနှုန်းထားများ (LiteLLM ၏ ဈေးနှုန်းဒေတာမှ ရယူထားသည်) ကို အသုံးပြု၍ **ကုန်ကျစရိတ် ခန့်မှန်းခြင်း** သို့ ပြန်လည်အသုံးပြုသည်။

| `custom`     | အသုံးပြုသူသတ်မှတ်ထားသည့် အစ/အဆုံး | စာရင်းစစ်ဆေးခြင်းများ၊ လိုအပ်သလို မေးမြန်းမှုများ      |

### တွက်ချက်ပေးသော Dashboard Widget များ

မည်သည့် ရက်စွဲအပိုင်းအခြားအတွက်မဆို analytics layer သည် အောက်ပါတို့ကို တွက်ချက်သည်-

| Widget                                | ဖော်ပြချက်                                                                                |
| ------------------------------------- | ----------------------------------------------------------------------------------------- |
| **အနှစ်ချုပ်ကတ်များ**                 | စုစုပေါင်း request များ၊ စုစုပေါင်းကုန်ကျစရိတ်၊ စုစုပေါင်း token များ၊ အောင်မြင်မှုနှုန်း |
| **နေ့စဉ်လမ်းကြောင်းဇယား**             | မော်ဒယ်အလိုက် ထပ်ဆင့်ဖော်ပြထားသော တစ်ရက်ချင်း ကုန်ကျစရိတ် + token များ                    |
| **လုပ်ဆောင်မှု heatmap**              | တစ်နေ့တာနာရီ × တစ်ပတ်တာနေ့ grid၊ အရောင် = request အရေအတွက်                                |
| **မော်ဒယ်အလိုက် ခွဲခြမ်းဖော်ပြမှု**   | မော်ဒယ်အလိုက် ကုန်ကျစရိတ် pie chart                                                       |
| **Provider အလိုက် ခွဲခြမ်းဖော်ပြမှု** | provider အလိုက် request များ၏ bar chart                                                   |
| **ထိပ်တန်း API ကီးများ**              | ကုန်ကျစရိတ်အလိုက် ထိပ်တန်းကီး ၁၀ ခု၏ ဇယား                                                 |
| **အမှား ခွဲခြမ်းစိတ်ဖြာမှု**          | အချိန်ကာလအလိုက် အမှားနှုန်း၊ ထိပ်တန်းအမှားအမျိုးအစားများ                                  |

### ပရိုဂရမ်မှတစ်ဆင့် အသုံးပြုခြင်း

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // အသုံးပြုမှုမှတ်တမ်းများ
  "7d",                 // အချိန်အပိုင်းအခြား- "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // provider ချိတ်ဆက်မှု map (connectionId → အကောင့်အမည်)
  {
    startDate: "2025-01-01",  // ရွေးချယ်နိုင်သည်- "custom" အပိုင်းအခြားအတွက်
    endDate: "2025-06-01",   // ရွေးချယ်နိုင်သည်- "custom" အပိုင်းအခြားအတွက်
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (ဆင့်)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## ခွဲတမ်း ကန့်သတ်အသုံးချခြင်း

API key တစ်ခုချင်းစီအလိုက် ခွဲတမ်းကို နေရာနှစ်ခုတွင် ကန့်သတ်အသုံးချသည်-

1. **ပျော့ပျောင်းသော ကန့်သတ်ချက်** (`quotaWarnAt`): အသုံးပြုမှုပမာဏသည် သတ်မှတ်အဆင့်ကို ကျော်လွန်သောအခါ dashboard တွင် သတိပေးချက်ပြသသည်
2. **တင်းကျပ်သော ကန့်သတ်ချက်** (`quotaLimit`): ကန့်သတ်ချက်ကျော်လွန်သောအခါ တောင်းဆိုမှုကို HTTP 429 ဖြင့် ငြင်းပယ်သည်

### စီစဉ်သတ်မှတ်ခြင်း

```ts
// API key တစ်ခုချင်းစီအတွက်
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — သတိပေးချက်ပြသရန်
  quotaLimit: 10_00,    // $10.00 — အပြီးသတ်ရပ်တန့်ရန်
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### ကန့်သတ်အသုံးချမှု လုပ်ငန်းစဉ်

```
တောင်းဆိုမှု ──▶ quotaCheck()
                   │
                   ├── ကန့်သတ်ချက်အတွင်း ရှိသလား?  ──▶ ခွင့်ပြု
                   │
                   └── ကန့်သတ်ချက် ကျော်လွန်သလား?  ──▶ 429 Too Many Requests
                                                        Retry-After header နှင့်အတူ
```

### ခွဲတမ်း လျှပ်တစ်ပြက်မှတ်တမ်းများ

`quotaSnapshots` table သည် လမ်းကြောင်းပြောင်းလဲမှုဆိုင်ရာ ခွဲခြမ်းစိတ်ဖြာမှုအတွက် **ယခင်ခွဲတမ်းအခြေအနေ** ကို သိမ်းဆည်းသည်-

| အကွက် | ဖော်ပြချက် |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | ခြေရာခံနေသော key |
| `window` | "day" | "week" | "month" |
| `used` | ဤအချိန်ကာလအတွင်း အသုံးပြုထားသော ကုန်ကျစရိတ် (ဆင့်) |
| `limit` | ကန့်သတ်ချက် (ဆင့်) |
| `resetAt` | အချိန်ကာလကို ပြန်လည်သတ်မှတ်မည့်အချိန် |
| `createdAt` | လျှပ်တစ်ပြက်မှတ်တမ်းကို ရယူခဲ့သည့်အချိန် |

ကုန်ကျစရိတ် > 0 အသုံးပြုသော **တောင်းဆိုမှုတိုင်းတွင်** လျှပ်တစ်ပြက်မှတ်တမ်းများကို ရယူပြီး အောက်ပါတို့အတွက် အသုံးပြုသည်-

- dashboard တွင် ခွဲတမ်းတိုးတက်မှု bar ကို ဖော်ပြရန်
- ရက် 30 ခွဲတမ်းလမ်းကြောင်းပြ ဇယားများကို ပြသရန်
- အသုံးပြုမှုပမာဏသည် ကန့်သတ်ချက်အနီးသို့ ရောက်လာသောအခါ သတိပေးချက်များ စတင်ပေးပို့ရန်

## ထိန်းသိမ်းမှုနှင့် ရှင်းလင်းမှု

အသုံးပြုမှုဒေတာသည် request တစ်ခုလျှင် ~1-10KB ခန့် တိုးပွားလာသည်။ ပမာဏကြီးမားလာသောအခါ ၎င်းသည် သိသာထင်ရှားလာနိုင်သည်။

### ထိန်းသိမ်းမှု ဆက်တင်များ

အသုံးပြုမှုမှတ်တမ်း ထိန်းသိမ်းမှုကို UI ရှိ Database Settings မှတစ်ဆင့် သို့မဟုတ် `/api/settings/database` မှတစ်ဆင့် စီစဉ်သတ်မှတ်နိုင်သည်။

မူလသတ်မှတ်ချက်အရ အသုံးပြုမှုမှတ်တမ်းကို **ရက် 90** ကြာ ထိန်းသိမ်းထားသည်။

### ရှင်းလင်းမှု

မှတ်တမ်းအဟောင်းများကို `src/lib/db/cleanup.ts` က ရှင်းလင်းပေးသည်-

- နောက်ခံ cron process မှ စတင်လုပ်ဆောင်သည်
- စီစဉ်သတ်မှတ်ထားသော `usageHistory` ထိန်းသိမ်းမှုကာလထက် ကျော်လွန်နေသည့် `usage_history` မှ မှတ်တမ်းများကို ဖျက်သည်

### သိုလှောင်မှုပမာဏ ခန့်မှန်းချက်

| Request နှုန်း     | ရက် 30 သိုလှောင်မှု | ရက် 90 သိုလှောင်မှု |
| ------------------ | ------------------- | ------------------- |
| တစ်ရက် 100 req     | ~3MB                | ~9MB                |
| တစ်ရက် 1,000 req   | ~30MB               | ~90MB               |
| တစ်ရက် 10,000 req  | ~300MB              | ~900MB              |
| တစ်ရက် 100,000 req | ~3GB                | ~9GB                |

Traffic အလွန်များပါက အောက်ပါတို့ကို စဉ်းစားပါ-

- Database Settings မှတစ်ဆင့် ထိန်းသိမ်းမှုကာလကို လျှော့ချခြင်း
- Raw record များအစား `aggregated_metrics` ကို အသုံးပြုခြင်း (analytics အတွက်သာ)

## ကုန်ကျစရိတ် အကောင်းဆုံးဖြစ်အောင် လုပ်ဆောင်ရန် အကြံပြုချက်များ

### 1. သင့်တော်သော Model ကို အသုံးပြုပါ

```bash
# လျင်မြန်သောအဖြေ — စျေးသက်သာပြီး မြန်ဆန်သည့်အရာကို အသုံးပြုပါ
curl -d '{"model":"auto/fast","messages":[...]}'

# ရှုပ်ထွေးသောအလုပ် — အရည်အသွေးကောင်းသည့်အရာကို အသုံးပြုပါ
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Caching ကို ဖွင့်ပါ

Anthropic prompt caching သည် **ထပ်ခါတလဲလဲ အသုံးပြုသော context အတွက် 90%** ချွေတာပေးသည်-

```ts
// Caching သည် အလိုအလျောက် လုပ်ဆောင်သည် — တူညီသော system prompt အကြီးစားကို ထည့်သွင်းရုံသာ
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // အလိုအလျောက် cache လုပ်မည်
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Compression ကို အသုံးပြုပါ

RTK + Caveman compression သည် **tool အများအပြား အသုံးပြုသော session များတွင် 15-95%** ချွေတာပေးသည်-

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Key တစ်ခုချင်းစီအတွက် Quota များ သတ်မှတ်ပါ

ကုန်ကျစရိတ် အကန့်အသတ်မရှိ မြင့်တက်ခြင်းကို ကာကွယ်ရန် `quotaLimit` ကို အမြဲသတ်မှတ်ပါ-

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // တစ်လလျှင် $10 ကန့်သတ်ချက်
```

### 5. အသုံးပြုမှုအများဆုံးသူများကို စစ်ဆေးပါ

API key အလိုက် အုပ်စုဖွဲ့ပြီး ကုန်ကျစရိတ်အလိုက် စီရန် dashboard သို့မဟုတ် **`/api/usage/analytics`** ကို အသုံးပြုပါ-

```bash
GET /api/usage/analytics?groupBy=apiKey
```

### "မှတ်တမ်းများ ပျောက်နေသည်"

- Dashboard → Database → Cleanup အောက်ရှိ DB ထိန်းသိမ်းမှုဆက်တင်များကို စစ်ဆေးပါ — မှတ်တမ်းအဟောင်းများကို အချိန်မှန် ရှင်းလင်းသည့် task (`src/lib/db/cleanup.ts`) က ဖျက်သည်
- `src/lib/db/usage*.ts` ရှိ error များကို စစ်ဆေးပါ — DB write မအောင်မြင်မှုများကို log မှတ်တမ်းတင်သော်လည်း အသုံးပြုသူထံ ဖော်ပြမည်မဟုတ်ပါ
- Request သည် `chatCore` သို့ အမှန်တကယ် ရောက်ရှိခဲ့ကြောင်း အတည်ပြုပါ — combo routing ကို စစ်ဆေးပါ

### "Quota ကန့်သတ်ချက် အလုပ်မလုပ်ပါ"

- Key ၏ `quotaLimit` ဆက်တင်ကို စစ်ဆေးပါ
- `quotaWindow` ကို မှန်ကန်စွာ သတ်မှတ်ထားကြောင်း အတည်ပြုပါ
- `quotaSnapshots` မှတ်တမ်းများကို ရှာဖွေပါ — request တိုင်းတွင် ၎င်းတို့ကို ဖန်တီးထားသင့်သည်
