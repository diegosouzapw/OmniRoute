## အမြန်ကိုးကားချက်

| "နှုန်းကန့်သတ်ချက် ကျော်လွန်သွားသည်"       | တောင်းဆိုချက်များ အလွန်များစွာ ပေးပို့နေသည်              | 1 မိနစ် စောင့်ပါ၊ သို့မဟုတ် အလိုအလျောက် အရန်ပြောင်းသုံးရန် `model: "auto"` ကို အသုံးပြုပါ                                                         |

## အသေးစိတ်ပြဿနာဖြေရှင်းနည်း

---

### အခမဲ့ဝန်ဆောင်မှုပေးသူများတွင် နှုန်းကန့်သတ်ခြင်း (429 / 400 / 401)

**လက္ခဏာ**: အခမဲ့/စစ်မှန်ကြောင်းအတည်ပြုရန်မလိုသော ဝန်ဆောင်မှုပေးသူများ (opencode, auggie စသည်) နှင့် `model: "auto"` ကို အသုံးပြုသောအခါ အဖြေများအစား `HTTP 429`, `400` သို့မဟုတ် `401` ကို ရံဖန်ရံခါ ရရှိသည်။ ခဏအကြာတွင် တူညီသော prompt ကို ပြန်လည်ကြိုးစားသောအခါ တောင်းဆိုချက်များ အောင်မြင်သော်လည်း အလိုအလျောက်လုပ်ဆောင်မှုများ (cron jobs, agents, scripts) သည် ပထမဆုံး ကျရှုံးမှုတွင် ပျက်သွားသည်။

**မူလအကြောင်းရင်း**: တစ်ခုနှင့်တစ်ခု သီးခြားဖြစ်သော ကျရှုံးမှုပုံစံ သုံးမျိုး ပေါင်းစပ်ဖြစ်ပေါ်သည်-

1. **ဝန်ဆောင်မှုပေးသူ၏ နှုန်းကန့်သတ်ချက် (`429`)**: အခမဲ့အဆင့်များတွင် အချိန်ကာလတစ်ခုစီအလိုက် ခွဲတမ်း သတ်မှတ်ထားနိုင်သည်။ အပြိုင်ခေါ်ဆိုမှုများ ရုတ်တရက်များပြားလာပါက ယင်းခွဲတမ်း ကုန်ဆုံးသွားသဖြင့် အချိန်ကာလ ပြန်လည်စတင်သည်အထိ နောက်တောင်းဆိုချက်ကို ငြင်းပယ်ခံရမည်။
2. **Passthrough အတွင်း ပျက်နေသော model (`400`/`401`)**: `auto/*` pool များတွင် catalog ထဲ၌ မှတ်ပုံတင်ထားသော်လည်း လက်ရှိအသုံးပြုနိုင်သော အထောက်အထားများ မရှိသည့် `opencode` မှ passthrough model များ ပါဝင်နိုင်သည် (ဥပမာ `oc/north-mini-code-free` → `401`)။ Auto-router က တစ်ခုကို စမ်းသပ်ပြီး မအောင်မြင်သည့်နောက် အရန်ပြောင်းသုံးမှု မစတင်မီ error ကို ဆက်လက်ပို့လွှတ်လိုက်သည်။
3. **တစ်ပြိုင်နက်လုပ်ဆောင်မှုကြောင့် ပြဿနာ ပိုမိုကြီးထွားခြင်း (ဝန်ပိနေစဉ် `429`)**: Agent/cron session အများအပြားက `auto` ကို တစ်ပြိုင်နက် အသုံးပြုသောအခါ စုစုပေါင်းတောင်းဆိုမှုနှုန်းသည် အခမဲ့ဝန်ဆောင်မှုပေးသူများ လက်ခံနိုင်သည့် ပမာဏထက် ကျော်လွန်သွားသဖြင့် မှန်ကန်သောခေါ်ဆိုမှုများကိုပင် အလွဲသုံးစားမှုအဖြစ် သတ်မှတ်ခံရသည်။

**အတည်ပြုပြီးသော ဖြေရှင်းနည်း (အသိုင်းအဝိုင်းမှ အစီရင်ခံထားသည်၊ 2026-08-10)**: အခမဲ့အဆင့်၏ အပြောင်းအလဲများကြောင့် စနစ်ရပ်တန့်မသွားဘဲ rotation၊ concurrency နှင့် fallback တို့က ကိုင်တွယ်နိုင်စေရန် environment variable သုံးခုကို ချိန်ညှိပါ-

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ဖြစ်ပါက အခြား model/ဝန်ဆောင်မှုပေးသူသို့ ပြောင်းပါ (ပျက်နေသော passthrough model များကို ကျော်သွားသည်)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # လေးလံသောတောင်းဆိုချက်များကို လက်ခံခွင့်ပြုသည့် အမြင့်ဆုံးအရေအတွက်ကို တိတိကျကျ သတ်မှတ်သည် (ပုံမှန်အားဖြင့် မသတ်မှတ်ထားပါ- တောင်းဆိုချက်အရေအတွက် ကန့်သတ်ချက်မရှိပါ၊ အောက်ပါမှတ်ချက်ကို ကြည့်ပါ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ချက်ချင်းပြန်လည်ကြိုးစားနိုင်သော 503 ထုတ်ပေးမည့်အစား လေးလံသောတောင်းဆိုချက်များအတွက် ရရှိနိုင်သည့် စွမ်းရည်ကို အချိန်ကန့်သတ်ထားပြီး ပိုကြာစွာ စောင့်သည်
```

၎င်းတို့ကို OmniRoute process environment (daemon၊ ဥပမာ LaunchAgent plist သို့မဟုတ် `systemctl edit` မှတစ်ဆင့်) တွင် သတ်မှတ်ပြီးနောက် OmniRoute ကို ပြန်လည်စတင်ပါ။ Rotation flag သည် အကျိုးသက်ရောက်မှုအမြင့်ဆုံးသော ချိန်ညှိချက်တစ်ခုဖြစ်သည်။ ယင်းက လုံးဝကျရှုံးမှုတစ်ခုကို pool အတွင်းရှိ အခြေအနေကောင်းသော ဝန်ဆောင်မှုပေးသူနှင့် နောက်ကွယ်မှ အလိုအလျောက် ပြန်လည်ကြိုးစားမှုအဖြစ် ပြောင်းလဲပေးသည်။

**မှတ်ချက်**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` သည် တစ်ပြိုင်နက် လုပ်ဆောင်နိုင်သော လေးလံသည့် — context ရှည်လျားသော — တောင်းဆိုချက်အရေအတွက်ကို ကန့်သတ်သည်။ ဤကန့်သတ်ချက်သည် ဝင်ခွင့်ထိန်းချုပ်မှုဖြစ်ပြီး ဝန်ဆောင်မှုပေးသူ၏ နှုန်းကန့်သတ်ချက် မဟုတ်ပါ။ **#503-fanout အပ်ဒိတ်:** ဤ var ကို ပုံမှန်အားဖြင့် မသတ်မှတ်တော့ပါ (ယခု အထက်ပါအတိုင်း တိတိကျကျ configure လုပ်ထားမှသာ သက်ရောက်သည်) — ယင်းအစား လေးလံသောတောင်းဆိုချက်များ လက်ခံမှုကို host ၏ အမှန်တကယ် memory ceiling အပေါ်မူတည်၍ အလိုအလျောက် ချိန်ညှိသည့် byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ဖြင့် ထိန်းချုပ်သည်။ ထို့ကြောင့် deployment အသစ်တစ်ခုသည် ဤ var ကို လုံးဝမသတ်မှတ်ဘဲ `503 chat_admission_busy` ငြင်းပယ်မှုများ သိသိသာသာ နည်းပါးသွားသင့်သည်။ ဤနေရာတွင် တိတိကျကျ သတ်မှတ်ခြင်းသည်လည်း မှတ်တမ်းတင်ထားသည့်အတိုင်း အတိအကျ ဆက်လက်အလုပ်လုပ်သည်။ တိတိကျကျ override လုပ်ထားသော byte-budget များကို 8 MiB–2 GiB အတွင်း ကန့်သတ်ထားသည်။ `413 body_exceeds_budget` သည် ယာယီဖြစ်ရပ် မဟုတ်ပါ။ ထို byte budget ကို တိုးမြှင့်ပါ၊ `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ကို လျှော့ချပါ၊ သို့မဟုတ် process memory ceiling ကို တိုးမြှင့်ပါ။ `inflight_bytes_budget` shed သည် ယာယီ အရင်းအမြစ်လုယက်မှုဖြစ်ပြီး ပြန်လည်ကြိုးစားနိုင်ဆဲဖြစ်သည်။ ဝန်ဆောင်မှုပေးသူတစ်ခုစီအလိုက် နှုန်းကန့်သတ်ခြင်း (`open-sse/services/rateLimitManager.ts`) ကို `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` နှင့် `RATE_LIMIT_AUTO_ENABLE` တို့က သီးခြားထိန်းချုပ်သည် — `.env.example` ကို ကြည့်ပါ။

**အလုပ်လုပ်ကြောင်း အတည်ပြုနည်း**: သင်၏ agent/cron ကို အချိန်တိုအတွင်း နှစ်ကြိမ် ဆက်တိုက်လုပ်ဆောင်ပြီး နှစ်ကြိမ်စလုံး အောင်မြင်ကြောင်း အတည်ပြုပါ။ ဖြေရှင်းချက် မထည့်မီတွင် ဒုတိယအကြိမ် လုပ်ဆောင်မှုက ပုံမှန်အားဖြင့် `429`/`401` ကို ဖြစ်ပေါ်စေသည်။ ဖြေရှင်းချက် ထည့်ပြီးနောက် ကျရှုံးမှုများ (ရှိပါက) ကို နောက်ကွယ်မှ အလိုအလျောက် ပြန်လည်ကြိုးစားပြီး ခေါ်ဆိုမှု ပြီးမြောက်သွားသည်။ `curl /monitoring/health` ကိုလည်း လုပ်ဆောင်နိုင်ပြီး ဝန်ဆောင်မှုပေးသူချိတ်ဆက်မှုများရှိ `rateLimitedUntil` field နှင့် သက်ရောက်မှုရှိသော ဝန်ဆောင်မှုပေးသူများအတွက် `circuitBreakers.providerBreakers[].state` ကို စောင့်ကြည့်နိုင်သည် — state သည် `CLOSED`, `DEGRADED`, `OPEN` သို့မဟုတ် `HALF_OPEN` တစ်ခုခုဖြစ်သည် (`src/shared/utils/circuitBreaker.ts` ကို ကြည့်ပါ)။ ဆက်တိုက်ကျရှုံးနေသော ဝန်ဆောင်မှုပေးသူသည် reset window က စမ်းသပ်တောင်းဆိုချက်တစ်ခုကို ဖြတ်သန်းခွင့်မပေးမီ `CLOSED → DEGRADED → OPEN` သို့ ပြောင်းလဲသွားမည် (`HALF_OPEN`)။

**429 ကို ဆက်လက်တွေ့မြင်နေရသေးပါက**: ထို provider အတွက် လက်ရှိအသုံးပြုနေသည့် account သည် ၎င်း၏ _quota_ ကို အမှန်တကယ် အပြည့်အဝအသုံးပြုပြီးဖြစ်သည် (rate ကိုသာ ကျော်လွန်ခြင်းမဟုတ်ပါ)။ OmniRoute dashboard → Providers → Accounts တွင် တူညီသော provider အတွက် ဒုတိယ account တစ်ခုကို ထည့်ပါ၊ သို့မဟုတ် အခြားအခမဲ့ provider တစ်ခု (ဥပမာ `routeway`, `auggie`) ကို ရောနှောအသုံးပြုပါ။ Rotation သည် ယာယီ rate/400/401 ပြဿနာများကိုသာ ကူညီပေးနိုင်သည်။ quota အပြည့်အဝကုန်သွားခြင်းအတွက်မူ ဒုတိယ credential တစ်ခု သို့မဟုတ် အခြား provider တစ်ခု လိုအပ်သည်။

**vision model များ (`auto/vision`, `bazaarlink/*`) တွင် 403 ကို တွေ့ရပါက**: ချိတ်ဆက်ထားသော account တွင် vision ပါဝင်သည့် အခပေးအစီအစဉ် မရှိပါ၊ သို့မဟုတ် API key ၌ လုံလောက်သော ခွင့်ပြုချက်များ မရှိပါ။ provider dashboard တွင် key scope ထဲ၌ vision/multimodal ပါဝင်ကြောင်း အတည်ပြုပါ၊ သို့မဟုတ် အခပေးအဆင့် account တစ်ခုကို ချိတ်ဆက်ပြီး ၎င်းကို vision target အဖြစ် ဆက်လက်ထားရှိပါ။

## npm install သတိပေးချက်များ (ERESOLVE / peer / deprecated)

`npm install -g omniroute` ကို လုပ်ဆောင်သည့်အခါ `npm warn ERESOLVE`၊ peer-dependency အသိပေးချက်များနှင့် `deprecated` မက်ဆေ့ချ်များကဲ့သို့ သတိပေးချက်အများအပြားကို တွေ့ရနိုင်ပါသည်။ **၎င်းတို့သည် မျှော်လင့်ထားသည့်အရာများဖြစ်ပြီး အန္တရာယ်မရှိပါ။** output တွင် `added <N> packages` ကို တွေ့ရပါက ထည့်သွင်းမှု အောင်မြင်ပါသည်။

အဆိုပါ သတိပေးချက်များသည် OmniRoute က ထိန်းချုပ်ထားခြင်းမရှိသည့် ပြင်ပ package များရှိ ခေတ်မမီတော့သော peer-dependency range များကြောင့် ဖြစ်ပေါ်လာခြင်းဖြစ်သည်-

1. **`marked-terminal` က `marked >=1 <16` ကို လိုအပ်သော်လည်း `marked@18` ကို တွေ့ရှိခြင်း** — လက်တွေ့တွင် ကောင်းမွန်စွာ အလုပ်လုပ်ပါသည်။ upstream peer range သာ ခေတ်မမီတော့ခြင်း ဖြစ်သည်။
2. **`deprecated prebuild-install@7.1.3`** — တစ်ဆင့်ခံ native-binary ရယူရေး helper တစ်ခုဖြစ်သည်။ ၎င်းကို ပုံသေသတ်မှတ်ထားသော `wreq-js` transport binding ထည့်သွင်းရန်
   အသုံးမပြုသည့်အပြင် web-cookie provider transport စီစဉ်သတ်မှတ်မှု မအောင်မြင်ကြောင်းကိုလည်း
   ညွှန်ပြခြင်းမဟုတ်ပါ။

**ဘာမျှ လုပ်ဆောင်ရန်မလိုပါ** — upstream package များကို fork မလုပ်ဘဲ သတိပေးချက်များကို အပြည့်အဝ ပိတ်ထား၍မရပါ။

## Antivirus မှားယွင်းသတိပေးချက်များ

<a name="antivirus-false-positives"></a>

### Avast/AVG က `README.md` ကို `MD:HttpRequest-inf[Susp]` ဖြင့် quarantine လုပ်ခြင်း

**၎င်းသည် မှားယွင်းသတိပေးချက်တစ်ခုဖြစ်သည်။ မည်သည့်အရာမျှ ကူးစက်ခံထားရခြင်းမရှိသလို မည်သည့်လုပ်ဆောင်ချက်မျှ လုပ်ဆောင်ရန်မလိုအပ်ပါ။**

Avast နှင့် AVG တို့သည် HTTP request များနှင့်တူသော link အများအပြားပါဝင်သည့် plain-text/Markdown file များကို အန္တရာယ်ရှိသည်ဟု မှတ်သားသည့် heuristic တစ်ခုကို အသုံးပြုပါသည်။ OmniRoute ၏ `README.md` ကို npm package အတွင်း ထည့်သွင်းဖြန့်ချိထားပြီး (`package.json` → `files` တွင် စာရင်းသွင်းထားသည်) global install ပြုလုပ်သည့်အခါ `node_modules/omniroute/README.md` သို့ ရောက်ရှိသွားပါသည် — ထို့အပြင် ၎င်းတွင် `http://localhost:20128/...` ဥပမာ ~15 ခု (MCP HTTP/SSE endpoint များ၊ A2A `.well-known` URL နှင့် `curl` snippet များ) ပါဝင်ပါသည်။ ထိုသို့ link များသိပ်သည်းစွာပါဝင်ခြင်းသည် heuristic ကို အလုပ်လုပ်စေရန် လုံလောက်ပါသည်။

ဤပြဿနာသည် မကြာသေးမီကမှ စတင်ဖြစ်ပေါ်ခဲ့ပါက file ၏ အမျိုးအစားဆိုင်ရာ သဘောသဘာဝမှာ ပြောင်းလဲခဲ့ခြင်းမရှိပါ။ README ၏ endpoint ဇယားတွင် MCP HTTP + SSE + A2A တို့ကို ထပ်မံဖြည့်စွက်ခဲ့ပြီး `curl` ဥပမာများ ပိုများလာသောကြောင့် သတ်မှတ်ထားသည့် အဆင့်ကျော်လွန်သွားခြင်းဖြစ်သည်။

ဤ file သည် executable content လုံးဝမပါဝင်သော သာမန် documentation တစ်ခုသာဖြစ်ပါသည်။ ၎င်းကို quarantine မှ ဘေးကင်းစွာ restore လုပ်နိုင်ပါသည်။

**လုပ်ဆောင်ရမည့်အရာများ:**

1. **အသိပေးချက်များကို ရပ်တန့်ပါ** — သင့် antivirus တွင် install directory ကို ချန်လှပ်စာရင်းသို့ ထည့်ပါ
   (Avast: Settings → Exceptions)၊ ထို့နောက် သင်၏ global `node_modules` path နှင့်/သို့မဟုတ်
   OmniRoute data dir (`~/.omniroute/`) ကို ထည့်ပါ။
2. **မှားယွင်းသတိပေးချက်ကို report လုပ်ပါ** — <https://www.avast.com/false-positive-file-form.php> တွင်
   quarantine လုပ်ထားသော `README.md` ကို ပူးတွဲတင်ပြပါ။ Vendor ၏ heuristic က text file တစ်ခုအပေါ်
   လွန်ကဲစွာ တုံ့ပြန်နေခြင်းဖြစ်သဖြင့် ဤနည်းလမ်းသည် လူတိုင်းအတွက် အထောက်အကူဖြစ်စေမည့် ဖြေရှင်းချက်ဖြစ်ပါသည်။

**ကျွန်ုပ်တို့ဘက်မှ ဤအရာကို အဘယ်ကြောင့် "ပြင်ဆင်" မပေးသနည်း:** ဥပမာအားလုံးသည် `http://localhost` ဖြစ်ပြီး
self-signed certificate ကြောင့်ဖြစ်သော အခက်အခဲများမရှိဘဲ localhost တွင် `https` ကို အသုံးမပြုနိုင်ပါ။ Vendor တစ်ခု၏ heuristic ကို ရှောင်ရှားရန် documentation ကို ပုံပျက်အောင် ပြောင်းလဲခြင်းသည် scanner bug တစ်ခုကို ဖြည့်ဆည်းပေးရန် စာဖတ်သူအားလုံးကို ထိခိုက်စေပါလိမ့်မည်။

### Kaspersky က Desktop app ကို `PDM:Trojan.Win32.Generic` ဟု သတ်မှတ်ခြင်း

**၎င်းသည် အပြုအမူဆိုင်ရာ heuristic ကြောင့် ဖြစ်ပေါ်သည့် မှားယွင်းသတိပေးချက်တစ်ခုဖြစ်သည်။ မည်သည့်အရာမျှ ကူးစက်ခံထားရခြင်းမရှိပါ။** Kaspersky ၏
`PDM:` prefix သည် ရလဒ်ကို ၎င်း၏ Proactive Defense Module (System Watcher) မှ သတ်မှတ်ထားခြင်းဖြစ်ကြောင်း ဆိုလိုပါသည်။ ၎င်းသည် သိရှိထားသော malware များနှင့် ကိုက်ညီမှုရှိမရှိ စစ်ဆေးခြင်းထက် installer က _မည်သည့်အရာကို လုပ်ဆောင်သည်_ ကို အကဲဖြတ်ပါသည်။ သတိပေးချက် ပေါ်လာသည့်အခါ Kaspersky က installation တစ်ခုလုံးကို "roll back" လုပ်ပြီး — ရေးသားပြီးသား file များကိုပါ ဖျက်ပစ်သဖြင့် — app သည် ပျက်စီးသွားခြင်း သို့မဟုတ် ပျောက်ဆုံးသွားခြင်း ဖြစ်နိုင်ပါသည်။

၎င်းက အန္တရာယ်ရှိသည်ဟု သတ်မှတ်သည့် file များသည် desktop app နှင့်အတူ ထည့်သွင်းထားသော ကြေညာပြီးသား open-source dependency များ၏ ပုံမှန်အစိတ်အပိုင်းများသာဖြစ်သည်၊ ဥပမာအားဖြင့်:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` နှင့်
  `workerProcessEntry.js` — app အတွင်း provider login နှင့် browser ကို အခြေခံသော chat အတွက် အသုံးပြုသည့် browser automation library ဖြစ်သော [Playwright](https://playwright.dev)။
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — web-cookie provider များအတွက် browser fingerprint ပါသော HTTP ကို အသုံးပြုရန် သတ်မှတ်ထားသည့် `wreq-js` native binding
  (`<arch>` သည် `x64` သို့မဟုတ် `arm64` ဖြစ်သည်)။

**သတိပေးချက် အဘယ်ကြောင့် ပေါ်လာသနည်း:** Windows installer သည် **code-sign မလုပ်ရသေးသောကြောင့်** unsigned NSIS
installer တွင် reputation လုံးဝမရှိဘဲ အပြုအမူဆိုင်ရာ heuristic များသည် အပြင်းထန်ဆုံးအဆင့်ဖြင့် အလုပ်လုပ်ပါသည်။ ၎င်းအခြေအနေကို bundled native DLL တစ်ခုနှင့်
`%LOCALAPPDATA%\Programs\OmniRoute` အောက်တွင် ရေးသားထားသည့် `.js` file ရာပေါင်းများစွာ
(Next.js standalone build မှ hash suffix ပါသော package directory များအပါအဝင်) နှင့် ပေါင်းစပ်လိုက်သောအခါ heuristic ကို အလုပ်လုပ်စေရန် လုံလောက်သွားပါသည်။ Code signing ပြုလုပ်ရန် စီစဉ်ထားပါသည်၊ သို့သော် ၎င်းကို အကောင်အထည်မဖော်မီအထိ release အသစ်များတွင် ဤပြဿနာ ထပ်မံဖြစ်ပေါ်နိုင်ပါသည်။

**လုပ်ဆောင်ရမည့်အရာများ:**

1. **Download ကို ဦးစွာ အတည်ပြုပါ** (file ကို လက်ဆော့ပြင်ဆင်ထားနိုင်ခြင်းအား ဖယ်ရှားစစ်ဆေးရန်)။ Release တိုင်းတွင်
   `OmniRoute.Setup.<version>.exe` installer တစ်ခုလုံးအတွက် အကျုံးဝင်သည့် `sha512` field (base64) ပါသော
   `latest.yml` ကို ထုတ်ပြန်ပေးပါသည်။ PowerShell တွင် installer ပါဝင်သော folder မှ အောက်ပါအတိုင်း လုပ်ဆောင်ပါ:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Output သည် `latest.yml` → `sha512` နှင့် ကိုက်ညီရပါမည်။ မကိုက်ညီပါက file ကို ဖျက်ပြီး
   [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) မှသာ ပြန်လည် download လုပ်ပါ။
2. **Restore လုပ်ပြီး ချန်လှပ်စာရင်းထဲ ထည့်ပါ** — roll back လုပ်ခံထားရသည့် item များကို quarantine မှ restore လုပ်ပြီး
   `%LOCALAPPDATA%\Programs\OmniRoute` အတွက် ချန်လှပ်မှုတစ်ခု ထည့်ပါ (Kaspersky → Settings → Threats and Exclusions)၊
   ထို့နောက် ပြန်လည် install လုပ်ပါ။
3. **မှားယွင်းသတိပေးချက်ကို report လုပ်ပါ** — <https://opentip.kaspersky.com/>။ အသုံးပြုသူများတင်ပြသော မှားယွင်းသတိပေးချက်
   report များသည် allowlist ထဲ ထည့်သွင်းပေးမှုကို အမှန်တကယ် မြန်ဆန်စေပါသည်။

## Node.js လိုက်ဖက်ညီမှု

<a name="nodejs-compatibility"></a>

### အကောင့်ဝင်စာမျက်နှာ ပျက်သွားခြင်း သို့မဟုတ် "Module self-registration" အမှားပြသခြင်း

**အကြောင်းရင်း:** OmniRoute က ခွင့်ပြုထားသည့် လုံခြုံသော runtime အနိမ့်ဆုံးဗားရှင်းပြင်ပရှိ Node.js ဗားရှင်းကို သင် အသုံးပြုနေပါသည်။ အများဆုံးတွေ့ရသည့် အခြေအနေမှာ OmniRoute လိုအပ်သည့် လုံခြုံရေးပြင်ဆင်ပြီး အနိမ့်ဆုံးဗားရှင်းထက် နိမ့်နေသော Node 22 သို့မဟုတ် 24 ၏ patch level အဟောင်းကို အသုံးပြုနေခြင်းဖြစ်သည်။

**လက္ခဏာများ:**

- အကောင့်ဝင်စာမျက်နှာတွင် မျက်နှာပြင်အလွတ် သို့မဟုတ် ဆာဗာအမှားတစ်ခု ပြသသည်
- Console တွင် `Error: Module did not self-register` သို့မဟုတ် အလားတူ native binding အမှားများ ပြသသည်
- Runtime သည် ပံ့ပိုးထားသည့် လုံခြုံရေးမူဝါဒပြင်ပတွင် ရှိနေပါက အကောင့်ဝင်စာမျက်နှာတွင် သင့် Node ဗားရှင်းနှင့်အတူ **လိမ္မော်ရောင် သတိပေးချက် banner** တစ်ခု ပြသသည်

**ဖြေရှင်းနည်း:**

1. ပံ့ပိုးထားသည့် Node.js LTS release တစ်ခုကို ထည့်သွင်းပါ (အကြံပြုချက်- Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. သင့်ဗားရှင်းကို စစ်ဆေးပါ- `node --version` သည် 24.x LTS line တွင် `v24.0.0` သို့မဟုတ် ထို့ထက်အသစ်ကို ပြသရမည်
3. OmniRoute ကို ပြန်လည်ထည့်သွင်းပါ- `npm install -g omniroute`
4. ပြန်လည်စတင်ပါ- `omniroute`

> **ပံ့ပိုးထားသည့် လုံခြုံသောဗားရှင်းများ:** `>=22.22.2 <23` သို့မဟုတ် `>=24.0.0 <27`။ Node.js 24.x LTS (Krypton) နှင့် Node.js 26 ကို အပြည့်အဝ ပံ့ပိုးထားသည်။

### npm v11+: `better-sqlite3` ကို မထည့်သွင်းထားခြင်း (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**အကြောင်းရင်း:** Node.js 24+ နှင့်အတူ ပါဝင်လာသော npm v11 သည် optional
dependencies များအတွက် install scripts များကို မူလသတ်မှတ်ချက်အရ ပိတ်ထားသည်။ `better-sqlite3` ကို `optionalDependencies`
တွင် စာရင်းသွင်းထားပြီး native compilation (`node-gyp rebuild`) လိုအပ်သောကြောင့် npm က ၎င်းကို အသိပေးချက်မရှိဘဲ ကျော်သွားသည်။

**လက္ခဏာများ:**

- ဆာဗာစတင်ချိန်တွင် `Cannot find module 'better-sqlite3'` ဖြင့် ပျက်သွားသည်
- `ls node_modules/better-sqlite3` က "No such file or directory" ဟု ပြသသည်
- `npm ls better-sqlite3` က `(empty)` ဟု ပြသသည်

**ဖြေရှင်းနည်း:**

1. Install scripts များကို ခွင့်ပြုပြီး ပြန်လည်ထည့်သွင်းပါ:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. သို့မဟုတ် ကြိုတင် build လုပ်ထားသည့် package ကို ကိုယ်တိုင်ထည့်သွင်းပါ:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. အလုပ်လုပ်ကြောင်း စစ်ဆေးပါ- `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**အကြောင်းရင်း:** Global `npm install -g omniroute` ပြုလုပ်ပြီးနောက် package အတွင်းရှိ `better-sqlite3` native binary ကို စက်တွင် လက်ရှိအသုံးပြုနေသည့် architecture သို့မဟုတ် Node.js ABI နှင့် မတူသောအမျိုးအစားအတွက် compile လုပ်ထားခြင်း ဖြစ်နိုင်သည်။ ကြိုတင် build လုပ်ထားသည့် binary သည် သင့် environment နှင့် မကိုက်ညီသည့်အခါ macOS (Apple Silicon နှင့် Intel နှစ်မျိုးလုံး) တွင် ဤပြဿနာကို အများအားဖြင့် တွေ့ရသည်။

**လက္ခဏာများ:**

- ဆာဗာစတင်ချိန်တွင် `dlopen` အမှားဖြင့် ချက်ချင်း မအောင်မြင်တော့ပါ
- အမှားတွင် `slice is not valid mach-o file` ပါဝင်သည်
- ဥပမာအပြည့်အစုံ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ဖြေရှင်းနည်း — သင့်စက်၏ environment အတွက် ပြန်လည် build လုပ်ပါ (Node.js ဗားရှင်းလျှော့ချရန် မလိုအပ်ပါ):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **မှတ်ချက်:** ဤလုပ်ဆောင်ချက်သည် သင့်စက်ရှိ Node.js ဗားရှင်းနှင့် CPU architecture အပေါ်အခြေခံ၍ native binding ကို ပြန်လည် compile လုပ်ပေးသဖြင့် binary မကိုက်ညီမှုပြဿနာကို ဖြေရှင်းပေးသည်။ တရားဝင်ပံ့ပိုးထားသည့် runtime range မှာ **`>=22.22.2 <23` သို့မဟုတ် `>=24.0.0 <27`** ဖြစ်သည် (`src/shared/utils/nodeRuntimeSupport.ts` ရှိ `SUPPORTED_NODE_RANGE` သည် `package.json` ရှိ `engines` field နှင့် ကိုက်ညီသည်)။ Node.js 24.x LTS (Krypton) နှင့် Node.js 26 ကို `better-sqlite3` v12.x ဖြင့် အပြည့်အဝ ပံ့ပိုးထားသည်။

## Proxy ပြဿနာများ

<a name="proxy-issues"></a>

### Provider အတည်ပြုစစ်ဆေးမှုတွင် "fetch failed" ဟု ပြသခြင်း

**အကြောင်းရင်း:** API key အတည်ပြုစစ်ဆေးရေး endpoint (`POST /api/providers/validate`) သည် ယခင်က proxy configuration ကို ကျော်လွှားအသုံးပြုနေသောကြောင့် proxy routing လိုအပ်သည့် environment များတွင် အလုပ်မလုပ်ခြင်းများ ဖြစ်ပေါ်ခဲ့သည်။

**ဖြေရှင်းချက် (v3.5.5+):** ယခု ပြင်ဆင်ပြီးဖြစ်သည်။ Provider အတည်ပြုစစ်ဆေးရေးသည် `runWithProxyContext` မှတစ်ဆင့် လုပ်ဆောင်ပြီး provider-level နှင့် global proxy setting များကို အလိုအလျောက် လိုက်နာအသုံးပြုသည်။

### Token ကျန်းမာရေးစစ်ဆေးမှုတွင် "fetch failed" ဟု ပြသခြင်း

**အကြောင်းရင်း:** နောက်ခံ OAuth token refresh သည် connection တစ်ခုချင်းစီအလိုက် proxy configuration ကို မသတ်မှတ်ပေးနိုင်ခဲ့ပါ။

**ဖြေရှင်းချက် (v3.5.5+):** Token ကျန်းမာရေးစစ်ဆေးမှု scheduler သည် ယခု refresh ပြုလုပ်ရန် မကြိုးစားမီ connection တစ်ခုချင်းစီအလိုက် proxy config ကို သတ်မှတ်ပေးသည်။ v3.5.5+ သို့ အပ်ဒိတ်လုပ်ပါ။

### SOCKS5 proxy တွင် "invalid onRequestStart method" ဟု ပြသခြင်း

**အကြောင်းရင်း:** Node.js 22 တွင် undici@8 dispatcher သည် Node ၏ built-in `fetch()` implementation နှင့် သဟဇာတမဖြစ်ပါ။

**ဖြေရှင်းချက် (v3.5.5+):** Proxy dispatcher ကို အသုံးပြုနေချိန်တွင် တစ်သမတ်တည်း အလုပ်လုပ်စေရန် OmniRoute သည် ယခု undici ၏ ကိုယ်ပိုင် `fetch()` function ကို အသုံးပြုသည်။ v3.5.5+ သို့ အပ်ဒိတ်လုပ်ပါ။

### WSL အောက်ရှိ MITM proxy: Windows host ပေါ်ရှိ desktop app များကို ကြားဖြတ်ဖမ်းယူ၍မရခြင်း

**အကြောင်းရင်း:** MITM proxy နှင့် ၎င်း၏ CA certificate ကို OmniRoute အလုပ်လုပ်နေသည့် environment အတွင်း ထည့်သွင်းထားသည်။ WSL အောက်တွင် ထို environment သည် Linux guest ဖြစ်ပြီး AI desktop app များ (Kiro, Trae, Copilot, Zed, …) သည် Windows host ပေါ်တွင် အလုပ်လုပ်သည်။ Host app များသည် guest ၏ certificate store ကို မယုံကြည်သည့်အပြင် guest ၏ system proxy မှတစ်ဆင့်လည်း လမ်းကြောင်းမပို့သောကြောင့် desktop ကြားဖြတ်ဖမ်းယူမှုသည် ထိုနေရာတွင် အလုပ်မလုပ်ပါ။

**အကြံပြုချက်:** သင်ကြားဖြတ်ဖမ်းယူလိုသည့် desktop app များနှင့် OS တူညီသည့်နေရာတွင် OmniRoute ကို native အနေဖြင့် အသုံးပြုပါ (Windows app များအတွက် Windows၊ macOS/Linux အတွက်လည်း အလားတူ)။ Host app များကို ပစ်မှတ်ထားပြီး OmniRoute ကို WSL အတွင်း ဆက်လက်ထားရှိလိုပါက ထုတ်ပေးထားသော CA certificate ကို Windows host ပေါ်တွင် ကိုယ်တိုင် ယုံကြည်ခွင့်ပြုပြီး host app တစ်ခုချင်းစီ၏ network/proxy setting များကို WSL proxy endpoint သို့ ညွှန်ပြပေးရန် လိုအပ်သည် — ယင်းသည် ပံ့ပိုးမထားသော၊ အလွယ်တကူ ပျက်ယွင်းနိုင်သည့် setup ဖြစ်သည်။

## Provider ပြဿနာများ

### "Language model did not provide messages"

**အကြောင်းရင်း:** Provider quota ကုန်ဆုံးသွားခြင်း။

**ဖြေရှင်းချက်:**

1. Dashboard ရှိ quota tracker ကို စစ်ဆေးပါ
2. Fallback tier များပါဝင်သည့် combo ကို အသုံးပြုပါ
3. ပိုမိုစျေးသက်သာသော/free tier သို့ ပြောင်းပါ

### Rate Limiting

**အကြောင်းရင်း:** Subscription quota ကုန်ဆုံးသွားခြင်း။

**ဖြေရှင်းချက်:**

- Fallback ထည့်ပါ: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- စျေးသက်သာသော backup အဖြစ် GLM/MiniMax ကို အသုံးပြုပါ

### OAuth Token သက်တမ်းကုန်ခြင်း

OmniRoute သည် token များကို အလိုအလျောက် refresh လုပ်ပေးသည်။ ပြဿနာများ ဆက်ရှိနေပါက-

1. Dashboard → Provider → ပြန်လည်ချိတ်ဆက်ပါ
2. Provider connection ကို ဖျက်ပြီး ပြန်လည်ထည့်သွင်းပါ

### Kiro multi-account: ဒုတိယ account က ပထမ account ကို အသုံးမပြုနိုင်အောင် ဖြစ်စေခြင်း

**အကြောင်းရင်း:** Kiro ၏ backend သည် OIDC client registration တစ်ခုလျှင် active session တစ်ခုသာ ခွင့်ပြုထားသည်။
Account နှစ်ခုသည် မှတ်ပုံတင်ထားသည့် client တစ်ခုတည်းကို မျှဝေသုံးစွဲသည့်အခါ (v3.8.0 မတိုင်မီ import လုပ်ထားသော connection များ)၊
account တစ်ခု၏ token ကို refresh လုပ်ခြင်းသည် အခြား account ၏ refresh token ကို အသုံးမပြုနိုင်အောင် ဖြစ်စေသည်။

**ဖြေရှင်းချက် (v3.8.0+):** ထိခိုက်နေသော connection များကို ပြန်လည် import လုပ်ပါ။
v3.8.0 မှစ၍ **Import Token**၊
**Google/GitHub social login** သို့မဟုတ် **Auto-Import** မှတစ်ဆင့် ဖန်တီးသည့် Kiro connection အသစ်တိုင်းသည် ၎င်း၏ကိုယ်ပိုင်
သီးခြား OIDC client ကို အလိုအလျောက် မှတ်ပုံတင်ပေးသည်။ ထို့ကြောင့် connection ကို အပြည့်အဝ သီးခြားခွဲထားပြီး account တစ်ခုကို
refresh လုပ်ခြင်းသည် အခြားမည်သည့် account ကိုမျှ သက်ရောက်မှုမရှိပါ။

v3.8.0 _မတိုင်မီ_ import လုပ်ထားသော connection များတွင် connection တစ်ခုချင်းစီအလိုက် client
registration မပါဝင်ပါ။ ထို connection များသည် မျှဝေထားသော social-auth refresh endpoint ကို ဆက်လက်အသုံးပြုသည်။
သီးခြားခွဲထားမှုကို ရရှိရန် Dashboard → Providers မှ connection အဟောင်းကို ဖျက်ပြီး import flow သုံးမျိုးအနက်

## Cloud ပြဿနာများ

### Cloud Sync အမှားများ

1. `BASE_URL` သည် လက်ရှိလည်ပတ်နေသော instance ကို ညွှန်ထားကြောင်း စစ်ဆေးပါ (ဥပမာ၊ `http://localhost:20128`)
2. `CLOUD_URL` သည် သင်၏ cloud endpoint ကို ညွှန်ထားကြောင်း စစ်ဆေးပါ (ဥပမာ၊ `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` တန်ဖိုးများကို server-side တန်ဖိုးများနှင့် ကိုက်ညီအောင်ထားပါ

### Cloud တွင် `stream=false` က 500 ပြန်ပေးခြင်း

**လက္ခဏာ:** Non-streaming call များအတွက် cloud endpoint တွင် `Unexpected token 'd'...` ပေါ်လာသည်။

**အကြောင်းရင်း:** Client က JSON ကို မျှော်လင့်နေသော်လည်း upstream က SSE payload ကို ပြန်ပေးသည်။

**ယာယီဖြေရှင်းနည်း:** Cloud သို့ တိုက်ရိုက်ခေါ်ဆိုမှုများအတွက် `stream=true` ကို အသုံးပြုပါ။ Local runtime တွင် SSE→JSON fallback ပါဝင်သည်။

### Cloud က Connected ဟု ပြသသော်လည်း "Invalid API key" ဟု ဆိုခြင်း

1. Local dashboard (`/api/keys`) မှ key အသစ်တစ်ခု ဖန်တီးပါ
2. Cloud sync ကို လုပ်ဆောင်ပါ: Enable Cloud → Sync Now
3. Key အဟောင်းများ သို့မဟုတ် sync မလုပ်ရသေးသော key များသည် cloud တွင် `401` ကို ပြန်ပေးနိုင်သေးသည်

## Docker ပြဿနာများ

### Docker IPv6 / Connection Reset

<a name="docker-ipv6"></a>

**လက္ခဏာများ:** `curl http://localhost:20128/v1/models` က `curl: (56) Recv failure: Connection reset by peer` ဟု ပြန်ပေးသည်။ Dashboard နှင့် authentication မလိုသော endpoint များ အလုပ်လုပ်သော်လည်း authenticated endpoint များ အလုပ်မလုပ်ပါ — authentication ပြဿနာကဲ့သို့ ထင်ရသော်လည်း အမှန်တကယ် မဟုတ်ပါ။

**အကြောင်းရင်း:** `docker run -p 20128:20128` သည် `0.0.0.0` (IPv4) နှင့် `::` (IPv6) နှစ်ခုလုံးတွင် publish လုပ်သော်လည်း container အတွင်းရှိ process သည် IPv4 ပေါ်တွင်သာ listen လုပ်သည်။ `localhost` က `::1` သို့ ဦးစွာ resolve လုပ်သော host များတွင် connection သည် နောက်ကွယ်၌ listener မရှိသော IPv6 published port သို့ ရောက်သွားသောကြောင့် → connection reset ဖြစ်သည်။

**ပြင်ဆင်နည်း:**

1. **အမြန်စစ်ဆေးနည်း:** `curl -4 http://localhost:20128/v1/models` ကို run ပါ။ `-4` ဖြင့် အလုပ်လုပ်သော်လည်း ၎င်းမပါဘဲ မအောင်မြင်ပါက IPv6 bind မကိုက်ညီမှု ရှိနေပါသည်။
2. **အမြဲတမ်းပြင်ဆင်နည်း:** သင်၏ `docker run` command တွင် `-p 127.0.0.1:20128:20128` ကို အသုံးပြုခြင်းဖြင့် IPv4 သို့ အတိအကျ bind လုပ်ပါ:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ဤနည်းသည် IPv4 bind ကို မဖြစ်မနေ အသုံးပြုစေပြီး proxy ကို host interface အားလုံးပေါ်တွင် ဖော်ထုတ်ထားခြင်းကိုလည်း ရှောင်ရှားပေးသည်။

## Debugging

### Log File များကို ဖွင့်ခြင်း

သင်၏ `.env` file တွင် `APP_LOG_TO_FILE=true` ကို သတ်မှတ်ပါ။ Application log များကို `logs/` အောက်တွင် ရေးသားသိမ်းဆည်းသည်။
Settings တွင် call log pipeline ကို ဖွင့်ထားသည့်အခါ request artifact များကို `${DATA_DIR}/call_logs/` အောက်တွင် သိမ်းဆည်းသည်။
Pipeline capture ကို ဖွင့်ထားသည့်အခါ stream chunk payload များကို ချန်လှပ်ရန် `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` ကို သတ်မှတ်ပါ၊ သို့မဟုတ် artifact အရွယ်အစားကန့်သတ်ချက်ကို KB ဖြင့် ပြောင်းလဲရန် `CALL_LOG_PIPELINE_MAX_SIZE_KB` ကို ချိန်ညှိပါ။

### Provider အခြေအနေကို စစ်ဆေးခြင်း

```bash
# Health dashboard
http://localhost:20128/dashboard/health

# API health စစ်ဆေးမှု
curl http://localhost:20128/api/monitoring/health
```

### Runtime Storage

- အဓိက state: `${DATA_DIR}/storage.sqlite` (provider များ၊ combo များ၊ alias များ၊ key များ၊ setting များ)
- အသုံးပြုမှု: `storage.sqlite` ရှိ SQLite table များ (`usage_history`, `call_logs`, `proxy_logs`) + ရွေးချယ်အသုံးပြုနိုင်သော `${DATA_DIR}/call_logs/`
- Application log များ: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ဖြစ်သည့်အခါ)
- Call log artifact များ: call log pipeline ကို ဖွင့်ထားသည့်အခါ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs စာမျက်နှာရှိ **Clean history** လုပ်ဆောင်ချက်သည် `call_logs`၊ အဟောင်းစနစ်သုံး
`request_detail_logs` နှင့် local `${DATA_DIR}/call_logs/` artifact directory ကို ရှင်းလင်းသည်။

## Circuit Breaker ပြဿနာများ

### Provider သည် OPEN အခြေအနေတွင် ရပ်တန့်နေခြင်း

Provider တစ်ခု၏ circuit breaker သည် OPEN ဖြစ်နေသောအခါ cooldown ကာလ ကုန်ဆုံးသည်အထိ request များကို ပိတ်ဆို့ထားပါသည်။

**ဖြေရှင်းနည်း:**

1. **Dashboard → Settings → Resilience** သို့ သွားပါ
2. ပြဿနာဖြစ်နေသော provider အတွက် circuit breaker card ကို စစ်ဆေးပါ
3. Breaker အားလုံးကို ရှင်းလင်းရန် **Reset All** ကို နှိပ်ပါ၊ သို့မဟုတ် cooldown ကာလ ကုန်ဆုံးသည်အထိ စောင့်ပါ
4. Reset မလုပ်မီ provider ကို အမှန်တကယ် အသုံးပြုနိုင်ကြောင်း အတည်ပြုပါ

### Provider က circuit breaker ကို ထပ်ခါတလဲလဲ အလုပ်လုပ်စေခြင်း

Provider တစ်ခုသည် OPEN အခြေအနေသို့ ထပ်ခါတလဲလဲ ဝင်ရောက်နေပါက:

1. မအောင်မြင်မှုပုံစံကို သိရှိရန် **Dashboard → Health → Provider Health** တွင် စစ်ဆေးပါ
2. **Settings → Resilience → Provider Profiles** သို့ သွား၍ failure threshold ကို မြှင့်ပါ
3. Provider က API ကန့်သတ်ချက်များကို ပြောင်းလဲထားခြင်း ရှိ၊ မရှိ သို့မဟုတ် ပြန်လည် authentication လုပ်ရန် လိုအပ်ခြင်း ရှိ၊ မရှိ စစ်ဆေးပါ
4. Latency telemetry ကို ပြန်လည်သုံးသပ်ပါ — latency မြင့်မားခြင်းကြောင့် timeout အခြေပြု မအောင်မြင်မှုများ ဖြစ်ပေါ်နိုင်ပါသည်

## အသံမှ စာသားပြောင်းခြင်းဆိုင်ရာ ပြဿနာများ

### "Unsupported model" အမှား

- သင့်တွင် အထောက်အထားများရှိသော provider ကို ပထမ segment အဖြစ် အသုံးပြုထားသည့် model id (`openai/whisper-1`, `openrouter/deepgram/nova-3`) ကို အသုံးပြုပါ။ `deepgram/nova-3` ကို တိုက်ရိုက်အသုံးပြုရန် မူရင်း Deepgram key တစ်ခု လိုအပ်ပါသည်။
- Provider ကို **Dashboard → Providers** တွင် ချိတ်ဆက်ထားကြောင်း အတည်ပြုပါ

### စာသားပြောင်းလဲမှုရလဒ် ဗလာဖြစ်နေခြင်း သို့မဟုတ် မအောင်မြင်ခြင်း

- ပံ့ပိုးထားသော အသံဖိုင် format များကို စစ်ဆေးပါ: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ဖိုင်အရွယ်အစားသည် provider ၏ ကန့်သတ်ချက်အတွင်း ရှိကြောင်း အတည်ပြုပါ (ပုံမှန်အားဖြင့် < 25MB)
- Provider card တွင် provider API key မှန်ကန်မှုကို စစ်ဆေးပါ

## Translator ကို Debug လုပ်ခြင်း

Format ဘာသာပြန်ခြင်းဆိုင်ရာ ပြဿနာများကို debug လုပ်ရန် **Dashboard → Translator** ကို အသုံးပြုပါ:

| Mode             | အသုံးပြုသင့်သည့်အချိန်                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Playground**   | Input/output format များကို ဘေးချင်းယှဉ် နှိုင်းယှဉ်ပါ — မအောင်မြင်သော request တစ်ခုကို paste လုပ်ပြီး ၎င်းကို မည်သို့ ဘာသာပြန်ထားသည်ကို ကြည့်ပါ |
| **Chat Tester**  | တိုက်ရိုက် message များ ပို့ပြီး header များအပါအဝင် request/response payload အပြည့်အစုံကို စစ်ဆေးပါ                                              |
| **Test Bench**   | မည်သည့် ဘာသာပြန်မှုများ ပျက်နေသည်ကို ရှာဖွေရန် format ပေါင်းစပ်မှုအမျိုးမျိုးတွင် batch test များ လုပ်ဆောင်ပါ                                    |
| **Live Monitor** | ကြားဖြတ်ဖြစ်ပေါ်သော ဘာသာပြန်ပြဿနာများကို ဖမ်းယူရန် အချိန်နှင့်တစ်ပြေးညီ request စီးဆင်းမှုကို စောင့်ကြည့်ပါ                                      |

### အဖြစ်များသော format ပြဿနာများ

- **Thinking tag များ မပေါ်လာခြင်း** — ပစ်မှတ် provider က thinking ကို ပံ့ပိုးခြင်း ရှိ၊ မရှိနှင့် thinking budget setting ကို စစ်ဆေးပါ
- **Tool call များ ပျောက်ဆုံးခြင်း** — အချို့ format ဘာသာပြန်မှုများက ပံ့ပိုးမထားသော field များကို ဖယ်ရှားနိုင်သည်၊ Playground mode တွင် အတည်ပြုပါ
- **System prompt ပျောက်ဆုံးခြင်း** — Claude နှင့် Gemini တို့က system prompt များကို မတူညီစွာ ကိုင်တွယ်ကြသည်၊ ဘာသာပြန် output ကို စစ်ဆေးပါ
- **SDK က object အစား raw string ကို ပြန်ပေးခြင်း** — v1.x တွင် ဖြေရှင်းပြီးဖြစ်သည်၊ response sanitizer သည် OpenAI SDK Pydantic validation မအောင်မြင်မှုများကို ဖြစ်စေသော စံမဟုတ်သည့် field များ (`x_groq`, `usage_breakdown` စသည်) ကို ဖယ်ရှားပေးသည်။ v3.x+ တွင် ဤပြဿနာကို တွေ့နေရဆဲဖြစ်ပါက issue တစ်ခု တင်ပြပေးပါ။
- **GLM/ERNIE က `system` role ကို လက်မခံခြင်း** — v1.x တွင် ဖြေရှင်းပြီးဖြစ်သည်၊ role normalizer သည် ကိုက်ညီမှုမရှိသော model များအတွက် system message များကို user message များထဲသို့ အလိုအလျောက် ပေါင်းစည်းပေးသည်။ v3.x+ တွင် ဤပြဿနာကို တွေ့နေရဆဲဖြစ်ပါက issue တစ်ခု တင်ပြပေးပါ။
- **`developer` role ကို မသိရှိခြင်း** — v1.x တွင် ဖြေရှင်းပြီးဖြစ်သည်၊ OpenAI မဟုတ်သော provider များအတွက် `system` သို့ အလိုအလျောက် ပြောင်းလဲပေးသည်။ v3.x+ တွင် ဤပြဿနာကို တွေ့နေရဆဲဖြစ်ပါက issue တစ်ခု တင်ပြပေးပါ။
- **`json_schema` က Gemini နှင့် အလုပ်မလုပ်ခြင်း** — v1.x တွင် ဖြေရှင်းပြီးဖြစ်သည်၊ ယခုအခါ `response_format` ကို Gemini ၏ `responseMimeType` + `responseSchema` သို့ ပြောင်းလဲပေးသည်။ v3.x+ တွင် ဤပြဿနာကို တွေ့နေရဆဲဖြစ်ပါက issue တစ်ခု တင်ပြပေးပါ။

## ခံနိုင်ရည်ဆိုင်ရာ ဆက်တင်များ

### အလိုအလျောက် နှုန်းကန့်သတ်မှု အလုပ်မလုပ်ခြင်း

- အလိုအလျောက် နှုန်းကန့်သတ်မှုသည် API key ပံ့ပိုးသူများအတွက်သာ သက်ရောက်သည် (OAuth/subscription အတွက် မသက်ရောက်ပါ)
- **Settings → Resilience → Provider Profiles** တွင် အလိုအလျောက် နှုန်းကန့်သတ်မှုကို ဖွင့်ထားကြောင်း အတည်ပြုပါ
- ပံ့ပိုးသူက `429` အခြေအနေကုဒ်များ သို့မဟုတ် `Retry-After` header များကို ပြန်ပေးခြင်းရှိမရှိ စစ်ဆေးပါ

### Exponential backoff ကို ချိန်ညှိခြင်း

ပံ့ပိုးသူ ပရိုဖိုင်များတွင် အောက်ပါဆက်တင်များကို အသုံးပြုနိုင်သည်-

- **Base delay** — ပထမအကြိမ် မအောင်မြင်ပြီးနောက် ကနဦးစောင့်ဆိုင်းချိန် (မူလသတ်မှတ်ချက်- 1s)
- **Max delay** — အများဆုံးစောင့်ဆိုင်းချိန် ကန့်သတ်ချက် (မူလသတ်မှတ်ချက်- 30s)
- **Multiplier** — ဆက်တိုက်မအောင်မြင်မှုတစ်ကြိမ်စီအတွက် စောင့်ဆိုင်းချိန်ကို တိုးမြှင့်ရမည့် ဆတန်ဖိုး (မူလသတ်မှတ်ချက်- 2x)

### တစ်ပြိုင်နက်တည်း စုပြုံတောင်းဆိုမှုကို ကာကွယ်ခြင်း

တစ်ပြိုင်နက်တည်း တောင်းဆိုမှုများစွာက နှုန်းကန့်သတ်ထားသော ပံ့ပိုးသူထံ ရောက်ရှိလာသည့်အခါ OmniRoute သည် တောင်းဆိုမှုများကို တစ်ခုပြီးတစ်ခု လုပ်ဆောင်စေရန်နှင့် ဆက်တိုက်ပျက်ကွက်မှုများကို ကာကွယ်ရန် mutex + အလိုအလျောက် နှုန်းကန့်သတ်မှုကို အသုံးပြုသည်။ API key ပံ့ပိုးသူများအတွက် ၎င်းကို အလိုအလျောက် လုပ်ဆောင်သည်။

### Chat တောင်းဆိုမှုများသည် 503 / chat_admission_busy ဖြင့် မအောင်မြင်ခြင်း

**လက္ခဏာများ-**

- Chat completions endpoint သည် ထပ်မံကြိုးစားနိုင်သော `503` တုံ့ပြန်မှုကို ပြန်ပေးပြီး ၎င်း၏ error code မှာ
  `chat_admission_busy` ဖြစ်သည်။
- တုံ့ပြန်မှုတွင် `Retry-After` ပါဝင်သည်။ #12135 မှစ၍ ယင်းတန်ဖိုးကို လေ့လာတွေ့ရှိထားသော
  အသုံးပြုမှုအခြေအနေမှ တွက်ချက်သည် — တောင်းဆိုမှုက စောင့်ဆိုင်းပြီးခဲ့သည့် `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  အချိန်အပိုင်းအခြားနှင့် လက်ရှိ heavyweight lease များကို ထိန်းထားပြီးသည့်အချိန်တို့အနက် ပိုကြီးသည့်တန်ဖိုးကို
  စက္ကန့်ပြည့်အထိ အထက်သို့ပတ်ကာ 60 ထက် မကျော်စေရန် ကန့်သတ်ထားသည်။ အသုံးမပြုထားသော gate တွင်
  မူလအနိမ့်ဆုံးတန်ဖိုးများကို ဆက်လက်အသုံးပြုသည်- byte-based path အတွက် 2 စက္ကန့်နှင့်
  structure-based path အတွက် 1 စက္ကန့်ဖြစ်သည် (နောက်တစ်ခုတွင်
  `reason: "structure_limit"` လည်း ပါဝင်သည်)။
- အခြား heavyweight chat သို့မဟုတ် အချိန်ကြာမြင့်စွာ လုပ်ဆောင်နေသည့် streaming တုံ့ပြန်မှုက
  လုပ်ဆောင်ဆဲဖြစ်နေချိန်တွင် ဤသို့ဖြစ်နိုင်သည်။

Byte-based တုံ့ပြန်မှု body မှာ-

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Structure-based တုံ့ပြန်မှုသည် တူညီသော type နှင့် code ကို အသုံးပြုပြီး message မှာ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ဖြစ်ကာ `reason: "structure_limit"` လည်း ပါဝင်သည်။
မူလသတ်မှတ်ထားသော threshold များအရ တောင်းဆိုမှုတစ်ခုတွင် message အနည်းဆုံး `200` ခု၊
tool အနည်းဆုံး `64` ခု သို့မဟုတ် ခန့်မှန်း token အနည်းဆုံး `32,000` ရှိလျှင်၊ သို့မဟုတ် ကန့်သတ်ထားသော
structure ခန့်မှန်းမှုသည် လည်ပတ်ကြည့်ရှုသည့် node `10,000` ခု သို့မဟုတ် depth `12` ဟူသော
၎င်း၏ကန့်သတ်ချက်များကို ကုန်ဆုံးစေလျှင် structurally heavy ဖြစ်သည်။

**အကြောင်းရင်း-** ၎င်းသည် upstream ပံ့ပိုးသူ၏ ပျက်ကွက်မှုမဟုတ်ဘဲ OmniRoute အတွင်း ရည်ရွယ်ချက်ရှိရှိ ပြုလုပ်သည့် load shedding ဖြစ်သည်။
Process တစ်ခုစီသည် ကြီးမားသော request body တစ်ခုကို ထိန်းသိမ်း၍ parse မလုပ်မီ အကန့်အသတ်ရှိသော
heavyweight capacity ကို ကြိုတင်ရယူရန် process-local guard တစ်ခုကို အသုံးပြုသည်။ SSE
တုံ့ပြန်မှု၏ သက်တမ်းတစ်လျှောက်လုံး heavyweight lease ကို ဆက်လက်ထိန်းထားသည်။

**#503-fanout:** ဤပြင်ဆင်မှုမတိုင်မီ guard သည် host memory ကို ထည့်သွင်းမစဉ်းစားဘဲ တစ်ပြိုင်နက်လုပ်ဆောင်မှုကို
သတ်မှတ်ထားသော တောင်းဆိုမှု အရေအတွက် (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`၊ မူလသတ်မှတ်ချက် `1`) ဖြင့်
ကန့်သတ်ထားသောကြောင့် coding-agent fan-out (subagent/CLI များစွာနှင့် ပုံမှန်အားဖြင့် 256 KB ထက်ကြီးသော body များ) သည်
ထိရောက်သော တစ်ပြိုင်နက်လုပ်ဆောင်နိုင်မှု ~1 အထိ ကျဆင်းသွားပြီး လုံးဝပုံမှန် load အောက်တွင်ပင် 503 ကို ပြန်ပေးခဲ့သည်။
ယခု guard သည် မိမိဘာသာ ချိန်ညှိသည်- process ၏ အမှန်တကယ် memory အမြင့်ဆုံးကန့်သတ်ချက်မှ
အရွယ်အစားတွက်ချက်ထားသော အလိုအလျောက်ရရှိသည့် ingest BYTE budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ဖြင့်
ထိန်းချုပ်ထားပြီး တိုက်ရိုက် resource-pressure signal ကိုလည်း စစ်ဆေးသည် — ထို့ကြောင့် heavyweight တောင်းဆိုမှုတစ်ခုထက်ပို၍
တစ်ပြိုင်နက်ရောက်ရှိလာရုံကြောင့် မဟုတ်ဘဲ host တွင် အမှန်တကယ် memory ဖိအားရှိသည့်အခါမှသာ load ကို လျှော့ချသည်။
အဟောင်း count cap (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ကို ဆက်လက်လိုက်နာသော်လည်း
၎င်းကို သင်က အတိအလင်း သတ်မှတ်ထားမှသာ ဖြစ်သည်။

Capacity မအားသည့်အခါ heavyweight တောင်းဆိုမှုသည် ထပ်မံကြိုးစားနိုင်သော `503` ကို မပြန်မီ
slot တစ်ခု လွတ်လာရန် `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` အထိ (မူလသတ်မှတ်ချက် `2000`၊ `0` သည် စောင့်ဆိုင်းမှုကို ပိတ်သည်)
ဦးစွာစောင့်ဆိုင်းသည်။ ဤကန့်သတ်ထားသော စောင့်ဆိုင်းမှုကြောင့် agent ပုံစံ client များ
(OpenCode, Claude Code, Cursor) က heavyweight sub-request များကို တစ်ပြိုင်နက် fan-out လုပ်သည့်အခါ
ချက်ချင်းငြင်းပယ်ခံရမှုများကြောင့် retry budget အားလုံးကို ကုန်ဆုံးစေပြီး လုပ်ငန်းအလယ်တွင် ရပ်တန့်သွားမည့်အစား
ရုတ်တရက်မြင့်တက်လာသော တောင်းဆိုမှုများကို တစ်ခုပြီးတစ်ခု လုပ်ဆောင်စေသည်။
လက်ရှိ heavyweight lease အသုံးပြုမှု၊ သတ်မှတ်ပြီးသော byte budget နှင့် တိုက်ရိုက် pressure severity တို့ကို
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) တွင် ဖော်ပြထားသည် — env var တစ်ခုခုကို
မပြင်ဆင်မီ ၎င်းတို့ကို စစ်ဆေးပါ။
Settings → Resilience → Request Queue → Concurrent Requests သည် ဤအရာကို မထိန်းချုပ်ပါ။ ထိုဆက်တင်သည်
သီးခြားပံ့ပိုးသူ request-queue ယန္တရားတစ်ခုကို ထိန်းချုပ်သည်။

**ပြင်ဆင်နည်း-**

1. ဦးစွာ ထပ်မံကြိုးစားပါ။ Client များသည် တောင်းဆိုမှုကို ချက်ချင်း
   ထပ်မလုပ်ဘဲ `Retry-After` ကို လိုက်နာပြီး backoff ကို အသုံးပြုသင့်သည်။
2. မည်သည့်အရာကိုမျှ မချိန်ညှိမီ `/api/monitoring/health` → `chatAdmission` ကို စစ်ဆေးပါ။ `countCapEnabled:
false` နှင့် လုံလောက်စွာကြီးမားသော `maxInflightBytes` ရှိခြင်းက အလိုအလျောက်ရရှိသည့် budget သည် ၎င်း၏
   အလုပ်ကို လုပ်ဆောင်နေပြီးဖြစ်ကြောင်း ဆိုလိုသည်။ `pressureSeverity` သည် `high`/`critical` ဖြစ်ခြင်းက host တွင်
   အမှန်တကယ် memory မလုံလောက်ကြောင်း ဆိုလိုသည် —
   ၎င်းကို admission env var ဖြင့် ပြင်ဆင်၍မရဘဲ RAM ပိုများရန် သို့မဟုတ် workload ကို ပိုသေးအောင်လုပ်ရန် လိုအပ်သည်။
3. `/api/monitoring/health` က အလိုအလျောက်ရရှိသည့် budget သည် သင့် host အတွက် အမှန်တကယ်
   အလွန်သေးငယ်ကြောင်း ပြသမှသာ (ရှားပါးသည် — ၎င်းသည် container မှ bare-metal အထိ အရွယ်အစားကို ချိန်ညှိပြီးသားဖြစ်သည်)
   legacy request-count cap ကို ပြန်လည်အသုံးပြုမည့်အစား `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ဖြင့် တိုက်ရိုက် override လုပ်ပါ။

တရားဝင် admission ဆက်တင်များအတွက် [environment-variable ရည်ညွှန်းချက်](../reference/ENVIRONMENT.md#4-security--authentication)
ကို ကြည့်ပါ။

## ရွေးချယ်အသုံးပြုနိုင်သော RAG / LLM ချို့ယွင်းမှု အမျိုးအစားခွဲခြားချက် (ပြဿနာ 16 ခု)

OmniRoute အသုံးပြုသူအချို့သည် gateway ကို RAG သို့မဟုတ် agent stack များ၏ ရှေ့တွင် ထားရှိကြသည်။ ထိုသို့ စီစဉ်ထားသည့်အခါ ထူးဆန်းသော ပုံစံတစ်ခုကို မကြာခဏ တွေ့ရတတ်သည်။ OmniRoute သည် ပုံမှန်အတိုင်း ကောင်းမွန်စွာ လည်ပတ်နေသည့်ပုံပေါ်သော်လည်း (provider များ လည်ပတ်နေခြင်း၊ routing profile များ မှန်ကန်ခြင်း၊ rate limit သတိပေးချက်များ မရှိခြင်း) နောက်ဆုံးအဖြေမှာ မှားယွင်းနေဆဲဖြစ်သည်။

လက်တွေ့တွင် ထိုဖြစ်ရပ်များသည် gateway ကိုယ်တိုင်ကြောင့် မဟုတ်ဘဲ downstream RAG pipeline ကြောင့် ဖြစ်လေ့ရှိသည်။

ထိုချို့ယွင်းမှုများကို ဖော်ပြရန် အားလုံးနားလည်နိုင်သော ဝေါဟာရများကို အသုံးပြုလိုပါက ထပ်တလဲလဲ ဖြစ်ပေါ်လေ့ရှိသည့် RAG / LLM ချို့ယွင်းမှုပုံစံ ဆယ့်ခြောက်မျိုးကို သတ်မှတ်ထားသော ပြင်ပ MIT license စာသားရင်းမြစ် WFGY ProblemMap ကို အသုံးပြုနိုင်သည်။ အကြမ်းဖျင်းအားဖြင့် အောက်ပါတို့ ပါဝင်သည်-

- retrieval လွဲချော်မှုနှင့် context နယ်နိမိတ်များ ပျက်ယွင်းခြင်း
- index နှင့် vector store များ ဗလာဖြစ်နေခြင်း သို့မဟုတ် အချက်အလက်ဟောင်းများ ဖြစ်နေခြင်း
- embedding နှင့် semantic အဓိပ္ပာယ် မကိုက်ညီခြင်း
- prompt တည်ဆောက်ပုံနှင့် context window ဆိုင်ရာ ပြဿနာများ
- ယုတ္တိကျသော ဆင်ခြင်မှု ပြိုကွဲခြင်းနှင့် ယုံကြည်မှုလွန်ကဲသော အဖြေများ
- ရှည်လျားသော chain နှင့် agent များ ပူးပေါင်းညှိနှိုင်းမှုဆိုင်ရာ ချို့ယွင်းမှုများ
- multi-agent memory နှင့် role လွဲချော်မှု
- deployment နှင့် bootstrap အစီအစဉ်ဆိုင်ရာ ပြဿနာများ

အယူအဆမှာ ရိုးရှင်းသည်-

1. မကောင်းသော တုံ့ပြန်ချက်တစ်ခုကို စုံစမ်းသည့်အခါ အောက်ပါတို့ကို မှတ်တမ်းတင်ပါ-
   - အသုံးပြုသူ၏ လုပ်ဆောင်စရာနှင့် request
   - OmniRoute ရှိ route သို့မဟုတ် provider combo
   - downstream တွင် အသုံးပြုခဲ့သည့် RAG context တစ်ခုခု (ရယူထားသော document များ၊ tool call များ စသည်)
2. ဖြစ်ရပ်ကို WFGY ProblemMap နံပါတ် တစ်ခု သို့မဟုတ် နှစ်ခုနှင့် ချိတ်ဆက်သတ်မှတ်ပါ (`No.1` … `No.16`)။
3. ထိုနံပါတ်ကို သင်၏ ကိုယ်ပိုင် dashboard၊ runbook သို့မဟုတ် incident tracker ထဲတွင် OmniRoute log များနှင့်အတူ သိမ်းဆည်းပါ။
4. သင်၏ RAG stack၊ retriever သို့မဟုတ် routing strategy ကို ပြောင်းလဲရန် လိုအပ်ခြင်းရှိ၊ မရှိ ဆုံးဖြတ်ရန် သက်ဆိုင်ရာ WFGY စာမျက်နှာကို အသုံးပြုပါ။

စာသားအပြည့်အစုံနှင့် လက်တွေ့အသုံးချနည်းများကို ဤနေရာတွင် ရရှိနိုင်သည် (MIT license၊ စာသားသီးသန့်)-

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute ၏ နောက်ကွယ်တွင် RAG သို့မဟုတ် agent pipeline များကို မလည်ပတ်ပါက ဤအပိုင်းကို လျစ်လျူရှုနိုင်သည်။

## v3.8.0 တွင် သိရှိထားသော ပြဿနာများ

v3.8.0 release နှင့် သက်ဆိုင်သော ပြဿနာများနှင့် လက်ရှိဖြေရှင်းကျော်လွှားနည်းများ။ နောက်ပိုင်း patch တစ်ခုတွင် ပြင်ဆင်ချက် ထည့်သွင်းလာပါက သက်ဆိုင်ရာ အကြောင်းအရာကို အပ်ဒိတ်လုပ်မည် သို့မဟုတ် ဖယ်ရှားမည်။

### Devin CLI auth ချို့ယွင်းမှုများ

**လက္ခဏာများ-**

- Devin အခြေပြု tool များကို ခေါ်ယူအသုံးပြုသည့်အခါ "Devin CLI ကို မတွေ့ပါ" သို့မဟုတ် "auth မအောင်မြင်ပါ" ဟု ပြသခြင်း
- CLI runtime စစ်ဆေးမှုတွင် `installed=false` ဟု ဖော်ပြခြင်း

**အကြောင်းရင်းများ-**

- `CLI_DEVIN_BIN` က မရှိသော path တစ်ခုကို ညွှန်ပြနေခြင်း
- Host တွင် Devin CLI ကို install မလုပ်ထားခြင်း

**ဖြေရှင်းနည်း-**

1. သင့် platform အတွက် Devin CLI ကို install လုပ်ပါ
2. `.env` တွင် `CLI_DEVIN_BIN=/usr/local/bin/devin` (သို့မဟုတ် အမှန်တကယ် path) ကို သတ်မှတ်ပါ
3. OmniRoute ကို restart လုပ်ပြီး **Dashboard → CLI Tools** မှ ပြန်လည်စမ်းသပ်ပါ

### Model cooldown တွင် ရပ်တန့်နေခြင်း (ကိုယ်တိုင် reset လုပ်ရန်)

**လက္ခဏာများ-**

- သက်တမ်းကုန်ဆုံးချိန် ကျော်လွန်ပြီးသည့်တိုင် model တစ်ခုက cooldown စာရင်းထဲတွင် ဆက်လက်ရှိနေခြင်း
- Timestamp သည် အတိတ်ကာလ ဖြစ်နေသော်လည်း combo routing က ထို model ကို ကျော်သွားနေဆဲဖြစ်ခြင်း

**ကိုယ်တိုင် reset လုပ်ရန်-**

- **Dashboard:** **Settings → Model Cooldowns** → သက်ရောက်မှုရှိသော card ပေါ်ရှိ **Re-enable** ကို နှိပ်ပါ
- **API:** Management auth header များနှင့်အတူ `DELETE /api/resilience/model-cooldowns`

### Command Code provider ချိတ်ဆက်မှု 403 ဖြင့် မအောင်မြင်ခြင်း

**လက္ခဏာများ-**

- Command Code provider ချိတ်ဆက်မှုကို စမ်းသပ်သည့်အခါ 403 ပြန်လာခြင်း
- Provider ကို အသစ်ထည့်သွင်းပြီးနောက် provider card တွင် "ခွင့်ပြုချက်မရှိ" ဟု ပြသခြင်း

**အကြောင်းရင်း-** OAuth flow မပြီးဆုံးခဲ့ခြင်း (callback ကို မရရှိခြင်း သို့မဟုတ် token ကို မသိမ်းဆည်းထားခြင်း)။

**ဖြေရှင်းနည်း-**

- OAuth flow ကို ပြန်လည်စတင်ရန် CLI မှ `omniroute providers` ကို run ပါ၊ သို့မဟုတ်
- **Dashboard → Providers → Command Code → Reconnect** မှ OAuth ကို ပြန်လည်လုပ်ဆောင်ပါ

### ModelScope က ပြင်းထန်သော 429 cooldown များကို ပြန်ပေးခြင်း

**လက္ခဏာများ-**

- Request အနည်းငယ်ကို အချိန်တိုအတွင်း ဆက်တိုက်ပို့ပြီးနောက် ModelScope တွင် အလွန်တိုတောင်းသော သို့မဟုတ် ချက်ချင်းစတင်သော cooldown များ ဖြစ်ပေါ်ခြင်း
- Combo routing က ModelScope ကို မျှော်လင့်ထားသည်ထက် စော၍ ကျော်သွားခြင်း

**အကြောင်းရင်း-** ModelScope သည် provider အလိုက် သီးသန့်ဖြစ်သော `Retry-After` header များကို ထုတ်ပေးသည်။ v3.8.0 တွင် ထို header များအတွက် သီးသန့်ကိုင်တွယ်မှု ပါဝင်သောကြောင့် ဗားရှင်းအဟောင်းများက ၎င်းတို့ကို ယေဘုယျ rate-limit အချက်ပြမှုများအဖြစ် မှားယွင်းဖတ်ရှုသည်။

**ဖြေရှင်းနည်း-**

- v3.8.0 သို့မဟုတ် နောက်ပိုင်းဗားရှင်းကို အသုံးပြုနေကြောင်း သေချာပါစေ
- **Settings → Resilience** အောက်တွင် `useUpstream429BreakerHints` toggle ကို ဖွင့်ထားကြောင်း စစ်ဆေးပါ

### Production တွင် OMNIROUTE_WS_BRIDGE_SECRET မရှိခြင်း

**လက္ခဏာများ-**

- Remote production host တစ်ခုပေါ်တွင် လည်ပတ်နေစဉ် Codex/Responses WebSocket bridge request တိုင်းတွင် 401 ပြန်လာခြင်း
- ချိတ်ဆက်ပြီးသည်နှင့် WebSocket bridge handshake ချက်ချင်း ပိတ်သွားခြင်း

**အကြောင်းရင်း-** Production environment တွင် `OMNIROUTE_WS_BRIDGE_SECRET` env var မရှိခြင်း။

**ဖြေရှင်းနည်း-**

1. ကျပန်း secret တစ်ခု ထုတ်လုပ်ပါ- `openssl rand -hex 32`
2. Production server env (နှင့် bridge နှင့် ဆက်သွယ်သည့် client တစ်ခုခု) တွင် `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ကို သတ်မှတ်ပါ
3. OmniRoute ကို restart လုပ်ပါ

### Responses API: background mode ကို synchronous သို့ လျှော့ချလုပ်ဆောင်ခြင်း

**လက္ခဏာများ-**

- မှတ်တမ်းတင်ထားသော သတိပေးချက်- `background mode degraded to synchronous`
- `background: true` request တစ်ခုက background job handle အစား ပုံမှန် synchronous response ကို ပြန်ပေးခြင်း

**အကြောင်းရင်း-** v3.8.0 တွင် Responses API ပေါ်ရှိ `background: true` ကို သတိပေးချက်တစ်ခု ထုတ်ပေးလျက် synchronous execution သို့ ရည်ရွယ်ချက်ရှိရှိ လျှော့ချထားသည်။ Async background execution အပြည့်အစုံကို အနာဂတ်တွင် ပံ့ပိုးပေးမည်ဖြစ်သည်။

**ဖြေရှင်းနည်း-**

- `background` မပါဘဲ ခေါ်ဆိုရန် client ကို ချိန်ညှိပါ၊ သို့မဟုတ်
- Async background mode အပြည့်အစုံ ပါဝင်လာမည့် နောက်ပိုင်း release ကို စောင့်ပါ (changelog ကို စောင့်ကြည့်ပါ)

**ဖြေရှင်းနည်း — အချိန်ပမာဏကို တိုးမြှင့်ပါ:**

```bash
# env var မှတစ်ဆင့် (စတင်မှုများအကြား ဆက်လက်သက်ရောက်သည်):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 မိနစ်
omniroute serve

# CLI flag မှတစ်ဆင့် (တစ်ကြိမ်သာ):
omniroute serve --ready-timeout 180000
```

မူလသတ်မှတ်ချက်မှာ 60 000 ms (60 s) ဖြစ်သည်။ သတိပေးချက်သည် အသိပေးရန်အတွက်သာဖြစ်ပြီး server သည် နောက်ကွယ်တွင် ဆက်လက်စတင်နေမည်ဖြစ်ကာ boot ပြီးဆုံးသည်နှင့် ချိတ်ဆက်အသုံးပြုနိုင်မည်ဖြစ်သည်။

`OMNIROUTE_READY_TIMEOUT_MS` အကြောင်း အသေးစိတ်အချက်အလက်အပြည့်အစုံအတွက် [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) ကို ကြည့်ပါ။
