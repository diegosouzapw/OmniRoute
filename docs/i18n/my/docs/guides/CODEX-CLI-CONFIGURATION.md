OpenAI နှင့် ကိုက်ညီသော backend အဖြစ် OmniRoute ကို ညွှန်ပြထားသည့် Codex CLI အသုံးပြုနည်း အပြည့်အစုံ။

---

> **TOML သာလျှင် အမှန်တကယ် အလုပ်လုပ်သော format ဖြစ်သည်။** ခေတ်မီ Codex သည် `~/.codex/config.toml`
> ကိုသာ သီးသန့်ဖတ်ရှုသည် (codex-cli 0.147.0 ဖြင့် အတည်ပြုထားသည်။ `codex --help` တွင်
> `-c/--config` override များကို "`~/.codex/config.toml` မှ load လုပ်သည်" ဟု ဖော်ပြထားသည်)။ ယခင်
> `~/.codex/config.yaml` သည် အဟောင်း npm CLI အတွက်ဖြစ်ပြီး မည်သည့်အသိပေးချက်မျှမရှိဘဲ လျစ်လျူရှုခံရသည်။
> Dashboard generator (`/api/cli-tools/apply`, tool `codex`) သည် ထိန်းသိမ်းသည့်နည်းလမ်းဖြင့် merge လုပ်ထားသော
> TOML ကို ရေးသားသည် — ရှိပြီးသား key များနှင့် အခြား provider block များကို မပြောင်းလဲဘဲ ထိန်းသိမ်းထားပြီး၊
> API key ကို `OMNIROUTE_API_KEY` ထဲတွင်သာ ထားရှိသည် (ဖိုင်ထဲတွင် လုံးဝမထားပါ)၊ ထို့အပြင် ကျန်ရှိနေသေးသော အဟောင်း
> `config.yaml` ကို မထိဘဲ migration မှတ်ချက်အဖြစ် အစီရင်ခံသည်။

## တိုက်ရိုက်ကူးထည့်နိုင်သော config.toml

`<YOUR_HOST>` နှင့် `<YOUR_KEY>` ကို သင့်တန်ဖိုးများဖြင့် အစားထိုးပါ-

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # tool call တစ်ခုစီအတွက် history သိုလှောင်မှု အများဆုံးပမာဏ

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc သို့မဟုတ် ~/.zshrc — key တန်ဖိုးအမှန်၊ config.toml ထဲတွင် လုံးဝမထားပါ
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT app အတွင်း ပူးတွဲပါရှိသော Codex

ChatGPT desktop app မှတစ်ဆင့် Codex ကို install လုပ်ထားပါက `codex` binary သည်
app bundle အတွင်း၌သာ ရှိနိုင်ပြီး သင့် shell `PATH` ထဲတွင် မရှိသေးနိုင်ပါ။ Resources
directory ကို သင့် shell startup file ထဲသို့ ထည့်ပါ-

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Shell အသစ်တစ်ခုဖွင့်ပြီးနောက် အောက်ပါအတိုင်း စစ်ဆေးပါ-

```bash
command -v codex
codex --version
```

### Authentication မလိုသော local OmniRoute: placeholder key တစ်ခုဖြင့် လုံလောက်သည်

ပထမဆုံး request ကို CLI မှ မပို့မီ `env_key` က အမည်သတ်မှတ်ထားသော environment variable
ရှိမရှိကို Codex က စစ်ဆေးသည်။ သင့် **local** OmniRoute instance တွင် auth
မလိုအပ်ပါက ဗလာမဟုတ်သော placeholder တစ်ခုခုကို အသုံးပြုနိုင်သည်-

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

သင့် OmniRoute server ကို ကာကွယ်ထားလျှင် သို့မဟုတ် remote server ဖြစ်လျှင် key အစစ်ကို အသုံးပြုပါ။

> **အသုံးများသော host ရွေးချယ်စရာများ**
>
> | ဝင်ရောက်မှု   | URL                           |
> | ------------- | ----------------------------- |
> | Local network | `http://192.168.0.1:20128/v1` |
> | Tailscale     | `http://100.x.x.x:20128/v1`   |
> | Loopback      | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — model အားလုံးအတွက် အဘယ်ကြောင့် အလုပ်လုပ်သနည်း

Codex CLI သည် 2026 ခုနှစ် ဖေဖော်ဝါရီလတွင် `wire_api = "chat"` (Chat Completions) ကို ပယ်ဖျက်ရန် သတ်မှတ်ခဲ့ပြီး ယခုအခါ `wire_api = "responses"` (OpenAI Responses API) ကို **မဖြစ်မနေ လိုအပ်သည်**။ `wire_api = "chat"` ဟု သတ်မှတ်ခြင်းသည် v0.138 မှစ၍ စတင်ချိန်တွင် ချက်ချင်း crash ဖြစ်စေသည်။

GLM နှင့် Kimi အပါအဝင် provider အများအပြားသည် Chat Completions endpoint ကိုသာ ပံ့ပိုးနေဆဲဖြစ်သည်။ ယခုအခါ DeepSeek V4 သည် မူရင်း Responses API အပြင် Anthropic နှင့် ကိုက်ညီသော endpoint တစ်ခုကိုလည်း ပံ့ပိုးထားသည်။ OmniRoute သည် Responses ကို default အဖြစ် အသုံးပြုပြီး DeepSeek connection တစ်ခုစီအား Anthropic compatibility ကို ရွေးချယ်ခွင့်ပေးသည်။

**OmniRoute သည် ဤကိစ္စကို နောက်ကွယ်တွင် အလိုအလျောက် ဖြေရှင်းပေးသည်-**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute သည် provider ၏ မူရင်း protocol ကို ရွေးချယ်ပြီး လိုအပ်သည့်အခါ ပြောင်းလဲပေးသည်
    → POST /responses (DeepSeek V4) သို့မဟုတ် /chat/completions (Mistral / GLM / Kimi / အခြားများ)
```

OmniRoute ကို အသုံးပြုသည့်အခါ သီးခြား translation proxy တစ်ခု လုံးဝမလိုအပ်ပါ။ **Model အားလုံးသည် `wire_api = "responses"` ကို အသုံးပြုသည်** — ကျန်အရာအားလုံးကို OmniRoute က ကိုင်တွယ်ပေးသည်။

> **`wire_api` သည် default ဖြစ်သည်** — ဤ field ၏ default တန်ဖိုးမှာ `"responses"` ဖြစ်ပြီး `config.toml` မှ လုံးဝချန်လှပ်ထားနိုင်သည်။ ရည်ရွယ်ချက်ကို မှတ်တမ်းတင်လိုသည့်အခါမှသာ ၎င်းကို အတိအလင်း သတ်မှတ်ပါ။

## ကွန်တက်စ်ဝင်းဒိုးနှင့် ချုံ့သိမ်းခြင်း

### တိုကင်ပြင်ဆင်သတ်မှတ်ချက် အကွက်များ

| အကွက်                            | ဖော်ပြချက်                                                                                                                                                                                                                                                                  |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | လက်ရှိအသုံးပြုနေသော မော်ဒယ်အတွက် စုစုပေါင်း တိုကင်ဘတ်ဂျက်။ မော်ဒယ်က ကြေညာထားသော ကန့်သတ်ချက်အတိုင်း သတ်မှတ်ပါ။                                                                                                                                                               |
| `model_auto_compact_token_limit` | မှတ်တမ်းကို အလိုအလျောက် ချုံ့သိမ်းစေမည့် သတ်မှတ်အဆင့်။ **အများဆုံး- `model_context_window` ၏ 90%** — 90% အထက်တန်ဖိုးများကို အသိပေးခြင်းမရှိဘဲ လျစ်လျူရှုသည်။                                                                                                                |
| `tool_output_token_limit`        | ကိရိယာခေါ်ဆိုမှုတစ်ကြိမ်စီ၏ အထွက်မှ မှတ်တမ်းထဲတွင် သိမ်းဆည်းမည့် တိုကင်အရေအတွက် ကန့်သတ်ချက်။ ကြီးမားသော ကိရိယာတုံ့ပြန်ချက်တစ်ခုတည်းက ဝင်းဒိုးတစ်ခုလုံး ပြည့်သွားခြင်းကို ကာကွယ်ပေးသည်။ **၎င်းသည် အများဆုံးအထွက်ပမာဏ မဟုတ်ပါ** — မှတ်တမ်းသိမ်းဆည်းမှု ကန့်သတ်ချက်သာ ဖြစ်သည်။ |
| `compact_prompt`                 | ချုံ့သိမ်းစဉ် အသုံးပြုသည့် စနစ်ပရောင့်အတွက် တိုက်ရိုက်အစားထိုးသတ်မှတ်ချက် (v0.138+)။                                                                                                                                                                                        |

> **`model_max_output_tokens` ဆိုင်ရာ မှတ်ချက်**- ဤအကွက်သည် **Codex CLI ပြင်ဆင်သတ်မှတ်မှု စကီးမား၏ အစိတ်အပိုင်းမဟုတ်ပါ** (Codex Rust ကုဒ်ဘေ့စ်တွင် မပါဝင်ပါ)။ သတ်မှတ်ထားလျှင် အသိပေးခြင်းမရှိဘဲ လျစ်လျူရှုသည်။ ၎င်းကို အားမကိုးပါနှင့် — မှတ်တမ်းထဲတွင် သိမ်းဆည်းမည့် ကိရိယာအထွက်ပမာဏကို ထိန်းချုပ်ရန် `tool_output_token_limit` ကို အသုံးပြုပါ။

## ဆင်ခြင်သုံးသပ်မှု အားထုတ်မှု

မော်ဒယ်က တုံ့ပြန်ခြင်းမပြုမီ မည်မျှ “စဉ်းစားမည်” ကို ထိန်းချုပ်သည်။

| တန်ဖိုး  | အသုံးပြုရန်                                                              |
| -------- | ------------------------------------------------------------------------ |
| `none`   | ဆင်ခြင်သုံးသပ်မှု မရှိ — တိုက်ရိုက်တုံ့ပြန်မှု                           |
| `low`    | ရိုးရှင်းသော အလုပ်များ (အမည်ပြောင်းခြင်း၊ ပုံစံချခြင်း)                  |
| `medium` | မသတ်မှတ်ထားသည့်အခါ **ဆာဗာ၏ ပုံသေတန်ဖိုး**                                |
| `high`   | အလယ်အလတ်အဆင့် အလုပ်များ (ကုဒ်ပြန်လည်ဖွဲ့စည်းခြင်း၊ အမှားရှာဖွေခြင်း)     |
| `xhigh`  | ဗိသုကာဒီဇိုင်း၊ နက်ရှိုင်းသော ခွဲခြမ်းစိတ်ဖြာမှု၊ ရှုပ်ထွေးသော ပြဿနာများ |

```bash
# ခေါ်ယူမှုတစ်ကြိမ်ချင်းအလိုက် ထပ်မံသတ်မှတ်ခြင်း
codex -c model_reasoning_effort=low "ကိန်းရှင် x ကို count ဟု အမည်ပြောင်းပါ"
codex -c model_reasoning_effort=xhigh "အထောက်အထားစိစစ်ရေး မော်ဂျူးကို ဒီဇိုင်းရေးဆွဲပါ"
```

Desktop က ကုဒ်ဝှက်ထားသော blob များကိုသာမက စဉ်းစားထားသည့် စာသားကိုပါ ဖော်ပြနိုင်ရန် ဆင်ခြင်သုံးသပ်မှု **အကျဉ်းချုပ်** ကိုလည်း သတ်မှတ်ပါ-

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # ပံ့ပိုးပေးသည့်အခါ ultra ကိုလည်း အသုံးပြုနိုင်သည်
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute စဉ်းစားမှု ဘတ်ဂျက် (ဆာဗာဆက်တင်)

OmniRoute host တွင် Codex ၏ အားထုတ်မှု/အကျဉ်းချုပ်သည် upstream သို့ ရောက်ရှိနိုင်ရန် **Settings → AI → Thinking Budget** ကို **`passthrough`** အဖြစ် သတ်မှတ်ထားရမည်။ **`auto` strips** မုဒ်သည် client ၏ `reasoning` / `reasoning_effort` field အားလုံးကို ဖယ်ရှားပြီး Codex ကို မှန်ကန်စွာ ပြင်ဆင်သတ်မှတ်ထားသည့်တိုင် စဉ်းစားမှု panel များကို ဗလာဖြစ်စေမည်။

လမ်းညွှန်အပြည့်အစုံ- [THINKING_BUDGET.md](./THINKING_BUDGET.md)။

ချုံ့ခြင်းနှင့် prompt cache တို့သည် သီးခြားစီဖြစ်ပြီး `passthrough` အောက်တွင် ဆက်လက်အလုပ်လုပ်သည်။

## Profile များ — မော်ဒယ်/လုပ်ငန်းစဉ်တစ်ခုချင်းအလိုက် အမည်ပေးထားသော ပြင်ဆင်သတ်မှတ်မှုများ

Profile များဖြင့် flag တစ်ခုတည်းကို အသုံးပြုပြီး မော်ဒယ်နှင့် context window ကို ပြောင်းနိုင်သည်။ Profile တစ်ခုစီသည် အခြေခံ `config.toml` အပေါ် ထပ်လွှမ်းသက်ရောက်သည့် အလွှာမခွဲထားသော
`~/.codex/<name>.config.toml` ဖိုင်တစ်ခု ဖြစ်သည်။

> **အမည်ပေးခြင်း စည်းမျဉ်း (Codex CLI v0.137+):** ဖိုင်သည် `~/.codex/<name>.config.toml` ဖြစ်ရမည် — **`profile-` ရှေ့ဆက်စာလုံး မပါရ**။
> CLI သည် `-p kimi-k27` → `~/.codex/kimi-k27.config.toml` ဟု ဖြေရှင်းသတ်မှတ်သည်။ ဖိုင်ကို ရှာမတွေ့ပါက ပုံသေတန်ဖိုးကို အသံတိတ် အသုံးပြုမည်။

```bash
codex --profile kimi-k27 "ဤ codebase ၏ လိုင်း 10k ကို ခွဲခြမ်းစိတ်ဖြာပါ"
codex -p glm52 "ဗိသုကာဒီဇိုင်းကို ပြန်လည်သုံးသပ်ပါ"

```

## `omniroute setup-codex` ဖြင့် profile များကို အလိုအလျောက် ဖန်တီးခြင်း

OmniRoute ကို VPS တစ်ခုပေါ်တွင် အသုံးပြုနေပါက လက်ရှိ model catalog မှ profile ဖိုင်များကို အလိုအလျောက် ဖန်တီးနိုင်သည်-

```bash
omniroute setup-codex

# မည်သည့်စက်မှမဆို — သင့် VPS ကို ညွှန်ပေးပါ
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# ဖိုင်များမရေးသားဘဲ အစမ်းကြည့်ရှုခြင်း
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# GLM နှင့် Kimi profile များကိုသာ ဖန်တီးခြင်း
omniroute setup-codex --only glm,kimi

# စိတ်ကြိုက် directory တစ်ခုသို့ ရေးသားခြင်း
omniroute setup-codex --codex-home /path/to/.codex
```

ဤ command သည် `/v1/models` ကို ရယူပြီး၊ သိရှိထားသော model များအတွက် ကောင်းစွာချိန်ညှိထားသည့် profile များကို အသုံးပြုကာ၊ အခြား တွဲဖက်အသုံးပြုနိုင်သော text model များအတွက် catalog metadata ကို အရန်အဖြစ် အသုံးပြုပြီး တစ်ခုစီအတွက် `~/.codex/<name>.config.toml` ကို ရေးသားပေးသည်။ Idempotent ဖြစ်သောကြောင့် ပြန်လည်လုပ်ဆောင်ရန် ဘေးကင်းသည်။

အောင်မြင်သော provider model ရှာဖွေတွေ့ရှိမှု/တင်သွင်းမှုတစ်ခုက လက်ရှိ catalog ကို ပြောင်းလဲပြီးနောက် OmniRoute သည် အဆိုပါ profile ဖိုင်များကိုပင် **အလိုအလျောက် sync** လုပ်နိုင်သည်။ ဤလုပ်ဆောင်ချက်ကို **ရွေးချယ်ဖွင့်ရပြီး ပုံမှန်အားဖြင့် ပိတ်ထားသည်**- **CLI Code dashboard** မှ ("CLI profile auto-sync" → Codex) ဖွင့်/ပိတ်နိုင်သည်၊ သို့မဟုတ် `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` ဟု သတ်မှတ်ပါ (`CLI_ALLOW_CONFIG_WRITES` ကိုလည်း လိုက်နာပြီး ၎င်းသည် ပုံမှန်အားဖြင့် ဖွင့်ထားသည်)။ ဖွင့်ထားသောအခါ သီးခြား `~/.codex/*.config.toml` profile ဖိုင်များကိုသာ ရေးသားသည်။ လက်ရှိအသုံးပြုနေသော/ပုံမှန် `~/.codex/config.toml`၊ Codex-lb ဆက်တင်များ၊ auth သို့မဟုတ် provider ရွေးချယ်မှုတို့ကို မည်သည့်အခါမျှ မပြောင်းလဲပါ။

## အချိန်ကြာမြင့်စွာ လုပ်ဆောင်ရသော task များ

OmniRoute ၏ မူလသတ်မှတ်ချက်နှစ်ခုသည် နာရီပေါင်းများစွာ ကြာမြင့်သော Codex CLI session များကို သတိမပြုမိဘဲ ပျက်စီးစေနိုင်သည်။ နှစ်ခုစလုံးသည် Codex CLI setting မဟုတ်ဘဲ OmniRoute ဘက်တွင် ရှိသည်။ Account များကို pin လုပ်ထားပြီး idle cutoff များကို ပိတ်ထားသည့် upstream proxy များမှ config ကို ပြောင်းရွှေ့အသုံးပြုသူများသည် ပြဿနာနှစ်ခုစလုံးကို မကြာခဏ ကြုံတွေ့ရပြီး OmniRoute သည် “ကြာမြင့်သော session တစ်ခုကို မထိန်းထားနိုင်” ဟု ကောက်ချက်ချတတ်ကြသည်။

| လက္ခဏာ                                                                                                        | ဖြစ်နိုင်ခြေရှိသော အကြောင်းရင်း                                                  | ချိန်ညှိချက်             |
| ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------ |
| Session က account များကို ဆက်တိုက်ပြောင်းနေသည် / turn များကြားတွင် prompt-cache ဆက်လက်တည်ရှိမှု ပျောက်ဆုံးသည် | Session affinity TTL သည် `0` ဖြစ်သည် (ပိတ်ထားသည်)                                | `sessionAffinityTtlMs`   |
| Client ဘက်သို့ အသိပေး prompt မရှိဘဲ စဉ်းစားတွက်ချက်နေစဉ်အတွင်း connection ပြတ်သွားသည်                         | Upstream chunk မရှိဘဲ 10 မိနစ်ကြာပြီးနောက် stream idle watchdog အလုပ်လုပ်သွားသည် | `STREAM_IDLE_TIMEOUT_MS` |

ဆက်စပ်ဆွေးနွေးချက်များ- [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (ကြာမြင့်သော task ပြတ်တောက်မှုများ), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (affinity ကို မူလအတိုင်း ပိတ်ထားရသည့်အကြောင်းရင်း)။ ခြေရာခံရန်- [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287)။

### 1. Session affinity — စကားဝိုင်းတစ်ခုကို account တစ်ခုတည်းတွင် pin လုပ်ထားရန်

**မူလသတ်မှတ်ချက်-** `sessionAffinityTtlMs = 0` (ပိတ်ထားသည်)။

**သတ်မှတ်ရမည့်နေရာ**

- Dashboard → **Settings → Routing** → **Session affinity** → **Affinity TTL (seconds)** (`ComboDefaultsTab`)
- သို့မဟုတ် **milliseconds** ဖြင့် `sessionAffinityTtlMs` ကို ထည့်၍ setting များကို PATCH လုပ်ပါ (Zod အပိုင်းအခြား `0`–`86_400_000`၊ ဆိုလိုသည်မှာ အများဆုံး 24 နာရီ)

> #7274 တွင် Codex အတွက်သာဖြစ်သော `codexSessionAffinityTtlMs` မှ အမည်ပြောင်းထားသည်။ ယခင် key ကို ဖတ်ရန်သာသုံးနိုင်သော alias အဖြစ် လက်ခံနေဆဲဖြစ်သော်လည်း config အသစ်များတွင် `sessionAffinityTtlMs` ကို အသုံးပြုသင့်သည်။ ယခုအခါ TTL သည် `0` ထက်ကြီးသည်နှင့် affinity သည် Codex အတွက်သာမက **မည်သည့်** provider အတွက်မဆို သက်ရောက်သည် — [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Session affinity ကို ကြည့်ပါ။

**0 အဖြစ် ဆက်ထားသောအခါ ပျက်စီးသည့်အရာ**

Turn များစွာပါဝင်သော Codex စကားဝိုင်း၏ turn တစ်ခုချင်းစီကို လက်ရှိအသုံးပြုနေသော combo strategy ဖြင့် သီးခြားစီ route လုပ်သောကြောင့် **turn တစ်ခုချင်းစီတွင် မတူညီသော account** သို့ ရောက်ရှိနိုင်သည်။ ထိုအရာက upstream session / prompt-cache ၏ ဆက်လက်တည်ရှိမှုကို ပျက်စီးစေသည်။ TTL သည် `0` ထက်ကြီးသောအခါမှသာ OmniRoute က Codex session header များ (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) နှင့် `prompt_cache_key` / `session_id` ကဲ့သို့သော body field များကို စစ်ဆေးအသုံးပြုသည် (`src/sse/services/auth.ts` ရှိ `extractSessionAffinityKey`)။

**နာရီပေါင်းများစွာ ကြာမြင့်သော task တစ်ခုတည်းအတွက် အကြံပြုချက်**

TTL ကို **task ၏ ခန့်မှန်း wall-clock ကြာချိန်ထက် ပိုမိုမြင့်မားစွာ** သတ်မှတ်ပါ (UI ၏ အများဆုံးတန်ဖိုးမှာ **86400 seconds** = 24 နာရီ ဖြစ်သည်)-

| ခန့်မှန်း task ကြာချိန် | Affinity TTL (UI၊ seconds) | `sessionAffinityTtlMs` |
| ----------------------- | -------------------------- | ---------------------- |
| နာရီအနည်းငယ်            | `14400` (4h)               | `14400000`             |
| တစ်ညလုံး / ~12h         | `43200` (12h)              | `43200000`             |
| တစ်နေ့လုံး              | `86400` (24h၊ အများဆုံး)   | `86400000`             |

Opt-in ပြုလုပ်ရခြင်းမှာ ရည်ရွယ်ချက်ရှိရှိဖြစ်သည်- affinity ကို ပိတ်ထားခြင်းက account များအကြား load-balancing ကို ဦးစားပေးပြီး၊ ဖွင့်ထားခြင်းက ကြာမြင့်သော agent session တစ်ခု၏ ဆက်လက်တည်ရှိမှုကို ဦးစားပေးသည်။ ဤလမ်းညွှန်သည် မူလသတ်မှတ်ချက်ကို **မပြောင်းလဲပါ** — ကြာမြင့်သော Codex task များကို လုပ်ဆောင်နေသည့် operator များသည် ကိုယ်တိုင် opt in ပြုလုပ်ရမည်။

### 2. Stream idle timeout — အသံတိတ်စွာ စဉ်းစားတွက်ချက်နေသော turn များကို မဖြတ်တောက်ပါနှင့်

**မူလသတ်မှတ်ချက်-** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 မိနစ်)။ မသတ်မှတ်ထားပါက ၎င်းသည် `REQUEST_TIMEOUT_MS` မှ ဆက်ခံသည်။ မျှဝေအသုံးပြုသော အခြေခံတန်ဖိုးမှာလည်း 600000 ဖြစ်သည်။ [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Timeouts ကို ကြည့်ပါ။

**မူလသတ်မှတ်ချက်တွင် ပျက်စီးသည့်အရာ**

Codex reasoning / tool turn တစ်ခုသည် **အမှန်တကယ် upstream chunk မရှိဘဲ** 10 မိနစ်ကျော် တိတ်ဆိတ်နေပါက SSE idle watchdog (`open-sse/utils/stream.ts`) က အတင်းအကျပ် ပိတ်ပစ်ပါသည်။ Client ဘက်တွင် အသိပေးချက်မရှိဘဲ connection ပြတ်တောက်သွားခြင်းကိုသာ မကြာခဏ မြင်ရပြီး — “အသိပေးချက်တစ်စုံတစ်ရာမရှိဘဲ အလိုအလျောက် ရပ်သွားသည်” ဆိုသည့် အခြေအနေနှင့် ကိုက်ညီပါသည်။

အရေးကြီးသော အသေးစိတ်အချက်- OmniRoute ၏ ဖန်တီးထားသော SSE **heartbeat သည် idle clock ကို ပြန်မစပါ**။ အမှန်တကယ် upstream body chunk တစ်ခုရောက်ရှိမှသာ `lastChunkTime` ကို အပ်ဒိတ်လုပ်ပါသည်။ “စဉ်းစားနေဆဲ” ဖြစ်သော တိတ်ဆိတ်နေသည့် model ကို watchdog ၏ ရှုထောင့်မှကြည့်လျှင် ရပ်တန့်နေသော upstream နှင့် ခွဲခြားမရပါ။

ဆက်စပ်နေသော Undici body လှုပ်ရှားမှုမရှိခြင်း- `FETCH_BODY_TIMEOUT_MS` (၎င်းသည်လည်း တူညီသော 10 မိနစ် baseline ကို မူလတန်ဖိုးအဖြစ် သတ်မှတ်ထားပြီး `0` ဖြင့် ပိတ်နိုင်သည်)။ Streaming အတွက် `FETCH_TIMEOUT_MS` သည် connection တည်ဆောက်ခြင်း / ပထမဆုံး headers ရရှိခြင်းအထိသာ အကျုံးဝင်သည် — stream စတင်လည်ပတ်ပြီးနောက် ရပ်တန့်မှုများကို `STREAM_IDLE_TIMEOUT_MS` နှင့် `FETCH_BODY_TIMEOUT_MS` တို့က ထိန်းချုပ်ပါသည်။

**နာရီပေါင်းများစွာကြာသည့် တစ်ခုတည်းသော task အတွက် အကြံပြုချက်**

OmniRoute process environment (`.env` / compose / systemd) တွင်-

```bash
# ကြာမြင့်သော reasoning turn များအတွက် stream idle နှင့် body လှုပ်ရှားမှုမရှိခြင်းဆိုင်ရာ ဖြတ်တောက်မှုများကို ပိတ်ရန်
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

သို့မဟုတ် သင်မျှော်မှန်းထားသော အကြာဆုံး တိတ်ဆိတ်ချိန်ထက် ပိုမြင့်အောင် သတ်မှတ်ပါ (တန်ဖိုးများသည် milliseconds ဖြစ်သည်)-

```bash
# ဥပမာ- upstream chunk များကြား 2 နာရီအထိ တိတ်ဆိတ်နေမှုကို ခွင့်ပြုရန်
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

ဤ env vars များကို ပြောင်းလဲပြီးနောက် OmniRoute ကို restart လုပ်ပါ။

### လက်တွေ့လုပ်ဆောင်နည်း — နာရီပေါင်းများစွာကြာသည့် Codex task

1. **Account ကို သတ်မှတ်ချိတ်ဆက်ထားပါ-** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12h) သို့မဟုတ် `86400` (အများဆုံး 24h)။
2. OmniRoute ၏ environment တွင် **idle ဖြတ်တောက်ချိန်များကို မြှင့်ပါ / ပိတ်ပါ**-

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. ပုံမှန် Codex `config.toml` (`wire_api = "responses"`, မှန်ကန်သော `base_url`, `OMNIROUTE_API_KEY`) ကို ဆက်လက်အသုံးပြုပါ — ဤအပြုအမူနှစ်ခုအတွက် Codex ဘက်တွင် affinity/idle ဆိုင်ရာ ချိန်ညှိချက်များ မရှိပါ။
4. OmniRoute ကို restart လုပ်ပြီးနောက် ကြာမြင့်သော Codex task ကို စတင်ပါ။

### မူလတန်ဖိုးများဆိုင်ရာ ဆုံးဖြတ်ချက် (#7287)

| ချိန်ညှိချက်             | ဖြန့်ချိသည့် မူလတန်ဖိုး | ဤလမ်းညွှန်တွင် ပြောင်းလဲမည်လား?                                                                                                              |
| ------------------------ | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (ပိတ်ထား)           | **မပြောင်းပါ** — ရွေးချယ်ဖွင့်ရသည့်စနစ်အဖြစ် ဆက်ထားမည် (load-balancing နှင့် continuity တို့အကြား ရွေးချယ်မှု၊ Discussion #5718 ကို ကြည့်ပါ) |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 မိနစ်)     | **မပြောင်းပါ** — ယေဘုယျ traffic အတွက် 10 မိနစ်အတိုင်း ဆက်ထားမည်၊ ကြာမြင့်သော Codex ကို လည်ပတ်သူများက ၎င်းကို မြှင့်မည် သို့မဟုတ် ပိတ်မည်     |

မူလတန်ဖိုးတစ်ခုခုကို စနစ်တစ်ခုလုံးအတွက် ပြောင်းပြန်လှန်ခြင်းသည် Codex တစ်ခုတည်းအတွက်သာ မဟုတ်ဘဲ instance တစ်ခု၏ client အားလုံးအတွက် အပြုအမူကို ပြောင်းလဲစေမည်ဖြစ်သည်။ ချိန်ညှိချက်များကို မှတ်တမ်းတင်ထားပါ၊ အတိအကျ operator ဆုံးဖြတ်ချက်တစ်ခုက အခြားနည်းလမ်းကို မညွှန်ကြားမချင်း မူလတန်ဖိုးများကို မပြောင်းဘဲထားပါ။

### Idle ဖြတ်တောက်မှုများကို ရောဂါရှာဖွေခြင်း

Idle watchdog အလုပ်လုပ်သောအခါ OmniRoute သည် အောက်ပါပုံစံနှင့်တူသော log စာကြောင်းတစ်ကြောင်းကို မှတ်တမ်းတင်ပါသည်-

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

`Idle timeout: no data from` ကို grep လုပ်ပါ (သို့မဟုတ် code `stream_idle_timeout` / error အမည် `StreamIdleTimeoutError`)။ Provider segment သည် ထို request အတွက် OmniRoute အသုံးပြုခဲ့သည့်အရာ (`codex`, အခြား provider id တစ်ခု သို့မဟုတ် မသိပါက `provider`) ဖြစ်ပြီး — အမြဲတမ်း စာသားအတိုင်း `codex` ဖြစ်နေမည် မဟုတ်ပါ။

## ပြဿနာဖြေရှင်းခြင်း

**`Error: wire_api = "chat" is no longer supported`**
သင့် config မှ `wire_api = "chat"` ကို ဖယ်ရှားပါ။ `wire_api = "responses"` ဟု သတ်မှတ်ပါ၊ သို့မဟုတ် အဆိုပါ field ကို ချန်လှပ်ထားပါ (v0.138 မှစ၍ မူလတန်ဖိုးမှာ `"responses"` ဖြစ်သည်)။

**`Error: model not found`**
မှန်ကန်သော prefix ဖြင့် model သည် OmniRoute ထဲတွင် ရှိကြောင်း စစ်ဆေးပါ။ `omniroute models list` ကို အသုံးပြုပါ၊ သို့မဟုတ် `/dashboard/providers/<provider>` ကို ဖွင့်ပါ။

**`Authentication error`**
`OMNIROUTE_API_KEY` ကို export လုပ်ထားကြောင်း `echo $OMNIROUTE_API_KEY` ဖြင့် အတည်ပြုပါ။

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex သည် ပထမဆုံး request မပြုလုပ်မီ env var ရှိကြောင်း စစ်ဆေးအတည်ပြုသည်။ ကာကွယ်ထားသော server များအတွက် တကယ့် key တစ်ခုကို export လုပ်ပါ၊ သို့မဟုတ် သင့် **local** OmniRoute instance တွင် auth မလိုအပ်ပါက `OMNIROUTE_API_KEY=local` ကဲ့သို့ ဗလာမဟုတ်သော placeholder တစ်ခုကို အသုံးပြုပါ။ ၎င်းကို `~/.bashrc` သို့မဟုတ် `~/.zshrc` ထဲသို့ ထည့်ခဲ့ပါက shell ကို ပြန်လည်စတင်ပါ။

**`Connection refused`**
OmniRoute အလုပ်လုပ်နေကြောင်းနှင့် `base_url` ၏ host/port သည် သင့် network (local၊ Tailscale သို့မဟုတ် VPS) အတွက် မှန်ကန်ကြောင်း စစ်ဆေးပါ။

**Context limit အနီးတွင် session ပျက်သွားခြင်း**
`model_context_window` နှင့် `model_auto_compact_token_limit` ကို တိတိကျကျ သတ်မှတ်ပါ။ အထက်ပါ context window ဇယားကို ကြည့်ပါ။

**Compaction စတင်ချိန် အလွန်နောက်ကျခြင်း**
`model_auto_compact_token_limit` ကို window ၏ 80–85% သို့ လျှော့ချပါ။ 90% အထက် မည်သည့်အခါမျှ မသတ်မှတ်ပါနှင့်။

**Profile မတင်နိုင်ခြင်း (`-p <name>` ကို အသိပေးခြင်းမရှိဘဲ လျစ်လျူရှုခြင်း)**
ဖိုင်သည် `~/.codex/<name>.config.toml` တွင် ရှိကြောင်း အတည်ပြုပါ (`profile-` prefix မပါရ)။ `ls ~/.codex/*.config.toml` ကို run ပါ။

**ကြာမြင့်သော Codex task သည် လုပ်ဆောင်နေစဉ် ပြတ်တောက်ခြင်း / turn များကြား account ပြောင်းသွားခြင်း**
[ကြာရှည်လုပ်ဆောင်သည့် task များ](#long-running-tasks) ကို ကြည့်ပါ။ Session affinity ကို ဖွင့်ပါ (TTL ကို task ကြာချိန်ထက် ပိုရှည်အောင် သတ်မှတ်ပါ)၊ ထို့နောက် `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS` ကို မြှင့်ပါ သို့မဟုတ် ပိတ်ပါ။ OmniRoute log များထဲတွင် `Idle timeout: no data from` ကို grep လုပ်၍ ရှာပါ။
