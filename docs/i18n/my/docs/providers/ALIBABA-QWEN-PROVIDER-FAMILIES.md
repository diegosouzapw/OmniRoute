ဤစာတမ်းတွင်
[Issue #7854](https://github.com/diegosouzapw/OmniRoute/issues/7854) အတွက် အကောင်အထည်ဖော်မှုဆိုင်ရာ ဆုံးဖြတ်ချက်ကို မှတ်တမ်းတင်ထားသည်။ အများသုံးထုတ်ကုန်များကို ပံ့ပိုးသူအုပ်စု လေးခုအဖြစ် ကိုယ်စားပြုထားသည်။ ဒေသသည် ချိတ်ဆက်မှုဒေတာဖြစ်ပြီး သီးခြားထုတ်ကုန်တစ်ခု မဟုတ်ပါ။

## ဆုံးဖြတ်ချက်

| ပံ့ပိုးသူအုပ်စု                                       | OmniRoute ID            | ကမ္ဘာလုံးဆိုင်ရာဒေသ | တရုတ်ဒေသ |
| ----------------------------------------------------- | ----------------------- | ------------------- | -------- |
| Alibaba Cloud Model Studio (အသုံးပြုသလောက် ပေးချေမှု) | `alibaba`               | စင်ကာပူ             | ပေကျင်း  |
| Alibaba Cloud Token Plan                              | `bailian-coding-plan`   | စင်ကာပူ             | ပေကျင်း  |
| Qwen Cloud (အသုံးပြုသလောက် ပေးချေမှု)                 | `qwen-cloud`            | ကမ္ဘာလုံးဆိုင်ရာ    | ပေကျင်း  |
| Qwen Cloud Token Plan                                 | `qwen-cloud-token-plan` | စင်ကာပူ             | ပေကျင်း  |

ရှိပြီးသား `alibaba-cn` ID ကို သိမ်းဆည်းထားသည့် ချိတ်ဆက်မှုများ၊ မော်ဒယ်လမ်းကြောင်းများ၊ ပေါင်းစပ်မှုများနှင့် ယခင်အသုံးပြုမှုများအတွက် runtime နောက်ပြန်သဟဇာတဖြစ်စေသည့် အမည်ကွဲအဖြစ် ဆက်လက်ထားရှိသည်။ ၎င်း၏ dashboard ကတ်ကို `alibaba` ထဲသို့ ပေါင်းထည့်ထားပြီး database ကို ပြန်လည်ရေးသားရန် မလိုအပ်ပါ။

Qwen Cloud ၏ အသုံးပြုသလောက် ပေးချေမှုနှင့် Alibaba Cloud Model Studio တို့သည် လက်ရှိတွင် DashScope နှင့် သဟဇာတဖြစ်သော runtime host များကို အတူတူအသုံးပြုသော်လည်း၊ အသုံးပြုသူများသည် မတူညီသော ထုတ်ကုန်မျက်နှာပြင်များမှတစ်ဆင့် key များရယူပြီး account များကို စီမံခန့်ခွဲသောကြောင့် ၎င်းတို့ကို သီးခြားပံ့ပိုးသူ အမှတ်သညာများအဖြစ် ဆက်လက်ထားရှိသည်။ Alibaba နှင့် Qwen Cloud Token Plan ထုတ်ကုန်များသည် မတူညီသော endpoint အုပ်စုများကို အသုံးပြုသောကြောင့် ထုတ်ကုန်လေးခုလုံးကို သီးခြား provider ID များအဖြစ် ဆက်လက်ထားရှိသည်။

API key နှင့် endpoint တို့သည် ထုတ်ကုန်နှင့် ဒေသတူညီရမည်။ ဒေသတစ်ခုကို ရွေးချယ်ခြင်းဖြင့် အတည်ပြုစစ်ဆေးမှုနှင့် ပုံမှန် request များတွင် အသုံးပြုသည့် ကြိုတင်သတ်မှတ် endpoint ကို ပြောင်းလဲစေသည်။

## ချိတ်ဆက်မှုဆိုင်ရာ သတ်မှတ်ချက်

ချိတ်ဆက်မှုအသစ်များသည် ပြောင်းလဲမှုမရှိသော ဒေသ key ကို `providerSpecificData` တွင် သိမ်းဆည်းသည်-

```json
{
  "region": "global-sg"
}
```

ခွင့်ပြုထားသော တန်ဖိုးများမှာ `global-sg` နှင့် `china-beijing` ဖြစ်သည်။ endpoint ကို provider ID နှင့် ဒေသတို့မှ ဗဟိုစနစ်ဖြင့် ဆုံးဖြတ်သည်။ ကြိုတင်သတ်မှတ်ထားခြင်းမရှိသော `providerSpecificData.baseUrl` သည် အော်ပရေတာက အတိအလင်း သတ်မှတ်သည့် override အဖြစ် ဆက်လက်ရှိပြီး ဦးစားပေးအသုံးပြုသည်။ သို့သော် ယခင်က သိမ်းဆည်းထားသော ကြိုတင်သတ်မှတ် URL များကို ဒေသဆိုင်ရာဇယားနှင့် ကိုက်ညီအောင် ပြန်လည်စံသတ်မှတ်သည်။

ဤနည်းဖြင့် ချိတ်ဆက်မှု schema ကို တိုးချဲ့နိုင်စွမ်းရှိစေသည်။ အခြားဒေသတစ်ခုကို provider ကတ်အသစ် ဖန်တီးခြင်း သို့မဟုတ် သိမ်းဆည်းထားသော provider ID များကို ပြောင်းလဲခြင်းမပြုဘဲ resolver ထဲသို့ ထည့်သွင်းနိုင်သည်။

## လိုက်ဖက်ညီမှုနှင့် ဖြန့်ချိခြင်း

1. ဒေသအလိုက် endpoint resolver ကို ထည့်သွင်းပြီး လက်ရှိ global default များကို ဆက်လက်ထိန်းသိမ်းထားပါ။
2. `alibaba`၊ ၎င်း၏ `alibaba-cn` လိုက်ဖက်ညီမှု ID နှင့် `qwen-cloud` တို့အတွက် လက်ရှိအသုံးပြုနေသော ဒေသအလိုက် DashScope `/models` discovery ကို အသုံးပြုပါ။ Generic endpoint သည် image၊ video၊ audio၊ embedding နှင့် အခြား chat မဟုတ်သော model များကိုလည်း ပြန်ပေးသောကြောင့် ၎င်းတို့၏ response များကို text-generation filter တစ်ခုဖြင့် ဦးစွာ စစ်ထုတ်ပါသည်။ ထို့နောက် `qwen-cloud` သည် ၎င်း၏ provider registry တွင် ကြေညာထားသော ထိန်းသိမ်းထားသည့် allowlist ကို အသုံးပြုပါသည်။ Alibaba Model Studio နှင့် Qwen Cloud တို့သည် လက်ရှိတွင် runtime host များကို မျှဝေအသုံးပြုနေသော်လည်း သီးခြားစီ စီမံရွေးချယ်ထားသော catalog များကို ဆက်လက်ထားရှိပါသည်။
3. လက်ရှိ Token Plan text-model allowlist နှင့်အတူ `qwen-cloud-token-plan` ကို register လုပ်ပါ။
4. Connection ထည့်သွင်း/ပြင်ဆင်သည့် dialog များတွင် type သတ်မှတ်ထားသော region selector တစ်ခု ထည့်ပါ။
5. ထပ်နေသော `alibaba-cn` card ကို ဖျောက်ထားပြီး ၎င်း၏ လက်ရှိ connection များကို `alibaba` provider စာမျက်နှာတွင် ထည့်သွင်းဖော်ပြပါ။
6. အဆင့်မြင့်နှင့် workspace အလိုက် deployment များအတွက် custom endpoint override များကို ဆက်လက်အသုံးပြုနိုင်အောင် ထားရှိပါ။

Token Plan media model များသည် သီးသန့် endpoint များကို အသုံးပြုသောကြောင့် chat catalog အပြင်ဘက်တွင် ဆက်လက်ရှိနေပါသည်။
`wan2.7-image` နှင့် `wan2.7-image-pro` တို့ကို `open-sse/config/imageRegistry.ts` တွင် register လုပ်ထားပြီး၊
`happyhorse-1.1-i2v`၊ `happyhorse-1.1-t2v` နှင့် `happyhorse-1.1-r2v` တို့ကို
`open-sse/config/videoRegistry.ts` တွင် register လုပ်ထားပါသည်။ Registry နှစ်ခုလုံးသည် `qwen-cloud-token-plan` connection identity နှင့် ၎င်း၏ ဒေသအလိုက် credential များကို ပြန်လည်အသုံးပြုပါသည်။

ပုံမှန် Qwen Cloud တွင် `qwen-cloud` identity အောက်၌ သီးခြား pay-as-you-go image နှင့် video catalog များ ရှိပါသည်။ ၎င်း၏ image model များမှာ `wan2.7-image-pro`၊ `wan2.7-image`၊ `qwen-image-3.0-pro`၊
`qwen-image-2.0-pro-2026-06-22`၊ `qwen-image-2.0-2026-03-03` နှင့် `z-image-turbo` တို့ ဖြစ်ပါသည်။ ၎င်း၏ video
model များမှာ `happyhorse-1.1-i2v`၊ `happyhorse-1.1-t2v`၊ `happyhorse-1.1-r2v`၊
`happyhorse-1.0-video-edit`၊ `wan2.7-t2v`၊ `wan2.7-i2v`၊ `wan2.7-r2v-2026-06-12` နှင့်
`wan2.7-videoedit` တို့ ဖြစ်ပါသည်။ ဤ model များသည် ပုံမှန် `qwen-cloud` connection နှင့် ဒေသအလိုက်

Alibaba Token Plan သည် လက်ရှိ text-generation model ID ခြောက်ခုကိုပင် ၎င်း၏
Anthropic-compatible endpoint မှတစ်ဆင့် ထုတ်ဖော်ပေးပါသည်။ ၎င်း၏ Singapore option သည် လက်ရှိ `global-sg` region key ကို သိမ်းဆည်းထားပြီး၊ region ကို Global ဟု ခေါ်ဆိုသော provider family များနှင့် နှိုင်းယှဉ်လျှင် အသုံးပြုသူမြင်ရသော label သာ ကွာခြားပါသည်။

ပုံမှန် Qwen Cloud chat catalog ကို လက်ရှိ live text response အပြည့်အစုံထက် ရည်ရွယ်ချက်ရှိရှိ ပိုမိုကျဉ်းမြောင်းစွာ သတ်မှတ်ထားပါသည်။ ၎င်း၏
ထိန်းသိမ်းထားသော allowlist သည် `open-sse/config/providers/registry/qwen-cloud/index.ts` တွင် ရှိပြီး၊ live
discovery သည် upstream response နှင့် ထို registry စာရင်း နှစ်ခုစလုံးတွင် ပါဝင်သော ID များကိုသာ ပြန်ပေးပါသည်။

Alibaba Model Studio သည်လည်း `open-sse/config/providers/registry/alibaba/index.ts` ရှိ သီးခြားလွတ်လပ်စွာ ထိန်းသိမ်းထားသော
allowlist နှင့် အလားတူ live-intersection စည်းမျဉ်းကို လိုက်နာပါသည်။ `alibaba-cn` လိုက်ဖက်ညီမှု
provider သည် Beijing endpoint ကို အသုံးပြု၍ discovery ကို resolve လုပ်စဉ် ထို catalog ကို ပြန်လည်အသုံးပြုပါသည်။
