`chatgpt-web-codex` (အမည်ပွား `cgpt-codex`) သည် အထောက်အထားစစ်မှန်ကြောင်း အတည်ပြုထားသော ChatGPT browser session မှတစ်ဆင့် Codex Responses turn များကို ချိတ်ဆက်ပေးသည်။ ၎င်းသည် ရပ်ဆိုင်းထားပြီးဖြစ်သော အများသုံး `chatgpt-web` provider နှင့် သီးခြားဖြစ်ပြီး `open-sse/vendor/codex-chatgpt-web/` အောက်ရှိ MIT အသိပေးချက်ပါ implementation ကို အသုံးပြုထားကာ upstream v4.0.7 commit `b59d7dc51b84fb1f465ff1d00f5207f3b2b4a494` အထိ အပ်ဒိတ်လုပ်ထားသည်။

## အများသုံး provider ကို ရပ်ဆိုင်းခြင်း

ယခင် အများသုံး provider ID များဖြစ်သော `chatgpt-web` နှင့် `cgpt-web` တို့ကို ၎င်းတို့၏ pre-key/proof-of-work implementation ၏ မူလရင်းမြစ်ကို ရှင်းလင်းအတည်ပြုနိုင်ခြင်းမရှိသောကြောင့် ယခုအခါ ဖြန့်ချိခြင်းမရှိတော့ပါ။ slash ဖြင့်စသော model ID များနှင့် သိမ်းဆည်းထားသော alias များအပါအဝင် မည်သည့် ID ကိုမဆို အတိအလင်း တောင်းဆိုပါက upstream request တစ်ခုမျှ မပြုလုပ်မီ HTTP `410` နှင့် code **PROVIDER_RETIRED** ဖြင့် လုံခြုံစွာ ပိတ်ပင်၍ မအောင်မြင်စေပါသည်။

Migration `168_retire_chatgpt_web.sql` သည် ကိုက်ညီသော provider connection များကို tombstone လုပ်ပြီး ၎င်းတို့၏ အသုံးပြုနေဆဲ session lease များကို ပျက်ပြယ်စေသည်။ ၎င်းသည် connection history နှင့် API-key allowlist များကို ဆက်လက်ထိန်းသိမ်းထားသော်လည်း အစားထိုး access ကို allowlist တစ်ခုသို့ ထည့်သွင်းပေးခြင်းမရှိပါ။ Codex provider နှင့် ၎င်း၏ connection များသည် ဤရပ်ဆိုင်းမှုနှင့် ကိုက်ညီခြင်းမရှိပါ။

## ကြိုတင်လိုအပ်ချက်များ

- အကောင့်ဝင်ထားသော ChatGPT session တစ်ခုမှ Cookie header အပြည့်အစုံ၊
- npm၊ systemd နှင့် PM2 installation များအတွက် Chrome သို့မဟုတ် Chromium အပြင် graphical session သို့မဟုတ် Xvfb display၊
- Docker `web` profile ကို အသုံးပြုပါက `docker-compose.yml` မှ အတွင်းပိုင်း Chromium service၊
- local Codex tool များအတွက် OpenAI `tunnel-client` v0.0.13 နှင့် ChatGPT custom connector တစ်ခု။

Tunnel ကို tool turn များအတွက်သာ လိုအပ်သည်။ `pro` အပါအဝင် စာရင်းပြုထားသော route အားလုံးသည် tunnel နှင့် connector ကို configure လုပ်ထားသည့်အခါ တူညီသော turn-bound local tool စွမ်းရည်ကို အသုံးပြုနိုင်သည်။

## Dashboard ထည့်သွင်းသတ်မှတ်ခြင်း

1. **ChatGPT Web (Codex)** provider ကိုဖွင့်ပြီး connection တစ်ခု ထည့်ပါ။
2. ChatGPT Cookie header အပြည့်အစုံ၊ tunnel ID၊ runtime key နှင့် custom connector အမည်တို့ကို ထည့်ပါ။ Tool အသုံးပြုနိုင်သော setup အသစ်များတွင် `OmniRoute Codex v2` ဟု အတိအကျ အမည်ပေးထားသော အသစ်ဖန်တီးသည့် connector ကို အသုံးပြုရမည်ဖြစ်ပြီး Authentication ကို None၊ Permissions ကို Allow all actions ဟု သတ်မှတ်ထားရမည်။
3. Connection check ကို လုပ်ဆောင်ပါ။ OmniRoute သည် browser-backed Temporary Chat တစ်ခုကို ဖွင့်ပြီး အကောင့်အတွက် Sol နှင့် Pro ရရှိနိုင်ခြင်းရှိမရှိ စစ်ဆေးသည်။
4. Connection ကို သိမ်းဆည်းပါ။ OmniRoute သည် ထည့်သွင်းထားသော cookie ကို အတည်ပြုပြီးသော Playwright storage state ဖြင့် အစားထိုးကာ encrypted credential abstraction မှတစ်ဆင့် runtime key နှင့်အတူ သိမ်းဆည်းသည်။

အောင်မြင်စွာ သိမ်းဆည်းပြီးနောက် raw cookie ကို ဆက်လက်သိမ်းထားမည်မဟုတ်ပါ။ Session သက်တမ်းကုန်ဆုံးသောအခါ connection ကိုဖွင့်ပြီး Cookie header အပြည့်အစုံအသစ်ကို ထည့်ကာ check ကို ပြန်လည်လုပ်ဆောင်ပါ။ Edit dialog ရှိ doctor status သည် browser၊ storage state၊ sign-in၊ Temporary Chat၊ tunnel၊ connector နှင့် tool round-trip တို့၏ အခြေအနေကို သီးခြားစီ အစီရင်ခံသည်။

> တကယ့် cookie၊ runtime key၊ storage state သို့မဟုတ် capability token ကို မည်သည့်အခါမျှ commit မလုပ်ပါနှင့်။ စမ်းသပ်မှုနှင့်
> စာရွက်စာတမ်းတန်ဖိုးများသည် placeholder များသာ အမြဲဖြစ်ရမည်။

## Model များနှင့် combo များ

သတ်မှတ်ထားသော model route များမှာ-

- `chatgpt-web-codex/luna` — GPT-5.6 Luna၊ အားထုတ်မှုနည်း
- `chatgpt-web-codex/think` — GPT-5.6 Luna၊ အားထုတ်မှုအလယ်အလတ်
- `chatgpt-web-codex/instant`
- `chatgpt-web-codex/medium`
- `chatgpt-web-codex/high`
- `chatgpt-web-codex/extra-high`
- `chatgpt-web-codex/pro`

အခြား model များကဲ့သို့ပင် ၎င်းတို့ထဲမှ တစ်ခုကို combo တစ်ခုသို့ ထည့်ပါ။ Codex app သည် ပုံမှန် Responses endpoint ဖြစ်သော `/v1/responses` သို့ combo အမည်ကို `model` အဖြစ် ပေးပို့သည်။ သီးခြား Codex endpoint သို့မဟုတ် mode switch မရှိပါ။

Free/Go အကောင့်များတွင် Luna route များကို အသုံးပြုနိုင်သည်။ Sol အသုံးပြုနိုင်သော အကောင့်များတွင် Instant မှ High အထိ အသုံးပြုနိုင်ပြီး Pro အသုံးပြုနိုင်သော အကောင့်များတွင် Extra High နှင့် Pro ကိုလည်း ထပ်မံအသုံးပြုနိုင်သည်။ Route တစ်ခုစီတွင် သတ်မှတ်ထားသော backend model နှင့် reasoning effort ရှိသည်။ ယင်းနှင့် ကွဲလွဲနေသော Responses effort ကို အတိအလင်း သတ်မှတ်ပါက ရွေးချယ်ထားသော browser mode ကို တိတ်တဆိတ် ပြောင်းလဲမည့်အစား လုံခြုံစွာ ပိတ်ပင်၍ မအောင်မြင်စေပါသည်။

အဟောင်းဖြစ်သော `Codex Native` သို့မဟုတ် `OmniRoute Codex` connector ကို အမည်ပြောင်းခြင်း သို့မဟုတ် ပြန်လည်အသုံးပြုခြင်း မပြုပါနှင့်။ ChatGPT သည် အများသုံး MCP contract ကို connector identity အလိုက် cache လုပ်ထားပြီး အပ်ဒိတ်လုပ်ထားသော bridge သည် direct turn-token contract အသစ်ကို အသုံးပြုသည်။ Runtime သည် အဆိုပါ legacy identity များကို ငြင်းပယ်ပြီး `OmniRoute Codex v2` connector အသစ်တစ်ခုကို လိုအပ်သည်။

## လုံခြုံရေးပုံစံ

- မူရင်းလမ်းကြောင်းအတွက် Responses တောင်းဆိုချက်၊ အသိအမှတ်ပြုထားသော Codex client နှင့် ကိုက်ညီသော
  thread နှင့် turn အထောက်အထားများ လိုအပ်သည်။
- Workspace၊ sandbox၊ approval policy နှင့် tool catalog တို့ကို မူရင်း Codex shell မှ ရရှိသည်။
  လွတ်လပ်စွာရေးသားထားသော prompt စာသားသည် ၎င်းတို့အတွက် လုပ်ပိုင်ခွင့်အာဏာ မဟုတ်ပါ။
- ChatGPT သည် turn တစ်ခုစီအတွက် သက်တမ်းတိုသော capability တစ်ခုသာ ရရှိသည်။ MCP broker သည်
  ထို turn အတိအကျတွင် Codex က ကမ်းလှမ်းထားသော tool များကိုသာ လက်ခံသည်။
- **Allow once** ကို အလိုအလျောက်အတည်ပြုခြင်းသည် tool တောင်းဆိုချက်ကို Codex ထံသို့သာ ပြန်ပို့ပေးသည်။ အတည်ပြုခြင်းနှင့်
  လုပ်ဆောင်ခြင်းတို့ကို Codex တစ်ခုတည်းကသာ ဆုံးဖြတ်သည်။
- ပထမဆုံး output မထွက်မီ combo တစ်ခုသည် ကိုက်ညီမှုရှိသော အခြား target တစ်ခုသို့ ပြန်လည်ပြောင်းနိုင်သည်။ Output
  စတင်ပြီးနောက် provider၊ model၊ connection နှင့် browser turn တို့ကို turn ပြီးဆုံးသည်အထိ
  ပုံသေသတ်မှတ်ထားသည်။
- Cookies၊ runtime keys၊ storage state နှင့် capability tokens တို့သည် provider
  responses သို့မဟုတ် request logs များတွင် မပေါ်လာပါ။

## မျက်နှာပြင်မရှိသော VPS နှင့် Docker

npm၊ systemd နှင့် PM2 တပ်ဆင်မှုများအတွက် OmniRoute သည် အသုံးများသော Chrome နှင့် Chromium လမ်းကြောင်းများကို ရှာဖွေသိရှိသည်။
တစ်နည်းအားဖြင့် `CHATGPT_WEB_CODEX_CHROME_PATH` ကို သတ်မှတ်နိုင်သည်။ ChatGPT သည် အမှန်တကယ် headless ဖြစ်သော browser ပုံစံကို ငြင်းပယ်သောကြောင့် runtime turn များတွင် headed
Chrome ကို တမင်အသုံးပြုထားသည်။ ထို့ကြောင့် မျက်နှာပြင်မရှိသော host သည်
သီးသန့် Xvfb display တစ်ခုဖြင့် OmniRoute ကို လုပ်ဆောင်ရမည်ဖြစ်ပြီး Chrome လမ်းကြောင်းကို သတ်မှတ်ရုံဖြင့် display တစ်ခု မရရှိနိုင်ပါ။

Docker `web` profile သည် အတွင်းပိုင်း Compose
network ပေါ်တွင် `chatgpt-web-codex-browser` ကို စတင်သည်။ Sidecar သည် Xvfb အတွင်း headed Chrome ကို လုပ်ဆောင်သောကြောင့် ရုပ်ပိုင်းဆိုင်ရာ display မလိုအပ်ပါ။ ၎င်း၏ CDP
port ကို host ပေါ်တွင် ထုတ်ဖော်ထားခြင်းမရှိပါ။ ကာကွယ်ထားသော browser profile volume သည်
OmniRoute data volume နှင့် သီးခြားဖြစ်ပြီး browser သည် လုံလောက်သော shared memory ကို ရရှိသည်။ အတွင်းပိုင်း CDP proxy သည်
Compose network အတွင်းရှိ port `9223` ပေါ်တွင်သာ နားထောင်ပြီး Chrome သည် sidecar အတွင်းရှိ loopback နှင့်သာ ဆက်စပ်ထားသည်။

`DATA_DIR` အောက်ရှိ supervisor lease တစ်ခုက OmniRoute process အများအပြားအား
တူညီသော tunnel နှင့် broker state ကို ပိုင်ဆိုင်ခြင်းမှ တားဆီးပေးသည်။ ပဋိပက္ခတစ်ခုကို doctor က အစီရင်ခံသည်။

## အပြန်အလှန်တုံ့ပြန်သော ပြန်လည်ရယူမှု

အလိုအလျောက် Docker လမ်းကြောင်းတွင် host မှ မြင်နိုင်သော window မရှိသော်လည်း Chrome ကိုယ်တိုင်က
သီးသန့် Xvfb display အတွင်း headed အဖြစ် လုပ်ဆောင်နေသည်။ ChatGPT က အပြန်အလှန်တုံ့ပြန်ရသော sign-in သို့မဟုတ် challenge တစ်ခုကို တောင်းဆိုသည့်အခါ လက်ရှိ VNC
browser infrastructure ကို ပြန်လည်ရယူရန် အသုံးပြုနိုင်သည်။ Browser UI နှင့် CDP ကို loopback၊ အထောက်အထားစစ်ဆေးထားသော management connection သို့မဟုတ် SSH tunnel မှတစ်ဆင့်သာ
အသုံးပြုနိုင်ရမည်ဖြစ်ပြီး ပုံမှန်လုပ်ဆောင်နေစဉ်အတွင်း noVNC ကို ပိတ်ထားသည်။

## WebSocket အရန်နည်းလမ်း

Combo တစ်ခုတွင် ChatGPT Web (Codex) ပါဝင်သောအခါ Responses WebSocket bridge သည်
upstream သို့ မချိတ်ဆက်မီ HTTP/SSE အရန်နည်းလမ်းကို တောင်းဆိုသည်။ ထို့နောက် လွှဲပြောင်းမှုသည်
`/v1/responses` မှတစ်ဆင့် ဆောင်ရွက်သည်။
