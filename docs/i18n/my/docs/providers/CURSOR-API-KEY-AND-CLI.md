IDE session မလိုဘဲ Cursor ကို OmniRoute နောက်ကွယ်တွင် ထားရှိအသုံးပြုနိုင်သည့် နည်းလမ်းနှစ်ခုရှိသည်-

1. **`cursor-api` provider** (ကတ် "Cursor API"၊ alias `cua`)- Cursor user API key
   (`crsr_…`၊ `https://cursor.com/dashboard/api` တွင် ဖန်တီးထားသော) ကို သိမ်းဆည်းထားသည့် API-key
   provider ဖြစ်သည်။ ထို့နောက် မည်သည့် OmniRoute client မဆို ပုံမှန် quota၊ fallback နှင့် logging
   layer များဖြင့် `/v1/chat/completions` မှတစ်ဆင့် `cursor-api/<model>` သို့မဟုတ်
   `cua/<model>` အဖြစ် Cursor model များကို ရယူအသုံးပြုနိုင်သည်။ IDE
   provider (`cursor`၊ OAuth/IDE session) မှာ ပြောင်းလဲမှုမရှိပါ။
2. **Cursor CLI passthrough**- Cursor CLI (`agent`) ကို OmniRoute သို့ ချိတ်ဆက်ညွှန်ပြခြင်းဖြင့်
   CLI က ပြုလုပ်သည့် RPC တိုင်းကို OmniRoute API key ဖြင့် စစ်မှန်ကြောင်းအတည်ပြုပြီး၊
   `cursor-api` connection ၏ credential ဖြင့် Cursor သို့ ဆက်လက်ပေးပို့ကာ
   Logs စာမျက်နှာတွင် မှတ်တမ်းတင်နိုင်သည်။

## Key ကို အဘယ်ကြောင့် လဲလှယ်ရသနည်း

`api2.cursor.sh` သည် `crsr_…` key အကြမ်းကို Bearer token အဖြစ် အသုံးပြုခြင်းအား ငြင်းပယ်သည် (401)။
Cursor CLI သည် ဦးစွာ key ကို `/auth/exchange_user_api_key` သို့ POST လုပ်ပြီး တစ်နာရီအကြာတွင်
သက်တမ်းကုန်ဆုံးမည့် session JWT ကို ရယူသည်။ ပြန်ပေးသော `refreshToken` တွင်လည်း တူညီသည့်
`exp` ပါဝင်သောကြောင့် refresh လုပ်ခြင်းသည် key ကို ပြန်လည်လဲလှယ်ခြင်းဖြစ်သည်။
`open-sse/services/cursorApiKeyAuth.ts` သည် ထိုလဲလှယ်မှုကို လုပ်ဆောင်ပြီး key တစ်ခုစီအတွက်
session token တစ်ခုကို cache လုပ်ထားကာ သက်တမ်းမကုန်မီ ငါးမိနစ်အလိုတွင် ပြန်လည်လဲလှယ်ပြီး
Cursor က 401 ပြန်ပေးသည့်အခါ cache လုပ်ထားသော token ကို ဖယ်ရှားသည်။ `CursorExecutor` သည်
`cursor-api` connection များအတွက် upstream stream ကို မဖွင့်မီ ၎င်းကို ခေါ်ယူသည်။

## `cursor-api` provider

Registry- `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`၊ `authType: "apikey"`၊ `cursor` နှင့် တူညီသော `format`၊ `baseUrl` နှင့်
`models`)။ Catalog ကတ်-
`src/shared/constants/providers/apikey/specialty-media.ts`။ Executor map-
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`)။

Dashboard- Providers → Cursor API → Add API key။

REST-

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

ထို့နောက်-

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

မှတ်ချက်များ-

- `cursor-api` အတွက် model စာရင်းသည် static Cursor registry မှ လာသည် (IDE provider က
  fallback လုပ်သည့် စာရင်းနှင့် တူညီသည်)။ OmniRoute host တွင် `cursor-agent` ကို install
  လုပ်ရန် မလိုအပ်ပါ။
- `POST /api/providers/{id}/refresh-cursor` သည် `cursor` IDE provider အတွက်သာ
  ဖြစ်သည်။ `cursor-api` connection များတွင် သက်တမ်းတိုးရန် IDE session မရှိပါ။

## မူရင်း model ID များနှင့် effort

`cursor` / `cu` နှင့် `cursor-api` / `cua` အတွက် မျှဝေသုံးသော Claude-effort normalizer သည်
တောင်းဆိုထားသည့် model ID ကို မပြောင်းလဲဘဲ ထားရှိသည်။ Cursor သည် OmniRoute effort alias
အဖြစ်မဟုတ်ဘဲ တကယ့် model ID ၏ အစိတ်အပိုင်းအဖြစ် `-low` ကဲ့သို့သော suffix ကို
ဖော်ပြနိုင်သည်။ Cursor executor သည် live catalog နှင့် အတိအကျကိုက်ညီမှုကို မပြောင်းလဲဘဲ
ထိန်းသိမ်းထားသည်။ ကိုက်ညီမှုမရှိသည့်အခါ ၎င်း၏ လက်ရှိ model resolver က
suffix-to-parameter fallback ကို ကိုင်တွယ်သည်။

၎င်းသည် direct Claude၊ Claude-compatible သို့မဟုတ် Vertex route များအတွက် effort
normalization ကို မပြောင်းလဲပါ။ အသုံးပြုနိုင်မှုသည် ရွေးချယ်ထားသော Cursor account ၏
catalog နှင့် entitlement ပေါ်တွင် ဆက်လက်မူတည်သည်။

## Cursor CLI passthrough

လမ်းကြောင်း: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`။ handler က ၎င်း၏ကိုယ်ပိုင် authentication ကို
အကောင်အထည်ဖော်ထားသောကြောင့် prefix `/api/cursor-cli/` ကို
`src/shared/constants/publicApiRoutes.ts` တွင် မှတ်ပုံတင်ထားသည်-

| လမ်းကြောင်း                                                                                                                        | CLI မှ မျှော်လင့်ထားသော Auth | OmniRoute လုပ်ဆောင်ပုံ                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /auth/exchange_user_api_key`                                                                                                 | `Bearer <OmniRoute API key>` | key ကို အတည်ပြုစစ်ဆေးပြီး 1 နာရီသက်တမ်းရှိ HS256 JWT (`JWT_SECRET` ဖြင့် လက်မှတ်ရေးထိုးထားသော) ကို ထုတ်ပေးကာ ပြန်ပေးသည်                                                                                                  |
| အခြားလမ်းကြောင်းတိုင်း (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`          | issuer/audience/expiry ကို အတည်ပြုစစ်ဆေးပြီး အသုံးပြုနိုင်သော `cursor-api` connection တစ်ခုကို ရွေးချယ်ကာ Authorization header ကို လဲလှယ်ထားသော Cursor token ဖြင့် အစားထိုးပြီး တုံ့ပြန်ချက်ကို stream အဖြစ် ပြန်ပို့သည် |

CLI သည် လက်ခံရရှိသည့် မည်သည့် token မှမဆို `exp` ကို decode လုပ်သောကြောင့် opaque
token တစ်ခု ပေးလိုက်ပါက request အားလုံးနီးပါးမတိုင်မီ ထပ်မံလဲလှယ်စေမည်ဖြစ်သည်။
ထုတ်ပေးထားသော JWT က ယင်းကို ရှောင်ရှားပေးသည်။ OmniRoute မှ 401 ပြန်လာပါက CLI သည်
ထပ်မံလဲလှယ်မည်ဖြစ်သည်။

### စနစ်ထည့်သွင်းခြင်း

1. OmniRoute API key တစ်ခု (Dashboard → API keys) နှင့် `cursor-api`
   connection တစ်ခု ဖန်တီးပါ။
2. agent stream အတွက် HTTP/1.1 ကို အသုံးပြုရန် CLI ကို သတ်မှတ်ပါ။
   `~/.cursor/cli-config.json` တွင်-

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   ဤသတ်မှတ်ချက်မရှိပါက CLI သည် သီးခြား configure လုပ်ထားသော agent host သို့
   HTTP/2 ဖြင့် agent turn ကို ဖွင့်မည်ဖြစ်ပြီး control-plane RPC များသာ
   endpoint မှတစ်ဆင့် ဖြတ်သန်းမည်ဖြစ်သည်။

3. OmniRoute ကို အသုံးပြု၍ CLI ကို run ပါ-

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

hop တစ်ခုချင်းစီကို provider `cursor-api`၊ request type `cursor-cli`၊
path `/api/cursor-cli/<rpc>` အဖြစ် Logs ထဲတွင် မှတ်တမ်းတင်ပြီး အသုံးပြုထားသော
OmniRoute API key နှင့် request ကို ဆောင်ရွက်ပေးခဲ့သည့် connection တို့နှင့်
ချိတ်ဆက်သတ်မှတ်ထားသည်။

### ချို့ယွင်းနိုင်သည့် အခြေအနေများ

| အခြေအနေ                                              | CLI သို့ တုံ့ပြန်ချက်                                      |
| ---------------------------------------------------- | ---------------------------------------------------------- |
| မသိသော OmniRoute key နှင့် `REQUIRE_API_KEY=true`    | လဲလှယ်စဉ် 401 `unauthenticated`                            |
| `REQUIRE_API_KEY=false`                              | anonymous session (`/v1/*` အပြုအမူအတိုင်း)                 |
| သက်တမ်းကုန် / ပြင်ပမှ / ပြုပြင်ထားသော session JWT    | 401၊ CLI က ထပ်မံလဲလှယ်သည်                                  |
| လဲလှယ်ပြီးနောက် OmniRoute API key ကို ရုပ်သိမ်းခြင်း | နောက် RPC တွင် 401                                         |
| အသုံးပြုနိုင်သော `cursor-api` connection မရှိခြင်း   | 503 `unavailable`                                          |
| Cursor က connection ၏ key ကို ငြင်းပယ်ခြင်း          | 401 `unauthenticated`၊ cache ထားသော session ကို ဖယ်ရှားသည် |
| Upstream သို့ ဆက်သွယ်၍မရခြင်း                        | 502 `unavailable` (သန့်စင်ထားသော message)                  |
| `JWT_SECRET` မသတ်မှတ်ထားခြင်း                        | လဲလှယ်စဉ် 503                                              |
