IDE session မပါဘဲ Cursor ကို OmniRoute နောက်တွင် ထားရှိရန် နည်းလမ်းနှစ်မျိုးရှိသည်-

1. **`cursor-api` provider** (ကတ် "Cursor API"၊ alias `cua`)- Cursor user API key (`crsr_…`၊
   `https://cursor.com/dashboard/api` တွင် ထုတ်လုပ်ထားသော) ကို ထိန်းသိမ်းထားသည့် API-key
   provider ဖြစ်သည်။ ထို့နောက် OmniRoute client မည်သည့်အမျိုးအစားမဆို ပုံမှန် quota၊ fallback နှင့်
   logging အလွှာများဖြင့် `/v1/chat/completions` မှတစ်ဆင့် Cursor model များကို
   `cursor-api/<model>` သို့မဟုတ် `cua/<model>` အဖြစ် အသုံးပြုနိုင်သည်။ IDE
   provider (`cursor`၊ OAuth/IDE session) သည် မပြောင်းလဲပါ။
2. **Cursor CLI passthrough**- Cursor CLI (`agent`) ကို OmniRoute သို့ ညွှန်ပေးခြင်းဖြင့်
   CLI ပြုလုပ်သည့် RPC တိုင်းကို OmniRoute API key ဖြင့် authentication ပြုလုပ်ကာ
   `cursor-api` connection တစ်ခု၏ credential ဖြင့် Cursor သို့ forward လုပ်ပြီး
   Logs စာမျက်နှာတွင် မှတ်တမ်းတင်ထားသည်။

## Key ကို အဘယ်ကြောင့် လဲလှယ်ရသနည်း

`api2.cursor.sh` သည် မူရင်း `crsr_…` key ကို Bearer token အဖြစ် လက်မခံဘဲ (401) ပြန်ပေးသည်။ Cursor
CLI သည် ပထမဦးစွာ key ကို `/auth/exchange_user_api_key` သို့ POST လုပ်ပြီး တစ်နာရီအကြာတွင်
သက်တမ်းကုန်ဆုံးမည့် session JWT ကို လက်ခံရရှိသည်။ ပြန်လာသော `refreshToken` တွင်လည်း တူညီသော
`exp` ပါဝင်သဖြင့် refresh ပြုလုပ်ခြင်းသည် key ကို ပြန်လည်လဲလှယ်ခြင်းကို ဆိုလိုသည်။
`open-sse/services/cursorApiKeyAuth.ts` သည် ထိုလဲလှယ်မှုကို လုပ်ဆောင်ပြီး key တစ်ခုစီအတွက် session
token တစ်ခုကို cache လုပ်ထားကာ သက်တမ်းမကုန်မီ ငါးမိနစ်အလိုတွင် ပြန်လည်လဲလှယ်ပြီး Cursor က 401
ပြန်ပေးသည့်အခါ cache လုပ်ထားသော token ကို ဖယ်ရှားသည်။ `CursorExecutor` သည်
`cursor-api` connection များအတွက် upstream stream ကို မဖွင့်မီ ၎င်းကို ခေါ်ယူသည်။

## `cursor-api` provider

Registry- `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`၊ `authType: "apikey"`၊ `cursor` နှင့် တူညီသော `format`၊ `baseUrl` နှင့်
`models`)။ Catalog ကတ်-
`src/shared/constants/providers/apikey/specialty-media.ts`။ Executor map-
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`)။

Dashboard- Providers → Cursor API → Add API key။

REST-

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

ထို့နောက်-

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

မှတ်ချက်များ-

- `cursor-api` အတွက် model စာရင်းသည် static Cursor registry မှ ရရှိသည် (IDE provider က
  fallback လုပ်သည့် စာရင်းနှင့် တူညီသည်)။ OmniRoute host တွင် `cursor-agent` ထည့်သွင်းရန်
  မလိုအပ်ပါ။
- `POST /api/providers/{id}/refresh-cursor` သည် `cursor` IDE provider အတွက်သာ
  ဖြစ်သည်။ `cursor-api` connection များတွင် သက်တမ်းတိုးရန် IDE session မရှိပါ။

## Cursor CLI passthrough

Route- `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`။ Handler သည် ၎င်း၏ကိုယ်ပိုင် authentication ကို
အကောင်အထည်ဖော်သောကြောင့် prefix `/api/cursor-cli/` ကို
`src/shared/constants/publicApiRoutes.ts` တွင် register လုပ်ထားသည်-

| Path                                                                                                                           | CLI မှ မျှော်လင့်ထားသော auth | OmniRoute လုပ်ဆောင်သည့်အရာ                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                             | `Bearer <OmniRoute API key>` | Key ကို validate လုပ်ပြီး 1h HS256 JWT (`JWT_SECRET` ဖြင့် sign လုပ်ထားသော) ကို ထုတ်ပေးကာ ပြန်ပို့သည်                                                                                                       |
| အခြား path အားလုံး (`/aiserver.v1.*`၊ `/agent.v1.AgentService/RunSSE`၊ `/aiserver.v1.BidiService/BidiAppend`၊ `/v1/traces`၊ …) | `Bearer <that JWT>`          | Issuer/audience/expiry ကို verify လုပ်ပြီး အသုံးပြုနိုင်သော `cursor-api` connection တစ်ခုကို ရွေးကာ Authorization header ကို လဲလှယ်ရရှိထားသည့် Cursor token ဖြင့် အစားထိုးပြီး reply ကို stream ပြန်ပို့သည် |

CLI သည် လက်ခံရရှိသည့် token မည်သည့်အမျိုးအစားမှမဆို ၎င်းမှ `exp` ကို decode လုပ်သောကြောင့် opaque
token တစ်ခုကို ပေးလိုက်ပါက request တိုင်းနီးပါးမတိုင်မီ ပြန်လည်လဲလှယ်မည်။ ထုတ်ပေးထားသော JWT က
ထိုအခြေအနေကို ရှောင်ရှားပေးသည်။ OmniRoute မှ 401 ပြန်လာပါက CLI သည် ထပ်မံလဲလှယ်သည်။

### Setup

1. OmniRoute API key တစ်ခု (Dashboard → API keys) နှင့် `cursor-api`
   connection တစ်ခုကို ဖန်တီးပါ။
2. Agent stream အတွက် HTTP/1.1 ကို အသုံးပြုရန် CLI ကို သတ်မှတ်ပါ။
   `~/.cursor/cli-config.json` တွင်-

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   ဤသတ်မှတ်ချက်မရှိပါက CLI သည် သီးခြား configure လုပ်ထားသော agent host သို့ HTTP/2 ဖြင့်
   agent turn ကို ဖွင့်မည်ဖြစ်ပြီး control-plane RPC များသာ endpoint မှတစ်ဆင့် သွားမည်ဖြစ်သည်။

3. OmniRoute ကို အသုံးပြုရန် CLI ကို အောက်ပါအတိုင်း run ပါ-

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

Hop တိုင်းသည် provider `cursor-api`၊ request type `cursor-cli`၊ path
`/api/cursor-cli/<rpc>` အဖြစ် Logs ထဲသို့ ရောက်ရှိပြီး OmniRoute API key နှင့် request ကို
ဆောင်ရွက်ပေးသည့် connection တို့နှင့် ချိတ်ဆက်မှတ်တမ်းတင်ထားသည်။

### ပျက်ကွက်နိုင်သော အခြေအနေများ

| အခြေအနေ                                                           | CLI သို့ တုံ့ပြန်ချက်                                      |
| ----------------------------------------------------------------- | ---------------------------------------------------------- |
| မသိရှိသော OmniRoute key နှင့် `REQUIRE_API_KEY=true`              | exchange ပြုလုပ်ရာတွင် 401 `unauthenticated`               |
| `REQUIRE_API_KEY=false`                                           | အမည်မသိ session (`/v1/*` ၏ လုပ်ဆောင်ပုံအတိုင်း)            |
| သက်တမ်းကုန် / အခြားစနစ်မှ / ပြင်ဆင်ထားသော session JWT             | 401၊ CLI က ပြန်လည် exchange ပြုလုပ်သည်                     |
| exchange ပြုလုပ်ပြီးနောက် OmniRoute API key ကို ရုပ်သိမ်းထားခြင်း | နောက် RPC တွင် 401                                         |
| အသုံးပြုနေသော `cursor-api` connection မရှိခြင်း                   | 503 `unavailable`                                          |
| Cursor က connection ၏ key ကို ငြင်းပယ်ခြင်း                       | 401 `unauthenticated`၊ cache ထားသော session ကို ဖယ်ရှားသည် |
| Upstream သို့ ဆက်သွယ်၍မရခြင်း                                     | 502 `unavailable` (သန့်စင်ထားသော message)                  |
| `JWT_SECRET` သတ်မှတ်မထားခြင်း                                     | exchange ပြုလုပ်ရာတွင် 503                                 |
