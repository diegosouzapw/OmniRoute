ဤစာတမ်းသည် OmniRoute တွင် ထည့်သွင်းထားသော တုံ့ပြန်ချက်အခြေပြု လိုက်လျောညီထွေဖြစ်သည့် လမ်းကြောင်းရွေးချယ်မှု အခြေခံအုတ်မြစ်ကို ဖော်ပြထားသည်။ ၎င်းကို ရည်ရွယ်ချက်ရှိရှိ အတိုချုံးထားသည်—type သတ်မှတ်ထားသော routing-outcome channel တစ်ခု၊ လက်ရှိ auto-combo scorer သို့ ထည့်သွင်းပေးသည့် အွန်လိုင်း အရည်အသွေး signal တစ်ခု၊ ရွေးချယ်အသုံးပြုနိုင်သော OpenTelemetry exporter တစ်ခုနှင့် ရှင်းလင်းဖော်ပြနိုင်မှု endpoint တစ်ခုတို့ကို မိတ်ဆက်ပေးထားသည်။ ၎င်းသည် လက်ရှိ resilience stack (circuit breaker၊ connection cooldown၊ model lockout၊ health matrix၊ autopilot) ကို **အစားမထိုးပါ**—ယင်းကို ဖြည့်စွက်ပေးခြင်းသာ ဖြစ်သည်။

## 1. ဗိသုကာဆိုင်ရာ အခြေအနေ

OmniRoute သည် **request hot path** နှင့် **control/intelligence
plane** ပါဝင်သော data plane တစ်ခုဖြစ်သည်။ hot path သည် မြန်ဆန်မှု၊ memory အသုံးချမှု ထိရောက်မှု၊ asynchronous ဖြစ်မှု၊ ချို့ယွင်းမှုခံနိုင်ရည်ရှိမှုနှင့် ကြိုတင်ခန့်မှန်းနိုင်မှုတို့ကို ဆက်လက်ထိန်းသိမ်းထားရမည်။ အကဲဖြတ်မှု၊ အရည်အသွေး အမှတ်ပေးခြင်း၊ စမ်းသပ်မှုများနှင့် သမိုင်းဆိုင်ရာ ဆန်းစစ်လေ့လာမှုတို့သည် control plane နှင့် သက်ဆိုင်သည်။

```
AI Agent / IDE
      │
      ▼
┌─────────────────────┐
│    OmniRoute        │   data plane (မြန်ဆန်၊ sync၊ in-memory)
│  routing / failover │
│  health / guardrail │
│  cache / streaming  │
└──────────┬──────────┘
           │ RoutingEvent (ပို့ပြီးမစောင့်၊ ~0.2µs)
           ▼
┌─────────────────────┐
│  တုံ့ပြန်ချက် sinks │   control plane (async၊ အကောင်းဆုံးကြိုးပမ်းမှု)
│  quality tracker    │
│  OTel exporter      │
│  explain store      │
└──────────┬──────────┘
           ▼  အရည်အသွေး အမှတ်
      auto-combo scorer
```

### ရှိနှင့်ပြီးသောအရာများ (စစ်ဆေးပြီး၊ ထပ်မံမပြုလုပ်ထား)

| အယူအဆ                                      | ရှိပြီးသား အကောင်အထည်ဖော်မှု                                                                               |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| ရရှိနိုင်မှု (traffic ပို့နိုင်ပါသလား?)    | Circuit breaker (CLOSED/DEGRADED/OPEN/HALF_OPEN၊ DB တွင် သိမ်းဆည်းထား)၊ connection cooldown၊ model lockout |
| Health အစီရင်ခံမှု                         | `providerHealthMatrix.ts`၊ `providerHealthAutopilot.ts`                                                    |
| Shadow traffic                             | `open-sse/services/combo/shadowRouting.ts`                                                                 |
| Guardrails                                 | `src/lib/guardrails/` (မလုပ်ဆောင်မီ/လုပ်ဆောင်ပြီး hooks)                                                   |
| Exact cache                                | `src/lib/semanticCache.ts` (signature အခြေပြု)                                                             |
| Evaluators / eval အခြေပြု routing          | `src/lib/evals/`၊ `open-sse/services/evalRouting.ts`                                                       |
| Combo ဆုံးဖြတ်ချက် ရှင်းလင်းဖော်ပြနိုင်မှု | `open-sse/services/combo/decisionTrace.ts`                                                                 |
| Dashboard အချိန်နှင့်တစ်ပြေးညီ events      | `src/lib/events/eventBus.ts` (UI အသိပေးချက် channel၊ `unknown` payloads၊ မှတ်တမ်း 100 ခု)                  |

routing-event layer သည် `eventBus` ကို ပြန်လည်အကောင်အထည်ဖော်ထားခြင်း **မဟုတ်ပါ**။ ထို bus သည် dashboard ၏ အချိန်နှင့်တစ်ပြေးညီ အသိပေးချက် channel (type သတ်မှတ်ထားသော _event names_၊ အတွင်းပိုင်းမမြင်နိုင်သော payloads၊ UI consumers) ဖြစ်သည်။ `RoutingEvent` သည် control plane ၏ feedback sinks (quality tracker၊ OTel exporter၊ explain store) က အသုံးပြုသည့် type သတ်မှတ်ထားသော _outcome_ struct (latency/tokens/cost/outcome/finish-reason) ဖြစ်သည်။

### မရှိခဲ့သဖြင့် ဤနေရာတွင် ထည့်သွင်းထားသောအရာများ

1. **type သတ်မှတ်ထားသော routing-outcome event + sink abstraction** (`RoutingEvent` /
   `RoutingEventSink`)။ `decisionTrace` သည် combo အတိုင်းအတာအတွင်းသာ သက်ဆိုင်ပြီး in-memory သာဖြစ်သည်။
   `comboMetrics` သည် စုစည်းတိုးပွားလာသော counters များဖြစ်ပြီး `call_logs` သည် မပြုပြင်ထားသော async persistence ဖြစ်သည်။
   ၎င်းတို့အနက် မည်သည့်အရာကမျှ quality tracker၊ OTel
   exporter သို့မဟုတ် Future-AGI ပုံစံ evaluator တစ်ခုက subscribe လုပ်နိုင်သည့် type သတ်မှတ်ထားပြီး sink အခြေပြုသော outcome channel မဟုတ်ပါ။
2. output အရည်အသွေးအတွက် **အွန်လိုင်း အရည်အသွေး signal** (EWMA)—ယခင်က scorer သည် static task fitness နှင့် ရွေးချယ်ဖွင့်ထားသော eval pass-rates များမှတစ်ဆင့်သာ "quality" ကို အစားထိုးကိုယ်စားပြုခဲ့သည်။
3. GenAI semantic conventions များကို အသုံးပြုထားသည့် **ရွေးချယ်အသုံးပြုနိုင်ပြီး dependency မလိုအပ်သော OTel exporter**။
4. အမှန်တကယ် routing ဆုံးဖြတ်ချက်များနှင့် quality state ကို ပြန်ပေးသည့် **ရှင်းလင်းဖော်ပြနိုင်မှု endpoint**။

## 2. Routing ဖြစ်ရပ်များ (တုံ့ပြန်ချက် အခြေခံအုတ်မြစ်)

ဖိုင်များ: `open-sse/services/routing/events.ts`, `.../index.ts`

`RoutingEvent` တွင် routing metadata များသာ ပါဝင်သည်-

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ... တို့ထဲမှ တစ်ခု
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // ခွင့်ပြုစာရင်းတွင် ပါဝင်သော union
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

`RoutingEventSink` သည် TypeScript ရှိ `Send+Sync` ပုံစံ trait တစ်ခုဖြစ်သည်-

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // O(1) ဖြစ်ရမည်၊ synchronous I/O မပြုလုပ်ရ
}
```

Hot path သည် ပြီးဆုံးသွားသော request တစ်ခုစီအတွက် `emitRoutingEvent(event)` ကို တစ်ကြိမ်ခေါ်သည်
(streaming-completion callback၊ non-streaming success path နှင့်
`handleChatCore` ရှိ malformed-200 failure path တို့တွင်)။ မှတ်ပုံတင်ထားသော sink များဆီသို့ dispatch ပြုလုပ်ခြင်းသည် synchronous fan-out ဖြစ်သော်လည်း sink တစ်ခုစီသည် in-memory state ကို queue ထဲထည့်ခြင်း/အပ်ဒိတ်လုပ်ခြင်းသာ ပြုလုပ်သည်။ **Hot path ပေါ်တွင်
synchronous database write များနှင့် network I/O မရှိပါ။**

မူလ sink များ-

- `MemoryRoutingEventStore` — explain endpoint အတွက် အရွယ်အစားကန့်သတ်ထားသော (500) ring buffer ဖြစ်ပြီး အသစ်ဆုံးကို ဦးစွာထားသည်။
- `QualityTracker` consumer — EWMA quality estimate ကို အပ်ဒိတ်လုပ်သည်။
- `OtlpHttpsEventSink` — စိတ်ကြိုက်အသုံးပြုနိုင်ပြီး `OMNIROUTE_OTEL_ENDPOINT`
  (သို့မဟုတ် `OTEL_EXPORTER_OTLP_ENDPOINT`) သတ်မှတ်ထားမှသာ ဖွင့်ထားသည်။

### တိုင်းတာရရှိသော overhead (ပွင့်လင်းရိုးသားသော နှိုင်းယှဉ်မှု)

ဤ workstation ပေါ်တွင် `npm run bench:routing-events` (iteration 100k; တစ်ကြိမ်ချင်း percentile များသည်
`performance.now()` timer resolution အောက်တွင် ရှိသောကြောင့် sub-µs operation များကို စုစုပေါင်း µs/op အဖြစ် တိုင်းတာထားသည်)-

| အခြေအနေ                                | µs/op  | ops/s  |
| -------------------------------------- | ------ | ------ |
| baseline (scoring သာ)                  | ~0.045 | ~22 M  |
| baseline + RoutingEvent (sink 2 ခု)    | ~0.168 | ~5.9 M |
| baseline + event + OTel enqueue        | ~0.163 | ~6.1 M |
| concurrent (ကြားညှပ်ထားသော burst 8 ခု) | ~0.18  | —      |

Baseline scoring ထက်ပိုသော event-dispatch delta သည် ~0.12 µs/request ဖြစ်ပြီး OTel sink သည်
enqueue သာပြုလုပ်သည် (O(1) buffer push)၊ ထို့ကြောင့် တိုင်းတာနိုင်လောက်သော ထပ်ဆောင်းကုန်ကျမှု မရှိပါ။ ဤကိန်းဂဏန်းများသည်
စက်တစ်လုံးချင်းအလိုက် ကွဲပြားပြီး နှိုင်းယှဉ်ချက်သာဖြစ်သည် — production အတွက် အာမခံချက်မဟုတ်ပါ။ v1 ၏ "~0.2 µs"
ကိန်းဂဏန်းသည် စုစုပေါင်းခန့်မှန်းချက်ဖြစ်ခဲ့သည်။ ဤနည်းလမ်းသည် scoring baseline ကို
event-dispatch ကုန်ကျစရိတ်မှ သီးခြားခွဲထားသည်။

## 3. Quality Signal (တုံ့ပြန်ချက်အခြေပြု provider state)

ဖိုင်များ: `open-sse/services/routing/quality.ts`

v2 သည် **operational** quality ကို **semantic** quality မှ ခွဲခြားထားသည်-

- **Operational** — routing hot path မှ ရယူထားသည် (HTTP 4xx/5xx၊ connection
  failure များ၊ 429 များ၊ malformed response များ၊ stream ပြတ်တောက်မှုများ၊ `finish_reason=length`၊
  output မရှိသော success များ၊ latency/TTFT EWMA)။ 200 ကို semantic
  quality အဖြစ် သတ်မှတ်မထားပါ။
- **Semantic** — ထုတ်လုပ်ထားသော output ၏ အမှန်တကယ်တန်ဖိုးဖြစ်သည်။ Evaluator တစ်ခုက
  `setSemanticQuality()` မှတစ်ဆင့်သာ ထုတ်ပေးနိုင်သည်။ တစ်ခုခုက မပေးမချင်း ၎င်းသည် `null` ဖြစ်ပြီး
  operational score ထဲသို့ မည်သည့်အခါမျှ စိမ့်ဝင်ခြင်းမရှိပါ။

(provider, model) အတွဲတစ်ခုစီအလိုက် state (EWMA + အရွယ်အစားကန့်သတ်ထားသော counter များ)-

- `successEwma` — outcome success ၏ EWMA (α=0.2)။
- `latencyEwma` / `ttftEwma` — latency ၏ EWMA (α=0.1)။
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`။
- `recencyMs` — model ကို နောက်ဆုံးတွေ့ရှိခဲ့သည့်အချိန်မှ မည်မျှမကြာသေးသည်ကို ဖော်ပြသည်။

### Confidence / sample အသိအမြင်

`confidence = clamp01(samples / 50)` ဖြစ်ပြီး scorer သို့ ပြန်ပေးသော score ကို
ကြားနေအလယ်မှတ်ဘက်သို့ ရောစပ်ထားသည်-

```
score = 0.5 + confidence * (operational - 0.5)
```

အကျိုးဆက်များ (test များဖြင့် အတည်ပြုထားသည်)-

- Cold provider တစ်ခု (sample 0 ခု) သည် **0.5** ရရှိသည် — မမျှမတ အပြစ်ပေးခံရခြင်းမရှိသော်လည်း
  ခိုင်မာသော observation ထောင်ပေါင်းများစွာရှိသည့် provider တစ်ခုကို ကျော်လွှားနိုင်ခြင်းမရှိပါ။
- ကံကောင်းစွာ success 7 ခုရထားသော provider တစ်ခုကို 0.5 ဘက်သို့ ဆွဲယူထားသည် (အကောင်းမြင်လွန်းသော initialization ကြောင့်
  မည်သည့်အခါမျှ လွှမ်းမိုးနိုင်မည်မဟုတ်ပါ)။
- Sample 50+ ရှိသော provider တစ်ခုသည် ၎င်း၏ operational score အမှန်သို့ ချဉ်းကပ်သည်။
- အရည်အသွေးကျဆင်းခြင်းနှင့် ပြန်လည်ကောင်းမွန်ခြင်းတို့သည် တဖြည်းဖြည်း ဖြစ်ပေါ်သည် (EWMA)၊ သီးခြား failure တစ်ခုတည်းက
  ကောင်းမွန်နေသော provider တစ်ခုကို ပျက်စီးစေမည်မဟုတ်ပါ။

`ProviderQuality` သည် `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }` ကို ဖော်ထုတ်ပေးသည်။

၎င်းကို `quality` scoring factor အဖြစ် auto-combo scorer ထဲသို့ ပေးပို့သည်-

- `open-sse/services/autoCombo/scoring.ts` ရှိ `ScoringFactors.quality` / `ScoringWeights.quality`။
- `DEFAULT_WEIGHTS`: `health` 0.1905 → 0.1605၊ `quality` 0.03။ စုစုပေါင်းသည် 1.0 အဖြစ် ဆက်ရှိသည်။
- `buildAutoCandidates` သည် tracker မှ `candidate.quality` ကို ဖြည့်သွင်းသည်။ ဒေတာမရှိသော candidate များအတွက်
  မူလတန်ဖိုးမှာ ကြားနေ **0.5** ဖြစ်သည် (cold candidate တစ်ခုသည် အားပေးမြှင့်တင်ခြင်းလည်း မခံရသကဲ့သို့
  အပြစ်ပေးခြင်းလည်း မခံရပါ)။

အပိတ် loop-

```
RoutingEvent → QualityTracker → getQualityScore → auto-combo quality factor
      ↑                                                    │
      └────── request outcome (handleChatCore) ←────────────┘
```

### Hard exclusion နှင့် soft penalty

Quality signal သည် **soft adaptive preference** သာဖြစ်သည်။ Hard exclusion ကို
လက်ရှိ resilience stack ကသာ ဆက်လက်တာဝန်ယူသည်- circuit breaker OPEN၊ quota ကုန်ဆုံးမှု၊
auth failure၊ model lockout — ဤအရာများထဲမှ မည်သည့်အရာကိုမျှ quality score က သက်ရောက်မှုမရှိပါ။
Quality score ယာယီကျဆင်းသွားသော provider တစ်ခုကို ဦးစားပေးမှုလျှော့ချမည်သာဖြစ်ပြီး
hard-disable မည်သည့်အခါမျှ ပြုလုပ်မည်မဟုတ်ပါ။

## 3b. စံသတ်မှတ်ထားသော stream အချိန်တိုင်းတာမှု (TTFT / ITL)

ဖိုင်များ: `open-sse/utils/streamTiming.ts`

`createStreamTiming()` သည် streaming လမ်းကြောင်းအတွက် တစ်ခုတည်းသော instrumentation ဆက်သွယ်မှတ်ဖြစ်ပြီး `createSSEStream` (open-sse/utils/stream.ts) နှင့် ချိတ်ဆက်ထားသည်-

- `markByte()` — upstream မှ ပထမဆုံး chunk ကို လက်ခံရရှိခြင်း။
- `markForward()` — client ထံ ပထမဆုံး chunk ပို့ဆောင်ခြင်း (TTFT အတွက် အသုံးပြုသည်)။
- `markInterrupted()` — ပုံမှန်အတိုင်း မပြီးဆုံးမီ stream timeout/abort/error ဖြစ်ခြင်း။
- `ttft()` = ပထမဆုံး ပို့ဆောင်လိုက်သည့် SSE chunk ၏ latency။ **၎င်းသည် token-level TTFT မဟုတ်ပါ** —
  SSE chunk တစ်ခုတွင် token သုည/တစ်ခု/အများအပြား ပါဝင်နိုင်သည်။ အတိအကျ မှတ်တမ်းပြုစုထားသည်။
- `avgItlMs()` = chunk များအကြား ပျမ်းမျှအချိန်ကွာဟချက် (ITL အတွက် chunk-latency အနီးစပ်ဆုံးညွှန်းကိန်း)။

TTFT/ITL/interrupted တို့သည် `RoutingEvent` (`ttftMs`, `itlMs`) ထဲသို့ စီးဝင်ပြီး
OTel sink က GenAI/OmniRoute span attribute များအဖြစ် export လုပ်သည်။

## 4. OpenTelemetry / GenAI စောင့်ကြည့်နိုင်စွမ်း

ဖိုင်များ: `open-sse/services/routing/otel.ts`

- Dependency မလိုအပ်သော OTLP/HTTP JSON exporter (`@opentelemetry/*` SDK မဟုတ်ဘဲ
  global `fetch` ကို အသုံးပြုသည်)။
- Span များသည် GenAI semantic convention များ (`gen_ai.provider.name`,
  `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`,
  `gen_ai.completion.finish_reason`, `gen_ai.system`) နှင့် OmniRoute routing
  attribute များ (outcome, status, ttft, retries, fallback) ကို လိုက်နာသည်။
- `record()` သည် bounded buffer တစ်ခုထဲသို့သာ enqueue လုပ်သည် (O(1)); နောက်ခံ timer
  တစ်ခုက `POST {endpoint}/v1/traces` မှတစ်ဆင့် asynchronous ပုံစံဖြင့် flush လုပ်သည်။ ဝန်ပိုနေချိန်တွင်
  သက်တမ်းအရင့်ဆုံး event များကို ဖယ်ရှားသည် (`dropped` counter) — data
  plane ကို မည်သည့်အခါမျှ backpressure မဖြစ်စေပါ။
- **Configure မလုပ်ထားပါက ပိတ်ထားသည်။** `OMNIROUTE_OTEL_ENDPOINT` (သို့မဟုတ်
  `OTEL_EXPORTER_OTLP_ENDPOINT`) ကို သတ်မှတ်ထားရမည်; မဟုတ်ပါက sink ကို
  register မလုပ်ဘဲ OTel code လုံးဝ မလည်ပတ်ပါ။

## 5. ရှင်းလင်းဖော်ပြနိုင်စွမ်း

- `GET /v1/explain/routing` သည် မကြာသေးမီက `RoutingEvent` များ (အမှန်တကယ်
  ဆုံးဖြတ်ချက်များကို နောက်ဆုံးအသစ်ဆုံးမှစ၍) နှင့် provider/model တစ်ခုချင်းစီ၏ quality snapshot ကို ပြန်ပေးသည်။
- Auth သည် `/v1/combos` နှင့် တူညီသည် (Bearer API key သို့မဟုတ် dashboard session;
  `REQUIRE_API_KEY=false` ဖြစ်သည့် single-user local deployment များတွင် anonymous အသုံးပြုနိုင်သည်)။
- Invocation တစ်ကြိမ်ချင်းစီအတွက် combo-level trace များကို ရှိပြီးသား
  `decisionTrace.ts` (header `X-OmniRoute-Combo-Trace`) မှတစ်ဆင့် ဆက်လက်ရယူနိုင်သည်။
- လုံခြုံရေး: event များတွင် routing metadata သာ ပါဝင်ပြီး prompt/body/credential များ
  လုံးဝမပါဝင်ပါ။

## 6. Evaluation-plane ပေါင်းစည်းမှု (အနာဂတ် AGI အဆင်သင့်ဖြစ်မှု)

OmniRoute သည် Future AGI (သို့မဟုတ် မည်သည့် evaluator ကိုမဆို) **ဖြစ်နိုင်ခြေရှိသော
intelligence/evaluation backend အဖြစ်သာ သတ်မှတ်ပြီး dependency အဖြစ် မသတ်မှတ်ပါ**။ ချိတ်ဆက်မှတ်များမှာ-

- `RoutingEventSink` တစ်ခုက event များကို evaluator ထံ asynchronous ပုံစံဖြင့် ပို့ဆောင်နိုင်သည်။
- `MemoryRoutingEventStore` + quality snapshot သည် evaluator အတွက် မပြုပြင်ရသေးသော
  decision stream ကို ပေးသည်။
- အနာဂတ် `Evaluator` (deterministic, local judge, HTTP, WASM) သည်
  event/trace များကို လက်ခံအသုံးပြုပြီး တူညီသော `getQualityScore`/quality-factor လမ်းကြောင်းထဲသို့
  ထည့်သွင်းမည့် `QualityScore` ကို ပြန်ပေးမည်။
- ရှိပြီးသား eval-driven routing (`open-sse/services/evalRouting.ts`) သည် ဖွင့်ထားသည့်အခါ
  `eval_runs` pass-rate များအလိုက် combo target များကို ပြန်လည်စီစဉ်ပြီးဖြစ်သည်။

Request လမ်းကြောင်းပေါ်တွင် evaluation ကို synchronous ပုံစံဖြင့် လုပ်ဆောင်ခြင်းမရှိဘဲ evaluator
မရှိသည့်အခါတွင်လည်း gateway သည် အပြည့်အဝ လည်ပတ်နိုင်သည်။

## 7. နောက်ဆုံး ဗိသုကာဆိုင်ရာ ပြန်လည်သုံးသပ်ချက်

1. **Synchronous hot path ပေါ်တွင် ဘာတွေကျန်ရှိသလဲ။** Routing/scoring၊ guardrail
   pre-check များ၊ cache lookup နှင့် in-memory sink များသို့ `emitRoutingEvent` fan-out တစ်ကြိမ်
   (baseline scoring ထက် ~0.12 µs ပိုကြာခြင်း) တို့ ဖြစ်သည်။
2. **Asynchronous processing သို့ မည်သည့်အရာများ ရွှေ့ပြောင်းခဲ့သလဲ။** OTel export (timer + fetch)၊
   `call_logs`/usage persistence၊ semantic-cache write များ; quality သည် in-memory
   ဖြစ်ပြီး O(1) ဖြစ်သောကြောင့် async မလိုအပ်ပါ။
3. **Routing outcome တစ်ခုသည် feedback မည်သို့ ဖြစ်လာသလဲ။** `handleChatCore` က
   `RoutingEvent` တစ်ခုကို emit လုပ်သည် → `QualityTracker` က EWMA state ကို update လုပ်သည် → `getQualityScore`
   က auto-combo `quality` factor ထဲသို့ ထည့်သွင်းပေးသည်။
4. **Quality သည် အနာဂတ် routing ကို မည်သို့ သက်ရောက်စေသလဲ။** Quality score နိမ့်ပါက
   `scoreAutoTargets` အတွင်းရှိ ထို provider/model ၏ weighted score ကို လျှော့ချသဖြင့် စွမ်းဆောင်ရည်ကျဆင်းနေသော
   model များကို တဖြည်းဖြည်း ဦးစားပေးမှုလျှော့ချပြီး ၎င်းတို့၏ EWMA တိုးတက်လာသည်နှင့် ပြန်လည်ကောင်းမွန်လာစေသည်။
5. **Future AGI သည် dependency မဖြစ်ဘဲ မည်သို့ ပေါင်းစည်းနိုင်သလဲ။** `RoutingEventSink`
   interface / အနာဂတ် `Evaluator` adapter မှတစ်ဆင့်ဖြစ်ပြီး hardcoded
   dependency မရှိပါ။
6. **Evaluator ကို မရရှိနိုင်သည့်အခါ ဘာဖြစ်မလဲ။** Routing ကို မထိခိုက်ပါ;
   စောင့်ကြည့်ရရှိထားသော signal မရှိသည့် model များအတွက် quality သည် neutral (1.0) ကို fallback လုပ်သည်။
7. **Telemetry ကို မရရှိနိုင်သည့်အခါ ဘာဖြစ်မလဲ။** OTel sink ကို
   register မလုပ်ရုံသာဖြစ်ပြီး routing layer ၏ ကျန်အစိတ်အပိုင်းများမှာ မပြောင်းလဲဘဲ ဆက်လက်လည်ပတ်သည်။
8. **ဝန်ပိုလာသည့်အခါ ဘာဖြစ်မလဲ။** OTel buffer သည် သက်တမ်းအရင့်ဆုံး event များကို ဖယ်ရှားသည်; quality
   နှင့် ring buffer တို့သည် တည်ဆောက်ပုံအရ bounded ဖြစ်ပြီး backpressure မရှိပါ။
9. **Provider state သည် စွမ်းဆောင်ရည်ကျဆင်းပြီးနောက် မည်သို့ ပြန်လည်ကောင်းမွန်လာသလဲ။** အောင်မြင်မှုများ
   စုဆောင်းလာသည်နှင့် EWMA သည် ပြန်လည် converge ဖြစ်သည်; warmup သည် cold model များကို neutral အဖြစ် ထိန်းထားပြီး circuit breaker
   သည် HALF_OPEN probe များမှတစ်ဆင့် သီးခြားစီ ပြန်လည်ကောင်းမွန်လာသည်။
10. **အဆိုပြုထားသော မည်သည့် feature များကို ရည်ရွယ်ချက်ရှိရှိ အကောင်အထည်မဖော်ခဲ့သနည်း၊ အဘယ်ကြောင့်နည်း။**
    - Shadow traffic / experiment များ — အကောင်အထည်ဖော်ပြီးဖြစ်သည်
      (`combo/shadowRouting.ts`); ထပ်မံတည်ဆောက်ထားခြင်းမရှိပါ။
    - Guardrail များ — အကောင်အထည်ဖော်ပြီးဖြစ်သည် (`src/lib/guardrails/`); ပုံတူထပ်မံမပြုလုပ်ပါ။
    - Semantic cache — အကောင်အထည်ဖော်ပြီးဖြစ်သည် (`src/lib/semanticCache.ts`); ပုံတူထပ်မံမပြုလုပ်ပါ။
    - ပြည့်စုံသော experiment-management platform၊ dataset tooling၊ prompt-optimization
      platform၊ vector DB သို့မဟုတ် မဖြစ်မနေလိုအပ်သော external OTel infrastructure — ပေါ့ပါးသည့်
      data plane ၏ scope ပြင်ပတွင် ရှိသည်။
    - Rust `RoutingEvent` struct — data plane သည် TypeScript ဖြစ်သည်; TS type သည်
      လိုက်လျောညီထွေ ပြောင်းလဲထားသော တူညီသည့်အရာဖြစ်သည်။
