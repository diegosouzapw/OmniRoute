## အားနည်းချက်များကို အစီရင်ခံခြင်း

OmniRoute တွင် လုံခြုံရေးအားနည်းချက်တစ်ခုကို တွေ့ရှိပါက တာဝန်သိစွာ အစီရင်ခံပါ-

1. အများမြင်နိုင်သော GitHub issue ကို **မဖွင့်ပါနှင့်**
2. [GitHub Security Advisories](https://github.com/diegosouzapw/OmniRoute/security/advisories/new) ကို အသုံးပြုပါ
3. ဖော်ပြချက်၊ ပြန်လည်ဖြစ်ပေါ်စေရန် အဆင့်များနှင့် ဖြစ်လာနိုင်သော သက်ရောက်မှုတို့ကို ထည့်သွင်းပါ

3.8.59 ပြီးနောက် နောက်ဗားရှင်းမှာ **3.9.0** ဖြစ်ပြီး၊ ၎င်းသည်
`stable/v3` branch တွင် ရေရှည်ပံ့ပိုးမှုလိုင်းကို စတင်ပေးသည် ([`ROADMAP.md`](ROADMAP.md) → "အဆင့် 3 — v3.9.0 LTS" ကို ကြည့်ပါ)။

- **`stable/v3` က လက်ခံရရှိမည့်အရာများ-** bug ပြင်ဆင်ချက်များ၊ လုံခြုံရေး patch များနှင့် provider အပ်ဒိတ်များ။ လုပ်ဆောင်ချက်အသစ်များကို
  v4 channel သို့ ထည့်သွင်းမည်ဖြစ်ပြီး၊ LTS လိုင်းသည် တည်ငြိမ်မှုကို ဦးစားပေးသည်။ `npm install omniroute`
  (`latest` dist-tag) သည် v4 cycle တစ်လျှောက်လုံး v3 ပေါ်တွင် ဆက်ရှိနေမည်။
- **ကာလကြာမြင့်ချိန်-** `<T-GAP-3: ပိုင်ရှင်၏ ဆုံးဖြတ်ချက်ကို စောင့်ဆိုင်းနေသည် — ROADMAP.md ကို ကြည့်ပါ>`။ v4.0 GA ပြီးနောက်
  (`latest` က v4 သို့ ပြောင်းသည့်အချိန်) ပံ့ပိုးမှုကာလ၏ အရှည်ကို **မဆုံးဖြတ်ရသေးပါ**။ ထိန်းသိမ်းသူက
  ကြေညာသည့်အခါ ဤကဏ္ဍကို အပ်ဒိတ်လုပ်မည်။ ထိုအချိန်မတိုင်မီ အဆုံးသတ်ရက်ကို မယူဆပါနှင့်။
- **LTS လိုင်းတွင် အားနည်းချက်တစ်ခုကို အစီရင်ခံခြင်း-** အခြားမည်သည့်ဗားရှင်းနှင့်မဆို တူညီသော channel ကို အသုံးပြုပါ —
  သီးသန့် [GitHub Security Advisory](https://github.com/diegosouzapw/OmniRoute/security/advisories/new) ကို အသုံးပြုပြီး၊

  `stable/v3` တွင် ထည့်သွင်းပြီး v4 သို့ forward-port လုပ်မည်။

  [`docs/security/LTS_SECURITY_BASELINE.md`](docs/security/LTS_SECURITY_BASELINE.md) တွင် မှတ်တမ်းတင်ထားသည်။

## လုံခြုံရေး ဗိသုကာ

OmniRoute သည် အလွှာစုံ လုံခြုံရေးမော်ဒယ်ကို အကောင်အထည်ဖော်ထားသည်-

```
တောင်းဆိုမှု → CORS → Authz pipeline (အမျိုးအစားခွဲခြင်း → မူဝါဒများ → ကျင့်သုံးခြင်း)
       → ကာကွယ်ရေးစည်းမျဉ်းများ (PII ဖုံးကွယ်စနစ်၊ prompt injection၊ vision bridge)
       → နှုန်းကန့်သတ်စနစ် → Circuit Breaker → Cooldown → Model Lockout → Provider
```

| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 🛡️ သိမ်းဆည်းထားစဉ် ကုဒ်ဝှက်ခြင်း

SQLite တွင် သိမ်းဆည်းထားသည့် ထိခိုက်လွယ်သော ဒေတာအားလုံးကို scrypt key derivation ပါသော **AES-256-GCM** ဖြင့် ကုဒ်ဝှက်ထားသည်-

- API key များ၊ access token များ၊ refresh token များနှင့် ID token များ
- ဗားရှင်းသတ်မှတ်ထားသော ဖော်မတ်- `enc:v1:<iv>:<ciphertext>:<authTag>`
- `STORAGE_ENCRYPTION_KEY` ကို မသတ်မှတ်ထားပါက passthrough mode (စာသားအတိုင်း)

```bash
# ကုဒ်ဝှက်ခြင်း key ကို ထုတ်လုပ်ရန်-
STORAGE_ENCRYPTION_KEY=$(openssl rand -hex 32)
```

### 🛡️ ကာကွယ်ရေးစည်းမျဉ်း Framework

OmniRoute တွင် ဦးစားပေးအစီအစဉ်အလိုက် စီထားသော ထည့်သွင်းပြီး ကာကွယ်ရေးစည်းမျဉ်း 3 ခုပါဝင်သည့် hot-reload လုပ်နိုင်သော **guardrails registry** (`src/lib/guardrails/`) ပါရှိသည်-

| ကာကွယ်ရေးစည်းမျဉ်း | ဦးစားပေးအဆင့် | ရည်ရွယ်ချက်                                                                                                                         |
| ------------------ | ------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `vision-bridge`    | 5             | ပုံများကို သိရှိနားလည်သော ဖော်ပြချက်များဖြင့် vision မပါသည့် model များကို ချိတ်ဆက်ပေးပြီး၊ ပုံ URL များအတွက် SSRF ကာကွယ်မှု ပေးသည် |
| `pii-masker`       | 10            | ခေါ်ဆိုမှုမတိုင်မီနှင့် ပြီးနောက် PII ဖယ်ရှားဖုံးကွယ်ခြင်း (အီးမေးလ်များ၊ ဖုန်း၊ CPF၊ CNPJ၊ credit card များ၊ SSN)                  |
| `prompt-injection` | 20            | override/role-hijack/jailbreak/leak ပုံစံများကို ရှာဖွေသိရှိသည်                                                                     |

စိတ်ကြိုက် ကာကွယ်ရေးစည်းမျဉ်းများကို `registerGuardrail(new MyGuardrail())` မှတစ်ဆင့် မှတ်ပုံတင်နိုင်သည်။ မော်ဒယ်သည် fail-open ဖြစ်သည် (exception များက traffic ကို မည်သည့်အခါမျှ ပိတ်ဆို့မည်မဟုတ်ပါ)။ Request တစ်ခုချင်းအလိုက် ဖယ်ထုတ်ရန် `x-omniroute-disabled-guardrails` header ကို အသုံးပြုပါ။ → [`docs/security/GUARDRAILS.md`](docs/security/GUARDRAILS.md) ကို ကြည့်ပါ။

### 🧠 Prompt Injection ကာကွယ်ရေးစနစ်

LLM တောင်းဆိုမှုများအတွင်းရှိ prompt injection ပုံစံများကို အကောင်းဆုံးကြိုးပမ်းမှု heuristic နည်းလမ်းဖြင့် ရှာဖွေသည့် middleware ဖြစ်သည်။
**ပြီးပြည့်စုံသော prompt-injection firewall မဟုတ်ပါ** — false positive များ (အန္တရာယ်မရှိသော
persona/RPG prompt များ) နှင့် false negative များ (leetspeak၊ spacing နှင့် အင်္ဂလိပ်မဟုတ်သော ပုံစံများ) ဖြစ်ပေါ်နိုင်သည်။

| ပုံစံအမျိုးအစား                 | ပြင်းထန်မှု | ဥပမာ                                                                        |
| ------------------------------- | ----------- | --------------------------------------------------------------------------- |
| စနစ်ညွှန်ကြားချက် အစားထိုးခြင်း | မြင့်       | "ယခင်ညွှန်ကြားချက်အားလုံးကို လျစ်လျူရှုပါ"                                  |
| အခန်းကဏ္ဍ အပိုင်စီးခြင်း        | အလယ်အလတ်    | "ယခု သင်သည် DAN ဖြစ်ပြီး မည်သည့်အရာကိုမဆို လုပ်နိုင်သည်"                    |
| အကန့်အသတ်သင်္ကေတ ထိုးသွင်းခြင်း | မြင့်       | context နယ်နိမိတ်များကို ချိုးဖောက်ရန် encode လုပ်ထားသော ခွဲခြားသင်္ကေတများ |
| DAN/Jailbreak                   | အလယ်အလတ်    | လူသိများသော jailbreak prompt ပုံစံများ                                      |
| ညွှန်ကြားချက် ပေါက်ကြားခြင်း    | မြင့်       | "သင့် system prompt ကို ပြပါ"                                               |
| Encoding ဖြင့် ရှောင်လွှဲခြင်း  | အလယ်အလတ်    | base64/rot13/hex decode + ညွှန်ကြားချက်ဆိုင်ရာ keyword များ                 |

`block` mode တွင် **မြင့်** ပြင်းထန်မှုရှိသော ရှာဖွေတွေ့ရှိချက်များကိုသာ ပိတ်ဆို့သည်။ အလယ်အလတ်ပြင်းထန်မှုရှိသော
အုပ်စုများကို မှတ်တမ်းတင်သော်လည်း `sanitizeRequest` က မည်သည့်အခါမျှ ပိတ်ဆို့မည်မဟုတ်ပါ။

dashboard (Settings → Security) သို့မဟုတ် `.env` မှတစ်ဆင့် စီစဉ်သတ်မှတ်ပါ-

```env
INPUT_SANITIZER_ENABLED=true
INPUT_SANITIZER_MODE=block    # warn | block (injection မူဝါဒ၊ ယခင် "redact" သည် injection စာသားကို ဖယ်ရှားခြင်းမပြုပါ)
INPUT_SANITIZER_BLOCK_THRESHOLD=high  # high (မူလသတ်မှတ်ချက်) | medium | low — ဤအဆင့်နှင့်အထက် ပြင်းထန်မှုများကို block mode တွင် ပိတ်ဆို့သည်
```

### 🔒 PII ဖုံးကွယ်ခြင်း

ကိုယ်ရေးကိုယ်တာအထောက်အထားဖော်ထုတ်နိုင်သော အချက်အလက်များကို အလိုအလျောက်ရှာဖွေခြင်းနှင့် ရွေးချယ်နိုင်သော ဖုံးကွယ်ခြင်း-

| PII အမျိုးအစား | ပုံစံ                 | အစားထိုးစာသား      |
| -------------- | --------------------- | ------------------ |
| အီးမေးလ်       | `user@domain.com`     | `[EMAIL_REDACTED]` |
| CPF (ဘရာဇီး)   | `123.456.789-00`      | `[CPF_REDACTED]`   |
| CNPJ (ဘရာဇီး)  | `12.345.678/0001-00`  | `[CNPJ_REDACTED]`  |
| ခရက်ဒစ်ကတ်     | `4111-1111-1111-1111` | `[CC_REDACTED]`    |
| ဖုန်း          | `+55 11 99999-9999`   | `[PHONE_REDACTED]` |
| SSN (အမေရိကန်) | `123-45-6789`         | `[SSN_REDACTED]`   |

```env
PII_REDACTION_ENABLED=true   # တောင်းဆိုမှုရှိ PII ကို ပြန်လည်ရေးသားခြင်း၊ INPUT_SANITIZER_MODE နှင့် သီးခြားလွတ်လပ်သည်
PII_RESPONSE_SANITIZATION=true  # ရွေးချယ်နိုင်သည်- client များထံ ပြန်ပေးသည့် provider တုံ့ပြန်ချက်များရှိ PII ကို ဖုံးကွယ်သည်
```

## လိုအပ်သော ပတ်ဝန်းကျင် Variable များ

ဆာဗာကို မစတင်မီ လျှို့ဝှက်တန်ဖိုးအားလုံးကို သတ်မှတ်ထားရမည်။ ၎င်းတို့ မရှိလျှင် သို့မဟုတ် လုံခြုံမှုအားနည်းလျှင် ဆာဗာသည် **ချက်ချင်း ရပ်တန့်မည်**။

```bash
# လိုအပ်သည် — အောက်ပါတန်ဖိုးများမရှိဘဲ ဆာဗာ စတင်မည်မဟုတ်ပါ:
JWT_SECRET=$(openssl rand -base64 48)     # အနည်းဆုံး စာလုံး 32 လုံး
API_KEY_SECRET=$(openssl rand -hex 32)    # အနည်းဆုံး စာလုံး 16 လုံး

# အကြံပြုသည် — သိမ်းဆည်းထားစဉ် ကုဒ်ဝှက်ခြင်းကို ဖွင့်ပေးသည်:
STORAGE_ENCRYPTION_KEY=$(openssl rand -hex 32)
```

ဆာဗာသည် `changeme`, `secret` သို့မဟုတ် `password` ကဲ့သို့ လုံခြုံမှုအားနည်းသည်ဟု သိထားသော တန်ဖိုးများကို တက်ကြွစွာ ငြင်းပယ်သည်။

## Docker လုံခြုံရေး

- Production တွင် root မဟုတ်သော user ကို အသုံးပြုပါ
- လျှို့ဝှက်တန်ဖိုးများကို read-only volume များအဖြစ် mount လုပ်ပါ
- `.env` ဖိုင်များကို Docker image များထဲသို့ မည်သည့်အခါမျှ copy မလုပ်ပါနှင့်
- အရေးကြီးသောဖိုင်များကို ဖယ်ထုတ်ရန် `.dockerignore` ကို အသုံးပြုပါ
- HTTPS နောက်ကွယ်တွင် အသုံးပြုသည့်အခါ `AUTH_COOKIE_SECURE=true` ဟု သတ်မှတ်ပါ

docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --read-only \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  -e JWT_SECRET="$(openssl rand -base64 48)" \
  -e API_KEY_SECRET="$(openssl rand -hex 32)" \

  diegosouzapw/omniroute:latest

## Dependency များ

- `npm audit` ကို ပုံမှန် run ပါ (`npm run audit:deps` သည် main + electron ကို လွှမ်းခြုံသည်)
- Dependency များကို အမြဲ update လုပ်ထားပါ
- Project သည် commit မလုပ်မီ စစ်ဆေးမှုများအတွက် `husky` + `lint-staged` ကို အသုံးပြုသည် (lint-staged + check-docs-sync + check:any-budget:t11)
- CI pipeline သည် push တိုင်းတွင် ESLint လုံခြုံရေးစည်းမျဉ်းများကို run သည် (`no-eval`, `no-implied-eval`, `no-new-func` = error)
- Provider constant များကို module load လုပ်ချိန်၌ Zod မှတစ်ဆင့် စစ်ဆေးအတည်ပြုသည် (`src/shared/validation/schemas.ts`)
- ပုံမှန်အခြေအနေကတည်းက လုံခြုံသော library များကို အသုံးပြုထားသည်- `dompurify` / `isomorphic-dompurify` (XSS), `jose` (JWT), `better-sqlite3` (parameterized query များကြောင့် SQLi အန္တရာယ်မရှိ), `bcryptjs` (စကားဝှက် hash ပြုလုပ်ခြင်း)

## တင်းကျပ်သော လုံခြုံရေးစည်းမျဉ်းများ

ဤစည်းမျဉ်းများကို tooling နှင့် reviewer များက မဖြစ်မနေ လိုက်နာစေသည်-

1. **လျှို့ဝှက်တန်ဖိုးများကို မည်သည့်အခါမျှ commit မလုပ်ပါနှင့်** — `.env` ကို gitignore လုပ်ထားသည်။ `.env.example` သည် template ဖြစ်သည် (literal များမပါ၊ comment များသာပါသည် — အောက်ပါ PUBLIC_CREDS.md ကို ကြည့်ပါ)
2. **`eval()`, `new Function()` သို့မဟုတ် implied eval ကို မည်သည့်အခါမျှ မသုံးပါနှင့်** — ESLint က မဖြစ်မနေ လိုက်နာစေသည်
3. တာဝန်ရှိ operator ၏ ရှင်းလင်းသော ခွင့်ပြုချက်မရှိဘဲ **Husky hook များကို မည်သည့်အခါမျှ ကျော်မသွားပါနှင့်** (`--no-verify`, `--no-gpg-sign`)
4. **Route များတွင် raw SQL ကို မည်သည့်အခါမျှ မရေးပါနှင့်** — `src/lib/db/` (parameterized) မှတစ်ဆင့်သာ အမြဲလုပ်ဆောင်ပါ
5. **Input များကို Zod ဖြင့် အမြဲစစ်ဆေးအတည်ပြုပါ** — `src/shared/validation/schemas.ts`
6. **Upstream header များကို အမြဲ သန့်စင်ပါ** — denylist ကို `src/shared/constants/upstreamHeaders.ts` တွင် ထားရှိသည်
7. **သိမ်းဆည်းထားသော credential များကို ကုဒ်ဝှက်ပါ** — `src/lib/db/encryption.ts` မှတစ်ဆင့် AES-256-GCM ကို အသုံးပြုပါ
8. **အများသုံး upstream OAuth identifier များအတွက် `resolvePublicCred()` ကို အသုံးပြုပါ** — `AIza…` / `GOCSPX-…` / `…apps.googleusercontent.com` literal များကို source ထဲတွင် မည်သည့်အခါမျှ ထည့်သွင်းမထားပါနှင့်။ [`docs/security/PUBLIC_CREDS.md`](docs/security/PUBLIC_CREDS.md) ကို ကြည့်ပါ။
9. **Error response များကို `buildErrorBody()` / `sanitizeErrorMessage()` မှတစ်ဆင့် ပေးပို့ပါ** — raw `err.stack` / `err.message` ကို HTTP / SSE / executor / MCP response body များတွင် မည်သည့်အခါမျှ မထည့်ပါနှင့်။ [`docs/security/ERROR_SANITIZATION.md`](docs/security/ERROR_SANITIZATION.md) ကို ကြည့်ပါ။
10. **`exec()` / `spawn()` runtime တန်ဖိုးများကို `env` option မှတစ်ဆင့် ပေးပါ** — ပြင်ပ path များ သို့မဟုတ် ယုံကြည်စိတ်ချရမှုမရှိသော တန်ဖိုးများကို shell မှတစ်ဆင့် ပေးပို့သော script များထဲသို့ string interpolation ဖြင့် မည်သည့်အခါမျှ မထည့်ပါနှင့်။ ကိုးကားရန်- `src/mitm/cert/install.ts::updateNssDatabases`။
11. **ပုံမှန်အခြေအနေကတည်းက လုံခြုံသော library များကို ဦးစားပေးပါ** — [tldrsec/awesome-secure-defaults](https://github.com/tldrsec/awesome-secure-defaults) (Helmet.js, DOMPurify, ssrf-req-filter, safe-regex, Google Tink) ကို ကြည့်ပါ။ ကိုယ်တိုင် ဖန်တီးမည့်အစား ၎င်းတို့ကို ဦးစွာ ရွေးချယ်အသုံးပြုပါ။

## Supply-chain စကင်နာ တွေ့ရှိချက်များ (Socket.dev / Snyk / အလားတူ)

> **စစ်ဆေးမှုနယ်ပယ် မှတ်ချက်:** Repository root ရှိ `socket.yml` သည် ထုတ်ဝေထားသော npm artifact ကို Socket.dev ၏ registry ဘက်မှ ထုတ်ဝေပြီးနောက် စကင်ဖတ်ရာတွင် `projectIgnorePaths` ကိုသာ သတ်မှတ်ပေးသည် — ၎င်းသည် မဖြစ်မနေလိုက်နာရသော CI/PR merge gate မဟုတ်ပါ။ `.github/workflows` ရှိ မည်သည့် workflow ကမျှ၊ `package.json` script ကမျှ၊ `Makefile` target ကမျှ Socket.dev ကို ခေါ်ယူအသုံးမပြုပါ။

ထုတ်ဝေထားသော `omniroute` npm artifact တွင် Next.js `output: "standalone"`
build ကို ထည့်သွင်းထားသည်။ ဆိုလိုသည်မှာ မှတ်တမ်းပြုထားသော အထူးအခွင့်အရေးလိုအပ်သည့်
လုပ်ဆောင်ချက်များ (MITM၊ Zed import၊ Cloud Sync၊ ထည့်သွင်းပါဝင်သော service supervisor) အပါအဝင်
route handler တိုင်းသည် `.next/server/*.js` minified chunk များထဲသို့
ရောက်ရှိသွားသည်။ Heuristic supply-chain စကင်နာများသည် အဆိုပါ chunk များကို
malware signature များနှင့် မကြာခဏ pattern-match လုပ်ကြသည်။

ကျွန်ုပ်တို့အသုံးပြုသော စကင်နာ configuration သည် repo root ရှိ
[`socket.yml`](socket.yml) တွင် ရှိသည် (Socket.dev GitHub App format v2 —
<https://docs.socket.dev/docs/socket-yml> ကို ကြည့်ပါ)။ ၎င်းသည် ဖြန့်ချိထားခြင်းမရှိသော
directory များ (`tests/`, `_tasks/`, `_references/`, `_ideia/`,
`_mono_repo/`, `docs/` စသည်တို့) ကို ရှင်းလင်းစွာ ဖယ်ထုတ်ထားသဖြင့် စကင်နာသည်
ထုတ်ဝေထားသော package ကို အသုံးပြုသူများထံ အမှန်တကယ်ရောက်ရှိသည့် code path များကိုသာ
