## Hoàn thành hội thoại

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Viết một hàm để..."}
  ],
  "stream": true
}
```

### Header tùy chỉnh

| Header                   | Hướng    | Mô tả                                                                                                                                                                                                                            |
| ------------------------ | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Yêu cầu  | Đặt thành `true` để bỏ qua bộ nhớ đệm                                                                                                                                                                                            |
| `x-omniroute-no-memory`  | Yêu cầu  | Đặt thành `true` để bỏ qua việc chèn bộ nhớ + kỹ năng cho yêu cầu này (tương tự no-cache; tránh chi phí token/chi phí trên mỗi lần gọi)                                                                                          |
| `X-OmniRoute-Progress`   | Yêu cầu  | Đặt thành `true` để nhận các sự kiện tiến trình                                                                                                                                                                                  |
| `X-Session-Id`           | Yêu cầu  | Khóa phiên cố định dành cho cơ chế liên kết phiên bên ngoài                                                                                                                                                                      |
| `x_session_id`           | Yêu cầu  | Biến thể có dấu gạch dưới cũng được chấp nhận (HTTP trực tiếp)                                                                                                                                                                   |
| `X-OmniRoute-Session-Id` | Yêu cầu  | Thẻ phiên/cuộc hội thoại do bên gọi cung cấp (cũng được đưa vào bộ nhớ). Khi có mặt, giá trị được lưu nguyên văn vào `call_logs.session_tag` để phân bổ chi phí theo từng phiên (#8249) — không bao giờ được tự tạo khi vắng mặt |
| `Idempotency-Key`        | Yêu cầu  | Khóa khử trùng lặp (cửa sổ 5 giây)                                                                                                                                                                                               |
| `X-Request-Id`           | Yêu cầu  | Khóa khử trùng lặp thay thế                                                                                                                                                                                                      |
| `X-OmniRoute-Cache`      | Phản hồi | `HIT` hoặc `MISS` (không truyền phát)                                                                                                                                                                                            |
| `X-OmniRoute-Idempotent` | Phản hồi | `true` nếu đã được khử trùng lặp                                                                                                                                                                                                 |
| `X-OmniRoute-Progress`   | Phản hồi | `enabled` nếu tính năng theo dõi tiến trình đang bật                                                                                                                                                                             |
| `X-OmniRoute-Session-Id` | Phản hồi | ID phiên thực tế được OmniRoute sử dụng                                                                                                                                                                                          |
| `X-OmniRoute-Request-Id` | Phản hồi | ID tương quan của yêu cầu (khi xác định được)                                                                                                                                                                                    |
| `X-OmniRoute-Version`    | Phản hồi | Phiên bản bản dựng OmniRoute (luôn hiện diện)                                                                                                                                                                                    |
| `X-OmniRoute-Cost-Saved` | Phản hồi | Số USD mà bộ nhớ đệm giúp tiết kiệm khi `HIT` (chỉ áp dụng cho lượt truy cập bộ nhớ đệm)                                                                                                                                         |
| `X-OmniRoute-Decision`   | Phản hồi | Dấu vết định tuyến: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` là chiến lược combo hoặc `single` đối với yêu cầu không phải combo) — luôn hiện diện trong các phản hồi hoàn tất                               |

> Lưu ý về Nginx: nếu bạn sử dụng các header có dấu gạch dưới (ví dụ: `x_session_id`), hãy bật `underscores_in_headers on;`.

> **Các header đo lường chi phí:** các phản hồi thành công không phát trực tuyến cũng chứa bộ thông tin đo lường chi phí `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, cố định 10 chữ số thập phân; `0.0000000000` nếu miễn phí/chưa định giá), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` và `X-OmniRoute-Fallback-Attempts` (chỉ khi > 0), cùng với `X-OmniRoute-Request-Id` và `X-OmniRoute-Version`. Các header này được trả về bởi các API hoàn thành trò chuyện, `/v1/responses`, `/v1/messages`, **cũng như các endpoint đa phương tiện** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` và `/v1/moderations` (chi phí luôn là `0`). Chi phí đa phương tiện được tính theo từng phương thức (theo hình ảnh, theo giây, theo ký tự, theo đơn vị tìm kiếm) khi có thông tin định giá; nếu không, chi phí là `0` (fail-open).

> **Ngữ nghĩa chi phí khi truy cập bộ nhớ đệm:** khi HIT bộ nhớ đệm ngữ nghĩa (`X-OmniRoute-Cache-Hit: true`), không có lệnh gọi nào được gửi đến dịch vụ thượng nguồn, vì vậy `X-OmniRoute-Response-Cost` là `0.0000000000` (chi phí **gia tăng** để phục vụ lần truy cập này). Chi phí ban đầu/lẽ ra đã phát sinh được báo cáo riêng trong `X-OmniRoute-Cost-Saved`. Các hệ thống xử lý thanh toán nên cộng tổng `X-OmniRoute-Response-Cost` (các lần truy cập bộ nhớ đệm không phát sinh chi phí); hệ thống phân tích bộ nhớ đệm có thể tổng hợp `X-OmniRoute-Cost-Saved`.

## Lease phiên được quản lý độc quyền

Lease phiên được quản lý độc quyền là một hợp đồng định tuyến tùy chọn, trung lập với client: một chủ sở hữu đang hoạt động nắm giữ một kết nối OmniRoute đủ điều kiện. Cơ chế này không lease một mô hình, không yêu cầu OAuth, không xác định một client cụ thể và cũng không yêu cầu một nhà cung cấp cụ thể.

Khóa API dùng để xác thực phải có phạm vi `lease:exclusive` và danh sách `allowedConnections` tường minh, không rỗng. Ranh giới đột biến cơ sở dữ liệu thực thi đồng thời cả hai trường khi tạo khóa và cập nhật một phần.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Các phản hồi acquire, renew và release thành công cung cấp dấu thời gian, `state` và giá trị `generation` dương chính xác, nhưng không bao giờ cung cấp kết nối đã chọn hoặc thông tin xác thực. Renew và release cung cấp generation trong phần thân JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Chủ sở hữu lease đang hoạt động có thể yêu cầu rõ ràng metadata hiển thị an toàn về quyền riêng tư cho liên kết hiện tại của mình:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Hành động status tùy chọn này được rào chắn bằng chủ sở hữu không trong suốt, khóa API được quản lý đã xác thực và generation đang hoạt động chính xác trong một giao dịch cơ sở dữ liệu duy nhất. `displayName` chỉ là tên kết nối đã cấu hình được cắt bỏ khoảng trắng; giá trị này là `null` khi không tồn tại tên cấu hình an toàn. OmniRoute không bao giờ thay thế bằng email hoặc danh tính tài khoản được tạo. Giá trị nhà cung cấp là một nhãn hiển thị không nhạy cảm và không bao giờ là mã định danh nhà cung cấp tương thích được tạo. Thông tin xác thực, token, cookie, id kết nối hoặc khóa API thô, hàm băm chủ sở hữu, bí mật rào chắn và dữ liệu định tuyến nội bộ đều bị loại trừ.

Các truy vấn sử dụng sai khóa, sai chủ sở hữu, generation cũ, bị thiếu, hết hạn, đã phát hành hoặc bị vô hiệu hóa đều trả về cùng một lỗi `409 LEASE_FENCE_STALE` mà không có metadata kết nối. Client đã nhận phản hồi chờ dung lượng không có liên kết đang hoạt động để kiểm tra. Khi định tuyến chuyển đổi một lease đang hoạt động, cùng một generation vẫn hợp lệ và status trả về liên kết mới một cách nguyên tử, không bao giờ trả về liên kết cũ. Các client hiện có không thay đổi vì phản hồi acquire, renew, release và chờ vẫn giữ nguyên cấu trúc trước đó.

Hợp đồng máy chủ này không thay đổi `/status` của OpenAI Codex nguyên bản. Codex nguyên bản hiện báo cáo nhà cung cấp mô hình và trạng thái xác thực/tài khoản tích hợp sẵn, nhưng không hiển thị metadata tài khoản tùy ý của nhà cung cấp tùy chỉnh; một tích hợp client sau này phải gọi hành động này và quyết định cách hiển thị `connection.displayName`.

Sau đó, mỗi yêu cầu suy luận được quản lý đều cung cấp cả hai header điều khiển:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Chủ sở hữu chính xác, generation, kết nối đang hoạt động và khóa API đã xác thực được rào chắn ngay trước mỗi lần thử upstream được hỗ trợ. Việc phát lại chủ sở hữu và generation bằng một khóa khác sẽ thất bại ngay cả khi khóa đó cho phép cùng một kết nối. Chủ sở hữu thô không được lưu trữ lâu dài, ghi nhật ký, giữ lại trong snapshot yêu cầu hoặc chuyển tiếp upstream.

Tranh chấp tạm thời trả về HTTP `429` cùng với `Retry-After` và:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Phản hồi này chỉ có nghĩa là tập hợp đủ điều kiện thông thường không rỗng và mọi ứng viên đang rảnh đều do một lease ngoại lai đang hoạt động nắm giữ. Các mô hình/nhà cung cấp không được hỗ trợ, chính sách không khớp, thời gian chờ, hạn ngạch, tình trạng hoạt động và các lỗi đủ điều kiện thông thường khác vẫn giữ nguyên phản hồi OmniRoute hiện có.

### `x-omniroute-compression`

Ghi đè kế hoạch nén theo từng yêu cầu. Có mức ưu tiên cao nhất — cao hơn ghi đè tổ hợp định tuyến, hồ sơ đang hoạt động, trình kích hoạt tự động và giá trị Mặc định của bảng điều khiển. Các giá trị:

| Giá trị       | Hiệu ứng                                                                                              |
| ------------- | ----------------------------------------------------------------------------------------------------- |
| `off`         | Không nén yêu cầu này.                                                                                |
| `default`     | Hồ sơ Mặc định lấy từ bảng điều khiển (bỏ qua hồ sơ đang hoạt động).                                  |
| `engine:<id>` | Một engine duy nhất khi được bật, ví dụ: `engine:rtk`.                                                |
| `<combo>`     | Một combo có tên, trước tiên được khớp theo tên (không phân biệt chữ hoa chữ thường), sau đó theo id. |

Lưu ý:

- Các giá trị không xác định sẽ bị bỏ qua (yêu cầu không bao giờ bị từ chối); quá trình phân giải sẽ chuyển sang thứ tự ưu tiên toán tử thông thường.
- Nếu nhiều combo có cùng tên, hãy truyền **id** của combo để có kết quả khớp xác định.
- Không thể chọn theo tên một combo có tên là `off` hoặc `default` (các từ khóa này được diễn giải trước); hãy tham chiếu combo đó bằng id.
- Công tắc nén chính là một cổng cứng: khi tính năng nén bị vô hiệu hóa trên toàn hệ thống, header này không thể bật tính năng đó.

Kế hoạch được áp dụng sẽ được phản hồi lại trong header phản hồi:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

trong đó `<source>` là một trong các giá trị `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` hoặc `off`.

## Embedding

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Các nhà cung cấp khả dụng: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

ID danh mục có dạng `provider/model` (ví dụ: `jina-ai/jina-embeddings-v5-omni-small`). Các ID mô hình Jina không kèm tên nhà cung cấp xuất hiện trong registry (ví dụ: `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) cũng được phân giải. Các thao tác embed/rerank/classify/segment của Jina ưu tiên sử dụng thông tin xác thực `jina-ai` trên dashboard; `JINA_AI_API_KEY` chỉ được dùng làm phương án dự phòng khi không có khóa trên dashboard. Thẻ `jina-reader` chỉ dành cho Reader / `r.jina.ai` (`POST /v1/web/fetch`) và không bao giờ phục vụ embedding hoặc rerank.

Các mô hình trong registry công bố hỗ trợ đa phương thức cũng chấp nhận tối đa 32 mục có cấu trúc, trung lập với nhà cung cấp.
Các loại mục phương tiện gồm `text`, `image`, `audio`, `video` và `document`. `source` của phương tiện
có thể là `{"type":"url","url":"https://..."}` hoặc
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
và bí danh họ mô hình `jina-ai/jina-embeddings-v5-omni` → omni-small) cũng chấp nhận các tài liệu EmbeddingsV5Request gốc của Jina
và **chuyển tiếp nguyên vẹn** chúng đến `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    {
      "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }]
    }
  ]
}
```

Các giá trị `{ image | audio | video | pdf }` gốc có thể là URL HTTPS công khai, URI `data:` hoặc dữ liệu
base64 thô. OmniRoute không chuyển các đối tượng đó thành chuỗi hoặc tải các URL hình ảnh gốc — Jina tự truy xuất
phương tiện công khai. Các trường Jina bổ sung (`task`, `normalized`, `truncate`, `embedding_type`) được
chuyển tiếp. Các SKU Jina chỉ hỗ trợ văn bản vẫn từ chối tài liệu không phải văn bản.

Giới hạn bảo mật và truyền tải:

- URL phương tiện từ xa phải là HTTPS công khai. Các mục chuẩn hóa `{type,source:url}` được tải
  ở phía máy chủ (xác thực lại chuyển hướng, thời gian chờ, giới hạn kích thước, DNS công khai, ghim kết nối) và
  được nhúng trực tiếp trước khi gọi nhà cung cấp. Các mục gốc của Jina `{image:"https://..."}` được chuyển tiếp nguyên trạng
  sau cùng bước kiểm tra HTTPS công khai; Jina sẽ tải URL.
- Phương tiện base64 nội tuyến được giới hạn ở 8 MiB dữ liệu đã giải mã cho mỗi mục và 16 MiB dữ liệu đã giải mã cho toàn bộ yêu cầu.

Chuyển đổi theo nhà cung cấp (các mục chuẩn hóa không bao giờ được chuyển tiếp nguyên trạng):

- Các mô hình đa phương thức của Jina: mỗi mục cấp cao nhất trở thành một đối tượng có khóa theo phương thức
  (`text` / `image` / `audio` / `video` / `pdf`), sử dụng URI dữ liệu cho phương tiện nội tuyến; mỗi
  mục cấp cao nhất tương ứng với một vector.
- Họ Gemini Embedding 2: một mảng cấp cao nhất trở thành một yêu cầu gốc duy nhất
  `models/{model}:embedContent` với `content.parts` (`text` hoặc `inline_data`).
- Các mô hình không xác định/động không có siêu dữ liệu phương thức rõ ràng sẽ từ chối đầu vào có cấu trúc với HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Các tổ hợp mô hình/phương thức không được hỗ trợ sẽ trả về HTTP 400 thay vì ép kiểu mục đó. Các trường mở rộng không thuộc đầu vào
trên những yêu cầu chuỗi/token cũ tiếp tục được truyền nguyên trạng.

```bash
# Liệt kê tất cả các mô hình embedding
GET /v1/embeddings
```

## OCR tài liệu

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` chọn nhà cung cấp OCR thông qua tiền tố `provider/model`; một id mô hình đơn lẻ (ví dụ:
`mistral-ocr-latest`) được phân giải thành nhà cung cấp đã đăng ký tương ứng, còn nếu bỏ qua `model` thì mặc định là
Mistral (`mistral-ocr-latest`). Các nhà cung cấp đã đăng ký (`open-sse/config/ocrRegistry.ts`):

| Id nhà cung cấp               | Id mô hình           | Giá trị `model`                                                      | Ghi chú                                                                                                |
| ----------------------------- | -------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (hoặc dạng đơn lẻ `mistral-ocr-latest`) | Đồng bộ — phản hồi được trả về trực tiếp từ một lệnh gọi upstream duy nhất.                            |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                          | Upstream bất đồng bộ (`analyze` + thăm dò) — xem bên dưới.                                             |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                              | Đồng bộ, qua endpoint đối tác `openapi/chat/completions` của Vertex AI — xem bên dưới về xác thực/URL. |

Cả ba nhà cung cấp đều phản hồi bằng phần thân có cùng định dạng như Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Văn bản đã trích xuất..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Luồng thăm dò của Azure Document Intelligence

API `analyze` của Azure Document Intelligence hoạt động bất đồng bộ: yêu cầu ban đầu trả về header
`Operation-Location` thay vì phần thân, và kết quả phải được thăm dò. Trình xử lý
(`open-sse/handlers/ocr.ts`) thăm dò URL đó mỗi giây, tối đa 30 lần; dừng và báo lỗi ngay (không
tiếp tục thăm dò) khi phản hồi thăm dò không phải `ok` hoặc có trạng thái `"failed"`, đồng thời trả về `504` nếu
thao tác vẫn đang chạy sau khi đã sử dụng hết số lần thử. Phản hồi cuối cùng của Azure được
chuẩn hóa thành cùng cấu trúc `pages`/`markdown` mà Mistral sử dụng trước khi được trả về cho
bên gọi, vì vậy mã phía máy khách không cần xử lý riêng theo từng nhà cung cấp.

### Xác thực và phân giải endpoint OCR DeepSeek của Vertex AI

`vertex-deepseek-ocr` tái sử dụng cùng cơ chế xác thực Vertex AI mà OmniRoute đã hỗ trợ cho
lưu lượng trò chuyện/hình ảnh (`open-sse/executors/vertex.ts`): khóa API của kết nối là thông tin xác thực
Service Account JSON (được trao đổi lấy token truy cập OAuth ngắn hạn thông qua luồng JWT-bearer)
hoặc một token truy cập OAuth đã được cấp sẵn và được sử dụng nguyên trạng. URL endpoint upstream là endpoint
đối tác `openapi/chat/completions` dùng chung của Vertex, được tạo từ dự án và
khu vực của kết nối — `providerSpecificData.project`/`providerSpecificData.region` được chỉ định rõ ràng luôn được ưu tiên;
nếu không, dự án được lấy từ `project_id` trong Service Account JSON và khu vực
mặc định là `us-central1`. Cả hai quá trình phân giải đều diễn ra trong `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`), được
`src/app/api/v1/ocr/route.ts` sử dụng trước khi chuyển tiếp đến `handleOcr`.

## Liệt kê mô hình

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Trả về tất cả mô hình trò chuyện, embedding và hình ảnh cùng các tổ hợp theo định dạng OpenAI
```

### Tiền tố id mô hình (`?prefix=`)

Hầu hết các mô hình được công bố dưới một **tiền tố nhà cung cấp**. Tiền tố bạn nhận được chịu sự kiểm soát của cờ tính năng `MODELS_CATALOG_PREFIX_MODE` và có thể được ghi đè **cho từng yêu cầu** bằng một tham số truy vấn — hữu ích cho ứng dụng khách muốn có một danh sách gọn gàng mà không thay đổi thiết lập trên toàn máy chủ cho những người khác:

```bash
GET /v1/models?prefix=alias        # một id cho mỗi mô hình — tiền tố bí danh ngắn
GET /v1/models?prefix=dual         # cả hai dạng (mặc định của máy chủ)
GET /v1/models?prefix=canonical    # chỉ tiền tố id đầy đủ của nhà cung cấp
```

| Chế độ      | Xuất ra                                                  | Ghi chú                                                                                                                                                                                                  |
| ----------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **và** `claude/claude-sonnet-4-6` | **Mặc định.** Cả hai id đều định tuyến đến cùng một mô hình; được duy trì để các cấu hình ứng dụng khách đã mã hóa cứng một trong hai dạng tiếp tục hoạt động. Kích thước danh mục gần như tăng gấp đôi. |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Một mục cho mỗi mô hình. Các nhà cung cấp không có bí danh riêng vẫn xuất mục của họ, nên không có gì bị mất.                                                                                            |
| `canonical` | `claude/claude-sonnet-4-6`                               | Một mục cho mỗi mô hình dưới tiền tố id đầy đủ của nhà cung cấp. Các nhà cung cấp không có bí danh riêng (ví dụ: `antigravity/…`, `agy/…`) cũng xuất id duy nhất của họ ở đây, nên không có gì bị mất.   |

Một bản sao ở chế độ `dual` cũng có thể được nhận diện mà không cần tham số truy vấn: nó chứa trường `parent` trỏ đến id chính.

Các ứng dụng khách hiển thị bộ chọn mô hình nên yêu cầu `?prefix=alias` — đây là cách [tiện ích mở rộng OmniCopilot cho VS Code](../guides/VSCODE-COPILOT.md) hoạt động.

### Các biến thể mô hình không suy luận

Đối với các mô hình Claude có khả năng suy luận, `/v1/models` cũng công bố một biến thể **không suy luận** có id được thêm tiền tố `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Việc chọn id này (ví dụ: trong cấu hình Claude Code luôn đính kèm khối `thinking`) sẽ phân giải trở lại `<provider>/<model>` thực với khả năng suy luận bị vô hiệu hóa — `thinking:{type:"disabled"}` trên đường dẫn `/v1/messages`, hoặc loại bỏ các trường `reasoning`/`reasoning_effort` trên đường dẫn `/v1/chat/completions`. Biến thể này chỉ được liệt kê cho các mô hình thuộc họ Claude có hỗ trợ suy luận **và** chấp nhận `disabled` (do đó, ví dụ: các mô hình chỉ thích ứng nhưng từ chối `disabled` sẽ bị loại trừ). Người vận hành có thể buộc bật hoặc tắt biến thể này cho từng mô hình thông qua `ModelSpec.noThinkingAlias`.

Trả về manifest plugin nhà cung cấp an toàn cho JSON, được Bifrost, CLIProxyAPI và
các bộ định tuyến sidecar trong tương lai sử dụng. Phản hồi được tạo từ registry
nhà cung cấp TypeScript và chủ ý loại trừ các bí mật OAuth client, quá trình phân
giải môi trường runtime, các hàm thực thi, header yêu cầu và dữ liệu tài khoản.

Sử dụng endpoint này khi một sidecar chạy ngoài tiến trình và không thể nhập trực tiếp
`open-sse/config/providerPluginManifestRegistry.ts`.

## API Tải nội dung Web

Trích xuất nội dung từ một URL thông qua nhà cung cấp tải nội dung web đã cấu hình (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract).

| Phương thức | Đường dẫn       | Mô tả                                                                        |
| ----------- | --------------- | ---------------------------------------------------------------------------- |
| POST        | `/v1/web/fetch` | Tải/thu thập dữ liệu từ URL — phần thân được xác thực bởi `v1WebFetchSchema` |

**Xác thực:** Khóa API Bearer (`extractApiKey` + `isValidApiKey`). Chính sách được thực thi qua `enforceApiKeyPolicy`.

**Chuyển đổi dự phòng có xét hạn ngạch (#8297):** khi không chỉ định `provider` rõ ràng, nhóm
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search`) được
duyệt theo thứ tự ưu tiên cố định
(ưu tiên lấp đầy) — một nhà cung cấp đã cấu hình nhưng bị giới hạn tốc độ sẽ được bỏ qua
thay vì chấm dứt sớm yêu cầu, và một lỗi phía thượng nguồn có thể thử lại/liên quan đến hạn ngạch
(HTTP 429 trong mọi trường hợp; 402/403 đối với các gói miễn phí kiểu hạn ngạch của Firecrawl/Tavily/TinyFish —
không áp dụng cho Jina Reader và không bao giờ áp dụng cho yêu cầu không hợp lệ 400 thông thường) sẽ chuyển sang
nhà cung cấp tiếp theo có thông tin xác thực và chưa được thử tại thời điểm xử lý yêu cầu. Khi mọi nhà cung cấp trong
nhóm đều đã cạn, endpoint trả về một mã `429` duy nhất (kèm header `Retry-After`)
thay cho mã `400` chung trước đây. Khi yêu cầu một `provider` rõ ràng,
sẽ **không** có chuyển đổi dự phòng ngầm — nhà cung cấp được chỉ định rõ ràng nếu bị giới hạn tốc độ hoặc gặp lỗi
sẽ trả về lỗi của chính nó (`429` nếu bị giới hạn tốc độ, nếu không thì là trạng thái
từ phía thượng nguồn).

## Truyền trực tuyến qua WebSocket

```bash
GET /v1/ws?handshake=1
```

Xác thực quá trình bắt tay nâng cấp WebSocket và trả về các thông điệp mẫu của giao thức truyền (`request`, `cancel`). Các frame WS thực tế được xử lý bởi máy chủ WS đi kèm bên ngoài bảng định tuyến Next.js.

**Xác thực:** Khóa API Bearer trong quá trình bắt tay.

### Responses API qua WebSocket (chỉ codex)

```bash
# Cùng host:port với API HTTP (mặc định là 20128); nâng cấp kết nối:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (hoặc: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Frame đầu tiên PHẢI là response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Một proxy Responses-API-over-WebSocket được kết nối **độc quyền với `codex`** (backend
ChatGPT). Proxy này lắng nghe trên cùng cổng với API/bảng điều khiển tại các đường dẫn `/v1/responses`,
`/responses` và `/api/v1/responses`. Khi nhận frame `response.create` đầu tiên, proxy
xác thực + chuẩn bị thông qua cầu nối nội bộ `codex-responses-ws`, chọn một
kết nối OAuth codex và tạo đường hầm tới `wss://chatgpt.com/backend-api/codex/responses`
thông qua phương thức truyền tải `wreq-js`. **Các mô hình không phải codex sẽ bị từ chối** (`codex_ws_provider_required`).
Để định tuyến theo tỷ lệ hạn ngạch, hãy dùng `model: "qtSd/<group>/codex/<model>"`. Được triển khai trong
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Xác thực:** Khóa API Bearer trong quá trình bắt tay. Máy chủ HTTP đi kèm (`server-ws.mjs`)
phải là entrypoint đang hoạt động (mặc định là như vậy khi `app/server-ws.mjs` tồn tại).

#### ID mô hình: dùng ID ChatGPT thuần (không có tiền tố `codex/`)

**Codex CLI** của OpenAI xác thực tên mô hình ở phía máy khách khi
`supports_websockets = true` và **từ chối các ID có tiền tố nhà cung cấp** như
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Hãy gửi ID **thuần** (ví dụ: `gpt-5.5`). Cầu nối của OmniRoute
chỉ dành cho codex, vì vậy nó phân giải lại một ID thuần thành mô hình codex
(`resolveCodexWsModelInfo`) trước khi tạo đường hầm đến phía thượng nguồn — mặc dù một ID thuần
`gpt-5.5` nếu không sẽ được định tuyến đến nhà cung cấp khác qua HTTP.

#### Cấu hình OpenAI Codex CLI

Trỏ Codex CLI đến OmniRoute bằng cách thêm một nhà cung cấp tùy chỉnh có hỗ trợ WebSocket
vào `~/.codex/config.toml` (dùng một `CODEX_HOME` riêng để tránh tác động đến
cấu hình hiện có):

```toml
model = "gpt-5.5"                 # ID thuần — KHÔNG PHẢI "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # không có dấu gạch chéo ở cuối; URL WS được suy ra (dùng https/wss trong môi trường production)
wire_api = "responses"                    # giá trị duy nhất được hỗ trợ kể từ tháng 2 năm 2026
supports_websockets = true                # bật phương thức truyền Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # chứa khóa API OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # một khóa API OmniRoute (khóa bất kỳ nếu REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI nâng cấp `base_url + /responses` thành WebSocket và OmniRoute tạo đường hầm kết nối đó
tới kết nối OAuth codex đã chọn. Đã được xác thực đầu-cuối với máy chủ
cục bộ: ChatGPT trả về `codex.rate_limits` + `response.created` và truyền trực tuyến
phần hoàn thành.

## Sử dụng tự phục vụ (`/api/usage/om-usage`)

Bất kỳ khóa API nào cũng có thể đọc mức sử dụng và hạn mức **của chính nó** — không cần quyền xác thực quản lý. Đây là endpoint mà
client (CLI, bảng điều khiển OmniCopilot) sử dụng để hiển thị mức chi tiêu cho chủ sở hữu khóa.

```bash
# Dạng văn bản (giao ước truyền thống — văn bản thuần túy dành cho terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Dạng có cấu trúc — dạng mà UI sử dụng
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Khóa phải được bật **`allowUsageCommand`** (mặc định là tắt — trình quản lý khóa API trên bảng điều khiển
bật/tắt tùy chọn này cho từng khóa). Nếu không, endpoint sẽ trả về `403`.

`?format=json` trả về một cấu trúc phân biệt để trình gọi không bao giờ đọc trường dữ liệu từ một
phản hồi từ chối. Khi thành công:

```jsonc
{
  "allowed": true,
  // chỉ xuất hiện khi khóa chọn sử dụng giới hạn mức dùng theo từng khóa (USD hằng ngày/hằng tuần):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // ảnh chụp hạn mức của nhà cung cấp đã chọn, hoặc null khi chưa có gì được lưu vào bộ nhớ đệm:
  "provider": {
    "connectionId": "…",
    "provider": "claude",
    "plan": "…",
    "quotas": {/* … */},
  },
  // ảnh chụp của mọi kết nối để UI có thể hiển thị nhiều nhà cung cấp cạnh nhau:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Khi bị từ chối (`401` khóa không hợp lệ / `403` không được phép), cùng route đó trả về
`{ "allowed": false, "error": { "message": "…" } }` — `personal`/`provider` có mặt nhưng trống
(khóa được cho phép, nhưng chưa thu thập được dữ liệu) là trạng thái khác với bị từ chối, và chỉ dạng JSON
mới phân biệt được chúng.

**Xác thực:** Khóa API Bearer của chính trình gọi, được xác thực bằng `isValidApiKey` — đây _không phải_ là
bề mặt quản lý (`/api/keys/…`), vốn vẫn được bảo vệ bởi `requireManagementAuth`.

### Ảnh hưởng đến độ trễ

Một HIT của bộ nhớ đệm ngữ nghĩa phục vụ phản hồi từ bộ nhớ đệm **mà không thực hiện lệnh gọi ngược dòng**,
do đó `X-OmniRoute-Response-Latency` được báo cáo gần bằng không
(bất kể độ trễ ngược dòng ban đầu). Các client nhạy cảm với độ trễ
(đo điểm chuẩn, giám sát p50/p99) nên kiểm tra header phản hồi
`X-OmniRoute-Cache-Latency`:

| Giá trị      | Ý nghĩa                                                                             |
| ------------ | ----------------------------------------------------------------------------------- |
| `synthetic`  | Phản hồi được phục vụ từ bộ nhớ đệm; độ trễ không phải thời gian ngược dòng thực tế |
| _(không có)_ | Phản hồi từ lệnh gọi ngược dòng thực tế                                             |

### Bỏ qua bộ nhớ đệm theo từng khóa

Các khóa API có thể không sử dụng thao tác đọc bộ nhớ đệm ngữ nghĩa thông qua `cacheDefaultMode`:

| Giá trị  | Hành vi                                                       |
| -------- | ------------------------------------------------------------- |
| `legacy` | Hành vi bộ nhớ đệm thông thường (mặc định)                    |
| `bypass` | Bỏ qua hoàn toàn việc tra cứu bộ nhớ đệm; luôn gọi ngược dòng |

Thiết lập khi tạo khóa (`POST /api/keys`) hoặc cập nhật (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Bỏ qua theo từng yêu cầu

Bất kỳ yêu cầu nào cũng có thể bỏ qua bộ nhớ đệm bất kể cài đặt của khóa:

```
X-OmniRoute-No-Cache: true
```

## Phiên âm thanh

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Phiên âm các tệp âm thanh bằng bất kỳ nhà cung cấp STT nào đã được cấu hình. Phân đoạn đầu tiên của đường dẫn chọn nhà cung cấp gốc (`openai/…`, `deepgram/…`). Các cổng kết nối cung cấp lại mô hình của nhà cung cấp khác sử dụng id đầy đủ
(`openrouter/deepgram/nova-3`).

**Yêu cầu:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Phản hồi:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Ví dụ về id mô hình:** `openai/whisper-1` (yêu cầu khóa OpenAI),
`openrouter/deepgram/nova-3` (yêu cầu khóa OpenRouter),

## Bí danh được mã hóa bằng token cho VS Code / Không cần header

Sử dụng các bí danh này khi một tích hợp không thể chèn header `Authorization` và cần nhúng khóa API vào URL cơ sở.

```bash
# Bí danh danh mục theo kiểu OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Bí danh trò chuyện theo kiểu OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Bí danh theo kiểu Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Ví dụ:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Lưu ý:

- Các bí danh được mã hóa bằng token tái sử dụng cùng các trình xử lý như `/v1/*` và `/api/tags`; cấu trúc phản hồi vẫn giữ nguyên.
- Ưu tiên sử dụng `Authorization: Bearer ...` bất cứ khi nào client hỗ trợ header tùy chỉnh.
- Token dựa trên URL có thể xuất hiện trong nhật ký reverse proxy, lịch sử trình duyệt và dữ liệu đo từ xa bên ngoài OmniRoute. Hãy coi chúng là một tùy chọn tương thích, không phải chế độ xác thực mặc định.

## Giới hạn token

Ngân sách **token** theo từng khóa API (khác với Ngân sách dựa trên USD ở trên). Được thực thi trực tiếp trên luồng xử lý yêu cầu: khi mức sử dụng trong cửa sổ hiện tại của một khóa đạt đến giới hạn, các yêu cầu sẽ bị từ chối với `429 Too Many Requests`. Các giới hạn có thể được áp dụng cho một `model`, một `provider` cụ thể hoặc áp dụng `global` trên toàn bộ khóa; khi có nhiều giới hạn khớp với một yêu cầu, giới hạn nghiêm ngặt nhất sẽ được áp dụng.

```bash
# Liệt kê các giới hạn token của một khóa (bao gồm mức sử dụng trực tiếp trong cửa sổ)
GET /api/usage/token-limits?apiKeyId=key-123

# Tạo hoặc cập nhật một giới hạn token
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Xóa một giới hạn token theo id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Ghi chú về schema** (`setTokenLimitSchema`): `apiKeyId` và `scopeType` (`model` | `provider` | `global`) là bắt buộc. `scopeValue` là bắt buộc trừ khi `scopeType` là `global` (ví dụ: id mô hình cho phạm vi `model`, id nhà cung cấp cho phạm vi `provider`). `tokenLimit` phải là một số nguyên dương (được ép kiểu từ chuỗi). Tùy chọn: `id` (bỏ qua để tạo mới, cung cấp để cập nhật), `resetInterval` (`daily` | `weekly` | `monthly`, mặc định là `monthly`), `resetTime` (`HH:MM`), `enabled` (mặc định là `true`). Phản hồi `GET` bổ sung cho mỗi giới hạn các trường `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` và `nextResetAt`. Đây là endpoint thuộc lớp quản lý (việc xác thực được thực thi tập trung bởi quy trình authz).

## Xử lý yêu cầu

1. Máy khách gửi yêu cầu đến `/v1/*`
2. Trình xử lý tuyến gọi `handleChat`, `handleEmbedding`, `handleAudioTranscription` hoặc `handleImageGeneration`
3. Mô hình được phân giải (nhà cung cấp/mô hình trực tiếp hoặc bí danh/combo)
4. Thông tin xác thực được chọn từ cơ sở dữ liệu cục bộ, có lọc theo tính khả dụng của tài khoản
5. Đối với chat: `handleChatCore` kiểm tra bộ nhớ đệm ngữ nghĩa/chữ ký và phân giải các cài đặt nén của combo
6. Tính năng nén chủ động chạy trước bước chuyển đổi cho nhà cung cấp khi được bật (`lite`, Caveman, RTK hoặc kết hợp nhiều lớp)
7. Bộ thực thi của nhà cung cấp gửi yêu cầu ngược dòng
8. Phản hồi được chuyển đổi trở lại định dạng của máy khách (chat) hoặc được trả về nguyên trạng (embeddings/hình ảnh/âm thanh)
9. Mức sử dụng, dữ liệu phân tích về nén và nhật ký yêu cầu được ghi lại
10. Cơ chế dự phòng được áp dụng khi xảy ra lỗi theo các quy tắc của combo

Tài liệu tham khảo kiến trúc đầy đủ: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Proxy quản lý

Các proxy HTTP(S)/SOCKS đi ra có thể được gán cho nhà cung cấp, tài khoản hoặc trên toàn cục.

| Phương thức | Đường dẫn                                    | Mô tả                                                                                                                                                          |
| ----------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET         | `/api/v1/management/proxies`                 | Liệt kê proxy (với `?id=` trả về một proxy; với `?id=&where_used=1` trả về biểu đồ phân công)                                                                  |
| POST        | `/api/v1/management/proxies`                 | Tạo proxy — phần thân được xác thực bằng `createProxyRegistrySchema`                                                                                           |
| PATCH       | `/api/v1/management/proxies`                 | Cập nhật proxy — phần thân được xác thực bằng `updateProxyRegistrySchema` (yêu cầu `id`)                                                                       |
| DELETE      | `/api/v1/management/proxies?id=...&force=1`  | Xóa proxy (dùng `force=1` để gỡ các phân công)                                                                                                                 |
| GET         | `/api/v1/management/proxies/assignments`     | Liệt kê các phân công — có thể lọc theo `proxy_id`, `scope`, `scope_id`; truyền `resolve_connection_id=<id>` để phân giải proxy đang hoạt động cho một kết nối |
| PUT         | `/api/v1/management/proxies/assignments`     | Gán — phần thân được xác thực bằng `proxyAssignmentSchema` (`{scope, scopeId?, proxyId?}`). Xóa bộ nhớ đệm của bộ điều phối                                    |

| GET         | `/api/v1/management/proxies/health?hours=24` | Tổng hợp tình trạng proxy (số lần thành công/thất bại, độ trễ) trong một khoảng thời gian                                                                      |

## Khả năng phục hồi (mở rộng)

OmniRoute cung cấp ba cơ chế xử lý lỗi tạm thời độc lập; các endpoint quản lý bên dưới cho phép người vận hành xem và ghi đè chúng:

| Phạm vi                   | Nơi lưu trữ trạng thái                               | Xem                                       | Đặt lại / xóa                                          |
| ------------------------- | ---------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------ |
| Bộ ngắt mạch nhà cung cấp | `domain_circuit_breakers` + trong bộ nhớ             | `/api/monitoring/health`                  | `POST /api/resilience/reset`                           |
| Thời gian chờ kết nối     | `rateLimitedUntil` trên các kết nối của nhà cung cấp | `/api/rate-limits`, `/api/providers/[id]` | (được bật lại khi cần; xóa thông qua PUT nhà cung cấp) |
| Khóa mô hình              | Sổ đăng ký tính khả dụng của mô hình trong bộ nhớ    | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`               |

`PATCH /api/resilience` chấp nhận các giá trị ghi đè cho bộ ngắt mạch nhà cung cấp trong `providerBreaker.oauth` và `providerBreaker.apikey`. Mỗi hồ sơ hỗ trợ `degradationThreshold`, `failureThreshold` và `resetTimeoutMs`; các trường tương tự cũng có trong Bảng điều khiển → Cài đặt → Khả năng phục hồi.

```bash
# Xóa trạng thái khóa của một mô hình
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Xóa toàn bộ trạng thái khóa
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Tài liệu tham khảo khái niệm đầy đủ và các giá trị mặc định của bộ ngắt mạch: xem [`CLAUDE.md`](../../CLAUDE.md) → "Trạng thái thời gian chạy của khả năng phục hồi".

## Máy chủ MCP

OmniRoute đi kèm một máy chủ Model Context Protocol tích hợp sẵn với 3 phương thức truyền tải (stdio, SSE, streamable-http) và các công cụ có phạm vi. Các endpoint bảng điều khiển bên dưới đọc dữ liệu trạng thái/kiểm tra và làm proxy cho các phương thức truyền tải HTTP.

| Phương thức | Đường dẫn | Mô tả |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Nhịp tim, phương thức truyền tải, trạng thái trực tuyến, lần gọi gần nhất, công cụ hàng đầu, tỷ lệ thành công trong 24 giờ |
| GET | `/api/mcp/tools` | Danh sách các công cụ MCP với `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | Mở luồng SSE cho phương thức truyền tải SSE (trả về `503` nếu MCP bị vô hiệu hóa hoặc phương thức truyền tải không khớp) |
| POST | `/api/mcp/sse` | Gửi khung JSON-RPC qua phương thức truyền tải SSE |
| GET | `/api/mcp/stream` | Mở phía SSE của phương thức truyền tải Streamable HTTP (thông báo do máy chủ khởi tạo) |
| POST | `/api/mcp/stream` | Gửi khung JSON-RPC qua phương thức truyền tải Streamable HTTP |
| DELETE | `/api/mcp/stream` | Kết thúc một phiên Streamable HTTP |
| GET | `/api/mcp/audit` | Truy vấn nhật ký kiểm tra — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Số liệu thống kê kiểm tra tổng hợp (tổng số, tỷ lệ thành công, thời lượng trung bình, công cụ hàng đầu) |

**Xác thực:** các phương thức truyền tải `sse`/`stream` tuân theo cơ chế xác thực dành riêng cho MCP (khóa API Bearer có phạm vi `mcp`); các route `status`/`tools`/`audit*` có thể được đọc từ bảng điều khiển (không yêu cầu xác thực bổ sung ngoài khả năng truy cập máy chủ bảng điều khiển).

> Cả hai phương thức truyền tải HTTP đều được kiểm soát bởi `settings.mcpEnabled` và `settings.mcpTransport` — phương thức truyền tải không khớp sẽ trả về `400`, trạng thái MCP bị vô hiệu hóa sẽ trả về `503`.

## Máy chủ A2A

OmniRoute cung cấp một điểm cuối A2A (Agent-to-Agent) JSON-RPC 2.0 cùng với một lớp bọc REST dùng cho việc kiểm tra/bảng điều khiển.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # không bắt buộc trừ khi OMNIROUTE_API_KEY được thiết lập
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Định tuyến tác vụ lập trình này"}]
  }
}
```

Các phương thức được hỗ trợ (tất cả đều chịu sự kiểm soát của `settings.a2aEnabled`):

| Phương thức      | Mô tả                                                          |
| ---------------- | -------------------------------------------------------------- |
| `message/send`   | Thực thi kỹ năng đồng bộ; trả về `{task, artifacts, metadata}` |
| `message/stream` | Thực thi truyền luồng SSE cho cùng một tập hợp kỹ năng         |
| `tasks/get`      | Truy xuất một tác vụ theo `taskId`                             |
| `tasks/cancel`   | Hủy một tác vụ theo `taskId`                                   |

Các kỹ năng tích hợp sẵn: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Thẻ tác nhân

```bash
GET /.well-known/agent.json
```

Trả về thẻ tác nhân A2A công khai (tên, mô tả, khả năng, danh mục kỹ năng, cơ chế xác thực) — được lưu vào bộ nhớ đệm công khai trong 1 giờ. Không yêu cầu xác thực.

### Trình trợ giúp REST

| Phương thức | Đường dẫn                    | Mô tả                                                                                                               |
| ----------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET         | `/api/a2a/status`            | Trạng thái bật A2A + thống kê tác vụ + bản tóm tắt thẻ tác nhân đã lưu trong bộ nhớ đệm                             |
| GET         | `/api/a2a/tasks`             | Liệt kê tác vụ — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST        | `/api/a2a/tasks`             | (Chưa được triển khai dưới dạng trình trợ giúp REST — tạo qua JSON-RPC `message/send`)                              |
| GET         | `/api/a2a/tasks/[id]`        | Truy xuất một tác vụ                                                                                                |
| POST        | `/api/a2a/tasks/[id]/cancel` | Hủy một tác vụ                                                                                                      |

**Xác thực:** các trình trợ giúp REST chạy mà không cần xác thực quản trị (bảng điều khiển có thể đọc); tuyến JSON-RPC `/a2a` sử dụng Bearer `OMNIROUTE_API_KEY` nếu được cấu hình.

## Xác thực

Xem [Xác thực quản trị](../guides/MANAGEMENT-AUTH.md) để biết bốn nhóm thông tin xác thực (phiên dashboard, token CLI cục bộ, Access Token `oma_live_…`, API key có phạm vi quản trị) và điểm khác biệt giữa chúng với các khóa suy luận.

- Các route của dashboard (`/dashboard/*`) sử dụng cookie `auth_token`
- Đăng nhập sử dụng hàm băm mật khẩu đã lưu; dự phòng bằng `INITIAL_PASSWORD`
- Có thể bật/tắt `requireLogin` qua `/api/settings/require-login`
- Các route `/v1/*` có thể yêu cầu Bearer API key khi `REQUIRE_API_KEY=true`
- “management token” / “management-scoped API key” trong tài liệu tham khảo này có nghĩa là một trong các nhóm được nêu trong hướng dẫn đó — không phải một loại bí mật bổ sung chưa được định nghĩa

> **Thay đổi không tương thích ngược (v3.8.0)** — `/api/v1/agents/tasks/*` và các endpoint quản lý thời gian chờ hiện yêu cầu **xác thực quản trị** (cookie `auth_token` của dashboard hoặc API key có phạm vi quản trị). Các client trước đây gọi những route này mà không xác thực sẽ nhận được `401 Unauthorized`. Xem commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
