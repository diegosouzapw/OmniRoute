> オプトインで、デフォルトでは無効です（`settings.freeAccessPolicy !== "strict"` の場合、すべての `auto/*`
> 候補プールはバイト単位で完全に同一のままです）。これは `hidePaidModels`
> （`open-sse/services/autoCombo/paidModelFilter.ts`、#6512）より厳格な関連機能であり、単に「無料と明記されている」だけでなく、
> 追加の金銭的支出が一切発生しないことを厳密に保証する必要がある運用者向けです。

## この機能が存在する理由と、`hidePaidModels` だけでは不十分な理由

`hidePaidModels` が答えるのは、「このモデルは現時点で `FREE_MODEL_BUDGETS` において無料と分類されているか？」という問いです。
これは、`isFreeModel()`/`providerHasFreeModels()`
（`src/shared/utils/freeModels.ts`）を介して確認される、特定時点のカタログ情報です。以下の2つの現実的なリスクについては何も保証しません。

1. `recurring-*`/`one-time-initial` 無料枠の利用可能量が**使い果たされている**可能性があります。カタログには
   依然としてモデルが無料と記載されていても、その背後にあるアカウントには残りの利用可能枠がありません。
2. 無料枠の超過時に、必ずしも利用が強制停止されるとは限りません。一部のプロバイダーは、支払い方法を追加できないことを
   明示しています（「クレジットカード不要」）。一方で、明記していないプロバイダーもあり、少数ながら
   無料枠を超えると自動的に課金するプロバイダーもあります。

`hidePaidModels` はこれらを区別できません。そもそも、そのための機能ではありませんでした。STRICT_ZERO_COST は、
カテゴリ／ティアの順位付け**前**かつディスパッチ**前**に、候補ごとにこの2つのチェックを正確に追加します。
リクエストがすでに送信された後にチェックすることは決してありません。

## 候補の分類

プール内の各候補について（`open-sse/services/autoCombo/virtualFactory.ts::buildPreparedPool` 内の
`filterPaidOnlyCandidates` の直後）：

1. **`FREE_MODEL_BUDGETS` にまったく含まれていない** → 除外されます。これには、実際に有料のモデルと、
   OmniRoute がまだ分類していないプロバイダー／モデルが含まれます。新しい候補は、包含ではなく除外された状態から始まります。
2. **`freeType: "keyless"`** → 即座に通過しますが、**実際に認証なしの経路を通じて追加された候補に限ります**
   （`connectionId === SYNTHETIC_NOAUTH_CONNECTION_ID`、
   `open-sse/services/autoCombo/resilienceCandidateFilter.ts`）。その候補には認証情報が存在しないため、
   その候補へのリクエストが課金されることはありません。実行時チェックは不要であり、実行することもできません。
   カタログ上は同じ `keyless` プロバイダー／モデルであっても、**実際の** DB 接続を通じて到達したもの
   （`connectionId` が実在する接続 ID であるか、候補が `allowedConnectionIds` を保持している場合）には、
   この近道は適用されません。`keyless` メタデータが表すのは認証なしの経路に限られ、プロバイダー全般を表すものではなく、
   認証情報を持つ実際のアカウントを許可することも決してありません。このような候補は他の候補と同様にチェック3へ進み、
   カタログエントリに別途 `hardStopGuaranteed: true` が設定されていない限り除外されます（実際の
   `keyless` エントリには設定されません。この近道だけが安全性を満たす唯一の経路だからです）。
3. **その他の `freeType`**（`recurring-daily`、`recurring-monthly`、`recurring-credit`、
   `recurring-uncapped`、`one-time-initial`、およびこのモジュールが特別扱いしていない将来の型）→
   以下の条件を**すべて**満たす場合に限り通過します。
   - カタログエントリ（`FreeModelBudget.hardStopGuaranteed`、
     `open-sse/config/freeModelCatalog.ts`）に `hardStopGuaranteed: true` が設定されていること。
     これは、プロバイダー自身が公開している利用条件（明示的な「クレジットカード不要」という記載など）に関する、
     **精査のうえ手動で設定された事実**であり、`freeType` やライブ API レスポンスから導出されることはありません。
     未設定（`undefined`）と `false` は、どちらも「保証されていない」として扱われます。
   - `USAGE_FETCHER_PROVIDERS`
     （`open-sse/services/usage.ts`）に、そのプロバイダー用の利用量アダプターが存在すること。これは、
     すでにクォータダッシュボードと `getUsageForProvider()` を支えているものと同じレジストリです。
     アダプターがない場合は除外され、アダプターが追加されるまでその状態が続きます。
   - **実際に評価されている特定の接続**に対応する、ライブかつキャッシュ済みの `FreeAccessState` が
     `status: "SAFE"` であり、`settings.autoRefreshProviderQuotaInterval` 以内に確認されていて
     （デフォルトは180秒。新しい値ではなく、既存の設定です）、報告された `remainingFreeAllowance` が
     小さな安全マージンを上回っていること。
4. **`freeType: "discontinued"`** → 常に除外されます。

## 接続の安全性（候補単位ではなく、常に接続単位で検証）

auto-combo プール内の候補は、必ずしも単一の接続に紐付いているとは限りません。「論理」候補
（`connectionId: null`）は `allowedConnectionIds` 許可リストを保持します。これは、リクエストを処理できる可能性がある、1 つ以上の実際の
プロバイダー接続／アカウントのリストです。実際に使用されるアカウントは、後のディスパッチ時に `open-sse/services/combo/autoStrategy.ts`
によって決定されます（`allowedConnectionIds` と独自の接続選択ロジックとの共通部分を取得、約 315～331 行目）。

STRICT_ZERO_COST は、その許可リスト内にある**各接続の無料アクセス状態を個別に**
検証し（`strictZeroCostFilter.ts` の `evaluateCandidateConnections()`）、`allowedConnectionIds` を、
結果が `SAFE` だった接続のみで構成される部分集合へ書き換えます。元のリスト全体に戻すことも、恣意的に選んだ 1 件だけにすることもありません。具体的には次のとおりです。

- アカウント A が `SAFE`、アカウント B が `UNKNOWN`／上限到達／課金対象 → A のみが選択可能な状態で残ります。
- すべてのアカウントが `UNKNOWN` → 安全な集合が空になるため、候補全体が除外されます。
- 単一接続の候補（`connectionId` が直接設定され、許可リストがないもの）が検証に失敗した場合は、即座に除外され、空の `allowedConnectionIds` を持つ状態で返されることはありません。

`autoStrategy.ts` は接続先を選択する前に、すでに `allowedConnectionIds` を厳格な許可リストとして適用しているため、検証済みの `SAFE` な部分集合へ書き換えるだけで、ディスパッチ時に実際に使用される接続が、必ずこのフィルター自身によって検証されたものであることを保証できます。同じ候補に含まれる別の未検証アカウントが使用されることはありません。回帰テストによる証明については、
`tests/unit/autoCombo/strict-zero-cost-connection-safety.test.ts` を参照してください
（キーレスバイパスのケース A/B/C、複数アカウントのケース 1～5）。

`discovered automatically`：適切なメタデータを備えたプロバイダー／モデル（カタログに登録され、usage adapter があり、`hardStopGuaranteed: true` であるもの）が明日追加された場合、OmniRoute がそれを認識した時点で利用可能になります。コード変更も、許可リストへの追加も、このモジュール内の編集も必要ありません。カタログから削除されたものも、同様に利用対象から消えます。回帰テストによる証明については、
`tests/unit/autoCombo/strict-zero-cost-autodiscovery.test.ts` を参照してください（実際のカタログを変更するのではなく、注入可能なフィクスチャを使用）。

## クォータのキャッシュ（`open-sse/services/autoCombo/freeAccessQuota.ts`）

`getUsageForProvider()` を再利用しており、別のクォータシステムは導入していません。その前段には、有効期間がプロセスの生存期間に限定された短時間のインメモリキャッシュが置かれています（TTL はデフォルトの
`autoRefreshProviderQuotaInterval` と同じ）。これにより、Telegram 規模のリクエストレートでも、リクエストごと、候補ごとにライブの
課金 API 呼び出しが発生することはありません。読み取りは同期的です。キャッシュミス時には
`undefined` を返し（→ 除外、フェイルクローズ）、_次回_の読み取りに備えてバックグラウンド更新を開始します。
候補プールの構築経路でネットワーク呼び出しを待機することは一切ありません。

接続が何らかの理由で失敗した時点で、
`src/sse/services/auth.ts::markAccountUnavailable()` から `invalidateFreeAccessState(provider, connectionId)` が呼び出されます。そのため、次回のプール構築では、古い `SAFE` エントリではなく、消去済みのキャッシュミス状態が読み取られます。402／403／クォータ上限到達のレスポンス後に TTL が切れるのを待つ必要はありません。

## ToS ガード（経済的安全性とは独立）

`excludeTosAvoid`（デフォルトは `false`）は、キュレーションされた `tos` の判定
（`FreeModelBudget.tos`）が `"avoid"` である候補をすべて除外します。これは、`hidePaidModels` の関連ドキュメント
（`docs/reference/FREE_TIERS.md`）ですでに設定されているものと同じフィールドを再利用します。
これは意図的に `freeAccessPolicy` とは分離されています。候補は経済的には `SAFE` でも契約上の理由で
ここで除外される場合があり、逆にこのガードがオフなら、`freeAccessPolicy: "strict"` がオンでも候補として残ります。

## ガードが除外する内容の確認

`GET /v1/auto-combo/{channel}/candidates` は、このガードによってディスパッチから
除外される候補も含め、すべての候補を一覧表示します。各候補には `freeAccessExclusion` が含まれ、
ガードの条件を満たす場合は `null`、そうでない場合はその理由が設定されます。この一覧は状態を報告するだけで、
強制は行いません。ポリシーをオフにすると、このフィールドはすべての候補で `null` となり、コストはかかりません。

| `freeAccessExclusion`  | 意味                                                                                                                | 対処方法                                                                                                                         |
| :--------------------- | :------------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------- |
| `not-in-catalog`       | プロバイダーとモデルの組み合わせが `FREE_MODEL_BUDGETS` に存在しません。                                            | キュレーションされたエントリを追加するか、新しい組み合わせは最初から除外されるという設計を受け入れてください。                   |
| `regime-not-free`      | カタログにはありますが、その `freeType` は無料アクセスを提供するものではありません（廃止されたプランなど）。        | 修正すべきものはありません。このモデルは有料です。                                                                               |
| `no-hard-stop`         | 無料枠ですが、`hardStopGuaranteed` が `true` ではないため、上限を超えると通知なく課金が始まる可能性があります。     | プロバイダーの規約を確認し、出典をコメントに記載してフラグを設定してください。カタログを増やす目的で設定してはいけません。       |
| `contradictory-noauth` | 認証不要の候補なのに、カタログエントリが `keyless` ではありません。メタデータの不整合時は安全側に倒して拒否します。 | カタログエントリを修正してください。2 つの事実が矛盾しています。                                                                 |
| `exhausted`            | 最新の読み取り結果で、割り当てを使い切っていることが示されています。                                                | リセットを待ってください。これは自然に解消されます。                                                                             |
| `state-unknown`        | クォータの読み取り結果がないか、古すぎて信頼できません。                                                            | 確認してください。プロバイダーの使用量アダプターが登録されていないか、クォータの取得に失敗している可能性があります。             |
| `no-connection`        | 候補に、確認対象となるアカウントがまったく含まれていません。                                                        | クォータの問題ではありません。候補が接続なしで構築されたため、検索は一度も行われていません。プールの構築方法を確認してください。 |

最後の 2 つは、区別する価値がある組み合わせです。使い切った割り当ては自然にリセットされますが、
読み取り結果がまったく届かない場合は検索自体が壊れています。これまでは、どちらも外部からは同じように見え、
候補が単に消えていました。

**まだ 1 つ抜けが残っており、これは意図的なものです。** `excludeTosAvoid` は引き続き、一覧が構築される前に
候補を削除するため、`tos: "avoid"` としてキュレーションされたモデルは理由が示されないまま一覧から消えます。
これは、このセクションでゼロコストガードについて解消した不可視性と同じものです。これも解消するには、
ToS による除外で何を報告すべきかを決める必要がありますが、それは経済的安全性とは別の問題です。このページでは、
存在しないふりをせず、その抜けを明記しています。

オフラインで前後を比較するには、`npx tsx scripts/ad-hoc/dry-run-strict-zero-cost.ts` を
稼働中のインスタンスの候補出力に対して引き続き使用できます。これは各候補の実際の `connectionId` を読み取るため、
接続安全性の経路も検証します。Keyless 候補では、実際の接続ではなく、合成された認証不要の
`connectionId` が必ず渡されなければなりません。現在組み込まれている keyless 自動経路は OpenCode Free です。正確な候補数は、
引き続きライブのモデル検出に依存するため、古い実行結果からコピーするのではなく、対象のデプロイ環境で測定してください。
`recurring-*` 候補が通過するのは、登録済みの使用量アダプターと `hardStopGuaranteed: true` の両方を備えている場合だけです。
不完全なメタデータは、引き続き安全側に倒して拒否されます。

`excludeTosAvoid: true` の場合、`tos: "avoid"` としてキュレーションされた候補はすべて削除されます。現在、
OpenCode Free にはその判定が設定されているため、このガードを有効にすると、デプロイ環境に残っている keyless
プールが空になる可能性があります。これは ToS ガードを有効にすることで生じる想定内のトレードオフであり、
バグではありません。まさにこの理由から、このガードはデフォルトで `false` です（上記の「ToS ガード」を参照）。

## 有効化

```json
PUT /api/settings
{ "freeAccessPolicy": "strict", "excludeTosAvoid": false }
```

どちらの新しい設定も、デフォルトでは機能導入前の値（`"off"` / `false`）になります。そのため、どちらも有効化しなければ、既存の `auto/*` ルーティング動作は変更されません。
