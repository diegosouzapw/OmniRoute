## ✨ v3.8.0 のハイライト

v3.7.x → v3.8.0 のサイクルでは、設定不要の自動ルーティング、新しいプロバイダー、OAuth フロー、より高度な耐障害性、そして大幅に充実した CLI エクスペリエンスが追加されました。主な機能は以下のとおりです。詳細については、本ドキュメントの後半およびリンク先の仕様をご覧ください。

- 🤖 **Auto Combo / 設定不要の自動ルーティング** — `auto/coding`、`auto/fast`、`auto/cheap`、`auto/offline`、`auto/smart`、`auto/lkgp`、`auto/chaos` のプレフィックスを使用できます。16 要素のスコアリングエンジンと、厳選された 6 つの **モードパック**（ship-fast、cost-saver、quality-first、offline-friendly、reliability-first、chaos-mode）を基盤としています
- 🆕 **Command Code プロバイダー**（#2199）— モデルカタログとクォータ追跡を備えたファーストクラスの登録機能
- 🆕 **Z.AI プロバイダー** — クォータラベルを備えた新しい無料枠プロバイダー
- 🎬 **KIE メディアの拡充** — 動画生成モデルを含むカタログの拡張
- 🔐 **Devin 認証** — Desktop は既存の Devin API キーをインポートし、CLI はローカルの `devin auth login` 認証情報を使用します
- 🆓 **8 つの新しい無料プロバイダー** — LLM7、Lepton、UncloseAI、BazaarLink、Completions、Enally、FreeTheAi、Command Code
- 🎯 **マニフェスト対応の W1～W4 ティアルーティング** — プロバイダーマニフェストに基づいて重み付きティア選択を行います
- 🎨 **Cursor の OpenAI 完全互換** — ツール呼び出し、ストリーミング、セッション管理をエンドツーエンドでサポート
- 📊 **Cursor Pro プランの使用状況** — クォータおよびサイクルデータをプロバイダー制限ダッシュボードに表示
- ⚡ **サービスティア別の内訳 / Codex 高速ティア分析** — ティアごとの消費量を可視化
- 📌 **セッション単位のスティッキールーティング** — Codex セッションでは、ターン間で同じアカウントを固定して使用します
- 🔊 **Inworld TTS の強化** — 音声カタログ、ストリーミング、レイテンシーの改善
- 🔑 **Kiro ヘッドレス認証** — ブラウザーを必要とせず、ローカルの `kiro-cli` SQLite ストアを介してログイン
- 📉 **DeepSeek のクォータおよび制限監視** — 日次および月次の使用状況をダッシュボードに表示
- 🔄 **リセット時刻を考慮したルーティング戦略** — コンボは、クォータウィンドウが最も早くリセットされるアカウントを優先するようになりました
- ⏱️ **`fallbackDelayMs`** と **動的なツール上限検出** — より細かなフォールバックタイミングと、プロバイダーごとのツール数上限

## 🔌 プロバイダー

AIプロバイダー接続を管理します：OAuthプロバイダー（Claude Code、Codex）、APIキープロバイダー（Groq、DeepSeek、OpenRouter）、無料プロバイダー（Qoder、Kiro）。Kiroアカウントではクレジット残高も追跡され、残りクレジット、総割当量、更新日を「Dashboard → Usage」で確認できます。

OpenRouter接続では、「Advanced Settings」で接続ごとの`preset`を保存できます。設定すると、クライアントリクエストですでに独自の`preset`が指定されていない限り、OmniRouteはそれをOpenRouterのトップレベルリクエストフィールドとして送信します（例：`"preset": "email-copywriter"`）。

## 🎨 コンボ

19種類の公開戦略を使用してモデルルーティングコンボを作成できます：priority、weighted、round-robin、context-relay、fill-first、p2c（power-of-two choices）、random、least-used、cost-optimized、reset-aware、reset-window、headroom、strict-random、auto、lkgp（last-known-good-provider）、context-optimized、cache-optimized、**fusion**（複数モデルのパネルへ並列にリクエストを送り、judgeを介して1つの回答に統合）、**pipeline**。各コンボは複数のモデルを自動フォールバック付きで連結し、クイックテンプレートと準備状況チェックを備えています。

最近のコンボの改善点：

- **構造化コンボビルダー** — プロバイダー、モデル、正確なアカウント／接続を選択して各ステップを作成
- **同一プロバイダーの繰り返し使用をサポート** — `(provider, model, connection)`タプルが一意である限り、1つのコンボ内で同じプロバイダーを何度でも再利用可能
- **コンボターゲットのヘルス** — 分析画面とヘルス画面で、すべてをモデル文字列として集約するのではなく、個々のコンボターゲット／ステップを区別
- **複合ティアの順序付け** — `defaultTier -> fallbackTier`が、トップレベルのコンボステップにおける実行時の処理順序／フォールバック順序に影響
- **システムプロンプトテンプレート** — コンボの`system_message`は、サーバー側の
  `{{MODEL_ID}}`、`{{PROVIDER_ID}}`、`{{ACCOUNT}}`、`{{FINGERPRINT}}`
  プレースホルダーをサポートし、ディスパッチ直前に実際にルーティングされたターゲットの値で展開されます。
  許可リスト方式で再帰展開は行われません。不明なプレースホルダーはリテラルのまま残り、空の値は
  空文字列に展開されます。クライアントのシステムプロンプトが書き換えられることはありません。`{{FINGERPRINT}}`
  は、固定または自動ローテーションされたフィンガープリントを持つ、フィンガープリントベースの無料プロバイダーでのみ
  解決されます。それ以外（例：
  単一フィンガープリント接続、非フィンガープリントプロバイダー）では空文字列に展開されます。展開は
  標準ディスパッチループ、round-robin、固定されたcontext-cacheセッションに対応しています。
  fusion、chaos、pipeline、nested-execute戦略では、現時点で
  プレースホルダーは展開されません。

## 🎮 モデルプレイグラウンド _(v2.0.9+)_

ダッシュボードから任意のモデルを直接テストできます。プロバイダー、モデル、エンドポイントを選択し、Monaco Editor でプロンプトを作成して、レスポンスをリアルタイムでストリーミングできます。ストリームの途中で中止したり、タイミング指標を確認したりすることもできます。

---

## 🎨 テーマ _(v2.0.5+)_

ダッシュボード全体のカラーテーマをカスタマイズできます。7 つのプリセットカラー（コーラル、ブルー、レッド、グリーン、バイオレット、オレンジ、シアン）から選択するか、任意の 16 進カラーを指定してカスタムテーマを作成できます。ライト、ダーク、システムモードに対応しています。

## ⚙️ 設定

**7 つのタブ**を備えた包括的な設定パネル：

- **外観** — テーマセレクター（ダーク／ライト／システム）、カラーテーマのプリセットとカスタムカラー、ヘルスログの表示設定、サイドバー項目とグループ区切りの表示コントロール、エンドポイントトンネルの表示コントロール

## 🔗 コンテキストリレー _(v3.5.5+)_

会話の途中でアカウントがローテーションされても、セッションの継続性を維持するコンボ戦略です。アクティブなアカウントのクォータを使い切る前に、OmniRoute がバックグラウンドで構造化された引き継ぎ要約を生成します。次のリクエストが別のアカウントに振り分けられると、その要約がシステムメッセージとして挿入され、新しいアカウントが完全なコンテキストを引き継いで処理を続行できるようになります。

コンボ単位またはグローバル設定で構成できます：

- **引き継ぎしきい値** — 要約生成をトリガーするクォータ使用率（デフォルトは 85%）
- **要約対象の最大メッセージ数** — 要約する直近の履歴量
- **要約モデル** — 引き継ぎ要約の生成に使用するモデルを任意で上書き

現在、Codex アカウントのローテーションをサポートしています。[コンテキストリレーのドキュメント](../architecture/ARCHITECTURE.md)を参照してください。

## 🗜️ プロンプト圧縮 _(v3.7.9+)_

「コンテキストとキャッシュ」では、Caveman、RTK、および圧縮コンボ専用のページを利用できるようになりました：

- **Caveman** — 言語対応のルールパック、プレビュー、出力モード制御、および分析
- **RTK** — シェル、git、テスト、ビルド、パッケージ、Docker、インフラ、JSON、およびスタックトレース出力に対応したコマンド認識型圧縮
- **圧縮コンボ** — `rtk -> caveman` のような名前付きパイプラインをルーティングコンボに割り当てます。両方のエンジンが適用される場合、デフォルトの積算方式により、平均 `~89%`、圧縮対象コンテキストでは `78-95%` の削減率を実現します
- **生出力の復元** — 圧縮に起因するエラーのデバッグ用に、任意で機密情報を除去した RTK 生出力へのポインターを提供

[圧縮ガイド](../compression/COMPRESSION_GUIDE.md)、[RTK 圧縮](../compression/RTK_COMPRESSION.md)、および
[圧縮エンジン](../compression/COMPRESSION_ENGINES.md)を参照してください。

## 🛡️ プロキシの強化 _(v3.5.5+)_

リクエストパイプライン全体にわたって、プロキシ設定を包括的に適用します：

- **トークンのヘルスチェック** — バックグラウンドでの OAuth 更新時に接続ごとのプロキシ設定を解決するようになり、プロキシが必須の環境での失敗を防止

## 🌐 V1 WebSocket ブリッジ _(v3.6.6+)_

OmniRoute は、`/v1/ws` アップグレードエンドポイントを介して **OpenAI 互換 WebSocket クライアント**をサポートするようになりました。カスタムの `scripts/dev/v1-ws-bridge.mjs` サーバーが Next.js をラップし、WS 接続を完全な双方向ストリーミングセッションへアップグレードします。認証には、HTTP リクエストと同じ API キーまたはセッションクッキーを使用します。

- セッション終了時またはアップストリームエラー発生時にストリームを正常に終了
- 既存の HTTP+SSE ストリーミング経路と同時に動作

## 🔑 同期トークンと設定バンドル _(v3.6.6+)_

**スコープ付き同期トークン**により、複数デバイスや外部オペレーターからのアクセスが可能になりました。

- **`POST /api/sync/tokens`** — 新しい同期トークンを発行（スコープ付き、有効期限は任意）
- **`DELETE /api/sync/tokens/:id`** — トークンを失効
- **`GET /api/sync/bundle`** — 機密性のないすべての設定について、バージョン管理され、ETagをキーとするJSONスナップショットをダウンロード（パスワードはマスキング済み）

設定バンドルは`src/lib/sync/bundle.ts`によって構築されます。コンシューマーは`ETag`レスポンスヘッダーを比較することで、ペイロード全体を再ダウンロードせずに変更を検出できます。

## 🛡️ 安全なアウトバウンドフェッチとSSRFガード _(v3.6.6+)_

すべてのプロバイダー検証およびモデル検出の呼び出しは、2層のアウトバウンドガードを経由するようになりました。

1. **URLガード**（`src/shared/network/outboundUrlGuard.ts`）— ソケットが開かれる前に、プライベート、ループバック、リンクローカルのIP範囲をブロックします。
2. **安全なフェッチラッパー**（`src/shared/network/safeOutboundFetch.ts`）— URLガードを適用し、タイムアウトを正規化して、一時的なエラーを指数バックオフで再試行します。

ガード違反はHTTP 422（`URL_GUARD_BLOCKED`）として通知され、`providerAudit.ts`を介してコンプライアンス監査ログに記録されます。

## 🔄 クールダウン対応の再試行 _(v3.6.6+)_

上流プロバイダーがモデル単位のクールダウンを返した場合、チャットリクエストが**自動的に再試行**されるようになりました。`REQUEST_RETRY`（デフォルト：2）および`MAX_RETRY_INTERVAL_SEC`（デフォルト：30 s）で設定できます。`x-ratelimit-reset-requests`、`x-ratelimit-reset-tokens`、`Retry-After`にわたるレート制限ヘッダーの学習が改善され、モデルごとのクールダウン状態をレジリエンスダッシュボードで確認できます。
