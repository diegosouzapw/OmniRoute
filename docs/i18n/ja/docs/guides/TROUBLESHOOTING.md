### 無料プロバイダーでのレート制限（429 / 400 / 401）

**症状**：無料または認証不要のプロバイダー（opencode、auggie など）で `model: "auto"` を使用すると、回答の代わりに断続的に `HTTP 429`、`400`、または `401` が返されます。少し時間を置いて同じプロンプトを再試行するとリクエストは成功しますが、自動化（cron ジョブ、エージェント、スクリプト）は最初の失敗で停止します。

**根本原因**：3 つの独立した障害モードが重なっています。

1. **プロバイダーのレート制限（`429`）**：無料枠では、一定期間ごとのクォータが適用される場合があります。並列呼び出しが集中するとクォータを使い切り、制限期間がリセットされるまで次のリクエストが拒否されます。
2. **パススルー内の壊れたモデル（`400`/`401`）**：`auto/*` プールには、カタログには登録されているものの、有効な認証情報がない `opencode` のパススルーモデルが含まれる場合があります（例：`oc/north-mini-code-free` → `401`）。自動ルーターがそのいずれかを試して失敗すると、フォールバックが作動する前にエラーが伝播します。
3. **同時実行による増幅（高負荷時の `429`）**：複数のエージェントまたは cron セッションが同時に `auto` へアクセスすると、リクエストの合計レートが無料プロバイダーの許容範囲を超え、正当な呼び出しまで不正利用として判定されます。

**検証済みの修正方法（コミュニティ報告、2026-08-10）**：無料枠の不安定さによって処理が停止するのではなく、ローテーション、同時実行制御、フォールバックで吸収できるよう、次の 3 つの環境変数を調整します。

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 の場合は別のモデルまたはプロバイダーへ切り替える（壊れたパススルーモデルをスキップ）
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # 重いリクエストの明示的な受付上限（デフォルトでは未設定：リクエスト数の上限なし。下記の注記を参照）
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # 即座に再試行可能な 503 を返す代わりに、重いリクエストの処理枠を待つ時間を制限付きで延長
```

これらを OmniRoute プロセスの環境（デーモン。例：LaunchAgent plist または `systemctl edit`）に設定し、OmniRoute を再起動します。ローテーションフラグが最も効果の大きい設定です。ハードエラーを、プール内の正常なプロバイダーに対する透過的な再試行へ変換します。

**注記**：`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` は、同時に実行できる重い — 長いコンテキストを持つ — リクエストの数を制限します。この上限は受付ゲートであり、プロバイダーのレートリミッターではありません。**#503-fanout の更新：**この変数はデフォルトでは設定されなくなりました（上記のように明示的に設定した場合にのみ適用されます）。代わりに、重いリクエストの受付は、自動算出されるバイト予算（`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`）によって制御されます。この予算はホストの実際のメモリ上限に応じて自動的に調整されるため、新規デプロイでは、この変数を一切設定しなくても `503 chat_admission_busy` による拒否が大幅に減るはずです。ここで明示的に設定した場合も、記載どおりに動作します。明示的なバイト予算のオーバーライドは、8 MiB～2 GiB の範囲に制限されます。`413 body_exceeds_budget` は一時的なエラーではありません。バイト予算を増やすか、`OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` を引き下げるか、プロセスのメモリ上限を増やしてください。`inflight_bytes_budget` による負荷遮断は一時的な競合であり、引き続き再試行できます。プロバイダーごとのレート制限（`open-sse/services/rateLimitManager.ts`）は、`RATE_LIMIT_MAX_WAIT_MS`、`RATE_LIMIT_MAX_QUEUE_DEPTH`、`RATE_LIMIT_AUTO_ENABLE` によって個別に制御されます。`.env.example` を参照してください。

**修正を確認する方法**：エージェントまたは cron を短時間に 2 回実行し、両方が成功することを確認します。修正前は通常、2 回目の実行で `429`/`401` が発生します。修正後は、エラーが発生しても透過的に再試行され、呼び出しが完了します。また、`curl /monitoring/health` を実行し、プロバイダー接続の `rateLimitedUntil` フィールドと、影響を受けるプロバイダーの `circuitBreakers.providerBreakers[].state` を確認することもできます。状態は `CLOSED`、`DEGRADED`、`OPEN`、`HALF_OPEN` のいずれかです（`src/shared/utils/circuitBreaker.ts` を参照）。失敗が続くプロバイダーは、リセット期間後にプローブを通せるようになる（`HALF_OPEN`）まで、`CLOSED → DEGRADED → OPEN` と遷移します。

**それでも 429 が表示される場合**: そのプロバイダーで現在アクティブなアカウントは、単なるレート制限ではなく、実際に_クォータ_を使い切っています。OmniRoute ダッシュボードの Providers → Accounts で同じプロバイダーの2つ目のアカウントを追加するか、別の無料プロバイダー（例: `routeway`、`auggie`）を併用してください。ローテーションが有効なのは一時的なレート制限や 400/401 に対してのみです。クォータを完全に使い切った場合は、2つ目の認証情報または別のプロバイダーが必要です。

**ビジョンモデル（`auto/vision`、`bazaarlink/*`）で 403 が表示される場合**: 接続済みアカウントにビジョン機能を含む有料プランがないか、API キーの権限が不足しています。プロバイダーのダッシュボードで、キーのスコープにビジョン/マルチモーダルが含まれていることを確認するか、有料プランのアカウントを接続してビジョンのターゲットとして設定してください。

## npm install の警告（ERESOLVE / peer / deprecated）

`npm install -g omniroute` を実行すると、`npm warn ERESOLVE`、peer dependency に関する通知、`deprecated` メッセージなど、大量の警告が表示される場合があります。**これらは想定内であり、問題ありません。** 出力に `added <N> packages` と表示されていれば、インストールは成功しています。

これらの警告は、OmniRoute が管理していないサードパーティパッケージの古い peer dependency 範囲が原因です。

1. **`marked-terminal` は `marked >=1 <16` を要求しているが、`marked@18` が検出された** — 実際には問題なく動作します。アップストリームの peer dependency 範囲が古いだけです。
2. **`deprecated prebuild-install@7.1.3`** — 推移的依存関係にある、ネイティブバイナリ取得用のヘルパーです。これは固定された `wreq-js` トランスポートバインディングのインストールには
   使用されておらず、Web Cookie プロバイダーのトランスポート設定が失敗したことを示すものでも
   ありません。

**対応は不要です** — アップストリームパッケージをフォークしない限り、これらの警告を完全に非表示にすることはできません。

## アンチウイルスによる誤検知

<a name="antivirus-false-positives"></a>

### Avast/AVG が `README.md` を `MD:HttpRequest-inf[Susp]` として隔離する

**これは誤検知です。何も感染しておらず、対応は不要です。**

Avast と AVG は、HTTP リクエストのように見えるリンクを多数含むプレーンテキスト/Markdown ファイルを検出するヒューリスティックを実行します。OmniRoute の `README.md` は npm パッケージに同梱されているため（`package.json` → `files` に記載されています）、グローバルインストール時に `node_modules/omniroute/README.md` に配置されます。また、このファイルには約15個の `http://localhost:20128/...` の例（MCP HTTP/SSE エンドポイント、A2A `.well-known` URL、`curl` スニペット）が含まれています。このリンク密度がヒューリスティックの検出基準を超えるのに十分な量となっています。

これが最近になって発生し始めた場合でも、ファイルの性質が変わったわけではありません。README のエンドポイント表が拡充され（MCP HTTP + SSE + A2A が追加されました）、さらに `curl` の例も増えたことで、しきい値を超えました。

このファイルは実行可能な内容を一切含まない、無害なドキュメントです。隔離から安全に復元できます。

**対応方法：**

1. **通知を停止する** — アンチウイルスでインストールディレクトリを除外し（Avast: Settings → Exceptions）、グローバルの `node_modules` パスおよび/または OmniRoute のデータディレクトリ（`~/.omniroute/`）を追加してください。
2. **誤検知を報告する** — <https://www.avast.com/false-positive-file-form.php> から、隔離された `README.md` を添付して報告してください。テキストファイルに対してベンダーのヒューリスティックが過剰反応しているため、これがすべてのユーザーに役立つ解決策です。

**こちら側で「修正」しない理由：** すべての例は `http://localhost` であり、自己署名証明書に伴う煩雑さなしに localhost を `https` にすることはできません。あるベンダーのヒューリスティックを回避するためにドキュメントを不自然に改変すると、スキャナーのバグに対応するためにすべての読者の利便性を損なうことになります。

### Kaspersky がデスクトップアプリを `PDM:Trojan.Win32.Generic` として検出する

**これは挙動ベースのヒューリスティックによる誤検知です。何も感染していません。** Kaspersky の `PDM:` プレフィックスは、その判定が Proactive Defense Module（System Watcher）によるものであることを意味します。これは既知のマルウェアとの一致ではなく、インストーラーの_挙動_を評価します。検出が発生すると、Kaspersky はインストール全体を「ロールバック」し、すでに書き込まれたファイルを削除するため、アプリが破損したり消失したりします。

検出されるファイルは、デスクトップアプリにバンドルされている、明示済みのオープンソース依存関係の標準的な構成要素です。例：

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` および
  `workerProcessEntry.js` — アプリ内でのプロバイダーログインとブラウザーベースのチャットに使用されるブラウザー自動化ライブラリ、[Playwright](https://playwright.dev)。
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — Web Cookie を使用するプロバイダーで、ブラウザーフィンガープリントを模倣した HTTP 通信に使用される、バージョン固定済みの `wreq-js` ネイティブバインディング（`<arch>` は `x64` または `arm64`）。

**検出される理由：** Windows インストーラーは**まだコード署名されていない**ため、署名のない NSIS インストーラーにはレピュテーションがまったくなく、挙動ベースのヒューリスティックが最大限に厳しい状態で実行されます。バンドルされたネイティブ DLL と、`%LOCALAPPDATA%\Programs\OmniRoute` 配下に書き込まれる数百個の `.js` ファイル（Next.js のスタンドアロンビルドによって生成される、ハッシュ接尾辞付きのパッケージディレクトリを含む）が組み合わさることで、ヒューリスティックの検出基準を超えるのに十分な条件となります。コード署名は予定されていますが、導入されるまでは新しいリリースでもこの問題が繰り返し発生する可能性があります。

**対応方法：**

1. **まずダウンロードを検証する**（ファイルが改ざんされている可能性を排除します）。各リリースでは `latest.yml` が公開されており、その `sha512` フィールド（base64）は `OmniRoute.Setup.<version>.exe` インストーラーに対応しています。インストーラーが含まれるフォルダーから、PowerShell で以下を実行してください：
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   出力は `latest.yml` → `sha512` と一致する必要があります。一致しない場合はファイルを削除し、[GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) からのみ再ダウンロードしてください。
2. **復元して除外する** — ロールバックされた項目を隔離から復元し、`%LOCALAPPDATA%\Programs\OmniRoute` を除外対象に追加して（Kaspersky → Settings → Threats and Exclusions）、再インストールしてください。
3. **誤検知を報告する** — <https://opentip.kaspersky.com/>。ユーザーから提出された誤検知レポートは、実際に許可リストへの登録を迅速化します。

## Node.js の互換性

<a name="nodejs-compatibility"></a>

### ログインページがクラッシュする、または「Module self-registration」エラーが表示される

**原因:** OmniRoute が承認している安全なランタイムの最低要件を満たさない Node.js バージョンを実行しています。最も一般的なのは、OmniRoute が必須としているセキュリティ修正済みの最低バージョンより古い Node 22 または 24 のパッチバージョンを使用しているケースです。

**症状:**

- ログインページに空白画面またはサーバーエラーが表示される
- コンソールに `Error: Module did not self-register` または同様のネイティブバインディングエラーが表示される
- ランタイムがサポート対象のセキュリティポリシーから外れている場合、ログインページに使用中の Node バージョンを示す**オレンジ色の警告バナー**が表示される

**修正方法:**

1. サポート対象の Node.js LTS リリースをインストールします（推奨: Node.js 24.x）。
   ```bash
   nvm install 24
   nvm use 24
   ```
2. バージョンを確認します。24.x LTS 系では、`node --version` に `v24.0.0` 以降が表示される必要があります
3. OmniRoute を再インストールします: `npm install -g omniroute`
4. 再起動します: `omniroute`

> **サポート対象の安全なバージョン:** `>=22.22.2 <23` または `>=24.0.0 <27`。Node.js 24.x LTS (Krypton) および Node.js 26 は完全にサポートされています。

### npm v11 以降: `better-sqlite3` がインストールされない（Cannot find module）

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**原因:** Node.js 24 以降に同梱される npm v11 は、オプションの依存関係に対するインストールスクリプトをデフォルトでブロックします。`better-sqlite3` は `optionalDependencies` に含まれており、ネイティブコンパイル（`node-gyp rebuild`）を必要とするため、npm は通知せずにこれをスキップします。

**症状:**

- 起動時に `Cannot find module 'better-sqlite3'` が表示され、サーバーがクラッシュする
- `ls node_modules/better-sqlite3` を実行すると「No such file or directory」と表示される
- `npm ls better-sqlite3` を実行すると `(empty)` と表示される

**修正方法:**

1. インストールスクリプトを承認して、再インストールします。
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. または、ビルド済みパッケージを手動でインストールします。
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. 正常に動作することを確認します: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / 「slice is not valid mach-o file」

<a name="macos-native-module-rebuild"></a>

**原因:** グローバルな `npm install -g omniroute` の実行後、パッケージ内の `better-sqlite3` ネイティブバイナリが、ローカルで実行されているものとは異なるアーキテクチャまたは Node.js ABI 向けにコンパイルされている場合があります。これは、ビルド済みバイナリが環境と一致しない場合に、macOS（Apple Silicon と Intel の両方）でよく発生します。

**症状:**

- 起動直後に `dlopen` エラーが発生し、サーバーが停止する
- エラーに `slice is not valid mach-o file` が含まれる
- 完全な例:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**修正方法 — ローカル環境向けに再ビルドします（Node.js のダウングレードは不要です）:**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **注:** これにより、ローカルの Node.js バージョンおよび CPU アーキテクチャに合わせてネイティブバインディングが再コンパイルされ、バイナリの不一致が解消されます。公式にサポートされているランタイム範囲は **`>=22.22.2 <23` または `>=24.0.0 <27`** です（`src/shared/utils/nodeRuntimeSupport.ts` の `SUPPORTED_NODE_RANGE`。`package.json` の `engines` フィールドと整合しています）。Node.js 24.x LTS (Krypton) および Node.js 26 は、`better-sqlite3` v12.x で完全にサポートされています。

## プロキシの問題

<a name="proxy-issues"></a>

### プロバイダー検証で「fetch failed」と表示される

**原因:** API キー検証エンドポイント（`POST /api/providers/validate`）が以前はプロキシ設定を経由していなかったため、プロキシ経由の通信が必要な環境でエラーが発生していました。

**修正（v3.5.5+）:** この問題は修正済みです。プロバイダー検証は `runWithProxyContext` を経由し、プロバイダー単位およびグローバルのプロキシ設定が自動的に適用されるようになりました。

### トークンのヘルスチェックが「fetch failed」で失敗する

**原因:** バックグラウンドでの OAuth トークン更新時に、接続ごとのプロキシ設定が解決されていませんでした。

**修正（v3.5.5+）:** トークンのヘルスチェックスケジューラーは、更新を試みる前に接続ごとのプロキシ設定を解決するようになりました。v3.5.5+ にアップデートしてください。

### SOCKS5 プロキシが「invalid onRequestStart method」を返す

**原因:** Node.js 22 では、undici@8 のディスパッチャーが Node の組み込み `fetch()` 実装と互換性がありません。

**修正（v3.5.5+）:** OmniRoute は、プロキシディスパッチャーが有効な場合に undici 独自の `fetch()` 関数を使用するようになり、一貫した動作が保証されます。v3.5.5+ にアップデートしてください。

### WSL 環境の MITM プロキシで Windows ホスト上のデスクトップアプリが傍受されない

**原因:** MITM プロキシとその CA 証明書は、OmniRoute が実行されている環境にインストールされます。WSL では、その環境は Linux ゲストですが、AI デスクトップアプリ（Kiro、Trae、Copilot、Zed、…）は Windows ホスト上で実行されます。ホスト側のアプリはゲスト側の証明書ストアを信頼せず、ゲスト側のシステムプロキシも経由しないため、デスクトップアプリの通信は傍受されません。

**推奨:** 傍受対象のデスクトップアプリと同じ OS 上で OmniRoute をネイティブ実行してください（Windows アプリの場合は Windows、macOS/Linux の場合も同様）。OmniRoute を WSL 内で実行したままホスト側アプリを対象にするには、生成された CA 証明書を Windows ホストで手動で信頼し、各ホストアプリのネットワーク／プロキシ設定で WSL のプロキシエンドポイントを指定する必要があります。この構成はサポート対象外であり、安定性に欠けます。

## プロバイダーの問題

### 「Language model did not provide messages」

**原因:** プロバイダーのクォータを使い切っています。

**修正:**

1. ダッシュボードのクォータトラッカーを確認する
2. フォールバック階層を備えたコンボを使用する
3. より安価な階層または無料階層に切り替える

### レート制限

**原因:** サブスクリプションのクォータを使い切っています。

**修正:**

- フォールバックを追加する: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- 安価なバックアップとして GLM/MiniMax を使用する

### OAuth トークンの期限切れ

OmniRoute はトークンを自動更新します。問題が解消しない場合:

1. ダッシュボード → プロバイダー → 再接続
2. プロバイダー接続を削除して再追加する

### Kiro の複数アカウント: 2 番目のアカウントによって最初のアカウントが無効になる

**原因:** Kiro のバックエンドでは、OIDC クライアント登録ごとに有効なセッションが 1 つに制限されています。
2 つのアカウントが同じ登録済みクライアントを共有している場合（v3.8.0 より前にインポートされた接続）、
一方のアカウントのトークンを更新すると、もう一方のリフレッシュトークンが無効になります。

**修正（v3.8.0+）:** 影響を受ける接続を再インポートしてください。
v3.8.0 以降では、**トークンのインポート**、
**Google/GitHub ソーシャルログイン**、または **自動インポート**で作成された新しい Kiro 接続ごとに、
専用の OIDC クライアントが自動的に登録されます。これにより接続が完全に分離され、一方の
アカウントを更新しても、他のアカウントには影響しません。

v3.8.0 _より前_にインポートされた接続には、接続ごとのクライアント
登録がありません。これらの接続では、引き続き共有のソーシャル認証更新エンドポイントが使用されます。
接続を分離するには、ダッシュボード → プロバイダーから古い接続を削除し、
3 つのインポートフローのいずれかを使用して再追加してください。

2 つの Kiro アカウントを並行して追加するための詳細および手順については、
[`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md)を参照してください。

## クラウドの問題

### クラウド同期エラー

1. `BASE_URL` が実行中のインスタンスを指していることを確認します（例：`http://localhost:20128`）
2. `CLOUD_URL` がクラウドエンドポイントを指していることを確認します（例：`https://omniroute.dev`）
3. `NEXT_PUBLIC_*` の値をサーバー側の値と一致させます

### クラウドで `stream=false` を指定すると 500 が返される

**症状：** 非ストリーミング呼び出しで、クラウドエンドポイントから `Unexpected token 'd'...` が返されます。

**原因：** クライアントは JSON を想定していますが、アップストリームが SSE ペイロードを返しています。

**回避策：** クラウドへの直接呼び出しでは `stream=true` を使用します。ローカルランタイムには SSE→JSON フォールバックが含まれています。

### クラウドでは接続済みと表示されるが「Invalid API key」となる

1. ローカルダッシュボード（`/api/keys`）から新しいキーを作成します
2. クラウド同期を実行します：Cloud を有効化 → Sync Now
3. 古いキーや同期されていないキーでは、クラウドで引き続き `401` が返される場合があります

## Docker の問題

### Docker の IPv6 / 接続リセット

<a name="docker-ipv6"></a>

**症状：** `curl http://localhost:20128/v1/models` を実行すると、`curl: (56) Recv failure: Connection reset by peer` が返されます。ダッシュボードと認証不要のエンドポイントは動作しますが、認証が必要なエンドポイントは失敗します。認証の問題に見えますが、実際にはそうではありません。

**原因：** `docker run -p 20128:20128` は `0.0.0.0`（IPv4）と `::`（IPv6）の両方でポートを公開しますが、コンテナ内のプロセスは IPv4 でのみリッスンしています。`localhost` が最初に `::1` に解決されるホストでは、接続先が IPv6 の公開ポートになりますが、その背後にリスナーがないため、接続がリセットされます。

**修正方法：**

1. **簡易診断：** `curl -4 http://localhost:20128/v1/models` を実行します。`-4` を指定すると動作し、指定しないと失敗する場合は、IPv6 のバインド不一致が発生しています。
2. **恒久的な修正：** `docker run` コマンドで `-p 127.0.0.1:20128:20128` を使用し、IPv4 に明示的にバインドします：
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   これにより IPv4 へのバインドが強制され、ホストのすべてのインターフェースでプロキシが公開されることも回避できます。

1. Dashboard → Usage で使用状況を確認します
2. プライマリモデルを GLM/MiniMax に切り替えます
3. 重要度の低いタスクには無料枠（Qoder、Kiro）を使用します
4. API キーごとにコスト予算を設定します：Dashboard → API Keys → Budget

## デバッグ

### ログファイルを有効にする

`.env` ファイルで `APP_LOG_TO_FILE=true` を設定します。アプリケーションログは `logs/` 配下に書き込まれます。
設定で呼び出しログパイプラインが有効になっている場合、リクエストのアーティファクトは `${DATA_DIR}/call_logs/` 配下に保存されます。
パイプラインキャプチャが有効な場合、ストリームチャンクのペイロードを除外するには `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` を設定します。または、アーティファクトの上限（KB）を変更するには `CALL_LOG_PIPELINE_MAX_SIZE_KB` を調整します。

### プロバイダーの正常性を確認する

```bash
# ヘルスダッシュボード
http://localhost:20128/dashboard/health

# API ヘルスチェック
curl http://localhost:20128/api/monitoring/health
```

### ランタイムストレージ

- メイン状態：`${DATA_DIR}/storage.sqlite`（プロバイダー、コンボ、エイリアス、キー、設定）
- 使用状況：`storage.sqlite` 内の SQLite テーブル（`usage_history`、`call_logs`、`proxy_logs`）+ オプションの `${DATA_DIR}/call_logs/`
- アプリケーションログ：`<repo>/logs/...`（`APP_LOG_TO_FILE=true` の場合）
- 呼び出しログのアーティファクト：呼び出しログパイプラインが有効な場合は `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs ページの **Clean history** 操作を実行すると、`call_logs`、従来の
`request_detail_logs`、およびローカルの `${DATA_DIR}/call_logs/` アーティファクトディレクトリが消去されます。

## サーキットブレーカーの問題

### プロバイダーが OPEN 状態のままになる

プロバイダーのサーキットブレーカーが OPEN の場合、クールダウンが終了するまでリクエストはブロックされます。

**修正方法:**

1. **ダッシュボード → 設定 → レジリエンス**に移動します
2. 影響を受けているプロバイダーのサーキットブレーカーカードを確認します
3. **すべてリセット**をクリックしてすべてのブレーカーをクリアするか、クールダウンが終了するまで待ちます
4. リセットする前に、プロバイダーが実際に利用可能であることを確認します

### プロバイダーでサーキットブレーカーが繰り返し作動する

プロバイダーが繰り返し OPEN 状態になる場合:

1. **ダッシュボード → ヘルス → プロバイダーのヘルス**で障害パターンを確認します
2. **設定 → レジリエンス → プロバイダープロファイル**に移動し、障害しきい値を引き上げます
3. プロバイダーが API 制限を変更していないか、または再認証が必要になっていないか確認します
4. レイテンシのテレメトリを確認します。レイテンシが高いと、タイムアウトによる障害が発生する可能性があります

## 音声文字起こしの問題

### 「Unsupported model」エラー

- 最初のセグメントが、認証情報を設定済みのプロバイダーになっているモデル ID を使用してください（`openai/whisper-1`、`openrouter/deepgram/nova-3`）。単独の `deepgram/nova-3` を使用するには、ネイティブの Deepgram キーが必要です。

- プロバイダーカードでプロバイダー API キーが有効であることを確認します

## トランスレーターのデバッグ

形式変換の問題をデバッグするには、**ダッシュボード → トランスレーター**を使用します:

| モード               | 使用する場面                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| **プレイグラウンド** | 入出力形式を並べて比較します。失敗するリクエストを貼り付けて、どのように変換されるか確認できます |
| **チャットテスター** | ライブメッセージを送信し、ヘッダーを含む完全なリクエスト/レスポンスペイロードを確認します        |
| **テストベンチ**     | 形式の組み合わせに対してバッチテストを実行し、どの変換に問題があるかを特定します                 |
| **ライブモニター**   | リアルタイムのリクエストフローを監視し、断続的に発生する変換の問題を検出します                   |

### 一般的な形式の問題

- **Thinking タグが表示されない** — 対象プロバイダーが Thinking をサポートしているか、および Thinking の予算設定を確認してください
- **ツール呼び出しが欠落する** — 一部の形式変換では、サポートされていないフィールドが削除される場合があります。プレイグラウンドモードで確認してください
- **システムプロンプトが欠落する** — Claude と Gemini ではシステムプロンプトの処理方法が異なります。変換後の出力を確認してください
- **SDK がオブジェクトではなく生の文字列を返す** — v1.x で解決済みです。レスポンスサニタイザーが、OpenAI SDK の Pydantic 検証エラーを引き起こす非標準フィールド（`x_groq`、`usage_breakdown` など）を削除します。v3.x+ でもこの問題が発生する場合は、issue を作成してください。
- **GLM/ERNIE が `system` ロールを拒否する** — v1.x で解決済みです。ロールノーマライザーが、互換性のないモデル向けにシステムメッセージをユーザーメッセージへ自動的に統合します。v3.x+ でもこの問題が発生する場合は、issue を作成してください。
- **`developer` ロールが認識されない** — v1.x で解決済みです。OpenAI 以外のプロバイダーでは、自動的に `system` に変換されます。v3.x+ でもこの問題が発生する場合は、issue を作成してください。
- **`json_schema` が Gemini で機能しない** — v1.x で解決済みです。現在は `response_format` が Gemini の `responseMimeType` + `responseSchema` に変換されます。v3.x+ でもこの問題が発生する場合は、issue を作成してください。

## 耐障害性設定

### 自動レート制限が作動しない

- 自動レート制限は API キープロバイダーにのみ適用されます（OAuth/サブスクリプションには適用されません）
- **設定 → 耐障害性 → プロバイダープロファイル**で自動レート制限が有効になっていることを確認してください
- プロバイダーが `429` ステータスコードまたは `Retry-After` ヘッダーを返しているか確認してください

### 指数バックオフの調整

プロバイダープロファイルでは、以下の設定がサポートされています。

- **基本遅延** — 最初の失敗後の初期待機時間（デフォルト: 1s）
- **最大遅延** — 待機時間の上限（デフォルト: 30s）
- **乗数** — 連続して失敗するたびに遅延を増加させる倍率（デフォルト: 2x）

### サンダリングハード対策

レート制限のあるプロバイダーに多数の同時リクエストが送信された場合、OmniRoute は mutex と自動レート制限を使用してリクエストを直列化し、連鎖的な障害を防止します。これは API キープロバイダーに対して自動的に適用されます。

### チャットリクエストが 503 / chat_admission_busy で失敗する

**症状:**

- チャット補完エンドポイントが、エラーコード
  `chat_admission_busy` を含む再試行可能な `503` レスポンスを返します。
- レスポンスには `Retry-After` が含まれます。#12135 以降、この値は観測された
  占有状況から算出されます。つまり、リクエストがすでに待機した `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  の時間枠と、現在の重量級リースが保持されている時間のうち大きい方を秒単位に
  切り上げ、最大 60 秒に制限します。ゲートがアイドル状態の場合は、従来の下限値が維持されます。
  バイトベースのパスでは 2 秒、構造ベースのパスでは 1 秒です（後者には
  `reason: "structure_limit"` も含まれます）。
- これは、別の重量級チャットまたは長時間実行されるストリーミングレスポンスがまだ
  処理中の場合に発生する可能性があります。

バイトベースのレスポンス本文は次のとおりです。

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

構造ベースのレスポンスでは、同じタイプとコードが使用され、メッセージは
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
となり、`reason: "structure_limit"` が含まれます。
デフォルトのしきい値では、メッセージ数が `200` 以上、ツール数が `64` 以上、
推定トークン数が `32,000` 以上のいずれかに該当する場合、または境界付き構造推定が
訪問ノード数 `10,000` または深度 `12` の上限に達した場合に、リクエストは構造的に重量級と見なされます。

**原因:** これは OmniRoute 内部で意図的に行われる負荷制限であり、アップストリームプロバイダーの障害ではありません。
各プロセスは、プロセスローカルなガードを使用して、大きなリクエスト本文を保持および解析する前に、
制限された重量級処理容量を予約します。重量級リースは、SSE
レスポンスの存続期間中、保持され続けます。

**#503 の多発:** この修正以前は、ホストのメモリ容量に関係なく、ガードが同時実行数を固定のリクエスト数
（`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`、デフォルト `1`）に制限していたため、コーディングエージェントの
ファンアウト（複数のサブエージェント/CLI、本文は通常 256 KB 超）では実効同時実行数が
約 1 まで低下し、完全に通常の負荷でも 503 が発生していました。現在、ガードは自動調整されます。
プロセスの実際のメモリ上限に基づいて算出される、取り込み用の自動導出バイト予算
（`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`）によって制御され、さらにリアルタイムのリソース圧迫シグナルも
参照します。そのため、複数の重量級リクエストが同時に到着したというだけではなく、ホストが実際に
メモリ不足に陥っている場合にのみ負荷を制限します。従来のリクエスト数上限
（`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`）も引き続き尊重されますが、明示的に設定した場合に限られます。

容量が使用中の場合、重量級リクエストは再試行可能な `503` を返す前に、スロットが空くまで
最大 `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`（デフォルト `2000`、`0` で待機を無効化）の間、まず待機します。
この制限付き待機は、重量級のサブリクエストを同時にファンアウトするエージェント型クライアント
（OpenCode、Claude Code、Cursor）が、即時拒否によって再試行回数をすべて使い果たし、
タスクの途中で停止するのではなく、バーストを直列化できるようにするためのものです。
現在の重量級リースの占有状況、確定したバイト予算、およびリアルタイムの圧迫度は、
`GET /api/monitoring/health` → `chatAdmission`（`inflightBytes`、`maxInflightBytes`、
`budgetSource`、`pressureSeverity`、`countCapEnabled`）で確認できます。環境変数を変更する前に、これらを確認してください。
設定 → 耐障害性 → リクエストキュー → 同時リクエスト数では、この動作を制御できません。この設定が
制御するのは、別のプロバイダーリクエストキュー機構です。

**修正方法:**

1. まず再試行してください。クライアントはリクエストを即座に繰り返すのではなく、
   `Retry-After` に従い、バックオフを使用する必要があります。
2. 何かを調整する前に、`/api/monitoring/health` → `chatAdmission` を確認してください。`countCapEnabled:
false` で `maxInflightBytes` が十分に大きい場合、自動導出された予算はすでに
   正常に機能しています。`pressureSeverity` が `high`/`critical` の場合、ホストのメモリが実際に
   不足しています。これはアドミッション関連の環境変数では修正できず、RAM の増設またはワークロードの縮小が必要です。
3. `/api/monitoring/health` によって、自動導出された予算が実際にホストに対して小さすぎることが
   示された場合に限り（これはまれです。コンテナからベアメタルまで、すでにスケーリングされます）、
   従来のリクエスト数上限に戻すのではなく、`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` で直接上書きしてください。

正式なアドミッション設定については、[環境変数リファレンス](../reference/ENVIRONMENT.md#4-security--authentication)
を参照してください。

## オプションの RAG / LLM 障害分類（16 の問題）

一部の OmniRoute ユーザーは、RAG またはエージェントスタックの前段にゲートウェイを配置しています。このような構成では、奇妙なパターンがよく見られます。OmniRoute は正常に見える（プロバイダーは稼働中、ルーティングプロファイルも正常、レート制限アラートもなし）にもかかわらず、最終的な回答が依然として誤っているというものです。

実際には、こうしたインシデントは通常、ゲートウェイ自体ではなく、後段の RAG パイプラインに起因します。

これらの障害を説明するための共通用語が必要な場合は、WFGY ProblemMap を利用できます。これは、繰り返し発生する 16 種類の RAG / LLM 障害パターンを定義した、MIT ライセンスの外部テキストリソースです。概要として、次の内容を扱っています。

- 検索のドリフトとコンテキスト境界の破綻
- 空または古くなったインデックスとベクトルストア
- 埋め込みとセマンティクスの不一致
- プロンプト構築とコンテキストウィンドウの問題
- 論理の崩壊と過度に自信のある回答
- 長いチェーンとエージェント連携の障害
- マルチエージェントのメモリとロールのドリフト
- デプロイとブートストラップ順序の問題

考え方はシンプルです。

1. 不適切なレスポンスを調査する際は、次の情報を記録します。
   - ユーザーのタスクとリクエスト
   - OmniRoute で使用したルートまたはプロバイダーの組み合わせ
   - 後段で使用された RAG コンテキスト（検索されたドキュメント、ツール呼び出しなど）
2. インシデントを 1 つまたは 2 つの WFGY ProblemMap 番号（`No.1` … `No.16`）に分類します。
3. OmniRoute のログと併せて、その番号を独自のダッシュボード、ランブック、またはインシデントトラッカーに保存します。
4. 対応する WFGY ページを使用して、RAG スタック、リトリーバー、またはルーティング戦略のどれを変更する必要があるか判断します。

全文と具体的な手順はこちらにあります（MIT ライセンス、テキストのみ）。

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute の後段で RAG またはエージェントパイプラインを実行していない場合、このセクションは無視できます。

## v3.8.0 の既知の問題

v3.8.0 リリース固有の問題と、現在の回避策です。修正が後続のパッチに含まれた場合、この項目は更新または削除されます。

### Devin CLI の認証失敗

**症状：**

- Devin ベースのツールを呼び出すと、「Devin CLI が見つかりません」または「認証に失敗しました」と表示される
- CLI ランタイムチェックで `installed=false` と報告される

**原因：**

- `CLI_DEVIN_BIN` が存在しないパスを指している
- ホストに Devin CLI がインストールされていない

**修正方法：**

1. 使用しているプラットフォーム向けの Devin CLI をインストールします
2. `.env` に `CLI_DEVIN_BIN=/usr/local/bin/devin`（または実際のパス）を設定します
3. OmniRoute を再起動し、**ダッシュボード → CLI ツール**から再テストします

### モデルのクールダウンが解除されない（手動リセット）

**症状：**

- 有効期限が過ぎた後も、モデルがクールダウン中として表示され続ける
- タイムスタンプが過去になっているにもかかわらず、組み合わせルーティングでリクエストが引き続きそのモデルをスキップする

**手動リセット：**

- **ダッシュボード：** **設定 → モデルのクールダウン** → 影響を受けているカードで **再有効化**をクリックします
- **API：** 管理認証ヘッダーを指定して `DELETE /api/resilience/model-cooldowns` を実行します

### Command Code プロバイダーへの接続が 403 で失敗する

**症状：**

- Command Code プロバイダーへの接続テスト時に 403 が発生する
- 新規追加後、プロバイダーカードに「未認証」と表示される

**原因：** OAuth フローが完了していません（コールバックを受信していない、またはトークンが保存されていない）。

**修正方法：**

- CLI から `omniroute providers` を実行して OAuth フローを再度開始するか、
- **ダッシュボード → プロバイダー → Command Code → 再接続**から OAuth を再実行します

### ModelScope が過度に長い 429 クールダウンを返す

**症状：**

- 少数のリクエストを短時間に送信しただけで、ModelScope が非常に短時間のうちに、または即座にクールダウン状態になる
- 組み合わせルーティングが予想より早く ModelScope をスキップする

**原因：** ModelScope はプロバイダー固有の `Retry-After` ヘッダーを送信します。v3.8.0 にはこれらのヘッダー専用の処理が含まれているため、古いバージョンでは汎用的なレート制限のヒントとして誤って解釈されます。

**修正方法：**

- v3.8.0 以降を使用していることを確認します
- **設定 → レジリエンス**で `useUpstream429BreakerHints` トグルが有効になっていることを確認します

### 本番環境で OMNIROUTE_WS_BRIDGE_SECRET が設定されていない

**症状：**

- リモートの本番ホストで実行している場合、Codex/Responses WebSocket ブリッジへのすべてのリクエストで 401 が発生する
- WebSocket ブリッジのハンドシェイクが接続直後に終了する

**原因：** 本番環境に `OMNIROUTE_WS_BRIDGE_SECRET` 環境変数が設定されていません。

**修正方法：**

1. ランダムなシークレットを生成します：`openssl rand -hex 32`
2. 本番サーバーの環境（およびブリッジと通信するすべてのクライアント）に `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` を設定します
3. OmniRoute を再起動します

### Responses API：バックグラウンドモードが同期実行に縮退する

**症状：**

- 警告がログに記録される：`background mode degraded to synchronous`
- `background: true` を指定したリクエストが、バックグラウンドジョブのハンドルではなく、通常の同期レスポンスを返す

**原因：** v3.8.0 では、Responses API の `background: true` は意図的に同期実行へ縮退し、その際に警告が出力されます。完全な非同期バックグラウンド実行は、今後提供される予定です。

**修正方法：**

- `background` を指定せずに呼び出すようクライアントを調整するか、
- 完全な非同期バックグラウンドモードが提供される後続リリースを待ちます（変更履歴を確認してください）

## 起動の遅延 / 準備完了タイムアウト

CLI に `⚠ Server did not respond within 60s` と表示されてもサーバーが実際には動作している場合、お使いの環境に対して準備完了プローブの待機時間が短すぎます。

これは、Windows（ウイルス対策ソフト、ファイルシステム監視）や、起動時の負荷が高いコンテナでよく発生します。

**修正方法 — 待機時間を延長する:**

```bash
# 環境変数で設定（次回以降の起動でも維持）:
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 分
omniroute serve

# CLI フラグで設定（今回のみ）:
omniroute serve --ready-timeout 180000
```

デフォルトは 60 000 ms（60 秒）です。この警告は情報提供のみを目的としています。サーバーはバックグラウンドで起動を続け、起動が完了するとアクセス可能になります。

`OMNIROUTE_READY_TIMEOUT_MS` の詳細については、[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md)を参照してください。
