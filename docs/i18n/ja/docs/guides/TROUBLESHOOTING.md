### 無料プロバイダーでのレート制限（429 / 400 / 401）

**症状**：無料または認証不要のプロバイダー（opencode、auggie など）で `model: "auto"` を使用すると、回答の代わりに `HTTP 429`、`400`、または `401` が断続的に返されます。少し時間を置いて同じプロンプトを再試行するとリクエストは成功しますが、自動化処理（cron ジョブ、エージェント、スクリプト）は最初の失敗時点で停止します。

**根本原因**：次の 3 つの独立した障害モードが重なっています。

1. **プロバイダーのレート制限（`429`）**：無料枠では、時間枠ごとのクォータが適用される場合があります。並列呼び出しが集中するとクォータを使い果たし、時間枠がリセットされるまで後続のリクエストが拒否されます。
2. **パススルー内の機能しないモデル（`400`/`401`）**：`auto/*` プールには、カタログに登録されていても有効な認証情報を持たない `opencode` のパススルーモデルが含まれる場合があります（例：`oc/north-mini-code-free` → `401`）。自動ルーターがそのうちの 1 つを試して失敗すると、フォールバックが作動する前にエラーが伝播します。
3. **並行処理による増幅（負荷時の `429`）**：複数のエージェントまたは cron セッションが同時に `auto` にアクセスすると、リクエスト総数が無料プロバイダーの許容量を超え、正当な呼び出しも不正利用として判定されます。

**検証済みの修正方法（コミュニティ報告、2026-08-10）**：3 つの環境変数を調整し、無料枠の不安定さによって処理が停止するのではなく、ローテーション、並行処理、およびフォールバックによって吸収されるようにします。

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 の場合は別のモデルまたはプロバイダーへ移行する（機能しないパススルーモデルをスキップ）
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # 高負荷リクエストの明示的な受け入れ上限（デフォルトでは未設定：リクエスト数の上限なし。以下の注記を参照）
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # 低速なアップストリーム向けに、制限付き待機時間を RATE_LIMIT_MAX_WAIT_MS のデフォルト値より長くする
```

これらを OmniRoute プロセスの環境（デーモン。例：LaunchAgent plist または `systemctl edit`）に設定してから、OmniRoute を再起動してください。ローテーションフラグは、最も大きな効果をもたらす単一の設定です。ハードエラーを、プール内の正常なプロバイダーに対する透過的な再試行へと変換します。

**注記**：`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` は、同時に実行される高負荷（長いコンテキスト）のリクエスト数を制限します。この上限は受け入れゲートであり、プロバイダーのレートリミッターではありません。**#503-fanout 更新：**この変数はデフォルトでは設定されなくなりました（上記のように明示的に設定した場合にのみ適用されます）。代わりに、高負荷リクエストの受け入れは、ホストの実際のメモリ上限に基づいて自動調整されるバイト予算（`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`）によって制御されます。そのため、新規デプロイでは、この変数をまったく設定しなくても `503 chat_admission_busy` による拒否が大幅に減少するはずです。ここで明示的に設定した場合も、記載どおりに機能します。バイト予算を明示的に上書きする場合、値は 8 MiB～2 GiB に制限されます。`413 body_exceeds_budget` は一時的なエラーではありません。そのバイト予算を増やすか、`OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` を下げるか、プロセスのメモリ上限を増やしてください。`inflight_bytes_budget` による負荷制御は一時的な競合であり、引き続き再試行できます。プロバイダーごとのレート制限（`open-sse/services/rateLimitManager.ts`）は、`RATE_LIMIT_MAX_WAIT_MS`、`RATE_LIMIT_MAX_QUEUE_DEPTH`、および `RATE_LIMIT_AUTO_ENABLE` によって個別に管理されます。詳細については `.env.example` を参照してください。

**動作確認方法**: エージェント/cron を短時間に続けて2回実行し、両方が成功することを確認してください。修正前は、通常2回目の実行で `429`/`401` が発生します。修正後は、失敗した場合でも透過的に再試行され、呼び出しが完了します。また、`curl /monitoring/health` を実行し、プロバイダー接続の `rateLimitedUntil` フィールドと、影響を受けるプロバイダーの `circuitBreakers.providerBreakers[].state` を監視することもできます。状態は `CLOSED`、`DEGRADED`、`OPEN`、`HALF_OPEN` のいずれかです（`src/shared/utils/circuitBreaker.ts` を参照）。失敗し続けるプロバイダーは、リセット期間後にプローブが許可される（`HALF_OPEN`）まで、`CLOSED → DEGRADED → OPEN` と遷移します。

**それでも 429 が表示される場合**: そのプロバイダーで現在使用中のアカウントが、単なるレート制限ではなく実際に _クォータ_ を使い果たしています。OmniRoute ダッシュボードの Providers → Accounts で同じプロバイダーの2つ目のアカウントを追加するか、別の無料プロバイダー（例: `routeway`、`auggie`）を併用してください。ローテーションが有効なのは一時的なレート制限/400/401 に対してのみです。クォータを完全に使い果たした場合は、2つ目の認証情報または別のプロバイダーが必要です。

**ビジョンモデル（`auto/vision`、`bazaarlink/*`）で 403 が表示される場合**: 接続されているアカウントにビジョン機能を含む有料プランがないか、API キーの権限が不足しています。プロバイダーのダッシュボードで、キーのスコープにビジョン/マルチモーダルが含まれていることを確認するか、有料プランのアカウントを接続してビジョン用のターゲットとして設定してください。

## npm install の警告（ERESOLVE / peer / deprecated）

`npm install -g omniroute` を実行すると、`npm warn ERESOLVE`、peer dependency に関する通知、`deprecated` メッセージなど、大量の警告が表示される場合があります。**これらは想定内であり、問題ありません。** 出力に `added <N> packages` と表示されていれば、インストールは成功しています。

peer dependency の解決に関する警告を抑制するには、OmniRoute がサポートする次のインストール形式を使用してください。

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` が抑制するのは、`ERESOLVE` と peer dependency に関する通知のみです。非推奨に関する通知は推移的なサードパーティパッケージから発生するため、引き続き表示されますが、インストールの失敗を示すものではありません。

これらの警告は、OmniRoute が管理していないサードパーティパッケージの古い peer dependency のバージョン範囲が原因です。

1. **`marked-terminal` は `marked >=1 <16` を要求しているが、`marked@18` が検出された** — 実際には問題なく動作します。アップストリームの peer dependency のバージョン範囲が古いだけです。
2. **`deprecated prebuild-install@7.1.3`** — 推移的に依存している、ネイティブバイナリ取得用のヘルパーです。固定バージョンの `wreq-js` トランスポートバインディングのインストールには
   使用されておらず、Web Cookie プロバイダーのトランスポート設定が失敗したことを示すものでも
   ありません。

**対応は不要です** — アップストリームパッケージをフォークしない限り、これらの警告を完全に非表示にすることはできません。

## npm install-scripts のブロック警告（グローバルインストール）

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` を実行すると、新しいバージョンの npm（v11+ および v12+）では、パッケージのライフサイクルスクリプトがデフォルトでブロックされ、install-scripts 警告が表示されます。

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### この警告は無視できますか？

**一部は無視できますが、スクリプトを実行せずに使用することは推奨されません。** OmniRoute には適切なフォールバック機能があります。スタンドアロンバンドルからネイティブの `better-sqlite3` バインディングを読み込めない場合、アプリケーションは `node:sqlite` や `sql.js` などの代替ドライバーにフォールバックします（[SQLite ランタイムの解決](../ops/SQLITE_RUNTIME.md)を参照）。サーバーは引き続き起動しますが、`sql.js` のような WASM フォールバックで実行すると、SQLite の WAL（Write-Ahead Logging）モードが無効になり、メモリ使用量とディスク同期のオーバーヘッドが増加します。

### 実際に必要なスクリプトはどれですか？

ブロックされるすべてのスクリプトが、OmniRoute の実行に不可欠というわけではありません。

- **必須（`omniroute`、`better-sqlite3`）：** OmniRoute は Next.js のスタンドアロンアプリケーションバンドル（`dist/`）から実行されます。インストール中に、npm はホスト固有のネイティブ SQLite ドライバーをトップレベルの `node_modules/better-sqlite3/` にダウンロードまたはコンパイルします。その後、OmniRoute の `postinstall` スクリプト（`scripts/build/postinstall.mjs`）が、これらのホスト固有バイナリを検証して `dist/node_modules/` にコピーし、スタンドアロンサーバーからアクセスできるようにします。`omniroute` の postinstall スクリプトがブロックされると、このコピー処理はスキップされます。
- **任意／推移的（`keytar`、`@parcel/watcher`、`@swc/core`、`protobufjs`、`esbuild`）：** これらはビルドヘルパー、監視ツール、またはシステムキーチェーン用ユーティリティです。許可するとビルド警告を防げますが、コアルーティング機能には必要ありません。
- **除外（`onnxruntime-node`）：** ローカル AI 埋め込み用の任意依存関係であり、OmniRoute の実行には**必要ありません**。その postinstall スクリプトは、NuGet から約 300MB の CUDA アセットをダウンロードします。サポート対象のハードウェアでローカル ONNX アクセラレーションを使用する明確な意図がない限り、許可リストに含めないでください。

### 推奨される修正方法

グローバルインストール時に必要なインストールスクリプトを許可し、警告を非表示にするには、OmniRoute とそのネイティブ依存関係を指定した `--allow-scripts` を渡します。

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

または、ユーザーアカウントで行うすべてのグローバルインストールに対して恒久的に設定するには、次を実行します。

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### インストールの確認

インストール後、組み込みの診断ツールを実行し、ネイティブバインディングとランタイム環境が正常であることを確認してください。

```bash
omniroute doctor
```

## Gemini Web と Playwright Chromium

Gemini Web リクエストが、Playwright Chromium がインストールされていないというメッセージとともに `503` を返す場合、npm パッケージは存在しますが、ブラウザバイナリがありません。Playwright では、ブラウザのダウンロードを意図的に npm パッケージのインストールとは分離しているため、ブラウザをインストールするまではこのレスポンスが返されます。

npm をグローバルインストールしている場合は、ブラウザキャッシュが同じ Playwright インストールに属するように、OmniRoute パッケージのディレクトリから Chromium をインストールします。

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

インストール後に OmniRoute を再起動し、Gemini Web リクエストを再試行してください。Docker イメージから OmniRoute を実行する場合は、Chromium とその依存関係が同梱されている `-web` イメージ（または `runner-web` ビルドターゲット）を使用してください。ベースイメージには含まれていません。

## アンチウイルスソフトによる誤検知

<a name="antivirus-false-positives"></a>

### Avast/AVG が `README.md` を `MD:HttpRequest-inf[Susp]` として隔離する

**これは誤検知です。何も感染しておらず、対応は不要です。**

Avast と AVG は、HTTP リクエストのように見えるリンクを多数含むプレーンテキスト/Markdown ファイルを
検出するヒューリスティックを実行します。OmniRoute の `README.md` は npm パッケージ内に同梱され
（`package.json` → `files` に記載されています）、グローバルインストール時に
`node_modules/omniroute/README.md` に配置されます。また、このファイルには約15個の
`http://localhost:20128/...` の例（MCP HTTP/SSE エンドポイント、A2A `.well-known` URL、
および `curl` スニペット）が含まれています。このリンク密度だけでヒューリスティックの検出条件を
満たしてしまいます。

この問題が最近になって発生し始めた場合でも、ファイルの性質が変わったわけではありません。README の
エンドポイント表が拡充され（MCP HTTP + SSE + A2A が追加され）、`curl` の例も増えたことで、
しきい値を超えただけです。

このファイルは実行可能な内容を一切含まない、無害なドキュメントです。隔離から安全に復元できます。

**対処方法：**

1. **通知を停止する** — アンチウイルスソフトでインストールディレクトリを除外し
   （Avast: 設定 → 例外）、グローバル `node_modules` のパスや
   OmniRoute のデータディレクトリ（`~/.omniroute/`）を追加してください。
2. **誤検知を報告する** — <https://www.avast.com/false-positive-file-form.php> から、
   隔離された `README.md` を添付して報告してください。これはベンダーのヒューリスティックが
   テキストファイルに過剰反応している問題であるため、この対応がすべてのユーザーに役立つ解決策となります。

**こちら側で「修正」しない理由：** 例はすべて `http://localhost` であり、
自己署名証明書に伴う煩雑さなしに localhost を `https` にすることはできません。あるベンダーの
ヒューリスティックを回避するためにドキュメントを不自然に改変すると、スキャナーの不具合に合わせる代わりに
すべての読者の利便性を損なうことになります。

### Kaspersky がデスクトップアプリを `PDM:Trojan.Win32.Generic` として検出する

**これは動作ヒューリスティックによる誤検知です。何も感染していません。** Kaspersky の
`PDM:` プレフィックスは、その判定が既知のマルウェアとの照合ではなく、インストーラーの
_動作_ を評価する Proactive Defense Module（System Watcher）によるものであることを意味します。
検出が発生すると、Kaspersky はインストール全体を「ロールバック」し、すでに書き込まれたファイルも
削除するため、アプリが破損したり消失したりします。

検出されるファイルは、デスクトップアプリに同梱された、明示済みのオープンソース依存関係に含まれる
標準的な構成要素です。例：

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` および
  `workerProcessEntry.js` — [Playwright](https://playwright.dev)。アプリ内でのプロバイダーログインと、
  ブラウザーを利用したチャットに使用されるブラウザー自動化ライブラリです。
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — Web Cookie を使用するプロバイダーで、ブラウザーのフィンガープリントを模倣した HTTP 通信に使用する、
  バージョン固定済みの `wreq-js` ネイティブバインディングです（`<arch>` は `x64` または `arm64`）。

**検出される理由：** Windows インストーラーは**まだコード署名されていない**ため、署名のない NSIS
インストーラーにはレピュテーションがまったくなく、動作ヒューリスティックが最も厳しい設定で実行されます。
さらに、同梱されたネイティブ DLL と、`%LOCALAPPDATA%\Programs\OmniRoute` 配下に書き込まれる
数百個の `.js` ファイル（Next.js スタンドアロンビルドによるハッシュサフィックス付きのパッケージ
ディレクトリを含む）が組み合わさることで、ヒューリスティックの検出条件を満たしてしまいます。
コード署名は予定されていますが、導入されるまでは新しいリリースでもこの問題が繰り返される可能性があります。

**対処方法：**

1. **まずダウンロードを検証する**（ファイルが改ざんされていないことを確認します）。各リリースでは、
   `OmniRoute.Setup.<version>.exe` インストーラー全体を対象とした base64 形式の `sha512`
   フィールドを含む `latest.yml` が公開されています。PowerShell で、インストーラーがある
   フォルダーから次を実行してください：
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   出力は `latest.yml` → `sha512` と一致する必要があります。一致しない場合はファイルを削除し、
   [GitHub リリースページ](https://github.com/diegosouzapw/OmniRoute/releases)からのみ再ダウンロードしてください。
2. **復元して除外する** — ロールバックされて隔離された項目を復元し、
   `%LOCALAPPDATA%\Programs\OmniRoute` を除外対象に追加して（Kaspersky → 設定 → 脅威と除外）、
   再インストールしてください。
3. **誤検知を報告する** — <https://opentip.kaspersky.com/>。ユーザーが送信する誤検知報告は、
   実際に許可リストへの登録を迅速化します。

## Node.js の互換性

<a name="nodejs-compatibility"></a>

### ログインページがクラッシュする、または「Module self-registration」エラーが表示される

**原因:** OmniRoute が承認している安全なランタイムの最低要件を満たしていない Node.js バージョンを実行しています。最も一般的なケースは、OmniRoute が必須としているセキュリティ修正済みの最低バージョンを下回る、古い Node 22 または 24 のパッチバージョンを実行している場合です。

**症状:**

- ログインページに何も表示されない、またはサーバーエラーが表示される
- コンソールに `Error: Module did not self-register` または同様のネイティブバインディングエラーが表示される
- ランタイムがサポート対象のセキュリティポリシー範囲外の場合、ログインページに使用中の Node バージョンを示す**オレンジ色の警告バナー**が表示される

**修正方法:**

1. サポート対象の Node.js LTS リリースをインストールします（推奨: Node.js 24.x）。
   ```bash
   nvm install 24
   nvm use 24
   ```
2. バージョンを確認します。`node --version` で、24.x LTS 系列の `v24.0.0` 以降が表示される必要があります
3. OmniRoute を再インストールします: `npm install -g omniroute`
4. 再起動します: `omniroute`

> **サポート対象の安全なバージョン:** `>=22.22.2 <23` または `>=24.0.0 <27`。Node.js 24.x LTS (Krypton) および Node.js 26 は完全にサポートされています。

### npm v11+: `better-sqlite3` がインストールされない（Cannot find module）

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**原因:** npm v11（Node.js 24+ に同梱）は、オプション依存関係のインストールスクリプトをデフォルトでブロックします。`better-sqlite3` は `optionalDependencies` に記載されており、ネイティブコンパイル（`node-gyp rebuild`）を必要とするため、npm によって警告なしにスキップされます。

**症状:**

- サーバーが起動時に `Cannot find module 'better-sqlite3'` エラーでクラッシュする
- `ls node_modules/better-sqlite3` で「No such file or directory」と表示される
- `npm ls better-sqlite3` で `(empty)` と表示される

**修正方法:**

1. インストールスクリプトを承認し、再インストールします。
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. または、ビルド済みパッケージを手動でインストールします。
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. 正常に動作することを確認します: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / 「slice is not valid mach-o file」

<a name="macos-native-module-rebuild"></a>

**原因:** グローバルで `npm install -g omniroute` を実行した後、パッケージ内の `better-sqlite3` ネイティブバイナリが、ローカルで実行されているものとは異なるアーキテクチャまたは Node.js ABI 向けにコンパイルされている場合があります。これは、ビルド済みバイナリが環境と一致しない場合に、macOS（Apple Silicon と Intel の両方）でよく発生します。

**症状:**

- サーバーが起動直後に `dlopen` エラーで停止する
- エラーに `slice is not valid mach-o file` が含まれる
- 完全な例:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**修正方法 — ローカル環境向けに再ビルドします（Node.js のダウングレードは不要です）:**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **注:** これにより、ローカルの Node.js バージョンおよび CPU アーキテクチャに合わせてネイティブバインディングが再コンパイルされ、バイナリの不一致が解消されます。公式にサポートされているランタイム範囲は **`>=22.22.2 <23` または `>=24.0.0 <27`** です（`src/shared/utils/nodeRuntimeSupport.ts` の `SUPPORTED_NODE_RANGE`。`package.json` の `engines` フィールドと整合しています）。Node.js 24.x LTS (Krypton) および Node.js 26 は、`better-sqlite3` v12.x で完全にサポートされています。

## プロキシの問題

<a name="proxy-issues"></a>

### プロバイダーの検証で「fetch failed」と表示される

**原因:** API キー検証エンドポイント（`POST /api/providers/validate`）が以前はプロキシ設定を経由していなかったため、プロキシ経由のルーティングが必要な環境でエラーが発生していました。

**修正（v3.5.5+）:** この問題は修正済みです。プロバイダーの検証は `runWithProxyContext` を経由するようになり、プロバイダー単位およびグローバルのプロキシ設定が自動的に適用されます。

### トークンのヘルスチェックが「fetch failed」で失敗する

**原因:** バックグラウンドでの OAuth トークン更新時に、接続ごとのプロキシ設定が解決されていませんでした。

**修正（v3.5.5+）:** トークンのヘルスチェックスケジューラーは、更新を試みる前に接続ごとのプロキシ設定を解決するようになりました。v3.5.5+ にアップデートしてください。

### SOCKS5 プロキシで「invalid onRequestStart method」が返される

**原因:** Node.js 22 では、undici@8 のディスパッチャーは Node の組み込み `fetch()` 実装と互換性がありません。

**修正（v3.5.5+）:** OmniRoute は、プロキシディスパッチャーが有効な場合に undici 独自の `fetch()` 関数を使用するようになり、一貫した動作が保証されます。v3.5.5+ にアップデートしてください。

### WSL 環境の MITM プロキシで Windows ホスト上のデスクトップアプリが傍受されない

**原因:** MITM プロキシとその CA 証明書は、OmniRoute が実行されている環境にインストールされます。WSL 環境では、その環境は Linux ゲストですが、AI デスクトップアプリ（Kiro、Trae、Copilot、Zed、…）は Windows ホスト上で実行されます。ホスト側のアプリはゲスト側の証明書ストアを信頼せず、ゲスト側のシステムプロキシを経由しないため、デスクトップアプリの通信は傍受されません。

**推奨事項:** 傍受対象のデスクトップアプリと同じ OS 上で OmniRoute をネイティブに実行してください（Windows アプリの場合は Windows。macOS/Linux も同様です）。OmniRoute を WSL 内で実行したままホスト側のアプリを対象にするには、生成された CA 証明書を Windows ホスト上で手動で信頼し、各ホストアプリのネットワーク／プロキシ設定で WSL のプロキシエンドポイントを指定する必要があります。この構成はサポート対象外であり、安定性にも欠けます。

## プロバイダーの問題

### 「Language model did not provide messages」

**原因:** プロバイダーのクォータを使い切っています。

**修正:**

1. ダッシュボードのクォータトラッカーを確認する
2. フォールバック階層を持つコンボを使用する
3. より安価な階層または無料階層に切り替える

### レート制限

**原因:** サブスクリプションのクォータを使い切っています。

**修正:**

- フォールバックを追加する: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- 安価なバックアップとして GLM/MiniMax を使用する

### OAuth トークンの有効期限切れ

OmniRoute はトークンを自動更新します。問題が解消しない場合:

1. ダッシュボード → プロバイダー → 再接続
2. プロバイダー接続を削除して再追加する

### Kiro の複数アカウント利用時に、2 つ目のアカウントによって 1 つ目が無効になる

**原因:** Kiro のバックエンドでは、OIDC クライアント登録ごとに有効なセッションが 1 つに制限されています。
2 つのアカウントが同じ登録済みクライアントを共有している場合（v3.8.0 より前にインポートされた接続）、
一方のアカウントのトークンを更新すると、もう一方のリフレッシュトークンが無効になります。

**修正（v3.8.0+）:** 影響を受ける接続を再インポートしてください。
v3.8.0 以降、**Import Token**、
**Google/GitHub ソーシャルログイン**、または **Auto-Import** を使用して作成された新しい Kiro 接続には、それぞれ専用の
OIDC クライアントが自動的に登録されます。これにより接続は完全に分離され、一方の
アカウントを更新しても、他のアカウントには影響しません。

v3.8.0 より_前_にインポートされた接続には、接続ごとのクライアント
登録がありません。これらの接続では、引き続き共有のソーシャル認証更新エンドポイントが使用されます。
接続を分離するには、ダッシュボード → プロバイダーから古い接続を削除し、
3 つのインポートフローのいずれかを使用して再追加してください。

2 つの Kiro アカウントを並行して追加するための詳細と手順については、
[`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md) を参照してください。

## Docker の問題

### Docker の IPv6 / 接続リセット

<a name="docker-ipv6"></a>

**症状：** `curl http://localhost:20128/v1/models` を実行すると、`curl: (56) Recv failure: Connection reset by peer` が返されます。ダッシュボードと認証不要のエンドポイントは動作しますが、認証が必要なエンドポイントは失敗します。認証の問題に見えますが、実際にはそうではありません。

**原因：** `docker run -p 20128:20128` は `0.0.0.0`（IPv4）と `::`（IPv6）の両方でポートを公開しますが、コンテナ内のプロセスは IPv4 でのみリッスンしています。`localhost` が最初に `::1` へ解決されるホストでは、接続先がバックエンドのリスナーが存在しない IPv6 の公開ポートになるため、接続がリセットされます。

**修正方法：**

1. **簡易診断：** `curl -4 http://localhost:20128/v1/models` を実行します。`-4` を指定すると動作し、指定しないと失敗する場合は、IPv6 のバインド不一致が発生しています。
2. **恒久的な修正：** `docker run` コマンドで `-p 127.0.0.1:20128:20128` を使用し、明示的に IPv4 へバインドします：
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   これにより IPv4 へのバインドが強制され、ホストのすべてのインターフェースでプロキシが公開されることも防げます。

```bash
# ヘルスダッシュボード
http://localhost:20128/dashboard/health

# API ヘルスチェック
curl http://localhost:20128/api/monitoring/health
```

## サーキットブレーカーの問題

### プロバイダーが OPEN 状態のままになる

プロバイダーのサーキットブレーカーが OPEN の場合、クールダウン期間が終了するまでリクエストはブロックされます。

**解決方法:**

1. **ダッシュボード → 設定 → レジリエンス** に移動します
2. 影響を受けているプロバイダーのサーキットブレーカーカードを確認します
3. **すべてリセット** をクリックしてすべてのブレーカーを解除するか、クールダウン期間が終了するまで待ちます
4. リセットする前に、プロバイダーが実際に利用可能であることを確認します

### プロバイダーによってサーキットブレーカーが繰り返し作動する

プロバイダーが OPEN 状態に繰り返し移行する場合:

1. **ダッシュボード → ヘルス → プロバイダーのヘルス** で障害のパターンを確認します
2. **設定 → レジリエンス → プロバイダープロファイル** に移動し、障害しきい値を引き上げます
3. プロバイダーが API の制限を変更していないか、または再認証が必要になっていないか確認します
4. レイテンシーのテレメトリを確認します — レイテンシーが高いと、タイムアウトによる障害が発生する場合があります

## トランスレーターのデバッグ

形式変換の問題をデバッグするには、**ダッシュボード → トランスレーター** を使用します:

| モード               | 使用する場面                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| **プレイグラウンド** | 入出力形式を並べて比較します — 失敗するリクエストを貼り付けて、どのように変換されるか確認します |
| **チャットテスター** | ライブメッセージを送信し、ヘッダーを含むリクエストとレスポンスの完全なペイロードを確認します    |
| **テストベンチ**     | 形式の組み合わせに対してバッチテストを実行し、どの変換に問題があるかを特定します                |
| **ライブモニター**   | リアルタイムのリクエストフローを監視し、断続的な変換の問題を検出します                          |

### 一般的な形式の問題

- **Thinking タグが表示されない** — 対象プロバイダーが Thinking をサポートしているか、および Thinking バジェットの設定を確認します
- **ツール呼び出しが欠落する** — 一部の形式変換では、サポートされていないフィールドが削除される場合があります。プレイグラウンドモードで確認してください
- **システムプロンプトが欠落する** — Claude と Gemini ではシステムプロンプトの処理方法が異なります。変換出力を確認してください
- **SDK がオブジェクトではなく生の文字列を返す** — v1.x で解決済みです。レスポンスサニタイザーは、OpenAI SDK の Pydantic 検証エラーを引き起こす非標準フィールド（`x_groq`、`usage_breakdown` など）を削除します。v3.x+ でもこの問題が発生する場合は、issue を作成してください。
- **GLM/ERNIE が `system` ロールを拒否する** — v1.x で解決済みです。ロールノーマライザーは、互換性のないモデル向けにシステムメッセージをユーザーメッセージへ自動的に統合します。v3.x+ でもこの問題が発生する場合は、issue を作成してください。
- **`developer` ロールが認識されない** — v1.x で解決済みです。OpenAI 以外のプロバイダーでは自動的に `system` に変換されます。v3.x+ でもこの問題が発生する場合は、issue を作成してください。
- **`json_schema` が Gemini で機能しない** — v1.x で解決済みです。`response_format` は現在、Gemini の `responseMimeType` + `responseSchema` に変換されます。v3.x+ でもこの問題が発生する場合は、issue を作成してください。

## レジリエンス設定

### 自動レート制限が作動しない

- 自動レート制限は API キープロバイダーにのみ適用されます（OAuth/サブスクリプションには適用されません）
- **設定 → レジリエンス → プロバイダープロファイル**で自動レート制限が有効になっていることを確認してください
- プロバイダーが `429` ステータスコードまたは `Retry-After` ヘッダーを返しているか確認してください

### 指数バックオフの調整

プロバイダープロファイルでは、次の設定がサポートされています。

- **基本遅延** — 最初の失敗後の初期待機時間（デフォルト: 1s）
- **最大遅延** — 待機時間の上限（デフォルト: 30s）
- **乗数** — 連続する失敗ごとに遅延を増加させる倍率（デフォルト: 2x）

### サンダリングハード対策

レート制限されたプロバイダーに多数の同時リクエストが送信された場合、OmniRoute はミューテックスと自動レート制限を使用してリクエストを直列化し、連鎖的な障害を防ぎます。API キープロバイダーでは、これは自動的に行われます。

### チャットリクエストが 503 / chat_admission_busy で失敗する

**症状:**

- チャット補完エンドポイントが、エラーコード
  `chat_admission_busy` を含む再試行可能な `503` レスポンスを返します。
- レスポンスには `Retry-After` が含まれます。#12135 以降、この値は観測された
  占有状況に基づいて算出されます。つまり、リクエストがすでに待機した `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  の時間枠と、現在の重量級リースが保持されている時間のうち、大きい方を秒単位に
  切り上げ、最大 60 に制限した値です。ゲートがアイドル状態の場合は、従来の下限値が維持されます。
  バイトベースのパスでは 2 秒、構造ベースのパスでは 1 秒です（後者には
  `reason: "structure_limit"` も含まれます）。
- これは、別の重量級チャットまたは長時間実行中のストリーミングレスポンスがまだ
  処理中の場合に発生する可能性があります。

バイトベースのレスポンス本文は次のとおりです。

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

構造ベースのレスポンスでは、同じタイプとコードに加えて、メッセージ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
および `reason: "structure_limit"` が使用されます。
デフォルトのしきい値では、リクエストに少なくとも `200` 件のメッセージ、
少なくとも `64` 個のツール、または少なくとも `32,000` 個の推定トークンが含まれている場合、あるいは制限付きの構造推定が、
訪問ノード数 `10,000` または深さ `12` の上限に達した場合、そのリクエストは構造的に重量級と見なされます。

**原因:** これは OmniRoute 内部で意図的に行われる負荷遮断であり、アップストリームプロバイダーの障害ではありません。
各プロセスはプロセスローカルなガードを使用し、大きなリクエスト本文を保持して
解析する前に、制限された重量級処理のキャパシティを予約します。重量級リースは、SSE
レスポンスの存続期間中、保持され続けます。

**#503-fanout:** この修正以前は、ガードがホストのメモリ量に関係なく、固定のリクエスト数
（`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`、デフォルトは `1`）で同時実行数を制限していたため、コーディングエージェントの
ファンアウト（複数のサブエージェント/CLI、通常 256 KB を超える本文）によって、実効同時実行数が
約 1 まで低下し、まったく通常の負荷でも 503 が発生していました。現在、ガードは自己調整されます。プロセスの
実際のメモリ上限から算出された自動導出の取り込みバイト予算（`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`）によって
制御され、さらにリアルタイムのリソース圧迫シグナルも参照します。そのため、
複数の重量級リクエストが同時に到着したというだけではなく、ホストが実際にメモリ不足に陥っている場合にのみ
負荷を遮断します。従来の件数上限（`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`）も
引き続き適用されますが、明示的に設定した場合に限られます。

キャパシティが使用中の場合、重量級リクエストは、再試行可能な `503` を返す前に、
スロットが空くまで最大 `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`（デフォルトは `RATE_LIMIT_MAX_WAIT_MS`。`0` で待機を無効化）
まで待機します。この制限付き待機により、重量級サブリクエストを同時にファンアウトするエージェント形式のクライアント
（OpenCode、Claude Code、Cursor）は、即時拒否によって再試行回数をすべて使い果たし、タスクの途中で停止する代わりに、
バーストを直列化できます。
現在の重量級リースの占有状況、確定したバイト予算、およびリアルタイムの圧迫度は、
`GET /api/monitoring/health` → `chatAdmission`（`inflightBytes`、`maxInflightBytes`、
`budgetSource`、`pressureSeverity`、`countCapEnabled`）で確認できます。環境変数を変更する前に、これらを確認してください。
設定 → レジリエンス → リクエストキュー → 同時リクエスト数では、これは制御されません。この設定が
制御するのは、別のプロバイダーリクエストキュー機構です。

**修正方法:**

1. まず再試行してください。クライアントはリクエストを即座に繰り返すのではなく、`Retry-After` に従って
   バックオフを使用する必要があります。
2. 何かを調整する前に、`/api/monitoring/health` → `chatAdmission` を確認してください。`countCapEnabled:
false` であり、`maxInflightBytes` に十分な余裕がある場合、自動導出された予算はすでに正常に
   機能しています。`pressureSeverity` が `high`/`critical` の場合、ホストは実際にメモリ不足に
   陥っています。これは受け入れ制御用の環境変数では修正できず、RAM を増やすか、ワークロードを縮小する必要があります。
3. `/api/monitoring/health` によって、自動導出された予算が実際にホストに対して小さすぎることが
   示された場合にのみ（これはまれです。コンテナからベアメタルまで、すでに自動でスケーリングされます）、
   従来のリクエスト件数上限に戻すのではなく、`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` を使用して直接上書きしてください。

正式な受け入れ制御設定については、[環境変数リファレンス](../reference/ENVIRONMENT.md#4-security--authentication)
を参照してください。

## オプション: RAG / LLM 障害分類（16の問題）

一部の OmniRoute ユーザーは、RAG またはエージェントスタックの前段にゲートウェイを配置しています。このような構成では、OmniRoute は正常に見える（プロバイダーは稼働中、ルーティングプロファイルも正常、レート制限アラートもなし）にもかかわらず、最終的な回答が依然として誤っている、という奇妙なパターンがよく見られます。

実際には、こうしたインシデントは通常、ゲートウェイ自体ではなく、後段の RAG パイプラインに起因します。

こうした障害を説明するための共通語彙が必要な場合は、WFGY ProblemMap を使用できます。これは、繰り返し発生する16種類の RAG / LLM 障害パターンを定義した、MIT ライセンスの外部テキストリソースです。大まかには、以下を扱っています。

- 検索のドリフトとコンテキスト境界の破綻
- 空または古くなったインデックスとベクトルストア
- 埋め込みとセマンティクスの不一致
- プロンプト構築とコンテキストウィンドウの問題
- 論理の崩壊と過度に確信的な回答
- 長いチェーンとエージェント連携の障害
- マルチエージェントのメモリと役割のドリフト
- デプロイとブートストラップ順序の問題

考え方はシンプルです。

1. 不適切な応答を調査するときは、以下を記録します。
   - ユーザーのタスクとリクエスト
   - OmniRoute のルートまたはプロバイダーの組み合わせ
   - 後段で使用された RAG コンテキスト（取得したドキュメント、ツール呼び出しなど）
2. インシデントを1つまたは2つの WFGY ProblemMap 番号（`No.1` … `No.16`）に対応付けます。
3. OmniRoute のログと併せて、自身のダッシュボード、ランブック、またはインシデントトラッカーにその番号を保存します。
4. 対応する WFGY ページを使用して、RAG スタック、リトリーバー、またはルーティング戦略を変更する必要があるかどうかを判断します。

全文と具体的なレシピはこちらにあります（MIT ライセンス、テキストのみ）。

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute の後段で RAG またはエージェントパイプラインを実行していない場合は、このセクションを無視してかまいません。

## v3.8.0 の既知の問題

v3.8.0 リリース固有の問題と、現在の回避策です。修正が後続のパッチに含まれた場合、その項目は更新または削除されます。

### Devin CLI の認証失敗

**症状:**

- Devin をバックエンドとするツールを呼び出すと、「Devin CLI が見つかりません」または「認証に失敗しました」と表示される
- CLI ランタイムチェックで `installed=false` と報告される

**原因:**

- `CLI_DEVIN_BIN` が存在しないパスを指している
- ホストに Devin CLI がインストールされていない

**修正方法:**

1. お使いのプラットフォーム向けの Devin CLI をインストールします
2. `.env` に `CLI_DEVIN_BIN=/usr/local/bin/devin`（または実際のパス）を設定します
3. OmniRoute を再起動し、**ダッシュボード → CLI ツール**から再テストします

### モデルのクールダウンが解除されない（手動リセット）

**症状:**

- 有効期限が過ぎた後も、モデルがクールダウン中として表示され続ける
- タイムスタンプが過去になっているにもかかわらず、組み合わせルーティングで引き続きそのモデルがスキップされる

**手動リセット:**

- **ダッシュボード:** **設定 → モデルのクールダウン** → 該当するカードの **再有効化**をクリック
- **API:** 管理認証ヘッダーを付けて `DELETE /api/resilience/model-cooldowns`

### Command Code プロバイダーへの接続が 403 で失敗する

**症状:**

- Command Code プロバイダーの接続テスト時に 403 が返される
- 新しく追加した後、プロバイダーカードに「未承認」と表示される

**原因:** OAuth フローが完了していません（コールバックが受信されなかった、またはトークンが保存されなかった）。

**修正方法:**

- CLI から `omniroute providers` を実行して OAuth フローを再度開始する、または
- **ダッシュボード → プロバイダー → Command Code → 再接続**から OAuth を再実行する

### ModelScope で過度な 429 クールダウンが返される

**症状:**

- 少数のリクエストを短時間に送信しただけで、ModelScope に非常に短い、または即時のクールダウンが発生する
- 組み合わせルーティングで、想定より早く ModelScope がスキップされる

**原因:** ModelScope はプロバイダー固有の `Retry-After` ヘッダーを送信します。v3.8.0 にはこれらのヘッダー専用の処理が含まれているため、古いバージョンでは一般的なレート制限のヒントとして誤って解釈されます。

**修正方法:**

- v3.8.0 以降を使用していることを確認します
- **設定 → レジリエンス**で `useUpstream429BreakerHints` トグルが有効になっていることを確認します

### 本番環境で OMNIROUTE_WS_BRIDGE_SECRET が設定されていない

**症状:**

- リモートの本番ホストで実行している場合、Codex/Responses WebSocket ブリッジへのすべてのリクエストで 401 が返される
- WebSocket ブリッジのハンドシェイクが、接続直後に終了する

**原因:** 本番環境に `OMNIROUTE_WS_BRIDGE_SECRET` 環境変数が設定されていません。

**修正方法:**

1. ランダムなシークレットを生成します: `openssl rand -hex 32`
2. 本番サーバーの環境（およびブリッジと通信するすべてのクライアント）に `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` を設定します
3. OmniRoute を再起動します

### Responses API: バックグラウンドモードが同期処理にフォールバックする

**症状:**

- 警告 `background mode degraded to synchronous` がログに記録される
- `background: true` リクエストで、バックグラウンドジョブのハンドルではなく、通常の同期レスポンスが返される

**原因:** v3.8.0 では、Responses API の `background: true` は意図的に同期実行へフォールバックし、その際に警告が出力されます。完全な非同期バックグラウンド実行は、今後提供される予定です。

**修正方法:**

- `background` を指定せずに呼び出すようクライアントを調整する、または
- 完全な非同期バックグラウンドモードが提供される今後のリリースを待つ（変更履歴を確認してください）

## 起動の遅延 / 準備完了タイムアウト

CLI に `⚠ Server did not respond within 60s` と表示されてもサーバーが実際には動作している場合は、お使いの環境に対して準備完了プローブの待機時間が短すぎます。

これは、Windows（ウイルス対策ソフト、ファイルシステム監視）や、起動時の負荷が高いコンテナでよく発生します。

**対処方法 — 待機時間を延長する:**

```bash
# 環境変数を使用（以降の起動でも維持）:
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3分
omniroute serve

# CLI フラグを使用（今回のみ）:
omniroute serve --ready-timeout 180000
```

デフォルトは 60 000 ms（60秒）です。この警告は情報提供のみを目的としており、サーバーはバックグラウンドで起動を続け、起動が完了するとアクセスできるようになります。

`OMNIROUTE_READY_TIMEOUT_MS` の詳細については、[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) を参照してください。
