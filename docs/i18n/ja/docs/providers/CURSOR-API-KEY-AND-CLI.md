IDE セッションなしで Cursor を OmniRoute の背後に配置するには、次の 2 つの方法があります。

1. **`cursor-api` プロバイダー**（カード「Cursor API」、エイリアス `cua`）：Cursor ユーザー API キー（`crsr_…`、`https://cursor.com/dashboard/api` で生成）を保持する API キープロバイダーです。任意の OmniRoute クライアントは、通常のクォータ、フォールバック、ロギングレイヤーを介して、`/v1/chat/completions` から `cursor-api/<model>` または `cua/<model>` として Cursor モデルにアクセスできます。IDE プロバイダー（`cursor`、OAuth/IDE セッション）に変更はありません。
2. **Cursor CLI パススルー**：Cursor CLI（`agent`）を OmniRoute に向けることで、CLI が行うすべての RPC が OmniRoute API キーで認証され、`cursor-api` 接続の認証情報を使用して Cursor に転送され、Logs ページに記録されます。

## キーが交換される理由

`api2.cursor.sh` は、生の `crsr_…` キーを Bearer トークンとして使用すると拒否します（401）。Cursor CLI は最初にキーを `/auth/exchange_user_api_key` へ POST し、1 時間後に期限切れとなるセッション JWT を受け取ります。返される `refreshToken` の `exp` も同じであるため、更新するにはキーを再交換する必要があります。
`open-sse/services/cursorApiKeyAuth.ts` はこの交換を実行し、キーごとに 1 つのセッショントークンをキャッシュし、有効期限の 5 分前に再交換し、Cursor から 401 が返された場合はキャッシュされたトークンを破棄します。`CursorExecutor` は、`cursor-api` 接続のアップストリームストリームを開く直前にこれを呼び出します。

## `cursor-api` プロバイダー

レジストリ：`open-sse/config/providers/registry/cursor/index.ts`
（`cursor_apiProvider`、`authType: "apikey"`、`cursor` と同じ `format`、`baseUrl`、`models`）。カタログカード：
`src/shared/constants/providers/apikey/specialty-media.ts`。Executor マップ：
`open-sse/executors/index.ts`（`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`）。

ダッシュボード：Providers → Cursor API → Add API key。

REST：

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

その後：

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

注意：

- `cursor-api` のモデル一覧は、静的な Cursor レジストリ（IDE プロバイダーがフォールバック先として使用するものと同じ一覧）から取得されます。OmniRoute ホストに `cursor-agent` をインストールする必要はありません。
- `POST /api/providers/{id}/refresh-cursor` は `cursor` IDE プロバイダー専用です。`cursor-api` 接続には更新対象となる IDE セッションがありません。

## Cursor CLI パススルー

ルート：`src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`。プレフィックス `/api/cursor-cli/` は、ハンドラーが独自の認証を強制するため、`src/shared/constants/publicApiRoutes.ts` に登録されています。

| パス                                                                                                                            | CLI から期待される認証       | OmniRoute の処理                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /auth/exchange_user_api_key`                                                                                              | `Bearer <OmniRoute API key>` | キーを検証し、1 時間有効な HS256 JWT（`JWT_SECRET` で署名）を発行して返します                                                                                            |
| その他すべてのパス（`/aiserver.v1.*`、`/agent.v1.AgentService/RunSSE`、`/aiserver.v1.BidiService/BidiAppend`、`/v1/traces`、…） | `Bearer <that JWT>`          | issuer、audience、有効期限を検証し、アクティブな `cursor-api` 接続を選択し、Authorization ヘッダーを交換済み Cursor トークンに置き換えて、応答をストリーミングで返します |

CLI は受け取ったトークンから `exp` をデコードするため、不透明なトークンを渡すと、ほぼすべてのリクエストの前に再交換が行われます。発行された JWT はこれを回避します。OmniRoute から 401 が返されると、CLI は再度交換を実行します。

### セットアップ

1. OmniRoute API キー（Dashboard → API keys）と `cursor-api` 接続を作成します。
2. エージェントストリームで HTTP/1.1 を使用するよう CLI に指定します。`~/.cursor/cli-config.json` に次を記述します。

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   これを設定しない場合、CLI は別途設定されたエージェントホストへのエージェントターンを HTTP/2 で開き、コントロールプレーン RPC のみがエンドポイントを通過します。

3. OmniRoute に向けて CLI を実行します。

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

すべてのホップは、プロバイダー `cursor-api`、リクエストタイプ `cursor-cli`、パス `/api/cursor-cli/<rpc>` として Logs に記録され、OmniRoute API キーと、そのリクエストを処理した接続に紐付けられます。

### 障害モード

| 状況                                             | CLI へのレスポンス                                    |
| ------------------------------------------------ | ----------------------------------------------------- |
| 不明な OmniRoute キーかつ `REQUIRE_API_KEY=true` | 交換時に 401 `unauthenticated`                        |
| `REQUIRE_API_KEY=false`                          | 匿名セッション（`/v1/*` の動作に準拠）                |
| 期限切れ / 外部発行 / 改ざんされたセッション JWT | 401、CLI が再交換                                     |
| 交換後に OmniRoute API キーが失効                | 次回の RPC で 401                                     |
| 有効な `cursor-api` 接続がない                   | 503 `unavailable`                                     |
| Cursor が接続キーを拒否                          | 401 `unauthenticated`、キャッシュ済みセッションを破棄 |
| アップストリームに到達不能                       | 502 `unavailable`（サニタイズされたメッセージ）       |
| `JWT_SECRET` が未設定                            | 交換時に 503                                          |
