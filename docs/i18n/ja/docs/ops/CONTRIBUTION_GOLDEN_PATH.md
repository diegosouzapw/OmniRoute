このガイドを使用して、プルリクエストに対する信頼性のある最小限の開発ループを選択してください。これは、以下にリンクされている領域固有のアーキテクチャおよびセキュリティドキュメントに代わるものではありません。それぞれの一般的な変更タイプを、対応する契約、重点チェック、CI カバレッジに結び付けるものです。

## すべての変更がたどる手順

1. **編集前にベースを選択する。** アクティブな `release/v*` ブランチのうち最上位のものを見つけ、その先端からブランチを作成します。`main` ではなく、そのブランチをターゲットにしてください。リリース凍結期間中の場合は、凍結されたブランチをターゲットにせず、[ブランチおよびリリースモデル](BRANCHING_MODEL.md)に記載されている次のアクティブなサイクルを使用してください。
2. **契約を明示する。** 変更が影響を与えるすべてのカタログ、スキーマ、生成済み成果物、公開 API、またはユーザーインターフェイスを特定します。以下の表は、最低限の開始セットを示しています。
3. **重点テストを作成または更新する。** `src/`、`open-sse/`、`electron/`、または `bin/` に対する本番コードの変更には、同じ PR 内で自動テストが必要です。動作を証明する最小限のテストファイルを実行してから、記載されている重点ゲートを実行してください。
4. **広範なマトリックスは CI に実行させる。** 完全なユニットテストのシャード、Vitest、カバレッジラチェット、および本番ビルドは PR 上で実行されます。重点テストの失敗からより広い影響が示唆された場合、または変更が複数のサブシステムにまたがる場合にのみ、広範なスイートをローカルで実行してください。
5. **レビュー前に整合させる。** アクティブなベースをフェッチし、その新しいコミットと、それに対する自分の差分を確認してから、コントリビューターワークフローに従ってベースをリベースまたはマージします。生成ファイルおよびカタログの競合は、そのソース側で解決して再生成し、重点ループを再実行したうえで、PR が引き続きアクティブなリリースブランチをターゲットにしていることを確認してください。
6. **根拠を記録する。** PR テンプレートに、実行したコマンド、追加または変更したすべてのテストファイル、マイグレーションまたは機能フラグ、および保留中の CI 専用検証を記載してください。

## 変更タイプ別の推奨手順

以下のコマンドは最低限の重点チェックであり、変更した動作を直接カバーするテストを省略してよいという意味ではありません。

### プロバイダー

**契約**

- `src/shared/constants/providers/` 内のプロバイダー定義、および `src/shared/constants/providers.ts` におけるその構成。
- `open-sse/config/providerRegistry.ts` またはそこから抽出されたレジストリファイル内のモデルおよび機能。
- 該当する場合、エグゼキューター／トランスレーターの選択、OAuth または API キーの設定、ダッシュボードアセット、および生成済みプロバイダーリファレンス。
- 公開認証情報では `resolvePublicCred()` を使用する必要があり、エラーレスポンスでは共有のサニタイズ済みエラーヘルパーを使用する必要があります。`docs/security/PUBLIC_CREDS.md`（git 内にあり、`/docs` にはコンパイルされません）および[エラーのサニタイズ](../security/ERROR_SANITIZATION.md)を参照してください。

**重点ループ**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # カタログが変更された場合。生成された差分をコミットする
npm run lint
```

影響を受けるすべてのリクエストファミリー（チャット、Responses、画像、埋め込み、音声、動画）もテストしてください。生成されたカタログおよびゴールデン差分は契約変更としてレビューし、無条件に受け入れないでください。

### ルーティング

**契約**

- `src/shared/constants/routingStrategies.ts` 内の公開ストラテジー値および UI メタデータ。
- `open-sse/services/combo.ts` および `open-sse/services/combo/` 配下のディスパッチと順序。
- コンボのスキーマ、永続化、レジリエンス状態、モデル機能、および API／UI コントロール。
- 動作が変更される場合は、[Auto-Combo エンジン](../routing/AUTO-COMBO.md)およびレジリエンスに関するドキュメント。

**重点ループ**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ストラテジーまたはディスパッチの変更
npm run check:known-symbols      # ストラテジー登録の変更
npm run lint
```

ローカルでは、モック化したアップストリームを使用する決定論的テストを使用してください。実環境のコンボスモークテストには認証情報が必要であり、手動で実行するものであって、CI の代替ではありません。

### UI / UX

**契約**

- `src/app/` および `src/shared/components/` 配下の Next.js ルート／ページと共有コンポーネントの境界。
- API レスポンスの形状、読み込み中／空／エラー状態、キーボードおよびスクリーンリーダーでの動作、レスポンシブレイアウト、テーマ設定、ロケール展開。
- `src/i18n/messages/en.json` 内の英語 UI ソース文字列。新しいユーザー向け文言をハードコードしないでください。

**重点ループ**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

操作または表示に関する変更ではアプリを実行し、狭いビューポートと広いビューポートの両方を確認してください。CI は本番ビルドとより広範なスイートを実行しますが、表示上の動作については、変更内容に適した重点コンポーネントテスト、Playwright テスト、または文書化された手動チェックが引き続き必要です。

### i18n

**契約**

- `src/i18n/messages/en.json` は UI のソースであり、`config/i18n.json` はロケールのソースです。
- CLI カタログは別に `bin/cli/locales/` 配下にあります。
- ICU プレースホルダーおよびタグは正確に維持してください。製品名／プロバイダー名／モデル名、プロトコル名およびヘッダー名、コマンド、コード／JSON 識別子、URL、環境変数、または `OmniRoute`、`OAuth`、`MCP`、`A2A` などの保護対象用語は翻訳しないでください。現在のソースリストは `scripts/i18n/glossary/protected-terms.json` です。

**重点ループ**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI 文字列／カタログが変更された場合
npm run lint
```

これは既存システムに対するガイダンスであり、そのツール群やキーモデルの拡張を推奨するものではありません。代替システムの設計中は、i18n のパッチを必要最小限に保ってください。タスクで生成済み翻訳が明示的に必要とされ、かつ生成された差分をレビューできる場合を除き、外部サービスを呼び出す翻訳コマンドを実行しないでください。

### CLI

**契約**

- `bin/cli/` 内の公開コマンドとフラグ、生成された API コマンド、終了コード、stdout/stderr と
  JSON 出力形式、設定/環境の挙動、およびパッケージ化されるファイル。
- CLI のユーザー向け文字列では CLI i18n レイヤーを使用し、`en`/`pt-BR` カタログの整合性を維持する必要があります。
- Node をサポート対象ランタイムとして維持し、公開済みバイナリの契約を保持してください。

**重点確認ループ**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # 生成/バンドルされた CLI の変更
npm run check:pack-policy     # パッケージ公開範囲の変更
npm run lint
```

挙動が解析、ファイル、または終了ステータスに依存する場合は、一時データディレクトリで正確なコマンドを使用してください。CI では、より広範なパッケージ成果物とエコシステムのチェックが実行されます。

### データベース

**契約**

- `src/lib/db/` 配下のドメインモジュール。特定のモジュールを直接インポートしてください（旧 `localDb.ts` 再エクスポートレイヤーは削除されました）。
- `src/lib/db/migrations/` 配下の番号付きで冪等な SQL マイグレーション、トランザクションの安全性、アップグレード時の
  挙動、インデックス、およびスキーマの影響を受けるすべての呼び出し元。
- ルートとハンドラーから raw SQL を直接発行してはいけません。

**重点確認ループ**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

マイグレーションを追加する場合は、新規データベースと直前のスキーマからのアップグレードの両方をテストしてください。データベーステストでは、クリーンアップ時にハンドルを閉じ、`resetDbInstance()` を呼び出す必要があります。ベストエフォートの Bun アダプターパスを変更した場合にのみ `npm run test:bun:db` を実行してください。Node が引き続き正とされます。

### ビルド / デプロイ

**契約**

- ルートおよびワークスペースのマニフェスト/ロックファイル、`scripts/build/`、Next.js スタンドアロンアセンブリ、`dist/`
  パッケージの内容、Electron のプラットフォームメタデータ、CI ワークフロー、およびデプロイのセンチネル。
- サポート対象の Node バージョン範囲と、`CLAUDE.md` で許可リストに登録されている Bun の使用を維持する必要があります。
- ビルド成果物は追跡対象外のままとし、依存関係、ライセンス、ワークフロー、およびパッケージのポリシーを適用します。

**重点確認ループ**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # 依存関係またはロックファイルの変更
npm run check:pack-policy      # 公開パッケージ範囲の変更
npm run lint
```

変更がコンパイル、スタンドアロンアセンブリ、アセット、またはランタイムバンドルに影響する場合にのみ、ローカルで `npm run build` を使用してください。`npm run build:release` はリリース/デプロイ検証にのみ使用してください。CI のビルドが最終的なクロスプラットフォーム判定となります。プラットフォーム固有の Electron の変更には、該当する重点ビルドまたはスモークテストの証跡が必要です。

## ローカルループと CI の比較

| 各パッチでローカル実行するもの                                       | CI が提供する広範なシグナル                                                |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 上記の直接的な動作テストとカテゴリゲート                             | シャーディングされた完全なユニットテストスイートとシリアルテスト           |
| `npm run lint`                                                       | Vitest スイートとカバレッジ／品質ラチェット                                |
| 影響を受ける契約で必要な場合に限り、型チェックまたはビルドを実行     | 本番ビルド、セキュリティ、ドキュメント、依存関係、PR ポリシーのゲート      |
| 自動化で動作を証明できない場合に限り、手動操作／ライブチェックを実行 | ワークフローで構成されたジョブ横断の統合チェックとプラットフォームチェック |

対象を絞ったローカルループが成功することは、変更された契約に関する証拠ではありますが、無関係な CI チェックも
成功することの証明ではありません。一方で、ローカルでのすべての編集について、リポジトリ全体のマトリクスの完了を待つ必要もありません。

## 整合確認チェックリスト

レビューを依頼する前に、以下を確認してください。

- PR のベースが、引き続きアクティブな `release/v*` ブランチのうち最上位であることを確認する。
- そのベースをフェッチし、ブランチ作成後に追加されたコミットをレビューする。
- `git diff <active-base>...HEAD` を確認し、意図しない変更や生成物の不要な差分がないか確認する。
- カタログおよび生成ドキュメントの競合は、ソースを更新して出力を再生成することで解消する。
- 整合確認後、PR の説明に記載された対象テスト／ゲートをすべて再実行する。
- ベースの移動に合わせるためだけに、アサーションを弱めたり、必須テストを削除したりしない。

リリース凍結とリターゲットのルールについては、
[ブランチおよびリリースモデル](BRANCHING_MODEL.md)を参照してください。CI の完全な一覧については、
[品質ゲートリファレンス](../architecture/QUALITY_GATES.md)を参照してください。
