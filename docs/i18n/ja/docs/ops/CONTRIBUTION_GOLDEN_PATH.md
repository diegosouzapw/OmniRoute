このガイドを使用して、プルリクエストに対する信頼性のある最小限の開発ループを選択してください。このガイドは、
以下にリンクされている領域固有のアーキテクチャおよびセキュリティドキュメントに代わるものではありません。一般的な
変更タイプごとに、そのコントラクト、重点チェック、CI カバレッジを関連付けるものです。

## すべての変更がたどる手順

1. **編集前にベースを選択します。** アクティブな `release/v*` ブランチのうち最上位のものを見つけ、その
   先端からブランチを作成します。`main` ではなく、そのブランチをターゲットにしてください。リリースフリーズ中の場合は、フリーズされている
   ブランチをターゲットにせず、
   [ブランチとリリースモデル](BRANCHING_MODEL.md)に記載された次のアクティブなサイクルを使用してください。
2. **コントラクトを明示します。** 変更が影響するすべてのカタログ、スキーマ、生成済みアーティファクト、公開 API、またはユーザー
   インターフェースを特定します。以下の表に、最低限の開始セットを示します。
3. **重点テストを作成または更新します。** `src/`、`open-sse/`、`electron/`、または
   `bin/` の本番コードを変更する場合は、同じ PR に自動テストが必要です。動作を実証する最小限のテストファイルを
   実行してから、記載されている重点ゲートを実行してください。
4. **広範なマトリックスは CI に実行させます。** 完全なユニットテストのシャード、Vitest、カバレッジラチェット、および
   本番ビルドは PR 上で実行されます。重点テストの失敗がより広い影響を示している場合、または変更が複数のサブシステムに
   またがる場合にのみ、広範なスイートをローカルで実行してください。
5. **レビュー前に整合させます。** アクティブなベースをフェッチし、その新しいコミットと、それに対する自分の差分を
   確認したうえで、コントリビューターワークフローに従ってベースをリベースまたはマージします。生成ファイルおよび
   カタログの競合はソース側で解決し、再生成して重点ループを再実行し、PR が引き続きアクティブなリリースブランチを
   ターゲットにしていることを確認してください。
6. **証跡を記録します。** PR テンプレートに、実行したコマンド、追加または変更したすべてのテストファイル、
   マイグレーションまたは機能フラグ、および CI でのみ実施される保留中の検証を記載します。

## 変更タイプ別の推奨手順

以下のコマンドは最低限の重点チェックであり、変更した動作を直接カバーするテストを省略してよいという意味では
ありません。

### プロバイダー

**コントラクト**

- `src/shared/constants/providers/` 内のプロバイダー定義、および
  `src/shared/constants/providers.ts` でのその構成。
- `open-sse/config/providerRegistry.ts` またはそこから抽出されたレジストリファイル内のモデルと機能。
- 該当する場合は、Executor/translator の選択、OAuth または API キーの設定、ダッシュボードアセット、および生成された
  プロバイダーリファレンス。
- 公開認証情報では `resolvePublicCred()` を使用する必要があります。エラーレスポンスでは、共有のサニタイズ済み
  エラーヘルパーを使用する必要があります。`docs/security/PUBLIC_CREDS.md`（git 内のみ。`/docs` にはコンパイルされません）および
  [エラーのサニタイズ](../security/ERROR_SANITIZATION.md)を参照してください。

**重点ループ**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # カタログを変更した場合。生成された差分をコミットする
npm run lint
```

影響を受けるすべてのリクエストファミリー（chat、Responses、images、embeddings、audio、video）もテストしてください。
生成されたカタログとゴールデン差分はコントラクトの変更としてレビューし、無条件に受け入れないでください。

### ルーティング

**コントラクト**

- `src/shared/constants/routingStrategies.ts` 内の公開ストラテジー値および UI メタデータ。
- `open-sse/services/combo.ts` および `open-sse/services/combo/` 配下のディスパッチと順序付け。
- Combo スキーマ、永続化、レジリエンス状態、モデル機能、および API/UI コントロール。
- 動作を変更する場合は、[Auto-Combo エンジン](../routing/AUTO-COMBO.md)およびレジリエンス関連ドキュメント。

**重点ループ**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ストラテジーまたはディスパッチの変更
npm run check:known-symbols      # ストラテジー登録の変更
npm run lint
```

ローカルでは、モック化されたアップストリームを使用する決定論的なテストを使用してください。実環境の combo スモークテストには認証情報が必要であり、
手動で実施するものであって、CI の代替にはなりません。

### UI / UX

**コントラクト**

- `src/app/` および `src/shared/components/` 配下の Next.js ルート／ページと共有コンポーネントの境界。
- API レスポンスの形状、読み込み中／空／エラー状態、キーボードおよびスクリーンリーダーの動作、
  レスポンシブレイアウト、テーマ、ロケール展開。
- `src/i18n/messages/en.json` 内の英語 UI ソース文字列。ユーザー向けの新しい文言をハードコードしないでください。

**重点ループ**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

インタラクションまたはビジュアルを変更する場合はアプリを実行し、狭いビューポートと広いビューポートの両方を確認してください。CI では
本番ビルドおよびより広範なスイートが実行されますが、ビジュアルの動作には引き続き、変更内容に応じた重点コンポーネントテスト、
Playwright テスト、または文書化された手動チェックが必要です。

### i18n

**コントラクト**

- `src/i18n/messages/en.json` は UI のソースであり、`config/i18n.json` はロケールのソースです。
- CLI カタログは `bin/cli/locales/` 配下で個別に管理されます。
- ICU プレースホルダーとタグをそのまま維持してください。製品名／プロバイダー名／モデル名、
  プロトコル名とヘッダー名、コマンド、コード／JSON 識別子、URL、環境変数、および
  `OmniRoute`、`OAuth`、`MCP`、`A2A` などの保護用語は翻訳しないでください。現在のソースリストは
  `scripts/i18n/glossary/protected-terms.json` です。

**重点ループ**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI 文字列／カタログを変更した場合
npm run lint
```

これは既存システムに対するガイダンスであり、そのツールやキーモデルの拡張を促すものではありません。
代替システムの設計中は、i18n パッチを必要最小限に保ってください。タスクで生成された翻訳が明示的に必要とされ、
かつ生成された差分をレビュー済みでない限り、外部サービスを呼び出す翻訳コマンドを実行しないでください。

### CLI

**コントラクト**

- `bin/cli/` 内の公開コマンドとフラグ、生成された API コマンド、終了コード、stdout/stderr と
  JSON 出力形式、設定/環境の動作、およびパッケージに含まれるファイル。
- CLI のユーザー向け文字列では CLI の i18n レイヤーを使用し、`en`/`pt-BR` カタログの整合性を維持する必要があります。
- Node をサポート対象のランタイムとして維持し、公開済みバイナリの契約を保持してください。

**重点確認ループ**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # 生成済み/バンドル済み CLI の変更
npm run check:pack-policy     # パッケージ公開範囲の変更
npm run lint
```

解析、ファイル、または終了ステータスによって動作が変わる場合は、一時データディレクトリで正確なコマンドを使用してください。CI では、より広範なパッケージアーティファクトおよびエコシステムのチェックが実行されます。

### データベース

**契約**

- `src/lib/db/` 配下のドメインモジュール。特定のモジュールを直接インポートしてください（旧 `localDb.ts` 再エクスポートレイヤーは削除済みです）。
- `src/lib/db/migrations/` 配下の番号付きで冪等な SQL マイグレーション、トランザクションの安全性、アップグレード時の動作、インデックス、およびスキーマの影響を受けるすべての呼び出し元。
- ルートとハンドラーから raw SQL を直接発行してはいけません。

**重点確認ループ**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

マイグレーションを追加する際は、新規データベースと直前のスキーマからのアップグレードの両方をテストしてください。データベーステストでは、クリーンアップ時にハンドルを閉じ、`resetDbInstance()` を呼び出す必要があります。ベストエフォートの Bun アダプターパスが変更された場合に限り、`npm run test:bun:db` を実行してください。Node が引き続き正式な基準です。

### ビルド / デプロイ

**契約**

- ルートおよびワークスペースのマニフェスト/ロックファイル、`scripts/build/`、Next.js のスタンドアロンアセンブリ、`dist/`
  パッケージの内容、Electron のプラットフォームメタデータ、CI ワークフロー、およびデプロイのセンチネル。
- サポート対象の Node バージョン範囲と、`CLAUDE.md` で許可リストに含まれている Bun の使用は、そのまま維持する必要があります。
- ビルドアーティファクトは追跡対象外のままにしてください。依存関係、ライセンス、ワークフロー、およびパッケージのポリシーが適用されます。

**重点確認ループ**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # 依存関係またはロックファイルの変更
npm run check:pack-policy      # 公開パッケージ範囲の変更
npm run lint
```

変更がコンパイル、スタンドアロンアセンブリ、アセット、またはランタイムバンドルに影響する場合に限り、ローカルで `npm run build` を使用してください。`npm run build:release` は、リリース/デプロイの検証にのみ使用してください。CI のビルドがクロスプラットフォーム対応の最終的な判断材料です。プラットフォーム固有の Electron の変更には、該当する重点ビルドまたはスモークテストの証跡が必要です。

## ローカル候補ループ

ソースのテストだけでは、パッケージ化された成果物が起動することを証明できません。パッケージ対象ファイルのリスト、削減された依存関係、
ネイティブバイナリに関する問題は、tarball をインストールして起動したときに初めて明らかになります。`npm run dev:candidate`
（`scripts/dev/candidate.mjs`）は、RFC #8084 で定義された「一度ビルド / 検証 / 昇格」フローのローカル側です。
候補を一度ビルドし、その同一の成果物を検証し、ディレクトリ名の変更によって昇格させ、昇格後のスロットがヘルスチェックに失敗した場合は
ロールバックします。

```bash
npm run dev:candidate -- run --dry-run --json  # 計画を表示し、何も変更しない
npm run dev:candidate -- run                   # ビルド + 検証 + 昇格、自動ロールバック
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ へのインストール
npm run dev:candidate -- validate --id <id>    # 空きポートで起動し、/api/health + /v1/models を確認
npm run dev:candidate -- promote --id <id>     # <id> → current、current → previous
npm run dev:candidate -- rollback              # current と previous を入れ替える
npm run dev:candidate -- run --from-tarball <file.tgz>  # 別の場所（CI）でビルドされた tarball を再利用
```

- **一度だけビルドします。** `build` は現在のツリーをパッケージ化する（`dist/server.js` が必要なため、先に
  `npm run build:release` を実行してください）か、`--from-tarball` をコピーしてから、tarball には
  `node_modules` が含まれないため、分離された npm prefix に tarball をインストールします。ID は短縮された `HEAD`
  sha（ツリーにローカル変更がある場合は `-dirty` 付き）、または tarball の場合は `tgz-<sha256>` です。すでに
  ビルド済みのクリーンな ID は、再ビルドせずに再利用されます。再ビルドするには `--force` を指定してください。
- **ソースではなくパッケージを検証します。** `validate` は、インストール済みの CLI
  （`serve --port <free port>`）を、新しい `DATA_DIR=<candidate>/data` とダミーのシークレットを使用して起動します。また、
  オペレーターの `OMNIROUTE_API_KEY`、`STORAGE_ENCRYPTION_KEY`、`INITIAL_PASSWORD` を環境から除外することで、
  新規インストール時のキーなしループバック構成を検証します。`GET /api/health` が 200 を返すまで待機し、
  `GET /v1/models` が 200 を返すことを必須とし、プロセスグループを停止して、判定結果を tarball のハッシュとともに
  `validation.json` に記録します。
- **同じ成果物を昇格させます。** `promote` は、現在の tarball ハッシュに対する検証に合格していない候補の
  昇格を拒否します。デフォルトのアクティブスロットは `_artifacts/candidate/current` です。`--target <dir>`
  を指定すると、同じファイルシステム上の別のディレクトリが選択され、その以前のスロットは `<dir>.previous` になります。
  各名前変更はアトミックであり、途中で失敗した場合は、それまでに実行された名前変更が元に戻されます。
- **ロールバックします。** `run` は昇格後のスロットを再度検証し、そのチェックが失敗した場合は
  `current` と `previous` を元に戻します。最初の検証に失敗した候補が昇格されることはありません。

すべては gitignore の対象である `_artifacts/candidate/` 配下に書き込まれます。既存の OmniRoute
インストールとそのデータディレクトリには一切変更を加えません。昇格後の CLI は
`_artifacts/candidate/current/prefix/bin/omniroute` です。使用する際は、独自の `DATA_DIR` を指定して起動してください。
終了コード: `0` は成功、`1` は検証または昇格の失敗、`2` は使用方法の誤りまたはビルドの欠落を示します。

## ローカルループと CI の比較

| 各パッチでローカル実行する項目                                           | CI が提供する広範なシグナル                                            |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 上記の直接的な振る舞いのテストとカテゴリゲート                           | シャーディングされた完全なユニットテストスイートと直列テスト           |
| `npm run lint`                                                           | Vitest スイートとカバレッジ／品質のラチェット                          |
| 影響を受ける契約で必要な場合にのみ型チェックまたはビルドを実行           | 本番ビルド、セキュリティ、ドキュメント、依存関係、PR ポリシーゲート    |
| 自動化では振る舞いを証明できない場合にのみ手動操作／ライブチェックを実行 | ワークフローで構成されたジョブ間統合チェックとプラットフォームチェック |

対象を絞ったループが成功することは、変更された契約に関する証拠ではありますが、無関係な CI チェックも
成功することの証明ではありません。逆に、ローカルでの編集のたびにリポジトリ全体のマトリクスの完了を待つ必要はありません。

## リコンシリエーションチェックリスト

レビューを依頼する前に：

- PR のベースが、引き続きアクティブな `release/v*` ブランチのうち最上位であることを確認します。
- そのベースをフェッチし、ブランチを作成してから追加されたコミットをレビューします。
- `git diff <active-base>...HEAD` を確認し、意図しない変更や生成物の不要な差分がないか調べます。
- カタログおよび生成ドキュメントの競合は、ソースを更新して出力を再生成することで解決します。
- リコンシリエーション後、PR の説明に記載された対象を絞ったテスト／ゲートをすべて再実行します。
- ベースが移動したことに合わせるためだけに、アサーションを弱めたり、必須テストを削除したりしてはいけません。

リリース凍結とリターゲットのルールについては、
[ブランチおよびリリースモデル](BRANCHING_MODEL.md)を参照してください。CI の完全な一覧については、
[品質ゲートリファレンス](../architecture/QUALITY_GATES.md)を参照してください。
