Web Cookieプロバイダーを使用すると、APIキーの代わりに既存のブラウザーセッションを通じてOmniRouteからAIサービスを利用できます。Webサイト経由ですでにサービスへのアクセス権があり、OmniRouteでも同じ認証済みセッションを使用したい場合に便利です。

APIキープロバイダーとは異なり、Web Cookieプロバイダーは、ブラウザーがWebサイトに送信する認証情報を使用して認証します。

---

# 始める前に

> **重要:** 認証情報は必ずブラウザーのCookieストレージからではなく、**実際のネットワークリクエスト**からコピーしてください。

認証に関する問題の多くは、Cookieを誤った場所からコピーすることが原因です。

## Cookieストレージからコピーしないでください

ほとんどのブラウザーでは、保存されているCookieを次の場所から確認できます。

```
DevTools
→ Application（またはStorage）
→ Cookies
```

これらのCookieは正しく見える場合でも、次のような状態になっている可能性があります。

- 古くなっている
- 不完全である
- 認証済みリクエストでのみ送信されるCookieが含まれていない

これらの値は有効に見えても、使用すると認証に失敗する場合があります。

## 実際のリクエストからコピーする

代わりに、成功したリクエストのCookieを使用してください。

```
DevTools
→ Network
→ ページを更新
→ チャットまたは会話のリクエストを開く
→ Request Headers
→ Cookie
```

`Cookie`リクエストヘッダーには、ブラウザーが正常に使用した認証情報がそのまま含まれています。

ほとんどのWeb Cookieプロバイダーでは、この値をOmniRouteに貼り付けます。

---

# 一般的なセットアップ

セットアップ手順は、ほとんどのWeb Cookieプロバイダーで共通です。

1. プロバイダーのWebサイトにサインインします。
2. ブラウザーの開発者ツールを開きます。
3. **Network**タブを開きます。
4. ページを更新します。
5. 認証済みのチャットまたは会話のリクエストを開きます。
6. 必要な認証情報をコピーします。
7. OmniRouteを開きます。
8. **Providers → Add Provider**に移動します。
9. 使用するWeb Cookieプロバイダーを選択します。
10. 認証情報を貼り付けます。
11. **Test Connection**をクリックします。
12. プロバイダーを保存します。

必要な認証情報はプロバイダーによって異なります。

## NoTrack (notrack-web)

NoTrack ([notrack.ai](https://notrack.ai)) は、登録不要で利用できる無料の一般消費者向けチャットプラットフォームです。初回アクセス時に匿名でセッションが作成され、`uid`、`si_usr_id`、`si_ses_id` の3つの Cookie によって維持されます。OmniRoute は、単一のモデル ID（`notrack-c`、エイリアスは `ntw`）を介して、同じ `/api/dispatch` エンドポイントをプロキシします。

### 接続手順

1. ブラウザで [notrack.ai](https://notrack.ai) を開き、匿名セッション Cookie が設定されるまで待ちます。
2. **DevTools → Network** を開き、ページを更新して、任意の `/api` リクエストをクリックします。
3. **Request Headers** で、`Cookie` ヘッダーの値全体をコピーします。
4. OmniRoute で、**Providers → Add Provider → NoTrack Web (Free)** に移動します。
5. Cookie 文字列を `apiKey` フィールドに貼り付け、**Save** をクリックします。

OmniRoute は、貼り付けられた文字列から `uid`、`si_usr_id`、`si_ses_id` を抽出し、それらのペアのみを含むクリーンな `Cookie` ヘッダーを再構築します。また、存在する場合は `nt_session`（ログイン済みアカウントに設定される `ntk_…` トークン）も追加されます。3つのうちいずれかが欠けている場合、運用者が別の形式を試せるよう、貼り付けられた元の文字列が変更されずに転送されます。

### モデル ID

| モデル ID   | 表示名    | 備考                                                                   |
| ----------- | --------- | ---------------------------------------------------------------------- |
| `notrack-c` | NoTrack C | デフォルト — アップストリームのディスパッチモデル `C`。                |
| `C`         | NoTrack C | `notrack-c` のエイリアス（アップストリームの生のディスパッチコード）。 |
| `notrack`   | NoTrack C | `notrack-c` のエイリアス。                                             |
| `ntw`       | NoTrack C | `notrack-c` の短縮エイリアス。                                         |

4つのモデル ID はすべて、同じアップストリームのディスパッチモデル（`C`）にマッピングされます。

### リクエストオプション

エグゼキューターは、リクエストボディで次のオプションフィールドを受け付けます。

| ボディフィールド      | デフォルト | 用途                                                                                  |
| --------------------- | ---------- | ------------------------------------------------------------------------------------- |
| `notrack_mode`        | `usual`    | ディスパッチモード（自由形式の文字列。アップストリームは `usual` などを受け付けます） |
| `notrack_max_turns`   | `6`        | 回答するまでにアップストリームが実行できる内部ターン数。                              |
| `notrack_chat_id`     | `null`     | 既存のアップストリームチャットを再開します（新しいチャットの場合は省略）。            |
| `notrack_attachments` | `[]`       | アップストリームの添付ファイル記述子をそのまま渡す配列。                              |
| `notrack_regenerate`  | `false`    | 前のターンに対する回答の再生成をリクエストするには `true` に設定します。              |

### 機能

- **ストリーミングおよび非ストリーミング**のチャット補完。
- **ツール呼び出し** — リクエストに `tools: [...]` を設定します。エグゼキューターはそれらをツール呼び出しエンベロープのコントラクトにシリアライズし、モデルの応答を解析して OpenAI の `tool_calls` に戻します。
- **`response_format`** — `json_object` と `json_schema` がサポートされています。エグゼキューターはモデルの応答から最初の JSON オブジェクトを抽出し、文字列化してから返します。
- **推論ヒント** — アップストリームが `thinking` イベントを送信すると、エグゼキューターは `reasoning` デルタを出力します。

### 制限事項

- アップストリームでは匿名利用のクォータが適用されます。上限に達すると、エグゼキューターは分かりやすいメッセージとともに 429 を返します。
- すべてのモデル ID は同じアップストリームのディスパッチモデルに解決され、モデルごとの切り替えはありません。
- エグゼキューターはアップストリームの `/api/chats` エンドポイントを呼び出さないため、チャット履歴やセッションは自動管理されません。既存のアップストリームチャットを再開するには `notrack_chat_id` を使用してください。

# Web Cookie プロバイダーでできることとできないこと

Web Cookie プロバイダーは、Web サイトのチャットインターフェースを再利用します。公式 API と同じ機能を提供するものでは**ありません**。

## サポート対象

- 既存のブラウザーセッションを使用した認証
- アカウントで利用可能なモデルへのアクセス
- チャット応答のストリーミング
- APIキー不要

## サポート対象外

- 関数呼び出し
- ツール呼び出し
- ファイルの自動編集
- エージェント型IDEワークフロー
- API限定機能

これは想定されている動作であり、**バグではありません**。

ツールの実行、ファイルの自動編集、またはその他のエージェントワークフローが必要な場合は、Web Cookieプロバイダーではなく、**APIキープロバイダー**を使用してください。

# 検証に関する注意事項

**Test Connection**またはCookieの検証が成功しても、指定された認証情報が想定される形式に見えることを確認しているだけです。

Issue #7857が解決されるまでは、検証に成功しても、プロバイダーの認証が成功することは**保証されません**。

認証が引き続き失敗する場合は、ブラウザーのCookieストレージではなく、実際のネットワークリクエストから認証情報をコピーしたことを確認してください。

---

# トラブルシューティング

## 認証に失敗する

認証情報が次の場所からコピーされたことを確認してください。

```
Network
→ Request Headers
→ Cookie
```

次の場所からコピーしたものは使用しないでください。

```
Application
→ Cookies
```

---

## ブラウザーではCookieが機能するがOmniRouteでは機能しない

一部のプロバイダーには、認証済みリクエストでのみ送信されるCookieが含まれています。

会話を正常に開いた後、新しいネットワークリクエストから認証情報を再度コピーしてください。

---

## セッションの有効期限切れ

Web Cookieプロバイダーは、既存のブラウザーセッションを使用します。

ブラウザーセッションの有効期限が切れた場合、またはサインアウトした場合は、新しい認証情報一式をコピーする必要があります。サポートされているWebプロバイダーのCookie更新を自動化するには、付属ツールの[Browser Session Sync Extension](../guides/SESSION-SYNC-EXTENSION.md)を参照してください。

---

## Test Connectionは成功するがリクエストが失敗する

Issue #7857が解決されるまでは、検証に成功しても、認証リクエストが成功することは保証されません。

さらにトラブルシューティングを行う前に、新しい認証済みリクエストから認証情報を再度コピーしてください。

# ベストプラクティス

- 新しい認証済みリクエストから認証情報をコピーしてください。
- 古いCookieの再利用は避けてください。
- Web Cookieプロバイダーを使用している間は、ブラウザーセッションをアクティブな状態に保ってください。
- コピーしたCookieは機密性の高い認証情報として扱ってください。
- 関数呼び出しやエージェントワークフローが必要な場合は、APIキープロバイダーを使用してください。
