リレー（Vercel、Deno、Cloudflare）は、サーバーレスバックエンド上でアップストリーム接続を終端します。これにより、プロバイダーの API キーをサーバー側に保持しながら、OmniRoute は安定したリージョンから外部へ通信できます。このドキュメントでは、運用担当者が本番環境で遭遇する 2 つの障害モードと、それぞれに対して OmniRoute が提供する復旧方法について説明します。

## リレー認証情報の保存方法

**Settings → Proxy Pool → Deploy Relay** からリレーをデプロイすると、デプロイフローによってリレーの認証トークンがプロキシの `notes` JSON フィールドに保存されます。

- `STORAGE_ENCRYPTION_KEY` が設定されている場合、トークンは `relayAuthEnc`
  として保存されます（保存時に AES で暗号化）。
- それ以外の場合、プレーンテキストの `relayAuth` として保存されます。

リクエスト時には `extractRelayAuth(notes)` が存在する形式の値を返すため、再起動後もリレーは動作し続けます。

## 障害モード 1 — キーのローテーション後にトークンを復号できない

**症状:** 以前は動作していたリレーが、環境またはシークレットマネージャーで
`STORAGE_ENCRYPTION_KEY` をローテーションした後、アップストリームの `401`/認証
エラーを返すようになります。保存されている `relayAuthEnc` blob を復号できなくなったため、`extractRelayAuth` は空文字列を返し、リレーは認証情報を送信しません。

**復旧 — その場で修復（再デプロイ不要）:**

1. **Settings → Proxy Pool** を開きます。
2. 認証情報が欠落しているリレーの行には、黄色の `auth missing` バッジと
   **Repair** ボタンが表示されます。
3. **Repair** をクリックします。OmniRoute は
   `POST /api/settings/proxies/[id]/repair-relay` を呼び出し、次の処理を行います。
   - **現在の**キーで `relayAuthEnc` を復号する
   - プレーンテキストの `relayAuth` を `notes` に書き戻す
   - `{ repaired: true, mode: "recovered" }` を返す

デプロイ用の認証情報を再入力することなく、リレーはサービス提供を再開します。

これは、現在の `STORAGE_ENCRYPTION_KEY` で引き続き blob を復号できる場合にのみ機能します。移行を行わずにキーをローテーションした場合、その blob は復旧できません。

## 障害モード 2 — 復旧不可能なトークン（以前のキーが失われた場合）

**症状:** **Repair** をクリックすると、
`{ repaired: false, mode: "redeploy", status: 409 }` が返されます。

**復旧 — 再デプロイ:**

保存されたトークンは、現在のキーでは復旧できません。最初に使用したものと同じモーダル（**Deploy Relay** メニュー → Vercel / Deno
/ Cloudflare）からリレーを再デプロイします。デプロイフローによって新しいトークン（現在のキーで暗号化）が書き込まれ、その行の `auth missing` バッジが消えます。

UI では、トークンが復旧不可能な場合、**Repair** ボタン自体が再デプロイ用モーダルを開くため、手動で探す必要はありません。

## 障害モード 3 — リレーには到達できるが正常ではない

**症状:** プロキシテスト（`speed` ボタン）ではリレーが稼働中と表示されますが、リクエストが断続的に失敗します。

OmniRoute の自動テストプローブから返されるリレー認識用ヘッダーを確認してください
（**Settings → Proxy Pool** と `relayTested` / `relayAlive` カウンターを参照）。

- `x-relay-url` — 応答したリレーバックエンド。
- `x-relay-mode` — そのリクエストの `ts` | `bifrost` | `auto`。
- `x-relay-attempts` — 成功するまでに試行されたリレーホップ数。
- `x-relay-fallback` — リクエストが優先バックエンドから TypeScript リレーへフォールバックした場合は `true`。

`relayAlive` が低く、`x-relay-fallback` の発生率が高い場合は、サイドカーバックエンドが正常ではありません。バックエンドを修復するか、リレーバックエンド戦略を `ts` に切り替えてください（`RELAY_BACKEND_STRATEGY.md` を参照）。

## API リファレンス

| メソッド | パス                                      | ボディ                  | 成功                                                                                                                                         | 失敗                                                                                                    |
| -------- | ----------------------------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `POST`   | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | 再導出した場合は `200 { repaired: true, mode: "recovered" }`、プレーンテキストがすでに存在する場合は `200 { repaired: false, mode: "noop" }` | 復旧不可能な場合は `409 { mode: "redeploy" }`、リレータイプでない場合は `400`、見つからない場合は `404` |

一覧取得ルート `GET /api/settings/proxies` は、各項目にシークレットを含まない
`relayInfo: { isRelay, authMissing, repairMode }` を付加します。これにより、ダッシュボードはトークンを一切公開することなく、修復操作用の UI を表示できます。
