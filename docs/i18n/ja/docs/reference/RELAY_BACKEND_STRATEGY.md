## 概要

OmniRoute は現在、`/api/v1/relay/chat/completions` で 3 つのリレーモードをサポートしています。

- `ts`: TypeScript リレーをプロセス内で使用します。
- `bifrost`: Bifrost ゲートウェイを強制的に使用します。
- `auto`: 利用可能な場合は Bifrost を優先し、障害時には TypeScript にフォールバックします。

高いリクエストレート（1 日あたりのトークン数が多く、ほぼ一定のスループット）で運用する場合、最適な戦略は、停止したサイドカーによってホットパスがブロックされないように、フォールバックパスを明示的かつ高速に保つことです。

## モードの動作

- `ts`
  - 運用上の複雑さが最も低いモードです。
  - すべてのルーティングと検証が Node 内で実行されます。
  - 可用性がサイドカーに依存しません。
- `bifrost`
  - すべてのリクエストを強制的にサイドカーゲートウェイ経由にします。
  - 自動フォールバックはありません。
  - サイドカーの正常性とレイテンシーが保証されている場合にのみ有用です。
- `auto`
  - サイドカーが有効で到達可能な場合に使用されます。
  - 試行が失敗するとフォールバックヘッダーが設定され、トラフィックが TS に戻されるため、リクエストの成功が一定の範囲内で維持されます。
  - 厳密なサイドカー限定ルーティングよりも稼働率を重視する本番環境では、このモードが最も安全な選択肢です。

## 現在の 9router と CLIPROXYAPI の比較

9router と CLIPROXYAPI は、どちらも従来からアップストリームプロバイダー向けの互換性パスを提供してきた統合機能です。

- 9router は、アップストリームのオーケストレーションと互換動作のための組み込みパスです。
- CLIPROXYAPI は、CLI / SDK 形式のトラフィック向けのプロキシ API ブリッジです。
- Bifrost は、専用のサイドカーのような中継と低レイテンシーのローカルディスパッチが必要な場合に使用する外部化されたパスとして、安定化が進められています。

現在 9router/CLIPROXYAPI を比較している場合:

- 引き渡し前に、API ルート内でリクエスト署名、許可リストのチェック、DB ポリシーゲートを維持してください。
- ワークフローで厳密なサイドカー動作とリクエストごとのばらつきの低減が必要な場合は、`OMNIROUTE_RELAY_BACKEND=bifrost` を使用してください。
- インシデント発生時に段階的に機能を縮退させながらサイドカーの耐障害性を確保する必要がある場合は、`OMNIROUTE_RELAY_BACKEND=auto` を使用してください。

## バックエンド境界の契約

安定したプロダクト境界は OmniRoute リレー API であり、ダッシュボードの実装ではありません。Next.js ダッシュボードはローカルサービスのインストール、設定、監視を行えますが、リクエストルーティングはリレー API を通じて開始し、その境界の背後で引き渡す必要があります。

長期的なバックエンドの選択肢:

- TypeScript リレーは、プロセス内のポリシーおよびフォールバックパスとして維持します。認証、許可リスト、リクエストの正規化、アカウンティング、安全性チェックは、バックエンドへの引き渡し前にここで実行します。
- デプロイでルーティングのばらつきの低減、プロバイダーの一元的なローテーション、または複数の OmniRoute レプリカへのスケールアウトが必要な場合は、Bifrost を推奨される高スループットの Tier-1 サイドカーとして使用します。
- 9router と CLIPROXYAPI は、組み込みの互換性サービスとして維持します。これらは監視対象のローカルプロセスとして実行され、そのプロバイダー/CLI 動作が望ましいアダプターである場合に有用ですが、デフォルトの Tier-1 ルーティングエンジンにすべきではありません。
- ダッシュボードからホットパスへ任意のサービス URL を渡さないでください。UI から提供される URL は設定入力です。ルーティングコードは、サーバー側の設定とスーパーバイザーの状態から、登録済みで正常性チェック済みのバックエンドを解決する必要があります。
- 現在は、監視対象サービスにループバック HTTP を優先してください。管理対象プロセスがすでに HTTP 互換 API を公開しており、ルートガードが境界を監査でき、障害およびフォールバックの動作がリクエストログで確認できるためです。将来 SDK またはソケットトランスポートを追加する価値があるのは、分離やフォールバックのセマンティクスを弱めることなく、p99 ルーティングレイテンシーを測定可能な形で短縮できる場合に限られます。

したがって、非常に高スループットなデプロイでは、Bifrost を有効にした `auto` がデフォルトの選択肢です。ホットパスでは Go サイドカーを使用しながら、成功率を維持するために TypeScript フォールバックを保持します。段階的な機能縮退よりも厳密なサイドカー限定の動作が重要な場合にのみ、`bifrost` を使用してください。

## 高スループット向けのガイダンス

高い RPM/RPS を継続的に維持し、厳格な成功率 SLO を達成するには:

1. 実用的なクールダウンと障害テレメトリを設定して `auto` を使用します。
2. アップストリームの検証と API キーのチェックを TypeScript ルート境界に維持します。
3. 明示的なヘッダー/カウンターを有効にして、アラートシステムがフォールバックの頻度と理由を検出できるようにします。
4. サイドカーのタイムアウトを、いつまでも待機するのではなく高速に失敗するように調整します。
5. サービスの自動再起動と正常性テレメトリのループを健全に保ち、フォールバックが本当に例外的な事象となるようにします。

## 推奨ベースライン

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- API キー、許可リスト、サニタイザー、レート制限のチェックをルートハンドラーで有効に維持します（これらは常にダウンストリームへの転送前に実行されます）。
- リバースプロキシとリクエストログからフォールバックメトリクスをエクスポートし、サイドカーの停止を 1 分以内に検出できるようにします。

## プロバイダープラグイン契約

サイドカーは TypeScript エグゼキューターの内部実装に依存するのではなく、JSON セーフなプロバイダープラグイン
マニフェストを通じてプロバイダーのメタデータをインポートする必要があります。サイドカーの
適格性に関する契約と移行フェーズについては、[プロバイダープラグインマニフェスト](./PROVIDER_PLUGIN_MANIFEST.md)を参照してください。
