`open-sse/config/providerPluginManifest.ts` mentakrifkan kontrak pemalam penyedia yang selamat untuk JSON. `open-sse/config/providerPluginManifestRegistry.ts` mengikat kontrak tersebut kepada pendaftaran penyedia semasa untuk sidecar seperti Bifrost, CLIProxyAPI, atau penghala Go/Rust pada masa hadapan. Pendaftaran TypeScript kekal sebagai sumber kebenaran, tetapi sidecar boleh menggunakan manifes tanpa mengimport kod pelaksana, nilai lalai OAuth, pengepala, atau keadaan persekitaran proses.

Manifes yang sama tersedia melalui HTTP di
`GET /api/v1/provider-plugin-manifest` untuk sidecar yang berjalan di luar proses.

OmniRoute mengiklankan URL tersebut kepada Bifrost dan CLIProxyAPI melalui pengepala permintaan
`X-OmniRoute-Provider-Manifest-Url`. Tetapkan
`OMNIROUTE_PROVIDER_MANIFEST_URL` apabila sidecar memerlukan URL rangkaian awam atau kontena dan bukannya asal permintaan setempat.

## Menyegarkan Manifes

Titik akhir HTTP mengembalikan `Cache-Control: public, max-age=60` dan
`ETag` yang kukuh. Sidecar harus mengekalkan manifes terakhir yang telah disahkan dan menghantar ETag-nya
dalam `If-None-Match` semasa menyegarkan. Respons `304 Not Modified` tidak mempunyai isi;
sidecar mengekalkan manifes yang dicache. Jika tiada manifes cache yang telah disahkan,
sidecar mesti membuat permintaan tanpa syarat dan bukannya menerima `304`.

## Matlamat

Mengalihkan metadata penyedia ke arah kontrak pemalam supaya laluan permintaan aktif
akhirnya boleh dikendalikan oleh sidecar dengan kependaman lebih rendah, sementara OmniRoute mengekalkan
laluan TypeScript sebagai pintu dasar dan sandaran. Manifes ini bersifat tambahan: ia
tidak mengubah penghalaan permintaan dengan sendirinya.

## Kontrak

Manifes mengandungi:

- id dan alias penyedia
- format huluan dan nama pelaksana
- jenis pengesahan, pengepala pengesahan, dan awalan pengesahan pilihan
- metadata titik akhir statik
- kelayakan sidecar dan sebab yang jelas apabila penyedia harus kekal pada TS
- metadata model yang selamat untuk JSON seperti panjang konteks, bendera penglihatan/penaakulan, dan
  parameter yang tidak disokong
- tag keupayaan termasuk `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch`, dan `usage-supported`

Manifes sengaja mengecualikan:

- rahsia klien OAuth dan nilai rahsia lalai
- penyelesaian persekitaran masa jalan
- pengepala permintaan dan pembantu kelayakan awam
- pembina URL dinamik
- fungsi pelaksana
- butiran dalaman kumpulan sesi

## Tag Keupayaan

`capabilities` ialah tatasusunan tag terisih yang diperoleh daripada entri pendaftaran. Penyepadu
harus menganggapnya sebagai jawapan yang boleh dibaca mesin kepada "apakah yang boleh dilakukan oleh penyedia ini", dan bukannya
membaca semula sumber TypeScript.

| Tag                  | Maksud                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------ |
| `apikey`             | Menerima kunci API (`authType` ialah `apikey` atau `optional`).                            |
| `oauth`              | Menggunakan aliran OAuth atau sesi.                                                        |
| `responses`          | Mendedahkan URL asas OpenAI Responses-API.                                                 |
| `passthrough-models` | Menyediakan model terus daripada huluan dan bukannya katalog statik.                       |
| `custom-executor`    | Menjalankan pelaksana bukan lalai, maka ia kekal pada laluan TypeScript.                   |
| `sidecar-candidate`  | Mencerminkan `sidecar.eligible` — selamat dipertimbangkan untuk import sidecar.            |
| `usage-fetch`        | Mempunyai pengambil penggunaan atau kuota yang telah disambungkan (`getUsageForProvider`). |
| `usage-supported`    | API penggunaan menerima penyedia ini (`isSupportedUsageConnection`).                       |

`usage-fetch` adalah untuk penemuan sahaja. Ia melaporkan bahawa OmniRoute tahu cara membaca penggunaan bagi
penyedia tersebut; ia tidak mengaktifkan pengambilan, mengubah semantik kuota, atau membayangkan bahawa
widget kuota Dashboard didayakan untuk penyedia tersebut — widget itu dikawal secara berasingan oleh
`USAGE_SUPPORTED_PROVIDERS`. Sumber kebenaran ialah `USAGE_FETCHER_PROVIDERS` dalam
`open-sse/services/usage/fetcherProviders.ts`.

Senarai itu menggunakan rentetan yang diterima oleh penghantar penggunaan sebagai kunci, jadi ia mencampurkan id kanonik
dengan alias dan sedikit lebih panjang daripada bilangan penyedia yang ditag: entri yang
bukan penyedia sembang dalam pendaftaran manifes (contohnya penyedia carian `firecrawl`
dan penyedia ACP `amazon-q`) tidak mempunyai entri manifes untuk ditag.

`usage-supported` menunjukkan sama ada laluan penggunaan pelayan dan Dashboard menerima sambungan
bagi penyedia tersebut. Ia mencerminkan `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
dan `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), yang kedua-duanya dikawal oleh
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). Tidak seperti
`usage-fetch`, ia dihasilkan berdasarkan id penyedia sahaja — pengawal masa jalan menjalankan
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` tanpa penyelesaian alias, maka manifes
mengekalkan peraturan yang sama. Kedua-dua tag mempunyai skop yang berbeza: 3 penyedia hanya mempunyai
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) dan 1 hanya mempunyai
`usage-supported` (`xiaomi-mimo-token-plan`), maka kewujudan satu tag tidak membayangkan kewujudan tag yang lain.

## Penggunaan Sidecar

Sidecar harus menganggap `sidecar.eligible` sebagai isyarat calon yang konservatif, bukan
sebagai keputusan penghalaan tanpa syarat. Sasaran import pertama hendaklah
penyedia yang menggunakan kunci API dan titik akhir statik dengan pelaksana lalai. Penyedia dengan
pelaksana web tersuai, aliran OAuth/sesi, pembina URL dinamik, atau konfigurasi kumpulan
hendaklah kekal pada laluan sandaran TypeScript sehingga sidecar melaksanakan tingkah laku
yang setara dan telemetri membuktikan kesetaraan.

Fasa migrasi yang dicadangkan:

1. Jana dan sahkan manifes pemalam penyedia daripada pendaftaran TS.
2. Ajar Bifrost atau CLIProxyAPI untuk mengimport manifes bagi penyedia
   yang menggunakan kunci API/titik akhir statik.
3. Halakan penyedia yang layak melalui sidecar di sebalik `OMNIROUTE_RELAY_BACKEND`
   sambil memastikan sandaran TS kekal didayakan.
4. Naik taraf penyedia hanya apabila kadar kejayaan, kependaman p99, tingkah laku penstriman,
   dan pengendalian parameter yang tidak disokong sepadan dengan laluan TS.
5. Tambahkan pemalam natif sidecar untuk pelaksana tersuai, satu keluarga penyedia pada satu
   masa.

## Mengapa Tidak Membenamkan Penyedia Secara Langsung Dalam Next

Frontend Next tidak seharusnya mengendalikan pelaksanaan penyedia. Ia seharusnya memanggil sempadan
API. Backend kemudiannya boleh menentukan sama ada hendak menggunakan pelaksana TypeScript,
Bifrost, CLIProxyAPI, atau sidecar natif pada masa hadapan. Ini memastikan penandatanganan permintaan,
semakan senarai yang dibenarkan, dasar DB, dan tingkah laku sandaran dipusatkan sebelum sebarang
penyerahan kepada sidecar.
