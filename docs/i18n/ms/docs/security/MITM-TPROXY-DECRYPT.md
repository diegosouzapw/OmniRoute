Penyahsulitan telus TPROXY ialah **mod tangkapan ke-5** OmniRoute untuk tindanan MITM
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md).
Ia memintas dan **menyahsulit** trafik HTTPS keluar setempat pada Linux menggunakan
TPROXY kernel + penghalaan dasar — **tanpa** memalsukan `/etc/hosts` dan
**tanpa** mengubah tetapan proksi sistem seluruh OS. Ia sesuai untuk persekitaran
tanpa antaramuka grafik (tiada suntingan DNS untuk dibersihkan) dan peraturan tembok api
dikosongkan secara automatik apabila sistem dibut semula.

Tidak seperti mod tangkapan lain, TPROXY tidak memerlukan persediaan bagi setiap hos:
ia memintas secara telus hos destinasi **sebarangan** pada port sasaran, menamatkan TLS
dengan sijil daun yang dikeluarkannya serta-merta bagi setiap nama hos SNI, menangkap
pertukaran yang telah dinyahsulit, dan menyulitkan semula permintaan ke destinasi asal.

> **Linux sahaja, root sahaja, ikut serta.** Mod ini memerlukan Linux, tambahan natif
> yang dibina dengan rantaian alat C, dan keupayaan **CAP_NET_ADMIN** (lazimnya root). Ia dikawal
> melalui API AgentBridge gelung balik sahaja dan dinyahdayakan secara lalai. CA
> MITM dipercayai yang boleh menandatangani sebarang hos merupakan keupayaan yang berkuasa — lihat [§6 Keselamatan](#6-security).

**Sumber:** `src/mitm/tproxy/`
**Laluan API:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**Togol papan pemuka:** Traffic Inspector → bar alat mod tangkapan → **"Penyahsulitan TPROXY"** ⚠
**Lihat juga:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 Apakah cirinya dan bila perlu menggunakannya

Setiap satu daripada empat mod tangkapan lain mempunyai kekangan:

| Mod                   | Cara trafik dihalakan                                 | Kekangan                                                |
| --------------------- | ----------------------------------------------------- | ------------------------------------------------------- |
| AgentBridge           | Pemalsuan DNS `/etc/hosts` bagi set hos tetap         | hanya hos ejen IDE yang didaftarkan                     |
| Hos Tersuai           | Pemalsuan DNS `/etc/hosts` bagi setiap hos            | satu entri bagi setiap hos; sudo untuk menyunting hos   |
| HTTP_PROXY            | Pemboleh ubah persekitaran `HTTP_PROXY`/`HTTPS_PROXY` | hanya aplikasi yang mematuhi pemboleh ubah persekitaran |
| Proksi seluruh sistem | Tetapan proksi OS                                     | mengubah keadaan global; perlu dikembalikan             |

Penyahsulitan telus TPROXY sebaliknya menghalakan trafik pada lapisan **kernel**. Ia
menandakan sambungan TCP keluar setempat yang baharu ke port sasaran (lalai `443`) dalam
rantai `mangle OUTPUT`, satu `ip rule` menghalakan semula paket yang ditandakan kepada penghantaran setempat,
dan apabila dimasukkan semula, sasaran `TPROXY` `mangle PREROUTING` menyerahkannya kepada
pendengar **IP_TRANSPARENT** — yang kemudian menamatkan TLS dan menangkap teks biasa.

Gunakannya apabila anda mahu menangkap dan menyahsulit trafik daripada proses yang:

- berkomunikasi dengan hos yang tidak didaftarkan oleh AgentBridge, dan
- tidak mematuhi `HTTP_PROXY`, dan
- anda tidak mahu mengganggunya dengan perubahan proksi seluruh sistem.

Oleh sebab pemintasan berlaku dalam kernel, proses asal **tidak memerlukan
sebarang perubahan konfigurasi** — tetapi proses tersebut mesti mempercayai CA dinamik yang
dipasang oleh OmniRoute (lihat [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 Keperluan

| Keperluan         | Perincian                                                                                                                                                     |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**            | Linux sahaja — **IP_TRANSPARENT** ialah pilihan soket khusus Linux. Pemuat mengembalikan "tidak tersedia" pada setiap platform lain.                          |
| **Keistimewaan**  | Keupayaan **CAP_NET_ADMIN** untuk mencipta soket telus dan menggunakan peraturan `iptables`/`ip` — dalam amalan, jalankan sebagai root.                       |
| **Tambahan asli** | Tambahan N-API kecil (`src/mitm/tproxy/native/transparent.c`) mesti dibina atau dibekalkan sebagai prabinaan. Lihat [§3](#3-the-native-ip_transparent-addon). |
| **Modul kernel**  | `iptables` dengan sokongan padanan `TPROXY`, `mangle`, dan `mark` (disahkan dengan kernel 6.8.0).                                                             |

**Degradasi secara terkawal:** jika mana-mana keperluan tiada (bukan Linux, tiada rantai alat,
tambahan tidak dibina), pemuat tambahan (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
mengembalikan `null` dan bukannya melontarkan ralat. Status mod tangkapan kemudiannya melaporkan
`available: false`, suis papan pemuka **dinyahdayakan** dengan petua alat
"Penyahsulitan TPROXY memerlukan Linux + root + tambahan asli", dan bahagian lain
OmniRoute terus berfungsi.

## §3 Tambahan asli IP_TRANSPARENT

Modul `net` Node tidak boleh menjalankan `setsockopt(IP_TRANSPARENT)` _sebelum_ `bind()`, yang
diperlukan oleh TPROXY (jika tidak, kernel akan menggugurkan paket yang dihalakan semula). Tambahan
(`src/mitm/tproxy/native/transparent.c`, dibina melalui `binding.gyp`) ialah modul N-API
kecil yang mendedahkan tiga fungsi, digunakan melalui `transparentSocket.ts`:

| Fungsi tambahan                       | Operasi soket                                                                                       | Digunakan untuk                                                                 |
| ------------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, mengembalikan fd mentah | pendengar tangkapan telus (Node menggunakan fd melalui `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | `setsockopt` **SO_MARK** pada fd sedia ada                                                          | antipengelungan (menandai soket milik proksi sendiri)                           |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **sebelum** `connect()` tanpa sekatan, mengembalikan fd                    | pemajuan huluan yang disulitkan semula (SYN membawa tanda tersebut)             |

Destinasi asal dibaca daripada `socket.localAddress`/`localPort` — TPROXY
mengekalkannya, jadi tiada carian **SO_ORIGINAL_DST**/NAT.

### Membina tambahan

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- Semasa `npm run build`, `scripts/build/build-tproxy-native.mjs` menjalankan `node-gyp
rebuild`. Ia **khusus Linux dan tidak membawa maut** — ketiadaan rantai alat hanya menyebabkan
  mod tangkapan tidak tersedia.
- `assembleStandalone.mjs` menyalin `build/Release/transparent.node` ke dalam berkas
  kendiri; `transparentSocket.ts` mencarinya secara relatif kepada modul dan juga
  secara relatif kepada cwd (`<cwd>/src/mitm/tproxy/native/...`).
- `build/` dan `prebuilds/` diabaikan oleh git — binari tersebut **dibina, tidak pernah
  dikomit**.

Pemuat menyemak, mengikut turutan keutamaan:
`native/build/Release/transparent.node`, kemudian `native/prebuilds/transparent.node`
(kedua-duanya secara relatif kepada modul dan di bawah `<cwd>/src/mitm/tproxy/`).

## §4 CA dinamik per-SNI dan pemasang stor kepercayaan

> **Kemas kini #6684:** pelayan statik AgentBridge (`src/mitm/server.cjs`) kini
> berkongsi corak seni bina CA/leaf yang sama ini dan bukannya menggunakan satu
> leaf ditandatangani sendiri yang statik. Ia menggunakan tika CA yang **berbeza**
> (`src/mitm/cert/rootCa.ts`, disimpan secara berterusan di `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> dan dipasang di bawah slot stor kepercayaan `omniroute-mitm.crt` yang sedia ada
> (menggantikan leaf tunggal lama di situ — tiada pembersihan dwi-kepercayaan diperlukan),
> serta diasingkan sepenuhnya daripada slot `omniroute-tproxy-ca.crt` milik TPROXY
> di bawah. Pemasangan baharu AgentBridge mendapat model CA secara automatik;
> pemasangan yang sudah mempercayai leaf statik lama akan terus menggunakannya
> sehingga pengendali memilih untuk beralih melalui `MITM_ROOT_CA_ENABLED=true`
> (lihat `src/mitm/cert/migration.ts`) — CA MITM dipercayai yang boleh
> menandatangani leaf untuk **mana-mana** hos jauh lebih berkuasa berbanding leaf
> SAN tetap yang lama, maka pertukaran ini tidak sekali-kali berlaku secara senyap
> bagi pemasangan yang sudah dipercayai.

Dari segi sejarah, sijil MITM AgentBridge yang statik hanya berfungsi kerana
AgentBridge memalsukan DNS bagi set hos yang **tetap** (kini disatukan dengan
model di bawah). TPROXY memintas hos **sewenang-wenangnya**, maka pendengarnya
mesti membentangkan leaf yang sah untuk apa-apa SNI yang diminta oleh klien —
keperluan yang sama kini turut dikenakan pada AgentBridge untuk set penuh
`MITM_TOOL_HOSTS` (9 entri alat), dan bukan sekadar 4 hos antigravity.

### CA dinamik (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` menjalankan CA setempat (dibina berasaskan kebergantungan
`selfsigned`) yang:

- Menjana CA berjangka panjang melalui `generateMitmCa()` (CN `"OmniRoute MITM CA"`,
  kesahan 10 tahun, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  RSA 2048-bit / SHA-256).
- Mengeluarkan **satu leaf bagi setiap nama hos SNI apabila diperlukan** melalui
  `issueLeafCert()` (kesahan 1 tahun, `subjectAltName` = hos SNI) dan menyimpan
  satu `tls.SecureContext` dalam cache bagi setiap nama hos.
- Mendedahkan `createSNICallback()` untuk pelayan penamat TLS (lihat [§5](#5-how-decrypt-and-capture-work)).
- Boleh dibina dengan `existingCa` untuk memastikan CA kekal stabil merentas
  mula semula (supaya stor kepercayaan tidak perlu dipasang semula).

Kunci peribadi CA **tidak pernah meninggalkan mesin**.

### Pemasang stor kepercayaan (`src/mitm/tproxy/caTrust.ts`)

Klien yang dipintas mesti mempercayai CA dinamik, maka memulakan mod tangkapan
akan memasang sijil CA ke dalam stor kepercayaan OS di bawah **slot khusus** —
`omniroute-tproxy-ca.crt` (pemalar `TPROXY_CA_CERT_NAME`) — yang diasingkan
daripada slot sijil MITM statik (`omniroute-mitm.crt`) supaya kedua-duanya tidak
sekali-kali menimpa satu sama lain.

`installTproxyCa(caPem, sudoPassword?)` mengesan direktori sauh distro
(mengikut urutan: gaya Debian terlebih dahulu) dan menjalankan perintah segar
semula yang sepadan:

| Direktori sauh                              | Perintah segar semula    |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Pemasangan menempatkan sementara PEM ke dalam fail sementara, kemudian
menjalankan `mkdir -p` (dengan keistimewaan) pada direktori sauh, menggunakan
`cp` untuk menyalin fail sementara itu ke dalamnya, dan menjalankan perintah
segar semula. `uninstallTproxyCa()` hanya mengalih keluar slot khusus tersebut
(sambil membiarkan sijil MITM statik tidak disentuh) dan menyegarkan semula —
tiada operasi dilakukan pada sistem bukan Linux.

Semua perintah berkeistimewaan dijalankan melalui `execFileWithPassword`
(`src/mitm/systemCommands.ts`) — `spawn` dengan **tatasusunan argumen, tanpa shell,
tanpa interpolasi rentetan** (Peraturan Tegas #13). Apabila proses berjalan
sebagai root (contohnya VPS), sasaran dijalankan secara langsung dan kata laluan
tidak diperlukan; pada desktop bukan root, `sudoPassword` dihantar melalui
`sudo -S` pada stdin.

> `sudoPassword` desktop dibekalkan dalam badan POST untuk membenarkan
> pemasangan stor kepercayaan; ia diabaikan sepenuhnya apabila proses berjalan
> sebagai root.

## §5 Cara penyahsulitan dan penangkapan berfungsi

Saluran pemprosesan (semuanya di bawah `src/mitm/tproxy/`):

```
aplikasi setempat ──TCP/443──▶ mangle OUTPUT menandai sambungan (fwmark)
                               ip rule → jadual penghalaan setempat → lo
                               mangle PREROUTING TPROXY → pendengar IP_TRANSPARENT (port 8443)
                                   │  captureMode.ts: membaca destinasi asal daripada socket.localAddress
                                   ▼
                               tlsCapture.ts:
                                 1. Tamatkan TLS KLIEN dengan perantara daun per-SNI (dynamicCert)
                                 2. http.Server dalaman menghuraikan teks biasa yang dinyahsulitkan
                                 3. tangkap → globalTrafficBuffer.push() dengan source: "tproxy"
                                    (sanitizeHeaders + maskSecret digunakan)
                                 4. majukan dengan penyulitan SEMULA ke destinasi asal
                                    melalui soket bertanda pintasan (connectMarked, antigelung)
                                   │
                                   ▼
                               huluan asal (api.example.com)
```

- **Penamatan TLS** (`createTlsCaptureServer`): membalut soket mentah yang dipintas
  dalam `tls.TLSSocket` sisi pelayan menggunakan panggil balik SNI daripada CA dinamik,
  kemudian menyerahkan strim yang dinyahsulitkan kepada `http.Server` dalaman (kaedah
  penamatan MITM standard). Jangka hayat soket dihadkan oleh `MITM_IDLE_TIMEOUT_MS`
  supaya terowong yang tergantung tidak menghabiskan deskriptor fail.
- **Penangkapan** (`handleDecryptedRequest`): menolak `InterceptedRequest` dengan
  `source: "tproxy"`, status bermula sebagai `"in-flight"`, pengepala diproses melalui
  `sanitizeHeaders()` dan isi melalui `maskSecret()` sebelum dimasukkan ke dalam
  penimbal. Entri itu kemudiannya dikemas kini dengan respons, saiz dan kependaman.
- **Pemajuan dengan penyulitan semula** (`createForward` / `realForward`): menyulitkan
  semula ke destinasi asal. `rejectUnauthorized` secara lalai ialah **`true`** (selamat
  secara lalai) — sijil huluan disahkan terhadap SNI/Host yang diminta oleh klien,
  maka proksi menolak perkara yang sama seperti yang akan ditolak oleh klien asal.

### Antigelung (SO_MARK)

Oleh sebab peraturan menandai sambungan keluar setempat yang baharu, pemajuan
dengan penyulitan semula milik proksi **sendiri** biasanya akan dipintas semula —
menghasilkan gelung tanpa henti. Laluan pemajuan menghalang perkara ini dengan
tanda soket pintasan (**SO_MARK**):

- `realForward` membuka soket huluannya melalui `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  — `DEFAULT_BYPASS_MARK = 0x539` — yang menetapkan **SO_MARK** **sebelum** `connect()`,
  supaya SYN pemajuan membawa tanda pintasan.
- Peraturan `mangle OUTPUT` mengecualikan sambungan yang sudah membawa tanda pintasan
  (`-m mark ! --mark <bypassMark>`), supaya pemajuan proksi **tidak** ditandai semula
  dan tidak memasuki TPROXY semula.

> Nota pelaksanaan: soket bertanda pintasan mesti dipasang pada `createConnection`
> ejen (`https.request({ createConnection })` diabaikan secara senyap apabila ejen
> tersedia), jika tidak, pemajuan akan membuka soket tanpa tanda dan gelung akan
> kembali. Ini ialah pembetulan antigelung yang disahkan secara e2e.

## §6 Keselamatan

| Kawalan                                    | Butiran                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API gelung balik sahaja**                | `/api/tools/agent-bridge/tproxy` diliputi oleh awalan `/api/tools/agent-bridge/` dalam `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`). Penguatkuasaan gelung balik dijalankan **sebelum** pengesahan (Peraturan Tegas #15 + #17) — JWT yang bocor melalui terowong tidak boleh memulakan tangkapan TPROXY, yang menggunakan peraturan `iptables` dan memasang CA gedung amanah melalui proses anak. |
| **Slot CA khusus**                         | CA dinamik dipasang ke `omniroute-tproxy-ca.crt`, tanpa menimpa sijil MITM statik.                                                                                                                                                                                                                                                                                                                                |
| **Kunci CA tidak pernah meninggalkan hos** | `DynamicCertStore` menyimpan kunci CA dalam memori; kunci tersebut tidak dieksport.                                                                                                                                                                                                                                                                                                                               |
| **Penyamaran rahsia**                      | `maskSecret()` pada badan permintaan/respons dan `sanitizeHeaders()` pada pengepala dijalankan **sebelum** `globalTrafficBuffer.push()`.                                                                                                                                                                                                                                                                          |
| **Tiada interpolasi shell**                | Semua perintah `iptables`/`ip`/gedung amanah dijalankan melalui `execFile`/`execFileWithPassword` dengan tatasusunan argumen (Peraturan Tegas #13).                                                                                                                                                                                                                                                               |
| **Pengesahan sijil huluan**                | Pemajuan yang disulitkan semula mengesahkan sijil huluan secara lalai (`rejectUnauthorized: true`).                                                                                                                                                                                                                                                                                                               |
| **Sanitasi ralat**                         | Respons ralat laluan melalui `sanitizeErrorMessage()` (Peraturan Tegas #12).                                                                                                                                                                                                                                                                                                                                      |

**CA MITM ialah keupayaan yang amat berkuasa.** CA yang dipercayai oleh OS dan boleh menandatangani mana-mana
hos bermakna apa-apa yang dipintas oleh OmniRoute boleh dinyahsulit. Ia dikawal oleh
mod tangkapan TPROXY eksplisit yang setempat sahaja, dimatikan secara lalai, dan entri
gedung amanah dialih keluar apabila anda menghentikan mod tersebut.

## §7 Aplikasi / pengembalian semula firewall secara transaksional

Ranap tidak boleh sesekali meninggalkan peraturan `mangle` atau laluan lapuk. Pembina perintah
(`src/mitm/tproxy/commands.ts`) dan pelaksana (`src/mitm/tproxy/setup.ts`) menjamin bahawa
**pengembalian semula ialah songsangan tepat bagi aplikasi, dalam susunan terbalik**.

`applyTproxy(cfg)` menjalankan perintah aplikasi mengikut turutan; sekiranya berlaku **sebarang** kegagalan, ia menjalankan
`revertTproxy(cfg)` penuh secara usaha terbaik lalu melontarkan semula ralat — maka firewall sama ada
diaplikasikan sepenuhnya atau dikembalikan semula sepenuhnya, dan tidak pernah diaplikasikan separuh sahaja. `revertTproxy(cfg)` menjalankan
perintah songsangan dalam susunan terbalik dan mengabaikan kegagalan (idempoten — selamat untuk dipanggil
tanpa syarat, contohnya daripada pembersihan AgentBridge `repairMitm()`).

`validateTproxyConfig(cfg)` dijalankan sebelum sebarang perintah: port mestilah `1–65535`,
`mark`/`routeTable`/`bypassMark` mestilah integer positif, dan `bypassMark` mestilah
berbeza daripada `mark` (anti-gelung).

### Perintah aplikasi (mengikut turutan)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Pengembalian semula memadamkannya dalam susunan terbalik: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> Resipi ini **berasaskan OUTPUT** kerana kes penggunaan MITM ialah trafik keluar
> _setempat_ (aplikasi pada hos yang sama), yang tidak dapat dilihat oleh TPROXY dalam `PREROUTING`
> sahaja — `PREROUTING` hanya melihat trafik yang dimajukan. Rantaian `OUTPUT` menandakan sambungan
> setempat baharu, `ip rule` menghalakannya semula kepada penghantaran setempat (`lo`), dan
> `PREROUTING` kemudiannya menetapkannya kepada pendengar telus.

## §8 Konfigurasi

Permintaan mula (`POST /api/tools/agent-bridge/tproxy`) menerima medan berikut,
yang disahkan oleh `StartTproxyBodySchema` (`tproxy/route.ts`). Kesemuanya adalah pilihan
dan akan menggunakan nilai lalainya jika tidak diberikan:

| Medan            | Jenis              | Lalai    | Catatan                                                                                                                                    |
| ---------------- | ------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **dport**        | int (1–65535)      | `443`    | Port TCP destinasi untuk dipintas secara telus                                                                                             |
| **mark**         | int (≥1)           | `0x2333` | Tanda firewall yang ditetapkan pada `OUTPUT`, dipadankan oleh `ip rule` + `PREROUTING`                                                     |
| **onPort**       | int (1–65535)      | `8443`   | Port yang diikat oleh pendengar telus (**IP_TRANSPARENT**)                                                                                 |
| **routeTable**   | int (≥1)           | `233`    | ID jadual penghalaan dasar yang mengandungi laluan `local 0.0.0.0/0`                                                                       |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | Tanda soket pintasan (**SO_MARK**) yang ditetapkan oleh proksi pada sambungan huluannya sendiri; dikecualikan dalam `OUTPUT` (anti-gelung) |
| **sudoPassword** | string             | —        | Desktop bukan root sahaja: membenarkan pemasangan gedung amanah; diabaikan apabila root                                                    |

Tiada **pemboleh ubah persekitaran** untuk TPROXY — semua konfigurasi dilakukan melalui
kandungan POST atau nilai lalai di atas.

## §9 Mendayakan daripada Pemeriksa Trafik

1. Buka **Pemeriksa Trafik** (`/dashboard/tools/traffic-inspector`).
2. Dalam bar alat mod tangkapan, cari butang **"Nyahsulit TPROXY"** ⚠
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Jika ia **dinyahdayakan** dengan tip alat "Penyahsulitan TPROXY memerlukan Linux + root +
     tambahan natif", tambahan natif tidak tersedia pada hos ini (bukan Linux,
     tiada rantai alat, atau tambahan belum dibina). Lihat [§2](#2-requirements) dan [§3](#3-the-native-ip_transparent-addon).
3. Klik butang tersebut. Ia memanggil `POST /api/tools/agent-bridge/tproxy` melalui
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`), yang:
   membina CA dinamik, membuka pendengar telus, menggunakan peraturan tembok api,
   dan memasang CA dalam gedung amanah OS.
4. Semasa berjalan, togol bertukar kepada warna ambar dan menunjukkan kiraan pemintasan langsung
   (`· <interceptCount>`). Permintaan yang dipintas muncul dalam senarai permintaan dengan
   `source: "tproxy"`.
5. Klik sekali lagi untuk menghentikannya — `DELETE /api/tools/agent-bridge/tproxy` melalui
   `stopTproxyCaptureMode()` menutup pendengar, menyahpasang CA, dan mengembalikan
   peraturan tembok api.

Status mod tangkapan (berjalan / tersedia / kiraan pemintasan / port pendengar) diperoleh
daripada `GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` dalam
`src/mitm/tproxy/captureManager.ts`). Hanya **satu** sesi TPROXY berjalan pada satu-satu masa —
cubaan memulakan sesi kedua ditolak dengan "Mod tangkapan TPROXY sedang berjalan".

## §10 Penyelesaian masalah

### Togol dinyahdayakan

Tambahan natif tidak dapat dimuatkan. Sahkan: anda menggunakan Linux, anda telah membina tambahan
(`npm run build:native:tproxy`), dan proses boleh memuatkan `transparent.node`.
`isTransparentSocketAvailable()` mengawal togol; `GET /api/tools/agent-bridge/tproxy`
mengembalikan `available: false` apabila tambahan tiada.

### Tiada apa-apa yang ditangkap

- Sahkan proses yang dipintas benar-benar menyambung kepada `dport` yang dikonfigurasikan
  (lalai `443`).
- Sahkan proses mempercayai CA dinamik. CA dipasang sebagai
  `omniroute-tproxy-ca.crt`; aplikasi dengan gedung amanahnya sendiri (Firefox/Chrome NSS)
  mungkin perlu menambahkan sijil tersebut di sana juga.
- Jalankan ujian kendiri **Diagnose** AgentBridge (lihat
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) untuk pemeriksaan kepercayaan sijil / kesihatan
  pelayan.

### Peraturan tembok api lapuk selepas ranap

`revertTproxy()` ialah songsangan tepat bagi operasi penggunaan dan bersifat idempoten. Menghentikan
mod akan mengembalikan peraturan; jika OmniRoute dimatikan di pertengahan sesi, gunakan tindakan
**Repair** AgentBridge (`POST /api/tools/agent-bridge/repair`) untuk membatalkan keadaan sistem
terbiar (pemalsuan DNS, CA akar, proksi sistem). Peraturan `mangle` dan laluan TPROXY juga
dikosongkan secara automatik apabila sistem dibut semula.

### Gelung tidak terhingga / proksi memintas pemajuan sendiri

Ini ialah kes anti-gelung. Sahkan `bypassMark` berbeza daripada `mark` (pengesahan
menguatkuasakan perkara ini) dan pemajuan menggunakan `connectMarked` (sememangnya digunakan dalam `realForward`).
Lihat [§5 Anti-gelung](#anti-loop-so_mark).
