Gunakan panduan ini untuk memilih kitaran pembangunan boleh dipercayai yang paling kecil bagi sesuatu pull request. Panduan ini tidak
menggantikan dokumen seni bina dan keselamatan khusus bidang yang dipautkan di bawah; sebaliknya, ia menghubungkan setiap jenis
perubahan lazim kepada kontrak, semakan berfokus dan liputan CI masing-masing.

## Laluan yang diikuti oleh setiap perubahan

1. **Pilih asas sebelum mengedit.** Cari cabang `release/v*` aktif yang tertinggi dan cipta cabang daripada
   hujungnya. Sasarkan cabang tersebut, bukan `main`. Jika pembekuan keluaran sedang berkuat kuasa, jangan sasarkan
   cabang yang dibekukan; gunakan kitaran aktif seterusnya yang diterangkan dalam
   [Model Pencabangan & Keluaran](BRANCHING_MODEL.md).
2. **Nyatakan kontrak.** Kenal pasti setiap katalog, skema, artifak terjana, API awam atau antara muka
   pengguna yang terjejas oleh perubahan tersebut. Jadual di bawah memberikan set permulaan minimum.
3. **Tulis atau kemas kini ujian berfokus.** Perubahan produksi dalam `src/`, `open-sse/`, `electron/` atau
   `bin/` memerlukan ujian automatik dalam PR yang sama. Jalankan fail ujian terkecil yang membuktikan
   tingkah laku tersebut, kemudian gerbang berfokus yang disenaraikan.
4. **Biarkan CI menjalankan matriks menyeluruh.** Kesemua serpihan unit, Vitest, ratchet liputan dan
   binaan produksi dijalankan pada PR. Jalankan suite menyeluruh secara setempat hanya apabila kegagalan berfokus menunjukkan
   kesan yang lebih luas atau apabila perubahan merentasi beberapa subsistem.
5. **Selaraskan sebelum semakan.** Dapatkan asas aktif, teliti commit baharunya serta diff anda terhadap
   asas tersebut, kemudian rebase atau gabungkan asas mengikut aliran kerja penyumbang. Selesaikan konflik fail terjana
   dan katalog daripada sumbernya, jana semula fail tersebut, jalankan semula kitaran berfokus dan sahkan bahawa
   PR masih menyasarkan cabang keluaran aktif.
6. **Rekodkan bukti.** Dalam templat PR, senaraikan arahan yang dijalankan, setiap fail ujian yang ditambah atau diubah,
   migrasi atau feature flag, serta sebarang pengesahan khusus CI yang masih belum selesai.

## Laluan utama mengikut jenis perubahan

Arahan di bawah ialah semakan berfokus minimum, bukan kebenaran untuk melangkau ujian yang secara langsung meliputi
tingkah laku yang anda ubah.

### Penyedia

**Kontrak**

- Takrifan penyedia dalam `src/shared/constants/providers/` dan komposisinya dalam
  `src/shared/constants/providers.ts`.
- Model dan keupayaan dalam `open-sse/config/providerRegistry.ts` atau fail registry yang diekstrak daripadanya.
- Pemilihan pelaksana/penterjemah, konfigurasi OAuth atau kunci API, aset papan pemuka dan rujukan
  penyedia terjana apabila berkenaan.
- Bukti kelayakan awam mesti menggunakan `resolvePublicCred()`; respons ralat mesti menggunakan pembantu ralat
  tersanitasi yang dikongsi. Lihat `docs/security/PUBLIC_CREDS.md` (git; tidak dikompil ke dalam `/docs`) dan
  [Sanitasi Ralat](../security/ERROR_SANITIZATION.md).

**Kitaran berfokus**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # apabila katalog berubah; commit diff yang dijana
npm run lint
```

Uji juga setiap keluarga permintaan yang terjejas: sembang, Responses, imej, embeddings, audio atau video.
Semak katalog terjana dan diff golden sebagai perubahan kontrak; jangan terimanya secara membuta tuli.

### Penghalaan

**Kontrak**

- Nilai strategi awam dan metadata UI dalam `src/shared/constants/routingStrategies.ts`.
- Penghantaran dan pengisihan di bawah `open-sse/services/combo.ts` dan `open-sse/services/combo/`.
- Skema combo, pengekalan, keadaan daya tahan, keupayaan model dan kawalan API/UI.
- [Enjin Auto-Combo](../routing/AUTO-COMBO.md) dan dokumentasi daya tahan apabila tingkah laku berubah.

**Kitaran berfokus**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # perubahan strategi atau penghantaran
npm run check:known-symbols      # perubahan pendaftaran strategi
npm run lint
```

Gunakan ujian upstream olok-olok yang deterministik secara setempat. Ujian ringkas combo langsung memerlukan bukti kelayakan dan
dijalankan secara manual, bukan sebagai pengganti CI.

### UI / UX

**Kontrak**

- Laluan/halaman Next.js dan sempadan komponen dikongsi di bawah `src/app/` dan
  `src/shared/components/`.
- Bentuk respons API, keadaan pemuatan/kosong/ralat, tingkah laku papan kekunci dan pembaca skrin,
  reka letak responsif, tema dan peluasan locale.
- Rentetan sumber UI bahasa Inggeris dalam `src/i18n/messages/en.json`; jangan hard-code salinan baharu yang dipaparkan kepada pengguna.

**Kitaran berfokus**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Jalankan aplikasi bagi perubahan interaksi atau visual dan semak kedua-dua viewport sempit dan lebar. CI menjalankan
binaan produksi dan suite yang lebih luas; tingkah laku visual masih memerlukan komponen berfokus, Playwright
atau semakan manual terdokumen yang sesuai dengan perubahan tersebut.

### i18n

**Kontrak**

- `src/i18n/messages/en.json` ialah sumber UI; `config/i18n.json` ialah sumber locale.
- Katalog CLI disimpan secara berasingan di bawah `bin/cli/locales/`.
- Kekalkan ruang letak dan tag ICU dengan tepat. Jangan terjemahkan nama produk/penyedia/model,
  nama protokol dan pengepala, arahan, pengecam kod/JSON, URL, pemboleh ubah persekitaran atau
  istilah terlindung seperti `OmniRoute`, `OAuth`, `MCP` dan `A2A`. Senarai sumber semasa ialah
  `scripts/i18n/glossary/protected-terms.json`.

**Kitaran berfokus**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # apabila rentetan/katalog CLI berubah
npm run lint
```

Ini ialah panduan untuk sistem sedia ada, bukan undangan untuk memperluas perkakas atau model kekuncinya.
Pastikan patch i18n bersasar ketika sistem pengganti sedang direka. Jangan jalankan arahan terjemahan
yang memanggil perkhidmatan luaran melainkan tugasan tersebut secara jelas memerlukan terjemahan terjana dan
anda telah menyemak diff yang terhasil.

### CLI

**Kontrak**

- Perintah dan bendera awam dalam `bin/cli/`, perintah API yang dijana, kod keluar, stdout/stderr dan
  bentuk output JSON, tingkah laku konfigurasi/persekitaran, serta fail yang dipakejkan.
- Rentetan CLI yang dipaparkan kepada pengguna mesti menggunakan lapisan i18n CLI dan memastikan katalog `en`/`pt-BR` diselaraskan.
- Kekalkan Node sebagai persekitaran masa jalan yang disokong dan kontrak binari yang diterbitkan.

**Gelung berfokus**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # perubahan CLI yang dijana/dihimpunkan
npm run check:pack-policy     # perubahan pada permukaan pakej
npm run lint
```

Gunakan perintah yang tepat dalam direktori data sementara apabila tingkah laku bergantung pada penghuraian, fail atau status
keluar. CI menjalankan semakan artifak pakej dan ekosistem yang lebih luas.

### Pangkalan data

**Kontrak**

- Modul domain di bawah `src/lib/db/`; import modul tertentu secara langsung (lapisan eksport semula `localDb.ts` yang lama telah dialih keluar).
- Migrasi SQL bernombor dan idempoten di bawah `src/lib/db/migrations/`, keselamatan transaksi, tingkah laku
  naik taraf, indeks dan setiap pemanggil yang terjejas oleh skema.
- Laluan dan pengendali tidak sekali-kali mengeluarkan SQL mentah secara langsung.

**Gelung berfokus**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Uji kedua-dua pangkalan data baharu dan naik taraf daripada skema terdahulu apabila menambahkan migrasi. Ujian pangkalan data
mesti menutup pemegang dan memanggil `resetDbInstance()` semasa pembersihan. Jalankan `npm run test:bun:db` hanya apabila
laluan penyesuai Bun usaha terbaik berubah; Node kekal sebagai rujukan berwibawa.

### Binaan / penggunaan

**Kontrak**

- Manifes/lockfile akar dan ruang kerja, `scripts/build/`, pemasangan kendiri Next.js, kandungan pakej `dist/`,
  metadata platform Electron, aliran kerja CI dan penanda penggunaan.
- Julat Node yang disokong dan penggunaan Bun yang disenaraikan sebagai dibenarkan dalam `CLAUDE.md` mesti dikekalkan.
- Artifak binaan kekal tidak dijejaki; dasar kebergantungan, lesen, aliran kerja dan pakej terpakai.

**Gelung berfokus**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # perubahan kebergantungan atau lockfile
npm run check:pack-policy      # perubahan pada permukaan pakej yang diterbitkan
npm run lint
```

Gunakan `npm run build` secara setempat hanya apabila perubahan menjejaskan pengkompilan, pemasangan kendiri, aset
atau penghimpunan masa jalan. Gunakan `npm run build:release` hanya untuk pengesahan keluaran/penggunaan. Binaan CI ialah
isyarat rentas platform muktamad; perubahan Electron khusus platform memerlukan bukti binaan berfokus atau ujian ringkas
yang sepadan.

## Gelung calon setempat

Ujian sumber tidak dapat membuktikan bahawa artifak berpakej boleh dimulakan: senarai pembungkusan, kebergantungan yang dipangkas,
dan binari natif hanya gagal setelah tarball dipasang dan dimulakan. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) ialah bahagian setempat bagi aliran bina-sekali / sahkan / promosikan daripada
RFC #8084: ia membina satu calon, mengesahkan artifak tepat tersebut, mempromosikannya melalui penamaan semula
direktori, dan mengembalikannya kepada keadaan sebelumnya apabila slot yang dipromosikan gagal semakan kesihatannya.

```bash
npm run dev:candidate -- run --dry-run --json  # cetak pelan, jangan ubah apa-apa
npm run dev:candidate -- run                   # bina + sahkan + promosikan, pengembalian automatik
npm run dev:candidate -- build                 # npm pack + pasang ke dalam _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # mulakan pada port kosong, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → semasa, semasa → sebelumnya
npm run dev:candidate -- rollback              # tukar ganti semasa dan sebelumnya
npm run dev:candidate -- run --from-tarball <file.tgz>  # guna semula tarball yang dibina di tempat lain (CI)
```

- **Bina sekali.** `build` membungkus pepohon semasa (ia memerlukan `dist/server.js`, jadi jalankan
  `npm run build:release` terlebih dahulu) atau menyalin `--from-tarball`, kemudian memasang tarball ke dalam
  awalan npm yang diasingkan kerana tarball tidak mengandungi `node_modules`. ID ialah sha `HEAD` pendek
  (`-dirty` apabila pepohon mempunyai perubahan setempat) atau `tgz-<sha256>` untuk tarball. ID bersih yang
  telah dibina akan digunakan semula dan bukannya dibina semula; gunakan `--force` untuk membinanya semula.
- **Sahkan pakej, bukan sumber.** `validate` memulakan CLI yang dipasang
  (`serve --port <free port>`) dengan `DATA_DIR=<candidate>/data` yang baharu, rahsia palsu, serta
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` dan `INITIAL_PASSWORD` milik pengendali yang dialih keluar daripada
  persekitaran supaya ia menyemak konfigurasi gelung balik tanpa kunci bagi pemasangan baharu. Ia menunggu
  `GET /api/health` mengembalikan 200, menghendaki `GET /v1/models` mengembalikan 200, menghentikan kumpulan proses,
  dan merekodkan keputusan dalam `validation.json` bersama-sama dengan cincangan tarball.
- **Promosikan artifak yang sama.** `promote` menolak calon tanpa pengesahan yang lulus bagi
  cincangan tarball semasanya. Slot aktif lalai ialah `_artifacts/candidate/current`; `--target <dir>`
  memilih direktori lain pada sistem fail yang sama, dan slot sebelumnya ialah `<dir>.previous`.
  Setiap penamaan semula adalah atomik, dan kegagalan di pertengahan proses membalikkan penamaan semula yang telah dijalankan.
- **Kembali kepada keadaan sebelumnya.** `run` mengesahkan slot yang dipromosikan sekali lagi dan menukar ganti `current` dengan `previous`
  apabila semakan tersebut gagal. Calon yang gagal dalam pengesahan pertama tidak akan dipromosikan.

Segala-galanya ditulis di bawah `_artifacts/candidate/` yang diabaikan oleh git; pemasangan OmniRoute
sedia ada dan direktori datanya tidak pernah disentuh. CLI yang dipromosikan ialah
`_artifacts/candidate/current/prefix/bin/omniroute`; mulakannya dengan `DATA_DIR` anda sendiri apabila anda
menggunakannya. Kod keluar: `0` berjaya, `1` pengesahan atau promosi gagal, `2` ralat penggunaan atau binaan tiada.

## Gelung setempat berbanding CI

| Jalankan secara setempat untuk setiap tampalan                                                | CI menyediakan isyarat menyeluruh                                                   |
| --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Ujian tingkah laku langsung dan pagar kategori di atas                                        | Suite unit penuh berpecah dan ujian bersiri                                         |
| `npm run lint`                                                                                | Suite Vitest serta mekanisme ratchet liputan/kualiti                                |
| Semakan jenis atau binaan hanya apabila diperlukan oleh kontrak yang terjejas                 | Binaan produksi, keselamatan, dokumentasi, kebergantungan dan pagar dasar PR        |
| Interaksi manual/semakan langsung hanya apabila automasi tidak dapat membuktikan tingkah laku | Semakan integrasi antara tugas dan platform yang dikonfigurasikan oleh aliran kerja |

Gelung berfokus yang berjaya ialah bukti tentang kontrak yang diubah, bukan jaminan bahawa semakan CI
yang tidak berkaitan akan lulus. Sebaliknya, jangan biarkan setiap suntingan setempat menunggu keseluruhan matriks repositori.

## Senarai semak penyelarasan

Sebelum meminta semakan:

- Sahkan bahawa asas PR masih merupakan cabang `release/v*` aktif yang tertinggi.
- Ambil asas tersebut dan semak komit yang telah digabungkan sejak anda mencipta cabang.
- Semak `git diff <active-base>...HEAD` untuk perubahan tidak sengaja atau yang dijana.
- Selesaikan konflik katalog dan dokumen yang dijana dengan mengemas kini sumber dan menjana semula output.
- Jalankan semula setiap ujian/pagar berfokus yang disenaraikan dalam perihalan PR selepas penyelarasan.
- Jangan sekali-kali melonggarkan penegasan atau menggugurkan ujian yang diperlukan semata-mata untuk menyesuaikan diri dengan asas yang telah berubah.

Untuk peraturan pembekuan keluaran dan penyasaran semula, gunakan
[Model Percabangan & Keluaran](BRANCHING_MODEL.md). Untuk inventori CI yang lengkap, gunakan
[Rujukan Pagar Kualiti](../architecture/QUALITY_GATES.md).
