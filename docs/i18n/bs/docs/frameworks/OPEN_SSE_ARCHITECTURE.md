# open-sse Arhitektura

> **TL;DR (Ukratko)**: `open-sse/` je osnovni streaming mehanizam koji pokreće svaki LLM zahtjev u OmniRoute-u. Sadrži oko 1.400 datoteka koje implementiraju pipeline zahtjeva, izvršitelje (executors), servise, MCP server i sloj za prevođenje. Ovaj vodič objašnjava kako se dijelovi uklapaju.

**Izvor:** `open-sse/` (workspace paket, ~1.440 `.ts` datoteka koje nisu testovi)

---

## Zašto poseban workspace paket?

`open-sse/` je **samostalni workspace** u OmniRoute monorepo-u iz nekoliko razloga:

1. **Ponovna iskoristivost** — `open-sse` je objavljen kao `@omniroute/open-sse` na npm-u, tako da ga drugi projekti mogu koristiti nezavisno
2. **Čiste granice** — streaming mehanizam je odvojen od OmniRoute-specifičnog UI/DB sloja
3. **Performanse** — mehanizam nema Next.js zavisnosti, što omogućava brže hladno pokretanje (cold starts) u CLI/serverless kontekstima
4. **Verzionisanje** — `open-sse` može izdavati verzije prema vlastitom ritmu

```json
// package.json
"workspaces": ["open-sse"]
```

## Pipeline zahtjeva

Svaki LLM zahtjev prolazi kroz **pipeline od 5 faza**:

```
                              ┌──────────────┐
   HTTP zahtjev                │  1. RUTIRANJE │   razrješenje kombinacije, odabir modela
   (Next.js ruta)             └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. PREVOĐENJE│   konverzija formata (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. IZVRŠAVANJE│   izvršitelj provajdera, HTTP, ponovni pokušaj, prekidač
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAMING │   SSE transformacija, povratni pritisak (backpressure)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. ZAPISIVANJE│   praćenje upotrebe, log poziva, klasifikacija grešaka
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP odgovor (SSE ili JSON)
```

### Faza 1: Rutiranje (services/combo.ts)

**Ulazna tačka**: `handleComboChat()` u `services/combo.ts`

Razrješava zahtjev u konkretnu `(provider, model, account, credentials)` torku:

- Pronalazi kombinaciju po ID-u (ili gradi virtuelnu kombinaciju za `auto/*` modele)
- Primjenjuje strategiju rutiranja (prioritet, ponderisano, round-robin, itd.)
- Filtrira nezdrave provajdere (circuit breaker)
- Bira sljedeću održivu metu

Za `auto/*` modele, ova faza također:

- Pokreće algoritam **bodovanja sa 16 faktora** (`services/autoCombo/`)
- Bira `provider+model` par na osnovu zdravlja, troškova, latencije, itd.

### Faza 2: Prevođenje (translator/)

Ako se izvorni format (npr. OpenAI) razlikuje od ciljnog formata (npr. Claude), zahtjev se **prevodi**:

- Sistemski prompt → sistemska poruka
- Definicije alata → format alata specifičan za provajdera
- Parametri rezonovanja/razmišljanja → ekvivalenti specifični za provajdera
- Normalizacija uloge poruke (`developer` → `system` za ne-OpenAI)

`translator/index.ts` izlaže:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Faza 3: Izvršavanje (executors/)

**Ulazna tačka**: `getExecutor(providerId).execute(request, options)`

Svi provajderi koriste `DefaultExecutor` (`executors/default.ts`) putem `getExecutor()` fabričkog fallback-a. Izvršitelj:

- Gradi upstream URL (`buildUrl()`)
- Dodaje zaglavlja specifična za provajdera (`buildHeaders()`)
- Transformiše tijelo zahtjeva (`transformRequest()`)
- Šalje HTTP zahtjev uz ponovni pokušaj + eksponencijalno odlaganje (exponential backoff)
- Obrađuje osvježavanje autentifikacije ako je potrebno (OAuth provajderi)

Svi izvršitelji proširuju `BaseExecutor` (`executors/base.ts`, 1170 LOC) koji pruža:

- Uobičajenu logiku ponovnog pokušaja
- Integraciju proxy-ja
- Integraciju circuit breaker-a
- Hook-ove za zapisivanje upotrebe

### Faza 4: Streaming (utils/stream.ts)

Za streaming odgovore, izvršitelj vraća **ReadableStream**. Handler:

- Provlači kroz SSE transformaciju (`createSSETransformStreamWithLogger`)
- Primjenjuje heartbeat pingove za otkrivanje prekinutih veza
- Elegantno rukuje prekidom veze klijenta (`pipeWithDisconnect`)
- Transformiše SSE → JSON za klijente koji ne koriste striming

Za odgovore koji nisu striming, izvršilac vraća parsiran JSON objekat koji se prosljeđuje nepromijenjen.

### Faza 5: Zapisivanje (services/usage.ts)

Nakon odgovora (uspjeh ili neuspjeh), upotreba se zapisuje:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` iz odgovora
- `cost_usd` izračunat iz podataka o cijenama
- `latency_ms`, `status`, `error_class` ako nije uspjelo
- Trajno pohranjeno u tabelu `usage_history`

Artefakti dnevnika poziva (ako su omogućeni) se zapisuju u `${DATA_DIR}/call_logs/`.

## Detaljan pregled ključnih datoteka

### chatCore.ts (5977 linija)

**Glavni rukovalac zahtjevima**. Uprkos svojoj veličini, ima jasnu strukturu:

```ts
// Pseudo-struktura chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Provjera autentičnosti + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Validacija tijela zahtjeva
  const body = await parseRequestBody(request);

  // 3. Detekcija formata + prevođenje
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo rutiranje
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Nastavi na sljedeći cilj
    }
  }

  // 5. Hitna alternativa (fallback)
  return await emergencyFallback(body);
}
```

Uprkos tome što je jedna ogromna funkcija, organizovana je u **komentarisane sekcije** koje se mapiraju na cjevovod (pipeline) od 5 faza.

### combo.ts (4456 linija koda)

**Mehanizam za rutiranje** koji razrješava combo na uređene ciljeve.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

Podržava **19 strategija rutiranja** (pogledajte `src/shared/constants/routingStrategies.ts`):

| Strategija          | Ponašanje                                                                 |

| `weighted`          | Vjerovatnosno prema težini po cilju                                       |
| `round-robin`       | Kruženje kroz ciljeve po redu                                             |
| `context-relay`     | Prenos konteksta između ciljeva                                           |
| `fill-first`        | Popunjavanje kvote prije prelaska na sljedeći                             |
| `p2c`               | Snaga dva izbora (Power of two choices)                                   |
| `random`            | Uniformno nasumično                                                       |
| `least-used`        | Odabir onog sa najmanje nedavnih upotreba                                 |
| `cost-optimized`    | Najjeftiniji ispravan cilj prvi                                           |
| `reset-aware`       | Svjestan prozora za resetovanje provajdera                                |

## Izvršioci (75+ datoteka)

Jedna datoteka po provajderu. Svi oni proširuju `BaseExecutor` i nadjačavaju ono što se razlikuje.

### Uobičajeni obrasci

Provajderi se razrješavaju putem `getExecutor(providerId)`, koji vraća konfigurisanog izvršioca. Provajderi kompatibilni sa OpenAI/Anthropic koriste `DefaultExecutor` (`executors/default.ts`). Ponašanje specifično za provajdera (osnovni URL, autorizacijska zaglavlja, verzija API-ja) konfiguriše se u `open-sse/config/providers/`, dok se transformacije tijela zahtjeva obrađuju u `open-sse/translator/`.

**Prilagođeni URL** se postavlja putem konfiguracije provajdera:

```ts
// Konfiguracija provajdera u open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
};
```

**Prilagođena autorizacija** se obrađuje kroz konfiguraciju autorizacije registra provajdera (API ključ, OAuth, profili zaglavlja).

**Prilagođene transformacije tijela zahtjeva** (npr. Anthropic koji odvaja `system` od `messages`) registruju se po provajderu u `open-sse/translator/`.

### Fabrika izvršilaca

`executors/index.ts` izvozi `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
```

Razrješavanje ide kroz `ExecutorRegistry` (`executors/registry.ts`): svaki specijalizovani izvršilac je deklarisan u ugrađenoj tabeli u `executors/index.ts` i registrovan putem `registerExecutor(alias, instance)` pri učitavanju modula; `getExecutor()` konsultuje registar i vraća se na memoizovani `DefaultExecutor` za bilo kog provajdera bez specijalizovanog unosa. Puno mapiranje alias → izvršilac je karakterisano zlatnim testom `tests/unit/executor-map-golden.test.ts`.

## Prevoditelji

Prevod između **3 formata**: OpenAI, Anthropic, Gemini, plus novi Responses API.

### Kada se dešava prevod

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Uobičajeni prevodi:

- `OpenAI → Anthropic`: odvojeno `system` polje, `x-api-key` zaglavlje
- `OpenAI → Gemini`: `contents` umjesto `messages`, `systemInstruction`
- `OpenAI → Responses API`: `input` niz, `previous_response_id` stanje

### Obrađeni granični slučajevi

- `developer` uloga → `system` za ne-OpenAI
- `system` uloga → spojeno u prvu korisničku poruku za GLM/ERNIE
- `json_schema` → Gemini-jev `responseMimeType` + `responseSchema`
- `tools` → format alata specifičan za provajdera
- Parametri razmišljanja (o1, Claude) → ekvivalenti specifični za provajdera

## MCP Server

`open-sse/mcp-server/` implementira **Model Context Protocol** server:

- **110 alata** (upravljanje provajderima, kombinacije, memorija, keš, kompresija, proksi, vještine, gamifikacija, dodaci, Notion, Obsidian, lokalni korpus)
- **3 transporta**: stdio, SSE, Streamable HTTP
- **33 opsega** za detaljnu autorizaciju

### Registracija alata

Alati se registruju kao samostalni fajlovi u `open-sse/mcp-server/tools/`, od kojih svaki izvozi ime, šemu, handler i opseg:

```ts
// open-sse/mcp-server/tools/getHealth.ts
```

## Transformatori

`open-sse/transformer/` vrši konverziju između **Chat Completions** i **Responses API** formata.

### Zašto poseban Transformer?

Responses API je OpenAI-jev novi format sa **konverzacijama sa stanjem** (`previous_response_id`). Kada klijent pošalje Responses zahtjev, OmniRoute:

1. Interno konvertuje Responses → Chat Completions
2. Šalje provajderu (bilo kojem provajderu koji podržava Chat Completions)
3. Konvertuje odgovor nazad u Responses format
4. Strimuje konvertovani odgovor klijentu

Transformer (`transformer/responsesTransformer.ts`) obezbjeđuje:

```ts
createResponsesApiTransformStream(): TransformStream
```

Ovo obrađuje:

- `response.output_item.added` događaje
- `response.output_text.delta` događaje
- `response.completed` događaj
- Mapiranje poziva alata (`function_call` ↔ `tool_calls`)

## Ograničenja performansi

Routing engine ima stroge budžete performansi:

| Operacija                                       | Cilj  | Mjerenje                     |
| ----------------------------------------------- | ----- | ---------------------------- |
| Combo rezolucija                                | <10ms | Za 50 ciljeva                |
| Provjera ograničenja stope (rate limit)         | <1ms  | Token bucket u memoriji      |
| Fallback porodice modela                        | <5ms  | Keširane definicije porodica |
| Slanje (dispatch) rutiranja zahtjeva            | <2ms  | Hot path                     |
| **Bez blokirajućeg I/O u hot path-u rutiranja** | —     | Sve asinhrono                |

## Anti-obrasci

❌ **Sinhroni DB pozivi u `combo.ts`** — prethodno izračunajte i keširajte
❌ **Logika ponovnog pokušaja (retry) u handlerima** — koristite `retry()` iz resilience servisa
❌ **Direktan pristup konfiguraciji provajdera** — koristite gettere `providerRegistry`
❌ **Hardkodirani lanci fallback-a** — definirajte u `modelFamilyFallback.ts`
❌ **Mutacije stanja kroz konkurentne zahtjeve** — koristite samo kontekst ograničen na zahtjev (request-scoped)

## Dodavanje nove komponente

### Dodavanje novog servisa

1. Kreirajte `open-sse/services/[serviceName].ts` sa fokusiranom odgovornošću
2. Izvezite glavnu handler funkciju i sve konstante
3. Dodajte jedinične testove u `tests/unit/services/[serviceName].test.mjs`
4. Integrirajte u pipeline zahtjeva u `handlers/chatCore.ts` (ako je povezano sa rutiranjem)
5. Ažurirajte logiku rutiranja u `combo.ts` ako servis utiče na odabir cilja
6. Dokumentirajte u ovoj datoteci

### Dodavanje novog izvršitelja (Executor)

1. Kreirajte `open-sse/executors/[provider].ts` proširujući `BaseExecutor`
2. Registrirajte u `config/providerRegistry.ts`
3. Dodajte u `executors/index.ts` factory
4. Dodajte jedinične testove za izvršitelja
5. Dokumentirajte u `docs/architecture/ARCHITECTURE.md`

### Dodavanje novog MCP alata

1. Kreirajte ili ažurirajte `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definirajte Zod shemu za ulaze
3. Registrirajte alat u `mcp-server/index.ts`
4. Dodajte u matricu opsega (scope matrix) u `mcp-server/auth/`
5. Dodajte jedinične testove
