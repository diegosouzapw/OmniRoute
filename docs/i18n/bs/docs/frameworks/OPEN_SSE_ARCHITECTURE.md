> **Ukratko**: `open-sse/` je osnovni mehanizam za streaming koji pokreće svaki LLM zahtjev u OmniRouteu. Sadrži oko 1.400 datoteka koje implementiraju tok obrade zahtjeva, izvršioce, servise, MCP server i sloj za prevođenje. Ovaj vodič objašnjava kako su svi dijelovi povezani.

**Izvor:** `open-sse/` (workspace paket, oko 1.440 `.ts` datoteka koje nisu testovi)

---

## Zašto zaseban workspace paket?

`open-sse/` je **samostalan workspace** u OmniRoute monorepozitoriju iz nekoliko razloga:

1. **Ponovna upotrebljivost** — `open-sse` se objavljuje kao `@omniroute/open-sse` na npm-u, tako da ga drugi projekti mogu koristiti nezavisno
2. **Jasne granice** — mehanizam za streaming odvojen je od UI/DB sloja specifičnog za OmniRoute
3. **Performanse** — mehanizam nema Next.js zavisnosti, što omogućava brže hladno pokretanje u CLI/serverless okruženjima
4. **Verzioniranje** — `open-sse` može objavljivati izdanja vlastitim tempom

```json
// package.json
"workspaces": ["open-sse"]
```

## Tok obrade zahtjeva

Svaki LLM zahtjev prolazi kroz **tok obrade od 5 faza**:

```
                              ┌──────────────┐
   HTTP zahtjev                │  1. USMJERI  │   razrješavanje kombinacije, odabir modela
   (Next.js ruta)              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. PREVEDI  │   konverzija formata (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. IZVRŠI   │   izvršilac pružaoca, HTTP, ponovni pokušaj, prekidač
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAM   │   SSE transformacija, povratni pritisak
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. ZABILJEŽI│   praćenje upotrebe, dnevnik poziva, klasifikacija grešaka
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP odgovor (SSE ili JSON)
```

### Faza 1: Usmjeravanje (services/combo.ts)

**Ulazna tačka**: `handleComboChat()` u `services/combo.ts`

Razrješava zahtjev u konkretan skup `(provider, model, account, credentials)`:

- Pronalazi kombinaciju prema ID-u (ili gradi virtuelnu kombinaciju za `auto/*` modele)
- Primjenjuje strategiju usmjeravanja (prioritet, ponderisano, kružno itd.)
- Filtrira pružaoce koji nisu ispravni (prekidač strujnog kola)
- Odabire sljedeće dostupno odredište

Za `auto/*` modele ova faza također:

- Pokreće algoritam **bodovanja prema 16 faktora** (`services/autoCombo/`)
- Odabire par `provider+model` na osnovu stanja, cijene, latencije itd.

### Faza 2: Prevođenje (translator/)

Ako se izvorni format (npr. OpenAI) razlikuje od ciljnog formata (npr. Claude), zahtjev se **prevodi**:

- Sistemski prompt → sistemska poruka
- Definicije alata → format alata specifičan za pružaoca
- Parametri zaključivanja/razmišljanja → ekvivalenti specifični za pružaoca
- Normalizacija uloga poruka (`developer` → `system` za sisteme koji nisu OpenAI)

`translator/index.ts` izlaže:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Faza 3: Izvršavanje (executors/)

**Ulazna tačka**: `getExecutor(providerId).execute(request, options)`

Svi pružaoci koriste `DefaultExecutor` (`executors/default.ts`) putem rezervne opcije `getExecutor()` factory obrasca. Izvršilac:

- Gradi upstream URL (`buildUrl()`)
- Dodaje zaglavlja specifična za pružaoca (`buildHeaders()`)
- Transformiše tijelo zahtjeva (`transformRequest()`)
- Šalje HTTP zahtjev uz ponovne pokušaje i eksponencijalno povećavanje intervala čekanja
- Po potrebi upravlja osvježavanjem autentifikacije (OAuth pružaoci)

Svi izvršioci proširuju `BaseExecutor` (`executors/base.ts`, 1170 LOC), koji pruža:

- Zajedničku logiku ponovnih pokušaja
- Integraciju proxyja
- Integraciju prekidača strujnog kola
- Hookove za bilježenje upotrebe

### Faza 4: Streaming (utils/stream.ts)

Za streaming odgovore izvršilac vraća **ReadableStream**. Obrađivač:

- Prosljeđuje podatke kroz SSE transformaciju (`createSSETransformStreamWithLogger`)
- Primjenjuje heartbeat pingove radi otkrivanja prekinutih veza
- Elegantno obrađuje prekid veze klijenta (`pipeWithDisconnect`)
- Transformiše SSE → JSON za klijente koji ne koriste streaming

Za odgovore bez streaminga izvršilac vraća parsirani JSON objekt koji se prosljeđuje bez izmjena.

### Faza 5: Bilježenje (services/usage.ts)

Nakon odgovora (uspješnog ili neuspješnog), bilježe se podaci o korištenju:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` iz odgovora
- `cost_usd` izračunat na osnovu podataka o cijenama
- `latency_ms`, `status`, `error_class` u slučaju neuspjeha
- Pohranjeno u tabelu `usage_history`

Artefakti evidencije poziva (ako su omogućeni) zapisuju se u `${DATA_DIR}/call_logs/`.

## Detaljna analiza ključnih datoteka

### chatCore.ts (5977 linija)

**Glavni rukovalac zahtjevima**. Uprkos svojoj veličini, ima jasnu strukturu:

```ts
// Pseudo-struktura datoteke chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Autentifikacija + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Validacija tijela zahtjeva
  const body = await parseRequestBody(request);

  // 3. Detekcija formata + prevođenje
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Combo usmjeravanje
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Nastavi na sljedeći cilj
    }
  }

  // 5. Hitna rezervna opcija (fallback)
  return await emergencyFallback(body);
}
```

Iako je jedna ogromna funkcija, organizirana je u **komentarisane sekcije** koje odgovaraju cjevovodu od 5 faza.

### combo.ts (4456 LOC)

**Motor za usmjeravanje** koji razrješava combo u uređene ciljeve.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

## Executori (150 modula)

Uglavnom jedan fajl po provideru. Sve executor klase proširuju `BaseExecutor` i nadjačavaju ono što se razlikuje; ostali moduli su pomoćni moduli po provideru (tool sheme, fetch/TTS adapteri, rukovaoci specifičnostima).

### Uobičajeni obrasci

Provideri se razrješavaju putem `getExecutor(providerId)`, koji vraća konfigurisani executor. OpenAI/Anthropic-kompatibilni provideri koriste `DefaultExecutor` (`executors/default.ts`). Ponašanje specifično za providera (base URL, auth zaglavlja, API verzija) konfiguriše se u `open-sse/config/providers/`, dok se transformacije tijela zahtjeva obrađuju u `open-sse/translator/`.

**Prilagođeni URL** postavlja se kroz konfiguraciju providera:

```ts
// Konfiguracija providera u open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Prilagođena autentikacija** obrađuje se kroz auth konfiguraciju registra providera (API ključ, OAuth, profili zaglavlja).

Transformacije **prilagođenog tijela zahtjeva** (npr. Anthropic koji odvaja `system` od `messages`) registruju se po provideru u `open-sse/translator/`.

````

### Executor fabrika

`executors/index.ts` izvozi `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Razrješavanje ide kroz `ExecutorRegistry` (`executors/registry.ts`): svaki specijalizirani executor deklarisan je u ugrađenoj tabeli `executors/index.ts` i registrovan putem `registerExecutor(alias, instance)` pri učitavanju modula; `getExecutor()` konsultuje registar i vraća se na memoizirani `DefaultExecutor` za svakog providera bez specijaliziranog unosa. Potpuno mapiranje alias → executor karakterizirano je golden testom `tests/unit/executor-map-golden.test.ts`.

## Prevodioci

Prevodite između **3 formata**: OpenAI, Anthropic, Gemini, kao i novi Responses API.

### Kada se vrši prevođenje

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Uobičajena prevođenja:

- `OpenAI → Anthropic`: zasebno polje `system`, zaglavlje `x-api-key`
- `OpenAI → Gemini`: `contents` umjesto `messages`, `systemInstruction`
- `OpenAI → Responses API`: niz `input`, stanje `previous_response_id`

### Obrađeni rubni slučajevi

- uloga `developer` → `system` za sisteme koji nisu OpenAI
- uloga `system` → spojena s prvom korisničkom porukom za GLM/ERNIE
- `json_schema` → Geminijevi `responseMimeType` + `responseSchema`
- `tools` → format alata specifičan za pružaoca
- Parametri razmišljanja (o1, Claude) → ekvivalenti specifični za pružaoca

## MCP server

`open-sse/mcp-server/` implementira server za **Model Context Protocol**:

- **110 alata** (upravljanje pružaocima, kombinacije, memorija, predmemorija, kompresija, proxy, vještine, gamifikacija, dodaci, Notion, Obsidian, lokalni korpus)
- **3 transporta**: stdio, SSE, Streamable HTTP
- **33 opsega** za detaljnu autorizaciju

### Registracija alata

Alati su registrovani kao samostalne datoteke u `open-sse/mcp-server/tools/`, pri čemu svaka izvozi naziv, shemu, rukovalac i opseg:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transporti

```ts
// stdio (upotreba putem CLI-ja)
startMcpStdio(server);

// SSE (streaming zasnovan na HTTP-u)
startMcpSse(server, port);

// Streamable HTTP (moderni MCP)
startMcpStreamable(server, port);
```

### Autorizacija

Svaki poziv alata prolazi kroz provjere opsega (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Transformatori

`open-sse/transformer/` vrši konverziju između formata **Chat Completions** i **Responses API**.

### Zašto zaseban transformator?

Responses API je novi OpenAI format sa **razgovorima sa stanjem** (`previous_response_id`). Kada klijent pošalje Responses zahtjev, OmniRoute:

1. Interno konvertuje Responses → Chat Completions
2. Šalje pružaocu (bilo kojem pružaocu koji podržava Chat Completions)
3. Konvertuje odgovor nazad u Responses format
4. Strimuje konvertovani odgovor klijentu

Transformator (`transformer/responsesTransformer.ts`) pruža:

```ts
createResponsesApiTransformStream(): TransformStream
```

On obrađuje:

- događaje `response.output_item.added`
- događaje `response.output_text.delta`
- događaj `response.completed`
- Mapiranje poziva alata (`function_call` ↔ `tool_calls`)

## Konfiguracija

`open-sse/config/` sadrži sloj konfiguracije:

| Fajl                          | Svrha                                                |
| ----------------------------- | ---------------------------------------------------- |
| `providerRegistry.ts`         | Registar chat-modela nad katalogom od 375 provajdera |
| `providerModels.ts`           | Alijasi modela, mapiranje formata                    |
| `constants.ts`                | Vremenska ograničenja, limiti, statusni kodovi       |
| `defaultThinkingSignature.ts` | Zadani Claude thinking potpis                        |
| `modelStrip.ts` (u servisima) | Uklanjanje polja po provajderu                       |

### Šema registra provajdera

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Zod validacija pri učitavanju modula osigurava da su sve konfiguracije provajdera ispravne.

## Ograničenja performansi

Mehanizam za usmjeravanje ima strogo definirane ciljeve performansi:

| Operacija                                                   | Cilj  | Mjerenje                     |
| ----------------------------------------------------------- | ----- | ---------------------------- |
| Razrješavanje kombinacije                                   | <10ms | Za 50 odredišta              |
| Provjera ograničenja stope                                  | <1ms  | Memorijska kanta tokena      |
| Rezervni odabir porodice modela                             | <5ms  | Keširane definicije porodica |
| Prosljeđivanje zahtjeva                                     | <2ms  | Kritična putanja             |
| **Bez blokirajućeg I/O-a u kritičnoj putanji usmjeravanja** | —     | Sve je asinhrono             |

## Antipatterni

❌ **Sinhroni pozivi baze podataka u `combo.ts`** — unaprijed izračunajte i keširajte
❌ **Logika ponovnog pokušaja u rukovaocima** — koristite `retry()` iz servisa za otpornost
❌ **Direktan pristup konfiguraciji pružaoca** — koristite gettere iz `providerRegistry`
❌ **Tvrdo kodirani lanci rezervnih opcija** — definirajte ih u `modelFamilyFallback.ts`
❌ **Izmjene stanja među konkurentnim zahtjevima** — koristite samo kontekst ograničen na zahtjev

## Dodavanje nove komponente

### Dodavanje novog servisa

1. Kreirajte `open-sse/services/[serviceName].ts` s jasno definiranom odgovornošću
2. Izvezite glavnu funkciju rukovaoca i sve konstante
3. Dodajte jedinične testove u `tests/unit/services/[serviceName].test.mjs`
4. Integrirajte u proces obrade zahtjeva u `handlers/chatCore.ts` (ako je povezano s usmjeravanjem)
5. Ažurirajte logiku usmjeravanja u `combo.ts` ako servis utječe na odabir odredišta
6. Dokumentirajte u ovoj datoteci

### Dodavanje novog izvršioca

1. Kreirajte `open-sse/executors/[provider].ts` koji proširuje `BaseExecutor`
2. Registrirajte u `config/providerRegistry.ts`
3. Dodajte u tvornicu u `executors/index.ts`
4. Dodajte jedinične testove za izvršioca
5. Dokumentirajte u `docs/architecture/ARCHITECTURE.md`

### Dodavanje novog MCP alata

1. Kreirajte ili ažurirajte `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definirajte Zod shemu za ulazne podatke
3. Registrirajte alat u `mcp-server/index.ts`
4. Dodajte u matricu opsega u `mcp-server/auth/`
5. Dodajte jedinične testove
