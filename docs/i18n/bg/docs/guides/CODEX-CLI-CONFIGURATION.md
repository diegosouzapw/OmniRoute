Пълно ръководство за използване на Codex CLI, насочен към OmniRoute като съвместим с OpenAI бекенд.

---

> **TOML е единственият действащ формат.** Съвременният Codex чете само
> `~/.codex/config.toml` (потвърдено с codex-cli 0.147.0: `codex --help`
> описва заместванията чрез `-c/--config` като „заредени от
> `~/.codex/config.toml`“). Старият `~/.codex/config.yaml` е принадлежал
> към остарелия npm CLI и се игнорира без предупреждение. Генераторът от
> таблото за управление (`/api/cli-tools/apply`, инструмент `codex`) записва TOML
> с консервативно сливане — съществуващите ключове и блоковете на други доставчици
> се запазват, API ключът остава в `OMNIROUTE_API_KEY` (никога във файла), а
> останалият стар `config.yaml` се отчита като бележка за миграция, без да бъде
> променян.

## Готов за поставяне config.toml

Заменете `<YOUR_HOST>` и `<YOUR_KEY>` с вашите стойности:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # ограничение за съхраняване в историята за всяко извикване на инструмент

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc или ~/.zshrc — действителната стойност на ключа, никога в config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex, включен в приложението ChatGPT

Ако сте инсталирали Codex чрез настолното приложение ChatGPT, двоичният файл
`codex` може да съществува само в пакета на приложението и все още да не е във
вашия `PATH` на обвивката. Добавете директорията с ресурсите към стартовия файл
на обвивката:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Отворете нова обвивка, след което проверете:

```bash
command -v codex
codex --version
```

### Локален OmniRoute без удостоверяване: достатъчен е заместващ ключ

Codex проверява дали променливата на средата, посочена чрез `env_key`, съществува
**преди** първата заявка да напусне CLI. Ако вашият **локален** екземпляр на
OmniRoute не изисква удостоверяване, достатъчна е всяка непразна заместваща
стойност:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Вместо това използвайте истински ключ, когато вашият OmniRoute сървър е защитен
или отдалечен.

> **Често използвани опции за хост**
>
> | Достъп         | URL                           |
> | -------------- | ----------------------------- |
> | Локална мрежа  | `http://192.168.0.1:20128/v1` |
> | Tailscale      | `http://100.x.x.x:20128/v1`   |
> | Обратна връзка | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — защо работи за всички модели

Codex CLI оттегли `wire_api = "chat"` (Chat Completions) през февруари 2026 г. и вече **изисква** `wire_api = "responses"` (OpenAI Responses API). Задаването на `wire_api = "chat"` води до незабавен срив при стартиране, считано от v0.138.

Много доставчици, включително GLM и Kimi, все още предлагат само крайна точка за Chat Completions. DeepSeek V4 вече предлага собствен Responses API, както и съвместима с Anthropic крайна точка; OmniRoute използва Responses по подразбиране и позволява на всяка връзка с DeepSeek да избере съвместимост с Anthropic.

**OmniRoute решава това прозрачно:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute избира собствения протокол на доставчика и при необходимост извършва преобразуване
    → POST /responses (DeepSeek V4) или /chat/completions (Mistral / GLM / Kimi / други)
```

Когато използвате OmniRoute, никога не ви е необходимо отделно прокси за преобразуване. **Всички модели използват `wire_api = "responses"`** — OmniRoute се грижи за останалото.

> **`wire_api` е стойността по подразбиране** — полето по подразбиране е `"responses"` и може да бъде изцяло пропуснато от `config.toml`. Задавайте го изрично само ако документирате намерението си.

## Контекстен прозорец и компактиране

### Полета за конфигуриране на токените

| Поле                             | Описание                                                                                                                                                                                                                                                        |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Общ бюджет от токени за активния модел. Задайте го на обявеното ограничение на модела.                                                                                                                                                                          |
| `model_auto_compact_token_limit` | Праг, който задейства автоматично компактиране на историята. **Максимум: 90% от `model_context_window`** — стойностите над 90% се игнорират без предупреждение.                                                                                                 |
| `tool_output_token_limit`        | Ограничение за броя токени, съхранявани в историята за резултата от всяко извикване на инструмент. Предотвратява запълването на прозореца от един голям отговор на инструмент. **Това не е максималният изход** — това е ограничение за съхранение в историята. |
| `compact_prompt`                 | Вградена замяна на системната подкана, използвана при компактиране (v0.138+).                                                                                                                                                                                   |

> **Бележка относно `model_max_output_tokens`**: Това поле **не е част от конфигурационната схема на Codex CLI** (липсва в кодовата база на Codex на Rust). Ако бъде зададено, то се игнорира без предупреждение. Не разчитайте на него — използвайте `tool_output_token_limit`, за да контролирате каква част от резултата на инструментите се съхранява в историята.

## Усилие за разсъждение

Контролира колко „мисли“ моделът, преди да отговори.

| Стойност | Използвайте за                                                     |
| -------- | ------------------------------------------------------------------ |
| `none`   | Без разсъждение — директен отговор                                 |
| `low`    | Тривиални задачи (преименуване, форматиране)                       |
| `medium` | **Настройка по подразбиране на сървъра**, ако липсва               |
| `high`   | Задачи със средна сложност (рефакториране, отстраняване на грешки) |
| `xhigh`  | Архитектура, задълбочен анализ, сложни проблеми                    |

```bash
# Задаване за отделно извикване
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

Задайте също **обобщение** на разсъждението, така че Desktop да може да визуализира текста на мисловния процес (а не само криптирани блокове):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # или ultra, когато се поддържа
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### Бюджет за разсъждение в OmniRoute (сървърна настройка)

На хоста на OmniRoute **Settings → AI → Thinking Budget** трябва да бъде зададено на **`passthrough`**, за да могат усилието/обобщението на Codex да достигнат до доставчика нагоре по веригата. Режимът **`auto` премахва** всички клиентски полета `reasoning` / `reasoning_effort` и ще остави панелите за разсъждение празни дори когато Codex е конфигуриран правилно.

Пълно ръководство: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Компресирането и кешът на подканите са независими и продължават да работят при `passthrough`.

## Профили — именувани конфигурации за всеки модел/работен процес

Профилите ви позволяват да превключвате модела + контекстния прозорец с един флаг. Всеки профил представлява плосък
файл `~/.codex/<name>.config.toml`, който се наслагва върху базовия `config.toml`.

> **Правило за именуване (Codex CLI v0.137+):** файлът трябва да бъде `~/.codex/<name>.config.toml` — **без префикс `profile-`**.
> CLI преобразува `-p kimi-k27` към `~/.codex/kimi-k27.config.toml`. Ако файлът не бъде намерен, настройката по подразбиране се прилага без предупреждение.

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # бързо, евтино
```

### Профили за усилие (един и същ модел, различно усилие)

```bash
codex -p low      # cx/gpt-5.5, effort=low
codex -p medium   # cx/gpt-5.5, effort=medium
codex -p high     # cx/gpt-5.5, effort=high
codex -p xhigh    # cx/gpt-5.5, effort=xhigh (по подразбиране)
codex -p chat     # cx/gpt-5.5, без зададено effort (сървърната настройка по подразбиране)
```

## Автоматично генериране на профили с `omniroute setup-codex`

Ако изпълнявате OmniRoute на VPS, можете автоматично да генерирате профилни файлове от актуалния каталог с модели:

```bash
# От VPS (използва локалния OmniRoute на порт 20128)
omniroute setup-codex

# От произволна машина — насочете към вашия VPS
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Преглед без записване на файлове
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Генериране само на GLM и Kimi профили
omniroute setup-codex --only glm,kimi

# Записване в персонализирана директория
omniroute setup-codex --codex-home /path/to/.codex
```

Командата извлича `/v1/models`, използва оптимизирани профили за познатите модели, прибягва до метаданните от каталога за други съвместими текстови модели и записва `~/.codex/<name>.config.toml` за всеки от тях. Идемпотентна е — може безопасно да се изпълнява повторно.

OmniRoute може също така **автоматично да синхронизира** същите профилни файлове, след като успешно откриване/импортиране на модели от доставчик промени актуалния каталог. Това е **по избор и е изключено по подразбиране**: включете го от таблото **CLI Code** („CLI profile auto-sync“ → Codex) или задайте `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (съобразява се и с `CLI_ALLOW_CONFIG_WRITES`, което е включено по подразбиране). Когато е активирано, се записват само отделни профилни файлове `~/.codex/*.config.toml`; никога не се променят активният/подразбиращият се `~/.codex/config.toml`, настройките на Codex-lb, удостоверяването или изборът на доставчик.

## Продължителни задачи

Две настройки по подразбиране на OmniRoute могат незабелязано да провалят продължаващи с часове сесии на Codex CLI. Нито една от тях не е настройка на Codex CLI — и двете са от страната на OmniRoute. Потребителите, които мигрират конфигурация от проксита нагоре по веригата, които фиксират акаунти и деактивират прекъсванията при неактивност, често се сблъскват и с двата проблема и заключават, че OmniRoute „не може да поддържа продължителна сесия“.

| Симптом                                                                                            | Вероятна причина                                                                                                 | Настройка                |
| -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------ |
| Сесията продължава да сменя акаунти / непрекъснатостта на кеша на подканите се губи между ходовете | TTL на афинитета на сесията е `0` (деактивиран)                                                                  | `sessionAffinityTtlMs`   |
| Връзката прекъсва по време на разсъждение без видима за клиента подкана                            | Наблюдателят за неактивност на потока се е задействал след 10 минути без фрагмент от услугата нагоре по веригата | `STREAM_IDLE_TIMEOUT_MS` |

Свързани дискусии: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (прекъсвания на продължителни задачи), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (защо афинитетът е деактивиран по подразбиране). Проследяване: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Афинитет на сесията — фиксиране на един разговор към един акаунт

**По подразбиране:** `sessionAffinityTtlMs = 0` (деактивиран).

**Къде да го зададете**

- Табло → **Настройки → Маршрутизиране** → **Афинитет на сесията** → **TTL на афинитета (секунди)** (`ComboDefaultsTab`)
- Или актуализирайте настройките чрез PATCH със `sessionAffinityTtlMs` в **милисекунди** (диапазон на Zod `0`–`86_400_000`, т.е. до 24 часа)

> Преименувано в #7274 от предназначеното само за Codex `codexSessionAffinityTtlMs`. Наследеният ключ все още се приема като псевдоним само за четене; новите конфигурации трябва да използват `sessionAffinityTtlMs`. Афинитетът вече се прилага към **всеки** доставчик, след като TTL е над `0`, а не само към Codex — вижте [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Афинитет на сесията.

**Какво се нарушава, когато остане 0**

Всеки ход в разговор с множество ходове на Codex се маршрутизира независимо от активната комбинирана стратегия и може да попадне в **различен акаунт при всеки ход**. Това нарушава непрекъснатостта на сесията / кеша на подканите нагоре по веригата. OmniRoute проверява заглавките на сесията на Codex (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) и полетата на тялото, като `prompt_cache_key` / `session_id`, само когато TTL е по-голям от `0` (`extractSessionAffinityKey` в `src/sse/services/auth.ts`).

**Препоръчително за единична задача, продължаваща няколко часа**

Задайте TTL **над очакваната продължителност на задачата по часовник** (максимумът в потребителския интерфейс е **86400 секунди** = 24 часа):

| Очаквана продължителност на задачата | TTL на афинитета (интерфейс, секунди) | `sessionAffinityTtlMs` |
| ------------------------------------ | ------------------------------------- | ---------------------- |
| Няколко часа                         | `14400` (4 ч.)                        | `14400000`             |
| През нощта / ~12 ч.                  | `43200` (12 ч.)                       | `43200000`             |
| Цял ден                              | `86400` (24 ч., максимум)             | `86400000`             |

Изричното активиране е умишлено: деактивирането на афинитета благоприятства балансирането на натоварването между акаунтите; активирането му благоприятства непрекъснатостта на една продължителна сесия на агент. Това ръководство **не** променя настройката по подразбиране — операторите, изпълняващи продължителни задачи на Codex, трябва изрично да я активират.

### 2. Време на изчакване при неактивност на потока — не прекъсвайте тихите ходове на разсъждение

**По подразбиране:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 минути). Когато не е зададено, наследява стойността от `REQUEST_TIMEOUT_MS`; споделената базова стойност също е 600000. Вижте [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Времена на изчакване.

**Какво се нарушава при настройката по подразбиране**

Цикъл на разсъждение / извикване на инструмент в Codex, който остава безмълвен за повече от 10 минути без **реален upstream фрагмент**, се прекратява принудително от SSE механизма за следене на неактивност (`open-sse/utils/stream.ts`). Клиентът често вижда просто прекъсване на връзката — което съответства на „спря автоматично без никакво известие“.

Критична подробност: синтетичният SSE **heartbeat на OmniRoute не нулира** таймера за неактивност. Само реален фрагмент от upstream тялото актуализира `lastChunkTime`. От гледна точка на механизма за следене тих модел, който все още „мисли“, изглежда по същия начин като блокирал upstream.

Свързана неактивност на тялото в Undici: `FETCH_BODY_TIMEOUT_MS` (също по подразбиране използва същата базова стойност от 10 минути; `0` го деактивира). При поточно предаване `FETCH_TIMEOUT_MS` обхваща само установяването на връзката / първите заглавки — след като потокът стане активен, блокиранията се управляват от `STREAM_IDLE_TIMEOUT_MS` и `FETCH_BODY_TIMEOUT_MS`.

**Препоръчително за единична задача с продължителност няколко часа**

В средата на процеса OmniRoute (`.env` / compose / systemd):

```bash
# Деактивиране на прекъсванията при неактивен поток и неактивно тяло за дълги цикли на разсъждение
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Или ги увеличете над най-дългия очакван период без активност (стойностите са в милисекунди):

```bash
# Пример: разрешаване на до 2 часа бездействие между upstream фрагментите
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Рестартирайте OmniRoute, след като промените тези променливи на средата.

### Конкретна процедура — задача в Codex с продължителност няколко часа

1. **Фиксирайте акаунта:** Табло → Настройки → Маршрутизиране → Афинитет на сесията → TTL на афинитета = `43200` (12 ч.) или `86400` (максимум 24 ч.).
2. **Увеличете / деактивирайте прекъсванията при неактивност** в средата на OmniRoute:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Запазете обичайната конфигурация на Codex в `config.toml` (`wire_api = "responses"`, правилен `base_url`, `OMNIROUTE_API_KEY`) — в Codex няма настройки за афинитет/неактивност, управляващи тези две поведения.
4. Рестартирайте OmniRoute, след което стартирайте дългата задача в Codex.

### Решение относно стойностите по подразбиране (#7287)

| Настройка                | Стойност по подразбиране | Промяна в това ръководство?                                                                                  |
| ------------------------ | ------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `sessionAffinityTtlMs`   | `0` (изключено)          | **Не** — остава по избор (балансиране на натоварването спрямо непрекъснатост; вижте Дискусия #5718)          |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 мин)        | **Не** — остава 10 минути за общия трафик; операторите на дълги задачи в Codex го увеличават или деактивират |

Глобалната промяна на която и да е от стойностите по подразбиране би променила поведението за всеки клиент на даден екземпляр, а не само за Codex. Документирайте настройките; оставете стойностите по подразбиране непроменени, докато изрично решение на оператора не наложи друго.

### Диагностициране на прекъсванията поради неактивност

Когато механизмът за следене на неактивност се задейства, OmniRoute записва ред във формат като следния:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Търсете с grep за `Idle timeout: no data from` (или кода `stream_idle_timeout` / името на грешката `StreamIdleTimeoutError`). Сегментът за доставчика е този, който OmniRoute е използвал за съответната заявка (`codex`, идентификатор на друг доставчик или `provider`, ако е неизвестен) — той невинаги е буквалният низ `codex`.

## Отстраняване на проблеми

**`Error: wire_api = "chat" is no longer supported`**
Премахнете `wire_api = "chat"` от конфигурацията си. Задайте `wire_api = "responses"` или пропуснете полето (от v0.138 стойността по подразбиране е `"responses"`).

**`Error: model not found`**
Проверете дали моделът съществува в OmniRoute с правилния префикс. Използвайте `omniroute models list` или отворете `/dashboard/providers/<provider>`.

**`Authentication error`**
Уверете се, че `OMNIROUTE_API_KEY` е експортирана: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex проверява дали променливата на средата съществува, преди да направи първата заявка. Експортирайте реален ключ за защитени сървъри или непразна заместваща стойност, например `OMNIROUTE_API_KEY=local`, когато вашата **локална** инстанция на OmniRoute не изисква удостоверяване. Рестартирайте обвивката, ако сте я добавили в `~/.bashrc` или `~/.zshrc`.

**`Connection refused`**
Проверете дали OmniRoute работи и дали хостът/портът в `base_url` са правилни за вашата мрежа (локална, Tailscale или VPS).

**Сесията се срива близо до лимита на контекста**
Задайте изрично `model_context_window` и `model_auto_compact_token_limit`. Вижте таблицата за прозореца на контекста по-горе.

**Компактирането се задейства твърде късно**
Намалете `model_auto_compact_token_limit` до 80–85% от прозореца. Никога не задавайте стойност над 90%.

**Профилът не се зарежда (`-p <name>` се игнорира без съобщение)**
Уверете се, че файлът съществува на адрес `~/.codex/<name>.config.toml` (без префикс `profile-`). Изпълнете `ls ~/.codex/*.config.toml`.

**Продължителна задача на Codex прекъсва по време на изпълнение / превключва между акаунти при отделните заявки**
Вижте [Продължителни задачи](#long-running-tasks). Активирайте афинитет на сесията (с TTL, по-дълъг от продължителността на задачата) и увеличете или деактивирайте `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`. Потърсете `Idle timeout: no data from` в регистрационните файлове на OmniRoute с `grep`.
