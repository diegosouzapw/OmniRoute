Това ръководство описва добавянето на акаунти в Kiro (AI асистент за програмиране, хостван от AWS) към OmniRoute, с акцент върху едновременното използване на няколко акаунта без конфликти между сесиите.

---

## Контекст: Защо акаунтите в Kiro могат да влизат в конфликт

Бекендът на Kiro използва регистрации на OIDC клиенти в AWS SSO, за да проследява активните сесии.
Критичното ограничение е: **всяка регистрация на OIDC клиент поддържа само една активна
сесия в даден момент**. Когато второ устройство или потребител се удостовери чрез същия
регистриран клиент, бекендът анулира токена за опресняване на първия акаунт.

Това е същият механизъм, който създава проблеми при изпълнение на `kiro-cli login` на
машина, на която вече е вписан друг акаунт в Kiro — новото вписване анулира
токена на първия акаунт.

---

## Как OmniRoute решава този проблем (v3.8.0+)

От v3.8.0 нататък OmniRoute извиква `registerClient()` (AWS SSO OIDC) при всяко
импортиране на връзка с Kiro. Така всяка връзка в OmniRoute получава своя собствена
регистрация на OIDC клиент. Тъй като всяка регистрация на клиент е независима,
опресняването или повторното удостоверяване на един акаунт не засяга токена за
опресняване на никой друг акаунт.

Изолацията се прилага за методите за импортиране чрез токен за опресняване, а
удостоверяването с API ключ изцяло избягва OIDC сесиите за опресняване:

| Метод за импортиране                                               | Състояние на изолацията                                                                                          |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| AWS Builder ID / IDC поток с код за устройство                     | Изолиран от въвеждането на потока с код за устройство                                                            |
| **Импортиране на токен** (ръчно поставяне на токен за опресняване) | Изолиран от v3.8.0                                                                                               |
| **Социално вписване чрез Google / GitHub**                         | Изолиран от v3.8.0                                                                                               |
| **Автоматично импортиране** (SQLite на kiro-cli)                   | Изолиран от v3.8.0 (пътят през SQLite вече беше изолиран; резервният вариант чрез SSO кеша вече също е изолиран) |
| **API ключ** (дълготраен ключ за CodeWhisperer)                    | Няма сесия за опресняване; ключът се валидира и съхранява като идентификационни данни от тип bearer              |

---

## Бележка за мигриране на връзки, създадени преди v3.8.0

Връзките, импортирани преди v3.8.0, нямат специална регистрация на OIDC клиент,
съхранена в `providerSpecificData`. Тези връзки продължават да работят, но използват
споделената крайна точка за опресняване при социално удостоверяване, което означава,
че две такива връзки все още могат взаимно да анулират токените си.

**За да получите изолация:** изтрийте старата връзка от **Табло → Доставчици** и
я импортирайте отново чрез някой от поддържаните потоци за импортиране. Всички
новосъздадени връзки автоматично ще получат собствена регистрация на клиент.

## Добавяне на два акаунта в Kiro един до друг

### Предварителни изисквания

- OmniRoute v3.8.0 или по-нова версия.
- Работещ акаунт в Kiro (имейл + парола или вписване чрез Google или GitHub).
- По желание — втори акаунт в Kiro.

### Стъпка 1: Импортирайте първия акаунт

1. Отворете **Табло → Доставчици → Добавяне на доставчик → Kiro**.
2. Изберете една от следните възможности:
   - **Импортиране на токен** — поставете токен за опресняване, започващ с `aorAAAAAG`.
   - **API ключ** — поставете дълготраен API ключ за Kiro / CodeWhisperer.
   - **Вписване чрез Google / GitHub** — завършете OAuth потока в браузъра.
   - **Автоматично импортиране** — щракнете върху бутона; OmniRoute прочита идентификационните данни от
     локалната база данни на kiro-cli или от `~/.aws/sso/cache`.
3. Връзката се запазва. Потоците с токен за опресняване автоматично регистрират
   специален OIDC клиент. Потоците с API ключ валидират ключа чрез AWS и не съхраняват токен за опресняване.

### Стъпка 2: Импортирайте втория акаунт

Повторете стъпка 1 за втория акаунт. Тъй като всяко импортиране създава отделна
регистрация на OIDC клиент, двете връзки са напълно изолирани.

### Стъпка 3: Проверете дали и двете връзки са активни

1. **Табло → Доставчици** — и двете връзки с Kiro трябва да показват състояние **Активна**.
2. **Табло → Състояние** — и двете връзки трябва да преминат успешно проверката за валидност на токена.

### Стъпка 4: Използвайте комбинация за маршрутизиране между акаунтите

Създайте комбинация с двете връзки като цели, за да балансирате натоварването или да превключвате резервно между тях:

```
kiro/kiro-dev → kiro/kiro-pro
```

Вижте [FEATURES.md](./FEATURES.md) и документацията за маршрутизиране относно конфигурирането на комбинации.

## Корпоративни / IDC потребители

За акаунти в AWS IAM Identity Center (IDC) използвайте потока с **AWS Builder ID / IDC код на устройство**
от **Табло → Доставчици → Kiro → Код на устройство**. Потокът с код на устройство винаги е бил
напълно изолиран. За тези връзки не е необходимо повторно импортиране.

Корпоративните потребители, които работят в AWS регион, различен от региона по подразбиране, могат да посочат региона при
импортиране чрез API за импортиране на токени:

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

Когато е пропуснато, полето `region` по подразбиране е `us-east-1`.

## Поток за импортиране на API ключ

Удостоверяването с API ключ е предназначено за дългосрочни удостоверителни данни за достъп от тип bearer за Kiro / AWS CodeWhisperer. То
не използва OAuth опресняване и така избягва анулирането на споделена OIDC сесия.

### Табло

1. Отворете **Табло -> Доставчици -> Kiro**.
2. Изберете **API ключ**.
3. Поставете API ключа и по желание AWS региона (`us-east-1` по подразбиране).
4. OmniRoute валидира ключа и запазва връзката.

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### Вътрешен договор

API маршрутът валидира ключа чрез извикване на `KiroService.validateApiKey()`, което
използва `ListAvailableProfiles` спрямо съответстващата на региона крайна точка на CodeWhisperer/Amazon Q
и определя `profileArn`.

Запазената връзка използва:

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

По време на изпълнение `KiroExecutor.buildHeaders()` изпраща ключа като
`Authorization: Bearer <key>` и добавя `tokentype: API_KEY`. Извикванията за квота/профил
използват същия маркер, така че AWS третира bearer ключа като дългосрочен API ключ, а не като
OIDC токен или токен за достъп чрез социален профил.

## Изтичане на валидността на OIDC клиента

Публичните клиенти на AWS SSO OIDC обикновено изтичат след 90 дни
(`clientSecretExpiresAt`). OmniRoute съхранява това времево клеймо в `providerSpecificData`
за целите на наблюдаемостта. Ако връзката спре да се опреснява след около 90 дни, импортирайте я
повторно, за да получите нова регистрация на OIDC клиент. Автоматичната повторна регистрация при
изтичане на валидността е планирана като бъдещо подобрение.

Връзките с API ключ нямат срок на валидност на OIDC клиент, тъй като не се опресняват
чрез AWS SSO OIDC.

## Отстраняване на неизправности

### Вторият акаунт продължава да бъде отписван

- Проверете и двете връзки в **Табло → Доставчици** и потвърдете, че всяка показва стойност, различна от null, за
  `clientId` в необработения JSON (видим чрез иконата за информация). Ако в някоя от връзките липсва
  `clientId`, тя е била импортирана преди v3.8.0 — импортирайте я повторно.

### Импортирането е неуспешно със съобщение „Неуспешно валидиране на токена“

- Уверете се, че токенът за опресняване започва с `aorAAAAAG`.
- Уверете се, че OmniRoute има достъп до `https://oidc.us-east-1.amazonaws.com` (или конфигурирания
  регион). Ако сте зад корпоративен прокси сървър, задайте прокси на ниво доставчик в
  **Табло → Настройки → Прокси сървъри**.

### Импортирането на API ключ е неуспешно

- Потвърдете, че ключът е API ключ за Kiro / CodeWhisperer, а не токен за опресняване.
- Потвърдете, че AWS регионът съответства на ключа/акаунта. `us-east-1` е стойността по подразбиране.
- Ключът трябва да може да извиква `ListAvailableProfiles`; в противен случай OmniRoute не може
  да определи необходимия `profileArn`.

За други проблеми вижте основния файл [TROUBLESHOOTING.md](./TROUBLESHOOTING.md).
