> **Накратко**: OmniRoute проследява използването на токени за всяка заявка, изчислява разходите, налага квота за всеки API ключ и показва аналитични данни в таблото за управление. Това ръководство обяснява как работи всичко.

**Източници:**

- `open-sse/services/usage.ts` (~70KB) — основно проследяване на използването
- `src/lib/usageAnalytics.ts` (~10KB) — агрегиране за таблото за управление
- `src/lib/db/quotaSnapshots.ts` — исторически данни за квотите
- `src/lib/db/usage*.ts` — множество модули на базата данни, свързани с използването

---

## Общ преглед

Всяка заявка, която преминава през OmniRoute, генерира **запис за използването**, който съдържа:

- **Идентичност**: кой API ключ, доставчик, модел и комбинация са използвани
- **Токени**: токени на подканата, токени на отговора, кеширани токени, общ брой
- **Разходи**: сума в USD (изчислена от ценовите данни)
- **Времеви показатели**: латентност, времеви маркери за начало/край
- **Състояние**: успех, грешка, ограничена честота и др.

```
Заявка ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    анализи    квота   таксуване
                    (табло)  (налагане) (експорт)
```

## Какво се записва

Услугата `usage.ts` регистрира **събитие за използване** за всяка заявка:

| Поле               | Тип     | Източник                                                                     |
| ------------------ | ------- | ---------------------------------------------------------------------------- |
| `id`               | string  | UUID, генериран при записване                                                |
| `apiKeyId`         | string  | API ключът, който е инициирал заявката                                       |
| `provider`         | string  | Идентификатор на доставчика (openai, anthropic и др.)                        |
| `model`            | string  | Идентификатор на модела (gpt-5, claude-opus-4-6 и др.)                       |
| `comboId`          | string? | Идентификатор на комбинацията, ако заявката е маршрутизирана през комбинация |
| `promptTokens`     | number  | От отговора на външната услуга                                               |
| `completionTokens` | number  | От отговора на външната услуга                                               |
| `cachedTokens`     | number  | Токени от попадения в кеша (кеширане на подкани от Anthropic и др.)          |
| `totalTokens`      | number  | подканата + отговора                                                         |
| `costUsd`          | number  | Изчислено от ценовите данни                                                  |
| `latencyMs`        | number  | Продължителност на заявката от край до край                                  |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`                   |
| `errorClass`       | string? | Клас на грешката, ако състоянието != успех                                   |
| `timestamp`        | string  | ISO 8601 UTC                                                                 |
| `metadata`         | object  | Персонализирани данни, добавени от плъгини                                   |

### Откъде идват токените

Токените се извличат от отговора на външния доставчик в **обработчика на отговори**:

```ts
// От open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

За доставчици, които не връщат данни за използването (някои доставчици, използващи уеб бисквитки), OmniRoute **оценява приблизително** броя на токените чрез евристиката `~4 знака на токен` (вижте `open-sse/services/autoCombo/pipelineRouter.ts`).

### Кеширани токени

OmniRoute проследява `cached_tokens` отделно от `prompt_tokens`, защото:

- Кеширането на подкани от Anthropic таксува кешираните токени на намалена цена (10% от стандартната)
- Някои доставчици връщат `cache_read_input_tokens`, които трябва да бъдат ценообразувани по различен начин
- Аналитичните данни могат да показват **коефициента на попадения в кеша** = `cached_tokens / prompt_tokens`

## Изчисляване на разходите

Разходите се изчисляват от **ценови данни**, синхронизирани от LiteLLM (`src/lib/pricingSync.ts`):

| Модел             | Вход $/1M | Изход $/1M | Кеширани $/1M |
| ----------------- | --------- | ---------- | ------------- |
| gpt-5             | $2.50     | $10.00     | —             |
| claude-opus-4-6   | $15.00    | $75.00     | $1.50         |
| claude-sonnet-4-5 | $3.00     | $15.00     | $0.30         |
| gemini-2.5-pro    | $1.25     | $10.00     | —             |

Формулата за разходите (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Защо кешираните токени се изваждат от токените на подканата?** Кешираната част се таксува отделно; прилагането на входната цена към цялата подкана би довело до завишено отчитане.

### Синхронизиране на цените

Ценовите данни се синхронизират автоматично от LiteLLM чрез крайната точка `/api/pricing/sync` (задейства се от вградената cron задача, а не от достъпна за потребителя променлива на средата):

```bash
# Ръчно задействане
curl -X POST http://localhost:20128/api/pricing/sync
```

За модели без ценови данни OmniRoute преминава към **приблизително изчисляване на разходите** чрез вътрешни средни тарифи (извлечени от ценовите данни на LiteLLM).

## Агрегиране по период от време

Модулът `usageAnalytics.ts` изчислява компонентите на таблото за управление от необработените данни за използването. Той поддържа 7 периода от време:

| Период   | Времеви прозорец                      | Предназначение                                |
| -------- | ------------------------------------- | --------------------------------------------- |
| `1d`     | Последните 24 часа                    | Откриване на почасови пикове в разходите      |
| `7d`     | Последните 7 дни                      | Седмичен преглед                              |
| `30d`    | Последните 30 дни                     | Месечно фактуриране                           |
| `90d`    | Последните 90 дни                     | Тримесечен анализ                             |
| `ytd`    | От 1 януари на текущата година        | Проследяване на годишния бюджет               |
| `all`    | За цялото време                       | Статистика за целия период                    |
| `custom` | Зададени от потребителя начало и край | Одити, специализирани заявки при необходимост |

### Изчислявани компоненти на таблото за управление

За всеки период от време аналитичният слой изчислява:

| Компонент                         | Описание                                                        |
| --------------------------------- | --------------------------------------------------------------- |
| **Обобщаващи карти**              | Общ брой заявки, общи разходи, общ брой токени, успеваемост     |
| **Графика на дневния тренд**      | Разходи + токени на ден, групирани по модел                     |
| **Топлинна карта на активността** | Мрежа час от денонощието × ден от седмицата, цвят = брой заявки |
| **Разбивка по модели**            | Кръгова диаграма на разходите по модели                         |
| **Разбивка по доставчици**        | Стълбовидна диаграма на заявките по доставчици                  |
| **Водещи API ключове**            | Таблица с 10-те водещи ключа по разходи                         |
| **Анализ на грешките**            | Процент грешки във времето, най-чести класове грешки            |

### Програмен достъп

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // записи от хронологията на използването
  "7d",                 // период от време: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // карта на връзките с доставчици (connectionId → име на акаунта)
  {
    startDate: "2025-01-01",  // незадължително: за периода "custom"
    endDate: "2025-06-01",   // незадължително: за периода "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (цента)
console.log(analytics.byModel[0]);           // { модел, разходи, заявки, токени на подканата, токени на завършването }

## Налагане на квоти

Квотата за всеки API ключ се налага на две места:

1. **Мек лимит** (`quotaWarnAt`): предупреждение в таблото, когато потреблението надвиши прага
2. **Твърд лимит** (`quotaLimit`): заявката се отхвърля с HTTP 429 при надвишаване

### Конфигурация

```ts
// За всеки API ключ
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — показване на предупреждение
  quotaLimit: 10_00,    // $10.00 — твърдо спиране
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Процес на налагане

```
Заявка ──▶ quotaCheck()
              │
              ├── В рамките на лимита?  ──▶ разрешаване
              │
              └── Над лимита?  ──▶ 429 Too Many Requests
                                   със заглавка Retry-After
```

### Моментни снимки на квотите

Таблицата `quotaSnapshots` съхранява **историческото състояние на квотите** за анализ на тенденциите:

| Поле | Описание |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | Проследяваният ключ |
| `window` | "day" | "week" | "month" |
| `used` | Използвани разходи в този прозорец (центове) |
| `limit` | Лимитът (центове) |
| `resetAt` | Кога се нулира прозорецът |
| `createdAt` | Кога е направена моментната снимка |

Моментни снимки се правят **при всяка заявка** с разход > 0 и се използват за:

- Визуализиране на лентата за напредъка на квотата в таблото
- Показване на графики за тенденциите на квотата през последните 30 дни
- Задействане на предупреждения, когато потреблението наближи лимита

## Съхранение и почистване

Данните за използването нарастват с ~1-10KB на заявка. При голям мащаб това може да бъде значително.

### Настройки за съхранение

Периодът за съхранение на историята на използването се конфигурира чрез настройките на базата данни в потребителския интерфейс или чрез `/api/settings/database`.

По подразбиране историята на използването се съхранява **90 дни**.

### Почистване

Старите записи се почистват от `src/lib/db/cleanup.ts`:

- Задейства се от фоновия cron процес
- Изтрива от `usage_history` записите, по-стари от конфигурирания период за съхранение `usageHistory`

### Оценка на необходимото пространство

| Честота на заявките | Пространство за 30 дни | Пространство за 90 дни |
| ------------------- | ---------------------- | ---------------------- |
| 100 заявки/ден      | ~3MB                   | ~9MB                   |
| 1,000 заявки/ден    | ~30MB                  | ~90MB                  |
| 10,000 заявки/ден   | ~300MB                 | ~900MB                 |
| 100,000 заявки/ден  | ~3GB                   | ~9GB                   |

При много висок трафик обмислете:

- Намаляване на периода за съхранение чрез настройките на базата данни
- Използване на `aggregated_metrics` вместо необработени записи (само за анализи)

## Съвети за оптимизиране на разходите

### 1. Използвайте правилния модел

```bash
# Бърз отговор — използвайте евтин + бърз модел
curl -d '{"model":"auto/fast","messages":[...]}'

# Сложна задача — използвайте качествен модел
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Активирайте кеширането

Кеширането на подкани от Anthropic спестява **90% при повтарящ се контекст**:

```ts
// Кеширането е автоматично — просто включете същата голяма системна подкана
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Ще бъде кеширана автоматично
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Използвайте компресия

Компресията с RTK + Caveman спестява **15-95% при сесии с интензивно използване на инструменти**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Задайте квоти за всеки ключ

Винаги задавайте `quotaLimit`, за да предотвратите неконтролируеми разходи:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Лимит от $10/месец
```

### 5. Проверявайте най-големите потребители

Използвайте таблото или **`/api/usage/analytics`**, за да групирате по API ключ и да сортирате по разход:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Отстраняване на неизправности

### „Разходът е по-висок от очакваното“

1. Проверете **`/api/usage/analytics?groupBy=model`** — открийте скъпия модел
2. Проверете **`/api/usage/analytics?groupBy=apiKey`** — открийте големия потребител
3. Уверете се, че данните за цените са актуални: `POST /api/pricing/sync`

### „Липсващи записи“

- Проверете настройките за съхранение на базата данни в Табло → База данни → Почистване — старите записи се изтриват от периодичната задача за почистване (`src/lib/db/cleanup.ts`)
- Проверете за грешки в `src/lib/db/usage*.ts` — неуспешните записвания в базата данни се регистрират, но не се показват
- Уверете се, че заявката действително е достигнала `chatCore` — проверете комбинираното маршрутизиране

### „Квотата не се прилага“

- Проверете настройката `quotaLimit` на ключа
- Уверете се, че `quotaWindow` е зададена правилно
- Потърсете записи в `quotaSnapshots` — те трябва да се създават при всяка заявка
