Изпълнявайте CLI инструмента `omniroute` на лаптопа си, докато самият OmniRoute работи някъде другаде
(на VPS, домашен сървър или друга машина във вашата Tailnet мрежа). Влизате веднъж с
`omniroute connect` и от този момент нататък **всяка** CLI команда е насочена към отдалечения
сървър — същите команди, същият изход, но изпълнени спрямо отдалечения сървър.

Не е необходимо да инсталирате втори инструмент: отдалеченият режим използва обикновения CLI
инструмент `omniroute` плюс **токени за достъп** с определен обхват.

```bash
npm install -g omniroute                 # стандартният CLI инструмент
omniroute connect 192.168.0.15           # влизане (парола → токен с обхват)
omniroute models list                    # ← вече изброява моделите на ОТДАЛЕЧЕНИЯ сървър
omniroute configure codex                # ← записва локален Codex профил от отдалечения каталог
```

## Как работи

```
вашият лаптоп                          отдалечен OmniRoute (VPS)
┌────────────────────┐                   ┌───────────────────────────────┐
│ CLI omniroute      │  POST /api/cli/connect  (парола → токен)           │
│  контекст: vps     │ ───────────────►  │ издава токен с обхват          │
│  baseUrl, токен    │  Authorization: Bearer oma_live_…                  │
│                    │ ───────────────►  │ всеки маршрут за управление,   │
│ записва конфигурации│ ◄───────────────  │ проверен спрямо обхвата на токена│
│ ЛОКАЛНО            │                   └───────────────────────────────┘
└────────────────────┘
```

- **Контекстите** съхраняват по един сървър (`~/.omniroute/config.json`, `chmod 600`).
  `omniroute contexts use <name>` превключва активния сървър; `default` е локалният.
- **Токените за достъп** (`oma_live_…`) разрешават команди за управление. Те са
  различни от API ключовете за извод (`sk-…`, използвани за `/v1/chat/completions`).
- От страна на сървъра се съхранява само SHA-256 хешът на токена. Токенът в четим вид се показва
  **само веднъж** при създаването.

## Свързване

### С паролата за управление (първоначално настройване)

```bash
omniroute connect 192.168.0.15
# Парола за управление за http://192.168.0.15:20128: ********
# ✔ Свързано с http://192.168.0.15:20128 — контекст „192.168.0.15“ (обхват: admin)
```

По подразбиране процесът с парола издава токен с обхват **admin** (разполагате с паролата, така че
вече имате пълен контрол). Ограничете обхвата с `--scope`:

```bash
omniroute connect 192.168.0.15 --scope write
```

Опции: `--port <p>` (когато към хоста няма зададен порт), `--name <ctx>` (име на контекста),
`--scope read|write|admin`. Пълният URL адрес се използва във вида, в който е зададен:
`omniroute connect https://omni.example.com`.

### С предварително генериран токен

Генерирайте токен с определен обхват в таблото за управление (или с `omniroute tokens create`) и
го поставете — не е необходима парола:

```bash
omniroute connect 192.168.0.15 --key oma_live_xxxxxxxx
```

CLI инструментът го валидира чрез `GET /api/cli/whoami` и го запазва като активен контекст.

## Обхвати

Три йерархични нива (`admin ⊃ write ⊃ read`):

| Обхват  | Позволени действия                                                                        |
| ------- | ----------------------------------------------------------------------------------------- |
| `read`  | изброяване/преглед — `models list`, `providers status`, `logs`, `usage`, `cost`           |
| `write` | read **+** конфигуриране/прилагане — `setup-codex`, `keys add`, `config set`, комбинации  |
| `admin` | write **+** управление — CRUD за `tokens`, добавяне на доставчици, услуги, правила, oauth |

Сървърът определя необходимия за всеки маршрут обхват въз основа на HTTP метода
(`GET`→read, промени→write), както и чрез списък с чувствителни операции, разрешени само за admin
(`/api/cli/tokens`, промени в `/api/providers`, `/api/oauth`, `/api/services`, …).
Токен с недостатъчен обхват получава отговор `403` с ясно съобщение.

> Маршрутите, които стартират процеси (`/api/services/*`, `/api/mcp/*`, …), остават
> достъпни **само през loopback** — отдалечен токен никога не може да ги достъпи, независимо от обхвата.

## Свързване на Antigravity при отдалечена инсталация

Antigravity използва екрана за съгласие firstparty/nativeapp на Google. Google
предоставя кода за оторизация само когато **loopback пренасочването**
(`http://127.0.0.1:<port>/callback`) е **достъпно от браузъра, който
одобрява влизането**. При инсталация на отдалечен VPS този loopback адрес се намира
на сървъра, а не на вашата машина, затова екранът за съгласие **увисва завинаги и
никога не връща код** — обичайният резервен вариант „поставете URL адреса за обратно
извикване“ няма какво да постави. (Това е ограничение от страна на Google: същото
увисване възниква във всяко прокси, което използва включения настолен клиент
Antigravity, а не само в OmniRoute.)

Таблото открива това, преди да блокирате: отварянето на **Providers → Antigravity →
Connect** от адрес, различен от localhost, заменя общото известие „копирайте URL
адреса за обратно извикване“ с двете решения по-долу, като вашите хост и порт вече
са попълнени. (LAN адрес също се брои — `192.168.x.x` не е localhost по отношение
на това обратно извикване.)

Има два поддържани начина за свързване на Antigravity към отдалечен OmniRoute.

### Вариант A — локален помощник за влизане (препоръчително)

Изпълнете OAuth на **собствения си компютър**, където `127.0.0.1` е достъпен.
Помощникът комуникира директно с Google, така че процесът на съгласие завършва там,
където версията в таблото не може.

**Ако вече сте свързани** (`omniroute connect <host>`), няма нищо за копиране —
помощникът предава идентификационните данни към тази инсталация вместо вас:

```bash
# На вашата ЛОКАЛНА машина (необходими са Node.js + браузър):
omniroute connect 192.168.0.15        # еднократно — създава контекстен токен с администраторски обхват
npx omniroute login antigravity
#   ↳ отваря екрана за съгласие на Google, прихваща обратното извикване на локален loopback порт,
#     обменя го и изпраща с POST идентификационните данни към активния контекст:
#
#   Antigravity е свързан на http://192.168.0.15:20128 (връзка abc123).
#   Няма нищо за поставяне — можете да затворите този терминал.
```

Изпращането се извършва автоматично винаги когато активният контекст сочи към друга
машина. Наложете го в едната или другата посока с `--push` / `--no-push` или
насочете към конкретен контекст с `--context <name>`.

**Ако вашата машина не може да достигне VPS** (защитна стена, липса на SSH,
изолиран компютър), помощникът продължава да работи — той _се нуждае_ единствено
от Google. Използвайте `--no-push` или просто оставете изпращането да се провали:
тогава вместо да отхвърли вече завършеното оторизиране, той извежда blob низа.

```bash
npx omniroute login antigravity --no-push
#   omniroute-cred-v1.eyJ2IjoxLCJ...
```

След това в **отдалеченото** табло отворете **Providers → Antigravity → Connect** и
поставете blob низа `omniroute-cred-v1.…` в полето **Step 2** (то приема както URL
адрес за обратно извикване, така и blob низ с идентификационни данни). OmniRoute го
декодира, изпълнява въвеждането в Cloud Code от страна на сървъра и запазва
връзката.

> Blob низът съдържа токен за опресняване — третирайте го като парола. При изпращане
> той се предава веднъж през удостоверената връзка на вашия контекст; при ръчно
> поставяне — през връзката с вашето табло. И в двата случая се съхранява криптиран,
> а при успешно изпращане никога не се извежда във вашия терминал.

Флагове: `--no-browser` (извежда URL адреса вместо автоматично отваряне),
`--port <n>` (фиксира loopback порта), `--timeout <ms>`, `--push` / `--no-push`
(заменя автоматичния избор за предаване), `--context <name>` (насочва към конкретен
контекст).

### Вариант B — SSH тунел с локално препращане

Ако имате SSH достъп до VPS, препратете порта на таблото, така че loopback
обратното извикване да се насочва обратно към сървъра през тунела:

```bash
# На вашата ЛОКАЛНА машина:
ssh -L 20128:127.0.0.1:20128 user@your-vps
# след това отворете http://localhost:20128 в ЛОКАЛНИЯ си браузър и свържете Antigravity
# по обичайния начин — пренасочването към 127.0.0.1:20128/callback вече достига VPS чрез SSH.
```

Тъй като достъпвате таблото като `localhost:20128`, процесът за съгласие на Google
завършва и обратното извикване се доставя до сървъра през същия тунел — не е
необходим blob низ. Дръжте тунела отворен, докато връзката не се покаже като
активна.

За разлика от доставчиците с фиксиран loopback по-долу, тук е достатъчно **едно
препращане**: обратното извикване на Antigravity използва самия порт на таблото,
така че няма втори специфичен за доставчика порт, който да бъде пренасочван.

> Напълно безинтерфейсна алтернатива (без помощник и без тунел) е да конфигурирате
> **собствени** идентификационни данни за Google OAuth уеб приложение + публичен
> базов URL адрес; вижте OAuth променливите на средата за доставчика. Двата варианта
> по-горе не изискват допълнителна настройка в Google.

## Свързване на Codex / Grok при отдалечена инсталация (доставчици с фиксиран loopback адрес)

Codex, xAI (`xai-oauth`) и Grok CLI (`grok-cli`) регистрират **фиксиран** loopback
`redirect_uri` в своето upstream OAuth приложение. OmniRoute не може да го промени —
доставчикът винаги връща браузъра към един и същ твърдо зададен адрес:

| Доставчик   | Фиксиран callback адрес, към който пренасочва доставчикът |
| ----------- | --------------------------------------------------------- |
| `codex`     | `http://localhost:1455/auth/callback`                     |
| `xai-oauth` | `http://127.0.0.1:56121/callback`                         |
| `grok-cli`  | `http://127.0.0.1:56122/callback`                         |

Тук `localhost` означава **машината, на която работи браузърът**, докато callback
сървърът на OmniRoute за PKCE слуша на loopback адреса на **сървъра**. Ако отворите
таблото за управление на LAN адрес като `http://192.168.0.15:20128`, двете никога
не се свързват: кодът за оторизация се доставя до `localhost:1455` на собствения ви
лаптоп, където нищо не слуша, и доставчикът прекратява вписването, без да покаже
грешка.

Таблото за управление засича това, преди да отвори изскачащия прозорец, и показва
командата за тунела, вместо да остави вписването да се провали безшумно (#8046).

### Решение — пренасочете **и двата** порта

```bash
# На машината, на която работи БРАУЗЪРЪТ:
ssh -L 20128:127.0.0.1:20128 -L 1455:127.0.0.1:1455 <user>@192.168.0.15
# след това отворете http://localhost:20128 и свържете Codex оттам
```

Необходими са две пренасочвания, а пренасочването само на едното пак няма да
работи:

- **`20128`** (портът на таблото за управление) прави origin адреса действително
  локален `localhost`, което позволява на OmniRoute изобщо да стартира callback
  сървъра за PKCE — LAN origin адрес никога не достига до този клон.
- **`1455`** (фиксираният callback порт на доставчика) е адресът, към който се връща
  браузърът; той трябва да бъде тунелиран до loopback адреса на сървъра.

Заменете `1455` с `56121`/`56122`, когато свързвате xAI или Grok CLI, а `20128` —
с действителния порт на вашето табло за управление. Оставете тунела отворен, докато
връзката не бъде показана като активна.

> **Нямате SSH достъп?** Codex и Grok CLI приемат и поставен токен — разделът
> **Поставяне на API ключ** / **Импортиране на auth.json** в диалоговия прозорец
> за свързване. Този начин няма loopback callback, затова работи от всеки origin
> адрес. Освен това Codex приема самостоятелен access токен или session blob от
> `~/.codex/auth.json`.

## Управление на токени

```bash
omniroute tokens create --name "laptop" --scope write [--expires 30]
#   ↳ отпечатва тайната стойност САМО ВЕДНЪЖ — копирайте я сега
omniroute tokens list                 # маскирани: id, име, обхват, префикс, състояние, срок на валидност
omniroute tokens revoke <id|prefix>   # отменя незабавно
omniroute tokens scopes               # обяснява трите обхвата
```

Командите `tokens` изискват **администраторски** идентификационни данни. Можете
също да управлявате токени от таблото за управление под **Настройки → Токени за
достъп** (създаване, отмяна, еднократно копиране).

## Конфигуриране на CLI за програмиране от отдалечения каталог

`omniroute configure` прочита актуалния каталог с модели на **активния сървър** и
записва конфигурация на **вашата** машина.

```bash
omniroute configure codex
#   Доставчици: glm, kmc, ollamacloud, opencode-go, …
#   Доставчик: glm
#   ID на модел: glm/glm-5.2
#   ✔ Записан е ~/.codex/glm52.config.toml
#   Използване:  codex --profile glm52

# неинтерактивно
omniroute configure codex --provider glm --model glm/glm-5.2 --name glm52

# задържане на често използван модел в горната част на интерактивния списък
omniroute configure codex --provider glm --model glm/glm-5.2 --favorite --yes
```

Интерактивният списък съхранява само ID на модели (никога URL адреси или
идентификационни данни) в локалния файл `model-preferences.json`, с отделен обхват
според контекста и целевия CLI. Предпочитаните модели се показват преди последно
избираните; използвайте `--unfavorite`, за да премахнете избран модел от списъка
за съответния контекст/цел.

Записаният профил препраща към ключа за inference чрез променлива на средата
(`OMNIROUTE_API_KEY`) — тайната стойност никога не се записва на диска. За
еднократната базова настройка на Codex (блока `[model_providers.omniroute]`) вижте
[CODEX-CLI-CONFIGURATION.md](./CODEX-CLI-CONFIGURATION.md).

### Стартиране на CLI към отдалечения сървър (без записване на конфигурация)

`omniroute run <target>` също се съобразява с активния контекст: отдалеченият
основен URL адрес и идентификационните данни на контекста се подават само към
стартирания процес.

```bash
omniroute connect 192.168.0.15
omniroute run claude   --model openai/gpt-5.4          # Claude Code → отдалечен сървър
omniroute run gemini   --model glm/glm-5.2 -- --skip-trust -p "hello"
omniroute run opencode --model glm/glm-5.2 -- run "reply OK"

# Прегледайте точно какво ще бъде стартирано (само ИМЕНАТА НА КЛЮЧОВЕТЕ на средата, никога стойностите):
omniroute run codex --dry-run --json
```

Цели: `claude`, `codex`, `aider`, `goose`, `opencode`, `qwen`, `gemini`
(единствен източник: `bin/cli/cli-manifest.mjs`). Qwen и Gemini се изпълняват с
временна изолирана home директория, която се премахва при приключване, така че
стартирането никога не засяга — нито допуска изтичане към — личната ви
конфигурация на инструментите.

Всеки поддържан CLI има команда за настройка, съобразена с отдалечения сървър
(всички използват активния контекст или `--remote <url> --api-key <key>`):

| ----------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Codex       | `omniroute setup-codex`    | профили в `~/.codex/<name>.config.toml` (за всеки модел)                                                                                                                                                       |
| Claude Code | `omniroute setup-claude`   | `~/.claude/profiles/<name>/settings.json` (за всеки модел)                                                                                                                                                     |

| Cline       | `omniroute setup-cline`    | `~/.cline/data/{globalState,secrets}.json` (CLI режим) + извежда настройките за разширението за VS Code, които да поставите (съвместимо с OpenAI, базов URL **без** `/v1`)                                     |

> за идентификационни данни на OpenCode, така че за отдалечен шлюз изобщо не е необходим ключ в
> `opencode.json`.

## Управление на контексти (превключване между сървъри)

**Контекст** е запазен сървър (baseUrl + идентификационни данни + обхват). `omniroute connect`
създава такъв и го прави активен; от този момент нататък всяка команда е насочена към него. Управлявайте
и превключвайте между контекстите с `omniroute contexts`:

```bash
omniroute contexts list            # всички контексти; активният е отбелязан с ●
omniroute contexts current         # активният сървър, състоянието на удостоверяването и обхватът
```

```text
  | Име     | Базов URL адрес           | Удостоверяване | Обхват | Описание
● | vps     | http://100.67.86.91:20128 | token          | admin  | Отдалечен OmniRoute (…)
  | default | http://localhost:20128    | ✗              |        |
```

**Превключване между сървъри** — всяка следваща команда използва активния контекст:

```bash
omniroute contexts use vps         # → всички команди вече са насочени към отдалечения VPS
omniroute tokens list              #   (изпълнява се спрямо VPS)

omniroute contexts use default     # → обратно към localhost
omniroute tokens list              #   (изпълнява се спрямо локалния сървър)
```

**Ръчно добавяне на контекст** (вместо `connect`), преглед или преименуване:

```bash
omniroute contexts add staging --url https://staging.example.com:20128 \
  --access-token oma_live_xxxx --scope write --description "staging box"
omniroute contexts show staging    # пълни подробности за конкретен контекст
omniroute contexts rename staging stg
```

**Премахване на контекст** — изисква потвърждение; подайте `--yes`, за да го пропуснете
(задължително за скриптове/неинтерактивни обвивки, които в противен случай отказват безопасно):

```bash
omniroute contexts remove stg --yes
```

> `default` (localhost) не може да бъде премахнат. При премахване на активния контекст се преминава
> към `default`. Съвет: премахването на контекст изтрива само **локално** запазените идентификационни данни —
> оттеглете токена на сървъра с `omniroute tokens revoke <id>`, за да прекратите действително
> достъпа.

**Експортиране/импортиране** на контексти (например за прехвърлянето им между машини). Новите контексти съхраняват
само препратка към хранилището за ключове; идентификационните данни не се копират в експортирания файл, когато е налично
хранилището за ключове на операционната система:

```bash
omniroute contexts export --out contexts.json     # по подразбиране: stdout
omniroute contexts import contexts.json            # презаписване; използвайте --merge, за да запазите съществуващите
omniroute contexts migrate --yes                  # преместване на наследените токени в обикновен текст към хранилището за ключове
```

При системи без графична среда и без използваемо хранилище за ключове на операционната система CLI преминава към
`config.json` с режим `0600` и показва еднократно предупреждение. Третирайте експортираните файлове от
този резервен вариант (както и всички наследени конфигурации преди миграцията) като поверителен материал.

## Бърза цялостна проверка

Жизнен цикъл за директно копиране и поставяне, с който да проверите от нулата отдалечена конфигурация — свързване, издаване на
токен с определен обхват, насочване на команда, връщане обратно и премахване. Заменете
`192.168.0.15` с името на хоста/IP адреса на вашия сървър (Tailscale, LAN или публичен
`https://…` URL адрес).

```bash
# 1. Свързване (парола → администраторски токен, запазен като контекст, който става активен)
omniroute connect 192.168.0.15                 # или: --key oma_live_xxxx  (без парола)
omniroute contexts current                     # показва отдалечения сървър + обхвата

# 2. Използване — командите за управление вече се изпълняват спрямо отдалечения сървър
omniroute tokens create --name laptop --scope read   # издаване на токен с по-тесен обхват
omniroute tokens list                                 # маскиран списък от отдалечения сървър

# 3. Превключване в двете посоки
omniroute contexts use default                 # → локален
omniroute contexts use 192-168-0-15            # → отново отдалечен (името е от `contexts list`)

# 4. Премахване. ЗАБЕЛЕЖКА: `contexts remove` изтрива само ЛОКАЛНИТЕ идентификационни данни —
#    НЕ оттегля токена на сървъра. Първо го оттеглете от страната на сървъра, ако
#    искате действително да прекратите достъпа.
omniroute tokens revoke <id|prefix>            # прекратява достъпа до сървъра
omniroute contexts remove 192-168-0-15 --yes   # премахване на локалния контекст (дори ако е активен → преминава към default), без подкана
```

> `--yes` прави `contexts remove` неинтерактивна (задължително в скриптове/CI; без
> него неинтерактивната обвивка отказва безопасно, вместо да увисне). При премахване на
> **активния** контекст автоматично се преминава към `default`.

## Бележки за сигурността

- Токенът в обикновен текст се показва еднократно; съхранява се само SHA-256 хешът (както при API ключовете).
- `omniroute connect` използва същото блокиране при многократни неуспешни опити за вход и същото регистриране за одит.
- За транспорта предпочитайте HTTPS или Tailnet; при задаване само на хост по подразбиране се използва `http://`
  за удобство в LAN/Tailscale — подайте пълен `https://…` URL за TLS.
- Предпочитаният локален контекстен файл е `~/.omniroute/config.json` (`chmod 600`),
  съдържащ само `credentialRef`; самият токен се съхранява в хранилището за идентификационни
  данни на операционната система (`keytar`) и никога не се отпечатва в регистрационните файлове. Инсталациите без графичен интерфейс, при които
  няма работещо собствено хранилище за идентификационни данни, използват същия файл с права `0600` като изрично резервно решение и
  извеждат предупреждение еднократно. Използвайте `omniroute contexts migrate --yes` след инсталиране на
  бекенд за хранилището за идентификационни данни.
