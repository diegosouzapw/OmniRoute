---

OmniRoute предоставя **два** начина за използване на OpenAI Codex:

| Доставчик              | Как комуникира с OpenAI                                                                                                                                                                              | Уточнение за употребата                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| **`codex`**            | Препредава директно вашия ChatGPT/OpenAI OAuth токен към Responses API                                                                                                                               | **Да** — официалната сесия не е оторизирана за използване чрез прокси/маршрутизатор |
| **`codex-app-server`** | Управлява **собствения `codex app-server` на Codex CLI** чрез JSON-RPC/WebSocket; CLI притежава и автоматично опреснява своя OAuth (`~/.codex/auth.json`) точно както при интерактивна `codex` сесия | **Не** — OmniRoute никога не препредава токен към API                               |

Тъй като `codex-app-server` никога не препредава токен, за него не важи
уточнението за употреба, свързано с препредаване на сесия. Той изисква **Codex CLI, достъпен на
конфигурирания URL на app-server**, като този CLI трябва да е **вписан**.

---

## 1. Архитектура

```
┌─ Приложение OmniRoute ──────────┐        ┌─ Страничен контейнер codex-app-server ┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                     │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456            │
│  (+ токен за достъп)             │  JSON  │  --ws-auth capability-token            │
│                                  │  RPC   │  управлява самостоятелно OpenAI OAuth  │
└──────────────────────────────────┘        │  (~/.codex/auth.json, автоопресняване) │
        │ споделя (compose томове)           └────────────────────────────────────────┘
        ▼
  codex-appserver-token   → WS токенът за достъп (монтиран и от двете)
  codex-appserver-home    → ~/.codex (auth.json се записва от таблото,
                             чете се от codex app-server в страничния контейнер)
```

- Страничният контейнер слуша **само** във вътрешната compose мрежа
  (`ws://codex-app-server:1456`) зад токен за достъп. Той **никога** не се
  публикува към хоста или интернет.
- Codex CLI е вграден в `omniroute:base`, така че не е необходимо codex да бъде
  инсталиран на хоста или на машината на потребителя, когато стартирате страничния контейнер.

## 2. Стартиране

```bash
# Стартирайте стека С профила за страничния контейнер codex app-server:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

При първото стартиране страничният контейнер генерира своя WS токен за достъп (в споделения
том `codex-appserver-token`), а приложението прочита същия токен чрез
`OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`. Не е необходимо ръчно конфигуриране на токена.

## 3. Свързване и вписване

1. В таблото добавете връзка за **OpenAI Codex (App-Server)**. Не се изисква API
   ключ или токен (това е доставчик без удостоверяване — страничният контейнер управлява удостоверяването).
2. Ако Codex CLI на страничния контейнер **все още не е вписан**, проверката за
   изправност на връзката показва _„работи, но не е вписан“_ (а не червена грешка при удостоверяване). Използвайте
   **Вписване с ChatGPT**: това изпълнява стандартното device-OAuth удостоверяване на Codex във вашия
   браузър и след това записва `~/.codex/auth.json` в споделения том чрез
   **Прилагане на удостоверяването** (едно и също вписване обслужва както доставчика `codex`, така и
   доставчика `codex-app-server`).
3. След вписването проверката за изправност става зелена (тя проверява както `/readyz`, **така и**
   `account/read` — т.е. че услугата работи _и_ е удостоверена) и започва да работи.

Таблото никога не презаписва изправен съществуващ `~/.codex/auth.json` — то записва
само когато файлът липсва или токенът му е остарял (винаги се създава резервно копие).

## 4. Сценарии за внедряване

- **Оператор с вече удостоверен Codex CLI** — монтирайте вашата хост директория
  `~/.codex` в страничния контейнер (`codex-appserver-home`) и пропуснете стъпката за вписване.
- **Публичен потребител без локално инсталиран codex** — това няма значение: страничният контейнер разполага с
  CLI. Потребителят се удостоверява единствено чрез таблото.
- **OmniRoute директно върху физическа машина (без страничен контейнер, с codex на хоста)** — насочете
  `OMNIROUTE_CODEX_APPSERVER_WS` към вашия собствен `codex app-server` и се уверете, че
  codex на хоста е вписан; подсказката „codex не е инсталиран“ се появява, ако изпълнимият
  файл липсва.

## 5. Домашен / UDP изходящ трафик (допълнение за оператори, не се доставя)

Общият страничен контейнер по-горе изпраща изходящия трафик през обичайната мрежа на контейнера. Оператор,
който се нуждае трафикът на Codex да излиза през **домашна изходна точка** (напр. TUN
tailscale страничен контейнер, пренасящ TCP + UDP/QUIC), изпълнява това като отделно compose
заместване; то умишлено **не** е част от доставяния профил `codex-app-server`.
Вижте вътрешното оперативно ръководство за тази конфигурация.
