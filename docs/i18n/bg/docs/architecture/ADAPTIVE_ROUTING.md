Този документ описва основата за адаптивно маршрутизиране, управлявано от обратна връзка, добавена към
OmniRoute. Тя умишлено е малка: въвежда типизиран канал за резултати от маршрутизирането,
онлайн сигнал за качество, който захранва съществуващия механизъм за оценяване на auto-combo,
незадължителен OpenTelemetry експортер и крайна точка за обяснимост. Тя **не**
заменя съществуващия стек за устойчивост (прекъсвач на веригата, период на изчакване за връзка,
блокиране на модел, матрица на състоянието, автопилот) — тя го допълва.

## 1. Архитектурен контекст

OmniRoute е равнина за данни с **критичен път на заявките** и **равнина за
управление/интелигентност**. Критичният път трябва да остане бърз, ефективен по отношение на паметта, асинхронен, устойчив и
предсказуем. Оценяването, определянето на качеството, експериментите и историческият анализ принадлежат
към равнината за управление.

```
AI агент / IDE
      │
      ▼
┌─────────────────────┐
│    OmniRoute        │   равнина за данни (бърза, синхронна, в паметта)
│  маршрутизиране /   │
│  превключване       │
│  състояние / защита │
│  кеш / поточно      │
│  предаване          │
└──────────┬──────────┘
           │ RoutingEvent (изпрати и забрави, ~0.2µs)
           ▼
┌─────────────────────┐
│  Приемници на       │   равнина за управление (асинхронна, без гаранция за доставка)
│  обратна връзка     │
│  проследяване на    │
│  качеството         │
│  OTel експортер     │
│  хранилище за       │
│  обяснения          │
└──────────┬──────────┘
           ▼  оценка за качество
      механизъм за оценяване на auto-combo
```

### Какво вече съществуваше (проверено, без дублиране)

| Концепция                                 | Съществуваща реализация                                                                                                          |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Наличност (можем ли да изпращаме трафик?) | Прекъсвач на веригата (CLOSED/DEGRADED/OPEN/HALF_OPEN, съхраняван в БД), период на изчакване за връзка, блокиране на модел       |
| Отчитане на състоянието                   | `providerHealthMatrix.ts`, `providerHealthAutopilot.ts`                                                                          |
| Сенчест трафик                            | `open-sse/services/combo/shadowRouting.ts`                                                                                       |
| Защитни механизми                         | `src/lib/guardrails/` (куки преди/след обработката)                                                                              |
| Точен кеш                                 | `src/lib/semanticCache.ts` (базиран на сигнатури)                                                                                |
| Оценители / маршрутизиране чрез оценки    | `src/lib/evals/`, `open-sse/services/evalRouting.ts`                                                                             |
| Обяснимост на решенията за комбинации     | `open-sse/services/combo/decisionTrace.ts`                                                                                       |
| Събития в реално време за таблото         | `src/lib/events/eventBus.ts` (канал за известяване на потребителския интерфейс, полезни товари `unknown`, история от 100 записа) |

Слоят за събития при маршрутизиране **не** е повторна реализация на `eventBus`: тази шина е
каналът за известия в реално време на таблото (типизирани _имена на събития_, непрозрачни
полезни товари, потребители от потребителския интерфейс). `RoutingEvent` е типизирана структура за _резултат_
(латентност/токени/цена/резултат/причина за приключване), използвана от приемниците за
обратна връзка на равнината за управление (проследяване на качеството, OTel експортер, хранилище за обяснения).

### Какво липсваше (добавено тук)

1. **Типизирано събитие за резултат от маршрутизирането + абстракция за приемник** (`RoutingEvent` /
   `RoutingEventSink`). `decisionTrace` е ограничено до комбинации и съществува само в паметта;
   `comboMetrics` са кумулативни броячи; `call_logs` е необработено асинхронно съхранение.
   Нито едно от тях не представлява типизиран, базиран на приемници канал за резултати, за който могат да се абонират
   проследяващ механизъм за качество, OTel експортер или оценител в стил Future-AGI.
2. **Онлайн сигнал за качество** (EWMA) за качеството на изхода — преди това механизмът за оценяване
   представяше „качеството“ само чрез статична пригодност за задачата и честота на преминаване на незадължителните оценки.
3. **Незадължителен OTel експортер без зависимости**, използващ семантичните конвенции на GenAI.
4. **Крайна точка за обяснимост**, връщаща реалните решения за маршрутизиране + състоянието на качеството.

## 2. Събития за маршрутизиране (основа за обратна връзка)

Файлове: `open-sse/services/routing/events.ts`, `.../index.ts`

`RoutingEvent` съдържа само метаданни за маршрутизирането:

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ...
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // обединение от разрешени стойности
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

`RoutingEventSink` е trait в стил `Send+Sync` за TypeScript:

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // трябва да е O(1), без синхронен I/O
}
```

Критичният път извиква `emitRoutingEvent(event)` веднъж за всяка завършена заявка
(callback-а при завършване на поточно предаване, пътя за успешен резултат без поточно
предаване и пътя за неуспех при невалиден отговор със статус 200 в `handleChatCore`).
Разпращането е синхронно към всички регистрирани приемници, но всеки приемник само
добавя към опашка/актуализира състояние в паметта. **Без синхронни записи в база
данни и без мрежов I/O по критичния път.**

Приемници по подразбиране:

- `MemoryRoutingEventStore` — ограничен (500) кръгов буфер, първо най-новите записи,
  за крайната точка за обяснения.
- Консуматорът `QualityTracker` — актуализира EWMA оценката за качество.
- `OtlpHttpsEventSink` — незадължителен, активира се само когато е зададена
  `OMNIROUTE_OTEL_ENDPOINT` (или `OTEL_EXPORTER_OTLP_ENDPOINT`).

### Измерено натоварване (обективно сравнение)

`npm run bench:routing-events` на тази работна станция (100k итерации; операциите
под µs са измерени като агрегирани µs/op, тъй като персентилите за отделна операция
са под разделителната способност на таймера `performance.now()`):

| Сценарий                                         | µs/op  | ops/s  |
| ------------------------------------------------ | ------ | ------ |
| базов вариант (само оценяване)                   | ~0.045 | ~22 M  |
| базов вариант + RoutingEvent (2 приемника)       | ~0.168 | ~5.9 M |
| базов вариант + събитие + OTel добавяне в опашка | ~0.163 | ~6.1 M |
| паралелно (8 преплетени серии)                   | ~0.18  | —      |

Разликата при разпращането на събития спрямо базовото оценяване е ~0.12 µs/заявка;
OTel приемникът само добавя към опашка (O(1) добавяне в буфер), без измеримо
допълнително натоварване. Тези стойности са специфични за машината и относителни —
не са гаранция за продукционна среда. Стойността „~0.2 µs“ във v1 беше агрегирана
оценка; тази методология отделя базовото оценяване от разхода за разпращане на
събития.

## 3. Сигнал за качество (състояние на доставчика, управлявано от обратна връзка)

Файлове: `open-sse/services/routing/quality.ts`

v2 разделя **оперативното** от **семантичното** качество:

- **Оперативно** — извлича се от критичния път за маршрутизиране (HTTP 4xx/5xx,
  неуспешни връзки, отговори 429, невалидни отговори, прекъсвания на потока,
  `finish_reason=length`, успешни резултати с нулев изход, EWMA за латентност/TTFT).
  Статус 200 НЕ се третира като семантично качество.
- **Семантично** — действителната стойност на генерирания изход. ВИНАГИ се създава
  само от оценител чрез `setSemanticQuality()`. Стойността му е `null`, докато
  оценител не я предостави, и никога не се включва в оперативната оценка.

Състояние за всяка двойка (доставчик, модел) (EWMA + ограничени броячи):

- `successEwma` — EWMA (α=0.2) на успешния резултат.
- `latencyEwma` / `ttftEwma` — EWMA на латентността (α=0.1).
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`.
- `recencyMs` — колко скоро е бил наблюдаван моделът за последно.

### Отчитане на увереността/броя извадки

`confidence = clamp01(samples / 50)`, а оценката, връщана към механизма за
оценяване, се смесва към неутралната средна стойност:

```
score = 0.5 + confidence * (operational - 0.5)
```

Последствия (потвърдени чрез тестове):

- Нов доставчик (0 извадки) получава оценка **0.5** — не се санкционира
  несправедливо, но не може да изпревари доставчик с хиляди надеждни наблюдения.
- Доставчик със 7 успешни резултата поради късмет се доближава към 0.5 (никога не
  доминира поради оптимистична инициализация).
- Доставчик с 50+ извадки се доближава до действителната си оперативна оценка.
- Влошаването и възстановяването са постепенни (EWMA), а единичен изолиран неуспех
  не проваля здрав доставчик.

`ProviderQuality` предоставя `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }`.

Това се подава към механизма за оценяване на auto-combo като фактора за оценяване
`quality`:

- `ScoringFactors.quality` / `ScoringWeights.quality` в
  `open-sse/services/autoCombo/scoring.ts`.
- `DEFAULT_WEIGHTS`: `health` 0.1905 → 0.1605, `quality` 0.03. Сумата остава 1.0.
- `buildAutoCandidates` попълва `candidate.quality` от проследяващия компонент;
  кандидатите без данни по подразбиране получават неутрална стойност **0.5**
  (нов кандидат не е нито облагодетелстван, нито санкциониран).

Затвореният цикъл:

```
RoutingEvent → QualityTracker → getQualityScore → фактор за качество на auto-combo
      ↑                                                    │
      └────── резултат от заявката (handleChatCore) ←──────┘
```

### Твърдо изключване спрямо мека санкция

Сигналът за качество е само **мека адаптивна настройка на предпочитанията**.
Твърдото изключване остава отговорност на съществуващия стек за устойчивост:
прекъсвач на веригата в състояние OPEN, изчерпана квота, неуспешно удостоверяване,
блокиране на модела — нито едно от тях не се влияе от оценката за качество.
Доставчик, чиято оценка за качество временно спадне, получава по-нисък приоритет,
но никога не се деактивира твърдо.

## 3b. Канонично измерване на времето на потока (TTFT / ITL)

Файлове: `open-sse/utils/streamTiming.ts`

`createStreamTiming()` е единствената точка за инструментално измерване на поточния път,
интегрирана в `createSSEStream` (open-sse/utils/stream.ts):

- `markByte()` — получен е първият фрагмент от източника.
- `markForward()` — първият фрагмент е препратен към клиента (използва се за TTFT).
- `markInterrupted()` — изтичане на времето, прекъсване или грешка на потока преди нормалното му завършване.
- `ttft()` = латентност до първия препратен SSE фрагмент. **Това НЕ е TTFT на ниво токен** —
  един SSE фрагмент може да съдържа нула, един или много токени. Това е прецизно документирано.
- `avgItlMs()` = среден интервал между фрагментите (приблизителен показател за ITL, базиран на латентността между фрагментите).

TTFT/ITL/състоянието на прекъсване постъпват в `RoutingEvent` (`ttftMs`, `itlMs`) и се
експортират като атрибути на GenAI/OmniRoute интервалите от OTel приемника.

## 4. Наблюдаемост с OpenTelemetry / GenAI

Файлове: `open-sse/services/routing/otel.ts`

- OTLP/HTTP JSON експортер без зависимости (използва глобалния `fetch`, без
  `@opentelemetry/*` SDK).
- Интервалите следват семантичните конвенции на GenAI (`gen_ai.provider.name`,
  `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`,
  `gen_ai.completion.finish_reason`, `gen_ai.system`), както и атрибутите за
  маршрутизиране на OmniRoute (резултат, състояние, ttft, повторни опити, резервен вариант).
- `record()` само добавя в ограничен буфер (O(1)); фонов таймер
  изпраща асинхронно чрез `POST {endpoint}/v1/traces`. При претоварване
  най-старите събития се премахват (брояч `dropped`) — без прилагане на обратно налягане
  върху равнината за данни.
- **Деактивирано, освен ако не е конфигурирано.** Трябва да бъде зададена
  `OMNIROUTE_OTEL_ENDPOINT` (или `OTEL_EXPORTER_OTLP_ENDPOINT`); в противен случай
  приемникът не се регистрира и не се изпълнява никакъв OTel код.

## 5. Обяснимост

- `GET /v1/explain/routing` връща последните `RoutingEvent` събития (реалните
  решения, първо най-новите) и моментното състояние на качеството за всяка двойка доставчик/модел.
- Удостоверяването следва това на `/v1/combos` (Bearer API ключ или сесия на таблото за управление; анонимен достъп при
  локални внедрявания за един потребител с `REQUIRE_API_KEY=false`).
- Следите на ниво комбинация за отделните извиквания остават достъпни чрез съществуващия
  `decisionTrace.ts` (заглавка `X-OmniRoute-Combo-Trace`).
- Безопасност: събитията съдържат само метаданни за маршрутизирането, никога подкани, тела или идентификационни данни.

## 6. Интеграция на равнината за оценяване (готовност за Future AGI)

OmniRoute разглежда Future AGI (или всеки друг оценител) като **потенциален
бекенд за интелигентност/оценяване, а не като зависимост**. Точките за интеграция са:

- `RoutingEventSink` може асинхронно да препраща събития към оценител.
- `MemoryRoutingEventStore` и моментното състояние на качеството предоставят на оценителя необработения
  поток от решения.
- Бъдещ `Evaluator` (детерминистичен, локален оценител, HTTP, WASM) би използвал
  събитията/следите и би връщал `QualityScore`, който постъпва в същия
  път `getQualityScore`/фактор за качество.
- Съществуващото маршрутизиране, управлявано от оценки (`open-sse/services/evalRouting.ts`), вече
  пренарежда целите на комбинациите според процентите на успешно преминаване в `eval_runs`, когато е активирано.

Никакво оценяване не се изпълнява синхронно по пътя на заявката, а шлюзът работи
напълно дори при липса на оценител.

## 7. Финален архитектурен преглед

1. **Какво остава в синхронния критичен път?** Маршрутизирането/оценяването, предварителните
   проверки на защитните механизми, търсенето в кеша и едно разклоняване чрез `emitRoutingEvent` (~0.12 µs над
   базовото време за оценяване) към приемници в паметта.
2. **Какво е преместено към асинхронна обработка?** Експортирането към OTel (таймер + fetch),
   съхраняването на `call_logs`/използването, записите в семантичния кеш; качеството се поддържа в паметта
   и е O(1) (не е необходима асинхронност).
3. **Как резултатът от маршрутизирането се превръща в обратна връзка?** `handleChatCore` излъчва
   `RoutingEvent` → `QualityTracker` актуализира състоянието на EWMA → `getQualityScore`
   захранва фактора `quality` на автоматичната комбинация.
4. **Как качеството влияе върху бъдещото маршрутизиране?** Ниският резултат за качество намалява
   претегления резултат на съответния доставчик/модел в `scoreAutoTargets`, така че моделите
   с влошено качество постепенно получават по-нисък приоритет и се възстановяват с подобряването на тяхната EWMA.
5. **Как Future AGI може да се интегрира, без да се превръща в зависимост?** Чрез
   интерфейса `RoutingEventSink` / бъдещ адаптер `Evaluator` — без твърдо кодирана
   зависимост.
6. **Какво се случва, когато оценителят не е достъпен?** Маршрутизирането не се засяга;
   качеството използва неутралната стойност (1.0) за модели без наблюдаван сигнал.
7. **Какво се случва, когато телеметрията не е достъпна?** OTel приемникът просто не се
   регистрира; останалата част от слоя за маршрутизиране работи без промени.
8. **Какво се случва при претоварване?** OTel буферът премахва най-старите събития; хранилищата
   за качество и кръговият буфер са ограничени по замисъл; няма обратно налягане.
9. **Как се възстановява състоянието на доставчика след влошаване?** EWMA повторно се сближава с нормалното състояние с
   натрупването на успешни резултати; периодът на загряване запазва неутралността на студените модели; прекъсвачът на веригата
   се възстановява независимо чрез проби в състояние HALF_OPEN.
10. **Кои предложени функционалности умишлено НЕ са реализирани и защо?**
    - Огледален трафик / експерименти — вече са реализирани
      (`combo/shadowRouting.ts`); не са изграждани повторно.
    - Защитни механизми — вече са реализирани (`src/lib/guardrails/`); не са дублирани.
    - Семантичен кеш — вече е реализиран (`src/lib/semanticCache.ts`); не е
      дублиран.
    - Пълноценна платформа за управление на експерименти, инструменти за набори от данни, платформа за оптимизиране на подкани,
      векторна БД или задължителна външна OTel инфраструктура — извън
      обхвата на олекотена равнина за данни.
    - Rust структура `RoutingEvent` — равнината за данни е на TypeScript; TS типът
      е адаптираният еквивалент.
