Два начина да използвате Cursor зад OmniRoute без IDE сесия:

1. **Доставчик `cursor-api`** (карта „Cursor API“, псевдоним `cua`): доставчик
   с API ключ, който съхранява потребителски API ключ за Cursor (`crsr_…`,
   генериран на `https://cursor.com/dashboard/api`). След това всеки клиент на
   OmniRoute получава достъп до моделите на Cursor чрез `/v1/chat/completions`
   като `cursor-api/<model>` или `cua/<model>`, с обичайните слоеве за квоти,
   резервно превключване и регистриране. IDE доставчикът (`cursor`, OAuth/IDE
   сесия) остава непроменен.
2. **Директно препредаване на Cursor CLI**: насочете Cursor CLI (`agent`) към
   OmniRoute, така че всяко RPC извикване от CLI да се удостоверява с API ключ
   на OmniRoute, да се препраща към Cursor с идентификационните данни на
   `cursor-api` връзка и да се записва на страницата Logs.

## Защо ключът се обменя

`api2.cursor.sh` отхвърля необработен ключ `crsr_…` като Bearer токен (401).
Cursor CLI първо изпраща ключа чрез POST към `/auth/exchange_user_api_key` и
получава сесиен JWT, който изтича след един час; върнатият `refreshToken` съдържа
същата стойност за `exp`, така че опресняването означава повторна обмяна на
ключа.
`open-sse/services/cursorApiKeyAuth.ts` извършва тази обмяна, кешира по един
сесиен токен за всеки ключ, извършва повторна обмяна пет минути преди изтичането
и премахва кеширания токен, когато Cursor отговори с 401. `CursorExecutor` го
извиква непосредствено преди отварянето на потока към услугата нагоре по веригата
за `cursor-api` връзки.

## Доставчикът `cursor-api`

Регистър: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"`, със същите `format`, `baseUrl` и
`models` като `cursor`). Карта в каталога:
`src/shared/constants/providers/apikey/specialty-media.ts`. Карта на
изпълнителите: `open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`).

Табло за управление: Providers → Cursor API → Add API key.

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

След това:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

Бележки:

- Списъкът с модели за `cursor-api` идва от статичния регистър на Cursor (същия
  списък, който IDE доставчикът използва като резервен вариант); не е необходимо
  `cursor-agent` да бъде инсталиран на хоста на OmniRoute.
- `POST /api/providers/{id}/refresh-cursor` е предназначен само за IDE доставчика
  `cursor`; `cursor-api` връзките нямат IDE сесия за подновяване.

## Собствени идентификатори на модели и ниво на усилие

За `cursor` / `cu` и `cursor-api` / `cua` споделеният нормализатор за нивото на
усилие на Claude оставя заявения идентификатор на модела непроменен. Cursor може
да обяви суфикс като `-low` като част от действителен идентификатор на модел, а
не като псевдоним на OmniRoute за ниво на усилие. Изпълнителят на Cursor запазва
точното съвпадение с активния каталог; когато няма съвпадение, съществуващият му
механизъм за определяне на модели управлява резервното преобразуване на суфикса
към параметър.

Това не променя нормализирането на нивото на усилие за директни маршрути към
Claude, съвместими с Claude маршрути или маршрути към Vertex. Наличността
продължава да зависи от каталога и правата на избрания акаунт в Cursor.

## Препращане през Cursor CLI

Маршрут: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`. Префиксът `/api/cursor-cli/` е
регистриран в `src/shared/constants/publicApiRoutes.ts`, тъй като обработчикът
налага собствено удостоверяване:

| Път                                                                                                                        | Удостоверяване, очаквано от CLI | Какво прави OmniRoute                                                                                                                                                                            |
| -------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /auth/exchange_user_api_key`                                                                                         | `Bearer <OmniRoute API key>`    | Валидира ключа, издава HS256 JWT с валидност 1 час (подписан с `JWT_SECRET`) и го връща                                                                                                          |
| всеки друг път (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`             | Проверява издателя, аудиторията и срока на валидност, избира активна връзка `cursor-api`, заменя заглавката Authorization с получения чрез обмен Cursor токен и предава поточно отговора обратно |

CLI декодира `exp` от всеки получен токен, затова подаването на непрозрачен
токен го кара да извършва нов обмен преди почти всяка заявка; издаденият JWT
предотвратява това. Отговор 401 от OmniRoute кара CLI да извърши обмена отново.

### Настройка

1. Създайте OmniRoute API ключ (Табло → API ключове) и връзка `cursor-api`.
2. Укажете на CLI да използва HTTP/1.1 за потока на агента. В
   `~/.cursor/cli-config.json`:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   Без тази настройка CLI отваря сесията на агента през HTTP/2 към отделно
   конфигуриран хост на агента и само RPC извикванията на контролната равнина
   минават през крайната точка.

3. Стартирайте CLI срещу OmniRoute:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

Всяка стъпка се записва в Logs с доставчик `cursor-api`, тип на заявката
`cursor-cli`, път `/api/cursor-cli/<rpc>`, свързана с OmniRoute API ключа и
връзката, която я е обслужила.

### Режими на отказ

| Ситуация                                         | Отговор към CLI                                     |
| ------------------------------------------------ | --------------------------------------------------- |
| Непознат OmniRoute ключ и `REQUIRE_API_KEY=true` | 401 `unauthenticated` при обмена                    |
| `REQUIRE_API_KEY=false`                          | анонимна сесия (отразява поведението на `/v1/*`)    |
| Изтекъл / чужд / подправен JWT на сесията        | 401, CLI извършва обмена отново                     |
| OmniRoute API ключът е отнет след обмена         | 401 при следващото RPC извикване                    |
| Няма активна връзка `cursor-api`                 | 503 `unavailable`                                   |
| Cursor отхвърля ключа на връзката                | 401 `unauthenticated`, кешираната сесия се премахва |
| Услугата нагоре по веригата е недостъпна         | 502 `unavailable` (санитизирано съобщение)          |
| `JWT_SECRET` не е зададена                       | 503 при обмена                                      |
