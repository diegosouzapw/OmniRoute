> **Аудитория:** Инженери, които добавят, поддържат или отстраняват грешки във вградени услуги (9Router, CLIProxyAPI, Mux, Bifrost, open-wa).

Вградените услуги са локално инсталирани помощни процеси, които OmniRoute инсталира, управлява и
предоставя като пълноправни цели за маршрутизиране. За разлика от външните доставчици (които се достъпват през интернет
чрез API ключове), вградените услуги се изпълняват на същата машина като OmniRoute и комуникират през loopback интерфейса.

## 1. Общ преглед

### Защо вградени услуги?

Вградени са шест услуги:

| Услуга          | npm пакет                                   | Порт по подразбиране | Предназначение                                                                                                                                                                                                                 |
| --------------- | ------------------------------------------- | :------------------: | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **9Router**     | `9router`                                   |        20130         | AI маршрутизатор, който OmniRoute може да използва като поддоставчик. Моделите са достъпни като `9router/{sub}/{model}`                                                                                                        |
| **CLIProxyAPI** | Двоичен файл от GitHub издание (`cliproxy`) |         8317         | Локален прокси адаптер за потоците за удостоверяване на Anthropic CLI. Осигурява резервно маршрутизиране при изтичане на OAuth токените                                                                                        |
| **Mux**         | `mux` (без интерфейс `mux server`)          |         8322         | Локален демон за оркестрация на агенти (coder/mux). Управлява се само жизненият му цикъл — не е цел за маршрутизиране (без LLM проксиране).                                                                                    |
| **Bifrost**     | `@maximhq/bifrost`                          |         8080         | Go сървърна система за препредаване през AI шлюз. Когато работи, се избира автоматично от маршрута за препредаване (`/v1/relay/`)                                                                                              |
| **Dario**       | `@askalf/dario`                             |         3456         | Прокси за абонамент за Claude — алтернатива/резервен вариант на CLIProxyAPI за трафик във формата на Claude Code; инжектираният ключ става `DARIO_ADMIN_TOKEN`, ограничаващ достъпа до неговия OAuth контролен слой `/admin/*` |
| **open-wa**     | `@open-wa/wa-automate`                      |         8323         | Автоматизация на WhatsApp Web (Chromium без интерфейс чрез Puppeteer). Управлява се само жизненият му цикъл — не е цел за маршрутизиране.                                                                                      |

И шестте следват един и същ модел на надзор:

- OmniRoute ги инсталира в `DATA_DIR/services/{name}/` (изолирано от собствения `package.json` на OmniRoute)
- OmniRoute ги стартира и наблюдава като дъщерни процеси
- OmniRoute инжектира временен API ключ в средата на дъщерния процес и го сменя без прекъсване на работата (когато е приложимо)
- Всички маршрути за управление (`/api/services/*`) са **LOCAL_ONLY** — достъпни само от loopback интерфейса (строго правило №17)

### Ключови решения (от плана за проектиране)

| Решение                                       | Стойност                                                                             |
| --------------------------------------------- | ------------------------------------------------------------------------------------ |
| Достъп от таблото до собствения UI на 9Router | Обратно прокси на `/dashboard/providers/services/9router/embed/*`                    |
| Механизъм за инсталиране                      | `npm install {package}` чрез `execFile` (без интерполация от shell)                  |
| Режим на използване                           | Доставчикът е регистриран като `9router/{sub}/{model}` в системата за маршрутизиране |
| Управление на API ключове                     | OmniRoute генерира, криптира при съхранение (AES-256-GCM) и инжектира чрез средата   |
| Местоположение в таблото                      | `/dashboard/providers/services` (три раздела)                                        |
| Автоматично стартиране                        | Превключвател за всяка услуга, изключен по подразбиране                              |

## 3. Машина на състоянията на жизнения цикъл

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
            успешна здравна проверка│         срив / SIGTERM     │
                               ┌────▼─────┐  (изход до 5 s)     │
                               │ running  │──── срив ───────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

Състоянията се съхраняват в таблицата `version_manager` на БД (колона `status`) и се отразяват
в състоянието в паметта на `ServiceSupervisor`. Състоянието в паметта е водещо за
работещ процес; състоянието в БД е устойчивият резервен вариант при стартиране.

### Преходи между състоянията

| От              | Събитие                               | Към                    |
| --------------- | ------------------------------------- | ---------------------- |
| `not_installed` | `install()` завършва успешно          | `stopped`              |
| `stopped`       | извикан е `start()`                   | `starting`             |
| `starting`      | здравната проверка връща 200          | `running`              |
| `starting`      | процесът приключва, преди да е готов  | `error`                |
| `running`       | извикан е `stop()`                    | `stopping` → `stopped` |
| `running`       | процесът приключва неочаквано (< 5 s) | `error` (бърз срив)    |
| `running`       | процесът приключва неочаквано (> 5 s) | `error`                |
| `error`         | извикан е `start()`                   | `starting`             |
| всяко           | `stop()` по време на `stopping`       | без действие           |

### Заключване на операциите

`ServiceSupervisor` сериализира операциите по жизнения цикъл чрез асинхронно заключване на операциите
(`withLock()`). Едновременните извиквания на `start()` върху един и същ надзорен обект водят до точно
едно стартиране на процес; вторият извикващ изчаква и получава съществуващото състояние. Това предотвратява
състояния на състезание, когато например автоматичното стартиране и бутон в потребителския интерфейс се задействат едновременно.

## 4. Справочник за API

Всички маршрути под `/api/services/` са **LOCAL_ONLY** (само loopback, строго правило #17).
Заявките, които не са от loopback, получават `403 LOCAL_ONLY` независимо от токена за удостоверяване.

### 4.1 Крайни точки на 9Router (11 маршрута)

#### `POST /api/services/9router/install`

Инсталирайте 9Router от npm. Създава `DATA_DIR/services/9router/` със собствени
`package.json` и `node_modules/`. Не влиза в конфликт със зависимостите на OmniRoute.

**Тяло на заявката** (всички полета са незадължителни):

```json
{ "version": "latest" }
```

| Поле      | Тип      | По подразбиране | Описание                                       |
| --------- | -------- | --------------- | ---------------------------------------------- |
| `version` | `string` | `"latest"`      | npm етикет за версия или semver за инсталиране |

**Отговори:**

| Статус | Описание                                                        |
| ------ | --------------------------------------------------------------- |
| `200`  | `{ ok: true, installedVersion: "x.y.z", path: "..." }`          |
| `400`  | Невалидно тяло на заявката (неуспешна Zod валидация)            |
| `409`  | Вече се извършва инсталиране (заключването е заето)             |
| `500`  | Неуспешна npm инсталация — вижте `message` за разбираема грешка |

**Бележки:** Използва `execFile('npm', [...])` — без обвивка и без интерполация (строго правило #13).
Грешките EACCES се представят като разбираеми съобщения.

---

#### `POST /api/services/9router/start`

Стартирайте 9Router. Регистрира supervisor, ако все още не е регистриран, след което извиква
`supervisor.start()`. Идемпотентно, когато услугата вече работи.

**Тяло на заявката:** няма

**Отговори:**

| Статус | Описание                                                    |
| ------ | ----------------------------------------------------------- |
| `200`  | Обект `ServiceStatus` (вижте схемата по-долу)               |
| `409`  | 9Router не е инсталиран (`status: "not_installed"`)         |
| `503`  | Неуспешно стартиране (грешка в процеса — вижте `lastError`) |

**Схема на ServiceStatus:**


### 4.7 Обратен прокси сървър (вграждане на таблото за управление на 9Router)

Таблото за управление вгражда уеб интерфейса на 9Router в iframe чрез вътрешен обратен
прокси сървър на:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

Този прокси сървър:

- Препраща заявката към `http://127.0.0.1:{port}/{path}` (само през loopback)
- Премахва входящите заглавки `cookie` и `authorization` (без изтичане на сесията на OmniRoute)
- Инжектира `Authorization: Bearer {apiKey}` за удостоверяване в 9Router
- Премахва `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*` от отговора
- Пренаписва HTML отговорите, за да инжектира `<base href>` и да нормализира абсолютните пътища (`/foo` → `/dashboard/.../embed/foo`)

WebSocket надгражданията за вграденото табло за управление се обработват от спомагателен сървър на
специализиран порт (вижте `src/lib/services/embedWsProxy.ts`).

**Сигурност:** Маршрутите на прокси сървъра за вграждане са класифицирани в `LOCAL_ONLY_API_PREFIXES`
и могат да бъдат достъпвани само през loopback. Нападател, който получи JWT чрез
тунел на Cloudflare/Ngrok, не може да използва прокси достъп до вградените услуги.

## 5. Сигурност

### Прилагане на LOCAL_ONLY (твърдо правило #17)

Всички маршрути под `/api/services/` и `/dashboard/providers/services/*/embed/` са
класифицирани като LOCAL_ONLY в `src/server/authz/routeGuard.ts`. Проверката за
loopback адрес се изпълнява безусловно преди всяко разклонение за удостоверяване:

```
заявката пристига
  → isLocalOnlyPath(path)?
      → адрес извън loopback → 403 LOCAL_ONLY (винаги, преди проверката за удостоверяване)
      → loopback            → преминаване към стандартното удостоверяване
```

Това предотвратява възможността изтекъл JWT (напр. чрез тунел) да задейства `npm install`
или стартиране на процес. Вижте `docs/security/ROUTE_GUARD_TIERS.md` за пълната матрица
на нивата.

### Инжектиране на API ключ

9Router и Mux изискват API ключ/bearer token за собствените си HTTP крайни точки.
OmniRoute:

1. Генерира ключ чрез `crypto.randomBytes(32).toString("base64url")` със
   специфичен за услугата префикс (`nr_` за 9Router, `mx_` за Mux).
2. Криптира го при съхранение чрез AES-256-GCM (същият шифър, използван за идентификационните данни на доставчиците).
3. Декриптира го и го инжектира като променлива на средата при стартиране —
   `NINEROUTER_API_KEY` за 9Router, `MUX_SERVER_AUTH_TOKEN` за Mux (никога като CLI
   флаг, така че токенът никога да не се появява в `ps`/списъците с процеси).
4. Никога не връща ключа в некриптиран вид в HTTP отговор.

CLIProxyAPI получава специален ключ за равнината за данни, инжектиран при стартиране
(`needsApiKey: true` — използва се за синхронизиране на модели спрямо адаптера).

### Защита срещу SSRF

Обратният HTTP прокси сървър (`/dashboard/.../embed/[...path]`) е твърдо конфигуриран да препраща
единствено към `http://127.0.0.1:{port}`. Той никога не следва пренасочвания към дестинации,
които не са loopback. Библиотеката `ssrf-req-filter` се използва за отхвърляне на всеки upstream URL,
който се преобразува до адрес извън loopback диапазона.

### Безопасност на shell командите (твърдо правило #13)

`npm install` се извиква чрез `execFile('npm', ['install', pkg, '--prefix', dir])` —
без шаблонни литерали, без shell и без интерполация на външни пътища в низа на командата.
Стойностите по време на изпълнение (портове, API ключове) се предават чрез обекта `env` на дъщерния процес.

### Санитизиране на грешки (твърдо правило #12)

Всички отговори за грешки от `/api/services/*` преминават през `buildErrorBody()` или
`sanitizeErrorMessage()`. Необработените `err.stack` и `err.message` никога не се връщат
дословно на извикващата страна.

## 6. Добавяне на нова вградена услуга

Следвайте тези 8 стъпки. Използвайте съществуващите реализации в `src/lib/services/installers/`
и `src/app/api/services/` като каноничен пример.

### Стъпка 1 — Създайте инсталатора

Създайте `src/lib/services/installers/{name}.ts` по модела на `ninerouter.ts`:

```typescript
export const NAME_PACKAGE = "your-npm-package";
export const NAME_DEFAULT_PORT = 20132; // изберете свободен порт

export async function install(version = "latest"): Promise<InstallResult> { ... }
export async function update(version = "latest"): Promise<InstallResult> { ... }
export async function uninstall(): Promise<void> { ... }
export function resolveSpawnArgs(apiKey: string, port: number): SpawnArgs { ... }
export async function getInstalledVersion(): Promise<string | null> { ... }
export async function getLatestVersion(): Promise<string | null> { ... }
```

Използвайте `runNpm(['install', NAME_PACKAGE, '--prefix', dir])` от `installers/utils.ts`
— никога `execSync` или shell интерполация.

### Стъпка 2 — Регистрирайте в bootstrap

Добавете `ServiceEntry` към масива `SERVICES` в `src/lib/services/bootstrap.ts`:

```typescript
{
  tool: "myservice",
  port: NAME_DEFAULT_PORT,
  healthPath: "/health",
  healthIntervalMs: 5_000,
  stopTimeoutMs: 15_000,
  logsBufferBytes: 5_242_880,
  needsApiKey: true, // false, ако не е необходим API ключ
}
```

Разширете `buildSpawnArgsFactory()`, за да обработва `cfg.tool === "myservice"`.

#### Разширяем договор за плъгини на доставчици (Фаза 1, #7333)

`src/lib/services/providerPlugins/` въвежда договор `ServiceProviderPlugin`, който
обединява полетата `ServiceEntry` от `bootstrap.ts` на даден backend и полетата на шаблона
на манифеста от `serviceBackends.ts` в един обект, вместо структурата на същия backend да бъде
описвана поотделно в два несвързани файла. Към момента на написване **само `9router` е
мигриран** — `bootstrap.ts` извлича своя запис в `SERVICES[]` от
`getServiceProviderPlugin("9router")` (`src/lib/services/providerPlugins/registry.ts`),
като хвърля грешка при стартиране, ако плъгинът липсва. `cliproxy`, `mux` и `bifrost`
остават с предишните inline литерали в `SERVICES[]` без промени.

`open-sse/config/providerPluginManifest.ts` също получи допълваща помощна функция
`createServiceBackendManifestEntry(pluginId, template)`, която създава правилно структуриран
`ProviderPluginManifestEntry` от запис в `SERVICE_BACKEND_MANIFEST_TEMPLATE` — тя
**все още не е свързана** с никой активен път за заявки (нито с `generateProviderPluginManifestFromRegistry()`,
нито с `/v1/providers/[provider]/models`); това остава за последваща работа, след като договорът
бъде доказан с втори backend.

## 7. Отстраняване на неизправности

### Услугата не се стартира

**Симптоми:** Бутонът за стартиране връща 503, състоянието остава `"error"` или `"starting"`.

**Списък за проверка:**

1. Проверете `GET /api/services/{name}/logs` (или панела Logs в таблото за управление). Потърсете
   редове като `Error: ENOENT`, `address already in use` или `Cannot find module`.
2. Проверете дали `npm` е в PATH: изпълнете `which npm` от същия потребителски акаунт, под който работи OmniRoute.
3. Проверете дали услугата е инсталирана: вижте `GET /api/services/{name}/status` за
   `installedVersion`. Ако стойността е `null`, първо изпълнете инсталирането.
4. Проверете дали `DATA_DIR/services/{name}/node_modules/` съществува и не е празна.
5. Проверете полето `lastError` в отговора за състоянието за филтрираната причина за прекратяване.

---

### Студеното стартиране е бавно (> 10 s до достигане на `running`)

**Симптоми:** Състоянието остава `"starting"` дълго време, преди да премине към `"running"` или `"error"`.

**Обяснение:** Студеното стартиране на 9Router включва импортиране на големи дървета от зависимости (DNS,
тунелни и MITM модули). Интервалът по подразбиране за проверка на изправността е 2 s с 3 опита, преди
надзорният процес да отчете изтичане на времето за изчакване (но продължава проверките).

**Решение:** `healthIntervalMs` и времето за изчакване на `waitForHealthy`
(`healthIntervalMs * 3`) могат да бъдат конфигурирани в `bootstrap.ts`. За услуги с по-дълго
време за стартиране увеличете `healthIntervalMs` на 5000 и `stopTimeoutMs` на 30 000.

---

### Конфликт на портове (`EADDRINUSE`)

**Симптоми:** Дневниците показват `address already in use :::20130`.

**Причини:**

- Друг процес вече използва порт 20130.
- Предишен процес на 9Router не е бил напълно спрян (зомби PID).

**Решение:**

1. Променете порта по подразбиране чрез променливата на средата `NINEROUTER_PORT` във файла `.env`.
2. Намерете и прекратете конфликтния процес: `lsof -ti :20130 | xargs kill -9`.
3. Портът може да се конфигурира за всяка услуга в `bootstrap.ts` чрез полето `port`.

**Забележка:** 9Router по подразбиране използва порт 20130, специално за да избегне конфликт с
порта по подразбиране на OmniRoute — 20128.

---

### Отказан достъп (EACCES) при инсталиране

**Симптоми:** Инсталирането връща 500, а дневниците показват `EACCES` или `permission denied`.

**Причини:**

- `DATA_DIR` или родителската ѝ директория не позволява запис от процеса на OmniRoute.
- Изпълнение в Docker без root права и без достъп за запис до свързания том.

**Решение:**

1. Проверете `DATA_DIR` (по подразбиране: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. Уверете се, че потребителят на процеса OmniRoute притежава директорията: `chown -R $USER ~/.omniroute/`
3. В Docker се уверете, че монтираният том има правилните разрешения за потребителя в контейнера.

---

### Актуализирането е неуспешно (изтичане на времето за изчакване на `npm install` или мрежова грешка)

**Симптоми:** Актуализирането връща 500 с `InstallError`, а дневниците показват изтичане на времето за изчакване на мрежата.

**Списък за проверка:**

1. Потвърдете, че регистърът на npm е достъпен: `npm ping`.
2. Проверете за корпоративен прокси сървър: `npm config get proxy`, `npm config get https-proxy`.
3. Опитайте да инсталирате ръчно: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`.
4. Ако системата е в изолирана мрежа, изтеглете предварително tarball архива и използвайте `npm install /path/to/tarball.tgz`.

---

### Услугата показва състояние `"error"` веднага след стартиране (бърз срив)

**Симптоми:** Състоянието преминава от `"starting"` към `"error"` за по-малко от 5 секунди.
`lastError` показва `"Fast crash (exited with code 1)"`.

**Списък за проверка:**

1. Прочетете пълния край на дневника: `GET /api/services/{name}/logs?tail=500`.
2. Честа причина: липсващи променливи на средата, очаквани от услугата.
3. За 9Router: проверете дали `NINEROUTER_DISABLE_MITM=true` и
   `NINEROUTER_DISABLE_TUNNEL=true` присъстват в средата, предадена при стартиране на процеса (вижте
   `installers/ninerouter.ts` `resolveSpawnArgs`).

## 8. ЧЗВ

**В: Мога ли да направя крайните точки на вградените услуги достъпни за клиенти извън loopback интерфейса?**

Не. Нивото LOCAL_ONLY е умишлено (твърдо правило №17). Маршрутите, които могат да извикват
`npm install` или да стартират процеси на `node`, не трябва да бъдат достъпни за трафик
извън loopback интерфейса, тъй като изтекъл JWT чрез тунел (Cloudflare, Ngrok, Tailscale)
иначе би позволил произволно стартиране на процеси. Няма изключение за отказ от това
правило за `/api/services/` — за разлика от `/api/mcp/`, той е изключен от списъка
за заобикаляне чрез обхвата manage. Вижте `docs/security/ROUTE_GUARD_TIERS.md`.

---

**В: Ще бъдат ли 9Router и CLIProxyAPI налични в продукционни/облачни внедрявания?**

Да. И двете услуги следват същия модел с приоритет на локалната среда като самия
OmniRoute. Те работят на една и съща машина и комуникират чрез loopback интерфейса.
Тук „продукционна среда“ означава VPS или локалния сървър, където е внедрен OmniRoute,
а не отдалечен облачен доставчик.

---

**В: Как да отстранявам проблеми със супервизора?**

1. Следете SSE потока с журнали: `curl -N http://localhost:20128/api/services/9router/logs`.
2. Проверете структурираните журнали в pino изхода на OmniRoute, филтрирани по
   пространството от имена `service:supervisor`.
3. Прегледайте реда в БД: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`.
4. Използвайте `GET /api/services/9router/status`, за да видите в една заявка текущото
   състояние в реално време, PID, изправността и `lastError`.

---

**В: Супервизорът показва `health: "degraded"` или `health: "unknown"`, но състоянието е `"running"`. Това проблем ли е?**

`"degraded"` означава, че проверката за изправност е върнала отговор, различен от 200.
`"unknown"` означава, че все още не е завършила проверка (състезание с първото
анкетиране). И двете състояния са временни по време на стартиране. Ако изправността
остане `"degraded"` за повече от `healthIntervalMs * 3` ms след `"running"`, вградената
услуга работи, но нейният HTTP API не отговаря. Проверете дали портът в отговора за
състоянието е правилен и дали услугата действително слуша на този порт.

---

**В: Мога ли да променя API ключа на 9Router без пълно рестартиране?**

Не. API ключът се предава на 9Router чрез променлива на средата при стартиране на
процеса. Променливите на средата не могат да бъдат променяни в работещ процес.
`POST .../rotate-key` автоматично спира и рестартира услугата, за да приложи новия
ключ. Ротацията на ключа влиза в сила в рамките на `stopTimeoutMs` на услугата
(по подразбиране 15 s) плюс времето за нейното стартиране.

---

**В: Какво е ограничението на пръстеновидния буфер и какво се случва, когато се запълни?**

Всяка услуга има собствен пръстеновиден буфер от 5 MB. Когато буферът се запълни,
най-старите редове от журнала се премахват, за да се освободи място за новите.
SSE събитието `snapshot` връща най-скорошните редове в рамките на ограничението
`tail`. Журналите не се съхраняват на диска, освен ако `logsBufferPath` не е зададен
в реда на БД.
