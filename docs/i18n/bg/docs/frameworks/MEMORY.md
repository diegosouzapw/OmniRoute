> **Източник на истината:** `src/lib/memory/` и `src/app/api/memory/`
> **Последна актуализация:** 2026-06-28 — v3.8.40 (изключена по подразбиране + наваксващо int8 квантуване)

OmniRoute предоставя постоянна памет за разговори, обвързана с API ключ (и
по желание с идентификатор на сесия). Спомените се извличат автоматично от отговорите на LLM
чрез леко съпоставяне с шаблони посредством регулярни изрази и се вмъкват обратно в следващите
заявки като водещо системно съобщение (или като първо потребителско съобщение за доставчици, които
отхвърлят системната роля).

> **Паметта е ИЗКЛЮЧЕНА по подразбиране (v3.8.30+).** `DEFAULT_MEMORY_SETTINGS.enabled`
> вече е `false` (`src/lib/memory/settings.ts`). Активирането на паметта вмъква до
> `maxTokens` (~2k) извлечен контекст във **всяка** заявка за чат, който
> се таксува — изненадващ разход за нови инсталации и за клиенти, които управляват
> собствения си контекст. Включете я изрично от **Настройки → Памет** (
> `MemorySkillsTab` показва предупреждение за разхода на токени, когато паметта е активирана).
> Клиент може да изключи паметта за отделна заявка чрез заглавката
> `x-omniroute-no-memory` (`true`/`1`/`yes`) — вижте таблицата със заглавки на заявките в
> [API_REFERENCE.md](../reference/API_REFERENCE.md). Заявка без памет задава
> `memoryOwnerId = null`, което деактивира **както** паметта, **така и** вмъкването на умения за
> тази заявка (`open-sse/handlers/chatCore/headers.ts::isNoMemoryRequested`).

Паметта е **обхваната по API ключ**, а не по потребител — всяка заявка, удостоверена
със същия API ключ, споделя един и същ набор от памет, с възможност за допълнително
ограничаване на обхвата чрез `sessionId`.

## Архитектура

```
Клиент → /v1/chat/completions (apiKeyInfo е разрешен по-рано в потока)
  → handleChatCore() [open-sse/handlers/chatCore.ts]
    → resolveMemoryOwnerId(apiKeyInfo)        # извлича идентификатора
    → getMemorySettings()                     # кеширани настройки
    → shouldInjectMemory(body, {enabled})     # проверка
    → retrieveMemories(apiKeyId, config)      # SQL + FTS5 + незадължителен вектор
    → injectMemory(body, memories, provider)  # системно или потребителско съобщение
  → извикване на доставчика нагоре по веригата
  → при отговор: extractFacts(text, apiKeyId, sessionId)  # неблокиращо
    → setImmediate → createMemory(fact) за всяко съвпадение
                   → embed(content) + upsertVector(id, vec)
```

Местата за извикване на вмъкването и извличането са свързани в
`open-sse/handlers/chatCore.ts` (потърсете `retrieveMemories`, `injectMemory`
и `extractFacts`).

## Архитектура на двигателя (3-степенно определяне)

Memory Engine определя пътя за извличане по време на изпълнение въз основа на наличната
инфраструктура и настройките. Съществуват три нива, прилагани по ред на приоритет:

```
  ┌─────────────────────────────────────────────────────────────┐
  │  НИВО 0 — Ключови думи (FTS5)                               │
  │  Наличност според проверка: FTS5, когато компилацията на     │
  │  SQLite го поддържа (better-sqlite3 / node:sqlite /          │
  │  bun:sqlite); недостъпно при компилации без FTS5 (напр.      │
  │  sql.js/WASM — "no such module: fts5"). Използва се, когато  │
  │  strategy = "exact", или като резервен вариант; полето       │
  │  keyword в engine-status отразява резултата от проверката.   │
  └──────────────────────────────────┬──────────────────────────┘
                                     │ strategy = semantic|hybrid?
                                     ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  НИВО 1 — Вграден вектор (sqlite-vec)                        │
  │  sqlite-vec v0.1.9 се зарежда чрез db.loadExtension().       │
  │  KNN търсене с груба сила във Float32 вектори. Активно при:   │
  │   • успешно sqlite-vec loadExtension                         │
  │   • наличен източник на вграждания (remote | static |        │
  │     transformers), който може да създаде Float32Array        │
  │   • съществуваща таблица vec_memories (създава се при        │
  │     първото ready())                                         │
  └──────────────────────────────────┬──────────────────────────┘
                                     │ qdrant.enabled?
                                     ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  НИВО 2 — Qdrant (външна векторна база данни по избор)       │
  │  Когато е активирано, заменя sqlite-vec за semantic/hybrid.  │
  │  Изисква работещ екземпляр на Qdrant + конфигурирани         │
  │  хост/порт.                                                  │
  └─────────────────────────────────────────────────────────────┘
```

Понижаването на нивото е автоматично и прозрачно:

- Ако sqlite-vec не успее да се зареди, ниво 1 е недостъпно → преминава към ниво 0.
- Ако източникът на вграждания върне грешка, ниво 1 преминава към ниво 0.
- Ако Qdrant не работи нормално, ниво 2 преминава към ниво 1 (или ниво 0, ако ниво 1
  също е недостъпно).

## Източници за вграждане

Слоят за вграждане (`src/lib/memory/embedding/`) определя кой източник да използва
въз основа на `MemorySettingsExtended.embeddingSource`:

| Източник       | Описание                                                                                | Необходим ключ | Студен старт     |
| -------------- | --------------------------------------------------------------------------------------- | -------------- | ---------------- |
| `remote`       | Използва API за вграждане на конфигуриран доставчик (OpenAI, Cohere и др.)              | Да             | Няма             |
| `static`       | Локално вграждане чрез таблица за търсене с `potion-base-8M` (WordPiece + mean pooling) | Не             | ~200ms           |
| `transformers` | Локално ONNX извеждане чрез `@huggingface/transformers` v4, `all-MiniLM-L6-v2`          | Не             | ~3s + ~400MB RAM |
| `auto`         | Определяне по време на изпълнение: remote (ако има ключ) → static → transformers → null | Зависи         | Зависи           |

**Ред на определяне за `auto`:**

1. Намира първия доставчик в `listEmbeddingProviders()` с `hasKey === true` → `remote`.
2. Ако `settings.staticEnabled === true` → `static`.
3. Ако `settings.transformersEnabled === true` → `transformers`.
4. В противен случай → `null` (преминава към търсене по ключови думи с FTS5).

Кешът за вграждания (`src/lib/memory/embedding/cache.ts`) използва намираща се в паметта
LRU карта с ключ `${source}:${model}:${dim}:${sha256(text)}`, ограничена до
`MEMORY_EMBEDDING_CACHE_MAX` записа (по подразбиране 1000) с TTL от
`MEMORY_EMBEDDING_CACHE_TTL_MS` (по подразбиране 5 минути). Споделя се между всички извикващи
за жизнения цикъл на процеса.

## Хибриден RRF (k=60)

Когато `strategy = "hybrid"` и векторното хранилище е налично, извличането използва
Reciprocal Rank Fusion за обединяване на резултатите от FTS5 и векторното търсене:

```
RRF(d) = Σ  1 / (k + rank_i(d))      където k = 60 (конфигурируемо чрез MEMORY_RRF_K)
          i
```

По-конкретно:

1. Изпълнява FTS5 търсене → класиран списък `R_fts` (позиции 1..N).
2. Изпълнява KNN векторно търсене → класиран списък `R_vec` (позиции 1..M).
3. За всеки уникален `memoryId`:  
   `rrf_score = 1/(60 + fts_rank)` + `1/(60 + vec_rank)` (0, ако не присъства в списъка).
4. Сортира по `rrf_score` в низходящ ред и прилага обхождане според бюджета от токени.

Известно е, че RRF е ефективен, без да се налага нормализиране на оценките между
разнородни системи за извличане. Стойността по подразбиране `k=60` идва от оригиналната
статия на Cormack и др. и работи добре за малки масиви (<10k спомена).

## Попълване със задна дата (отложено + преиндексиране)

Когато моделът за вграждане се промени (установено чрез `embedding_signature`),
векторното хранилище се изгражда наново и всички съществуващи спомени се маркират с
`needs_reindex = 1` в таблицата `memories`.

**Отложено попълване**: При следващото извличане всеки спомен, за който липсва векторен запис,
се вгражда и вмъква във `vec_memories`, преди да бъде изпълнено търсенето. Това
разпределя разходите за попълване между реалните заявки, без да блокира стартирането.

**Изрично преиндексиране**: Разделът Engine в `/dashboard/memory` предоставя бутон
„Преиндексиране сега“, който извиква `POST /api/memory/reindex`. Обработчикът извиква
`runReindexBatch()` от `src/lib/memory/reindex.ts`, който обработва до
`limit` чакащи записа на заявка. Напредъкът може да се проверява периодично чрез
`GET /api/memory/engine-status` (`vectorStore.needsReindex`).

Таблицата `memory_vec_meta` (миграция `083_memory_vec.sql`) съхранява:

- `active_dim` — текущ размер на вектора (null = все още не е калибриран).
- `embedding_signature` — `${source}:${model}:${dim}`, използван за откриване на промени.
- `last_reset_at` — времеви маркер на последното пълно нулиране.
- `vec_loaded` — флаг 0/1, указващ дали sqlite-vec е зареден успешно.

## Разширение на настройките

В `MemorySettingsExtended` в `src/shared/schemas/memory.ts` са налични девет полета за вграждания и вектори, които се съхраняват чрез `src/lib/db/settings.ts`:

| Поле                     | Тип                                                | По подразбиране | Описание                                                             |
| ------------------------ | -------------------------------------------------- | --------------- | -------------------------------------------------------------------- |
| `embeddingSource`        | `"remote" \| "static" \| "transformers" \| "auto"` | `"auto"`        | Кой източник на вграждания да се използва                            |
| `embeddingProviderModel` | `string \| null`                                   | `null`          | Доставчик/модел във формат `provider/model`                          |
| `customBaseUrl`          | `string \| null`                                   | `null`          | Базов URL адрес на OpenAI-съвместима крайна точка само за паметта    |
| `customModelId`          | `string \| null`                                   | `null`          | Идентификатор на модела, изпращан към персонализираната крайна точка |
| `transformersEnabled`    | `boolean`                                          | `false`         | Изрично включване на Transformers.js (MiniLM, ~400MB)                |
| `staticEnabled`          | `boolean`                                          | `false`         | Изрично включване на локалния статичен модел potion-base-8M          |
| `rerankEnabled`          | `boolean`                                          | `false`         | Активиране на стъпката за преподреждане (добавя +200-500ms/заявка)   |
| `rerankProviderModel`    | `string \| null`                                   | `null`          | Доставчик/модел за преподреждане във формат `provider/model`         |

`rerankProviderModel` се разрешава от `POST /v1/rerank` (извиквано през loopback), така че приема всичко, което приема този маршрут: подбран облачен модел за преподреждане (`cohere/rerank-v3.5`, `jina-ai/jina-reranker-v3.5`, …) или възел на OpenAI-съвместим доставчик като `<node-prefix>/<model>` (напр. `skilled-mini/bge-reranker-v2-m3` за TEI/Infinity сървър). Loopback възлите винаги са допустими; възел на друг хост (LAN, Tailscale) допълнително изисква флага за функционалност `RERANK_REMOTE_PROVIDER_NODES` и трябва да премине политиката за изходящи URL адреси на доставчика — вижте [Флагове за функционалност](../reference/FEATURE_FLAGS.md). Селекторът в таблото за управление показва подбрани доставчици и локални възли; всеки валиден низ `provider/model` може да бъде зададен директно чрез `PUT /api/settings/memory`.
| `vectorStore` | `"sqlite-vec" \| "qdrant" \| "auto"` | `"auto"` | Коя векторна бекенд система да се използва |

Те са достъпни чрез `GET /PUT /api/settings/memory` (схема `MemorySettingsExtendedSchema`).

За източника `remote` Memory приема също незадължителните настройки `customBaseUrl` и
`customModelId`. Заедно те избират OpenAI-съвместима крайна точка `/embeddings`
и модел, без да променят глобалния регистър за вграждания. Крайната точка се
нормализира преди употреба и се проверява от политиката за изходящи URL адреси на доставчика: изисква се
HTTP(S), вградените идентификационни данни и низовете на заявките се отхвърлят, а адресите
за облачни метаданни остават блокирани. Празните стойности запазват избрания доставчик от регистъра. Грешките,
връщани към таблото за управление, се пречистват, а идентификационните данни за крайната точка никога не се записват в журналите.

## Слоеве за съхранение

### Основен: SQLite (таблица `memories`)

Създадена чрез миграцията `015_create_memories.sql`:

| Колона                      | Тип                | Бележки                                                                     |
| --------------------------- | ------------------ | --------------------------------------------------------------------------- |
| `id`                        | `TEXT PRIMARY KEY` | UUID, генериран чрез `crypto.randomUUID()`                                  |
| `api_key_id`                | `TEXT NOT NULL`    | Собственикът — API ключ                                                     |
| `session_id`                | `TEXT`             | Незадължителен обхват за отделен разговор                                   |
| `type`                      | `TEXT NOT NULL`    | Една от стойностите `factual`, `episodic`, `procedural`, `semantic`         |
| `key`                       | `TEXT`             | Стабилен ключ за upsert, напр. `preference:i_prefer_python`                 |
| `content`                   | `TEXT NOT NULL`    | Действителният текст на факта                                               |
| `metadata`                  | `TEXT`             | JSON блок (категория, extractedAt, източник, ...)                           |
| `created_at` / `updated_at` | `TEXT`             | Низове във формат ISO 8601                                                  |
| `expires_at`                | `TEXT`             | Незадължителен срок на валидност; `NULL` означава постоянен                 |
| `memory_id`                 | `INTEGER UNIQUE`   | Добавена от `023_fix_memory_fts_uuid.sql` за свързване на UUID ↔ FTS5 rowid |

Индекси: `api_key_id`, `session_id`, `type`, `expires_at`, както и уникалният индекс `memory_id`.

**Семантика на upsert**: `createMemory()` търси съществуващ ред със същата двойка `(api_key_id, key)` и при намиране го актуализира на място (обединявайки `metadata` чрез плитко разгръщане). Това предотвратява неограниченото нарастване на таблицата при повтарящи се твърдения за предпочитания.

### Пълнотекстово търсене (виртуална таблица `memory_fts`)

`022_add_memory_fts5.sql` създава виртуална FTS5 таблица върху `content` и `key`. `023_fix_memory_fts_uuid.sql` отстранява реален проблем, при който първичният UUID ключ не се свързваше с целочисления rowid на FTS5 — миграцията добавя колоната `memory_id`, създава отново FTS таблицата и свързва тригери (`memory_fts_ai`, `memory_fts_ad`, `memory_fts_au`), които поддържат FTS синхронизиран при INSERT, DELETE и UPDATE.

Използва се от `retrieval.ts` за стратегиите `semantic` и `hybrid` (вижте по-долу). Кодът за извличане прави защитна проверка с `hasTable("memory_fts")` и преминава към хронологичен ред, ако FTS таблицата липсва или FTS заявката предизвика грешка.

### Незадължителен: Qdrant (векторно хранилище от ниво 2)

`src/lib/memory/qdrant.ts` реализира незадължителна интеграция с Qdrant като векторно хранилище от ниво 2. Извличането се насочва към Qdrant само когато селекторът на механизма `memoryVectorStore === "qdrant"` — стойността по подразбиране `"auto"` (както и `"sqlite-vec"`) **никога** не избира Qdrant. Превключвателят в раздела Engine задава **едновременно** `qdrantEnabled` и `memoryVectorStore`: включването прави Qdrant основно хранилище, а изключването възстановява `"auto"` (#5597 — преди тази корекция включването не оказваше ефект, защото нищо не записваше селектора на механизма). Ако Qdrant е недостъпен или не върне нищо, извличането преминава резервно към sqlite-vec → FTS5.

- `upsertSemanticMemoryPoint()` — вгражда `key + content` чрез конфигурирания
  модел за вграждане, гарантира, че колекцията съществува (при първа употреба
  създава вектори с косинусно разстояние), и добавя или актуализира точка с полезен товар `{memoryId,
apiKeyId, sessionId, key, content, metadata, createdAtUnix, expiresAtUnix}`.
- `searchSemanticMemory(query, topK, scope)` — вгражда заявката и търси в
  колекцията, филтрирана по `kind = "omniroute_memory"` и по избор по
  `apiKeyId` / `sessionId`. Ограничава `topK` до `[1, 20]`.
- `deleteSemanticMemoryPoint(id)` — изтрива единична точка. Извиква се от
  `deleteMemory()`, след като редът в SQLite бъде премахнат (D15).
- `cleanupSemanticMemoryPoints({retentionDays})` — групово изтрива точки, чието
  `expiresAtUnix` е в миналото или чието `createdAtUnix` е по-старо от прага
  за съхранение. Първо ги преброява, за да може таблото да показва действителните стойности.
- `checkQdrantHealth()` — проверка на състоянието чрез `GET /readyz` със закъснение.

Потребителският интерфейс за настройки предоставя конфигурация на Qdrant, проверка на състоянието, тест на семантичното търсене
и почистване в раздела **Машина** на `/dashboard/memory`. Съответните
маршрути в `src/app/api/settings/qdrant/` са напълно свързани от v3.8.6:

| Маршрут                                 | Метод         | Описание                                         |
| --------------------------------------- | ------------- | ------------------------------------------------ |
| `/api/settings/qdrant`                  | `GET` / `PUT` | Прочитане/актуализиране на настройките на Qdrant |
| `/api/settings/qdrant/health`           | `GET`         | Проверка на достъпността + закъснение            |
| `/api/settings/qdrant/search`           | `POST`        | Тест на семантичното търсене                     |
| `/api/settings/qdrant/cleanup`          | `POST`        | Премахване на изтекли/стари точки                |
| `/api/settings/qdrant/embedding-models` | `GET`         | Списък с наличните модели за вграждане           |

**Бележки за поведението (какво да очаквате):**

- **Избор на машина** — активирането на Qdrant в раздела Машина го прави основното
  хранилище (задава `memoryVectorStore="qdrant"`); деактивирането възстановява `"auto"` (#5597).
- **Без попълване със задна дата** — в него се записват само памети, създадени/актуализирани **след** активирането на Qdrant
  (двойно записване без изчакване на резултата). Съществуващите отпреди памети в SQLite **не**
  се мигрират; „Преиндексиране сега“ възстановява само индекса на sqlite-vec, но не и Qdrant.
- **Размерността на векторите се открива автоматично** от действителното вграждане при първата употреба — няма
  поле за размерност, което да се попълва. Промяната на модела за вграждане след създаването на колекцията
  **не** се обработва автоматично: съществуващата колекция остава непроменена, а записите/търсенията
  с несъответстваща размерност се провалят и преминават резервно към sqlite-vec. Създайте колекцията отново
  (с ново име или като я изтриете в Qdrant), за да смените модела за вграждане.
- **Метрика за разстояние** — винаги **косинусна** (твърдо зададена при създаването на колекцията; не
  подлежи на конфигуриране).
- **Удостоверяване** — само чрез API ключ (изпращан в заглавката `api-key`; незадължителен за неудостоверен
  локален Docker). JWT/RBAC не се използват.
- **Конфигурационни полета** — потребителският интерфейс предоставя `host`, `port`, `collection`, `embeddingModel`,
  `apiKey`. `vectorSize` / `hnswEfConstruct` са достъпни само чрез средата/БД, а `vectorSize` не
  се използва при създаването на колекцията (размерността се извлича от вграждането).

### Квантуване на вектори (int8 — по избор, и за двата бекенда)

И двата векторни бекенда поддържат **квантуване до int8 по избор**, за да намалят паметта,
заемана от съхраняваните вектори (~4× по-малко от Float32), с цената на малък спад в пълнотата на резултатите.
По подразбиране то е **изключено** и за двата — векторите остават с пълна точност, освен ако не бъде
изрично активирано.

| Бекенд     | Настройка                         | Тип                            | По подразбиране | Откъде се прочита                                           |
| ---------- | --------------------------------- | ------------------------------ | --------------- | ----------------------------------------------------------- |
| Qdrant     | `qdrantQuantization` (ключ в БД)  | `"none" \| "int8" \| "binary"` | `"none"`        | `src/lib/memory/qdrant.ts::normalizeQdrantConfig()`         |
| sqlite-vec | `MEMORY_VEC_QUANTIZATION` (среда) | `"none" \| "int8"`             | `"none"`        | `src/lib/memory/vectorStore.ts::requestedVecQuantization()` |

- **Qdrant** се конфигурира за всяка инстанция чрез ключа за настройка `qdrantQuantization`
  (предоставен като полето `quantization` в `PUT /api/settings/qdrant`). Когато е
  `"int8"`, `buildQuantizationConfig()` заявява скаларно квантуване
  (`always_ram`, квантил `0.99`), а търсенията активират `rescore: true`, така че
  векторите с пълна точност да прецизират набора от кандидати в int8.
- Квантуването на **sqlite-vec** е **само чрез средата** (не е настройка в БД): задайте
  `MEMORY_VEC_QUANTIZATION=int8`, за да съхранявате локалните вектори като колона `int8[dim]`
  чрез `vec_quantize_int8(?, 'unit')`. Избраният режим се включва в
  `embedding_signature` (суфикс `:int8`), така че смяната на режима задейства пълно
  преиндексиране на таблицата `vec_memories` — по същия път за отложено попълване,
  който се използва при промяна на модела за вграждане.

## Типове памет

`MemoryType` (`src/lib/memory/types.ts`):

| Тип          | Използва се за                                                                            |
| ------------ | ----------------------------------------------------------------------------------------- |
| `factual`    | Предпочитания, устойчиви факти за потребителя, поведенчески модели                        |
| `episodic`   | Решения, свързани с конкретен момент („Избрах Postgres“)                                  |
| `procedural` | Памет за работни процеси / инструкции (запазена; понастоящем няма автоматичен екстрактор) |
| `semantic`   | Запазена за записи във векторното хранилище                                               |

Стратегията за извличане на `MemoryConfig` е една от `exact`, `semantic` или `hybrid`,
а обхватът е един от `session`, `apiKey` или `global`. Обхватът по подразбиране от
`getMemorySettings()` е `apiKey`.

## Извличане на факти (`extraction.ts`)

Извличането е **базирано на регулярни изрази**, а не на LLM — то се изпълнява в рамките на процеса чрез
`setImmediate()`, така че никога да не блокира потока на отговора:

- **Шаблони за предпочитания** → `MemoryType.FACTUAL`
  (напр. `I prefer …`, `I really like …`, `my favorite is …`, `I hate …`)
- **Шаблони за решения** → `MemoryType.EPISODIC`
  (напр. `I'll use …`, `I chose …`, `I went with …`, `I'm going to adopt …`)
- **Шаблони за поведение** → `MemoryType.FACTUAL`
  (напр. `I usually …`, `I always …`, `I tend to …`)

Всяко съвпадение се нормализира (`trim`, свиване на последователните празни знаци, ограничаване до 500 знака),
дедуплицира се в рамките на партидата чрез стабилен `factKey(category, content)` и
се съхранява чрез `createMemory()` с метаданни
`{category, extractedAt, source: "llm_response"}`. Входният текст е ограничен до
64 KiB (`MAX_EXTRACTION_TEXT_LENGTH`) — когато е по-дълъг, се използва **краят** на текста,
така че най-скорошното съдържание от асистента винаги да участва.

`extractFactsFromText(text)` се експортира за тестове и връща структурираните
факти, без да ги съхранява.

## Извличане (`retrieval.ts`)

`retrieveMemories(apiKeyId, config)` е основната входна точка. Тя:

1. Нормализира и валидира конфигурацията чрез `MemoryConfigSchema`.
2. Незабавно връща `[]`, когато `enabled` е false или `maxTokens <= 0`.
3. Ограничава `maxTokens` до диапазона `[1, 8000]`.
4. Установява дали съществува съвременната таблица `memories` (вместо наследената таблица `memory`),
   така че по-старите бази данни да продължат да работят.
5. Изгражда базовата заявка с проверка за изтичане
   (`expires_at IS NULL OR datetime(expires_at) > datetime('now')`), незадължителен
   обхват на сесията и незадължително гранично условие `retentionDays`.
6. Разклонява се според стратегията:
   - **`exact`** (по подразбиране): хронологично `ORDER BY created_at DESC LIMIT 100`.
   - **`semantic`**: ако е зададено `config.query` и съществува `memory_fts`, изпълнява JOIN с
     `memory_fts MATCH ?` и подрежда по FTS ранг; връща се към хронологично подреждане,
     когато FTS върне 0 реда.
   - **`hybrid`**: обединение на FTS резултатите (с по-висока релевантност) и
     хронологичния набор, дедуплицирано по id.
7. Изчислява оценка за релевантност по ключови думи (`getRelevanceScore`) върху
   `content`, `key` и JSON метаданните `metadata`, когато е предоставена заявка. Редовете с
   нулева оценка се филтрират.
8. Сортира по оценка в низходящ ред, след това по `createdAt` в низходящ ред.
9. Обхожда класирания списък и приема записи, докато текущата стойност на
   `estimateTokens(content)` (≈ `length / 4`) остава в рамките на бюджета. Винаги
   връща поне един запис, когато има съвпадения.

`estimateTokens` се експортира и се използва при извличане, обобщаване и от MCP
инструмента `omniroute_memory_search`.

## Инжектиране (`injection.ts`)

`injectMemory(request, memories, provider)`:

1. Обединява съдържанието на всички спомени в един низ `Memory context: …`.
2. Избира стратегия според името на доставчика:
   - **Системно съобщение** (по подразбиране за OpenAI, Anthropic, Gemini, …) — добавя
     `{role: "system", content: memoryText}` преди всички съществуващи системни
     съобщения, така че системните инструкции на потребителя да запазят предимство.
   - **Потребителско съобщение** (резервен вариант) — за доставчиците в
     `PROVIDERS_WITHOUT_SYSTEM_MESSAGE`: `o1`, `o1-mini`, `o1-preview`,
     `glm`, `glmt`, `glm-cn`, `zai`, `qianfan`. Те отхвърлят системната роля
     и в противен случай биха върнали 400 (вж. проблем #1701 за GLM/Zhipu).
3. Записва в журнала броя, стратегията и модела под `memory.injection.injected`.

`providerSupportsSystemMessage(provider)` се експортира за извикващи компоненти, които трябва
да вземат собствени решения за маршрутизиране. За неизвестни доставчици по подразбиране се връща `true`
(системната роля е разрешена) от съображения за безопасност.

## Обобщаване (`summarization.ts`)

`summarizeMemories(apiKeyId, sessionId?, maxTokens = 4000)` уплътнява по-старото
съдържание, когато текущият общ брой токени в паметите за даден ключ надвиши
бюджета. Функцията обхожда редовете в низходящ ред по `created_at`, запазва редовете,
които се побират, а за останалите заменя на място `content` с първите три изречения
от оригинала. `tokensSaved` е разликата в `estimateTokens` между старото и
новото съдържание.

Тази процедура е **налична, но не се извиква автоматично** в текущия
конвейер за чат — извикайте я от cron задача, административно действие или
свързващ код за `MemoryConfig.autoSummarize`, ако се нуждаете от непрекъснато
уплътняване. Загубата на данни е необратима: оригиналният текст се презаписва.

## MCP инструменти (`open-sse/mcp-server/tools/memoryTools.ts`)

Когато MCP сървърът е активиран, се регистрират три инструмента за памет:

- `omniroute_memory_search` — `{apiKeyId, query?, type?, maxTokens?, limit?}`
  → обвива `retrieveMemories()`. От v3.8.6 (D16) `strategy` се прочита
  от `getMemorySettings()`, вместо да бъде твърдо зададена като `"exact"`. Ако
  е предоставена `query` и `strategy` е `semantic` или `hybrid`, се използва
  векторното хранилище, когато е налично.
- `omniroute_memory_add` — `{apiKeyId, sessionId?, type, key, content,
metadata?}` → обвива `createMemory()`. Приема само 4-те канонични типа:

- `omniroute_memory_clear` — `{apiKeyId, type?, olderThan?}` → извежда съвпадащите
  записи, по избор ги филтрира по времеви маркер за създаване преди зададен момент, след което изтрива всеки
  чрез `deleteMemory()` (което също премахва векторите от sqlite-vec + Qdrant).

Вижте [MCP-SERVER.md](./MCP-SERVER.md) за подробности относно транспорта и обхвата.

## Избор на доставчик на векторни представяния (v3.8.16+)

Механизмът за памет на OmniRoute поддържа **четири източника на векторни представяния** (`src/lib/memory/embedding/`). Всеки има различни компромиси по отношение на **латентност, цена, качество на модела и сложност на настройката**.

### Източниците на векторни представяния

| Доставчик      | Източник                                                  | Латентност                                   | Цена                 | Качество                                   | Настройка                                           |
| -------------- | --------------------------------------------------------- | -------------------------------------------- | -------------------- | ------------------------------------------ | --------------------------------------------------- |
| `transformers` | Локален ONNX модел (Xenova/all-MiniLM-L6-v2)              | ~50-150ms (CPU)                              | Безплатно            | Добро                                      | Само `npm install`                                  |
| `static`       | Предварително изчислени вектори (кеширани)                | <1ms                                         | Безплатно            | Неприложимо (зависи от попадението в кеша) | Няма                                                |
| `remote`       | API на OpenAI / Cohere / Voyage                           | ~100-300ms                                   | $0.02-0.10/1M токена | Отлично                                    | API ключ                                            |
| `auto`         | Избира най-добрия наличен източник по време на изпълнение | Същата като избрания източник                | Безплатно            | Същото като при избрания източник          | Няма                                                |
| _(кеш)_        | LRU слой в паметта върху всеки източник                   | <1ms (попадение), пълна латентност (пропуск) | Безплатно            | Същото като при базовия източник           | Винаги включен (не може да се избира като източник) |

## Настройване на хибридния RRF (v3.8.16+)

Алгоритъмът **Reciprocal Rank Fusion (RRF)** комбинира резултатите от FTS5 (по ключови думи) и векторното (семантично) търсене. Параметърът `k` определя каква тежест се дава на резултатите с по-ниско класиране.

### Формулата

За всеки кандидат-запис в паметта RRF резултатът е:

```
RRF(d) = Σ  1 / (k + rank_i(d))
```

Където:

- `k` е константата (по подразбиране 60)
- `rank_i(d)` е рангът на документа `d` в i-тата система за извличане (FTS, векторна)
- Сумата се изчислява за всички системи за извличане

### Как `k` влияе върху резултатите

| Стойност на `k`              | Ефект                                                                                              | Най-подходящо за                                  |
| ---------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `k=0`                        | Чисто сливане на рангове (без изглаждане)                                                          | Теоретична базова линия                           |
| `k=10-30`                    | Дава голяма тежест на водещите резултати; ниският ранг допринася минимално                         | Когато първите 3 резултата обикновено са правилни |
| **`k=60`** (по подразбиране) | Балансирано — първите 10 резултата допринасят значимо                                              | Извличане с общо предназначение                   |
| `k=100+`                     | По-равномерно — дори резултати с нисък ранг могат да доминират, ако присъстват в множество системи | Когато пълнотата > прецизността е критично важна  |

### Настройване на `k` на практика

```bash
# По подразбиране
MEMORY_RRF_K=60

# Агресивна прецизност (малка памет, малко документи)
MEMORY_RRF_K=20

# Максимална пълнота (голяма памет, разнообразни заявки)
MEMORY_RRF_K=120
```

**Пример с `k=20`:**

- FTS ранг 1 → принос `1/21 = 0.048`
- FTS ранг 10 → принос `1/30 = 0.033`
- Векторен ранг 1 → принос `0.048`
- Максимална комбинирана стойност: `0.096`

**Пример с `k=60`:**

- FTS ранг 1 → принос `1/61 = 0.016`
- FTS ранг 10 → принос `1/70 = 0.014`
- Векторен ранг 1 → принос `0.016`
- Максимална комбинирана стойност: `0.033`

При по-високо `k` **относителната разлика** между първия резултат и резултата с ранг 10 е по-малка, така че алгоритъмът разчита повече на **съгласието между системите за извличане**, отколкото на увереността в най-високия ранг.

### Кога да промените `k`

| Симптом                                            | Опитайте                                                                         |
| -------------------------------------------------- | -------------------------------------------------------------------------------- |
| Първият резултат винаги печели, но е грешен        | **По-ниско** k (напр. 20) — увереността в най-високия ранг е по-важна            |
| Правилният отговор е сред първите 5, но не е първи | **По-високо** k (напр. 100) — по-равномерното оценяване възнаграждава консенсуса |
| Пълнотата е висока, но прецизността е ниска        | **По-ниско** k — направете класирането по-категорично                            |
| Пълнотата е ниска (липсват релевантни документи)   | **По-високо** k — дайте шанс на документите с по-нисък ранг                      |

### Претегляне при RRF

Реципрочното сливане на рангове използва еднакви тегла за семантичния векторен ранг и ранга от пълнотекстовото търсене:

```
RRF(d) = 1/(k + rank_vector) + 1/(k + rank_fts)
```

Няма променливи на средата за настройване на отделните тегла (`MEMORY_RRF_VECTOR_WEIGHT`/`MEMORY_RRF_FTS_WEIGHT` не съществуват).

## Стратегия за обобщаване (v3.8.16+)

Модулът `summarization.ts` (`src/lib/memory/summarization.ts`) компресира по-старите спомени, за да запази активния набор малък, като същевременно съхранява възможността за извличането им.

### Кога се задейства обобщаването

| Задействащ механизъм       | Праг (по подразбиране) |
| -------------------------- | ---------------------- |
| Ръчно задействане чрез API | неприложимо            |

### Какво се обобщава

От `summarization.ts` се експортират две входни точки:

- **`summarizeMemories(apiKeyId, sessionId?, maxTokens = 4000)`** — кондензира
  спомените за дадена сесия в един обобщен текст, ограничен от бюджет на токените.
- **`summarizeMemoriesOlderThan(apiKeyId, days, dryRun)`** — базираното на възрастта
  компактиране, използвано от API: избира всеки спомен, по-стар от `days`, създава
  от тях един кондензиран обобщен спомен и (когато `dryRun` е `false`) изтрива
  оригиналите. Подайте `dryRun: true`, за да прегледате набора от кандидати и общия
  брой токени, без да променяте нищо.

Няма етап за групиране по таг/ключ или оценяване на отделните спомени като „основни спрямо подлежащи на обобщаване“ —
изборът се извършва единствено според възрастовата граница, а обобщеният текст представлява кондензиран,
предшестван от тип ред за всеки кандидат.

### Задействане на обобщаването

Обобщаването е **ръчно / по избор** — настройката `autoSummarize` по подразбиране е
`false`, така че нищо не се компактира автоматично. Задействайте го чрез API:

```bash
curl -X POST http://localhost:20128/api/memory/summarize \
  -H "Authorization: Bearer $OMNIROUTE_KEY"
```

За да остане изключено, просто запазете стойността по подразбиране (`false`) на `autoSummarize`.

### Съвети за качествено обобщаване

- **Първо направете предварителен преглед с `dryRun`** — `summarizeMemoriesOlderThan(..., true)` връща
  списъка с кандидати и общия брой токени, за да можете да потвърдите какво ще бъде обединено,
  преди да изтриете оригиналите.
- **Изпълнявайте обобщаването в часове с ниско натоварване**, ако разполагате с голям корпус от спомени — извикването на LLM е бавната част

```bash
# В стил Cron: обобщаване всеки ден в 3 ч. сутринта
0 3 * * * curl -X POST http://localhost:20128/api/memory/summarize \
  -H "Authorization: Bearer $OMNIROUTE_KEY"
```

## Шаблон за доставчик MemoryBackend

> **Източник на достоверна информация:** `src/lib/memory/backend.ts`, `src/lib/memory/genericBackend.ts`, `src/lib/memory/manager.ts`
> **Тестове:** `src/lib/memory/__tests__/generic-backend.test.ts`

Шаблонът за доставчик MemoryBackend въвежда **сменяем абстракционен слой за бекенд** върху съществуващия механизъм за памет. Вместо да бъде обвързана с една реализация за съхранение, системата за памет вече поддържа множество бекенди (SQLite, Obsidian, Notion, персонализирани HTTP бекенди) с конфигурируемо маршрутизиране към основен/резервни бекенди.

### Архитектура

```
┌──────────────────────────────────────────────────────────┐
│                    API маршрути                           │
│            (src/app/api/memory/route.ts)                  │
└──────────────────────┬───────────────────────────────────┘
                       │
┌──────────────────────▼───────────────────────────────────┐
│                   MemoryManager                           │
│         Единичен оркестратор (manager.ts)                 │
│                                                          │
│  Основен ──► Бекенд A  (напр. SQLite)                    │
│  Резервен ─► Бекенд B  (напр. Obsidian)                  │
│              Бекенд C  (напр. Notion чрез GenericBackend) │
└──────────────────────┬───────────────────────────────────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
┌────────────┐ ┌────────────┐ ┌──────────────────┐
│ SQLite     │ │ Obsidian   │ │ GenericMemory    │
│ бекенд     │ │ бекенд     │ │ бекенд (HTTP)    │
└────────────┘ └────────────┘ └──────────────────┘
```

#### Основен интерфейс (`backend.ts`)

Всеки бекенд трябва да имплементира интерфейса `MemoryBackend`:

```typescript
interface MemoryBackend {
  readonly id: string;
  readonly displayName: string;

  // CRUD
  create(input: CreateMemoryInput): Promise<Memory>;
  get(id: string): Promise<Memory | null>;
  update(id: string, updates: Partial<...>): Promise<boolean>;
  delete(id: string): Promise<boolean>;
  list(filter: MemoryFilter): Promise<{ data: Memory[]; total: number; byType: Record<string, number> }>;

  // Търсене
  search(config: SearchConfig): Promise<Memory[]>;

  // Състояние
  health(): Promise<HealthCheckResult>;

  // Жизнен цикъл (по избор)
  initialize?(): Promise<void>;
  shutdown?(): Promise<void>;
}
```

#### MemoryManager (`manager.ts`)

Единичен оркестратор, който:

- **Регистрира** бекенди чрез `register(backend)` — извиква се при стартиране от `index.ts`
- **Конфигурира** основен + резервни бекенди чрез `configure(primary, fallbacks)`
- **Маршрутизира** CRUD операциите/търсенето към основния бекенд, с верига от резервни бекенди при неуспех
- **Проверява състоянието** на всички бекенди периодично

**Поведение при превключване към резервен бекенд:**

| Операция | Основен                      | Резервни                           |
| -------- | ---------------------------- | ---------------------------------- |
| `create` | ✅ Само основният            | ❌                                 |
| `get`    | ✅ Първо се опитва основният | ✅ Резервен, ако резултатът е null |
| `update` | ✅ Само основният            | ✅ Асинхронна синхронизация        |
| `delete` | ✅ Само основният            | ✅ Асинхронна синхронизация        |
| `list`   | ✅ Само основният            | ❌                                 |
| `search` | ✅ Първо се опитва основният | ✅ Резервен при грешка             |

#### GenericMemoryBackend (`genericBackend.ts`)

Универсален HTTP конектор, който адаптира всеки REST API към MemoryBackend. Полезен за:

- **Notion** — свързване чрез Notion API
- **Obsidian** — свързване чрез Obsidian Local REST API
- **Персонализирани бекенди** — всяка услуга, която предоставя RESTful API за памет

**Конфигурация:**

```typescript
interface GenericBackendConfig {
  baseUrl: string;           // Базов URL на API на бекенда
  apiKey?: string;           // Bearer токен за удостоверяване
  headers?: Record<string, string>;  // Персонализирани HTTP заглавки
  timeout?: number;          // Време за изчакване на заявката (по подразбиране: 30000ms)
  backendType?: string;      // За регистриране в журнала

  // Замени на крайни точки (стойностите по подразбиране използват REST конвенции)
  endpoints?: {
    search?: string;   // по подразбиране: "/memories/search"
    create?: string;   // по подразбиране: "/memories"
    list?: string;     // по подразбиране: "/memories"
    get?: string;      // по подразбиране: "/memories/{id}"
    update?: string;   // по подразбиране: "/memories/{id}"
    delete?: string;   // по подразбиране: "/memories/{id}"
    health?: string;   // по подразбиране: "/health"
  };

  // Съответствия на имената на параметрите на заявката
  queryParams?: {
    query?/apiKeyId?/limit?/offset?/strategy?/maxTokens?/type?/sessionId?/orderBy?/orderDir?/options?
  };

  // Съответствия на имената на параметрите на пътя
  pathParams?: {
    id?/memoryId?
  };
}
```

**Познатите бекенди** са предварително конфигурирани в `KNOWN_BACKENDS`:

```typescript
createKnownBackend("obsidian"); // → GenericMemoryBackend, насочен към localhost:27123
createKnownBackend("notion"); // → GenericMemoryBackend, насочен към api.notion.com/v1
```

#### Вградени бекенди

##### SQLiteBackend (`sqliteBackend.ts`)

Основният бекенд по подразбиране. Обвива съществуващото базирано на SQLite хранилище за памет чрез `src/lib/memory/store.ts`. Регистрира се автоматично при стартиране.

```typescript
import { sqliteBackend } from "./sqliteBackend";
memoryManager.register(sqliteBackend);
```

##### ObsidianBackend (`obsidianBackend.ts`)

Обвива съществуващата интеграция с Obsidian (`src/lib/memory/obsidianBackend.ts`). Свързва се с хранилище на Obsidian чрез Obsidian Local REST API.

### Настройки

Настройките на бекендите за памет се съхраняват в таблицата с настройки на приложението и се управляват чрез `src/lib/memory/settings.ts`:

| Настройка                 | Ключ за среда/конфигурация | По подразбиране | Описание                                 |
| ------------------------- | -------------------------- | --------------- | ---------------------------------------- |
| Основен бекенд            | `memoryPrimaryBackend`     | `"sqlite"`      | ID на основния бекенд                    |
| Резервни бекенди          | `memoryFallbackBackends`   | `[]`            | Подредени ID на резервните бекенди       |
| Конфигурации на бекендите | `memoryBackendConfigs`     | `{}`            | Замени на конфигурацията за всеки бекенд |

Настройките се нормализират чрез `normalizeMemorySettings()` и се кешират в `getMemorySettings()`.

### Процес на инициализация

```
Стартиране на приложението
  → импортиранията в index.ts (като страничен ефект): регистрират SQLiteBackend
  → initMemoryBackends() се извиква от жизнения цикъл на приложението:
      1. Зареждане на настройките (getMemorySettings)
      2. Конфигуриране на основния и резервните бекенди
      3. Инициализиране на всички бекенди (проверка на състоянието)
      4. Готовност за заявки
```

### Добавяне на нов бекенд

1. **Имплементирайте интерфейса `MemoryBackend`** в `src/lib/memory/<name>Backend.ts`
2. **Експортирайте** от `src/lib/memory/index.ts`
3. **Регистрирайте** чрез `memoryManager.register(yourBackend)` при стартиране
4. **Конфигурирайте** чрез настройките: задайте ID на вашия бекенд за `memoryPrimaryBackend`
5. **Тествайте**, като използвате `src/lib/memory/__tests__/generic-backend.test.ts` за справка

#### Пример: Brain Backend

```typescript
import { createGenericMemoryBackend } from "./genericBackend";

const brainBackend = createGenericMemoryBackend("brain", "BK-Brain", {
  baseUrl: process.env.BRAIN_API_URL || "http://localhost:9099",
  apiKey: process.env.BRAIN_API_KEY,
  endpoints: {
    search: "/api/memory/search",
    create: "/api/memory",
    health: "/api/health",
  },
});

memoryManager.register(brainBackend);
```
