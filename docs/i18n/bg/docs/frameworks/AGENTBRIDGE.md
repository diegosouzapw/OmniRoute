AgentBridge е MITM (Man-in-the-Middle, „посредник“) проксито на OmniRoute, което прихваща HTTPS трафика от AI агенти в IDE и го пренасочва през унифицирания механизъм за маршрутизиране на OmniRoute. То поддържа **10 IDE агента** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code и Trae (в процес на проучване) — което прави OmniRoute MITM проксито с най-широко покритие за AI асистенти за програмиране на пазара.

**Местоположение в таблото:** `/dashboard/tools/agent-bridge`
**Група в страничната лента:** Инструменти (след Облачни агенти)
**Вижте също:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — наблюдавайте целия прихванат трафик в реално време; `docs/security/MITM-TPROXY-DECRYPT.md` (git; не се компилира в `/docs`) — режимът за прихващане с прозрачно дешифриране чрез Linux TPROXY, управляван от маршрута `/api/tools/agent-bridge/tproxy`.

## §1 Общ преглед

### Какво представлява AgentBridge?

Когато IDE агент (напр. GitHub Copilot, Cursor, Claude Code) извършва API заявка, той се свързва директно с външния AI доставчик (OpenAI, Anthropic и др.). AgentBridge прихваща тази връзка прозрачно на TLS ниво — без да изисква промяна в конфигурацията на агента — и пренасочва заявката през OmniRoute.

Това означава, че можете да:

- **Пренасочвате всеки агент към всеки доставчик**: Copilot комуникира с OpenAI? Пренасочете го към Anthropic Claude, Gemini или към който и да е от 352-та доставчика на OmniRoute.
- **Прилагате съпоставяния на модели**: `gemini-3-flash` → `claude-sonnet-4.7` прозрачно на ниво обработчик.
- **Наблюдавате целия трафик на агентите**: всяка прихваната заявка се публикува в [Инспектора на трафика](./TRAFFIC_INSPECTOR.md).
- **Прилагате устойчивостта на OmniRoute**: комбинираното маршрутизиране, прекъсвачите на веригата, резервните варианти и проследяването на разходите работят и за трафика от IDE агенти.

## §2 Архитектура

### 2.1 Преглед на компонентите

```
IDE агент (VS Code / Cursor / и др.)
    │  HTTPS (порт 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← DNS пренасочване
    │
    ▼
src/mitm/server.cjs  (порт 443, CJS дъщерен процес)
    │  определя целта чрез SNI от Host заглавката
    │  генерира TLS сертификат за всеки SNI, подписан от CA на AgentBridge
    ├── Съвпадение със списъка за заобикаляне? → TCP директно препредаване (без декриптиране)
    ├── Съвпадение с цел? → fetch → маршрутизатор OmniRoute (порт 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() върху тялото/заглавките на заявката
    │               ├── TrafficBuffer.push() — публикува в Traffic Inspector
    │               └── fetchRouter() → /v1/chat/completions
    └── Няма съвпадение? → TCP директно препредаване (без декриптиране)
```

### 2.2 MITM сървър (`src/mitm/server.cjs`)

Основният MITM сървър работи като дъщерен Node.js CJS процес (за да се избегне пренаписването на съществуващата CJS кодова база). Той:

- Слуша на порт 443 (изисква привилегии или `authbind`/`setcap`)
- Получава CONNECT тунели от операционната система (чрез DNS пренасочване в `/etc/hosts`)
- Генерира TLS сертификати за всеки SNI, подписани от CA на AgentBridge (`DATA_DIR/mitm/ca.crt`)
- Определя целевия агент чрез Host заглавката посредством регистъра `targets/index.ts`
- Предава заявките към слоя с TypeScript обработчици чрез HTTP към `http://127.0.0.1:20128`

`TARGET_HOSTS` се зарежда от `DATA_DIR/mitm/targets.json` (записван от `targets/index.ts` при стартиране), което позволява динамични актуализации без рестартиране на CJS сървъра.

> **Модел с коренен CA (#6684).** Описаният по-горе модел със сертификат за всеки SNI, подписан от CA,
> е устойчивият модел с коренен CA, добавен в #6684 (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, използващ повторно криптографската реализация за CA/крайни сертификати,
> вече доказала се за TPROXY в `src/mitm/tproxy/dynamicCert.ts`) — той заменя
> по-стария единичен статичен самоподписан краен сертификат (`src/mitm/cert/generate.ts`, който все още
> е ограничен само до antigravity хостовете), за който указва наличието на двойка
> `server.crt`/`server.key` на диска. **Поведение при миграция**: нова инсталация (без предишен
> `server.crt`) автоматично получава модела с коренен CA; инсталация, която вече
> се доверява на стария статичен краен сертификат, продължава да го използва, докато операторът не зададе
> `MITM_ROOT_CA_ENABLED=true` и не рестартира моста (`src/mitm/cert/migration.ts`
> е чистата функция за вземане на решение — доверен MITM CA, който може да подпише краен сертификат за
> **всеки** хост, е значително по-мощен от стария краен сертификат с фиксиран SAN, затова
> превключването никога не се извършва без известяване при вече доверена инсталация). CA сертификатът се инсталира
> в същия слот `omniroute-mitm.crt` в хранилището за доверени сертификати, който се използваше от стария краен сертификат
> (`cert/install.ts::installCaCert`) — не е необходимо почистване на двойно доверие.

### 2.3 Базов обработчик (`src/mitm/handlers/base.ts`)

Всички обработчици на агенти разширяват `MitmHandlerBase`:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // Защитени помощни методи: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

Всеки обработчик извиква `hookBufferStart()` преди проксирането и `hookBufferUpdate()` при завършване. Те добавят записи `InterceptedRequest` в `globalTrafficBuffer` (вижте [Инспектор на трафика](./TRAFFIC_INSPECTOR.md) §4).

### 2.4 Регистър на целите (`src/mitm/targets/`)

Всеки агент има декларативен файл с цел:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

Регистърът (`targets/index.ts`) експортира `ALL_TARGETS` и генерира `DATA_DIR/mitm/targets.json` при стартиране.

### 2.5 Директно препредаване и списък за заобикаляне (`src/mitm/passthrough.ts`)

**Списък за заобикаляне** (проверява се първо и има предимство пред съвпадението с цел):

- Шаблони по подразбиране: банкови хостове, `.gov.`, доставчици на OAuth/SSO (Okta, Auth0) и др.
- Потребителски шаблони: съхраняват се в таблицата `agent_bridge_bypass` на базата данни
- Заобикаляните хостове получават прозрачен TCP тунел — TLS **никога не се декриптира**

**Директно препредаване по подразбиране** (няма съвпадение с цел и хостът не е в списъка за заобикаляне):

- Също получава TCP тунел — връзките никога не се прекъсват
- Предотвратява нарушаването на общия системен HTTPS трафик от AgentBridge

Приоритет на маршрутизирането:

```
списък за заобикаляне → съвпадение с цел → директно препредаване
```

### 2.6 Сертификат на upstream CA (`src/mitm/upstreamTrust.ts`)

За корпоративни мрежови среди с персонализиран CA:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

Когато е зададена, стойността конфигурира глобалния диспечер на `undici` с допълнителния CA сертификат, позволявайки на AgentBridge да достига upstream доставчици през корпоративни прокси сървъри за TLS терминиране.

### 2.7 Маскиране на тайни (`src/mitm/maskSecrets.ts`)

Независимият скенер, разработен по метода на чистата стая, се прилага към телата на заявките и заглавките с идентификационни данни
**преди** те да попаднат в буфера на Traffic Inspector или в който и да е журнал. Той извършва еднократно линейно обхождане:

- Токени с префикс `sk-` / `ak-` / `pk-` (в стил OpenAI/Anthropic)
- Идентификационни данни по RFC 6750 `Authorization: Bearer <token>`, с приоритет на целия токен
- Общи дълги непрозрачни токени (≥40 знака), включително форми с точки и допълване

`sanitizeHeaders()` преобразува запазените имена в малки букви, обединява стойностите на масивите детерминистично, премахва
споделения списък със забранени hop-by-hop/рамкиращи заглавки (включително прокси удостоверяване), напълно редактира `cookie` и
`set-cookie` и делегира стойностите с идентификационни данни на скенера.

## §3 Настройка

### 3.1 Стартиране/спиране на MITM сървъра

Използвайте картата на AgentBridge Server на адрес `/dashboard/tools/agent-bridge`:

| Действие                     | Описание                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------- |
| Стартиране на сървъра        | Стартира `src/mitm/server.cjs` на порт 443                                                  |
| Спиране на сървъра           | Коректно спира дъщерния процес                                                              |
| Рестартиране на сървъра      | Спиране + стартиране (прилага промените в целите)                                           |
| Доверяване на сертификат     | Инсталира `DATA_DIR/mitm/ca.crt` в хранилището за доверени сертификати на ОС                |
| Изтегляне на сертификат      | Изтегля `ca.crt` за ръчно инсталиране                                                       |
| Генериране на нов сертификат | Създава нова двойка CA ключове (всички съществуващи сертификати за агенти стават невалидни) |

### 3.2 Доверяване на сертификата

CA сертификатът на AgentBridge трябва да бъде добавен като доверен от ОС, преди IDE средите да приемат MITM връзката.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

Или използвайте бутона „Доверяване на сертификат“ в таблото за управление (изпълнява подходящата команда за вашата ОС, като при необходимост показва подкана за sudo).

#### Базираните на Electron IDE среди игнорират хранилището за доверени сертификати на ОС (`NODE_EXTRA_CA_CERTS`)

Някои IDE среди — най-вече **Antigravity IDE**, както и други приложения, базирани на Electron / VS Code — включват
собствена среда за изпълнение на Node.js, която **не използва хранилището за доверени сертификати на ОС** за изходящи
`fetch`/HTTPS заявки. Доверяването на CA на ниво ОС/NSS е достатъчно за нативния **бекенд** на IDE средата
(например езиков сървър на Go, който използва CA пакета на ОС), но **Electron фронтендът** все пак ще
претърпи TLS грешка — това се проявява като _излизане от профила_ в приложението или показване на _„грешка при свързване“_,
въпреки че MITM журналът показва, че началните заявки на бекенда връщат `200`. Необходими са
две стъпки и и двете са важни:

1. Насочете изрично средата за изпълнение към CA:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **Стартирайте IDE средата от същата обвивка.** Стартирането ѝ от иконата на работния плот / Dock / менюто Start
   **не** наследява експортираните променливи на обвивката, а `~/.config/environment.d/*.conf` се прилага едва след
   ново влизане в графичната сесия. Първо затворете напълно IDE средата — заключването за единичен екземпляр на Electron означава, че второто
   стартиране само фокусира съществуващия процес и новата среда се игнорира.

Стъпката за доверяване на ниво ОС + NSS по-горе остава необходима (мрежовият стек на Chromium, използван от някои потоци
за удостоверяване, чете потребителското NSS хранилище и има собствени статични фиксирани сертификати за `*.googleapis.com`, които
локално доверен CA заменя). `NODE_EXTRA_CA_CERTS` допълнително покрива пътя на Node `fetch`.

### 3.3 DNS маршрутизиране

За всеки агент, който искате да прихващате, неговият API хост (или хостове) трябва да се разрешава до `127.0.0.1`. AgentBridge управлява автоматично записите в `/etc/hosts`, когато превключите DNS за даден агент в съветника за настройка.

Примерни записи в `/etc/hosts` за GitHub Copilot:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 Съпоставяне на модели

Използвайте таблицата за съпоставяне на модели в картата на всеки агент, за да зададете съпоставяния източник → цел:

| Модел източник (нативен за агента) | Целеви модел (OmniRoute) |
| ---------------------------------- | ------------------------ |
| `gpt-4o`                           | `claude-sonnet-4.7`      |
| `*` (заместващ символ)             | `claude-haiku-4.7`       |

Заместващият символ `*` съпоставя всеки неразпознат модел с посочената цел. Данните се съхраняват в таблицата `agent_bridge_mappings`.

> **Съвет — открийте действителните идентификатори на моделите на агента.** IDE средата може да изпраща имена на модели, които се различават от
> етикетите в нейния потребителски интерфейс и се променят между основните версии. Например **Antigravity 2** изпраща
> `gemini-3.1-pro-low`, `gemini-pro-agent` и `gemini-3.1-flash-lite` по мрежата — а не
> `gemini-2.5-pro`, показан в по-старата документация. Изпратете едно чат съобщение без налично съответстващо съпоставяне: MITM
> регистрира точната входяща стойност на `model:` и пропуска заявката без промяна. Съпоставете тази буквална стойност, след което
> следващата заявка ще бъде прихваната и маршрутизирана към вашата цел.

### 3.5 Известие за риск

AgentBridge прихваща идентификационни данни (OAuth токени, API ключове), които IDE средата използва за удостоверяване пред доставчиците нагоре по веригата. Те са **маскирани преди записване в журнала** (вижте §2.7), но са видими за MITM слоя на OmniRoute. При първото активиране на всеки агент се показва модален прозорец с известие за риск, който може да бъде затворен.

### 3.6 Поддръжка и диагностика

Таблото за управление съдържа карта **Поддръжка и диагностика** (`AgentBridgeMaintenanceCard`, в `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`), която предоставя достъп до оперативни MITM маршрути, за които преди не е имало потребителски интерфейс. Нейният подзаглавен текст е: _„Извършете самопроверка на конвейера за прихващане, отменете останалото системно състояние и прехвърлете настройката си между машини.“_ Клиентските помощни функции на картата се намират в `src/lib/inspector/agentBridgeMaintenanceApi.ts`.

| Бутон                              | Маршрут                                | Какво прави                                                                                                                                                                                                        |
| ---------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Диагностика**                    | `GET /api/tools/agent-bridge/diagnose` | Изпълнява самотеста на конвейера за прихващане и показва отчет за всяка проверка (✓/✗ + насока за отстраняване).                                                                                                   |
| **Поправка**                       | `POST /api/tools/agent-bridge/repair`  | Отменя изоставеното системно състояние на MITM (записи за DNS подмяна, коренов CA, системен прокси), останало след срив или SIGKILL. Идемпотентно — съобщава „Няма нищо за поправяне“, когато състоянието е чисто. |
| **Премахване на CA**               | `DELETE /api/tools/agent-bridge/cert`  | Премахва доверието и кореновия CA на MITM от хранилището за доверени сертификати на ОС (изрично, идемпотентно). Показва се само когато CA в момента е доверен; изисква потвърждение „Премахване на CA?“ на място.  |
| **Експортиране на конфигурацията** | `GET /api/tools/agent-bridge/config`   | Изтегля преносимата JSON конфигурация (вижте §3.7).                                                                                                                                                                |
| **Импортиране на конфигурация**    | `POST /api/tools/agent-bridge/config`  | Качва експортирана по-рано JSON конфигурация (вижте §3.7).                                                                                                                                                         |

**Диагностични проверки** (`summarizeDiagnostics()` в `src/mitm/inspector/diagnostics.ts`). Маршрутът изпълнява проверката със странични ефекти за всеки елемент и подава булевите стойности към чистата обобщаваща функция; връщат се една обща оценка `healthy` и насока за всяка неуспешна проверка:

| Име на проверката  | Какво проверява                                                     | Насока при неуспех                                                                                                                                                                   |
| ------------------ | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `server-running`   | Процесът на MITM сървъра е активен                                  | „MITM сървърът не работи. Стартирайте го от раздела AgentBridge.“                                                                                                                    |
| `server-reachable` | MITM сървърът приема връзки на своя порт (TCP проверка)             | „MITM сървърът не приема връзки на своя порт. Проверете дали портът е свободен и дали имате права да се свържете с него.“                                                            |
| `cert-exists`      | MITM сертификатът е генериран на диска                              | „Все още не е генериран MITM сертификат. Генерирайте такъв от раздела AgentBridge.“                                                                                                  |
| `cert-trusted`     | Кореновият CA на MITM е в хранилището за доверени сертификати на ОС | „Кореновият CA на MITM не е доверен от хранилището на ОС, така че прихващането на TLS ще е неуспешно. Укажете доверие на сертификата от раздела AgentBridge.“                        |
| `dns-configured`   | Целевите имена на хостове са подменени в `/etc/hosts`               | „Целевите имена на хостове не са подменени в /etc/hosts, така че трафикът никога не достига до проксито. Активирайте DNS за агента или агентите, чийто трафик искате да прихващате.“ |

**Банер за изоставено състояние:** когато страницата открие състояние, останало след срив (DNS подмяна / CA / системен прокси), картата показва кехлибарен банер — _„Предишна сесия е оставила системно състояние (DNS подмяна, CA или системен прокси). Изпълнете „Поправка“, за да го изчистите.“_ — и откроява бутона **Поправка**. `Repair` е аналогът на ниво приложение на флага `--cleanup` на ProxyBridge (делегира към `repairMitm()` в `src/mitm/manager.ts`).

> Кореновият CA на MITM остава инсталиран при спиране/стартиране, за да се избегнат
> повтарящи се подкани от sudo (същото поведение като при mitmproxy/Charles), затова премахването му е изрично
> действие **Премахване на CA**, а не нещо, което се извършва автоматично при спиране.

### 3.7 Импортиране/експортиране на преносима конфигурация

AgentBridge може да сериализира **настройваното от оператора** състояние във версиониран JSON обект, така че дадена конфигурация да може да бъде възпроизведена на различни машини. Сериализаторът е `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`), валидиран чрез `AgentBridgeConfigSchema`.

Експортът включва точно три части (вградените стойности по подразбиране умишлено **НЕ** се експортират, така че импортирането никога да не ги дублира или да влиза в конфликт с тях):

| Поле             | Източник                                                                 | Бележки                                                                      |
| ---------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `bypassPatterns` | дефинирани от потребителя шаблони за заобикаляне (`agent_bridge_bypass`) | шаблоните по подразбиране за банки/правителствени сайтове/okta са изключени  |
| `customHosts`    | персонализирани хостове на Traffic Inspector (`inspector_custom_hosts`)  | всеки: `{ host, kind: "llm"\|"app"\|"custom", label? }`                      |
| `agentMappings`  | съпоставяния на модели по агенти (`agent_bridge_mappings`)               | `{ [agentId]: [{ source, target }] }` за всеки агент, който има съпоставяния |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**Поведение при импортиране** (`POST /api/tools/agent-bridge/config`): шаблоните за заобикаляне и съпоставянията по агенти се **заменят изцяло**; персонализираните хостове се добавят **идемпотентно** (`INSERT OR IGNORE`). Отговорът съобщава колко елемента от всеки тип са приложени:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

Какво **НЕ** присъства в конфигурацията: състоянието на работещия сървър, пътищата до сертификатите, DNS състоянието за всеки агент, пътят до CA на сървъра нагоре по веригата и настройките на TPROXY — това е състояние на хоста/средата за изпълнение, а не преносими предпочитания.

### Списък за заобикаляне за чувствителни хостове

Списъкът за заобикаляне гарантира, че финансови институции, доставчици на OAuth/SSO и други чувствителни хостове **никога не се дешифрират**. Техният TLS трафик преминава като прозрачен TCP тунел — OmniRoute никога не вижда нешифрования текст.

Шаблоните за заобикаляне по подразбиране включват:

- `*.bank.*`, `*.gov.*` (финансови/правителствени)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/идентичност)
- `*.apple.com`, `*.icloud.com` (системни услуги на Apple)

Добавените от потребителя шаблони за заобикаляне се съхраняват в таблицата `agent_bridge_bypass` и имат предимство пред всичко останало.

### Маскиране на тайни

Прилага се `maskSecrets()` от `src/mitm/maskSecrets.ts`:

- Към тялото на всяка заявка преди `TrafficBuffer.push()`
- Към всяка заглавка преди записване в журнал или излъчване

Шаблони: токени с префикс `sk-`/`ak-`/`pk-`, `Bearer` токени и общи токени с дължина ≥40 знака.

### Сертификат на CA за връзката нагоре

Когато е зададена `AGENTBRIDGE_UPSTREAM_CA_CERT`, файлът се прочита при стартиране. Ако пътят съществува, но файлът не може да бъде прочетен, AgentBridge записва ясна грешка и отказва да стартира (предотвратява незабелязани TLS неизправности в корпоративни среди).

### Известни ограничения

- **Порт 443 изисква привилегии**: В Linux AgentBridge се нуждае от `setcap 'cap_net_bind_service=+ep'` върху изпълнимия файл на Node или трябва да се стартира чрез `authbind`. Съветникът за настройка показва инструкции, специфични за операционната система.
- **Изисква се рестартиране на IDE средата**: След DNS пренасочването IDE средата трябва да бъде рестартирана, за да влезе в сила новото разрешаване на хостовете.
- **Твърдо зададени OAuth токени**: Някои агенти (Kiro, Antigravity) съхраняват локално OAuth токени за опресняване. Те са прозрачни за AgentBridge — той вижда `Bearer` токена във всяка заявка, който се маскира преди записване в журнал.
- **Electron интерфейсите се нуждаят от `NODE_EXTRA_CA_CERTS`**: IDE среди, чийто интерфейс работи в комплектована Node/Electron среда за изпълнение, игнорират хранилището за доверие на операционната система/NSS и трябва да бъдат стартирани от shell със зададена `NODE_EXTRA_CA_CERTS` (вижте §3.2). Симптом при липса: бекендът на IDE средата се удостоверява (MITM показва отговори `200`), но интерфейсът остава извън профила.
- **Множеството инсталации на една и съща IDE среда са независими**: системна инсталация (например `/usr/share/antigravity/antigravity`) и локална за потребителя „Full“ инсталация (например `~/AntigravityIDE_Full/antigravity-ide`) са отделни процеси със собствени среди за изпълнение — всяка трябва да бъде стартирана повторно с инжектиран CA. Преди повторното стартиране установете коя от тях работи чрез пътя до изпълнимия ѝ файл.
- **Идентичността се задава от системната подкана на агента, а не от маршрутизирания модел**: когато пренасочите модела на агент към друг доставчик, отговорът продължава да заявява вградената идентичност на агента (например Antigravity отговаря „Задвижван съм от Gemini“), защото IDE средата я вмъква в системната подкана. Потвърдете действителния бекенд в `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`), а не като питате модела какъв е.

## §6 Отстраняване на неизправности

### Конфликт с порт 443

Ако друг процес вече слуша на порт 443 (уеб сървър, VPN и др.):

```bash
lsof -i :443          # намиране на процеса
sudo fuser -k 443/tcp  # принудително прекратяване (използвайте внимателно)
```

Като алтернатива конфигурирайте непривилегирован порт в настройките на AgentBridge и задайте правила за пренасочване чрез `iptables` / `pf`.

### Сертификатът не е доверен

Ако IDE показва TLS грешки след стартиране на AgentBridge:

1. Проверете дали сертификатът е инсталиран: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) или `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. Някои приложения поддържат собствено хранилище за доверени сертификати (Firefox, Chrome под Linux). Изпълнете отново „Trust Cert“ и проверете хранилището за сертификати, специфично за NSS/Firefox.
3. Рестартирайте IDE след задаване на доверие — текущите TLS сесии използват предишното състояние на доверие.

### IDE е излязла от профила / „грешка при свързване“ въпреки доверения CA

Симптом: след пренасочване на DNS и задаване на доверие за CA, базирана на Electron IDE (напр. Antigravity)
се отваря **без влязъл профил** или показва грешка при удостоверяване/свързване, въпреки че регистърът на MITM показва, че
първоначалните извиквания (`loadCodeAssist`, `fetchAvailableModels`, …) връщат `200`.

Причина: **вградената Node/Electron среда за изпълнение на IDE игнорира хранилището за доверени сертификати на операционната система**. Нативният
бекенд (езиков сървър на Go) се доверява на CA на операционната система и се удостоверява, но Electron фронтендът
не го прави — затова потребителският интерфейс смята, че няма връзка.

Решение (и двете стъпки): експортирайте `NODE_EXTRA_CA_CERTS=<ca.crt>` **и стартирайте отново IDE от същата
обвивка**, а не чрез иконата на работния плот. Първо затворете напълно IDE — заключването за единична инстанция на Electron означава,
че второ стартиране само фокусира съществуващия процес и новата среда се игнорира. Вижте §3.2.
Това съответства на отворен доклад към основния проект, според който самостоятелен агент работи през MITM, но вариантът
за IDE не работи при същата конфигурация.

### DNS не е обновен

Проверете дали `/etc/hosts` е актуализиран:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

Изчистете DNS кеша:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE не е открита

Автоматичното откриване използва често срещани пътища за инсталиране. Ако откриването е неуспешно, но IDE е инсталирана:

- Проверете дали изпълнимият файл на IDE се намира на нестандартно местоположение
- Съветникът за настройка продължава да работи — неуспешното откриване означава само, че значката няма да показва пътя на инсталацията

### Грешки на обработчика (извличането от източника е неуспешно)

Ако AgentBridge прихваща заявките, но всички те са неуспешни:

1. Проверете дали поне един доставчик е свързан на `/dashboard/providers`
2. Проверете регистрационните файлове на сървъра OmniRoute: `APP_LOG_LEVEL=debug` в `.env`
3. Проверете дали `OMNIROUTE_BASE_URL` сочи към правилната крайна точка на маршрутизатора (по подразбиране: `http://127.0.0.1:20128`)

## §8 Пътна карта

### Проучване на Trae

Trae е сравнително нов AI асистент за програмиране. Преди да имплементирате обработчик:

1. Идентифицирайте изпълнимия файл/разширението в пазарите за VS Code / JetBrains или като самостоятелно приложение
2. Прихванете трафика с mitmproxy, за да откриете API хостовете и структурите на крайните точки
3. Определете механизма за удостоверяване
4. Вземете решение за продължаване или отказ въз основа на условията за ползване и възможността за откриване на API

Докато проучването не приключи, картата на Trae в таблото показва значка „В процес на проучване“ с връзка „Докладване на приложимостта“. Заготовката на обработчика в `src/mitm/handlers/trae.ts` хвърля структурирана грешка `Все още не е имплементирано`.

### Агенти в списъка с предстоящи задачи (изисква се MITM — няма поддръжка за персонализиран базов URL адрес)

Следните инструменти не поддържат персонализирани базови URL адреси в текущите си версии, което прави MITM единствения възможен начин за прихващане. Оценката на приложимостта предстои:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — отделно от Kiro IDE)
- **Cowork** (настолното приложение на Anthropic)

Забележка: GitHub Copilot CLI ≥v1.0.19 поддържа `COPILOT_PROVIDER_BASE_URL` — за този инструмент използвайте директна конфигурация вместо MITM.
