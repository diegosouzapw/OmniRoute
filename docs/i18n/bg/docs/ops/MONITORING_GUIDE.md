> **Накратко**: OmniRoute се предоставя с вграден мониторинг на изправността, автопилот за доставчиците, проследяване на квотите и механизми за наблюдаемост. Това ръководство обхваща таблото за управление, известията и отстраняването на неизправности.

**Източници:**

- `src/lib/monitoring/observability.ts` — моментна снимка на наблюдаемостта
- `src/lib/monitoring/comboHealthAutopilot.ts` — автопилот за изправността на комбинациите
- `src/lib/monitoring/providerHealthAutopilot.ts` — автопилот за доставчиците
- `src/lib/monitoring/providerHealthMatrix.ts` — матрица на изправността на доставчиците
- `src/lib/localHealthCheck.ts` — локална проверка на изправността
- `src/lib/tokenHealthCheck.ts` — изправност при обновяването на токени
- `src/lib/proxyHealth.ts` — кеш за изправността на проксито (разгледан в PROXY_GUIDE.md)

## Общ преглед

OmniRoute има **3 нива на мониторинг**:

```
┌──────────────────────────────────────────────────────────────┐
│  Ниво 1: Изправност на системата (на ниво сървър)             │
│  ├─ localHealthCheck.ts — БД, портове, нативни зависимости    │
│  ├─ db/healthCheck.ts — цялост, FK, осиротели артефакти       │
│  └─ Табло: /dashboard/health                                  │
├──────────────────────────────────────────────────────────────┤
│  Ниво 2: Изправност на доставчиците (устойчивост по доставчик) │
│  ├─ providerHealthAutopilot.ts — прекъсвач, изчаквания         │
│  ├─ providerHealthMatrix.ts — оценки по доставчик/модел       │
│  └─ Табло: /dashboard/providers                               │
├──────────────────────────────────────────────────────────────┤
│  Ниво 3: Наблюдаемост в реално време (моментни снимки)         │
│  ├─ observability.ts — прекъсвачи, сесии, квота                │
│  ├─ tokenHealthCheck.ts — обновяване на OAuth токени           │
│  └─ MCP инструменти: omniroute_get_health, omniroute_get_session_snapshot │
└──────────────────────────────────────────────────────────────┘
```

### `/dashboard/health` (Изправност на системата)

Главното табло за изправността показва:

| Раздел                        | Какво показва                                         |
| ----------------------------- | ----------------------------------------------------- |
| **Състояние на сървъра**      | Време на работа, версия, порт, активни връзки         |
| **База данни**                | Връзка, цялост, размер на WAL, скорошни миграции      |
| **Обобщение на доставчиците** | Брой активни, брой изправни, брой отворени прекъсвачи |
| **Монитори на квотите**       | Активни сесии, известявани, изчерпани                 |
| **Скорошни грешки**           | Последните 10 грешки със стекови трасировки           |
| **Използване на ресурси**     | Памет, CPU, индикатор за натоварване на heap паметта  |

### `/dashboard/providers` (Изправност на доставчиците)

Табло за всеки доставчик:

| Колона     | Описание                                           |
| ---------- | -------------------------------------------------- |
| Доставчик  | ID на доставчика + показвано име                   |
| Изправност | Зелено/жълто/червено състояние                     |
| Прекъсвач  | Отворено/затворено/полуотворено състояние          |
| Връзки     | Брой връзки, последно обновяване                   |
| Модели     | Налични модели, изправност за всеки модел          |
| Разходи    | Разходи за днес, тенденция за 7 дни                |
| Грешки     | Брой грешки за последните 24 ч., водещ клас грешки |

Щракнете върху доставчик, за да видите:

- Скорошни заявки с разбивка на латентността
- Оценки за изправността на всяка връзка
- Блокирания за всеки модел
- Препоръки от автопилота

### `/dashboard/quota` (Проследяване на квотите)

За всеки API ключ:

- Текущо използване спрямо лимита (лента за напредъка)
- Тенденция на квотата (30-дневна диаграма)
- Час на следващото нулиране
- Хронология на известията

### `/dashboard/combos` (Изправност на комбинациите)

За всяка комбинация:

- Стратегия + цели
- Изправност на всяка цел
- Скорошни събития за преминаване към резервна цел
- Процент на успеваемост (24 ч., 7 дни, 30 дни)

## API за проверка на състоянието

OmniRoute предоставя **две** HTTP повърхности за проверка на състоянието. Те не са взаимозаменяеми за оркестратори.

| Път                          | Предназначение                                                                       | Натоварване                               | Използвайте за                                                                     |
| ---------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------- | ---------------------------------------------------------------------------------- |
| `GET /healthz`               | Жизненост/готовност на жизнения цикъл (`ok` / `starting` / `stopping`)               | Минимално (само флаг за фазата)           | Kubernetes **readiness**; лека **liveness**, ако трябва да използвате HTTP         |
| `GET /api/monitoring/health` | Подробно обобщение на системата и доставчиците (БД, heap, брой записи в каталога, …) | Високо (синхронна работа с БД/мониторинг) | Табла, задълбочени blackbox проверки, вградената проверка на състоянието на Docker |

> **Забележка:** Матриците за състоянието на доставчиците, проблемите на autopilot, мониторите на квоти, състоянието на токените и подробностите за латентността извън `/api/monitoring/health` са достъпни чрез **MCP инструмента** `observability_snapshot` или страниците на **таблото** — за тях няма отделни REST маршрути.

И двата маршрута се изпълняват в **същия event loop на Node**, който обработва заявките. Натоварващ процесора път (обработка на голям каталог чрез `GET /v1/models`, компресиране на дълъг контекст/броене на токени) може да забави **всички** HTTP обработчици, включително `/healthz`. Зает event loop ≠ спрял процес. За предпочитане е да отстраните причината за натоварването; настройването на проверките само намалява погрешните прекратявания.

### Лека проверка за оркестратори

```bash
GET /healthz
# или HEAD /healthz
```

- **200** + тяло `ok`, когато фазата на жизнения цикъл на сървъра е в готовност
- **503** + `starting` / `stopping` по време на стартиране или спиране
- Реализация: `src/app/healthz/route.ts` (без проверка на БД)

### Състояние на системата (подробно)

```bash
GET /api/monitoring/health
```

Отговор:

```json
{
  "status": "healthy",
  "version": "3.8.16",
  "uptime": 123456,
  "checks": {
```

#### `credentialHealth`: кеш на проверките спрямо SQLite `test_status`

`GET /api/monitoring/health` → `credentialHealth` е **метриката от кеша на проверките в паметта**, а не моментно извличане на живо от `provider_connections.test_status`. След #12532 пътят на заявката чете само `getCachedCredentialHealthSummary()`; фоновите проверки обновяват кеша извън event loop.

| Слой                            | Къде                                                                  | Какво означава                                                                                                                                                                                                                 |
| ------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Метрика от кеша на проверките   | `credentialHealth.total` / `healthy` / `failed` / `unknown` / `stale` | Последните резултати от проверките на състоянието на идентификационните данни, които все още се съхраняват в паметта на процеса. `source` винаги е `probe-cache`.                                                              |
| Подробности за неуспешни връзки | `credentialHealth.failedConnections`                                  | Присъства **само когато `failed > 0`**. Ограничен списък от редове в кеша със `status=error` (`connectionId`, `status`, пречистени `lastError` / `lastErrorType`). `failedOmitted` се задава, когато списъкът е бил ограничен. |
| Постоянен статус в SQLite       | `credentialHealth.staleDbNonOkCount`                                  | Брой редове на **активни** (`is_active=1`) връзки, чийто съхранен `test_status` е известна стойност, различна от ok (`error`, `expired`, `credits_exhausted`, `banned`, `deactivated`, `unavailable`).                         |

Двата слоя могат умишлено да се разминават:

- Метриката показва `failed=0`, докато `staleDbNonOkCount>0` — SQLite все още съдържа постоянен `test_status` (например `expired` или `credits_exhausted`), който последната моментна снимка от кеша на проверките не отчита като `status=error`.
- Метриката показва `failed>0`, докато SQLite изглежда в добро състояние — скорошна проверка е била неуспешна и резултатът е кеширан; редът в БД не е бил обновен или по-късно е бил изчистен.

Не задействайте известяване единствено въз основа на `provider_connections.test_status`, когато извличате данни от тази крайна точка. Използвайте `failed` + `failedConnections` за текущи неуспешни проверки и `staleDbNonOkCount`, когато ви е необходим броят на съхранените постоянни статуси.

### Препоръки за проверки в Kubernetes

OmniRoute е **един процес на Node** (един event loop). Стандартният Docker `HEALTHCHECK` използва лекия `/healthz`. `/api/monitoring/health` е **твърде тежък** за интервалите на liveness проверките на kubelet.

| Проверка                 | Препоръчителна цел                                                                           | Бележки                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------ | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Стартиране**           | HTTP `GET /healthz` с дълъг `failureThreshold` (или голям `startPeriod`)                     | Студеното стартиране + миграцията на SQLite могат да отнемат повече от няколко секунди                                                                                                                                                                                                                                                                                                                                                              |
| **Готовност**            | HTTP `GET /healthz`                                                                          | Състояние на жизнения цикъл `ok` / `starting` / `stopping` (200 спрямо 503). Все още може да превключва между състоянията, ако цикълът е блокиран от процесора. Отговор **200 след няколко секунди не означава добро състояние** (#10303) — това означава, че цикълът за събития е бил лишен от процесорно време, преди да се изпълни обработчикът за 3 байта                                                                                       |
| **Жизненост**            | HTTP `GET /livez` **или TCP** на основния порт на услугата (`PORT`, по подразбиране `20128`) | `/livez` проверява само дали процесът работи (винаги връща 200, ако обработчикът се изпълни). Той също използва същия цикъл за събития — зает ≠ спрял и не открива изчерпването на процесорното време за цикъла за събития (#10303) по-добре от TCP. Предпочитайте **TCP**, ако HTTP проверките изтичат по време при натоварване от каталога/компресирането; и в двата случая **не** прекратявайте pod-а при кратки блокирания на цикъла за събития |
| **Задълбочена проверка** | `GET /api/monitoring/health` от външна система за проверка                                   | Не е предназначено за `livenessProbe` на kubelet / често изпълнявана `readinessProbe`                                                                                                                                                                                                                                                                                                                                                               |

Примерна структура (коригирайте праговете според натоварването при студено стартиране и компресиране):

```yaml
ports:
  - name: http
    containerPort: 20128
startupProbe:
  httpGet:
    path: /healthz
    port: http
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /healthz
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 6
livenessProbe:
  httpGet:
    path: /livez
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 6
  # При блокиране на цикъла за събития HTTP /livez все пак може да изтече по време. TCP е
  # консервативната алтернатива:
  # tcpSocket:
  #   port: http
```

**Не** насочвайте проверката за **жизненост** на kubelet към `/api/monitoring/health`. Този път извършва реални операции с базата данни/наблюдението и при натоварване ще отчита фалшиви положителни резултати.

Свързани: [#10052](https://github.com/diegosouzapw/OmniRoute/issues/10052) (проверки, докато цикълът за събития е зает), [#9685](https://github.com/diegosouzapw/OmniRoute/issues/9685) / [#10055](https://github.com/diegosouzapw/OmniRoute/pull/10055) (прекомерно натоварване от ценообразуването на каталога), [#10117](https://github.com/diegosouzapw/OmniRoute/issues/10117) (прекомерно натоварване при броенето на токени за компресиране).

### Незадължителни операции по пътя на заявката (памет, умения, обновяване на токени)

Извличането на памет, инжектирането на умения и обновяването на OAuth токени споделят **основния цикъл за събития на Node** с `/healthz`. Това са функции, включвани и изключвани от таблото (`memoryEnabled`, `skillsEnabled`), а не пул от работници. Вижте [Среда — натоварване на цикъла за събития](../reference/ENVIRONMENT.md#event-loop-cost-of-memory-skills-and-token-refresh-10349).

### Състояние на доставчиците

> **Няма REST крайна точка.** Данните за състоянието на доставчиците са достъпни чрез MCP инструмента `observability_snapshot` или страницата `/dashboard/providers` в таблото.

### Подробности за доставчика

> **Няма REST крайна точка.** Подробностите за отделните доставчици са достъпни чрез страницата `/dashboard/providers` в таблото.

## Автопилот за състоянието на доставчиците

Модулът `providerHealthAutopilot.ts` е **система за самовъзстановяване**, която:

1. Открива проблеми с доставчиците (отворена верига, периоди на изчакване, блокирания, предупреждения за квоти)
2. Генерира **препоръчителни действия** за отстраняването им
3. По избор **изпълнява автоматично** действия с нисък риск

### Видове откривани проблеми

| Вид проблем                  | Сериозност     | Примерно условие                                    |
| ---------------------------- | -------------- | --------------------------------------------------- |
| `provider_circuit_open`      | критична       | Прекъсвачът е отворен след 5 неуспешни опита        |
| `provider_circuit_half_open` | предупреждение | Прекъсвачът тества възстановяването                 |
| `connection_cooldown`        | предупреждение | Връзката е в период на изчакване след 429           |
| `stale_connection_error`     | предупреждение | Последното опресняване е неуспешно преди 30+ минути |
| `terminal_connection_error`  | критична       | OAuth е отменен, ключът е невалиден                 |
| `inactive_connection`        | информация     | Връзката е деактивирана в настройките               |
| `model_lockout`              | предупреждение | Конкретен модел е поставен под карантина            |
| `quota_monitor_warning`      | предупреждение | Използвани са 80%+ от квотата                       |

### Видове генерирани действия

| Действие                       | Риск   | Описание                                      |
| ------------------------------ | ------ | --------------------------------------------- |
| `clear_provider_breaker`       | среден | Нулиране на прекъсвача до затворено състояние |
| `clear_connection_cooldown`    | нисък  | Премахване на периода на изчакване от връзка  |
| `clear_stale_connection_error` | нисък  | Изчистване на флага за остаряла грешка        |
| `clear_model_lockout`          | нисък  | Повторно активиране на карантиниран модел     |
| `reactivate_connection`        | среден | Повторно активиране на деактивирана връзка    |
| `deactivate_connection`        | висок  | Деактивиране на проблемна връзка              |

### API

> **Няма REST крайна точка.** Проблемите, открити от автопилота, са достъпни чрез MCP инструмента `observability_snapshot` или таблото за управление. Автопилотът работи вътрешно; поведението му се конфигурира чрез базата данни с настройки (полето `autopilotMode` за всяка връзка), а не чрез променливи на средата — `grep -rn` за променлива на средата за режима на автопилота не връща нито едно съвпадение.

### Режим на автопилота

По подразбиране автопилотът работи в **ръчен режим** — той открива проблеми и генерира препоръчителни действия, но не ги прилага автоматично. Действията могат да бъдат приложени чрез таблото за управление.

## Автопилот за състоянието на комбинациите

`comboHealthAutopilot.ts` е **специфичният за комбинации** еквивалент на автопилота за доставчици. Той:

- Открива неизправни комбинации
- Препоръчва пренареждане на целите
- Предлага деактивиране на неработещи цели
- Автоматично премахва неработещи цели след N неуспешни опита

### Примери за проблеми с комбинации

```
Комбинация "always-on" (стратегия по приоритет)
├─ Цел 1: openai/gpt-5 (изправна)
├─ Цел 2: anthropic/claude-opus-4-6 (⚠️ моделът е блокиран до 14:00)
└─ Цел 3: kiro/claude-sonnet-4-5 (изправна)

Препоръчително действие: Пренареждане — преместете kiro над anthropic, докато блокирането изтече
```

| Състояние   | Кога                              | Действие в потребителския интерфейс            |

## Проверка на състоянието на токените

OAuth доставчиците (Claude Code, GitHub Copilot, Cursor) се нуждаят от **периодично опресняване на токените**. `src/lib/tokenHealthCheck.ts` изпълнява фонов планировчик:

- **Цикъл на обхождане**: на всеки 60 секунди (обхождане в `TICK_MS = 60 * 1000` на `src/lib/tokenHealthCheck.ts:30`)
- **Интервал за проверка на състоянието на всяка връзка**: по подразбиране 60 минути (`DEFAULT_HEALTH_CHECK_INTERVAL_MIN = 60`); конфигурира се чрез базата данни с настройки
- **Превантивно опресняване при 401**: обработва се от прихващача за съответната връзка

### Състояние на токените

## Отстраняване на неизправности

### „Доставчикът се показва като работещ, но заявките са неуспешни“

1. Проверете **проблемите с автопилота** — възможно е даден модел да е блокиран
2. Прегледайте **скорошните грешки** за конкретния клас грешка
3. Опитайте **теста на връзката** в картата на доставчика
4. Проверете дали доставчикът няма **ограничение на честотата от външната услуга** (не се вижда локално)

### „Квотата се показва като налична, но виждам грешки 429“

- 429 означава, че според доставчика сте изчерпали квотата си
- Проследяването на квотата от OmniRoute може да е **неактуално** — достоверните данни са при доставчика
- Данните за квотата се опресняват автоматично чрез вътрешния монитор за квоти

### „Комбинацията е неуспешна, но всички цели изглеждат работещи“

- Проверете таблото за **състоянието на комбинациите** за проблеми с подредбата на целите
- Прегледайте **събитията за преминаване към резервен вариант** — възможно е комбинацията да изчерпва вариантите твърде бързо
- Проверете дали **стратегията** съответства на случая ви на употреба (приоритетна спрямо циклична спрямо автоматична)

### „Проверката на състоянието на базата данни е неуспешна“

- Изпълнете `sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"`
- Ако резултатът е „ok“ — фалшива тревога, проверката на състоянието е прекалено строга
- Ако резултатът е друг — **спрете OmniRoute** и следвайте [ръководството за възстановяване след бедствие](./DATABASE_GUIDE.md#disaster-recovery)

### „Натоварването на heap паметта е критично“

```bash
# Проверка на текущата heap памет
node -e "console.log(process.memoryUsage())"

# Задействане на ръчно събиране на отпадъци (ако е зададено --expose-gc)
node --expose-gc -e "global.gc(); console.log(process.memoryUsage())"

# Намаляване на едновременните заявки (задава се от страницата Settings на таблото, а не чрез променлива на средата)
# Няма променлива на средата `MAX_CONCURRENT_REQUESTS` — конфигурирайте това в Settings → Concurrency.
```
