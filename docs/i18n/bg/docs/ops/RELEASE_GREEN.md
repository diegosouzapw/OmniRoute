## Проблемът, който това решава

**Пълният набор от проверки** (`.github/workflows/ci.yml` — unit shards, vitest, ratchets,
`package-artifact`, SonarQube, E2E) се изпълнява **само за PR за издание** (PR → `main`). PR-ите, насочени
към `release/**`, получават **бързите проверки** (`quality.yml`: засегнати според TIA тестове + проверка на типовете + lint)
и, при промени в кода, **информативно** production build. В резултат на това грешки, проявяващи се само при издание, могат
да се натрупват незабелязано в клона за изданието и **да избухнат на слоеве от по ~40 минути** при издаването,
една по една.

Фамилията „release-green“ съществува, за да **предвижда** тези грешки — да валидира еквивалента на пълния
набор от проверки **локално / извън процеса на издаване**, по всяко време, така че PR-ът за изданието да е
успешен още при първото си CI изпълнение.

> **Принцип без компромиси:** нищо от това не блокира участника. Не добавяме задължителна
> проверка, която проваля неговия PR. **Отклонението** (ratchets) е за поддържащия проекта, който да актуализира базовите стойности при издаването —
> то никога не е грижа на участника. Нито една част не **затваря** PR (присвояване на заслуги), нито
> **отслабва** тест, за да премине успешно.

## Фамилията (4 части) — и как всяка се изпълнява независимо

| Част                                                                      | Какво представлява                                                                                  | Кога да се изпълнява                                                 | Обхват                               |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------ |
| **`/green-prs`** (Решение A)                                              | Сканиране при поискване от поддържащия проекта на **опашката от отворени PR-и**                     | **Независимо, периодично** — и особено **преди** `/generate-release` | Цялата опашка от PR-и → `release/**` |
| **`/validate-release-green`** (Решение C — `npm run check:release-green`) | Механизъм за валидиране: възпроизвежда пълния набор от проверки спрямо клон ИЛИ кандидат за сливане | Независимо, по всяко време                                           | Конкретен клон или PR за сливане     |
| **`/babysit <PR#>`**                                                      | Довежда **текущия CI** на **един** PR до успешно състояние                                          | Независимо, за всеки отделен PR                                      | Един PR                              |
| **`nightly-release-green.yml`** (Решение D)                               | Автоматизиран нощен workflow; отваря issue при HARD неуспех                                         | Автоматично (cron)                                                   | Активният клон за изданието          |

**Кратък отговор на „това само за издания ли е?“:** **не.** `/green-prs` е проектиран да се
изпълнява **периодично, между изданията**. Независимото изпълнение е нормалният начин на употреба — изданието е просто
моментът, в който изпълнението му носи най-голяма полза.

## Консултативно изграждане от PR към издание

`quality.yml` вече включва `Build (advisory)` за PR-и с код, които не са чернови, и за клонове от опашката на Mergify.
То възпроизвежда процедурата за продукционно изграждане от `ci.yml`: Node 24, `npm-ci-retry`,
`check:node-runtime` и `npm run build` с `OMNIROUTE_USE_TURBOPACK=1`. Умишлено
не се качва артефакт от изграждането, защото никоя последваща задача за качество в този работен процес не използва такъв.
Премахнете `continue-on-error` след една седмица стабилни изпълнения за PR-и за издание, така че сигналът да се превърне
в блокираща проверка по пътя от PR към издание.

## Решение C — `npm run check:release-green` (двигателят)

Възпроизвежда валидация, еквивалентна на тази за издание, спрямо текущото работно дърво и класифицира всяка неуспешна проверка:

- **HARD** (проверка на типовете, грешки от lint, unit, vitest, db-rules, public-creds, незадължителен
  `package-artifact`) → **реален дефект**; `exit 1`. Коригира се в изходния клон (TDD, правило №18).
- **DRIFT** (**предупреждения** от eslint, когнитивна сложност, размер на файловете) → отклонение на праговете, натрупано
  по време на цикъла, **без вина на допринеслия участник**; то само се отчита и **базовите му стойности се актуализират от поддържащия
  при издаването**. DRIFT **никога** не променя кода за изход — следователно никога не блокира никого.

```bash
npm run check:release-green                 # текущ клон (работно дърво)
node scripts/quality/validate-release-green.mjs --json   # структуриран изход
node scripts/quality/validate-release-green.mjs --quick  # пропуска unit+vitest (само отклонения+проверка на типовете+lint)
node scripts/quality/validate-release-green.mjs --with-build  # включва package-artifact (бавно)
```

Само диагностицира и **отчита** (без автоматични корекции). Оркестрацията за коригиране до успешно състояние се намира в
`/green-prs` и `/review-prs`.

## Решение A — `/green-prs` (сканирането на опашката)

Процедура (обобщение — вижте умението `green-prs` за подробности):

1. **Инвентаризирайте** опашката от отворени PR-и спрямо активния клон за издание.
2. **Категоризирайте** всеки PR (приемлив / подходящ за отхвърляне / изисква намеса на автора) — тези за отхвърляне/изискващи намеса на автора се
   **отчитат, а не се затварят** (авторът решава).
3. За всеки приемлив PR, в **изолирано работно дърво** (правило №19), актуализирайте PR-а спрямо върха на клона за издание и изпълнете
   `npm run check:release-green`:
   - **HARD** → коригирайте **в клона на допринеслия участник** чрез съавторство (запазва статуса „Merged“ на автора),
     изпълнявайте отново, докато всички HARD проверки преминат успешно.
   - **DRIFT** → оставете го; базовите му стойности ще бъдат актуализирани при изданието.
4. **Представете** таблица PR × (присъда, HARD неуспехи, коригиран?, DRIFT, готов за издание сега?).

Може да **подготвя** опашката без сливане; слива само при изрична заявка — и никога не затваря PR.

## Препоръчителна периодичност

- Изпълнявайте **`/green-prs` периодично** (напр. ежеседмично) и **винаги преди
  `/generate-release`**.
- Запазете **`nightly-release-green.yml`** (Решение D) като непрекъснат сигнал: когато отвори
  issue за HARD неуспех, е време за сканиране.
- Използвайте **`/validate-release-green`** при необходимост, за да проверите клон или конкретен кандидат за сливане.
- Използвайте **`/babysit <PR#>`**, когато конкретен PR трябва да бъде доведен до успешно състояние в работещия CI.

## Връзка с изданието

- `/generate-release` извиква валидацията във **Фаза 0 (предварителна проверка)**: актуализира базовите стойности за DRIFT и коригира
  HARD неуспехите, преди да отвори PR-а за издание.
- `/review-prs` използва проверката за готовност за издание на етапа за вземане на решение за сливане (успешни проверки преди сливане).

Целта на всички компоненти е една и съща: **PR за издание с успешни проверки още при първото изпълнение на CI**, вместо преодоляване
на неуспехи на 40-минутни етапи в деня на издаването.
