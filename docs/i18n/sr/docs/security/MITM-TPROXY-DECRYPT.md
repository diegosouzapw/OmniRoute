TPROXY транспарентно дешифровање је OmniRoute-ов **5. режим хватања** за
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM стек. Он пресреће и **дешифрује** локални одлазни HTTPS саобраћај на Linux-у
користећи TPROXY језгра + рутирање засновано на правилима — **без** лажирања `/etc/hosts` и
**без** измене системских подешавања проксија на нивоу целог ОС-а. Погодан је за рад без графичког интерфејса
(нема DNS измена које треба очистити), а правила заштитног зида се аутоматски уклањају при поновном покретању.

За разлику од других режима хватања, TPROXY не захтева подешавање за сваки хост појединачно: он транспарентно
пресреће **произвољне** одредишне хостове на циљном порту, прекида TLS помоћу
сертификата крајњег ентитета који у ходу издаје за сваки SNI назив хоста, хвата дешифровану
размену и поново шифрује захтев ка оригиналном одредишту.

> **Само за Linux, само за root корисника, уз изричито омогућавање.** Овај режим захтева Linux, изворни додатак
> изграђен помоћу C ланца алата и могућност **CAP_NET_ADMIN** (обично root). Доступан је
> искључиво преко AgentBridge API-ја ограниченог на loopback и подразумевано је онемогућен. Поуздани
> MITM CA који може да потпише сертификат за било који хост представља моћну могућност — погледајте [§6 Безбедност](#6-security).

**Извор:** `src/mitm/tproxy/`
**API рута:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**Прекидач на контролној табли:** Traffic Inspector → трака са алаткама за режиме хватања → **"TPROXY дешифровање"** ⚠
**Такође погледајте:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 Шта је ово и када га користити

Сваки од остала четири режима хватања има одређено ограничење:

| Режим               | Како се саобраћај усмерава                      | Ограничење                                         |
| ------------------- | ----------------------------------------------- | -------------------------------------------------- |
| AgentBridge         | `/etc/hosts` DNS лажирање фиксног скупа хостова | само регистровани хостови IDE агента               |
| Прилагођени хостови | `/etc/hosts` DNS лажирање по хосту              | један унос по хосту; sudo за измену hosts датотеке |
| HTTP_PROXY          | `HTTP_PROXY`/`HTTPS_PROXY` окружење             | само апликације које поштују променљиву окружења   |
| Системски прокси    | Подешавања проксија ОС-а                        | мења глобално стање; захтева враћање измена        |

TPROXY транспарентно дешифровање уместо тога усмерава саобраћај на нивоу **језгра**. Оно
означава нове локалне одлазне TCP везе ка циљном порту (подразумевано `443`) у
ланцу `mangle OUTPUT`, затим `ip rule` преусмерава означене пакете ка локалној испоруци,
а при поновном уласку циљ `TPROXY` у `mangle PREROUTING` их прослеђује
**IP_TRANSPARENT** слушаоцу — који затим прекида TLS и хвата отворени текст.

Користите га када желите да хватате и дешифрујете саобраћај процеса који:

- комуницира са хостом који AgentBridge не региструје,
- не поштује `HTTP_PROXY`, и
- не желите да ометате изменом системског проксија.

Пошто се пресретање одвија у језгру, изворном процесу није потребна **никаква
измена конфигурације** — али процес мора да верује динамичком CA-у који OmniRoute
инсталира (погледајте [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 Захтеви

| Захтев              | Детаљи                                                                                                                                                                           |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ОС**              | Само Linux — **IP_TRANSPARENT** је опција сокета доступна искључиво на Linux-у. Учитавач враћа „недоступно“ на свакој другој платформи.                                          |
| **Привилегије**     | Могућност **CAP_NET_ADMIN** за прављење транспарентног сокета и примену правила `iptables`/`ip` — у пракси, покрените као root.                                                  |
| **Изворни додатак** | Мали N-API додатак (`src/mitm/tproxy/native/transparent.c`) мора бити изграђен или испоручен као унапред изграђена верзија. Погледајте [§3](#3-the-native-ip_transparent-addon). |
| **Модули језгра**   | `iptables` са подршком за `TPROXY`, `mangle` и подударање `mark` (проверено са језгром 6.8.0).                                                                                   |

**Постепено умањење функционалности:** ако неки захтев недостаје (систем није Linux, нема ланца алата,
додатак није изграђен), учитавач додатка (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
враћа `null` уместо да избаци изузетак. Статус режима пресретања тада пријављује
`available: false`, прекидач на контролној табли је **онемогућен** уз опис
„TPROXY дешифровање захтева Linux + root + изворни додатак“, а остатак
OmniRoute-а наставља да ради.

## §3 Изворни додатак IP_TRANSPARENT

Node-ов модул `net` не може да изврши `setsockopt(IP_TRANSPARENT)` _пре_ `bind()`, што
TPROXY захтева (у супротном језгро одбацује преусмерене пакете). Додатак
(`src/mitm/tproxy/native/transparent.c`, изграђен преко `binding.gyp`) је мали N-API
модул који излаже три функције, коришћене преко `transparentSocket.ts`:

| Функција додатка                      | Рад са сокетом                                                                                  | Користи се за                                                                           |
| ------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, враћа необрађени fd | транспарентни ослушкивач за пресретање (Node преузима fd преко `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | `setsockopt` **SO_MARK** на постојећем fd                                                       | спречавање петље (означавање сопствених сокета проксија)                                |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **пре** неблокирајућег `connect()`, враћа fd                           | поново шифровано прослеђивање ка узводном серверу (SYN носи ознаку)                     |

Оригинално одредиште се чита из `socket.localAddress`/`localPort` — TPROXY
га чува, тако да није потребна претрага преко **SO_ORIGINAL_DST**/NAT-а.

### Изградња додатка

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- Током `npm run build`, `scripts/build/build-tproxy-native.mjs` покреће `node-gyp
rebuild`. Ово је **само за Linux и није фатално** — недостатак ланца алата само оставља
  режим пресретања недоступним.
- `assembleStandalone.mjs` копира `build/Release/transparent.node` у
  самостални пакет; `transparentSocket.ts` га проналази и у односу на модул и у
  односу на cwd (`<cwd>/src/mitm/tproxy/native/...`).
- `build/` и `prebuilds/` су игнорисани у git-у — бинарна датотека се **изграђује, никада
  не отпрема у репозиторијум**.

Учитавач испробава, по редоследу приоритета:
`native/build/Release/transparent.node`, затим `native/prebuilds/transparent.node`
(оба у односу на модул и под `<cwd>/src/mitm/tproxy/`).

## §4 Динамички CA по SNI-ју и инсталатер складишта поверења

> **Ажурирање #6684:** статички AgentBridge сервер (`src/mitm/server.cjs`) сада
> користи исти образац архитектуре CA/leaf уместо једног статичког
> самопотписаног leaf сертификата. Користи **засебну** CA инстанцу
> (`src/mitm/cert/rootCa.ts`, сачувану у `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> и инсталира је у постојећи слот складишта поверења `omniroute-mitm.crt`
> (замењујући стари појединачни leaf сертификат у њему — није потребно чишћење
> двоструког поверења), који је потпуно одвојен од TPROXY-јевог сопственог слота
> `omniroute-tproxy-ca.crt` описаног у наставку.
> Нове AgentBridge инсталације аутоматски добијају CA модел; инсталација која
> већ верује старом статичком leaf сертификату наставља да га користи док
> оператер не омогући прелаз преко `MITM_ROOT_CA_ENABLED=true` (погледајте
> `src/mitm/cert/migration.ts`) — поуздани MITM CA који може да потпише leaf
> сертификат за **било који** хост знатно је моћнији од старог leaf сертификата
> са фиксним SAN-овима, па се прелаз никада не обавља неприметно за инсталацију
> која му већ верује.

Историјски гледано, статички AgentBridge MITM сертификат радио је само зато што
AgentBridge лажира DNS за **фиксни** скуп хостова (сада обједињен са моделом
описаним у наставку). TPROXY пресреће **произвољне** хостове, па његов слушалац
мора да представи важећи leaf сертификат за сваки SNI који клијент затражи —
исти захтев који AgentBridge сада има за цео скуп `MITM_TOOL_HOSTS` (9 уноса
алата), уместо само за 4 antigravity хоста.

### Динамички CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` покреће локални CA (заснован на зависности `selfsigned`) који:

- Генерише дуготрајни CA преко `generateMitmCa()` (CN `"OmniRoute MITM CA"`,
  рок важења од 10 година, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-битни RSA / SHA-256).
- На захтев издаје **leaf сертификат за свако SNI име хоста** преко
  `issueLeafCert()` (рок важења од 1 године, `subjectAltName` = SNI хост) и
  кешира по један `tls.SecureContext` за свако име хоста.
- Излаже `createSNICallback()` за сервер који терминира TLS (погледајте [§5](#5-how-decrypt-and-capture-work)).
- Може се конструисати са `existingCa` како би CA остао стабилан између поновних
  покретања (тако да складиште поверења не мора поново да се инсталира).

Приватни кључ CA **никада не напушта машину**.

### Инсталатер складишта поверења (`src/mitm/tproxy/caTrust.ts`)

Пресретнути клијент мора да верује динамичком CA-у, па покретање режима снимања
инсталира CA сертификат у складиште поверења оперативног система у
**наменски слот** — `omniroute-tproxy-ca.crt` (константа `TPROXY_CA_CERT_NAME`) —
који се чува одвојено од слота статичког MITM сертификата
(`omniroute-mitm.crt`), тако да никада не преписују један другог.

`installTproxyCa(caPem, sudoPassword?)` открива директоријум сидрених сертификата
дистрибуције (редом, прво онај у Debian стилу) и покреће одговарајућу команду
за освежавање:

| Директоријум сидрених сертификата           | Команда за освежавање    |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

При инсталацији се PEM прво смешта у привремену датотеку, затим се (са
повишеним привилегијама) извршава `mkdir -p` за директоријум сидрених
сертификата, `cp` копира припремљену датотеку у њега и на крају се покреће
команда за освежавање. `uninstallTproxyCa()` уклања само наменски слот
(остављајући статички MITM сертификат нетакнутим) и освежава складиште —
на системима који нису Linux не ради ништа.

Све привилеговане команде покрећу се преко `execFileWithPassword`
(`src/mitm/systemCommands.ts`) — `spawn` са **низовима аргумената, без shell-а,
без интерполације стрингова** (Строго правило #13). Када се процес извршава као
root (нпр. на VPS-у), циљна команда се покреће директно и лозинка није потребна;
на desktop систему који се не извршава као root, `sudoPassword` се прослеђује
преко `sudo -S` на stdin.

> Desktop `sudoPassword` се доставља у телу POST захтева ради ауторизације
> инсталације у складиште поверења; у потпуности се игнорише када се процес
> извршава као root.

## §5 Како функционишу дешифровање и хватање

Ток обраде (све унутар `src/mitm/tproxy/`):

```
локална апликација  ──TCP/443──▶  mangle OUTPUT означава везу (fwmark)
                                  ip rule → локална табела рутирања → lo
                                  mangle PREROUTING TPROXY → IP_TRANSPARENT слушалац (порт 8443)
                                      │  captureMode.ts: чита изворно одредиште из socket.localAddress
                                      ▼
                                  tlsCapture.ts:
                                    1. TLS-терминација КЛИЈЕНТА помоћу per-SNI leaf сертификата (dynamicCert)
                                    2. интерни http.Server рашчлањује дешифровани отворени текст
                                    3. хватање → globalTrafficBuffer.push() са source: "tproxy"
                                       (примењени sanitizeHeaders + maskSecret)
                                    4. прослеђивање, поново шифровано, ка изворном одредишту
                                       преко сокета означеног за заобилажење (connectMarked, спречавање петље)
                                      │
                                      ▼
                                  изворни узводни сервер (api.example.com)
```

- **TLS терминација** (`createTlsCaptureServer`): обавија сирови пресретнути
  сокет серверским `tls.TLSSocket` користећи SNI callback динамичког CA-а,
  а затим предаје дешифровани ток интерном `http.Server`-у (стандардни MITM
  трик за терминацију). Животни век сокета ограничен је вредношћу
  `MITM_IDLE_TIMEOUT_MS`, тако да заглављени тунел не може да исцрпи дескрипторе
  датотека.
- **Хватање** (`handleDecryptedRequest`): додаје `InterceptedRequest` са
  `source: "tproxy"`, почетним статусом `"in-flight"`, заглављима обрађеним помоћу
  `sanitizeHeaders()` и телима обрађеним помоћу `maskSecret()` пре него што уђу у
  бафер. Запис се затим ажурира одговором, величинама и кашњењем.
- **Поново шифровано прослеђивање** (`createForward` / `realForward`): поново шифрује
  саобраћај ка изворном одредишту. `rejectUnauthorized` подразумевано има вредност
  **`true`** (подразумевано безбедно) — сертификат узводног сервера проверава се
  у односу на SNI/Host који је клијент затражио, тако да прокси одбија управо оно
  што би одбио и изворни клијент.

### Спречавање петље (SO_MARK)

Пошто правила означавају нове локалне одлазне везе, **сопствено** поново шифровано
прослеђивање проксија обично би било поново пресретнуто — што би створило
бесконачну петљу. Путања прослеђивања то спречава ознаком сокета за заобилажење
(**SO_MARK**):

- `realForward` отвара свој сокет ка узводном серверу помоћу
  `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` — `DEFAULT_BYPASS_MARK = 0x539` —
  што поставља **SO_MARK** **пре** `connect()`, тако да SYN прослеђивања носи
  ознаку за заобилажење.
- Правило `mangle OUTPUT` изузима везе које већ носе ознаку за заобилажење
  (`-m mark ! --mark <bypassMark>`), тако да прослеђивање проксија **није**
  поново означено и не улази поново у TPROXY.

> Напомена о имплементацији: сокет означен за заобилажење мора бити постављен у
> `createConnection` агента (`https.request({ createConnection })` се неприметно
> игнорише када је агент присутан), иначе би прослеђивање отворило неозначен сокет
> и петља би се вратила. Ова исправка за спречавање петље потврђена је e2e тестовима.

## §6 Безбедност

| Контрола                                        | Детаљи                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API доступан само преко loopback интерфејса** | `/api/tools/agent-bridge/tproxy` је обухваћен префиксом `/api/tools/agent-bridge/` у `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`). Ограничавање на loopback примењује се **пре** аутентификације (Строга правила #15 + #17) — процурели JWT преко тунела не може да покрене TPROXY пресретање, које примењује `iptables` правила и инсталира CA у складиште поузданих сертификата путем подређених процеса. |
| **Наменско место за CA**                        | Динамички CA се инсталира као `omniroute-tproxy-ca.crt` и никада не преписује статички MITM сертификат.                                                                                                                                                                                                                                                                                                                     |
| **CA кључ никада не напушта хост**              | `DynamicCertStore` чува CA кључ у меморији; кључ се не извози.                                                                                                                                                                                                                                                                                                                                                              |
| **Маскирање тајни**                             | `maskSecret()` над телима захтева/одговора и `sanitizeHeaders()` над заглављима извршавају се **пре** `globalTrafficBuffer.push()`.                                                                                                                                                                                                                                                                                         |
| **Без интерполације у љусци**                   | Све `iptables`/`ip` команде и команде за складиште поузданих сертификата извршавају се путем `execFile`/`execFileWithPassword` са низовима аргумената (Строго правило #13).                                                                                                                                                                                                                                                 |
| **Провера узводног сертификата**                | Поново шифровано прослеђивање подразумевано проверава узводни сертификат (`rejectUnauthorized: true`).                                                                                                                                                                                                                                                                                                                      |
| **Санитизација грешака**                        | Одговори руте са грешком пролазе кроз `sanitizeErrorMessage()` (Строго правило #12).                                                                                                                                                                                                                                                                                                                                        |

**MITM CA представља моћну могућност.** CA коме оперативни систем верује и који може да потпише сертификат за било који
хост значи да се све што OmniRoute пресретне може дешифровати. Ова могућност је заштићена
изричитим, искључиво локалним режимом TPROXY пресретања, подразумевано је искључена, а ставка у
складишту поузданих сертификата уклања се када зауставите режим.

## §7 Трансакциона примена / поништавање заштитног зида

Пад никада не сме да остави `mangle` правило или застарелу руту. Градитељ команди
(`src/mitm/tproxy/commands.ts`) и покретач (`src/mitm/tproxy/setup.ts`) гарантују да је
**поништавање тачна инверзија примене, обрнутим редоследом**.

`applyTproxy(cfg)` покреће команде за примену редом; при **било ком** неуспеху покреће
потпуно `revertTproxy(cfg)` по принципу најбољег покушаја и поново прослеђује грешку — тако да је заштитни зид или
у потпуности примењен или у потпуности враћен, никада делимично примењен. `revertTproxy(cfg)` покреће
инверзне команде обрнутим редоследом и занемарује неуспехе (идемпотентно — безбедно је позвати га
безусловно, нпр. из AgentBridge `repairMitm()` чишћења).

`validateTproxyConfig(cfg)` се покреће пре било које команде: портови морају бити `1–65535`,
`mark`/`routeTable`/`bypassMark` морају бити позитивни цели бројеви, а `bypassMark` мора
да се разликује од `mark` (спречавање петље).

### Команде за примену (редом)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Поништавање их брише обрнутим редоследом: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> Поступак је заснован на ланцу **OUTPUT** зато што MITM случај употребе обухвата _локални_ одлазни
> саобраћај (апликације на истом хосту), који TPROXY само у `PREROUTING` не
> види — `PREROUTING` види само прослеђени саобраћај. Ланац `OUTPUT` означава нове
> локалне везе, `ip rule` их преусмерава на локалну испоруку (`lo`), а
> `PREROUTING` их затим додељује транспарентном слушаоцу.

## §8 Конфигурација

Захтев за покретање (`POST /api/tools/agent-bridge/tproxy`) прихвата следећа
поља, која проверава `StartTproxyBodySchema` (`tproxy/route.ts`). Сва су опциона
и, ако нису наведена, користе своје подразумеване вредности:

| Поље             | Тип                | Подразумевано | Напомене                                                                                                                         |
| ---------------- | ------------------ | ------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`         | Одредишни TCP порт који се транспарентно пресреће                                                                                |
| **mark**         | int (≥1)           | `0x2333`      | Ознака заштитног зида постављена у `OUTPUT`, коју подударају `ip rule` + `PREROUTING`                                            |
| **onPort**       | int (1–65535)      | `8443`        | Порт за који се везује транспарентни (**IP_TRANSPARENT**) слушалац                                                               |
| **routeTable**   | int (≥1)           | `233`         | Идентификатор табеле усмеравања заснованог на правилима која садржи руту `local 0.0.0.0/0`                                       |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`       | Ознака заобилазног сокета (**SO_MARK**) коју прокси поставља на сопствене узводне везе; изузета је у `OUTPUT` (спречавање петље) |
| **sudoPassword** | string             | —             | Само за десктоп системе без root приступа: одобрава инсталацију у складиште поузданих сертификата; игнорише се када је root      |

За TPROXY **не постоје променљиве окружења** — сва конфигурација се задаје путем
POST тела или горенаведених подразумеваних вредности.

## §9 Омогућавање из Инспектора саобраћаја

1. Отворите **Инспектор саобраћаја** (`/dashboard/tools/traffic-inspector`).
2. На траци са алаткама за режиме снимања пронађите дугме **„TPROXY дешифровање“** ⚠
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Ако је **онемогућено** уз опис „TPROXY дешифровање захтева Linux + root +
     нативни додатак“, нативни додатак није доступан на овом хосту (није Linux,
     нема ланца алата или додатак није изграђен). Погледајте [§2](#2-requirements) и [§3](#3-the-native-ip_transparent-addon).
3. Кликните на дугме. Оно позива `POST /api/tools/agent-bridge/tproxy` преко
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`), што:
   прави динамички CA, отвара транспарентни ослушкивач, примењује правила заштитног
   зида и инсталира CA у складиште поузданих сертификата оперативног система.
4. Док је покренут, прекидач постаје ћилибарне боје и приказује тренутни број пресретања
   (`· <interceptCount>`). Пресретнути захтеви се појављују на листи захтева са
   `source: "tproxy"`.
5. Кликните поново да бисте зауставили — `DELETE /api/tools/agent-bridge/tproxy` преко
   `stopTproxyCaptureMode()` затвара ослушкивач, деинсталира CA и поништава
   правила заштитног зида.

Статус режима снимања (покренут / доступан / број пресретања / порт ослушкивача) долази
из `GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` у
`src/mitm/tproxy/captureManager.ts`). Истовремено може бити покренута само **једна** TPROXY сесија —
покушај покретања друге одбија се поруком „TPROXY режим снимања је већ покренут“.

## §10 Решавање проблема

### Прекидач је онемогућен

Нативни додатак не може да се учита. Проверите: да ли користите Linux, да ли сте изградили додатак
(`npm run build:native:tproxy`) и да ли процес може да учита `transparent.node`.
`isTransparentSocketAvailable()` контролише прекидач; `GET /api/tools/agent-bridge/tproxy`
враћа `available: false` када додатак недостаје.

### Ништа се не снима

- Проверите да ли се пресретнути процес заиста повезује на конфигурисани `dport`
  (подразумевано `443`).
- Проверите да ли процес верује динамичком CA-у. CA је инсталиран као
  `omniroute-tproxy-ca.crt`; апликације са сопственим складиштем поузданих сертификата (Firefox/Chrome NSS)
  можда захтевају да се сертификат дода и тамо.
- Покрените AgentBridge **Дијагностику**, односно самотестирање (погледајте
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) ради провере поузданости сертификата / стања
  сервера.

### Заостала правила заштитног зида након пада

`revertTproxy()` је тачна супротност примене и идемпотентан је. Заустављање
режима поништава правила; ако је OmniRoute прекинут усред сесије, употребите AgentBridge
радњу **Поправка** (`POST /api/tools/agent-bridge/repair`) да бисте поништили заостало системско
стање (DNS лажирање, корени CA, системски прокси). TPROXY `mangle` правила и рута такође
се аутоматски бришу при поновном покретању система.

### Бесконачна петља / прокси пресреће сопствено прослеђивање

Ово је случај спречавања петље. Проверите да ли се `bypassMark` разликује од `mark` (валидација
ово обезбеђује) и да ли прослеђивање користи `connectMarked` (користи га у `realForward`).
Погледајте [§5 Спречавање петље](#anti-loop-so_mark).
