Од v3.8.49 (WS3.2/WS3.4 плана квалитета/брзине), подразумевана путања спајања
прегледаних PR-ова у `release/vX.Y.Z` јесте **Mergify ред за спајање** (`.mergify.yml`);
**ручни воз за спајање** документован у наставку представља РЕЗЕРВНУ ОПЦИЈУ — користи се током инцидената,
замрзавања издања или ако се Mergify Open Source план икада промени.

## Подразумевана путања: Mergify ред

1. PR је прегледан/озелењен у кампањама и одобрен путем власникове ⭐
   контролне тачке пре спајања (извештај + одлука за сваку ставку — погледајте `/merge-prs`, корак 0.75).
2. Власник (или сесија која поступа на основу одлуке власника) примењује ознаку **`queue`**.
   Ознака ЈЕСТЕ одобрење за спајање; Mergify га само извршава.
3. Mergify проверава PR-ове у реду **серијски** (један по један) у односу на брзе контролне тачке
   и спаја их (squash). Груписање + аутоматска бисекција доступни су у плаћеном Mergify пакету
   („Cannot use Merge Queue batch“ у бесплатном плану, #7220), па `.mergify.yml` не поставља
   `batch_size`; груписање остаје задатак ручног ланца спајања у наставку. PR чије
   провере и даље нису завршене након `checks_timeout` (240 минута = 2× измерени p95 за
   `quality.yml`) уклања се из реда уместо да блокира ред.
4. Након спајања, континуирани ток рада за проверу исправности издања проверава нови врх при push догађају
   и отвара проблем за приписивање одговорности ако је комбинација довела до регресије (без аутоматског враћања измена).

Заштитна правила (одражавају строга правила #21/#22 из `CLAUDE.md`):

- **Замрзавање издања је активно** → НЕМОЈТЕ означавати PR-ове који циљају замрзнуту грану; прво им
  промените циљ на активну грану `release/vX+1`.
- **PR друге сесије на којем је рад у току** → никада га немојте означавати; само власничка сесија ставља
  сопствени рад у ред.
- Разлике које садрже само тестове и PR-ови са ознаком `hotfix` већ покрећу скраћени CI (погледајте
  `RELEASE_CHECKLIST.md` → Hotfix Fast-Lane); услови реда прихватају било који
  скуп провера који је заиста покренут (`#check-failure=0` + `#check-pending=0`).

## Резервна опција: ручни воз за спајање

Користи се када ред није доступан. Овим се формализује пракса којом су током циклуса v3.8.47
обрађена 33 PR-а за један дан:

1. **Саставите групу** (приближно 10–30 прегледаних и одобрених PR-ова). Проверите `linked:` колизије
   (исти `tap.testFiles`, исти делови CHANGELOG-а) и обрадите их редом.
2. **Проверите ЈЕДНОМ**: у изолованом worktree-ју заснованом на врху гране издања локално спојите све
   врхове грана из групе, а затим покрените скуп провера еквивалентан оном за издање
   (`npm run check:release-green`, а пре издања додајте `--with-build`).
   `scripts/release/merge-train.sh <base> <PR#>…` аутоматизује кораке 1–2 (конфликтни
   PR-ови се избацују, а воз наставља). Потпуни режим покреће `npm run test:unit` — извршилац
   подешен за машину (`--test-concurrency=20`), **а не** два узастопна CI сегмента са по 4 језгра,
   због којих је доминантна фаза користила око 25% машине са 16 језгара (исправљено
   2026-07-18). `--fast` (пражњење великих возова током дана, власник одобрио 2026-07-18)
   задржава сваку статичку контролу + vitest, али покреће само node:test датотеке које су изменили
   укључени PR-ови; ПОТПУНИ скуп и даље мора да се покрене најмање једном дневно над
   акумулираним врхом (један воз без `--fast`).
3. **Успешно** → спојите PR-ове редом (поново проверавајући `state,headRefOid` пре сваког —
   PR чији се врх померио враћа се на преглед). Докажите да је нето разлика сваког спајања
   искључиво промена тог PR-а (без аутоматског разрешавања које поништава измене: проверите `git diff --stat`
   ради брисања изван опсега).
4. **Неуспешно** → поделите групу на половине (проверите сваку половину), уместо поновне провере
   сваког PR-а појединачно; вратите проблематични PR у ред за преглед заједно са доказима.
5. **Никада**: немојте спајати у замрзнуту грану током замрзавања; немојте користити `git stash` нигде;
   немојте масовно поново покретати CI у нади да ће неуспех нестати (правило: неуспех је информација).

## Нивои (зашто је ред безбедан само са брзим контролама)

- **По PR-у** (брзе контроле из quality.yml): тестови на које утиче TIA + потпуни јединични тестови у 4 сегмента +
  vitest + скуп lint провера + провера типова + интегритет документације/евиденције измена.
- **По групи/врху** (континуирана провера исправности издања): `--quick` ОБАВЕЗНЕ контроле при сваком push-у на
  грану издања; потпуне провере `--with-build --full-ci` 3× дневно.
- **По издању** (ci.yml на PR-у издања): комплетна матрица, укључујући E2E ×9,
  артефакт пакета + основну проверу покретања tarball-а, покривеност/прагове.

Ништа се не проверава мање него раније — захтевне провере се само извршавају по групи/врху
уместо по PR-у, чиме се уклања O(N) циклуса повратне комуникације.

## Предуслови за `merge-train.sh` у свежем checkout-у

Скрипта покреће **предпроверу** која се одмах прекида при грешци над кореним checkout-ом (пре било каквог рада
у worktree-ју), тако да неисправна инсталација никада не може да се представи као неуспешан воз:

1. `npm ci`, а затим покрените `bun` postinstall који npm блокира:
   `(cd node_modules/bun && node install.js)` — у супротном `check:provider-consistency`
   и `check:known-symbols` (оба користе `bun scripts/…`) не успевају и на возу И на основи,
   без реда који наводи прекршај.
2. Не сме постојати заостали `node_modules/node_modules` (дуплирано стабло зависности; React се учитава двапут,
   а UI vitest скупови одмах не успевају).
3. `node_modules/.bin/tsc` мора бити присутан и извршив (у делимичној инсталацији недостаје).

Воз покреће обавезни `npm run check:cycles:ratchet`; самостални `npm run check:cycles`
је информативан (наводи SCC-ове и завршава се кодом различитим од нуле чак и на исправној основи).
