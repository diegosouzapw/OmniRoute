Користите овај водич да изаберете најмању поуздану развојну петљу за pull request. Он не
замењује документе о архитектури и безбедности за одређене области који су наведени у наставку; он повезује сваки уобичајени
тип измене са његовим уговорима, циљаним проверама и CI покривеношћу.

## Путања коју прати свака измена

1. **Изаберите основу пре уређивања.** Пронађите највишу активну грану `release/v*` и направите грану од
   њеног врха. Циљајте ту грану, а не `main`. Ако је замрзавање издања активно, немојте циљати замрзнуту
   грану; користите следећи активни циклус описан у
   [Моделу гранања и издавања](BRANCHING_MODEL.md).
2. **Наведите уговоре.** Идентификујте сваки каталог, шему, генерисани артефакт, јавни API или кориснички
   интерфејс на који измена утиче. Табела у наставку даје минимални почетни скуп.
3. **Напишите или ажурирајте циљане тестове.** Измене продукционог кода у `src/`, `open-sse/`, `electron/` или
   `bin/` захтевају аутоматизовани тест у истом PR-у. Покрените најмањи скуп тест-датотека који доказује
   понашање, а затим наведене циљане контроле.
4. **Препустите CI-ју покретање широке матрице.** Комплетне јединичне партиције, Vitest, праг покривености и
   продукционо састављање покрећу се у PR-у. Покрените широк скуп тестова локално само када циљани неуспех указује на
   шири утицај или када измена обухвата више подсистема.
5. **Ускладите измене пре прегледа.** Добавите активну основну грану, прегледајте њене нове commit-ове и своју разлику у односу
   на њу, а затим урадите rebase или merge основне гране у складу са током рада за доприносиоце. Решите сукобе у генерисаним датотекама
   и каталозима полазећи од њиховог извора, поново их генеришите, поново покрените циљану петљу и потврдите да
   PR и даље циља активну грану издања.
6. **Забележите доказе.** У PR шаблону наведите покренуте команде, сваку додату или измењену тест-датотеку,
   миграције или заставице функција и све валидације које се обављају само у CI-ју и још увек су на чекању.

## Препоручене путање према типу измене

Команде у наставку представљају минималне циљане провере, а не дозволу да прескочите тест који непосредно покрива
понашање које сте изменили.

### Провајдер

**Уговори**

- Дефиниција провајдера у `src/shared/constants/providers/` и њено састављање у
  `src/shared/constants/providers.ts`.
- Модели и могућности у `open-sse/config/providerRegistry.ts` или његовим издвојеним датотекама регистра.
- Избор извршиоца/преводиоца, OAuth конфигурација или конфигурација API кључа, ресурси контролне табле и генерисана
  референца провајдера када је применљиво.
- Јавни акредитиви морају да користе `resolvePublicCred()`; одговори са грешкама морају да користе дељене помоћне функције за
  санитизацију грешака. Погледајте `docs/security/PUBLIC_CREDS.md` (git; не компајлира се у `/docs`) и
  [Санитизацију грешака](../security/ERROR_SANITIZATION.md).

**Циљана петља**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # када се каталог промени; commit-ујте генерисану разлику
npm run lint
```

Такође тестирајте сваку обухваћену породицу захтева: ћаскање, Responses, слике, угнежђивања, аудио или видео.
Прегледајте генерисане каталошке и референтне разлике као измене уговора; немојте их прихватати без провере.

### Усмеравање

**Уговори**

- Јавне вредности стратегија и метаподаци корисничког интерфејса у `src/shared/constants/routingStrategies.ts`.
- Отпремање и редослед у `open-sse/services/combo.ts` и `open-sse/services/combo/`.
- Combo шеме, перзистенција, стање отпорности, могућности модела и API/UI контроле.
- [Auto-Combo механизам](../routing/AUTO-COMBO.md) и документација о отпорности када се понашање промени.

**Циљана петља**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # измене стратегије или отпремања
npm run check:known-symbols      # измене регистрације стратегије
npm run lint
```

Локално користите детерминистичке тестове са симулираним узводним сервисом. Живи combo smoke тестови захтевају акредитиве и
обављају се ручно; они нису замена за CI.

### UI / UX

**Уговори**

- Next.js границе рута/страница и дељених компоненти у `src/app/` и
  `src/shared/components/`.
- Облици API одговора, стања учитавања/празног садржаја/грешке, понашање тастатуре и читача екрана,
  прилагодљив распоред, теме и проширење локализације.
- Изворни енглески UI текстови у `src/i18n/messages/en.json`; немојте директно уносити нови текст намењен корисницима у код.

**Циљана петља**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Покрените апликацију за измене интеракције или визуелног приказа и проверите и уске и широке приказе. CI покреће
продукционо састављање и шире скупове тестова; визуелно понашање и даље захтева циљани тест компоненте, Playwright,
или документовану ручну проверу која одговара измени.

### i18n

**Уговори**

- `src/i18n/messages/en.json` је извор за UI; `config/i18n.json` је извор за локализације.
- CLI каталози се налазе засебно у `bin/cli/locales/`.
- Сачувајте ICU чуваре места и ознаке без икаквих измена. Немојте преводити називе производа/провајдера/модела,
  називе протокола и заглавља, команде, идентификаторе кода/JSON-а, URL-ове, променљиве окружења или
  заштићене термине као што су `OmniRoute`, `OAuth`, `MCP` и `A2A`. Тренутна изворна листа је
  `scripts/i18n/glossary/protected-terms.json`.

**Циљана петља**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # када се CLI текстови/каталози промене
npm run lint
```

Ово су смернице за постојећи систем, а не позив за проширивање његових алата или модела кључева.
Нека i18n закрпе буду прецизне и ограничене док се пројектује заменски систем. Немојте покретати команде за превођење
које позивају спољне сервисе осим ако задатак изричито захтева генерисане преводе и
ако сте прегледали насталу разлику.

### CLI

**Уговори**

- Јавне команде и заставице у `bin/cli/`, генерисане API команде, излазни кодови, stdout/stderr и
  облици JSON излаза, понашање конфигурације/окружења и датотеке укључене у пакет.
- CLI ниске намењене корисницима морају да користе CLI i18n слој, а каталози `en`/`pt-BR` морају да остану усклађени.
- Задржите Node као подржано извршно окружење и уговор објављене бинарне датотеке.

**Усмерена петља**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # измене генерисаног/обједињеног CLI-ја
npm run check:pack-policy     # измене површине пакета
npm run lint
```

Користите тачну команду у привременом директоријуму за податке када понашање зависи од рашчлањивања, датотека или излазног
статуса. CI обавља шире провере артефаката пакета и екосистема.

### База података

**Уговори**

- Доменски модули у `src/lib/db/`; директно увозите одређене модуле (стари слој за поновни извоз `localDb.ts` је уклоњен).
- Нумерисане, идемпотентне SQL миграције у `src/lib/db/migrations/`, безбедност трансакција, понашање при надоградњи,
  индекси и сваки позивалац на који шема утиче.
- Руте и руковаоци никада не извршавају сирови SQL директно.

**Усмерена петља**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

При додавању миграције тестирајте и нову базу података и надоградњу са претходне шеме. Тестови базе података
морају да затворе ручице и позову `resetDbInstance()` током чишћења. Покрените `npm run test:bun:db` само када
се промени путања Bun адаптера која се користи по принципу најбољег могућег резултата; Node остаје меродаван.

### Изградња / примена

**Уговори**

- Корени манифести и манифести радних простора/датотека закључавања, `scripts/build/`, Next.js самостално склапање, садржај
  пакета `dist/`, Electron метаподаци платформе, CI токови рада и контролни маркери примене.
- Подржани опсези верзија Node-а и употреба Bun-а са листе дозвољених у `CLAUDE.md` морају да остану непромењени.
- Артефакти изградње остају ван праћења; примењују се правила за зависности, лиценце, токове рада и пакете.

**Усмерена петља**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # измене зависности или датотеке закључавања
npm run check:pack-policy      # измене површине објављеног пакета
npm run lint
```

Користите `npm run build` локално само када измена утиче на компилацију, самостално склапање, ресурсе
или обједињавање извршног окружења. Користите `npm run build:release` само за проверу издања/примене. CI изградња је
коначни сигнал за више платформи; измене Electron-а специфичне за платформу захтевају одговарајућу усмерену изградњу
или доказ основне провере.

## Локални циклус кандидата

Тестови изворног кода не могу доказати да се упаковани артефакт успешно покреће: спискови за паковање, уклоњене зависности
и изворне бинарне датотеке отказују тек када се tarball инсталира и покрене. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) представља локални део тока једнократне изградње / валидације / промовисања из
RFC #8084: гради једног кандидата, валидира управо тај артефакт, промовише га преименовањем
директоријума и враћа га на претходну верзију када промовисани слот не прође проверу исправности.

```bash
npm run dev:candidate -- run --dry-run --json  # прикажи план, не мењај ништа
npm run dev:candidate -- run                   # изгради + валидирај + промовиши, аутоматски врати уназад
npm run dev:candidate -- build                 # npm pack + инсталирање у _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # покрени на слободном порту, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # замени current и previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # поново употреби tarball изграђен другде (CI)
```

- **Изградите једном.** `build` пакује тренутно стабло (потребан му је `dist/server.js`, зато прво покрените
  `npm run build:release`) или копира `--from-tarball`, а затим инсталира tarball у
  изоловани npm префикс, јер tarball не садржи `node_modules`. ID је скраћени `HEAD`
  SHA (`-dirty` када стабло има локалне измене) или `tgz-<sha256>` за tarball. Чист ID који
  је већ изграђен поново се користи уместо поновне изградње; проследите `--force` да бисте га поново изградили.
- **Валидирајте пакет, а не изворни код.** `validate` покреће инсталирани CLI
  (`serve --port <free port>`) са новим `DATA_DIR=<candidate>/data`, лажним тајнама, док су
  операторове вредности `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` и `INITIAL_PASSWORD` уклоњене из
  окружења, тако да проверава понашање нове инсталације без кључа на loopback интерфејсу. Чека да
  `GET /api/health` врати 200, захтева да `GET /v1/models` врати 200, зауставља групу процеса
  и бележи исход у `validation.json` заједно са хешом tarball датотеке.
- **Промовишите исти артефакт.** `promote` одбија кандидата који нема успешну валидацију за
  хеш свог тренутног tarball-а. Подразумевани активни слот је `_artifacts/candidate/current`; `--target <dir>`
  бира други директоријум на истом систему датотека, а његов претходни слот је `<dir>.previous`.
  Свако преименовање је атомично, а отказ током поступка поништава већ обављена преименовања.
- **Вратите претходну верзију.** `run` поново валидира промовисани слот и замењује `current` и `previous`
  назад ако та провера не успе. Кандидат који не прође прву валидацију никада се не промовише.

Све се уписује у gitignored директоријум `_artifacts/candidate/`; постојећа OmniRoute
инсталација и њен директоријум података никада се не мењају. Промовисани CLI се налази у
`_artifacts/candidate/current/prefix/bin/omniroute`; када га користите, покрените га са сопственим `DATA_DIR`.
Излазни кодови: `0` успех, `1` неуспешна валидација или промовисање, `2` грешка при употреби или недостајућа изградња.

## Локална петља у односу на CI

| Покренути локално за сваку измену                                                       | CI пружа шири сигнал                                                                |
| --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Директни тестови понашања и горенаведене провере категорија                             | Паралелизовани комплет свих јединичних тестова и серијски тестови                   |
| `npm run lint`                                                                          | Vitest скупови тестова и прагови покривености/квалитета                             |
| Провера типова или изградња само када то захтева уговор на који измена утиче            | Продукциона изградња и провере безбедности, документације, зависности и PR смерница |
| Ручне интерактивне/директне провере само када аутоматизација не може да докаже понашање | Међупословна интеграција и провере платформи конфигурисане током рада               |

Успешна фокусирана петља представља доказ о измењеном уговору, али не и потврду да ће неповезане CI провере
проћи. С друге стране, немојте да свака локална измена чека на комплетну матрицу репозиторијума.

## Контролна листа за усклађивање

Пре него што затражите преглед:

- Потврдите да је основна грана PR-а и даље највиша активна грана `release/v*`.
- Преузмите ту основну грану и прегледајте измене које су у њу укључене откако сте направили своју грану.
- Прегледајте `git diff <active-base>...HEAD` ради случајних или генерисаних непотребних измена.
- Решите конфликте у каталогу и генерисаним документима ажурирањем извора и поновним генерисањем излаза.
- Након усклађивања поново покрените сваки фокусирани тест/проверу наведену у опису PR-а.
- Никада немојте слабити тврдње нити уклањати обавезне тестове само да бисте се прилагодили помереној основној грани.

За правила о замрзавању издања и промени циљне гране погледајте
[Модел гранања и издавања](BRANCHING_MODEL.md). За комплетан списак CI провера погледајте
[Референца провера квалитета](../architecture/QUALITY_GATES.md).
