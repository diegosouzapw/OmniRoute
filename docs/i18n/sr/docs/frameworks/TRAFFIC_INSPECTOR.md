Traffic Inspector је уграђени OmniRoute алат за отклањање грешака у HTTPS саобраћају — алат налик Charles Proxy / mitmweb / HTTP Toolkit који је **свестан LLM-ова** и **свестан агената**. Налази се на `/dashboard/tools/traffic-inspector` и прима саобраћај уживо из највише 5 истовремених извора снимања.

**Локација на контролној табли:** `/dashboard/tools/traffic-inspector`
**Група на бочној траци:** Алатке (после AgentBridge)
**Такође погледајте:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge је режим снимања 1.

### Архитектура у једном пасусу

`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) је дељени кружни бафер у меморији (подразумевано 1000 уноса, подесиво преко `INSPECTOR_BUFFER_SIZE`). Сви извори снимања уписују у њега путем `push()`. Бафер класификује сваки унос користећи `kindDetector.ts` (утврђује да ли је у питању LLM захтев), израчунава `contextKey` (SHA-256 отисак системског упита) и емитује га свим WebSocket претплатницима путем `globalTrafficBuffer.subscribe()`. Контролна табла се повезује путем `GET /api/tools/traffic-inspector/ws` и по повезивању прима снимак стања, након чега следе догађаји `new`/`update`/`clear`.

## §2 Режими снимања

Traffic Inspector подржава **5 истовремених извора снимања**. Сваки се може независно укључити или искључити. Поље `source` у сваком објекту `InterceptedRequest` (`src/mitm/inspector/types.ts`) има једну од вредности `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"` или `"tproxy"`.

### Режим 1 — AgentBridge (подразумевано, увек укључен)

**Извор:** AgentBridge обрађивачи (`src/mitm/handlers/base.ts`)
**Механизам:** Сваки позив `intercept()` у `MitmHandlerBase` позива `hookBufferStart()` пре прослеђивања и `hookBufferUpdate()` по завршетку. Није потребно никакво додатно подешавање — ради чим се AgentBridge покрене.
**Обухват:** 9 IDE агената конфигурисаних у AgentBridge-у
**Напомена:** Поље `source` у `InterceptedRequest` = `"agent-bridge"`

### Режим 2 — Прилагођени хостови (DNS преусмеравање)

**Извор:** Кориснички дефинисана листа хостова (табела `inspector_custom_hosts`)
**Механизам:** Додавањем хоста преко корисничког интерфејса додаје се `127.0.0.1 <host>` у `/etc/hosts` (захтева sudo). Постојећи AgentBridge MITM сервер (порт 443) динамички генерише SNI сертификат за нови хост.
**Обухват:** Свака апликација која користи додати хост — није потребна промена конфигурације апликације
**Напомена:** `source` = `"custom-host"`

Примери употребе:

- Надгледање `api.openai.com` из Python скрипти
- Отклањање грешака за `my-internal-llm.company.com`
- Снимање саобраћаја са мобилних уређаја на истој мрежи (путем ARP лажирања — напредно)

### Режим 3 — HTTP_PROXY слушалац (порт 8080)

**Извор:** Апликације које користе променљиве окружења `HTTP_PROXY`/`HTTPS_PROXY`
**Механизам:** Секундарни слушалац на порту 8080 (`src/mitm/inspector/httpProxyServer.ts`) који функционише као стандардни експлицитни HTTP/HTTPS прокси. Прихвата `CONNECT` тунеле (HTTPS) и директне HTTP захтеве.
**Обухват:** Свака апликација која поштује променљиву окружења `HTTP_PROXY` — без DNS измена и без sudo
**Напомена:** `source` = `"http-proxy"`

```bash
# Брзо снимање за једну команду:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# Трајно снимање у сесији командног окружења:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**TLS ограничење:** HTTPS `CONNECT` тунели се подразумевано снимају само као метаподаци (хост, порт, временски подаци) — TLS тело се не дешифрује. Укључите опцију „Дешифруј HTTPS у прокси режиму“ (захтева изричито укључивање и да AgentBridge сертификат буде означен као поуздан) за потпун преглед тела.

**Сукоб портова:** Ако је порт 8080 заузет, AgentBridge враћа 409 са структурисаном грешком. Промените порт путем променљиве окружења `INSPECTOR_HTTP_PROXY_PORT`.

### Режим 4 — Системски прокси (напредно, захтева изричито укључивање)

**Извор:** Подешавања проксија на нивоу оперативног система (примењују се на све апликације на рачунару)
**Механизам:** Користи API-је оперативног система за преусмеравање целокупног HTTP/HTTPS саобраћаја кроз HTTP_PROXY слушалац:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **Обухват:** Свака апликација на рачунару која поштује системска подешавања проксија
  **Напомена:** `source` = `"system-proxy"`

**Безбедносни механизми:**

- Тајмер за аутоматско искључивање (подразумевано 30 минута, може се конфигурисати путем `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES`)
- Претходно стање системског проксија чува се у бази података и враћа приликом поништавања
- Контролна табла приказује упит „Враћање системског проксија“ ако корисник напусти страницу док је прокси активан
- Кориснички интерфејс приказује ознаку `⚠ Напредно` + експлицитно поље за потврду

### Режим 5 — TPROXY транспарентно дешифровање (Linux, root, захтева изричито укључивање)

**Извор:** TPROXY језгра + усмеравање засновано на правилима (`src/mitm/tproxy/`)
**Механизам:** Означава нове локалне одлазне TCP везе ка циљном порту (подразумевано `443`) у `mangle OUTPUT`, затим `ip rule` преусмерава означене пакете на локалну испоруку, а циљ `TPROXY` у `mangle PREROUTING` прослеђује их транспарентном (**IP_TRANSPARENT**) слушаоцу (подразумевани порт `8443`). Слушалац прекида TLS помоћу крајњег сертификата који динамички CA издаје **на захтев за сваки SNI назив хоста**, снима дешифровану размену и прослеђује поново шифровани захтев првобитном одредишту.
**Обухват:** **Произвољни** одредишни хостови на циљном порту — без лажирања `/etc/hosts`, без променљиве окружења `HTTP_PROXY` и без измене системског проксија. Пресретнутом процесу није потребна промена конфигурације, али мора да верује динамичком CA-у.
**Напомена:** `source` = `"tproxy"`

**Захтеви:** Само Linux (**IP_TRANSPARENT** је доступан само на Linux-у), могућност **CAP_NET_ADMIN** (root) и изворни N-API додатак који мора да се изгради помоћу C ланца алата (`npm run build:native:tproxy`). Када није доступно, прекидач на контролној табли је онемогућен уз опис „TPROXY дешифровање захтева Linux + root + изворни додатак“. Правила заштитног зида примењују се и поништавају трансакционо (пад система никада не оставља `mangle` правило за собом) и бришу се при поновном покретању. Механизам против петљи заснован на SO_MARK спречава поновно пресретање сопственог поново шифрованог прослеђивања проксија.

Ово је значајан подсистем са сопственим наменским водичем за оператере — погледајте `docs/security/MITM-TPROXY-DECRYPT.md` (git; није компајлиран у `/docs`) за комплетан рецепт заштитног зида, динамички CA за сваки SNI + програм за инсталацију у складиште поузданих сертификата, руту ограничену само на локални систем, детаље механизма против петљи и шему конфигурације. Прекидачем се управља путем `GET / POST / DELETE /api/tools/agent-bridge/tproxy` (напомена: рута се налази под AgentBridge префиксом, а не под Traffic Inspector префиксом).

### 3.2 Листа захтева (лево окно)

- **Виртуализована** (`useVirtualList` + `ResizeObserver`): обрађује 1000 ставки без замрзавања
- **Аутоматско померање** са прекидачем за паузирање током прегледа
- **Статус означен бојом**: зелена (2xx), жута (3xx), црвена (4xx/5xx), сива (у току)
- **Емоџи агента**: 🔵 Antigravity, 🟢 Copilot, 🟠 Kiro, 🟣 Codex, 🔷 Cursor, 🟤 Zed, 🟡 Claude Code, ⚫ Open Code, 🌐 прилагођени хост
- **Трака боје контекста**: лева ивица од 1px обојена према `contextKey` (SHA-256 системског упита) — визуелно групише повезане разговоре
- **Одложено учитавање тела**: само се тело изабраног захтева материјализује у картицама са детаљима (избегава приказивање 1000 × 1MB тела)

## §4 Функционалности прилагођене LLM-овима

### 4.1 Детектор врсте (`src/mitm/inspector/kindDetector.ts`)

Класификује сваки захтев као `"llm"`, `"app"` или `"unknown"` користећи 4 сигнала:

1. **Регистар хостова** — око 18 познатих имена хостова LLM API-ја (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot итд.)
2. **Обрасци путања** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses` итд.
3. **Структура тела** — открива поља `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input`
4. **Назнаке корисничког агента** — `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor` у UA ниски

Прилагођени хостови додати путем режима 2 наслеђују свој `kind` из уноса у обрасцу (подразумевана вредност је `"custom"`).

### 4.2 SSE обједињавач (`src/mitm/inspector/sseMerger.ts`)

**Независна имплементација од почетка.** Рашчлањивање догађаја прати
[WHATWG алгоритам за догађаје које шаље сервер](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream),
док реконструкција прати јавне шеме стримовања сервиса [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) и
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent).

Реконструише коначну поруку асистента из сирових SSE догађаја разлика:

- **Anthropic**: акумулира `content_block_delta` према индексу; обрађује `text_delta`, `input_json_delta` (позиве алата), `thinking_delta`
- **OpenAI**: акумулира изборе/позиве алата Chat Completions API-ја и излазне ставке Responses API-ја
  према индексу
- **Gemini**: акумулира `candidates[i].content.parts`
- **Непознато**: враћа сирове догађаје без измена

Картица Response приказује прекидач: **„Сирови догађаји ↔ Обједињено“**.

### 4.3 Нормализатор разговора (`src/mitm/inspector/conversationNormalizer.ts`)

**Независна имплементација од почетка.** Нормализација је дефинисана локалним уговорима
типа „црне кутије“ и јавним шемама порука сервиса OpenAI, Anthropic и Gemini; није коришћен
изворни код узводне имплементације.

Конвертује формате порука сервиса OpenAI, Anthropic и Gemini у јединствени `NormalizedConversation` пре приказивања:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // поруке / садржај / упит из тела захтева
  response: NormalizedTurn[]; // одговор асистента (обједињен помоћу sseMerger)
  contextKey: string | null; // SHA-256 отисак системског упита
}
```

Типови блокова: `text`, `tool_use`, `tool_result`. Картица Conversation користи овај облик без обзира на добављача.

### 4.4 Бојење кључа контекста (`src/mitm/inspector/contextKey.ts`)

- Израчунава `SHA-256` системског упита (прва порука `role:system`, или поље `system`, или Gemini `systemInstruction`)
- Враћа хексадекадни префикс од 12 знакова (`"a3f9c2..."`)
- Кориснички интерфејс мапира кључ на детерминистичку HSL боју за траку леве ивице
- **Филтер „исти контекст“**: кликом на ознаку `ctx #a3f` додаје се филтер који приказује само захтеве са истим отиском

Ово олакшава визуелно разликовање различитих „персона“ или задатака који се извршавају у истој сесији агента.

### 4.5 Издвајање LLM метаподатака

За LLM захтеве, картица LLM Details издваја:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // из тела захтева или одговора
  messages: number; // број потеза
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // true ако је у питању SSE одговор
  mappedTo: string | null; // заглавље x-omniroute-mapped
  costEstimateUsd: number | null; // процењени трошак на основу OmniRoute цена
}
```

### 4.6 Филтер активних захтева уживо

Поље `status` захтева има тип `number | "in-flight" | "error"` — унос се
додаје као `"in-flight"` у тренутку када захтев започне и **ажурира на лицу места**
када стигне одговор (или грешка). Прекидач **„Уживо“** на траци са алаткама
(`liveOnly`, i18n кључ `trafficInspector.liveOnly`) ограничава листу на уносе
чији је `status === "in-flight"`, омогућавајући праћење отворених веза у реалном времену.

Филтер је чист предикат на клијентској страни у
`src/lib/inspector/matchesTrafficFilter.ts`:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

Стање прекидача налази се у `useTrafficFilters` (hooks контролне табле инспектора) и
комбинује се са осталим филтерима (профил, хост, агент, извор, статус, контекст).

### 4.7 Приписивање процесу (Linux)

На систему Linux, сваки пресретнути захтев може се приписати **локалном процесу
из ког потиче**. У `InterceptedRequest` су додата два опциона поља:

```ts
pid?: number;          // идентификатор изворног процеса (само Linux)
processName?: string;  // назив изворног процеса (само Linux)
```

`src/mitm/inspector/processAttribution.ts` мапира привремени порт _клијента_
везе на PID + назив тако што:

1. Чита `/proc/net/tcp` и `/proc/net/tcp6` ради проналажења inode-а сокета за
   порт (`parseProcNetTcpForInode`, чист рашчлањивач који се може тестирати помоћу фикстура).
2. Скенира `/proc/<pid>/fd/` ради проналажења симболичке везе ка `socket:[<inode>]`.
3. Чита назив процеса из `/proc/<pid>/comm`.

Кеш са TTL-ом од 1 секунде ограничава трошак скенирања procfs-а под оптерећењем. Приписивање се
обавља по принципу **најбољег покушаја** — сваки неуспех се разрешава као `null` и никада не блокира снимање. На
системима macOS/Windows функција враћа `null` (заменска имплементација; подршка за `lsof`/`GetExtendedTcpTable`
биће накнадно додата).

## §6 Безбедност

Traffic Inspector приказује **сав пресретнути HTTPS саобраћај**, укључујући заглавља за ауторизацију и тела захтева. Примењене су следеће контроле:

| Контрола                             | Детаљи                                                                                                                                                                                               |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LOCAL_ONLY**                       | Све руте и WebSocket крајња тачка доступне су само преко повратне петље (спроводи се у `routeGuard.ts` пре аутентификације)                                                                          |
| **Маскирање тајни**                  | Линеарни `maskSecret()` скенер редигује RFC 6750 Bearer акредитиве, кључеве са префиксом добављача и дугачке непрозирне токене пре `TrafficBuffer.push()`                                            |
| **Ограничење величине тела**         | Тела > `INSPECTOR_MAX_BODY_KB` (подразумевано 1024 KB) скраћују се уз обавештење `„(скраћено ради перформанси)“`                                                                                     |
| **Санитизација заглавља**            | Називи се претварају у мала слова; заглавља за уоквиравање/по скоку и прокси аутентификацију се одбацују; колачићи су потпуно редиговани; вредности акредитива прослеђују се функцији `maskSecret()` |
| **CSP**                              | Строга политика безбедности садржаја на страницама Traffic Inspector-а ради спречавања XSS-а путем уметнутих тела одговора                                                                           |
| **Подразумевано без трајног чувања** | `TrafficBuffer` се налази у меморији и губи се при поновном покретању сервера. Сесије се трајно чувају само када се изричито снимају                                                                 |

### Примењена строга правила

| Правило                           | Примена                                                                                     |
| --------------------------------- | ------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | Сви HTTP одговори са грешком из рута Traffic Inspector-а су санитизовани                    |
| **#15 + #17** `isLocalOnlyPath()` | `/api/tools/traffic-inspector/` је LOCAL_ONLY + SPAWN_CAPABLE (команде системског проксија) |

### Позната ограничења

- **Режим системског проксија** утиче на све апликације на рачунару, укључујући VPN клијенте и SSO. Увек га користите са тајмером за аутоматско онемогућавање. Не користите га на дељеним рачунарима.
- **HTTPS CONNECT тунел**: Режим 3 (HTTP_PROXY) бележи само метаподатке тунела за HTTPS одредишта, осим ако је омогућено TLS пресретање. Ово је намерно — транспарентно бележење без поузданог AgentBridge сертификата прекинуло би TLS верификацију за те апликације.
- **Хардкодирани нискови у неким компонентама**: Неки UI компоненти (F7/F8) имају мали број хардкодираних ниски које i18n кључеви још не покривају. Оне су документоване као познато ограничење у извештају о i18n недостацима; биће мигриране у наредном пролазу. Погођени нискови су декоративне UI ознаке које не захтевају превод за функционалну употребу.

## §7 Решавање проблема

### Прекид WebSocket везе

Ако праћење уживо приказује „Прекинута веза“:

1. Проверите да ли сервер и даље ради: `GET /api/tools/traffic-inspector/capture-modes`
2. Поново учитајте страницу — WebSocket ће се поново повезати и примити нови снимак стања
3. Ако је сервер поново покренут, бафер у меморији је обрисан — стари уноси више не постоје, осим ако је сесија била снимљена

### Сукоб на порту 8080

Ако режим HTTP_PROXY не успе да се покрене:

```bash
lsof -i :8080    # пронађите процес
```

Промените порт:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### Системски прокси није враћен на претходно стање

Ако се OmniRoute сруши док је активан режим системског проксија:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

Контролна табла ће при следећем учитавању такође понудити „Врати системски прокси на претходно стање“ ако открије да стање у бази података указује на то да је прокси био активан.

### Пун бафер

Када бафер достигне `INSPECTOR_BUFFER_SIZE` (подразумевано 1000), нови уноси потискују најстарије. Ако се важни захтеви губе:

- Повећајте `INSPECTOR_BUFFER_SIZE` (нпр. 5000) — већа потрошња меморије у замену за дуже задржавање
- Снимите сесију да бисте релевантни период трајно сачували у бази података

| GET   | `/capture-modes`               | Стање режима AgentBridge / прилагођени хостови / HTTP_PROXY / системски прокси + прекидач `tls-intercept` |
| POST  | `/capture-modes/http-proxy`    | Покреће/зауставља HTTP_PROXY ослушкивач (`{action: "start"\|"stop"}`)                                     |
| POST  | `/capture-modes/system-proxy`  | Примењује/враћа системски прокси (`{action: "apply"\|"revert"}`)                                          |
| POST  | `/capture-modes/tls-intercept` | Укључује/искључује дешифровање HTTPS тела у прокси режиму (`{enabled: boolean}`)                          |

> **TPROXY дешифровање** (режим снимања 5) контролише се преко **засебне** руте под
> AgentBridge префиксом — `GET / POST / DELETE /api/tools/agent-bridge/tproxy` — а не
> под `/api/tools/traffic-inspector/`. Погледајте
> `docs/security/MITM-TPROXY-DECRYPT.md` (git; није компајлирано у `/docs`).
