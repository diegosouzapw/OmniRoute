`open-sse/config/providerPluginManifest.ts` дефинише уговор додатка провајдера који је безбедан за JSON.
`open-sse/config/providerPluginManifestRegistry.ts` повезује тај уговор са
тренутним регистром провајдера за пратеће процесе као што су Bifrost,
CLIProxyAPI или будући Go/Rust рутер. TypeScript регистар остаје
извор истине, али пратећи процеси могу да користе манифест без увоза
кода извршавача, подразумеваних OAuth вредности, заглавља или стања окружења процеса.

Исти манифест је доступан преко HTTP-а на
`GET /api/v1/provider-plugin-manifest` за пратеће процесе који се извршавају ван главног процеса.

OmniRoute оглашава ту URL адресу Bifrost-у и CLIProxyAPI-ју преко
`X-OmniRoute-Provider-Manifest-Url` заглавља захтева. Подесите
`OMNIROUTE_PROVIDER_MANIFEST_URL` када је пратећем процесу потребна јавна URL адреса или
мрежна URL адреса контејнера уместо локалног извора захтева.

## Освежавање манифеста

HTTP крајња тачка враћа `Cache-Control: public, max-age=60` и снажан
`ETag`. Пратећи процес треба да задржи последњи потврђени манифест и пошаље његов ETag
у `If-None-Match` приликом освежавања. Одговор `304 Not Modified` нема тело;
пратећи процес задржава свој кеширани манифест. Ако не постоји потврђени кеширани манифест,
пратећи процес мора да пошаље безуслован захтев уместо да прихвати `304`.

## Циљ

Померити метаподатке провајдера ка уговору додатка како би критична путања захтева
на крају могла да буде у надлежности пратећег процеса са мањим кашњењем, док OmniRoute задржава
TypeScript руту као контролу смерница и резервну путању. Манифест је адитиван: сам по себи
не мења рутирање захтева.

## Уговор

Манифест садржи:

- идентификатор и алијас провајдера
- формат узводног сервиса и назив извршавача
- тип аутентификације, заглавље аутентификације и опциони префикс аутентификације
- статичке метаподатке крајње тачке
- подобност за пратећи процес и изричите разлоге када провајдер треба да остане на TS путањи
- метаподатке модела безбедне за JSON, као што су дужина контекста, ознаке за визуелне могућности/резоновање и
  неподржани параметри
- ознаке могућности, укључујући `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` и `usage-supported`

Манифест намерно изоставља:

- OAuth клијентске тајне и подразумеване вредности тајни
- разрешавање окружења током извршавања
- заглавља захтева и јавне помоћне функције за акредитиве
- динамичке градитеље URL адреса
- функције извршавача
- интерне детаље скупа сесија

## Ознаке могућности

`capabilities` је сортиран низ ознака изведених из ставке регистра. Интегратори
треба да га сматрају машински читљивим одговором на питање „шта овај провајдер може да ради“, уместо
поновног читања TypeScript изворног кода.

| Ознака               | Значење                                                                     |
| -------------------- | --------------------------------------------------------------------------- |
| `apikey`             | Прихвата API кључ (`authType` је `apikey` или `optional`).                  |
| `oauth`              | Користи OAuth ток или ток сесије.                                           |
| `responses`          | Излаже основну URL адресу OpenAI Responses API-ја.                          |
| `passthrough-models` | Послужује моделе директно из узводног сервиса уместо из статичког каталога. |
| `custom-executor`    | Покреће извршавач који није подразумеван, па остаје на TypeScript путањи.   |
| `sidecar-candidate`  | Одражава `sidecar.eligible` — безбедно је размотрити увоз у пратећи процес. |
| `usage-fetch`        | Има повезан добављач података о употреби или квоти (`getUsageForProvider`). |
| `usage-supported`    | API за употребу прихвата овог провајдера (`isSupportedUsageConnection`).    |

`usage-fetch` служи само за откривање. Он означава да OmniRoute зна како да прочита податке о употреби за
провајдера; не активира добављање података, не мења семантику квота нити подразумева да је
виџет за квоте на контролној табли омогућен за тог провајдера — тај виџет се засебно контролише помоћу
`USAGE_SUPPORTED_PROVIDERS`. Извор истине је `USAGE_FETCHER_PROVIDERS` у
`open-sse/services/usage/fetcherProviders.ts`.

Та листа је индексирана нискама које диспечер употребе прихвата, па меша канонске идентификаторе
са алијасима и нешто је дужа од броја означених провајдера: ставке које
нису провајдери за ћаскање у регистру манифеста (на пример `firecrawl` провајдер за претрагу
и `amazon-q` ACP провајдер) немају ставку манифеста којој би се додала ознака.

`usage-supported` показује да ли руте за употребу на серверу и контролној табли прихватају везу
за тог провајдера. Он одражава `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
и `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), при чему су обе функције контролисане помоћу
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). За разлику од
`usage-fetch`, ова ознака се емитује искључиво на основу идентификатора провајдера — провера током извршавања користи
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` без разрешавања алијаса, па манифест
задржава исто правило. Две ознаке имају различите домете: 3 провајдера имају само
`usage-fetch` (`opencode`, `opencode-zen`, `xai`), а 1 има само
`usage-supported` (`xiaomi-mimo-token-plan`), тако да једна не подразумева другу.

## Коришћење sidecar-а

Sidecar-и треба да третирају `sidecar.eligible` као конзервативан сигнал да је провајдер кандидат, а не као безусловну одлуку о усмеравању. Први циљ за увоз треба да буду провајдери који користе API кључеве и статичке крајње тачке, уз подразумевани извршилац. Провајдери са прилагођеним веб-извршиоцима, OAuth токовима/токовима сесија, динамичким градитељима URL-ова или конфигурацијом скупа остају на TypeScript резервној путањи док sidecar не имплементира еквивалентно понашање и телеметрија не потврди паритет.

Предложене фазе миграције:

1. Генерисати и валидирати манифест додатака провајдера из TS регистра.
2. Омогућити Bifrost-у или CLIProxyAPI-ју да увезе манифест за провајдере са API кључевима и статичким крајњим тачкама.
3. Усмеравати одговарајуће провајдере кроз sidecar иза `OMNIROUTE_RELAY_BACKEND`, уз задржавање омогућене TS резервне путање.
4. Унапредити статус провајдера тек када стопа успешности, p99 латенција, понашање стриминга и обрада неподржаних параметара буду усклађени са TS путањом.
5. Додавати изворне sidecar додатке за прилагођене извршиоце, једну по једну породицу провајдера.

## Зашто не уградити провајдере директно у Next

Next фронтенд не треба да буде задужен за извршавање провајдера. Треба да позива API границу. Позадински систем затим може да одлучи да ли ће користити TypeScript извршилац, Bifrost, CLIProxyAPI или неки будући изворни sidecar. На тај начин потписивање захтева, провере листе дозвољених ставки, DB смернице и резервно понашање остају централизовани пре било каквог прослеђивања sidecar-у.
