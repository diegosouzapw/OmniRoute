Овај документ описује основу адаптивног рутирања вођеног повратним информацијама, додату у
OmniRoute. Намерно је малог обима: уводи типизирани канал исхода рутирања,
онлајн сигнал квалитета који се прослеђује постојећем auto-combo механизму за бодовање,
опциони OpenTelemetry извозник и крајњу тачку за објашњивост. Он **не**
замењује постојећи слој отпорности (заштитни прекидач, период мировања везе,
блокаду модела, матрицу здравља, аутопилот) — већ га допуњује.

## 1. Архитектонски контекст

OmniRoute је раван података са **критичном путањом захтева** и **контролном/интелигентном
равни**. Критична путања мора остати брза, меморијски ефикасна, асинхрона, отпорна и
предвидљива. Евалуација, бодовање квалитета, експерименти и историјска анализа припадају
контролној равни.

```
AI агент / IDE
      │
      ▼
┌─────────────────────┐
│    OmniRoute        │   раван података (брза, синхрона, у меморији)
│ рутирање / прелазак │
│ здравље / заштита   │
│ кеш / стримовање    │
└──────────┬──────────┘
           │ RoutingEvent (покрени и настави, ~0.2µs)
           ▼
┌─────────────────────┐
│ Пријемници повратних│   контролна раван (асинхрона, по принципу најбољег покушаја)
│ информација         │
│ пратилац квалитета  │
│ OTel извозник       │
│ складиште објашњења │
└──────────┬──────────┘
           ▼  оцена квалитета
      auto-combo механизам за бодовање
```

### Шта је већ постојало (прегледано, није дуплирано)

| Концепт                                    | Постојећа имплементација                                                                                                   |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| Доступност (можемо ли слати саобраћај?)    | Заштитни прекидач (CLOSED/DEGRADED/OPEN/HALF_OPEN, сачуван у бази података), период мировања везе, блокада модела          |
| Извештавање о здрављу                      | `providerHealthMatrix.ts`, `providerHealthAutopilot.ts`                                                                    |
| Саобраћај у сенци                          | `open-sse/services/combo/shadowRouting.ts`                                                                                 |
| Заштитни механизми                         | `src/lib/guardrails/` (закачке пре/после обраде)                                                                           |
| Кеш тачних погодака                        | `src/lib/semanticCache.ts` (заснован на потписима)                                                                         |
| Евалуатори / рутирање вођено евалуацијом   | `src/lib/evals/`, `open-sse/services/evalRouting.ts`                                                                       |
| Објашњивост combo одлука                   | `open-sse/services/combo/decisionTrace.ts`                                                                                 |
| Догађаји контролне табле у реалном времену | `src/lib/events/eventBus.ts` (канал обавештења корисничког интерфејса, `unknown` корисни садржаји, историја од 100 ставки) |

Слој догађаја рутирања **није** поновна имплементација `eventBus`: та магистрала је
канал контролне табле за обавештења у реалном времену (типизирани _називи догађаја_, непрозирни
корисни садржаји, потрошачи из корисничког интерфејса). `RoutingEvent` је типизирана _структура исхода_
(кашњење/токени/трошак/исход/разлог завршетка) коју користе пријемници повратних информација
контролне равни (пратилац квалитета, OTel извозник, складиште објашњења).

### Шта је недостајало (додато овде)

1. **Апстракција типизираног догађаја исхода рутирања и његовог пријемника** (`RoutingEvent` /
   `RoutingEventSink`). `decisionTrace` је ограничен на combo и постоји само у меморији;
   `comboMetrics` су кумулативни бројачи; `call_logs` представља необрађену асинхрону трајну меморију.
   Ништа од тога није типизирани канал исхода заснован на пријемницима, на који се могу претплатити
   пратилац квалитета, OTel извозник или евалуатор у стилу Future-AGI.
2. **Онлајн сигнал квалитета** (EWMA) за квалитет излаза — механизам за бодовање је претходно
   апроксимирао „квалитет“ искључиво путем статичке прикладности за задатак и опционих стопа
   пролазности евалуације.
3. **Опциони OTel извозник без зависности** који користи GenAI семантичке конвенције.
4. **Крајња тачка за објашњивост** која враћа стварне одлуке о рутирању и стање квалитета.

## 2. Догађаји рутирања (основа повратне спреге)

Датотеке: `open-sse/services/routing/events.ts`, `.../index.ts`

`RoutingEvent` садржи само метаподатке рутирања:

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ...
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // унија са листом дозвољених вредности
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

`RoutingEventSink` је особина у TypeScript-у налик на `Send+Sync`:

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // мора бити O(1), без синхроног I/O-а
}
```

Критична путања позива `emitRoutingEvent(event)` једном по завршеном захтеву
(повратни позив по завршетку стримовања, путања успеха без стримовања и
путања неуспеха због неисправног одговора 200 у `handleChatCore`). Расподела је
синхроно прослеђивање свим регистрованим пријемницима, али сваки пријемник само
ставља догађај у ред или ажурира стање у меморији. **Нема синхроног уписивања у
базу података нити мрежног I/O-а на критичној путањи.**

Подразумевани пријемници:

- `MemoryRoutingEventStore` — ограничени (500) кружни бафер, од најновијег ка
  најстаријем, за крајњу тачку за објашњења.
- Потрошач `QualityTracker` — ажурира EWMA процену квалитета.
- `OtlpHttpsEventSink` — опционалан, омогућен само када је подешен
  `OMNIROUTE_OTEL_ENDPOINT` (или `OTEL_EXPORTER_OTLP_ENDPOINT`).

### Измерено оптерећење (реално поређење)

`npm run bench:routing-events` на овој радној станици (100 хиљада итерација;
операције испод µs измерене су агрегатно у µs/op јер су перцентили по операцији
испод резолуције тајмера `performance.now()`):

| Сценарио                               | µs/op  | ops/s  |
| -------------------------------------- | ------ | ------ |
| основа (само бодовање)                 | ~0.045 | ~22 M  |
| основа + RoutingEvent (2 пријемника)   | ~0.168 | ~5.9 M |
| основа + догађај + OTel стављање у ред | ~0.163 | ~6.1 M |
| конкурентно (8 испреплетаних налета)   | ~0.18  | —      |

Разлика коју отпремање догађаја додаје у односу на основно бодовање износи
~0.12 µs/захтев; OTel пријемник само ставља догађај у ред (O(1) додавање у
бафер), без мерљивог додатног трошка. Ови бројеви су специфични за машину и
релативни — нису гаранција за продукционо окружење. Вредност „~0.2 µs“ из v1
била је агрегатна процена; ова методологија раздваја основно бодовање од трошка
отпремања догађаја.

## 3. Сигнал квалитета (стање добављача засновано на повратној спрези)

Датотеке: `open-sse/services/routing/quality.ts`

v2 раздваја **оперативни** од **семантичког** квалитета:

- **Оперативни** — изведен из критичне путање рутирања (HTTP 4xx/5xx, неуспеси
  везе, 429 одговори, неисправни одговори, прекиди стрима, `finish_reason=length`,
  успешни одговори без излаза, EWMA латенције/TTFT-а). Одговор 200 се НЕ сматра
  показатељем семантичког квалитета.
- **Семантички** — стварна вредност генерисаног излаза. УВЕК га производи
  искључиво оцењивач путем `setSemanticQuality()`. Вредност је `null` док је неки
  оцењивач не обезбеди и никада се не прелива у оперативни резултат.

Стање по пару (добављач, модел) (EWMA + ограничени бројачи):

- `successEwma` — EWMA (α=0.2) успешности исхода.
- `latencyEwma` / `ttftEwma` — EWMA латенције (α=0.1).
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`.
- `recencyMs` — колико је недавно модел последњи пут забележен.

### Узимање у обзир поузданости / броја узорака

`confidence = clamp01(samples / 50)`, а резултат који се враћа механизму за
бодовање меша се са неутралном средишњом вредношћу:

```
score = 0.5 + confidence * (operational - 0.5)
```

Последице (потврђене тестовима):

- Нови добављач (0 узорака) има резултат **0.5** — није неправедно кажњен, али
  не може да надмаши добављача са хиљадама поузданих запажања.
- Добављач са 7 случајних успеха помера се ка 0.5 (никада не доминира захваљујући
  оптимистичкој иницијализацији).
- Добављач са 50+ узорака конвергира ка свом стварном оперативном резултату.
- Погоршање и опоравак су постепени (EWMA), а један изоловани неуспех не
  уништава здравог добављача.

`ProviderQuality` излаже `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }`.

Ово се прослеђује механизму за бодовање аутоматске комбинације као фактор
бодовања `quality`:

- `ScoringFactors.quality` / `ScoringWeights.quality` у
  `open-sse/services/autoCombo/scoring.ts`.
- `DEFAULT_WEIGHTS`: `health` 0.1905 → 0.1605, `quality` 0.03. Збир остаје 1.0.
- `buildAutoCandidates` попуњава `candidate.quality` из пратиоца; кандидати без
  података подразумевано добијају неутралних **0.5** (нови кандидат није ни
  фаворизован ни кажњен).

Затворена петља:

```
RoutingEvent → QualityTracker → getQualityScore → фактор квалитета аутоматске комбинације
      ↑                                                    │
      └────── исход захтева (handleChatCore) ←─────────────┘
```

### Строго искључивање наспрам благе казне

Сигнал квалитета је само **блага адаптивна преференција**. Строго искључивање
остаје у надлежности постојећег слоја отпорности: прекидач кола у стању OPEN,
исцрпљена квота, неуспех аутентификације, закључавање модела — резултат квалитета
не утиче ни на једно од њих. Добављач чији резултат квалитета привремено опадне
добија нижи приоритет, али никада није строго онемогућен.

## 3b. Канонско временско праћење стрима (TTFT / ITL)

Датотеке: `open-sse/utils/streamTiming.ts`

`createStreamTiming()` је јединствена тачка инструментације за путању стримовања,
интегрисана у `createSSEStream` (open-sse/utils/stream.ts):

- `markByte()` — примљен је први узводни сегмент.
- `markForward()` — први сегмент је прослеђен клијенту (користи се за TTFT).
- `markInterrupted()` — истек времена, прекид или грешка стрима пре уредног завршетка.
- `ttft()` = кашњење до првог прослеђеног SSE сегмента. **Ово НИЈЕ TTFT на нивоу токена** —
  један SSE сегмент може садржати нула, један или више токена. Прецизно документовано.
- `avgItlMs()` = просечан размак између сегмената (посредна мера кашњења сегмената за ITL).

TTFT/ITL/статус прекида улазе у `RoutingEvent` (`ttftMs`, `itlMs`) и
OTel одвод их извози као GenAI/OmniRoute атрибуте распона.

## 4. OpenTelemetry / GenAI опсервабилност

Датотеке: `open-sse/services/routing/otel.ts`

- OTLP/HTTP JSON извозник без зависности (користи глобални `fetch`, без
  `@opentelemetry/*` SDK-а).
- Распони прате GenAI семантичке конвенције (`gen_ai.provider.name`,
  `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`,
  `gen_ai.completion.finish_reason`, `gen_ai.system`) заједно са OmniRoute
  атрибутима рутирања (исход, статус, ttft, поновни покушаји, резервна опција).
- `record()` само додаје ставку у ограничени бафер (O(1)); позадински тајмер
  асинхроно отпрема податке преко `POST {endpoint}/v1/traces`. При преоптерећењу
  најстарији догађаји се одбацују (бројач `dropped`) — без повратног притиска на
  раван података.
- **Онемогућено је ако није конфигурисано.** `OMNIROUTE_OTEL_ENDPOINT` (или
  `OTEL_EXPORTER_OTLP_ENDPOINT`) мора бити подешено; у супротном одвод није
  регистрован и ниједан OTel кôд се не извршава.

## 5. Објашњивост

- `GET /v1/explain/routing` враћа недавне `RoutingEvent` догађаје (стварне
  одлуке, почев од најновије) и снимак квалитета по добављачу/моделу.
- Аутентификација одговара оној за `/v1/combos` (Bearer API кључ или сесија
  контролне табле; анонимни приступ у локалним применама за једног корисника са
  `REQUIRE_API_KEY=false`).
- Трагови појединачних позива на нивоу комбинације остају доступни преко
  постојећег `decisionTrace.ts` (заглавље `X-OmniRoute-Combo-Trace`).
- Безбедност: догађаји садрже само метаподатке о рутирању, никада упите, тела
  захтева или акредитиве.

## 6. Интеграција равни евалуације (спремност за Future AGI)

OmniRoute третира Future AGI (или било који евалуатор) као **потенцијални
позадински систем за интелигенцију/евалуацију, а не као зависност**. Тачке интеграције су:

- `RoutingEventSink` може асинхроно прослеђивати догађаје евалуатору.
- `MemoryRoutingEventStore` + снимак квалитета пружају евалуатору сирови
  ток одлука.
- Будући `Evaluator` (детерминистички, локални оцењивач, HTTP, WASM) користио би
  догађаје/трагове и враћао `QualityScore`, који се прослеђује истој
  путањи `getQualityScore`/фактора квалитета.
- Постојеће рутирање вођено евалуацијом (`open-sse/services/evalRouting.ts`) већ
  мења редослед циљева комбинације према стопама успешности `eval_runs` када је омогућено.

Ниједна евалуација се не извршава синхроно на путањи захтева, а мрежни пролаз
у потпуности функционише и без евалуатора.

## 7. Завршни преглед архитектуре

1. **Шта остаје на синхроној критичној путањи?** Рутирање/бодовање, прелиминарне
   провере заштитних механизама, претрага кеша и једно `emitRoutingEvent` гранање
   (~0,12 µs преко основног бодовања) ка одводима у меморији.
2. **Шта је премештено у асинхрону обраду?** OTel извоз (тајмер + fetch),
   чување `call_logs`/употребе, уписи у семантички кеш; квалитет је у меморији
   и O(1) (асинхрона обрада није потребна).
3. **Како исход рутирања постаје повратна информација?** `handleChatCore` емитује
   `RoutingEvent` → `QualityTracker` ажурира EWMA стање → `getQualityScore`
   обезбеђује фактор `quality` за аутоматску комбинацију.
4. **Како квалитет утиче на будуће рутирање?** Ниска оцена квалитета смањује
   пондерисану оцену тог добављача/модела у `scoreAutoTargets`, па се деградираним
   моделима постепено смањује приоритет, а они се опорављају како се њихов EWMA побољшава.
5. **Како се Future AGI може интегрисати а да не постане зависност?** Преко
   интерфејса `RoutingEventSink` / будућег `Evaluator` адаптера — без чврсто
   кодиране зависности.
6. **Шта се дешава када евалуатор није доступан?** То не утиче на рутирање;
   квалитет се враћа на неутралну вредност (1.0) за моделе без уоченог сигнала.
7. **Шта се дешава када телеметрија није доступна?** OTel одвод се једноставно
   не региструје; остатак слоја за рутирање ради без измена.
8. **Шта се дешава при преоптерећењу?** OTel бафер одбацује најстарије догађаје;
   квалитет и кружни бафер су конструкцијски ограничени; нема повратног притиска.
9. **Како се стање добављача опоравља након деградације?** EWMA поново конвергира
   како се успеси акумулирају; загревање одржава хладне моделе неутралним; прекидач
   кола се независно опоравља путем HALF_OPEN проба.
10. **Које предложене функције намерно НИСУ имплементиране и зашто?**
    - Саобраћај у сенци / експерименти — већ имплементирано
      (`combo/shadowRouting.ts`); није поново изграђено.
    - Заштитни механизми — већ имплементирано (`src/lib/guardrails/`); није дуплирано.
    - Семантички кеш — већ имплементирано (`src/lib/semanticCache.ts`); није
      дуплирано.
    - Потпуна платформа за управљање експериментима, алати за скупове података,
      платформа за оптимизацију упита, векторска база података или обавезна спољна
      OTel инфраструктура — ван опсега за економичну раван података.
    - Rust структура `RoutingEvent` — раван података је у TypeScript-у; TS тип
      је прилагођени еквивалент.
