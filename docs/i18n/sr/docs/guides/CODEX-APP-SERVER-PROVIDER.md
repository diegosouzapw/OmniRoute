OmniRoute пружа **два** начина за коришћење OpenAI Codex-а:

| Провајдер              | Како комуницира са OpenAI-јем                                                                                                                                                                            | Напомена о коришћењу                                                       |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **`codex`**            | Директно прослеђује ваш ChatGPT/OpenAI OAuth токен Responses API-ју                                                                                                                                      | **Да** — званична сесија није овлашћена за коришћење преко проксија/рутера |
| **`codex-app-server`** | Управља **сопственим `codex app-server`-ом Codex CLI-ја** преко JSON-RPC/WebSocket-а; CLI поседује и самостално освежава свој OAuth (`~/.codex/auth.json`), потпуно исто као интерактивна `codex` сесија | **Не** — OmniRoute никада не прослеђује токен API-ју                       |

Пошто `codex-app-server` никада не прослеђује токен, на њега се не односи
напомена о коришћењу која важи за поновно коришћење сесије. Међутим, неопходан је
**Codex CLI доступан на конфигурисаном URL-у app-server-а**, а тај CLI мора бити
**пријављен**.

## 1. Архитектура

```
┌─ OmniRoute апликација ──────────┐        ┌─ codex-app-server пратећи контејнер ┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                   │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456         │
│  (+ токен могућности)            │  JSON  │  --ws-auth capability-token         │
│                                  │  RPC   │  самостално управља OpenAI OAuth-ом │
└──────────────────────────────────┘        │  (~/.codex/auth.json, аутоматско    │
        │ дели (compose волумени)            │   освежавање)                        │
        ▼                                    └─────────────────────────────────────┘
  codex-appserver-token   → WS токен могућности (оба га монтирају)
  codex-appserver-home    → ~/.codex (auth.json уписује контролна табла,
                             а чита га codex app-server пратећег контејнера)
```

- Пратећи контејнер слуша **искључиво** на интерној compose мрежи
  (`ws://codex-app-server:1456`), заштићен токеном могућности. **Никада** није
  изложен хосту нити интернету.
- Codex CLI је уграђен у `omniroute:base`, тако да приликом покретања пратећег
  контејнера није потребно инсталирати codex на хосту нити на корисниковом
  рачунару.

## 2. Покретање

```bash
# Покрените стек СА профилом пратећег контејнера codex app-server-а:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

Пратећи контејнер при првом покретању генерише свој WS токен могућности (у
дељеном волумену `codex-appserver-token`), а апликација чита исти токен преко
`OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`. Ручно повезивање токена није потребно.

## 3. Повезивање и пријављивање

1. На контролној табли додајте везу за **OpenAI Codex (App-Server)**. API кључ
   или токен нису потребни (ово је провајдер без аутентификације — пратећи
   контејнер управља аутентификацијом).
2. Ако Codex CLI пратећег контејнера **још није пријављен**, провера исправности
   везе приказује _„покренут, али није пријављен“_ (а не црвену грешку
   аутентификације). Користите **Пријави се помоћу ChatGPT-а**: тиме се у
   прегледачу покреће стандардни OAuth за уређаје Codex-а, а затим се
   `~/.codex/auth.json` уписује у дељени волумен преко опције **Примени
   аутентификацију** (једна иста пријава служи и провајдеру `codex` и провајдеру
   `codex-app-server`).
3. Након пријављивања, провера исправности постаје зелена (проверава и `/readyz`
   **и** `account/read` — односно да је сервис покренут _и_ аутентификован) и
   почиње да ради.

Контролна табла никада не преписује исправну постојећу датотеку
`~/.codex/auth.json` — уписује је само када датотека не постоји или је њен токен
застарео (резервна копија се увек прави).

## 4. Сценарији постављања

- **Оператор са већ аутентификованим Codex CLI-јем** — монтирајте директоријум
  `~/.codex` са хоста у пратећи контејнер (`codex-appserver-home`) и прескочите
  корак пријављивања.
- **Јавни корисник без локално инсталираног codex-а** — није битно: пратећи
  контејнер садржи CLI. Корисник се аутентификује само преко контролне табле.
- **Самостални OmniRoute на физичком серверу (без пратећег контејнера, codex на
  хосту)** — усмерите `OMNIROUTE_CODEX_APPSERVER_WS` на сопствени
  `codex app-server` и уверите се да је codex на хосту пријављен; ако бинарна
  датотека недостаје, приказује се напомена „codex није инсталиран“.

## 5. Резиденцијални / UDP излазни саобраћај (додатак оператора, не испоручује се)

Генерички пратећи контејнер изнад усмерава излазни саобраћај преко уобичајене
мреже контејнера. Оператор коме је потребно да Codex саобраћај излази преко
**резиденцијалне излазне тачке** (нпр. TUN tailscale пратећег контејнера који
преноси TCP + UDP/QUIC) покреће је као засебну compose допуну; она намерно
**није** део испорученог профила `codex-app-server`. Упутства за то подешавање
потражите у интерном оперативном приручнику.
