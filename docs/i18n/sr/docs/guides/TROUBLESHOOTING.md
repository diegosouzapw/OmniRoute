## Брзи преглед

**Први пут користите OmniRoute?** Почните овде — ово решава 90% проблема:

| Видим ово                       | Шта то значи                                    | Шта треба урадити                                                                                            |
| ------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| "Није могуће повезивање"        | OmniRoute није покренут                         | Покрените `omniroute` или `docker restart omniroute`                                                         |
| "Неважећи API кључ"             | Ваш кључ је погрешан или је истекао             | Поново копирајте кључ са веб-сајта добављача                                                                 |
| "Ограничење брзине прекорачено" | Шаљете превише захтева                          | Сачекајте 1 минут или користите `model: "auto"` за аутоматски прелаз на резервну опцију                      |
| "Квота прекорачена"             | Потрошили сте бесплатну/плаћену квоту           | Повежите више добављача или користите бесплатне добављаче (Kiro, Pollinations)                               |
| "Спори одговори"                | Добављач је преоптерећен или је далеко          | Користите `model: "auto/fast"` или повежите бржег добављача (Groq, Cerebras)                                 |
| "Коришћен је погрешан добављач" | `auto` је изабрао другог добављача              | То је нормално! `auto` бира најбољег. Принудно изаберите одређеног добављача помоћу `model: "openai/gpt-4o"` |
| "502 Bad Gateway"               | Добављач није доступан                          | Сачекајте и покушајте поново или користите `model: "auto"` да бисте променили добављача                      |
| "401 Unauthorized"              | Ваши акредитиви су погрешни                     | Проверите API кључ или се поново аутентификујте помоћу OAuth-а                                               |
| "omniroute није препознат"      | У Windows PATH-у недостају глобални node модули | Додајте глобални npm префикс у Windows PATH. Пронађите га помоћу `npm config get prefix`.                    |
| "429 Too Many Requests"         | Примењено је ограничење брзине                  | Сачекајте 1 минут или повежите више добављача                                                                |

**И даље имате проблем?** Погледајте [детаљно решавање проблема](#detailed-troubleshooting) у наставку или питајте на [Discord-у](https://discord.gg/U47eFqAXCn).

## Детаљно решавање проблема

---

### Ограничење брзине код бесплатних добављача (429 / 400 / 401)

**Симптом**: Када користите `model: "auto"` са бесплатним добављачима/добављачима који не захтевају аутентификацију (opencode, auggie итд.), повремено добијате `HTTP 429`, `400` или `401` уместо одговора. Захтеви успевају када неколико тренутака касније поновите исти упит, али аутоматизација (cron задаци, агенти, скрипте) прекида се при првој грешци.

**Основни узрок**: Три независна режима отказа надовезују се један на други:

1. **Ограничење брзине добављача (`429`)**: Бесплатни нивои могу да примењују квоту по временском интервалу. Низ паралелних позива је исцрпљује, па се следећи захтев одбија док се временски интервал не ресетује.
2. **Неисправан модел у директном прослеђивању (`400`/`401`)**: `auto/*` скупови могу да садрже моделе за директно прослеђивање из `opencode` који су регистровани у каталогу, али немају важеће акредитиве (нпр. `oc/north-mini-code-free` → `401`). Аутоматски рутер испроба један, он не успе, а грешка се проследи пре него што се активира резервна опција.
3. **Појачавање услед конкурентности (`429` под оптерећењем)**: Када више агентских/cron сесија истовремено приступи опцији `auto`, укупна брзина захтева премашује оно што бесплатни добављачи могу да поднесу, па се исправни позиви означавају као злоупотреба.

**Проверено решење (пријавила заједница, 2026-08-10)**: подесите три променљиве окружења тако да ротација, конкурентност и прелазак на резервну опцију апсорбују нестабилност бесплатног нивоа уместо да због ње процес прекине рад:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # пређи на други модел/добављача при 400/401 (прескаче неисправне моделе за директно прослеђивање)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # изричито ограничење пријема захтевних захтева (подразумевано није постављено: нема ограничења броја захтева, погледајте напомену испод)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # дуже ограничено чекање на капацитет за захтевне захтеве уместо тренутне поновљиве грешке 503
```

Поставите их у окружењу OmniRoute процеса (демона, нпр. преко LaunchAgent plist датотеке или `systemctl edit`), а затим поново покрените OmniRoute. Ознака за ротацију је појединачно најутицајније подешавање: она претвара потпуни неуспех у неприметан поновни покушај преко исправног добављача у скупу.

**Напомена**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ограничава број захтевних — дугоконтекстних — захтева који се извршавају истовремено; то ограничење је улазна капија, а не ограничивач брзине добављача. **Ажурирање за #503-fanout:** ова променљива се више не поставља подразумевано (сада се примењује само када је изричито конфигурисана, као изнад) — уместо тога, пријем захтевних захтева контролише се аутоматски изведеним бајтним буџетом (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) који се прилагођава стварном меморијском ограничењу рачунара, па би ново постављање требало да има знатно мање одбијања `503 chat_admission_busy` без икаквог подешавања ове променљиве; њено изричито постављање овде и даље функционише тачно као што је документовано. Изричите измене бајтног буџета ограничавају се на опсег од 8 MiB до 2 GiB. Грешка `413 body_exceeds_budget` није привремена: повећајте тај бајтни буџет, смањите `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` или повећајте меморијско ограничење процеса. Одбацивање `inflight_bytes_budget` представља привремено надметање за ресурсе и захтев се и даље може поновити. Ограничење брзине по добављачу (`open-sse/services/rateLimitManager.ts`) засебно се контролише променљивама `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` и `RATE_LIMIT_AUTO_ENABLE` — погледајте `.env.example`.

**Како да проверите да ли је успело**: покрените свој агент/cron два пута у кратком размаку и потврдите да су оба покретања успешна. Пре исправке, друго покретање обично пријављује `429`/`401`. Након исправке, неуспели покушаји (ако их има) аутоматски се понављају и позив се завршава. Такође можете покренути `curl /monitoring/health` и пратити поље `rateLimitedUntil` на везама са провајдерима и `circuitBreakers.providerBreakers[].state` за погођене провајдере — стање је једно од `CLOSED`, `DEGRADED`, `OPEN` или `HALF_OPEN` (погледајте `src/shared/utils/circuitBreaker.ts`), а провајдер који наставља да отказује прећи ће из `CLOSED → DEGRADED → OPEN` пре него што период ресетовања омогући пробни захтев (`HALF_OPEN`).

**Ако и даље видите 429**: активни налог за тог провајдера заиста је исцрпео своју _квоту_ (а не само ограничење брзине). Додајте други налог за истог провајдера у OmniRoute контролној табли → Провајдери → Налози или укључите другог бесплатног провајдера (нпр. `routeway`, `auggie`). Ротација помаже само код привремених ограничења брзине/грешака 400/401; потпуно исцрпљена квота захтева друге акредитиве или другог провајдера.

**Ако видите 403 на моделима за обраду слика (`auto/vision`, `bazaarlink/*`)**: повезани налог нема плаћени пакет који обухвата обраду слика или API кључ нема довољне дозволе. На контролној табли провајдера проверите да ли опсег кључа обухвата обраду слика/мултимодалне функције или повежите налог са плаћеним пакетом и задржите га као циљ за обраду слика.

## Упозорења при npm install (ERESOLVE / peer / deprecated)

Када покренете `npm install -g omniroute`, можда ћете видети велики број упозорења као што су `npm warn ERESOLVE`, обавештења о peer зависностима и поруке `deprecated`. **Она су очекивана и безопасна.** Инсталација је успела ако у излазу видите `added <N> packages`.

Да бисте потиснули упозорења о разрешавању peer зависности, користите подржани начин инсталације за OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` потискује само `ERESOLVE` и обавештења о peer зависностима. Обавештења о застарелости остају видљива јер потичу од транзитивних пакета трећих страна; она не значе да инсталација није успела.

Упозорења потичу од застарелих опсега peer зависности у пакетима трећих страна које OmniRoute не контролише:

1. **`marked-terminal` захтева `marked >=1 <16`, а пронађен је `marked@18`** — у пракси ради без проблема; upstream опсег peer зависности је само застарео.
2. **`deprecated prebuild-install@7.1.3`** — транзитивна помоћна алатка за преузимање изворних бинарних датотека. Не
   користи се за инсталирање фиксиране `wreq-js` транспортне спреге и не значи да подешавање транспорта
   добављача веб-колачића није успело.

**Није потребно ништа предузимати** — упозорења није могуће у потпуности утишати без прављења fork верзија upstream пакета.

## Gemini Web и Playwright Chromium

Ако Gemini Web захтев врати `503` са поруком да Playwright Chromium
није инсталиран, npm пакет је присутан, али недостаје бинарна датотека прегледача.
Playwright намерно држи преузимања прегледача одвојено од инсталације npm
пакета, па је овај одговор очекиван док се прегледач не инсталира.

За глобалну npm инсталацију, инсталирајте Chromium из директоријума OmniRoute
пакета како би кеш прегледача припадао истој Playwright инсталацији:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Поново покрените OmniRoute након инсталације, а затим поновите Gemini Web захтев. Ако
покрећете OmniRoute из Docker слике, користите `-web` слику (или `runner-web`
циљ изградње), која садржи Chromium и његове зависности; основна слика их
не садржи.

## Лажно позитивни резултати антивируса

<a name="antivirus-false-positives"></a>

### Avast/AVG ставља `README.md` у карантин због `MD:HttpRequest-inf[Susp]`

**Ово је лажно позитиван резултат. Ништа није заражено и није потребно предузимати никакве радње.**

Avast и AVG користе хеуристику која означава обичне текстуалне/Markdown датотеке које садрже много
веза налик HTTP захтевима. OmniRoute-ов `README.md` испоручује се унутар npm пакета (наведен је
у `package.json` → `files`), па се при глобалној инсталацији смешта у `node_modules/omniroute/README.md` —
а садржи око 15 примера `http://localhost:20128/...` (MCP HTTP/SSE крајње тачке, A2A `.well-known`
URL и `curl` исечке). Та густина веза довољна је да активира хеуристику.

Ако је ово почело тек недавно: врста датотеке се није променила. README је проширен
табелом крајњих тачака (додати су MCP HTTP + SSE + A2A) и додатним `curl` примерима, због чега је
премашен праг.

Датотека је неактивна документација без икаквог извршног садржаја. Можете је безбедно вратити
из карантина.

**Шта треба да урадите:**

1. **Зауставите обавештења** — изузмите директоријум инсталације у антивирусу
   (Avast: Подешавања → Изузеци), тако што ћете додати путању до глобалног `node_modules` директоријума и/или
   OmniRoute директоријум са подацима (`~/.omniroute/`).
2. **Пријавите лажно позитиван резултат** — <https://www.avast.com/false-positive-file-form.php>,
   прилажући `README.md` из карантина. Ово је решење које помаже свима, јер је у питању
   хеуристика произвођача која претерано реагује на текстуалну датотеку.

**Зашто ово не „поправљамо“ на нашој страни:** сви примери користе `http://localhost`, а
localhost не може да користи `https` без компликација са самопотписаним сертификатима. Изобличавање документације
ради заобилажења хеуристике једног произвођача нашкодило би сваком читаоцу само да би се удовољило грешци скенера.

### Kaspersky означава десктоп апликацију као `PDM:Trojan.Win32.Generic`

**Ово је лажно позитиван резултат хеуристике понашања. Ништа није заражено.** Kaspersky-јев
префикс `PDM:` значи да процена долази из његовог модула Proactive Defense Module (System Watcher),
који процењује шта инсталатер _ради_, уместо да га пореди са познатим злонамерним софтвером. Када
се активира, Kaspersky „поништава“ целу инсталацију — бришући датотеке које је већ
записао — па апликација на крају буде оштећена или недостаје.

Датотеке које означава представљају стандардне делове декларисаних зависности отвореног кода које се испоручују са
десктоп апликацијом, на пример:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` и
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), библиотека за аутоматизацију
  прегледача која се користи за пријављивање код добављача унутар апликације и ћаскање које користи прегледач.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — фиксирана изворна `wreq-js` веза која се користи за HTTP са отиском прегледача код добављача
  који користе веб-колачиће (`<arch>` је `x64` или `arm64`).

**Зашто се активира:** Windows инсталатер **још увек није потписан кодним сертификатом**, па непотписани NSIS
инсталатер нема никакву репутацију и хеуристика понашања ради са максималном агресивношћу. У комбинацији
са укљученим изворним DLL-ом и стотинама `.js` датотека записаних у
`%LOCALAPPDATA%\Programs\OmniRoute` (укључујући директоријуме пакета са суфиксима хешева из
самосталне Next.js верзије), то је довољно да активира хеуристику. Потписивање кода је планирано;
док се не уведе, ово се може понављати са новим издањима.

**Шта треба да урадите:**

1. **Прво проверите преузету датотеку** (тако искључујете могућност да је датотека измењена). Свако издање објављује
   `latest.yml`, чије поље `sha512` (base64) покрива инсталатер
   `OmniRoute.Setup.<version>.exe`. У PowerShell-у, из фасцикле која садржи инсталатер:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Излаз мора да се подудара са `latest.yml` → `sha512`. Ако се не подудара, избришите датотеку и
   поново је преузмите искључиво са [GitHub странице издања](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Вратите + изузмите** — вратите поништене ставке из карантина и додајте изузетак
   за `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Подешавања → Претње и изузеци),
   а затим поново инсталирајте.
3. **Пријавите лажно позитиван резултат** — <https://opentip.kaspersky.com/>. Пријаве лажно позитивних резултата
   које шаљу корисници заиста убрзавају додавање на листу дозвољених ставки.

## Компатибилност са Node.js-ом

<a name="nodejs-compatibility"></a>

### Страница за пријављивање се руши или приказује грешку „Module self-registration“

**Узрок:** Користите верзију Node.js-а која је изван безбедносног опсега извршног окружења који је одобрио OmniRoute. Најчешћи случај је коришћење старијег нивоа закрпе за Node 22 или 24, који је испод минималног нивоа безбедносних закрпа који OmniRoute захтева.

**Симптоми:**

- Страница за пријављивање приказује празан екран или серверску грешку
- Конзола приказује `Error: Module did not self-register` или сличне грешке изворних повезивања
- Страница за пријављивање приказује **наранџасти банер упозорења** са вашом верзијом Node-а ако је извршно окружење изван подржане безбедносне политике

**Решење:**

1. Инсталирајте подржано Node.js LTS издање (препоручено: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Проверите верзију: `node --version` треба да прикаже `v24.0.0` или новију верзију из линије 24.x LTS
3. Поново инсталирајте OmniRoute: `npm install -g omniroute`
4. Поново покрените: `omniroute`

> **Подржане безбедне верзије:** `>=22.22.2 <23` или `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) и Node.js 26 су у потпуности подржани.

### npm v11+: `better-sqlite3` није инсталиран (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Узрок:** npm v11 (који се испоручује уз Node.js 24+) подразумевано блокира скрипте за инсталацију опционих
зависности. Пошто је `better-sqlite3` наведен у `optionalDependencies`
и захтева изворно компајлирање (`node-gyp rebuild`), npm га тихо прескаче.

**Симптоми:**

- Сервер се руши при покретању уз поруку `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` приказује „No such file or directory“
- `npm ls better-sqlite3` приказује `(empty)`

**Решење:**

1. Одобрите скрипте за инсталацију и поново инсталирајте:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Или ручно инсталирајте унапред изграђени пакет:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Проверите да ли ради: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file“

<a name="macos-native-module-rebuild"></a>

**Узрок:** Након глобалног `npm install -g omniroute`, изворна бинарна датотека `better-sqlite3` унутар пакета можда је компајлирана за другачију архитектуру или Node.js ABI од оног који се локално користи. Ово је уобичајено на macOS-у (и на Apple Silicon и на Intel системима) када унапред изграђена бинарна датотека не одговара вашем окружењу.

**Симптоми:**

- Сервер одмах отказује при покретању уз грешку `dlopen`
- Грешка садржи `slice is not valid mach-o file`
- Потпун пример:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Решење — поново изградите за своје локално окружење (враћање на старију верзију Node.js-а није потребно):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Напомена:** Овим се изворно повезивање поново компајлира за вашу локалну верзију Node.js-а и архитектуру процесора, чиме се отклања неподударност бинарних датотека. Званично подржан опсег извршног окружења је **`>=22.22.2 <23` или `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` у `src/shared/utils/nodeRuntimeSupport.ts`, усклађен са пољем `engines` у `package.json`). Node.js 24.x LTS (Krypton) и Node.js 26 су у потпуности подржани са `better-sqlite3` v12.x.

## Проблеми са проксијем

<a name="proxy-issues"></a>

### Валидација добављача приказује „fetch failed“

**Узрок:** Крајња тачка за валидацију API кључа (`POST /api/providers/validate`) раније је заобилазила конфигурацију проксија, што је доводило до грешака у окружењима која захтевају усмеравање преко проксија.

**Решење (v3.5.5+):** Ово је сада исправљено. Валидација добављача се усмерава кроз `runWithProxyContext` и аутоматски поштује подешавања проксија на нивоу добављача и глобална подешавања проксија.

### Провера исправности токена не успева уз поруку „fetch failed“

**Узрок:** Освежавање OAuth токена у позадини није разрешавало конфигурацију проксија за сваку везу појединачно.

**Решење (v3.5.5+):** Планер провере исправности токена сада разрешава конфигурацију проксија за сваку везу пре покушаја освежавања. Ажурирајте на v3.5.5+.

### SOCKS5 прокси враћа „invalid onRequestStart method“

**Узрок:** На Node.js 22, диспечер undici@8 није компатибилан са уграђеном имплементацијом функције `fetch()` у Node-у.

**Решење (v3.5.5+):** OmniRoute сада користи сопствену функцију `fetch()` пакета undici када је активан прокси диспечер, чиме се обезбеђује доследно понашање. Ажурирајте на v3.5.5+.

### MITM прокси под WSL-ом: десктоп апликације на Windows хосту се не пресрећу

**Узрок:** MITM прокси и његов CA сертификат инсталирају се у окружење у којем OmniRoute ради. Под WSL-ом то окружење је Linux гост, док AI десктоп апликације (Kiro, Trae, Copilot, Zed, …) раде на Windows хосту. Апликације на хосту не верују складишту сертификата госта и не усмеравају саобраћај кроз системски прокси госта, па се пресретање десктоп апликација тамо не активира.

**Препорука:** Покрените OmniRoute изворно на истом оперативном систему као и десктоп апликације које желите да пресрећете (Windows за Windows апликације; исто важи за macOS/Linux). Задржавање OmniRoute-а унутар WSL-а уз циљање апликација на хосту захтева ручно додавање генерисаног CA сертификата као поузданог на Windows хосту и усмеравање мрежних/прокси подешавања сваке апликације на хосту ка WSL прокси крајњој тачки — што представља неподржано и непоуздано подешавање.

## Проблеми са добављачима

### „Language model did not provide messages“

**Узрок:** Квота добављача је исцрпљена.

**Решење:**

1. Проверите праћење квоте на контролној табли
2. Користите комбинацију са резервним нивоима
3. Пређите на јефтинији/бесплатни ниво

### Ограничавање броја захтева

**Узрок:** Претплатничка квота је исцрпљена.

**Решење:**

- Додајте резервну опцију: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Користите GLM/MiniMax као јефтину резервну опцију

### OAuth токен је истекао

OmniRoute аутоматски освежава токене. Ако се проблеми наставе:

1. Контролна табла → Добављач → Поново повежи
2. Избришите везу са добављачем и поново је додајте

### Више Kiro налога: други налог поништава први

**Узрок:** Kiro позадински систем примењује ограничење од једне активне сесије по регистрацији OIDC клијента.
Када два налога деле исти регистровани клијент (везе увезене пре v3.8.0),
освежавање токена једног налога поништава токен за освежавање другог налога.

**Решење (v3.8.0+):** Поново увезите погођене везе.
Почев од v3.8.0, свака нова Kiro веза направљена преко опције **Увези токен**,
**Пријава преко Google/GitHub налога** или **Аутоматски увоз** аутоматски региструје сопствени
наменски OIDC клијент. Веза је стога потпуно изолована и освежавање једног
налога не утиче ни на један други налог.

Везе које су увезене _пре_ v3.8.0 немају регистрацију клијента
по вези. Те везе настављају да користе дељену крајњу тачку за освежавање токена друштвене пријаве.
Да бисте постигли изолацију, избришите стару везу преко Контролна табла → Добављачи и поново је додајте
користећи било који од три поступка увоза.

За све детаље и детаљна упутства за истовремено додавање два Kiro налога,
погледајте [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Проблеми са облаком

### Грешке при синхронизацији са облаком

1. Проверите да `BASE_URL` упућује на вашу покренуту инстанцу (нпр. `http://localhost:20128`)
2. Проверите да `CLOUD_URL` упућује на вашу крајњу тачку у облаку (нпр. `https://omniroute.dev`)
3. Ускладите вредности `NEXT_PUBLIC_*` са вредностима на страни сервера

### `stream=false` у облаку враћа 500

**Симптом:** `Unexpected token 'd'...` на крајњој тачки у облаку за позиве без стримовања.

**Узрок:** Систем узводно враћа SSE садржај, док клијент очекује JSON.

**Привремено решење:** Користите `stream=true` за директне позиве ка облаку. Локално окружење за извршавање садржи резервни механизам за претварање SSE→JSON.

### Облак приказује да је повезан, али пријављује „Неважећи API кључ“

1. Направите нови кључ на локалној контролној табли (`/api/keys`)
2. Покрените синхронизацију са облаком: Омогући облак → Синхронизуј сада
3. Стари/несинхронизовани кључеви и даље могу да врате `401` у облаку

## Проблеми са Docker-ом

### Docker IPv6 / Ресетовање везе

<a name="docker-ipv6"></a>

**Симптоми:** `curl http://localhost:20128/v1/models` враћа `curl: (56) Recv failure: Connection reset by peer`. Контролна табла и крајње тачке без аутентификације раде, али крајње тачке са аутентификацијом не раде — делује као проблем са аутентификацијом, али није.

**Узрок:** `docker run -p 20128:20128` објављује порт и на `0.0.0.0` (IPv4) и на `::` (IPv6), али процес унутар контејнера слуша само на IPv4 адреси. На хостовима на којима се `localhost` прво разрешава у `::1`, веза стиже на објављени IPv6 порт иза којег нема процеса који слуша → веза се ресетује.

**Решење:**

1. **Брза дијагностика:** Покрените `curl -4 http://localhost:20128/v1/models`. Ако ради са `-4`, али не ради без тога, постоји неусклађеност IPv6 повезивања.
2. **Трајно решење:** Експлицитно повежите на IPv4 тако што ћете користити `-p 127.0.0.1:20128:20128` у команди `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Ово намеће IPv4 повезивање и такође спречава излагање проксија на свим интерфејсима хоста.

## Отклањање грешака

### Омогућавање датотека евиденције

Подесите `APP_LOG_TO_FILE=true` у датотеци `.env`. Евиденције апликације записују се у `logs/`.
Артефакти захтева чувају се у `${DATA_DIR}/call_logs/` када је ток обраде евиденције позива
омогућен у подешавањима.
Када је снимање тока обраде омогућено, подесите `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` да бисте изоставили
садржаје делова стрима или прилагодите `CALL_LOG_PIPELINE_MAX_SIZE_KB` да бисте променили ограничење величине артефаката у KB.

### Провера стања добављача

```bash
# Контролна табла стања
http://localhost:20128/dashboard/health

# API провера стања
curl http://localhost:20128/api/monitoring/health
```

### Складиште окружења за извршавање

- Главно стање: `${DATA_DIR}/storage.sqlite` (добављачи, комбинације, алијаси, кључеви, подешавања)
- Коришћење: SQLite табеле у `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + опционално `${DATA_DIR}/call_logs/`
- Евиденције апликације: `<repo>/logs/...` (када је `APP_LOG_TO_FILE=true`)
- Артефакти евиденције позива: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` када је ток обраде евиденције позива омогућен

Радња **Обриши историју** на страници Евиденција захтева брише `call_logs`, застареле
`request_detail_logs` и локални директоријум артефаката `${DATA_DIR}/call_logs/`.

| **Надзор уживо**    | Пратите ток захтева у реалном времену да бисте уочили повремене проблеме са превођењем                                 |

### Уобичајени проблеми са форматима

- **Ознаке за размишљање се не приказују** — Проверите да ли циљни добављач подржава размишљање и подешавање буџета за размишљање

- **Системски упит недостаје** — Claude и Gemini различито обрађују системске упите; проверите излаз превођења
- **SDK враћа необрађени ниски уместо објекта** — Решено у v1.x; програм за чишћење одговора уклања нестандардна поља (`x_groq`, `usage_breakdown`, итд.) која изазивају грешке при Pydantic валидацији у OpenAI SDK-у. Ако ово и даље видите у v3.x+, пријавите проблем.
- **GLM/ERNIE одбија улогу `system`** — Решено у v1.x; нормализатор улога аутоматски спаја системске поруке са корисничким порукама за некомпатибилне моделе. Ако ово и даље видите у v3.x+, пријавите проблем.
- **Улога `developer` није препозната** — Решено у v1.x; аутоматски се претвара у `system` за добављаче који нису OpenAI. Ако ово и даље видите у v3.x+, пријавите проблем.
- **`json_schema` не ради са Gemini-јем** — Решено у v1.x; `response_format` се сада претвара у Gemini-јеве `responseMimeType` + `responseSchema`. Ако ово и даље видите у v3.x+, пријавите проблем.

## Подешавања отпорности

### Аутоматско ограничавање брзине се не активира

- Аутоматско ограничавање брзине примењује се само на добављаче са API кључем (не на OAuth/претплату)
- Проверите да ли је у одељку **Подешавања → Отпорност → Профили добављача** омогућено аутоматско ограничавање брзине
- Проверите да ли добављач враћа статусне кодове `429` или заглавља `Retry-After`

### Подешавање експоненцијалног одлагања

Профили добављача подржавају следећа подешавања:

- **Основно одлагање** — Почетно време чекања након првог неуспеха (подразумевано: 1s)
- **Максимално одлагање** — Горња граница времена чекања (подразумевано: 30s)
- **Множилац** — Колико се одлагање повећава по узастопном неуспеху (подразумевано: 2x)

### Спречавање ефекта крда

Када велики број истовремених захтева погоди добављача са ограничењем брзине, OmniRoute користи mutex + аутоматско ограничавање брзине како би серијализовао захтеве и спречио каскадне неуспехе. Ово се аутоматски примењује на добављаче са API кључем.

### Захтеви за ћаскање не успевају уз 503 / chat_admission_busy

**Симптоми:**

- Крајња тачка за довршавање ћаскања враћа одговор `503` који се може поновити и чији је кôд грешке
  `chat_admission_busy`.
- Одговор садржи `Retry-After`. Од измене #12135, вредност се изводи из уочене
  заузетости — узима се већа вредност између периода `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` који је захтев већ
  чекао и времена током којег се тренутно држе закупи за захтеве великог оптерећења — заокружена навише на целе
  секунде и ограничена на 60. Када је пролаз неактиван, задржавају се историјске доње границе: 2 секунде на
  путањи заснованој на бајтовима, 1 секунда на путањи заснованој на структури (која такође садржи
  `reason: "structure_limit"`).
- Ово се може догодити док је друго ћаскање великог оптерећења или дуготрајни стриминг одговор још увек
  у току.

Тело одговора заснованог на бајтовима је:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Одговор заснован на структури користи исти тип и кôд, са поруком
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
и `reason: "structure_limit"`.
Са подразумеваним праговима, захтев се сматра структурно захтевним када има најмање `200` порука,
најмање `64` алатке или најмање `32,000` процењених токена, или када ограничена процена структуре
исцрпи своје границе од `10,000` посећених чворова или дубине `12`.

**Узрок:** Ово је намерно одбацивање оптерећења унутар OmniRoute-а, а не грешка узводног добављача.
Сваки процес користи локални заштитни механизам како би резервисао ограничени капацитет за велико оптерећење пре задржавања
и рашчлањивања великог тела захтева. Закуп за велико оптерећење остаје активан током читавог трајања SSE
одговора.

**#503-fanout:** пре ове исправке, заштитни механизам је ограничавао конкурентност на фиксни БРОЈ захтева
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, подразумевано `1`) без обзира на меморију хоста, па је
лепезасто ширење агената за програмирање (више подагената/CLI алатки, тела редовно > 256 KB) сводило ефективну
конкурентност на ~1 и доводило до грешака 503 под потпуно нормалним оптерећењем. Заштитни механизам се сада самостално подешава: њиме управља
аутоматски изведен БАЈТ буџет за пријем (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), одређен на основу
стварног меморијског ограничења процеса, а такође проверава и сигнал притиска на ресурсе уживо — тако да
одбацује захтеве само када је хост заиста под притиском меморије, а не само зато што је више од једног
захтевног захтева стигло истовремено. Старо ограничење броја (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) се
и даље поштује, али само ако га изричито подесите.

Када је капацитет заузет, захтев великог оптерећења прво чека највише
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (подразумевано `2000`, `0` онемогућава чекање) да се место ослободи
пре него што врати одговор `503` који се може поновити. Ограничено чекање постоји како би клијенти агенатског типа
(OpenCode, Claude Code, Cursor), који истовремено лепезасто шире захтевне подзахтеве, серијализовали налет
уместо да потроше цео буџет поновних покушаја на тренутна одбијања и прекину рад усред задатка.
Тренутна заузетост закупа за велико оптерећење, разрешени бајт буџет и озбиљност притиска уживо
доступни су на `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — проверите их пре него што измените било коју променљиву окружења.
Подешавања → Отпорност → Ред захтева → Истовремени захтеви не контролише ово; то подешавање
управља засебним механизмом реда захтева добављача.

**Решење:**

1. Прво поновите захтев. Клијенти треба да поштују `Retry-After` и користе одлагање уместо да одмах
   понове захтев.
2. Проверите `/api/monitoring/health` → `chatAdmission` пре било каквог подешавања. `countCapEnabled:
false` и великодушан `maxInflightBytes` значе да аутоматски изведен буџет већ обавља свој
   посао; вредност `pressureSeverity` од `high`/`critical` значи да хост заиста има мало меморије —
   то се не може решити променљивом окружења за пријем, већ је потребно више RAM-а или мање радно оптерећење.
3. Само ако `/api/monitoring/health` покаже да је аутоматски изведен буџет заиста премали за
   ваш хост (што је ретко — већ се прилагођава од контејнера до физичког сервера), директно га замените помоћу
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` уместо да се вратите на застарело ограничење броја захтева.

Погледајте [референцу променљивих окружења](../reference/ENVIRONMENT.md#4-security--authentication)
за меродавна подешавања пријема.

## Опциона таксономија грешака за RAG / LLM (16 проблема)

Неки корисници OmniRoute-а постављају мрежни пролаз испред RAG система или стекова агената. У таквим окружењима често се јавља необичан образац: OmniRoute делује исправно (добављачи су доступни, профили рутирања су исправни, нема упозорења о ограничењу брзине), али је коначни одговор и даље погрешан.

У пракси, ови инциденти обично потичу из низводног RAG цевовода, а не из самог мрежног пролаза.

Ако желите заједнички речник за описивање тих грешака, можете користити WFGY ProblemMap, спољни текстуални ресурс под MIT лиценцом који дефинише шеснаест образаца грешака који се понављају у RAG / LLM системима. На високом нивоу, он обухвата:

- одступање при проналажењу и нарушене границе контекста
- празне или застареле индексе и векторска складишта
- неусклађеност уграђивања и семантике
- проблеме са састављањем промпта и контекстуалним прозором
- колапс логике и претерано самоуверене одговоре
- грешке у дугим ланцима и координацији агената
- одступање меморије и улога код више агената
- проблеме са редоследом постављања и почетног покретања

Идеја је једноставна:

1. Када истражујете лош одговор, забележите:
   - кориснички задатак и захтев
   - комбинацију руте или добављача у OmniRoute-у
   - сваки RAG контекст коришћен низводно (пронађене документе, позиве алата итд.)
2. Повежите инцидент са једним или два броја из WFGY ProblemMap-а (`No.1` … `No.16`).
3. Сачувајте број на сопственој контролној табли, у приручнику за поступање или систему за праћење инцидената, поред OmniRoute евиденција.
4. Користите одговарајућу WFGY страницу да бисте одлучили да ли треба да измените свој RAG стек, механизам за проналажење или стратегију рутирања.

Комплетан текст и конкретна упутства налазе се овде (MIT лиценца, само текст):

[README за WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Овај одељак можете занемарити ако иза OmniRoute-а не покрећете RAG цевоводе или цевоводе агената.

## Познати проблеми у v3.8.0

Проблеми специфични за издање v3.8.0 и њихова тренутна заобилазна решења. Ако исправка буде објављена у каснијој закрпи, ставка ће бити ажурирана или уклоњена.

### Грешке при аутентификацији Devin CLI-ја

**Симптоми:**

- „Devin CLI није пронађен“ или „аутентификација није успела“ при позивању алата који користе Devin
- Провера CLI окружења пријављује `installed=false`

**Узроци:**

- `CLI_DEVIN_BIN` указује на путању која не постоји
- Devin CLI није инсталиран на хосту

**Исправка:**

1. Инсталирајте Devin CLI за своју платформу
2. Подесите `CLI_DEVIN_BIN=/usr/local/bin/devin` (или стварну путању) у `.env`
3. Поново покрените OmniRoute и поновите тестирање преко **Контролна табла → CLI алати**

### Модел је заглављен у периоду мировања (ручно ресетовање)

**Симптоми:**

- Модел остаје наведен као модел у периоду мировања чак и након истека времена
- Захтеви и даље прескачу модел при комбинованом рутирању, иако је временска ознака у прошлости

**Ручно ресетовање:**

- **Контролна табла:** **Подешавања → Периоди мировања модела** → кликните на **Поново омогући** на одговарајућој картици
- **API:** `DELETE /api/resilience/model-cooldowns` са заглављима за управљачку аутентификацију

### Повезивање са добављачем Command Code не успева уз грешку 403

**Симптоми:**

- Грешка 403 при тестирању везе са добављачем Command Code
- Картица добављача приказује „неовлашћено“ након што је добављач управо додат

**Узрок:** OAuth ток није довршен (повратни позив није примљен или токен није трајно сачуван).

**Исправка:**

- Покрените `omniroute providers` из CLI-ја да бисте поново покренули OAuth ток или
- Поново покрените OAuth преко **Контролна табла → Добављачи → Command Code → Поново повежи**

### ModelScope враћа агресивне периоде мировања уз грешку 429

**Симптоми:**

- Веома кратки или тренутни периоди мировања на ModelScope-у након малог налета захтева
- Комбиновано рутирање прескаче ModelScope раније него што се очекује

**Узрок:** ModelScope емитује заглавља `Retry-After` специфична за добављача. v3.8.0 садржи наменску обраду тих заглавља, па их старије верзије погрешно тумаче као генеричке назнаке ограничења брзине.

**Исправка:**

- Уверите се да користите v3.8.0 или новију верзију
- Проверите да ли је прекидач `useUpstream429BreakerHints` омогућен у одељку **Подешавања → Отпорност**

### OMNIROUTE_WS_BRIDGE_SECRET недостаје у продукционом окружењу

**Симптоми:**

- Грешка 401 при сваком захтеву ка Codex/Responses WebSocket мосту када се систем покреће на удаљеном продукционом хосту
- WebSocket руковање са мостом прекида се одмах након повезивања

**Узрок:** Променљива окружења `OMNIROUTE_WS_BRIDGE_SECRET` недостаје у продукционом окружењу.

**Исправка:**

1. Генеришите насумичну тајну: `openssl rand -hex 32`
2. Подесите `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` у окружењу продукционог сервера (и на сваком клијенту који комуницира са мостом)
3. Поново покрените OmniRoute

### Responses API: позадински режим деградиран на синхрони

**Симптоми:**

- Забележено је упозорење: `background mode degraded to synchronous`
- Захтев са `background: true` враћа уобичајени синхрони одговор уместо ознаке позадинског задатка

**Узрок:** v3.8.0 намерно деградира `background: true` на Responses API-ју на синхроно извршавање, уз емитовање упозорења. Потпуно асинхроно позадинско извршавање планирано је за будуће издање.

**Исправка:**

- Прилагодите клијент тако да позив обавља без `background` или
- Сачекајте касније издање које укључује потпуно асинхрони позадински режим (пратите дневник измена)

## Споро покретање / истек времена за проверу спремности

Ако CLI прикаже `⚠ Сервер није одговорио у року од 60s`, али сервер заправо
ради, временски оквир за проверу спремности је прекратак за ваше окружење.

Ово се често дешава у Windows окружењу (антивирус, надгледање система датотека) или у контејнерима
са великим радним оптерећењем при покретању.

**Решење — повећајте временски оквир:**

```bash
# Преко променљиве окружења (остаје подешено између покретања):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 минута
omniroute serve

# Преко CLI опције (само једном):
omniroute serve --ready-timeout 180000
```

Подразумевана вредност је 60 000 ms (60 s). Упозорење је само информативно; сервер
наставља да се покреће у позадини и постаће доступан када се покретање заврши.

Комплетне информације о `OMNIROUTE_READY_TIMEOUT_MS` потражите у
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
