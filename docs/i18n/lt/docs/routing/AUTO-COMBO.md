## Nulinės konfigūracijos automatinis maršruto parinkimas (`auto/` priešdėlis)

> **NAUJA:** Derinio kurti nebereikia. Naudokite `auto/` priešdėlį tiesiogiai bet kuriame kliente.

### Trumpi pavyzdžiai

| Modelio ID     | Variantas | Veikimas                                                                                  |
| -------------- | --------- | ----------------------------------------------------------------------------------------- |
| `auto`         | default   | Visi prijungti teikėjai, LKGP strategija, subalansuoti svoriai                            |
| `auto/coding`  | coding    | Kokybei pirmenybę teikiantys svoriai, tinkami kodui generuoti                             |
| `auto/fast`    | fast      | Mažos delsos svertinis pasirinkimas                                                       |
| `auto/cheap`   | cheap     | Pagal kainą optimizuotas maršruto parinkimas (pirmiausia mažiausia kaina)                 |
| `auto/offline` | offline   | Pirmenybė teikėjams, turintiems didžiausią pasiekiamą kvotą                               |
| `auto/smart`   | smart     | Pirmenybė kokybei + didesnis tyrinėjimo dažnis (10 %), kad modeliai būtų atrandami geriau |
| `auto/lkgp`    | lkgp      | Aiškiai nurodytas LKGP (tas pats kaip numatytasis `auto`)                                 |
| `auto/chaos`   | chaos     | Lygiagretus išsiuntimas, po vieną modelį kiekvienam teikėjui (ne trikčių įterpimas)       |

### Kategorijos × lygio kompozicija (`auto/<category>:<tier>`)

OpenRouter stiliaus priesagos atskiria **maršruto tipą** (kategoriją) nuo **jo optimizavimo būdo** (lygio), todėl juos galima laisvai derinti (#4235 B etapas, `open-sse/services/autoCombo/suffixComposition.ts`):

- **Kategorijos** (filtruoja kandidatų rinkinį pagal galimybes): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` palieka regą palaikančius modelius; `reasoning` palieka samprotavimo / mąstymo modelius.
- **Lygiai** (parenka vertinimo svorius / rinkinio filtrą): `fast` (greitas pateikimas) · `cheap` (alternatyvus pavadinimas `floor`, išlaidų taupymas) · `reliable` (grandinės pertraukiklio būklė + delsos stabilumas) · `free` / `pro` (filtruoja rinkinį pagal modelio lygį naudodamas `classifyTier` — nemokamas lygis arba aukščiausios klasės lygis).

| Pavyzdys               | Rezultatas                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| `auto/coding:fast`     | kodavimo rinkinys, mažos delsos svoriai                                                    |
| `auto/coding:cheap`    | kodavimo rinkinys, optimizuotas pagal kainą (alternatyvus pavadinimas `auto/coding:floor`) |
| `auto/reasoning:pro`   | tik samprotavimo / mąstymo modeliai, aukščiausios klasės lygis                             |
| `auto/vision`          | regą palaikantys modeliai (be lygio → subalansuoti svoriai)                                |
| `auto/multimodal:free` | daugiarūšius duomenis palaikantys modeliai, tik nemokamas lygis                            |

Bet kuris galiojantis `auto/<category>[:<tier>]` išsprendžiamas pagal poreikį; kruopščiai atrinktas poaibis skelbiamas `/v1/models` ir valdymo skydelyje (`AUTO_SUFFIX_VARIANTS`, esantis `open-sse/services/autoCombo/builtinCatalog.ts`). Filtravimas yra **leidžiantis tęsti įvykus klaidai** — jei apribojimo neatitinka nė vienas prijungtas modelis, naudojamas visas rinkinys, kad maršruto parinkimas niekada nenutrūktų. Pagrindinis vertintojas (`combo.ts`) nekeičiamas; kategorijos / lygio filtras taikomas funkcijoje `buildAutoCandidates`.

> **Tiesioginė modelių informacija:** kai įjungta žyma `ARENA_ELO_SYNC_ENABLED`, automatinio maršruto parinkimo tinkamumas nustatomas pagal tiesioginius **Arena ELO** reitingus ir **models.dev** lygių duomenis (kitu atveju naudojamas statinis tinkamumo žemėlapis).

**Kaip naudoti:**

```bash
# Bet kuris OpenAI formatą palaikantis IDE arba CLI įrankis
Bazinis URL: http://localhost:20128/v1
API raktas:  <jūsų-galinio-taško-raktas>

# Savo kode / konfigūracijoje nustatykite modelį:
model: "auto"                 # subalansuotas numatytasis variantas
model: "auto/coding"          # geriausiai tinka kodavimo užduotims
model: "auto/fast"            # greičiausias pasiekiamas
model: "auto/cheap"           # pigiausias pagal žetoną
```

**Kas vyksta:**

1. OmniRoute aptinka `auto/` priešdėlį faile `src/sse/handlers/chat.ts`
2. Duomenų bazėje užklausia visų **aktyvių teikėjų jungčių**
3. Atrenka tas, kurios turi galiojančius prisijungimo duomenis (API raktą arba OAuth prieigos raktą)
4. Nustato kiekvienos jungties modelį (`connection.defaultModel` arba pirmąjį teikėjo modelį)
5. Atmintyje sukuria **virtualų derinį** (jis nesaugomas DB)
6. Parenka maršrutą naudodama pasirinkto varianto svorių profilį ir LKGP strategiją

**Pagrindinės savybės:**

- ✅ **Visada aktyvu:** nereikia perjungiklio, derinio kūrimo ar konfigūravimo
- ✅ **Dinamiška:** automatiškai atspindi šiuo metu prijungtus teikėjus
- ✅ **Seanso pastovumas:** LKGP užtikrina, kad paskutiniam sėkmingam teikėjui būtų teikiama pirmenybė
- ✅ **Kelių paskyrų palaikymas:** kiekviena teikėjo jungtis tampa atskiru kandidatu
- ✅ **Nerašoma į DB:** virtualus derinys egzistuoja tik užklausos metu, todėl nėra jokių ilgalaikio saugojimo sąnaudų

### Kandidatų valdymas pagal raktą (#7819, 1+2 lygis)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = priesaga po `auto/` arba
pažodinis `auto` baziniam kanalui) yra **tik skaitomas** galinis taškas, pateikiantis
dabartinį `auto/*` kanalo kandidatų rinkinį su tiesiogine pasiekiamumo informacija ir
pakartotinai naudojantis esamais atsparumo nuskaitymais (niekada nenaudojama neapdorota
pertraukiklio `state`):

- teikėjo grandinės pertraukiklis — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- jungties laukimo laikotarpis — `rateLimitedUntil` / `testStatus` išspręstoje
  `provider_connections` eilutėje
- modelio blokavimas — `isModelLocked(provider, connectionId, model)`

Kiekvienas kandidatas taip pat turi šio API rakto žymą `excluded`. Išimtys saugomos
atskirai kiekvienam API raktui (`auto_candidate_overrides` lentelė, migracija `128`) —
OmniRoute yra vieno nuomininko sistema be `users` lentelės, todėl `apiKeyId` yra
artimiausia tikra kiekvieno kvietėjo tapatybė — ir pritaikomos kandidatų rinkinio
kontroliniame taške, esančiame
`open-sse/services/autoCombo/virtualFactory.ts`, naudojant gryną, vienetų testais
patikrintą `filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`).
Filtras yra **leidžiantis tęsti įvykus klaidai**: nenustatytas apiKeyId / kanalas arba
DB paieškos klaida palieka rinkinį nefiltruotą, todėl operatoriui, kuriam nesukonfigūruotos
jokios išimtys, maršruto parinkimas baitų tikslumu išlieka toks pat kaip prieš šią funkciją.

**Atidėta tolesniam klausimui:** kiekvieno kandidato svoriai + aiški tvarka (3 lygis
— naudojami esamuose svorinės / prioritetinės strategijos keliuose) ir konkrečios
`combo.ts` strategijos susiejimas su kiekvienu `auto/*` kanalu (4 lygis). Žr. #7819 planą dėl atviro
klausimo, ar, atsižvelgiant į vieno nuomininko modelį, perrašymai turėtų likti susieti su kiekvienu API raktu, ar tapti visuotiniai.

**Veikimas viduje:**

```txt
Užklausa: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts aptinka prefiksą
   ↓
createVirtualAutoCombo('coding') → candidatePool iš aktyvių ryšių
   ↓
handleComboChat (tas pats variklis kaip ir išsaugotiems deriniams)
   ↓
Automatinis vertinimas kiekvienai užklausai parenka geriausią teikėją / modelį
```

**Įgyvendinimo failai:**

| Failas                                                    | Paskirtis                                          |
| --------------------------------------------------------- | -------------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | Prefikso analizatorius (`parseAutoPrefix`)         |
| `open-sse/services/autoCombo/virtualFactory.ts`           | Kuria virtualius `AutoComboConfig` objektus        |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | Testavimo sąsaja teikėjų registrui imituoti        |
| `src/sse/handlers/chat.ts`                                | Integracija: spartusis automatinio prefikso kelias |
| `src/shared/constants/providers.ts`                       | `SYSTEM_PROVIDERS.auto` sistemos įrašas            |

## Kombinacijų pavadinimai, sutampantys su tikru modelio ID

Kombinacija, kurios `name` yra identiškas nepapildytam modelio ID (pvz., kombinacija, pavadinta
`gpt-5.5`), yra **sąmoningai palaikomas naudojimo būdas**, o ne klaida: tai
atsarginio paslaugų teikėjo parinkimo pagal modelio ID mechanizmas, aprašytas
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940). Kadangi kombinacijų
atitiktis tikrinama prieš nepapildyto modelio ID atitiktį
(`getComboForModel()` faile `src/sse/services/model.ts`), užklausa dėl nepapildyto
ID `gpt-5.5` nukreipiama per kombinacijos paskirties vietas (pvz.,
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`), o ne tiesiai pas
vieną paslaugų teikėją — taip pakartotinai panaudojama pirmumo taisyklė, pagal kurią
kombinacija tikrinama prieš perrašymą, sukurta
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227), o regresijos
tikrinamos testais `tests/unit/responses-combo-resolution-3227.test.ts` ir
`tests/unit/combo-name-codex-responses-rewrite.test.ts`.

Kombinacijos kūrimas arba pervadinimas suteikiant jai pavadinimą, kuris užgožia tikrą modelio ID,
**niekada neatmetamas** — kitaip būtų pažeistas šis dokumentuotas darbo procesas. Vietoje to
(#8530), `POST /api/combos` ir `PUT /api/combos/[id]` prie atsako prideda neblokuojantį
`warning` lauką, kai (naujas) pavadinimas sutampa su tikru
modelio ID:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

Paleidimo metu `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) taip pat į žurnalą įrašo vienos eilutės `[STARTUP]` įspėjimą,
kuriame išvardijamos visos esamos kombinacijos, užgožiančios modelio ID, kad operatoriai, kurie
su tuo susidūrė netyčia (o ne sąmoningai, kaip aprašyta #6940), gautų įspėjamąjį signalą.
Aptikimo pagalbinė funkcija yra faile `src/lib/combos/modelNameCollision.ts`.

## Pasirinktinės kombinacijos iškvietimas iš kliento

Išsaugotos kombinacijos (Nustatymai → Kombinacijos) naudojamos tik tada, kai klientas `model` lauke siunčia **tikslų kombinacijos pavadinimą** — nėra nei apytikslės ar dalinės kombinacijos pavadinimo atitikties, nei `auto/` priešdėlio. Atitikties nustatymo tvarka (`getComboForModel()` faile `src/sse/services/model.ts`):

1. tiksli kombinacijos pavadinimo atitiktis (`model: "my-combo"`),
2. `combo/<name>` priešdėlis (`model: "combo/my-combo"`),
3. modelio→kombinacijos glob šablonų susiejimai (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

Dvi dažnos klaidos:

- **`auto` nenaudoja jūsų kombinacijų.** `auto`/`auto/*` sukuria savo be konfigūracijos veikiančių kandidatų telkinį ir atsižvelgia į išsaugotas kombinacijas tik tuo atveju, jei kombinacija tiesiogine prasme pavadinta `auto` (nerekomenduojama). Norėdami nukreipti per kombinaciją, siųskite tikslų jos pavadinimą, o ne `auto`.
- **`openrouter/auto` yra tikras mokamas OpenRouter produktas** („Automatiškai parenkamas geriausias prieinamas“), o ne OmniRoute alternatyvusis pavadinimas. Tai yra vienintelis statinis OpenRouter registro modelio įrašas (`open-sse/config/providers/registry/openrouter/index.ts`), už kurį atsiskaitoma atskirai. Norėdami jo neįtraukti į `auto` telkinius, naudokite Nustatymai → Maršruto parinkimas → Slėpti mokamus modelius.

Pirminė painiava, kurią paaiškina šis dokumentas, aprašyta [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) ir [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111).

## Kaip tai veikia (išsaugomi automatiniai deriniai)

Automatinių derinių variklis dinamiškai parenka geriausią paslaugų teikėją ir modelį kiekvienai užklausai, naudodamas **16 veiksnių vertinimo funkciją** (apibrėžtą `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`). Numatytųjų svorių suma yra `1.0`; pasirinktiniai svoriai iš naujo normalizuojami naudojant `normalizeScoringWeights()`. Dviejų iš šešiolikos veiksnių — `cacheAffinity` ir `resetWindowAffinity` — numatytasis svoris yra `0`; `reliability` svoris `DEFAULT_WEIGHTS` yra `0`, tačiau bendruosiuose rinkiniuose jis yra `0.03`, o rinkinyje `reliability-first` — `0.04`; `quality` svoris rinkiniuose yra `0.02` (rinkinyje `quality-first` — `0.03`). Jie vis tiek apskaičiuojami kiekvienam kandidatui, o `cacheAffinity` už vertinimo funkcijos ribų valdo raginimų podėlio dubliavimo šalinimą, todėl veiksniai, kurių numatytasis svoris lygus nuliui, pagal numatytuosius nustatymus tiesiog nedalyvauja vertinant, tačiau rinkiniuose yra naudojami.

### `weighted` semantika

`weighted` yra **proporcingas atsitiktinis pasirinkimas kiekvienai užklausai**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), o ne išlyginimo mechanizmas:

- Kiekvienai užklausai pasirenkamas **vienas** žingsnis, kurio tikimybė yra `weight / totalWeight`; likę žingsniai
  tai užklausai surikiuojami mažėjančia svorio tvarka kaip atsarginė grandinė.
- Žingsnis, kurio svoris yra `0` (arba nenurodytas), **niekada nepasirenkamas**, kol bent vieno kito žingsnio
  svoris yra > 0 — jis gali būti naudojamas tik kaip atsarginis variantas, jei pasirinktas žingsnis nepavyksta. Tik kai **visi**
  svoriai yra 0, pasirinkimas tampa tolygiai atsitiktinis.
- Žingsniai, kurių visi tikslai nepasiekiami — teikėjo grandinės pertraukiklis yra `OPEN`, ryšiui taikomas
  laukimo laikotarpis arba modelis užblokuotas — prieš pasirenkant pašalinami
  (`open-sse/services/combo/targetResolution.ts`), todėl vienintelis tinkamai veikiantis žingsnis gali laikinai
  būti pasirinktas kiekvienai užklausai.
- `stickyWeightedLimit` (kombinacijos konfigūracija, numatytoji reikšmė `1` = išjungta) išlaiko pasirinktą žingsnį tiek
  sėkmingų užklausų iš eilės, prieš atliekant naują pasirinkimą.

Griežtai rotacijai naudokite `round-robin`; vienodi `weighted` svoriai suteikia statistinį, o ne
griežtą balansą.

### Agentinio konvejerio režimas

`pipeline` derinys, turintis bent du modelius, gali įjungti planuotojo / vykdytojo maršruto parinkimą
naudojant `config.agenticOrchestration.enabled`. Pirmasis tikslas atsakingas už planavimą ir galutinius atsakymus;
antrasis tikslas generuoja kliento vietinio formato įrankių iškvietimus. „OmniRoute“ pagal užklausos protokolą aptinka
tęsinius su įrankių rezultatais, klausia planuotojo, ar reikia dar vieno įrankių vykdymo ciklo,
ir dinamiškai parenka vykdytoją arba planuotoją kaip galutinį klientui skirtą
etapą.

Po antrojo tikslo nurodyti papildomi modeliai yra iš eilės naudojami kaip atsarginiai vykdytojai. Gavus nesėkmingą
HTTP atsakymą arba įvykus transporto išimčiai pereinama prie kito vykdytojo, išlaikant
tą patį planuotojo sprendimą bei vietinius įrankius, tačiau naudojant to vykdytojo etapo instrukciją ir
nustatytą ryšį. Pirmasis sėkmingas atsakymas grąžinamas nepakeistas, įskaitant
SSE srautinį perdavimą; prasidėjus sėkmingam srautui, vėlesnių trikčių čia pakartotinai apdoroti negalima.
Jei visi vykdytojai patiria triktį, grąžinama paskutinė triktis. Klientui nutraukus užklausą, siuntimas sustabdomas.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

Vykdytojas viename atsakyme gali pateikti kelis nepriklausomus iškvietimus. Priklausomi iškvietimai
apdorojami vėlesniuose kliento įrankių rezultatų cikluose, planuotojui peržiūrint kiekvieną rezultatą.
Numatytoji `maxToolRounds` reikšmė yra `8`, o priimamas intervalas — `1`–`32`; pasiekus šią ribą, planuotojas turi
pateikti geriausią įmanomą galutinį atsakymą. Vidiniai planuotojo sprendimai kaupiami buferyje, o
pasirinktame klientui skirtame atsakyme išlaikoma pradinė srautinio perdavimo nuostata.

### `round-robin` susietas paketinis apdorojimas ir paskyrų išplėtimas

„Round-robin“ apdorojimas vykdomas paketais, o ne po vieną užklausą kiekviename etape:

- `stickyRoundRobinLimit` (pirmiausia derinio konfigūracija, tada `comboStickyRoundRobinLimit`, tada
  `settings.stickyRoundRobinLimit`, numatytoji reikšmė **3**) išlaiko tą patį tikslą tiek
  sėkmingų užklausų iš eilės, prieš pereinant prie kito. Nustatykite derinio perrašymo reikšmę į `1`, kad tikslas būtų keičiamas
  po kiekvienos užklausos. Derinio rengyklėje rodoma galiojanti reikšmė ir sluoksnis, iš kurio ji gauta.
- `connectionAwareExpansion` (pirmiausia derinio konfigūracija, tada nuostatos, numatytoji reikšmė **false**) išplečia
  kiekvieną teikėjo lygmens etapą į atskirus paskyrų tikslus prieš atliekant rotaciją. B grupės strategijos
  (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp,
  fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion,
  pipeline) išlaiko teikėjo lygmens rodinį, kol ši funkcija neįjungta. Derinio rengyklėje galima pasirinkti
  paveldėjimą / įjungimą / išjungimą; paveldint naudojama visuotinė numatytoji reikšmė (išjungta).
- Maršruto parinkimas pagal užklausų podėlio lokalumą (`promptCacheAffinityEnabled`, numatytoji reikšmė **true**) pertvarko
  fiksuotus ryšius, kad sutampantys podėlio raktai liktų vienoje paskyroje. Jam teikiama pirmenybė prieš
  „round-robin“ ir svertinę rotaciją tarp fiksuotų kiekvienos paskyros etapų. Jei reikia griežtos rotacijos, išjunkite jį skiltyje
  Settings → Combo defaults. Atskiro derinio perrašymo nėra.

Kelių paskyrų rotacijai viename modelyje geriau naudoti **vieną dinaminės paskyros etapą** (tuščias
`connectionId`, visas telkinys) su susiejimo riba `1`, o ne tris fiksuotus `connectionId`.
Naudojant fiksuotus etapus kartu su susiejimu, pasirenkama ta pati paskyra, net kai RR skaitiklis
didėja.

## Sintezės strategija

`fusion` yra vienintelė strategija, kuri **nepasirenka** vieno tikslinio modelio. Ji vienu metu
perduoda užklausą **kiekvienam komisijos modeliui lygiagrečiai**, o tada konfigūruojamas
**vertinimo modelis** iš visų komisijos atsakymų susintetina vieną galutinį atsakymą. Perkelta iš pirminio `decolua/9router`
(„OpenRouter“ Fusion architektūros); realizacija pateikta `open-sse/services/fusion.ts`.

Kaip tai veikia:

0. **Užklausų su įrankiais apėjimas** — užklausa, kurioje yra netuščias `tools` masyvas, o
   `tool_choice` nėra aiškiai nustatytas į `"none"`, visiškai praleidžia komisiją: ji nukreipiama tiesiai į
   vieną modelį (sukonfigūruotą vertinimo modelį arba `panel[0]`), nekeičiant perduodamų `tools`/`tool_choice`.
   Komisijos nariai neturi prieigos prie įrankių, o vertinimo modelio
   sintezės nurodymas neskatina generuoti įrankių iškvietimų, todėl agentinės / įrankius iškviečiančios kliento programos
   gauna tikrą sprendimą dėl įrankio iškvietimo, o ne susintetintą tekstą (#6771).
1. **Lygiagretus išskleidimas** (tik užklausoms be įrankių) — užklausa vienu metu siunčiama kiekvienam komisijos
   modeliui, priverstinai išjungiant srautinį perdavimą ir pašalinant įrankius (vertinimo modeliui sintezei
   reikia išsamių tekstinių atsakymų).
2. **Surinkimas su kvorumo atidėjimu** — kai tik gaunama `minPanel` atsakymų, paleidžiamas trumpas
   papildomo laukimo laikmatis vėluojantiems modeliams, o jam pasibaigus sintezė tęsiama su tuo, kas buvo surinkta.
   Taip apribojama lėčiausio modelio įtaka bendrai vykdymo trukmei, kurią taip pat riboja griežtas skirtasis laikas.
3. **Vertinimo modelio sintezė** — komisijos atsakymai anonimizuojami (`Source 1`, `Source 2`, … — kad
   vertinimo modelis vertintų turinį, o ne modelio prekės ženklą) ir perduodami vertinimo modeliui, kuris išanalizuoja
   sutapimus / prieštaravimus / dalinę aprėptį / unikalias įžvalgas / nepastebėtus aspektus, o tada
   parengia **vieną** autoritetingą atsakymą. Vertinimo modelio iškvietimas išlaiko pradinę kliento
   `stream` reikšmę ir įrankius, todėl srautinis perdavimas ir tolesnis įrankių naudojimas tebėra galimi.
4. **Sklandus funkcionalumo mažinimas** — 0 komisijos atsakymų → `503`; jei išlieka tik 1 atsakymas →
   jis grąžinamas tiesiogiai (nėra ko sintetinti); vieno modelio komisija atsako tiesiogiai.

Komisijos narys taip pat gali būti `combo-ref` veiksmas (`{kind: "combo-ref", comboName: "..."}`), nurodantis
kitą derinį — jis vykdomas kaip **vienas uždaras komisijos balsas** (atliekamas visas rekursinis iškvietimo perdavimas į
nurodytą derinį, o ne lygiagretus išskleidimas į to derinio tikslinius modelius), taikant tą pačią gylio ir ciklų apsaugą,
kurią jau naudoja visos kitos `combo-ref` naudojančios strategijos (#6764).

## Virtuali „Auto-Combo“ gamykla

„Auto Combo“ varikliui nereikia iš anksto apibrėžtų kombinacijų. Vietoje to `open-sse/services/autoCombo/virtualFactory.ts` dinamiškai kuria kandidatus:

1. Gauna `getProviderConnections({ isActive: true })` (visus įjungtus ryšius)
2. Atrenka ryšius su galiojančiais prisijungimo duomenimis (API raktu arba nepasibaigusio galiojimo „OAuth“ prieigos raktu, naudojant `hasUsableOAuthToken()`)
3. Sutikrina juos su `getProviderRegistry()`, kad nustatytų modelių pasiekiamumą ir kainodarą
4. Kiekvienai sekai `(provider, model, connection)` sukuria `VirtualAutoComboCandidate`
5. Kaip siuntimo tikslą pasirenka `connection.defaultModel` (arba pirmąjį registro modelį)
6. Įvertina kiekvieną kandidatą naudodama 16 veiksnių `scorePool()` ir varianto svorių rinkinį
7. Grąžina gautą atmintyje laikomą `AutoComboConfig`, skirtą `handleComboChat()` — jis niekada neišsaugomas DB

Tai reiškia, kad **pridėjus naują teikėją su įjungtu `auto/*`, kandidatų telkinys automatiškai išplečiamas** — kombinacijos nereikia redaguoti rankiniu būdu. Virtuali kombinacija atkuriama kiekvienai užklausai, todėl naujai pridėti arba vėl tinkamai veikiantys ryšiai panaudojami iš karto.

## Savaiminis atkūrimas

- **Laikinas pašalinimas**: Įvertis < 0.2 → pašalinama 5 min. (progresyvus atidėjimas, daugiausia 30 min.)
- **Grandinės pertraukiklio būsenos įvertinimas**: OPEN → automatiškai pašalinama; HALF_OPEN → bandomosios užklausos
- **Incidento režimas**: >50 % OPEN → išjungiamas tyrinėjimas, maksimaliai padidinamas stabilumas
- **Atkūrimas po laukimo laikotarpio**: Pasibaigus pašalinimui, pirmoji užklausa yra „bandomoji“ ir jai taikomas trumpesnis skirtasis laikas

## Bandito tyrinėjimas

5 % užklausų (šį dydį galima konfigūruoti) tyrinėjimo tikslais nukreipiamos atsitiktiniams teikėjams. Incidento režimu ši funkcija išjungiama.

## API

**Nėra atskiro `POST /api/combos/auto` galinio taško** — automatinis derinys naudojamas dviem būdais:

2. **Išsaugotas derinys su `strategy: "auto"`:** sukurkite įprastą derinį per `POST /api/combos` ir nustatykite `strategy: "auto"` bei `config.auto.weights` / `config.auto.candidatePool`. Skelbti DIDŽIAUSIĄ reikšmę yra saugu, nes automatinio derinio konteksto pirminis filtras per dideles užklausas nukreipia kandidatams su dideliais langais.

### Automatinio maršruto parinktuvo strategijos

Išsaugotuose `strategy: "auto"` deriniuose galima nustatyti `config.routerStrategy` (arba senesnį
`config.auto.routerStrategy`) į vieną iš šių reikšmių:

- `rules` — numatytasis svertinis vertinimas
- `score` — pasirenka didžiausią sukonfigūruotą svertinį įvertį. Esant visiškai vienodiems įverčiams išlaikoma sukonfigūruota
  kandidatų tvarka; esamas `explorationRate` atrenka iš viso surikiuoto rinkinio.
- `cost` / `eco` — pigiausias tinkamai veikiantis teikėjas
- `latency` / `fast` — mažiausia p95 delsa, pritaikius patikimumo baudą
- `sla-aware` / `sla` — pirmenybė teikiama kandidatams, atitinkantiems p95 delsos, klaidų dažnio ir pasirinktinius
  kainos SLO
- `lkgp` — pirmiausia naudojamas paskutinis žinomas gerai veikiantis teikėjas
- `nadir` — paklausia [Nadir](https://getnadir.com) sprendimų API, kurio rinkinyje esančio modelio
  reikia užklausai; pasirenkama funkcija, o įvykus klaidai pereinama prie `rules`

### Išsamiai apie maršruto parinktuvo strategijas

Automatinio derinio variklis pateikia 7 keičiamus **RouterStrategy** įgyvendinimus, kuriuos
galite keisti naudodami `config.routerStrategy` (arba senesnį `config.auto.routerStrategy`).
Kiekviena strategija iš kandidatų rinkinio pasirenka vieną teikėją pagal `RoutingContext`
(užduoties tipą, įrankių / vaizdo požymius, numatomą žetonų skaičių, pasirinktinę SLA politiką, pasirinktinį
paskutinį žinomą gerai veikiantį teikėją).

#### 1. `rules` (numatytoji) — 16 veiksnių svertinis vertinimas

Apgaubia esamą vertinimo variklį. Išfiltruoja kandidatus, kurių grandinės pertraukiklio
būsena yra `OPEN`, tada paleidžia `scorePool()` su dabartiniu užduoties tipu ir `getTaskFitness()`,
pasirinkdama didžiausią įvertį gavusį teikėją.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**Kada naudoti**: numatytasis pasirinkimas. Naudokite, kai norite subalansuoto kompromiso tarp visų signalų.

**Alternatyvus pavadinimas**: `rules` (alternatyvaus pavadinimo nėra)

---

#### 2. `cost` / `eco` — pigiausias tinkamai veikiantis teikėjas

Surikiuoja kandidatų rinkinį pagal `costPer1MTokens` (didėjančia tvarka) ir pasirenka pigiausią.
Pirmiausia išfiltruoja kandidatus, kurių būsena yra `OPEN`.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Kada naudoti**: kainai jautriems darbo krūviams, paketiniam apdorojimui arba foninėms užduotims.

**Alternatyvūs pavadinimai**: `cost`, `eco`

---

#### 3. `latency` / `fast` — mažiausia p95 delsa, pritaikius patikimumo baudą

Rikiuoja pagal `p95LatencyMs + (errorRate * 1000)`. Bauda už klaidų dažnį užtikrina,
kad nepatikimi teikėjai būtų reitinguojami žemiau, net jei jų nominali delsa yra maža.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Kada naudoti**: delsai jautriems darbo krūviams, pvz., pokalbiams realiuoju laiku, automatiniam užbaigimui arba
interaktyviems programavimo asistentams.

**Alternatyvūs pavadinimai**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — delsos / klaidų / kainos SLO atitiktis

Kiekvieną kandidatą įvertina pagal tai, kaip gerai jis atitinka sukonfigūruotą SLO politiką:

| Veiksnys          | Svoris | Formulė                                                           |
| ----------------- | ------ | ----------------------------------------------------------------- |
| Delsos įvertis    | 35%    | `threshold / max(value, ε)`                                       |
| Klaidų įvertis    | 35%    | `threshold / max(value, ε)`                                       |
| Būsenos įvertis   | 15%    | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)                 |
| Sąnaudų įvertis   | 10%    | `threshold / max(value, ε)` arba atvirkščiai normalizuota reikšmė |
| Stabilumo įvertis | 5%     | atvirkščiai normalizuotas delsos standartinis nuokrypis           |

Kai `hardConstraints: true`, kandidatai pirmiausia rikiuojami pagal **pažeidimo įvertį**
(kiek jie viršija kurį nors SLO), o tada pagal sudėtinį įvertį. Kitu atveju naudojamas tik
sudėtinis įvertis.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... kiekvienas kandidatas įvertinamas pagal politiką: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA laukai** (nustatomi kombinacijos konfigūracijoje):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**Kada naudoti**: Produkcinėms darbo apkrovoms, kurioms taikomi griežti delsos, klaidų dažnio ar sąnaudų apribojimai.

**Alternatyvūs pavadinimai**: `sla-aware`, `sla`

#### 5. `lkgp` — pirmiausia paskutinis žinomas tinkamas teikėjas

Pirmiausia bandomas **paskutinis žinomas tinkamas teikėjas** (jei nustatytas), tada pereinama prie
`rules` strategijos. Tai naudinga sesijos susiejimui — tas pats teikėjas apdoroja
tolesnes pokalbio užklausas.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Pereinama prie rules strategijos
    return getStrategy("rules").select(pool, context);
  }
}
```

**Kada naudoti**: Kelių žingsnių pokalbiams, kai norite, kad tas pats teikėjas apdorotų
tolesnes užklausas (pvz., dėl podėliavimo, konteksto tęstinumo ar kainodaros nuoseklumo).

**Alternatyvus pavadinimas**: `lkgp` (nėra alternatyvaus pavadinimo)

#### 6. `nadir` — užklausą įvertinantis modelio pasirinkimas naudojant Nadir

Kiekviena pirmiau aprašyta strategija reitinguoja kandidatus pagal savo telemetriją; nė viena iš jų neskaito
užklausos. `nadir` siunčia paskutinę naudotojo žinutę kartu su telkinio modelių ID į
[Nadir](https://getnadir.com) sprendimų API (`POST /v1/bucket`) ir nukreipia į modelį,
kurį Nadir pasirenka iš šio sąrašo (`simple` → pigiausias tinkamas modelis, `complex` → pažangiausias
modelis). Tą modelį aptarnaujantis ryšys vis tiek parenkamas naudojant `rules`, todėl kvota,
būsena ir sąnaudos ir toliau lemia, kuri paskyra bus pasirinkta.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` ir `OMNIROUTE_NADIR_BASE_URL` yra atsarginės aplinkos kintamųjų reikšmės šioms dviem
eilutėms. `baseUrl` reikalingas tik savarankiškai talpinamam Nadir (galinis `/v1` yra leidžiamas).
Užklausos be rakto patenka į anoniminį Nadir planą, kurio užklausų dažnis ribojamas pagal IP.

Kas išsiunčiama už sistemos ribų: paskutinės naudotojo žinutės tekstas (pirmieji 16 tūkst. simbolių), kandidatų
modelių ID ir `source: "omniroute"` kanalo žyma. Nei sistemos instrukcija, nei istorija, nei įrankiai ar
antraštės nesiunčiami.

Gedimo atveju taikomas atviras atsarginis režimas: pasibaigus skirtajam laikui (numatytoji reikšmė – 2000 ms), gavus ne 2xx atsakymą, nepasiekiamą
serverį, netinkamai suformuotą atsakymą arba pasirinkimą, kurio nėra telkinyje, grąžinamas `rules`
sprendimas, o priežasties pradžioje pridedama `NadirStrategy: fallback (…)`. Po nepavykusio iškvietimo
strategija 30 s nesikreipia į tinklą, todėl sutrikimas kainuoja vieną laukimo laikotarpio viršijimą per 30 s, o ne
po vieną kiekvienai užklausai. Maršruto parinkimo įvykiuose `strategy: "nadir"` nurodoma tik tada, kai pasirinkimą
iš tikrųjų atliko Nadir.

**Kada naudoti**: skirtingo sudėtingumo srautui telkinyje, apimančiame skirtingų lygių modelius (mažą, vidutinį
ir pažangiausią modelį), kai norite sumažinti sąnaudas, patiriamas visada naudojant pažangiausią modelį.

**Alternatyvus pavadinimas**: `nadir` (nėra alternatyvaus pavadinimo)

## Kaip lygiai dera su Auto-Combo

16 veiksnių vertinimo funkcija (`open-sse/services/autoCombo/scoring.ts`) narystę lygyje vertina kaip du signalus: `tierPriority` (0.0476) ir `tierAffinity` (0.0476). Visą `DEFAULT_WEIGHTS` rinkinį žr. aukščiau pateiktoje kanoninėje [vertinimo veiksnių lentelėje](#how-it-works-persisted-auto-combos) — kiekvieno paketo išimtys (ship-fast/cost-saver/quality-first/
offline-friendly) pateiktos lentelėje „Svorių profiliai pagal paketą“.

Vien lygis **neužtikrina**, kad 1 lygis bus pirmas — jei 1 lygio delsa yra didelė arba kainos ir kokybės santykis nėra optimalus, laimi 2 lygis. Norėdami užtikrinti eiliškumą pagal lygius, naudokite derinio strategiją `priority` ir išdėstykite teikėjus pagal lygį.

Norėdami suteikti didelę pirmenybę 1 lygiui (prenumeratai), padidinkite `tierPriority` svorį:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

Lygių apibrėžtis ir teikėjų klasifikaciją žr. [`docs/guides/TIERS.md`](../guides/TIERS.md).

## Testavimas ir aprėptis

### Deterministinė maršruto parinkimo sprendimų matrica (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` patvirtina visų 19 viešųjų strategijų maršruto parinkimo **sprendimą**
nuo pradžios iki galo per tikrąjį derinių konvejerį, naudojant imituojamą išorinę paslaugą.
Aprėpiama:

- Visos 19 `ROUTING_STRATEGY_VALUES` strategijų (ordered, weighted, cost, context, fusion, …).
- Visapusis `quota-share` (vidinės strategijos) testavimas: DRR teisingumas + apkrovos prisotinimo prioriteto mažinimas per
  tikrąją `selectQuotaShareTarget` sąsają (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`).
- Universaliojo perdavimo `context-relay` aprėptis su kiekvienu galimu paskirties vietų skaičiumi.

Šis testų rinkinys vykdomas CI (`test:integration` užduotyje) su `--test-concurrency=1` ir
`--test-force-exit`, todėl jis yra deterministinis ir jam nereikia tikrų prisijungimo duomenų.

### Sąlyginiai tiesioginiai baziniai testai (NE CI aplinkoje — tikri teikėjai)

| Komanda                                | Ką ji atlieka                                                                                                                |
| :------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | Tikras maršruto parinkimas tame pačiame procese su `RUN_COMBO_LIVE=1`; sukuriama veikiančios „OmniRoute“ DB momentinė kopija |
| `npm run test:combo:live:vps`          | HTTP iškvietos į veikiantį „OmniRoute“ serverį (nustatykite `COMBO_LIVE_BASE_URL`)                                           |
| `npm run test:combo:live:vps:failover` | Tas pats, tačiau su sąmoningai sukeltais perjungimo sutrikimo atveju scenarijais                                             |

Šie baziniai testai tikrina tikrąjį duomenų perdavimo kelią (derinys → teikėjas → užbaigimas). Jie
sąmoningai neįtraukti į CI, nes jiems reikia tikrų prisijungimo duomenų ir prieigos prie VPS.
