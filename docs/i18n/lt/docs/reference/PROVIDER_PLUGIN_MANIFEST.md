`open-sse/config/providerPluginManifest.ts` apibrėžia su JSON suderinamą teikėjo
papildinio sutartį. `open-sse/config/providerPluginManifestRegistry.ts` susieja šią
sutartį su dabartiniu teikėjų registru, skirtu tokiems „sidecar“ komponentams kaip Bifrost,
CLIProxyAPI ar būsimas Go/Rust maršruto parinktuvas. TypeScript registras išlieka
pirminiu tiesos šaltiniu, tačiau „sidecar“ komponentai gali naudoti manifestą neimportuodami
vykdyklių kodo, numatytųjų OAuth reikšmių, antraščių ar proceso aplinkos būsenos.

Tas pats manifestas pasiekiamas per HTTP adresu
`GET /api/v1/provider-plugin-manifest`, kad jį galėtų naudoti atskirame procese veikiantys „sidecar“ komponentai.

OmniRoute perduoda šį URL Bifrost ir CLIProxyAPI per
`X-OmniRoute-Provider-Manifest-Url` užklausos antraštę. Nustatykite
`OMNIROUTE_PROVIDER_MANIFEST_URL`, kai „sidecar“ komponentui reikia viešojo arba konteinerio
tinklo URL, o ne vietinės užklausos kilmės adreso.

## Manifesto atnaujinimas

HTTP galinis taškas grąžina `Cache-Control: public, max-age=60` ir stiprią
`ETag` reikšmę. „Sidecar“ komponentas turėtų išsaugoti paskutinį patvirtintą manifestą ir atnaujindamas
siųsti jo ETag antraštėje `If-None-Match`. Atsakymas `304 Not Modified` neturi turinio;
„sidecar“ komponentas toliau naudoja podėlyje saugomą manifestą. Jei patvirtinto podėlyje saugomo manifesto nėra,
„sidecar“ komponentas privalo siųsti besąlyginę užklausą, užuot priėmęs `304`.

## Tikslas

Perkelti teikėjų metaduomenis į papildinio sutartį, kad ilgainiui apdorojamų užklausų
kelias galėtų priklausyti mažesnės delsos „sidecar“ komponentui, o OmniRoute išlaikytų
TypeScript maršrutą kaip politikos vartus ir atsarginį variantą. Manifestas yra papildomas:
pats savaime jis nekeičia užklausų maršruto parinkimo.

## Sutartis

Manifeste pateikiama:

- teikėjo ID ir alternatyvusis vardas
- aukštesnio lygmens paslaugos formatas ir vykdyklės pavadinimas
- autentifikavimo tipas, autentifikavimo antraštė ir pasirinktinis autentifikavimo priešdėlis
- statiniai galinio taško metaduomenys
- tinkamumas „sidecar“ komponentui ir aiškios priežastys, kodėl teikėjas turėtų likti TS kelyje
- su JSON suderinami modelio metaduomenys, pvz., konteksto ilgis, vaizdų ir samprotavimo
  požymiai bei nepalaikomi parametrai
- galimybių žymos, įskaitant `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` ir `usage-supported`

Į manifestą sąmoningai neįtraukiama:

- OAuth kliento paslaptys ir numatytosios slaptos reikšmės
- vykdymo aplinkos reikšmių nustatymas
- užklausų antraštės ir viešųjų prisijungimo duomenų pagalbinės priemonės
- dinaminės URL kūrimo priemonės
- vykdyklių funkcijos
- vidiniai seansų telkinio elementai

## Galimybių žymos

`capabilities` yra surūšiuotas iš registro įrašo išvestų žymų masyvas. Integruotojai
turėtų jį laikyti mašininiu būdu nuskaitomu atsakymu į klausimą „ką gali šis teikėjas“, užuot
iš naujo analizavę TypeScript šaltinius.

| Žyma                 | Reikšmė                                                                                  |
| -------------------- | ---------------------------------------------------------------------------------------- |
| `apikey`             | Priima API raktą (`authType` yra `apikey` arba `optional`).                              |
| `oauth`              | Naudoja OAuth arba seanso eigą.                                                          |
| `responses`          | Pateikia OpenAI Responses API bazinį URL.                                                |
| `passthrough-models` | Modelius pateikia tiesiogiai iš aukštesnio lygmens paslaugos, o ne iš statinio katalogo. |
| `custom-executor`    | Naudoja nenumatytąją vykdyklę, todėl lieka TypeScript kelyje.                            |
| `sidecar-candidate`  | Atspindi `sidecar.eligible` — saugu svarstyti importavimą į „sidecar“ komponentą.        |
| `usage-fetch`        | Turi prijungtą naudojimo arba kvotos gavimo priemonę (`getUsageForProvider`).            |
| `usage-supported`    | Naudojimo API priima šį teikėją (`isSupportedUsageConnection`).                          |

`usage-fetch` skirta tik aptikimui. Ji nurodo, kad OmniRoute moka nuskaityti teikėjo
naudojimo duomenis; ji neaktyvina duomenų gavimo, nekeičia kvotų semantikos ir nereiškia, kad
teikėjui įjungtas Dashboard kvotos valdiklis — šį valdiklį atskirai valdo
`USAGE_SUPPORTED_PROVIDERS`. Pirminis tiesos šaltinis yra `USAGE_FETCHER_PROVIDERS`, esantis
`open-sse/services/usage/fetcherProviders.ts`.

Šis sąrašas indeksuojamas pagal naudojimo duomenų dispečerio priimamas eilutes, todėl jame maišomi kanoniniai ID
ir alternatyvieji vardai, o pats sąrašas yra šiek tiek ilgesnis už pažymėtų teikėjų skaičių: įrašai, kurie
nėra pokalbių teikėjai manifesto registre (pavyzdžiui, paieškos teikėjas `firecrawl`
ir ACP teikėjas `amazon-q`), neturi manifesto įrašo, kuriam būtų galima priskirti žymą.

`usage-supported` nurodo, ar serverio ir Dashboard naudojimo maršrutai priima šio teikėjo
ryšį. Ji atspindi `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
ir `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), kuriuos abu valdo
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). Kitaip nei
`usage-fetch`, ji išvedama tik pagal teikėjo ID — vykdymo metu tikrinama
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` neatliekant alternatyviojo vardo nustatymo, todėl manifeste
išlaikoma ta pati taisyklė. Šių dviejų žymų aprėptis skiriasi: 3 teikėjai turi tik
`usage-fetch` (`opencode`, `opencode-zen`, `xai`), o 1 turi tik
`usage-supported` (`xiaomi-mimo-token-plan`), todėl viena žyma nereiškia kitos.

## Pagalbinio proceso naudojimas

Pagalbiniai procesai turėtų traktuoti `sidecar.eligible` kaip konservatyvų kandidato signalą, o ne kaip besąlyginį maršruto parinkimo sprendimą. Pirmieji importuojami taikiniai turėtų būti API raktus ir statinius galinius taškus naudojantys teikėjai, vykdomi numatytuoju vykdikliu. Teikėjai, naudojantys pasirinktinius žiniatinklio vykdiklius, OAuth / seansų eigas, dinaminius URL kūrimo įrankius arba telkinio konfigūraciją, lieka TypeScript atsarginiame kelyje, kol pagalbinis procesas įgyvendins lygiavertę elgseną, o telemetrija patvirtins lygiavertiškumą.

Siūlomi perkėlimo etapai:

1. Sugeneruoti ir patikrinti teikėjų papildinių manifestą iš TS registro.
2. Išmokyti Bifrost arba CLIProxyAPI importuoti manifestą API raktus / statinius galinius taškus naudojantiems teikėjams.
3. Nukreipti tinkamus teikėjus per pagalbinį procesą, valdomą `OMNIROUTE_RELAY_BACKEND`, išlaikant įjungtą TS atsarginį kelią.
4. Perkelti teikėjus tik tada, kai sėkmės rodiklis, p99 delsa, srautinio perdavimo elgsena ir nepalaikomų parametrų apdorojimas atitinka TS kelią.
5. Po vieną teikėjų šeimą pridėti pagalbiniame procese veikiančius vietinius papildinius pasirinktiniams vykdikliams.

## Kodėl nereikėtų tiesiogiai įterpti teikėjų į Next

Next sąsaja neturėtų valdyti teikėjų vykdymo. Ji turėtų kreiptis į API ribą. Tada galinė sistema gali nuspręsti, ar naudoti TypeScript vykdiklį, Bifrost, CLIProxyAPI, ar būsimą vietinį pagalbinį procesą. Taip užklausų pasirašymas, leidžiamų reikšmių sąrašo patikros, DB politika ir atsarginė elgsena išlieka centralizuoti prieš bet kokį perdavimą pagalbiniam procesui.
