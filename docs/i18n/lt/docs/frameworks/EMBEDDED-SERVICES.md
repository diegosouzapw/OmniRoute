Visoms šešioms taikomas tas pats priežiūros modelis:

- „OmniRoute“ jas įdiegia kataloge `DATA_DIR/services/{name}/` (atskirai nuo paties „OmniRoute“ failo `package.json`)
- „OmniRoute“ jas paleidžia kaip antrinius procesus ir stebi
- „OmniRoute“ į antrinio proceso aplinką įterpia trumpalaikį API raktą ir jį pakeičia be prastovos (kai taikoma)
- Visi valdymo maršrutai (`/api/services/*`) yra **LOCAL_ONLY** — pasiekiami tik iš grįžtamojo ryšio sąsajos (griežta taisyklė Nr. 17)

## 3. Gyvavimo ciklo būsenų automatas

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
            parengties patikra gera │         strigtis / SIGTERM │
                               ┌────▼─────┐  (baigta per 5 s)    │
                               │ running  │──── strigtis ───────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

Būsenos saugomos DB lentelėje `version_manager` (`status` stulpelyje) ir dubliuojamos
`ServiceSupervisor` būsenoje atmintyje. Atmintyje esanti būsena yra autoritetinga
vykdomam procesui; DB būsena yra ilgalaikė atsarginė būsena paleidimo metu.

### Būsenų perėjimai

| Iš              | Įvykis                              | Į                         |
| --------------- | ----------------------------------- | ------------------------- |
| `not_installed` | `install()` sėkmingai užbaigiamas   | `stopped`                 |
| `stopped`       | iškviečiamas `start()`              | `starting`                |
| `starting`      | parengties patikra grąžina 200      | `running`                 |
| `starting`      | procesas baigiasi iki parengties    | `error`                   |
| `running`       | iškviečiamas `stop()`               | `stopping` → `stopped`    |
| `running`       | procesas netikėtai baigiasi (< 5 s) | `error` (greita strigtis) |
| `running`       | procesas netikėtai baigiasi (> 5 s) | `error`                   |
| `error`         | iškviečiamas `start()`              | `starting`                |
| bet kuri        | `stop()`, kai būsena yra `stopping` | nieko nedaroma            |

### Operacijų užraktas

`ServiceSupervisor` nuosekliai vykdo gyvavimo ciklo operacijas naudodamas asinchroninį operacijų užraktą
(`withLock()`). Vienu metu tam pačiam prižiūrėtojui iškvietus `start()`, procesas sukuriamas lygiai
vieną kartą; antrasis kvietėjas laukia ir gauna esamą būseną. Tai apsaugo nuo
lenktyniavimo sąlygų, kai, pavyzdžiui, automatinis paleidimas ir naudotojo sąsajos mygtukas suaktyvinami vienu metu.

## 4. API žinynas

Visi maršrutai, esantys po `/api/services/`, yra **LOCAL_ONLY** (tik grįžtamojo ryšio sąsajai, griežta taisyklė Nr. 17).
Ne iš grįžtamojo ryšio sąsajos gaunamos užklausos gauna `403 LOCAL_ONLY`, neatsižvelgiant į autentifikavimo prieigos raktą.

### 4.1 9Router galiniai taškai (11 maršrutų)

#### `POST /api/services/9router/install`

Įdiegia 9Router iš npm. Sukuria `DATA_DIR/services/9router/` su atskirais
`package.json` ir `node_modules/`. Nesukelia konfliktų su paties OmniRoute priklausomybėmis.

**Užklausos turinys** (visi laukai neprivalomi):

```json
{ "version": "latest" }
```

| Laukas    | Tipas    | Numatytoji reikšmė | Aprašymas                              |
| --------- | -------- | ------------------ | -------------------------------------- |
| `version` | `string` | `"latest"`         | Diegtina npm versijos žyma arba semver |

**Atsakymai:**

| Būsena | Aprašymas                                                       |
| ------ | --------------------------------------------------------------- |
| `200`  | `{ ok: true, installedVersion: "x.y.z", path: "..." }`          |
| `400`  | Netinkamas užklausos turinys (Zod patikros klaida)              |
| `409`  | Diegimas jau vyksta (užraktas užimtas)                          |
| `500`  | npm diegimas nepavyko — suprantamą klaidos aprašą žr. `message` |

**Pastabos:** Naudojamas `execFile('npm', [...])` — be apvalkalo ir interpoliavimo (griežta taisyklė Nr. 13).
EACCES klaidos pateikiamos suprantamais pranešimais.

---

#### `POST /api/services/9router/start`

Paleidžia 9Router. Užregistruoja prižiūrėtoją, jei jis dar neužregistruotas, tada iškviečia
`supervisor.start()`. Jei paslauga jau veikia, operacija yra idempotentinė.

**Užklausos turinys:** nėra

**Atsakymai:**

| Būsena | Aprašymas                                            |
| ------ | ---------------------------------------------------- |
| `200`  | `ServiceStatus` objektas (žr. schemą toliau)         |
| `409`  | 9Router neįdiegtas (`status: "not_installed"`)       |
| `503`  | Paleisti nepavyko (proceso klaida — žr. `lastError`) |

**ServiceStatus schema:**

```json
{
  "tool": "9router",
  "state": "running",
  "pid": 12345,
  "port": 20130,
  "health": "healthy",
  "startedAt": "2026-05-25T10:00:00.000Z",
  "lastError": null
}
```

---

#### `POST /api/services/9router/stop`

Tvarkingai sustabdo 9Router. Išsiunčia SIGTERM, laukia 15 s, tada išsiunčia SIGKILL, jei procesas vis dar veikia.
Jei paslauga jau sustabdyta, operacija yra idempotentinė.

**Užklausos turinys:** nėra

**Atsakymai:**

| Būsena | Aprašymas                                 |
| ------ | ----------------------------------------- |
| `200`  | `ServiceStatus` (state: "stopped")        |
| `503`  | Sustabdyti nepavyko dėl netikėtos klaidos |

---

#### `POST /api/services/9router/restart`

Atitinka `stop()`, po kurio, naudojant operacijos užraktą, vykdomas `start()`.

**Užklausos turinys:** nėra

**Atsakymai:** tokie patys kaip `start` (grąžinama galutinė `ServiceStatus` būsena).

#### `POST /api/services/9router/update`

### 4.7 Atvirkštinis tarpinis serveris (9Router skydelio įterpimas)

Skydelyje 9Router žiniatinklio naudotojo sąsaja įterpiama į iframe per vidinį
atvirkštinį tarpinį serverį adresu:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

Šis tarpinis serveris:

- Persiunčia užklausą į `http://127.0.0.1:{port}/{path}` (tik grįžtamojo ryšio sąsaja)
- Pašalina gaunamas `cookie` ir `authorization` antraštes (OmniRoute seanso duomenys nenutekinami)
- Įterpia `Authorization: Bearer {apiKey}`, skirtą 9Router autentifikavimui
- Iš atsako pašalina `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*`
- Perrašo HTML atsakus, įterpdamas `<base href>` ir normalizuodamas absoliučiuosius kelius (`/foo` → `/dashboard/.../embed/foo`)

Įterpto skydelio WebSocket protokolo naujinimus apdoroja pagalbinis serveris,
veikiantis per atskirą prievadą (žr. `src/lib/services/embedWsProxy.ts`).

**Saugumas:** įterpimo tarpinio serverio maršrutai priskiriami
`LOCAL_ONLY_API_PREFIXES` ir yra pasiekiami tik per grįžtamojo ryšio sąsają.
Užpuolikas, gavęs JWT per Cloudflare/Ngrok tunelį, negali per tarpinį serverį
pasiekti įterptųjų paslaugų.

## 5. Saugumas

### LOCAL_ONLY vykdymo užtikrinimas (griežta taisyklė Nr. 17)

Visi maršrutai, esantys po `/api/services/` ir `/dashboard/providers/services/*/embed/`,
faile `src/server/authz/routeGuard.ts` klasifikuojami kaip LOCAL_ONLY. Vietinio grįžtamojo ryšio patikra
vykdoma besąlygiškai prieš bet kurią autentifikavimo šaką:

```
gaunama užklausa
  → isLocalOnlyPath(path)?
      → ne grįžtamojo ryšio adresas → 403 LOCAL_ONLY (visada, prieš autentifikavimo patikrą)
      → grįžtamojo ryšio adresas    → tęsti įprastą autentifikavimą
```

Tai neleidžia nutekėjusiam JWT (pvz., per tunelį) inicijuoti `npm install` arba
procesų paleidimo. Visą lygių matricą žr. `docs/security/ROUTE_GUARD_TIERS.md`.

### API rakto įterpimas

9Router ir Mux savo HTTP galiniams taškams reikalauja API rakto / nešėjo prieigos rakto.
OmniRoute:

1. Sugeneruoja raktą naudodama `crypto.randomBytes(32).toString("base64url")` su
   konkrečiai paslaugai skirtu prefiksu (`nr_` – 9Router, `mx_` – Mux).
2. Užšifruoja jį saugojimo metu naudodama AES-256-GCM (tą patį šifrą, kuris naudojamas teikėjo prisijungimo duomenims).
3. Iššifruoja ir paleidimo metu įterpia jį kaip aplinkos kintamąjį —
   `NINEROUTER_API_KEY` – 9Router, `MUX_SERVER_AUTH_TOKEN` – Mux (niekada kaip CLI
   parinktį, todėl prieigos raktas niekada nerodomas `ps` / procesų sąrašuose).
4. Niekada negrąžina nešifruoto rakto jokiame HTTP atsakyme.

CLIProxyAPI paleidimo metu gauna specialų duomenų lygmens raktą
(`needsApiKey: true` — naudojamą modeliams sinchronizuoti su adapteriu).

### Apsauga nuo SSRF

Atvirkštinis HTTP tarpinis serveris (`/dashboard/.../embed/[...path]`) yra griežtai sukonfigūruotas persiųsti
tik į `http://127.0.0.1:{port}`. Jis niekada neseka peradresavimų į paskirties vietas,
kurios nėra grįžtamojo ryšio adresai. Biblioteka `ssrf-req-filter` naudojama atmesti bet kokį aukštesniojo lygmens serverio URL, kuris
nurodo už grįžtamojo ryšio diapazono ribų esantį adresą.

### Komandų apvalkalo sauga (griežta taisyklė Nr. 13)

`npm install` iškviečiama naudojant `execFile('npm', ['install', pkg, '--prefix', dir])` —
be šabloninių literalų, komandų apvalkalo ar išorinių kelių interpoliavimo komandos
eilutėje. Vykdymo metu naudojamos reikšmės (prievadai, API raktai) perduodamos per antrinio proceso objektą `env`.

### Klaidų informacijos išvalymas (griežta taisyklė Nr. 12)

Visi klaidų atsakymai iš `/api/services/*` apdorojami naudojant `buildErrorBody()` arba
`sanitizeErrorMessage()`. Neapdorotos `err.stack` ir `err.message` reikšmės niekada nėra pažodžiui grąžinamos
kvietėjui.

#### Prijungiamo teikėjo papildinio sutartis (1 etapas, Nr. 7333)

`src/lib/services/providerPlugins/` pristato `ServiceProviderPlugin` sutartį, kuri
sujungia vidinės sistemos `bootstrap.ts` laukus `ServiceEntry` ir `serviceBackends.ts`
manifesto šablono laukus į vieną objektą, užuot to paties vidinės sistemos komponento struktūrą
atskirai aprašius dviejuose nesusijusiuose failuose. Šiuo metu **perkeltas tik `9router`**
— `bootstrap.ts` suformuoja savo `SERVICES[]` įrašą iš
`getServiceProviderPlugin("9router")` (`src/lib/services/providerPlugins/registry.ts`),
o jei papildinio kada nors trūktų, išmeta paleidimo klaidą. `cliproxy`, `mux` ir `bifrost`
toliau naudoja ankstesnius įterptinius `SERVICES[]` literalus be pakeitimų.

`createServiceBackendManifestEntry(pluginId, template)` pagalbine funkcija, kuri iš `SERVICE_BACKEND_MANIFEST_TEMPLATE` įrašo sukuria tinkamai suformuotą
`ProviderPluginManifestEntry` — ji
**dar nėra** prijungta prie jokio aktyvaus užklausų kelio (nei `generateProviderPluginManifestFromRegistry()`,
nei `/v1/providers/[provider]/models`); tai lieka vėlesniam darbui, kai sutartis bus
patikrinta su antruoju vidinės sistemos komponentu.

Atidėta vėlesnėms PR ir sekama pagal užduotį Nr. 7333: `cliproxyapi` perkėlimas naudojant tą patį
registrą, `mux` / `bifrost` apibendrinimas į sąjungą `ServiceBackendPluginId`,
vykdyklės maršrutizavimo specialiųjų atvejų (`open-sse/executors/index.ts`,
`open-sse/handlers/chatCore/executorProxy.ts`) įtraukimas į papildinio sutartį ir
`createServiceBackendManifestEntry()` prijungimas prie aktyvaus manifesto / modelių kodo kelio.

Jei įterptoji paslauga pateikia su OpenAI suderinamą `/v1/chat/completions` galinį tašką:

1. Pridėkite teikėjo įrašą faile `src/shared/constants/providers.ts` su `isEmbeddedService: true`.
2. Sukurkite `open-sse/executors/{name}.ts`, išplečiantį `BaseExecutor`. Kiekvienai užklausai
   iš naujo raskite prievadą ir API raktą (niekada nelaikykite jų konstruktoriaus podėlyje).
   Grąžinkite `503 service_not_running` atsakymą, kai prižiūryklės būsena nėra `"running"`.
3. Užregistruokite modelius faile `open-sse/config/providerRegistry.ts`, naudodami paslaugos
   priešdėlį (pvz., `myservice/sub/model`). `modelSync.ts` palaikys jų aktualumą.

### 8 veiksmas — dokumentuokite ir testuokite

1. Atnaujinkite `docs/frameworks/EMBEDDED-SERVICES.md` (šį failą) — įtraukite paslaugą į
   §1 lentelę, o visus naujus galinius taškus — į §4.
2. Pridėkite vienetinius testus kataloge `tests/unit/services/` (gyvavimo ciklo, diegimo programos, API formos).
3. Pridėkite integracinį testą kataloge `tests/integration/services/` (vykdomą tik nustačius `RUN_SERVICES_INT=1`).
4. Papildykite `docs/openapi.yaml` naujais galiniais taškais.

## 7. Trikčių šalinimas

### Paslauga nepasileidžia

**Požymiai:** Paleidimo mygtukas grąžina 503, būsena lieka `"error"` arba `"starting"`.

**Patikros sąrašas:**

1. Patikrinkite `GET /api/services/{name}/logs` (arba žurnalo skydelį valdymo skydelyje). Ieškokite
   tokių eilučių kaip `Error: ENOENT`, `address already in use` arba `Cannot find module`.
2. Patikrinkite, ar `npm` yra PATH: vykdykite `which npm` naudodami tą pačią naudotojo paskyrą, su kuria veikia OmniRoute.
3. Patikrinkite, ar paslauga įdiegta: `GET /api/services/{name}/status` atsakyme patikrinkite
   `installedVersion`. Jei reikšmė yra `null`, pirmiausia įdiekite paslaugą.
4. Patikrinkite, ar `DATA_DIR/services/{name}/node_modules/` egzistuoja ir nėra tuščias.
5. Būsenos atsakymo lauke `lastError` patikrinkite išvalytą proceso užbaigimo priežastį.

---

### Šaltasis paleidimas yra lėtas (> 10 s, kol pasiekiama būsena `running`)

**Požymiai:** Būsena ilgą laiką lieka `"starting"`, kol pasikeičia į `"running"` arba `"error"`.

**Paaiškinimas:** 9Router šaltasis paleidimas apima didelių priklausomybių medžių (DNS,
tunelio, MITM modulių) importavimą. Numatytasis veikimo patikros intervalas yra 2 s, atliekant 3 bandymus, kol
prižiūrėtojas paskelbia skirtąjį laiką pasibaigusiu (tačiau tęsia tikrinimą).

**Sprendimas:** `healthIntervalMs` ir `waitForHealthy` skirtąjį laiką
(`healthIntervalMs * 3`) galima konfigūruoti faile `bootstrap.ts`. Paslaugoms, kurių
paleidimas trunka ilgiau, padidinkite `healthIntervalMs` iki 5000, o `stopTimeoutMs` – iki 30 000.

---

### Prievado konfliktas (`EADDRINUSE`)

**Požymiai:** Žurnaluose rodoma `address already in use :::20130`.

**Priežastys:**

- Kitas procesas jau naudoja 20130 prievadą.
- Ankstesnis 9Router procesas nebuvo visiškai sustabdytas (likęs procesas su PID).

**Sprendimas:**

1. Pakeiskite numatytąjį prievadą naudodami `NINEROUTER_PORT` aplinkos kintamąjį faile `.env`.
2. Raskite ir priverstinai užbaikite konfliktuojantį procesą: `lsof -ti :20130 | xargs kill -9`.
3. Kiekvienos paslaugos prievadą galima konfigūruoti faile `bootstrap.ts`, naudojant lauką `port`.

**Pastaba:** 9Router pagal numatytuosius nustatymus naudoja 20130 prievadą būtent tam, kad išvengtų konflikto su
numatytuoju OmniRoute 20128 prievadu.

---

### Diegiant nepakanka teisių (EACCES)

**Požymiai:** Diegimo užklausa grąžina 500, žurnaluose rodoma `EACCES` arba `permission denied`.

**Priežastys:**

- OmniRoute procesas neturi rašymo teisių į `DATA_DIR` arba jo pirminį katalogą.
- Programa vykdoma Docker aplinkoje be root teisių ir neturi rašymo prieigos prie prijungto tomo.

**Sprendimas:**

1. Patikrinkite `DATA_DIR` (numatytoji reikšmė: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. Įsitikinkite, kad katalogas priklauso OmniRoute procesą vykdančiam naudotojui: `chown -R $USER ~/.omniroute/`
3. Docker aplinkoje įsitikinkite, kad prijungtas tomas turi tinkamas teises konteinerio naudotojui.

---

### Atnaujinti nepavyksta (`npm install` skirtasis laikas arba tinklo klaida)

**Požymiai:** Atnaujinimo užklausa grąžina 500 su `InstallError`, žurnaluose rodoma tinklo skirtojo laiko klaida.

**Patikros sąrašas:**

1. Patikrinkite, ar npm registras pasiekiamas: `npm ping`.
2. Patikrinkite įmonės įgaliotojo serverio nustatymus: `npm config get proxy`, `npm config get https-proxy`.
3. Pabandykite įdiegti rankiniu būdu: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`.
4. Jei naudojamas nuo išorinių tinklų izoliuotas tinklas, iš anksto atsisiųskite tar archyvą ir naudokite `npm install /path/to/tarball.tgz`.

---

### Iškart po paleidimo rodoma paslaugos būsena `"error"` (greitas proceso sutrikimas)

**Požymiai:** Būsena iš `"starting"` į `"error"` pasikeičia greičiau nei per 5 sekundes.
`lastError` rodoma `"Fast crash (exited with code 1)"`.

**Patikros sąrašas:**

1. Perskaitykite visą žurnalo pabaigą: `GET /api/services/{name}/logs?tail=500`.
2. Dažna priežastis: trūksta paslaugai reikalingų aplinkos kintamųjų.
3. Naudodami 9Router patikrinkite, ar `NINEROUTER_DISABLE_MITM=true` ir
   `NINEROUTER_DISABLE_TUNNEL=true` yra procesui paleidimo metu perduodamoje aplinkoje (žr.
   `installers/ninerouter.ts` `resolveSpawnArgs`).

## 8. DUK

**K.: Ar galiu įterptųjų paslaugų galinius taškus padaryti pasiekiamus ne vietinės sąsajos klientams?**

Ne. LOCAL_ONLY lygmuo yra numatytas sąmoningai (griežtoji taisyklė Nr. 17). Maršrutai, kurie gali vykdyti
`npm install` arba paleisti `node` procesus, neturi būti pasiekiami srautui ne iš vietinės sąsajos,
nes per tunelį („Cloudflare“, „Ngrok“, „Tailscale“) nutekėjęs JWT priešingu atveju leistų
savavališkai paleisti procesus. Maršrutui
`/api/services/` nėra jokios galimybės taikyti išimtį — kitaip nei `/api/mcp/`, jis neįtrauktas į valdymo aprėpties apėjimo
sąrašą. Žr. `docs/security/ROUTE_GUARD_TIERS.md`.

---

**K.: Ar 9Router ir CLIProxyAPI bus pasiekiamos produkcinėje / debesijos aplinkoje?**

Taip. Abi paslaugos veikia pagal tą patį pirmiausia vietinio naudojimo modelį kaip ir pati „OmniRoute“. Jos veikia
tame pačiame kompiuteryje ir bendrauja per vietinę sąsają. „Produkcinė“ aplinka čia reiškia VPS
arba vietinį serverį, kuriame įdiegta „OmniRoute“, o ne nuotolinį debesijos paslaugų teikėją.

---

**K.: Kaip derinti prižiūrėtoją?**

1. Stebėkite SSE žurnalų srautą: `curl -N http://localhost:20128/api/services/9router/logs`.
2. Patikrinkite „OmniRoute“ „pino“ išvesties struktūrinius žurnalus, filtruodami pagal
   `service:supervisor` vardų sritį.
3. Patikrinkite DB eilutę: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`.
4. Naudokite `GET /api/services/9router/status`, kad vienu iškvietimu pamatytumėte dabartinę vykdymo būseną, PID, veikimo būklę
   ir `lastError`.

---

**K.: Prižiūrėtojas rodo `health: "degraded"` arba `health: "unknown"`, tačiau būsena yra `"running"`. Ar tai problema?**

`"degraded"` reiškia, kad veikimo būklės patikra grąžino ne 200 atsakymą. `"unknown"` reiškia, kad dar nebaigta
nė viena patikra (sutapo su pirmąja apklausa). Abi būsenos paleidimo metu yra laikinos.
Jei praėjus daugiau nei `healthIntervalMs * 3` ms po
`"running"` veikimo būklė vis dar yra `"degraded"`, įterptoji paslauga veikia, tačiau jos HTTP API neatsako. Patikrinkite,
ar būsenos atsakyme nurodytas tinkamas prievadas ir ar paslauga iš tiesų
jo klausosi.

---

**K.: Ar galiu pakeisti 9Router API raktą visiškai nepaleisdamas iš naujo?**

Ne. API raktas perduodamas 9Router per aplinkos kintamąjį proceso paleidimo metu.
Veikiančio proceso aplinkos kintamųjų pakeisti negalima. `POST .../rotate-key`
automatiškai sustabdo ir iš naujo paleidžia paslaugą, kad būtų pritaikytas naujasis raktas. Rakto pakeitimas
įsigalioja per paslaugos `stopTimeoutMs` laiką (numatytoji reikšmė – 15 s) ir jos paleidimo
trukmę.

---

**K.: Kokia yra žiedinio buferio riba ir kas nutinka jam užsipildžius?**

Kiekviena paslauga turi atskirą 5 MB žiedinį buferį. Kai buferis užsipildo, seniausios
žurnalo eilutės pašalinamos, kad atsirastų vietos naujoms. SSE `snapshot` įvykis grąžina
naujausias eilutes, neviršijant `tail` ribos. Žurnalai nėra nuolat įrašomi į diską, nebent
DB eilutėje nustatytas `logsBufferPath`.
