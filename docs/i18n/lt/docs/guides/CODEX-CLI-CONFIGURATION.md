> **TOML yra vienintelis veiksmingas formatas.** Šiuolaikinė Codex versija skaito tik
> `~/.codex/config.toml` (patikrinta su codex-cli 0.147.0: `codex --help` nurodo,
> kad `-c/--config` pakeitimai „įkeliami iš `~/.codex/config.toml`“). Senasis
> `~/.codex/config.yaml` priklausė ankstesnei npm CLI versijai ir yra tyliai ignoruojamas.
> Valdymo skydelio generatorius (`/api/cli-tools/apply`, įrankis `codex`) įrašo TOML,
> konservatyviai sujungdamas turinį — esami raktai ir kitų teikėjų blokai išsaugomi,
> API raktas lieka `OMNIROUTE_API_KEY` (niekada neįrašomas į failą), o likęs senasis
> `config.yaml` pateikiamas kaip perkėlimo pastaba jo nekeičiant.

## Paruoštas įklijuoti config.toml

Pakeiskite `<YOUR_HOST>` ir `<YOUR_KEY>` savo reikšmėmis:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # vieno įrankio iškvietimo istorijos saugojimo riba

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc arba ~/.zshrc — tikroji rakto reikšmė, niekada ne config.toml faile
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex, įtrauktas į ChatGPT programą

Jei Codex įdiegėte per ChatGPT darbalaukio programą, `codex` dvejetainis failas gali
būti tik programos pakete ir dar nebūti jūsų apvalkalo `PATH`. Įtraukite
išteklių katalogą į apvalkalo paleisties failą:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Atidarykite naują apvalkalą, tada patikrinkite:

```bash
command -v codex
codex --version
```

### Vietinis OmniRoute be autentifikavimo: pakanka laikino rakto

Codex patikrina, ar `env_key` nurodytas aplinkos kintamasis egzistuoja,
**prieš** pirmajai užklausai paliekant CLI. Jei jūsų **vietinis** OmniRoute
egzempliorius nereikalauja autentifikavimo, tinka bet kokia netuščia laikina reikšmė:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Jei jūsų OmniRoute serveris yra apsaugotas arba nuotolinis, naudokite tikrą raktą.

> **Dažniausiai naudojami pagrindinio kompiuterio variantai**
>
> | Prieiga          | URL                           |
> | ---------------- | ----------------------------- |
> | Vietinis tinklas | `http://192.168.0.1:20128/v1` |
> | Tailscale        | `http://100.x.x.x:20128/v1`   |
> | Atgalinis ryšys  | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — kodėl tai veikia su visais modeliais

2026 m. vasarį Codex CLI paskelbė `wire_api = "chat"` (Chat Completions) pasenusiu ir dabar **reikalauja** `wire_api = "responses"` (OpenAI Responses API). Nuo v0.138 nustačius `wire_api = "chat"`, programa iškart užstringa paleidimo metu.

Daugelis teikėjų, įskaitant GLM ir Kimi, vis dar pateikia tik Chat Completions galinį tašką. DeepSeek V4 dabar pateikia savąją Responses API bei su Anthropic suderinamą galinį tašką; OmniRoute pagal numatytąją nuostatą naudoja Responses ir leidžia kiekvienam DeepSeek ryšiui pasirinkti suderinamumą su Anthropic.

**OmniRoute tai išsprendžia skaidriai:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute pasirenka savąjį teikėjo protokolą ir prireikus konvertuoja
    → POST /responses (DeepSeek V4) arba /chat/completions (Mistral / GLM / Kimi / kiti)
```

Naudojant OmniRoute, atskiro konvertavimo tarpinio serverio niekada nereikia. **Visi modeliai naudoja `wire_api = "responses"`** — visu kitu pasirūpina OmniRoute.

> **`wire_api` yra numatytoji nuostata** — numatytoji lauko reikšmė yra `"responses"`, todėl jį galima visiškai praleisti faile `config.toml`. Aiškiai jį nustatykite tik tada, jei dokumentuojate ketinimą.

## Konteksto langas ir glaudinimas

### Žetonų konfigūracijos laukai

| Laukas                           | Aprašymas                                                                                                                                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `model_context_window`           | Bendras aktyvaus modelio žetonų biudžetas. Nustatykite modelio nurodytą ribą.                                                                                                                    |
| `model_auto_compact_token_limit` | Slenkstis, suaktyvinantis automatinį istorijos glaudinimą. **Didžiausia reikšmė: 90 % `model_context_window`** — didesnės nei 90 % reikšmės tyliai ignoruojamos.                                 |
| `tool_output_token_limit`        | Vieno įrankio iškvietimo išvesties istorijoje saugomų žetonų riba. Neleidžia vienam dideliam įrankio atsakymui užpildyti lango. **Tai nėra didžiausia išvestis** — tai istorijos saugojimo riba. |
| `compact_prompt`                 | Tiesiogiai įrašomas sistemos raginimo, naudojamo glaudinant, perrašymas (v0.138+).                                                                                                               |

> **Pastaba dėl `model_max_output_tokens`**: šis laukas **nėra Codex CLI konfigūracijos schemos dalis** (jo nėra Codex Rust kodų bazėje). Jei jis nustatytas, yra tyliai ignoruojamas. Juo nepasikliaukite — naudokite `tool_output_token_limit`, kad valdytumėte, kiek įrankio išvesties saugoma istorijoje.

## Samprotavimo intensyvumas

Valdo, kiek modelis „mąsto“ prieš atsakydamas.

| Reikšmė  | Kam naudoti                                                   |
| -------- | ------------------------------------------------------------- |
| `none`   | Be samprotavimo — tiesioginis atsakymas                       |
| `low`    | Elementarioms užduotims (pervadinti, formatuoti)              |
| `medium` | **Numatytoji serverio reikšmė**, kai nenurodyta               |
| `high`   | Vidutinio sudėtingumo užduotims (refaktorizavimui, derinimui) |
| `xhigh`  | Architektūrai, išsamiai analizei, sudėtingoms problemoms      |

```bash
# Perrašymas vienam iškvietimui
codex -c model_reasoning_effort=low "pervadink kintamąjį x į count"
codex -c model_reasoning_effort=xhigh "suprojektuok autentifikavimo modulį"
```

Taip pat nustatykite samprotavimo **santrauką**, kad Desktop galėtų pateikti mąstymo tekstą (ne tik užšifruotus duomenų blokus):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # arba ultra, kai palaikoma
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute mąstymo biudžetas (serverio nustatymas)

OmniRoute serveryje **Settings → AI → Thinking Budget** turi būti nustatyta į **`passthrough`**, kad Codex intensyvumo ir santraukos parametrai pasiektų pirminį teikėją. Režimas **`auto` pašalina** visus kliento `reasoning` / `reasoning_effort` laukus, todėl mąstymo skydeliai bus tušti net tada, kai Codex sukonfigūruotas tinkamai.

Visas vadovas: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Glaudinimas ir raginimų podėlis yra nepriklausomi ir toliau veikia naudojant `passthrough`.

## Profiliai — įvardytos kiekvieno modelio / darbo eigos konfigūracijos

Profiliai leidžia vienu parametru pakeisti modelį ir konteksto langą. Kiekvienas profilis yra paprastas
`~/.codex/<name>.config.toml` failas, kurio nustatymai užklojami ant pagrindinio `config.toml`.

> **Pavadinimų taisyklė (Codex CLI v0.137+):** failas turi būti `~/.codex/<name>.config.toml` — **be `profile-` prefikso**.
> CLI susieja `-p kimi-k27` → `~/.codex/kimi-k27.config.toml`. Jei failas nerastas, tyliai pritaikoma numatytoji konfigūracija.

```bash
codex --profile kimi-k27 "išanalizuok 10 tūkst. šios kodų bazės eilučių"
codex -p glm52 "architektūros peržiūra"
codex --profile deepseek-flash "pervadink kintamąjį"   # greita, pigu
```

### Intensyvumo profiliai (tas pats modelis, skirtingas intensyvumas)

```bash
codex -p low      # cx/gpt-5.5, intensyvumas=low
codex -p medium   # cx/gpt-5.5, intensyvumas=medium
codex -p high     # cx/gpt-5.5, intensyvumas=high
codex -p xhigh    # cx/gpt-5.5, intensyvumas=xhigh (numatytasis)
codex -p chat     # cx/gpt-5.5, intensyvumas nenustatytas (serverio numatytasis)
```

## Automatinis profilių generavimas naudojant `omniroute setup-codex`

Jei „OmniRoute“ naudojate VPS serveryje, galite automatiškai sugeneruoti profilių failus pagal aktyvų modelių katalogą:

```bash
# Iš VPS serverio (naudojama vietinė „OmniRoute“ paslauga per 20128 prievadą)
omniroute setup-codex

# Iš bet kurio kompiuterio — nurodykite savo VPS serverį
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Peržiūra neįrašant failų
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Generuoti tik GLM ir Kimi profilius
omniroute setup-codex --only glm,kimi

# Įrašyti į pasirinktinį katalogą
omniroute setup-codex --codex-home /path/to/.codex
```

Komanda gauna `/v1/models`, žinomiems modeliams naudoja optimizuotus profilius, kitiems suderinamiems tekstiniams modeliams naudoja katalogo metaduomenis ir kiekvienam jų įrašo `~/.codex/<name>.config.toml`. Komanda yra idempotentinė, todėl ją saugu vykdyti pakartotinai.

„OmniRoute“ taip pat gali **automatiškai sinchronizuoti** tuos pačius profilių failus, kai sėkmingas paslaugos teikėjo modelių aptikimas ar importavimas pakeičia aktyvų katalogą. Ši funkcija yra **pasirenkama ir pagal numatytuosius nustatymus išjungta**: įjunkite ją **CLI Code valdymo skydelyje** („CLI profile auto-sync“ → Codex) arba nustatykite `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (taip pat atsižvelgiama į `CLI_ALLOW_CONFIG_WRITES`, kuris pagal numatytuosius nustatymus įjungtas). Kai ši funkcija įjungta, ji įrašo tik atskirus `~/.codex/*.config.toml` profilių failus; ji niekada nekeičia aktyvaus arba numatytojo `~/.codex/config.toml`, Codex-lb nustatymų, autentifikavimo ar paslaugos teikėjo pasirinkimo.

## Ilgai trunkančios užduotys

Dvi numatytosios OmniRoute nuostatos gali nepastebimai pakenkti daug valandų trunkantiems Codex CLI seansams. Nė viena iš jų nėra Codex CLI nuostata — abi yra OmniRoute pusėje. Naudotojai, perkeliantys konfigūraciją iš tarpinių serverių, kurie priskiria paskyras ir išjungia neveiklumo ribojimus, dažnai susiduria su abiem problemomis ir padaro išvadą, kad OmniRoute „negali palaikyti ilgo seanso“.

| Požymis                                                                                  | Tikėtina priežastis                                                                                       | Nuostata                 |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------ |
| Seansas nuolat perjungia paskyras / tarp veiksmų prarandamas raginimų podėlio tęstinumas | Seanso susiejimo TTL yra `0` (išjungtas)                                                                  | `sessionAffinityTtlMs`   |
| Ryšys nutrūksta samprotavimo metu, klientui nepateikiant jokio raginimo                  | Srauto neveiklumo stebėjimo mechanizmas suveikė, kai 10 minučių negauta jokio pirminio serverio fragmento | `STREAM_IDLE_TIMEOUT_MS` |

Susijusios diskusijos: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (ilgų užduočių nutrūkimai), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (kodėl susiejimas pagal numatytąją nuostatą išjungtas). Stebėjimas: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Seanso susiejimas — vieną pokalbį priskirkite vienai paskyrai

**Numatytoji reikšmė:** `sessionAffinityTtlMs = 0` (išjungta).

**Kur ją nustatyti**

- Valdymo skydas → **Nuostatos → Maršruto parinkimas** → **Seanso susiejimas** → **Susiejimo TTL (sekundėmis)** (`ComboDefaultsTab`)
- Arba PATCH metodu atnaujinkite nuostatas, nurodydami `sessionAffinityTtlMs` **milisekundėmis** (Zod diapazonas `0`–`86_400_000`, t. y. iki 24 valandų)

> #7274 pakeitime pavadinimas pakeistas iš tik Codex skirto `codexSessionAffinityTtlMs`. Senasis raktas vis dar priimamas kaip tik skaityti skirtas alternatyvus pavadinimas; naujose konfigūracijose turėtų būti naudojamas `sessionAffinityTtlMs`. Dabar susiejimas taikomas **bet kuriam** teikėjui, kai TTL yra didesnis nei `0`, ne tik Codex — žr. [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Seanso susiejimas.

**Kas neveikia, kai reikšmė lieka 0**

Kiekvienas kelių veiksmų Codex pokalbio veiksmas maršrutu parenkamas atskirai pagal aktyvią kombinuotąją strategiją ir kiekvieną kartą gali patekti į **kitą paskyrą**. Tai sutrikdo pirminio serverio seanso / raginimų podėlio tęstinumą. OmniRoute atsižvelgia į Codex seanso antraštes (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) ir užklausos turinio laukus, pvz., `prompt_cache_key` / `session_id`, tik kai TTL yra didesnis nei `0` (`extractSessionAffinityKey`, esantis `src/sse/services/auth.ts`).

**Rekomenduojama vienai kelias valandas trunkančiai užduočiai**

Nustatykite TTL, **viršijantį numatomą bendrą užduoties trukmę** (didžiausia reikšmė naudotojo sąsajoje yra **86400 sekundžių** = 24 valandos):

| Numatoma užduoties trukmė | Susiejimo TTL (naudotojo sąsajoje, sekundėmis) | `sessionAffinityTtlMs` |
| ------------------------- | ---------------------------------------------- | ---------------------- |
| Kelios valandos           | `14400` (4 val.)                               | `14400000`             |
| Per naktį / ~12 val.      | `43200` (12 val.)                              | `43200000`             |
| Visa para                 | `86400` (24 val., didžiausia reikšmė)          | `86400000`             |

Pasirenkamasis įjungimas yra apgalvotas: išjungus susiejimą pirmenybė teikiama apkrovos balansavimui tarp paskyrų, o jį įjungus — vieno ilgo agento seanso tęstinumui. Šiame vadove numatytoji nuostata **nekeičiama** — operatoriai, vykdantys ilgas Codex užduotis, turi patys ją įjungti.

### 2. Srauto neveiklumo skirtasis laikas — nenutraukite tylių samprotavimo veiksmų

**Numatytoji reikšmė:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 minučių). Kai reikšmė nenustatyta, ji perimama iš `REQUEST_TIMEOUT_MS`; bendroji bazinė reikšmė taip pat yra 600000. Žr. [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Skirtieji laikai.

**Kas neveikia naudojant numatytąją reikšmę**

„Codex“ samprotavimo / įrankio veiksmas, kuris išlieka tylus ilgiau nei 10 minučių ir negauna **jokio tikro iš pirminio serverio gaunamo duomenų fragmento**, yra priverstinai nutraukiamas SSE neveiklumo stebėjimo mechanizmo (`open-sse/utils/stream.ts`). Klientas dažnai mato tik nutrūkusį ryšį — tai atitinka situaciją „sustojo automatiškai be jokio pranešimo“.

Svarbi detalė: „OmniRoute“ sintetinis SSE **periodinis signalas neatnaujina** neveiklumo laikmačio. `lastChunkTime` atnaujinamas tik gavus tikrą pirminio serverio atsakymo turinio fragmentą. Tyliai vis dar „mąstantis“ modelis stebėjimo mechanizmo požiūriu atrodo lygiai taip pat kaip nebeatsakantis pirminis serveris.

Susijęs „Undici“ atsakymo turinio neveiklumo nustatymas: `FETCH_BODY_TIMEOUT_MS` (pagal numatytuosius nustatymus taip pat taikoma ta pati 10 minučių bazinė reikšmė; `0` jį išjungia). Srautiniam perdavimui `FETCH_TIMEOUT_MS` apima tik ryšio užmezgimą / pirmąsias antraštes — kai srautas tampa aktyvus, jo strigtis valdo `STREAM_IDLE_TIMEOUT_MS` ir `FETCH_BODY_TIMEOUT_MS`.

**Rekomenduojama vienai kelias valandas trunkančiai užduočiai**

„OmniRoute“ proceso aplinkoje (`.env` / compose / systemd):

```bash
# Išjungti srauto neveiklumo ir atsakymo turinio neveiklumo ribojimus ilgiems samprotavimo veiksmams
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Arba padidinkite jų reikšmes virš ilgiausio numatomo tylos intervalo (reikšmės nurodomos milisekundėmis):

```bash
# Pavyzdys: leisti iki 2 valandų tylos tarp iš pirminio serverio gaunamų fragmentų
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Pakeitę šiuos aplinkos kintamuosius, paleiskite „OmniRoute“ iš naujo.

### Konkretus receptas — kelias valandas trunkanti „Codex“ užduotis

1. **Priskirkite paskyrą:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12 val.) arba `86400` (maks. 24 val.).
2. **Padidinkite / išjunkite neveiklumo ribojimus** „OmniRoute“ aplinkoje:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Palikite įprastą „Codex“ `config.toml` (`wire_api = "responses"`, teisingą `base_url`, `OMNIROUTE_API_KEY`) — šiems dviem veikimo aspektams „Codex“ pusėje nėra seanso susiejimo / neveiklumo valdiklių.
4. Paleiskite „OmniRoute“ iš naujo, tada pradėkite ilgą „Codex“ užduotį.

### Sprendimas dėl numatytųjų reikšmių (#7287)

| Valdiklis                | Platinama numatytoji reikšmė | Keisti šiame vadove?                                                                                            |
| ------------------------ | ---------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (išjungta)               | **Ne** — lieka pasirenkama funkcija (apkrovos balansavimas ar tęstinumas; žr. Discussion #5718)                 |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 min.)           | **Ne** — bendram srautui lieka 10 minučių; ilgų „Codex“ užduočių operatoriai šią reikšmę padidina arba išjungia |

Visuotinis bet kurios numatytosios reikšmės pakeitimas pakeistų kiekvieno egzemplioriaus kliento, o ne tik „Codex“, veikimą. Dokumentuokite valdiklius; nekeiskite numatytųjų reikšmių, kol nebus priimtas aiškus operatoriaus sprendimas.

### Neveiklumo nutraukimų diagnostika

Suveikus neveiklumo stebėjimo mechanizmui, „OmniRoute“ įrašo maždaug tokią žurnalo eilutę:

```text
[STREAM] Neveiklumo skirtasis laikas: iš codex negauta duomenų 600000ms (modelis: cx/gpt-5.5)
```

Ieškokite `Idle timeout: no data from` (arba kodo `stream_idle_timeout` / klaidos pavadinimo `StreamIdleTimeoutError`). Teikėjo segmentas yra tas, kurį „OmniRoute“ naudojo tai užklausai (`codex`, kitas teikėjo identifikatorius arba `provider`, jei jis nežinomas) — tai ne visada yra tiesioginė eilutė `codex`.

## Trikčių šalinimas

**`Error: wire_api = "chat" is no longer supported`**
Pašalinkite `wire_api = "chat"` iš konfigūracijos. Nustatykite `wire_api = "responses"` arba praleiskite šį lauką (nuo v0.138 numatytoji reikšmė yra `"responses"`).

**`Error: model not found`**
Patikrinkite, ar modelis egzistuoja „OmniRoute“ ir ar naudojamas tinkamas prefiksas. Naudokite `omniroute models list` arba atverkite `/dashboard/providers/<provider>`.

**`Authentication error`**
Patikrinkite, ar `OMNIROUTE_API_KEY` yra eksportuotas: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Prieš pateikdama pirmąją užklausą „Codex“ patikrina, ar aplinkos kintamasis egzistuoja. Eksportuokite
tikrą raktą apsaugotiems serveriams arba netuščią pakaitinę reikšmę, pvz.,
`OMNIROUTE_API_KEY=local`, kai jūsų **vietinis** „OmniRoute“ egzempliorius
nereikalauja autentifikavimo. Jei kintamąjį pridėjote prie `~/.bashrc` arba `~/.zshrc`, paleiskite apvalkalą iš naujo.

**`Connection refused`**
Patikrinkite, ar „OmniRoute“ veikia ir ar `base_url` pagrindinio kompiuterio adresas bei prievadas yra tinkami jūsų tinklui (vietiniam, „Tailscale“ ar VPS).

**Seansas nutrūksta priartėjus prie konteksto ribos**
Aiškiai nustatykite `model_context_window` ir `model_auto_compact_token_limit`. Žr. pirmiau pateiktą konteksto lango lentelę.

**Glaudinimas suaktyvinamas per vėlai**
Sumažinkite `model_auto_compact_token_limit` iki 80–85 % lango dydžio. Niekada nenustatykite didesnės nei 90 % reikšmės.

**Profilis neįkeliamas (`-p <name>` tyliai ignoruojamas)**
Patikrinkite, ar failas yra adresu `~/.codex/<name>.config.toml` (be prefikso `profile-`). Paleiskite `ls ~/.codex/*.config.toml`.

**Ilgai vykdoma „Codex“ užduotis nutrūksta / tarp užklausų perjungiamos paskyros**
Žr. [Ilgai vykdomos užduotys](#long-running-tasks). Įjunkite seanso susiejimą (TTL turi būti ilgesnis už užduoties trukmę) ir padidinkite arba išjunkite `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`. „OmniRoute“ žurnaluose ieškokite `Idle timeout: no data from` naudodami „grep“.
