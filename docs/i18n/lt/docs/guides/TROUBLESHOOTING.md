## Trumpa atmintinė

**Pirmą kartą naudojate „OmniRoute“?** Pradėkite čia — šie sprendimai išsprendžia 90 % problemų:

| Matau šį pranešimą            | Ką jis reiškia                                       | Ką daryti                                                                                               |
| ----------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| „Can't connect“               | „OmniRoute“ neveikia                                 | Paleiskite `omniroute` arba `docker restart omniroute`                                                  |
| „Invalid API key“             | Jūsų raktas neteisingas arba nebegalioja             | Dar kartą nukopijuokite raktą iš paslaugų teikėjo svetainės                                             |
| „Rate limit exceeded“         | Siunčiate per daug užklausų                          | Palaukite 1 minutę arba naudokite `model: "auto"`, kad būtų automatiškai pasirinkta atsarginė parinktis |
| „Quota exceeded“              | Išnaudojote nemokamą arba mokamą kvotą               | Prijunkite daugiau paslaugų teikėjų arba naudokite nemokamus teikėjus („Kiro“, „Pollinations“)          |
| „Slow responses“              | Paslaugų teikėjas yra užimtas arba geografiškai toli | Naudokite `model: "auto/fast"` arba prijunkite spartesnį teikėją („Groq“, „Cerebras“)                   |
| „Wrong provider used“         | `auto` pasirinko kitą paslaugų teikėją               | Tai normalu! `auto` pasirenka geriausią. Nurodykite konkretų teikėją naudodami `model: "openai/gpt-4o"` |
| „502 Bad Gateway“             | Paslaugų teikėjas neveikia                           | Palaukite ir bandykite dar kartą arba naudokite `model: "auto"`, kad būtų pakeistas paslaugų teikėjas   |
| „401 Unauthorized“            | Jūsų prisijungimo duomenys neteisingi                | Patikrinkite API raktą arba iš naujo autentifikuokite naudodami „OAuth“                                 |
| „omniroute is not recognized“ | „Windows“ PATH nėra visuotinių „node“ modulių        | Įtraukite visuotinį npm prefiksą į „Windows“ PATH. Jį rasite paleidę `npm config get prefix`.           |
| „429 Too Many Requests“       | Viršytas užklausų dažnio limitas                     | Palaukite 1 minutę arba prijunkite daugiau paslaugų teikėjų                                             |

**Vis dar nepavyksta?** Žr. toliau pateiktą [išsamų trikčių šalinimą](#detailed-troubleshooting) arba klauskite [„Discord“](https://discord.gg/U47eFqAXCn).

## Išsamus trikčių šalinimas

---

### Nemokamų paslaugų teikėjų užklausų dažnio ribojimas (429 / 400 / 401)

**Požymis**: naudojant `model: "auto"` su nemokamais arba autentifikavimo nereikalaujančiais teikėjais („opencode“, „auggie“ ir kt.), vietoje atsakymų protarpiais gaunama `HTTP 429`, `400` arba `401` klaida. Po kelių akimirkų pakartojus tą pačią užklausą, ji įvykdoma sėkmingai, tačiau automatizavimas („cron“ užduotys, agentai, scenarijai) nutrūksta jau po pirmosios klaidos.

**Pagrindinė priežastis**: susideda trys nepriklausomi gedimų tipai:

1. **Paslaugų teikėjo užklausų dažnio limitas (`429`)**: nemokamuose planuose gali būti taikoma vienam laiko intervalui skirta kvota. Lygiagrečių iškvietimų pliūpsnis ją išnaudoja, todėl kita užklausa atmetama, kol prasideda naujas intervalas.
2. **Neveikiantis modelis tiesioginio perdavimo režimu (`400`/`401`)**: `auto/*` telkiniuose gali būti tiesioginio perdavimo modelių iš `opencode`, kurie užregistruoti kataloge, bet neturi galiojančių prisijungimo duomenų (pvz., `oc/north-mini-code-free` → `401`). Automatinis maršruto parinkiklis išbando vieną iš jų, patiria klaidą, o ši išplatinama dar prieš suveikiant atsarginiam variantui.
3. **Lygiagretumo sustiprinimas (`429` esant apkrovai)**: kai kelios agentų arba „cron“ sesijos vienu metu kreipiasi į `auto`, bendras užklausų dažnis viršija nemokamų paslaugų teikėjų toleruojamą ribą, todėl teisėtos užklausos pažymimos kaip piktnaudžiavimas.

**Patvirtintas sprendimas (bendruomenės pranešimas, 2026-08-10)**: sureguliuokite tris aplinkos kintamuosius, kad rotacija, lygiagretumas ir atsarginio varianto naudojimas suvaldytų nemokamo plano nepastovumą, užuot dėl jo nutraukę veikimą:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # gavus 400/401, pereiti prie kito modelio ar teikėjo (praleidžiami neveikiantys tiesioginio perdavimo modeliai)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # aiški sunkiasvorių užklausų priėmimo riba (pagal numatytąją nuostatą nenustatyta: užklausų skaičius neribojamas, žr. pastabą toliau)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ilgiau, bet ribotai laukti sunkiasvorėms užklausoms skirtų išteklių, užuot iškart grąžinus pakartotinai bandyti leidžiančią 503 klaidą
```

Nustatykite šiuos kintamuosius „OmniRoute“ proceso aplinkoje (demone, pvz., per „LaunchAgent“ plist arba `systemctl edit`), tada paleiskite „OmniRoute“ iš naujo. Rotacijos žyma yra vienas veiksmingiausių svertų: ji negrįžtamą gedimą paverčia skaidriu pakartotiniu bandymu naudojant veikiantį telkinio paslaugų teikėją.

**Pastaba**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` riboja, kiek sunkiasvorių — ilgo konteksto — užklausų gali būti vykdoma vienu metu; ši riba yra užklausų priėmimo vartai, o ne paslaugų teikėjo užklausų dažnio ribotuvas. **#503-fanout atnaujinimas:** šis kintamasis pagal numatytąją nuostatą nebėra nustatomas (dabar jis taikomas tik aiškiai sukonfigūravus, kaip parodyta pirmiau) — vietoje to sunkiasvorių užklausų priėmimą riboja automatiškai apskaičiuojamas baitų biudžetas (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), kuris prisitaiko prie faktinės pagrindinio kompiuterio atminties ribos, todėl naujame diegime turėtų pasitaikyti gerokai mažiau `503 chat_admission_busy` atmetimų net ir visai nenustačius šio kintamojo; aiškus jo nustatymas čia vis tiek veikia tiksliai taip, kaip aprašyta. Aiškiai nurodyti baitų biudžeto pakeitimai apribojami iki 8 MiB–2 GiB. `413 body_exceeds_budget` nėra laikina klaida: padidinkite šį baitų biudžetą, sumažinkite `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` arba padidinkite proceso atminties ribą. `inflight_bytes_budget` atmetimas reiškia laikiną išteklių konkurenciją, todėl užklausą galima kartoti. Kiekvieno paslaugų teikėjo užklausų dažnio ribojimas (`open-sse/services/rateLimitManager.ts`) atskirai valdomas naudojant `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` ir `RATE_LIMIT_AUTO_ENABLE` — žr. `.env.example`.

**Kaip patikrinti, ar pataisa suveikė**: paleiskite savo agentą / cron užduotį du kartus greitai iš eilės ir įsitikinkite, kad abu paleidimai sėkmingi. Prieš pataisą antrasis paleidimas paprastai pateikia `429` / `401` klaidą. Po pataisos klaidos (jei tokių yra) automatiškai pakartotinai apdorojamos ir iškvieta užbaigiama. Taip pat galite vykdyti `curl /monitoring/health` ir stebėti lauką `rateLimitedUntil` teikėjų ryšiuose bei `circuitBreakers.providerBreakers[].state` paveiktiems teikėjams — būsena gali būti `CLOSED`, `DEGRADED`, `OPEN` arba `HALF_OPEN` (žr. `src/shared/utils/circuitBreaker.ts`), o teikėjas, kuriam nuolat nepavyksta įvykdyti užklausų, pereis per būsenas `CLOSED → DEGRADED → OPEN`, kol pasibaigus atkūrimo laikotarpiui bus praleista bandomoji užklausa (`HALF_OPEN`).

**Jei vis dar matote 429**: aktyvi to teikėjo paskyra iš tiesų išnaudojo savo _kvotą_ (tai nėra vien tik užklausų dažnio ribojimas). OmniRoute valdymo skydelyje, pasirinkę Providers → Accounts, pridėkite antrą to paties teikėjo paskyrą arba įtraukite kitą nemokamą teikėją (pvz., `routeway`, `auggie`). Rotacija padeda tik esant laikinoms dažnio ribojimo / 400 / 401 klaidoms; visiškai išnaudojus kvotą reikia kitų prisijungimo duomenų arba kito teikėjo.

**Jei naudojant vaizdo modelius (`auto/vision`, `bazaarlink/*`) rodoma 403 klaida**: prijungta paskyra neturi mokamo plano, apimančio vaizdo funkcijas, arba API raktui nesuteikta pakankamai leidimų. Teikėjo valdymo skydelyje patikrinkite, ar rakto apimtis apima vaizdo / multimodalines funkcijas, arba prijunkite mokamo plano paskyrą ir palikite ją kaip vaizdo užklausų tikslą.

## `npm install` įspėjimai (ERESOLVE / lygiaverčių priklausomybių / nebenaudojama)

Vykdydami `npm install -g omniroute`, galite pamatyti daugybę įspėjimų, pvz., `npm warn ERESOLVE`, pranešimų apie lygiavertes priklausomybes ir `deprecated` pranešimų. **Tai numatyta ir nekenksminga.** Diegimas pavyko, jei išvestyje matote `added <N> packages`.

Norėdami nerodyti lygiaverčių priklausomybių nustatymo įspėjimų, naudokite „OmniRoute“ palaikomą diegimo formą:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` paslepia tik `ERESOLVE` ir lygiaverčių priklausomybių pranešimus. Pranešimai apie nebenaudojamus paketus lieka matomi, nes juos pateikia tranzityviniai trečiųjų šalių paketai; jie nereiškia, kad diegimas nepavyko.

Įspėjimus sukelia pasenę lygiaverčių priklausomybių versijų intervalai trečiųjų šalių paketuose, kurių „OmniRoute“ nevaldo:

1. **`marked-terminal` reikalauja `marked >=1 <16`, bet rasta `marked@18`** — praktiškai veikia tinkamai; pirminio paketo lygiaverčių priklausomybių versijų intervalas tiesiog pasenęs.
2. **`deprecated prebuild-install@7.1.3`** — tranzityvinė pagalbinė priemonė, skirta savųjų dvejetainių failų gavimui. Ji nėra
   naudojama fiksuotos versijos `wreq-js` transporto sąsajai įdiegti ir nereiškia, kad žiniatinklio slapukų
   teikėjo transporto konfigūravimas nepavyko.

**Jokių veiksmų imtis nereikia** — šių įspėjimų neįmanoma visiškai paslėpti nekuriant pirminių paketų atšakų.

## „Gemini Web“ ir „Playwright Chromium“

Jei „Gemini Web“ užklausa grąžina `503` su pranešimu, kad „Playwright Chromium“
neįdiegtas, npm paketas yra, tačiau trūksta naršyklės dvejetainio failo.
„Playwright“ sąmoningai atskiria naršyklės atsisiuntimą nuo npm paketo
diegimo, todėl toks atsakymas yra numatytas, kol naršyklė neįdiegta.

Jei npm įdiegtas visuotinai, įdiekite „Chromium“ iš „OmniRoute“ paketo
katalogo, kad naršyklės podėlis priklausytų tam pačiam „Playwright“ dieginiui:

npx playwright install chromium

Įdiegę iš naujo paleiskite „OmniRoute“, tada pakartokite „Gemini Web“ užklausą. Jei
„OmniRoute“ paleidžiate iš „Docker“ atvaizdo, naudokite `-web` atvaizdą (arba `runner-web`
komponavimo paskirties objektą), kuriame yra „Chromium“ ir jo priklausomybės; baziniame atvaizde jų

## Klaidingi antivirusinės programos aptikimai

<a name="antivirus-false-positives"></a>

### Avast/AVG izoliuoja `README.md` kaip `MD:HttpRequest-inf[Susp]`

**Tai klaidingas aptikimas. Niekas nėra užkrėsta ir nereikia imtis jokių veiksmų.**

Avast ir AVG naudoja heuristinį tikrinimą, kuris pažymi paprastojo teksto / Markdown failus, kuriuose yra daug
į HTTP užklausas panašių nuorodų. OmniRoute `README.md` pateikiamas npm pakete (jis yra
nurodytas `package.json` → `files`), todėl atliekant visuotinį diegimą patenka į
`node_modules/omniroute/README.md` — o jame yra apie 15 `http://localhost:20128/...`
pavyzdžių (MCP HTTP/SSE galiniai taškai, A2A `.well-known` URL ir `curl` fragmentai). Tokio nuorodų
tankio pakanka, kad suveiktų heuristinis tikrinimas.

Jei tai prasidėjo tik neseniai: failo pobūdis nepasikeitė. README buvo papildytas
galinių taškų lentele (pridėti MCP HTTP + SSE + A2A) ir daugiau `curl` pavyzdžių, todėl
buvo viršyta aptikimo riba.

Failas yra pasyvi dokumentacija, kurioje nėra jokio vykdomojo turinio. Galite saugiai atkurti jį
iš karantino.

**Ką daryti:**

1. **Sustabdykite pranešimus** — antivirusinėje programoje pridėkite diegimo katalogą prie išimčių
   (Avast: Settings → Exceptions), nurodydami savo visuotinį `node_modules` kelią ir (arba)
   OmniRoute duomenų katalogą (`~/.omniroute/`).
2. **Praneškite apie klaidingą aptikimą** — <https://www.avast.com/false-positive-file-form.php>,
   pridėdami į karantiną perkeltą `README.md`. Tai padės išspręsti problemą visiems, nes
   tiekėjo heuristinis tikrinimas pernelyg jautriai sureagavo į tekstinį failą.

**Kodėl mes to „netaisome“ savo pusėje:** visuose pavyzdžiuose naudojamas `http://localhost`, o
localhost negali naudoti `https` be nepatogumų dėl savarankiškai pasirašyto sertifikato. Dokumentacijos
iškraipymas siekiant apeiti vieno tiekėjo heuristinį tikrinimą pakenktų visiems skaitytojams vien tam, kad
būtų įtikta klaidingai veikiančiam skaitytuvui.

### Kaspersky pažymi darbalaukio programą kaip `PDM:Trojan.Win32.Generic`

**Tai klaidingas elgsena pagrįsto heuristinio tikrinimo aptikimas. Niekas nėra užkrėsta.** Kaspersky
priešdėlis `PDM:` reiškia, kad sprendimą priėmė jos Proactive Defense Module (System Watcher),
kuris vertina, ką diegimo programa _daro_, o ne lygina ją su žinomomis kenkėjiškomis programomis. Jam
suveikus, Kaspersky „atšaukia“ visą diegimą — ištrina jau įrašytus failus — todėl
programa galiausiai būna sugadinta arba jos nebelieka.

Pažymėti failai yra standartinės deklaruotų atvirojo kodo priklausomybių, įtrauktų į
darbalaukio programą, dalys, pavyzdžiui:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ir
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), naršyklės automatizavimo
  biblioteka, naudojama prisijungti prie paslaugų teikėjų programoje ir naršykle grindžiamiems pokalbiams.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — fiksuotos versijos savasis `wreq-js` susiejimas, naudojamas naršyklės identifikavimo požymius
  atkartojančioms HTTP užklausoms žiniatinklio slapukus naudojantiems paslaugų teikėjams (`<arch>` yra `x64` arba `arm64`).

**Kodėl tai suveikia:** Windows diegimo programa **dar nėra pasirašyta kodiniu parašu**, todėl nepasirašyta NSIS
diegimo programa neturi jokios reputacijos, o elgsenos heuristika veikia maksimaliai agresyviai. Kartu
su įtraukta savąja DLL ir šimtais `.js` failų, įrašomų į
`%LOCALAPPDATA%\Programs\OmniRoute` (įskaitant Next.js autonominio komponavimo paketo katalogus
su maišos priesagomis), to pakanka heuristiniam tikrinimui suaktyvinti. Kodinį pasirašymą planuojama įdiegti;
kol tai nebus padaryta, problema gali kartotis su naujais leidimais.

**Ką daryti:**

1. **Pirmiausia patikrinkite atsisiųstą failą** (taip atmesite failo pakeitimo galimybę). Su kiekvienu leidimu
   paskelbiamas `latest.yml`, kurio laukas `sha512` (base64 formatu) apima
   `OmniRoute.Setup.<version>.exe` diegimo programą. PowerShell lange, aplanke, kuriame yra diegimo programa:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Išvestis turi sutapti su `latest.yml` → `sha512`. Jei nesutampa, ištrinkite failą ir
   atsisiųskite jį iš naujo tik iš [GitHub leidimų puslapio](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Atkurkite ir pridėkite prie išimčių** — atkurkite iš karantino elementus, pašalintus atšaukiant diegimą, ir pridėkite
   `%LOCALAPPDATA%\Programs\OmniRoute` prie išimčių (Kaspersky → Settings → Threats and Exclusions),
   tada įdiekite iš naujo.
3. **Praneškite apie klaidingą aptikimą** — <https://opentip.kaspersky.com/>. Naudotojų pateikti pranešimai apie klaidingus
   aptikimus iš tiesų pagreitina įtraukimą į leidžiamųjų sąrašą.

## Node.js suderinamumas

<a name="nodejs-compatibility"></a>

### Prisijungimo puslapis užstringa arba rodoma klaida „Module self-registration“

**Priežastis:** naudojate Node.js versiją, kuri neatitinka OmniRoute patvirtintų saugaus vykdymo aplinkos minimalių reikalavimų. Dažniausiai naudojama senesnė Node 22 arba 24 pataisos versija, kuri yra senesnė už OmniRoute reikalaujamą saugumo pataisų minimumą.

**Požymiai:**

- Prisijungimo puslapyje rodomas tuščias ekranas arba serverio klaida
- Konsolėje rodoma `Error: Module did not self-register` arba panašios savųjų sąsajų klaidos
- Jei vykdymo aplinka neatitinka palaikomos saugumo politikos, prisijungimo puslapyje rodoma **oranžinė įspėjimo juosta** su jūsų Node versija

**Sprendimas:**

1. Įdiekite palaikomą Node.js LTS leidimą (rekomenduojama: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Patikrinkite versiją: `node --version` turėtų rodyti `v24.0.0` arba naujesnę 24.x LTS šakos versiją
3. Iš naujo įdiekite OmniRoute: `npm install -g omniroute`
4. Paleiskite iš naujo: `omniroute`

> **Palaikomos saugios versijos:** `>=22.22.2 <23` arba `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) ir Node.js 26 yra visiškai palaikomos.

### npm v11+: `better-sqlite3` neįdiegtas (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Priežastis:** npm v11 (pateikiama su Node.js 24+) pagal numatytuosius nustatymus blokuoja pasirinktinių
priklausomybių diegimo scenarijus. Kadangi `better-sqlite3` yra nurodytas `optionalDependencies`
ir jam būtinas savasis kompiliavimas (`node-gyp rebuild`), npm jį tyliai praleidžia.

**Požymiai:**

- Paleidžiant serveris užstringa ir rodoma `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` parodo „No such file or directory“
- `npm ls better-sqlite3` parodo `(empty)`

**Sprendimas:**

1. Patvirtinkite diegimo scenarijus ir įdiekite iš naujo:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Arba rankiniu būdu įdiekite iš anksto sukompiliuotą paketą:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Patikrinkite, ar veikia: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file“

<a name="macos-native-module-rebuild"></a>

**Priežastis:** visuotinai įdiegus paketą naudojant `npm install -g omniroute`, pakete esantis `better-sqlite3` savasis dvejetainis failas galėjo būti sukompiliuotas kitai architektūrai arba Node.js ABI nei naudojama vietoje. Tai dažnai pasitaiko macOS sistemose (tiek Apple Silicon, tiek Intel), kai iš anksto sukompiliuotas dvejetainis failas neatitinka jūsų aplinkos.

**Požymiai:**

- Paleidžiamas serveris iš karto nustoja veikti ir rodoma `dlopen` klaida
- Klaidoje yra `slice is not valid mach-o file`
- Visas pavyzdys:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Sprendimas — perkompiliuokite vietinei aplinkai (nereikia naudoti senesnės Node.js versijos):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Pastaba:** taip savoji sąsaja perkompiliuojama jūsų vietinei Node.js versijai ir procesoriaus architektūrai, todėl pašalinama dvejetainių failų neatitiktis. Oficialiai palaikomas vykdymo aplinkos versijų intervalas yra **`>=22.22.2 <23` arba `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` faile `src/shared/utils/nodeRuntimeSupport.ts`, suderintas su `package.json` lauku `engines`). Node.js 24.x LTS (Krypton) ir Node.js 26 yra visiškai palaikomos naudojant `better-sqlite3` v12.x.

## Tarpinio serverio problemos

<a name="proxy-issues"></a>

### Teikėjo patvirtinimo metu rodoma „fetch failed“

**Priežastis:** API rakto patvirtinimo galinis taškas (`POST /api/providers/validate`) anksčiau nepaisė tarpinio serverio konfigūracijos, todėl aplinkose, kuriose būtinas maršruto parinkimas per tarpinį serverį, kildavo klaidų.

**Pataisymas (v3.5.5+):** Ši problema ištaisyta. Dabar teikėjo patvirtinimas vykdomas per `runWithProxyContext`, automatiškai atsižvelgiant į teikėjo lygmens ir visuotinius tarpinio serverio nustatymus.

### Prieigos rakto būklės patikra nepavyksta ir rodoma „fetch failed“

**Priežastis:** Foninis OAuth prieigos rakto atnaujinimas nenustatydavo kiekvienam ryšiui skirtos tarpinio serverio konfigūracijos.

**Pataisymas (v3.5.5+):** Prieigos rakto būklės patikros planuoklis dabar prieš bandydamas atnaujinti nustato kiekvieno ryšio tarpinio serverio konfigūraciją. Atnaujinkite į v3.5.5+.

### SOCKS5 tarpinis serveris grąžina „invalid onRequestStart method“

**Priežastis:** Naudojant Node.js 22, undici@8 dispečeris nesuderinamas su Node integruotu `fetch()` įgyvendinimu.

**Pataisymas (v3.5.5+):** Kai aktyvus tarpinio serverio dispečeris, „OmniRoute“ dabar naudoja pačios undici funkciją `fetch()`, taip užtikrinant nuoseklų veikimą. Atnaujinkite į v3.5.5+.

### MITM tarpinis serveris WSL aplinkoje: „Windows“ pagrindinėje sistemoje veikiančios darbalaukio programos neperimamos

**Priežastis:** MITM tarpinis serveris ir jo CA sertifikatas įdiegiami aplinkoje, kurioje veikia „OmniRoute“. Naudojant WSL, ši aplinka yra „Linux“ svečio sistema, o DI darbalaukio programos („Kiro“, „Trae“, „Copilot“, „Zed“, …) veikia „Windows“ pagrindinėje sistemoje. Pagrindinės sistemos programos nepasitiki svečio sistemos sertifikatų saugykla ir neperduoda srauto per svečio sistemos tarpinį serverį, todėl darbalaukio srauto perėmimas jose neveikia.

**Rekomendacija:** Paleiskite „OmniRoute“ tiesiogiai toje pačioje operacinėje sistemoje kaip darbalaukio programos, kurių srautą norite perimti („Windows“ – „Windows“ programoms; analogiškai „macOS“ ar „Linux“). Jei „OmniRoute“ laikomas WSL aplinkoje, o taikomasi į pagrindinės sistemos programas, sugeneruotu CA sertifikatu reikia neautomatiškai pažymėti kaip patikimu „Windows“ pagrindinėje sistemoje ir kiekvienos pagrindinės sistemos programos tinklo arba tarpinio serverio nustatymuose nurodyti WSL tarpinio serverio galinį tašką — tai nepalaikoma ir nepatikima konfigūracija.

„OmniRoute“ automatiškai atnaujina prieigos raktus. Jei problemos išlieka:

1. Valdymo skydelis → Teikėjas → Prisijungti iš naujo
2. Pašalinkite ir iš naujo pridėkite teikėjo ryšį

Ryšiai, kurie buvo importuoti _iki_ v3.8.0, neturi kiekvienam ryšiui atskiros kliento
registracijos. Šie ryšiai ir toliau naudoja bendrą socialinio autentifikavimo atnaujinimo galinį tašką.
Norėdami juos izoliuoti, pašalinkite seną ryšį pasirinkę Valdymo skydelis → Teikėjai ir pridėkite jį iš naujo
naudodami bet kurį iš trijų importavimo būdų.

Išsamią informaciją ir nuoseklias instrukcijas, kaip vienu metu pridėti dvi „Kiro“ paskyras,
rasite [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Debesijos problemos

### Debesijos sinchronizavimo klaidos

1. Patikrinkite, ar `BASE_URL` nurodo jūsų veikiantį egzempliorių (pvz., `http://localhost:20128`)
2. Patikrinkite, ar `CLOUD_URL` nurodo jūsų debesijos galinį tašką (pvz., `https://omniroute.dev`)
3. Užtikrinkite, kad `NEXT_PUBLIC_*` reikšmės atitiktų serverio pusės reikšmes

### Debesijoje `stream=false` grąžina 500

**Požymis:** `Unexpected token 'd'...` debesijos galiniame taške vykdant nesrautines užklausas.

**Priežastis:** Tiekėjas grąžina SSE naudingąją apkrovą, nors klientas tikisi JSON.

**Laikinas sprendimas:** Tiesioginėms debesijos užklausoms naudokite `stream=true`. Vietinėje vykdymo aplinkoje yra SSE→JSON atsarginis mechanizmas.

### Debesija rodo, kad prisijungta, tačiau pateikia „Invalid API key“

1. Vietiniame valdymo skydelyje sukurkite naują raktą (`/api/keys`)
2. Paleiskite debesijos sinchronizavimą: Įgalinti debesiją → Sinchronizuoti dabar
3. Seni arba nesinchronizuoti raktai debesijoje vis tiek gali grąžinti `401`

## Docker problemos

### Docker IPv6 / ryšio atstatymas

<a name="docker-ipv6"></a>

**Požymiai:** `curl http://localhost:20128/v1/models` grąžina `curl: (56) Recv failure: Connection reset by peer`. Valdymo skydelis ir tapatybės nepatvirtinantys galiniai taškai veikia, tačiau tapatybės patvirtinimo reikalaujantys galiniai taškai neveikia — atrodo, kad tai tapatybės patvirtinimo problema, nors taip nėra.

**Priežastis:** `docker run -p 20128:20128` publikuoja ir per `0.0.0.0` (IPv4), ir per `::` (IPv6), tačiau konteineryje veikiantis procesas klausosi tik IPv4. Pagrindiniuose kompiuteriuose, kuriuose `localhost` pirmiausia išsprendžiamas į `::1`, ryšys patenka į publikuotą IPv6 prievadą, už kurio nėra klausytojo → ryšys atstatomas.

**Sprendimas:**

1. **Greita diagnostika:** Paleiskite `curl -4 http://localhost:20128/v1/models`. Jei su `-4` veikia, o be jo — ne, IPv6 susiejimas neatitinka.
2. **Nuolatinis sprendimas:** Aiškiai susiekite su IPv4, komandoje `docker run` naudodami `-p 127.0.0.1:20128:20128`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Tai priverstinai susieja su IPv4 ir taip pat neleidžia tarpiniam serveriui būti pasiekiamam per visas pagrindinio kompiuterio sąsajas.

---

### CLI įrankis rodomas kaip neįdiegtas

## Atsparumo nustatymai

### Automatinis užklausų dažnio ribojimas nesuveikia

- Automatinis užklausų dažnio ribojimas taikomas tik API rakto teikėjams (ne OAuth / prenumeratoms)
- Patikrinkite, ar skiltyje **Nustatymai → Atsparumas → Teikėjų profiliai** įjungtas automatinis užklausų dažnio ribojimas
- Patikrinkite, ar teikėjas grąžina `429` būsenos kodus arba `Retry-After` antraštes

### Eksponentinio delsos didinimo derinimas

Teikėjų profiliai palaiko šiuos nustatymus:

- **Bazinė delsa** — pradinis laukimo laikas po pirmosios nesėkmės (numatytoji reikšmė: 1s)
- **Didžiausia delsa** — didžiausia laukimo laiko riba (numatytoji reikšmė: 30s)
- **Daugiklis** — kiek didinti delsą po kiekvienos iš eilės įvykusios nesėkmės (numatytoji reikšmė: 2x)

### Užklausų antplūdžio prevencija

Kai daug lygiagrečių užklausų pasiekia teikėją, kuriam taikomas užklausų dažnio ribojimas, OmniRoute naudoja mutex ir automatinį užklausų dažnio ribojimą, kad užklausos būtų vykdomos nuosekliai ir būtų išvengta pakopinių gedimų. API rakto teikėjams tai atliekama automatiškai.

### Pokalbio užklausos nepavyksta su 503 / chat_admission_busy

**Požymiai:**

- Pokalbio užbaigimų galinis taškas grąžina pakartotinai bandyti leidžiantį `503` atsakymą, kurio klaidos kodas yra
  `chat_admission_busy`.
- Atsakyme yra `Retry-After`. Nuo #12135 reikšmė nustatoma pagal stebimą
  užimtumą — pasirenkama didesnė iš `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` intervalo, kurį užklausa jau
  laukė, ir laiko, kurį laikomos esamos sunkiasvorių užklausų nuomos — suapvalinama aukštyn iki sveikų
  sekundžių ir apribojama iki 60. Kai vartai neužimti, išlaikomos istorinės minimalios reikšmės: 2 sekundės
  baitais pagrįstame kelyje, 1 sekundė struktūra pagrįstame kelyje (jame taip pat pateikiama
  `reason: "structure_limit"`).
- Taip gali nutikti, kol kita sunkiasvorė pokalbio užklausa arba ilgai vykdomas srautinis atsakymas vis dar
  apdorojamas.

Baitais pagrįsto atsakymo turinys yra:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Struktūra pagrįstame atsakyme naudojamas tas pats tipas ir kodas, o pranešimas yra
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ir `reason: "structure_limit"`.
Esant numatytosioms ribinėms reikšmėms, užklausa laikoma struktūriškai sunkia, kai joje yra bent `200` pranešimų,
bent `64` įrankiai arba bent `32,000` apskaičiuotų atpažinimo ženklų, arba kai apribotas struktūros vertinimas
išnaudoja savo ribas: `10,000` aplankytų mazgų arba gylį `12`.

**Priežastis:** Tai sąmoningas apkrovos mažinimas OmniRoute viduje, o ne aukštesnio lygio teikėjo gedimas.
Kiekvienas procesas naudoja vietinę proceso apsaugą, kad rezervuotų ribotus sunkiasvorių užklausų išteklius prieš išlaikydamas
ir analizuodamas didelį užklausos turinį. Sunkiasvorės užklausos nuoma lieka aktyvi visą SSE
atsakymo gyvavimo laiką.

**#503 išplitimas:** prieš šį pataisymą apsauga ribojo lygiagretumą pagal fiksuotą užklausų SKAIČIŲ
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, numatytoji reikšmė `1`), neatsižvelgdama į pagrindinio kompiuterio atmintį, todėl programavimo agentų
išsišakojimas (keli pagalbiniai agentai / CLI, užklausų turiniai įprastai > 256 KB) sumažindavo faktinį
lygiagretumą iki ~1 ir visiškai įprastos apkrovos metu sukeldavo 503 klaidas. Dabar apsauga prisiderina
automatiškai: ją valdo automatiškai nustatytas priimamų BAITŲ biudžetas (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), apskaičiuotas pagal
tikrąją proceso atminties ribą, be to, atsižvelgiama į tiesioginį išteklių apkrovos signalą — todėl
apkrova mažinama tik tada, kai pagrindiniame kompiuteryje iš tiesų trūksta atminties, o ne vien todėl, kad vienu metu
gauta daugiau nei viena sunki užklausa. Senoji skaičiaus riba (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) vis dar
taikoma, tačiau tik jei ją aiškiai nustatote.

Kai ištekliai užimti, sunkiasvorė užklausa pirmiausia iki
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (numatytoji reikšmė `2000`, `0` išjungia laukimą) laukia, kol atsilaisvins vieta,
ir tik tada pateikiamas pakartotinai bandyti leidžiantis `503` atsakymas. Ribotas laukimas naudojamas tam, kad agentų tipo klientai
(OpenCode, Claude Code, Cursor), vienu metu išsišakojantys į sunkias pagalbines užklausas, apdorotų antplūdį nuosekliai,
užuot išnaudoję visą pakartotinių bandymų limitą dėl nedelsiamų atmetimų ir nutrūkę viduryje užduoties.
Dabartinis sunkiasvorių užklausų nuomų užimtumas, nustatytas baitų biudžetas ir tiesioginis apkrovos lygis
pateikiami adresu `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — patikrinkite juos prieš keisdami bet kokį aplinkos kintamąjį.
Nustatymai → Atsparumas → Užklausų eilė → Lygiagrečios užklausos šio mechanizmo nevaldo; šis nustatymas
valdo atskirą teikėjo užklausų eilės mechanizmą.

**Sprendimas:**

1. Pirmiausia bandykite pakartotinai. Klientai turėtų paisyti `Retry-After` ir naudoti didėjančią delsą, užuot nedelsdami
   kartoję užklausą.
2. Prieš ką nors derindami patikrinkite `/api/monitoring/health` → `chatAdmission`. `countCapEnabled:
false` ir pakankamai didelė `maxInflightBytes` reikšmė reiškia, kad automatiškai nustatytas biudžetas jau veikia
   tinkamai; `pressureSeverity` reikšmė `high`/`critical` reiškia, kad pagrindiniame kompiuteryje iš tiesų trūksta atminties —
   to negalima ištaisyti priėmimo aplinkos kintamuoju, reikia daugiau RAM arba mažesnio darbo krūvio.
3. Tik jei `/api/monitoring/health` rodo, kad automatiškai nustatytas biudžetas iš tiesų yra per mažas
   jūsų pagrindiniam kompiuteriui (tai reta — jis jau prisitaiko nuo konteinerio iki fizinės infrastruktūros), pakeiskite jį tiesiogiai naudodami
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, užuot grįžę prie senojo užklausų skaičiaus apribojimo.

Autoritetingus priėmimo nustatymus rasite [aplinkos kintamųjų žinyne](../reference/ENVIRONMENT.md#4-security--authentication).

## Žinomos v3.8.0 problemos

v3.8.0 leidimui būdingos problemos ir dabartiniai jų sprendimo būdai. Jei pataisa bus įtraukta į vėlesnį pataisų leidimą, įrašas bus atnaujintas arba pašalintas.

### Devin CLI autentifikavimo klaidos

**Požymiai:**

- Iškviečiant Devin pagrįstus įrankius rodoma „Devin CLI nerasta“ arba „autentifikuoti nepavyko“
- CLI vykdymo aplinkos patikra pateikia `installed=false`

**Priežastys:**

- `CLI_DEVIN_BIN` nurodo neegzistuojantį kelią
- Devin CLI neįdiegta pagrindiniame kompiuteryje

**Sprendimas:**

1. Įdiekite savo platformai skirtą Devin CLI
2. Faile `.env` nustatykite `CLI_DEVIN_BIN=/usr/local/bin/devin` (arba tikrąjį kelią)
3. Paleiskite OmniRoute iš naujo ir dar kartą patikrinkite per **Valdymo skydas → CLI įrankiai**

### Užstrigęs modelio atvėsinimas (rankinis nustatymas iš naujo)

**Požymiai:**

- Modelis tebėra nurodomas kaip atvėsinamas net ir pasibaigus nustatytam laikui
- Maršruto parinkimas pagal derinį vis dar praleidžia modelį, nors laiko žyma yra praeityje

**Rankinis nustatymas iš naujo:**

- **Valdymo skydas:** **Nustatymai → Modelių atvėsinimai** → paveiktoje kortelėje spustelėkite **Įjungti iš naujo**
- **API:** `DELETE /api/resilience/model-cooldowns` su valdymo autentifikavimo antraštėmis

### Command Code teikėjo ryšys nutrūksta su 403 klaida

**Požymiai:**

- Tikrinant ryšį su Command Code teikėju gaunama 403 klaida
- Ką tik pridėto teikėjo kortelėje rodoma „neautorizuota“

**Priežastis:** OAuth procesas nebuvo užbaigtas (negautas atgalinis iškvietimas arba prieigos raktas neišsaugotas).

**Sprendimas:**

- CLI aplinkoje paleiskite `omniroute providers`, kad iš naujo inicijuotumėte OAuth procesą, arba
- Dar kartą paleiskite OAuth per **Valdymo skydas → Teikėjai → Command Code → Prisijungti iš naujo**

### ModelScope grąžina agresyvius 429 atvėsinimo laikotarpius

**Požymiai:**

- Po nedidelio užklausų pliūpsnio ModelScope pritaiko labai trumpus arba momentinius atvėsinimo laikotarpius
- Maršruto parinkimas pagal derinį pradeda praleisti ModelScope anksčiau nei tikėtasi

**Priežastis:** ModelScope pateikia konkrečiam teikėjui skirtas `Retry-After` antraštes. v3.8.0 turi specialią šių antraščių apdorojimo funkciją, todėl senesnės versijos klaidingai interpretuoja jas kaip bendrąsias užklausų dažnio ribojimo nuorodas.

**Sprendimas:**

- Įsitikinkite, kad naudojate v3.8.0 arba naujesnę versiją
- Patikrinkite, ar skiltyje **Nustatymai → Atsparumas** įjungtas `useUpstream429BreakerHints` perjungiklis

### Gamybinėje aplinkoje nėra OMNIROUTE_WS_BRIDGE_SECRET

**Požymiai:**

- Vykdant nuotoliniame gamybiniame pagrindiniame kompiuteryje, kiekviena Codex/Responses WebSocket tilto užklausa gauna 401 klaidą
- WebSocket tilto ryšio užmezgimas nutraukiamas iš karto po prisijungimo

**Priežastis:** Gamybinėje aplinkoje nėra `OMNIROUTE_WS_BRIDGE_SECRET` aplinkos kintamojo.

**Sprendimas:**

1. Sugeneruokite atsitiktinę paslaptį: `openssl rand -hex 32`
2. Gamybinio serverio aplinkoje nustatykite `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` (taip pat visuose klientuose, kurie palaiko ryšį su tiltu)
3. Paleiskite OmniRoute iš naujo

### Responses API: foninis režimas pakeistas sinchroniniu režimu

**Požymiai:**

- Žurnale įrašomas įspėjimas: `background mode degraded to synchronous`
- Užklausa su `background: true` vietoje foninės užduoties deskriptoriaus grąžina įprastą sinchroninį atsakymą

**Priežastis:** v3.8.0 versijoje Responses API užklausoms su `background: true` sąmoningai naudojamas sinchroninis vykdymas ir pateikiamas įspėjimas. Visavertis asinchroninis foninis vykdymas bus įdiegtas ateityje.

**Sprendimas:**

- Pakoreguokite klientą, kad jis siųstų užklausas be `background`, arba
- Palaukite vėlesnio leidimo, kuriame bus įdiegtas visavertis asinchroninis foninis režimas (sekite pakeitimų žurnalą)

## Lėtas paleidimas / parengties skirtasis laikas

Jei CLI išveda `⚠ Server did not respond within 60s`, tačiau serveris iš tikrųjų
veikia, jūsų aplinkai skirtas parengties tikrinimo laikas yra per trumpas.

Taip dažnai nutinka sistemoje Windows (dėl antivirusinės programos, failų sistemos stebėjimo priemonių) arba konteineriuose,
kuriuose paleidimo metu vykdomas didelis darbo krūvis.

**Sprendimas — padidinkite skirtąjį laiką:**

```bash
# Naudojant aplinkos kintamąjį (išlieka tarp paleidimų):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minutės
omniroute serve

# Naudojant CLI parametrą (vienam kartui):
omniroute serve --ready-timeout 180000
```

Numatytoji reikšmė yra 60 000 ms (60 s). Įspėjimas yra tik informacinio pobūdžio; serveris
toliau paleidžiamas fone ir bus pasiekiamas, kai paleidimas bus baigtas.

Išsamią informaciją apie `OMNIROUTE_READY_TIMEOUT_MS` rasite
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
