La decrittazione trasparente TPROXY è la **5ª modalità di cattura** di OmniRoute per lo stack MITM di
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md).
Intercetta e **decrittografa** il traffico HTTPS locale in uscita su Linux
utilizzando TPROXY del kernel e il routing basato su criteri — **senza** falsificare `/etc/hosts` e
**senza** modificare le impostazioni del proxy di sistema a livello di sistema operativo. È adatta agli ambienti headless
(nessuna modifica DNS da ripulire) e le regole del firewall vengono eliminate automaticamente al riavvio.

A differenza delle altre modalità di cattura, TPROXY non richiede alcuna configurazione per singolo host: intercetta in modo trasparente
host di destinazione **arbitrari** su una porta di destinazione, termina TLS con
un certificato leaf emesso al volo per ciascun nome host SNI, acquisisce lo scambio
decrittografato e crittografa nuovamente la richiesta verso la destinazione originale.

> **Solo Linux, solo root, con attivazione esplicita.** Questa modalità richiede Linux, un addon nativo
> compilato con una toolchain C e la funzionalità **CAP_NET_ADMIN** (in genere root). È protetta
> dall'API AgentBridge accessibile solo tramite loopback ed è disabilitata per impostazione predefinita. Una CA
> MITM attendibile in grado di firmare per qualsiasi host è una funzionalità potente — consulta [§6 Sicurezza](#6-security).

**Sorgente:** `src/mitm/tproxy/`
**Route API:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**Interruttore nella dashboard:** Traffic Inspector → barra degli strumenti delle modalità di cattura → **"Decrittazione TPROXY"** ⚠
**Vedi anche:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 Che cos'è e quando utilizzarla

Le altre quattro modalità di cattura presentano ciascuna una limitazione:

| Modalità            | Come viene instradato il traffico                              | Limitazione                                                  |
| ------------------- | -------------------------------------------------------------- | ------------------------------------------------------------ |
| AgentBridge         | spoofing DNS tramite `/etc/hosts` per un insieme fisso di host | solo gli host degli agenti IDE registrati                    |
| Host personalizzati | spoofing DNS tramite `/etc/hosts` per ciascun host             | una voce per host; sudo per modificare il file hosts         |
| HTTP_PROXY          | variabili di ambiente `HTTP_PROXY`/`HTTPS_PROXY`               | solo le applicazioni che rispettano la variabile di ambiente |
| Proxy di sistema    | impostazioni proxy del sistema operativo                       | modifica lo stato globale; richiede il ripristino            |

La decrittazione trasparente TPROXY instrada invece il traffico a livello di **kernel**.
Contrassegna le nuove connessioni TCP locali in uscita verso una porta di destinazione (predefinita: `443`) nella
catena `mangle OUTPUT`; una `ip rule` reindirizza i pacchetti contrassegnati alla consegna locale
e, al rientro, la destinazione `TPROXY` di `mangle PREROUTING` li inoltra a un
listener **IP_TRANSPARENT**, che termina quindi TLS e acquisisce il testo in chiaro.

Utilizzala quando vuoi acquisire e decrittografare il traffico proveniente da un processo che:

- comunica con un host non registrato da AgentBridge, e
- non rispetta `HTTP_PROXY`, e
- non vuoi interferire con una modifica del proxy a livello di sistema.

Poiché l'intercettazione avviene nel kernel, il processo di origine non richiede **alcuna
modifica della configurazione** — ma deve considerare attendibile la CA dinamica installata da OmniRoute
(consulta [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 Requisiti

| Requisito         | Dettaglio                                                                                                                                                            |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **SO**            | Solo Linux — **IP_TRANSPARENT** è un'opzione socket disponibile esclusivamente su Linux. Il loader restituisce "non disponibile" su qualsiasi altra piattaforma.     |
| **Privilegi**     | La capability **CAP_NET_ADMIN** per creare il socket trasparente e applicare le regole `iptables`/`ip` — in pratica, eseguire come root.                             |
| **Addon nativo**  | È necessario compilare o distribuire come prebuild un piccolo addon N-API (`src/mitm/tproxy/native/transparent.c`). Vedere [§3](#3-the-native-ip_transparent-addon). |
| **Moduli kernel** | `iptables` con supporto per `TPROXY`, `mangle` e la corrispondenza `mark` (convalidato con il kernel 6.8.0).                                                         |

**Degradazione controllata:** se manca uno qualsiasi dei requisiti (sistema non Linux, toolchain assente,
addon non compilato), il loader dell'addon (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
restituisce `null` anziché generare un'eccezione. Lo stato della modalità di acquisizione segnala quindi
`available: false`, l'interruttore nella dashboard è **disabilitato** con il tooltip
"La decrittazione TPROXY richiede Linux + root + l'addon nativo", mentre il resto di
OmniRoute continua a funzionare.

## §3 L'addon nativo IP_TRANSPARENT

Il modulo `net` di Node non può eseguire `setsockopt(IP_TRANSPARENT)` _prima_ di `bind()`, come
richiesto da TPROXY (altrimenti il kernel scarta i pacchetti reindirizzati). L'addon
(`src/mitm/tproxy/native/transparent.c`, compilato tramite `binding.gyp`) è un piccolo modulo
N-API che espone tre funzioni, utilizzate tramite `transparentSocket.ts`:

| Funzione dell'addon                   | Operazioni sul socket                                                                                       | Utilizzo                                                                                    |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, restituisce il fd non elaborato | il listener di acquisizione trasparente (Node adotta il fd tramite `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | `setsockopt` **SO_MARK** su un fd esistente                                                                 | prevenzione dei loop (contrassegna i socket del proxy stesso)                               |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **prima** di un `connect()` non bloccante, restituisce il fd                       | l'inoltro upstream ricifrato (il SYN trasporta il contrassegno)                             |

La destinazione originale viene letta da `socket.localAddress`/`localPort` — TPROXY
la preserva, quindi non è necessaria alcuna ricerca **SO_ORIGINAL_DST**/NAT.

### Compilazione dell'addon

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- Durante `npm run build`, `scripts/build/build-tproxy-native.mjs` esegue `node-gyp
rebuild`. È un'operazione **esclusiva di Linux e non fatale** — una toolchain mancante rende semplicemente
  non disponibile la modalità di acquisizione.
- `assembleStandalone.mjs` copia `build/Release/transparent.node` nel bundle
  standalone; `transparentSocket.ts` lo risolve sia relativamente al modulo sia
  relativamente alla cwd (`<cwd>/src/mitm/tproxy/native/...`).
- `build/` e `prebuilds/` sono ignorati da git — il file binario viene **compilato, mai
  incluso nei commit**.

Il loader verifica, in ordine di priorità:
`native/build/Release/transparent.node`, quindi `native/prebuilds/transparent.node`
(sia relativamente al modulo sia in `<cwd>/src/mitm/tproxy/`).

## §4 La CA dinamica per SNI e il programma di installazione nell'archivio di attendibilità

> **Aggiornamento #6684:** il server statico AgentBridge (`src/mitm/server.cjs`) ora
> condivide lo stesso modello architetturale CA/foglia anziché utilizzare un singolo
> certificato foglia statico autofirmato. Utilizza un'istanza CA **distinta**
> (`src/mitm/cert/rootCa.ts`, persistita in `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> e viene installata nello slot preesistente `omniroute-mitm.crt` dell'archivio di
> attendibilità (sostituendo il precedente certificato foglia singolo — non è necessaria
> alcuna pulizia della doppia attendibilità), mantenuto completamente separato dallo slot
> `omniroute-tproxy-ca.crt` di TPROXY descritto di seguito.
> Le nuove installazioni di AgentBridge adottano automaticamente il modello CA; un'installazione
> che considerava già attendibile il precedente certificato foglia statico continua a utilizzarlo
> finché l'operatore non abilita esplicitamente `MITM_ROOT_CA_ENABLED=true` (vedere
> `src/mitm/cert/migration.ts`) — una CA MITM attendibile in grado di firmare un certificato
> foglia per **qualsiasi** host è sostanzialmente più potente del precedente certificato foglia
> con SAN fisso, pertanto il passaggio non avviene mai silenziosamente per un'installazione
> che lo considera già attendibile.

Storicamente, il certificato MITM statico di AgentBridge funzionava solo perché
AgentBridge esegue lo spoofing DNS di un insieme **fisso** di host (ora unificato
con il modello seguente). TPROXY intercetta host **arbitrari**, quindi il relativo
listener deve presentare un certificato foglia valido per qualsiasi SNI richiesto
dal client — lo stesso requisito che ora AgentBridge deve soddisfare per l'intero
insieme `MITM_TOOL_HOSTS` (9 voci di strumenti), anziché per i soli 4 host
antigravity.

### CA dinamica (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` gestisce una CA locale (basata sulla dipendenza `selfsigned`) che:

- Genera una CA di lunga durata tramite `generateMitmCa()` (CN `"OmniRoute MITM CA"`,
  validità di 10 anni, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  RSA a 2048 bit / SHA-256).
- Emette **un certificato foglia per ciascun nome host SNI su richiesta** tramite
  `issueLeafCert()` (validità di 1 anno, `subjectAltName` = host SNI) e memorizza
  nella cache un `tls.SecureContext` per nome host.
- Espone `createSNICallback()` per il server che termina TLS (vedere [§5](#5-how-decrypt-and-capture-work)).
- Può essere costruito con un `existingCa` per mantenere stabile la CA tra i riavvii
  (in modo che non sia necessario reinstallarla nell'archivio di attendibilità).

La chiave privata della CA **non lascia mai la macchina**.

### Programma di installazione nell'archivio di attendibilità (`src/mitm/tproxy/caTrust.ts`)

Il client intercettato deve considerare attendibile la CA dinamica, pertanto l'avvio
della modalità di acquisizione installa il certificato CA nell'archivio di attendibilità
del sistema operativo in uno **slot dedicato** — `omniroute-tproxy-ca.crt` (costante
`TPROXY_CA_CERT_NAME`) — mantenuto separato dallo slot del certificato MITM statico
(`omniroute-mitm.crt`), affinché i due non si sovrascrivano mai a vicenda.

`installTproxyCa(caPem, sudoPassword?)` rileva la directory degli anchor della distribuzione
(nell'ordine: prima lo stile Debian) ed esegue il comando di aggiornamento corrispondente:

| Directory degli anchor                      | Comando di aggiornamento |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

L'installazione deposita il PEM in un file temporaneo, quindi esegue (con privilegi)
`mkdir -p` sulla directory degli anchor, copia tramite `cp` il file temporaneo al suo
interno ed esegue il comando di aggiornamento. `uninstallTproxyCa()` rimuove soltanto
lo slot dedicato (lasciando intatto il certificato MITM statico) ed esegue l'aggiornamento
— sui sistemi non Linux non esegue alcuna operazione.

Tutti i comandi con privilegi vengono eseguiti tramite `execFileWithPassword`
(`src/mitm/systemCommands.ts`) — `spawn` con **array di argomenti, senza shell e senza
interpolazione di stringhe** (Regola rigida n. 13). Quando il processo viene eseguito
come root (ad esempio sul VPS), il comando di destinazione viene eseguito direttamente
e non è necessaria alcuna password; su un desktop non root, `sudoPassword` viene passata
a `sudo -S` tramite stdin.

> Il valore `sudoPassword` del desktop viene fornito nel corpo della richiesta POST per
> autorizzare l'installazione nell'archivio di attendibilità; viene completamente ignorato
> quando il processo viene eseguito come root.

## §5 Come funzionano la decifratura e l'acquisizione

La pipeline (interamente in `src/mitm/tproxy/`):

```
app locale  ──TCP/443──▶  mangle OUTPUT contrassegna la connessione (fwmark)
                           ip rule → tabella di routing locale → lo
                           mangle PREROUTING TPROXY → listener IP_TRANSPARENT (porta 8443)
                               │  captureMode.ts: legge la destinazione originale da socket.localAddress
                               ▼
                           tlsCapture.ts:
                             1. termina TLS per il CLIENT con un certificato foglia per SNI (dynamicCert)
                             2. un http.Server interno analizza il testo in chiaro decifrato
                             3. acquisizione → globalTrafficBuffer.push() con source: "tproxy"
                                (sanitizeHeaders + maskSecret applicati)
                             4. inoltra, nuovamente cifrato, alla destinazione originale
                                tramite un socket contrassegnato per il bypass (connectMarked, anti-loop)
                               │
                               ▼
                           upstream originale (api.example.com)
```

- **Terminazione TLS** (`createTlsCaptureServer`): incapsula il socket grezzo
  intercettato in un `tls.TLSSocket` lato server utilizzando il callback SNI
  della CA dinamica, quindi passa il flusso decifrato a un `http.Server` interno
  (la tecnica standard di terminazione MITM). La durata dei socket è limitata da
  `MITM_IDLE_TIMEOUT_MS`, affinché un tunnel bloccato non possa esaurire i
  descrittori di file.
- **Acquisizione** (`handleDecryptedRequest`): inserisce un `InterceptedRequest`
  con `source: "tproxy"`, stato iniziale `"in-flight"`, header elaborati tramite
  `sanitizeHeaders()` e corpi tramite `maskSecret()` prima del loro inserimento
  nel buffer. La voce viene quindi aggiornata con la risposta, le dimensioni e
  la latenza.
- **Inoltro nuovamente cifrato** (`createForward` / `realForward`): cifra
  nuovamente il traffico verso la destinazione originale. `rejectUnauthorized`
  è impostato per impostazione predefinita su **`true`** (sicuro per impostazione
  predefinita): il certificato upstream viene verificato rispetto all'SNI/Host
  richiesto dal client, quindi il proxy rifiuta esattamente ciò che rifiuterebbe
  il client originale.

### Anti-loop (SO_MARK)

Poiché le regole contrassegnano le nuove connessioni locali in uscita, l'inoltro
nuovamente cifrato del proxy verrebbe normalmente intercettato di nuovo, creando
un ciclo infinito. Il percorso di inoltro evita questo problema mediante un
contrassegno di bypass del socket (**SO_MARK**):

- `realForward` apre il proprio socket upstream tramite
  `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` — `DEFAULT_BYPASS_MARK = 0x539`
  — che imposta **SO_MARK** **prima** di `connect()`, in modo che il SYN
  dell'inoltro includa il contrassegno di bypass.
- La regola `mangle OUTPUT` esclude le connessioni che includono già il
  contrassegno di bypass (`-m mark ! --mark <bypassMark>`), quindi l'inoltro del
  proxy **non** viene contrassegnato di nuovo e non rientra in TPROXY.

> Nota sull'implementazione: il socket contrassegnato per il bypass deve essere
> installato nel `createConnection` dell'agent (`https.request({ createConnection })`
> viene ignorato senza alcun avviso quando è presente un agent), altrimenti
> l'inoltro aprirebbe un socket non contrassegnato e il ciclo si ripresenterebbe.
> Questa è stata la correzione anti-loop convalidata tramite test e2e.

## §6 Sicurezza

| Controllo                                    | Dettaglio                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API accessibile solo da loopback**         | `/api/tools/agent-bridge/tproxy` è coperta dal prefisso `/api/tools/agent-bridge/` in `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`). L'accesso da loopback viene imposto **prima** dell'autenticazione (Regole rigide n. 15 e n. 17): un JWT trapelato attraverso un tunnel non può avviare l'acquisizione TPROXY, che applica regole `iptables` e installa una CA nell'archivio delle autorità attendibili tramite processi figlio. |
| **Slot CA dedicato**                         | La CA dinamica viene installata in `omniroute-tproxy-ca.crt`, senza mai sovrascrivere il certificato MITM statico.                                                                                                                                                                                                                                                                                                                                  |
| **La chiave della CA non lascia mai l'host** | `DynamicCertStore` conserva la chiave della CA in memoria e non la esporta.                                                                                                                                                                                                                                                                                                                                                                         |
| **Mascheramento dei segreti**                | `maskSecret()` sui corpi delle richieste/risposte e `sanitizeHeaders()` sulle intestazioni vengono eseguiti **prima** di `globalTrafficBuffer.push()`.                                                                                                                                                                                                                                                                                              |
| **Nessuna interpolazione della shell**       | Tutti i comandi `iptables`/`ip`/relativi all'archivio delle autorità attendibili vengono eseguiti tramite `execFile`/`execFileWithPassword` con array di argomenti (Regola rigida n. 13).                                                                                                                                                                                                                                                           |
| **Verifica del certificato upstream**        | L'inoltro con nuova cifratura verifica per impostazione predefinita il certificato upstream (`rejectUnauthorized: true`).                                                                                                                                                                                                                                                                                                                           |
| **Sanificazione degli errori**               | Le risposte di errore della route vengono elaborate tramite `sanitizeErrorMessage()` (Regola rigida n. 12).                                                                                                                                                                                                                                                                                                                                         |

**La CA MITM è una funzionalità potente.** Una CA considerata attendibile dal sistema operativo e in grado di firmare per qualsiasi
host implica che tutto ciò che OmniRoute intercetta possa essere decifrato. È protetta dalla
modalità esplicita di acquisizione TPROXY, accessibile solo localmente e disattivata per impostazione predefinita; inoltre, la relativa voce
viene rimossa dall'archivio delle autorità attendibili quando la modalità viene arrestata.

## §7 Applicazione / ripristino transazionale del firewall

Un arresto anomalo non deve mai lasciare una regola `mangle` o una route obsoleta. Il generatore di comandi
(`src/mitm/tproxy/commands.ts`) e l'esecutore (`src/mitm/tproxy/setup.ts`) garantiscono che
**il ripristino sia l'esatto inverso dell'applicazione, in ordine inverso**.

`applyTproxy(cfg)` esegue in ordine i comandi di applicazione; in caso di **qualsiasi** errore, esegue un
`revertTproxy(cfg)` completo in modalità best-effort e rilancia l'errore — pertanto il firewall viene
applicato completamente o ripristinato completamente, senza mai rimanere applicato solo in parte. `revertTproxy(cfg)` esegue i
comandi inversi in ordine inverso e ignora gli errori (è idempotente, quindi può essere chiamato
incondizionatamente, ad esempio durante la pulizia di AgentBridge `repairMitm()`).

`validateTproxyConfig(cfg)` viene eseguito prima di qualsiasi comando: le porte devono essere comprese tra `1–65535`,
`mark`/`routeTable`/`bypassMark` devono essere numeri interi positivi e `bypassMark` deve
essere diverso da `mark` (anti-loop).

### Comandi di applicazione (in ordine)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Il ripristino li elimina in ordine inverso: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> La procedura è basata su **OUTPUT** perché il caso d'uso MITM riguarda il traffico
> in uscita _locale_ (app sullo stesso host), che TPROXY nella sola catena `PREROUTING` non
> rileva — `PREROUTING` rileva soltanto il traffico inoltrato. La catena `OUTPUT` marca le nuove
> connessioni locali, la regola `ip rule` le reindirizza alla consegna locale (`lo`) e
> `PREROUTING` le assegna quindi al listener trasparente.

## §8 Configurazione

La richiesta di avvio (`POST /api/tools/agent-bridge/tproxy`) accetta i seguenti
campi, convalidati da `StartTproxyBodySchema` (`tproxy/route.ts`). Sono tutti facoltativi
e, se omessi, utilizzano i rispettivi valori predefiniti:

| Campo            | Tipo               | Valore predefinito | Note                                                                                                                             |
| ---------------- | ------------------ | ------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`              | Porta TCP di destinazione da intercettare in modo trasparente                                                                    |
| **mark**         | int (≥1)           | `0x2333`           | Marca del firewall impostata su `OUTPUT`, usata come criterio di corrispondenza da `ip rule` + `PREROUTING`                      |
| **onPort**       | int (1–65535)      | `8443`             | Porta a cui si associa il listener trasparente (**IP_TRANSPARENT**)                                                              |
| **routeTable**   | int (≥1)           | `233`              | ID della tabella di routing basato su policy che contiene la route `local 0.0.0.0/0`                                             |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`            | Marca di bypass del socket (**SO_MARK**) impostata dal proxy sulle proprie connessioni upstream; esclusa in `OUTPUT` (anti-loop) |
| **sudoPassword** | string             | —                  | Solo per desktop non root: autorizza l'installazione nell'archivio di attendibilità; ignorata quando si opera come root          |

Non esistono **variabili di ambiente** per TPROXY: l'intera configurazione viene fornita tramite il
corpo della richiesta POST o i valori predefiniti sopra indicati.

## §9 Abilitazione dal Traffic Inspector

1. Apri il **Traffic Inspector** (`/dashboard/tools/traffic-inspector`).
2. Nella barra degli strumenti delle modalità di acquisizione, individua il pulsante ⚠ **"TPROXY Decrypt"**
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Se è **disabilitato** con il suggerimento "La decrittazione TPROXY richiede Linux + root +
     l'addon nativo", l'addon nativo non è disponibile su questo host (sistema non Linux,
     toolchain assente o addon non compilato). Consulta [§2](#2-requirements) e [§3](#3-the-native-ip_transparent-addon).
3. Fai clic sul pulsante. Viene chiamato `POST /api/tools/agent-bridge/tproxy` tramite
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`), che:
   crea la CA dinamica, apre il listener trasparente, applica le regole del firewall
   e installa la CA nell'archivio di attendibilità del sistema operativo.
4. Durante l'esecuzione, il selettore diventa color ambra e mostra il conteggio in tempo reale
   delle intercettazioni (`· <interceptCount>`). Le richieste intercettate vengono visualizzate nell'elenco delle richieste con
   `source: "tproxy"`.
5. Fai nuovamente clic per arrestare la modalità: `DELETE /api/tools/agent-bridge/tproxy` tramite
   `stopTproxyCaptureMode()` chiude il listener, disinstalla la CA e ripristina
   le regole del firewall.

Lo stato della modalità di acquisizione (in esecuzione / disponibile / numero di intercettazioni / porta del listener) proviene
da `GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` in
`src/mitm/tproxy/captureManager.ts`). Può essere eseguita una sola sessione TPROXY alla volta:
il tentativo di avviarne una seconda viene rifiutato con il messaggio "La modalità di acquisizione TPROXY è già in esecuzione".

## §10 Risoluzione dei problemi

### Il selettore è disabilitato

L'addon nativo non può essere caricato. Verifica di utilizzare Linux, di aver compilato l'addon
(`npm run build:native:tproxy`) e che il processo possa caricare `transparent.node`.
`isTransparentSocketAvailable()` controlla l'abilitazione del selettore; `GET /api/tools/agent-bridge/tproxy`
restituisce `available: false` quando l'addon è assente.

### Non viene acquisito nulla

- Verifica che il processo intercettato si connetta effettivamente alla `dport` configurata
  (valore predefinito: `443`).
- Verifica che il processo consideri attendibile la CA dinamica. La CA viene installata come
  `omniroute-tproxy-ca.crt`; le app dotate di un proprio archivio di attendibilità (NSS di Firefox/Chrome)
  potrebbero richiedere che il certificato venga aggiunto anche lì.
- Esegui l'autodiagnosi **Diagnose** di AgentBridge (consulta
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) per verificare l'attendibilità del certificato e
  l'integrità del server.

### Regole del firewall obsolete dopo un arresto anomalo

`revertTproxy()` è l'esatto inverso dell'applicazione ed è idempotente. L'arresto della
modalità ripristina le regole; se OmniRoute è stato terminato durante una sessione, utilizza
l'azione **Repair** di AgentBridge (`POST /api/tools/agent-bridge/repair`) per annullare lo stato di sistema
orfano (spoofing DNS, CA root, proxy di sistema). Anche le regole TPROXY `mangle` e la route vengono
rimosse automaticamente al riavvio.

### Loop infinito / il proxy intercetta il proprio inoltro

Questo è il caso gestito dalla protezione anti-loop. Verifica che `bypassMark` sia diverso da `mark` (la convalida
lo impone) e che l'inoltro utilizzi `connectMarked` (come avviene in `realForward`).
Consulta [§5 Anti-loop](#anti-loop-so_mark).
