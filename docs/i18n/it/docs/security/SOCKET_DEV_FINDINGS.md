> **Nota sull'ambito:** `socket.yml` configura la scansione post-pubblicazione lato registry di Socket.dev dell'artefatto npm (percorsi ignorati per contenuti non distribuiti quali `tests/`, `docs/` e report di build). Non configura un gate di merge CI/PR: nessun workflow in `.github/workflows`, nessuno script di `package.json` e nessun target di `Makefile` invoca Socket.dev.

Questo documento è l'attestazione redatta dai manutentori relativa ai sei
rilevamenti `AI-detected potential malware` segnalati per `omniroute@3.8.5` e
alle mitigazioni applicate in `omniroute@3.8.6`. Esiste affinché:

1. Gli operatori delle pipeline di sicurezza dispongano di un unico riferimento da citare quando devono
   valutare i rilevamenti rispetto al codice sorgente effettivo.
2. I futuri scanner basati sull'IA possano rilevare la dichiarazione firmata dai manutentori secondo cui ciascun
   percorso segnalato è intenzionale, facoltativo e documentato.
3. Sia disponibile una registrazione scritta del _perché_ ciascun sito di chiamata è strutturato in questo modo —
   affinché un refactoring futuro non reintroduca accidentalmente un'impronta che
   è stata rimossa deliberatamente.

Se gestite uno scanner che segnala nuovamente uno dei siti di chiamata riportati di seguito dopo la
distribuzione delle mitigazioni della v3.8.6, aprite una issue con la traccia della scansione e
estenderemo qui l'attestazione.

## §1 — Installazione della CA radice MITM (`77484.js`)

**File sorgente**:

- `src/mitm/cert/install.ts` — funzioni pubbliche `installCert()` / `uninstallCert()`,
  `installCertWindows/Mac/Linux` specifiche per ciascuna piattaforma.
- `src/mitm/systemCommands.ts` — helper condivisi `execFile` / `spawn` / PowerShell
  utilizzati dai percorsi di installazione.

**Attivazione**: l'utente fa clic su "Abilita proxy MITM" nella dashboard locale all'indirizzo
`/dashboard/cli-tools/mitm`. La route è accessibile solo tramite loopback — vedere la regola inderogabile n. 17 in
`CLAUDE.md` e `src/server/authz/routeGuard.ts::isLocalOnlyPath()`. Un JWT divulgato
tramite un tunnel **non può** attivare questo percorso di codice.

**Operazioni privilegiate eseguite (per piattaforma)**:

| SO                     | Comando/i                                                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | `certutil -addstore Root <cert>` tramite UAC                                                                      |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | aggiornamento del DB NSS per profilo tramite `certutil -d sql:<profile>`                                          |

Si tratta degli stessi comandi utilizzati da `mitmproxy`, Charles Proxy, Fiddler e
Caddy. La loro presenza in OmniRoute è documentata in
`docs/security/STEALTH_GUIDE.md`.

**Mitigazione della v3.8.6**:

- `runElevatedPowerShell()` non utilizza più `-EncodedCommand <base64utf16le>`.
  Il payload con privilegi elevati viene scritto in un file temporaneo `.ps1` per ogni chiamata (modalità 0o600,
  all'interno di una directory privata `mkdtempSync`) e richiamato tramite `-File`. Il
  file viene scollegato in `finally`. Ciò elimina la tipica firma digitale
  dell'elevazione tramite PowerShell con base64 segnalata dal classificatore IA di
  Socket.dev.
- `installCertWindows` contiene un blocco inline `SECURITY-AUDITOR-NOTE:`
  che rimanda a questo documento.

**Perché lo manteniamo**: il proxy MITM è una funzionalità documentata utilizzata da
`docs/security/STEALTH_GUIDE.md` e `docs/frameworks/MITM-PROXY.md`. La sua rimozione
comprometterebbe l'insieme di funzionalità agent-bridge.

## §2 — Importazione delle credenziali Zed (`app/api/providers/zed/import/route.js`)

**File sorgente**:

- `src/app/api/providers/zed/discover/route.ts` _(nuovo nella v3.8.6)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(nuovo nella v3.8.6)_

**Attivazione**: l'utente fa clic su "Importa da Zed" nella pagina Provider
della dashboard locale. L'endpoint è protetto da `requireManagementAuth`. Lo
stesso editor Zed scrive le chiavi API dei provider nel portachiavi del sistema
operativo usando nomi di servizio documentati — vedere
https://zed.dev/docs/ai/llm-providers.

**Comportamento della v3.8.5 (quello segnalato da Socket.dev)**:

`POST /import` individuava le credenziali e le salvava automaticamente
nell'archivio SQLite locale in un unico round-trip. Nessuna conferma per singolo
account, nessuna impronta, solo "trovati N token, tutti importati".

**Mitigazione della v3.8.6 — conferma in 2 passaggi**:

1. **`POST /api/providers/zed/discover`** restituisce
   `{ candidates: [{ provider, service, account, fingerprint }] }`. Il token
   grezzo **non viene mai** trasmesso. L'impronta è
   `sha256(service|account|token).slice(0,16)`.
2. La dashboard mostra l'elenco dei candidati, l'operatore seleziona quelli da
   importare e invia `{ confirmedAccounts: [{ service, account, fingerprint }] }`
   a **`POST /api/providers/zed/import`**.
3. L'endpoint di importazione **rilegge il portachiavi sul server** e filtra per
   `(service, account, fingerprint)`. Una risposta di individuazione alterata o
   riprodotta non può indurre l'endpoint di importazione a salvare un token non
   correlato — se il token attivo è cambiato dopo l'individuazione, l'impronta
   non corrisponde più e la credenziale viene ignorata.

Un flag di ambiente `OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` mantiene il
comportamento della v3.8.5 per gli operatori che non hanno ancora aggiornato la
propria automazione. Verrà rimosso nella v3.9.

**Perché lo manteniamo**: l'importazione da Zed è il percorso di onboarding più
semplice per gli utenti che utilizzano già Zed e desiderano replicare le chiavi
dei propri provider in OmniRoute senza doverle incollare nuovamente.

## §3 — `execFile` / `spawn` / PowerShell con privilegi elevati (`21843.js`)

**File sorgente**: `src/mitm/systemCommands.ts`.

**Motivo della segnalazione**: il chunk riesporta `execFileWithPassword`,
`runElevatedPowerShell` e l'helper condiviso `quotePowerShell`. Il classificatore
IA di Socket.dev li identifica come un generico "toolkit per l'esecuzione
sull'host e l'elevazione dei privilegi". All'interno di OmniRoute vengono usati
esclusivamente dal percorso di installazione del certificato MITM (§1) e da
`execFileWithPassword` per l'esecuzione di comandi `sudo`.

**Mitigazione della v3.8.6**:

- Refactoring di `runElevatedPowerShell` (vedere §1).
- Un blocco inline `SECURITY-AUDITOR-NOTE:` sia in
  `runElevatedPowerShell` sia in `execFileWithPassword` documenta i chiamanti
  inclusi nell'elenco consentito e l'elenco fisso degli eseguibili.
- La chiamata `spawn()` di `execFileWithPassword` contiene un marcatore
  `nosemgrep` con l'elenco degli eseguibili che l'helper può ricevere — non
  esiste **alcun percorso dall'input dell'utente a `finalCommand`/`finalArgs`**.

## §4 / §6 — Supervisore del servizio 9router (`api/services/9router/{start,restart}/route.js`)

**File sorgente**:

- `src/app/api/services/9router/_lib.ts` — factory del supervisore.
- `src/app/api/services/9router/{start,stop,restart,status,install,update,auto-start}/route.ts`.
- `src/lib/services/ServiceSupervisor.ts` — gestione generica di spawn / polling dello stato / buffer dei log.

**Attivazione**: l'utente fa clic su "Installa" / "Avvia" nella pagina dei
servizi incorporati della dashboard locale.

**Protezioni già presenti**:

- Tutte le route `/api/services/*` sono LOCAL_ONLY secondo
  `src/server/authz/routeGuard.ts` (regola rigida n. 17). L'applicazione della
  restrizione al loopback avviene prima di qualsiasi controllo di
  autenticazione — un JWT trapelato non può raggiungerle.
- La riga del database relativa a 9router viene inizializzata con
  `status='not_installed', auto_start=0` (vedere
  `src/lib/db/migrations/071_services.sql:19`). Il servizio **non** viene
  avviato al primo lancio.
- `spawn()` viene chiamato con il percorso del binario restituito da
  `resolveSpawnArgs(apiKey, PORT)` in `src/lib/services/installers/ninerouter.ts`,
  che usa un elenco fisso di binari supportati.
- Stdout/stderr viene memorizzato in un buffer in memoria (limite di 5 MB,
  vedere `_lib.ts`) — non viene effettuata alcuna scrittura su disco, a meno
  che l'utente non abiliti la registrazione dalla dashboard.

**Mitigazione della v3.8.6**: nessuna modifica funzionale. Il profilo di build
minimale (`OMNIROUTE_BUILD_PROFILE=minimal`) sostituisce
`src/lib/services/installers/ninerouter.ts` con uno stub per gli utenti che
desiderano rimuovere fisicamente dal bundle i percorsi con privilegi elevati.

**Perché lo manteniamo**: 9router è un servizio complementare opzionale,
installabile localmente (simile a un plugin in stile WordPress) — rigorosamente
attivabile solo su esplicita richiesta.

## §5 — Scrittura delle credenziali tramite OmniRoute Cloud Sync (`api/keys/[id]/route.js`)

**File sorgente**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`.
- `src/app/api/keys/[id]/route.ts` — invoca `syncKeysToCloudIfEnabled()`.

**Condizione di attivazione**: `isCloudEnabled()` restituisce `true` (impostato dalla dashboard) **e**
`CLOUD_URL` è configurato. Quando entrambi sono disattivati, non viene effettuata alcuna chiamata di rete in uscita
all'endpoint Cloud.

**Comportamento della v3.8.5 (il bug rilevato correttamente da Socket.dev)**:

`updateLocalTokens()` sovrascriveva `accessToken`, `refreshToken` e
`providerSpecificData` con i valori della risposta Cloud quando
`cloudUpdatedAt > localUpdatedAt`. Nessun HMAC, nessuna firma, nessun checksum. Un
`CLOUD_URL` configurato in modo errato o ostile (oppure un attacco MITM sul canale) poteva sostituire
silenziosamente i token OAuth del provider.

**Mitigazione nella v3.8.6**:

1. **Verifica HMAC**: `verifyCloudSignature(rawBody, sigHeader)` controlla
   l'header `X-Cloud-Sig` (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`) prima di analizzare il JSON. Se il segreto è impostato, la firma è
   obbligatoria. In caso contrario (modalità legacy), viene registrato un avviso e la risposta viene
   accettata — il segreto sarà obbligatorio nella v3.9.
2. **Attivazione esplicita dei campi segreti**: `accessToken` / `refreshToken` /
   `providerSpecificData` vengono sovrascritti **solo** quando
   `OMNIROUTE_CLOUD_SYNC_SECRETS=true`. La modalità predefinita sincronizza soltanto
   i metadati non relativi alle credenziali (`expiresAt`, `status`, `lastError*`,
   `rateLimitedUntil`, `updatedAt`). Si tratta di una **modifica incompatibile** per gli utenti
   che facevano affidamento sulla sincronizzazione remota dei token — devono abilitarla esplicitamente.

**Perché la manteniamo**: Cloud Sync è l'unico modo per consentire a un tenant OmniRoute Cloud
di centralizzare le credenziali del team. La correzione rende esplicito il modello di minaccia:
"il server firma, il client verifica, l'operatore acconsente."

## Profilo di build: `minimal`

Per gli utenti che necessitano di un artefatto compatibile con Socket, eseguire la build con:

```bash
OMNIROUTE_BUILD_PROFILE=minimal npm run build
```

Il `NormalModuleReplacementPlugin` di webpack associa quattro moduli a stub:

| Modulo                                      | Stub                                             |
| ------------------------------------------- | ------------------------------------------------ |
| `src/mitm/cert/install.ts`                  | `src/mitm/cert/install.stub.ts`                  |
| `src/lib/zed-oauth/keychain-reader.ts`      | `src/lib/zed-oauth/keychain-reader.stub.ts`      |
| `src/lib/cloudSync.ts`                      | `src/lib/cloudSync.stub.ts`                      |
| `src/lib/services/installers/ninerouter.ts` | `src/lib/services/installers/ninerouter.stub.ts` |

Ogni stub esporta la stessa interfaccia, ma ogni funzione genera un
`featureDisabledError(name)` in fase di esecuzione. Le route che dipendono dal modulo
disabilitato restituiscono HTTP 503 con un messaggio chiaro, anziché attivare il
percorso di codice sensibile.

Il bundle risultante è destinato alla pubblicazione come `omniroute-secure`. Consultare
`docs/ops/PUBLISHING_SECURE.md` per la procedura di pubblicazione.
