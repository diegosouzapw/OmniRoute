OmniRoute si integra con provider i cui sistemi perimetrali rilevano attivamente le impronte digitali dei client non ufficiali (TLS JA3/JA4, ordine degli header, struttura del corpo JSON, token di integrità). Questa pagina documenta le superfici stealth esposte da OmniRoute e dove sono implementate.

## Avvertenza legale ed etica

Le funzionalità stealth esistono affinché OmniRoute possa fungere da livello di compatibilità tra gli account ufficiali di proprietà degli utenti (Claude Code CLI, Codex, Antigravity, Cursor, ecc.) e l'API unificata di OmniRoute. **Non** sono destinate ad aggirare il rilevamento delle frodi, condividere credenziali o violare i Termini di servizio dei provider. I manutentori si aspettano che gli operatori rispettino i ToS upstream accettati al momento della creazione degli account.

## Livello di fingerprinting TLS

### `open-sse/utils/tlsClient.ts` — wreq-js (Chrome 124)

Le sessioni persistenti `wreq-js` vengono create in modo lazy per ciascun ambito dell'account e proxy risolto. I pool di `TlsClient` a livello di processo contengono al massimo 128 sessioni che emulano **Chrome 124 su macOS** per gli upstream protetti da Cloudflare. `TlsClient.fetch()` interrompe l'operazione in sicurezza quando il runtime nativo non è disponibile; un chiamante può selezionare esplicitamente un fallback esterno a questo wrapper.

- Profilo della sessione: `browser: "chrome_124", os: "macos"`
- Risoluzione del proxy (priorità): `HTTPS_PROXY` → `HTTP_PROXY` → `ALL_PROXY` (anche in minuscolo)
- Timeout: `TLS_CLIENT_TIMEOUT_MS` (eredita da `FETCH_TIMEOUT_MS`, valore predefinito 600000)
- La Response di `wreq-js` è compatibile con fetch (`headers`, `text()`, `json()`, `clone()`, `body`).
- Watchdog del primo byte (`open-sse/utils/tlsFirstByteWatchdog.ts`, #12656): `TlsClient.fetch()` viene risolto non appena arrivano gli header upstream, pertanto `TLS_CLIENT_TIMEOUT_MS` da solo non può imporre un limite a un corpo che non restituisce mai un primo byte. `guardTlsFirstByte()` mette in competizione la prima chiamata `read()` del corpo con `TLS_FIRST_BYTE_WATCHDOG_MS` (valore predefinito `10000`, `0` lo disabilita); un corpo integro non viene interessato, mentre in caso di stallo il reader wreq viene annullato, consentendo alla logica di fallback TLS esistente di `proxyFetch` di passare al dispatcher diretto/proxy (una richiesta che non può essere riprodotta in sicurezza, ad esempio una POST con un corpo, genera comunque un errore anziché essere ripetuta silenziosamente).

### Trasporto dei provider basato su cookie web — wreq-js 3.2.0

`open-sse/services/tlsClientBase.ts` è l'adattatore condiviso per i cinque trasporti specializzati basati su cookie web riportati di seguito. Ogni sottile wrapper specifico per provider seleziona un profilo browser/OS. L'adattatore utilizza il singolo loader del runtime wreq e il pool di trasporto in `open-sse/utils/tlsClient.ts`, indicizzato per profilo + OS + proxy risolto, mentre ogni richiesta utilizza `cookieMode: "ephemeral"`. Gli account e le richieste condividono quindi le connessioni a livello di trasporto, ma mai una sessione wreq o un cookie jar.

| Provider   | Profilo       | OS emulato | Criterio EOF dello stream                |
| ---------- | ------------- | ---------- | ---------------------------------------- |
| Claude     | `chrome_146`  | Linux      | include `[DONE]`                         |
| Perplexity | `firefox_148` | macOS      | include `event: end_of_stream`           |
| Grok       | `chrome_146`  | Linux      | esclude `[DONE]`                         |
| Notion     | `chrome_146`  | Windows    | include `[DONE]`                         |
| LMArena    | `chrome_146`  | Windows    | nessun sentinella; chiude all'EOF nativo |

- Lo streaming utilizza direttamente il `ReadableStream` della risposta nativa; non viene creato alcun file temporaneo o sidecar.
- Vengono ispezionati fino a 256 byte iniziali prima di esporre uno stream. I provider SSE memorizzano nel buffer gli errori non SSE; Grok/LMArena mappano le challenge di Cloudflare a `403` e le pagine interstiziali HTML a `502`.
- Il timeout della richiesta nativa resta racchiuso in una scadenza rigida JS assoluta. Un blocco invalida e chiude soltanto il trasporto interessato per profilo/OS/proxy, prima che la richiesta successiva lo ricrei.
- La priorità di risoluzione del proxy è `proxyUrl` per chiamata → contesto dell'account/dashboard con ambito di richiesta → `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` (incluse le varianti in minuscolo). Gli errori di risoluzione interrompono l'operazione in sicurezza anziché causare la fuoriuscita di una connessione diretta. LMArena esegue deliberatamente la risoluzione rispetto a `arena.ai`.
- `byteResponse` restituisce un URL `data:` con il tipo di contenuto appropriato, senza corruzione UTF-8.
- Gli errori sono `TlsClientUnavailableError` (pacchetto/addon non disponibile), `TlsClientHangError` (scadenza superata) e `WreqTransportCapacityError` (il codice di errore condiviso relativo alla capacità delle sessioni) quando tutti i 128 slot limitati per profilo/OS/proxy sono attivi o in fase di chiusura.

La sessione generica `TlsClient` descritta sopra rimane specializzata per lo stato persistente dei cookie supportato dal browser. Entrambi i percorsi riutilizzano un unico loader memorizzato nella cache per il modulo wreq e un unico hook del ciclo di vita del processo; i rispettivi pool restano separati perché la durata dei cookie è intenzionalmente diversa.

I profili sono supportati dal pacchetto fissato, ma l'effettiva accettazione da parte del WAF può variare indipendentemente dai test locali del contratto. Convalidare le modifiche alle impronte digitali rispetto a un account attivo esplicitamente autorizzato prima di dichiarare la parità con un browser upstream.

## Pacchetto stealth di Claude Code

Quando `cliCompatMode` è attivo, OmniRoute rimodella le richieste Claude in uscita affinché siano indistinguibili dal traffico di `claude-cli`. Tre moduli collaborano:

### `claudeCodeFingerprint.ts`

Calcola l'impronta `cc_version` di 3 caratteri incorporata nell'header di fatturazione:

```
SHA256(SALT + msg[4] + msg[7] + msg[20] + version)[:3]
```

- `FINGERPRINT_SALT = "59cf53e54c78"` (codificato direttamente; corrisponde al client ufficiale)
- Input: caratteri agli indici 4, 7 e 20 del testo del primo messaggio utente + stringa della versione
- Output: prefisso esadecimale di 3 caratteri

### `claudeCodeCCH.ts` (hash del contenuto client)

Controllo di integrità lato server che la CLI ufficiale di Claude Code calcola tramite Bun/Zig. OmniRoute lo reimplementa con `xxhash-wasm`:

1. Serializza il corpo con il segnaposto `cch=00000;`
2. `xxhash64(bytes, seed) & 0xFFFFF`
3. Valore esadecimale minuscolo di 5 caratteri con riempimento di zeri
4. Sostituisce `cch=00000;` con il token calcolato

Costanti:

- Seed: `0x6e52736ac806831e`
- Pattern: `/\bcch=([0-9a-f]{5});/`

### `claudeCodeObfuscation.ts`

Inserisce un **connettore a larghezza zero** Unicode (`U+200D`) dopo il primo carattere dei nomi client "sensibili", in modo che i filtri upstream non possano individuarli tramite grep. Elenco di parole predefinito:

```
opencode, open-code, cline, roo-cline, roo_cline, cursor, windsurf,
aider, continue.dev, copilot, avante, codecompanion
```

Applicato a: blocchi `system`, tutti i `messages[].content` e `tools[].description` / `tools[].function.description`. Personalizzabile dall'operatore tramite `setSensitiveWords()`.

### `claudeCodeCompatible.ts` — provider `anthropic-compatible-cc-*`

Per relay Anthropic di terze parti che accettano esclusivamente traffico "Claude Code autentico":

- `CLAUDE_CODE_COMPATIBLE_USER_AGENT = "claude-cli/2.1.258 (external, sdk-cli)"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_PACKAGE_VERSION = "0.112.1"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_RUNTIME_VERSION = "v26.3.0"`
- `anthropic-beta = "claude-code-20250219,interleaved-thinking-2025-05-14,effort-2025-11-24"` per impostazione predefinita
- L'opzione "Abilita la beta redact-thinking" per connessione aggiunge `redact-thinking-2026-02-12` quando uno specifico upstream CC Compatible richiede flussi di ragionamento oscurati
- L'opzione "Abilita la visualizzazione del ragionamento riepilogato" per connessione memorizza `providerSpecificData.requestDefaults.summarizeThinking` e aggiunge `display: "summarized"` alle richieste di ragionamento CC Compatible che non hanno già impostato una modalità di visualizzazione
- `CONTEXT_1M_BETA_HEADER = "context-1m-2025-08-07"` (famiglia Opus/Sonnet 4.x)
- Percorso predefinito: `/v1/messages?beta=true`

Moduli correlati nello stesso pacchetto:

- `claudeCodeConstraints.ts` — regole per temperatura + controllo della cache
- `claudeCodeToolRemapper.ts` — rimappatura dei nomi degli strumenti
- `claudeCodeExtraRemap.ts` — normalizzazione aggiuntiva del payload

## Stealth di Antigravity

Le richieste Antigravity preservano il testo del chiamante byte per byte. OmniRoute non inserisce caratteri a larghezza zero nei prompt né rinomina/inietta strumenti per imitare un client IDE.

### `antigravityHeaderScrub.ts`

Rimuove gli indicatori dell'SDK Stainless (`x-stainless-lang`, `x-stainless-package-version`, `x-stainless-os`, `x-stainless-arch`, `x-stainless-runtime`, `x-stainless-runtime-version`, `x-stainless-timeout`, `x-stainless-retry-count`, `x-stainless-helper-method`) prima dell'inoltro.

### ⚠️ Rischio: `ANTIGRAVITY_CREDITS=always` (punto critico per il ban dell'account)

`ANTIGRAVITY_CREDITS=always` (utilizzato da `open-sse/executors/antigravity.ts`) instrada **ogni** richiesta tramite gli addebiti eccedenti dei crediti AI di Antigravity (crediti Google a pagamento), anziché lasciare che la quota del livello gratuito di Google faccia da limite. Questa funzionalità è documentata, ma rappresenta **la segnalazione di violazione dei ToS più comune che osserviamo**: diversi account Google Ultra sono stati sospesi con `403 / "service disabled for ToS violation" / insufficient_quota` dopo essere rimasti in esecuzione per alcune ore con `=always`.

L'applicazione delle regole upstream avviene **da parte di Google** e OmniRoute non può impedirla. Il nome della variabile di ambiente e la documentazione esistente fanno sembrare che sia un'opzione sicura da attivare, ma non lo è.

**Perché ciò attiva il rilevamento degli abusi in modo più aggressivo rispetto all'utilizzo esclusivo del livello gratuito:**

- Una spesa automatizzata e continuativa su un singolo account Google viene segnalata diversamente rispetto al raggiungimento della quota del livello gratuito con conseguente arresto.
- Gli addebiti eccedenti dei crediti non hanno un limite massimo di frequenza, quindi un client configurato erroneamente può consumare diverse centinaia di USD in pochi minuti e apparire come traffico di rivendita di chiavi API o di bot.
- Più utenti OmniRoute che utilizzano in parallelo i crediti eccedenti dallo stesso IP esterno amplificano il segnale.

**Configurazione consigliata:**

1. Mantieni il valore predefinito `ANTIGRAVITY_CREDITS=off`, a meno che l'operatore non accetti esplicitamente il rischio relativo ai crediti a pagamento e ai provvedimenti sull'account. `retry` invia prima la richiesta normale e inietta i crediti al massimo una volta dopo un errore 429 di quota idoneo; `always` inietta i crediti fin dalla prima richiesta.
2. **Distribuisci il carico tra i provider tramite Auto-Combo** (`model: "auto"` o `kr/glm/etc`-combo), anziché saturare un singolo account Antigravity.
3. **Imposta limiti RPM per connessione** nella pagina di modifica del provider Antigravity (Dashboard → Provider → Antigravity → connessione → limite di frequenza). 30–60 RPM rappresentano un limite massimo ragionevole per un utilizzo continuativo.
4. **Utilizza una rete upstream stabile e controllata dall'operatore** ed evita di condividere un singolo account tra utenti o carichi di lavoro non correlati.
5. **In caso di ban**: presenta ricorso tramite `support.google.com` → "Ripristina l'accesso a Workspace/account", includendo esattamente il corpo della risposta `quota_exceeded` / `service disabled` inviato da Google. Il ripristino non è garantito.

La documentazione di riferimento dell'ambiente descrive le implicazioni per l'account e la spesa di ciascuna modalità dei crediti.

Punti di intervento:

- `open-sse/executors/antigravity.ts` — legge `process.env.ANTIGRAVITY_CREDITS`
- `src/lib/oauth/providers/antigravity.ts` — gestione delle credenziali
- Segnalazione originale dell'incidente: discussione [#1183](https://github.com/diegosouzapw/OmniRoute/discussions/1183)

## Registro delle fingerprint CLI — `open-sse/config/cliFingerprints.ts`

Tabella per provider che fissa l'ordinamento **esatto** degli header e dei campi del corpo JSON acquisito dalle tracce mitmproxy delle CLI ufficiali. Attualmente registrati: `codex`, `claude`, oltre ai profili derivati in fase di esecuzione in `providerHeaderProfiles.ts` per `antigravity` e `github`.

```ts
interface CliFingerprint {
  headerOrder: string[]; // distingue tra maiuscole e minuscole
  bodyFieldOrder: string[]; // chiavi JSON di primo livello
  userAgent?: string | (() => string);
  extraHeaders?: Record<string, string>;
}
```

Attivabile o disattivabile per ciascun provider tramite variabili d'ambiente (vedere sotto). Quando è disabilitato, gli header e le chiavi del corpo vengono visualizzati nell'ordine fornito da Node/JSON, rendendoli facilmente identificabili tramite fingerprint.

## Proxy MITM (Antigravity, Linux/macOS/Windows)

Per le CLI i cui binari non possono essere reindirizzati tramite `OPENAI_BASE_URL`, OmniRoute esegue un proxy locale con terminazione TLS. Gli endpoint si trovano in `src/app/api/cli-tools/antigravity-mitm/`.

| Metodo | Endpoint                                | Scopo                                              |
| ------ | --------------------------------------- | -------------------------------------------------- |
| GET    | `/api/cli-tools/antigravity-mitm`       | Stato — running, pid, dnsConfigured, certExists    |
| POST   | `/api/cli-tools/antigravity-mitm`       | Avvia il MITM (richiede `apiKey` + `sudoPassword`) |
| DELETE | `/api/cli-tools/antigravity-mitm`       | Arresta il MITM                                    |
| GET    | `/api/cli-tools/antigravity-mitm/alias` | Elenca gli alias dei modelli                       |
| PUT    | `/api/cli-tools/antigravity-mitm/alias` | Salva gli alias dei modelli per uno strumento      |

Host intercettato di destinazione: **`daily-cloudcode-pa.googleapis.com`** (upstream di Antigravity).

### Sequenza di avvio (`src/mitm/manager.ts::startMitm`)

1. Genera un certificato autofirmato tramite `selfsigned` (RSA-2048, SHA-256, 1 anno) — `cert/generate.ts`
2. Installa il certificato nell'archivio di attendibilità del sistema — `cert/install.ts`
3. Aggiunge la voce hosts `127.0.0.1 daily-cloudcode-pa.googleapis.com` — `dns/dnsConfig.ts`
4. Avvia `src/mitm/server.cjs` con `ROUTER_API_KEY` + `MITM_LOCAL_PORT` (valore predefinito `443`)
5. Salva in modo persistente il PID in `<DATA_DIR>/mitm/.mitm.pid`

### Rilevamento dinamico dell'archivio di attendibilità su Linux — `cert/install.ts`

`getLinuxCertConfig()` esamina un elenco ordinato per priorità e seleziona la prima directory esistente:

| Famiglia di distribuzioni | Directory                                   | Comando di aggiornamento |
| ------------------------- | ------------------------------------------- | ------------------------ |
| Debian / Ubuntu           | `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| Arch / CachyOS / Manjaro  | `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| Fedora / RHEL / CentOS    | `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| openSUSE                  | `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Nome del file del certificato: `omniroute-mitm.crt`. Verifica della corrispondenza della fingerprint tramite `getCertFingerprint()` (SHA-1 del DER).

Inoltre, `updateNssDatabases()` esegue l'installazione nei database NSS specifici dell'utente quando `certutil` è disponibile: `~/.pki/nssdb`, `~/snap/chromium/.../nssdb`, tutti i profili Firefox (inclusi quelli snap), con il nome descrittivo **`OmniRoute MITM Root CA`**.

### macOS / Windows

- **macOS:** `security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain`
- **Windows:** PowerShell con privilegi elevati → `certutil -addstore Root`

### Autenticazione

Tutti gli endpoint MITM richiedono l'autenticazione di gestione (`requireCliToolsAuth`). La password sudo viene memorizzata nella cache nell'ambito del modulo (mai in `globalThis`) e cancellata durante `stopMitm()`.

| `CLI_COMPAT_KILOCODE=1`    | KiloCode                        |
| `CLI_COMPAT_CLINE=1`       | Cline                           |
| `CLI_COMPAT_ALL=1`         | Abilita tutte le opzioni sopra  |

L'IP del provider viene **sempre preservato**: l'opzione modifica soltanto la struttura della richiesta trasmessa e non cambia l'IP di uscita.

---

## Sanitizzazione degli header in ingresso

OmniRoute rimuove gli header del client in ingresso prima dell'inoltro, così una richiesta proveniente da Cursor non espone `User-Agent: Cursor/X.Y.Z` a un upstream Claude. Consultare `src/shared/constants/upstreamHeaders.ts` per la lista di esclusione, mantenuta sincronizzata con gli schemi Zod e i test unitari.

---

## Aggiornamento dei fingerprint quando un provider li modifica

1. Acquisire il traffico della CLI ufficiale con `mitmproxy` (intercettazione TLS + dump)
2. Estrarre JA3/JA4 e l'ordine letterale degli header
3. Aggiornare la voce `CLI_FINGERPRINTS[...]` pertinente
4. Aggiornare il valore predefinito `*_USER_AGENT` corrispondente in `.env.example`
5. Se è cambiato anche l'handshake TLS, aggiornare il wrapper del provider pertinente o l'opzione `browser:` di wreq-js
6. Eseguire i test TLS specifici del provider e un test canary manuale sul provider attivo
7. Distribuire in una release patch; documentare in `CHANGELOG.md`
