> Opzioni di runtime che modificano il comportamento di OmniRoute **senza una nuova distribuzione**.
> Ogni flag elencato qui è definito in
> [`src/shared/constants/featureFlagDefinitions.ts`](../../src/shared/constants/featureFlagDefinitions.ts)
> — l'unica fonte autorevole. Sia la dashboard sia l'API REST leggono da
> quel file, quindi la tabella seguente viene generata in modo da corrispondervi 1:1.

---

## Cosa sono i feature flag

Un feature flag è un'opzione denominata (booleana o enum) il cui valore può essere modificato in
fase di esecuzione e salvato nel database, senza richiedere la ridistribuzione del processo. Ogni
flag è descritto da una `FeatureFlagDefinition` con `key`, `label`,
`description`, `category`, `defaultValue`, `type` e un'indicazione `requiresRestart`.

### Ordine di risoluzione

Il **valore effettivo** di un flag viene determinato da
[`resolveFeatureFlag()`](../../src/shared/utils/featureFlags.ts) secondo questo
ordine di precedenza (vince quello più alto):

1. **Override del DB** — un valore archiviato nella tabella `key_value` nello
   spazio dei nomi `feature_flags` (impostato tramite la dashboard o l'API REST).
2. **Variabile di ambiente** — `process.env[<KEY>]`, se impostata e non vuota.
3. **Valore predefinito della definizione** — il `defaultValue` di `featureFlagDefinitions.ts`.

Un flag booleano è considerato **abilitato** quando il suo valore effettivo è `"true"`,
`"1"` o `"yes"` (vedere `isFeatureFlagEnabled()`).

> [!NOTE]
> La maggior parte dei flag dispone anche di una variabile di ambiente corrispondente con lo **stesso nome**,
> documentata in [`ENVIRONMENT.md`](./ENVIRONMENT.md). L'override del DB del flag
> ha la precedenza su tale variabile di ambiente. Un flag con
> `requiresRestart: true` viene salvato immediatamente, ma riletto solo all'avvio
> del processo: modificandolo, nella dashboard viene visualizzato un banner **"Riavvia il server"**.

## Gestione dei Flag

### Dashboard

Naviga su **Dashboard → Impostazioni → Feature Flags**
(`/dashboard/settings/feature-flags`). La griglia
(`src/app/(dashboard)/dashboard/settings/components/FeatureFlagsGrid.tsx`)
supporta:

- **Ricerca** per chiave o descrizione, e **filtro** per categoria (più una vista sintetica
  **Richiede Riavvio**).
- Un **interruttore** per i flag booleani e un **menu a discesa** per i flag enum
  (`src/app/(dashboard)/dashboard/settings/components/FeatureFlagCard.tsx`).
- Un **badge di origine** per flag — `DB`, `ENV`, o `DEF` — che mostra da dove proviene il
  valore effettivo.
- Un pulsante **Reset** (mostrato solo per i flag con origine `DB`) per annullare l'override,
  e un pulsante **Resetta Tutti gli Override** in fondo.
- Un banner **Riavvia Server** quando un flag `requiresRestart` viene modificato.

### API REST

Tutte le operazioni passano attraverso un'unica rotta:
[`src/app/api/settings/feature-flags/route.ts`](../../src/app/api/settings/feature-flags/route.ts).
Ogni metodo richiede una sessione dashboard autenticata (altrimenti `401`).

#### `GET /api/settings/feature-flags`

Restituisce ogni flag con il suo valore effettivo, la sua origine e un riepilogo.

```jsonc
{
  "flags": [
    {
      "key": "REQUIRE_API_KEY",
      "label": "Require API Key",
      "description": "Require an API key for all incoming requests",
      "category": "security",
      "type": "boolean",
      "enumValues": null,
      "defaultValue": "false",
      "effectiveValue": "false",
      "source": "default", // "db" | "env" | "default"
      "requiresRestart": false,
      "warningLevel": "caution",
    },
    // ... all 77 flags
  ],
  "summary": {
    "total": 56,
    "active": 0,
    "inactive": 0,
    "overriddenByDb": 0,
    "overriddenByEnv": 0,
  },
}
```

#### `PUT /api/settings/feature-flags`

Imposta o rimuove un singolo override. Corpo: `{ key: string; value?: string }`.
Omettere `value` rimuove l'override (ripristinando env / default).

```bash
# Imposta un override DB
curl -X PUT http://localhost:20128/api/settings/feature-flags \
  -H "Content-Type: application/json" \
  -d '{"key":"REQUIRE_API_KEY","value":"true"}'

# Rimuove l'override (senza "value")
curl -X PUT http://localhost:20128/api/settings/feature-flags \
  -H "Content-Type: application/json" \
  -d '{"key":"REQUIRE_API_KEY"}'
```

La risposta restituisce il nuovo `effectiveValue`/`source`, il `previousValue`/
`previousSource` e `requiresRestart`. Chiavi sconosciute e valori enum fuori intervallo
vengono rifiutati con `400`.

#### `DELETE /api/settings/feature-flags`

Cancella **tutti** gli override DB in una volta, ripristinando ogni flag al suo valore env / predefinito.
Restituisce `{ cleared: <count>, message: "..." }`.

> [!NOTE]
> I flag con `requiresRestart: true` hanno effetto solo dopo un ricaricamento del processo.
> Il flusso di riavvio della dashboard chiama `POST /api/restart` e poi interroga
> `GET /api/health/ping` finché il server non è di nuovo attivo.

## Fallback di emergenza per il budget

`OMNIROUTE_EMERGENCY_FALLBACK` (categoria `runtime`, valore predefinito `true`) controlla il
percorso gratuito di fallback di emergenza in
[`open-sse/services/emergencyFallback.ts`](../../open-sse/services/emergencyFallback.ts).
Quando è abilitato, le richieste che esauriscono il proprio budget vengono instradate verso un
provider/modello di fallback gratuito anziché non riuscire del tutto. Impostalo su `false` (o `0`) — tramite
l'interruttore della dashboard, un override nel DB o la variabile di ambiente
`OMNIROUTE_EMERGENCY_FALLBACK` — per disabilitare questo comportamento e lasciare che le richieste
con budget esaurito non vadano a buon fine. (Disponibile come interruttore nella dashboard nelle PR #3741 / #3752.)
