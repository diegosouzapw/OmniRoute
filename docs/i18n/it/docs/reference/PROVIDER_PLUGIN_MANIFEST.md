`open-sse/config/providerPluginManifest.ts` definisce il contratto JSON-safe dei
plugin dei provider. `open-sse/config/providerPluginManifestRegistry.ts` associa tale
contratto al registro corrente dei provider per sidecar come Bifrost,
CLIProxyAPI o un futuro router Go/Rust. Il registro TypeScript rimane la
fonte di verità, ma i sidecar possono utilizzare il manifest senza importare
codice degli executor, impostazioni predefinite OAuth, header o stato delle variabili d'ambiente
del processo.

Lo stesso manifest è disponibile tramite HTTP all'indirizzo
`GET /api/v1/provider-plugin-manifest` per i sidecar eseguiti in processi separati.

OmniRoute comunica tale URL a Bifrost e CLIProxyAPI tramite l'header di richiesta
`X-OmniRoute-Provider-Manifest-Url`. Impostare
`OMNIROUTE_PROVIDER_MANIFEST_URL` quando il sidecar necessita di un URL pubblico o della rete
del container anziché dell'origine della richiesta locale.

## Aggiornamento del Manifest

L'endpoint HTTP restituisce `Cache-Control: public, max-age=60` e un
`ETag` forte. Un sidecar dovrebbe conservare l'ultimo manifest convalidato e inviare il relativo ETag
in `If-None-Match` durante l'aggiornamento. Una risposta `304 Not Modified` non contiene alcun corpo;
il sidecar mantiene il manifest memorizzato nella cache. Se non esiste alcun manifest convalidato nella cache,
il sidecar deve inviare una richiesta non condizionale invece di accettare una risposta `304`.

## Obiettivo

Orientare i metadati dei provider verso un contratto per plugin, affinché il percorso critico delle richieste possa
essere infine gestito da un sidecar a latenza inferiore, mentre OmniRoute mantiene la
route TypeScript come punto di applicazione delle policy e fallback. Il manifest è additivo: non
modifica autonomamente l'instradamento delle richieste.

## Contratto

Il manifest contiene:

- ID e alias del provider
- formato upstream e nome dell'executor
- tipo di autenticazione, header di autenticazione e prefisso di autenticazione opzionale
- metadati statici dell'endpoint
- idoneità per il sidecar e motivazioni esplicite quando un provider deve rimanere su TS
- metadati dei modelli JSON-safe, come lunghezza del contesto, indicatori di visione/ragionamento e
  parametri non supportati
- tag di funzionalità, tra cui `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` e `usage-supported`

Il manifest esclude intenzionalmente:

- segreti client OAuth e valori segreti predefiniti
- risoluzione dell'ambiente di runtime
- header delle richieste e helper per le credenziali pubbliche
- generatori dinamici di URL
- funzioni degli executor
- dettagli interni del pool di sessioni

## Tag di Funzionalità

`capabilities` è un array ordinato di tag derivati dalla voce del registro. Gli integratori
dovrebbero considerarlo la risposta leggibile dalle macchine alla domanda "cosa può fare questo provider",
anziché rileggere i sorgenti TypeScript.

| Tag                  | Significato                                                                                                     |
| -------------------- | --------------------------------------------------------------------------------------------------------------- |
| `apikey`             | Accetta una chiave API (`authType` è `apikey` o `optional`).                                                    |
| `oauth`              | Utilizza un flusso OAuth o di sessione.                                                                         |
| `responses`          | Espone un URL di base per l'API Responses di OpenAI.                                                            |
| `passthrough-models` | Fornisce i modelli direttamente dall'upstream anziché da un catalogo statico.                                   |
| `custom-executor`    | Esegue un executor non predefinito, quindi rimane sul percorso TypeScript.                                      |
| `sidecar-candidate`  | Rispecchia `sidecar.eligible` — può essere preso in considerazione in sicurezza per l'importazione nel sidecar. |
| `usage-fetch`        | Dispone di un fetcher configurato per utilizzo o quota (`getUsageForProvider`).                                 |
| `usage-supported`    | L'API di utilizzo accetta questo provider (`isSupportedUsageConnection`).                                       |

`usage-fetch` serve esclusivamente per il rilevamento. Indica che OmniRoute sa come leggere l'utilizzo del
provider; non attiva il recupero, non modifica la semantica delle quote e non implica che il
widget delle quote della Dashboard sia abilitato per il provider — tale widget è controllato separatamente da
`USAGE_SUPPORTED_PROVIDERS`. La fonte di verità è `USAGE_FETCHER_PROVIDERS` in
`open-sse/services/usage/fetcherProviders.ts`.

Tale elenco utilizza come chiavi le stringhe accettate dal dispatcher dell'utilizzo, quindi combina ID canonici
e alias ed è leggermente più lungo del numero di provider con tag: le voci che non sono
provider di chat nel registro del manifest (ad esempio il provider di ricerca `firecrawl`
e il provider ACP `amazon-q`) non dispongono di una voce del manifest a cui applicare il tag.

`usage-supported` indica se le route di utilizzo del server e della Dashboard accettano una connessione
per il provider. Rispecchia `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
e `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), entrambe controllate da
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). A differenza di
`usage-fetch`, viene emesso esclusivamente in base all'ID del provider — il controllo di runtime esegue
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` senza risoluzione degli alias, quindi il manifest
mantiene la stessa regola. I due tag hanno ambiti diversi: 3 provider hanno solo
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) e 1 ha solo
`usage-supported` (`xiaomi-mimo-token-plan`), pertanto l'uno non implica l'altro.

## Utilizzo dei sidecar

I sidecar devono considerare `sidecar.eligible` come un segnale conservativo di possibile idoneità, non come una decisione di instradamento incondizionata. Il primo obiettivo dell'importazione deve essere costituito dai provider con chiave API ed endpoint statico che utilizzano l'esecutore predefinito. I provider con esecutori web personalizzati, flussi OAuth/sessione, generatori di URL dinamici o configurazioni di pool devono rimanere sul percorso di fallback TypeScript finché un sidecar non implementa un comportamento equivalente e la telemetria non ne dimostra la parità.

Fasi di migrazione suggerite:

1. Generare e convalidare il manifest dei plugin dei provider a partire dal registro TS.
2. Consentire a Bifrost o CLIProxyAPI di importare il manifest per i provider con chiave API ed endpoint statico.
3. Instradare i provider idonei attraverso il sidecar dietro `OMNIROUTE_RELAY_BACKEND`, mantenendo abilitato il fallback TS.
4. Promuovere i provider solo quando il tasso di successo, la latenza p99, il comportamento dello streaming e la gestione dei parametri non supportati corrispondono al percorso TS.
5. Aggiungere plugin nativi del sidecar per gli esecutori personalizzati, una famiglia di provider alla volta.

## Perché non integrare i provider direttamente in Next

Il frontend Next non deve gestire l'esecuzione dei provider. Deve chiamare il confine dell'API. Il backend può quindi decidere se utilizzare l'esecutore TypeScript, Bifrost, CLIProxyAPI o un futuro sidecar nativo. In questo modo, la firma delle richieste, i controlli dell'elenco consentito, le policy del DB e il comportamento di fallback rimangono centralizzati prima di qualsiasi passaggio al sidecar.
