---

OmniRoute offre **due** modi per utilizzare OpenAI Codex:

| Provider               | Come comunica con OpenAI                                                                                                                                                                                              | Avvertenza sull'utilizzo                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **`codex`**            | Inoltra direttamente il token OAuth di ChatGPT/OpenAI alla Responses API                                                                                                                                              | **Sì** — la sessione ufficiale non è autorizzata per l'uso tramite proxy/router |
| **`codex-app-server`** | Controlla il **`codex app-server` della Codex CLI** tramite JSON-RPC/WebSocket; la CLI gestisce e aggiorna automaticamente il proprio OAuth (`~/.codex/auth.json`), esattamente come una sessione `codex` interattiva | **No** — OmniRoute non inoltra mai un token all'API                             |

Poiché `codex-app-server` non inoltra mai un token, non presenta
l'avvertenza sull'utilizzo relativa all'inoltro della sessione. Richiede però una
**Codex CLI raggiungibile all'URL dell'app-server configurato**, e tale CLI deve
aver **effettuato l'accesso**.

---

## 1. Architettura

```
┌─ App OmniRoute ─────────────────┐        ┌─ Sidecar codex-app-server ──────────┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                   │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456         │
│  (+ token di funzionalità)       │  JSON  │  --ws-auth capability-token         │
│                                  │  RPC   │  gestisce autonomamente OAuth OpenAI│
└──────────────────────────────────┘        │  (~/.codex/auth.json, aggiorn. aut.)│
        │ condivisione (volumi compose)      └─────────────────────────────────────┘
        ▼
  codex-appserver-token   → il token di funzionalità WS (montato da entrambi)
  codex-appserver-home    → ~/.codex (auth.json scritto dalla dashboard,
                             letto dal codex app-server del sidecar)
```

- Il sidecar resta in ascolto **solo** sulla rete compose interna
  (`ws://codex-app-server:1456`) dietro un token di funzionalità. **Non** viene
  mai esposto sull'host o su Internet.
- La Codex CLI è inclusa in `omniroute:base`, quindi non è necessario installare
  codex sull'host o sul computer dell'utente quando si esegue il sidecar.

## 2. Avvio

```bash
# Avvia lo stack CON il profilo sidecar codex app-server:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

Al primo avvio, il sidecar genera il proprio token di funzionalità WS (nel volume
condiviso `codex-appserver-token`) e l'app legge lo stesso token tramite
`OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`. Non è necessario configurare
manualmente il token.

## 3. Connessione + accesso

1. Nella dashboard, aggiungi una connessione per **OpenAI Codex (App-Server)**.
   Non è necessaria alcuna chiave API o alcun token (è un provider senza
   autenticazione: il sidecar gestisce l'autenticazione).
2. Se la Codex CLI del sidecar **non ha ancora effettuato l'accesso**, il
   controllo dello stato della connessione segnala _"in esecuzione, ma accesso
   non effettuato"_ (non un errore di autenticazione rosso). Usa **Accedi con
   ChatGPT**: questa operazione esegue il normale OAuth tramite dispositivo di
   Codex nel browser, quindi scrive `~/.codex/auth.json` nel volume condiviso
   tramite **Applica autenticazione** (lo stesso accesso serve entrambi i
   provider `codex` e `codex-app-server`).
3. Dopo aver effettuato l'accesso, il controllo dello stato diventa verde
   (verifica sia `/readyz` **sia** `account/read`, ossia che il servizio sia
   attivo _e_ autenticato) e inizia a funzionare.

La dashboard non sovrascrive mai un file `~/.codex/auth.json` esistente e valido:
scrive soltanto quando il file è assente o il relativo token è obsoleto (viene
sempre creata una copia di backup).

## 4. Scenari di distribuzione

- **Operatore con una Codex CLI già autenticata** — monta la directory
  `~/.codex` dell'host nel sidecar (`codex-appserver-home`) e salta il passaggio
  di accesso.
- **Utente pubblico, senza codex installato localmente** — irrilevante: il
  sidecar include la CLI. L'utente deve autenticarsi soltanto tramite la
  dashboard.
- **OmniRoute bare metal (senza sidecar, codex sull'host)** — configura
  `OMNIROUTE_CODEX_APPSERVER_WS` in modo che punti al tuo `codex app-server` e
  assicurati che codex sull'host abbia effettuato l'accesso; se il binario non è
  presente, viene visualizzato il suggerimento "codex non installato".

## 5. Uscita residenziale / UDP (opzione aggiuntiva per l'operatore, non inclusa)

Il sidecar generico descritto sopra instrada il traffico in uscita attraverso la
normale rete del container. Un operatore che necessita che il traffico Codex
esca tramite un'**uscita residenziale** (ad esempio, un sidecar TUN tailscale che
trasporta TCP + UDP/QUIC) deve eseguirla mediante un override compose separato;
questa configurazione **non** fa intenzionalmente parte del profilo
`codex-app-server` distribuito. Consulta il runbook operativo interno per tale
configurazione.
