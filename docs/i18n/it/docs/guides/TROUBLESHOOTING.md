## Riferimento rapido

**Non conosci ancora OmniRoute?** Inizia da qui: queste soluzioni risolvono il 90% dei problemi:

| Vedo questo             | Cosa significa                                   | Cosa fare                                                                                           |
| ----------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| "Can't connect"         | OmniRoute non è in esecuzione                    | Esegui `omniroute` o `docker restart omniroute`                                                     |
| "Invalid API key"       | La chiave è errata o scaduta                     | Copia nuovamente la chiave dal sito web del provider                                                |
| "Rate limit exceeded"   | Stai inviando troppe richieste                   | Attendi 1 minuto oppure usa `model: "auto"` per il fallback automatico                              |
| "Quota exceeded"        | Hai esaurito la quota gratuita/a pagamento       | Collega altri provider oppure usa provider gratuiti (Kiro, Pollinations)                            |
| "Slow responses"        | Il provider è occupato o geograficamente lontano | Usa `model: "auto/fast"` oppure collega un provider più veloce (Groq, Cerebras)                     |
| "Wrong provider used"   | `auto` ha scelto un provider diverso             | È normale! `auto` sceglie quello migliore. Forza un provider specifico con `model: "openai/gpt-4o"` |
| "502 Bad Gateway"       | Il provider non è disponibile                    | Attendi e riprova oppure usa `model: "auto"` per cambiare provider                                  |
| "401 Unauthorized"      | Le credenziali sono errate                       | Controlla la chiave API oppure esegui nuovamente l'autenticazione con OAuth                         |
| "429 Too Many Requests" | È stato applicato un limite di frequenza         | Attendi 1 minuto oppure collega altri provider                                                      |

**Il problema persiste?** Consulta la [risoluzione dettagliata dei problemi](#detailed-troubleshooting) qui sotto oppure chiedi su [Discord](https://discord.gg/U47eFqAXCn).

## Risoluzione dettagliata dei problemi

---

### Limitazione della frequenza sui provider gratuiti (429 / 400 / 401)

**Sintomo**: quando usi `model: "auto"` con provider gratuiti/senza autenticazione (opencode, auggie, ecc.), a intermittenza ricevi `HTTP 429`, `400` o `401` anziché le risposte. Le richieste riescono quando riprovi lo stesso prompt pochi istanti dopo, ma l'automazione (processi cron, agenti, script) si interrompe al primo errore.

**Causa principale**: si sommano tre modalità di errore indipendenti:

1. **Limite di frequenza del provider (`429`)**: i livelli gratuiti possono imporre una quota per intervallo temporale. Una raffica di chiamate parallele la esaurisce, quindi la richiesta successiva viene rifiutata finché l'intervallo non viene reimpostato.
2. **Modello non funzionante in passthrough (`400`/`401`)**: i pool `auto/*` possono includere modelli passthrough di `opencode` registrati nel catalogo ma privi di credenziali attive (ad es. `oc/north-mini-code-free` → `401`). Il router automatico ne prova uno, fallisce e l'errore si propaga prima che venga attivato il fallback.
3. **Amplificazione dovuta alla concorrenza (`429` sotto carico)**: quando più sessioni agente/cron accedono contemporaneamente ad `auto`, la frequenza aggregata delle richieste supera quella tollerata dai provider gratuiti, quindi chiamate legittime vengono contrassegnate come abusive.

**Correzione verificata (segnalata dalla community, 2026-08-10)**: regola tre variabili d'ambiente affinché la rotazione, la concorrenza e il fallback assorbano l'instabilità del livello gratuito anziché interrompersi:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # passa a un altro modello/provider in caso di 400/401 (ignora i modelli passthrough non funzionanti)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # limite esplicito di ammissione per le richieste pesanti (non impostato per impostazione predefinita: nessun limite al numero di richieste, consulta la nota sotto)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # attesa limitata più lunga per la capacità delle richieste pesanti anziché un 503 immediato e ripetibile
```

Imposta queste variabili nell'ambiente del processo OmniRoute (il daemon, ad es. tramite il plist LaunchAgent o `systemctl edit`), quindi riavvia OmniRoute. Il flag di rotazione è il singolo strumento più efficace: trasforma un errore definitivo in un nuovo tentativo trasparente con un provider funzionante del pool.

**Nota**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` limita il numero di richieste pesanti, ovvero con contesto lungo, eseguite contemporaneamente; il limite è un controllo di ammissione, non un limitatore della frequenza del provider. **Aggiornamento #503-fanout:** questa variabile non viene più impostata per impostazione predefinita (ora entra in funzione solo quando viene configurata esplicitamente, come sopra): l'ammissione delle richieste pesanti è invece regolata da un budget di byte derivato automaticamente (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), che si adatta al limite reale di memoria dell'host. Di conseguenza, una nuova distribuzione dovrebbe produrre molti meno rifiuti `503 chat_admission_busy` senza che sia necessario impostare questa variabile; impostarla esplicitamente come mostrato qui continua comunque a funzionare esattamente come documentato. Le sostituzioni esplicite del budget di byte vengono limitate all'intervallo 8 MiB–2 GiB. Un errore `413 body_exceeds_budget` non è transitorio: aumenta il budget di byte, riduci `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` oppure aumenta il limite di memoria del processo. Un rifiuto `inflight_bytes_budget` indica una contesa temporanea e può essere ritentato. La limitazione della frequenza per provider (`open-sse/services/rateLimitManager.ts`) è gestita separatamente da `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` e `RATE_LIMIT_AUTO_ENABLE`: consulta `.env.example`.

**Come verificare che abbia funzionato**: esegui l'agente/il processo cron due volte in rapida successione e verifica che entrambe le esecuzioni riescano. Prima della correzione, la seconda esecuzione genera in genere `429`/`401`. Dopo la correzione, gli errori, se presenti, vengono ritentati in modo trasparente e la chiamata viene completata. Puoi anche eseguire `curl /monitoring/health` e osservare il campo `rateLimitedUntil` nelle connessioni dei provider e `circuitBreakers.providerBreakers[].state` per i provider interessati: lo stato può essere `CLOSED`, `DEGRADED`, `OPEN` o `HALF_OPEN` (consulta `src/shared/utils/circuitBreaker.ts`) e un provider che continua a generare errori passerà da `CLOSED → DEGRADED → OPEN` prima che la finestra di ripristino consenta il passaggio di una richiesta di prova (`HALF_OPEN`).

**Se continui a visualizzare 429**: l'account attivo per quel provider ha effettivamente esaurito la propria _quota_ (non si tratta solo di un limite di frequenza). Aggiungi un secondo account per lo stesso provider nella dashboard di OmniRoute → Provider → Account, oppure aggiungi un altro provider gratuito (ad es. `routeway`, `auggie`). La rotazione è utile solo per errori transitori di frequenza/400/401; l'esaurimento completo della quota richiede una seconda credenziale o un provider diverso.

**Se visualizzi 403 sui modelli di visione (`auto/vision`, `bazaarlink/*`)**: l'account connesso non dispone di un piano a pagamento che includa la visione oppure la chiave API non dispone di autorizzazioni sufficienti. Verifica nella dashboard del provider che l'ambito della chiave includa visione/multimodalità oppure connetti un account di livello a pagamento e mantienilo come destinazione per la visione.

## Avvisi di npm install (ERESOLVE / peer / deprecated)

Quando esegui `npm install -g omniroute`, potresti visualizzare numerosi avvisi come `npm warn ERESOLVE`, notifiche relative alle dipendenze peer e messaggi `deprecated`. **Questi avvisi sono previsti e innocui.** L'installazione è riuscita se nell'output compare `added <N> packages`.

Gli avvisi derivano da intervalli obsoleti delle dipendenze peer in pacchetti di terze parti non controllati da OmniRoute:

1. **`marked-terminal` richiede `marked >=1 <16`, ma è stato trovato `marked@18`** — in pratica funziona correttamente; l'intervallo peer upstream è semplicemente obsoleto.
2. **`deprecated prebuild-install@7.1.3`** — un helper transitivo per il recupero di binari nativi. Non viene
   utilizzato per installare il binding di trasporto `wreq-js` bloccato a una versione specifica e non indica che la configurazione
   del trasporto del provider web-cookie non sia riuscita.

**Non è necessario alcun intervento** — gli avvisi non possono essere eliminati completamente senza creare fork dei pacchetti upstream.

| Problema                                                   | Soluzione                                                                                                                                                                                      |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| La strategia di routing non viene salvata                  | Aggiorna all'ultima versione v3.x (la correzione dello schema Zod per la persistenza delle impostazioni è stata inclusa nelle versioni precedenti)                                             |

## Falsi positivi dell'antivirus

<a name="antivirus-false-positives"></a>

### Avast/AVG mette in quarantena `README.md` con `MD:HttpRequest-inf[Susp]`

**Questo è un falso positivo. Nulla è infetto e non è richiesta alcuna azione.**

Avast e AVG eseguono un'euristica che segnala i file di testo semplice/Markdown contenenti
molti link che sembrano richieste HTTP. Il file `README.md` di OmniRoute è incluso nel
pacchetto npm (è elencato in `package.json` → `files`), quindi, con un'installazione globale,
viene collocato in `node_modules/omniroute/README.md` e contiene circa 15 esempi
`http://localhost:20128/...` (gli endpoint HTTP/SSE di MCP, l'URL `.well-known` di A2A e
frammenti `curl`). Questa densità di link è sufficiente ad attivare l'euristica.

Se il problema si è presentato solo di recente: la natura del file non è cambiata. Nel
README è stata ampliata la tabella degli endpoint (sono stati aggiunti MCP HTTP + SSE + A2A)
e sono stati inclusi altri esempi `curl`, superando così la soglia.

Il file è documentazione inerte e non contiene alcun contenuto eseguibile. Può essere
ripristinato dalla quarantena in tutta sicurezza.

**Cosa fare:**

1. **Interrompere le notifiche** — escludere la directory di installazione nell'antivirus
   (Avast: Impostazioni → Eccezioni), aggiungendo il percorso globale di `node_modules`
   e/o la directory dei dati di OmniRoute (`~/.omniroute/`).
2. **Segnalare il falso positivo** — <https://www.avast.com/false-positive-file-form.php>,
   allegando il file `README.md` in quarantena. Questa è la soluzione che aiuta tutti,
   poiché è l'euristica del fornitore a reagire in modo eccessivo a un file di testo.

**Perché non lo "risolviamo" da parte nostra:** tutti gli esempi usano `http://localhost`
e localhost non può utilizzare `https` senza le complicazioni legate ai certificati
autofirmati. Alterare la documentazione per aggirare l'euristica di un singolo fornitore
penalizzerebbe ogni lettore per assecondare un bug dello scanner.

### Kaspersky segnala l'app desktop come `PDM:Trojan.Win32.Generic`

**Questo è un falso positivo generato da un'euristica comportamentale. Nulla è infetto.**
Il prefisso `PDM:` di Kaspersky indica che il verdetto proviene dal suo Proactive Defense
Module (System Watcher), che valuta ciò che il programma di installazione _fa_, anziché
confrontarlo con malware noto. Quando viene attivato, Kaspersky esegue il "rollback"
dell'intera installazione, eliminando i file già scritti; di conseguenza, l'app risulta
danneggiata o assente.

I file segnalati sono componenti standard di dipendenze open source dichiarate e incluse
nell'app desktop, ad esempio:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` e
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), la libreria di automazione
  del browser utilizzata per l'accesso ai provider all'interno dell'app e per la chat
  supportata dal browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — il binding nativo `wreq-js` con versione bloccata, utilizzato per richieste HTTP con
  impronta digitale del browser sui provider che usano cookie web (`<arch>` è `x64` o
  `arm64`).

**Perché viene attivato:** il programma di installazione per Windows **non è ancora firmato
digitalmente**, quindi un programma di installazione NSIS non firmato non gode di alcuna
reputazione e le euristiche comportamentali vengono eseguite con la massima aggressività.
Insieme a una DLL nativa inclusa e a centinaia di file `.js` scritti in
`%LOCALAPPDATA%\Programs\OmniRoute` (incluse le directory dei pacchetti con hash nel nome
provenienti dalla build standalone di Next.js), ciò è sufficiente ad attivare l'euristica.
La firma del codice è prevista; fino alla sua introduzione, il problema può ripresentarsi
con le nuove versioni.

**Cosa fare:**

1. **Verificare prima il download** (per escludere che il file sia stato manomesso). Ogni
   release pubblica `latest.yml`, il cui campo `sha512` (base64) copre il programma di
   installazione `OmniRoute.Setup.<version>.exe`. In PowerShell, dalla cartella contenente
   il programma di installazione:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   L'output deve corrispondere a `latest.yml` → `sha512`. In caso contrario, eliminare il
   file e scaricarlo nuovamente esclusivamente dalla [pagina delle release di GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Ripristinare + escludere** — ripristinare dalla quarantena gli elementi rimossi dal
   rollback e aggiungere un'esclusione per `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky →
   Impostazioni → Minacce ed esclusioni), quindi reinstallare.
3. **Segnalare il falso positivo** — <https://opentip.kaspersky.com/>. Le segnalazioni di
   falsi positivi inviate dagli utenti accelerano concretamente l'inserimento nella lista
   degli elementi consentiti.

## Compatibilità con Node.js

<a name="nodejs-compatibility"></a>

### La pagina di accesso si arresta in modo anomalo o mostra l'errore "Module self-registration"

**Causa:** Stai eseguendo una versione di Node.js non compresa nell'intervallo minimo di runtime sicuro approvato da OmniRoute. Il caso più comune consiste nell'utilizzo di una versione patch meno recente di Node 22 o 24, precedente alla versione minima corretta richiesta da OmniRoute per motivi di sicurezza.

**Sintomi:**

- La pagina di accesso mostra una schermata vuota o un errore del server
- La console mostra `Error: Module did not self-register` o errori simili relativi ai binding nativi
- La pagina di accesso mostra un **banner di avviso arancione** con la tua versione di Node se il runtime non rientra nei criteri di sicurezza supportati

**Soluzione:**

1. Installa una versione LTS supportata di Node.js (consigliata: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Verifica la versione: `node --version` dovrebbe mostrare `v24.0.0` o una versione successiva della linea LTS 24.x
3. Reinstalla OmniRoute: `npm install -g omniroute`
4. Riavvia: `omniroute`

> **Versioni sicure supportate:** `>=22.22.2 <23` o `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) e Node.js 26 sono pienamente supportati.

### npm v11+: `better-sqlite3` non installato (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Causa:** npm v11 (incluso con Node.js 24+) blocca per impostazione predefinita gli script di installazione per le dipendenze opzionali. Poiché `better-sqlite3` è elencato in `optionalDependencies` e richiede la compilazione nativa (`node-gyp rebuild`), npm lo ignora senza mostrare alcun avviso.

**Sintomi:**

- Il server si arresta in modo anomalo all'avvio con `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` mostra "No such file or directory"
- `npm ls better-sqlite3` mostra `(empty)`

**Soluzione:**

1. Approva gli script di installazione e reinstalla:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. In alternativa, installa manualmente il pacchetto precompilato:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Verifica che funzioni: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Causa:** Dopo un'installazione globale con `npm install -g omniroute`, il file binario nativo di `better-sqlite3` incluso nel pacchetto potrebbe essere stato compilato per un'architettura o un ABI di Node.js diverso da quello in esecuzione localmente. Questo problema è comune su macOS (sia Apple Silicon sia Intel) quando il file binario precompilato non corrisponde all'ambiente in uso.

**Sintomi:**

- Il server si arresta immediatamente all'avvio con un errore `dlopen`
- L'errore contiene `slice is not valid mach-o file`
- Esempio completo:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Soluzione — ricompila per l'ambiente locale (non è necessario eseguire il downgrade di Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Nota:** Questa operazione ricompila il binding nativo per la versione locale di Node.js e l'architettura della CPU, risolvendo l'incompatibilità del file binario. L'intervallo di runtime ufficialmente supportato è **`>=22.22.2 <23` o `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` in `src/shared/utils/nodeRuntimeSupport.ts`, allineato al campo `engines` di `package.json`). Node.js 24.x LTS (Krypton) e Node.js 26 sono pienamente supportati con `better-sqlite3` v12.x.

## Problemi relativi al proxy

<a name="proxy-issues"></a>

### La convalida del provider mostra "fetch failed"

**Causa:** In precedenza, l'endpoint di convalida della chiave API (`POST /api/providers/validate`) ignorava la configurazione del proxy, causando errori negli ambienti che richiedono l'instradamento tramite proxy.

**Correzione (v3.5.5+):** Il problema è stato risolto. La convalida del provider ora viene instradata tramite `runWithProxyContext`, rispettando automaticamente le impostazioni proxy a livello di provider e globali.

### Il controllo dello stato del token non riesce con "fetch failed"

**Causa:** L'aggiornamento in background del token OAuth non risolveva la configurazione del proxy per ciascuna connessione.

**Correzione (v3.5.5+):** Lo scheduler del controllo dello stato dei token ora risolve la configurazione del proxy per ciascuna connessione prima di tentare l'aggiornamento. Aggiornare alla versione v3.5.5 o successiva.

### Il proxy SOCKS5 restituisce "invalid onRequestStart method"

**Causa:** Su Node.js 22, il dispatcher di undici@8 non è compatibile con l'implementazione integrata di `fetch()` di Node.

**Correzione (v3.5.5+):** OmniRoute ora utilizza la funzione `fetch()` di undici quando è attivo un dispatcher proxy, garantendo un comportamento coerente. Aggiornare alla versione v3.5.5 o successiva.

### Proxy MITM in WSL: le applicazioni desktop sull'host Windows non vengono intercettate

**Causa:** Il proxy MITM e il relativo certificato CA vengono installati nell'ambiente in cui viene eseguito OmniRoute. In WSL, tale ambiente è il sistema guest Linux, mentre le applicazioni desktop di IA (Kiro, Trae, Copilot, Zed, …) vengono eseguite sull'host Windows. Le applicazioni host non considerano attendibile l'archivio dei certificati del guest e non instradano il traffico attraverso il proxy di sistema del guest; pertanto, l'intercettazione delle applicazioni desktop non viene attivata.

**Raccomandazione:** Eseguire OmniRoute in modo nativo sullo stesso sistema operativo delle applicazioni desktop che si desidera intercettare (Windows per le applicazioni Windows; analogamente per macOS/Linux). Mantenere OmniRoute all'interno di WSL mentre si prendono di mira le applicazioni host richiede di considerare manualmente attendibile il certificato CA generato sull'host Windows e di configurare le impostazioni di rete/proxy di ciascuna applicazione host affinché utilizzino l'endpoint proxy WSL: si tratta di una configurazione non supportata e fragile.

## Problemi relativi ai provider

### "Language model did not provide messages"

**Causa:** La quota del provider è esaurita.

**Correzione:**

1. Controllare il monitoraggio della quota nella dashboard
2. Utilizzare una combinazione con livelli di fallback
3. Passare a un livello più economico/gratuito

### Limitazione della frequenza

**Causa:** La quota dell'abbonamento è esaurita.

**Correzione:**

- Aggiungere un fallback: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Utilizzare GLM/MiniMax come alternativa economica

### Token OAuth scaduto

OmniRoute aggiorna automaticamente i token. Se i problemi persistono:

1. Dashboard → Provider → Riconnetti
2. Eliminare e aggiungere nuovamente la connessione al provider

### Account multipli Kiro: il secondo account invalida il primo

**Causa:** Il backend di Kiro impone una sola sessione attiva per ogni registrazione client OIDC.
Quando due account condividono lo stesso client registrato (connessioni importate prima della v3.8.0),
l'aggiornamento del token di un account invalida il token di aggiornamento dell'altro.

**Correzione (v3.8.0+):** Importare nuovamente le connessioni interessate.
A partire dalla v3.8.0, ogni nuova connessione Kiro creata tramite **Importa token**,
**Accesso social con Google/GitHub** o **Importazione automatica** registra automaticamente un
client OIDC dedicato. La connessione è quindi completamente isolata e l'aggiornamento di un
account non ha alcun effetto sugli altri account.

Le connessioni importate _prima_ della v3.8.0 non dispongono di una registrazione client
specifica per connessione. Tali connessioni continuano a utilizzare l'endpoint di aggiornamento condiviso per l'autenticazione social.
Per ottenere l'isolamento, eliminare la vecchia connessione da Dashboard → Provider e aggiungerla nuovamente
tramite uno qualsiasi dei tre flussi di importazione.

Per informazioni complete e istruzioni dettagliate su come aggiungere due account Kiro affiancati,
consultare [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Problemi di Docker

### IPv6 di Docker / Reimpostazione della connessione

<a name="docker-ipv6"></a>

**Sintomi:** `curl http://localhost:20128/v1/models` restituisce `curl: (56) Recv failure: Connection reset by peer`. La dashboard e gli endpoint non autenticati funzionano, ma quelli autenticati non riescono: sembra un problema di autenticazione, ma non lo è.

**Causa:** `docker run -p 20128:20128` pubblica sia su `0.0.0.0` (IPv4) sia su `::` (IPv6), ma il processo all'interno del container resta in ascolto solo su IPv4. Sugli host in cui `localhost` viene risolto prima come `::1`, la connessione raggiunge la porta IPv6 pubblicata, ma non trova alcun listener sottostante → reimpostazione della connessione.

**Correzione:**

1. **Diagnosi rapida:** Esegui `curl -4 http://localhost:20128/v1/models`. Se funziona con `-4` ma non senza, è presente una mancata corrispondenza del binding IPv6.
2. **Correzione permanente:** Esegui esplicitamente il binding a IPv4 usando `-p 127.0.0.1:20128:20128` nel comando `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Questo forza il binding IPv4 ed evita inoltre di esporre il proxy su tutte le interfacce dell'host.

## Impostazioni di resilienza

### Il limite automatico della frequenza non si attiva

- Il limite automatico della frequenza si applica solo ai provider con chiave API (non OAuth/abbonamento)
- Verificare che in **Impostazioni → Resilienza → Profili provider** il limite automatico della frequenza sia abilitato
- Controllare se il provider restituisce codici di stato `429` o intestazioni `Retry-After`

### Regolazione del backoff esponenziale

I profili dei provider supportano queste impostazioni:

- **Ritardo di base** — Tempo di attesa iniziale dopo il primo errore (predefinito: 1s)
- **Ritardo massimo** — Limite massimo del tempo di attesa (predefinito: 30s)
- **Moltiplicatore** — Fattore di incremento del ritardo per ogni errore consecutivo (predefinito: 2x)

### Prevenzione del thundering herd

Quando molte richieste simultanee raggiungono un provider soggetto a limitazione della frequenza, OmniRoute utilizza mutex + limitazione automatica della frequenza per serializzare le richieste e prevenire errori a cascata. Questo avviene automaticamente per i provider con chiave API.

### Le richieste di chat non riescono con 503 / chat_admission_busy

**Sintomi:**

- L'endpoint dei completamenti della chat restituisce una risposta `503` ritentabile il cui codice di errore è
  `chat_admission_busy`.
- La risposta include `Retry-After`. A partire da #12135, il valore deriva dall'occupazione osservata:
  viene usato il valore maggiore tra la finestra `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` già attesa dalla richiesta
  e il tempo per cui sono rimasti attivi i lease correnti per richieste pesanti, arrotondato per eccesso a secondi
  interi e limitato a 60. Quando il gate è inattivo, mantiene i valori minimi storici: 2 secondi nel percorso
  basato sui byte, 1 secondo nel percorso basato sulla struttura (che include anche
  `reason: "structure_limit"`).
- Questo può accadere mentre un'altra chat pesante o una risposta in streaming di lunga durata è ancora
  in corso.

Il corpo della risposta basata sui byte è:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

La risposta basata sulla struttura utilizza lo stesso tipo e codice, con il messaggio
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
e `reason: "structure_limit"`.
Con le soglie predefinite, una richiesta è strutturalmente pesante quando contiene almeno `200` messaggi,
almeno `64` strumenti o almeno `32,000` token stimati, oppure quando la stima limitata della struttura
esaurisce i propri limiti di `10,000` nodi visitati o di profondità `12`.

**Causa:** si tratta di una riduzione intenzionale del carico all'interno di OmniRoute, non di un errore del provider upstream.
Ogni processo utilizza una protezione locale al processo per riservare una capacità limitata alle richieste pesanti prima di conservare
e analizzare il corpo di una richiesta di grandi dimensioni. Un lease per richieste pesanti rimane attivo per l'intera durata di una risposta
SSE.

**#503-fan-out:** prima di questa correzione, la protezione limitava la concorrenza a un NUMERO fisso di richieste
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, valore predefinito `1`) indipendentemente dalla memoria dell'host; di conseguenza, il
fan-out degli agenti di programmazione (più sottoagenti/CLI, corpi normalmente > 256 KB) si riduceva a una
concorrenza effettiva di circa 1 e generava errori 503 con un carico del tutto normale. Ora la protezione si autoregola: è controllata
da un budget automatico di BYTE in ingresso (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), dimensionato in base al
limite reale di memoria del processo, e consulta anche un segnale in tempo reale relativo alla pressione sulle risorse; pertanto
riduce il carico solo quando l'host è effettivamente sotto pressione di memoria, non semplicemente perché è arrivata più di una
richiesta pesante contemporaneamente. Il precedente limite numerico (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) viene
ancora rispettato, ma solo se viene impostato esplicitamente.

Quando la capacità è occupata, una richiesta pesante attende innanzitutto fino a
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (valore predefinito `2000`; `0` disabilita l'attesa) affinché si liberi uno slot,
prima di restituire la risposta `503` ritentabile. L'attesa limitata esiste affinché i client di tipo agente
(OpenCode, Claude Code, Cursor) che eseguono in fan-out richieste secondarie pesanti simultanee serializzino il picco
anziché consumare tutto il proprio budget di tentativi con rifiuti immediati e interrompersi durante l'attività.
L'occupazione corrente dei lease per richieste pesanti, il budget di byte determinato e la gravità della pressione in tempo reale sono
esposti in `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`): controllare questi valori prima di modificare qualsiasi variabile di ambiente.
Impostazioni → Resilienza → Coda delle richieste → Richieste simultanee non controlla questo comportamento; tale impostazione
gestisce un meccanismo separato per la coda delle richieste del provider.

**Soluzione:**

1. Riprovare innanzitutto. I client devono rispettare `Retry-After` e utilizzare il backoff anziché ripetere
   immediatamente la richiesta.
2. Controllare `/api/monitoring/health` → `chatAdmission` prima di modificare qualsiasi impostazione. `countCapEnabled:
false` e un valore generoso di `maxInflightBytes` indicano che il budget derivato automaticamente sta già svolgendo il proprio
   compito; un valore `pressureSeverity` pari a `high`/`critical` indica che l'host dispone effettivamente di poca memoria:
   il problema non può essere risolto tramite una variabile di ambiente per l'ammissione, ma richiede più RAM o un carico di lavoro inferiore.
3. Solo se `/api/monitoring/health` mostra che il budget derivato automaticamente è effettivamente troppo ridotto per
   l'host (caso raro, poiché è già dimensionato automaticamente dai container ai sistemi bare-metal), sovrascriverlo direttamente con
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` anziché ricorrere al precedente limite basato sul numero di richieste.

Consultare il [riferimento delle variabili di ambiente](../reference/ENVIRONMENT.md#4-security--authentication)
per le impostazioni autorevoli relative all'ammissione.

## Tassonomia opzionale degli errori RAG / LLM (16 problemi)

Alcuni utenti di OmniRoute posizionano il gateway davanti a stack RAG o di agenti. In queste configurazioni è comune osservare uno schema insolito: OmniRoute sembra funzionare correttamente (provider operativi, profili di routing corretti, nessun avviso sui limiti di frequenza), ma la risposta finale è comunque errata.

Nella pratica, questi incidenti derivano solitamente dalla pipeline RAG a valle, non dal gateway stesso.

Se desideri un vocabolario condiviso per descrivere questi errori, puoi utilizzare WFGY ProblemMap, una risorsa testuale esterna con licenza MIT che definisce sedici schemi di errore ricorrenti relativi a RAG / LLM. A grandi linee, tratta:

- deriva del recupero e confini del contesto non corretti
- indici e archivi vettoriali vuoti o obsoleti
- mancata corrispondenza tra embedding e semantica
- problemi di composizione dei prompt e della finestra di contesto
- collasso della logica e risposte eccessivamente sicure
- errori nelle catene lunghe e nel coordinamento degli agenti
- deriva della memoria e dei ruoli nei sistemi multi-agente
- problemi di ordinamento nella distribuzione e nel bootstrap

L'idea è semplice:

1. Quando analizzi una risposta errata, acquisisci:
   - attività e richiesta dell'utente
   - combinazione di route o provider in OmniRoute
   - qualsiasi contesto RAG utilizzato a valle (documenti recuperati, chiamate agli strumenti, ecc.)
2. Associa l'incidente a uno o due numeri della WFGY ProblemMap (`No.1` … `No.16`).
3. Memorizza il numero nella tua dashboard, nel runbook o nel sistema di monitoraggio degli incidenti, accanto ai log di OmniRoute.
4. Utilizza la pagina WFGY corrispondente per decidere se modificare lo stack RAG, il retriever o la strategia di routing.

Il testo completo e le procedure concrete sono disponibili qui (licenza MIT, solo testo):

[README di WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Puoi ignorare questa sezione se non esegui pipeline RAG o di agenti dietro OmniRoute.

## Problemi noti di v3.8.0

Problemi specifici della versione v3.8.0 e relative soluzioni alternative attuali. Se una correzione viene inclusa in una patch successiva, la voce verrà aggiornata o rimossa.

### Errori di autenticazione di Devin CLI

**Sintomi:**

- "Devin CLI not found" o "auth failed" durante l'invocazione di strumenti basati su Devin
- Il controllo di runtime della CLI segnala `installed=false`

**Cause:**

- `CLI_DEVIN_BIN` punta a un percorso inesistente
- Devin CLI non è installata sull'host

**Soluzione:**

1. Installa Devin CLI per la tua piattaforma
2. Imposta `CLI_DEVIN_BIN=/usr/local/bin/devin` (o il percorso effettivo) in `.env`
3. Riavvia OmniRoute ed esegui nuovamente il test da **Dashboard → Strumenti CLI**

### Cooldown del modello bloccato (ripristino manuale)

**Sintomi:**

- Un modello continua a essere elencato come in cooldown anche dopo la scadenza
- Le richieste continuano a ignorare il modello nel routing combinato, nonostante il timestamp sia nel passato

**Ripristino manuale:**

- **Dashboard:** **Impostazioni → Cooldown dei modelli** → fai clic su **Riabilita** nella scheda interessata
- **API:** `DELETE /api/resilience/model-cooldowns` con le intestazioni di autenticazione per la gestione

### Connessione al provider Command Code non riuscita con errore 403

**Sintomi:**

- Errore 403 durante il test della connessione al provider Command Code
- La scheda del provider mostra "unauthorized" dopo una nuova aggiunta

**Causa:** Il flusso OAuth non è stato completato (callback non ricevuto o token non salvato).

**Soluzione:**

- Esegui `omniroute providers` dalla CLI per avviare nuovamente il flusso OAuth, oppure
- Esegui nuovamente OAuth da **Dashboard → Provider → Command Code → Riconnetti**

### ModelScope restituisce cooldown 429 aggressivi

**Sintomi:**

- Cooldown molto brevi o immediati su ModelScope dopo un numero ridotto di richieste ravvicinate
- Il routing combinato ignora ModelScope prima del previsto

**Causa:** ModelScope invia intestazioni `Retry-After` specifiche del provider. v3.8.0 include una gestione dedicata per tali intestazioni, pertanto le versioni precedenti le interpretano erroneamente come indicazioni generiche sui limiti di frequenza.

**Soluzione:**

- Assicurati di utilizzare v3.8.0 o una versione successiva
- Verifica che l'opzione `useUpstream429BreakerHints` sia abilitata in **Impostazioni → Resilienza**

### OMNIROUTE_WS_BRIDGE_SECRET mancante in produzione

**Sintomi:**

- Errore 401 per ogni richiesta al bridge WebSocket Codex/Responses durante l'esecuzione su un host di produzione remoto
- L'handshake del bridge WebSocket si chiude immediatamente dopo la connessione

**Causa:** La variabile di ambiente `OMNIROUTE_WS_BRIDGE_SECRET` non è presente nell'ambiente di produzione.

**Soluzione:**

1. Genera un segreto casuale: `openssl rand -hex 32`
2. Imposta `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` nell'ambiente del server di produzione (e in qualsiasi client che comunica con il bridge)
3. Riavvia OmniRoute

### Responses API: modalità in background degradata a sincrona

**Sintomi:**

- Avviso registrato: `background mode degraded to synchronous`
- Una richiesta `background: true` restituisce una normale risposta sincrona anziché un handle per un'attività in background

**Causa:** v3.8.0 degrada intenzionalmente `background: true` nelle Responses API all'esecuzione sincrona, generando al contempo un avviso. L'esecuzione asincrona completa in background è prevista per il futuro.

**Soluzione:**

- Modifica il client affinché esegua la chiamata senza `background`, oppure
- Attendi una versione successiva che includa la modalità asincrona completa in background (segui il changelog)

## Avvio lento / Timeout di disponibilità

Se la CLI visualizza `⚠ Server did not respond within 60s`, ma il server
funziona correttamente, il tempo massimo del controllo di disponibilità è troppo breve per il tuo ambiente.

Questo accade comunemente su Windows (antivirus, monitoraggio del filesystem) o nei container
con carichi di lavoro elevati durante l'avvio.

**Soluzione — aumenta il tempo massimo:**

```bash
# Tramite variabile di ambiente (rimane valida tra gli avvii):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuti
omniroute serve

# Tramite opzione della CLI (una tantum):
omniroute serve --ready-timeout 180000
```

Il valore predefinito è 60 000 ms (60 s). L'avviso è solo informativo; il server
continua ad avviarsi in background e sarà raggiungibile una volta completato l'avvio.

Consulta [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) per tutti
i dettagli su `OMNIROUTE_READY_TIMEOUT_MS`.
