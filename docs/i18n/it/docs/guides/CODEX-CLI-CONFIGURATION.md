Guida completa per utilizzare Codex CLI configurato affinché usi OmniRoute come backend compatibile con OpenAI.

---

> **TOML è l'unico formato effettivamente supportato.** Le versioni moderne di Codex leggono
> esclusivamente `~/.codex/config.toml` (verificato con codex-cli 0.147.0: `codex --help`
> documenta che le impostazioni specificate con `-c/--config` sostituiscono quelle
> "caricate da `~/.codex/config.toml`"). Il vecchio `~/.codex/config.yaml`
> apparteneva alla CLI npm precedente e viene ignorato silenziosamente.
> Il generatore della dashboard (`/api/cli-tools/apply`, strumento `codex`) scrive il TOML
> eseguendo un'unione conservativa: le chiavi esistenti e i blocchi degli altri provider
> vengono mantenuti, la chiave API rimane in `OMNIROUTE_API_KEY` (mai nel file) e
> l'eventuale file `config.yaml` residuo viene segnalato in una nota di migrazione senza
> essere modificato.

## config.toml pronto da incollare

Sostituisci `<YOUR_HOST>` e `<YOUR_KEY>` con i tuoi valori:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # limite di archiviazione nella cronologia per ogni chiamata allo strumento

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc o ~/.zshrc — valore effettivo della chiave, mai in config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex incluso nell'app ChatGPT

Se hai installato Codex tramite l'app desktop ChatGPT, il binario `codex` potrebbe
esistere soltanto all'interno del bundle dell'app e non essere ancora presente nel
`PATH` della shell. Aggiungi la directory delle risorse al file di avvio della shell:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Apri una nuova shell, quindi verifica:

```bash
command -v codex
codex --version
```

### OmniRoute locale senza autenticazione: è sufficiente una chiave segnaposto

Codex verifica che la variabile d'ambiente indicata da `env_key` esista
**prima** che la prima richiesta venga inviata dalla CLI. Se la tua istanza
**locale** di OmniRoute non richiede autenticazione, è sufficiente qualsiasi
segnaposto non vuoto:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Usa invece una chiave reale quando il tuo server OmniRoute è protetto o remoto.

> **Opzioni comuni per l'host**
>
> | Accesso     | URL                           |
> | ----------- | ----------------------------- |
> | Rete locale | `http://192.168.0.1:20128/v1` |
> | Tailscale   | `http://100.x.x.x:20128/v1`   |
> | Loopback    | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — perché funziona con tutti i modelli

Codex CLI ha deprecato `wire_api = "chat"` (Chat Completions) nel febbraio 2026 e ora **richiede** `wire_api = "responses"` (OpenAI Responses API). Impostare `wire_api = "chat"` causa un arresto anomalo immediato all'avvio a partire dalla versione v0.138.

Molti provider, inclusi GLM e Kimi, espongono ancora soltanto un endpoint Chat Completions. DeepSeek V4 ora espone sia un'API Responses nativa sia un endpoint compatibile con Anthropic; OmniRoute usa Responses per impostazione predefinita e consente a ogni connessione DeepSeek di selezionare la compatibilità con Anthropic.

**OmniRoute risolve tutto questo in modo trasparente:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute seleziona il protocollo nativo del provider ed esegue la traduzione quando necessario
    → POST /responses (DeepSeek V4) o /chat/completions (Mistral / GLM / Kimi / altri)
```

Quando usi OmniRoute, non hai mai bisogno di un proxy di traduzione separato. **Tutti i modelli usano `wire_api = "responses"`** — OmniRoute gestisce tutto il resto.

> **`wire_api` è il valore predefinito** — il campo assume automaticamente il valore `"responses"` e può essere omesso completamente da `config.toml`. Impostalo esplicitamente soltanto se vuoi documentarne l'intento.

## Finestra di contesto e compattazione

### Campi di configurazione dei token

| Campo                            | Descrizione                                                                                                                                                                                                                                                                 |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Budget totale di token per il modello attivo. Impostalo sul limite dichiarato del modello.                                                                                                                                                                                  |
| `model_auto_compact_token_limit` | Soglia che attiva la compattazione automatica della cronologia. **Massimo: 90% di `model_context_window`** — i valori superiori al 90% vengono ignorati senza alcun avviso.                                                                                                 |
| `tool_output_token_limit`        | Limite massimo dei token archiviati nella cronologia per ogni output di una chiamata a uno strumento. Impedisce che una singola risposta di grandi dimensioni riempia la finestra. **Non è il limite massimo dell'output** — è un limite di archiviazione nella cronologia. |
| `compact_prompt`                 | Sostituzione inline del prompt di sistema usato durante la compattazione (v0.138+).                                                                                                                                                                                         |

> **Nota su `model_max_output_tokens`**: questo campo **non fa parte dello schema di configurazione di Codex CLI** (è assente dal codebase Rust di Codex). Se impostato, viene ignorato senza alcun avviso. Non farvi affidamento — usa `tool_output_token_limit` per controllare la quantità di output degli strumenti archiviata nella cronologia.

## Prefisso del modello: `cx/`

Tutti i modelli Codex in OmniRoute utilizzano il prefisso `cx/`:

| Nome nella CLI Codex    | Modello OmniRoute  |
| ----------------------- | ------------------ |
| `cx/gpt-5.5`            | GPT-5.5 standard   |
| `cx/gpt-5.4`            | GPT-5.4 standard   |
| `cx/gpt-5.4-mini`       | GPT-5.4 mini       |
| `cx/gpt-5.1-codex-mini` | GPT-5.1 Codex mini |

Gli altri provider utilizzano il proprio prefisso (`kmc/`, `glm/`, `ds/`, `ollamacloud/`, `opencode-go/`, `mistral/`) — il prefisso corrisponde all'alias del provider OmniRoute.

## Impegno di ragionamento

Controlla quanto il modello "pensa" prima di rispondere.

| Valore   | Da utilizzare per                                      |
| -------- | ------------------------------------------------------ |
| `none`   | Nessun ragionamento — risposta diretta                 |
| `low`    | Attività banali (rinomina, formattazione)              |
| `medium` | **Valore predefinito del server** se non specificato   |
| `high`   | Attività intermedie (refactoring, debug)               |
| `xhigh`  | Architettura, analisi approfondita, problemi complessi |

```bash
# Override per singola invocazione
codex -c model_reasoning_effort=low "rinomina la variabile x in count"
codex -c model_reasoning_effort=xhigh "progetta il modulo di autenticazione"
```

Imposta anche un **riepilogo** del ragionamento affinché Desktop possa visualizzare il testo del processo di pensiero (non soltanto blob crittografati):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # oppure ultra, quando supportato
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### Budget di ragionamento OmniRoute (impostazione del server)

Sull'host OmniRoute, **Settings → AI → Thinking Budget** deve essere impostato su **`passthrough`** affinché l'impegno e il riepilogo di Codex raggiungano il servizio upstream. La modalità **`auto` rimuove** tutti i campi client `reasoning` / `reasoning_effort` e lascia vuoti i pannelli del processo di pensiero anche quando Codex è configurato correttamente.

Guida completa: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

La compressione e la cache dei prompt sono indipendenti e continuano a funzionare con `passthrough`.

## Profili — configurazioni denominate per modello/flusso di lavoro

I profili consentono di cambiare modello + finestra di contesto con un singolo flag. Ogni profilo è un file semplice
`~/.codex/<name>.config.toml` che viene sovrapposto al file `config.toml` di base.

> **Regola di denominazione (Codex CLI v0.137+):** il file deve essere `~/.codex/<name>.config.toml` — **senza il prefisso `profile-`**.
> La CLI risolve `-p kimi-k27` in `~/.codex/kimi-k27.config.toml`. Se il file non viene trovato, viene applicata silenziosamente la configurazione predefinita.

```bash
codex --profile kimi-k27 "analizza 10.000 righe di questa base di codice"
codex -p glm52 "revisione dell'architettura"
codex --profile deepseek-flash "rinomina la variabile"   # veloce, economico
```

### Profili di impegno (stesso modello, impegno diverso)

```bash
codex -p low      # cx/gpt-5.5, impegno=low
codex -p medium   # cx/gpt-5.5, impegno=medium
codex -p high     # cx/gpt-5.5, impegno=high
codex -p xhigh    # cx/gpt-5.5, impegno=xhigh (predefinito)
codex -p chat     # cx/gpt-5.5, nessun impegno impostato (valore predefinito del server)
```

## Generazione automatica dei profili con `omniroute setup-codex`

Se esegui OmniRoute su un VPS, puoi generare automaticamente i file dei profili dal catalogo dei modelli attivo:

```bash
# Da un VPS (usa OmniRoute locale sulla porta 20128)
omniroute setup-codex

# Da qualsiasi macchina — punta al tuo VPS
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Anteprima senza scrivere file
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Genera solo i profili GLM e Kimi
omniroute setup-codex --only glm,kimi

# Scrive in una directory personalizzata
omniroute setup-codex --codex-home /path/to/.codex
```

Il comando recupera `/v1/models`, usa profili ottimizzati per i modelli noti, ricorre ai metadati del catalogo per gli altri modelli di testo compatibili e scrive `~/.codex/<name>.config.toml` per ciascuno. È idempotente, quindi può essere rieseguito in sicurezza.

OmniRoute può anche **sincronizzare automaticamente** gli stessi file dei profili dopo che il rilevamento o l'importazione dei modelli di un provider modifica correttamente il catalogo attivo. Questa funzionalità è **facoltativa e disattivata per impostazione predefinita**: attivala dalla **dashboard CLI Code** ("Sincronizzazione automatica dei profili CLI" → Codex), oppure imposta `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (rispetta anche `CLI_ALLOW_CONFIG_WRITES`, attivo per impostazione predefinita). Quando è abilitata, scrive soltanto file di profilo separati in `~/.codex/*.config.toml`; non modifica mai il file attivo/predefinito `~/.codex/config.toml`, le impostazioni di Codex-lb, l'autenticazione o la selezione del provider.

## Avvio di Codex con `omniroute launch-codex`

Verifica lo stato della tua istanza OmniRoute prima di avviare Codex:

```bash
# Avvia usando OmniRoute locale (porta predefinita 20128)
omniroute launch-codex

# Avvia con un profilo specifico
```

## Attività di lunga durata

Due impostazioni predefinite di OmniRoute possono compromettere silenziosamente le sessioni di Codex CLI che durano diverse ore. Nessuna delle due è un'impostazione di Codex CLI: entrambe si trovano sul lato OmniRoute. Gli utenti che migrano una configurazione da proxy upstream che vincolano gli account e disabilitano i limiti di inattività spesso si imbattono in entrambi i problemi e concludono che OmniRoute «non è in grado di sostenere una sessione lunga».

| Sintomo                                                                                                | Causa probabile                                                                       | Impostazione             |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- | ------------------------ |
| La sessione continua a cambiare account / la continuità della cache dei prompt viene persa tra i turni | Il TTL dell'affinità di sessione è `0` (disabilitata)                                 | `sessionAffinityTtlMs`   |
| La connessione si interrompe durante il ragionamento senza alcun prompt visibile al client             | Il watchdog di inattività dello stream è scattato dopo 10 minuti senza chunk upstream | `STREAM_IDLE_TIMEOUT_MS` |

Discussioni correlate: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (interruzioni delle attività lunghe), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (perché l'affinità è disabilitata per impostazione predefinita). Monitoraggio: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Affinità di sessione — vincolare una conversazione a un account

**Valore predefinito:** `sessionAffinityTtlMs = 0` (disabilitata).

**Dove configurarla**

- Dashboard → **Impostazioni → Instradamento** → **Affinità di sessione** → **TTL dell'affinità (secondi)** (`ComboDefaultsTab`)
- Oppure applicare una PATCH alle impostazioni con `sessionAffinityTtlMs` in **millisecondi** (intervallo Zod `0`–`86_400_000`, ovvero fino a 24 ore)

> Rinominata nella #7274 dalla chiave esclusiva di Codex `codexSessionAffinityTtlMs`. La chiave precedente è ancora accettata come alias di sola lettura; le nuove configurazioni devono utilizzare `sessionAffinityTtlMs`. Ora l'affinità si applica a **qualsiasi** provider quando il TTL è superiore a `0`, non soltanto a Codex — vedere [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Affinità di sessione.

**Cosa non funziona quando rimane impostata su 0**

Ogni turno di una conversazione Codex con più turni viene instradato indipendentemente dalla strategia combinata attiva e può finire su un **account diverso a ogni turno**. Ciò interrompe la continuità della sessione upstream / della cache dei prompt. OmniRoute consulta gli header di sessione di Codex (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) e i campi del corpo come `prompt_cache_key` / `session_id` soltanto quando il TTL è maggiore di `0` (`extractSessionAffinityKey` in `src/sse/services/auth.ts`).

**Impostazione consigliata per una singola attività di più ore**

Impostare il TTL su un valore **superiore alla durata prevista dell'attività in tempo reale** (il massimo nell'interfaccia utente è **86400 secondi** = 24 ore):

| Durata prevista dell'attività | TTL dell'affinità (interfaccia, secondi) | `sessionAffinityTtlMs` |
| ----------------------------- | ---------------------------------------- | ---------------------- |
| Alcune ore                    | `14400` (4 ore)                          | `14400000`             |
| Tutta la notte / ~12 ore      | `43200` (12 ore)                         | `43200000`             |
| Giornata intera               | `86400` (24 ore, massimo)                | `86400000`             |

L'attivazione esplicita è intenzionale: disabilitare l'affinità favorisce il bilanciamento del carico tra gli account; abilitarla favorisce la continuità di una singola sessione prolungata dell'agente. Questa guida **non** modifica il valore predefinito: gli operatori che eseguono attività Codex di lunga durata devono attivarla esplicitamente.

### 2. Timeout di inattività dello stream — non interrompere i turni di ragionamento silenziosi

**Valore predefinito:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 minuti). Se non è impostato, eredita il valore da `REQUEST_TIMEOUT_MS`; anche il valore di base condiviso è 600000. Vedere [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Timeout.

**Cosa non funziona con il valore predefinito**

Un turno di reasoning / uso strumenti di Codex che rimane silenzioso per più di 10 minuti **senza alcun vero chunk upstream** viene chiuso forzatamente dal watchdog di inattività SSE (`open-sse/utils/stream.ts`). Il client spesso rileva soltanto un'interruzione della connessione, coerente con il comportamento “interrotto automaticamente senza alcuna notifica”.

Dettaglio fondamentale: l'**heartbeat SSE sintetico** di OmniRoute non reimposta il timer di inattività. Solo un vero chunk del corpo upstream aggiorna `lastChunkTime`. Dal punto di vista del watchdog, un modello silenzioso che sta ancora “ragionando” è indistinguibile da un upstream bloccato.

Inattività del corpo Undici correlata: `FETCH_BODY_TIMEOUT_MS` (anche questo valore predefinito corrisponde alla stessa soglia di base di 10 minuti; `0` lo disabilita). Per lo streaming, `FETCH_TIMEOUT_MS` copre solo la configurazione della connessione / le prime intestazioni: una volta attivo lo stream, i blocchi sono gestiti da `STREAM_IDLE_TIMEOUT_MS` e `FETCH_BODY_TIMEOUT_MS`.

**Configurazione consigliata per una singola attività di più ore**

Nell'ambiente del processo OmniRoute (`.env` / compose / systemd):

```bash
# Disabilita i timeout di inattività dello stream e del corpo per i turni di reasoning lunghi
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

In alternativa, impostali su valori superiori al periodo di silenzio più lungo previsto (i valori sono espressi in millisecondi):

```bash
# Esempio: consenti fino a 2 ore di silenzio tra i chunk upstream
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Riavvia OmniRoute dopo aver modificato queste variabili di ambiente.

### Procedura concreta — attività Codex di più ore

1. **Fissa l'account:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12 ore) oppure `86400` (massimo 24 ore).
2. **Aumenta / disabilita i timeout di inattività** nell'ambiente di OmniRoute:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Mantieni il consueto `config.toml` di Codex (`wire_api = "responses"`, `base_url` corretto, `OMNIROUTE_API_KEY`): non esistono impostazioni lato Codex per l'affinità o l'inattività relative a questi due comportamenti.
4. Riavvia OmniRoute, quindi avvia l'attività Codex di lunga durata.

### Decisione sui valori predefiniti (#7287)

| Impostazione             | Valore predefinito distribuito | Modificarlo in questa guida?                                                                             |
| ------------------------ | ------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (disattivato)              | **No** — rimane facoltativo (bilanciamento del carico rispetto alla continuità; vedi Discussione #5718)  |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 min)              | **No** — rimane a 10 minuti per il traffico generale; gli operatori Codex lo aumentano o lo disabilitano |

Modificare globalmente uno dei due valori predefiniti cambierebbe il comportamento per ogni client di un'istanza, non solo per Codex. Documenta le impostazioni; lascia invariati i valori predefiniti finché una decisione esplicita dell'operatore non stabilisce diversamente.

### Diagnosi delle interruzioni per inattività

Quando si attiva il watchdog di inattività, OmniRoute registra una riga con questa struttura:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Cerca con grep `Idle timeout: no data from` (oppure il codice `stream_idle_timeout` / il nome dell'errore `StreamIdleTimeoutError`). Il segmento del provider corrisponde a quello usato da OmniRoute per la richiesta (`codex`, un altro ID provider oppure `provider` se sconosciuto): non è sempre la stringa letterale `codex`.

## Risoluzione dei problemi

**`Error: wire_api = "chat" is no longer supported`**
Rimuovi `wire_api = "chat"` dalla configurazione. Imposta `wire_api = "responses"` oppure ometti il campo (il valore predefinito è `"responses"` dalla v0.138).

**`Error: model not found`**
Verifica che il modello esista in OmniRoute con il prefisso corretto. Usa `omniroute models list` oppure apri `/dashboard/providers/<provider>`.

**`Authentication error`**
Verifica che `OMNIROUTE_API_KEY` sia esportata: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex verifica che la variabile di ambiente esista prima di effettuare la prima richiesta. Esporta
una chiave reale per i server protetti oppure un segnaposto non vuoto, ad esempio
`OMNIROUTE_API_KEY=local`, quando la tua istanza OmniRoute **locale** non
richiede autenticazione. Riavvia la shell se l'hai aggiunta a `~/.bashrc` o `~/.zshrc`.

**`Connection refused`**
Verifica che OmniRoute sia in esecuzione e che l'host/la porta di `base_url` siano corretti per la tua rete (locale, Tailscale o VPS).

**La sessione si arresta in modo anomalo vicino al limite di contesto**
Imposta esplicitamente `model_context_window` e `model_auto_compact_token_limit`. Consulta la tabella della finestra di contesto riportata sopra.

**La compattazione viene avviata troppo tardi**
Riduci `model_auto_compact_token_limit` all'80–85% della finestra. Non impostarlo mai oltre il 90%.

**Il profilo non viene caricato (`-p <name>` viene ignorato senza alcun messaggio)**
Verifica che il file esista in `~/.codex/<name>.config.toml` (senza il prefisso `profile-`). Esegui `ls ~/.codex/*.config.toml`.

**Un'attività Codex di lunga durata si interrompe durante l'esecuzione / cambia account tra un turno e l'altro**
Consulta [Attività di lunga durata](#long-running-tasks). Abilita l'affinità di sessione (con un TTL superiore alla durata dell'attività) e aumenta o disabilita `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`. Cerca nei log di OmniRoute con grep la stringa `Idle timeout: no data from`.
