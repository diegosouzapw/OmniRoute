> **TL;DR**: `open-sse/` è il motore di streaming principale che gestisce ogni richiesta LLM in OmniRoute. Contiene circa 1.400 file che implementano la pipeline delle richieste, gli executor, i servizi, il server MCP e il livello di traduzione. Questa guida spiega come i vari componenti si integrano tra loro.

**Origine:** `open-sse/` (pacchetto del workspace, circa 1.440 file `.ts` non di test)

---

## Perché un pacchetto workspace separato?

`open-sse/` è un **workspace autonomo** nel monorepo di OmniRoute per diversi motivi:

1. **Riutilizzabilità** — `open-sse` viene pubblicato come `@omniroute/open-sse` su npm, quindi può essere utilizzato in modo indipendente da altri progetti
2. **Confini ben definiti** — il motore di streaming è disaccoppiato dal livello UI/DB specifico di OmniRoute
3. **Prestazioni** — il motore non ha dipendenze da Next.js, consentendo avvii a freddo più rapidi nei contesti CLI/serverless
4. **Controllo delle versioni** — `open-sse` può pubblicare nuove versioni secondo una propria cadenza

```json
// package.json
"workspaces": ["open-sse"]
```

## La pipeline delle richieste

Ogni richiesta LLM attraversa una **pipeline in 5 fasi**:

```
                              ┌──────────────┐
   Richiesta HTTP              │  1. ROUTING  │   risoluzione delle combo, selezione del modello
   (route Next.js)             └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │ 2. TRADUZIONE│   conversione del formato (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │ 3. ESECUZIONE│   executor del provider, HTTP, tentativi, circuit breaker
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │ 4. STREAMING │   trasformazione SSE, backpressure
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │5. REGISTRAZ. │   monitoraggio utilizzo, log chiamate, classificazione errori
                              └──────┬───────┘
                                     │
                                     ▼
                              Risposta HTTP (SSE o JSON)
```

### Fase 1: Routing (services/combo.ts)

**Punto di ingresso**: `handleComboChat()` in `services/combo.ts`

Risolve la richiesta in una tupla concreta `(provider, model, account, credentials)`:

- Cerca la combo in base all'ID (oppure crea una combo virtuale per i modelli `auto/*`)
- Applica la strategia di routing (priorità, ponderata, round-robin, ecc.)
- Esclude i provider non operativi (circuit breaker)
- Seleziona il successivo target utilizzabile

Per i modelli `auto/*`, questa fase inoltre:

- Esegue l'algoritmo di **valutazione basato su 16 fattori** (`services/autoCombo/`)
- Seleziona una coppia `provider+model` in base a stato operativo, costo, latenza, ecc.

### Fase 2: Traduzione (translator/)

Se il formato di origine (ad esempio, OpenAI) è diverso dal formato di destinazione (ad esempio, Claude), la richiesta viene **tradotta**:

- Prompt di sistema → messaggio di sistema
- Definizioni degli strumenti → formato degli strumenti specifico del provider
- Parametri di ragionamento/pensiero → equivalenti specifici del provider
- Normalizzazione del ruolo dei messaggi (`developer` → `system` per i provider diversi da OpenAI)

`translator/index.ts` espone:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Fase 3: Esecuzione (executors/)

**Punto di ingresso**: `getExecutor(providerId).execute(request, options)`

Tutti i provider utilizzano `DefaultExecutor` (`executors/default.ts`) tramite il fallback della factory `getExecutor()`. L'executor:

- Costruisce l'URL upstream (`buildUrl()`)
- Aggiunge gli header specifici del provider (`buildHeaders()`)
- Trasforma il corpo della richiesta (`transformRequest()`)
- Invia la richiesta HTTP con nuovi tentativi e backoff esponenziale
- Gestisce l'aggiornamento dell'autenticazione, se necessario (provider OAuth)

Tutti gli executor estendono `BaseExecutor` (`executors/base.ts`, 1170 LOC), che fornisce:

- Logica comune per i nuovi tentativi
- Integrazione con il proxy
- Integrazione con il circuit breaker
- Hook per la registrazione dell'utilizzo

### Fase 4: Streaming (utils/stream.ts)

Per le risposte in streaming, l'executor restituisce un **ReadableStream**. Il gestore:

- Esegue il piping attraverso una trasformazione SSE (`createSSETransformStreamWithLogger`)
- Applica ping heartbeat per rilevare le connessioni interrotte
- Gestisce correttamente la disconnessione del client (`pipeWithDisconnect`)
- Trasforma SSE → JSON per i client non in streaming

Per le risposte non in streaming, l'executor restituisce un oggetto JSON analizzato che viene inoltrato senza modifiche.

### Fase 5: Registrazione (services/usage.ts)

Dopo la risposta (con esito positivo o negativo), vengono registrati i dati di utilizzo:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` dalla risposta
- `cost_usd` calcolato in base ai dati sui prezzi
- `latency_ms`, `status`, `error_class` in caso di errore
- Persistiti nella tabella `usage_history`

Gli artefatti dei log delle chiamate (se abilitati) vengono scritti in `${DATA_DIR}/call_logs/`.

## Analisi approfondita dei file chiave

### chatCore.ts (5977 righe)

Il **gestore principale delle richieste**. Nonostante le dimensioni, presenta una struttura chiara:

```ts
// Pseudo-struttura di chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Autenticazione + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Validazione del corpo
  const body = await parseRequestBody(request);

  // 3. Rilevamento del formato + traduzione
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Instradamento della combo
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continua con il target successivo
    }
  }

  // 5. Fallback di emergenza
  return await emergencyFallback(body);
}
```

Nonostante sia un'unica funzione gigantesca, è organizzata in **sezioni commentate** che corrispondono alla pipeline in 5 fasi.

### combo.ts (4456 LOC)

Il **motore di instradamento** che risolve una combo in una sequenza ordinata di target.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

Supporta **19 strategie di instradamento** (vedere `src/shared/constants/routingStrategies.ts`):

| Strategia           | Comportamento                                                                             |
| ------------------- | ----------------------------------------------------------------------------------------- |
| `priority`          | Elenco ordinato a partire dal primo target                                                |
| `weighted`          | Selezione probabilistica in base al peso di ciascun target                                |
| `round-robin`       | Scorre ciclicamente i target in ordine                                                    |
| `context-relay`     | Trasferisce il contesto tra i target                                                      |
| `fill-first`        | Esaurisce la quota prima di passare al target successivo                                  |
| `p2c`               | Potenza di due scelte                                                                     |
| `random`            | Selezione casuale uniforme                                                                |
| `least-used`        | Sceglie quello con meno utilizzi recenti                                                  |
| `cost-optimized`    | Prima il target integro meno costoso                                                      |
| `reset-aware`       | Tiene conto delle finestre di azzeramento del provider                                    |
| `reset-window`      | Instradamento basato sulla finestra di azzeramento                                        |
| `headroom`          | Prima il target con il maggior margine di quota residua                                   |
| `strict-random`     | Davvero uniforme (senza ponderazione della qualità)                                       |
| `auto`              | Utilizza un punteggio basato su 16 fattori (`autoCombo/`)                                 |
| `lkgp`              | Prima l'ultimo provider noto come funzionante                                             |
| `context-optimized` | Ideale per le richieste con contesto esteso                                               |
| `fusion`            | Distribuisce in parallelo a un gruppo, quindi sintetizza tramite un giudice (`fusion.ts`) |

### base.ts (1170 LOC)

L'**esecutore astratto** esteso da tutti i 107 esecutori. Contiene:

- `buildUrl()` — costruzione predefinita dell'URL (le sottoclassi la sovrascrivono per una costruzione personalizzata)
- `buildHeaders()` — intestazioni predefinite (autenticazione, content-type)
- `transformRequest()` — pass-through per impostazione predefinita
- `execute()` — il ciclo HTTP principale con tentativi, backoff e circuit breaker

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Gestisce tutti i provider compatibili con OpenAI/Anthropic
  // I provider registrano le configurazioni (URL, autenticazione, intestazioni), ma condividono la logica dell'esecutore
}
```

Il comportamento specifico del provider (intestazioni di autenticazione, URL di base, intestazioni di versione) viene configurato tramite il registro dei provider, non mediante classi di esecutori separate.

## Executor (oltre 75 file)

Un file per provider. Estendono tutti `BaseExecutor` ed eseguono l'override degli elementi differenti.

### Schemi comuni

I provider vengono risolti tramite `getExecutor(providerId)`, che restituisce l'executor configurato. I provider compatibili con OpenAI/Anthropic utilizzano `DefaultExecutor` (`executors/default.ts`). Il comportamento specifico del provider (URL di base, header di autenticazione, versione dell'API) viene configurato in `open-sse/config/providers/`, mentre le trasformazioni del corpo della richiesta vengono gestite in `open-sse/translator/`.

L'**URL personalizzato** viene impostato tramite la configurazione del provider:

```ts
// Configurazione del provider in open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

L'**autenticazione personalizzata** viene gestita tramite la configurazione di autenticazione del registro dei provider (chiave API, OAuth, profili degli header).

Le trasformazioni personalizzate del **corpo della richiesta** (ad esempio, Anthropic che separa `system` da `messages`) vengono registrate per ciascun provider in `open-sse/translator/`.

````

### La factory degli executor

`executors/index.ts` esporta `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

La risoluzione avviene tramite `ExecutorRegistry` (`executors/registry.ts`): ogni executor specializzato viene dichiarato nella tabella integrata di `executors/index.ts` e registrato tramite `registerExecutor(alias, instance)` al caricamento del modulo; `getExecutor()` consulta il registro e utilizza come fallback un `DefaultExecutor` memorizzato per qualsiasi provider privo di una voce specializzata. La mappatura completa alias → executor è definita dal golden test `tests/unit/executor-map-golden.test.ts`.

## Traduttori

Traduce tra **3 formati**: OpenAI, Anthropic, Gemini, oltre alla nuova Responses API.

### Quando avviene la traduzione

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Traduzioni comuni:

- `OpenAI → Anthropic`: campo `system` separato, intestazione `x-api-key`
- `OpenAI → Gemini`: `contents` al posto di `messages`, `systemInstruction`
- `OpenAI → Responses API`: array `input`, stato `previous_response_id`

### Casi limite gestiti

- Ruolo `developer` → `system` per provider diversi da OpenAI
- Ruolo `system` → unito al primo messaggio utente per GLM/ERNIE
- `json_schema` → `responseMimeType` + `responseSchema` di Gemini
- `tools` → formato degli strumenti specifico del provider
- Parametri di ragionamento (o1, Claude) → equivalenti specifici del provider

## Server MCP

`open-sse/mcp-server/` implementa il server **Model Context Protocol**:

- **110 strumenti** (gestione dei provider, combinazioni, memoria, cache, compressione, proxy, competenze, gamification, plugin, Notion, Obsidian, corpus locale)
- **3 trasporti**: stdio, SSE, Streamable HTTP
- **33 ambiti** per un'autorizzazione granulare

### Registrazione degli strumenti

Gli strumenti sono registrati come file autonomi in `open-sse/mcp-server/tools/`; ciascuno esporta un nome, uno schema, un gestore e un ambito:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Trasporti

```ts
// stdio (utilizzo tramite CLI)
startMcpStdio(server);

// SSE (streaming basato su HTTP)
startMcpSse(server, port);

// Streamable HTTP (MCP moderno)
startMcpStreamable(server, port);
```

### Autorizzazione

Ogni chiamata a uno strumento viene sottoposta a controlli degli ambiti (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Trasformatori

`open-sse/transformer/` converte tra i formati **Chat Completions** e **Responses API**.

### Perché un trasformatore separato?

La Responses API è il nuovo formato di OpenAI con **conversazioni con stato** (`previous_response_id`). Quando un client invia una richiesta Responses, OmniRoute:

1. Converte internamente Responses → Chat Completions
2. Invia la richiesta al provider (qualsiasi provider che supporti Chat Completions)
3. Converte nuovamente la risposta nel formato Responses
4. Trasmette in streaming al client la risposta convertita

Il trasformatore (`transformer/responsesTransformer.ts`) fornisce:

```ts
createResponsesApiTransformStream(): TransformStream
```

Questo gestisce:

- Eventi `response.output_item.added`
- Eventi `response.output_text.delta`
- Evento `response.completed`
- Mappatura delle chiamate agli strumenti (`function_call` ↔ `tool_calls`)

| ----------------------------- | ---------------------------------------------------------------- |
| `providerRegistry.ts`         | Registro dei modelli di chat basato sul catalogo di 352 provider |
| `providerModels.ts`           | Alias dei modelli, mappatura dei formati                         |
| `constants.ts`                | Timeout, limiti, codici di stato                                 |
| `defaultThinkingSignature.ts` | Firma di ragionamento predefinita di Claude                      |
| `modelStrip.ts` (nei servizi) | Rimozione dei campi specifica per provider                       |

### Schema del registro dei provider

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

La convalida Zod al caricamento del modulo garantisce che tutte le configurazioni dei provider siano valide.

## Vincoli di prestazione

Il motore di routing ha budget prestazionali rigorosi:

| Operazione                                                | Obiettivo | Misurazione                                        |
| --------------------------------------------------------- | --------- | -------------------------------------------------- |
| Risoluzione delle combinazioni                            | <10ms     | Per 50 destinazioni                                |
| Controllo del limite di frequenza                         | <1ms      | Token bucket in memoria                            |
| Fallback della famiglia di modelli                        | <5ms      | Definizioni delle famiglie memorizzate nella cache |
| Dispatch del routing delle richieste                      | <2ms      | Percorso critico                                   |
| **Nessun I/O bloccante nel percorso critico del routing** | —         | Tutto asincrono                                    |

---

## Anti-pattern

❌ **Chiamate sincrone al DB in `combo.ts`** — precalcolare e memorizzare nella cache
❌ **Logica di nuovo tentativo negli handler** — usare `retry()` dal servizio di resilienza
❌ **Accesso diretto alla configurazione del provider** — usare i getter di `providerRegistry`
❌ **Catene di fallback codificate direttamente** — definirle in `modelFamilyFallback.ts`
❌ **Mutazioni dello stato tra richieste concorrenti** — usare solo il contesto specifico della richiesta

## Aggiunta di un nuovo componente

### Aggiunta di un nuovo servizio

1. Creare `open-sse/services/[serviceName].ts` con una responsabilità specifica
2. Esportare la funzione handler principale ed eventuali costanti
3. Aggiungere test unitari in `tests/unit/services/[serviceName].test.mjs`
4. Integrare nella pipeline delle richieste in `handlers/chatCore.ts` (se correlato al routing)
5. Aggiornare la logica di routing in `combo.ts` se il servizio influisce sulla selezione delle destinazioni
6. Documentare in questo file

### Aggiunta di un nuovo executor

1. Creare `open-sse/executors/[provider].ts` estendendo `BaseExecutor`
2. Registrare in `config/providerRegistry.ts`
3. Aggiungere alla factory `executors/index.ts`
4. Aggiungere test unitari per l'executor
5. Documentare in `docs/architecture/ARCHITECTURE.md`

### Aggiunta di un nuovo strumento MCP

1. Creare o aggiornare `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definire lo schema Zod per gli input
3. Registrare lo strumento in `mcp-server/index.ts`
4. Aggiungere alla matrice degli ambiti in `mcp-server/auth/`
5. Aggiungere test unitari
