AgentBridge è il proxy MITM (Man-in-the-Middle) di OmniRoute che intercetta il traffico HTTPS degli agenti IA degli IDE e lo reindirizza attraverso il motore di routing unificato di OmniRoute. Supporta **10 agenti IDE** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code e Trae (in fase di valutazione) — rendendo OmniRoute il proxy MITM con la più ampia copertura sul mercato per gli assistenti di programmazione basati sull'IA.

**Posizione nella dashboard:** `/dashboard/tools/agent-bridge`
**Gruppo nella barra laterale:** Strumenti (dopo Cloud Agents)
**Vedi anche:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — monitora in tempo reale tutto il traffico intercettato; `docs/security/MITM-TPROXY-DECRYPT.md` (git; non incluso nella compilazione di `/docs`) — la modalità di acquisizione Linux TPROXY con decrittazione trasparente, gestita dalla route `/api/tools/agent-bridge/tproxy`.

## §1 Panoramica

### Che cos'è AgentBridge?

Quando un agente IDE (ad es. GitHub Copilot, Cursor, Claude Code) effettua una chiamata API, si connette direttamente al provider IA upstream (OpenAI, Anthropic, ecc.). AgentBridge intercetta la connessione in modo trasparente a livello TLS — senza richiedere alcuna modifica alla configurazione dell'agente — e riscrive la richiesta instradandola attraverso OmniRoute.

Ciò consente di:

- **Reindirizzare qualsiasi agente verso qualsiasi provider**: Copilot comunica con OpenAI? Reindirizzalo ad Anthropic Claude, Gemini o a uno qualsiasi dei 352 provider di OmniRoute.
- **Applicare mappature dei modelli**: `gemini-3-flash` → `claude-sonnet-4.7` in modo trasparente a livello di handler.
- **Osservare tutto il traffico degli agenti**: ogni richiesta intercettata viene pubblicata nel [Traffic Inspector](./TRAFFIC_INSPECTOR.md).
- **Applicare la resilienza di OmniRoute**: il routing combinato, i circuit breaker, i fallback e il monitoraggio dei costi funzionano anche per il traffico degli agenti IDE.

## §2 Architettura

### 2.1 Panoramica dei componenti

```
Agente IDE (VS Code / Cursor / ecc.)
    │  HTTPS (porta 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← reindirizzamento DNS
    │
    ▼
src/mitm/server.cjs  (porta 443, processo figlio CJS)
    │  risolve la destinazione tramite l'SNI dell'header Host
    │  genera un certificato TLS per ogni SNI firmato dalla CA di AgentBridge
    ├── Corrispondenza nella lista di bypass? → passthrough TCP (senza decifratura)
    ├── Corrispondenza con una destinazione? → fetch → router OmniRoute (porta 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() sul corpo/sugli header della richiesta
    │               ├── TrafficBuffer.push() — pubblica in Traffic Inspector
    │               └── fetchRouter() → /v1/chat/completions
    └── Nessuna corrispondenza? → passthrough TCP (senza decifratura)
```

### 2.2 Server MITM (`src/mitm/server.cjs`)

Il server MITM principale viene eseguito come processo figlio CJS di Node.js (per evitare di riscrivere il codebase CJS esistente). Il server:

- Rimane in ascolto sulla porta 443 (richiede privilegi oppure `authbind`/`setcap`)
- Riceve tunnel CONNECT dal sistema operativo (tramite il reindirizzamento DNS in `/etc/hosts`)
- Genera certificati TLS per ogni SNI firmati dalla CA di AgentBridge (`DATA_DIR/mitm/ca.crt`)
- Risolve l'agente di destinazione tramite l'header Host usando il registro `targets/index.ts`
- Inoltra al livello handler TypeScript tramite HTTP all'indirizzo `http://127.0.0.1:20128`

`TARGET_HOSTS` viene caricato da `DATA_DIR/mitm/targets.json` (scritto da `targets/index.ts` all'avvio), consentendo aggiornamenti dinamici senza riavviare il server CJS.

> **Modello con CA radice (#6684).** La descrizione precedente dei certificati per SNI firmati da una CA
> fa riferimento al modello persistente con CA radice aggiunto in #6684 (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, che riutilizza la crittografia di CA/certificati foglia già
> collaudata per TPROXY in `src/mitm/tproxy/dynamicCert.ts`) — sostituisce il
> precedente singolo certificato foglia statico autofirmato (`src/mitm/cert/generate.ts`, ancora
> limitato esclusivamente agli host antigravity) indicato dalla presenza su disco di una coppia
> `server.crt`/`server.key`. **Comportamento della migrazione**: una nuova installazione (senza un
> `server.crt` precedente) adotta automaticamente il modello con CA radice; un'installazione che
> considera già attendibile il vecchio certificato foglia statico continua a utilizzarlo finché
> l'operatore non imposta `MITM_ROOT_CA_ENABLED=true` e riavvia il bridge
> (`src/mitm/cert/migration.ts` è la funzione decisionale pura — una CA MITM attendibile in grado
> di firmare un certificato foglia per **qualsiasi** host è sostanzialmente più potente del vecchio
> certificato foglia con SAN fissi, pertanto il passaggio non avviene mai in modo silenzioso per
> un'installazione già considerata attendibile). Il certificato della CA viene installato nello
> stesso slot `omniroute-mitm.crt` dell'archivio di attendibilità utilizzato dal vecchio certificato
> foglia (`cert/install.ts::installCaCert`) — non è necessaria alcuna pulizia della doppia attendibilità.

### 2.3 Handler di base (`src/mitm/handlers/base.ts`)

Tutti gli handler degli agenti estendono `MitmHandlerBase`:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // Helper protetti: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

Ogni handler chiama `hookBufferStart()` prima di eseguire il proxy e `hookBufferUpdate()` al completamento. Questi inseriscono voci `InterceptedRequest` in `globalTrafficBuffer` (vedere [Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4).

### 2.4 Registro delle destinazioni (`src/mitm/targets/`)

Ogni agente dispone di un file di destinazione dichiarativo:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

Il registro (`targets/index.ts`) esporta `ALL_TARGETS` e genera `DATA_DIR/mitm/targets.json` all'avvio.

### 2.5 Passthrough e lista di bypass (`src/mitm/passthrough.ts`)

**Lista di bypass** (verificata per prima, con precedenza sulla corrispondenza delle destinazioni):

- Modelli predefiniti: host bancari, `.gov.`, provider OAuth/SSO (Okta, Auth0), ecc.
- Modelli utente: archiviati nella tabella DB `agent_bridge_bypass`
- Gli host ignorati ricevono un tunnel TCP trasparente — TLS non viene **mai decifrato**

**Passthrough predefinito** (nessuna corrispondenza con una destinazione e host non presente nella lista di bypass):

- Riceve anch'esso un tunnel TCP — le connessioni non vengono mai interrotte
- Impedisce ad AgentBridge di interferire con il traffico HTTPS generale del sistema

Precedenza dell'instradamento:

```
lista di bypass → corrispondenza con una destinazione → passthrough
```

### 2.6 Certificato CA upstream (`src/mitm/upstreamTrust.ts`)

Per gli ambienti di rete aziendali con una CA personalizzata:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

Quando è impostata, configura il dispatcher globale di `undici` con il certificato CA aggiuntivo, consentendo ad AgentBridge di raggiungere i provider upstream attraverso proxy aziendali di terminazione TLS.

### 2.7 Mascheramento dei segreti (`src/mitm/maskSecrets.ts`)

Lo scanner clean-room indipendente viene applicato ai corpi delle richieste e agli header delle credenziali
**prima** che vengano inseriti nel buffer di Traffic Inspector o in qualsiasi log. Esegue un singolo passaggio lineare:

- Token con prefisso `sk-` / `ak-` / `pk-` (in stile OpenAI/Anthropic)
- Credenziali RFC 6750 `Authorization: Bearer <token>`, con precedenza dell'intero token
- Token opachi lunghi generici (≥40 caratteri), incluse le forme con punti e padding

`sanitizeHeaders()` converte in minuscolo i nomi conservati, unisce deterministicamente i valori degli array, elimina la
denylist condivisa degli header hop-by-hop/di framing (inclusa l'autenticazione proxy), oscura completamente `cookie` e
`set-cookie` e delega allo scanner i valori delle credenziali.

## §3 Configurazione

### 3.1 Avviare/arrestare il server MITM

Utilizzare la scheda AgentBridge Server all'indirizzo `/dashboard/tools/agent-bridge`:

| Azione                               | Descrizione                                                                                            |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| Avvia server                         | Avvia `src/mitm/server.cjs` sulla porta 443                                                            |
| Arresta server                       | Arresta correttamente il processo figlio                                                               |
| Riavvia server                       | Arresta + avvia (applica le modifiche alle destinazioni)                                               |
| Considera attendibile il certificato | Installa `DATA_DIR/mitm/ca.crt` nell'archivio certificati attendibili del sistema operativo            |
| Scarica certificato                  | Scarica `ca.crt` per l'installazione manuale                                                           |
| Rigenera certificato                 | Crea una nuova coppia di chiavi della CA (tutti i certificati esistenti per agente vengono invalidati) |

### 3.2 Considerare attendibile il certificato

Il certificato della CA AgentBridge deve essere considerato attendibile dal sistema operativo affinché gli IDE accettino la connessione MITM.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Portachiavi):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

In alternativa, utilizzare il pulsante "Considera attendibile il certificato" nella dashboard (esegue il comando appropriato per il sistema operativo, richiedendo sudo se necessario).

#### Gli IDE basati su Electron ignorano l'archivio certificati attendibili del sistema operativo (`NODE_EXTRA_CA_CERTS`)

Alcuni IDE — in particolare **Antigravity IDE** e altre applicazioni derivate da Electron / VS Code — includono
un proprio runtime Node.js che **non consulta l'archivio certificati attendibili del sistema operativo** per le richieste
`fetch`/HTTPS in uscita. Considerare attendibile la CA a livello di sistema operativo/NSS è sufficiente per il **backend**
nativo dell'IDE (ad esempio un server di linguaggio Go, che utilizza il bundle di CA del sistema operativo), ma il
**frontend Electron** continuerà a generare errori TLS, che si manifestano nell'app come _disconnessione dell'account_
o visualizzazione di un _"errore di connessione"_, anche se il log MITM mostra che le chiamate di bootstrap del backend
restituiscono `200`. Sono necessari due passaggi, entrambi importanti:

1. Indicare esplicitamente la CA al runtime:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **Avviare l'IDE da quella shell.** L'avvio dall'icona del desktop / Dock / menu Start
   **non** eredita le variabili esportate dalla shell e `~/.config/environment.d/*.conf` viene applicato solo dopo
   un nuovo accesso grafico. Chiudere completamente l'IDE prima di procedere: il blocco di istanza singola di Electron
   fa sì che un secondo avvio si limiti a portare in primo piano il processo esistente, ignorando il nuovo ambiente.

Il passaggio precedente relativo all'attendibilità nel sistema operativo + NSS resta necessario (lo stack di rete Chromium
utilizzato da alcuni flussi di autenticazione legge l'archivio NSS dell'utente e dispone di propri pin statici per
`*.googleapis.com`, che una CA considerata attendibile localmente sostituisce). `NODE_EXTRA_CA_CERTS` copre inoltre il
percorso `fetch` di Node.

### 3.3 Instradamento DNS

Per ogni agente da intercettare, i relativi host API devono risolversi in `127.0.0.1`. AgentBridge gestisce automaticamente le voci di `/etc/hosts` quando si attiva o disattiva il DNS di un agente nella procedura guidata di configurazione.

Esempio di voci `/etc/hosts` per GitHub Copilot:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 Mappatura dei modelli

Utilizzare la tabella di mappatura dei modelli nella scheda di ciascun agente per definire le mappature origine → destinazione:

| Modello di origine (nativo dell'agente) | Modello di destinazione (OmniRoute) |
| --------------------------------------- | ----------------------------------- |
| `gpt-4o`                                | `claude-sonnet-4.7`                 |
| `*` (carattere jolly)                   | `claude-haiku-4.7`                  |

Il carattere jolly `*` associa qualsiasi modello non riconosciuto alla destinazione specificata. Le mappature vengono salvate nella tabella `agent_bridge_mappings`.

> **Suggerimento — individuare gli ID reali dei modelli dell'agente.** Un IDE può inviare nomi di modelli diversi
> dalle etichette mostrate nell'interfaccia e che cambiano tra le versioni principali. Ad esempio, **Antigravity 2** invia
> `gemini-3.1-pro-low`, `gemini-pro-agent` e `gemini-3.1-flash-lite` via rete, anziché
> `gemini-2.5-pro` mostrato nella documentazione precedente. Inviare un messaggio di chat senza una mappatura corrispondente:
> il MITM registra il valore `model:` esatto in ingresso e inoltra la richiesta senza modificarla. Mappare quel valore letterale;
> la richiesta successiva verrà quindi intercettata e instradata verso la destinazione scelta.

### 3.5 Avviso sui rischi

AgentBridge intercetta le credenziali (token OAuth, chiavi API) utilizzate dall'IDE per autenticarsi presso i provider upstream. Tali credenziali vengono **mascherate prima della registrazione nei log** (vedere §2.7), ma sono visibili al livello MITM di OmniRoute. Alla prima attivazione di ciascun agente viene mostrata una finestra modale chiudibile con un avviso sui rischi.

### 3.6 Manutenzione e diagnostica

La dashboard include una scheda **Manutenzione e diagnostica** (`AgentBridgeMaintenanceCard`, in `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`) che espone le route MITM operative che in precedenza non disponevano di un'interfaccia utente. Il suo sottotitolo è: _"Verifica automaticamente la pipeline di acquisizione, annulla lo stato di sistema residuo e trasferisci la configurazione tra computer."_ Gli helper client della scheda si trovano in `src/lib/inspector/agentBridgeMaintenanceApi.ts`.

| Pulsante           | Route                                  | Funzione                                                                                                                                                                                                                                                |
| ------------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Diagnostica**    | `GET /api/tools/agent-bridge/diagnose` | Esegue l'autotest della pipeline di acquisizione e mostra un report per ogni controllo (✓/✗ + suggerimento per la risoluzione).                                                                                                                         |
| **Ripara**         | `POST /api/tools/agent-bridge/repair`  | Annulla lo stato di sistema MITM orfano (voci di spoofing DNS, CA radice, proxy di sistema) lasciato da un arresto anomalo o da SIGKILL. Idempotente: restituisce "Nulla da riparare" se lo stato è pulito.                                             |
| **Rimuovi CA**     | `DELETE /api/tools/agent-bridge/cert`  | Revoca l'attendibilità e rimuove la CA radice MITM dall'archivio attendibilità del sistema operativo (esplicito, idempotente). Viene mostrato solo quando la CA è attualmente considerata attendibile; richiede una conferma inline "Rimuovere la CA?". |
| **Esporta config** | `GET /api/tools/agent-bridge/config`   | Scarica il JSON di configurazione portatile (vedere §3.7).                                                                                                                                                                                              |
| **Importa config** | `POST /api/tools/agent-bridge/config`  | Carica un JSON di configurazione esportato in precedenza (vedere §3.7).                                                                                                                                                                                 |

**Controlli diagnostici** (`summarizeDiagnostics()` in `src/mitm/inspector/diagnostics.ts`). La route esegue il probe con effetti collaterali per ciascun controllo e passa i valori booleani al riepilogatore puro; vengono restituiti un singolo verdetto `healthy` e un suggerimento per ogni errore:

| Nome del controllo | Cosa verifica                                                                | Suggerimento in caso di errore                                                                                                                                                                       |
| ------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | Il processo del server MITM è attivo                                         | "Il server MITM non è in esecuzione. Avvialo dalla scheda AgentBridge."                                                                                                                              |
| `server-reachable` | Il server MITM accetta connessioni sulla propria porta (probe TCP)           | "Il server MITM non accetta connessioni sulla propria porta. Verifica che la porta sia libera e di disporre dei privilegi necessari per associarla."                                                 |
| `cert-exists`      | Il certificato MITM è stato generato su disco                                | "Non è stato ancora generato alcun certificato MITM. Generane uno dalla scheda AgentBridge."                                                                                                         |
| `cert-trusted`     | La CA radice MITM si trova nell'archivio attendibilità del sistema operativo | "La CA radice MITM non è considerata attendibile dall'archivio del sistema operativo, pertanto l'intercettazione TLS non riuscirà. Rendi attendibile il certificato dalla scheda AgentBridge."       |
| `dns-configured`   | I nomi host di destinazione vengono sottoposti a spoofing in `/etc/hosts`    | "I nomi host di destinazione non vengono sottoposti a spoofing in /etc/hosts, pertanto il traffico non raggiunge mai il proxy. Abilita il DNS per gli agenti di cui desideri acquisire il traffico." |

**Banner dello stato orfano:** quando la pagina rileva uno stato lasciato da un arresto anomalo (spoofing DNS / CA / proxy di sistema), la scheda mostra un banner color ambra — _"Una sessione precedente ha lasciato uno stato di sistema residuo (spoofing DNS, CA o proxy di sistema). Esegui Ripara per ripristinarlo."_ — ed evidenzia il pulsante **Ripara**. `Repair` è l'analogo a livello applicativo del flag `--cleanup` di ProxyBridge (delega a `repairMitm()` in `src/mitm/manager.ts`).

> La CA radice MITM rimane installata tra un arresto e un avvio per evitare richieste
> sudo ripetute (lo stesso comportamento di mitmproxy/Charles), pertanto la sua rimozione è un'azione
> esplicita **Rimuovi CA**, anziché qualcosa che avviene automaticamente all'arresto.

### 3.7 Importazione/esportazione della configurazione portatile

AgentBridge può serializzare lo stato **configurabile dall'operatore** in un blob JSON con versione, in modo che una configurazione possa essere replicata su più macchine. Il serializzatore è `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`), convalidato da `AgentBridgeConfigSchema`.

L'esportazione include esattamente tre elementi (i valori predefiniti integrati **NON** vengono intenzionalmente esportati, in modo che l'importazione non li duplichi né entri in conflitto con essi):

| Campo            | Origine                                                             | Note                                                                         |
| ---------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `bypassPatterns` | pattern di bypass definiti dall'utente (`agent_bridge_bypass`)      | i pattern predefiniti bank/gov/okta sono esclusi                             |
| `customHosts`    | host personalizzati di Traffic Inspector (`inspector_custom_hosts`) | ciascuno: `{ host, kind: "llm"\|"app"\|"custom", label? }`                   |
| `agentMappings`  | mapping dei modelli per agente (`agent_bridge_mappings`)            | `{ [agentId]: [{ source, target }] }` per ogni agente che dispone di mapping |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**Comportamento dell'importazione** (`POST /api/tools/agent-bridge/config`): i pattern di bypass e i mapping per agente vengono **sostituiti integralmente**; gli host personalizzati vengono aggiunti in modo **idempotente** (`INSERT OR IGNORE`). La risposta indica quanti elementi di ciascun tipo sono stati applicati:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

Cosa **NON** è presente nella configurazione: lo stato di esecuzione del server, i percorsi dei certificati, lo stato DNS di ciascun agente, il percorso della CA upstream e le impostazioni TPROXY — questi elementi costituiscono lo stato dell'host o di runtime, non preferenze trasferibili.

## §5 Sicurezza

### Regole rigide applicate

| Regola                                | Applicazione                                                                                                 |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **#12** `sanitizeErrorMessage`        | Tutti gli errori degli handler vengono sanificati prima della risposta o dell'inserimento nel buffer         |
| **#13** Passaggio dell'env alla shell | Le modifiche a `/etc/hosts` utilizzano l'opzione `env`, senza interpolazione di stringhe per i percorsi      |
| **#15 + #17** `isLocalOnlyPath()`     | `/api/tools/agent-bridge/` è LOCAL_ONLY + SPAWN_CAPABLE: il loopback viene imposto prima dell'autenticazione |

### Elenco di bypass per gli host sensibili

L'elenco di bypass garantisce che istituti finanziari, provider OAuth/SSO e altri host sensibili non vengano **mai decrittografati**. Il loro traffico TLS transita attraverso un tunnel TCP trasparente: OmniRoute non vede mai il testo in chiaro.

I pattern di bypass predefiniti includono:

- `*.bank.*`, `*.gov.*` (servizi finanziari/governativi)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/identità)
- `*.apple.com`, `*.icloud.com` (servizi di sistema Apple)

I pattern di bypass aggiunti dall'utente vengono memorizzati nella tabella `agent_bridge_bypass` e hanno la precedenza su tutto il resto.

### Mascheramento dei segreti

Viene applicata la funzione `maskSecrets()` di `src/mitm/maskSecrets.ts`:

- A ogni corpo della richiesta prima di `TrafficBuffer.push()`
- A ogni header prima della registrazione nei log o della trasmissione

Pattern: token con prefisso `sk-`/`ak-`/`pk-`, token `Bearer` e token generici di almeno 40 caratteri.

### Certificato CA upstream

Quando `AGENTBRIDGE_UPSTREAM_CA_CERT` è impostata, il file viene letto all'avvio. Se il percorso esiste ma il file non è leggibile, AgentBridge registra un errore chiaro e si rifiuta di avviarsi (evitando errori TLS silenziosi negli ambienti aziendali).

### Limitazioni note

- **La porta 443 richiede privilegi**: su Linux, AgentBridge richiede `setcap 'cap_net_bind_service=+ep'` sul binario Node oppure deve essere eseguito tramite `authbind`. La procedura guidata di configurazione mostra istruzioni specifiche per il sistema operativo.
- **È necessario riavviare l'IDE**: dopo il reindirizzamento DNS, l'IDE deve essere riavviato affinché la nuova risoluzione dell'host abbia effetto.
- **Token OAuth codificati direttamente**: alcuni agenti (Kiro, Antigravity) memorizzano localmente i token di aggiornamento OAuth. Questi sono trasparenti per AgentBridge: esso vede il token Bearer in ogni richiesta, che viene mascherato prima della registrazione nei log.
- **I frontend Electron richiedono `NODE_EXTRA_CA_CERTS`**: gli IDE il cui frontend viene eseguito in un runtime Node/Electron integrato ignorano l'archivio di attendibilità del sistema operativo/NSS e devono essere avviati da una shell con `NODE_EXTRA_CA_CERTS` impostata (vedere §3.2). Sintomo in caso di mancata configurazione: il backend dell'IDE si autentica (il MITM mostra risposte `200`), ma l'interfaccia utente rimane disconnessa.
- **Le installazioni multiple dello stesso IDE sono indipendenti**: un'installazione di sistema (ad esempio `/usr/share/antigravity/antigravity`) e un'installazione "Full" locale dell'utente (ad esempio `~/AntigravityIDE_Full/antigravity-ide`) sono processi separati con runtime propri; ciascuno deve essere riavviato con la CA iniettata. Prima del riavvio, identificare quale sia in esecuzione tramite il percorso del relativo binario.
- **L'identità è determinata dal prompt di sistema dell'agente, non dal modello instradato**: quando si rimappa il modello di un agente verso un provider diverso, la risposta continua a dichiarare l'identità nativa dell'agente (ad esempio, Antigravity risponde "I am powered by Gemini"), poiché l'IDE la inserisce nel prompt di sistema. Verificare il backend effettivo in `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`), invece di chiedere al modello quale sia la sua identità.

## §6 Risoluzione dei problemi

### Conflitto sulla porta 443

Se un altro processo è già in ascolto sulla porta 443 (server web, VPN, ecc.):

```bash
lsof -i :443          # individua il processo
sudo fuser -k 443/tcp  # termina forzatamente (usare con cautela)
```

In alternativa, configura una porta non privilegiata nelle impostazioni di AgentBridge e imposta regole di reindirizzamento `iptables` / `pf`.

### Certificato non attendibile

Se l'IDE mostra errori TLS dopo l'avvio di AgentBridge:

1. Verifica che il certificato sia stato installato: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) oppure `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. Alcune applicazioni gestiscono un proprio archivio di attendibilità (Firefox, Chrome su Linux). Esegui nuovamente "Considera attendibile il certificato" e controlla l'archivio dei certificati specifico di NSS/Firefox.
3. Riavvia l'IDE dopo aver considerato attendibile il certificato: le sessioni TLS in corso utilizzano il precedente stato di attendibilità.

### Disconnessione dall'IDE / "errore di connessione" nonostante una CA attendibile

Sintomo: dopo aver reindirizzato il DNS e reso attendibile la CA, un IDE basato su Electron (ad es. Antigravity)
si apre **con l'utente disconnesso** oppure mostra un errore di autenticazione/connessione, nonostante il log MITM mostri
che le chiamate di bootstrap (`loadCodeAssist`, `fetchAvailableModels`, …) restituiscono `200`.

Causa: il **runtime Node/Electron incluso nell'IDE ignora l'archivio di attendibilità del sistema operativo**. Il backend
nativo (un language server Go) considera attendibile la CA del sistema operativo e si autentica, mentre il frontend Electron
non lo fa; pertanto, l'interfaccia utente ritiene di essere offline.

Soluzione (entrambi i passaggi): esporta `NODE_EXTRA_CA_CERTS=<ca.crt>` **e riavvia l'IDE da quella
shell**, non dall'icona sul desktop. Prima chiudi completamente l'IDE: a causa del blocco dell'istanza singola di Electron,
un secondo avvio porta semplicemente in primo piano il processo esistente e il nuovo ambiente viene ignorato. Consulta il §3.2.
Ciò rispecchia una segnalazione upstream ancora aperta, secondo cui un agente autonomo funziona attraverso un MITM, mentre la variante
IDE non funziona con la stessa configurazione.

### DNS non propagato

Controlla che `/etc/hosts` sia stato aggiornato:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

Svuota la cache DNS:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE non rilevato

Il rilevamento automatico utilizza i percorsi di installazione comuni. Se il rilevamento non riesce, ma l'IDE è installato:

- Controlla se il file binario dell'IDE si trova in una posizione non standard
- La configurazione guidata funziona comunque: il mancato rilevamento significa soltanto che il badge non mostrerà il percorso di installazione

### Errori dell'handler (recupero upstream non riuscito)

Se AgentBridge intercetta le richieste, ma tutte non riescono:

1. Verifica che almeno un provider sia connesso in `/dashboard/providers`
2. Controlla i log del server OmniRoute: `APP_LOG_LEVEL=debug` in `.env`
3. Verifica che `OMNIROUTE_BASE_URL` punti all'endpoint corretto del router (predefinito: `http://127.0.0.1:20128`)

## §8 Roadmap

### Indagine su Trae

Trae è un assistente di programmazione basato sull'IA relativamente nuovo. Prima di implementare un handler:

1. Identificare il file binario/l'estensione nei marketplace di VS Code / JetBrains o come applicazione autonoma
2. Acquisire il traffico con mitmproxy per individuare gli host API e la struttura degli endpoint
3. Determinare il meccanismo di autenticazione
4. Valutare se procedere o meno in base ai TOS e alla possibilità di individuare le API

Fino al completamento dell'indagine, la scheda Trae nella dashboard mostra un badge "In fase di indagine" con un link "Segnala fattibilità". Lo stub dell'handler in `src/mitm/handlers/trae.ts` genera un errore strutturato `Non ancora implementato`.

### Agenti nel backlog (MITM obbligatorio — nessun supporto per URL di base personalizzati)

I seguenti strumenti non supportano URL di base personalizzati nelle versioni attuali, rendendo MITM l'unico metodo di intercettazione. La valutazione della fattibilità è in sospeso:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — separato da Kiro IDE)
- **Cowork** (applicazione desktop di Anthropic)

Nota: GitHub Copilot CLI ≥v1.0.19 supporta `COPILOT_PROVIDER_BASE_URL` — per questo strumento, utilizzare la configurazione diretta anziché MITM.
