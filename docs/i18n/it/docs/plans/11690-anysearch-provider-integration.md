## 1. Dati di riferimento del servizio (documentazione ufficiale, sottoposta a verifica incrociata)

- URL di base: `https://api.anysearch.com` (REST) + `POST /mcp` (MCP, JSON-RPC 2.0).
- `POST /v1/search` - parametri: `query` (obbligatorio), `max_results` (1-10, valore predefinito 10), `tag` (`{domain}.{sub_domain}` per l'instradamento verticale), `zone` (cn/intl), `language`, `params` (campi verticali strutturati), `format` (json/markdown).
- `GET /v1/sub-domains?domain=...` - catalogo delle funzionalità, NON incide sulla quota.
- `POST /v1/extract` - recupera/estrae `{url, title, content}`; corpo JSON rigoroso, limite di 16 KiB.
- `POST /v1/auth/email/register` - registrazione con un'unica chiamata, restituisce una chiave monouso in testo normale `as_sk_...`.
- Autenticazione: `Authorization: Bearer <as_sk_...>` facoltativa; l'accesso anonimo è soggetto a limiti per IP che consumano la quota gratuita giornaliera; una chiave non valida restituisce 401/403 SENZA fallback anonimo silenzioso.
- Piano gratuito: 1000 richieste/giorno, 20 QPS per chiave. Piano a pagamento: prezzo non definito (Prossimamente).
- Involucro della risposta: successo `{code: 0, message: "success", request_id, data}`; errore `{code: -1, message}`. Gli errori di autenticazione/quota non includono un `error_code` strutturato (il testo del messaggio funge da segnale); gli errori specifici dell'estrazione includono invece `error_code` (`invalid_extract_url`, `extract_failed`). Nessuna intestazione `Retry-After` nelle risposte 429.

## 3. Decisioni (tutte raggiunte il 2026-08-26)

1. **Strategia di routing: `fallbackOnly`.** Motivazione: un provider gratuito con costo 0 non deve mai prevalere nel routing automatico basato sui costi; la selezione esplicita e il ritorno al fallback non subiscono modifiche. Precedente: voce xquik integrata.
2. **Ambito: webSearch + webFetch tramite `POST /v1/extract` nella v1.** In linea con il modello mentale a doppia funzionalità di tavily/exa. Le funzionalità verticali (`tag`, `sub-domains`, `batch_search`) restano fuori ambito: attualmente non esiste alcuna IR per i parametri verticali.
3. **Visualizzazione della quota: `freeMonthlyQuota: 0`** (visualizzazione conservativa in stile xquik). Il limite reale (1000 richieste/giorno, reimpostazione giornaliera) viene invece indicato nel testo `authHint` del catalogo dell'interfaccia utente. Motivazione: la visualizzazione della quota deve corrispondere alla semantica di reimpostazione; convertire un limite giornaliero in un equivalente mensile (30000) sarebbe una falsa promessa che l'interfaccia utente non può rispettare.
4. **searchTypes: solo `["web"]`.** Non vi sono prove pubbliche dell'esistenza di una verticale per notizie/immagini nell'API AnySearch; i gateway che integrano API prive di una verticale documentata (ad esempio Google Custom Search) espongono solo il web anziché mappare silenziosamente notizie -> web.
5. **Strategia per la chiave:** il funzionamento senza chiave è supportato; una chiave non valida restituisce 401/403 e non viene mai convertita silenziosamente in accesso anonimo (rispecchiando il contratto upstream).
6. **Esclusioni deliberate:** `FETCH_BACKEND_TO_PROVIDER` / `FetchInterceptionBackend` (l'intercettazione della chat resta affidata a firecrawl/jina/tavily); `ANONYMOUS_CAPABLE_WEB_FETCH_PROVIDERS` (gli endpoint remoti anonimi condividono un unico pool con limite basato sull'IP per ciascun IP di uscita, pertanto l'estrazione senza chiave è facoltativa e non è candidata al routing automatico); `QUOTA_STATUS_PROVIDERS` (AnySearch segnala il raggiungimento della quota tramite 429/envelope, non tramite lo stato 402/403).
