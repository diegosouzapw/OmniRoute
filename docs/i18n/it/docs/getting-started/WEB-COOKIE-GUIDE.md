I provider Web Cookie consentono a OmniRoute di utilizzare un servizio di IA tramite la sessione esistente del browser, anziché tramite una chiave API. Sono utili quando si dispone già dell'accesso a un servizio attraverso il relativo sito web e si desidera che OmniRoute utilizzi la stessa sessione autenticata.

A differenza dei provider con chiave API, i provider Web Cookie eseguono l'autenticazione utilizzando le credenziali inviate dal browser al sito web.

---

# Prima di iniziare

> **Importante:** Copiare sempre le credenziali da una **richiesta di rete attiva**, **non** dall'archivio dei cookie del browser.

Molti problemi di autenticazione sono causati dalla copia dei cookie dalla posizione sbagliata.

## NON copiare dall'archivio dei cookie

La maggior parte dei browser mostra i cookie memorizzati tramite:

```
DevTools
→ Application (o Storage)
→ Cookies
```

Anche se questi cookie sembrano corretti, potrebbero essere:

- obsoleti
- incompleti
- privi di cookie inviati solo nelle richieste autenticate

L'utilizzo di questi valori può causare errori di autenticazione, anche se sembrano validi.

## Copiare da una richiesta attiva

Utilizzare invece i cookie di una richiesta completata correttamente:

```
DevTools
→ Network
→ Aggiornare la pagina
→ Aprire una richiesta di chat o conversazione
→ Request Headers
→ Cookie
```

L'header di richiesta `Cookie` contiene le informazioni di autenticazione esatte utilizzate correttamente dal browser.

Per la maggior parte dei provider Web Cookie, questo è il valore da incollare in OmniRoute.

# Configurazione generale

Il processo di configurazione è lo stesso per la maggior parte dei provider Web Cookie.

1. Accedere al sito web del provider.
2. Aprire gli strumenti per sviluppatori del browser.
3. Aprire la scheda **Network**.
4. Aggiornare la pagina.
5. Aprire una richiesta autenticata di chat o conversazione.
6. Copiare le credenziali di autenticazione richieste.
7. Aprire OmniRoute.
8. Andare su **Providers → Add Provider**.
9. Selezionare il provider Web Cookie.
10. Incollare le credenziali.
11. Fare clic su **Test Connection**.
12. Salvare il provider.

Le credenziali esatte richieste dipendono dal provider.

## NoTrack (notrack-web)

NoTrack ([notrack.ai](https://notrack.ai)) è una piattaforma di chat gratuita per utenti, che non richiede registrazione: la sessione viene creata in forma anonima alla prima visita e viene mantenuta tramite tre cookie: `uid`, `si_usr_id` e `si_ses_id`. OmniRoute inoltra tramite proxy lo stesso endpoint `/api/dispatch` usando un unico ID modello (`notrack-c`, alias `ntw`).

### Passaggi per la connessione

1. Apri [notrack.ai](https://notrack.ai) nel browser e attendi che venga impostato il cookie della sessione anonima.
2. Apri **Strumenti per sviluppatori → Rete**, aggiorna la pagina e fai clic su una qualsiasi richiesta `/api`.
3. In **Intestazioni della richiesta**, copia il valore completo dell'intestazione `Cookie`.
4. In OmniRoute, vai a **Provider → Aggiungi provider → NoTrack Web (gratuito)**.
5. Incolla la stringa dei cookie nel campo `apiKey` e fai clic su **Salva**.

OmniRoute estrae `uid`, `si_usr_id` e `si_ses_id` dalla stringa incollata e ricostruisce un'intestazione `Cookie` pulita contenente solo tali coppie, più `nt_session` (il token `ntk_…` impostato per gli account autenticati), se presente. Se manca uno dei tre valori, la stringa originale incollata viene inoltrata senza modifiche, in modo che gli operatori possano sperimentare formati alternativi.

### ID modello

| ID modello  | Nome visualizzato | Note                                                       |
| ----------- | ----------------- | ---------------------------------------------------------- |
| `notrack-c` | NoTrack C         | Predefinito: il modello di dispatch upstream `C`.          |
| `C`         | NoTrack C         | Alias di `notrack-c` (codice dispatch upstream originale). |
| `notrack`   | NoTrack C         | Alias di `notrack-c`.                                      |
| `ntw`       | NoTrack C         | Alias breve di `notrack-c`.                                |

Tutti e quattro gli ID modello corrispondono allo stesso modello di dispatch upstream (`C`).

### Opzioni della richiesta

L'esecutore accetta i seguenti campi facoltativi nel corpo della richiesta:

| Campo del corpo       | Valore predefinito | Scopo                                                                           |
| --------------------- | ------------------ | ------------------------------------------------------------------------------- |
| `notrack_mode`        | `usual`            | Modalità di dispatch (stringa in formato libero; l'upstream accetta `usual`, …) |
| `notrack_max_turns`   | `6`                | Numero di turni interni che l'upstream può eseguire prima di rispondere.        |
| `notrack_chat_id`     | `null`             | Riprende una chat upstream esistente (omettere per iniziare una nuova chat).    |
| `notrack_attachments` | `[]`               | Array pass-through dei descrittori degli allegati upstream.                     |
| `notrack_regenerate`  | `false`            | Impostare su `true` per richiedere la rigenerazione della risposta precedente.  |

### Funzionalità

- Completamenti di chat **in streaming e non in streaming**.
- **Chiamata di strumenti**: imposta `tools: [...]` nella richiesta; l'esecutore li serializza in un contratto envelope per le chiamate di strumenti e analizza le risposte del modello riconvertendole in `tool_calls` di OpenAI.
- **`response_format`**: sono supportati `json_object` e `json_schema`. L'esecutore estrae il primo oggetto JSON dalla risposta del modello e lo converte in stringa prima di restituirlo.
- **Indicazione del ragionamento**: l'esecutore emette un delta `reasoning` quando l'upstream invia un evento `thinking`.

### Limitazioni

- L'upstream applica quote di utilizzo anonimo: quando vengono superate, l'esecutore restituisce un errore 429 con un messaggio comprensibile.
- Tutti gli ID modello vengono risolti nello stesso modello di dispatch upstream; non è possibile selezionare un modello specifico.
- L'esecutore non chiama l'endpoint `/api/chats` dell'upstream, pertanto la cronologia delle chat e le sessioni non vengono gestite automaticamente. Usa `notrack_chat_id` per riprendere una chat upstream esistente.

# Cosa possono e non possono fare i provider basati sui cookie web

I provider basati sui cookie web riutilizzano l'interfaccia di chat di un sito web. **Non** offrono le stesse funzionalità delle API ufficiali.

## Supportato

- Autenticazione tramite la sessione esistente del browser
- Accesso ai modelli disponibili tramite il tuo account
- Streaming delle risposte della chat
- Nessuna chiave API richiesta

## Non supportato

- Chiamata di funzioni
- Chiamata di strumenti
- Modifica automatica dei file
- Flussi di lavoro IDE agentici
- Funzionalità disponibili solo tramite API

Questo è il comportamento previsto e **non** è un bug.

Se hai bisogno dell'esecuzione di strumenti, della modifica automatica dei file o di altri flussi di lavoro agentici, utilizza un **provider con chiave API** anziché un provider Web Cookie.

---

# Avvertenza sulla convalida

Un esito positivo di **Test Connection** o della convalida dei cookie verifica soltanto che le credenziali fornite sembrino essere nel formato previsto.

Finché l'Issue #7857 non sarà risolta, una convalida riuscita **non garantisce** che il provider riesca ad autenticarsi correttamente.

Se l'autenticazione continua a non riuscire, verifica di aver copiato le credenziali da una richiesta di rete attiva anziché dall'archivio dei cookie del browser.

---

# Risoluzione dei problemi

## Autenticazione non riuscita

Verifica che le credenziali siano state copiate da:

```
Network
→ Request Headers
→ Cookie
```

e **non** da:

```
Application
→ Cookies
```

---

## Il cookie funziona nel browser ma non in OmniRoute

Alcuni provider includono cookie che vengono inviati soltanto durante le richieste autenticate.

Copia nuovamente le credenziali da una nuova richiesta di rete dopo aver aperto correttamente una conversazione.

---

## Sessione scaduta

I provider Web Cookie utilizzano la sessione esistente del browser.

Se la sessione del browser scade o esegui la disconnessione, devi copiare un nuovo set di credenziali. Per automatizzare il rinnovo dei cookie per i provider web supportati, consulta lo strumento complementare [Browser Session Sync Extension](../guides/SESSION-SYNC-EXTENSION.md).

---

## Test Connection riesce ma le richieste non vanno a buon fine

Finché l'Issue #7857 non sarà risolta, il superamento della convalida non garantisce che la richiesta di autenticazione vada a buon fine.

Copia nuovamente le credenziali da una nuova richiesta autenticata prima di procedere con un'ulteriore risoluzione dei problemi.

# Procedure consigliate

- Copia le credenziali da una nuova richiesta autenticata.
- Evita di riutilizzare cookie vecchi.
- Mantieni attiva la sessione del browser mentre utilizzi provider Web Cookie.
- Tratta i cookie copiati come credenziali sensibili.
- Utilizza provider con chiave API quando hai bisogno della chiamata di funzioni o di flussi di lavoro agentici.
