AgentBridge پراکسی MITM (مرد میانی) در OmniRoute است که ترافیک HTTPS عاملهای هوش مصنوعی IDE را رهگیری کرده و از طریق موتور مسیریابی یکپارچه OmniRoute بازهدایت میکند. این ابزار از **۱۰ عامل IDE** پشتیبانی میکند — Antigravity، Kiro، GitHub Copilot، GHE Copilot، OpenAI Codex، Cursor، Zed، Claude Code، Open Code و Trae (در دست بررسی) — و به این ترتیب AgentBridge را به پراکسی MITM با گستردهترین پوشش برای دستیارهای کدنویسی هوش مصنوعی در بازار تبدیل میکند.

**محل داشبورد:** `/dashboard/tools/agent-bridge`
**گروه نوار کناری:** ابزارها (پس از عاملهای ابری)
**همچنین ببینید:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — تمام ترافیک رهگیریشده را بهصورت بلادرنگ پایش کنید؛ `docs/security/MITM-TPROXY-DECRYPT.md` (در git؛ در `/docs` کامپایل نمیشود) — حالت ضبط رمزگشایی شفاف TPROXY در Linux که توسط مسیر `/api/tools/agent-bridge/tproxy` هدایت میشود.

## §1 نمای کلی

### AgentBridge چیست؟

هنگامی که یک عامل IDE (برای مثال GitHub Copilot، Cursor یا Claude Code) یک فراخوانی API انجام میدهد، مستقیماً به ارائهدهنده بالادستی هوش مصنوعی (OpenAI، Anthropic و غیره) متصل میشود. AgentBridge این اتصال را بهصورت شفاف در سطح TLS رهگیری میکند — بدون نیاز به هیچگونه تغییر در پیکربندی عامل — و درخواست را از طریق OmniRoute بازنویسی میکند.

این یعنی میتوانید:

- **هر عاملی را به هر ارائهدهندهای بازهدایت کنید**: آیا Copilot با OpenAI ارتباط برقرار میکند؟ آن را به Anthropic Claude، Gemini یا هر یک از ۳۵۲ ارائهدهنده OmniRoute هدایت کنید.
- **نگاشتهای مدل را اعمال کنید**: `gemini-3-flash` → `claude-sonnet-4.7` بهصورت شفاف در سطح کنترلکننده.
- **تمام ترافیک عاملها را مشاهده کنید**: هر درخواست رهگیریشده در [بازرس ترافیک](./TRAFFIC_INSPECTOR.md) منتشر میشود.
- **تابآوری OmniRoute را اعمال کنید**: مسیریابی ترکیبی، قطعکنندههای مدار، مسیرهای جایگزین و ردیابی هزینه برای ترافیک عاملهای IDE نیز کار میکنند.

## §2 معماری

### 2.1 نمای کلی مؤلفهها

```
عامل IDE (VS Code / Cursor / غیره)
    │  HTTPS (پورت 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← تغییر مسیر DNS
    │
    ▼
src/mitm/server.cjs  (پورت 443، فرایند فرزند CJS)
    │  مقصد را بر اساس SNI سرآیند Host تفکیک میکند
    │  برای هر SNI یک گواهی TLS امضاشده توسط CA متعلق به AgentBridge تولید میکند
    ├── تطابق با فهرست دور زدن؟ → عبور مستقیم TCP (بدون رمزگشایی)
    ├── تطابق با مقصد؟ → fetch → مسیریاب OmniRoute (پورت 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() روی بدنه/سرآیندهای درخواست
    │               ├── TrafficBuffer.push() — انتشار در بازرس ترافیک
    │               └── fetchRouter() → /v1/chat/completions
    └── بدون تطابق؟ → عبور مستقیم TCP (بدون رمزگشایی)
```

### 2.2 سرور MITM (`src/mitm/server.cjs`)

سرور اصلی MITM بهصورت یک فرایند فرزند CJS در Node.js اجرا میشود (تا از بازنویسی پایگاه کد CJS موجود جلوگیری شود). این سرور:

- روی پورت 443 گوش میدهد (به دسترسی ویژه یا `authbind`/`setcap` نیاز دارد)
- تونلهای CONNECT را از سیستمعامل دریافت میکند (از طریق تغییر مسیر DNS در `/etc/hosts`)
- برای هر SNI گواهیهای TLS امضاشده توسط CA متعلق به AgentBridge (`DATA_DIR/mitm/ca.crt`) تولید میکند
- عامل مقصد را بر اساس سرآیند Host و از طریق رجیستری `targets/index.ts` تفکیک میکند
- درخواستها را از طریق HTTP و در آدرس `http://127.0.0.1:20128` به لایه مدیریتکننده TypeScript ارسال میکند

`TARGET_HOSTS` از `DATA_DIR/mitm/targets.json` بارگذاری میشود (که هنگام راهاندازی توسط `targets/index.ts` نوشته میشود) و بهروزرسانی پویا را بدون راهاندازی مجدد سرور CJS امکانپذیر میکند.

> **مدل Root-CA (#6684).** توضیح بالا درباره گواهی امضاشده برای هر SNI توسط یک CA،
> به مدل پایدار Root-CA اشاره دارد که در #6684 اضافه شده است (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`، با استفاده مجدد از رمزنگاری CA/leaf که پیشتر
> برای TPROXY در `src/mitm/tproxy/dynamicCert.ts` اثبات شده بود) — این مدل جایگزین
> گواهی leaf خودامضای ایستای قدیمی (`src/mitm/cert/generate.ts`، که همچنان
> فقط به میزبانهای antigravity محدود است) میشود؛ وجود یک جفت
> `server.crt`/`server.key` روی دیسک نشاندهنده مدل قدیمی است. **رفتار مهاجرت**:
> یک نصب جدید (بدون `server.crt` قبلی) مدل Root-CA را بهطور خودکار دریافت میکند؛
> نصبی که از قبل به گواهی leaf ایستای قدیمی اعتماد دارد، استفاده از آن را ادامه
> میدهد تا زمانی که اپراتور `MITM_ROOT_CA_ENABLED=true` را تنظیم کرده و پل را
> مجدداً راهاندازی کند (`src/mitm/cert/migration.ts` تابع تصمیمگیری خالص است —
> یک CA مورد اعتماد MITM که میتواند برای **هر** میزبانی گواهی leaf امضا کند،
> عملاً بسیار قدرتمندتر از گواهی leaf قدیمی با SAN ثابت است؛ بنابراین این تغییر
> برای نصبی که از قبل مورد اعتماد است، هرگز بیاطلاع انجام نمیشود). گواهی CA
> در همان جایگاه `omniroute-mitm.crt` در مخزن اعتماد نصب میشود که گواهی leaf
> قدیمی از آن استفاده میکرد (`cert/install.ts::installCaCert`) — نیازی به
> پاکسازی اعتماد دوگانه نیست.

### 2.3 پایه مدیریتکننده (`src/mitm/handlers/base.ts`)

همه مدیریتکنندههای عامل از `MitmHandlerBase` ارثبری میکنند:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // ابزارهای کمکی محافظتشده: fetchRouter، pipeSSE، hookBufferStart، hookBufferUpdate
}
```

هر مدیریتکننده پیش از پراکسیکردن، `hookBufferStart()` و پس از تکمیل، `hookBufferUpdate()` را فراخوانی میکند. این فراخوانیها ورودیهای `InterceptedRequest` را به `globalTrafficBuffer` اضافه میکنند (بخش §4 از [بازرس ترافیک](./TRAFFIC_INSPECTOR.md) را ببینید).

### 2.4 رجیستری مقصدها (`src/mitm/targets/`)

هر عامل یک فایل مقصد اعلانی دارد:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

رجیستری (`targets/index.ts`) مقدار `ALL_TARGETS` را صادر میکند و هنگام راهاندازی، `DATA_DIR/mitm/targets.json` را تولید میکند.

### 2.5 عبور مستقیم و فهرست دور زدن (`src/mitm/passthrough.ts`)

**فهرست دور زدن** (ابتدا بررسی میشود و نسبت به تطابق مقصد اولویت دارد):

- الگوهای پیشفرض: میزبانهای بانکی، `.gov.`، ارائهدهندگان OAuth/SSO ‏(Okta، Auth0) و غیره
- الگوهای کاربر: در جدول `agent_bridge_bypass` پایگاه داده ذخیره میشوند
- میزبانهای دور زدهشده یک تونل شفاف TCP دریافت میکنند — TLS **هرگز رمزگشایی نمیشود**

**عبور مستقیم پیشفرض** (بدون تطابق مقصد و خارج از فهرست دور زدن):

- این موارد نیز یک تونل TCP دریافت میکنند — اتصالها هرگز قطع نمیشوند
- از ایجاد اختلال توسط AgentBridge در ترافیک عمومی HTTPS سیستم جلوگیری میکند

اولویت مسیریابی:

```
فهرست دور زدن → تطابق مقصد → عبور مستقیم
```

### 2.6 گواهی CA بالادستی (`src/mitm/upstreamTrust.ts`)

برای محیطهای شبکه سازمانی دارای CA سفارشی:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

در صورت تنظیم، توزیعکننده سراسری `undici` را با گواهی CA اضافی پیکربندی میکند تا AgentBridge بتواند از طریق پراکسیهای سازمانی خاتمهدهنده TLS به ارائهدهندگان بالادستی دسترسی پیدا کند.

### 2.7 پوشاندن اسرار (`src/mitm/maskSecrets.ts`)

اسکنر مستقلِ پیادهسازی پاک روی بدنه درخواستها و سرآیندهای اطلاعات اعتبارسنجی،
**پیش از** ورود آنها به بافر بازرس ترافیک یا هرگونه گزارش، اعمال میشود. این اسکنر یک گذر خطی انجام میدهد:

- توکنهای دارای پیشوند `sk-` / `ak-` / `pk-` (به سبک OpenAI/Anthropic)
- اطلاعات اعتبارسنجی RFC 6750 بهشکل `Authorization: Bearer <token>`، با اولویت برای کل توکن
- توکنهای عمومی، طولانی و مبهم (≥40 نویسه)، از جمله شکلهای نقطهدار و پُرشده

`sanitizeHeaders()` نامهای حفظشده را به حروف کوچک تبدیل میکند، مقادیر آرایه را بهصورت قطعی به هم میپیوندد، موارد موجود در
فهرست منع مشترک hop-by-hop/قاببندی (از جمله احراز هویت پراکسی) را حذف میکند، `cookie` و
`set-cookie` را بهطور کامل میپوشاند و مقادیر اطلاعات اعتبارسنجی را به اسکنر واگذار میکند.

## §3 راهاندازی

### 3.1 راهاندازی/توقف سرور MITM

از کارت سرور AgentBridge در `/dashboard/tools/agent-bridge` استفاده کنید:

| عملیات              | توضیحات                                                                          |
| ------------------- | -------------------------------------------------------------------------------- |
| راهاندازی سرور      | `src/mitm/server.cjs` را روی پورت 443 اجرا میکند                                 |
| توقف سرور           | فرایند فرزند را بهشکل صحیح متوقف میکند                                           |
| راهاندازی مجدد سرور | توقف + راهاندازی (تغییرات مقصد را اعمال میکند)                                   |
| اعتماد به گواهی     | `DATA_DIR/mitm/ca.crt` را در مخزن اعتماد سیستمعامل نصب میکند                     |
| دانلود گواهی        | `ca.crt` را برای نصب دستی دانلود میکند                                           |
| بازتولید گواهی      | یک جفتکلید CA جدید ایجاد میکند (تمام گواهیهای موجود مختص هر عامل نامعتبر میشوند) |

### 3.2 اعتماد به گواهی

پیش از آنکه IDEها اتصال MITM را بپذیرند، گواهی CA متعلق به AgentBridge باید مورد اعتماد سیستمعامل قرار گیرد.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

یا از دکمه «اعتماد به گواهی» در داشبورد استفاده کنید (این دکمه فرمان مناسب سیستمعامل شما را اجرا میکند و در صورت نیاز، اعلان sudo را نمایش میدهد).

#### IDEهای مبتنی بر Electron مخزن اعتماد سیستمعامل را نادیده میگیرند (`NODE_EXTRA_CA_CERTS`)

برخی IDEها — بهویژه **Antigravity IDE** و دیگر برنامههای مبتنی بر Electron / VS Code — محیط اجرایی
Node.js مخصوص خود را همراه دارند که برای درخواستهای خروجی `fetch`/HTTPS، **به مخزن اعتماد سیستمعامل مراجعه نمیکند**.
اعتماد به CA در سطح سیستمعامل/NSS برای **بکاند** بومی IDE کافی است
(برای مثال، یک سرور زبان Go که از مجموعه CA سیستمعامل استفاده میکند)، اما **فرانتاند Electron** همچنان
در TLS شکست خواهد خورد — این وضعیت بهصورت _خارج شدن از حساب_ برنامه یا نمایش یک _«خطای اتصال»_
بروز میکند، حتی اگر گزارش MITM نشان دهد فراخوانیهای راهاندازی اولیه بکاند پاسخ `200` دریافت کردهاند. دو مرحله
لازم است و هر دو اهمیت دارند:

1. محیط اجرایی را بهطور صریح به CA هدایت کنید:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **IDE را از همان پوسته اجرا کنید.** اجرای آن از طریق نماد دسکتاپ / Dock / منوی Start
   متغیرهای exportشده پوسته را به ارث **نمیبرد** و `~/.config/environment.d/*.conf` تنها پس از
   ورود گرافیکی مجدد اعمال میشود. ابتدا IDE را کاملاً ببندید — قفل تکنمونهای Electron باعث میشود اجرای
   دوم فقط پنجره فرایند موجود را فعال کند و محیط جدید نادیده گرفته شود.

مرحله اعتماد در سطح سیستمعامل + NSS که در بالا آمده، همچنان ضروری است (پشته شبکه Chromium که برخی جریانهای
احراز هویت از آن استفاده میکنند، مخزن NSS هر کاربر را میخواند و برای `*.googleapis.com` نیز پینهای ایستای
خود را دارد که یک CA مورد اعتماد محلی آنها را بازنویسی میکند). `NODE_EXTRA_CA_CERTS` نیز مسیر `fetch` در Node را پوشش میدهد.

### 3.3 مسیریابی DNS

برای هر عاملی که میخواهید رهگیری کنید، میزبان یا میزبانهای API آن باید به `127.0.0.1` تفکیک شوند. هنگامی که DNS یک عامل را در راهنمای راهاندازی فعال یا غیرفعال میکنید، AgentBridge ورودیهای `/etc/hosts` را بهطور خودکار مدیریت میکند.

نمونه ورودیهای `/etc/hosts` برای GitHub Copilot:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 نگاشت مدل

برای تعریف نگاشتهای مبدأ → مقصد، از جدول نگاشت مدل در کارت هر عامل استفاده کنید:

| مدل مبدأ (بومی عامل) | مدل مقصد (OmniRoute) |
| -------------------- | -------------------- |
| `gpt-4o`             | `claude-sonnet-4.7`  |
| `*` (نویسه عام)      | `claude-haiku-4.7`   |

نویسه عام `*` هر مدل ناشناخته را به مقصد مشخصشده نگاشت میکند. این تنظیم در جدول `agent_bridge_mappings` ذخیره میشود.

> **نکته — شناسههای واقعی مدل عامل را کشف کنید.** ممکن است یک IDE نام مدلهایی را ارسال کند که با
> برچسبهای رابط کاربری آن متفاوتاند و بین نسخههای اصلی تغییر میکنند. برای مثال، **Antigravity 2**
> مقادیر `gemini-3.1-pro-low`، `gemini-pro-agent` و `gemini-3.1-flash-lite` را روی شبکه ارسال میکند — نه
> `gemini-2.5-pro` که در مستندات قدیمیتر نمایش داده شده است. درحالیکه هیچ نگاشت منطبقی وجود ندارد، یک پیام گفتگو
> ارسال کنید: MITM مقدار دقیق `model:` ورودی را ثبت میکند و درخواست را بدون تغییر عبور میدهد. همان مقدار
> دقیق را نگاشت کنید؛ سپس درخواست بعدی رهگیری شده و به مقصد شما هدایت میشود.

### 3.5 اطلاعیه خطر

AgentBridge اطلاعات احراز هویت (توکنهای OAuth و کلیدهای API) را که IDE برای احراز هویت نزد ارائهدهندگان بالادستی استفاده میکند، رهگیری میکند. این اطلاعات **پیش از ثبت در گزارش پوشانده میشوند** (بخش §2.7 را ببینید)، اما برای لایه MITM متعلق به OmniRoute قابل مشاهدهاند. هنگام نخستین فعالسازی هر عامل، یک پنجره اطلاعیه خطر قابلبستن نمایش داده میشود.

### 3.6 نگهداری و عیبیابی

داشبورد یک کارت **نگهداری و عیبیابی** (`AgentBridgeMaintenanceCard`، در `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`) ارائه میکند که مسیرهای عملیاتی MITM را که پیشتر رابط کاربری نداشتند، در دسترس قرار میدهد. زیرعنوان آن: _«خط لوله ثبت را خودآزمایی کنید، وضعیت باقیمانده سیستم را بازگردانید و راهاندازی خود را بین دستگاهها جابهجا کنید.»_ توابع کمکی سمت کلاینت این کارت در `src/lib/inspector/agentBridgeMaintenanceApi.ts` قرار دارند.

| دکمه                  | مسیر                                   | کاری که انجام میدهد                                                                                                                                                                                              |
| --------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **عیبیابی**           | `GET /api/tools/agent-bridge/diagnose` | خودآزمایی خط لولهٔ ضبط را اجرا میکند و گزارشی برای هر بررسی نمایش میدهد (✓/✗ بههمراه راهنمای رفع مشکل).                                                                                                          |
| **تعمیر**             | `POST /api/tools/agent-bridge/repair`  | وضعیت سیستمی MITM رهاشده در اثر خرابی یا SIGKILL را برمیگرداند (ورودیهای جعل DNS، مرجع صدور گواهی ریشه و پراکسی سیستم). همتوان — وقتی وضعیت پاک باشد، «چیزی برای تعمیر وجود ندارد» را گزارش میکند.               |
| **حذف CA**            | `DELETE /api/tools/agent-bridge/cert`  | اعتماد به مرجع صدور گواهی ریشهٔ MITM را لغو و آن را از مخزن اعتماد سیستمعامل حذف میکند (صریح و همتوان). فقط زمانی نمایش داده میشود که CA در حال حاضر مورد اعتماد باشد؛ به تأیید درونخطی «CA حذف شود؟» نیاز دارد. |
| **برونبری پیکربندی**  | `GET /api/tools/agent-bridge/config`   | فایل JSON پیکربندی قابلانتقال را دانلود میکند (بخش §3.7 را ببینید).                                                                                                                                              |
| **درونریزی پیکربندی** | `POST /api/tools/agent-bridge/config`  | یک فایل JSON پیکربندی را که قبلاً برونبری شده است بارگذاری میکند (بخش §3.7 را ببینید).                                                                                                                           |

**بررسیهای عیبیابی** (`summarizeDiagnostics()` در `src/mitm/inspector/diagnostics.ts`). مسیر، کاوش اثرگذار را برای هر مورد اجرا میکند و مقادیر بولی را به خلاصهساز خالص میدهد؛ یک نتیجهٔ کلی `healthy` بههمراه راهنمایی برای هر شکست بازگردانده میشود:

| نام بررسی          | آنچه تأیید میکند                                              | راهنمای هنگام شکست                                                                                                                             |
| ------------------ | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | فرایند سرور MITM فعال است                                     | «سرور MITM در حال اجرا نیست. آن را از زبانهٔ AgentBridge راهاندازی کنید.»                                                                      |
| `server-reachable` | سرور MITM اتصالها را روی پورت خود میپذیرد (کاوش TCP)          | «سرور MITM اتصالها را روی پورت خود نمیپذیرد. بررسی کنید که پورت آزاد باشد و مجوز لازم برای اتصال به آن را داشته باشید.»                        |
| `cert-exists`      | گواهی MITM روی دیسک ایجاد شده است                             | «هنوز هیچ گواهی MITM ایجاد نشده است. یکی را از زبانهٔ AgentBridge ایجاد کنید.»                                                                 |
| `cert-trusted`     | مرجع صدور گواهی ریشهٔ MITM در مخزن اعتماد سیستمعامل قرار دارد | «مرجع صدور گواهی ریشهٔ MITM مورد اعتماد مخزن سیستمعامل نیست، بنابراین رهگیری TLS شکست خواهد خورد. از زبانهٔ AgentBridge به گواهی اعتماد کنید.» |
| `dns-configured`   | نامهای میزبان هدف در `/etc/hosts` جعل شدهاند                  | «نامهای میزبان هدف در /etc/hosts جعل نشدهاند، بنابراین ترافیک هرگز به پراکسی نمیرسد. DNS را برای عاملهایی که میخواهید ضبط کنید فعال کنید.»     |

**نوار وضعیت رهاشده:** وقتی صفحه وضعیتی را تشخیص دهد که در اثر خرابی باقی مانده است (جعل DNS / CA / پراکسی سیستم)، کارت یک نوار کهربایی نمایش میدهد — _«یک نشست قبلی وضعیت سیستمی بر جای گذاشته است (جعل DNS،‏ CA یا پراکسی سیستم). برای پاکسازی آن، تعمیر را اجرا کنید.»_ — و دکمهٔ **تعمیر** را برجسته میکند. `Repair` همتای لایهٔ کاربرد پرچم `--cleanup` در ProxyBridge است (به `repairMitm()` در `src/mitm/manager.ts` واگذار میشود).

> مرجع صدور گواهی ریشهٔ MITM در طول توقف/شروع همچنان نصبشده باقی میماند تا از
> درخواستهای مکرر sudo جلوگیری شود (همان رفتار mitmproxy/Charles)، بنابراین حذف آن
> یک عمل صریح **حذف CA** است، نه کاری که هنگام توقف بهصورت خودکار انجام شود.

### 3.7 درونریزی/برونبری پیکربندی قابلانتقال

AgentBridge میتواند وضعیت **قابلتنظیم توسط اپراتور** را در قالب یک شیء JSON نسخهبندیشده سریالسازی کند تا یک تنظیمات را بتوان در چندین دستگاه تکرار کرد. سریالساز `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`) است که توسط `AgentBridgeConfigSchema` اعتبارسنجی میشود.

برونبری دقیقاً شامل سه بخش است (پیشفرضهای داخلی عمداً برونبری **نمیشوند** تا درونریزی هرگز باعث تکرار یا تداخل با آنها نشود):

| فیلد             | منبع                                                          | نکات                                                                   |
| ---------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `bypassPatterns` | الگوهای عبور تعریفشده توسط کاربر (`agent_bridge_bypass`)      | الگوهای پیشفرض بانک/دولت/okta مستثنا هستند                             |
| `customHosts`    | میزبانهای سفارشی Traffic Inspector (`inspector_custom_hosts`) | هر مورد: `{ host, kind: "llm"\|"app"\|"custom", label? }`              |
| `agentMappings`  | نگاشت مدل برای هر عامل (`agent_bridge_mappings`)              | `{ [agentId]: [{ source, target }] }` برای هر عاملی که دارای نگاشت است |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**رفتار درونریزی** (`POST /api/tools/agent-bridge/config`): الگوهای عبور و نگاشتهای هر عامل **بهطور کامل جایگزین میشوند**؛ میزبانهای سفارشی بهشکل **همتوان** افزوده میشوند (`INSERT OR IGNORE`). پاسخ گزارش میدهد که چه تعداد از هر مورد اعمال شدهاند:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

مواردی که در پیکربندی **وجود ندارند**: وضعیت اجرای سرور، مسیرهای گواهی، وضعیت DNS هر عامل، مسیر CA بالادستی و تنظیمات TPROXY — اینها وضعیت میزبان/زمان اجرا هستند، نه ترجیحات قابلانتقال.

### مراحل راهاندازی جادویی (برای هر عامل)

کارت هر عامل دارای یک راهاندازی جادویی ۳ مرحلهای است:

1. **بررسی پیشنیازها** — آیا سرور در حال اجرا است؟ آیا گواهی مورد اعتماد است؟ آیا IDE نصب شده است (تشخیص خودکار)؟
2. **فعالسازی DNS** — ورودیهایی را به `/etc/hosts` اضافه میکند (به sudo نیاز دارد). دقیقاً نشان میدهد کدام خطوط اضافه خواهند شد.
3. **نگاشت مدلها** — جدول اختیاری نگاشت مدل. نویسههای عام پذیرفته میشوند.

### تشخیص عامل

برای عاملهای ۱ تا ۸، AgentBridge تلاش میکند نصب IDE را بهصورت خودکار تشخیص دهد:

```ts
export async function detectAgent(agentId: AgentId): Promise<DetectionResult>;
// برمیگرداند: { installed: boolean, version?: string, path?: string }
```

تشخیص با استفاده از مسیرهای مختص سیستمعامل و بررسی فایلهای اجرایی انجام میشود (برای مثال، `code --list-extensions | grep github.copilot` برای Copilot و `~/.config/antigravity/` برای Antigravity).

### فهرست عبور مستقیم برای میزبانهای حساس

فهرست عبور مستقیم تضمین میکند که مؤسسات مالی، ارائهدهندگان OAuth/SSO و دیگر میزبانهای حساس **هرگز رمزگشایی نشوند**. ترافیک TLS آنها بهصورت یک تونل شفاف TCP عبور میکند — OmniRoute هرگز متن ساده را نمیبیند.

الگوهای پیشفرض عبور مستقیم شامل موارد زیر هستند:

- `*.bank.*`، `*.gov.*` (مالی/دولتی)
- `*.okta.com`، `*.auth0.com`، `*.microsoft.com` (SSO/هویت)
- `*.apple.com`، `*.icloud.com` (سرویسهای سیستمی Apple)

الگوهای عبور مستقیم افزودهشده توسط کاربر در جدول `agent_bridge_bypass` ذخیره میشوند و بر همهچیز اولویت دارند.

### پوشاندن اطلاعات محرمانه

`maskSecrets()` از `src/mitm/maskSecrets.ts` اعمال میشود:

- روی بدنه هر درخواست، پیش از `TrafficBuffer.push()`
- روی هر هدر، پیش از ثبت گزارش یا انتشار

الگوها: توکنهایی با پیشوند `sk-`/`ak-`/`pk-`، توکنهای `Bearer` و توکنهای عمومی با طول حداقل ۴۰ نویسه.

### گواهی CA بالادستی

هنگامی که `AGENTBRIDGE_UPSTREAM_CA_CERT` تنظیم شده باشد، فایل هنگام راهاندازی خوانده میشود. اگر مسیر وجود داشته باشد اما فایل قابل خواندن نباشد، AgentBridge خطایی واضح ثبت میکند و از شروع به کار خودداری میکند (این کار از خطاهای بیسروصدای TLS در محیطهای سازمانی جلوگیری میکند).

### محدودیتهای شناختهشده

- **درگاه 443 به دسترسی ویژه نیاز دارد**: در Linux، ‏AgentBridge به اجرای `setcap 'cap_net_bind_service=+ep'` روی فایل اجرایی Node نیاز دارد، یا باید از طریق `authbind` اجرا شود. راهاندازی جادویی دستورالعملهای مختص سیستمعامل را نمایش میدهد.
- **راهاندازی مجدد IDE الزامی است**: پس از تغییر مسیر DNS، ‏IDE باید مجدداً راهاندازی شود تا تفکیک نام میزبان جدید اعمال گردد.
- **توکنهای OAuth کدنویسیشده**: برخی عاملها (Kiro، Antigravity) توکنهای نوسازی OAuth را بهصورت محلی ذخیره میکنند. این موارد برای AgentBridge شفاف هستند — AgentBridge توکن Bearer را در هر درخواست میبیند که پیش از ثبت گزارش پوشانده میشود.
- **رابطهای کاربری Electron به `NODE_EXTRA_CA_CERTS` نیاز دارند**: IDEهایی که رابط کاربری آنها روی زماناجرای داخلی Node/Electron اجرا میشود، مخزن اعتماد OS/NSS را نادیده میگیرند و باید از پوستهای اجرا شوند که `NODE_EXTRA_CA_CERTS` در آن تنظیم شده باشد (§3.2 را ببینید). نشانه نبود آن: بخش پشتی IDE احراز هویت میشود (MITM پاسخهای `200` را نشان میدهد)، اما رابط کاربری همچنان در حالت خارجشده باقی میماند.
- **نصبهای متعدد یک IDE مستقل از یکدیگر هستند**: یک نصب سیستمی (برای مثال `/usr/share/antigravity/antigravity`) و یک نصب محلی کاربر از نوع «Full» (برای مثال `~/AntigravityIDE_Full/antigravity-ide`) فرایندهایی جداگانه با زماناجراهای مختص خود هستند — هرکدام باید با CA تزریقشده مجدداً اجرا شوند. پیش از اجرای مجدد، با استفاده از مسیر فایل اجرایی مشخص کنید کدامیک در حال اجرا است.
- **هویت توسط اعلان سیستمی عامل تعیین میشود، نه مدل مسیریابیشده**: هنگامی که مدل یک عامل را به ارائهدهندهای دیگر نگاشت میکنید، پاسخ همچنان هویت بومی عامل را ادعا میکند (برای مثال Antigravity پاسخ میدهد «من با Gemini قدرت گرفتهام»)، زیرا IDE آن را در اعلان سیستمی تزریق میکند. سامانه پشتی واقعی را در `call_logs` / `proxy_logs` (`provider`، `model`، `target_format`) تأیید کنید، نه با پرسیدن هویت مدل از خودش.

## §6 عیبیابی

### تداخل پورت 443

اگر فرایند دیگری از قبل روی پورت 443 در حال گوشدادن است (وبسرور، VPN و غیره):

```bash
lsof -i :443          # فرایند را پیدا کنید
sudo fuser -k 443/tcp  # خاتمه اجباری فرایند (با احتیاط استفاده کنید)
```

بهعنوان جایگزین، یک پورت غیرممتاز را در تنظیمات AgentBridge پیکربندی کنید و قوانین تغییر مسیر `iptables` / `pf` را تنظیم کنید.

### گواهی مورد اعتماد نیست

اگر IDE پس از راهاندازی AgentBridge خطاهای TLS نشان میدهد:

1. بررسی کنید که گواهی نصب شده باشد: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) یا `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. برخی برنامهها مخزن اعتماد خود را نگه میدارند (Firefox و Chrome در Linux). دوباره «Trust Cert» را اجرا و مخزن گواهی مخصوص NSS/Firefox را بررسی کنید.
3. پس از مورد اعتماد قرار دادن گواهی، IDE را مجدداً راهاندازی کنید — نشستهای TLS در حال اجرا از وضعیت اعتماد قبلی استفاده میکنند.

### خروج IDE از حساب / «خطای اتصال» با وجود CA مورد اعتماد

نشانه: پس از تغییر مسیر DNS و مورد اعتماد قرار دادن CA، یک IDE مبتنی بر Electron (برای مثال Antigravity)
بهصورت **خارجشده از حساب** باز میشود یا خطای احراز هویت/اتصال را نشان میدهد، درحالیکه گزارش MITM نشان میدهد
فراخوانیهای راهاندازی اولیه (`loadCodeAssist`، `fetchAvailableModels`، …) پاسخ `200` دریافت میکنند.

علت: **محیط اجرای Node/Electron همراه IDE، مخزن اعتماد سیستمعامل را نادیده میگیرد**. بکاند بومی
(یک سرور زبان Go) به CA سیستمعامل اعتماد میکند و احراز هویت میشود، اما فرانتاند Electron
اینطور نیست — بنابراین رابط کاربری تصور میکند آفلاین است.

راهحل (هر دو مرحله): `NODE_EXTRA_CA_CERTS=<ca.crt>` را export کنید **و IDE را از همان
پوسته دوباره اجرا کنید**، نه از نماد دسکتاپ. ابتدا IDE را کاملاً ببندید — قفل تکنمونهای Electron باعث میشود
اجرای دوم فقط فرایند موجود را در کانون توجه قرار دهد و محیط جدید نادیده گرفته شود. §3.2 را ببینید.
این وضعیت مشابه یک گزارش باز در پروژه بالادستی است که در آن یک عامل مستقل از طریق MITM کار میکند، اما گونه IDE
با همان پیکربندی ناموفق است.

### DNS منتشر نشده است

بررسی کنید که `/etc/hosts` بهروزرسانی شده باشد:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

حافظه نهان DNS را پاک کنید:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE شناسایی نمیشود

شناسایی خودکار از مسیرهای رایج نصب استفاده میکند. اگر شناسایی ناموفق است اما IDE نصب شده است:

- بررسی کنید که فایل اجرایی IDE در مکانی غیراستاندارد قرار نداشته باشد
- Setup Wizard همچنان کار میکند — ناموفق بودن شناسایی فقط به این معناست که نشان مسیر نصب را نمایش نمیدهد

### خطاهای کنترلکننده (واکشی بالادستی ناموفق است)

اگر AgentBridge درخواستها را رهگیری میکند اما همه آنها ناموفق هستند:

1. بررسی کنید که دستکم یک ارائهدهنده در `/dashboard/providers` متصل باشد
2. گزارشهای سرور OmniRoute را بررسی کنید: `APP_LOG_LEVEL=debug` در `.env`
3. بررسی کنید که `OMNIROUTE_BASE_URL` به نقطه پایانی صحیح مسیریاب اشاره کند (پیشفرض: `http://127.0.0.1:20128`)

## §8 نقشه راه

### بررسی Trae

Trae یک دستیار نسبتاً جدید برای کدنویسی با هوش مصنوعی است. پیش از پیادهسازی یک handler:

1. فایل اجرایی/افزونه را در فروشگاههای VS Code / JetBrains یا بهصورت یک برنامه مستقل شناسایی کنید
2. ترافیک را با mitmproxy ضبط کنید تا میزبانهای API و ساختار endpointها مشخص شوند
3. سازوکار احراز هویت را تعیین کنید
4. بر اساس TOS و میزان قابلشناسایی بودن API، درباره ادامهدادن یا صرفنظرکردن تصمیم بگیرید

تا زمان تکمیل بررسی، کارت Trae در داشبورد نشان «در حال بررسی» را همراه با پیوند «گزارش امکانپذیری» نمایش میدهد. stub مربوط به handler در `src/mitm/handlers/trae.ts` یک خطای ساختاریافته `هنوز پیادهسازی نشده است` ایجاد میکند.

### عاملهای موجود در فهرست کارهای آتی (نیازمند MITM — بدون پشتیبانی از URL پایه سفارشی)

ابزارهای زیر در نسخههای فعلی خود از URLهای پایه سفارشی پشتیبانی نمیکنند؛ بنابراین MITM تنها مسیر رهگیری است. ارزیابی امکانپذیری آنها هنوز در انتظار انجام است:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — مجزا از Kiro IDE)
- **Cowork** (برنامه دسکتاپ Anthropic)

نکته: GitHub Copilot CLI ≥v1.0.19 از `COPILOT_PROVIDER_BASE_URL` پشتیبانی میکند — برای این ابزار بهجای MITM از پیکربندی مستقیم استفاده کنید.
