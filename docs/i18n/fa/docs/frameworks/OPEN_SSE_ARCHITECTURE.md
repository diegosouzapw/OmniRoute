> **خلاصه**: `open-sse/` موتور اصلی استریم است که تمام درخواستهای LLM در OmniRoute را اجرا میکند. این بخش شامل حدود ۱٬۴۰۰ فایل است که خط لولهٔ درخواست، اجراگرها، سرویسها، سرور MCP و لایهٔ ترجمه را پیادهسازی میکنند. این راهنما توضیح میدهد که این اجزا چگونه در کنار یکدیگر کار میکنند.

**منبع:** `open-sse/` (بستهٔ workspace، حدود ۱٬۴۴۰ فایل غیرآزمایشی `.ts`)

## چرا یک بستهٔ Workspace جداگانه؟

`open-sse/` به چند دلیل یک **workspace مستقل** در monorepo مربوط به OmniRoute است:

1. **قابلیت استفادهٔ مجدد** — `open-sse` با نام `@omniroute/open-sse` در npm منتشر میشود؛ بنابراین پروژههای دیگر میتوانند بهطور مستقل از آن استفاده کنند
2. **مرزبندی شفاف** — موتور استریم از لایهٔ UI/DB مختص OmniRoute جدا شده است
3. **کارایی** — این موتور هیچ وابستگیای به Next.js ندارد و در نتیجه شروع سرد سریعتری را در محیطهای CLI/serverless ممکن میکند
4. **نسخهبندی** — `open-sse` میتواند با چرخهٔ زمانی مستقل خود منتشر شود

```json
// package.json
"workspaces": ["open-sse"]
```

## خط لولهٔ درخواست

هر درخواست LLM از یک **خط لولهٔ ۵مرحلهای** عبور میکند:

```
                              ┌──────────────┐
   درخواست HTTP               │  ۱. مسیریابی │   حل combo، انتخاب مدل
   (مسیر Next.js)             └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  ۲. ترجمه    │   تبدیل قالب (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  ۳. اجرا     │   اجراگر ارائهدهنده، HTTP، تلاش مجدد، قطعکننده
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  ۴. استریم   │   تبدیل SSE، فشار معکوس
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  ۵. ثبت      │   رهگیری مصرف، گزارش فراخوانی، طبقهبندی خطا
                              └──────┬───────┘
                                     │
                                     ▼
                              پاسخ HTTP (SSE یا JSON)
```

### مرحلهٔ ۱: مسیریابی (services/combo.ts)

**نقطهٔ ورود**: `handleComboChat()` در `services/combo.ts`

درخواست را به یک چندتایی مشخص `(provider, model, account, credentials)` نگاشت میکند:

- یافتن combo بر اساس شناسه (یا ساخت یک combo مجازی برای مدلهای `auto/*`)
- اعمال راهبرد مسیریابی (اولویت، وزندار، نوبتگردشی و غیره)
- حذف ارائهدهندگان ناسالم (قطعکنندهٔ مدار)
- انتخاب هدف قابلاستفادهٔ بعدی

برای مدلهای `auto/*`، این مرحله همچنین:

- الگوریتم **امتیازدهی ۱۶عاملی** (`services/autoCombo/`) را اجرا میکند
- یک جفت `provider+model` را بر اساس سلامت، هزینه، تأخیر و عوامل دیگر انتخاب میکند

### مرحلهٔ ۲: ترجمه (translator/)

اگر قالب مبدأ (برای مثال OpenAI) با قالب مقصد (برای مثال Claude) متفاوت باشد، درخواست **ترجمه** میشود:

- اعلان سیستمی → پیام سیستمی
- تعریف ابزارها → قالب ابزار مختص ارائهدهنده
- پارامترهای استدلال/تفکر → معادلهای مختص ارائهدهنده
- عادیسازی نقش پیام (`developer` → `system` برای ارائهدهندگان غیر OpenAI)

فایل `translator/index.ts` موارد زیر را در دسترس قرار میدهد:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### مرحلهٔ ۳: اجرا (executors/)

**نقطهٔ ورود**: `getExecutor(providerId).execute(request, options)`

تمام ارائهدهندگان از طریق سازوکار جایگزین کارخانهٔ `getExecutor()` از `DefaultExecutor` (`executors/default.ts`) استفاده میکنند. اجراگر:

- URL بالادستی را میسازد (`buildUrl()`)
- هدرهای مختص ارائهدهنده را اضافه میکند (`buildHeaders()`)
- بدنهٔ درخواست را تبدیل میکند (`transformRequest()`)
- درخواست HTTP را با تلاش مجدد و عقبنشینی نمایی ارسال میکند
- در صورت نیاز، نوسازی احراز هویت را مدیریت میکند (ارائهدهندگان OAuth)

تمام اجراگرها از `BaseExecutor` (`executors/base.ts`، با ۱۱۷۰ خط کد) ارثبری میکنند که قابلیتهای زیر را فراهم میکند:

- منطق مشترک تلاش مجدد
- یکپارچهسازی پروکسی
- یکپارچهسازی قطعکنندهٔ مدار
- هوکهای ثبت مصرف

### مرحلهٔ ۴: استریم (utils/stream.ts)

برای پاسخهای استریمی، اجراگر یک **ReadableStream** برمیگرداند. هندلر:

- دادهها را از یک تبدیل SSE عبور میدهد (`createSSETransformStreamWithLogger`)
- برای تشخیص اتصالهای قطعشده، پینگهای heartbeat اعمال میکند
- قطع اتصال کلاینت را بهدرستی مدیریت میکند (`pipeWithDisconnect`)
- برای کلاینتهای غیراستریمی، SSE را به JSON تبدیل میکند

برای پاسخهای غیراستریمی، اجراگر یک شیء JSON تجزیهشده برمیگرداند که بدون تغییر عبور داده میشود.

### مرحلهٔ ۵: ثبت (services/usage.ts)

پس از پاسخ (موفق یا ناموفق)، اطلاعات مصرف ثبت میشود:

- `prompt_tokens`، `completion_tokens` و `cached_tokens` از پاسخ
- `cost_usd` محاسبهشده بر اساس دادههای قیمتگذاری
- `latency_ms`، `status` و در صورت ناموفق بودن `error_class`
- ذخیرهشده در جدول `usage_history`

مصنوعات گزارش فراخوانی (در صورت فعال بودن) در `${DATA_DIR}/call_logs/` نوشته میشوند.

## بررسی عمیق فایلهای کلیدی

### chatCore.ts (5977 خط)

**مدیریتکنندهٔ اصلی درخواستها**. با وجود حجم زیاد، ساختار روشنی دارد:

```ts
// ساختار شبهکد chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. احراز هویت + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. اعتبارسنجی بدنه
  const body = await parseRequestBody(request);

  // 3. تشخیص قالب + ترجمه
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. مسیریابی ترکیبی
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // ادامه با هدف بعدی
    }
  }

  // 5. جایگزین اضطراری
  return await emergencyFallback(body);
}
```

با وجود اینکه یک تابع بسیار بزرگ است، در قالب **بخشهای توضیحگذاریشدهای** سازماندهی شده که با خط لولهٔ ۵مرحلهای مطابقت دارند.

### combo.ts (4456 خط کد)

**موتور مسیریابی** که یک ترکیب را به اهداف مرتبشده تبدیل میکند.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

از **۱۹ راهبرد مسیریابی** پشتیبانی میکند (به `src/shared/constants/routingStrategies.ts` مراجعه کنید):

| راهبرد              | رفتار                                                              |
| ------------------- | ------------------------------------------------------------------ |
| `priority`          | فهرست مرتبشده بر اساس هدف نخست                                     |
| `weighted`          | انتخاب احتمالاتی بر اساس وزن هر هدف                                |
| `round-robin`       | پیمایش چرخهای اهداف بهترتیب                                        |
| `context-relay`     | انتقال زمینه میان اهداف                                            |
| `fill-first`        | تکمیل سهمیه پیش از رفتن به هدف بعدی                                |
| `p2c`               | قدرت دو انتخاب                                                     |
| `random`            | انتخاب تصادفی یکنواخت                                              |
| `least-used`        | انتخاب گزینهای با کمترین استفادههای اخیر                           |
| `cost-optimized`    | ارزانترین هدف سالم در اولویت                                       |
| `reset-aware`       | آگاه از بازههای بازنشانی ارائهدهنده                                |
| `reset-window`      | مسیریابی مبتنی بر بازهٔ بازنشانی                                   |
| `headroom`          | هدفی با بیشترین ظرفیت باقیماندهٔ سهمیه در اولویت                   |
| `strict-random`     | کاملاً یکنواخت (بدون وزندهی کیفی)                                  |
| `auto`              | استفاده از امتیازدهی ۱۶عاملی (`autoCombo/`)                        |
| `lkgp`              | آخرین ارائهدهندهٔ سالم شناختهشده در اولویت                         |
| `context-optimized` | بهترین گزینه برای درخواستهای دارای زمینهٔ طولانی                   |
| `fusion`            | ارسال موازی به یک پنل و سپس ترکیب نتایج توسط یک داور (`fusion.ts`) |

### base.ts (1170 خط کد)

**اجراکنندهٔ انتزاعی** که هر ۱۰۷ اجراکننده از آن ارثبری میکنند. شامل موارد زیر است:

- `buildUrl()` — ساخت پیشفرض URL (زیرکلاسها برای موارد سفارشی آن را بازنویسی میکنند)
- `buildHeaders()` — هدرهای پیشفرض (احراز هویت، نوع محتوا)
- `transformRequest()` — بهصورت پیشفرض، عبور بدون تغییر
- `execute()` — حلقهٔ اصلی HTTP همراه با تلاش مجدد/عقبنشینی/قطعکننده

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // همهٔ ارائهدهندگان سازگار با OpenAI/Anthropic را مدیریت میکند
  // ارائهدهندگان پیکربندیها (URL، احراز هویت، هدرها) را ثبت میکنند، اما منطق اجراکننده را بهاشتراک میگذارند
}
```

رفتار اختصاصی هر ارائهدهنده (هدرهای احراز هویت، URL پایه، هدرهای نسخه) از طریق رجیستری ارائهدهندگان پیکربندی میشود، نه کلاسهای اجراکنندهٔ جداگانه.

````
## سرویسها (117 ماژول)

سرویسها، **ماژولهای متمرکز و تکمنظورهای** هستند که هندلرها آنها را با یکدیگر ترکیب میکنند. دستهبندیهای اصلی:

### مسیریابی و ترکیب

- `combo.ts` — نقطهٔ ورود درخواستهای مسیریابیشده بهصورت ترکیبی
- `services/autoCombo/` — امتیازدهی 16 عاملی، 8 راهبرد مسیریابی خودکار
- `wildcardRouter.ts` — تطبیق مسیرهای دارای نویسهٔ عام (`gpt-*`)
- `modelFamilyFallback.ts` — جایگزینی درونخانوادگی T5

### محدودسازی نرخ و سهمیه

## اجراکنندهها (بیش از 75 فایل)

برای هر ارائهدهنده یک فایل وجود دارد. همهٔ آنها `BaseExecutor` را توسعه میدهند و موارد متفاوت را بازنویسی میکنند.

### الگوهای رایج

ارائهدهندهها از طریق `getExecutor(providerId)` تفکیک میشوند که اجراکنندهٔ پیکربندیشده را برمیگرداند. ارائهدهندگان سازگار با OpenAI/Anthropic از `DefaultExecutor` (`executors/default.ts`) استفاده میکنند. رفتار مختص هر ارائهدهنده (نشانی پایه، هدرهای احراز هویت و نسخهٔ API) در `open-sse/config/providers/` پیکربندی میشود، در حالی که تبدیل بدنهٔ درخواست در `open-sse/translator/` انجام میشود.

**نشانی سفارشی** از طریق پیکربندی ارائهدهنده تنظیم میشود:

```ts
// پیکربندی ارائهدهنده در open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**احراز هویت سفارشی** از طریق پیکربندی احراز هویت رجیستری ارائهدهنده (کلید API، OAuth و پروفایلهای هدر) مدیریت میشود.

تبدیلهای **بدنهٔ سفارشی درخواست** (برای مثال، جداکردن `system` از `messages` توسط Anthropic) بهازای هر ارائهدهنده در `open-sse/translator/` ثبت میشوند.

````

### کارخانهٔ اجراکننده

`executors/index.ts` تابع `getExecutor(providerId)` را صادر میکند:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

فرایند تفکیک از طریق `ExecutorRegistry` (`executors/registry.ts`) انجام میشود: هر اجراکنندهٔ تخصصی در جدول داخلی `executors/index.ts` تعریف شده و هنگام بارگذاری ماژول از طریق `registerExecutor(alias, instance)` ثبت میشود؛ `getExecutor()` رجیستری را بررسی میکند و برای هر ارائهدهندهای که ورودی تخصصی نداشته باشد، به یک `DefaultExecutor` یادسپاریشده بازمیگردد. نگاشت کامل نام مستعار ← اجراکننده توسط آزمون طلایی `tests/unit/executor-map-golden.test.ts` مشخص شده است.

## مترجمها

ترجمه بین **3 قالب**: OpenAI، Anthropic، Gemini، بهعلاوه Responses API جدید.

### زمان انجام ترجمه

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

ترجمههای رایج:

- `OpenAI → Anthropic`: فیلد جداگانه `system`، هدر `x-api-key`
- `OpenAI → Gemini`: استفاده از `contents` بهجای `messages`، بههمراه `systemInstruction`
- `OpenAI → Responses API`: آرایه `input`، وضعیت `previous_response_id`

### موارد خاص پشتیبانیشده

- نقش `developer` → تبدیل به `system` برای سرویسهای غیر OpenAI
- نقش `system` → ادغام در نخستین پیام کاربر برای GLM/ERNIE
- `json_schema` → تبدیل به `responseMimeType` و `responseSchema` در Gemini
- `tools` → تبدیل به قالب ابزار مختص هر ارائهدهنده
- پارامترهای تفکر (o1، Claude) → معادلهای مختص هر ارائهدهنده

## سرور MCP

`open-sse/mcp-server/` سرور **Model Context Protocol** را پیادهسازی میکند:

- **110 ابزار** (مدیریت ارائهدهنده، ترکیبها، حافظه، کش، فشردهسازی، پروکسی، مهارتها، بازیسازی، افزونهها، Notion، Obsidian، پیکره محلی)
- **3 روش انتقال**: stdio، SSE، Streamable HTTP
- **33 دامنه دسترسی** برای مجوزدهی دقیق

### ثبت ابزارها

ابزارها بهصورت فایلهای مستقل در `open-sse/mcp-server/tools/` ثبت میشوند و هرکدام یک نام، طرحواره، کنترلکننده و دامنه دسترسی صادر میکنند:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### روشهای انتقال

```ts
// stdio (استفاده در CLI)
startMcpStdio(server);

// SSE (استریم مبتنی بر HTTP)
startMcpSse(server, port);

// Streamable HTTP (روش مدرن MCP)
startMcpStreamable(server, port);
```

### مجوزدهی

هر فراخوانی ابزار تحت بررسی دامنههای دسترسی (`open-sse/mcp-server/auth/`) قرار میگیرد:

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## تبدیلکنندهها

`open-sse/transformer/` بین قالبهای **Chat Completions** و **Responses API** تبدیل انجام میدهد.

### چرا یک تبدیلکننده جداگانه؟

Responses API قالب جدید OpenAI با **مکالمات دارای وضعیت** (`previous_response_id`) است. هنگامی که یک کلاینت درخواستی با قالب Responses ارسال میکند، OmniRoute:

1. در داخل، Responses را به Chat Completions تبدیل میکند
2. آن را به ارائهدهنده ارسال میکند (هر ارائهدهندهای که از Chat Completions پشتیبانی کند)
3. پاسخ را دوباره به قالب Responses تبدیل میکند
4. پاسخ تبدیلشده را بهصورت استریم برای کلاینت ارسال میکند

تبدیلکننده (`transformer/responsesTransformer.ts`) مورد زیر را فراهم میکند:

```ts
createResponsesApiTransformStream(): TransformStream
```

این تبدیلکننده موارد زیر را مدیریت میکند:

- رویدادهای `response.output_item.added`
- رویدادهای `response.output_text.delta`
- رویداد `response.completed`
- نگاشت فراخوانی ابزار (`function_call` ↔ `tool_calls`)

## پیکربندی

`open-sse/config/` لایه پیکربندی را در خود نگه میدارد:

| فایل                          | هدف                                             |
| ----------------------------- | ----------------------------------------------- |
| `providerRegistry.ts`         | رجیستری مدلهای چت بر روی کاتالوگ 352 ارائهدهنده |

| `defaultThinkingSignature.ts` | امضای پیشفرض تفکر Claude                        |
| `modelStrip.ts` (در سرویسها)  | حذف فیلدها بهصورت مختص هر ارائهدهنده            |

### طرحواره رجیستری ارائهدهندگان

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
```

اعتبارسنجی Zod هنگام بارگذاری ماژول تضمین میکند که تمام پیکربندیهای ارائهدهندگان معتبر باشند.

## افزودن یک مؤلفه جدید

### افزودن یک سرویس جدید

1. فایل `open-sse/services/[serviceName].ts` را با مسئولیتی متمرکز ایجاد کنید
2. تابع هندلر اصلی و تمام ثابتها را export کنید
3. تستهای واحد را در `tests/unit/services/[serviceName].test.mjs` اضافه کنید
4. آن را در خط لوله درخواست در `handlers/chatCore.ts` یکپارچه کنید (اگر مرتبط با مسیریابی است)
5. اگر سرویس بر انتخاب مقصد تأثیر میگذارد، منطق مسیریابی را در `combo.ts` بهروزرسانی کنید
6. آن را در این فایل مستند کنید

### افزودن یک اجراکننده جدید

1. فایل `open-sse/executors/[provider].ts` را با گسترش `BaseExecutor` ایجاد کنید
2. آن را در `config/providerRegistry.ts` ثبت کنید
3. آن را به کارخانه `executors/index.ts` اضافه کنید
4. تستهای واحد اجراکننده را اضافه کنید
5. آن را در `docs/architecture/ARCHITECTURE.md` مستند کنید

### افزودن یک ابزار MCP جدید

1. فایل `open-sse/mcp-server/tools/[category]Tools.ts` را ایجاد یا بهروزرسانی کنید
2. شِمای Zod را برای ورودیها تعریف کنید
3. ابزار را در `mcp-server/index.ts` ثبت کنید
4. آن را به ماتریس محدوده در `mcp-server/auth/` اضافه کنید
5. تستهای واحد را اضافه کنید
