بازرس ترافیک، اشکالزدای داخلی ترافیک HTTPS در OmniRoute است — ابزاری مشابه Charles Proxy / mitmweb / HTTP Toolkit که **از LLM آگاه** و **از عامل آگاه** است. این ابزار در `/dashboard/tools/traffic-inspector` قرار دارد و ترافیک زنده را از حداکثر ۵ منبع ضبط همزمان دریافت میکند.

**مکان در داشبورد:** `/dashboard/tools/traffic-inspector`
**گروه نوار کناری:** ابزارها (پس از AgentBridge)
**همچنین ببینید:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge حالت ضبط ۱ است.

### معماری در یک پاراگراف

`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) یک بافر حلقهای مشترک درونحافظهای است (بهطور پیشفرض ۱۰۰۰ ورودی، قابل پیکربندی از طریق `INSPECTOR_BUFFER_SIZE`). همه منابع ضبط از طریق `push()` در آن مینویسند. کلاس بافر هر ورودی را با استفاده از `kindDetector.ts` طبقهبندی میکند (تشخیص میدهد که آیا یک درخواست LLM است یا خیر)، یک `contextKey` را محاسبه میکند (اثر انگشت SHA-256 از اعلان سیستمی) و از طریق `globalTrafficBuffer.subscribe()` آن را برای همه مشترکان WebSocket پخش میکند. داشبورد از طریق `GET /api/tools/traffic-inspector/ws` متصل میشود و هنگام اتصال یک تصویر لحظهای دریافت میکند و پس از آن رویدادهای `new`/`update`/`clear` را دریافت میکند.

## §2 حالتهای ضبط

بازرس ترافیک از **۵ منبع ضبط همزمان** پشتیبانی میکند. هرکدام را میتوان بهطور مستقل فعال یا غیرفعال کرد. فیلد `source` در هر `InterceptedRequest` (`src/mitm/inspector/types.ts`) یکی از مقادیر `"agent-bridge"`، `"custom-host"`، `"http-proxy"`، `"system-proxy"` یا `"tproxy"` است.

### حالت ۱ — AgentBridge (پیشفرض، همیشه فعال)

**منبع:** هندلرهای AgentBridge (`src/mitm/handlers/base.ts`)
**سازوکار:** هر فراخوانی `intercept()` در `MitmHandlerBase`، پیش از فوروارد کردن `hookBufferStart()` و پس از تکمیل `hookBufferUpdate()` را فراخوانی میکند. به هیچ پیکربندی اضافهای نیاز ندارد — بهمحض اجرای AgentBridge کار میکند.
**دامنه پوشش:** ۹ عامل IDE پیکربندیشده در AgentBridge
**نکته:** فیلد `source` در `InterceptedRequest` = `"agent-bridge"`

### حالت ۲ — میزبانهای سفارشی (تغییر مسیر DNS)

**منبع:** فهرست میزبانهای تعریفشده توسط کاربر (جدول `inspector_custom_hosts`)
**سازوکار:** افزودن یک میزبان از طریق رابط کاربری، `127.0.0.1 <host>` را به `/etc/hosts` اضافه میکند (به sudo نیاز دارد). سرور MITM موجود AgentBridge (پورت 443) بهصورت پویا برای میزبان جدید یک گواهی SNI تولید میکند.
**دامنه پوشش:** هر برنامهای که از میزبان اضافهشده استفاده کند — بدون نیاز به تغییر پیکربندی برنامه
**نکته:** `source` = `"custom-host"`

نمونههای کاربرد:

- نظارت بر `api.openai.com` از اسکریپتهای Python
- اشکالزدایی `my-internal-llm.company.com`
- ضبط ترافیک دستگاههای همراه در همان شبکه (از طریق جعل ARP — پیشرفته)

### حالت ۳ — شنونده HTTP_PROXY (پورت 8080)

**منبع:** برنامههایی که از متغیرهای محیطی `HTTP_PROXY`/`HTTPS_PROXY` استفاده میکنند
**سازوکار:** یک شنونده ثانویه روی پورت 8080 (`src/mitm/inspector/httpProxyServer.ts`) که بهعنوان یک پراکسی صریح استاندارد HTTP/HTTPS عمل میکند. تونلهای `CONNECT` (برای HTTPS) و درخواستهای مستقیم HTTP را میپذیرد.
**دامنه پوشش:** هر برنامهای که متغیر محیطی `HTTP_PROXY` را رعایت کند — بدون تغییر DNS و بدون sudo
**نکته:** `source` = `"http-proxy"`

```bash
# ضبط سریع برای یک فرمان:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# ضبط مداوم در یک نشست پوسته:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**محدودیت TLS:** تونلهای HTTPS مبتنی بر `CONNECT` فقط در حد فراداده (میزبان، پورت و زمانبندی) ضبط میشوند — بدنه TLS بهطور پیشفرض رمزگشایی نمیشود. برای بازرسی کامل بدنه، گزینه «رمزگشایی HTTPS در حالت پراکسی» را فعال کنید (اختیاری است و نیاز دارد گواهی AgentBridge مورد اعتماد باشد).

**تداخل پورت:** اگر پورت 8080 در حال استفاده باشد، AgentBridge یک پاسخ 409 با خطای ساختاریافته برمیگرداند. پورت را از طریق متغیر محیطی `INSPECTOR_HTTP_PROXY_PORT` تغییر دهید.

### حالت ۴ — پراکسی سراسری سیستم (پیشرفته، اختیاری)

**منبع:** تنظیمات پراکسی در سطح سیستمعامل (برای همه برنامههای دستگاه اعمال میشود)
**سازوکار:** از APIهای سیستمعامل برای هدایت تمام ترافیک HTTP/HTTPS از طریق شنونده HTTP_PROXY استفاده میکند:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **دامنه پوشش:** هر برنامهای روی دستگاه که تنظیمات پراکسی سیستم را رعایت کند
  **نکته:** `source` = `"system-proxy"`

**سازوکارهای ایمنی:**

- زمانسنج غیرفعالسازی خودکار (پیشفرض ۳۰ دقیقه، قابل پیکربندی از طریق `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES`)
- وضعیت قبلی پراکسی سیستم در پایگاه داده ذخیره و هنگام بازگردانی بازیابی میشود
- اگر کاربر هنگام فعال بودن پراکسی از صفحه خارج شود، داشبورد اعلان «در حال بازگردانی پراکسی سیستم» را نمایش میدهد
- رابط کاربری نشان `⚠ پیشرفته` و یک کادر تأیید صریح را نمایش میدهد

### حالت ۵ — رمزگشایی شفاف TPROXY (Linux، root، اختیاری)

**منبع:** TPROXY هسته + مسیریابی مبتنی بر سیاست (`src/mitm/tproxy/`)
**سازوکار:** اتصالهای TCP خروجی محلی جدید به یک پورت هدف (پیشفرض `443`) را در `mangle OUTPUT` علامتگذاری میکند، یک `ip rule` بستههای علامتگذاریشده را به تحویل محلی تغییر مسیر میدهد و هدف `TPROXY` در `mangle PREROUTING` آنها را به یک شنونده شفاف (**IP_TRANSPARENT**) تحویل میدهد (پورت پیشفرض `8443`). شنونده، TLS را با یک گواهی انتهایی که **برای هر نام میزبان SNI و هنگام نیاز** توسط یک CA پویا صادر شده است خاتمه میدهد، تبادل رمزگشاییشده را ضبط میکند و درخواست را پس از رمزگذاری مجدد به مقصد اصلی فوروارد میکند.
**دامنه پوشش:** میزبانهای مقصد **دلخواه** روی پورت هدف — بدون جعل `/etc/hosts`، بدون متغیر محیطی `HTTP_PROXY` و بدون تغییر پراکسی سراسری سیستم. فرایند رهگیریشده به هیچ تغییر پیکربندی نیاز ندارد، اما باید به CA پویا اعتماد کند.
**نکته:** `source` = `"tproxy"`

**الزامات:** فقط Linux (**IP_TRANSPARENT** مختص Linux است)، قابلیت **CAP_NET_ADMIN** (root) و یک افزونه بومی N-API که باید با زنجیرهابزار C ساخته شود (`npm run build:native:tproxy`). در صورت در دسترس نبودن، گزینه داشبورد غیرفعال میشود و راهنمای «رمزگشایی TPROXY به Linux، دسترسی root و افزونه بومی نیاز دارد» را نمایش میدهد. قواعد فایروال بهصورت تراکنشی اعمال/بازگردانی میشوند (خرابی هرگز یک قاعده `mangle` را باقی نمیگذارد) و هنگام راهاندازی مجدد پاک میشوند. یک سازوکار ضدحلقه مبتنی بر SO_MARK مانع رهگیری مجدد ترافیک فورواردشده و رمزگذاریشده خود پراکسی میشود.

این یک زیرسامانه قابلتوجه با راهنمای اختصاصی اپراتور است — برای دستورالعمل کامل فایروال، CA پویای مبتنی بر هر SNI بههمراه نصبکننده مخزن اعتماد، مسیر صرفاً محلی، جزئیات ضدحلقه و شِمای پیکربندی، به `docs/security/MITM-TPROXY-DECRYPT.md` مراجعه کنید (در git؛ در `/docs` کامپایل نمیشود). این گزینه توسط `GET / POST / DELETE /api/tools/agent-bridge/tproxy` کنترل میشود (توجه: این مسیر زیر پیشوند AgentBridge قرار دارد، نه پیشوند بازرس ترافیک).

```
│ ▎ 14:30 GET  200 3k  🌐 سفارشی ║                                      │

```

### 3.2 فهرست درخواستها (پنل سمت چپ)

- **مجازیسازیشده** (`useVirtualList` + `ResizeObserver`): بدون توقف رابط کاربری، 1000 مورد را مدیریت میکند
- **پیمایش خودکار** همراه با کلیدی برای توقف آن هنگام بررسی
- **وضعیت با کدگذاری رنگی**: سبز (2xx)، زرد (3xx)، قرمز (4xx/5xx)، خاکستری (در حال پردازش)
- **ایموجی عامل**: 🔵 Antigravity، 🟢 Copilot، 🟠 Kiro، 🟣 Codex، 🔷 Cursor، 🟤 Zed، 🟡 Claude Code، ⚫ Open Code، 🌐 میزبان سفارشی
- **نوار رنگی زمینه**: حاشیهٔ چپ 1px که بر اساس `contextKey` (SHA-256 پرامپت سیستم) رنگآمیزی میشود — مکالمات مرتبط را بهصورت بصری گروهبندی میکند
- **بدنهٔ تنبل**: فقط بدنهٔ درخواست انتخابشده در زبانههای جزئیات ساخته میشود (از رندرشدن 1000 بدنهٔ 1MB جلوگیری میکند)

## §4 قابلیتهای آگاه از LLM

### 4.1 تشخیصدهندهٔ نوع (`src/mitm/inspector/kindDetector.ts`)

هر درخواست را با استفاده از ۴ سیگنال بهعنوان `"llm"`، `"app"` یا `"unknown"` دستهبندی میکند:

1. **رجیستری میزبان** — حدود ۱۸ نام میزبان شناختهشدهٔ APIهای LLM (OpenAI، Anthropic، Gemini، Groq، Mistral، Together، Fireworks، Cohere، Perplexity، Hugging Face، OpenRouter، xAI، Moonshot و غیره)
2. **الگوهای مسیر** — `/v1/chat/completions`، `/v1/messages`، `/generateContent`، `/v1/responses` و غیره
3. **ساختار بدنه** — فیلدهای `messages[]` (OpenAI/Claude)، `contents[]` (Gemini)، `prompt` و `input` را تشخیص میدهد
4. **نشانههای عامل کاربر** — وجود `codex`، `claude`، `gemini`، `antigravity`، `kiro`، `copilot` و `cursor` در رشتهٔ UA

میزبانهای سفارشی که از طریق حالت ۲ اضافه میشوند، مقدار `kind` خود را از ورودی فرم به ارث میبرند (مقدار پیشفرض `"custom"` است).

### 4.2 ادغامکنندهٔ SSE (`src/mitm/inspector/sseMerger.ts`)

**پیادهسازی مستقل به روش clean-room.** تجزیهٔ رویدادها از
[الگوریتم رویدادهای ارسالشده از سرور WHATWG](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)
پیروی میکند، درحالیکه بازسازی از طرحوارههای عمومی استریم
[OpenAI](https://platform.openai.com/docs/api-reference/chat/create)،
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) و
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent)
پیروی میکند.

پیام نهایی دستیار را از رویدادهای خام دلتای SSE بازسازی میکند:

- **Anthropic**: مقادیر `content_block_delta` را بر اساس اندیس انباشته میکند؛ از `text_delta`، `input_json_delta` (فراخوانی ابزارها) و `thinking_delta` پشتیبانی میکند
- **OpenAI**: گزینهها/فراخوانیهای ابزار Chat Completions و آیتمهای خروجی Responses API را بر اساس اندیس انباشته میکند
- **Gemini**: مقادیر `candidates[i].content.parts` را انباشته میکند
- **ناشناخته**: رویدادهای خام را بدون تغییر برمیگرداند

زبانهٔ Response یک کلید تغییر وضعیت نشان میدهد: **«رویدادهای خام ↔ ادغامشده»**.

### 4.3 نرمالساز مکالمه (`src/mitm/inspector/conversationNormalizer.ts`)

**پیادهسازی مستقل به روش clean-room.** نرمالسازی بر اساس قراردادهای محلی جعبهسیاه
و طرحوارههای عمومی پیام OpenAI، Anthropic و Gemini تعریف شده است؛ از هیچ کد منبع
پیادهسازی بالادستی استفاده نمیشود.

قالبهای پیام OpenAI، Anthropic و Gemini را پیش از رندر به یک `NormalizedConversation` واحد تبدیل میکند:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // پیامها / محتواها / پرامپت از بدنهٔ درخواست
  response: NormalizedTurn[]; // پاسخ دستیار (ادغامشده از طریق sseMerger)
  contextKey: string | null; // اثر انگشت SHA-256 پرامپت سیستمی
}
```

انواع بلوک: `text`، `tool_use`، `tool_result`. زبانهٔ Conversation بدون توجه به ارائهدهنده از این ساختار استفاده میکند.

### 4.4 رنگآمیزی کلید زمینه (`src/mitm/inspector/contextKey.ts`)

- مقدار `SHA-256` پرامپت سیستمی را محاسبه میکند (اولین پیام `role:system`، یا فیلد `system`، یا `systemInstruction` در Gemini)
- یک پیشوند هگز ۱۲ کاراکتری (`"a3f9c2..."`) برمیگرداند
- فرانتاند کلید را برای نوار حاشیهٔ سمت چپ به یک رنگ HSL قطعی نگاشت میکند
- **فیلتر «زمینهٔ یکسان»**: کلیک روی چیپ `ctx #a3f` فیلتری اضافه میکند تا فقط درخواستهایی با اثر انگشت یکسان نمایش داده شوند

این قابلیت، تشخیص بصری «پرسوناها» یا وظایف مختلفی را که در یک نشست عامل اجرا میشوند آسان میکند.

### 4.5 استخراج فرادادهٔ LLM

برای درخواستهای LLM، زبانهٔ LLM Details موارد زیر را استخراج میکند:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // از بدنهٔ درخواست یا پاسخ
  messages: number; // تعداد نوبتها
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // در صورت استریم بودن پاسخ SSE برابر true است
  mappedTo: string | null; // هدر x-omniroute-mapped
  costEstimateUsd: number | null; // هزینهٔ تخمینی بر اساس قیمتگذاری OmniRoute
}
```

### 4.6 فیلتر زندهٔ درخواستهای در حال اجرا

فیلد `status` درخواست از نوع `number | "in-flight" | "error"` است — بهمحض شروع درخواست،
یک ورودی با مقدار `"in-flight"` افزوده میشود و هنگام رسیدن پاسخ (یا خطا)،
**در همان محل بهروزرسانی میشود**. کلید تغییر وضعیت **«زنده»** در نوار ابزار
(`liveOnly`، کلید i18n برابر `trafficInspector.liveOnly`) فهرست را به ورودیهایی
محدود میکند که `status === "in-flight"` دارند و به شما امکان میدهد اتصالهای باز را بهصورت بیدرنگ مشاهده کنید.

فیلتر یک گزارهٔ خالص سمت کلاینت در
`src/lib/inspector/matchesTrafficFilter.ts` است:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

وضعیت کلید تغییر در `useTrafficFilters` (هوکهای داشبورد بازرس) نگهداری میشود و
با سایر فیلترها (پروفایل، میزبان، عامل، منبع، وضعیت، زمینه) ترکیب میشود.

### 4.7 انتساب فرایند (Linux)

در Linux، هر درخواست رهگیریشده را میتوان به **فرایند محلی مبدأ**
منتسب کرد. دو فیلد اختیاری به `InterceptedRequest` افزوده میشوند:

```ts
pid?: number;          // شناسهٔ فرایند مبدأ (فقط Linux)
processName?: string;  // نام فرایند مبدأ (فقط Linux)
```

`src/mitm/inspector/processAttribution.ts` پورت موقتی _کلاینت_ اتصال را از طریق مراحل زیر
به یک PID و نام نگاشت میکند:

1. خواندن `/proc/net/tcp` و `/proc/net/tcp6` برای یافتن inode سوکت مربوط به
   پورت (`parseProcNetTcpForInode`، یک تجزیهگر خالص که با fixture قابل آزمایش است).
2. اسکن `/proc/<pid>/fd/` برای یافتن یک پیوند نمادین به `socket:[<inode>]`.
3. خواندن نام فرایند از `/proc/<pid>/comm`.

یک کش TTL یکثانیهای، هزینهٔ اسکن procfs را تحت بار محدود میکند. انتساب
بهصورت **best-effort** انجام میشود — هرگونه شکست به `null` منتهی میشود و هرگز ثبت ترافیک را مسدود نمیکند. در
macOS/Windows، تابع مقدار `null` را برمیگرداند (پیادهسازی stub؛ پشتیبانی از `lsof`/`GetExtendedTcpTable`
در ادامه اضافه خواهد شد).

## §5 نشستها

### 5.1 ضبط یک نشست

1. در نوار ابزار روی **"● ضبط نشست"** کلیک کنید ← یک نام وارد کنید (اختیاری)
2. نمایش زنده طبق معمول ادامه مییابد؛ یک نشانگر قرمز چشمکزن عبارت `◉ ضبط · <نام> · 00:42 · 23 درخواست` را نشان میدهد
3. روی **"⏹ توقف"** کلیک کنید ← اسنپشات نشست در `inspector_sessions` و `inspector_session_requests` ذخیره میشود

### 5.2 مشاهده یک نشست ضبطشده

منوی کشویی **نشستها** در نوار ابزار، نشستهای ذخیرهشده را فهرست میکند. با انتخاب هرکدام:

- اسنپشات نشست بارگذاری میشود (حالت ثابت)
- بنری نمایش داده میشود: `در حال مشاهده نشست ضبطشده "<نام>" — [بازگشت به حالت زنده]`
- زبانه آمار با دادههای تجمیعی Recharts در دسترس قرار میگیرد

### 5.3 قالبهای خروجی

هر نشست را میتوان در قالبهای زیر صادر کرد:

| قالب                       | کاربرد                                                                         |
| -------------------------- | ------------------------------------------------------------------------------ |
| **HAR** (بایگانی HTTP 1.2) | سازگار با Chrome DevTools، Charles و Fiddler — قابل واردکردن برای تحلیل آفلاین |
| **JSONL**                  | یک `InterceptedRequest` در هر خط — سازگار با قالب `llm-interceptor`            |

خروجیگرفتن از طریق `GET /api/tools/traffic-inspector/sessions/{id}/export.har` یا دکمه ⬇ در منوی کشویی نشستها انجام میشود.

## §6 امنیت

بازرس ترافیک **تمام ترافیک رهگیریشده HTTPS**، از جمله سرآیندهای احراز هویت و بدنه درخواستها را نمایش میدهد. کنترلهای زیر اعمال شدهاند:

| کنترل                       | جزئیات                                                                                                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **LOCAL_ONLY**              | همه مسیرها و نقطه پایانی WebSocket فقط از طریق loopback قابل دسترسیاند (پیش از احراز هویت در `routeGuard.ts` اعمال میشود)                                                |
| **پوشاندن اطلاعات محرمانه** | اسکنر خطی `maskSecret()`، اعتبارنامههای Bearer مطابق RFC 6750، کلیدهای دارای پیشوند ارائهدهنده و توکنهای مبهم طولانی را پیش از `TrafficBuffer.push()` حذف میکند          |
| **سقف اندازه بدنه**         | بدنههای بزرگتر از `INSPECTOR_MAX_BODY_KB` (پیشفرض 1024 KB) کوتاه شده و اعلان `"(برای حفظ کارایی کوتاه شد)"` نمایش داده میشود                                             |
| **پاکسازی سرآیندها**        | نامها با حروف کوچک میشوند؛ سرآیندهای قاببندی، hop-by-hop و احراز هویت پراکسی حذف میشوند؛ کوکیها کاملاً پوشانده میشوند؛ مقادیر اعتبارنامه به `maskSecret()` واگذار میشوند |
| **CSP**                     | سیاست امنیت محتوای سختگیرانه در صفحات بازرس ترافیک برای جلوگیری از XSS از طریق بدنههای پاسخ تزریقشده                                                                     |
| **عدم ماندگاری پیشفرض**     | `TrafficBuffer` در حافظه نگهداری میشود و با راهاندازی مجدد سرور از بین میرود. نشستها فقط زمانی ماندگار میشوند که صراحتاً ضبط شده باشند                                   |

### قواعد سختگیرانه اعمالشده

| قاعده                             | کاربرد                                                                                        |
| --------------------------------- | --------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | همه پاسخهای خطای HTTP از مسیرهای بازرس ترافیک پاکسازی میشوند                                  |
| **#15 + #17** `isLocalOnlyPath()` | `/api/tools/traffic-inspector/` از نوع LOCAL_ONLY و SPAWN_CAPABLE است (فرمانهای پراکسی سیستم) |

### محدودیتهای شناختهشده

- **حالت پراکسی سراسری سیستم** بر همه برنامههای دستگاه، از جمله کلاینتهای VPN و SSO اثر میگذارد. همیشه آن را همراه با تایمر غیرفعالسازی خودکار استفاده کنید. روی دستگاههای اشتراکی از آن استفاده نکنید.
- **HTTPS از طریق تونل CONNECT**: حالت 3 (HTTP_PROXY) برای مقصدهای HTTPS فقط فراداده تونل را ثبت میکند، مگر اینکه رهگیری TLS فعال شده باشد. این رفتار عمدی است؛ ثبت شفاف بدون مورد اعتماد بودن گواهی AgentBridge، اعتبارسنجی TLS را برای آن برنامهها مختل میکند.
- **رشتههای هاردکدشده در برخی مؤلفهها**: بعضی مؤلفههای رابط کاربری (F7/F8) تعداد کمی رشته هاردکدشده دارند که هنوز تحت پوشش کلیدهای i18n قرار نگرفتهاند. این موارد در گزارش شکاف i18n بهعنوان محدودیت شناختهشده مستند شدهاند و در مرحله بعدی منتقل خواهند شد. رشتههای متأثر، برچسبهای تزئینی رابط کاربری هستند که برای استفاده عملکردی به ترجمه نیاز ندارند.

1. بررسی کنید که سرور همچنان در حال اجرا باشد: `GET /api/tools/traffic-inspector/capture-modes`
2. صفحه را دوباره بارگذاری کنید — WebSocket مجدداً متصل میشود و یک تصویر لحظهای تازه دریافت میکند
3. اگر سرور راهاندازی مجدد شده باشد، بافر درونحافظهای پاک شده است — ورودیهای قدیمی از بین رفتهاند، مگر اینکه یک نشست ضبط شده باشد

### تداخل پورت 8080

اگر حالت HTTP_PROXY راهاندازی نمیشود:

```bash
lsof -i :8080    # فرایند را پیدا کنید
```

پورت را تغییر دهید:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### بازگردانده نشدن پراکسی سیستم

اگر OmniRoute هنگامی که حالت پراکسی سراسری سیستم فعال است از کار بیفتد:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

اگر داشبورد هنگام بارگذاری بعدی تشخیص دهد که وضعیت DB نشاندهنده فعال بودن پراکسی است، گزینه «بازگرداندن پراکسی سیستم» را نیز ارائه خواهد کرد.

### پر شدن بافر

وقتی بافر به `INSPECTOR_BUFFER_SIZE` (مقدار پیشفرض 1000) میرسد، ورودیهای جدید جایگزین قدیمیترین ورودیها میشوند. اگر درخواستهای مهم از دست میروند:

- `INSPECTOR_BUFFER_SIZE` را افزایش دهید (برای مثال، 5000) — این کار در ازای مصرف بیشتر حافظه، نگهداری طولانیتری فراهم میکند
- یک نشست ضبط کنید تا بازه مرتبط در DB ماندگار شود

## §8 مرجع API

همه مسیرها `LOCAL_ONLY` (فقط loopback) و `SPAWN_CAPABLE` (فرمانهای پراکسی سیستم) هستند. به `src/server/authz/routeGuard.ts` مراجعه کنید.

مسیر پایه: `/api/tools/traffic-inspector/`

### مدیریت درخواستها

| روش    | مسیر                        | توضیحات                                                                              |
| ------ | --------------------------- | ------------------------------------------------------------------------------------ |
| GET    | `/requests`                 | فهرست درخواستها (قابل فیلتر: `?profile=llm&host=&agent=&status=&source=&sessionId=`) |
| GET    | `/requests/{id}`            | جزئیات یک درخواست                                                                    |
| DELETE | `/requests`                 | پاک کردن بافر درونحافظهای                                                            |
| POST   | `/requests/{id}/replay`     | اجرای مجدد همان درخواست از طریق مسیریاب OmniRoute                                    |
| PUT    | `/requests/{id}/annotation` | ذخیره یا بهروزرسانی یادداشت یک درخواست                                               |

### WebSocket

| روش | مسیر  | توضیحات                                                                                            |
| --- | ----- | -------------------------------------------------------------------------------------------------- |
| GET | `/ws` | جریان زنده WebSocket. هنگام اتصال `snapshot` و سپس رویدادهای `new`/`update`/`clear` را ارسال میکند |

### خروجیگیری

| روش | مسیر          | توضیحات                                            |
| --- | ------------- | -------------------------------------------------- |

| روش    | مسیر            | توضیحات                                    |

### حالتهای ضبط

| روش  | مسیر                           | توضیحات                                                                                               |
| ---- | ------------------------------ | ----------------------------------------------------------------------------------------------------- |
| GET  | `/capture-modes`               | وضعیت حالتهای AgentBridge / میزبانهای سفارشی / HTTP_PROXY / پراکسی سیستم بههمراه کلید `tls-intercept` |
| POST | `/capture-modes/http-proxy`    | شروع/توقف شنونده HTTP_PROXY (`{action: "start"\|"stop"}`)                                             |
| POST | `/capture-modes/system-proxy`  | اعمال/بازگرداندن پراکسی سراسری سیستم (`{action: "apply"\|"revert"}`)                                  |
| POST | `/capture-modes/tls-intercept` | فعال/غیرفعال کردن رمزگشایی بدنه HTTPS در حالت پراکسی (`{enabled: boolean}`)                           |

> **رمزگشایی TPROXY** (حالت ضبط 5) از طریق مسیری **جداگانه** زیر پیشوند
> AgentBridge کنترل میشود — `GET / POST / DELETE /api/tools/agent-bridge/tproxy` — و نه
> زیر `/api/tools/traffic-inspector/`. به
> `docs/security/MITM-TPROXY-DECRYPT.md` مراجعه کنید (git؛ در `/docs` کامپایل نشده است).
