OmniRoute عاملهای کدنویسی میزبانیشده در فضای ابریِ شخص ثالث (Codex Cloud، Cursor،
Devin، Jules) را بهعنوان وظایف طولانیمدت هماهنگ میکند. هر عامل پشت یک رابط یکپارچه قرار
میگیرد تا کلاینتها بتوانند یک پرامپت + URL مخزن ارسال کنند و بدون درگیر شدن با
APIهای مختص هر ارائهدهنده، نتایج را دریافت کنند.

یک وظیفه Cloud Agent، تکمیل معمولی چت **نیست**. این وظیفه یک واحد کاری پایدار و چندمرحلهای
است که ممکن است از چند دقیقه تا چند ساعت طول بکشد، میتواند یک Pull Request را بهعنوان
مصنوع خود تولید کند و از پیامهای پیگیری و (در برخی ارائهدهندگان) دروازههای تأیید طرح پشتیبانی میکند.

## معماری

```
کلاینت (داشبورد / CLI / API)
  → POST /api/v1/agents/tasks (احراز هویت مدیریتی الزامی است)
    → اعتبارسنجی CreateCloudAgentTaskSchema (Zod)
    → registry.getAgent(providerId)
    → getCloudAgentCredentials(providerId)
      └─ دریافت از getProviderConnections({ provider, isActive: true })
         (ابتدا apiKey، با بازگشت به accessToken)
    → agent.createTask({ prompt, source, options }, credentials)
      └─ HTTP POST به API ارائهدهنده بالادستی
      └─ CloudAgentTask را با id داخلی + externalId برمیگرداند
    → insertCloudAgentTask(...) در cloud_agent_tasks (SQLite)

نظرسنجی (همگامسازی تنبل هنگام خواندن):
  GET /api/v1/agents/tasks/[id]
    → getCloudAgentTaskById(id)
    → agent.getStatus(externalId, credentials)  // وضعیت + فعالیتها را تازهسازی میکند
    → updateCloudAgentTask(...) با وضعیت، نتیجه و completed_at جدید
    → برگرداندن وظیفه سریالسازیشده

تعاملات:
  POST /api/v1/agents/tasks/[id]  بدنه: { action: "approve" | "message" | "cancel" }
    → agent.approvePlan(externalId, credentials)        برای "approve"
    → agent.sendMessage(externalId, message, credentials) برای "message"
    → وضعیت برای "cancel" به "cancelled" تغییر میکند     (فقط محلی)
```

همگامسازی **تنبل** است: وضعیت در هر درخواست `GET /tasks/[id]` از بالادست تازهسازی میشود.
هیچ نظرسنج پسزمینهای وجود ندارد. داشبوردهایی که به وضعیت تازه نیاز دارند باید نقطه پایانی GET را
در بازهای معقول نظرسنجی کنند.

## رابط `CloudAgentBase`

منبع: `src/lib/cloudAgent/baseAgent.ts`

```typescript
export interface AgentCredentials {
  apiKey: string;
  baseUrl?: string;
}

export interface CreateTaskParams {
  prompt: string;
  source: CloudAgentSource;
  options: {
    autoCreatePr?: boolean;
    planApprovalRequired?: boolean;
    environment?: Record<string, string>;
  };
}

export interface GetStatusResult {
  status: CloudAgentStatus;
  externalId?: string;
  result?: CloudAgentResult;
  activities: CloudAgentActivity[];
  error?: string;
}

export abstract class CloudAgentBase {
  abstract readonly providerId: string;
  abstract readonly baseUrl: string;

  abstract createTask(p: CreateTaskParams, c: AgentCredentials): Promise<CloudAgentTask>;
  abstract getStatus(externalId: string, c: AgentCredentials): Promise<GetStatusResult>;
  abstract approvePlan(externalId: string, c: AgentCredentials): Promise<void>;
  abstract sendMessage(
    externalId: string,
    message: string,
    c: AgentCredentials
  ): Promise<CloudAgentActivity>;
  abstract listSources(
    c: AgentCredentials
  ): Promise<{ name: string; url: string; branch?: string }[]>;

  protected mapStatus(raw: string): CloudAgentStatus; // نگاشت ابتکاری رشته بالادستی → enum
  protected generateTaskId(): string; // `task_<ts>_<rand>`
  protected generateActivityId(): string; // `act_<ts>_<rand>`
}
```

متد `CodexCloudAgent.approvePlan` عمداً خطا پرتاب میکند — Codex Cloud بهصورت خودکار برنامهریزی میکند و
هیچ مرحلهای برای تأیید ندارد. متد `CodexCloudAgent.listSources` مقدار `[]` را برمیگرداند.

`CursorCloudAgent` عاملهای پسزمینه / ابری Cursor را از طریق REST API رسمی آن
(`api.cursor.com/v0`) و با یک **کلید API کاربر یا حساب سرویس** کنترل میکند — جایگزین امنتر
و رسمی برای استفاده مجدد از نشست OAuth محیط توسعه Cursor (ارائهدهنده `cursor`،
که دارای هشدار خطر مسدودشدن است). این یک آداپتور REST ساده است (بدون وابستگی بومی
`@cursor/sdk`). متد `approvePlan` خطا پرتاب میکند (عاملهای Cursor بهصورت خودمختار اجرا میشوند)؛
`listSources` مخزنهای در دسترس برای کلید را فهرست میکند. Cursor مقادیر وضعیت را با حروف بزرگ
(`CREATING`/`RUNNING`/`FINISHED`/`ERROR`) برمیگرداند که بهطور صریح به
`CloudAgentStatus` مشترک نگاشت میشوند. `baseUrl` برای هر اعتبارنامه قابل بازنویسی است تا
نسخه/مسیر API بدون تغییر کد اصلاح شود.

```typescript
export const CLOUD_AGENT_STATUS = {
```

## پایگاه داده

منبع: `src/lib/cloudAgent/db.ts` — جدول بهصورت تنبل از طریق
`createCloudAgentTaskTable()` ایجاد میشود (این تابع هنگام وارد کردن ماژول نیز از
`src/lib/cloudAgent/index.ts` فراخوانی میشود).

```sql
CREATE TABLE IF NOT EXISTS cloud_agent_tasks (
  id           TEXT PRIMARY KEY,
  provider_id  TEXT NOT NULL,
  external_id  TEXT,
  status       TEXT NOT NULL DEFAULT 'queued',
  prompt       TEXT NOT NULL,
  source       TEXT NOT NULL,             -- JSON
  options      TEXT DEFAULT '{}',         -- JSON
  result       TEXT,                       -- JSON
  activities   TEXT DEFAULT '[]',          -- JSON
  error        TEXT,
  created_at   TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at   TEXT NOT NULL DEFAULT (datetime('now')),
  completed_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_cloud_agent_tasks_provider ON cloud_agent_tasks(provider_id);
CREATE INDEX IF NOT EXISTS idx_cloud_agent_tasks_status   ON cloud_agent_tasks(status);
CREATE INDEX IF NOT EXISTS idx_cloud_agent_tasks_created  ON cloud_agent_tasks(created_at DESC);
```

`updateCloudAgentTask` برای جلوگیری از تزریق SQL یک **فهرست مجاز ستونها** را اعمال میکند:
`status`، `prompt`، `source`، `options`، `result`، `activities`، `error`،
`completed_at`. هر کلید دیگری در بهروزرسانی جزئی، بدون هشدار حذف میشود.

## REST API — چرخهٔ عمر وظیفه

**احراز هویت:** همهٔ نقاط پایانی `/api/v1/agents/tasks*` به **احراز هویت مدیریتی**
نیاز دارند (`requireCloudAgentManagementAuth` تابع `requireManagementAuth` را از
`src/lib/api/requireManagementAuth` دربر میگیرد). این الزام پس از کامیت `588a0333`
(_«fix(auth): الزام احراز هویت مدیریتی برای APIهای عامل و cooldown»_) اعمال شده است.

| متد     | مسیر                          | هدف                                                          |
| ------- | ----------------------------- | ------------------------------------------------------------ |
| OPTIONS | `/api/v1/agents/tasks`        | پیشدرخواست CORS                                              |
| GET     | `/api/v1/agents/tasks`        | فهرست وظایف (فیلتر: `provider`، `status`، `limit≤500`)       |
| POST    | `/api/v1/agents/tasks`        | ایجاد وظیفه (ارسال به سرویس بالادستی + ذخیرهسازی پایدار)     |
| DELETE  | `/api/v1/agents/tasks?id=...` | حذف وظیفه با شناسهٔ کوئری (سرویس بالادستی را لغو **نمیکند**) |
| OPTIONS | `/api/v1/agents/tasks/[id]`   | پیشدرخواست CORS                                              |
| GET     | `/api/v1/agents/tasks/[id]`   | خواندن وظیفه + همگامسازی تنبل وضعیت از سرویس بالادستی        |
| POST    | `/api/v1/agents/tasks/[id]`   | عملیات: `approve` / `message` / `cancel`                     |
| DELETE  | `/api/v1/agents/tasks/[id]`   | حذف وظیفه با شناسهٔ موجود در مسیر                            |


### لغو (فقط وضعیت محلی)

```bash
curl -X POST http://localhost:20128/api/v1/agents/tasks/<id> \
  -d '{"action":"cancel"}'
```

`cancel` مقدار `status` را در پایگاه دادهٔ محلی به `"cancelled"` تغییر میدهد، اما
ارائهدهندهٔ بالادستی را فراخوانی **نمیکند** — هیچ RPC برای توقف در `CloudAgentBase`
وجود ندارد. برای متوقف کردن هزینهکرد در سرویس بالادستی، وظیفه را در کنسول خود
ارائهدهنده خاتمه دهید.

## REST API — زیرساخت ارائهدهنده ابری

این نقاط پایانی کمکی در `src/app/api/cloud/` توسط کلاینتهای راهدور
(رابط خط فرمان، برنامه Electron یا پردازشگرهای همگامسازی) برای خواندن فراداده اتصال ارائهدهنده
و برطرفسازی نامهای مستعار مدل استفاده میشوند. احراز هویت آنها با یک **کلید API معمولی**
(از طریق `validateApiKey`) انجام میشود، نه با احراز هویت مدیریتیِ مورد استفاده نقاط پایانی وظایف.

| متد  | مسیر                            | هدف                                                                            |
| ---- | ------------------------------- | ------------------------------------------------------------------------------ |
| POST | `/api/cloud/auth`               | اعتبارسنجی کلید API و بازگرداندن فراداده اتصالِ پوشاندهشده + نامهای مستعار مدل |
| PUT  | `/api/cloud/credentials/update` | تازهسازی `accessToken` / `refreshToken` / `expiresAt`                          |
| POST | `/api/cloud/model/resolve`      | برطرفسازی نام مستعار مدل به `{ provider, model }`                              |
| GET  | `/api/cloud/models/alias`       | فهرستکردن همه نامهای مستعار مدل                                                |
| PUT  | `/api/cloud/models/alias`       | تنظیم نام مستعار مدل (و همگامسازی خودکار با Cloud در صورت فعالبودن)            |

`/api/cloud/auth` هرگز مقادیر خام `apiKey` / `accessToken` / `refreshToken` را بازنمیگرداند. این نقطه پایانی
`hasApiKey`، `hasAccessToken`، `hasRefreshToken` و یک پیشنمایش پوشاندهشده
(`maskedApiKey`: ۴ نویسه اول + `****` + ۴ نویسه آخر) را بازمیگرداند.

## برطرفسازی اعتبارنامهها

`getCloudAgentCredentials(providerId)` در `src/lib/cloudAgent/api.ts`:

1. اتصالهای فعال ارائهدهنده را از طریق `getProviderConnections({ provider: providerId, isActive: true })` بارگذاری میکند.
2. برای هر اتصال، `apiKey` (پس از حذف فاصلههای ابتدا و انتها) را ترجیح میدهد. در صورت نبود آن، از `accessToken` استفاده میکند.
3. نخستین توکن غیرخالی را در قالب `{ apiKey: token }` بازمیگرداند.
4. اگر هیچ توکن قابلاستفادهای پیدا نشود، `null` را بازمیگرداند — API با کد `400` و پیام
   `"هیچ اعتبارنامه فعالی برای ارائهدهنده عامل ابری پیکربندی نشده است: <id>"` پاسخ میدهد.

این یعنی عاملهای ابری از همان جدول اتصال ارائهدهنده استفاده میکنند که ارائهدهندگان عادی LLM
استفاده میکنند. برای فعالسازی Jules، یک اتصال فعال با `provider: "jules"`
و یک `apiKey` مقداردهیشده ایجاد کنید.

## داشبورد

منبع: `src/app/(dashboard)/dashboard/cloud-agents/page.tsx`

یک صفحه React با `"use client"` که:

- وظایف را فهرست میکند (با نظرسنجی دورهای از طریق `GET /api/v1/agents/tasks`).
- وظایف جدید را از طریق فرمی ارسال میکند که به `CreateCloudAgentTaskSchema` نگاشت میشود.
- نشانهای وضعیت (`queued`، `running`، `awaiting_approval`، `completed`،
  `failed`، `cancelled`) را نمایش میدهد و خط زمانی `activities[]` را رندر میکند.
- هنگامی که `status === "completed"` باشد، `result.prUrl` / `commitMessage` / `summary` را نمایش میدهد.

## یکپارچهسازی با A2A

عاملهای ابری را میتوان با ثبت یک مهارت A2A که کنترلکننده `tasks/send` خود را
به `getAgent(...).createTask(...)` واگذار میکند و رویدادهای وضعیت وظیفه A2A را
به پروتکل JSON-RPC 2.0 ترجمه میکند، بهعنوان مهارتهای A2A ارائه کرد. به [A2A-SERVER.md](./A2A-SERVER.md) مراجعه کنید.

## افزودن یک عامل ابری جدید

1. فایل `src/lib/cloudAgent/agents/<name>.ts` را با ارثبری از `CloudAgentBase` ایجاد کنید.
2. متدهای `createTask`، `getStatus`، `approvePlan` (یا در صورت کاربرد نداشتن، خطا ایجاد کنید)،
   `sendMessage` و `listSources` را پیادهسازی کنید. برای عادیسازی وضعیت از `this.mapStatus(...)` استفاده کنید.
3. آن را در `src/lib/cloudAgent/registry.ts` با یک `providerId` پایدار ثبت کنید.
4. اجتماع لیترالهای `providerId` را در `src/lib/cloudAgent/types.ts`
   (`CloudAgentTask.providerId` و `CreateCloudAgentTaskSchema`) گسترش دهید.
5. اگر ارائهدهنده به رکورد اتصال نیاز دارد، آن را به `src/shared/constants/providers.ts` اضافه کنید.
   ارائهدهندگان مبتنی بر OAuth همچنین به `src/lib/oauth/providers/` نیاز دارند.
6. آزمونها را در `tests/unit/cloud-agent-*.test.ts` اضافه کنید.
7. این مستند و ثابت `CLOUD_AGENTS` داشبورد را بهروزرسانی کنید.

## پیکربندی

| متغیر محیطی      | کاربرد                                                                    |
| ---------------- | ------------------------------------------------------------------------- |
| `DATA_DIR`       | محل پایگاه داده SQLite که `cloud_agent_tasks` را نگهداری میکند            |
| `JWT_SECRET`     | برای احراز هویت مدیریتی در نقاط پایانی وظایف الزامی است                   |
| `API_KEY_SECRET` | برای رمزنگاری اطلاعات احراز هویت اتصال ارائهدهنده در حالت سکون الزامی است |

در حال حاضر هیچ متغیر محیطی مختص Cloud-Agent وجود ندارد — همه اسرار در جدول
`provider_connections` قرار دارند.
