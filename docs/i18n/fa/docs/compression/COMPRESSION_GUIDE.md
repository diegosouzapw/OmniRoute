> بهصورت خودکار 15 تا 95٪ در محتوای واجد شرایط صرفهجویی کنید. برای یک مرور سریع، به [بخش فشردهسازی README](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) مراجعه کنید.

## نمای کلی

OmniRoute یک خط لولهٔ ماژولار برای فشردهسازی پرامپت پیادهسازی میکند که **بهصورت پیشگیرانه** پیش از رسیدن درخواستها به ارائهدهندگان بالادستی اجرا میشود. این یعنی صرفهجویی در توکنها بهطور شفاف انجام میشود — نیازی به تغییر در گردش کار شما نیست.

```
درخواست کلاینت
  → انتخابگر راهبرد فشردهسازی
    → بازنویسی توسط ترکیب؟ → استفاده از تنظیم ترکیب
    → آستانهٔ فعالسازی خودکار؟ → استفاده از حالت خودکار
    → حالت پیشفرض؟ → استفاده از تنظیم سراسری
    → خاموش؟ → صرفنظر از فشردهسازی
  → حالت فشردهسازی انتخابشده
    → خاموش: بدون فشردهسازی
    → سبک: پاکسازی ایمن فاصلهها/قالببندی (~15%)
    → استاندارد: حذف کلمات زائد به سبک Caveman (~30%)
    → تهاجمی: قدیمیسازی تاریخچه + خلاصهسازی (~50%)
    → فوقفشرده: هرس اکتشافی + تُنُکسازی بلوکهای کد (~75%)
    → RTK: پالایش آگاه از فرمانِ خروجی ترمینال/ابزار (بازهٔ بالادستی 60-90%)
    → انباشته: خط لولهٔ چندموتورهٔ مرتب، معمولاً ابتدا RTK و سپس Caveman (بازهٔ واجد شرایط 78-95%)
  → درخواست فشردهشده → ارائهدهنده
```

## حالتهای فشردهسازی

### خاموش

هیچ فشردهسازیای اعمال نمیشود. همهٔ پیامها بدون تغییر عبور میکنند.

### حالت سبک (~15% صرفهجویی، <1ms تأخیر)

ایمنترین حالت — بدون هیچ تغییر معنایی و فقط با پاکسازی قالببندی:

| تکنیک                    | توضیحات                                   |
| ------------------------ | ----------------------------------------- |
| `collapseWhitespace`     | ادغام خطوط خالی متوالی و فاصلههای انتهایی |
| `dedupSystemPrompt`      | حذف پیامهای سیستمی تکراری                 |
| `compressToolResults`    | فشردهسازی خروجیهای پرحجم ابزار/تابع       |
| `removeRedundantContent` | حذف دستورالعملهای تکراری                  |
| `replaceImageUrls`       | کوتاهسازی URIهای دادهٔ base64 تصاویر      |

**مناسب برای:** استفادهٔ دائمی و گردشکارهای حساس به ایمنی.

### حالت استاندارد (~30% صرفهجویی)

با الهام از [Caveman](https://github.com/JuliusBrussee/caveman) — کلمات زائد و عبارتهای طولانی را با حفظ معنا حذف میکند:

- حذف کلمات زائد («لطفاً»، «فکر میکنم»، «اساساً»، «در واقع»)
- فشردهسازی عبارتهای طولانی («بهمنظور» ← «برای»، «در نتیجهٔ» ← «زیرا»)
- حذف عبارات مؤدبانهٔ محتاطانه («ممکن است...»، «اگر امکان دارد...»)
- بیش از 30 قاعدهٔ regex بهینهشده برای پرامپتهای برنامهنویسی

**مناسب برای:** گردشکارهای روزمرهٔ برنامهنویسی و تیمهای حساس به هزینه.

### حالت تهاجمی (~50% صرفهجویی)

مدیریت هوشمند تاریخچه برای نشستهای طولانی:

- **قدیمیسازی پیامها** — پیامهای قدیمیتر بهتدریج بیشتر فشرده میشوند
- **فشردهسازی نتایج ابزار** — خروجیهای طولانی ابزار کوتاه یا حذف میشوند (خطوط ابتدایی/انتهایی،
  پالایش خطوط منطبق و فشردهسازی کلیدهای JSON)
- **محافظهای یکپارچگی ساختاری** — اطمینان میدهد جفتهای `tool_use` + `tool_result` سازگار باقی بمانند
- **آگاهی از پنجرهٔ محتوا** — محدودیت توکن هر مدل را رعایت میکند

**مناسب برای:** نشستهای طولانی اشکالزدایی و کدبیسهای بزرگ.

### حالت فوقفشرده (~75% صرفهجویی)

بیشترین فشردهسازی برای سناریوهایی که توکن در آنها حیاتی است:

- **هرس اکتشافی** — هرس امتیازمحور توکنهای متن
- **حفظ ساختار** — بلوکهای کد حصاردار، کد درونخطی، URLها و شناسهها
  با نشانگر موقت جایگزین و سپس عیناً بازسازی میشوند و هرگز هرس نمیشوند
- **لایهٔ اختیاری SLM** — در صورت پیکربندی، یک مدل محلی کوچک میتواند هرس را بهبود دهد
- مستقل از حالت تهاجمی: قدیمیسازی پیامها، فشردهسازی نتایج ابزار
  یا خلاصهساز جایگزین را اجرا نمیکند (فقط شکست لایهٔ SLM میتواند یک اجرای جایگزین را از
  مسیر حالت تهاجمی عبور دهد)

**مناسب برای:** زمانی که مرتباً به محدودیتهای محتوا میرسید.

### حالت RTK (بازهٔ بالادستی 60-90%)

حالت RTK برای خروجیهای پرحجم ابزار که در نشستهای عامل برنامهنویسی ظاهر میشوند بهینه شده است:

- کلاسهای فرمان/خروجی مانند `git status`، `git diff`، `git log`، اجراکنندههای آزمون،
  ساختهای TypeScript/Vite/Webpack، ابزارهای ESLint/Biome/Prettier، ممیزیها/نصبهای npm، گزارشهای Docker، خروجی زیرساخت
  و خروجی عمومی پوسته را تشخیص میدهد
- بستههای پالایش JSON را از `open-sse/services/compression/engines/rtk/filters/` اعمال میکند
- پالایههای RTK TOML schema v1 را از فایلهای پروژه یا سراسری `filters.toml`، همراه با اعتبارسنجی آزمونهای درونخطی
  و کنترل اعتماد برای فایلهای پروژه، وارد میکند
- شامل 55 پالایهٔ داخلی همراه با نمونههای راستیآزمایی درونخطی است
- توالیهای کنترلی ANSI، نوارهای پیشرفت، خطوط تکراری و نویزهای غیرقابلاقدام را حذف میکند
- شکستها، خطاها، هشدارها، فایلهای تغییریافته، خلاصهها و بخش انتهایی خروجیهای طولانی را حفظ میکند
- از پالایههای پروژه با کنترل اعتماد، پالایههای سراسری و بازیابی اختیاری خروجی خام با اطلاعات محرمانهٔ پوشاندهشده پشتیبانی میکند

**مناسب برای:** نشستهای عامل شامل رونوشتهای پوسته، ساخت، آزمون، git، grep و خروجی فایل.

### حالت انباشته (بازهٔ واجد شرایط 78-95%)

حالت انباشته چندین موتور فشردهسازی را با ترتیبی قطعی اجرا میکند. خط لولهٔ پیشفرض عبارت است از:

```txt
RTK -> Caveman
```

این ترتیب ابتدا خروجی ترمینال/ابزار را فشرده نگه میدارد و سپس فشردهسازی معنایی Caveman را روی
بخش باقیماندهٔ پرامپتِ زبان طبیعی اعمال میکند. خط لولههای انباشته را میتوان بهصورت سراسری یا از طریق
ترکیبهای فشردهسازی اختصاصیافته به ترکیبهای مسیریابی پیکربندی کرد.

**مناسب برای:** محتوای ترکیبی شامل گزارشهای حجیم ابزار بههمراه دستورالعملهای انسانی یا خلاصههای دستیار.

## محاسبهٔ صرفهجویی بالادستی

OmniRoute صرفهجویی ناشی از فشردهسازی را بر اساس دو منبع مستند میکند: بنچمارکهای پروژههای بالادستی و
ترکیب موتورهای خود OmniRoute.

| منبع    | عدد استفادهشده از README بالادستی در اینجا                                                                            |
| ------- | --------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` توکن خروجی کمتر، میانگین `65%` صرفهجویی در خروجی بنچمارک، بازهٔ `22-87%` و ابزار فشردهسازی ورودی با نرخ `~46%` |
| RTK     | `60-90%` صرفهجویی در خروجی فرمان؛ نشست نمونه با `~118,000 -> ~23,900` توکن، یا `79.7%` صرفهجویی (`~80%`)              |

برای بارهای همپوشان ابزار/بافت، ترکیب پیشفرض OmniRoute موتورها را بهصورت زنجیرهای به کار میگیرد:

```txt
RTK -> Caveman
```

صرفهجویی ترکیبی بهصورت ضربی محاسبه میشود، نه جمعی:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

عدد `78-95%` زمانی صدق میکند که RTK و Caveman هر دو بتوانند همان بار ورودی/بافت را کاهش دهند.
حالت خروجی پاسخ Caveman مستقل است: وقتی فعال باشد، از ارقام صرفهجویی خروجی خود Caveman استفاده کنید (میانگین `65%`،
عدد شاخص `~75%` و بازهٔ `22-87%`). صرفهجویی کلی در هزینه به ترکیب پرامپت/خروجی شما بستگی دارد.

### «واجد شرایط» واقعاً به چه معناست

بازهٔ شاخص 15-95% واقعی است، اما فقط برای محتوای **تکراری یا بیشازحد مفصل** صدق میکند — خطوط خطای تکراری،
گزارش ساختی که یک هشدار را مدام تکرار میکند، یا خروجی بیشازحد بزرگ `grep`/خواندن فایل. این
**به این معنا نیست** که هر درخواست تا این اندازه صرفهجویی ایجاد میکند.

بهصورت تجربی تأیید شده است (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): اجرای
`stacked` (RTK + Caveman) روی یک بلوک `tool_result` با ساختار Anthropic که شامل 300 خط خطای یکسان بود،
**95.93% صرفهجویی در توکن / 96.26% صرفهجویی در نویسه** ایجاد کرد — کاملاً در محدودهٔ بازهٔ اعلامشده.
اما اجرای همان خط لوله روی خروجی عادی و غیرتکراری ابزار (فهرستی تمیز از تطبیقهای `grep`،
خواندن کوتاه یک فایل یا متن مکالمهای معمولی) بهدرستی **صرفهجویی نزدیک به صفر** ایجاد میکند، زیرا
هیچ محتوای تکراریای برای حذف وجود ندارد و `validateCompression()` (`validation.ts`) اجازه نمیدهد
بازنویسیای ارسال شود که بلوکهای کد، URLها، عنوانها، نسخهها یا شناسههای ثابت تماماً با حروف بزرگ را حذف یا تغییر دهد.

این رفتاری مورد انتظار و ایمن است، نه یک باگ: یک نشست کدنویسی که عمدتاً فایلهای تمیز را میخواند یا در آنها
جستوجو میکند، حتی با فعال بودن کامل فشردهسازی نیز صرفهجویی کلی محدودی خواهد داشت؛ درحالیکه نشستی که با یک
حلقهٔ ناموفق یا یک لینتر پرحرف مواجه میشود، روی آن ترافیک از تمام بازهٔ 78-95% بهرهمند خواهد شد. درصد پایین
صرفهجویی تجمیعی در یک نشست را بهتنهایی نشانهٔ پیکربندی نادرست فشردهسازی ندانید — ابتدا بررسی کنید که آیا
خروجی زیربنایی ابزار واقعاً تکراری بوده است یا خیر.

## نمایش بصری صرفهجویی در توکن

```
بدون فشردهسازی:      47K توکن ارسالشده به LLM
با Lite:              40K توکن ارسالشده          (15% صرفهجویی — ایمن و همیشه فعال)
با Standard:          33K توکن ارسالشده          (30% صرفهجویی — قواعد caveman-speak)
با Aggressive:        24K توکن ارسالشده          (50% صرفهجویی — کهنهسازی + خلاصهسازی)
با Ultra:             12K توکن ارسالشده          (75% صرفهجویی — هرس ابتکاری)
با RTK:               19K-5K توکن ارسالشده       (60-90% صرفهجویی در خروجی فرمان/ابزار)
با Stacked:           10K-2.5K توکن ارسالشده     (بازهٔ واجد شرایط 78-95% برای RTK+Caveman)
```

## پیکربندی

### داشبورد

به `Dashboard → Context & Cache` بروید:

- **Caveman** — انتخاب حالت، بستههای زبان، پیشنمایش و پیشفرضهای سراسری
- **RTK** — پیشنمایش فیلتر فرمان، تنظیمات ایمنی RTK و فهرست فیلترها
- **ترکیبهای فشردهسازی** — پایپلاینهای نامگذاریشدهٔ موتور که به ترکیبهای مسیریابی اختصاص داده میشوند
- **آستانهٔ فعالسازی خودکار** — هنگامی که تعداد توکنها از آستانه فراتر میرود، فشردهسازی را بهطور خودکار فعال میکند

### بازنویسی بهازای هر ترکیب

در `Dashboard → Context & Cache → Compression Combos`، یک ترکیب فشردهسازی را به یک ترکیب مسیریابی اختصاص دهید:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

این کار به شما امکان میدهد از فشردهسازی پشتهای برای ارائهدهندگان رایگان/کدنویسی استفاده کنید، درحالیکه حالت سبک را برای اشتراکهای پولی حفظ میکنید.

این تخصیص «بازنویسی بهازای هر ترکیب» کنترلی متفاوت از بازنویسی **حالت فشردهسازی ترکیب مسیریابی** است (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — شِمای این فیلد `rtk`،‏ `stacked` و `omniglyph` را نیز میپذیرد). آن بازنویسی، یک پایپلاین ترکیب فشردهسازی نامگذاریشده را انتخاب نمیکند؛ بلکه فقط فیلد `compressionMode` را تنظیم میکند که `resolveCompressionPlan` آن را بررسی میکند. این گزینه را میتوان روی کارت ترکیب (`Dashboard → Combos`) یا، از #6760 به بعد، برای هر ترکیب مسیریابی در فهرست «Assign to routing» در `Dashboard → Context & Cache → Compression Combos`، درست کنار کادر انتخاب تخصیص پایپلاین که در بالا مستند شده است، تنظیم کرد. هر دو رابط از طریق همان نقطهٔ پایانی `PUT /api/combos/{id}` ذخیره میشوند.

### بازنویسی بهازای هر درخواست

برای بازنویسی طرح فشردهسازی یک درخواست منفرد، هدر درخواست `x-omniroute-compression` را ارسال کنید. این هدر بالاترین اولویت را دارد — بر بازنویسی ترکیب مسیریابی، پروفایل فعال، فعالسازی خودکار و مقدار Default پنل مقدم است. مقادیر ناشناخته نادیده گرفته میشوند (درخواست هرگز رد نمیشود) و کلید اصلی سراسری همچنان همهچیز را کنترل میکند: وقتی فشردهسازی بهصورت سراسری خاموش باشد، هدر نمیتواند آن را روشن کند. مقادیر:

| مقدار         | اثر                                                                                                                 |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| `off`         | برای این درخواست فشردهسازی انجام نمیشود.                                                                            |
| `default`     | پروفایل Default مشتقشده از پنل (پروفایل فعال را نادیده میگیرد). موتورهای اتلافی خاموش میمانند.                      |
| `safe`        | همانند حذف هدر است: فقط حذف موارد تکراری و یکپارچهسازی فاصلههای سفید.                                               |
| `allow-lossy` | طرح اپراتور این درخواست، شامل خلاصهها، فیلترهای مرتبطبودن و بازنویسیهای سبک، حفظ میشود.                             |
| `engine:<id>` | در صورت فعالبودن، یک موتور منفرد؛ برای مثال `engine:rtk`. این گزینهٔ پذیرش بهازای هر درخواست برای آن موتور است.     |
| `<combo>`     | یک ترکیب نامگذاریشده که ابتدا بر اساس نام (بدون حساسیت به بزرگی و کوچکی حروف) و سپس بر اساس شناسه تطبیق داده میشود. |

بدون `allow-lossy`،‏ `engine:<id>` یا یک ترکیب نامگذاریشده، موتورهای اتلافی اعمال نمیشوند. وقتی فشردهسازی روشن باشد، درخواست همچنان از حذف موارد تکراری نشست و یکپارچهسازی فاصلههای سفید بهرهمند میشود.

طرح اعمالشده در هدر پاسخ `X-OmniRoute-Compression: <mode>; source=<source>` بازگردانده میشود؛ در آن، `<source>` یکی از مقادیر `request-header`،‏ `routing-override`،‏ `active-profile`،‏ `auto-trigger`،‏ `default` یا `off` است.

## قدردانیها

قواعد فشردهسازی حالت Standard از پروژه **[Caveman](https://github.com/JuliusBrussee/caveman)** ساخته **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ بیش از 51K) الهام گرفتهاند — پروژه فراگیر «چرا وقتی با توکن کم کار انجام میشود، از توکن زیاد استفاده کنیم». طبق گزارش Caveman، خروجی آن `~75%` توکن کمتر دارد، میانگین صرفهجویی خروجی در بنچمارکها `65%` است، دامنه صرفهجویی خروجی آن `22-87%` است و یک ابزار فشردهسازی ورودی با نرخ `~46%` ارائه میکند.

حالت RTK از **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** ساخته **[RTK AI](https://github.com/rtk-ai)** الهام گرفته است — پروژهای با کارایی بالا برای فشردهسازی خروجی فرمانها در ترمینال، ساخت، آزمون، git و پالایش خروجی ابزارها. طبق گزارش RTK، میزان صرفهجویی `60-90%` است و نشست نمونه در README آن، صرفهجویی `~80%` را نشان میدهد.

## سامانههای پیشرفته فشردهسازی

فراتر از 7 حالت توضیحدادهشده در بالا (منبع، حالتهای `codex-responses` و
`omniglyph` را نیز میپذیرد که در این راهنما پوشش داده نمیشوند)، بخشهای زیر ویژگیهایی
را پوشش میدهند که درون این حالتها یا در کنار آنها کار میکنند: فشردهسازی نتیجه ابزار و فرسایش تدریجی،
مراحل 1 و 2 موتور aggressive هستند (حالت Aggressive و یک مرحله `aggressive` از یک
خط لوله stacked)، خط لوله Stacked نحوه اجرای حالت Stacked است، فشردهسازی آگاه از کش
در زمان فعال بودن فشردهسازی و برای ارائهدهندگان دارای کش، `aggressive` و `ultra` را
به `standard` تنزل میدهد و حالت خروجی Caveman و سبکهای خروجی، دستورالعملهای اختیاری
پرامپت سیستم هستند که بهطور پیشفرض غیرفعالاند و بهجای فشردهکردن درخواست، خروجی مدل را شکل میدهند.

### فشردهسازی آگاه از کش

برخی ارائهدهندگان (مانند Anthropic با قابلیت کشکردن پرامپت) از **کشکردن پرامپت**
پشتیبانی میکنند؛ این قابلیت به آنها اجازه میدهد بخشهایی از پرامپت را کش کنند تا هزینه و تأخیر کاهش یابد. هنگامی که
کش فعال است، فشردهسازی aggressive میتواند در واقع به عملکرد **آسیب بزند**،
زیرا توکنهای کششده را تغییر میدهد و کش را نامعتبر میکند.

ماژول `cachingAware.ts` این مشکل را با **تشخیص زمینه کش** و
**تنظیم متناسب راهبرد فشردهسازی** حل میکند.

#### نحوه کار

1. **تشخیص زمینه کش** — بدنه درخواست را برای یافتن نشانگرهای `cache_control` بررسی میکند
2. **شناسایی ارائهدهندگان دارای کش** — بررسی میکند که آیا ارائهدهنده مقصد از کش پشتیبانی میکند
3. **تنظیم راهبرد** — برای ارائهدهندگان دارای کش، `aggressive`/`ultra` را به `standard` تنزل میدهد
4. **نادیدهگرفتن پرامپت سیستم** — پرامپتهای سیستم معمولاً کش میشوند، بنابراین آنها را فشرده نمیکند

تابع کمکی راهبرد، یک پرچم `deterministicOnly` نیز برمیگرداند، اما سازنده طرح فقط
راهبرد را مصرف میکند — در حال حاضر هیچ بخش پاییندستی این پرچم را نمیخواند.

#### نمونه کد

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← نشانگر کش
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### زمان استفاده

فشردهسازی آگاه از کش **همیشه فعال است** — به هیچ پیکربندیای نیاز ندارد. هر زمان
که فشردهسازی فعال باشد و ارائهدهنده مقصد از کشکردن پرامپت پشتیبانی کند (Anthropic، OpenAI
و غیره)، این قابلیت وارد عمل میشود؛ وجود نشانگرهای صریح `cache_control` الزامی نیست — صرفاً
کشپذیر بودن ارائهدهنده باعث تنزل راهبرد میشود و نشانگرها بهتنهایی هرگز چنین کاری نمیکنند (تشخیص نشانگر
دادههای تلهمتری کش را تغذیه میکند، نه تصمیمگیری راهبرد را).

### فرسایش تدریجی

گفتوگوهای طولانی شامل نوبتهای پیام زیادی میشوند، اما نوبتهای قدیمیتر بهتدریج
ارتباط کمتری پیدا میکنند. ماژول `progressiveAging.ts` **پیامها را بر اساس فاصله نوبت تنزل میدهد**
(فاصله از انتهای گفتوگو اندازهگیری میشود). با مقادیر پیشفرض عرضهشده
(`verbatim: 2, light: 2, moderate: 3`):

- **۲ نوبت آخر (فاصله ≤ 2)**: عیناً حفظ میشوند
- **فاصله 3**: فشردهسازی غارنشینی (حذف کلمات زائد)
- **فاصله 4+**: پیامهای دستیار خلاصه میشوند؛ پیامهای کاربر به خط اولشان
  کاهش مییابند و حداکثر به ۱۲۰ نویسه محدود میشوند؛ نقشهای دیگر دستنخورده باقی میمانند. اعلانهای سیستم، پیامهایی که
  قبلاً قدیمیسازی شدهاند و آخرین پیام کاربر، صرفنظر از فاصله، همیشه عیناً حفظ میشوند.
  هیچچیز بهطور کامل حذف نمیشود و با پیشفرضهای عرضهشده، باند `light`
  غیرقابلدسترسی است (`light` با `verbatim` برابر است).

#### مثال کد

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... ۵۰ نوبت دیگر ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // ۳ نوبت آخر: عیناً
  light: 8, // فاصله <= 8: فشردهسازی سبک
  moderate: 20, // فاصله <= 20: فشردهسازی غارنشینی
  fullSummary: 5, // توسط نوع الزامی است، اما کد باندبندی آن را نمیخواند
  // فاصله > 20: خلاصهشده (دستیار) / حفظ خط اول (کاربر)
});

// saved = تعداد توکنهای صرفهجوییشده
```

#### زمان استفاده

قدیمیسازی تدریجی در حالت `aggressive` **همیشه فعال است** — این مرحلهٔ دوم
`compressAggressive()` است. حالت Ultra آن را اجرا نمیکند. این قابلیت
بهویژه برای موارد زیر مؤثر است:

- نشستهای طولانیمدت کدنویسی
- گفتگوهای چندروزه
- گردشکارهای عاملی با فراخوانیهای متعدد ابزار

### حالت خروجی غارنشینی

حالت خروجی غارنشینی **دستورالعملهای اعلان سیستم** را اضافه میکند که از خود مدل
خروجی مختصر میخواهند — سطح `lite` پاسخهای موجزی میخواهد که جملههای کامل را حفظ میکنند، سطح `full`
از آن میخواهد «مختصر و مثل یک غارنشین باهوش پاسخ دهد»، و سطح `ultra` خروجی تلگرافی میخواهد؛
دستورالعملها فقط درخواست میکنند و نمیتوانند آن را تضمین کنند. درخواستها این دستورالعملها را از طریق
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) دریافت میکنند:
`open-sse/handlers/chatCore.ts` ابتدا انتخاب را با لایهٔ سازگاری عقبرو
(`resolveOutputStyleSelection()` در
`open-sse/services/compression/outputStyles/backCompat.ts`) حل میکند که وقتی `outputStyles`
خالی است، یک `cavemanOutputMode` فعال را در سطح
`cavemanOutputMode.intensity` به سبک خروجی `terse-prose` نگاشت میکند (بخش سازگاری عقبرو در پایین را ببینید)؛ یک انتخاب
غیرخالی `outputStyles` همانطور که هست استفاده میشود و پس از آن `cavemanOutputMode.enabled` و `intensity`
هیچ اثری ندارند، درحالیکه کلید `autoClarity` آن همچنان اعمال میشود. `outputMode.ts`
متن دستورالعملها (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`)، میانبُر محتوا و
تابع کمکی جایگذاری مورداستفادهٔ تزریق را نگه میدارد؛ تزریقکنندهٔ `applyCavemanOutputMode()` خود آن
هیچ فراخوانندهای در محیط عملیاتی ندارد.

#### نحوهٔ کار

این حالت ورودی را فشرده نمیکند. یک بلوک دستورالعمل به اعلان سیستم اضافه میکند
(بخش نحوهٔ تزریق در پایین را ببینید) و هر حالت فشردهسازی ورودی که برای درخواست انتخاب شده باشد
پس از آن، روی بدنهای که اکنون این بلوک را در خود دارد، اجرا میشود. پیش از بند مشترک
محدودیتها که همهٔ سطوح با آن پایان مییابند، متن انگلیسی سطح `full` چنین است:

> «مختصر و مثل یک غارنشین باهوش پاسخ بده. حروف تعریف (a/an/the)، کلمات زائد (just/really/basically/actually/simply)، تعارفات و عبارات تردیدآمیز را حذف کن. عبارتهای ناقص قابلقبولاند. از مترادفهای کوتاه استفاده کن (big نه extensive، fix نه implement). تمام محتوای فنی، کد، خطاها، URLها و شناسهها را دقیق حفظ کن.»

این حالت بهویژه برای موارد زیر بهخوبی کار میکند:

- تولید کد (خروجی موجزتر = توکنهای کمتر)
- پرسشوپاسخ سریع (بدون نیاز به توضیحات مفصل)
- پردازش دستهای (بیشینهسازی توان عملیاتی)

#### زمان استفاده

حالت خروجی غارنشینی **اختیاری** است. هنگامی که فشردهسازی روشن است (`enabled: true`، کلید اصلی
در صفحهٔ تنظیمات فشردهسازی)، آن را با `cavemanOutputMode.enabled` روشن کنید؛ `intensity`
یکی از `lite`، `full` یا `ultra` را انتخاب میکند:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

کلید **حالت خروجی** یک ترکیب فشردهسازی (`outputMode`، با سطحی در `outputModeIntensity`)
همین کلید را برای درخواستهایی تنظیم میکند که آن ترکیب بر آنها اعمال میشود، و ابزار MCP
`omniroute_set_compression_engine` آن را از طریق آرگومان بولی `outputMode`
خود مینویسد. یک انتخاب غیرخالی `outputStyles` بر این کلید اولویت دارد. در
داشبورد، فعالکردن سبک خروجی **نثر موجز** همان بلوک را تزریق میکند (بخش سبکهای خروجی
در پایین را ببینید).

### سبکهای خروجی (کاتالوگ)

حالت خروجی غارنشینی در بالا **مسیر قدیمی تکسبکی** است. فاز ۴ آن را
به کاتالوگی از سبکهای خروجی قابلترکیب تعمیم داد: `OUTPUT_STYLE_CATALOG` در
`open-sse/services/compression/outputStyles/catalog.ts`. هر سبک یک دستورالعمل اعلان سیستم
است که از خود مدل خروجی کمهزینهتری میخواهد؛ سبکها را میتوان
همزمان فعال کرد و آنها به ترتیب کاتالوگ تزریق میشوند.

| سبک                             | `id`          | کاری که انجام میدهد                                                                                                                                                                                             | زبانهای دستورالعمل                            |

بلوکهای کد، مسیرهای فایل، دستورها، خطاها و URLها را دقیق نگه میدارد. متن سطوح
`terse-prose` و `terse-cjk` شناسهها را نیز به این فهرست اضافه میکند.

`terse-cjk` در دو محل به locale برابر با `zh` محدود شده است. صفحه تنظیمات فشردهسازی،
ردیف آن را فقط زمانی نمایش میدهد که زبان رابط کاربری داشبورد چینی (`zh-CN` یا `zh-TW`)
باشد، و `applyOutputStyles()` فقط زمانی آن را تزریق میکند که زبان حلشده درخواست
(بخش انتخاب زبان در پایین را ببینید) `zh` باشد. پنهانکردن ردیف، انتخاب ذخیرهشده
`terse-cjk` را پاک نمیکند: API تنظیمات هر style id را میپذیرد و ذخیرهکردن سبکهای
دیگر در صفحه آن را حفظ میکند. هنگام درخواست، بررسی زبان در `applyOutputStyles()`
تنها محدودیت locale است.

#### نحوه کار تزریق

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) انتخاب را
در برابر کاتالوگ حل میکند (شناسههای ناشناخته و سبکهای ناسازگار با locale حذف
میشوند و هرگز خطا ایجاد نمیکنند؛ انتخابی که به هیچ سبکی منتهی نشود، بدنه را بدون
تغییر باقی میگذارد و با `no_styles` رد میشود)، دستورالعملهای انتخابشده را به ترتیب
کاتالوگ به هم متصل میکند، بند محدودیتها را **یکبار** میافزاید (بهعلاوه بند ایمنی،
`SAFETY_BOUNDARIES` یا ترجمه آن، هنگامی که `less-code` یا `ponytail` انتخاب شده باشد)
و بلوک را با یک نشانگر یکتای idempotency (`[OmniRoute Output Styles]`) آغاز میکند؛
بنابراین اعمال مجدد هیچ اثری ندارد. وقتی زبان حلشده (بخش انتخاب زبان در پایین را
ببینید) ترجمهای داشته باشد، دستورالعمل بومیسازیشده بهجای نسخه انگلیسی تزریق
میشود.

در بدنهای با آرایه غیرخالی `messages`، بررسی idempotency پیش از content bypass اجرا
میشود: اگر نشانگر `[OmniRoute Output Styles]` از قبل در فیلد سطحبالای `system`
(بهشکل رشته یا آرایه بلوکهای محتوا) یا در یک پیام system با محتوای رشتهای وجود
داشته باشد، بدنه با وضعیت `already_applied` بدون تغییر باقی میماند و هیچ بررسی
کلیدواژهای انجام نمیشود. در غیر این صورت، content bypass
(`shouldBypassCavemanOutputMode()` در
`open-sse/services/compression/outputMode.ts`) متن سه پیام آخر را، فارغ از نقش آنها،
بررسی میکند و اگر متن با کلیدواژههای امنیتی، اقدام برگشتناپذیر یا شفافسازی مطابقت
داشته باشد، سبکها را برای کل نوبت رد میکند؛ همین رفتار برای یک توالی حساس به ترتیب
نیز اعمال میشود: `first`، `then`، `after that`، `before`، `rollback` یا `backup` که
حداکثر تا 240 نویسه پس از آنها `delete`، `drop`، `migrate`، `deploy` یا `release`
آمده باشد. این bypass تا زمانی اجرا میشود که کلید **Auto-Clarity Bypass**
(`cavemanOutputMode.autoClarity`، بهطور پیشفرض روشن) فعال باشد؛ خاموشکردن کلید،
بررسی کلیدواژهها را غیرفعال میکند.

وقتی bypass اجازه عبور نوبت را بدهد، `placeSystemInstruction()` (در همان فایل)، که
هرگز `messages[0]` جدیدی ایجاد نمیکند، بلوک را در نخستین مورد موجود از گزینههای زیر
قرار میدهد:

1. یک پیام system ابتدایی با محتوای رشتهای: بلوک پس از متن آن افزوده میشود.
2. فیلد سطحبالای `system`: بلوک پس از متن یک رشته افزوده میشود یا بهصورت بلوک متن
   جدید به آرایه بلوکهای محتوا اضافه میشود.
3. نخستین پیام system بعدی با محتوای رشتهای: بلوک پس از متن آن افزوده میشود.
4. اگر هیچیک از موارد بالا وجود نداشته باشد: بلوک در یک پیام system جدید در انتهای
   `messages` قرار میگیرد.

در بدنهای بدون آرایه `messages` (یا با آرایهای خالی)، هیچ content bypassای اجرا
نمیشود و فیلد سطحبالای `system` بررسی نمیشود. بلوک پس از متن فیلد رشتهای
`instructions` افزوده میشود، مگر اینکه آن فیلد از قبل نشانگر
`[OmniRoute Output Styles]` را داشته باشد؛ در این صورت بدنه با وضعیت
`already_applied` بدون تغییر باقی میماند. اگر بدنه فیلد رشتهای `instructions`
نداشته باشد اما دارای `input` (یک رشته یا آرایه) باشد، بلوک به `instructions` تبدیل
میشود و هر مقدار غیررشتهای قبلی آن فیلد را جایگزین میکند. بدنهای که نه فیلد
رشتهای `instructions` دارد و نه `input` رشتهای یا آرایهای، بدون تغییر باقی
میماند و با وضعیت `no_messages` رد میشود.

#### نحوه فعالسازی

در داشبورد: **زمینهٔ فشردهسازی ← تنظیمات فشردهسازی**
(`/dashboard/context/settings`)، بخش سبکهای خروجی: برای هر سبک یک ردیف با کلید روشن/خاموش
و انتخابگر سطح وجود دارد. سبکها زمانی تزریق میشوند که خود فشردهسازی روشن باشد (کلید اصلی
صفحه، `enabled`). کلید **عبور خودکار از شفافسازی** در صفحهٔ **Caveman**
(`/dashboard/context/caveman`)، داخل کارت **حالت خروجی** قرار دارد. از نظر برنامهنویسی،
پیکربندی فشردهسازی انتخاب را بهشکل زیر ذخیره میکند:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

سازگاری با نسخههای قبلی: تا زمانی که `outputStyles` خالی باشد، تنظیم قدیمی
`cavemanOutputMode.enabled` با شدت `cavemanOutputMode.intensity` به `terse-prose`
نگاشت میشود. سپس بلوک با نشانگر `[OmniRoute Output Styles]` آغاز میشود؛ درحالیکه
تزریقکنندهٔ قدیمی `applyCavemanOutputMode()` عبارت `[OmniRoute Caveman Output Mode]`
را درج میکرد. در زیر نشانگر، متن در زبانهای en، pt-BR، es، de، fr، it، ru، id و vi
با تزریق قدیمی مطابقت دارد؛ در ja و zh، پیش از بند مربوط به مرزها یک فاصلهٔ اضافی وجود
دارد. `terse-prose` به pt-BR، es، de، fr، it، ru، zh، ja، id و vi ترجمه میشود؛ بنابراین
درخواستی که زبان نهایی آن `hu` باشد، متن انگلیسی را دریافت میکند، درحالیکه تزریقکنندهٔ
قدیمی از متن مجاری خود استفاده میکرد.

انتخاب زبان سبک خروجی (`resolveOutputStyleLanguage()` در
`outputStyles/apply.ts`): وقتی `languageConfig.enabled` روشن باشد، `autoDetect` از
جدیدترین پیام کاربر در آرایهٔ `messages` درخواست که دارای متن است (محتوای رشتهای یا
`text` بخشهای محتوای آن) نمونهبرداری میکند و آشکارساز موتور Caveman
(`detectCompressionLanguage()`) را روی آن اجرا میکند. آشکارساز برای متنی که نویسههای
Han داشته باشد اما kana نداشته باشد، `zh` را برمیگرداند؛ در غیر این صورت، هرکدام از
`it`، `pt-BR`، `es`، `de`، `fr`، `ru`، `ja`، `hu` و `id` را که بیشترین تطابق با
نشانهها داشته باشد برمیگرداند و وقتی هیچ تطابقی وجود نداشته باشد، `en` را برمیگرداند —
متنی که قابل طبقهبندی نباشد، انگلیسی در نظر گرفته میشود و هرگز `defaultLanguage`
نیست؛ همچنین `vi` هیچگاه شناسایی نمیشود، هرچند سبکها متن `vi` را ارائه میکنند.
بدنهٔ Responses API نوبتهای خود را در `input` نگه میدارد که از آن نمونهبرداری
نمیشود؛ بنابراین ابتدا `defaultLanguage` و سپس انگلیسی را دریافت میکند. وقتی هیچ
پیام کاربری در `messages` دارای متن نباشد، یا `autoDetect` خاموش باشد، ابتدا
`defaultLanguage` و سپس انگلیسی اعمال میشود. وقتی `languageConfig.enabled` خاموش
باشد، زبان انگلیسی است — مگر اینکه یک ترکیب فشردهسازی برای درخواست اعمال شود (ترکیبی
که به ترکیب مسیریابی درخواست تخصیص یافته، یا ترکیب فشردهسازی پیشفرضی که chatCore
برای خط لولهٔ پشتهای داخلی به آن برمیگردد): اعمال یک ترکیب، `languageConfig.enabled`
را برای آن درخواست روشن میکند و `defaultLanguage` را از بستههای زبانی ترکیب تنظیم
میکند (مقدار ذخیرهشده، اگر یکی از بستههای ترکیب باشد؛ در غیر این صورت نخستین بستهٔ
ترکیب که مقدار پیشفرض آن `en` است)، درحالیکه مقدار ذخیرهشدهٔ `autoDetect` (که بهطور
پیشفرض روشن است) همچنان اعمال میشود. موتور ورودی Caveman زبان بستهٔ قواعد خود را
بهشکل متفاوتی انتخاب میکند — برای هر بخش متنی بهصورت جداگانه و، وقتی تشخیص خودکار
خاموش است، مشروط به `enabledPacks`.

ماتریس سبک × زبان توسط
`tests/unit/compression/output-styles-i18n-matrix.test.ts` تثبیت شده است: هر سبک موجود
در کاتالوگ باید در `BASELINE_LANGUAGES` آزمون ورودی داشته باشد؛ سبکی که محدود به
locale نیست باید ترجمهٔ pt-BR ارائه کند (سبک محدود به locale یعنی `terse-cjk` از این
قاعده مستثناست)، مگر اینکه در `KNOWN_ENGLISH_ONLY` فهرست شده باشد؛ این فهرست فقط
میتواند شامل سبکهایی باشد که اصلاً ترجمهای ندارند — اگر سبک فهرستشده هرگونه ترجمهای
داشته باشد، آزمون شکست میخورد؛ همچنین اگر سبکی زبانی را که ورودی آن در
`BASELINE_LANGUAGES` فهرست کرده است از دست بدهد، آزمون شکست میخورد. برای افزودن یک
سبک، به [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style)
مراجعه کنید.

### فشردهسازی نتیجهٔ ابزار

`compressToolResult()` در `open-sse/services/compression/toolResultCompressor.ts`
متن نتیجهٔ ابزار را با **۵ راهبرد** فشرده میکند. این راهبردها را به ترتیب زیر امتحان
میکند و نخستین راهبرد فعال که بررسی آن با محتوا مطابقت داشته باشد، نتیجه را تعیین
میکند:

1. **`fileContent`**: محتوایی شامل ۳ خط یا بیشتر که در آن دستکم یک خط، با نادیدهگرفتن
   تورفتگی ابتدایی، با `import `، `export `، `function `، `class `،
   `const `، `let `، `var ` یا `return ` (کلمهٔ کلیدی بههمراه یک فاصله) آغاز شود، یا با `if`،
   `for` یا `while` که پس از آن `(` یا ` (` آمده باشد؛ ۲۰ خط اول و ۵ خط آخر آن را نگه میدارد و
   بخش میانی حذفشده را علامتگذاری میکند.
2. **`grepSearch`**: محتوایی با دستکم یک خط بهشکل `<path>:<digits>:`
   که در آن متن پیش از نخستین دونقطه هیچ فاصلهای ندارد؛ فقط همان خطها را، حداکثر تا
   ۳۰ مورد، نگه میدارد و پس از آن تعداد تطبیقهای بیشتر و فهرست فایلهای منطبق را میآورد؛
   همهٔ خطهای دیگر حذف میشوند. یک خط از این نوع برای فعالشدن راهبرد کافی است، بنابراین
   خط گزارشی که با مهر زمانیای مانند `12:30:45` آغاز شود نیز محسوب میشود.
3. **`shellOutput`**: خروجیای که شامل یک دنبالهٔ ANSI CSI (`ESC[` و سپس ارقام یا
   نقطهویرگولها و بعد یک حرف، مانند کدهای رنگ) یا یک `$` باشد که در هر جای متن پس از آن
   فاصله آمده است، این دنبالهها را از دست میدهد (سایر دنبالههای گریز، مانند `ESC[?25l` یا یک
   دنبالهٔ عنوان پنجرهٔ OSC، نگه داشته میشوند) و ۵۰ خط آخر خود را نگه میدارد، درحالیکه
   خطهای تکراری متوالی ادغام میشوند. ازآنجاکه این بررسی پیش از `json` و `errorMessage`
   اجرا میشود، خروجی JSON یا خطایی که چنین `$`ای داشته باشد، هنگام روشنبودن
   `shellOutput` هرگز به آنها نمیرسد.
4. **`json`**: یک بار JSON با بیش از ۲٬۰۰۰ نویسه که (پس از
   فاصلهٔ اختیاری) با `{` یا `[` آغاز شود و با موفقیت تجزیه شود، خلاصه میشود: آرایهای با بیش
   از ۷ آیتم، ۵ آیتم اول و ۲ آیتم آخر و تعداد کل آیتمهای خود را نگه میدارد، و یک شیء ۲۰
   کلید اول خود را نگه میدارد، بهطوریکه مقدار هر شیء یا آرایهٔ تودرتو با جاینگهدار `{…N keys}`
   جایگزین میشود (برای آرایه، N طول آن است) و نشانگر `_remaining_<N>_keys` تعداد کلیدهای
   حذفشده پس از ۲۰ کلید اول را نشان میدهد. مقادیر اسکالر بهطور کامل کپی میشوند، بنابراین
   شیئی با ۲۰ کلید یا کمتر که هیچ مقدار تودرتویی ندارد، فقط دوباره تورفتگی میگیرد — نسخهٔ
   کمینهشدهٔ آن نویسههای بیشتری پیدا میکند و بدون تغییر باقی میماند.
5. **`errorMessage`**: خروجیای که در هر جای خود و بدون حساسیت به بزرگی و کوچکی حروف شامل `error:`،
   `error ` (کلمهای که پس از آن یک فاصله آمده باشد، مانند `no error found`)، `[error]`،
   `exception:`، `exception `، `[exception]` یا `traceback` باشد، خط اول،
   ۱۰ خط بعدی و ۳ خط آخر را نگه میدارد و بهجای خطهای بین آنها نشانگر
   `… [N frames elided] …` را قرار میدهد. این نشانگر فقط زمانی ظاهر میشود که پس از خط
   اول بیش از ۱۳ خط وجود داشته باشد، بنابراین خروجی خطای ۱۴خطی یا کوتاهتر خلاصه نمیشود
   (در ۱۲ یا ۱۳ خط، ۳ خط آخر، خطهایی را که از قبل نگه داشته شدهاند تکرار میکنند).

پس از تطبیق یک راهبرد، حتی اگر هیچ صرفهجوییای ایجاد نکند، راهبردهای بعدی
امتحان نمیشوند. وقتی راهبرد منطبقشده هیچ توکن تخمینیای ذخیره نکند (طول ÷ ۴، گردشده به بالا) —
برای مثال، یک فایل کدمانند با ۲۵ خط یا کمتر، یا یک آرایهٔ JSON با بیش از ۲٬۰۰۰
نویسه و ۷ آیتم یا کمتر — موتور تهاجمی نتیجهٔ اصلی ابزار را نگه میدارد:
هر دو فراخواننده (`compressAggressive()` و `compressAnthropicToolResultBlock()`)
هنگامی که `saved` صفر یا کمتر باشد، نسخهٔ اصلی را نگه میدارند، درحالیکه خود `compressToolResult()`
همچنان خروجی آن راهبرد را برمیگرداند. مرحلهٔ نتیجهٔ ابزار حرف آخر را نمیزند:
خلاصهساز جایگزین موتور همچنان میتواند یک پیام `tool` یا `function` با طول بیش
از ۸٬۱۹۲ نویسه (`maxTokensPerMessage`، برابر با ۲٬۰۴۸، ضربدر ۴) را کوتاه کند.

#### زمان استفاده

فشردهسازی نتیجهٔ ابزار مرحلهٔ ۱ موتور تهاجمی است (`compressAggressive()` در
`open-sse/services/compression/aggressive.ts`)، بنابراین در حالت Aggressive و در یک
مرحلهٔ `aggressive` از خط لولهٔ پشتهای اجرا میشود. این قابلیت پیامهای `tool` و `function`
با قالب OpenAI و متن داخل بلوکهای `tool_result` در Anthropic را فشرده میکند. هر راهبرد
کلید مخصوص به خود را زیر `aggressive.toolStrategies` دارد که همگی بهطور پیشفرض روشناند.
در داشبورد، این کلیدها در نمای **پیشرفته** صفحهٔ Caveman قرار دارند، زمانی که فشردهسازی
روشن و حالت پیشفرض Aggressive باشد.

### خط لولهٔ پشتهای

حالت پشتهای **چندین موتور را بهترتیب** اجرا میکند — معمولاً ابتدا RTK
(صرفهجویی ۶۰ تا ۹۰ درصدی در خروجی ابزار)، سپس Caveman روی متن باقیمانده (حدود ۴۶٪
صرفهجویی در ورودی). ترکیب آنها **بازهٔ واجد شرایط ۷۸ تا ۹۵ درصدی** را ایجاد میکند
(ریاضیات صرفهجویی بالادستی در بالا را ببینید): `1 - (1 - 0.60..0.90) × (1 - 0.46)`
بهطور میانگین ≈۸۹٪ است.

#### نحوهٔ کار

```
ورودی (۱۰۰۰ توکن)
  → RTK (فیلتر آگاه از فرمان) → ۲۰۰ توکن
    → Caveman (حذف محتوای زائد) → ۱۰۸ توکن
  → خروجی (۱۰۸ توکن، حدود ۸۹٪ صرفهجویی)
```

#### زمان استفاده

از حالت پشتهای برای موارد زیر استفاده کنید:

- گردشکارهای وابسته به ابزار (کدنویسی عاملمحور، پژوهش)
- پردازش دستهای حساس به هزینه
- زمانی که به حداکثر صرفهجویی در توکن نیاز دارید

خطوط لولهٔ پشتهای از طریق تنظیم سراسری فشردهسازی `stackedPipeline`
پیکربندی میشوند، یا از طریق یک ترکیب فشردهسازی نامگذاریشده که به یک ترکیب مسیریابی
اختصاص یافته است (به بخش بازنویسی بهازای هر ترکیب در بالا مراجعه کنید) — نه از طریق
`modePack` متعلق به یک ترکیب خودکار (آن فیلد فقط وزن انتخاب مدل در ترکیب خودکار را
تغییر میدهد و `stacked` نام معتبری برای بسته نیست).

## بازنویسیهای ترکیب برای فشردهسازی

میتوانید حالت سراسری فشردهسازی را **برای هر ترکیب** بازنویسی کنید تا رفتار آن را
برای کاربردهای مختلف بهدقت تنظیم کنید:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

این قابلیت برای موارد زیر مفید است:

- **ترکیبهای کدنویسی**: برای نشستهای طولانی از حالت `aggressive` استفاده کنید
- **ترکیبهای پرسشوپاسخ سریع**: برای پاسخهای سریع از حالت `lite` استفاده کنید
- **ترکیبهای متکی بر ابزار**: برای بیشترین صرفهجویی از حالت `stacked` استفاده کنید
- **ترکیبهای عملیاتی**: برای ارائهدهندگان دارای کش، بازنویسی را غیرفعال بگذارید — تنظیم همیشهفعال
  و آگاه از کش، حالتهای `aggressive`/`ultra` را بهطور خودکار به `standard` تنزل میدهد
  (حالت قابلانتخابی به نام `cache-aware` وجود ندارد)
