این راهنما نحوه افزودن حسابهای Kiro (دستیار کدنویسی هوش مصنوعی میزبانیشده توسط AWS) به OmniRoute را توضیح میدهد و بر اجرای همزمان چند حساب بدون تداخل نشستها تمرکز دارد.

---

## پیشزمینه: چرا حسابهای Kiro ممکن است با یکدیگر تداخل داشته باشند

بکاند Kiro برای ردیابی نشستهای فعال از ثبت کلاینت AWS SSO OIDC استفاده میکند.
محدودیت مهم این است: **هر ثبت کلاینت OIDC در هر لحظه تنها از یک نشست فعال پشتیبانی میکند**. هنگامی که دستگاه یا کاربر دومی با استفاده از همان کلاینت ثبتشده احراز هویت میکند، بکاند توکن نوسازی حساب اول را نامعتبر میکند.

این همان سازوکاری است که هنگام اجرای `kiro-cli login` روی سیستمی که حساب Kiro دیگری از قبل در آن وارد شده است، مشکل ایجاد میکند — ورود جدید توکن حساب اول را لغو میکند.

---

## OmniRoute چگونه این مشکل را حل میکند (v3.8.0+)

از v3.8.0 به بعد، OmniRoute هنگام هر بار وارد کردن اتصال Kiro، `registerClient()` (AWS SSO OIDC) را فراخوانی میکند. به این ترتیب، هر اتصال OmniRoute ثبت کلاینت OIDC اختصاصی خود را دریافت میکند. از آنجا که هر ثبت کلاینت مستقل است، نوسازی یا احراز هویت مجدد یک حساب بر توکن نوسازی هیچ حساب دیگری تأثیر نمیگذارد.

این جداسازی شامل روشهای وارد کردن توکن نوسازی میشود و احراز هویت با کلید API نیز بهطور کامل از نشستهای نوسازی OIDC اجتناب میکند:

| روش وارد کردن                                   | وضعیت جداسازی                                                                                        |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| جریان کد دستگاه AWS Builder ID / IDC            | از زمان معرفی جریان کد دستگاه، جداشده است                                                            |
| **وارد کردن توکن** (جایگذاری دستی توکن نوسازی)  | از v3.8.0 جداشده است                                                                                 |
| **ورود اجتماعی Google / GitHub**                | از v3.8.0 جداشده است                                                                                 |
| **وارد کردن خودکار** (SQLite مربوط به kiro-cli) | از v3.8.0 جداشده است (مسیر SQLite از قبل جدا بود؛ روش جایگزین مبتنی بر کش SSO اکنون نیز جدا شده است) |
| **کلید API** (کلید بلندمدت CodeWhisperer)       | نشست نوسازی ندارد؛ کلید اعتبارسنجی شده و بهعنوان اعتبارنامه bearer ذخیره میشود                       |

---

## نکته مهاجرت برای اتصالهای ایجادشده پیش از v3.8.0

اتصالهایی که پیش از v3.8.0 وارد شدهاند، ثبت کلاینت OIDC اختصاصی ذخیرهشده در `providerSpecificData` ندارند. این اتصالها همچنان کار میکنند، اما از نقطه پایانی مشترک نوسازی احراز هویت اجتماعی استفاده میکنند؛ در نتیجه، دو اتصال از این نوع هنوز میتوانند یکدیگر را نامعتبر کنند.

**برای دستیابی به جداسازی:** اتصال قدیمی را از **داشبورد ← ارائهدهندگان** حذف کرده و آن را با استفاده از هر یک از جریانهای وارد کردن پشتیبانیشده دوباره وارد کنید. همه اتصالهای تازه ایجادشده بهطور خودکار ثبت کلاینت اختصاصی خود را دریافت خواهند کرد.

## افزودن دو حساب Kiro در کنار یکدیگر

### پیشنیازها

- OmniRoute v3.8.0 یا جدیدتر.
- یک حساب فعال Kiro (ایمیل + گذرواژه، یا ورود با Google یا GitHub).
- در صورت تمایل، یک حساب دوم Kiro.

### مرحله 1: وارد کردن حساب اول

1. **داشبورد ← ارائهدهندگان ← افزودن ارائهدهنده ← Kiro** را باز کنید.
2. یکی از گزینههای زیر را انتخاب کنید:
   - **وارد کردن توکن** — یک توکن نوسازی را که با `aorAAAAAG` شروع میشود جایگذاری کنید.
   - **کلید API** — یک کلید API بلندمدت Kiro / CodeWhisperer را جایگذاری کنید.
   - **ورود با Google / GitHub** — جریان OAuth را در مرورگر تکمیل کنید.
   - **وارد کردن خودکار** — روی دکمه کلیک کنید؛ OmniRoute اعتبارنامهها را از پایگاه داده محلی kiro-cli یا `~/.aws/sso/cache` میخواند.
3. اتصال ذخیره میشود. جریانهای توکن نوسازی بهطور خودکار یک کلاینت OIDC اختصاصی ثبت میکنند. جریانهای کلید API، کلید را با AWS اعتبارسنجی میکنند و توکن نوسازی ذخیره نمیکنند.

### مرحله 2: وارد کردن حساب دوم

مرحله 1 را برای حساب دوم تکرار کنید. از آنجا که هر بار وارد کردن، یک ثبت کلاینت OIDC جداگانه ایجاد میکند، این دو اتصال کاملاً از یکدیگر جدا هستند.

### مرحله 3: تأیید فعال بودن هر دو اتصال

1. **داشبورد ← ارائهدهندگان** — هر دو اتصال Kiro باید وضعیت **فعال** را نشان دهند.
2. **داشبورد ← سلامت** — هر دو اتصال باید بررسی سلامت توکن خود را با موفقیت پشت سر بگذارند.

### مرحله 4: استفاده از یک ترکیب برای مسیریابی بین حسابها

برای توزیع بار یا استفاده از حساب جایگزین، یک ترکیب با هر دو اتصال بهعنوان مقصد ایجاد کنید:

```
kiro/kiro-dev → kiro/kiro-pro
```

برای پیکربندی ترکیب، به [FEATURES.md](./FEATURES.md) و مستندات مسیریابی مراجعه کنید.

## کاربران سازمانی / IDC

برای حسابهای AWS IAM Identity Center (IDC)، از جریان **AWS Builder ID / کد دستگاه IDC**
در مسیر **داشبورد → ارائهدهندگان → Kiro → کد دستگاه** استفاده کنید. جریان کد دستگاه
همیشه کاملاً ایزوله بوده است. برای این اتصالها نیازی به وارد کردن مجدد نیست.

کاربران سازمانی که در یک منطقه غیراپیشفرض AWS فعالیت میکنند، میتوانند هنگام
وارد کردن از طریق Import Token API، منطقه را مشخص کنند:

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

اگر فیلد `region` حذف شود، مقدار پیشفرض آن `us-east-1` خواهد بود.

## جریان وارد کردن کلید API

احراز هویت با کلید API برای اعتبارنامههای bearer بلندمدت Kiro / AWS CodeWhisperer است.
این روش از نوسازی OAuth استفاده نمیکند، بنابراین از نامعتبر شدن نشست مشترک OIDC جلوگیری میکند.

### داشبورد

1. مسیر **داشبورد -> ارائهدهندگان -> Kiro** را باز کنید.
2. **کلید API** را انتخاب کنید.
3. کلید API و منطقه اختیاری AWS را وارد کنید (مقدار پیشفرض `us-east-1` است).
4. OmniRoute کلید را اعتبارسنجی کرده و اتصال را ذخیره میکند.

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### قرارداد داخلی

مسیر API با فراخوانی `KiroService.validateApiKey()` کلید را اعتبارسنجی میکند؛ این متد
از `ListAvailableProfiles` در برابر نقطه پایانی CodeWhisperer/Amazon Q متناظر با منطقه
استفاده کرده و یک `profileArn` را تعیین میکند.

اتصال ذخیرهشده از ساختار زیر استفاده میکند:

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

در زمان اجرا، `KiroExecutor.buildHeaders()` کلید را بهصورت
`Authorization: Bearer <key>` ارسال کرده و `tokentype: API_KEY` را اضافه میکند. فراخوانیهای سهمیه/پروفایل
از همین نشانگر استفاده میکنند تا AWS این bearer را بهعنوان یک کلید API بلندمدت در نظر بگیرد، نه
یک توکن دسترسی OIDC یا اجتماعی.

## انقضای کلاینت OIDC

کلاینتهای عمومی AWS SSO OIDC معمولاً پس از ۹۰ روز منقضی میشوند
(`clientSecretExpiresAt`). OmniRoute برای مشاهدهپذیری، این مُهر زمانی را در `providerSpecificData`
ذخیره میکند. اگر نوسازی یک اتصال پس از حدود ۹۰ روز متوقف شد، اتصال را مجدداً وارد کنید
تا یک ثبت کلاینت OIDC جدید دریافت شود. ثبت مجدد خودکار پس از انقضا
بهعنوان یک بهبود آتی پیگیری میشود.

اتصالهای مبتنی بر کلید API انقضای کلاینت OIDC ندارند، زیرا نوسازی آنها
از طریق AWS SSO OIDC انجام نمیشود.

## عیبیابی

### حساب دوم مرتباً از سیستم خارج میشود

- هر دو اتصال را در **داشبورد → ارائهدهندگان** بررسی کنید و تأیید کنید که هرکدام در JSON خام خود
  یک `clientId` غیرتهی نشان میدهند (از طریق آیکون اطلاعات قابل مشاهده است). اگر یکی از اتصالها فاقد
  `clientId` است، پیش از v3.8.0 وارد شده است — آن را مجدداً وارد کنید.

### وارد کردن با خطای «اعتبارسنجی توکن ناموفق بود» مواجه میشود

- مطمئن شوید توکن نوسازی با `aorAAAAAG` شروع میشود.
- مطمئن شوید OmniRoute میتواند به `https://oidc.us-east-1.amazonaws.com` (یا منطقه پیکربندیشده)
  دسترسی داشته باشد. اگر پشت یک پروکسی سازمانی هستید، در
  **داشبورد → تنظیمات → پروکسیها** یک پروکسی در سطح ارائهدهنده تنظیم کنید.

### وارد کردن کلید API ناموفق است

- تأیید کنید که کلید، یک کلید API مربوط به Kiro / CodeWhisperer است، نه یک توکن نوسازی.
- تأیید کنید که منطقه AWS با کلید/حساب مطابقت دارد. مقدار پیشفرض `us-east-1` است.
- کلید باید قادر به فراخوانی `ListAvailableProfiles` باشد؛ در غیر این صورت OmniRoute نمیتواند
  `profileArn` موردنیاز را تعیین کند.

برای مشکلات دیگر، فایل اصلی [TROUBLESHOOTING.md](./TROUBLESHOOTING.md) را ببینید.
