OmniRoute **دو** روش برای استفاده از OpenAI Codex ارائه میدهد:

| ارائهدهنده             | نحوهٔ ارتباط آن با OpenAI                                                                                                                                                                                        | ملاحظهٔ استفاده                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **`codex`**            | توکن OAuth مربوط به ChatGPT/OpenAI شما را مستقیماً برای Responses API بازپخش میکند                                                                                                                               | **بله** — نشست رسمی برای استفاده از طریق پراکسی/مسیریاب مجاز نیست |
| **`codex-app-server`** | **فرمان `codex app-server` متعلق به Codex CLI** را از طریق JSON-RPC/WebSocket کنترل میکند؛ خود CLI مالک OAuth است و آن را دقیقاً مانند یک نشست تعاملی `codex` بهطور خودکار تازهسازی میکند (`~/.codex/auth.json`) | **خیر** — OmniRoute هرگز توکنی را برای API بازپخش نمیکند          |

ازآنجاکه `codex-app-server` هرگز توکنی را بازپخش نمیکند، ملاحظهٔ استفاده
مربوط به بازپخش نشست شامل آن نمیشود. بااینحال، به یک **Codex CLI قابلدسترسی
در URL پیکربندیشدهٔ app-server** نیاز دارد و آن CLI باید **وارد حساب شده باشد**.

## 1. معماری

```
┌─ برنامهٔ OmniRoute ──────────────┐        ┌─ سایدکار codex-app-server ─────────┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                   │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456         │
│  (+ توکن قابلیت)                 │  JSON  │  --ws-auth capability-token         │
│                                  │  RPC   │  مدیریت خودکار OAuth مربوط به OpenAI│
└──────────────────────────────────┘        │  (~/.codex/auth.json، تازهسازی خودکار) │
        │ اشتراکگذاری (والیومهای compose)  └─────────────────────────────────────┘
        ▼
  codex-appserver-token   → توکن قابلیت WS (هر دو آن را mount میکنند)
  codex-appserver-home    → ~/.codex (فایل auth.json توسط داشبورد نوشته و
                             توسط codex app-server در سایدکار خوانده میشود)
```

- سایدکار، پشت یک توکن قابلیت، **فقط** روی شبکهٔ داخلی compose
  (`ws://codex-app-server:1456`) گوش میدهد. این سرویس **هرگز** روی میزبان یا
  اینترنت منتشر نمیشود.
- Codex CLI درون `omniroute:base` تعبیه شده است؛ بنابراین هنگام اجرای سایدکار،
  نیازی به نصب codex روی میزبان یا دستگاه کاربر نیست.

## 2. راهاندازی

```bash
# پشته را همراه با پروفایل سایدکار codex app-server راهاندازی کنید:
docker compose --profile base --profile codex-app-server up -d
# (برای podman: podman compose --profile base --profile codex-app-server up -d)
```

سایدکار در نخستین راهاندازی، توکن قابلیت WS خود را ایجاد میکند (در والیوم
مشترک `codex-appserver-token`) و برنامه همان توکن را از طریق
`OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE` میخواند. نیازی به تنظیم دستی توکن
نیست.

## 3. اتصال + ورود به حساب

1. در داشبورد، یک اتصال برای **OpenAI Codex (App-Server)** اضافه کنید. هیچ کلید
   API یا توکنی لازم نیست (این یک ارائهدهندهٔ بدون احراز هویت است — سایدکار
   مدیریت احراز هویت را بر عهده دارد).
2. اگر Codex CLI سایدکار **هنوز وارد حساب نشده باشد**، بررسی سلامت اتصال پیام
   _«در حال اجرا است، اما وارد حساب نشده است»_ را گزارش میکند (نه یک خطای قرمز
   احراز هویت). از **ورود با ChatGPT** استفاده کنید: این گزینه فرایند استاندارد
   device-OAuth مربوط به Codex را در مرورگر شما اجرا میکند و سپس از طریق
   **اعمال احراز هویت**، فایل `~/.codex/auth.json` را در والیوم مشترک مینویسد
   (همان یکبار ورود، هر دو ارائهدهندهٔ `codex` و `codex-app-server` را پوشش
   میدهد).
3. پس از ورود، بررسی سلامت سبز میشود (هم `/readyz` **و هم** `account/read` را
   بررسی میکند — یعنی سرویس هم فعال است _و هم_ احراز هویت شده است) و شروع به
   کار میکند.

داشبورد هرگز یک فایل سالم و موجود `~/.codex/auth.json` را بازنویسی نمیکند —
فقط زمانی فایل را مینویسد که وجود نداشته باشد یا توکن آن منقضی شده باشد
(همیشه یک نسخهٔ پشتیبان تهیه میشود).

## 4. سناریوهای استقرار

- **اپراتوری با Codex CLI که از قبل احراز هویت شده است** — مسیر `~/.codex`
  میزبان خود را در سایدکار (`codex-appserver-home`) mount کنید و مرحلهٔ ورود را
  نادیده بگیرید.
- **کاربر عمومی، بدون نصب محلی codex** — اهمیتی ندارد: سایدکار CLI را در اختیار
  دارد. کاربر فقط از طریق داشبورد احراز هویت میکند.
- **OmniRoute روی bare-metal (بدون سایدکار، با codex میزبان)** —
  `OMNIROUTE_CODEX_APPSERVER_WS` را به `codex app-server` خودتان اشاره دهید و
  مطمئن شوید codex میزبان وارد حساب شده است؛ اگر فایل اجرایی وجود نداشته باشد،
  راهنمای «codex نصب نشده است» نمایش داده میشود.

## 5. خروجی شبکهٔ خانگی / UDP (افزونهٔ اپراتور، ارائهنشده)

سایدکار عمومی بالا، ترافیک خروجی را از طریق شبکهٔ معمول کانتینر ارسال میکند.
اپراتوری که نیاز دارد ترافیک Codex از طریق یک **خروجی شبکهٔ خانگی** ارسال شود
(برای مثال، یک سایدکار tailscale مبتنی بر TUN که TCP + UDP/QUIC را حمل میکند)،
آن را بهصورت یک override جداگانهٔ compose اجرا میکند؛ این قابلیت عمداً بخشی
از پروفایل ارائهشدهٔ `codex-app-server` نیست. برای این پیکربندی به راهنمای
اجرایی داخلی مراجعه کنید.
