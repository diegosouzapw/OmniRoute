## مرجع سریع

**تازه با OmniRoute آشنا شدهاید؟** از اینجا شروع کنید — این موارد ۹۰٪ مشکلات را حل میکنند:

| چیزی که میبینم                        | معنای آن                                         | کاری که باید انجام دهم                                                                                       |
| ------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| «اتصال برقرار نمیشود»                 | OmniRoute در حال اجرا نیست                       | `omniroute` یا `docker restart omniroute` را اجرا کنید                                                       |
| «کلید API نامعتبر است»                | کلید شما اشتباه است یا منقضی شده                 | کلید را دوباره از وبسایت ارائهدهنده کپی کنید                                                                 |
| «از محدودیت نرخ درخواست عبور کردهاید» | درخواستهای بیشازحدی ارسال میکنید                 | ۱ دقیقه صبر کنید، یا برای جایگزینی خودکار از `model: "auto"` استفاده کنید                                    |
| «سهمیه تمام شده است»                  | سهمیه رایگان/پولی خود را مصرف کردهاید            | ارائهدهندگان بیشتری متصل کنید، یا از ارائهدهندگان رایگان (Kiro، Pollinations) استفاده کنید                   |
| «پاسخها کند هستند»                    | ارائهدهنده شلوغ یا از شما دور است                | از `model: "auto/fast"` استفاده کنید یا یک ارائهدهنده سریعتر (Groq، Cerebras) متصل کنید                      |
| «ارائهدهنده اشتباهی استفاده شد»       | `auto` ارائهدهنده دیگری را انتخاب کرده است       | طبیعی است! `auto` بهترین گزینه را انتخاب میکند. با `model: "openai/gpt-4o"` یک ارائهدهنده مشخص را اجبار کنید |
| «502 دروازه نامعتبر»                  | ارائهدهنده از دسترس خارج شده است                 | صبر کنید و دوباره تلاش کنید، یا برای تغییر ارائهدهنده از `model: "auto"` استفاده کنید                        |
| «401 غیرمجاز»                         | اطلاعات احراز هویت شما اشتباه است                | کلید API خود را بررسی کنید یا دوباره با OAuth احراز هویت کنید                                                |
| «omniroute شناخته نمیشود»             | ماژولهای سراسری node در Windows PATH وجود ندارند | پیشوند سراسری npm خود را به Windows PATH اضافه کنید. آن را با `npm config get prefix` پیدا کنید.             |
| «429 درخواستهای بیشازحد»              | با محدودیت نرخ درخواست مواجه شدهاید              | ۱ دقیقه صبر کنید، یا ارائهدهندگان بیشتری متصل کنید                                                           |

## عیبیابی تفصیلی

---

### محدودیت نرخ درخواست در ارائهدهندگان رایگان (429 / 400 / 401)

**نشانه**: هنگام استفاده از `model: "auto"` با ارائهدهندگان رایگان/بدون نیاز به احراز هویت (opencode، auggie و غیره)، گاهی بهجای پاسخ، خطای `HTTP 429`، `400` یا `401` دریافت میکنید. اگر چند لحظه بعد همان درخواست را دوباره ارسال کنید موفق میشود، اما فرایندهای خودکار (کارهای cron، عاملها و اسکریپتها) با اولین خطا متوقف میشوند.

**علت اصلی**: سه حالت خرابی مستقل روی هم انباشته میشوند:

1. **محدودیت نرخ ارائهدهنده (`429`)**: سطوح رایگان ممکن است برای هر بازه زمانی سهمیهای اعمال کنند. مجموعهای ناگهانی از فراخوانیهای موازی آن را مصرف میکند، بنابراین درخواست بعدی تا بازنشانی بازه رد میشود.
2. **مدل خراب در حالت عبوری (`400`/`401`)**: مجموعههای `auto/*` ممکن است شامل مدلهای عبوری از `opencode` باشند که در کاتالوگ ثبت شدهاند، اما اطلاعات احراز هویت فعال ندارند (برای مثال `oc/north-mini-code-free` ← `401`). مسیریاب خودکار یکی را امتحان میکند، با شکست مواجه میشود و خطا پیش از فعال شدن جایگزینی منتشر میشود.
3. **تشدید همزمانی (`429` تحت بار)**: وقتی چندین نشست عامل/cron بهصورت همزمان از `auto` استفاده میکنند، نرخ کلی درخواستها از حد تحمل ارائهدهندگان رایگان فراتر میرود و در نتیجه فراخوانیهای معتبر نیز بهعنوان سوءاستفاده علامتگذاری میشوند.

**راهحل تأییدشده (گزارششده توسط جامعه، 2026-08-10)**: سه متغیر محیطی را تنظیم کنید تا چرخش، همزمانی و جایگزینی، ناپایداری سطح رایگان را مدیریت کنند و بهجای آن از کار نیفتند:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # در خطای 400/401 به مدل/ارائهدهنده دیگری برو (مدلهای عبوری خراب را رد میکند)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # سقف صریح پذیرش درخواستهای سنگین (بهطور پیشفرض تنظیم نشده است: محدودیتی برای تعداد درخواستها وجود ندارد؛ یادداشت زیر را ببینید)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # بهجای خطای فوری و قابلتلاشمجدد 503، مدت بیشتری بهصورت محدود برای ظرفیت پردازش سنگین منتظر بمان
```

این موارد را در محیط پردازش OmniRoute تنظیم کنید (یعنی daemon، برای مثال از طریق LaunchAgent plist یا `systemctl edit`) و سپس OmniRoute را راهاندازی مجدد کنید. پرچم چرخش بهتنهایی مؤثرترین اهرم است: این پرچم یک خرابی قطعی را به تلاشی مجدد و شفاف روی یک ارائهدهنده سالم در مجموعه تبدیل میکند.

**توجه**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` تعداد درخواستهای سنگین — با زمینه طولانی — را که همزمان اجرا میشوند محدود میکند؛ این حد یک دروازه پذیرش است، نه محدودکننده نرخ ارائهدهنده. **بهروزرسانی #503-fanout:** این متغیر دیگر بهصورت پیشفرض تنظیم نمیشود (اکنون فقط زمانی اعمال میشود که مانند بالا صراحتاً پیکربندی شده باشد) — در عوض، پذیرش درخواستهای سنگین با بودجه بایتی محاسبهشده بهصورت خودکار (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) کنترل میشود که خود را بر اساس سقف واقعی حافظه میزبان مقیاس میکند؛ بنابراین یک استقرار تازه باید بدون نیاز به تنظیم این متغیر، تعداد بسیار کمتری خطای رد `503 chat_admission_busy` مشاهده کند. تنظیم صریح آن در اینجا همچنان دقیقاً مطابق مستندات عمل میکند. بازنویسیهای صریح بودجه بایتی در محدوده 8 MiB تا 2 GiB محدود میشوند. خطای `413 body_exceeds_budget` موقتی نیست: آن بودجه بایتی را افزایش دهید، `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` را کاهش دهید، یا سقف حافظه پردازش را افزایش دهید. کنارگذاری `inflight_bytes_budget` ناشی از رقابت موقتی است و همچنان میتوان آن را دوباره امتحان کرد. محدودیت نرخ برای هر ارائهدهنده (`open-sse/services/rateLimitManager.ts`) بهطور جداگانه توسط `RATE_LIMIT_MAX_WAIT_MS`، `RATE_LIMIT_MAX_QUEUE_DEPTH` و `RATE_LIMIT_AUTO_ENABLE` کنترل میشود — به `.env.example` مراجعه کنید.

**نحوهٔ اطمینان از کارکرد صحیح**: عامل/کرون خود را دو بار با فاصلهٔ زمانی کوتاه اجرا کنید و تأیید کنید که هر دو اجرا موفق هستند. پیش از اصلاح، اجرای دوم معمولاً خطای `429`/`401` میدهد. پس از اصلاح، خطاها (در صورت وجود) بهطور شفاف دوباره امتحان میشوند و فراخوانی کامل میشود. همچنین میتوانید `curl /monitoring/health` را اجرا کنید و فیلد `rateLimitedUntil` را در اتصالهای ارائهدهنده و `circuitBreakers.providerBreakers[].state` را برای ارائهدهندگان متأثر زیر نظر بگیرید — وضعیت یکی از مقادیر `CLOSED`، `DEGRADED`، `OPEN` یا `HALF_OPEN` است (به `src/shared/utils/circuitBreaker.ts` مراجعه کنید) و ارائهدهندهای که همچنان با خطا مواجه میشود، پیش از آنکه پنجرهٔ بازنشانی اجازهٔ ارسال یک درخواست آزمایشی (`HALF_OPEN`) را بدهد، از وضعیتهای `CLOSED → DEGRADED → OPEN` عبور میکند.

**اگر همچنان خطای 429 مشاهده میکنید**: حساب فعال آن ارائهدهنده واقعاً _سهمیهٔ_ خود را به پایان رسانده است (نه صرفاً محدودیت نرخ درخواست). در داشبورد OmniRoute از مسیر Providers → Accounts یک حساب دوم برای همان ارائهدهنده اضافه کنید، یا یک ارائهدهندهٔ رایگان دیگر (برای مثال `routeway` یا `auggie`) را نیز به ترکیب اضافه کنید. چرخش حسابها فقط برای خطاهای موقت نرخ درخواست/400/401 مؤثر است؛ اتمام کامل سهمیه به یک اعتبارنامهٔ دوم یا ارائهدهندهای متفاوت نیاز دارد.

**اگر در مدلهای بینایی (`auto/vision`، `bazaarlink/*`) خطای 403 مشاهده میکنید**: حساب متصل، طرح پولی شامل قابلیت بینایی ندارد یا کلید API از مجوزهای کافی برخوردار نیست. در داشبورد ارائهدهنده بررسی کنید که دامنهٔ دسترسی کلید شامل قابلیت بینایی/چندوجهی باشد، یا یک حساب با سطح اشتراک پولی متصل کنید و آن را بهعنوان مقصد بینایی نگه دارید.

## هشدارهای npm install ‏(ERESOLVE / peer / deprecated)

هنگامی که `npm install -g omniroute` را اجرا میکنید، ممکن است با انبوهی از هشدارها مانند `npm warn ERESOLVE`، اعلانهای مربوط به وابستگیهای همتا و پیامهای `deprecated` مواجه شوید. **این موارد مورد انتظار و بیضرر هستند.** اگر در خروجی `added <N> packages` را مشاهده کردید، نصب شما با موفقیت انجام شده است.

برای پنهانکردن هشدارهای حل وابستگی همتا، از روش نصب پشتیبانیشده توسط OmniRoute استفاده کنید:

```bash
npm install -g omniroute --legacy-peer-deps
```

گزینهٔ `--legacy-peer-deps` فقط پیامهای `ERESOLVE` و اعلانهای وابستگی همتا را پنهان میکند. اعلانهای منسوخشدن همچنان قابل مشاهده خواهند بود، زیرا از بستههای شخص ثالثِ دارای وابستگی غیرمستقیم میآیند؛ این اعلانها به معنی ناموفقبودن نصب نیستند.

این هشدارها از محدودههای قدیمی وابستگی همتا در بستههای شخص ثالثی میآیند که تحت کنترل OmniRoute نیستند:

1. **`marked-terminal` به `marked >=1 <16` نیاز دارد، اما `marked@18` پیدا شده است** — در عمل بهخوبی کار میکند؛ محدودهٔ همتای پروژهٔ بالادستی صرفاً قدیمی است.
2. **`deprecated prebuild-install@7.1.3`** — یک ابزار کمکی برای دریافت فایلهای باینری بومی است که بهصورت غیرمستقیم وابسته شده است. این ابزار برای
   نصب اتصال انتقالی پینشدهٔ `wreq-js` استفاده نمیشود و نشاندهندهٔ ناموفقبودن
   راهاندازی انتقال ارائهدهندهٔ کوکی وب نیست.

**نیازی به انجام کاری نیست** — بدون فورککردن بستههای بالادستی، امکان پنهانکردن کامل هشدارها وجود ندارد.

## Gemini Web و Playwright Chromium

اگر یک درخواست Gemini Web پاسخ `503` را همراه با پیامی مبنی بر نصبنبودن Playwright Chromium
برگرداند، بستهٔ npm موجود است اما فایل باینری مرورگر وجود ندارد.
Playwright عمداً دانلود مرورگر را از نصب بستهٔ npm
جدا نگه میدارد؛ بنابراین تا زمانی که مرورگر نصب نشده باشد، دریافت این پاسخ مورد انتظار است.

برای نصب سراسری npm، Chromium را از دایرکتوری بستهٔ OmniRoute
نصب کنید تا کش مرورگر متعلق به همان نصب Playwright باشد:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

پس از نصب، OmniRoute را مجدداً راهاندازی کنید و سپس درخواست Gemini Web را دوباره امتحان کنید. اگر
OmniRoute را از یک ایمیج Docker اجرا میکنید، از ایمیج `-web` (یا هدف ساخت `runner-web`)
استفاده کنید که Chromium و وابستگیهای آن را در خود دارد؛ ایمیج پایه
شامل آنها نیست.

## مثبتهای کاذب آنتیویروس

<a name="antivirus-false-positives"></a>

### قرنطینه شدن `README.md` توسط Avast/AVG با تشخیص `MD:HttpRequest-inf[Susp]`

**این یک مثبت کاذب است. هیچ فایلی آلوده نیست و نیازی به هیچ اقدامی وجود ندارد.**

Avast و AVG از یک روش اکتشافی استفاده میکنند که فایلهای متن ساده/Markdown حاوی تعداد زیادی
لینک شبیه به درخواست HTTP را علامتگذاری میکند. فایل `README.md` متعلق به OmniRoute داخل بسته npm ارائه میشود (این فایل
در `package.json` ← `files` فهرست شده است)، بنابراین در نصب سراسری در مسیر `node_modules/omniroute/README.md` قرار میگیرد
— و شامل حدود ۱۵ نمونه `http://localhost:20128/...` است (نقاط پایانی HTTP/SSE مربوط به MCP،
نشانی `.well-known` مربوط به A2A و قطعهکدهای `curl`). همین تراکم لینک برای فعال شدن
این روش اکتشافی کافی است.

اگر این مشکل فقط اخیراً شروع شده است: ماهیت فایل تغییری نکرده است. جدول نقاط پایانی README گسترش یافته
(HTTP و SSE مربوط به MCP و همچنین A2A اضافه شدهاند) و نمونههای `curl` بیشتری نیز افزوده شدهاند؛ در نتیجه
تعداد آنها از آستانه عبور کرده است.

این فایل صرفاً مستنداتی غیرفعال و کاملاً فاقد محتوای اجرایی است. میتوانید با خیال راحت آن را
از قرنطینه بازیابی کنید.

**چه باید کرد:**

1. **اعلانها را متوقف کنید** — دایرکتوری نصب را در آنتیویروس خود مستثنا کنید
   (Avast: تنظیمات ← استثناها) و مسیر سراسری `node_modules` و/یا دایرکتوری دادههای
   OmniRoute (`~/.omniroute/`) را اضافه کنید.
2. **مثبت کاذب را گزارش دهید** — <https://www.avast.com/false-positive-file-form.php>،
   و فایل قرنطینهشده `README.md` را پیوست کنید. این راهحلی است که به همه کمک میکند، زیرا
   روش اکتشافی شرکت سازنده در برابر یک فایل متنی بیشازحد حساسیت نشان داده است.

**چرا این مورد را در سمت خودمان «رفع» نمیکنیم:** همه نمونهها از `http://localhost` استفاده میکنند و
استفاده از `https` برای localhost بدون دردسر گواهیهای خودامضا ممکن نیست. تحریف مستندات برای
دور زدن روش اکتشافی یک شرکت، به همه خوانندگان آسیب میزند تا صرفاً یک باگ اسکنر برآورده شود.

### Kaspersky برنامه دسکتاپ را با عنوان `PDM:Trojan.Win32.Generic` علامتگذاری میکند

**این یک مثبت کاذب ناشی از یک روش اکتشافی رفتاری است. هیچ فایلی آلوده نیست.** پیشوند
`PDM:` در Kaspersky به این معناست که نتیجه تشخیص از ماژول دفاع پیشگیرانه آن (System Watcher) ناشی میشود؛
این ماژول بهجای تطبیق فایل با بدافزارهای شناختهشده، کاری را که نصبکننده _انجام میدهد_ ارزیابی میکند. وقتی
این تشخیص فعال شود، Kaspersky کل فرایند نصب را «برمیگرداند» — یعنی فایلهایی را که قبلاً
نوشته است حذف میکند — و در نتیجه برنامه خراب میشود یا از بین میرود.

فایلهایی که علامتگذاری میشوند، بخشهای استانداردی از وابستگیهای متنباز و اعلامشدهای هستند که همراه
برنامه دسکتاپ بستهبندی شدهاند، برای مثال:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` و
  `workerProcessEntry.js` — [Playwright](https://playwright.dev)، کتابخانه خودکارسازی مرورگر
  که برای ورود به ارائهدهندگان درون برنامه و گفتوگوی متکی به مرورگر استفاده میشود.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — بایندینگ بومی و دارای نسخه ثابت `wreq-js` که برای HTTP با اثرانگشت مرورگر در ارائهدهندگان
  مبتنی بر کوکی وب استفاده میشود (`<arch>` برابر با `x64` یا `arm64` است).

**چرا فعال میشود:** نصبکننده ویندوز **هنوز با امضای کد امضا نشده است**، بنابراین یک نصبکننده NSIS
بدون امضا هیچ اعتباری ندارد و روشهای اکتشافی رفتاری با حداکثر سختگیری اجرا میشوند. ترکیب این موضوع
با یک DLL بومی بستهبندیشده و صدها فایل `.js` که در مسیر
`%LOCALAPPDATA%\Programs\OmniRoute` نوشته میشوند (از جمله دایرکتوریهای بسته دارای پسوند هش از
ساخت مستقل Next.js)، برای فعال شدن این روش اکتشافی کافی است. امضای کد برنامهریزی شده است؛
تا زمانی که انجام شود، این مشکل ممکن است در نسخههای جدید تکرار شود.

**چه باید کرد:**

1. **ابتدا فایل دانلودی خود را تأیید کنید** (تا دستکاری شدن فایل رد شود). هر نسخه فایل
   `latest.yml` را منتشر میکند که فیلد `sha512` آن (با قالب base64) مربوط به نصبکننده
   `OmniRoute.Setup.<version>.exe` است. در PowerShell و از پوشه حاوی نصبکننده:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   خروجی باید با `latest.yml` ← `sha512` مطابقت داشته باشد. اگر مطابقت ندارد، فایل را حذف کرده و
   آن را فقط از [صفحه انتشارهای GitHub](https://github.com/diegosouzapw/OmniRoute/releases) دوباره دانلود کنید.
2. **بازیابی + مستثنا کردن** — موارد برگرداندهشده را از قرنطینه بازیابی کنید و برای
   `%LOCALAPPDATA%\Programs\OmniRoute` یک استثنا اضافه کنید (Kaspersky ← تنظیمات ← تهدیدها و استثناها)،
   سپس دوباره نصب کنید.
3. **مثبت کاذب را گزارش دهید** — <https://opentip.kaspersky.com/>. گزارشهای مثبت کاذب
   ارسالشده توسط کاربران واقعاً فرایند افزودن به فهرست مجاز را تسریع میکنند.

## سازگاری با Node.js

<a name="nodejs-compatibility"></a>

### صفحه ورود از کار میافتد یا خطای «Module self-registration» را نشان میدهد

**علت:** شما نسخهای از Node.js را اجرا میکنید که خارج از حداقل نسخه امن مورد تأیید OmniRoute است. رایجترین حالت، استفاده از سطح وصله قدیمیتر Node 22 یا 24 است که پایینتر از حداقل نسخه امنیتی اصلاحشده موردنیاز OmniRoute قرار دارد.

**نشانهها:**

- صفحه ورود، صفحهای خالی یا خطای سرور را نشان میدهد
- کنسول خطای `Error: Module did not self-register` یا خطاهای مشابه مربوط به اتصال بومی را نشان میدهد
- اگر محیط اجرا خارج از سیاست امن پشتیبانیشده باشد، صفحه ورود یک **بنر هشدار نارنجی** حاوی نسخه Node شما نشان میدهد

**راهحل:**

1. یک نسخه LTS پشتیبانیشده Node.js را نصب کنید (پیشنهاد: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. نسخه خود را بررسی کنید: `node --version` باید در شاخه LTS نسخه 24.x، مقدار `v24.0.0` یا جدیدتر را نشان دهد
3. OmniRoute را دوباره نصب کنید: `npm install -g omniroute`
4. دوباره اجرا کنید: `omniroute`

> **نسخههای امن پشتیبانیشده:** `>=22.22.2 <23` یا `>=24.0.0 <27`. نسخههای Node.js 24.x LTS (Krypton) و Node.js 26 بهطور کامل پشتیبانی میشوند.

### npm v11+: بسته `better-sqlite3` نصب نشده است (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**علت:** npm v11 (ارائهشده همراه با Node.js 24+) بهطور پیشفرض اسکریپتهای نصب وابستگیهای اختیاری را مسدود میکند. از آنجا که `better-sqlite3` در `optionalDependencies` فهرست شده و به کامپایل بومی (`node-gyp rebuild`) نیاز دارد، npm بدون نمایش خطا از نصب آن صرفنظر میکند.

**نشانهها:**

- سرور هنگام راهاندازی با خطای `Cannot find module 'better-sqlite3'` از کار میافتد
- دستور `ls node_modules/better-sqlite3` پیام «No such file or directory» را نشان میدهد
- دستور `npm ls better-sqlite3` مقدار `(empty)` را نشان میدهد

**راهحل:**

1. اسکریپتهای نصب را تأیید و دوباره نصب کنید:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. یا بسته ازپیشساختهشده را بهصورت دستی نصب کنید:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. عملکرد آن را بررسی کنید: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: خطای `dlopen` / «slice is not valid mach-o file»

<a name="macos-native-module-rebuild"></a>

**علت:** پس از اجرای سراسری `npm install -g omniroute`، ممکن است فایل باینری بومی `better-sqlite3` درون بسته برای معماری یا ABI نسخهای از Node.js متفاوت با محیط اجرای محلی کامپایل شده باشد. این مشکل زمانی که فایل باینری ازپیشساختهشده با محیط شما مطابقت ندارد، در macOS (هم Apple Silicon و هم Intel) رایج است.

**نشانهها:**

- سرور بلافاصله هنگام راهاندازی با خطای `dlopen` متوقف میشود
- خطا شامل `slice is not valid mach-o file` است
- نمونه کامل:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**راهحل — بازسازی برای محیط محلی شما (بدون نیاز به تنزل نسخه Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **نکته:** این کار اتصال بومی را متناسب با نسخه محلی Node.js و معماری CPU شما دوباره کامپایل کرده و ناسازگاری فایل باینری را برطرف میکند. محدوده رسمی محیط اجرای پشتیبانیشده **`>=22.22.2 <23` یا `>=24.0.0 <27`** است (`SUPPORTED_NODE_RANGE` در `src/shared/utils/nodeRuntimeSupport.ts` که با فیلد `engines` در `package.json` همراستا است). نسخههای Node.js 24.x LTS (Krypton) و Node.js 26 همراه با `better-sqlite3` v12.x بهطور کامل پشتیبانی میشوند.

## مشکلات پروکسی

<a name="proxy-issues"></a>

### اعتبارسنجی ارائهدهنده خطای "fetch failed" را نشان میدهد

**علت:** نقطه پایانی اعتبارسنجی کلید API (`POST /api/providers/validate`) پیشتر پیکربندی پروکسی را نادیده میگرفت و در محیطهایی که به مسیریابی از طریق پروکسی نیاز دارند باعث بروز خطا میشد.

**رفع مشکل (v3.5.5+):** این مشکل اکنون برطرف شده است. اعتبارسنجی ارائهدهنده از طریق `runWithProxyContext` مسیریابی میشود و تنظیمات پروکسی در سطح ارائهدهنده و سراسری را بهطور خودکار رعایت میکند.

### بررسی سلامت توکن با خطای "fetch failed" مواجه میشود

**علت:** تازهسازی پسزمینهای توکن OAuth، پیکربندی پروکسی را برای هر اتصال بهصورت جداگانه شناسایی نمیکرد.

**رفع مشکل (v3.5.5+):** زمانبند بررسی سلامت توکن اکنون پیش از تلاش برای تازهسازی، پیکربندی پروکسی را برای هر اتصال شناسایی میکند. به v3.5.5+ بهروزرسانی کنید.

### پروکسی SOCKS5 خطای "invalid onRequestStart method" را برمیگرداند

**علت:** در Node.js 22، توزیعکننده undici@8 با پیادهسازی داخلی `fetch()` در Node سازگار نیست.

**رفع مشکل (v3.5.5+):** اکنون هنگامی که یک توزیعکننده پروکسی فعال باشد، OmniRoute از تابع `fetch()` خود undici استفاده میکند تا رفتاری سازگار تضمین شود. به v3.5.5+ بهروزرسانی کنید.

### پروکسی MITM در WSL: برنامههای دسکتاپ روی میزبان Windows رهگیری نمیشوند

**علت:** پروکسی MITM و گواهی CA آن در محیطی نصب میشوند که OmniRoute در آن اجرا میشود. در WSL، این محیط مهمان Linux است، درحالیکه برنامههای دسکتاپ هوش مصنوعی (Kiro، Trae، Copilot، Zed، …) روی میزبان Windows اجرا میشوند. برنامههای میزبان به مخزن گواهی مهمان اعتماد ندارند و ترافیک خود را از طریق پروکسی سیستمی مهمان مسیریابی نمیکنند؛ بنابراین رهگیری دسکتاپ در آنجا فعال نمیشود.

**توصیه:** OmniRoute را بهصورت بومی روی همان سیستمعاملی اجرا کنید که برنامههای دسکتاپ موردنظر برای رهگیری روی آن اجرا میشوند (Windows برای برنامههای Windows؛ و به همین ترتیب macOS/Linux). نگهداشتن OmniRoute درون WSL و در عین حال هدفگرفتن برنامههای میزبان، مستلزم آن است که گواهی CA تولیدشده را بهصورت دستی روی میزبان Windows مورد اعتماد قرار دهید و تنظیمات شبکه/پروکسی هر برنامه میزبان را به نقطه پایانی پروکسی WSL هدایت کنید — این راهاندازی پشتیبانی نمیشود و شکننده است.

برای جزئیات کامل و دستورالعملهای گامبهگام افزودن دو حساب Kiro در کنار یکدیگر،
به [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md) مراجعه کنید.

## مشکلات Docker

### IPv6 در Docker / بازنشانی اتصال

<a name="docker-ipv6"></a>

**نشانهها:** دستور `curl http://localhost:20128/v1/models` خطای `curl: (56) Recv failure: Connection reset by peer` را برمیگرداند. داشبورد و نقاط پایانی بدون احراز هویت کار میکنند، اما نقاط پایانی احراز هویتشده با خطا مواجه میشوند — این وضعیت شبیه مشکل احراز هویت است، اما چنین نیست.

**علت:** دستور `docker run -p 20128:20128` پورت را هم روی `0.0.0.0` ‏(IPv4) و هم روی `::` ‏(IPv6) منتشر میکند، اما فرایند داخل کانتینر فقط روی IPv4 گوش میدهد. در میزبانهایی که `localhost` ابتدا به `::1` نگاشت میشود، اتصال به پورت منتشرشده IPv6 میرسد، درحالیکه هیچ شنوندهای پشت آن وجود ندارد ← اتصال بازنشانی میشود.

**راهحل:**

1. **تشخیص سریع:** دستور `curl -4 http://localhost:20128/v1/models` را اجرا کنید. اگر با `-4` کار میکند، اما بدون آن با خطا مواجه میشود، ناهماهنگی در اتصال IPv6 دارید.
2. **راهحل دائمی:** با استفاده از `-p 127.0.0.1:20128:20128` در دستور `docker run`، اتصال را صراحتاً به IPv4 محدود کنید:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   این کار اتصال IPv4 را اجباری میکند و همچنین از در معرض قرار گرفتن پروکسی روی تمام رابطهای میزبان جلوگیری میکند.

## اشکالزدایی

### فعالسازی فایلهای گزارش

مقدار `APP_LOG_TO_FILE=true` را در فایل `.env` خود تنظیم کنید. گزارشهای برنامه در مسیر `logs/` نوشته میشوند.

### بررسی سلامت ارائهدهنده

```bash
# داشبورد سلامت
http://localhost:20128/dashboard/health

# بررسی سلامت API
curl http://localhost:20128/api/monitoring/health
```

### فضای ذخیرهسازی محیط اجرا

- وضعیت اصلی: `${DATA_DIR}/storage.sqlite` (ارائهدهندگان، ترکیبها، نامهای مستعار، کلیدها، تنظیمات)
- مصرف: جدولهای SQLite در `storage.sqlite` شامل (`usage_history`، `call_logs`، `proxy_logs`) + مسیر اختیاری `${DATA_DIR}/call_logs/`

عملیات **پاکسازی تاریخچه** در صفحه گزارشهای درخواست، `call_logs`، مورد قدیمی
`request_detail_logs` و دایرکتوری محلی مصنوعات `${DATA_DIR}/call_logs/` را پاک میکند.

## مشکلات قطعکننده مدار

### ارائهدهنده در وضعیت OPEN گیر کرده است

وقتی قطعکننده مدار یک ارائهدهنده در وضعیت OPEN باشد، درخواستها تا پایان دوره انتظار مسدود میشوند.

**راهحل:**

1. به **داشبورد → تنظیمات → تابآوری** بروید
2. کارت قطعکننده مدار مربوط به ارائهدهنده تحتتأثیر را بررسی کنید
3. برای پاککردن همه قطعکنندهها، روی **بازنشانی همه** کلیک کنید یا منتظر بمانید تا دوره انتظار به پایان برسد

اگر یک ارائهدهنده مکرراً وارد وضعیت OPEN میشود:

3. بررسی کنید آیا ارائهدهنده محدودیتهای API را تغییر داده یا نیازمند احراز هویت مجدد است
4. دادههای تلهمتری تأخیر را بررسی کنید — تأخیر زیاد ممکن است باعث خطاهای ناشی از پایان مهلت شود

## تنظیمات تابآوری

### محدودسازی خودکار نرخ فعال نمیشود

- محدودسازی خودکار نرخ فقط برای ارائهدهندگان کلید API اعمال میشود (نه OAuth/اشتراک)
- بررسی کنید که محدودسازی خودکار نرخ در **تنظیمات → تابآوری → پروفایلهای ارائهدهنده** فعال باشد
- بررسی کنید آیا ارائهدهنده کدهای وضعیت `429` یا سرآیندهای `Retry-After` را برمیگرداند

### تنظیم عقبنشینی نمایی

پروفایلهای ارائهدهنده از تنظیمات زیر پشتیبانی میکنند:

- **تأخیر پایه** — زمان انتظار اولیه پس از نخستین شکست (پیشفرض: 1s)
- **حداکثر تأخیر** — سقف حداکثر زمان انتظار (پیشفرض: 30s)
- **ضریب** — میزان افزایش تأخیر بهازای هر شکست متوالی (پیشفرض: 2x)

### جلوگیری از ازدحام همزمان

وقتی تعداد زیادی درخواست همزمان به یک ارائهدهنده دارای محدودیت نرخ ارسال میشوند، OmniRoute با استفاده از mutex و محدودسازی خودکار نرخ، درخواستها را بهصورت ترتیبی پردازش میکند تا از شکستهای زنجیرهای جلوگیری شود. این فرایند برای ارائهدهندگان کلید API خودکار است.

### درخواستهای چت با 503 / chat_admission_busy شکست میخورند

**نشانهها:**

- نقطه پایانی تکمیلهای چت، پاسخ قابلتلاشمجدد `503` را با کد خطای
  `chat_admission_busy` برمیگرداند.
- پاسخ شامل `Retry-After` است. از زمان #12135، مقدار آن بر اساس میزان اشغال مشاهدهشده محاسبه
  میشود — بزرگترِ پنجره `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` که درخواست پیشتر در آن منتظر
  مانده است و مدتی که اجارههای سنگین فعلی در اختیار بودهاند — که به بالا و به نزدیکترین
  ثانیه کامل گرد میشود و حداکثر آن 60 است. در یک دروازه بیکار، حداقلهای تاریخی حفظ میشوند:
  2 ثانیه در مسیر مبتنی بر بایت و 1 ثانیه در مسیر مبتنی بر ساختار (که
  `reason: "structure_limit"` را نیز شامل میشود).
- این وضعیت ممکن است زمانی رخ دهد که یک چت سنگین دیگر یا پاسخ جریانی طولانیمدت همچنان
  در حال پردازش باشد.

بدنه پاسخ مبتنی بر بایت بهشکل زیر است:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

پاسخ مبتنی بر ساختار از همان نوع و کد استفاده میکند، با پیام
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
و `reason: "structure_limit"`.
با آستانههای پیشفرض، یک درخواست زمانی از نظر ساختاری سنگین محسوب میشود که حداقل `200` پیام،
حداقل `64` ابزار یا حداقل `32,000` توکن تخمینی داشته باشد، یا هنگامی که تخمین محدودشده ساختار
به کرانهای خود، یعنی `10,000` گره بازدیدشده یا عمق `12`، برسد.

**علت:** این یک کاهش بار عمدی درون OmniRoute است، نه شکست ارائهدهنده بالادستی.
هر فرایند از یک محافظ محلیِ فرایند استفاده میکند تا پیش از نگهداری و تجزیه بدنه یک درخواست بزرگ،
ظرفیت محدود پردازش سنگین را رزرو کند. اجاره سنگین در تمام طول عمر یک پاسخ SSE در اختیار باقی
میماند.

**گسترش #503:** پیش از این اصلاح، محافظ بدون توجه به حافظه میزبان، همزمانی را به یک تعداد ثابت درخواست
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`، پیشفرض `1`) محدود میکرد؛ بنابراین گسترش درخواستهای عامل
کدنویسی (چندین زیرعامل/CLI، با بدنههایی که معمولاً > 256 KB بودند) همزمانی مؤثر را به حدود
1 کاهش میداد و زیر بار کاملاً عادی باعث خطای 503 میشد. اکنون محافظ خودتنظیم است: عملکرد آن
با یک بودجه خودکار بایت ورودی (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) که بر اساس سقف واقعی حافظه
فرایند اندازهگذاری میشود، کنترل میگردد و علاوه بر آن یک سیگنال زنده فشار منابع را بررسی میکند —
بنابراین تنها زمانی بار را کاهش میدهد که میزبان واقعاً تحت فشار حافظه باشد، نه صرفاً به این دلیل
که بیش از یک درخواست سنگین بهطور همزمان رسیده است. سقف قدیمی تعداد درخواستها
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) همچنان رعایت میشود، اما فقط در صورتی که آن را صراحتاً تنظیم کنید.

وقتی ظرفیت مشغول است، یک درخواست سنگین ابتدا تا مدت
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (پیشفرض `2000`، مقدار `0` انتظار را غیرفعال میکند) منتظر آزاد شدن
یک جایگاه میماند و سپس پاسخ قابلتلاشمجدد `503` را برمیگرداند. این انتظار محدود وجود دارد تا
کلاینتهای مبتنی بر عامل (OpenCode، Claude Code، Cursor) که زیردرخواستهای سنگین را بهطور همزمان
گسترش میدهند، موج درخواستها را بهصورت ترتیبی پردازش کنند، بهجای آنکه کل بودجه تلاش مجدد خود را
صرف رد شدنهای فوری کنند و در میانه کار از کار بیفتند.
میزان اشغال فعلی اجارههای سنگین، بودجه بایت نهاییشده و شدت فشار زنده در
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`، `maxInflightBytes`،
`budgetSource`، `pressureSeverity`، `countCapEnabled`) نمایش داده میشوند — پیش از تغییر هر متغیر
محیطی، این موارد را بررسی کنید.
تنظیمات → تابآوری → صف درخواست → درخواستهای همزمان این مورد را کنترل نمیکند؛ آن تنظیم
سازوکار جداگانه صف درخواست ارائهدهنده را مدیریت میکند.

**راهحل:**

1. ابتدا دوباره تلاش کنید. کلاینتها باید `Retry-After` را رعایت کنند و بهجای تکرار فوری
   درخواست، از عقبنشینی استفاده کنند.
2. پیش از هرگونه تنظیم، `/api/monitoring/health` → `chatAdmission` را بررسی کنید. `countCapEnabled:
false` و یک `maxInflightBytes` سخاوتمندانه به این معناست که بودجه محاسبهشده خودکار از قبل
   وظیفه خود را انجام میدهد؛ مقدار `high`/`critical` برای `pressureSeverity` یعنی حافظه میزبان
   واقعاً کم است — این مشکل با یک متغیر محیطی پذیرش قابلحل نیست و به RAM بیشتر یا حجم کاری
   کوچکتری نیاز دارد.
3. فقط اگر `/api/monitoring/health` نشان میدهد بودجه محاسبهشده خودکار واقعاً برای میزبان شما
   بیش از حد کوچک است (که نادر است — این بودجه از کانتینر تا سختافزار فیزیکی مقیاس میشود)،
   آن را مستقیماً با `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` بازنویسی کنید، نه اینکه به سقف قدیمی
   تعداد درخواستها بازگردید.

برای مشاهده تنظیمات معتبر پذیرش، به [مرجع متغیرهای محیطی](../reference/ENVIRONMENT.md#4-security--authentication)
مراجعه کنید.

## طبقهبندی اختیاری خطاهای RAG / LLM ‏(۱۶ مشکل)

برخی از کاربران OmniRoute درگاه را در جلوی پشتههای RAG یا عاملها قرار میدهند. در چنین پیکربندیهایی مشاهده یک الگوی عجیب رایج است: OmniRoute سالم به نظر میرسد (ارائهدهندگان فعالاند، پروفایلهای مسیریابی مشکلی ندارند و هیچ هشدار محدودیت نرخی وجود ندارد)، اما پاسخ نهایی همچنان نادرست است.

در عمل، این رخدادها معمولاً از خط لوله پاییندستی RAG ناشی میشوند، نه از خود درگاه.

اگر برای توصیف این خطاها به واژگان مشترکی نیاز دارید، میتوانید از WFGY ProblemMap استفاده کنید؛ یک منبع متنی خارجی با مجوز MIT که شانزده الگوی تکرارشونده خطا در RAG / LLM را تعریف میکند. در سطح کلی، این موارد را پوشش میدهد:

- انحراف بازیابی و شکستهشدن مرزهای زمینه
- ایندکسها و مخازن برداری خالی یا قدیمی
- عدم تطابق تعبیهسازی با معنا
- مشکلات مونتاژ پرامپت و پنجره زمینه
- فروپاشی منطقی و پاسخهای بیشازحد مطمئن
- شکستهای زنجیرههای طولانی و هماهنگی عاملها
- انحراف حافظه و نقش در سیستمهای چندعاملی
- مشکلات ترتیب استقرار و راهاندازی اولیه

ایده ساده است:

1. هنگام بررسی یک پاسخ نامناسب، موارد زیر را ثبت کنید:
   - وظیفه و درخواست کاربر
   - مسیر یا ترکیب ارائهدهندگان در OmniRoute
   - هر زمینه RAG که در پاییندست استفاده شده است (اسناد بازیابیشده، فراخوانی ابزارها و غیره)
2. رخداد را به یک یا دو شماره از WFGY ProblemMap نگاشت کنید (`No.1` … `No.16`).
3. شماره را در داشبورد، راهنمای عملیاتی یا سامانه پیگیری رخداد خود، در کنار لاگهای OmniRoute ذخیره کنید.
4. از صفحه متناظر WFGY استفاده کنید تا مشخص شود آیا لازم است پشته RAG، بازیابیکننده یا راهبرد مسیریابی خود را تغییر دهید.

متن کامل و دستورالعملهای عملی در اینجا قرار دارند (مجوز MIT، فقط متن):

[README مربوط به WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

اگر در پشت OmniRoute خط لولههای RAG یا عامل اجرا نمیکنید، میتوانید این بخش را نادیده بگیرید.

**علائم:**

**بازنشانی دستی:**

- **داشبورد:** **Settings → Model Cooldowns** → روی کارت تحت تأثیر، روی **Re-enable** کلیک کنید
- **API:** ارسال `DELETE /api/resilience/model-cooldowns` همراه با هدرهای احراز هویت مدیریتی

### اتصال ارائهدهنده Command Code با خطای 403 مواجه میشود

**علائم:**

- دریافت 403 هنگام آزمایش اتصال ارائهدهنده Command Code
- کارت ارائهدهنده پس از افزودن مجدد، «غیرمجاز» را نمایش میدهد

**علت:** جریان OAuth کامل نشده است (فراخوانی بازگشتی دریافت نشده یا توکن ذخیره نشده است).

**راهحل:**

- برای فعالکردن مجدد جریان OAuth، دستور `omniroute providers` را از CLI اجرا کنید، یا
- OAuth را از **Dashboard → Providers → Command Code → Reconnect** دوباره اجرا کنید

### ModelScope دورههای انتظار تهاجمی 429 برمیگرداند

**علائم:**

- دورههای انتظار بسیار کوتاه یا فوری در ModelScope پس از حجم کمی از درخواستها

**علت:** ModelScope هدرهای مختص ارائهدهنده `Retry-After` را ارسال میکند. v3.8.0 با مدیریت اختصاصی این هدرها عرضه شده است؛ بنابراین نسخههای قدیمیتر آنها را بهاشتباه بهعنوان نشانههای عمومی محدودیت نرخ تفسیر میکنند.

**راهحل:**

- مطمئن شوید که از v3.8.0 یا نسخهای جدیدتر استفاده میکنید
- بررسی کنید که گزینه `useUpstream429BreakerHints` در **Settings → Resilience** فعال باشد

**علائم:**

- دریافت 401 برای تمام درخواستهای پل WebSocket مربوط به Codex/Responses هنگام اجرا روی یک میزبان عملیاتی راهدور
- دستدهی پل WebSocket بلافاصله پس از اتصال بسته میشود

**علت:** متغیر محیطی `OMNIROUTE_WS_BRIDGE_SECRET` در محیط عملیاتی وجود ندارد.

**راهحل:**

1. یک رمز تصادفی تولید کنید: `openssl rand -hex 32`
2. مقدار `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` را در محیط سرور عملیاتی (و هر کلاینتی که با پل ارتباط برقرار میکند) تنظیم کنید
3. OmniRoute را مجدداً راهاندازی کنید

### Responses API: تنزل حالت پسزمینه به اجرای همگام

**علائم:**

- هشدار ثبتشده: `background mode degraded to synchronous`
- یک درخواست با `background: true` بهجای شناسه یک کار پسزمینه، پاسخی همگام و عادی برمیگرداند

**علت:** در v3.8.0، مقدار `background: true` در Responses API عمداً به اجرای همگام تنزل مییابد و همزمان یک هشدار صادر میشود. اجرای کاملاً ناهمگام در پسزمینه قابلیتی است که در آینده ارائه خواهد شد.

**راهحل:**

- کلاینت را طوری تنظیم کنید که فراخوانی را بدون `background` انجام دهد، یا
- منتظر نسخهای بعدی بمانید که حالت پسزمینه کاملاً ناهمگام را ارائه میکند (تغییرات نسخه را پیگیری کنید)

## راهاندازی کند / پایان مهلت آمادگی

اگر CLI پیام `⚠ Server did not respond within 60s` را نمایش میدهد، اما سرور
در واقع کار میکند، بودجهٔ بررسی آمادگی برای محیط شما بیش از حد کوتاه است.

این اتفاق معمولاً در Windows (بهدلیل آنتیویروس یا پایشگرهای سیستم فایل) یا کانتینرهایی
با بارهای کاری سنگین هنگام راهاندازی رخ میدهد.

**راهحل — بودجه را افزایش دهید:**

```bash
# از طریق متغیر محیطی (در راهاندازیهای بعدی نیز باقی میماند):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # ۳ دقیقه
omniroute serve

# از طریق فلگ CLI (فقط برای یک بار):
omniroute serve --ready-timeout 180000
```

مقدار پیشفرض 60 000 میلیثانیه (60 ثانیه) است. این هشدار صرفاً اطلاعرسانی است؛ سرور
در پسزمینه به راهاندازی ادامه میدهد و پس از تکمیل فرایند راهاندازی در دسترس خواهد بود.

برای جزئیات کامل دربارهٔ `OMNIROUTE_READY_TIMEOUT_MS` به
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) مراجعه کنید.
