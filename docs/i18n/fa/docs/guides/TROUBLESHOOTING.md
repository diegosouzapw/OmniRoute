## مرجع سریع

**تازه با OmniRoute آشنا شدهاید؟** از اینجا شروع کنید — این موارد ۹۰٪ مشکلات را حل میکنند:

| چیزی که میبینم                        | معنای آن                                         | کاری که باید انجام دهم                                                                                            |
| ------------------------------------- | ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| "اتصال برقرار نمیشود"                 | OmniRoute در حال اجرا نیست                       | `omniroute` یا `docker restart omniroute` را اجرا کنید                                                            |
| "کلید API نامعتبر است"                | کلید شما اشتباه است یا منقضی شده                 | کلید را دوباره از وبسایت ارائهدهنده کپی کنید                                                                      |
| "از محدودیت نرخ درخواست عبور کردهاید" | درخواستهای بیشازحدی ارسال میکنید                 | ۱ دقیقه صبر کنید، یا برای بازگشت خودکار از `model: "auto"` استفاده کنید                                           |
| "سهمیه تمام شده است"                  | سهمیه رایگان یا پولی خود را مصرف کردهاید         | ارائهدهندگان بیشتری متصل کنید، یا از ارائهدهندگان رایگان (Kiro، Pollinations) استفاده کنید                        |
| "پاسخهای کند"                         | ارائهدهنده مشغول است یا فاصله زیادی دارد         | از `model: "auto/fast"` استفاده کنید یا یک ارائهدهنده سریعتر (Groq، Cerebras) متصل کنید                           |
| "ارائهدهنده اشتباه استفاده شده است"   | `auto` ارائهدهنده دیگری را انتخاب کرده است       | این طبیعی است! `auto` بهترین گزینه را انتخاب میکند. با `model: "openai/gpt-4o"` یک ارائهدهنده مشخص را اجباری کنید |
| "502 Bad Gateway"                     | ارائهدهنده از دسترس خارج است                     | صبر کنید و دوباره تلاش کنید، یا برای جابهجایی بین ارائهدهندگان از `model: "auto"` استفاده کنید                    |
| "401 Unauthorized"                    | اطلاعات احراز هویت شما اشتباه است                | کلید API خود را بررسی کنید یا با OAuth دوباره احراز هویت کنید                                                     |
| "omniroute شناسایی نمیشود"            | ماژولهای سراسری node در Windows PATH وجود ندارند | پیشوند سراسری npm خود را به Windows PATH اضافه کنید. آن را با `npm config get prefix` پیدا کنید.                  |
| "429 Too Many Requests"               | محدودیت نرخ درخواست اعمال شده است                | ۱ دقیقه صبر کنید، یا ارائهدهندگان بیشتری متصل کنید                                                                |

## عیبیابی تفصیلی

---

### محدودیت نرخ درخواست در ارائهدهندگان رایگان (429 / 400 / 401)

**نشانه**: هنگام استفاده از `model: "auto"` با ارائهدهندگان رایگان/بدون احراز هویت (opencode، auggie و غیره)، گاهی بهجای پاسخ، خطای `HTTP 429`، `400` یا `401` دریافت میکنید. اگر چند لحظه بعد همان درخواست را دوباره امتحان کنید موفق میشود، اما فرایندهای خودکار (کارهای cron، عاملها و اسکریپتها) با اولین شکست متوقف میشوند.

**علت اصلی**: سه حالت خرابی مستقل روی هم اثر میگذارند:

1. **محدودیت نرخ ارائهدهنده (`429`)**: سطوح رایگان ممکن است برای هر بازه زمانی سهمیهای اعمال کنند. موجی از فراخوانیهای موازی آن را تمام میکند و در نتیجه درخواست بعدی تا زمان بازنشانی بازه رد میشود.
2. **مدل خراب در passthrough (`400`/`401`)**: مخزنهای `auto/*` ممکن است شامل مدلهای passthrough از `opencode` باشند که در کاتالوگ ثبت شدهاند اما اطلاعات احراز هویت فعال ندارند (برای مثال `oc/north-mini-code-free` → `401`). مسیریاب خودکار یکی را امتحان میکند، شکست میخورد و پیش از فعال شدن بازگشت، خطا منتشر میشود.
3. **تشدید همزمانی (`429` زیر بار)**: هنگامی که چند نشست عامل/cron بهطور همزمان به `auto` درخواست میفرستند، نرخ تجمیعی درخواست از حد تحمل ارائهدهندگان رایگان فراتر میرود؛ بنابراین فراخوانیهای معتبر نیز بهعنوان سوءاستفاده علامتگذاری میشوند.

**راهحل تأییدشده (گزارششده توسط جامعه، 2026-08-10)**: سه متغیر محیطی را طوری تنظیم کنید که چرخش، همزمانی و بازگشت، نوسانات سطح رایگان را مدیریت کنند و بهجای آن از کار نیفتند:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # در خطاهای 400/401 به مدل/ارائهدهنده دیگری بروید (مدلهای خراب passthrough را نادیده میگیرد)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # سقف صریح پذیرش درخواستهای سنگین (بهطور پیشفرض تنظیم نشده است: محدودیتی برای تعداد درخواست وجود ندارد؛ یادداشت زیر را ببینید)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # زمان انتظار محدود را برای upstreamهای کند از مقدار پیشفرض RATE_LIMIT_MAX_WAIT_MS بیشتر کنید
```

این موارد را در محیط فرایند OmniRoute تنظیم کنید (daemon، برای مثال از طریق plist مربوط به LaunchAgent یا `systemctl edit`)، سپس OmniRoute را راهاندازی مجدد کنید. پرچم چرخش مؤثرترین اهرم است: این پرچم یک شکست قطعی را به تلاشی مجدد و شفاف با یک ارائهدهنده سالم در مخزن تبدیل میکند.

**نکته**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` تعداد درخواستهای سنگین — با زمینه طولانی — را که میتوانند همزمان اجرا شوند محدود میکند؛ این حد، یک دروازه پذیرش است، نه محدودکننده نرخ ارائهدهنده. **بهروزرسانی #503-fanout:** این متغیر دیگر بهطور پیشفرض تنظیم نمیشود (اکنون فقط زمانی اعمال میشود که مانند بالا صریحاً پیکربندی شده باشد) — در عوض، پذیرش درخواستهای سنگین با یک بودجه بایتی که بهطور خودکار محاسبه میشود (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) کنترل میگردد؛ این بودجه خود را بر اساس سقف واقعی حافظه میزبان مقیاس میکند. بنابراین یک استقرار جدید، بدون نیاز به تنظیم این متغیر، باید تعداد بسیار کمتری رد شدن با خطای `503 chat_admission_busy` داشته باشد؛ بااینحال، تنظیم صریح آن در اینجا همچنان دقیقاً مطابق مستندات کار میکند. بازنویسیهای صریح بودجه بایتی به بازه 8 MiB تا 2 GiB محدود میشوند. خطای `413 body_exceeds_budget` موقتی نیست: آن بودجه بایتی را افزایش دهید، `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` را کاهش دهید یا سقف حافظه فرایند را افزایش دهید. کنارگذاری `inflight_bytes_budget` ناشی از رقابت موقتی است و همچنان میتوان دوباره تلاش کرد. محدودیت نرخ بهازای هر ارائهدهنده (`open-sse/services/rateLimitManager.ts`) بهطور جداگانه توسط `RATE_LIMIT_MAX_WAIT_MS`، `RATE_LIMIT_MAX_QUEUE_DEPTH` و `RATE_LIMIT_AUTO_ENABLE` کنترل میشود — به `.env.example` مراجعه کنید.

**نحوهٔ اطمینان از عملکرد صحیح**: عامل/cron خود را دو بار با فاصلهٔ زمانی کوتاه اجرا کنید و مطمئن شوید هر دو اجرا موفق هستند. پیش از اصلاح، اجرای دوم معمولاً خطای `429`/`401` ایجاد میکند. پس از اصلاح، خطاها (در صورت وجود) بهطور شفاف مجدداً امتحان میشوند و فراخوانی تکمیل میشود. همچنین میتوانید `curl /monitoring/health` را اجرا کنید و فیلد `rateLimitedUntil` را در اتصالهای ارائهدهندگان و مقدار `circuitBreakers.providerBreakers[].state` را برای ارائهدهندگان تحتتأثیر مشاهده کنید — وضعیت یکی از مقادیر `CLOSED`، `DEGRADED`، `OPEN` یا `HALF_OPEN` است (به `src/shared/utils/circuitBreaker.ts` مراجعه کنید) و ارائهدهندهای که پیوسته با خطا مواجه میشود، پیش از آنکه پنجرهٔ بازنشانی اجازهٔ عبور یک درخواست آزمایشی (`HALF_OPEN`) را بدهد، از حالت `CLOSED → DEGRADED → OPEN` عبور میکند.

**اگر همچنان خطای 429 مشاهده میکنید**: حساب فعال آن ارائهدهنده واقعاً _سهمیهٔ_ خود را تمام کرده است (نه صرفاً محدودیت نرخ را). در داشبورد OmniRoute از مسیر Providers → Accounts، حساب دومی برای همان ارائهدهنده اضافه کنید یا یک ارائهدهندهٔ رایگان دیگر (مانند `routeway` یا `auggie`) را نیز به ترکیب اضافه کنید. چرخش فقط برای خطاهای موقتی نرخ/400/401 مفید است؛ اتمام قطعی سهمیه به اعتبارنامهٔ دوم یا ارائهدهندهای متفاوت نیاز دارد.

**اگر در مدلهای بینایی (`auto/vision`، `bazaarlink/*`) خطای 403 مشاهده میکنید**: حساب متصل فاقد طرح پولی شامل قابلیت بینایی است یا کلید API مجوزهای کافی ندارد. در داشبورد ارائهدهنده بررسی کنید که دامنهٔ دسترسی کلید شامل بینایی/چندوجهی باشد، یا یک حساب با سطح پولی متصل کرده و آن را بهعنوان مقصد بینایی نگه دارید.

## هشدارهای npm install ‏(ERESOLVE / peer / deprecated)

هنگامی که `npm install -g omniroute` را اجرا میکنید، ممکن است با انبوهی از هشدارها مانند `npm warn ERESOLVE`، اعلانهای وابستگی همتا و پیامهای `deprecated` مواجه شوید. **این موارد قابل انتظار و بیضرر هستند.** اگر در خروجی عبارت `added <N> packages` را مشاهده کنید، نصب شما با موفقیت انجام شده است.

برای پنهانکردن هشدارهای مربوط به رفع وابستگیهای همتا، از روش نصب پشتیبانیشده OmniRoute استفاده کنید:

```bash
npm install -g omniroute --legacy-peer-deps
```

گزینه `--legacy-peer-deps` فقط پیامهای `ERESOLVE` و اعلانهای وابستگی همتا را پنهان میکند. اعلانهای منسوخشدن همچنان نمایش داده میشوند، زیرا از بستههای شخص ثالثِ وابسته ناشی میشوند؛ این اعلانها به معنی ناموفقبودن نصب نیستند.

این هشدارها از محدودههای قدیمی وابستگی همتا در بستههای شخص ثالثی ناشی میشوند که تحت کنترل OmniRoute نیستند:

1. **`marked-terminal` به `marked >=1 <16` نیاز دارد، اما `marked@18` پیدا شده است** — در عمل بهدرستی کار میکند؛ محدوده همتای پروژه بالادستی صرفاً قدیمی است.
2. **`deprecated prebuild-install@7.1.3`** — یک ابزار کمکی وابسته برای دریافت باینریهای بومی است. از آن برای
   نصب اتصال انتقال تثبیتشده `wreq-js` استفاده نمیشود و نشان نمیدهد که راهاندازی انتقال ارائهدهنده
   web-cookie ناموفق بوده است.

**هیچ اقدامی لازم نیست** — بدون ایجاد انشعاب از بستههای بالادستی، نمیتوان این هشدارها را بهطور کامل پنهان کرد.

## هشدار مسدودشدن install-scripts در npm (نصب سراسری)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

هنگام اجرای `npm install -g omniroute`، نسخههای جدیدتر npm ‏(v11+ و v12+) اسکریپتهای چرخه عمر بسته را بهطور پیشفرض مسدود میکنند و هشدار install-scripts را نمایش میدهند:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### آیا میتوان این هشدار را نادیده گرفت؟

**تا حدی، اما اجرا بدون اسکریپتها توصیه نمیشود.** OmniRoute دارای سازوکارهای جایگزین مناسبی است: اگر اتصالهای بومی `better-sqlite3` از بسته مستقل بارگیری نشوند، برنامه از درایورهای جایگزینی مانند `node:sqlite` یا `sql.js` استفاده میکند (به [تفکیک زمان اجرای SQLite](../ops/SQLITE_RUNTIME.md) مراجعه کنید). سرور همچنان اجرا خواهد شد، اما استفاده از گزینههای جایگزین WASM مانند `sql.js`، حالت WAL ‏(Write-Ahead Logging) در SQLite را غیرفعال میکند و سربار حافظه و همگامسازی دیسک را افزایش میدهد.

### کدام اسکریپتها واقعاً ضروری هستند؟

همه اسکریپتهای مسدودشده برای اجرای OmniRoute ضروری نیستند:

- **ضروری (`omniroute`، `better-sqlite3`):** OmniRoute از یک بسته مستقل برنامه Next.js ‏(`dist/`) اجرا میشود. هنگام نصب، npm درایور بومی SQLite مختص میزبان را در سطح بالای `node_modules/better-sqlite3/` دانلود یا کامپایل میکند. سپس اسکریپت `postinstall` متعلق به OmniRoute ‏(`scripts/build/postinstall.mjs`) این باینریهای مختص میزبان را بررسی کرده و در `dist/node_modules/` کپی میکند تا سرور مستقل بتواند به آنها دسترسی داشته باشد. اگر اسکریپت postinstall متعلق به `omniroute` مسدود شود، این مرحله کپی انجام نخواهد شد.
- **اختیاری/وابسته (`keytar`، `@parcel/watcher`، `@swc/core`، `protobufjs`، `esbuild`):** این موارد ابزارهای کمکی ساخت، ابزارهای پایش یا ابزارهای مربوط به جاکلیدی سیستم هستند. اجازهدادن به اجرای آنها از نمایش هشدارهای ساخت جلوگیری میکند، اما برای قابلیت اصلی مسیریابی ضروری نیستند.
- **مستثناشده (`onnxruntime-node`):** یک وابستگی اختیاری برای embeddingهای محلی هوش مصنوعی است و برای اجرای OmniRoute **ضروری نیست**. اسکریپت postinstall آن حدود 300MB از داراییهای CUDA را از NuGet دانلود میکند؛ مگر اینکه صراحتاً قصد استفاده از شتابدهی محلی ONNX روی سختافزار پشتیبانیشده را داشته باشید، آن را در فهرست مجاز قرار ندهید.

### راهحل پیشنهادی

برای اجازهدادن به اجرای اسکریپتهای نصب ضروری در یک نصب سراسری و پنهانکردن هشدارها، گزینه `--allow-scripts` را برای OmniRoute و وابستگیهای بومی آن مشخص کنید:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

همچنین میتوانید این تنظیم را برای تمام نصبهای سراسری حساب کاربری خود بهطور دائمی پیکربندی کنید:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### نصب خود را بررسی کنید

پس از نصب، ابزار تشخیصی داخلی را اجرا کنید تا از سالمبودن اتصالهای بومی و محیط زمان اجرا اطمینان حاصل شود:

```bash
omniroute doctor
```

## Gemini Web و Playwright Chromium

اگر یک درخواست Gemini Web خطای `503` را همراه با پیامی مبنی بر نصب نبودن Playwright Chromium
برگرداند، بسته npm موجود است اما فایل اجرایی مرورگر وجود ندارد.
Playwright عمداً دانلود مرورگر را از نصب بسته npm جدا نگه میدارد،
بنابراین تا زمانی که مرورگر نصب نشده باشد، دریافت این پاسخ مورد انتظار است.

برای نصب سراسری npm، Chromium را از دایرکتوری بسته OmniRoute نصب کنید
تا کش مرورگر متعلق به همان نصب Playwright باشد:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

پس از نصب، OmniRoute را مجدداً راهاندازی کنید و سپس درخواست Gemini Web را دوباره امتحان کنید. اگر
OmniRoute را از یک ایمیج Docker اجرا میکنید، از ایمیج `-web` (یا تارگت ساخت `runner-web`)
استفاده کنید که Chromium و وابستگیهای آن را بههمراه دارد؛ ایمیج پایه
این موارد را شامل نمیشود.

## مثبتهای کاذب آنتیویروس

<a name="antivirus-false-positives"></a>

### قرنطینهکردن `README.md` توسط Avast/AVG با تشخیص `MD:HttpRequest-inf[Susp]`

**این یک مثبت کاذب است. هیچ فایلی آلوده نیست و نیازی به هیچ اقدامی وجود ندارد.**

Avast و AVG از یک روش اکتشافی استفاده میکنند که فایلهای متنی ساده/Markdown حاوی تعداد زیادی لینک شبیه به درخواست HTTP را علامتگذاری میکند. فایل `README.md` مربوط به OmniRoute درون بسته npm قرار دارد (در `package.json` ← `files` فهرست شده است)، بنابراین هنگام نصب سراسری در مسیر `node_modules/omniroute/README.md` قرار میگیرد — و شامل حدود ۱۵ نمونه `http://localhost:20128/...` است (نقاط پایانی HTTP/SSE مربوط به MCP، نشانی `.well-known` مربوط به A2A و قطعهکدهای `curl`). همین تراکم لینک برای فعالشدن این روش اکتشافی کافی است.

اگر این مشکل بهتازگی آغاز شده است: نوع فایل تغییری نکرده است. جدول نقاط پایانی README گسترش یافته (MCP HTTP + SSE + A2A اضافه شدهاند) و نمونههای `curl` بیشتری نیز افزوده شدهاند؛ در نتیجه، تعداد موارد از آستانه تشخیص عبور کرده است.

این فایل صرفاً مستنداتی غیرفعال و فاقد هرگونه محتوای اجرایی است. میتوانید با خیال راحت آن را از قرنطینه بازیابی کنید.

**چه کاری باید انجام دهید:**

1. **اعلانها را متوقف کنید** — دایرکتوری نصب را در آنتیویروس خود مستثنا کنید
   (Avast: Settings ← Exceptions) و مسیر سراسری `node_modules` و/یا دایرکتوری دادههای
   OmniRoute (`~/.omniroute/`) را اضافه کنید.
2. **مثبت کاذب را گزارش دهید** — <https://www.avast.com/false-positive-file-form.php>،
   و فایل قرنطینهشده `README.md` را پیوست کنید. این راهحلی است که به همه کمک میکند، زیرا مشکل از حساسیت بیش از حد روش اکتشافی شرکت سازنده نسبت به یک فایل متنی ناشی میشود.

**چرا این مورد را از سمت خودمان «اصلاح» نمیکنیم:** همه نمونهها از `http://localhost` استفاده میکنند و localhost بدون دردسر گواهی خودامضا نمیتواند از `https` استفاده کند. دستکاری مستندات برای دورزدن روش اکتشافی یک شرکت سازنده، به همه خوانندگان آسیب میزند تا صرفاً یک باگ اسکنر برطرف شود.

### علامتگذاری برنامه دسکتاپ توسط Kaspersky بهعنوان `PDM:Trojan.Win32.Generic`

**این یک مثبت کاذب ناشی از روش اکتشافی رفتاری است. هیچ فایلی آلوده نیست.** پیشوند `PDM:` در Kaspersky به این معناست که تشخیص توسط Proactive Defense Module (System Watcher) انجام شده است؛ این ماژول بهجای تطبیق فایل با بدافزارهای شناختهشده، عملکرد نصبکننده را ارزیابی میکند. با فعالشدن این تشخیص، Kaspersky کل فرایند نصب را «برمیگرداند» — و فایلهایی را که پیشتر نوشته بود حذف میکند — در نتیجه برنامه خراب میشود یا بهکلی از بین میرود.

فایلهایی که علامتگذاری میشوند، اجزای استاندارد وابستگیهای متنباز و اعلامشدهای هستند که همراه برنامه دسکتاپ بستهبندی شدهاند؛ برای مثال:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` و
  `workerProcessEntry.js` — مربوط به [Playwright](https://playwright.dev)، کتابخانه خودکارسازی مرورگر که برای ورود به ارائهدهندگان درون برنامه و گفتوگوی مبتنی بر مرورگر استفاده میشود.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — اتصال بومی سنجاقشده `wreq-js` که برای HTTP با اثرانگشت مرورگر در ارائهدهندگان مبتنی بر کوکی وب استفاده میشود (`<arch>` برابر با `x64` یا `arm64` است).

**چرا این تشخیص فعال میشود:** نصبکننده Windows **هنوز با کد امضا نشده است**، بنابراین نصبکننده NSIS بدون امضا هیچ اعتباری ندارد و روشهای اکتشافی رفتاری با حداکثر حساسیت اجرا میشوند. وجود یک DLL بومی بستهبندیشده و صدها فایل `.js` که در
`%LOCALAPPDATA%\Programs\OmniRoute` نوشته میشوند (از جمله دایرکتوریهای بسته دارای پسوند هش از ساخت مستقل Next.js)، در مجموع برای فعالشدن این روش اکتشافی کافی است. امضای کد برنامهریزی شده است؛ تا پیش از انجام آن، ممکن است این مشکل در انتشارهای جدید تکرار شود.

**چه کاری باید انجام دهید:**

1. **ابتدا فایل دانلودشده را تأیید کنید** (تا دستکاریشدن فایل منتفی شود). هر انتشار شامل
   `latest.yml` است که فیلد `sha512` آن (با قالب base64)، نصبکننده
   `OmniRoute.Setup.<version>.exe` را پوشش میدهد. در PowerShell، از پوشه حاوی نصبکننده:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   خروجی باید با `latest.yml` ← `sha512` مطابقت داشته باشد. اگر مطابقت ندارد، فایل را حذف کنید و آن را فقط از [صفحه انتشارهای GitHub](https://github.com/diegosouzapw/OmniRoute/releases) دوباره دانلود کنید.
2. **بازیابی + مستثناکردن** — موارد برگرداندهشده را از قرنطینه بازیابی کنید و برای
   `%LOCALAPPDATA%\Programs\OmniRoute` یک استثنا اضافه کنید (Kaspersky ← Settings ← Threats and Exclusions)،
   سپس دوباره نصب کنید.
3. **مثبت کاذب را گزارش دهید** — <https://opentip.kaspersky.com/>. گزارشهای مثبت کاذب ارسالشده توسط کاربران واقعاً فرایند قرارگرفتن در فهرست مجاز را تسریع میکنند.

## سازگاری با Node.js

<a name="nodejs-compatibility"></a>

### صفحه ورود از کار میافتد یا خطای "Module self-registration" را نشان میدهد

**علت:** شما نسخهای از Node.js را اجرا میکنید که خارج از حداقل نسخه امن مورد تأیید OmniRoute است. رایجترین حالت، اجرای نسخهای قدیمیتر از بهروزرسانیهای Node 22 یا 24 است که پایینتر از حداقل نسخه امنیتی اصلاحشده موردنیاز OmniRoute قرار دارد.

**نشانهها:**

- صفحه ورود، صفحهای خالی یا خطای سرور را نشان میدهد
- کنسول خطای `Error: Module did not self-register` یا خطاهای مشابه مربوط به اتصالهای بومی را نشان میدهد
- اگر محیط اجرا خارج از سیاست امنیتی پشتیبانیشده باشد، صفحه ورود یک **نوار هشدار نارنجی** حاوی نسخه Node شما نشان میدهد

**راهحل:**

1. یکی از نسخههای LTS پشتیبانیشده Node.js را نصب کنید (پیشنهاد: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. نسخه را بررسی کنید: `node --version` باید در شاخه LTS نسخه 24.x، مقدار `v24.0.0` یا جدیدتر را نشان دهد
3. OmniRoute را دوباره نصب کنید: `npm install -g omniroute`
4. آن را مجدداً راهاندازی کنید: `omniroute`

> **نسخههای امن پشتیبانیشده:** `>=22.22.2 <23` یا `>=24.0.0 <27`. نسخه Node.js 24.x LTS (Krypton) و Node.js 26 کاملاً پشتیبانی میشوند.

### npm v11+: ‏`better-sqlite3` نصب نشده است (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**علت:** npm v11 (ارائهشده همراه با Node.js 24+) بهطور پیشفرض اسکریپتهای نصب وابستگیهای اختیاری را مسدود میکند. از آنجا که `better-sqlite3` در `optionalDependencies` فهرست شده است و به کامپایل بومی (`node-gyp rebuild`) نیاز دارد، npm بدون نمایش خطا از آن صرفنظر میکند.

**نشانهها:**

- سرور هنگام راهاندازی با خطای `Cannot find module 'better-sqlite3'` از کار میافتد
- دستور `ls node_modules/better-sqlite3` پیام "No such file or directory" را نشان میدهد
- دستور `npm ls better-sqlite3` مقدار `(empty)` را نشان میدهد

**راهحل:**

1. اسکریپتهای نصب را تأیید کرده و دوباره نصب کنید:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. یا بسته ازپیشساختهشده را بهصورت دستی نصب کنید:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. از درست کار کردن آن مطمئن شوید: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: ‏`dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**علت:** پس از اجرای سراسری `npm install -g omniroute`، ممکن است فایل باینری بومی `better-sqlite3` درون بسته برای معماری یا ABI متفاوتی از Node.js نسبت به محیط در حال اجرای محلی کامپایل شده باشد. این مشکل در macOS (هم Apple Silicon و هم Intel) زمانی رایج است که فایل باینری ازپیشساختهشده با محیط شما مطابقت ندارد.

**نشانهها:**

- سرور بلافاصله هنگام راهاندازی با خطای `dlopen` از کار میافتد
- خطا شامل `slice is not valid mach-o file` است
- نمونه کامل:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**راهحل — برای محیط محلی خود دوباره بیلد کنید (نیازی به دانگرید Node.js نیست):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **نکته:** این کار اتصال بومی را متناسب با نسخه محلی Node.js و معماری CPU شما دوباره کامپایل میکند و ناسازگاری فایل باینری را برطرف میسازد. محدوده محیط اجرای رسمی پشتیبانیشده **`>=22.22.2 <23` یا `>=24.0.0 <27`** است (`SUPPORTED_NODE_RANGE` در `src/shared/utils/nodeRuntimeSupport.ts`، همراستا با فیلد `engines` در `package.json`). نسخه Node.js 24.x LTS (Krypton) و Node.js 26 همراه با `better-sqlite3` v12.x کاملاً پشتیبانی میشوند.

## مشکلات پروکسی

<a name="proxy-issues"></a>

### اعتبارسنجی ارائهدهنده خطای "fetch failed" را نشان میدهد

**علت:** نقطه پایانی اعتبارسنجی کلید API (`POST /api/providers/validate`) پیشتر پیکربندی پروکسی را نادیده میگرفت و در محیطهایی که به مسیریابی از طریق پروکسی نیاز دارند، باعث بروز خطا میشد.

**رفع مشکل (v3.5.5+):** این مشکل اکنون برطرف شده است. مسیرهای اعتبارسنجی ارائهدهنده از `runWithProxyContext` عبور میکنند و بهطور خودکار تنظیمات پروکسی در سطح ارائهدهنده و تنظیمات پروکسی سراسری را رعایت میکنند.

### بررسی سلامت توکن با خطای "fetch failed" مواجه میشود

**علت:** نوسازی پسزمینهای توکن OAuth، پیکربندی پروکسی را برای هر اتصال بهصورت جداگانه تعیین نمیکرد.

**رفع مشکل (v3.5.5+):** زمانبند بررسی سلامت توکن اکنون پیش از تلاش برای نوسازی، پیکربندی پروکسی را برای هر اتصال تعیین میکند. به v3.5.5+ بهروزرسانی کنید.

### پروکسی SOCKS5 خطای "invalid onRequestStart method" را برمیگرداند

**علت:** در Node.js 22، توزیعکننده undici@8 با پیادهسازی داخلی `fetch()` در Node سازگار نیست.

**رفع مشکل (v3.5.5+):** اکنون هنگامی که یک توزیعکننده پروکسی فعال باشد، OmniRoute از تابع `fetch()` خود undici استفاده میکند تا رفتار سازگار و یکسانی تضمین شود. به v3.5.5+ بهروزرسانی کنید.

### پروکسی MITM در WSL: برنامههای دسکتاپ روی میزبان Windows رهگیری نمیشوند

**علت:** پروکسی MITM و گواهی CA آن در محیطی نصب میشوند که OmniRoute در آن اجرا میشود. در WSL، این محیط همان مهمان Linux است، درحالیکه برنامههای دسکتاپ هوش مصنوعی (Kiro، Trae، Copilot، Zed، …) روی میزبان Windows اجرا میشوند. برنامههای میزبان به مخزن گواهی مهمان اعتماد ندارند و ترافیک آنها از پروکسی سیستم مهمان عبور نمیکند؛ بنابراین رهگیری برنامههای دسکتاپ در آنجا فعال نمیشود.

**توصیه:** OmniRoute را بهصورت بومی روی همان سیستمعاملی اجرا کنید که برنامههای دسکتاپ موردنظر برای رهگیری روی آن اجرا میشوند (Windows برای برنامههای Windows؛ و به همین ترتیب macOS/Linux). نگهداشتن OmniRoute درون WSL و همزمان هدفگرفتن برنامههای میزبان، مستلزم آن است که گواهی CA تولیدشده را بهصورت دستی در میزبان Windows مورد اعتماد قرار دهید و تنظیمات شبکه/پروکسی هر برنامه میزبان را به نقطه پایانی پروکسی WSL هدایت کنید — این پیکربندی پشتیبانی نمیشود و شکننده است.

## مشکلات Cloud

### خطاهای همگامسازی Cloud

1. بررسی کنید که `BASE_URL` به نمونه در حال اجرای شما اشاره کند (برای مثال، `http://localhost:20128`)

**نشانه:** خطای `Unexpected token 'd'...` در نقطه پایانی Cloud برای فراخوانیهای غیرجریانی.

### Cloud اتصال را تأیید میکند، اما پیام "کلید API نامعتبر است" نمایش داده میشود

1. یک کلید جدید از داشبورد محلی (`/api/keys`) ایجاد کنید
2. همگامسازی Cloud را اجرا کنید: فعالسازی Cloud ← همگامسازی اکنون
3. کلیدهای قدیمی یا همگامنشده همچنان ممکن است در Cloud خطای `401` برگردانند

## مشکلات Docker

### IPv6 در Docker / بازنشانی اتصال

<a name="docker-ipv6"></a>

**نشانهها:** دستور `curl http://localhost:20128/v1/models` خطای `curl: (56) Recv failure: Connection reset by peer` را برمیگرداند. داشبورد و نقاط پایانی بدون احراز هویت کار میکنند، اما نقاط پایانی نیازمند احراز هویت با خطا مواجه میشوند — این وضعیت شبیه یک مشکل احراز هویت به نظر میرسد، اما چنین نیست.

**علت:** دستور `docker run -p 20128:20128` پورت را هم روی `0.0.0.0` (IPv4) و هم روی `::` (IPv6) منتشر میکند، اما فرایند داخل کانتینر فقط روی IPv4 گوش میدهد. در میزبانهایی که `localhost` ابتدا به `::1` تفکیک میشود، اتصال به پورت منتشرشده IPv6 هدایت میشود، اما هیچ شنوندهای پشت آن وجود ندارد ← اتصال بازنشانی میشود.

**راهحل:**

1. **عیبیابی سریع:** دستور `curl -4 http://localhost:20128/v1/models` را اجرا کنید. اگر با `-4` کار میکند اما بدون آن با خطا مواجه میشود، عدم تطابق اتصال IPv6 دارید.
2. **راهحل دائمی:** با استفاده از `-p 127.0.0.1:20128:20128` در دستور `docker run`، اتصال را صراحتاً به IPv4 محدود کنید:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   این کار اتصال IPv4 را اجباری میکند و همچنین از در معرض قرار گرفتن پراکسی روی تمام رابطهای میزبان جلوگیری میکند.

## مشکلات Circuit Breaker

### ارائهدهنده در وضعیت OPEN گیر کرده است

وقتی Circuit Breaker یک ارائهدهنده در وضعیت OPEN باشد، درخواستها تا پایان زمان cooldown مسدود میشوند.

**راهحل:**

1. به **Dashboard → Settings → Resilience** بروید
2. کارت Circuit Breaker مربوط به ارائهدهنده تحتتأثیر را بررسی کنید
3. برای پاککردن همه Breakerها روی **Reset All** کلیک کنید، یا منتظر بمانید تا زمان cooldown به پایان برسد
4. پیش از بازنشانی، مطمئن شوید که ارائهدهنده واقعاً در دسترس است

### ارائهدهنده مرتباً Circuit Breaker را فعال میکند

اگر یک ارائهدهنده مکرراً وارد وضعیت OPEN میشود:

1. برای بررسی الگوی خطا، به **Dashboard → Health → Provider Health** بروید
2. به **Settings → Resilience → Provider Profiles** بروید و آستانه خطا را افزایش دهید
3. بررسی کنید که آیا ارائهدهنده محدودیتهای API را تغییر داده یا به احراز هویت مجدد نیاز دارد
4. دادههای تلهمتری تأخیر را بررسی کنید — تأخیر زیاد ممکن است باعث خطاهای ناشی از پایان مهلت شود

## تنظیمات تابآوری

### فعال نشدن محدودسازی خودکار نرخ درخواست

- محدودسازی خودکار نرخ درخواست فقط برای ارائهدهندگان مبتنی بر کلید API اعمال میشود (نه OAuth/اشتراک)
- بررسی کنید که محدودسازی خودکار نرخ درخواست در **تنظیمات → تابآوری → پروفایلهای ارائهدهنده** فعال باشد
- بررسی کنید که آیا ارائهدهنده کدهای وضعیت `429` یا هدرهای `Retry-After` را برمیگرداند

### تنظیم عقبنشینی نمایی

پروفایلهای ارائهدهنده از تنظیمات زیر پشتیبانی میکنند:

- **تأخیر پایه** — زمان انتظار اولیه پس از نخستین خطا (پیشفرض: 1s)
- **حداکثر تأخیر** — سقف حداکثر زمان انتظار (پیشفرض: 30s)
- **ضریب** — میزان افزایش تأخیر بهازای هر خطای متوالی (پیشفرض: 2x)

### جلوگیری از هجوم همزمان درخواستها

هنگامی که تعداد زیادی درخواست همزمان به یک ارائهدهنده دارای محدودیت نرخ میرسند، OmniRoute با استفاده از mutex و محدودسازی خودکار نرخ، درخواستها را بهصورت ترتیبی اجرا میکند و از بروز خطاهای زنجیرهای جلوگیری میکند. این فرایند برای ارائهدهندگان مبتنی بر کلید API بهصورت خودکار انجام میشود.

### درخواستهای چت با 503 / chat_admission_busy ناموفق میشوند

**نشانهها:**

- نقطه پایانی تکمیلهای چت یک پاسخ قابلتلاشمجدد `503` برمیگرداند که کد خطای آن
  `chat_admission_busy` است.
- پاسخ شامل `Retry-After` است. از #12135 به بعد، مقدار آن بر اساس اشغال مشاهدهشده محاسبه
  میشود — بزرگترِ بازه `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` که درخواست پیشتر منتظر مانده
  و مدتزمانی که اجارههای سنگین فعلی نگه داشته شدهاند — که به ثانیه کامل رو به بالا گرد
  شده و حداکثر به 60 محدود میشود. در یک دروازه بیکار، حداقلهای تاریخی حفظ میشوند: 2 ثانیه
  در مسیر مبتنی بر بایت و 1 ثانیه در مسیر مبتنی بر ساختار (که
  `reason: "structure_limit"` را نیز شامل میشود).
- این وضعیت ممکن است زمانی رخ دهد که یک چت سنگین دیگر یا پاسخ استریم طولانیمدت هنوز
  در حال اجرا باشد.

بدنه پاسخ مبتنی بر بایت به این صورت است:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

پاسخ مبتنی بر ساختار از همان نوع و کد استفاده میکند و پیام آن
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
و `reason: "structure_limit"` است.
با آستانههای پیشفرض، یک درخواست زمانی از نظر ساختاری سنگین محسوب میشود که دستکم `200` پیام،
دستکم `64` ابزار یا دستکم `32,000` توکن تخمینی داشته باشد، یا هنگامی که برآورد محدودشده ساختار
از کرانهای `10,000` گره بازدیدشده یا عمق `12` فراتر رود.

**علت:** این یک کاهش عمدی بار درون OmniRoute است، نه خطای ارائهدهنده بالادستی.
هر فرایند پیش از نگهداری و تجزیه بدنه یک درخواست بزرگ، از یک محافظ محلی همان فرایند برای رزرو
ظرفیت محدود درخواستهای سنگین استفاده میکند. اجاره سنگین در تمام طول عمر یک پاسخ SSE
نگه داشته میشود.

**#503-fanout:** پیش از این اصلاح، محافظ، همزمانی را بدون توجه به حافظه میزبان بر اساس یک تعداد ثابت درخواست
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`، با مقدار پیشفرض `1`) محدود میکرد؛ در نتیجه، گسترش همزمان
عاملهای کدنویسی (چندین زیرعامل/CLI، با بدنههایی که معمولاً > 256 KB بودند) عملاً همزمانی را
به حدود 1 کاهش میداد و تحت بار کاملاً عادی به خطای 503 منجر میشد. اکنون محافظ خودتنظیم است:
فعالسازی آن به یک بودجه خودکار بایت برای دریافت داده (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) وابسته
است که بر اساس سقف واقعی حافظه فرایند تعیین میشود؛ همچنین یک سیگنال زنده فشار منابع را بررسی
میکند — بنابراین فقط هنگامی بار را کاهش میدهد که میزبان واقعاً تحت فشار حافظه باشد، نه صرفاً
به این دلیل که بیش از یک درخواست سنگین همزمان رسیده است. سقف شمارش قدیمی
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) همچنان رعایت میشود، اما فقط در صورتی که آن را صریحاً تنظیم کنید.

هنگامی که ظرفیت اشغال است، یک درخواست سنگین ابتدا حداکثر تا
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (مقدار پیشفرض `RATE_LIMIT_MAX_WAIT_MS` است؛ `0` انتظار را غیرفعال میکند) منتظر آزاد شدن یک جایگاه میماند
و سپس پاسخ قابلتلاشمجدد `503` را برمیگرداند. این انتظار محدود وجود دارد تا کلاینتهای عاملمحور
(OpenCode، Claude Code، Cursor) که زیردرخواستهای سنگین را بهطور همزمان گسترش میدهند، جهش بار را
بهصورت ترتیبی پردازش کنند، بهجای اینکه تمام بودجه تلاش مجدد خود را صرف رد شدنهای فوری کنند و
در میانه کار از کار بیفتند.
میزان فعلی اشغال اجارههای سنگین، بودجه بایت نهاییشده و شدت زنده فشار منابع در
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`، `maxInflightBytes`،
`budgetSource`، `pressureSeverity`، `countCapEnabled`) نمایش داده میشوند — پیش از تغییر هر متغیر محیطی
این موارد را بررسی کنید.
تنظیمات → تابآوری → صف درخواست → درخواستهای همزمان این رفتار را کنترل نمیکند؛ آن تنظیم
سازوکار جداگانه صف درخواست ارائهدهنده را مدیریت میکند.

**راهحل:**

1. ابتدا دوباره تلاش کنید. کلاینتها باید `Retry-After` را رعایت کنند و بهجای تکرار فوری
   درخواست، از عقبنشینی استفاده کنند.
2. پیش از تنظیم هر چیزی، `/api/monitoring/health` → `chatAdmission` را بررسی کنید. `countCapEnabled:
false` و یک `maxInflightBytes` سخاوتمندانه به این معناست که بودجه خودکار از قبل بهدرستی کار
   میکند؛ مقدار `high`/`critical` برای `pressureSeverity` به این معناست که میزبان واقعاً با کمبود حافظه
   مواجه است — این مشکل با یک متغیر محیطی پذیرش قابلحل نیست و به RAM بیشتر یا بار کاری کوچکتری نیاز دارد.
3. تنها اگر `/api/monitoring/health` نشان دهد که بودجه خودکار واقعاً برای میزبان شما بسیار کوچک است
   (که نادر است — زیرا از کانتینر تا سختافزار فیزیکی مقیاسبندی میشود)، آن را مستقیماً با
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` بازنویسی کنید، نه اینکه به سقف قدیمی تعداد درخواست بازگردید.

برای مشاهده تنظیمات معتبر پذیرش، به [مرجع متغیرهای محیطی](../reference/ENVIRONMENT.md#4-security--authentication)
مراجعه کنید.

## طبقهبندی اختیاری خطاهای RAG / LLM ‏(۱۶ مشکل)

برخی از کاربران OmniRoute درگاه را در مقابل پشتههای RAG یا عاملها قرار میدهند. در چنین پیکربندیهایی، مشاهده یک الگوی عجیب رایج است: OmniRoute سالم به نظر میرسد (ارائهدهندگان فعال هستند، پروفایلهای مسیریابی مشکلی ندارند و هیچ هشدار محدودیت نرخی وجود ندارد)، اما پاسخ نهایی همچنان اشتباه است.

در عمل، این رخدادها معمولاً از خط لوله پاییندستی RAG ناشی میشوند، نه از خود درگاه.

اگر برای توصیف این خطاها به واژگان مشترکی نیاز دارید، میتوانید از WFGY ProblemMap استفاده کنید؛ یک منبع متنی خارجی با مجوز MIT که شانزده الگوی تکرارشونده خطا در RAG / LLM را تعریف میکند. در سطح کلی، این موارد را پوشش میدهد:

- انحراف در بازیابی و شکست مرزهای زمینه
- ایندکسها و مخازن برداری خالی یا قدیمی
- عدم تطابق embedding با معنا
- مشکلات مونتاژ پرامپت و پنجره زمینه
- فروپاشی منطق و پاسخهای بیشازحد مطمئن
- خطاهای زنجیرههای طولانی و هماهنگی عاملها
- انحراف حافظه و نقش در سیستمهای چندعاملی
- مشکلات ترتیب استقرار و راهاندازی اولیه

ایده ساده است:

1. هنگام بررسی یک پاسخ نامناسب، موارد زیر را ثبت کنید:
   - وظیفه و درخواست کاربر
   - مسیر یا ترکیب ارائهدهندگان در OmniRoute
   - هرگونه زمینه RAG استفادهشده در پاییندست (اسناد بازیابیشده، فراخوانی ابزارها و غیره)
2. رخداد را به یک یا دو شماره از WFGY ProblemMap نگاشت کنید (`No.1` … `No.16`).
3. شماره را در داشبورد، راهنمای عملیاتی یا سامانه پیگیری رخداد خود، در کنار گزارشهای OmniRoute ذخیره کنید.
4. از صفحه متناظر WFGY برای تصمیمگیری درباره نیاز به تغییر پشته RAG، بازیاب یا راهبرد مسیریابی خود استفاده کنید.

متن کامل و دستورالعملهای عملی در اینجا قرار دارند (مجوز MIT، فقط متن):

[README مربوط به WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

اگر در پشت OmniRoute خط لوله RAG یا عامل اجرا نمیکنید، میتوانید این بخش را نادیده بگیرید.

## مشکلات شناختهشده v3.8.0

مشکلات مختص نسخه v3.8.0 و راهحلهای موقت فعلی آنها. اگر اصلاحی در یک وصله بعدی ارائه شود، این مدخل بهروزرسانی یا حذف خواهد شد.

### خطاهای احراز هویت Devin CLI

**نشانهها:**

- نمایش «Devin CLI پیدا نشد» یا «احراز هویت ناموفق بود» هنگام فراخوانی ابزارهای مبتنی بر Devin
- بررسی زمان اجرای CLI مقدار `installed=false` را گزارش میدهد

**علتها:**

- `CLI_DEVIN_BIN` به مسیری اشاره میکند که وجود ندارد
- Devin CLI روی میزبان نصب نشده است

**راهحل:**

1. Devin CLI را برای پلتفرم خود نصب کنید
2. مقدار `CLI_DEVIN_BIN=/usr/local/bin/devin` (یا مسیر واقعی) را در `.env` تنظیم کنید
3. OmniRoute را راهاندازی مجدد کرده و از مسیر **داشبورد → ابزارهای CLI** دوباره آزمایش کنید

### گیر کردن دوره انتظار مدل (بازنشانی دستی)

**نشانهها:**

- حتی پس از سپری شدن زمان انقضا، یک مدل همچنان در فهرست دوره انتظار باقی میماند
- با وجود اینکه زمان ثبتشده در گذشته است، درخواستها همچنان در مسیریابی ترکیبی از مدل صرفنظر میکنند

**بازنشانی دستی:**

- **داشبورد:** **تنظیمات → دورههای انتظار مدل** → روی کارت مربوطه، **فعالسازی مجدد** را کلیک کنید
- **API:** درخواست `DELETE /api/resilience/model-cooldowns` را همراه با سرآیندهای احراز هویت مدیریتی ارسال کنید

### اتصال ارائهدهنده Command Code با خطای 403 مواجه میشود

**نشانهها:**

- دریافت خطای 403 هنگام آزمایش اتصال ارائهدهنده Command Code
- کارت ارائهدهنده پس از افزودن مجدد، وضعیت «غیرمجاز» را نشان میدهد

**علت:** فرایند OAuth تکمیل نشده است (callback دریافت نشده یا token ذخیره نشده است).

**راهحل:**

- برای فعالسازی مجدد فرایند OAuth، دستور `omniroute providers` را از CLI اجرا کنید، یا
- OAuth را از مسیر **داشبورد → ارائهدهندگان → Command Code → اتصال مجدد** دوباره اجرا کنید

### ModelScope دورههای انتظار شدید 429 برمیگرداند

**نشانهها:**

- ایجاد دورههای انتظار بسیار کوتاه یا فوری در ModelScope پس از تعداد کمی درخواست متوالی
- مسیریابی ترکیبی زودتر از حد انتظار از ModelScope صرفنظر میکند

**علت:** ModelScope سرآیندهای `Retry-After` مختص ارائهدهنده ارسال میکند. v3.8.0 شامل مدیریت اختصاصی این سرآیندها است؛ بنابراین نسخههای قدیمیتر آنها را بهاشتباه بهعنوان نشانههای عمومی محدودیت نرخ تفسیر میکنند.

**راهحل:**

- مطمئن شوید از v3.8.0 یا نسخهای جدیدتر استفاده میکنید
- بررسی کنید که گزینه `useUpstream429BreakerHints` در بخش **تنظیمات → تابآوری** فعال باشد

### نبودن OMNIROUTE_WS_BRIDGE_SECRET در محیط عملیاتی

**نشانهها:**

- دریافت خطای 401 برای تمام درخواستهای پل WebSocket مربوط به Codex/Responses هنگام اجرا روی یک میزبان عملیاتی راهدور
- دستدهی پل WebSocket بلافاصله پس از اتصال بسته میشود

**علت:** متغیر محیطی `OMNIROUTE_WS_BRIDGE_SECRET` در محیط عملیاتی وجود ندارد.

**راهحل:**

1. یک راز تصادفی ایجاد کنید: `openssl rand -hex 32`
2. مقدار `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` را در محیط سرور عملیاتی (و هر کلاینتی که با پل ارتباط برقرار میکند) تنظیم کنید
3. OmniRoute را راهاندازی مجدد کنید

### Responses API: تنزل حالت پسزمینه به اجرای همگام

**نشانهها:**

- هشدار زیر ثبت میشود: `background mode degraded to synchronous`
- یک درخواست `background: true` بهجای شناسه کار پسزمینه، یک پاسخ همگام عادی برمیگرداند

**علت:** در v3.8.0، مقدار `background: true` در Responses API عمداً به اجرای همگام تنزل داده میشود و همزمان یک هشدار صادر میگردد. اجرای کاملاً ناهمگام در پسزمینه در آینده ارائه خواهد شد.

**راهحل:**

- کلاینت را طوری تنظیم کنید که بدون `background` فراخوانی انجام دهد، یا
- منتظر نسخه بعدی بمانید که حالت پسزمینه کاملاً ناهمگام را ارائه میکند (تغییرات نسخه را دنبال کنید)

## راهاندازی کُند / پایان مهلت آمادگی

اگر CLI پیام `⚠ Server did not respond within 60s` را نمایش میدهد، اما سرور در واقع کار میکند، بودجهٔ زمانی بررسی آمادگی برای محیط شما بسیار کوتاه است.

این اتفاق معمولاً در Windows (بهدلیل آنتیویروس یا پایشگرهای سیستم فایل) یا در کانتینرهایی با بار کاری سنگین هنگام راهاندازی رخ میدهد.

**راهحل — افزایش بودجهٔ زمانی:**

```bash
# از طریق متغیر محیطی (در راهاندازیهای بعدی نیز باقی میماند):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # ۳ دقیقه
omniroute serve

# از طریق پرچم CLI (فقط برای یکبار):
omniroute serve --ready-timeout 180000
```

مقدار پیشفرض 60 000 میلیثانیه (60 ثانیه) است. این هشدار صرفاً اطلاعرسانی است؛ سرور در پسزمینه به راهاندازی ادامه میدهد و پس از تکمیل فرایند بوت، در دسترس خواهد بود.

برای جزئیات کامل دربارهٔ `OMNIROUTE_READY_TIMEOUT_MS`، به [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) مراجعه کنید.
