دو روش برای قرار دادن Cursor پشت OmniRoute بدون نشست IDE وجود دارد:

1. **ارائهدهندهٔ `cursor-api`** (کارت «Cursor API»، نام مستعار `cua`): یک
   ارائهدهندهٔ مبتنی بر کلید API که کلید API کاربر Cursor را نگه میدارد
   (`crsr_…`، تولیدشده در `https://cursor.com/dashboard/api`). سپس هر کلاینت
   OmniRoute میتواند از طریق `/v1/chat/completions` و با نام
   `cursor-api/<model>` یا `cua/<model>` به مدلهای Cursor دسترسی پیدا کند و
   لایههای معمول سهمیه، جایگزینی و ثبت گزارش نیز اعمال میشوند. ارائهدهندهٔ
   IDE (`cursor`، نشست OAuth/IDE) بدون تغییر باقی میماند.
2. **عبور مستقیم Cursor CLI**: Cursor CLI (`agent`) را به OmniRoute متصل کنید
   تا هر RPC که CLI ارسال میکند با یک کلید API متعلق به OmniRoute احراز هویت
   شود، با اعتبارنامهٔ یک اتصال `cursor-api` به Cursor فرستاده شود و در صفحهٔ
   گزارشها ثبت گردد.

## چرا کلید مبادله میشود

`api2.cursor.sh` یک کلید خام `crsr_…` را بهعنوان توکن Bearer رد میکند (401).
Cursor CLI ابتدا کلید را با POST به `/auth/exchange_user_api_key` ارسال میکند
و یک JWT نشست دریافت میکند که پس از یک ساعت منقضی میشود؛ `refreshToken`
برگرداندهشده نیز همان `exp` را دارد، بنابراین تازهسازی به معنای مبادلهٔ
مجدد کلید است.
`open-sse/services/cursorApiKeyAuth.ts` این مبادله را انجام میدهد، برای هر
کلید یک توکن نشست را در کش نگه میدارد، پنج دقیقه پیش از انقضا دوباره کلید را
مبادله میکند و هنگامی که Cursor پاسخ 401 میدهد، توکن کششده را حذف میکند.
`CursorExecutor` درست پیش از باز کردن جریان بالادستی برای اتصالهای
`cursor-api` آن را فراخوانی میکند.

## ارائهدهندهٔ `cursor-api`

رجیستری: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`، `authType: "apikey"`، با `format`، `baseUrl` و
`models` یکسان با `cursor`). کارت کاتالوگ:
`src/shared/constants/providers/apikey/specialty-media.ts`. نگاشت اجراکننده:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`).

داشبورد: ارائهدهندگان → Cursor API → افزودن کلید API.

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

سپس:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

نکات:

- فهرست مدلهای `cursor-api` از رجیستری ایستای Cursor دریافت میشود (همان
  فهرستی که ارائهدهندهٔ IDE در حالت جایگزین از آن استفاده میکند)؛ نیازی به
  نصب `cursor-agent` روی میزبان OmniRoute نیست.
- `POST /api/providers/{id}/refresh-cursor` فقط برای ارائهدهندهٔ IDE با نام
  `cursor` است؛ اتصالهای `cursor-api` هیچ نشست IDEای برای تمدید ندارند.

## شناسههای بومی مدل و سطح تلاش

برای `cursor` / `cu` و `cursor-api` / `cua`، نرمالساز مشترک سطح تلاش Claude
شناسهٔ مدل درخواستی را دستنخورده باقی میگذارد. Cursor میتواند پسوندی مانند
`-low` را بهعنوان بخشی از شناسهٔ واقعی مدل اعلام کند، نه بهعنوان نام مستعار
سطح تلاش در OmniRoute. اجراکنندهٔ Cursor تطابق دقیق با کاتالوگ زنده را حفظ
میکند؛ وقتی تطابقی وجود نداشته باشد، تحلیلگر مدل فعلی آن مدیریت تبدیل پسوند
به پارامتر را بر عهده میگیرد.

این موضوع نرمالسازی سطح تلاش را برای مسیرهای مستقیم Claude، مسیرهای سازگار
با Claude یا مسیرهای Vertex تغییر نمیدهد. دسترسپذیری همچنان به کاتالوگ و
مجوزهای حساب Cursor انتخابشده بستگی دارد.

## گذردهی Cursor CLI

مسیر: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`. پیشوند `/api/cursor-cli/` در
`src/shared/constants/publicApiRoutes.ts` ثبت شده است، زیرا کنترلکننده
احراز هویت اختصاصی خود را اعمال میکند:

| مسیر                                                                                                                     | احراز هویت مورد انتظار از CLI | کاری که OmniRoute انجام میدهد                                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------ | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                       | `Bearer <OmniRoute API key>`  | کلید را اعتبارسنجی میکند، یک JWT از نوع HS256 با اعتبار ۱ ساعت (امضاشده با `JWT_SECRET`) صادر میکند و آن را برمیگرداند                                                            |
| هر مسیر دیگر (`/aiserver.v1.*`، `/agent.v1.AgentService/RunSSE`، `/aiserver.v1.BidiService/BidiAppend`، `/v1/traces`، …) | `Bearer <that JWT>`           | صادرکننده/مخاطب/انقضا را تأیید میکند، یک اتصال فعال `cursor-api` را انتخاب میکند، هدر Authorization را با توکن مبادلهشده Cursor جایگزین میکند و پاسخ را بهصورت جریانی بازمیگرداند |

CLI مقدار `exp` را از هر توکنی که دریافت کند رمزگشایی میکند؛ بنابراین، ارائه
یک توکن مات باعث میشود تقریباً پیش از هر درخواست دوباره تبادل انجام دهد؛ JWT
صادرشده از این مسئله جلوگیری میکند. پاسخ 401 از OmniRoute باعث میشود CLI
دوباره تبادل را انجام دهد.

### راهاندازی

1. یک کلید API برای OmniRoute (Dashboard → API keys) و یک اتصال `cursor-api`
   ایجاد کنید.
2. به CLI بگویید برای جریان عامل از HTTP/1.1 استفاده کند. در
   `~/.cursor/cli-config.json`:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   بدون این تنظیم، CLI نوبت عامل را از طریق HTTP/2 به یک میزبان عامل که
   جداگانه پیکربندی شده است باز میکند و فقط RPCهای صفحه کنترل از endpoint
   عبور میکنند.

3. CLI را در برابر OmniRoute اجرا کنید:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

هر گام در Logs با ارائهدهنده `cursor-api`، نوع درخواست `cursor-cli` و مسیر
`/api/cursor-cli/<rpc>` ثبت میشود و به کلید API مربوط به OmniRoute و اتصالی
که آن را پردازش کرده است نسبت داده میشود.

### حالتهای خرابی

| وضعیت                                            | پاسخ به CLI                                    |
| ------------------------------------------------ | ---------------------------------------------- |
| کلید ناشناخته OmniRoute و `REQUIRE_API_KEY=true` | 401 `unauthenticated` هنگام تبادل              |
| `REQUIRE_API_KEY=false`                          | نشست ناشناس (همانند رفتار `/v1/*`)             |
| JWT نشست منقضیشده / خارجی / دستکاریشده           | 401، CLI دوباره تبادل را انجام میدهد           |
| لغو کلید API مربوط به OmniRoute پس از تبادل      | 401 در RPC بعدی                                |
| نبود اتصال فعال `cursor-api`                     | 503 `unavailable`                              |
| رد شدن کلید اتصال توسط Cursor                    | 401 `unauthenticated`، نشست ذخیرهشده حذف میشود |
| در دسترس نبودن بالادست                           | 502 `unavailable` (پیام پاکسازیشده)            |
| تنظیم نبودن `JWT_SECRET`                         | 503 هنگام تبادل                                |
