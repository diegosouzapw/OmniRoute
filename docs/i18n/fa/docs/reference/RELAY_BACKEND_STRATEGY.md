## خلاصه

OmniRoute اکنون از سه حالت رله برای `/api/v1/relay/chat/completions` پشتیبانی میکند:

- `ts`: استفاده از رله TypeScript درون همان پردازش.
- `bifrost`: اجبار به استفاده از دروازه Bifrost.
- `auto`: ترجیح Bifrost در صورت دسترسپذیری و بازگشت به TypeScript هنگام بروز خطا.

هنگامی که با نرخ درخواست بالایی کار میکنید (تعداد زیاد توکن در روز و توان عملیاتی تقریباً ثابت)، بهترین راهبرد این است که مسیر بازگشت را صریح و سریع نگه دارید تا مسیر پرترافیک هیچگاه منتظر یک sidecar ازکارافتاده نماند.

## رفتار حالتها

- `ts`
  - کمترین پیچیدگی عملیاتی.
  - تمام مسیریابی و اعتبارسنجی در Node اجرا میشود.
  - برای دسترسپذیری به sidecar وابسته نیست.
- `bifrost`
  - تمام درخواستها را مجبور میکند از دروازه sidecar عبور کنند.
  - بازگشت خودکار ندارد.
  - تنها زمانی مفید است که سلامت و تأخیر sidecar تضمین شده باشند.
- `auto`
  - هنگامی که sidecar قابل دسترسی و فعال باشد، از آن استفاده میشود.
  - تلاشهای ناموفق، هدرهای بازگشت را فعال کرده و ترافیک را به TS بازمیگردانند تا موفقیت درخواست در محدودهای کنترلشده باقی بماند.
  - وقتی زمان کارکرد بدون وقفه مهمتر از مسیریابی صرفاً از طریق sidecar باشد، این حالت امنترین انتخاب برای محیط عملیاتی است.

## وضعیت کنونی 9router در برابر CLIPROXYAPI

9router و CLIPROXYAPI هر دو یکپارچهسازیهایی هستند که در گذشته مسیرهای سازگاری را برای ارائهدهندگان بالادستی فراهم میکردند.

- 9router مسیری تعبیهشده برای هماهنگسازی بالادستی و رفتارهای سازگاری است.
- CLIPROXYAPI یک پل API پراکسی برای ترافیک به سبک CLI / SDK است.
- Bifrost بهعنوان مسیر برونسپاریشده در حال تثبیت است تا در مواردی که به یک گام اختصاصی شبیه sidecar و ارسال محلی با تأخیر کم نیاز دارید، استفاده شود.

اگر در حال حاضر 9router/CLIPROXYAPI را مقایسه میکنید:

- امضای درخواست، بررسیهای allowlist و دروازههای سیاست DB را پیش از تحویل، در مسیر API نگه دارید.
- اگر یک گردشکار به رفتار سختگیرانه sidecar و پراکندگی کمتر بین درخواستها نیاز دارد، از `OMNIROUTE_RELAY_BACKEND=bifrost` استفاده کنید.
- اگر به تابآوری sidecar همراه با افت تدریجی و کنترلشده هنگام رخدادها نیاز دارید، از `OMNIROUTE_RELAY_BACKEND=auto` استفاده کنید.

## قرارداد مرزی بکاند

مرز پایدار محصول، API رله OmniRoute است، نه پیادهسازی داشبورد. داشبورد Next.js میتواند سرویسهای محلی را نصب، پیکربندی و نظارت کند، اما مسیریابی درخواست باید از طریق API رله وارد شود و پس از آن مرز تحویل داده شود.

گزینههای بلندمدت بکاند:

- رله TypeScript را بهعنوان مسیر درونپردازشی سیاستگذاری و بازگشت حفظ کنید. احراز هویت، allowlistها، نرمالسازی درخواست، حسابداری و بررسیهای ایمنی باید پیش از هرگونه تحویل به بکاند، در این بخش باقی بمانند.
- هنگامی که استقرار به پراکندگی کمتر در مسیریابی، چرخش متمرکز ارائهدهندگان یا مقیاسپذیری افقی در چندین نمونه OmniRoute نیاز دارد، از Bifrost بهعنوان sidecar ترجیحی Tier-1 با توان عملیاتی بالا استفاده کنید.
- 9router و CLIPROXYAPI را بهعنوان سرویسهای سازگاری تعبیهشده حفظ کنید. آنها بهصورت پردازشهای محلی تحت نظارت اجرا میشوند و وقتی رفتار ارائهدهنده/CLI آنها آداپتور موردنظر است مفید هستند، اما نباید به موتور پیشفرض مسیریابی Tier-1 تبدیل شوند.
- اجازه ندهید داشبورد URLهای دلخواه سرویس را وارد مسیر پرترافیک کند. URLهای ارائهشده از طریق UI ورودیهای پیکربندی هستند؛ کد مسیریابی باید بکاندهای ثبتشده و سلامتسنجیشده را از تنظیمات سمت سرور و وضعیت ناظر resolve کند.
- در حال حاضر HTTP روی loopback را برای سرویسهای تحت نظارت ترجیح دهید، زیرا پردازشهای مدیریتشده از قبل APIهای سازگار با HTTP ارائه میکنند، نگهبان مسیر میتواند مرز را ممیزی کند و رفتار خطا/بازگشت در گزارشهای درخواست قابل مشاهده است. افزودن انتقال مبتنی بر SDK یا socket در آینده تنها زمانی ارزشمند است که بهشکلی قابلاندازهگیری تأخیر مسیریابی p99 را کاهش دهد، بدون آنکه جداسازی یا معنای بازگشت را تضعیف کند.

بنابراین، برای یک استقرار با توان عملیاتی بسیار بالا، پاسخ پیشفرض استفاده از `auto` با Bifrost فعال است: از sidecar نوشتهشده با Go در مسیر پرترافیک استفاده کنید و در عین حال مسیر بازگشت TypeScript را برای حفظ نرخ موفقیت نگه دارید. تنها زمانی از `bifrost` استفاده کنید که رفتار سختگیرانه و صرفاً مبتنی بر sidecar از افت تدریجی و کنترلشده مهمتر باشد.

## راهنمای توان عملیاتی بالا

برای RPM/RPS بالا و پایدار همراه با SLO سختگیرانه موفقیت:

1. از `auto` همراه با یک دوره انتظار عملی و تلهمتری خطا استفاده کنید.
2. اعتبارسنجی بالادستی و بررسی کلید API را در مرز مسیر TypeScript نگه دارید.
3. هدرها/شمارندههای صریح را فعال کنید تا سامانه هشدار شما دفعات و دلایل بازگشت را مشاهده کند.
4. زمانهای انقضای sidecar را طوری تنظیم کنید که سریعاً شکست بخورد، نه اینکه برای همیشه منتظر بماند.
5. راهاندازی مجدد خودکار سرویس و حلقه تلهمتری سلامت را در وضعیت سالم نگه دارید تا بازگشت واقعاً استثنایی باشد.

## خط مبنای پیشنهادی

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- کلیدهای API، allowlist، پاکساز و بررسیهای محدودسازی نرخ را در مدیریتکنندههای مسیر فعال نگه دارید (آنها همیشه پیش از ارسال به پاییندست اجرا میشوند).
- معیارهای بازگشت را از پراکسی معکوس و گزارشهای درخواست صادر کنید تا قطعیهای sidecar ظرف یک دقیقه قابل مشاهده باشند.

## قرارداد افزونه ارائهدهنده

sidecarها باید فراداده ارائهدهنده را از طریق manifest افزونه ارائهدهنده سازگار با JSON وارد کنند، نه اینکه به اجزای داخلی اجراکننده TypeScript وابسته باشند. برای مشاهده قرارداد واجدشرایطبودن sidecar و مراحل مهاجرت، به
[Manifest افزونه ارائهدهنده](./PROVIDER_PLUGIN_MANIFEST.md) مراجعه کنید.
