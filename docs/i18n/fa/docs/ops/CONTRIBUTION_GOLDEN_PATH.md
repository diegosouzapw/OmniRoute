از این راهنما برای انتخاب کوچکترین چرخه توسعه قابلاعتماد برای یک pull request استفاده کنید. این راهنما جایگزین اسناد معماری و امنیت مختص هر حوزه که در ادامه پیوند داده شدهاند نیست؛ بلکه هر نوع تغییر رایج را به قراردادها، بررسیهای متمرکز و پوشش CI مربوط به آن متصل میکند.

## مسیری که هر تغییر طی میکند

1. **پیش از ویرایش، شاخه پایه را انتخاب کنید.** بالاترین شاخه فعال `release/v*` را پیدا کنید و از آخرین commit آن شاخه جدیدی بسازید. همان شاخه را هدف قرار دهید، نه `main`. اگر توقف انتشار فعال است، شاخه متوقفشده را هدف قرار ندهید؛ از چرخه فعال بعدی که در
   [مدل شاخهبندی و انتشار](BRANCHING_MODEL.md) توضیح داده شده است استفاده کنید.
2. **قراردادها را مشخص کنید.** همه کاتالوگها، schemaها، artifactهای تولیدشده، APIهای عمومی یا رابطهای کاربری را که تغییر بر آنها اثر میگذارد شناسایی کنید. جدول زیر حداقل مجموعه لازم برای شروع را ارائه میدهد.
3. **تستهای متمرکز را بنویسید یا بهروزرسانی کنید.** تغییرات محیط عملیاتی در `src/`، `open-sse/`، `electron/` یا
   `bin/` به یک تست خودکار در همان PR نیاز دارند. ابتدا کوچکترین فایلهای تستی را که رفتار را اثبات میکنند اجرا کنید و سپس دروازههای متمرکز فهرستشده را اجرا کنید.
4. **اجازه دهید CI ماتریس گسترده را اجرا کند.** همه shardهای تست واحد، Vitest، ratchet پوشش و build محیط عملیاتی روی PR اجرا میشوند. یک مجموعه تست گسترده را فقط زمانی بهصورت محلی اجرا کنید که شکست یک تست متمرکز نشاندهنده اثرگذاری وسیعتر باشد یا تغییر چندین زیرسیستم را در بر بگیرد.
5. **پیش از بازبینی، تغییرات را تطبیق دهید.** شاخه پایه فعال را fetch کنید، commitهای جدید آن و diff خود را در برابر آن بررسی کنید، سپس مطابق گردشکار مشارکتکنندگان، شاخه پایه را rebase یا merge کنید. تداخلهای فایلهای تولیدشده و کاتالوگها را از منبع آنها برطرف کنید، آنها را دوباره تولید کنید، چرخه متمرکز را مجدداً اجرا کنید و تأیید کنید که PR همچنان شاخه انتشار فعال را هدف قرار میدهد.
6. **شواهد را ثبت کنید.** در قالب PR، فرمانهای اجراشده، همه فایلهای تست افزوده یا تغییریافته، migrationها یا feature flagها و هر اعتبارسنجی مختص CI را که هنوز در انتظار است فهرست کنید.

## مسیرهای طلایی بر اساس نوع تغییر

فرمانهای زیر حداقل بررسیهای متمرکز هستند و مجوزی برای نادیدهگرفتن تستی که مستقیماً رفتار تغییریافته را پوشش میدهد محسوب نمیشوند.

### ارائهدهنده

**قراردادها**

- تعریف ارائهدهنده در `src/shared/constants/providers/` و ترکیب آن در
  `src/shared/constants/providers.ts`.
- مدلها و قابلیتها در `open-sse/config/providerRegistry.ts` یا فایلهای registry استخراجشده آن.
- انتخاب executor/translator، پیکربندی OAuth یا API key، assetهای dashboard و مرجع تولیدشده ارائهدهنده، در صورت کاربرد.
- credentialهای عمومی باید از `resolvePublicCred()` استفاده کنند؛ پاسخهای خطا باید از helperهای مشترک پاکسازی خطا استفاده کنند. به `docs/security/PUBLIC_CREDS.md` (در git؛ در `/docs` کامپایل نمیشود) و
  [پاکسازی خطا](../security/ERROR_SANITIZATION.md) مراجعه کنید.

**چرخه متمرکز**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # هنگامی که کاتالوگ تغییر میکند؛ diff تولیدشده را commit کنید
npm run lint
```

همچنین همه خانوادههای درخواست متأثر را تست کنید: chat، Responses، images، embeddings، audio یا video.
diffهای کاتالوگ تولیدشده و golden را بهعنوان تغییرات قرارداد بازبینی کنید؛ آنها را کورکورانه نپذیرید.

### مسیریابی

**قراردادها**

- مقادیر عمومی strategy و metadata رابط کاربری در `src/shared/constants/routingStrategies.ts`.
- dispatch و ترتیبدهی در `open-sse/services/combo.ts` و `open-sse/services/combo/`.
- schemaهای combo، persistence، وضعیت resilience، قابلیتهای مدل و کنترلهای API/UI.
- هنگام تغییر رفتار، [موتور Auto-Combo](../routing/AUTO-COMBO.md) و مستندات resilience.

**چرخه متمرکز**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # تغییرات strategy یا dispatch
npm run check:known-symbols      # تغییرات ثبت strategy
npm run lint
```

در محیط محلی از تستهای deterministic با upstream شبیهسازیشده استفاده کنید. smoke testهای زنده combo به credential نیاز دارند و دستی هستند؛ آنها جایگزین CI نیستند.

### رابط کاربری / تجربه کاربری

**قراردادها**

- route/page مربوط به Next.js و مرزهای componentهای مشترک در `src/app/` و
  `src/shared/components/`.
- شکل پاسخهای API، وضعیتهای loading/empty/error، رفتار keyboard و screen reader، چیدمان responsive، theming و گسترش locale.
- رشتههای منبع انگلیسی رابط کاربری در `src/i18n/messages/en.json`؛ متن جدیدی را که کاربر میبیند بهصورت hard-code اضافه نکنید.

**چرخه متمرکز**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

برای تغییرات تعاملی یا بصری، برنامه را اجرا کنید و هر دو viewport باریک و عریض را بررسی کنید. CI، build محیط عملیاتی و مجموعههای تست گستردهتر را اجرا میکند؛ رفتار بصری همچنان به یک component test متمرکز، Playwright یا بررسی دستی مستند و متناسب با تغییر نیاز دارد.

### i18n

**قراردادها**

- `src/i18n/messages/en.json` منبع رابط کاربری است؛ `config/i18n.json` منبع locale است.
- کاتالوگهای CLI بهصورت جداگانه در `bin/cli/locales/` قرار دارند.
- placeholderها و tagهای ICU را دقیقاً حفظ کنید. نام محصولات/ارائهدهندگان/مدلها، نام protocolها و headerها، فرمانها، identifierهای code/JSON، URLها، environment variableها یا اصطلاحات محافظتشدهای مانند `OmniRoute`، `OAuth`، `MCP` و `A2A` را ترجمه نکنید. فهرست منبع فعلی
  `scripts/i18n/glossary/protected-terms.json` است.

**چرخه متمرکز**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # هنگامی که رشتهها/کاتالوگهای CLI تغییر میکنند
npm run lint
```

این بخش راهنمایی برای سیستم موجود است، نه دعوتی برای گسترش ابزارها یا مدل key آن.
تا زمانی که سیستم جایگزین در حال طراحی است، patchهای i18n را دقیق و محدود نگه دارید. فرمانهای ترجمهای را که سرویسهای خارجی را فراخوانی میکنند اجرا نکنید، مگر اینکه task صراحتاً به ترجمههای تولیدشده نیاز داشته باشد و diff حاصل را بازبینی کرده باشید.

### CLI

**قراردادها**

- فرمانها و پرچمهای عمومی در `bin/cli/`، فرمانهای API تولیدشده، کدهای خروج، stdout/stderr و
  ساختار خروجی JSON، رفتار پیکربندی/محیط، و فایلهای بستهبندیشده.
- رشتههای قابلمشاهده برای کاربر در CLI باید از لایهٔ i18n مربوط به CLI استفاده کنند و کاتالوگهای `en`/`pt-BR` همراستا نگه داشته شوند.
- Node را بهعنوان محیط اجرای پشتیبانیشده و قرارداد باینری منتشرشده حفظ کنید.

**چرخهٔ متمرکز**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # تغییرات CLI تولیدشده/باندلشده
npm run check:pack-policy     # تغییرات سطح عمومی بسته
npm run lint
```

هنگامی که رفتار به تجزیه، فایلها یا وضعیت خروج وابسته است، فرمان دقیق را در یک دایرکتوری دادهٔ موقت اجرا کنید. CI بررسیهای گستردهتر مصنوعات بسته و زیستبوم را انجام میدهد.

### پایگاه داده

**قراردادها**

- ماژولهای دامنه در `src/lib/db/`؛ ماژولهای مشخص را مستقیماً وارد کنید (لایهٔ بازصدور قدیمی `localDb.ts` حذف شده است).
- مهاجرتهای SQL شمارهگذاریشده و ایدمپوتنت در `src/lib/db/migrations/`، ایمنی تراکنش، رفتار ارتقا،
  ایندکسها و هر فراخوانی که تحتتأثیر طرحواره قرار میگیرد.
- مسیرها و هندلرها هرگز مستقیماً SQL خام اجرا نمیکنند.

**چرخهٔ متمرکز**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

هنگام افزودن مهاجرت، هم یک پایگاه دادهٔ تازه و هم ارتقا از طرحوارهٔ قبلی را آزمایش کنید. آزمونهای پایگاه داده
باید هندلها را ببندند و هنگام پاکسازی `resetDbInstance()` را فراخوانی کنند. فقط زمانی `npm run test:bun:db` را اجرا کنید
که مسیر آداپتور Bun با پشتیبانی در حد بهترین تلاش تغییر کند؛ Node همچنان مرجع اصلی است.

### ساخت / استقرار

**قراردادها**

- مانیفستها/فایل قفل ریشه و فضای کاری، `scripts/build/`، مونتاژ مستقل Next.js، محتوای بستهٔ `dist/`،
  فرادادهٔ پلتفرم Electron، گردشکارهای CI و نشانگرهای استقرار.
- بازههای پشتیبانیشدهٔ Node و استفادهٔ مجازشدهٔ Bun در `CLAUDE.md` باید دستنخورده باقی بمانند.
- مصنوعات ساخت بدون ردیابی باقی میمانند؛ سیاستهای وابستگی، مجوز، گردشکار و بسته اعمال میشوند.

**چرخهٔ متمرکز**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # تغییرات وابستگی یا فایل قفل
npm run check:pack-policy      # تغییرات سطح عمومی بستهٔ منتشرشده
npm run lint
```

فقط زمانی `npm run build` را بهصورت محلی اجرا کنید که تغییر بر کامپایل، مونتاژ مستقل، داراییها
یا باندلسازی زمان اجرا اثر میگذارد. از `npm run build:release` فقط برای اعتبارسنجی انتشار/استقرار استفاده کنید. ساخت CI
سیگنال نهایی میانپلتفرمی است؛ تغییرات Electron مختص یک پلتفرم به ساخت متمرکز متناظر
یا شواهد آزمون دود نیاز دارند.

## چرخهٔ محلی در برابر CI

| اجرای محلی برای هر وصله                                                       | CI سیگنال گسترده را فراهم میکند                                        |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| آزمونهای مستقیم رفتار و دروازههای دستهبندیِ بالا                              | مجموعهٔ کامل آزمونهای واحد بهصورت بخشبندیشده و آزمونهای ترتیبی         |
| `npm run lint`                                                                | مجموعهآزمونهای Vitest و سازوکارهای افزایش تدریجی پوشش/کیفیت            |
| بررسی نوعها یا ساخت، فقط زمانی که قراردادِ متأثر آن را ایجاب میکند            | ساخت تولید، امنیت، مستندات، وابستگیها و دروازههای سیاست PR             |
| بررسیهای تعامل دستی/زنده، فقط زمانی که خودکارسازی نمیتواند رفتار را اثبات کند | بررسیهای یکپارچهسازی میان کارها و پلتفرم که در گردشکار پیکربندی شدهاند |

یک چرخهٔ متمرکزِ موفق، شاهدی دربارهٔ قرارداد تغییرکرده است، نه اثباتی بر اینکه بررسیهای نامرتبط CI
با موفقیت عبور خواهند کرد. از سوی دیگر، هر ویرایش محلی را نیز منتظر اجرای ماتریس کامل مخزن نگذارید.

## چکلیست تطبیق

پیش از درخواست بازبینی:

- تأیید کنید که مبنای PR همچنان بالاترین شاخهٔ فعال `release/v*` است.
- آن مبنا را دریافت کنید و commitهایی را که پس از ایجاد شاخهٔ شما اضافه شدهاند، بازبینی کنید.
- خروجی `git diff <active-base>...HEAD` را برای تغییرات ناخواسته یا تولیدشده بازبینی کنید.
- تعارضهای فهرست و مستندات تولیدشده را با بهروزرسانی منبع و تولید مجدد خروجی برطرف کنید.
- پس از تطبیق، همهٔ آزمونها/دروازههای متمرکزِ فهرستشده در توضیحات PR را دوباره اجرا کنید.
- هرگز صرفاً برای هماهنگی با مبنای جابهجاشده، assertionها را تضعیف یا آزمونهای الزامی را حذف نکنید.

برای قواعد توقف انتشار و هدفگذاری مجدد، به
[مدل شاخهبندی و انتشار](BRANCHING_MODEL.md) مراجعه کنید. برای فهرست کامل CI، از
[مرجع دروازههای کیفیت](../architecture/QUALITY_GATES.md) استفاده کنید.
