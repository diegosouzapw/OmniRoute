از این راهنما برای انتخاب کوچکترین چرخهٔ توسعهٔ قابلاعتماد برای یک درخواست کشش (PR) استفاده کنید. این راهنما
جایگزین اسناد معماری و امنیت مختص هر حوزه که در ادامه پیوند داده شدهاند نمیشود؛ بلکه هر نوع تغییر رایج را
به قراردادها، بررسیهای متمرکز و پوشش CI مرتبط میکند.

## مسیری که هر تغییر طی میکند

1. **پیش از ویرایش، شاخهٔ پایه را انتخاب کنید.** بالاترین شاخهٔ فعال `release/v*` را پیدا کنید و شاخهٔ خود را از
   آخرین commit آن بسازید. همان شاخه را هدف قرار دهید، نه `main`. اگر توقف انتشار فعال است، شاخهٔ متوقفشده را
   هدف قرار ندهید؛ از چرخهٔ فعال بعدی که در
   [مدل شاخهبندی و انتشار](BRANCHING_MODEL.md) توضیح داده شده است استفاده کنید.
2. **قراردادها را مشخص کنید.** تمام کاتالوگها، schemaها، artifactهای تولیدشده، APIهای عمومی یا رابطهای
   کاربریای را که تغییر بر آنها اثر میگذارد شناسایی کنید. جدول زیر حداقل مجموعهٔ لازم برای شروع را ارائه میدهد.
3. **تستهای متمرکز را بنویسید یا بهروزرسانی کنید.** تغییرات محصول در `src/`، `open-sse/`، `electron/` یا
   `bin/` به یک تست خودکار در همان PR نیاز دارند. ابتدا کوچکترین فایلهای تستی را اجرا کنید که رفتار را
   اثبات میکنند، سپس دروازههای متمرکز فهرستشده را اجرا کنید.
4. **اجازه دهید CI ماتریس گسترده را اجرا کند.** shardهای کامل تست واحد، Vitest، سازوکار افزایش تدریجی پوشش و
   build محصول روی PR اجرا میشوند. یک مجموعهٔ گسترده را فقط زمانی بهصورت محلی اجرا کنید که شکست یک تست متمرکز
   از تأثیر گستردهتر خبر میدهد یا تغییر چندین زیرسامانه را در بر میگیرد.
5. **پیش از بازبینی، تغییرات را همگامسازی کنید.** شاخهٔ پایهٔ فعال را fetch کنید، commitهای جدید آن و تفاوتهای
   خود با آن را بررسی کنید، سپس مطابق گردشکار مشارکتکنندگان، شاخهٔ پایه را rebase یا merge کنید. تعارضهای
   فایلهای تولیدشده و کاتالوگها را از منبعشان رفع کنید، آنها را دوباره تولید کنید، چرخهٔ متمرکز را مجدداً اجرا کنید و تأیید کنید که
   PR همچنان شاخهٔ انتشار فعال را هدف قرار میدهد.
6. **شواهد را ثبت کنید.** در قالب PR، فرمانهای اجراشده، تمام فایلهای تست افزودهشده یا تغییریافته،
   migrationها یا feature flagها و هرگونه اعتبارسنجی مختص CI را که هنوز در انتظار است فهرست کنید.

## مسیرهای طلایی بر اساس نوع تغییر

فرمانهای زیر حداقل بررسیهای متمرکز هستند و مجوزی برای نادیده گرفتن تستی که مستقیماً رفتار
تغییریافته را پوشش میدهد محسوب نمیشوند.

### ارائهدهنده

**قراردادها**

- تعریف ارائهدهنده در `src/shared/constants/providers/` و ترکیب آن در
  `src/shared/constants/providers.ts`.
- مدلها و قابلیتها در `open-sse/config/providerRegistry.ts` یا فایلهای registry استخراجشدهٔ آن.
- انتخاب executor/translator، پیکربندی OAuth یا کلید API، assetهای داشبورد و مرجع تولیدشدهٔ
  ارائهدهنده، در صورت کاربرد.
- اعتبارنامههای عمومی باید از `resolvePublicCred()` استفاده کنند؛ پاسخهای خطا باید از helperهای مشترک
  پاکسازی خطا استفاده کنند. به `docs/security/PUBLIC_CREDS.md` (در git؛ در `/docs` کامپایل نمیشود) و
  [پاکسازی خطا](../security/ERROR_SANITIZATION.md) مراجعه کنید.

**چرخهٔ متمرکز**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # وقتی کاتالوگ تغییر میکند؛ تفاوت تولیدشده را commit کنید
npm run lint
```

همچنین هر خانوادهٔ درخواست متأثر را تست کنید: chat، Responses، images، embeddings، audio یا video.
تفاوتهای کاتالوگ تولیدشده و golden را بهعنوان تغییرات قرارداد بازبینی کنید؛ آنها را کورکورانه نپذیرید.

### مسیریابی

**قراردادها**

- مقادیر عمومی strategy و metadata رابط کاربری در `src/shared/constants/routingStrategies.ts`.
- dispatch و ترتیبدهی در `open-sse/services/combo.ts` و `open-sse/services/combo/`.
- schemaهای combo، ماندگاری، وضعیت تابآوری، قابلیتهای مدل و کنترلهای API/رابط کاربری.
- [موتور Auto-Combo](../routing/AUTO-COMBO.md) و مستندات تابآوری، هنگامی که رفتار تغییر میکند.

**چرخهٔ متمرکز**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # تغییرات strategy یا dispatch
npm run check:known-symbols      # تغییرات ثبت strategy
npm run lint
```

بهصورت محلی از تستهای قطعی با upstream شبیهسازیشده استفاده کنید. smoke testهای زندهٔ combo به اعتبارنامه نیاز دارند و
دستی هستند؛ آنها جایگزین CI نیستند.

### رابط کاربری / تجربهٔ کاربری

**قراردادها**

- مرزهای route/page در Next.js و componentهای مشترک در `src/app/` و
  `src/shared/components/`.
- شکل پاسخهای API، وضعیتهای loading/empty/error، رفتار صفحهکلید و صفحهخوان،
  چیدمان واکنشگرا، پوستهبندی و گسترش locale.
- رشتههای مبدأ انگلیسی رابط کاربری در `src/i18n/messages/en.json`؛ متن جدید قابلمشاهده برای کاربر را hard-code نکنید.

**چرخهٔ متمرکز**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

برای تغییرات تعاملی یا بصری، برنامه را اجرا کنید و viewportهای باریک و عریض را بررسی کنید. CI
build محصول و مجموعهتستهای گستردهتر را اجرا میکند؛ رفتار بصری همچنان به یک component test متمرکز، Playwright
یا بررسی دستی مستندشده و متناسب با تغییر نیاز دارد.

### بینالمللیسازی

**قراردادها**

- `src/i18n/messages/en.json` منبع رابط کاربری است؛ `config/i18n.json` منبع locale است.
- کاتالوگهای CLI بهطور جداگانه در `bin/cli/locales/` قرار دارند.
- placeholderها و tagهای ICU را دقیقاً حفظ کنید. نامهای محصول/ارائهدهنده/مدل،
  نامهای protocol و header، فرمانها، شناسههای code/JSON، URLها، متغیرهای محیطی یا
  اصطلاحات محافظتشدهای مانند `OmniRoute`، `OAuth`، `MCP` و `A2A` را ترجمه نکنید. فهرست فعلی منبع
  `scripts/i18n/glossary/protected-terms.json` است.

**چرخهٔ متمرکز**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # وقتی رشتهها/کاتالوگهای CLI تغییر میکنند
npm run lint
```

این دستورالعمل برای سیستم موجود است، نه دعوتی برای گسترش ابزارها یا مدل کلید آن.
تا زمانی که سیستم جایگزین در حال طراحی است، patchهای بینالمللیسازی را محدود و دقیق نگه دارید. فرمانهای ترجمهای را
که سرویسهای خارجی را فراخوانی میکنند اجرا نکنید، مگر اینکه وظیفه صراحتاً به ترجمههای تولیدشده نیاز داشته باشد و
تفاوت حاصل را بازبینی کرده باشید.

### CLI

**قراردادها**

- فرمانها و فلگهای عمومی در `bin/cli/`، فرمانهای API تولیدشده، کدهای خروج، stdout/stderr و
  ساختارهای خروجی JSON، رفتار پیکربندی/محیط و فایلهای بستهبندیشده.
- رشتههای قابلمشاهده برای کاربر در CLI باید از لایهٔ i18n مربوط به CLI استفاده کنند و کاتالوگهای `en`/`pt-BR` را همگام نگه دارند.
- Node را بهعنوان محیط اجرای پشتیبانیشده و قرارداد باینری منتشرشده حفظ کنید.

**چرخهٔ متمرکز**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # تغییرات CLI تولیدشده/باندلشده
npm run check:pack-policy     # تغییرات سطح بسته
npm run lint
```

وقتی رفتار به تجزیه، فایلها یا وضعیت خروج وابسته است، فرمان دقیق را در یک دایرکتوری دادهٔ موقت اجرا کنید. CI بررسیهای گستردهتر مصنوعات بسته و اکوسیستم را انجام میدهد.

### پایگاه داده

**قراردادها**

- ماژولهای دامنه در `src/lib/db/`؛ ماژولهای مشخص را مستقیماً import کنید (لایهٔ قدیمی بازصدور `localDb.ts` حذف شده است).
- مهاجرتهای SQL شمارهگذاریشده و ایدمپوتنت در `src/lib/db/migrations/`، ایمنی تراکنش، رفتار
  ارتقا، ایندکسها و تمام فراخوانهایی که از طرحواره تأثیر میپذیرند.
- مسیرها و هندلرها هرگز SQL خام را مستقیماً اجرا نمیکنند.

**چرخهٔ متمرکز**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

هنگام افزودن یک مهاجرت، هم یک پایگاه دادهٔ تازه و هم ارتقا از طرحوارهٔ قبلی را آزمایش کنید. تستهای پایگاه داده
باید هندلها را ببندند و هنگام پاکسازی `resetDbInstance()` را فراخوانی کنند. تنها زمانی `npm run test:bun:db` را اجرا کنید که
مسیر آداپتور Bun با ماهیت best-effort تغییر کرده باشد؛ Node همچنان مرجع اصلی است.

### ساخت / استقرار

**قراردادها**

- مانیفستها/فایل قفل ریشه و فضای کاری، `scripts/build/`، مونتاژ مستقل Next.js، محتوای بستهٔ `dist/`،
  فرادادهٔ پلتفرم Electron، گردشکارهای CI و نگهبانهای استقرار.
- بازههای پشتیبانیشدهٔ Node و استفادهٔ مجازشده از Bun در `CLAUDE.md` باید بدون تغییر باقی بمانند.
- مصنوعات ساخت همچنان ردیابینشده باقی میمانند؛ سیاستهای وابستگی، مجوز، گردشکار و بسته اعمال میشوند.

**چرخهٔ متمرکز**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # تغییرات وابستگی یا فایل قفل
npm run check:pack-policy      # تغییرات سطح بستهٔ منتشرشده
npm run lint
```

تنها زمانی از `npm run build` بهصورت محلی استفاده کنید که تغییر بر کامپایل، مونتاژ مستقل، داراییها
یا باندلکردن زمان اجرا تأثیر بگذارد. از `npm run build:release` فقط برای اعتبارسنجی انتشار/استقرار استفاده کنید. ساخت CI
نشانگر نهایی چندسکویی است؛ تغییرات Electron ویژهٔ هر پلتفرم به ساخت متمرکز متناظر
یا شواهد آزمون دود نیاز دارند.

## چرخهٔ محلی کاندیدا

آزمونهای کد منبع نمیتوانند ثابت کنند که آرتیفکت بستهبندیشده راهاندازی میشود: فهرستهای بستهبندی، وابستگیهای حذفشده،
و باینریهای بومی فقط پس از نصب و اجرای tarball با شکست مواجه میشوند. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) بخش محلی جریان یکبار ساختن / اعتبارسنجی / ارتقا از
RFC #8084 است: یک کاندیدا میسازد، دقیقاً همان آرتیفکت را اعتبارسنجی میکند، آن را با تغییر نام
دایرکتوریها ارتقا میدهد، و اگر بررسی سلامت اسلات ارتقایافته ناموفق باشد، آن را بازمیگرداند.

```bash
npm run dev:candidate -- run --dry-run --json  # نمایش برنامه، بدون ایجاد هیچ تغییری
npm run dev:candidate -- run                   # ساخت + اعتبارسنجی + ارتقا، بازگردانی خودکار
npm run dev:candidate -- build                 # npm pack + نصب در _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # راهاندازی روی یک پورت آزاد، /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current، current → previous
npm run dev:candidate -- rollback              # جابهجایی current و previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # استفادهٔ مجدد از tarball ساختهشده در جایی دیگر (CI)
```

- **فقط یکبار بسازید.** `build` درخت فعلی را بستهبندی میکند (به `dist/server.js` نیاز دارد، بنابراین ابتدا
  `npm run build:release` را اجرا کنید) یا `--from-tarball` را کپی میکند، سپس tarball را در یک
  پیشوند مجزای npm نصب میکند، زیرا tarball شامل `node_modules` نیست. شناسه، sha کوتاه `HEAD`
  است (`-dirty` زمانی که درخت دارای تغییرات محلی باشد) یا برای یک tarball بهصورت `tgz-<sha256>` خواهد بود. یک شناسهٔ پاک که
  از قبل ساخته شده باشد، بهجای ساخت مجدد دوباره استفاده میشود؛ برای ساخت مجدد آن، `--force` را ارسال کنید.
- **بسته را اعتبارسنجی کنید، نه کد منبع را.** `validate` رابط خط فرمان نصبشده را
  (`serve --port <free port>`) با یک `DATA_DIR=<candidate>/data` تازه، اسرار جعلی، و با حذف
  `OMNIROUTE_API_KEY`، `STORAGE_ENCRYPTION_KEY` و `INITIAL_PASSWORD` متعلق به اپراتور از
  محیط اجرا میکند تا وضعیت loopback بدون کلید یک نصب تازه را بررسی کند. منتظر میماند تا
  `GET /api/health` کد 200 را برگرداند، الزام میکند که `GET /v1/models` نیز کد 200 را برگرداند، گروه پردازه را متوقف میکند،
  و نتیجه را همراه با هش tarball در `validation.json` ثبت میکند.
- **همان آرتیفکت را ارتقا دهید.** `promote` کاندیدایی را که برای هش فعلی tarball خود
  اعتبارسنجی موفقی ندارد، نمیپذیرد. اسلات فعال پیشفرض `_artifacts/candidate/current` است؛ `--target <dir>`
  دایرکتوری دیگری را روی همان فایلسیستم انتخاب میکند و اسلات قبلی آن `<dir>.previous` است.
  هر تغییر نام اتمی است و اگر در میانهٔ عملیات شکستی رخ دهد، تغییر نامهایی که از قبل اجرا شدهاند معکوس میشوند.
- **بازگردانی کنید.** `run` اسلات ارتقایافته را دوباره اعتبارسنجی میکند و اگر
  آن بررسی ناموفق باشد، `current` و `previous` را به حالت قبل جابهجا میکند. کاندیدایی که در اعتبارسنجی اول شکست بخورد، هرگز ارتقا داده نمیشود.

همهچیز در `_artifacts/candidate/` که توسط git نادیده گرفته میشود نوشته خواهد شد؛ نصب موجود OmniRoute
و دایرکتوری دادهٔ آن هرگز دستکاری نمیشوند. رابط خط فرمان ارتقایافته در
`_artifacts/candidate/current/prefix/bin/omniroute` قرار دارد؛ هنگام استفاده، آن را با `DATA_DIR` خودتان
راهاندازی کنید. کدهای خروج: `0` موفقیت، `1` شکست اعتبارسنجی یا ارتقا، `2` خطای نحوهٔ استفاده یا نبود build.

## چرخهٔ محلی در برابر CI

| اجرا بهصورت محلی برای هر وصله                                              | CI سیگنال گسترده را فراهم میکند                                         |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| آزمونهای مستقیم رفتار و دروازههای دستهبندی بالا                            | مجموعهٔ کامل آزمونهای واحد بهصورت تقسیمشده و آزمونهای سریالی            |
| `npm run lint`                                                             | مجموعهآزمونهای Vitest و ضامنهای پوشش/کیفیت                              |
| بررسی نوع یا ساخت، فقط زمانی که قرارداد متأثر آن را ایجاب میکند            | ساخت تولید، امنیت، مستندات، وابستگیها و دروازههای سیاست PR              |
| تعامل دستی/بررسی زنده، فقط زمانی که خودکارسازی نمیتواند رفتار را اثبات کند | بررسیهای یکپارچهسازی بین وظایف و پلتفرم که توسط گردشکار پیکربندی شدهاند |

یک چرخهٔ متمرکز موفق، شاهدی دربارهٔ قرارداد تغییریافته است، نه اثباتی بر اینکه بررسیهای نامرتبط CI
با موفقیت عبور خواهند کرد. از سوی دیگر، هر ویرایش محلی را منتظر اجرای کامل ماتریس مخزن نگذارید.

## چکلیست تطبیق

پیش از درخواست بازبینی:

- تأیید کنید که مبنای PR همچنان بالاترین شاخهٔ فعال `release/v*` است.
- آن مبنا را واکشی کنید و commitهایی را که از زمان ایجاد شاخهٔ شما اضافه شدهاند بازبینی کنید.
- خروجی `git diff <active-base>...HEAD` را برای تغییرات ناخواسته یا تولیدشده بررسی کنید.
- تعارضهای کاتالوگ و اسناد تولیدشده را با بهروزرسانی منبع و تولید مجدد خروجی برطرف کنید.
- پس از تطبیق، همهٔ آزمونها/دروازههای متمرکز فهرستشده در توضیحات PR را دوباره اجرا کنید.
- هرگز صرفاً برای انطباق با مبنای جابهجاشده، assertionها را تضعیف یا آزمونهای الزامی را حذف نکنید.

برای قوانین توقف انتشار و تغییر هدف، به
[مدل شاخهبندی و انتشار](BRANCHING_MODEL.md) مراجعه کنید. برای فهرست کامل CI، از
[مرجع دروازههای کیفیت](../architecture/QUALITY_GATES.md) استفاده کنید.
